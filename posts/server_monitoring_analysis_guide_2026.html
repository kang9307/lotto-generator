이 글은 kciter 가 2026-07-20 에 쓴 「서버 모니터링 분석 가이드」의 주장과 구조만을 해설한다. 수치와 사례는 모두 그 글에 있는 것이며, 원문 밖 일반론은 「원문에는 없다」고 구분해 표시한다. 어떤 도구의 사용법도 원문에 없으므로 다루지 않는다.

원문의 뼈대 - 증상을 먼저, 원인은 그다음

모니터링 글은 대시보드를 만드는 방법을 다루는 것이 대부분이고, 만들어 놓은 그래프를 읽고 해석하는 방법을 다루는 글은 드물다. 원문은 이 빈자리를 겨냥한다. 그래프를 읽고 진단하고 행동하는 법이 주제다. 이 글은 원문의 흐름을 따라 「무엇을 어떤 순서로 보고 어떤 결론에 이르는가」를 한 편의 절차로 다시 배열한다.

원문의 출발점은 지표를 네 가지로 묶는 틀이다. Google SRE 에서 온 네 가지 골든 시그널, 곧 트래픽, 지연 시간, 오류, 포화도다. 여기에 이어지는 핵심 구분이 증상과 원인이다. 지연과 오류는 사용자가 겪는 증상이고, CPU·메모리·스레드 풀·커넥션 풀은 인프라의 상태, 곧 원인 후보다. 원문의 문장은 「증상을 먼저 파악하고 원인으로 범인을 좁혀야 한다」이다.

  • 트래픽. 시스템에 들어오는 요청의 양이다. 이후의 모든 지표를 나누는 분모 역할을 한다.
  • 지연 시간. 요청에서 응답까지 걸리는 시간이다. 사용자가 느끼는 느림이 여기에 나타난다.
  • 오류. 실패한 요청의 비율이다. 사용자가 겪는 실패가 여기에 나타난다.
  • 포화도. 자원이 얼마나 차 있는가다. 원인 후보를 좁히는 쪽의 지표이며, 뒤에서 다룰 CPU·풀·큐가 여기에 속한다.

이 구분은 알람 설계에도 이어진다. 원문은 「CPU 80%」 같은 임의의 자원 임계값에 알람을 걸면 거짓 경보가 많고, 오류율이 임계값을 넘는 것처럼 증상에 알람을 걸어야 실제 사용자 영향과 맞아떨어진다고 한다. 자원 지표는 혼자 읽으면 거짓말을 한다는 것이 뒤따르는 절들의 공통 전제다.

트래픽 - 얼마나 들어오는가

첫 번째 질문은 얼마나 들어오고 있는가다. 특별한 행사가 없는 서비스는 일정한 트래픽 모양을 유지한다. 원문은 그 평소의 모양을 익혀 두는 것이 이상을 알아보는 전제라고 한다. 지표가 평소의 절반이라면 정상 범위 안이라도 무언가 잘못된 것이라는 문장이 그 예다.

  • 수직 하락. 요청이 서버에 도달하지 못한다는 신호다. 로드밸런서, DNS, 게이트웨이 같은 상류의 문제를 의심한다. 직관과 어긋나게 이 순간 서버 쪽 지표는 깨끗하다.
  • 수직 급등. 갑작스러운 몰림이다. 화제가 된 경우, 크롤러 접근, 공격이 후보이고, 주기적으로 반복되는 급등이라면 배치 작업이나 크론을 떠올린다.
  • 분모로서의 트래픽. 같은 500건의 오류도 하루 100만 건 중이냐 1,000건 중이냐로 뜻이 전혀 다르다. 오류는 개수가 아니라 트래픽 대비 비율로 읽는다.

이 절이 주는 절차는 단순하다. 다른 지표를 열기 전에 요청량의 모양이 평소와 같은지부터 본다. 요청량이 꺾였다면 서버 안을 뒤지는 일은 뒤로 미룬다.

지연 - 평균이 감추는 것

두 번째 질문은 얼마나 걸리는가다. 원문은 평균 응답 시간이 분포의 모양을 감춘다고 말한다. 평균이 똑같이 100ms 인 두 서버가 전혀 다른 성능 특성을 가질 수 있기 때문이다. 그래서 백분위수를 쓴다. P50 은 전형적인 사용자의 경험이고, P95 와 P99 는 목표를 정하고 조기 경보를 잡는 데 쓴다. 원문은 이상 징후가 거의 항상 P99 에 먼저 나타난다고 한다.

  • 규모로 환산하기. 초당 1,000건이면 P99 는 초당 10명이 느린 응답을 받는다는 뜻이고, 하루로는 86만 4천 건이다. 1퍼센트는 작은 숫자가 아니다.
  • 호출이 곱해지는 문제. 화면 하나를 그리는 데 40번이 넘는 API 호출이 쓰이는 서비스에서, 호출마다 99퍼센트가 목표 시간 안에 끝난다고 해도 40번이 모두 목표 안에 끝날 확률은 약 67퍼센트로 떨어진다.
  • 꼬리의 주인. 데이터를 많이 쌓은 헤비 유저는 자연히 느린 꼬리에 들어간다. 원문은 P99 가 서비스의 최우수 고객이 겪는 응답 시간일 가능성이 높다고 표현한다.

같은 주제를 서버가 여러 대일 때의 집계 문제로 넓힌 글은 서버 10대의 p99 를 평균했다에서 다뤘다. 이 글에서는 P99 를 읽는 이유까지만 원문을 따른다.

오류 - 빠른 실패와 느린 실패

세 번째 질문은 얼마나 실패하는가다. 원문은 상태 코드부터 나눈다. 5xx 는 서버 쪽 실패이므로 언제나 우려 대상이다. 4xx 는 클라이언트의 잘못된 요청이지만, 옛 앱과 새 서버의 버전이 어긋나 API 계약이 깨진 신호일 수도 있다. 그다음 구분이 실패의 속도다.

  • 느린 실패. 타임아웃처럼 몇 초를 기다린 뒤 실패하는 유형이다. 기다리는 동안 스레드와 커넥션을 붙잡으므로 오류와 포화가 동시에 나타난다.
  • 빠른 실패. connection refused 나 죽은 의존 서비스에서 온 null 참조처럼 밀리초 안에 실패하는 유형이다. 자원 사용률은 멀쩡하게 유지된다.
  • 생존자 편향. 오류율이 치솟는데 P99 는 오히려 좋아 보이는 역설이 있다. 즉시 실패한 요청이 밀리초짜리 표본으로 섞여 들어오기 때문이다. 이때 지연 그래프만 보면 안심하게 된다.

이 절의 절차는 오류가 늘면 실패가 빠른지 느린지를 먼저 가르는 것이다. 빠른 실패면 자원 지표가 아니라 의존 대상의 생사를 본다. 느린 실패면 다음 절의 자원과 풀 지표로 내려간다.

증상별 진단표 - 먼저 볼 지표와 다음 행동

원문은 여러 지표의 조합으로 원인을 가르는 짧은 진단 조합을 제시한다. 아래 표는 그 조합에 앞 절들의 규칙을 더해 독자가 바로 쓸 수 있는 형태로 정리한 것이다. 첫 여섯 행은 원문의 조합표에 있는 것이고, 나머지 행은 원문의 개별 서술에서 옮겼다. 「다음 행동」은 원문이 제시한 확인 대상을 그대로 쓴다.

증상먼저 볼 지표해석다음 행동
P99 급등과 CPU 급등이 함께 나타남트래픽과부하이거나 코드 결함트래픽이 평소면 코드 쪽을 점검

이 표에서 가장 값싼 분기는 「모두 느린가, 일부만 느린가」다. 원문은 이 구분 하나가 용의 선상을 절반으로 줄인다고 한다. 표를 그대로 외우기보다 증상 열의 순서, 곧 요청량, 지연, 오류를 먼저 확정한 뒤에 두 번째 열로 넘어가는 흐름을 몸에 익히는 것이 이 표의 쓰임이다.

표에서 여러 행이 동시에 들어맞을 때는 원문의 가설 주도 조사를 따른다. 스무 개의 그래프를 훑는 대신 가설을 하나 세우고, 그것을 확인하거나 반박할 그래프 하나를 본다. 원문의 예는 「DB 가 느리다면 커넥션 대기가 높을 것이다」이다. 확인되면 증상 체크리스트의 다음 항목으로 가고, 반박되면 다음 가설로 넘어간다. 이렇게 하면 대시보드를 목적 없이 돌아다니는 시간이 줄어든다.

자원 지표 - CPU와 메모리를 혼자 읽지 않는다

원문의 문장은 「리소스 지표는 혼자 읽으면 거짓말을 한다」이다. CPU 는 반드시 지연과 겹쳐서 읽는다. 원문은 CPU 패턴과 지연의 조합으로 세 가지 경우를 든다.

CPU 의 모양지연원문의 진단
완만하게 상승낮고 안정적정상적인 확장. 지켜본다
20~30% 수준치솟음I/O 대기. DB 지연, 락, 풀 고갈, 타임아웃. CPU 가 아니라 막힌 자원을 본다
100% 에 평평하게 붙음높음용량 초과이거나 무한 루프. 트래픽이 평소면 코드를 검토한다

컨테이너 환경에는 이 표가 놓치는 함정이 하나 더 있다고 원문은 말한다. 쿠버네티스의 CPU 제한이 만드는 스로틀링이다. 컨테이너는 기본 100ms 주기마다 CPU 시간 쿼터를 받고, 0.5코어 제한이면 주기당 50ms 다. 쿼터를 다 쓰면 다음 주기까지 강제로 멈춘다. 그런데 CPU 사용률 그래프에는 멈춘 시간이 나타나지 않으므로 사용률은 정상인데 P99 꼬리만 길어진다.

  • 정상 신호, 톱니. JVM 이나 Node.js 처럼 GC 가 있는 런타임에서 메모리가 올라갔다 GC 로 급격히 내려오는 톱니는 심장 박동과 같은 정상 패턴이다.
  • 누수는 바닥을 본다. 봉우리가 아니라 골짜기를 본다. 골짜기가 수평이면 정상이고, 계단처럼 슬금슬금 올라가면 GC 가 회수하지 못하는 객체가 매번 남는다는 신호다.
  • 계단 모양의 급등. 톱니 위로 수직 점프하면 대량 데이터를 한꺼번에 메모리에 올린 것이다. 전체 테이블 조회, 큰 파일 처리, 엑셀 다운로드가 예로 나온다. OOM 이 나기 전에 페이지네이션이나 스트리밍으로 바꾼다.

풀과 큐 - 동시 처리 수의 산수

원문의 산수 하나가 이 절의 중심이다. 리틀의 법칙, 곧 동시에 처리 중인 요청 수는 초당 유입량에 평균 처리 시간을 곱한 것이다. 초당 1,000건이 들어오고 평균 처리에 50ms 가 걸리면 동시 요청은 50개이고 스레드 200개짜리 풀로 충분하다. 그런데 DB 가 느려져 평균이 2초가 되면 동시 요청은 1,000에 2를 곱한 2,000개가 되어 풀이 바닥나고 1,800개가 줄을 선다. 트래픽은 그대로인데 시스템이 무너진다.

  • 연쇄 붕괴. 모든 스레드가 DB 를 기다리면 새 요청을 처리할 스레드가 없다. 헬스 체크가 타임아웃하고, 로드밸런서가 서버를 빼고, 남은 서버가 더 많은 트래픽을 받아 더 빨리 무너진다. 느린 쿼리 하나가 클러스터 전체의 장애로 번진다.
  • 재시도 폭풍. 클라이언트가 실패한 요청을 다시 보내면 트래픽이 2~3배로 늘어 회복할 틈을 막는다.
  • 풀 자체보다 기울기. 스레드 풀 사용량은 절대값보다 기울기를 본다. 트래픽에 따라 완만하게 오르면 정상이고, 수직으로 오르면 다른 곳의 지연이 대기를 만든 것이다.
  • 이벤트 루프 서버. Node.js 나 WebFlux 는 요청마다 스레드를 두지 않고 하나의 실행 스레드가 루프를 돈다. 한 곳이 막히면 프로세스 전체가 멈춘다. 지표는 이벤트 루프 지연이며, 평균이 아니라 최댓값이나 P99 로, 절대 기준이 아니라 평소 대비 추세로 읽는다. 8개 프로세스의 평균 CPU 40% 가 100% 짜리 하나를 숨길 수 있으므로 프로세스별 최댓값을 본다.

커넥션 풀에서도 같은 원리가 나온다. 원문의 예는 HikariCP 기본값 10개 커넥션에 애플리케이션 스레드 200개다. DB 가 느려지면 커넥션 타임아웃 오류가 난다. 잘못된 대응은 풀 크기를 늘리는 것이고, 옳은 대응은 「왜 반납이 느려졌는가」를 묻는 것이다. 원문의 문장은 「원인은 대개 풀 자체가 아니라 어딘가의 지연이다」이다.

병목·포화·캐시·타임아웃 - 두 그래프가 어긋날 때

여러 지표가 함께 움직일 때 원문이 주는 마지막 도구 몇 가지가 있다. 첫째는 병목의 모양이다. 병목이 되는 곳 앞은 대기가 쌓이고 그 뒤는 한가하다. 시스템의 처리량은 가장 약한 고리가 정한다. 둘째는 포화 곡선이 직선이 아니라는 점이다. 사용률이 오를수록 대기 시간은 비선형으로 불어난다.

사용률대기 시간(기준 대비)원문의 해석
50%1배기준
80%4배여기서부터 가파르다
90%9배아직 10% 남았다는 생각은 위험하다
95%19배남은 5% 는 대기 시간 19배로 돌아온다
  • 큐는 공짜가 아니다. 큐는 일시적인 몰림을 흡수할 때는 건강하지만, 유입이 처리량을 계속 넘으면 지연의 빚이 된다. 처리량이 초당 100건일 때 100개가 쌓이면 다음 요청은 1초, 1만 개가 쌓이면 100초를 더 기다린다. 이미 클라이언트가 포기한 요청에 자원을 쓰는 일도 생긴다.
  • 배압과 로드 셰딩. 큐 길이가 회복 없이 계속 오르면 흐름 제어가 없다는 신호다. 큐가 넘칠 때 429 로 명시적으로 거절하면, 모두가 조금씩 느려지는 대신 일부는 빨리 실패하고 나머지는 정상 처리된다.
  • 캐시 히트율이 무너질 때. 히트율 97퍼센트는 DB 가 트래픽의 3퍼센트만 받는다는 뜻이고, 캐시가 무너지면 DB 는 30배가 넘는 부하를 받는다. 인기 키의 TTL 이 만료될 때 수백 요청이 동시에 DB 로 가는 것이 캐시 스탬피드다. DB 부하 급증 시각과 히트율 하락 시각이 겹치는지 먼저 본다.
  • 타임아웃 불일치. 게이트웨이 타임아웃이 3초, 백엔드 쿼리 타임아웃이 5초라면 사용자는 3초에 504 를 받는데 백엔드는 5초에 조용히 성공을 기록한다. 백엔드 지표에는 오류가 없고 게이트웨이에는 504 가 있는 모순이 생긴다. 해법은 안쪽으로 갈수록 줄이는 타임아웃 예산이다. 원문의 예는 게이트웨이 3초, HTTP 클라이언트 2.5초, DB 2초다.

이 절의 진단 규칙은 하나로 모인다. 한 계층은 오류인데 다음 계층은 성공이라는 모순이 보이면 타임아웃 정렬을 먼저 의심한다.

타임아웃 예산의 목적은 안쪽 계층이 바깥 계층보다 먼저 깔끔하게 실패하게 만들어 오류가 위로 제대로 전달되게 하는 것이다. 바깥이 먼저 포기하면 안쪽은 아무도 읽지 않을 응답을 계속 만들며 과부하 중에도 CPU 와 커넥션을 쓴다. 3초, 2.5초, 2초라는 값은 원문의 예이므로 자기 서비스의 값은 실제 응답 분포를 보고 정해야 하며, 원문은 서비스별 값을 제시하지 않았다.

시간축 세 가지 - 평시, 배포 직후, 장애 중과 그 뒤

원문은 같은 그래프도 언제 보느냐에 따라 읽는 법이 다르다고 정리한다. 평시에는 기준선을 배우고, 배포 직후에는 30분을 조심하고, 장애 중에는 복구가 원인 분석보다 앞선다.

  • 평시의 5분. 하루 5분씩 대시보드를 한 바퀴 돈다. 트래픽 모양, CPU 리듬, 정상 P99 범위를 익히면 「평소를 모르면 무언가 이상하다는 것도 알아볼 수 없다」는 문장이 뜻하는 문제가 사라진다. 기준선을 넘으면 알람이 울리게 설정한다. 하루 1퍼센트씩 4주 나빠지는 변화는 알람이 울리지 않으므로, 오늘의 P99 를 지난주 같은 요일과 겹쳐 놓는 패널이 필요하다.
  • 배포 직후 30분. 배포 시각을 그래프에 표식으로 남긴다. 「배포 전인가 후인가」에 답하는 데 다른 정보가 필요 없어지고 비용 대비 효과가 가장 크다고 원문은 말한다. 새 프로세스는 JIT 컴파일 미완료, 로컬 캐시 비어 있음, 커넥션 풀 재구성 때문에 P99 가 일시적으로 두 배가 되기도 한다. 몇 분에 걸쳐 회복하면 워밍업이고 10분 넘게 높으면 회귀다.
  • 롤백 기준과 카나리. 배포 후 오류율이 X퍼센트를 넘거나 P99 가 10분 안에 회복 추세를 보이지 않으면 토론 없이 롤백한다는 식의 기준을 미리 합의한다. 카나리는 서버 한두 대에 먼저 배포하고 같은 트래픽 조건에서 카나리와 안정판을 버전 레이블로 나눠 나란히 비교한다.
  • 장애 중과 그 뒤. 먼저 범위를 확정한다. 전체인지, 특정 API 인지, 특정 지역이나 고객인지다. 그다음 최근 30분에서 몇 시간 안의 변경, 곧 배포, 설정, 기능 플래그, 인프라 작업, 마케팅 유입을 찾는다. 복구가 먼저다. 롤백, 재시작, 스케일 아웃, 플래그로 기능 끄기 순이고, 증거인 지표·로그·힙 덤프는 복구 뒤에도 남는다. 사후 분석은 첫 증상, 알람, 사람의 대응 시작, 복구의 네 시각으로 타임라인을 그리고, 감지의 공백과 대응 속도의 공백을 액션 아이템으로 바꾼다. 원인 서술에 사람을 적지 않는다.

이 절의 절차 요약은 세 줄이다. 평시에는 기준선을 만들고, 배포 뒤에는 회복 여부로 워밍업과 회귀를 가르며, 장애 중에는 복구를 먼저 하고 가설 하나에 그래프 하나로 확인한다.

독자의 서버에 적용하는 여섯 단계

아래 여섯 단계는 원문의 흐름을 독자가 자기 서버에서 반복할 수 있는 순서로 옮긴 것이다. 각 단계의 근거는 앞 절들에 있다.

  1. 요청량의 모양을 본다. 평소와 같은가, 수직으로 꺾였는가, 급등했는가. 꺾였다면 서버 내부보다 상류를 먼저 본다.
  2. 지연을 백분위수로 읽는다. 평균이 아니라 P50, P95, P99 를 본다. 특정 API 만 느린지, 모두 느린지를 가른다.
  3. 오류를 비율로 읽고 속도를 가른다. 개수가 아니라 트래픽 대비 비율로 보고, 빠른 실패인지 느린 실패인지 구분한다.
  4. 자원 지표를 지연 위에 겹친다. CPU 가 낮은데 지연이 높으면 대기를, CPU 가 평평하게 붙으면 용량이나 루프를 의심한다. 컨테이너라면 스로틀링도 후보에 올린다.
  5. 대기가 쌓이는 자리를 찾는다. 풀, 큐, 캐시 히트율, 타임아웃 정렬을 본다. 병목 앞은 대기가 쌓이고 뒤는 한가하다.
  6. 최근 변경과 기준선을 대조한다. 배포 표식과 지난주 같은 요일 패널을 놓고, 회복하지 않으면 사전에 합의한 기준으로 롤백한다.

원문의 결론 체크리스트는 이 여섯 단계를 네 문장으로 줄인다. 얼마나 들어오고, 얼마나 걸리고, 얼마나 실패하고, 무엇이 차 있는가다. 알람이 울리면 멈추고 이 네 가지를 묻는다.

아래 세 줄은 원문에는 없는 것이다. 위 순서 가운데 자원 지표를 셸에서 읽기 전용으로 살피고 싶을 때 쓸 수 있는 무부하 명령이며, 원문이 이 명령을 권한 것은 아니다. 시스템 부하 평균, 프로세스 대기와 CPU 상태 표본, 디스크 사용량을 각각 읽기만 한다.

# 원문에는 없음: 읽기 전용, 무부하
                    uptime
                    vmstat 1 5
                    df -h

이 명령들의 출력을 읽는 요령은 다른 글에서 다룬다. 로그를 좁혀 읽는 법은 리눅스 로그 분석 명령어 가이드, 관측 도구를 직접 만들지 않는 선택은 Sentry 와 PostHog 글, 알람을 코드로 표준화하는 방법은 알림 시스템 표준화 글을 참고한다.

이 절차에는 전제가 있다. 원문의 사례는 JVM 과 Node.js 같은 런타임, 쿠버네티스 컨테이너, 스레드 풀과 커넥션 풀을 가진 웹 서비스를 배경으로 한다. 배치 처리나 스토리지처럼 구조가 다른 시스템에서 같은 표를 그대로 쓸 수 있는지는 원문에 없으므로, 각 행의 원리인 증상 먼저와 대기가 쌓이는 자리 찾기만 가져가고 지표 이름은 자기 환경에 맞게 바꿔 읽어야 한다.

확인하지 못한 것

  • 원문에 특정 모니터링 도구의 화면이나 설정 방법은 없다. 이 글도 도구별 사용법을 다루지 않았다.
  • 원문의 애니메이션 시연. 원문에는 그래프가 움직이는 시연이 있으나 텍스트로 옮겨지지 않아 수치 세부는 본문 서술에서만 인용했다.
  • 사용률 대기 곡선의 식. 원문은 50퍼센트 1배에서 95퍼센트 19배까지의 값을 제시하며, 이 글은 그 값만 옮겼다.
  • 롤백 기준의 구체적 임계값. 원문은 X퍼센트와 10분이라는 형식으로 제시하며 서비스별 값은 정하지 않았다.
  • 원문이 쓴 대시보드 도구와 언어별 런타임의 지표 이름. 이 글은 개념 수준까지만 다뤘다.
