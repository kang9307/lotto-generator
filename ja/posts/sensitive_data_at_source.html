マスキングは出力段階では遅い - 機微な値を発生地点で止める構造

出力で隠す方式は知っている形式しか止められない。その時点で複製はすでに増えている

2026-08-01 開発/インフラ

序論: ログからは消したのに、バックアップには残っていた

いちばんよくある順番はこうだ。誰かがログを見ていて、あってはならない値が出ているのを見つける。急いでマスキング規則を入れて配備する。翌日のログ画面はきれいだ。そして一か月ほど経ち、障害調査のために古いバックアップを展開した人が同じ値を再び見つける。

この話でマスキング規則は仕事をした。問題は規則が働き始めた時点だ。その値はすでに標準出力に出て、ファイルに書かれ、コレクタへ送られ、ローテーションされ、バックアップに入っている。出力段階で隠すというのは、すでに何部も複製された後にそのうちの一部だけを直すことだ。

だからこの記事の主張は「マスキングしよう」ではない。マスキングは最後の防衛線であり、本当の解法はそもそもその値がログ経路に入らないようにすることだ。そのためには規則の向きを裏返す必要がある。除くものを選ぶのではなく、入れるものを選ばなければならない。

  • 出力で隠す方式はパターンを知っているものしか止められない。 形式が少し違えばそのまま通り、何も失敗しない
  • オブジェクトを丸ごと入れると、後からできたフィールドが自動的に付いてくる。 ログのコードは一行も変わっていないのに漏れる項目が増える
  • 直そうと決めた時点ですでに複製が何部もある。 どの複製が残っているかを知る人がいない
  • 値を包んでおけば、間違えても元の値は出ない。 文字列結合に入れても、ログに入れても同じだ

実行環境。 以下のすべての出力はWindows 10 Pro (10.0.19045)でNode.js v22.16.0 (win32)により実際に実行した結果である。スクリプトはすべてファイルに保存して実行し、一時ディレクトリの中だけでファイルを作った。

★例示の値はすべて形式だけを合わせた偽物だ。 桁数だけを合わせて数字はすべてゼロで埋め(000000-0000000、0000-0000-0000-0000、010-0000-0000)、メールアドレスは実際には配達されない予約ドメインを使った。実在する個人情報ではない。 この記事は値がどう漏れるかの構造だけを扱い、迂回や抽出の方法は扱わない。

この記事が扱わないこと。 どのデータをどこまで外部ツールに入れてよいかという判断基準と社内規程は社内データをLLMに入れてよいかの話だ。何をどのレベルで出すかというレベル規約はWARNがゴミ箱になる理由で扱ったので、ここでは説明し直さない。許可リストへ裏返す一般的な手順は禁止リストは常に後手に回るにある。この記事はその原理をログ経路という一点に適用した実装だ。

法令について。 個人情報を扱う組織には収集・保管・破棄に関する義務がある。ただしこの記事は条文も金額も引用しない。 適用範囲と保存期間は事業形態と国によって変わるため、関連法令と社内規程を確認して決めてほしい。この記事が扱うのは技術的な実装だけだ。

1. オブジェクトを丸ごと入れると、後からできたフィールドが付いてくる

まずいちばん重要な再現だ。これ一つを理解すればこの記事の半分になる。問題は「機微な値をログに出した」ではなく「ログに出る範囲を誰も固定していない」ことである。

オブジェクトを丸ごと直列化して出力するコードを一つ置き、時間が経って別のチームが別の機能のためにフィールドを追加する状況を作った。ログ呼び出しには手を付けていない。

node v22.16.0 / win32
--- 1-1. release v1: the object has 3 fields ---
signup ok {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01T00:00:00Z"}

--- 1-2. release v2: product adds fields. the log call is UNCHANGED ---
signup ok {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01T00:00:00Z","phone":"010-0000-0000","cardNumber":"0000-0000-0000-0000","nationalId":"000000-0000000"}

--- 1-3. diff: what the log gained without a code change ---
fields logged in v1 : 3  id,nickname,createdAt
fields logged in v2 : 6  id,nickname,createdAt,phone,cardNumber,nationalId
newly leaking        : phone,cardNumber,nationalId
lines of code changed to cause this : 0

最後の行がこの記事全体の要約だ。この変化を起こすために変わったコードの行数はゼロである。 フィールドを追加した人はログのコードを読んだことがなく、ログのコードを書いた人はそのフィールドができたことを知らない。どちらも悪くないのに値が漏れる。

この種の欠陥はコードレビューでは捕まらない。レビュアーが見るのは「フィールドを三つ追加した」という変更だけであり、その変更だけを見れば何の問題もないからだ。問題は二つの変更のあいだの距離にある。

1.1 スプレッドも入れ子も同じだ

「オブジェクトをそのまま入れなければよいのでは」と考えるのは自然だ。ところがよく使う二つの迂回はまったく迂回になっていない。

--- 1-4. the same happens through spread, nesting and ORM rows ---
spread into context  : {"requestId":"r-0001","id":"u-0001","nickname":"tester","createdAt":"2026-08-01T00:00:00Z","phone":"010-0000-0000","card ...
nested one level     : nationalId still present
depth does not help  : JSON.stringify walks the whole tree
  • スプレッド演算子でコンテキストに合わせるのはフィールドを選んだことにならない。同じフィールドが一段上がっただけだ
  • 一段包むことも役に立たない。直列化関数は木構造全体をたどるので、深さは防御にならない
  • データベースの行オブジェクトをそのまま渡すことがいちばん危ない。列が増えればログも一緒に増え、列の追加はログと無関係な人が行う
  • リクエスト本文全体をコンテキストに付けることも同じ構造だ。クライアントが何を送るかをサーバのコードは決めない
  • 共通点は一つだ。範囲を決める主体がログを書く人ではない。 それがこの欠陥の定義である

2. 出力で隠す方式は知っている形式しか止められない

まず思いつく対応は出力直前に正規表現で隠すことだ。実際によく使われる。この方式がどこで崩れるかを無害な値だけで確認した。電話番号の形と社員番号の形で、数字はすべてゼロである。

node v22.16.0 / win32
--- 2-1. a typical output-stage masker ---
input                                 after masking
------------------------------------------------------------------------------
contact 010-0000-0000 assigned        contact 010-****-**** assigned
contact 010 0000 0000 assigned        contact 010 0000 0000 assigned   <- NOT MASKED
contact 01000000000 assigned          contact 01000000000 assigned   <- NOT MASKED

九つのうち七つがそのまま通った。 そして通った理由はどれも些細だ。

  • 区切り文字がハイフンから空白や点に変わった。上流システムが正規化の方式を変えれば、その日から規則は遊ぶことになる
  • 区切り文字がまったくない。 データベースに保存するときによく消される形だ
  • 国番号が前に付いた。 国際表記に正規化する層を一つ通るとこうなる
  • 大文字と小文字が違う。 正規表現にフラグが一つ欠けているだけだ
  • 社員番号の桁が一つ増えた。 採番の方針が変わっただけなのに規則が外れた
  • 共通点は何も失敗しないことだ。マスキングされなかったと知らせる合図がない

2.1 逆方向にも誤る

あまり知られていない失敗モードがもう一つある。規則が消してはいけないものを消す場合だ。

--- 2-2. why the rule cannot be finished ---
the masker matches shapes. the data is defined by MEANING.
every upstream format change is a silent hole, and nothing fails loudly.

--- 2-3. and the rule can be too greedy in the other direction ---
order 010-0000-0000 shipped           order 010-****-**** shipped   <- masked, but this was not personal data
build EMP-000000 finished             build EMP-****** finished   <- masked, but this was not personal data

a pattern rule has two failure modes at once: it misses, and it destroys.

注文コードとビルドタグが偶然その形式に合った。この場合マスキングは機微でない値を消してデバッグを妨げる。 すると人々は規則を緩め、緩んだ規則はまた取りこぼし始める。この振り子運動に終わりはない。

根本の理由は一文で整理できる。正規表現は形式を当て、機微情報は意味で定義される。 同じ十一桁の数字がある文脈では個人情報で、別の文脈では注文番号だ。その差は値の中に入っていない。

止める地点何を止めるか新しいフィールドが増えると複製に及ぶ範囲戻し方
発生地点(ラッパー型)値そのものが文字列として存在しない影響なし(包んだ値だけを扱う)新しい複製が作られないコードを戻す
イベント組み立て(許可リスト)入れると決めたフィールド以外すべて自動的に除外ロガーより下の全区間コードを戻す
ロガーの直列化器名前を知っているフィールド名前を知らなければ通るそのロガーを使う場所だけ設定を戻す
コレクタ規則パターンが合う値パターンが違えば通る即座に全域、ただし既存の複製は除く即座
出力後の一括洗浄見つけたものだけわからない手を付けた複製一つ不可(元が消える)

3. 直そうと決めた時点ですでに何部もある

ここからが三つ目の軸だ。前の二節が「何を取りこぼすか」だったなら、この節は「いつ取りこぼすか」である。ログ一行が生まれてから経験する平凡な一生を実行で追ってみた。

九部のうち八部に元の値が残っている。 直したのは一部だ。そしてこの八部の保存期間を決める人がそれぞれ違う。

  • ローテーションされたファイルはサーバ設定が決める。たいていアプリケーションのチームではなくインフラ側だ
  • コレクタのセグメントはコレクタの方針が決める。索引ができていれば検索でも出てくる
  • バックアップはバックアップ方針が決める。おおむねいちばん長く、手を入れるのがいちばん難しい
  • 障害スナップショットとチケット添付は誰も決めない。 作った人が忘れれば永遠に残る
  • だから「消した」と言うためにはこの一覧をまず作らなければならない。多くの組織にその一覧がない

3.1 数えられる複製だけで八つだ

--- 3-5. and these are the ones you can enumerate ---
not counted here: collector replicas, object-storage versions,
search-engine inverted index, alert payloads already delivered,
an engineer terminal scrollback, and any chat message quoting the line.
the retention clock of each copy is set by a different owner.

ここから出る結論がこの記事の中心の主張だ。複製を追いかける戦いには勝てない。 値が生まれた瞬間に複製はすでに予定されており、その後のすべての措置は予定された複製の一部だけに触れる。戦いを移さなければならない。値がその経路に入る前へ。

4. エラーオブジェクトが値を運ぶ

ログ呼び出しをどれだけきれいに整理しても残る経路が一つある。例外だ。 例外は「ログを出そう」と決めた人がいなくても出力される。

node v22.16.0 / win32
--- 4-1. route A: the value goes into the message ---
e.message           : invalid nationalId: 000000-0000000
first stack line    : Error: invalid nationalId: 000000-0000000

--- 4-2. route B: the value rides on a property ---
e2.message          : payment declined   (clean)
JSON of e2.context  : {"request":{"userId":"u-0001","phone":"010-0000-0000","nationalId":"000000-0000000"},"attempt":2}

--- 4-3. what each common serializer emits ---
JSON.stringify(e2)            : {"name":"AppError","context":{"request":{"userId":"u-0001","phone":"010-0000-0000","nationalId":"000000-0000000"},"attempt":2}}
  -> CONTAINS nationalId
String(e2)                    : AppError: payment declined
  -> clean
util.inspect(e2) contains     : CONTAINS nationalId
console.error path uses inspect, so the terminal shows it too

二つの経路は性格が違う。

  • 経路Aは目に見える。 検証失敗のメッセージに値を入れるのは親切な習慣なのでとても多く、だからとても多く漏れる。メッセージに入れた瞬間スタックの先頭行にも入る
  • 経路Bは目に見えない。 メッセージはきれいなのにコンテキスト属性にリクエスト全体が付いている。しかもこの習慣は推奨される習慣なのでより広く普及している
  • メッセージだけを見て判断すると誤る。直列化器が何をたどるかが実際に出る内容を決める
  • ターミナル出力も同じ検査経路を使うので画面にもそのまま出る

4.1 原因の連鎖、未処理例外、そして安全に見える罠

--- 4-4. the cause chain carries it further ---
outer.message                 : checkout failed   (clean)
inspect(outer) contains       : CONTAINS nationalId
a wrapper error looks innocent while dragging the original context

--- 4-5. why JSON.stringify(err) looks safe and is not ---
JSON.stringify(new Error(payload.phone)) : {}
message and stack are non-enumerable, so plain JSON drops them,
which is exactly why teams add a custom error serializer,
and the custom serializer is what puts message, stack and context back in.

--- 4-6. an unhandled rejection prints it with no logging code at all ---
uncaught handler saw : AppError: payment declined
full text contains   : CONTAINS nationalId

nobody called a logger here. the runtime did.

4-5がとくに示唆的だ。既定の直列化はエラーを空のオブジェクトにする。メッセージとスタックが列挙されない属性だからだ。そこでチームは「エラーがログに出ない」という不便を経験し、専用のエラー直列化器を付ける。 その直列化器がメッセージとスタックとコンテキストを再び入れ直す。安全に見えた既定値を自ら取り払うことになる。

  • 原因の連鎖で包んだ外側のエラーはメッセージがきれいなのでより安心できる。 ところが内側のコンテキストをそのまま引きずっていく
  • 未処理例外は誰もロガーを呼ばなくてもランタイムが出力する。ログ呼び出しを監査してもこの経路は一覧に出ない
  • したがってエラーコンテキストには識別子だけを入れる規則が必要だ。リクエストID、ユーザーID、注文IDのようなものである
  • 検証失敗のメッセージには値ではなく何が違うのかを書く。「形式不一致、フィールド名 nationalId」で十分だ
  • この規則は5節のラッパーがあればおのずと守られる。 包んだ値をメッセージに入れても元の値は出ないからである

5. 発生地点で止める - 取り出さなければ出ないラッパー

ここからが解法だ。発想は単純である。機微な値を文字列のまま持ち歩かない。 代わりに取り出す呼び出しを明示してはじめて元の値が出る型で包む。包んだ瞬間から、間違いは値ではなくプレースホルダを露出する。

const util = require('util');
const RAW = Symbol('raw');

class Secret {
  constructor(value, label) {
    this[RAW] = value;
    this.label = label || 'secret';
  }
  // 明示的で検索可能な、唯一の出口
  expose() { return this[RAW]; }
  // 暗黙の経路はすべて同じプレースホルダを返す
  toString() { return '[' + this.label + ' redacted]'; }
  toJSON()   { return '[' + this.label + ' redacted]'; }
  [util.inspect.custom]() { return '[' + this.label + ' redacted]'; }
  [Symbol.toPrimitive]() { return '[' + this.label + ' redacted]'; }
}

const phone = new Secret('010-0000-0000', 'phone');

四つのフックを一緒に覆うのが要点だ。一つでも欠ければその穴からすべて出ていく。間違いが起こりうる経路を十三通り選んですべて通してみた。

十三の経路で漏洩ゼロだ。 テンプレート文字列に入れても、文字列を足しても、配列でまとめて結合しても、直列化しても、入れ子にして直列化しても、フォーマット指定子を三種類に変えても元の値は出ない。これが「発生地点で止める」の実体だ。間違いを禁じるのではなく、間違えても値が出ないようにすることである。

--- 5-3. console.log goes through inspect, so it is covered too ---
  direct  : [phone redacted]
  nested  : {
  requestId: 'r-0001',
  user: { id: 'u-0001', contact: [phone redacted] }

--- 5-4. the only way to the value is a call you can grep for ---
  phone.expose() : 010-0000-0000
  a code search for .expose( lists every real use site.
  a code search for the field name does not, because the field is everywhere.

5-4の最後の二行が運用上いちばん大きな利得だ。元の値に至る通路が名前のあるメソッド一つなので、コード検索一回で「この値が実際に元の形で使われている場所」をすべて列挙できる。フィールド名で検索するとその一覧は出てこない。フィールド名はどこにでもあるからだ。監査対象が数百か所から十いくつかに減る。

5.1 半分だけ実装すると無いほうがましだ

--- 5-5. what happens if you implement only half of it ---
  toString only, template : [redacted]
  toString only, JSON     : {"v":"010-0000-0000"}   <- LEAK
  toString only, inspect  : HalfSecret { v: '010-0000-0000' }   <- LEAK
  a partial wrapper is worse than none: it reads as safe.

--- 5-6. the strict variant: refuse instead of substituting ---
  concat -> TypeError: Secret must be unwrapped with .expose() before use
  JSON  -> "[phone redacted]"   (toJSON still substitutes, so logs never crash)
  throwing catches mistakes in tests; substituting keeps production quiet.
  a common split: throw in dev and test, substitute in production.

--- 5-7. the wrapper does not survive the network boundary ---
  after JSON round trip : {"contact":"[phone redacted]"}
  the type is a source-side guard. across a boundary you must re-wrap on parse.
  • 文字列変換だけを実装したラッパーは画面では隠れるが、直列化と検査出力で元の値をそのまま吐いた。しかもそちらが実際のログ経路だ
  • 半端なラッパーは無いより危険だ。 コードを読む人が「これは包まれているから安全だ」と判断するからである
  • 厳格な変種は文字列として使おうとすると例外を投げる。テストで間違いを即座に捕まえる代わりに、運用で新しい事故を作りうる
  • よくある折衷は開発とテストでは投げ、運用ではプレースホルダで置き換えることだ。直列化フックは両方とも置き換えを保ってログが死なないようにする
  • ラッパーは境界を越えられない。 直列化して送れば相手はプレースホルダの文字列を受け取る。受け取る側で包み直す必要があるので、この方式はサービスごとに各自立てるものだ
  • 付け加えると型システムがあればさらに強くなる。 文字列を要求する場所に包んだ値を入れるとコンパイル段階で引っかかる

6. 除くフィールドではなく入れるフィールドを決める

ラッパーは値を守る。ところが1節の問題は値ではなく範囲だった。その範囲を固定するのがこの節だ。ここでは「機微なフィールドをどう除くか」の一点だけを見る。

// 方向1. 除くフィールドを決める
const DENY = ['phone', 'cardNumber', 'nationalId'];
function denylist(obj) {
  const out = { ...obj };
  for (const k of DENY) delete out[k];
  return out;
}

// 方向2. 入れるフィールドを決める
const ALLOW = ['id', 'nickname', 'createdAt', 'plan'];
function allowlist(obj) {
  const out = {};
  for (const k of ALLOW) if (k in obj) out[k] = obj[k];
  return out;
}

二つの関数は最初に書かれたスキーマでは区別がつかない。 それがこの欠陥が長く生き残る理由だ。

node v22.16.0 / win32
--- 6-1. both rules look fine on the schema they were written for ---
  denylist (v2)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic"}
  allowlist(v2)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic"}

--- 6-2. now the schema moves. neither rule is edited ---
  denylist (v3)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic","national_id":"000000-0000000","backupPhone":"010-0000-0000","kyc":{"documentNo":"D-000000000"}}
  allowlist(v3)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic"}

  sensitive values present in denylist output  : id-shaped value, phone-shaped value, document-shaped value
  sensitive values present in allowlist output : none

スキーマを三方向に動かした。同じデータが別の表記のフィールド名で入ってきて、誰も知らせなかった新しいフィールドが付き、一段入れ子になった構造ができた。除くフィールドの一覧は三つとも通し、入れるフィールドの一覧は三つとも止めた。1節と正確に対照される。1節で自動的に漏れていたものが、ここでは自動的に止まる。

--- 6-3. the asymmetry, stated plainly ---
  denylist  fails OPEN : an unknown field is emitted
  allowlist fails CLOSED: an unknown field is dropped
  a new field is added by someone who has never read the logging code.
  so the rule has to be safe when nobody updates it.

--- 6-4. what you lose, and how to notice ---
  fields dropped from the log : phone, cardNumber, nationalId, national_id, backupPhone, kyc
  a field you needed for debugging is now missing, and that is the cost.
  make it visible instead of silent:
  {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic","_dropped":6}
  the count tells you the schema moved, without telling you what moved.

--- 6-5. the allowlist has to be applied at build time, not at write time ---
  event object keys : ["id","nickname","createdAt","plan"]
  the wide object never reaches the logger, so no later stage can widen it.
  narrowing inside the logger is one layer too late: everything upstream
  of the logger, including error handlers, still sees the wide object.
  • 失敗する方向が逆だ。 除く一覧は知らないフィールドを出し、入れる一覧は知らないフィールドを捨てる。誰も規則を更新しない状態で安全でなければならないので後者が正しい
  • 代償がある。 デバッグに必要だったフィールドが静かに消える。これが許可リストの実際の費用であり、隠してはいけない
  • 代償を静かでなくする安価な方法が6-4にある。捨てたフィールドの個数だけを一緒に残すことだ。何が変わったかは言わずに、スキーマが動いたという事実は知らせてくれる
  • その数字がある日急に大きくなれば上流に変更があったという合図だ。許可リストを更新するか検討する契機になる
  • ★適用地点が決定的だ。 ロガーの内部で狭めると一層遅い。ロガーより上にあるすべて、とくにエラー処理器は依然として広いオブジェクトを見る
  • だから狭める作業はイベントオブジェクトを作る瞬間に行う。広いオブジェクトがロガーに届かなければ、後のどの段階もそれを再び広げられない

7. 下4桁だけ見せる必要があるとき、どこで切るか

現実には部分表示の要求がある。相談画面でカードの下4桁を確認してはじめて本人かどうかを尋ねられる。この要求そのものは正当だ。問題はどこで切るかである。

node v22.16.0 / win32
--- 7-1. the requirement: a support screen shows the last 4 digits ---
  requested display value : ****-****-****-0000

--- 7-2. attempt A: keep both on the same record ---
  record  : {"userId":"u-0001","cardNumber":"0000-0000-0000-0000","cardLast4":"0000"}
  the display value exists, and so does the original, one key apart.
  every whole-object log, error context and API response carries both.
  the partial value did not reduce anything. it added a field.

--- 7-3. attempt B: cut at the source, keep only the derived value ---
  record  : {"userId":"u-0001","cardLast4":"0000","card":"[card redacted]"}
  inspect : { userId: 'u-0001', cardLast4: '0000', card: [card redacted] }
  the screen gets cardLast4. the logger gets cardLast4. nothing else is reachable
  without calling .expose(), and .expose() is greppable.

--- 7-4. the two attempts under the same accidental log line ---
  A : {"msg":"checkout","data":{"userId":"u-0001","cardNumber":"0000-0000-0000-0000","cardLast4":"0000"}}
      -> ORIGINAL PRESENT
  B : {"msg":"checkout","data":{"userId":"u-0001","cardLast4":"0000","card":"[card redacted]"}}
      -> derived value only

7-2はとてもよくある間違いだ。切った値と元の値を同じオブジェクトに並べて置く。 画面は切った値を使うので要求は満たされる。ところがこのオブジェクトが丸ごとログに入った瞬間、元の値も一緒に行く。 部分表示が減らしたものは何もなく、フィールドが一つ増えただけだ。

7-3が答えだ。境界で一度切って派生値だけを残し、元の値は包んだまま置く。 そうすれば画面もロガーも切った値だけを受け取る。

--- 7-5. cutting late produces drift ---
  input                : "0000 0000 0000 0000"
  last4  (digits only) : 0000
  last4v2(naive slice) : "0000"
  same field name, two values, depending on which layer computed it.
  cutting once at the boundary makes the answer single-valued.

--- 7-6. a partial value is still personal data ---
  one record may hold several partials : {"u-0001":["0000","010-0000","a***@example.invalid"]}
  each is harmless alone. joined on the same subject they narrow the set.
  so a partial is a display format, not a declassification.
  keep the same retention and access rules on it.
  • 7-5は遅く切るときに生じる二つ目の問題だ。切るコードが複数の層にできると同じフィールド名に別の値が入る。一方は数字だけを残して切り、もう一方は文字列の末尾をそのまま切った
  • 空白が混ざった入力で二つの結果が分かれた。一つは数字四桁、もう一つは空白を含む四文字だ。画面によって違って見える値ができ、それが問い合わせとなって返ってくる
  • 境界で一度だけ切ればこの問題は定義上なくなる。派生値を作る場所が一つしかないからだ
  • 7-6が最後の注意だ。部分値も依然として個人情報である。 一つだけ見れば無害だが、同じ主体に複数の部分値が付くと範囲が狭まる
  • したがって部分表示は表示形式であって等級解除ではない。 保存期間とアクセス権限を元の値と同じ基準に置いてほしい
  • 具体的な桁数と表示範囲は業種と契約によって異なる。関連法令と社内規程、そして決済網の規定を確認して決めること

8. すでに溜まったログの危険箇所探しと導入順序

ここまでが「これからどうするか」だったなら、この節は「すでに溜まったものをどうするか」だ。診断は二度走査する。

node v22.16.0 / win32
--- 8-1. build a sample log tree ---
  api.log       3 lines
  worker.log    2 lines
  auth.log      2 lines
  batch.log     3 lines

--- 8-2. pass 1: key names, not value shapes ---
  file          lines   risky keys found
  ----------------------------------------------------------------------
  api.log       3       phone(1) context.cardNumber(1)
  worker.log    2       -
  auth.log      2       authorization(1) password(1)
  batch.log     3       national_id(1) nationalId(1) email(1)

--- 8-3. pass 2: key inventory, to catch names you did not list ---
  distinct keys in the sample : 14
  matched the risk list       : 7
  NOT on the risk list        : 7
  lvl, msg, path, userId, context, jobId, durationMs
  read this list by hand once. that is the review, and it is finite.
  a value-shape scan cannot produce this list at all.

一次走査は値の形ではなくキー名で探す。2節で見たように値の形式は上流によって変わるが、キー名は比較的安定している。入れ子のキーも経路ごと捕まえなければならない。context.cardNumberがそうして引っかかった。

ところが二次走査のほうが重要だ。 危険キーの一覧に引っかからなかった残りのキーをすべて列挙し、人が一度読むことである。標本では異なるキーが十四個あり、そのうち七個が一覧の外だった。この一覧は有限だ。 一度読めば終わる。そして値の形式だけを走査する方式ではそもそも作れない一覧である。

--- 8-4. rank by blast radius, not by count ---
  file          keys   retain   copies   score
  ----------------------------------------------------------
  batch.log     3      365d     3        3285
  auth.log      2      365d     4        2920
  api.log       2      90d      4        720
  worker.log    0      14d      1        0
  score = risky keys x retention days x number of destinations.
  a low-volume line kept for a year in four places outranks a noisy one kept for two weeks.

--- 8-5. order of work, by how hard each step is to undo ---
  # action                                cost      undo                  buys you
  ------------------------------------------------------------------------------------------------------------
  1   collector-side drop rule              minutes   fully reversible      stops NEW copies today
  2   shorten retention on the worst file   minutes   reversible            shrinks the window
  3   purge existing copies                 days      NOT reversible        needs an owner list first
  4   allowlist the event builders          weeks     reversible by revert  the actual fix
  5   wrapper type on the fields            weeks     reversible by revert  makes step 4 hold
  6   remove the collector rule             minutes   reversible            only after 4 and 5 are verified

優先順位を件数ではなく波及範囲で付けたのが8-4だ。危険キーの数と保存日数と複製先の数を掛けた。すると静かでも一年保管され三か所に複製されるログが、うるさくても三か月しか残らないログより上に来た。件数で並べていたら順序は逆だっただろう。

導入順序で議論になる点が一つある。コレクタからか、コードからか。 8-5の答えはコレクタからで、理由は「そのほうがよい解法だから」ではない。

段階効果の範囲かかる時間戻し方限界
1. コレクタ遮断規則即座に全域分完全に戻せる2節のパターンの限界そのまま
2. 保存期間の短縮該当ログ分戻せるすでに作られた複製はそのまま
3. 既存複製の破棄破棄したものだけ日不可所有者の一覧が先に必要
4. イベント組み立ての許可リスト配備済みサービス週コードを戻すサービスごとに別々
5. ラッパー型の適用包んだフィールド週コードを戻す境界を越えられない
6. コレクタ規則の除去即座に全域分戻せる4と5の検証前は禁止
  • コレクタ規則が先である理由は止血帯だからだ。 配備なしで即座に全域に適用され、間違っていれば即座に外せる
  • 同時に止血帯は治療ではない。 すでに作られた複製には何の効果もなく、それ自体が2節で不完全だと確認したパターン照合である
  • 破棄を急いではいけない。 戻せない唯一の段階であり、所有者の一覧なしに実行すれば「消した」とは言えない
  • コード修正を4番と5番の順に置く理由は、許可リストが範囲を固定しラッパーがその固定を維持させるからだ。逆にすると包まれていない新しいフィールドが入り続ける
  • 最後の6番は検証の後にだけ行う。検証方法は簡単で、コレクタ規則を切ってステージングで同じ走査を回し、危険キーがゼロかを見る
  • 新しいサービスでは順序が逆だ。 最初から4と5だけをすればよく、コレクタ規則は要らない

8.1 点検リスト

  • ログ呼び出しにオブジェクトを丸ごと渡す箇所があるか探した(スプレッド・入れ子・データベース行・リクエスト本文を含む)
  • イベントオブジェクトを作る地点で入れるフィールドを明示した。除くフィールドを指定していない
  • 許可リストをロガーの中ではなくイベント組み立ての時点で適用した
  • 捨てたフィールドの個数を一緒に残してスキーマ変更を検知できるようにした
  • 機微フィールドにラッパー型を適用し、四つのフックをすべて実装した
  • ラッパーの取り出し呼び出しをコード検索して使用箇所をすべて確認した
  • エラーコンテキストに識別子だけを入れる規則を立てた
  • 検証失敗のメッセージに値ではなくフィールド名を書く
  • 専用のエラー直列化器が何をたどるか確認した
  • 部分表示は境界で一度だけ切り、元の値と同じオブジェクトに置いていない
  • 部分値にも元の値と同じ保存・アクセス基準を適用した
  • 既存ログをキー名基準で走査し、一覧の外のキーすべてを人が読んだ
  • 優先順位をキー数 × 保存日数 × 複製先の数で付けた
  • ログ複製の行き先の一覧と所有者を文書にした
  • 個人情報の取扱範囲と保存期間を関連法令と社内規程に合わせて確認した

結論: 除くものを選ぶのではなく、入れるものを選べ

実行して確認したことを一行ずつ並べ直すとこうなる。オブジェクトを丸ごと入れるコードはコード0行の変更で漏れるフィールドが三つ増えた。出力段階の正規表現は無害な形式の変形九つのうち七つを取りこぼし、同時に機微でない値を二つ消した。ログ一行は平凡な運用だけで九部になり、マスキングが直したのはそのうち一部だった。

反対側も実行で確認した。四つのフックを覆ったラッパーは間違いの経路十三個で漏洩ゼロだった。入れるフィールドを決めた直列化はスキーマが三方向に動いても何も通さなかった。同じ状況で除くフィールドを決めた側は三つとも通した。

だから結論は「マスキングをもっと上手にしよう」ではない。マスキングは最後の防衛線だ。 出力で隠す方式はパターンを知っているものしか止められず、その時点ですでに複製は終わっている。本当の解法はその値がログ経路に入る前にあり、そこで使う規則は一つだ。除くものを選ぶのではなく、入れるものを選べ。 知らないフィールドに出会ったときに捨てる側に傾いていてこそ、誰も規則を更新しない数年間を持ちこたえる。

いますぐできることが一つある。ログのコードでオブジェクトを丸ごと渡す呼び出しを一つだけ探し、そのオブジェクトのフィールド一覧をいま出力してみてほしい。 その一覧を最後に確認したのがいつだったか思い出せなければ、そのあいだに何が増えたかも知らないということだ。8節の二次走査はその確認を一度で終わらせるための手順である。

# 機微な値を発生地点で止める — ラッパー・許可リスト・診断手順

> 出典: braindetox.kr — マスキングは出力段階では遅い
> 根拠: Windows 10 / Node.js v22.16.0 での実行検証
> このファイルをそのままAIに貼り、「この基準でうちのログ経路を点検して」と書けば使えます。
> 以下の例示の値は形式だけを合わせた偽物です。桁数だけ合わせて数字はすべてゼロです。
> 個人情報の取扱範囲と保存期間は関連法令と社内規程を確認して決めてください。

## 0. 一行の原則

マスキングは最後の防衛線だ。本当の解法はその値がログ経路に入らないようにすることであり、
そこで使う規則は一つ。**除くものを選ぶのではなく、入れるものを選べ。**

| 方式 | 知らないフィールドに出会うと | 判断 |
|---|---|---|
| 除くフィールドの一覧 | 出してしまう (fail open) | スキーマが動けば漏れる |
| 入れるフィールドの一覧 | 捨てる (fail closed) | **こちらを使う** |
| 出力の正規表現 | 形式が違えば通る | 止血帯。解決策ではない |

## 1. ラッパー型 — 取り出さなければ元の値は出ない

四つのフックを**すべて**覆うこと。一つでも欠ければその穴からすべて出ていく。

```js
const util = require('util');
const RAW = Symbol('raw');

class Secret {
  constructor(value, label) {
    this[RAW] = value;
    this.label = label || 'secret';
  }
  // 唯一の出口。名前があるのでコード検索で使用箇所をすべて列挙できる
  expose() { return this[RAW]; }

  toString() { return '[' + this.label + ' redacted]'; }   // テンプレート・結合
  toJSON()   { return '[' + this.label + ' redacted]'; }   // 直列化
  [util.inspect.custom]() { return '[' + this.label + ' redacted]'; }  // console.log
  [Symbol.toPrimitive]() { return '[' + this.label + ' redacted]'; }   // 暗黙変換
}
```

検証した13の経路で漏洩ゼロ:
テンプレート文字列 / 文字列結合 / String() / 配列join / JSON.stringify /
入れ子のJSON / util.inspect / 入れ子のinspect / format %s / format %j /
format %o / String.prototype.concat / + 演算子

注意:
- **半分だけ実装すると無いほうがましだ。** toStringだけでは直列化・検査出力でそのまま漏れる
- 開発・テストでは投げ、運用では置き換える折衷がよくある。toJSONは両方とも置き換えを維持
- **境界を越えられない。** 直列化して送れば相手はプレースホルダを受け取る。受け取る側で包み直すこと

## 2. 許可リスト直列化 — イベントを作る瞬間に狭める

```js
const ALLOW = ['id', 'nickname', 'createdAt', 'plan'];

function allowlist(obj) {
  const out = {};
  for (const k of ALLOW) if (k in obj) out[k] = obj[k];
  return out;
}

// 狭める位置が決定的だ。ロガーの中ではなくここ。
function buildEvent(user) {
  const picked = allowlist(user);
  const droppedCount = Object.keys(user).length - Object.keys(picked).length;
  return { event: 'signup', user: picked, _dropped: droppedCount };
}
```

- ロガーの中で狭めると一層遅い。エラー処理器などロガーより上は依然として広いオブジェクトを見る
- 捨てた個数を残せば**何が変わったかを言わずに**スキーマ変更を知ることができる
- その数字が急に大きくなれば上流変更の合図。許可リストの更新を検討

## 3. エラーコンテキストの規則

- 検証失敗のメッセージに**値を入れない。**「形式不一致、フィールド nationalId」で十分
- エラーコンテキストには**識別子だけ**: リクエストID、ユーザーID、注文ID
- 原因の連鎖で包んだ外側のエラーはメッセージがきれいに見えても**内側のコンテキストを引きずる**
- 未処理例外は**ロガーを呼ばなくても**ランタイムが出力する。ログ呼び出しの監査では捕まらない
- 既定の直列化がエラーを空のオブジェクトにするからと安心しないこと。**専用直列化器が入れ直す**

## 4. 診断手順 — 二度走査する

1) **一次: キー名で走査する**(値の形ではなく)
   - 入れ子のキーは経路ごと: context.cardNumber
   - 値の形式は上流によって変わるが、キー名は比較的安定している
2) **二次: 一覧の外のキーをすべて列挙して人が読む**
   - この一覧は有限だ。一度読めば終わる
   - 値の形式の走査ではそもそも作れない一覧である
3) **優先順位 = 危険キー数 × 保存日数 × 複製先の数**
   - 件数で並べないこと。静かでも長く広く残るログが上だ

## 5. 導入順序 — 戻しにくい順に

| # | 段階 | 時間 | 戻し方 | 得るもの |
|---|---|---|---|---|
| 1 | コレクタ遮断規則 | 分 | **完全に戻せる** | 今日から新しい複製を遮断 |
| 2 | 保存期間の短縮 | 分 | 戻せる | 露出の窓を狭める |
| 3 | 既存複製の破棄 | 日 | **不可** | 所有者の一覧が先 |
| 4 | イベント組み立ての許可リスト | 週 | コードを戻す | **実際の解決** |
| 5 | ラッパー型の適用 | 週 | コードを戻す | 4を維持させる |
| 6 | コレクタ規則の除去 | 分 | 戻せる | 4と5の検証後にだけ |

- コレクタが先である理由はよい解法だからではなく**止血帯**だからだ
- 新規サービスは順序が逆。4と5だけをすればよく、コレクタ規則は要らない

## 6. 点検リスト

- [ ] ログ呼び出しに**オブジェクトを丸ごと渡す箇所**を探した(スプレッド・入れ子・DB行・リクエスト本文を含む)
- [ ] イベント組み立ての地点で**入れるフィールドを明示**した(除くフィールドの指定ではない)
- [ ] 許可リストを**ロガーの中ではなくイベント組み立ての時点**で適用した
- [ ] 捨てたフィールドの**個数**を一緒に残した
- [ ] 機微フィールドにラッパーを適用し**四つのフックをすべて**実装した
- [ ] 取り出し呼び出しをコード検索して**使用箇所をすべて**確認した
- [ ] エラーコンテキストに**識別子だけ**を入れる規則を立てた
- [ ] 検証失敗のメッセージに**値ではなくフィールド名**を書く
- [ ] 専用のエラー直列化器が**何をたどるか**確認した
- [ ] 部分表示は**境界で一度だけ**切り、元の値と同じオブジェクトに置いていない
- [ ] 部分値にも**元の値と同じ保存・アクセス基準**を適用した
- [ ] 既存ログを**キー名基準**で走査し**一覧の外のキーすべて**を読んだ
- [ ] 優先順位を**キー数 × 保存日数 × 複製先の数**で付けた
- [ ] ログ複製の**行き先の一覧と所有者**を文書にした
- [ ] 取扱範囲・保存期間を**関連法令と社内規程**に合わせて確認した

## 7. してはいけないこと

- ❌ オブジェクト・DB行・リクエスト本文を**丸ごと**ログに渡すこと — 新しいフィールドがコード0行で付いてくる
- ❌ 出力の正規表現マスキングを**解決策とみなすこと** — 形式の変形に破られ無害な値を消す
- ❌ 切った値と**元の値を同じオブジェクトに**置くこと — 丸ごとログ一回で両方出る
- ❌ 検証失敗のメッセージに**値を入れること** — スタックの先頭行にも一緒に入る
- ❌ 所有者の一覧なしに**破棄から**始めること — 戻せない唯一の段階だ
- ❌ コレクタ規則だけを入れて**終わったとすること** — すでに作られた複製には効果がない
- ❌ ラッパーを**半分だけ**実装すること — 安全に見えるぶん危険だ
