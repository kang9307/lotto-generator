如果重新设计随机数 API - 可复现性、安全性、一致性

统计用与安全用、种子、范围、洗牌、全局状态，全部实际运行验证后整理成设计原则

2026-08-01 开发/基础设施

引子: 复现不了的失败，和名字相同的两个函数

用生成输入驱动的检查，某天只失败了一次。日志里只写着与期望值不符。再跑一遍通过了，再跑十遍也通过了。究竟是哪个输入把它弄坏的，随着进程退出一起消失了。

在找原因的路上，先发现了别的东西。生成那批输入的代码，和给密码重置链接铸造令牌的代码，调用的是名字几乎一样的函数。一个是统计用生成器，另一个是安全用。只看调用点根本分不出哪个是哪个。

这两件事看起来是两个事故，根却只有一个。随机数 API 的难点不是算法，而是名字和默认值。用哪个生成器、要不要接受种子、范围怎么截取，全都是接口设计的问题；接口一旦含糊，使用方就必然出事。

所以就真的跑了一遍。下面的每个数字都来自在这个运行时里直接执行。确认了四件事。

  • 名字把类别藏了起来。统计用和安全用共用同一个词时，调用点什么也说明不了
  • 没有种子就没法把缺陷看第二遍。可复现性不是便利功能，而是调试的前提
  • 截取范围的瞬间分布就开始倾斜。而这份倾斜取决于源的宽度，可能一眼看见，也可能永远看不见
  • 一个全局生成器就能把可复现性扣为人质。即便固定了种子，消费顺序一变结果就变

运行环境。下面所有输出都是在 Windows 10 Pro (10.0.19045) 上用 Node.js v22.16.0 (win32 x64) 实际执行得到的。统计用生成器是自己实现的、带 32 位状态的 splitmix32；安全用直接使用这个运行时提供的密码学随机数接口。脚本全部保存成文件后执行。样本量在正文中逐项标注。

本文不涉及的内容。不讲如何利用可预测性。只确认统计用是可预测的这一性质，不写利用这一性质的任何步骤。服务端故意返回被打散的值，以及把随机标识用作主键时的存储代价，各有单独的文章。检查是否依赖执行顺序也不在本文范围内。本文只看随机数 API 自身的接口。

1. 名字只有一个，类别却有两种

先把这个运行时提供的随机数相关调用列出来，标注各自属于哪一类。然后单独放一行真实代码，看看能不能判断类别。

--- 1-1. every one of these has "random" in the name ---
call                          family        seedable  sample output
--------------------------------------------------------------------------------------------
Math.random()                 statistical   no        0.4962049585478472
crypto.randomInt(0, 100)      security      no        57
crypto.randomBytes(4).hex     security      no        16ca5c5e
crypto.getRandomValues(u32)   security      no        4091828560
crypto.randomUUID()           security      no        9ba23fe3-3912-4644-9d45-3025617158a5
seeded splitmix32(42)         statistical   YES       551831576

--- 1-2. can you tell the family from the call site alone? ---
const pick   = Math.random();                           statistical   
const nonce  = crypto.randomInt(0, 1e9);                security-grade
const shard  = Math.random() * 16 | 0;                  statistical   
const token  = crypto.randomBytes(16).toString("hex");  security-grade
const jitter = Math.random() * 200;                     statistical   
const id     = crypto.randomUUID();                     security-grade

六个调用点里统计用三个、安全用三个。而且六个的名字里都含着同一个词。在代码评审里扫过这些行时，要判断属于哪一类，就得把被调用者的名字一个个记在脑子里。

  • 表里的 seedable 一列是决定性的。能塞种子的只有统计用，安全用连塞种子的地方都没有
  • 可是这个性质在名字里完全看不出来。要看文档才知道，不看文档就不知道
  • 变量叫 token 还是 jitter 是唯一线索，而变量名并不受强制
  • 想用静态分析抓也难，因为要追踪这个值会不会离开进程，一般情况下并不容易

1.1 为什么需要两类 - 在这个运行时里测得的吞吐

分成两类是有理由的。这个理由到底有多大，实测了一下，同时也确认了两类在收到非法参数时各自的反应。

--- 1-3. why both exist: throughput in this runtime ---
Math.random()                        2,000,000 draws       30.6 ms       65,425,972 /s
seeded splitmix32                    2,000,000 draws       34.6 ms       57,830,211 /s
crypto.randomInt(0, 256)               200,000 draws       11.9 ms       16,771,910 /s
crypto.getRandomValues(1 word)         200,000 draws      537.1 ms          372,338 /s
getRandomValues, 4096 batched        2,000,000 draws       39.8 ms       50,269,065 /s

ratio Math.random / crypto.randomInt      : 3.9 x
ratio Math.random / getRandomValues(1)    : 175.7 x
ratio Math.random / getRandomValues(batch): 1.3 x
batching closes most of the gap; per-call overhead was the cost, not the algorithm

--- 1-4. the security call has limits the statistical one does not ---
getRandomValues(65536 bytes)      ok
getRandomValues(65537 bytes)      QuotaExceededError: The requested length exceeds 65,536 bytes
getRandomValues(Float64Array)     TypeMismatchError: The data argument must be an integer-type TypedArray
crypto.randomInt(10, 5)           RangeError: The value of "max" is out of range. It must be greater than the value of "min" (10). Received 5
Math.random(10, 5)                0.00437523505103643   <- extra arguments accepted and ignored
Math.random("seed")               0.8035145788730187   <- a seed argument is silently dropped

差距确实存在，但差距的来源很有意思。安全用一次取一个字时慢了 175 倍，一次取 4,096 个时只差 1.3 倍。也就是说代价的大部分是每次调用的开销，而不是算法本身。

  • 因为安全用慢所以改用统计用，这个理由在多数情况下站不住。批量取值后，多数负载下差距就消失了
  • 安全用调用有一次 65,536 字节的上限，超过就抛异常。这个上限本身就表达了批量取值但要有节制的设计意图
  • 安全用会拒绝非整数类型的数组，最小值大于最大值时也当场抛出异常
  • 相反，统计用调用多给参数也会被默默忽略。传进一个看起来像种子的字符串什么都不会发生。把它当成种子的代码将永远无法复现

2. 种子不是便利功能，而是调试的前提

回到开头的症状: 用生成输入驱动的检查失败了，却不知道是哪个输入。只要有种子，这种局面根本不会出现。

准备一个当区间宽度为 0 时除法会给出无穷大的函数，用生成的输入检查 500 次。把种子写进报告和不写进报告的两种做法并排跑了一遍。

--- 2-1. same seed, two independent generators, same sequence ---
seed 20260801, run A : 266 648 876 913 47 571
seed 20260801, run B : 266 648 876 913 47 571
seed 20260802, run C : 944 290 515 272 128 899
A equals B : true     A equals C : false

--- 2-2. a data-driven check finds a failing input ---
seed recorded in the failure report : 424242
iterations run                      : 500
failures                            : 14
first failing input                 : iteration 92, lo=30 hi=30

--- 2-3. replay: rerun with the recorded seed, get the identical failure ---
replay 1 : first failure at iteration 92, lo=30 hi=30
replay 2 : first failure at iteration 92, lo=30 hi=30
replay 3 : first failure at iteration 92, lo=30 hi=30
the failing input is now a fixed, quotable value; you can attach it to the fix

三次重放全都指向同一个迭代序号、同一个输入。到这一步，失败就不再是随机事件，而变成可以引用的固定值。它能原样写进修复提交里，验证是否修好时也用同一个值来验。

2.1 没有种子时同一个检查每次讲的故事都不同

--- 2-4. the same check without a seed: five runs, five different stories ---
run     failures / 500    first failing input
--------------------------------------------------------
1       19                iteration 8, lo=10 hi=10
2       9                 iteration 52, lo=34 hi=34
3       9                 iteration 119, lo=10 hi=10
4       11                iteration 14, lo=25 hi=25
5       13                iteration 32, lo=16 hi=16
first-failure iteration across runs : 8, 52, 119, 14, 32
nothing here is quotable: the input that broke it is gone the moment the process exits

--- 2-5. what a seed buys, measured ---
property                              seeded    unseeded
----------------------------------------------------------------------------
can rerun the exact input set         yes       no
failure report is a fixed value       yes       no
fix can be proven against the case    yes       not the same case
unpredictable to an outside party     no        no (both are statistical)
safe for tokens and secrets           no        no

同一个检查跑五次，首次失败的迭代是 8、52、119、14、32，全都不一样。失败次数也在 9 到 19 之间摇摆。在这种状态下没有办法证明修好了，因为下一次没失败，究竟是因为修好了还是运气好，无法区分。

  • 种子必须是失败报告的一部分。不写进日志，有和没有是一样的
  • 最后一张表的下面两行很关键。无论有没有种子，统计用都是可预测的，两种形态都不能用来造秘密值
  • 也就是说，有没有种子是可复现性这条轴上的问题，不是安全性这条轴上的问题。把两条轴混在一起，判断就模糊了
  • 实践中常把种子推迟成需要时再加的东西，可是需要它的那一刻已经太晚了

3. 一旦构造范围，分布就开始倾斜

把随机值搬进目标范围，最常见的做法是取模。取一百万个 8 位值对 100 取余，统计分布。同时也看了骰子这种小范围的情形。

--- 3-1. modulo on an 8-bit source, bound = 100 ---
256 = 2 * 100 + 56   -> values 0..55 have 3 preimages, 56..99 have 2
theoretical p(low)  = 1.1719%   p(high) = 0.7813%   ratio = 1.500
measured  mean(0..55) = 11715.7   mean(56..99) = 7816.4   ratio = 1.499
measured  min = 7615  max = 11917  expected if fair = 10000
chi-square (df 99) = 37546   (fair sample lands near 99)
first 8 buckets  : 11623 11596 11859 11710 11869 11676 11634 11520
buckets 56..63   : 7949 7884 7659 7807 7886 7615 7881 7824

--- 3-2. same bug, small bound = 6 (a dice roll) ---
256 = 42 * 6 + 4
face       :         1        2        3        4        5        6
count      :    167301   167670   168621   167747   164466   164195
share      :   16.730%  16.767%  16.862%  16.775%  16.447%  16.419%
expected fair share 16.667% each
chi-square (df 5) = 104.1   (fair sample lands near 5)
theoretical excess of faces 1..4 = 2.38%

原因就是一行算术。256 除以 100，商是 2 余数是 56。0 到 55 各有三条路径，56 到 99 各有两条。所以靠前的值恰好多出 1.5 倍。实测的 1.499 与理论吻合。

骰子也是同样的结构。256 除以 6 余 4，所以 1 到 4 多出 2.38%。用眼睛看像是误差，但卡方值 104.1，超出自由度 5 的期望二十倍以上。

3.1 源一宽，同样的缺陷就永远看不见

这里是本节的核心。把完全相同的取模用在 32 位值上，跑同样的一百万次。同时也测了消除偏差的方法和它的代价。

--- 3-3. same "% 6" on a 32-bit source: bias still there, invisible ---
2^32 = 715827882 * 6 + 4
theoretical excess of faces 1..4 = 1.397 parts per billion
count      :    166645   166580   166318   167237   166273   166947
chi-square (df 5) = 4.1   -> indistinguishable from fair
draws needed to see this bias at all: about 512410 x 10^12

--- 3-4. rejection sampling removes the bias at a measurable cost ---
accept only bytes < 200 (= 256 - 256 % 100), then take % 100
measured  min = 9708  max = 10279  expected = 10000
chi-square (df 99) = 104   (fair sample lands near 99)
rejected 280146 of 1280146 bytes = 21.88%  (theory 21.88%)
worst-case rejection rate for an 8-bit source is just under 50% (bound = 129)

32 位那边的结果是卡方 4.1，与公平样本无法区分。偏差并没有消失，只是在十亿分之 1.4 的量级上看不见而已。要在统计上抓住它，需要 10 的 17 次方量级的样本。也就是说它变成了检查永远抓不到的缺陷。

源宽度范围低值的超额概率一百万次能看见吗实践判断
8 位62.38%能立刻暴露，容易修
8 位10050%能最危险的组合
8 位1000744 个值根本不出现能范围比源还宽
16 位10001.54%能临界
32 位60.00000014%不能检查抓不到
32 位10000.0000233%不能检查抓不到
53 位10000.0000000000111%不能实际上无害

这张表要这样读: 上面三行是很快会被发现的缺陷，下面两行是永远不会被发现的缺陷。可是两边的代码长得一模一样。所以到目前为止没出过问题并不能当作依据。

  • 字节宽度的源配上窄范围，是最容易出事的组合。抽签、掷骰、抽卡全都落在这里
  • 拒绝采样只接受到范围的整数倍为止，把尾巴丢掉。8 位配 100 时丢掉 21.88%，换来偏差为 0
  • 在 32 位源上拒绝的代价是平均 1.00 次、最坏 2.00 次，在实践中不构成问题
  • 最可靠的解法是由库来提供这个函数。让调用方每次自己造，有一半会造错
// unbiased bounded integers - the code a caller should never have to write again
function intBelow(next, n) {                     // next() returns a uint32
  if (!Number.isInteger(n) || n <= 0) throw new RangeError('bound must be a positive integer');
  if (n > 4294967296) throw new RangeError('bound exceeds source width (2^32)');
  const limit = 4294967296 - (4294967296 % n);   // largest exact multiple of n
  let v;
  do { v = next(); } while (v >= limit);         // drop the ragged tail
  return v % n;
}

function intBetween(next, lo, hi) {              // closed range, both ends included
  if (!Number.isInteger(lo) || !Number.isInteger(hi)) throw new TypeError('intBetween takes integers');
  if (hi < lo) throw new RangeError('intBetween(lo, hi) needs hi >= lo');
  return lo + intBelow(next, hi - lo + 1);
}

4. 把 0 到 1 的浮点数变成整数时的边界

很多随机数 API 返回大于等于 0、小于 1 的浮点数。把它变成整数的瞬间就出现了边界问题。把 1 正下方那个最大的浮点数直接喂给常见写法，看看反应。

--- 4-1. the two endpoints of [0, 1) ---

is it really < 1       : true
next double up         : 1

--- 4-2. does floor(r * n) ever reach n? feed it the worst possible r ---

------------------------------------------------------------------------------------
6                     5.999999999999999         5                     no
100                   99.99999999999999         99                    no
1000                  999.9999999999999         999                   no
65536                 65535.99999999999         65535                 no
1000000000            999999999.9999999         999999999             no
4503599627370496      4503599627370495.5        4503599627370495      no
9007199254740992      9007199254740991          9007199254740991      no

--- 4-3. the same worst-case r through the usual range idioms ---
idiom                     r = 0   r = 0.5 r = max<1  intended range
----------------------------------------------------------------------------------------
Math.floor(r * n)         0       5       9          0..9   inclusive-exclusive
Math.round(r * n)         0       5       10         0..10  endpoints half-weight

先说一件能放心的事: 只要用向下取整，最大值就不会蹦出来。乘上 1 之前那个最大浮点数，乘积仍会向下舍入，够不到 n。n 不超过 2 的 53 次方时全都如此。问题出在别的写法上。

写法实际范围喂给 1 之前的值时判定
Math.floor(r * n)0 到 n-1，均匀n-1正确（半开区间）
Math.floor(r * (n + 1))0 到 n，均匀n正确（闭区间）
Math.round(r * n)0 到 n，两端权重减半n错误
Math.ceil(r * n)0 到 n，0 几乎不出现n错误
(r * n) | 0超过 2 的 31 次方变负n-1错误（范围受限）

四舍五入那一侧的分布很扎眼。两端是 5.01%，中间是 10.00%，正好一半。因为四舍五入把 0 和 n 对应到了宽度只有一半的区间上。抽奖或分档用了这个写法，就只有两端那两档悄悄变得稀有。

  • 大于等于 0 小于 1 是半开区间。五百万次里既没出现恰好的 0，也没出现恰好的 1，观测到的最小值是 1.8e-7
  • 用位运算截断的写法在超过 2 的 31 次方的范围上会给出负数。跨度 50 亿时得到了 -544,967,296
  • 一个浮点数最多承载 53 位信息。要求比这更宽的范围，就会有永远出不来的值
  • 想包含两端，就不要用四舍五入，而要把区间数加一再向下取整。表里的第二行就是这个做法
  • 为了不让调用方每次都要判断这些，API 必须用名字说清是开区间还是闭区间

比较器方式的结果非常极端。保持原顺序的情况出现了 45,021 次，是公平值 10,000 次的四倍以上。完全颠倒的顺序也扎堆在 41,219 次。反过来有的排列只出现了 3,671 次，最大与最小之比 12.26 倍。

Fisher-Yates 落在 9,782 到 10,197 之间，卡方值 24，与自由度 23 的期望基本一致。目的相同的两段代码，实际上是完全不同的东西。

5.1 为什么错误的洗牌在原理上不可能均匀

--- 5-3. why broken Fisher-Yates cannot be fair, by counting ---
length 3 :       27 equally likely swap paths spread over    6 permutations           27 / 6 = 4.5000  <- not an integer, cannot be uniform
length 4 :      256 equally likely swap paths spread over   24 permutations         256 / 24 = 10.6667  <- not an integer, cannot be uniform
length 5 :     3125 equally likely swap paths spread over  120 permutations       3125 / 120 = 26.0417  <- not an integer, cannot be uniform
length 6 :    46656 equally likely swap paths spread over  720 permutations      46656 / 720 = 64.8000  <- not an integer, cannot be uniform
correct Fisher-Yates draws from 0..i, giving exactly n! paths for n! outcomes

--- 5-4. the comparator version also depends on the sort algorithm and length ---
length   2 : P(element 0 stays at index 0)  comparator   49.84%   Fisher-Yates   50.02%   fair value 50.00%
length   3 : P(element 0 stays at index 0)  comparator   43.62%   Fisher-Yates   33.35%   fair value 33.33%
length   4 : P(element 0 stays at index 0)  comparator   35.96%   Fisher-Yates   25.06%   fair value 25.00%
length   8 : P(element 0 stays at index 0)  comparator   22.13%   Fisher-Yates   12.45%   fair value 12.50%
length  16 : P(element 0 stays at index 0)  comparator   13.26%   Fisher-Yates    6.26%   fair value 6.25%

只靠数数就能证明。交换对象从整个数组里抽，路径就有 n 的 n 次方条，而结果只有 n 的阶乘种。4 元素时 256 除以 24 等于 10.667，不是整数。等概率的路径没法按整数份分下去，所以均匀不可能。正确写法是把交换对象限制在 0 到当前位置之间抽取，这样路径恰好是 n 的阶乘条。

  • 比较器洗牌数组越长越糟。长度 16 时首元素留在原位的概率是 13.26%，是公平值 6.25% 的两倍
  • 同一段代码会因排序实现不同而给出不同分布，也就是说换个运行时结果就变
  • 比较器建立在同样两个元素比较总得同样答案这一前提上，而随机比较器打破了这个前提
  • 结论与第 3 节相同: 洗牌也应该由库提供。不提供的话，比较器写法必然出现

6. 必须使用安全用的场合

接下来看两类的差别如何体现在输出上。把同一个令牌生成函数分别架在统计用和安全用之上。

先说明一点。本节只确认统计用是可预测的这一性质。如何利用这个性质、用什么步骤推出下一个值，都不涉及。

the two lists are identical: a statistical generator IS its state, nothing more

that identity is exactly the property section 2 wanted. it is also the property
a reset token must not have. the same feature, two opposite verdicts.

本文不写的东西。没有写利用可预测性的任何步骤，因为要做的判断只靠性质就够了。这个值一旦状态确定就随之确定，这一条事实本身就足以成为不把它当秘密使用的理由。反方向的安全主张，也就是难以推出来这种说法，会随着技术进步而崩塌；而结构上已被确定这个事实不会改变。

6.1 长度该取多少

选定了安全用，下一个问题就是长度。计算了字符集大小与长度决定的位数，以及在该位数下发生碰撞之前能容纳多少个值。

--- 6-5. which call belongs where ---
what you are generating         family        why
------------------------------------------------------------------------------------------------
A/B bucket assignment           statistical   reproducible bucketing is a feature
retry backoff jitter            statistical   only needs to spread load

lottery or prize draw           security      money plus an outside party

one line rule: if a stranger holding the value gains something, it is the security family

第三列是实践判断的依据。十六进制 8 位是 32 比特，只造 7.7 万个碰撞概率就到一半了。而 62 字符集的 22 位是 131 比特，比现实中可能造出的任何数量都宽裕得多。另一个值得注意的是令牌长度并不等于熵。用只有 32 位状态的生成器造 24 位令牌，实际的熵也不会超过 32 位。

要生成的东西类别种子理由
会话标识、重置令牌、API 密钥安全用无值本身就是权限
CSRF 令牌、随机数、盐安全用无新鲜度就是安全性
临时文件和目录的名字安全用无别人能预知的名字有风险
抽奖、发奖、排位分配安全用无牵涉金钱与外部当事人
检查用的合成数据统计用必需种子要写进失败报告
A/B 分桶统计用必需同一用户落进同一个桶
日志抽样统计用建议抽样变得可审计
重试退避抖动统计用不需要只要把负载摊开
动画、粒子、音效统计用可选速度就是全部
  • 判断标准只有一行: 陌生人知道这个值会得到什么吗。会，就是安全用
  • 拿不准就用安全用。选错时一边只损失速度，另一边无法挽回
  • 直接把通用唯一标识当秘密值用时，要算上格式吃掉的固定位: 128 位里有 6 位被版本号和变体标记占死
  • 临时文件名之所以在这份清单里，是因为先知道名字的一方可以先占住那个位置。这是需要不可预测性的场合

7. 一个全局生成器就能破坏可复现性

第 2 节靠种子换来了可复现性，可这份可复现性比想象中更容易碎。让两个组件共享一个固定种子的全局生成器，只把消费顺序改成三种。

--- 7-1. one global generator, two consumers, two interleavings ---
order                 component A sees      component B sees
------------------------------------------------------------------
A A A B B B           201 652 582           38 515 449
B B B A A A           38 515 449            201 652 582
A B A B A B           201 582 515           652 38 449

same seed, same code, three different results for A: 3 distinct sequences out of 3
the seed pins the stream. it does not pin who draws from it, or when.

--- 7-2. one instance per consumer: order stops mattering ---
order                 component A sees      component B sees
------------------------------------------------------------------
A A A B B B           876 436 698           745 310 389
B B B A A A           876 436 698           745 310 389
A B A B A B           876 436 698           745 310 389

distinct sequences for A : 1 out of 3
distinct sequences for B : 1 out of 3

同样的种子、同样的代码，组件 A 看到的数列三种全都不同。种子只固定数列本身，固定不了谁在什么时候取走多少个。把生成器分开发放后，三种顺序的结果完全一致。

7.1 异步交错时崩得更快

--- 7-3. the same break under async interleaving ---
shared generator, timing 1 : A 201 582 515   |   B 652 38 449
shared generator, timing 2 : A 652 582 449   |   B 201 38 515
identical                  : false

own generator,   timing 1 : A 876 436 698   |   B 745 310 389
own generator,   timing 2 : A 876 436 698   |   B 745 310 389
identical                 : true

a global generator makes every consumer a hidden dependency of every other one

--- 7-4. what a global seed can and cannot promise ---
layout                  stable alone  stable in parallel  stable on reorder  depends on
------------------------------------------------------------------------------------------------------------
one global generator    no            no                  no                 call order and timing
one per component       yes           yes                 partly             draw count inside the component
one per unit of work    yes           yes                 yes                nothing outside the unit

deriving a child generator per unit of work (seed + work id) keeps reproducibility
while letting the units run in any order or in parallel

只改了时序的两次运行给出了不同结果，而拥有自己生成器的那一侧不受时序影响。全局生成器会把每个使用者变成彼此的隐藏依赖。代码里某处多抽一次随机数，就会改变毫不相干的另一处的结果。

布局单独可复现并行可复现顺序变了仍可复现取决于
一个全局生成器否否否调用顺序与时序
每个组件一个是是部分组件内部的消耗量
每个工作单元一个是是是无
  • 实践中推荐的形态是按工作单元派生子生成器，由上层种子与工作标识组合生成
  • 这样即使工作并行运行、顺序改变，每个工作的数列也原样保持
  • 提供全局生成器的 API 看着方便，却为了这一点方便让人交出全部可复现性
  • 无论把种子管理得多细致都解决不了这个问题。这是结构的问题，不是值的问题

8. 重新设计的话 - 名字、种子、范围、默认值

把前面七节里出现的陷阱全部堵住的接口，实际造出来跑了一遍。规则有四条: 让名字显出类别，让种子显式，提供范围函数，把默认值放在谨慎的一侧。

// the family is in the constructor name, and the seed is not optional
function statisticalRng(seed) {
  if (!Number.isInteger(seed)) throw new TypeError('statisticalRng(seed) requires an explicit integer seed');
  const api = core(splitmix32(seed));    // deterministic engine
  api.seed = seed;                       // the value that goes into a failure report
  api.kind = 'statistical';
  return api;                            // an instance, never a module-level singleton
}

const secureRandom = (() => {
  const pool = new Uint32Array(1024);    // batched: per-call overhead was the cost, not the algorithm
  let i = pool.length;
  const u32 = () => { if (i >= pool.length) { crypto.getRandomValues(pool); i = 0; } return pool[i++]; };
  const api = core(u32);
  api.kind = 'security';
  api.token = (chars = 22) => { /* ... */ };     // exists only on this object
  return api;                            // no seed parameter, so none can be passed
})();

// one shared surface, so range and collection helpers read the same on both
function core(u32) {
  return {
    intBelow:     (n) => bounded(u32, n),                      // [0, n)  half-open, the name says below
    intBetween:   (lo, hi) => lo + bounded(u32, hi - lo + 1),  // [lo, hi] closed, the name says between
    unitInterval: () => u32() / 4294967296,                    // [0, 1)  named after its range
    pick:         (arr) => arr[bounded(u32, arr.length)],      // no index arithmetic at the call site
    shuffled:     (arr) => { /* Fisher-Yates on a copy */ },   // past tense: returns a copy
  };
}

关键在于两个构造器的形状本身就不同。统计用没有种子就造不出来，安全用没有放种子的地方。不读文档，接口也会强制。用这个接口重新跑了前面三个陷阱。

--- 8-1. the surface, and what each name promises ---
name                    family         contract
------------------------------------------------------------------------------------------------
statisticalRng(seed)    statistical    seed is required; there is no zero-argument form
secureRandom            security       no seed parameter exists, so none can be passed
.intBelow(n)            both           half-open [0, n), unbiased by rejection
.intBetween(lo, hi)     both           closed [lo, hi]; the word between states it
.unitInterval()         both           the [0, 1) float, named after its range
.pick(array)            both           no index arithmetic at the call site
.shuffled(array)        both           past tense: returns a copy
secureRandom.token(n)   security only  not present on the statistical object at all

范围偏差、端点权重、洗牌均匀性全部通过。更重要的是下面那份清单: 所有非法参数都被异常挡住了。漏掉种子就造不出对象，范围是 0 或小数会被拒绝，最小值大于最大值就当场停下。而统计用对象上根本没有令牌函数。

最坏的情况是范围略超过源宽度的一半，即便那时也只是平均 2.00 次。其余大多数范围下是 1.00 次，也就是几乎没有发生拒绝。如果消除偏差的代价只有这么点，就没有理由不把它设成默认。

设计规则省掉它会发生什么
名字里能看出类别用错了类别也没人提出异议
种子是必填参数失败过的那次运行没法再跑一遍
安全用一侧没有种子参数有人为了让检查变确定而传进种子
库自带范围函数每个调用方都重新造取模，一半会造错
范围的名字说明开闭在范围上端差一个
库自带洗牌比较器写法会顶上来
生成器是实例两个调用方一共享，可复现性就死了
非法参数抛异常悄悄错掉的数字会流向下游
令牌生成只存在于安全用一侧令牌会由可复现的数列造出来
默认值取谨慎的一侧快的那一侧不是被选中的，而是被撞上的
  • 范围命名的规则很简单: 表示小于的词不含端点，表示之间的词包含端点
  • 处理数组的函数应当不就地修改而返回副本，用过去分词形式的名字来告知这一点
  • 可复现性契约也该写进文档。升级版本后同一个种子是否给出同一数列，对确定性用途是重要的承诺
  • 需要快路径就提供，但要给它一个又长又显眼的名字，免得被误选

9. 小结 - 难的不是算法，是名字和默认值

把这一路跑出来的结论压成一句话就是: 随机数上出错的地方，多半不在生成，而在处理这个值的接口。算法早有定论，库可以代劳。而这个库用什么名字暴露什么，决定了事故的频率。

其中两点尤其关键。第一，统计用和安全用一旦名字相似，事故必然发生。实测中六个调用三三分开，光看名字分不出来。这是接口的缺陷，不是使用者的疏忽。

第二，可复现性不是有了更好的东西，而是调试的前提。没有种子就没法引用失败，无法引用就无法证明修好了。把种子做成可选参数，就没人会传。所以它必须是必填参数。

  • 陌生人知道这个值会得到什么吗。用这一行分开两类
  • 不要用取模截取范围。源窄时立刻暴露，源宽时永远不暴露
  • 不要用四舍五入构造整数范围。两端会变成一半的权重
  • 不要用比较器打乱。结果取决于排序实现和数组长度
  • 不要共享全局生成器。可复现性会被调用顺序绑架
  • 不要事后再加种子。需要它的那一刻已经太晚了

# 随机数 API 检查清单 — 统计用与安全用、范围、洗牌、种子

> 来源: braindetox.kr — 如果重新设计随机数 API
> 依据: 在 Windows 10 / Node.js v22.16.0 (win32 x64) 上实际运行验证, 2026-08-01

## 1. 一句话分开两类

**陌生人拿到这个值会得到什么吗?**

- 会 → **安全用**。令牌、会话、密码重置链接、邀请码、临时文件名、抽奖
- 不会 → **统计用**。抽样、抖动、A/B 分流、检查用的合成数据、视觉效果

拿不准就选安全用。在只需统计用的地方用安全用，损失的只是速度；
反方向的错误无法挽回。

## 2. 按用途选择

| 要生成的东西 | 类别 | 种子 | 理由 |
|---|---|---|---|
| 会话标识 | 安全用 | 无 | 值本身就是权限 |
| 密码重置令牌 | 安全用 | 无 | 值本身就是权限 |
| API 密钥、邀请码 | 安全用 | 无 | 值本身就是权限 |
| CSRF 令牌、随机数、盐 | 安全用 | 无 | 新鲜度就是安全性 |
| 临时文件或目录名 | 安全用 | 无 | 别人能预知的名字有风险 |
| 抽奖、发奖 | 安全用 | 无 | 涉及金钱与外部当事人 |
| 检查用的合成数据 | 统计用 | **必需** | 种子要写进失败报告 |
| A/B 分桶 | 统计用 | **必需** | 同一用户落进同一桶 |
| 日志抽样 | 统计用 | 建议 | 抽样变得可审计 |
| 重试退避抖动 | 统计用 | 不需要 | 只要把负载摊开 |
| 动画与粒子 | 统计用 | 可选 | 速度就是全部 |

## 3. 范围 — 没有偏差的整数

用 `%` 截断时，源值越窄分布越偏。8 位源上做 `% 100`，
最低的 56 个值会 **多出现 50%**（实测比值 1.499）。

```js
// 无偏的 [0, n) — 拒绝采样
function intBelow(next, n) {
  if (!Number.isInteger(n) || n <= 0) throw new RangeError('bound must be a positive integer');
  if (n > 4294967296) throw new RangeError('bound exceeds source width');
  const limit = 4294967296 - (4294967296 % n);
  let v;
  do { v = next(); } while (v >= limit);   // next() 返回 uint32
  return v % n;
}

// 闭区间 [lo, hi]
function intBetween(next, lo, hi) {
  if (hi < lo) throw new RangeError('intBetween(lo, hi) needs hi >= lo');
  return lo + intBelow(next, hi - lo + 1);
}
```

- 32 位源上拒绝的代价实测平均 **1.00 次**，最坏 **2.00 次**
- 8 位源上 `% 100` 的拒绝率为 21.88%，换来的是零偏差
- 源越窄偏差越大: 8 位的 `% 6` 是 2.38%，32 位的 `% 6` 是 0.00000014%

## 4. 浮点到整数的边界

| 写法 | 实际范围 | 判定 |
|---|---|---|
| `Math.floor(r * n)` | 0..n-1 均匀 | **正确**（半开区间） |
| `Math.floor(r * (n + 1))` | 0..n 均匀 | **正确**（闭区间） |
| `Math.round(r * n)` | 0..n，两端权重减半 | **错误** — 实测 5.01% 对 10.00% |
| `Math.ceil(r * n)` | 0..n，0 几乎不出现 | **错误** |
| `(r * n) \| 0` | 超过 2^31 变负数 | **错误** — 跨度 5e9 得到 -544967296 |

`[0, 1)` 是半开区间。500 万次实测中既没有出现恰好的 0，也没有出现恰好的 1。
把小于 1 的最大浮点数喂给 `floor(r * n)`，只要 n 不超过 2^53，结果仍停在 n-1。

## 5. 洗牌

```js
// Fisher-Yates — j 只从 0..i 中抽
function shuffled(next, arr) {
  const x = arr.slice();
  for (let i = x.length - 1; i > 0; i--) {
    const j = intBelow(next, i + 1);
    const t = x[i]; x[i] = x[j]; x[j] = t;
  }
  return x;
}
```

4 个元素、全部 24 种排列，每种方法各洗 24 万次:

| 方法 | 最小 | 最大 | 最大/最小 | 卡方 (df 23) |
|---|---|---|---|---|
| `sort(() => Math.random() - 0.5)` | 3,671 | 45,021 | **12.26** | 277,371 |
| 错误的 Fisher-Yates（j 取全范围） | 7,420 | 13,939 | 1.88 | 6,952 |
| Fisher-Yates（j 取 0..i） | 9,782 | 10,197 | 1.04 | **24** |

- 比较器洗牌把原顺序留在原地的次数多了 **11 倍**（45,021 对期望值 10,000）
- 错误的 Fisher-Yates 把 n^n 条路径摊到 n! 个结果上。n=4 时 256/24 = 10.667 不是整数，所以均匀 **不可能**
- 数组越长偏斜越明显: 长度 16 时首元素留在原位的概率为 13.26%（公平值 6.25%）

## 6. 种子

```js
// 种子是必填参数，不是可选项
function statisticalRng(seed) {
  if (!Number.isInteger(seed)) throw new TypeError('statisticalRng(seed) requires an explicit integer seed');
  // ...
}
```

- 用生成输入驱动的检查，必须**把种子一并写进失败报告**
- 有种子时失败输入成为固定值，可以直接引用（实测: 三次重放都停在 iteration 92, lo=30 hi=30）
- 没有种子时，同一个检查跑五次讲了五个不同的故事（首次失败在 8、52、119、14、32）
- **种子服务于复现，不服务于安全。** 带种子的生成器按定义就是可预测的

## 7. 不要全局生成器

| 布局 | 单独可复现 | 并行可复现 | 顺序变了仍可复现 | 取决于 |
|---|---|---|---|---|
| 一个全局生成器 | 否 | 否 | 否 | 调用顺序与时序 |
| 每个组件一个 | 是 | 是 | 部分 | 组件内部的消耗量 |
| 每个工作单元一个 | 是 | 是 | 是 | 无 |

同样的种子、同样的代码，只把消费顺序改成三种，组件 A 看到的数列
**三种全都不同**。给每个消费者各自的生成器后，三种完全一致。按工作单元
从 `种子 + 工作 ID` 派生子生成器，即使并行运行也能保住可复现性。

## 8. API 设计检查清单

- [ ] 函数**名字里能看出类别**（statistical / secure）
- [ ] 统计用的**种子是必填参数**，不提供无参形式
- [ ] 安全用的对象上**根本没有种子参数**
- [ ] 库自带范围函数（`intBelow`、`intBetween`）
- [ ] 范围的名字**说明开闭**（`below` 不含、`between` 含）
- [ ] 库自带洗牌，让比较器写法没有出现的余地
- [ ] 生成器是**实例**，不导出全局单例
- [ ] 参数不合法就**抛出**，绝不静悄悄返回一个错值
- [ ] 令牌生成**只存在于安全用对象上**
- [ ] 默认值取谨慎的一侧，快的那一侧必须显式选择
- [ ] 把可复现性契约写进文档（升版本后是否仍是同一数列）
- [ ] 数组操作**返回副本而不是就地修改**（`shuffled` 用过去分词表明）

## 9. 不要做的事

- 不要靠名字猜类别 — 实测中六个调用点三统计三安全，而全都带着 `random` 这个词
- 不要用统计用生成器造令牌 — 种子相同时，换一台机器也会得到相同的令牌
- 不要用 `%` 截断范围 — 源窄时立刻暴露，源宽时永远不暴露
- 不要用 `Math.round` 构造整数范围 — 两端会变成一半的权重
- 不要用 `| 0` 截断 — 超过 2^31 的范围会得到负数
- 不要用比较器洗牌 — 结果取决于排序算法和数组长度
- 不要让多处共享同一个全局生成器 — 可复现性会被调用顺序绑架
- 不要把种子推迟成「以后再加的东西」— 复现是调试的前提
