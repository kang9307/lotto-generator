glojure — GoランタイムでClojureを動かすインタープリター、なぜ存在するのか

JVMを捨ててGoをホストに選んだClojureインタープリターの意義と技術的課題 — 2026年6月時点での分析

2026-06-21 開発・インフラ

序論：なぜGoにClojureを？

Rich HickeyがClojureを設計したとき、JVMをホストに選んだのは趣味ではなく実用主義からだった。Javaの膨大なライブラリエコシステム、検証済みのGC、成熟したスレッドモデルをそのまま使う判断だ。Clojureは意図的にホスト型言語（hosted language）として設計されている。ClojureScriptも同じ哲学をJavaScriptに適用している。

glojureはそのパターンをGoに適用したプロジェクトだ。一言で言えば「JVMではなくGoランタイム上でClojureを実行する」。2026年6月時点でv0.6.5、GeekNewsにも紹介されたこのプロジェクトがなぜ存在し、何を解決し、何が難しいのかを正直に分析する。

1. Clojureの「ホスト型言語」哲学

Clojureの公式ドキュメントにはっきり書かれている。ClojureはJVM上にホストされる言語であり、ホストのタイプシステム、値、GC、スレッドがそのまま言語の一部になる。JVM上でJavaオブジェクトはそのままClojure値だ。(.method object args)という文法でJavaメソッドを直接呼ぶ。FFIもブリッジも不要。

glojureはこれをGoに適用する。Goの値がClojure値であり、Clojure値がGo値だ。ランタイムレベルの統合であって、ブリッジ層を介したFFIではない。これが「Goで書かれたClojureパーサー」と根本的に異なる点だ。

2. なぜGoをホストに選んだのか — 現実的な理由

2.1 配布のシンプルさ：単一静的バイナリ

Goの最大の実用的強みは単一静的バイナリビルドだ。外部ランタイム依存なしに一つのファイルで配布できる。JVMはJREかJDKのインストールが必要で、OpenJDKベースのDockerイメージだけで数百MBになる。Goはマルチステージビルドとscratchベースイメージを使えば5〜20MBまで圧縮できる。

起動時間の差はさらに大きい。標準のSpring Boot（JVM）は起動に約3.8秒かかる。同等のGoバイナリは約180ms — 約20倍の差だ。サーバーレス関数、Kubernetesポッドのスケールアウト、Lambdaコールドスタート環境では、この差はベンチマークではなく運用コストの問題になる。

glojureとGloat（AOTコンパイルツール）を組み合わせれば、Clojureコードをネイティブバイナリとしてビルドできる。Clojure文法でGoの配布メリットをそのまま享受できる。

2.2 Goエコシステムへのアクセス

GoはクラウドインフラとDevOpsツールの領域でJavaやJavaScriptにない強みを持つ。Kubernetes、Docker、Prometheus、TerraformはすべてGoで書かれている。これらGoネイティブのライブラリにClojure文法で直接アクセスできれば、インフラ自動化ツールとしての訴求力が生まれる。glojureはfmt、net:http、os、timeなど20以上のGo標準ライブラリをデフォルトで内蔵している。

2.3 ClojureコミュニティにおけるJVM忌避

ClojureコミュニティにはJVM自体を負担と感じる層が一定数いる。JVMチューニングの複雑さ、メモリオーバーヘッド、環境依存性を避けたいが、Clojureの不変データ構造とマクロシステムは使い続けたい。BabashkaがGraalVMネイティブでその需要を満たしているように、glojureはGoを通じた別の解答だ。

3. 技術的課題：なぜホスト型言語実装は難しいのか

3.1 Java互換性レイヤーの問題

現実のClojureコードはJVMに深く依存している。Math/sqrt、System/getenv、java.lang.String、正規表現クラス、数値ラッパー型 — これらはClojure標準ライブラリが直接呼び出す。GoはこれらのJava APIを一切知らない。

glojureはこの問題を解決するためにgojavaというGoネイティブのJava互換性レイヤーを開発した。Math、System、Stringなどの主要クラスの動作をGoで再実装したものだ。2026年6月時点でClojure互換性テストスイートをJVM専用9項目を除いて全通過しており、このレイヤーが相当完成していることを示している。

3.2 名前空間セパレーターの衝突

Clojureでは/が名前空間区切り文字として使われる（clojure.core/map）。GoのパッケージパスにもSlashが使われる（net/http）。glojureはGoパッケージの/を:に置換してこれを解決している。net:http.Getのように書く。エレガントではないが実用的な妥協だ。

3.3 並行性モデルの差異

ClojureのSTM（ソフトウェアトランザクショナルメモリ）はJVMのメモリモデル上に設計されている。GoはゴルーチンとチャネルというGoルーチン・チャネルモデルを使う。この2つのモデルを滑らかに橋渡しすることは、理論的にも実装的にも難しい課題だ。glojureはatomと基本的な並行プリミティブをサポートしているが、完全なSTMセマンティクスの移植は進行中の課題だ。

3.4 AOTコンパイルとGloat

インタープリターモードだけでは性能と配布に限界がある。glojureチームはGloat（Glojure Automation Tool）を別途開発し、AOTコンパイルパイプラインを構築した。.clj → .glj → .go → ネイティブバイナリ/WASMの段階を経て実際の配布可能バイナリを生成する。GraalVMのnative-imageが分単位のコンパイル時間を要するのに対し、Gloatは秒単位でビルドできることを強みとしている。

4. エコシステム上の位置：let-go、Babashka、ClojureScriptとの比較

プロジェクトホストランタイム配布成熟度主用途
Clojure（公式）JVMJAR + JVMプロダクション汎用
ClojureScriptJavaScript（V8等）JSバンドルプロダクションブラウザ/Node
BabashkaGraalVMネイティブ単一バイナリ成熟スクリプティング/CLI

let-goとglojureはどちらもGoを基盤とするが方向性が違う。let-goは独自のClojure類似方言を設計する。glojureは既存のClojureコードとの互換性を最大限維持しながらGoをホストとして使う。2026年6月時点のGitHubスター増加数はlet-goが2ヶ月で407個対glojureの35個と差がある。コミュニティの関心はlet-goに集まっているが、Clojureコード互換性への真剣度はglojureが高い。

5. 実際の使い方 — REPL、CLI、組み込み

5.1 glj CLIとREPL

インストールはGoモジュールで一行で完了する。

go install github.com/glojurelang/glojure/cmd/glj@latest

Go 1.24以上が必要。gljを実行するとvi/emacsモード、マルチライン入力、タブ補完、履歴保持、スマートインデントを備えたREPLが起動する。既存のClojure開発者にとってなじみやすい環境だ。

5.2 GoアプリへのClojure組み込み

より興味深い用途は既存GoアプリにClojureをスクリプティング層として追加することだ。GoサーバーやCLIツールにClojureでランタイム設定・ポリシーロジック・プラグインを書くパターン。C++ゲームエンジンにLuaを組み込むように、GoアプリにClojureを組み込める。

6. 限界と現実的な評価

6.1 v1前 — 後方互換性の保証なし

開発チームが明示している。v1前はAPIの変更が予告なく発生する可能性がある。今書いたコードが次のリリースで壊れるかもしれない。ミッションクリティカルなプロダクションパスにはまだ早い。

6.2 インタープリターモードのパフォーマンス制限

インタープリターモードの性能はJVM基盤のClojureに及ばない。JVMには数十年分のJIT最適化がある。GoはネイティブコンパイルによりGoが速いが、インタープリター層がその速度を十分に活かせていない。AOTコンパイル（Gloat）でかなり改善されるが、性能重要なワークロードでは検証が必要だ。

6.3 Clojureライブラリエコシステムが使えない

Ring、Compojure、core.async、specなどClojureの豊富なライブラリエコシステムはJVM基盤であり、glojureではそのまま動かない。Goインターopは強みだが、経験豊富なClojure開発者が期待するライブラリ環境はまだ形成途上だ。

6.4 glojureが真に強い場所

筆者の見立てでは、glojureが最も説得力を持つのはインフラツールスクリプティングとGoアプリへの組み込みだ。Kubernetesオペレーター、インフラ自動化ツール、DevOpsパイプラインをGoで書きながら、ClojureのREPL駆動開発と表現力を持ち込みたいとき。BabashkaやClojureScriptが埋められないGoネイティブinteropが必要なとき。そのニッチは狭いが実在する。

7. 2026年6月時点の状況

Clojurists Together 2026年6月アップデートによると、glojureは重要なマイルストーンを越えた。フォーク上での開発が公式アップストリームリポジトリ（glojurelang/glojure）に戻った。Clojure互換性テストスイートをJVM専用9項目を除いて全通過した。gojavaがMath、System、Stringなどのコアクラスをカバーしている。Gloat v0.1.50までリリース済みで、ウェブサイト上でインストール不要のWebAssembly REPLも提供されている。

残された課題として、より小さく速いバイナリ、実際のClojureプログラムとの互換性改善、ランタイム性能最適化が明示されている。「おもちゃ」レベルは超えたが、「本格的な代替」にはまだ時間がかかる。

結論：ホスト型言語哲学のもうひとつの実験

glojureはClojureのホスト型言語論のGoバージョンだ。ClojureScriptがJavaScriptエコシステムをClojureに開いたように、glojureはGoエコシステムをClojureに開こうとしている。技術的基盤は実在し、2026年6月のマイルストーンは意味がある。

正直な結論はこうだ。GoネイティブのインフラワークがあってJVMなしでClojureを使いたいなら、今すぐ試す価値はある。そうでないならv1を待つのが合理的だ。BabashkaはJVMフリーのClojureスクリプティングとして引き続き安全な選択肢だ。glojureが投げかけるより深い問い — 言語のアイデンティティはランタイムにあるのか、文法とセマンティクスにあるのか — は、使う人それぞれが答えを見つけることになる。
