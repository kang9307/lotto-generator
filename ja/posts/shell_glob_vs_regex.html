グロブと正規表現は違う - アスタリスクが別の意味になる瞬間

ls と grep に同じパターンを入れると違う答えが返る。実際に動かして確かめた分かれ道

2026年9月1日 開発・インフラ

ls ab* は ab で始まる名前を返す。同じ四文字を grep 'ab*' に入れると、ab が一つも無い行まで付いてくる。打ち間違いでもバージョンの問題でもない。この二つの場所で * が別々の文法に属している。

ファイル名を選ぶ側の文法をグロブ、仕様の用語ではパターンマッチング表記と呼ぶ。grep・sed・awk の側は正規表現だ。重なる記号が多く — *、?、[...] が両方に存在する — 片方の感覚でもう片方を書くとエラーの出ない誤った結果が返る。厄介なのはここだ。エラーなら気づくが、静かに別のものが引っかかる事故は本番に出てから表面化する。

以下の出力はすべて実際に動かして書き写したものだ。シェルのバージョンや shopt の設定で答えが変わる箇所は、その都度断っている。

この記事のすべての出力は、下の「動かした環境」節に記した一台のマシンから得たものだ。シェルのパターン動作は種類・バージョン・shopt の状態に左右されるので、各自の環境で一度動かしてから使うほうが安全である。他のシェルで結果が反転する箇所は本文に印を付けた。

動かした環境

シェルのパターンは「どのシェルのどのバージョンか」で答えが変わる領域だ。その情報が抜けると、以下の出力は根拠にならない。

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

$ uname -o -r
Msys 3.5.7-882031da.x86_64

$ find --version | head -1
find (GNU findutils) 4.10.0

$ grep --version | head -1
grep (GNU grep) 3.0

$ sed --version | head -1
sed (GNU sed) 4.9

Windows 10 上の Git Bash(MSYS2)環境で、シェルは GNU bash 5.2.37、ユーティリティは GNU 系だ。Linux ディストリビューションで動かせばほぼ同じ出力になるが、macOS 標準の grep・sed・find は BSD 系でオプション名から違う。その差は 正規表現の方言とツール間の互換性の主題なので、ここでは踏み込まない。

実験用ディレクトリはこう作った。以降の出力はすべてこのディレクトリの中で得たものだ。

$ mkdir -p /tmp/demo/sub && cd /tmp/demo
$ touch a.txt ab.txt abb.txt b.txt notes.log report.log .hidden .bashrc
$ touch sub/deep.txt sub/deep.log

$ shopt nullglob failglob dotglob extglob globstar nocaseglob
nullglob        off
failglob        off
dotglob         off
extglob         off
globstar        off
nocaseglob      off

shopt の状態を先に出したのには理由がある。この記事で扱う動作の半分ほどは、あのスイッチが決めている。非対話的なスクリプトではあの六つが全部オフの状態が既定値で、対話シェルではディストリビューションの初期化ファイルが extglob のようなものを有効にしていることもある。「自分の端末では動くのにスクリプトでは動かない」の相当数がここから来る。

* — 「任意の文字列」と「直前の0回以上」

最もよく使う記号から見る。同じ ab* を両側に入れてみた。

# グロブ - シェルがファイル名と照合する
$ ls ab*
ab.txt
abb.txt

# 正規表現 - grep が各行と照合する
$ printf '%s\n' a.txt ab.txt abb.txt b.txt | grep 'ab*'
a.txt
ab.txt
abb.txt

グロブ側は二つ、正規表現側は三つ。増えた一つが a.txt で、これが核心だ。グロブの ab* は「a、b、そして任意の文字列」である。正規表現の ab* は「a、そして b が0回以上」だ。b が0回でもよいので、b の無い名前が引っかかる。

整理するとこうなる。グロブの * は単独で意味を持つ記号だ。正規表現の * は直前に付いたものを繰り返させる演算子なので、単独では意味がない。正規表現でグロブの * に相当する表記は .* だ。「任意の一文字が0回以上」と書き下してはじめて同じ意味になる。

拡張子を外した短い一覧でもう一度確かめると、差がさらにはっきりする。

$ printf '%s\n' a ab abb xabz | grep 'ab*'
a
ab
abb
xabz

$ printf '%s\n' a ab abb xabz | grep -E '^ab*$'
a
ab
abb
  • グロブ * = 任意の文字列。空文字列も含むので、ab* は ab 自体とも一致する
  • 正規表現 * = 直前の要素の0回以上の繰り返し。前に要素が無ければ構文エラーかリテラル扱いになる
  • 正規表現で「任意の文字列」を書くには .*。. が「任意の一文字」、* が「その繰り返し」
  • xabz が引っかかったのは * のせいではなく部分一致のせいだ。これは二つ先の節で別に扱う

? と . — 一文字を指す二つの方法

両方に「任意の一文字」を表す記号があるが、使う文字が違う。グロブは ?、正規表現は . だ。そしてグロブでの . はただの句点である。特別な意味はまったく無い。

# グロブの ? - ちょうど一文字
$ ls ?.txt
a.txt
b.txt

# グロブでは ? がドットも拾う。ドットはグロブでは普通の文字だ
$ ls a?txt
a.txt

# 正規表現の . - ここでも一文字、だからドット以外も引っかかる
$ printf '%s\n' a.txt axtxt aatxt | grep 'a.txt'
a.txt
axtxt
aatxt

最後の出力が実務でよく事故を起こす。grep 'a.txt' と書くと人間は「a.txt というファイル名」を探しているつもりだが、grep は「a、任意の一文字、txt」と読む。ファイル名やドメインのようにドットを含む文字列を正規表現で探すときは a\.txt とドットをエスケープしなければならない。逆にグロブではドットをエスケープする場面がない。そもそも特殊文字ではないからだ。

  • グロブ ? — ちょうど一文字。0文字も駄目、2文字も駄目
  • グロブ . — 文字通りの句点。エスケープ不要
  • 正規表現 ? — 「直前が0回または1回」。基本正規表現(BRE)では \? と書く必要があり、grep -E では ? のまま使える
  • つまり ? という一文字が両側でまったく別の仕事をする。グロブでは「一文字を消費」、正規表現では「直前を任意に」

アンカー — 名前全体か部分か

この差は * の意味の違いよりも人を混乱させる。グロブは名前全体と照合される。暗黙のうちに前後が固定されている。正規表現は既定が部分一致だ。行のどこかにありさえすれば引っかかる。

# グロブ - 名前全体が txt でなければならない。そんなファイルは無い
$ ls txt
ls: cannot access 'txt': No such file or directory

# 正規表現 - 行の中のどこかに txt があれば引っかかる
$ printf '%s\n' a.txt notes.log | grep 'txt'
a.txt

だから正規表現で「名前全体がこれ」を表すには ^ と $ を自分で付ける必要がある。前節の grep -E '^ab*$' が xabz を落とした理由がこれだ。逆にグロブで「どこかに含む」を表すには両側に * を付けて *txt* と書く。

対応関係を表にすると頭に残る。左と右が同じ意味になる組だ。

[...] は否定で分かれる

角括弧は両側で最も似ている部分だ。[abc]、[a-z]、[[:digit:]] といった表記はグロブでも正規表現でも同じ意味で動く。POSIX 文字クラスまで共有している。ところが否定の表記一つで分かれる。

# グロブの標準的な否定は [!...]
$ ls [!a]*.txt
b.txt

# bash はグロブでも [^...] を否定として受け付ける
$ ls [^a]*.txt
b.txt

# 正規表現の否定は [^...]
$ printf '%s\n' a.txt ab.txt b.txt | grep '^[^a]'
b.txt

# 正規表現で [!...] は否定ではなく「! または a」という集合だ
$ printf '%s\n' a.txt ab.txt b.txt '!x.txt' | grep '^[!a]'
a.txt
ab.txt
!x.txt

最後の出力を見れば状況がはっきりする。正規表現に [!a] と書くと「a でないもの」ではなく「! または a」になる。意図と正確に反対に動きながら、エラーは出ない。

bash が寛容なことが移植性の問題になる

ls [^a]*.txt がうまく動いたので、グロブでも [^...] を使ってよいと考えやすい。それは bash の拡張だ。同じパターンを dash に渡すとこうなる。

$ dash -c 'cd /tmp/demo; echo [!a]*.txt'
b.txt

$ dash -c 'cd /tmp/demo; echo [^a]*.txt'
a.txt ab.txt abb.txt

完全にひっくり返った。dash では [^a] は否定ではなく「文字 ^ または文字 a」という集合なので、a で始まる名前を全部集めてくる。排除しようとしたものを正確に選んできたわけだ。そしてここでも警告は一行も出ない。

配布先のシステムで /bin/sh が dash に繋がっていることは珍しくない。消したり移したりするスクリプトでこの反転が起きると、結果は静かに最悪へ向かう。

  • グロブには [!...]、正規表現には [^...]。この二つだけを使えばどのシェルでも意味が変わらない
  • bash が [^...] を受け付けることは、使ってよいという意味ではない。テストを通してしまう寛容さが移植性では危険になる
  • 範囲 [a-z] はロケールの照合順序に左右される。安全にいくなら [[:lower:]] のような文字クラスを使う
  • [[:digit:]] のような POSIX クラスは両側でそのまま通る。ls *[[:digit:]]*.txt と grep '[[:digit:]]' のどちらも動く

グロブはファイル名専用の文法ではない

グロブを「コマンドラインでファイルを選ぶときに使うもの」としてだけ知っていると半分だ。bash の中でグロブが使われる場所は四つあり、そのうち三つはファイルが一切関わらない。

case 文の各分岐

$ for v in report.log a.txt sub README; do
>   case "$v" in
>     *.log)  echo "$v -> log" ;;
>     *.txt)  echo "$v -> text" ;;
>     [A-Z]*) echo "$v -> uppercase-start" ;;
>     *)      echo "$v -> other" ;;
>   esac
> done
report.log -> log
a.txt -> text
sub -> other
README -> uppercase-start

case の各分岐ラベルはグロブだ。最後の *) が「それ以外すべて」として動くのも、グロブの * が任意の文字列と一致するからである。ここに正規表現を入れると大抵どの分岐にも当たらない。case $v in ^ab.*$) は「^ab で始まり $ で終わる文字列」を探すことになる。

パラメータ展開のパターン欄

$ p="/var/log/app/server.access.log"

$ echo "${p##*/}"
server.access.log

$ echo "${p%.*}"
/var/log/app/server.access

$ echo "${p%%.*}"
/var/log/app/server

$ n="v1.2.3-rc4"
$ echo "${n//[!0-9]/}"
1234

${v#pat}・${v##pat}・${v%pat}・${v%%pat}・${v/pat/rep}・${v//pat/rep} の pat の位置はすべてグロブだ。ここでも * は「任意の文字列」であり、一文字版と二文字版(# と ##)はそれぞれ最短でと最長で切り落とすという違いになる。

最後の例の ${n//[!0-9]/} が「数字でない文字を全部消す」として動くのも、グロブの [!...] 否定のおかげだ。ちなみに dash には ${v//pat/rep} 自体が無く Bad substitution で死ぬ。${v#pat} と ${v%pat} は POSIX なので dash でも動く。

== はグロブ、=~ だけが正規表現

bash の中で正規表現を使う場所は [[ x =~ re ]] ただ一つだ。すぐ隣にある [[ x == pat ]] はグロブである。二つの演算子が同じ角括弧の中に並びながら文法が違うことが、この箇所を難しくしている。

$ s="aXbXc"

$ [[ $s == a*c ]] && echo true || echo false
true

$ [[ $s =~ a*c ]] && echo true || echo false
true

$ [[ $s =~ ^a*c$ ]] && echo true || echo false
false

$ t="aaac"
$ [[ $t =~ ^a*c$ ]] && echo true || echo false
true

二行目が罠だ。=~ に a*c を入れたのに true が出た。グロブのように動いたからではなく、正規表現 a*c が「a が0回以上の後に c」であり、これは文字列の中の c 一文字だけでも成立するからだ。部分一致なので偶然に真になった。アンカーを付けた三行目でようやく false が出る。

偶然当たる結果が一番たちが悪い。テストを通って本番に出た後、入力の形が少し変わったときに初めて外れる。=~ には習慣的にアンカーを付けるほうがよい。

代わりに =~ だけができることもある。一致した部分を取り出すことだ。

$ v="v2.10.3"
$ [[ $v =~ ^v([0-9]+)\.([0-9]+)\.([0-9]+)$ ]] &&
>   echo "major=${BASH_REMATCH[1]} minor=${BASH_REMATCH[2]} patch=${BASH_REMATCH[3]}"
major=2 minor=10 patch=3

$ [[ $v == v*.*.* ]] && echo "matched, but no captured parts"
matched, but no captured parts

グロブにキャプチャは無い。== は真偽だけを返す。バージョン文字列を割ったりログ行からフィールドを抜いたりするのは正規表現の仕事であり、BASH_REMATCH 配列がその結果を収める。0番の要素が一致した全体、1番からが括弧のグループだ。

引用符が文法を決める

同じ行で引用符一つで意味が変わる。この節は シェルのクォート規則全般ではなく、グロブと正規表現が分かれる部分だけを見る。

$ f='report.log'
$ pat='*.log'

$ [[ $f == $pat ]]   && echo true || echo false
true

$ [[ $f == "$pat" ]] && echo true || echo false
false

$ re='^rep.*\.log$'

$ [[ $f =~ $re ]]    && echo true || echo false
true

$ [[ $f =~ "$re" ]]  && echo true || echo false
false

規則は一つだ。== と =~ の右辺を引用符で囲むと、パターンではなくリテラル文字列になる。[[ $f == "*.log" ]] は「ファイル名がちょうどアスタリスク・ドット・l・o・g の六文字か」を問うており、そんな名前は無いので false になる。

=~ の側のほうがよくやられる。正規表現の中に空白があるので引用符で囲んだら、急に何も一致しなくなるという状況だ。正規表現を変数に入れて引用符なしで使うのが標準的な書き方である。

  • [[ $f == *.log ]] — 右辺がグロブパターン。真
  • [[ $f == "*.log" ]] — 右辺がリテラル。偽
  • [[ $f =~ $re ]] — 正規表現として解釈。これが推奨形
  • [[ $f =~ "$re" ]] — リテラルに降格。正規表現のメタ文字が全部死ぬ
  • 逆にリテラル比較をしたいときは意図的に引用符を付ける。ユーザー入力をそのまま比較するときに有用だ
  • grep・find に渡すパターンは必ず引用符で囲む。そうしないとシェルが先にグロブとして展開する

合うものが無いとパターンがそのまま残る

グロブにしかない動作で、スクリプト事故の常連だ。パターンに合うファイルが一つも無いと、シェルはパターン文字列をそのまま残す。

$ ls *.csv
ls: cannot access '*.csv': No such file or directory

$ for f in *.csv; do
>   echo "loop sees: [$f]"
>   [ -e "$f" ] && echo "  exists" || echo "  DOES NOT EXIST"
> done
loop sees: [*.csv]
  DOES NOT EXIST

.csv ファイルが無いのにループが一度回る。そして $f には *.csv という五文字が入っている。これで rm や mv をしたら何が起きるかは、わざわざ実験しなかった。

方法は三つある。

$ shopt -s nullglob
$ cnt=0; for f in *.csv; do cnt=$((cnt+1)); done; echo "iterations: $cnt"
iterations: 0

$ shopt -u nullglob; shopt -s failglob
$ for f in *.csv; do echo "$f"; done
bash: no match: *.csv

$ shopt -u failglob
$ for f in *.csv; do [ -e "$f" ] || continue; echo "processing $f"; done

最後のものがオプションに依存しない方法なので、他人の環境で回るスクリプトにはこれが向く。nullglob は楽だが全体スイッチなので、スクリプトの途中で有効にすると他の場所で期待していた動作まで変えてしまう。failglob は対話シェルで打ち間違いを捕まえるのに役立つ。

  • 既定値(nullglob off)— 合わなければパターンのまま。最も危険な既定値だが POSIX がそう決めている
  • nullglob on — 合わなければ何も残らない。繰り返しが0回になる
  • failglob on — 合わなければエラーで止まる。no match のメッセージが出て終了ステータスが0でなくなる
  • 手動の防御 — ループの先頭に [ -e "$f" ] || continue。どのシェルでも同じように動く
  • 正規表現にはこの問題が最初から無い。grep が見つけられなければ出力が空になり終了ステータスが1になるだけで、パターンがデータに化けることはない

ドットで始まる名前

グロブには正規表現に無い規則がもう一つある。先頭のドットは明示的に照合しなければならない。* は「任意の文字列」と言いながら .bashrc を拾わない。

$ echo *
a.txt ab.txt abb.txt b.txt notes.log report.log sub

$ echo .*
.bashrc .hidden

$ shopt -s dotglob; echo *
.bashrc .hidden a.txt ab.txt abb.txt b.txt notes.log report.log sub

$ shopt -u dotglob
$ shopt globskipdots
globskipdots    on

$ shopt -u globskipdots; echo .*
. .. .bashrc .hidden

三つのことが一度に見える。第一に、* は隠しファイルを飛ばす。これはシェルの特別規則であって、* の意味から導かれるものではない。第二に、dotglob を有効にするとその規則が消えて * が全部を拾う。第三に、echo .* が . と .. 無しで出たのは bash 5.2 で追加された globskipdots が既定で有効になっているためだ。無効にすると昔の動作が戻る。

最後の項目が重要だ。かつては rm -rf .* のようなコマンドが上位ディレクトリまで触る事故につながった。bash 5.2 以上では既定で塞がれているが、古いシェルでは依然として開いている。

  • グロブ — 先頭のドットは特別扱い。.bashrc を拾うにはパターンがドットで始まる必要がある
  • 正規表現 — そんな規則は無い。grep '.*' は .bashrc をそのまま拾う
  • dotglob — 有効にすると * が隠しファイルまで含む。バックアップスクリプトでよく有効にする
  • globskipdots — bash 5.2 で新設、既定で on。. と .. をグロブの結果から外す
  • スラッシュも似ている。グロブの * は / を越えない。下位ディレクトリを拾うには */*.log のように階層を明示するか globstar を有効にする

find -name はグロブ、find -regex は正規表現

find は二つの文法を一つのコマンドの中に併せ持つので、最も紛らわしい場所だ。-name・-path はグロブ、-regex は正規表現である。そして照合する対象まで違う。

$ find . -name '*.log' | sort
./notes.log
./report.log
./sub/deep.log

$ find . -name 'deep.log'
./sub/deep.log

$ find . -regex 'deep\.log'

$ find . -regex '.*/deep\.log'
./sub/deep.log

$ find . -name 'sub/*'

三番目のコマンドが何も出力しなかったのが罠だ。-regex は探索が作り出したパス文字列全体と照合され、部分一致ではなく全体一致である。実際のパスが ./sub/deep.log なので deep\.log では絶対に合わない。前を .*/ で開けてやる必要がある。

五番目も似ている。-name はパスの最後の断片しか見ないので、スラッシュを含むパターンは構造的に絶対に合わない。パスの形で絞るなら -path '*/sub/*' を使う。

ここに引用符の問題が重なると、エラーメッセージが難解になる。

$ find . -name *.log
find: paths must precede expression: `report.log'
find: possible unquoted pattern after predicate `-name'?

$ find . -name '*.log' | sort
./notes.log
./report.log
./sub/deep.log

最初のコマンドが失敗したのは find の問題ではない。シェルが先に *.log を展開して find . -name notes.log report.log にして渡したからだ。find は二番目の引数をパスと勘違いして抗議する。親切にも二行目で原因を指摘してくれるが、このメッセージを見たことがなければ読み取りにくい。

もっと悪いのはエラーすら出ない場合だ。現在のディレクトリに .log ファイルがちょうど一つあれば find . -name *.log はその一つだけを静かに見つけてくれる。そしてファイルが二つに増えた日に壊れる。

  • -name — グロブ、ファイル名(パスの最後の断片)のみが対象。スラッシュは絶対に合わない
  • -path — グロブ、パス全体が対象。* が / を越える点がシェルのグロブと違う
  • -regex — 正規表現、パス全体が対象、全体一致。GNU find の既定方言は emacs 系で -regextype posix-extended で変えられる
  • BSD・macOS の find は -regextype の代わりに -E を使う。GNU findutils 4.10.0 に -E を渡すと unknown predicate として拒否される
  • 結果を他のコマンドに渡すときの空白・改行の問題は find・xargs の空白の罠のほうで別に扱った

拡張グロブと globstar

基本のグロブには繰り返し演算子も選択(alternation)も無い。bash はこれを extglob で補うが、既定では無効だ。

$ shopt extglob
extglob         off

$ ls !(*.log)
ls: cannot access '!(*.log)': No such file or directory

$ shopt -s extglob
$ ls @(a|b).txt
a.txt
b.txt

$ ls +(a)b*.txt
ab.txt
abb.txt

$ ls a*(b).txt
a.txt
ab.txt
abb.txt

無効の状態では !(*.log) はパターンではなく、ただその名前のファイルを探す文字列になる。有効にすると a*(b).txt が a.txt・ab.txt・abb.txt を全部拾う。*(b) が「b が0回以上」なので、正規表現の b* と同じ仕事をする。括弧の位置が反対なだけだ。

globstar も同じ事情である。

$ shopt globstar
globstar        off

$ echo **/*.log
sub/deep.log

$ shopt -s globstar
$ echo **/*.log
notes.log report.log sub/deep.log

$ echo **
a.txt ab.txt abb.txt b.txt notes.log report.log sub sub/deep.log sub/deep.txt

無効の状態の ** はただの * 二つなので、*/*.log と同じくちょうど一階層下だけを見る。有効にすると **/ が0階層以上を横断するので、現在の階層の notes.log まで含まれる。これを知らずに ** を使ったスクリプトが「なぜ下位ディレクトリを探さないのか」で時間を食う。

拡張グロブの表記意味正規表現の対応必要なオプション
?(p)p が0回または1回(p)?extglob
*(p)p が0回以上(p)*extglob
+(p)p が1回以上(p)+extglob
@(a|b)a または b のちょうど一つ(a|b)extglob
!(p)p でないもの否定先読みなどextglob
**/0階層以上のディレクトリ対応なしglobstar
[[:digit:]]数字一文字[[:digit:]]不要

!(p) の正規表現の対応がきれいでないのは、「何かでない文字列」が正規表現ではもともと厄介な注文だからだ。否定先読みを使うがそれ自体が別の主題なので、先読みの実践のほうに整理してある。

どこがグロブでどこが正規表現か

記号を覚えるより場所を覚えるほうが実務では早く効く。パターンを書く前に「ここはどちら側か」だけ判別すれば、残りは付いてくる。

場所文法照合する対象アンカー
コマンドラインの ls *.logグロブファイル名全体一致
for f in *.txtグロブファイル名全体一致
case $v in *.log)グロブ文字列(ファイル無関係)全体一致
[[ $v == pat ]]グロブ文字列全体一致
${v#pat} ${v%pat} ${v//pat/}グロブ文字列前・後・全体
[[ $v =~ re ]]正規表現(ERE)文字列部分一致
grep re / grep -E re正規表現(BRE/ERE)行部分一致
sed 's/re/rep/'正規表現(BRE)行部分一致
awk '/re/'正規表現(ERE)行またはフィールド部分一致
expr s : re正規表現(BRE)文字列先頭のみ
find -name / -pathグロブファイル名 / パス全体一致
find -regex正規表現パス全体全体一致

表の最後の列も併せて見る必要がある。grep は部分一致なのに find -regex は全体一致なので、同じ正規表現を移し替えると結果が変わる。expr はさらに違って、文字列の先頭からのみ照合し、一致した長さを数値で返す。

$ printf '%s\n' a ab abb | sed 's/ab*/X/'
X
X
X

$ printf '%s\n' a ab abb xyz | awk '/ab*/'
a
ab
abb

$ expr 'abb' : 'ab*'
3

sed が a を X に変えたのも、awk が a を出力したのも同じ理由だ。正規表現 ab* は b の無い a と一致する。expr の 3 は abb の三文字が一致したという意味である。

どちらを使うか

悩む必要のない場合がほとんどだ。場所が決まっていれば文法も決まっている。選択肢が生じるのは同じことを二つの方法でできるときで、そのときはグロブのほうが概ねよい。

  • ファイルを選ぶ仕事ならグロブ。ls *.log を ls | grep '\.log$' に書き換える理由がない。後者は空白や改行を含むファイル名で壊れる
  • 拡張子・接頭辞・接尾辞の判別ならグロブ。[[ $f == *.tar.gz ]] のほうが [[ $f =~ \.tar\.gz$ ]] より短く、エスケープも要らない
  • パスから断片を切るならパラメータ展開。${p##*/} は外部プロセスを起こさない。basename の呼び出しより速く $(...) も要らない
  • 部分を取り出す必要があれば正規表現。キャプチャが必要になった時点でグロブは候補から外れる。バージョン文字列の分解、ログのフィールド抽出がここに当たる
  • 個数が関わるなら正規表現。「数字3〜5桁」のような条件は {3,5} 無しには表しにくい。extglob でも個数の指定はできない
  • 移植性がかかるならグロブのほうが安全だ。正規表現はツールごとに方言が分かれるが、基本のグロブは POSIX シェル全体でほぼ同じである。ただし [^...] と extglob は例外だ

ハングルの混ざったデータを正規表現で扱うときは、また別の問題が付く。音節単位の照合が直感と食い違う箇所で、ハングル正規表現の罠のほうに別途整理した。

まとめ

同じ * なのに答えが違う理由は一つだ。グロブの * はそれ自体で「任意の文字列」を意味し、正規表現の * は直前にあるものを繰り返させる演算子である。ここから ? と . の役割が入れ替わり、アンカーの既定値が分かれ、角括弧の否定記号が分かれる。

実務で覚えておくべきは記号表より場所だ。bash の中では case・[[ == ]]・${}・ファイル名展開がすべてグロブで、正規表現は [[ =~ ]] 一つだけ。外に出れば grep・sed・awk・expr が正規表現で、find -name はまたグロブだ。

そしてこの領域は shopt 一行で動作が変わる。nullglob・failglob・dotglob・extglob・globstar・globskipdots がそれぞれ何を有効・無効にするのか分かっていれば、「昨日は動いたのに今日は動かない」の半分は事前に見当がつく。確認は一行だ。shopt を引数なしで打てば全部出る。

確認できなかったこと

  • すべての出力は Windows 10 上の Git Bash(MSYS2)、GNU bash 5.2.37 という一つの環境からのみ得た。Linux ネイティブの bash や macOS で同一かは突き合わせていない。特にファイルシステムが大文字小文字を区別しない環境では、[a-z] の範囲や nocaseglob 関連の結果が変わりうる
  • zsh と ksh はこのマシンに入っておらず動かせなかった。zsh はグロブ文法がかなり拡張されており(修飾子、正規表現風グロブなど)、この記事の「基本のグロブに繰り返し演算子は無い」という記述はそのままは当てはまらない。本文の他シェル比較は dash 一つだけで確認した範囲だ
  • globskipdots が bash 5.2 で追加されたという点は、このマシンの 5.2.37 でオプションが存在し既定で on であるという事実までしか確認していない。5.1 以下でオプションが無いことは自分で動かしていない。古いサーバーに触る機会があれば shopt globskipdots で各自確認するほうがよい
  • GNU find 4.10.0 の -regex の既定方言は -regextype 無しで .+ を受け入れた。文書上の既定値は emacs 系だが、どの文法まで通るのか境界を網羅的に試してはいない。移植性が必要なら -regextype posix-extended を明示するほうがよい
  • ロケールによる [a-z] の範囲の変化は実測していない。文字クラスを勧めたのは広く知られた推奨に従ったのであって、自前の実験結果ではない
  • POSIX 仕様原文の Pattern Matching Notation 節は直接開けなかった。表記の規則は GNU bash マニュアルの該当節で突き合わせており、仕様の条文自体は引用していない
