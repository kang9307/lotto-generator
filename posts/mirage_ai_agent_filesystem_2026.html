AI 에이전트를 위한 통합 가상 파일시스템 - Mirage가 제시하는 2026 새 표준

멀티 에이전트 시대의 진짜 병목은 모델이 아니라 스토리지다 - 가상 파일시스템이 AI 인프라의 다음 표준이 되는 이유

2026-05-21 IT/기술

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: AI 에이전트의 보이지 않는 병목 - 파일시스템 액세스

2026년 상반기를 지나오면서 AI 에이전트 담론의 무게중심이 또 한 번 이동했습니다. 작년까지만 해도 화두는 "어떤 모델이 가장 똑똑한가", "에이전트를 어떤 프롬프트로 묶을 것인가"였습니다. 그런데 멀티 에이전트 시스템을 1년 이상 운영해 본 팀들의 사후 회고를 보면, 정작 실 서비스의 발목을 잡은 것은 모델 성능이 아닙니다. 에이전트가 파일을 어떻게 읽고 쓰고 공유하는가 - 이 보이지 않는 영역이 가장 큰 병목이었습니다.

예를 들어 본인이 운영해 본 사내 코드 리뷰 에이전트는 모델은 Claude Sonnet, 도구는 MCP, 호스트는 Claude Code였지만, 실제 디버깅의 80%는 "왜 이 파일이 안 보이지", "어떤 권한으로 어디에 썼지", "다른 에이전트가 작업 중인 파일과 어떻게 충돌하지" 같은 스토리지 계층의 문제였습니다. 모델 비용보다 파일 동기화 비용이 더 들었습니다. 이런 사례가 누적되면서 2026년 5월 hada.io 트렌딩 2위에 오른 Mirage 프로젝트는 단순한 한 개의 도구가 아니라 "에이전트 인프라의 다음 표준이 무엇이어야 하는가"라는 더 큰 질문을 끌어냅니다.

이 글은 Mirage라는 단일 도구의 사용법을 다루는 글이 아닙니다. Mirage를 단서로 삼아 AI 에이전트 시대의 통합 가상 파일시스템(Virtual Filesystem for Agents)이 왜 등장했고, 어디에 쓸 수 있으며, 한국 개발자와 한국 클라우드 환경에서 어떻게 활용해야 하는가를 12개 섹션에 걸쳐 정리합니다. 본인의 운영 경험과 시장 흐름을 결합한 본인 시각의 분석이며, Mirage README의 직번역이나 단순 소개가 아니라는 점을 미리 분명히 밝힙니다.

현재 AI 에이전트의 파일 처리 방식과 한계

지금 시점에서 AI 에이전트가 파일을 다루는 방식은 거칠게 말해 다섯 가지입니다. ChatGPT의 code interpreter 같은 샌드박스 컨테이너, Anthropic Claude의 MCP filesystem 서버, OpenAI Codex Goals 같은 에이전트 호스트가 직접 마운트한 로컬 디렉터리, LangChain·LlamaIndex 같은 프레임워크 안의 retrieval 어댑터, 그리고 클라우드 SDK를 통한 S3·GCS 직접 호출이 그것입니다. 문제는 이 다섯 가지가 서로 인터페이스가 다르고, 권한 모델이 다르고, 세션 보존 정책이 다르다는 점입니다.

구체적으로 어떤 문제가 발생하는지 본인이 경험한 사례를 정리하면 다음과 같습니다. 첫째, 상태 비유지 문제입니다. ChatGPT 샌드박스는 세션이 끝나면 파일이 사라집니다. 같은 사용자가 어제 만든 분석 결과를 오늘 이어서 다듬으려고 해도 처음부터 다시 업로드해야 합니다. 둘째, 인터페이스 파편화입니다. Claude는 read_file·write_file MCP 도구를 쓰고, OpenAI는 자체 함수 호출 스펙을 쓰고, LangChain은 vectorstore.similarity_search()라는 전혀 다른 추상화를 씁니다. 같은 사내 데이터에 접근하려는데 에이전트 호스트마다 다른 코드를 짜야 합니다. 셋째, 멀티 에이전트 협업의 부재입니다. 두 에이전트가 같은 파일에 동시에 쓰면 누가 이기는가, 누가 락을 잡는가 같은 기본적인 합의가 없습니다. 넷째, 이종 백엔드 통합의 부재입니다. 로컬 파일 + S3 + 사내 Git을 하나의 작업공간으로 보고 싶지만 에이전트는 셋을 별개로 인식합니다.

이 네 가지 문제는 단일 모델의 성능을 아무리 끌어올려도 해결되지 않습니다. 모델 위에 깔린 인프라 레이어가 통일되어야 풀리는 문제입니다. Mirage가 던지는 가설은 바로 이 지점에 있습니다.

통합 가상 파일시스템(Virtual FS for Agents)이란

가상 파일시스템이라는 개념 자체는 새로운 것이 아닙니다. 리눅스의 VFS, FUSE, 그리고 클라우드 시대의 rclone·s3fs까지 백엔드를 추상화하는 시도는 30년 이상 누적되어 왔습니다. AI 에이전트를 위한 가상 파일시스템은 이 전통을 잇되, 에이전트가 사용하기에 최적화된 몇 가지 요구사항을 추가합니다.

본인이 정리한 핵심 요구사항은 다섯 가지입니다. 첫째, 다양한 백엔드(로컬, S3, Git, DB, 메모리)를 단일 인터페이스로 노출해야 합니다. 에이전트 코드는 백엔드가 무엇이든 동일한 read/write/list API만 호출합니다. 둘째, 에이전트 관점에서 일관된 의미론이어야 합니다. 같은 read 호출이 어떤 백엔드에서는 동기, 어떤 백엔드에서는 비동기여서는 안 됩니다. 응답 형태도 통일되어야 합니다. 셋째, 권한 모델이 명시적이어야 합니다. 어느 에이전트가 어느 경로에 어떤 권한으로 접근하는지가 단일 정책으로 정의되어야 합니다. 넷째, 세션 사이 상태 보존이 가능해야 합니다. 어제의 작업이 오늘 이어져야 합니다. 다섯째, 관찰 가능성이 보장되어야 합니다. 누가 언제 무엇을 읽고 썼는지 감사 로그로 남아야 합니다.

이 다섯 가지가 동시에 만족되어야 에이전트 인프라가 운영 가능한 수준에 도달합니다. 지금까지는 어느 솔루션도 다섯 가지를 모두 만족하지 못했습니다. MCP filesystem 서버는 1번을 부분적으로, LangChain DataLoader는 2번을 부분적으로 다룰 뿐입니다. Mirage가 의미 있는 것은 이 다섯 가지를 한 묶음으로 다루려 한다는 시도 자체에 있습니다.

Mirage의 핵심 아이디어

Mirage의 자세한 구현은 GitHub 저장소에서 직접 확인하는 편이 정확하므로 본 글에서는 핵심 발상만 짧게 정리합니다. Mirage는 TypeScript로 작성된 가상 파일시스템 레이어이며, 백엔드 어댑터를 플러그인 형태로 받아 하나의 마운트 트리에 합칩니다. /local은 로컬 디스크, /s3는 S3 버킷, /git은 깃 저장소, /db는 데이터베이스 테이블 같은 식입니다. 에이전트는 fs.read('/s3/reports/2026-05.csv') 한 줄로 어떤 백엔드든 접근합니다.

여기서 본인이 주목한 설계 선택은 두 가지입니다. 첫째, 경로(path)를 단일 식별자로 쓴다는 점입니다. URI를 쓰지 않고 POSIX 스타일 경로를 고수합니다. 이유는 분명합니다. LLM이 가장 잘 다루는 식별자가 POSIX 경로이기 때문입니다. 모델의 학습 데이터에 압도적으로 많이 등장하는 형식이므로, 에이전트가 경로를 추론하고 조작하는 비용이 최소화됩니다. 둘째, 읽기/쓰기 인터페이스를 의도적으로 좁게 유지한다는 점입니다. read·write·list·delete·stat 다섯 개만 노출하고, 나머지는 백엔드 고유 능력으로 위임합니다. 이는 에이전트가 인터페이스를 "외워야" 하는 비용을 줄이는 트레이드오프입니다.

본인 관점에서 Mirage가 흥미로운 것은 도구 자체의 완성도라기보다, 이 두 가지 설계 선택이 "에이전트가 가장 잘 다룰 수 있는 추상화는 무엇인가"라는 질문에 대한 시장의 답을 보여준다는 점입니다.

왜 지금 등장했나 - Agentic AI 폭증과 MCP 표준화

Mirage가 2026년 5월에 화제가 된 것은 우연이 아닙니다. 두 가지 거시 흐름이 같은 시점에 임계점을 넘었기 때문입니다.

첫째, Agentic AI의 폭증입니다. 2024년까지만 해도 "에이전트"는 LangChain 같은 프레임워크 안에서 체인 조작하는 것을 의미했습니다. 2025년에 Claude Code·Codex·Cursor가 코드 에이전트를 상용 수준으로 끌어올렸고, 2026년에는 한 명의 개발자가 동시에 3~5개의 에이전트를 돌리는 것이 흔한 일이 되었습니다. 멀티 에이전트가 일상이 되면서 "에이전트끼리 공유하는 작업공간"이 필요해졌습니다.

둘째, MCP(Model Context Protocol) 표준화입니다. Anthropic이 2024년에 공개한 MCP는 2025~2026년에 걸쳐 사실상 업계 표준이 되었습니다. MCP는 모델과 도구 사이의 통신 규약을 정의했고, 그 결과 "도구"라는 추상화가 통일되었습니다. 그런데 MCP는 인터페이스 규약이지 구현이 아닙니다. 같은 read_file 도구가 어떻게 구현되는가는 여전히 호스트마다 다릅니다. Mirage 같은 가상 FS 레이어가 등장한 것은 MCP 위에 한 단계 더 올려진 추상화가 필요하다는 시장 신호입니다.

이 두 흐름의 교차점에서 "에이전트가 다루기 좋은 통합 스토리지 추상화"가 필연적으로 요청되었고, Mirage는 그 응답 중 하나입니다. 본인의 예상으로는 향후 12~18개월 안에 비슷한 시도가 5~10개 더 등장할 것이고, 그중 1~2개가 사실상 표준이 될 가능성이 높습니다.

유사 시도들 비교 - LangChain, LlamaIndex, MCP filesystem

Mirage가 진공 상태에서 등장한 것은 아닙니다. 비슷한 문제를 다른 각도에서 풀려고 한 선행 시도들과 비교해야 위치가 분명해집니다.

도구 추상화 단위 주 용도 약점
LangChain VectorStore 임베딩 벡터 RAG 검색 읽기 중심, 쓰기 모델 부재
LlamaIndex DataSources 문서 인덱싱·검색 POSIX 의미론 부재
MCP filesystem server 로컬 파일 단일 백엔드 노출 이종 백엔드 통합 부재
Mirage POSIX 경로 이종 백엔드 통합 초기 단계, 권한 모델 미성숙
rclone / s3fs POSIX 경로 클라우드 마운트 에이전트 특화 기능 부재

본인이 주목하는 차별점은 두 가지입니다. LangChain·LlamaIndex는 "에이전트가 검색하기 좋은 인덱스"에 초점이 맞춰져 있고, MCP filesystem 서버는 "단일 백엔드를 표준 프로토콜로 노출"하는 수준에 머물러 있습니다. Mirage는 그 둘 사이에 있는 "이종 백엔드를 단일 POSIX 트리로 묶는다"는 빈자리를 노립니다. 이 위치 선정이 정확하다면 Mirage가 아니더라도 유사한 추상화가 결국 자리를 잡을 것입니다.

실무 시나리오 - 어디에 쓸 수 있나

추상적 논의를 본인이 직접 운영해 본 또는 운영을 검토해 본 네 가지 시나리오로 구체화합니다.

1) 멀티 에이전트 협업 - 공유 작업공간

코드 작성 에이전트 A, 테스트 작성 에이전트 B, 문서 작성 에이전트 C가 같은 저장소를 다룬다고 가정합시다. 현재는 셋이 각자의 로컬 클론을 들고 있고 합의는 사람이 PR로 중재합니다. 가상 FS가 있으면 셋이 동일한 마운트 트리를 공유하고, 락·머지 정책을 가상 FS 레이어에서 처리할 수 있습니다. 단일 에이전트의 출력 품질보다 합의 비용이 더 큰 멀티 에이전트 시스템에서 이 효과는 즉시 체감됩니다.

2) 장기 메모리 - 대화 사이 파일 보존

"어제 우리가 분석하던 그 CSV 다시 열어줘"라는 발화가 그대로 작동해야 합니다. 현재 ChatGPT 샌드박스로는 불가능하지만 가상 FS의 /persist 마운트에 어제의 산출물이 보관되어 있으면 가능합니다. 본인이 운영해 본 사내 보고서 에이전트에서 이 시나리오가 가장 강한 효용을 보였습니다. 매일 새로 시작하지 않아도 되는 것만으로 사용성이 압도적으로 올라갑니다.

3) 외부 데이터 통합 - S3 + DB + Git을 하나로

실 서비스 데이터는 S3 로그, RDB 트랜잭션, Git의 코드 세 군데에 흩어져 있습니다. 분석 에이전트가 세 곳을 동시에 보려면 지금은 세 가지 SDK를 쓰는 코드를 작성해야 합니다. 가상 FS가 있으면 /s3/logs, /db/transactions, /git/src 세 경로를 같은 API로 다룹니다. 본인 추정으로 이 시나리오 하나만으로 데이터 분석 에이전트의 개발 시간이 30~40% 줄어듭니다.

4) 코드 에이전트 - Claude Code, Codex Goals 등

Claude Code와 Codex Goals 같은 코드 에이전트는 이미 로컬 파일에는 잘 접근합니다. 다음 단계는 로컬을 넘어 /s3, /db를 코드처럼 다루는 것입니다. 예를 들어 "프로덕션 로그를 보고 이번 주 가장 자주 발생한 에러의 원인을 코드에서 찾아 수정해줘"라는 한 줄 명령이 가능해집니다. 본인 시각으로 이 시나리오가 코드 에이전트의 가장 큰 다음 도약입니다.

기술 스택 관점 - 인터페이스 디자인의 선택지

가상 FS를 직접 만들 일이 없더라도, 본인이 쓰는 에이전트 인프라의 추상화를 평가할 줄 알아야 합니다. 핵심 평가 축은 다섯 가지입니다.

  • 인터페이스의 최소성: 노출되는 메서드가 다섯 개 이내인가, 아니면 스무 개 이상으로 비대한가. LLM은 적은 인터페이스를 더 잘 다룹니다.
  • 경로 표현의 일관성: POSIX인가, URI인가, JSON 경로인가. 본인 추천은 POSIX입니다. 학습 데이터 분포상 LLM이 가장 잘 다룹니다.
  • 에러 응답의 결정론성: 같은 에러가 같은 메시지로 돌아오는가. 에이전트가 자동 복구하려면 메시지 패턴이 안정적이어야 합니다.
  • 스트리밍 지원: 큰 파일을 한 번에 읽지 않고 청크로 받을 수 있는가. 컨텍스트 윈도 한계 때문에 이 기능이 점점 중요해집니다.
  • 관찰 가능성: 모든 read/write가 OpenTelemetry로 추적되는가. 운영 단계에서 결국 이 영역이 가장 큰 운영 부담이 됩니다.

이 다섯 축으로 본인 환경의 도구들을 점검해 보면 대부분의 인터페이스가 1~2개 축에서만 합격점을 받고 나머지는 부족합니다. 가상 FS 영역의 표준이 정해지는 시점은 이 다섯 축을 모두 통과한 도구가 등장할 때입니다.

AI 에이전트 인프라의 진화 흐름

본인이 정리한 시기별 흐름은 다음과 같습니다. 이 흐름의 한 페이지 도식이 본인의 사고 골격입니다.

  • 2023 - LangChain 체인 시대: 체인·에이전트·메모리가 프레임워크 안에 갇혀 있던 시기. 같은 체인을 다른 호스트에서 쓰려면 처음부터 다시 짜야 했음.
  • 2024 - MCP 표준화: Anthropic이 MCP를 공개. 도구와 모델 사이의 통신 규약이 표준화. 같은 도구를 여러 호스트에서 쓸 수 있게 됨.
  • 2025 - 멀티 에이전트 협업: Claude Code·Codex·Cursor가 코드 에이전트를 상용화. 한 사람이 여러 에이전트를 동시에 운영하는 패턴이 일상화.
  • 2026 - 통합 파일시스템: 이질적 백엔드를 한 트리로 묶는 가상 FS의 부상. Mirage 같은 실험적 프로젝트가 그 신호.
  • 2027 예측 - 권한·감사·비용 미터링 표준화: 가상 FS 위에 권한 모델과 감사 로그, 비용 미터링이 표준화. 엔터프라이즈 도입의 전제조건.

이 흐름은 인프라 영역의 일반적 진화 패턴을 따릅니다. 추상화 → 표준화 → 통합 → 거버넌스. 본인 예상으로 2027~2028년에는 가상 FS가 "에이전트 인프라의 기본 요소"로 인식될 것이고, 그 시점에 가상 FS를 다루지 못하는 팀은 빠르게 뒤처질 것입니다.

한국 개발자 / 한국 클라우드 환경에서의 응용

글로벌 흐름을 한국 환경에 적용할 때 고려할 점이 몇 가지 있습니다.

첫째, 네이버 클라우드·KT 클라우드·NHN 클라우드의 객체 스토리지 어댑터입니다. Mirage 같은 도구는 기본적으로 AWS S3·GCP·Azure를 우선 지원합니다. 한국 클라우드의 S3 호환 API에는 미세한 차이가 있어 그대로 쓰면 일부 메서드가 실패합니다. 본인이 시도해 본 결과 NHN Cloud Object Storage는 S3 호환이지만 multi-part upload 일부 헤더가 다릅니다. 한국 환경에 쓰려면 어댑터를 직접 패치하거나 한국 클라우드 전용 어댑터를 작성해야 합니다.

둘째, 망분리 환경입니다. 공공·금융 영역의 망분리 환경에서는 외부 LLM 호출이 막혀 있고, 사내 LLM(예: 하이퍼클로바X)을 쓰는 구조가 일반적입니다. 이 경우 가상 FS는 모두 사내 망 안에서 동작해야 하며, 사내 NAS·사내 Git·사내 RDB를 어댑터로 노출해야 합니다. 한국 환경에서는 외부 클라우드보다 사내 NAS 어댑터의 수요가 더 클 수 있습니다. 본인의 한국 SI 경험상 이 부분이 가장 큰 차별 포인트입니다.

셋째, 한국어 경로명 처리입니다. 한글 파일명을 어댑터가 어떻게 인코딩하는가가 의외로 큰 변수입니다. 일부 어댑터는 NFC, 일부는 NFD를 쓰고, 이 차이로 같은 한글 파일이 두 번 나타나는 버그가 발생합니다. 가상 FS를 도입할 때 본인이 가장 먼저 점검하는 항목입니다.

한계와 미해결 과제 - 보안, 권한, 비용

가상 FS가 만능은 아닙니다. 본인이 보는 미해결 과제는 다음과 같습니다.

  • 권한 모델: 어느 에이전트가 어느 경로에 어떤 권한으로 접근하는가를 단일 정책으로 표현하는 표준이 아직 없습니다. POSIX 권한·ACL·RBAC를 어떻게 매핑할지가 미정입니다.
  • 비용 회계: 가상 FS가 백엔드 호출을 묶어 보여줄수록 누가 얼마를 썼는지 추적이 어려워집니다. S3 호출 1만 건이 어느 에이전트에서 발생했는지 분해할 수 있어야 합니다.
  • 보안: 에이전트가 잘못된 권한으로 민감 파일에 접근했을 때 어떻게 막을 것인가. 단순 차단이 아니라 감사 로그·이상 탐지가 결합되어야 합니다.
  • 일관성 모델: 멀티 에이전트가 동시에 같은 파일에 쓰는 상황에서 last-writer-wins인지, CRDT인지, OT인지가 결정되지 않았습니다. 운영 단계에서 가장 큰 함정이 될 영역입니다.
  • 성능: 모든 호출이 어댑터를 거치므로 직접 호출보다 느립니다. 캐시·프리페치 전략이 표준화되어야 합니다.

이 다섯 가지는 본인 예상으로 향후 2~3년 동안 시장이 풀어야 할 숙제입니다. Mirage가 그 답을 모두 가지고 있다고 보지 않습니다. 다만 질문이 정확하다면 답은 결국 시장이 만들어 냅니다.

결론과 2026 하반기 전망

이 글의 핵심 명제로 돌아옵니다. 멀티 에이전트 시대의 진짜 병목은 모델이 아니라 스토리지입니다. 모델 성능이 평준화되는 속도가 빨라질수록 인프라 레이어가 차별화 요소가 됩니다. 가상 파일시스템은 그 인프라 레이어의 다음 표준 후보 중 하나이며, Mirage는 그 후보를 보여주는 시장 신호입니다.

본인이 한국 개발자에게 추천하는 행동 지침은 세 가지입니다. 첫째, 본인이 운영하는 에이전트가 파일을 다루는 방식을 한 번 도식화해 보세요. 다섯 가지 방식 중 어디에 속하는지, 어떤 한계를 겪고 있는지가 명확해집니다. 둘째, 사내 에이전트 인프라에 가상 FS 추상화를 한 단계 도입해 보세요. 처음부터 Mirage를 그대로 쓰지 않아도 됩니다. read·write·list 다섯 개 인터페이스만 본인 코드에 정의해도 큰 진전입니다. 셋째, 본인 사이트의 관련 글로 맥락을 확장하세요. OpenAI Codex Goals 실전 가이드, Ruflo로 보는 Claude Code 멀티 에이전트, 로컬 LLM 하드웨어 선택 가이드가 이 글과 가장 잘 어울립니다.

2026년 하반기 전망입니다. 본인 예측으로는 9월 전후로 Mirage와 경쟁할 1~2개의 가상 FS 프로젝트가 더 등장하고, 12월 즈음에는 MCP 진영이 가상 FS 표준 초안을 공식 발표할 가능성이 높습니다. 한국 클라우드 사업자 중에는 NHN Cloud나 네이버 클라우드가 자체 어댑터를 공개할 여지가 있고, 이 시점이 바로 한국 개발자가 한 발 앞서 움직일 수 있는 구간입니다. 가상 FS는 1년 뒤에는 "이미 도입한 사람과 아직 안 한 사람"으로 갈리는 영역이 될 것입니다. 지금 시작하는 사람이 그 격차의 수혜자입니다.
