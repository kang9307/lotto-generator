SameSite Lax、Strict、None - 哪些请求会丢掉 Cookie

从支付页面返回后为何变成未登录，用按请求类型的判定表读出答案

2026-07-31 开发/基础设施

症状：支付完成回来后发现已经退出登录

用户在购物车里点了支付，浏览器跳到外部支付服务商的页面，填好卡片信息完成授权，然后回到我们站点。可是登录状态没了。支付明明处理成功，偏偏进不去订单记录页面。

这类工单通常以延长会话有效期、去问支付服务商，或者干脆以无法复现为由悄悄关闭。可服务端日志里往往早就写着答案。返回的那条请求，Cookie 头里压根没有会话名。不是认证失败，而是Cookie 一开始就没被带上来。

决定要不要发送 Cookie 的不是服务端，而是客户端。参与这个决定的属性是 SameSite，取值只有三个。但这三个并不是「强、中、弱」的一条直线。它们按请求的类型分出不同的岔路。

  • Strict 对别的站点发起的请求一律不携带。哪怕是用户自己点了链接进来也不携带
  • Lax 只在地址栏会改变的跳转并且是安全方法时破例携带。这两个条件就是本文的核心
  • None 全都携带。代价是没有 Secure 时 Cookie 连保存都不会发生

本文不会以「那就改成 None 吧」收尾。那是不看原因就把门敞开。取而代之的是建立一套流程：先把这个 Cookie 必须搭载的请求逐条写下来。清单一旦定下，取值自然就出来了。

运行环境。下面所有输出都是在 Windows 10 Pro (10.0.19045) 上用 Node.js v22.16.0 (win32) 实际跑出来的。两台本地服务器绑定在任意高位端口(18081、18082)上做验证，实验结束后全部关闭。规范依据是 RFC 6265bis (draft-ietf-httpbis-rfc6265bis-22, 2025-12-01) 与 MDN。脚本一律写入文件后执行，没有作为 shell 参数或 heredoc 传递。

★本文未能直接验证的部分。没有启动浏览器，也没有观察 Cookie 存储。因此「这条请求会不会带上 Cookie」的判定，是把规范文字实现为代码后计算出来的结果，不是从真实浏览器观测到的。下表专门设了一列标明哪些行依据规范、哪些行来自实测。上线前请在目标浏览器上复核。

本文不涉及的内容。Web 安全通论与 CSRF 防护的整体框架已在Web 安全基础与 IDS 与 IPS 中讨论。这里只钻研一个点：SameSite 取值的行为。文中出现的域名、端口与 Cookie 名称全部为虚构。

1. 三个取值实际在区分什么

规范的句子很短。RFC 6265bis 把 Strict 定义为「只随同站点请求发送」，把 Lax 定义为「随同站点请求发送，并随跨站顶层导航发送」，把 None 定义为「同站点与跨站请求都发送」。麻烦在于，仅凭这三句话无法判断自己页面上的哪个元素属于哪一类。图片标签算顶层导航吗？表单提交呢？iframe 呢？

于是把规范的判定规则原样搬进代码，让页面可能产生的所有请求形态都跑一遍。

--- 3-2. the same table, but only the differences that matter ---
  shapes where Strict and Lax disagree:
    - cross-site link click
    - cross-site form GET
    - cross-site 302 landing as GET
  shapes where Lax and None disagree:
    - cross-site image load
    - cross-site script/css load
    - cross-site form POST
    - cross-site fetch / XHR
    - cross-site iframe load
    - cross-site 307 landing as POST
  • Strict 与 Lax 的分歧只有三行。链接点击、form GET，以及经 302 返回并以 GET 落地。三者的共同点都是地址栏会改变的跳转
  • Lax 与 None 的分歧是剩下的全部。图片、脚本、fetch、iframe，以及 POST
  • 也就是说 Lax 可以概括成「不搭载子资源」。别人的页面来拉我们服务器上的图片，并不会带上我们的会话。这也是 Lax 成为默认值的原因
  • 在同一站点内三个取值的行为完全一致。所以只在自家站点里点来点去的测试，永远暴露不出差别

2. 不写取值会变成什么

最常见的事故就从这里开始。完全不写 SameSite 的 Cookie 并不等于「不受限制」。RFC 6265bis 写明，属性缺失或取值无法识别时，将套用「等同于 Lax 的默认施行模式」。MDN 的说法相同：「若未设置 SameSite 属性，Cookie 默认按 Lax 对待。」

于是就会出现代码一行未改，某天支付回跳却坏掉的情形。服务端没变，变的是解释这个 Cookie 那一侧的默认策略。不写取值不是没做决定，而是把决定权交给了别人。

更糟的是写了却没生效。为此做了一个解析器，看看取值里出现拼写错误会怎样。

--- 2-3. the silent-typo trap, side by side ---
  SameSite=Strict     -> Strict
  SameSite=strict     -> Strict
  SameSite=Strick     -> Default(Lax)   <- NOT what the author typed
  Samesite=Strict     -> Strict
  SameSite =Strict    -> Strict
  • SameSite=Strick 不是错误。由于取值无法识别，它会悄悄退回默认施行模式，也就是 Lax
  • 与之相对，属性名称的大小写以及等号两侧的空白都是无害的。Samesite 和 SameSite =Strict 都能被正常处理
  • 也就是说危险的只有取值里的那一个拼写错误，而且只有它会毫无警告地改变策略
  • 因此实际有效的防线是把取值字符串放进常量，并在代码评审时用眼睛确认。语法检查器不会替你抓到这个错

默认值还附带一个条件。规范允许一种叫 Lax-allowing-unsafe 的可选兼容模式：仅限没有显式写出 SameSite 的 Cookie，并且只在它刚创建不久时，才可以搭载跨站 POST。规范指出「两分钟以内」看起来是合理的界限。

--- 3-3. the 2-minute window applied to a cross-site POST ---
  cookie age   10s  ->  maybe*   (explicit Lax would be: no)
  cookie age  119s  ->  maybe*   (explicit Lax would be: no)
  cookie age  121s  ->  no   (explicit Lax would be: no)
  cookie age 3600s  ->  no   (explicit Lax would be: no)
  a cookie that works in testing and fails in production may simply be older.

这往往正是「我这边是好的呀」的真相。开发者登录后立刻点支付，Cookie 是全新的；真实用户登录后放着，过很久才去支付。同一份代码看起来会随时间表现不同。由于该模式是可选的，能生效只算走运，绝不能作为设计依据。

3. 用了 None 却漏掉 Secure，Cookie 会被丢弃

只看症状就改成 SameSite=None 是很常见的反应。可这里有个陷阱，而且这个陷阱不报任何错误。RFC 6265bis 的保存算法里有这样一句：若 Cookie 的 same-site 标志为 None，则除非 secure-only 标志为真，否则中止算法并完全忽略该 Cookie。

服务器是否真的会发出那个响应头，以及此时响应看起来是什么样子，都直接验证了一遍。

node v22.16.0 / win32   server 127.0.0.1:18081

--- 7-1. server emits it, the jar decides ---
recipe             HTTP status   what left the server                    jar verdict
-----------------------------------------------------------------------------------------------
None, no Secure    200 OK        sid=abc; SameSite=None                  REJECTED  (None without Secure)
None + Secure      200 OK        sid=abc; SameSite=None; Secure          stored  (None + Secure)
Lax, no Secure     200 OK        sid=abc; SameSite=Lax                   stored  (Lax)
Strict + Secure    200 OK        sid=abc; SameSite=Strict; Secure        stored  (Strict + Secure)
none + secure      200 OK        sid=abc; samesite=none; secure          stored  (None + Secure)
None; Secure=1     200 OK        sid=abc; SameSite=None; Secure=1        stored  (None + Secure)

  every row returned 200. the server never objects.
  row 1 is thrown away before it is ever stored, so no request will carry it.
  row 6 shows Secure is a valueless flag: Secure=1 still reads as present.

六行全是 200 OK。服务器对这个组合毫无异议。服务器所做的只是把字符串放进响应头发出去，丢不丢弃的判定发生在另一侧。

--- 7-2. the failure you will actually observe ---
  HTTP/1.1 200 OK
  Set-Cookie: sid=abc; SameSite=None
  Date: Thu, 30 Jul 2026 20:33:11 GMT
  Connection: close
  Content-Length: 3

  response looks perfect. no 4xx, no log line, no exception.
  the symptom surfaces one request later, as a missing session,
  in a completely different part of the code. that is why it costs a day.

--- 7-3. why the rule exists, in one line ---
  SameSite=None means: send me on requests I did not initiate.
  Secure means: only over a protected transport.
  the spec refuses to let a cookie be maximally exposed and unprotected at once.
  • 失败根本不出现在响应里。状态码是 200，日志里没有，异常里也没有
  • 症状会在一条请求之后、在完全不同的代码区域以「没有会话」的形式浮现。这就是它能吃掉一整天的原因
  • Secure 是一个无取值的标志。正如上面第五、第六行，写成小写或写成 Secure=1，都会被读作「存在」
  • 规则本身是简单逻辑。None 的意思是「即使是我没有发起的请求也请把我带上」，Secure 的意思是「只走受保护的传输通道」，所以规范不允许一个 Cookie 同时处于最大暴露且毫无保护的状态

实务上顺序很重要。None 以 https 为前提。如果内部工具还在以明文提供服务，那么 None 不是可选项，而是必须先解决的前置条件。另外使用 __Host- 前缀可以强制 Secure、Path=/ 且不指定 Domain，从结构上堵住这类失误。

4. Set-Cookie 字符串究竟是怎么被读的

弄清一行 Set-Cookie 如何被解析，就能明白上面那些陷阱为何如此安静。把规范的解析流程原样实现，喂进十个字符串。

node v22.16.0 / win32

--- 2-1. parsing ten Set-Cookie strings ---
input                                                              -> SameSite      Secure  note
---------------------------------------------------------------------------------------------------------
[sid=abc123; Path=/; HttpOnly; SameSite=Lax]                       -> Lax           false
[sid=abc123; path=/; httponly; samesite=lAx]                       -> Lax           false
[sid=abc123;SameSite=Strict;Path=/]                                -> Strict        false
[sid=abc123;    SameSite   =   None   ;   Secure  ]                -> None          true
[sid=abc123; SameSite=None]                                        -> None          false   DISCARDED (None without Secure)
[sid=abc123; SameSite=Loose; Path=/]                               -> Default(Lax)  false
[sid=abc123; SameSite; Path=/]                                     -> Default(Lax)  false
[sid=abc123; SameSite=Strict; SameSite=None; Secure]               -> None          true
[sid=abc123; Path=/; Flavour=vanilla; Priority=High; SameSite=Lax] -> Lax           false   ignored attrs: Flavour=vanilla, Priority=High
[sid=; Path=/; Max-Age=0]                                          -> Default(Lax)  false

--- 2-2. what the parser proved ---
  case of attribute name and value is irrelevant : true
  attribute order is irrelevant                  : true
  surrounding whitespace is stripped             : true
  unknown attribute drops the ATTRIBUTE only     : true  (ignored: Flavour=vanilla)
  duplicate attribute: last one wins             : None
  typo in the VALUE is not an error, it degrades : Default(Lax)   <- raw was [Loose]
  • 属性名不区分大小写。规范直接写道：这里用 CamelCase 呈现，但任何大小写都被接受
  • 顺序无关。Secure 写在前面还是后面，结果相同
  • 空白会被去掉。去除名称与取值前后空白这一步，流程里写得很明确
  • 未知属性只丢弃该属性。混进 Flavour=vanilla 这类东西，Cookie 本身照样存活。这正是新属性得以进入标准而不打断旧客户端的原因
  • 同一属性出现两次时，以最后一次为准。第八行先写了 Strict，结果却是 None。两处中间件同时改同一个 Cookie 时，事故就出在这里
  • 无法识别的取值不是错误，而是降级。第六、第七行即是如此，第 2 节的拼写陷阱正源于此

最后一行同样值得注意。sid=; Max-Age=0 是删除 Cookie 的惯用写法，而此时 SameSite 同样会退回默认值。如果用于删除的 Set-Cookie 没有与原 Cookie 对齐同一套属性组合，删除就不会生效，这正是「退出登录退不掉」这类缺陷的常见根因。

5. Domain、Path，以及「站点」的判定标准

只看 SameSite 只是一半。一条请求会不会带上 Cookie，要通过三道筛子才定得下来：域名要对上，路径要对上，然后才轮到 SameSite 的判定。先验证前两道。

node v22.16.0 / win32

--- 5-1. host-only cookie vs Domain cookie ---
request host              no Domain attr   Domain=example.com
---------------------------------------------------------------
example.com               true             true
www.example.com           false            true
api.a.example.com         false            true
notexample.com            false            false
example.com.evil.net      false            false
  omitting Domain is the TIGHTER setting. adding it widens the blast radius.

--- 5-2. Path matching ---
Path=/app   request path        match
------------------------------------------
            /app                true
            /app/               true
            /app/orders         true
            /application        false
            /                   false
            /x/app              false
  /application does not match /app. the boundary is a slash, not a prefix.
  • 省略 Domain 反而更窄。省略后 Cookie 只会发给下发它的那台主机。这与「默认值应该比较松」的直觉恰好相反
  • 写上 Domain=example.com 就会发给所有子域。像 api.a.example.com 这样往下好几层也一样
  • 相似的名字不会命中。notexample.com 和 example.com.evil.net 都不匹配，因为后缀比较之前必须存在一个点作为边界
  • Path 的边界是斜杠。Path=/app 不会匹配 /application。不过正如 MDN 明确指出的，Path 不是安全机制

接着是「站点」这个词的问题。日常语里它大概等于「我们这个服务」，但在这里它有精确含义：协议加可注册域。它和人们常常连着用的「源(origin)」并不是一回事。

--- 5-4. what "same site" actually compares ---
A                              B                              same site?
---------------------------------------------------------------------------
https://app.example.com/       https://api.example.com/       YES
https://app.example.com/       https://example.com/           YES
https://app.example.com:443/   https://app.example.com:8443/  YES
https://app.example.com/       http://app.example.com/        no
https://app.example.com/       https://app.example.net/       no
https://shop.example.co.kr/    https://pay.example.co.kr/     YES
https://a.github.io/           https://b.github.io/           no
http://localhost:18081/        http://localhost:18082/        YES
http://localhost:18081/        http://127.0.0.1:18082/        no

--- 5-5. site vs origin, side by side ---
  URL    : https://app.example.com:8443/orders?x=1
  origin : https://app.example.com:8443        <- scheme + host + PORT
  site   : https://example.com     <- scheme + registrable domain, no port
  these two words are not interchangeable, and cookies use the second one.
  • 端口不同仍是同一站点。Cookie 不以源为单位。跑在 8443 上的开发服务器会与生产共享 Cookie，原因就在这里
  • 协议不同就是不同站点。http 与 https 会被分开
  • 在公共后缀之下会多消耗一段标签。shop.example.co.kr 与 pay.example.co.kr 是同一站点，但 a.github.io 与 b.github.io 不是。静态页面托管彼此读不到 Cookie，正是这个缘故
  • localhost 与 127.0.0.1 是不同站点。在本地模拟跨站时混用这两者，会造成意料之外的跨站条件；反过来只改端口则根本无法复现跨站

这对设计有一个影响。从 SameSite 的角度看，拆分子域不产生任何隔离。把支付域单独拆出来，只要仍在同一个可注册域之下，它依然是同一站点，彼此之间的跳转连 Strict 的 Cookie 都照带不误。若想要隔离，应该考虑分离域名本身，或者去掉 Domain 属性。

6. 逐步拆解登录掉线的那条路径

现在回到开头的症状。在跳出到外部支付服务商或身份提供方再返回的流程里，核心问题是Cookie 究竟在哪一步消失。岔路只有一条：返回时使用的方法。

这一部分不是规则而是实测。在本地起两台服务器，让其中一台重定向到另一台，以 POST 发出后按状态码分别测量落地时的方法。

node v22.16.0 / win32
provider 127.0.0.1:18082  ->  app 127.0.0.1:18081/return

--- 4-1. we POST to the provider; it redirects us back. which method lands? ---
redirect status   we sent   we landed with   Lax cookie would ride?
---------------------------------------------------------------------------
301               POST      GET              yes - safe method
302               POST      GET              yes - safe method
303               POST      GET              yes - safe method
307               POST      POST             NO  - unsafe method
308               POST      POST             NO  - unsafe method

  measured with an HTTP client on this machine, not with a browser.
  the method rewrite on 301/302/303 is the whole ballgame:
  307 and 308 preserve POST, and a Lax cookie is withheld on arrival.
  • 301、302、303 会把方法改写为 GET 再落地。这样就同时满足了 Lax 的两个条件(顶层跳转加安全方法)，Cookie 得以携带
  • 307、308 原样保留 POST。落地请求成为跨站 POST，在 Lax 之下 Cookie 不会携带
  • 这个差别根本不在我们的代码里，而是对方配置界面上的一个数字。我们这边一动不动，对方一改，症状就会时有时无
  • 若用 Strict，则与方法无关都不携带。以 302 落地为 GET 也一样
  • 自动提交表单、把结果以 POST 送回的做法结果相同。它只是看起来不像重定向，本质仍是跨站 POST
--- 4-2. the redirect chain, step by step ---
  step 1  POST http://127.0.0.1:18082/go?code=307
          <- 307 Location: http://127.0.0.1:18081/return?via=307
  step 2  the client repeats the request at the new URL
          this second request is cross-site AND it is a POST
          -> Strict: withheld.  Lax: withheld.  None+Secure: sent.

--- 4-3. same chain, but the provider returns us with 303 ---
  landed method : GET   (the body was dropped)
  -> Strict: still withheld (cross-site).  Lax: sent.  None+Secure: sent.
  one number in the provider config moves the session between present and absent.

--- 4-4. and the second hop, once we are back on our own site ---
  same-site GET landed with method GET
  this is why the bug looks intermittent: reload the page after landing
  and the next request IS same-site, so Strict starts working again.

6.1 拆成六步来看

  1. 用户在我们站点点下支付按钮。到这一步全都是同站点，三个取值都正常工作
  2. 浏览器跳到支付服务商的域名。这一段与我们的 Cookie 无关
  3. 支付服务商把授权结果送回我们的回跳 URL。这条请求是跨站的
  4. 如果送回方式是 GET，Lax 的 Cookie 会被携带，登录状态得以保持
  5. 如果送回方式是 POST，Lax 的 Cookie 不会被携带。服务端把它当成未登录用户的请求，于是弹出登录页
  6. 一旦用户在那个页面上点了什么，从这里开始就是同站点，Cookie 又回来了。所以后面会跟着一句「我刷新一下就好了呀」，工单也就以无法复现被关掉

处置顺序也由此而来。把取值放宽到 None 是最后手段。首先考虑把回跳那一步改成接受 GET 的轻量端点。如果需要支付结果正文，就让正文走服务端到服务端的通知，用户浏览器只用 GET 送回即可。这样不必放宽 Cookie 策略，症状也会消失。

7. 大小与数量：天花板有两层

会话消失还有另一条路径：Cookie 大到存不下。规范的句子很明确：名称与取值的长度之和超过 4096 字节时，中止算法并完全忽略这条 Set-Cookie 字符串。

node v22.16.0 / win32
max HTTP header size this runtime accepts: 16384 bytes

--- 6-1. the 4096-octet line, name + value together ---
name len   value len   sum     jar keeps it?
-----------------------------------------------
3          4093        4096    true
3          4094        4097    false
3          4095        4098    false
500        3596        4096    true
500        3597        4097    false
  the limit counts the NAME too. renaming session_identifier to sid buys you bytes.

--- 6-2. an oversized cookie is dropped whole, not truncated ---
  value length          : 5000
  jar keeps it          : false
  what the app receives : nothing at all
  no error, no warning, no half-value. the next request simply has no session.
  • 名称也计入长度。把 session_identifier 缩短为 sid，就能为取值多腾出同样多的字节
  • 是整条丢弃而不是截断。不会留下前半段，而是彻底当作没有
  • 所以症状表现为「没有这个 Cookie」而不是「取值看起来不对」。要过一阵子才有人怀疑到大小，原因就在这里
  • 一旦混入非 ASCII 文本或表情符号，算法又不一样了。单位是字节，所以必须数编码之后的字节数而不是字符数

天花板不止一层。在 Cookie 存储的限制之上，还有一层独立的限制：HTTP 响应头大小。这一层是对着真实服务器撞出来的。

--- 6-3. many cookies at once, measured against a real server ---
count   Cookie header bytes   server response
-------------------------------------------------------
10      856                   200 OK  cookies=10 bytes=848
50      4296                  200 OK  cookies=50 bytes=4288
100     8596                  200 OK  cookies=100 bytes=8588
180     15556                 200 OK  cookies=180 bytes=15548
300     25996                 431 Request Header Fields Too Large
  past the runtime header budget the request dies before your code runs.
  the cookie jar has its own per-domain cap on top of this. two ceilings, not one.

--- 6-4. every cookie rides on EVERY matching request ---
  one 1.2 KB cookie             : 1204 bytes per request
  60 requests to render a page  : 72240 bytes uploaded, per page view
  and Domain=example.com sends it to the image host and the API host too.
  this is the real argument for keeping an identifier in the cookie and state on the server.

180 个(15,556 字节)通过了，300 个(25,996 字节)返回了 431。这里最关键的是应用代码根本没有执行。你的日志、你的异常处理、你的错误页面统统不会出现。「只有某一个用户整站打不开」的工单就是这样来的，清掉那位用户的 Cookie 就好了。MDN 所说的「Cookie 会随每一条请求发送，因此可能拖慢性能」讲的正是这件事。

8. 服务端为何无从得知原因

这件事难以诊断有其结构性原因：服务端发出去的东西和收回来的东西并不对称。

node v22.16.0 / win32
server A 127.0.0.1:18081   server B 127.0.0.1:18082

--- 1-1. exact Set-Cookie bytes the server puts on the wire ---
recipe            Set-Cookie line as received
---------------------------------------------------------------------------
no-attr          Set-Cookie: sid=abc123; Path=/; HttpOnly
lax-explicit     Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=Lax
strict           Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=Strict
none-no-secure   Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=None
none-secure      Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=None; Secure
bogus-value      Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=Loose
weird-case       Set-Cookie: sid=abc123; path=/; httponly; samesite=lAx

--- 1-3. what the server sees when a client sends a Cookie header ---
  with Cookie header : cookie-header-seen: sid=abc123; theme=dark
  without            : cookie-header-seen: (none)
  the server cannot tell WHY a cookie is missing. absent == never-sent == blocked.

--- 1-4. no SameSite attribute survives into the Cookie header ---
  cookie-header-seen: sid=abc123
  Cookie: carries name=value only. no Path, no Domain, no SameSite.
  the server gets no evidence of which policy was applied.
  • Set-Cookie 会把属性全部带上。Path、HttpOnly、SameSite 都会原样发出去
  • 回来的 Cookie 头里只有名称与取值。关于它是按哪条策略保存的，一点信息都没有
  • 所以服务端无法区分 Cookie 缺失的原因。是已退出登录的用户，是被 SameSite 拦下，是超出大小限制没能保存，还是用户自己清掉了，看起来全都一模一样
  • 最终只能从请求侧的信息去推断。用 Origin 与 Referer 看它从哪来，看方法是什么，再把这个组合对照第 1 节的表，判断我们的策略是否允许携带

因此实用的对策是日志。对所有没有带会话就抵达的请求，把方法、Origin、Referer 一并记录下来，只要与判定表一对照，原因就能大幅收窄。缺了这一行日志，就得在复现尝试上耗掉好几天。

9. 什么放在哪里，取值又该怎么选

走到这一步，问题本身变了。不是「哪个取值更好」，而是「什么该放进 Cookie」在先。

原则只有两句。Cookie 里只放标识，状态放在服务端。第 7 节的两层天花板就是依据，照做之后大小问题与带宽问题会一起消失。接着把这个标识必须搭载的请求写成清单，取值就会从清单里自动浮出来。

Cookie 里装的东西跨站是否需要建议取值一并设置
登录会话标识(普通 Web 应用)不需要LaxSecure HttpOnly Path=/
登录会话 + 外部支付或 OAuth 回跳仅回跳那一步Lax + 把回跳改为 GETSecure HttpOnly
管理控制台或内部工具不需要StrictSecure HttpOnly __Host- 前缀
CSRF 令牌(双重提交方案)不需要Strict 或 LaxSecure，不加 HttpOnly
嵌入第三方页面的组件或 SSO iframe需要None必须加 Secure + 评估 Partitioned
广告或分析用标识需要NoneSecure，按会被拦截来设计
语言、主题一类的显示偏好不需要LaxSecure，也可考虑本地存储
  1. 把这个 Cookie 必须搭载别的站点发起的请求的场景全部写出来。一个也没有，就写上没有
  2. 清单为空就用 Lax。如果确信连顶层跳转也不需要，就收窄到 Strict
  3. 只有清单非空时才动用 None，并且同时写上 Secure。然后把这份清单留在注释或文档里。这能防止后来者因为不知道理由而再次放宽

最后把界线划清楚。SameSite 是 CSRF 的缓解手段，不是 CSRF 防护的全部。MDN 的措辞是「对跨站请求伪造攻击提供一定程度的保护」，并没有说它能解决问题。无论取值是什么，会改变状态的请求都仍需另行做令牌校验。Web 安全的整体骨架整理在Web 安全基础，检测层则在 IDS 与 IPS。

取值一句话定义典型症状
Strict只搭载同站点请求从外部链接进来的第一屏处于未登录状态
Lax同站点，外加顶层跳转的安全方法支付或 OAuth 用 POST 送回来时会话消失
None搭载所有请求去掉 Secure，Cookie 根本不会被保存
(未写取值)按 Lax 对待「代码没动，某天突然坏了」

表里的「典型症状」一列在实战中最有用。先看症状再反推取值，远比一个取值一个取值地发上去试要快得多。

10. 检查清单

  • 会话 Cookie 显式写出了 SameSite 取值(不依赖默认值)
  • 所有使用 None 的 Cookie 都带着 Secure
  • 选择 None 的理由能以请求清单的形式写出来
  • 已确认外部支付或 OAuth 回跳那一步的状态码与方法
  • 若回跳是 POST，另外准备了轻量的 GET 端点
  • Domain 属性只在确有需要时才加(省略反而更窄)
  • 设计中已考虑子域会被归为同一站点
  • 本地验证没有无意中混用 localhost 与 127.0.0.1
  • 每个 Cookie 的名称加取值都在 4096 字节以内
  • 已实测每个域名下的 Cookie 数量与总字节数
  • SameSite 取值字符串没有拼写错误(拼错会悄悄退回默认值)
  • 对没有带会话就抵达的请求，把方法、Origin、Referer 记入日志

11. 常见误解与不要做的事

  • ❌ 一看到症状就改成 None — 先把真正需要它的请求列成清单
  • ❌ 用了 None 却漏掉 Secure — Cookie 在保存阶段就被丢弃
  • ❌ 依赖默认值 — 没写明的 Cookie 只能听凭解释方的默认策略
  • ❌ 只在 localhost 上验证就收工 — 只改端口的本地环境复现不出跨站条件
  • ❌ 相信拆分子域就实现了隔离 — 同一个可注册域之下就是同一站点
  • ❌ 把 SameSite 当作 CSRF 防护的全部 — 它是缓解手段，不是防线本身
  • ❌ 把会话状态整个塞进 Cookie — 4096 字节的上限与每请求的带宽要一起付账

最后还有一点。不要断言某个浏览器版本的行为。默认值的适用范围、是否采纳 Lax-allowing-unsafe、分区存储如何处理，各实现可能不同，也会随时间变化。规范只规定什么是被允许的，并不保证所有实现表现一致。在上线前加入一道在目标浏览器上亲自确认的流程，才是唯一不会过时的对策。

# SameSite Cookie — 取值决策表与按请求类型的判定表

> 来源: braindetox.kr — SameSite Lax、Strict、None：哪些请求会丢掉 Cookie
> 依据: RFC 6265bis (draft-ietf-httpbis-rfc6265bis-22, 2025-12-01) + MDN
> 运行环境: Windows 10 Pro 10.0.19045 / Node.js v22.16.0 (win32) / 两台本地服务器
> **界限声明**: 浏览器 Cookie 存储的真实行为在本文中未直接验证。
> 下表的判定格是**把规范文字实现为代码后计算出的结果**。上线前请在目标浏览器上复核。

## 1. 按请求类型的判定表

设置 Cookie 的一方: `https://app.example.com`
发起请求的一方: `https://portal.other-site.com`

| 请求类型 | Strict | Lax | None+Secure | 未写取值 | 依据 |
|---|---|---|---|---|---|
| 同站点内的页面跳转 | 携带 | 携带 | 携带 | 携带 | 规范 |
| 从别的站点点击链接 | **不携带** | 携带 | 携带 | 携带 | 规范 |
| 别的站点加载图片 | 不携带 | 不携带 | 携带 | 不携带 | 规范 |
| 别的站点加载脚本或 CSS | 不携带 | 不携带 | 携带 | 不携带 | 规范 |
| 从别的站点提交 form GET | **不携带** | 携带 | 携带 | 携带 | 规范 |
| 从别的站点提交 form POST | 不携带 | **不携带** | 携带 | 不携带 | 规范 |
| 从别的站点发起 fetch 或 XHR | 不携带 | 不携带 | 携带 | 不携带 | 规范 |
| 在 iframe 内加载 | 不携带 | 不携带 | 携带 | 不携带 | 规范 |
| 同站点 fetch | 携带 | 携带 | 携带 | 携带 | 规范 |
| 经 302 返回并以 GET 落地 | **不携带** | 携带 | 携带 | 携带 | 规范 + 落地方法为实测 |
| 经 307 返回并以 POST 落地 | 不携带 | **不携带** | 携带 | 不携带 | 规范 + 落地方法为实测 |

看懂它只需两句话。

- **Strict 与 Lax 的差别只落在「顶层跳转 + 安全方法」这三行。**
- **Lax 与 None 的差别落在子资源和 POST 上，也就是剩下的全部。**

## 2. 取值决策表

| Cookie 里装的东西 | 跨站请求是否需要它 | 建议取值 | 一并设置 |
|---|---|---|---|
| 登录会话标识（普通 Web 应用） | 不需要 | `Lax` | `Secure` `HttpOnly` `Path=/` |
| 登录会话 + 存在外部支付或 OAuth 回跳 | 仅回跳那一步 | `Lax` + 把回跳改为 **GET** | `Secure` `HttpOnly` |
| 管理控制台或内部工具 | 不需要 | `Strict` | `Secure` `HttpOnly` `__Host-` 前缀 |
| CSRF 令牌（双重提交方案） | 不需要 | `Strict` 或 `Lax` | `Secure`，不加 `HttpOnly` |
| 嵌入第三方页面的组件或 SSO iframe | 需要 | `None` | **必须加 `Secure`** + 评估 `Partitioned` |
| 广告或分析用标识 | 需要 | `None` | `Secure`，按会被拦截来设计 |
| 语言、主题一类的显示偏好 | 不需要 | `Lax` | `Secure`，也可考虑本地存储 |

**选择过程只有三句话。**

1. 把这个 Cookie 必须搭载的**跨站发起请求**逐条列出来。
2. 列表为空就用 `Lax`；连顶层跳转也不需要，就用 `Strict`。
3. 只有列表非空时才动用 `None`，此时 `Secure` 是**必需项**。

## 3. 三个取值一览

| 取值 | 一句话定义 | 典型症状 |
|---|---|---|
| `Strict` | 只搭载同站点请求 | 从外部链接进来的第一屏处于未登录状态 |
| `Lax` | 同站点，外加**顶层跳转的安全方法** | 支付或 OAuth 用 POST 送回来时会话消失 |
| `None` | 搭载所有请求 | 去掉 `Secure`，Cookie 根本不会被保存 |
| （未写） | 按 `Lax` 对待 | 「代码没动，某天突然坏了」 |

## 4. Set-Cookie 书写规则（用解析器验证过）

- 属性的**名称与取值不区分大小写**。`samesite=lax` 等同于 `SameSite=Lax`
- 属性**顺序无关**。`Secure; SameSite=Lax` 与 `SameSite=Lax; Secure` 相同
- 等号两侧的**空白会被去掉**。`SameSite = None` 也能解析
- **未知属性只丢弃该属性。** Cookie 本身不会作废
- **同一属性出现两次时，以最后一次为准**
- **取值写错不是错误。** `SameSite=Strick` 会悄悄变成默认值（Lax）
- `Set-Cookie` 从服务端到客户端，`Cookie` 从客户端到服务端。**`Cookie` 头里只有名称=取值。** 服务端无从得知应用了哪条策略

## 5. 会话掉线的排查顺序

1. 在服务端日志里确认失败请求的 **`Cookie` 头里是否带着会话名**。没有就说明是 Cookie 问题，不是认证问题
2. 确认那条请求**是否由别的站点发起**。若是同站点，SameSite 不是元凶
3. 确认那条请求的**方法**。若是 `POST`，`Lax` 不携带才是正常行为
4. 确认外部服务**用哪个状态码把你送回来**。301、302、303 以 GET 落地，**307 与 308 保留 POST**
5. 把落地那一步改成**接受 GET 的轻量端点**。这一步要排在把取值放宽为 `None` 之前
6. 若仍不行，让落地页面再发**一次同站点请求**，在那里核对会话

## 6. 大小与数量的天花板（实测）

- 单个 Cookie 的上限是**名称长度 + 取值长度不超过 4096 字节**。名称也计入
- 超过不会截断，而是**整条丢弃**。既无错误也无警告
- 测试运行时的 HTTP 头预算为 **16384 字节**，300 个 Cookie（25996 字节）触发了 **431 响应**。应用代码根本没有执行
- Cookie 会**搭载在每一条匹配的请求上**。一个 1.2 KB 的 Cookie，按每页 60 条请求算，每次浏览要上传约 72 KB
- 因此原则只有一条：**Cookie 里只放标识，状态放在服务端。**

## 7. 检查清单

- [ ] 会话 Cookie **显式写出了 `SameSite` 取值**（不依赖默认值）
- [ ] 所有使用 `None` 的 Cookie **都带着 `Secure`**
- [ ] 选择 `None` 的理由能**以请求清单的形式**写出来
- [ ] 已确认外部支付或 OAuth **回跳那一步的状态码与方法**
- [ ] 若回跳是 `POST`，另外准备了轻量的 **GET 端点**
- [ ] `Domain` 属性**只在确有需要时**才加（省略反而更窄）
- [ ] 设计中已考虑**子域会被归为同一站点**
- [ ] 本地验证没有**混用 `localhost` 与 `127.0.0.1`**（二者是不同站点）
- [ ] 已确认协议不同即为不同站点（http 与 https）
- [ ] 每个 Cookie 的**名称加取值都在 4096 字节以内**
- [ ] 已实测每个域名下的 Cookie **数量与总字节数**
- [ ] `SameSite` 取值字符串**没有拼写错误**（拼错会悄悄退回默认值）
- [ ] 会话 Cookie 上加了 `HttpOnly`
- [ ] CSRF 防护**没有只押在 SameSite 上**

## 8. 不要这样做

- ❌ 一看到症状就**改成 `None`** — 先确定哪些请求真的需要它
- ❌ 用了 `None` 却**漏掉 `Secure`** — Cookie 在保存阶段就被丢弃
- ❌ **依赖默认值** — 没写明的 Cookie 只能听凭实现的默认策略
- ❌ **只在 `localhost` 上验证**就收工 — 本地环境复现不出跨站条件
- ❌ **断言某个浏览器版本的行为** — 各实现可能不同，请在目标浏览器上确认
- ❌ 把 SameSite 当作 **CSRF 防护的全部** — 它是缓解手段，不是防线本身
- ❌ 把会话状态**整个塞进 Cookie** — 大小上限与带宽要一起付账
