The trigger - an article about design judgement, not about structure

An article titled Claude Code Skill Patterns was published on stock-engineer.com on July 28, 2026 and modified on September 29, 2026, and GeekNews introduced it as an item registered on October 4, 2026. The original is divided into seven chapters. It starts from the question of why the same task has to be explained from scratch every time, builds a view of skills as criteria for judging work rather than collections of commands, and then goes through four principles it read in Anthropic's skill design, composition methods by scale, the design philosophies of three public collections, five lessons the author gained in practice, and finally six questions for deciding whether a task deserves a skill of its own. According to the author profile, the writer is an engineer with a career in embedded software development, and the practical experience is described as coming from that development work and from running a blog.

The basic structure and authoring method of this subject are already laid out in the A-to-Z guide to Claude Code Skills, and how one particular skill is actually built is covered in the Archify analysis. The structural comparison between keeping rules in context and turning them into hooks is covered in the analysis of compiling CLAUDE.md rules into hooks. Here the scope is limited to the questions those posts do not answer directly, that is, design judgement: when to split work into a skill, what to write in the description so the call timing matches, and which rules to keep in a skill and which to hand to a hook.

Design judgement is an area where kinds of evidence mix easily. When facts fixed by the official documentation, things the documentation recommends, and experience that one person says they gained in practice are blended in a single paragraph, the reader cannot tell where the rule ends. So below, each claim of the original is compared with the official documentation and sorted into what is confirmed, what is only partly confirmed, and what remains the author's experience. It should also be stated first that the hook section of the original has no explanation of exit code 2, only a remark that the concrete settings and the exit code trap are written up in another post, on a dual gate for regulated industries. The PreToolUse event and exit code 2 come from the official hooks documentation and are shown as separate items.

A description is a trigger, not an explanation

The original names this as its fourth principle. It says that the description is not an explanation for users but the signal by which an agent decides whether to switch a skill on, and it asks that what the skill does and when to use it be written together. The example is: for work that needs compatibility testing and migration validation after an API change. The official material points the same way. The best practices explain that the description is the basis of skill discovery, and that Claude uses this field to choose the right skill from potentially 100 or more. The Claude Code documentation also says that Claude uses this field to decide when to apply a skill, and that if it is omitted the first non-empty line of the body is used instead.

The code below is the format of a SKILL.md header as shown in the Claude Code documentation. It is the current documentation's example, copied as it is; the documentation says the example sets four fields.

---
                    name: my-skill
                    description: What this skill does
                    disable-model-invocation: true
                    allowed-tools: Read Grep
                    ---
                    Your skill instructions here...

In this example more than one field relates to triggering. The description is the material for judging the call timing, and setting disable-model-invocation to true keeps Claude from loading that skill automatically. The table in the same document also lists when_to_use, which is appended to the description, user-invocable, which controls whether only Claude invokes the skill, and paths, which limits the activation scope by glob patterns. This means that matching the call timing does not hang on a single phrase.

  • What and when together - the good example in the best practices follows functions such as extracting PDF text and tables and filling forms with a clause saying to use it when working with PDF files or when the user mentions PDFs, forms or document extraction.
  • Vague descriptions fail - the best practices give sentences such as Helps with documents and Processes data as bad examples. They point to nothing and cannot be told apart from other skills.
  • Third person - the best practices say that the description is injected into the system prompt, so an inconsistent point of view can cause discovery problems, and they recommend the third person.
  • The limit differs by document - the skill authoring best practices give the description a maximum of 1,024 characters, while the Claude Code documentation says the description and when_to_use combined are cut at 1,536 characters in the skill listing. The two figures are statements of different documents and cannot be merged into one.
  • Key use case first - because the text can be truncated in the listing, the Claude Code documentation says to put the key use case first.
  • Procedure belongs in the body - putting procedure into a field with a limit pushes out the call-timing signal. This is an interpretation that follows from the two limits, and the original does not say it.
  • Exclusion conditions - there was no guidance within the official documentation consulted on how to write when not to use a skill. It is for the designer to decide when skills overlap.

SKILL.md is a table of contents and the details move out

The second and third principles of the original point in the same direction. For progressive disclosure, SKILL.md is used as a table of contents, with details in references, executable code in scripts and templates in assets. Instructions keep only the order that must be followed, the completion conditions and the prohibitions, and background explanation moves to separate documents. The official counterpart is the 500-line recommendation. The Claude Code documentation says to keep SKILL.md under 500 lines and to move detailed reference material into separate files. The skill authoring best practices give the same standard for optimal performance.

Two places in this principle need design judgement. One is what to move out, and the other is how deep to move it. The official best practices are concrete on the latter. Reference files should link directly from SKILL.md, one level deep. When a reference points to another reference, Claude may preview only the beginning of a file and stop, which makes the information incomplete. The advice to put a table of contents at the top of a reference file longer than 100 lines comes from the same reason.

  • 500 lines is a recommendation - both official documents say to keep it and for optimal performance, and there is no statement that an excess is rejected automatically.
  • One level deep - link from SKILL.md straight to the reference file, and avoid a structure where that reference points on to yet another file.
  • A table of contents in long references - past 100 lines, put one at the top so that the whole scope is visible even to a partial read.
  • State whether to execute or to read - say in the instructions whether a script is to be read or run. When it is run, only the script's output uses tokens and its contents do not enter the context.
  • Match the degrees of freedom to the task - give text instructions when several approaches are valid, a script with parameters when a preferred pattern exists, and a narrow instruction such as run exactly this script when the task is fragile and the order is fixed.
  • One default and the exceptions - do not list many tools; choose one default tool and add only the exceptional situations.

Where to draw the line between pipeline skills and tool skills

This split is the first of the practical lessons in the original. The author describes a pipeline skill as linking several stages, from reading a ticket through analysis, writing tests, implementation and verification to creating a pull request, with the individual actions inside it, namely build, test, format and lint, handled by tool skills. These two terms do not exist in the official documentation, so the split has to be treated as the author's design experience. There is, however, an adjacent recommendation to rest on. The skill authoring best practices say to use scripts for deterministic operations, giving as reasons that they are more reliable than generated code, save tokens and time, and ensure consistency across uses.

The conditions under which the split has meaning can be summarized as two. The first is when the same action repeats across several procedures. If an action every pipeline passes through, such as build and test, is set apart as a tool skill, the definition of the action stays in one place even when the procedure changes. The second is when the procedure changes often but the action is fixed. These two conditions are not written in the original; they are a design interpretation readable from the author's description, and the evidence the original offers is the experience of having split them.

  • Pipeline skill - holds the order of stages, the completion conditions between stages, and the prohibitions. The example in the original runs from reading a ticket to creating a pull request.
  • Tool skill - handles actions with comparatively fixed input and output, such as build, test, format and lint.
  • How they connect - the pipeline calls the tool skill. The details of the calling method are not in the original.
  • Limit of application - there is no evidence that this distinction fits every team. The original says it comes from the author's own development pipeline and blog operation.

The axes that three public collections separate

The original cites three public collections as examples of different design philosophies. The public collections the original cites are Superpowers, GSD and caveman, and no more are added here. In its section on scale it also cites a CLAUDE.md project based on Karpathy's observations and a 42-skill catalog, but those are examples of composition methods. The second column of the table below is the original's summary, and the third column is an interpretation of which axis of skill design each represents.

CollectionSummary in the originalDesign axis it represents (interpretation)
SuperpowersSkills that enforce a development procedure: brainstorming, planning, RED-GREEN-REFACTOR implementation, specification review, code quality reviewEnforcement of procedure. Order and review stages are the centre of the skill
GSDSplits context from discuss to execute: discuss, plan, execute, verify, ship. It divides work into small plans to reduce the growth of the main session contextSeparation of context. The context used at each stage is kept apart
cavemanAdjusts output density rather than procedure. It cuts long explanations and idiomatic phrases and prints only the core resultAdjustment of output. It changes the way of responding, not the order of work

The original sets these three beside composition methods by scale. A single rules file is simple to install and maintain but hard to use for per-task detailed procedures. A small set of skills makes it easy to separate recurring development flows but role boundaries may overlap. A large skill catalog supports many jobs and tasks broadly but complicates search, permissions and version management. The strengths and weaknesses of the three are carried over from the table in the original, and the official documentation does not contain the same classification.

  • Single rules file - the strength is simple installation and upkeep, the caution is that per-task detailed procedures are hard to hold.
  • Small skill set - the strength is that recurring development flows are easy to separate, the caution is overlapping role boundaries.
  • Large skill catalog - the strength is broad support, the caution is the complexity of search, permissions and version management.

Where the trap list should live

The first principle of the original is that a good skill states common mistakes and failure patterns, not only the normal procedure. The sentence it gives as an example is: do not conclude that a requirement is met from passing tests alone. This principle runs into a problem in the second practical lesson. The author says that the trap list grows faster than a skill body can carry, and that the remedy chosen was to split traps into a knowledge file outside the skill. The skill body holds only the procedure, and the knowledge file accumulates the lessons from each session, classified by prefixes such as review, format, build, test, CI and design.

What comes close in the official documentation is the splitting of reference files and the way of handling time-sensitive information. The best practices say not to keep information that will soon be outdated in the main body but to fold it into an old patterns section. Traps age at different speeds, and that is where the recommendation touches. But the classification by prefix and the operating method of accumulating them session by session are the author's own and are not in the official documentation.

  • Traps for the body - prohibitions whose violation fails at once when a step is skipped. They correspond to the third principle of the original, the required order, completion conditions and prohibitions.
  • Traps for the knowledge file - individual cases that keep growing over sessions. Classify them by prefix so that only the needed classification is read.
  • Traps that age - traps tied to a specific version or point in time are gathered in a section such as old patterns, apart from the body.
  • How much is experience - the criteria separating the body from the knowledge file are interpreted as above, and the original does not present a threshold in numbers.

Skills instruct and hooks block - a division of roles

The fourth lesson of the original is this division. The author says it is better to enforce, with a Claude Code hook that blocks the push command itself when no review document exists, than to write an instruction in a skill saying to push after creating the review document. In short, a skill says to do it and a hook stops it from being done. The original does not explain hook events or exit codes, and says only that the concrete settings and the exit code trap are written up in another post on a dual gate for regulated industries. What follows is the part that the official hooks documentation confirms.

In the official hooks documentation, exit code 2 is a blocking error. On events that can block, exit code 2 blocks whether or not JSON was printed, and a permissionDecision of allow in the JSON cannot override it. In PreToolUse, exit code 2 blocks the tool call. The blocking message is the reason in the JSON if there is one, and otherwise the standard error text. Exit code 0 is success, and other exit codes do not block on their own for most events.

{
                      "hookSpecificOutput": {
                        "hookEventName": "PreToolUse",
                        "permissionDecision": "deny",
                        "permissionDecisionReason": "Destructive command blocked by hook"
                      }
                    }

The JSON above is the structured PreToolUse output that the official documentation shows as an alternative to exit code 2. The values usable for permissionDecision are allow, deny, ask and defer. Hooks are defined in JSON settings files such as settings.json or in plugins, and the matcher field filters which tools they react to. The official hooks reference describes hooks as shell commands, HTTP endpoints, MCP tool calls, LLM prompts or subagents. The word "deterministic" is in the hooks guide, which says that hooks give deterministic control: actions always happen at the set point rather than relying on the LLM to choose to run them. That property supports the division in the original, the judgement that a rule that must not be broken is left to a hook.

  • Rules for the skill (interpretation) - those that need judgement and order, and whose breach can be undone. It is a procedure the agent reads and follows.
  • Rules for the hook - those that must not be broken (the original's division). The condition is checked just before the tool call and the call is blocked. The original's example is blocking a push when the review document is missing.
  • The exit code trap - to block, the exit code must be 2 or the structured output must be deny. Other nonzero exit codes do not block on their own for most events, so one must not assume that a script that exited with an error has blocked anything.
  • Conveying the reason for a block - the blocking message is information the agent reads, so stating concretely what is missing helps the next action. This is an interpretation that follows from the documentation.
  • Where skills and hooks meet - the list of places where hooks can be defined in the official documentation includes the frontmatter of skills and subagents, in which case they apply while the skill runs.
  • A deeper comparison - the limits of injecting rules into context and the approach of turning them into hooks are covered in the earlier analysis.

The cost that grows with the number of skills

The fifth lesson of the original is that the per-session cost also grows as skills multiply. The author describes that the full description text and lists of about 50 skills, about 20 agents and about 60 tools entered the context, and writes that two agent orchestration plugins were turned off and the setup returned to its defaults. The plugin names are not given in the original. The author's conclusion is that a catalog with many unused skills is a cost in itself.

Comparing with the official documentation makes the identity of the cost more precise. The skill authoring best practices say that at startup only the name and description of all skills are preloaded and SKILL.md is read when the skill becomes relevant. The Claude Code documentation also says that the description is always in context and the full skill loads when invoked, and that because a skill body loads only when used, long reference material costs almost nothing until it is needed. In other words, what an unused skill occupies is the description, not the body. And the description part is also cut at 1,536 characters in the listing.

  • Constant cost - the name and description (metadata). It grows in proportion to the number of skills.
  • Cost on invocation - the SKILL.md body. It loads only when invoked, and the 500-line recommendation is aimed at this cost.
  • Reading the author's figures - the original counts about 50 skills, about 20 agents and about 60 tools separately. Since 50 is the number of skills, the skill list alone is said to have put about 50 entries into the context every session. The agent and tool lists and the notices attached to each tool use are separate costs.
  • Ways to reduce it - write descriptions short and non-overlapping, and for skills that do not need automatic invocation there is the option of setting disable-model-invocation: true. The table in the official skills documentation lists this case as "Description not in context, full skill loads when invoked", and the documentation describes the setting as a way that "removes the skill from Claude's context entirely". In exchange Claude cannot invoke the skill on its own and the user has to invoke it.

A table for deciding whether to split a skill

The seventh chapter of the original checks whether a task deserves a skill with six questions. The table below carries over those questions and signals, and attaches in the third column an adjacent recommendation from the official best practices. The third column lists only the items that can be connected.

Question to checkSignal the original namesAdjacent recommendation in the official documentation
Frequency of repetitionSimilar instructions are repeated across several sessions-
Complexity of procedureThere is a fixed sequence of three or more stepsBreak complex work into ordered steps and a checklist
Cost of failureSkipping one step carries a high risk of rework or an incidentFragile work gets narrow instructions and a validation step
Reference materialThe same documents, templates or scripts must be found every timeReference files and scripts are read or run only when needed
Verification criterionCompletion can be judged by a test or a checklistA feedback loop: run the validator, fix, and repeat
Scope of reuseSeveral projects or team members can use the same procedure-

What the official documentation says directly in this table is not the timing of the split but the quality after it. The best practices say to build evaluations before writing extensive documentation, and give an order: run representative tasks without the skill, record the failures, and write the minimum instructions that fill the gap. There is also a checklist item to create at least three evaluations and to test with every model to be used. The closing of the original points the same way. Its point is that the measure of success is not the number of skills but whether the same mistakes decreased and whether the skill is invoked exactly when needed.

  • All the signals in the table are questions about the present state: whether something repeats, whether there is a fixed order, whether completion can be judged, and so on.
  • After a split, the original's criterion is to use as indicators whether the same mistakes decreased and whether the invocation is accurate.
  • Building evaluations first is a recommendation of the best practices, and the six questions of the original correspond to the judgement to split that comes before such evaluations.

What could not be confirmed

  • Every sentence of the original. The consultation was a chapter-by-chapter extraction, so the original was not compared word by word, and the closing sentence was confirmed only at the level of a summary.
  • The author's username. Only the byline Stock Engineer was confirmed on the original page.
  • The official documentation's statement about an assets folder. The excerpts consulted contained only reference.md, examples.md and scripts/.
  • How much disable-model-invocation: true would actually shrink the author's list of about 50 skills. The original records no such attempt.
  • The author's measured counts of 50, 20 and 60, and which plugins were turned off. The plugin names are not in the original either.
  • How a pipeline skill calls a tool skill in implementation. The original has no description of it.
  • Reproducibility of the experience the original calls accumulated in practice. No results from direct execution are included here.
