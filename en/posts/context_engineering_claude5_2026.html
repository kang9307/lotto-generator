Context Engineering in Practice - Beyond Prompts

In the agent era, designing context beats crafting a single clever prompt

Jul 26, 2026 Tech & IT

Introduction: The Center of Gravity Shifts From Prompt to Context

Every time a new model lands, a document titled something like new context engineering rules starts circulating in developer circles. In July 2026 it happened again: a practical rules writeup aimed at the latest generation of models (a post by trq212 on X) and a vendor-published cookbook and engineering guide became the talk of the town, and the topic was shared on GeekNews too. The interesting part is that although the discussion is triggered by one company's specific model, the actual content applies to nearly every large language model. The newest Claude release may have pulled the trigger, but the same rules hold just as well for OpenAI's GPT and Google's Gemini.

This piece is not out to promote any product or argue that one model is superior. Its aim is to lay out, from a vendor-neutral angle, what the practice of context engineering actually is, how it differs from prompt engineering, and how to design relevant, minimal context while preventing contamination. Cross-checking self-verified public engineering write-ups against a range of practitioner material, it walks through the concept, the principles, the practical rules, and the implications for the agent era.

1. What Context Engineering Is

1.1 Definition: Designing the Whole Set of Tokens Visible at Inference

Context engineering is the practice of deliberately selecting and maintaining which tokens sit in the context window at the very moment a model generates its next token. Public engineering guides define it as strategies for curating and managing the optimal set of tokens during inference. That set includes the system prompt, the user input, documents pulled in by retrieval, the conversation history so far, the definitions of tools the model can call, and any long-term memory kept across sessions. In short, the key question shifts from which words to write to what configuration of context is most likely to produce the desired behavior.

1.2 How It Differs From Prompt Engineering

The two are not rivals; one contains the other. If prompt engineering is about what you say to the model, context engineering also designs everything else the model sees - the memory from past interactions, retrieved documents, tool definitions, conversation history, user profile, and system state. So it is more accurate to treat prompt engineering as a subset of context engineering. For a one-off question, a single well-written prompt is enough. But the moment a system has to remember, retrieve, and act across multiple steps, prompts alone become brittle, and reliability comes not from wordsmithing but from information architecture.

2. The Four Pillars: Instructions, Retrieval, Memory, Tools

Brought down to practice, context engineering usually breaks into four axes. How you fill each one - and what you put in versus leave out - is most of the design work.

2.1 Instructions

This is the system prompt and behavioral framing: role, prohibitions, output format, decision criteria, written neither vaguely nor excessively. Listing rules too verbosely eats into the context itself; writing them too thinly makes the model behave differently each time. Good instructions keep only the minimal always-true principles at the top and inject situational detail on demand.

2.2 Retrieval

This is the axis that pulls external knowledge into context at the moment it is needed, as in RAG or grounded search. Rather than pre-loading every document, the key is selecting only the fragments that match the query. Poor retrieval that mixes in irrelevant documents leads straight to the context confusion discussed later, so it matters to cap how much gets pulled in.

2.3 Memory

Short-term memory is the ongoing conversation history; long-term memory is persistent state that survives after a session ends. Because the context window is finite, the emerging standard is to record only the important decisions and facts in structured external storage and recall them when needed rather than shoving everything back in each time. This memory design is especially decisive in work like coding sessions where context evaporates easily, a topic covered with a concrete case in turning the volatile context of an AI coding session into project memory.

2.4 Tools

The surface of functions a model can call - the tool definitions - takes up a large part of context. Lately, tool connections are being standardized through protocols like MCP (Model Context Protocol). More tools is not better. When several tools have similar names or overlapping functions, the model gets confused, and verbose descriptions burn tokens. Keeping tool definitions clear, non-overlapping, and minimal is part of context design too.

3. The Core Principle: Relevant, Minimal Context

If there is a single principle running through all four pillars, it is enough but no more. The so-called just-enough principle that public guides stress boils down to finding the smallest set of high-signal tokens that maximizes the chance of the desired outcome. Underneath it sits a counterintuitive fact: more context does not make things better. A phenomenon called context rot is observed, where reasoning quality drops as context lengthens even before the window fills.

The reason is simple. A model tries to make use of whatever it is given, so when irrelevant material is mixed in, it tries to reflect that too and ends up blurring the answer. Practical rules therefore tend to settle like this. First, keep only what this particular judgment actually needs. Second, strip out information that is redundant or already present in the environment. Third, do not pile up long history verbatim - summarize and compact it, or offload it to external storage. Not more, but more precise, is where this field is headed.

4. Breaking Context Into Components

Treated as a single blob, context offers nowhere obvious to intervene. In practice it is far easier to split what goes into the window into a few layers with different characteristics and apply different rules to each. Three criteria separate the layers: does it get re-sent on every call (cost), how long does it stay in the window (lifetime), and how long does bad information survive once it slips in (contamination risk).

ComponentToken cost profileLifetimeContamination riskManagement principle
System prompt / instructionsFixed, repeated every call (cache-eligible)Whole sessionLow - but contradictory rules cause clashOnly always-true items, kept short, change-tracked
Tool definitions / schemasFixed and repeated, scales with tool countWhole sessionMedium - similar names create confusionCap the count, separate names, compress descriptions
Retrieval results (RAG)Varies per query, explodes without a capOne turn to a few turnsHigh - irrelevant documents are confusionCap top-k, rerank, cite sources
Conversation and tool-call historyMonotonically increasingAccumulates until compactionHigh - the main channel for poisoning and distractionThreshold-based compaction, keep raw text outside
Long-term memorySmall but always loadedPersists across sessionsVery high - a false fact becomes permanentStrict write criteria, record source and timestamp, re-verify periodically
Current query / acceptance criteriaSmallCurrent turnLowMark boundaries with delimiters, place toward the end

This split matters for two practical reasons. First, physically separating the layers that repeat from the layers that change lets prompt caching actually work. Per each vendor's documentation, a prompt cache hits only when the leading prefix is unchanged, so the recommended layout puts rarely-changing material - system instructions, tool definitions, few-shot examples - up front and pushes per-request material such as the user query and retrieval results to the end. Caching is not one vendor's exclusive trick: Anthropic introduced prompt caching in 2024, OpenAI shipped automatic caching the same year, and Google offers both explicit context caching and implicit caching that applies automatically when conditions are met on Gemini. Eligibility rules, minimum token counts, and discounts differ by vendor and model, so check the relevant docs before relying on them.

Second, the order in which you cut differs by layer. When the window gets tight, people usually reach for the system prompt first - but the bulk is almost always in the history and evidence layers. The fixed layer is the part caching covers, so trimming it saves little while risking behavioral drift from a dropped rule. The following layout rules come up repeatedly in practice.

  • Rarely-changing material first, per-request material last - this targets cache hits and recency bias at the same time.
  • Bulk inputs such as documents, logs, and code should have clear boundaries marked with delimiters (XML-like tags work well), with instructions placed outside them. Major vendor guides converge on this layout.
  • Never interleave retrieval results into the system instructions. Disturbing the fixed layer invalidates the cache wholesale.
  • Write only verified decisions into long-term memory. A guess promoted to memory becomes permanent contamination that outlives the session.
  • Do not keep raw tool output in the window; replace it with a summary plus external pointers (file paths, identifiers).

The long-term memory layer is increasingly a product category of its own. Tools that carry state across sessions and dedicated memory engines were examined in CTX Explained - A Persistent Memory Tool for Claude Code Sessions and Supermemory - The Memory and Context Engine for AI 2026 respectively.

5. Practical Rules to Prevent Context Contamination

5.1 Four Failure Modes

As context lengthens and steps accumulate, typical breakdown patterns appear. The four most often catalogued in practitioner literature are these.

  • Context poisoning: a hallucination or false fact that slipped in gets reproduced at every later step, and the model builds a strategy on that false premise.
  • Context distraction: as history grows, the model leans on accumulated past actions rather than trained knowledge, replaying old patterns instead of forming a new plan.
  • Context confusion: irrelevant information in the window degrades response quality, because the model tries to use everything it is given even when it hurts.
  • Context clash: contradictory pieces of information coexist in the window and destabilize judgment.

The four look similar from the outside but differ in cause and cure. Rather than rewriting the prompt the moment output goes bad, it is much faster to first sort which mode you are in. The table below maps symptoms to causes and mitigations.

Failure modeTypical symptomCauseMitigation
PoisoningAn early false fact keeps getting cited and plans get built on top of itA hallucination or bad detection stays in history and hardens into a premiseKeep facts in structured external storage with sources and re-verify; truncate history past the poisoning point and restart
DistractionNo new plan forms; the same tool call and the same attempt repeatAs history grows the model imitates accumulated past actions over trained knowledgeThreshold-based compaction, a cap on step count, restate the goal and remaining work each turn
ConfusionAnswers cite documents or tools unrelated to the questionIrrelevant retrieval results and unused tool definitions sit in the windowReduce top-k and rerank, load tools dynamically, mask tools irrelevant to the current task
ClashThe same question swings between opposite conclusions and the reasoning wobblesContradictory documents or rules coexist in one windowState source-priority rules explicitly, merge on recency or authority, isolate branches into sub-agents

This four-way taxonomy follows a widely cited practitioner write-up (notably Drew Breunig's piece on how long contexts fail); it is not an academically settled classification, and overlapping cases are common. Still, it works well enough as a map for deciding what to suspect first.

5.2 Defensive Rules

The rules that reduce these failures are fairly standardized too, and there are three core ones. First, compaction and summarization: rather than leaving stale history as is, swap it for a summary to reclaim tokens, and drop information that already exists in the environment and can simply be recomputed. Second, structured external recording: keeping important state only in the chat window lets poisoned facts survive, so record decisions, facts, and to-dos in structured storage outside the window (notes, files, a state object) and read them back only when needed.

Third, sub-agent isolation: instead of cramming a complex task into one long context, delegate to sub-agents that each hold an isolated context window and return only a short, compacted summary. That way, poisoning or contradiction that arises in one branch does not spread across the whole window. When rules are hard for a human to follow every time, another approach is to enforce the frequently-broken ones with automated checks or hooks - a direction covered separately in compiling CLAUDE.md rules into hooks.

6. How to Budget Your Context

6.1 Window Size and Usable Budget Are Not the Same

The most common misconception is that a 200K-token context window means 200K usable tokens. It does not. Chroma's context rot technical report, published in July 2025, evaluated 18 models including the GPT-4.1, Claude 4, Gemini 2.5, and Qwen3 families and observed performance wobbling with longer input across all of them, even on simple tasks (per the report). The more important observation is that degradation is not uniform. At the same length, the lower the semantic similarity between the target content and the question, and the more distracting documents are mixed in, the steeper the drop. In other words, the advertised limit is a physical ceiling, not a performance guarantee.

None of this is entirely new. The lost-in-the-middle observation (Liu et al., 2023) already showed that information placed in the middle of a long input is used less than material at either end, and later work reported that the U-shape does not always hold and that attention skews toward recent tokens once the window is sufficiently full. The details vary by model and task, but the conclusion that length is not free is common to all of it. Hence the practice of not treating window size as budget, and setting per-layer caps in advance.

6.2 A Starting Point for Layer Allocation

LayerWhat goes inStarting shareWhat to cut first when it overflows
FixedSystem instructions, tool definitions, few-shot examplesAround 10%Reduce tool count, compress descriptions
TaskCurrent query, acceptance criteria, output spec5-10%Move the spec to an external file and keep only a pointer
EvidenceRetrieval results, reference docs and code30-40%Lower top-k, rerank, tune chunk size
HistoryConversation history, tool execution results30-40%Swap in compacted summaries, offload raw text
HeadroomSpace for output and reasoningKeep 20% or moreDo not encroach - shrink another layer instead

The percentages are not absolutes. Document question answering needs a bigger evidence layer; a long-running coding agent lives or dies on history management. What matters is not the specific number but the fact that every layer has a cap at all. Without caps, retrieval results and history eat into the headroom layer, and past that point no amount of prompt rewriting brings quality back.

6.3 When to Compact, and What to Keep

Once the history layer hits its cap, compaction is required. The hard part is timing. Compact too early and too often and you pay the summarizer call repeatedly while invalidating the prompt cache every time the prefix changes. Compact too late and you are summarizing from a stretch where quality has already degraded, so the bad state gets carried into the summary verbatim. Published implementations use thresholds anywhere from the 50% range to the 80% range of the window, and the numbers differ across documents. The lesson to take is not a specific number but that the threshold is a parameter to be measured per workload.

Content matters more than timing, in fact. A summary is not an abridged transcript; it must be the state required for the next step to be executable on its own. Deciding in advance what to keep and what to drop turns compaction from loss into cleanup.

What a summary must retain:

  • Settled decisions and a one-line reason for each
  • Unresolved problems and the immediate next action
  • Constraints and prohibitions the user stated - ideally in their original wording
  • Approaches already tried and why they failed (so the same dead end is not re-walked)
  • Pointers such as file paths, identifiers, and URLs, in place of raw text
  • An explicit marker separating verified facts from working assumptions

What a summary can safely drop:

  • Full raw tool output - call the tool again if you need it
  • The complete diff of changes already applied
  • Full stack traces from failed attempts
  • Intermediate reasoning already folded into the conclusion
  • Procedural chatter such as greetings and acknowledgements

7. Designing Tool Definitions - Why More Tools Make Things Worse

Tool definitions are the most underrated item in the context. Once attached they are a fixed cost carried on every single call, and as the count grows it is not only tokens that increase - selection accuracy itself falls. Adding a tool is less a feature addition than a budget expenditure.

7.1 The Problem in Numbers

The RAG-MCP paper (arXiv 2505.03275, May 2025), which tackles tool overload in MCP setups, reports that a baseline placing every tool description directly in the prompt scored 13.62% tool-selection accuracy, while exposing only semantically retrieved relevant tools raised it to 43.13% - more than triple. The same approach also cut prompt tokens by more than half (per the paper). The authors themselves note a limit, though: retrieval precision degrades once the tool registry scales into the thousands, so this is not a universal fix.

Practitioner write-ups repeatedly report noticeable selection degradation once roughly 15 to 20 tools are in active rotation. A positional bias is also reported, where tools in the middle of a list get chosen less often than those at either end - the same grain as the middle-of-a-long-input problem above. The figures swing widely by model and benchmark, so they should not be taken as absolutes; take only the direction. Returns from adding tools diminish, then turn negative past some point.

7.2 Common Anti-Patterns and Fixes

Anti-patternSymptom it producesFix
Several similarly named tools (search_docs / search_files / search_code)Wrong tool invoked; arguments borrowed from another tool's schemaSplit names by verb and target domain, or merge into one tool and branch on a parameter
Verbose tool descriptionsContinuous drain on the fixed layerCut to one or two sentences stating when to use it and when not to
All parameters as free-form stringsArgument hallucination - invented values that do not existUse enums for closed value sets, separate required from optional, provide defaults
Return values as raw dumps (full JSON)History layer explodes, evidence gets confusedReturn only needed fields, add size caps and pagination, offer a summary mode
No cap on tool countSelection accuracy drops, positional bias appearsLoad tools dynamically (tool retrieval), split by role into sub-agents
Returning raw stack traces on failurePoisoning, plus pointless retry loopsNormalize into error messages that state the next action

7.3 A Tool Schema Review List

  • Can a human tell from the name alone when this tool applies?
  • Does the first sentence of the description say when to use it, and the second when not to?
  • Are closed-value parameters declared as enums rather than free strings?
  • Are required and optional parameters distinguished, with sensible defaults?
  • Is the return value something the model can read and reason over directly (names, URLs, descriptions - not internal ID dumps)?
  • Does the return have a size cap and pagination?
  • On failure, does the error message tell the caller what to do next?
  • Could two overlapping tools be merged into one that branches on a parameter?

The view that treats tools and the execution environment as an extension of context is laid out separately in Code as Agent Harness - A New Paradigm for AI Agentic Systems.

8. Why It Is Decisive Precisely in the Agent Era

For a one-shot chatbot, the burden of context engineering is light. Ask once, answer once, and you only need to get that single context right. But an agent is a loop. It plans a goal, calls tools, checks results, and decides the next step, repeating this dozens to hundreds of times. The judgment at step 47 is made on top of the residue of steps 1 through 46. So a small early poisoning or overload snowballs the further along it goes.

In fact, in some agent experiments, once context crossed a certain threshold (roughly the 100,000-token range), the model was observed replaying past actions rather than forming new plans - the distraction effect. That is why running an agent long and stably requires actively managing, at every step, what to keep and what to discard, and what to hold as memory versus fetch via retrieval on demand. Context engineering is less a replacement for prompt engineering than a case of the agent execution structure pushing its importance up the stack.

9. Measurement and Debugging - Finding Where It Broke

The hardest thing about context problems is that from the outside they look like the model's fault. Judged on final output alone, the model appears to have suddenly gotten dumber - but the real cause is often the shape of the window at step 47. Context engineering is therefore a design discipline and an observability problem at once. If you cannot see what entered the window and what actually got used in the answer, improvement degenerates into prompt tweaking by intuition.

9.1 From Symptom to Cause

Observed signalFailure mode to suspectHow to confirm
The same tool is called repeatedly with no progressDistractionCorrelate step number against cumulative tokens; force a compaction and rerun the same task to see if it reproduces
An early false fact keeps being citedPoisoningBinary-search the trace for the fact's first appearance and rerun with everything after it removed
Answers cite documents unrelated to the questionConfusionLower top-k and check reproduction; require the answer to cite source document identifiers
Conclusions oscillate on the same questionClashCollect the evidence in the window and diff the contradicting pairs directly
Accuracy drops from length aloneContext rotEvaluate the identical task at length tiers (say 10K, 50K, 200K tokens) and plot the degradation curve
Answers stay correct but cost and latency keep climbingCache invalidation / history accumulationCheck cache hit rate alongside the per-step input token trend

9.2 What to Instrument

Instrumentation itself is being standardized. OpenTelemetry's GenAI semantic conventions specify recording LLM calls, agent invocations, and tool executions under a shared gen_ai.* attribute vocabulary. Because traces land in the same vocabulary regardless of framework or vendor, questions like which step was slow, which call was expensive, and which tool failed with what arguments can be answered by querying attributes instead of reading log prose (per the OpenTelemetry docs). Note, though, that the conventions do not cover output quality evaluation. Factuality and format-compliance scoring has to be layered on separately. A case study that pulled apart real session logs to trace token waste appears in Agent-Blackbox: Analyzing Claude Code and OpenCode via Session Maps and Token Waste.

Whatever tooling you use, at minimum the following need to be captured for a context problem to be reconstructable after the fact.

  • Input token count per step - better still, broken down by layer
  • Prompt cache hit rate and the points where invalidation occurred
  • Per tool call: name, arguments, duration, success or failure
  • The retrieval step's top-k, and what fraction of documents were actually cited in the answer
  • When compaction fired, token counts before and after, and the generated summary itself
  • Total step count and termination reason (completed, cap reached, error)
  • The link between the final output and the context fragments cited as its basis

9.3 Preventing Regressions

Changing the context configuration carries the same regression risk as changing code, but it is easy to miss and often ships without review. Whether adding one tool degrades selection accuracy on existing tasks, whether one more rule in the system prompt clashes with existing rules, whether raising top-k increases confusion - these can only be known by measuring. Keeping a golden set, however small, and running it across input length tiers whenever the context configuration changes is close to the only real safeguard in this field.

10. A Practical Checklist

10.1 The One-Page Summary

Here is a set of checks worth using when moving these rules into a real system. These are criteria for LLMs in general, not any one model.

AreaCheck questionAim
InstructionsDoes the system prompt hold only always-true minimal principles?Neither thin nor verbose
RetrievalDo you pull only query-matching fragments, with a cap?Avoid loading everything
MemoryIs important state recorded outside the window, structured?Minimize re-injection
ToolsHave you pruned tools with overlapping functions?Clear, minimal, non-overlapping
Poison defenseDo you compact, summarize, and isolate long history?Block the snowball

This table is a starting point, not an absolute answer. Depending on the nature of the work, you might weight retrieval more heavily or compact memory more aggressively. What matters is treating context not as a sentence you write once and are done with but as a living resource to be managed at every step.

10.2 Check at Design Time

  • Is every rule left in the system prompt always true, with situational exceptions split out elsewhere?
  • Are token caps for the five layers - fixed, task, evidence, history, headroom - written down somewhere?
  • Is rarely-changing material placed first and per-request material last?
  • Have you pruned tools that have not been called once in the past month?
  • Can a person judge from the tool name and description alone when to use it?
  • Do retrieval top-k and chunk size have caps, and were those values chosen with a rationale?
  • Are bulk inputs like documents and logs delimited with clear boundaries?

10.3 Check in Operation

  • Was the compaction threshold set by measurement, rather than left at a framework default?
  • Does the compacted summary retain decisions, constraints, open items, and failed attempts without omission?
  • Are summaries and external pointers kept in place of raw tool output?
  • Is there a verification step before writing to long-term memory, with assumptions recorded separately from facts?
  • Do sub-agents get isolated windows, with only short summaries returned?
  • Are step count, tokens, and cost capped, with a safe stop when exceeded?
  • Are the goal and remaining work restated periodically as sessions run long?

10.4 Guarding Contamination and Quality

  • Is externally sourced text - retrieval results, web pages, tool output - delimited so it is not mistaken for instructions?
  • Can the evidence an answer cites be traced back to the original?
  • Is there a documented procedure for truncating history and restarting when poisoning is suspected?
  • When sources conflict, is there an explicit rule for which one wins?
  • Is there a golden set across length tiers, and is it run whenever the context configuration changes?
  • Are tool additions and prompt changes reviewed at the same level as code changes?

10.5 On Cost and Performance

  • Are you watching the cache hit rate, and do you know how much compaction breaks it?
  • Is the per-step input token trend diverging?
  • Has the repeated fixed prefix been stabilized into a cache-friendly shape?
  • Do large return values have pagination or a summary mode ready?
  • Is the same information being loaded redundantly across multiple layers?
  • Have you checked which parts could be served by retrieval instead of relying on a long window?

Conclusion

The context engineering rules that get refreshed with every new model all point in one direction: the reliability of an AI system comes from information architecture, not clever phrasing. Prompt engineering is still valid, but the moment tool, memory, and retrieval layers are attached, a good prompt becomes a tiny fraction of the whole job. The rules - keep relevant, minimal context, strip out contamination, and call on memory and retrieval only when needed - do not care whether it is Claude, GPT, or Gemini. A new version of a specific model is just an occasion to revisit these rules; the essence a practitioner must internalize is the habit of designing, at every step, what to show the model. As of 2026, that habit is no longer optional but the fundamentals of running an agent properly.
