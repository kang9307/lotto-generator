OAuth를 오해하는 자리들 - 인증이 아니라 위임된 인가다

역할 넷, 흐름 넷, 그리고 최신 BCP가 목록에서 지운 것들

2026-08-24 개발/인프라

회의에서 「OAuth로 로그인 붙였어요」라는 말이 나오면 그 뒤 30분의 대화가 대체로 정해진다. 누군가는 액세스 토큰을 열어 사용자 식별자를 꺼내 쓰고 있고, 누군가는 그 토큰을 브라우저 저장소에 넣어 두었으며, 또 누군가는 스코프를 화면에서만 감춰 두고 권한 통제라고 부르고 있다. 셋 다 흔하고, 셋 다 같은 뿌리에서 나온다.

뿌리는 규격 이름에 있다. OAuth 2.0의 정식 명칭은 The OAuth 2.0 Authorization Framework이고 여기에 authentication이라는 단어가 없다. 우연이 아니다. 이 규격이 풀려던 문제가 애초에 「이 사람이 누구인가」가 아니라 「이 애플리케이션이 저 자원에 어디까지 손댈 수 있는가」였기 때문이다. 이 한 줄을 놓치면 그 위에 쌓는 결정들이 순서대로 어긋난다.

아래는 그 어긋남이 드러나는 자리들을 규격 순서대로 짚은 것이다. 각 절은 「무엇이 규범인가」와 「그 규범을 어겼을 때 무엇이 무너지는가」까지만 다룬다. 공격을 어떻게 수행하는지는 다루지 않는다.

이 글에서 다루는 것

  1. 가장 큰 오해 - OAuth는 인증 프로토콜이 아니다
  2. 역할은 넷이고, 신뢰의 방향은 하나가 아니다
  3. 흐름별로 무엇이 다른가
  4. 목록에서 빠진 두 흐름 - 암시적과 비밀번호 그랜트
  5. PKCE가 막는 것 - 이제 공개 클라이언트만의 이야기가 아니다
  6. 토큰을 어디에 두나 - 브라우저 저장소와 쿠키의 대가
  7. 스코프와 최소 권한 - 실제로 강제되는 자리
  8. 리프레시 토큰과 회전 - 감지한다는 말의 뜻
  9. 검증은 어디서 하나 - 클라이언트가 대신할 수 없는 것
  10. 자주 나오는 잘못된 조합 - 이 조합에서 무엇이 무너지나
  11. 확인하지 못한 것
  12. 읽을 문서 순서

1. 가장 큰 오해 - OAuth는 인증 프로토콜이 아니다

RFC 6749는 2012년 10월에 나온 Proposed Standard다. 초록은 이 틀이 하는 일을 「제3자 애플리케이션이 HTTP 서비스에 제한된 접근 권한을 얻게 한다」로 규정한다. 자원 소유자를 대신해서든, 애플리케이션 자신을 위해서든, 결과물은 언제나 접근 권한이다. 신원 증명이 아니다.

그러면 액세스 토큰의 성격도 자연히 정해진다. 액세스 토큰은 자원 서버에 제시하라고 만든 물건이지 클라이언트가 읽으라고 만든 물건이 아니다. 그 안에 무엇이 들어 있든 「이 요청에 어디까지 응해도 되는가」에 대한 정보이지 「화면 앞의 사람이 누구인가」에 대한 정보가 아니다. RFC 6749의 보안 고려사항 절에도 액세스 토큰을 신원 증명처럼 쓰는 것에 대한 경고가 따로 들어 있다.

로그인이 목적이라면 층을 하나 더 얹어야 한다. OpenID Connect Core 1.0은 스스로를 「OAuth 2.0 프로토콜 위에 얹은 단순한 신원 계층」이라고 정의한다. 이 층이 새로 들여오는 것이 ID 토큰이다. ID 토큰은 최종 사용자의 인증에 관한 클레임을 담은 보안 토큰이고, JWT 형태를 취하며, 다음 클레임이 필수다.

  • iss - 응답을 발급한 발급자 식별자
  • sub - 주체 식별자. 발급자 안에서 지역적으로 유일하며 재할당되지 않는다
  • aud - 이 ID 토큰이 향하는 대상. OAuth 클라이언트 식별자를 포함한다
  • exp - 이 시각 이후로는 ID 토큰을 받아들이면 안 되는 만료 시각
  • iat - JWT가 발급된 시각

두 토큰의 수신자가 다르다는 점이 이 절의 핵심이다. 액세스 토큰은 자원 서버가 받고, ID 토큰은 클라이언트가 받는다. 프로필이 필요하면 OpenID Connect는 UserInfo 엔드포인트를 두는데, 이것은 액세스 토큰을 제시하면 인가된 최종 사용자 정보를 돌려주는 보호 자원이다. 프로필 조회조차 인가의 문법으로 이루어진다.

판단 기준. 우리 서비스가 필요로 하는 것이 「저 서비스의 내 캘린더에 일정을 넣을 권한」이면 OAuth로 끝난다. 「이 사람이 우리 서비스의 어느 계정인지 확정하는 것」이면 OpenID Connect가 필요하다. 두 요구가 섞여 있으면 두 층을 다 쓴다. 액세스 토큰 하나로 둘 다 하려는 순간이 사고의 출발점이다.

2. 역할은 넷이고, 신뢰의 방향은 하나가 아니다

RFC 6749는 참여자를 넷으로 나눈다. 용어를 정확히 붙잡아 두면 이후 절이 훨씬 쉬워진다.

  • 자원 소유자(resource owner) - 보호 자원에 대한 접근을 허가할 수 있는 주체
  • 클라이언트(client) - 자원 소유자를 대신해, 그의 인가를 받아 보호 자원 요청을 보내는 애플리케이션
  • 인가 서버(authorization server) - 자원 소유자를 성공적으로 인증하고 인가를 얻은 뒤 클라이언트에 액세스 토큰을 발급하는 서버
  • 자원 서버(resource server) - 보호 자원을 호스팅하며, 액세스 토큰을 사용한 보호 자원 요청을 받아 응답하는 서버

여기서 자주 뭉개지는 것이 신뢰의 방향이다. 자원 소유자가 믿는 상대는 인가 서버 하나이고, 비밀번호나 2단계 인증 수단을 입력하는 자리는 거기뿐이어야 한다. 클라이언트는 자원 소유자를 믿지 않고 인가 서버가 내준 결과물을 믿는다. 자원 서버 역시 클라이언트가 아니라 인가 서버가 발급한 토큰의 유효성을 믿는다. 네 당사자가 서로를 대칭적으로 믿는 구조가 아니라는 점이 이 규격의 뼈대다.

또 하나 갈리는 축이 클라이언트 유형이다. 자기 자격증명을 비밀로 유지할 수 있는 기밀 클라이언트와 그럴 수 없는 공개 클라이언트가 있다. 서버에서 도는 백엔드는 앞쪽, 브라우저의 단일 페이지 애플리케이션이나 사용자 기기의 네이티브 앱은 뒤쪽이다. 이후 규범 대부분이 이 축에서 갈라진다. 클라이언트 자격증명 그랜트를 쓸 수 있는지도, PKCE가 필수인지 권고인지도, 리프레시 토큰에 회전이 요구되는지도 전부 여기에 달렸다.

네이티브 앱에는 규범이 하나 더 붙는다. RFC 8252는 2017년 10월에 나온 Best Current Practice이며 BCP 212 번호를 달고 있다. 네이티브 앱의 인가 요청은 임베디드 사용자 에이전트가 아니라 외부 사용자 에이전트, 주로 사용자의 브라우저를 통해서만 이루어져야 한다는 것이 핵심이다. 이유는 앞 문단의 신뢰 방향으로 읽으면 분명하다. 임베디드 웹뷰는 클라이언트가 소유한 화면이고, 자원 소유자가 인가 서버에만 자격증명을 준다는 전제가 그 화면에서는 성립하지 않는다.

3. 흐름별로 무엇이 다른가

흐름을 외우는 것보다 흐름을 가르는 질문 두 개를 잡는 편이 빠르다. 첫째, 자원 소유자가 지금 그 자리에 있는가. 둘째, 클라이언트가 비밀을 지킬 수 있는가. 이 둘의 답이 흐름을 결정한다.

흐름 규격과 상태 자원 소유자가 그 자리에 있나 클라이언트 유형 쓰이는 자리
인가 코드 흐름 RFC 6749 (Proposed Standard, 2012-10) 있다. 브라우저에서 동의한다 기밀과 공개 모두 사람이 개입하는 거의 모든 경우
PKCE (인가 코드 흐름의 확장) RFC 7636 (Proposed Standard, 2015-09) 있다 공개는 필수, 기밀은 권고 코드 가로채기와 코드 주입 방어를 덧댈 때
기기 인가 그랜트 RFC 8628 (Proposed Standard, 2019-08) 있지만 다른 기기에서 승인한다 주로 공개 스마트 TV, 콘솔, 프린터처럼 입력이 빈약한 기기
클라이언트 자격증명 그랜트 RFC 6749 (Proposed Standard, 2012-10) 없다. 사람이 개입하지 않는다 기밀 클라이언트만 서비스가 자기 이름으로 하는 서버 간 통신

3.1 인가 코드 흐름이 두 단계인 이유

인가 코드 흐름을 처음 보면 단계가 왜 둘로 나뉘는지가 걸린다. 브라우저 리디렉션으로 인가 코드를 받고, 그 코드를 다시 인가 서버에 보내 액세스 토큰으로 바꾼다. 한 번에 토큰을 주면 될 것을 굳이 두 번 왕복한다.

이유는 두 왕복이 서로 다른 채널이기 때문이다. 앞쪽은 사용자의 브라우저를 경유하는 경로다. 리디렉션 URL은 주소창에 뜨고, 브라우저 이력에 남고, 여러 계층을 지난다. 뒤쪽은 클라이언트와 인가 서버가 직접 주고받는 경로다. 액세스 토큰을 뒤쪽 경로에서만 오가게 하면 토큰 자체가 앞쪽 경로의 흔적으로 남지 않는다. 이 분리가 인가 코드 흐름이 지금까지 남은 이유다.

3.2 기기 흐름과 클라이언트 자격증명 흐름

기기 인가 그랜트는 브라우저를 띄울 수 없는 기기를 위한 것이다. 기기는 사용자에게 코드를 보여 주고, 사용자는 스마트폰 같은 별도의 기기에서 승인을 마친다. 그동안 기기는 클라이언트와 사용자 에이전트 사이의 양방향 통신을 요구하는 대신 인가 서버를 반복해서 폴링한다. 리모컨으로 비밀번호를 입력하게 만드는 대신 인가라는 행위 자체를 다른 기기로 옮겨 버린 설계다.

클라이언트 자격증명 그랜트는 성격이 아예 다르다. 여기에는 자원 소유자가 없다. 클라이언트가 자기 통제 아래 있거나 인가 서버와 미리 합의된 자원에 접근할 때 쓴다. 그래서 규격은 못을 박아 둔다. 이 그랜트 유형은 기밀 클라이언트만 사용해야 한다. 흔한 오용은 사용자 데이터를 이 흐름으로 가져오는 것이다. 그러면 「누가 허가했는가」에 해당하는 당사자가 구조에서 사라지고, 감사 기록에 남는 것은 서비스 계정 하나뿐이다.

4. 목록에서 빠진 두 흐름 - 암시적과 비밀번호 그랜트

2025년 1월에 RFC 9700이 나왔다. 이름은 Best Current Practice for OAuth 2.0 Security이고, 상태는 Best Current Practice, BCP 240이다. 이 문서는 RFC 6749와 RFC 6750, 그리고 위협 모델 문서인 RFC 6819를 갱신한다. 즉 오늘 OAuth를 설계한다면, 기준선은 6749가 아니라 이 문서다.

이 문서가 한 일 가운데 가장 눈에 띄는 것이 두 흐름을 목록에서 내린 것이다.

4.1 암시적 흐름

RFC 9700은 클라이언트가 암시적 그랜트를 쓰지 않아야 한다(SHOULD NOT)고 적는다. 인가 응답에 액세스 토큰이 실려 나오는 다른 응답 유형도 같이 묶인다. 다만 인가 응답으로의 액세스 토큰 주입이 차단되는 경우는 예외로 남겨 둔다. 근거는 두 가지다.

  • 액세스 토큰 유출과 재사용에 취약하다
  • 이 방식에는 송신자 결속을 걸 표준화된 수단이 없다

같은 문서는 대안을 한 줄로 준다. code 응답 유형을 쓰라. 앞 절의 채널 분리를 떠올리면 이유가 겹친다. 암시적 흐름은 토큰을 프런트 채널에 태운다. 그러면 3.1에서 애써 분리해 둔 것이 다시 합쳐진다.

4.2 자원 소유자 비밀번호 자격증명 그랜트

이쪽은 표현이 더 강하다. RFC 9700은 이 그랜트를 쓰면 안 된다(MUST NOT)고 적는다. 사유가 넷이다.

  • 자원 소유자의 자격증명을 클라이언트에 안전하지 않게 노출한다
  • 공격 표면을 넓힌다
  • 사용자가 인가 서버 바깥에서 자격증명을 입력하도록 훈련시킨다
  • 2단계 인증과 함께 동작하도록 설계되지 않았다

세 번째 사유가 특히 실무적이다. 사용자를 훈련시킨다는 표현은 기술적 취약점이 아니라 습관에 관한 지적이다. 앱 화면에서 비밀번호를 넣는 것이 정상이라고 학습한 사용자는, 그 화면이 누구 것인지 구별할 근거를 잃는다. 네 번째 사유는 더 직접적이다. 자격증명 한 쌍을 그대로 넘겨받는 구조에는 2단계 인증이 끼어들 자리가 없다. 이 지점은 2단계 인증을 방식별로 정리한 글과 이어서 읽으면 더 선명해진다.

참고로 OAuth 2.1 작업이 진행 중이다. 2026년 3월 2일자 15판이 나와 있고 상태는 인터넷 초안(Internet-Draft)이며, RFC 6749와 RFC 6750을 통합하면서 암시적 그랜트와 비밀번호 그랜트를 규정에서 제외한다. 다만 초안은 표준이 아니다. 오늘 규범적 근거가 필요하면 인용해야 할 것은 RFC 9700 쪽이다.

5. PKCE가 막는 것 - 이제 공개 클라이언트만의 이야기가 아니다

RFC 7636의 제목은 Proof Key for Code Exchange by OAuth Public Clients다. 2015년 9월에 나온 Proposed Standard이고, 초록이 겨냥하는 문제는 하나다. 인가 코드 그랜트를 쓰는 공개 클라이언트가 인가 코드 가로채기 공격에 취약하다는 것.

완화 방식은 이름 그대로다. 클라이언트가 요청마다 동적으로 암호학적 키를 만들어 인가 요청과 토큰 요청을 서로 묶는다. 인가 요청에는 그 키에서 파생한 값을, 토큰 요청에는 원본 값을 보내고 인가 서버가 둘을 대조한다. 결과적으로 코드만 손에 넣은 쪽은 그것을 토큰으로 바꿀 수 없다.

여기까지가 오래된 이해다. 바뀐 것은 적용 범위다. RFC 9700은 이렇게 정리한다.

  • 공개 클라이언트는 PKCE를 반드시 써야 한다(MUST).
  • 기밀 클라이언트에도 PKCE 사용이 권고된다(RECOMMENDED). 인가 코드의 오용과 주입에 강한 보호를 제공하기 때문이다.
  • 공격자가 탈취한 인가 코드를 주입하려 해도, 원본 값 대조가 어긋나면서 토큰 엔드포인트에서 교환이 성립하지 않는다.
  • 같은 문서는 PKCE가 강한 공격자가 있는 상황에서도 CSRF에 대한 보호를 제공한다고 적는다.

이 변화를 한 문장으로 옮기면 이렇다. PKCE는 「비밀을 못 지키는 클라이언트를 위한 보완재」에서 「코드 주입이라는 위협 자체에 대한 방어」로 자리를 옮겼다. 백엔드가 클라이언트 비밀을 잘 보관하고 있으니 PKCE는 필요 없다는 판단은, 방어 대상이 무엇인지를 한 세대 전 기준으로 잡고 있는 것이다.

같은 절에서 함께 봐야 할 규범이 리디렉션 URI 대조다. RFC 9700은 인가 서버가 정확한 문자열 일치를 사용해야 한다(MUST)고 요구한다. 예외는 네이티브 앱의 localhost 리디렉션 URI에서의 포트 번호뿐이며, 패턴 매칭은 복잡도와 보안 문제 때문에 명시적으로 기각됐다. 대조가 느슨하면 인가 응답이 돌아갈 목적지의 집합이 클라이언트가 의도한 것보다 넓어진다.

인가 서버를 여럿 붙이는 클라이언트에는 규범이 하나 더 있다. RFC 9207은 2022년에 나온 Proposed Standard로, 인가 응답에 발급자 식별자를 명시적으로 담는 iss 파라미터를 정의한다. 목적은 혼합 공격(mix-up attack) 대응이다. RFC 9700은 클라이언트가 요청을 보낸 발급자를 저장해 두었다가 응답에서 받은 값과 대조하고, 불일치하면 상호작용을 중단해야 한다고 요구한다.

6. 토큰을 어디에 두나 - 브라우저 저장소와 쿠키의 대가

이 질문에는 단일 정답이 없다. 규격도 그렇게 말한다. 2026년 8월에 나온 RFC 10017은 OAuth 2.0 for Browser-Based Applications라는 제목의 Best Current Practice이며 BCP 212 번호를 공유한다. 이 문서는 브라우저 기반 애플리케이션이 취할 수 있는 구조를 셋으로 놓는다.

  • 백엔드 포 프런트엔드(BFF) - 토큰을 서버 쪽에 두고, 브라우저와는 세션 쿠키로 대화한다
  • 토큰 중개 백엔드 - 백엔드가 기밀 클라이언트로 동작하되 액세스 토큰을 브라우저에 내려 준다
  • 브라우저 기반 OAuth 2.0 클라이언트 - 브라우저 안의 코드가 곧 클라이언트다

문서가 세 구조를 나란히 놓으며 붙인 문장이 판단의 기준이 된다. 각 구조는 보안과 단순함 사이에서 서로 다른 절충을 제시한다. 민감한 애플리케이션에는 BFF를 권하지만 나머지 구조에도 정당한 쓰임이 있다는 것이 문서의 태도다.

그 절충을 읽는 축이 되는 문장이 하나 더 있다. 악성 자바스크립트 코드는 정상 애플리케이션 코드와 같은 권한을 가진다. 스크립트 실행이 뚫린 상황에서 「스크립트가 못 읽는 브라우저 안 저장소」라는 것은 없다. 다만 접근 난이도에는 차이가 있어서, 문서는 로컬 스토리지처럼 어디서나 접근 가능한 저장 영역은 더 고립된 영역보다 악성 자바스크립트가 접근하기 쉽다고 적는다.

보관 위치 스크립트 실행이 뚫렸을 때 브라우저 자동 전송 따라오는 요구
로컬 스토리지 사정권. 문서가 접근이 더 쉬운 영역으로 분류한다 없음 스크립트 주입 차단이 사실상 유일한 방어선
세션 스토리지 사정권. 수명이 탭에 묶일 뿐 접근 통제가 아니다 없음 탭 간 공유가 안 되는 데 따르는 경험 설계
자바스크립트 메모리 변수 사정권. 같은 실행 문맥에 있다 없음 새로고침마다 재취득 경로가 필요
HttpOnly와 Secure 쿠키 (BFF) 세션 상태를 스크립트가 직접 읽지 못한다 있음. 브라우저가 실어 보낸다 자동 전송 때문에 교차 사이트 요청 축의 방어

BFF 쪽에 붙는 규범은 명시적이다. BFF는 자기 쿠키에 Secure 플래그와 HttpOnly 플래그를 반드시 켜야 한다(MUST). 문서는 HttpOnly 쿠키가 공격자가 세션 상태에 직접 접근하는 것을 막는다고 설명한다. 반대편 대가도 분명하다. 쿠키는 브라우저가 알아서 붙여 보내므로 「요청이 우리 화면에서 시작됐는가」를 따로 확인하는 축이 필요해진다. 이 대가 계산은 신뢰 경계와 웹 보안 통제를 정리한 글에서 쿠키 전송 규칙과 함께 더 다뤘다.

토큰 중개 백엔드에 대해서도 문서는 양면을 같이 적는다. 백엔드는 기밀 클라이언트로 동작해야 하지만(MUST), 액세스 토큰이 브라우저로 내려가는 순간 브라우저 안의 악성 코드에 의한 토큰 탈취에 노출된다. 어느 구조를 고르든 사라지는 위험이 아니라 옮겨 가는 위험이다.

7. 스코프와 최소 권한 - 실제로 강제되는 자리

스코프는 RFC 6749에서 공백으로 구분된 대소문자 구분 문자열의 목록으로 정의된다. 여기서 놓치기 쉬운 규범이 이어진다. 인가 서버는 클라이언트가 요청한 스코프를 전부 또는 일부 무시할 수 있다. 인가 서버의 정책이나 자원 소유자의 지시에 따라 그렇게 한다. 그리고 발급된 스코프가 요청한 것과 다르면, 인가 서버는 실제로 부여된 범위를 알리기 위해 응답에 scope 파라미터를 포함해야 한다.

여기서 나오는 결론이 실무적으로 크다. 스코프는 요청이지 보장이 아니다. 클라이언트 코드가 「우리는 이 셋을 요청했으니 이 셋이 있다」를 전제로 짜여 있으면, 인가 서버가 하나를 깎아 준 순간 그 전제는 사실이 아니다. 읽어야 할 것은 요청 목록이 아니라 응답의 scope다.

그리고 더 중요한 질문. 스코프는 어디서 강제되는가. 답은 자원 서버다. RFC 9700은 이렇게 적는다. 모든 자원 서버는 모든 요청에 대해, 그 요청과 함께 온 액세스 토큰이 바로 그 자원 서버에서 쓰이도록 의도된 것인지 검증할 의무가 있다. 같은 절은 토큰의 권한 자체를 좁히라고도 요구한다. 액세스 토큰은 특정 자원 서버로 대상이 한정되어야 하며(SHOULD), 여의치 않으면 소수의 자원 서버 집합으로 한정되어야 한다. 대상 지정은 scope 파라미터로도, RFC 8707의 resource 파라미터로도 가능하다고 문서는 덧붙인다.

여기서 무너지는 것. 프런트엔드에서 스코프를 보고 버튼을 감추는 것은 강제가 아니라 안내다. 자원 서버가 매 요청마다 토큰의 대상과 범위를 확인하지 않으면, 그 버튼이 화면에 있든 없든 해당 엔드포인트는 열려 있다. 대상 한정을 하지 않으면 다른 자원 서버를 위해 발급된 토큰이 그대로 통과한다. 최소 권한이라는 말은 스코프 문자열을 짧게 쓰는 것이 아니라, 검사하는 지점을 자원 서버에 두는 것이다.

8. 리프레시 토큰과 회전 - 감지한다는 말의 뜻

RFC 9700의 요구부터 정확히 옮긴다. 공개 클라이언트에 발급되는 리프레시 토큰은 송신자 결속이 걸려 있거나 리프레시 토큰 회전을 써야 한다(MUST). 둘 중 하나다. 기밀 클라이언트 쪽은 RFC 6749가 이미 리프레시 토큰이 발급받은 클라이언트에서만 쓰일 수 있도록 요구하고 있다.

송신자 결속 수단으로 문서가 드는 것은 상호 TLS와 DPoP 두 가지다. DPoP는 RFC 9449로 2023년에 나온 Proposed Standard이며, 애플리케이션 계층에서 소유 증명을 붙여 토큰에 송신자 결속을 거는 방식이다. 초록은 이 방식이 액세스 토큰과 리프레시 토큰의 재사용 공격을 탐지할 수 있게 한다고 적는다. 이런 장치가 왜 따로 필요한지는 RFC 6750의 정의로 되돌아가면 분명하다. 소지자 토큰은 암호학적 키의 소유를 증명하지 않아도 그 토큰과 연결된 자원에 접근을 허용하는 물건이다. 가진 사람이 곧 권한자라는 뜻이다.

회전 쪽의 원리는 문서에 그대로 적혀 있다. 리프레시 토큰이 탈취되어 공격자와 정상 클라이언트가 모두 그것을 사용하면, 둘 중 하나는 무효화된 리프레시 토큰을 제시하게 되고 그 사실이 인가 서버에 침해를 알린다. 그다음 문장이 실무적으로 더 중요하다. 인가 서버는 어느 쪽이 무효 토큰을 제출했는지 판별할 수 없으므로, 활성 리프레시 토큰을 폐기한다.

이 두 문장을 붙여 읽으면 회전의 성격이 드러난다. 회전은 탈취를 막는 장치가 아니다. 탈취된 토큰이 사용되는 순간을 감지하고, 판별이 불가능하므로 양쪽을 함께 끊는 장치다. 여기서 따라오는 설계 부담이 둘이다.

  • 정상 사용자도 함께 끊긴다. 감지가 걸리면 재로그인이 필요하다. 그 경험을 설계해 두지 않으면 보안 장치가 장애로 인식된다
  • 클라이언트가 새 토큰을 확실히 저장해야 성립한다. 갱신 응답에서 받은 새 리프레시 토큰을 저장하지 못하고 예전 것을 다시 쓰면 그 클라이언트가 스스로 무효 토큰을 제시하는 쪽이 된다. 여러 요청이 동시에 갱신을 시도하는 구조에서는 갱신 경로를 한 줄로 모으는 조건이 새로 붙는다

클라이언트 쪽 저장 문제를 명령줄 도구 관점에서 더 파고든 내용은 CLI 인증 설계를 정리한 글에 있다.

9. 검증은 어디서 하나 - 클라이언트가 대신할 수 없는 것

토큰이 둘이면 검증하는 쪽도 둘이다. 이 대응을 뒤집으면 사고가 난다.

9.1 액세스 토큰은 자원 서버가 검증한다

RFC 9700의 문장을 다시 가져온다. 모든 자원 서버는 모든 요청에 대해, 함께 온 액세스 토큰이 그 자원 서버에서 쓰이도록 의도된 것인지 검증할 의무가 있다. 이 검증은 토큰 형식에 따라 두 갈래로 갈린다.

  • JWT 형식이면 - RFC 9068이 2021년에 나온 Proposed Standard로, OAuth 2.0 액세스 토큰을 JWT로 발급할 때의 필수와 선택 클레임, 그리고 검증 절차를 정한다. 이 프로파일이 생긴 이유 자체가 제품마다 제각각인 JWT 토큰 구현 때문에 상호운용이 깨졌기 때문이다
  • 불투명 토큰이면 - RFC 7662가 2015년 10월에 나온 Proposed Standard로, 보호 자원이 인가 서버에 토큰의 활성 여부와 메타데이터를 물어보는 인트로스펙션 규격을 정의한다. 토큰 안에 정보가 들어 있든 아니든 동작한다는 것이 이 방식의 설계 의도다

9.2 ID 토큰은 클라이언트가 검증한다

OpenID Connect Core 1.0은 ID 토큰 검증 절에서 클라이언트가 확인해야 할 것을 열거한다.

  • 발급자가 정확히 일치하는가
  • 대상에 자기 클라이언트 식별자가 들어 있는가
  • 현재 시각이 만료 시각 이전인가
  • 인가 요청에 nonce를 보냈다면 그 값이 일치하는가
  • 발급자가 제공하는 키로 서명이 유효한가

9.3 그래서 클라이언트에서 하면 안 되는 것

브라우저 안의 코드가 토큰을 해석하는 것 자체는 문제가 아니다. 만료가 가까워졌는지 보고 갱신을 준비하거나 사용자 이름을 화면에 그리는 것은 정상적인 쓰임이다. 문제는 그 해석 결과를 권한 판정의 근거로 삼는 것이다.

이유가 둘이다. 첫째, 6절의 문장이 여기서도 성립한다. 브라우저에서 도는 코드는 악성 코드와 같은 권한 위에 있고, 그 코드가 수행한 서명 검증은 같은 실행 문맥에서 무력화될 수 있다. 둘째, 서버는 브라우저가 무엇을 검증했는지 알 방법이 없다. 자원 서버에 도착하는 것은 요청과 토큰뿐이다.

그래서 서명 검증, 발급자 확인, 수신자 확인, 만료 확인은 그 토큰을 근거로 무언가를 내주는 쪽에서 이루어져야 한다. 액세스 토큰이면 자원 서버, ID 토큰이면 그것을 근거로 세션을 만드는 클라이언트 서버다. 브라우저에서의 디코드는 표시용 편의이지 통제가 아니다.

10. 자주 나오는 잘못된 조합 - 이 조합에서 무엇이 무너지나

아래 표는 금지 목록이 아니다. 각 조합이 어떤 보장을 잃게 되는지를 규격 문장에 대응시킨 것이다.

조합 이 조합에서 무너지는 것 대응하는 규격
액세스 토큰을 신원 증명으로 사용 누구를 위해 어떤 인증을 거쳐 발급됐는지 확인할 근거가 없다 RFC 6749 보안 고려사항, OpenID Connect Core 1.0
암시적 흐름 유지 토큰이 인가 응답에 실려 나오고, 송신자 결속을 걸 표준 수단이 없다 RFC 9700 (SHOULD NOT)
비밀번호 그랜트와 2단계 인증을 함께 요구 그랜트 자체가 2단계 인증과 동작하도록 설계되지 않았다 RFC 9700 (MUST NOT)
공개 클라이언트에 PKCE 미적용 코드 가로채기와 코드 주입에 대한 방어 자체가 없다 RFC 7636, RFC 9700 (공개 클라이언트 MUST)
리디렉션 URI 부분 일치 허용 인가 응답이 되돌아갈 목적지 집합이 의도보다 넓어진다 RFC 9700 (정확한 문자열 일치 MUST)
브라우저에 리프레시 토큰을 두고 회전 미적용 탈취를 감지할 지점도, 송신자를 묶어 둘 지점도 없다 RFC 9700, RFC 10017
인가 서버 여럿을 붙이고 발급자 미확인 응답이 어느 인가 서버에서 왔는지 확정할 근거가 없다 RFC 9207, RFC 9700
자원 서버가 토큰의 대상을 확인하지 않음 다른 자원 서버를 위해 발급된 토큰이 그대로 통과한다 RFC 9700 (모든 요청에 대한 검증 의무)
네이티브 앱을 임베디드 웹뷰로 인가 인가 서버에만 자격증명을 준다는 전제가 성립하지 않는다 RFC 8252 (BCP 212)
스코프를 화면에서만 강제 강제 지점이 자원 서버가 아니면 엔드포인트는 열려 있다 RFC 6749 스코프 정의, RFC 9700
클라이언트 자격증명 그랜트로 사용자 데이터 접근 인가한 당사자가 사라져 감사 기록이 서비스 계정으로 수렴한다 RFC 6749 (기밀 클라이언트만 MUST)

확인하지 못한 것

  • 이 글의 근거는 RFC 원문과 OpenID Connect Core 1.0 문서에 적힌 규범적 서술뿐이다. 개별 인가 서버 제품이나 라이브러리가 그 규범을 어떻게 구현했는지는 확인하지 않았다. 특정 구현이 규격을 지키는지 여부에 대해서는 아무 주장도 하지 않는다
  • OAuth 2.1은 2026년 3월 2일자 15판 인터넷 초안이다. 초안은 표준이 아니고 발행 전까지 내용이 바뀔 수 있다. 이 글은 초안이 암시적 그랜트와 비밀번호 그랜트를 규정에서 제외한다는 편집 방향까지만 인용했고, 세부 조항은 인용하지 않았다
  • RFC 9700이 대상 지정 수단으로 언급하는 RFC 8707의 resource 파라미터는 인용 관계로만 다뤘고 원문을 대조하지 않았다
  • 상호 TLS 기반 인증서 결속 토큰의 규격 원문은 열지 않았다. RFC 9700이 송신자 결속 수단으로 상호 TLS와 DPoP 둘을 든다는 사실까지만 확인했다
  • 각 흐름의 실제 채택 비중을 보여 주는 신뢰할 만한 공개 통계는 찾지 못했다. 그래서 「대부분의 서비스가 이렇게 한다」류의 서술은 이 글에 없다

읽을 문서 순서

규격을 처음부터 순서대로 읽으면 시간이 많이 든다. 아래 순서는 어휘를 먼저 잡고, 그다음에 지금의 기준선을 덮어쓰는 방식이다.

  1. RFC 6749의 역할·용어 절과 인가 코드 흐름 절. 여기서 네 역할과 파라미터 이름을 잡는다. 나머지 문서가 전부 이 어휘로 쓰여 있다
  2. RFC 6750. 소지자 토큰이 무엇을 보장하지 않는지를 짧게 확인한다. 8절의 논의가 여기서 출발한다
  3. RFC 7636. PKCE. 짧고, 문제 정의가 명확하다
  4. RFC 9700 (BCP 240). 오늘의 기준선. 6749와 6750, 6819를 갱신한다. 6749를 먼저 읽고 이것을 읽어야 목록에서 무엇이 빠졌는지가 보인다. 순서를 바꾸면 왜 빠졌는지가 안 보인다
  5. 자기 상황에 맞는 것 하나. 브라우저 앱이면 RFC 10017, 네이티브 앱이면 RFC 8252, 입력이 빈약한 기기면 RFC 8628
  6. 로그인이 목적이면 OpenID Connect Core 1.0의 ID 토큰 절과 ID 토큰 검증 절
  7. 토큰 형식과 검증이 문제면 RFC 9068이나 RFC 7662 중 자기 토큰 형식에 해당하는 쪽
  8. 인가 서버를 여럿 붙였으면 RFC 9207, 소지자 토큰을 벗어나려면 RFC 9449, 엔드포인트 디스커버리가 필요하면 RFC 8414

마지막으로 이 글이 주장하는 것을 셋으로 줄인다. 첫째, OAuth는 위임된 인가 규격이고 로그인은 그 위에 얹히는 별도의 층이다. 규격 이름이 이미 그렇게 말하고 있다. 둘째, 검사하는 지점을 어디에 두었는지가 그 통제의 실체다. 스코프도 토큰 검증도, 화면에서 하면 안내이고 자원 서버에서 해야 강제다. 셋째, 오늘의 기준선은 RFC 6749가 아니라 RFC 9700이다. 2012년 문서만 읽고 설계하면 그 사이 13년 동안 목록에서 내려간 것들을 그대로 안고 시작하게 된다.
