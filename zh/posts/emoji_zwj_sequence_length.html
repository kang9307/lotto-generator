一个表情符号被数成 11 个字符 - ZWJ 序列与字符数校验

字符串的长度不止一个。如何在五个数字中确定该数哪一个

2026-07-30 开发/基础设施

引言: 「限 20 字」被一个表情符号击穿

昵称输入框上写着「最多 20 字」。用户敲了十二个字，又加了两个表情符号。屏幕上的计数器显示 14，可一按保存就跳出 「已超过 20 字」。用户数的是十四个字，服务器数的是别的东西。

这类反馈很容易以「无法复现」结案。因为开发者用自己的名字测试时根本不会出问题。而这恰恰就是这个缺陷能存活好几年的原因。

原因只有一个。字符串的长度不止一个。

  • UTF-8 字节 — 存储与传输看到的数字
  • UTF-16 代码单元 — JavaScript .length 返回的数字
  • 码点 — Python len() 返回的数字
  • 字素簇 — 人所数的「一个字」
  • 显示宽度 — 在屏幕上占用的格数

一共五个。而且在绝大多数输入下，这五个数字完全相同。只输入英文和数字时，hello world 用哪把尺子量都是 11。混入韩文后只有字节数会分叉。而表情符号一进来，五个数字就全部散开。

「限 20 字」这句话之所以算不上规格，是因为没写明它指的是这五个中的哪一个。本文会把这五个数字逐一数给你看，并在最后给出按用途决定该数哪一个的表。结论不是「请禁止表情符号」。

执行环境。下面所有输出都是在 Windows 10 Pro (10.0.19045) 上实际跑出来的结果。运行时是 Node.js v22.16.0 (win32/x64, V8 12.4, ICU 77.1, Unicode 16.0) 与 Python 3.13.3 (unicodedata 15.1.0)。Intl.Segmenter 可用，Python 侧的第三方 regex 模块并未安装。没有的东西就写成没有。

码点一律以 U+XXXX 并列标注。本文的题材是表情符号，浏览器或终端画不出字形时就什么都确认不了。所以每个样本都同时附上码点列表。实际验证过程中也不是靠肉眼看形状，而是靠十六进制输出判断的。所有字符串都用 String.fromCodePoint 和 chr() 从码点组装，再与源码字面量比对确认一致。

本文不讨论的内容。韩文在 Unicode 内部会变成两种码点序列的规范化原理，已在 NFC 与 NFD 里讲过。这里第 5 节只展示长度会分叉这个数字。因字符集读错而导致文字损坏的编码诊断在 cp949 与 UTF-8，第 8 节只谈字节长度。用正则范围处理韩文音节的算术在 韩文正则陷阱，第 7 节只看针对表情符号的点号与标志位。

1. 解剖一个表情符号 - 四个数字

拿一个家庭表情符号，用四种方式数了一遍。样本是 U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466，在屏幕上看起来只是 👨‍👩‍👧‍👦 一个。

11、7、25、1。这是把同一个东西数了四遍的结果。没有哪个数字是错的。它们数的是不同的单位。

为什么会这样，按码点拆开看就一目了然。

  code point   utf-16 units   utf-8 bytes   name

  U+1F468      2              4             MAN
  U+200D       1              3             ZERO WIDTH JOINER
  U+1F469      2              4             WOMAN
  U+200D       1              3             ZERO WIDTH JOINER

  • 四个图形字符各占 2 个 UTF-16 代码单元。U+1F468 这类字符位于 U+FFFF 之上，在 UTF-16 里放不进一个位置，要用两个代码单元(代理对)来表示。4 乘 2 得 8
  • 三个粘合剂 U+200D 各占 1 个。这个字符在 U+FFFF 以下，一个位置就装得下。8 加 3 就是 11
  • 在 UTF-8 里图形字符是 4 字节，粘合剂是 3 字节。4 乘 4 再加 3 乘 3，等于 25
  • 码点只是单纯数个数，所以是 7
  • 字素簇是 1。这是按 Unicode 标准附件 29 规定的规则切分出来的结果，与人所数的数字一致

2. ZWJ 就是粘合剂 - 去掉 U+200D，一个变成四个

本文标题里的 ZWJ 就是 U+200D ZERO WIDTH JOINER。它宽度为 0、肉眼不可见，作用是把前后的图形字符粘成一个。是不是真这样，去掉试试就知道。

with    U+200D : cps=7  units=11  bytes=25  graphemes=1
without U+200D : cps=4  units=8   bytes=16  graphemes=4
without U+200D code points : U+1F468 U+1F469 U+1F467 U+1F466
grapheme split             : [U+1F468] [U+1F469] [U+1F467] [U+1F466]

one glue character removed -> 1 grapheme becomes 4.
the utf-8 byte count only dropped from 25 to 16.

去掉三个粘合剂后，字素簇从 1 变成了 4。屏幕上本来是一整块的一家人，散成了男人、女人、女孩、男孩四个。可是字节只从 25 降到 16，只少了一点点。这个对比很关键。从存储容量看几乎没有变化，可「字符数」变成了 4 倍。

把链条一节一节加长，结构就更清楚了。

growing the chain, one link at a time:
  cps units bytes graphemes  code points
  ----------------------------------------------------------------------
  1    2     4      1          U+1F468
  2    3     7      1          U+1F468 U+200D
  3    5     11     1          U+1F468 U+200D U+1F469
  5    8     18     1          U+1F468 U+200D U+1F469 U+200D U+1F467
  7    11    25     1          U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466

note row 2: U+1F468 U+200D is a DANGLING joiner, an invalid sequence,
and it still counts as 1 grapheme.
  • 字素簇始终是 1。在码点从 1 增到 7、字节从 4 增到 25 涨了六倍的过程中，人所数的数字没有变
  • 第二行在实际工作中很重要。U+1F468 U+200D 是什么都没连上的粘合剂悬挂在那里的状态。按 Unicode 规格它不是有效序列，但字素簇个数依然是 1，任何一层都不会报错
  • 这种状态在截断字符串时会真实出现。第 5 节会看到那个位置
  • 附件 29 的规则 GB11 定义了这个行为。规则是图形字符、粘合剂、图形字符之间不切分。所以悬挂的粘合剂也会粘在前一个字上

Unicode 技术标准 51 把这种方式称为 emoji ZWJ sequence，并说明它是为了让实现把该序列当作单个字形处理而设的机制。也就是说这既不是缺陷也不是副作用，而是设计好的行为。要扩充表情符号就得不断造新码点，而用粘合剂就能把已有字符组合出新图案。代价就是长度的爆炸。

3. 肤色与国旗 - 另外几种粘成一个的方式

除了粘合剂，还有三种把多个码点聚成一个的方式。逐一确认过了。

3.1 肤色修饰符是独立的码点

label                  cps  units  bytes  graphemes  code points
------------------------------------------------------------------------------
thumbs up bare         1    2      4      1          U+1F44D
thumbs up tone-2       2    4      8      1          U+1F44D U+1F3FC
thumbs up tone-3       2    4      8      1          U+1F44D U+1F3FD
thumbs up tone-5       2    4      8      1          U+1F44D U+1F3FF
modifier alone         1    2      4      1          U+1F3FD
man + tone-3           2    4      8      1          U+1F468 U+1F3FD

toned couple with a variation selector - the realistic worst case:
  U+1F468 U+1F3FB U+200D U+2764 U+FE0F U+200D U+1F469 U+1F3FF
  cps=8  units=12  bytes=28  graphemes=1
  U+FE0F is VARIATION SELECTOR-16, 3 more bytes that draw nothing.
  • 肤色不是给原字符上色。而是在后面再加一个修饰符码点。所以长度正好翻倍。码点从 1 到 2，字节从 4 到 8
  • 五个等级里加哪一个，长度都一样。从 U+1F3FB 到 U+1F3FF 全都是 4 字节
  • 修饰符单独存在也是一个字素簇。没有基字符、只剩 U+1F3FD 时，会画出类似色卡的东西
  • 最后一个样本接近实际工作中会遇到的最坏情况。两个肤色加两个粘合剂，再加上 U+FE0F，一共 8 个码点、28 字节是一个字
  • U+FE0F 是 VARIATION SELECTOR-16。它只是指示把前一个字符画成图形形态，自己什么都不画却要占 3 字节。这是长度计算中最常被漏掉的值

3.2 国旗是两个区域指示符

label        cps  units  bytes  graphemes  code points
----------------------------------------------------------------------
KR flag      2    4      8      1          U+1F1F0 U+1F1F7
JP flag      2    4      8      1          U+1F1EF U+1F1F5
US flag      2    4      8      1          U+1F1FA U+1F1F8

a single regional indicator U+1F1F0 alone:
  cps=1  units=2  bytes=4  graphemes=1
  it is not half a flag - it is a boxed letter K.

pairing is greedy, left to right:
  2 RI  U+1F1F0 U+1F1F7   graphemes=1   [U+1F1F0 U+1F1F7]
  3 RI  + U+1F1FA         graphemes=2   [U+1F1F0 U+1F1F7] [U+1F1FA]
  4 RI  + U+1F1F8         graphemes=2   [U+1F1F0 U+1F1F7] [U+1F1FA U+1F1F8]

deleting ONE regional indicator re-pairs everything after it.

tag sequence flag (black flag + 5 tag letters + terminator):
  U+1F3F4 U+E0067 U+E0062 U+E0073 U+E0063 U+E0074 U+E007F
  cps=7  units=14  bytes=28  graphemes=1

国旗没有专用码点。把对应字母的两个区域指示符并排放在一起，渲染器就会画成国旗。韩国国旗就是对应 K 的 U+1F1F0 和对应 R 的 U+1F1F7。

  • 只留一个不会变成半面国旗。看到的是方框里的字母 K。作为数据它是完全有效的一个字素簇
  • 配对是从左往右贪婪的。放三个的话前两个成为国旗，第三个单独剩下。这是附件 29 的规则 GB12 和 GB13 定义只在奇数个之前切分的结果
  • 所以删掉中间一个，后面所有国旗都会变成别的国家。在用了多个国旗的输入里，一次退格就会造成这种事
  • 最后一个样本是标签序列。一面黑旗加五个标签字符和终止符，一共 7 个码点、28 字节是一个字。国家下属地区的旗帜用的就是这种方式
  • 技术标准 51 明确规定只有登记在规格数据文件里的国旗序列才有效。也就是说随便拼两个字母，看到的不是国旗而是两个字母

4. 这不只是表情符号的问题 - 韩文 NFD 与组合重音

读到这里很容易想「那禁止表情符号不就行了」。可是就算没有表情符号，长度照样会分叉。确认了一下。

label              .length  cps  bytes  graphemes  code points
--------------------------------------------------------------------------------
hangul NFC         1        1    3      1          U+D55C
hangul NFD         3        3    9      1          U+1112 U+1161 U+11AB

  .length 2 vs 6   bytes 6 vs 18   graphemes 2 vs 2
no emoji involved. the split between units and graphemes is already there.

只看数字就够了。屏幕上同样显示为两个韩文字的东西，一边 .length 是 2，另一边是 6。字节是 6 对 18，差三倍。可是字素簇两边都是 2。

  • 同一个字既可以用一个预组合码点表示，也可以用三个字母表示。哪一种都是有效的 Unicode
  • 为什么会这样、在哪里产生不在本文范围内。已整理在 NFC 与 NFD。这里只需要长度会分叉这个事实
  • 拉丁字母也一样。一个 U+00E9 和两个 U+0065 U+0301 在屏幕上是同一个字
  • 组合字符个数没有限制。叠三个也是 1 个字素簇，后面会看到叠 200 个也还是 1
  • 结论很重要。代码单元与字素簇分叉这件事不是表情符号造成的。表情符号只是把这个差距拉到 25 倍，让它变得肉眼可见而已

附件 29 正面提到了这个问题。一个码点并不总等于用户心目中的「一个字」，文档举的例子也正是字母结合重音的情况。字素簇就是为了填平这个差距而定义的单位。

现在来复现引言里的症状。样本昵称是 DevTeam01 后面接空格、家庭表情符号，再接 2026。就是一个带了一个表情符号的普通昵称。

最后一个代码单元是 0xD83D。这不是字符，而是代理对的前一半，它的搭档被切掉了。这种状态的名字叫孤立代理项。

  • isWellFormed() 返回 false。这个方法只看有没有孤立代理项。它是本文中唯一需要的校验函数
  • 把这个字符串编码成 UTF-8，末尾是 EF BF BD。这是 U+FFFD 替换字符。原来的字节在那一刻就消失了，也不会留下它替代了哪个字符的信息
  • 往返被破坏了。编码后再解码的结果与原文不同。意思是存进去再读出来就成了另一个值
  • substring 的结果也一样。两者都是按代码单元截断
  • 按码点截断(Array.from 后切片)则不会产生孤立代理项。可这次是粘合剂被切断，四口之家变成三口，字素簇减到 14。数据虽然有效，但和用户输入的图案不一样

  code points  : U+0063 U+1F1F0 U+1F1F7 U+0062 U+0061   graphemes=4
  flag intact  : true

same three ways on A + family + B:
  units     : U+0042 U+DC66 U+D83D U+200D U+DC67 U+D83D U+200D U+DC69 U+D83D U+200D U+DC68 U+D83D U+0041
  cps       : U+0042 U+1F466 U+200D U+1F467 U+200D U+1F469 U+200D U+1F468 U+0041
  graphemes : U+0042 U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466 U+0041

三种方式的结果全都不同。

  • 按代码单元反转会把代理对也翻过来。会产生两个孤立代理项，在 UTF-8 里各变成 EF BF BD。数据被破坏了
  • 按码点反转会得到有效的字符串。可是区域指示符的顺序颠倒了，于是变成另一个国家的国旗。既不报错也能通过校验，可内容变了
  • 在家庭表情符号上，按码点反转会把人物顺序倒过来。成了男孩、女孩、女人、男人顺序的另一个表情符号
  • 只有按字素簇反转才能保住原文。国旗保持不变，一家人的顺序也保持不变
  • 实务上的结论很简单。需要反转字符串就按字素簇来。而且说实话，真正需要反转字符串的场合很少

8. 存储与传输 - 四字节字符撞上的墙

就算长度算对了，在存储层还会再被挡一次。我确认了边界到底在哪里。

the boundary is exact:

  U+10000 utf-8 length = 4   first code point above it

边界是 U+FFFF。在它之下 UTF-8 最多 3 字节，在它之上是 4 字节。而且所有表情符号都在 U+FFFF 之上。所以每个字符最多只收 3 字节的字符集一个表情符号都装不下。典型例子就是名字叫 UTF-8 却只存到 3 字节的老数据库字符集，而遗留字符集 cp949 和 shift_jis 干脆抛出了编码异常。

这里就分出了按字符数设定列长与按字节设定列长的差别。用同一个昵称算了一下。

  declared as        needs   verdict
  ----------------------------------------
  20 bytes           39      OVERFLOW
  20 utf-16 units    25      OVERFLOW
  20 code points     21      OVERFLOW
  20 graphemes       15      fits

how many bytes must you reserve for "20 characters"?
  20 code points, worst case utf-8   : 80 bytes
  20 family emoji                    : 500 bytes (cps=140, units=220)
  20 kiss sequences                  : 700 bytes (cps=200, units=300)
  1 grapheme, 200 combining marks    : 401 bytes (cps=201, graphemes=1)
  20 graphemes of stacked marks      : 8020 bytes
  -> "20 graphemes" has NO byte upper bound.

这个计算是本节的核心。

「20 字」的定义需要的 UTF-8 字节有上限吗能当列大小用吗
20 字节20有能用 (定义本身就是字节)
20 个 UTF-16 代码单元最多 80有能用 (按 80 设定)
20 个码点最多 80有能用 (按 80 设定)
20 个字素簇家庭表情符号 500 / 组合字符 8,020没有不能用
  • 用字素簇设定列大小，不存在安全的值。因为一个字素簇里能放的码点个数没有上限。叠 200 个组合字符，字素簇还是 1，字节却是 401
  • 实际确认过 20 个字素簇的字符串能涨到 8,020 字节。这不是 VARCHAR(20) 装得下的值
  • 所以必须把显示上限和存储上限分开。屏幕计数器用字素簇，列大小用字节。想把两者合成一个，正是这个缺陷的根源
  • 校验也要同时加两个条件。只有字素簇不超过 20 且字节不超过上限时才放行
  • 拒绝时要告诉用户是卡在哪个条件上。只弹出「已超过 20 字」，数了 15 个字的用户根本无法理解

  • URL 编码是每字节 3 个字符。一个家庭表情符号会变成 75 个字符

9.1 半个表情符号在各层的反应各不相同

what happens to a half emoji downstream:
  JSON.stringify(lone high surrogate) : "\ud83d"
  JSON.parse of that                  : succeeds, isWellFormed=false
  encodeURIComponent(...)             : THROWS URIError - URI malformed
  Buffer.from(...,"utf8")             : EF BF BD   silently replaced by U+FFFD
  -> JSON accepts it, the URL layer throws, the byte layer corrupts it.
     three layers, three different behaviours, no error at the source.

这就是让诊断变难的结构。在发生的地点不会报任何错。

  • JSON 会放行。序列化和反序列化都成功。只是结果在 isWellFormed() 下是 false
  • URL 层会抛异常。到这里才第一次看到错误。可它离做截断的代码很远，追溯原因很困难
  • 字节层会悄悄弄坏它。换成替换字符后还报告成功。这是最危险的行为
  • 所以必须在截断之后立刻校验。一行 isWellFormed() 就能在发生的地点抓住这三层的问题

11.1 显示宽度不是数据的性质

家庭表情符号的宽度特别有意思。按码点相加是4 个图形字符各 2 格共 8 格，3 个粘合剂各 0 格，合计 8。可是支持该序列的终端会把一个字形画在 2 格里。

  • 同样的数据要么 2 格要么 8 格。取决于渲染器认不认识这个序列
  • 没有任何库能把它确定下来。不知道字体就无法计算。它是五个之中唯一无法仅凭数据决定的值
  • 所以等宽对齐在表情符号面前原理上就会崩。想按含表情符号的字符串来对齐表格宽度，在某些终端上一定会错位
  • 实务上的应对有两种。含表情符号的列放弃等宽对齐，或者显示前把表情符号替换成占位符

  • 只要混进一个非 ASCII 字符，整条消息就变成 UCS-2。那一刻一段的上限就缩到 70 个单元
  • 所以加了一个表情符号后，93 个字的消息变成了两段。用户以为只是多加了一个字，费用却翻倍
  • 一段里放得下的家庭表情符号是 6 个。用户眼里是六个字，一条短信就被塞满了

等宽屏幕排版显示宽度布局由格数决定用实际字体确认，并以无法确定为前提设计
跨语言 API 契约字节唯一在所有语言里得出同一个值的单位两边用同一样本是否得出同一个数
去重、哈希、排序键规范化后的字节同一个字可能是不同的字节是否先做了规范化
搜索索引的词元长度码点大多数索引器按码点工作在索引器文档里确认单位

用这张表时的关键是第三行。实务中的输入校验不是只挑一个单位的问题。显示用和存储用要分开设定，两个都要检查。想把这两者合成一个的尝试，正是引言那个缺陷的来源。

  • 把单位写进规格文档。不要写「昵称最多 20 字」，而要写「昵称最多 20 个字素簇，存储上限 80 字节」
  • 用同一个样本确认前端与后端用的是同一个单位。语言不同，length 的含义就不同
  • 把单位和超出量写进拒绝提示。「已超过 20 个字」对数了 15 个字的用户毫无意义
  • 不要截断，直接拒绝。悄悄截断会损坏数据，用户还察觉不到。不得不截断时就按字素簇截断并校验
  • 先确认存储层收不收四字节字符。长度算得再对，卡在这里也全都白搭

13. 它为什么会悄悄溜过去，以及测试样本

最后整理一下这个缺陷的性质。它为什么能活好几年。

  • 绝大多数输入下五个数字都一样。11 个 ASCII 字符的字节、代码单元、码点、字素簇全是 11。开发者用自己的名字测试不会有任何问题
  • 复现条件很窄。要特定种类的表情符号、特定长度、特定截断位置全对上了才会爆。反馈就以「无法复现」结案
  • 失败是安静的。孤立代理项能通过 JSON，替换字符也会无错存入。日志里什么都不留
  • 能看到的地方与爆炸的地方相距很远。做截断的代码和抛异常的 URL 层是不同的模块
  • 肉眼检查也抓不到。U+200D 残渣和 U+FEFF 在屏幕上什么都不画

所以真正需要的是样本。把下面这些放进测试数据，本文里的所有事故都能在开发阶段被抓住。

  • ZWJ 序列 — U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466 (字素簇 1、代码单元 11、字节 25)
  • 国旗 — U+1F1F0 U+1F1F7 以及连续放三个国旗的样本 (确认配对重排)
  • 肤色修饰符 — U+1F44D U+1F3FD
  • 含 U+FE0F 的序列 — 确认宽度为 0 的 3 字节没有在计算中被漏掉
  • 韩文 NFD — U+1112 U+1161 U+11AB (字素簇 1、码点 3)
  • 组合重音 — U+0065 U+0301 以及叠了多个标记的样本
  • 标签序列 — 用来确认近似正则会出错的样本
  • 含孤立代理项的字符串 — 确认校验函数是否真的能抓到
  • 边界长度样本 — 让截断位置正好落在表情符号中间的、上限之前、上限、上限之后的样本
  • 只含 ASCII 的样本 — 作为对照组。这里所有单位都应该相同

最后一项意外地重要。只有 ASCII 样本能通过的测试，等于什么都没验证。因为它只在五个数字相同的区间里确认过。

# 表情符号字符数 — 五种长度对照表与安全的计数、截断

> 来源: braindetox.kr — 一个表情符号被数成 11 个字符
> 依据: Windows 10 / Node.js v22.16.0 (ICU 77.1, Unicode 16.0) / Python 3.13.3 实跑验证
> 把这个文件整份贴给 AI，然后写「按这个标准检查我们的输入校验」就能用。
> ⚠ 先说结论: 「限 20 字」不是一句话，而是**必须写明单位**才能算规格。

## 0. 30 秒速览

字符串的长度**不止一个。**数同一个表情符号(👨‍👩‍👧‍👦)，数字会这样分叉。

| 单位 | 值 | 在哪里看到这个数字 |
|---|---|---|
| UTF-8 字节 | 25 | DB 存储、网络、Go 与 Rust 的 len |
| UTF-16 代码单元 | 11 | JavaScript `.length`、Java、C#、SMS UCS-2 |
| 码点 | 7 | Python `len()`、Swift `unicodeScalars` |
| 字素簇 | 1 | 人所数的「字」、光标移动、退格 |
| 终端显示宽度 | 2 (渲染器支持时) | 等宽对齐、表格布局 |

绝大多数输入下这五个数字是相同的。**只在表情符号进来的那一刻才分叉。**所以它会一直安静地溜过去，某天突然爆掉。

## 1. 实测值 (亲手执行)

| 字符串 | 字节 | UTF-16 | 码点 | 字素簇 |
|---|---|---|---|---|
| `hello world` | 11 | 11 | 11 | 11 |
| 漢字 (U+6F22 U+5B57) | 6 | 2 | 2 | 2 |
| é NFC (U+00E9) | 2 | 1 | 1 | 1 |
| é NFD (U+0065 U+0301) | 3 | 2 | 2 | 1 |
| 😀 (U+1F600) | 4 | 2 | 1 | 1 |
| 🇰🇷 (U+1F1F0 U+1F1F7) | 8 | 4 | 2 | 1 |
| 👍🏽 (U+1F44D U+1F3FD) | 8 | 4 | 2 | 1 |
| 👨‍👩‍👧‍👦 (ZWJ 四口之家) | 25 | 11 | 7 | 1 |
| `DevTeam01 👨‍👩‍👧‍👦2026` | 39 | 25 | 21 | 15 |

最后一行是关键。**把这个昵称放进「不超过 20 字」的规则里，结果会随着按哪个单位数而分叉。**

- 按字节数是 39 → 拒绝
- 按 UTF-16 数是 25 → 拒绝
- 按码点数是 21 → 拒绝
- 按字素簇数是 15 → 通过

## 2. 表情符号变长的四种方式

| 方式 | 结构 | 例 | 码点 |
|---|---|---|---|
| ZWJ 序列 | 图形字符之间加 U+200D | 👨‍👩‍👧‍👦 | 7 |
| 修饰符序列 | 基字符 + 肤色修饰符 | 👍🏽 | 2 |
| 国旗序列 | 2 个区域指示符 | 🇰🇷 | 2 |
| 标签序列 | 黑旗 + 标签字符 + 终止符 | 苏格兰旗 | 7 |

- **U+200D(ZWJ)就是粘合剂。**在四口之家里去掉三个 U+200D，字素簇会从 1 涨到 **4**。字节只从 25 降到 16，只少一点点
- **U+FE0F(VS16)是宽度 0 的 3 字节**。什么都不画却把长度撑长
- **国旗配对是从左往右贪婪的**。删掉一个区域指示符，它后面的全部会重新配对
- 肤色、国旗、标签也全都是 1 个字素簇

## 3. 按用途该数的单位

**这张表是本文档的核心。**「数什么」由需求决定。

| 用途 | 该数的单位 | 理由 | 校验方法 |
|---|---|---|---|
| 给用户看的「还剩 n 字」 | **字素簇** | 与人所数的数字一致 | 确认 1 个表情符号是否被数成 1 |
| 决定 DB 列大小 | **字节** | 存储上限就是字节 | 按最坏情况的字节数计算 |
| 输入表单硬上限 | **字节与字素簇两者** | 显示用与存储用不同 | 两个条件都要加上 |
| SMS 计费 | **UTF-16 代码单元** | UCS-2 分段以单元为单位 | 70 单元(拼接时 67)的边界 |
| 等宽屏幕排版 | **显示宽度** | 格数决定布局 | 用实际字体肉眼确认 |
| 跨语言 API 契约 | **字节** | 唯一在所有语言里都相同 | 两边是否得出同一个数 |
| 日志、哈希、去重检查 | **规范化后的字节** | NFC 与 NFD 是不同的字节 | 先做规范化 |

## 4. 可直接用的代码 (JavaScript)

`Intl.Segmenter` 在 Node 16 以上和现代浏览器里可用。验证环境(Node v22.16.0, ICU 77.1)里确认了正常工作。

```js
const seg = new Intl.Segmenter('ko', { granularity: 'grapheme' });

// 计数 — 把一个表情符号数成 1
function countGraphemes(s) {
  return [...seg.segment(s)].length;
}

// 截断 — 绝不把表情符号劈成两半
function sliceGraphemes(s, n) {
  return [...seg.segment(s)].slice(0, n).map(function (x) { return x.segment; }).join('');
}

// 反转 — 国旗不会变成别的国家
function reverseGraphemes(s) {
  return [...seg.segment(s)].map(function (x) { return x.segment; }).reverse().join('');
}

// 按字节截断 — 守住列上限同时保住表情符号
function sliceByBytes(s, maxBytes) {
  const enc = new TextEncoder();
  let outStr = '';
  let used = 0;
  for (const part of seg.segment(s)) {
    const n = enc.encode(part.segment).length;
    if (used + n > maxBytes) break;
    outStr += part.segment;
    used += n;
  }
  return outStr;
}

// 校验 — 是否混入了半个代理项
function isIntact(s) {
  if (typeof s.isWellFormed === 'function') return s.isWellFormed();
  const paired = s.replace(/[\uD800-\uDBFF][\uDC00-\uDFFF]/g, '');
  return !/[\uD800-\uDFFF]/.test(paired);
}
```

**已确认的行为**

- 用 `countGraphemes` 数 👨‍👩‍👧‍👦 得到 **1**
- 把 `DevTeam01 👨‍👩‍👧‍👦2026` 截到 12 个字素簇，表情符号完好，`isWellFormed()` 为 true
- 同一个字符串用 `.slice(0, 20)` 截断，`isWellFormed()` 为 **false**，编码成 UTF-8 后末尾变成 `EF BF BD`(U+FFFD)

## 5. 没有 Intl.Segmenter 的环境

可以用正则做近似。**要知道它并不完备再用。**

```js
const RX = new RegExp(
  '(?:\\p{RI}\\p{RI})' +
  '|(?:\\p{Extended_Pictographic}(?:\\p{Emoji_Modifier}|\\uFE0F)?' +
  '(?:\\u200D\\p{Extended_Pictographic}(?:\\p{Emoji_Modifier}|\\uFE0F)?)*)' +
  '|(?:\\P{M}\\p{M}*)|.', 'gu');

function approxCount(s) { return (s.match(RX) || []).length; }
```

实测准确度

| 对象 | 近似值 | 正确答案 |
|---|---|---|
| 👨‍👩‍👧‍👦 | 1 | 1 |
| 🇰🇷 | 1 | 1 |
| 👍🏽 | 1 | 1 |
| `DevTeam01 👨‍👩‍👧‍👦2026` | 15 | 15 |
| hangul NFD (U+1112 U+1161 U+11AB) | 3 | 1 |
| 标签序列旗帜 | 7 | 1 |

表情符号都数对了，**但在 hangul NFD 和标签序列上会出错。**UAX #29 有 16 条规则，而这段正则只有 4 条。近似值不是替代品。

## 6. Python 这一侧

- `len()` 数的是**码点**。👨‍👩‍👧‍👦 是 **7**，与 JavaScript 的 11 不同
- 标准库里**没有字素簇 API。**验证环境确认: `hasattr(str, 'graphemes')` 为 False，标准 `re` 拒绝 `\X`(`PatternError: bad escape \X`)
- 需要第三方 `regex` 模块的 `\X`。验证环境里**并未安装**
- 切片不会造出孤立代理项，但**会把 ZWJ 链条直接切断。**`NICK[:16]` 的末尾会变成 U+200D，成为「什么都没连上的粘合剂」

```python
# 需要字素簇就需要第三方模块
import regex
def count_graphemes(s):
    return len(regex.findall(r'\X', s))

# 守住字节上限的截断 (只用标准库)
def slice_by_bytes(s, max_bytes):
    b = s.encode('utf-8')[:max_bytes]
    return b.decode('utf-8', 'ignore')   # 丢掉在边界上被切断的碎片
```

`decode(..., 'ignore')` 会悄悄丢掉被切断的碎片。需要日志就用 `strict` 抓住异常自己处理。

## 7. 存储与传输层的计算

- 表情符号全部在 **U+FFFF 之上**。U+FFFF 是 UTF-8 3 字节，U+10000 是 **4 字节**
- 每个字符最多只收 3 字节的字符集**一个表情符号都装不下。**验证中 cp949 和 shift_jis 都拒绝了 😀(`UnicodeEncodeError`)
- 把「20 字」折算成字节时**必须按最坏情况**来算

| 「20 字」的含义 | 需要的 UTF-8 字节 |
|---|---|
| 20 个码点 | 最多 80 |
| 20 个字素簇 (家庭表情符号) | 500 |
| 20 个字素簇 (每个叠 200 个组合字符) | 8,020 |
| 20 个字素簇 (一般情况) | **没有上限** |

**不要用字素簇设定列大小。**一个字素簇里能放的码点个数没有上限。

## 8. JSON 与 URL 的膨胀率

| 转换 | 结果 | 倍率 |
|---|---|---|
| 👨‍👩‍👧‍👦 UTF-8 | 25 字节 | 1.0x |
| JSON `{"nick":"..."}` UTF-8 | 36 字节 | — |
| JSON ASCII 转义 | 77 字节 | 2.14x |
| `encodeURIComponent` | 75 个 ASCII 字符 | 3.0x (每字节 3 个) |
| Base64 | 36 个字符 | 1.44x |

- JSON 的 `\u` 转义基于 UTF-16，所以**一个 U+1F468 会变成两个转义**(`\uD83D` 与 `\uDC68`)
- URL 查询长度预算为 2048 时，20 个字素簇的家庭字符串只放得下**一个**
- 孤立代理项在各层的反应各不相同: JSON 会**放行**，`encodeURIComponent` 会**抛 URIError**，UTF-8 编码会**悄悄换成 U+FFFD**。而在发生的地点什么错都不报

## 9. SMS 计费 (另一套规则)

- 只有 ASCII 时是 GSM-7，一段 **160 个字符**
- **只要混进一个**非 GSM 字符，整条就变成 UCS-2，一段 **70 个单元**(拼接时 67)
- 实测: 93 个字的 ASCII 消息是 GSM-7 一段。**加一个表情符号就转成 UCS-2 变成两段**
- 一段(70 单元)里能放的个数: 普通字符 70 个 / 😀 35 个 / 🇰🇷 17 个 / 👨‍👩‍👧‍👦 **6 个**

用户以为只是多加了「一个字」，费用却翻倍。

## 10. 想用正则拦截表情符号时

| 模式 | 👨‍👩‍👧‍👦 匹配次数 |
|---|---|
| `/./g` | 11 |
| `/./gu` | 7 |
| `/./gv` | 7 |
| `\p{Emoji}` | 4 |
| `\p{Emoji_Presentation}` | 4 |
| `\p{Extended_Pictographic}` | 4 |
| `\p{RGI_Emoji}` (v 标志) | **1** |

- 没有 `u` 标志时 `.` 数的是**代码单元**，会匹配 11 次
- 加上 `u` 标志变成按码点是 7 次。**依然不是 1**
- 要数成 1 就需要 **`v` 标志与 `\p{RGI_Emoji}`**。验证环境里两者都支持
- 用 `\p{Extended_Pictographic}` 删除会**留下三个 U+200D。**是肉眼看不见的残渣
- `\p{Emoji}` **连数字和 `#`、`*` 都会匹配。**用它拦截表情符号，订单号会被拒绝

## 11. 检查清单

- [ ] 「限 n 字」的规格文档里**写明了单位** (字节 / 代码单元 / 码点 / 字素簇)
- [ ] 屏幕计数器与服务器校验用的是**同一个单位**
- [ ] 用同一个字符串**确认过**前端(JavaScript)与后端(Python、Java、Go)的长度计算**是否一致**
- [ ] DB 列按**字节最坏情况**计算过 (没有按字素簇来定)
- [ ] 存储层是**能接收四字节字符的字符集**
- [ ] 截断时**不直接使用** `slice`、`substring` 或字节切片
- [ ] 用 `isWellFormed()` **校验**截断结果
- [ ] 反转与截断的测试里放了**ZWJ 序列、国旗、肤色、hangul NFD 样本**
- [ ] 表情符号过滤器**不会留下 U+200D 残渣**
- [ ] 拦截表情符号的正则**不会误判数字和 `#`、`*`**
- [ ] 短信发送路径上**计算了 UCS-2 转换与段数**
- [ ] 去重检查与哈希之前**先做规范化**
- [ ] 校验失败提示会告诉用户**按哪个单位超出了多少**

## 12. 不要做的事

- ❌ **以「请禁止表情符号」草草结束** — 不确定要数的单位，规则就会一直崩
- ❌ 把 `.length` 叫成「字符数」 — 它是 UTF-16 代码单元
- ❌ 用字素簇**设定 DB 列大小** — 它没有上限
- ❌ 前端按字素簇、服务器按字节数，却**期待得到同一个数字**
- ❌ 用 `.slice()` 截断后**不校验就存储** — 孤立代理项会流出去
- ❌ 用数组反转来做字符串反转 — 国旗会变成**别的国家**
- ❌ 用 `\p{Emoji}` 拦截表情符号 — 它会把数字挡掉
- ❌ 把正则近似值**当成完整的字素簇切分** — 在 hangul NFD 与标签序列上会出错
- ❌ 测试样本里**只放 ASCII** — 五个数字全都相同，什么都抓不到
