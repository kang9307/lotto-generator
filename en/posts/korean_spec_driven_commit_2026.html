Committing Korean Specs Instead of Code

How spec-driven development redefines the "source" - what changes when specs become the source of truth and code becomes the output

Jul 18, 2026 Dev & Infra

Intro: The Idea of Committing a Spec Instead of Code

A post that recently surfaced on GeekNews caught my attention. The author describes a PWA app they built, and how they compressed 152 lines of code into a 28-line spec and committed that to version control instead. On first hearing it sounds odd - isn't version control supposed to be for source code? But in an era where AI can write code almost instantly, asking what actually deserves to be preserved changes the answer.

I am not writing this to promote one experiment. I want to trace the larger current this experiment points to - spec-driven development, and beneath it, the shift toward treating the spec as the source and code as its output. That current has already worked its way into mainstream coding-agent tooling through GitHub Spec Kit and AWS Kiro, and it connects to two pieces I covered yesterday: Understanding Is the New Bottleneck and Specify. All three, in different ways, are asking the same question: in a world where AI makes code nearly free, what is actually worth preserving?

1. What's the Story - Running an App and a Server From a Few Pages of Spec

1.1 The Shape of the Experiment

The case shared on GeekNews centers on 'Rimlog', a reading and study-log PWA. The author describes a custom tool that converts a Korean-language spec into code. The server side is likewise a single Node file generated from one page of spec, with zero external dependencies, designed to plug into multiple AI backends - NVIDIA, Claude CLI, OpenAI, and Google among them.

1.2 How Consistency Is Enforced

The most interesting part is how the spec and the code are kept in sync. The author describes embedding a hash of the spec inside the generated code, and blocking the commit outright if the spec changes without the code being regenerated to match. That's a mechanical filter against a spec and code falling out of alignment. It's not documentation for documentation's sake - it's a declaration that the spec is a tightly coupled contract with the code.

2. The Shift - Code as Output, Spec as the Source of Truth

2.1 Where the Single Source of Truth Moves

For most of software history, the "source of truth" has been code. Docs, design notes, and comments were secondary material that described the code, and when code and docs disagreed, the docs were usually assumed to be wrong. Spec-driven development inverts that hierarchy. A versioned, structured spec becomes the source of truth, and code becomes a secondary artifact that humans and AI agents generate or verify against it.

2.2 Where Review Moves

I think the most direct practical effect of this shift is where review happens. Code review used to ask "is this implementation correct?" Spec review asks "is this intent correct?" Now that AI effectively handles the implementation step, the judgment call that actually matters to a human shifts away from code syntax and toward whether the requirements are consistent and complete. GitHub Spec Kit puts this as code being "the last-mile approach" to development.

2.3 The Reproducibility Payoff

Treating the spec as the source is also a reproducibility fix. If only code is committed, the reasoning behind a design choice tends to live inside a chat window and vanish once it's closed. As I noted in yesterday's Specify piece, the problem of nobody being able to answer "why was this function written this way" has, if anything, gotten worse in the AI-coding era. Commit the spec, and that intent lives in version history - giving you a baseline to return to even if the implementation is regenerated later.

3. Why Now - Connecting to the Spec-Driven Movement

3.1 Already Inside Mainstream Tools

This idea is not confined to one side project. As of 2026, most major AI coding tools - GitHub Spec Kit, AWS Kiro, Claude Code, Cursor, OpenSpec, BMAD, Tessl, Google Antigravity among them - are reported to ship some version of spec-driven development. The common pattern is a specs/-style directory inside the repo: when a bug or feature request comes in, the spec is updated first, and the code is regenerated or modified to match.

3.2 Answering Three Failure Modes

The problems this current is responding to are clear. First is intent drift: an instruction like "add a login feature" is severely underspecified, and the model fills in plausible defaults that often don't match what the team actually wanted. Second is context decay: as a conversation lengthens or a session changes, previously agreed constraints fade. Third is unverifiable output: plausible-looking code has no fixed standard to check it against. Putting a fixed spec in front as a contract gives all three problems a verifiable baseline.

3.3 Where It Meets ADRs and Intent Commits

The idea of "recording the reasoning behind a decision" is not new. Architecture Decision Records (ADRs) have long served as a separate document capturing "why we chose this structure." What's different now is that ADRs used to be secondary documents read only by humans, whereas today they're designed for an AI agent to reference directly before starting work. My own read is that committing a spec is this old practice being summoned back for the AI era, elevated from documentation into an executable contract.

4. What It Means to Commit a Natural-Language (Korean) Spec

4.1 Preserving Intent and Enabling Non-Developer Collaboration

The most direct benefit of a natural-language spec is a lower barrier to entry. A sentence like "this feature should behave this way" can be read and edited by a planner, PM, or designer even if they can't read code. A spec written in one's native language, in particular, can carry intent without the cognitive overhead of translation. In practice, subtle nuance is often lost when thinking gets translated into English; drafting the spec in Korean first can reduce that loss.

4.2 Easier to Swap Implementations

If a spec isn't tied to a specific language or framework, pulling a different implementation from the same spec becomes theoretically easier. That the Rimlog server was designed to plug into multiple AI backends can be read as an extension of this language-neutrality. But this depends entirely on how much implementation detail the spec actually excludes, staying at the level of "what" rather than "how." If specific library function names or API signatures are baked into the spec itself, that neutrality is nominal at best.

5. The Hard Parts - It's Not All Upside

5.1 The Fundamental Ambiguity of Natural Language

Natural language is not a Boolean condition. "It should respond quickly" reads naturally to a person, but without defining how fast or under what conditions, an AI and a human will each interpret it differently. Research points out that natural-language specs cannot directly define executable, concrete conditions, which makes them hard to check directly against execution traces. No matter how carefully a spec is written, ambiguity can be reduced but never fully removed.

5.2 Non-Deterministic Generation

Feeding in the same spec is no guarantee of getting the same code every time. Research finds that LLMs are not fully deterministic even at temperature zero, with some models reportedly producing a different output for the same input roughly one time in four. The idea that code is "just an output" cuts both ways - it also means accepting that the same spec may not yield identical code each time. If reproducibility is secured on the spec side, reproducibility on the code side can actually loosen - a real trade-off.

5.3 The Verification and Testing Problem

According to related research, 43% of AI-generated code changes that passed QA and staging still needed manual debugging once in production. Unit tests catch, to some degree, whether code matches a spec, but they often miss architectural violations or API contract drift that cross service boundaries. Putting the spec first doesn't remove the verification burden - it's more accurate to say it adds a new thing to verify: whether the code actually matches the spec.

5.4 Spec Drift

A more insidious problem is spec drift. Over time, actual behavior can quietly diverge from the spec without a single test breaking or a pipeline failing. Keep patching code without updating the spec, and the spec quickly becomes "the document that used to be true." The Rimlog approach of embedding a spec hash in the code and blocking mismatched commits reads as a direct attempt to mechanically prevent exactly this drift - though not every team has the capacity to build that kind of safeguard themselves.

5.5 Debugging Still Happens in Code

The most practical limit is this: no matter how much the spec is the source of truth, what actually runs in production is code. When a bug hits, someone has to dig through logs, read stack traces, and trace the execution path - work that happens at the code level, not the spec level. The expectation that spec-driven development lets you skip reading code entirely is an overstatement. A spec is powerful for clarifying "what to build," but diagnosing "why did this break right now" still requires being able to read code.

6. Writing Specs in Korean - Real Benefits, Real Limits

6.1 The Benefit of a Native Language

For a project that stays entirely within a Korean team, writing specs in Korean has a clear payoff. Phrasing straight out of a planning meeting can go almost directly into the spec, and non-developer roles can participate in review. The small losses that occur when thinking gets translated into English are also reduced.

6.2 The Limit for International Collaboration and Open Source

On the other hand, for a project meant to be open-sourced or worked on with an overseas team, a Korean-only spec becomes a barrier in itself. It's also worth accounting for the fact that LLM natural-language comprehension is not uniform across languages. With English training data still overwhelmingly larger, it's premature to assume a Korean spec and an equally rigorous English spec would produce identical output quality from the same model. The balanced view is that Korean specs are strong for internal thinking and collaboration, but external publication and cross-language portability call for a separate translation layer.

7. A Practical Guide - What Actually Belongs in a Spec

7.1 Capture Intent, Constraints, and Interfaces

Across the examples I've looked at, the common thread is that a spec should capture "what, why, and within what constraints" rather than implementation detail. Nailing down a specific function name or internal algorithm inside the spec only removes the room for AI to propose a better alternative.

7.2 Pin Down Behavior With Tests

Because a spec alone can't eliminate ambiguity, it's safer to lock in core behavior with tests. Related research points to combining specs with TDD as a combination that actually produces shippable AI-generated code. If the spec expresses intent, tests are the mechanical check that the intent was actually honored.

7.3 Let Spec and Code Evolve Together

Rather than the extreme stance of "never look at the code," it's more realistic to let the spec and the code evolve side by side as living documents. Related research describes this "spec-anchored" approach as the sweet spot for most production systems: update the spec first, regenerate the code, but still have a human skim the generated output and touch it directly when needed.

8. Where This Connects to Yesterday's Two Pieces

This current lines up precisely with yesterday's two pieces. Understanding Is the New Bottleneck argued that in a world where AI makes code cheap, the scarce resource is actually the speed of human comprehension. Spec-driven development can be one structural answer to that problem: verifying intent at the spec level, instead of verifying code line by line, shrinks the surface area that needs to be understood. That said, it only reduces the burden of "understanding to verify" - it doesn't substitute for "understanding to participate," the ability to judge whether a given direction is actually the right one.

It also connects to the workspace-memory concept I covered in the Specify analysis. If Specify records the reasoning behind decisions so an AI agent can reference it directly, committing a spec pulls that same background record into the version control system itself, rather than a separate workspace. Which is better is a tooling question; the substance is the same. What's actually worth preserving in the AI era is not the code itself, but the context of why it was built that way.

Conclusion: Commit Intent, Not Just Code

Committing a spec is an attempt to move software's source of truth from code to intent. As of July 2026, this current has already moved beyond one person's experiment and into mainstream tools like GitHub Spec Kit and AWS Kiro. The upside is real: intent lives in version history, non-developers can participate in review, and swapping implementations gets easier. But the ambiguity of natural language, non-deterministic generation, drift, and the plain fact that debugging still happens in code, all remain.

My conclusion is this: treating spec-driven development as magic that lets you skip reading code is a setup for disappointment. Treating it instead as a tool that lifts the unit of review and reproducibility from code up to intent has real payoff. Before handing an AI agent your next feature, try starting with a short spec - what, why, and under what constraints - written to a file and committed first, instead of just firing off a prompt.
