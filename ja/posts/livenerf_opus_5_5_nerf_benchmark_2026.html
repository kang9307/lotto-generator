劣化の疑いと Livenerf - 何を測ろうとするプロジェクトか

大規模言語モデルが公開されて数週間がたつと、「最近答えが悪くなった」という体感談が繰り返し上がってくる。この体感談は検証が難しい。公開初日と一か月後に同じ条件で同じ質問を投げておいた人は少なく、モデルが変わったのか利用者の期待が変わったのかを分ける基準線もないからだ。Livenerf はこの空白を狙う。リポジトリの最初の文は、プロジェクトを「公開後に最新モデルが静かに悪化するかを検出するための、できる限り決定論的な長期ベンチマーク」と説明している。

対象は2026年9月22日に公開された Claude Opus 5.5 である。Anthropic のモデル概要ドキュメントは、このモデルの API 識別子を claude-opus-5-5、既定の effort を medium、思考(thinking)を常時オンの適応型と記している。基準線の測定は9月24日に始まった。プロジェクトは自らを独立プロジェクトと位置づけ、Anthropic とは提携していないと明記する。したがってここで扱う数値と判定ルールはすべて第三者の設計であり、測定が終わる前は結果ではなく方法が話の本体になる。

この記事の角度は結論を出すことではなく、測定の構造を読むことにある。劣化の疑いが持ち上がるとき議論がすれ違うのは、たいてい同じ言葉で違うものを指しているからだ。モデルの重みが変わったこと、既定設定が変わったこと、提供経路が変わったこと、製品層の設定が変わったことは、いずれも利用者には「品質が変わった」として現れる。ある測定がそのうち何を捉え何を捉えないかを区別しておけば、結果が出たときにその結果が何を語っているのかを読める。

  • 性格。個人の独立プロジェクトで、Anthropic の公式資料ではない。ライセンスもまだ決まっていないと記されている。
  • 対象。Opus 5.5。公式ドキュメントでは API 識別子が claude-opus-5-5、既定の effort が medium である。
  • 目標。公開初日の基準線を取り、その後の変化を統計的に判定すること。
  • この記事の範囲。設計が述べる範囲にとどめ、提供者側の意図や原因を推測しない。

測定方法論を扱った同じサイトの記事にはLLM 評価の死角があり、このモデルの公開内容はClaude Opus 5.5 公開の分析で扱った。この記事は二つの内容を繰り返さず、劣化測定という狭い主題に集中する。

設計を一覧で - 問題プール2,336、有効パネル78、30日

リポジトリが示した設計を一つの表にまとめると次のようになる。この表で注目したいのは、問題数の二つの数字だ。2,336は候補プールで、78は毎日測る有効パネルである。両者の関係は次の節で解き、ここでは設計の骨格を見る。

項目リポジトリが示す内容
目的公開後に最新モデルが静かに悪化するかを検出する、長期的でできる限り決定論的なベンチマーク
対象モデル・基準線の開始Claude Opus 5.5(2026-09-22 公開)・2026-09-24
問題の出典GPQA Diamond、MMLU-Pro、競技数学、AIME 2025-26
候補プール → 有効パネル2,336問を各4回測定して選別 → 正答率がおよそ30〜70%の78問
測定の頻度と期間1日1回、30日。1〜10日目は基準線、その後に10日の窓が二つ
第一の指標完全一致(exact-match)の正解率。採点に LLM の審判を使わない
第二の指標(優先順)サンプルあたりの出力トークン数、遅延、拒否率
統計手法問題ごとの対応比較とクラスター標準誤差。Anthropic の評価に誤差バーを付ける枠組みに従う

出力の長さ、正解率、拒否率がどれも記録の対象であることは事実だが、重みが違う点は見落としやすい。リポジトリは完全一致の正解率を第一の指標に置き、出力トークン、遅延、拒否率を第二に置く。出力トークン数は、正解率が動く前に劣化の兆候を見せることが多いという理由で、第二の指標の先頭に置かれている。

  • プールとパネルの区別。2,336は選別前の候補数で、78は毎日測る問題数である。二つの数字は同じ集合の大きさではない。
  • 期間の構造。30日のうち最初の10日が基準線で、その後の10日の窓二つを基準線と比べる。
  • 採点方式。完全一致で採点し、審判モデルは使わない。審判も一緒に変わりうるからという理由が記されている。
  • 記録の保存。生の結果は Inspect のネイティブ評価ログとして追記のみの形で積まれ、プロンプト、応答、使用量、遅延、CLI のバージョン、ハーネスのハッシュが併せて残る。

なぜ不安定な問題だけを選ぶのか - 30〜70%の帯の論理

有効パネルに入る条件は、正答率が中間の帯にあることだ。リポジトリの説明は単純である。モデルが常に正解する問題は性能の低下を示せず、そうした問題を回すのはトークンを使うだけだ。リポジトリは、Opus 5.5 が最初の試行でおよそ93%を正解すると記している。そのようなモデルにとって、大半の問題は低下の信号を出せない問題である。そこで各問題を4回ずつ解かせ、正答率がおよそ30〜70%の問題だけを残した結果が78問だ。

この選別には統計の古い落とし穴がついて回る。4回測定して中間の帯に入った問題は、たまたま低く出た問題を多く含みやすい。リポジトリはこの現象を数値で書いている。選ばれた問題の最初の正答率は54.7%で、新たに測った正答率は62.0%だった。選別のときに低く出た運が、次の測定で回復したのである。設計はこの差を検出力の計算に反映し、新たに測った値を基準にすると述べる。また問題ごとに情報量が違うと見て、正答率が p の問題はサンプルあたり p(1-p) の情報を与えるという形で重みづけする。

  • 中間の帯の理由。常に正解する、または常に不正解の問題は変化に反応しない。反応するのは、ときに正解しときに不正解になる問題である。
  • 選別の偏りの補正。最初の54.7%と新たな測定の62.0%の差を検出力の計算に反映したと述べる。
  • 情報量の重みづけ。正答率 p の問題はサンプルあたり p(1-p) の情報を与えるとして重みづけする。
  • 代表性の限界。パネルは変化に敏感になるよう選んだ標本なので、モデルの全体的な正解率を代表しない(設計からの推論)。リポジトリは最初の試行の正解率がおよそ93%だと記す。

固定プロンプトと隔離環境 - 決定論をどこまで守るか

リポジトリは決定論の限界を先に認める。新しいモデルではサンプリングのパラメータを固定できないため、同じ入力から同じ出力を得ることは不可能だ。そこで設計は、固定できるそれ以外をすべて固定する方を選ぶ。リポジトリの表現では、プロンプトを凍結し、CLI のバージョンを固定し、採点は完全一致で行い、生のログを永久に保存する。出力の同一性ではなく、数千のサンプルにわたる統計的なずれを測る設計である。

隔離の水準はかなり厳格だ。測定に使う環境は、短く固定されたシステムプロンプト、ツールなし、MCP サーバーなし、設定・フックなし、CLAUDE.md とメモリなし、1回のターン、固定された空の作業ディレクトリと記述される。この条件は、測定結果がモデル以外の要因で揺れるのを防ぐ代わりに、実際の利用環境の多くを測定の外に置く。利用で体感する品質はツールとメモリと長い会話を経た結果なので、この隔離は、この測定が何を測らないかも同時に決める。

  • 固定したもの。プロンプト、CLI のバージョン、採点方式、作業ディレクトリ。生のログは追記するだけである。
  • 固定できなかったもの。サンプリングのパラメータ。だから同一の出力ではなく統計的なずれを見る。
  • 経由の経路。対象は、サブスクリプションで Claude Code を通じて提供される Opus 5.5 であり、生の API のモデルではない。
  • 事前登録。方法論はデータ収集の前に git にコミットして公開のタイムスタンプを残す。事後に基準を直せなくする仕掛けである。

判定ルール - 99%区間、3点、対照群

劣化が確認されたと言うには三つの条件が同時に必要だと、リポジトリは釘を刺す。第一に、基準線との差についての99%区間が、連続する二つの10日の窓の両方で0を除外すること。第二に、効果の大きさが最低3点であること。第三に、対照群で同じ方向の動きがないこと。対照群は Opus 5 である。一度跳ねた値や一時的な提供の揺らぎが判定として固まらないよう、敷居を三重に置いた構造だ。

設計自身が示す検出力もあわせて読む必要がある。選んだ標本サイズで、10日の窓ごとにおよそ7.5点の正解率の変化を検出できると予測する。それより小さいずれは窓の中では捉えられない。測定器が動くことを示すため、既知の変化で試した結果も記されている。effort を medium に下げると出力トークンが26%減り正解率が4.2点(±3.9)下がり、low に下げるとトークンが62%減り正解率が8.3点(±4.5)下がった。

  • 三重の敷居。二つの窓の連続で99%区間が0を除外し、効果が3点以上で、対照群が一緒に動かないこと。
  • 検出力。10日の窓あたりおよそ7.5点の変化を検出できるよう設計したと予測する。それより小さいずれは捉えられない。
  • 既知の変化での試験。effort の medium はトークン26%減で4.2点低下、low は62%減で8.3点低下だった。
  • 両方向の検定。リポジトリはどちらの方向の変化も検定し、原因のしくみを前提にしないと述べる。

体感の劣化の経路ごとに測定は捉えるか

下の表は、体感の劣化につながりうる経路を並べ、この測定設計がそれぞれを捉えるかを整理したものである。経路の一覧は、リポジトリとそれを扱った報道にある説明のうち、設計と突き合わせられるものだけを選んだ。最後の列はリポジトリの設計の文から読み取った理由で、一部は設計からの推論なのでその箇所で明示する。

体感の劣化の経路測定で捉えられるか理由
モデル自体の変化(重み・提供時の精度など)一部正解率と出力トークンの変化として現れうるが、窓あたり約7.5点より小さいずれは検出の外
既定の effort 設定の違い—effort を変えるとトークンと正解率が動くことは試験で示されたが、ハーネスが使う effort 設定は出典になく、この経路が反映されるかは分からない
安全分類器の介入(別モデルの応答・拒否)捉えられない介入されたサンプルは却下して集計し、関わった問題は分析から除外する
長いセッションに溜まった文脈捉えられない測定は1回のターンで、メモリも作業ディレクトリの状態もない(設計からの推論)
製品層の設定・ツールの変更捉えられないツール・MCP・設定・フック・CLAUDE.md なしの固定環境で測定
インフラの不具合・負荷一部遅延とトークンは記録するが原因は区別しない。リポジトリは原因のしくみを前提にしないと明記
利用者の期待の上昇捉えられない固定した問題は、利用者の期待と無関係に同じ条件で繰り返される(設計からの推論)

表で目を引くのは、捉えられないの欄が多いことだ。これは測定が粗いからではなく、測定の対象が狭く定義されているからである。この設計が答えようとする問いは、固定した条件で同じモデルが同じ問題を解く能力が変わったかどうかだ。利用者が体感する品質は、その上に製品設定、長いセッション、提供状態が重なった結果なので、二つの問いは重なるが同じではない。

  • 捉えられる側。同じ条件の同じ問題での正解率と出力トークンのずれ。窓あたり約7.5点以上の変化。
  • 一部だけ捉えられる側。提供の揺らぎのように、遅延とトークンに痕跡が残るもの。ただし原因までは分けられない。
  • 捉えられない側。安全分類器の介入、長いセッション、製品層の設定、期待の変化。設計が意図的に除外している。
  • 読み方。測定で変化がないという結果は、体感の劣化がないという証明ではなく、体感の劣化をモデルの外に探す根拠になる。

測定が証明できないこと

リポジトリは自らの限界を具体的な数値で記している。最も目を引くのはモデルの入れ替えを区別する能力だ。対照群の Opus 5 を Opus 5.5 の位置に入れてみたところ、99%の水準では区別できなかったという。差は-3.8点で誤差は±6.3点、トークンは23%少なかった。これは、同じ世代の別のモデルに静かに入れ替わる場合を、この測定器が安定して捉えられないという意味である。自らの限界をこのように先に公開することが、このプロジェクトの信頼度を測る手がかりになる。

問題そのものの質についても記録がある。監査で、正解が誤って見える問題が8問、曖昧な問題が30問見つかったが、今のところ何も除去していないという。事前登録された感度分析で、これらを除いて再実行する予定だ。公開直後の週を基準線にすることにも前提がある。リポジトリは、2025年の品質問題の事例は意図的な性能低下ではなくインフラの不具合だったと記し、そのため、どの方向の変化も原因のしくみを前提にせず検定すると説明する。

  • 同系統の入れ替え。Opus 5 への入れ替えは、99%の水準で Opus 5.5 と区別できなかった(-3.8±6.3点、トークン-23%)。
  • 問題の質。正解が疑わしい問題が8問、曖昧な問題が30問あり、除去せず感度分析で扱う。
  • 経由の経路の限界。測定はサブスクリプション版 Claude Code を通じた Opus 5.5 であり、生の API の動作とは異なりうる。
  • 原因のしくみの中立。変化の原因がモデルかインフラかは、この測定だけでは分けられない。両方向の変化を、しくみの仮定なしで見る。
  • 範囲外。完全一致の正解率を超える推論の質や事実性、正解率の変化を伴わない拒否の挙動の変化は、この設計の第一の指標の外にある。

現在の状態と結果の読み方

リポジトリが示す進捗は、9月29日時点で30日のうち6日分が集まり、基準線の10日のうち6日が終わったというものだ。設計上、統計的な推論は基準線が終わった11日目から始まり、連続する二つの窓を要求する判定は、二つ目の10日の窓が終わる30日目以降に可能になる。この設計を伝えた報道は、結果が10月下旬に出ると伝える。つまり本稿の時点では、劣化があるという結果も、ないという結果も出ていない。この記事もそのどちらも主張しない。

同じ主題を扱った報道には、別の追跡ツールが Opus 5.5 を公開日の能力の99.2%の水準とみているという言及がある。このツールの設計と測定条件はこの記事の出典では確認できないので、Livenerf の結果として読んではならない。体感の劣化の別の説明として、既定の effort 設定、安全分類器の経路、長いセッションの文脈、期待の上昇のようなものが報道で挙げられるが、これらは Anthropic の発言ではなく議論の中の仮説である。公式のモデル概要ドキュメントで確認できるのは、Opus 5.5 の既定の effort が medium だという事実だけだ。

  • 今言えること。測定の設計と進捗。結果はない。
  • 結果が出たら見ること。二つ目の窓まで99%区間が0を除外するか、3点以上か、対照群も一緒に動いたか。
  • 変化がないという結果。変化が検出されなくても、窓あたり約7.5点より小さい変化や測定の外の経路は、なお排除されない。
  • 変化があるという結果。変化が検出されても、原因がモデルか提供側かは、この測定だけでは分けられない。
  • 照合資料。モデル名や既定設定などの事実は、公式のモデル概要ドキュメントを基準にする。

確認できなかったこと

  • 測定結果。9月29日時点で基準線の段階であり、判定に当たるデータがまだない。
  • ハーネスが使う effort 設定。既定の medium を使うかを明記した文が見つからず、effort の経路が反映されるかは分からない。
  • 思考(thinking)の表示方法の変更が体感に与える影響。この記事のどの出典にも扱われていない。
  • 遅延と拒否率の具体的な数値と分析方法。リポジトリが第二の指標として記録するとだけ出てくる。
  • 別の追跡ツールが報告した99.2%の設計と測定条件。
  • Opus 5.5 の品質に関する Anthropic 側の見解。出典に直接の引用がない。
