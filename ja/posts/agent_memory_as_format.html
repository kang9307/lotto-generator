記憶を手続きとして組むと閉じ込められる - エージェントメモリをファイル形式にするという提案が触れているもの

パイプラインに縛られた記憶は道具を替えた瞬間に付いてこない。形式にすると何が変わり、何がそのまま残るのか

2026年9月3日 開発・インフラ

エージェントに記憶を持たせる方法を論じるとき、議論はほとんど常に手続きの側へ流れていく。会話から何を抜き出すか、どう要約するか、どこに埋め込むか、どの順で検索して戻すか。その一覧はすべて動詞である。ところがその一覧が一度も正面から問わないことがひとつある。そうして作られた記憶は何の形をしているのか。ファイルなのか、データベースの行なのか、それともどこかのサービスの内部状態なのか。

この記事は道具を比較しない。記憶がなぜ必要かも扱わない。軸はひとつである。記憶を処理手続きとして表現するか、保存形式として表現するか。この選択が何を決め、何は決められないまま残るのかだけを見る。

この記事は2026年9月時点で公開されている仕様文書と公式文書に基づく。扱う形式の提案は自ら草案段階であることを明記しており、特定の製品や企業を勧めたり貶めたりするものではない。

きっかけ - パイプラインではなくファイル形式という一文

2026年9月初め、韓国の開発者コミュニティに紹介された英語圏の記事ひとつが、この議論を正確な位置に置いた。題は「Agent memory as a file format」であり、本文中の節の見出しはもっと露骨だ。記憶は多段パイプラインではなくデータ形式であるべきだ。

記事の冒頭には Frederick Brooks の古い一文が引かれている。フローチャートを見せて表を隠すなら私は当惑し続けるだろう、表を見せてくれればフローチャートはたいてい要らない、自明になるからだ。この引用が記事全体の論旨である。データ構造を決めれば手続きは後から出てくるということ。

ここですぐ断っておくことがある。この提案は確定した標準ではない。仕様文書が自ら草案 0.1 と記しており、日付は2026年8月である。だからこの記事も「こう決まった」ではなく「この方向が何に触れているのか」として読む方が正しい。

原文が実際に述べていること

原文は既存のメモリシステムを三つに分けて批判する。ひとつめは利用者を特定のハーネスに縛りつけるものだ。ふたつめは原文の表現そのままに途方もなく複雑なもの — 何が記憶する価値があるかを決めるためにベクトル拡張とグラフデータベースと自前の LLM まで立てる構成を挙げる。みっつめは理想化された合理主義的な記憶の形を描く系統である。グラフと論理命題で事実を切り出す方式だが、著者はこれが情報を文脈から引き剥がして孤立させると見る。

三つの共通点は一文に要約される。記憶を手続きとして扱っているということ。著者の代案はその反対側だ。記憶は、とりわけモデルにとっては、データとして表現する方がずっとよい。

根拠も明確である。既存の検索拡張パイプラインが複雑なのは、人の書いたレガシー文書をエージェントが読めるようにしようと苦心しているからで、エージェントの記憶はそもそもそういう代物ではない、というのだ。記憶が作られる瞬間、それは散文を書けるエージェントが自ら書いている。だからチャンキングも強化も二重要約も要らない。実際に提案された形式は三つの断片しかない。

  • マークダウンのページ群 — 記憶ひとつがファイルひとつ
  • 任意の YAML frontmatter — 題、uuid、作成・更新時刻、要約
  • 任意の SQLite ベクトルインデックス — 意味検索のため傍らに置くファイルひとつ

この束の正規の保存形はzipである。交換を容易にするための選択で、仕様はローカルファイルでもオブジェクトストレージでも HTTP でも、どこから提供されてもよいように開いてある。ディレクトリを開けばこういう形だ。

my-memories.memoryfield.zip
├── carbon-fibre-woks.md
├── finnish-bureaucracy-tips.md
├── wec-2026-season-notes.md
└── nomic-embed-text-v1.5.sqlite3

原文にない主張をここに付け足さない方がよい。著者はこれが記憶の問題をすべて解くとは言っていない。後で見るように、彼自身が未解決として残した項目がいくつもある。

手続きとして作ると記憶が実装の中に閉じ込められる

パイプラインで作った記憶の本当の問題は性能ではない。所有権である。要約の規則がそのベンダーのプロンプトの中にあり、埋め込みがそのベンダーの選んだモデルで計算され、検索がそのベンダーのインデックスの上でしか回らなくなった瞬間、記憶はその実装の内部状態になる。見た目は自分の記憶だが、実際に持ち出せるのは元の会話ログだけであり、そのログを再び同じ記憶にするには同じパイプラインをもう一度回すしかない。

この閉じ込めは静かだ。道具を替えるまでは何の症状もない。替える日に露見するのだが、よりによってその時には数か月分が積み上がっていて、移す費用が最も大きい時点である。だからこの問題はいつも遅れて見つかる。

原文が挙げる別の角度も実務的だ。機械仕掛けの多いシステムでは、エージェントは目標に届くまでインターフェースの迷路を通らねばならない。インターフェースが大きければスキーマ定義だけで文脈を食い、小さければできることがない。均衡が取れていても、他人の書いた API なので自分の必要を見越していないという問題は残る。著者はここでより多くのモデル、より少ない機械仕掛けという原則を立てる。

項目手続きとして置くとき形式として置くとき
記憶の実体サービスのインデックスの内部状態ディレクトリの中のファイル
道具の乗り換え元のログを回し直して再生成同じファイルを別の道具が開く
変更履歴サービスが提供する分だけバージョン管理がそのまま扱う
監査何が保存されたかを問い合わせる手段が別に要る開いて読む
削除削除要求と実際の削除が別物ファイルを消す
故障の追跡パイプラインのどの段かを突き止めるファイルひとつに絞られる

形式にすると何が変わるのか

最も大きく変わるのは他の道具が同じファイルを読むという点である。形式が文書として書かれていれば、それを読む実装は原著者が作らなくても現れる。これは楽観ではなく観察だ。長く生き延びたファイル形式はすべてそうなった。

次が人の側の利得である。テキストファイルは diff が取れる。diff が取れればレビューができ、レビューができれば何がいつなぜ入ったかが残る。記憶が誤って入ったとき、どのセッションでそれが入ったのかを辿る作業が、サービスに問い合わせる作業からログを一行読む作業に変わる。

  • 読める — 何が保存されたかを確かめるのに別の照会道具が要らない
  • 比べられる — 二つの時点の間に何が増え何が減ったかがそのまま出る
  • 移せる — 圧縮して送れば終わる。再計算が要るのはインデックスだけで、インデックスは元から作り直せる
  • 一部を消せる — ファイル単位の削除がそのまま記憶単位の削除になる
  • 他の道具が割り込める — 綴りの検査器でも漏洩の検査器でも、テキストファイルなら付く

注意すべきは、この一覧がすべて表現をファイルにしたおかげであって、この提案ひとつの手柄ではないという点だ。同じ利得は記憶をテキストファイルに置くどの設計からも出る。だから次の節が重要になる。

すでにその形で固まっている慣行

興味深いのは、この方向が提案される前にすでに現場がその形で固まっていたという点である。二つが目につく。

AGENTS.md は自らをコーディングエージェントを導くための単純で開かれた形式だと紹介する。より正確な表現はその次の一文だ — エージェントのための README、文脈と指示を置く専用の予測可能な場所。必須の項目はなく、ただのマークダウンである。2026年9月時点でそのサイトは6万を超えるオープンソースプロジェクトが使っていると表記しており、管理主体はリナックス財団傘下の Agentic AI Foundation だと明かしている。

CLAUDE.md の方は規則がもっと細かい。公式文書によれば、このファイルは作業ディレクトリとその上のすべてのディレクトリで探して読まれ、見つかったファイル同士は上書きせずに連結される。順序はファイルシステムのルートから作業ディレクトリの方へ下りてくる。下位ディレクトリのファイルは、その中のファイルを実際に読むときにその都度読み込まれる。@パス で他のファイルを引き込むインポートがあり、深さは最大四ホップである。

同じ文書がもうひとつ確認させてくれる。道具が自動的に積む記憶もファイルだ。プロジェクトごとのディレクトリの中に MEMORY.md という索引ひとつと主題別のマークダウンファイル群が置かれ、各ファイルの frontmatter には種類を示す type の項目が付く。文書の表現は明確だ — いつでも編集または削除できる普通のマークダウンである。

だから記憶をファイル形式にしようという提案は、無かったものを作ろうという話ではない。すでにそうしていることを形式として書き留めようという話に近い。セッションの記憶を道具の側でどう扱うかは CTX分析 - Claude Codeのセッション間の記憶をつなぐ永続メモリツール と AIコーディングセッションの揮発的コンテキストをプロジェクトの記憶に残す でそれぞれ扱った。

形式は無料ではない

形式にすればよいと言うのは簡単だ。形式になるために実際に何を決めねばならないかを見ると、そこまで軽くない。草案仕様がその一覧をよく示している。ページひとつの頭はこういう形だ。

---
title: Carbon Fibre Woks
created: '2026-03-01T09:00:00Z'
updated: '2026-08-22T14:30:00Z'
uuid: 6aa615f0-486f-48a7-a210-ba4f5ff18c8b
summary: Thermal properties of carbon fibre cookware
---

ここで時刻の値が引用符で括られているのは趣味ではない。仕様は理由まで書いてある。日付・時刻の項目は必ず引用符付きの文字列でなければならない — そうしないと YAML 1.1 のパーサーがこれを日付オブジェクトに変えてしまうからだ。形式を決めるとは、こういうものをひとつずつ釘打ちしていく作業である。

決めねばならないこと草案が決めた方式残る問題
スキーマtitle・uuid・created・updated は推奨、summary は任意。必須は事実上ない緩いから互換になり、緩いから互いに違うものを期待する
バージョン文書が自ら草案 0.1(2026年8月)と明記0.2 が出たとき 0.1 のファイルをどう読むかはまだ
マージページ単位の最後の書き込み優先。条件付き書き込みはサーバーが対応してもよいが要求してはならない衝突を可視化はできても解消はしてくれない
サイズ上限ページは 8,192 バイトを超えない方がよく、実装は先頭 8,192 バイトだけ扱えばよい超える内容をどう割るかは書く側の仕事
同一性保存されたものと入ってきたものの uuid が違えば 409 で拒否することを推奨同じ事実を二つのファイルに書いた場合は捕まらない

表の右の列がこの節の要点だ。形式を決める作業は問題を移す作業であって、無くす作業ではない。ただし移った先が文書に書かれていて議論できる場所だという点が違う。

二人が同時に直したら - マージ規則が本当の試験台だ

形式の議論で最もよく飛ばされる場所がここである。記憶を二つのセッションが同時に直したらどうなるか。

草案が選んだ答えは正直に単純だ。ページ単位の最後の書き込み優先。ETag に If-Match を掛けるような条件付き書き込みで衝突を可視化するのは、サーバーが対応してもよいが要求してはならないと書かれている。つまり形式は衝突を表示する場所は用意したが解消はしない。

これは欠陥ではなく選択である。ただしその選択の値は知っておかねばならない。人が書く文書なら、最後の書き込み優先は編集者二人が互いに気づくことでたいてい収まる。エージェントが同時に複数走る環境では気づく者がいない。片方が書いたばかりのものが静かに消える。

  • ファイルを細かく割れば衝突は減る。代わりにひとつの事実が複数のファイルに散らばる
  • ファイルを大きく置けば事実はまとまっている。代わりに同じファイルを二方が触る確率が上がる
  • 8,192 バイトという上限は、この天秤ですでに片方を選んだ値である。細かく割る側だ
  • バージョン管理の上に載せれば衝突は目に見えるようになる。代わりにマージの衝突を誰が解くかという問題が新たに生じる
  • uuid でページの同一性を押さえておけばファイル名を変えても同じ記憶として扱われる。代わりに uuid を付けないファイルが混じるとその保証が切れる

何を書くかは形式が解かない

はっきりさせておくことがある。表現形式を決めても何が記憶する価値があるかはそのまま残る。形式は器であり、これは中身の問題だ。

原文の著者もこの質問を受けており、答えはこうだった。無関係な資料はどのみち意味検索に出てこないから問題にならない、場所は取るがエージェントの邪魔はしない、だから気前よく入れよ。添えられた助言ひとつは実用的だ — 記憶は出典を一緒に含むとき、できれば URL の形で含むときに最もよく働く。後で読み返すときに強化され、古びたり怪しかったりする内容を照合できるからだ。

議論に出た反論は正反対の方向だった。メモリ機能をまるごと切って一時フォルダに文書を置き、絶えず整理して消しているという話、間違った一行が混じると以後の結果全体が汚染されるという話、時が経って規模が大きくなると情報の陳腐化と文脈の誤適用のせいで役に立たなくなるという話が並んでいた。場所を取るだけと汚染するの間のこの隔たりは、形式が片付けてくれない。

保存する対象を選ぶ作業がなぜそこまで難しいのかは 記憶を作ろうとして解析エンジンになる理由 で別に扱ったので、ここでは繰り返さない。要旨だけ移せば、何を保存するか選ぶにはそれが何を意味するかを知らねばならず、意味を知るには結局は解析が要るということだ。

読む側の費用 - 選別が再び手続きになる

この話の最も正直な箇所がここである。ファイルが大きくなれば毎回の呼び出しに全部は入れられない。だから何を入れるかを選ぶ段階が必要になり、その段階が選別であり選別は手続きだ。手続きを減らそうと始めた話が手続きを呼び戻す。

この循環は言葉遊びではなく数字で表れる。公開されている上限を並べるとこうなる。

対象掛かっている上限超えると
草案仕様の記憶ページ8,192 バイトを超えない方がよい実装は先頭 8,192 バイトだけ扱えばよい
指示ファイル CLAUDE.md一ファイルあたり 200 行以下を目標に4 MiB を超えるファイルは飛ばす
自動記憶の索引 MEMORY.md先頭 200 行または 25KB のうち先に届く方その後の内容はセッション開始時に読み込まれない
主題別の記憶ファイル開始時には読み込まない必要なときにファイル操作で読む

最後の行がこの節の答えだ。全部は入れない。索引だけを常に入れ、本文は必要なときに読む。そして索引を短く保つ作業そのものが要約であり選別である。草案仕様が検索を道具呼び出し二回 — 検索一回、並列読み一回 — で終えようとしたのも同じ圧力への答えだ。リンクを辿る方式は N 段の深さなら N+1 回の呼び出しが要り、呼び出しごとに数秒が付く。

だから正確な一文はパイプラインが要らないではなく、こちらである。パイプラインは残るが、その産出物がパイプラインの外に残る。手続きが消えるのではなく、手続きの結果が開かれた形式に着地する。この区別を曖昧にすると提案そのものが誇張された主張になる。意味検索を何の上に載せるかも同じ性質の決定で、草案が SQLite ファイルひとつを選んだのはインデックスを元から作り直せるようにするための選択だ。選択肢の全体は ベクトル検索を何の上に載せるか で整理した。

長く生きた形式が共有しているもの

新しい形式を提案するとき参考になるのは、長く生き延びた設定ファイルたちだ。四つを並べれば共通点がはっきりする。

形式どこに置くか階層が重なったら
.gitignore対象パスと同じディレクトリ、そして上位のディレクトリ群上位ファイルの規則を下位ファイルが上書きする。同じ層では最後に一致した規則が勝つ
.editorconfig開いたファイルのディレクトリとすべての上位ディレクトリ上から下へ読み、後で見つけた規則が勝つ。root = true に出会えば探索を止める
package.jsonパッケージのルート公開するときだけ name と version が必須。公開しないなら両方とも任意
CLAUDE.md作業ディレクトリとその上のすべてのディレクトリ上書きせず連結される。ルートから作業ディレクトリの方へ下りてくる順序
  • 置き場所が慣行として固まっている。どこを見ればよいか尋ねずに済む
  • 階層のマージ規則が文書に書かれている。重なったとき誰が勝つかが曖昧なら、その形式は道具ごとに違う挙動をする
  • 必須を最小にする。package.json でさえ公開しないプロジェクトには必須の項目がない
  • 逃げ道がある。.editorconfig の root = true は上位への探索を断つスイッチだ

最後の項目は記憶の形式にそのまま移してみる価値がある。階層マージを導入した形式は例外なく、ここから上は見るなという場所を持っている。記憶にもそういう条項が要るはずだが — 業務リポジトリの記憶と個人の記憶がひとつの木で重なるとき — 草案にはまだそれに当たるものが見当たらない。

マークダウンを器として使うこと

記憶をマークダウンに置く選択は理由が明確だ。モデルがうまく扱い、人が読めて、道具がすでに溢れている。原文の著者の表現を借りれば、モデルは bash にも、マークダウンにも、SQLite にも偶然とても長けている。形式の設計では珍しい種類の利点だ。新しく学ぶ文法がないということ。

短所も知られている。マークダウンには長く確定した単一の文法がない。CommonMark 側の説明がその事情を要約してくれる — 元の正式な説明が文法を曖昧さなく規定できず、曖昧さのない仕様がなかったために実装がかなり分かれた。だから同じ文書がシステムによって違って描画される。

記憶ファイルでこれが問題になる場所は思ったより狭い。強調や表の描画が少し違うのは構わない。問題はfrontmatter のような機械が読む部分だ。草案が日付を引用符で括れと釘を打ったのがまさにその場所である。人が読む部分は寛容でよく、機械が読む部分は寛容であってはならない。

  • 本文は散文のまま置く。構造を強いればエージェントは形を合わせるのに内容を失う
  • 機械が読む項目は狭く、明示的に決める。パーサーの差が値を変えてはならない
  • ファイル名を意味あるものにする。検索の前に一覧を見るだけで振り落とせるものがある

間違って覚えたものを消せるか

形式か手続きかで結果が最も大きく分かれる場所がここだ。記憶はいつか間違う。事実が変わったことを誰も告げなかったから間違うこともあり、そもそも誤って書かれて間違うこともある。そのとき問うべきことはひとつである。それを見つけて消せるか。

ファイルにしておけば答えは短い。開いて読み、消す。公式文書が自動記憶について書いた表現がそれだ — いつでも編集または削除できる普通のマークダウンであり、コマンドひとつで一覧を開ける。監査と修正と削除が同じ動作になる。

手続きの中にあると、その三つが分かれる。何が保存されたかを見る方法が別にあり、直す方法はあったりなかったりし、消したという応答と実際に消えたという事実が同じかを確かめる手段がない。間違った記憶を消せないシステムは時が経つほど悪くなる。これは予測ではなく算数だ。間違った項目は時とともに増え、消せなければ減らない。

付け加えると、モデルが答えを作り出したのかどこかで読んだものを吐き戻したのかを見分ける問題はこれとは性質の違う主題であり、推論に見えるものと思い出したものを見分ける方法 で別に扱った。

記憶ファイルがリポジトリに入るとき

ファイルにしておく利点のひとつがバージョン管理に入ることだった。その一文の裏面がこの節である。コミットされる瞬間に一緒に出ていく。

記憶ファイルには何が入るか。作業中のシステムの名前、内部ホスト、どのパスに何があるか、どの手順で配備するか、そして誤って貼り付けた値。人が書く文書ならコミット前に一度は目を通しもする。エージェントが書いた記憶には目を通す者が決まっていない。

原文の著者もこの方向を指摘していて、表現がかなり強い — 信頼しない相手とコンテキストウィンドウを共有してはならず、記憶を通じてもそれは同じだ。静的な zip 形式を仕様に入れた理由のひとつが、他人から受け取った記憶の束を手動で検討しハッシュで固定できるようにするためだと書いている。そして残る問題も認めた。エージェントが良いプロンプトと悪意あるプロンプトを区別する方法は依然として無い。危険は双方向だ。出ていく側では自分のものが漏れ、入ってくる側では他人が仕込んだ文が入る。

  • 記憶ディレクトリは既定でバージョン管理から除外し、共有するものだけ選んで入れる方が安全だ
  • 公式文書によれば自動記憶は機械ローカルであり、マシン間では共有されない。共有するには人が意図して移すという意味だ
  • 他人から受け取った記憶の束は、開いて読むまで信頼しない。ハッシュの固定は同じものを受け取ったことを保証するだけで、安全であることを保証しない
  • コミット前に資格情報が混じっていないか見る作業には別の習慣が要る。よく漏れる場所は リモートURLにトークンが埋まっている にまとめてある

慣行と標準は違う

最後に、言葉を正確に使う必要がある。この記事で扱ったもののうち標準と呼べるものはない。

  • 草案仕様は自ら草案 0.1 と書いた。バージョン番号が付いていることと標準であることは違う
  • AGENTS.md は自らを開かれた形式と呼び、標準とは呼ばない。財団傘下の組織が管理しているという事実はガバナンスができたという意味であって、標準化が終わったという意味ではない
  • CLAUDE.md はひとつの道具の規約だ。公式文書が明示的に書いているとおり、その道具は AGENTS.md を直接読まず、インポートやシンボリックリンクでつなぐよう案内する

最後の項目が今の地点をよく示している。同じ目的の二つの慣行が互いのファイルを読まず、人がつないでくれることを期待している。ひとつの会社が出したファイルの慣行が広く使われれば事実上の慣行になるが、それと複数の実装が相互運用を約束した状態とは違う。ファイルを決める作業と合意を作る作業は別物であり、難しいのはいつも後者だ。エージェントの振る舞いを仕様として書こうという発想が同じ種類の壁に当たることは 長く走るエージェントを何で採点するのか で扱った。

まとめ

記憶を手続きとして表現すればその手続きを所有する側が記憶を所有する。形式として表現すればファイルを持つ側が記憶を持つ。この議論の骨格はそれであり、残りはその決定に付いてくる値だ。

形式の側が買う値は明確だ。読めて、比べられて、移せて、消せる。払う値も明確である。スキーマを決めねばならず、バージョンを管理せねばならず、マージ規則を決めねばならず、上限を掛けねばならない。草案が選んだ答えはおおむね最小限だけ決めて残りは開いておく側だが、それは採用を容易にし相互運用を難しくする選択だ。その選択を悪いと言う根拠はない。ただしその代償が何かは知って選ぶべきである。

そして形式が解かない二つが残る。何を書くか、そして毎回の呼び出しに何を入れるか。後者は結局は選別であり選別は再び手続きだ。だからこの提案の正確な大きさはこうである。手続きを無くすのではなく、手続きの産出物を手続きの外に残すこと。それだけでも十分に大きな差だが、それ以上に読めば失望することになる。

確認できなかったこと

  • 元の議論スレッドは直接開けなかった。サーバーが要求過多の応答を返したため、議論の内容は韓国のコミュニティページが移した範囲でのみ確認した。個々の発言の原文の文は照合できておらず、特定の人物に帰属する表現はそのため使っていない
  • この形式の実際の採用規模 — この形式を読み書きする実装がいくつあるか — は確認できる資料が見つからなかった。仕様文書自体が草案 0.1 と明記している
  • 形式にする側が手続きにする側より結果がよいという比較測定は確認できなかった。原文もそうした測定を提示していない。この記事が整理したのは利得と費用の一覧であって優劣の証拠ではない
  • AGENTS.md の採用プロジェクト数はそのサイトが自ら表記した数値であり、独立に検証された集計は確認できなかった
  • 異なる道具が同じ記憶ファイルを読み書きした事例が実際にどれだけあるかは確認できなかった。二つの慣行をインポートやシンボリックリンクでつなぐ方法が文書に案内されていることは確認したが、そのつなぎがどれだけ使われているかは別の話だ
