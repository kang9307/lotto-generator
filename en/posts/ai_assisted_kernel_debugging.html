How a Hard Kernel Bug Gets Narrowed Down - Bisection, Minimal Reproduction, Instrumentation and the Role of Tools

Shrinking the candidate set and confirming the cause are two different jobs

Aug 24, 2026 Dev & Infra

Introduction: it reproduces every time, and the log says nothing

You power the machine on and get a black screen. Restart the login manager once and everything is fine, and nothing goes wrong after that. Until the next cold boot. Reproduction is one hundred percent, yet the logs hold no clue. A bug like this is hard not because information is missing but because the thing that failed never wrote anything down.

On 20 August 2026 a commit fixing exactly this kind of bug landed in the Linux kernel. The functional change is one line, turning a round_up() into a round_down(). What makes it worth reading is that the commit message records not only the result but the path to it: 24 patches that added more and more debug information, 18 kernel boots, and an account of what an AI tool did and did not do along the way.

This article is not about how to use that tool. It is about the order in which a hard bug gets narrowed down, and about where inside that order a tool can take a slot and where it cannot. The argument over attitudes toward such tools in kernel development is covered in a separate article; here we stay with method.

1. What happened - the confirmed scope

The commit touches one file, drivers/gpu/drm/xe/xe_vram.c, adding 18 lines and removing 5. Its subject says not to hand out the compression storage as usable VRAM. The chain of the problem is laid out in the commit message itself.

  • In the Intel Xe driver, get_flat_ccs_offset() reads the base address of the region where compression metadata lives from the hardware, scales it by the number of enabled L3 nodes to get a software view, and then rounded that result up to 128KiB. Everything below that offset is handed to the VRAM allocator as usable memory.
  • That is the defect. Rounding up a limit that means usable memory ends here publishes everything between the real base and the rounded value as free memory, and that stretch belongs to the compression hardware.
  • On a Battlemage G21 with 16GiB the raw value 0x3fafff800 rounded to 0x3fb000000, so the last 2KiB of page 0x3fafff000 landed in the allocator pool. In the commit message's words that tail gets overwritten by hardware that needs no page-table entry, no buffer object and no GPU submission to do it, and does it before user space exists.
  • On this machine a Mesa VM's level-3 page table landed on that page on every cold boot. The entry covering the compositor's batch-buffer heap disappeared, the first submission faulted, and the display manager restarted it forever. Restarting it by hand cleared the symptom because the next VM's page tables were allocated somewhere else.
  • The fix rounds down to the page size the allocator works in instead. On this machine that excludes exactly one page.

What settled the case was an observation rather than an argument. Reading the excluded page afterwards showed 0xcccc000000000000 and 0xcc77000000000000 alternating, which the commit message identifies as compression metadata, two bytes per sixteen. That is the evidence that named who had been writing the memory.

There is a more instructive detail still. An assertion meant to catch exactly this situation was already in the code. It compared the offset against GSMBASE - ccs_size for equality, and since that value is 128KiB aligned it agrees with the rounded-up offset precisely when the base is not aligned. It was a check that fell silent in the one case it existed for, and it is compiled out entirely unless CONFIG_DRM_XE_DEBUG is set. The replacement is shaped so that it can fail: compression storage must not run into the GSM region.

The account of the process sits inside the commit message in brackets. Quoted directly:

And this was a debug session from hell, enormously helped by an AI doing much of the grunt-work.
the AI several times stated flat out that this was impossible and unsolvable and that we should just write a report about it.

The same paragraph records that the tool was ready to give up several times but kept adding debug code and analyzing it faithfully when pushed, and that the body of the commit message was written by the tool. The numbers are there too: reaching a one-line fix took 24 patches adding more and more debug information and 18 kernel boots.

That is everything the public commit confirms. It does not say which tool was used, or what each of the 24 patches printed. Rather than filling those blanks, this article looks at why the order of operations is the order it is.

2. Why kernel and driver bugs are hard

Walking into the kernel with an application developer's reflexes, the first thing that breaks is your sense of time. Checking one thing costs something entirely different here.

AxisApplicationKernel and drivers
Distance from symptom to causeUsually the same process and stackSeveral layers between; the symptom does not identify one
Cost of one attemptA few seconds to rerunRebuild, reboot, and reset hardware state
Means of observationBreakpoints, structured logs, profilersConsole output, roughly, in early boot
State isolationKill the process and it resetsThe broken state lives in the whole machine
Third-party actorsEssentially noneHardware and firmware write memory without running code
Side effects of lookingMostly harmlessDebug options change layout and timing, moving the symptom

The last two rows describe this case precisely. What corrupted the memory was not code, so it left its name in no stack trace. And turning on debug options changes allocation order, which can put something else on the offending page. The act of observing moving the thing you are observing is a routine condition in kernel debugging.

  • Absence rather than trace — an overwrite leaves no footprint, only a hole. The missing page-table entry does not announce that it is missing; it shows up much later as a fault somewhere unrelated.
  • Combinatorial explosion — a specific chip, a specific memory size and a specific L3 configuration have to line up for the value to be misaligned. In other combinations the same code is fine.
  • Timing dependence — which allocation happens in which order decides who the victim is, and if the victim is not a page table the symptom looks completely different.
  • Indistinguishable from correct behaviour — memory handed out in error is perfectly valid memory as far as the allocator is concerned. No rule was broken, so no check fires.

Under these conditions the fact that testing a single hypothesis is expensive determines the entire method. Where attempts are cheap, trying things is a viable strategy; where one boot equals one attempt, you have to design the order of your attempts.

3. The classical ways to narrow a bug down

The tools for narrowing are old and there are not many of them. What matters is what each one assumes, and how it fails when that assumption breaks.

MethodAssumesGives youFails when
BisectionA good point, a bad point and a reliable verdictThe moment the change enteredReproduction is intermittent, or the cause is outside the code
Minimal reproductionThe symptom can be summoned reliablyA lower unit cost per attemptThe symptom vanishes while you reduce
InstrumentationA hypothesis about where to lookThe lineage of an internal valuePrinting changes the phenomenon
FalsificationYou can define an observation that kills itDefinitive removal of candidatesThe hypothesis has no kill condition
Post-mortem inspectionThe broken state can be read as it isDirect evidence naming the culpritThe traces have already been erased

3.1 Bisection answers since when, not why

git bisect is a binary search that halves the range between a good commit and a bad one. As the documentation's progress lines show, roughly 10 steps remain with 675 revisions left and roughly 9 with 337 left, so the number of tests scales with the logarithm of the commit count. A range of a thousand commits collapses to one in about ten rounds.

When you automate it, the rules are expressed as exit codes. The contract the documentation defines is this.

  • 0 — the current source is good.
  • 1 to 127, excluding 125 — the current source is bad.
  • 125 — the current source cannot be tested, so skip this revision. This is the value to use across ranges where the build is broken.
  • Anything else — abort the search entirely.

The strength of the method is that you do not have to read the code. As long as the verdict is accurate, the range shrinks without understanding. The practical command combinations are written up separately in the Git history commands guide.

The limit comes from the same place. Bisection answers the question since when, not the question why. This case carries a Fixes tag pointing at the commit that introduced the behaviour, and knowing that commit still does not explain why the value is misaligned only on this machine. The misalignment came from the combination of a code change and a hardware configuration, and combinations do not live on the commit list. Be careful with unstable verdicts too. Mark one good revision as bad and the search spends every remaining step in the wrong region.

3.2 Minimal reproduction is really buying time

Minimising a reproduction is not a matter of elegance but of arithmetic. The speed of narrowing is ultimately how many hypotheses you can kill per day, and that number is divided by the time one reproduction takes. Shortening the reproduction is not tidying-up you do later; it is the first investment you make.

  • Pin one axis at a time — kernel configuration, user-space setup, hardware. Change all three at once and the result tells you nothing.
  • The conditions under which the symptom disappears are data too — the single fact that restarting the display manager cures it points the cause away from persistent corruption and toward an accident of placement. If the symptom vanishes as you reduce, step back and re-examine the last thing you removed.
  • Build the automatic verdict first — if a human has to look at a screen to judge, bisection cannot be automated. The exit-code contract from the previous section only means something once a verdict script exists.

3.3 Instrumentation is making logs, not reading them

Debugging an application is mostly reading logs that already exist. On the kernel side it is closer to manufacturing logs that do not exist. Twenty-four debug patches is precisely that work: print something, boot, find the value is not what you expected, print the next point, boot again.

Choosing what to print is where skill shows. Print one value alone and you cannot even tell whether it is wrong. What you need is the lineage of a value: the raw reading from the hardware, the scaled version, the aligned version, printed side by side, so you can see which transformation went off. The commit message putting the raw and rounded values next to each other is not decoration; placing them together is what makes the defect visible.

Post-mortem inspection is a form of instrumentation too. What proved decisive here was not a log taken during execution but the result of reading the offending page afterwards. When the culprit is hardware rather than code, reading what was left behind is effectively the only direct evidence available. Handling the output that piles up overlaps with the Linux log analysis commands material.

3.4 A hypothesis needs a way to die

What you must write down beside a hypothesis is not its supporting reasons but its execution condition. What observation, if it comes back true, kills this? If you cannot write that sentence alongside it, what you have is an impression, not a hypothesis.

The assertion from section 1 demonstrates the principle from the other side. It was written so that it came out true in the very situation it was supposed to catch. That is a hypothesis with no falsification condition frozen into code, which is why it existed and did nothing. When you write a replacement, one test suffices: can I imagine an input that makes this check fail?

  • Write the killing observation next to each hypothesis, and handle the cheap kills first. A hypothesis that dies to a one-line print goes before a half-day experiment.
  • When several hypotheses survive, look for the observation that splits more than one of them at once.
  • Keep what you confirmed and what you inferred separate in your notes. The moment they mix, an inference gets promoted to a premise.

4. Where the tool helped and where it could not

The commit message names three contributions from the tool: much of the grunt-work, continuing to add debug code and analyze it when pushed, and writing the body of the commit message. What generalizes from this is not the capability of the tool but the nature of the work.

4.1 Narrowing and confirming are different jobs

Narrowing shrinks the candidate set. Finding which function produces a value in a wide codebase and where that value flows is closer to bulk reading, and a wrong candidate costs almost nothing because you move on to the next one. Confirming is saying this is the cause. A cause does not become true because the explanation reads well; it becomes true when an observation supports it, and in this case what produced the confirmation was not an argument but the value read out of the reserved page.

So the rule is simple. Work where being wrong just means moving to the next candidate can be delegated; work where being wrong collapses everything built on top of it stays with a person. Because the distinction comes from the nature of the work, it holds whether tools get better or worse.

4.2 What a tool structurally cannot do

  • It is not attached to the machine — 18 boots means somebody actually powered a computer on 18 times. As long as reproduction and verification are what create confirmation, the physical trials cannot be delegated.
  • Its verdict of impossible carries no weight — the commit message records that the tool stated flat out several times that this was unsolvable, and it was in fact solved. A cannot-do answer is information about the shape of that response, not about the shape of the problem.
  • It does not separate plausible from true — a well-written explanation is still well written when it is wrong. That property generates the cost described in the next section.

5. Why a wrong hypothesis is expensive - where to put verification

Time in debugging usually leaks not in the stretch where you know nothing but in the stretch where you are holding a wrong conviction. The costs are not symmetric.

  • A correct hypothesis ends after one verification. A wrong one does not end when verification fails, because you then spend the same time again checking whether your instrumentation was faulty or your conditions differed.
  • The instrumentation and experimental setup you built in the meantime are shaped around the wrong hypothesis, so almost none of it carries over to the next one.
  • The most expensive kind is the plausible wrong answer. A random wrong answer is discarded instantly; a plausible one gets defended. Even when a refutation arrives you find yourself attaching an exception to keep it alive.

The answer, then, is not to postpone verification. Decide the observation that would kill a hypothesis in the same breath as stating it, and build nothing on top of that hypothesis until the observation has been made. The discipline matters more when tools are involved, because when the production rate of explanations rises, so does the accumulation rate of unverified ones.

The kernel documentation draws a line in the same place. The paragraph defining the procedure for AI assistants finding bugs requires that for any non-trivial bug you attempt to create a reproducer to demonstrate that it is real, and it gives the reason: many unverified reports sent to maintainers turn out to be invalid. The same paragraph requires that you state explicitly what could not be done when something could not be built or tested. Separating what was confirmed from what was not is prescribed as procedure, not as manners.

6. Why one anecdote is not a methodology

The story is vivid, but the sample size is one. It is worth separating what can and cannot be drawn from it.

  • There is no control group — nobody knows how many boots the same person chasing the same bug by other means would have needed. Multiplier claims cannot come out of this case. What the commit records are the absolute numbers 24 and 18, and absolute numbers without a comparison do not produce a ratio.
  • Only successful samples are visible — sessions that ended in a fix leave commits behind; sessions that ended in a dead end leave nothing anywhere. The pool of stories we read is pre-filtered.
  • The conditions are unusual — reproducing reliably on your own machine, deep familiarity with the code in question, and as much time as you want. Remove any one of them and the same path does not hold.
  • A one-line fix is not a difficulty rating — if anything it is the opposite. The shorter the fix, the further the symptom often sits from the cause, and the harder the narrowing. And once solved, every step looks inevitable in hindsight, when most of them were probably discarded hypotheses.

What can legitimately be drawn is an existence proof. That something was solved this way once and that this way solves things are different sentences. What you take from the story is the order, not the multiplier.

7. The open source problem - attribution and review burden

The moment tool-produced work heads for a public repository the nature of the problem changes. It stops being about how you spend your own time and becomes about how you spend other people's. The Linux kernel has written this down, and as checked against the master branch on 24 August 2026 the content is as follows.

  • AI agents must not add Signed-off-by — the stated reason is that only humans can legally certify the Developer Certificate of Origin. Reviewing generated code, confirming licensing compliance, signing off and taking full responsibility all sit on the human submitter's side.
  • Attribution takes the form Assisted-by: LLM — optionally followed by specialized analysis tools such as coccinelle or sparse, while basic tools like git and compilers are not listed.
  • Using a tool to find the bug is also disclosable — the companion document says that if a tool was used to find the problem a change addresses, that belongs in the changelog, and it includes the case where the changelog itself was tool-generated.
  • The reason is bandwidth — that document states plainly that reviewer and maintainer bandwidth is a scarce resource, and that knowing which parts came from humans and which from tools is how that resource is protected.

A distinction worth carrying into practice falls out here. Disclosure comes in two forms: prose in the message and a machine-readable trailer. In the commit above the trailer lines carry only Fixes, Cc and Signed-off-by, while the tool use is disclosed inside the body. That is enough for a human reader and invisible to any tally. If you ever intend to count who used what and where, you need a rule that puts it in a fixed place in a fixed format from the start.

The larger axis is the asymmetry of review. The cost of producing went down and the cost of reading did not. Translated into practice on the receiving end, that looks like this.

  • Proposals without a reproduction procedure and verification results go to the back of the review queue. Keeping the verification burden on the submitter is the only way to protect bandwidth.
  • Proposals that do not state what was not done get sent back. If the reviewer cannot see what went untested, the reviewer ends up running those tests.
  • Fix the attribution format and reject what ignores it; unifying it after the fact costs far more. And length is not a quality signal — long, smooth explanations are the easiest place to hide an unverified claim.

8. What a practitioner takes away

Cut the discussion into units of work and the delegation question becomes a table. The criterion is not capability but the cost of recovering from being wrong.

WorkWhat a tool is good atWhat a person must doWhy the line falls there
Sweeping code pathsListing candidate functions and call flowsAccepting or rejecting the listBeing wrong just means the next candidate
Forming hypothesesEnumerating possible causes broadlyDefining the killing observationVariety is cheap, falsification design is not
Reproduction design and runsDraft procedure and verdict scriptThe actual trials and the verdictPhysical trials cannot be delegated
Instrumentation codeWriting the prints, collating resultsDeciding what to print and whereChoosing the print point is the hypothesis
Confirming the causeNothingJudging whether observation supports itA plausible explanation is not evidence
Deciding to stopNothingCalling halt or continueA tool's impossible verdict is not grounds
Commit messageDraftingFact-checking and the final wordingThe record gets cited as evidence later
Sign-off and liabilityNothingAll of itProcedure places it explicitly on humans

Turned into the order of a working day, the table reads like this.

  • Cut the reproduction time first. The unit cost of every other activity is set here.
  • Automate the verdict. If human eyes are in the judging loop, repeated trials are bound to human hours.
  • Write the killing observation on the same line as the hypothesis, and execute the cheap refutations first. Only survivors go to expensive experiments.
  • In your notes, separate what you confirmed from what you inferred, and record what you could not do. It saves the next person from the same wall.

If you do not decide what a print is meant to answer before you add it, the accumulated output becomes a new burden rather than an answer. The root of that is the same problem covered in why the observability data you collect never gets read.

9. The same method works without any tool

None of the methods in this article require a tool. Bisection has been used in kernel development for a long time, and minimal reproduction, instrumentation and falsification are older discipline still. What tooling changed is the speed of narrowing candidates, not what counts as evidence.

Reverse the order and you lose. Put a tool on top of an absent method and the only thing that improves is the production rate of plausible wrong answers, which section 5 identified as the most expensive kind.

  • The learning order — method first, tool second. Without the ability to design a refutation you have no way to judge whether a tool's answer is right.
  • The self-check question — can I design the observation that would kill the answer this tool gave me? If not, that answer is not yet even a hypothesis.
  • What changed and what did not — the upfront cost of pulling candidates out of a large codebase went down, and verification became the bottleneck by the same amount. That confirmation comes from reproduction and verification is unchanged.

Skill, in the end, separates people on the confirming side rather than the narrowing side. Listing candidates got cheap; deciding which of them is true is still expensive and still a person's job.

What could not be confirmed

The items this article could not ground are collected here.

  • Which AI tool was used. The commit message names none.
  • The contents of the 24 debug patches and the output of the 18 boots. Only the final commit is public, and the elapsed time and the split between human and tool hours are not recorded either.
  • Why this commit's trailers carry no Assisted-by. The trailer composition is verifiable in the public commit, but the reasoning behind it is not.
  • The current state of discussion around that tag requirement. The wording quoted here was checked in the master branch documentation on 24 August 2026; whether it has changed since was not verified.
  • How widely the same defect appeared across other hardware configurations. The commit records the values from one machine.

Conclusion: narrowing and confirming are not the same act

The procedure for narrowing a hard bug was not newly invented. Halve the range between good and bad, shorten the reproduction, manufacture the logs that do not exist and print the lineage of a value, attach a killing observation to each hypothesis and erase them one by one. What remains at the end is not an explanation but an observation.

A tool can occupy some of these slots: reading broadly, pulling candidates, drafting. The slots it cannot occupy are equally clear — powering on the machine, judging whether an observation supports an explanation, deciding whether to stop or continue, and signing off and carrying the liability. That division does not shift as tools improve, because it came from the nature of the work rather than from capability.

It is better to set aside the urge to extract a multiplier from a single story. What you can do instead is keep the order the next time you meet a bug whose logs say nothing: shorten the reproduction, decide the killing observation first, and record what you confirmed apart from what you inferred. With that order the bug narrows whether or not a tool is present; without it, a tool only piles up plausible wrong answers faster.
