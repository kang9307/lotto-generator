find・xargs の空白と改行の罠 - ファイル名ひとつがスクリプトを壊す

「-print0 を使え」で終わらせない - 一時ディレクトリで実際に壊した出力

2026年7月29日 開発・インフラ

はじめに: 消えたのは別のファイルだった

整理スクリプトを流した。エラーが一行出た。rm: cannot remove './data': No such file or directory。たいしたことはなさそうに見える。存在しないファイルを消そうとしたという意味なのだから、もう片付いているのだろう。ところがディレクトリを見直すと、消すつもりだったファイルはそのまま残っていて、触る理由のなかった別のファイルが消えている。

この記事はその瞬間を再現するところから始まる。結論を先に言えば、原因はファイル名の中の空白ひとつである。そしてこの話は「-print0 を使え」の一行では終わらない。そこで終わらせるとなぜ壊れるのかを知らないまま残り、区切り文字を直しても消えない三種類の欠陥を見落とすことになる。

そこでこの記事は概念の説明をしない。一時ディレクトリを作り、意地の悪いファイル名を実際に作り、本当に壊れた出力をそのまま貼った。以下のコードブロックはすべて手で書いた例ではなく実行結果である。扱う順序はこうなる。

  • なぜ壊れるのか — ファイル名はバイト列なのにパイプラインはテキストを切るという根本的な不一致
  • どう壊れるのか — 空白・改行・ハイフン・グロブをそれぞれ再現し、実際に何が消えたのかを確認
  • 何が安全なのか — ヌル区切り、read の二つのオプション、-exec の三つの形、引数長の限界、-delete の性格

実行前の安全告知。この記事のすべての再現は新しく作った一時ディレクトリの中だけで行った。本文に rm * や rm -rf が出てくる箇所は、その一時ディレクトリとその配下に限定されている。実際のサーバーや作業ディレクトリで真似しないこと。とくに後段の「ハイフンで始まるファイル名」の再現は rm * 一回で配下のディレクトリを丸ごと消す。破壊的なコマンドを試すときは、まず rm を echo や ls に置き換えて対象の一覧を目で確認してから実行するほうが安全である。

1. 実行環境とこの記事の根拠

以下の出力はすべて実際に流した結果である。再現環境は次のとおり。

$ uname -s
MINGW64_NT-10.0-19045
$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)
$ find --version | head -1
find (GNU findutils) 4.10.0
$ xargs --version | head -1
xargs (GNU findutils) 4.10.0

Windows 10 上の MSYS2 / Git Bash 環境で、道具は GNU findutils 4.10.0 と bash 5.2 である。単語分割・ヌル区切り・-exec の挙動は Linux と同じ GNU のコードなので結果はそのまま移る。ただしこの環境に固有の制約が三つあるので先に明かしておく。読む側が結果を判断するために必要な情報である。

  • バックスラッシュを含むファイル名は作れない。Windows ではパス区切り文字だからである。そのためバックスラッシュ関連の再現はファイルではなくパイプに流した文字列で行った。read の挙動を見るのが目的なので結果は同じである。
  • getconf ARG_MAX が undefined を返す。そこで引数長の節では xargs --show-limits が報告する実際の値を使う。
  • グロブ長の超過は再現できなかった。4 万個のファイルを作って 1.9MB のグロブを渡してもこの環境では失敗しなかった。Linux なら Argument list too long が出る大きさである。確認できなかったことは確認できなかったと書く。代わりに各自の環境で限界を確認する方法を併載する。

判定基準は二つに固定した。実際のファイル数とスクリプトが処理した数が一致するか、そして各反復で対象パスが実際に存在するかである。この二つが食い違えば、そのパイプラインはすでに壊れている。数は find . -type f -printf 'x\n' | wc -l で数えた。ファイル名ではなくファイルごとに固定の一文字を出させることで、数える行為そのものがファイル名に汚染されないようにしたのである。

2. なぜ壊れるのか - ファイル名はバイト列、パイプラインはテキスト

根本原因は単純だ。カーネルがファイル名に許すものと、シェルのパイプラインが一覧を切る方法が噛み合っていない。

POSIX でファイル名に使えないバイトは事実上二つだけである。ヌルバイトとスラッシュだ。スラッシュはパス区切りだから、ヌルは文字列の終わりを意味するから使えない。残りはすべて合法である。空白も改行もタブもアスタリスクも引用符もハイフンも、すべて正常なファイル名の一部になりうる。

一方 find ... | xargs はテキストを切る。POSIX の xargs 仕様は、標準入力の引数が「引用符で囲まれていない空白類文字、エスケープされていない空白類文字、改行文字で区切られる」と記している。つまり xargs はファイル名の中の空白とファイル名の間の空白を区別する根拠をそもそも持っていない。どちらも同じ 0x20 バイトだからだ。

ここで大事な認識がひとつある。これは道具の欠陥ではない。xargs はファイル一覧を受け取るために設計された道具ではなく、空白で区切られた引数列を受け取るために設計された道具である。それをファイル一覧の受け渡し手段として使い始めたところに不一致が生まれた。だから解も「xargs を直そう」ではなく「ファイル名に絶対に現れないバイトを区切りに使おう」になる。ヌルバイトがそれである。

実際に作ってみた類型を整理するとこうなる。各行の「何が壊れるか」は後段で一つずつ再現する。

3. 再現 ① 空白 - 見当違いのファイルが消えた

もっともよくある事故をそのまま再現する。ディレクトリにファイルが二つある。data backup.log が消したい対象で、backup.log は触ってはいけないファイルだ。find は data* だけを探す。

--- before ---
backup.log
data\ backup.log
--- find output (what xargs receives) ---
./data backup.log
--- run: find . -name 'data*' | xargs rm ---
rm: cannot remove './data': No such file or directory
  exit=123
--- after ---
data\ backup.log

結果をゆっくり見よう。ls -b は特殊文字をバックスラッシュで表示するので、data\ backup.log が空白を含むファイルひとつである。find はこのファイル一つだけを見つけた。ところが実行後に残っているのは data backup.log ひとつだけだ。つまり、

  • 消したかったファイルは生き残った。rm は ./data という名前を受け取り、そんなファイルは存在しなかった。
  • 一度も一致していない backup.log が消えた。rm の二番目の引数がそれだったからである。
  • エラーは一行だけである。二番目の引数は実在したので静かに成功した。

事故の方向がちょうど裏返った。そしてログには「存在しないファイルを消そうとした」という無害に見える一行だけが残る。実務でこのパターンが危険な理由がここにある。エラーメッセージが被害を指していると信じさせるのだ。

3.1 -t で確認しても見えない

xargs -t は実行するコマンド行を先に表示してくれる。デバッグのためのオプションだ。ところがこの事故では役に立たない。

$ find . -name 'data*' | xargs -t echo RM
echo RM ./data backup.log
RM ./data backup.log

表示された行は echo RM ./data backup.log である。引数が一つなのか二つなのか区別できない。目で見るかぎり正常に見える。一方ヌル区切りを使うと xargs -t が引用符を付けて表示する。

$ find . -name 'data*' -print0 | xargs -0 -t ls -b
ls -b './data backup.log'
./data\ backup.log

引用符が見えれば一つの引数である。パイプラインを点検するときは -t だけを付けず -0 -t で付けてこそ実際の境界が見える。

4. 再現 ② 改行 - ファイル 2 個が 3 回繰り返された

空白はまだ目につく。改行はそうではない。ファイル名に改行を入れる人はいないと思いがちだが、ウェブのアップロード・外部連携・コピー貼り付けの事故で実際に入ってくる。作るのは一行だ。

$ touch $'line1\nline2.txt'
$ touch plain.txt
$ ls -b
line1\nline2.txt
plain.txt

ファイルは二つである。ls -b が \n と表示したものが改行を含む名前ひとつだ。これをもっともよくある繰り返し文に入れてみる。

--- find . -type f | while IFS= read -r f ---
GOT: [./line1] exists=NO
GOT: [line2.txt] exists=NO
GOT: [./plain.txt] exists=yes
--- true file count (find -printf) ---
2

実際のファイルは 2 個なのに繰り返しは 3 回まわり、うち 2 回は存在しないパスを指していた。ここで押さえるべき点が二つある。

  • IFS= と -r をすでに付けているのに壊れた。この二つのオプションは一行を受け取ったあとの処理を直すものであって、行を分ける基準そのものは変えられない。区切り文字の問題は生産側（find）で解かねばならない。
  • 静かに間違える。exists=NO の二項目に rm を回していればエラーが二行出ただろうが、chmod・touch・統計の集計のように失敗しても目立たない作業なら、結果の数値だけが静かに狂ったまま通り過ぎる。

数える方法も汚染される。ファイル数を数えるときに find . -type f | wc -l を使うと上のディレクトリでは 3 が出る。実際は 2 だ。ファイル名を数えるのではなく、ファイルごとに一文字を数えるべきである。find . -type f -printf 'x\n' | wc -l がその形だ。-printf がない環境なら find . -type f -exec printf 'x\n' {} + | wc -l で同じ結果が得られる。

5. 再現 ③ ハイフン始まり - rm ひとつがディレクトリを丸ごと消した

この節がこの記事でもっとも危険な再現である。一時ディレクトリの中でのみ実行した。構成はこうだ。配下のディレクトリ project/ があってその中にファイルが二つ、そして -rf という名前の空ファイルと note.txt がある。

--- before ---
-rf
note.txt
project
tree:
.
./-rf
./note.txt
./project
./project/README
./project/src
./project/src/main.c
--- run: rm * (一時ディレクトリの中) ---
  exit=0
--- after ---
.
./-rf

ディレクトリが丸ごと消えた。終了コードは 0 である。エラーは一行も出ない。シェルが * を展開すると rm -rf note.txt project になり、rm は -rf をファイルではなくオプションとして読む。再帰削除が有効になったのだ。

同じ構成から -rf ファイルだけを外して流すとどうなるかが対照群である。

--- 対照群: -rf ファイルがないときの rm * ---
rm: cannot remove 'project': Is a directory
  exit=1
--- after ---
.
./project
./project/README
./project/src
./project/src/main.c

rm はもともとディレクトリを拒む。その安全装置を無力にしたのが、あの空ファイルひとつである。名前が -rf のファイルを置いておくだけで他人の整理スクリプトに再帰削除をさせられるという意味であり、これが find・xargs の問題が単なる「見栄え」ではなくセキュリティの問題に分類される理由だ。

5.1 オプションとして読まれるさまを目で見る

--help という名前のファイルを作るともっと露骨に見える。

$ touch ./--help ./real.txt
$ ls * | head -4
Usage: ls [OPTION]... [FILE]...
List information about the FILEs (the current directory by default).
Sort entries alphabetically if none of -cftuvSUX nor --sort is specified.

$ ls -- *
--help
real.txt

ファイル一覧を頼んだのにヘルプが出る。-- を付ければその後ろはすべて被演算子として読まれるので正常に戻る。

5.2 三つの防御とそれぞれの限界

$ ls *          # -rf がオプションとして食われる
normal.txt
$ ls -- *       # オプション終端の印
-rf
normal.txt
$ ls ./*        # パスの前置
./-rf
./normal.txt
$ find . -name '-rf' -exec ls -b {} \;   # find はそもそも免疫がある
./-rf
  • --（オプション終端の印） — もっとも標準的である。ただしこのオプションに対応していない古いユーティリティがあり、-- のあとでも独自に解析する道具がまれにある。
  • ./ の前置 — どんな道具にも通じる。名前が -rf でも ./-rf はハイフンで始まらないからだ。もっとも堅い防御である。代わりに出力に ./ が付く。
  • find の -exec — そもそも免疫がある。find が見つけたパスは ./-rf のように起点を含み、シェルを経ずそのまま execve に渡されるので再解析がない。上の最終行で ls -b が正常に動いた理由である。

したがって実務の規則はこう整理される。利用者や外部システムが作った名前をコマンドに渡すときは -- を付けるか、そもそも find が作った ./ 付きのパスをそのまま使う。

6. 再現 ④ ls を grep に噛ませたものはファイル一覧ではない

「ls を解析するな」という助言は広く知られているが、たいてい理由なしに伝わる。実際に壊してみると理由が一度で見える。ファイルが 3 個あり、うち一つに改行が入っている。

--- true file count ---
3
--- ls | wc -l ---
4
--- ls | grep log ---
log1
log2.txt
my log.txt
--- ls | grep log | wc -l ---
3

実際は 3 個なのに ls の行数は 4 だ。grep を通した結果は3 行なので正常に見える。だから目で検討すると通ってしまう。その一覧を実際に使うと何が起きるかが核心である。

$ ls | grep log | xargs ls
ls: cannot access 'log1': No such file or directory
ls: cannot access 'log2.txt': No such file or directory
ls: cannot access 'my': No such file or directory
ls: cannot access 'log.txt': No such file or directory

4 個の名前を参照し、そのうち実在するファイルは一つもない。改行を含む名前ひとつが二行に割れ、空白を含む名前ひとつがさらに二つの引数に割れた結果である。

ここにあまり知られていない罠がもう一つある。ls は出力先によって違うバイトを出す。端末に直接出すときは印字できない文字を ? などに置き換えて見せるが、パイプに渡すときは元のバイトをそのまま流す。つまり人が目で確認した見た目と、次の段が受け取るバイトが食い違う。検討を通ったパイプラインが運用で壊れる典型的な経路である。

6.1 引用符なしのコマンド置換は二度壊れる

for f in $(find ...) の形は ls | grep よりありふれていて、もっと悪い。単語分割とグロブ展開が続けざまに起きるからだ。ファイルが 4 個あるディレクトリで確認した。うち一つは名前が文字どおり * である。

$ ls -b
*
a.txt
b.txt
my\ file.txt
$ for f in $(find . -type f); do printf 'GOT [%s]\n' "$f"; done
GOT [./a.txt]
GOT [./b.txt]
GOT [./my]
GOT [file.txt]
GOT [./*]
GOT [./a.txt]
GOT [./b.txt]
GOT [./my file.txt]
--- count ---
real files = 4
iterations = 8

ファイル 4 個に繰り返し 8 回である。二つの段が重なった。

  • 単語分割 — ./my file.txt が ./my と file.txt に分かれた。
  • グロブの再展開 — ./* というファイル名がパターンとして解釈し直され、ディレクトリ全体に膨れた。そのため a.txt と b.txt が二度ずつ処理された。

面白い点がある。最後の GOT [./my file.txt] は空白が生きている。グロブ展開の結果は再び分割されないからだ。同じファイルが一度は割れ、一度は無傷で処理されたわけである。こうしたパイプラインが「たまに動いてたまに動かない」理由はこの非対称性にある。

7. -print0 と -0 - 何が生き返るのか

ここからは解のほうだ。ヌルバイトはファイル名に絶対に入りえない唯一のバイトなので区切りとして安全である。先の二つの事故をそのまま流し直した。

--- find -print0 | xargs -0 -t (空白のケース) ---
ls -b './data backup.log'
./data\ backup.log

--- find -print0 | while IFS= read -r -d '' (改行のケース) ---
GOT: [./backup.log] exists=yes
GOT: [./data backup.log] exists=yes
GOT: [./line1
line2.txt] exists=yes

三つのファイルすべてが exists=yes である。改行を含む名前は出力では二行に見えるが一つの値だ。画面が二行だから二項目なのではないという点を exists の検査が証明している。

7.1 移植性に関する最新の事実

よく「-print0 は GNU の拡張だから POSIX ではない」と言われる。2024 年時点ではもう正しくない。The Open Group Base Specifications Issue 8（IEEE Std 1003.1-2024）は find の -print0 を標準に入れ、変更履歴に「Austin Group Defect 243 が適用され -print0 プリマリが追加された」と記している。xargs 側も同じ欠陥番号で -0 と -r が一緒に入った。

ただし標準に入ったことと目の前のサーバーにあることは別である。Issue 8 は 2024 年版であり、古い Unix や最小構成のコンテナの find はいまだ -print0 を知らないことがある。移植性が必要なら-exec ... {} +を使うほうが安全だ。この形はずっと以前から標準であり、ヌル区切りなしでも空白・改行を無傷で渡す。

$ find . -type f -exec sh -c 'for p do printf "portable: [%s]\n" "$p"; done' _ {} +
portable: [./a b.txt]
portable: [./c
d.txt]

7.2 read -d '' にヌルが来ないとき

消費側だけ直して生産側を直さないと何も処理されない。そしてエラーも出ない。

$ find . -type f -print | while IFS= read -r -d '' f; do printf 'GOT [%s]\n' "$f"; done
  (出力なし)
  iterations = 0   real files = 1

-print は改行で終えるのに read -d '' はヌルを待つ。ヌルは永遠に来ず、最後に read が失敗してループ本体が一度も実行されない。終了コードは 0 でログも静かだ。-print0 と -d '' は必ず対で付く。

8. read の IFS= と -r - それぞれが防ぐもの

while IFS= read -r -d '' f は呪文のように覚えて使うが、各部品が何を防ぐのかはあまり知られていない。一つずつ外して流した。

8.1 IFS= を外すと前後の空白が消える

pad のうしろに空白が二つ付いたファイルと、真ん中にタブが入ったファイルで試した。

--- WITH IFS= ---
[./pad  ] len=7 exists=yes
[./ta	b] len=6 exists=yes
--- WITHOUT IFS= ---
[./pad] len=5 exists=NO
[./ta	b] len=6 exists=yes

長さが7 から 5 へ縮み exists=NO になった。read は値を入れる前に IFS に含まれる空白類文字を前後から削り取るのだが、既定の IFS には空白・タブ・改行が入っている。IFS= はその一覧を空にして削り取れなくする。

真ん中のタブが生き残った点も注目に値する。変数が一つだけなら read は残りを丸ごと入れるので、内部の区切り文字は保たれ前後だけが削られる。そのためこの欠陥は前後に空白がある名前でのみ顕在化し、そういう名前は画面では目につかない。発見が遅れる理由である。

パスではなくファイル名だけを扱うときはもっと露骨に表れる。

$ find . -name '*lead*' -printf '%f\0' | while IFS= read -r -d '' f; do ...
[  lead.txt] len=10
$ find . -name '*lead*' -printf '%f\0' | while read -r -d '' f; do ...
[lead.txt] len=8

8.2 -r を外すとバックスラッシュが食われる

この環境ではバックスラッシュを含むファイルを作れないので、文字列をパイプに流して試した。read の挙動を見るのが目的なので結果は同じである。

$ printf 'C:\\temp\\new\n' | while IFS= read -r x; do ...
with -r    : [C:\temp\new]
$ printf 'C:\\temp\\new\n' | while IFS= read    x; do ...
without -r : [C:tempnew]

バックスラッシュが丸ごと消えた。-r がないと read はバックスラッシュをエスケープ文字として解釈し、次の文字をそのまま通して自分は消滅する。もっと悪いのは行末にバックスラッシュがある場合だ。

$ printf 'one\\\ntwo\n' | while IFS= read -r x; do ...
with -r    : [one\]
with -r    : [two]
$ printf 'one\\\ntwo\n' | while IFS= read    x; do ...
without -r : [onetwo]

二行が一行に結合された。バックスラッシュ＋改行を行の継続として処理したからである。ファイル一覧ならば二つのファイルが一つの存在しないパスに潰れるという意味だ。

8.3 最終行に改行がないとき

ヌル区切りとは別だが同じ read ループでよく起きる問題である。ファイルの末尾に改行がないと最終行が丸ごと消える。

--- while IFS= read -r line ---
GOT [a]
GOT [b]
--- while IFS= read -r line || [ -n "$line" ] ---
GOT [a]
GOT [b]
GOT [c]

read は区切り文字に出会えないまま入力の終わりに達すると、変数は満たしつつ 0 でない値を返す。そのため while の条件が偽になり本体を飛ばす。|| [ -n "$line" ] を足せば最後の断片を救える。一覧の最後の項目が静かに欠ける不具合があるなら、まずここを疑う価値がある。

9. -exec の三つの形 - セミコロン、プラス、そして xargs

-exec はシェルを経ないので三つの形すべてが空白・改行に安全である。分かれるのは呼び出し回数・速度・終了コードだ。ファイル 500 個（すべて名前に空白を含む）で呼び出し回数を直接数えた。

-exec {} \;  invocations=500  args=500
-exec {} +   invocations=1    args=500
--- 子プロセスが受け取った最初の二引数 (cat -A) ---
files/f 1.txt$
files/f 10.txt$

$ は行末の印である。空白がそのまま生きていて、引数一つがファイル一つに対応している。速度はファイル 2000 個で計った。

--- -exec /bin/true {} \; ---
real	1m25.965s
--- -exec /bin/true {} + ---
real	0m0.252s
--- xargs -0 /bin/true ---
real	0m0.291s

340 倍の差である。ただしこの倍率はそのまま信じないこと。この環境は Windows 上の MSYS2 なのでプロセス生成の費用が Linux よりずっと大きい。Linux では差はこれより小さい。方向はどこでも同じだが倍率は環境ごとに異なる。

9.1 終了コードが分かれる

ここがあまり知られていない部分だ。子プロセスが失敗したとき find が何を返すのかを確認した。

$ find . -name '*.txt' -exec false {} \;   ; echo $?
0
$ find . -name '*.txt' -exec false {} +    ; echo $?
1
$ find . -name '*.txt' -print0 | xargs -0 false ; echo $?
123

セミコロン形は 0 を返す。子プロセスが失敗したのにパイプラインは成功と報告する。CI でこの形を使えば失敗が緑のランプで通過する。GNU の文書はプラス形についてのみ「プラス形のどの呼び出しであれ 0 でない値を終了状態として返せば find が 0 でない終了状態を返す」と記している。観測結果と一致する。

xargs の終了コード体系も知っておく価値がある。直接確認した値だ。

子が 3 で終了     -> xargs 123
子が 255 で終了   -> xargs 124  (xargs: exited with status 255; aborting)
コマンドが見つからない -> xargs 127
  • 123 — 一つ以上の呼び出しが 1〜125 で失敗。子の実際のコードは失われる。
  • 124 — 子が 255 で終了。xargs が即座に中断する。残りのバッチは実行されない。
  • 126 / 127 — コマンドを実行できない / 見つけられない。

実務上の含意は明快だ。どのファイルが失敗したのかを知る必要があるなら xargs の終了コードでは分からない。子プロセス側で失敗したパスを自分で記録せねばならない。

9.3 -exec sh -c に {} を挟み込まないこと

シェルをもう一度呼んだ瞬間に安全性が失われる。名前にシングルクォートが入ったファイルで確認した。

--- 悪い形: {} をシェル文字列の中に貼る ---
$ find . -name '*.txt' -exec sh -c 'echo FILE={}' \;
sh: -c: line 1: unexpected EOF while looking for matching `''

--- よい形: {} を引数として渡す ---
$ find . -name '*.txt' -exec sh -c 'echo FILE="$1"' _ {} \;
FILE=./it's here.txt

前の形はファイル名がシェルのソースコードとして解釈される。ここでは構文エラーで終わったが、名前にセミコロンやバッククォートが入っていればそこに書かれたコマンドが実行される。これがコマンドインジェクションである。後の形はファイル名を $1 というデータとして受け取るので、どんな文字が入っていても実行されない。_ は $0 の位置を埋める場所取りだ。これを外すと最初のファイルが $0 に入って静かに欠落する。

10. 引数長の限界 - 静かに分かれ、静かに上書きする

区切り文字を直して引用もすべて済ませたのに結果が足りない場合がある。この節はその話だ。xargs は一覧が長いと自分で複数回に分けて実行する。親切な機能だが、分かれたという事実を教えてくれない。

$ xargs --show-limits < /dev/null
Your environment variables take up 5825 bytes
POSIX upper limit on argument length (this system): 24127
POSIX smallest allowable upper limit on argument length (all systems): 4096
Maximum length of command we could actually use: 18302
Size of command buffer we are actually using: 24127

POSIX 仕様は xargs が「コマンド行を起動するときに引数と環境の一覧の合計が {ARG_MAX}-2048 バイトを超えないようコマンド行の長さを制限しなければならない」と記している。上の出力の二行目と四行目の差がその余裕分と環境変数の取り分だ。環境変数が多いシェルでは使える長さが減ることも上の一行目が示している。

分かれる回数はこう変わる。

$ seq 1 200000 | xargs echo | wc -l
68
$ seq 1 200000 | xargs -n 1000 echo | wc -l
200
$ seq 1 200000 | xargs -s 4096 echo | wc -l
316

10.1 分かれると何が壊れるのか

バッチに分かれること自体は問題ではない。バッチの中で向きを変えてファイルに書くと問題になる。ファイル 3 万個で再現した。

real file count = 30000
--- xargs -0 sh -c 'printf "%s\n" "$@" > out.txt' _ ---
lines in out.txt = 426
--- 修正 1: 上書きではなく追記（>>） ---
lines in out2.txt = 30000
--- 修正 2: 向きの変更を xargs の外へ ---
lines in out3.txt = 30000
--- xargs が使ったバッチ数 ---
62   (batch: 482 args ...)

3 万個を渡したのに結果ファイルには426 行しか残らなかった。62 個のバッチが順に同じファイルを上書きし、最後のバッチだけが生き残ったのである。エラーは一行もなく終了コードも 0 だ。この形は tar -cf・zip・リダイレクトのように「出力ファイルを新しく作る」コマンド全部に当てはまる。圧縮アーカイブを作るときに一部のファイルしか入っていない事故は、たいていこの形である。

対応は三つのうちいずれかだ。

  • 追記に変える — >> を使うが、実行前に対象ファイルを空にしておく。再実行で累積しないようにするにはこの初期化が必須である。
  • 向きの変更を xargs の外に置く — xargs ... > out.txt の形ならファイルは一度だけ開かれる。
  • 追加モードのあるコマンドを使う — アーカイブなら新しく作るのではなく追加するオプションを使う。ただし最初のバッチでは新規作成し以降は追加せねばならないので、初期化を分離する必要がある。

10.3 入力が空のときコマンドが一度実行される

この挙動は標準に明記されており、知らないと事故になる。POSIX 仕様は「標準入力から引数がひとつも与えられない場合、-r が指定されていればユーティリティは 0 回実行され、-r がなければちょうど一度実行される」と記している。実際に確認した。

$ find . -name 'nothing*' -print0 | xargs -0 echo "RAN with args:"
RAN with args:
  exit=0
$ find . -name 'nothing*' -print0 | xargs -0 -r echo "RAN with args:"
  (実行されない)
$ find . -name 'nothing*' -exec echo "RAN with args:" {} +
  (実行されない)

見つかったファイルが一つもないのにコマンドが実行された。ここに後続の引数が固定で付いていれば、その引数だけでコマンドが回る。整理スクリプトでこの形が危険な理由である。-r（--no-run-if-empty）を付けるか、-exec ... + を使えばこの問題自体がない。三行目がそれを示している。

11. find -delete と -exec rm の違い

消す作業には -delete という専用のアクションがある。一つずつ再現してみると性格がはっきり違う。まず安全性だ。空白・改行・ハイフンを含むファイル三つを入れ子のディレクトリに作り、一度に消した。

--- before ---
./a/-rf.tmp
./a/b/c/hostile name.tmp
./a/b/line1
line2.tmp
--- find . -name '*.tmp' -delete ---
  exit=0
--- after ---
.
./a
./a/b
./a/b/c

三つとも綺麗に消えた。途中にシェルも rm も挟まらないからである。find が自分の中で直接削除の呼び出しを行う。ファイル名がどんな形であれ関与する余地がない。

11.1 -depth が入り -prune が死ぬ

代償がある。-delete は走査の順序を変える。

既定の順序（前順）:    x → x/y
-depth の順序（後順）: x/y → x

ディレクトリを消すには中を先に空けねばならないので当然の選択だ。問題はこの -depth が-prune を無力化することである。除外規則を -prune で書いていた人が -delete を付けると除外が消える。幸い GNU の find はこの組み合わせを拒む。

$ find . -path ./keep -prune -o -name '*.tmp' -delete
find: The -delete action automatically turns on -depth, but -prune does
nothing when -depth is in effect.  If you want to carry on anyway, just
explicitly use the -depth option.
  exit=1
survivors: ./drop/b.tmp  ./keep/a.tmp

拒んで何も消さなかった。よい設計である。警告を無視して -depth を自分で付けると -prune が静かに無視されたまま実行されるので、その助言には従わないほうがよい。除外は ! -path で書く。

$ find . -name '*.tmp' ! -path './keep/*' -delete
survivors: ./keep/a.tmp

11.2 空でないディレクトリは消せない

$ find . -name 'full' -delete
find: cannot delete './full': Directory not empty
  exit=1

ディレクトリごと消すには -delete だけでは足りず、中まで一緒に一致させねばならない。rm -rf とは性格が違うということだが、この保守性がむしろ長所である。一致条件を誤っても被害がファイル単位にとどまる。

12.1 試験用の危険なファイル名を作る

自分のスクリプトを点検するにはこれらのファイルを先に作っておけばよい。必ず新しい一時ディレクトリの中で行う。

$ mkdir -p /tmp/fx-test && cd /tmp/fx-test
$ touch -- 'space name.txt' $'newline\nname.txt' -dash.txt \
      "quote'name.txt" 'glob*name.txt' $'tab\tname.txt' \
      '  pad  .txt' 'semi;name.txt' 'dollar$name.txt'
$ find . -type f -printf 'x\n' | wc -l     # 実際の個数
9
$ ls | wc -l                               # 素朴なパイプラインが見る数
10

判定は二行で終わる。スクリプトが処理した個数が 9 でなければすでに壊れている。そして各反復で [ -e "$f" ] が真かを確認すれば、どの項目が食い違ったかまで分かる。touch の前の -- を外すと -dash.txt がオプションとして読まれ、試験用ファイルすら作られないことも併せて確認できる。

12.2 Unicode は少し別の問題である

最後に区切り文字とは無関係な類型を一つ挙げる。同じに見えるのに別のファイルである。

$ ls -b
cafe?\201.txt
café.txt
$ (バイトの確認)
10 bytes   c  a  f  e 314 201  .  t  x  t     <- 結合文字（NFD）
 9 bytes   c  a  f 303 251  .  t  x  t        <- 合成済み（NFC）
$ find . -type f -printf 'x\n' | wc -l
2

画面ではどちらも café.txt に見えるがバイトが違うので別々のファイルである。find -name はそれぞれ自分の形にのみ一致した。ここから得られる規則は一つだ。ファイル名の比較は目ではなくバイトで行う。ls -b やバイトダンプで確認する習慣が要り、一覧を並べ替えて比べるときは LC_ALL=C sort でロケールの影響を消してこそ結果が再現する。

付け加えると、ファイルシステムによって挙動が分かれる。正規化をしないファイルシステムでは上のように二つのファイルが共存し、正規化するファイルシステムや大文字小文字を区別しないファイルシステムでは一つに合わさるか衝突する。複数のプラットフォームを跨ぐ同期作業で「確かに複製したのにない」が出たら、こちらを疑う価値がある。

結論: オプションではなく境界を選ぶ問題

「-print0 を使え」は正しいが半分である。この記事で再現したものを畳み直すと、欠陥は四つの層にまたがっており、ヌル区切りはそのうち一つの層だけを覆う。

  • 区切り文字の層 — 空白・改行が項目を切る。-print0／-0／-d '' が覆う。
  • 引用の層 — 値を引用しないとループの中で再び分割されグロブが再展開される。ファイル 4 個が繰り返し 8 回になったあの事故だ。
  • オプション解釈の層 — ハイフンで始まる名前は区切り文字と無関係にオプションになる。-- や ./ が覆う。rm * ひとつがディレクトリを消した再現がここに属する。
  • バッチの層 — 一覧が長いと静かに分かれる。3 万個が 426 行になった再現がここに属する。

だから実務の規則はオプションの一覧ではなく境界に関する判断として整理するほうがよい。ファイル名がシェルの構文を通過する地点を作らない。この一文が上の四つの層をすべて覆う。-exec ... + がよい既定である理由もこれだ。シェルを経ず、バッチを自分で分けつつ一度の呼び出しでできるだけ処理し、子の失敗を終了コードに上げてくれ、標準に長く入っているのでどこでも動く。

最後にこの記事からもっとも安価な習慣を一つだけ残すなら個数の検査だ。find ... -printf 'x\n' | wc -l で数えた実際の個数とスクリプトが処理した個数を比べる二行があれば、上の四つの層の欠陥が運用ではなく試験の段階で表に出る。危険なファイル名 9 種を作ってこの二行を回すのに 1 分あれば足りる。

# find・xargs 安全な一括処理パターン — 貼って使うスニペット集

> 出典: braindetox.kr — find・xargs の空白と改行の罠
> 根拠: POSIX Issue 8（find・xargs）, GNU findutils 4.10.0, Bash 5.2 での実行検証
> このファイルをそのまま AI に貼り「うちのスクリプトをこの基準で直して」と書けば使えます。
> ⚠ 破壊的なコマンドは必ず新しい一時ディレクトリで先に試すこと。

## 0. スクリプトの先頭に置く三行

```bash
#!/usr/bin/env bash
set -Eeuo pipefail          # 失敗を飲み込まない
IFS=$'\n\t'                 # 既定の IFS から空白を外す
shopt -s nullglob           # 一致 0 件のときパターン文字列が残らないように
```

とくに `set -o pipefail` が効く。`find ... | while ...` の形では最後のコマンドの
終了コードしか残らないため、`find` が死んでも気づけないからである。

## 1. 削除

```bash
# 推奨 — 途中にシェルが入らない
find "$ROOT" -type f -name '*.tmp' -mtime +7 -delete

# 除外は -prune ではなく ! -path（-delete は -depth を入れて -prune を殺す）
find "$ROOT" -type f -name '*.tmp' ! -path "$ROOT/keep/*" -delete

# どうしても rm を使うとき
find "$ROOT" -type f -name '*.tmp' -exec rm -f -- {} +

# 空ディレクトリだけ整理（内側から）
find "$ROOT" -depth -type d -empty -delete
```

- [ ] `-delete` を条件の**あと**に置いた（前に置くと条件評価より先に消す）
- [ ] `$ROOT` が空のときを防いだ — `[ -n "${ROOT:-}" ] && [ "$ROOT" != "/" ]`
- [ ] `rm` に `--` を付けてハイフン始まりの名前を防御した
- [ ] 実行前に `-delete` を `-print` に替えて対象を目で見た

## 2. 移動・複製

```bash
# バッチで一度に
find "$SRC" -type f -name '*.log' -exec mv -t "$DST" -- {} +

# -t のない mv（BSD 系など）なら個別に実行
find "$SRC" -type f -name '*.log' -exec sh -c '
  for p do mv -- "$p" "$DST/"; done
' _ {} +

# ディレクトリ構造を保ったまま複製
find "$SRC" -type f -print0 |
  while IFS= read -r -d '' f; do
    rel=${f#"$SRC"/}
    mkdir -p -- "$DST/$(dirname -- "$rel")"
    cp -p -- "$f" "$DST/$rel"
  done
```

- [ ] `mv -t DEST SRC...` の順にした（バッチ最後の引数を宛先と誤認させない）
- [ ] 相対パスを作るとき `${f#"$SRC"/}` のように**パターンを引用**した
- [ ] `$DST` を `sh -c` の中で使うときは `export` するか引数で渡した

## 3. 名前の変更

```bash
# 拡張子の一括変更
find "$ROOT" -type f -name '*.jpeg' -exec sh -c '
  for p do mv -- "$p" "${p%.jpeg}.jpg"; done
' _ {} +

# 空白をアンダースコアに（ファイル名だけを変えディレクトリには触れない）
find "$ROOT" -depth -name '* *' -exec sh -c '
  for p do
    d=$(dirname -- "$p"); b=$(basename -- "$p")
    n=${b// /_}
    [ "$b" = "$n" ] || mv -n -- "$p" "$d/$n"
  done
' _ {} +
```

- [ ] `-depth` を付けた — 親を先に変えると子のパスが無効になる
- [ ] `mv -n` で既存ファイルの上書きを防いだ
- [ ] `${p%.jpeg}` のように**シェルのパラメータ展開**を使った（`sed` でパスを作らない）

## 4. 内容の置換

```bash
# 一致するファイルだけ選んでバッチで置換
find "$ROOT" -type f -name '*.conf' -exec grep -lZ -e 'OLD' -- {} + |
  xargs -0 -r sed -i -e 's/OLD/NEW/g' --

# バックアップを残しながら
find "$ROOT" -type f -name '*.conf' -exec sed -i.bak -e 's/OLD/NEW/g' -- {} +
```

- [ ] `grep -Z` と `xargs -0` でヌル区切りを繋いだ
- [ ] `xargs -r` で一致 0 件のとき `sed` が空の引数で回るのを防いだ
- [ ] `sed`・`grep` のうしろに `--` を付けた
- [ ] パターンを `-e` で渡し、ハイフン始まりのパターンをオプションと誤認させない

## 5. 圧縮・アーカイブ

```bash
# ★もっともよくある事故: xargs がバッチを分けると二つ目がアーカイブを上書きする
# 悪い: find ... -print0 | xargs -0 tar -cf out.tar
# よい — tar に一覧を直接読ませる
find "$ROOT" -type f -name '*.log' -print0 |
  tar --null --files-from=- -cf out.tar

# GNU tar でないなら: 一覧ファイルを作って一度だけ実行
find "$ROOT" -type f -name '*.log' -print0 > list.nul
tar --null --files-from=list.nul -cf out.tar

# zip は標準入力の一覧を受ける（-@ は改行区切りなので改行入りの名前に弱い）
find "$ROOT" -type f -print0 | xargs -0 -r zip -q out.zip --
```

- [ ] 「出力ファイルを新しく作る」コマンドを `xargs` のうしろに置かなかった
- [ ] どうしてもバッチにするなら**最初のバッチで生成、以降は追加**に分けた
- [ ] 一覧ファイルを使うときもヌル区切り（`-print0` と `--null`）を保った

## 6. 集計・個数

```bash
# 個数 — ファイル名ではなくファイルごとに一文字を数える
find "$ROOT" -type f -printf 'x\n' | wc -l
find "$ROOT" -type f -exec printf 'x\n' {} + | wc -l   # -printf がない環境

# 容量の合計
find "$ROOT" -type f -printf '%s\n' | awk '{s+=$1} END{print s+0}'

# 最新のファイル 1 個（改行入りの名前にも安全）
find "$ROOT" -type f -printf '%T@\t%p\0' | sort -zrn | head -zn1 | cut -zf2-

# 並べ替えはロケールを固定してこそ再現する
find "$ROOT" -type f -print0 | LC_ALL=C sort -z
```

- [ ] `find | wc -l` を使わなかった（改行入りの名前ひとつで数値が狂う）
- [ ] `sort`・`head`・`cut` に `-z`（ヌル区切り）を付けた
- [ ] 並べ替えに `LC_ALL=C` を固定した

## 7. 並列処理

```bash
find "$ROOT" -type f -print0 |
  xargs -0 -r -P "$(nproc)" -n 20 sh -c '
    for p do process_one -- "$p" || echo "FAILED: $p" >> "$FAILLOG"; done
  ' _
```

- [ ] `-P` と `-n` を**一緒に**使った（`-n` がないと一つのバッチが全部さらう）
- [ ] 失敗したパスは子プロセスが自分で記録する — `xargs` の終了コードは 123 に潰れる
- [ ] 子が同じファイルに書くなら追記（`>>`）にし、行が混ざってよいか確認した

## 8. 使わないパターン

| 使わない | 理由 |
|---|---|
| `find ... \| xargs cmd` | 空白・改行で引数が割れる |
| `for f in $(find ...)` | 単語分割とグロブ再展開が重なる |
| `ls \| grep pat` | `ls` は一行＝一ファイルを保証できない |
| `ls -1 \| while read f` | 同上。さらに `-r`・`IFS=` も抜けやすい |
| `-exec sh -c 'cmd {}' \;` | ファイル名がシェルのソースとして解釈される |
| `find ... \| wc -l` | 改行入りの名前が個数を水増しする |
| `rm $f` / `cp $f $d` | 引用のない変数は再び分割・展開される |
| `cmd *`（利用者が作ったファイル） | `-rf` のような名前がオプションになる |
| `xargs`（`-r` なし） | 入力が空でもコマンドが 1 回実行される |
| `-delete` と `-prune` | `-depth` が入り `-prune` が効かなくなる |

## 9. 検証手順 — 1 分

```bash
# ⚠ 必ず新しい一時ディレクトリで
LAB=$(mktemp -d) && cd "$LAB" || exit 1

# 危険なファイル名 9 種
touch -- 'space name.txt' $'newline\nname.txt' -dash.txt \
  "quote'name.txt" 'glob*name.txt' $'tab\tname.txt' \
  '  pad  .txt' 'semi;name.txt' 'dollar$name.txt'

REAL=$(find . -type f -printf 'x\n' | wc -l)     # 9 でなければならない
MINE=$(your_script_here | wc -l)                  # スクリプトが処理した数

echo "real=$REAL  script=$MINE"
[ "$REAL" = "$MINE" ] || echo "★ すでに壊れている"

# 各項目が実際に存在するか
find . -type f -print0 | while IFS= read -r -d '' f; do
  [ -e "$f" ] || echo "★ 存在しないパス: [$f]"
done
```

- [ ] 実際の個数と処理した個数が**一致する**
- [ ] すべての反復で対象パスが**存在する**
- [ ] ハイフンのファイル（`-dash.txt`）がオプションとして食われていない
- [ ] 改行入りのファイルが**1 件**として数えられた
- [ ] 前後に空白のある名前の長さが縮んでいない
- [ ] 試験が終わったら `cd / && rm -rf "$LAB"` で片付けた

## 10. 移植性

| 機能 | 標準への収載 | ないときの代替 |
|---|---|---|
| `-exec ... {} +` | POSIX（古くから） | —（もっとも安全な既定） |
| `-print0` | POSIX **Issue 8**（2024）で収載 | `-exec ... {} +` |
| `xargs -0` | POSIX **Issue 8** で収載 | `-exec ... {} +` |
| `xargs -r` | POSIX **Issue 8** で収載 | `-exec ... {} +`（空入力の問題なし） |
| `-printf` | GNU 拡張 | `-exec printf ... {} +` |
| `-delete` | GNU/BSD 拡張 | `-exec rm -f -- {} +` |
| `grep -Z` / `sort -z` | GNU 拡張 | 一覧ファイル経由 |
| `globstar` | bash 4 以降 | `find` |
