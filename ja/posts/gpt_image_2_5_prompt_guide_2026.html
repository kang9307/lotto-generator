1. 生成中心から保持中心の編集へ移行するパラダイムシフト

視覚生成人工知能の黎明期において、技術開発の主眼はもっぱら自然言語テキストから全く新しいキャンバスを生成する単発のText-to-Image能力に集中していました。描写語や画風指定を並べることで、モデルが潜在空間から結果を描き出す手法です。しかし、このアプローチは実際の商用プロダクトデザイン、UIプロトタイピング、Eコマースカタログ制作などの実務パイプラインに導入された瞬間、構造的限界に直面します。実務環境で求められるのは勝手な変形ではなく、承認済みの基準画像の構図や被写体のアイデンティティを維持しながら、特定の衣装や背景要素のみを正確に差し替える制御能力だからです。

編集指示が意図しない部分まで変更してしまう問題は、パイプラインにおける信頼性の課題となります。OpenAIのGPT Image 2.5プロンプトガイドは、まさにこの課題に対する実践的な指針を示しています。同ガイドは編集指示において「change only X」と保持する詳細リストを併記するよう案内しています。

原文は編集において変更する対象1点と保持するもの（アイデンティティ、幾何学的形状、レイアウト、照明、ラベル）を分けて記述するよう案内しています。また原文は反復編集が保持しようとしていた詳細を変更する可能性があると明記しています（第7節）。なお、原文にはgpt-image-1.5が2026年12月1日、gpt-image-1が2026年10月23日に提供終了予定である旨の案内があります。

2. FlareとSunburstの設計特性とモデル選択基準

OpenAIの公式仕様書では、GPT Image 2.5世代において利用可能な2つのモデル識別子としてgpt-image-2.5-flareとgpt-image-2.5-sunburstが規定されています。両モデルは同一のプロンプト構文やパラメータ仕様を共有していますが、最適化の方向性が異なります。

  • GPT Image 2.5 Flare: 原文は「small model, optimized for speed, with image quality comparable to GPT Image 2」と説明し、日常的な高速・高品質生成に選定するよう案内しています。
  • GPT Image 2.5 Sunburst: 原文は「base model, optimized for quality, with higher image quality than GPT Image 2」と説明し、編集精度が最も重視されるワークフローに選定するよう案内しています。

公式文書は実務移行における具体的な選択原則を提示しています。GPT Image 2がすでに品質要件を満たしている場合はFlareから開始して遅延時間の改善をテストし、複雑なユースケースでGPT Image 2が不十分な場合はSunburstから開始せよ。最初の比較ではプロンプト・参照・サイズ・出力形式と、明示的に選択したquality値をそのまま維持すべきです。

原文は両モデルともに画像生成、編集、透過背景をサポートしていると明記しています。

3. 公式パラメータ体系とAPI制御範囲

GPT Image 2.5では、プロンプトテキストとは別にAPIリクエストペイロード上で直接指定する4つの主要パラメータが提供されています。これらはインフラストラクチャレベルでレンダリング挙動を決定づける境界条件となります。

表 1: GPT Image 2.5公式APIパラメータおよび許容値一覧
パラメータ名 公式許容値 デフォルト値および仕様特性 実務運用における考慮事項
model gpt-image-2.5-flare, gpt-image-2.5-sunburst 原文に記載のモデル名。GPT Image 1、1.5、2も文書で言及されている 原文は、日常的な高速・高品質の生成にはFlare、編集精度が最も重要なワークフローにはSunburstを選ぶよう案内している。
quality auto, low, medium, high, xhigh, max デフォルトはauto 原文: quality: lowは迅速な下書き用。xhigh・maxは遅延予算内で未達の品質要件を改善する場合にのみ使用する。
size autoまたはカスタムWIDTHxHEIGHT 代表例: 1024x1024, 1536x1024, 1024x1536, 2048x2048, 2048x1152, 3840x2160, 2160x3840 任意解像度を指定する場合、以下の4大サイズ条件を遵守する必要がある。
background auto, opaque, transparent 原文はデフォルト値を明示していない 透過背景はbackground: transparentとoutput_formatをpngまたはwebpで指定する。output_compressionはjpeg・webpのみ適用される（0–100%）。

原文は、より高いquality設定がすべてのプロンプトでより良い結果を保証するわけではないと明記し、迅速な下書きにはlowを使用するよう指示しています。xhighやmaxは遅延予算内で未達の品質要件を改善する場合にのみ使用するよう案内しています。

透過背景が必要な場合はbackground: "transparent"を指定し、pngまたはwebpで受け取るというのが原文の案内です。

4. 解像度制約の4大原則と算術的境界条件

GPT Image 2.5 APIは、標準的なプリセット以外にもWIDTHxHEIGHT形式による任意の矩形サイズ出力をサポートしています。原文はカスタムサイズをWIDTHxHEIGHT文字列として受け付け、以下の条件を課しています。

  • 単一辺の上限: 両辺ともに3,840ピクセルを超えることはできない。
  • 16ピクセル倍数: 幅と高さはそれぞれ16の倍数でなければならない。
  • アスペクト比: 1:3から3:1の範囲内でなければならない。
  • 総ピクセル数: 655,360以上8,294,400以下。

公式ドキュメントは総ピクセル数が3,686,400（2560x1440）を超える出力を実験的（experimental）段階に分類しています。これらの制約に基づき、有効な寸法と拒否される寸法の具体例を算術的に整理した結果を以下に示します。

表 2: GPT Image 2.5のサイズ制約4原則および算術計算例（※計算例は本稿による算術導出結果）
制約規則 公式仕様基準 適合解像度の計算例 不適合解像度と拒否理由
単一辺の最大上限 各辺 ≤ 3,840px 3840x2160 (幅3,840pxで上限に正確に合致) 4000x2000 (幅4,000pxで単一辺の上限3,840pxを超過)
16ピクセルの倍数 幅・高さ mod 16 = 0 1536x1024 (1536=16×96, 1024=16×64で双方合致) 1530x1020 (1530/16=95.625で16の倍数条件に違反)
アスペクト比限度 長辺 / 短辺 ≤ 3.0 3072x1024 (比率が正確に3.0:1で許容範囲内) 3200x1000 (比率3.2:1で最大許容比率3:1を超過)
総ピクセル数範囲 655,360px 〜 8,294,400px 3840x2160 (計8,294,400pxで上限に合致), 1024x1024 (計1,048,576px) 640x640 (計409,600pxで最小下限655,360pxに未達)

640x640は16の倍数であるが総ピクセル数が409,600であり、上記の総ピクセル条件（655,360以上）に満たない。本稿の提案として、上記4条件をクライアント側で事前に検査すればサイズエラーをリクエスト前に検出できる。

5. 変更と制約の分離 — ラベルセクションプロンプトエンジニアリング

OpenAI公式ドキュメントは、複雑な指示を整理する手法として、長大な散文形式ではなく明示的なラベル構造（labeled sections）の採用を案内しています。基本構造として提唱されているのは、場面（Scene）、主題（Subject）、詳細（Details）、制約（Constraints）の4層構造です。

  • 主題と用途の明確な定義: 商品写真、広告、図解など完成品の用途を明記します。
  • 観察可能な物理的詳細の記述: 材質、照明、色彩、視覚メディアを直接指定します。
  • 描画文字の完全な引用指定: 画像内に描画する文字は引用符で囲み、配置位置やタイポグラフィを明記します。余計な文字を要求せず、出力の綴りと可読性を確認します。
  • 除外事項と制約の分離: 不要なテキスト、ロゴ、透かしなどの除外対象を制約セクションとして独立させます。

以下のプロンプト例は、OpenAI公式ガイドの構造化方針に準拠し、実務的なセクション分割手法を提示するために本稿独自に作成したサンプルです。

[Scene]: A bright, modern Nordic kitchen counter with soft morning daylight entering from the left window.
[Subject]: A compact matte-black espresso coffee machine placed on a light oak wood surface.
[Details]: Brushed metal drip tray, visible steam wand texture, warm ambient reflections, shallow depth of field focusing on the portafilter.
[Text Requirement]: The word "AURA" engraved on the front panel in clean minimalist sans-serif capitals, rendered exactly once.
[Constraints]: No human hands or figures, no commercial brand watermarks, no decorative clutter, clean photorealistic finish.

原文は複雑な要求を場面・主題・詳細・制約に分けたラベルセクションで整理するよう案内しています。ラベル名および例示ブロックの具体的文言は本稿の構成です。

6. 実務編集ワークフロー — 保持リストの策定と適用手法

GPT Image 2.5の画像編集API（client.images.edit）において、公式ドキュメントが最も強調している原則は以下の構文指示です。

Say "change only X" and list the details to preserve, such as identity, geometry, layout, lighting, or labels.

つまり、指示文の冒頭で「Xのみを変更せよ」と明言した上で、絶対に改変してはならない保持対象リスト（Preserve List）を直ちに列挙するアプローチです。公式ガイドが挙げる5大保持項目は以下の通りです。

  • アイデンティティ（Identity）: 人物の場合、顔立ち、目元、肌の質感、表情などを保持対象として固定すること。
  • 幾何学的形状（Geometry）: 既存の製品や構造物の立体的なプロポーションや輪郭線を維持すること。
  • レイアウト（Layout）: 画面全体における被写体の位置関係、画角、余白比率を保持すること。
  • 照明（Lighting）: 原本画像に存在する主光線の向き、色温度、影の落ち方を一致させること。
  • ラベルと記号（Labels）: 原本に含まれる説明文字、ブランド表記、矢印などの位置やフォントを保護すること。

局所的な編集作業では、これらに加えて彩度、コントラスト、矢印、カメラ角度、周辺オブジェクトの位置も固定要素として指定します。また、複数の入力画像を利用する場合は、各画像に番号を付与して被写体、スタイル、衣装、背景などの役割を割り当てる必要があります。

以下は、人物のアイデンティティを保護しながら衣装のみを差し替えるために、本稿の指針に基づいて構成した実務プロンプトの例です。

[Task]: Edit the input image to change only the clothing of the subject.
[Change Target]: Replace the current gray knit sweater with the dark-navy waterproof trench coat provided in reference image 2.
[Preserve List - Critical]:
- Identity: Keep the subject's face, facial features, eyes, smile, skin texture, and hairstyle completely unchanged.
- Geometry: Retain the existing upper body posture, shoulder angle, and arm placement.
- Lighting: Match the soft golden-hour directional sunlight and shadows of the original photo.
- Layout: Do not alter the urban street background, depth of field, or camera framing.
[Constraints]: Coat must drape naturally according to the body geometry, realistic fabric creases, no added accessories, no brand logos.

原文は編集において「change only X」と保持リストを併記し、複数の入力画像がある場合は各画像に番号と役割（被写体、スタイル、衣装、背景）を指定するよう案内しています。上記のプロンプトはその案内に従った本稿の例示です。

7. 制約明示の代償と反復コスト — 残るドリフトと対応

しかし、保持リストを詳細に記述するプロンプトエンジニアリングにも固有の代償と技術的限界が存在します。

第一に、制約が増加するコスト。本稿の推測としては、保持項目を多く記述するほどプロンプトが長くなり、核心となる変更指示が埋もれてしまう可能性があります。原文がこの現象を扱っているわけではありません。

第二に、反復編集におけるドリフト。原文は「Repeated edits can still change details you intended to preserve」と明記しています。公式文書はこの問題を認めた上で、次のように対処方針を示しています。

Restate critical constraints if the result drifts. If a region must remain pixel-identical, composite the approved edit into the original image instead of relying on prompting alone.

反復編集の過程で出力が逸脱し始めた場合は重要制約を改めて強調し直す必要があります。そして、特定領域の完全なピクセル的一致が要求される場合は、プロンプトのみに頼るのではなく、承認された変更領域を原本画像に直接マスク合成（compositing）するハイブリッド手法を採用すべきであると公式に結論づけています。

8. 検証手順 — 同一画像に対する保持プロンプト比較評価手法

実務において保持リストに基づくプロンプトが及ぼす影響を把握したい場合は、A/B比較によって確認することができます。本稿が提案する検証手順は以下の通りです。

  1. 基準アセットの選定と固定: 人物写真、図解、透過背景の商品写真など、明確な保持対象を含むベース画像を1点ずつ準備します。
  2. 対照群A（単純変更指示）の実行: 同一のモデルおよびパラメータ（size、quality）環境下で、変更点のみを記述したプロンプト（例: 「ジャケットをベージュのレザージャケットに変更せよ」）を用いて編集APIを呼び出します。
  3. 実験群B（保持リスト分離指示）の実行: 同一環境下で、ラベルセクションと保持リストを明記したプロンプト（例: 「ジャケットのみを変更せよ。顔、髪型、照明、背景を保持せよ」）を用いて編集APIを呼び出します。
  4. 4大視覚整合性指標による評価:
    • アイデンティティ保持率: 原本と編集後画像における被写体の顔立ちや特徴の一致度を検証。
    • 環境整合性: 背景テクスチャ、照明の照射角、被写界深度が原本と整合しているか確認。
    • 境界アーティファクト: 変更されたオブジェクトの輪郭線に不自然なにじみや破綻がないか検査。
    • 意図しない変異の発生件数: 指示していない装飾の追加や色味のシフトが発生していないかを記録。

本節の手順は原文にあるものではなく本稿の提案であり、本稿はこの比較を直接実施したわけではありません。結果は各自の画像および設定で確認する必要があります。

9. 確認できなかった事項

本稿の技術分析はOpenAIの公式APIプロンプトガイドに基づいていますが、公式文書において言及されておらず確認できなかった事項は以下の通りです。

  • 公式プロンプトガイド内にはGPT Image 2.5 FlareおよびSunburstのトークン単位または生成1枚あたりの具体的なAPI利用料金体系が原文に記載されておらず確認できなかった。正確なコスト試算にはプラットフォームの価格一覧を別途照合する必要がある。
  • FlareおよびSunburstの平均応答時間（latency）数値: 原文は定量的な数値を提示していない。
  • 複数回の連続編集を繰り返した際、平均して何回目の反復で被写体のドリフトが許容限界値を超えるかについての統計的な耐久サイクル数は原文で確認できなかった。
