Hexana - JetBrains' WebAssembly Binary Analysis Toolkit, What Gap It Fills

Now that WebAssembly has spread past the browser, here's what a tool that opens .wasm inside the IDE is actually filling in

Jul 16, 2026 Dev & Infra

Introduction: Why WebAssembly Now Needs Binary Analysis Tools

As of July 2026, WebAssembly (wasm) is no longer a JavaScript sidekick confined to browser tabs. It's become a deployment unit for edge compute, plugin systems, server-side runtimes, and even IDE extensions themselves. That spread inevitably raises a question: what's actually inside this .wasm file? JetBrains' new Hexana - an IntelliJ plugin plus a VS Code extension - is a direct answer to that question.

Rather than restating the release notes, this piece works through why WebAssembly now demands binary analysis tooling, exactly what gap Hexana fills in the existing tool landscape, and what it means that JetBrains ships one Kotlin Multiplatform core into two IDEs at once.

1. What .wasm Actually Is - Stack-Machine Bytecode and WAT

1.1 A binary instruction format for a stack machine

WebAssembly is a binary instruction format for a stack-based virtual machine. Whatever the source language - C/C++, Rust, Kotlin - compilation produces structured binary bytecode organized into type, import, function, table, memory, global, export, code, and data sections. Execution pushes and pops values on a stack rather than using registers, and only structured control flow (blocks, loops, branches) is allowed instead of arbitrary jumps - a design choice that narrows the room for jump-based obfuscation. That structure is what lets wasm run predictably inside a sandbox at close to native speed.

1.2 The human-readable counterpart: WAT

That bytecode isn't pleasant to read or edit by hand, so a human-readable counterpart - the WebAssembly Text Format (WAT), built on S-expressions - is defined alongside it. That's also why conversions like wat2wasm/wasm2wat exist as a standard part of the toolchain. The catch is that in practice this conversion tends to stay a one-off "dump the whole file to text" step. Picking out a single function, editing it in place and saving it back, or diffing two versions side by side, doesn't flow naturally out of a CLI converter alone.

2. The Existing Tool Landscape and the Gap Hexana Fills

2.1 wabt and wasm-tools - CLI-first, low-level

wabt (the WebAssembly Binary Toolkit) is a suite of C/C++ CLI tools: wat2wasm, wasm2wat, wasm-objdump, wasm-interp, wasm2c, wasm-strip, wasm-validate, wast2json. wasm-tools plays the same role in the Rust ecosystem as a low-level manipulation library and CLI. Both are accurate and pipeline-friendly, but they're fundamentally batch tools - run one command, get text output. They weren't built for jumping across sections interactively, re-validating right after editing a single function, or visually comparing the structural difference between two binaries.

2.2 Chrome DevTools - debugging locked inside the browser

Chrome DevTools lets you set breakpoints and debug wasm at the source level when DWARF debug info is present. But that's tied to the context of a page actually running in a browser tab. It's no help for modules running in a server-side runtime (Wasmtime, WasmEdge), wasm shipped inside an edge function or a plugin system, or cases where you just want to statically inspect structure without running anything.

2.3 Where Hexana sits - a structured document inside the IDE

Hexana opens a .wasm file not as a blob of compiled text, but as a structured, navigable document inside the IDE: a section browser, imports/exports, function types, code bodies, GC types, and Component Model interfaces (WIT), all laid out as a tree. The JetBrains plugin (v0.13, for the IntelliJ IDEA 2025.2+ family) adds an editable WAT view with row-level editing, WIT language support, an integrated MCP server, and multi-architecture disassembly (x86, x86-64, ARM, AArch64, RISC-V 32/64) bundled as a Rust/Wasm module with no separate toolchain to install. The VS Code extension (v0.6.0, also working in Cursor and VSCodium) plays the same role with a Compose-for-Web custom editor, a virtual-scrolling hex viewer, and 11 structural-analysis tabs. Both versions can run and experimentally debug (breakpoints, DWARF source mapping) against Wasmtime, WAMR, and GraalVM, and both ship a diff editor for comparing two .wasm modules side by side - a Size Impact tab showing per-section and per-function byte deltas, and an Entities tab that classifies every entity as added, removed, modified, or moved.

In short: the workflow wabt and wasm-tools can't offer - living inside the IDE and connecting exploration, editing, debugging, and comparison into one loop - is exactly the gap Hexana fills.

3. One Kotlin Multiplatform Core, Two IDEs - What the Multi-IDE Strategy Means

3.1 What's actually shared

Hexana states that a single Kotlin Multiplatform codebase is used by both the JetBrains plugin and the VS Code extension. In other words, the complex logic - .wasm parsing, section interpretation, support for newer proposals like the Component Model, GC, SIMD, and threading, and the disassembly integration - lives in exactly one place, with an IntelliJ Platform UI layer and a VS Code extension UI layer each sitting on top of it.

3.2 Why this strategy, and why now

This is the developer-tooling version of the "shared core, native shell" pattern JetBrains has been pushing through 2026 - the same split between a shared library module and platform-specific app modules that shows up in the new default Kotlin Multiplatform project structure. Practically, it removes the cost of building and maintaining a complex binary-format parser twice: once against the IntelliJ Platform API and once against the VS Code extension API. Strategically, it's bigger than that. A large share of wasm and Rust developers live in VS Code (or forks like Cursor), while JVM and enterprise developers live in the IntelliJ family. Shipping to both from day one, instead of picking a side, reads as a signal that JetBrains treats the VS Code extension as a first-class investment, not a port.

4. Practical Use - Reverse Engineering, Performance, Security, Optimization

4.1 Reverse engineering

When a wasm module ships without source - a recompiled legacy game, a third-party SDK, a closed binary - the section browser and the editable WAT view are the natural starting point. The recompilation and decompilation work behind this blog's own Pokemon Emerald at 100k FPS in the browser project is itself a good illustration of why this kind of structural analysis tool matters.

4.2 Performance analysis and binary diets

When a bundle grows after a dependency bump or a build-config change, the Size Impact tab points straight at per-section and per-function byte deltas - which function's code body ballooned, which export is dead weight - instead of eyeballing wasm-objdump output by hand.

4.3 Security auditing

Whether a wasm module pulled in as a supply-chain dependency carries unexpected imports or exports, or whether something was quietly injected between two releases, is exactly what the Entities tab's added/removed/modified/moved classification is built to catch. The same sandboxing that makes wasm attractive for running untrusted code is precisely why structurally verifying what's inside it matters just as much.

4.4 Verifying wasm optimization

After running something like wasm-opt, a diff view lets you confirm right away whether DWARF debug info survived with its source mapping intact, and exactly which section actually shrank and by how much. Whether debug info survives or not can make or break how fast you can triage a production incident.

5. The 2026 WASM Ecosystem Context - WASI and the Component Model

5.1 Where WASI stands

WASI (the WebAssembly System Interface) defines the standard way a wasm module reaches system resources - files, networking, the clock. WASI 0.2 (Preview 2) stabilized in January 2024 and turned the Component Model into a real API target; as of July 2026, WASI 0.3 is available as a preview in Wasmtime 37 and later, aiming for native async I/O without callback-based workarounds. There's also talk of a long-term WASI 1.0 standard targeted for 2026, though that timeline isn't fixed (based on limited industry reporting).

5.2 The Component Model and WIT

The Component Model is the standard for assembling wasm modules compiled from different languages into composable components, and WIT (WebAssembly Interface Types) is the language used to describe those interfaces. Between 2025 and 2026, this axis is widely described as having moved from "experimental demo" to "real multi-language, multi-runtime cloud-native systems." That Hexana explicitly targets the Component Model and WIT alongside GC, SIMD, and threading says something: this tool is built for wasm's current frontier, not the legacy MVP era. Industry surveys report that more than 70% of developers already use or are evaluating wasm outside the browser, and that a meaningful share of new enterprise projects ship at least one wasm module. Edge functions, plugin systems, and untrusted-code execution are consistently named as the areas where wasm has genuinely landed.

6. Limitations and Caveats

Hexana is still early (plugin v0.13, extension v0.6.0), and its own documentation labels the debugging features "experimental." Rather than leaning on it as the primary tool for production troubleshooting, it's safer to run it alongside proven CLIs like wasm-objdump and wasm-tools while you build confidence. Bundling the disassembly backend as a Rust/Wasm module makes installation easy, but the backend's own accuracy and instruction-set coverage still deserve independent verification. And because it touches standards that are still moving - WASI 0.3, WIT - its parsing results will need to keep pace as those specs evolve.

Conclusion - Three Things to Check Today

Hexana turns wasm from a blob of text out of a CLI converter into a structured document inside the IDE. It fills the half-gap wabt and wasm-tools leave at the low level and the half-gap Chrome DevTools leaves inside the browser, closing both with IDE integration, diffing, and multi-architecture disassembly. And shipping one Kotlin Multiplatform core into both the IntelliJ family and VS Code at once reads as a practical choice not to lock developer tooling into a single IDE ecosystem.

1) If you're already working with wasm modules - reverse engineering, performance, or security - install Hexana as a companion tool and run it alongside your existing CLI workflow. 2) Treat debugging as experimental for now and keep cross-checking against proven tools. 3) If your project touches the moving frontier of the Component Model, WIT, or WASI 0.3, it's worth watching Hexana simply because tools that explicitly target that frontier are still rare.
