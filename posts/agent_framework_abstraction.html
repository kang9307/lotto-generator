에이전트를 코드에서 무엇으로 표현할 것인가 - 클래스·그래프·설정 파일이 각각 가리는 것

추상화를 고르는 순간 디버깅과 재개와 이식 비용이 같이 정해진다

2026-09-01 개발/인프라

에이전트를 만들 때 가장 먼저 고르는 것은 모델도 도구도 아니다. 에이전트를 코드에서 무엇으로 부를 것인가다. 클래스인가, 그래프의 노드인가, 설정 파일의 한 항목인가, 프롬프트 파일 한 장인가. 첫날에는 문법 취향처럼 보이고 두 달 뒤에 청구서로 돌아온다.

청구서의 항목은 정해져 있다. 모델에 실제로 무엇이 갔는지 확인하는 시간, 끊긴 작업을 이어 붙일 수 있는지, 로그를 읽으려고 프레임워크 문서를 같이 열어야 하는지, 옮길 때 무엇을 버리는지. 추상화는 이 넷을 조용히 미리 정해 둔다. 계기가 된 저장소는 네 갈래 중 하나를 가장 선명하게 밀어붙인 사례라 출발점으로 좋을 뿐, 그 프로젝트를 소개하는 것이 목적은 아니다.

이 글은 여러 에이전트 프레임워크의 설계 방식을 비교하지만 어느 쪽이 낫다는 평가는 하지 않는다. 인용한 설계 사실은 각 프로젝트의 공식 문서와 저장소에서 확인한 2026년 9월 초 시점의 것이며, 이 분야는 판올림 사이의 변경이 잦다.

계기 - 에이전트가 파이썬 클래스가 될 때

NVIDIA-NeMo 조직의 labs-OO-Agents 저장소는 이름 그대로다. 필드가 상태이고, 메서드가 능력이고, 독스트링이 프롬프트이고, 타입 애너테이션이 계약이다. 본문이 ... 인 메서드는 실행 시점에 모델이 채우고, 코드가 있는 메서드는 결정적인 파이썬으로 남는다.

from nooa import Agent

class SupportAgent(Agent):
    """You are a support agent."""
    order_db: OrderDB

    def is_refund_eligible(self, order: Order) -> bool:
        return order.delivered and order.days_since_delivery <= 30

    async def triage(self, message: str, order: Order) -> Ticket:
        """Create a typed support ticket."""
        ...

이 열두 줄 안에 보통 세 군데에 나뉘어 있던 것이 모여 있다. 시스템 프롬프트, 도구 스키마, 콜백이다. 메서드 이름과 인자와 독스트링이 곧 프롬프트라서 독스트링을 고치면 지시가 바뀐다. 모델은 self 와 임포트된 모듈에 접근하는 주피터 스타일 REPL 에서 파이썬을 써서 행동한다.

  • 저장소는 2026년 7월 20일 생성. 8월 31일 시점에 별 1,955개·포크 266개·열린 이슈 77개다. 6주 만의 숫자다
  • PyPI 패키지 nooa 의 공개 버전은 7월 30일 0.0.7 부터 8월 18일 0.0.9 까지다
  • 라이선스는 Apache-2.0, LICENSE 의 저작권 표시는 NVIDIA CORPORATION & AFFILIATES. 개인 실험이 아니라 사내 랩 산출물이다
  • 문서는 스스로를 연구용 소프트웨어라고 적는다. AST 검사와 모듈 차단 목록은 겹겹 방어의 한 겹일 뿐 격리 경계가 아니며, 격리는 컨테이너나 VM 같은 OS 수준이라고 못 박는다
  • 같은 이름의 논문이 7월 22일 arXiv 에 올라와 있다. 저자 15명, 여섯 개념으로 타입 있는 입출력·살아 있는 객체 참조 전달·행동으로서의 코드·루프 설계·명시적 객체 상태·모델이 부르는 하니스 API 를 든다

여기까지가 저장소와 논문 초록에서 직접 확인되는 것이다. 이 글이 관심 있는 것은 그다음이다. 왜 하필 클래스인가, 클래스로 부르면 여섯 달 뒤에 무엇이 정해져 있는가. 프레임워크 하나를 뜯어보는 작업은 TypeScript 샌드박스 프레임워크를 다룬 글에서 했으니, 여기서는 표현 방식 자체를 본다.

표현 방식은 네 갈래로 모인다

지금 쓸 수 있는 것들을 늘어놓으면 표현 방식은 대체로 네 갈래로 모인다. 각각이 자연스럽게 만드는 코드 모양이 다르고, 그래서 어색하게 만드는 것도 다르다.

갈래에이전트는 무엇인가자연스러워지는 코드어색해지는 것
객체클래스 인스턴스. 필드가 상태, 메서드가 능력상속으로 공통 동작 재사용, 타입으로 계약 고정흐름을 한 장의 그림으로 보여 주기
그래프·상태기계노드와 엣지. 상태가 그래프를 흘러 다닌다분기·병렬·중단점을 구조로 표현에이전트의 정체성이 노드로 흩어짐
선언형 설정YAML·JSON 항목. 역할·목표·도구의 나열개발자가 아닌 사람도 고침, 변경 이력이 짧음조건부 로직. 결국 코드로 탈출한다
프롬프트 파일마크다운 한 장. 본문이 곧 시스템 프롬프트프롬프트를 그대로 읽고 diff 로 검토타입·재사용·조립

실제 구현이 넷 중 하나에 순수하게 머무는 경우는 드물다. 다만 주된 갈래는 문서 첫 화면에서 보인다. 첫 예제가 클래스면 객체 쪽이고, 노드를 등록하는 코드면 그래프 쪽이다.

  • Pydantic AI 의 Agent 는 의존성 타입과 출력 타입에 대해 제네릭한 클래스다. 문서는 Agent[Foobar, list[str]] 같은 표기를 예로 든다
  • OpenAI Agents SDK 의 Agent 는 이름·지시문·모델·도구·핸드오프·출력 타입을 필드로 갖고 컨텍스트 타입에 제네릭이다. 지시문 자리에 함수를 넣을 수도 있다
  • LangGraph 는 사용자가 정의한 State 로 매개변수화된 StateGraph 가 중심이다. 노드는 상태를 받아 갱신분을 돌려주고, 엣지는 다음 노드를 정한다
  • CrewAI 는 역할·목표·배경 이야기로 에이전트를 규정한다. 새 프로젝트는 agents/<이름>.jsonc 를 쓰는 설정 우선 방식이고, 예전 config/agents.yaml 도 지원된다
  • AutoGen 코어 문서는 에이전트를 메시지로 통신하고 자기 상태를 유지하며 받은 메시지에 반응해 행동하는 소프트웨어 개체로 정의한다. 메시지가 유일한 접점이다
  • Claude Code 의 서브에이전트는 YAML 프런트매터가 붙은 마크다운 파일이고, 본문이 그대로 시스템 프롬프트다
---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.

앞의 클래스 예시와 이 파일이 스펙트럼의 양 끝이다. 한쪽은 타입과 상속을 최대한 끌어다 쓰고, 다른 쪽은 텍스트 파일 한 장으로 끝낸다. 어디가 옳으냐가 아니라 각 지점이 치르는 대가가 다르다는 것이 요점이다.

객체로 감쌀 때 얻는 것

객체지향으로 감싸는 쪽의 이점은 우아함이 아니라 도구가 대신 해 주는 일에서 나온다.

  • 편집기가 안다. 자동완성이 되고 인자 이름 오타가 저장 시점에 잡히며 이름 바꾸기가 호출부까지 따라간다. 문자열 상수로만 있으면 어느 것도 되지 않는다
  • 타입이 경계를 고정한다. 출력 타입을 선언해 두면 모델이 이상한 것을 뱉었을 때 그 자리에서 걸린다. 세 단계 위에서 엉뚱하게 터지지 않는다
  • 공통 동작이 한 곳에 모인다. 재시도, 예산 상한, 감사 로그를 기반 클래스에 한 번 쓰면 하위 전부에 걸린다
  • 테스트 대역을 끼워 넣기 쉽다. 모델 호출 메서드만 덮어쓰면 나머지를 모델 없이 시험할 수 있다. CI 에서 돌릴 수 있느냐가 여기서 갈린다
  • 결정적 코드와 모델 판단이 한 파일에 있다. 환불 자격 판정은 파이썬으로, 문의 분류는 모델에 맡기는 식이다. 흩어지면 책임 경계가 흐려진다

마지막 항목이 가장 크다. 에이전트 코드가 오래 살아남는지는 규칙으로 쓸 수 있는 것을 모델에 맡기지 않았느냐에 달려 있다. 배송 30일 이내인지 판정하는 일을 모델에 물으면 대부분 맞히지만 가끔 틀리고, 그 가끔이 환불 사고가 된다. 본문이 있으면 결정적이고 ... 이면 모델의 몫이라는 규칙은 그 경계선을 문법에 새겨 둔다.

객체로 감쌀 때 가려지는 것

대가는 한 곳에 집중된다. 모델에 실제로 나가는 프롬프트가 소스 어디에도 통째로 적혀 있지 않게 된다는 것이다. 독스트링과 시그니처와 기반 클래스가 덧붙인 조각과 실행 시점 주입이 합쳐진 결과물이라, 최종 형태는 계산되어야 알 수 있다.

이 문제는 상속 깊이에 비례해 커진다. 기반 클래스에 공통 지시문 한 줄을 넣는 것은 재사용이지만, 세 단계 아래 클래스를 읽는 사람은 그 줄이 붙어 있다는 사실 자체를 모른다. 도구 목록도 같다. 데코레이터로 등록되고 믹스인으로 합쳐지고 실행 시점에 걸러지면, 도구가 몇 개 붙어 있는지를 소스만 읽어서는 셀 수 없다.

Anthropic 의 에이전트 설계 글도 같은 자리를 지적한다. 프레임워크가 밑에 깔린 프롬프트와 응답을 가리는 층을 추가해 디버깅을 어렵게 만드는 경우가 많고, 밑에서 무슨 일이 일어나는지에 대한 잘못된 가정이 흔한 오류의 원인이라는 것이다. 특정 제품이 아니라 층을 쌓는 행위 일반에 대한 지적이다.

  • 가려짐이 위험해지는 순간은 사고 30분 뒤다. 그때 필요한 것은 모델이 받은 텍스트 전문이다
  • 그래서 첫날에 확인할 것은 기능 목록이 아니라 최종 페이로드를 파일로 떨구는 방법이다. 한 줄로 되면 상속이 깊어도 견딜 만하다
  • 기본 추적 여부도 선택 기준이다. 앞서 본 저장소는 모든 호출이 기본 추적된다고 밝힌다. 켜져 있음과 켤 수 있음은 다르다
  • 상속을 얕게 유지하는 것도 방법이다. 두 단계까지는 읽히고 네 단계부터는 안 읽힌다
  • 공통 프롬프트 조각을 클래스 안 문자열로 묻는 대신 파일로 빼서 이름으로 참조하면 검색이 된다

그래프가 보여 주는 것과 흩뜨리는 것

그래프 쪽의 강점은 흐름이 자료구조가 된다는 데 있다. 자료구조이면 그릴 수 있고, 검사할 수 있고, 멈추는 규칙을 구조로 정의할 수 있다. 명령형 함수 안에 if 로 흩어진 분기는 셋 중 어느 것도 되지 않는다.

LangGraph 문서는 이 구조를 간결하게 정리한다. 노드가 일을 하고 엣지가 다음을 알려 준다. 상태 스키마는 모든 노드와 엣지의 입력 스키마가 되고, 각 키에는 리듀서가 붙는다. 리듀서를 명시하지 않으면 그 키의 갱신은 모두 덮어쓰기다. 이 기본값이 미묘한 버그의 단골 자리다. 누적돼야 할 대화 기록을 덮어쓰기로 두면 마지막 것만 남는데, 증상이 맥락 상실로 나타나 프롬프트 문제로 오인된다.

그래프가 치르는 대가는 정체성이다. 한 에이전트가 무엇을 하는지 보려면 노드와 엣지를 따라가야 한다. 흐름이 복잡할수록 그래프가 이기고, 에이전트 하나하나가 두툼할수록 객체가 이긴다. 몇 개로 쪼갤지는 서브에이전트 개수를 다룬 글에 있다.

  • 그래프는 흐름을 코드가 쥐는 쪽으로 기운다. 노드를 미리 등록해야 하므로 없던 경로가 생기기 어렵다
  • 그 성질이 재현성에는 유리하고 예상 밖 입력에는 불리하다. 정의되지 않은 상황도 정의된 경로로 흘러가 버린다
  • 그래프 정의는 프레임워크 고유 어휘가 많아 옮기기 가장 어려운 자산에 속한다
  • 반대로 중단점을 구조로 정의할 수 있다는 것은 그래프만의 이점이다. 사람 승인이 끼어드는 흐름에서 크다
  • 리듀서를 명시하는 습관은 값싸고 효과가 크다. 덮어쓰기가 맞는 키에도 적어 두면 의도인지 방치인지 구분된다

선언형 설정의 천장

설정 파일 방식의 장점은 사회적인 데 있다. 개발자가 아닌 사람이 열어 읽고 고칠 수 있고, 변경 이력이 짧고 명확해서 리뷰에서 다투기 쉽다. 프롬프트 문구를 기획자가 직접 고치는 조직이라면 이 장점이 다른 모든 것을 압도한다.

천장은 조건부에서 온다. 이 경우에만 저 도구를 쓴다는 요구가 들어오는 순간 설정 언어는 프로그래밍 언어를 흉내내기 시작한다. 그다음 갈림길은 둘뿐이다. 표현식 문법을 설정 안에 넣거나, 코드로 나가는 탈출구를 뚫거나. 앞은 디버거도 타입 검사기도 없는 작은 언어를 새로 만드는 일이고, 뒤는 설정과 코드를 둘 다 읽어야 전체가 보이는 상태다.

  • 설정에 남기기 좋은 것 — 사람이 자주 조정하고 분기가 없는 값. 역할 설명, 온도, 모델 이름, 도구 허용 목록
  • 코드로 보내야 하는 것 — 조건, 반복, 계산, 외부 상태 조회. 설정 안에서 흉내내면 반드시 읽기 어려워진다
  • 같은 개념이 두 곳에 나뉜 상태가 가장 나쁘다. 도구 목록 절반이 파일에, 절반이 데코레이터에 있으면 전체를 아는 사람이 없다
  • 설정 우선 방식이 코드 쪽 진입로를 남겨 두는 것은 이 천장을 아는 설계다

프롬프트 파일 - 가장 얇은 추상화

마크다운 한 장이 곧 에이전트인 방식은 앞의 문제 하나를 아예 없앤다. 무엇이 모델에 갔는지가 질문이 되지 않는다. 파일에 적힌 것이 갔기 때문이다. 프런트매터에 이름과 설명과 도구 허용 목록을 적고, 그 아래 본문이 시스템 프롬프트가 된다.

Claude Code 문서는 이 경계를 명시한다. 서브에이전트는 이 시스템 프롬프트와 작업 디렉터리 같은 기본 환경 정보만 받으며 전체 시스템 프롬프트는 받지 않는다는 것이다. 무엇이 들어가지 않는지까지 적혀 있다는 점이 이 방식의 성격을 보여 준다.

대가는 프로그래밍에서 온다. 타입이 없으니 출력 형태는 프롬프트로 부탁해야 하고, 공통 부분을 빼내려면 텍스트 포함 기능이 필요하고, 그 순간 다시 앞 절의 문제로 돌아간다. 역할을 나누는 구성이 어디까지 성립하는지는 역할 분담 시뮬레이션을 다룬 글에 있다.

  • 잘 맞는 자리 — 사람이 자주 손대고, 흐름이 한 갈래이고, 산출물이 텍스트인 작업
  • 안 맞는 자리 — 출력이 다른 시스템의 입력이 되어 스키마를 어겨서는 안 되는 작업
  • 숨은 장점은 버전 관리와의 궁합이다. 프롬프트 변경이 diff 로 보이고 되돌리기가 파일 되돌리기다
  • 숨은 단점은 검색이다. 같은 지시가 열 군데에 복사되고, 하나만 고쳐 놓고 고쳤다고 생각하게 된다

가장 큰 갈림길 - 흐름을 누가 쥐는가

지금까지 본 네 갈래는 표현 방식의 차이다. 그런데 시스템의 성질을 실제로 결정하는 것은 그 아래 질문이다. 다음에 무엇을 할지를 코드가 정하는가, 모델이 정하는가. Anthropic 은 둘을 이름으로 갈라 둔다. 워크플로는 LLM 과 도구가 미리 정해진 코드 경로를 따라 조율되는 시스템이고, 에이전트는 LLM 이 자기 과정과 도구 사용을 스스로 지휘하는 시스템이다.

프레임워크마다 이 스위치를 어디에 두는지가 다르고, 그 위치가 표현 방식보다 결과에 크게 영향을 준다. 같은 클래스 기반이라도 흐름을 코드가 다 쥐면 워크플로에 가깝고, 모델이 REPL 에서 다음 행동을 만들면 반대쪽 끝에 가깝다.

흐름의 주인어울리는 표현잘 되는 것무너지는 자리실패했을 때 증상
코드가 전부 쥔다그래프·명령형 함수재현성, 비용 예측, 테스트정의되지 않은 입력조용히 잘못된 경로로 완주
모델이 전부 쥔다프롬프트 파일·단일 루프처음 보는 상황, 탐색루프와 중복 호출, 예산같은 도구를 여덟 번 부르고 멈춤
코드가 뼈대, 모델이 구간객체(결정적 + 생성 메서드)실무의 대부분경계를 어디에 그을지경계가 잘못 그어진 구간에서만 실패
모델이 코드를 써서 흐름을 만든다REPL·코드 실행 환경분기와 반복을 한 번에격리가 없을 때샌드박스 밖에서 사고가 난다

셋째 줄과 넷째 줄을 같이 쓰는 것이 지금 나오는 설계의 흐름이다. 표현력은 늘지만 실행 환경이 곧 공격면이 된다. 앞서 본 문서가 AST 검사와 차단 목록을 격리 경계가 아니라고 굳이 못 박는 이유다. 넷째 줄을 고른 모두가 함께 지는 부담이다.

행동을 JSON 으로 쓸까 코드로 쓸까

모델이 도구를 부르는 방법에도 두 갈래가 있고, 이 선택은 앞 절의 갈림길과 붙어 있다. smolagents 는 둘을 나란히 구현해 둔다. CodeAgent 는 도구 호출을 파이썬 코드 조각으로 만들고, ToolCallingAgent 는 JSON 으로 쓴다. 문서는 어느 쪽이든 쓸 수 있다고 하면서, 웹 브라우징처럼 매 상호작용 뒤에 기다려야 하는 작업에는 JSON 이 잘 맞는다고 적는다.

  • 코드 쪽의 이점 — 한 번의 행동 안에 반복과 조건과 중간 변수가 들어간다. 목록 스무 개를 훑는 일이 왕복 한 번이 된다
  • 코드 쪽의 비용 — 실행 환경 전체가 신뢰 경계 안으로 들어온다. 모듈, 파일 시스템, 네트워크가 전부 고려 대상이다
  • JSON 쪽의 이점 — 인자를 스키마로 검증할 수 있고 감사 로그가 균일해 세거나 재생하기 쉽다
  • JSON 쪽의 비용 — 왕복이 늘어난다. 토큰과 지연이 늘고 맥락이 잘릴 확률도 는다
  • 표현 방식과의 관계 — 객체를 REPL 에 노출하는 설계는 코드 쪽으로, 도구를 독립 함수 목록으로 두는 설계는 JSON 쪽으로 기운다

코드로 행동하는 방식이 본질적으로 똑똑한 것은 아니다. 표현 밀도가 높은 대신 검증 지점이 줄어드는 교환이다. 도구가 순수 계산에 가까울수록 코드 쪽이 이기고, 외부 세계를 바꾸는 도구일수록 JSON 쪽의 검증 지점이 값을 한다.

상태와 재개 - 직렬화가 되묻는 것

짧은 작업에서는 어떤 추상화든 잘 돈다. 되물리는 것은 오래 도는 작업에서다. 30분짜리 작업이 25분째에 죽었을 때 무엇이 남아 있는가. 각 갈래가 다른 답을 내놓는다.

그래프 쪽은 정면으로 다룬다. LangGraph 는 컴파일할 때 체크포인터를 지정할 수 있고, 체크포인트는 슈퍼스텝 경계에서 저장되어 인터럽트나 실패 뒤에 재개할 수 있게 한다. 흐름이 자료구조이기 때문에 어디서 멈췄는지를 값으로 표현할 수 있다.

객체 쪽에서 이 질문은 인스턴스를 어떻게 직렬화하느냐가 된다. 살아 있는 객체에 참조를 넘기는 설계는 표현력을 얻지만 그 참조는 프로세스 밖으로 나가지 못한다. 열린 소켓과 파일 디스크립터는 값이 아니라 핸들이기 때문이다. 앞서 본 패키지가 PyPI 요약에서 스스로를 이벤트 소싱과 직렬화된 실행을 갖춘 시스템이라고 소개하는 것은, 이 문제를 설계 단계에서 다룬다는 신호다.

프롬프트 파일 쪽은 상태를 아예 안 갖는 쪽으로 답한다. 대화 기록이 곧 상태이고 재개는 기록을 다시 먹이는 것이다. 단순하고 튼튼하지만 기록이 길어지면 그대로 토큰 비용이 된다.

  • 상태가 값인가 핸들인가. 값이면 저장되고 핸들이면 안 된다. 재개가 요구사항이면 이 구분을 초기에 그어야 한다
  • 저장 지점이 어디인가. 매 도구 호출 뒤인지 노드 경계인지에 따라 최악의 손실 구간이 정해진다
  • 재실행이 멱등인가. 체크포인트에서 다시 시작할 때 같은 결제 API 를 두 번 부르지 않는지. 프레임워크가 보장해 주지 않는다
  • 저장 형식이 배포를 넘기는가. 못 읽으면 배포할 때마다 진행 중 작업이 사라진다

확인 방법은 하나다. 도입 첫 주에 세 번째 도구 호출 뒤에 프로세스를 강제로 죽여 보는 것이다. 이 실험 한 번이 문서보다 많은 것을 알려 준다.

관측성 - 로그가 프레임워크의 말로 바뀔 때

추상화 층이 늘어나면 로그도 층을 얻는다. 노드 3에서 리듀서가 어쩌고 하는 줄은 그 프레임워크의 문서를 아는 사람에게만 문장이고 모르는 사람에게는 소리다. 새벽에 호출받은 사람이 그 문서를 처음 여는 상황을 생각하면 왜 비용인지 분명해진다.

필요한 로그는 두 종류다. 하나는 모델과 주고받은 원본이다. 최종 프롬프트, 응답 전문, 도구 인자, 도구가 돌려준 결과. 다른 하나는 프레임워크의 실행 기록이다. 뒤의 것만 있으면 디버깅이 추측이 된다. 왜 이런 답이 나왔는지 물었는데 어디를 지났는지만 알려 주는 셈이다.

  • 좋은 신호 — 추적이 기본으로 켜져 있고 호출들이 부모와 자식 관계를 유지한 채 남는다. 앞서 본 저장소는 이 성질을 문서에 명시하고 CLI 로 뷰어를 띄운다
  • 주의할 신호 — 추적을 보려면 외부 서비스에 가입해야 하는 구조. 데이터가 나가는 경로가 늘고, 서비스가 죽으면 그날 사고 조사가 멈춘다
  • 최소선 — 실행 하나의 원본이 로컬 파일로 떨어질 것. 대시보드는 그다음 문제다
  • 세어 볼 것 — 로그 한 줄에 프레임워크 개념이 몇 개 필요한가. 셋을 넘으면 그 로그는 아는 사람만 읽는다

에이전트를 여럿 붙여 두면 이 비용이 곱해진다. 조율 자체의 비용은 오케스트레이션 비용을 다룬 글에서 정리했다.

잠김의 실제 크기

고를 때 가장 걱정하는 것이 잠김인데, 걱정의 크기와 실제 크기가 잘 안 맞는다. 옮기는 비용은 코드 줄 수가 아니라 그것이 텍스트인가 프레임워크 고유 형식인가에서 나온다.

자산옮기는 난이도이유
프롬프트 텍스트쉬움그냥 텍스트다. 붙여넣으면 된다
도구 함수 본문쉬움대개 평범한 함수. 데코레이터만 갈아 끼운다
출력 스키마보통표준 타입 라이브러리에 얹혀 있으면 그대로 간다. 자체 타입이면 다시 쓴다
흐름 구조어려움그래프 정의, 상속 사슬, 핸드오프 규칙은 그 프레임워크의 어휘다
저장된 체크포인트매우 어려움형식이 프레임워크 것이다. 진행 중이던 작업은 버린다
추적과 평가 이력매우 어려움스키마가 다르다. 회귀를 비교할 기준선을 잃는다
팀의 사고 습관가장 어려움사람이 그 프레임워크의 개념으로 문제를 나누기 시작한다

마지막 두 줄이 진짜 잠김이다. 코드는 다시 쓰면 되지만 평가 기준선을 잃으면 새 구성이 예전보다 나은지를 증명할 방법이 없어진다. 반년쯤 쓰고 나면 사람들이 문제를 그 프레임워크의 개념으로 쪼개 이야기하게 되는데, 이것은 이전 문서에 적히지 않는 비용이다.

  • 프롬프트를 클래스 안 문자열이 아니라 파일이나 상수 모듈로 빼 둔다. 이전 비용의 상당 부분이 사라진다
  • 도구는 데코레이터가 붙지 않은 순수 함수로 쓰고 등록은 얇은 어댑터에서 한다. 어댑터만 다시 쓰면 된다
  • 평가 데이터셋과 판정 기준은 프레임워크 밖 파일에 둔다. 마지막 두 줄 중 하나를 지워 준다

프레임워크를 안 쓰는 쪽이 맞는 조건

Anthropic 의 권고는 분명하다. LLM API 를 직접 호출하는 것부터 시작하기를 권하며, 많은 패턴이 몇 줄이면 구현된다고 적는다. 프레임워크가 더 단순한 구성으로 충분한 자리에 복잡함을 더하고 싶게 만들 수 있다고도 덧붙인다.

messages = [{"role": "user", "content": task}]
while True:
    reply = client.messages.create(model=MODEL, tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": reply.content})
    calls = [b for b in reply.content if b.type == "tool_use"]
    if not calls:
        return reply
    results = [run_tool(c) for c in calls]   # 여기서부터 끝까지 전부 내 코드다
    messages.append({"role": "user", "content": results})

이 아홉 줄에는 가려진 것이 없다. 무엇이 나가고 들어오는지가 변수 이름으로 보인다. 대신 재시도도 예산 상한도 재개도 병렬도 직접 써야 한다. 문제는 이 아홉 줄이 여섯 달 뒤에 아홉 줄로 남아 있지 않다는 것이다.

  • 직접 루프가 충분한 조건 하나 — 흐름이 한 갈래이고 분기를 손가락으로 셀 수 있다
  • 둘 — 도구가 열 개 안쪽이고 서로 상태를 공유하지 않는다
  • 셋 — 작업이 한 요청 안에서 끝나 재개가 요구사항이 아니다
  • 넷 — 사람이 한둘이라 규약을 문서 없이 유지할 수 있다
  • 다섯 — 로그 형식을 직접 정하고 싶고 그럴 이유가 있다
  • 프레임워크가 값을 하는 조건 하나 — 사람이 여럿이고 각자 에이전트를 추가한다. 공통 규약이 코드로 강제돼야 한다
  • 둘 — 재개와 사람 승인 개입이 요구사항이다. 직접 만들면 프레임워크를 하나 만들게 된다
  • 셋 — 여러 제공자와 여러 모델을 갈아 끼운다
  • 넷 — 추적과 평가를 처음부터 균일하게 쌓아야 한다. 소급이 가장 어려운 항목이다

실제로 자주 나오는 답은 중간이다. 루프는 직접 쓰고 추적과 평가만 라이브러리를 쓰거나, 프레임워크를 쓰되 프롬프트와 도구를 바깥 파일에 두는 식이다. 전부 쓰거나 전부 안 쓰는 선택으로 보이는 것 자체가 이미 프레임워크의 어휘다.

고르기 전에 답해 둘 여섯 가지

기능 비교표는 도움이 안 된다. 어느 쪽이든 결국 다 되기 때문이다. 대신 후보를 며칠 써 보면서 아래 여섯에 답해 두면 반년 뒤에 무엇이 아플지가 보인다.

  • 프롬프트 전문을 파일로 떨구는 데 몇 분 걸리는가. 십 분을 넘기면 사고 대응 시간이 그만큼 늘어난다
  • 도구 목록을 소스만 읽어서 셀 수 있는가. 아니면 권한 검토가 실행 로그 검토가 된다
  • 세 번째 도구 호출 뒤에 프로세스를 죽이면 무엇이 남는가. 아무것도 안 남으면 긴 작업은 이 구성으로 하지 않는다
  • 흐름의 분기를 코드가 쥐는가 모델이 쥐는가, 그 답이 문서에 적혀 있는가. 없으면 둘이 섞여 있고, 섞인 자리가 사고 지점이 된다
  • 프레임워크를 모르는 동료가 로그만 읽고 무엇이 잘못됐는지 말할 수 있는가. 못 하면 운영이 한 사람에게 묶인다
  • 이 프레임워크를 걷어낸다면 무엇을 다시 쓰게 되는가. 프롬프트와 도구 함수뿐이면 잠김이 얕고, 평가 이력이 끼어 있으면 깊다

추상화는 무엇을 쉽게 만들지 고르는 일이고, 쉬워진 것은 많이 일어난다. 클래스로 부르면 상속으로 공유하기 시작하고, 그래프로 부르면 노드를 쪼개기 시작하고, 파일로 부르면 파일이 늘어난다. 고르는 순간 팀이 반년 동안 자주 하게 될 동작이 정해진다. 프레임워크가 그 답을 대신 정해 주지는 않지만, 무엇을 쉽게 만들어 두었는지는 첫 예제에 다 나와 있다. 문서의 첫 화면을 설계 선언으로 읽으면 비교표보다 많은 것이 보인다.

확인하지 못한 것

  • 저장소의 커밋 수는 목록 화면에서 322개로 표시되지만 기본 브랜치 기준이고 시점에 따라 바뀐다. 브랜치와 태그별 내역은 확인하지 않았다
  • 논문의 SWE-bench Verified 와 Terminal-Bench 2.0 결과는 초록 범위에서만 확인했고 본문 표는 열지 않았다. 그래서 성능 수치는 한 개도 쓰지 않았다
  • 여기 든 프레임워크들을 같은 조건에서 비교한 자료는 확인하지 못했다. 어느 쪽이 낫다는 말을 하지 않는 이유다
  • 적어 둔 설계 사실은 2026년 9월 초 각 프로젝트 공식 문서 기준이다. 설정 파일 형식은 최근에 바뀐 사례가 있다
  • 프레임워크를 갈아 끼운 팀들의 실제 이전 비용을 정량화한 조사는 찾지 못했다. 12절의 난이도 구분은 측정값이 아니다
