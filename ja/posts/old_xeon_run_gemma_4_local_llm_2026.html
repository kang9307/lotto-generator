10年前のXeonでGemma 4を動かす - 旧型ハードでローカルLLMを運用する方法 2026

You Don't Need a GPU - Running Gemma 4 on Decade-Old Xeon Hardware in 2026

2026年6月3日 IT・技術

序論：GPUがなくてもローカルLLMは動く

ローカルLLMの話になると、ほぼ反射的に「GPUが必要だろう」という言葉が続きます。数十万円のグラフィックカードがなければ始められない、という認識が根強くあります。ところが2026年現在、この前提は思ったより簡単に崩れます。倉庫に眠っていた10年前のXeonサーバー、会社で廃棄寸前の旧型ワークステーション、中古市場で数万円で出回るデュアルソケットボード。こうしたハードでもGemma 4のような軽量オープンモデルは十分に動かせます。

本稿はGeekNews（hada.io）で話題になった「10年前のXeonでGemma 4が運用可能」というテーマを、単なる紹介ではなく実際に運用する者の視点で再構成した分析です。どこかの記事の翻訳や要約ではありません。なぜ旧型CPUでも可能なのか、どこまでが現実的でどこからが無理なのか、中古サーバー市場と電気代の環境でこの戦略が成り立つのかを直接検証します。

核心の問いは単純です。「GPUに大金を投じる代わりに、すでに持っているか格安で手に入る旧型XeonでローカルLLMを回せば、本当に使えるのか？」結論から言えば、作業の性質を正しく分類すれば、かなり多くの用途で答えは「はい」です。ただしすべてを旧型CPUに押し付けようとすると、遅い速度と電力という壁にぶつかります。

1. Gemma 4とは - Googleのオープン軽量モデル概要

GemmaはGoogleが公開したオープンウェイトの軽量LLMファミリーです。巨大な閉鎖型モデルと異なり重みが公開され、誰でもダウンロードして自分のハードで動かせます。何より旧型ハード活用に決定的なのは、複数のサイズを同時に提供する点です。

1.1 サイズ選択の自由

Gemma 4系列は小型から大型まで派生が分かれます。小型派生は数十億パラメータ規模で、量子化すれば旧型CPUでも無理なく動きます。ここで鍵となるのは「最大のモデル」ではなく「自分のハードが扱える最小の十分なモデル」を選ぶ考え方です。

1.2 なぜ軽量モデルで十分なのか

要約、分類、タグ付け、一次ドラフト生成といった非中核の反復作業では、小型モデルの品質はすでに十分使えます。最高品質が必要な作業と「そこそこ良ければいい」作業を分ければ、後者の比重が思ったより大きいことにすぐ気づきます。まさにその領域が旧型Xeon＋軽量Gemmaの組み合わせが輝く場所です。

2. 旧型Xeonで可能な理由 - 量子化・メモリ・CPU推論

10年前のサーバーCPUがどうやって最新LLMを動かすのか。三つの技術的事実がこれを可能にします。

2.1 量子化がモデルを小さくする

元のモデルは通常16ビット浮動小数点で保存されますが、4ビットや8ビットに量子化するとメモリ使用量が半分から4分の1に減ります。品質低下は非中核作業ではほとんど体感されません。量子化のおかげで、以前なら高価なGPUでしか動かなかったモデルが普通のサーバーRAMに収まります。

2.2 メモリがGPU VRAMの代わりになる

GPU推論の核心は高速なVRAMです。CPU推論はその役割をシステムRAMが担います。旧型Xeonサーバーの利点はRAMを非常に安価に大量に挿せることです。中古DDR4 ECCメモリは格安なので、64GB、128GBも負担なく確保できます。

2.3 AVX命令と多数のコア

2010年代半ば以降のXeonはAVX2などのベクトル命令をサポートし、コア数も多いです。llama.cppのような推論エンジンはこの命令とマルチコアを活かして行列演算を並列化します。おかげで一世代前のCPUでも意味のある推論速度が出ます。

3. 必要なハード - 最小構成と推奨構成

実際に何を揃えるべきかを表にまとめました。絶対値はモデルサイズで変わるので相対関係に注目してください。

最も重要なのはメモリ帯域です。CPU推論で速度を決める真のボトルネックはコア数ではなく、メモリから重みをどれだけ速く読み出せるかです。だからメモリチャネルを全部埋めることが、単に容量を増やすより体感速度に大きく効きます。

4. CPU推論の現実 - 速度 vs コストのトレードオフ

正直になる時間です。旧型XeonでのCPU推論は遅いです。量子化小型モデルで毎秒数トークンから低い二桁が一般的です。人が文字を読む速度と同程度かやや遅い程度で、短い回答は耐えられますが長い文書を丸ごと生成するともどかしさが明確に感じられます。

しかし速度だけ見れば半分の絵しか見ていません。反対側にはコストがあります。すでに所有するサーバーなら導入コストは実質ゼロ、中古で買ってもGPU一枚の値段にはるかに及びません。トークンをいくら生成しても追加課金がない点は、API従量制と決定的に異なります。つまり速度をコストと引き換えにする構造です。時間に余裕があり費用を抑えたい作業なら、この交換は十分合理的です。

5. 量子化の魔法 - Q4・Q5・Q8

旧型ハード活用の核心技術が量子化です。同じモデルでもどの量子化を選ぶかでメモリと速度、品質が大きく変わります。

  • Q4（4ビット）：メモリを最も少なく使い最速。非中核の反復作業に適し、旧型Xeonの第一選択として薦めます。
  • Q5（5ビット）：Q4とQ8の間のバランス点。少しメモリを多く使う代わりに品質が安定します。
  • Q8（8ビット）：元に最も近い品質。RAMが潤沢で品質が重要なときに選びます。

実務ではQ4から始め、品質が足りなければQ5、Q8へ一段ずつ上げる方式を薦めます。量子化のより深い原理とモデル選択基準はローカルLLMハードウェア選択ガイドに続きます。

6. 実践セットアップガイド - llama.cppとOllama

では実際に動かします。最も広く使われる二つの経路を紹介します。

6.1 Ollamaで最速に始める

OllamaはCPU推論を標準サポートし、インストールと実行が最もシンプルです。

# Ollamaインストール（Linux）
curl -fsSL https://ollama.com/install.sh | sh

# 軽量Gemmaモデルを取得して実行（CPU自動使用）
ollama run gemma:2b

# バックグラウンドサービスでAPIを立てる
ollama serve

GPUがなければOllamaが自動でCPU推論で動作します。追加設定なしですぐ対話を始められ、最初の検証に理想的です。

6.2 llama.cppで細かく制御する

速度とメモリを直接チューニングするならllama.cppが正解です。GGUF量子化モデルを直接指定しスレッド数を調整できます。

# ビルド（AVX2自動検出）
git clone https://github.com/ggerganov/llama.cpp
cd llama.cpp && make

# 4ビット量子化モデルで推論、物理コア数に合わせてスレッド指定
./llama-cli -m gemma-4-q4.gguf -p "ローカルLLMの利点を三つ" -t 16

# OpenAI互換APIサーバーとして立てる
./llama-server -m gemma-4-q4.gguf -t 16 --port 8080

ここで-tの値は物理コア数に合わせるのが通常最速です。ハイパースレッディングを含む論理コア全てを使うとかえって遅くなる場合が多いので、自分で測定してみてください。

7. どんな作業に向くか vs 向かないか

7.1 向く作業

  • 大量文書の要約：時間に余裕のあるバッチ処理に最適です。
  • 分類・タグ付け：カテゴリ分類、感情分析は小型モデルでも十分です。
  • 一次ドラフト生成：人が最終確認するので速度の重要度が下がります。
  • 内部RAG検索：外部露出のない社内知識検索はプライバシー面でも有利です。
  • 学習・実験：LLMの動作を直接いじって学ぶのにコスト負担がありません。

7.2 向かない作業

  • リアルタイム対話型サービス：遅いトークン速度がユーザー体験を損ないます。
  • 大規模同時処理：単一の旧型サーバーで高い同時実行を支えるのは困難です。
  • 複雑な多段推論：小型モデルの限界が最もよく表れる領域です。
  • 低遅延SLA保証サービス：応答時間の保証が難しいです。

8. 旧型ハード活用の5つのシナリオ

  1. ホームラボ実験室：廃棄寸前のサーバーをLLMの遊び場に再活用。クラウド費用を気にせず存分に実験します。
  2. プライバシー優先処理：機微な社内文書を外部APIに送らずローカルだけで処理します。
  3. 学習プラットフォーム：量子化、推論エンジン、プロンプトを直接触って学ぶコストゼロの学習環境。
  4. バックアップ推論ノード：メインGPUサーバー障害時に非中核作業を支える補助ノード。
  5. コスト削減バッチパイプライン：夜間に大量の要約・分類を回しAPI従量制を代替します。

9. ローカル環境への適用 - 中古サーバー市場、電気代、ホームサーバー

多くの市場でこの戦略は特に魅力的な条件を備えています。第一に中古サーバー市場が活発です。データセンターの入れ替えで、デュアルXeonボード、ECCメモリ、サーバーケースを合理的な価格で手に入れられます。

第二に、ただし電気代は慎重に見るべきです。旧型サーバーは電力効率が低く、24時間稼働すると電気代が積み重なります。家庭用の段階制料金に当たると費用が急上昇するので、常時稼働より必要なときだけ電源を入れるバッチ運用が現実的です。発熱と騒音のため、居住空間と分けた場所に置くことも検討すべきです。

第三に、ホームサーバー文化とよく合います。すでにNASやホームサーバーを運用しているなら、そこにLLM推論を載せる参入障壁は低いです。より広い文脈は安価な外注人材＋LocalAIコスト戦略の記事で扱います。

10. リスクと限界 - 遅い速度、電力、発熱

バラ色だけ描くのは誠実ではありません。旧型XeonのLLM運用には明確な限界があります。

  • 遅い速度：最大の制約。リアルタイム性が必要などの用途にも不向きです。
  • 電力消費：旧型サーバーの低い電力効率は長期運用で電気代として返ってきます。
  • 発熱・騒音：サーバーファンの騒音と発熱は家庭環境で無視できません。
  • 保守負担：老朽ハードは故障の可能性が高く、部品調達が難しいことがあります。

これらの限界を認め「バッチ・非中核・学習用」という定位置に置けば、旧型ハードのLLMは優れた道具になります。メモリ割り当てや推論性能をより深く掘り下げたいならmimalloc 高性能メモリアロケータの記事も参考になります。

11. 結論 + すぐ試せる3つ

結論は明確です。ローカルLLMにGPUは必須ではありません。作業を正しく分類し量子化軽量Gemma 4を旧型Xeonに載せれば、非中核作業のかなりの部分を実質無料に近いコストで処理できます。鍵は「全部回す」ではなく「回していいものだけ回す」です。

今すぐ試せる三つを薦めます。

  • Ollamaで5分検証：手持ちの旧型サーバーにOllamaを入れ軽量Gemmaを立ててトークン速度を直接測定しましょう。
  • バッチ作業を一つ移行：夜間の文書要約のような非中核作業を一つ旧型サーバーに移し6週間品質・速度・コストを記録しましょう。
  • 電気代の損益計算：24時間稼働時の月電気代を計算し、常時運用と必要時運用のどちらが合理的か判断しましょう。
