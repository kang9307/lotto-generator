データを運ぶことより意味を合意することが難しい - スキーマが捕まえられない意味のずれとデータ契約

カラムが消えればすぐ気づくが、意味が変わっても誰も気づかない

2026年8月31日 開発・インフラ

はじめに: パイプラインは全部緑なのに、二つのチームの数字が違う

月曜の指標会議でこういう場面が出る。グロースのチームが先月のアクティブユーザーを412万だと言い、財務側の資料には388万と書かれている。誰も間違えていない。パイプラインはすべて成功し、スキーマ検証も通り、二つの数字はどちらも正常範囲の中にある。

その会議はたいていデータを直す会議ではなく、どちらの数字が正しいかを争う会議として終わる。そして翌月にまた開かれる。定義がどこにも書かれていないので、合意した内容が人の記憶にだけ残り、パイプラインには残らないからだ。

この問題はインフラが貧弱だから起きるのではない。むしろ逆だ。データを運び、積み、速く走査する仕事はこの十年でかなり解決した。残った難しさはそこに新しく生まれたのではなく、手前の難しさが片づいたことで露出したものだ。

ちょうどこの構図を正面から捉えた記事がある。2026年8月19日に公開された Data Architecture Patterns: Decisions for the AI Era だ。著者はよく列挙される六つのアーキテクチャパターンを、互いに排他的な選択肢ではなく、異なる次元の決定として並べ直す。あるものは処理方式の決定であり、あるものは変換段階の決定であり、あるものは所有権の決定で、保存はそのうちの一マスにすぎないという整理だ。そして著者の結論はこの記事の出発点と重なる。AI による消費が支配的な圧力になると、価値が上がるのは保存・処理・統合ではなく意味・契約・ガバナンスだという主張である。

この記事はその主張を受けて一階下りる。ツールを選ぶ話ではなく、同じ名前のカラムがチームごとに別の意味を抱えているときに何が起きるかの話だ。何が良い製品かは扱わない。何が約束であり、その約束をどこで守らせるかだけを見る。

1. 保存が安くなった跡地に残ったもの - 同じ名前、別の意味

まず何が実際に解けたのかを正直に書いておこう。容量と速度はおおむね金で解決する問題になった。安くてほぼ無限のファイル倉庫にデータを積み、カラム単位で圧縮の効くファイル形式で保存し、読む計算資源を保存から切り離して必要なときだけ起動する構成が標準に近づいた。以前は数か月がかりの容量見積り会議が必要だった決定が、いまはかなりの部分が料金プランの選択に降りてきている。

最近よく聞くレイクハウスという言葉が指すのもこの構成だ。ほどいて書けばこうなる。安くて大きなファイル倉庫の上に、何がいつどう変わったかを記す台帳を一枚重ねて、その倉庫を表のように扱えるようにした方式である。台帳があるので巻き戻せるし、同時書き込みもある程度は扱える。良い前進だ。ただしこれは保存の決定である。どのカラムが何を意味するかを台帳は教えてくれない。

だからいま実務で時間を食うのはたいていこの種類だ。カラム名は三つのチームが同じものを使っているのに、その中身が互いに違う。

カラム生産者が入れていたもの消費者がそうだと思っていたものずれたときに出る症状
country決済手段の請求先の国ユーザーが実際に接続した国地域別の成長率が特定の国に偏って見える
revenue税込み、返金を差し引く前の総額認識可能な純売上財務の締めの数字とダッシュボードが常時ずれる
signup_dateアカウントのレコードが最初に作られた時刻メール認証まで終わった時刻登録から初回決済までの期間が実際より長く出る
is_activeアカウントが停止されていないという意味最近実際に使っているという意味休眠アカウントがアクティブに数えられ、離脱率が低く見える
order_idカート単位の識別子配送単位の識別子分割配送のある注文で件数が膨らむ

この表のどの行もバグではない。生産者側ではそれぞれ正しい値を入れている。問題はその選択がカラム名のどこにも書かれておらず、消費者は名前だけを見て自分の側の常識で読むという点にある。データがチームの境界を越えた瞬間、名前は残り、文脈は落ちる。

そしてこうしたずれは組織が大きくなるほど加速度的に増える。生産者が五つで消費者が二十なら解釈の組み合わせは百通りだ。その百通りがそれぞれのダッシュボードとそれぞれのクエリの中に散らばっていて、どこにも一か所にまとまっていない。

2. 「アクティブユーザー」が何なのか誰も知らない

最もありふれていて最も解けない例がこれだ。ほとんどの会社にアクティブユーザー指標があり、ほとんどの会社でその定義を一文で言える人がいない。定義がないからではなく、複数が同時に存在しているからだ。

定義を一度ほどいてみると、どこで割れるのかが見える。分かれ道は少なくとも五か所ある。

分かれ道実際に選択が割れる地点数字が動く方向
何が活動なのかログイン、アプリ起動、特定画面への到達、API 呼び出し、プッシュ受信基準をアプリ起動まで広げると大きく増え、中核機能の利用に絞ると急減する
誰がユーザーなのかアカウント、人、端末、組織（一契約に従業員300人）端末基準は膨らみ、組織基準は急激に減る
いつまでか暦月、30日ローリング、最終活動基準、UTC で見るか現地時刻で見るか月末の一日の差で数パーセントが行き来する
何を除くのか社内アカウント、テストアカウント、ボットとクローラ、自動リトライ、ヘルスチェックボットフィルタを入れるか外すかだけで数パーセントが移動する
どう数えるのか重複排除の基準、退会後の再登録、アカウント統合時の過去履歴の扱い統合の扱い方によって過去の値そのものが変わる

五つの分かれ道でそれぞれ二つか三つの枝を取るだけで組み合わせは数十通りになる。そのどれを選んでも正直な数字が出る。だから二つのチームが別々の数字を持ってくる状況は、誰かが間違っているのではなく、二つのチームが別々の指標を同じ名前で呼んでいるのだ。

ここに二つめの問題がつく。会議で定義をそろえたとしよう。その合意は議事録に残る。翌四半期に新しいアナリストが来て、その人は議事録を見ないまま表を見てクエリを書く。カラム名は is_active だ。彼が何を入れるかは決まっている。

だからこの問題の本質は知識ではなく知識の置かれた場所だ。定義が人の頭と議事録にあれば、人が入れ替わるときに一緒に消える。コードの隣にあって検査を通らないとマージできないなら残る。この違い一つが次節から先の話のすべてである。

3. スキーマは形式しか語らない - 仕様が自らそう書いている

「ならスキーマをちゃんと使えばいいのでは」というのが自然な次の問いだ。答えは仕様の中にすでに書かれている。スキーマの仕様たちは、自分が何を検査して何を検査しないのかを自ら明示的に分けている。

JSON Schema 2020-12 の検証仕様はキーワードを二種類に分ける。一つは値の真偽を判定するアサーションキーワードで、もう一つはドキュメントと画面表示のための基本メタデータアノテーション語彙だ。title と description は後者に属する。仕様はこの二つがこのインターフェースが生み出すデータに関する情報でユーザーインターフェースを飾るのに使えるとだけ言う。検証には関与しない。

Avro のほうはもっと露骨だ。スキーマ解決の規則でフィールドは名前で照合されると明記し、スキーマの doc フィールドはスキーマ解決の目的では無視されると別に書いてある。フィールドの順序が違っても名前が同じなら互換であり、そのフィールドが何を意味するかを書いた文は判定に何の影響もない。

{
  "name": "is_active",
  "type": "boolean",
  "doc": "停止されていないアカウント（2026-08 以前）"
}
// doc だけ下に変えたリリース → スキーマ解決は完全互換で通過
{
  "name": "is_active",
  "type": "boolean",
  "doc": "直近30日以内にログインしたアカウント"
}

上の二つのスキーマは機械にとって同じスキーマだ。ところが is_active が実際に数える対象は完全に変わっている。このリリースはどの検査にも触れずに通過し、その表を使う二十のダッシュボードは何の警告もなく別の数字を描きはじめる。

3.1 スキーマが捕まえるものと捕まえないもの

  • 捕まえる — フィールドが消えた、型が文字列から数値に変わった、必須フィールドがヌルになった、列挙値にない値が入った
  • 捕まえる — 形式がずれた。日付文字列が規格を外れた、数値が宣言した範囲を超えた
  • 捕まえない — 同じ型の中で意味が変わった。金額の通貨が変わり、時刻の基準タイムゾーンが変わり、真偽値が数える対象が変わった
  • 捕まえない — 集計規則が変わった。フィルタ条件が一つ増え、結合の向きが変わり、重複排除の基準が変わった
  • 捕まえない — 値はそのままなのに母集団が変わった。昨日まで国内だけ入っていた表に今日から海外が混ざり込み、文書に書かれた意味と実際のクエリがずれても、文書はそもそも検査対象ではない

まとめるとスキーマは契約の半分だ。それも比較的やさしい半分である。API文書はなぜいつもコードより遅れるのかで扱った機械が読む規格の話がこの半分にあたる。残りの半分、つまり意味はその外にあり、これまでおおむね管理されないままだった。

4. データ契約は何を約束し、何を約束しないのか

データ契約という言葉を流行語のまま置くと何も言っていないことになる。だから自分の言葉に絞っておくほうがいい。データを作る側と使う側のあいだで、何を送り、何を保証し、変えるときにどう知らせるかを書いておいた約束だ。そしてその約束が人の善意ではなく機械で検査され、ずれたら何かが失敗するときに初めて契約と呼ぶ値打ちがある。検査されない約束はただの文書だ。

この形を規格として書いた公開標準はすでにある。Bitol が管理する Open Data Contract Standard は契約文書を十一の節に分けるが、そのうちスキーマは一節にすぎない。残りがデータ品質、サポートとコミュニケーション経路、チーム、役割、サービス水準合意、インフラとサーバといったものだ。規格そのものが契約の大部分はスキーマの外にあると言っているわけである。

契約が約束すること契約が約束しないこと
フィールド構成と型、必須かどうかそのデータが事業的に正しい指標なのか
各フィールドが何を意味するかの定義文消費者がその定義を正しく読むかどうか
値の有効範囲、ヌル許容比率の上限定義がこれから変わらないということ
いつまでに届くかという鮮度の基準クエリ性能と保存費用
変えるときの予告期間と通知経路過去データを遡って訂正すること
これに責任を持つチームと連絡経路契約文と実際のクエリが一致しているか

右列の三つめが最も誤解を呼ぶ。契約は定義が不変だとは言っていない。事業が変われば定義も変わらなければならない。契約が約束するのは変えるときに黙って変えないということ一つだ。この違いを取り落とすと契約を変化を止める装置だと誤解することになり、その誤解が後に出る官僚化の失敗にそのままつながる。

右列の一番下も正直に書いておく必要がある。契約ファイルにアクティブユーザーとは直近30日以内に中核機能を一回以上使ったアカウントと書いておいても、実際のクエリがログインだけを数えているかどうかは機械には検査できない。その照合はどこかの時点で人がやるしかない。契約がするのはその地点を狭めることであって、なくすことではない。

5. 壊れ方が静かだ

この記事で最も重要なところだ。形式が壊れることと意味が壊れることは性質が違う。そしてその違いは深刻度ではなく発見の速さにある。

形式が壊れるとうるさい。カラムが消えればその場でクエリが失敗し、スケジューラが赤くなり、通知が鳴り、誰かが夜中に起こされる。不快だがこれはよく設計された失敗だ。数時間以内に認知され、数時間以内に復旧する。

意味が変わると何の音もしない。パイプラインは成功し、検査も通り、ダッシュボードは描かれ続ける。変わるのは数字だけで、その変化幅はたいてい季節性やマーケティング効果と区別がつかない。3パーセント増えた数字を見て事故を疑う人はいない。

5.1 静かに壊れる典型的な経路

  • フィルタが一つ増えた。上流がボットトラフィックを除きはじめると、すべての下流の数字が同時に下がる。良い変更なのに通知がなければ事故と区別がつかない
  • タイムゾーンの基準が変わった。集計基準を UTC から現地時刻に移すと、月末と月初の数日が別の月に移る。年間合計は同じなので検算でも捕まらない
  • ヌルの扱いが変わった。値がないときヌルにしていたものをゼロで埋めはじめると、平均を取る側だけ静かに値が下がる。合計を見る側には何の変化もない
  • 通貨換算の時点が変わった。決済時刻のレートから締め日のレートに移すと、海外売上の比率が大きい月だけ揺れる
  • 上流が過去を埋め直した。再処理が走ると、昨日出した報告書と今日出した報告書で先月の数字が違う。誰も再処理の事実を知らない
  • 結合の片側が空になった。イベント一つがデプロイ漏れで入ってこないのに結合が左基準だと、行はそのまま残り値だけがゼロになる。行数の検査では絶対に捕まらない

ステータスコードに新しい列挙値ができたのに下流の CASE 文にその分岐がなく、その件数がその他に落ちる場合も同じ部類だ。六つとも失敗通知を作らない。発見経路は一つしかない。誰かが数字を見ておかしいと感じることだ。そしてその感覚はたいてい数週間後に来る。そのあいだに取締役会に出た報告書、パートナーに請求した精算、モデル学習に入ったデータはもう戻せない。

ここに組織の非対称が重なる。うるさく壊れる側にはすでに通知と当番と予算がついていて、静かに壊れる側にはその三つがない。だから投資はずっとすでによく捕まる側に向かう。パイプライン成功率のダッシュボードをもう一枚作るほうが、定義一つをチーム間で合意させるよりいつも簡単だからだ。

対応の方向はそれで一つに絞られる。値の有無ではなく値の分布を見る。ヌル比率、一意値の数、値の区間別分布、前日比の行数変動を契約に書いておき、閾値を超えたら知らせる。完璧ではない。3パーセントの変化はやはり捕まらない。ただフィルタの追加やヌル埋めのように分布が階段状に飛ぶ変更はこの方式で捕まる。そして実務で静かに壊れる事故のかなりの部分がその階段状のほうだ。

6. AI がこの問題を大きくする場所

ここまでは AI なしでも成り立つ話だ。ではなぜいまこの主題が再び上がってきたのか。きっかけとなった記事の著者はその理由を消費者の性格が変わったところに見いだす。著者は、二つのドメインが customerId を文字列にすることで合意しても顧客の定義が互いに違えば失敗するという例を挙げる。スキーマの互換だけでは足りず、意味の一貫性が必要だということだ。

この指摘が重いのは、人のアナリストとモデルの振る舞いが違うからである。

  • 人は聞き返す。数字が普段と違えば表を作った人に連絡する。この聞き返しがこれまで意味のずれを捕まえてきた実質的な安全網だった
  • モデルは聞き返さない。与えられたカラムをそのまま使い、その結果を自然な文章にして出す。誤った前提の上でも文章はなめらかだ
  • 検算しないことが導入の目的だった。人が毎回検算するならそもそも自動化する理由がない。しかも生成された要約には留保が形式的にしか付かないので、読む人は確信の度合いを区別できない

6.1 遡って追いにくくなる理由

もっと厄介なのは間違えたあとだ。どこで間違えたのかを遡る作業が構造的に難しくなる。

  • 問いが自然言語なのでどのカラムを選んだかの記録が薄い。生成されたクエリを残しておかなければ根拠が消える
  • 複数のソースを合わせて一段落に要約するとどのソースが誤りだったのかが文の中で分離されない
  • 学習やファインチューニングに入ったデータは成果物から切り離せない。誤った定義で作ったラベルが混ざるとその影響は個別の回答ではなくモデル全体に広がり、同じ問いをもう一度尋ねても同じ経路で答えるとは限らないので再現で原因を狭めることも難しい

ここでよく出る処方がセマンティックレイヤーだ。この言葉もほどいておこう。表とカラムの上に指標の計算式と意味を一か所に書いておき、すべてのクエリがその一か所を通って出るようにする層である。要点は特定のツールではなく定義をコードにして一か所だけに置くことだ。このアプローチを言語とツールの観点から見た話は ktx — データ・分析AIエージェントのための実行可能なコンテキストレイヤー と 2026年のデータツール地形 に別途まとめてある。

ただしこれも万能ではない。その層を迂回するクエリが一つでもあれば定義はまた割れる。そして現実にはほぼ必ずある。急ぎの分析、臨時の抽出、ノートブックの中の個人的なクエリがそれだ。定義を一か所に集めるのは技術の仕事だが、その一か所を必ず通らせるのは組織の仕事である。

7. 契約を強制する場所 - 文書か、テストか、デプロイゲートか

契約をどこに置くかによって効きめと代償が正反対に動く。三つのうち一つを選ぶ問題ではなく、何をどこに置くかを分ける問題だ。

7.1 文書に置く

  • 効きめ — 最も低い。文書は間違っても誰も痛くないので、コードよりいつも遅れる
  • 代償 — 最も安い。会議を何度かとファイル一つで済む
  • それでも価値 — 定義を文章にする行為そのものが合意を強制的に始めさせる。三つのチームが別の答えを出すという事実は、書いてみるまで表に出ない。ゼロから一に進む区間ではこれが最大の前進だ

7.2 パイプラインの中で検査する

  • 効きめ — 中間だ。ヌル比率、値の範囲、到着時刻、行数変動のように機械が数えられるものは確実に捕まえる
  • 代償 — 検査が失敗したときの判断を先に決めておかないと崩れる。止めれば下流全体が遅れ、通せば警告がたまって雑音になる。実務ではたいてい通す側に傾く
  • 限界 — すでにデータが届いたあとだ。誤った値が保存先に入ったあとで捕まえるので、遡及訂正の費用はそのまま残る

7.3 生産者のデプロイゲートに置く

  • 効きめ — 最も大きい。スキーマや定義を変える変更がマージされる前に止まれば、誤ったデータがそもそも生まれない
  • 代償 — 最も高い。生産者チームのデプロイが他チームの事情で止まることをそのチームが受け入れて初めて成立する。ここでほとんどの導入が失敗する
  • 失敗の形 — 組織の合意なしにツールだけ入れると例外承認という迂回路がすぐにでき、二か月後にはすべての変更が例外として出ていく

実際に回っている配置はたいていこう分かれる。形式はデプロイゲートに、分布と鮮度はパイプラインの検査に、意味は文書と人のレビューに置く。最後のマスが残ることがこの記事の結論であり限界だ。意味を機械が検査できないので、契約をどれだけうまく組んでも人が見なければならない地点はなくならない。契約がするのはその地点を十か所から一か所に減らすことである。

8. 誰が所有するのか - 技術の問題が終わる場所

契約には署名が要る。署名する人がいなければそれは契約ではなく願望リストだ。そしてデータの側で所有が空くのは例外ではなく既定値である。

典型的な構図はこうだ。中央のデータチームがすべての表を管理する。そのチームはパイプラインをうまく回すが意味を決める権限がない。決済が何を意味するかは決済チームが知り、契約が何を意味するかは営業チームが知っている。中央チームは真ん中で推測し、推測したものをカラム名に込め、その名前が会社全体の共通語になる。ずれの半分はこの構造から出る。

最近よく出るデータメッシュという言葉が狙うのがまさにこの地点だ。ほどいて書けば中央の一チームが全社データの意味を全部知ることはできないのだから、データを作るドメインチームが自分のデータを他人が使える形で出し、その品質まで責任を持とうという方式である。きっかけとなった記事もこのパターンを所有権の決定に分類し、その代償をドメイン間の標準合意が必ず要る点として書いている。所有を分けた代わりに互いにそろえるべきものが増えるという意味だ。

所有が実際に成立するには最低でも四つが要る。

  • 個人ではなく名前のあるチームでなければならない。担当者一人なら、その人が転職した瞬間に契約が孤児になる
  • そのチームの目標に消費者への影響が入っていなければならない。下流が壊れても自分の指標が悪くならないなら、予告を守る理由がない
  • 予告を守れるリリース手順が要る。二週間の予告を約束したのに毎週ホットフィックスが出るチームでは約束が守られない
  • 断る権限が要る。入ってくる要求を全部受けなければならないチームは所有者ではなく下請けであり、下請けは責任を負えない

四項目のどれもツールが作ってくれない。目標設定と権限配分は組織図が決める仕事だ。オントロジーはスキーマと何が違うのかで同じ結論に別の経路で到達したことがある。構築費用より合意費用のほうが大きく、その請求書は技術ではなく組織に行く。

9. 小さく始める方法

全社導入計画から始める試みはたいてい失敗する。理由は単純だ。すべての表に契約を付けるにはすべてのチームの合意が同時に必要なのに、そんな合意は一度では出ない。そして成果が見える前に疲労が先に来る。

順序を変えるほうがいい。カバレッジではなく一度の成功事例を先に作る。

  1. すでに痛かった指標を一つ選び、それを作る表を一つか二つに絞る。会議で二つのチームの数字が割れたそれが対象だ。存在しない問題から始めれば誰も時間を割かないし、上流全体に手をつけようとすれば初週で止まる
  2. 定義を文章で書く。何を含めて何を除くのか、時間窓がどれだけか、重複をどう除くのかまで書く。この場で三つのチームが別の答えを出すのが正常であり、その会議そのものが最初の成果物だ
  3. 合意した文章を契約ファイルに移す。フィールドごとに意味を一行、有効範囲、鮮度の基準、所有チームと連絡経路。形式は公開規格を借りてくれば十分で、最初から作る必要はない
  4. 機械が数えられるものから自動化する。ヌル比率、値の範囲、到着時刻、前日比の行数変動。ここで捕まるものがすなわち前節の階段状の変更だ
  5. 生産者リポジトリに予告の規則を植える。そのフィールドを消したり意味を変えたりする変更で、PR テンプレートに消費者の一覧が出るようにする。止めなくてよい。見えるだけで行動が変わる
  6. 二つめの指標に行く。ここからは形式を複製する。一つめの半分の時間で済む

五番目が安いわりに効果が大きいほうだ。強制ではなく可視性なので反発が少なく、生産者の側から見ても自分が何を壊すのかを初めて見ることになる。静かな事故のほとんどは悪意ではなく知らずにやったことだ。

そして最初の事例が実際に事故を捕まえた瞬間を記録しておく。「あのときのずれをこの検査が捕まえた」という一文が、三つめの指標からの抵抗を目に見えて減らす。

10. やりすぎると起きること - 契約が官僚制になるとき

反対側の失敗もはっきりある。契約をうまく導入した組織より契約を過剰に導入して無力化した組織のほうが多い。

  • 全表への義務化。すべての表に契約ファイルを強制すると、誰も読まないファイルが数百できる。文書が増えるほど文書の信頼度は落ち、結局は契約があるという事実そのものが信号にならない
  • 承認段階の増殖。フィールド一つの追加に二週間かかると、人は契約の外に出る。臨時の表、個人のノートパソコンの抽出、スプレッドシートが増える。ずれがなくなったのではなく見えないところに移ったので、これが最悪の結末だ
  • 通知過多。閾値を細かく取ると違反通知が毎日数十件来る。静かに壊れる問題を捕まえようとしてうるさいが無視される通知だけを増やしたことになる
  • 完璧な定義の追求。アクティブユーザーの定義会議が六週目に入っているなら、それは合意が難しいのではなくそもそも二つの指標だったのだ。こういうときは一つにまとめようとせず名前を二つに分けるほうが速い

四つが一つの方向を指している。契約を変える手続きが重くなるほど定義は古いまま固まり、そうなると契約は変化を知らせる装置ではなく変化を止める装置に変質する。判断基準は一つにしておけばいい。契約を新しく付けるときに「これを破ったら誰が痛いのか」に名前を挙げられなければ付けない。痛む人のいない契約は管理対象を増やすだけで、そうして増えた一覧が本物の契約を隠す。集めた観測データがなぜ読まれないのかでダッシュボードについて言ったことがここでそのまま繰り返される。増やすことにはすでに動力があり、手続きにしなければならないのは減らすほうだ。

確認できなかったこと

  • データ契約を導入した組織の比率や効果を測った公開調査は見つからなかった。この記事の判断は構造の説明であって測定値ではない
  • 「アクティブユーザー」の定義が組織間で実際にどれだけ割れるかに関する公開統計もない。上の表の分かれ道は定義を分解した結果であって調査結果ではない
  • 意味のずれがAI 成果物の誤り率にどれだけ寄与するかを定量化した資料は確認できなかった
  • Open Data Contract Standard は規格文書にある節の一覧だけを確認した。実際の現場でどの節が埋まりどの節が空くのかは確認していない
  • きっかけとなった記事に出てくる三つの事例は著者が挙げた例であり、事例の出典や検証の有無は原文に書かれていない。三つの強制地点の効果を比較した公開実験もないので、効きめと代償の記述は各地点がいつ働きいつ迂回されるかから導いたものだ

結論: 運ぶ仕事は終わり、合意する仕事が残った

保存が難しかった時代には、データの問題が技術の問題に見えた。容量を増やし処理を速くすれば前に進んだ。その層が解決してみると、残ったものは性格が違う。同じ単語を互いに別の意味で使う人たちのあいだで一つの意味を選ぶ仕事であり、これはツールでは終わらない。

だからこの記事の結論はツールの名前ではなく三つの文だ。スキーマは形式しか語らず、意味はその外にある。形式はうるさく壊れ意味は静かに壊れるのに、組織の投資はうるさいほうにだけ付いている。契約は定義が変わらないという約束ではなく、変えるときに黙って変えないという約束だ。

今日できることもその分だけ小さい。前四半期に数字が割れた指標を一つ選び、その定義を一段落で書き、その段落を誰が守るのか名前を書く。契約はそこから始まる。形式はあとから付けても遅くない。
