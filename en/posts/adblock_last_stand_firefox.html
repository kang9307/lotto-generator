When Extensions Lose Permissions, What Changes in the Browser

The two ways content blocking works, why the model changed, and the arithmetic left for readers and publishers

Aug 16, 2026 Tech & IT

Introduction: One Extension Did Not Simply Switch Off

You open the browser and the blocker you have used for years is greyed out with a note saying it is no longer supported. There is no button to turn it back on. This is not an abandoned project or a failed update. The shape of the permissions a browser hands to extensions was redesigned, and that extension was built assuming the old shape.

It is easy to consume this purely as an ad-blocking story, but what changed is broader. What an extension may ask a browser for was rebuilt from the ground up, and password managers, translators, and accessibility tools fall under exactly the same rules. Content blocking was simply the first and most visible place the redesign surfaced.

So this piece is not about which extension died. It is about what becomes possible and impossible in a browser once the permission structure shifts. Dates and figures here were verified on 16 August 2026, and where a schedule has not been announced, this article stops at the announced range rather than guessing.

Why browser diversity matters in its own right is covered in Leaving Mozilla - Firefox's Place and the Road to Community-Driven Growth, and the principle that applications should not rebuild what the browser already does is in The Don't Roll Your Own Principle 2026. Here we look at one layer only: extension permissions.

1. How Content Blocking Works, Technically

1.1 The Requests a Single Page Sets Off

Opening a web page is not downloading one file. Once the HTML document arrives, what it contains spawns dozens to hundreds of further requests for scripts, stylesheets, images, fonts, ad slots, analytics tags, and social widgets. Many of those go out to domains other than the one you typed.

A blocker intervenes at three distinct layers. This split governs everything that follows, so it is worth fixing first.

  • The network request layer — certain requests are never sent at all, which saves bandwidth and prevents the tracking in one move
  • The element hiding layer — regions of a page that already arrived are removed from view, so the request went out but the layout stays tidy
  • The page script layer — intervening in how the page's own code behaves. This carries the most power of the three and is where the new permission model narrowed most sharply

Most of what people call ad blocking is produced by the first two layers, and both largely survive under the new model. The argument lives at the third layer and in the expressiveness of the first.

1.2 Interception - The Extension Decides

The older approach works like this. Just before the browser sends a request, it calls into the extension's code. The extension receives the address, the resource type, and the page it came from, computes a verdict in its own code, and returns pass or block. The extension is the judge.

The power of this structure is obvious. The matching logic can be written freely in a programming language. Conditions combine, state persists, and filter lists can be swapped out while the browser is running. When a new pattern shows up, one changed line in a list takes effect immediately.

The cost is equally obvious. First, the extension has to be able to see the address of every request, which in practice is a live feed of the entire browsing history. Second, the request waits for the extension to answer, which places extension code on the critical path of every network call.

1.3 Declarative Rules - The Browser Decides

The new approach inverts the order. The extension registers a rule list in advance — block anything matching this address pattern — and when a request actually occurs, the browser engine applies those rules itself. The extension's code is never called. It does not even learn that the request happened.

Two things are gained: blocking works without granting the extension read access to browsing, and the verdict resolves in native code so nothing waits on an extension. Two things are lost: the matching logic has to fit inside the rule grammar, and the number of rules is capped.

One common misreading is worth clearing up. The declarative model did not make blocking impossible. Request blocking driven by address patterns still works fine. What narrowed is expressiveness and the update path. That is precisely why most pages feel unchanged, and the gap only opens against parties that change shape frequently.

2. What Each Model Gives Up and Gains

Placing them side by side shows that this was not a feature cut but a trade. Capability shrank, and so did permission.

The last two rows sit closest to the substance of the dispute. The old model is powerful but hard to review and blurry about who owns a performance problem. The new one is reviewable and predictable but not powerful.

3. Why It Changed (1) - The Security and Performance Case

Dismissing this side as pretext will lead you to a wrong conclusion. The grounds are real.

  • The permission is too broad — reading every request means reading every address visited. Given how commonly search terms and account identifiers ride in URLs, that reach is far wider than a list of sites
  • Permission travels with ownership — widely installed extensions changing hands and then changing character has been reported repeatedly. A user consented once at install, and that consent attaches to the extension, not to the person who wrote it
  • Extension code sits on the critical path — if the extension is slow to decide, the whole page is slow, and users attribute that delay to the browser. On top of that, extensions in the old model stayed resident in memory the entire time the browser was open; the new model wakes them on demand and lets them sleep
  • No remotely hosted code — what was reviewed and what actually runs become the same thing. When matching logic could be fetched from elsewhere at runtime, a reviewer's snapshot could differ from what ran on a user's machine

That last point is really a defence against extensions posing as blockers rather than against blockers themselves. Content blocking is exactly the category where demanding sweeping permissions looks natural, which has long made it a convenient disguise. Seen from anyone who has dealt with that problem, narrowing permissions is not a strange direction to take.

4. Why It Changed (2) - The Conflict of Interest Argument

Whether the reasoning holds up and who made the decision are separate questions. On the second question, the argument runs as follows.

The company behind the world's most-used browser earns overwhelmingly from advertising. When that company changes the extension specification in a way that narrows what ad blockers can express, part of the benefit lands on its own revenue side. Motive cannot be proven, but the alignment of interests needs no proving. Regulators treat this arrangement as a category of its own for the same reason.

Stopping there, however, produces a conspiracy theory. What turns the observation into something testable is a technical counterexample.

  • In May 2022 Mozilla stated publicly that it would keep interception under the new specification while also shipping the declarative API for compatibility
  • So the claim that security requires removing interception is not a necessity. A browser offering both exists
  • The existence of an alternative makes it legitimate to ask why the choice went the way it did. There is simply no answer available

Fairness requires putting the counterarguments alongside it.

  • Shipping both leaves the permission problem untouched. Dangerous extensions will still request interception and users still cannot tell them apart. Offering both can be read as handing the decision to users rather than solving anything. Nor is the browser that kept interception outside the web of interests — Mozilla's income also depends heavily on a default search agreement
  • A decision by the market leader effectively becomes the standard. That other browsers on the same engine end up bound by an upstream decision regardless of their own view is a separate problem, and it is about engine consolidation rather than advertising

Neither explanation cancels the other. A genuine security case does not make the conflict of interest disappear, and a conflict of interest does not make the security risk false. Motive cannot be adjudicated with the available material; outcomes can be checked. From here on, only outcomes.

5. What the Declarative Model Actually Constrains

5.1 The Rule Ceilings

This model comes with published numbers. The constants below are defined in the official API reference.

CategoryCeilingNature
Static rulesets in total100Bundled in the extension package
Static rulesets enabled at once50The rest sit disabled
Guaranteed enabled static rules30,000Guaranteed up to this count
Dynamic rules30,000Updatable at runtime
Unsafe rules among dynamic5,000A sub-cap inside the 30,000
Session rules5,000Cleared when the browser shuts down
Regular expression rules1,000Applied per rule type

A safe rule here means one that only lets a request through or stops it — block, allow, allow-all, and scheme upgrade. Rules that rewrite headers or redirect elsewhere are not in that set and must fit through the narrower door of 5,000. In effect, the more powerful the action, the lower the ceiling.

What these numbers mean in practice is one thing. Enabling several large, widely used filter lists wholesale is no longer viable. Blockers built on this model therefore curate what they ship and offer users tiers such as basic, optimal, and complete.

5.2 Where Static and Dynamic Rules Diverge

Despite sharing the number 30,000, the two kinds behave completely differently.

  • Static rules are files inside the extension package. A human can read them at review time, which is the advantage; changing one line requires shipping a new release, which is the cost
  • Dynamic rules can be added and removed while the extension runs. They apply without a release, but the cap is lower and the more powerful kinds only fit within 5,000
  • Session rules vanish when the browser closes or the extension updates, so they cannot serve as storage for a persistent filter list

5.3 Response Time - The Round Trip Gets Longer

Suppose a new delivery pattern appears. Under the old model a rule is added to a filter list, the extension fetches the list, and the next page load reflects it. That is a matter of hours.

Under the new model, if that fix belongs in a static rule, it has to go through a release and a store review. If it can be handled as a dynamic rule it is fast, but that space is small and the stronger rule types make it smaller still. However quick the list maintainers are, the distribution path itself got longer.

And there is no layer here that decides based on context beyond the request — what the page has already done, for instance. Matching on address, type, and origin is the whole of it. That is the concrete meaning of saying the third layer narrowed sharply.

What matters in this table is not the individual dates but the relationship between the second and fourth columns. Some browsers fill the gap left by narrowed extension permissions by taking the specification in a different direction (Firefox), and others by pulling blocking inside the browser (Vivaldi, Brave). The latter is immune to specification changes, but the judgment about what to block now sits with the vendor. Rather than more choice, this is closer to a change in who holds your trust.

7. Your Options (1) - Browsers and Extensions

There are three practical routes. Less better or worse than suited to different conditions.

  • Move to a browser that keeps interception — the only way to retain the full capability. The cost is the migration itself; if passwords, bookmarks, extensions, and sync are all tied to one ecosystem, budget half a day
  • Use a declarative-model blocker — on most sites you will not notice a difference, and the smaller permission footprint can make this the better privacy choice. The trade is blocking less while seeing less
  • Use a browser with built-in blocking — unaffected by extension specification changes, but rule updates and policy rest with the vendor and fine-grained list control is harder

Some concrete criteria, since ending on it depends on your situation would be useless.

  • If the device is managed by your employer, switching browsers is not on the menu. The only layers left are a different extension and the DNS layer discussed next
  • If a work extension exists only in one store, migration is genuinely expensive, and running two browsers is the realistic answer — the old one for work, another for personal reading. Conversely, if you have a single profile and your passwords live outside the browser, migration is a thirty-minute job and there is little reason to postpone it
  • If your goal is tracking rather than advertising, built-in tracking protection combined with a declarative blocker is usually enough, and the capability gap barely matters

8. Your Options (2) - DNS and Network Level

There are layers outside the browser as well. They are not substitutes for an extension but tools of a different character. Expect the same thing and you will be disappointed; expect something different and they are useful.

8.1 DNS Level - Cutting at Name Resolution

This blocks the response for certain hostnames at the point where a name is turned into an address. It does not go through the browser, so it applies to every app on the device.

  • Upside — no extension permissions at all, coverage extends to apps and games outside the browser, and the performance and battery cost is low
  • Limit 1 — decisions are made at hostname granularity only. When one domain serves both what you need and what you do not, there is no way to split it. Block it and features break; allow it and nothing is filtered
  • Limit 2 — there is no element hiding. The request failed but the space stays empty and the layout looks off
  • Limit 3 — if the browser is set to use its own encrypted DNS, it never reaches the system resolver, which is where the puzzle of rules that work everywhere except in the browser comes from. Per-site exceptions are awkward too — unblocking a domain for one site unblocks it everywhere

8.2 Network Level - One Rule for the Whole Line

Rules go on the router or a dedicated resolver and apply to every device on that network.

  • Upside — it covers devices where you cannot install anything at all: smart TVs, consoles, and IoT hardware
  • Limit 1 — it becomes a single point of failure. If that box stops, name resolution for the whole household stops, and to everyone else this looks simply like the internet is down
  • Limit 2 — it cannot be toggled per device or per person, so you end up blocking something another household member needs
  • Limit 3 — it is still hostname-level and cannot see inside encrypted connections. Seeing inside would mean terminating and re-establishing the connection in the middle, which is not a blocking technique but a wholesale change to the trust model, a different problem entirely. And the moment you leave the house on a mobile connection, this layer disappears

The general principle about where trust is relocated is set out in What a VPN Protects and What It Does Not. DNS and network blocking face the same question — a risk was not removed so much as moved onto someone else.

8.3 The Real Cost of Stacking Layers

Stacking layers raises the block rate and destroys your ability to diagnose failures. When a login button does nothing, you cannot tell whether the cause is the extension, DNS, the router, or simply the site being down. There is one workable procedure: when something breaks, turn off the outermost layer first and try to reproduce, then work inward. Without deciding this order before adding layers, the usual ending is switching everything off.

Breakage arrives in a few recognisable shapes. Sign-in flows that use an external account cut out midway because the authentication redirect passes through an analytics domain, and payments get declined because a risk-scoring script was blocked. Embedded video, maps, and comment widgets failing to appear at all, or images loading halfway, are also common. A site detecting the blocker and refusing access to the article is not breakage but intended behaviour, and worth telling apart.

9. From the Side of an Ad-Funded Site

Something to state first. This site runs on advertising. That makes this section an interested account, and writing it while hiding that fact would be worse. There is no intent here to condemn blocking or to recommend it. The structure gets described; the judgment stays with you.

Free access paired with advertising is a bargain: you do not pay at the moment of reading, and you pay instead with attention and some data. Blocking is the state of holding up only one side of that bargain. The counterargument stands just as firmly — the reader never explicitly agreed to those terms, and ad delivery networks have repeatedly been reported as a distribution path for malware. Taken as a moral argument, it does not resolve.

What does resolve is the structural account. When blocking becomes widespread, other revenue routes fill the gap, and each distorts differently.

  • Subscriptions and memberships — the most stable, but there is a ceiling on how many any one person will carry, and that ceiling favours large outlets over small sites
  • Donations — the share who actually pay is very low, so a small group of committed readers carries everything, which creates an incentive to lean toward that group's tastes
  • Sponsorship and native advertising — the advertiser moves closer to editorial. Disclosure obligations follow, and failing them makes it a regulatory matter
  • Affiliate links — revenue arrives only when the reader buys, which builds bias into the recommendation itself. Writing the conclusion that you do not need this becomes structurally hard
  • Paid newsletters, events, and content licensing — traffic decouples from revenue, weakening the incentive to write the informational pieces that arrive through search, and an individual site has little leverage negotiating with data buyers
  • Consent or pay — readers who decline tracking are asked to pay for access. It has been deployed in some jurisdictions and has drawn regulatory scrutiny

One more thing. Blocking is not the only pressure on that revenue base. Answers that complete inside the search results page, removing the click to the site entirely, are advancing in parallel, and for many publishers that force is the larger one. Leaving it out makes the picture simpler than it is.

The only practical suggestion is this. Instead of reaching a moral verdict, check once which sites you would miss if they disappeared and how those sites make money. After that check, whether you block, add an exception, or contribute, you will at least know what you chose.

10. What Could Not Be Confirmed

The following could not be pinned down from primary sources and so is not asserted in the body.

  • Brave's current support state for old-specification extensions and any end date — its built-in blocker being independent of the extension architecture is described consistently, but the extension support status could not be confirmed from official documentation
  • The rule ceiling for Safari content blocking — figures appear in filter-list vendor documentation, but they could not be verified in Apple's own documentation and so were left out of the table
  • Timelines for Opera and Samsung Internet — these appear likely to follow upstream engine policy, but no official statement from either was confirmed. Edge's timeline likewise marks the cut-off for updates to old-specification extensions as undetermined
  • How many rules declarative-model blockers actually ship — configurations differ by tier and change over time, so no specific figure is given
  • Firefox's restatements after 2022 — a recent reaffirmation was reported in the press, but the original post was not read directly, so the Firefox position here rests solely on the May 2022 official blog statement

Conclusion: What to Judge By

Summarising this as the death of ad blocking gets most of it wrong. The accurate summary is this: the permissions an extension may request have shrunk, and the capabilities that depended on them shrank with them. Content blocking was simply the heaviest user of those permissions and therefore the first casualty anyone noticed.

Three criteria remain.

  • Decide first what you are trying to stop. Ad display, tracking, and bandwidth each need a different layer. If tracking is the goal, a declarative blocker plus the browser's own protections is usually sufficient
  • Capability and permission move together. A tool that blocks more also sees more. Chasing capability without knowing what you granted can relocate the very risk you meant to remove onto the tool
  • Set a diagnostic order before stacking layers. With browser, extension, DNS, and network all engaged, a single failure has four candidate causes. Deciding in advance to disable from the outside in removes that cost entirely

This landscape is not fixed. Published ceilings can be adjusted and browser policies can change. The dates and numbers here were verified against each vendor's own documentation on 16 August 2026, and if you are reading this six months later, check each browser's official timeline again.
