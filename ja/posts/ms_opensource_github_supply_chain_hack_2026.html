MS オープンソース GitHub サプライチェーン攻撃 2026 - ミアズマワームの解説

ミアズマワームが見せたソフトウェアサプライチェーン攻撃の新しい顔

2026-06-11 IT・技術

はじめに: 最も信頼されていたリポジトリが武器になった日

開発者にとって、マイクロソフトの公式 GitHub リポジトリほど無批判に信頼される場所も少ないでしょう。Azure 組織のデプロイアクション、microsoft 組織のサンプルコード、MicrosoftDocs のドキュメント。私たちはこれらを毎日 npm install で、git clone で、GitHub Actions ワークフローの一行で取り込みながら、「これが悪意あるものかもしれない」と疑うことは一度もありません。信頼とは効率の別名であり、効率とは開発速度だからです。

ところが2026年6月8日、まさにその信頼が攻撃の通路となる事件が起きました。GeekNews でも6月10日に話題となったこの事件の核心はこうです。マイクロソフトがホストする GitHub プロジェクト73個が侵害され、ソースコードにパスワード窃取マルウェアが注入され、その結果 AI コーディングツールを使う開発者の認証情報が窃取されたというものです。報道によれば、GitHub はこの73リポジトリをわずか105秒で自動的に無効化しましたが、その短い露出時間とすでに広がったワームの影響範囲は決して小さくありません。本稿では、何が起きたのか、ソフトウェアサプライチェーン攻撃とは何か、なぜオープンソースと開発ツールが標的になるのか、そして開発者と組織が今すぐ取るべき防御策を、理解と防御の観点から整理します。悪用コードや再現手順は扱いません。私たちの目的は攻撃ではなく防御だからです。

1. 何が起きたか - ミアズマワームの侵入

今回の主犯は ミアズマ（Miasma） という名のマルウェアです。一部のセキュリティ業界では「春の枯病（The Spring Blight）」という別名でも呼ばれます。最も恐ろしい特徴は、これが単なる静的なマルウェアではなく 自己複製型のワーム である点です。ワームは一箇所にとどまらず、感染した環境で認証情報を盗み、その認証情報で他のリポジトリに自分自身を植え付け、エコシステム全体へ広がります。

報道によれば、このワームはマイクロソフトの中核 GitHub 組織4つ — Azure、Azure-Samples、microsoft、MicrosoftDocs — に侵入し、その結果 73のリポジトリ が無効化されました。その中には、多くの組織が Azure Functions のデプロイに使う公式 GitHub Action である Azure/functions-action も含まれていました。このリポジトリが無効化されると、そのアクションに依存していた多数の CI/CD パイプラインが一斉に止まりました。信頼されたツール一つの侵害が、それを使うすべての場所の麻痺につながったのです。

サプライチェーン攻撃の本質は、一点を突いて全体を崩すことにある。最も信頼されるノードが侵害されれば、その信頼がそのまま感染の高速道路になる。

特に注目すべきは、これが 再侵害（re-compromise） と分析されている点です。報道によれば、5月中旬、マイクロソフトのオープンソースプロジェクトである Durable Task — 開発者が信頼性の高いワークフローアプリを作るのを助けるツール — がまず侵害され、公式 SDK の悪性バージョンがパッケージレジストリに短時間で押し込まれました。6月の今回の事件は、その Durable Task 侵害が完全に除去されなかったか、窃取された認証情報がローテーションされないまま残り、攻撃者が足場を維持していたことを示唆します。一度の不完全な対応が、二度目のより大きな事故として返ってきたわけです。

2. マルウェアはどのように認証情報を盗んだか

具体的な悪用手法は示さず、脅威モデルの観点からこのワームの動作構造だけを押さえます。これは防御点を特定するためであり、再現のためではありません。

報道によれば、ミアズマは複数の侵入経路を同時に用いました。セキュリティ業界の分析によると、攻撃は大きく三つの波として展開されました。

  • 悪性パッケージのインストールフック: パッケージに preinstall のようなインストール段階のフックを仕込み、開発者が依存関係をインストールした瞬間にコードが実行されるようにしました。これはサプライチェーン攻撃の古典的手口です。
  • インストールフック回避手法: 標準のインストールフックを使わずに npm install の過程でコードが実行される変種手法が報告されました。従来の防御が「インストールフック」だけを監視していた隙を正確に突いたのです。
  • エディタを狙った直接コミット: 最も新しい波です。窃取した貢献者の認証情報でリポジトリに悪性コミットを直接押し込み、開発者がそのリポジトリを AI コーディングツールや IDE で開いた瞬間 に認証情報収集ペイロードが作動するようにしました。

いったん開発者環境内で作動したワームは、報道によれば AWS、Azure、GCP、Kubernetes、npm、GitHub の認証情報を収集し、GitHub Actions のシークレットを外部サービスへ流出させました。そして盗んだトークンで、被害者が書き込み権限を持つすべてのリポジトリに自分自身を再コミットし、自律的に広がりました。この「盗み → 広め → また盗む」という循環こそ、ワームをこれほど危険にする仕組みです。

3. AI コーディングツールが新たな攻撃面になった理由

今回の事件で最も衝撃的な進化は、マルウェアが パッケージマネージャを飛ばして開発者のエディタを直接狙った 点です。報道によれば、三つ目の波の攻撃は、開発者が感染したリポジトリを Claude Code、Gemini CLI、Cursor、VS Code のような AI コーディング環境で開くだけでペイロードが作動するよう設計されていました。

これまでサプライチェーン防御は、主に preinstall、postinstall、setup.py のようなパッケージのインストールフックを監視することに集中してきました。ところが「リポジトリを開くだけでトリガーされる」攻撃の前では、この防御線が丸ごと無力になります。AI コーディングツールはリポジトリの設定ファイルやコンテキストを自動で読み解釈するため、その自動性自体が攻撃者に新たな実行経路を与えたのです。

これは AI コーディングツールが本質的に危険だという意味ではありません。ただ 「開発者が明示的に何かを実行しなくてもコードが動きうる地点」が増えた という信号です。ツールが賢く自動的に処理するほど、その自動性を狙う攻撃面も同時に広がります。AI エージェントに権限と境界をどう設計すべきかは、別稿 ネットワークセキュリティ - ファイアウォール でも関連して扱っています。

4. ソフトウェアサプライチェーン攻撃とは何か

一歩引いて概念を整理します。ソフトウェアサプライチェーン攻撃 とは、最終ソフトウェアを直接攻撃する代わりに、そのソフトウェアが作られ配布される過程 — すなわち「供給網」の一点を汚染する攻撃です。

現代のソフトウェアはほぼ例外なく、数百、数千の外部依存の上に築かれます。私たちが書いたコードは氷山の一角で、その下には自分で書いていない膨大なライブラリ、ビルドツール、コンテナベースイメージ、CI/CD アクションが敷かれています。攻撃者はその中で最も弱く、最も信頼される環を一つ狙います。その環が汚染されると、それを取り込むすべての下流へマルウェアが 自動的に 流れ込みます。

汚染された依存一つが数千のプロジェクトへ広がるシナリオは、もはや仮説ではありません。業界報告によれば、2025年だけで npm、PyPI、Maven などの主要エコシステムで45万を超える悪性オープンソースパッケージが新たにカタログ化され、前年比で約75%の増加でした。その半分以上が認証情報窃取・データ収集を狙うものに分類されます。ミアズマは、この巨大な流れの最も精巧で象徴的な事例の一つにすぎません。

5. なぜオープンソースと開発ツールが標的なのか

攻撃者の立場では、オープンソースと開発ツールは「費用対効果」が圧倒的な標的です。理由は次のとおりです。

  • 広範な再利用: 人気パッケージ一つは数万、数十万のプロジェクトに入ります。一つ汚染するだけで到達範囲が天文学的です。
  • 自動インストール・実行: 依存関係は人が一つ一つ精査せず自動でダウンロードされ実行されます。インストールフックやビルドスクリプトはしばしば何の疑いもなく動きます。
  • 高価値な認証情報の集中: 開発者のワークステーションや CI 環境には、クラウド鍵、デプロイトークン、パッケージ発行権限といった「王冠の宝石」が集まっています。一箇所を抜くと収穫が大きいのです。
  • 信頼の継承: メンテナ一人のアカウントを盗めば、その人が信頼される分だけ悪性コードも信頼されます。ミアズマがマイクロソフト組織を狙った理由が、まさにこの信頼の重さです。

ここで核心の教訓が見えます。信頼は攻撃者にとって最も魅力的な資産 だということです。あるリポジトリを信頼するほど、そこが侵害されたときの被害は大きくなります。したがって成熟したセキュリティは「信頼するが検証せよ」を超え、「信頼の大きさだけ検証も大きくせよ」へ進まねばなりません。

6. 開発者が露出する経路

では、普通の開発者は具体的にどの分かれ道でこうした攻撃に露出するのでしょうか。防御を設計するには、露出経路をまず明確に描く必要があります。

6.1 依存関係を取り込むとき

npm install、pip install の一行が数十の推移的依存を一緒にダウンロードします。そのうち一つでも汚染されていれば、インストール段階のフックやビルドスクリプトがただちに攻撃者のコードを実行します。

6.2 ビルドと CI/CD パイプラインで

GitHub Actions のような CI ワークフローは、強力な権限とシークレットを持って動きます。汚染されたアクションやコンテナイメージ一つがパイプラインに入ると、そのシークレットが丸ごと外部へ流出しかねません。今回の事件でシークレットが外部サービスへ窃取されたのが、まさにこの経路です。

6.3 リポジトリを開くとき

最も新しい露出経路です。感染したリポジトリを AI コーディングツールや IDE で開く行為自体が、設定ファイルに潜むペイロードを作動させるトリガーになりえます。「クローンして開いただけ」なのに認証情報が漏れるのです。

7. 防御策 - 依存関係の検証とハッシュ・署名

ここから本題の防御策です。第一の軸は 依存関係の完全性を検証する ことです。

  • バージョン固定とロックファイル: package-lock.json、poetry.lock のようなロックファイルで依存バージョンを固定し、無分別な自動アップグレードを避けます。ある日突然悪性バージョンがこっそり入るのを防ぐ一次防御線です。
  • ハッシュ・完全性検証: ロックファイルの完全性ハッシュを信頼し、インストール時にハッシュが一致するか検証するよう設定します。パッケージ内容がひそかに変われば、ハッシュがずれて検知されます。
  • 署名検証: 可能であればパッケージやコミットの署名（例: Sigstore、コミットの GPG 署名）を検証し、「本当にそのメンテナが作ったか」を確認します。
  • インストールスクリプトの精査と遮断: 信頼できないパッケージのインストールスクリプト自動実行を無効化するか、隔離環境でのみインストールを行います。
  • 依存関係レビューの自動化: SBOM（ソフトウェア部品表）を生成し、既知の悪性パッケージ・脆弱性データベースと自動照合するツールをパイプラインに組み込みます。

8. 防御策 - シークレット管理と 2FA

第二の軸は 認証情報そのものの露出面積を減らす ことです。マルウェアが入っても盗むものが少なく、盗んだものがすぐ無効になれば、被害は制御されます。

  • 平文シークレットの排除: トークンや鍵をコード、.env、シェル履歴、環境変数に平文で置かず、専用のシークレットマネージャに保管します。今回のワームはまさに環境変数と設定ファイルを漁りました。
  • 短命・OIDC トークン: 長寿命の静的トークンの代わりに、短く失効する OIDC ベースのトークンを使います。窃取されてもすぐ無効になり、露出の有効期間が短くなります。
  • 最小権限の原則: CI トークンや PAT に必要最小限のスコープだけを与えます。被害の上限はトークン権限の大きさそのものです。
  • 二要素認証（2FA）の義務化: すべての GitHub・パッケージ発行アカウントに 2FA を強制し、アカウント乗っ取り自体を難しくします。
  • シークレットスキャンとプッシュ保護: トークンが誤ってコミットされるのを防ぎ、露出時の自動失効フローをつなぎます。

これらの原則は結局 最小権限の原則（Principle of Least Privilege） の直接的な適用です。「この認証情報が漏れたら何までできるか」をまず問い、その範囲を狭める思考は、トークンであれエージェントであれ同じです。一行の権限を狭めることが、一度の侵害被害を減らします。

9. 被害確認と対応 - 侵害が疑われるなら

もし影響圏内にいた可能性があるなら、何をどう点検すべきでしょうか。報道とセキュリティ業界の推奨を基に整理します。

  1. 組織内の異常リポジトリ点検: 不明な新規公開リポジトリができていないか、特にワームの痕跡として知られる説明や JSON 形式でコミットされたシークレットがないか検索します。
  2. ワークステーションとビルド環境の点検: GitHub での異常な活動、不明な新規リポジトリの作成、VS Code や AI コーディング CLI を通じた予期しないバックグラウンドプロセスの実行がなかったか確認します。
  3. 全面的な認証情報のローテーション: 当該システムからアクセス可能なすべての認証情報 — GitHub トークン、npm トークン、AWS 鍵、Azure サービスプリンシパル、GCP サービスアカウント、SSH 鍵、Kubernetes シークレット、Docker 設定、環境変数やシェル履歴にあった値 — を直ちにローテーションします。
  4. 依存関係の再検証: 最近インストール・更新した依存のバージョンとハッシュを点検し、疑わしいバージョンは既知の正常版へ戻します。
  5. 監査ログの確認: 組織とクラウドの監査ログで、見知らぬ IP・時間帯のアクセス、大量クローン、異常なプッシュがなかったか調べます。

核心は ローテーションを先延ばしにしないこと です。今回の再侵害が5月の認証情報がローテーションされなかったことに端を発したという分析は、不完全な対応がいかに二度目の事故を招くかをはっきり示しています。疑わしければローテーションしましょう。失効したトークンは無害です。

10. 脅威モデルの比較

今回の事件の構造的含意を表に圧縮します。同じ認証情報でも、どの環境で扱われるかで脅威モデルが変わります。

区分 従来のインストールフック攻撃 リポジトリを開くトリガー攻撃（新種）
トリガー時点 パッケージインストール時 リポジトリを IDE/AI ツールで開くとき
主な防御線 インストールフックの監視・遮断 設定ファイルの検証・サンドボックス
従来防御の効果 比較的有効 相当部分が無力
窃取対象 インストール環境の認証情報 エディタ・クラウド・CI の認証情報

この表が語ることは明白です。サプライチェーン防御が「インストール段階」一箇所にとどまってはならない、ということです。コードが実行されうるすべての地点 — インストール、ビルド、そして今や「リポジトリを開く行為」まで — を脅威モデルに入れる必要があります。マルウェアの仕組みと対処については ネットワークセキュリティ - マルウェア でも関連して扱っています。

11. サプライチェーンセキュリティの教訓 - 信頼を設計せよ

最後に一歩引いてバランスの取れた視点を持ちましょう。こうした事件が起きると「オープンソースは危険だから使うのをやめよう」「AI コーディングツールを切ろう」という反応が出やすいものです。しかしそれは正しい結論ではありません。オープンソースと自動化ツールの生産性の利得は圧倒的であり、それを丸ごと捨てるのは、虫を捕るために家を焼くようなものです。

合理的な態度は 信頼を漠然とした感情ではなく、設計された手順に変えること です。依存を固定し、ハッシュと署名を検証し、シークレットをマネージャに閉じ込め、トークンを短命にし、全アカウントに 2FA を強制し、疑わしければ直ちにローテーションする — これらの手順が整えば、ミアズマのようなワームが入っても盗むものが少なく、広がる道が狭まります。

同時に、プラットフォームとメンテナにも責任があります。GitHub が73リポジトリを105秒で自動遮断したのは防御の好例ですが、その105秒さえサプライチェーンでは長いことがあります。侵害された認証情報を最後までローテーションし、足場を完全に除去し、再侵害の循環を断ち切るのは、結局運用主体の務めです。良いセキュリティは一度の遮断で終わらず、根を抜くまで続きます。

結論: 依存一つを疑い、トークン一つを狭めよ

マイクロソフト GitHub を襲ったミアズマワーム事件は、最も信頼されるリポジトリさえサプライチェーン攻撃の通路になりうること、そして AI コーディングツールの自動性が新たな攻撃面を開いたことを圧縮的に示します。しかしこれは終末の信号ではなく、信頼を再設計せよという信号 です。

今すぐ適用できる三つで締めくくります。第一に、依存を固定し完全性を検証 しましょう。ある日こっそり変わったパッケージを捕まえるのが一次防御線です。第二に、シークレットをマネージャに閉じ込め、トークンを短命・最小権限に しましょう。盗むものが少なくすぐ無効になれば、被害は制御されます。第三に、侵害が疑われたら先延ばしせず直ちにローテーション しましょう。今回の再侵害が教えたように、ローテーションされない認証情報は二度目の事故の種です。信頼を享受しつつ、その信頼を手順で検証すること — それがサプライチェーン時代を安全に生きる開発者の基本です。
