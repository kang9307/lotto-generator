Project Valhalla in JDK 28: How a Decade of Work Finally Ships

Value classes, heap flattening, and scalarization dismantle Java's object overhead — what JEP 401 delivers and what it means for developers

2026-06-22 Dev & Infra

Introduction: Changing a 30-Year-Old Assumption

As of June 2026, one of Java's longest-running unfinished projects has finally entered the mainline. Project Valhalla, proposed by Brian Goetz in 2014, lands in JDK 28 as a preview through JEP 401 (Value Classes and Objects). Twelve years, roughly 197,000 lines of code, and dozens of design iterations later — what actually changed, what's still pending, and what does it mean in practice?

A note on scope upfront: JDK 28 is a planned release (based on published OpenJDK information and reporting as of June 2026). This article covers the preview feature as designed, not a finalized production release. Benchmark figures quoted are from reported benchmarks; actual results on any given workload will vary.

1. Why Did It Take a Decade? Java's Identity Crisis

Java has rested on one foundational assumption since 1995: every object has identity. Identity means two objects can hold identical values but still be distinct entities if they live at different heap addresses. This is why == compares references, why synchronized locks object instances, and why System.identityHashCode() has meaning.

Identity has a cost. Every Java object carries a 12-16 byte header beyond its payload. A Point holding two ints (8 bytes of data) pays 16 bytes of header tax. Worse, collections like ArrayList<Point> do not contain Point data — they contain an array of pointers to scattered heap objects. Accessing list.get(i).x requires two memory hops: array slot to pointer, pointer to object, object to field. Cache misses compound across millions of iterations.

Brian Goetz called this "Java's identity crisis." The fix is conceptually obvious: strip identity from small, immutable data types, and the JVM gains the freedom to place data inline, without pointers. The reason this took a decade is that Java's entire stack — JVM specification, compiler, standard library, tooling, and thirty years of ecosystem code — was built assuming every object has identity. synchronized(integer), identity-based == on boxed values, reflective identity tracking: all of these are woven into real codebases. Changing the foundation without fracturing the ecosystem required careful, iterative design — not slow progress, but honest complexity.

2. What Is a Value Class?

Valhalla's slogan has been consistent from the start: "codes like a class, works like an int." JEP 401 is the concrete realization of that goal.

2.1 Declaring a Value Class

A value class is declared with the value modifier:

value class Point {
    int x;
    int y;
    Point(int x, int y) { this.x = x; this.y = y; }
}

Two things change. First, Point instances have no identity. Second, the JVM is free to place the object inline — in arrays, in fields, or decomposed into registers — without breaking semantics. The code structure (constructors, methods, interface implementations) remains unchanged. What changes is the runtime representation.

value record is also supported. Records already express immutable data carriers, making value records the most natural combination.

2.2 Constraints That Enable Optimization

Value classes lose capabilities that ordinary classes take for granted: synchronized(point) is a compile error; System.identityHashCode(point) is meaningless; reference == becomes content equality. These restrictions are exactly what enable JVM optimization. Without identity, the JVM can copy, move, and reconstruct value instances freely — which is the prerequisite for both heap flattening and scalarization.

3. Heap Flattening and Scalarization — Where the Performance Comes From

JEP 401 delivers two performance techniques. They operate at different levels but point in the same direction: eliminate pointers, keep data close.

3.1 Heap Flattening

In ordinary Java, Color[] colors = new Color[1_000_000] allocates an array of one million pointers, each pointing to a scattered heap object. Accessing colors[i].r requires following the pointer chain. CPU prefetchers struggle with pointer-chasing patterns.

When Color is a value class, the array stores the r, g, b fields of each Color contiguously in a single memory block, with no pointers. Accessing colors[i].r is a direct offset from the array base. Iterating the array becomes a sequential memory scan — the pattern CPUs love most. Reported benchmarks show this can reduce aggregate memory footprint by 40-50% and deliver up to 3x speedups on iteration-heavy workloads.

3.2 Scalarization

Scalarization is a JIT compiler optimization that goes further. If a method creates Point p = new Point(3, 4) and only accesses p.x and p.y, the JIT can skip heap allocation entirely and place x=3, y=4 directly in CPU registers. No heap, no GC tracking, no pointer. The object is treated as a scalar — just like arithmetic on primitives.

This is impossible for identity-bearing objects: someone might hold a reference to the heap address, and moving or decomposing the object would be an observable change. Value classes eliminate that concern, giving the JIT the license to go fully scalar. This is the deepest optimization Valhalla unlocks.

4. What Is and Is Not in JDK 28

Based on public OpenJDK information and reporting through June 2026, here is a clear delineation.

4.1 Included in JDK 28 Preview (per published plans)

  • value class and value record declaration syntax (JEP 401)
  • Heap flattening and scalarization JVM optimizations for value classes
  • Migration of primitive wrapper classes (Integer, Double, Long, etc.) to value classes (preview scope)
  • Cheaper boxing — reduced boxing overhead for migrated wrappers
  • Activated with --enable-preview

4.2 Not in JDK 28 (Future Work)

  • Null-restricted types (non-nullable references, e.g., Point!)
  • Specialized generics (JEP 402): List<int> without boxing
  • 128-bit encodings
  • A fully stabilized JEP 402

The absence of specialized generics is the most significant gap. List<Integer> still boxes even with value classes, because the generics mechanism has not yet been specialized. Brian Goetz described JEP 401 as clearing the first barrier: removing identity makes scalarization possible, and scalarization is what specialized generics need underneath.

5. The Wrapper Class Migration Trap

Integer becoming a value class sounds like pure upside — Integer[] approaches int[] efficiency, boxing overhead shrinks. But there are meaningful behavioral breaks.

Code that synchronizes on an Integer instance will throw at runtime. This is not an obscure pattern; caches and state machines keyed on Integer monitors exist in real codebases. Value classes cannot serve as monitor locks — no identity, no lock. Similarly, == comparisons on boxed Integers relied on the JDK's caching of -128 to 127; the semantics of identity equality disappear once Integer is a value class.

The practical advice: audit any code that (a) synchronizes on a boxed type, or (b) compares boxed types with ==. These should be cleaned up before reaching a JDK where wrappers finalize their value class status. Since this is a preview in JDK 28, there is time — but the earlier the audit, the smaller the migration surprise.

6. Which Workloads Benefit Most

Valhalla is not a universal speedup. The gains concentrate in specific patterns.

6.1 High-Benefit Patterns

  • Large arrays of small value objects: financial trade records, geographic coordinates, RGB pixel buffers, sensor readings — anywhere that involves millions of small, immutable data items
  • Numerically intensive loops: vector arithmetic, matrix operations, statistical aggregation — workloads where cache utilization is the bottleneck
  • High-frequency creation and discard of small immutable types: currency amounts, coordinate pairs, option types, result wrappers

6.2 Limited-Benefit Patterns

  • Shared mutable state with locking: value classes cannot replace synchronized patterns
  • Code already using primitive arrays: if you already write int[] and avoid boxing, marginal gains are small
  • I/O and network-bound code: when the bottleneck is not memory layout, Valhalla optimizations are irrelevant

7. My Analysis: What This Means for Java Developers

Here is my read — not fact-delivery but interpretation.

7.1 Defensive Performance Patterns Become Optional

Java performance guidance has long included: avoid creating many small objects, prefer primitive arrays over object lists, minimize boxing. These rules exist because of Java's structural overhead. Valhalla lowers that overhead at the source. Some defensive patterns become less necessary. Small immutable data types can be expressed as value classes without guilt about the hidden cost. That is a genuine gain in design freedom.

7.2 Closing the Gap with C#, Rust, and Swift

C# has had struct value types for decades. Rust defaults to stack allocation with ownership semantics. Swift's struct is a value type. Java has been structurally disadvantaged in numerically intensive work compared to these languages. After Valhalla, that gap narrows substantially. Not eliminated — the JVM's safety guarantees (GC, bounds checking) still carry cost. But the specific disadvantage of pointer-chasing through object arrays largely goes away.

7.3 Migration Should Be Incremental

Valhalla does not break existing code by default. Existing class Point {} continues to work. Value class benefits require an explicit opt-in with the value modifier. The risk vector is the standard library migration: as Integer and friends become value classes in a finalized release, code that relied on their identity will break. My practical recommendation: explore value classes with --enable-preview now, target production adoption after a future LTS finalizes the feature, and start auditing synchronized-on-boxed-type patterns immediately.

8. Conclusion: Why a Decade Is Justified

Project Valhalla took twelve years not because progress was slow, but because the problem was genuinely hard. Changing a foundational assumption of a language used by millions of developers, across billions of lines of code, without breaking what works — that is not a routine engineering task. The 197,000-line commit count for JEP 401 reflects real complexity, not bureaucratic delay.

As of June 2026, JDK 28's preview of JEP 401 is the first gate. Value classes, heap flattening, scalarization — these three together structurally reduce Java's memory waste and cache-miss penalty on the workloads that suffer most. Specialized generics, when they arrive, will extend the gains into collection APIs and generic code. But what ships now is already meaningful. "Codes like a class, works like an int." After twelve years, you can write that code.
