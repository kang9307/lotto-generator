bigset — Build Live Web Datasets from a Single Natural Language Sentence

How the Fusion of AI Agents, Web Scraping, and ETL Is Democratizing Data Collection

2026-06-24 Tech & IT

Introduction: The Data Collection Bottleneck Still Lives in Human Hands

As of June 2026, AI writes code, summarizes documents, and generates images — yet asking for "a list of AI startups currently hiring" still requires an engineer to write a scraper, a data team to design a pipeline, or someone to manually fill a spreadsheet. This bottleneck has persisted longer than it should. The web holds vast, structurable data, but the entry cost of turning it into a usable table has been high enough that only well-resourced technical organizations could afford it.

bigset attempts to break that bottleneck with natural language. Developed by TinyFish and released as open-source (AGPL-3.0), it is a multi-agent system that takes a single sentence as input, infers a schema via AI, dispatches autonomous agents to crawl live web pages, deduplicates and validates the data, and returns a structured table. Scheduled auto-refresh keeps the dataset alive over time. This article analyzes bigset's architecture and real-world behavior, identifies where it genuinely shines and where expectations must be tempered, and addresses the legal and ethical questions that arise when you let agents loose on the live web.

1. What Is bigset — Natural Language to Structured Dataset

bigset's core promise is concise: one natural language sentence in, one structured dataset out. Input "YC companies currently hiring engineers, with funding stage, location, and job count" and a table matching that shape appears — no column design, no XPath, no ETL pipeline required.

1.1 Feature Summary

As of June 2026, bigset's documented capabilities include: Automatic schema inference — AI determines column names, data types, and primary keys from the input. Parallel web agents — one independent sub-agent per entity runs in parallel against the live web. Deduplication and source tracking — primary-key deduplication runs after collection; each row records the source URL. Auto-refresh — agents re-run on a user-set schedule (30 min, 6 h, 12 h, daily, weekly) to keep data current. Export — CSV and XLSX download supported.

1.2 Installation and Quickstart

bigset ships as an npm package. After npm install --global @adamexu/bigset, running bigset starts the local UI at 127.0.0.1:3500. Node.js 22+ is required, along with three external service credentials: a TinyFish API key for web search and page fetching, an OpenRouter key for LLM calls (Claude Sonnet and Qwen), and a Clerk account for authentication. Via the CLI: bigset create "topic" --rows 10 --wait --csv output.csv generates a dataset directly from the terminal.

2. Architecture — The Five-Stage Multi-Agent Pipeline

Understanding bigset's internals tells you where it works well and where it fails. The pipeline has five stages.

2.1 Stage 1: Schema Inference (Claude Sonnet)

When natural language input arrives, Claude Sonnet infers the schema before touching the web — column names, data types, primary keys, and which web locations to target are all derived from language understanding alone. This stage sets the quality ceiling for everything downstream. Ambiguous or domain-specific input can produce a misaligned schema that sends every subsequent stage in the wrong direction.

2.2 Stage 2: Orchestrator Agent (Qwen)

Once the schema is established, a Qwen-based orchestrator agent uses TinyFish Search to broadly discover entities that will become rows. This stage determines recall — how many matching entities are surfaced. Poor search coverage or data buried in poorly indexed locations will leave the candidate list thin.

2.3 Stage 3: Parallel Sub-Agents

Each discovered entity gets exactly one dedicated sub-agent running in parallel. The critical constraint: each sub-agent is capped at six tool calls. Within that budget, the agent must collect all the detail data for one entity. Complex entities whose information spans multiple pages or requires dynamic rendering may return partially filled rows when the cap is hit. The cap exists to control parallel execution cost, but it creates a precision ceiling.

2.4 Stage 4: Deduplication and Source Attribution

Data returned from parallel agents is deduplicated using the inferred primary key. Simultaneously, each row gets a source URL automatically recorded. This source tracking is not cosmetic convenience — it is the structural prerequisite for cross-verifying the data. A user who receives a dataset with no provenance has no way to check "where did this number come from?"

2.5 Stage 5: Final Table and Export

Validated data is assembled into a final table browsable in the UI and downloadable as CSV or XLSX. The end-to-end process takes two to five minutes — the real time cost of agents actually crawling the live web, not a cached lookup.

3. Democratizing Data Collection — What Actually Changes

bigset's claim of "democratizing data collection" can sound like marketing. Comparing it against the existing landscape makes the substance of the claim concrete.

3.1 The Entry Cost Before bigset

Three paths existed before tools like bigset: write a custom scraper (Python + BeautifulSoup + Playwright, site-specific selectors, rate limit handling, scheduler setup — high engineering cost, high maintenance); pay a commercial data provider (Clearbit, ZoomInfo, LinkedIn Data API — financially expensive, limited coverage, slow refresh cycles); or collect manually (high labor cost, hard to scale). bigset eliminates most of this entry cost. Non-technical users can express a data request in natural language; agents replace the selector config, pipeline, and scheduler.

3.2 Combining AI Agents + Web Scraping + ETL

What makes bigset architecturally interesting is that it merges three previously separate domains into a single natural-language-driven flow. AI agents (LLM-based schema inference and autonomous discovery), web scraping (live web data collection), and ETL (extract, transform, load, refresh scheduling) were each specialized crafts requiring their own tools and expertise. Collapsing them into a single natural-language input is a genuine abstraction leap, not just a UX layer.

3.3 Use Cases — Where It Fits

Competitive intelligence: track hiring activity, funding stages, and product launches across an industry on a recurring schedule. Market research: compare open-source projects by GitHub stars, license type, and hardware support. Price monitoring: auto-refreshing tables of GPU retail prices or AI model API rates. Lead generation: sales teams without engineers generate targeted company lists directly. Research assistance: journalists and academics quickly aggregate public attributes across many entities.

4. Limitations — Five Things to Address Honestly

bigset's own documentation describes it as experimental software. Where to lower expectations matters as much as knowing where it works.

4.1 Imperfect Schema Inference

Stage 1 relies entirely on language understanding. bigset's documentation explicitly states that "schema inference isn't always perfect." Ambiguous queries ("good startups" — good by what measure?), queries requiring deep domain knowledge, or multi-interpretable inputs can produce schemas that diverge from what the user intended. The further the inferred schema drifts from user intent, the less useful the resulting data.

4.2 The Six-Tool-Call Cap

The six-tool-call limit per sub-agent is a deliberate engineering trade-off between efficiency and precision. Entities with data distributed across multiple pages, behind dynamic rendering, or requiring navigational steps will frequently hit the cap before complete data is retrieved. The rows that result may be partially filled. The cap controls cost but creates a hard precision ceiling for complex data targets.

4.3 LLM Hallucination and Data Accuracy

LLM-based extraction carries the inherent risk of misinterpreting what was actually on the page, fabricating plausible-sounding data, or producing truncated outputs when API timeouts or rate limits interrupt processing. Research on comparable systems (e.g., ScrapeGraphAI-100k) puts schema validation pass rates around 93% — but that measures syntactic compliance, not whether the extracted values are semantically correct. The per-row source URL is your safety net: important data must be checked against the recorded source.

4.4 External Service Dependencies and Cost

bigset is open-source, but it is not free. Three paid external services are required: TinyFish API, OpenRouter, and Clerk. At scale — large datasets, high-frequency refresh — API costs accumulate quickly. There is also a documented limit of 2,500 row operations per user per month on the free tier. "Open-source" describes the code; the operational cost structure is something users must calculate separately.

4.5 No SQL Support Yet

As of June 2026, bigset does not support SQL queries for filtering or joining generated datasets. It is on the roadmap but unshipped. Any analytical work beyond browsing the table requires exporting to CSV and processing externally (spreadsheet, pandas, DuckDB, etc.). The broader community and ecosystem maturity are also at an early stage.

5. Legal and Ethical Questions — robots.txt, Privacy, and the EU AI Act

Letting agents crawl the live web raises questions that a technical analysis cannot dodge.

5.1 robots.txt and Legal Boundaries

Scraping publicly accessible web data is generally legal in both the US and EU as of 2026. However, violating robots.txt is more than an etiquette issue. In the US, bypassing an explicit access restriction could be interpreted as a CFAA violation; in the EU, it can constitute breach of contract. Crucially, robots.txt only expresses access control, not usage intent — a site owner cannot signal "indexing is fine, AI training is not" through the current standard. Emerging formats (ai.txt, llms.txt) aim to fill this gap but have no legal force as of 2026. bigset users must check the robots.txt and terms of service of every target domain themselves.

5.2 Personal Data and GDPR

If bigset's collection sweeps up personal identifiers — names, emails, job titles — GDPR and equivalent national privacy laws apply. Data being publicly accessible does not automatically mean collecting, combining, and storing it is lawful under GDPR's data minimization and purpose limitation principles. bigset provides no automated safeguards here. Compliance is the user's responsibility.

5.3 The EU AI Act and Data Provenance

The EU AI Act requires organizations building AI systems to document data provenance and demonstrate lawful collection. bigset's per-row source URL recording partially addresses this requirement. However, using bigset output as AI training data or as input to a high-risk AI system requires stricter data governance documentation than source URLs alone provide. The design direction is correct; the current implementation is not sufficient for full EU AI Act compliance.

6. The Direction bigset Points — LLM-Native ETL

Beyond bigset's own maturity, the direction it points is worth examining: ETL pipelines being abstracted by LLMs.

6.1 Code-Free Data Pipelines

Traditional ETL required explicit code and configuration at every layer: source connectors, transformation mappings, load targets, refresh schedulers. bigset collapses all of that into a natural language sentence. The execution is imperfect, but the direction is unambiguous. As LLMs improve at understanding intent and agents improve at reliable web navigation, the entry requirement for building a data pipeline shifts from coding skill to the ability to articulate what you want.

6.2 What "Living Datasets" Actually Mean

Traditional datasets are point-in-time snapshots. bigset's auto-refresh means agents re-execute on the user's schedule, keeping the dataset synchronized with the current state of the web. For data that changes fast — hiring activity, pricing, open-source project metrics — this is a fundamentally different model. You are not periodically re-requesting a snapshot; you are subscribing to an evolving view of a subset of the public web.

7. Assessment — Signal or Hype?

How should bigset be evaluated? A few positions worth stating plainly.

7.1 What Is Genuinely New

The integration of natural language → schema inference → parallel agent collection → auto-refresh into a single flow is a real abstraction advance. The specific combination is not achievable by stitching together existing tools without significant engineering. The practical implication — non-technical users directly generating live datasets without writing code — is a genuine capability shift, not just a wrapper around existing primitives.

7.2 What Must Not Be Overstated

bigset calls itself experimental, and the maturity level matches that description. Accuracy, completeness, and cost efficiency are not yet at production ETL levels. The tool is unsuitable as-is for domains where data accuracy is critical — finance, legal, medical applications. And "open-source" does not mean zero cost; operational API expenses must be calculated before committing to bigset at scale.

7.3 Who Should Use It Now

bigset is most valuable for: teams that need rapid competitive intelligence or market research without a dedicated data engineer; organizations that need fast-moving data (hiring, pricing, open-source metrics) kept automatically current; engineering teams running PoC validation before investing in a production pipeline. It is unsuitable for large-scale, high-precision, or personally identifiable data collection without additional safeguards.

8. Conclusion — When Data Collection Becomes a Language Skill

bigset is a meaningful attempt to lower the entry barrier to structured data collection. The combination of AI agents, web scraping, and ETL under a single natural-language interface moves data access away from being the exclusive domain of technical teams. As of June 2026, it is experimental, and accuracy, cost, and legal compliance remain the user's responsibility.

What matters more than bigset's current maturity is the direction it signals: ETL being abstracted into natural language, pipelines replaced by prompts, and "living datasets" as a first-class concept. Data collection will not suddenly require no expertise — but the expertise required is shifting from writing scrapers to formulating good questions. That shift is worth watching, and bigset is a clear early marker of it.
