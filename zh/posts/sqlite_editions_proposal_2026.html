SQLite也需要Rust式版本(Edition) - 安全默认值提案

Rust Editions for SQLite - 在不破坏旧代码的前提下选择启用更安全的默认值

2026-07-17 开发/基础设施

引言: 为什么现在要谈SQLite的默认值

截至2026年7月，SQLite很可能是全世界部署量最大的数据库引擎。它悄悄嵌在浏览器、移动应用、桌面软件与嵌入式设备当中。然而，成就这一成功的根本原因——近乎偏执的向后兼容——同时也成了它的枷锁。SQLite坚守着「绝不破坏近三十年积累下来的应用程序」这一承诺，代价是它至今仍背负着按今天标准看既不安全也不够快的默认值。

近期在hada.io(GeekNews)引发讨论的mort.coffee文章《SQLite should have (Rust-style) editions》，精准地指出了这一问题。作者以自己在实践中遇到的真实故障为例——字符串'1'被原样写入整数列的事故、因外键从未被强制执行而导致参照完整性悄然崩坏、并发写入时应用直接因SQLITE_BUSY而崩溃——提出SQLite应当引入类似Rust「Edition(版本)」的机制。本文不打算照搬这一提案，而是直接追问: 为什么向后兼容是软件演化中一个普遍存在的障碍? Rust的Edition机制究竟是如何解决这个问题的? 而把这套解法移植到SQLite这样一种完全不同类型的软件上时，真正的困难又在哪里?

1. 向后兼容: 一个普遍存在的问题

1.1 软件会老化，却难以改变

每一款成熟的软件都会面对同样的困境。设计之初做出的判断，随着时间推移被证明是失误，但那时早已有无数代码依赖着这一行为运行，动不得了。C语言的空字符结尾字符串、PHP宽松的比较运算符、JavaScript的隐式类型转换，都属于同一谱系。明知有问题却不能修的原因很简单: 一旦改变默认值，建立在其上的大量应用就可能在毫无预警的情况下崩溃。

1.2 SQLite为何格外棘手

SQLite把这个困境背负得比大多数软件更为极端。首先，SQLite不是一个服务器，而是被链接进应用程序的库，同时也是一种文件格式。创建某个数据库文件时所用的应用，与十年后打开同一文件的应用，完全可能使用着不同版本的SQLite。其次，SQLite官方项目本身就明确将「长期支持(long-term support)」列为核心设计目标，将文件格式的超长寿命奉为最优先的价值。正是这两个特性，使得在SQLite中修改默认值，比在一般应用程序库中要沉重得多。

2. 拆解Rust的Edition机制

2.1 Edition改变了什么，又没有改变什么

Rust在1.0发布时立下承诺: 「能在1.x下编译的代码，此后在任何1.y下都能编译」。随着语言不断演进，与这一承诺相冲突的改进不断累积，Rust团队于是通过Cargo.toml中的edition字段(2015、2018、2021、2024)引入了按crate逐一选择启用的机制。核心保证是: 在某个Edition下编译通过一次的代码，将永远能在该Edition下编译通过; 既有crate除非开发者显式提升该字段，否则永远不会被自动套用新规则。为减轻迁移负担，cargo fix --edition能自动完成大部分可机械化处理的变更。

2.2 为何同一个二进制文件中Edition可以混用

Rust的Edition设计中最精巧的部分是跨Edition的互操作性。用2015 Edition写的crate可以依赖2024 Edition的crate，反过来也一样。之所以能做到这一点，是因为Edition的差异只影响编译期对源码的解析与语法理解，编译完成之后的产物中不会留下任何Edition的痕迹。换言之，Edition只是关于「如何读取源码」的一种约定，而不会改变运行时语义或二进制格式。正是这种狭窄而明确的作用域，从原理上保证了「新旧代码能在同一个项目里共存」。

3. SQLite那些有问题的默认值

3.1 宽松的类型 - 类型亲和性与STRICT表

SQLite并不强制列上声明的类型，而是使用TEXT、NUMERIC、INTEGER、REAL、BLOB这五种「类型亲和性(affinity)」的概念，这只是一种偏好的存储形式。即便某列声明为INTEGER，只要无损转换不可行，字符串也会被原样存入。这在实践中会直接导致本该是干净整数列的地方混入字符串'1'和'0'这类事故。自SQLite 3.37.0(2021-11-27)起，可以用CREATE TABLE ... STRICT为单个表启用严格类型检查。STRICT表要求每一列都必须声明为INT、INTEGER、REAL、TEXT、BLOB、ANY之一，若值无法无损转换则抛出SQLITE_CONSTRAINT_DATATYPE错误。问题在于，这只是针对新建表的可选功能——既有的表，以及更重要的是，大多数根本不知道有这个功能存在的开发者，仍然停留在宽松的旧默认值上。

3.2 foreign_keys默认关闭

多年来SQLite只解析外键语法而不强制执行。后来加入真正的外键强制功能时，若默认开启，长期依赖宽松参照完整性的既有应用就可能突然收到从未见过的错误码而崩溃。因此PRAGMA foreign_keys至今仍默认关闭，且这是连接级别设置，每个连接都要重新显式开启。在这种默认状态下，父行被删除后子行会沦为孤儿，再叠加SQLite的ROWID复用算法，甚至可能演变成静默的数据损坏——被删除用户的帖子，悄悄重新指向了日后复用同一ID的新用户。

3.3 不是WAL而是回滚日志，以及SQLITE_BUSY

SQLite默认的原子提交方式是传统的回滚日志(rollback journal)。后来引入的WAL(预写式日志)模式需要通过PRAGMA journal_mode = WAL手动启用，它能让读写并发进行得远比以前顺畅，大幅提升性能。但WAL在网络文件系统上无法工作，还会额外产生-wal、-shm文件，正因如此它从未被强制设为默认值。在并发写入的场景下，多个写操作挤在一起时会立即返回SQLITE_BUSY错误。PRAGMA busy_timeout可以让其重试一段时间来缓解，但开发者社区一直指出，在锁升级的场景下，这也并非完整的解决方案。

4. 为什么Edition方式适合SQLite

mort.coffee的提案简洁而优雅: 用一行像PRAGMA edition = 2026;这样的语句，一次性选择启用当下那个时间点的「推荐默认值组合」。这个组合可以包含foreign_keys = ON、一个合理的busy_timeout、journal_mode = WAL，以及把STRICT表设为标准。这种方式的好处很明确: 只要不指定Edition，既有应用就完全维持旧行为，什么都不会坏。而新项目，或者有余力承担迁移成本的团队，则可以用一行代码同时打开多重安全开关。相比现在要一个一个记住并手动开启各个PRAGMA，能用一个标准化的名字来指代「一整套安全默认值」，本身就大幅降低了认知负担。

5. 难题 - 与嵌入式、超兼容性哲学的冲突

5.1 各项设置的作用域各不相同

Rust的Edition依附于crate这一个明确定义的编译单元。而SQLite的安全相关设置作用域却各不相同: foreign_keys是连接级别，journal_mode实际上是数据库文件级别，STRICT则是表级别。正如围绕这篇文章的hada.io讨论所指出的，首先必须决定统一的PRAGMA究竟放在文件层面还是连接层面，一旦设计有误，旧版本的库在打开带有新Edition标记的文件时，就可能误处理甚至损坏文件。

5.2 文件可移植性与超兼容性哲学的冲突

SQLite数据库文件天生就是要跨系统、跨应用版本流转的。这与Rust的crate在编译时就一次性固定下来有着根本区别。一旦在文件中打上Edition元数据，就等于给能打开该文件的SQLite版本设了一道门槛。对于一种要嵌在老旧设备或遗留系统里存活数十年的文件格式而言，设下这样的门槛，与SQLite一贯坚持的超兼容性原则正面冲突。

5.3 测试矩阵与组合爆炸

如果存在多个Edition，且每个Edition又捆绑多项功能，SQLite的核心开发者事实上就得验证「Edition×平台×编译选项」的全部组合。Rust能够承受这份成本，是因为只有一个编译器掌握着标准; 但SQLite要经由为数众多的绑定层(Python、Node.js、各类移动端SDK)被使用，引入Edition会把测试与文档维护的负担扩散到整个绑定生态系统。

6. 与其他语言、数据库版本化策略的对比

6.1 Python的__future__ - 渐进式强制化

Python长期使用from __future__ import 特性语法，让模块按需选择启用未来的语言特性，并设定一个「强制发布版本」，从那之后该特性便直接成为默认行为。这与Rust的Edition一样是可选启用，但最终会在某个时间点之后强制施加给所有人，这与SQLite、Rust那种「永久保留旧行为」的模式在本质上并不相同。

6.2 JavaScript的"use strict"

ES5允许仅在脚本或函数开头声明"use strict"，就能选择启用更严格的语义。既有的ES3代码若没有这条指令则完全不受影响。它在作用域清晰(以文件或函数为单位)这一点上与Rust的Edition相似，但更为简单——没有版本的概念，只存在「宽松模式」与「严格模式」这一种二元选择。

6.3 MySQL真正改变默认值的案例

并非所有数据库都选择了SQLite这种可选启用的路线。MySQL自5.7.5版(2015年)起，把STRICT_TRANS_TABLES纳入sql_mode的默认值，把「错误值自动转换或悄悄截断」的旧默认行为直接改成了「报错」。这是一种强制迁移路线。全新安装的MySQL变得更安全了，但依赖旧有宽松行为的既有应用，在升级时确实发生了崩溃，许多运维人员不得不在迁移窗口期显式调低sql_mode作为权宜之计。这恰好与SQLite、Rust的可选启用策略形成鲜明对比: MySQL选择的是「大家终究都要迁移到新默认值」，而SQLite与Rust选择的是「旧代码永远不动，只有新代码才会拿到新默认值」。

7. 实践启示 - 现在就能用上的东西

7.1 三行PRAGMA立刻变得更安全

即便官方的Edition机制尚未出现，在每次建立连接时执行以下三条PRAGMA，就能缓解本文中提到的大部分问题。

PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;

第一行强制参照完整性，防止孤儿行与静默的数据损坏。第二行提升并发读写性能(但需注意它只在本地文件系统上有效，网络驱动器上无法工作)。第三行让并发写入冲突时重试五秒，而不是立即失败。

7.2 新建表用STRICT

新建的表可以加上STRICT选项来获得类型安全。

CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  age INTEGER
) STRICT;

这样一来，试图向age列写入字符串'30'的操作会立刻以错误的形式暴露出来，而不是被悄悄存入。

7.3 依然需要人工把关的局限

上述所有PRAGMA都必须由应用代码在每个连接上显式设置，一旦经过ORM或连接池，就很容易被遗漏。mort.coffee提案真正的价值在于: 如果Edition机制真的出现，就能把这种重复劳动标准化成「一行声明」。但正如第5节所述，让这种标准化不与SQLite的文件可移植性哲学相冲突，绝非易事。

结论

SQLite默认值宽松的问题，并非SQLite独有的缺陷，而是每一款成熟软件都无一例外要面对的向后兼容困境的一个具体案例。Rust的Edition机制以「旧代码绝不触碰，只有新代码才能选择启用新规则」的方式化解了这一困境，留下了一个优雅的先例。mort.coffee提出把这一思路直接移植到SQLite，方向是对的，但对于一个设置分散在连接、文件、表这些不同层级——而非像crate那样被清晰划分——且文件本身还要历经数十年流转的嵌入式数据库引擎而言，要做到这一点，在作用域设计与向后兼容验证上需要解决的难题，远比一门编译型语言要多得多。无论官方Edition机制最终是否出现，眼下最现实的做法，是把foreign_keys、journal_mode、busy_timeout与STRICT表，明确地定为你所在项目自己的标准并主动启用。
