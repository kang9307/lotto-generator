有一段代码负责在后台写一行日志。它起一个任务，不等它就返回。看代码似乎就能知道会输出什么，但实际上答案取决于它跑在哪个运行时上。不是性能不同，是可观测的结果不同。

缘起 - 一行日志有四种收尾

原文的起点是一个极小的程序。它起一个模拟慢速日志写入的任务，外层函数不等这个任务就返回。外面稍作停顿，再打印一个标记。跑出来的字符串在七个运行时上分成四类。

这里重要的不是哪个答案正确。这个程序没有竞态，没有共享资源，也没有用到多条线程。如果答案仍然分岔，那分岔的成因就不在程序里，而在它底下那层运行时把什么定成了默认值。原文之所以要立九条轴，理由就在这里。

原文把任务的一生切成三段来安放这些轴：任务如何开始、如何结束、如何被取消。并且对每条轴都明确写道，只存在性能、内存占用、易用性与语义之间的权衡，没有对错之分。每种语言都有自己的设计理由。

从代码外部去抓并发缺陷，也就是枚举各种交错顺序、扫过可达状态的做法，已经在先写规格能抓到什么里单独谈过。下面是它的另一面，主题是语言把异步表达成什么形状。

有颜色的函数 - 标记为何沿调用层级向上蔓延

第一次接触异步的人撞上的第一堵墙，既不是取消也不是异常。而是想调一个 async 函数，结果调用方也得是 async，再上一层也得是，最后标记一路爬到了入口点。这通常被叫做有颜色的函数。

栈放在哪里

这种蔓延不是语法口味问题，而是实现方式强制出来的结果。普通的函数调用把局部变量和返回地址压进机器调用栈，而那条栈由操作系统线程所有。所以同步函数一等待，整条线程就停住。栈绑在线程上，别无他法。

可挂起的函数打破了这个前提。它要中途停下、把控制权交回调用方，之后再从那个位置接着跑。要做到这一点，就必须把跨越 await 还要活下来的状态存到栈以外的地方。什么必须留下来是确定的。

  • await 之后还会用到的局部变量 — 栈帧消失以后值还得在
  • 恢复点 — 指明从函数体的哪个位置接着跑的标记
  • 待清理项 — 打开的资源、要释放的锁，以及还欠一次执行的 finally 块的位置

编译器造一个对象来装这三样，然后在每个 await 处切开函数体，重新排成一段段可恢复的片段。这项变换只在函数带着标记时才发生。MDN 的 await 文档所说的 async 函数体在 await 处被切分，指的就是这一点。

于是它往上爬

没有标记的普通函数不具备那块存储。因此要用可挂起函数的结果只剩两条路：整条线程阻塞着等，或者自己也接受同样的变换。选前者，用异步的理由就消失了；选后者，标记就往上挪一级。这正是它蔓延到整条调用层级的原因。

这种蔓延只发生在标记出现在签名里的设计中。后面要看的轻量线程一系，选择的是把栈从线程上摘下来、给每个任务配一条，于是任何函数都能挂起，也就不需要标记。

蔓延是缺陷还是信息

判断在这里真的会分岔。一边把它读作传染。一个库改成异步，它上面所有代码都得改，同一份功能的同步版和异步版并排维护，重复就此产生。

另一边把它读作有意为之的类型信息。带着标记意味着「这次调用可能挂起」这个事实写在了签名上，而这个事实确实有用。

  • 能看出不变式在哪里被观测 — 一旦发生挂起，别的任务就能插进来看到共享状态。标记标出了那扇窗开在哪
  • 能用眼睛找出持锁挂起的代码 — 锁区间里的 await 不在签名里，就明摆在函数体上
  • 能看出取消可能在哪里到达 — 协作式取消通常在挂起点被送达
  • 把开销不同的调用区分开 — 立即返回的调用和夹着等待的调用，靠签名就分开了

这里不是判高下的场合。同一种性质，被算作改动成本时是缺陷，被算作可读信息时是功能。代码库已经很大、与同步库深度纠缠，前一项成本就高；碰共享状态的代码多、交错点必须受控，后一项价值就高。

开始的两条轴 - 即时性与挂起保证

即时性划分的是调用 async 函数的那一刻活儿是否就开始了。惰性一侧，调用只是造出一个对象，什么都没发生。Python 标准库文档明确写道，仅仅调用一个协程并不会把它排上执行，并附了调用结果显示为协程对象的例子。Rust 标准库的 Future 文档写得更重：future 本身是惰性的，底下的计算要往前推进，就必须被主动轮询。

急切一侧正相反。C# 文档描述 async 方法在第一个 await 处挂起时把一个任务交回调用方，而那个任务代表着正在进行的工作。拿到手时它已经在跑了。

挂起保证这条轴更微妙。它问的是：能不能假定既然这里写了 await，就一定会让出一次。MDN 对 JavaScript 说得很清楚：即便所用的 promise 已经兑现，async 函数的执行仍会暂停到下一个 tick；而且哪怕被等待的值不是 promise 也一样，因为在所有已排队的微任务处理完之前，控制权不会回到该函数。

// 即使操作数不是 promise，await 也会让出到下一个 tick
async function step(name) {
  console.log(name, 'start');
  await console.log(name, 'middle');
  console.log(name, 'end');
}

step('first');
step('second');
// first start / first middle / second start / second middle / first end / second end

C# 在同一处给出不同答案。微软文档指出，如果被等待的操作在到达 await 之前就已完成，控制权就留在该方法里，并一并给出理由：挂起再返回的开销白花了。同一个 await 这个词，一边保证让出，一边不保证。

  • 静态挂起让交错点可以从源码上数出来。代价是即便值已就绪也要付一个 tick
  • 动态挂起在值已就绪时省下这趟往返。代价是同一份代码在不同负载下按不同顺序跑
  • 惰性启动让组合、重试、超时可以事后再套上去。代价是忘了驱动它，就什么都不会发生

结束的四条轴 - 生存、引用、清理、异常

生存范围规定起出来的任务允许活到什么时候。无限期一侧，任务可以比创建它的函数活得更久；动态一侧，它在创建它的作用域退出前就被收拾掉。Swift 并发提案把后一条规则写成了一句话：创建子任务的函数必须等它结束后才能返回。Trio 也是同一形状。它的文档写道，那个块要等所有任务都完成才退出，并补上一句：你得准备好当一个负责任的父级，才能启动子任务。

引用强度是工程上最安静地硌人的一条轴。Python 的 asyncio 文档在 create_task 条目上挂了一条警告：事件循环只以弱引用持有任务，别处没有引用的任务随时可能被回收，哪怕它还没跑完。所以文档建议把后台任务收进一个集合以建立强引用，并在完成回调里把这个引用摘掉。

import asyncio

background = set()

async def main():
    task = asyncio.create_task(write_log())
    background.add(task)                       # 建立强引用
    task.add_done_callback(background.discard) # 结束后摘掉引用
    await asyncio.sleep(1)

清理方式是生存期结束那一刻的处置。有的等着剩下的任务，有的下达取消让它自行收拾，有的干脆掐断。这条轴决定清理代码到底跑不跑。C# 文档里的一个条件很能说明这条轴的性格：在 await 处挂起并不算退出该方法，所以那一刻 finally 块不会执行。永远不再恢复的任务，其清理代码也就一直没跑。

异常传播处理的是没人等待的任务失败了怎么办。Python 文档写道，用这种从不等待的写法，任务失败时它的异常永远不会被取回，直到该任务被垃圾回收时，asyncio 才记下一条「任务异常从未被取回」的日志。Trio 站在另一端：未处理的异常会在父任务里重新抛出，并合并成一个异常组。

  • 无限期生存让后台工作变容易。代价是关停时谁也不知道还剩下什么
  • 动态生存保证离开作用域后什么都不剩。代价是每个长跑任务都要手工造一个作用域
  • 弱引用从结构上减少引用泄漏。代价是没被持有的后台任务可能消失
  • 把异常关在任务内部的设计让一次失败不会连累邻居。代价是失败只剩下一行日志

取消的三条轴 - 感知、方向、持续

取消是原文唯一单独分配了三条轴的一组，可见它的分支之多。

感知问的是任务能不能对被取消作出反应。能反应的一侧，取消就成了协作式。Swift 提案写道，取消完全是协作且同步的，除非有代码去检查取消，否则它毫无效果。Python 文档换个说法描述同一性质：Task.cancel 只是安排在事件循环的下一个周期把取消异常抛进被包装的协程，协程因而有机会清理，甚至可以通过吞掉异常来拒绝这个请求。文档同时写明并不鼓励这样做。

方向问的是取消沿任务图往哪边走。Swift 提案写道，父任务带着错误退出时，子任务会被隐式取消。Python 的 TaskGroup 是另一种形状：组内任一任务第一次以取消异常之外的异常失败时，组内其余任务会被取消；此时若语句体仍在活动，包含该语句的任务也会被取消。这些失败最终会合并成异常组抛出。

async def main():
    try:
        async with asyncio.TaskGroup() as tg:   # 作用域抓住子任务
            tg.create_task(write_log())
            tg.create_task(fetch_config())      # 一个失败，其余被取消
    except* OSError:                            # 剩下的失败合并成组送来
        handle_failure()

async def write_log():
    try:
        await asyncio.sleep(2)
    except asyncio.CancelledError:
        raise                                   # 不吞掉，重新抛出
    finally:
        close_handle()

持续问的是一次取消能维持多久。Trio 文档用电平触发这个词解释自己这一侧的性格：一个块被取消之后，块内所有可取消的操作都会持续抛出取消异常。Swift 指向同一方向，其提案写道取消标志一旦置位就永不清除。Python 则留了另一侧的余地：捕获并吞掉取消异常的代码必须调用 Task.uncancel 来摘除取消状态，摘除之后，此前安排好的取消可能被撤回。

  • 持久型取消能防止取消在清理途中悄悄失效、活儿又接着跑。代价是清理里若需要等待，就得另开一段受保护的区间
  • 瞬时型取消留下取消之后继续做后处理的余地。代价是只要还有吞掉取消的代码，截止期限就守不住
  • 不感知的取消对目标代码不提任何要求。代价是停下那一刻有什么做了一半，得另行处理

原文没有的轴 - 谁来恢复执行，栈放在哪里

原文那九条轴划分的是任务可观测的语义。工程上做选择时，它们底下还需要两条轴，而这两条不在原文的分类里。这里与原文的轴区分开来，单独立出。

第一条是谁来恢复执行。有的设计由语言连同执行器一起提供；有的设计里语言只定义可挂起的片段，执行器交由库来挑。Rust 的 Future 文档就是这么写后者的：使用 future 时通常不自己调 poll，而是 .await 那个值，而在 future 可以推进时反复调用 poll 的责任在执行器。就绪的信号通过 Waker 传回。轮询返回 Poll::Pending 时，会存下当前上下文里 waker 的一份克隆，等到可以推进时再唤醒它。

第二条是栈放在哪里。前面看到的状态机变换是一种答案，给每个任务配一条独立的栈是另一种。Java 虚拟线程提案明确写了后者的实现：虚拟线程的栈作为栈块对象存放在 Java 的垃圾回收堆里，并随程序运行而伸缩。

  • 运行时自带执行器 — 标准只有一个，库之间的兼容容易。代价是调度策略可改动的余地窄
  • 可挑选执行器 — 能按负载性质换执行器。代价是各自假定不同执行器的库互不相容
  • 状态机变换 — 每个任务的内存只占需要的那么多。代价是栈轨迹与原本的调用层级对不上
  • 独立栈 — 调用层级原样保留，追踪和调试能接得上。代价是栈本身要有地方放

去掉颜色的设计 - 换回什么，让出什么

有一种办法不用任何标记也能达到同样目的：把线程做得比操作系统线程便宜，照常写阻塞代码，而在阻塞期间把载体线程放开。Java 虚拟线程是把这套设计写得最详细的一例。提案把虚拟线程定义为不绑定到特定操作系统线程的 java.lang.Thread 实例，并写道虚拟线程在底层操作系统线程上运行 Java 代码，但不会在代码的整个生命周期里占住那条线程。

换回来的

提案关于异步风格的那些表述，正好就是换回来的清单。异步风格迫使开发者把请求处理逻辑拆成一个个小阶段，并放弃循环、try-catch 这些语言基本的顺序组合手段。在可观测性上的说法更直接：栈轨迹提供不了可用的上下文，调试器无法单步跟进请求处理逻辑，性能分析器也无法把某次操作的开销关联到它的调用方。

// 没颜色的那一侧：阻塞调用照写，每个任务配一条线程
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var request : requests) {
        executor.submit(() -> {
            var body = httpClient.send(request, ofString()); // 阻塞也没关系
            return store.save(body);                         // 循环和 try 照用
        });
    }
}

让出去的

作为交换也有让出去的东西。首先是挂起点的可见性。哪次调用可能停住并不写在签名上，于是持锁挂起的代码，或者不变式被破坏期间可被别的线程观测到的那段窗口，光看签名找不出来。其次是边界条件。提案明确列出虚拟线程因被钉在载体上而无法卸下的两种情形：在 synchronized 块或方法内部执行时，以及执行本地方法或外部函数时。

提案给自己划的那条线也要一并看：虚拟线程不是更快的线程，它并不会让代码跑得更快，它的存在是为了规模而不是速度。适用条件也一并写着：并发任务数超过几千且负载不是 CPU 密集型时，吞吐量才会提升。

这里同样不是判高下的场合。计算占主导的活儿，两边都没有等待可以回收，得到的就少；既有代码已经塞满阻塞调用、而那些库又没有异步版本，往有颜色那一侧搬的成本就高。反过来，碰共享状态的代码多、交错点必须受控时，写在签名上的标记就体现出价值。

实际工程里真正硌人的地方

取消没传到、于是留下来的活儿

成因很简单：取消抵达的通路没有铺到那段工作上。通路只有三种形态：作为参数往下流的取消信号、抓住子任务的作用域、以及丢弃。三样都不用而只是起一个任务，它就不属于任何人的子级。

  • 传信号的形态 — Go 标准库文档规定不要把 context 放进结构体，而要显式传给每个需要它的函数，并作为第一个参数。没有传的那一段，通路就断了
  • 作用域抓住的形态 — Swift 提案写道，非结构化任务与分离任务都不遵守父子完成约束。跑出作用域的任务不会随作用域一起结束
  • 引用断掉的形态 — Python 文档里的弱引用警告就是这种情况。没被持有的后台任务可能在完成前消失

异常消失的路径

没人等待的任务失败时，没有人来接这个异常。Python 文档用「任务异常从未被取回」这条日志消息来描述这种状态，并指出这条消息出现的时机是该任务被垃圾回收时。也就是说，失败与日志之间隔着一段时间。

  • 返回类型载不动异常时 — C# 文档写道，返回 void 的 async 方法不能被等待，而且调用方无法捕获该方法抛出的任何异常
  • 结果没人取回时 — Python 文档建议用 TaskGroup 来避开这条路径。组会对每个任务保持强引用、等待它们、并传播它们的异常
  • 把异常关在任务内部的设计 — 这就是原文异常传播轴上「从不」的那一侧。另一侧则像 Trio 那样由父级重新抛出

一次阻塞调用让整个运行时停摆

成因在于执行器线程此刻正在跑你的代码这一事实。在状态机方案里，恢复片段跑在执行器线程上。片段内部若做了操作系统层面的阻塞调用，这条线程在此期间就跑不了任何别的任务的片段。执行器若是单线程的，那就等于整个运行时在这段时间里停住了。

  • 计算耗时很长的区间 — 就算不是阻塞调用，结果也一样。没有让出点，这期间谁都推进不了
  • 同步库的调用 — 文件读写、名字解析、密码学运算这类没有异步版本的调用最典型
  • 轻量线程一侧的对应现象 — Java 提案里的钉住条件就在这个位置。在 synchronized 内部或本地函数内部放不开载体线程

互相等待、谁也推进不了的结构本身并不是异步独有的问题。共用一个资源而两头都停住的实例，整理在管道缓冲区装满引发的死锁里。

没有顺序保证却假定有的代码

这正是前面挂起保证那条轴直接以缺陷形式现身的地方。要么是这里会让出一次，那期间对面应该会跑的假定，要么是这个立刻就完事，所以不会挂起的假定，被写进了代码。两个假定互相相反，而运行时保证的是哪一个，只能翻文档才知道。

  • 把假定静态挂起的代码搬到动态挂起的运行时上 — 排好的后续工作比预期跑得晚
  • 把假定动态挂起的代码搬到静态挂起的运行时上 — 以为会一口气跑完的区间冒出了交错
  • 把惰性启动误当成急切启动 — 只造出来却没驱动的协程，安安静静什么都不做

假设了顺序的代码在哪里悄悄碎掉

异步代码的各种缺陷里，最难复现的就是顺序假定。成因是三件事叠在一起。

第一，是否保证挂起因运行时而异。像 JavaScript 这样总是让出的一侧，await 之后的代码一定被推到下一个 tick，哪怕值已经就绪也一样。像 C# 这样在值已就绪时留在原地的一侧，同一份代码就当场接着跑。把结构相同的代码在两个运行时之间搬动，顺序就变了。

第二，任务开始的时刻不同。惰性一侧，造出来和驱动它是两件事；急切一侧，一调用就跑起来了。若一个只造出来的协程要等到后面被等待时才开始，那么围绕这中间那段时间搭起来的顺序假定就会散架。

第三，完成顺序与提交顺序不同。同时起好几个，谁先结束由外部因素决定。可代码常常假定结果按起动的先后到来。

  • 把它挪进表达 — 需要顺序就用事件、队列、锁这类显式表达顺序的手段来写，别依赖等待点的副作用
  • 用作用域捆起来 — 起好几个、全部完成后才继续的那一段，用组 API 表达。作用域退出这一事实本身就是保证
  • 用测试把假定钉住 — 顺序假定若非留不可，就一并放一个检验它的测试，让它靠逻辑而不是靠负载来复现

结论 - 你选的不是语法，是失败的方式

同一个程序在七个运行时上有四种收尾，这个观察揭出的事实是：异步不是一对关键字，而是九项以上互相独立的决定。这些决定散落在各处文档里，而且通常是出事之后才被翻出来读。

  • 标记的蔓延是栈放在哪里的后果 — 不是语法口味。要去掉它，就得走给每个任务配一条栈的路，而那样就让出了挂起点的可见性
  • 取消不是功能，而是通路 — 先定下用信号、作用域还是丢弃来造，后面才不会留下没人管的活儿
  • 读默认值这件事占一半 — 生存范围、引用强度、异常传播，只要没人明说，用的就是运行时的默认值

因此，引入异步这个决定，实质是愿意承受哪一种失败方式的决定。原文之所以写下每条轴只有权衡、没有对错，理由也是一样的。
