맥에서 로컬 LLM이 느린 진짜 이유 - GPU를 쓰고 있는지 확인하고 켜는 법

장치가 잡히는 것과 실제로 도는 것은 다른 문제다

2026-08-04 IT/기술

서론: 맥이 느린 게 아니라 GPU가 놀고 있다

맥북에서 로컬 LLM을 돌리는데 팬이 돌고 배터리는 녹는데 토큰은 한 글자씩 떨어진다. 그러면 대개 다음 수순은 정해져 있다. 더 작은 모델로 바꾸고, 양자화를 더 세게 걸고, 그래도 안 되면 「역시 맥은 안 되나」로 끝난다.

그런데 이 상태에서 활성 상태 보기를 열어 GPU 기록 창을 띄워 보면 GPU 사용률이 거의 바닥인 경우가 흔하다. 애플 실리콘 맥의 GPU는 놀고 있고 CPU 코어만 전부 튀고 있는 그림이다. 모델이 큰 게 아니라 계산이 엉뚱한 장치에서 돌고 있는 것이다.

이런 상황은 특히 파이프라인을 직접 조립한 경우에 잘 생긴다. 모델 로딩 코드는 어디선가 복사해 왔고, 그 코드는 CUDA가 있으면 GPU를 쓰고 없으면 CPU로 떨어지도록 쓰여 있다. 맥에는 CUDA가 없으니 조건문은 아무 오류 없이 CPU 경로를 탄다. 실패가 아니라 조용한 폴백이라 로그에 아무것도 남지 않는다.

이 글은 그 지점을 다룬다. 지금 GPU를 쓰고 있는지 확인하는 절차, 프레임워크별로 실제로 존재하는 스위치, 그리고 켜도 안 빨라지는 다섯 가지 경우다. 하드웨어를 새로 고르는 이야기는 로컬 LLM 하드웨어 선택 가이드에서, 양자화 포맷을 어디까지 조일지는 로컬 LLM 실행 가이드 - 하드웨어 요건과 GGUF 양자화 트레이드오프에서 다뤘으므로 여기서는 반복하지 않는다. 여기서 다루는 것은 이미 손에 있는 맥에서 GPU를 쓰게 만드는 일이다.

참고로 이 주제가 다시 화제가 된 계기는 한 개인 파이프라인의 최적화 기록이 커뮤니티에 올라온 것이었다. 한 줄 수정으로 전체 실행 시간이 절반 가까이 줄었다는 내용인데, 그 배수를 그대로 옮겨 쓰는 것은 의미가 없다. 이유는 뒤에서 따로 정리했다.

1. 통합 메모리 - 맥에서 「GPU로 옮긴다」가 다른 뜻인 이유

먼저 구조를 정확히 잡아야 그다음 이야기가 이해된다. NVIDIA 카드가 달린 PC에서 GPU를 쓴다는 것은 데이터를 VRAM으로 복사한다는 뜻이다. 시스템 메모리와 VRAM은 물리적으로 다른 칩이고 그 사이를 오가는 복사가 비용이다. 그래서 CUDA 코드는 어디에 무엇이 있는지를 늘 신경 쓴다.

애플 실리콘은 여기가 다르다. MLX 문서가 정리한 표현대로 CPU와 GPU가 같은 메모리 풀에 직접 접근한다. 배열은 어디에 놓을지 지정할 필요 없이 통합 메모리에 있고, 대신 연산 쪽이 어느 장치에서 실행될지를 고른다. 이 차이가 실무에서 만드는 결과는 셋이다.

  • 복사 비용이 없다. CPU 전처리와 GPU 추론을 섞어도 그 경계에서 전송이 발생하지 않는다
  • 모델 크기 상한이 VRAM이 아니라 기기 전체 메모리로 정해진다. 16GB 카드 한 장으로 못 올리던 모델이 통합 메모리 64GB 기기에는 올라간다
  • 대신 경쟁이 생긴다. 브라우저와 IDE가 먹는 메모리가 곧 모델이 못 쓰는 메모리다. VRAM이 분리돼 있을 때는 없던 문제다

PyTorch 쪽 용어로 이 장치를 부르는 이름이 MPS다. 공식 문서 설명은 머신러닝 계산 그래프와 프리미티브를 Metal Performance Shaders Graph 프레임워크와 Metal Performance Shaders가 제공하는 튜닝된 커널에 각각 매핑하는 새 장치를 도입한다는 것이다. 요약하면 애플의 GPU 계산 스택에 파이토치를 연결하는 백엔드다.

여기서 자주 어긋나는 기대 하나. 통합 메모리는 「메모리를 넉넉히 쓸 수 있다」는 뜻이지 「메모리 대역폭이 넉넉하다」는 뜻이 아니다. LLM 디코딩은 매 토큰마다 가중치를 훑는 메모리 대역폭 지배적인 작업이라, 같은 통합 메모리 용량이어도 칩 등급에 따라 초당 토큰 수가 크게 벌어진다. 용량은 올릴 수 있느냐를 정하고, 대역폭은 얼마나 빠르냐를 정한다. 두 축을 섞지 말 것.

2. 프레임워크별 스위치 - PyTorch·llama.cpp·MLX

실제로 존재하는 스위치만 정리한다. 프레임워크마다 기본값이 다르다는 점이 중요하다. 어떤 것은 켜야 하고, 어떤 것은 이미 켜져 있다.

스택GPU 기본값켜는 방법끄고 비교하는 방법
PyTorch꺼짐. 명시하지 않으면 CPU장치 문자열 "mps"device="cpu"로 바꿔 같은 코드 실행
llama.cpp켜짐. macOS에서 Metal이 기본 활성별도 조치 불필요--device none
MLXGPU가 기본 실행 장치별도 조치 불필요연산에 stream=mx.cpu 지정

2.1 PyTorch - 옮기는 것이 두 개다

파이토치는 명시하지 않으면 CPU다. 그래서 코드에서 장치를 직접 지정해야 한다.

import torch

print(torch.backends.mps.is_available())  # 지금 이 기기에서 쓸 수 있는가
print(torch.backends.mps.is_built())      # 설치한 빌드에 MPS가 들어 있는가

device = "mps" if torch.backends.mps.is_available() else "cpu"
model = model.to(device)
inputs = inputs.to(device)   # ← 여기를 빠뜨리는 경우가 가장 많다

가장 흔한 실수가 마지막 줄이다. 모델만 옮기고 입력 텐서를 CPU에 남겨 두면 장치 불일치 오류가 나거나, 라이브러리가 조용히 맞춰 주면서 매 스텝 전송이 끼어든다. 확인 함수를 두 개 쓴 이유도 분명하다. is_available()이 거짓이면 기기나 macOS 버전 문제이고, is_built()가 거짓이면 설치한 파이토치 빌드에 MPS가 없는 것이다. 후자는 재설치로 풀리고 전자는 재설치로 절대 안 풀린다.

안 될 때 파이토치가 내놓는 문구도 이 둘을 그대로 구분해서 알려 준다. 하나는 「MPS not available because the current PyTorch install was not built with MPS enabled.」이고, 다른 하나는 「MPS not available because the current macOS version is not 14.0+ and/or you do not have an MPS-enabled device on this machine.」이다. 메시지를 끝까지 읽으면 어느 쪽인지 이미 적혀 있다.

2.2 llama.cpp - 이미 켜져 있으니 끄는 쪽을 배워라

GGUF 모델을 llama.cpp로 돌리는 구성이라면 스위치를 찾을 필요가 없다. 공식 빌드 문서가 macOS에서 Metal은 기본으로 켜진다고 못 박고 있다. 여기서 배워야 할 것은 반대 방향, 즉 비교군을 만들기 위해 끄는 법이다.

# GPU 계층 수를 0으로: GPU 추론은 꺼지지만 일부 연산은 여전히 GPU를 탈 수 있다
llama-cli -m model.gguf -ngl 0 -p "안녕하세요"

# 완전히 끄기: GPU 가속을 전부 비활성화한다
llama-cli -m model.gguf --device none -p "안녕하세요"

두 옵션의 차이가 중요하다. 문서는 -ngl 0으로도 일부 계산은 GPU로 가속될 수 있다고 적는다. 그러니 「GPU 없이 얼마나 걸리나」를 정직하게 재려면 --device none을 써야 한다. 이걸 모르고 -ngl 0으로만 비교하면 기준선이 이미 GPU 도움을 받은 값이라 배수가 실제보다 작게 나온다.

빌드 단계에서 아예 빼는 방법도 있다. CMake에 -DGGML_METAL=OFF를 주면 Metal 없이 빌드된다. 직접 빌드한 바이너리가 느리다면 이 플래그가 어딘가에 들어가 있는지부터 확인하는 게 순서다.

2.3 MLX - 장치를 옮기는 대신 연산에 지정한다

애플이 공개한 MLX는 통합 메모리를 전제로 설계돼 있어서 발상 자체가 다르다. 배열을 옮기는 API가 없고, 연산에 stream 인자로 실행 장치를 지정한다.

import mlx.core as mx

a = mx.random.normal((4096, 512))
b = mx.random.uniform(shape=(512,))

c = mx.add(a, b, stream=mx.gpu)   # GPU에서
d = mx.add(a, b, stream=mx.cpu)   # 같은 배열을 CPU에서

같은 배열 a, b를 복사 없이 양쪽에서 쓴다는 점이 요점이다. 의존 관계가 있으면 MLX 스케줄러가 스트림 사이에 의존성을 자동으로 끼워 넣어 순서를 보장한다. 문서는 무거운 연산을 GPU에, 가벼운 연산을 CPU에 나눠 병렬로 돌리는 예제에서 약 2배가 나온 사례를 보여 준다. 다만 이건 문서의 예제 워크로드에서 나온 값이지 LLM 추론에서 그렇다는 뜻이 아니다.

3. 지금 GPU를 쓰고 있는지 확인하는 세 가지 절차

여기가 이 글의 핵심이다. 세 층을 따로 확인해야 한다. 하나만 보면 반드시 틀린 결론에 도달한다.

3.1 첫째 - 장치가 잡히는가

코드 레벨 확인이다. 앞서 본 is_available()과 is_built()를 둘 다 찍는다. 여기까지는 대부분 통과한다. 그리고 여기서 통과했다고 GPU를 쓰고 있는 건 아니다. 장치가 존재한다는 것과 내 코드가 그 장치를 쓴다는 것은 별개다.

3.2 둘째 - 실제로 도는가

시스템 레벨 확인이다. 추론을 돌려 둔 채로 다음 둘 중 하나를 본다.

  • 활성 상태 보기를 열고 상단 메뉴의 창 항목에서 GPU 기록 창을 띄운다. 추론이 시작될 때 그래프가 올라가야 한다
  • 터미널에서 sudo powermetrics --samplers gpu_power -i 1000 -n 5를 돌려 GPU 관련 수치를 본다. 관리자 권한이 필요하다

판독 기준은 단순하다. 추론 중인데 GPU 그래프가 평평하고 CPU 코어만 전부 차 있으면, 장치 확인을 통과했더라도 계산은 CPU에서 돌고 있는 것이다. 반대로 GPU 그래프는 올라가는데 사용률이 낮게 요동친다면 다음 절의 CPU 폴백을 의심할 차례다.

3.3 셋째 - 메모리를 잡고 있는가

파이토치는 이걸 직접 볼 수 있는 함수를 제공한다. 셋을 함께 찍으면 상태가 한눈에 드러난다.

import torch

# 텐서가 실제로 점유한 GPU 메모리(바이트)
print(torch.mps.current_allocated_memory())

# Metal 드라이버가 이 프로세스에 할당한 총 GPU 메모리(바이트)
print(torch.mps.driver_allocated_memory())

# 권장 최대 워킹셋 크기(바이트)
print(torch.mps.recommended_max_memory())
  • current_allocated_memory()가 0에 가깝다 → 모델이 GPU 쪽에 안 올라갔다. 장치 지정을 다시 보라
  • driver_allocated_memory()가 recommended_max_memory()에 근접한다 → 다음 절의 메모리 압박 구간이다
  • 둘 다 정상인데 느리다 → 장치 문제가 아니다. 측정 방식이나 워크로드 형태 쪽을 보라

이 세 층을 순서대로 통과시키는 것이 진단의 전부다. 「GPU를 켰는데 안 빨라져요」라는 질문의 절반 이상은 사실 3.2에서 이미 걸린다.

4. 제대로 재는 법 - 배수를 말하기 전에 갖춰야 할 조건

스위치를 켰다면 이제 얼마나 빨라졌는지 재야 한다. 그런데 여기서 틀리는 경우가 스위치를 못 켜는 경우만큼 흔하다. 특히 MPS는 비동기라 시계 위치를 잘못 잡으면 실제보다 훨씬 좋은 숫자가 나온다.

4.1 동기화 없이 재면 커널이 끝나기 전에 시계가 멈춘다

torch.mps.synchronize()의 문서 설명은 MPS 장치의 모든 스트림에 있는 모든 커널이 완료될 때까지 기다린다는 것이다. 이 함수를 안 쓰면 파이썬은 커널을 큐에 넣자마자 다음 줄로 넘어가고, 시계는 제출 시간을 재게 된다.

import torch, time

def timed(fn, warmup=1, runs=3):
    for _ in range(warmup):          # 첫 실행 비용을 버린다
        fn()
    torch.mps.synchronize()

    times = []
    for _ in range(runs):
        torch.mps.synchronize()
        t0 = time.perf_counter()
        fn()
        torch.mps.synchronize()      # 끝날 때까지 기다린 뒤에 멈춘다
        times.append(time.perf_counter() - t0)

    times.sort()
    return times[len(times) // 2]    # 중앙값

4.2 고정해야 할 조건

배수를 말하려면 아래를 전부 같게 두고 장치만 바꿔야 한다. 하나라도 흔들리면 그 숫자는 아무것도 증명하지 않는다.

  • 같은 프롬프트, 같은 최대 생성 토큰 수. 출력 길이가 다르면 시간이 다른 게 당연하다
  • 같은 시드. 파이토치라면 torch.mps.manual_seed()로 고정한다
  • 워밍업 1회 이상을 버리고, 3회 이상의 중앙값. 평균이 아니라 중앙값을 쓰는 이유는 배경 작업 한 번이 평균을 통째로 망치기 때문이다
  • 전원 상태를 고정한다. 어댑터 연결 여부와 저전력 모드를 두 측정에서 동일하게 둔다
  • 배경 프로세스를 정리한다. 회사 지급 장비의 보안 에이전트나 백업 데몬이 돌던 중이면 그 회차는 버린다
  • 프리필과 디코드를 나눠 본다. 첫 토큰까지 걸린 시간과 이후 초당 토큰 수는 병목이 다르다. 합쳐서 하나의 숫자로 만들면 무엇이 개선됐는지 알 수 없다

4.3 남에게 숫자를 말할 때 함께 적어야 하는 것

같은 이유로, 어디선가 본 배수를 인용할 때도 아래가 같이 적혀 있지 않으면 그 값은 참고가 안 된다. 자기 결과를 공유할 때도 마찬가지다.

  • 칩 등급과 GPU 코어 수, 통합 메모리 용량
  • 모델 이름과 파라미터 규모, 양자화 유형
  • 컨텍스트 길이와 실제 생성한 토큰 수, 배치 크기
  • 비교 대상이 무엇인지 (CPU 실행인지, -ngl 0인지, --device none인지)
  • 파이프라인 전체 시간을 말한다면 그중 GPU로 옮길 수 있는 구간이 원래 몇 퍼센트였는지

마지막 항목이 결정적이다. 전체 8분짜리 파이프라인에서 GPU 구간이 원래 6분이었다면 절반을 줄이는 게 가능하지만, 2분이었다면 아무리 잘해도 2분 밑으로는 못 내려간다. 배수는 스위치가 아니라 그 파이프라인의 구성이 만든다.

5. 켜도 안 빨라지는 다섯 가지

스위치를 정확히 켰고 GPU 그래프도 올라가는데 체감이 그대로인 경우가 남는다. 원인은 대개 이 다섯 중 하나다.

원인증상확인 방법대응
미지원 연산의 CPU 폴백GPU 사용률이 낮게 오르내리고 CPU도 함께 튄다폴백 환경 변수를 끄고 실행해 NotImplementedError가 어느 연산에서 나는지 본다해당 연산을 지원되는 형태로 교체하거나 상류 라이브러리를 갱신
첫 실행 비용첫 회만 유난히 느리고 두 번째부터 정상워밍업 후 다시 측정측정에서 첫 회를 버린다. 서비스라면 기동 시 더미 추론 한 번
배치 1 · 짧은 프롬프트벤치마크에서는 빨라지는데 대화창에서는 체감이 없다배치와 프롬프트 길이를 키워 다시 측정일괄 처리 작업으로 묶는다. 대화형은 원래 이득이 작다
메모리 압박과 스왑처음엔 괜찮다가 중간부터 급격히 느려지고 디스크가 돈다driver_allocated_memory()와 recommended_max_memory()를 비교양자화를 더 걸거나 컨텍스트를 줄인다. 다른 앱을 닫는다
측정 오류말이 안 되게 좋은 배수가 나온다torch.mps.synchronize()를 앞뒤에 넣고 다시 측정측정 코드를 고친다. 결과가 반토막 나는 게 정상이다

5.1 CPU 폴백 - 편하지만 공짜가 아니다

MPS가 아직 구현하지 않은 연산을 만나면 파이토치는 오류를 낸다. 이때 쓰는 것이 PYTORCH_ENABLE_MPS_FALLBACK이다. 문서 설명은 1로 설정하면 MPS가 지원하지 않는 연산을 CPU로 폴백시킨다는 것이다.

export PYTORCH_ENABLE_MPS_FALLBACK=1
python app.py

이걸 켜면 일단 돌아간다. 그런데 돌아가는 것과 빨라지는 것은 다르다. 폴백이 걸린 연산마다 CPU와 GPU 사이를 오가는 왕복이 생기고, 그 연산이 루프 안에 있으면 배수가 통째로 사라진다. 그래서 순서는 이렇게 잡는 게 맞다. 먼저 폴백을 끄고 돌려 어느 연산이 문제인지 이름을 확보한 다음, 그 연산을 우회할 수 있는지 보고, 우회가 어려울 때만 폴백을 켠 채로 운영한다. 처음부터 켜 두면 무엇이 발목을 잡는지 영영 모른다.

이 변수는 프로세스 환경에서 읽힌다. 파이썬 코드 안에서 os.environ으로 설정할 거라면 import torch보다 앞이어야 하고, 안전한 쪽은 셸에서 export로 거는 것이다. 파이토치 이슈 트래커와 포럼에는 import 뒤에 설정해 아무 효과가 없었다는 보고가 반복해서 올라와 있다.

5.2 배치 1이라는 구조적 한계

GPU가 CPU를 크게 앞서는 조건은 같은 연산을 대량으로 병렬 처리할 때다. 그런데 대화형 로컬 LLM은 정확히 그 반대다. 배치 1, 짧은 프롬프트, 한 번에 토큰 하나. 디코딩 구간은 계산량보다 메모리에서 가중치를 읽어 오는 속도에 묶인다.

그래서 같은 기기에서도 프리필 구간은 크게 빨라지고 디코드 구간은 덜 빨라지는 비대칭이 생긴다. 긴 문서를 넣고 짧게 답하게 하는 작업이라면 체감이 크고, 짧게 묻고 길게 답하게 하는 작업이라면 체감이 작다. 이건 설정으로 뒤집을 수 있는 게 아니라 작업의 성질이다. 디코드 자체를 구조적으로 빠르게 하려는 접근은 투기적 디코딩 쪽 기법에서 다뤘다.

6. 통합 메모리 용량과 모델 크기 - 산술로 먼저 걸러라

「16GB 맥북에서 뭐가 되나요」라는 질문에는 산술로 답할 수 있다. 가중치가 차지하는 용량은 파라미터 수 × 파라미터당 바이트다. 16비트는 파라미터당 2바이트, 8비트는 1바이트, 4비트는 0.5바이트다.

모델 규모16비트8비트4비트편하게 돌리려면
3B약 6GB약 3GB약 1.5GB8GB 이상
7~8B약 16GB약 8GB약 4GB16GB
13~14B약 28GB약 14GB약 7GB16GB는 빠듯 · 24GB 권장
30~32B약 64GB약 32GB약 16GB32GB는 빠듯 · 48GB 권장
70B약 140GB약 70GB약 35GB64GB 이상

표의 숫자는 가중치만 계산한 산술값이다. 실제로는 여기에 세 가지가 더 붙는다.

  • OS와 상시 앱의 몫. macOS 자체, 브라우저, 에디터가 늘 몇 GB를 잡고 있다
  • KV 캐시. 컨텍스트 길이에 대략 비례해 늘어난다. 긴 문서를 넣는 순간 여기서 먼저 터진다
  • 양자화 유형에 따른 여유분. 4비트급 GGUF라도 일부 텐서는 더 높은 정밀도로 남기므로 파일 크기가 산술값보다 크다. 산술값이 아니라 실제 파일 크기로 계산하라

그래서 「32GB니까 32B 4비트가 16GB, 절반이 남네」는 성립하지 않는다. 실제로 그렇게 올리면 그 맥으로 다른 일을 거의 못 하게 된다. 표의 마지막 열을 「가능한 최대」가 아니라 「다른 작업을 하면서도 쓸 수 있는 선」으로 읽는 편이 맞다. 양자화 단계별 품질 손실을 어디까지 감수할지는 GGUF 양자화 트레이드오프 정리를 참고하면 된다.

통합 메모리는 나중에 못 늘린다. 애플 실리콘의 메모리는 SoC 패키지에 함께 실려 있어 구매 후 증설이 불가능하다. 중고를 포함해 기기를 고를 때 이 항목만은 되돌릴 수 없는 선택이라는 뜻이다. 지금 8B로 충분하다고 판단해 최소 옵션을 고르면, 1년 뒤 30B를 돌려 보고 싶어졌을 때 방법이 없다.

7. CUDA와 무엇이 다른가

PC에서 하던 감각을 그대로 들고 오면 어긋나는 지점이 있다. 축별로 정리하면 이렇다.

축맥 (Metal / MPS)NVIDIA (CUDA)

여기서 나오는 실무적 결론이 하나 있다. 맥은 「큰 모델을 일단 올려 보는 것」에 강하고, 「올린 모델을 최대 속도로 짜내는 것」에는 약하다. 64GB 통합 메모리 기기에 70B급을 올리는 일은 카드 한 장으로는 흉내 낼 수 없지만, 올린 뒤의 초당 토큰 수를 커널 수준에서 끌어올리는 여지는 CUDA 생태계 쪽이 훨씬 넓다. 이 비대칭을 알고 있으면 맥으로 무엇을 하고 무엇을 하지 말지가 정리된다.

8. 로컬을 접고 API로 갈 판단 기준

스위치를 다 켜고 제대로 측정한 뒤에도 목표 지연을 못 맞추는 경우가 있다. 그때 같은 기기에서 더 짜낼 여지는 대개 크지 않다. 남은 선택지는 셋뿐이고, 각각 대가가 분명하다.

  • 모델을 줄인다 → 품질을 내준다
  • 기기를 바꾼다 → 비용을 내준다. 그리고 통합 메모리는 증설이 안 되므로 통째 교체다
  • API로 간다 → 데이터가 밖으로 나가고 호출당 비용이 붙는다

어느 쪽이 맞는지는 조건으로 갈린다. 아래 기준이면 로컬을 유지하는 편이다.

  • 데이터가 조직 밖으로 나가면 안 된다. 이 조건에서는 속도가 협상 대상이 아니다
  • 호출 빈도가 높고 프롬프트가 짧은 반복 작업이다. 분류·태깅·추출 같은 것들
  • 오프라인이거나 네트워크가 불안정한 환경에서 돌아야 한다
  • 지연이 느려도 되지만 예측 가능해야 한다. 외부 API의 혼잡 시간대 변동이 더 곤란한 경우다

반대로 아래 기준이면 API로 넘기는 편이다.

  • 모델 품질이 결과물의 가치를 직접 결정한다. 최종 원고, 고객 응대 문안 같은 것들
  • 필요한 규모가 기기 메모리를 넘어선다. 32GB 기기에서 70B가 필요한 상황
  • 컨텍스트가 길다. KV 캐시가 통합 메모리를 먹는 구조라 로컬에서 가장 먼저 무너지는 축이다
  • 여러 사람이 동시에 쓴다. 맥 한 대는 동시 요청에 약하다

현실적인 답은 대개 둘을 섞는 것이다. 전처리·분류·1차 요약은 로컬에서 돌리고 최종 생성만 외부로 보내면, 호출 수는 줄이면서 품질이 필요한 지점에만 비용을 쓴다. 이 구성에서 모델을 어떻게 갈아 끼우고 라우팅할지는 LLM 라우터로 여러 모델을 단일 API로 다루는 방식에서 다뤘고, 로컬 모델을 에이전트로 굴릴 때의 별도 제약은 로컬 LLM 에이전트 개발, 툴 검색과 HITL이 필요한 이유에 정리돼 있다.

9. 한국에서 맥으로 로컬 LLM을 돌릴 때

9.1 초당 토큰 수가 같아도 체감 속도는 다르다

속도 지표는 대부분 초당 토큰으로 표기되는데, 같은 문장이 몇 토큰으로 쪼개지는지는 언어와 토크나이저에 따라 다르다. 그래서 영어 기준으로 발표된 초당 토큰 수를 한국어 작업의 체감으로 그대로 옮기면 어긋난다. 자기가 실제로 넣을 한국어 문장이 자기 모델의 토크나이저에서 몇 토큰이 되는지 먼저 세어 보는 편이 빠르다. 토큰 수를 대략 가늠하는 데에는 아래 도구 목록의 토큰 계산기를 쓰면 된다.

9.2 폐쇄망에서는 스위치 점검이 성능 문제가 아니다

금융·공공처럼 외부 API 호출이 막힌 환경에서는 로컬이 선택지가 아니라 전제다. 이때 GPU 활용 여부는 「더 빠르게」의 문제가 아니라 「쓸 만한가」의 문제가 된다. CPU로 돌아가는 상태에서 도입 검토를 하면 성능이 요건에 못 미친다는 결론이 나오고, 그 결론은 모델이 아니라 설정 때문에 나온 것일 수 있다. 도입 판단 전에 3장의 세 층을 반드시 통과시켜라. 순서가 뒤바뀌면 멀쩡한 후보를 탈락시킨다.

9.3 회사 지급 장비의 변수

사내 지급 맥에는 보안 에이전트나 자산 관리 도구가 상주하는 경우가 많다. 이들이 주기적으로 CPU를 점유하면 측정값이 회차마다 흔들린다. 4장에서 평균이 아니라 중앙값을 쓰라고 한 이유가 여기에도 걸린다. 측정 중에 예상 못 한 튐이 있으면 그 회차를 버리고 다시 재는 게 맞다.

9.4 중고 맥을 살 때 확인할 순서

국내 중고 시장에서 맥을 고를 때 로컬 LLM이 목적이라면 확인 순서가 정해져 있다.

  • 통합 메모리 용량이 첫째다. 증설이 불가능하므로 되돌릴 수 없는 유일한 항목이다
  • 칩 등급이 둘째다. 같은 용량이어도 메모리 대역폭이 다르고, 디코드 속도가 여기에 묶인다
  • 저장 장치는 셋째다. 모델 파일은 크지만 외장으로 감당할 수 있다
  • 세대 차이는 위 셋을 정한 뒤에 볼 항목이다. 메모리가 작은 최신 세대보다 메모리가 큰 이전 세대가 올릴 수 있는 모델의 범위에서는 낫다

10. 확인하지 못한 것

다음 항목은 1차 근거를 확보하지 못해 본문에서 수치나 방법으로 쓰지 않았다.

  • 이 글의 발단이 된 최적화 기록의 배수. 커뮤니티에 공유된 개인 파이프라인 기록으로, 한 줄 수정으로 실행 시간이 절반 가까이 줄었다는 내용이다. 어떤 칩·통합 메모리·모델·양자화·컨텍스트 길이에서 나온 값인지 특정하지 못해 본문에 수치로 옮기지 않았다. 원문은 참고 자료에 링크해 두었다
  • 애플의 권장 워킹셋 크기 정의 원문. torch.mps.recommended_max_memory()가 반환하는 값의 근거인 Metal 쪽 정의를 애플 공식 문서에서 열지 못했다. 그래서 「전체 메모리의 몇 퍼센트까지 GPU가 쓸 수 있는가」에 해당하는 구체 수치는 쓰지 않았다. 함수가 돌려주는 값을 자기 기기에서 직접 찍어 보는 편이 확실하다
  • GPU 가용 메모리 상한을 sysctl로 올리는 방법. 커뮤니티에 널리 퍼져 있으나 애플 1차 문서를 특정하지 못했다. 시스템 전역 설정을 건드리는 조치라 근거 없이 권하지 않는다
  • MLX 문서의 약 2배. 문서가 제시한 예제 워크로드에서 나온 값이며 LLM 추론에서 측정된 값이 아니다. 본문에서도 그 범위로만 인용했다
  • Ollama·LM Studio 같은 런처의 내부 스위치. 이들이 하위 엔진의 Metal 관련 설정을 어디까지 노출하는지는 버전에 따라 달라 각 배포판의 문서를 확인해야 한다. 이 글의 표에는 공식 문서로 확인한 세 스택만 넣었다
  • 칩 등급별 초당 토큰 수. 기기·모델·양자화·컨텍스트 조합마다 달라지고, 조건이 명시된 공개 측정을 확보하지 못해 넣지 않았다. 4장의 절차로 자기 기기에서 재는 편이 정확하다

11. 결론: 스위치 하나가 아니라 순서다

맥에서 로컬 LLM이 느릴 때 가장 먼저 의심할 것은 모델 크기가 아니라 계산이 어디서 돌고 있는지다. 그리고 이건 추측할 일이 아니라 3분이면 확인되는 일이다.

순서를 정리하면 이렇다.

  1. 장치가 잡히는지 확인한다. 파이토치라면 is_available()과 is_built()를 둘 다 찍는다. 실패 메시지 두 종류는 원인이 완전히 다르다
  2. 실제로 도는지 본다. 추론 중에 활성 상태 보기의 GPU 기록이 올라가는지. 여기서 걸리는 경우가 가장 많다
  3. 메모리를 잡고 있는지 본다. driver_allocated_memory()가 0에 가까우면 모델이 GPU 쪽에 없다
  4. 제대로 잰다. torch.mps.synchronize()로 감싸고, 워밍업을 버리고, 중앙값을 쓴다. 이 단계를 건너뛰면 이후 판단이 전부 흔들린다
  5. 그래도 안 빨라지면 다섯 가지를 순서대로 지운다. CPU 폴백, 첫 실행 비용, 배치 크기, 메모리 압박, 측정 오류

마지막으로 배수 이야기를 정리하고 끝내자. 「한 줄로 몇 배」라는 형태의 수치는 방향만 가져오고 크기는 버리는 게 맞다. GPU를 안 쓰던 파이프라인이 GPU를 쓰게 되면 크게 빨라진다는 결론은 구조에서 나오므로 흔들리지 않는다. 하지만 그 배수는 그 사람의 칩과 그 사람의 모델과 그 사람의 파이프라인에서 GPU 구간이 차지하던 비중이 만든 값이다.

지금 당장 할 일은 하나다. 돌아가고 있는 추론 옆에 활성 상태 보기의 GPU 기록 창을 띄워 보는 것. 그래프가 평평하다면, 바꿔야 할 것은 모델이 아니다.
