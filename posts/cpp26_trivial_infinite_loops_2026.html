1. while (true);가 미정의 동작이었던 배경

일반적으로 프로그래밍 언어에서 반복 제어문은 특정 조건이 충족될 때까지 실행 흐름을 유지하거나 시스템을 대기 상태로 두기 위한 기본 구조로 사용된다. 많은 개발자는 소스 코드에서 본문이 비어 있는 while (true); 구문을 작성할 때 프로그램이 해당 지점에 도달하여 영원히 멈추는 명시적인 무한 루프를 의도한다. 그러나 원문은 C++26 이전까지 아무런 부작용(side effect)이 없는 while (true); 형태의 루프가 표준 명세상 미정의 동작(undefined behaviour)이었다고 적는다. 많은 프로그래머가 이 코드가 온전히 정의된 동작(well-defined)일 것이라고 짐작하지만, 원문에 따르면 C++26 이전의 표준 규정상 이는 잘못된 생각이었다.

원문은 부작용을 일으키지 않는 무한 루프에 대해 컴파일러가 해당 루프가 언젠가는 반드시 종료될 것이라고 가정할 수 있는 재량을 부여받았다고 설명한다. 그리고 일부 컴파일러, 특히 Clang과 같은 최적화기는 이러한 표준 규정을 근거로 루프 전체를 최적화 과정에서 완전히 제거(optimize away)해 버리는 거동을 보여주었다고 원문은 지적한다. 원문은 이러한 루프 제거가 개발자가 예상하지 못한 충격적인 결과(spectacular consequences)로 이어졌다고 기술한다.

이 글의 해석으로는, 컴파일러의 최적화 규칙과 개발자의 직관적인 코드 작성 의도가 충돌한 문제를 문법적 예외로 정리한 것이다.

원문은 이번 변경이 무한 루프 전반을 무차별적으로 안전하게 만든 것이 아니라는 점을 분명히 한다. C++26이 도입한 변화는 모든 무한 반복문을 구제하는 것이 아니라, 문법적으로 극히 제한된 형태에 대해서만 미정의 동작의 딱지를 떼어낸 좁은 수정이다. 원문은 단순 무한 루프라는 엄격한 정의를 충족할 때에만 비로소 컴파일러의 제거 대상에서 제외된다고 적는다.

2. 진행 보장(Forward Progress) 가정과 컴파일러의 루프 최적화

원문은 컴파일러가 무한 루프를 지울 수 있었던 이론적 배경으로 C++11 표준에서 공식화된 진행 보장(forward progress) 규칙을 인용한다. 원문이 인용한 C++ 표준 [intro.progress] 조항에 따르면, 컴파일러 구현체는 실행 중인 모든 스레드가 궁극적으로 정해진 동작 중 하나를 수행할 것이라고 전제할 수 있다. 원문에 인용된 C++11 표준 문언은 다음과 같다(「the implementation may assume any thread will eventually do one of the following: terminate, call a library I/O function, access a volatile glvalue, or perform a synchronization or atomic operation」). 즉, 컴파일러는 모든 스레드가 결국 아래 네 가지 동작 중 하나에 도달한다고 가정할 권한을 갖는다.

  • 스레드의 정상적인 실행 종료(terminate).
  • 표준 라이브러리 I/O 함수의 호출(call a library I/O function).
  • volatile 한정자가 붙은 glvalue 메모리에 대한 접근(access a volatile glvalue).
  • 동기화 연산 또는 원자적(atomic) 연산의 수행(perform a synchronization or atomic operation).

원문은 본문이 세미콜론 하나로 끝나는 while (true); 구문이 위 네 가지 동작 중 단 하나도 일으키지 않는다는 사실을 지적한다. 루프 내부에는 I/O 호출도 없고, volatile 메모리 접근도 없으며, 원자적 동기화도 없고, 정상 종료 경로도 존재하지 않는다. 원문의 설명에 따르면, 컴파일러는 진행 보장 규칙에 근거하여 이 스레드가 영원히 실행되지 않고 결국 언젠가는 종료될 것이라고 가정해 버린다. 그리고 루프 내부에 관찰 가능한 부작용이 전혀 없으므로, 루프 자체를 실행할 필요가 없다고 판단하여 루프 검사와 점프 명령을 바이너리에서 통째로 제거한다.

이 글의 해석으로는, 진행 보장 규정이 명시한 네 가지 관찰 가능한 동작 중 어느 것도 수행하지 않는 루프를 컴파일러가 종료 가능한 것으로 취급한 결과다.

3. Clang의 루프 제거 사례와 unreachable 코드 실행

원문은 컴파일러가 루프를 제거했을 때 실제로 어떤 결과가 발생하는지를 보여주기 위해 Clang 컴파일러를 사용한 대표적인 예제 코드를 제시한다. 원문에 실린 코드는 다음과 같다.

// https://godbolt.org/z/WYMxxeW1T
#include <iostream>

int main() {
    while (true)
        ;
}

void unreachable() {
    std::cout << "Hello world!" << std::endl;
}

원문은 Clang 컴파일러 환경에서 이 프로그램을 컴파일하여 실행할 경우 놀랍게도 화면에 「Hello world!」라는 문자열이 출력된다고 적는다. 소스 코드 어디에서도 unreachable() 함수를 호출하는 문장이 존재하지 않으며, main() 함수 안에는 오직 while (true); 루프 하나만 있을 뿐이다. 그럼에도 불구하고 프로그램은 호출되지 않은 함수 내부로 진입하여 문자열을 출력하고 종료한다.

원문은 컴파일러가 while (true); 무한 루프를 아무런 부작용이 없다는 이유로 완전히 삭제했고, 그 결과 main 함수의 실행 흐름이 루프를 지나쳐 함수 끝으로 빠져나왔다고 설명한다. 그리고 링커(linker)가 메모리상에서 main 함수 바로 뒤에 배치한 unreachable() 함수의 첫 머리로 제어 흐름이 그대로 낙하(fall through)하면서 해당 함수의 본체가 실행되었다고 원문은 밝힌다.

이 글의 해석으로는, 루프가 제거되면서 함수의 제어 흐름 경계가 사라져 메모리상 바로 뒤에 배치된 함수가 실행된 것이다.

4. C++26 P2809R3이 정의한 '단순 무한 루프'의 요건

원문은 이러한 미정의 동작 문제를 해결하기 위해 표준에 공식 채택된 제안이 바로 P2809R3 제안이라고 밝힌다. 원문은 이 제안이 채택됨에 따라 C++26부터 단순 무한 루프가 더 이상 미정의 동작이 아니게 되었다고 적는다. 그러나 원문은 이 제안이 부여하는 보호의 범위가 극히 엄격하고 좁게 정의되어 있다는 점을 핵심 사실로 강조한다.

원문이 인용한 제안서의 정의 문언은 다음과 같다(「The loop must be a trivially empty iteration statement — meaning its body is literally empty (`;` or `{}`). Any non-empty statement in the body, even a meaningless expression statement such as `"a string";`, disqualifies it. The controlling expression must be a constant expression that evaluates to `true`.」). 원문에 명시된 보호 요건을 정리하면 다음과 같은 조건으로 압축된다.

  • 루프 본문은 문자 그대로 완전히 비어 있는 빈 반복문(trivially empty iteration statement)이어야 한다.
  • 허용되는 본문 형태는 단독 세미콜론(;) 또는 빈 중괄호 블록({})뿐이다.
  • 본문 내부에 아무런 효과가 없는 무의미한 표현식 문장(예: "a string";)이라도 존재하면 즉시 보호 자격을 상실한다.
  • 루프를 제어하는 조건식(controlling expression)은 반드시 true로 평가되는 컴파일 타임 상수식(constant expression)이어야 한다.

원문은 루프 본문이 비어 있어야 한다는 규칙이 조금의 예외도 허용하지 않는 엄격한 형태적 요건이라고 설명한다. 비록 실행 시점에 아무런 레지스터를 건드리지 않고 메모리를 읽거나 쓰지 않는 무해한 표현식이라 하더라도, 문법적으로 본문이 비어 있지 않다면 P2809R3이 규정한 단순 무한 루프에 해당하지 않는다. 따라서 그러한 루프는 C++26에서도 여전히 과거와 마찬가지로 미정의 동작으로 남는다.

이 글의 해석으로는, 보호 범위가 문법적으로 판별 가능한 빈 본문 형태로 한정된 것이 이 규칙의 핵심이다.

5. 문법 형태별 C++26 보호 여부 대조

원문은 개발자가 작성할 수 있는 다양한 무한 반복문 구문을 예시로 들어, C++26에서 공식적으로 보호되는 코드와 여전히 보호되지 않는 코드를 명확한 표로 대비하여 설명한다. 원문에 정리된 보호 여부의 대조 결과는 아래 표와 같다.

구문 형태 C++26 보호 여부 원문 판정 근거 및 사유
while (true); 보호됨 제어식이 상수식 true이고 본문이 단독 세미콜론으로 비어 있음
for (;;); 보호됨 제어식이 생략되어 true로 간주되며 본문이 완전히 비어 있음
do {} while (true); 보호됨 루프 본문 블록이 빈 중괄호이고 제어식이 상수식 true임
constexpr bool go = true; while (go); 보호됨 constexpr 변수는 컴파일 시점 상수식으로 true 평가되며 본문이 비어 있음
while (true) { "a string"; } 보호 안 됨 부작용 없는 문자열 리터럴이라도 본문이 비어 있지 않으므로 자격 박탈
while (true) if (done) break; 보호 안 됨 조건문 분기 문장이 본문에 포함되어 완전히 비어 있지 않음
while (true) if constexpr (false) break; 보호 안 됨 문법적으로 if constexpr 문장이 본문에 존재하여 빈 본문 요건 미충족
bool done = false; while (!done); 보호 안 됨 조건식이 컴파일 시점 상수식이 아니므로 단순 무한 루프 요건 미충족

위 대조 결과에서 확인되듯, C++26의 보호를 받는 구문은 형태적으로 극히 단출하다. 원문이 강조하는 보호 구문의 특징과 주의점은 다음과 같이 정리된다.

  • while (true);, for (;;);, do {} while (true);라는 표준적인 세 가지 빈 루프 구문은 모두 보호 대상이다.
  • 조건 변수를 외부에서 선언하더라도 constexpr 한정자가 붙어 컴파일 타임에 true로 확정되면 보호 대상에 포함된다.
  • 본문 안에 "a string";과 같은 문장을 단 하나라도 넣는 순간 단순 루프 자격을 잃고 미정의 동작이 된다.
  • 런타임 변수의 참/거짓 여부에 의존하는 루프(while (!done);)는 본문이 비어 있더라도 보호되지 않는다.

이 글의 해석으로는, 표에서 while (!done);이 보호 안 됨으로 분류된 것처럼, 본문이 비어 있더라도 조건식이 [intro.progress]에 명시된 volatile 접근이나 동기화 연산, 원자적 연산을 수반하지 않는 일반 변수라면 컴파일러 최적화로부터 보호받지 못한다.

6. 결함 보고(Defect Report) 채택과 이전 C++ 표준으로의 소급 적용

원문은 P2809R3 제안의 적용 범위와 관련하여 실무적으로 대단히 중요한 사실을 전한다. 원문은 언급된 제안이 표준위원회의 결함 보고(defect report)로 공식 승인되었다고 적는다(「The mentioned proposal was also accepted as a defect report, so implementations may apply the fix to earlier C++ modes as well.」).

원문에 따르면, 결함 보고로 승인되었기 때문에 컴파일러 구현체들은 이 수정을 C++26 모드뿐만 아니라 이전 C++ 모드(earlier C++ modes)에 대해서도 동일하게 소급 적용할 수 있다. 따라서 최신 버전의 컴파일러를 사용하는 환경이라면, 프로젝트의 빌드 플래그가 이전 표준 모드로 설정되어 있더라도 단순 무한 루프가 최적화로 제거되는 과거의 이상 동작이 더 이상 재현되지 않을 수 있다. 표준 규정의 역사적 변화와 소급 적용 관계는 아래 표와 같다.

표준 구분 진행 보장 규정 상태 단순 무한 루프(while (true);) 취급
C++11 이후(진행 보장 규칙 도입 이후) [intro.progress] 진행 보장 가정 적용 부작용 없는 루프는 미정의 동작(UB)으로 컴파일러 제거 허용

이전 C++ 모드 (소급) 결함 보고(Defect Report) 반영 구현체 재량에 따라 이전 C++ 모드 빌드 시에도 루프 제거 억제

결함 보고 채택이 개발 생태계에 미치는 실질적인 영향은 다음과 같다.

  • 이전 C++ 모드로 컴파일하더라도 컴파일러 도구 체인이 최신화되어 있다면 단순 무한 루프가 보존될 가능성이 열렸다.
  • 원문이 명시했듯 구현체가 이 수정을 이전 모드에 적용할 수 있는 재량을 가지므로 도구별 적용 여부는 구현체에 달려 있다.
  • 기존 레거시 코드베이스에서 while (true); 구문을 사용하던 프로젝트가 이전 언어 모드에서도 혜택을 볼 수 있다.
  • 이 글의 해석으로는, 구현체가 이전 C++ 모드에서도 단순 무한 루프를 보존할 수 있는 근거가 마련된 것이 결함 보고 채택의 실질적인 의미다.

원문은 구현체에 따라 이전 언어 모드에서도 이 수정을 적용할 수 있다는 점을 명시함으로써, 개발자가 사용하는 컴파일러의 동작 방식을 직접 확인할 필요가 있음을 시사한다.

7. 임베디드 halt-on-error 패턴과 자립형 구현의 yield 우려

원문은 단순 무한 루프가 사용되는 대표적인 사례로 임베디드 시스템과 운영체제 커널의 'halt-on-error 패턴'을 든다. 원문의 설명에 따르면, 운영체제가 없어 종료할 곳이 없을 때 프로그램은 그냥 멈춘다(원문: 「there's no operating system to exit to, you simply stop」). 원문은 이러한 상황의 예시로 하드웨어 초기화 실패(`hardware_init_failed()`)를 언급하며, 치명적 오류 후 시스템을 정지시키기 위해 빈 무한 루프를 사용한다고 적는다.

원문은 만약 컴파일러가 이 무한 루프를 제거한다면 프로그램이 의도한 정지 상태를 유지하지 못하고 루프 바깥으로 빠져나오게 된다고 설명한다. 원문은 P2809R3이 이러한 시스템 프로그래밍의 요구를 수용하여 빈 루프를 보존하도록 만든 것이라고 짚는다.

원문은 자립형(freestanding) 환경에서 표준이 정한 대체 방식에 대해 우려를 적는다. 표준 제안은 단순 무한 루프가 진행 보장 규칙을 위반하지 않도록 만들기 위해, 해당 루프를 의미론적으로 std::this_thread::yield() 호출로 대체하는 방식을 채택했다. 원문은 자립형 구현 환경에 대해 다음과 같은 단서가 붙어 있다고 적는다(「it is implementation-defined whether the replacement with `std::this_thread::yield()` occurs at all」). 즉, 자립형 환경에서 이 대체가 실제로 일어날지 여부는 구현 정의(implementation-defined) 사항이다.

원문은 의도적인 정지 루프를 협력적 양보로 바꾸는 것이 프로그래머가 전혀 의도하지 않은 동작을 유발할 수 있다는 우려를 적는다(「turning a deliberate halt loop into a cooperative yield could introduce behaviour the programmer never intended」). 자립형 환경과 관련하여 원문이 짚은 사항은 다음과 같다.

  • 자립형 구현에서는 std::this_thread::yield()로의 대체가 실제로 일어날지 여부가 구현 정의(implementation-defined) 사항이다.
  • 의도적인 정지(halt) 루프를 협력적 양보(yield)로 바꾸는 것은 프로그래머가 전혀 의도하지 않은 동작을 유발할 수 있다.
  • 원문은 협력적 양보가 유발할 수 있는 구체적인 오작동 시나리오는 적지 않는다.
  • 이 글의 해석으로는, 자립형 환경에서 구현 정의로 남겨진 yield 대체 여부를 플랫폼별로 점검하는 것이 실무적으로 필요하다.

원문은 이러한 우려를 바탕으로 자립형 시스템에서 단순 무한 루프를 다룰 때 컴파일러의 구현 정의 동작에 주의를 기울여야 한다고 설명한다.

8. C11과의 비교 및 C++ 표준위원회의 선택

원문은 무한 루프의 미정의 동작 문제를 해결하는 과정에서 인접 언어인 C 언어의 역사적 결정을 비교 대상으로 조명한다. 원문은 C 언어가 이 문제를 올바르게 처리했다는 취지로 「C got this right」라고 평가한다. ISO C 표준 위원회는 이미 C11 개정 당시 진행 보장 규칙을 도입하면서, 조건식이 상수식인 무한 루프에 대해서는 진행 보장 가정의 예외를 명시적으로 규정해 컴파일러가 함부로 삭제하지 못하도록 보호했다.

원문은 C++ 표준위원회 내부에서도 C11이 택한 해결 방식을 그대로 C++에 가져오는 방안이 검토되었으나 최종적으로 기각되었다고 적는다(「considered and rejected」). C11의 방식을 그대로 수용할 경우, 조건식만 상수라면 본문에 코드가 포함되어 있더라도 루프를 미정의 동작으로 취급할 수 없게 된다. 원문의 설명에 따르면, 이는 C++ 컴파일러가 자랑하는 고도화된 최적화기에 지나치게 넓은 제약(optimizer constraints)을 부과할 위험이 있었기 때문에 거부되었다.

결과적으로 C++ 위원회는 C11보다 훨씬 좁고 까다로운 타협안을 선택했다. 루프 제어식이 상수식 true여야 할 뿐만 아니라, 루프 본문이 세미콜론이나 빈 블록으로 완전히 비어 있어야 한다는 추가 족쇄를 채운 것이다. C 언어와의 비교 및 C++ 표준의 설계 선택을 정리하면 다음과 같다.

  • C11은 상수 조건식을 가진 무한 루프 전반을 진행 보장의 예외로 인정하여 비교적 폭넓게 보호했다.
  • C++ 위원회는 C11의 규칙을 그대로 들여올 경우 최적화기의 루프 분석 기능이 과도하게 제약된다고 판단하여 기각했다.
  • C++26은 루프 본문이 완전히 비어 있어야 한다는 강력한 제약을 추가함으로써 최적화기 손실을 최소화하는 좁은 길을 택했다.
  • 이 글의 해석으로는, C++이 최적화 성능을 보존하기 위해 C11보다 훨씬 좁은 빈 본문 규칙을 택한 것이다.

원문은 C와 C++이 서로 다른 방식으로 무한 루프를 정의하고 있으며, C++26의 개정 역시 C11의 전면적 보호와는 구별되는 독자적인 타협안임을 강조한다.

9. 확인하지 못한 것

원문의 서술 범위를 넘어서는 구체적인 사실들에 대해, 원문에 기재되지 않아 확인하지 못한 항목들을 사유와 함께 아래에 정리한다.

  • 특정 컴파일러 릴리스 버전 번호(예: Clang 또는 GCC의 몇 번째 버전부터 결함 보고에 따른 소급 적용 패치가 공식 릴리스에 포함되었는지)는 원문에 구체적인 버전 숫자가 기재되어 있지 않아 확인하지 못했다. (사유: 원문이 개별 벤더의 버전 번호를 명시하지 않고 구현체 일반으로만 설명함)
  • 단순 무한 루프가 컴파일러에 의해 std::this_thread::yield() 호출로 대체될 때 발생하는 실행 시간 오버헤드나 CPU 클록 소모량에 관한 구체적인 정량적 벤치마크 수치는 원문에 언급되지 않아 확인하지 못했다. (사유: 원문이 성능 측정 수치나 벤치마크 데이터를 제공하지 않음)
  • P2809R3 제안서 본문과 원문에서 언급된 [intro.progress] 이외에, 이 변경과 연계된 표준 문서 내의 추가적인 세부 조문 번호나 위원회 회의록의 찬반 표결 통계는 원문에 기재되지 않아 확인하지 못했다. (사유: 원문이 표준 제정 내부 표결 통계 및 파생 조문 번호를 다루지 않음)
  • 임베디드 및 운영체제 커널의 실제 대규모 오픈소스 코드베이스에서 이 규칙 개정으로 인해 직접적인 패치가 이루어졌거나 버그가 예방된 실제 적용 사례 통계는 원문에 나오지 않아 확인하지 못했다. (사유: 원문이 산업계 전수 조사 통계를 포함하지 않음)
