減点74から3へ、語彙34パーセント減 - そして、これを全文書に適用してはいけない理由

2026-08-01 IT/技術

序論: 同じ文を二人が逆に理解した

手順書にこういう一文があったとする。「カバーを取り外す前にケーブルが取り外されていなければならない」。一人はケーブルを先に抜き、もう一人はカバーを先に開けた。二人ともその文を読み、二人とも自分は正しく読んだと思っていた。文が間違っていたのではない。その文は二通りに読まれることが許された文だっただけである。

こうした事故が起きると、たいてい出てくる処方は「文書をもっと詳しく書こう」だ。ところが詳しく書くほど文は長くなり、長くなるほど分岐する箇所が増える。別方向の処方がある。使える単語と文構造をあらかじめ削ってしまうことだ。分かれる余地のある表現を最初から使えなくする。これを統制された言語という。

この記事はその方式を扱うが、「やさしい英語で書こう」という話はしない。代わりに二つのことをする。

  • チェッカーを自作して数字で測る。同じ手順の段落を統制の前後で入れ、文の長さ、受動態の比率、曖昧語、用語の揺れの数を比べた。減点74が3に落ち、意外にも全体の語数は40パーセント減った
  • 適用してはいけない場所を同じチェッカーで証明する。よく書かれた概念説明の段落を入れたら、文の60パーセントが規則違反になった。それは悪文ではなく目的の異なる文章である

実行環境。以下の数字はすべて Windows 10 Pro (10.0.19045) の Node.js v22.16.0 (win32) で自作のチェッカーを実行して得たものである。外部ライブラリは使っていない。チェッカーの全コードは3節にあり、そのままコピーして走らせられる。

規格の本文は開いていない。この分野の代表格である ASD-STE100 は、公式サイトの申請フォームを通じて PDF で配布される。私は公式サイトの概要ページと FAQ、それに公開されている解説ページまでを確認し、規格の本文は読んでいない。したがってこの記事には53個の規則の全一覧も、承認語彙900語の中身もない。以下で引く数値と規則は公式サイトと公開解説が述べている範囲であり、本文に出てくる具体的な検査規則は私が作ったチェッカーの規則であって規格の規則ではない。

この記事の例文はすべて架空である。登場する装置、手順、文書は実在しない。文書のフォーマットそのものの問題はAI時代の韓国文書フォーマットで扱った。この記事はフォーマットではなく文を扱う。

1. 統制された言語とは何か

統制された言語は文体指針ではない。文体指針は「なるべく能動態を使いましょう」と勧め、統制された言語は受動態をそもそも使えなくする。勧告と禁止の差ではなく、選択肢がある状態とない状態の差である。

最もよく知られた事例は航空機の整備文書から出てきた。公式サイトの説明によれば背景はこうだ。複雑な技術指示は誤解されうるし、誤解は事故につながりうる。そこで欧州の航空会社が要請し、1980年代に規格が作られた。確認した範囲でこの規格の構成は次のとおりである。

  • 作成規則53個が9つの節に分かれている。文法と文体を扱う
  • 承認語彙は約900語。各語は原則として意味ひとつ、品詞ひとつだけを持つ
  • 非承認語彙は約1,200語が代替語とともに一覧で示される。広く引かれる例が、start は承認され begin と commence は承認されないというものだ
  • 現行版は Issue 9 (2025年1月) で、維持管理は1983年に作られた専任グループが担う
  • 航空から出発したが、陸上・海上の車両、再生可能エネルギー、医療機器の分野でも使われていると公式 FAQ が述べている

見落としやすい点がひとつある。承認語彙900語はすべてではない。公式 FAQ は、各産業の技術名詞と技術動詞は別に使えると明記している。図面、公式文書、社内用語集から出てきた用語であれば承認一覧の外の語でもよい、という意味だ。つまり統制された言語は語彙を900語に閉じ込めるのではなく、「一般語彙は900語で固定し、専門用語は根拠のある一覧でのみ増やす」という構造である。この区別を知らずに導入すると、最初の一週間で「この語が使えない」という不満で崩れる。

規則53個を全部見る必要はない。実務で事故を起こすのはたいてい四つか五つだ。重要なのはそれぞれがどんな種類の誤解を生むかである。

2.1 受動態が危険な本当の理由

受動態を禁じる理由が「不自然だから」だと思っているなら半分しか当たっていない。同じ指示を三通りに書いて並べると問題が見えてくる。

--- 同じ指示、三通りの表現 ---
(1) The cable must be disconnected before the cover is removed.
(2) Disconnect the cable. Then remove the cover.
(3) Remove the cover after disconnecting the cable.

                        (1)          (2)            (3)
誰がやるのか             記載なし     読む人         記載なし
何が先か                 ケーブル     ケーブル       ケーブル
読む順序と作業順序       逆           一致           逆
一文に入った指示の数     2個          1個            2個
must が誰にかかるか      不明確       不要           不明確
  • (1) と (3) は読む順序と作業順序が逆である。急いでいる場面で前から読んで行動すると順序が入れ替わる。(2) だけが読んだとおりにやればよい
  • (1) の must は誰に対する義務なのかを言わない。作業者なのか設計なのかソフトウェアなのか、文の中に根拠がない
  • (3) の after disconnecting は文法的に瑕疵がないが、動名詞は時間関係と条件の両方を意味しうる。「外したあとで」なのか「外した場合にのみ」なのかで割れる
  • 受動態禁止の実効は文体ではなく、行為者を必ず書かせることにある。命令文で書けば行為者は自動的に読む人になる

3. チェッカーを作って測った - 何をどう数えるか

規則を言葉で説明することと、その規則が実際に文書をどれだけ変えるかは別の問題だ。そこでチェッカーを作った。どの規格も実装していない。統制規則が縛る四つ、すなわち文の長さ・受動態・曖昧な指示・用語の一貫性だけを数える。

// ste_check.js — Node 22, 依存なし。 実行: node ste_check.js doc.txt proc
const LIM = { proc: 20, desc: 25 }, PARA = 6, NOUN = 3;

const PASSIVE = /\b(?:is|are|was|were|be|been|being)\s+(?:not\s+|often\s+|normally\s+)?([a-z]+(?:ed|en)|done|set|put|kept|sent|made)\b/gi;

const VAGUE = ['as required', 'if necessary', 'as appropriate', 'properly', 'correctly',
  'regularly', 'periodically', 'normally', 'usually', 'typically', 'should', 'may',
  'might', 'could', 'various', 'relevant'];

// ひと組 = ひとつの概念。文書全体で一語だけで表されなければならない
const SYN = {
  start:  ['start', 'begin', 'commence', 'initiate', 'launch'],
  stop:   ['stop', 'halt', 'cease', 'terminate', 'abort'],
  check:  ['check', 'verify', 'confirm', 'validate', 'ensure', 'make sure'],
  remove: ['remove', 'detach', 'disconnect', 'unplug'],
  fix:    ['fix', 'repair', 'correct', 'rectify']
};

核心は次の三つの関数だ。語形変化の処理を落とすとチェッカーは静かに失敗する。最初に作ったとき commence に ed を付けて commenceed を探していて、同義語の混用が明らかな段落で違反0を返した。チェッカーが0を返したとき、文書がきれいなのではない。チェッカーが壊れているのかもしれない。

// 語形変化 — commence で commenced まで拾うには必ず要る
const forms = v => { const o = new Set([v, v + 's', v + 'ed', v + 'ing']);
  if (v.endsWith('e')) o.add(v + 'd');
  if (v.endsWith('y')) o.add(v.slice(0, -1) + 'ied'); return [...o]; };

// 文の分割 — ピリオドの次が大文字か数字のときだけ切る
const sents = t => t.replace(/\s+/g, ' ').trim()
  .split(/(?<=[.!?:])\s+(?=[A-Z0-9(])/).filter(Boolean);

// 名詞の塊 — 句読点、機能語、数字で切る
function runs(s) { const out = [];
  for (const c of s.split(/[,;:.()]+/)) { let cur = [];
    for (const t of c.split(/\s+/).filter(Boolean)) {
      const l = t.toLowerCase().replace(/[^a-z0-9]/g, '');
      if (!l || /\d/.test(l) || STOP.has(l) || /(?:ed|ing|ly)$/.test(l)) {
        if (cur.length > NOUN) out.push(cur.join(' ')); cur = [];
      } else cur.push(t); }
    if (cur.length > NOUN) out.push(cur.join(' ')); }
  return out; }

// 減点 — 重みは恣意的だ。絶対値ではなく同じ文書の前後比較にだけ使う
score: over * 3 + passive * 2 + vague.length + pron + varied.length * 3
     + clusters.length * 2 + longP * 2

over上限を超えた文の数指示文20語 / 説明文25語文の分割をピリオドに頼る。略語のピリオドで誤って切りうる

pronit, they, them の出現数0形式主語の it と指示代名詞を区別しない
vague曖昧語リストとの一致0リストがすべて。リストにない曖昧語は拾えない
synVarひとつの概念に二語以上使った組の数0過検出が最もひどい指標。4.1節で実際の誤検出を示す

  • 減点の絶対値に意味はない。重みは私が決めたものだ。使いどころがあるのは同じ文書を直す前後で比べた変化量だけである
  • 指標をひとつにまとめず七つを別々に見せるようにした。合計だけ見てもどの規則が問題なのか分からず、直しようがない
  • proc と desc の二つのモードを置いた理由は、手順書と説明書に同じ上限を当ててはいけないからだ。この区別が8節の結論の技術的根拠になる
  • 200行に満たないコードでも文書品質の議論を数字の上に移せる。これが道具の唯一だが決定的な値打ちである

4.1 チェッカーが間違えた箇所 - 誤検出をまず認めること

統制後の段落 B にも違反がひとつ残った。ところがこれは文書の欠陥ではなく私のチェッカーの欠陥である。

  B still flags: ["remove"]
  A flags       : ["start","check","remove"]

  B の本文で引っかかった二語
    "Disconnect the redundant supply cable."   -> disconnect
    "remove the power. Then start the unit."   -> remove

  私の SYN 定義:  remove: ['remove', 'detach', 'disconnect', 'unplug']
  実際の規格では: remove と disconnect は意味の異なる別々の承認語彙である
                  (ケーブルを「抜く」ことと部品を「取り外す」ことは別の作業)
  • 私の同義語グループが異なる概念をひと組に入れてしまった。実際の統制語彙では disconnect と remove はそれぞれ別の意味で承認された別々の語である
  • 教訓はこれだ。チェッカーが違反を報告したら、文書より先にチェッカーを疑え。とくに同義語の規則は社内用語集で定義すべきで、他人の一覧をそのまま持ってくるとこの種の誤検出があふれる
  • 逆方向の失敗もあった。3節に書いたとおり語形変化を落とした初期版は A の段落で用語の揺れ0を返した。明らかな混用がある段落をきれいだと報告したのだ。チェッカーの0は証拠ではない

5. 翻訳が楽になる - 語彙34パーセント減の意味

統制された言語の導入根拠として最もよく引かれるのが翻訳だ。公式 FAQ も原文の変異が減るから翻訳が容易になると書いている。この文を数字に移すと4節の distinct 列になる。107語から71語。同じ内容を移すのに翻訳者が判断すべき異なる表現が三分の一減った。

  • 翻訳の単価は分量より変異に左右される。翻訳メモリは以前に訳した文とどれだけ似ているかで値を付ける。文型が反復されれば完全一致と近似一致の比率が上がり、新しく訳す分が減る
  • 機械翻訳が間違える三つが統制で消える。長い文で修飾語を別の名詞に付ける誤り、受動態で行為者を捏造する誤り、代名詞を誤ってつなげる誤りだ。三つとも文が短く能動態で代名詞がなければ起きる場所がない
  • 用語の一貫性は翻訳で倍に効く。原文で start と commence を混ぜて使えば、翻訳者は「意味が違うから書き分けたのだろう」と判断して別々の訳語を選ぶ。原文の無意味な揺れが訳文では意味のある差として固まる
  • ただしこの利点は原文を規則どおりに書いた対価である。翻訳エンジンを替えたり後処理を足して得られるものではない。コストは原文の書き手が払う

ここで正直であるべき点がひとつある。公式 FAQ は、規格に対応すると称する自動ツールを認証も推奨もしないと明記している。どんな道具も規格そのものの代わりにはならない、ということだ。私が作ったチェッカーも同じである。これは規則を測る物差しであって規則ではない。

錯覚しやすい点。「統制された言語を導入すれば翻訳費が減る」という結論は多言語で出す文書に限って成り立つ。国内だけで使う日本語の手順書にこの論理をそのまま持ち込むと根拠がない。その場合の利点は翻訳費ではなく誤読の減少であり、それは事故記録でしか証明できない。導入を説得するとき、自分の組織に当てはまらない根拠を借りてくると最初の反論で崩れる。

--- E. 同じ内容、統制規則を適用 ---
Do the inspection. Set the power switch to OFF. Disconnect the cable.
Install the new part. Make sure that the new part is tight.

  sents 5 / words 24 / avg 4.8 / max 8 / over 0 / passive 0 / cluster 0 / score 0
韓国語の習慣英語で起きることチェッカーでの現れ方直す場所
主語の省略行為者を埋める根拠がなく受動態になるpassive が増える翻訳ではなく韓国語の原文に主体を書く
助詞の省略格関係が消えて名詞の羅列になるcluster が増える述語を復活させて句を節にする
名詞の羅列四語の名詞句になり修飾関係が多義になるcluster が増える動詞でほどく。of の連鎖より動詞がよい
連結語尾でつなぐ一文に指示が複数入るover と平均長が増える指示ひとつに文ひとつで切る
体言止めに近い終止義務か推奨かが英語で割れるvague の should必須は命令文、条件付きは if 節で明示
  • D の26語は一文である。韓国語の原文が一文だったからだ。翻訳者が文を割る権限はないと考えると、原文の構造がそのまま渡る
  • cable separation work progress は英語として意味が成立しない。ところが韓国語のほうは自然に読める。原文では見えなかった欠陥が翻訳で露見する典型である
  • E は D より語数がむしろ少ない(24対26)。名詞で固めたものを動詞でほどくと長くなりそうだが、is required や must be performed by のような包装が消えるからだ
  • 実務では順序をひっくり返すのが要点だ。英語の翻訳品質を上げたいなら翻訳段階ではなく韓国語の作成段階を直す。原文に「一文一指示、主語明示、助詞の省略禁止」を掛けるだけで英語側の指標が下がる
  • 逆に韓国語の原文に英語式の統制規則をそのまま当ててはいけない。20語の上限のような数値は英語の基準であり、韓国語は文節数と文の成分で別に定めなければならない

7. 自動強制の代償 - よい文章も減点される

ここがこの記事で最も重要な実験だ。よく書かれた概念説明の段落を同じチェッカーに入れた。わざと悪く書いた文章ではなく、読む人を説得しようと丁寧に書いた種類の文章である。

--- C. 概念説明の段落 (説明文モード、上限25語) ---
Controlled language is often misunderstood as a style guide, but it is closer to a
contract between the writer and every reader who will ever open the document. When you
accept that contract, you give up a great deal: the rhythm you would use to keep a
reader interested, the aside that explains why a decision was made, and the well-placed
metaphor that makes an unfamiliar mechanism suddenly obvious. What you get in return is
narrow and valuable. Two people who read the same sentence in different rooms, in
different years, with different amounts of English, will act on it the same way.

  sents 5 / words 143 / avg 28.6 / max 42
  over 3  (全文の60%が上限超過)
  passive 3   pron 3   vague 0   synVar 0   cluster 0
  score 18       (B 統制された手順書の3より6倍)

この段落は直す必要がない。規則を破った部分こそがこの文章のしていることだからだ。「契約」という比喩、コロンのあとに三つを並べる構造、最後の文の長い呼吸は読者を説得するための装置である。これを20語に切れば意味は残り説得力が消える。

  • 強制モードを全文書に掛けると、こういう文章が CI で止まる。すると書き手は二つのうちどちらかをする。規則を回避しようと文を機械的に切るか、チェッカーを切ってしまうかだ。どちらも道具を無意味にする
  • 受動態3か所のうち a decision was made は行為者を隠すのが意図である。誰が決めたかが要点ではないからだ。手順書では欠陥であるものが説明文では機能になる
  • it 3個も同じだ。説明文で代名詞は前の文とのつながりを作る。それをすべて名詞に戻すと段落が箇条書きのように読める
  • だからチェッカーはディレクトリ単位でのみ有効にすべきだ。規則の強さは文書の種類が決めるものであって、組織全体にひとつの値を掛ける問題ではない

8. どこに使い、どこに使わないか

判断基準はひとつに縮められる。誤読の代償は何か。代償が機材や人であれば適用し、代償が「もう一度読むこと」であれば適用しない。

文書の種類適用モード理由
作業手順書・整備指示強制proc (20語)順序が入れ替わると事故になる。読む順序が作業順序でなければならない
警告文・安全表示強制proc (より厳しく)急いでいる場面で一度で読まれる。条件節が付いてはいけない
設置・配備ランブック強制proc初めて見る人が深夜にそのままなぞる
API リファレンス (引数・エラー説明)強制proc機械翻訳と検索要約にそのまま露出する。項目ごとに文型がそろっていなければならない
UI 文言・エラーメッセージ強制proc翻訳対象でありながら画面幅の制約もある。変異がそのままコスト
規程・契約条項部分適用proc、語彙のみ用語の一貫性は必須だが、法的表現をむやみに短く切れない
リリースノート警告のみdesc変更の要約は短いほどよいが、背景説明まで切ると役に立たない
概念説明・アーキテクチャ文書適用しない-7節の実験を参照。規則を破る部分こそがこの文章の機能である
チュートリアル・オンボーディング文書適用しない-文脈と動機が半分だ。命令文だけ残すと途中で投げ出す
設計判断記録・事後分析適用しない-「なぜそうしたか」が本文だ。統制規則にその場所がない
  • 表の上の五行には共通点がある。読者が文書を読みながら同時に手を動かす。下の三行は読者が読むだけだ。この区別が実務で最もよく合う境界線である
  • 「部分適用」と「警告のみ」を別に置いた理由がある。全部か無かで行くと導入が失敗する。語彙の一貫性だけ強制して文の長さは緩めておく組み合わせが、現実には最も長く続く
  • ひとつのリポジトリの中でパスで分けるのが最もきれいだ。手順書のディレクトリにだけフックを掛け、残りにはチェッカーをそもそも走らせない
  • 同じ製品文書の中でも一ページに二種類が混ざっているなら、手順の部分だけ別ファイルに切り出すほうがよい。そうしてはじめて規則をファイル単位で掛けられる

9. 導入の手順 - 用語集、警告モード、強制モード

順序を間違えると必ず失敗する。チェッカーから点けることが最もよくある失敗だ。誰も合意していない規則で他人の文章に減点を付ける道具は、導入の最初の一週間で切られる。

段階やること終わったと言える条件失敗の兆候
1. 用語集既存の文書から同じ概念を指す表現を集め、ひとつだけ残す上位30概念について代表語と禁止語が決まった一覧が他人のものの写しだ。4.1節の誤検出があふれる
2. 範囲の決定8節の表でディレクトリを分ける。適用しない場所を先に決めるパスの規則が設定ファイルに書かれている「とりあえず全体に掛けてあとで外す」で始める
3. 警告モード減点だけ出してビルドは通す。最低4週間既存文書の減点の分布を知っている分布を測らずに閾値を決める
4. 閾値の決定分布の中央値付近から始めて四半期ごとに下げる既存文書の半分以上が通る理想的な値を先に決めて全部落とす
5. 強制モード手順書のパスに限ってビルドを止める新しい文書が直った状態で上がってくる回避コメントが増える。規則のほうが間違っている
6. 維持誤検出の報告を受けて規則を直す四半期ごとに用語集が更新される報告を受けて文書を直せと言う

9.1 警告モードから強制モードへ

フックは単純なほど長く続く。パスでモードを分け、閾値はひとつだけ置く。

# 手順書のパス — 強制。閾値を超えたらビルドを止める
for f in docs/procedures/*.md; do
  node ste_check.js "$f" proc | tee -a report.txt
done
node ste_gate.js report.txt --max-score=10 || exit 1

# 説明文書のパス — 警告のみ。ビルドは止めない
for f in docs/concepts/*.md; do
  node ste_check.js "$f" desc
done

# 適用しないパスはそもそも実行しない
#   docs/tutorials/  docs/adr/  docs/postmortems/
  • 閾値は文書ひとつを基準に取る。リポジトリ全体の合計で取ると、文書が増えるたびにひとりでに失敗する
  • 回避手段を必ず作っておく。特定の段落を検査から外すコメントを許し、そのコメントが何個使われたかを数えること。増えるなら文書ではなく規則のほうが間違っている
  • 新しい文書にだけ強制し、既存の文書は触れたついでに直させる。全数改訂を先に求めると導入そのものが立ち消える
  • 成否は道具ではなく1段階の用語集で決まる。チェッカーは用語集を強制する手段にすぎず、用語集がなければ強制するものもない

10. 点検リストとやってはいけないこと

導入を検討するなら、以下の項目で自分の組織の状態をまず確認するほうがよい。

  • 適用しない文書の種類を先に一覧にした
  • 用語集の代表語が他人の一覧ではなく自分たちの文書から出てきた
  • 手順書と説明書に異なる上限を適用する
  • チェッカーの指標が合計ひとつではなく項目別に見える
  • 警告モードで4週間以上回して既存文書の分布を測った
  • 閾値で既存文書の半分以上が通る
  • 誤検出の報告経路があり、報告が来たら規則を直す
  • 多言語で出さない文書に翻訳費の節減を根拠として使わなかった
  • 原文の規則と英語の規則を別々に定義した
  • チェッカーが違反0を報告したときチェッカーをまず疑ってみた

10.1 やってはいけないこと

  • 全リポジトリに強制モードから点けること — 概念説明の文書が止まり、人はチェッカーを切る
  • 他人の同義語一覧をそのまま持ってくること — 4.1節の remove と disconnect のように別の概念がひと組に入る
  • 減点の絶対値で文書を評価すること — 重みは恣意的だ。使えるのは同じ文書の前後比較だけである
  • 英語の上限を他言語の文書にそのまま当てること — 20語は英語の基準だ
  • 翻訳品質の問題を翻訳段階で直そうとすること — 6節の名詞の塊は原文で作られたものだ
  • 規格の本文を読まずに規則をでっち上げること — この記事も本文を開いておらず、だから53個の規則の一覧を書いていない
  • チュートリアルと事後分析に統制規則を掛けること — 「なぜ」を書く場所が規則の中にない

結論は最初の場面に戻る。カバーとケーブルの順序を二人が違うように読んだのは文書が読みにくかったからではなく、二通りに読まれることが許されていたからだ。統制された言語がすることは文書をやさしくすることではなく解釈の幅をなくすことである。だから基準はひとつだ。この文書の目的は「読まれること」なのか、「同じ意味で読まれること」なのか。前者なら統制するな、後者なら統制せよ。すべての文書に適用するものではない。

# 統制された言語の導入 — 文の規則表 · チェッカー · 判断表 · 点検リスト

> 出典: braindetox.kr — 技術文書を統制された言語で書かせると何が変わるか
> 根拠: Windows 10 Pro / Node.js v22.16.0 で以下のチェッカーを実行した結果
> ⚠ 規格の本文 PDF は開いていない。以下の規則は公開説明の範囲と自前の実験から出たもので、
>   53個の規則の全一覧と承認語彙の一覧はここにない。

## 0. 大前提

**文書の目的が「読まれること」なら統制するな、「同じ意味で読まれること」なら統制せよ。**
すべての文書に適用するものではない。

## 1. 文の規則表

| 規則 | 値 | なぜ |
|---|---|---|
| 指示文 1文 | **20語以下** | 修飾関係が分かれる余地をなくす |
| 説明文 1文 | **25語以下** | 同じ理由、ただし上限を緩める |
| 1段落 | **6文以下** | 1段落1主題 |
| 名詞の羅列 | **3語以下** | 4語から修飾関係が多義になる |
| 1文に入る指示 | **1個** | 順序が入れ替わる事故の最大要因 |
| 受動態 | **禁止** | 行為者が消える |
| 指示のない代名詞 | **禁止** | it, this, that は人ごとに別につなげる |
| ひとつの概念 | **ひとつの語** | start / begin / commence の混用禁止 |
| 曖昧語 | **禁止** | properly, as required, regularly → 数値に |

## 2. チェッカー (Node 22, 依存なし)

```js
// ste_check.js   実行: node ste_check.js doc.txt proc
const LIM = { proc: 20, desc: 25 }, PARA = 6, NOUN = 3;
const PASSIVE = /\b(?:is|are|was|were|be|been|being)\s+(?:not\s+|often\s+|normally\s+)?([a-z]+(?:ed|en)|done|set|put|kept|sent|made)\b/gi;
const VAGUE = ['as required','if necessary','as appropriate','properly','correctly','regularly',
  'periodically','normally','usually','typically','should','may','might','could','various','relevant'];
const SYN = { start:['start','begin','commence','initiate','launch'],
  stop:['stop','halt','cease','terminate','abort'],
  check:['check','verify','confirm','validate','ensure','make sure'],
  remove:['remove','detach','disconnect','unplug'],
  fix:['fix','repair','correct','rectify'] };
const STOP = new Set(('a an the and or but if then of to in on at by for with from into over under is are was were be been ' +
  'being do does did has have had will shall can may must should would could not no this that these those it its they them ' +
  'their you your we our as than so when while after before during until up down out off about again also only very each ' +
  'who which whom whose what where why how all any some both more most other such there here one two three').split(' '));

const forms = v => { const o = new Set([v, v+'s', v+'ed', v+'ing']);
  if (v.endsWith('e')) o.add(v+'d'); if (v.endsWith('y')) o.add(v.slice(0,-1)+'ied'); return [...o]; };
const sents = t => t.replace(/\s+/g,' ').trim().split(/(?<=[.!?:])\s+(?=[A-Z0-9(])/).filter(Boolean);
const wc = s => s.toLowerCase().replace(/[^a-z0-9' ]/g,' ').split(/\s+/).filter(Boolean);

function runs(s) { const out = [];
  for (const c of s.split(/[,;:.()]+/)) { let cur = [];
    for (const t of c.split(/\s+/).filter(Boolean)) {
      const l = t.toLowerCase().replace(/[^a-z0-9]/g,'');
      if (!l || /\d/.test(l) || STOP.has(l) || /(?:ed|ing|ly)$/.test(l)) {
        if (cur.length > NOUN) out.push(cur.join(' ')); cur = [];
      } else cur.push(t); }
    if (cur.length > NOUN) out.push(cur.join(' ')); }
  return out; }

function analyze(text, mode) {
  const lim = LIM[mode || 'proc'], paras = text.trim().split(/\n{2,}/), ss = paras.flatMap(sents);
  const lens = ss.map(s => wc(s).length), total = lens.reduce((a,b) => a+b, 0);
  const low = ' ' + text.toLowerCase().replace(/[^a-z0-9' ]/g,' ').replace(/\s+/g,' ') + ' ';
  const has = w => low.includes(' ' + w + ' ');
  const passive = (text.match(PASSIVE) || []).length;
  const pron = (text.match(/\b(?:it|they|them)\b/gi) || []).length;
  const vague = VAGUE.filter(has);
  const varied = Object.entries(SYN).filter(e => e[1].filter(v => forms(v).some(has)).length > 1).map(e => e[0]);
  const cl = ss.flatMap(runs), over = lens.filter(n => n > lim).length;
  const longP = paras.filter(p => sents(p).length > PARA).length;
  return { sents: ss.length, words: total, distinct: new Set(ss.flatMap(wc)).size,
    avg: +(total/ss.length).toFixed(1), max: Math.max(...lens), over, passive, pron,
    vague: vague.length, varied, clusters: cl.length,
    score: over*3 + passive*2 + vague.length + pron + varied.length*3 + cl.length*2 + longP*2 };
}
module.exports = { analyze };
if (require.main === module) { const fs = require('fs');
  console.log(analyze(fs.readFileSync(process.argv[2], 'utf8'), process.argv[3])); }
```

## 4. 適用対象の判断表

| 文書の種類 | 適用 | モード | 理由 |
|---|---|---|---|
| 作業手順書・整備指示 | **強制** | proc (20語) | 順序が入れ替わると事故 |
| 警告文・安全表示 | **強制** | proc (より厳しく) | 急ぐ場面で一度で読まれる必要 |
| 設置・配備ランブック | **強制** | proc | 初めて見る人がそのままなぞる |
| API リファレンス | **強制** | proc | 機械翻訳・検索要約にそのまま露出 |
| UI 文言・エラーメッセージ | **強制** | proc | 変異がそのまま翻訳コスト |
| 規程・契約条項 | 部分 (語彙のみ) | proc | 法的表現はむやみに切れない |
| リリースノート | 警告のみ | desc | 背景まで切ると役に立たない |
| 概念説明・アーキテクチャ | **適用しない** | — | 規則違反こそが機能 |
| チュートリアル・オンボーディング | **適用しない** | — | 文脈と動機が半分 |
| 設計判断記録・事後分析 | **適用しない** | — | 「なぜ」の場所が規則にない |

**境界線: 読者が読みながら同時に手を動かすか。** そうなら強制、違うなら適用しない。

## 5. 原文の側で先に直すこと

| 習慣 | 英語で起きること | 直し方 |
|---|---|---|
| 主語の省略 | 行為者がなく受動態になる | 原文に主体を書く |
| 助詞の省略 | 名詞の羅列になる | 述語を復活させる |
| 名詞の羅列 | 4語の名詞句、修飾関係が多義 | 動詞でほどく |
| 連結語尾でつなぐ | 一文に指示が複数 | 指示ひとつに文ひとつ |
| 体言止めに近い終止 | 義務か推奨かが割れる | 必須は命令文、条件付きは if 節 |

**翻訳品質は翻訳段階ではなく作成段階で決まる。**

## 6. 導入の点検リスト

- [ ] 適用**しない**文書の種類を**先に**一覧にした
- [ ] 用語集の代表語が他人の一覧ではなく**自分たちの文書**から出てきた
- [ ] 手順書と説明書に**異なる上限**を適用する
- [ ] チェッカーの指標が合計ひとつではなく**項目別**に見える
- [ ] 警告モードで**4週間以上**回して既存文書の分布を測った
- [ ] 閾値で**既存文書の半分以上**が通る
- [ ] 誤検出の報告経路があり、報告が来たら**規則を直す**
- [ ] 多言語で出さない文書に**翻訳費の節減を根拠として使わなかった**
- [ ] 原文の規則と英語の規則を**別々に**定義した
- [ ] チェッカーが違反0を報告したとき**チェッカーをまず疑って**みた

## 7. やってはいけないこと

- ❌ 全リポジトリに**強制モードから**点けること — 人がチェッカーを切る
- ❌ **他人の同義語一覧**をそのまま持ってくること — 別の概念がひと組に入る
- ❌ **減点の絶対値**で文書を評価すること — 重みは恣意的だ
- ❌ 英語の上限(20語)を**他言語の文書**にそのまま当てること
- ❌ 翻訳品質の問題を**翻訳段階で**直そうとすること
- ❌ 規格の本文を読まずに**規則をでっち上げること**
- ❌ チュートリアル・事後分析に統制規則を掛けること — 「なぜ」の場所がない
- ❌ チェッカーの**0を証拠として**受け取ること — 語形変化ひとつ落ちても0が出る
