ロールの受け渡し、信頼ポリシー、リソースポリシー、サービスの代理呼び出しがそれぞれ何をつなぎ、何を見ればその継ぎ目が表に出るのか

2026-09-05 開発・インフラ

クラウドのセキュリティ点検結果が緑で埋まっているのに、どうにも安心できない瞬間がある。項目はすべて通った。バケットは公開ではなく、保存時の暗号化は有効で、セキュリティグループに開いたままのポートもない。それでもアカウント全体が安全だという文にはつながらない。この居心地の悪さは感覚ではなく構造から来ている。

点検項目が見る単位と、危険が発生する単位が違うからだ。項目はリソース一つを見る。危険はリソースとリソースの間で作られる。この二つの単位がずれている限り、項目をいくら増やしてもその間にできた経路はリストに入ってこない。

ここで扱うのはそのずれの構造である。権限が流れうる通路にはいくつかの決まった型があり、型ごとに別の場所を見なければ表に出ない。以下ではその型を四つに分け、型ごとに何が危険を作るのかと何を見ればそれが表に出るのかを対にして整理する。攻撃手順ではなく可視性の問題として扱う。

きっかけ - 通過と安全が同じ言葉でなくなる場所

2026 年 9 月初旬、開発者コミュニティにAWS の設定の間に隠れている攻撃経路を見つけるセキュリティ検証ツールという見出しで、あるオープンソースのリポジトリが紹介された。見出しで引っかかるのは間という語だ。設定の中ではなく、設定と設定の間だと言っている。

この表現はツールの宣伝文句として流すには正確すぎる。クラウド設定点検が抱える構造的な限界がまさにその場所にあるからだ。点検項目はリソースごとに真と偽を付ける。しかし権限はリソースの中に閉じ込められておらず、つながった先へ流れる。流れは項目ではなくグラフの性質である。

ツールの話は記事の後半で事実関係だけを押さえる。前半で扱うのは、ツールがなくても成り立つ問いだ。自分のアカウントで何を点検リストに入れればその間が見えるのか、そしてそのリストがなぜ個々の項目の集合だけでは完成しないのか。

セキュリティがなぜ知識ではなく構造の問題なのかは情報セキュリティはなぜ学びにくいのかで扱い、認証情報そのものを手渡さずに仕事をさせる方法はエージェントに認証情報を渡さずに仕事をさせる方法にある。ここではその二つの軸と重ならないよう、権限がリソースの間を移動する構造だけを見る。

点検項目が見る単位はリソース一つ

クラウド設定の点検ルールを一つ思い浮かべれば形はすぐ見えてくる。ルールはたいていこのリソースのこの属性がこの値かという問いだ。バケットのパブリックアクセスブロックは有効か。データベースのスナップショットは公開扱いになっていないか。ロググループに保持期間は設定されているか。答えは真か偽で、判定に必要な情報はそのリソースの属性の中にすべて入っている。

この形には大きな利点がある。判定が決定的で、ルール同士が独立していて、新しいルールを足しても既存のルールが揺らがない。ルールを一つ書く人は他のルールを知る必要がない。カタログを数千件まで育てられる理由はここにある。

同時にこの形には明確な天井がある。判定に必要な情報が一つのリソースの中に収まっていなければならないという前提だ。ある事実が二つのリソースの属性を同時に見なければ成立しないなら、その事実はこの形のルールでは表現できない。表現できないものは通過も失敗もしない。ただ観測対象ではないだけだ。

ここでよくある誤読が生まれる。項目が失敗しなかったのだからその部分は安全だ、と読んでしまう。実際には失敗しなかったと見ていないが同じ画面に同じ緑で表示される。ダッシュボードは二つの状態を区別して見せてくれない。

危険が生まれる単位 - 関係

権限はリソースの属性ではなく主体とリソースの間の関係である。AWS の文書体系そのものがその点を表している。アイデンティティベースポリシーは主体側に付き、リソースベースポリシーはリソース側に付く。ロールの信頼ポリシーは誰がこのロールになれるかを定める。どれも片側だけ見ても結論は出ない。

AWS ユーザーガイドはロールをアカウントに作成できる特定の許可を持つ IAM アイデンティティと定義しつつ、ユーザーと違って一人に固有に結び付くのではなく、必要とする誰もが引き受けられるよう意図されたものだと記す。ロールにはパスワードやアクセスキーのような標準的な長期認証情報がなく、ロールを引き受けるとロールセッション用の一時的セキュリティ認証情報が提供される。つまりロールはそれ自体が移動する権限の束である。

同じ文書は委任を自分が管理するリソースへのアクセスを許可するために誰かに許可を付与することと定義し、委任には二つのアカウント間の信頼設定が伴うと説明する。リソースを所有する信頼する側のアカウントと、アクセスを必要とするユーザーを持つ信頼される側のアカウントである。信頼する側に作ったロールには二つのポリシーが付く。何ができるかを定める許可ポリシーと、誰が引き受けられるかを定める信頼ポリシーだ。

ここにロールチェーンが加わると関係は鎖になる。文書の定義は簡潔で、ロールを使って二つ目のロールを引き受けることである。あるロールが別のロールを引き受ける許可を持てば、最初のロールの短期認証情報で二つ目のロールを引き受けられる。文書は、チェーンを使うとコンソール、コマンドライン、API のロールセッションが最大 1 時間に制限され、これは個々のロールに設定された最大セッション時間とは無関係に適用されると付け加える。

鎖の各節は個別の項目として見ればすべて正常でありうる。ロール A がロール B を引き受けられるという事実はそれ自体では欠陥ではない。問題になるのは鎖の始点と終点だ。始点が意図より広く開いていて終点が意図より強い権限を握っていれば、途中のすべての節が正常でも結果は意図と異なる。

通路その一 - ロールを渡す動作

一つ目の通路はサービスにロールを渡す動作である。AWS 文書の説明はこう始まる。多くの AWS サービスを構成するには、サービスに IAM ロールを渡さなければならない。こうすることでサービスは後でそのロールを引き受け、利用者に代わってアクションを実行できる。ほとんどのサービスでは設定時に一度渡せばよく、サービスがロールを引き受けるたびに渡す必要はない。

渡すには許可が要る。同じ文書はサービスにロールとその許可を渡すには、利用者にロールを渡す許可がなければならないと記し、その趣旨を承認された利用者だけがロールでサービスを構成できるようにするためと説明する。

この通路の性質を示す警告文が文書にそのまま置かれている。PassRole の許可を設定するときは、利用者に持たせたい以上の許可を持つロールを渡せないようにするべきだというものだ。文書が挙げる例は明快である。ある利用者がストレージ操作を一切実行できなくても、ストレージ操作が許可されたロールをサービスに渡せるなら、そのサービスが利用者に代わってストレージ操作を実行することになる。

ここで関係の性格がはっきりする。利用者の許可ポリシーだけを見ても、ロールの許可ポリシーだけを見ても、この事実は出てこない。二つをつなぎ合わせて初めて出てくる。利用者の実効的な許可が、自分のポリシーではなく自分が渡せるロールのポリシーまで含めて決まるからだ。

渡す対象を絞る装置は文書が併せて案内している。一つはポリシー文のリソース要素で渡せるロールを絞ること、もう一つは条件要素だ。特にiam:PassedToService 条件キーは、ロールを渡せるサービスプリンシパルを指定するのに使う。文書はもう一つの落とし穴も明示的に警告する。ロールにタグを付け、ResourceTag 条件キーで誰がロールを渡せるかを制御しようとしてはならない。この方法は信頼できる結果を生まない。

可視性の観点で最も重要な事実はログ側にある。文書の文はこうだ。PassRole は API 呼び出しではない。PassRole は許可であり、したがって IAM PassRole に対する CloudTrail ログは生成されない。どのロールがどのサービスへ渡されたかを見るには、ロールを受け取った AWS リソースを作成または変更した側の CloudTrail ログを見る必要がある。文書の例に従えば、関数の作成時にロールが渡されるので、作成動作のログに渡されたロールの記録が残る。

この一文がなぜ重要か。監査パイプラインを IAM イベント中心に組んでおくと、この通路は構造的にログに残らない。見るべき場所は IAM ではなくロールを受け取ったサービス側である。

通路その二 - 信頼ポリシーが受け入れる主体

二つ目の通路はロールの入口である。AWS 文書は信頼ポリシーをロールを引き受けることを信頼する主体を定義する JSON ポリシードキュメントと定義し、ロールの信頼ポリシーは IAM のロールに付く必須のリソースベースポリシーであると記す。信頼ポリシーに指定できる主体にはユーザー、ロール、アカウント、サービスが含まれる。

同じ文書はロールを引き受けられる主体も列挙する。同一アカウントまたは別アカウントの IAM ユーザー、同一アカウントの IAM ロール、サービスプリンシパル、そして SAML 2.0 や OpenID Connect と互換のある外部 ID プロバイダーが認証した外部ユーザーである。この最後の項目が信頼ポリシーをアカウント境界を越える文書にする。

文法レベルの制約が一つ文書に明記されている。信頼ポリシーを作成するとき、プリンシパル要素の ARN の一部としてワイルドカードを指定できないというものだ。この制約があるからといって信頼範囲が自動的に狭まるわけではない。アカウント単位の主体や条件のないフェデレーション主体は文法的に完全に有効であり、その場合の信頼の実効範囲はポリシー文法ではなく条件要素が定める。

だから信頼ポリシーで見るべきは主体要素一つではなく主体と条件の対である。主体がアカウントや外部プロバイダーを指すとき、その横に範囲を狭める条件が併記されているかどうかが実際の信頼範囲を決める。条件が空の信頼ポリシーは、文法検査も個別項目の点検もすべて通過しながら、意図したより広い入口として残る。

通路その三 - リソースポリシーがアカウントの外を向くとき

三つ目の通路はリソース側に付くポリシーである。AWS 文書はリソースベースポリシーは、指定されたプリンシパルがそのポリシーの付いたリソースにどうアクセスできるかを制御すると定義する。そしてロールを代理として使わずリソースに直接ポリシーを付けて別アカウントの主体にアクセスを許可できるサービスがあると説明する。

この通路が個別項目の点検をよくすり抜ける理由は、危険を作るのがポリシーの存在ではなくポリシーが指す方向だからだ。ポリシーがあるという事実だけでは真でも偽でもない。その中の主体が自分の信頼領域の内か外かを判定しなければならないが、その判定にはアカウントと組織の範囲という外部の情報が要る。

AWS がこの判定をサービスとして提供しているのが IAM Access Analyzer である。文書は組織とアカウントのリソースのうち外部エンティティと共有されたものを特定するのに役立つと記し、その方式を環境のリソースベースポリシーを論理ベースの推論で分析して外部プリンシパルと共有されたリソースを特定することと説明する。アナライザーを作るときに指定した組織またはアカウントがその信頼ゾーンになり、信頼ゾーン内の主体によるアクセスは信頼済みとみなされる。

運用上知っておくべき但し書きも文書にある。ポリシーを追加または変更すると約 30 分以内に分析され、通知が漏れる稀な場合は次の定期スキャンである 24 時間以内に分析される。そして決定的な制約が一つ太字で書かれている。外部アクセスについて、IAM Access Analyzer は有効化されたリージョンと同じリージョンのリソースに適用されたポリシーのみを分析する。全リージョンを見るにはリージョンごとに外部アクセスアナライザーを作る必要がある。未使用アクセスのアナライザーはリージョンによって結果が変わらないためリージョンごとに作る必要はない、という対比も併記されている。

つまりこの通路の可視性は有効にするだけでは完成しない。どのリージョンにアナライザーがあるかが、そのままどのリージョンが見えるかである。

通路その四 - サービスが利用者に代わって呼ぶとき

四つ目の通路は、主体が人ではなくサービスになる場所だ。AWS 文書はこの状況の問題を混乱した代理と呼び、あるアクションを実行する許可を持たないエンティティが、より高い権限を持つエンティティを強制してそのアクションを実行させるセキュリティ上の問題と定義する。

サービス間の事例の説明が特に正確である。文書は呼び出す側のサービスの AWS サービスプリンシパルが呼び出される側のサービスのリソースにアクセスするとき、呼び出される側のリソースポリシーはその AWS サービスプリンシパルのみを承認し、呼び出す側のサービスを構成した行為者は承認しないと記す。文書が挙げる例では、条件なしに特定のサービスプリンシパルを信頼するストレージは、信頼された管理者が構成したログだけでなく、名前を知っている別アカウントのログも受け取りうる。

アカウント間の事例では外部 ID が装置になる。文書はこれを誰がロールを引き受けられるかを指定するために IAM ロールの信頼ポリシーで使える任意の識別子として紹介し、外部 ID の主な機能は混乱した代理の問題に対処し防ぐことであると明記する。値の管理主体もはっきり書かれている。外部 ID の値はサービス提供者の顧客の間で一意でなければならず、顧客ではなく提供者が管理しなければならない。だからその値は提供者から受け取るものであって自分で考え出すものではない。

{
  "Version": "2012-10-17",
  "Statement": {
    "Effect": "Allow",
    "Principal": { "AWS": "EXAMPLE-PROVIDER-ACCOUNT-ID" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": { "sts:ExternalId": "EXAMPLE-EXTERNAL-ID" }
    }
  }
}

上の形は文書が示すアカウント間の信頼ポリシーの骨格であり、アカウント識別子と外部 ID の位置にはプレースホルダーだけを置いた。ここで見るべきは値ではなく条件要素の有無である。

サービス間の事例の装置は条件キーの側だ。文書はAWS サービスプリンシパルにリソースへのアクセス許可が付与されるすべての箇所で、aws:SourceArn, aws:SourceAccount, aws:SourceOrgID, aws:SourceOrgPaths をリソースポリシーに使うことを推奨すると記す。それぞれの用途も分かれている。特定のリソースに代わって動くときは SourceArn、特定のアカウントに代わるときは SourceAccount、特定の組織に代わるときは SourceOrgID、組織のパス単位では SourceOrgPaths である。

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "EXAMPLE-SERVICE.amazonaws.com" },
      "Action": "EXAMPLE-SERVICE:ExampleAction",
      "Resource": "EXAMPLE-RESOURCE-ARN",
      "Condition": {
        "StringEquals": { "aws:SourceAccount": "EXAMPLE-ACCOUNT-ID" }
      }
    }
  ]
}

同じ制御を組織単位で一度に掛けたいときの手段も文書にある。リソースコントロールポリシーは、個々のリソースベースポリシーに文を追加せずに、組織と組織単位とアカウントにサービス間の混乱した代理の制御を中央から適用させてくれる。ただし文書はサービスコントロールポリシーとリソースコントロールポリシーについて、これらのポリシーだけでは組織の主体とリソースに許可を付与するのに十分ではない。サービスコントロールポリシーとリソースコントロールポリシーはいかなる許可も付与しないと釘を刺す。これらは上限であって許可ではない。

関係の型と可視性の対応表

四つの通路を一つの表にまとめると、型ごとに別の場所を見なければ表に出ないという点が一目で分かる。右の列がこの記事の核心である。危険を作るものとそれを表に出すものが同じリソースの中にない。

関係の型何が危険を作るのか何を見れば表に出るのか
ロールをサービスに渡す動作渡せるロールの許可が渡す側の主体の許可より広いとき、実効的な許可がロール側へ広がるPassRole が掛かるリソース範囲と iam:PassedToService 条件の有無。ログは IAM ではなくロールを受け取ったリソースの作成・変更記録
ロールの信頼ポリシーの入口主体がアカウントや外部プロバイダーを指すのに、範囲を狭める条件が空のとき主体要素と条件要素を一対として読む。アカウント間なら sts:ExternalId 条件の存在有無
ロールがロールを引き受ける鎖始点の信頼範囲と終点の権限の広さが遠く離れているとき。途中の節はそれぞれ正常である引き受け関係を向きのある辺として置き、始点から終点への到達可能性を問う

サービスが利用者に代わって呼ぶリソースポリシーがサービスプリンシパルのみを承認し、そのサービスを構成した行為者は承認しないという非対称サービスプリンシパルを許可する文に aws:SourceArn・aws:SourceAccount・aws:SourceOrgID・aws:SourceOrgPaths が付いているか

表の左二列は設計時点で決まり、右の列は運用時点で確保しなければならないものだ。二つの列の時点が違うことが、この問題を難しくしている実質的な理由である。設計時に作られた関係は残り、それを見る装置は後から別に有効にしなければならない。

実効的な許可は積集合 - ポリシー種別が重なる場所

関係をたどるには実際に通る許可がどう決まるかを知らなければならない。AWS 文書は実効的な許可をユーザーやロールに影響するすべてのポリシーが付与する許可と定義し、アカウント内でエンティティの許可に影響しうるものとしてアイデンティティベースポリシー、リソースベースポリシー、アクセス許可境界、組織のサービスコントロールポリシー、セッションポリシーを挙げる。

規則の骨格は二文である。第一に、これらのポリシー種別のいずれか一つでもあるオペレーションへのアクセスを明示的に拒否すれば、その要求は拒否される。第二に、許可の側は種別の組み合わせで分かれる。アイデンティティベースポリシーとアクセス許可境界の場合、実効的な許可は二つのポリシー種別の積集合であり、組織のサービスコントロールポリシーまで掛かると三つのポリシー種別すべてが許可した場合にのみ要求が許可され、実効的な許可は三種別の積集合になる。セッションポリシーがある場合も同じく三種別の積集合である。

アクセス許可境界の定義は先に引用したとおりだ。アイデンティティベースポリシーが IAM エンティティに付与できる最大の許可を管理ポリシーによって設定する高度な機能であり、エンティティのアクセス許可境界は、アイデンティティベースポリシーとアクセス許可境界の両方が許可するアクションのみ実行できるようにする。そして決定的に権限を制限するだけでそれ自体は権限を提供しない。

ここまでは積集合という一語で要約できる。ところが文書はすぐにその要約を崩す例外を並べる。この例外こそ関係の分析を難しくする部分である。

  • 同一アカウント内で IAM ユーザーの ARN に許可を付与するリソースベースポリシーは、アイデンティティベースポリシーやアクセス許可境界の暗黙的拒否に制限されない
  • IAM ロールの ARN に許可を付与するリソースベースポリシーは、アクセス許可境界やセッションポリシーの暗黙的拒否に制限される
  • ロールセッションの ARN に直接許可を付与するリソースベースポリシーはセッションに直接権限を与え、アイデンティティベースポリシーやアクセス許可境界やセッションポリシーの暗黙的拒否に制限されない。ロールを引き受けて要求すると、要求する主体はロール自体の ARN ではなくロールセッションの ARN である
  • フェデレーティッドユーザーのセッションも同じ性質を持ち、ただしリソースポリシーがフェデレーションした IAM ユーザーの ARN に権限を与えた場合はアクセス許可境界やセッションポリシーの暗黙的拒否に制限される
  • 文書が挙げる例では、アクセス許可境界が明示的に拒否した対象はリソースポリシーが許可してもアクセスできないが、境界に明示的拒否のないサービスはリソースポリシーの許可だけでアクセスが成立する。暗黙的拒否はリソースベースポリシーを制限しないからだ

この一覧を読めば、なぜ実効的な許可を人が目で合算しにくいかがはっきりする。同じ許可文でも、主体がユーザー ARN かロール ARN かセッション ARN かで結果が変わる。個別項目の点検がこの計算を代行してくれないことも同時にはっきりする。

グラフとして見るということ - 到達可能性を問う

関係が危険の単位なら、次の一手は関係をノードと辺に移すことだ。主体とロールとリソースをノードに置き、引き受けと受け渡しとアクセス許可を向きのある辺に置く。すると問いの形が変わる。この設定は正しいかではなくここからあそこまで行けるかになる。

この転換の利点ははっきりしている。第一に、個別項目の通過可否と無関係に経路の存在を問える。第二に、経路があるという事実はその経路上のどの節が欠陥かとは別に成立するので、欠陥がないのに経路がある状態を表現できる。第三に、対処の優先順位が変わる。経路を断つのに必要な最小の変更がどこかが、グラフの上で計算可能な問いになる。

きっかけとなったリポジトリの設計文書もこの方向を取っている。その文書は個別の設定ミスと複合的な危険をこう分ける。個別の設定ミスは侵害の条件を作るだけで、それ自体が侵害ではない。そして制御と連鎖の違いを制御は単一資産の属性についての述語であり、連鎖は複数の制御の間の関係であると定義する。制御が答える問いはこれ一つが正しく構成されているかであり、連鎖が答える問いはこれらの失敗が合わさって部分の和より大きい危険を作るかである。

同じ文書には実務的に興味深い設計上の選択も書かれている。連鎖に昇格しきい値を置き、構成する制御三つのうち二つが同時に失敗したときに連鎖が発動する、という形で定義するというものだ。文書は理由を二つ挙げる。攻撃経路はたいていすべての条件ではなくほとんどの条件を必要とするという点、そして制御一つの一時的な失敗がただちに致命的な複合結果に跳ねるノイズを防ぐという点である。

辺の作り方も文書にある。連鎖ごとに閉じた語彙から選んだ前提条件と事後条件を付けておき、ある連鎖の事後条件が別の連鎖の前提条件と一致すれば、二つの連鎖の間に向きのある辺ができる。文書はこれをグラフアルゴリズムではなく、有効な連鎖に対する二重ループと集合の積であるとし、グラフ構造はデータであって計算ではないと記す。経路探索と中心性分析と可視化は外部のツールが担う。

静的解析が解けないこと

グラフによる方法には明確な限界があり、その限界はおおむねポリシー文書に書かれていないものから来る。AWS 自身の文書がその境界を何か所かで示している。

第一は条件キーだ。AWS はポリシー文が効力を持つ条件を指定でき、そうすればアクセス要求が特定の条件を満たす場合にのみアクションとリソースへのアクセスを付与できると案内する。文書が挙げる例は、すべての要求が TLS で送信されなければならないという条件、そして特定のサービスを通じて使われる場合にのみ許可する条件である。問題は条件の真偽が要求時点の文脈で決まる点だ。ポリシー文書だけを置いて、その条件が実際にいつ真になるかは決定できない。

第二は時間である。ロールチェーンの 1 時間上限のように文書に釘を打たれた値もあるが、セッションの実際の寿命や認証情報が実際に保持されているかどうかは設定スナップショットに含まれない。ある経路が構造的に可能であることと今通ることは別の言明である。

第三はアカウントの外の状態だ。フェデレーション主体を受け入れる信頼ポリシーの実効範囲は、外部 ID プロバイダー側の設定に懸かっている。スナップショットの中にそのプロバイダーの状態はない。

第四は分析ツール自体の観測範囲である。先に引用したとおり、外部アクセス分析は有効化されたリージョンと同じリージョンのリソースに適用されたポリシーのみを見る。また文書は、特定の条件下でポリシー変更の通知が漏れて結果の生成が遅れうること、マルチリージョンアクセスポイントに関わる変更は最大 6 時間かかりうることを記す。スナップショットに基づく分析はここに一つ加わる。スナップショットを取った時点以降の変更はそのスナップショットにない。

第五はログの穴だ。PassRole が CloudTrail に残らないという事実は静的解析の限界ではなく事後追跡の限界だが、二つの限界が重なる地点で問題が大きくなる。静的解析が経路の存在を教えてくれても、その経路が実際に使われたかを IAM のログだけで確かめる方法はない。

きっかけとなったリポジトリが実際に掲げていること

ここで紹介の見出しとリポジトリの自己規定を並べておく必要がある。コミュニティに付いた見出しはAWS の設定の間に隠れている攻撃経路を見つけるセキュリティ検証ツールだった。リポジトリの README 冒頭の表現は違う。オープンソースのクラウド構成検証ツール。何が間違っているかを探す代わりに、AWS の構成が正しいことを証明する。認証情報なしでオフラインで動作する。リポジトリの説明欄には単一リソースのスキャナーが見落とす複合的な攻撃経路を見つけると書かれている。

二つの文が置く重心が違う。見出しは探すことにあり、README は証明にある。README はこの区別を明示的に強調しさえする。語はスキャナーではなく検証ツールである。ヒューリスティックではなく証明である。複合経路の探索はその上に乗った一筋であって、リポジトリの自己規定のすべてではない。

もう一つ見出しとずれる部分がある。見出しはAWS を特定するが、リポジトリの生成された制御参照文書にはサービス別の一覧に Azure 141 件、Cloudflare 29 件、Cisco 30 件といった AWS 以外の項目も一緒に入っている。AWS が主力なのは確かだが AWS 専用ではない。

動作モデルについても一つ正しておく必要がある。認証情報なしという文句は評価の段階に当たる。README は評価が AWS の API を呼ばずローカルの JSON スナップショットだけを見ると説明する一方、スナップショットを取る収集段階については読み取り専用の API 呼び出しを行いSecurityAudit の認証情報が必要だと記す。認証情報が要らないのは評価であり、収集には読み取り専用の認証情報が要る。

収集方式が三筋に分かれる点も README に表で整理されている。規制環境向けのバンドル収集ツールまたは事前に用意されたフィルターの方式は大規模言語モデルを使わず、実務寄りの筋はローカルのモデルが生の JSON を契約形式にマッピングした後で決定的に評価し、貢献者の筋はモデルがフィルターを書きチームが検証してリポジトリに載せる。契約と評価はいずれの場合も決定的だというのが文書の主張である。

公式文書が定めた四つの最小原則

ツールを使うにせよ使わないにせよ、関係をリストに入れるための土台は AWS の文書がすでに明記している原則である。四つを原文の表現に近い形で移す。

第一に、最小権限。文書の文はIAM ポリシーで許可を設定するときは、タスクの実行に必要な許可のみを付与するであり、方法は特定の条件下で特定のリソースに対して取れるアクションを定義することである。現実的な但し書きも併せてある。ワークロードやユースケースに必要な許可を探索する間は広い許可から始めてもよく、ユースケースが成熟したら付与する許可を減らして最小権限へ近づけていける。管理ポリシーについてもすべての AWS の顧客が利用できるよう提供されているため、特定のユースケースに対して最小権限を付与しないことがあると明記する。

第二に、アクセス許可境界。文書はアカウント内で権限管理を委任するとき委任する最大の許可を設定するためにアクセス許可境界を使うよう勧める。例に挙げる状況は、開発者が自分のワークロード用のロールを作成し管理できるようにする場合である。先に見たとおり境界は上限であり、それ自体は権限を与えない。

第三に、条件キー。文書はIAM ポリシーで条件を使ってアクセスをさらに制限するという項目を別に置いている。条件は関係の分析で特に重要で、先の表で見たように複数の通路で危険と安全を分けるのが文の存在ではなく条件の存在だからだ。

第四に、アクセス分析。文書は三筋を勧める。公開やアカウント間のアクセスを付与する前にそうしたアクセスが必要かを確認し結果を検討すること、CloudTrail の活動に基づいて最小権限のポリシーを生成すること、そしてポリシーの検証で文法とベストプラクティスを確かめることである。検証については100 を超えるポリシーチェックと実行可能な推奨を提供すると記す。未使用アクセスについてはもはや必要のないユーザー・ロール・許可・ポリシー・認証情報を定期的に見直して削除するという別項目がある。

この四つを関係の言葉で書き直せば点検リストになる。渡せるロールの範囲が渡す側の主体の許可より広くないか。委任の上限が掛かっているか。広い主体を受け入れる文ごとに条件が付いているか。アカウントの外を向くポリシーが各リージョンで観測されているか。四つの問いはいずれも二つ以上の対象を同時に見るときだけ答えが出る。
