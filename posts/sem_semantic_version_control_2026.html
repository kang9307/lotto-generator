이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: Git이 보여주는 무엇이 바뀌었나는 종종 틀린 질문에 대한 답이다

2026년 7월, 개발자 커뮤니티 hada에 Ataraxy Labs가 공개한 sem이라는 CLI 도구가 올라왔다. 한 줄 소개는 단순하다. Git 위에 함수·클래스 단위 변경 추적을 더한 시맨틱 버전관리 도구. 코드를 줄이 아니라 엔티티(함수·메서드·클래스) 단위로 비교해, 무엇이 추가·수정·삭제·이동·이름변경됐는지 보여준다는 것이다.

얼핏 사소한 UX 개선처럼 들릴 수 있다. 그러나 이 문제는 소프트웨어 공학에서 10년 넘게 다뤄온 오래된 난제다. Git의 기본 diff는 여전히 1970년대에 뿌리를 둔 Myers 알고리즘 계열의 줄 비교에 머물러 있고, 그 위에 시맨틱한 이해를 얹으려는 시도는 학계의 GumTree부터 GitHub 자신이 만들었다가 접은 semantic 라이브러리, 상용 SemanticDiff, 그리고 근래 널리 쓰이는 difftastic까지 계보가 길다. sem은 그 계보의 가장 최신 지점에서, diff를 보여주는 것을 넘어 엔티티 단위 이력 관리까지 git 워크플로 안에 통합하려는 시도다.

이 글은 sem이라는 도구 하나를 리뷰하는 데 그치지 않는다. 라인 기반 diff가 정확히 어디서 왜 깨지는지, AST(추상 구문 트리) 비교가 원리적으로 무엇을 하는지, 앞선 시도들이 각각 어디서 막혔는지, 그리고 AI가 코드를 읽고 쓰는 지금 이 문제가 왜 다시 중요해지는지를 순서대로 짚는다. 2026년 7월 기준으로 확인 가능한 공개 자료와 학술 연구를 근거로 삼되, 해석과 평가는 본인의 것임을 분명히 한다.

1. 라인 기반 diff의 구조적 한계 - 무엇이, 왜 깨지는가

1.1 diff가 실제로 비교하는 단위

git diff의 기본 알고리즘은 Myers의 최장 공통 부분수열(LCS) 기반 편집 거리 알고리즘이다. 두 파일을 줄의 배열로 보고, 한쪽에서 다른 쪽으로 가기 위해 몇 줄을 지우고 몇 줄을 더해야 하는지를 계산한다. 이 방식의 장점은 언어를 가리지 않고 빠르며 40년 넘게 검증된 안정성이다. 문제는 전제 자체에 있다. 코드의 의미 단위는 줄이 아니라 함수·클래스·표현식 같은 구조인데, diff는 그 구조를 전혀 모른 채 텍스트 줄만 비교한다.

1.2 리팩터링·이동·이름변경에서 노이즈가 폭발하는 이유

이 전제 불일치는 코드가 그대로 재배치되기만 해도 곧바로 드러난다. 함수 하나를 파일 아래로 옮기면, 실제 로직은 한 글자도 바뀌지 않았는데도 diff는 N줄 삭제와 N줄 추가로 보고한다. 변수 하나의 이름을 바꾸면 그 변수가 쓰인 모든 줄이 변경으로 표시된다. 들여쓰기를 통일하거나 줄바꿈 스타일만 바꿔도 실질적으로 무관한 줄들이 무더기로 빨갛고 파랗게 물든다. 이런 사례는 학술적으로도 반복 확인된 문제다. 줄 기반 diff는 추가·삭제만 계산할 뿐 수정·이동 같은 다른 편집 행위를 다루지 못하고, 소스 코드 구조와 정렬되지 않는 거친 단위(텍스트 줄)에서 작동한다는 점이 AST diff 연구의 출발점으로 꼽힌다.

1.3 코드 리뷰에 미치는 실질적 비용

이 노이즈의 대가는 추상적이지 않다. 리뷰어는 이 PR이 실제로 무엇을 바꿨는가라는 질문에 답하기 위해, 진짜 로직 변경과 단순 재배치를 diff 화면에서 직접 걸러내야 한다. 리팩터링이 코드를 원래 위치에서 멀리 옮기는 경우가 많다는 점을 고려하면, 이 필터링 비용은 변경이 복잡할수록 커진다. 결과적으로 리뷰어는 큰 PR을 더 대충 보거나, 리팩터링 PR과 로직 변경 PR을 분리하라고 강제하는 규율에 의존하게 된다. 두 대응 모두 diff 도구 자체의 한계를 사람이 메우는 방식이라는 점에서 근본 해결책은 아니다.

2. 시맨틱 diff란 무엇인가 - AST 비교의 원리

2.1 텍스트 줄 대신 구문 트리를 비교한다는 것

시맨틱 diff(구조적 diff)는 비교 대상을 텍스트 줄이 아니라 추상 구문 트리(AST)로 바꾼다. 소스 코드를 파싱해 함수·클래스·조건문·표현식이 부모-자식 관계로 얽힌 트리로 표현한 뒤, 두 버전의 트리를 맞대어 어떤 노드가 그대로 남았고 어떤 노드가 추가·삭제·수정·이동됐는지를 계산한다. 트리 구조를 보기 때문에 코드가 물리적으로 다른 줄에 있어도 같은 함수라는 것을 인식할 수 있고, 포맷팅처럼 트리 구조에 영향을 주지 않는 변경은 애초에 비교 대상에서 걸러진다.

2.2 GumTree - 시맨틱 diff의 학술적 원형

이 접근의 대표적 학술 원형이 2014년 Falleri 등이 제안한 GumTree다. GumTree는 두 AST를 두 단계로 매칭한다. 먼저 하향식(top-down) 단계에서 두 트리 사이의 동형(isomorphic) 부분트리, 즉 완전히 동일한 큰 덩어리를 먼저 찾아 고정한다. 그다음 상향식(bottom-up) 단계에서 아직 매칭되지 않은 노드들을 주변 맥락 유사도로 이어 붙인다. 그리고 편집 스크립트에 이동(move)이라는 연산을 처음으로 정식 도입해, 코드 블록이 옮겨진 경우를 삭제와 추가가 아니라 이동으로 표현할 수 있게 했다. 다만 최적 트리 편집 거리 계산은 비용이 커서, 원본 GumTree는 대형 AST에서 느려진다는 한계가 있었다. 이 한계는 2024년 후속 연구에서 휴리스틱으로 상당 부분 극복됐는데, 매칭 속도가 50배에서 최대 281배까지 빨라지고 편집 스크립트 크기는 중앙값 기준 절반으로 줄었다고 보고됐다.

2.3 tree-sitter - 실전 배치를 가능케 한 인프라

GumTree류 알고리즘이 이론이라면, 그것을 실제 개발자 도구에 밀어넣을 수 있게 한 인프라가 tree-sitter다. tree-sitter는 증분 파싱을 지원하는 파서 생성기로, 파일이 조금 바뀌면 트리 전체를 다시 만들지 않고 바뀐 부분만 재파싱한다. 이 증분 재인덱싱은 전체 재인덱싱 대비 약 4배 빠르다고 보고되며, 리눅스 커널처럼 2,800만 줄·7만 5천 파일 규모의 코드베이스도 수 분 안에 처리할 수 있는 규모로 검증됐다. difftastic·sem을 포함해 근래 등장한 실전 구조적 diff 도구 대부분이 언어별 파서를 직접 구현하는 대신 tree-sitter의 문법 생태계에 올라탄 이유가 여기에 있다. 파서를 새로 만드는 비용 없이 언어 지원을 확장할 수 있다는 것은 이 계보의 도구들이 과거 학술 프로토타입보다 훨씬 빠르게 실전에 도달한 핵심 이유다.

3. sem은 무엇을 하는 도구인가 - 엔티티 단위 diff와 이력 관리

3.1 세 단계 매칭 - 정확 ID에서 구조 해시, 퍼지 유사도로

sem(Ataraxy Labs, Rust로 구현, MIT·Apache-2.0 이중 라이선스)은 tree-sitter로 소스에서 함수·클래스·메서드 같은 엔티티를 추출한 뒤, 세 단계로 두 버전 사이의 엔티티를 매칭한다. 먼저 정확 ID 매칭으로 그대로 남은 엔티티를 걸러내고, 남은 것들은 구조 해시 비교로 포맷팅 같은 겉모습 변화와 실제 로직 변화를 구분한다. 마지막으로 토큰 중첩도가 80%를 넘는 경우 퍼지 유사도로 판단해 이름이 바뀌었거나 다른 위치로 옮겨간 엔티티까지 짝지어 준다. 이 3단계 구조 자체는 GumTree의 하향식·상향식 2단계 매칭에 구조 해시라는 실용적 필터를 하나 더 얹은 형태로 읽을 수 있다. 즉 sem은 새로운 이론을 제시하기보다, 검증된 접근을 제품화 단계까지 다듬은 도구에 가깝다.

3.2 명령어 구성 - diff를 넘어 이력 전체로

sem이 흥미로운 지점은 diff 한 번 보여주는 데서 멈추지 않는다는 것이다. sem diff는 엔티티 단위 변경과 이름변경 감지, 단어 단위 강조를 보여주고, sem impact는 특정 엔티티를 바꿨을 때 어떤 다른 파일·함수가 영향을 받는지 교차 파일 의존성을 분석한다. sem blame은 줄이 아니라 엔티티 단위로 이 함수를 마지막으로 실질적으로 바꾼 사람을 추적하고, sem log는 특정 함수 하나가 커밋 역사를 거치며 어떻게 진화했는지를 보여준다. sem entities는 파일·디렉터리의 함수·클래스 목록을 나열하고, sem context는 뒤에서 다룰 LLM 컨텍스트 추출 기능이다. 이 조합은 diff 도구라기보다 엔티티를 1급 시민으로 삼는 버전관리 레이어에 가깝다.

3.3 git과의 통합 방식

sem은 별도 저장소를 만들지 않고 git을 감싸는 방식으로 동작한다. sem setup 명령으로 git의 기본 diff 핸들러 자리에 들어갈 수 있어, 팀 전체가 도구를 바꾸지 않아도 git diff·git log -p 같은 익숙한 명령의 출력만 시맨틱하게 바뀐다. tree-sitter가 지원하지 않는 파일 형식은 청크 기반 텍스트 diff로 자동 폴백한다는 점도 실무적으로 중요하다. 32개 언어를 지원한다고 해서 지원 밖 코드가 아예 diff되지 않는 게 아니라, 못 알아보는 파일은 조용히 예전 방식으로 돌아간다는 뜻이다.

4. 기존 시도들과 비교 - difftastic·GumTree·github/semantic·SemanticDiff

sem을 계보 없는 첫 시도로 보면 과대평가하기 쉽다. 이 자리에 도달하기까지 최소 세 갈래의 선행 시도가 있었고, 각각 다른 지점에서 멈췄다.

4.1 difftastic - 보기 좋은 구조적 diff, 그러나 이력은 아니다

difftastic은 Wilfred Hughes가 Rust로 만든 도구로, tree-sitter로 50개 이상 언어를 파싱해 포맷팅 차이를 무시하고 의미 있는 변경만 나란히 보여준다. sem과 가장 가까운 이웃이지만 목적이 다르다. difftastic은 한 번의 비교를 더 잘 보여주는 도구이고, 함수 단위 이력이나 영향 분석, blame 같은 시간축 기능은 없다. 즉 difftastic이 이번 diff를 더 읽기 좋게 만든다면, sem은 이 함수가 시간에 걸쳐 어떻게 변해왔는가까지 다룬다.

4.2 GumTree - 정확하지만 도구가 아니라 알고리즘이었다

GumTree는 애초에 최종 사용자 도구가 아니라 연구 라이브러리였다. 최적 트리 편집 거리 계산의 비용 문제, 그리고 프로덕션 수준 CLI·git 통합의 부재가 대중적 채택을 가로막았다. sem이나 difftastic 같은 이후 도구들이 사실상 GumTree류 알고리즘의 아이디어(하향식·상향식 매칭, move 연산)를 제품 수준 엔지니어링으로 감싼 결과물이라고 보는 것이 정확하다.

4.3 github/semantic의 교훈 - 구조적 diff 인프라는 유지비가 크다

가장 시사적인 사례는 GitHub 자신이 만든 semantic이다. Haskell로 작성돼 Myers 알고리즘과 RWS 계열 매칭을 결합해 여러 언어의 구조적 diff·분석을 제공하려 했던 이 라이브러리는 2025년 4월 1일 아카이브됐다. 대형 플랫폼조차 모든 언어에 대해 정확한 구조적 파서·매처를 자체 구현하고 계속 유지한다는 과제의 비용을 감당하지 못했다는 뜻으로 읽을 수 있다. sem이 자체 파서 대신 tree-sitter 생태계에 올라탄 선택은 이 교훈을 정면으로 반영한 설계로 보인다. 언어 지원을 도구 제작자가 전담하는 대신 커뮤니티가 유지하는 문법 저장소에 위임한 것이다.

4.4 sem의 위치 - 계보 위의 다음 걸음

이렇게 놓고 보면 sem의 기여는 AST 비교를 처음 시도했다는 데 있지 않다. ①tree-sitter라는 검증된 파싱 인프라, ②GumTree류 3단계 매칭의 실용화, ③diff를 넘어 impact·blame·log까지 묶은 엔티티 중심 워크플로, ④git wrapper 방식의 낮은 도입 마찰이라는 네 조각을 하나의 CLI로 조립한 데 있다. 개별 조각은 새롭지 않지만, 조합과 실행이 이 계보에서 상대적으로 완성도 높게 이뤄졌다는 것이 본인 평가다.

5. AST 기반 비교가 실제로 주는 것 - 리뷰 명료성·리팩터 추적·의미 있는 이력

5.1 리뷰 명료성

리뷰어에게 가장 직접적인 효과는 diff 화면에서 재배치와 로직 변경이 분리된다는 점이다. 이름변경·이동으로 표시된 항목은 눈으로 훑고 넘어가고, 실제 수정으로 표시된 항목에 리뷰 시간을 집중할 수 있다. 이는 단순 편의가 아니라, 앞서 짚은 리뷰어가 노이즈를 직접 필터링해야 하는 비용을 도구 쪽으로 옮기는 구조적 변화다.

5.2 리팩터 추적

sem log·sem blame이 엔티티 단위로 동작한다는 것은, 이 함수가 커밋 히스토리 전체에서 어떻게 바뀌어 왔는가를 파일 단위 blame으로는 사실상 불가능했던 방식으로 재구성할 수 있다는 뜻이다. 파일 blame은 함수가 파일을 옮겨 다니거나 다른 파일에서 추출·병합되는 순간 이력이 끊긴다. 엔티티 ID를 기준으로 추적하면 그 단절을 넘길 수 있다.

5.3 의미 있는 변경 이력

결과적으로 이 접근은 커밋 로그를 줄이 몇 개 바뀌었나의 기록에서 이 함수·클래스가 왜, 어떻게 진화했는가의 기록으로 바꾼다. 이는 코드 리뷰뿐 아니라 온보딩(신규 인력이 핵심 로직의 변천사를 따라가기), 사후 분석(버그가 어느 시점 어떤 엔티티 변경에서 유입됐는지 추적) 같은 인접 작업에도 파급된다.

6. AI 코드리뷰·에이전트 시대에 시맨틱 변경 추적의 가치

6.1 LLM 컨텍스트 예산과 diff 노이즈

2026년 현재 코드 리뷰의 상당 부분은 이미 LLM 기반 에이전트가 먼저 훑는다. 이때 문제는 사람이 겪는 것과 근본적으로 같지만 대가가 다르다. 사람은 노이즈 낀 diff를 눈으로 걸러내며 시간을 쓰지만, LLM은 노이즈를 그대로 토큰으로 소비한다. 이동·재배치로 부풀려진 diff를 통째로 프롬프트에 넣으면 컨텍스트 예산을 불필요하게 잡아먹고, 모델이 정말 중요한 변경에 쏟을 수 있는 주의를 희석시킨다. 함수 단위로 무엇이 실제로 바뀌었는가만 압축해 넣을 수 있다면, 같은 컨텍스트 예산으로 더 많은 실제 신호를 담을 수 있다.

6.2 sem context와 MCP 통합

sem이 sem context라는 토큰 예산 기반 LLM 컨텍스트 추출 명령과 MCP(Model Context Protocol) 연동을 갖춘 것은 이 문제를 정확히 겨냥한다. AI 코딩 에이전트가 이 PR에서 무엇이 바뀌었는지 알려달라는 질의를 받았을 때, 원시 git diff 대신 엔티티 단위로 정제된 변경 목록을 받으면 같은 토큰 수로 더 정확한 답을 낼 여지가 커진다. 이는 sem 하나만의 특징이라기보다, AI 코드리뷰 도구들이 2026년 들어 공통으로 향하는 방향과 겹친다. 최근 코드리뷰 도구들은 PR의 diff만 보는 것을 넘어 리포지토리 전체의 의미 그래프를 구축해 아키텍처 맥락을 함께 제공하는 쪽으로 이동하고 있다. sem의 엔티티 그래프는 그 그래프의 재료를 diff 시점에서부터 정제해 공급하는 상류 단계로 읽을 수 있다.

6.3 자율 에이전트에게 이동과 수정은 다른 신호다

사람 리뷰어에게 재배치와 로직 변경을 구분하는 것이 편의라면, 자율 코딩 에이전트에게는 그 구분이 행동 결정에 직결된다. 어떤 함수가 단순히 이동만 됐다면 에이전트는 테스트를 다시 설계할 필요가 없지만, 로직이 바뀌었다면 관련 테스트·문서·의존 코드를 함께 갱신해야 한다. 이 판단을 diff 텍스트에서 추론하게 만드는 것과, 도구가 애초에 이동과 수정을 구분해 태그를 붙여 주는 것은 에이전트 파이프라인의 신뢰도에서 꽤 큰 차이를 만든다.

7. 실무 도입 고려 - 언어 지원·성능·git 통합

7.1 언어 지원의 현실 - 32개와 그 바깥

sem은 TypeScript·Python·Go·Rust·Java·C/C++·JavaScript·Ruby·PHP·Swift·Kotlin 등 32개 언어와 JSON·YAML·TOML·CSV·Markdown 같은 구조화 포맷을 지원한다. 주류 백엔드·프런트엔드 스택은 대체로 포괄하지만, 사내 DSL이나 소수 언어, 또는 tree-sitter 문법이 아직 성숙하지 않은 언어라면 청크 기반 텍스트 폴백으로 조용히 떨어진다는 점을 미리 알고 있어야 한다. 폴백 자체는 안전하지만(도구가 멈추지 않는다), 폴백 상태에서는 이 글에서 설명한 이점(엔티티 매칭·이동 감지·impact 분석)이 사라지고 평범한 diff로 돌아간다는 점은 기억해야 한다.

7.2 성능 - 증분 파싱과 클라우드 가속의 트레이드오프

tree-sitter의 증분 파싱 덕분에 개별 파일 재파싱은 빠르지만, impact처럼 리포지토리 전체 의존 그래프를 훑는 질의는 성격이 다르다. sem 문서에 공개된 예시에 따르면 대형 리포지토리(deno 규모)에서 impact 질의가 로컬 재계산 시 약 573ms, 클라우드 캐시를 쓰면 약 86ms로 보고된다. 이는 큰 그래프 질의를 매번 처음부터 다시 계산하는 방식이 실전에서 부담스러울 수 있고, 캐시·인덱스 전략이 성능을 좌우한다는 뜻이다. sem setup 이후에는 로컬에 상주 그래프를 유지해 반복 질의를 빠르게 하는 방식도 함께 제공된다고 안내된다. 도입 전에 본인 리포지토리 규모에서 diff뿐 아니라 impact·log 같은 그래프 질의의 실제 지연을 재보는 것이 안전하다.

7.3 git 통합 방식과 팀 도입 마찰

sem이 별도 저장소나 워크플로를 요구하지 않고 git의 기본 diff 핸들러 자리를 대체하는 방식을 택한 것은 도입 마찰을 줄이는 합리적 설계다. 팀 전체가 새 도구를 배우지 않아도 기존 git diff·git log 습관 위에서 자동으로 시맨틱한 출력을 받을 수 있다. 다만 CI·코드리뷰 봇·기존 diff를 파싱하는 사내 스크립트가 있다면, 출력 형식이 바뀌는 지점에서 별도 검증이 필요하다.

8. 한계와 아직 안 풀린 문제

8.1 학계가 지적하는 AST diff의 공통 한계

이 글이 소개한 도구들에 취해 AST diff를 만능으로 그리는 것은 정직하지 않다. 리팩터링 인식 AST diff를 다룬 2024년 연구는 현재의 AST diff 도구들이 여전히 공통으로 겪는 한계를 다섯 가지로 정리한다. ①한 노드가 여러 노드에 대응하는 다중 매핑을 지원하지 못하고, ②의미적으로 맞지 않는 AST 노드끼리 매칭해 버리는 경우가 있으며, ③언어별 문법 단서를 매칭 과정에 충분히 활용하지 못하고, ④리팩터링 패턴 자체를 인식하는 능력이 부족하고, ⑤커밋 단위가 아니라 파일 단위 비교에 머무는 경우가 많다는 것이다. sem이 3단계 매칭과 impact·log 기능으로 이 중 일부(특히 이력·리팩터링 추적)를 완화하지만, 다섯 항목 전부를 해소했다고 볼 근거는 없다.

8.2 신생 도구의 안정성 - hada 반응이 보여준 온도차

sem이 hada에 소개됐을 때 달린 반응 중 하나는 이런 게 가능할 줄 몰랐다는 감탄과 동시에, 프로덕션에 쓸 만큼 안정적이냐는 질문이었다. 이는 합리적인 경계다. 3단계 매칭의 퍼지 유사도 임계값(토큰 중첩 80%)처럼 휴리스틱이 개입하는 지점에서는 오탐(엉뚱한 함수를 이름변경으로 오판)이나 미탐(진짜 이동을 놓침)이 발생할 수 있고, 이는 언어·코드 스타일에 따라 체감이 다를 수 있다. 대형 팀에 전면 도입하기 전에, 본인 코드베이스에서 실제 리팩터링 커밋 몇 건을 sem diff로 재현해 결과를 직접 확인하는 것이 안전하다.

8.3 구조 파일과 비지원 코드의 폴백

sem이 지원하는 JSON·YAML·TOML 같은 구조화 포맷도 있지만, 정규식 기반 설정 파일이나 사내 커스텀 포맷, tree-sitter 문법이 아직 없는 신생 언어는 청크 기반 텍스트 diff로 조용히 돌아간다. 리포지토리가 다국어·다포맷으로 섞여 있다면, 실제로 시맨틱하게 보이는 파일 비율이 기대보다 낮을 수 있다는 점을 미리 확인해야 한다.

9. 결론 - 오늘 확인해볼 만한 3가지

시맨틱 버전관리는 새로운 개념이 아니다. GumTree가 학술적 토대를 놓은 지 10년이 넘었고, GitHub 자신도 한 번 시도했다가 접었다. sem이 흥미로운 이유는 새 이론을 들고 나와서가 아니라, tree-sitter라는 성숙한 인프라 위에서 diff·impact·blame·log를 하나의 git 네이티브 워크플로로 묶어 냈고, 그 과정에서 AI 에이전트의 컨텍스트 소비라는 2026년형 문제까지 정면으로 겨냥했기 때문이다. 다만 학계가 지적하는 AST diff의 근본 한계(다중 매핑, 의미 불일치 매칭, 리팩터링 패턴 인식 부족)는 sem에서도 완전히 해소되지 않았고, 신생 도구 특유의 안정성 검증은 아직 진행형이다.

9.1 본인 코드베이스로 먼저 재현해 보라

최근 리팩터링 커밋 5~10건을 골라 sem diff로 다시 봤을 때, 실제로 노이즈가 줄고 이동·이름변경이 정확히 잡히는지 확인하라. 언어·코드 스타일에 따라 체감이 다를 수 있다.

9.2 CI·리뷰 봇과의 접점을 먼저 점검하라

sem setup으로 기본 diff 핸들러를 바꾸기 전에, 기존 diff 출력을 파싱하는 CI 스크립트나 리뷰 봇이 있는지 확인하고 별도 환경에서 먼저 검증하라.

9.3 AI 에이전트 파이프라인이 있다면 컨텍스트 소비량을 먼저 재라

코드리뷰·리팩터링에 LLM 에이전트를 이미 쓰고 있다면, 원시 diff와 sem context 출력을 같은 PR에 각각 넣어 토큰 소비와 답변 품질을 비교해 보라. 그 격차가 도입 여부를 결정할 가장 구체적인 근거가 된다.
