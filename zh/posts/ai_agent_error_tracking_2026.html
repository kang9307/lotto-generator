如何追踪生产环境中 AI 智能体的错误

如何观测非确定性、多步骤的智能体故障并防止回归 - 一篇从社区提问出发的 LLM 可观测性实务分析

2026-07-08 开发/基础设施

引言:「智能体出错了,我们怎么知道」这个实务问题

一个已经在生产环境中运行多个 AI 智能体的小团队,在开发者社区 hada.io 上提出了一个实务问题,核心有三点:如何事后追踪智能体的错误(日志、审计记录、人工核验)?如何在「AI 提议、人类决定」这一原则与效率之间取得平衡?当多个智能体依次接力完成工作时,责任该如何划分?该团队已经在使用角色/权限说明和逐任务审批标签。

回复大体指向同一个方向:与其事后追踪,不如事前预防更有效 - 缩小智能体可用的 CLI 权限范围,从源头减少可能出问题的范围,能有效降低审计负担,这是评论者的一线经验之谈。但当多个智能体依次接力工作时,该如何分别强制不同的 CLI 限制,仍是尚未解决的难题。

这个方向是对的,但只是答案的一半。要设计出好的预防机制,首先要能够观测到究竟哪里在出错;权限该收窄到什么程度,这个判断标准本身也来自观测数据。而且,一种从未出现过的新失败模式,按定义就不可能被现有的预防规则拦住。本文不打算复述 hada 上的讨论,而是从实务角度梳理这个提问所指向的更大主题 - 如何观测生产环境中的 LLM 与 AI 智能体、并追踪其失败。内容涵盖追踪、评估方法论、工具格局与隐私问题,均整理自截至 2026 年 7 月公开的资料。

1. 为什么追踪很难 - 非确定性与多步骤流水线

1.1 相同输入,不同输出

传统软件的日志与调试建立在「相同输入产生相同输出」这一前提之上。LLM 打破了这个前提:温度(temperature)和采样机制意味着同一条提示词每次都可能得到不同答案,厂商悄悄替换模型版本也可能让昨天还能通过的用例今天就失败。「复现问题、再定位原因」这一调试的基本动作,根基本身就在动摇。

1.2 不是单次请求,而是一棵树

智能体不是一问一答,而是在制定计划、调用工具、观察结果、重新计划之间反复循环多次。在多智能体流水线中,一个智能体的输出会成为下一个智能体的输入,一旦上游某个智能体产生一次幻觉,这个错误就会原样传播到下游,形成级联失败(cascading failure)。错误不再是一行日志,而是横跨多个步骤的因果链条。

1.3 失败看起来不像「错误」

工具调用在程序层面可能成功(HTTP 200),但如果传入该调用的参数本身就是幻觉产生的错误值,结果就会悄悄出错。这类工具参数幻觉与一般的 LLM 文本幻觉性质不同:它不是表面可见的文字错误,而是决定「查询什么数据、用什么参数」的程序化输入本身就是错的,只看系统日志会以为这是一次正常请求。不抛出异常的失败也不会触发告警。这正是黑盒监控 - 只看响应时间和错误率的方式 - 在智能体系统中失灵的原因。

2. 应该观测什么 - 追踪、跨度与工具调用

2.1 追踪与跨度

从分布式系统追踪借来的概念在这里同样适用。追踪是一次用户请求穿越系统的完整历程,跨度是构成这段历程的单个工作单元。把智能体循环中的每一步 - 一次 LLM 调用、一次工具调用、一次向子智能体的委派 - 都记录为独立的跨度,当最终答案出问题时,就能沿着树状结构精确回溯「究竟哪一步出了错」。没有这个机制,留下的就只有最初的输入和最终的输出,中间的计划、重新计划、工具选择过程全都消失在黑盒之中。

2.2 工具调用的参数与返回值

实务中调试价值最高的埋点,往往出人意料地不是最终答案文本,而是工具调用的参数与返回值。记录调用了哪个工具、用了什么参数、调用了几次,以及智能体如何把结果带入下一步决策,就能让人完整还原「为什么会做出这个判断」。工具误用 - 选错工具或传错参数 - 被公认为智能体特有失败模式中最常见的一种。

2.3 token、成本与延迟

从运维角度看,成本失控和质量问题一样是实实在在的风险。一次失败的工具调用触发重试,重试又失败再触发下一次重试的重试风暴,或者智能体陷入不断「优化」自身输出的无限精修循环,都可能连续消耗数小时算力,把账单越吹越大。以跨度为单位记录每次请求的 token 数、延迟与成本,并设置硬性上限(hard cap),就能把这类失控从「事故」提前变成「告警」。

2.4 完整记录提示词与输出的两难

单从可复现性考虑,完整保留提示词与响应原文是最可靠的做法,因为在尝试复现问题时,经过摘要的日志往往不够用。但这种全文日志会与隐私问题正面冲突,这一张力将在第 7 节单独讨论。

3. 追踪的标准化 - OpenTelemetry GenAI 语义约定

3.1 为什么需要标准

如果字段名称和结构因构建智能体所用的框架不同而各不相同,那么每次更换工具、或是想把多个团队的追踪数据汇总到一处时,都要重复做一遍映射工作。OpenTelemetry GenAI 语义约定,是 CNCF 旗下 OTel GenAI 工作组为解决这个问题而定义的标准模式(schema)。它把记录提示词、模型响应、token 用量、工具/智能体调用、提供商元数据所用的属性名标准化,使来自 LangChain 智能体的跨度,和来自原生 OpenAI API 调用的跨度,结构上看起来是一致的。

3.2 核心结构

一次 LLM 调用被表示为一个跨度,其 gen_ai.operation.name 属性携带 chat、text_completion、generate_content(多模态)等值。请求的模型名称、提示词 token 数、补全 token 数、温度等参数,以标准属性的形式附加在该跨度上。工具调用与智能体间的委派也被作为独立的跨度类型处理,使得在同一条追踪中可以区分「模型的推理部分」与「工具的执行部分」。

3.3 采用现状与局限

截至 2026 年初,该约定的相当一部分内容仍处于实验性(experimental)阶段,但据报道 Datadog、Google Cloud、AWS、Azure 等多家可观测性平台和云厂商已经开始支持。面向多智能体系统的扩展 - 任务、动作、智能体团队、内存、产出物的追踪 - 也正在工作组内讨论中。标准尚未完全定型这一点需要留意,但如果想在不被特定厂商锁定的前提下留存追踪数据,现阶段以这套约定作为基础仍是合理的选择。

4. LLM 可观测性工具的格局 - 三大阵营

4.1 三种类型

市场大致分为三个阵营。其一是 APM 扩展型,Datadog、New Relic 这类既有基础设施监控产品,在原有的基础设施指标旁边加入 token、延迟等 LLM 标签页。其二是 AI 原生追踪型,LangSmith、Langfuse、Arize Phoenix 这类产品深耕追踪采集,并向上扩展到评估、漂移检测等能力。其三是网关型,Helicone、Portkey 这类产品作为应用与 LLM 提供商之间的代理,以最小的代码改动叠加路由、缓存、成本追踪功能。

4.2 三款工具对比

三款 AI 原生追踪工具的优势区分十分明显。

工具擅长的技术栈开放性差异化特点
LangSmithLangChain / LangGraph闭源 SaaS(企业版支持自托管)LangGraph 状态差异追踪,集成深度
Langfuse框架无关开源(MIT),自托管优先社区采用面最广,基于 ClickHouse
Arize Phoenix以 RAG 为中心开源核心 + 托管版(Arize AX)RAG 质量评估模板,嵌入漂移可视化

4.3 如何选择

如果以 LangGraph 为基础,希望从开发到部署都在同一平台内完成,LangSmith 更有优势。如果不想被特定框架绑定,或需要数据主权与自托管能力,Langfuse 更接近社区的默认选择。如果检索质量(上下文精确度、忠实度、答案相关性)是核心业务风险,评估功能更丰富的 Phoenix 更合适。值得一提的是,ClickHouse 收购 Langfuse 之后,其自托管方案与特定数据库的绑定更紧密了;而 Braintrust 这类托管替代方案也完成了大额融资,依然活跃在市场中 - 这两点在选型时都值得纳入考量。无论最终选择哪款工具,先明确「自己到底想观测什么」都应该排在选工具之前。

5. 离线评估与在线监控

5.1 概念区分

离线评估运行在团队完全掌控的数据集上 - 一个输入与预期输出(或评分标准)都预先设定好的黄金测试集。在线监控运行在真实用户流量上,而这类流量大多数情况下没有参考答案。团队通常会把这两套工作流分开运维:测试阶段使用经过筛选的数据集,生产阶段则针对杂乱、无参考答案的真实追踪数据分别评估。

5.2 两个维度的分工

离线评估捕捉的是部署前已知的失败模式,在线监控捕捉的则是离线测试套件未曾预料到的新失败与分布变化。二者缺一不可:只做离线评估,会漏掉真实用户抛出的意料之外的输入;只做在线监控,那些本可以在部署前就拦下的明显回归,每次都要等到生产环境才第一次被发现。

5.3 以循环方式运维

实务中推荐的流程是循环式的:先用离线评估验证,再部署,通过在线监控收集新的失败案例,再把这些案例并回离线黄金测试集以改进智能体,如此循环往复。这套流程一旦成型,LLM 运维就会从「出事后再应对」转变为「问题变大之前先察觉」。

5.4 LLM-as-judge 及其局限

在给没有明确标准答案的响应质量打分时,用另一个 LLM 充当评审(LLM-as-judge)的做法被广泛使用,在人工无法逐条打分的规模下尤其有用。但评审模型本身也存在偏见和一致性问题,与其盲目相信评审结果,不如同时建立抽样人工复核的机制,更为稳妥。

6. 收集失败案例与防止回归

6.1 先对失败模式分类

常见的智能体特有失败模式包括:工具误用(选错工具、传错参数)、演变成重试风暴的无限循环、一个智能体的错误扩散到下一个的幻觉级联、逐渐偏离最初目标的目标漂移(goal drift)、提示词注入,以及表面看起来正常、质量却在悄悄下滑的静默质量退化。在决定要观测什么之前,先在团队内部就「什么算作失败」达成共识,能让后续的追踪设计容易得多。

6.2 构建黄金测试集

黄金测试集是经过审核、版本化管理的评估数据集,包含具有代表性的输入以及预期输出或评分标准。一开始不需要做得很庞大:针对单个功能准备 50 到 100 个样本,其中核心用例 40 到 60 个、边缘用例 15 到 25 个左右,就足以捕捉大部分回归,同时执行成本也不会太高。这个数据集不是一次建成就结束,而要持续从在线监控中挖掘评审得分较低或轨迹异常的真实失败追踪,并不断并入其中,逐步壮大。

6.3 把它接入 CI 作为回归测试

从黄金测试集中挑出大约 30 个特别稳定的核心用例,接入 CI,作为每次 PR 都自动运行的回归套件。每当模型更新、提示词修改或检索流水线变动时,只要这套回归套件检测到准确性、相关性或安全性下降,就能在 PR 阶段而非部署之后,捕捉到「修好了这里、却弄坏了那里」的问题。

7. 隐私 - 敏感信息日志需谨慎

7.1 为什么这是个问题

用户常常把邮箱、电话号码、地址,有时甚至是凭证信息直接粘贴进提示词。如果可观测性工具为了可复现性,把完整的提示词和响应原样存入追踪记录,这些个人信息就会一直留存在日志与追踪存储中。据报道,自 2018 年以来累积的 GDPR 罚款金额已达数十亿欧元规模,说明这并非抽象风险,而是实实在在会导致罚款的问题。在医疗场景中,一旦患者信息(PHI)在没有业务伙伴协议(BAA)的情况下出现在提示词里,这本身就可能构成需要报告的 HIPAA 违规披露。

7.2 脱敏处理方式

业界常见做法是先用正则表达式与命名实体识别(NER)检测敏感信息,再进行不可逆脱敏(匿名化),或在需要恢复时进行可逆令牌化(假名化)。与其把这套逻辑分散在应用代码各处,不如在网关或日志管道这样的单一节点集中处理 - 例如在 OTel 管道中插入一个自定义的 PII 脱敏处理器 - 这样能减少遗漏的风险。敏感程度越高,越建议把脱敏逻辑本身放在自有网络内部处理,确保脱敏前的原始文本不经过公网。

7.3 与日志留存义务之间的平衡

棘手之处在于,监管并不只是禁止记录日志,有时还会要求记录日志。欧盟《AI 法案》就对高风险系统课以日志记录义务(第 12 条)。也就是说,「什么都不记录」并不是一个选项,真正的课题是设计好哪些该保留、哪些该过滤掉。实务中观察到的折中方案是:为满足合规要求保留经过脱敏的追踪数据以及成本、延迟等指标,同时对原始提示词这类高敏感字段单独设置更短的保留期限或更严格的访问控制。

8. 重新审视 hada 的讨论 - 预防与追踪并非对立

8.1 社区回答说对了什么

hada 评论区指出的「收窄权限范围能降低审计负担」这一点是准确的。智能体本来就做不到的事,自然也不需要追踪。这是在第 5 节讨论的离线/在线评估之前,在系统设计阶段就缩小失败影响半径的做法。

8.2 为什么仅靠预防还不够

但权限该收窄到什么程度、收窄到哪里,并不会自己浮现答案,这个判断标准恰恰来自对「实际哪里出了错」的观测数据。而且,一种从未经历过的新失败模式,按定义就不可能被写进现有的预防规则里 - 在提示词注入这类攻击者不断寻找新路径的领域尤其如此。预防规则不是一份固定的答案,而是一份需要持续从观测中更新的、活的产出物。

8.3 实务上的综合 - 观测磨砺预防

可观测性与权限最小化并非两个相互竞争的选项,而应被视为同一个循环的两个组成部分。当追踪数据揭示出新的失败模式时,再据此进一步收紧权限范围与审批闸门。hada 原帖提出的第三个问题 - 多个智能体依次接力工作时如何划分责任 - 也可以从这个角度得到解答。只要把每个智能体的调用都记录为独立的跨度,并通过追踪 ID 串联起来,「谁在何时做了什么」就会成为自动生成的执行记录,而不再依赖设计文档。

9. 实务清单 - 今天就能落地的事项

9.1 先把追踪接上

在选定评估体系或工具之前,先加入最基础的埋点:把智能体循环的每一步(LLM 调用、工具调用、向子智能体的委派)都记录为跨度。以 OpenTelemetry GenAI 约定作为基础,意味着日后更换工具时,这些追踪数据资产依然可以带走。

9.2 搭建黄金测试集与 CI 回归

基于自己真实的工作负载构建一个 50 到 100 个用例的黄金测试集,并把其中约 30 个稳定用例接入每次 PR 都会运行的 CI 回归套件。定期把在线监控中发现的失败案例并入这个黄金测试集。

9.3 把脱敏作为日志管道的默认设置

在开启提示词/响应全文日志之前,先把敏感信息脱敏作为默认设置放进网关或管道这个单一节点,而不是分散写进应用代码里。到底该保留什么,应由团队在日志留存义务(如欧盟 AI 法案)与最小化收集原则之间明确权衡后决定。
