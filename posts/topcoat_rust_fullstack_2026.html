Topcoat — 「API 계층을 없앤다」는 발상이 실제로 없애는 것

Rust 풀스택 프레임워크가 지운 경계선은 사라진 것이 아니라 옮겨간 것이다

2026-07-29 개발/인프라

서론: 「API 계층이 없다」는 문장을 뜯어보면

2026년 7월 22일, Tokio 팀이 Topcoat이라는 Rust 풀스택 웹 프레임워크를 공개했다. 발표문의 핵심 주장은 간명하다. 모든 마크업을 서버에서 렌더링하고, 컴포넌트를 async 함수로 만들어 데이터베이스를 직접 조회하게 하면, 별도의 API 계층에 필요했던 보일러플레이트가 전부 사라진다는 것이다.

이 문장은 매력적이지만, 기술 선택을 할 때 위험한 종류의 매력이다. 「없앤다」는 말은 두 가지를 뜻할 수 있기 때문이다. 하나는 정말 필요 없어서 사라지는 것이고, 다른 하나는 여전히 필요하지만 다른 곳으로 옮겨가는 것이다. 앞의 것은 순이익이지만, 뒤의 것은 회계 장부의 항목 이동에 가깝다. 눈에 보이는 코드가 줄어들 뿐, 그 코드가 담당하던 책임은 어딘가에서 다시 처리돼야 한다.

이 글은 Topcoat을 소개하려는 글이 아니다. 「API 계층을 없앤다」는 발상 자체를 실무 관점에서 해부하려는 글이다. 서버 렌더링이 다시 돌아오는 2026년의 흐름 속에서, 이 선택이 언제 맞고 언제 틀리는지를 따진다. 확인 방법은 공식 저장소와 발표 글, 그리고 Cargo.toml과 docs.rs의 메타데이터다. 확인되지 않은 것은 확인되지 않았다고 적었다. 특히 성능 수치는 공식 자료에 없어서 이 글에도 없다. 프레임워크 소개 글에서 흔히 보이는 「빠르다」류의 주장을 이 글은 하지 않는다.

서버 렌더링이 어떤 경로로 다시 주류 후보가 됐는지에 대해서는 프론트엔드 20년의 순환을 정리한 글에서 따로 다뤘다. 여기서는 그 흐름의 가장 최근 사례 하나를 깊게 판다.

1. Topcoat은 무엇인가 — 공식 자료에서 확인된 것만

먼저 사실 관계를 고정한다. 아래는 2026년 7월 말 시점에 공식 저장소·발표 글·docs.rs에서 직접 확인한 것이다.

  • 주체와 위치: tokio-rs/topcoat 저장소. 비동기 런타임 Tokio를 만든 팀의 조직 계정 아래에 있다.
  • 라이선스: MIT. Cargo.toml의 license 필드와 저장소 표기가 일치한다.
  • 버전: docs.rs 기준 0.5.0이 2026년 7월 27일자로 게시돼 있다. 즉 발표 닷새 만에 마이너 버전이 올라갔다.
  • 자기 표기: README가 「Early-stage and experimental. Expect breaking changes.」라고 스스로 밝힌다. 벤더가 마케팅으로 쓴 문구가 아니라 저자가 붙인 경고다.
  • 요구 툴체인: Cargo.toml의 rust-version이 1.95다. 사내 빌드 이미지가 고정돼 있으면 이 한 줄이 도입 일정을 좌우할 수 있다.
  • 구성: 워크스페이스가 30개 이상의 크레이트로 쪼개져 있다. 세션·쿠키·메일·아이콘·폰트·에셋·Tailwind·UI가 각각 별도 크레이트이고, htmx·Alpine AJAX·Datastar 통합도 크레이트로 분리돼 있다.

동작 방식의 뼈대는 세 가지다. 첫째, 모든 마크업은 서버에서 렌더링된다. 컴포넌트는 async 함수이므로 그 안에서 DB를 조회하거나 권한을 확인할 수 있다. 둘째, 브라우저에서 살아 움직여야 하는 부분은 $(...) 표현식으로 쓴다. 발표 글의 설명에 따르면 이 표현식은 타입 검사된 Rust 표현식의 부분집합을 JavaScript로 상호 컴파일한 것이며, 그래서 WebAssembly 번들도 별도 클라이언트 빌드 단계도 필요하지 않다. 셋째, 서버가 다시 그려야 하는 갱신은 #[shard]로 표시한 컴포넌트가 담당한다.

최소 형태는 이렇다. 아래는 공식 README의 시작 예제를 최소한으로 옮긴 것이다.

#[page("/")]
async fn home() -> Result {
    view! { <h1>"Hello, World!"</h1> }
}

라우트가 함수 위 속성 하나로 끝난다. 라우터 등록 코드도, 핸들러 시그니처를 맞추는 작업도 없다. 발표 글은 모듈 구조에서 라우트 트리를 유추하는 방식도 함께 제공한다고 밝힌다.

여기서 중요한 것은 확인된 것과 확인되지 않은 것을 갈라 두는 일이다.

2. 「API 계층 제거」가 없애는 것과 옮기는 것

이제 본론이다. 화면 하나를 그리기 위해 오늘날 흔히 쓰는 구조를 떠올려 보자. 백엔드에 엔드포인트를 만들고, 응답 DTO를 정의하고, 프론트에 같은 모양의 타입을 다시 선언하고, 페치 함수를 감싸고, 로딩·에러 상태를 컴포넌트에 배선한다. 이 배선 작업이 화면당 반복된다.

Topcoat의 주장은 이 반복이 서버와 브라우저 사이에 경계선이 있기 때문에 생긴다는 것이다. 경계선이 있으니 직렬화가 필요하고, 직렬화가 필요하니 타입이 두 번 선언되고, 타입이 두 벌이니 드리프트가 생긴다. 컴포넌트를 서버에서 실행하면 이 사슬이 통째로 끊긴다. 논리는 정확하다.

// 컴포넌트 안에서 바로 조회한다 — 별도 엔드포인트가 없다
#[component]
async fn user_profile(cx: &Cx, user_id: &str) -> Result {
    let user = load_user(cx, user_id).await?;
    view! { <div>{user.name}</div> }
}

문제는 그 경계선이 직렬화만 하고 있던 게 아니라는 점이다. HTTP 엔드포인트는 보일러플레이트인 동시에 여러 관심사가 붙어 있던 게시판이었다. 게시판을 떼면 붙어 있던 종이들은 사라지는 게 아니라 바닥에 떨어진다.

표의 아래 절반을 하나씩 풀어 본다.

2.1 인가 — 장점과 위험이 같은 뿌리에서 나온다

발표 글은 컴포넌트 안에서 데이터를 직접 보호할 수 있다는 점을 장점으로 제시한다. 코드베이스의 완전히 다른 곳에 있는, 실행될지 안 될지 모르는 미들웨어에 기대는 것보다 낫다는 논리다. 실무 경험상 이 지적은 타당하다. 인가 미들웨어가 라우트 등록 순서 때문에 특정 경로에서 건너뛰어지는 사고는 흔하다.

그런데 같은 성질이 반대 방향으로도 작동한다. 검사 지점이 미들웨어 한 곳일 때 감사 범위는 파일 하나다. 컴포넌트마다 검사할 때 감사 범위는 컴포넌트 전수다. 놓칠 확률이 지점 수에 비례해 늘어난다는 뜻은 아니지만, 놓친 것을 찾는 비용은 확실히 늘어난다. 「이 조회는 권한 검사를 거쳤는가」를 사람이 눈으로 확인해야 하는 곳이 열 배가 된다.

실무적으로는 두 방식 중 하나를 골라야 한다. 데이터 접근 함수 자체를 권한 컨텍스트 없이는 호출할 수 없게 타입으로 강제하거나, 컴포넌트 안에서 원시 DB 접근을 금지하고 검사가 내장된 도메인 함수만 부르도록 규약을 세우는 것이다. 두 번째가 현실적이고, 이는 곧 9장에서 말할 도메인 크레이트 분리와 같은 결론으로 이어진다.

2.2 조회 횟수 — 메모이제이션이 막는 것과 못 막는 것

컴포넌트가 각자 DB를 조회하면 렌더 트리를 따라 쿼리가 늘어난다. Topcoat은 요청 수준 메모이제이션을 제공하며, 발표 글은 이를 React의 캐시 개념에서 영감을 얻었다고 밝힌다. 같은 요청 안에서 동일한 조회가 반복되면 한 번만 실행한다는 뜻이다.

이 장치는 중복을 막는다. 다수는 막지 못한다. 목록 화면에서 행마다 컴포넌트가 각자 다른 키로 조회하면 그것은 중복이 아니라 서로 다른 N개의 조회다. 메모이제이션은 여기에 관여하지 않는다. 전통적인 N+1 문제가 SQL 계층에서 뷰 계층으로 자리를 옮긴 형태이며, 해법도 전통적인 것과 같다. 부모에서 한 번에 모아 조회해 자식에 내려주거나, 데이터로더 계열의 배칭을 도입하는 것이다.

여기서 실질적인 위험은 성능 자체가 아니라 발견 시점이다. 엔드포인트가 있으면 느린 API가 대시보드에 이름으로 뜬다. 컴포넌트 내부 조회는 이름이 없다. 도입한다면 컴포넌트 단위 트레이싱을 초기부터 붙여 두는 편이 낫고, 이는 「보일러플레이트가 줄었다」는 이익의 일부를 되돌려주는 비용이다.

2.3 캐시 — URL은 공짜 캐시 키였다

덜 논의되지만 실무에서 크게 다가오는 항목이다. GET /api/products/123은 그 자체로 CDN과 리버스 프록시와 브라우저가 공유하는 캐시 키다. 이 키는 아무도 설계하지 않았는데 존재했다. HTTP가 준 것이다.

컴포넌트가 내부에서 조회하면 이 키가 없다. 서버 렌더링 결과 전체를 페이지 단위로 캐싱하거나, 애플리케이션 계층에서 자체 캐시를 설계해야 한다. 개인화된 화면이 섞이면 페이지 단위 캐싱은 곧바로 어려워진다. Topcoat의 로드맵에 정적 내보내기가 들어 있는 것은 이 지점의 수요를 인지하고 있다는 신호로 읽히지만, 2026년 7월 말 기준으로는 로드맵 항목이다.

3. shard — 사라진 게 아니라 자동 생성된 경계

이 글에서 가장 강조하고 싶은 대목이다. 클라이언트 상태가 바뀌었을 때 서버가 UI의 일부를 다시 그려야 하는 경우, Topcoat은 #[shard]로 표시한 컴포넌트를 쓴다. 그리고 발표 글의 설명에 따르면 shard는 엔드포인트를 노출한다.

즉 API 계층은 없어진 것이 아니라 손으로 쓰지 않게 된 것이다. HTTP 경계는 그대로 있고, 그 위의 요청·응답도 그대로 오간다. 달라진 것은 그 경계를 사람이 선언하지 않고 매크로가 생성한다는 점이다.

  • 이것은 나쁜 설계가 아니다. 오히려 좋은 설계다. 반복 작업을 도구가 하는 것은 컴퓨터를 쓰는 이유 그 자체다.
  • 다만 보안 검토의 대상이 사라지지는 않는다. 생성된 엔드포인트도 인터넷에 열린 엔드포인트다. 무엇이 어떤 파라미터로 노출되는지는 여전히 알아야 한다.
  • 레이트 리밋, 남용 방지, 인증 토큰 검증 같은 정책은 자동 생성된 경계에도 적용돼야 한다. 손으로 쓴 엔드포인트라면 자연스럽게 붙였을 것들이다.
  • 「API가 없다」고 믿고 API 게이트웨이 정책을 세우지 않는 것이 실제 위험이다. 추상화가 존재를 숨겼을 뿐 존재를 없애지는 않았다.

보일러플레이트가 줄어들 때 함께 사라지는 것이 하나 더 있다. 보일러플레이트가 수행하던 표지판 기능이다. 엔드포인트를 손으로 쓰는 행위는 「여기가 신뢰 경계다」라는 사실을 개발자에게 강제로 인식시킨다. 그 행위가 사라지면 인식도 함께 흐려진다. 이것은 Topcoat만의 문제가 아니라 서버 액션·RPC 자동 생성 계열 전반이 공유하는 구조적 성질이다.

4. 클라이언트 상호작용이 늘어날 때 부딪히는 벽

Topcoat의 클라이언트 모델은 두 층으로 되어 있다. 서버 왕복 없이 브라우저에서 끝나는 것과, 서버가 다시 그려 부분 교체하는 것이다. 앞의 것은 signal 선언과 $(...) 표현식으로, 뒤의 것은 shard로 처리한다. 토글이나 드롭다운 열기 같은 로컬 상태는 왕복이 필요 없다.

상호작용이 단순할 때 이 모델은 우아하다. 문제는 밀도가 올라갈 때다.

  • 부분집합의 벽: $(...)는 타입 검사된 Rust 표현식의 부분집합을 JavaScript로 옮긴다. 부분집합 밖으로 나가면 컴파일 시점에 막힌다. 조용히 깨지는 것보다는 훨씬 낫지만, 복잡한 클라이언트 로직에서는 이 벽을 자주 만나게 된다.
  • 왕복의 벽: 부분집합 밖의 로직은 shard로 넘어간다. 그 순간 네트워크 지연이 상호작용 지연이 된다. 드래그로 도형을 옮기거나 캔버스를 그리는 상호작용에는 구조적으로 불리하다.
  • 공식 문서가 인정한 벽: 발표 글은 클라이언트 반응성 시스템이 아직 개발 초기 단계이며 몇 가지 제약이 있다고 명시한다. 그리고 그동안 htmx와 Alpine.js 통합을 쓸 수 있다고 안내한다.
  • 모델 혼재의 벽: 위 안내를 따르면 한 화면에 세 가지 상호작용 모델이 섞일 수 있다. Rust의 $(), htmx의 HTML 속성, Alpine의 지시자다. 「행동의 지역성」을 설계 원칙으로 내건 프레임워크가 정작 복잡한 화면에서 지역성을 잃는 역설이 생긴다.
  • 오프라인의 벽: 서버가 진실의 원천인 구조에서 오프라인 우선이나 낙관적 UI는 별도의 설계를 요구한다. 프레임워크가 대신 해 주지 않는다.

공평하게 덧붙이면, 프레임워크가 자기 핵심 기능의 한계를 문서에 적고 대안을 안내하는 것은 신뢰의 신호다. 초기 프로젝트가 흔히 하는 과장 대신 현재 상태를 밝혔다. 다만 도입을 검토하는 쪽에서는 이 문장을 액면 그대로 받아들여야 한다. 「곧 개선될 것」이라는 기대를 일정에 넣으면 안 된다.

5. 서버 렌더링 회귀 — 같은 문제를 푸는 다른 답들

Topcoat이 갑자기 나타난 아이디어가 아니라는 점을 짚어야 공정한 평가가 된다. 「데이터는 서버에 있는데 왜 로직을 클라이언트로 옮겨야 하는가」라는 질문은 최근 몇 년 동안 여러 생태계에서 각자의 답을 냈다. 개념적 차이만 정리한다.

  • Phoenix LiveView(Elixir): 상태를 서버의 지속 연결된 프로세스에 두고, 변경분을 소켓으로 밀어 준다. 상호작용마다 왕복이 있지만 연결이 유지되므로 지연이 작다. 대신 서버가 사용자 수만큼 상태를 들고 있어야 한다. Topcoat의 요청 단위 모델과는 자원 사용 성격이 다르다.
  • htmx: 서버가 HTML 조각을 반환하고, 클라이언트는 어디를 교체할지 속성으로만 선언한다. 프레임워크라기보다 규약에 가깝다. Topcoat의 shard가 개념적으로 여기에 가장 가깝고, 실제로 Topcoat은 htmx 통합을 별도 크레이트로 제공한다.
  • 서버 컴포넌트 계열: 컴포넌트를 서버에서 도는 것과 클라이언트에서 도는 것으로 나누고, 서버 쪽은 데이터에 직접 접근한다. 문제의식이 Topcoat의 async 컴포넌트와 사실상 같다. 차이는 클라이언트 런타임을 여전히 배송하느냐다. Topcoat은 클라이언트 빌드 단계 자체를 없애는 쪽을 택했다.
  • 공통 원인: 세 방향 모두 같은 압력에서 나왔다. 클라이언트로 옮긴 로직의 비용(번들 크기, 하이드레이션, 타입 이중 선언, 빌드 파이프라인)이 얻는 것보다 커진 지점이 있었다는 인식이다.

Topcoat의 자리를 한 문장으로 놓으면, htmx의 서버 중심 모델을 Rust의 타입 시스템 안으로 끌어들이고, 클라이언트 빌드 단계까지 없앤 시도다. 새로운 발상이라기보다 기존 발상들의 조합을 Rust 생태계로 가져온 것에 가깝고, 그 조합 자체가 이 프로젝트의 기여다.

6. 이 방식이 맞는 앱과 맞지 않는 앱

기술 선택은 프레임워크의 우열이 아니라 앱의 성질로 결정된다. 아래 표는 이 글의 분석을 판단 기준으로 정리한 것이다.

축맞는 쪽맞지 않는 쪽
화면 성격폼·목록·상세·대시보드 중심의 업무 화면캔버스·에디터·실시간 협업처럼 상호작용이 연속적인 화면
클라이언트 수웹 하나모바일 앱·파트너 연동 등 소비자가 둘 이상

표의 왼쪽 열에 여러 개가 걸린다면 진지하게 검토할 가치가 있다. 오른쪽에 하나라도 강하게 걸린다면 그 하나가 다른 장점 전부를 상쇄할 가능성이 크다. 특히 클라이언트 수 항목은 되돌리기가 가장 비싸다. 웹 전용으로 만들어 둔 뒤 모바일 앱 요구가 들어오면 API 계층을 그때 새로 만들어야 하는데, 그 시점의 도메인 로직은 이미 컴포넌트 안에 흩어져 있을 확률이 높다.

7. Rust를 웹에 쓸 때의 현실적 트레이드오프

프레임워크 이야기에서 한 층 내려간다. 언어 선택 자체의 문제다. Rust를 서버에 쓰는 것과 기존 스택에서 Rust로 옮기는 판단은 이미 여러 조직이 겪은 주제이지만, 웹 화면 계층까지 Rust로 올리는 것은 성질이 조금 다르다.

7.1 얻는 것

  • 타입 시스템이 한 벌: DB 행에서 HTML 속성까지 같은 컴파일러가 검사한다. 백엔드 타입과 프론트 타입을 맞추는 코드 생성 파이프라인이 통째로 사라진다.
  • 런타임 오류의 상당수가 컴파일 오류로 이동: 필드 이름 오타나 nullable 처리 누락처럼 배포 후에 발견되던 것들이 빌드에서 걸린다.
  • 배포 산출물이 단순: Node 툴체인도 WASM 번들도 없는 구성이면 컨테이너 이미지와 CI 단계가 눈에 띄게 짧아진다.
  • 메모리 사용 예측 가능성: GC 정지가 없는 런타임은 사이드카 밀집 배치나 저사양 인스턴스에서 유리하다.

7.2 치르는 것

  • 피드백 루프: 웹 UI 개발은 초 단위 반복이 생명인데 Rust 빌드는 그 리듬과 잘 맞지 않는다. 매크로가 무거운 프레임워크는 특히 그렇다. Topcoat의 구체적인 빌드 시간 수치는 공식 자료에서 확인되지 않았으므로 이 글에서는 수치를 제시하지 않는다. 도입 검토라면 실제 프로젝트 규모로 직접 측정하는 편이 유일하게 믿을 만한 방법이다.
  • 매크로 층의 진단 품질: view!, #[page], $()가 모두 매크로다. Rust의 최대 강점 중 하나가 컴파일러 진단 메시지인데, 매크로 안에서 난 오류는 원래 위치를 정확히 가리키지 못할 수 있다.
  • 0.x 표면적: 30개 넘는 크레이트로 구성된 워크스페이스에서 파괴적 변경이 오면 영향 범위가 넓다. 버전 올릴 때마다 화면 코드 전반을 손봐야 할 수 있다.
  • 툴체인 최신성 요구: rust-version 1.95는 사내 표준 빌드 이미지가 보수적인 조직에서 실제 장애물이 된다.

정리하면 Rust를 웹에 쓰는 결정은 배포 이후의 안정성을 개발 중의 속도와 맞바꾸는 거래다. 운영 부담이 크고 배포 주기가 긴 시스템에서는 좋은 거래이고, 화면을 매일 바꿔야 하는 제품 초기에는 나쁜 거래가 되기 쉽다.

8. 팀 역량과 채용 — 가장 비싼 항목

기술 문서가 거의 다루지 않지만 실제로는 가장 큰 비용이 여기서 발생한다.

  • 인력 풀의 이중 협소: Rust 개발자 풀은 이미 좁고, 그중 웹 화면 작업을 하려는 사람은 더 좁다. 여기에 신생 프레임워크 경험까지 요구하면 사실상 채용 조건이 아니라 교육 계획이 된다.
  • 학습 곡선의 주체는 프레임워크가 아니라 언어: 이미 Rust로 서버를 운영하는 팀에게 Topcoat의 추가 학습 비용은 크지 않다. 반대로 Rust를 안 쓰는 팀에게 이 결정은 프레임워크 도입이 아니라 언어 도입이다. 두 결정을 하나로 묶어서 논의하면 판단이 왜곡된다.
  • 버스 팩터: 사내에서 Rust를 읽을 수 있는 사람이 한둘이면, 그 인원이 이탈하는 순간 서비스 전체가 읽히지 않는 코드가 된다. 프레임워크가 신생일수록 외부에서 사람을 데려와 메우기도 어렵다.
  • AI 보조의 역설: 발표 글은 인간과 AI 모두 작은 영역에서 추론을 더 잘한다는 점을 설계 근거로 든다. 방향은 타당하지만, 신생 프레임워크는 학습 데이터가 거의 없어서 코딩 도구의 보조 효과가 널리 쓰이는 스택보다 훨씬 약하다. 설계 의도와 현실이 당분간 반대로 간다.
  • 온보딩 자료의 부재: 스택오버플로 답변, 블로그 글, 강의, 사내 선례가 모두 없는 상태에서 시작한다. 문제에 막혔을 때 기댈 곳이 공식 문서와 저장소 이슈뿐이라는 뜻이다.

이 항목들은 프레임워크의 품질과 무관하다. 아무리 잘 만든 도구여도 조직이 감당할 수 없으면 도입은 실패한다. 신생 프레임워크 평가에서 기술적 완성도만 보는 것이 흔한 실수이며, 다른 신생 프레임워크를 검토했던 글에서도 같은 결론에 도달했다.

9. 도입 전 확인할 것 — 라이선스·성숙도·탈출 경로

그럼에도 검토하기로 했다면, 아래 여섯 가지는 코드를 쓰기 전에 확인하는 편이 낫다.

  • 라이선스 전이 확인: 본체는 MIT로 확인됐다. 다만 워크스페이스가 여러 크레이트로 나뉘어 있고 각각이 외부 의존성을 가진다. 사내 정책이 엄격하다면 cargo deny 같은 도구로 전이 의존성 라이선스를 한 번 훑어 두는 것이 안전하다.
  • 성숙도 표기를 그대로 받아들이기: README의 「experimental, expect breaking changes」는 겸양 표현이 아니라 사양이다. 0.5.0이 발표 닷새 만에 나왔다는 사실도 같은 방향의 신호다.
  • 버전 고정 정책: 0.x 구간에서는 마이너 버전이 파괴적 변경을 담을 수 있다. Cargo.lock을 커밋하고, 업그레이드는 별도 작업으로 잡아 두는 것이 기본이다.
  • 도메인 크레이트 분리: 이것이 사실상 유일한 탈출 경로다. 비즈니스 규칙과 데이터 접근을 Topcoat에 의존하지 않는 별도 크레이트에 두고, 컴포넌트는 그 크레이트의 함수만 호출하게 한다. 뷰는 매크로 DSL이라 옮길 수 없지만, 도메인이 분리돼 있으면 최악의 경우에도 화면만 다시 만들면 된다.
  • 탈출 경로와 장점의 충돌 인식: 그런데 Topcoat이 내세우는 최대 장점은 「컴포넌트가 DB를 직접 조회한다」이다. 이를 그대로 따르면 도메인 분리가 깨진다. 장점을 최대한 누리는 방식과 탈출 비용을 낮추는 방식이 정면으로 충돌한다. 이 긴장을 알고 어느 쪽으로 갈지 팀이 먼저 정해야 한다.
  • 외부 계약면 확보 시점: 로드맵에 OpenAPI 엔드포인트가 있다. 모바일이나 파트너 연동이 예정돼 있다면 이 항목이 들어오는 시점이 도입 시점을 결정한다. 2026년 7월 말 기준으로는 아직 로드맵이다.

네 번째와 다섯 번째 항목이 이 장의 핵심이다. 프레임워크가 주는 편의를 최대로 쓸수록 그 프레임워크에서 나오기 어려워진다는 것은 Topcoat만의 성질이 아니다. 다만 「API 계층을 없앤다」는 설계는 그 결합도를 데이터 접근 계층까지 끌어내리기 때문에, 결합의 깊이가 일반적인 뷰 프레임워크보다 깊다.

10. 언제 쓰지 말아야 하는가

지금까지의 분석을 뒤집어 정리한다. 아래 중 하나라도 해당하면 2026년 7월 말 시점에서는 다른 선택을 권한다.

  • 팀에 Rust를 상시 유지보수할 수 있는 인원이 두 명 미만인 경우. 한 명은 버스 팩터가 아니라 단일 장애점이다.
  • 모바일 앱이나 파트너 API 같은 두 번째 소비자가 이미 있거나 12개월 안에 예정된 경우. API 계층을 없앴다가 다시 만드는 일이 된다.
  • 상호작용 밀도가 높은 화면이 제품의 핵심인 경우. 에디터, 캔버스, 실시간 협업, 오프라인 우선 앱이 여기에 속한다.
  • SLA가 걸려 있거나 외부 감사를 받는 시스템인 경우. 0.x의 파괴적 변경 주기를 감당할 여유가 없다.
  • Rust 도입과 프레임워크 도입을 동시에 결정해야 하는 경우. 두 개의 큰 변경을 한 번에 하면 실패 원인을 분리할 수 없다.
  • 마감이 정해진 재작성 프로젝트인 경우. 신생 프레임워크의 미지수와 고정된 마감은 함께 두면 안 되는 조합이다.

반대로 먼저 해 볼 만한 자리도 분명히 있다. 사내 관리 도구, 운영 대시보드, 이미 Rust 서비스가 있는 팀의 보조 화면처럼 실패 비용이 낮고 사용자 수가 통제되는 곳이다. 이런 자리에서 한 분기쯤 굴려 보면 위 항목들이 우리 조직에서 실제로 어떻게 작동하는지 데이터가 쌓인다. 그 데이터 없이 주력 서비스에 올리는 것이 위험한 것이지, 도구 자체가 위험한 것은 아니다.

결론: 경계선을 지우는 결정은 되돌리기 어렵다

Topcoat은 잘 정리된 문제 인식 위에 서 있다. 화면 하나를 위해 엔드포인트를 만들고 타입을 두 번 선언하고 페치를 감싸는 작업이 반복이라는 지적은 옳다. 그 반복을 서버 렌더링과 async 컴포넌트로 걷어내는 접근도 최근 몇 년간 여러 생태계가 각자 도달한 방향과 일치한다. Tokio 팀이 만들었다는 점, MIT 라이선스라는 점, 그리고 README가 스스로 실험 단계임을 밝힌 정직함은 모두 긍정적인 신호다.

다만 이 글이 확인한 것은 그 접근이 제거가 아니라 재배치라는 사실이다. 인가는 컴포넌트로 흩어졌고, 캐시 키는 사라졌고, 관측 지점은 이름을 잃었고, shard는 엔드포인트를 여전히 노출한다. 보일러플레이트가 줄어든 만큼 「여기가 경계다」라고 알려 주던 표지판도 함께 줄었다. 이 거래가 이익인지 손해인지는 프레임워크가 아니라 앱의 성질과 팀의 상태가 결정한다.

그리고 이 결정은 되돌리기 어렵다. 데이터 접근이 뷰 계층으로 내려간 코드베이스에서 나중에 API 계층을 복원하려면, 화면을 다시 만드는 것으로 끝나지 않고 도메인 로직을 흩어진 자리에서 다시 모아야 한다. 그래서 도입을 검토한다면 첫 화면을 쓰기 전에 도메인 크레이트를 먼저 떼어 두는 편이 낫다. 프레임워크가 주는 가장 큰 편의를 일부 포기하는 선택이지만, 0.x 단계의 도구를 다룰 때 치르는 합리적인 보험료다.

정리하면 이렇다. 2026년 7월 말 시점의 Topcoat은 지켜볼 가치가 있고, 낮은 위험의 자리에서 시험해 볼 만하며, 주력 서비스에 올리기에는 이르다. 다음 분기의 판단 재료는 두 가지다. 클라이언트 반응성 시스템의 제약이 어디까지 해소되는지, 그리고 OpenAPI 엔드포인트처럼 외부 계약면을 다시 여는 로드맵 항목이 실제로 들어오는지다.
