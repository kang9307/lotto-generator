어느 칸이 틀렸는지 화면이 못 찾는다 - 검증 오류에 필드 경로를 붙이는 법

점 표기·JSON Pointer·대괄호를 직접 구현해 돌려 본 이스케이프, 배열 인덱스, 그리고 표기법이 계약인 이유

2026-08-01 개발/인프라

서론: 빨간 줄이 폼 전체에 그어졌다

주문서를 제출했더니 서버가 422와 함께 「입력이 잘못됐습니다」 한 줄을 돌려줬다. 화면은 그 한 줄로 무엇을 해야 할지 정하지 못했고, 결국 열네 개 입력칸 전부에 빨간 테두리를 둘렀다. 사용자는 멀쩡한 칸 여덟 개를 포함해 처음부터 다시 훑기 시작한다. 서버는 정확히 여섯 곳이 틀렸다는 것을 알고 있었는데, 그 정보가 응답을 건너오지 못했다.

이 상황을 「오류 메시지가 불친절하다」로 요약하면 문제를 놓친다. 메시지의 친절함은 부차적이다. 핵심은 검증 오류 응답을 실제로 소비하는 쪽이 사람이 아니라 화면이라는 사실이다. 사용자가 응답 본문을 읽는 일은 없다. 응답을 읽는 것은 코드이고, 그 코드가 해야 하는 일은 단 하나다. 어느 입력 요소에 표시를 붙일지 결정하는 것.

그 결정이 가능하려면 오류마다 「어디」가 붙어 있어야 한다. 그리고 그 「어디」는 사람이 읽는 문장이 아니라 화면이 자기 입력 요소와 대조할 수 있는 기계용 좌표여야 한다. 여기서부터 표기법 문제가 시작된다. 같은 위치를 items.2.qty로 쓸 수도, /items/2/qty로 쓸 수도, items[2].qty로 쓸 수도 있다. 셋 다 사람 눈에는 똑같이 읽힌다. 그런데 파싱하는 코드 입장에서는 전혀 다른 물건이고, 어떤 필드 이름 앞에서는 셋 중 둘이 조용히 무너진다.

이 글은 그 지점을 다룬다. 스키마 검증기를 직접 구현해 중첩 세 단계와 배열이 섞인 요청을 통과시키고, 나온 오류를 세 가지 표기법으로 찍어 다시 파싱해 원본과 비교했다. 이스케이프가 깨지는 자리, 배열 인덱스가 밀려 엉뚱한 칸에 빨간 줄이 가는 자리, 메시지에 필드 이름을 넣었을 때 번역이 무너지는 자리를 전부 실행으로 확인했다. 결론을 미리 말하면, 표기법은 취향이 아니라 계약이다.

실행 환경. 아래 출력은 모두 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 런타임은 Node.js v22.16.0 (win32), 셸은 GNU bash 5.2.37 (MSYS2/MinGW64)다. 검증기와 실험 스크립트는 모두 파일로 저장해 실행했고, 저장소 바깥의 임시 작업 폴더에서만 돌렸다. 히어독으로 코드를 넘기면 따옴표와 역슬래시가 조용히 변형되기 때문이다.

예제는 전부 가상이다. 등장하는 주문 API, 필드 이름, 상품 코드, 항목 식별자는 설명을 위해 지어낸 것이다. 특정 검증 라이브러리를 고르거나 평가하지 않는다. 이 글에서 쓰는 검증기는 논점을 드러내려고 직접 만든 200줄짜리 장난감이며, 어떤 도구를 쓰든 바뀌지 않는 것은 응답의 모양이라는 것이 이 글의 전제다.

이 글이 다루지 않는 것. 오류 코드 자체를 어떻게 이름 짓고 어떻게 늘려 갈지는 오류 코드 체계를 만든다는 것에서 다뤘다. 여기서는 코드가 이미 있다고 보고 「어디」에만 집중한다. 목록 응답의 좌표 문제, 즉 페이지를 넘길 때 항목이 밀리는 이야기는 오프셋 페이징이 구조적으로 못 하는 것에 있다.

1. 재현 - 「입력이 잘못됐습니다」가 화면에 남기는 것

1-4에 눈여겨볼 지점이 하나 있다. items.2.options.0.value는 본문에서 값을 꺼내면 undefined가 나온다. 필수 필드가 아예 없기 때문이다. 즉 경로가 가리키는 곳에 값이 없어도 경로 자체는 유효하다. 경로는 값의 주소가 아니라 자리의 주소다. 이 구분을 놓치면 클라이언트가 「본문에서 못 찾은 경로는 버린다」는 규칙을 만들었다가 필수 누락 오류를 통째로 삼키게 된다.

  • 서버는 실패한 규칙과 위치를 이미 알고 있었다. 문제는 계산이 아니라 전달이다
  • 경로 없는 응답에서 화면이 할 수 있는 최선은 모두 표시이고, 그것은 표시하지 않는 것과 사용성 면에서 거의 같다
  • 깊이 5짜리 경로가 실제로 나온다. 배열 안 객체 안 배열 안 객체는 특별한 구조가 아니라 평범한 주문서다
  • 검증기는 실패를 문자열이 아니라 세그먼트 배열로 모았다. 인쇄는 마지막 단계로 미뤘고, 그래서 표기법을 바꾸는 데 검증 로직을 건드릴 필요가 없었다

평범한 경로에서는 셋 다 아무 문제가 없다. 인쇄한 뒤 다시 파싱해 원본 세그먼트와 비교하는 왕복 시험을 돌려도 전부 통과한다.

3. 이스케이프 함정 - 이름에 점·슬래시·대괄호가 들어가면

여기가 표기법 선택이 실제로 갈리는 지점이다. JSON 객체의 키에는 거의 아무 문자나 들어갈 수 있다. 그리고 실무 본문에는 그런 키가 흔하다. 버전 문자열을 키로 쓰는 설정 맵, 헤더 이름을 그대로 키로 쓰는 딕셔너리, 사용자가 입력한 태그 이름, 연도를 키로 쓰는 집계 결과 같은 것들이다. 아홉 가지 사례를 만들어 세 표기법으로 인쇄한 뒤 다시 파싱했다.

점 표기 5건, 대괄호 4건, JSON Pointer 8건. 차이의 원인은 능력이 아니라 규칙의 유무다. 점 표기와 대괄호에는 구분자를 이름 안에 넣었을 때 어떻게 표시할지에 대한 규정이 아예 없다. 그러니 인쇄 단계에서 정보가 사라지고, 파싱 단계에서 복구할 방법이 남지 않는다.

무너질 때 클라이언트가 실제로 무엇을 받게 되는지 보면 심각성이 분명해진다.

--- 3-3. what the client actually receives when a notation collapses ---
  dot in key
    server meant : ["meta","app.version"]
    printed as   : meta.app.version
    client reads : ["meta","app","version"]
    segments     : 2 -> 3
  digits as key
    server meant : ["byYear","2024","total"]
    printed as   : byYear.2024.total
    client reads : ["byYear",2024,"total"]
    segments     : 3 -> 3
  dot plus index
    server meant : ["rows",3,"unit.price"]
    printed as   : rows.3.unit.price
    client reads : ["rows",3,"unit","price"]
    segments     : 3 -> 4
  key that looks like a path
    server meant : ["fields","items.0.qty"]
    printed as   : fields.items.0.qty
    client reads : ["fields","items",0,"qty"]
    segments     : 2 -> 4

--- 3-4. bracket notation on a key that contains a bracket ---
  server meant : ["tags","group[a]"]
  printed as   : tags.group[a]
  client reads : ["tags","group",null]
  the printer has no escape rule for ] at all, so the string is not recoverable

세그먼트 개수가 2에서 4로 늘어나는 사례가 가장 나쁘다. 클라이언트는 자기가 잘못 읽었다는 사실조차 알 수 없다. fields.items.0.qty는 문법적으로 완벽한 경로처럼 보이고, 파싱도 성공하고, 예외도 나지 않는다. 그저 없는 자리를 가리킬 뿐이다. 3-4의 대괄호 사례는 더 노골적이다. 이름 안의 닫는 괄호를 만난 파서가 null을 세그먼트로 뱉었다. 인쇄기에 탈출 규칙이 없어서 문자열 자체가 복구 불가능해진 것이다.

JSON Pointer는 이 지점에서 다르게 행동한다. 규칙이 문서에 적혀 있기 때문이다.

--- 3-5. the only notation with a written escape rule ---
  key "x-forwarded/for"    pointer /headers/x-forwarded~1for  back "x-forwarded/for"    equal true
  key "draft~2"            pointer /tags/draft~02             back "draft~2"            equal true
  key "a~/b"               pointer /tags/a~0~1b               back "a~/b"               equal true

--- 3-6. and the one it still cannot settle by itself ---
  object with a numeric KEY : {"byYear":{"2024":{"total":0}}}
  pointer                   : /byYear/2024/total
  parsed with number guess  : ["byYear",2024,"total"]
  parsed as pure strings    : ["byYear","2024","total"]
  RFC 6901 says: try the string key first, treat it as an index only for arrays.
  a client that guesses by shape alone will mislabel numeric object keys.

슬래시는 ~1로, 물결표는 ~0으로 바뀐다. 세 번째 줄이 규칙의 정교함을 보여 준다. a~/b는 a~0~1b가 되고 정확히 되돌아왔다. 되돌릴 때 순서가 중요하다. ~1을 먼저 슬래시로 바꾸고 그다음 ~0을 물결표로 바꿔야 한다. 순서를 뒤집으면 ~01 같은 입력에서 결과가 달라진다. RFC 6901이 이 순서를 명시하는 이유다.

그래도 JSON Pointer가 혼자 해결하지 못하는 것이 하나 남는다. 숫자로 된 객체 키다. 연도를 키로 쓰는 집계 객체에서 /byYear/2024/total을 받은 클라이언트가 「숫자처럼 생겼으니 인덱스」라고 판단하면 틀린다. RFC 6901의 규정은 명확하다. 대상이 객체면 그 문자열을 이름으로 취급하고, 배열일 때만 인덱스로 해석한다. 즉 판정 기준은 문자열의 생김새가 아니라 그 자리에 있는 값의 타입이다.

4. 배열 인덱스의 수명 - 항목 하나가 사라지면

이스케이프를 해결해도 배열에는 다른 종류의 문제가 남는다. 인덱스는 요청을 보낸 순간의 배열 상태에만 유효한 좌표라는 것이다. 장바구니 네 줄을 만들고, 세 번째 줄에 문제를 심고, 응답이 오는 사이에 사용자가 두 번째 줄을 지우는 상황을 재현했다.

이 문제는 타이밍 사고처럼 보이지만 그렇지 않다. 인덱스가 정체성을 갖고 있지 않은 것이 원인이다. 항목마다 클라이언트가 붙인 고유 식별자를 요청에 함께 실어 보내고, 서버가 그것을 오류에 되돌려 주면 문제가 사라진다.

안정 식별자로 바꾸니 오배치가 2건에서 0건이 됐다. 항목이 삭제됐다면 그 오류는 붙일 곳이 없다는 사실이 명확히 드러나므로 조용히 버려도 안전하다. 인덱스는 그 판단을 못 한다. 인덱스는 항상 「누군가」를 가리키고, 그 누군가가 원래 대상인지 알 방법이 없다.

4-7이 가장 자주 놓치는 전제다. 서버는 클라이언트가 보내지 않은 식별자를 되돌려 줄 수 없다. 요청 본문에 sku와 qty만 들어 있으면 서버가 echo할 수 있는 것도 그 둘뿐이다. 즉 안정 식별자는 응답 설계가 아니라 요청 스키마 설계의 문제다. 오류 응답에 그것을 넣기로 결정하는 순간, 요청 쪽 계약도 함께 바뀐다.

  • 인덱스 경로는 버리지 말고 함께 보내는 것이 낫다. 로그와 서버 측 디버깅에서는 인덱스가 여전히 편하다
  • 두 좌표를 같이 실으면 응답이 117바이트에서 193바이트로 늘어난다. 오류 하나당 38바이트다
  • 식별자는 서버가 만들어 준 것이어도 되고 클라이언트가 만든 임시값이어도 된다. 요청과 응답 사이에 변하지 않기만 하면 된다
  • 클라이언트가 항목을 추가했을 때도 같은 문제가 생긴다. 삭제만 조심하면 되는 문제가 아니다
  • 항목 순서를 사용자가 정렬할 수 있는 화면이라면 인덱스는 처음부터 쓸 수 없다

5. 첫 오류에서 멈출까, 전부 모을까

위치를 붙이기로 했다면 다음 결정은 개수다. 첫 실패에서 즉시 반환할 것인가, 전부 모아 한 번에 줄 것인가. 같은 본문을 두 방식으로 처리해 봤다. 첫 오류만 주는 서버를 상대로 사용자가 지적받은 칸만 하나씩 고쳐 나가는 과정을 그대로 돌렸다.

--- 5-1. stop at the first failure: how many round trips to a clean form ---
  trip 1  server says: orderId                   (pattern)
  trip 2  server says: customer.name             (minLength)
  trip 3  server says: customer.contact.email    (pattern)
  trip 4  server says: items.2.sku               (minLength)
  trip 5  server says: items.2.qty               (min)
  trip 6  server says: items.2.options.0.value   (required)
  total round trips : 6

--- 5-2. collect everything: one round trip ---
  errors returned   : 6
  total round trips : 1

--- 5-3. three response shapes for the same six failures ---
  flat path list      302 B    client walk = one loop
  plus params         459 B    client walk = one loop
  plus english text   859 B    client walk = one loop
  nested tree         217 B    client walk = recursive

  the nested tree, printed:
{"orderId":["pattern"],"customer":{"name":["minLength"],"contact":{"email":["pattern"]}},"items":{"2":{"sku":["minLength"],"qty":["min"],"options":{"0":{"value":["required"]}}}}}
  note: to find a leaf the client must recurse, and array levels look like objects.

여섯 번 대 한 번이다. 사용자 입장에서 이것은 여섯 번의 제출과 여섯 번의 대기다. 폼이 길수록 이탈률이 올라가는 전형적인 형태이고, 서버 입장에서도 요청이 여섯 배다. 검증에 부수효과가 없다면 모아서 주는 편이 거의 항상 낫다.

5-3의 중첩 트리 형태는 흥미로운 함정이다. 217바이트로 가장 작고, 언뜻 구조가 예쁘다. 그런데 배열 단계가 객체처럼 보인다. "items":{"2":{...}}에서 2는 인덱스인데 키처럼 직렬화됐다. 3절의 숫자 키 문제가 여기서 그대로 재현된다. 게다가 클라이언트는 잎을 찾기 위해 재귀를 돌아야 한다. 평평한 목록이 크기 면에서 약간 손해를 보는 대신, 반복문 하나로 끝난다.

모아 주기로 했다면 크기가 어디까지 자라는지 확인해야 한다.

항목 1,000개짜리 일괄 요청에서 오류가 2,000개가 되고, 사람이 읽을 문장까지 넣으면 응답이 263킬로바이트가 된다. 화면에는 어차피 처음 몇 개만 보인다. 그래서 상한을 두는 것이 맞는데, 잘랐다는 사실을 반드시 알려야 한다. 잘린 것을 모르는 화면은 「목록에 없으니 해결됐다」고 판단해 나머지 표시를 지운다.

5-6은 응답 형태를 고르는 결정적 이유 하나를 준다. 한 필드에 규칙 두 개가 동시에 실패할 수 있다. orderId가 길이도 부족하고 형식도 안 맞는 상황이다. 오류를 경로를 키로 하는 맵으로 만들면 나중 것이 앞의 것을 덮어써서 하나가 사라진다. 사용자는 길이를 고친 뒤 다시 제출하고 그제서야 형식 오류를 듣게 된다. 맵이 아니라 목록이어야 하는 이유가 이것이다.

6. 사람용 문구와 기계용 경로를 가른다

여기서 흔한 절충안이 하나 등장한다. 「메시지에 필드 이름을 넣어 두면 사용자도 알아보고 화면도 대조할 수 있지 않나」다. 실제로 돌려 보면 두 기대가 모두 무너진다.

--- 6-1. the server bakes the label into the sentence, one language only ---
  response : [{"message":"Quantity must be at least 1."}]

  a screen in another language now has three bad options:
    1. show the English sentence to a non English reader
    2. translate the sentence at runtime, per request
    3. match the sentence text to decide which box to mark

--- 6-2. option 3 in practice: matching on the sentence ---
  screen locale en   label on screen Quantity     found in the sentence: true
  screen locale de   label on screen Menge        found in the sentence: false
  screen locale es   label on screen Cantidad     found in the sentence: false
  screen locale pt   label on screen Quantidade   found in the sentence: false
  labels matched : 1 of 4
  the only locale that matches is the one the server happened to be written in.

--- 6-3. the same sentence after a harmless copy edit on the server ---
  before : Quantity must be at least 1.   -> client match on "Quantity" = true
  after  : The quantity must be at least 1.   -> client match on "Quantity" = false
  a wording change is a breaking change once the screen parses the wording.

네 개 로케일 중 하나만 대조에 성공했고, 그 하나는 서버 코드를 쓴 사람의 언어였다. 나머지 셋은 자기 화면의 필드 이름을 문장에서 찾지 못한다. 그런데 더 위험한 것은 6-3이다. 문장 앞에 관사 하나를 붙이는 사소한 수정으로 대조가 곧바로 실패했다. 문구를 화면이 파싱하는 순간, 카피 수정이 곧 호환성 파괴가 된다. 그리고 이 파괴는 어떤 테스트에도 안 걸린다. 서버 쪽에서는 문장을 다듬었을 뿐이기 때문이다.

해법은 나누는 것이다. 위치와 규칙 코드와 파라미터는 서버가, 사람이 읽을 문장은 화면이 만든다.

--- 6-4. split it: path and rule stay, wording moves to the client ---

6-6이 이 절의 요약이다. 문장은 28자에서 40자까지 제각각인데 경로는 네 번 모두 11자로 같다. 문구는 언어별로 다르고 시간이 지나며 바뀌지만, 경로는 스키마가 바뀌지 않는 한 그대로다. 변하는 것과 변하지 않는 것을 같은 문자열에 섞어 넣으면, 변하지 않아야 할 쪽이 변하는 쪽에 끌려간다.

다만 문구를 완전히 없애는 것도 답이 아니다. 6-7이 그 이유다. 서버가 새 규칙 코드를 추가했는데 화면의 문구 사전에 그 코드가 아직 없으면, 칸은 빨갛게 칠해지고 설명은 비어 있는 상태가 된다. 그래서 서버는 모르는 규칙을 위한 기본 문장을 하나 함께 실어야 한다. 중요한 것은 그 문장의 역할이다. 최후의 수단이지 화면이 파싱하는 대상이 아니다. 화면은 아는 규칙이면 자기 문구를 쓰고, 모르는 규칙일 때만 서버 문장을 그대로 보여 준다.

  • 서버가 만드는 것은 경로·규칙 코드·파라미터 세 가지다. 파라미터는 문장에 끼워 넣을 숫자와 힌트를 그대로 담는다
  • 화면이 만드는 것은 필드 이름과 문장이다. 필드 이름 사전의 키는 인덱스를 뺀 경로가 되므로 배열 항목 전체가 한 항목을 공유한다
  • 규칙 코드는 안정적이어야 한다. 코드 이름을 바꾸는 것은 경로를 바꾸는 것과 같은 무게의 변경이다
  • 서버 기본 문장은 한 언어로 충분하다. 어차피 화면이 아는 규칙에서는 쓰이지 않는다
  • 번역 파일에 없는 규칙 코드를 만났을 때 경고를 남기게 해 두면, 서버가 규칙을 추가한 사실이 배포 후 조용히 묻히지 않는다

7-6이 이 절의 실천 항목이다. 화면 쪽에 불변식 하나를 둔다. 응답에 담긴 오류 개수와 화면 어딘가에 표시된 개수가 같아야 한다. 이 검사를 개발 빌드에서 경고로 띄우기만 해도, 서버가 새 필드를 추가했을 때 화면이 삼키는 사고를 배포 전에 잡는다.

접두사 승격 정책은 조금 더 친절하다. items.9.sku에서 items.9를 시도하고 없으면 items를 시도해 장바구니 영역 전체에 표시를 붙였다. 사용자는 최소한 어느 구역을 봐야 하는지 안다. 다만 이 정책도 한계가 있다. billing.taxId는 상위 billing조차 화면에 없으므로 결국 배너로 갔다.

9. 응답 스키마를 린트로 검사한다

지금까지 나온 요구사항을 규칙으로 적고, 다섯 가지 응답 형태에 실제로 돌려 봤다. 요청을 검사하는 검증기가 아니라 계약을 검사하는 린터다.

후보 C가 5점에 그친 이유가 이 린터의 존재 이유를 보여 준다. C는 경로도 있고 크기도 작지만 한 응답 안에서 표기법이 섞여 있다. 홀수 번째 오류는 JSON Pointer, 짝수 번째는 점 표기다. 실제로 이런 응답이 나오는 경로가 있다. 프레임워크 기본 검증기가 만든 오류와 사람이 손으로 넣은 도메인 검증 오류가 같은 배열에 섞여 나갈 때다. 화면 입장에서는 오류마다 표기법을 추측해야 하고, 추측이 틀리는 순간 3절의 사고가 재현된다.

10. 설계 규칙과 점검 목록

실행으로 확인한 것을 규칙으로 정리하면 다섯 줄이다. 각 규칙 뒤의 근거는 앞 절의 출력이다.

  • 표기법을 하나 고르고 문서에 적는다. 이름에 특수문자가 들어갈 여지가 조금이라도 있으면 JSON Pointer다. 왕복 시험에서 9건 중 8건을 통과한 유일한 표기법이고, 탈출 규칙이 표준 문서에 있다
  • 한 응답 안에서 표기법을 섞지 않는다. 프레임워크가 만든 오류와 도메인 검증 오류가 같은 배열에 들어간다면, 나가기 직전 한 곳에서 표기법을 통일한다
  • 배열 항목에는 인덱스와 안정 식별자를 함께 준다. 그러려면 식별자가 요청 스키마에 먼저 있어야 한다. 응답만 고쳐서는 안 되는 유일한 규칙이다
  • 오류는 맵이 아니라 목록으로 준다. 한 필드에 두 규칙이 동시에 실패할 수 있고, 맵은 그중 하나를 조용히 버린다
  • 문구는 화면이 만들되 서버는 기본 문장을 하나 남긴다. 화면이 모르는 규칙 코드가 왔을 때의 유일한 안전망이다

가장 자주 놓치는 것. 표기법을 정하는 회의는 열리는데, 「알 수 없는 경로가 오면 어떻게 하나」를 정하는 회의는 열리지 않는다. 그런데 실측에서 응답의 절반이 화면에 대응 요소가 없는 경로였다. 이 규칙이 없으면 각 화면이 알아서 처리하고, 대부분은 조용히 버리는 쪽을 택한다. 서버가 제대로 알려 준 오류의 3분의 1이 사용자에게 닿지 않는 상태가 여기서 만들어진다.

점검 목록은 다음과 같다. 각 항목은 앞 절에서 실제로 실패를 만들어 본 것들이다.

  • 오류 응답의 표기법이 규격 문서에 적혀 있다
  • 필드 이름에 점·슬래시·대괄호가 들어간 표본으로 왕복 시험을 통과시켰다
  • 숫자로 된 객체 키가 인덱스로 오해되지 않는지 확인했다
  • 배열 항목 오류에 안정 식별자가 함께 실린다
  • 그 식별자가 요청 스키마에도 정의돼 있다
  • 오류가 목록이고, 한 필드에 두 개가 붙을 수 있다
  • 목록에 상한이 있고 잘렸다는 표시가 함께 나간다
  • 화면이 문장을 파싱하지 않는다
  • 규칙 코드마다 화면 쪽 문구 항목이 있고, 없을 때 경고가 남는다
  • 빈 경로가 본문 전체를 뜻한다는 규약이 문서에 있다
  • 화면에 표시 개수 불변식이 있다
  • 입력 요소 이름과 요청 본문 경로가 같은 함수에서 나온다
  • 알 수 없는 경로의 처리 정책이 화면마다 같다

11. 이 글에서 확인하지 못한 것

  • 실제 브라우저에서의 접근성 연결. 경로를 입력 요소에 붙이는 것까지는 확인했지만, 그 표시가 보조 기술에 어떻게 전달되는지는 이 실험 밖이다
  • 중첩 폼 컴포넌트의 상태 관리. 화면이 항목을 추가·삭제·정렬할 때 경로와 컴포넌트 상태를 어떻게 동기화하는지는 프레임워크마다 다르다
  • 부분 성공 응답. 일괄 요청에서 일부만 실패했을 때 성공한 항목과 실패한 항목을 한 응답에 어떻게 담을지는 다른 설계 문제다
  • 비동기 검증. 중복 확인처럼 서버 왕복이 필요한 규칙은 제출 시점이 아니라 입력 도중에 오류가 도착한다. 그때 경로의 유효 기간은 이 글의 배열 문제와 비슷하지만 같지는 않다
  • 실서비스 규모의 응답 크기. 5절의 수치는 합성 데이터다. 실제 필드 이름은 더 길고 파라미터도 더 많다

결론: 오류 응답의 수신자는 사람이 아니라 화면이다

검증 오류를 잘 주자는 이야기로 시작하면 결론이 「메시지를 친절하게 쓰자」로 흘러간다. 그런데 실행해서 확인한 것은 반대 방향을 가리킨다. 친절한 문장은 화면에서 만들 수 있지만, 어느 칸이 틀렸는지는 서버만 안다. 서버가 보내야 할 것은 문장이 아니라 좌표다.

좌표를 보내기로 하면 곧바로 표기법 문제가 따라온다. 그리고 표기법은 겉보기와 달리 취향의 영역이 아니었다. 필드 이름에 점 하나가 들어간 것만으로 세그먼트 두 개가 세 개로 늘어났고, 클라이언트는 자기가 잘못 읽었다는 사실조차 알 수 없었다. 대괄호 표기는 이름 안의 닫는 괄호 하나에 null 세그먼트를 뱉었다. 탈출 규칙이 문서에 있는 표기법과 없는 표기법의 차이가 왕복 시험 5건 대 8건으로 나타났다.

배열은 별도의 문제였다. 인덱스는 정체성이 없어서 항목 하나가 사라지자 오류 두 개가 모두 엉뚱한 줄에 붙었고, 멀쩡한 칸에 빨간 줄이 그어지고 정작 틀린 줄에는 아무 표시가 없는 상태가 됐다. 안정 식별자로 바꾸니 0건이 됐지만, 그러려면 요청 스키마부터 바꿔야 했다. 응답만 고쳐서 해결되는 문제가 아니었다.

그래서 결론은 이렇다. 표기법은 계약이다. 서버가 인쇄하는 규칙과 화면이 파싱하는 규칙이 같아야 하고, 그 규칙이 어딘가에 적혀 있어야 하고, 한 응답 안에서 흔들리지 않아야 한다. 그 계약이 서 있어야 비로소 오류 응답에 값어치가 생긴다.

지금 당장 확인할 수 있는 것이 하나 있다. 지금 다루는 화면에서 검증 오류를 처리하는 코드를 열고, 응답에 담긴 오류 개수와 화면에 실제로 표시된 개수를 비교하는 줄이 있는지 보라. 없다면 그 화면은 서버가 제대로 알려 준 오류를 조용히 버리고 있을 가능성이 있다. 그리고 그 사실은 오류 응답을 아무리 잘 만들어도 드러나지 않는다.

# 검증 오류 필드 경로 — 복붙용 표기법 비교표와 응답 스키마

> 출처: braindetox.kr — 어느 칸이 틀렸는지 화면이 못 찾는다
> 근거: Windows 10 / Node.js 22.16 (win32) / bash 5.2.37 (MSYS2) 에서 직접 구현한 검증기로 실행 검증
> 이 파일을 그대로 AI에 붙여 「이 기준으로 우리 오류 응답을 점검해줘」라고 쓰면 됩니다.
> 원칙: 오류 응답의 수신자는 사람이 아니라 화면이다. 화면이 경로를 입력 요소에 연결할 수 있어야 값어치가 생긴다.

## 1. 표기법 3종 비교 (왕복 시험 실측)

| 항목 | 점 표기 `items.2.qty` | JSON Pointer `/items/2/qty` | 대괄호 `items[2].qty` |
|---|---|---|---|
| 파서 크기 | 154자 | 302자 | **472자** |
| 토큰화 반복문 | 불필요 | 불필요 | **필요** |
| 탈출 규칙 | **없음** | 물결표 `~0` · 슬래시 `~1` | **없음** |
| 배열 단계 표시 | 안 보임 | 안 보임 | 보임(서버 주장) |
| 표준 문서 | 관행 | **RFC 6901** | 관행 |
| 전체 본문 지칭 | 규약 필요 | 빈 문자열 | 규약 필요 |
| 까다로운 키 9건 왕복 | 5건 | **8건** | 4건 |

**결론: 이름에 특수문자가 들어갈 여지가 있으면 JSON Pointer.**

## 2. 이스케이프가 깨지는 지점

| 키에 든 문자 | 점 | Pointer | 대괄호 | 증상 |
|---|---|---|---|---|
| 점 `app.version` | 깨짐 | 통과 | 깨짐 | 세그먼트 2 → 3 |
| 슬래시 `x-forwarded/for` | 통과 | 통과 | 통과 | 점 표기는 우연히 안전 |
| 대괄호 `group[a]` | 통과 | 통과 | 깨짐 | 파서가 null 세그먼트 반환 |
| 물결표 `draft~2` | 통과 | 통과 | 통과 | 탈출 규칙이 정확히 되돌림 |
| 숫자 키 `2024` | 깨짐 | 깨짐 | 통과 | 키를 인덱스로 오해 |
| 빈 문자열 키 | 통과 | 통과 | 깨짐 | 세그먼트가 조용히 사라짐 |
| 경로처럼 생긴 키 | 깨짐 | 통과 | 깨짐 | 2 → 4, 없는 자리를 지목 |

- 되돌릴 때 순서 주의: `~1` → 슬래시 를 먼저, 그다음 `~0` → 물결표
- 숫자 키 판정은 표기법이 아니라 **그 자리 값의 타입**으로 한다 (객체면 이름, 배열이면 인덱스)

## 3. 배열 인덱스의 수명

- 인덱스는 **요청을 보낸 순간의 배열 상태**에만 유효한 좌표다
- 항목 하나가 삭제되면 오류가 아래 줄로 밀린다 → 멀쩡한 칸에 빨간 줄, 틀린 줄에는 무표시
- 실측: 오배치 2/2 → 안정 식별자로 바꾸면 0/2
- **식별자는 요청 스키마에 먼저 있어야 한다.** 클라이언트가 안 보낸 값을 서버가 되돌려 줄 수 없다
- 추가·정렬에서도 같은 문제가 난다. 삭제만 조심하면 되는 문제가 아니다

## 4. 응답 스키마

```
{
  "error": "validation_failed",
  "truncated": false,
  "totalErrors": 6,
  "errors": [
    {
      "path": "items.2.qty",
      "keyPath": "items[ln_5518].qty",
      "rule": "min",
      "params": { "min": 1, "got": 0 },
      "message": "모르는 규칙일 때만 쓰는 기본 문장"
    }
  ]
}
```

| 필드 | 누가 쓰나 | 없으면 |
|---|---|---|
| `path` | 화면·로그 | 어느 칸을 칠할지 정할 수 없다 |
| `keyPath` | 화면(배열) | 항목이 밀리면 엉뚱한 줄에 표시 |
| `rule` | 화면(문구 선택) | 문장을 파싱하게 됨 → 카피 수정이 파괴 |
| `params` | 화면(문구 조립) | 「최소 1」의 1을 넣을 수 없다 |
| `message` | 화면(모르는 규칙만) | 설명 없는 빨간 칸 |
| `truncated` | 화면(목록) | 잘린 목록을 전부로 믿음 |
| `totalErrors` | 화면·관제 | 몇 개 잘렸는지 못 알림 |

- **맵이 아니라 목록.** 한 필드에 규칙 두 개가 동시에 실패할 수 있다
- 첫 오류만 주면 실측 왕복 6회, 전부 모으면 1회
- 항목 1,000개 일괄 요청 = 오류 2,000개 = 문장 포함 시 263 KB → 상한 + `truncated` 필수

## 5. 클라이언트 매핑

```
function applyErrors(resp, form) {
  let shown = 0;
  for (const e of resp.errors) {
    const el = form.querySelector('[name="' + cssEscape(e.path) + '"]');
    if (el) { markField(el, textFor(e.rule, e.params)); shown++; continue; }
    if (e.path === '') { banner(textFor(e.rule, e.params)); shown++; continue; }
    // 알 수 없는 경로: 접두사를 잘라 상위 영역을 찾는다
    const segs = parsePath(e.path);
    let box = null;
    for (let n = segs.length - 1; n > 0; n--) {
      if (box) break;
      box = form.querySelector('[data-scope="' + printPath(segs.slice(0, n)) + '"]');
    }
    if (box) { markScope(box, textFor(e.rule, e.params)); shown++; }
    else { banner(fallbackText(e)); shown++; }
  }
  // 불변식: 응답에 담긴 개수와 화면에 표시된 개수가 같아야 한다
  if (shown !== resp.errors.length) warnInDev(resp.errors.length - shown);
}
```

| 정책 | 표시 | 사용자가 보는 것 | 위험 |
|---|---|---|---|
| 무시 | 4/6 | 제출 실패, 설명 없음 | **불변식 깨짐. 기본값 금지** |
| 배너 | 6/6 | 상단에 경로 노출 | 내부 필드명이 사용자에게 보임 |
| 접두사 승격 | 6/6 | 관련 영역 표시 + 나머지 배너 | 승격 범위가 넓으면 오해 |

## 6. 사람용 문구와 기계용 경로

- 서버가 만드는 것: **경로 · 규칙 코드 · 파라미터**
- 화면이 만드는 것: **필드 이름 · 문장**
- 실측: 서버 영어 문장으로 칸을 특정하는 방식은 4개 로케일 중 1개만 성공
- 관사 하나 추가하는 카피 수정으로 대조가 즉시 실패 → **문구 수정 = 호환성 파괴**
- 문장 길이는 28~40자로 제각각, 경로는 네 번 모두 11자로 동일
- 서버는 **모르는 규칙용 기본 문장**을 하나 남긴다 (최후의 수단, 파싱 대상 아님)

## 7. 점검 목록

- [ ] 오류 응답의 **표기법이 규격 문서에 적혀** 있다
- [ ] 점·슬래시·대괄호가 든 필드 이름으로 **왕복 시험**을 통과시켰다
- [ ] 숫자로 된 **객체 키**가 인덱스로 오해되지 않는지 확인했다
- [ ] 배열 항목 오류에 **안정 식별자**가 함께 실린다
- [ ] 그 식별자가 **요청 스키마**에도 정의돼 있다
- [ ] 오류가 **목록**이고, 한 필드에 두 개가 붙을 수 있다
- [ ] 목록에 **상한**이 있고 잘렸다는 표시가 함께 나간다
- [ ] 화면이 **문장을 파싱하지 않는다**
- [ ] 규칙 코드마다 화면 쪽 **문구 항목**이 있고, 없을 때 경고가 남는다
- [ ] **빈 경로**가 본문 전체를 뜻한다는 규약이 문서에 있다
- [ ] 화면에 **표시 개수 불변식**이 있다
- [ ] 입력 요소 이름과 요청 본문 경로가 **같은 함수**에서 나온다
- [ ] 알 수 없는 경로의 처리 정책이 **화면마다 같다**

## 8. 하지 말 것

- ❌ 한 응답 안에서 **표기법 섞기** — 프레임워크 오류와 도메인 오류가 섞이는 자리
- ❌ 오류를 **경로 키 맵**으로 주기 — 한 필드 두 규칙 중 하나가 사라진다
- ❌ 배열 오류를 **인덱스만으로** 가리키기 — 삭제·추가·정렬에서 전부 밀린다
- ❌ 화면이 **서버 문장을 파싱**하기 — 카피 수정이 곧 장애
- ❌ 알 수 없는 경로를 **조용히 버리기** — 제출 실패 + 설명 없음
- ❌ 목록을 **말없이 자르기** — 화면이 나머지를 해결된 것으로 처리한다
- ❌ 입력 요소 이름을 **손으로 적기** — 첫 항목 삽입에서 본문 경로와 어긋난다
