20年以上生き残るソフトウェアは何が違うのか - 完成と放置を分ける指標

コード量・依存・変更理由を実際に測って完成と死を区別する方法

2026年8月2日 開発・インフラ

はじめに: コミットが3年ないという事実だけでは何も分からない

依存リストに入れようとしているライブラリを開いてみる。スターは十分にあり、ドキュメントもあり、やることもちょうど必要な分だけだ。ところがコミットグラフが3年間平坦である。この瞬間に手が止まる。管理が途切れたコードを本番に入れるように思えるからだ。

そこで多くの人はコミットが活発な代替を探す。その判断がいつも間違いというわけではないが、根拠は間違っている。コミット頻度はソフトウェアの健康状態ではなく、残っている仕事の量を示す指標に近い。残りが多くて活発な場合もあれば、残りがなくて静かな場合もある。グラフだけではどちらか分からない。

この記事はその区別を測定可能な形に変える試みだ。長生きするソフトウェアの条件を感想ではなく数字で扱い、その数字を測るスクリプトを実際に走らせて結果を貼った。結論から言えば、長生きするコードの条件は情熱でも人気でもない。小さく、依存が少なく、範囲が狭く、ドキュメントがあること。そしてこの四つはすべて、何かを入れないと決めた結果である。技術ではなく拒否の蓄積だ。

実行環境。以下の測定はすべてWindows 10 Pro (10.0.19045)で実際に実行した結果だ。シェルはGNU bash 5.2.37 (MSYS2/MinGW64)、ツールはPython 3.13.3、Node.js v22.16.0、npm 11.5.2である。測定対象はその環境にインストールされたPython 3.13標準ライブラリと、公開レジストリから解決だけした依存ツリーだ。スクリプトはすべてファイルに保存して実行し、コマンドはそのまま書き写した。

この記事が扱わないこと。整理作業の費用をいつ回収するかという計算はリファクタリング費用はいつ回収されるのかで扱った。ここでは会計ではなく判定基準だけを見る。コードを最初から保守しやすく書く習慣は保守しやすいコードの書き方のほうだ。この記事はすでに存在するコードをどう判定し処分するかだけを扱う。

1. 死んだと完成したは同じグラフを描く

コミットが止まった状態は、二つの異なる事実を同じ形で見せる。一つはやるべきことが残っているのに誰もやっていないこと、もう一つはやるべきことが実際に終わったことだ。前者は危険で後者はむしろ安全なのに、リポジトリの最初の画面では区別されない。

区別するにはグラフではなく残っているものの性質を見る必要がある。以下は実務で実際に使える判別信号だ。

観察点放置に近い信号完成に近い信号
開いた課題の性質再現可能なバグ報告が無応答で積み上がる大半が機能追加要望で、範囲外として閉じられる
ビルド状態最新のツールチェーンで壊れるという報告が放置新しいランタイムが出ると対応コミットだけ静かに載る
ドキュメントの時点ドキュメントがコードより数版前を説明ドキュメントとコードが同じコミットで変わる
直近の変更理由変更自体がない、または理由が不明バグ修正と外部環境への対応が大半
セキュリティ対応脆弱性報告の後数か月無反応機能は増えなくても修正は出る
リリース最後のリリースに既知の致命的欠陥が残る間隔は長いが内容が明確

この表の核心は変更が少ないことを問題として読まないことだ。問題は変更が少ないことではなく、あるべき変更がないことである。そして「あるべき変更」は大半が二種類だ。内部で見つかった欠陥を直すことと、外で変わった世界に合わせること。この二つが出ているなら、そのプロジェクトは生きている。機能が増えないのは別の事実であり、時には意図された結果だ。

実務的に一つ付け加えるなら、判定をリポジトリ一つで終えないことだ。ディストリビューションがそのソフトウェアを含み続けているか、他のプロジェクトが依然としてリンクしているかのほうがはるかに強い信号である。上流が静かでも下流が活発なら、そのコードはすでにインフラになった状態だ。

2. 小さいコードベースが生き残る理由 - 読めれば直せる

小さいコードが長生きするのは優雅だからではなく、引き継ぎ費用が一人の中に収まるからだ。「このモジュールは今日から君が担当」という言葉が実行可能な文になる大きさがある。その大きさを勘で語らないためには測るしかない。

測り方は単純だ。コメントと空行を除いて実際のコード行だけ数える。Python標準ライブラリを対象に走らせた結果である。

$ python measure_size.py C:/Python313/Lib/json C:/Python313/Lib/email \
                        C:/Python313/Lib/asyncio C:/Python313/Lib/csv.py C:/Python313/Lib/textwrap.py

target                       files      code   comment     blank      bytes
json                             5      1105        51       172      50103
email                           29      7764      1035      1592     396685
asyncio                         33     11165      1008      2568     533673
csv.py                           1       392        40        81      19691
textwrap.py                      1       355        68        74      20436

ここで読むべきは順位ではなく桁だ。355行と11,165行は同じ種類の物ではない。前者は一人が一日で全部読み責任を引き受けられるが、後者はそうならない。保守可能性は連続的な尺度ではなく閾値のある性質に近い。

ただし小さいことがそのまま良いという意味ではない。小さいモジュールは機能を少なくしか含んでおらず、足りない部分は利用者が自分で埋めなければならない。大きく機能の多いほうは、その費用を自分で背負って利用者を楽にしたということだ。どちらが正しいかは、そのコードが何人にどれだけ長く使われるかで決まる。利用者が多く寿命が長いほど、利用者側に押しつけた費用の合計は大きくなる。

2.1 規模と一緒に見るべきもの

  • コメント比率。上の出力でemailはコード7,764行に対しコメント1,035行で13%程度だった。コメントが極端に少ない大きなファイルは読む費用が行数以上である。
  • ファイル数。同じ行数でも33ファイルに散っているのと1ファイルなのとでは探索費用が違う。
  • 最大ファイル一つの大きさ。平均ではなく最大値が律速だ。一ファイルが3,000行ならそのファイルがそのままモジュールである。
  • テストコードを含めるか。テストを含めて数えると規模は膨らむが、引き継ぎの観点ではテストも読むべき資産だ。二つの値を別々に記録するほうがよい。
  • 生成コードの除外。パーサ生成器の出力のように人が読まないファイルは外すべきだ。外さないと指標が無意味になる。

参考までに、長く維持されるプロジェクトにはコメント比率を公開指標として掲げる例もある。SQLiteのドキュメントは自らのソースが35%以上コメントだと明示し、それを長期サポートの根拠の一つに挙げる。コメント比率が高いから良いコードという意味ではないが、引き継ぐ人を定数として書かれたコードだという信号にはなる。

3. 依存が寿命を決める - 自分が触らなくても他人が変える

コードが壊れる理由の相当部分は自分が作ったものではない。自分が何もしなくても他人が変えれば壊れる。だから依存の数は機能の便利さを測る数字ではなく、外部に露出した面積を測る数字だ。

問題は大半がこの数字を直接宣言した数で数えることである。実際の面積はそれよりはるかに広い。インストールせずツリーだけ解決して測ってみた。

$ cat package.json
{"name":"probe","version":"1.0.0","dependencies":{"express":"4.21.2"}}

$ npm install --package-lock-only --no-audit --no-fund
up to date in 3s

$ node -e "const l=require('./package-lock.json');
           console.log(Object.keys(l.packages).filter(Boolean).length)"
69

依存を一行書いただけでロックファイルには69項目が入った。同じやり方でいくつか追加で測った。表のtreeは自分自身を含む値だ。

パッケージ直接依存解決されたツリー読み方
express@4.21.23169宣言1行が68個の他人のリポジトリを連れてくる
axios@1.7.9323直接の数と実際の面積が7倍以上違う
chalk@5.4.101外部の変化が届く場所が自分自身だけ
lodash@4.17.2101同じ構造。規模が大きくても面積は狭い
typescript@5.7.301大きなツールでも選べば0に保てる

この表からどちらが優れているという結論を出してはいけない。ツリーが大きいほうはそれだけ他人の成果を再利用してより速くより多くの仕事をする。その速度が事業的に正しい局面は確実にある。ツリーが1のほうは必要なものを自前で実装したという意味であり、その実装とそのバグを自分が生涯背負うという意味だ。両者は同じ軸の両端ではなく、異なる費用を選んだ結果である。

ただし寿命という軸一つだけで見れば方向ははっきりしている。ツリーに入っている項目一つ一つが、それぞれのリリース周期とそれぞれの保守者を持つ。そのうち一つでも維持が途切れたり互換を壊せば、自分のコードが対応しなければならない。自分のコードの安定性は、自分が制御できない項目数に反比例する。

3.1 ロックファイルがない言語で測る方法

Pythonのように標準ライブラリの中でインポートが絡む場合は、ソースを構文解析して閉包を求める必要がある。核心はホップ数を制限することだ。

def closure_by_depth(root, max_depth=8):
    seen = {root}
    frontier = {root}
    levels = [set(seen)]
    for _ in range(max_depth):
        nxt = set()
        for name in frontier:
            for f in package_files(name):
                for dep in imports_of(f, name):
                    if dep not in seen and package_files(dep):
                        nxt.add(dep)
        if not nxt:
            break
        seen |= nxt
        frontier = nxt
        levels.append(set(seen))
    return levels

なぜ制限が必要かは結果を見れば分かる。以下はPython 3.13.3標準ライブラリで測った値だ。modは自分自身を除いたモジュール数、locはそれらのコード行の合計である。

モジュール自身のコード行1ホップ2ホップ3ホップ全体閉包

csv3923 / 2,8499 / 7,09919 / 16,774124 / 171,129
json1,1053 / 5,87313 / 42,08140 / 63,433125 / 171,436
email7,76418 / 20,76854 / 52,50378 / 106,451180 / 699,430
unittest5,37221 / 36,93372 / 98,229110 / 581,682180 / 699,430

ここで得られた最も実用的な発見はこれだ。全体閉包は飽和して弁別力がない。355行のモジュールでも11,165行のモジュールでも、最後までたどれば124個と180個に収束する。一方3ホップで区切ると16個と174個へ10倍以上開く。つまり依存の指標は「全部数える」ことではなく、どこで区切るかを決める問題である。

この測定には明確な限界がある。構文解析は関数の中や例外処理ブロックの中の遅延インポートまで全部数えるため、実行時に必要な数より多く出る。したがってこの値は上限だ。それでも同じ物差しで比較する用途には十分である。

4. 範囲を狭く取ることは機能を捨てることだ

寿命の長いソフトウェアを見ると、共通してやらないことの一覧が長い。ところがこの文はよく誤解される。「ミニマリズムが良い」と読まれるが、実際に起きているのは機能要望を断る労働である。

具体的な事例としてOpenBSDのhttpd(8)がある。manページはこれをFastCGIとTLSに対応したHTTPサーバとだけ説明する。リリースノートを見ると、このサーバはOpenBSD 5.6で初めて入り、同じリリースでApacheが基本システムから削除された。そのリリース日は2014年11月1日だ。

ここで一方が優れているという結論に向かうと間違う。Apache HTTP Server 2.4のモジュール索引には140個前後のモジュールが載っている。認証と認可、プロキシとロードバランシング、キャッシュ、圧縮、URL書き換え、ロギング、TLSまでそれぞれ別モジュールとして提供される。この規模は放漫さではなく設計目標だ。運用者は必要なものだけ選んで付けられ、その拡張性のおかげで数多くの環境が今もそれを使う。狭い範囲で作られたサーバがそもそもできないことがその一覧の中にある。

だから正確な表現はこうだ。範囲を狭めれば寿命が伸び、代わりに適用範囲が減る。どちらも代償である。判断するとき問うべきは「機能が多いか」ではなく「この機能がなくて使えない人が自分の組織にいるか」だ。

  • 機能を入れないと決めればその機能のバグ・ドキュメント・テスト・セキュリティ対応が丸ごと消える。節約されるのはコード行数ではなく恒久的な保守費用だ。
  • 代わりに利用者が自分で埋めなければならない。その費用は消えず移動する。
  • 範囲をドキュメントに文章として書いておかなければ断る根拠がない。だから狭い範囲はドキュメントなしには維持されない。
  • 拡張点を一つ作っておくことと機能を全部含めることは違う。境界を一つだけ開けておく設計が折衷案だ。
  • 拒否は人気を失う。寿命と採用率はしばしば相反するという事実を認めたうえで選ぶ必要がある。

5. ドキュメントがコードと一緒に生きるべき理由

ドキュメントのないコードは引き継げない。正確には引き継ぐことはできるが、引き継いだ人が元の意図を復元できない。だからドキュメントはコードの付属物ではなく、引き継ぎ可能性そのものだ。

この部分で参考になる慣行がある。OpenBSDのFAQはmanページについて、OpenBSDの情報の権威ある出典であり、最新性と正確性を保つのに相当な努力を払っていると書く。より重要なのはその次の文だ。システムを変更する開発者はコードの変更と一緒にmanページも更新することが期待されると明示している。

この規則の実質は、ドキュメントをよく書こうという勧告ではない。ドキュメントをコード変更の完了条件に入れたということだ。こうすればドキュメントがコードより遅れることが構造的に減る。先の判別表で「ドキュメントとコードが同じコミットで変わる」を完成の信号に入れた理由はここにある。

5.1 ドキュメントを一級に置くための最小装置

  • ドキュメントをコードと同じリポジトリに置く。ウィキに出した瞬間に更新主体が分離し、分離すれば遅れる。
  • 公開インターフェースを変える変更はドキュメント変更を伴うことを通過条件としてレビュー規則に入れる。
  • ドキュメントに範囲宣言を書く。「これはやらない」が書かれていて初めて要望を閉じられる。
  • 例は実行可能な形で置く。実行されない例は時間が経てば全部嘘になる。
  • バージョンごとに何が変わったか人が読める変更履歴を残す。コミットログは代替にならない。
  • コメントにはなぜそうしたかを書く。何をするかはコードがすでに語っている。

ドキュメントの分量がそのまま品質ではない。ただし先に見たSQLiteのようにコメント比率を公開指標として管理したり、manページ更新を開発者の義務として固定するプロジェクトが共通して長く続く点は注目に値する。どちらも人が入れ替わることを前提に作られた装置だ。

6. 互換性の約束 - 何を変えないと決めるか

利用者が離れる理由は機能が足りないからよりもアップグレードが痛いからである場合が多い。逆に言えば、何を変えないと固定するかが利用者を残す最も強い装置だ。

この約束を極端まで押し進めた例にSQLiteがある。公式ドキュメントは開発者たちの意図が2050年まで支えることだと書き、C言語のAPIとディスク上のファイル形式を完全な後方互換で維持すると約束する。今日書いたアプリケーションが数十年後にリリースされる版ともリンクして動くべきだという文まである。同じ文書はデータベースファイルが32ビットと64ビット、ビッグエンディアンとリトルエンディアンでバイト単位で同一だと明示する。

この約束が生む効果は二方向だ。

  • 利用者側:アップグレードが事件でなくなる。版を上げることがコード修正を呼ばないなら使い続けることが既定値になる。
  • 開発者側:設計の自由度が恒久的に減る。一度公開したインターフェースは間違いまで含めて抱えていくことになる。

だから互換性の約束はただではない。頻繁に壊す側にも理由がある。誤った設計を早く捨てられ、そのおかげでより良い形へ収束する速度が速い。利用者層が薄く変化が速い領域ではそちらが合理的でありうる。問題は約束をしないまま頻繁に壊すことだ。そうなると利用者は毎回驚く。

実務で移して使える形にまとめるとこうなる。

  • 何が公開インターフェースかをドキュメントに書く。書かれていないものは変えてよいという意味になる。
  • 壊す変更には予告期間と移行経路を一緒に出す。どちらか一方だけでは利用者はついてこられない。
  • ファイル形式と保存スキーマはAPIよりはるかに長く生きる。ここを壊すとデータが人質になる。
  • 既定値の変更はAPI変更と同じ重さで扱う。シグネチャがそのままでも動作が変われば壊れたのだ。
  • 互換を保てないなら名前を変える。同じ名前で違う物を出すのが最悪だ。

7. 引き継ぎ - 保守者が変わっても続く条件

20年生きるソフトウェアで同じ人が20年張り付いている例はまれだ。したがって寿命の実質的な条件は情熱ではなく交代可能性である。よくバス係数と呼ばれる値を下げる問題だ。

面白い事例が先に見た二つのデーモンにある。relayd(8)のmanページのHISTORY節を見ると、このプログラムは元々hoststatedという名前でOpenBSD 4.1に初めて登場し、4.3で今の名前に変わった。AUTHORS節には二人の名前が書かれている。そしてhttpd(8)のmanページは、このサーバがrelayd から派生したと明かす。名前が変わり、人が複数いて、あるプログラムのコードが別のプログラムへ分かれていく。こうした移動が可能であるためには、ドキュメントと境界が先にあるしかない。

バス係数を下げる装置は抽象的な話ではなく実際のファイルと規則だ。

  • ビルドが一つのコマンドで終わること。「担当者のノートPCでしかビルドできない」が最も多い死因だ。
  • 実行環境をコードとして書いておく。必要なランタイム版と外部ツールを文章ではなく設定ファイルに固定する。
  • テストが失敗を知らせる。引き継いだ人が何かを直したとき壊れたかどうか自分で知る手段がなければ手を出せない。
  • 配備手順がドキュメントにある。コードより配備のほうがずっとよく忘れられる。
  • 決定の記録を残す。なぜこの構造を選んだかがなければ、後任は全部考え直すか、理由なく作り直す。
  • 連絡先ではなくリポジトリが権威を持つ。「それは誰々に聞いて」で維持される知識はその人が辞めると一緒に出ていく。
  • 名前を変えられること。名前・所有者・ホスティングが特定個人に紐づいていると移管自体が不可能になる。

ここでよく見落とされるのが最後の二つだ。技術的に完璧でもアカウントと権限が個人に紐づいていれば、そのソフトウェアの寿命はそのアカウントの寿命と等しくなる。ドメイン、パッケージレジストリの所有権、署名鍵がすべてここに該当する。

8. いつ書き直すのが正しいか

ここまでの話が「古いものを守れ」と読まれると困る。古いという事実はそれ自体で価値でも欠陥でもない。書き直しが正当になる条件は別にある。

先に見た事例がここでも役立つ。OpenBSD 5.6は既存のサーバを基本システムから外し、新しく作ったサーバを入れた。これは「古いものを守る」の反対の行動だ。だからこの記事の主張は保存ではなく判定である。

状況判定根拠
要求の前提が変わり既存構造では表現不能書き直し機能追加ではなく骨格の不一致だ
ランタイム・言語・中核ライブラリがサポート終了書き直しまたは移植コードが健全でも動かす場所がない
読んで直す人がおらずドキュメントからも復元不能書き直し理解の費用が書き直しの費用を超えた
セキュリティ欠陥が構造から繰り返し発生書き直し個別の修正では収束しない
直近の変更がバグ修正と外部対応中心維持うまく動いているという信号だ
不満がコードの書き方や流行に関するもの維持動くものを好みに変える費用
遅いが律速が特定されている部分置換全面書き直しは過剰だ

書き直しを決めたなら、もう一つ守るべきことがある。既存のコードがなぜそういう形なのかを先に復元することだ。おかしく見える分岐一つが実際の障害対応の痕跡である場合が多い。その理由を知らずに書き直すと同じ障害をもう一度経験する。

費用をいつ回収するか、整理作業を投資としてどう説明するかの計算はこの記事の範囲外だ。その部分はリファクタリング費用はいつ回収されるのかで別に扱った。

9. 社内コードに適用する - 何を凍結するか

ここまでの条件は公開プロジェクトだけの話ではない。社内コードにそのまま適用される。むしろ社内コードのほうが切実だ。公開プロジェクトは保守者が去ってもフォークされうるが、社内モジュールは担当者が部署を移ればその場で化石になる。

社内で実際にやるべきことは「全部を最新に保つ」ことではない。どのモジュールを完成と宣言して凍結するか選ぶことだ。凍結は放置と違う。凍結は保守費用を予算に明示的に入れる決定である。

点検項目凍結可能凍結不可
機能要求直近4四半期新規要求なし四半期ごとに要求が入る
契約文書入出力仕様がリポジトリの中にある担当者の頭の中にしかない
自動検査失敗を知らせるテストが回る手動確認に依存
外部依存解決されたツリーが片手で数えられるツリーが数十個以上
規模担当者でない人が一日で読める水準読むだけで数日
障害履歴直近1年運用障害なし同じ原因が繰り返す
再検討時点次の検討日付が固定されている決まった時点がない

仮の例を挙げるとこうだ。ある会社に社員番号の形式検証だけをするモジュールがあるとする。300行で、外部依存がなく、仕様が社内標準文書に書かれていて、テストがあり、2年間要求がなかった。これは凍結対象だ。逆に精算バッチは仕様が毎四半期変わり、外部決済事業者の応答形式に噛み合っている。規模が小さくても凍結不可である。判断基準は規模ではなく外がどれだけ頻繁に動くかだ。

凍結を宣言するとき一緒に書くべきものがある。

  • 凍結の意味を定義する。機能追加は受けないがセキュリティ修正とランタイム更新は継続する、という形で範囲を書く。
  • 再検討日を固定する。条件なしの凍結は放置と区別できない。
  • 壊れたとき誰が受けるかを書く。人の名前ではなく役割で書いてこそ人事異動に耐える。
  • 代替計画の起動条件を書く。「この条件になれば書き直しを検討」を先に決めておけば論争が短くなる。
  • 凍結モジュールの一覧を一か所に集めて公開する。一覧がなければ誰もそれが凍結されたことを知らない。

10. 寿命を測る指標と測り方

ここまで出た条件を定期的に測れる形に整理する。監査ツールを新しく買おうという話ではない。三つの数字でほとんどの判断がつく。

三つ目の指標である変更理由の分布が最も重要で、同時に最も使われていない。直近の変更が機能追加なのか外への対応なのかでそのコードの状態が分かれるからだ。実際に測ってみた。対象はこの環境にインストールされたPythonが一緒に配布する変更履歴ファイルである。

$ export PYTHONIOENCODING=utf-8
$ python news_entries.py NEWS.txt "3.13.2 final" | python classify_changes.py

reason     count   share
feature        8    8.8%
defect        58   63.7%
external       6    6.6%
doc            1    1.1%
chore          2    2.2%
other         16   17.6%
------------------------
total         91

feature share : 8.8%  (n=91)
shape: maintenance only - freeze candidate
note: keyword rules; always eyeball the 'other' bucket before trusting this

同じツールで三つの区間を比べると、指標が実際に機能することが見える。以下はPython 3.13.3と一緒に配布された変更履歴ファイルから三つの区間をそれぞれ分類した結果だ。

区間機能欠陥外部対応その他項目数
3.13.0 alpha 1 (開発区間)27.1%37.4%13.4%16.1%634
3.13.2 final (保守区間)8.8%63.7%6.6%17.6%91
3.13.3 final (保守区間)11.7%66.0%15.5%1.9%103

開発区間で27%だった機能の比重が、保守区間では9〜12%に落ちる。同じプロジェクト、同じ時期、同じ人たちなのに変更の性格が違う。コミット数だけ見れば保守区間は「静かになった」と見えるが、実際には性格が変わったのだ。これが前に述べた「死んだと完成したの区別」を数字にした形である。

この測定には正直に明かすべき限界がある。

  • キーワード分類だ。文を理解するのではなく単語を探す。上の出力でotherが17.6%だったが、この区間は人が直接読む必要がある。
  • 欠陥を外部対応より先に判定する順序にした。だから「特定のプラットフォームで出るバグの修正」が欠陥として捕まる。つまり外部対応の比率は下限だ。
  • 変更履歴の書き方の慣行によって結果が変わる。コミットメッセージの規則がある組織なら精度ははるかに上がる。
  • 一区間だけ見ても意味がない。同じプロジェクトの時間変化として見る必要がある。
  • 正規表現の規則は組織ごとに手を入れるべきだ。規則を直すときは正規表現テスターで標本の文にまず当ててみるほうが速い。

10.1 三つの指標と閾値

指標測り方おおよその解釈
コード量コメント・空行を除くコード行、ファイル数、最大ファイル数百行なら一人で引き継ぎ可能、数千行ならチーム単位
依存の面積ロックファイルの項目数、または3ホップのインポート閉包全体閉包は飽和するのでホップ制限が必須
変更理由の分布直近の変更履歴を機能・欠陥・外部・文書・その他に分類機能25%以上なら成長中、10%未満なら凍結候補
コメント比率コメント行をコード行で割る絶対基準はなく、同一リポジトリ内の趨勢で見る
ドキュメント遅延ドキュメント最終変更とコード最終変更の時差時差が長いほど引き継ぎ費用が大きくなる
権限の集中度配備・署名・ドメイン権限を持つ人数1ならその人がそのまま寿命の上限

閾値は絶対的なものではない。上に書いた数字はこの記事で実際に測った値から導いた出発点であり、組織のコードの性格に合わせて動かすべきだ。重要なのは値そのものではなく同じ物差しで繰り返し測ることである。一度測った値は判定に使えず、二度目から役に立つ。

11. 確認できなかったこと

この記事で確認できなかった、または確認しようがなかったことを明かす。残りの記述と同じ重さで読んでほしい。

  • 出発点になった記事の原文を開けなかった。そのためその記事の主張や表現は引用していない。主題だけを取り、一次情報源から調べ直した。
  • 範囲の縮小が明示的な意図だったかは文書で確認できない。上で見た二つのデーモンのmanページは何をするかだけを書き、何をしないかを宣言していない。「狭い範囲」は文書に書かれた機能一覧から推論したものであり、プロジェクトの宣言ではない。
  • OpenBSDの公式目標文書の原文は確認していない。FAQが別ページへリンクしていることだけを確認した。
  • 長寿リポジトリのコミットログで変更理由の分布を出す計画は失敗した。この実行環境ではリポジトリの複製が遮断された。そこで代わりにローカルにインストールされたPythonが一緒に配布する変更履歴ファイルを対象にした。コミット単位ではなくリリースノートの項目単位であることを踏まえる必要がある。
  • モジュール数は概数だ。Apache 2.4のモジュール索引の正確な総数は数えておらず、索引ページで確認した140個前後という規模だけを書いた。
  • 分類器の未分類区間を全数検討していない。開発区間で16.1%がotherとして残った。標本を目で流し見た限りでは性能改善と動作変更の記述が多かったが、全部読んではいない。
  • インポート閉包は上限だ。関数の中や例外処理ブロックの中の遅延インポートを区別しない。実際の実行経路で必要な数はこれより少ない。
  • 「規模が小さければ長生きする」を統計的に検証した資料は見つからなかった。この記事が示すのは因果の証明ではなく指標の定義と測定方法である。事例は事例にすぎず、反例がありうる。
  • 測定は一時点・一環境の値だ。別のバージョンや別のOSで同じスクリプトを走らせれば数字は変わりうる。

結論: 長生きとは拒否の蓄積である

最初の場面に戻ろう。コミットが3年ないライブラリを使うかどうかは、コミットグラフでは決められない。代わりに三つを測ればよい。どれだけ大きいか、何に縛られているか、直近の変更はなぜ起きたか。

その三つを測ると判断がひっくり返ることが多い。静かなリポジトリが数百行で依存が一つ、直近の変更はすべてランタイム対応なら、それは死んだのではなく終わったのだ。逆にコミットが活発でもツリーに数十個がぶら下がり、ドキュメントがコードより二版遅れているなら、その活発さは安定性ではなく残っている仕事の量である。

そしてこれらの条件は作るときから決まる。小さく保つには機能を断らねばならず、依存を減らすには便利なライブラリを断らねばならず、範囲を守るには利用者の要望を断らねばならず、ドキュメントを維持するには文書のないマージを断らねばならない。寿命は何を入れたかではなく、何を入れなかったかで決まる。

同じ原理が社内コードにもそのまま適用される。ただし社内では断る人が明確でないため条件が守られにくい。だから必要なのが凍結宣言だ。あるモジュールについて「ここまでがこのモジュールの仕事で、それ以外の要望は受けない」と文書に書いた瞬間、そのモジュールは管理対象から外れるのではなくようやく管理され始める。放置と凍結を分けるのはその一文である。

# ソフトウェア寿命の点検 — 指標の測り方 · 凍結判断表 · 引き継ぎ項目

> 出典: braindetox.kr — 20年以上生き残るソフトウェアは何が違うのか
> 検証環境: Windows 10 Pro 10.0.19045 / bash 5.2.37 (MSYS2) / Python 3.13.3 / Node 22.16.0 / npm 11.5.2

---

## 0. 5分で終わる判定 — この順にやるだけ

1. コード行数を数える（コメント・空行を除く）
2. 依存の面積を数える（ロックファイルの項目数、または3ホップ閉包）
3. 直近の変更理由を分類する（機能かそれ以外か）
4. 4節の閾値表に当てはめる
5. 三つとも「完成」側なら凍結候補。一つでも「放置」側なら手を止めて見直す

**一度測った値は判定に使えない。二度目から役に立つ。**

---

## 1. 指標1 — コード量

```
python measure_size.py PATH1 PATH2 ...
```

`measure_size.py`

```python
import os, sys
SKIP = {".git", "__pycache__", "node_modules", ".venv", "build", "dist"}

def measure(root):
    files = code = blank = comment = size = 0
    targets = [root] if os.path.isfile(root) else []
    if not targets:
        for dirpath, dirnames, filenames in os.walk(root):
            dirnames[:] = [d for d in dirnames if d not in SKIP]
            targets += [os.path.join(dirpath, f) for f in filenames if f.endswith(".py")]
    for path in targets:
        files += 1
        size += os.path.getsize(path)
        for line in open(path, encoding="utf-8", errors="replace"):
            s = line.strip()
            if not s: blank += 1
            elif s.startswith("#"): comment += 1
            else: code += 1
    return files, code, comment, blank, size

for arg in sys.argv[1:]:
    print(os.path.basename(arg.rstrip("/\\")), measure(arg))
```

**一緒に記録すること**

- [ ] 最大ファイル一つの行数（平均ではなく最大値が律速）
- [ ] テストを含めた値と除いた値を**別々に**
- [ ] 生成コード（パーサ出力など）を除外したか
- [ ] コメント行をコード行で割った比率

**参考実測値**（Python 3.13.3 標準ライブラリ）

| 対象 | ファイル | コード | コメント | 空行 |
|---|---|---|---|---|
| textwrap.py | 1 | 355 | 68 | 74 |
| csv.py | 1 | 392 | 40 | 81 |
| json | 5 | 1,105 | 51 | 172 |
| email | 29 | 7,764 | 1,035 | 1,592 |
| asyncio | 33 | 11,165 | 1,008 | 2,568 |

## 2. 指標2 — 依存の面積

### 2-1. ロックファイルがある生態系（インストールせずに測る）

```
mkdir probe && cd probe
printf '{"name":"probe","version":"1.0.0","dependencies":{"PKG":"VERSION"}}' > package.json
npm install --package-lock-only --no-audit --no-fund
node -e "const l=require('./package-lock.json');
         console.log(Object.keys(l.packages).filter(Boolean).length)"
```

- `--package-lock-only` は**ツリーの解決だけ**を行う。tarball を取得せず何もインストールしない
- 出る数は**自分自身を含む**。実際に連れてくる他人のリポジトリはその数から1を引いた値

**参考実測値**

| パッケージ | 直接 | ツリー |
|---|---|---|
| express@4.21.2 | 31 | 69 |
| axios@1.7.9 | 3 | 23 |
| chalk@5.4.1 | 0 | 1 |
| lodash@4.17.21 | 0 | 1 |
| typescript@5.7.3 | 0 | 1 |

### 2-2. ロックファイルがない場合 — 3ホップのインポート閉包

```python
def closure_by_depth(root, max_depth=8):
    seen = {root}
    frontier = {root}
    levels = [set(seen)]
    for _ in range(max_depth):
        nxt = set()
        for name in frontier:
            for f in package_files(name):
                for dep in imports_of(f, name):
                    if dep not in seen and package_files(dep):
                        nxt.add(dep)
        if not nxt:
            break
        seen |= nxt
        frontier = nxt
        levels.append(set(seen))
    return levels
```

- **全体閉包は使わない。**飽和して弁別力がない（355行のモジュールと11,165行のモジュールが124と180に収束）
- **3ホップで区切る。**同じ対象が16個から174個へ10倍以上開く
- 構文解析は関数内の遅延インポートまで数えるため、この値は**上限**である

## 3. 指標3 — 変更理由の分布

```
git log --since=2.years --format=%s | python classify_changes.py
```

`classify_changes.py` の中核規則（順序が重要）

```python
RULES = [
    ("defect",   r"(fix\w*|bug|crash\w*|leak\w*|regress\w*|cve|vulnerab\w*|"
                 r"overflow|incorrect\w*|correctly|properly|avoid\w*|prevent\w*|"
                 r"no longer|wrong\w*|fail\w*|hang\w*|deadlock)"),
    ("feature",  r"(add\w*|introduc\w*|implement\w*|new |now support\w*|"
                 r"support\w*|allow\w*|expose\w*|optimiz\w*|improv\w*)"),
    ("external", r"(update\w*|upgrade\w*|bump\w*|bundled|vendored|deprecat\w*|"
                 r"compat\w*|toolchain|compiler|installer|platform|portab\w*|"
                 r"windows|macos|android|freebsd|openssl|sqlite|zlib)"),
    ("doc",      r"(document\w*|docs?|docstring|comment\w*|typo|readme|man page)"),
    ("chore",    r"(refactor\w*|clean ?up|style|reformat|renam\w*|test\w*|"
                 r"remov\w*|drop\w*|release|version bump)"),
]
```

**読み方**

- `feature` 比率 **25%以上** → 成長中。凍結禁止
- `feature` 比率 **10〜25%** → 混合。6か月後に測り直す
- `feature` 比率 **10%未満** → 保守専用。**凍結候補**

**必ず守ること**

- [ ] `other` バケットを**目で読んだ**（実測では最大17.6%がここに残った）
- [ ] `defect` を `external` より先に判定している → **外部対応の比率は下限**だと理解している
- [ ] 一区間ではなく**同じプロジェクトの時間変化**で比較した
- [ ] 正規表現を自組織のコミットメッセージの慣行に合わせた

**参考実測値**（Python 3.13.3 に同梱の変更履歴）

| 区間 | 機能 | 欠陥 | 外部 | その他 | n |
|---|---|---|---|---|---|
| 3.13.0 alpha 1（開発） | 27.1% | 37.4% | 13.4% | 16.1% | 634 |
| 3.13.2 final（保守） | 8.8% | 63.7% | 6.6% | 17.6% | 91 |
| 3.13.3 final（保守） | 11.7% | 66.0% | 15.5% | 1.9% | 103 |

## 5. 凍結判断表

| 点検項目 | 凍結可能 | 凍結不可 | 判定 |
|---|---|---|---|
| 機能要求 | 直近4四半期は新規要求なし | 四半期ごとに要求 | |
| 契約文書 | 入出力仕様がリポジトリ内 | 担当者の頭の中 | |
| 自動検査 | 失敗を知らせるテストが回る | 手動確認 | |
| 外部依存 | ツリーが片手で数えられる | 数十個以上 | |
| 規模 | 非担当者が一日で読める | 読むだけで数日 | |
| 障害履歴 | 直近1年は運用障害なし | 同じ原因が繰り返す | |
| 外の変動 | 外部仕様が固定 | 外が四半期ごとに変わる | |
| 再検討時点 | 日付が固定されている | 決まった時点がない | |

**判定規則**

- 8項目中**7項目以上が「凍結可能」** → 凍結を宣言
- **4〜6項目** → 6か月後に再点検。その間に文書とテストを補強
- **3項目以下** → 凍結不可。通常の保守対象

**注意:** 規模が小さくても**外が頻繁に動くなら凍結不可**である。基準は規模ではなく外部の変動頻度だ。

## 7. 引き継ぎ点検項目

**渡す側が確認すること**

- [ ] ビルドが**一つのコマンド**で終わる（担当者のPCに依存しない）
- [ ] 必要なランタイム版と外部ツールが**設定ファイルに固定**されている
- [ ] テストが回り、**失敗したときに失敗と言う**
- [ ] 配備手順が文書にあり、その通りにやれば配備できる
- [ ] ロールバック手順が文書にある
- [ ] なぜこの構造を選んだかの**決定記録**が残っている
- [ ] おかしく見える分岐ごとに**そうなった理由**がコメントか課題として残っている
- [ ] ドキュメントがコードと同じリポジトリにある
- [ ] 例が**実行可能な形**である

**権限 — ここが最も抜けやすい**

- [ ] リポジトリ管理権限の保有者が**2名以上**
- [ ] 配備権限の保有者が2名以上
- [ ] パッケージレジストリの所有権が**個人アカウントではない**
- [ ] 署名鍵の保管場所とアクセス方法が文書にある
- [ ] ドメイン・証明書の更新主体が**役割として**指定されている
- [ ] 外部サービスのアカウントが共用アドレスで登録されている

**受け取る側が確認すること**

- [ ] 文書だけを見て**最初から最後までビルドと配備**をやってみた
- [ ] わざと一つ壊してみて**テストが捕まえるか**確認した
- [ ] 最大のファイル一つを**最後まで読んだ**
- [ ] 直近1年の課題と障害を眺め、繰り返しの型を探した
- [ ] 分からないことを**文書に質問として残した**（人に聞いて終わりにしなかった）

## 8. 書き直し判定表

| 状況 | 判定 |
|---|---|
| 要求の前提が変わり既存構造では表現不能 | 書き直し |
| ランタイム・言語・中核ライブラリのサポート終了 | 書き直しまたは移植 |
| 読んで直す人がおらず文書からも復元不能 | 書き直し |
| セキュリティ欠陥が構造から繰り返し発生 | 書き直し |
| 遅いが律速が特定されている | 部分置換 |
| 直近の変更がバグ修正・外部対応中心 | 維持 |
| 不満がコードの書き方や流行に関するもの | 維持 |
| 古いという以外に理由がない | 維持 |

**書き直しに着手する前に必須**

- [ ] 既存コードが**なぜそういう形なのか**を先に復元した
- [ ] おかしく見える分岐が障害対応の痕跡かどうか確認した
- [ ] 新しいコードが通すべき**既存動作の一覧**を洗い出した
- [ ] データ・ファイル形式の互換範囲を決めた

## 9. やってはいけないこと

- ❌ **コミットグラフだけで判定** — それは残った仕事の量であって健康状態ではない
- ❌ **直接宣言した依存の数だけ数える** — 実測では宣言1個がツリー69個だった
- ❌ **全体の推移的閉包で比較** — 飽和して何も区別できない
- ❌ **分類器の結果をそのまま信頼** — `other` バケットを読まないと最大17.6%を取り逃がす
- ❌ **日付のない凍結** — 放置と区別がつかない
- ❌ **個人名で担当を指定** — 人事異動に耐えられない
- ❌ **セキュリティ修正の費用を0とした凍結** — それは凍結ではなく負債だ
- ❌ **ドキュメントをウィキに分離** — 更新主体が割れれば必ず遅れる
- ❌ **一度測って判定** — 指標は同じ物差しの反復でのみ意味を持つ
- ❌ **小さいという理由だけで良いと結論** — その分の費用が利用者側へ移っただけだ
- ❌ **依存が多いという理由だけで悪いと結論** — 速度が正しい局面がある
