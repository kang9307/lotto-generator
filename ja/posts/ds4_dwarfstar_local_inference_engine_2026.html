契機 — 単一モデル特化から複数フロンティア系列への拡張

Redisの生みの親であるSalvatore Sanfilippo（antirez）が主導するオープンソース推論エンジンDwarfStar 4（ds4）が、公式技術文書サイト（dwarfstar.sh）を立ち上げ、そのアーキテクチャを公開した。ds4は当初、2,840億パラメータの巨大なMoE構造を持つDeepSeek V4 Flashを個人用ワークステーションで動かす目的で開発されたC言語製推論エンジンである。しかし近時の更新により、GLM 5.x（GLM 5.2およびGLM 5.3 Flash）やQwen3.8 Flash Nextへとサポート対象を大きく拡大した。

超巨大MoEモデルをローカル環境で動かす試みは、メモリ容量と帯域幅という物理的限界に直面してきた。数千億パラメータのモデルは量子化なしには128GB級のマシンに収まらず、一般的な推論基盤はクラウドの分散クラスタを前提としている。ds4は大容量統合メモリを備えたApple Silicon Mac、Linux CUDA、AMD ROCmマシンを対象とし、逆の制約から設計をスタートさせた。ローカル環境におけるモデル実行の背景はローカルLLM実行ガイドやMac統合メモリの最適化手法でも詳しく分析されている。

単一モデルに極限まで特化していたエンジンが複数のフロンティアモデルを抱え込むにあたり、設計思想やリソース管理がどのように変化したのか、公式文書の記録から確認する。

設計思想 — 汎用ランナーではなく狭く深い最適化エンジン

公式文書が最も強く強調している方針は「ds4は汎用GGUFランナーではない（Not a generic GGUF runner）」という点である。llama.cppやOllamaがコミュニティの多種多様なモデルを汎用的に実行することを目指すのに対し、ds4は厳選された少数のモデル系列と、プロジェクト自身がエンドツーエンドで検証した専用GGUFレイアウトのみを対象とする。

  • プロジェクト公式が検証した特定レイアウトのGGUFファイルのみを読み込み、一般的なコミュニティGGUFは拒絶する。
  • 対象モデルのアテンション構造に合わせてC言語カーネルとアクセラレータ（Metal、CUDA、ROCm）を直接最適化する。
  • 対応モデルのすべてについて、公式オリジナルモデルの出力とレイヤー単位で照合テストを実施する。

この目的を絞り込む戦略は、汎用的な抽象化レイヤーを排除し、モデル構造固有のボトルネックをCコードで直接解決することを可能にしている。

非対称2ビット量子化とMoE圧縮メカニズム

DeepSeek V4 FlashやGLM 5.xのような大規模モデルが単一マシンに収まる鍵は「非対称2ビット量子化（Asymmetric 2-bit quantization）」にある。MoEアーキテクチャでは、トークンごとに活性化される専門家（routed experts）はごく一部にすぎない。ds4はこの性質を徹底活用する。

ルーティングされる専門家パラメータの大部分は2ビット（q2）まで大胆に圧縮され、全体のデータ量を劇的に減らす。一方で、すべてのトークンが通過する重要な共有パス（shared paths）や中核アテンション層は高精度を保つ。公式ドキュメントではこのアプローチを「圧縮されたが、知性を切除されていない状態（Compressed, not lobotomized）」と表現している。これにより、2,840億パラメータの巨大ネットワークが96GB〜128GBのメモリ枠内に収まりつつ実用的な推論能力を維持する。

配布スクリプトでもds4f-q2、glm53-q2、qwen38-q2のように専用調整されたプロファイル名が使用され、PROモデル向けには重要度行列（imatrix）適用版も用意されている。

ディスク市民としてのKVキャッシュ — SSD保持とプリフィル省略

コーディングエージェントの運用において最大の無駄となるのが、セッションごとに長大なコードベースをゼロから再計算するプリフィル（prefill）の待機時間である。数万トークンに達するコンテキストでは、プリフィルが膨大な時間と帯域を浪費する。

ds4はKVキャッシュをメモリ内にとどめず「ディスクの第一級市民（disk citizen）」として扱う。エンジンはプロンプト接頭辞のSHA1ハッシュを算出してキーとし、長大な接頭辞のKVキャッシュをSSDへ直接永続化する。デモ画面に示された動作は明快である。

プロセスを再起動しても、入力プロンプトの接頭辞ハッシュが合致すれば、モデルは再計算を行わずSSDからシリアライズされたKVキャッシュを即座にメモリへ展開する。数千行のファイルをコンテキストに載せたセッションであっても、再起動直後から即座に対話を再開できる。コンテキスト保持の重要性はローカルエージェントコーディング分析でも論じられた要素である。

単一エンジンと3つのインターフェース — CLI・サーバ・ネイティブエージェント

ds4のユニークな点は、単一のC推論コアの上で3つの異なるインターフェースが完全に同一のモデル状態とKVキャッシュを共有して動作することである。

  • ./ds4: ターミナル対話用CLI。/read、/think、/ctxなどの対話コマンドを内蔵する。
  • ./ds4-server: 外部連携用のローカルHTTP APIサーバ。--ctx 100000等でコンテキストを指定して常駐させる。
  • ./ds4-agent: 永続的なコーディングセッションとツール実行を担うネイティブエージェント。

とりわけ./ds4-serverは業界標準であるOpenAI互換（/v1/chat/completions、/v1/responses）のみならず、Anthropic互換（/v1/messages）のエンドポイントをネイティブに備える。Claude Code、OpenAI Codex CLI、OpenCode、Piなどの外部エージェントにおいてベースURLをローカルに向け替えるだけで、ローカルのds4インスタンスへと推論負荷を転換できる。デスクトップ統合のあり方はDeepSeek Harnessの解説にも通じるものがある。

対応モデルと64GB〜1024GBのハードウェア適合基準

公式ドキュメントの適合性チェック機能（Fit Check）およびハードウェアガイドには、搭載メモリに応じた具体的な対応モデルが示されている。

メモリ容量適合モデルと実行形態推奨ハードウェア環境
64 GBQwen3.8 Flash Next Q2（常駐41.73GiB、n-gramはSSD参照）Apple Silicon Mac（8Kコンテキスト、1024チャンク推奨）
96〜128 GBDeepSeek V4 Flash Q2完全常駐、GLM 5.3 Q2、V4.1 Q2はSSDストリーミングM5 Max 128GB（Metal）、DGX Spark 128GB（CUDA）
256 GBV4 Flash Q4完全常駐、GLM 5.3 Q2完全保持、V4.1 Q2本体重み常駐Apple Silicon Mac 256GB
512 GBDeepSeek V4.1 Q4常駐検証済み、PRO Q2の運用余裕を確保Mac Studio 512GB（Metal）
1024 GB（2台）DeepSeek PRO Q4分散実行（Thunderbolt/RDMAによるレイヤー分割）Mac Studio 512GB 2台構成クラスタ
64 GB 未満実用基準未満（モデル重みおよびアクティベーション容量不足）ローカル実行不可と判定

アクセラレータとしてはApple Silicon（Metal）が主軸であり、Linux NVIDIA CUDA（DGX Sparkおよび汎用GPU）、Linux AMD ROCm（Strix Halo搭載機）が公式サポートされる。ただしROCm環境ではV4 FlashとGLMのみが動作し、V4.1とQwen3.8は対象外となっている。

ベンチマーク実測値の分析 — プリフィルと生成速度の分離評価

ローカルモデルの評価において生成トークン速度のみを見るのは不完全である。エージェント用途では、長大なコードを読み込むプリフィル処理速度こそが実効パフォーマンスを決定づける。公式ベンチマークは両指標を明確に分離して報告している。

  • M5 Max（128GB、Q2、2,048トークン）: プリフィル 790.2 t/s、生成 39.4 t/s。
  • M5 Max（128GB、Q2、65,536トークン）: プリフィル 398.5 t/s、生成 27.6 t/s。
  • DGX Spark（128GB、Q2、2,048トークン）: プリフィル 825.8 t/s、生成 18.1 t/s。
  • DGX Spark（128GB、Q2、65,536トークン）: プリフィル 823.0 t/s、生成 13.8 t/s。

この数値はアーキテクチャ特性を反映している。Apple Siliconは広帯域統合メモリの恩恵により、長大なコンテキストでも27.6 t/sという高い生成速度を維持する。一方DGX Sparkは、65Kトークンに達しても823.0 t/sという驚異的なプリフィル速度を維持し、並列処理能力の高さを示している。32K参照環境では、M5 Maxが生成34.4 t/s・プリフィル557 t/s、DGX Spark GB10が生成14.4 t/s・プリフィル856 t/sであった。

ビルドと実行手順 — バックエンド別コンパイルと安全なコマンド

ds4はピュアC言語で構築されており、重厚な外部依存パッケージを必要としない。公式手順は簡潔に整理されている。

モデル重みの取得は公式スクリプトを通じて行う。

git clone https://github.com/antirez/ds4
                    cd ds4 && ./download_model.sh ds4f-q2

コンパイルはマシンのアクセラレータに応じたmakeターゲットを選択する。

make              # macOS Metal
                    make cuda-spark   # Linux NVIDIA DGX Spark
                    make cuda-generic # Linux generic CUDA
                    make strix-halo   # Linux AMD Strix Halo
                    make cpu          # CPU-only for diagnostics

実行時は対話CLIを立ち上げるか、コンテキスト長を指定してAPIサーバを起動する。

./ds4
                    ./ds4-server --ctx 100000
                    ./ds4 -m gguf/GLM-5.3-Flash-Q2.gguf --ctx 32768
                    ./ds4 --ctx 8192 --prefill-chunk 1024

外部ツールを接続する際はサーバが提供するAPI規格を利用する。

# OpenAI互換エンドポイント:
                    POST /v1/chat/completions
                    # Anthropic互換エンドポイント:
                    POST /v1/messages
                    # Responsesエンドポイント:
                    POST /v1/responses

確認できなかったこと

  • SSDに保存されたKVキャッシュファイルの自動クリーンアップ（TTLやLRU）方針は公式ドキュメントに明記されていない。
  • Windowsネイティブ環境（MSVC環境）におけるビルド対応状況は文書に言及がない。
  • Claude Code等の高度なマルチターンツール呼び出し（Function Calling）における構文解析成功率の統計は示されていない。
  • AMD ROCm環境においてQwen3.8およびV4.1が除外されている具体的な技術的要因は公表されていない。
  • Mac Studio 2台をThunderboltではなく通常の10GbE有線LANで接続した際の推論遅延測定値は記載がない。
  • ビジョン入力対応時における画像解像度の上限値やビジョンエンコーダのVRAM消費量は数値化されていない。
  • 非対称2ビット量子化適用時におけるFP16元モデルに対する定量的精度劣化幅（MMLUスコア等）は示されていない。
  • CPU単体動作モード（make cpu）における実際の推論トークンレートは記載がない。
