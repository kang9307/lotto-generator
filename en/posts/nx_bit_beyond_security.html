What the No-Execute Bit Actually Prevents - The Work NX Does Outside Security, and What It Costs

When readable meant executable, the second face of the bit in speculative instruction fetch, and the price of holding W^X

2026-09-06 Dev & Infra

The no-execute bit is almost always introduced in the language of attack and defense. Push machine code into a buffer and it will not run from there. Data pages and code pages live on opposite sides of a line. None of that is wrong. But the range that this bit actually governs inside the page tables is wider than that story, and the extra width shows up most clearly in situations where no attacker appears at all.

A recent article made that width very concrete. A developer building a bare-metal ARM64 hypervisor spent weeks on a phone that refused to boot, and in the end fixed it by marking a mapping execute-never. The culprit was not an intruder. It was the branch predictor. And once the fix was in, the hypervisor picked up a layer of defense in depth as a side effect. The usual order of that story is completely reversed.

What follows is that reversed order. Exactly what an execute permission is inside a translation table, what readable implies executable meant in the era before the bit existed, what kind of failure is solved by the property that execute-never also stops speculative fetch, and what a program that generates its own machine code at runtime hands over in exchange for respecting that property.

The flag names, macro definitions and documented behavior below are as written in the primary sources: Linux man pages, kernel documentation and kernel source, Apple developer documentation, and the OpenBSD man pages. Where a vendor architecture manual could not be cross-checked directly, the gap is collected with its reason in the second-to-last section.

The trigger - a hypervisor that would not boot, fixed by a security bit

The article in question is a guest post by a writer named Sonya on the purplesyringa blog. The subject is a bare-metal ARM64 hypervisor for postmarketOS. The symptom is simple enough to state in one line. Turn on the interception of reads to a particular system register and the phone hangs and resets. The same code runs perfectly well under QEMU.

Half the article is the sound of hypotheses collapsing one after another. The idea that the exception handler was corrupting registers fell apart under single-stepping in QEMU. The idea that this was an instruction cache versus data cache coherency problem was addressed by moving a sorting step to build time. The idea that the hardware was behaving out of spec led to more exception handlers being installed, and none of them caught anything.

The breakthrough came from comparing binaries. The difference between the version that worked and the version that died was two forms that are semantically identical. A static direct branch, with the destination baked into the instruction itself, survived. An indirect branch that reads its destination out of a register died. There is only one thing that difference can point at: branch prediction.

The predictor was mispredicting to address zero. And under the hypervisor's one-to-one mapping, that address held locked-out bootrom. The fix the author chose was to mark that region execute-never, and at that moment the phone booted for the first time. The closing sentence of the article captures the shape of the whole thing: since a way to map memory non-executable had to be implemented anyway, everything except the payload was mapped non-executable, and so the hypervisor finally got a bit of defense in depth too. Security arrived as a by-product rather than as the goal.

What an execute permission is - a bit attached to one page

Permissions attach at page granularity

In virtual memory the smallest unit of address translation is the page. Each entry in the translation table records not only which physical frame a page maps to, but also what may be done with that page. May it be read. May it be written. And may the bytes inside it be fetched as instructions.

On the application side, the window onto those three questions is the prot argument of mmap and mprotect. The man pages define each value in a single sentence. PROT_READ means the memory can be read, PROT_WRITE means it can be modified, PROT_EXEC means it can be executed, and PROT_NONE means the memory cannot be accessed at all. The prototype is int mprotect(void *addr, size_t size, int prot);, and the starting address has to be aligned to a page boundary.

FlagDefinition in the man pageWhat it means in practice
PROT_READThe memory can be readReachable as data. Load instructions succeed
PROT_WRITEThe memory can be modifiedStore instructions succeed. On i386 this implies read access
PROT_EXECThe memory can be executedInstruction fetch is allowed. Meaningful only where the hardware separates the axis
PROT_NONEThe memory cannot be accessed at allAny access faults. Used to build guard pages

What happens on hardware with no execute axis

Here the careful qualifier in the man page matters. Whether PROT_EXEC has any effect different from PROT_READ depends on the processor architecture, the kernel version and the process state. The same document notes that when the READ_IMPLIES_EXEC personality is set on a process, specifying PROT_READ will implicitly add PROT_EXEC.

So having three flags in the API does not mean the hardware has three axes. The API has always accepted three, but the execute axis only started carrying real meaning once the hardware gained a place to record it separately. Until then the execute axis rode along on the read axis, and a page you could read was a page you could run.

Before that - readable meant executable

The reason is a question of room. A traditional 32-bit x86 page table entry is 32 bits wide. Address bits and assorted status bits already filled that width, and there was no spare position to carve out for an execute permission. The no-execute bit arrived in page tables only after entries grew wider.

That history is still visible in the Linux kernel source. The x86 page type header reserves position 63 for the no-execute bit and attaches a comment saying it is valid only after a cpuid check. The actual mask is then defined to use that bit position only when the build is 64-bit or uses PAE, and to be zero in every other configuration. On hardware without the bit, the mask becomes a value that sets nothing at all.

So the arrival of the no-execute bit is less a story about one more protection feature and more a story about one more state the translation table can express. Before it, there was simply no way to write down the difference between a page you may read and a page you may run. The separation of data from code was a convention observed by programs rather than a property enforced by hardware.

That distinction is the root of everything that follows. Once a state becomes expressible, the expression does not stay confined to the single purpose that motivated it. Execute-never was introduced for defense, but the moment it occupied a place in the translation table it began to be used as a general statement about how the processor is permitted to treat that page.

W^X - never both permissions at the same moment

Once the execute axis existed, the principle known as W^X followed immediately. No page may hold write permission and execute permission at the same time. The no-execute bit does not enforce this by itself. The bit only makes states writable; the prohibition on a particular combination is a policy laid on top of it. Which is why the layer and the strength of that enforcement differ from system to system.

OpenBSD holds the line most tightly. Its man page states plainly that mappings requesting both write and execute are not permitted, and it narrows the exception path to two conditions that must hold together. The filesystem has to be mounted wxallowed and the process has to be link-time tagged wxneeded. A violation comes back as ENOTSUP, and the documentation even points at kern.wxabort as a way to diagnose where the failure happened.

Apple silicon is also on the strict side. Apple's developer documentation states that memory protection is enabled for all apps regardless of whether they adopt the Hardened Runtime, in contrast with Intel-based Mac computers where it applied only to apps that adopted it. The rule while that protection is on is written as a single sentence too: a thread cannot write to a memory region and execute instructions in that region at the same time.

Linux picks a different place to stand. Neither the mmap nor the mprotect documentation says that the write plus execute combination is rejected. The controls live in other layers instead. Mount a filesystem no-exec and any attempt to map a file from it with PROT_EXEC is refused with EPERM, as the mmap man page records. The no-exec seal on memory files, which appears later in this article, belongs to the same family.

What the source article actually claims - speculative instruction fetch

Same meaning, only one of them died

The contrast that turned the debugging around looks like this in shape.

    bl   get_ctr_el0     // static direct branch — destination is baked into the instruction
    blr  x1              // indirect branch — destination is read from a register at run time

Both lines call the same function. The only difference is when the destination becomes known. A direct branch already has its destination at the moment the instruction is fetched. An indirect branch makes the processor predict a destination before the register value is ready. When the prediction misses, the results are discarded later, but the instructions along that path have already been fetched.

What a Device marking does not close

On ARM, memory-mapped I/O regions are marked as Device memory rather than Normal memory. A common assumption grows out of that: mark it Device and the processor will not touch it casually. The ARM documentation sentence quoted in the source article narrows that assumption by exactly one notch. There is a subtle distinction that is easy to miss, and it is this: marking a region as Device prevents speculative data accesses only, while preventing speculative instruction accesses requires marking the region non-executable.

The situation in the article fell precisely into that gap. Because the mapping was one-to-one, address zero was locked-out bootrom, and a mispredicted indirect branch tried to fetch instructions from it. The data axis was already closed by the Device marking; the instruction axis was still open. Hence the fix was execute-never. What got reduced was not attack surface but the range the processor can touch on speculation alone.

This is the point the title of the source article is aiming at. The no-execute bit functions as an architectural attribute that governs speculative behavior before it functions as a defense. Read data execution prevention purely as a countermeasure to stack overflows and you will miss the hardware-level failures that the very same bit catches.

Already baked into the kernel source - execute-never on device mappings

General purpose operating systems already ship that conclusion as a default. The arm64 page protection header in Linux shows it at a glance.

#define PROT_DEFAULT		(PTE_TYPE_PAGE | PTE_MAYBE_NG | PTE_MAYBE_SHARED | PTE_AF)

#define PROT_DEVICE_nGnRnE	(PROT_DEFAULT | PTE_PXN | PTE_UXN | PTE_WRITE | PTE_ATTRINDX(MT_DEVICE_nGnRnE))
#define PROT_DEVICE_nGnRE	(PROT_DEFAULT | PTE_PXN | PTE_UXN | PTE_WRITE | PTE_ATTRINDX(MT_DEVICE_nGnRE))
#define PROT_NORMAL		(PROT_DEFAULT | PTE_PXN | PTE_UXN | PTE_WRITE | PTE_ATTRINDX(MT_NORMAL))

The base attribute set, PROT_DEFAULT, carries no execute-never bit at all. What device mappings add on top of it is PTE_PXN and PTE_UXN together, and the normal memory the kernel uses does the same. Each macro then ends with a separate memory type selector. The fact that the execute axis and the memory type axis are filled in independently is visible right there in a single line of code.

Two things follow. First, arm64 has not one execute-never bit but two. They are split by privilege level, which makes it possible to express a page that user space may execute but the kernel may not. Second, executable kernel text is produced by removing those bits rather than by adding an execute permission. The default is prohibition and permission is the exception. That ordering matters more than it looks.

Which means the property the author of the source article had to implement by hand is a property that a general purpose kernel already lays down for free. Someone writing page tables directly on bare metal inherits none of those defaults. In the place where the operating system's quiet convention used to sit, a subtle distinction in the architecture manual showed up immediately as a boot failure.

Faults as signals - same machinery, different bit

Violate a page permission and you get a fault, and the fault goes to the kernel. But there is a whole family of techniques that treat that fault not as an error but as a notification. A protection mechanism turned into an observation mechanism. On Linux the representative of that family is userfaultfd.

The man page defines it as the delegation of page-fault handling to a user-space application. The purposes it names are lazy restore for checkpoint and restore mechanisms, and post-copy migration that allows nearly uninterrupted execution when moving virtual machines and containers from one host to another. The mechanism is spelled out as well. When a fault occurs in a registered region, the faulting thread is put to sleep, an event is generated that can be read through the file descriptor, and user space reads it and responds.

There are three registration modes: access to a page that is missing, a write to a page that is write-protected, and a minor fault where the page exists but the page table entries do not. The documentation positions the facility as an alternative to traditional user-space paging techniques based on the use of the SIGSEGV signal.

And here comes the fact that matters most for the axis of this article. There is no execute mode on that list. The fault-as-signal family runs on the read and write axes. Execute permission is used less to generate a notification and more to stop the access from happening in the first place. The source article went the same direction exactly. It did not catch a fault and handle it; it removed the situation that would have faulted.

So the structure by which a security feature ends up doing other work splits into two branches. One borrows the event that a fault represents. The other borrows the range of hardware behavior that a permission bit defines. The no-execute bit belongs to the second branch.

How a JIT holds W^X

A program that produces executable code while it is running collides with W^X directly. Machine code has to be written and then run, and the principle forbids holding both permissions in the same instant. What just-in-time compilation is trying to buy in the first place is covered in the article on Perry, the compiler that lowers TypeScript straight to LLVM machine code; the concern here is narrower and only about how the permissions are handled.

Flipping the permission

/* Open a write window, fill it with machine code, then make it executable */
void *p = mmap(NULL, len, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
if (p == MAP_FAILED) return -1;

emit_code(p, len);                       /* up to here the page is not executable */

if (mprotect(p, len, PROT_READ | PROT_EXEC) != 0) return -1;
/* from this point the same page is executable and no longer writable */

This is the simplest shape. Open an anonymous mapping for reading and writing, fill it with machine code, then flip it to read plus execute with mprotect. Before the flip it cannot be executed and after the flip it cannot be written, so at no instant do write and execute stand together on the same page.

Splitting the mapping in two

/* Attach two virtual addresses with different permissions to the same physical pages */
int fd = memfd_create("jit", MFD_CLOEXEC);
if (fd == -1) return -1;
ftruncate(fd, len);

void *rw = mmap(NULL, len, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
void *rx = mmap(NULL, len, PROT_READ | PROT_EXEC,  MAP_SHARED, fd, 0);

emit_code(rw, len);   /* write only through rw, execute only through rx */

The same file descriptor is mapped twice as a shared mapping. The mmap man page states that updates to a shared mapping are visible to others mapping the same region, so bytes written through rw are read as instructions through rx. The physical pages stay single, only the virtual addresses double, and the permissions differ between them.

The flip syscall disappears and something else takes its place. Two sets of addresses must be carried around, and the question of which window a relative branch target was computed against keeps coming back. And if the no-exec seal described later is in force, this approach does not exist at all.

Apple silicon - flipping per thread

Apple built a third route. A JIT region is created by passing the MAP_JIT flag to mmap. An app that adopts the Hardened Runtime needs the com.apple.security.cs.allow-jit entitlement before the system allows it to call mmap with that flag, and an app that does not adopt the capability does not need the entitlement to use the flag at all. With the Hardened Runtime and that entitlement together, however, an app can create only one memory region with MAP_JIT set.

The flip itself is done through pthread_jit_write_protect_np. The documentation also describes a newer path. Adding the com.apple.security.cs.jit-write-allowlist entitlement lets an app write into its JIT region through pthread_jit_write_with_callback_np, and an app carrying that entitlement can no longer call pthread_jit_write_protect_np. A further entitlement exists for updating the allowlist at run time when libraries are loaded dynamically.

The structurally interesting part is the scope of the flip. The documentation says the callback route makes the memory region writable and not executable for the current thread only, and that on the way back it makes the region executable and not writable for the current thread. mprotect from the previous section does nothing of the kind. It changes the mapping in the address space, so for as long as the window is open every thread in the process sees that page as writable. The per-thread flip narrows that window to one thread.

And permissions are not the whole job. Apple's documentation insists that sys_icache_invalidate be called before executing the machine instructions on a recently updated memory page. On Apple silicon the instruction caches are not coherent with the data caches, and executing without invalidating can produce unexpected results. The same call is documented as safe on Intel-based Mac computers, where it does nothing.

This overlaps with the source article. One of the hypotheses that fell there was instruction versus data cache coherency as well. Anything that produces its own machine code has to handle permissions and caches together. Get only one of the two right and the symptom looks identical either way: an irreproducible hang.

Where the cost really sits - syscalls, page granularity, caches

The price of holding W^X splits into several parts. Whichever approach is chosen, some of these are always paid.

  • Syscalls — the flip approach enters and leaves the kernel every time a batch of machine code is produced. The more finely code generation is divided, the more often this cost lands.
  • Page granularity — permissions change for a whole page, not for a range of bytes. Pack several small code fragments into one page and opening it to fix one of them makes all the others writable along with it.
  • The whole address space — mprotect changes the mapping for the process. In a multithreaded program, the interval where the flip is open is an interval open to every thread.
  • Doubled virtual addresses — double mapping trades the syscall away for two addresses. Address arithmetic inside the generated code has to stay consistent about which window it is based on.
  • Instruction caches — on some platforms a cache maintenance step is mandatory before freshly written bytes are executed as instructions.
  • Policy collisions — with certain hardening knobs turned on, some of the approaches above simply do not exist. The no-exec seal in the next section is the example.

One intuition tends to go wrong here. Setting or clearing the no-execute bit itself costs essentially nothing. What costs is changing that state, and the reason for changing it is that the program manufactures code while it runs. In a process that only ever runs statically compiled code, this entire cost is effectively zero.

Where architectures differ

The x86 definition is exactly as described earlier. Seeing the shape makes it obvious where the condition sits.

#define _PAGE_BIT_NX		63	/* No execute: only valid after cpuid check */

#if defined(CONFIG_X86_64) || defined(CONFIG_X86_PAE)
#define _PAGE_NX	(_AT(pteval_t, 1) << _PAGE_BIT_NX)
#else
#define _PAGE_NX	(_AT(pteval_t, 0))
#endif

The bit position is fixed at a single number, but whether that bit actually exists depends on the configuration. The mask is raised only for 64-bit builds or PAE, and is zero otherwise. The comment carries the same message. Being valid only after a cpuid check means the capability was not there from the start but was added later as an option.

arm64 is structured differently. Execute-never comes in two pieces split by privilege level, and a separate memory type axis sits alongside them. The macros in the earlier section, where both axes are filled on the same line, are the evidence.

ArchitectureHow execute-never is expressedName in the Linux sourceAxis that must be read alongside
x86-64 and PAEA single bit at position 63 of the page table entry_PAGE_BIT_NX and _PAGE_NXNone. The execute axis is singular
32-bit x86 without PAEThe bit does not exist_PAGE_NX is defined as zeroThe read axis doubles as the execute axis
arm64 privileged levelA bit forbidding execution at the privileged levelPTE_PXNA separate memory type axis exists
arm64 unprivileged levelA bit forbidding execution at the unprivileged levelPTE_UXNA separate memory type axis exists
arm64 device regionsBoth bits are included in device mappings by defaultPROT_DEVICE_nGnRnE and PROT_DEVICE_nGnREA Device marking closes the data axis only

The last row of that table is the wall the source article ran into. Writing Device does not close the execute axis automatically. The two axes govern different things.

Where operating systems differ

Given the same hardware bit, operating systems layer different policies on top. Restricted to what the documentation actually says, it comes out like this.

SystemMappings asking for write and executeException pathSupporting machinery
OpenBSDNot permitted. Rejected with ENOTSUPFilesystem mounted wxallowed and the process link-time tagged wxneededkern.wxabort to locate the failure
macOS on Apple siliconA thread cannot write and execute in the same region at onceMAP_JIT regions plus dedicated entitlementsThe flip is per thread. Instruction cache invalidation is mandatory
macOS on IntelProtection applies only to apps that adopt the Hardened RuntimeThe same entitlement schemeThe cache invalidation call does nothing there
LinuxNo statement in the mmap or mprotect docs forbidding the combinationThe policy is applied in other layersNo-exec mounts and the no-exec seal on memory files

The Linux row is easy to misread. The absence of a prohibition in the documentation means that the base syscall layer does not reject the combination, not that W^X cannot be enforced on Linux. Linux moved that decision out to mount options, to per-object seals, and to separate security modules. Only the location of the policy is different. The same question about where to draw a trust boundary shows up on the web side in the article on why you cannot trust the client.

Execute permission as policy - the no-exec seal

Linux memory files contain a case where execute permission stopped being a page bit and became a property of an object. The kernel documentation defines three controls.

  • The no-exec seal flag — when this bit is set, the memory file is created non-executable and an execute seal is applied together with it, so the file cannot be modified to add execute permission later.
  • The exec flag — when this bit is set, the memory file is created carrying execute permission.
  • The system-wide setting — at value zero, a call specifying neither flag behaves as if execution were allowed; at one it behaves as if the no-exec seal had been requested; and at two a call without the seal is rejected outright.

The kernel documentation is explicit about the reasoning. Executable memory files become a route for confused deputy style misuse and for bypassing no-exec policy, yet there are clearly legitimate uses such as a container runtime executing a binary, so a way to tell the two apart was needed.

What that design demonstrates lands right on the axis of this write-up. Execute permission became a state that cannot be reversed once chosen. What used to be a single bit in a page table now attaches to a file descriptor as an object and governs the rest of that object's life. A bit that entered as a protection mechanism has been promoted into the vocabulary of resource management.

And it collides head-on with the double-mapped JIT from the earlier section. With the system-wide setting at its strictest value, a memory file for a JIT cannot be created at all. One hardening knob switches off one legitimate capability. Which side is right depends on what that system is running, and no default value can make the judgment on anyone's behalf.

Where the source article and this write-up part ways

The claim in the source article is narrow and clear. It is a debugging record for one bare-metal ARM64 hypervisor, and the conclusion is that a Device marking and an execute-never marking prevent different things. The author lost weeks to missing that fact, and the problem dissolved once it was known.

What is not in that article deserves to be stated just as plainly. The origin of the no-execute bit, the per-system differences in W^X policy, JIT implementation strategies and the x86 situation are not its subject. Everything filling those sections above rests on the primary text of each document and source file, and none of it stretches the source article's claim.

One line should be drawn against over-generalization as well. The article's conclusion is that a Device marking must not be read as closing the instruction axis, not that turning on execute-never resolves speculation-related problems in general. That would be an entirely different claim, and the article does not make it.

What remains is a single sentence. A mechanism introduced for defense turned out to be expressing a different architectural rule all along, and for the developer who needed that rule, security arrived as a by-product. A gap between the purpose of introduction and the eventual use is not a failure. Once one more state becomes expressible, the expression always travels further than the place it started.

What could not be confirmed

  • The architecture documentation pages on the ARM developer site are rendered by script, so their body text could not be opened. The ARM documentation sentence quoted in the source article was cross-checked only through that article, and the manual's section and revision numbers could not be pinned down.
  • The Intel and AMD architecture manual PDFs could not be opened. The bit at position 63 on x86 and its conditional definition were cross-checked only against the definition and comment in the Linux kernel header. Vendor naming does not appear in that header, so no vendor name is used in the body text.
  • The expansion of the names PXN and UXN was read off the macro names and could not be confirmed against the ARM manual text. The body describes only the function, which is execute-never per privilege level.
  • In the disassembly in the source article, the register number used by the indirect branch appeared differently across renderings. Since the point rests on the contrast between direct and indirect branches, the prose keeps the shape and drops the number.
  • Figures for the real cost of a permission flip or a double mapping were not found in any primary source. Only the kinds of cost are listed, never their magnitude.
  • The macOS version that introduced Apple's callback-based write API could not be established. The documentation describes the entitlement and the behavior without a version note.
  • Text about the execute seal on memory files was not found on the man page side, so the kernel documentation was used instead. The gap looks like a difference in revision timing between the two documents.
  • The Linux kernel source quotations are taken from the main development branch rather than pinned to a release tag. Macro composition can differ between versions.
