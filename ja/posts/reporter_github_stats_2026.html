GitHub Insightsの14日制限問題 - Repo-rterに見るローカル永続保存という選択肢

GitHub Insightsはなぜ14日分のデータしか表示しないのか - ローカル永続保存アプリRepo-rterに見るオープンソース成長指標の管理法

2026年7月13日 開発・インフラ

序論: スターは残るのにトラフィックは消える

オープンソースのリポジトリを一つでも運営したことがある人なら、GitHub Insights画面で一度はもどかしさを感じたはずだ。Trafficタブを開くと閲覧数(Views)とクローン数(Clones)のグラフが表示されるが、どれだけスクロールしてもたった14日分しかない。先月のリリースが実際にどれだけ閲覧されたのか、流入が急増したのが正確にいつだったのかは、すでに跡形もなく消え去っている。一方でスター数は、star-historyのような外部ツールを使えば何年も前の履歴までグラフ化できる。この非対称性はなぜ生まれるのか。

2026年7月、GeekNewsにこの問題に正面から取り組んだオープンソースプロジェクトRepo-rterが紹介された。GitHub Insightsの14日分のデータをローカルデスクトップアプリで永久保存するというアイデアだが、本稿はこのツール自体を宣伝するのではなく、その背景にある問い - なぜGitHubはトラフィックを14日しか見せないのか、そしてそのデータを自分で所有するとはどういう意味か - を掘り下げる。

1. GitHub Insightsの14日制限とは何か

1.1 何が、どう消えるのか

GitHub公式ドキュメントによれば、リポジトリへの書き込み(push)権限を持つユーザーは、Insightsの Trafficページで直近14日間のフルクローン数、ユニーク訪問者数、閲覧数を確認できる。クローン数と訪問者数は毎時更新され、人気コンテンツ(Popular content)と参照元サイト(Referring sites)は毎日更新される。問題は更新頻度ではなく保存期間だ。これらの数値はすべて、正確に14日が経過するとUI上から、そして後述するAPIレスポンスからも消える。

1.2 APIで取得しても意味がない理由

REST APIを直接呼び出せばもっと長い期間を見られるのではと期待するかもしれないが、結論から言うとそれは違う。/repos/{owner}/{repo}/traffic/viewsと/repos/{owner}/{repo}/traffic/clonesエンドポイントは、per=dayでもper=weekでも返ってくる範囲は同じく直近14日に固定されている。per=weekを使ってもその14日を週単位の2つのまとまりに分けて表示するだけで、より古い過去を開示するオプションではない。さらにこのエンドポイントは認証なしではアクセスできず、リポジトリへの書き込み権限がなければ403 Forbiddenが返る。つまりAPIは「より広い窓」ではなく、UIと全く同じ窓をプログラム的に見る方法に過ぎない。結局、14日より長く残したいなら、データがまだ存在するうちに誰かが直接値を読み取り、どこかに保存しておく必要がある。

2. オープンソースメンテナーと製品チームが抱える不便

2.1 長期トレンドを再構成できない

最も直接的な損失はトレンド分析の断絶だ。過去6か月間で閲覧数が着実に伸びたのか、特定のリリース後にクローン数がどれだけ跳ね上がったのかを知りたくても、その期間中誰かが手動でスクリーンショットを撮り続けていない限り答えようがない。半期・年次でプロジェクトの成長を振り返る場面(カンファレンス発表、スポンサー向けレポート、採用募集での実績記載)で、まさにその根拠データが存在しないという状況が繰り返される。

2.2 原因と結果を結びつけられない

マーケティングやコミュニティ活動の効果を検証するには、イベント前後を比較する必要がある。ブログで紹介された日、カンファレンスで発表した日、メジャーバージョンをリリースした日のトラフィック反応を見たくても、14日が経過すれば比較の基準点そのものが消えてしまう。結果として、どの活動が実際に流入を生んだのかを事後的に検証しづらく、次の活動を計画する際も勘に頼ることになる。

2.3 ドキュメント・ページの優先順位をデータで決めにくい

Popular content(人気コンテンツ)指標は、どのドキュメントページやファイルが多く閲覧されたかを示し、ドキュメント整備の優先順位付けに役立つ。しかしこれも14日間のスナップショットに過ぎないため、季節変動や一時的な流入(例えば特定の記事が他所からリンクされた場合)を長期的なパターンと区別しにくい。結果として多くのメンテナーが勘でドキュメントを修正し、実際の読者行動とは無関係な部分に時間を費やすことになる。

3. Repo-rter - ローカル永続保存というアプローチ

3.1 何をするツールか

Repo-rterはこの問題に正面から取り組むために作られた無料オープンソースのデスクトップアプリだ(MITライセンス)。リポジトリ情報によれば、Tauri(Rust)バックエンドにNext.js・React・TailwindCSSのフロントエンドを組み合わせた構成で、macOS(Apple Silicon・Intel)・Windows・Linuxをすべてサポートするクロスプラットフォームアプリである。バックグラウンドでシステムトレイに常駐し、cronベースで定期的にGitHub APIを呼び出して閲覧数・クローン数・スターなどのデータをローカルに蓄積保存し、CSV・JSONでエクスポートできる。つまりGitHubが削除する前に、ユーザーに代わって定期的にスナップショットを取ってローカルDBに積み上げていく仕組みだ。

3.2 なぜあえてローカルデスクトップアプリなのか

同じ問題を解く方法は複数ある(4章・5章で比較する)。その中でローカルデスクトップアプリを選んだということは、いくつかの設計判断を含んでいる。サーバーやクラウドアカウントなしで動作するためインフラ運用負担がなく、収集したデータが第三者サーバーを経由せずユーザーの端末にのみ残る。逆に言えば、その端末の電源が切れていれば収集も止まるという制約、そして複数人が同じ履歴を見るにはファイルを共有しなければならないという協業上の限界とのトレードオフでもある。

4. ローカルデスクトップアプリ方式の長所と短所

4.1 APIトークンとプライバシー

Repo-rterを含め、トラフィック・クローンデータを収集するすべての方式は例外なく、対象リポジトリへの書き込み権限を持つGitHubトークンを要求する。これはRepo-rter特有のリスクではなく、GitHub Traffic API自体の権限モデルだ。ただし、そのトークンをどこにどう保管するかはツールごとに異なる。GitHub公式ガイドはOS資格情報マネージャーの活用を推奨し、平文ファイルでの保存を避けるよう勧めている。ローカルアプリを使うなら、トークンの保存方式と権限範囲(できればfine-grained PATで最小範囲に)を自分で確認する習慣が必要だ。その代わり、データ自体は外部SaaSサーバーを経由せず自分の端末にのみ蓄積されるという点は、プライバシー面で明確な利点である。

4.2 自動収集(バックグラウンド同期)の得失

システムトレイに常駐して定期的に同期する方式は、うっかり起動し忘れてその間データが空白になるという手動方式にありがちな失敗を減らしてくれる。一方で常時稼働するバックグラウンドプロセスはバッテリーやリソースを少しずつ消費し、ノートPCを数日間電源オフにすればその区間は依然として空白になるという根本的な限界は残る。サーバー上で動くcron(GitHub Actionsなど)とは異なり、自分のPCが起動している間しか収集されないという制約を理解した上で使うことが重要だ。

4.3 その他の限界

ローカル保存という特性上、端末を買い替えたりアプリを再インストールしたりすると履歴も一緒に移す必要があり、チーム単位で共有するにはエクスポートしたCSV・JSONを別途集約しなければならない。クラウドダッシュボードのようにどこからでもブラウザで即座に確認できる利便性とは異なるトレードオフだ。

5. 類似する代替策との比較

同じ問題 - GitHubが削除するデータをどう捕まえるか - を解く方法はローカルアプリ以外にも複数存在する。

5.1 GitHub Actions cron + リポジトリへのコミット

最も一般的なセルフホスト型の代替策は、リポジトリ内に毎日実行されるGitHub Actionsワークフローを置き、Traffic APIを呼び出した結果を同じリポジトリ(または別のデータ用リポジトリ)にコミットする方式だ。サーバーが不要でGitHubのインフラ内で完結し、履歴がgitのコミットログそのものに残るためチーム全体で共有しやすい。ただし、パブリックリポジトリであればコミットされたトラフィックデータもそのまま公開されるという点、そしてアクションが毎日正常に実行されたかを自分で確認する必要がある点は考慮すべきだ。

5.2 独自cron + DB(+ Grafana)

すでに社内モニタリング基盤(Prometheus・Grafanaなど)を運用している組織なら、GitHub APIを定期的に呼び出して自社のDBや時系列ストレージに蓄積し、既存のダッシュボードに載せる方式が自然だ。完全な制御とカスタマイズが可能だが、構築・運用の負担を組織がそのまま背負うことになり、個人メンテナーには重い。

5.3 star-history系 - スター専用ツール

star-history.comやdaily-stars-explorerのようなツールは、スター履歴だけを扱うという点でRepo-rterとは根本的に異なる。スターはGitHubがイベントログをAPIで公開しているため、過去の履歴を遡って再構成できる。一方、閲覧数・クローン数はそもそも集計済みの要約値としてのみ公開され、その集計結果自体が14日後に消去されるため遡ることができない。「スター専用ツールがあるならトラフィックも同様にできるはず」という期待は成り立たない。

5.4 OSSInsight系 - ホスト型の大規模分析

OSSInsightのようなプラットフォームは、GitHubの公開イベント(スター・PR・イシュー・コミット)を大規模に収集・分析するホスト型サービスだ。インストール不要ですぐ使え、エコシステム比較に強い。しかし、そもそも公開イベントベースであるため、リポジトリへの書き込み権限がなければ見られない閲覧数・クローン数のような非公開指標は扱わない。この点が、ローカル・セルフホスト型のアプローチとホスト型分析サービスを分ける根本的な境界線だ。

6. オープンソース成長指標を、なぜ・どう追跡するか

6.1 なぜ追跡するのか

メンテナーにとってトラフィック・クローン履歴は、スポンサー向け提案書、カンファレンス発表、採用募集で使う実績の根拠であると同時に、リリース・ドキュメント・マーケティング活動の効果を検証する実験データでもある。データがなければ「体感的に増えている気がする」という印象論にとどまるが、履歴が蓄積されれば具体的な数字で語れるようになる。

6.2 何を見るべきか - スターよりクローン

スターは参入障壁が最も低い関心表明(お気に入り登録に近い行為)であるため、実際の利用状況との相関が弱いという指摘がコミュニティで根強く出ている。一方、ユニーククローン数は実際にコードをダウンロードして使う人数により近い信号だ。両方の指標を見つつも、意思決定にはクローン・閲覧数のような行動指標により重きを置くのが合理的だ。さらにpopular/referrers(流入経路)も重ねて見れば、どこで人々がこのプロジェクトを知ったのかまで追跡できる。

6.3 実務ワークフローの提案

規模に関係なく適用できる最小限のワークフローは次の通りだ。第一に、14日が経過する前に必ずどこかへデータを移す(ローカルアプリでもActionsでも構わない、方式よりも「途切れず継続的に収集されているか」が重要だ)。第二に、リリース・発表・ブログ掲載といったイベントの日付を別途記録しておき、後でトラフィックグラフと並べて因果関係を推測できるようにする。第三に、月1回程度の周期で履歴を見返す習慣をつけ、異常な兆候(急激な流入・離脱)を見逃さないようにする。

結論 - データ所有権という小さな問い

GitHub Insightsの14日制限は些細に見えるが、掘り下げると「自分のプロジェクトに関するデータを、誰が、どこに、どれだけ長く持っているのか」というより大きな問いにつながる。Repo-rterはその答えをローカル・無期限・オープンソースという三語で示した事例だ。正解は一つではない。個人で小規模なリポジトリを運営しているなら、インストール一つで完結するローカルアプリが最も負担が少なく、チーム・組織であればすでにあるCI・モニタリング基盤に載せる方が持続可能だ。どの方式を選ぶにせよ、核心は同じである。14日が経過する前に、今すぐデータを移しておくこと - その些細な習慣一つが、後にプロジェクトの成長物語を語る唯一の根拠になる。(2026年7月時点)
