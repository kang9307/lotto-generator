禁止执行位几乎总是在攻防的语境里被介绍。把机器码塞进缓冲区也不会在那里跑起来，数据区与代码区之间划着一条线。这些说法本身并没有错。只是这个比特在页表里真正规定的范围要比那个故事更宽，而这份额外的宽度，恰恰在一个攻击者都不出现的场合里显露得最清楚。

缘起 - 修好开不了机的监控程序的是一个安全比特

引发这篇文章的原文，是一位署名 Sonya 的作者发在 purplesyringa 博客上的客座文章。对象是给 postmarketOS 用的 ARM64 裸机虚拟机监控程序。症状一句话就能说清：一旦打开对某个系统寄存器读取的拦截，手机就会卡住并重启；同一份代码在 QEMU 上跑得好好的。

文章有一半篇幅是假设一个接一个倒下的声音。异常处理程序把寄存器弄坏了这个假设，在 QEMU 的单步跟踪下站不住。这是指令缓存与数据缓存一致性问题这个假设，靠把排序工作挪到构建期得到了处理。硬件跑出了规范之外这个假设，让作者又加装了几个异常处理程序，结果什么也没抓到。

突破口来自二进制比对。能跑的那一版和会死的那一版，差别是在语义上完全等价的两种写法。目的地被编进指令本身的静态直接分支活了下来，从寄存器里读目的地的间接分支死掉了。这个对比指向的只有一件事：分支预测。

预测器把目的地误判到了地址 0。而在这个监控程序的一对一映射下，那个位置放着被锁住的 bootrom。作者选择的解法是给那块区域打上禁止执行，就在那一刻手机第一次启动成功。文章最后一句话概括了整件事的性质：反正都得把映射成不可执行这条路打通，那就把除载荷之外的一切都映射成不可执行，于是这个监控程序终于也有了一点纵深防御。安全不是目的，而是副产品。

执行权限是什么 - 挂在一个页上的比特

权限是按页挂上去的

在虚拟内存里，地址转换的最小单位是页。转换表的每个条目里写的不只是这个页对应到哪个物理帧，还一并写着这个页可以被怎样对待：可不可以读，可不可以写，以及里面装着的字节可不可以被当作指令取出来。

应用程序一侧碰这三件事的窗口，是 mmap 与 mprotect 的 prot 参数。man page 用一句话定义了每个取值。PROT_READ 是这块内存可以被读，PROT_WRITE 是可以被修改，PROT_EXEC 是可以被执行，PROT_NONE 则是根本无法访问。mprotect 的原型是 int mprotect(void *addr, size_t size, int prot);，起始地址必须对齐到页边界。

标志man page 里的定义实务上意味着什么
PROT_READ这块内存可以被读可以作为数据访问，加载指令能通过
PROT_WRITE这块内存可以被修改存储指令能通过。在 i386 上它蕴含读权限
PROT_EXEC这块内存可以被执行允许取指。只有在硬件把这条轴分开时才有意义
PROT_NONE这块内存根本无法访问任何访问都会产生异常，用来做守卫页

在没有执行轴的硬件上会发生什么

这里 man page 谨慎加上的那句限定很关键。PROT_EXEC 是否会产生与 PROT_READ 不同的效果，取决于处理器架构、内核版本和进程状态。同一份文档还写道，当进程带上 READ_IMPLIES_EXEC 这个人格标志时，只指定 PROT_READ 也会被隐式地加上 PROT_EXEC。

也就是说，API 里有三个标志，并不代表硬件上也有三条轴。API 一直接受三个，但其中执行这条轴，是在硬件获得了单独记录它的位置之后才真正带上意义的。在那之前，执行这条轴一直搭在读这条轴上。

在那之前 - 可读就意味着可执行

为什么会这样，可以用位置不够来解释。32 位 x86 传统的页表条目宽 32 位，地址位和各种状态位已把宽度填满，没有可为执行权限新划的位置。禁止执行位进入页表是在条目变宽之后。

这段来历原封不动地留在 Linux 内核源码里。x86 一侧的页类型头文件把禁止执行位定在第 63 位，旁边还加了一句注释说它要通过 cpuid 检查之后才有效。而真正的掩码只在 64 位或启用 PAE 时才使用那个比特值，在其余配置下被定义为零。

所以禁止执行位的引入，与其说是多了一项保护功能，不如说是转换表能够表达的状态多了一种。在那之前，根本没有办法把可读的页与可执行的页区分着写下来。数据与代码的分界是程序之间的约定，而不是硬件强制的性质。

这个差别是后面所有内容的根。一旦某种状态变得可以表达，这种表达就不会只停在最初设想的那一个用途上。禁止执行是为了防御而引入的，但它一在转换表里占住位置，就开始被当作关于处理器可以怎样对待这个页的一般性规定来使用。

W^X - 不在同一瞬间给出两种权限

执行这条轴一出现，紧跟着来的原则就是 W^X：任何页都不同时持有可写与可执行。禁止执行位本身并不强制这条原则，它只是让状态可以被写下来，禁止某种组合的是叠在它上面的策略。

施加得最重的是 OpenBSD。它的 man page 明说同时要求写与执行的映射不被允许，并把例外通道收窄成必须同时成立的两个条件：文件系统以 wxallowed 挂载，并且进程在链接期被打上 wxneeded 标记。违规会以 ENOTSUP 返回，文档里甚至写明了 kern.wxabort 这个用来定位失败点的开关。

Apple 芯片也在偏严的一侧。Apple 的开发者文档写道，内存保护对所有应用都生效，与它是否采用 Hardened Runtime 无关，这与 Intel 平台的 Mac 上只对采用了该能力的应用生效形成对照。保护开启时的规则同样只有一句：一个线程不能在向某块区域写入的同时执行那块区域里的指令。

Linux 打的是另一个位置。mmap 与 mprotect 的文档里，并没有拒绝写加执行这一组合的表述。开关被放在了别的层。把文件系统以 no-exec 挂载之后，试图用 PROT_EXEC 映射其上文件的请求本身就会被 EPERM 拒绝，这一点写在 mmap 的 man page 里。后面会看到的内存文件禁止执行封印，属于同一支。

原文真正主张的东西 - 投机性取指

意思一样，却只死了一个

把那个成为调试转折点的对比落到形式上，就是下面这样。

    bl   get_ctr_el0     // 静态直接分支 —— 目的地被编进了指令本身
    blr  x1              // 间接分支 —— 目的地在运行时从寄存器里读出来

这两行调用的是同一个函数。差别只在目的地是什么时候确定的。直接分支在取指的那一刻目的地就已经定了。间接分支则会让处理器在寄存器的值备好之前先预测一个目的地。预测落空时结果会在稍后被丢弃，但那条路径上的指令早已被取了进来。

标成 Device 也堵不住的东西

在 ARM 上，内存映射输入输出的区域会被标成 Device 内存而不是 Normal 内存。常见的误解就从这里长出来：标成 Device，处理器就不会随便去碰那块区域。原文引用的那句 ARM 文档，把这个理解恰好收窄了一格。其中有一个很容易被漏掉的微妙区别：把一个区域标记为 Device，只能阻止投机性的数据访问；要阻止投机性的指令访问，就必须把该区域标记为不可执行。

原文里的局面正好掉进了那道缝里。因为是一对一映射，地址 0 就是被锁住的 bootrom，而一次误预测的间接分支想从那里取指。数据那条轴已经被 Device 标记关上了，指令那条轴却还开着。所以解法才是禁止执行。被缩小的不是攻击面，而是处理器仅凭预测就能触及的范围。

这里正是原文标题所指的地方。禁止执行位在成为防御装置之前，先作为规定投机行为的架构属性在工作。若只把数据执行防护读成针对栈溢出的对策，就会把同一个比特替你接住的硬件层面故障整个漏掉。

内核源码里早已写死的东西 - 设备映射的禁止执行

通用操作系统早就把那个结论铺成了默认值。看一眼 Linux 的 arm64 页保护头文件，答案一目了然。

#define PROT_DEFAULT		(PTE_TYPE_PAGE | PTE_MAYBE_NG | PTE_MAYBE_SHARED | PTE_AF)

#define PROT_DEVICE_nGnRnE	(PROT_DEFAULT | PTE_PXN | PTE_UXN | PTE_WRITE | PTE_ATTRINDX(MT_DEVICE_nGnRnE))
#define PROT_DEVICE_nGnRE	(PROT_DEFAULT | PTE_PXN | PTE_UXN | PTE_WRITE | PTE_ATTRINDX(MT_DEVICE_nGnRE))
#define PROT_NORMAL		(PROT_DEFAULT | PTE_PXN | PTE_UXN | PTE_WRITE | PTE_ATTRINDX(MT_NORMAL))

作为基础属性的 PROT_DEFAULT 里并没有禁止执行位。在它之上把 PTE_PXN 与 PTE_UXN 两个都加上去的，才是设备映射，内核使用的普通内存映射也一样。而每个宏的末尾还另外挂着一个指定内存类型的项。执行这条轴与内存类型那条轴是分别填进去的，这个事实就明明白白摆在一行代码里。

从这里能看出两件事。第一，arm64 的禁止执行位不是一个而是两个，按特权级别分开，因此可以表达出内核不能执行而用户空间可以执行这样的状态。第二，可执行的内核代码区是靠去掉这些比特做出来的：默认是禁止，允许才是例外。

换句话说，原文那位开发者必须亲手实现的性质，通用内核早就当成默认值铺好了。在裸机上直接写页表的一方并不会继承那份默认值。在操作系统原本替你守着的惯例消失的地方，架构文档里那个微妙的区别立刻以启动失败的形式现了身。

把异常当信号用的技法 - 同一套机器，不同的比特

违反页权限就会产生异常，异常会进内核。可是另有一支技法，把这个异常当成的不是错误而是通知，等于把保护装置改用作观测装置。在 Linux 上，这一支的代表是 userfaultfd。

man page 把它定义为把缺页异常的处理委托给用户空间应用程序的机制。文档列出的用途是检查点与恢复机制中的延迟恢复，以及在主机之间搬运虚拟机和容器时让执行几乎不中断的后拷贝迁移。运作方式也写得很明确：注册过的区域一旦发生异常，触发异常的线程会被挂起睡眠，一个事件会经由文件描述符送上来，由用户空间读取并处理。

注册模式有三种：访问了缺失的页时、向写保护的页写入时，以及页存在但页表条目不存在时。文档写明，这个机制是过去依赖 SIGSEGV 信号的用户空间分页技法的替代方案。

而这里出现了一个与本文主轴直接相关的事实：那份清单里没有执行这条轴。把异常当信号用的这一支，跑在读与写的轴上。执行权限被用在从一开始就不让那次访问发生的一侧，多过被用来制造通知。原文的案例走的正是这个方向：它不是接住异常再处理，而是把会产生异常的局面本身消掉了。

于是，安全功能被挪去做别的事这件事的结构，就分成了两支。一支借的是异常这个事件，另一支借的是权限比特所规定的硬件行为范围。禁止执行位属于后者。

JIT 是怎么守住 W^X 的

在运行过程中生产可执行代码的程序，会与 W^X 正面相撞。机器码必须先写完再执行，而这条原则禁止在同一瞬间持有这两种权限。即时编译这种方式本身在图什么，已经整理在 介绍把 TypeScript 直接编译成 LLVM 机器码的 Perry 的那篇文章里，这里只看权限是怎么处理的。

翻转权限的做法

/* 打开写入窗口，填入机器码，再改成可执行 */
void *p = mmap(NULL, len, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
if (p == MAP_FAILED) return -1;

emit_code(p, len);                       /* 到这里为止这个页还不可执行 */

if (mprotect(p, len, PROT_READ | PROT_EXEC) != 0) return -1;
/* 从这一刻起同一个页不可写但可执行 */

这是最简单的形态。以读加写打开一份匿名映射，填入机器码，再用 mprotect 翻成读加执行。翻之前执行不了，翻之后写不了，所以在任何一个瞬间，写与执行都不会同时站在同一个页上。

把映射拆成两份的做法

/* 给同一批物理页挂上两个权限不同的虚拟地址 */
int fd = memfd_create("jit", MFD_CLOEXEC);
if (fd == -1) return -1;
ftruncate(fd, len);

void *rw = mmap(NULL, len, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
void *rx = mmap(NULL, len, PROT_READ | PROT_EXEC,  MAP_SHARED, fd, 0);

emit_code(rw, len);   /* 只经 rw 写入，只经 rx 执行 */

把同一个文件描述符以共享映射的方式挂两次。mmap 的 man page 写道，对共享映射的更新对映射同一区域的其他一方也是可见的。所以经 rw 写下的字节，会经 rx 被当作指令读出来。物理页仍旧只有一份，只有虚拟地址变成两个，权限互不相同。

省下了翻转的系统调用，换来的是别的负担。要随身带着两组地址，而以相对地址算出来的分支目的地究竟以哪个窗口为基准这个问题会反复回来。而且，只要后面要讲的禁止执行封印生效，这条路本身就不成立。

Apple 芯片 - 以线程为单位翻转

Apple 造了第三条路。JIT 用的区域是给 mmap 传 MAP_JIT 标志创建的。采用了 Hardened Runtime 的应用，需要有 com.apple.security.cs.allow-jit 授权，系统才允许它带着这个标志调用 mmap；没有采用这项能力的应用，则不需要授权也能用这个标志，文档是这么写的。不过在 Hardened Runtime 与该授权并用的组合下，应用只能创建唯一一个带 MAP_JIT 的内存区域。

翻转是用 pthread_jit_write_protect_np 做的。除此之外文档还指出了一条新路径：加上 com.apple.security.cs.jit-write-allowlist 授权之后，应用要通过 pthread_jit_write_with_callback_np 往自己的 JIT 区域里写，而带着这项授权的应用就再也不能调用 pthread_jit_write_protect_np。为了动态加载的库，还有一项在运行期更新名单的单独授权。

在结构上最耐人寻味的是翻转的作用范围。文档写道，回调方式会把那块区域变成可写且不可执行，但只针对当前线程；换回去的时候，也是针对当前线程把它变成可执行且不可写。上一节的 mprotect 并非如此，它改的是地址空间里的映射，所以只要翻转的窗口开着，同一进程里的所有线程都会把那个页看成可写状态。线程级的翻转把那扇窗收窄到了一个线程。

而且光处理权限还不算完。Apple 的文档特意叮嘱，在执行一个刚刚更新过的内存页上的机器指令之前，必须先调用 sys_icache_invalidate。因为在 Apple 芯片上指令缓存与数据缓存并不一致，不做失效处理就执行可能会得到意料之外的结果。文档还补充说，在 Intel 平台的 Mac 上调用同一个函数也是安全的，只是它在那边什么都不做。

这一段与原文重叠。那篇文章里倒下的假设之一，同样是指令缓存与数据缓存的一致性。自己生产机器码的一方，必须把权限和缓存一起处理。两者只对上一个，症状在两种情况下都表现为无法复现的停顿。

代价的真面目 - 系统调用、页粒度、缓存

守住 W^X 的价钱分成好几笔。无论选哪种做法，其中几笔都是必付的。

  • 系统调用 —— 翻转做法每生产一批机器码就要进一次内核再出来。代码生成的单位切得越碎，这笔开销就落得越频繁。
  • 页粒度 —— 权限不是按字节而是按整页改变的。把好几段小代码塞进同一个页里，为了改其中一段而打开的那一刻，其余全部也跟着变成可写。
  • 整个地址空间 —— mprotect 改的是进程的映射。在多线程程序里，翻转开着的那段区间，就是对所有线程都开着的区间。
  • 虚拟地址的双份化 —— 双重映射用两个地址换掉了系统调用。代码里的地址运算以哪一边为基准，必须一致地管起来。
  • 指令缓存 —— 在把刚写下的字节当指令执行之前，清理缓存这一步在某些平台上是必需的。
  • 策略冲突 —— 加固开关一旦打开，上面几种做法里的一部分就根本不成立。下一节的禁止执行封印就是例子。

这里有一处直觉常常出错：把禁止执行位本身立起来或放下去，几乎不花什么代价。花代价的是改变那个状态这件事，而要改的理由是程序在运行中生产代码。在只跑静态编译代码的进程里，这笔开销实际上是零。

各架构之间的差别

x86 一侧的定义就是前面提到的样子。看形式就能看清条件卡在哪里。

#define _PAGE_BIT_NX		63	/* No execute: only valid after cpuid check */

#if defined(CONFIG_X86_64) || defined(CONFIG_X86_PAE)
#define _PAGE_NX	(_AT(pteval_t, 1) << _PAGE_BIT_NX)
#else
#define _PAGE_NX	(_AT(pteval_t, 0))
#endif

比特编号固定在一个数上，但那个比特是否真的存在，取决于配置。只有 64 位或启用 PAE 时掩码才立得起来，其余情况下是零。注释里的限定说的是同一件事：要通过 cpuid 询问之后才有效，意味着这项能力不是一开始就有的，而是后来才追加的选项。

arm64 的结构不一样。禁止执行按特权级别分成两个，旁边还并排挂着内存类型这条独立的轴。

架构禁止执行的表达方式Linux 源码里的名字必须一起看的轴
x86-64 与 PAE页表条目里第 63 位这一个比特_PAGE_BIT_NX 与 _PAGE_NX没有，执行轴是单一的
32 位 x86 非 PAE相应的比特并不存在_PAGE_NX 被定义为零读这条轴兼作执行轴
arm64 特权级别禁止在特权级别执行的比特PTE_PXN另有一条内存类型轴
arm64 非特权级别禁止在非特权级别执行的比特PTE_UXN另有一条内存类型轴
arm64 设备区域设备映射默认带上这两个比特PROT_DEVICE_nGnRnE 与 PROT_DEVICE_nGnREDevice 标记只关上数据那条轴

表的最后一行，就是原文撞上的那堵墙。写了 Device，并不等于执行那条轴会自动关上。这两条轴规定的是不同的东西。

各操作系统之间的差别

面对同一个硬件比特，各操作系统叠上去的策略并不相同。只按文档写明的内容整理，大致如下。

系统同时要求写与执行的映射例外通道配套机制
OpenBSD不被允许，以 ENOTSUP 拒绝文件系统以 wxallowed 挂载且进程在链接期带上 wxneeded 标记用 kern.wxabort 定位失败点
Apple 芯片上的 macOS一个线程不能在同一瞬间边写边执行MAP_JIT 区域与专用授权翻转按线程生效，指令缓存失效是必需的
Intel 平台的 macOS只有采用 Hardened Runtime 的应用才受保护同一套授权体系缓存失效的调用在那边什么也不做
Linuxmmap 与 mprotect 文档里没有禁止该组合的表述策略放在别的层去施加no-exec 挂载与内存文件的禁止执行封印

Linux 那一行不能读错。文档里没有禁止组合的表述，意思是基础的系统调用层不拒绝这个组合，而不是说在 Linux 上没法施加 W^X。Linux 把这个决定挪到了挂载选项、按对象施加的封印，以及单独的安全模块那一侧。信任边界该画在哪里这同一个问题在 Web 一侧是怎么显现的，另有 讲为什么不能信任客户端的那篇文章做了整理。

把执行权限当作策略来处理 - 禁止执行封印

执行权限越过页比特、变成对象自身的性质的例子，就在 Linux 的内存文件上。内核文档定义了三个开关。

  • 禁止执行封印标志 —— 立起这个比特，内存文件就以禁止执行的状态创建，并同时打上执行封印，此后无法再被改成带有执行权限。
  • 允许执行标志 —— 立起这个比特，则以带着执行权限的状态创建。
  • 系统全局设置 —— 取值为零时，两者都不指定的调用会按允许执行的一侧行事；取 1 则按禁止执行封印的一侧行事；取 2 时，没有指定封印的调用本身会被拒绝。

内核文档交代的背景也很清楚：可执行的内存文件会成为混淆代理人式滥用和绕过禁止执行策略的通道，但像容器运行时执行二进制这样的正当用途确实存在，所以需要一种把两者区分开来的办法。

这套设计所展示的东西，正好落在本文的主轴上。执行权限变成了一旦决定就无法撤回的状态。原本只是页表里的一个比特，如今挂在文件描述符这个对象上，规定着这个对象余生的性质。以保护装置身份进来的比特，被提拔进了资源管理的词汇表。

而它与上一节的双重映射式 JIT 正面冲突。系统全局设置一旦取到最严格的值，给 JIT 用的内存文件根本就建不出来。一个加固开关关掉了一项正常功能。哪一边对，取决于那个系统在跑什么，而没有任何默认值能替人做这个判断。

原文与本文分道扬镳的地方

原文主张的范围既窄又清楚。它是一台 ARM64 裸机虚拟机监控程序的调试记录，结论是 Device 标记与禁止执行标记挡住的是不同的东西。

那篇文章里没有的东西也需要说清楚。禁止执行位的引入经过、W^X 策略在各系统间的差异、JIT 的实现方式、x86 一侧的情形，都不是它的主题。上面各节里填补这些内容所依据的，全部是各份文档与源码的原文，并没有把原文的主张往外拉扯。

还值得划一条不该过度推广的线。原文的结论是不能因为标了 Device 就认为指令那条轴也关上了，而不是说打开禁止执行就能普遍解决与投机执行相关的问题。后者是完全不同的主张，原文并没有这么说。

留下的只有一句话。以安全功能身份进来的机制，其实一直在替架构表达另一条规定；而对需要那条规定的开发者来说，安全是作为副产品到来的。引入的目的与实际的用法之间出现错位并不是失败。只要能被表达的状态多出一种，这种表达就总会走得比它最初的位置更远。

未能确认的部分

  • ARM 开发者网站上的架构文档页面是靠脚本渲染的结构，正文没能打开。原文引用的那句 ARM 文档只通过那篇文章核对过，手册的章节号与版本号未能确定。
  • Intel 与 AMD 的架构手册 PDF 原本没能打开。x86 的第 63 位及其条件式定义，只与 Linux 内核头文件里的定义和注释核对过。厂商使用的名称写法并不在那份头文件里，因此正文中没有使用厂商名称。
  • PXN 与 UXN 这两个名字的展开读法是从宏名里读出来的，未能与 ARM 手册原文核对确定。正文里只写了按特权级别禁止执行这一功能层面的说明。
  • 原文的反汇编里，间接分支所用的寄存器编号在不同引用版本中看起来并不一致。论点在于静态分支与间接分支的对比，因此正文叙述中去掉了编号，只保留形态。
  • 表示权限翻转与双重映射实际开销的数值，在一手资料里没有找到。文中只写了代价的种类，没有写它的大小。
  • Apple 那套回调式写入 API 是在哪个 macOS 版本引入的，未能查实。文档里只写了授权与行为，没有找到版本标注。
  • 关于内存文件执行封印的表述，在 man page 一侧没有找到，改从内核文档一侧核对。看起来是两份文档修订时点的差异。
  • Linux 内核源码的引用以主开发分支的时点为准，并未固定到某个发布标签。宏的构成可能随版本而变。
