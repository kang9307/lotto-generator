When an Agent Picks a Vendor, Which Agent Was It - Measuring Third-Party Choices Across 16,893 Coding Agent Runs

Agreement in 42 percent of cells, a name raised 139 times and never picked, and the way language rewrites the winner

2026-09-06 Dev & Infra

Ask for payments and code comes back. Inside that code a particular company's SDK is already wired in, the environment variable names are already decided, and a pricing tier is already assumed. The request was a single word, payments, and yet the result arrives with a vendor baked into it. What happened in between is something almost nobody looks at.

A study published in early September 2026 looked at exactly that gap, at scale. It put three coding agents in front of the same kinds of requests, repeated those requests thousands of times, and then counted, for every session, which names were raised as candidates and which one actually ended up in the code. The number of executions was 16,893. The 17k that headlines tend to use is that figure rounded off.

What follows is not an argument that one tool is better than another. The subject is what determines an agent's choice, and what happens to a market when that choice is repeated tens of thousands of times. The separate question of where selection accuracy breaks down as the number of available tools grows was already covered in How Many Tools Can an Agent Handle, so this piece stays on the distribution of what was actually chosen.

Every figure below appears in the original write-up. What differs from figure to figure is the denominator. 16,893 counts executions, 5,292 counts sessions that passed a validity filter, and 42 percent counts cells in an aggregation grid rather than sessions. Mixing those denominators turns the same number into an entirely different claim, so each section states which one applies.

The starting point - the empty subject in the agent picked it

A sentence that shows up regularly in team channels goes like this: the agent picked this one. It sounds like an explanation, but the subject is actually missing. Which agent, running on top of which repository, reasoning from what evidence, none of that is in the sentence. If all three agents converge on the same answer, the subject does not matter. If they do not, the subject is the answer.

This study is an attempt to fill that subject in. The same class of request went to three tools over and over, and the conversation logs were read alongside the actual code diffs so that candidates raised and final winners could be separated and counted independently. The output is therefore not a ranking of products. It is a distribution of choices.

Once a distribution exists, the useful question changes shape. It stops being which service should we use and becomes: given that our organization already has an answer, what is the probability that the agent produces that answer. If the probability is low, the fix belongs in the repository rather than in the prompt.

What was measured and how - denominators before numbers

The design is straightforward. Build 75 repositories across 10 programming languages, prepare 1,163 prompt variations, and run them against three coding agents. Each execution takes place in an isolated sandbox, and the sandbox provider was rotated across three vendors. The write-up notes that the choice of sandbox was separately verified as having no bearing on the conclusions, which is the kind of control that is easy to skip and easy to be criticized for skipping.

The user side of the conversation is not a person but an orchestrator. In the original phrasing that role is played by Gemini 3.7 Flash, and rather than issuing a single instruction it carries a multi-turn exchange forward the way a real request tends to unfold. Judging is automated as well. The conversation log and the actual code diff are read together to extract the candidates that were mentioned and then to name the final winner.

What makes a session valid

A validity check sits inside the judging step. The two criteria given as examples are these: the choice must not have been biased by a repository that had already pre-chosen the provider, and a solution must actually have been chosen. A session that listed candidates and stopped there has no winner, so it does not enter the tally.

What survived that filter is 5,292 sessions, roughly 31 percent of the 16,893 executions. The remaining 11,601 dropped out of the first published analysis, and the breakdown of which reason accounted for how many is not in the published text. This number matters because it is where the denominator of everything that follows is set. Web search rates, in-house build rates, and mention counts all sit on the filtered side of that line rather than on the full 16,893.

42 percent - the share of cells where all three agreed

This is the first number worth sitting with. All three agents picked the same tool in 42 percent of the cells. That is less than half.

The word to carry over precisely is cells. It is not a session-level agreement rate but a count over an aggregation grid, and the article never defines what the rows and columns of that grid are. The example attached immediately afterward is at the level of a category. In the voice agents category, one tool chose Twilio, another chose the OpenAI Realtime API, and the third chose Vapi. One request, three answers.

The practical consequence is blunt. The agent picked it carries less than half the information it appears to carry. Unless the sentence also says which agent, the choice is not reproducible, and a decision that cannot be reproduced cannot really be reviewed either.

  • What 42 percent does say — in more than half of the categories, changing the tool changes the outcome. Standardizing on one agent across a company therefore amounts to standardizing on roughly half the vendor list as a side effect
  • What 42 percent does not say — nothing in the figure indicates which agent made the better choice. Agreement is a dispersion measure, not a quality measure, and treating it as quality is the most common misreading of numbers like this
  • What remains open — with no definition of a cell, restating the figure as a session-level agreement rate overstates it. The fewer categories a grid contains, the more a cell-based percentage moves on small changes

Where the evidence comes from - web search versus priors

One reason the three tools land on different answers is where each of them sources its evidence. The study tallied, per tool, the share of sessions in which a web search occurred, and the spread across the three is wide enough to be structural rather than incidental.

Codex used web search in 94 percent of sessions. The original phrasing is that it almost always goes to the web. Cursor based its decision on the web in about two thirds of sessions. Claude Code leaned mainly on its priors and searched in only about 30 percent of cases, but when it did search it browsed three times as many pages as Codex.

These are not three grades on one scale. They are three designs with different failure modes. Heavy web reliance makes an agent sensitive to whatever the current documentation says and to how that page happens to be worded. Light reliance leaves the distribution of the training snapshot showing through in the result. The study does not rule on which produced better choices, and nothing in the numbers supports such a ruling.

Behavior shifts when the category is new

These are not fixed traits either. The write-up notes that in more recent sectors such as sandboxes, where priors are weaker, Claude Code's web search rate rose to around 80 percent. The 30 percent figure is an overall average, and it moves substantially with how mature the category is.

Put together, the web search rate is set half by the tool and half by the age of the category. In long-established areas the three tools converge toward whatever their priors encode, and in newer ones the search results of that particular day compose the answer. The newer the category, the more room there is for the same prompt to return something different on a second run, which is exactly the situation where reproducibility matters most.

The fourth option - pick nothing and build it yourself

There were never three options, only four. Instead of selecting among candidates, an agent can implement the thing directly and add no dependency at all. The study counted that path too.

Claude Code built in-house in 19 percent of sessions. Codex and Cursor each sat at around 10 percent. The original describes this as almost twice as often.

This metric has no built-in direction. Not growing the dependency list is a benefit, and leaving hand-written code where a proven service would have gone is a liability. In places where regulation and security apply, such as payments or authentication, the liability side weighs far more. The study did not measure the quality of the code that got written in those sessions. The 19 percent is therefore a record of behavior, not an evaluation of it.

Mentions versus adoption - raised 139 times, chosen zero times

The most striking part of this study is neither the agreement rate nor the search rates. It is that being named as a candidate and ending up in the code turn out to be separate events, and that the separation is now visible as counts.

PayPal was mentioned 139 times and adopted zero times. The article adds that Stripe took 124 of those same 139 sessions, which tells you the mentions were clustered in the payments category and that the category had a near-settled winner. LangChain was adopted 4 times out of 194 mentions, Netlify 6 out of 152, and Adyen 3 out of 175. Supabase drew 242 mentions, more than any of them, while the database category tilted toward Neon.

This is the point at which interpretation should slow down. The study does not establish why the gap exists. What was observed is a difference in frequencies, and the mechanism behind that difference sits outside what was measured. Several explanations are plausible, and none of them was tested here.

  • Integration effort — the number of steps between the documentation landing page and a working minimal example varies a great deal. An agent has to produce running code inside one session, which favors whichever path is shorter
  • Volume and vintage of training data — a name with many worked examples in public repositories is more likely to be carried all the way to completion on priors alone. This axis reinforces itself over time, because the code produced today becomes the corpus of tomorrow
  • Constraints written into the documentation — limits and retention windows spelled out on a pricing page become comparison criteria. The next section is a concrete instance of exactly this
  • Different bars for listing and for building — enumerating alternatives resembles reciting known names, while implementing narrows on something else entirely. If mention counts track name recognition and adoption counts track execution conditions, the two diverging is unsurprising rather than mysterious

Language rewrites the winner - same request, different conclusion

Send the same request into repositories written in different languages and a different name comes back. The email sending task shows that separation about as cleanly as it can be shown.

The first thing to notice in that table is that the denominators are not the same. TypeScript has 89 runs while the other three have 23 or 24 each. With a nearly fourfold difference in sample size, the values are not equally stable. And the strength of dominance varies. The 62 percent in TypeScript describes a category where competition is still live, while the 96 percent in Java describes a question that is effectively closed. Language changes the winner, but how forcefully it does so is itself language-dependent.

Structurally, the mechanism is easy to state. An agent reads the repository before it produces an answer. The repository carries a language, a framework, libraries that are already present, and conventions embedded in configuration files. That context narrows the candidate set before any comparison begins. The overwhelming showing for the Azure-aligned option in Java repositories is hard to separate from the distribution of documentation and examples in the enterprise Java ecosystem. That causal step, though, is inferred from the shape of the table rather than demonstrated by the study.

The practical consequence appears at the level of an organization rather than a file. If the front end is TypeScript, the batch jobs are Python, and the gateway is Go, then handing the same requirement to an agent in each repository can bring in three different vendors. Three contracts, three sets of keys to rotate, three support channels during an incident. None of that is the agent behaving incorrectly. Each choice is faithful to its context, which is precisely why the drift happens quietly and shows up months later during a security review.

Concentration differs by category

Not every category splits the same way. Some have effectively settled on a single answer, and others scatter across three.

There is one operational rule embedded in that table. Highly concentrated categories do not need to be specified, and fragmented ones must be. In a category like payments, where nine runs out of ten converge, writing the vendor into the prompt buys almost nothing. In voice or email, where the answer splits three ways, anything left unspecified will differ from run to run, and the differences accumulate across a codebase without anyone deciding they should.

One caveat belongs with these numbers. Whether Stripe's nine out of ten, Neon's 66 percent and S3's 45 percent are shares within their category or shares of all sessions is not stated. Reading them as within-category is the natural reading given the surrounding text, but the assumption is worth carrying along whenever the figures are quoted.

Where a single line of documentation changed the outcome

The most concrete fragment of causation in the whole study sits here. Explaining why Mailgun repeatedly lost to Postmark, the article points to agents reading the phrase 1-day retention on the free plan.

What that observation says is unambiguous. An agent does not try a product. It reads one. It is not running benchmarks or pulling up incident history; it is comparing sentences that happen to be on a page at that moment. Under those conditions, how a claim is worded and where it sits can weigh more heavily on the verdict than the underlying behavior of the service.

How a vendor might act on that finding is not the concern here. For the side adopting the tool, two consequences follow. First, the sentence the agent reasoned from may not describe the terms you are actually on. A retention window on a free tier is frequently a different number under a paid contract, and an agent comparing free tiers will happily discard an option your company already pays for. Second, if the evidence is a sentence, then requiring the evidence to be recorded is enough to make the decision auditable. One line explaining the choice is all it takes for a human to notice that the premise was wrong.

Where this study stands - who measured, and who played the user

Separately from the size of the numbers, this is not a neutral observation, and that fact is stated inside the article itself.

The authors sell growth services to developer tool companies. They also write that the research is part of a broader effort to influence what coding agents choose and to get products picked. The interest is disclosed in the body rather than hidden, which is the version of a conflict that is easiest to work with. Being vendor-produced is not on its own a reason to discard data. The general procedure for weighing a study's sponsorship is laid out in How to Read AI Usage Pattern Reports About Software Teams, so what remains here are the design questions specific to this study.

The simulated user is another LLM

The largest variable is the user role. The counterpart in every conversation is not a person but an orchestrator running on Gemini 3.7 Flash. Real developers mention budgets, cite an internal standard, insist on a vendor that is already under contract, and push back when they dislike an answer. How much of that pressure the simulated user was built to apply can move the entire winner distribution, and there is no way to bound that effect from the outside.

There is also the matter of the user role and the judging role being models of the same family. If the side generating the conversations and the side naming the winners share tendencies, then whatever direction that shared tendency pushed the results is difficult to isolate from within this design.

  • The composition of the four personas — a spectrum running from vibe coder to enterprise engineer is something the designers chose. There is no guarantee it matches the real mix of users, and no per-persona breakdown has been released to check against
  • What the 1,163 prompt variations cover — how a requirement is phrased changes the candidate set that gets considered at all. How closely those variations resemble the distribution of real requests is not something the article establishes
  • The 31 percent the validity filter kept — the criteria are reasonable on their face, but if a particular pattern concentrated among the excluded runs the result is selection bias. Without a breakdown by exclusion reason there is no way to test that
  • The undefined cell — because the grid behind the 42 percent is never described, the same underlying data aggregated on a different unit could yield a different headline figure
  • Missing versions and dates — the model and CLI versions of the three agents, and the window during which the runs happened, are absent. Agents change on a scale of weeks, so this is best treated as a snapshot of one moment rather than a standing ranking

What the study did well is equally clear. It disclosed its interest in the body, it rotated sandbox providers and separately checked that the execution environment was not producing the result, and it made the traces public so the same exercise can be repeated. Vendor data that leaves reproduction open is easier to work with than neutral data that keeps it closed.

How these choices harden a market

Tie the figures together and a loop appears. The loop itself is not something the study proved; it is the direction the observed values structurally point in, which is a weaker claim and should stay that way.

When an agent chooses from priors, the names that appear most often in training data win. That choice becomes code, the code accumulates in public repositories, and the repositories become training data for the next generation. When an agent chooses by web search, the direction is much the same. What ranks near the top of search results is what already has documentation and examples, and the capacity to produce those comes from scale that has already been achieved.

  • The priors-driven path freezes the market structure of the training snapshot. An alternative that appeared after that point may be named as a candidate while lacking the worked examples needed to carry a session to completion
  • The search-driven path responds to how documentation is written. It updates faster, but the advantage still accrues to whoever has the resources to polish those pages, which is not a neutral condition either
  • The mentions-versus-adoption gap shows that a position exists inside this loop where a name gets discussed without ever getting installed. Sustained over time, being raised 139 times and chosen zero times means recognition rises while code share does not

Layer the per-language divergence on top and the picture sharpens. Ecosystem inertia, passing through an agent, gets reproduced faster and more quietly than before. When people made these calls there was at least one meeting. When an agent makes them, the meeting disappears and only a diff remains, and a diff is a poor place to notice that a vendor decision was just made.

So what has to be pinned down

The conclusion is not to switch tools. It is that when an organization already has an answer, there is no substitute for writing that answer down where the agent will read it. As long as the three tools diverge in more than half the categories, anything left unspecified gets filled in by the tool's disposition and the repository's inertia, in whatever proportion the day happens to supply.

The minimum worth writing down

Four things are worth pinning. The allowlist of services already under contract and cleared by security review, the existing stack already present in the same repository, a requirement to record the reasoning behind a choice, and an approval path for whenever a new dependency appears. The first two narrow the answer; the last two create a place for a human to intervene wherever narrowing was not possible.

# Minimum block for a repository rules file (AGENTS.md, CLAUDE.md and similar)

## Rules for choosing external services

Allowlist - choose only from these. Contracts and security review are done.
  Payments      : Stripe
  Email         : SendGrid
  Object storage: Amazon S3
  Database      : internal managed PostgreSQL

Already present - use these instead of adding anything new.
  lib/mailer  : a SendGrid client already exists here
  lib/storage : an S3 client already exists here

If a category outside the allowlist is requested - stop instead of choosing.
  Write down 2 or 3 candidates with the reason each was rejected, then ask for approval.

Forbidden - a change that adds a new SDK to package.json, go.mod or pom.xml
            is never committed without human approval.

Where a rules file does not exist or cannot be edited, the same content goes into the prompt. What matters is separating the instruction to choose from the instruction to record why. Once the reasoning is on the page, the problem from the previous section, a judgment resting on one sentence about a free plan, becomes something a person can reverse before it ships.

When an external service is needed, follow this order.

1. Read the repository first. If a client doing the same job already exists, use it.
2. If not, list at least 2 candidates, and for each one write
   - the evidence behind the judgment (a documentation URL or a path inside the repo)
   - the pricing tier and limits that were assumed
   - the reason it was rejected
   as one line each.
3. Our plan may not be the free tier. Do not use free-tier limits as evidence.
4. Propose the final choice only. Commit the dependency after approval.

What could not be established

  • The definition of a cell behind the 42 percent remains unknown. Whether the grid's axes are categories, or categories crossed with languages, is never written down. That is why the figure is not restated here as a session-level agreement rate
  • The breakdown by exclusion reason for the 11,601 runs that failed the validity filter is not published. With no split between bias exclusion and no-choice sessions, the character of the excluded set cannot be assessed
  • The model and CLI versions of the three agents, and the dates the runs took place, are absent from the article. There is no basis for estimating how much the values would move if the same study ran at a different time
  • Whether Stripe's nine out of ten, Neon's 66 percent, S3's 45 percent and email's 35.6 percent are within-category shares or shares of the whole is not specified. They are read here as within-category, with that assumption stated alongside
  • A per-persona breakdown has not been released. Whether the winner distribution differs between a vibe coder and an enterprise engineer cannot be judged from this study alone
  • The full list of the 18 sectors and the session count for each are not available. Only payments, databases, file storage, email, deployment and voice surface in the text
  • The adoption count corresponding to Supabase's 242 mentions is not given. Only the statement that Neon led the database category appears, which is why that cell in the mentions table is left blank
