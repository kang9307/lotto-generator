一个字符的宽度不是 1 - 东亚宽度属性与终端表格错位的地方

字符数、字节数与显示宽度是三个不同的数字，而对齐取决于其中的宽度

2026-07-31 开发/基础设施

症状：表格只在宽字符行上错位

打开运维脚本输出的库存表，英文行的列对得严丝合缝，只有含宽字符的行整体往右偏。翻代码也找不出毛病。所有单元格走同一个函数，传同一个宽度值。可屏幕上就是对不齐。

原因只有一个。补空格的函数所数的数字，和终端所数的数字不是同一个。Python 的 ljust 和 JavaScript 的 padEnd 都按「有几个字符」补空格，而终端按「占几列」绘制。汉字、韩文音节和日文假名都是一个字符占两列，所以字符数对齐必然导致列数错位。

这里出现了第五个数字。一个字符串身上原本已经挂了四个：字节数、代码单元数、码位数，以及人类眼中算作一个字的字素数。这四者的区别在一个表情符号被数成 11 个字符里讲过。本文只处理叠在它们之上的第五个数字，也就是显示宽度。

  • 显示宽度无法由前面四个数字中的任何一个推导出来。后面会看到，同样是 3 字节的字符，有的宽度是 1，有的是 2
  • 显示宽度也不只由字符本身决定。Unicode 专门标出了一类「模糊」的字符，它们的宽度由环境决定
  • 所以本文的结论不是「按 2 来数」。现实的目标是分清哪些地方该数宽度、哪些地方该数字符数，并且让输出即便错位也仍然可读

执行环境。下面所有数字都是在 Windows 10 Pro (10.0.19045) 上实际跑出来的。工具是 Python 3.13.3 (win32) 内置的 unicodedata（Unicode 数据 15.1.0）与 Node.js v22.16.0 (win32)。标准输出编码固定为 UTF-8。

没有的库就写没有。这台机器没有安装 Python 的 wcwidth 包，也没有 Node 的 string-width 包。因此下面所有宽度值都是在脚本里自己算出来的，直接来自 Unicode 属性值，而不是某个第三方实现的判断。

★全文不依赖渲染。本文的所有判断都基于码位与宽度属性值。没有把「我的终端里看起来是这样」当作依据，每个字符都标注了 U+XXXX。屏幕上实际画成几列是由字体和终端决定的另一个问题，这条边界会在第 3 节单独处理。

本文不涉及的内容。字节、代码单元与字素之间的差别在 ZWJ 序列与字符数校验 里。同一个字变成两串码位的规范化原理在 NFC 与 NFD 里，本文第 4 节只看规范化对宽度的影响。因为用错编码去读字节而导致文字损坏，属于 cp949 与 UTF-8 那一侧，与本文无关。

1. 字符数相同，宽度却不同

先把症状原样复现。用 str.ljust 画一张品名、负责人、数量三列的表。错位的输出原封不动贴在下面。

python 3.13.3 / win32 / unicodedata 15.1.0

--- 1-1. a table padded by character count (str.ljust) ---
----------------------------
item          owner   qty
USB-C cable   kim     12
USB-C 케이블     김철수     12
모니터 받침대       박영희     3
keyboard      lee     7
마우스           최민수     40
----------------------------

三行英文对齐，三行宽字符往右偏。要点在于代码并没有出错。ljust 完全按照指令执行，只是指令的单位选错了。换成数字来看是这样。

--- 1-2. one cell, three different numbers ---
cell                chars  utf8B  width
--------------------------------------------
[kim]                   3      3      3
[김철수]                   3      9      6
[USB-C cable]          11     11     11
[USB-C 케이블]             9     15     12
[모니터 받침대]               7     19     13

--- 1-3. same character count, different width ---
  [kim] vs [김철수]   chars 3 = 3   utf8 3B vs 9B   width 3 vs 6   gap 3
  [abcd] vs [정산표]   chars 4 = 3   utf8 4B vs 9B   width 4 vs 6   gap 2
  [KR] vs [한국]   chars 2 = 2   utf8 2B vs 6B   width 2 vs 4   gap 2

  ljust(8) on both, then a pipe:
    [kim     ]|
    [김철수     ]|
    padding added: 5 vs 5 spaces, but the printed columns differ by 3

头两行就是全文的摘要。kim 和 김철수 都是 3 个字符。但字节数是 3 与 9，列数是 3 与 6。ljust(8) 给两边补的都是同样的 5 个空格。函数做得一视同仁，结果却差了 3 列。

  • 字符数相同而宽度不同。所以用字符数算出来的补白必然错位
  • 按字节数算同样不对。김철수 是 9 字节而宽度是 6 列。3 字节对 2 列，连比例都不是整数
  • 错位的幅度正好等于该单元格里宽字符的个数。김철수 有 3 个宽字符，错位也正好是 3 列
  • 纯英文的表格永远不会出这个问题。在 ASCII 区间里三个数字完全一致。事故从第一个宽字符进来的那一刻开始

把一个单元格拆到字符级别，就能看见分歧发生在哪里。

--- 1-4. per character of one cell ---

  [S]  U+0053  eaw=Na  chars=1  utf8=1B  width=1
  [B]  U+0042  eaw=Na  chars=1  utf8=1B  width=1

  [블]  U+BE14  eaw=W   chars=1  utf8=3B  width=2

标为 eaw 的那一列就是本文的主角。它是东亚宽度（East Asian Width）属性，Unicode 给每一个码位都挂了一个这样的值。前六个字符是 Na，后三个是 W。下一节先数清楚这个值一共有几种。

2. 宽度属性的六个取值 - W、F、H、Na、A、N

Unicode 标准附件第 11 号（UAX #11）定义了六个值。每个值挑一个代表字符，用 unicodedata.east_asian_width 实测。

整理成表格如下。核心是真正表示两列的取值只有 W 和 F。

取值名称含义实测例（码位）列数
WWide本身就宽的字符。汉字、韩文音节、日文假名U+4E00, U+D55C, U+30422
FFullwidth窄字符的全角对应形U+FF21, U+FF102
HHalfwidth宽字符的半角对应形U+FF76, U+20A91
NaNarrow拥有全角对应形的窄字符。ASCIIU+0041, U+00241
AAmbiguous时宽时窄的字符U+03B1, U+00B1由环境决定
NNeutral从未出现在东亚遗留字符集中的其余部分U+0627, U+26031
  • W 和 F 的差别在来历。W 本来就宽，F 是为对应某个窄字符而另外造出来的全角形。结果都是两列
  • H 是反方向。它是对应某个宽字符的半角形，占一列。半角片假名属于这一类
  • 韩元符号 U+20A9 竟然是 H，很扎眼。它是货币符号却被归为半角。第 4 节会讲这个值为什么重要
  • N 不是「不认识的字符」，而是「从未进过东亚遗留编码的字符」。阿拉伯字母和图形符号落在这里，实用上按一列处理
  • A 不是多出来的一个宽度，而是尚未做出决定的状态。这一类占了本文的一半篇幅
  • UAX #11 明确说这个属性不是渲染宽度。用标准自己的话说，字形的实际显示宽度由字体给出，还可能被排版进一步调整。宽度属性记录的是等宽语境下的惯例，不是屏幕实测值

W 有 18 万个，是因为汉字和韩文音节。值得留意的是 A 有 13 万个，但这个数字不能照单全收。第 3 节把它拆开。

3. 模糊宽度（A）才是真正的问题

UAX #11 写明，模糊宽度需要字符编码之外的额外信息才能确定宽度。它指向语言标签、文字系统识别、关联字体、数据来源、显式标记这类上下文，并建议在无法确立上下文时按窄字符处理。换句话说，这是唯一一类宽度不由字符本身决定的字符。

关键在于哪些字符属于这一类。我挑了 39 个日常使用的字符做实测。

39 个里有 33 个是模糊宽度。把这份清单读一遍，就能立刻明白为什么它才是真问题。

  • 希腊字母和西里尔字母整体都是模糊宽度。带公式的报告、统计输出、俄语数据全都撞在这里
  • 引号和省略号是模糊宽度。U+201C、U+201D、U+2026 是文字处理软件自动替你插入的字符，会无声无息混进用户输入
  • 制表符整块都是模糊宽度。U+2500、U+2502、U+250C。画一张带边框的表，先随环境分歧的不是内容而是边框
  • 紧挨着的字符也可能取值不同。U+2588（实心块）是 A，而 U+2591（浅阴影）是 N。用这两个画进度条，同一行里规则就混了
  • 货币符号也分家。欧元 U+20AC 是 A，而英镑 U+00A3 是 Na。「符号都是模糊宽度」这种猜测是错的

所以同一个字符串在不同环境里宽度不同。把模糊宽度当 1 和当 2 的结果并排算出来。

13 万里有大约 13.7 万落在私用区（Co），真正已分配的字符是 1,271 个。可这 1,271 个的分布偏偏是最糟的。

  • U+2500 区段 162 个。画表格边框用的字符全在这里
  • U+2400 区段 159 个。U+2460 系的带圈数字，列清单时常用
  • U+0300 区段 160 个。希腊字母与组合符号混在一起。组合符号在第 6 节单独处理
  • U+2100 区段 53 个。摄氏度 U+2103、编号 U+2116 这类单位符号在这里
  • 合计 1,271 个，说明它们绝不是「生僻字符」。办公文档和报告里天天在用的就是这些

本文的第二个论点由此而来。宽度不只由字符本身决定。对这 1,271 个字符，Unicode 拒绝给出答案，而是把决定权交给环境。因此在所有终端、所有字体上得到相同的对齐，原理上就是不可能的。

4. 全角与半角 - 同一个 A 有两个码位

看看第 2 节的 F 和 H 在实务中长什么样。Unicode 里看起来像字母 A 的字符有两个。

--- 4-1. two codepoints that both look like the letter A ---
  U+0041  LATIN CAPITAL LETTER A             eaw=Na  utf8=1B  width=1  [A]
  U+FF21  FULLWIDTH LATIN CAPITAL LETTER A   eaw=F   utf8=3B  width=2  [Ａ]

  are they equal as strings? False
  NFKC of U+FF21 -> U+0041
  NFC  of U+FF21 -> U+FF21  (unchanged)

--- 4-2. a fullwidth-typed ID compared to an ascii one ---
  ascii     [INV-2026]  chars=8  utf8=8B  width=8
            codepoints: U+0049 U+004E U+0056 U+002D U+0032 U+0030 U+0032 U+0036
  fullwidth [ＩＮＶ－２０２６]  chars=8  utf8=24B  width=16
            codepoints: U+FF29 U+FF2E U+FF36 U+FF0D U+FF12 U+FF10 U+FF12 U+FF16
  s_ascii == s_full            : False
  NFKC(s_full) == s_ascii      : True
  width before NFKC: 16   after NFKC: 8

这个结果在实务中会引发两类事故。

  • 字符数一样，宽度翻倍。用全角输入的订单号还是 8 个字符，却吃掉 16 列。按字符数做的校验全都通过，只有表格错位
  • 字符串比较失败。INV-2026 和用全角打出来的同一个值并不相等。输入法停在全角模式时进来的值根本查不到
  • NFC 修不了这个问题。把全角折叠成 ASCII 的是兼容规范化（NFKC），而人们常用的 NFC 会原样保留 U+FF21。两种规范化的区别见 NFC 与 NFD 那篇
  • 套上 NFKC 之后宽度从 16 减半到 8。也就是说规范化放在哪个位置，会让同一份输入有不同的宽度

再看反方向的半角：半角片假名和半角韩元符号。

--- 4-3. halfwidth katakana: 1 column, still not ascii ---
  halfwidth [ｶﾀｶﾅ]  chars=4  utf8=12B  width=4  eaw=H H H H
            codepoints: U+FF76 U+FF80 U+FF76 U+FF85
  normal    [カタカナ]  chars=4  utf8=12B  width=8  eaw=W W W W
            codepoints: U+30AB U+30BF U+30AB U+30CA
  NFKC(halfwidth) -> カタカナ   width 4 -> 8

--- 4-4. the trap: a voiced halfwidth kana is TWO codepoints ---
  [ﾊﾞ] codepoints: U+FF8A U+FF9E  chars=2  width=2
  NFKC -> [バ] codepoints: U+30D0  chars=1  width=2
  so normalization changed BOTH the character count and the width

--- 4-5. width is not decided by byte count ---
char   codepoint eaw  chars  utf8B  width
----------------------------------------------
[A]    U+0041    Na       1      1      1
[Ａ]    U+FF21    F        1      3      2
[ｶ]    U+FF76    H        1      3      1
[é]    U+00E9    A        1      2      1
[₩]    U+20A9    H        1      3      1
[一]    U+4E00    W        1      3      2
[😀]    U+1F600   W        1      4      2

4-5 这一块证明了开头的第一个主张。宽度无法由字节数推导。同样是 UTF-8 三字节的字符，U+FF21 宽度为 2，而 U+FF76 和 U+20A9 宽度为 1。字节数相同，答案不同。

  • 半角片假名是 4 个字符、12 字节、4 列。它不是 ASCII，宽度却是 1。「非 ASCII 就是宽度 2」的假设在这里破产
  • 套上 NFKC 之后宽度从 4 翻倍到 8。与 4-2 的方向相反。可见规范化既能压缩宽度也能放大宽度
  • 带浊音记号的半角假名是两个码位。U+FF8A 加 U+FF9E，NFKC 会把它们合成单个 U+30D0。字符数和宽度同时改变
  • 韩元符号 U+20A9 宽度为 1 这一点会直接影响金额列。因为它是货币符号就预留两列，就会正好错这么多

5. 按宽度计数的函数

现在来修。需要的是用宽度合计而非字符数来计算补白的函数。这台机器上没有外部包，所以只用标准库自己写了一个。

# width_util.py   (Python 3.13.3, unicodedata 15.1.0)
import unicodedata

ZERO_CATS = ("Mn", "Me", "Cf")     # combining, enclosing, format

def char_width(ch, ambiguous=1):
    if unicodedata.category(ch) in ZERO_CATS:
        return 0                            # gate 1: advances nothing
    e = unicodedata.east_asian_width(ch)
    if e in ("W", "F"):
        return 2                            # gate 2: always two columns
    if e == "A":
        return ambiguous                    # gate 3: the environment decides
    return 1

def str_width(s, ambiguous=1):
    return sum(char_width(c, ambiguous) for c in s)

def pad(s, n, ambiguous=1, align="l", fill=" "):
    gap = n - str_width(s, ambiguous)
    if gap <= 0:
        return s
    if align == "l":
        return s + fill * gap
    if align == "r":
        return fill * gap + s
    left = gap // 2
    return fill * left + s + fill * (gap - left)

def trunc(s, n, ambiguous=1, ellipsis="..."):
    if str_width(s, ambiguous) <= n:
        return s
    room = n - str_width(ellipsis, ambiguous)
    out, acc = [], 0
    for ch in s:
        cw = char_width(ch, ambiguous)
        if acc + cw > room:
            break
        out.append(ch)
        acc += cw
    return "".join(out) + ellipsis

要点是 ambiguous 作为参数暴露在外。模糊宽度没有写死在函数里，而是交给调用方决定。正如第 3 节所示，那个值属于环境，不是函数能知道的东西。用这个函数把第 1 节的表重画一遍。

  • 补进去的空格数量本身就不同。看 5-2，同样是 16 列的字段，不同单元格分别补了 12、5、4、3 个空格
  • 截断同样要按宽度做。long[:10] 留下 10 个字符，可它们的宽度是 17 列，会撑破字段
  • 省略号本身的宽度也要算进预算。上面的函数先减去 ... 的宽度，再填剩下的位置

6. 组合字符与零宽 - 简单求和再次出错的地方

第 5 节的函数有三道关卡。这一节讲为什么第一道关卡是必需的。有些字符的宽度属性值与它实际占用的列数并不一致。

--- 6-1. characters whose EAW value says nothing useful ---
codepoint eaw cat   name
----------------------------------------------------------
U+0301    A   Mn    combining acute accent
U+0308    A   Mn    combining diaeresis
U+200D    N   Cf    zero width joiner
U+200B    N   Cf    zero width space
U+200E    N   Cf    left-to-right mark
U+FE0F    A   Mn    variation selector-16
U+0E31    N   Mn    thai mai han akat
U+302A    W   Mn    ideographic level tone mark

最后一行是决定性的。U+302A 的宽度属性是 W。只看宽度属性求和的函数会给它记 2。可它是叠在前一个字符上方的声调符号，实际占用的列数是 0。UAX #11 本身就写明，对这一类字符宽度属性无法与字符的前进宽度对应。

规范化状态会自己制造出这个问题。

--- 6-2. accent as a separate codepoint changes both counts ---
  precomposed : [café]  chars=4 naive=4 zero-aware=4
    codepoints: U+0063 U+0061 U+0066 U+00E9
  decomposed  : [café]  chars=5 naive=5 zero-aware=4
    codepoints: U+0063 U+0061 U+0066 U+0065 U+0301
    same text? False   naive width gap: 1

  precomposed : [Ångström]  chars=8 naive=8 zero-aware=8
    codepoints: U+00C5 U+006E U+0067 U+0073 U+0074 U+0072 U+00F6 U+006D
  decomposed  : [Ångström]  chars=10 naive=10 zero-aware=8
    codepoints: U+0041 U+030A U+006E U+0067 U+0073 U+0074 U+0072 U+006F U+0308 U+006D
    same text? False   naive width gap: 2
  • 同一个词，分解形的宽度求和大 2。因为 Ångström 里的两个组合符号各被数成了 1
  • 懂得零宽的函数给出 8 和 8，两者相同。它把类别为 Mn 的 U+030A 和 U+0308 当作 0 处理
  • 这个差别肉眼看不见。屏幕上是同一个词，只有表格错位
  • 在规范化形式混杂的数据库里尤其常见。有的行是分解形、有的行是预组合形，同一列里的宽度就会来回晃

宽字符单元格里混进不可见字符也会产生同样的结果。

--- 6-5. so the rule needs two gates, not one ---
  counter-example proving gate 1 must come FIRST:
    U+0301  cat=Mn  eaw=A  -> naive rule says 1, correct answer is 0
    U+302A  cat=Mn  eaw=W  -> naive rule says 2, correct answer is 0
    U+FE0F  cat=Mn  eaw=A  -> naive rule says 1, correct answer is 0

6-3 的三行只能靠码位清单区分。显示出来都是同样的四个字，可其中一个含有 U+200B，另一个含有 U+200D。简单求和把这两个数成 9 列，于是各少补了 1 列。

由此宽度函数的关卡顺序就固定下来了。

  • 关卡 1：一般类别为 Mn、Me、Cf 则返回 0。无论宽度属性是什么都无视
  • 关卡 2：宽度属性为 W 或 F 则返回 2。到这里为止是确定的部分
  • 关卡 3：宽度属性为 A 则返回调用方传进来的值。函数不做决定
  • 其余返回 1。H、Na、N 都落在这里
  • 关卡 1 必须排在最前。如果 U+302A 先被关卡 2 拦住就会变成 2，多算两列

这是最难缠的一种。十一个边框字符全是模糊宽度。上面这张表是按模糊宽度等于 1 画出来的，所以在把模糊宽度当作 2 的环境里，先翻倍崩掉的不是内容而是边框。内容单元格算得再准，框架一晃就全无意义。

  • 用制表符画的表没有可移植性。同一份输出在一种环境里是对的，在另一种里宽了一倍
  • 替代方案是 ASCII 边框。-、|、+ 全是 Na，不会晃。样子朴素，但宽度是确定的
  • 进度条也是同样的问题。U+2588 是 A 而 U+2591 是 N，一根条里规则就混了
  • 用表格库时也要确认这个值。不知道库采用哪种惯例，就无法预测结果

接下来是如何事先判定哪些单元格可能撼动版面。只由确定宽度的字符组成的单元格是安全的，含有模糊宽度或零宽字符的单元格会随环境移动。

  [정산완료       ] UNSTABLE
        U+200B  zero-width  eaw=N  cat=Cf
  [café        ] UNSTABLE
        U+00E9  ambiguous   eaw=A  cat=Ll
  [「인용」        ] stable  (no A, no zero-width)

--- 8-5. the cheapest fix: stop aligning by padding ---
  padded (breaks when the environment disagrees):
    주문번호    A-20260731-0012
    담당        kim
    상태        승인 대기
  delimiter-separated (cannot break):
    주문번호	A-20260731-0012
    담당	kim
    상태	승인 대기
  key=value (cannot break):
    주문번호=A-20260731-0012
    담당=kim
    상태=승인 대기

这套判定的核心在于，8-4 里只含宽字符的单元格判为稳定，而 café 判为不稳定。韩文音节全是 W，宽度确定；é 是 A，交给环境。结果与「宽字符才是问题」的通俗印象正好相反。

  • 只需标出含模糊宽度的单元格。不必全量审查，只找宽度属性为 A 的字符，以及类别为 Mn、Me、Cf 的字符即可
  • 直角引号 「」 是稳定的。U+300C 系确定为 W，而 U+201C 系是 A
  • 最便宜的解法是放弃用空格对齐。改用制表符或等号分隔，就根本不需要宽度计算
  • 分隔方式对机器也更友好。用空格对齐的表格，解析时还得重新猜列边界
  • 如果确实需要表格，就把模糊宽度赶出去。边框换成 ASCII，带圈数字换成括号数字，晃动就消失了
  • 完美对齐不是目标。错位也能读才是目标。列偏一格的表格还能读，列错乱的表格读不了

Python 的标准库里有 unicodedata.east_asian_width，可以直接问属性值。Node 没有这样的 API。Intl.Segmenter 是有的，但它是切分字素边界的工具，不会告诉你宽度。因此必须自己随身携带一张范围表，而自己做的表最容易把模糊宽度这一类整个漏掉。上面那张表就默默把 U+03B1 和 U+2500 当成了一列。

  • 范围表被绑死在某个 Unicode 版本上。本文的 Python 用的是 Unicode 数据 15.1.0，而官方公布的属性文件最新版是 17.0.0。每加入新字符，手工表就落后一截
  • 未分配码位的默认值也得知道。属性文件把默认设为 N，但给 U+3400..U+4DBF、U+4E00..U+9FFF、U+F900..U+FAFF 以及第 2、3 平面的未指定区域默认 W。做范围表时漏掉这条规则，未来的汉字就会变成一列
  • 两种运行时混用的流水线最危险。Python 按宽度对齐好的东西，Node 再按代码单元切一刀，结果就哪一边的标准都不是了
  • 挑选实现时先确认它怎么处理模糊宽度。没有选项的实现，等于已经替你把决定做完了

检查清单。① 补白与截断用的是宽度合计而不是字符数吗。② 宽度函数是否先把类别 Mn、Me、Cf 筛为零。③ 模糊宽度的取值是暴露给调用方还是写死在函数里。④ 表格边框有没有在用 U+2500 系。⑤ 全角输入（U+FF01~U+FF60）是否在边界处用 NFKC 折叠。⑥ 完成的行有没有再喂回宽度函数确认全部相同。⑦ 这里真的需要对齐吗，能不能换成分隔符。

没有用眼睛确认的部分。本文所有判断都基于属性值与码位。模糊宽度的字符在某个具体终端里实际画成几列、半角片假名在某种字体里长什么样、表情符号是不是画成两列宽，这些都没有确认，也无法确认，因为它们因环境而异。而这恰恰就是本文的结论。渲染是另一个问题，代码所能做到的极限，是给出一个建立在属性值之上的预测。

# 显示宽度对齐 — 可复制的对照表与补白函数

> 来源: braindetox.kr — 一个字符的宽度不是 1
> 依据: Windows 10 / Python 3.13.3 (unicodedata 15.1.0) / Node.js v22.16.0 实际执行
> wcwidth 与 string-width 均未安装，仅用标准库计算

## 1. 一个字符串身上的五个数字

| 数字 | 数的是什么 | 例: 김철수 | 例: café (U+00E9) |
|---|---|---|---|
| UTF-8 字节 | 传输与存储大小 | 9 | 5 |
| UTF-16 代码单元 | JS 字符串长度 | 3 | 4 |
| 码位 | Unicode 字符个数 | 3 | 4 |
| 字素 | 人眼中的字 | 3 | 4 |
| **显示宽度** | **终端列数** | **6** | **1 或 2（看环境）** |

## 2. 东亚宽度属性六值对照表

| 取值 | 名称 | 列数 | 实测例 |
|---|---|---|---|
| `W` | Wide | 2 | U+4E00, U+D55C, U+3042 |
| `F` | Fullwidth | 2 | U+FF21, U+FF10 |
| `H` | Halfwidth | 1 | U+FF76, U+20A9 |
| `Na` | Narrow | 1 | U+0041, U+0024 |
| `A` | Ambiguous | **由环境决定** | U+03B1, U+00B1 |
| `N` | Neutral | 1 | U+0627, U+2603 |

- 表示两列的取值只有 `W` 和 `F`
- `A` 不是宽度而是**未决定状态**。UAX #11 建议无上下文时按窄处理
- 全码位扫描: W 182,417 / F 104 / H 123 / Na 111 / A 138,739 / N 790,570
- A 之中实际已分配的字符只有 **1,271 个**，其余是私用区

## 3. 按宽度补白的函数（Python，无依赖）

```python
import unicodedata

ZERO_CATS = ("Mn", "Me", "Cf")

def char_width(ch, ambiguous=1):
    if unicodedata.category(ch) in ZERO_CATS:
        return 0                          # 关卡 1: 必须最先
    e = unicodedata.east_asian_width(ch)
    if e in ("W", "F"):
        return 2                          # 关卡 2
    if e == "A":
        return ambiguous                  # 关卡 3: 调用方决定
    return 1

def str_width(s, ambiguous=1):
    return sum(char_width(c, ambiguous) for c in s)

def pad(s, n, ambiguous=1, align="l", fill=" "):
    gap = n - str_width(s, ambiguous)
    if gap <= 0:
        return s
    if align == "l":
        return s + fill * gap
    if align == "r":
        return fill * gap + s
    left = gap // 2
    return fill * left + s + fill * (gap - left)

def trunc(s, n, ambiguous=1, ellipsis="..."):
    if str_width(s, ambiguous) <= n:
        return s
    room = n - str_width(ellipsis, ambiguous)
    out, acc = [], 0
    for ch in s:
        cw = char_width(ch, ambiguous)
        if acc + cw > room:
            break
        out.append(ch)
        acc += cw
    return "".join(out) + ellipsis
```

## 4. 模糊宽度（A）清单 — 实务里真会踩到的

| 区段 | 个数 | 内容 |
|---|---|---|
| U+0000..U+00FF | 44 | ° ± × ÷ § · ® ¶ |
| U+0100..U+01FF | 34 | 扩展拉丁 |
| U+0300..U+03FF | 160 | 组合符号 + 希腊字母 |
| U+0400..U+04FF | 66 | 西里尔字母 |
| U+2000..U+20FF | 29 | ‘ ’ “ ” – — … • |
| U+2100..U+21FF | 53 | ℃ № ™ Ω ⅓ |
| U+2200..U+22FF | 50 | ∀ ∑ √ ∞ ≤ |
| U+2400..U+24FF | 159 | 带圈数字 ① ② ③ |
| U+2500..U+25FF | 162 | **表格边框 ─ │ ┌ ┬ ■ ○** |
| U+2600..U+26FF | 69 | ★ ☆ ☎ ♠ |

- 实测 39 个日常字符 → **33 个是 A**
- 一行制表符: A=1 时 10 列，A=2 时 **20 列**（差一倍）
- 容易看漏的例外: U+00A3(£)=Na, U+00A9(©)=N, U+2591(░)=N, U+2713(✓)=N

## 5. 宽度属性与实际列数不符的字符

| 码位 | 宽度属性 | 类别 | 实际列数 |
|---|---|---|---|
| U+0301 组合锐音符 | A | Mn | **0** |
| U+302A 声调符号 | **W** | Mn | **0** |
| U+FE0F 变体选择符 | A | Mn | **0** |
| U+200B 零宽空格 | N | Cf | **0** |
| U+200D 零宽连接符 | N | Cf | **0** |

- 只加宽度属性会给 U+302A 记 2，**多算两列**
- 因此类别检查（关卡 1）必须排在宽度属性检查**之前**
- UAX #11 也写明组合符号的宽度属性无法与字符前进宽度对应

## 6. 全角与半角小结

| 字符 | 码位 | 宽度属性 | UTF-8 | 列 |
|---|---|---|---|---|
| A | U+0041 | Na | 1 B | 1 |
| Ａ | U+FF21 | F | 3 B | 2 |
| ｶ | U+FF76 | H | 3 B | 1 |
| ₩ | U+20A9 | H | 3 B | 1 |
| 一 | U+4E00 | W | 3 B | 2 |

- 同样 3 字节，宽度却分为 1 与 2 → **无法由字节推导宽度**
- NFKC 把全角折成 ASCII 使宽度减半（16→8），把半角假名展成正常形使宽度翻倍（4→8）
- NFC 原样保留 U+FF21。全角问题靠 NFC 解决不了

## 7. 哪个场合用哪个数字

| 场合 | 该数的数字 |
|---|---|
| 终端表格补白 | **显示宽度** |
| 定宽日志列 | **显示宽度** |
| 文本小票 | **显示宽度** |
| HTTP 正文长度 | 字节 |
| 字符串切片 | 代码单元 / 码位 |
| 表单 maxlength | 代码单元 |
| 数据库长度限制 | 字符或字节（视产品而定） |

## 8. 检查清单

- [ ] 补白与截断用的是**宽度合计**而不是字符数
- [ ] 宽度函数**先把**类别 `Mn`/`Me`/`Cf` 筛为零
- [ ] 模糊宽度的取值**暴露给调用方**，没有写死在函数里
- [ ] 表格边框改用 ASCII 的 `-` `|` `+` 而不是 U+2500 系
- [ ] 全角输入在边界处用 NFKC 折叠
- [ ] 完成的行**再喂回宽度函数**确认全部相同
- [ ] 确认过这里是否真的需要对齐，能否换成制表符或等号分隔
- [ ] 手工做的范围表已反映未分配默认值（N，但 CJK 区段为 W）
- [ ] Python 与 Node 混用的流水线里两边标准一致

## 9. 不要做的事

- 从**字节数推导**显示宽度 — 三字节里既有宽度 1 也有宽度 2
- 把模糊宽度**当常量写死在函数里** — 那是环境该决定的
- 想用制表符画出**可移植的表格** — 十一个边框字符全是 A
- 不做类别检查就**只对宽度属性求和** — U+302A 会被数成两列
- 把「完美对齐」当目标 — 错位也能读才是现实的目标
- 看着顺眼就**判定全都对了** — 那只是你这台终端的模糊宽度惯例
