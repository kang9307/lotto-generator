画面与服务器错开的那些瞬间

状态不是一整块 - 按寿命与归属拆开来看，就能看清难点在哪里

2026年8月28日 开发/基础设施

引言：按下返回键，旧标题还留在那里

在详情页改了标题并保存。按返回键回到列表，旧标题还原封不动地排在那儿。这是一种刷新之后就会消失的缺陷。复现不稳定，没有调用栈，修好之后一个月又会以同样的形状出现在别的画面上。在前端最能吞掉时间的缺陷，多半长着这副面孔。

前不久 hackers.pub 上 FL 的一篇文章列出了状态管理工具至今仍未解决的四件事：状态的共享范围事后很难更改，共享状态的寿命难以表达，派生状态难以像一个值那样被共享，以及构成同一个功能的代码会散落到多个位置。作者认为这四件事其实是同一个问题换了几张脸。

这里不打算把那份清单抄过来，而是换一个位置去看同一个问题：不是工具没能替你做什么，而是画面上看到的东西与服务器上的东西什么时候会错开。先把错开发生的位置数清楚，无论你用哪种工具，都能看出它替你分担了什么、又把什么原样留了下来。

有一点要先说清楚。这篇文章里没有这样做就解决了。这四件事之所以被称为难点，正是因为不存在完整的解法，下面提到的每一种对策都会拿走一些东西作为代价。把那份代价一并写出来，才是这篇文章的目的。

1. 「状态」这一个词掩盖了什么

说状态管理很难的时候，这个词里混着性质截然不同的值。把它们塞进同一个容器，问题就是从这里开始的。

区分的轴有两条：原本在哪里，以及该活到什么时候。按这两条轴切开，会分出四群。

  • 服务器持有原本的数据 — 订单列表、用户资料、库存。画面上的是副本，原本别人也能改
  • 只在这个画面里活着的值 — 展开的折叠面板、正在输入的文本、拖拽坐标。画面关闭时一起消失才是正确的
  • 写在 URL 里的值 — 搜索词、页码、当前选中的标签页。这是可以当作链接交给别人的值
  • 留在浏览器里的值 — 登录令牌、深色模式设置、被关掉的提示横幅。关掉标签页也还活着
种类原本所在自然寿命由谁清除错开时的症状
服务器数据的副本服务器直到再次去问为止失效规则拿旧值去判断与展示
画面内的值那个画面直到画面消失为止画面自己别的条目的状态被带了过来
URL 参数地址栏该地址保持不变期间导航分享出去的链接打开了别的画面
浏览器存储设备不删就一直在人写下的代码发布之后旧格式仍然残留

表里值得盯着看的是由谁清除这一列。只有画面内的值把自己的寿命写进了代码结构里。剩下三种，什么时候丢弃都得由人另行决定。不决定，值就只是留着，而留得够久的值终有一天会变成错误的值。

2. 难点之一 — 原本在对面

画面上画出来的订单状态，并不是服务器上的订单状态，而是几秒前抄来的副本。这期间可能有另一位管理员改过，也可能配送公司的 Webhook 已经发过来了。副本从取来的那一刻起就开始变旧。所以问题只有一个：什么时候再去问一次。

2.1 再去问一次的时机候选

  • 刚进入画面时 — 最基本，但会漏掉停留在画面期间发生的变化
  • 距上次取回过了一段时间 — 这段时间定成多久，最终是业务判断而不是技术判断
  • 标签页重新回到前台时 — 对离开座位又回来的用户效果明显
  • 自己刚改过什么之后 — 只反映自己造成的变化，别人造成的依旧一无所知
  • 服务器主动通知时 — 随之而来的是维持长连接的成本，以及断开后的恢复设计

2.2 往哪边偏都有代价

问得频繁，请求数就上去，而且每来一次响应画面就微微抖动。正在看的列表被重排，滚动位置跳走。问得稀疏，请求少了，但用户会拿旧值作为依据去做决定。画面显示只剩一件库存、点下单却发现早已售罄，就是这样造出来的。

所以刷新间隔不该由技术偏好决定。判断标准是这个值错了还能不能挽回。资料里的昵称旧几秒钟什么事也没有，但余额、库存、权限一旦变旧，用户就会做出无法撤回的动作。对于无法撤回的那一类，不要相信进入画面时取的那份副本，而应让服务器在执行前重新判定。画面反正只是副本，不把最终判定交给画面，才是唯一可靠的对策。

3. 难点之二 — 等待期间给用户看什么

按钮按下去了。响应 300 毫秒后才到。这 300 毫秒里画面该说什么？可选项实际上只有三个。

  • 挡住并等待 — 弹出加载指示并锁住操作。诚实，但短请求也会让画面闪一下，体感反而更慢
  • 保留旧值、只改标记 — 列表原样留着，边缘做淡化处理。画面不动因而安稳，但没注意到标记的用户会把旧值当成新值
  • 乐观更新 — 假定成功，先改画面。体感延迟直接消失

3.1 乐观更新真正给的是什么

乐观更新带来的不是速度，而是连续性。点下喜欢，红心立刻填满，用户接着看下一条。实际往返时间一点没变，但等待这个体验消失了。在一边滚动一边连续操作的画面上，这个差别很大。

3.2 需要回滚时要付的代价

麻烦在失败的时候。回滚并不是把画面上的值放回去就完事了。

  • 用户已经做了下一个动作 — 新操作叠在被还原的值之上，回滚到哪个时点就变得含糊
  • 回滚的过程没人看见 — 元素已随滚动移出视野，或者用户已经切到别的标签页，那他会带着成功的印象离开
  • 服务器部分成功了 — 保存成功、只有通知发送失败时，把整个画面回滚反而离事实更远
  • 回滚改变了列表顺序 — 条目弹回原位，用户点错了本来想点的另一条

所以乐观更新不该一刀切地用在所有操作上，而要带条件地用：失败率低、失败影响只停留在那一个元素、并且回滚过程发生在用户视野之内的操作。反过来，删除、支付、改排序这类回滚不容易被看见、或者会牵动其他条目的操作，老老实实让用户等待更好。这一点与每一帧都保持一致才能建立信任的说法正面咬合：最快的画面和最诚实的画面，并不总是同一个画面。

4. 难点之三 — 同一份数据出现在多个画面时

一个订单出现在三个地方：列表里的行、详情页，还有页头那个未处理数量的角标。在详情页改了状态，另外两处要怎么知道这件事？开头那个缺陷就诞生在这里。

4.1 三种做法与各自的代价

  • 只放一份，其余去引用 — 从原理上缩小了发散的余地。代价是这一份要同时满足多个画面的诉求，改一个画面就得动到公共的形状
  • 各自持有，靠通知传播变更 — 画面之间耦合松。代价是漏掉一处订阅，那个画面就会无声地变旧，而漏掉这件事往往是用户先发现的
  • 放进以键标识的缓存，写入后让键失效 — 规则明确、易于追踪。代价是失效的键选错了，旧值会在没有任何报错的情况下留下来。键的设计直接成了一致性的设计

4.2 归一化这个岔路口

同一个实体反复出现在多个响应里时，人会想把它按实体展开、只保留一份。这样一来改一处，所有画面就都看到同一个值。代价是服务器给的形状、存储的形状、画面想要的形状全都不一样了。于是有了把响应展开的代码，也有了为展示重新组装的代码，而这两段代码一旦跟不上新增字段，值就改在组装环节丢失了。

消除重复，换来的是不一致消失、但多出转换成本；保留重复，换来的是没有转换、但得盯着不一致。两边都不是免费的，这才是重点。如果一个实体同时出现在三个以上的画面里、并且其中一个可以编辑，归一化通常痛感更小；如果只有两个画面在读，就没什么理由付这个成本。

5. 难点之四 — 顺序没有保证

在搜索框里输入到 ser，接着又输入了 serv。请求是按顺序发出去的。响应也按顺序回来，这一点没有任何保证。如果 serv 的响应先到、ser 的响应姗姗来迟，画面上留下的就是与输入框里的文字对不上的结果。

5.1 只采用最后一个

最简单的防御，是给每个请求编号，等响应回来时确认这个编号是否还是最新的。

latest = 0

on_input(query):
    latest = latest + 1
    my_seq = latest
    result = await fetch(query)
    if my_seq != latest:
        return            # 这期间已经发出了更新的请求
    render(result)

这几行挡住了画面与输入错开的大部分情况。代价是被丢弃的响应。用户删掉一个字又敲回去，实际上是同一个查询，前一次的响应却被扔掉了。而且这种做法只护住画面，服务器已经搜了五次。

5.2 中断做不到的事

发出新请求时中断上一个请求，也是常见做法。但中断是我不接收响应了的声明，不等于这个请求没发生过。请求若已抵达服务器，处理与副作用照样发生。读取时这不成问题，可一旦开始把写入也当作可中断的，就会造出画面以为已取消、服务器却已写入的状态。

5.3 写入互相叠加时

假设开关被快速按了两下。开和关都发了出去，如果响应颠倒着回来，服务器的最终状态与画面的最终状态就分岔了。这里只采用最后一个响应的规则反而有害，因为先到的那个可能正是后发的那个。在写入上，要么把请求串成串行，要么只保留用户最后的意图、只发一次，要么带上版本号让服务器去判定。无论哪一种，画面都无法独自决定，必须和服务器对齐约定。离线时关掉的设置又自己回来的同步问题，根子也在同一个地方。

6. 派生状态与重复保存

有购物车条目，也有合计金额。合计是可以从条目算出来的值，也就是派生状态。可是画面上到处都要用合计，某个时刻你就会想把合计单独存起来。岔路口出现在这里。

  • 存起来就会错开 — 一定会出现某条只改条目、忘了更新合计的路径。而那条路径通常藏在后来加的功能里
  • 每次都算又很贵 — 条目上千，或者计算里带着排序与分组，画面每刷新一次就把同样的计算重做一遍
  • 记下来则键成了问题 — 把计算结果缓存起来，就需要一条判断输入是否变化的依据。这条依据一旦比真实依赖更窄，旧值就会无声地留下

判断标准收敛成两个问题：这个值是否总能从原本推导出来，以及用户能不能直接改它。如果总能推导、用户又碰不到，默认就是不存。反过来，用户能插手的值 — 比如自动算出的运费允许客服覆盖 — 就已经不是派生，而本身成了原本，必须保存。在这里把派生和原本弄混，就会出现用户填进去的值被重算覆盖掉的事故。

引发这篇文章的那篇文章点出的第三个问题，正是在这个位置：由同样的输入产生的派生值，很难让多个画面像一个值那样共享；尤其当计算里混进副作用时 — 比如要拿到这个值得先去问服务器一次 — 那些以纯计算为前提的工具就不能原样套用。计算与拉取混在一起的值，长着派生状态的脸，实际上更接近前面说的服务器数据副本，把变旧与重新拉取的问题原封不动地继承了下来。

7. 把 URL 当作状态来用

把搜索词、筛选条件和页码放进地址，有几样东西会免费跟过来。复制链接发给同事，对方看到同一个画面；返回键的行为符合用户预期；刷新之后画面还在；收藏和新标签页天然可用。这四样若要自己写，代码量相当可观，而地址栏已经替你做好了。

代价是随之而来的约束。

  • 只能是字符串 — 对象和日期得序列化，而那套格式立刻变成对外公开的契约
  • 别人看得见 — 它会原样留在服务器访问日志、来源页头，以及别人越过肩膀看到的画面里。这不是放个人标识信息或令牌的地方
  • 长度有现实上限 — 把几百个选中项塞进地址的设计，总会在某个点被截断
  • 改结构就会弄坏旧链接 — 改掉参数名的那一刻，已经分享出去的链接会无声地打开别的画面
  • 历史记录被污染 — 搜索词每敲一个字就压一条记录，用户得按二十次返回才能离开这一页

最后一条在实务里撞得最多，判断却很简单：问一句这是不是用户会想用返回键回来的位置，是就压入新记录，不是就替换当前记录。输入过程中替换，筛选确定和翻页压入，多半符合预期。

还有一点。在使用服务端渲染的结构里，URL 是服务器唯一能知道的客户端状态。首屏要在服务器上画出来，那么画什么就必须写在地址里。决定哪些值该放进地址时，这个事实的分量比想象中更重。

8. 全局存储真正解决的与推迟的

走到这一步，人自然会想到全局存储：把值集中到一处，错开应该就少了。确实有一些东西被解决了。

  • 不必再经由中间组件手工把值一层层往下传
  • 变更集中在一处，什么在什么时候变了都能观察到
  • 画面之外发生的变化 — 收到通知、令牌过期 — 终于有了落脚的地方

被推迟的同样清楚。引发这篇文章的那四项里，有三项恰好落在这个位置。

  • 寿命 — 画面内的值随画面一起消失，提升到全局的值却没有自然的消亡时刻。退出登录时、切换到另一个组织时、离开画面时，该清掉什么会变成一份手工维护的清单。这份清单变旧的速度，和功能增加的速度一样快
  • 共享范围 — 起初只在一个画面用的值，第二个画面要用时就往上提；日后想再收窄，就得改写它的整个表达方式。范围一旦放宽就难以收回，于是多半就那样宽着留下来
  • 内聚 — 构成一个功能的值、更新逻辑与初始化散落在不同文件里。删功能时谁也说不准该一起删掉什么，这种状态就是从这里造出来的

报几个工具名字并没有用。有把一切汇进单一存储的一派，有拆成小单元再组合的一派，也有把服务器数据缓存单独抽成一层的一派，区别只在于它们让上面三件事中的哪一件不那么疼。它们都不会消除错开本身。无论在评估哪种工具，要问的都是同样三句：这个值由谁清除，改变范围要动到什么，整块删掉功能之后还剩下什么。这三句有了答案，选工具才是下一步的事。

9. 常见的误解

团队里总有些反复出现的说法。它们多半对了一半，而错的那一半日后很贵。

常听到的说法实际上该改问的问题
放到全局就省事传递变省事，丢弃变困难这个值何时由谁清除
缓存会自己管好拉取是自动的，何时丢弃由人来定什么变了这个值才算旧
有加载指示就够了它只告知延迟，说不出失败、部分成功与中断失败时画面给用户看什么
乐观更新一定是更好的体验回滚看不见的话，界面反而在撒谎回滚过程落在用户视野里吗
用了全局，画面同步就完事了只是看到同一个值，何时重新拉取原封不动这个值的原本归谁
换个工具就能理顺寿命、范围与内聚在设计里，不在工具里现在错开的位置究竟在哪

表里最后一行重复得最多。换工具会逼着你把代码重新梳理一遍，所以之后确实看起来变好了。变好的通常是那次顺手重划的边界，而不是工具本身。同样的边界用旧工具划出来，多半也会好上差不多的幅度。

10. 测试变难的地方

状态相关的缺陷之所以能活很久，原因之一是测试不容易挂上去。难处几乎都来自时间与顺序。

  • 需要变换响应到达的顺序去验证，而真实网络里那个顺序很难按需复现
  • 等真实计时器的测试很慢，慢的测试最后会被关掉
  • 缓存在测试之间存活下来，结果就随执行顺序改变。单跑通过、整体跑挂掉，就是这一类
  • 乐观更新的中间帧，只看最终状态的测试根本抓不到。回滚是否正确，必须刻意制造失败才验得出来
  • 留在浏览器存储里的值在测试环境里也照样留着，刚删掉的功能的旧值还在持续产生影响

对策各有代价。把时间与网络做成可替换的，顺序就能随意编排，但代码多了一层，而那一层与真实环境有微妙差别，于是造出一段只有测试能通过的区间。搭一个假服务器会更贴近真实，可契约一旦对不上它就沉默。没有完全安全的组合，你只是在挑选要漏掉什么。

不过优先级还算清楚：先测回滚路径与失效规则。这两者失败时不会报错，只会静静留下一个错误的值，没有自动检查的话，用户反馈就成了唯一的发现手段。反过来，加载提示、有没有转圈图标，看一眼就知道，检查的优先级更低。

11. 没能确认的部分

  • 各种做法之间性能差异的通用数字 — 结果随画面规模、数据量与更新频率而变，因此没有引用未说明条件的基准测试
  • 特定库当前的默认行为与 API — 刷新时机的默认值与失效方式每次升版都可能变，准确的答案还是各自去看所用版本的官方文档
  • 引发这篇文章的那位作者提出的解法细节 — 只确认了四个问题的提法，后续讨论与反响不在本文范围内

12. 小结 — 与其消除，不如学会应对

画面与服务器会错开。这不是缺陷，而是结构。只要原本在另一台计算机上、别人也能改动它、中间的网络既不保证顺序也不保证成功，那么持有副本的画面就永远会有一点点不对。状态管理与其说是消除这种错开的技术，不如说更接近选择让错开在哪里显形的技术。

所以实务上先做的不是挑工具，而是把值分开。从现在的代码里随便挑一个值，问三句就行：这个值的原本在哪里，它该在什么时候消失，它错了用户能不能撤回。三句都能立刻答上来的值，通常不会惹麻烦。只要有一句卡住，那里就是下一个缺陷诞生的地方。

不存在完整解法这件事，也不全是坏消息。没有解法，剩下的就是选择，而选择可以随条件不同而不同。无法撤回的值让服务器做最后判定；只在回滚看得见的操作上用乐观更新；把失效的键按数据而不是按画面来划；只把用户会想用返回键回来的位置记进地址。仅这四条守住，开头那个缺陷的大部分压根就不会诞生。剩下的到时候一个一个看就好。正如需求从相加变成相乘的界面那样，这里难的也不是单个条目，而是它们的组合。
