微软开源 GitHub 供应链攻击 2026 - 米亚斯玛蠕虫窃取凭据解析

米亚斯玛蠕虫所揭示的软件供应链攻击新面孔

2026-06-11 IT/技术

引言：最受信任的仓库化为武器的那一天

对开发者而言，很少有地方能像微软官方 GitHub 仓库那样获得不加质疑的信任。Azure 组织的部署 Action、microsoft 组织的示例代码、MicrosoftDocs 的文档——我们每天通过 npm install、git clone 以及 GitHub Actions 工作流中的一行把它们拉进来，却从未怀疑过「这会不会是恶意的」。信任是效率的另一个名字，而效率就是开发速度。

然而在 2026 年 6 月 8 日，恰恰是这份信任成为攻击通道的事件爆发了。在 GeekNews 上于 6 月 10 日被热议的这一事件，核心是这样的：微软托管的 73 个 GitHub 项目遭到入侵，源码中被注入了窃取密码的恶意软件，结果使用 AI 编码工具的开发者凭据被窃取。据报道，GitHub 仅用 105 秒就自动停用了这 73 个仓库，但那段短暂的暴露窗口以及一只已经扩散的蠕虫的影响范围绝不算小。本文将从理解与防御的角度梳理发生了什么、什么是软件供应链攻击、为何开源与开发工具会成为目标，以及开发者和组织当下应采取的防御措施。我们不会涉及利用代码或复现步骤。我们的目的是防御，而非攻击。

1. 发生了什么——米亚斯玛蠕虫的渗透

此次事件的元凶是一款名为米亚斯玛（Miasma）的恶意软件。部分安全业界也以「春枯病（The Spring Blight）」的别名称呼它。它最可怕的特征在于：这不是单纯的静态恶意代码，而是一只自我复制的蠕虫。蠕虫不会停留在一处，它在被感染的环境中窃取凭据，再用这些凭据把自身植入其他仓库，向整个生态扩散。

据报道，这只蠕虫渗入了微软的四个核心 GitHub 组织——Azure、Azure-Samples、microsoft 和 MicrosoftDocs——结果导致 73 个仓库被停用。其中包括众多组织用于部署 Azure Functions 的官方 GitHub Action Azure/functions-action。该仓库一旦被停用，依赖该 Action 的大量 CI/CD 流水线便一齐停摆。一个受信任工具的被入侵，演变为所有使用该工具之处的瘫痪。

供应链攻击的本质，在于刺中一点而撼动全局。最受信任的节点一旦被入侵，那份信任便径直化为感染的高速公路。

尤其值得注意的是，这被分析为一次二次入侵（re-compromise）。据报道，5 月中旬，微软的开源项目 Durable Task——一款帮助开发者构建可靠工作流应用的工具——率先被入侵，其官方 SDK 的恶意版本在很短的窗口内被推送到包仓库。6 月的此次事件表明，Durable Task 的入侵并未被彻底清除，或被窃取的凭据未经轮换便被保留，使攻击者得以维持立足点。一次不彻底的应对，化作第二次更大的事故卷土重来。

2. 恶意软件如何窃取凭据

在不给出具体利用手法的前提下，我们仅从威胁模型的层面梳理这只蠕虫的运作结构。这是为了识别防御要点，而非用于复现。

据报道，米亚斯玛同时采用了多条渗透路径。据安全业界分析，攻击大致分三波展开。

  • 恶意包的安装钩子：在包中植入 preinstall 之类的安装阶段钩子，使开发者安装依赖的瞬间即执行代码。这是供应链攻击的经典手法。
  • 绕过安装钩子的技术：有变种手法被报告，可在不使用标准安装钩子的情况下，于 npm install 过程中执行代码，精准钻入只监视「安装钩子」的传统防御留下的空隙。
  • 针对编辑器的直接提交：这是最新的一波。攻击者用窃取的贡献者凭据将恶意提交直接推入仓库，使开发者用 AI 编码工具或 IDE 打开该仓库的瞬间，凭据收集载荷便被触发。

蠕虫一旦在开发者环境中运行，据报道便会收集 AWS、Azure、GCP、Kubernetes、npm 和 GitHub 的凭据，并将 GitHub Actions 的密钥外泄至外部服务。随后它用窃来的令牌，向受害者拥有写权限的所有仓库重新提交自身，自主扩散。这种「窃取→扩散→再窃取」的循环，正是蠕虫如此危险的机制所在。

3. AI 编码工具为何成为新的攻击面

此次事件中最令人震惊的演进，是恶意软件绕过包管理器，直接瞄准了开发者的编辑器。据报道，第三波攻击的设计是：开发者只要在 Claude Code、Gemini CLI、Cursor、VS Code 等 AI 编码环境中打开被感染的仓库，载荷便会触发。

长期以来，供应链防御主要集中于监视 preinstall、postinstall、setup.py 等包的安装钩子。然而面对「只要打开仓库就被触发」的攻击，这条防线整个失效。由于 AI 编码工具会自动读取并解读仓库的配置文件与上下文，那份自动性本身便给攻击者提供了新的执行路径。

这并不意味着 AI 编码工具天生危险。它只是一个信号：「无需开发者显式执行任何东西，代码就可能运行」的位置增多了。工具越聪明、越自动地处理工作，针对那份自动性的攻击面也随之扩大。关于如何为系统凭据设计权限与边界，安卓版本与安全一文也有相关探讨。

4. 什么是软件供应链攻击

退一步厘清概念。所谓软件供应链攻击，是指不直接攻击最终软件，而是污染软件被构建与分发的过程——即「供应链」中的一个环节。

现代软件几乎无一例外地建立在数百乃至数千个外部依赖之上。我们写的代码只是冰山一角，其下铺着我们从未编写的大量库、构建工具、容器基础镜像与 CI/CD Action。攻击者会盯住其中最薄弱、最受信任的一环。该环节一旦被污染，恶意代码便会自动流入拉取它的所有下游。

一个被污染的依赖扩散到数千个项目的情景，早已不是假设。据业界报告，仅 2025 年一年，npm、PyPI、Maven 等主要生态就新编录了超过 45 万个恶意开源包，较上一年增长约 75%，其中半数以上被归类为意在窃取凭据与采集数据。米亚斯玛只是这股巨大潮流中最精巧、最具象征意义的案例之一。

5. 为何开源与开发工具是目标

站在攻击者的角度，开源与开发工具是「性价比」压倒性的目标，原因如下。

  • 广泛复用：一个热门包会被装进数万乃至数十万个项目。只污染一个，触达范围就是天文数字。
  • 自动安装与执行：依赖无需人逐一审查便自动下载并执行。安装钩子或构建脚本往往毫无戒备地运行。
  • 高价值凭据的集中：开发者工作站与 CI 环境里聚集着云密钥、部署令牌、包发布权限等「皇冠上的宝石」。攻破一处，收获丰厚。
  • 信任的传递：只要窃取一名维护者的账户，恶意代码便继承其全部信任。米亚斯玛盯上微软组织，正是因为这份信任之重。

核心教训由此浮现：信任是攻击者最具吸引力的资产。我们越信任某个仓库，它被入侵时的危害就越大。因此成熟的安全必须超越「信任但要验证」，迈向「信任有多大，验证就要有多大」。

6. 开发者暴露的路径

那么，一个普通开发者究竟会在哪些岔路口暴露于此类攻击？要设计防御，须先把暴露路径画清楚。

6.1 拉取依赖时

一行 npm install 或 pip install 会一并拉下数十个传递依赖。只要其中一个被污染，安装阶段的钩子或构建脚本便立即执行攻击者的代码。

6.2 在构建与 CI/CD 流水线中

GitHub Actions 之类的 CI 工作流带着强大的权限与密钥运行。一个被污染的 Action 或容器镜像进入流水线，便可能让那些密钥被整体外泄。此次事件中密钥被外泄至外部服务，正是这条路径。

6.3 打开仓库时

这是最新的暴露路径。用 AI 编码工具或 IDE 打开被感染仓库的动作本身，就可能触发藏在配置文件中的载荷。你「只是克隆并打开了一下」，凭据却泄露了。

7. 防御方法——依赖验证与哈希、签名

进入正题——防御措施。第一根轴是验证依赖的完整性。

  • 版本锁定与锁文件：用 package-lock.json、poetry.lock 之类的锁文件钉住依赖版本，避免无节制的自动升级。这是防止某天恶意版本悄然混入的第一道防线。
  • 哈希与完整性校验：信任锁文件中的完整性哈希，并将安装配置为校验哈希是否一致。包内容若被暗中篡改，哈希便会对不上而被发现。
  • 签名验证：在可能时验证包或提交的签名（如 Sigstore、提交的 GPG 签名），以确认「这真的出自那位维护者吗」。
  • 审查并阻断安装脚本：对不可信的包，禁用安装脚本的自动执行，或仅在隔离环境中安装。
  • 依赖审查自动化：生成 SBOM（软件物料清单），并在流水线中加入自动对照已知恶意包与漏洞数据库的工具。

8. 防御方法——密钥管理与双因素认证

第二根轴是缩小凭据本身的暴露面。即便恶意软件混入，只要可窃之物少、窃得之物很快失效，危害便可被控制。

  • 清除明文密钥：不要把令牌和密钥以明文留在代码、.env、Shell 历史或环境变量中，而应存入专用的密钥管理器。此次蠕虫恰恰翻遍了环境变量与配置文件。
  • 短期、OIDC 令牌：用很快过期的 OIDC 令牌取代长期静态令牌。即便被窃也会迅速失效，缩短暴露的有效期。
  • 最小权限原则：只给 CI 令牌和 PAT 授予确有必要的范围。危害的上限即令牌权限的大小。
  • 强制双因素认证（2FA）：为所有 GitHub 与包发布账户强制 2FA，使账户被接管本身更难。
  • 密钥扫描与推送保护：防止令牌被误提交，并接入暴露后的自动吊销流程。

这些原则归根结底是最小权限原则（Principle of Least Privilege）的直接应用。先问「这份凭据若泄露能做到什么」，再去收窄其范围——无论对象是令牌还是代理，思路相同。收窄一行权限，就能减少一次入侵的危害。

9. 受害排查与应对——若怀疑被入侵

倘若你可能身处波及范围，应当排查什么、如何排查？依据报道与安全业界的建议整理如下。

  1. 排查组织内的异常仓库：检索是否出现不明的新公开仓库，尤其是被视为蠕虫痕迹的描述，或以 JSON 形式提交的密钥。
  2. 排查工作站与构建环境：确认 GitHub 上是否有异常活动、是否新建了未知仓库、是否通过 VS Code 或 AI 编码 CLI 运行了意外的后台进程。
  3. 全面轮换凭据：立即轮换该系统可访问的所有凭据——GitHub 令牌、npm 令牌、AWS 密钥、Azure 服务主体、GCP 服务账户、SSH 密钥、Kubernetes 密钥、Docker 配置，以及环境变量与 Shell 历史中的值。
  4. 重新验证依赖：核对最近安装或更新的依赖的版本与哈希，把可疑版本回退到已知正常的版本。
  5. 审阅审计日志：在组织与云的审计日志中，查找来自陌生 IP、陌生时段的访问、大量克隆与异常推送。

关键是不要拖延轮换。此次二次入侵源于 5 月未被轮换的凭据，这一分析清楚地表明，不彻底的应对如何招来第二次事故。怀疑就轮换。已被吊销的令牌是无害的。

10. 威胁模型对比

把此次事件的结构性含义压缩成一张表。同一份凭据，处理它的环境不同，威胁模型也随之改变。

维度 传统安装钩子攻击 打开仓库即触发攻击（新型）
触发时机 包安装时 用 IDE/AI 工具打开仓库时
主要防线 监视并阻断安装钩子 校验配置文件、沙箱化
传统防御效果 相对有效 很大程度失效
窃取对象 安装环境的凭据 编辑器、云端、CI 的凭据

这张表说得明白：供应链防御不能只停留在「安装阶段」一处。凡是代码可能运行的所有位置——安装、构建，乃至如今「打开仓库」的行为——都必须纳入威胁模型。关于恶意软件的机制与应对，语音钓鱼与诈骗警示一文也有相关探讨。

11. 供应链安全的教训——把信任设计出来

最后，让我们退一步保持平衡的视角。此类事件一旦爆发，「开源危险，别用了」或「关掉 AI 编码工具」之类的反应很容易出现。但那并非正确结论。开源与自动化工具的生产力收益是压倒性的，把它们整个抛弃，无异于为捉一只臭虫而烧掉整间屋子。

合理的态度是把信任从一种模糊的感觉，变为一套设计好的流程。锁定依赖、验证哈希与签名、把密钥关进管理器、让令牌短命、为所有账户强制 2FA、怀疑即刻轮换——这些流程一旦到位，纵使米亚斯玛这样的蠕虫混入，可窃之物也寥寥，扩散之路也变窄。

与此同时，平台与维护者亦有责任。GitHub 在 105 秒内自动封禁 73 个仓库是防御的范例，但在供应链中，哪怕那 105 秒也可能很长。把被入侵的凭据彻底轮换、把立足点完全清除、把二次入侵的循环斩断，归根结底是运营方的本分。好的安全不会止于一次封禁，而会延续到把根拔除为止。

结语：怀疑一个依赖，收窄一个令牌

袭击微软 GitHub 的米亚斯玛蠕虫事件，凝练地表明：即便最受信任的仓库也可能成为供应链攻击的通道，而 AI 编码工具的自动性打开了新的攻击面。但这并非末日的信号，而是重新设计信任的信号。

以三条当下即可落实的要点收尾。其一，锁定依赖并验证完整性。逮住某天悄然变更的包，是第一道防线。其二，把密钥关进管理器，让令牌短命且最小权限。可窃之物少且很快失效，危害便可控。其三，怀疑被入侵就别拖延，立即轮换。正如此次二次入侵所教训的，未被轮换的凭据是第二次事故的种子。享受信任，又以流程去验证那份信任——这便是在供应链时代安全生存的开发者的基本功。
