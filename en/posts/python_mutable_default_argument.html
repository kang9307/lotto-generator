An Empty List Default That Keeps Growing - When Python Evaluates Default Arguments

Going past 「just use None」 to the reason the design works this way

2026-07-31 Dev/Infra

Opening: from the second call on, the response held someone else's data

There was a function that took an order, dropped it into a list and returned the list. The tests passed and the first request was fine. Then the response to the second request still carried the order number from the first one. The third request contained both of the earlier ones. The database was clean, there was no global variable to be found, and no caching layer had ever been added.

The culprit was one line of the signature. An empty list had been written as the default value of a parameter. This trap is famous, and searching for it produces 「use None」 within three seconds. But memorising the prescription alone leaves you permanently unable to recognise two other symptoms that come from the same cause.

The axis of this article is the cause, not the cure. The cause fits in one sentence.

A default expression is evaluated exactly once, when the def statement runs, and the resulting object lives on the function.

What is wrong is the intuition that it must be rebuilt on every call; the mutability of the list is not the cause. Mutability is merely the condition that makes that fact visible. Why the distinction matters becomes clear the moment the three symptoms are lined up side by side.

  • Symptom A. An empty list default accumulates values across calls → cause: evaluated once at definition time
  • Symptom B. The 「today」 placed in a default is still the same date days later → cause: evaluated once at definition time
  • Symptom C. A list in a class body is shared by every instance → cause: the class body runs once

Three things that look nothing alike turn out to be one face. B occurs with an immutable type, so 「because it is mutable」 simply cannot explain it. That is why this article puts the cause before the cure.

Execution environment. Every output below was actually produced on Windows 10 Pro (10.0.19045). The interpreter is Python 3.13.3 (tags/v3.13.3:6280bb5, 2025-04-08) [MSC v.1943 64 bit (AMD64)] and the platform identifier is win32. Every script was saved to a file before being run. A language in which indentation carries meaning gets silently mangled when it is passed through shell arguments or here-documents.

What this article does not cover. General Python syntax and introductory material live in the Python automation series. This article digs into exactly one point: when default arguments are evaluated. All sample code used in the runs is fictional.

1. Reproduction - three calls, three different answers

Built in the shortest possible form. The function takes a name, puts it in a basket and returns the basket. If you do not pass a basket, it starts with an empty one - or so it reads. It does not.

python 3.13.3 / win32

--- 1-1. three calls, one function ---
call 1 -> ['apple']
call 2 -> ['apple', 'banana']
call 3 -> ['apple', 'banana', 'cherry']

--- 1-2. two unrelated callers share one list ---
order_a = ['A-1001', 'B-2002']
order_b = ['A-1001', 'B-2002']
order_a is order_b : True

1-1 is the textbook reproduction. Three calls returned three different results, and each one retains what came before. The function looks like it performs 「put one thing in an empty basket」 each time, but what it actually does is 「keep putting things in the same basket」.

1-2 is the part that actually hurts in production. Two callers with no relationship to each other received the same object. That order_a is order_b is true means they are two names for one list. When two web requests pass through a function like this, one user's data ends up in another user's response. That is precisely the symptom from the opening.

  • The first call is always fine. A unit test that calls the function once will therefore never catch it
  • Reordering the tests changes the results. A good share of 「our tests depend on ordering」 reports take this shape
  • Restarting the process makes the symptom disappear. So it gets closed as 「it worked after a restart」 and comes back later
  • No exception is raised. There is no trace in the logs and the error-rate metric does not move

2. Where the default lives - pulling the object out directly

Let us fetch the object instead of guessing. A function object has a slot that holds its defaults.

--- 1-3. the default object itself ---
add_item.__defaults__      : (['apple', 'banana', 'cherry'],)
type of default[0]         : list
len of default[0]          : 3

--- 1-4. identity across calls ---
id(default) before call    : 1997832273600
id(returned) call 1        : 1997832273600  same: True
id(returned) call 2        : 1997832273600  same: True
id(default) after 2 calls  : 1997832273600
r1 is r2                   : True

--- 1-5. mutating through the returned reference ---
probe.__defaults__         : (['touched from outside'],)
a caller that never passed anything now sees : ['touched from outside']

1-3 is decisive. After three calls, looking inside the function's defaults reveals three items sitting there. The slot written as 「an empty list」 now holds data. The function really was editing its own default.

1-4 nails down why. The address of the default before any call and the address of the object returned by the call are identical. The second call is the same. Nothing is being created; one and the same object keeps being handed out.

1-5 is the most unpleasant face of this structure. A caller modified the returned list from the outside, and the function's default changed. From then on every caller who omits the argument sees a value someone else planted. No amount of reading the function body reveals this path.

Diagnostic tip. When you meet state contamination with no obvious source, the first thing to do is print the defaults of the suspect function. If there is data in a slot that should be empty, the diagnosis is finished. Do this before hunting for globals or suspecting caches. The check is one line and it does not require stopping the process.

3. When is it computed - when the def statement runs, exactly once

Now the cause gets observed directly. Put a call with a visible side effect in the default slot and you can count with your eyes how many times it runs.

--- 2-1. the default expression runs at def time, not call time ---
about to execute the def statement
    [side effect] make_default() ran
def statement finished
now calling f() three times:
make_default ran exactly once, before any call

Look carefully at the order. The call that builds the default ran inside the def statement, before the function had been called even once. The function was then called three times and that call never happened again.

One common misconception clears up here. def is not 「a marker that declares a function」; it is a statement that executes. When Python reaches that line it evaluates the default expressions from left to right, builds a function object holding those results and binds it to the name. Computing the defaults is the work of the def statement itself, not of the function body.

--- 2-2. defaults are attached to the function object ---
g.__defaults__        : (1, [])
g.__kwdefaults__      : {'d': 2, 'e': {}}
g.__code__.co_varnames: ('a', 'b', 'c', 'd', 'e')

--- 2-3. the default is writable state ---
before : (1, [])
after  : (99, ['patched'])
g('x') : ('x', 99, ['patched'], 2, {})

2-2 shows the storage layout. Defaults for positional parameters and defaults for keyword-only parameters go into different places. The former is a tuple, the latter a dictionary. When you write your own audit script you have to look at both or you will miss cases.

2-3 shows that this is writable state, not read-only metadata. Replacing the defaults wholesale from outside changed the behaviour of subsequent calls. A function object is a thing that carries code and data together, and the defaults belong on the data side.

  • Defaults are evaluated in the defining scope. Changing what that name refers to later does not follow through to an already computed default
  • Default expressions are evaluated from left to right. A later default expression cannot refer to an earlier parameter's default
  • A decorator does not help; by the time it runs the computation is finished. A decorator receives an already built function object
  • This computation happens the moment the module is imported. In other words the age of a default is the age of the process

4. Time freezes - today's date placed in a default

This is where the article earns its keep. Knowing the principle above, you can predict a second symptom that has nothing to do with mutable types. A call that computes 「now」 was placed in a default slot.

--- 3-1. today captured in a default never moves ---
bad  ('row0', '2026-07-31 05:25:19.168606')
good ('row0', '2026-07-31 05:25:19.569502')
bad  ('row1', '2026-07-31 05:25:19.168606')
good ('row1', '2026-07-31 05:25:19.969964')
bad  ('row2', '2026-07-31 05:25:19.168606')
good ('row2', '2026-07-31 05:25:20.370294')

--- 3-2. the frozen value, straight from __defaults__ ---
stamp_bad.__defaults__ : (datetime.datetime(2026, 7, 31, 5, 25, 19, 168606),)
same object 0.5s later : (datetime.datetime(2026, 7, 31, 5, 25, 19, 168606),)
id stays the same      : 2480663196656
datetime.now() right now: 2026-07-31 05:25:20.870691

There was a 0.4 second pause between each of the three calls. The correct version (good) differs down to the microsecond every time, while the version with the value in the default (bad) shows exactly the same instant three times. The system clock was never touched. The value simply does not refresh.

3-2 nails down why. The function's default was printed twice, half a second apart, and the same object was still there with the same value. Real time kept flowing in between, as the last line shows.

--- 3-3. a date default: the day the module was imported ---
captured end date      : 2026-07-31
report_range.__defaults__: (7, datetime.date(2026, 7, 31))
date.today() now       : 2026-07-31
note: date is IMMUTABLE, yet the value is still stale
      the bug here is not mutation, it is one-time evaluation

--- 3-4. the same shape with a counter ---
{'id': 1, 'payload': 'first'}
{'id': 1, 'payload': 'second'}
{'id': 1, 'payload': 'third'}
_seq module counter    : 1   (next_id ran exactly once)

The note in 3-3 is the core of this section. The date object is plainly immutable and the value is stale anyway. Nobody modified that object. The date from the moment of import is simply still lodged there. An explanation built on 「a problem caused by mutability」 cannot account for this output.

What makes this symptom frightening in production is the delay before it manifests. On deployment day it works perfectly. Days later a report arrives at dawn saying 「the reporting period looks wrong」, the on-call engineer restarts the server and everything is fine. Then days later it drifts again. The shorter the restart cycle, the later it is discovered.

3-4 recasts the same shape as a serial number. Three rows were created and the number is 1 on all of them. The number generator ran once at import and its result froze as the default. The module counter stuck at 1 is the proof.

  • If you see parentheses in a default slot, be suspicious. A call expression runs once right there and only the result remains
  • Timestamps, random numbers, unique identifiers, config file reads, connection objects - all fall into the same trap
  • 「use the current connection as the default」 is especially dangerous. It reuses one first connection for the whole life of the process
  • Because the symptom appears long after deployment rather than right after it, blame lands in entirely the wrong place

5. Which types are dangerous - and the limits of that distinction

Now let us split things by type. For twelve candidate default values, hashability and in-place modifiability were both actually attempted.

--- 4-1. which default types can be mutated in place ---
type        hash   in-place  verdict
--------------------------------------------------------------
list        no     OK        MUTABLE  -> state leaks between calls
dict        no     OK        MUTABLE  -> state leaks between calls
set         no     OK        MUTABLE  -> state leaks between calls
bytearray   no     OK        MUTABLE  -> state leaks between calls
int         yes    Attribute immutable-> no leak, but value frozen
str         yes    Attribute immutable-> no leak, but value frozen
tuple       yes    Attribute immutable-> no leak, but value frozen
frozenset   yes    Attribute immutable-> no leak, but value frozen
bytes       yes    Attribute immutable-> no leak, but value frozen
NoneType    yes    Attribute immutable-> no leak, but value frozen
date        yes    Attribute immutable-> no leak, but value frozen
Decimal     yes    Attribute immutable-> no leak, but value frozen

There is a regularity in the middle column. Everything that cannot be hashed can be modified in place, and everything that can be hashed cannot. The evidence that this is not a coincidence sits inside the standard library. Dataclasses forbid mutable defaults, and the documentation states that they use unhashability as an approximation of mutability for that check. In other words, 「if hash(default) raises, that default is dangerous」 is the same criterion the standard library applies.

The most important cell in this table is the 「user-defined class instance」 row. The hash test does not filter it out and the hazard is entirely present. So the hash rule is a convenient approximation, not a complete verdict. The next output shows exactly how far 「immutable means safe」 holds true.

--- 4-2. proof: the immutable default is REBOUND, not changed ---
bump  id-in=140731345413000 id-out=140731345413032  same=False value=1
bump  id-in=140731345413000 id-out=140731345413032  same=False value=1
bump  id-in=140731345413000 id-out=140731345413032  same=False value=1
bump.__defaults__ : (0,)  <- never moved

grow  id-in=2415089405120 id-out=2415089405120  same=True  value=[1]
grow  id-in=2415089405120 id-out=2415089405120  same=True  value=[1, 1]
grow  id-in=2415089405120 id-out=2415089405120  same=True  value=[1, 1, 1]
grow.__defaults__ : ([1, 1, 1],)  <- grew every call

The two functions are nearly identical in source. One adds 1 to an integer default, the other adds an element to a list default. Yet the results are opposites.

  • The integer side: the address changed across the operation. The sum became a new object bound to the local name, and the function's default is still 0. That is why three calls all return 1
  • The list side: the address is the same across the operation. Appending edited that object itself and the function's default grew along with it
  • Identically shaped syntax rebinds for one type and modifies in place for the other. That is the actual mechanism separating the two symptoms
  • In short, an immutable default guarantees only 「no state leaks」. It guarantees nothing at all about 「the value is current」
--- 4-3. tuple default holding a mutable member ---
call 1 -> (['x'], {})
call 2 -> (['x', 'x'], {})
call 3 -> (['x', 'x', 'x'], {})
the tuple itself never changed; its member did

--- 4-4. immutable default, still evaluated once ---
seeded.__defaults__ : (6,)
value is fixed at def time even though int is immutable
so 'immutable = safe' is only half true:
  mutable   -> shared state leaks between calls
  immutable -> value is frozen at import time

4-3 proves the table's 「leaks if a member is mutable」 cell. A tuple was used as the default and values accumulated anyway. The tuple itself never changed once; the list inside it grew. An immutable container protects only itself, never its contents.

4-4 connects sections 3 and 5. An integer default written as a computed expression had its value fixed at definition time. Integers are immutable so nothing leaks, but the property of being evaluated only once applies unchanged. The hazard differs; the cause is one.

6. The correct idiom - the None sentinel and the traps around it

The prescription is simple. Put only an immutable marker in the default slot and build the real object inside the function. The accumulation disappearing was confirmed by running it.

--- 5-1. the None sentinel idiom ---
call 1 -> ['apple']
call 2 -> ['banana']
call 3 -> ['cherry']
add_item.__defaults__ : (None,)

--- 5-2. caller-supplied container still works ---
passed in  -> ['seed', 'apple']
passed in  -> ['seed', 'apple', 'banana']
caller list: ['seed', 'apple', 'banana']  (caller owns it, as intended)

The same function from section 1 now returns a single-element list all three times. The function's only default is None, and list creation happens fresh inside the body on every call.

5-2 matters. This prescription does not break the case where the caller passes a container in. The supplied list is used as given and the result is visible on the caller's side too. That is not a bug; it is the natural behaviour when a caller hands over their own object.

--- 5-3. why 'or' is not the same as 'is None' ---
arg=[]      or-> ['a', 'DEFAULT']        is-None-> ['a']
arg=['x']   or-> ['a', 'x']              is-None-> ['a', 'x']
arg=None    or-> ['a', 'DEFAULT']        is-None-> ['a', 'DEFAULT']

--- 5-4. when None is a legitimate argument value ---
lookup('a')            : 1
lookup('b')            : None
lookup('z', None)      : None
lookup('z')            : KeyError 'z'

5-3 shows why the popular shorthand is not equivalent. The first line splits. The caller explicitly passed an empty list, and one form respected it while the other replaced it with the default. That is because empty containers, 0 and empty strings all evaluate as false.

This divergence raises no exception. It comes back days later as 「I sent an empty filter and got everything」. Always use an identity comparison for the sentinel check.

5-4 addresses the limit of the prescription itself. If None can be a legitimate argument value for a function, you cannot use it as the sentinel. In the output, 「no value, so raise」 and 「received None as the value」 were cleanly separated. Create a private marker object in the module and compare against that.

--- 5-5. copying a caller's list so you do not own their data ---
r1 tags : ['urgent', 'processed']
r2 tags : ['urgent', 'processed']
caller  : ['urgent']  (untouched)

--- 5-6. frozen empty containers as a read-only default ---
render('a')            : a({})
render('b', {'x': 1})  : b({'x': 1})
writing to the default : TypeError 'mappingproxy' object does not support item assignment

5-5 goes one step further. The list handed in by the caller is copied so that the function does not silently modify it. In the output, two calls did not interfere with each other and the caller's original is untouched. 「May a function change the caller's object」 is a separate design decision, and the answer is usually no.

5-6 is the safe form when you want 「an empty mapping」 as a default. Put a read-only view in the default slot and any accidental write raises immediately. Sharing something that cannot be changed is safe. This output confirms once more that sharing was never the problem; modifying the shared thing was.

7. The same cause with a different face - mutable attributes in a class body

The third symptom. As promised in the opening, the same cause shows up in an entirely different place. A list was placed in a class body.

--- 6-1. a mutable attribute in the class body ---
a.items : ['apple', 'banana']
b.items : ['apple', 'banana']
a.items is b.items      : True
Cart.items              : ['apple', 'banana']
id(Cart.items)          : 1409693232192
id(a.items)             : 1409693232192
'items' in a.__dict__   : False

--- 6-2. the fix: build it in __init__ ---
c.items : ['apple']
d.items : ['banana']
c.items is d.items      : False
'items' in c.__dict__   : True

Two separate instances were created and one item put into each, yet both hold two items. The last line gives away the identity. The name is not present on the instance at all. When an attribute is read and the instance does not have it, lookup climbs to the class, so every instance was looking at the single object attached to the class.

The structure is exactly that of a default argument. A class body also runs once when the class is defined, and the object created there lives on the class. The fix in 6-2 is the same as well. Build it when the instance is created and each one gets its own.

--- 6-3. rebinding vs mutating on a class attribute ---
p.hits : 2   q.hits : 1   Counter.hits : 0
p.log  : [1, 2, 1]
q.log  : [1, 2, 1]
the int looks per-instance because += REBINDS onto the instance
the list is shared because append MUTATES the class-level object

--- 6-4. dataclasses refuse the same shape ---
dataclass with list default : ValueError mutable default <class 'list'> for field items is not allowed: use default_factory
Good() g1.items : ['x']
Good() g2.items : []
g1.items is g2.items : False

--- 6-5. plain functions get no such protection ---
plain() -> ['x']
plain() -> ['x', 'x']
no error, no warning: dataclasses check, the interpreter does not

6-3 explains the most confusing phenomenon in this section. Within the same class, the integer attribute is counted per instance while the list attribute is shared. The code sits side by side and the syntax looks similar.

  • Augmented assignment on an integer computes a new value and rebinds it onto the instance. So each instance gets its own value and the class-level one stays 0
  • Appending to a list edits the very object attached to the class. Nothing is rebound, so everyone sees the same thing
  • The contrast between rebinding and in-place modification from 4-2 repeats here verbatim. Functions and classes are different syntax standing on the same rule
  • So 「class variables are shared」 is only half right. What is shared is the object, and rebinding severs the sharing

6-4 shows how the standard library handles this. A dataclass refuses a mutable default outright and raises. The error message even names the alternative. Specifying a factory function creates a fresh object per instance, and the two instances' lists came out as different objects.

6-5 is the chilliest part of this article. A plain function has no such protection whatsoever. Code of exactly the same shape passes without a word. What a dataclass blocks for you, a function does not. So you have to attach the detection yourself.

8. Detection - the interpreter says nothing

First, what the interpreter does for you was checked. The answer is 「nothing」. And this environment had no dedicated static analysis tool installed at all. So a scanner was built and run using the standard library alone.

$ python find_mutable_defaults.py sample_app.py
sample_app.py
  L6    MUTABLE  enqueue(queue=...)           list literal []
  L11   MUTABLE  index(table=...)             dict literal {}
  L16   MUTABLE  dedupe(seen=...)             factory call set()
  L21   MUTABLE  buckets(store=...)           factory call defaultdict()
  L26   CALL     stamp(at=...)                time-like call now() frozen at import
  L30   CALL     window(size=...)             computed expression evaluated once at def time
  L45   CLASSATTR Worker.seen                  list literal [] shared by every instance
--------------------------------------------------------------------
findings: 7
exit=1

It walks the syntax tree and looks at the node kind sitting in each default slot. Seven findings, and the exit code is 1 so it drops straight into CI. The classification is what deserves attention.

  • MUTABLE - list, dict and set literals, comprehensions, and known factory calls. This is the leaking side
  • CALL - every call expression and computed expression in a default slot. This is the freezing side, and as section 4 showed, immutable types land here too
  • CLASSATTR - mutable attributes in a class body. Same cause, so the same tool catches it
  • The safely written functions and the forms that build inside __init__ produced zero false positives

For a process that is already running, another method is more conclusive: reading the defaults off the function objects while they run.

--- 7-1. scanning a live module for mutable defaults ---
function               parameter    type       current value

dedupe                 seen         set        set()
buckets                store        defaultdict defaultdict(<class 'list'>, {})
Worker.seen            <class attr> list       []

--- 7-2. the same scan AFTER the code has run ---
function               parameter    type       current value
------------------------------------------------------------------------
enqueue                queue        list       ['job-1', 'job-2']

dedupe                 seen         set        {'x'}

Worker.seen            <class attr> list       []
the defaults now carry leftover data from earlier calls

The trick is to compare the two tables. Right after import everything was empty. After a few calls the same scan shows data left by earlier calls sitting inside the defaults. This is the shortest way to see a state leak with your own eyes.

Attach this scan to a running service and you can measure 「how much is leaking right now」. Static analysis needs the source, but this method works just as well on libraries written by other people.

--- 7-3. what the interpreter itself will and will not tell you ---
warnings raised by compiling a leaky def : 0

--- 7-4. grep-level heuristic (works anywhere, noisy) ---
  L6    def enqueue(job, queue=[]):

misses multi-line signatures and factory calls -> use the AST scanner

7-3 is the conclusion of this section. Compiling an affected function yields zero warnings, and bytecode compilation passes with no diagnostic. There is no language-level safety net. That is why this defect has survived for decades.

7-4 is the last resort where no tooling is available. A regular expression did catch three of them. But it missed the factory calls and any signature split across lines. Use it in a hurry and move the standing check to the syntax tree.

9. Using it deliberately - a default as a cache

There is a usage that knows this behaviour and exploits it. It uses the very property that state survives between calls to cache computed results. It genuinely works.

--- 8-1. the deliberate version: a default used as a cache ---
fib(60)      : 1548008755920
elapsed      : 0.000050 s
cache size   : 61
cache leaks into introspection: fib.__defaults__[0][10] = 55

--- 8-2. a caller can overwrite the cache from outside ---
fib(10) normal            : 55
fib(10, {0: 0, 1: 100})   : 5500
fib(10) again             : 55
the parameter is part of the public signature; nothing hides it

8-1 shows the technique really is fast. The recursive computation finished essentially instantly. But the cache is exposed right there in the function's default slot. On the last line a value from the internal cache was read out from the outside.

8-2 is the first reason not to recommend this. The cache is part of the public signature, so a caller can pass something else. Passing a bogus seed produced a completely different result. Nothing is hidden; it is merely a parameter you assumed nobody would use.

--- 8-3b. read-modify-write on a shared default, 8 threads ---
switch interval default : 0.005
switch interval set to  : 1e-06
expected increments : 160000
observed increments : 99462
lost updates        : 60538
keys retained       : 8

The second reason is concurrency. Eight threads were made to repeat read-modify-write against the same default dictionary. 160,000 increments went in, roughly 99,000 survived and 60,000 vanished.

There is one more important observation here. With the default settings, zero updates were lost. Only after the thread switch interval was lowered far below its default did the loss appear. That is what makes this class of bug frightening. It never reproduces on the test machine and shows up for the first time on a loaded production box. The conclusion 「no problem in our environment」 was really 「we have not seen it yet」.

--- 8-4. the supported alternative ---
fib2(60)     : 1548008755920
elapsed      : 0.000080 s
cache_info   : CacheInfo(hits=58, misses=61, maxsize=128, currsize=61)
signature    : None (no hidden parameter)
after clear  : CacheInfo(hits=0, misses=0, maxsize=128, currsize=0)

--- 8-5. closure: state without touching the signature ---
c1('a') -> 1  c1('a') -> 2
c2('a') -> 1
two independent instances; callers cannot reach the state

8-4 is the alternative. Use the standard library's caching decorator and the speed is effectively the same while everything that was missing gets filled in.

  • The signature is clean. The wrapped original function has no defaults at all. The cache does not leak out as a parameter
  • There is a bound. A default-argument cache is never emptied and grows without limit; this one takes a maximum size
  • It is observable. Hits, misses and current size can be read directly. Cache efficiency becomes a metric
  • It can be emptied. There is an invalidation hook. The 「never cleared」 problem seen in 8-3 is solved here

8-5 is the form to use when the state should be hidden entirely. Keep the state inside a function that builds functions and callers cannot touch it and every instance is independent. Two were created and counted separately, and they did not interfere. If the reason for using a default argument as a cache was 「I want to put state somewhere」, that somewhere is a closure, not the signature.

11. Checklist

Arranged so it can be used directly in code review.

  • No signature contains =[], ={} or =set()
  • No factory calls such as =defaultdict(...), =Counter(), =deque()
  • No call expression in a default slot - timestamps, random numbers, unique ids, config reads, connections
  • No computed expression in a default slot - it freezes at import
  • If a tuple default is used, it was checked for mutable members inside
  • The sentinel check uses is None rather than or
  • Parameters where None may be a valid value use a private marker object
  • The function does not silently modify a container the caller passed in (copy if needed)
  • No list, dict or set attribute sits in a class body
  • Dataclass fields are declared with a factory function
  • When caching is needed, use the standard caching decorator or a closure, never a default argument
  • A syntax tree scanner is wired into CI so new instances cannot land
  • Long-running processes are audited with a runtime default scan for residual state
  • Concurrency checks are also run with a lowered thread switch interval

11.1 What not to do

  • 「only mutable types need care」 - immutable defaults freeze at definition time. Section 3 is the counterexample
  • 「the tests passed, so it is fine」 - the first call is always fine. It shows from the second one
  • 「the interpreter protects against threading issues」 - it hides or exposes them depending on the switch interval
  • patching the default from outside as a fix - 2-3 showed it is possible, but that is treating the symptom
  • blaming the environment for state contamination you cannot reproduce - print the defaults first
  • remembering this only as 「a famous gotcha」 - without the cause, the symptoms in sections 3 and 7 stay separate problems forever

# Python Default Arguments — Definition-Time Evaluation Checklist

> Source: braindetox.kr — I put an empty list in a default argument and every call piled onto it
> Evidence: verified on Windows 10 Pro (10.0.19045) / Python 3.13.3 (MSC v.1943, 64-bit)
> Paste this file into an AI tool and say: check our codebase against these rules.

## 0. The one sentence everything follows from

**A default expression is evaluated exactly once, when the def statement runs, and the resulting object lives on the function.**

It is not recomputed per call. That single fact is the shared cause of all three symptoms below.

| Symptom | Apparent cause | Actual cause |
|---|---|---|
| Empty-list default accumulates | the list is mutable | evaluated once at def time |
| Today in a default never updates | a date caching bug | evaluated once at def time |
| Class attribute shared by instances | it is a class variable | class body runs once |

## 1. Reproduce it in three lines

```python
def add_item(name, basket=[]):
    basket.append(name)
    return basket

print(add_item("apple"))    # ['apple']
print(add_item("banana"))   # ['apple', 'banana']
print(add_item("cherry"))   # ['apple', 'banana', 'cherry']

print(add_item.__defaults__)
# (['apple', 'banana', 'cherry'],)
```

The default lives in the `function.__defaults__` tuple. Its `id()` is identical before and after every call.
Keyword-only defaults live in `function.__kwdefaults__`.

## 2. Which default types are dangerous (sorted by execution)

| Default type | Hashable | In-place change | Verdict |
|---|---|---|---|
| `list` | no | yes | **state leaks between calls** |
| `dict` | no | yes | **state leaks between calls** |
| `set` | no | yes | **state leaks between calls** |
| `bytearray` | no | yes | **state leaks between calls** |
| `defaultdict` / `Counter` / `deque` | no | yes | **state leaks between calls** |
| `int` / `float` | yes | no | no leak |
| `str` / `bytes` | yes | no | no leak |
| `tuple` / `frozenset` | yes | no | no leak (unless a member is mutable) |
| `None` | yes | no | no leak — **the recommended default** |
| `date` / `datetime` / `Decimal` | yes | no | no leak, but **the value freezes** |

**Decision rule**: if `hash(default)` raises `TypeError`, that default is dangerous.
The standard library dataclass machinery makes the same call — it uses unhashability to approximate mutability.

**Immutable does not mean safe.** An immutable default simply cannot leak state; it still
**freezes at definition time.** That looks like this:

```python
from datetime import datetime

def stamp(label, when=datetime.now()):   # bad: import time is baked in forever
    return label, when

def stamp(label, when=None):             # good: read fresh on every call
    if when is None:
        when = datetime.now()
    return label, when
```

**A call expression in a default slot is suspicious regardless of its return type.**

## 3. The correct idiom

```python
# The standard form — a None sentinel
def add_item(name, basket=None):
    if basket is None:
        basket = []
    basket.append(name)
    return basket

# Copy if you do not want to own the caller's data
def tag_all(rows, tags=None):
    tags = list(tags) if tags is not None else []
    tags.append("processed")
    return {"rows": rows, "tags": tags}

# When None is itself a legitimate argument, use a private sentinel
_MISSING = object()

def lookup(key, fallback=_MISSING):
    table = {"a": 1, "b": None}
    if key in table:
        return table[key]
    if fallback is _MISSING:
        raise KeyError(key)
    return fallback

# A read-only mapping as a default
from types import MappingProxyType
_EMPTY = MappingProxyType({})

def render(name, opts=_EMPTY):
    return name, dict(opts)
```

### Why `or` is not a substitute

```python
extra = extra or ["DEFAULT"]     # bad: replaces an empty list with the default
if extra is None:                # good: filters only None
    extra = ["DEFAULT"]
```

An empty list, an empty dict, `0` and an empty string are all falsy.
A caller who deliberately passed emptiness silently gets the default back.

### Classes and dataclasses

```python
class Cart:
    items = []                # bad: every instance shares one object

class Cart:
    def __init__(self, items=None):
        self.items = [] if items is None else list(items)   # good

from dataclasses import dataclass, field

@dataclass
class Good:
    items: list = field(default_factory=list)   # good
```

A dataclass rejects a mutable default with `ValueError`. **A plain function warns about nothing.**

## 4. Detection

If no dedicated linter is installed, walk the tree yourself with the standard-library `ast` module.

```python
# find_mutable_defaults.py — standard library only
import ast, os, sys

FACTORIES = {"list", "dict", "set", "bytearray", "defaultdict",
             "OrderedDict", "Counter", "deque"}

def describe(node):
    if isinstance(node, (ast.List, ast.Dict, ast.Set)):
        return "MUTABLE", "mutable literal"
    if isinstance(node, (ast.ListComp, ast.DictComp, ast.SetComp)):
        return "MUTABLE", "comprehension"
    if isinstance(node, ast.Call):
        f = node.func
        name = f.id if isinstance(f, ast.Name) else getattr(f, "attr", "")
        if name in FACTORIES:
            return "MUTABLE", "factory call"
        return "CALL", "call evaluated once at def time"
    if isinstance(node, ast.BinOp):
        return "CALL", "expression evaluated once at def time"
    return None, None

def scan(path):
    tree = ast.parse(open(path, encoding="utf-8").read(), filename=path)
    for node in ast.walk(tree):
        if isinstance(node, ast.ClassDef):
            for stmt in node.body:
                value = getattr(stmt, "value", None)
                if value is not None and describe(value)[0] == "MUTABLE":
                    print(path, stmt.lineno, "CLASSATTR", node.name)
        if not isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef, ast.Lambda)):
            continue
        a = node.args
        pos = a.posonlyargs + a.args
        pairs = list(zip(pos[len(pos) - len(a.defaults):], a.defaults)) if a.defaults else []
        pairs += [(k, d) for k, d in zip(a.kwonlyargs, a.kw_defaults) if d is not None]
        for arg, default in pairs:
            kind, why = describe(default)
            if kind:
                print(path, default.lineno, kind,
                      getattr(node, "name", "lambda"), arg.arg, why)

for target in sys.argv[1:] or ["."]:
    if os.path.isdir(target):
        for root, _d, files in os.walk(target):
            for f in files:
                if f.endswith(".py"):
                    scan(os.path.join(root, f))
    else:
        scan(target)
```

For a process that is already running, a runtime scan is more conclusive.

```python
import inspect

MUTABLE = (list, dict, set, bytearray)

def scan_live(module):
    for name, obj in vars(module).items():
        if not inspect.isfunction(obj):
            continue
        for pname, p in inspect.signature(obj).parameters.items():
            if p.default is not inspect.Parameter.empty and isinstance(p.default, MUTABLE):
                print(name, pname, type(p.default).__name__, repr(p.default)[:40])
```

**Run this scan against a live service and you will see leftover data from earlier calls
sitting inside the defaults.** That is the leak, made visible.

### Detection methods compared

| Method | Multi-line signature | Factory call | Class attribute | Third-party code |
|---|---|---|---|---|
| regex grep | missed | missed | missed | yes |
| `ast` scanner | caught | caught | caught | yes, if source is present |
| runtime `__defaults__` scan | not applicable | caught | caught | **yes** |
| the interpreter itself | — | — | — | **no diagnostic at all** |

## 5. Using a default as a cache — why it is discouraged

```python
def fib(n, _memo={0: 0, 1: 1}):     # it works, but
    if n not in _memo:
        _memo[n] = fib(n - 1, _memo) + fib(n - 2, _memo)
    return _memo[n]
```

- The cache is **exposed in the public signature**. A caller can poison it with `fib(10, {0: 0, 1: 100})`
- **It is never emptied.** There is no bound and no invalidation hook
- **It is not thread-safe.** Split a read-modify-write and updates disappear
- Documentation tools and type checkers treat the slot as a real parameter

The alternative:

```python
from functools import lru_cache

@lru_cache(maxsize=128)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

fib.cache_info()    # hits, misses, current size
fib.cache_clear()   # empty it
```

If the state should stay hidden, use a closure. Callers cannot reach it and each instance is independent.

```python
def make_counter():
    tally = {}
    def bump(key):
        tally[key] = tally.get(key, 0) + 1
        return tally[key]
    return bump
```

## 6. Review checklist

- [ ] No signature contains `=[]`, `={}` or `=set()`
- [ ] No factory calls such as `=defaultdict(...)`, `=Counter()`, `=deque()`
- [ ] No **call expression** sits in a default slot (`datetime.now()`, `uuid4()`, `time()`)
- [ ] No **computed expression** sits in a default slot (it freezes at import)
- [ ] `is None` is used instead of `or` for the sentinel check
- [ ] Parameters where `None` is a valid value use a private sentinel object
- [ ] The function does not **silently mutate** a container the caller passed in (copy if needed)
- [ ] No list, dict or set attribute sits in a class body
- [ ] Dataclass fields use `field(default_factory=...)`
- [ ] Caching goes through `lru_cache` or a closure, never a default argument
- [ ] CI runs an `ast` scanner or a linter so new instances cannot land
- [ ] Long-running processes are audited with a runtime `__defaults__` scan

## 7. What not to do

- Assume only mutable types matter — immutable defaults **freeze at definition time** too
- Assume passing tests mean safety — the first call is always fine; **the second reveals it**
- Assume the GIL protects shared state — it **hides or exposes** the race depending on the switch interval
- Patch `function.__defaults__` in place to fix a symptom — that treats the symptom, not the cause
- Blame the environment for state contamination you cannot reproduce — print `__defaults__` first
