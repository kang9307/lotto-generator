Language Properties That Lower the Verification Cost of AI-Generated Code

The five traits that make Go look good right now, and what each of them charges in return

Aug 16, 2026 Dev & Infra

Introduction: where the review queue actually backs up

You hand an agent a ticket, step into a meeting, and come back to an 800-line change. The build is green. The tests pass. And yet something still has to happen before you press merge, and that something takes exactly as long as it did last year. This is the place teams actually get stuck.

Writing cost and checking cost did not fall at the same rate. That single asymmetry is the backdrop for every current language argument. On August 11, 2026, Cameron Balahan of the Go team and Richard Seroter of Google Cloud published a piece on the Google Developers Blog arguing that Go is an ideal language for AI-assisted software engineering, and within a day it was circulating in developer communities as another round of the familiar which-language debate.

The valuable part of that piece is not its conclusion. It is the question underneath: which properties of a language lower verification cost? That question is not about Go, and teams who will never write a line of Go can use the answer today. This article pulls out five such properties, shows how Go acquired them, states what it hands over in exchange, and looks at the languages that answered the same problem in the opposite direction.

One thing up front: this is not an argument that some language is better. Every property carries a price, and which price is bearable is decided by the constraints of the team paying it.

1. What verification cost is actually made of

A reviewer facing 800 lines is not doing one job. It splits into five.

  • Absorbing shape — the time your eyes take to adjust to indentation, line breaks, and brace placement
  • Comparing idiom — when a task has several accepted solutions, checking whether the one used here matches what this codebase already does
  • Confirming APIs exist — whether the called functions and packages are real, with that signature, in that version
  • Verifying meaning — whether it matches the requirement and whether boundary conditions were skipped
  • Tracing side effects — what this change leaves behind on other paths

Here is the split that matters. The first three can be delegated to the language and its tooling; the last two stay human whatever you choose. So the only place a language property can intervene is in the first three, and every minute pushed out of them is a minute of attention left for the last two. The goal is not a shorter review. The goal is where the remaining attention goes.

One line from the Google piece is worth keeping. It notes that when you keep asking a model to revise, a first pass may be 95% correct while successive passes compound the error rate. Which means the outcome is set by how fast you can turn a loop and how reliably the filter catches things. That is where loop speed and filter quality become language questions.

2. Five properties that lower verification cost

The ways a language can shrink those first three items come down to five. They are written so they hold with Go removed from the sentence.

PropertyItem it reducesHow to check itWhat it costs
Small syntactic surfaceAbsorbing shapeNumber of grammar rules a reviewer must holdLess expressiveness — you cannot narrow a domain in syntax
Idioms converge to oneComparing idiomWhether the docs give one standard solution per taskClever solutions are refused too — bodies grow longer
Formatter is mandatoryAbsorbing shapeWhether any diff line changed formatting onlyNo room for team preference
Broad standard libraryConfirming APIs existCount of newly added dependenciesWhen the standard ages, the language ages with it
Fast compilationLoop speed for all threeTime from edit to first reported errorSome optimization and analysis depth given up

The first three reduce what there is to read; the last two increase how fast a machine reads it for you. They are different in kind, so no single language needs all five.

The most underrated of the five is the third. Enforced formatting reads like an aesthetic concern, but its character changed once generation volume rose. A model emits the same code in a different shape every time. In a format-permissive language that variance lands in the diff, and lines whose meaning never changed still pass under a reviewer's eyes. When format is enforced, those lines never appear. This belongs to the same family as the question of why static typing came back into favour from the mid-2010s, which is laid out in The Rise of Static Typing.

3. How Go gets these properties

Go secures the five less through language design than through the tool bundle that ships with it. That is where it separates from most alternatives.

  • gofmt — formatting lives in the distribution. Style debates do not recur per organization, and formatting-only lines do not survive into a diff.
  • go vet — a standard tool catches suspicious constructs that still compile, such as format-string mismatches or copied locks.
  • govulncheck — known vulnerabilities in dependencies are checked with a standard tool. Its value rises with generation volume.
  • go fix and modernizers — machines move stale idioms forward. If a model learned old code and emits an old pattern, there is a path back.
  • Built-in fuzzing — part of go test since Go 1.18. Random-input testing without installing anything.
  • pprof, execution tracing, PGO — performance regressions get caught by profile rather than by feel.

Put together, this pipeline works with the standard distribution alone.

# erase formatting differences from the diff
gofmt -l ./...

# catch suspicious constructs that still compile
go vet ./...

# look at known vulnerabilities in dependencies
govulncheck ./...

# run tests together with race detection
go test -race ./...

The point is that all four run without a separate install. When there is no step for choosing tools, pinning versions, and agreeing on config files, a brand-new repository gets the same filter on day one. And when an agent iterates and corrects itself, that filter runs without a human in the loop.

Standard library breadth and the supply chain

This is the part of the Google argument that hits practice fastest. A model emits package names as of its training snapshot, which means it will confidently call packages that are no longer maintained, or that never existed. A broad standard library means fewer of those calls get made at all. With HTTP servers, JSON, crypto, and templating in the standard library, a model has less reason to reach outside, and fewer incoming dependencies means less surface to audit.

What the Go 1 compatibility promise actually covers

This is the property that pays off in long-lived code. The compatibility document states that programs written to the Go 1 specification are intended to continue to compile and run correctly, unchanged, over the lifetime of that specification. The scope is worth knowing precisely.

  • It guarantees the source level only. Binary compatibility of compiled packages across releases is not promised.
  • Security issues, code relying on behaviour the spec never defined, corrections to the specification itself, and bug fixes are all listed as exceptions.
  • Unkeyed struct literals, methods newly added to embedded types, dot imports, and use of unsafe are on the exception list too.

So the shape is not nothing ever breaks but the ways it may break are written down in advance and honoured outside them. With generated code accumulating, that difference matters. Staying off the exception list becomes a coding standard in itself.

How far the compile-speed claim holds

The Google piece says Go compilation is orders of magnitude faster than Java, C#, Rust, and comparable production languages. The direction matches what anyone who has used Go feels, but the piece attaches no hardware, no codebase size, and no toolchain version. A comparison without conditions cannot be used as a leaderboard. There is no substitute for measuring in your own repository, and even that number swings hard with cache state and module count.

4. The cost — a terse grammar bills you in body length

Properties have prices. Go pays four of them.

Verbose error handling

Go converged on one way to handle errors, so every call carries the same shape.

f, err := os.Open(path)
if err != nil {
    return nil, fmt.Errorf("open %s: %w", path, err)
}
defer f.Close()

data, err := io.ReadAll(f)
if err != nil {
    return nil, fmt.Errorf("read %s: %w", path, err)
}

On the generation side this is not a burden. Repetitive blocks are the shape a model produces most reliably, and no human pays the typing. The burden appears on the reading side. Once a large share of the diff looks identical, the one spot that quietly swallows an error is hard to see. Repetition becomes noise, and real signal hides in noise.

This price is not about to disappear. After the 2019 try proposal was declined and several later attempts, in June 2025 the Go team said it would stop pursuing syntactic language changes for error handling and closed the proposals concerned primarily with that syntax. The same post acknowledges that error handling is named the biggest specific challenge in using Go in surveys. It is a cost accepted with open eyes.

Constrained expressiveness

Go has no sum types and no exhaustive pattern matching. The consequence is that the compiler cannot refuse a state machine with a missing branch. States get expressed as string or integer constants with a default arm on the switch, and adding a new state still compiles cleanly. That check drops down to tests and to people.

Traces of the pre-generics era

Type parameters arrived in Go 1.18. Before that, container utilities were duplicated per type or taken as interface{} and asserted, and a large volume of that era's code sits in public repositories. That is why a model sometimes emits the older idiom. How often is not something any public measurement establishes. The response is not to estimate a frequency but to wire modernizers and static analysis into CI.

Concurrency — easy syntax is not the same as safe

This is the part to watch. A single go keyword starts a goroutine and channel syntax is terse, which also means a generator will scatter concurrent code freely. But data races are not caught by the compiler. The -race detector catches them, only if that path actually executes. Community discussion of the Google piece raised exactly this concern about AI-generated Go, and it matters because it is the area the five properties do not cover. Format can be uniform and idiom singular, and a race still will not show up in the shape of the code.

5. The other answer — pushing verification into the type system

Some languages answer the same bottleneck from the opposite side. If Go reduces what there is to read, these make the compiler refuse it so nobody has to read it. Neither is superior; they bill different parties.

  • Rust — ownership and borrow checking refuse a broad class of memory errors and data races at compile time. Sum types plus exhaustiveness checking in match mean that adding a state surfaces every unhandled site as a compile error. With more code going unread by humans, that is straightforwardly valuable. The price is build time, a learning curve, and managing unsafe boundaries. The decision axes for moving between the two are laid out in the Go to Rust migration guide.
  • TypeScript — discriminated unions close over states, and settings like strict and noUncheckedIndexedAccess tune how hard the checker pushes. Two costs: type-definition quality varies package by package, and any is always an open exit through which generated code can slip past checking.
  • Python — type hints do not affect execution, so unless a separate checker is wired into CI, verification lands entirely on tests and on runtime. In exchange the data and machine-learning ecosystem is wide enough that no other property substitutes for it.

Look first at which row your team's incident history clusters in, and the decision gets much faster. Picking a language that is good at a row where you never have incidents buys nothing.

6. Is the language AI writes well the same as the language humans read easily?

Mostly they overlap, but not entirely, and the judgment goes wrong exactly where they diverge.

  • Where they overlap — idiom convergence and enforced formatting help both sides. A model reproduces the single pattern it saw; a human has exactly one baseline to compare against.
  • First divergence — repetition. Humans read repetition as noise; a generator pays nothing for it. So the same code can be good from a generation standpoint and bad from a review standpoint.
  • Second divergence — compressed expression. A one-line functional pipeline is dense information to an expert, but when it is wrong it is wholly wrong and resists partial verification.
  • Third divergence — documentation convention. Humans fill gaps from context; tools invent whatever is not in the signature and the types.

Which is why the phrase AI-friendly bundles two separate claims. One is does the model generate accurately in this language; the other is can a human verify the result quickly. The first is a matter of training-data distribution and model behaviour, effectively unverifiable from outside; the second is checkable through tooling and language design. Use only the checkable half as evidence. The attempt to design a language purely for agents, and its limits, is covered separately in the agent-first programming language piece.

The rule for citing benchmarks follows from this. A number published without model version, hardware, task type, and grading criteria is not a leaderboard. Coding-task scores in particular reorder with task composition, so a citation missing its conditions does not even guarantee the direction.

8. What actually decides language choice

The forces that pick a language in the field sit upstream of verification cost. Reverse the order and you end up choosing a language with fine properties and then writing the missing libraries yourself.

  • Ecosystem — is there a mature library for this domain. Payment integration, document parsing, and machine-learning pipelines are often decided by this alone.
  • Hiring and handover — can you keep finding people to maintain it. If not, verification cost simply relocates to handover cost.
  • Runtime requirements — how much GC pause is tolerable, is there a memory ceiling, does cold start appear in your service targets.
  • Deployment shape — does it end as a single static binary, must a runtime ship with it, do image size and start time show up in the bill.
  • Regulation and procurement — in public sector and finance, permitted languages and tools are sometimes written into contracts. The option set narrows before any property argument begins.
  • Existing assets — which language holds your shared internal libraries, auth modules, and logging conventions.

The safer working order is this. Those constraints cut the field to two or three. Verification-cost properties rank what survives. Properties do not create candidates; they separate the ones left. Why the old advice to choose proven technology got stronger in the AI era is covered in Choose Boring Technology, revisited.

9. Where this decision reproduces on your team

More useful than a verdict is knowing where the same conclusion holds and where it does not.

  • Reproduces easily — internal platform APIs, gateways, batch pipelines, operational CLI tools. Low dependence on domain libraries, deployment that ends in one binary, and reviewers spread across teams so that uniform format and idiom pay well.
  • Reproduces poorly — data and machine-learning pipelines are decided by ecosystem. Front-end work already has a type checker holding that seat. Regulated legacy estates are constrained by talent pools and procurement specs first.
  • Hiring reality — the pool of engineers with production experience in a given language varies sharply by region and domain. Good properties with nobody to maintain them turn into debt.
  • Team structure — the fewer the reviewers, the more uniform format and idiom are worth. If review is already automated, that gain has been collected already.

If you do decide to move, start with the single path whose review queue is longest rather than converting wholesale. A failure stays contained to one service, and whether review time actually dropped on that path becomes the basis for the next decision. The adjacent question of writing code as though a human will maintain it is taken up in Write code like a human will maintain it.

10. What could not be confirmed

Collected in one place: the gaps that are not currently fillable. None of the items below were used as evidence in this article.

  • Public figures for per-language AI generation accuracy — no comparison stating model, task set, and grading criteria was confirmed.
  • Training-data language distribution — not published by any major model provider. The explanation that a language benefits from more training data cannot be verified.
  • Internal observations that agents write Go better — confirmed only as quoted in community discussion. No primary source stating method and sample was confirmed.
  • The original English discussion thread — access was blocked repeatedly, so the source thread could not be opened. Counterarguments here reflect only what was confirmed in the Korean community summary.
  • Conditions behind the compile-speed comparison — hardware, codebase size, and toolchain version are not stated in the original.
  • Frequency of concurrency defects in generated Go — the concern is documented; a measurement of frequency was not confirmed.

Conclusion: you chose a budget placement, not a language

What rose in value once generation got fast is the time spent checking. A language is the device that decides who gets billed for that time. You can hand format and idiom to tooling, hand a class of defects to a type checker, or leave it all with people. All three are answers; they just charge differently.

Three things are actionable tomorrow.

  1. Split review time into the five parts and measure it. If the leak is in absorbing shape, comparing idiom, or confirming APIs, that is usually a signal that tooling is off, not that the language is wrong.
  2. Turn on every property available in the language you already use. Enforce the formatter in CI, promote static analysis and vulnerability scanning to blocking checks, and apply strict type settings to new code. Replacement comes after that.
  3. Do not treat conditionless comparisons as evidence. A number without version, hardware, task, and grading criteria does not even guarantee direction.

Compressed to one line: Go is not favoured because it is correct, but because its properties pay off when verification is the bottleneck. On a team where it is not, those same properties leave only lost expressiveness and longer bodies. Choosing a language is, and remains, the act of writing down your constraints first.
