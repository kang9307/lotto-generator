What Makes Software Survive Twenty Years - Telling Finished From Abandoned

Measuring size, dependencies and change reasons to separate finished code from dead code

Aug 2, 2026 Dev & Infra

Introduction: three years without a commit tells you nothing

You open a library you are about to add to your dependency list. Enough stars, real documentation, and it does exactly the one thing you need. Then you notice the commit graph has been flat for three years. Your hand stops. Putting unmaintained code into production feels wrong.

So most people go looking for a busier alternative. That decision is not always wrong, but the reasoning is. Commit frequency is not a health indicator. It is closer to a measure of how much work is left. A project can be busy because much remains undone, or quiet because nothing does. The graph cannot tell you which.

This article tries to turn that distinction into something you can measure. It treats the conditions for long-lived software as numbers rather than sentiment, and every number below came from a script that was actually run. The conclusion up front: long-lived code is not about passion or popularity. It is small, lightly dependent, narrow in scope, and documented. All four are the result of deciding not to add something. That is not technique. It is accumulated refusal.

Environment. Every measurement below was run on Windows 10 Pro (10.0.19045). The shell was GNU bash 5.2.37 (MSYS2/MinGW64), and the tools were Python 3.13.3, Node.js v22.16.0 and npm 11.5.2. The targets were the Python 3.13 standard library installed in that environment and dependency trees resolved but never installed from the public registry. All scripts were saved to files and executed, and the commands are reproduced verbatim.

What this article does not cover. Working out when the cost of cleanup work is paid back belongs to when refactoring pays for itself. Here the subject is the verdict, not the accounting. Habits for writing maintainable code in the first place live in writing maintainable code. This article deals only with how to judge and dispose of code that already exists.

1. Dead and finished draw the same graph

A stalled commit history presents two very different facts in the same shape. One is that work remains and nobody is doing it. The other is that the work is actually done. The first is dangerous and the second is reassuring, yet the front page of a repository shows them identically.

To separate them, look at the nature of what is left open rather than at the graph. The signals below are usable in practice.

Where to lookLeans toward neglectedLeans toward finished
Character of open issuesReproducible bug reports pile up unansweredMostly feature requests, closed as out of scope
Build statusReports of breakage on current toolchains sit untouchedNew runtimes appear and only adjustment commits land
Documentation ageDocs describe a version several releases behindDocs and code change in the same commit
Reason for recent changesNo changes at all, or no discernible reasonMostly defect fixes and adaptation to the outside
Security responseVulnerability reports go months without replyFeatures stay flat but patches still ship
ReleasesThe last release carries a known critical defectReleases are rare but their contents are explicit

The point of that table is to stop reading few changes as a problem. The problem is not that changes are rare. The problem is that changes which should exist are missing. And the changes that should exist are mostly of two kinds: fixing defects found inside, and adapting to a world that moved outside. If both are appearing, the project is alive. Features not growing is a separate fact, and sometimes an intended one.

One practical addition: do not finish the verdict inside a single repository. Whether distributions still ship the software, and whether other projects still link against it, are far stronger signals. When upstream is quiet but downstream is busy, that code has already become infrastructure.

2. Why small codebases survive - readable means fixable

Small code lasts not because it is elegant but because the handover cost fits inside one person. There is a size at which the sentence you now own this module becomes an executable instruction. To avoid guessing where that size is, measure it.

The method is simple: count real code lines with comments and blanks removed. Here is the result against the Python standard library.

$ python measure_size.py C:/Python313/Lib/json C:/Python313/Lib/email \
                        C:/Python313/Lib/asyncio C:/Python313/Lib/csv.py C:/Python313/Lib/textwrap.py

target                       files      code   comment     blank      bytes

email                           29      7764      1035      1592     396685
asyncio                         33     11165      1008      2568     533673
csv.py                           1       392        40        81      19691
textwrap.py                      1       355        68        74      20436

What matters here is not the ranking but the order of magnitude. 355 lines and 11,165 lines are not the same category of object. One person can read the former in a day and accept responsibility for it. The latter, they cannot. Maintainability behaves less like a continuous scale and more like a property with a threshold.

That said, small does not simply mean good. A small module carries less functionality, and users must fill the gaps themselves. The larger, more featureful option absorbed that cost so its users would not have to. Which is correct depends on how many people use the code and for how long. The more users and the longer the life, the larger the total cost that was pushed onto the user side.

2.1 What to read alongside the size

  • Comment ratio. In the output above, email had 1,035 comment lines against 7,764 code lines, roughly 13 percent. A large file with almost no comments costs more to read than its line count suggests.
  • File count. The same line total spread across 33 files navigates very differently from one file.
  • The single largest file. The bottleneck is the maximum, not the average. If one file is 3,000 lines, that file effectively is the module.
  • Whether tests are counted. Including tests inflates the size, but from a handover perspective tests are also an asset that must be read. Record both numbers separately.
  • Excluding generated code. Parser generator output and similar files are never read by humans and must be removed, or the metric becomes meaningless.

Some long-lived projects publish their comment ratio as a metric outright. The SQLite documentation states that its source is over 35 percent comment and offers that as one of the grounds for long term support. A high comment ratio does not by itself mean good code, but it does signal code written on the assumption that someone else will inherit it.

3. Dependencies set the lifespan - others change what you did not touch

A large share of breakage originates outside your own work. Change nothing and something still breaks, because someone else changed theirs. Dependency count is therefore not a measure of convenience. It measures the surface you exposed to the outside world.

The trouble is that most people count that number as the number they declared. The real surface is far wider. Here it is, measured by resolving the tree without installing anything.

$ cat package.json
{"name":"probe","version":"1.0.0","dependencies":{"express":"4.21.2"}}

$ npm install --package-lock-only --no-audit --no-fund
up to date in 3s

$ node -e "const l=require('./package-lock.json');
           console.log(Object.keys(l.packages).filter(Boolean).length)"
69

One line of declared dependency produced 69 entries in the lock file. A few more were measured the same way. The tree column includes the package itself.

PackageDirectResolved treeHow to read it
express@4.21.23169One declared line drags in 68 other repositories
axios@1.7.9323Declared count and real surface differ by over sevenfold
chalk@5.4.101The only thing outside change can touch is itself
lodash@4.17.2101Same shape. Large in size, yet narrow in surface
typescript@5.7.301Even a big tool can hold this at zero by choice

Do not read a winner out of that table. A large tree means more reuse of other people, which delivers more work faster. There are clearly business situations where that speed is the right answer. A tree of one means the necessary parts were built in house, which also means owning that implementation and its bugs forever. These are not two ends of one axis. They are two different costs, deliberately chosen.

On the single axis of lifespan, though, the direction is unambiguous. Every entry in the tree has its own release cadence and its own maintainers. If any one of them stops being maintained or breaks compatibility, your code has to respond. Your stability is inversely proportional to the number of things you do not control.

3.1 Measuring where there are no lock files

Where imports tangle inside a standard library, as in Python, you parse the sources and compute a closure. The key detail is capping the hop count.

def closure_by_depth(root, max_depth=8):
    seen = {root}
    frontier = {root}
    levels = [set(seen)]
    for _ in range(max_depth):
        nxt = set()
        for name in frontier:
            for f in package_files(name):
                for dep in imports_of(f, name):
                    if dep not in seen and package_files(dep):
                        nxt.add(dep)
        if not nxt:
            break
        seen |= nxt
        frontier = nxt
        levels.append(set(seen))
    return levels

The reason for the cap is visible in the results. Below are values measured on the Python 3.13.3 standard library. mod is the module count excluding the root, and loc is the sum of their code lines.

The most practical finding here is this: the full closure saturates and discriminates nothing. Followed to the end, a 355 line module and an 11,165 line module both converge on 124 and 180. Cut at three hops, though, and they spread from 16 to 174, more than a tenfold gap. In other words a dependency metric is not about counting everything. It is about deciding where to stop.

This measurement has a clear limitation. Static parsing counts lazy imports inside functions and exception handlers too, so it reports more than runtime actually needs. Treat the value as an upper bound. It is still perfectly adequate for comparing things with the same ruler.

4. A narrow scope means throwing features away

Long-lived software tends to share one trait: a long list of things it does not do. That sentence is often misread as praise for minimalism. What actually happens is the labour of turning feature requests down.

A concrete example is OpenBSD's httpd(8). Its manual page describes it only as an HTTP server with FastCGI and TLS support. The release notes show the server first arriving in OpenBSD 5.6, in the same release where Apache was removed from the base system. That release is dated 1 November 2014.

Concluding that one side is superior would be wrong here. The Apache HTTP Server 2.4 module index lists somewhere around 140 modules. Authentication and authorisation, proxying and load balancing, caching, compression, URL rewriting, logging and TLS all arrive as separate modules. That scale is not sprawl. It is a design goal. Operators attach only what they need, and that extensibility is precisely why countless environments still run it. Things a deliberately narrow server cannot do at all are inside that list.

So the accurate formulation is this. Narrowing scope buys lifespan and spends applicability. Both are costs. The question to ask is not whether there are many features but whether anyone in your organisation is blocked by the missing ones.

  • Deciding not to add a feature removes its bugs, its documentation, its tests and its security response in one stroke. What is saved is not lines of code but permanent maintenance cost.
  • In exchange the user has to fill the gap. That cost does not vanish; it relocates.
  • If the scope is not written down, there is no basis on which to refuse. A narrow scope cannot survive without documentation.
  • Leaving one extension point open is different from including every feature. Opening exactly one boundary is the usual compromise.
  • Refusal costs popularity. Longevity and adoption often pull against each other, and that has to be acknowledged when choosing.

5. Why documentation has to live with the code

Undocumented code cannot be handed over. More precisely it can be handed over, but the recipient cannot recover the original intent. Documentation is therefore not an accessory to the code. It is the handover capability itself.

There is a practice worth borrowing here. The OpenBSD FAQ describes manual pages as the authoritative source of information for the system, and says considerable effort goes into keeping them up to date and accurate. The more important sentence follows: developers making a change to the system are expected to update the manual pages along with the code change.

The substance of that rule is not an appeal to write good documentation. It puts documentation inside the definition of done for a code change. Structurally, documentation then falls behind far less often. That is exactly why the earlier table lists docs and code changing in the same commit as a sign of finished rather than abandoned.

5.1 The minimum machinery for first-class documentation

  • Keep documentation in the same repository as the code. Move it to a wiki and the ownership splits; once split, it lags.
  • Put it in the review rules that changes to public interfaces must carry documentation changes to pass.
  • Write the scope declaration into the documentation. You can only close a request if what is out of scope is written down.
  • Keep examples in an executable form. Examples that are never run all become lies eventually.
  • Leave a human-readable change history per version. A commit log is not a substitute.
  • Use comments to record why. What the code does is already stated by the code.

Volume of documentation is not quality. Still, it is worth noticing that projects which manage comment ratio as a published metric, as SQLite does, or which nail manual page updates to developer obligation, tend to be the ones that last. Both are mechanisms built on the assumption that people will be replaced.

6. Compatibility promises - deciding what you will not change

Users leave less often because features are missing than because upgrading hurts. Put the other way, committing to what you will not change is the strongest device for keeping them.

SQLite pushes that promise to an extreme. Its documentation states that the developers intend to support it through the year 2050, and promises to keep the C language API and the on-disk file format fully backwards compatible. It goes as far as saying that an application written today should link against and work with versions released decades in the future. The same document notes that database files are bit-for-bit identical across 32-bit and 64-bit, big-endian and little-endian platforms.

That promise produces effects in two directions.

  • For users: upgrading stops being an event. When bumping a version does not force code changes, staying becomes the default.
  • For developers: design freedom shrinks permanently. An interface once published must be carried forward including its mistakes.

So compatibility is not free, and the people who break it often have reasons too. Bad designs can be discarded quickly, and convergence toward a better shape is faster as a result. In fast-moving areas with a thin user base that can be the rational choice. The real failure mode is breaking things often without ever having made a promise. Then users are surprised every time.

Rendered into practice, it comes down to this.

  • Write down what counts as the public interface. Anything not written down implicitly reads as changeable.
  • Ship breaking changes with both a notice period and a migration path. With only one of the two, users cannot follow.
  • File formats and storage schemas outlive APIs by a wide margin. Break those and the data becomes a hostage.
  • Treat default changes with the same weight as API changes. If behaviour shifts while the signature holds, it still broke.
  • If compatibility cannot be kept, change the name. Shipping a different thing under the same name is the worst option.

7. Handover - what has to be true when maintainers change

In software that lives twenty years, the same person rarely stays for twenty years. The real precondition for longevity is therefore not enthusiasm but replaceability. It is the problem usually described as lowering the bus factor.

The two daemons mentioned earlier illustrate this nicely. The HISTORY section of the relayd(8) manual page records that the program first appeared under the name hoststated in OpenBSD 4.1 and was renamed in 4.3. Its AUTHORS section lists two people. And the httpd(8) manual page states that the server derives from relayd. Names change, authorship is plural, and one program's code splits off into another. None of that movement is possible unless documentation and boundaries exist first.

The devices that lower the bus factor are concrete files and rules, not abstractions.

  • The build must finish in one command. It only builds on the owner's laptop is the most common cause of death.
  • Encode the runtime environment. Required runtime versions and external tools belong in configuration files, not prose.
  • Tests must report failure. If the person taking over has no way to learn that they broke something, they will not touch it.
  • The deployment procedure must be written down. Deployment is forgotten far more often than code.
  • Record decisions. Without a record of why this structure was chosen, successors either re-derive everything or replace it for no reason.
  • Authority belongs to the repository, not to a contact. Knowledge maintained by go ask that person leaves when the person does.
  • The name must be transferable. If naming, ownership or hosting is tied to one individual, handover is simply impossible.

The last two are the ones most often missed. Technically flawless code still has a lifespan equal to the lifespan of an account when permissions are bound to an individual. Domains, package registry ownership and signing keys all fall in this category.

8. When a rewrite is the right answer

None of the above should be read as preserve the old thing. Age by itself is neither a virtue nor a defect. The conditions under which a rewrite becomes justified are separate.

The earlier example applies here too. OpenBSD 5.6 removed an existing server from the base system and added a newly written one. That is the opposite of preservation. The claim of this article is not conservation. It is judgement.

SituationVerdictReasoning
Requirement premises changed beyond what the structure can expressRewriteA skeleton mismatch, not a missing feature
Runtime, language or core library reaches end of supportRewrite or portSound code with nowhere left to run
Nobody can read it and docs cannot restore itRewriteComprehension now costs more than rewriting
Security defects recur from the structure itselfRewriteIndividual patches are not converging
Recent changes are mostly fixes and outside adaptationKeepThat is the signature of code that works
The complaint concerns style or fashionKeepPaying to convert working code into taste
Slow, but the bottleneck is identifiedPartial replacementA full rewrite is overkill

If a rewrite is chosen, one rule remains. Recover why the existing code looks the way it does first. That odd-looking branch is frequently the scar of a real production incident. Rewrite without knowing the reason and you will have the same incident again.

When the cost is recovered, and how to present cleanup work as an investment, is outside this article's scope. That part is handled separately in when refactoring pays for itself.

9. Applying this in house - what to freeze

None of this is exclusive to public projects. It applies to in-house code unchanged, and arguably applies more urgently. When a maintainer leaves a public project it can at least be forked. An internal module whose owner transfers teams simply fossilises where it stands.

The internal task is not keep everything current. It is choosing which modules to declare finished and freeze. A freeze differs from neglect. A freeze is a decision to put the remaining cost into the budget explicitly.

CheckFreezableNot freezable
Feature demandNo new requests for four quartersRequests arrive every quarter
Contract documentInput and output spec lives in the repositoryIt exists only in the owner's head
Automated checksTests run and report failureVerification depends on people
External dependenciesResolved tree is countable on one handThe tree runs to dozens of entries
SizeA non-owner can read it in a dayReading alone takes days
Incident historyNo production incidents in a yearThe same cause keeps recurring
Review dateThe next review is pinned to a dateNo point in time is set

A hypothetical makes it concrete. Imagine a company with a module that only validates employee ID formats. Three hundred lines, no external dependencies, the specification written into an internal standard, tests present, and no requests for two years. That is a freeze candidate. By contrast a settlement batch whose spec changes every quarter and which is coupled to an external payment provider's response format is not freezable, however small it is. The criterion is not size. It is how often the outside moves.

Some things have to be written down alongside the freeze declaration.

  • Define what the freeze means. Spell out the scope, for instance no new features but security patches and runtime upgrades continue.
  • Pin a review date. An unconditional freeze is indistinguishable from neglect.
  • Say who catches it when it breaks. Write a role rather than a person's name so it survives reorganisation.
  • Define the trigger for the replacement plan. Deciding in advance what condition reopens the question shortens the argument later.
  • Publish the list of frozen modules in one place. Without a list, nobody knows anything was frozen at all.

10. Metrics for lifespan and how to measure them

The conditions above can be reduced to something measurable on a schedule. This is not a pitch for buying an audit tool. Three numbers settle most judgements.

The third of them, the distribution of change reasons, matters most and is used least. Whether recent changes were feature additions or reactions to the outside determines the state of the code. So it was measured. The target was the change history file that ships with the Python installed in this environment.

$ export PYTHONIOENCODING=utf-8
$ python news_entries.py NEWS.txt "3.13.2 final" | python classify_changes.py

Running the same tool over three sections shows the metric actually working. Below are three sections of the change history shipped with Python 3.13.3, each classified separately.

SectionFeatureDefectExternalOtherEntries
3.13.0 alpha 1 (development)27.1%37.4%13.4%16.1%634
3.13.2 final (maintenance)8.8%63.7%6.6%17.6%91

A feature share of 27 percent during development drops to 9 to 12 percent in maintenance. Same project, same period, same people, and yet the character of the changes differs. By commit count alone the maintenance phase looks like it went quiet, when in fact its nature changed. This is the distinction between dead and finished, expressed as a number.

The measurement has limits that deserve stating honestly.

  • It is keyword classification. It matches words rather than understanding sentences. In the output above other was 17.6 percent, and that bucket has to be read by a human.
  • Defect is tested before external by design. So a fix for a bug on one platform lands in defect. That means the external share is a lower bound.
  • Results shift with how changes are described. An organisation with commit message conventions will get considerably better accuracy.
  • A single section means nothing on its own. It has to be read as change over time within the same project.
  • The regular expressions need adapting per organisation. When editing them, running sample sentences through a regex tester first is quicker.

10.1 Three metrics and their thresholds

MetricHow to measureRough reading
Code sizeCode lines excluding comments and blanks, file count, largest fileHundreds of lines allows one-person handover, thousands needs a team

The thresholds are not absolute. The numbers above are a starting point derived from the values actually measured here, and they should be shifted to match the character of your own code. What matters is not the value but measuring repeatedly with the same ruler. A single measurement cannot support a verdict; it becomes useful from the second one onward.

11. What could not be verified

Here is what could not be confirmed, or could not be checked at all. Please read it with the same weight as the rest.

  • The article that prompted this piece could not be opened. So none of its claims or wording were quoted. Only the subject was taken, and everything was researched again from primary sources.
  • Whether narrowing scope was an explicit intention is not documented. The manual pages of both daemons above state only what they do, never declaring what they do not do. Narrow scope is inferred from the documented feature list, not declared by the project.
  • The official OpenBSD goals document itself was not read. Only the fact that the FAQ links to a separate page was confirmed.
  • The plan to run the change-reason classifier over a long-lived repository's commit log failed. Repository cloning was blocked in this execution environment. The change history file shipped with the locally installed Python was used instead. Note that the unit is a release note entry rather than a commit.
  • The module count is approximate. The exact total in the Apache 2.4 module index was not counted; only the scale of roughly 140 seen on the index page is reported.
  • The classifier's unclassified bucket was not reviewed exhaustively. In the development section 16.1 percent remained as other. A skim suggested it was mostly performance work and behaviour change descriptions, but it was not all read.
  • The import closure is an upper bound. It does not distinguish lazy imports inside functions or exception handlers. Runtime needs fewer.
  • No statistical study confirming that smaller means longer-lived was found. What this article offers is a definition of metrics and a way to measure them, not proof of causation. Examples are examples, and counterexamples may exist.
  • The measurements are one point in time on one environment. The same scripts on another version or operating system may return different numbers.

Conclusion: survival is accumulated refusal

Back to the opening scene. Whether to depend on a library with no commits for three years cannot be settled by the commit graph. Measure three things instead. How large is it, what is it tied to, and why did the last changes happen.

Once those three are measured, the verdict frequently flips. A quiet repository that is a few hundred lines, has one dependency, and whose recent changes are all runtime adaptations is not dead. It is done. Conversely, a busy repository that drags in dozens of entries and whose docs trail the code by two versions is not stable. That activity measures how much work is left.

And these conditions are set at construction time. Staying small requires refusing features. Reducing dependencies requires refusing convenient libraries. Holding a scope requires refusing user requests. Keeping documentation requires refusing undocumented merges. Lifespan is determined by what was left out, not by what was put in.

The same principle transfers to in-house code unchanged. Internally, though, it is rarely honoured, because there is no obvious person whose job it is to refuse. That is why the freeze declaration exists. The moment you write down for a given module that this is where its job ends and no other requests will be accepted, that module does not drop out of management. It finally starts being managed. That single sentence is what separates neglect from a freeze.

## 0. The five-minute verdict — just do these in order

1. Count code lines (comments and blanks excluded)
2. Count dependency surface (lock file entries, or the three-hop closure)
3. Classify recent change reasons (feature versus everything else)
4. Drop the values into the threshold table in section 4
5. If all three lean finished, it is a freeze candidate. If any leans neglected, stop and look again

**A single measurement cannot support a verdict. It becomes useful from the second one onward.**

## 1. Metric 1 — code size

```
python measure_size.py PATH1 PATH2 ...
```

`measure_size.py`

```python
import os, sys
SKIP = {".git", "__pycache__", "node_modules", ".venv", "build", "dist"}

def measure(root):
    files = code = blank = comment = size = 0
    targets = [root] if os.path.isfile(root) else []
    if not targets:
        for dirpath, dirnames, filenames in os.walk(root):
            dirnames[:] = [d for d in dirnames if d not in SKIP]
            targets += [os.path.join(dirpath, f) for f in filenames if f.endswith(".py")]
    for path in targets:
        files += 1
        size += os.path.getsize(path)
        for line in open(path, encoding="utf-8", errors="replace"):
            s = line.strip()
            if not s: blank += 1
            elif s.startswith("#"): comment += 1
            else: code += 1
    return files, code, comment, blank, size

for arg in sys.argv[1:]:
    print(os.path.basename(arg.rstrip("/\\")), measure(arg))
```

**Record alongside it**

- [ ] Line count of the single largest file (the maximum is the bottleneck, not the average)
- [ ] Values with and without tests, kept **separate**
- [ ] Whether generated code (parser output and similar) was excluded
- [ ] Comment lines divided by code lines, as the comment ratio

### 2-2. Without lock files — the three-hop import closure

```python
def closure_by_depth(root, max_depth=8):
    seen = {root}
    frontier = {root}
    levels = [set(seen)]
    for _ in range(max_depth):
        nxt = set()
        for name in frontier:
            for f in package_files(name):
                for dep in imports_of(f, name):
                    if dep not in seen and package_files(dep):
                        nxt.add(dep)
        if not nxt:
            break
        seen |= nxt
        frontier = nxt
        levels.append(set(seen))
    return levels
```

- **Do not use the full closure.** It saturates and discriminates nothing (a 355 line module and an 11,165 line module both converge on 124 and 180)
- **Cut at three hops.** The same targets spread from 16 to 174, more than tenfold
- Static parsing counts lazy imports inside functions, so the value is an **upper bound**

## 3. Metric 3 — the distribution of change reasons

```
git log --since=2.years --format=%s | python classify_changes.py
```

Core rules of `classify_changes.py` (order matters)

```python
RULES = [
    ("defect",   r"(fix\w*|bug|crash\w*|leak\w*|regress\w*|cve|vulnerab\w*|"
                 r"overflow|incorrect\w*|correctly|properly|avoid\w*|prevent\w*|"
                 r"no longer|wrong\w*|fail\w*|hang\w*|deadlock)"),
    ("feature",  r"(add\w*|introduc\w*|implement\w*|new |now support\w*|"
                 r"support\w*|allow\w*|expose\w*|optimiz\w*|improv\w*)"),
    ("external", r"(update\w*|upgrade\w*|bump\w*|bundled|vendored|deprecat\w*|"
                 r"compat\w*|toolchain|compiler|installer|platform|portab\w*|"
                 r"windows|macos|android|freebsd|openssl|sqlite|zlib)"),
    ("doc",      r"(document\w*|docs?|docstring|comment\w*|typo|readme|man page)"),
    ("chore",    r"(refactor\w*|clean ?up|style|reformat|renam\w*|test\w*|"
                 r"remov\w*|drop\w*|release|version bump)"),
]
```

**How to read it**

- `feature` share **25 percent or more** means growing. Do not freeze
- `feature` share **10 to 25 percent** means mixed. Measure again in six months
- `feature` share **below 10 percent** means maintenance only. **Freeze candidate**

**Non-negotiable**

- [ ] The `other` bucket was **read by a human** (up to 17.6 percent landed there in the measurements)
- [ ] `defect` is tested before `external`, so you know the **external share is a lower bound**
- [ ] Compared as **change over time in the same project**, not a single section
- [ ] Regular expressions adapted to your organisation's commit message conventions

**Reference measurements** (change history shipped with Python 3.13.3)

| Section | Feature | Defect | External | Other | n |
|---|---|---|---|---|---|
| 3.13.0 alpha 1 (development) | 27.1% | 37.4% | 13.4% | 16.1% | 634 |
| 3.13.2 final (maintenance) | 8.8% | 63.7% | 6.6% | 17.6% | 91 |

## 5. Freeze decision table

| Check | Freezable | Not freezable | Verdict |
|---|---|---|---|
| Feature demand | No new requests for four quarters | Requests every quarter | |
| Contract document | Spec lives in the repository | Only in the owner's head | |
| Automated checks | Tests run and report failure | Manual verification | |
| External dependencies | Tree countable on one hand | Dozens or more | |
| Size | A non-owner reads it in a day | Days just to read | |
| Incident history | No production incidents in a year | Same cause recurring | |
| Movement outside | External specs are fixed | Outside changes every quarter | |
| Review date | A date is pinned | No point in time set | |

**Decision rule**

- **Seven or more of eight freezable** means declare the freeze
- **Four to six** means re-check in six months and strengthen docs and tests meanwhile
- **Three or fewer** means not freezable. Keep it in normal maintenance

**Caution:** small size does not make it freezable if **the outside moves often**. The criterion is external change frequency, not size.

## 7. Handover checklist

**Confirmed by the person handing over**

- [ ] The build finishes in **one command** (no dependence on the owner's laptop)
- [ ] Required runtime versions and external tools are **pinned in configuration files**
- [ ] Tests run, and **say failed when something failed**
- [ ] The deployment procedure is documented, and following it actually deploys
- [ ] The rollback procedure is documented
- [ ] There is a **record of decisions** explaining why this structure was chosen
- [ ] Every odd-looking branch has **a stated reason** in a comment or an issue
- [ ] Documentation lives in the same repository as the code
- [ ] Examples are in an **executable form**

**Permissions — most often missed**

- [ ] **Two or more people** hold repository admin rights
- [ ] Two or more people hold deploy rights
- [ ] Package registry ownership is **not a personal account**
- [ ] Where signing keys live and how to access them is documented
- [ ] Domain and certificate renewal is assigned **to a role**
- [ ] External service accounts are registered to a shared address

**Confirmed by the person taking over**

- [ ] Built and deployed it **end to end using only the documentation**
- [ ] Deliberately broke one thing and confirmed **the tests catch it**
- [ ] Read the single largest file **all the way through**
- [ ] Skimmed a year of issues and incidents looking for repeating patterns
- [ ] Left unknowns **as questions in the documentation** rather than settling them by asking a person

## 8. Rewrite decision table

| Situation | Verdict |
|---|---|
| Requirement premises changed beyond what the structure expresses | Rewrite |
| Runtime, language or core library reaches end of support | Rewrite or port |
| Nobody can read it and docs cannot restore it | Rewrite |
| Security defects recur from the structure itself | Rewrite |
| Slow, but the bottleneck is identified | Partial replacement |
| Recent changes are mostly fixes and outside adaptation | Keep |
| The complaint concerns style or fashion | Keep |
| No reason other than it being old | Keep |

**Required before starting a rewrite**

- [ ] Recovered **why the existing code looks the way it does**
- [ ] Checked whether odd-looking branches are scars from incidents
- [ ] Extracted the **list of existing behaviours** the new code must pass
- [ ] Decided the compatibility range for data and file formats

## 9. Do not

- ❌ **Judge from the commit graph alone** — it measures remaining work, not health
- ❌ **Count only declared dependencies** — one declared line resolved to a tree of 69
- ❌ **Compare using the full transitive closure** — it saturates and separates nothing
- ❌ **Trust classifier output as is** — skipping the `other` bucket loses up to 17.6 percent
- ❌ **Freeze without a date** — that is indistinguishable from neglect
- ❌ **Assign ownership by personal name** — it does not survive reorganisation
- ❌ **Freeze while budgeting security patches at zero** — that is debt, not a freeze
- ❌ **Split documentation into a wiki** — separate ownership always falls behind
- ❌ **Measure once and decide** — metrics only mean something as repeated readings on one ruler
- ❌ **Conclude that small equals good** — the cost was moved onto the user side
- ❌ **Conclude that many dependencies equals bad** — there are phases where speed is right
