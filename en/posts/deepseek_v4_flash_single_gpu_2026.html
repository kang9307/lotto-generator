Intro: You read that it runs on one GPU and opened a budget sheet

A sentence saying some model runs on a single GPU always produces the same reaction. Then we can do it too. But that sentence has about six conditions stripped out of it, and one missing condition is the difference between one card and three.

Here is the conclusion first. A 284B MoE fits on one 192GB card not because the model is small, but because the official checkpoint already ships at effectively four bits. Stack the KV cache and activations on top and the headroom left is a couple of gigabytes. Add concurrent requests to that state and the speed each user feels collapses. What separates the workable case from the unworkable one is not card performance. It is how many requests arrive at once.

This article walks that arithmetic in order. It starts at weight bytes, moves to what total and active parameters each decide in an MoE, shows where the KV cache claims its own space, marks where the ROCm stack actually stops, and ends with the procedure for running the same calculation and finding the out-of-memory point on your own hardware.

The scope is narrow on purpose. This is about one datacenter accelerator and a large MoE. Running local models on consumer hardware, whether that means an old CPU driving a small model or turning on GPU acceleration on a Mac, lives in Running Gemma 4 on a Ten-Year-Old Xeon and Why Local LLMs Are Slow on a Mac. The general treatment of GGUF quantization tiers and consumer GPU VRAM requirements is in the local LLM running guide.

1. Weight capacity is set by bytes, not parameter count

The first calculation is a single multiplication.

weight bytes = parameter count × bytes per parameter

FP32  = 4 bytes
BF16 / FP16 = 2 bytes
FP8   = 1 byte
FP4   = 0.5 bytes

Skip that multiplication, look only at the parameter count, and the whole plan drifts. The same 284B needs four times as many cards depending on the precision it is stored in.

1.1 What each precision actually costs

The DeepSeek-V4-Flash model card lists 284B total parameters with 13B active per token. Storing that 284B at different precisions splits as follows. Card counts assume 192GB per card and cover weights only, so real deployments need more.

Storage precisionPer parameter284B weight capacityMinimum 192GB cards (weights only)
FP324 bytesabout 1,136 GB6
BF16 / FP162 bytesabout 568 GB3
FP81 byteabout 284 GB2
FP40.5 bytesabout 142 GB1
As shipped (FP4 experts + FP8 remainder)under 1 byte on averagecheckpoint about 160-167 GB1, with almost no headroom

That last row is the starting point for everything else here. The vLLM recipe documentation puts the checkpoint at roughly 160GB for the preview and about 167GB for the fused variants. The model card describes the format as mixed, with MoE expert parameters in FP4 and attention, normalization and router parameters in FP8.

1.2 How this differs from post-hoc quantization

A common confusion sits here. The familiar order when handling local models is this: take the BF16 original, squeeze it into Q4, then check how much quality was lost. This model reverses that. The distribution itself starts at low precision.

  • The average bytes per parameter is already below one without any user-side quantization
  • So the option of shrinking further by quantizing has largely been spent already
  • Instead the party absorbing the quality cost is the model author rather than the user, which means the training process can be adjusted with that precision in mind, a better position than squeezing after the fact
  • Put differently, the card labeled quantize to save a GPU has already been played for this model

Choosing how far to drop a post-hoc quantization tier, the tradeoff between Q4 and Q8, is a different problem and is covered separately in the local LLM running guide.

2. Total and active parameters consume different resources

One sentence ruins more MoE plans than any other: active is 13B so 13B of memory should do it. It does not. Leave that uncorrected and every downstream calculation is wrong.

2.1 The router picks again for every token

Each MoE layer in DeepSeek-V4-Flash holds one shared expert and 256 routed experts, and six routed experts fire per token. The expert intermediate dimension is 2048, and the first three MoE layers use hash routing.

The point is that you cannot know in advance which six get picked. The router decides on the spot based on what the next token is. So all 256 experts have to be sitting in memory. If they are not, the ones you need have to be pulled from disk or host memory at that moment, and that round trip is an order of magnitude away from GPU compute time.

2.2 What decides what

This valueDecides this resourceWhat happens when you raise it
Total parameters (284B)Resident memory for weightsYou need more cards
Active parameters (13B)Compute per tokenToken generation slows down
Context lengthKV cacheMore memory, independent of weights
Concurrent sequencesKV cache plus activationsBoth memory and per-stream speed worsen
Batch sizeActivations and workspaceThroughput rises, individual latency grows

The commercial value of MoE lives in the first two rows diverging. You get 284B-class expressiveness at 13B-class compute cost. The memory bill still arrives sized for 284B. That is design intent, not a defect, and the only discipline required is not mixing the two rows when planning.

Worth adding: because of that divergence, MoE is relatively favorable on hardware with generous memory and modest compute. In the reverse case, tight memory with compute to spare, a dense model of comparable quality can be the better pick. Why a 27B dense model is comfortable on a single GPU is covered in Qwen 3.6 27B, the sweet spot for local development, and that article's sweet-spot logic and this article's arithmetic are looking at the same wall from opposite sides.

3. Why the MI300X shows up in this conversation

There is one reason an AMD accelerator enters a single-GPU discussion: how much fits on one card. It is an arithmetic question, not a benchmark contest.

3.1 The published specifications

Per AMD materials the MI300X carries 192GB of HBM3. The memory bus is 8,192 bits at a 5.2 Gbps data rate for a peak bandwidth of 5.325 TB/s. It uses the CDNA 3 architecture with eight XCDs, and at the 750W class with a 2,100 MHz boost clock the peak theoretical FP16 and BF16 figures are each listed at 1,307.4 TFLOPS.

Peak theoretical is not a measurement. The 1,307.4 TFLOPS number is an upper bound computed from clock and unit count, and real inference never lands near it. That figure is for comparing card generations, not for predicting throughput.

3.2 Compare on two axes only

Comparison against NVIDIA parts is accurate when narrowed to two axes. Try to rank raw speed and the conditions diverge until the comparison stops meaning anything.

  • Capacity. How much fits on one card. On this axis the part with larger HBM has the advantage for single-card setups. The moment you cross a card boundary, tensor or expert parallelism enters, the interconnect becomes a new bottleneck candidate, and failure points and operational complexity grow together. Fit on one card and all of that disappears
  • Software maturity. Whether the kernels and servers exist to actually use that capacity. Here the CUDA ecosystem is still ahead, and section 6 puts numbers and names on that gap

Declining to post a speed comparison is not timidity. For the same model, throughput swings by multiples depending on precision, context length, batch size, kernel library version and whether speculative decoding is on. Placing two numbers side by side without matching conditions produces an illusion, not a comparison.

4. How memory actually divides on a single card

Arithmetic alone misses part of it. The real allocation diverges from a weights-only estimate by more than 40GB.

The figures below are what a published single-MI300X configuration repository recorded on its own stack. Conditions first. The target is DeepSeek-V4-Flash-0731, the hardware is a single MI300X (gfx942, 304 CUs, 192GB HBM3), the server is a vLLM ROCm nightly at 0.26.1rc1.dev229+g124154a88.rocm723, kernels come from AITER 0.1.19, the KV cache is FP8 (fp8_ds_mla, 256-token blocks), the weights are as shipped with no additional quantization, and the validated context is 256K.

Weights156.67 GBShipped precision, no extra quantization

Everything else (activations, workspace, graph buffers, allocator slack)about 28 GBDerived from the high-water mark below
Warmed high-water mark204.5 GB of 205.8 GB totalAbout 1.3 GB free

4.1 Three things to read off this table

  1. Counting weights alone misses by more than 40GB. Look at 156.67GB, conclude that 192GB leaves 35GB spare, and the 20GB KV pool plus 28GB of everything else will break the plan
  2. The high-water mark is 99.4% of total. Having only 1.3GB free means this is the number after tuning finished, not the number you start from. A first launch usually dies well before reaching it
  3. Why 192GB and 205.8GB differ. Most of it is unit convention. 192 GiB is roughly 206.2 GB in decimal. All you need to carry away is that the spec-sheet number and the allocator's number will not match exactly. Do not plan down to the last gigabyte

What kind of numbers these are. The values above were measured by the repository maintainer on their own stack and have not been vendor-validated. The server is a nightly build, so a kernel or version change shifts the allocation too. Do not copy them across. Measure on your own hardware using the procedure in section 9.

5. The KV cache is a separate axis from weights

This is where quantization discussions leak most often. Dropping weights from FP16 to FP4 removes exactly zero bytes from the KV cache. They are different axes.

5.1 The formula for conventional attention

For MHA or GQA family models the KV cache size comes out like this. Pull the values from your model's config.json and substitute.

KV bytes = 2 × layers × KV heads × head dimension
           × bytes per element × tokens × concurrent sequences

# the leading 2 covers the Key and Value copies
# bytes per element: FP16=2, FP8=1
# tokens = prompt + output generated so far

What to read from the formula is that weight precision appears nowhere in it. However far you squeeze the weights, this value is unchanged. Shrinking it means lowering KV precision separately, shortening the context, or reducing concurrent sequences.

5.2 Compressed attention families break the formula

The DeepSeek V4 family uses a hybrid of Compressed Sparse Attention and Heavily Compressed Attention. It caches latent representations, so substituting into the formula above overestimates. The model card states that for V4-Pro the KV cache is around ten percent of V3.2 at one million tokens.

For such models it is more accurate to work backwards from the pool size the server reports. Taking the section 4 configuration as an example:

20 GB ÷ 1,927,444 tokens ≈ about 10 KB per token
# conditions: FP8 KV cache, fp8_ds_mla, 256-token blocks, this server build

That 10 KB is a value from this setting, not a constant of the model. Change the KV precision or the block size and it changes. It is still useful for planning, because it gives you the feel that one 128K-context conversation takes roughly 1.3GB and a 256K one roughly 2.6GB.

5.3 How this splits decisions in practice

  • Advertised context and usable context are different numbers. A million-token ceiling is unusable if the KV pool cannot carry it
  • The KV pool is shared across concurrent streams. Even a pool holding 1.9 million tokens shows its floor at seven or eight 256K sessions
  • In vLLM the option that sets KV precision separately is --kv-cache-dtype, with fp8 on the NVIDIA path and fp8_e4m3 on the ROCm path
  • Modes that emit long outputs raise the requirement sharply. The recipe documentation tells you to set --max-model-len to at least 393,216 for modes using up to 384K output tokens
  • Turning on prefix caching pays off in reuse but needs a tier to push evicted entries down to the host. That is why the configuration above keeps a 96 GiB CPU offload tier

6. What works on ROCm today and what does not

Getting the model loaded and getting the stack running are different problems. Porting failures usually trace not to model architecture but to three lines: Python wheels, kernel libraries and quantization formats.

6.1 Where vLLM stands

From the vLLM installation documentation:

  • Required ROCm version is 6.3 or above
  • Supported GPUs named are MI200s (gfx90a), MI300 (gfx942), MI350 (gfx950, requiring ROCm 7.0+), Radeon RX 7900 and 9000 series, and Ryzen AI MAX / AI 300 series (requiring ROCm 7.0.2+)
  • Prebuilt wheels are Python 3.12 only, in ROCm 7.0 and 7.2.1 variants
  • Official Docker images are vllm/vllm-openai-rocm, in stable and nightly flavors
  • The from-source path means setting PYTORCH_ROCM_ARCH and running python3 setup.py develop

The trap that quietly costs the most time. The documentation warns about this directly: install on anything other than Python 3.12 and the installer silently falls back to CUDA wheels. Installation looks successful and execution fails on AMD hardware. The cause looks like the model or the kernels but it is one wheel. Checking the Python version and the identity of the installed wheel first is the habit that saves the most hours when setting up ROCm machines.

6.2 Where SGLang stands

  • The AMD documentation uses the MI300X as its representative example
  • Prebuilt images are lmsysorg/sglang on Docker Hub, built from rocm.Dockerfile in the repository
  • The acceleration switch documented is export SGLANG_USE_AITER=1. For RDMA configuration, export NCCL_IB_GID_INDEX=3
  • It names the quantization methods that do not work on AMD, all of them dependent on Marlin or NVIDIA-specific kernels
ItemOn AMD ROCmBasis
awq_marlin / gptq_marlinDoes not workMarlin kernel dependency
ggufDoes not workStated in SGLang docs
modelopt_fp8 / modelopt_fp4Does not workNVIDIA-only path

The AMD section of the vLLM recipe points the same way. For the MI325X configuration it documents export VLLM_ROCM_USE_AITER=1 and --moe-backend triton_unfused, and in eager mode it pairs --enable-chunked-prefill with --max-num-batched-tokens 256 and --kv-cache-memory-bytes 10000000000.

6.3 The judgment

Summed up: loading the model works, and what blocks you sits underneath it. So what an organization evaluating ROCm needs is not model knowledge but these three things.

  1. A deployment method that pins the Python version and the wheel. Using the Docker images is decisively safer
  2. Confirming that the quantization format you intend to use exists on the AMD path before choosing a model. A plan built around GGUF collapses right here
  3. If the configuration depends on nightly builds, pinning versions wholesale and writing down a reproduction procedure. The reproduction window is narrow

7. The point where concurrency breaks it

Fitting in memory does not make a service. The real limit of a single-card setup shows up here.

The numbers below come from the same stack as section 4. Conditions are identical, with DSpark-7 speculative decoding enabled for decode.

Concurrent streamsAggregate throughputPer streamHow to read it
1168.6 tok/s168.6 tok/s (median)Fast for a human reader
8542 tok/s90.3 tok/s (median)3.2× aggregate, under half the felt speed
64 (burst)830 tok/s—8× the streams for 1.5× aggregate. Saturated

The prefill figures belong here too: roughly 7.9-8.5K tokens per second with tuned kernels, and 6,988-7,019 tokens per second on fresh prompts in the production profile. Fast prefill means an advantage on work that pushes long prompts through, such as document summarization or codebase indexing.

7.1 What this table decides

Going from 1 to 8 gave 3.2× aggregate. Not bad. But going from 8 to 64 multiplies streams by eight and lifts the aggregate only 1.5×. Somewhere in between the card saturated, and requests past that point contribute nothing to throughput while adding queue latency.

The judgment that follows is clear.

  • Capacity planning on aggregate throughput will not match real user experience. Plan on per-stream speed
  • Put human reading speed at roughly 15-20 tokens per second and the point where per-stream falls below it is the practical concurrent-user ceiling for that card
  • Non-interactive batch work is the opposite. Individual latency can grow as long as the aggregate is high, so filling streams to the brim pays
  • Remember these figures have speculative decoding on. Speculative decoding helps most at single-stream and gives back some of its advantage as concurrency rises

8. Where a single GPU earns its place, and where it does not

Turning the arithmetic above into a decision splits it this way.

SituationSingle-GPU setupWhy
Batch-one experiments, prompt and eval iterationFitsConcurrency near 1 keeps per-stream speed at maximum
Overnight batch work (summarize, classify, index)FitsOnly aggregate throughput matters, not individual latency
Internal workloads where data cannot leaveFitsThe requirement is a boundary, not speed
Research observing model behavior itselfFitsReproducibility and control are the goal
Internal tools for a small team, queue acceptableConditionalOnly with a measured concurrency ceiling and a real queue
Multi-user service with a response-time commitmentDoes not fitPast concurrency 8 the per-stream speed collapses
Public service with traffic spikesDoes not fitBeyond saturation the queue only grows latency
Production with availability requirementsDoes not fitOne card is a single point of failure
Service holding many long-context sessionsDoes not fitConcurrent streams share the KV pool

8.1 Seen again as cost

One more judgment on top. For a workload that runs a few hours a day, self-hosting on one card almost always loses. Depreciation, power, rack space and operations labor keep accruing while the card idles, and an API costs zero when unused. Even counting only the electricity of a 750W-class accelerator running continuously, the cost of idle hours is not trivial.

The conditions where it does work are narrow.

  • Utilization is high. The queue is rarely empty during most of the day
  • Request patterns are uniform. Context and output lengths are predictable enough to fix a KV budget
  • A data boundary requirement genuinely exists. Contracts or regulation prevent sending the material outside
  • Volume reaches the point where self-hosted unit cost beats token pricing

All four hold and the single-card setup works. Break one and the API is the right answer. Commercial model pricing and performance comparisons are maintained in the AI model comparison hub, and how aggressive API pricing pushes the self-hosting break-even further out is covered in the DeepSeek V4 Pro price cut. The criteria for splitting local and API across an agent workload are in agentic coding with local LLMs.

9. How to measure this on your own hardware

Instead of copying someone else's numbers, here is the order for producing your own. Five steps is enough.

9.1 Check available memory first

# AMD
rocm-smi --showmeminfo vram

# NVIDIA
nvidia-smi --query-gpu=name,memory.total,memory.used --format=csv

Work from what the tool reports, not from the spec sheet. Check whether the unit is GB or GiB, and whether memory is already held by something else.

9.2 Get weight capacity from file size

# how many bytes the downloaded checkpoint actually is
du -sh /path/to/model
du -ah /path/to/model | grep safetensors | tail -5

This is more honest than a figure computed from parameter count. Mixed-precision checkpoints are hard to predict arithmetically, and tokenizer and index files come along for the ride.

9.3 Set a KV budget per context length

For a conventional attention model, substitute layer count, KV head count and head dimension from config.json into the formula in 5.1. For compressed attention families, bring the server up once with a short context and take the KV pool size and token capacity the startup log prints, then work back to bytes per token. Multiply that by your target context and target concurrent sessions to get the pool size you need.

9.4 Find the OOM point by bisection

# startup check only. narrow the success/failure boundary
vllm serve <model> \
  --max-model-len 32768 \
  --kv-cache-dtype fp8_e4m3 \
  --gpu-memory-utilization 0.90 \
  --enable-chunked-prefill \
  --max-num-batched-tokens 256
  • Raise --max-model-len by halves to find the boundary between successful and failed startup. The largest success is that configuration's real context ceiling
  • Start --gpu-memory-utilization at 0.90 and creep upward. Pin it at 1.0 and one fragmentation event kills the process
  • On the ROCm path use --kv-cache-dtype fp8_e4m3. The NVIDIA path uses fp8
  • If startup succeeds but requests kill it, the problem is activations. Lower --max-num-batched-tokens to shrink prefill chunks

9.5 Measure the concurrency limit

The last step matters most. Raise stream counts through 1, 4, 8 and 16 and record tokens per second per stream. Per stream, not aggregate. The point where it drops below your target felt speed is that card's concurrent-user ceiling, and you need that number before you can answer how many people this machine serves. Buy a card without that measurement and the plan is usually optimistic by about a factor of two.

10. What I could not confirm

The items in this article without secured backing, gathered in one place.

  • A parameter-count discrepancy. The official model card lists 284B total and 13B active. The single-MI300X repository cited above and its summary describe the target as DeepSeek-V4-Flash-0731 at 304B. I could not find a separate parameter figure for the 0731 revision in official documentation. So this article uses 284B/13B when describing the model and leaves 304B as the repository's own labeling
  • Layer count and head configuration. Not confirmable from the model card, so the KV formula in 5.1 was not substituted directly for this model. The server-reported figure was used instead
  • Reproducibility of the throughput numbers. The section 7 figures have no third-party validation and the server is a nightly build. There is no guarantee the same numbers appear on other hardware
  • Matched-condition numbers for other accelerators. I could not find public measurements with precision, context, batch and kernel version aligned. That is why there is no speed comparison table here
  • Actual power draw. Beyond the 750W class rating, the consumption and thermal profile under this workload are unconfirmed
  • Quality impact. How much the FP4-experts-plus-FP8-remainder format costs against the original on specific tasks is outside this article's scope. Beyond what the model card publishes, I found no independent evaluation

Conclusion: three things you can apply today

First, get in the habit of speaking in bytes rather than parameter counts. Writing about weights of roughly 157GB at shipped precision instead of a 284B model cuts meeting arguments in half. Card count is decided by bytes, not parameters.

Second, always write total and active parameters side by side in an MoE plan. The first is the memory bill, the second the compute bill. A plan that lists only one is guaranteed wrong on one side or the other.

Third, draw the concurrency curve before buying a card. What breaks a single-card setup is concurrency, not memory. A machine producing 168 tokens on one stream gives 90 per stream at eight, and at sixty-four even the aggregate stops rising. If you cannot answer how many people use it at once with a number, it is not time to buy yet.

One closing note. Single-GPU setups are interesting not because they are the cheapest way to serve. It is that the complexity which disappears the moment you stay inside one card is substantial. No parallelism strategy, no interconnect tuning, no cross-node failure handling. There are places where that simplicity is worth real money, and just as clearly places where it is not. Find your row in the table above before you start.
