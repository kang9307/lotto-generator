解こうとしている問題 — 強制プッシュ後に同じコードを読み直す

READMEは二つのワークフローを脚注で区別している。パッチシリーズ型のワークフローではレビューサイクルをまたいでコミットが書き換えられ（amend、rebase、force-pushなど）、プルリクエスト型のワークフローでは既存のコミットに触れずにブランチの先端へ新しいコミットを足す。2025年11月の記事はこの区別をより詳しく説明している。

作者が「PRワークフロー」と呼ぶのは、GitHubのプルリクエスト機能によって広まったやり方である。すでにレビューされたコミットには触れず、ブランチの先端に新しいコミットだけを足すよう促すので、レビュアーは最後にレビューしたコミットと最新のコミットの間のdiffだけを見ればよい。作者は、このやり方はすでに「漸進的」であり、これに満足している人がFlirtから得るものはそれほど多くないと書いている。

「パッチシリーズワークフロー」はメーリングリストでのやり方から名前を取っているが、GitHubでも行われており、作者はJujutsuプロジェクトを例に挙げる。コードの作者はレビューサイクルのたびにコミットをamend、squash、fixup、rebaseし、コミット履歴の品質を高めていく。作者が挙げる利点は、バグの原因を探すとき、整理された履歴があればそのバグを持ち込んだコミットを特定して取り消しやすいという点である。

その代償はレビューの側が払う。既存のコミットを変更する操作はコミットのハッシュを変え、その後はコミットがどう変わったかを知るのが容易ではなくなる。作者の例は次のとおりである。パッチシリーズのあるコミットが100行を変更しており、99行には問題がないが、最初のレビューで1行に抜けているセミコロンを足すよう指摘が出る。コードの作者は「セミコロンを追加」というコミットが履歴に残らないよう、既存のコミットをamendする。強制プッシュ（または新しいパッチシリーズの提出）の後、レビュアーの前にはたいてい100行のdiff全体が再び置かれる。前回のレビュー以降に1行しか変わっていないことをツールが理解していないからである。作者はこうしたツールを「非漸進的」なレビューツールと呼ぶ。

既存ツールの補助策に対する作者の評価も同じ記事にある。GitHubのプルリクエスト画面の「changes since last review」ボタンやファイルごとの「viewed」チェックボックスは助けになるが、ごく普通の状況の多くで機能しないというのが作者の記述であり、メーリングリストの側にはヒューリスティックでパッチシリーズの二つの版を比較するgit range-diffがあると書いている。作者が指摘した問題とFlirt側の対応をまとめると次のようになる。「構想」「計画」と書いた欄は、それぞれの記事の時点での記述である。

change-idでコミットを対応づける — interdiffとgit range-diff

解決策の土台はchange-idである。2025年11月の記事の定義では、コミットハッシュと違って、コミットがamendされてもrebaseされても変わらない、もう一つのコミット識別子である。レビューツールがすでにレビューしたコミットをchange-idとともに記憶しておけば、新しいコミットが出されたときに、同じchange-idを持つ以前のコミットと対応づけられる。二つのコミットの間のinterdiffを計算すると、レビュアーがまだ見ていない変更だけが残る。作者はこれをFlirtの中心機能だと書いている。レビューしたものを記憶し、既定ではそれと比べて変わったところだけを示す。

用語はAustin Seippの文章「Why some of us like "interdiff" code review」から来ており、READMEもワークフローの説明の参考としてこの文章にリンクしている。作者は、interdiffという語は実装方法を指していてやや技術的だとし、実用上の利点を表す「漸進的コードレビュー（incremental code review）」という名前を選んだと書いている。指しているものは同じである。

change-idがどこから来るかには条件が付く。

  • JujutsuはGit互換のバージョン管理ツールで、change-idをカスタムコミットヘッダーに記録する。Flirtがこの仕組みを使えるのは、コミットの作者がJujutsuを使っている場合である。
  • READMEは、この機能がコミットに含まれるさまざまな種類のメタデータに依存しており、作者がJujutsuを使う場合に信頼性が最も高いと書いている。
  • change-idヘッダーがなければ代替ヒューリスティックが使われる。2025年11月の記事は、この代替手段が概念上はgit range-diffと同じことをするが、最初はずっと単純なヒューリスティックになるだろうと書いていた。
  • 2026年8月の記事は、件名行や作者を照合するといったヒューリスティックを例に挙げ、現在の制約のもとでは何を選んでもヒューリスティックにならざるを得ないと書いている。
  • READMEはGerritにも同じ機能があると記す。作者は、Gerritのレビュー画面がchange-idによってすでに漸進的レビューを実現していると書きつつ、自分はGerritを本格的に使ったことがないと明かしている。

Gerritがあるのに新しいツールを作る理由として作者が挙げるのは、プラットフォームの問題である。自分が関わるプロジェクトのコード共有プラットフォームを自分では決められず、職場も、好んで貢献しているオープンソースプロジェクトの多くもGitHubを使っているという。レビューツールがコード共有プラットフォームに結びつけられているという点を解くことがFlirtの二つ目の動機だと作者は書いている。

代替手段の基準点であるgit range-diffは、Gitの公式ドキュメントで次のように定義されている。パッチシリーズの二つの版、より一般には二つのコミット範囲の間の差分を示すコマンドであり、マージコミットは無視する。対応を見つける根拠は識別子ではなく類似度である。

  • 二つのコミットのパッチ（作者情報、コミットメッセージ、コミットのdiff）同士のdiffがパッチの大きさに比べて十分に小さいとき、二つのコミットは対応するとみなされる。
  • 二つの範囲のコミットの組ごとに「diffのdiff」をコンテキスト3行で生成し、その行数をコストとして、最小コストの割り当て問題を解く。
  • 大きな変更を丸ごとの書き直し（あるコミットの削除と別のコミットの追加）と誤って判断する場合に調整するオプションが--creation-factorで、既定値は60である。
  • 出力は人が読むためのものである。ドキュメントは、出力は変更されうるものであり、機械で読むことを意図していないと書いている。

まとめると、range-diffはパッチの内容がどれだけ似ているかで対応を推定し、change-idの方式はコミットに記録された識別子が同じかどうかで対応を決める。FlirtのREADMEが、作者がJujutsuを使うかどうかで信頼性が変わると明記している理由はここにある。

4つのバックエンドの状態 — Forgejoはまだ存在しない

READMEは、ユーザーがプロジェクトのホスト先を気にしなくてよいことを理想として掲げる。ForgejoでもGitHubでもメーリングリストでも、途切れのない体験を提供することが目標だという。続いて4つのバックエンドとそれぞれの制約を挙げているが、完成度はそろっていない。

バックエンド READMEが記す状態 動作と制約 補足の記述
Forgejo まだ存在しない。「いずれできる」 FlirtはCodebergでホストされているため、できればコントリビューターがこのバックエンドをFlirtの開発で実際に使える 告知: これを作ることがToDoリストの次の項目
Native Git 独自の（不安定な）形式 レビュー情報をGitのオブジェクトストレージに置き、カスタムrefでリモートにpush・fetchする。主な用途は外部サービスなしでのテスト 全員がpush権限を持つチームで使うことはできるが、形式の不安定さと保管の問題から、今のところ良くない考えだとREADMEは書く
GitHub おそらく最も使われるバックエンド プロプライエタリであるため、貢献がGitHub対応の有無で止められてはならない 2026年8月の記事: 実装したが機能は限られ、いくつもの点でバグがある
メーリングリスト 今のところ概念実証のみ メールは送らず、テスト用のローカルpublic-inboxサーバーに取り込むだけである git send-emailがJujutsuのchange-idコミットヘッダーを保持しないため、主要機能の信頼性が低い

2026年8月の記事によれば、Native Gitバックエンドで使っていたカスタムrefの仕組みを、ほかのバックエンドでもそのまま使っている。何かをするたびにGitHub APIを呼んだりメールスレッドをダウンロードしたりするのを避けるためで、これらのrefはローカルにとどまり、ユーザーがバックエンドとの同期を要求したときにAPI呼び出しやメールに変換される。GitHubバックエンドについて同じ記事が書いている制約は次のとおりである。

  • 作者が挙げる最大の問題は、PRに対する過去の強制プッシュの情報をGitHubから得られないことである。そのため、すべての提出の間のinterdiffを示すことはできない。
  • 標準的な使い方である「最後にレビューした提出と現在の提出のinterdiff」はおおむね動作する。最後にレビューした提出をローカルに記憶しておけるからである。
  • 作業マシンを替えるとこれが壊れうる。そのマシンが最後にレビューした提出を一度も見ていなければ、GitHub APIから簡単には取得できない。
  • APIはレビューコメントが付けられたコミットハッシュを知らせるので、過去の提出の再構成に使える。ただし途中のコミットにだけコメントがあり先端のコミットにない場合、提出は部分的にしか再構成されない。
  • GitHubのレビュー画面はdiffの上にコメントを付けさせるが、Flirtはコードベースの特定の状態にコメントを付ける。そのためdiffの左側（削除された行）に付いたコメントの置き場所が課題として残っており、作者は実装に時間がかかりそうだと書いている。

メーリングリストのバックエンドはさらに初期の段階にある。同じ記事には次のことが書かれている。

  • 対応範囲はpublic-inboxを使うプロジェクトに限っている。作者は、LinuxカーネルとGitがメーリングリストのアーカイブにpublic-inboxを使っていると書いている。
  • git format-patchは既定ではbaseコミットの情報を入れず、--baseフラグを付ける必要がある。この情報がなければパッチをどこに適用すべきか決められない、というのが作者の指摘である。
  • git format-patchはJujutsuのchange-idヘッダーを保持しない。READMEの脚注は、これを改善するパッチシリーズがGitのメーリングリストに投稿され、比較的好意的に受け止められたものの別のアプローチが求められ、作者の知るかぎりまだ何も取り込まれていないと書いている。
  • 同じパッチシリーズの複数の版を結びつける根拠としては[PATCH v2 0/N]のような件名のバージョン表記があるが、表記が抜けたり文言が変わったりすることがある。
  • Flirtが現在対応している形式は一つである。新しい版の最初のメールを前の版の最初のメールへの返信として送り、すべての版が一つのスレッドになるようにする方式で、作者はGitプロジェクトがこれを推奨していると書いている。作者が引用するLinuxカーネルのドキュメントは、複数パッチのシリーズではIn-Reply-Toで古い版につなぐのを避けるのが概して最善だと書いている。
  • コメントを読む側は、引用記号が重なったプレーンテキストを構造に直す必要があり例外が多く、作者はごく単純な場合にしか動作しないと書いている。
  • コメントを送る側も実際のメールは送らない。メールを組み立ててpublic-inbox-mdaに渡し、ローカルのテスト用public-inboxインスタンスに取り込む。

Flirtが対応するスレッド構造を、作者は次のように図示している。

レビュー情報をGitリポジトリに置く方式 — git-notesではなくカスタムref

READMEはNative Gitバックエンドの保存形式を「独自の（不安定な）形式」としか書いていない。その内部は2026年2月の記事で説明されており、以下はその時点の記述である。

作者は、同じ発想の先行プロジェクトとしてgit-appraiseを調べた。レビュー情報をGitリポジトリの中に直接保存し、異なるツール同士が互換になるよう標準を定めることを主眼としたプロジェクトだと作者は紹介している。その保存形式がFlirtに使えるかを検討した結論は「使えない」であり、理由はgit-appraiseが情報をgit-notesに置くことにあった。

  • コミットがgit-rebaseなどで書き換えられるとハッシュが変わる。以前のハッシュに付いていたノートは新しいコミットに移るべきだが、Gitは既定ではそうしない。設定で有効にできるが、オプトインである。
  • Jujutsuではコミットを編集するときにgit-notesを移す機能がサポートされていないと作者は書いている。
  • git-appraiseにはこれを処理する文書化されていないrebaseコマンドがあるが、ユーザーがあらゆるコミット書き換えでそれを使うとは期待できない、というのが作者の判断である。
  • 作者は、レビューリクエストを作ってからコミットをamendし、reflogの期限切れとガベージコレクションをすぐに起こすとリクエストが消える短いスクリプトを示している。通常と違うのはガベージコレクションを即座に起こした点だけだと付け加えている。
  • 参照も不便だと書いている。コミット、change-id、ブランチからレビュー情報の場所が直接わからず、ノートの一覧をたどってJSONを解析しなければならないという。

代案はカスタムrefである。refはオブジェクトを指すポインタで、ブランチは.git/refs/heads/、タグは.git/refs/tags/、ノートは.git/refs/notes/の下にある。作者は、ほかのディレクトリ、たとえば.git/refs/flirt/の下に新しいrefを作れると説明する。こうしたrefはGitにとって特別な意味を持たないが、同じように動作する。指しているオブジェクトがガベージコレクションで消されないようにし、ブランチのようにpush・fetchできる。

最初は、データ構造をJSONに直列化してblobとして保存し、refがそのblobを指すようにした。問題は途中の提出だった。Flirtは、プルリクエストやパッチシリーズに当たるレビュー単位をSpirit（「Set of Patches Intended for Review and Intense Testing」）と呼び、作者が出すそれぞれの版を提出（submission）と呼ぶ。レビュアーがrefを取得するとレビュー情報は落ちてくるが、ブランチを取得しても最新の提出のコミットしか落ちてこず、その間の提出のコミットは落ちてこない。Spiritにハッシュは書かれていても、コミットがローカルにないので見ることができない。

作者が選んだ方法は、Gitの既存の動作に頼ることである。コミットを取得すると、まだ持っていない祖先のコミットも一緒に落ちてくる。そこで、カスタムrefがblobではなくコミットを指すようにし、そのコミットに各提出のheadコミットを親として入れた。コミットのツリーにはspirit.jsonというblobが一つあり、実際のレビュー情報はここに入る。レビュアーがSpiritをfetchすると以前の提出のコミットも一緒に落ちてくるので、Spiritがどう変わってきたか、過去のコメントが付けられた時点のコードの状態を見ることができる。

エディタで行うレビュー — HEADとワークツリー、コメントスレッドの構想

READMEが挙げる二つ目の特徴はローカルファーストである。ネットワークが必要なのはレビュー対象をダウンロードするときとレビューをアップロードするときだけで、レビューの過程そのものはオフラインで行われ、既存のツール、とりわけテキストエディタと連携すると書いている。2025年11月の記事は、エディタがすでにレビューに使える機能を持っているという点から出発する。Git HEADとワークツリーのdiffの表示、LSPや言語プラグインによるコードの探索、言語のコメント構文でのメモ書き、コードとテストの実行である。ところがコメントを残すには、エディタを離れてブラウザを開き、同じ場所を探し直してテキストボックスを開かなければならない。これが作者の指摘する隙間である。

Flirtの方式は、interdiffをローカルリポジトリに「マテリアライズ（materialize）」することである。Git HEADがレビュアーの以前レビューしたSpiritの状態を指すようにし、ワークツリーには現在の状態を書き込む。Git連携のあるエディタであれば、何が新しく変わったかをそのまま表示する。2025年11月の記事は、こうすればエディタがjj interdiffと同じものを表示すると書いている。コメントは言語のコメント構文で書き、Flirtがそれを集めて空白とコメント記号を取り除き、バックエンドに送るという構想である。

この方式で解けていなかったのがコメントスレッドである。エディタでインラインにコメントを読み書きするとき、新しいコメントが新しいスレッドなのか既存スレッドへの返信なのかをFlirtが知る方法が必要になる。2026年2月の記事で作者は、既存のスレッドをマーカーで囲み、返信を書く場所を別に設ける案を「現在の計画」として示した。例では、スレッドは// +<3+<3+<3+<3+<3+<3+<3+<3 Flirt thread-ID: ABCXYZという行で始まり、作者と時刻の付いたコメント、返信を書く場所、「全員に対して解決済みにする」と「自分に対してだけ解決済みにする」のチェック欄を経て、thread-endの行で終わる。作者はこの表記がやや冗長で読みにくいと自ら書いている。2026年8月の記事は、コメントスレッドが「基本的に動作する」ようになったと書いている。

同じ記事群に書かれている設計上の決定と構想は次のとおりである。いずれもそれぞれの記事の時点での計画である。

  • スレッドの再配置。 GitHubは、強制プッシュでスレッドが始まったコミットが変わると、スレッドをoutdatedと表示する。スレッドがリポジトリにマテリアライズされていれば、コードの作者は関数を移すときにスレッドも一緒に移すことができ、FlirtがIDで新しい位置を読み取ってSpiritに記録するという構想である。作者は、これに対応できるのはNative Gitバックエンドだけだと書いている。
  • 二つの解決トグル。 GitHubではスレッドの解決状態が全員で共有される。作者は共有用とローカル用のトグルを別々に設けるつもりで、解決表示のないメーリングリストではローカルのトグルだけが残ると書いている。
  • コミット単位のレビュー。 複数パッチからなるSpiritの結合diffへのコメントには対応しない計画である。行範囲へのコメントには対応し、Gerritにある行内の文字範囲へのコメントには対応しない計画である。
  • コミットメッセージへのコメント。 対応するつもりで、これに対応していないGitHubへ送るときは、コミットメッセージを引用した独立コメントとして表現することになりそうだと書いている。
  • 判定。 バックエンドごとに異なる。GitHubはComment・Approve・Request changes、GerritはCode-reviewラベルの-2から+2までのスコア、メーリングリストはReviewed-by・Tested-by・Acked-byといった慣習である。そのためバックエンドごとのカスタム判定が必要になると書いている。
  • 画面。 2025年11月の時点のFlirtは基本機能を見せるためのCLIだった。作者は、主な画面はおそらくTUIになり、中心のロジックはライブラリとして公開されるだろうと書いた。

リポジトリとコミュニティのルール — Rust、AGPL-3.0-or-later、LLMポリシー

リポジトリのCargo.tomlには、パッケージ名flirt、バージョン0.1.0、edition 2024、ライセンスAGPL-3.0-or-laterが書かれている。2025年11月に作者はライセンスを決めておらず、GPLとUnlicenseのどちらにもそれぞれ惹かれると書いていたが、LICENSEファイルは2026年9月30日のコミットで追加された。取得時点のリポジトリ画面はコミット111件、ブランチ2本、タグ0件で、言語の比率はRust 96.9%、Shell 3.1%である。依存関係の一覧にはclap、clap_complete、inquire、jiff、mail-parser、unidiff、serde、serde_json、anyhow、cmd_lib、rand、whichがある。

READMEにインストールやビルドの節はない。「Contributing & Development」の節は、ドキュメントはまだ多くないと書き、Zulipに立ち寄って関心のあることを話すところから始めるよう勧めている。よくある開発作業はtasks/ディレクトリのスクリプトとして定義されており、直接実行するか、simply-runまたはmiseで実行できると書いている。READMEが掲げる指針は三つである。

  • 成果物よりコミュニティ。 最良のコードレビューツールを作ることは、それが何であるかについての共通理解を人々が築いていく過程の副産物にすぎないと書いている。
  • パワーユーザー優先。 アクセシビリティに最適化したレビューツールは数多くあり、Flirtはその一つではないと書いている。アクセシビリティの改善は、パワーユーザーを犠牲にしないかぎり良いことだという立場である。
  • 自由でオープンソースのソフトウェア。 Flirtへの貢献とコミュニティへの参加にプロプライエタリなソフトウェアが必要であってはならない。脚注はその帰結として、Discordは公式のコミュニケーション手段になれず、プロプライエタリなバックエンド（GitHub）やオペレーティングシステム（Windows、Mac）への対応を理由に貢献が止められることはないと書いている。ほかのコントリビューターがベストエフォートで対応することはありうる。

LLMポリシーは、README自身が「かなり厳格な（fairly strict）」と呼んでいる。

  • FlirtのコミュニティスペースにLLMが生成したテキストを載せることは、手を入れたかどうかにかかわらず禁じられている。コード、コミットメッセージ、Issue、PRの説明、IssueやPRへのコメント、ZulipのメッセージはすべてLLMを使わずに書かなければならない。
  • 個人的な文脈での利用はポリシーの対象外である。コードベースの探索、調査、デバッグ、アイデアの検討が例として挙げられており、脚注は、ポリシーが個人的な利用を容認も非難もしないと書いている。
  • 狭い例外がある。生成を意図していなかった（事故だった）こと、そのテキストが特定の改善を行う最良または唯一の方法であること、可能なかぎり自分の頭で再現して「サニタイズ（sanitize）」したこと、の三つを満たす場合である。
  • サニタイズの例としてREADMEは、知らないライブラリ関数の呼び出しをLLMが出してきた場合を挙げる。そのライブラリを使うという発想にどうたどり着くかを考え、関数名を知らないつもりでドキュメントから機能を探し、ドキュメントを読んで自分で結論に至る、という過程を踏むよう求めている。
  • 運用は善意を前提としている。違反が疑われる場合は誤りとみなしてポリシーを思い出させるにとどめ、意図的な違反については原則として永久追放が妥当な帰結だと書いている。

現在の成熟度 — 文書で確認できることとまだないもの

告知、README、開発記録を合わせて現在の状態を分けると次のようになる。

項目 文書で確認できること まだないもの、制約
公開 2026-10-05、Codebergのflirt/flirt、AGPL-3.0-or-later タグ0件、Cargo.tomlのバージョン表記は0.1.0
主要機能 以前レビューしたコミットとその現在の版のinterdiffを検出して表示 信頼性はコミットのメタデータに依存し、作者がJujutsuを使う場合に最も高い
バックエンド Native Git、GitHub、メーリングリスト Forgejoはない。メーリングリストは概念実証で、Native Gitは形式が不安定
ドキュメント README（紹介、指針、LLMポリシー、バックエンド対応） インストールや使い方の案内はなく、ドキュメントはまだ多くないとREADMEが書いている
利用段階 貢献する意図のある人による試用 一般利用の準備はできておらず、準備が整う時期は示されていない
コミュニケーション Zulip LLMで書いたメッセージは認められない

まとめると、Flirtは「強制プッシュされた変更を再レビューするとき何を見せるか」という問いに、change-idとローカル保存で答えようとするツールであり、その答えが届く範囲は今のところ条件付きである。作者がJujutsuを使っているか、バックエンドが何か、レビュアーが以前の提出を同じマシンで見たかによって結果が変わることを、文書自身が書いている。

判断の基準は作者の文言そのままである。まだ一般利用の準備はできておらず、バグと欠けている機能が多く、コントリビューターになるつもりがなければもう少し待つように、ということである。READMEも貢献する意図がある場合だけ試すよう書いている。準備ができたら作者がおそらく別の記事で知らせるとしているので、業務の流れに組み込むかどうかの判断はその記事の後に回すのが作者の勧めに沿う。現時点の公開が向けられている読者は、パッチシリーズワークフローのレビュー問題に共感し、設計の議論やバックエンドの実装に加わろうとする人であり、READMEは関心のある新しいバックエンドへの対応を加えることが貢献を始める良い方法だと書いている。

隣接する話題は別の記事にある。大きな変更を複数層のPRに分けるGitHubのスタックPRはGitHub スタックPR パブリックプレビューで、ターミナルでdiffをレビューするツールHunkはAIエージェントコードレビューHunkで扱っている。スタックPRは変更を分ける方式であり、Flirtは書き換えられたコミットをレビュアーが以前見た状態と比べる方式である。

確認できなかったこと

  • 公開されたコードの実装範囲。 スレッドの再配置、二つの解決トグル、バックエンドごとの判定、コメントスレッドの表記は、以前の記事の計画と構想である。公開されたソースがこれらをどこまで含んでいるかはREADMEに書かれておらず、ソースコードは根拠資料に含めていない。
  • インストール、ビルド、コマンドラインの使い方。 READMEに該当する節がない。GeekNewsが伝えるLobste.rsの議論の要約には、作者がインストール手順を意図的に省いたと答えたという箇所があるが、元のコメントは確認できなかった。
  • 一般利用の準備が整う時期。 告知は、準備ができたら「おそらく」記事を書くとするだけで、日程は示していない。
  • Forgejoバックエンドの着手の有無と日程。 「ToDoリストの次の項目」「いずれできる」という表現以外の根拠はない。
  • 代替ヒューリスティックの実際の内容。 READMEは、change-idヘッダーがなければ代替ヒューリスティックが使われるとしか書いていない。何を基準に対応づけるのか、対応がずれたときに画面でどう現れるのかは文書にない。
  • Git側の変更の現状。 change-idヘッダーの保持を扱うパッチシリーズの経過はREADME脚注の記述に依拠しており、該当のメーリングリストのスレッドは根拠資料に含めていない。
  • 第三者による利用事例と検証。 作者以外の利用報告や、ほかのレビューツールとの比較測定は見つからなかった。
  • 修士論文。 論文本文が公開されているかどうか、どこにあるかは、ブログにもREADMEにも書かれていない。
  • リポジトリの数値の時点。 コミット・ブランチ・タグの数と言語の比率は2026年10月7日の取得時点の画面の値であり、その後変わりうる。
