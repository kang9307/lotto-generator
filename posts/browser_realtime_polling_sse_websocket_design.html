계기 — 「실시간」이라는 단어가 가리는 세 가지 요구

웹 애플리케이션 기획서나 기능 요구사항에 「이 화면은 실시간으로 반영되어야 한다」는 문장이 적혀 있을 때, 개발팀은 곧바로 WebSocket 도입을 떠올리기 쉽다. 하지만 현실의 화면 요구는 단일하지 않다. 협업 문서에서 상대방의 마우스 커서 궤적, 대용량 파일의 인코딩 완료 알림, 고객센터 상담 채팅 메시지는 허용 가능한 지연 시간도 다르고, 일시적으로 통신이 끊겼을 때 복구해야 하는 데이터의 성격도 전혀 다르다.

공학에서 실시간(real-time)은 결과의 논리적 정확성뿐만 아니라 결과가 산출되는 시점(마감 시각, deadline)까지 충족해야 올바른 동작으로 간주하는 개념이다. Carnegie Mellon SEI의 실시간 시스템 분류 기준에 따르면, 시스템은 마감 초과가 초래하는 영향에 따라 세 가지로 나뉜다. 마감을 단 한 번이라도 넘기면 치명적 오류가 되는 하드 실시간(hard real-time), 늦게 도착한 결과의 가치가 완전히 소멸하지만 시스템 전체가 파괴되지는 않는 펌 실시간(firm real-time), 지연될수록 결과의 유용성이 점진적으로 감소하는 소프트 실시간(soft real-time)이다. 브라우저 기반 웹 애플리케이션은 원칙적으로 엄격한 하드 실시간을 보장하기 어려운 비결정론적 환경이며, 대부분 소프트 실시간이나 펌 실시간의 범주에 머문다.

따라서 막연한 「실시간」이라는 단어를 설계 가능한 구체적 요구사항으로 바꾸기 위해서는 다음의 세 가지 질문에 먼저 명확히 답해야 한다.

  • 얼마나 늦어도 되는가 (허용 지연과 달성 비율): 작업 시작부터 화면 반영까지 허용되는 최대 지연 시간과, 이를 어떤 비율(예: 99%의 요청이 2초 이내)로 달성할 것인지 정의한다.
  • 누가 언제 통신을 주도하는가 (방향과 빈도): 서버가 변경을 일방적으로 알리는 형태인지, 클라이언트가 수시로 명령을 전달해야 하는지, 발생 주기가 초당 수십 회인지 수분에 한 번인지 구분한다.
  • 놓친 데이터를 어떻게 되찾을 것인가 (상태 복구 전략): 일시적 단절 후 재접속 시 최신 현재 상태만 조회하면 되는지, 누락된 모든 사건을 순서대로 재생해야 하는지 결정한다.

이 세 가지 축에 따라 최적의 기술 선택과 서버-클라이언트 계약이 완전히 달라진다. 다음 표는 웹에서 사용되는 주요 실시간 통신 방식의 전달 특성과 책임 경계를 요약한 것이다.

지연과 최신성은 다른 요구다 — 브라우저 렌더링 경로의 병목

실시간 시스템을 설계할 때 가장 흔히 범하는 오류는 지연 시간(latency)과 최신성(freshness)을 같은 개념으로 취급하는 것이다. 지연 시간은 특정 사건이 서버에서 확정된 시점부터 클라이언트가 이를 관측하기까지 경과한 물리적 시간이다. 반면 최신성은 클라이언트 화면에 렌더링된 정보가 서버 원본의 현재 상태와 얼마나 일치하는가를 나타내는 정합성 척도다.

예를 들어 네트워크 단절 후 1분간 연결이 끊겨 있던 브라우저가 방금 20밀리초(ms)라는 매우 짧은 왕복 지연으로 최신 패킷을 수신했다고 가정하자. 만약 단절된 1분 동안 발생한 핵심 변경 사항을 서버로부터 이어받지 못했다면, 화면에 표시된 데이터는 비록 방금 도착한 패킷일지라도 전체적으로는 심각하게 낡은 상태다. 반대로 하루 종일 아무런 수정이 발생하지 않은 정적 문서라면, 마지막 동기화 시점이 수 시간 전이라도 화면의 최신성은 100% 온전하다.

서버에서 데이터가 확정되어 브라우저 화면에 픽셀로 그려지기까지는 여러 단계를 거친다.

  • 서버 내부 처리 및 대기 큐: 데이터베이스 트랜잭션 커밋 후 브로커 및 소켓 송신 버퍼에 적재되기까지의 지연이다.
  • 네트워크 전송 및 프록시 버퍼링: 패킷 전송 시간, 라우터 홉, CDN 및 역방향 프록시의 버퍼링 구간이다.
  • 브라우저 네트워크 계층 파싱: TCP 세그먼트 조립, TLS 복호화, 프로토콜 프레임 디코딩 단계다.
  • 자바스크립트 태스크 큐 대기: 브라우저 메인 스레드의 이벤트 루프가 현재 실행 중인 작업을 마칠 때까지의 대기 시간이다.
  • DOM 조작 및 렌더링 파이프라인: 스타일 계산, 레이아웃(Reflow), 페인트(Repaint), 컴포지팅 단계다.

아무리 초저지연 WebSocket 프로토콜을 사용하더라도, 사용자의 브라우저 메인 스레드가 무거운 연산이나 거대한 JSON 파싱 태스크로 차단되어 있다면 이벤트는 제때 처리되지 못한다. 브라우저의 setTimeout(fn, 100)조차 100ms 정밀도를 보장하지 않고 다른 롱 태스크(Long Task)에 의해 수백 밀리초 이상 밀릴 수 있다. 메인 스레드의 부하를 줄이기 위한 구조적 분리 원리는 브라우저 메인 스레드 비용 해설에서 상세히 다룬 바 있다. 전송 계층의 속도만으로 전체 종단 간(End-to-End) 실시간성을 보장할 수는 없다.

폴링과 롱폴링 — 주기적 조회 비용과 응답 대기의 틈

가장 단순한 실시간 흉내내기 방식은 주기적으로 서버에 GET 요청을 보내는 폴링(polling)이다. 폴링은 기존 HTTP 인프라, CDN 캐시, 인증 체계를 그대로 활용할 수 있어 초기 구축이 매우 쉽다. 하지만 고정 주기 Δ(delta)로 폴링을 수행할 때 지연 시간과 서버 부하 사이의 트레이드오프는 수학적으로 명확하다.

서버 측의 데이터 변경이 시간 축 위에 균등하게 분포한다고 가정하고 요청 처리 시간이 충분히 짧다면, 클라이언트가 변경을 인지하기까지 대기하는 시간의 기댓값은 약 Δ / 2가 된다. 지연을 절반으로 줄이려면 폴링 주기를 2배로 단축해야 하며, 이는 클라이언트 수 N에 비례하여 초당 요청 건수(N / Δ)가 정확히 2배로 증가함을 뜻한다. 예를 들어 1만 대의 클라이언트가 5초 주기로 폴링하면 서버는 초당 2,000건의 조회를 감당해야 하며, 변경이 전혀 없는 상태에서도 방대한 네트워크 대역폭과 데이터베이스 I/O가 소모된다.

또한 자바스크립트의 setInterval을 사용해 무작정 폴링 요청을 날리면 재앙이 발생한다. 네트워크 상태가 일시적으로 불안정해져 앞선 요청의 응답이 늦어지면, 이전 요청이 끝나지 않은 상태에서 다음 요청이 연달아 발송된다. 서버 응답이 뒤바뀌어 도착하면 과거의 데이터가 최신 데이터를 덮어쓰는 순서 역전 결함이 발생한다. 이를 방지하려면 반드시 요청 완료 후 다음 주기를 예약하는 직렬화 제어와 지수 백오프(exponential backoff), 무작위 지터(jitter)를 적용해야 한다.

function startPolling({ read, apply, onError }, intervalMs = 5000) {
                      let stopped = false;
                      let timer;
                      let inFlightController;
                      let failures = 0;
                    
                      async function tick() {
                        if (stopped) return;
                        const controller = new AbortController();
                        inFlightController = controller;
                        const timeout = setTimeout(() => controller.abort(), 10000);
                    
                        try {
                          const data = await read(controller.signal);
                          if (stopped) return;
                          apply(data);
                          failures = 0;
                        } catch (err) {
                          if (stopped) return;
                          failures += 1;
                          onError(err);
                        } finally {
                          clearTimeout(timeout);
                          inFlightController = null;
                          if (!stopped) {
                            const backoffCap = Math.min(60000, intervalMs * (2 ** Math.min(failures, 4)));
                            const delay = failures ? backoffCap * (0.5 + Math.random() * 0.5) : intervalMs;
                            timer = setTimeout(tick, delay);
                          }
                        }
                      }
                    
                      void tick();
                      return () => {
                        stopped = true;
                        clearTimeout(timer);
                        inFlightController?.abort();
                      };
                    }

롱폴링(long polling)은 서버가 변경이 발생할 때까지 HTTP 응답을 끝내지 않고 보류(hold)하는 기법이다. 변경이 발생하거나 사전에 정의된 타임아웃(예: 30초)에 도달하면 응답을 보내고, 클라이언트는 응답을 수신하자마자 즉시 다음 대기 요청을 개설한다. 롱폴링은 이벤트 발생 즉시 응답하므로 대기 지연(Δ / 2)을 없앨 수 있다.

그러나 롱폴링에는 치명적인 구조적 틈(gap)이 존재한다. 브라우저가 응답을 수신하고 파싱한 뒤 다음 요청을 서버에 도달시키기까지 수십 밀리초의 물리적 공백이 발생한다. 만약 이 짧은 순간에 서버에서 또 다른 변경이 일어난다면, 연결이 비어 있는 동안 발생한 이벤트는 유실된다. 따라서 롱폴링이 정상 동작하려면 서버가 커서(cursor) 기반으로 최근 이벤트를 메모리나 저장소에 보관하고, 클라이언트가 다음 요청 헤더에 마지막으로 수신한 커서를 실어 보내는 재동기화 프로토콜이 반드시 뒷받침되어야 한다(RFC 6202 참조).

SSE(Server-Sent Events) — HTTP 단방향 스트림과 자동 재연결의 한계

Server-Sent Events(SSE)는 WHATWG HTML 표준에 정의된 기술로, 클라이언트가 단일 HTTP 요청을 보내면 서버가 응답 헤더를 보낸 후 연결을 닫지 않고 text/event-stream 형식의 텍스트 데이터를 지속적으로 푸시하는 방식이다. 브라우저 환경에서는 표준 EventSource 객체를 통해 간단히 연동된다.

SSE의 데이터 전송 포맷은 매우 명료하며 개행 문자( )로 개별 이벤트 경계를 구분한다.

Content-Type: text/event-stream
                    Cache-Control: no-cache
                    Connection: keep-alive
                    
                    id: evt-1001
                    event: order-status
                    retry: 3000
                    data: {"orderId": "ord-881", "status": "completed", "version": 4}
                    
                    : keep-alive heartbeat

SSE가 제공하는 가장 큰 기술적 이점은 브라우저 표준 명세 수준에서 자동 재연결을 보장한다는 점이다. 네트워크 단절이나 일시적 프록시 오류로 스트림이 끊어지면, 브라우저는 retry 필드에 지정된 시간(기본값 약 3초)을 대기한 뒤 서버로 자동 재접속을 시도한다. 이때 브라우저는 이전에 마지막으로 수신한 id 값을 HTTP 요청 헤더인 Last-Event-ID에 자동으로 첨부하여 전송한다. 서버는 이 헤더 값을 읽어 클라이언트가 어디까지 받았는지 확인하고, 보관 중인 이벤트 큐에서 그 이후의 누락분만 연속으로 스트리밍해 줄 수 있다.

그러나 실무 환경에서 SSE를 도입할 때는 다음과 같은 현실적 한계를 반드시 고려해야 한다.

  • 헤더 커스터마이징 불가: 기본 브라우저 EventSource API는 요청 시 임의의 HTTP 헤더(예: Authorization: Bearer ...)를 추가할 수 없다. 쿼리 파라미터로 토큰을 넘기면 웹 서버 로그나 모니터링 시스템에 자격 증명이 노출되는 보안 위험이 따른다.
  • 중간 장비의 응답 버퍼링: Nginx, Envoy, Cloudflare 등 중간 리버스 프록시나 CDN이 응답 버퍼링을 활성화해 두면 서버가 전송한 이벤트가 실시간으로 전달되지 않고 버퍼가 가득 찰 때까지 묶여 지연된다. Nginx의 경우 X-Accel-Buffering: no 헤더 설정이 필요하다.
  • HTTP/1.1 연결 한도: HTTP/1.1 환경에서는 도메인당 동시 연결 수가 6개로 제한되어 여러 브라우저 탭을 열면 연결이 고갈된다. 이 문제는 HTTP/2 멀티플렉싱 환경을 적용해야만 해소된다.
  • 단방향 통신: 클라이언트가 서버로 메시지를 보낼 수 없으므로, 사용자 입력이나 상호작용은 별도의 HTTP POST 요청으로 분리해야 한다.

WebSocket — 전이중 메시징과 애플리케이션 계층의 책임

WebSocket(RFC 6455)은 웹 브라우저와 서버 간에 단일 TCP 연결 위에서 메시지 기반의 전이중(full-duplex) 양방향 통신을 가능하게 하는 프로토콜이다. HTTP 핸드셰이크를 통해 101 Switching Protocols 응답을 주고받은 후 바이너리 또는 텍스트 프레임 계층으로 프로토콜이 승격된다.

클라이언트와 서버가 서로 독립적으로 언제든 통신할 수 있으므로, 협업 화이트보드, 체스 게임, 빠른 주식 호가 주문 등 빈번한 양방향 데이터 교환에 최적이다. 표준 브라우저 API는 이벤트 리스너 등록 방식으로 간결하게 제공된다.

const socket = new WebSocket('wss://example.com/stream');
                    
                    socket.addEventListener('open', () => {
                      socket.send(JSON.stringify({ type: 'subscribe', channel: 'orders' }));
                    });
                    
                    socket.addEventListener('message', (event) => {
                      try {
                        const payload = JSON.parse(event.data);
                        handleMessage(payload);
                      } catch (err) {
                        reportError('Payload parse failure', err);
                      }
                    });
                    
                    socket.addEventListener('close', (event) => {
                      scheduleReconnect(event.code, event.reason);
                    });

하지만 많은 개발자가 간과하는 사실은, 기본 브라우저 WebSocket API에는 자동 재연결 기능이 전혀 없다는 점이다. SSE가 표준 수준에서 처리해 주던 재시도, 지수 백오프, 지터, 세션 복구를 전부 애플리케이션 개발자가 자바스크립트로 직접 구현해야 한다. 또한 다음과 같은 중대한 엔지니어링 책임이 애플리케이션 계층으로 넘어온다.

  • 연결 완료(open)와 구독 완료의 분리: 소켓의 open 이벤트는 TCP 연결과 웹소켓 핸드셰이크가 끝났다는 뜻일 뿐, 서버가 클라이언트의 인증을 검증하고 특정 토픽 구독을 마쳤다는 뜻이 아니다. 서버가 명시적인 구독 승인 ACK 메시지를 회신할 때까지 데이터 준비 완료로 간주해서는 안 된다.
  • 애플리케이션 레벨 하트비트 구축: 프로토콜 차원의 Ping/Pong 제어 프레임이 존재하지만, 브라우저 자바스크립트 API에는 Ping을 임의로 송신할 수 있는 인터페이스가 없다. 따라서 애플리케이션 계층에서 주기적인 ping/pong JSON 메시지를 주고받아 좀비 연결을 감지해야 한다.
  • 수신 백프레셔(Backpressure) 부재: 서버가 브라우저의 처리 속도보다 빠르게 대량의 메시지를 쏟아부을 경우, 브라우저가 수신 속도를 늦추도록 피드백할 표준 백프레셔 API가 없다. 클라이언트 수신 큐가 무한정 팽창하여 메모리가 고갈되거나 브라우저 탭이 얼어붙는 사태를 막으려면 큐 크기 상한 설정과 최신 값 병합(coalescing) 전략이 필요하다.
  • CORS 미적용 및 보안: WebSocket은 일반 브라우저의 교차 출처 리소스 공유(CORS) 프리플라이트 제약을 받지 않는다. 악의적인 사이트에서 사용자의 브라우저를 통해 사내 웹소켓 서버로 무단 연결을 맺는 CSWSH(Cross-Site WebSocket Hijacking)를 방지하기 위해 서버 측에서 반드시 Origin 헤더를 화이트리스트와 엄격히 대조해야 한다.

재연결 이후의 상태 복구 — 스냅샷과 커서 분리

실시간 시스템의 완성도를 결정짓는 핵심은 통신이 정상일 때가 아니라, 통신이 끊겼다가 다시 이어졌을 때 상태를 모순 없이 복원하는 복구(recovery) 메커니즘이다. 단순히 웹소켓을 다시 연결하고 재구독하는 것만으로는 단절 기간 동안 발생한 변경분을 결코 복구할 수 없다.

흔히 사용되는 「재접속 시 REST API로 전체 목록을 조회한 후 웹소켓을 구독한다」는 로직에는 치명적인 경쟁 상태(race condition)가 숨어 있다. 클라이언트가 목록 조회 요청을 보내고 응답을 받아 처리하는 시간과 실시간 이벤트 구독이 서버에 등록되는 시점 사이에 시간적 공백이 발생한다. 이 틈에 일어난 데이터 수정은 조회된 스냅샷에도 없고, 이후 수신되는 이벤트 스트림에도 존재하지 않아 영구 유실된다.

이 문제를 해결하는 정석 설계는 스냅샷과 해당 시점의 커서(cursor)를 원자적으로 함께 반환하는 계약이다. 클라이언트가 스냅샷을 요청하면 서버는 현재 시점의 전체 데이터와 함께 당시의 트랜잭션 위치를 나타내는 커서 C를 넘겨준다. 클라이언트는 웹소켓 또는 SSE 구독을 요청할 때 이 커서 C를 전달하며, 서버는 C 이후에 발생한 이벤트 로그를 순서대로 재생(replay)해 준 뒤 실시간 브로드캐스트로 매끄럽게 전환한다.

이를 위해 시스템에는 각기 다른 역할을 수행하는 식별자(ID)들의 분리가 필수적이다. 다음 표는 상태 복구와 일관성을 위해 시스템이 갖추어야 할 5대 식별자의 역할을 정리한 것이다.

식별자담당 역할보장하는 성질단독 사용 시 한계
이벤트 ID (Event ID)개별 메시지의 고유 식별동일 메시지의 중복 수신 감지 및 중복 배제메시지 간의 시간 순서나 누락 여부는 증명하지 못함
커서 (Cursor)이벤트 스트림 로그 상의 단조 증가 위치단절 이후 어디서부터 이어받아야 하는지 지점 제공엔티티의 현재 최종 상태나 값 자체를 표현하지 못함
엔티티 버전 (Version / Sequence)특정 레코드의 갱신 차수오래된 지연 응답이 최신 화면을 덮어쓰는 사태 방지스트림 전체의 흐름이나 타 엔티티와의 순서는 모름
요청 ID (Request ID)비동기 통신과 원본 요청의 매핑비동기 메시지 응답이 어느 사용자 행위의 결과인지 식별네트워크 단절 시 안전한 재시도를 보장하지 못함
멱등 키 (Idempotency Key)명령의 단 1회 실행 보장응답 유실로 클라이언트가 재전송해도 중복 처리 차단데이터 갱신 후 화면 반영 순서와는 무관함

또한 UI 화면 상태를 단일 불리언 값인 isConnected로만 표현해서는 안 된다. 연결이 열렸더라도 동기화가 진행 중인 동안 사용자가 화면을 온전한 상태로 오인하고 작업을 수행하면 데이터 불일치가 가중된다. 상태 머신은 최소한 연결 끊김, 연결 중, 연결됨(동기화 중), 최신 동기화 완료, 동기화 실패(재시도 필요) 단계로 명확히 분리하여 렌더링에 반영해야 한다.

순서와 재전송을 다르게 다루는 전송 계층 대안

TCP 기반의 WebSocket이나 HTTP/2 SSE는 데이터의 완벽한 순서 보장과 신뢰성 있는 재전송을 제공한다. 하지만 이러한 신뢰성(Reliability)에는 대가가 따른다. 패킷 하나가 유실되면 운영체제 TCP 스택은 손실된 패킷이 재전송되어 도착할 때까지 그 뒤에 이미 도착한 정상 패킷들을 애플리케이션에 넘겨주지 않고 소켓 버퍼에 묶어 둔다. 이를 전송 계층의 Head-of-Line Blocking(HOLB)이라 부른다.

실시간 협업 도구에서 다른 사용자의 마우스 커서 위치 좌표나 화상 통화 중의 실시간 제스처 데이터는 과거의 패킷을 굳이 되찾을 필요가 없다. 2번 좌표 패킷이 유실되었다면 재전송을 기다리느라 3번, 4번 좌표까지 지연시키는 것보다, 2번을 과감히 버리고 최신 4번 좌표를 즉시 화면에 렌더링하는 것이 훨씬 자연스러운 사용자 경험을 제공한다.

이러한 요구를 수용할 수 있는 브라우저 표준 전송 기술로 WebRTC DataChannel과 WebTransport가 존재한다. WebRTC DataChannel은 피어 간 연결 위에서 SCTP 프로토콜을 사용하며, 채널 생성 시 신뢰성과 순서 보장 옵션을 유연하게 끌 수 있다.

const positionChannel = peerConnection.createDataChannel('cursor-positions', {
                      ordered: false,
                      maxRetransmits: 0,
                    });
                    
                    positionChannel.addEventListener('message', (event) => {
                      const { userId, x, y, seq } = JSON.parse(event.data);
                      applyCursorPosition(userId, x, y, seq);
                    });

ordered: false와 maxRetransmits: 0을 설정하면 패킷 손실 시 재전송을 시도하지 않고 즉시 뒤따르는 패킷을 올려보내므로 Head-of-Line Blocking이 완전히 제거된다. 다만 WebRTC는 피어 간 연결을 수립하기 위한 시그널링 서버와 NAT 트래버설을 위한 STUN/TURN 서버 인프라를 직접 운영해야 하는 상당한 비용이 발생한다. 한편 차세대 웹 표준인 WebTransport는 HTTP/3 및 QUIC 위에서 동작하여 브라우저-서버 간에 독립된 다중 스트림과 비신뢰성 데이터그램(Datagram)을 지원하므로, 인프라 지원이 성숙함에 따라 실시간 게임과 스트리밍 분야의 대안으로 자리잡고 있다.

백그라운드 탭과 서비스 워커의 생명주기 제약

브라우저 환경의 실시간 통신은 데스크톱 네이티브 애플리케이션과 근본적으로 다른 실행 환경 제약을 받는다. 사용자가 브라우저 탭을 비활성화하거나 다른 창으로 가릴 경우, 브라우저 엔진은 시스템 자원과 배터리를 절약하기 위해 Page Lifecycle API에 정의된 생명주기 제어에 돌입한다.

백그라운드로 전환된 탭은 자바스크립트 타이머가 초당 1회 이하로 쓰로틀링(Throttling)되거나, 심한 경우 스레드 실행 자체가 동결(Frozen)된다. 모바일 OS 환경에서는 메모리 확보를 위해 비활성 탭의 프로세스를 예고 없이 강제 폐기(Discarded)하기도 한다. 따라서 탭이 열려 있다고 해서 백그라운드에서 실시간 연결이 온전히 유지되고 데이터를 처리할 것이라 기대해서는 안 된다.

  • 페이지 가시성 복귀 감지: 사용자가 탭을 다시 활성화했을 때 document.visibilityState === 'visible' 이벤트를 감지하여 소켓 연결 상태를 즉시 재점검하고 스냅샷 동기화를 트리거해야 한다.
  • 웹 워커(Web Worker)의 한계: 웹 워커에 소켓 연결을 위임하면 메인 스레드의 UI 블로킹은 피할 수 있지만, 운영체제 차원에서 브라우저 탭 자체를 동결시키는 정책까지 우회할 수는 없다.
  • 서비스 워커(Service Worker)는 상시 소켓 서버가 아님: 서비스 워커는 푸시 이벤트나 페치 가로채기 등 특정 트리거가 있을 때만 잠시 깨어나는 이벤트 기반 워커이며, 브라우저가 유휴 시 수시로 종료하므로 상시 WebSocket/SSE 연결을 유지하는 용도로 쓸 수 없다.
  • Push API와 복구 연계: 탭이 완전히 닫힌 상태에서 긴급한 알림은 Push API를 통해 전달할 수 있지만, 푸시는 정시 실행 예약이 아니며 지연 도착할 수 있다. 푸시 알림을 클릭해 페이지로 돌아왔을 때 서버의 최종 상태를 재조회하는 절차가 필수적이다.
  • 다중 탭 연결 공유: 동일 도메인에서 탭마다 소켓을 열면 서버 커넥션이 낭비되므로 BroadcastChannel이나 SharedWorker로 탭 간 통신을 구성해 1개의 연결만 유지하는 패턴이 쓰인다. 그러나 마스터 탭 종료 시 리더 선출, 계정 전환 시 세션 정리 등 복구 상태 머신의 복잡도가 급격히 증가하므로 신중히 도입해야 한다.

실무 검증 — 네트워크 단절과 유실을 모의하는 9가지 시험 시나리오

로컬 개발 환경의 로컬호스트(localhost)에서 소켓이 끊기지 않고 매끄럽게 동작한다고 해서 프로덕션 배포 준비가 끝난 것은 아니다. 실제 인터넷 망에서는 패킷 유실, 통신사 프록시 버퍼링, Wi-Fi와 LTE 간 핸드오버, 사용자 디바이스 절전 등 온갖 장애가 일상적으로 발생한다. 시스템이 결함에 견딜 수 있는지 사전에 검증해야 할 핵심 9가지 시험 시나리오는 다음과 같다.

  • 30초 단절 중 서버 상태 변경: 클라이언트의 네트워크를 의도적으로 30초간 차단한 상태에서 서버 데이터베이스를 변경한 뒤 복구했을 때, 누락된 변경이 빠짐없이 순서대로 반영되거나 최신 스냅샷으로 모순 없이 교체되는지 검증한다.
  • 명령 처리 후 응답 패킷 유실: 클라이언트가 결제나 데이터 생성 명령을 보냈고 서버가 정상 처리했으나 브라우저로 돌아오는 응답이 중간에 유실되었을 때, 클라이언트가 멱등 키(Idempotency Key)를 사용해 안전하게 재시도하여 중복 결제나 이중 생성이 차단되는지 확인한다.
  • 이벤트 중복 및 늦은 HTTP 응답 도착: 네트워크 지연으로 인해 과거 버전의 데이터 응답이 최신 이벤트 스트림보다 늦게 도착했을 때, 엔티티 버전 검사를 통해 구형 데이터가 최신 화면을 덮어쓰지 않는지 검증한다.
  • 메인 스레드 롱 태스크와 대량 이벤트 폭주: 메인 스레드가 무거운 연산으로 3초간 멈춘 사이에 서버로부터 수천 개의 이벤트가 쏟아졌을 때, 메모리 누수 없이 큐 상한 내에서 최신 값으로 정상 합쳐지는지 확인한다.
  • 서버 인스턴스 재시작 및 타 노드 재접속: 로드밸런서 뒤의 특정 웹소켓 서버가 재시작되어 클라이언트가 다른 서버 노드로 재접속했을 때, 분산 캐시나 브로커를 통해 커서와 구독 권한이 일관되게 복원되는지 검증한다.
  • 이벤트 로그 보관 만료를 초과한 장기 단절: 클라이언트가 며칠 만에 탭을 열어 전달한 커서가 서버의 이벤트 보관 주기(TTL)를 초과했을 때, 서버가 조용히 무시하지 않고 복구 불가 에러를 반환하여 클라이언트가 전체 스냅샷으로 깔끔하게 재초기화하는지 확인한다.
  • 탭 전환 및 모바일 기기 절전 복귀: 브라우저 탭을 백그라운드로 내렸다가 10분 뒤 다시 활성화하거나 모바일 화면 잠금을 풀었을 때, 미확인된 과거 상태를 「최신」으로 오표시하지 않고 동기화 중 인디케이터를 거쳐 복구되는지 검증한다.
  • 세션 로그아웃 및 계정 전환: 사용자가 로그아웃하거나 다른 계정으로 전환했을 때, 기존 웹소켓 연결 및 채널 구독이 즉시 파기되어 이전 계정의 민감한 실시간 데이터가 새 세션 화면에 누출되지 않는지 확인한다.
  • 실제 CDN 및 로드밸런서 유휴 타임아웃 경유: 개발 환경이 아닌 실제 상용 CDN, L4/L7 스위치를 통과할 때 버퍼링으로 인한 묶음 수신이나 유휴 시간 초과(idle timeout)로 인한 주기적 연결 끊김이 발생하지 않는지 검증한다.

확인하지 못한 것

  • 클라우드 벤더별 관리형 웹소켓 서비스의 내부 큐잉 사양: AWS API Gateway WebSocket, Cloudflare Workers Durable Objects 등 상용 서버리스 벤더의 세부 버퍼링 임계치는 제공사별로 상이하여 본문에서 수치화하지 못했다.
  • 운영체제별 백그라운드 네트워크 차단 임계 시간: iOS WebKit과 안드로이드 크롬이 화면 꺼짐 상태에서 웹소켓 소켓을 강제 종료하는 정확한 시간 기준은 OS 빌드 및 전력 관리 정책에 따라 달라 단정할 수 없다.
  • WebTransport의 전 세계 주요 CDN 지원 현황: 2026년 기준 WebTransport 표준 지원 범위가 빠르게 변하고 있어 특정 클라우드 네트워크 환경에서의 UDP 통과율은 직접 측정하지 못했다.
  • 대규모 클러스터에서의 분산 커서 샤딩 지연: Kafka나 Redis Streams를 백엔드로 사용할 때 수백만 커넥션 단위에서 파티션 간 커서 오프셋 정합성을 유지하는 세부 벤치마크는 본문 범위에 포함하지 않았다.
