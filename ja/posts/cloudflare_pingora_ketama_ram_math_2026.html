1. PBRとコンシステントハッシュ法：100TBメモリ削減の背景

一般に、大規模な分散リバースプロキシ環境においては、各サーバープロセス内のリソース消費を厳格に管理し、メモリフットプリントを最小限に抑えることが、クラスタ全体の可用性と運用コストを左右する決定的な基盤となる。

Cloudflareの公式エンジニアリングブログによると、同社はペタバイト規模のRAMと数百万のCPUコアを備えた数千台のサーバーを世界中に展開しており、すべてのノードで全サービスを同時に常駐させるアーキテクチャを採用しているため、無駄なメモリ領域を削減することが極めて重要であると説明している。原掲示は、前月にDNSチームがDNSキャッシュメモリの最適化によって100TBの削減を達成したのに続き、今回はプロキシ基盤のコンシステントハッシュ法アルゴリズムを改善したことで、全世界で100TB以上のRAMを追加で回収したと記述している。

この取り組みの発端は、パフォーマンスチームのIvanエンジニアが発行した課題チケットであった。そのチケットには「Excessive memory usage from pingora-ketama in Pingora Backend Router」と記されていた。原掲示によると、Cloudflareの内部負荷分散サービスであるPingora Backend Router（通称PBR）が想定を大幅に上回るメモリを消費しており、特にコンシステントハッシュ法を担うオープンソースライブラリpingora-ketamaに関連するデータ構造がメモリ過多を引き起こしていたという。

原掲示で言及されている根本原因の背景要素は以下の3点に集約される。

  • PBRプロセス内部において、特定の構成下でハッシュリング構造体のメモリフットプリントが最大6GBにまで肥大化していた事実。
  • キャッシュ可能なHTTPリクエストをURLに基づいてデータセンター内の特定単一サーバーへルーティングし、キャッシュの重複を排除するためにコンシステントハッシュ法が不可欠であった事実。
  • コンプライアンス要件や各種機能フラグの組み合わせごとに、メモリ上に多数の独立したハッシュリングを並行して保持しなければならなかった事実。

本稿の解釈では、数千台規模で展開されるエッジサーバーにおいて、単一プロセス内のメタデータが数ギガバイトに膨らむと、クラスタ全体では容易にテラバイト単位のリソース損失に繋がる。原掲示は、統計数学に基づく仮想ノードの削減と、Rustのメモリレイアウトを考慮した構造体パッキングという2つのレバーを組み合わせることで、ノードあたり25%の構造体圧縮と90%のハッシュ点削減を達成し、100TB超のRAM回収を実現したと説明している。

2. コンシステントハッシュ法の基本原理と負荷不均衡の課題

一般に、分散ノードプールに対する単純な剰余（Modulo）ハッシュによるバランシングでは、サーバーの追加や離脱が発生するたびに大部分のキーの配置先が変更され、キャッシュの大規模な喪失を招く。

原掲示によると、コンシステントハッシュ法はサーバーの増減が発生しても大規模な再マッピングを伴わずにタスクを均等に分散できる手法として広く普及している。PBR内部では、URLをキーとしてキャッシュリクエストをサーバーに割り当てるためにこの手法が使われており、データセンターごとに各ファイルの単一コピーのみを保存させ、目的のファイルを確定的に検索できる基盤を提供している。

コンシステントハッシュ法の根幹は、任意の入力値を受け取り、固定の符号なし整数（アルゴリズムに応じて32ビット、64ビット、128ビットなど）を出力するハッシュ関数にある。一般的な技術文献ではこの出力空間を最大値から0へと環状に循環する円形リングとして図示することが多いが、原掲示では議論を直感的に整理するため、32ビットの整数空間を単純な数直線として表現している。

原掲示が示す基本的な割り当てメカニズムは以下の通りである。

  • サーバー群（A、B、C）の識別子（IPアドレスなど）をハッシュ化し、32ビット数直線上に配置する。
  • 各タスクやキャッシュキー（t〜z）も同様にハッシュ化して数直線上に配置する。
  • 各タスクのハッシュ値から左側（または一方向）に最も近い位置にあるサーバーをそのタスクの担当サーバーとして選択し、末端の区間は先頭へと循環（ラップアラウンド）する。

しかし原掲示は、この基本構造には即座に重大な課題が生じると指摘する。ハッシュ値は本質的にランダムな数値であるため、サーバーAがカバーする区間の長さがサーバーBやCよりも著しく広くなってしまうという不均衡が生じる。各サーバーが処理するリクエスト数は数直線上で担当する区間の長さに比例するため、均等な分散を意図しても統計的な偏りが発生してしまうのである。

3. 変動係数（CV）の数式モデルと初期統計分析

原掲示は、各サーバーに割り当てられる区間長のばらつきを定量化するため、統計学における2つの基本指標である期待値（Expected value）と標準偏差（Standard deviation）を導入している。期待値は分布の中心位置を示し、標準偏差はその中心値の周囲に測定値がどれほど密集しているかを示す。

原掲示によれば、N台のサーバーが存在し、各サーバーにつき1つのハッシュ点のみを配置する場合（k=1）、ある1台のサーバーが担当する区間比率の期待値と標準偏差は以下の式で表される。

Exp = 1/N

SD = (1/N)√((N-1)/(N+1))

原掲示は具体的な数値例としてN=100台のサーバー環境を提示する。このとき期待値は Exp = 1/100 = 1% となり、標準偏差は SD = (1/100)√(99/101) ≈ 0.99% と算出される。各サーバーが担当する区間が1%を中心としてその周囲1%前後に分布すると聞くと一見良好に思えるが、原掲示はこの0.99%が「数直線全体の長さに対する割合」であるという落とし穴を警告している。

目標とする区間サイズに対して誤差がどれほどの比率を占めているかを正しく把握するには、標準偏差を期待値で割った相対尺度である変動係数（Coefficient of Variation, CV）を算出しなければならない。原掲示が示した変動係数の数式は以下の通りである。

CV = SD/Exp = √((N-1)/(N+1))

原掲示においてN=100を代入した場合の結果と意味合いは以下の3点にまとめられる。

  • N=100のサーバー群において、変動係数は CV ≈ 99% という極めて大きな値に達する。
  • これは一部のサーバーが本来の期待値の約2倍（99%増）のリクエストを処理して過負荷に陥る可能性を示す。
  • 一方で、他のサーバーはほとんどリクエストを受け取らず、事実上アイドル状態のまま放置される可能性がある。

本稿の解釈では、仮想ノードを持たない初等的なコンシステントハッシュ法は、大規模クラスタにおいて特定ノードのホットスポット障害を日常的に誘発する水準の偏りを含んでいる。したがって、均等な負荷分散を担保するためには、1つの物理サーバーに対して複数のハッシュ点をリング上に投影する拡張が不可欠となる。

4. 仮想ノード増設の落とし穴：収穫逓減

不均衡な負荷分布を解消する伝統的な解決策は、サーバーごとに複数のハッシュ点（仮想ノード）を追加することである。個々の区間には大きな標準偏差が存在しても、多数のランダムな区間を合算すれば大数の法則（Law of large numbers）に従って全体の長さが均等化されるという直感に基づく。

原掲示の筆者は、数学教師の母親を持つ背景に触れつつ、粗い漸近限界や近似式に甘んじることなく、サーバーあたり k 個のハッシュが存在する場合の厳密な統計式を直接導出した。導出された期待値、標準偏差、および変動係数の一般式は以下の通りである。

Exp_k = 1/N

SD_k = √[(k+1)/(N(kN+1)) − 1/N²]

CV_k = SD_k / Exp_k = √((N-1)/(N*k+1))

原掲示は、NGINXのアップストリームハッシュモジュールにおいてノードあたりの基準ハッシュ数が160個に固定されており、Pingoraも同じデフォルト値を採用していることを紹介している。N=100のとき、ハッシュ数をk=1からk=160に増やすと、誤差マージンに相当する変動係数は約99%から約8%へと劇的に低下する。

しかし、原掲示はこの変動係数曲線をプロットした際に「ハッシュ点をひたすら増やせばよい」という思考停止の危険性が浮き彫りになると指摘する。原掲示の核心的な洞察は次の通りである：「each step down in error margin requires (almost) an order of magnitude increase in the number of hashes per server, so adding more hashes yields less and less improvement」。すなわち、誤差率を一段階引き下げるためには、サーバーあたりのハッシュ数をほぼ桁違い（10倍）に増やさなければならないのである。

原掲示が提示するスケーリング上の具体的な課題は以下の3点である。

  • ディスク容量に応じて重み付けを行う構成において、重み係数 w=625 の場合、k = 160 × 625 = 100,000 個ものハッシュ点が単一サーバーに割り当てられる。
  • 原掲示のグラフ解析によると、k=10,000からk=100,000へと追加された最後の90,000個のハッシュがもたらした誤差低減効果は、わずか0.7%にすぎなかった。
  • わずか0.7%の改善を得るためにメモリ消費量を10倍に増大させるという、極端な収穫逓減に直面していた事実。

本稿の計算では、N=100の環境で一般式を計算すると、k=160のときの変動係数は √(99 / (100 * 160 + 1)) = √(99 / 16001) ≈ 7.87% であり、ハッシュ数を10分の1のk=16に減らした場合でも変動係数は √(99 / (100 * 16 + 1)) = √(99 / 1601) ≈ 24.87% である。

5. 32ビット離散空間と誕生日の逆説による衝突限界

原掲示は、美しい数式による予測が成立するのは、ハッシュ空間が無限に連続した実数リングである場合に限られるという現実の制約を暴いている。実際のソフトウェア実装において、ハッシュ関数が出力する値は連続空間ではなく、32ビットの符号なし整数という離散的（Discrete）な有限空間に制限されている。

原掲示は、ハッシュ点の数が膨大になるにつれて、誕生日の逆説（Birthday paradox）によってハッシュ衝突の発生確率が急速に上昇すると説明する。理想的な環境ではすべてのハッシュ点がノードの受け持ち範囲を形成するが、衝突が起きると一部の点が上書きされて破棄され、システムに予測不能なランダム誤差が混入する。

原掲示で検証された32ビット離散ハッシュリングの限界は以下の3点である。

  • 連続リング上ではハッシュ点の増加が均等化に寄与するが、離散32ビット空間では衝突によって一部のノード寄与分が無作為に脱落する。
  • 2048台のサーバーを抱える大規模データセンター環境のシミュレーションにおいて、サーバーあたりのハッシュ数が10,000から100,000に増加した際、逆に実測誤差率が悪化する逆転現象が確認された。
  • 数式上はハッシュ増設で精度が向上するはずが、32ビット空間の衝突によって過剰なハッシュ生成がむしろシステムの精度を損なっていた事実。

原掲示は、この逆説的な事実こそがメモリ削減プロジェクトにとって最大の追い風となったと述べている。32ビット整数の制約により、過剰なハッシュ生成が無意味であるだけでなく有害であるという数学的・実証的根拠が得られたためである。これによりCloudflareは、サーバーあたりに生成していたハッシュ点の数を一挙に 90%削減 する決断を下した。

6. 構造体の圧縮：Rustのアライメント制約と8バイトから6バイトへの移行

ハッシュ点自体を削減する統計的アプローチと並行して、ZaidoonエンジニアはPBRがハッシュリングのノード情報を保持するRustのメモリ構造体そのものをスリム化する手法を着想した。

原掲示によると、PBRで従来使われていたハッシュポイントの構造体は、以下のような8バイトの構成であった。

struct Point {
    hash: u32,
    index: u32,
}

この構造体では、4バイトが32ビットハッシュ値に割り当てられ、残る4バイトが別配列に格納されたサーバー情報を参照するインデックスとして使われていた。Zaidoonエンジニアの着眼点は、単一のPBRインスタンスが同時に管理するサーバー台数が 2^16 ≈ 65k 台を超えることは現実的に考えにくいため、32ビット整数ではなく16ビット整数（u16）で十分に表現できるという点であった。

しかし原掲示は、Rustコンパイラがこれを一筋縄では通してくれないと述べている：「Rust doesn't make it that easy」。単にフィールドの型を `index: u16` に書き換えても、メモリ使用量は1バイトも減少しない。Rustのデータ配置規則（アライメント）により、構造体の全体のサイズはその中で最も大きなフィールド（最も厳格なアライメントを要求する型）の倍数でなければならず、`hash` が4バイトである以上、構造体全体は4の倍数である8バイトにパディングされてしまうからである。

原掲示は、構造体を6バイトへ圧縮するための検討過程を以下のように解説している。

  • コンパイラ属性の `#[repr(packed)]` を使えばパディングを除去できるが、原掲示は非アライン参照による未定義動作の懸念から 「`#[repr(packed)]` is controversial for good reasons」 と言及している。
  • 最も安全でありながら同一のマシンコードへとコンパイルされる手法として、ハッシュとインデックスを生のバイト配列 `[u8; 6]` として保持し、ゲッター関数経由でアクセスする設計を採用した。
  • バイト配列構造体への移行により、各エントリのメモリサイズを正確に8バイトから6バイトへと削減し、ハッシュ配列全体で 25% の省メモリ化を即座に実現した。

原掲示に記載された実際の最適化構造体およびゲッターの実装コードは以下の通りである。

struct Point([u8; 6]);

impl Point {
   fn hash(&self) -> u32 {
	u32::from_ne_bytes(self.0[0..4].try_into().unwrap())
   }

   fn index(&self) -> u16 {
	u16::from_ne_bytes(self.0[4..6].try_into().unwrap())
   }
}

本稿の解釈では、ポイント配列から2バイトのパディングを除去したことは、連続メモリ配置時における不要なメモリ浪費を抑制する直接的な効果をもたらす。

7. 重み付けとリング増殖：機能組み合わせによるメモリ圧迫

原掲示は、サーバーごとのスペック差を吸収するための重み付け処理と、機能ごとの多重リング展開がメモリ消費を急激に増大させていた構造的要因を詳述している。

Cloudflareのインフラではサーバーによってディスク容量が異なるため、ストレージが大きいノードにより多くのリクエストを配分できるようKetamaアルゴリズムが導入されている。原掲示によると、2台のサーバー S_1, S_2 が存在し、S_1 に w 倍の負荷を担わせる場合、割り当てるハッシュ数 H_1 は w * H_2 でなければならない。キャッシュ用途ではディスク容量が重みとなるが、コンピュート重視の業務ではCPUやGPUコア数が重みとして利用される。

しかし、問題は重み付けによるハッシュ増大だけにとどまらなかった。原掲示が明かすメモリ膨張の真の要因は以下の3点である。

  • すべてのサーバーがあらゆるリクエストを処理できるわけではなく、コンプライアンス要件やキャッシュ設定により特定サーバー群のみが対象となるケースが存在した。
  • 単一のリングにハッシュを追加する方式ではこれらの条件分岐に対応できず、機能の組み合わせごとに独立した新しいハッシュリングを生成する必要があった。
  • 機能フラグの掛け合わせにより、原掲示の表現で 2^(handful) = dozens（数十個）もの別個のリングがPBRプロセス内に併存し、メモリ消費が最大6GBに跳ね上がっていた事実。

本稿の解釈では、数十もの独立したハッシュリングがプロセス内に複製される状況下では、単一リング内のエントリサイズとノード数を圧縮しなければ、機能追加に伴うメモリ枯渇を回避することは不可能であったといえる。

8. キャッシュ消失を防ぐ2次元段階的ロールアウト戦略

原掲示は、ハッシュリングの構造を変更する際に直面する最大のリスクとして「オリジンサーバーの溶解（melting origins）」を挙げている。ハッシュリングの構成を変更すると、キャッシュリクエストの転送先サーバーが再配置される。ネットワーク全体で新旧リングを一斉に切り替えてしまうと、全拠点のキャッシュが瞬時に無効化され、オリジンサーバーへ制御不能なトラフィック津波が押し寄せる大惨事を招く。

原掲示が詳述する安全な移行アーキテクチャは、以下の4つの制御要素で構築された。

  • PBRプロセス内部に旧来の大規模なKetamaリングと新設のコンパクトな小型リングの双方を同時に常駐させた点。
  • 社内のマイグレーションフレームワークを用い、リクエストのハッシュ値に基づいてバックエンドを選択することで、リクエスト単位の決定性を維持した点。
  • 異常を検知した際には、PBRバイナリを再デプロイすることなく新規リクエストを旧リングへ瞬時に戻せる明確なロールバック経路を確保した点。
  • 単純な全社パーセンテージ方式ではなく、トラフィック割合と対象データセンター群という2つの次元（two dimensions）を個別に制御して影響範囲を局所化した点。

移行期間中、エンジニアたちはバックエンド選択トレース、リングバージョンカウンタ、PBR接続エラー率、プロセス常駐メモリ、起動時間、キャッシュ動作、オリジントラフィックの推移を監視し続けた。小規模な検証拠点から大規模データセンターへと移行が進み、トラフィックが100%に達した段階で旧リングのコードパスを完全に退役させた。その結果、PBRのメモリ使用量は急降下し、世界規模で100TB以上のRAMが安全に回収された。

9. pingora-ketamaクレートv2の変更点と設計上の示唆

原掲示によると、ブログで解説された最適化の成果はオープンソースの `pingora-ketama` クレートにおいて、Cargo機能フラグの形態で既に一般公開されている。ただし現時点では大々的な告知を行っていない（unadvertised）フラグとして提供されているという。

原掲示が明かしている新旧リングの実装特性は以下の通りである。

  • `v2` リング：6バイトバイト配列による圧縮ストレージ形式、高速化されたソートアルゴリズム、およびノードあたりの基準ハッシュ数を調整できるスケーリング機能を提供する。
  • `v1` リング：従来のpingora-ketamaが長年使用してきたレガシー動作と完全に同一の挙動を維持する。
  • 単一のライブラリ内でv1とv2を同時に稼働させ、リクエストごとの条件に応じて動的に振り分ける運用が可能である。

原掲示の執筆者は、読者への結びのメッセージとして、他社のコンシステントハッシュ法アルゴリズムを単に真似るだけでなく、自社システムにおいて「自明」や「当然」と見なされてきた設計判断を数値と数式を用いて再検証することの重要性を説いている。すべての問題をRust言語だけで解決できるわけではないが、統計数学はどのような技術スタックにおいても普遍的な価値を発揮する強力な武器であると強調している。

10. 確認できなかった事項

  • v2リングで言及された「より高速なソート手法（a faster sorting method）」の具体的なアルゴリズム名や詳細な実装コードは原掲示に開示されていなかった。
