Why One Trailing Slash Changes Everything in rsync

src and src/ are different commands - and with --delete there is no undo

Intro: when yesterday's command gives a different result today

When that sentence comes up around rsync, nine times out of ten it is one slash. Put the two lines side by side.

rsync -a /tmp/src  /tmp/dst/
rsync -a /tmp/src/ /tmp/dst/

The only difference is a single / at the end of the source path. The results diverge like this. The first line creates /tmp/dst/src/ and puts the contents inside it. The second line unpacks the contents directly under /tmp/dst/.

So far this is merely annoying. The problem starts when --delete is on the same line. At that moment the difference between one slash and none stops meaning one extra directory level and starts meaning everything that used to be in the destination directory is gone. rsync has no undo, and deleted files do not pass through any trash can on the way out.

This article nails down the rule, marks exactly where the point of no return sits once --delete is involved, and leaves you with a procedure that takes one second before you press Enter. General rsync coverage — compression, SSH transport, bandwidth limits, resuming partial transfers — lives in Mastering the Linux Rsync Command. This one digs into the single place where accidents happen.

1. The slash does not change the path, it changes what you are moving

The rule itself is one line. A trailing / on the source means copy the contents of this directory. No slash means copy this directory by name.

The manual also states the rule as an equivalence. The two lines below produce completely identical results, right down to how they set the attributes of the destination directory.

rsync -av /src/foo  /dest
rsync -av /src/foo/ /dest/foo

That equivalence is the fastest route to memorising the behaviour. Dropping the slash is the same as appending one more name segment to the destination path. Whenever you are unsure whether to add the slash to the source, picture how the destination path would grow, and the answer appears on its own.

One more detail: the number of slashes does not matter. /tmp/src// behaves exactly like a single trailing slash. That property is not trivia — section 9 uses it directly to build a defense that survives careless variable assignment.

2. All four combinations in one table

Fix the setup first. /tmp/src contains a.txt and sub/b.txt, and /tmp/dst already exists as a directory.

CommandWhat appears at the destinationMeaning
rsync -a /tmp/src /tmp/dst/tmp/dst/src/a.txt
/tmp/dst/src/sub/b.txt		The directory itself
rsync -a /tmp/src /tmp/dst/Same as aboveDestination slash has no effect
rsync -a /tmp/src/ /tmp/dst/tmp/dst/a.txt
/tmp/dst/sub/b.txt		Contents only
rsync -a /tmp/src/ /tmp/dst/Same as aboveDestination slash has no effect

Read it in two directions. Down the column, the destination slash changes nothing. Across the rows, the source slash changes everything. Read the table this way once and your eye will start going to the end of the source path first whenever you type a command.

If the destination directory does not exist yet, rsync creates it — but only one level. If the parent of the destination path is missing entirely, rsync cannot create the directory and stops. When you need intermediate directories created as well, add --mkpath.

3. The one place a destination slash actually matters

In the table above the destination slash did nothing at all. There is exactly one exception: copying a single item to a different name.

For rsync to rename the item it transfers to the last element of the destination path, all three of the following conditions must hold.

  • The transfer list must consist of a single item — one file, or one empty directory
  • The final element of the destination path must not already exist as a directory
  • The destination path must not have been specified with a trailing slash

The third condition is the point of this section. Here is how it splits in practice.

rsync -a a.txt /tmp/dst/b.txt
# -> /tmp/dst/b.txt          the name changes

rsync -a a.txt /tmp/dst/b.txt/
# -> /tmp/dst/b.txt/a.txt    b.txt is treated as a directory

One slash separates save it under this name from save it inside this directory. If a script assembles the destination path from variables and habitually tacks a / on the end, the rename quietly stops working and an unexpected directory appears instead. And this failure produces no error. That is why it usually surfaces days later, when somebody goes looking for a file that is one level deeper than it should be.

Summarised, the destination slash rule is two lines.

  • Syncing a directory — with or without, identical. Writing it is slightly better because it tells the reader the destination is a directory
  • Renaming a single item — do not write it

4. What -a really turns on, and what it does not

-a is not one option, it is a bundle. Precisely, it is -rlptgoD. Knowing what is inside is what lets you see where things leak.

OptionWhat it enablesWhat happens without it
-rRecurse into subdirectoriesDirectories are skipped entirely
-lCopy symlinks as symlinksSymlinks drop out of the transfer list
-pPreserve permissionsPermissions are set fresh from the destination umask
-tPreserve modification timesEverything is retransferred on every run
-gPreserve groupFiles take the destination default group
-oPreserve owner (super-user only)Files are owned by the account running rsync
-DPreserve device and special filesThose entries are dropped

The -t row is the one that bites most often in practice. rsync's default decision rule is: transfer if the size or the modification time differs. If times are not preserved, every file looks new on the next run, and that is the whole explanation behind the classic complaint that a sync retransfers everything every night.

Now the more important half: what is not included.

  • -H — finding and preserving hard links. Not enabled
  • -A — ACLs. Not enabled
  • -X — extended attributes. Not enabled
  • -U access times and -N creation times. Neither is enabled
  • --delete — never included. This is the one that matters
  • One exception worth knowing — when --files-from is used, the -r inside -a is no longer implied

Believing that -a also cleans up causes damage in both directions. If you assume it deletes, stale files pile up on the destination and a deploy becomes a blend of two releases. If you know it does not and reflexively type --delete alongside it, you eventually remove something that had to stay. Memorising the seven letters rlptgoD closes both failure modes at once.

5. What to know before you enable --delete

--delete is an option that destroys data. A command line carrying it must not be treated with the same weight as any other. The manual says so plainly under that entry: the option can be dangerous if used incorrectly, and it is a very good idea to first try a run with --dry-run (-n) to see what files are going to be deleted. Do not run anything from this section directly — read through section 7 first.

Stated precisely, here is what the option does. It deletes files that exist on the receiving side and do not exist on the sending side, limited to the directories actually being synchronised.

The part worth reading closely is the phrase do not exist on the sending side. rsync does not ask why they are missing. A file you deliberately removed from the source, a file that is invisible because you mistyped the path, and a file that is invisible because a mount fell off are all judged identically. That indifference is what generates every scenario in section 6.

A few conditions worth carrying in your head.

  • Deletion requires recursion (-r) or -d to be active. Since -a contains -r, it is usually on already
  • If the sending side detects I/O errors, deletion is disabled automatically. That is a real safeguard, but an empty source is not an I/O error. Do not treat this as your line of defense
  • Files excluded with --exclude are not deleted even when they exist on the destination. To have them removed you must separately enable --delete-excluded
  • On rsync 3 and later, if you do not specify otherwise, deletions happen incrementally during the transfer
OptionWhen and how it deletesWhen to use it
--deleteDefault behaviour (currently during transfer)Ordinary mirroring
--delete-beforeAll deletions before the transfer startsWhen free space on the destination is tight
--delete-during (--del)Incrementally while transferringVery large file counts, to save memory
--delete-delayComputed during, deleted at the endTo reduce the window of inconsistent state
--delete-afterAfter the transfer completesWhen the destination is live and files vanishing mid-run would hurt
--delete-excludedDeletes excluded items tooMaking the destination strictly identical to the source
--max-delete=NStops if it would exceed N deletionsThe seat belt every automated job should wear by default
--backup --backup-dir=DIRMoves instead of deleting or overwritingWhen you want a way back

The last two rows carry most of the value in this table. The six above them are situational preferences; the bottom two are insurance. --backup-dir in particular is the only mechanism that makes an rsync command reversible at all.

6. The path from one slash to lost data

Here is the intended command.

rsync -a --delete /tmp/src/ /tmp/dst/
# make /tmp/dst identical to the contents of /tmp/src

Now one slash goes missing.

rsync -a --delete /tmp/src /tmp/dst/
#                          ^ no slash

What happens, step by step.

  1. The source is interpreted as a single directory named src
  2. The sending side's entire file list becomes src/ and everything beneath it
  3. Every existing entry directly under /tmp/dst now qualifies as a file that does not exist on the sending side
  4. --delete removes all of them
  5. What remains is a single /tmp/dst/src/

The entire previous contents of the destination directory are gone, and in their place sits one copy that is one level too deep. This is the standard shape of an rsync accident. Forgetting the slash on its own is just a common typo; it only reaches this ending when it meets --delete.

6.1 Three other roads to the same ending

When the source is not mounted. If your backup source is an external disk or a network volume and the mount has fallen off, the mount point directory still exists — it is simply empty. rsync reads that as the sending side has no files at all and deletes everything on the destination. Unlike a mistyped path, this case produces no error. It exits successfully. Any automation that records success based on the exit code will file the accident away as a good run.

When a variable is empty. If the line below runs with an empty destination variable, the destination becomes /.

rsync -a --delete "$SRC/" "$DST/"
# DST empty -> the destination is /

What gets deleted needs no further explanation. In the mirror-image case, an empty SRC makes the source / and pushes the entire root filesystem into the destination. That one merely fills a disk until it stops; the other one costs you the machine. If an AI agent or an automation layer assembles shell variables into commands for you, that risk gains another layer — a similar class of accident is covered in the PowerShell variable collision incident.

When a filter is added later. A mirroring job runs fine for months. Someone adds one --exclude. Days later somebody notices the excluded files are still sitting on the destination and switches on --delete-excluded to tidy up. In that instant every file that had been protected until then is removed at once. Only one option was added, but the scope of deletion changed underneath it.

6.2 The point of no return is the Enter key

Put it plainly: rsync has no undo. Files removed by --delete do not pass through a trash can, and when the destination is remote they disappear from that server's filesystem immediately. Once they are gone, the only remaining move is restoring from another backup — and if that backup was the rsync you just ran, there is nothing left.

This is exactly why backups are kept in generations. A single mirror is not a backup. Any arrangement where deleting on the source deletes on the destination will, by definition, replicate your accident faithfully. How to split generations and retention windows is covered in the Complete Cloud Backup Guide and the databasement analysis, and the hardware side of keeping a copy at home is in How to Choose a Home NAS.

7. How to check in one second before you delete

Add -n. That is the whole trick, in three steps.

# 1) Check - run with -n so nothing is modified
rsync -avn --delete /tmp/src/ /tmp/dst/

# 2) Read the output  (how to read it is section 8)

# 3) Recall that line from shell history, delete the single character n
rsync -av --delete /tmp/src/ /tmp/dst/

Step three is the important one. You never retype the paths. The command you verified and the command you execute differ by exactly one character, so there is no room for a typo to appear between checking and running. Typing the command out a second time defeats the entire purpose of the check.

-n makes rsync perform a trial run that changes nothing while producing mostly the same output as a real run. It is worth knowing precisely where the word mostly applies.

  • What you can trust — the output of --itemize-changes (-i) is supposed to be exactly the same on a dry run and on the real run that follows. The item list you see with -ni, and the recorded reason for each item, is what will actually happen
  • What you cannot trust — a dry run does not send the actual file data. So the bytes sent, bytes received, literal data, and matched data statistics all come out too small, and --progress has no effect. Estimating transfer volume or duration from a dry run gives you a wrong number

The short version: trust the answer to what will change, ignore the answer to how long it will take.

One more note before this goes into cron or CI. Any --delete command that lands in automation must have been run by a human with -n at least once. Nothing is more dangerous than a deletion command whose first execution happens inside a scheduler. Nobody is watching, and if it goes wrong it will run again on the next tick.

8. How to read dry run output

With only -v, you get a list of file names. That cannot answer the question why is this file being transferred again. Adding -i answers it.

rsync -ain --delete /tmp/src/ /tmp/dst/

-i prefixes every item with an eleven-character summary. The general format is the string YXcstpoguax, and each position has a fixed meaning.

PositionLetterMeaning
1YType of update being done
2XFile type
3cChecksum (content) differs
4sSize differs
5tModification time differs
6pPermissions differ
7oOwner differs
8gGroup differs
9uReserved (access-time family)
10aACL differs
11xExtended attributes differ

The characters that appear in the first two positions are worth committing to memory on their own.

PositionCharacterMeaning
1st<Being sent to the remote host
1st>Being received on this host
1stcA local change or creation (directory or symlink creation, for example)
1sthThe item is a hard link to another item
1st.The item is not being updated (attributes may still change)
1st*The rest of the area is a message — deletions show up here
2ndfFile
2nddDirectory
2ndLSymlink
2ndDDevice
2ndSSpecial file (named sockets, FIFOs, and so on)

Three rules govern how the attribute columns get filled.

  • A newly created item replaces every letter with a +
  • An identical item replaces the dots with spaces
  • An unknown attribute is shown as ?

8.1 Reading practice

>f+++++++++   receiving a brand new file
>f..t......   content matches, only the modification time is being fixed
>f.st......   size and time differ = the content changed
.d..t......   directory itself unchanged, only its time is being set
cd+++++++++   creating a new directory
*deleting     removing it

The last line matters most. If even one *deleting line appears, stop there and read the whole list. If the count of things about to be removed does not match what you expected, the command is wrong.

Counting works too. The list is often far too long to scan by eye.

rsync -ain --delete /tmp/src/ /tmp/dst/ | grep -c '^\*deleting'

If a job that should print zero prints a three-digit number, you just caught a typo before it cost you anything. Some teams wire exactly this line into their deploy scripts as a pre-flight check, failing the pipeline when the count exceeds a threshold.

9. Seven common mistakes and the defense for each

  1. Missing source slash — the result lands one level deeper, and combined with --delete the destination is emptied. Defense: in scripts, keep the slash out of the variable and always append it at the point of use as "$SRC/". Even if the value already ends in a slash, // behaves like one, so both cases stay safe
  2. The slash tab completion added for you — typing by hand and completing with Tab produce different commands. Defense: after completing, look at the end of the source path once. Especially on any line containing --delete
  3. Believing -a includes --delete — stale files survive and the deploy becomes a mixture. Defense: memorise that -a is exactly the seven letters rlptgoD
  4. An empty destination variable — the destination becomes /. Defense: put set -euo pipefail and : "${DST:?}" at the top of the script. set -u alone will not catch a variable that is defined but empty
  5. An unmounted source — the destination is wiped and no error is raised. Defense: put mountpoint -q in front of rsync, and pair it with --max-delete
  6. Filesystems that cannot preserve times — exFAT and some network shares carry a different timestamp resolution, so everything retransfers every run. Defense: give it tolerance with --modify-window=1. If permission preservation also fails on that target, step down from -a to -rlt or add --no-p --no-g --no-o
  7. Exclude rules colliding with deletion — a file matched by --exclude is not deleted even when it sits on the destination. Not knowing that gives you why is this not being removed; switching on --delete-excluded without knowing gives you why was this removed. Defense: write down in a sentence which of the two you want, then pick the option

Remote paths follow exactly the same rule. The difference between user@backup.example.com:/srv/data and user@backup.example.com:/srv/data/ is identical to the local case; the only new thing is that everything after the colon is a path. Being remote does not relax the rule, and it does make an accident take considerably longer to notice.

10. A script skeleton that marks the point of no return

A line containing --delete deserves different handling from every other line. The skeleton below can be used as is.

#!/usr/bin/env bash
set -euo pipefail

# No trailing slash in the variables. It gets added at the point of use.
SRC=/srv/app/current
DST=/mnt/backup/app

: "${SRC:?source path is empty}"
: "${DST:?destination path is empty}"

mountpoint -q /mnt/backup || { echo "backup volume is not mounted"; exit 1; }

rsync -a --delete \
  --max-delete=100 \
  --backup --backup-dir="/mnt/backup/_trash/$(date +%F)" \
  --log-file=/var/log/app-sync.log \
  "$SRC/" "$DST/"

What each line is actually blocking.

  • set -u — using an undefined variable kills the script on the spot
  • : "${DST:?}" — kills it when the variable is an empty string as well. This plugs the gap that set -u leaves open
  • mountpoint -q — closes the quietest accident path there is, the mount that fell off
  • --max-delete=100 — if it is about to remove more than expected, rsync stops itself. Pick the number by looking at how many deletions this job normally produces
  • --backup-dir — files that would be deleted or overwritten are moved into that directory instead of vanishing. This is the only thing that leaves you a way back
  • --log-file — lets you find out later what was deleted. It is evidence you cannot create after the fact
  • "$SRC/" — no slash in the variable, appended at the point of use. The defense from item 1 of section 9 lives right here

Add two human procedures on top of that.

  • Every newly written rsync line gets run once with -n. No exceptions
  • If you use --backup-dir, decide the rotation schedule for that directory at the same time. Otherwise the backup volume fills up before anything else does

11. What was not verified by running it

Everything this article could not confirm by execution, collected in one place.

  • The output in the code blocks. The output shapes shown here follow the format specified in rsync's documentation. They were not captured from a run in the environment where this was written, because rsync was not installed there
  • Accordingly, every option combination here should be read as something to confirm once with -n in your own environment. The tables describe documented behaviour, and details can differ by distribution, version, and filesystem
  • Version differences. --mkpath is a relatively recent addition, and deletion working with -d alone dates from rsync 2.6.7 onward. On older machines the same command can behave differently
  • How many levels of destination path rsync will create when it does not exist, and the exact wording of the error at that point, were not verified. The one-level limit is documented; the message text varies by version
  • Timestamp resolution on exFAT and network shares. The full-retransfer symptom is a widely known pattern, but which mount options produce how many seconds of skew is outside what was checked here
  • The exit code when --max-delete hits its ceiling. If you intend to branch on that value in automation, measure it yourself on your own version

Frequently asked questions

Q. What exactly is the difference between src and src/?

A trailing slash on the source means the contents of this directory; without it the meaning is this directory by name. So rsync -a /tmp/src /tmp/dst creates /tmp/dst/src/, while rsync -a /tmp/src/ /tmp/dst unpacks directly under /tmp/dst. Remember it as: dropping the slash is the same as appending one more name segment to the destination path.

Q. Should I add a trailing slash to the destination too?

For the ordinary case of syncing a directory, the result is the same either way. The exception is copying a single item to a different name. That requires the transfer list to be a single item, the final element of the destination path to not already exist as a directory, and the destination path to carry no trailing slash. Break any one of them and the rename silently does not happen.

Q. Does -a delete old files that exist only on the destination?

No. -a is the seven-letter bundle -rlptgoD and deletion is not part of it. It also does not enable hard links, ACLs, extended attributes, access times, or creation times. To make the destination identical to the source you must enable --delete explicitly, and the moment you do, that command changes character.

Q. How do I test --delete safely?

Run it with -n first. Three steps: run rsync -avn --delete and read the output, verify that the number and identity of the lines marked for deletion match what you expected, then recall that line from shell history and delete the single character n. Add --max-delete for a ceiling and --backup-dir for a way back and the defense becomes three layers deep.

Q. Is dry run output identical to a real run?

Part of it is. The output of --itemize-changes is supposed to be exactly the same on a dry run and the real run that follows, so you can trust the answer to what will change. But a dry run does not send the actual data, so transfer statistics come out too small and --progress has no effect. Do not trust the answer to how long it will take.

Conclusion: three things to change today

First, look at the end of the source path before anything else. When you read an rsync command, the first place your eye should land is not the options but the final character of the source path. Slash means contents, no slash means the directory itself. That single glance prevents the overwhelming majority of accidents.

Second, keep the slash out of variables and append it at the point of use. Set SRC=/srv/app and write "$SRC/" when you use it. Because the result is identical even when the value already ends in a slash, the meaning of the command does not wobble depending on who on the team assigned it.

Third, never run a line containing --delete for the first time without -n. Check it, recall it from history, delete one character. Layer --max-delete and --backup-dir on top and the tool will catch you once more even when the human slips.

One closing thought. The subject of this article looks like a slash, but the real subject is how you handle commands that cannot be taken back. rsync offers exactly that kind of command in an extremely short and extremely easy-to-type form. Short means convenient; it does not mean safe. The more convenient a tool is, the more the safeguards have to live outside the tool — in the script skeleton and in the habits of your fingers.
