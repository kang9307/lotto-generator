본 글은 AI 코딩 제품 Nuanced의 개발자이자 전 GitHub 시니어 엔지니어인 Ayman Nadeem이 공개한 기술 회고 「Plan mode is dead」의 원문 서술을 바탕으로 작성되었다. 원문에서 직접 확인된 경험적 관찰과 저자의 판단을 중심축으로 다루며, 확인되지 않은 정량적 지표나 특정 상용 제품에 대한 자의적 평가를 배제한다.

1. 계획 중심 코딩 앱의 등장과 회고의 출발점

인공지능 코딩 도구가 발전하면서 소프트웨어 엔지니어링 환경에는 새로운 형태의 인지적 혼란이 나타나기 시작했다. 거대언어모델이 단 몇 분 만에 수천 줄의 코드를 작성해 내는 시대가 도래하자, 개발자는 자신이 무엇을 왜 만들고 있는지 충분히 숙고하기도 전에 방대한 유지보수 부담을 떠안게 되었다. 기계가 코드를 생성하는 속도가 인간이 그 변경 사항을 검토하고 이해하는 속도를 압도하면서, 아키텍처의 경계선이 무너지고 잘못된 가정이 코드베이스 깊숙한 곳에 조기에 굳어지는 부작용이 빈번해졌다.

이러한 문제의식을 바탕으로 계획(Planning)이라는 단계를 개발의 중심에 세우려 했던 시도가 있었다. 전 GitHub 시니어 엔지니어이자 AI 코딩 도구 Nuanced를 만든 Ayman Nadeem은 이 아이디어에 대한 강한 확신을 품고 제품을 설계했다. 저자는 원문에서 "My belief in this idea was so strong that I built and launched an entire desktop coding app around it."라고 당시의 시도를 회고했다. 모델의 코드 생성 속도와 작업량은 폭발적으로 증가했지만, 이처럼 새로운 작업 속도를 뒷받침해야 할 사용자 인터페이스는 과거의 방식에 머물러 있다는 관찰이 Nuanced의 출발점이었다. 저자는 Claude Code CLI에서 Conductor로, 그리고 출시된 Codex로 도구를 옮겨 다니며 계획을 공들여 다듬었지만 그 계획을 반복해 고쳐 나갈 뚜렷한 자리가 없었고, 대화에서 계획 조각을 새 메시지로 복사해 붙여 넣으며 고쳐야 했던 불편을 적는다. 계획에 자리를 마련해 주고 싶었다는 이 불편이 Nuanced를 만든 동기였다.

그러나 직접 데스크톱 앱을 구축하고 출시한 끝에 저자가 마주한 결론은 예상과 달랐다. 저자는 자신이 시도했던 계획 중심의 접근이 실패했다고 솔직하게 털어놓았다. 그러면서 그 실패는 동시에 더 넓은 관점에서 기존의 「계획 모드(Plan mode)」라는 추상화가 더 이상 유용하지 않다는 점을 명확히 드러내 주었다고 적었다. 원문의 문장은 다음과 같다: "Nuanced's approach to planning failed, but it also revealed to me how plan modes more broadly aren't as useful anymore."

여기서 중요한 점은 「계획 모드는 죽었다」는 도발적인 선언이 계획을 세우는 엔지니어링 행위 자체를 부정하는 뜻이 아니라는 사실이다. 저자가 문제 삼은 대상은 「계획 모드」라는 경직된 사용자 인터페이스 추상화와, 그 안에서 생산되는 방대한 분량의 AI 생성 계획 문서였다. 루프 안에서 소프트웨어를 구축하는 과정에서는 여전히 엄청난 양의 계획 행위가 일어나고 있지만, 그것이 굳이 「계획(the plan)」이라는 이름의 거대한 문서 형태로 존재할 필요는 없다는 것이 회고의 핵심이다.

  • AI의 빠른 코드 생성 속도와 인간의 검토 속도 사이에서 발생하는 인지적 불일치 문제 인식
  • 소프트웨어 설계와 가정을 사전에 정렬하기 위해 계획 단계를 전면에 내세운 데스크톱 코딩 앱 Nuanced의 개발
  • 실제 제품 운영 결과 확인된 계획 모드 접근의 한계와 그에 따른 저자 자신의 실패 인정
  • 부정의 대상이 「계획하는 행위」가 아니라 「계획 모드라는 UI 추상화와 거대한 문서 산출물」이라는 점의 확인

2. 계획 모드가 가졌던 두 가지 역사적 목적

저자는 에이전트 기반 코딩 환경에서 계획 모드가 역사적으로 해결하고자 했던 과제를 두 가지 독립적인 축으로 분류했다. 이 두 목적을 분리해서 바라보지 않으면 오늘날 계획 모드가 겪고 있는 혼란의 본질을 정확히 짚어낼 수 없다.

원문에서 저자는 계획 모드의 역사적 목적을 명확히 정의했다: "Historically, plan modes served two purposes: (1) they specified instructions that were sufficiently precise enough for an agent, and (2) they helped humans understand what they were building." 하나는 에이전트의 실행 정확도를 높이기 위한 기술적 지시서로서의 역할이고, 다른 하나는 인간 개발자가 복잡한 시스템의 청사진을 머릿속에 그릴 수 있도록 돕는 인지적 도구로서의 역할이다.

계획 모드의 역사적 목적 저자의 판단 원문 근거 인용
목적 1: 에이전트를 위한 정밀한 지시 지정 모델 성능 향상으로 빠르게 낡아 가고 있음 "I think #1 is rapidly becoming obsolete as models get better."
목적 2: 인간 개발자의 시스템 이해 지원 그 어느 때보다 중요하지만 계획 모드는 부적합한 추상화 "I think #2 matters more than ever, but plan modes are the wrong abstraction for it"

2.1 에이전트를 위한 정밀 지시의 노후화

초기 세대의 AI 모델이나 초기 코딩 에이전트를 사용할 때, 개발자는 모호한 자연어 지시만으로는 원하는 결과를 얻기 어려웠다. 모델이 맥락을 놓치거나 엉뚱한 가정을 사실로 받아들여 코드를 망가뜨리는 일이 잦았기 때문에, 실행에 들어가기 전에 아주 촘촘한 세부 단계와 파일 목록, 함수 시그니처를 담은 계획서를 먼저 작성하도록 강제하는 것이 효과적인 방어 수단이었다. 계획 문서는 에이전트가 탈선하지 않도록 잡아 주는 일종의 엄격한 가이드레일 구실을 했다.

그러나 프런티어 모델들의 추론 능력이 비약적으로 발전하면서 상황이 달라졌다. 현대의 모델들은 사용자의 간결한 프롬프트 속에서도 복잡한 의도를 맥락적으로 파악하고, 누락된 세부 사항을 지능적으로 보충하며, 자체적인 검증 도구를 호출해 오류를 스스로 바로잡는 수준에 도달했다. 이에 따라 에이전트에게 한 단계씩 떠먹여 주듯 정밀한 지침을 사전 명세서로 내려줄 필요성이 급격히 줄어들었다. 목적 1이 기술적 발전의 결과로 점차 그 가치를 잃어가고 있는 것이다.

2.2 시스템을 파악하려는 사람의 이해 수요

반면 두 번째 목적인 「인간이 무엇을 만들고 있는지 이해하는 것」은 오히려 그 중요성이 과거 어느 때보다 커졌다. 에이전트가 혼자서 코드를 수백 줄씩 쏟아내고 여러 파일의 의존성을 한 번에 수정할 수 있게 되었다. 저자는 Conductor와 Codex 같은 코딩 앱으로 더 많은 에이전트를 병렬로 돌릴 수 있게 되면서 정신적으로 단절되고 좀비 같은(zombie-like) 느낌을 받았다고 쓴다.

저자는 이 이해의 문제가 소프트웨어 공학에서 영원히 유효할 본질적인 질문이라고 보았다. 기계가 인간이 변경점을 검토할 수 있는 속도보다 더 빠르게 시스템을 수정하고 있을 때, 인간은 어떻게 소프트웨어 시스템에 대한 일관된 멘탈 모델을 유지할 수 있는가 하는 질문이다. 그러나 저자는 계획 모드라는 기존의 인터페이스가 이 문제를 해결하기에는 근본적으로 잘못된 추상화라고 결론지었다.

3. Nuanced가 마주한 실패의 네 가지 원인

저자는 기존 도구의 빈틈에 대한 생각 자체가 틀렸다기보다, 자신들의 구현이 기대한 해법을 내놓지 못했다고 본다. 그리고 그 이유를 원문에서 네 가지 명제로 정리했다: "I conflated planning with a plan / models got really good / no one wants to read AI-generated text / we separated planning from building in a way that was disruptive".

첫째, 계획하는 행위(Planning)와 산출물로서의 계획(Plan)을 혼동했다. 소프트웨어 엔지니어링에서 중요한 것은 무엇을 왜 만드는지 치열하게 생각하고, 다양한 아키텍처 결정을 평가하는 사고의 과정이다. 하지만 Nuanced는 그 사고의 과정을 정적인 텍스트 문서라는 결과물로 치환해 버리는 실수를 저질렀다.

둘째, 모델의 역량이 너무 빠르게 좋아졌다. 앞서 살펴본 바와 같이 모델 자체가 맥락을 능숙하게 다루게 되면서, 에이전트에게 잘 숙고된 결과를 내라고 명시적으로 지시할 필요가 크게 줄었다("had shrunk").

셋째, 아무도 AI가 생성한 방대한 텍스트를 읽고 싶어 하지 않았다. 저자는 초기 사용자들이 생성된 명세에 대해 놀라울 정도로 관심이 적었다고 증언했다("But early users had surprisingly little appetite for that spec."). 사용자뿐만 아니라 개발자인 저자 자신조차 AI가 화면 가득 출력해 낸 긴 명세를 읽으려 할 때 눈의 초점이 흐려지는 경험("My eyes kept glazing over.")을 반복했다. 이 문제를 해결하기 위해 명세의 중요한 부분을 짚어 주는 기능(Spec Tour)을 덧붙여 보았지만, 이는 시스템에 또 다른 복잡성의 층위만 얹어 주는 결과로 이어졌다("But that only bolted on an additional layer of complexity").

넷째, 계획과 구현을 분리한 방식 자체가 개발의 흐름을 파괴적(disruptive)으로 단절시켰다. 사용자가 「계획 모드」와 「빌드 모드」라는 두 가지 분리된 상태를 인지하고 수동으로 오가야 한다는 사실 자체가 인지 부담을 늘렸다. 저자는 이러한 구분이 인간이 직접 버튼을 눌러 전환할 것이 아니라, AI가 이미 확보한 풍부한 맥락을 바탕으로 스스로 알아서 판단해야 할 영역이라고 느꼈다("This felt like the kind of distinction AI should make for you based on context it already has").

  • 사고의 연속적 흐름인 계획 행위를 정적 아티팩트인 계획 문서로 고정해 버린 개념적 혼동
  • 프런티어 모델의 비약적 발전으로 인해 에이전트용 지침서로서 명세가 갖던 실용적 가치가 빠르게 줄어듦
  • 장황하고 정형화된 AI 생성 텍스트를 읽는 과정에서 인간 개발자가 겪는 극심한 피로감과 회피 성향
  • 계획 모드와 실행 모드를 인위적으로 분리함으로써 발생한 작업 맥락의 단절과 도구 조작 부담

4. 선형 명세 파이프라인과 순환적 탐색 루프의 대조

Nuanced가 초기에 구축했던 워크플로는 전형적인 폭포수식 선형 파이프라인이었다. 에이전트와 대화를 나눈 뒤 모호한 점을 해소하고, 거대한 명세를 생성하여 검토한 뒤 승인을 거쳐 구현으로 들어가는 방식이다. 반면 실제 현장에서 더 자연스럽고 강력하게 작동한 것은 단순한 대화 인터페이스를 기반으로 필요에 따라 계획을 세우는 점진적 탐색 루프였다.

저자는 원문에서 자신이 초기에 구현했던 파이프라인과, 에이전트가 나아지면서 가능해진 다른 루프를 원문 표기 그대로 대비시켰다. 이 두 흐름의 차이는 소프트웨어를 바라보는 철학의 차이를 반영한다.

흐름 구분 단계별 진행 순서 (원문 표기 그대로) 사람이 개입하는 지점 (원문 기준)
Nuanced의 선형 흐름 chat → disambiguate by answering questions → generate spec → review spec → revise spec → approve → implement → review code 질문 답변, 명세 검토 및 수정 승인, 최종 코드 리뷰
새로운 순환 루프 understand → act → inspect → clarify → adjust → act again 원문은 이 루프에서 사람의 개입 지점을 따로 적지 않는다(에이전트가 스스로 검사·수정할 수 있게 되며 가능해진 루프로 설명)

4.1 Nuanced가 채택했던 8단계 선형 구조

Nuanced의 선형 모델은 완벽한 사전 계획을 전제로 설계되었다. 개발자가 대화(chat)를 시작하면 시스템은 질문을 던져 모호성을 제거(disambiguate by answering questions)하고, 이를 바탕으로 완전한 명세를 자동 생성(generate spec)했다. 개발자는 생성된 명세를 읽고 검토(review spec)하며 필요 시 수정(revise spec)한 뒤 승인(approve)해야만 비로소 에이전트가 구현(implement) 단계로 넘어갈 수 있었다. 마지막은 작성된 코드의 리뷰(review code)였다.

이 선형 구조의 치명적인 약점은 구현에 착수하기 전까지 실제 시스템의 동작을 전혀 체감할 수 없다는 점이었다. 소프트웨어 개발의 요구사항은 대부분 코드가 실제로 돌아가고 인터페이스가 화면에 렌더링되는 것을 눈으로 확인하는 순간 비로소 명확해진다. 원문은 인터페이스가 구현을 시작하려면 사용자에게 섣불리 「생각을 끝내라」고 강요했고, 구현이 시작되면 앞 단계의 대화로 돌아가는 것이 워크플로에서 뒤로 가는 느낌이었다고 적는다("There was no going back up the waterfall.").

4.2 대화와 조정을 결합한 6단계 순환 루프

반면 원문은 Codex가 현재 작동하는 방식에서 계획과 실행의 경계가 사라지고 있다고 보고, 에이전트가 스스로 행동하고 결과를 검사한 뒤 접근을 고치는 데 능숙해지면서 다른 루프가 가능해졌다고 설명한다. 먼저 상황을 이해(understand)하고, 행동하며(act), 그 결과를 검사(inspect)한다. 검사 결과 의도와 다른 부분이 드러나면 다시 요구사항을 명확히 하고(clarify), 방향을 조정(adjust)한 뒤, 다시 새로운 행동으로 나아간다(act again).

원문은 이렇게 적는다: "There is still an enormous amount of planning happening inside that loop, but it doesn't necessarily need to appear as a document called “the plan”." 즉 이 순환 루프 안에서도 수많은 계획 행위가 끊임없이 일어난다. 다만 그 계획은 한 번 쓰이고 버려지는 무거운 독립 문서의 형태를 취하지 않는다. 대화의 맥락 속에서 자연스럽게 교환되고, 코드의 변경점 속에 녹아들며, 필요에 따라 즉석에서 다듬어진다. 저자는 기본값으로서가 아니라 필요에 따라 유연하게 계획을 세울 수 있는 대화 인터페이스의 단순함이야말로 실제로 훌륭한 작업 방식이었다고 밝혔다("the simplicity of a chat interface where planning was done as-needed rather than by default, was actually pretty great.").

# 기존 선형 명세 파이프라인
chat → disambiguate by answering questions → generate spec → review spec → revise spec → approve → implement → review code

# 순환적 탐색 루프
understand → act → inspect → clarify → adjust → act again

5. 가장 큰 실수 — 이해의 과정을 산출물 문서로 치환한 것

Ayman Nadeem의 회고록에서 가장 울림이 크고 중심이 되는 문장은 자신의 가장 큰 실수를 고백한 대목이다. 저자는 자신이 저지른 치명적 착오를 다음과 같이 분명하게 요약했다: "I think the biggest mistake I made was turning the plan into an artifact instead of designing a process for improved human understanding."

이 문장은 AI 에이전트 시대의 도구 개발자들이 빠지기 쉬운 핵심 함정을 정면으로 찌른다. 인간 개발자에게 진정으로 필요했던 것은 복잡한 시스템을 머릿속에서 놓치지 않고 통제할 수 있도록 돕는 「이해의 프로세스」였다. 그러나 제품을 설계하는 과정에서 그 본질적인 목표는 잊히고, 그 자리를 그럴듯하게 포장된 「계획이라는 산출물 문서」가 대신 차지해 버렸다.

원문이 드는 이유는 구체적이다. AI 생성 텍스트는 그 호흡과 과하게 구조화된 성격 때문에 읽기가 매우 어렵다는 것이다("There's something about the pacing and overly structured nature of AI-generated text that makes it very difficult to read."). 또 원문은 대화에서 결정을 풀어 가는 편이 더 직관적이지만, 시스템이 바뀔 때 그 이해를 최신으로 유지하는 것은 아직 풀리지 않은 문제라고 적는다.

저자는 계획 모드라는 이름의 산출물 중심 접근이 사라져야 한다고 말하면서도, 사고의 가치는 결코 줄어들지 않았음을 누차 강조했다. "Thinking through what to build, why it matters, and evaluating decisions remains important. People need to build a coherent mental model of what's going on, but I don't think a large body of AI-generated text is the right interface for that." 무엇을 만들지, 그것이 왜 중요한지 치열하게 고민하고 결정을 평가하는 일은 소프트웨어 공학의 심장으로 남아 있다. 사람은 무슨 일이 일어나고 있는지에 대한 일관된 멘탈 모델을 세워야 하지만, AI가 토해낸 방대한 텍스트 뭉치는 그 사고를 위한 올바른 인터페이스가 아니라는 뜻이다.

  • 인간의 인지적 통제력을 높이는 프로세스 설계 대신 정적인 텍스트 문서 생산에 집중한 설계상의 오류
  • AI 생성 텍스트의 호흡과 과한 구조 때문에 생기는 읽기 어려움, 그리고 시스템이 바뀔 때 이해를 최신으로 유지하는 문제는 아직 미해결
  • 무엇을 왜 만드는지 평가하는 엔지니어링의 본질적 사고 행위는 여전히 필수적이라는 점의 확인
  • 방대한 AI 텍스트 덩어리가 인간의 직관적 시스템 파악을 방해하는 부적합한 인터페이스라는 결론

6. 수백 개 에이전트 시대의 미해결 과제와 사람의 주의

기존의 계획 모드가 해답이 아니라는 점이 드러났다고 해서, 인간의 시스템 이해 문제가 해결된 것은 결코 아니다. 저자는 도구의 발전 속도 뒤편에 여전히 풀리지 않은 거대한 숙제가 남아 있다고 지적했다. 원문의 문장은 다음과 같다: "We still haven't solved how to help people stay oriented as hundreds of increasingly capable agents change a system at once."

에이전트 한두 개가 보조적인 스크립트를 작성해 주던 시기를 지나, 성능이 대폭 향상된 수십, 수백 개의 에이전트가 동시에 백엔드와 프론트엔드, 인프라 구성을 병렬로 수정해 나가는 환경이 열리고 있다. 이처럼 시스템의 모든 구석이 기계에 의해 동시다발적으로 재편될 때, 인간 개발자가 전체 시스템의 방향 감각을 잃지 않고 중심을 잡을 수 있도록 지원하는 방법은 아직 풀지 못했다고 저자는 적는다.

이 미해결 과제 앞에서 에이전트가 수행해야 할 진정한 역할에 대해 저자는 명확한 방향성을 제시했다. 에이전트가 할 일은 수십 페이지에 달하는 장황한 계획 문서를 쏟아내는 것이 아니다. 저자는 원문에서 에이전트의 역할을 이렇게 규정했다: "Agents need to identify the fewest places where human attention can have the greatest impact and surface enough context to make that attention useful."

인간의 주의력은 언제나 희소한 자원이다. 반면 기계의 코드 생성 역량은 사실상 무한대로 확장되고 있다. 따라서 지능적인 에이전트라면 인간의 귀중한 주의력이 가장 강력한 영향을 미칠 수 있는 최소한의 지점을 정확히 찾아내야 한다. 그리고 인간이 그 자리에서 올바른 의사결정을 내릴 수 있도록 딱 필요한 만큼의 맥락만을 간결하게 수면 위로 끌어올려 주어야 한다. 장황한 계획 모드가 아닌, 주의력의 레버리지를 극대화하는 새로운 형태의 상호작용 디자인이 요구되는 시점이다.

  • 수백 개의 유능한 에이전트가 동시에 시스템을 변경할 때 인간의 인지적 방향 감각 상실 위험 증대
  • 텍스트 생성 중심의 접근이 인간의 멘탈 모델 붕괴 문제를 해결하지 못했다는 현실 인식
  • 인간의 제한된 주의력이 가장 큰 임팩트를 낼 수 있는 최소한의 핵심 지점을 식별하는 에이전트의 과제
  • 불필요한 노이즈를 걷어내고 의사결정에 직결되는 맥락만을 정밀하게 표면화하는 인터페이스의 필요성

7. 명세 파일 고정론과의 관계 — 충돌이 아닌 전제의 차이

아래 구분은 이 글의 해석이다. Ayman Nadeem의 이번 회고는 소프트웨어 엔지니어링 진영에서 최근 활발하게 논의되고 있는 스펙 주도 개발(Spec-Driven Development) 논의와 겉보기에 정반대의 주장을 펴는 것처럼 비칠 수 있다. 예컨대 대화창의 맥락이 증발하는 문제를 해결하기 위해 proposal과 design 문서를 명시적인 파일로 저장소에 고정하자는 OpenSpec 프레임워크 분석이나, 코드를 작성하기 전에 엄격한 불변식을 수학적으로 검증해야 한다는 TLA+ 기반의 명세 우선 개발론, 그리고 에이전트의 관측 가능한 행동 규약을 문서로 정의하는 에이전트 행동 명세 분석은 모두 「명세를 문서화하여 고정하라」는 원칙을 강조하기 때문이다.

그러나 두 입장의 차이를 「스펙을 써야 하는가, 쓰지 말아야 하는가」라는 이분법적 대결 구도로 해석하는 것은 본질을 왜곡하는 시각이다. 이는 충돌이 아니라, 각 방법론이 해결하고자 하는 대상과 전제 조건이 서로 다르기 때문에 발생하는 관점의 차이로 이해하는 것이 타당하다.

OpenSpec과 같은 명세 고정 방식은 팀 단위의 협업, 서로 다른 시점에 투입되는 여러 에이전트 간의 규약 공유, 그리고 커밋 이력에 설계 결정의 근거를 영구적으로 남기는 데 초점을 맞춘다. 즉, 시스템의 상태를 외부화하여 다른 인간과 다른 기계가 동일한 지면을 바라보게 만드는 아티팩트로서의 가치를 지향한다.

반면 Ayman Nadeem의 실패 회고는 병렬로 돌리는 에이전트가 늘어날수록 사람이 시스템에 대한 이해와 방향 감각을 잃지 않게 하는 문제에 초점을 맞춘다. 원문은 목적 2에 대해 계획 모드가 잘못된 추상화라고 하면서 "especially as the number of parallel agents we run increases"라는 단서를 달았고, 이 문제는 에이전트가 다섯 개에서 수백 개로 늘어날수록 어려워진다고 적는다. 그런 상황에서 AI가 생성한 대규모 명세 문서를 일일이 읽고 승인하도록 하는 방식은 사람의 이해를 돕는 올바른 인터페이스가 아니라는 지적이다. 결국 아티팩트로서의 공유 명세가 필요한 협업과 아카이빙의 영역이 존재하는 한편, 사람의 시스템 이해를 돕는 영역에서는 고정된 계획 모드가 아닌 다른 추상화가 필요하다는 것이 이 글의 해석이다.

비교 축 명세 파일 고정론 (OpenSpec 등) 계획 모드 회고 (Ayman Nadeem)
주요 문제의식 에이전트와의 세션 종료 시 설계 지식 증발 AI 생성 계획 문서를 읽는 인간의 인지적 피로
명세의 성격 팀 공유 및 장기 유지보수를 위한 형식지 아티팩트 실시간 탐색 루프를 가로막는 무거운 추상화
최적의 활용 영역 다수 에이전트 및 여러 작업자 간의 계약 정의 병렬 에이전트가 늘수록 사람이 방향을 잃지 않게 하는 문제
핵심 지향점 설계 맥락의 불변적 기록과 객관적 검증 기준선 인간의 주의력이 최대의 효과를 내는 최소 지점 포착

8. 확인하지 못한 것

본 글은 공개된 1차 출처 기술 회고문과 공식 기록을 바탕으로 사실에 입각하여 작성되었으며, 조사 과정에서 확인하지 못한 한계 사항들을 아래와 같이 기록한다.

  • AI 코딩 제품 Nuanced의 구체적인 출시 시점, 현재 서비스 운영 유지 여부 및 폐업 여부는 원문에 언급되지 않아 확인하지 못했다(저자 소개란은 현재형으로 기재되어 있음).
  • Nuanced의 누적 사용자 수, 매출 규모, 실제 초기 사용자의 정량적 이탈률이나 실험 벤치마크 데이터는 원문에 기재되지 않아 확인하지 못했다.
  • 원문에서 비교 대상으로 언급된 Claude Code CLI, Conductor, Codex 등 상용 도구들의 구체적인 내부 계획 모드 구현 메커니즘과 세부 인터페이스 사양은 원문에서 다루어지지 않아 확인하지 못했다.
  • 수백 개의 에이전트가 동시에 실행되는 대규모 프로덕션 환경에서 인간의 인지적 주의력을 보존하는 구체적인 상용 도구의 구현 사례나 벤치마크 결과는 이 글에서 따로 조사하지 않았다.
