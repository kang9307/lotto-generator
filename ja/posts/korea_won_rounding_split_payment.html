10,000ウォンを3人で割ると9,999になる - ウォンに小数点がないために生じる1ウォン

分割・割引・返金・税額分離で1ウォンが消えたり生まれたりする箇所と、配分結果を保存すべき理由

2026-08-01 開発/インフラ

症状: 精算画面の合計が決済額より1ウォン少なかった

架空の状況だが形はよくある。3人が10,000ウォンの注文を分けて決済し、カード会社ではちょうど10,000ウォンが承認された。ところが精算画面の合計欄は9,999ウォンを示している。1ウォンがどこへ行ったのか誰にも分からず、突合バッチは合計不一致で止まっている。

1ウォンの誤差は金額として見れば何でもない。問題はその1ウォンが自動突合を通らないことだ。精算は合計が合っているかを機械的に検査し、合わなければ人が手で掘り下げるしかない。一日に数万件が流れる場所でこうした案件が数百件たまれば、金額は数百ウォンなのに作業は数日分になる。

先に結論を書く。よく出てくる処方である「丸めをきちんとしよう」は問題を半分しか指していない。本当の問題はこちらだ。

  • 除算は必ず余りを残す。 ウォンにはその余りを置く小数の桁がない。どの丸め方式を選んでも合計はずれる
  • 除算の結果を保存しなければ後から復元できない。 返金・取消・部分精算は「そのとき誰がいくら払ったか」を必要とするのに、計算し直してはその値が出てこない
  • 1ウォンは小さいが合計が合わなければ精算は止まる。 金額の大きさと事故の大きさが比例しない領域だ

以下の数字はすべて推定ではなく実際に走らせて得た出力である。電卓で確かめられるものばかりなので、疑わしければ自分で再現してほしい。

実行環境。 以下の出力はWindows 10 Pro (10.0.19045)で実際に実行した結果だ。ランタイムはPython 3.13.3 (win32)とNode.js v22.16.0 (win32, ICU 77.1)、シェルはGNU bash 5.2.37 (MSYS2/MinGW64)である。スクリプトはすべてファイルに保存して実行した。金額はすべて韓国ウォンである。

この記事が扱わないこと。 税法・会計規程がどの丸めを要求するかは扱わない。それは企業の方針と契約、そして担当する専門家の判断で決める領域だ。この記事はその方針が何に決まろうとコードがそこからずれないよう実装する方法だけを見る。数値が直列化・逆直列化の過程でつぶれる問題はJSON数値の精度損失で別に扱った。ここではウォン単位の配分という一点だけを掘る。例として出る金額とカートはすべて架空である。

1. ウォンには小数を置く桁がない

出発点は通貨そのものの性質だ。ドルにはセント、ユーロにもセントがあるので小数二桁を使う。ウォンはそうではない。国際通貨コード標準は通貨ごとに小数桁数(exponent)を指定しており、ウォンは0として載っている。実行環境に直接尋ねてみた。

node v22.16.0 / ICU 77.1

--- 0-1. default fraction digits per currency, straight from Intl ---
currency  formatted 1234.5        min  max
---------------------------------------------------
KRW       ₩1,235                 0    0
JPY       ¥1,235                 0    0
USD       $1,234.50              2    2
EUR       €1,234.50              2    2
KWD       KWD 1,234.500          3    3
CLF       CLF 1,234.5000         4    4

この表がこの記事の背景そのものだ。「小数二桁」は通貨の普遍的な性質ではない。 クウェート・ディナールは三桁、チリのウニダは四桁を使う。そしてウォンと円は0桁である。

通貨小数桁数最小単位実務上の意味
KRW (ウォン)01ウォン整数のまま保存する。 100倍保存は無意味
JPY (円)01円ウォンと同じ性質
USD (ドル)20.01ドルセント単位の整数で保存する慣行が成り立つ
EUR (ユーロ)20.01ユーロドルと同じ
KWD (ディナール)30.001ディナール1000倍保存。二桁前提が崩れる反例
CLF (ウニダ)40.0001物価連動の計算単位

表記上はウォンにもチョン(銭)という補助単位が名前としては残っている。ただし取引では使われず為替相場の表示のような場面にしか現れず、国際標準の小数桁数は0だ。流通する最も小さい貨幣が1ウォンだということが実務的にはすべてである。

ここで韓国特有の落とし穴が出てくる。金額を扱うライブラリの多くは「最小単位の整数で保存し、表示時に100で割る」方式を既定としている。ドルを基準にすれば優れた設計だ。それをそのままウォンに当てはめるとどうなるかを確かめた。

--- 0-2. what the generic cents pattern does to a KRW amount ---
amount in KRW                      : 1234
generic "store minor units" x100   : 123400
display that back /100 as KRW      : ₩1,234
the x100 is dead weight: KRW has no 1/100 to hold

--- 0-3. formatting a fractional KRW value ---
3333.3333333333335     -> ₩3,333
3333.5                 -> ₩3,334
3334.5                 -> ₩3,335
2450.5                 -> ₩2,451
2451.5                 -> ₩2,452
the formatter hides the fraction. it does not remove it,
and it is not the value that gets stored or charged
  • 100倍は純粋な無駄だ。 ウォンには100分の1がないので保存領域と変換コードだけが増える。しかもその100倍の値がどこかでそのまま画面に漏れれば123,400ウォンという事故になる
  • より危険なのは0-3のフォーマッタの挙動だ。小数の付いた値を入れてもフォーマッタは静かに整数として見せる。画面は正常なのに保存された値には小数が生きている
  • その状態で複数件を足すと画面の合計と実際の合計が分かれる。書式は値を直さない。 表示層で丸めるのと保存層で丸めるのはまったく別の行為だ
  • ちなみにこのフォーマッタは3334.5を3,335へ上げた。後で見る別の丸め実装とは挙動が違う。同じプロジェクトの中で二つの方式が混ざれば、それ自体が1ウォン誤差の原因になる

2. 10,000ウォンを3人で割ると

ここからが核心の再現だ。最も単純な状況から入る。

python 3.13.3 / win32   currency KRW (integer, no minor unit)

--- 1-1. 10000 KRW, 3 payers, the plain way ---
total                : 10000
total / n            : 3333.3333333333335
Decimal exact        : 3333.333333333333333333333333
floor           3333  3333  3333  sum   9999   total-sum +1
round-half-up   3333  3333  3333  sum   9999   total-sum +1
ceil            3334  3334  3334  sum  10002   total-sum -2

冒頭で述べた9,999ウォンがこれだ。読み方を整理するとこうなる。

  • 正確な取り分は3333.333…で、これをウォンで表す方法がない。3,333ウォンと3,334ウォンの間には何もない
  • 切り捨ては3人とも3,333ウォンなので合計9,999ウォン。1ウォンが消える
  • 四捨五入もこの金額では小数部が0.33なので切り捨てと結果が同じだ。四捨五入にすれば解決するわけではないという最初の証拠になる
  • 切り上げは3人とも3,334ウォンなので合計10,002ウォン。2ウォン多く取る。顧客の立場ではこちらの方が悪い

10,000ウォンという数字が特殊なのではないかと疑うかもしれない。他の金額へ広げてみた。

--- 1-2. it is not only 10000: same split, other totals ---
total    exact         floor x3   sum      round x3   sum      ceil x3    sum
-------------------------------------------------------------------------------
10000    3333.3333     3333       9999     3333       9999     3334       10002
10001    3333.6667     3333       9999     3334       10002    3334       10002
10002    3334.0000     3334       10002    3334       10002    3334       10002
9999     3333.0000     3333       9999     3333       9999     3333       9999
35000    11666.6667    11666      34998    11667      35001    11667      35001
100000   33333.3333    33333      99999    33333      99999    33334      100002
1        0.3333        0          0        0          0        1          3

note: the three modes agree with the total only on 10002 and 9999 - the two rows
      already divisible by 3. every other row is off by -2, -1 or +2.

結論は明白だ。総額が3の倍数である二行でのみ合計が合う。 残る五行はどの方式を選んでも-2ウォンから+2ウォンの間でずれる。最後の行は極端だ。1ウォンを3人で割ると切り捨て・四捨五入では3人とも0ウォンになり1ウォン全部が蒸発し、切り上げでは3人とも1ウォンになり元の3倍を取る。

この表から持ち帰るものは一つだ。丸め方式は誤差の向きを変えるだけで誤差をなくさない。 なくすには別のことをしなければならない。

3. 切り捨て・四捨五入・切り上げ - 三方式の合計差

一件ではなく複数行が集まれば誤差も積み上がる。五行の共同費用をそれぞれ3で割って一人分を作り、それを再び三倍して店が受け取る総額と比べた。

--- 2-1. three rounding modes on one 5-line order (each line 1/3 of a shared cost) ---
line total   /3 exact      floor  round  ceil
-------------------------------------------------
7000         2333.333333    2333   2333   2334
12500        4166.666667    4166   4167   4167
3300         1100.000000    1100   1100   1100
990          330.000000     330    330    330
45000        15000.000000   15000  15000  15000
-------------------------------------------------
one payer's share sums to   floor  22929   round  22930   ceil  22931
x3 (what the shop collects) floor  68787   round  68790   ceil  68793
order total                 68790
gap vs order total          floor -3      round +0       ceil +3

ここでは四捨五入がたまたま合った。小数が生じたのは二行だけで、その二つが互いに相殺したからだ。この偶然を「四捨五入が正しい」と読んではいけない。前節の10,000ウォンでは同じ四捨五入が1ウォンを落とした。合うときも合わないときもあるというのがこの方式の性質だ。

そして四捨五入にはもう一つ確認すべきことがある。「丸め」という語が指す挙動は一つではない。

--- 2-2. the default round() in this runtime is NOT half-up ---
0.5        python round() 0       ROUND_HALF_UP 1       ROUND_HALF_EVEN 0
1.5        python round() 2       ROUND_HALF_UP 2       ROUND_HALF_EVEN 2
2.5        python round() 2       ROUND_HALF_UP 3       ROUND_HALF_EVEN 2
3.5        python round() 4       ROUND_HALF_UP 4       ROUND_HALF_EVEN 4
4.5        python round() 4       ROUND_HALF_UP 5       ROUND_HALF_EVEN 4
2450.5     python round() 2450    ROUND_HALF_UP 2451    ROUND_HALF_EVEN 2450
2451.5     python round() 2452    ROUND_HALF_UP 2452    ROUND_HALF_EVEN 2452
half-even sends x.5 to the nearest even integer, so 2.5 becomes 2, not 3

このランタイムの既定の丸め関数は四捨五入ではない。 2.5を3ではなく2へ送る。ちょうど半分のとき近い偶数へ送る方式なので統計的には偏りが少ないが、人が期待する値とは違う。 先に見た国際化フォーマッタは3334.5を3,335へ上げた。同じプロジェクトの中にこの二つが混在すれば、ある行は上がりある行は下がって、原因を追いにくい1ウォン差が散発的に生じる。

方式10,000ウォン3分割の合計誤差の向き性質使いどころ
切り捨て9,999ウォン常に不足店が損、顧客が得顧客有利の原則があり余りを別途処理する場合
四捨五入9,999ウォン両方向、予測しにくい最も直感的だが保証がない表示用。保存値の計算には不十分

配分(余りを明示)10,000ウォン誤差なし合計が元の金額と常に一致分割・精算の既定とすること

4. 余った1ウォンを誰に渡すか

最後の行がこの記事の処方だ。丸め方式を選ぶ代わりに余りを明示的に配分する。方法は単純で、全員に切り捨ての値を渡し、残った金額を1ウォンずつ誰かに付ける。余りは常に人数より小さいので、一人が2ウォン以上多く払うことはない。

残る問題は誰に付けるかだ。四つの方針を実行して比較した。

---------------------------------------------------
first      3334   3333   3333   10000  True
last       3333   3333   3334   10000  True
largest    3334   3333   3333   10000  True
rotate     3334   3333   3333   10000  True

--- 3-2. unequal weights: a 100000 KRW bill shared by usage ---
total 100000  weights [3, 3, 1] (sum 7)
  member 0 exact share : 42857.14285714285714285714286
  member 1 exact share : 42857.14285714285714285714286
  member 2 exact share : 14285.71428571428571428571429
policy      A      B      C      sum    sum==total
---------------------------------------------------
first      42858  42857  14285  100000 True

largest-remainder gives the extra KRW to the biggest fractional part,
so the member who was cut the most is the one paid back first

四方式とも合計はちょうど元の金額だ。 sum==totalの列がすべてTrueである。違いは誰が1ウォン多く払うかだけだ。

二つ目のブロックが方針選択の基準を示す。使用量3:3:1で100,000ウォンを分ける状況で、小数部が最も大きいのは三人目(0.714)だ。最大剰余方式はその人に1ウォンを渡す。「最も削られた人を先に補償する」という規則なので、一回の配分だけを見ればこれが最も公平だ。

ところが精算はふつう繰り返される。毎月同じ構成で分けるなら話が変わる。

--- 3-3. rotate across 6 monthly bills keeps the unfairness bounded ---

2      10000   3333  3334  3333  10000 1

差が目に見える。開始位置を毎月回すと六か月後に3人がちょうど20,000ウォンずつ払った。差は0ウォンだ。一方最初の人に固定する方式はAが毎月1ウォンずつ多く払い6ウォンの累積差を生んだ。一か月だけ見れば1ウォンだが、サブスクのように続けば偏りが一方向へ積み上がる。

配分方針合計保証一回の公平性反復時の偏り実装の負担推奨する状況
最初の人へあり低い一方向に累積最も単純一回限りの分割
最後の人へあり低い一方向に累積単純一回限りの分割
最大剰余あり最も高い加重固定時は累積しうるソート一回加重の異なる一回の配分
巡回あり中程度相殺される(6か月で差0)開始位置の保存が必要繰り返す定期精算
単純な四捨五入なし--最も単純使わないこと

重要なのはどれが正解かではない。 四方式とも合計は合う。決めるべきは「我々はこの方式を使う」をコードの一箇所と文書に書いておくことであり、その次がその結果を保存することだ。

5. 割引はどこで丸めるかで値が分かれる

除算を生むのは分割だけではない。定率割引も除算だ。 15パーセントを掛けるとは85を掛けて100で割ることなので、同じように余りが生じる。四行の架空のカートで確かめた。

--- 4-1. where you round a percent discount changes the bill ---
cart [1990, 2990, 5990, 990]   subtotal 11960 KRW   discount 15 percent

line   price    exact discounted   per-line floor  per-line half-up
--------------------------------------------------------------------
A      1990     1691.5             1691            1692
B      2990     2541.5             2541            2542
C      5990     5091.5             5091            5092
D      990      841.5              841             842
--------------------------------------------------------------------
A. round every line, then add  : floor 10164   half-up 10168
B. add first, then round once  : floor 10166   half-up 10166
exact untouched value          : 10166
A minus B                      : floor -2       half-up +2
same cart, same rate, same rounding mode - two different totals

同じカート、同じ割引率、同じ丸め方式なのに総額が二つ出る。 差を生んだのはどの段階で丸めたかだけである。

  • 四行とも.5で終わる状況なので差が鮮明だ。行ごとに四捨五入すると四回とも上がって+2ウォン、行ごとに切り捨てると四回とも下がって-2ウォンになる
  • 実際の誤差幅は行数に比例する。二十行の注文なら最大10ウォン、百行なら50ウォンまで開きうる。「1ウォン問題」と呼びにくくなる地点だ
  • どちらも誤った計算ではない。 答えが違う質問への答えにすぎない。問題は注文画面と精算バッチが互いに違う方を使っているときに起きる
  • 顧客が見る領収書に行ごとの割引額が印字されるなら、必ず行単位で計算して保存しなければならない。総額だけ保存して行ごとの金額を画面で再計算すると領収書の行の合計が決済額と合わない

5.1 割引を二つ重ねると順序が結果を変える

クーポンと会員割引のように定率割引が重なることはよくある。純粋な乗算なら順序は結果を変えない。途中に丸めが挟まると変わる。

--- 4-2. two stacked discounts, same rates, reversed order ---
price    10 then 3      3 then 10      one combined rate
-----------------------------------------------------------
28900    26010  -> 25230  28033  -> 25230  25230
33000    29700  -> 28809  32010  -> 28809  28809
19900    17910  -> 17373  19303  -> 17373  17373
12345    11111  -> 10778  11975  -> 10778  10777
7700     6930   -> 6722   7469   -> 6722   6722

sweep 1..50000 KRW : 15550 prices give a different final amount (31.1 percent)
  first six : 17 gives 15 or 14, 18 gives 16 or 15, 26 gives 22 or 23,
              36 gives 31 or 32, 46 gives 40 or 41, 51 gives 45 or 44
rounding BETWEEN the two steps is what makes the order matter

よく使う価格帯五つでは順序を変えても結果が同じだった。ところが1ウォンから50,000ウォンまで全部走査すると15,550件の金額で答えが変わった。 三つに一つの割合である。

12345の行にはもう一つの落とし穴がある。二つの割引を段階的に適用すると10,778ウォンだが、0.90と0.97を先に掛けて一度に適用すると10,777ウォンだ。数学的には同じ割引率なのに途中の丸めの有無で1ウォンが分かれた。

  • テストをいくつかの値だけで行えば通ってしまう。 上の五行がその証拠だ。この種のバグが長く生き残る理由がここにある
  • 顧客からの問い合わせは「クーポンを先に適用したら1ウォン安い」という形で来る。再現が難しいので担当者が再現できないとして閉じてしまいやすい
  • 対策は途中の段階で丸めないことだ。有理数か固定小数点で最後まで持っていき、最終請求額を作るときに一度だけ整数へ落とす
  • 中間値を画面に見せる必要があるなら表示用にだけ丸め、次の段階の計算には丸める前の値を渡す

6. 部分返金 - 配分値を持っていなければ復元されない

ここがこの記事の論旨が最も鮮明になる場所だ。ここまでは「どう分けるか」で、ここからは「分けたものをどう戻すか」である。

--- 5-1. partial refund with no stored allocation ---
charged : [3334, 3333, 3333]   sum 10000

case A - refund recomputed as total/3 at refund time
  floor     refund each 3333  x3 = 9999    shop ends up +1 KRW off
  half-up   refund each 3333  x3 = 9999    shop ends up +1 KRW off
  ceil      refund each 3334  x3 = 10002   shop ends up -2 KRW off
case B - refund reads the stored per-payer amount
  refunds [3334, 3333, 3333]  sum 10000   shop ends up +0 KRW off

請求時には[3334, 3333, 3333]ときちんと分けた。問題は返金だ。

  • 事例Aは返金時点で総額 / 3を計算し直す。3人全員に3,333ウォンを返せば計9,999ウォンなので1ウォンが店に残る。 顧客の一人は3,334ウォンを払ったのに3,333ウォンしか受け取れない
  • 切り上げに変えるともっと悪い。 10,002ウォンを返して店が2ウォン損をする。受け取ったことのない金を出すので会計上説明できない金額になる
  • 事例Bは保存された値を読む。合計はちょうど10,000ウォンだ。差を生んだのはアルゴリズムではなく保存の有無である

より現実的な形はカート全体にかかった割引があるときだ。この場合はどの行がいくら「実際に払ったのか」がもともと曖昧である。

  • 返金時点で計算し直すと10,168ウォンが出て2ウォンの損だ。はるかに良いが依然として合わない。CとDの行で保存値と1ウォンずつずれたからである
  • 保存された配分値を読めばちょうど10,166ウォンだ。差は0ウォンである
  • 注目すべきは再計算方式がほとんどの行では合っていたことだ。AとBは保存値と同じだった。全数で走らせてこそずれが露見するという意味であり、だから部分返金のバグは長く隠れている
  • なぜずれるかは表の最後の二行にある。行ごとの再計算の合計は10,168ウォンなのに実際の請求額は10,166ウォンだ。配分と再計算はそもそも違う値を作る

この記事の論旨。 問題の本質は丸めではない。除算は情報を失う演算であり、その結果を保存しなければ後から復元する方法がないということだ。保存しなかった配分は計算し直すしかなく、再計算が元の値と一致するという保証はない。

だから処方はアルゴリズムではなくスキーマだ。請求時点の行ごとの配分金額を行として残す。 割引額も行ごとに配分して保存する。返金はその行を読んで処理し、計算しない。

9. 設計規則 - 丸めを一箇所に集める

ここまで見たものをコードに移すと規則は三行だ。整数で扱う。丸めは一つの関数でだけ行う。結果を保存する。 その関数の形はこうなる。

def split_krw(total, weights, policy="largest"):
    """Divide an integer KRW amount over integer weights.

    Rounds in exactly one place. Returns integers whose sum is total.
    """
    if not isinstance(total, int):
        raise TypeError("total must be an int in KRW")
    if not weights or any(w < 0 for w in weights):
        raise ValueError("weights must be non-negative")
    tw = sum(weights)
    if tw == 0:
        raise ValueError("weights sum to zero")
    base = [total * w // tw for w in weights]
    rem = total - sum(base)
    k = len(weights)
    if policy == "largest":
        frac = [(total * w) % tw for w in weights]
        order = sorted(range(k), key=lambda i: (-frac[i], i))
    elif policy == "first":
        order = list(range(k))
    else:
        raise ValueError(policy)
    for i in range(rem):
        base[order[i]] += 1
    assert sum(base) == total, "split_krw broke its own invariant"
    return base

構造は単純だ。total * w // twは整数の乗算が先なので実数誤差がない。余りはremに集まり、ソートされた順序で1ウォンずつ付く。最後の行の表明が合計が元の金額と同じであることを関数自身が検査する。

11. 点検リスト

新しい決済・精算コードを見るときはこの順で確認すればよい。

  • 金額を整数(ウォン単位)で扱っているか。実数型がどこかに残っていないか
  • ウォンに100倍保存の慣行をそのまま当てはめていないか。ウォンは小数桁数が0だ
  • 比率の計算が整数の乗算が先、除算が後の形か。実数の乗算が残っていれば特定の比率で1ウォンが分かれる
  • 丸める関数がコードベースにいくつあるか。一つであるべきだ
  • その関数が四捨五入か偶数丸めか文書に書かれているか。ランタイムの既定値をそのまま使っていないか
  • 除算の余りを捨てる箇所があるか。あるならその余りはどこへ行くのか
  • 配分関数に合計 = 元の金額の表明が入っているか
  • 配分結果がテーブルに保存されるか。行ごとの実支払額が行として残るか
  • 割引額も行ごとに配分して保存されるか。総額だけ保存していないか
  • 返金コードが保存された値を読むのか、計算し直すのか
  • 全額返金したとき返金合計 = 請求合計になるテストがあるか
  • 部分返金をすべての行について試したか。いくつかの行だけ合っている状態がよくある
  • 定率割引が重なるとき順序を変えても同じ値が出るテストがあるか
  • 本体価格と税額を両方とも丸めていないか。一方は引き算で求めるべきだ
  • 項目別の逆算と全体の逆算のうちどちらを使うか決まっているか。システムごとに違うものを使っていないか
  • 繰り返す精算で余りが常に同じ人へ行っていないか
  • 0ウォンの配分が出うる経路でその行をどう処理するか決めたか
  • 精算バッチに差額 = 0の検査があり、0でなければ止まるか
  • テストデータが3の倍数・11の倍数のような割り切れる値だけになっていないか
  • 大量件数で累積誤差の試験をしたか。数件では露見しない

# ウォンの1ウォン配分 — アルゴリズム・比較表・検算

> 出典: braindetox.kr — 10,000ウォンを3人で割ると9,999ウォンになる
> 根拠: Windows 10 / Python 3.13.3 / Node 22.16.0 (ICU 77.1) 実行検証
> 通貨: KRW。ISO 4217 の小数桁数は 0（補助単位なし）。以下の金額はすべて韓国ウォン

## 1. 原則を一箇所に

- 金額は **整数（ウォン単位）** で扱う。100倍して最小単位で保存する習慣はウォンでは無意味
- 除算の **余りを捨てずに配分** する
- 丸めは **コードベース全体で一つの関数** だけで行う
- 配分結果を **保存** する。返金は読み取るのであって計算し直さない

## 2. 配分アルゴリズム（合計が必ず元の金額になる）

```python
def split_krw(total, weights, policy="largest"):
    if not isinstance(total, int):
        raise TypeError("total must be an int in KRW")
    if not weights or any(w < 0 for w in weights):
        raise ValueError("weights must be non-negative")
    tw = sum(weights)
    if tw == 0:
        raise ValueError("weights sum to zero")

    base = [total * w // tw for w in weights]   # 整数の乗算が先、除算が後
    rem  = total - sum(base)                     # 余り、常に 0 <= rem < len(weights)
    k    = len(weights)

    if policy == "largest":                      # 小数部が大きい順
        frac  = [(total * w) % tw for w in weights]
        order = sorted(range(k), key=lambda i: (-frac[i], i))
    elif policy == "first":
        order = list(range(k))
    elif policy == "rotate":                     # 定期精算用、START を保存すること
        order = [(START + i) % k for i in range(k)]
    else:
        raise ValueError(policy)

    for i in range(rem):
        base[order[i]] += 1

    assert sum(base) == total, "split_krw broke its own invariant"
    return base
```

## 3. 方式別の比較（10,000ウォンを3分割）

| 方式 | 結果 | 合計 | 差 | 判断 |
|---|---|---|---|---|
| 切り捨て | 3333 / 3333 / 3333 | 9,999 | **-1** | 使わない |
| 四捨五入 | 3333 / 3333 / 3333 | 9,999 | **-1** | 保証がない |
| 偶数丸め | 3333 / 3333 / 3333 | 9,999 | **-1** | 多くの実行環境の既定値 |
| 切り上げ | 3334 / 3334 / 3334 | 10,002 | **+2** | 顧客が損をする |
| **配分 first** | 3334 / 3333 / 3333 | **10,000** | **0** | 一回限り |
| **配分 largest** | 3334 / 3333 / 3333 | **10,000** | **0** | 加重配分 |
| **配分 rotate** | 回ごとに巡回 | **10,000** | **0** | **定期精算** |

## 4. 残余配分ポリシーの選び方

| ポリシー | 合計保証 | 一回の公平性 | 反復時の偏り | 推奨 |
|---|---|---|---|---|
| first / last | あり | 低い | **累積する**（6か月で6ウォン） | 一回限りのみ |
| largest | あり | **最も高い** | 加重固定なら累積 | 加重分割 |
| rotate | あり | 中程度 | **相殺される**（6か月で0ウォン） | **サブスク・定期** |

## 5. 検算アサーション（すべて通ること）

```python
assert sum(parts) == total                    # 合計 = 元の金額
assert all(p >= 0 for p in parts)             # 負の値なし
assert len(parts) == len(weights)             # 件数の保存
assert max(abs(p * tw - total * w) for ...) < tw   # 各自の誤差が1ウォン未満
assert sum(refunds) == charged                # 全額返金 = 請求額
assert supply + tax == price_incl             # 本体価格 + 税額 = 税込価格
```

実測: ランダム30万件すべて通過。正確な取り分からの最大乖離は **0.873479ウォン**（1ウォン未満）

## 6. 税の分離ルール

- **片方だけ丸めて残りは引き算で求める** → 税率に関係なく合計が必ず一致する
- 両方とも切り捨て / 両方とも切り上げ → 20万件の価格のうち **181,819件** で合計が崩れた
- 項目別の逆算と全体の逆算は **別の値** になる（標本729件中239件、32.8%）
- どちらを使うかは **企業の方針・契約・担当専門家の判断** で決めて文書に書く

## 7. 割引のルール

- 途中の段階で丸めない。**最終請求額で一度だけ**
- 定率割引を二つ重ねると順序で値が変わる → 5万件の価格のうち **15,550件**（31.1%）
- 行ごとの丸めの合計と合計額の丸めは異なる → 例のカートで **2ウォン**
- 領収書に行ごとの金額を印字するなら **行単位で計算して保存** し、合計はそれを足して作る

## 8. 浮動小数点を禁じる理由

- `金額 * 0.7`（実数）と `金額 * 7 / 10`（整数）は **100万件中18,724件** で答えが違う
- 45ウォンの30%割引: 実数は `31.499999999999996` で31ウォン / 整数は `31.5` で32ウォン
- 率によっては食い違いが **0件の場合もあり**、数個の試験では捕まらない
- 金額自体は約9,007兆まで正確 → **危険なのは保存ではなく除算と率の乗算**

## 9. 保存スキーマの最低要件

- 決済行ごとの **実支払額** 列（配分後の値であって定価ではない）
- 割引額も **行ごとの配分値** として保存
- 税額・本体価格も計算ではなく **保存された値**
- 巡回配分を使うなら **次の開始位置** も一緒に保存
- 返金行は元の決済行を **参照** し、その金額を超えない制約を置く

## 10. 点検リスト

- [ ] 金額がすべて整数か（実数型の残存なし）
- [ ] ウォンに100倍保存を適用していないか
- [ ] 率の計算が整数の乗算を先に行う形か
- [ ] 丸め関数が **一つ** か
- [ ] その関数が四捨五入か偶数丸めか文書にあるか
- [ ] 配分関数に合計のアサーションがあるか
- [ ] 配分結果がテーブルに保存されるか
- [ ] 返金が保存値を **読むか**（再計算ではなく）
- [ ] 全額返金 = 請求額のテストがあるか
- [ ] 部分返金を **すべての行** で試験したか
- [ ] 割引の順序を変えても同じ値か
- [ ] 本体価格と税額のうち片方だけを丸めているか
- [ ] 項目別と全体、どちらの逆算かが決まっているか
- [ ] 定期精算で余りが同じ人に行き続けていないか
- [ ] 0ウォン配分行の処理方針があるか
- [ ] 精算バッチに差額0の検査があり、違えば止まるか
- [ ] テスト値が3の倍数・11の倍数だけになっていないか
- [ ] 大量件数での累積誤差試験をしたか

## 11. やってはいけないこと

- 丸め方式を変えるだけで合計を合わせようとすること — **どの方式も保証しない**
- 除算の結果を保存せず必要な時に計算し直すこと — **復元できない**
- 定価基準で返金すること — 例では **1,794ウォン** の過大返金
- 金額を実数で掛けること — 特定の率でだけ静かに間違う
- 段階ごとに丸めること — 順序が結果を変える
- 本体価格と税額をそれぞれ丸めること — 9割を超える価格で合計が崩れる
- 割り切れる金額だけでテストすること — 3の倍数ではバグが見えない
- 1ウォンの差をそのまま通すこと — 翌月には出所が分からなくなる
