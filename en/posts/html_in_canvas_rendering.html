Drawing HTML Into a Canvas - What You Gain, and What Accessibility Pays

What the experimental HTML-in-Canvas proposal fixes, and what text on a canvas was losing all along

Aug 20, 2026 Tech & IT

Why text on a canvas always feels slightly off

Anyone who has used a web-based design tool or whiteboard has run into this. Text is clearly on screen, yet dragging across it selects nothing. Ctrl+F reports no match. A translation extension leaves that region in the original language, and a screen reader skips the area entirely.

None of that is a bug. The text is a picture, not text. The moment it is painted into a <canvas> it becomes an array of colored pixels, and the browser has no way to know what was written there.

HTML-in-Canvas, which Chrome is experimenting with behind a flag, aims squarely at that gap. The proposal is to put real DOM elements inside a canvas and paint them into the canvas exactly as the browser laid them out. In Korea it surfaced when a developer who builds canvas editors published a small UI library on top of the feature. What follows is what you gain, what you pay for it, and what to reach for today.

What the feature actually does

The core idea fits in one sentence. Lay out the children of a <canvas> for real, and paint the result onto the canvas surface.

The WICG explainer defines three main pieces.

  • The layoutsubtree attribute — placed on a canvas element, it opts the descendants into layout and hit testing. Until now canvas children were never laid out at all
  • Drawing methods — drawElementImage() for 2D, texElementImage2D() for WebGL, and copyElementImageToTexture() for WebGPU. Name an element and its rendering lands in the canvas or in a texture
  • The paint event — fired when the rendering of any canvas child changes. It runs after the intersection observer step and carries the list of changed elements

Two helpers round it out: captureElementImage() turns an element into a snapshot that can be transferred to a worker, and getElementTransform() converts a drawing transform back into a CSS transform for 3D contexts. The basic shape in the explainer looks like this.

<canvas id="canvas" layoutsubtree>
  <form id="form_element">
    <label for="name">name:</label>
    <input id="name">
  </form>
</canvas>

<script>
  canvas.onpaint = () => {
    ctx.reset();
    const transform = ctx.drawElementImage(form_element, 100, 0);
    form_element.style.transform = transform.toString();
  };
</script>

It is a short snippet, but the last line reveals the character of the API. drawElementImage() returns the transform matrix for where it painted, and the developer feeds that matrix back into the element's own style.transform. You are manually keeping the painted pixels and the real DOM element in the same place. The accessibility section explains why that matters.

The rename is worth remembering too. It started as drawElement and later became drawElementImage and texElementImage2D. That is a signal the surface has not settled.

Why this has been hard - pixels carry no structure

The canvas 2D API is an imperative drawing surface. fillRect does not remember a rectangle, it colors the pixels in that spot. fillText behaves the same way. Once the glyphs land, only color remains — no text node, no box.

That was a performance choice. With no scene graph to maintain it stays light, which suits games and visualizations that redraw everything each frame. The cost is that everything the browser used to do for a document disappears with it. Line breaking, bidirectional text, font fallback, the box model, hit testing — all of it becomes your code.

The HTML specification knew about this and allowed fallback content inside the canvas element. The trouble is that the fallback has no relationship to what is actually painted. The explainer says as much: there is currently no guarantee that the canvas fallback content used for accessibility matches the rendered content, and such fallback content can be hard to generate in the first place.

So practitioners built workarounds. There are three, and all three stop at the same place.

Painting an SVG foreignObject as an image

Wrap HTML in an SVG <foreignObject>, turn the SVG into a data URL, load it through an <img>, then drawImage() it. The premise is the same as this proposal: borrow the browser's layout engine.

  • An SVG loaded as an image cannot fetch external resources. Web fonts and images must all be inlined as data URIs
  • Scripts do not run, so nothing dynamic can go in
  • Missing an inline is not an error — the typeface silently changes. It is a classic cause of dev and production output diverging
  • Decisively, the result is pixels again. No accessibility survives

Reimplementing DOM rendering in a library

This is the path html2canvas and its relatives took: walk the DOM, read computed styles, and translate them into canvas drawing calls. In effect it is reimplementing part of the browser rendering engine in JavaScript. The Codrops analysis of the proposal summarized the ceiling plainly — because every CSS property has to be hand-coded, full CSS support is not achievable. However long the supported list grows, the browser stays ahead, and here too the output is pixels.

Drawing the text by hand

The most common approach and the slowest one. Measure with measureText() and break lines yourself. For short Latin labels it is half a day of work. Then the rest arrives.

  • Line-breaking prohibitions in Korean and Japanese — characters that may not end or begin a line
  • Emoji and combining characters — slicing by code point breaks glyphs apart
  • Bidirectional text in Arabic and Hebrew — logical order differs from display order
  • Font fallback — baseline alignment when the typeface changes mid-string

The list never ends. Text layout is where the principle of not rebuilding native browser features applies most sharply.

The real motive - getting the layout engine for free

Sort the demand for this feature and it lands in four buckets.

  • Game UI — inventories, settings screens, dialogue boxes. Build a UI system inside the engine instead and you write code for what one line of CSS would have aligned
  • Labels over data visualization — in a WebGL chart drawing hundreds of thousands of points, the axis labels and tooltips take the most effort. The GPU handles the points; it does not handle the letters
  • Maps — POI label placement, multilingual font fallback, street names flowing along a curve. It is why map renderers ship their own text engines
  • Design tools and whiteboards — a single text box means caret math, selection highlighting and IME composition. As infinite-canvas tools multiply, so does that burden

The common thread is clear. What these people want is layout computation, not drawing. The most heavily exercised text layout engine in the world already ships inside the browser, and the canvas had no path to it. The explainer's motivation says the same thing: there is no web API to easily render complex layouts of text and other content into a canvas, and as a result canvas-based content suffers in accessibility, internationalization, performance and quality. Note that internationalization sits right next to accessibility there. For Korean, Japanese and Arabic the loss is far larger.

What you give up when text becomes pixels

This is the part that matters most when judging the feature. Painting UI on a canvas is a trade — you gain performance and hand something back — and the list you hand back is longer than people expect.

Which is why the problem does not yield to individual diligence. Conscientious teams do write fallback content, but that content lives on a separate code path from rendering, so it drifts over time. It is the same shape of problem seen where structureless output leaves machines nothing to read.

How the proposal handles accessibility, and what stays open

The interesting part of this API is that it located the cause in the dual maintenance. The explainer states that elements drawn with this API will match their corresponding canvas fallback. What you draw is the fallback, so the structural room for the two to diverge shrinks. And because layoutsubtree opts children into hit testing, much of the coordinate-to-element mapping code canvas editors write by hand disappears too. The Chrome for Developers blog goes further, describing content inside the canvas as exposed to the accessibility tree, compatible with assistive technology, and supporting find-in-page, copy and right-click.

None of that should be read as accessibility is solved. The primary documents record constraints of their own, and no report of real assistive-technology behavior was found while writing this.

Start with the constraints the explainer names.

  • CSS transforms are ignored when rendering but still affect hit testing and accessibility. That single line explains the last line of the earlier snippet. Fail to feed the paint position back into style.transform and the visible position drifts from what the accessibility tree reports. That feedback is something a developer can forget
  • Overflowing content is clipped to the border box. Text that would have spilled visibly in the DOM gets cut off on the canvas
  • Scrolling depends on JavaScript. That is the constraint Chrome's own write-up names, and it is not the compositor-driven scrolling you get outside a canvas. The explainer notes that threaded scrolling and animation are under consideration as an auto-updating canvas mode — meaning it does not exist yet

One more axis is unverified. Exposing text to the accessibility tree and relayouting inside the canvas when a low-vision user raises the browser font size are entirely different problems. To summarize, what this proposal attaches automatically is agreement between the accessibility tree and the rendering, not the overall usability of a canvas UI. That is already a better starting point, but the expectation that the API will simply handle accessibility has no support yet.

What cannot be painted - privacy constraints shape the API

This API carries a restriction that looks odd at first and becomes non-negotiable once you see why. The key is that a canvas is a readable surface. Script can read pixels back with getImageData(). The DOM, meanwhile, shows things on screen that script must not read — the color of a visited link being the classic case. Wire the two together naively and you revive the old attack of reading pixels to recover browsing history.

So the explainer introduces the notion of read-back-allowed rendering and requires that the element-image drawing methods and the paint event must not reveal security- or privacy-sensitive information. The exclusions are these.

  • Cross-origin data — content from another origin's iframe is not painted
  • System colors — color keywords sourced from the OS theme
  • Visited link information — :visited styling is not reflected
  • IME popups — input method candidate windows

This list is not an unimplemented backlog; it is the condition under which the API can exist at all. In practice, a UI baked into a canvas that relies on :visited styling, cross-origin widgets, or system color keywords may render differently from what is on screen.

Compatibility reality - where this actually stands

Start with the standards stage, precisely. This is a proposal in WICG incubation. The repository describes its own document as a living explainer that is continuously updated from feedback. It is not folded into the HTML specification, and it is nowhere near a W3C Recommendation.

The developer who introduced it in Korea asked for Chromium 146 or later, the browser support write-up says 147 or later, and the Chrome for Developers blog points at a separate origin trial window and Canary builds. The reliable move is to check your own browser for the flag.

Only one conclusion follows. This is not something to ship. The name has already changed once, the other two engines have stated no position, and only users who flipped a flag can see it. Wire a UI architecture to it now and you maintain a second path anyway — which erases the simplicity you adopted it for.

Comparing the alternatives - what to reach for today

Lay the options on one axis and the decision gets easy.

ApproachText qualityAccessibilityComposites with canvas pixelsUsable today
DOM overlayBrowser nativeFully preservedNoYes
Inline SVG foreignObjectBrowser nativeMostly preservedLimitedYes
SVG drawn as an imageAs far as you inlinedNoneYesYes
DOM-reimplementing libraryAs far as CSS is coveredNoneYesYes
Hand-drawn textAs far as you built itNoneYesYes
HTML-in-CanvasBrowser nativeFallback matches automaticallyYesFlag / trial only

The criterion narrows to one question. Does this text need to mix with canvas pixels?

  • If it does not, a DOM overlay is the answer. Chart axis labels, tooltips, legends, game HUDs and map info panels mostly land here. Absolutely positioned on top, they keep accessibility, selection, find and translation, and they work in every browser today
  • Only when it does should baking be considered: the text must pass through a shader, receive perspective in 3D space, or take canvas filters and blend modes
  • If you do bake, design the accessible alternative in the same commit. An offscreen DOM copy, ARIA attributes, a link to a text version. Plans to add it later usually do not land
  • If sheer element count is the problem, look at cutting DOM nodes with virtual scrolling before moving to canvas. That migration is hard to reverse

Standardization would not flip that order. Using canvas where a DOM overlay would do stays a loss even then. What the feature changes is the quality of the cases you have no choice about, not the range of reasons to use canvas.

What could not be confirmed

This article stays inside what the public primary documents state. These are the gaps.

  • There is no verification with real assistive technology on a flag-enabled build here. The accessibility claims go as far as the explainer and the Chrome documentation state
  • No report was found on how individual screen readers such as NVDA, JAWS or VoiceOver actually announce this content
  • No answer was found for how browser zoom, forced colors mode and minimum font size settings affect the painted result
  • Supported milestone numbers differ between sources, so none was declared correct
  • Performance comparisons were not confirmed in any primary document. That is why this article never claims it is faster or slower
  • No formal standards position documents from Mozilla or WebKit were located. The table's no signal reflects the state recorded in the Blink thread
  • How Korean IME composition behaves in a form element inside the canvas was not confirmed. The explainer only places IME popups on the read-back exclusion list
  • Whether this reaches formal standardization is unknowable. Proposals wind down at the incubation stage often enough

Expressiveness versus accessibility - an old tension

The web began as documents. Accessibility was effectively free early on because content was expressed as structure. The machine-readable form was the human-visible form. Features that raise expressiveness have almost always arrived by routing around that structure: plugin content, <canvas>, WebGL, fake checkboxes built from <div>. The shapes differ, the trade does not. You get the appearance you want and give up the structure machines can read. Each time, two kinds of response appeared.

  • Demanding that structure be maintained separately — canvas fallback content and ARIA attributes belong here
  • Adding platform features that attach structure automatically — letting elements that already carry accessibility be styled into the shape you wanted

The first does not work well. It is why canvas fallback content is in the specification yet barely used in practice, and why components whose ARIA attributes disagree with their real state are common.

That is what makes this proposal notable: it took the second route. By binding the thing being drawn and the thing exposed to the accessibility tree to the same element, it structurally shrinks the room for drift. It is not complete, of course. Skip the transform feedback and things still drift, and the privacy constraints and scroll handling remain open. Still, the difference between a default of drift and a default of agreement is large. The tension itself will not disappear, but whether it rests on individual diligence or on the platform is a choice.

What to do now, and what not to

The feature aims squarely at an old pain in canvas development: bring the browser's layout engine inside the canvas and remove the dual structure of hand-maintained fallback content. The direction looks right, but right now it is a proposal behind one engine's flag. So there are three things worth doing.

  • Count the text you currently paint on canvas. How much of it could move to a DOM overlay? Usually most of it, and that improvement needs no waiting
  • If you have a canvas UI, turn on a screen reader today. Thirty minutes tells you what is unreadable, and that result is the basis for deciding whether this feature matters to you
  • Open the demo on a flag build to get a feel for it. Observation, not adoption. Assume names and behavior will change

What not to do is equally clear. Do not ship it yet. And do not plan around the idea that accessibility gets solved when this API lands. What attaches automatically is agreement between rendering and fallback, not the whole of usability including zoom, forced colors, scrolling and assistive-technology behavior.

Even as painting text on a canvas gets easier, whether the people who need to read that text can read it stays something to check. A good API makes that check easier; it does not do it for you.
