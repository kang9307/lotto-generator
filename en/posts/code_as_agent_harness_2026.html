Code as Agent Harness — A New Paradigm for AI Agentic Systems

The UIUC, Meta & Stanford 102-page survey argues code is no longer what LLMs produce — it is the harness that structures agent reasoning, action, and verification

2026-06-26 Dev & Infra

Introduction: The Role of Code Has Been Inverted

For years, our mental model of AI and code followed a familiar arc: an LLM receives a prompt and produces code as its output. A function appears, a bug gets patched, a module gets generated. In this frame, code has always been the product.

In May 2026, a 102-page survey (arXiv: 2605.18747) from a joint team at UIUC, Meta, and Stanford challenges this picture directly. The core thesis is concise: "In emerging agentic systems, code is no longer only a target output. It increasingly serves as an operational substrate for agent reasoning, acting, environment modeling, and execution-based verification."

This post unpacks what that shift means, why it matters, and what changes in practice — grounded in the survey and cross-verified against independent sources. As of June 2026, this survey stands as one of the most systematic maps of where agentic AI is heading.

1. The Paradigm Shift: Code Is Substrate, Not Output

Anyone who has actually built an agent system senses this intuitively. Raw LLM text output accomplishes nothing on its own. For it to act in a real environment, it must be wrapped in executable structure. That wrapping is what the survey calls the harness.

The survey identifies three roles code plays in agentic systems:

  • Reasoning Executable: Code externalizes internal reasoning into verifiable computation. External interpreters, symbolic solvers, and execution traces check and refine intermediate steps.
  • Action Programmable: Code translates high-level intent into grounded operations — tool calls, robot policies, GUI commands — through structured executable interfaces.
  • Environment State Inspectable: Code represents world state, transition dynamics, and feedback signals via repositories, simulators, tests, and logs that agents can execute, edit, and query.

When these three functions interlock, the agent stops being a text generator and becomes a system forming a closed loop with its environment. Code is the skeleton of that loop.

2. The Anatomy of a Harness: Three Layers

The survey decomposes the agent harness into three connected layers. Understanding this structure makes clear why modern agent systems are architected as they are.

2.1 Harness Interface — How Code Bridges Agent and Environment

Layer one is how code serves as the interface between the agent and its reasoning, action, and environment modeling. This is where the agent's perception of the world converts into action. The key components are Guides — structured documents like AGENTS.md that tell the agent what to do and how to behave — and Sensors — type checkers, linters, and test runners that tell the agent what went wrong.

It is worth noting that Claude Code's CLAUDE.md and OpenAI's AGENTS.md already fulfill this guide role in production systems today. These structured instruction documents are part of the harness, constraining and directing agent behavior as first-class participants — not documentation.

2.2 Harness Mechanisms — The Engine Behind Long-Horizon Execution

Layer two covers the mechanisms that make the harness actually run. The survey identifies four:

  • Planning: Decomposes long-horizon tasks through linear, structure-grounded, search-based, or orchestration-based strategies.
  • Memory: Maintains working state, semantic knowledge, experiential records, and shared interaction histories.
  • Tool Use: Connects agents to APIs, verification systems, and execution environments.
  • Control & Optimization: Uses plan-execute-verify loops with runtime feedback for iterative repair and adaptation.

The plan-execute-verify loop deserves emphasis. The agent does not merely produce an output; it executes the output, inspects the result, and decides the next move. Code structures that entire loop. Without code as harness, the loop cannot close.

2.3 Scaling the Harness — From Single to Multi-Agent

Layer three addresses how to extend the harness to multi-agent settings. When multiple agents (manager, coder, reviewer, tester) divide labor, shared code artifacts become the substrate for coordination. Agents reference the same repository, share the same test results, and act on the same ground truth. Code becomes the inter-agent communication medium and the shared source of truth.

3. Four Properties of a Good Harness

The survey specifies four properties that any agent harness must possess. These function as a requirements specification for harness design.

PropertyMeaningPractical Example
ExecutableIntended outcomes can be formally verifiedTest runners, code interpreters
InspectableStructured traces expose intermediate computationExecution logs, step-by-step traces
StatefulTask progress is persistently representedRepository state, memory structures
GovernedPermission boundaries and safety constraints are enforcedTool permission limits, sandboxed execution

These four properties are mutually reinforcing. Without executability, verification is impossible. Without statefulness, long-horizon tasks cannot be sustained. Without governance, there is no way to catch or prevent unintended agent behavior. A trustworthy agent system requires all four working together.

4. The Rise of Harness Engineering: Agent = Model + Harness

Concurrent with the survey, 2026 has seen harness engineering emerge as a recognized discipline. The formula is simple: Agent = Model + Harness. If the model is the brain, the harness is the body and environment in which that brain operates.

The practical implication is significant. Conventional thinking says: use a better model, get a better agent. Harness engineering challenges this. With a frozen model, evolving the harness — system prompts, tool definitions, middleware, validation loops, memory structures, long-term memory — can dramatically improve agent performance.

The empirical evidence is real. The Agentic Harness Engineering (AHE) work achieved 84.7% on Terminal-Bench 2 by evolving only the harness around a fixed base model. It lifted GPT-5.4 from 69.7% to 77.0% across 10 iterations. Harness improvement can substitute for or complement model upgrades.

What I find particularly compelling about this is the portability implication. A well-designed harness largely preserves agent behavior even when the underlying model is swapped. That is a structural hedge against vendor lock-in: invest in the harness, and the system becomes model-agnostic over time.

5. The Expanded Meaning of Code: Tool Definitions, AGENTS.md, Execution Traces

From the harness perspective, the scope of "code" extends well beyond source files. The survey defines code broadly as "executable or machine-checkable artifacts," including:

  • Programs, scripts, formal specifications
  • Proof scripts, API schemas, tool definitions
  • Tests, repositories, simulators, configuration files
  • Code-adjacent artifacts: execution traces, logs
  • Guide documents like AGENTS.md

Tool definitions appear on that list. The schema that tells an agent which tools it can use and how is a core harness component. A 2025 study cited in the survey makes this concrete: agents that succeed with 10 tools functionally fail with 107. The non-linear performance cliff is counter-intuitive but consistent. Too many tools overwhelm rather than empower agents. Harness design requires active tool hygiene — pruning, clarifying, and scoping tool availability — as a first-class performance lever.

Guide documents like AGENTS.md carry equal weight. They are not explanations; they are executable constraints that agents read at runtime to determine how to act. As confirmed in Claude Code's architecture, these files are assembled alongside the system prompt as user content — a first-class part of the harness, not an afterthought.

6. Long-Horizon Execution and the Harness

Long-horizon execution remains one of the hardest unsolved problems in agentic AI. Single-turn tasks can be impressive. Multi-step agents that plan, execute, reflect, and maintain goals across dozens of steps are still fragile.

The harness offers a structural answer. Memory structures prevent the agent from losing its place in a long task. Planning layers decompose the task into executable units. Verification loops confirm intermediate results and redirect when necessary. When these three are implemented as code in the harness, the agent can self-correct structurally as it proceeds.

The critical point here is where verification lives. Verification is not an after-the-fact human review of final output. It is embedded in the execution loop — a gate the agent itself passes through. Tests that fail halt forward progress. This is the self-correcting capacity that code harnesses uniquely provide.

7. Multi-Agent Systems and Shared Code Substrate

Beyond single agents, multi-agent systems raise the harness stakes. When a manager agent, a coding agent, a review agent, and a test agent collaborate, natural language messages alone cannot coordinate them reliably. Shared repository state, a common test suite, and shared tool definitions provide the structural ground for coordination.

This is what the survey means by shared code artifacts. In a multi-agent system, consistent shared state requires all agents to act relative to the same code substrate. Without it, one agent overwrites another's changes or agents build on conflicting assumptions. Code becomes the single source of truth across distributed agent activity.

8. Open Challenges: What the Survey Does Not Yet Answer

The survey names six open challenges honestly. These are not weaknesses of the harness paradigm but the research agenda for what comes next.

  1. Evaluation beyond final success: Metrics for intermediate harness reliability are still lacking.
  2. Verification under incomplete feedback: How to assess semantic correctness without full oracles.
  3. Regression-free harness evolution: How to improve the harness without degrading existing capabilities.
  4. Shared state consistency across agents: How to enforce transactional semantics in multi-agent concurrent modification.
  5. Human-in-the-loop safety: How to encode accountability as executable harness state in safety-critical tasks.
  6. Multimodal extensions: How to extend code harness interfaces to vision, robotics, and perception.

Verification under incomplete feedback deserves particular attention. Real-world agents operate outside ideal test environments. How an agent confirms whether its actions were correct when the feedback signal is partial or delayed is an intensely practical engineering problem that the harness framing surfaces clearly.

9. Practical Implications: What Should Change

The Code as Agent Harness survey is academic framing, but the practical implications I draw from it are specific.

9.1 Design the harness before selecting a model

The first question in most agent projects is still "which model should we use?" The harness view says this question comes too early. Decide first: what tools will the agent access, what validation loops exist, what memory structure is in place. Then select a model that fits the harness. The same model in a different harness is a completely different agent.

9.2 Treat AGENTS.md and tool definitions as code

AGENTS.md, system prompts, and tool definitions are not documentation. They are executable specifications that determine agent behavior. They need version control, testing, and review processes. The entire team must understand that changes to the harness change agent behavior — with the same seriousness as changing source code.

9.3 Practice tool hygiene: fewer, clearer tools

The empirical finding of non-linear performance degradation with more tools is actionable today. Audit your agent's tool set: remove ambiguous or redundant tools, sharpen tool descriptions, and scope availability to the task context. Fewer well-defined tools consistently outperform many loosely defined ones.

Conclusion: Harness Engineers Are the Infrastructure Architects of the Agent Era

What the Code as Agent Harness survey describes is not a world where code becomes more important but a world where code's role changes. In an era where agents generate code, the structure that wraps and sustains those code-generating agents is itself code. Code is simultaneously the product and the foundation.

Harness engineering as a discipline emerges from this reality. Agent system performance is not determined by the model alone. The harness — tool definitions, guide documents, verification loops, memory structures, permission boundaries — co-determines it. Designing and evolving that harness is the infrastructure engineering of the agent era.

As of June 2026, agentic AI is still moving fast. But the framework this survey provides is a reliable compass for reading the direction of that movement. How you write code matters. But increasingly, what you wrap that code around matters just as much.
