被删除的包名为什么还在持续收到请求 - 消失的是代码，留下的是引用

删除并不是把名字腾空。断不掉的，是把那个名字写下来的引用

2026-09-11 开发/基础设施

某个包被判定为恶意，从注册表上被撤下。可是在那之后，指向这个名字的安装请求依然每周到来数百次。如果这句话听上去前后不搭，那说明还没有把删除这个动作到底切断了什么、又有什么是它始终切不断的分开。

要分开的只有一件事。删除切断的是新代码以那个名字发出去的通路，它并不会跑进谁的文件里去改写那个名字。代码消失了，引用还留着。留着的引用会在预定的时刻再发一次同样的请求。那个请求落进计数器，计数器又变成「到现在还有人在安装」这句话绕回来。

这里还分出第二件事。被腾出来的位置真的空了吗。至少在 npm 上并没有空着。恶意判定之后的处理流程里，公开文档写着要在那个位置立一块安全标记的步骤。所以这个问题准确的名字不是「空着的名字很危险」，而是「从未被切断的引用仍然指着那个名字」。

下文的依据是 npm 的两份公开政策文档、npm 说明下载统计如何产生的那份文档，以及引出这件事的仓库里的清单文档。被判定为恶意的包的真实名称不写在这里，写出名字只会把搜索引向它们。对厂商或运营方的评价也不在范围内，正文里的命令示例全部只读。

起因 - 一份被删名字仍在收请求的清单

引出这件事的，是某个公开仓库里的一份清单和生成那份清单的工具。生成方式决定了结论能走多远，所以先从方式说起。

以广泛使用的 npm 包240 个作为种子，机械地套用五种包名常见的走样方式来生成候选名。去掉作用域，把点和连字符互换，删掉连字符，去掉插件前缀，在后面接一个短后缀。这样得到的 npm 侧候选是 773 个，其中 263 个确实存在于注册表。工具判定为危险等级的有 130 个，其中公开进清单的是 50 个，剩下 80 个没有公开。

公开门槛设得很窄，这一点很重要。清单文档写明只考虑危险等级，而且在其中只有证据属于两类之一时才收录。一类是 npm 自己立起来的安全标记，另一类是点名真实包的弃用提示文字。所以公开的 50 个分成位置上立着标记的 36 条与带有弃用提示的 14 条。

这份清单还带着生成时间。文档上写的生成日是 2026-09-10，并且明确说明每周重新生成。把这件事带出来的那篇文章标题给的值是 35，而那一节里的行数是 36。两个值并不是谁对谁错，更自然的读法是它们属于不同的周次。把一份每周重生成的清单里的数字当成固定事实去引用，从那一刻起它就开始偏了。

那个数字实际数的是什么

在引用一个数字之前，先立住它没有数什么会更稳妥，因为调查的母集合本身就是窄的。

  • 没有数的 — 至今为止因恶意内容被撤下的包的总数。对象集合是由 240 个种子派生出来的候选，凡是那套派生规则生成不出来的名字，一开始就不在候选之列。这个数字不是全量普查的结果，原文也没有那样呈现它。
  • 数了的 — 在那个候选集合里，确实存在于注册表、被工具判为危险等级、并且其证据是 npm 自己立的安全标记的名字数量。是三个条件同时成立的交集。
  • 会变动的原因 — 清单每周重建，每一行的安装次数也随之重新查询。新标记立起来它就增加，工具的判定规则一改它又往别的方向走。这样得到的数是读数，不是常量。

所以准确地读，这份清单说的是：在按包名常见走样方式生成的候选里，有三十几个是 npm 出于安全原因撤下并立了标记的名字，而这些名字上仍然有请求到达。这和「35 个恶意包至今仍在流通」是两句不同的话。

删除之后名字会怎样

本文的主轴就在这里。npm 在处理恶意代码举报时写进文档的流程是三步。

  • 把该包从注册表移除。
  • 在该包的位置发布一个充当安全标记的包。
  • 发出告知社区的安全公告。

第二步纠正了本文开头立下的那个前提。被腾出来的位置并不空。那里立着一块牌子，意思大致是「原本在这儿的东西因安全原因被撤下了」。名字并没有开放，那个坐标上依然有东西在应答。

结果朝两个方向分开。从发出请求的一侧看，安装多半会失败，即便成功，进树的也只是一个没有功能的标记。从注册表一侧看，那却是被正常应答的一次请求。后面关于统计的讨论正是在这里分岔：风险被兑现的次数与请求到达的次数不是同一个值。

因此「删除会把名字腾空」这种说法，至少在这个注册表上并不成立。真正留下来的问题不是空位，而是依然指着那个位置的引用。剩下一半的章节都在处理这些引用。

让同一个坐标无法被再次占用的规则

取消发布的政策把名字和版本分开对待，而这个区分直接连着锁文件到底固定住了什么。

  • 名字与版本的组合不会被复用。一旦用过就再也不能用，即便撤下了也必须用新的版本号发布，这是政策文档自己的措辞，不是从行为里推出来的。
  • 把全部版本撤下会附带等待时间。要以那个名字发布新版本，必须等 24 小时过去。
  • 能自行撤下的条件本身就很窄。发布后 72 小时以内，只要没有别的包依赖它就可以撤下；超过 72 小时之后，三个条件必须同时满足：没有包依赖它、过去一周的下载少于 300 次、只有一个所有者。

这些规则的方向汇成一条。不让别的内容住进一个已经发出去的坐标。锁文件抓住的坐标是名字、版本、解析后的地址与完整性哈希的组合，其中名字与版本这一半在注册表层面被固定之后，「同一个坐标、不同的内容」这条通路就被大幅收窄了。

不过这是防止坐标被复用的规则，而不是强制清理引用的规则。自己仓库的锁文件依然指着那个坐标，这一点不会因注册表的规则而改变。至于一开始就少背依赖的判断，在「更少」地复用软件这个选择里另行讨论过。

别的注册表定得不一样

同样的情形，别的注册表用另一套方式处理。并排看会让「空位」这个说法为什么不准确变得更清楚。

  • 名字保留原则先立起来。Python 包索引的公开文档把「不会仅因为项目被弃置就将其从索引中移除」这条原则放在前面，理由是上传到索引的产物本身具有历史价值。
  • 文件名同样不许复用。文档写明即便项目被删除后又重新创建，先前用过的文件名也不能再次使用。方向与 npm 关于名字版本组合的规定一致。
  • 恶意举报的处理方式曾经不同。公告里写着，此前管理者手上可用的手段只有把项目从数据库中整个删除这一条，而且这个动作往往伴随着禁止该项目名被再次使用。他们指出这种方式的问题在于撤销几乎是不可能的。

于是引入了隔离这个中间状态。被隔离的项目会从可安装的索引中消失、无法被装上，但若属于误判则可以恢复回来。在只有彻底删除可用的局面里，新造出了一个可以撤回的档位。

把两个注册表并排放，一条轴就显出来了。一边是在位置上立牌子，另一边是把位置清空并上锁。做法几乎相反，但有一个共同点：两边都没有把那个名字敞开给任何人去取。风险的重心落在引用这一侧，而不是名字这一侧。

请求持续到来的原因 - 引用还在

一次安装请求，并不意味着有人刚刚敲下了那个名字。绝大多数情况下它意味着早就写在某处的名字被原样读了回去。制造请求的是文件的内容，而不是某个人的决定。

这个区分一旦立住，「为什么还在被安装」这个问题的形状就变了。要回答的不是谁的疏忽，而是哪些文件抓着那个名字，那些文件又为什么不更新。不更新通常是有理由的，而且这些理由往往在技术上站得住。标签按定义就不该被改写，要复现旧的构建就得让旧的副本留着。

删除治不了的恰恰是这个「被写着」。无论注册表那边做了什么，自己仓库锁文件里的那一行都还在。所以对策的位置也随之挪动：与其去追注册表删了什么，不如先把自己这一侧残留的引用数一遍。

引用残留的各层，以及各层为何不更新

引用残留的地方不止一处。每一层不更新的理由都不同，理由不同，该做的事也就不同。

机器读的那些地方

前五层不用人碰也会自己制造请求。把统计里出现的请求的大部分归给它们是合理的，因为它们靠的是时刻表而不是人的注意力。

人读的那些地方

后三层不直接制造请求，但它们会不断生出新的引用。文档里留着一行，读到的人就会把同样一行写进新的仓库。如果说前面那组制造的是本周的请求，后面这组制造的就是下个季度的请求。

残留的位置那里写着什么为什么不更新只靠读取如何确认
锁文件名字、版本、解析后的地址、完整性哈希只有在升依赖时才会更新，而升级本身被当作回归风险一再推迟在锁文件里搜那个名字，再把该条目的地址与哈希一起读出来
未合并的分支当时的清单与整份锁文件在被合并或删除之前会原样留着，分支越老越没有主人不只看当前检出，而是对仓库的全部引用做字符串搜索
标签与发行版出货时刻被固定下来的整套依赖标签按定义不该改写，改写会毁掉可复现性读标签所指向的那棵树里的清单
CI 缓存绑在还原键上的整棵依赖树缓存键若由锁文件哈希推导，只要锁文件不变，同一棵树就会一直被还原读缓存键的定义与流水线里的还原步骤配置
内部代理与镜像曾经拉取过一次的 tarball 副本上游删除不会自动清掉本地副本，清掉又会毁掉依赖它的所有历史构建读代理的保留策略与远程仓库清单
容器镜像层构建时刻装进去的产物镜像在重新构建之前就是那样，基础镜像被钉住时会留得更久读镜像标签与构建时使用的清单
文档、示例与被复制的代码一行安装命令和一段清单片段文档常常没有主人，即使有也缺少回头修订旧页面的动机在内部文档库与维基里搜那个名字
依赖更新机器人敞开着的更新提案及其基线提案不合并，基线就停在旧状态，机器人每个周期都会再确认一遍那个状态读敞开着的提案列表与机器人的配置文件

把表格竖着读第三列，会出来一条规则。不更新的理由里有一半是设计，不是缺陷。标签不变、代理攥着副本，都是为了可复现性才那样造出来的。所以若把这些层一律看成需要打扫的杂乱，就会以卫生之名破坏可复现性。

每周多少次这个值到底数了什么

npm 在解释下载统计时给出的定义很短。下载数是它返回过的、内容为 tarball 的 HTTP 200 响应的数量。它不数人，也不数安装有没有成功。它数的是响应。

里面还一并混进了什么，同一份文档也写了：自动构建服务器发出的请求、镜像同步发出的请求、逐个抓取全部包的分析机器人的请求，全都包含在内。不做过滤的理由也一并写着——准确辨别自动流量本身就很难，而且对构建工具这类包来说，自动请求本身就是真实的使用。然后同一份文档把话钉死：这些不是绝对数字，也绝不等同于一个包的用户数。它还给了个粗略的下限，指出每天不到 50 次的数值很难与背景噪声区分开。

请求的性质是否计入是人的安装吗在本案中把数值往哪边推
开发者第一次安装计入是基线。真正想数的就是这个
CI 每次构建都去取计入不是大幅放大。单个仓库一天就能造出几十次
镜像与代理的同步计入不是放大。一个名字被镜像的数量乘一遍
全量抓取机器人与研究性扫描计入不是放大。立了标记的名字反而更容易成为被调查的对象
安全扫描器读取元数据只有取 tarball 时才计入不是因工具而异，根本无法给它定一个方向
由本地缓存满足的安装不计入是缩小。真实的人的安装被漏掉
内部代理用缓存直接应答不计入是缩小。组织越大漏掉得越多

最后两行是这张表的要点。这个值并不只往一个方向偏。它因自动流量而膨胀，同时又因为缓存满足的安装根本到不了计数器而缩水。两项误差各自多大都不知道，就没有方向可供校正。说「实际肯定比这个少」和说「实际肯定比这个多」一样没有依据。

这个数字能读出什么，读不出什么

话虽如此，这个值并非无用。它能不能回答，完全取决于向它提什么问题，所以两边都值得写出来。

先立能读出来的。

  • 它不是零。这一条是确定的。指向那个名字的请求通路仍然活着，这个事实不管数值多少都成立。
  • 同一口径数出来的值之间的趋势。上周和这周若用同样的方法数，在涨还是在落是读得出来的。绝对值不可信，斜率仍可看。
  • 数量级的差别。每周几次和每周几千次是两种状态。就算有两倍的误差，数量级也翻不过来。

读不出来的是这些。

  • 有多少人被暴露。从响应数走到人数之间不存在换算系数。
  • 有多少个组织受影响。一个组织可以造出几千次，而几百个组织躲在缓存后面可以一次都不造。
  • 其中有多少次真的执行了代码。本案这批名字上已经立着安全标记，所以请求取回去的是标记而不是恶意代码。

第三条改变了这个数字的性质。因此这个值更准确的读法不是「现在有多少人正在被感染」，而是「还有多少条通路指着那个名字」的代理指标。它作为预警信号的价值依然完好：今天取回一块标记的通路，和明天可能从别的名字取回真代码的通路是同一类。

这和抢注相似包名不是同一个问题

这两件事常被当作一个话题来谈，但它们瞄准的位置相反。混在一起会让两边的对策都变松。

打错字诱饵冲着还没有人写下来的名字去。它盯的是人手打时容易滑的位置，成立的前提是「有人新犯一次错」。正因如此，相似度检查和名单对它确实很有效。而本文的情形正好相反：名字早就写得准确无误，只是写着它的地方从来不更新。哪怕一次新的打错都不发生，请求也照样往外发。

这里还要加上一条近年的轴：代码助手会造出并不存在的包名。引出这件事的仓库所引用的数值是，生成的包名里有 19.7% 属于凭空捏造，而把同样的请求再跑一遍时，其中 43% 又原样出现了同一个名字。这条轴上重要的不是比例而是可重复性。如果每次冒出来的都是不同的名字，那更接近噪声；同一个名字反复出现，那个名字就实际上变成了一个固定的地址。

轴打错字诱饵被删的名字与残留引用工具造出来的名字
瞄准的名字与真实名字相近的名字恰好就是那个名字从来没人创建过的名字
名字被写下的时点人在手打的时候很早以前就已经写下了工具给出建议的时候
扳机新发生的打错从未更新的文件建议被原样采纳的那一刻

真正管用的对策名字检查与相似度判定完整性固定与引用清理先看被建议的名字是否真实存在

中间一列与右边一列相交的地方，正是这份清单实际站着的位置：工具造出来的名字可能与已经因安全原因被撤下的名字重合。这就是为什么调查方式是「用名字走样规则生成候选再与注册表比对」，而结果撞上的是安全标记。

用名单去挡会从哪里漏

「列一份危险名字清单然后拦掉」是最先冒出来的对策，但在这个问题上它站的地方很窄。会漏的地方有四处。

  • 名单天然是过去式。只有已经知道的名字才会进去。新标记立起来的那一刻起，那个名字就在名单之外，名单的刷新周期有多长，敞开的窗口就有多宽。
  • 名单卡的是精确字符串。作用域有无、大小写、一个分隔符不同，就从旁边溜走了。这个问题里的候选名本就是用那类变形生成的，瞄准方向偏得相当根本。
  • 名单大多只扫直接依赖。清单里写着的名字它看得见，但从锁文件深处被间接拉进来的名字容易漏掉，而残留引用里相当一部分正在那边。
  • 名单看名字不看内容。同一个名字换个版本进来时，只要名字对得上就一路放行。

所以以名字为对象的防御应当放在辅助信号的位置。主轴在别处：把进来的东西按内容而不是按名字固定住。至于再下一层的问题——信任链条究竟从哪里开始——在引导信任崩塌的地方里另行处理过。

各种防御挡得住什么、挡不住什么

每种手段都有它挡得住的地方和会松的地方。列成表格，就能看出哪两种必须叠在一起用。

手段挡得住的挡不住的付出的代价
锁文件里的完整性哈希同一坐标上换了内容；传输途中被改动内容从第一次发布起就是恶意的；哈希连同内容一起被更新的情形几乎没有。把锁文件提交上去照着用就行
完全依照锁文件的可复现安装依赖树在每次构建之间悄悄变化已经写在锁文件里的名字依赖升级变成一件单独排期的工作
版本钉住与经过评审的升级未经预告的上游新版本流入被钉住的那个版本自身的缺陷升级滞后，安全修复也跟着一起晚到
私有注册表的许可名单名单之外的名字进入组织内部已经在名单里的名字名单的运营成本，每个新依赖都要走审批
阻断安装脚本安装时刻发生的代码执行应用运行期间跑的代码依赖安装脚本的包会坏掉
隔离的构建环境向凭据与内网的扩散产物本身被污染环境的搭建与维护成本
经由私有代理不知道究竟哪些名字被真的拉过代理缓存里已经存着的旧副本缓存保留策略需要另行制定
与依赖清单比对不知道里面装了什么的状态清单做完之后发生变化的部分维持清单新鲜度所需的工作

把表格竖着读，会掉出一条规则。凡是看名字的手段，都在「名字早就在名单里面」这一点上失效；凡是固定内容的手段，都在「内容从一开始就是那样」这一点上失效。两类必须叠着用的理由就在这里。只用其中一类，另一侧就整个敞着。

补一句：把升级往后拖同样是有代价的选择。关于什么该在什么时候升的判断，在怎么读发行说明里讨论过。攥着版本不动在这个问题上是安全的一侧，在另一个问题上却相反。

只靠读取来体检自己仓库的顺序

从这里开始是实际的顺序。判断所需的一切都从读取里出来，不需要安装，不需要删除，也不需要发布。

从锁文件里读的三样

锁文件的一个条目里装着三样东西，三样一起读才能立住判断：它冻结在哪个版本，从哪里取回来，以及用什么值来验证取回来的就是它。

# package-lock.json 一个条目里的三样东西
"node_modules/<名字>": {
  "version":   "1.2.3",                        # 冻结在哪个版本
  "resolved":  "https://registry.example/...", # 从哪里取回来
  "integrity": "sha512-..."                    # 验证取回来的就是它的值
}

# 读取已安装的依赖树 - 什么都不改动
npm ls --all              # 整棵树里真实的名字与版本
npm ls <名字>              # 那个名字挂在树的什么位置
npm explain <名字>         # 是谁把它拉进来的，以路径呈现

在整个仓库范围里清点引用

只看一份锁文件，看到的只是当前检出的那个分支的状态。残留的引用往往在那之外，所以第二遍要扩到全部引用。

# 工作树里残留的引用
grep -rn '"<名字>"' --include=package.json .
grep -rn '"<名字>"' --include=package-lock.json .

# 连未合并的分支与标签一起 - 不下载，只看名字
git grep -n '<名字>' -- '*.json'
git grep -n '<名字>' $(git for-each-ref --format='%(refname:short)' refs/heads)

# 注册表那个位置上立着什么 - 只读元数据
npm view <名字> --json    # 不安装，只取回元数据
npm view <名字> versions
顺序做什么用什么来判定该在这里停下的情形
1看锁文件有没有被提交进仓库文件是否存在，以及最后更新的时点没有的话后面全都没有意义，先把锁文件提交上去
2在锁文件里搜那个名字有没有匹配的条目没有也不算完，再从依赖树把间接依赖过一遍
3读那个条目里解析后的地址是公开注册表还是内部代理地址与预期不符时，先从依赖配置看起
4看完整性哈希有没有填上每个条目上是否有哈希值只要有条目是空的，那个条目就处在没被固定的状态
5从已安装的树里读真实的名字与版本树的输出与锁文件是否一致对不上就说明安装并没有照着锁文件走
6以路径查出是谁把那个名字拉进来的依赖路径开头的那个直接依赖路径不止一条时全部记下来，只改一条会有残留
7看未合并的分支与标签里还有没有对全部引用做的字符串搜索还留着的话，先定下那个分支的处置方针
8只读元数据，看注册表那边立着什么有没有安全标记，以及弃用提示文字立着标记就说明那个名字属于要清理引用的对象

这八步里没有任何一步会改变状态。而这套顺序的产出不是「安全」这个判定，而是一份引用残留位置的清单。清单出来之后，逐层决定该做什么的工作才开始：标签可以原样不动而只订正文档，代理缓存可以留着而只在新构建里挡掉。

小结 - 四句话

把上面的内容压成四句话，是这样。

  • 删除切断代码，不切断引用。注册表那边做什么，自己锁文件里的那一行都还在原处。
  • 至少在 npm 上被删掉的名字并不是空的。处理流程里写着要在那个位置立一块标记，而这改变了指向那个名字的请求究竟取回什么。
  • 每周多少次是响应的数量，不是人的数量。它因自动流量而膨胀、因缓存而缩水，不能直接拿去估算被暴露的人数。
  • 看名字的手段和固定内容的手段会从不同的地方漏。所以不是二选一，而是叠着用。

落到实务上只剩一句。最便宜的事情，是把锁文件保持在已提交的状态，并把里面解析后的地址与完整性哈希读一遍。它排在扩充名单之前，成本也低到不成比例。

未能确认的部分

以下各项在本文的调查范围内未能依一手资料得出结论。在依据齐备之前不作断言。

  • 安全标记是否永久 — npm 的公开文档只写到恶意判定时会发布标记这一步。那块标记是否被永久保留、别人在什么条件下可以接手那个名字，政策文档里找不到对应的句子。因此正文把「名字不会被腾空」作为已确定的范围来处理。
  • 清单里的安装次数是按哪个窗口统计的 — 清单文档只有列标题，没有交代来源的句子。工具一侧的文档写着使用 npm 的下载查询并设有六小时缓存，但这一句并没有接到清单中每个数值取的是哪一段时间，所以无法确定。
  • 19.7% 与 43% 的原始出处 — 这两个数值是引出本文的仓库所引用的。原始研究的正文与测量条件不在本次调查范围内，并未打开，因此它们出自哪些模型、哪一组提示词，在此仍属未确认。
  • 标题里的 35 与文档里的 36 分别属于哪一周 — 清单每周重新生成，而文档中没有保留旧版本的历史，因而无法比对。正文把二者当作不同周次的值来处理。
  • 其他语言生态的处理方式 — Rust、Ruby、Go 一侧注册表的删除与名字处理政策，引出本文的工具并未涵盖，本次也没有纳入范围。本文的比较仅限于文中提到的两个注册表。
  • 组织内部究竟是哪一层在制造请求 — 这不是靠公开文档能回答的问题。只有各自组织的代理访问记录与构建记录才给得出答案，正文里的分层只是寻找答案的顺序，而不是对比例的估计。
