同一个文件名为何在每个 Shell 里都不一样

PowerShell 找不到 Git Bash 刚建好的那个名字

2026年8月10日 开发/基础设施

引言：同一个文件夹，名字却不一样

脚本在 Git Bash 里跑，部署走 PowerShell，构建放进 WSL —— 这在 Windows 开发机上是很常见的组合。在这套组合里处理带空格或非 ASCII 字符的文件名，迟早会碰到讲不通的事：Git Bash 明明列得出来的文件，PowerShell 脚本说「不存在」。

# Git Bash 一侧
$ ls -1
x?y.txt

# PowerShell 一侧 —— 同一个文件夹，同一个文件
PS> Test-Path -LiteralPath '.\x?y.txt'
False

文件就在那里，没有被删也没有被隐藏。只是两个 shell 用两个不同的名字记住了同一个文件。这类错位不止发生在名字里的一个问号上。大小写、区域设置、Unicode 规范化、清单文件的编码，各自在各自的边界上分岔，而且每一次分岔都是安静的：不报错，只是结果不对。

本文逐个走一遍这些边界。引号语法本身已经写在Shell 引号规则 - 哪个引号挡住了什么里，把带空格和换行的名字通过 find 与 xargs 传递的实战组合写在find 与 xargs 的空格换行陷阱里。这里讲的是再往后一层：引号都加对了，可换一个工具名字就变了的那些地方。

本文覆盖的边界
  1. Windows 禁止字符与私用区置换 —— Git Bash 和 PowerShell 分岔的地方
  2. 不区分大小写的文件系统 —— 建两个只剩一个
  3. Git Bash 的路径自动转换 —— 参数在半路被改写
  4. PowerShell 5.1 的原生传参 —— 引号和空字符串会消失
  5. 默认编码与清单文件 —— BOM、CR 与 CP949
  6. 区域设置改变 bash 本身的三个地方
  7. 合成形与分解形共处一个文件夹时

1. 运行环境 —— 本文的依据

下面所有输出都来自这套环境。其中有好几项会随版本变化，所以先钉住。

  • 操作系统：Windows 10 Pro，版本 19045，文件系统 NTFS
  • Shell 1：Git for Windows 自带的 bash 5.2.37(1)-release，内核串为 MINGW64_NT-10.0-19045 … 3.5.7 … Msys
  • Shell 2：Windows PowerShell 5.1.19041.6456
  • 区域设置：LANG 与 LC_ALL 未设置，LC_CTYPE 为 C.UTF-8
  • 系统 ANSI 代码页：ks_c_5601-1987，即韩文 Windows 的 CP949
  • 查看参数用的外部程序：Node.js v22.16.0，原样打印 process.argv
  • WSL：wsl.exe 存在，但没有安装任何发行版，因此本文对 WSL 没有任何实测（见第 15 节）

所有实验都在一个空的临时目录里进行。本文的示例一律写成不删除任何文件的形式。要看清参数是怎么被切开的，echo 和 printf 就够了，而且这样照着试也安全。

2. 名字是字节串，每一层的规则都不同

一个文件名到达屏幕之前至少要经过三层。每层存储和解释名字的方式不同，转换发生在边界上。

  • 文件系统 —— NTFS 把名字存成 UTF-16 码元序列。它不做规范化，并且禁止若干字符。
  • Shell 与工具 —— POSIX 系工具把名字当作字节串。这些字节代表哪种编码，由区域设置决定。
  • 屏幕 —— 由字体画出来。字节不同也可能画出同一幅图。

第三点贯穿全文。眼睛看到的不算证据。名字可疑就去看字节，而这个手段到哪儿都一样。

$ printf '%s' "회의 자료.txt" | od -An -tx1
 ed 9a 8c ec 9d 98 20 ec 9e 90 eb a3 8c 2e 74 78 74

把这一行养成条件反射，排查时间会大幅缩短。比字节，不要比字形。

3. PowerShell 找不到 Git Bash 建的名字 —— 0xF000 置换

Windows 规定了一批不能出现在文件名里的字符。Cygwin 文档把它们描述为「ASCII 值 1 到 31 的控制字符，加上在 Win32 API 中具有特殊含义的下列字符」，并列出 " * : < > ? | \。但在 Git Bash 里，这样的名字建起来毫无阻力。

$ for c in '<' '>' ':' '"' '|' '?' '*'; do printf 'x\n' > "x${c}y.txt"; done
$ ls -1
x"y.txt
x*y.txt
x:y.txt
x<y.txt
x>y.txt
x?y.txt
x|y.txt

在 Git Bash 一侧把名字的字节打出来，和敲进去的一模一样：冒号是 3a，问号是 3f。可是从 Windows 一侧读同样这些文件，回来的却是别的码位。

PS> Get-ChildItem | ForEach-Object {
      ($_.Name.ToCharArray() | ForEach-Object { 'U+{0:X4}' -f [int]$_ }) -join ' '
    }
U+0078 U+F009 U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F00A U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F022 U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F02A U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F03A U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F03C U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F03E U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F03F U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F07C U+0079 U+002E U+0074 U+0078 U+0074

规律一眼就看得出：给禁止字符的码位加上 0xF000，挪进私用区。Cygwin 文档正是这么写的 —— 除反斜杠以外，上述字符在「创建或访问文件时，通过给禁止字符的码位加上 0xf000，被转换为 0xf000 到 0xf0ff 范围（私用区）内的特殊 UNICODE 字符」。反斜杠之所以例外，是因为它是路径分隔符。

敲入的字符原码位存储的码位存储名的 UTF-8 字节
制表符U+0009U+F009EF 80 89
换行U+000AU+F00AEF 80 8A

Git Bash 读目录时会把这个映射反过来，所以那一侧看不出问题。问题出在不做反向映射的工具上。

PS> Test-Path -LiteralPath '.\x?y.txt'
False

PS> Test-Path -LiteralPath '.\x|y.txt'
Test-Path : Illegal characters in path.

PS> $pua = 'x' + [char]0xF03F + 'y.txt'
PS> Test-Path -LiteralPath ".\$pua"
True

含竖线的名字返回的不是假，而是抛异常。Windows API 不允许这个字符出现在路径里，查询根本不成立。只有用私用区字符拼出来的名字才返回真。等于同一个文件有两个名字。

它在实际工作里咬人的时刻
典型场景是：Git Bash 跑的脚本产出日志或报表文件，再由 PowerShell 部署脚本去取。想把时间戳放进名字，用了 %H:%M 格式就带进一个冒号，从那一刻起两个 shell 就开始把它当成不同的文件。时间戳里用连字符而不用冒号的习惯不是迷信，正是绕开这个问题的规则。

另外，Cygwin 文档还单独讲了设备名（AUX、COM1、LPT1、PRN 等）和名字末尾的点与空格。设备名不能被原生 Win32 程序用作文件名或扩展名，末尾的点和空格则「在创建文件之前全部被去掉」。Cygwin 系程序可以绕过这些限制把文件建出来，而建出来之后用资源管理器或常规 Windows 工具很难清理。这不是拿来做实验的东西。答案是不要建。

4. 大小写 —— 建两个只剩一个

这是在 Linux 上跑得好好的脚本，到 Windows 上悄悄丢一个文件的经典位置。

$ printf '대문자\n' > "README.txt"
$ printf '소문자\n' > "readme.txt"
$ ls -1
README.txt
$ cat README.txt
소문자

只有一个文件。可是名字留的是先建的那个，内容留的是后写的那个。NTFS 默认配置不区分大小写但保留原始写法。第二次重定向没有新建文件，而是打开已有文件覆盖了它。

  • 仓库里若有仅大小写不同的同名路径，Windows 检出时会丢掉其中一个。
  • 一个脚本写 Config.json、另一个脚本读 config.json 的组合，只在 Linux 上失败。失败暴露得晚，方向更糟。
  • 没有大小写之分的文字写成的名字可以躲开这一条，代价是把后面各节的问题全接下来。

5. Git Bash 的路径自动转换 —— 参数在半路被改写

Git Bash 调用原生 Windows 可执行文件时，会把看起来像 POSIX 路径的参数改写成 Windows 路径再传过去。Shell 内建命令没有这道转换。

$ node -e 'console.log(JSON.stringify(process.argv.slice(1)))' "/usr/bin" "a/b" "-Dfoo=/bar"
["C:/Program Files/Git/usr/bin","a/b","-Dfoo=C:/Program Files/Git/bar"]

$ printf '%s\n' "/usr/bin"
/usr/bin

三件事同时浮出来。第一，/usr/bin 被重新解释到了 Git 安装目录之下。第二，开头没有斜杠的 a/b 没被动。第三也是最麻烦的 —— 像 -Dfoo=/bar 这样等号后面的值也被转换了。哪怕它本来是应用选项而不是路径，结果一样。

把容器卷挂载或 REST 路径当参数传的时候，这道转换会悄悄毁掉值。关掉它只需要一个环境变量。

$ MSYS_NO_PATHCONV=1 node -e 'console.log(JSON.stringify(process.argv.slice(1)))' \
      "/usr/bin" "a/b" "-Dfoo=/bar"
["/usr/bin","a/b","-Dfoo=/bar"]
  • 只想作用于一条命令就像上面那样前置使用。整个脚本都设上会连真正该当作路径的参数一起停止转换，所以范围窄一点更好。
  • 以两个斜杠开头（//c）来绕过转换的写法在部分场合可行，前提是接收方程序接受这种形式。
  • 这道转换只作用于原生可执行文件的调用。bash 内建和 MSYS 构建的工具不受影响，于是同一个字符串会因命令不同而以不同形式抵达。

6. PowerShell 5.1 —— 没有词分割，但参数会消失

切到 PowerShell，bash 里的一个老问题直接消失了：没有词分割。含空格的变量不加引号也是一个参数。

PS> $f = '회의 자료.txt'
PS> node -e 'process.argv.slice(1).forEach(function(a,i){console.log(i+String.fromCharCode(32)+a)})' $f 'a b.txt'
0 회의 자료.txt
1 a b.txt

在 bash 里去掉引号就会裂成两个的那个值，这里不加引号也是一个。但是取而代之，别的东西不见了。

PS> $s = 'a"b'
PS> $s.Length
3
PS> node -e 'console.log(JSON.stringify(process.argv.slice(1)))' $s
["ab"]

PS> node -e 'console.log(JSON.stringify(process.argv.slice(1)))' '' 'x'
["x"]

长度为 3 的字符串到接收方变成了 2。双引号悄无声息地没了。空字符串参数干脆从列表里掉了出去。既不报错也不告警。

原因写在文档里。调用原生命令时，PowerShell 「把解析后的参数拼接成一个字符串，各参数之间以空格分隔」，引号处理就在这次拼接中出错。PowerShell 7.3 改了传参方式，那份文档明确指出这个改动相对 Windows PowerShell 5.1 是破坏性变更，并写明新方式下「内嵌的引号会被保留」、「作为参数的空字符串会被保留」。换句话说，5.1 上面的结果不是 bug，而是已知行为。

如果被锁在 5.1 上，有三条路。

  • 停止解析记号 --% —— 把其后的文本按字面传过去。但正如文档所说，%变量% 形式的环境变量替换依然会发生，它只在遇到下一个换行或管道之前有效，而且其中的重定向也会被当作参数传出去。
  • Start-Process —— 用数组传参，命令行的拼装完全受控。
  • 升到 PowerShell 7 以上 —— 在 Windows 上新方式是默认，只有批处理文件和 cmd.exe 调用会退回旧方式。
陷阱在于它和 bash 恰好相反。在 bash 里，参数变多是因为你没加引号；在 PowerShell 5.1 里，参数变少是因为你加了引号。在两个 shell 之间移植同一个脚本时，要改的方向是互相反的。

7. -Path 与 -LiteralPath —— 一个方括号打开了另一个文件

bash 里没加引号的变量膨胀成通配的事故人尽皆知。PowerShell 也有同类陷阱，只不过它跟引号无关，是由参数名决定的。

放两个内容不同的文件 star1.txt 和 star[1].txt，去读带方括号的那个，情况如下。

# bash —— 由是否加引号决定
$ g='star[1].txt'
$ cat $g
star1 내용
$ cat "$g"
대괄호 파일 내용
# PowerShell —— 由参数名决定
PS> Get-Content -Path 'star[1].txt'
star1 내용
PS> Get-Content -LiteralPath 'star[1].txt'
대괄호 파일 내용

两边都不是「要了一个不存在的文件」，而是打开了另一个文件并安静地成功了。这种失败最难缠 —— 要是报个错，当场就发现了。

  • PowerShell 的 -Path 会解释通配符，*、?、[ ] 全是模式字符。
  • 来自用户输入或清单文件的名字，一律走 -LiteralPath。真实文件名里方括号很常见 —— 类似 [最终]报告.xlsx 这样的名字每天都在被创建。
  • bash 侧要做同样的防守，加引号即可；若只想让某个变量暂时不参与通配，用 set -f 单独关掉路径名展开也行。
$ v='star[1].txt'
$ echo $v          # 通配开启
star1.txt
$ set -f
$ echo $v          # 通配关闭
star[1].txt
$ set +f

8. 读写的默认编码 —— PowerShell 5.1 的 CP949

还有一类边界是名字传对了、内容却坏了。Git Bash 用 UTF-8 写的文件，PowerShell 5.1 来读：

PS> Get-Content -LiteralPath 'star1.txt'
star1 ?댁슜
PS> Get-Content -LiteralPath 'star1.txt' -Encoding UTF8
star1 내용

文件没问题，是读的一方选错了编码。Windows PowerShell 5.1 会用系统 ANSI 代码页读取没有字节顺序标记的文件。在韩文 Windows 上这个值是：

PS> [System.Text.Encoding]::Default.WebName
ks_c_5601-1987

写入端是对称的。把同一个字符串用两种方式存下来再拆字节，差别一目了然。

PS> Set-Content -LiteralPath 'a.txt' -Value '한글 저장'
PS> Set-Content -LiteralPath 'b.txt' -Value '한글 저장' -Encoding UTF8

a.txt : c7 d1 b1 db 20 c0 fa c0 e5 0d 0a
b.txt : ef bb bf ed 95 9c ea b8 80 20 ec a0 80 ec 9e a5 0d 0a
  • 默认存的那份以 c7 d1 开头，一个字两个字节，是 CP949。
  • UTF-8 那份以 ef bb bf 开头，带上了字节顺序标记。5.1 的 -Encoding UTF8 不是无 BOM 的 UTF-8。
  • 两份的行尾都是 0d 0a。这个 CRLF 就是下一节的原料。

从乱码的形状反推原因的方法，已经在定位韩文乱码发生的那一点 - cp949 与 UTF-8里列成表。压缩包里的名字乱掉则是另一套规则，那属于zip 文件名编码。

9. 用清单文件交接时 —— BOM 和 CR 会粘在名字上

把待处理清单做成文本文件交出去，是很常见的做法。把表格或记事本做的清单喂给 bash 循环，结果一个文件都不存在。原因有三个，而且三个都看不见。

$ while IFS= read -r f; do
      printf '읽은 값=[%s]  존재=%s\n' "$f" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"
  done < list_cp949.txt
읽은 값=[ȸ�� �ڷ�.txt]  존재=없음

$ … < list_utf8.txt      # 带 BOM 的 UTF-8
읽은 값=[﻿회의 자료.txt]  존재=없음

第一行是 CP949 字节，名字乱了。第二行肉眼看着正常，但开头粘了一个零宽的 BOM 字符，于是变成了另一个名字。第三个原因 CR 单独看是这样：

$ printf '회의 자료.txt\r\n' > list_crlf.txt
$ while IFS= read -r f; do printf '길이=%d 존재=%s\n' "${#f}" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"; done < list_crlf.txt
길이=18 존재=없음

$ while IFS= read -r f; do f=${f%$'\r'}; printf '길이=%d 존재=%s\n' "${#f}" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"; done < list_crlf.txt
길이=17 존재=있음

差一个字节，屏幕上什么也看不出来。接收清单去处理的脚本，最好一开始就把三件事一并处理干净。

$ iconv -f CP949 -t UTF-8 list.txt | sed '1s/^\xEF\xBB\xBF//' | tr -d '\r' \
  | while IFS= read -r f; do
        printf '읽은 값=[%s]  존재=%s\n' "$f" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"
    done
읽은 값=[회의 자료.txt]  존재=있음
  • 清单本来就是 UTF-8 就去掉 iconv，但去 BOM 和去 CR 要留着。这两样跟编码无关，都可能出现。
  • 如果能控制清单的生产方，一开始就用 NUL 分隔交接更好。那是唯一不可能出现在名字里的字节，边界不会被破坏。具体写法在find 与 xargs 的空格换行陷阱里。
  • read 去掉 -r 会吃掉反斜杠，对处理 Windows 路径的脚本是致命的 —— C:\temp\새 폴더 会变成 C:temp새 폴더。

10. 区域设置改变 bash 本身 —— 三个地方

这是最少被提及的一条轴：同一个 bash、同一个脚本，会因为区域设置不同而行为不同。在三个地方能看到。

10.1 ANSI-C 引用里的 Unicode 转义

Bash 手册把 $'string' 里的 \uHHHH 规定为 Unicode 字符转义。可实际结果受区域设置左右。

$ LC_ALL=C.UTF-8 bash -c "printf '%s' \$'\u00E9\uD55C' | od -An -tx1"
 c3 a9 ed 95 9c

$ LC_ALL=C bash -c "printf '%s' \$'\u00E9\uD55C' | od -An -tx1"
 e9 5c 75 44 35 35 43

UTF-8 区域设置下得到 c3 a9 和 ed 95 9c，即两个正确的字符。C 区域设置下 é 掉成单字节 e9，而另一个根本没被转换，原样留成 \uD55C 这六个字符（5c 75 44 35 35 43）。不报错，安静地变成字面量。

Git for Windows 默认安装下 LANG 是空的。也就是说默认状态就站在陷阱那一侧。脚本里打算用 Unicode 转义拼字符，就必须显式声明区域设置。

10.2 printf %q 的输出

这是把名字记成安全形式的常用手法，而它的输出形状随区域设置而变。

$ LC_ALL=C.UTF-8 bash -c "printf '%q\n' '회의 자료.txt'"
회의\ 자료.txt

$ LC_ALL=C bash -c "printf '%q\n' '회의 자료.txt'"
$'\232\214\235\230 \236\220\214.txt'

两种形式再喂回 shell 都能还原成同一个值，就功能而言都对。问题在日志。下面那种形状留下的日志人读不了，贴进工单也没人知道是哪个文件。

10.3 方括号里的字符范围

用 [가-힣] 这类范围筛出特定文字，是流传很广的习惯。这个范围在某些区域设置下会被当成字节范围而不是码位范围来解释。

$ for loc in C C.UTF-8 en_US.UTF-8 ko_KR.UTF-8; do
      a=$(printf '%s\n' "$NFC" | LC_ALL=$loc grep -cE '^[가-힣]+\.txt$')
      b=$(printf '%s\n' "$NFD" | LC_ALL=$loc grep -cE '^[가-힣]+\.txt$')
      echo "LC_ALL=$loc  composed=$a  decomposed=$b"
  done
LC_ALL=C          composed=1  decomposed=1
LC_ALL=C.UTF-8    composed=1  decomposed=0
LC_ALL=en_US.UTF-8 composed=1  decomposed=0
LC_ALL=ko_KR.UTF-8 composed=1  decomposed=0

C 区域设置下连拆开的名字也匹配上了，这是误报。UTF-8 区域设置下不匹配 —— 这一侧行为准确，但漏掉分解形这个另一个问题依然存在。无论哪一侧，单靠一个范围都表达不了「只要这一类名字」。

相比之下字面量搜索与区域设置无关。对同样两行执行 grep '한글'，在任何区域设置下结果都是 2 中 1。范围表达式出问题而字面量不出问题的原因，在下一节。

$'\uHHHH'（超出 Latin-1）不转换，留作字面量正确的 UTF-8 字节

11. 合成形与分解形共处一个文件夹时

NTFS 不对名字做规范化。因此屏幕上完全一样的两个文件可以共存于同一个文件夹。

$ ls -1
한글.txt
한글.txt

$ for f in *; do printf '%s  ' "$f"; printf '%s' "$f" | od -An -tx1 | tr -s ' ' | tr -d '\n'; echo; done
한글.txt   e1 84 92 e1 85 a1 e1 86 ab e1 84 80 e1 85 b3 e1 86 af 2e 74 78 74
한글.txt   ed 95 9c ea b8 80 2e 74 78 74

下面那个是合成形（NFC），一个音节三字节，整个名字十字节。上面那个是分解形（NFD），初声、中声、终声各占三字节，合计二十二字节。Unicode 标准附件 15 规定了各种规范化形式，并把这类文字点名为按算法分解与合成的特殊情形。

它在 shell 里怎么体现，才是实务上要紧的。

$ find . -maxdepth 1 -name '한글*' | wc -l
1

$ n=0; for f in 한글*; do n=$((n+1)); done; echo "$n"
1

$ ls -1 | sort | uniq | wc -l
2
  • Shell 通配和 find -name 都只抓到合成形那一个，因为用键盘敲出来的模式就是合成形。
  • sort 总把分解形排在前面，字母码位（U+1100 段）小于合成音节（U+AC00 段）。
  • uniq 把两者算作不同的行，去重脚本会回答「没有重复」。
  • 备份脚本用 find 生成清单时，分解形的文件会整个漏掉。这是遗漏而不是失败，所以连告警都不会有。

两种形式为何产生，以及在检索、排序、长度校验、序列化各个边界上会坏掉什么，写在韩文被拆成字母的瞬间 - NFC 与 NFD里。这里只留 shell 侧的结论就够：确定在流水线的哪一步做规范化，并把这个点写进文档。不定，各个工具就会在各自的时点规范化成各自的形式。

12. 跨越边界时靠得住的形式

到此为止的失败全都发生在同一个位置：把名字装进字符串再交给另一个工具。不装进去就不会坏。

在同一个 shell 里就用数组接。名字里有什么都无所谓，一个元素就是一个文件。

$ mapfile -d '' files < <(find . -maxdepth 1 -type f -print0)
$ echo "${#files[@]}"
$ printf '  [%s]\n' "${files[@]}"

执行之前先看看命令实际会收到哪些参数，也是又便宜又可靠的习惯。把要执行的命令换成 printf 就行。

$ target="회의 자료.txt"
$ printf '  인자[%s]\n' $target       # 不加引号
  인자[회의]
  인자[자료.txt]
$ printf '  인자[%s]\n' "$target"     # 加引号
  인자[회의 자료.txt]

如果在上面那种结果的状态下执行了移动或删除文件的命令，那条命令会以两个并不存在的文件为目标。目标不存在而失败还算走运；万一恰好有同名文件，遭殃的就是不相干的东西。在敲破坏性命令之前先用 printf 跑一遍同一行，成本只有几秒。

空值，以及以短横线开头的值，也能用同样的办法提前看见。

$ empty=""
$ set -- $empty;  echo "미인용 인자 개수=$#"
미인용 인자 개수=0
$ set -- "$empty"; echo "인용 인자 개수=$#"
인용 인자 개수=1

$ opt="-n"
$ echo $opt x
x

最后一行里 -n 没有被打印出来。echo 把它当作选项而不是值吃掉了。值有可能以短横线开头的地方，要用 -- 关闭选项区段，或者在前面加 ./。

$ touch "-n.txt"
touch: unknown option -- n
$ touch -- "-n.txt"      # 关闭选项区段
$ touch ./-n.txt         # 当成路径传

15. 没能验证的部分

以下几项在这套环境里无法通过实际运行确认。不用猜测去填，原样留着。

  • WSL 的文件名处理。wsl.exe 装着，但没有任何发行版（wsl -l -q 退出码为 1），什么都跑不了。WSL 挂载 Windows 驱动器时如何处理禁止字符与大小写，是否与 MSYS2 的 0xF000 置换兼容，没能验证。三套环境混用的人，最好在自己的机器上按第 3 节的办法把字节打出来确认一遍。
  • macOS 的自动分解。「macOS 文件系统把名字存成分解形一类」的说法流传很广，但这里没有 macOS 可供运行验证。本文第 11 节的结果仅限于NTFS 上两种形式共存的情形。
  • 名字末尾的点与空格，以及设备名。只引用了 Cygwin 文档的表述，没有做复现。这类名字一旦建出来，用常规 Windows 工具很难清理，没有拿来演示的理由。
  • PowerShell 7.x 的新传参方式。这里只有 5.1。7.3 以后的行为依据官方文档写成，没有用实际运行对照过。
  • 网络文件系统。Cygwin 文档提到部分网络文件系统对末尾的点与空格处理不同。本文只检查了本地 NTFS。

结论：名字在工具之间穿行时会变

归纳起来，本文的失败只有一种：名字这份数据每跨越一次工具边界就要经过一次转换，而转换规则因工具而异。Git Bash 把禁止字符挪进私用区再挪回来；PowerShell 5.1 把参数拼成字符串再重新切开；文本文件要过一遍代码页；Unicode 允许两种形式。每一次转换在自己的地盘里都是对的，错位永远只出现在接缝处。

所以排查顺序也就定了。名字对不上时，依次看三件事。

  1. 把字节打出来。od -An -tx1 或者列出码位。不要用眼睛比。
  2. 数一数跨过了哪些边界。换过几次 shell，进出过几次文件。
  3. 确认那个边界的默认值。区域设置、代码页、是否解释通配符、参数怎么传。

预防更简单：减少名字以字符串形态被传递的次数。用数组接，用 NUL 分隔，用直接管道代替清单文件。再加上创建时就别把冒号、问号、竖线放进名字，第 3 节的问题压根不会发生。能避开的字符就避开，这是最便宜的防守。
