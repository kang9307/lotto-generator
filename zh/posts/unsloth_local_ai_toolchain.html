在本地跑模型并训练它这个选择 - 它要求什么又回报什么

推理三十分钟就跑通，训练卡在数据上

2026-08-16 开发/基础设施

引言：装完只要三十分钟，之后才是问题

面前放一台插着一张显卡的机器，装一个应用，三十分钟内模型就开始回话了。这一段确实变简单了。几年前Python版本、CUDA工具包和驱动互相撕咬的位置上，如今摆着一个安装包。

问题出在之后。当有人说出「用我们自己的数据训一下，让它按我们的方式回答」这句话的瞬间，难度不是升一档，而是升了两档。而这部分增量的绝大多数来自数据，而不是显卡。

最近把本地运行、训练和智能体接入打包进一个应用的工具明显变多了。2026年8月初公开的Unsloth Desktop是其中之一，也是本文的起点。不过下面要谈的并不是某个具体应用的功能清单，而是把模型搬到自己机器上这个决定实际索取的代价，以及它作为回报交还的东西。工具在换，这笔账不换。

运行栈怎么选、GGUF量化格式怎么挑，已经在本地运行LLM指南2026里写过；重新采购设备时的对照矩阵在本地LLM硬件选择完全指南里。这里不重复，只聚焦从运行迈向训练时新出现的那些要求。

1. 搬到本地的三个理由 - 权重由处境决定

劝人上本地的文章通常并排列出三件事：数据不出门、没有按次计费、断网也能跑。三条都是事实。但三者的分量完全不同，多数情况下只有一条起决定作用，另外两条是搭头。

  • 数据禁止外传 — 只有当合同或法规明文禁止时，这一条才会重到压倒一切。此时无论其他条件多糟，本地都是唯一答案。反过来，没有禁止条款、纯粹因为心里不踏实而选本地的团队也很多。这也是一种选择，但要清楚为此付出的代价是运维负担
  • 调用单价 — 只有设备持续运转才会产生优势。如果一天只用几次，显卡的钱和电费就是净损失
  • 离线 — 只在确实没有网络的地方才具有决定性：内网隔离的厂区、船舶、现场设备。办公室网络偶尔断一下不算在这一条里

还有一个经常被漏掉的第四个维度：延迟。网络往返消失了，但自己机器的吞吐能力直接变成上限。在消费级显卡上跑大模型，明确存在比API更慢的区间，因为不了解这点而搬过去又搬回来的案例并不少见。

归纳起来是这样：有禁止外传条款，就不必再算别的账；没有的话，剩下的维度全都收敛到一个问题——利用率能跑到多高。至于内部数据是否可以送进外部模型这个判断标准本身，另见公司数据能不能喂给LLM。

2. 显存定上限 - 推理和训练的公式不一样

本地能做什么，大部分由内存容量这一个数字决定。而这里恰恰是预期最容易落空的地方。能推理的模型不等于能训练的模型，因为进入公式的项目本身就不同。

推理把权重装进内存然后只读。所以权重容量几乎就是全部，再加上与上下文长度成正比的KV缓存。训练要在这之上叠加梯度和优化器状态。每个参数会产生好几份数值，同一个模型所需内存瞬间翻上好几倍。

用途每参数约需折算8B模型额外附加
推理（4比特级）约0.5字节约4GBKV缓存（随上下文增长）
推理（8比特级）约1字节约8GBKV缓存
推理（16比特）约2字节约16GBKV缓存
适配器训练（4比特底座）底座0.5+适配器大致6~12GB激活缓冲（随批量与长度）
全量微调（混合精度Adam）16字节上下128GB量级激活缓冲、主权重

表里最后两行是本文真正的分岔口。全量微调的16字节来自权重4＋梯度4＋Adam两组动量8这套常见算术，实际上激活缓冲还要另外叠加，只会更大。8B模型对应128GB这个数字的含义很明确：想用单张消费级显卡做全量微调，这个计划在算术阶段就已经结束了。

# 概念示例 - 这是用来筛掉候选的算术，不是任何具体版本上的实测值。
def rough_bytes(params_b, mode):
    per_param = {
        "infer_4bit": 0.5,
        "infer_16bit": 2.0,
        "full_finetune_adam": 16.0,   # 权重+梯度+优化器状态
    }[mode]
    return params_b * 1e9 * per_param / (1024 ** 3)   # GiB

print(rough_bytes(8, "infer_4bit"))          # 大约4
print(rough_bytes(8, "full_finetune_adam"))  # 大约119

算术用来筛候选，不用来下结论。批大小和序列长度会通过激活缓冲把实际占用推得很远。用上面的计算先划掉明显不可能的组合，剩下的真跑一步再定，这个顺序才对。算术通过而运行时炸掉是常事；算术卡住却在运行时通过，不会发生。

3. 量化改变的三件事 - 以及训练里的不同之处

量化就是用更少的比特表示权重。改变的有三样，而窍门全在于这三条并不朝同一个方向移动。

  • 内存和速度 — 两者都会可预期地变好。内存几乎按比特宽度成比例下降；LLM解码是每出一个词就要扫一遍权重的显存带宽受限型作业，要读的字节少了就相应变快。前提是内核针对该比特宽度做过优化，速度收益才会真正兑现
  • 质量 — 只有这一条朝反方向走，而且掉多少因任务而异。闲聊和摘要扛得住，长链条推理、代码生成、精确数值引用则最先崩
比特宽度内存质量感受用在哪里作为训练底座
16比特基准基准质量对比的基线、适配器合并后发布可行但内存吃不消
8比特级一半大体难以分辨想保住质量又要降一档时可行
4比特级四分之一因任务而异日常对话、摘要、分类。本地的事实标准适配器训练的标准搭配
3比特及以下五分之一以下肉眼可见地不稳只在必须硬塞大模型时不建议

训练里有一处不同。在推理中，量化是让出一点质量换取内存的交易；在训练中，它更接近把原本不可能的事变成可能的装置。把底座权重冻结在4比特，在其上叠一层很小的可训练矩阵，就是这套做法。QLoRA论文报告用这种方式在单张48GB显卡上微调了650亿参数的模型，并保持了16比特全量微调水平的任务性能。其中用到的三样东西是4比特NormalFloat数据类型、把量化常数再量化一次的双重量化，以及用来管理内存尖峰的分页优化器。

要留意的是，这个数值出自那篇论文的模型与配置。改动批大小或序列长度就不能照搬。看别人的数字时，先确认模型规模、量化方式、序列长度、批大小是否一并写明；没写的话，取走方向、丢掉量级才是正确做法。

4. 纯CPU能做和做不了的范围

能不能不要显卡这个问题，必须按用途分开回答。瓶颈在哪，结论就会完全相反。

4.1 CPU上切实可行的

  • 小模型的对话使用 — 3B级别以下用4比特装载，系统内存扛得住。响应偏慢但没到不能用的程度
  • 嵌入生成与不赶时间的批处理 — 模型小、容易成批处理，CPU相对没那么吃亏。晚上开跑早上看结果的形式，速度就成了次要问题
  • 数据准备的全过程 — 收集、清洗、格式转换、去重。这一块占了微调项目的大部分工时，却完全用不到显卡

4.2 CPU上事实上做不到的

  • 中大型模型的对话响应与长上下文 — 内存带宽的差距会原样体现为每秒词数的差距。墙是带宽而不是容量，光是读入提示词就慢到能明显感觉出来
  • 训练 — 能做，但耗时拉长到几天甚至几周，已经不构成实务上的选项

由此可以得出一个真正有用的结论：买显卡之前先去做数据准备。那个阶段用手头现有的笔记本就能全部完成，而项目的成败通常在那个阶段就已经定了。

5. 推理很容易 - 微调八成是数据准备

当运行和训练并排摆在同一个应用里，难度看上去也差不多。实际上它们是完全不同种类的工作。

推理是有标准答案的问题。下载模型文件，挑一个适合机器的量化，跑起来。卡住时原因是有限的，大多能搜到解法。半天就结束。

微调不是。跑训练的命令只有一行，如今的工具连这一行都变成了按钮，而按下按钮之前的一切才是全部。

  • 收集与筛选 — 可用的样例散落在工单系统、维基、聊天记录和当事人的脑子里。而且并非所有过往案例都是好案例。拿糟糕的应对去训练，得到的是一个把糟糕应对做得很熟练的模型
  • 去标识化 — 必须剔除个人信息和合同秘密。如果搬到本地的理由本来就是保护数据，跳过这一步的瞬间理由就没了
  • 对齐与切分 — 输入和输出要成对咬合，而实务记录基本不是这个形状。然后把训练集和评测集切开且不重叠。一旦重叠，分数上去了，真实表现原地不动
  • 编写评测集 — 这才是真正的产出物，下面还要再说一遍
// 概念示例 - 指令与回复成对的典型形态。
// 实际字段名和结构因工具而异，请以所用工具的文档为准。
{"messages": [
  {"role": "system",    "content": "你是公司内部的基础设施运维负责人。"},
  {"role": "user",      "content": "夜间批处理在三点失败了，从哪儿开始查?"},
  {"role": "assistant", "content": "1) 作业日志的退出码 2) 前置作业是否完成 3) ..."}
]}

真正重要的是最后一项。先把评测集写出来。如果训练结束后没有手段判断是变好还是变差，那这次微调就成了一个读不出结果的实验。而且如果写五十道评测题就卡住了，说明这个任务还不到该微调的阶段，因为你还没有为自己定义什么才算好答案。微调的盈亏平衡点和总成本结构，另见500美元微调超越前沿模型这件事。

6. LoRA能解决和解决不了的问题

本地训练之所以变得现实可行，是因为不训练全部这种做法站稳了脚跟。LoRA冻结原始权重，只训练由低秩分解生成的两个更新矩阵。在Transformer里通常只挂在注意力块上，秩r决定这两个矩阵的大小。训练结束后可以把适配器权重合并回原模型成为单一模型，合并之后推理延迟不会增加。

6.1 做得好的 - 怎么说话

  • 固定输出格式 — 永远按特定JSON结构、永远按既定字段顺序作答。分类、抽取这类窄而重复的活儿不必惊动大模型就能收尾，也出自这里
  • 语气与术语适配 — 内部文档的调性、客服话术、行业里真正在用的说法。凡是一致性本身即质量的领域都属于此列
  • 拒答边界调校 — 把答到哪里、从哪里转交人工的标准变成本能

6.2 做不好的 - 知道什么

  • 事实知识注入 — 想让它背下一百条内部规章。即便看上去成功了，也无法核实覆盖到了多少，而且训进去的知识没法指出处
  • 频繁变动的信息 — 价目表、库存、组织架构。一旦每次更新都得重训，设计本身就已经错了
  • 根本性推理能力提升 — 底座模型解不了的题，适配器不会让它解得了

判断标准可以缩成一句话。要改的是怎么说，就训练；要改的是知道什么，就检索。而且两者并不互斥，用适配器固定格式、用检索挂上事实，通常是最好使的组合。

适配器有一个不太被提起的好处。它相对于底座非常小，所以可以做好几份随时换装。按团队、按任务各配一份适配器而共用同一个底座，这种拓扑是成立的。全量微调则是每个任务整份复制一遍模型，这种拓扑根本不成立。在存储和内存都紧张的本地环境里，这个差别比初看时要重要得多。

7. 打成一个盒子的工具 - 得到什么，又遮住什么

运行、训练、数据准备、智能体接入、API服务都装在一个应用里，这确实好。但抽象不是免费的，知道它遮住了什么再去用，和什么都不知道就用，结果并不一样。

7.1 得到的

  • 摆脱版本地狱 — 为了对齐驱动、运行时和依赖库而耗掉好几天的问题消失了。单凭这一点门槛就大幅降低
  • 抵达第一次成功的时间 — 能很快知道这条路走不走得通，而尽早砍掉注定失败的项目本身也是收益。训练完的模型直接部署、直接评测的链路已经接好，也在此处加分
  • 默认值的质量 — 做得好的工具，其默认超参数通常比新手手动挑的要好

7.2 被遮住的

  • 实际用了哪些数值 — 秩、学习率、调度策略、目标模块。结果不对劲时看不到这些值，就没法收敛原因
  • 到底在哪儿炸的 — 一体化工具的报错通常在上一层就被接住，把下层真正的原因盖住了。而且点一下按钮训练就开跑，你也失去了对这是两小时活还是两天活的感觉
  • 可移植性 — 结果建立在只有那个工具内部才成立的配置上，换环境时就得从头再来

所以务实的判据是这个：看产出是不是标准格式。如果训练结果落成GGUF或safetensors这类工具之外也读得懂的形式，那这个工具是便利层而不是牢笼。反过来，产出若是该应用专有的格式，现在省下的时间以后要连本带利还回去。另外，下面那一层值得亲手摸一次。不必每次都摸，但在不知道什么被自动化了的状态下，自动化出错时你根本没法察觉。

8. 开源权重不等于开源

这一节讲的是法务而非技术，但本地项目里发现得最晚、最难回头的问题恰恰出在这儿。能下载权重和能随意使用，完全是两回事。

Llama系列是典型例子。其社区许可要求如下。

  • 上一个自然月月活跃用户超过七亿的产品或服务，必须另行向Meta申请商业许可
  • 必须在网站、界面或文档中醒目展示Built with Llama
  • 对外发布衍生模型时名称必须以Llama开头，必须保留版权声明，并遵守另附的使用政策

开放源代码促进会明确表示这些条款不符合开源定义。其列举的问题是：限制了以任何目的使用的自由、对使用者构成歧视、限制了使用领域。该组织把这种标注称为开源洗白。

当然并非所有开源权重模型都如此。也有以Apache 2.0或MIT发布的系列，那边的条件宽松得多。要点在于各家完全不同，所以每次都必须核对。这一差距的技术面在开源权重LLM与闭源LLM的差距里谈过。

8.1 要核对的三层

  1. 工具的许可 — 运行与训练框架本身的条款。混用多种许可的情况很常见，用到哪些组件决定了适用哪些条文
  2. 模型权重的许可 — 商业使用、衍生模型分发、标注义务、领域限制。工具宽松并不会把模型一起带过来
  3. 训练数据的权利 — 送进微调的内部文档与客户记录的处理依据。数据不出门，并不会自动产生把这些数据拿去训练的权利

第三条尤其容易因为「反正是本地」而被整块跳过。觉得发生在自己服务器里就没问题，这是一种感觉，不是法律依据。

9. 本地不是答案的情形

读到这里，判断的维度就清楚了。下表是从条件通往结论的路径。

处境建议理由
合同或法规禁止数据外传本地其他条件再差也没有别的选项
确实没有网络的现场本地替代方案不成立
窄而重复的任务＋高利用率本地＋适配器单价优势真正显现的唯一组合
当下最强性能直接决定成果API公开权重出得晚，差距在本地补不上
用量不规则且很少API设备折旧与电费直接变成损失
没有指定运维负责人API半年后剩下一台没人敢碰的服务器
需求还在变动的早期探索期先用API目标未定就投本地，容易变成沉没成本
说不出一句话解释为何要本地API没有理由，剩下的只有运维负担

还有一个维度进不了表格：运维负担会随时间越来越重。一开始只要跑好一个模型，半年后驱动升级、模型更换、适配器重训、磁盘清理、访问控制全都变成某个人的活。落地时做的成本对比里，这一项几乎总是缺席。

10. 当前工具的状态，以及没能核实的部分

把截至2026年8月16日的状态记下来。这个领域的标注变动频繁，需要连同时点一起读。

  • 作为本文起点的Unsloth Desktop，在官方文档中标注为测试版（Beta）。仓库中显示的版本字符串0.1.800-beta同样处于测试阶段
  • 支持平台标注为macOS、Windows、Linux、WSL，另有Docker路径。硬件方面提到NVIDIA、AMD、Intel GPU以及Apple Silicon，CPU则标注用于对话与数据处理。训练结果可导出为GGUF与16比特safetensors，满足上一节的可移植性判据
  • 许可为双轨结构：核心包是Apache 2.0，工作室界面与部分可选组件是AGPL-3.0。若计划把AGPL组件作为服务对外提供，需要自行核对条文

没能核实的部分集中列在下面。正文中没有任何一句话以这些项目为依据。

  • 厂商给出的性能数值 — 训练快2倍、显存省70%、MoE最高12倍、20B模型50万上下文训练等数值已公开，但对比基线、模型、序列长度、批大小均未一并给出。因此正文的表格与算术完全没有采用
  • 测试版阶段的稳定性与平台差异 — 长期运行的可靠性未做验证，文档中也没有标注各平台的限制。Apple Silicon与AMD环境下训练功能是否与NVIDIA一致，未经核实
  • 表中适配器训练的内存区间 — 6~12GB是常被引用的估算而非实测，批量和长度会把它推出这个区间

结论：不要把顺序颠倒过来

搬向本地的项目失败起来大多是同一种方式：先买设备，后看数据。于是显卡闲着，人扑在数据清洗上，半年过去剩下一台没人碰的服务器。

顺序应该反过来。

  1. 用一句话写下选择本地的理由。是禁止外传条款、是利用率，还是离线。三者都不是，停在这里才是划算的
  2. 先写五十道评测题。写不出来，说明什么算好答案还没被定义，那种状态下训练也读不出结果
  3. 训练之前先用提示词和检索试。够用就不必微调，相当一部分需求到此为止
  4. 用算术筛候选。全量微调通常在算术阶段就被划掉，留下的是4比特底座之上的适配器训练
  5. 核对三层许可。工具、权重、训练数据。这是写代码之前就该收尾的事

工具变好了，第1到第4步的门槛确实大幅下降。但下降的是执行的门槛，不是判断的门槛。要训什么、怎么知道训好了，依旧得由人来定，而这部分无论装哪个应用都不会替你做。
