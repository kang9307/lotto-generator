DNS 缓存告诉我们的事 - 把什么放在哪里、放多久

作为契约的 TTL、分成四层的缓存、决定丢弃什么的问题，以及缓存悄悄绑在发布与回滚上的那段时间

2026年8月29日 开发/基础设施

引言：从 953 字节到 420 字节，以及随之而来的问题

发布刚完成，有人看到的是新页面，有人看到的还是旧页面。代码一样，服务器也一样。唯一不同的是这个人的机器在把名字换成地址时跑了多远。处理缓存这件事，一半的门道都藏在这一句话里。

眼下正好有个由头。Cloudflare 在技术博客上公开了它如何压缩自家 DNS 平台上每条缓存条目占用的内存。按该公司的说法，这个平台支撑着包括 1.1.1.1 在内的多项 DNS 服务，在任一时刻都持有超过 2,500 亿条缓存条目。经过五项优化，在其自家基准测试中，单条条目内存从 953 字节降到 420 字节，减少 56%。

被当作标题传播的100TB，值得把它究竟是什么对什么讲清楚。原文的表述是：在其服务器群（fleet）范围内，这些改动总共释放了约 100 TB 内存，相当于其第 13 代服务器 130 台的 RAM 容量。这不是单台机器省下的量，不是某个数据中心的数字，也不是某段时间累计出来的量，而是横跨众多机器的合计值。这个值究竟是峰值还是平均值、服务器群总共有多少台，原文并未说明。单条 953→420 字节同样来自基准测试而非生产环境测量；生产环境的数字是另外给出的 — 实例常驻内存 p99 从 9.3 GB 降到 5.3 GB，而原文自己就注明常驻内存里除了缓存还混着其他进程数据。以上全部是该运营方自行公布的数值，并非经第三方核验的数据。

产品的部分到此为止。这篇文章不打算推荐你使用哪一家 DNS 服务。真正有意思的是他们撞上的那个问题的形状。缓存归根结底就是把什么放在哪里、放多久，而 DNS 正是这三个决定显现得最清楚的地方。下面逐一走一遍。如果想弄清名字究竟握在谁手里，可以把域名服务器委派与信任的层级放在旁边；想看同样的原理在图片上如何体现，可参考决定图片分发的那些因素。

1. DNS 缓存实际保存的是什么

如果你把 DNS 缓存理解成一个名字对一个地址的表格，那就偏了一半。缓存的单位不是地址，而是对一次查询的完整应答。

作为键的是三样东西的组合：名字、记录类型、类别。同一个名字下，问 IPv4 地址的 A 与问 IPv6 的 AAAA 是两个条目。一个在缓存里、另一个不在，是完全正常的状态。

  • A 与 AAAA — 名字对应的地址。最常见，也是变动最频繁的一条轴。
  • CNAME — 指向另一个名字的别名。顺着走下去会多出一次查询。
  • NS — 这个区由谁负责。委派路径本身就会被缓存。
  • MX — 邮件送往何处。变动频率很低，但一旦出错投递就停。
  • TXT — 所有权证明、邮件策略之类的字符串。校验流程常常挂在这上面。
  • SOA — 区的基准信息。后面要讲的否定答复的寿命就出自这里。
  • CAA — 哪些证书机构可以为这个名字签发证书。

值这一侧也不是一行地址。应答的三个区段 — 回答、权威、附加 — 整块存入，再附上管理信息。Cloudflare 在介绍自家结构时举的例子也是同一个形状：值里除了应答本体，还装着创建时刻、命中次数与剩余寿命（TTL）。命中次数为什么有用，第 5 节会再出现。

还有一项最容易被忘掉。不存在这件事同样会被保存。名字不存在的答复，与名字存在但没有该类型记录的答复，是两种不同的情形，两者都在缓存范围内。这叫否定缓存，至于它为什么是稳定性问题而非性能问题，第 8 节单独来看。

2. 作为契约的 TTL — 权威服务器定，解析器守

在缓存里放多久，不由持有缓存的一方决定。由发布记录的一方，也就是域名所有者决定。随应答返回的 TTL 就是这个值，解析器承诺不超过这段时间复用答案。所有权与保存期限分属两方，这一点几乎决定了 DNS 缓存的全部性格。

不过这份契约只在一个方向上严格。RFC 2181 明确写道，TTL 是最长存活时间而非强制存活时间，实现可以对收到的值设上限。解析器把一天的 TTL 截成一小时，是在规范之内的；反过来延长则属于违约。同一份文档定下的其他规则，在实务中也常撞见。

  • 同一组（RRSet）内的所有记录必须携带相同的 TTL。取值不一致会造成只有一部分留在缓存里的半截状态。
  • TTL 是无符号值，最大为 2,147,483,647。32 位字段中只使用低 31 位。
  • 最高位被置起的 TTL 必须按 0 处理。这是防止一个错误的巨大值永远留存的护栏。
  • TTL 为 0 意味着不要缓存。这是最短的寿命，每次都要走到源头。

所以定 TTL 不是挑一个数字，而是挑一笔交易。得到什么、交出什么，分野如下。

3. 缓存不止一层

问同一个名字，答案来自哪里每次都可能不同。而命中在哪一层，体感、清除方式与影响范围全都不一样。

层级谁掌控影响范围如何清除
应用或浏览器自带缓存那个程序一个进程重启程序，或用它自己的设置
操作系统存根解析器设备管理者整台设备操作系统提供的功能、重启
递归解析器（内部或公共）解析器运营方使用该解析器的所有人只有运营方能做，用户只能等过期
权威服务器域名所有者源头，不是缓存没有可清的对象，靠 TTL 调控

第三行解释了大部分麻烦。递归解析器的缓存是共享资源。无论你在自己机器上清掉什么，那一层纹丝不动。发布之后人与人看到的页面不同、不同地区生效时间不一，多半都能追到这里，因为每个解析器过期的时刻各不相同。

分层这一事实还强制了一个规划决定。决定调短 TTL 之后，要以传播完成的时刻为基准做计划，而不是以下决定的时刻。把 TTL 降到 5 分钟这个改动本身，也是按旧 TTL 到期的先后顺序陆续抵达各个解析器的。旧值若是一天，新值传遍所有人最长要一天。迁移时提前一天把 TTL 调短的惯例，正是从这个性质推出来的，并非迷信。

还要补一点。选用哪个递归解析器，不只是响应速度的问题。还有另一条轴：查询被记录在哪里、依照什么策略处理。解析器所处的位置能看到某个用户在什么时候查了什么名字，而延迟数字替代不了这条轴。因为快所以用它是只看了两条轴之一得出的结论。各运营方公布的策略与保存期限并不相同，选择的一方应当直接阅读各自的官方文档自行判断。

4. 规模一大，内存先成为墙

在个人设备上，DNS 缓存的大小不构成话题，几千条条目占几兆字节。可对大规模运营递归解析器的一方来说，这个条目数会来到几十亿乃至几千亿的量级。如前所述，Cloudflare 称其平台在任一时刻持有超过 2,500 亿条条目。

在这个规模上，内存按三项之积增长。

  • 条目数 — 不同名字与记录类型的组合个数。一个名字会产生多条条目。
  • 单条大小 — 应答本体、键字符串、管理信息，以及数据结构本身的附带开销。
  • 复制 — 同一份缓存分别存在于多个实例与多个站点。一台上省下的字节要乘以台数。

第三项就是 100TB 这个数字的真身。每条省下五百字节左右，乘遍整个服务器群得出的合计值，并不意味着某一台机器少用了 100TB。

这里浮出缓存设计一个让人不太舒服的性质。热门的名字是少数，绝大多数名字用过一次就再也不来。少数大型服务的名字每秒被查无数次，而它们身后拖着一条长长的尾巴：自动生成的主机名、追踪用的子域、一次性的校验字符串，还有拼写错误。缓存容量里相当一部分被不会再被用到的东西占着。

这是浪费，但也是从缓存的本质直接推出的结果。缓存必须在不知道接下来会来什么的状态下作决定。如果事先就能认出那些不会再来的条目，一开始就不会收下它们。于是剩下的问题收窄成一个 — 位置不够时丢弃什么。

5. 丢弃什么 — 淘汰策略与它的陷阱

条目离开 DNS 缓存有两条路。一条是寿命到期，一条是位置不够。前者是契约，后者是策略。而后者没有标准答案。

Cloudflare 描述自家行为的那句话正好呈现了这个结构：随着查询涌入，缓存一直填到条目数上限，此时淘汰更旧或更不热门的条目腾出位置。注意这句描述里同时出现了两个判据。

  • 最近是否被用过（LRU） — 从最久没被碰过的开始丢。实现简单，能很好地跟上近期走势。
  • 被用得有多频繁（LFU） — 从命中次数最低的开始丢。保护持续的热度。

两者各以自己的方式失败。LRU 的软肋是扫过一遍就走的负载。当只会被查一次的名字大量涌入时，它们会轮流成为最近使用过的条目，把长期守住位置的热门条目挤出去。刚刚进来、以后再也用不到的东西，赶走了下一刻确定会用到的东西。自动化程序或扫描器批量查询不存在的名字时，这件事真的会发生。

LFU 的软肋在另一端。曾经热门的条目靠计数长期赖着不走。新起来的名字计数低，还没站稳就被挤掉，缓存于是被冻结在过去。所以实际实现大多不用纯粹的某一种，而是走向两者混合、给新条目一段试用期，或让计数随时间衰减。这些都不是白白更优的策略，而是按负载性质来挑的问题。把淘汰逻辑保持在最低限度、选择简单，也依然是有效的设计路线，这一脉思路在一台坚持简单的缓存服务器里另行讨论过。

DNS 还要在此之上叠一个条件。挑选丢弃对象时，剩余寿命也得一起看。马上就要过期的条目守不住多久位置；反过来，剩余寿命还长的条目只要仍在被使用，就值得留下。最近性、频度与剩余寿命这三个信号，进入同一个判断。

6. 缩小表示的那一侧 — 同一个值不放两遍

到这里谈的都是丢什么。还有反方向的做法：什么都不丢，把同样的东西用更少的字节放下。如果能在丝毫不牺牲正确性的前提下只压缩体积，这条路永远排在前面。

Cloudflare 公开的五项全属这一脉。细节实现绑在他们的语言与数据结构上，但思路本身可以搬到任何做缓存的地方。把该公司列出的项目按理路归拢，大致可以这样读。

  • 不携带富余容量 — 日后可能变大的容器，总会预留比实际内容更多的位置。条目进入缓存后内容不再变化，于是把这些可增长容器换成定长表示。原文明确写道，应答一旦存入缓存此后绝不再修改，这个不变性正是其余优化的前提。
  • 不把列表拆开 — 把应答的三个区段各做一个列表，每个列表都要付一份管理开销。合并成一个、只标出边界，这份开销就只付一次。
  • 省掉重复的名字 — 一次应答里的记录常常拥有相同的所有者名。与其把同一串字符放很多遍，不如只放一次、其余省略。
  • 不按最大的情形对齐全体 — 能容纳多种形态的类型，通常按最大的那种形态确定大小。把罕见的大形态挪到外面，常见的情形就会变小。
  • 不去重建已经有的表示 — 记录是以传输格式抵达的。与其把它拆成结构体存放，不如保留原始字节序列，需要时再解析。

贯穿五项的原则只有一条：同一份信息不要持有两遍，用不上的余地不要预先买下。这里也有代价。像最后一项那样压紧的表示，会在读取时付出解析开销。这是以空间换时间的经典交易，只不过在这个案例里，该公司称按其自家基准测试，查询延迟反而从 828 纳秒降到 670 纳秒，减少 19%。原因不难猜：数据变小后能更多地装进处理器缓存，这份收益可能盖过解析开销。但这是从他们的负载与他们的基准测试里得出的结果，换一种数据结构未必是同一个方向。

7. 缓存带来的副作用 — 陈旧的答案与被捆住的手脚

缓存不是白得的加速装置。它是用一部分正确性换来的时间，而这笔账偏偏在你最急的时候被追讨。

  • 陈旧答案流通的那段时间 — 从改动值的那一刻起，到所有缓存都看到新值为止，最长有一个 TTL 的空窗。在这段区间里，两个答案都有效。
  • 回滚比发布更慢 — 撤回一个错误的值同样要挨这份延迟。你可能五秒就发现了问题，召回却仍要一个 TTL。
  • 故障传播与恢复感知的不对称 — 长 TTL 会替权威服务器的故障遮掩一阵。听上去是好事，但同一个理由也意味着你已恢复这件事同样迟到。
  • 部分生效 — 各解析器过期的时刻不同，同一时刻不同用户会去往不同的目的地。会话横跨两代之后，排查会变得棘手。
  • 校验流程被拖住 — 所有权证明、证书签发这类要确认某条记录存在的流程，会撞上被缓存的旧状态。尤其当不存在被缓存下来时，你刚添加的记录会有一阵子看不见。

有一种看法认为，完全不用过期答案也不是答案。RFC 8767 整理了在递归解析器无法刷新信息这一例外情形下使用过期数据的做法，其判断是：源头挂掉时，给出一个旧答案好过给不出任何答案。文档要求先尝试刷新、确实失败后才使用，并给出推荐值：过期后的保留窗口为1 到 3 天，向客户端返回过期答案时附加的 TTL 为30 秒。

同一份文档列出的风险也要一并读。签名可能在有效期之外被返回，针对域名验证型证书的攻击窗口可能被拉宽，长期持有过期数据还会加重内存压力。一句话，这个功能是卖出新鲜度以买入可用性的选择。它不是开或关的问题，而是哪一种失败对你更贵的问题。

8. 不存在的答案与拼写错误 — 否定缓存做的事

对不存在名字的查询比想象中多：拼写错误、废弃配置里残留的名字、写坏的自动化，还有专门抛出随机名字的流量。要是每次都把这些查询送到权威服务器，等于为了取回最没用的答案而走了最贵的路。

RFC 2308 正面处理了这个问题。文档把否定答复分成两类。NXDOMAIN 是所查询的名字本身不存在；NODATA 是应答没有报错，但没有所请求类型的记录。两者是不同的情形，理应分开对待。

寿命从何而来？否定答复会带上该区的 SOA 记录，文档规定该条目的 TTL 取SOA 的 MINIMUM 字段与 SOA 自身 TTL 中较小的一个。推荐范围也写了下来 — 一到三小时的取值被证明运作良好，超过一天的取值出现过引发问题的情况。至于效果，文档写道如果所有解析器都实现否定缓存，互联网上相当一部分 DNS 流量将被消除。

对运营一方而言，这一节有两重意思。

  • 你刚建好的记录看不见，原因就在这里。只要在建立之前有人查过这个名字，那份否定答复就还留在缓存里。你等待生效的时间不取决于新记录的 TTL，而取决于旧否定应答的剩余寿命。
  • SOA 的 MINIMUM 是一个容易被遗忘的旋钮。它在建区时定一次、之后再也不看，实际上却决定了不存在这件事要流通多久。

否定缓存污染缓存的机理也值得点明。不存在的名字彼此互不重合。近乎随机的名字大量涌入时，条目数就随之膨胀，而按第 5 节所述，它们会成为最近使用过的条目并拿到位置。偏偏这些名字不会被再查一次。否定缓存保护了源头，但这份保护是拿缓存席位这另一项资源付的账。

9. 运营方真正要定的事 — 挑选 TTL 的判据

这一节不会写设成多少秒。那个数字因名字而异，照搬别人的取值多半不合身。这里放的是要先回答哪些问题，数字才定得下来。

基本的轴有两条：这个名字变得有多频繁，以及一个错误的值活着的时间你能承受多久。这两条定了，其余自然跟上。

权威服务器的余量查询增加也扛得住已经吃紧，或按查询次数计费
近期的变更计划迁移窗口已经排定短期内不打算动
绑在这条记录上的流程证书签发、所有权证明依赖它更接近给人看的便利用途

这张表的用法很简单。不要给整个域名挂同一个 TTL，按记录的性质分开。常搬家的服务的 A 记录，与好几年固定不动的 MX 记录，没有理由取同一个值。而如果迁移已经排上日程，就要把第 3 节的性质写进时间表：调短这件事本身要按旧 TTL 的时长才传得开。

最后再补一条。短 TTL 不是可用性设计的替代品。故障时用 DNS 切换的计划，建立在所有缓存都会配合的假设之上，而规范并不为这个假设背书。解析器可以把 TTL 截得更短，却没有必须严格遵守的义务；若启用了使用过期答案的行为，答案会在你所设想的那类例外情形里活得更久。DNS 是宣告切换的手段，不是立刻强制切换的手段。

10. 度量 — 只看命中率会漏掉什么

缓存看板上挂得最大的就是命中率，可这一个数字说的话少得惊人。只要少数热门项撑起了整体查询量，其余全部落空，比率照样很高。90% 是出色还是糟糕，光凭它自己判断不了。

该看的是落空那一侧的性质。未命中至少有三种，三者的处方各不相同。

  • 第一次到来的请求 — 从未被请求过，本来就不在缓存里。这是躲不掉的未命中；要动它，谈的应该是预加载而不是缓存。
  • 寿命耗尽的条目 — 本来在，过期了。这一类在增加，就该去看 TTL 的设置。
  • 被挤出去的条目 — 过期之前因位置不够被推走，之后又被请求。这一类在增长，问题就在容量或淘汰策略。它也是缓存确实被浪费掉的唯一直接信号。

还有几项值得一并观察。

  • 未命中时的延迟分布 — 看尾部而不是均值。未命中很少但每一次都极贵，体感照样很差。
  • 条目数与内存的关系 — 单条大小是否在悄悄膨胀，只有把这两者放在一起看才看得出来。
  • 否定应答的占比 — 不存在这类答复的份额上升，就该怀疑第 8 节说的污染。
  • 淘汰发生率 — 因过期离场与因被挤出离场，务必分开计数。
  • 从未被复用的条目比例 — 进来之后一次都没再被用到就消失的份额。它最诚实地显示缓存究竟有没有在干活。

再补一条度量原则：比较只有在条件对齐之后才成立。把缓存预热过的状态与冷启动的状态混在一起测，哪一边的数字都不可信。改了策略就一次只改一样，并把改了什么与量到什么一起留档。

未能确认的事

  • 100TB 究竟是峰值还是平均值，以及服务器群总共有多少台，原文没有说明。可确认的只有它是服务器群合计值，以及它折合为第 13 代服务器 130 台的 RAM。
  • 单条 953→420 字节、插入吞吐每秒 62.5 万→89.3 万、查询延迟 828→670 纳秒，全部是该运营方的自家基准测试数值。硬件与负载构成在撰写本文时未能确认。
  • 作为生产数值给出的实例常驻内存 p99 由 9.3 降到 5.3 GB，原文自己注明其中包含缓存之外的进程数据，不能当作纯粹的缓存节省量来读。
  • 所有数值都是该运营方自行发布的，未能找到第三方核验资料。
  • 那 2,500 亿条条目中实际被复用的比例并未公开。第 4 节关于长尾的论述基于缓存的一般性质，而非该平台的实测值。
  • 原文没有讨论否定缓存与 NXDOMAIN。第 8 节的内容完全来自 RFC 2308。

小结

缓存设计可以压缩成三个决定：放在哪里、放什么、放多久。DNS 之所以是好教材，是因为这三者分别握在不同主体手里。放在哪里由各层不同的人决定，丢弃什么由解析器运营方决定，放多久由域名所有者决定。三者一旦错位，缝隙里就长出人与人看到不同页面的现象。

可以带走的有三点。第一，TTL 是契约而不是性能开关。调短所得与所失分列在那张表的两侧，只看一侧作决定，必定从另一侧被追账。第二，内存成为瓶颈时，答案有两个方向 — 决定丢弃什么，或者把同样的东西放得更小。不损害正确性的那一条永远排在前面。第三，命中率是问题的开始而不是结论。漏掉了什么、为什么漏掉，才决定处方。

下次再听到发布生效因人而异，先别急着找原因，用一句话回答：此刻还握着旧答案的是哪一层。光是把那一层指认出来，能做什么与做不了什么就分清楚了。
