1. 샌드박싱의 본질: 침해 방지가 아닌 침해 후 횡적 이동 억제

리눅스 시스템 관리에서 서비스 유닛 하드닝을 검토할 때 가장 먼저 명확히 구분해야 하는 경계는 샌드박싱이 수행할 수 있는 역할의 한계입니다. 많은 관리자가 서비스 유닛 설정에 강력한 보안 지시어를 추가하면 웹 애플리케이션이나 백엔드 데몬 자체의 결함까지 차단할 수 있을 것으로 기대합니다. 그러나 systemd가 제공하는 실행 환경 격리 기능은 애플리케이션 내부의 입력 검증 누락, SQL 인젝션, 취약한 역직렬화 라이브러리 실행 등 1차 침해 시도 자체를 막지 못합니다.

샌드박싱의 실제 기술적 목표는 취약점이 트리거되어 프로세스 제어권이 공격자에게 넘어갔을 때 발생하는 2차 피해를 억제하는 데 있습니다. 임의 코드 실행 권한을 획득한 공격자가 호스트 파일시스템 전체를 탐색하거나, 다른 사용자의 자격 증명을 탈취하거나, 커널 파라미터를 조작하여 영속적인 백도어를 심지 못하도록 행동 반경을 엄격한 격벽 안에 가두는 것입니다. 이러한 접근은 다층 방어 체계에서 폭발 반경(Blast Radius)을 최소화하는 기술적 장치로 작동합니다.

공식 매뉴얼인 systemd.exec 및 관련 문서가 정의하는 격리 체계는 크게 파일시스템 시야 제한, 프로세스 특권 박탈, 리눅스 커널 공격 표면 축소, 시스템 콜 및 네트워크 필터링이라는 네 가지 축을 바탕으로 설계되어 있습니다. 이 격벽들이 조화를 이루어 작동할 때 비로소 프로세스가 탈취되더라도 호스트의 완전한 장악으로 이어지지 않습니다.

  • 샌드박싱은 취약점 발생 자체를 차단하는 방화벽이 아니라 침해 이후 시스템 장악과 횡적 이동을 차단하는 억제 격벽입니다.
  • 공격자가 프로세스 권한을 획득하더라도 영속성 확보(루트킷 설치, 서비스 등록)와 로컬 권한 상승을 물리적으로 차단합니다.
  • 모든 보안 지시어는 애플리케이션의 정상 동작에 필요한 리소스 접근과 직접적으로 충돌하므로 비용과 대가를 계산해야 합니다.

2. 파일시스템 격리: 무엇을 숨기고 무엇을 읽기 전용으로 만드는가

공격자가 쉘을 획득한 직후 가장 먼저 시도하는 행위는 호스트 내부의 민감한 파일 탐색과 악성 바이너리 다운로드입니다. systemd는 마운트 네임스페이스 기술을 활용하여 각 서비스 프로세스가 바라보는 디렉터리 트리를 시스템 전체와 분리하거나 읽기 전용으로 재마운트하는 다단계 지시어를 제공합니다.

ProtectSystem과 ProtectHome의 계층적 보호

ProtectSystem 지시어는 시스템 바이너리와 라이브러리가 위치한 핵심 운영체제 영역을 보호합니다. 매뉴얼에 명시된 바와 같이 yes로 설정하면 /usr 디렉터리와 부트로더 디렉터리(/boot, /efi)가 프로세스 네임스페이스 내에서 읽기 전용으로 마운트됩니다. full로 상향하면 시스템 설정 파일이 밀집한 /etc 디렉터리까지 읽기 전용으로 전환되어 설정 변조를 방어합니다. 가장 강력한 strict 모드는 API 파일시스템(/dev, /proc, /sys)을 제외한 전체 파일시스템 트리를 읽기 전용으로 잠급니다. strict 모드에서는 프로세스가 파일 쓰기를 수행해야 하는 로그, 상태, 캐시 경로를 ReadWritePaths 지시어나 StateDirectory 지시어를 통해 명시적으로 개방하지 않으면 서비스가 쓰기 오류를 일으킵니다.

ProtectHome 지시어는 사용자의 개인 파일과 인증 토큰이 보관된 홈 디렉터리를 격리합니다. yes로 설정하면 /home, /root, /run/user 디렉터리가 빈 디렉터리로 대체되며 권한 0000의 접근 불가 마운트로 봉쇄됩니다. read-only 값은 해당 경로들을 읽기 전용으로 열어두어 설정 읽기는 허용하되 수정을 금지하며, tmpfs 값은 메모리 기반의 빈 파일시스템을 해당 경로에 덮어씌워 프로세스가 가상의 디렉터리에만 쓰기를 수행하도록 제한합니다.

PrivateTmp와 UMask를 통한 파일 접근 격리

PrivateTmp 지시어는 리눅스 서버에서 가장 흔히 발생하는 심볼릭 링크 공격과 임시 파일 스누핑을 차단합니다. 이 옵션이 활성화되면 프로세스 전용 마운트 네임스페이스 안에서 격리된 /tmp 및 /var/tmp 디렉터리가 생성됩니다. 호스트 파일시스템 관점에서는 /tmp/systemd-private-UUID-서비스명-hash/ 와 같은 전용 하위 디렉터리로 매핑되므로, 호스트의 다른 프로세스나 공격자가 공유 /tmp 디렉터리를 매개로 악성 파일을 주입하거나 덮어쓰는 행위가 차단됩니다.

또한 ReadOnlyPaths, ReadWritePaths, InaccessiblePaths 지시어를 사용하면 절대 경로 단위로 파일시스템 접근을 미세 조정할 수 있습니다. 경로 앞에 빼기 기호(-)를 붙이면 해당 경로가 시스템에 존재하지 않더라도 서비스 시작 오류를 발생시키지 않고 건너뛰는 유연성을 제공합니다. 한편 UMask 지시어는 프로세스가 새로 생성하는 파일과 디렉터리의 기본 허가권을 제어합니다. systemd 기본값인 0022는 그룹과 타인에게 읽기 권한을 허용하지만, 0027이나 0077로 강화하면 생성된 로그나 데이터 파일이 타 계정이나 웹 서버에 노출되는 정보 유출 사고를 방지합니다.

  • ProtectSystem은 yes(/usr 읽기 전용), full(/etc 포함), strict(전체 파일시스템 읽기 전용) 단계로 나뉩니다.
  • ProtectHome은 홈 디렉터리 접근을 봉쇄(yes), 읽기 전용(read-only), 가상 메모리(tmpfs) 형태로 분리합니다.
  • PrivateTmp는 공유 임시 디렉터리 기반의 심볼릭 링크 하이재킹과 파일 조작을 원천적으로 분리 차단합니다.
  • UMask를 0077로 설정하면 서비스가 생성하는 파일에 대해 소유자 외 타인의 읽기 및 쓰기 접근이 완전히 봉쇄됩니다.

3. 커널 및 시스템 상태 보호: 런타임 변조 차단

공격자가 프로세스 권한을 장악했을 때 커널 튜너블을 변경하거나 드라이버 모듈을 적재하면 호스트 전체가 회복 불가능한 침해 상태에 빠집니다. systemd는 프로세스가 커널 내부 상태와 제어 그룹(cgroups) 계층을 건드리지 못하도록 방어하는 하드닝 옵션을 갖추고 있습니다.

커널 튜너블과 모듈 동적 로딩 방어

ProtectKernelTunables 지시어가 활성화되면 /proc/sys, /sys, /proc/sysrq-trigger, /proc/latency_stats, /proc/acpi 등 런타임 커널 매개변수를 노출하는 가상 경로들이 프로세스 시야에서 읽기 전용으로 마운트됩니다. 이를 통해 공격자가 sysctl 파라미터를 조작하여 네트워크 패킷 포워딩을 활성화하거나 메모리 보호 메커니즘을 약화시키는 행위를 막아냅니다.

ProtectKernelModules 지시어는 명시적인 커널 모듈 적재 및 언로드를 차단합니다. 프로세스에서 CAP_SYS_MODULE 케이퍼빌리티를 제거하고 /usr/lib/modules 디렉터리에 대한 접근을 제한하여, 침해된 프로세스가 루트킷 성격의 커널 모듈을 동적으로 올려 탐지를 우회하는 공격 통로를 봉쇄합니다. 네트워크 가속 도구나 가상화 보조 모듈을 런타임에 호출해야 하는 특수 데몬이 아니라면 대부분의 일반 서버 애플리케이션에서 활성화할 수 있습니다.

제어 그룹(cgroup)과 procfs 시야 제한

ProtectControlGroups 지시어는 /sys/fs/cgroup 아래에 마운트된 리눅스 제어 그룹 계층 트리를 읽기 전용으로 격리합니다. 서비스 내부에서 임의로 자신에게 할당된 CPU, 메모리, 프로세스 수(PIDs) 할당 한도를 수정하거나 다른 슬라이스의 자원 정책을 변조하여 호스트 고갈 공격을 감행하는 시도를 방어합니다.

ProtectProc 지시어는 procfs 파일시스템의 가시성을 제한하여 다른 프로세스의 상태 조사를 차단합니다. default 모드에서는 다른 사용자의 프로세스 정보를 읽을 수 있지만, noaccess는 메타데이터 접근을 제한하고 invisible 모드는 타 사용자의 프로세스를 /proc 트리에서 완전히 숨깁니다. ptraceable 모드는 디버깅 권한이 있는 프로세스만 보이도록 통제합니다. 이를 통해 공격자가 웹 서버 쉘에서 ps 명령어를 실행하여 데이터베이스나 백업 데몬의 실행 인자, 민감한 환경 변수를 정찰하는 행위를 무력화합니다.

  • ProtectKernelTunables는 /proc/sys와 /sys를 읽기 전용으로 묶어 sysctl 변조를 봉쇄합니다.
  • ProtectKernelModules는 루트킷 및 외부 드라이버의 동적 커널 삽입을 물리적으로 거부합니다.
  • ProtectControlGroups는 cgroup v2 계층 수정을 막아 자원 제한 회피 공격을 억제합니다.
  • ProtectProc=invisible은 /proc에서 타 프로세스를 완전히 감추어 시스템 내부 정찰 행위를 차단합니다.

4. 실행 권한과 프로세스 신원 축소: 루트 탈피와 권한 상승 봉쇄

과거의 많은 리눅스 데몬은 저포트(80, 443) 바인딩이나 특정 시스템 파일 읽기를 위해 루트(root) 계정으로 구동되었습니다. 현대의 systemd 환경에서는 최소 권한 원칙(Principle of Least Privilege)을 손쉽게 구현할 수 있는 신원 관리와 특권 상승 억제 지시어를 제공합니다.

NoNewPrivileges와 SUID/SGID 비활성화

NoNewPrivileges=yes 지시어는 프로세스 보안에서 가장 중요한 출발점입니다. 커널의 PR_SET_NO_NEW_PRIVILEGES 플래그를 설정하여, 서비스 프로세스와 이후 생성되는 모든 자식 프로세스가 execve 시스템 콜을 수행할 때 새로운 권한을 얻지 못하도록 영구히 강제합니다. 바이너리에 SUID(Set-UID)나 SGID 비트가 켜져 있거나 파일 케이퍼빌리티가 부여되어 있더라도 해당 권한이 절대 상속되지 않습니다. 공격자가 취약한 로컬 바이너리를 호출하여 루트 권한 쉘을 획득하는 고전적인 권한 상승 경로가 완전히 차단됩니다.

RestrictSUIDSGID=yes 지시어는 파일시스템 내부에서 새로운 권한 상승 거점을 만드는 행위를 차단합니다. 프로세스가 chmod, fchmodat 등의 시스템 콜을 호출하여 파일이나 디렉터리에 SUID 또는 SGID 비트를 설정하려는 시도를 커널 차원에서 차단합니다. 쓰기 가능한 디렉터리를 찾아낸 공격자가 백도어 실행 파일에 SUID 루트 권한을 부여해 두고 추후 재진입 경로로 활용하는 것을 방지합니다.

리눅스 케이퍼빌리티(Capabilities) 축소와 DynamicUser

루트 권한을 잘게 쪼갠 리눅스 케이퍼빌리티는 CapabilityBoundingSet 지시어를 통해 제어됩니다. 이 지시어에 허용할 케이퍼빌리티 목록을 공백으로 구분하여 명시하면, 서비스 프로세스가 실행 중에 획득할 수 있는 상한선(Bounding Set)이 해당 집합으로 제한됩니다. 값을 비워두면(CapabilityBoundingSet=) 모든 케이퍼빌리티가 박탈되어 프로세스는 순수한 비특권 상태가 됩니다. 반대로 비특권 사용자로 데몬을 구동하면서도 1024 미만의 특권 포트 바인딩이 필요하다면 AmbientCapabilities=CAP_NET_BIND_SERVICE 지시어를 선언하여 비특권 프로세스에 안전하게 단일 권한만 상속할 수 있습니다.

DynamicUser=yes 지시어는 정적 시스템 계정 생성의 번거로움과 관리 위험을 해소합니다. 서비스가 시작될 때 61184부터 65519 범위의 동적 UID/GID를 할당하고, 서비스가 중지되면 즉시 계정을 해제합니다. DynamicUser를 켜면 systemd 내부적으로 ProtectSystem=strict, ProtectHome=yes, NoNewPrivileges=yes, PrivateTmp=yes, RestrictNamespaces=yes가 자동으로 함의되어 최고 수준의 격리가 즉시 적용됩니다.

  • NoNewPrivileges는 execve 실행 시 SUID 및 파일 케이퍼빌리티를 통한 특권 상승을 영구히 차단합니다.
  • RestrictSUIDSGID는 파일시스템에 SUID/SGID 비트를 가진 악성 실행 파일을 생성하는 행위를 거부합니다.
  • CapabilityBoundingSet은 프로세스가 보유할 수 있는 리눅스 케이퍼빌리티의 최대 상한선을 축소합니다.
  • DynamicUser는 일회성 임시 UID를 부여하고 주요 샌드박싱 지시어를 자동으로 일괄 활성화합니다.

5. 시스템 콜과 아키텍처 필터링: Seccomp 기반 공격 표면 축소

커널 공간과 사용자 공간의 경계선인 시스템 콜(System Call) 인터페이스는 공격자가 커널 취약점을 공격하거나 호스트를 조작할 때 반드시 거쳐야 하는 통로입니다. systemd는 리눅스 커널의 Seccomp(Secure Computing Mode) BPF 필터를 직관적인 유닛 지시어로 추상화하여 제공합니다.

SystemCallFilter와 SystemCallArchitectures

SystemCallFilter 지시어는 프로세스가 호출할 수 있는 시스템 콜을 화이트리스트 또는 블랙리스트 방식으로 통제합니다. 개별 시스템 콜 이름을 나열할 수도 있지만, systemd가 사전에 정의한 시스템 콜 그룹(@)을 활용하는 것이 일반적입니다. 예를 들어 SystemCallFilter=@system-service 지시어를 선언하면 일반적인 서비스 데몬이 동작하는 데 필요한 표준 입출력, 네트워크, 프로세스 기본 콜만 허용되고 비정상적인 커널 인터페이스는 차단됩니다.

기본적으로 허용되지 않은 시스템 콜이 호출되면 커널은 프로세스에 SIGSYS 시그널을 전달하여 프로세스를 즉시 강제 종료시킵니다. 운영 안정성을 확보하며 점진적으로 필터를 적용하려면 SystemCallErrorNumber=EPERM 지시어를 함께 선언하여 강제 종료 대신 EPERM(오퍼레이션 비허용) 에러를 반환받도록 구성할 수 있습니다. 한편 SystemCallArchitectures=native 지시어는 64비트 시스템에서 구형 32비트 ABI 시스템 콜을 호출하는 통로를 차단합니다. 공격자가 32비트 호환성 계층의 알려진 취약점을 악용해 Seccomp 검사를 우회하는 공격 벡터를 원천 제거합니다.

MemoryDenyWriteExecute와 네임스페이스 제약

MemoryDenyWriteExecute=yes 지시어는 메모리 영역에 대한 W^X(Write XOR Execute) 보안 규칙을 강제합니다. mmap 시스템 콜 호출 시 PROT_WRITE와 PROT_EXEC가 동시에 설정된 메모리 페이지를 할당받지 못하게 막고, mprotect를 통해 기존 쓰기 가능 메모리를 실행 가능 메모리로 변경하는 행위를 거부합니다. 이를 통해 버퍼 오버플로우 공격 시 메모리에 주입된 쉘코드가 실행되는 것을 방지합니다.

LockPersonality=yes 지시어는 personality 시스템 콜을 잠가 실행 도메인의 변경을 금지합니다. 공격자가 레거시 실행 에뮬레이션을 활성화하거나 ASLR(주소 공간 배치 난수화)을 무력화하는 행위를 막아냅니다. RestrictNamespaces 지시어는 프로세스가 unshare나 clone 시스템 콜을 통해 cgroup, ipc, net, mnt, pid, user, uts 네임스페이스를 새로 생성하지 못하도록 통제합니다. 특히 사용자 네임스페이스(user namespace)는 비특권 사용자가 커널 내부 로직을 호출하는 주요 통로로 악용되어 왔으므로, 컨테이너 관리 데몬이 아니라면 반드시 차단해야 합니다.

  • SystemCallFilter는 @system-service 등의 그룹을 통해 데몬에 불필요한 시스템 콜 호출을 차단합니다.
  • SystemCallArchitectures=native는 32비트 레거시 ABI를 차단하여 시스템 콜 우회 통로를 제거합니다.
  • MemoryDenyWriteExecute는 W^X 메모리 원칙을 강제하여 메모리 주입 쉘코드 실행을 차단합니다.
  • RestrictNamespaces는 사용자 네임스페이스 생성과 커널 권한 탈취 시도를 격리합니다.

6. 네트워크 인터페이스 및 소켓 패밀리 제약

네트워크 계층 하드닝은 침해된 프로세스가 외부 C2(Command and Control) 서버와 통신하거나 로컬 네트워크의 다른 호스트를 스캔하는 행위를 차단하는 핵심 방어선입니다. 리눅스 소켓 패밀리와 패킷 흐름을 systemd 차원에서 통제할 수 있습니다.

RestrictAddressFamilies를 통한 소켓 통신 통제

RestrictAddressFamilies 지시어는 프로세스가 socket 시스템 콜로 생성할 수 있는 네트워크 주소 체계를 화이트리스트 방식으로 제한합니다. 일반적인 웹 서비스라면 AF_UNIX(로컬 소켓 통신), AF_INET(IPv4), AF_INET6(IPv6) 세 가지만 허용하면 정상 운영이 가능합니다. 이 지시어를 엄격하게 구성하면 로우 소켓(Raw Socket)을 생성하는 데 사용되는 AF_PACKET이나 로컬 라우팅 테이블과 방화벽 상태를 조작할 수 있는 AF_NETLINK, 블루투스 통신 체계인 AF_BLUETOOTH의 생성이 거부됩니다. 공격자가 시스템 내부에서 패킷을 스니핑하거나 악의적인 네트워크 인프라 조작을 시도하는 행위를 차단할 수 있습니다.

eBPF 기반 IPAddressDeny 및 IPAddressAllow

systemd.resource-control 매뉴얼에 명시된 IPAddressDeny 및 IPAddressAllow 지시어는 cgroup v2 환경에서 리눅스 커널의 eBPF 기반 소켓 필터링 기능을 직접 제어합니다. 방화벽 데몬(iptables, nftables)과 별개로 특정 서비스 단위의 패킷 인그레스(Ingress) 및 이그레스(Egress) 규칙을 부과할 수 있습니다.

예를 들어 외부 인터넷 통신이 전혀 필요 없는 내부 배치 작업이나 로컬 데이터 처리 서비스의 경우 IPAddressDeny=any를 설정하면 모든 IPv4 및 IPv6 소켓 통신이 차단됩니다. 내부 통신만 유지해야 하는 경우 IPAddressAllow=localhost 또는 특정 내부 서브넷 CIDR(예: 10.0.0.0/8)을 지정하여 최소한의 통신 경로만 허용할 수 있습니다. 단, 이 설정은 DNS 조회(53 포트)나 로컬 호스트 통신까지 영향을 미치므로 허용 대상을 정밀하게 설계해야 합니다.

  • RestrictAddressFamilies는 AF_INET, AF_INET6, AF_UNIX 외의 위험한 소켓(AF_PACKET 등) 생성을 차단합니다.
  • IPAddressDeny=any는 서비스의 모든 네트워크 통신을 cgroup eBPF 레벨에서 즉각 차단합니다.
  • IPAddressAllow를 결합하면 로컬호스트나 신뢰된 내부 서브넷으로만 네트워크 통신을 한정할 수 있습니다.

7. 지시어별 방어 범위와 흔한 장애 지점 및 다중 값 비교

보안 지시어를 적용할 때 가장 빈번하게 마주하는 문제는 보안을 강화할수록 서비스가 예상치 못한 지점에서 비정상 종료된다는 점입니다. 각 지시어가 막아내는 위협과 그에 따른 운영상 대가, 그리고 문제가 발생했을 때의 복구 방안을 정확히 파악해야 안정적인 운영이 가능합니다.

지시어 차단하는 위협 흔히 발생하는 장애 점검 및 복구 방법
NoNewPrivileges execve 실행 시 SUID/SGID 및 파일 케이퍼빌리티를 통한 루트 권한 상승 차단 sudo, ping, passwd 등 SUID 비트에 의존하는 내부 보조 도구 실행 실패 해당 보조 바이너리의 루트 의존성을 제거하거나 외부 워커 프로세스로 분리
PrivateTmp 공유 /tmp 디렉터리 기반 심볼릭 링크 공격 및 임시 파일 가로채기 차단 /tmp 디렉터리에 생성된 공유 UNIX 소켓(예: MySQL 소켓) 연결 불가 공유 소켓 경로를 /tmp 대신 표준 런타임 디렉터리인 /run 하위로 이전
PrivateDevices 물리 디바이스 노드(/dev/sd*, /dev/mem 등) 직접 접근 및 하드웨어 조작 차단 GPU 가속, 사운드 카드(/dev/snd), 하드웨어 암호화 토큰 접근 실패 하드웨어 장치가 필수적인 서비스인 경우 비활성화하거나 DeviceAllow 설정 활용
ProtectSystem 시스템 실행 파일(/usr) 및 환경 설정 파일(/etc)에 대한 악의적인 쓰기 변조 방어 서비스가 /etc 설정 파일을 동적으로 갱신하거나 런타임 데이터를 쓰려 할 때 에러 설정 자동 갱신 데몬의 경우 full 대신 yes로 완화하거나 ReadWritePaths 지정
ProtectHome 사용자 개인 홈 디렉터리(/home, /root)의 개인키, 인증 정보 탈취 방어 홈 디렉터리 내부의 설정 파일(~/.config)이나 작업 데이터를 읽지 못함 서비스 작업 경로를 /var/lib 등으로 이전하거나 read-only 모드로 완화
ProtectKernelTunables /proc/sys 및 /sys 내부 매개변수 변조를 통한 커널 보안 정책 약화 차단 sysctl 네트워크 파라미터나 하드웨어 절전 설정을 자체 조정하는 도구 실패 커널 튜닝 작업을 서비스 기동 전 sysctl.d 설정이나 사전 스크립트로 분리
ProtectKernelModules CAP_SYS_MODULE 박탈을 통한 악성 커널 모듈(루트킷) 적재 차단 iptables 모듈이나 터널링 드라이버를 런타임에 동적으로 로드하는 서비스 실패 필요한 커널 모듈을 시스템 부팅 시 /etc/modules-load.d/ 에 사전 등록
ProtectControlGroups /sys/fs/cgroup 수정을 통한 자원 쿼터 우회 및 타 cgroup 간섭 방어 도커, 포드맨 등 컨테이너 런타임이 하위 cgroup을 생성하려 할 때 거부 컨테이너 엔진 서비스에서는 비활성화하고 Delegate=yes 지시어 사용
ProtectProc /proc 가시성 제한을 통한 타 사용자 프로세스 실행 인자 및 환경변수 정찰 방어 top, htop, 모니터링 에이전트가 다른 서비스 프로세스를 감지하지 못함 모니터링 서비스는 default로 두고 일반 애플리케이션 서비스에만 invisible 적용
RestrictAddressFamilies AF_PACKET 등 특수 소켓을 악용한 패킷 스니핑 및 네트워크 설정 교란 방어 로컬 소켓 통신 실패(AF_UNIX 누락) 또는 DNS 쿼리 실패(AF_INET 누락) 서비스가 필요로 하는 최소 소켓 패밀리(AF_INET AF_INET6 AF_UNIX)를 명시
RestrictNamespaces 사용자 네임스페이스 등 격리 환경 생성을 통한 커널 취약점 공격 방어 내부적으로 샌드박스를 구축하는 도구(bwrap, 브라우저 샌드박스) 실행 불가 프로세스 격리를 자체 수행하는 서비스에서는 해당 네임스페이스 종류만 예외 허용
RestrictSUIDSGID 파일시스템 내 SUID/SGID 권한 부여를 통한 영속적 백도어 생성 차단 패키지 설치 관리자나 권한 동기화 스크립트의 파일 생성 실패 빌드 및 설치 자동화 도구가 아닌 일반 데몬 서비스에 한정하여 적용
RestrictRealtime 실시간 스케줄러(SCHED_FIFO) 선점을 통한 CPU 독점 서비스 거부(DoS) 차단 실시간 오디오 처리(JACK, PipeWire)나 고주파 매매 등 저지연 작업 지연 실시간 처리가 핵심 요구사항인 특수 데몬을 제외한 모든 일반 서비스에 적용
SystemCallFilter 지정되지 않은 비표준 시스템 콜 호출을 통한 커널 악용 차단 서비스 프로세스가 SIGSYS 시그널을 수신하며 비정상 종료(Exit 159) SystemCallErrorNumber=EPERM으로 원인 파악 후 누락된 시스템 콜 추가 허용
SystemCallArchitectures 64비트 환경에서 구형 32비트 ABI 호출을 통한 Seccomp 필터 우회 차단 32비트 구형 바이너리나 크로스 컴파일된 레거시 라이브러리 실행 불가 모든 실행 바이너리를 64비트 네이티브로 재컴파일하거나 필요 아키텍처 허용
CapabilityBoundingSet 프로세스가 보유할 수 있는 리눅스 특권 케이퍼빌리티의 최대 범위 제한 chown, setuid, net_bind_service 등 필요한 관리 작업 호출 시 거부 strace나 시스템 로그로 거부된 케이퍼빌리티를 확인하여 최소한으로 허용
MemoryDenyWriteExecute 메모리 영역의 W^X 원칙 강제로 버퍼 오버플로우 쉘코드 실행 방어 Node.js(V8), Java(JVM), .NET 등 JIT 컴파일 기반 언어 런타임 구동 실패 JIT 런타임에 쓰기/실행 분리 옵션을 적용하거나 해당 서비스에서 비활성화
LockPersonality 실행 도메인(Personality) 변경을 통한 ASLR 무력화 방어 구형 유닉스 에뮬레이션 바이너리 구동 실패 표준 리눅스 환경에서 구동되는 최신 애플리케이션 서비스에 기본 적용
ReadOnlyPaths 지정된 특정 파일시스템 디렉터리에 대한 임의의 쓰기 및 수정 차단 애플리케이션이 해당 디렉터리 내부에 임시 파일 생성을 시도할 때 EROFS 발생 실제 쓰기가 필요한 세부 하위 경로를 ReadWritePaths 지시어로 상쇄 지정
User / Group 루트 계정 대신 최소 권한 비특권 전용 계정으로 프로세스 실행 강제 루트 소유 파일이나 1024 미만 특권 포트에 접근하지 못해 기동 실패 파일 소유권을 서비스 계정으로 변경하고 AmbientCapabilities로 포트 허용
UMask 새로 생성되는 파일과 디렉터리의 기본 권한을 안전한 마스크로 통제 타 계정이나 웹 서버가 서비스가 생성한 로그나 결과 파일에 접근 불가 공유가 필요한 경우 0077 대신 그룹 접근을 허용하는 0027 등으로 조정
IPAddressDeny cgroup eBPF 레벨에서 허가되지 않은 네트워크 IP 통신 일괄 차단 외부 API 통신, 데이터베이스 원격 접속, DNS 질의 패킷 전송 실패 IPAddressAllow 지시어로 필요한 특정 내부 서브넷 및 DNS IP를 명시 허용

특히 ProtectSystem, ProtectHome, ProtectProc과 같이 boolean 외에 여러 세부 값을 지원하는 지시어는 각 단계별로 파일시스템과 프로세스 트리가 재구성되는 원리가 완전히 다릅니다. 공식 매뉴얼에 명시된 동작 차이를 명확히 구분해야 합니다.

지시어 설정값 공식 매뉴얼 기준 동작 및 격리 범위 주요 권장 대상 서비스
ProtectSystem no 파일시스템을 격리하지 않고 호스트 기본 마운트 상태를 그대로 유지 시스템 패키지 관리자, OS 업데이터 등 시스템 변조가 목적인 데몬
yes /usr 디렉터리와 부트로더 디렉터리(/boot, /efi)를 읽기 전용으로 마운트 /etc 설정을 자체 수정해야 하는 설정 관리 데몬
full /usr, /boot, /efi에 더하여 /etc 디렉터리까지 읽기 전용으로 마운트 일반 웹 서버, API 백엔드, 데이터베이스 등 대부분의 표준 서비스
strict API 가상 경로(/dev, /proc, /sys)를 제외한 전체 파일시스템 트리를 읽기 전용으로 마운트 쓰기 경로가 완전히 통제된 무상태(Stateless) 마이크로서비스
ProtectHome no 홈 디렉터리 접근을 제한하지 않음 사용자 세션 관리자, 백업 도구 등 홈 데이터 처리가 목적인 데몬
read-only /home, /root, /run/user 디렉터리를 읽기 전용으로 마운트 사용자 설정을 읽어야 하지만 수정은 필요 없는 도구
tmpfs /home, /root, /run/user에 빈 메모리 기반 파일시스템을 마운트하여 실제 데이터 차단 홈 디렉터리 경로에 임시 쓰기 공간을 요구하는 격리형 빌드 도구
yes /home, /root, /run/user 디렉터리를 0000 권한의 빈 디렉터리로 마운트하여 접근 차단 사용자 데이터와 무관한 일반 백그라운드 시스템 서비스
ProtectProc default procfs 기본 마운트 상태 유지 (DAC 권한 범위 내에서 타 프로세스 관찰 가능) 시스템 모니터링 도구, 프로세스 감시자 데몬
noaccess 다른 사용자의 프로세스 디렉터리 메타데이터 조사를 거부 기본적인 프로세스 정보 숨김이 필요한 범용 서버 서비스
invisible 다른 사용자의 프로세스를 /proc 트리에서 완전히 숨김 (ps 출력에 나타나지 않음) 다중 테넌트 환경의 격리형 웹 서비스 및 API 컨테이너
ptraceable 해당 서비스가 ptrace 권한을 보유한 프로세스만 /proc에서 가시화 디버거 서비스 및 특정 하위 워커 프로세스 관리 도구

8. 점진적 적용 전략: 드롭인 오버라이드와 단계별 배포

보안 강화를 서두르다 흔히 범하는 실수는 수십 개의 샌드박싱 지시어를 한 번에 서비스 유닛에 추가하는 것입니다. 이 경우 서비스가 기동되지 않았을 때 어떤 지시어가 원인인지 분별하기 어려워 결국 모든 보안 설정을 되돌리게 됩니다. 안정적인 하드닝을 위해서는 점진적인 적용과 올바른 설정 관리 체계가 필수적입니다.

드롭인(Drop-in) 오버라이드 구조의 필요성

패키지 관리자(apt, dnf 등)가 설치한 기본 서비스 유닛 파일은 대개 /usr/lib/systemd/system/ 또는 /lib/systemd/system/ 디렉터리에 위치합니다. 이 파일을 직접 편집하면 패키지가 업데이트될 때 설정이 덮어쓰여 보안 지시어가 소실되거나 패키지 충돌 경고가 발생합니다. systemd는 이러한 문제를 방지하기 위해 /etc/systemd/system/ 디렉터리 하위에 드롭인 오버라이드 구조를 지원합니다.

서비스 파일 전체를 복사할 필요 없이, /etc/systemd/system/서비스명.service.d/ 디렉터리를 생성하고 그 안에 override.conf 파일을 작성하여 변경하거나 추가할 지시어만 정의합니다. systemd는 런타임에 기본 유닛 파일과 override.conf를 병합하여 실행 구성을 완성합니다.

# 드롭인 오버라이드 디렉터리 생성 및 파일 작성 예시
sudo mkdir -p /etc/systemd/system/myapp.service.d
sudo nano /etc/systemd/system/myapp.service.d/override.conf

4단계 점진적 적용 절차와 예시 구성

보안 강화는 위험도가 낮고 장애 유발 가능성이 적은 파일시스템 기본 격리부터 시작하여, 커널 보호, 시스템 콜 필터링, 네트워크 통제 순으로 단계를 나누어 검증해야 합니다. 아래는 4단계 배포 프로세스를 보여주는 예시 설정입니다. 운영 환경에 적용하기 전에 반드시 스테이징 환경에서 서비스의 정상 동작을 검증해야 합니다.

# [주의: 아래 설정은 검증 목적으로 작성된 예시이며, 실제 운영 환경에서는
# 서비스의 의존성에 따라 적절히 수정한 후 적용해야 합니다.]

[Service]
# 1단계: 기본 신원 축소 및 파일시스템 격벽 (장애 위험: 낮음)
NoNewPrivileges=yes
ProtectSystem=full
ProtectHome=yes
PrivateTmp=yes
UMask=0027

# 2단계: 커널 및 시스템 상태 변조 방어 (장애 위험: 보통)
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
ProtectProc=invisible
RestrictRealtime=yes
RestrictSUIDSGID=yes

# 3단계: 시스템 콜 및 메모리 실행 방어 (장애 위험: 중상 - JIT 엔진 주의)
SystemCallFilter=@system-service
SystemCallFilter=~@privileged @resources
SystemCallArchitectures=native
MemoryDenyWriteExecute=yes
LockPersonality=yes
RestrictNamespaces=yes

# 4단계: 소켓 및 네트워크 통제 (장애 위험: 상 - 외부 연동 서비스 점검)
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
# IPAddressDeny=any
# IPAddressAllow=localhost 10.0.0.0/8

설정을 저장한 후에는 systemd 데몬 구성을 다시 읽어 들이고 서비스를 재기동해야 합니다. 이후 systemd-analyze security 명령어를 통해 해당 유닛의 종합 보안 노출도 점수를 진단합니다.

# 설정 반영 및 보안 진단 실행
sudo systemctl daemon-reload
sudo systemctl restart myapp.service
systemd-analyze security myapp.service
  • 1단계에서는 NoNewPrivileges, ProtectSystem=full, ProtectHome=yes, PrivateTmp=yes를 통해 기본 격벽을 세웁니다.
  • 2단계에서는 커널 튜너블, 모듈 적재, cgroup 수정 차단과 procfs 은폐를 추가하여 커널 공격면을 좁힙니다.
  • 3단계에서는 SystemCallFilter와 MemoryDenyWriteExecute를 적용하되 런타임 언어(JIT) 호환성을 철저히 검증합니다.
  • 4단계에서는 소켓 패밀리와 IP 제약을 통해 인가되지 않은 외부 패킷 흐름과 로컬 스니핑을 차단합니다.

9. 확인하지 못한 것

공식 매뉴얼 분석과 기술 검토 과정에서 다음과 같은 사항은 명확한 1차 출처를 통해 확인하지 못했으므로 사실로 단정하지 않습니다.

  • 주요 리눅스 배포판(Ubuntu, Debian, RHEL, Arch Linux 등)의 기본 systemd 빌드 시 지정된 컴파일 타임 매크로 및 기본 샌드박싱 정책의 세부 차이를 확인하지 못했습니다. 공식 매뉴얼은 배포판별 기본 설정값을 명시하지 않습니다.
  • CPU 아키텍처(x86_64, aarch64, riscv64 등)와 리눅스 커널 버전에 따라 SystemCallFilter의 @system-service 그룹에 포함되는 구체적인 시스템 콜 매핑 목록의 차이를 확인하지 못했습니다.
  • systemd-analyze security 명령어가 산출하는 전체 노출도 점수(0.0~10.0)에서 각 지시어별 가중치(weight)가 최종 점수에 반영되는 구체적인 수학적 합산 공식 및 임계치 구간은 man 페이지에 세부 수식이 공개되어 있지 않아 확인하지 못했습니다.
  • Docker나 Podman 등 비특권 루트리스(Rootless) 컨테이너 내부에서 systemd를 PID 1로 구동할 때, 호스트 커널의 네임스페이스 제약으로 인해 일부 샌드박싱 지시어가 조용히 무시되거나 오류를 내는 구체적인 조건 차이를 확인하지 못했습니다.
