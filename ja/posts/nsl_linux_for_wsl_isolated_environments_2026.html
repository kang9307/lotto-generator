背景 — ホスト環境を汚染しない開発基盤への要求

開発現場において、ライブラリのバージョン競合やシステム環境の汚染は長年の課題である。単一のホスト環境で異なるバージョンのコンパイラ、Cランタイム、あるいはディストリビューション固有のパッケージを混在させると、オペレーティングシステムの整合性が容易に崩れる。近年、基本ルートファイルシステムを読み取り専用で保護するイミュータブル（不変）Linuxディストリビューションが注目されている理由もここにある。しかし、システムの堅牢性が高まる一方で、日常的なパッケージ導入（apt installやdnf install）やデーモンの動作検証は制約を受けることになる。

Windows環境では、Windows Subsystem for Linux（WSL）がこの課題に対する実用的な解を提供してきた。ホストOSのレジストリや基本システムを改変することなく、独立したLinux環境内でツールを導入し、ホストの作業ディレクトリを共有して開発できるためである。GeekNewsで紹介されたオープンソースプロジェクトNSL（NSpawn Subsystem for Linux）は、このWSLと同様の体験をイミュータブルLinuxホストにもたらす試みである。一部の紹介では「WSL用Linux」と要約される場合もあるが、公式文書の定義では「Linuxホスト上でWSLスタイルの開発体験を提供するツール」である。

本稿では、Microsoft Learn公式文書に記されたWSL 2の仮想マシン隔離アーキテクチャを整理したうえで、NSLがLinux上でsystemd-nspawnと共有仮想マシンを組み合わせて依存関係を隔離する設計思想と制約について考察する。

WSL 2の隔離アーキテクチャ — Microsoft Learn文書に基づく軽量VMモデル

Microsoft Learn公式文書に記載されているWSL 2の中核設計は、完全なLinuxカーネルを実行する軽量仮想マシン（Utility VM）に基づいている。Windowsホストのハイパーバイザー上で動作し、以下の階層的隔離原則に従っている。

  • カーネル共有とコンテナ分離: 管理対象の仮想マシン内で単一のLinuxカーネルが稼働する。導入された複数のLinuxディストリビューションは、同一のVMカーネルとメモリ空間を共有しながら、PID・マウント・ユーザー・cgroupネームスペースによって隔離されたコンテナとして実行される。
  • システムコール互換性: 呼び出しを変換していたWSL 1とは異なり、実Linuxカーネル上で直接処理するため、FUSEファイルシステムやDockerデーモンなどの高度なシステム依存機能を完全サポートする。
  • systemdサポート: /etc/wsl.confの[boot]セクションにsystemd=trueを指定することで、ディストリビューション内でsystemdをPID 1として起動し、各種サービスデーモンを管理できる。
  • インスタンスの可搬性: wsl --exportコマンドでファイルシステム全体を.tarアーカイブとして出力し、wsl --importコマンドにより指定した場所へ独立インスタンスとして復元できる。

この構成は開発の利便性を高める一方で、仮想マシン境界を跨ぐファイルアクセスにおける9Pプロトコルのオーバーヘッドや、メモリ返却管理のチューニングを伴う特性がある。以下はMicrosoft Learnに記載された非破壊的な確認およびバックアップ手順である。

# インストール済みWSLディストリビューションと状態の確認
                    wsl --list -v
                    
                    # ディストリビューション全体をtarアーカイブとして安全にエクスポート
                    wsl --export Ubuntu-24.04 backup_ubuntu.tar
                    
                    # エクスポートしたアーカイブを新たな独立インスタンスとしてインポート
                    wsl --import Custom-Dev C:\WSL\CustomDev backup_ubuntu.tar

NSLの内部構造 — イミュータブルLinux上の共有VMとsystemd-nspawn

Frostyardの公式文書によると、NSL（NSpawn Subsystem for Linux）はホストのパッケージマネージャーを汚染することなく多様なLinux環境を提供するため、多層的な隔離設計を採用している。その中核を担うのがsystemd-nspawnと共有仮想マシン（QEMU）の連携である。

従来のchrootはroot権限の逸脱やリソース制御に課題があり、一般的なDockerコンテナは単一アプリの隔離を主眼とするため、完全なinitシステムの常駐を前提としていない。これに対しsystemd-nspawnは、OSコンテナを立ち上げてinitプロセス（PID 1）を正常に起動し、ディストリビューション全体のライフサイクルを管理できる。

NSLはイミュータブルLinuxホスト上で以下の4層構造を形成する。

  • 一般ユーザー権限での動作: NSLはホストの非特権ユーザー権限で起動する。ホストのシステムファイル、デバイス権限、グループ設定、/etc/sudoersを改変しない。
  • 共有仮想マシン層: ホストカーネル上で直接nspawnを実行するのではなく、QEMUおよびvirtiofsdによる共有VMの内部でマシン群を実行する。これにより、ホストのカーネル権限に影響を与えずに自由な環境を提供する。
  • systemd-nspawnマシン: 共有VM内部で各ディストリビューションは独立したsystemd-nspawnコンテナとしてインスタンス化される。パッケージの導入状態やサービス設定はセッション終了後も維持される。
  • 署名済みディストリビューションイメージの検証: Frostyard公開ワークフローで毎週再ビルドされ、暗号署名検証を通過したイメージのみがローカルにキャッシュされる。

以下は公式READMEに記載された基本的な作成および実行ワークフローである。

# 署名検証を経てDebian 13イメージを取得し初期マシンを作成
                    nsl create debian --distro debian:13
                    
                    # カレントディレクトリのコンテキストを維持したままログインシェルに入る
                    nsl
                    
                    # マシン内で単一コマンドを実行し、終了ステータスをホストへ返却
                    nsl run make test

ファイルシステムと権限の同期 — /mnt/hostとUIDの一致

隔離環境を導入する際、開発者が直面しやすい問題がファイルの同期遅延と権限の不整合である。コンテナ内でrootとしてファイルを作成すると、ホスト上の一般ユーザーがそのファイルを編集できなくなる現象が頻発する。

NSLはこれらの摩擦を防ぐため、透過的なバインドマウントと権限同期機構を備えている。

  • ホストディレクトリの自動マウント: ホストのホームディレクトリ（$HOME）、外部メディア（/run/media/USER）、およびマウントツリー（/mnt）が、マシン内の/mnt/host配下に自動配置される。
  • 同一ユーザー権限のマッピング: マシン内部のユーザーアカウントには、ホストと同一のユーザー名、UID、GIDが割り当てられる。そのため、マシン内でビルドした生成物もホスト上で正しい所有権を保つ。
  • マシン内パスワード不要sudo: マシン内部ではパスワードなしでsudoを実行できる権限が付与される。開発者は制約なくパッケージを導入できるが、この権限はマシン内部に限定されホストには及ばない。
  • 作業ディレクトリの追従: ホスト上のプロジェクトディレクトリでnslを実行すると、マシン内部でも該当ディレクトリが作業ディレクトリとして開かれる。
  • バックアップとマシンの可搬性: 停止中のマシンを単一アーカイブとしてエクスポートし、他のホストや新環境へインポートして復元できる。

この仕組みにより、ホストのエディタで編集を行い、実行とビルドのみをゲストマシンに委任する作業フローが円滑に行える。類似のファイル共有やバックアップの基礎はLinux Rsyncガイドでも解説されている。

ネットワークポートとGUI連携 — 127.0.0.1転送とWaypipe

Web開発やグラフィカルな検証作業では、ゲスト内のプロセスとホストのデスクトップとの連携が不可欠である。NSLはネットワークおよびディスプレイに対して以下の連携方式を提供する。

  • ローカルポート転送: マシン内でWebサーバーがポート（3000や8080など）を開くと、ホスト側のブラウザからIPアドレスを調べることなく127.0.0.1経由でアクセスできる。
  • Waypipeによるウィンドウ表示: マシン内で動作するWayland対応GUIアプリケーションは、Waypipeを通じてホストのデスクトップ画面に直接ウィンドウを表示する。これはWSLgに類似した体験を提供する。
  • SSH接続によるエディタ連携: nsl ssh-configコマンドによりSSHホスト設定が生成され、VS CodeのRemote - SSHやNeovimから各マシンへ直接接続できる。
  • 永続的な環境保持: 一時的なコンテナとは異なり、端末を終了しても導入したライブラリや設定ファイルは消失しない。
  • バックグラウンドサービスのライフサイクル管理: マシン内のsystemdがデーモンを管理するため、開発用データベースや常駐プロセスが安定して稼働する。

これらの連携により、隔離環境であることを意識させないシームレスな操作感が実現されている。

完全な分離が必要な場合 — --isolated専用VMとセキュリティ境界

日常の開発には透過的なファイル共有やポート転送が有用である一方、セキュリティの観点では境界の緩和につながる可能性がある。出所不明のスクリプトや検証前のパッケージを実行する場合、/mnt/host経由でホストの機密情報へアクセスされる懸念が生じるためである。

NSLはこのリスクに対応するため、明示的な--isolated実行モードを用意している。

  • 専用仮想マシンの起動: --isolatedフラグを指定すると共有VMを利用せず、そのマシン専用の独立したQEMU仮想マシンが立ち上がる。
  • ホストファイルシステムの完全遮断: /mnt/hostのマウントが無効化され、ホストのホームディレクトリや外部ストレージへの読み書きが遮断される。
  • 画面共有とホスト連携の停止: Waypipeによるウィンドウ表示やホスト連携アクションが停止され、ゲスト内の挙動が専用VMの内部に封じ込められる。
  • 安全な検証基盤: 外部から入手した未検証コードのビルドテストや隔離検査に適したセキュリティ境界が確保される。
  • ホスト向けアクション伝播の遮断: ホストOSへのイベント通知やIPCメッセージ送信が遮断され、悪意あるコードのホスト影響を阻止する。

開発用途の「密連携環境」とセキュリティ用途の「完全隔離環境」を用途に応じて切り替えられる設計となっている。

確認できなかった事項

  • NSLマシン内部においてDockerやPodmanなどのネストされたコンテナランタイムが正常に動作するかどうか。
  • Waypipeを用いた画面転送環境下でvirtio-gpuなどを利用した3Dグラフィックスのハードウェアアクセラレーションが有効か否か。
  • x86-64アーキテクチャ以外のAArch64（ARM64）環境における公式イメージの提供有無。
  • 共有VM内で複数マシンを同時実行した際のCPUやメモリ使用量を細かく制御するcgroup設定オプションの有無。
  • virtiofsdによるホストバインドマウント領域における大規模ファイルI/Oの具体的なベンチマーク性能値。
