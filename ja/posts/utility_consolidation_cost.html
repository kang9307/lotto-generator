メニューバーの場所とメモリを節約する代わりに何が一箇所に集まるのか

2026-09-04 IT・技術

メニューバーにアイコンが九つ並んだ画面を見たことがあるはずだ。クリップボード履歴が一つ、ウインドウ配置が一つ、温度表示が一つ、グローバルショートカットが一つ、画面キャプチャが一つ。それぞれは数年前のある日にたった一つの不便を消すために入れたもので、そのときは正しい選択だった。問題はその選択が九回繰り返されたことにある。

だから一つにまとめようという提案はいつも魅力的に聞こえる。十二個が一つになれば場所も減り、管理する対象も減りそうに見える。この計算は半分は正しい。ところが減るものと一緒に一箇所へ集まるものがあり、集まる側はたいてい問題が起きた後にしか見えない。

この記事は特定のアプリを選ぶための記事ではない。まとめるという形が成り立つ条件と成り立たない条件を数えておく記事だ。macOS の話から始めるが、計算そのものは OS を選ばない。Windows と Linux では同じ問題が違う形で現れるだけである。

この記事は統合型ユーティリティと個別ツールの間にある構造的な取引を整理したものであり、特定製品への推奨や評価ではない。インストールや設定の方法は扱わない。引用した OS の動作と権限の説明は2026年9月時点で各社の公式文書において確認したものである。

きっかけ - アイコン一つが十二個の代わりをするという提案

2026年9月初め、韓国の開発者コミュニティで macOS のユーティリティを一つに束ねたオープンソースアプリが紹介された。リポジトリの説明は無料オープンソースの macOS メニューバーツールキットとなっており、アプリ別の音量調整と出力デバイス切り替え、システム監視、ウインドウのライブプレビューが付いたアプリスイッチャー、ウインドウ配置、クリップボード履歴、テキストスニペット展開、画面キャプチャと収録、コマンドバー、アプリ削除と整理までが一つのリストに入っている。Swift で書かれライセンスは GPL-3.0 で、Apple Silicon と macOS 14 Sonoma 以上を要求する。

リポジトリが作られた日付は2026年6月12日で、2026年9月4日に照会した値でスターが15,004個、フォークが527個、開いている issue が327個である。三か月でこれだけの関心を集めたということだ。ウインドウ切り替え、ウインドウ配置、アプリ削除をそれぞれ別のアプリでやってきた人にとって、一つに減らそうという話は実質的な提案である。

ここから先この記事の関心は、そのアプリではなくまとめるという形そのものにある。この種の提案は周期的に出てくるし、そのたびに同じ計算が必要になる。何が減り、何が一箇所に集まり、集まったものが崩れたときの範囲がどれほどか。

ユーティリティはなぜ積み上がるのか

常駐ユーティリティはほぼ例外なくOS がやってくれない小さな欠落から生まれる。欠落はどれも小さい。さっきコピーしたものではなく三つ前にコピーしたものが要る。ウインドウ二つを画面半分ずつに置きたい。バッテリーが何パーセントかではなく何ワット使っているかを見たい。ファイル二百個の名前を規則どおりに変えたい。

欠落が小さいので解決も小さく済む。アプリを一つ落としてメニューバーに置けば終わりで、その瞬間の判断はたいてい正しい。問題は、この判断が数年かけて九回下される間に消す判断は一度も下されないことだ。常駐プロセスは静かなので、使わなくなった後も居続け、居続けているという事実自体が忘れられる。

積み上がり方には共通点がある。知っておくと後で何を整理するか選ぶときに役に立つ。

  • 導入コストがほぼゼロだ。落として有効にすれば終わりなので、導入の時点で天秤にかける作業が起きない
  • コストが後から、しかも分散して現れる。数十メガバイトとメニューバー一枠はその瞬間には感じられない
  • 削除のきっかけが来ない。ユーティリティは壊れて存在を知らせることがまれで、静かに回り続ける
  • 機能が重なっても重なった事実がわからない。三つのアプリがそれぞれ画面キャプチャを持っていても、別々のショートカットなら重なりは表に出ない
  • OS がその機能を後から標準搭載してもユーティリティは残る。手に馴染んでいるから、あるいは標準機能ができたことを知らないからだ

まとめるとユーティリティが積み上がるのは不注意の結果ではなく、導入は安く削除にはきっかけがない構造の結果である。この構造を理解して初めて、まとめることが何を解決するのかも正確に見える。同じ種類の計算をソフトウェアの乗り換え全般に当てはめたものは、軽量な代替ソフトへ乗り換える前にで六つの軸として扱った。

まとめて実際に得るもの

まとめることを貶す記事にならないためには、得る側を先に正確に数えなければならない。そして得るものは実在する。

一つ目はメニューバーの場所だ。好みの問題として扱われがちだが実際には有限の資源である。メニューバーの右側の幅は決まっており、メニューの多いアプリを使うとアイコンが切れて見えなくなる。カメラノッチのある機種はその幅がさらに狭い。

二つ目はプロセス数とログイン項目の数だ。十個が一つになればログイン直後に同時に目覚めるプロセスもそれだけ減る。リソース消費がどれだけ減るかは別の問題だが、数が減ること自体は確実である。

三つ目は設定の一貫性だ。個別ツール十個は互いのショートカットを知らない。新しいツールを入れると以前のツールのショートカットが静かに効かなくなり、原因を探すのに時間がかかる。一つのアプリの中ならアプリが衝突を知っていて、たいてい教えてくれる。

四つ目はアップデートと信頼判断の地点が一つになることだ。十個のツールは十人の開発者をそれぞれ信頼するという決定であり、OS のメジャーアップデートのたびに十回の互換性確認である。まとめればこれが一回になる。

そして五つ目が権限付与の回数である。五つのツールに五回与える代わりに一つのアプリに一度与えればよい。表面上は明らかな利得だ。ところがこの項目がこの記事の回転軸である。減ったのは付与の回数であって、付与した権限の総量ではないからだ。

まとめると失う五つ

失う側は五つに整理される。五つが互いに独立ではなく、一つが別の一つを大きくする関係にあることが重要だ。

失うもの個別ツールの場合統合アプリの場合実際に問題になる瞬間
単一障害点一つ死んでもその機能一つが止まるだけ一つ死ぬと十の機能が一緒に止まるアップデート直後、OS のメジャーアップグレード直後
権限の和集合各ツールが自分の機能に必要な分だけ持つ一つのプロセスが全部を持つそのアプリが侵害されたり所有・維持の主体が変わるとき
交換コスト気に入らない一つだけ差し替える部分交換ができない。全部が結び付いている一つの機能だけが自分の作業に合わないと判明したとき
機能の深さ専用ツールが長く磨いた細部があるよくある使い方を覆う平均的な実装になるその機能が自分の作業の中心であるとき
保守リスク一つ止まっても残り九つは生きる十が一度に消える開発が止まった後に OS が一段上がるとき

単一障害点から見よう。常駐アプリは OS のメジャーアップデートのたびに一度は壊れる。開発者の技量の問題ではなく、システムの動作に密着した機能があるからで、下が変われば上に載ったものも揺れる。個別ツール十個のうち二、三個が壊れる出来事と、統合アプリ一つが壊れて十の機能が同時に止まる出来事は同じ規模ではない。前者は不便であり後者は作業停止だ。

交換コストは個別ツールの最も実用的な長所を教えてくれる。部分交換の可能性である。ウインドウ配置が気に入らなければそれだけ替えればよい。統合アプリではそれができず、実際に起きるのはたいていこうだ。統合アプリを入れたままその一つのために別のアプリをもう一つ立ち上げる。まとめた理由がその場で消える。

機能の深さは設計上避けにくい側に近い。よくある使い方を覆うのは合理的な決定であり、大半の人に合う。食い違うのはその機能が自分の作業の中心である人たちだ。クリップボード履歴を一日に百回使う人には検索構文、書式保持の有無、特定アプリの除外規則が要り、そういう細部はその機能だけを長く作ってきたツールに積もっている。

保守リスクは統合がリスクをどう再配置するかを示す。個別ツール十個は十人に分散したリスクで、三つ止まっても七つは生きる。統合アプリはそのリスクが一箇所に寄った形だ。オープンソースならフォークの可能性が残るが、フォークが可能であることと誰かが実際に維持することは別の話である。

  • 五つのうち四つは時間が経たないと現れない。導入初週の満足度では判断がつかない
  • 単一障害点と保守リスクは同じ軸の短い版と長い版だ。前者は数日、後者は数年の話である
  • 交換コストはまとめの度合いによって変わる。機能ごとに有効化・無効化できるならかなり緩和される
  • 機能の深さは人によって違う場所で問題になる。他人のレビューで判断するのが最も難しい項目だ
  • 残る一つ、権限の和集合は性格が違う。時間ではなく構造の問題である

権限の和集合がこの問題の中心だ

macOS は常駐ユーティリティが必要とする権限を機能別に分けてある。システム設定のプライバシーとセキュリティの項目にそれぞれ別のリストとして並んでおり、Apple は各項目が何を許可するのかを短い文で書き添えている。この文をそのまま読むことがこの節の要点だ。

権限Apple の説明(2026年9月時点)この権限を要求するよくある機能
アクセシビリティアプリがスクリプトとシステムコマンドを実行して Mac を制御することを許可するウインドウ配置、ウインドウのサイズ変更、ショートカット拡張、自動化
入力監視アプリがマウスやトラックパッドの入力を監視し、キーボードで入力する内容を見ることを許可するグローバルショートカット、テキストスニペット展開
画面とシステムオーディオの収録アプリが画面とオーディオを収録すること、またはオーディオだけを録音することを許可する画面キャプチャ、ウインドウプレビュー、他アプリのウインドウタイトルの読み取り
フルディスクアクセス他のアプリのデータ、Time Machine バックアップのデータ、この Mac のすべてのユーザーに対する特定の管理設定を含め、コンピュータ上のすべてのファイルにアプリがアクセスすることを許可するアプリ削除・整理ツール、キャッシュ整理
マイクアプリが Mac のマイクにアクセスすることを許可する画面収録時の音声の同時録音

個別ツールを使うとき、これらの権限は別々のプロセスに付く。ウインドウ配置ツールはアクセシビリティだけ、キャプチャツールは画面収録だけ、整理ツールはフルディスクアクセスだけを持つ。それぞれ自分の仕事に必要な分だけを持ち、それ以上はシステムが止める。

一つにまとめると一つのプロセスが五つを全部持つ。機能の和集合を作れば権限の和集合が付いてくる。アプリが欲張ったからではなく、その機能をやるにはその権限が実際に必要だからだ。ウインドウ配置にはアクセシビリティが要り、ウインドウプレビューには画面収録が要る。機能が正直にその権限を使う。

では何が変わるのか。二つだ。一つ目、権限は機能単位ではなくアプリ単位で付与される。ウインドウ配置機能を使わないと決めても、そのアプリに与えたアクセシビリティ権限は、ユーザーがシステム設定で自ら回収するまで残る。機能を切ることと権限を取り上げることは別の動作だ。

二つ目、事故が起きたときの範囲が変わる。ウインドウ配置ツールが侵害されればウインドウを動かす権限が問題になるが、五つを全部持つアプリが侵害されれば画面と入力とすべてのファイルが一度にかかる。これは確率の話ではなく範囲の話である。

アクセシビリティ権限が許すものの実際の大きさ

五つの中でも特に広いのがアクセシビリティだ。Apple の説明は一文である。アプリがスクリプトとシステムコマンドを実行して Mac を制御することを許可する。短いが制御という語が抱える範囲が広い。他のアプリの画面要素を読んで操作でき、キー入力を作り出せる。ウインドウ配置が可能な理由がそれだ。他のアプリのウインドウという客体にアクセスして位置とサイズを変えているからである。

Apple 自身がこの権限をどう分類しているかがより明確な信号だ。Apple のプラットフォームセキュリティ文書は、アクセシビリティと自動化の機能について他の保護をすり抜けないようユーザーの許可を求めると記している。この権限は他の権限と並ぶ一つではなく、他の権限を越えうるので別に囲っておいたものだという意味である。

画面収録の権限も名前より広い。macOS 10.15 からウインドウ一覧 API が返すウインドウ名の値が画面収録権限に紐づけられており、Apple 開発者フォーラムの Apple エンジニアの回答がこの動作を確認している。アプリスイッチャーが他のアプリのウインドウタイトルを見せるのに画面収録権限が要る理由だ。ウインドウタイトルには開いている文書の名前、会話相手の名前、訪問中のページのタイトルがそのまま入る。収録しなくてもタイトルだけでその人が今何をしているかがかなり再構成される。

Apple が画面収録の設定画面に添えた案内文も読んでおく価値がある。サードパーティのアプリやウェブサイトに画面とオーディオの収録を許可すると、それらが収集する情報はその事業者の規約とプライバシーポリシーの適用を受ける、という文だ。つまり権限を与えた後の統制は OS ではなくそのアプリのポリシーにある。システムがしてくれるのは入口で一度尋ねるところまでだ。

誤解を一つ整理しておく。権限が強いということは、そのアプリが悪いことをするという意味ではない。要点は権限の大きさではなく権限が集まる地点の数だ。同じ五つが五箇所に分かれているか一箇所に集まっているかが、何かが間違ったときの結果を決める。

オープンソースはこの問題を減らすが消しはしない。ソースを読めることと自分が実際に読んだことは違うし、配布されたバイナリがそのソースから出たかは再現可能なビルドのような別の仕掛けがあって初めて確認できる。オープンソースの実質的な利益は監査可能性であって監査完了ではない。機器に対する統制権がどこで分かれるかは買ったのに自分のものではない部分で別に扱った。

何をまとめて何を分けておくか

ここまで来れば判断基準が作れる。軸は三つで、三つとも製品についての質問ではなく自分の使い方についての質問である。

軸問うべきことまとめるほうがよい場合分けておくほうがよい場合
使用頻度一日に何回使うか週に数回程度。深さが要らないので平均的な実装で十分だ一日に何十回。専用ツールが磨いた細部がすぐに惜しくなる
権限の強さこの機能にどの権限が必要か権限がそもそも要らない機能。単位変換、色の抽出、電卓のようなものフルディスクアクセスや画面収録が必要な機能。分ければ範囲が狭まる
代替不可能性止まると作業も止まるかなくても済む便利機能。数日なくても過ごせる業務の流れの一部になった機能。単一障害点の中に入れない

三つの軸が同じ方向を指せば答えは簡単だ。たまに使い、権限も要らず、なくても済む機能は全部まとめても失うものがほとんどない。逆に毎日使い、権限が強く、ないと困る機能は分けておくほうがよい。

難しいのは軸が食い違うときだ。代表例がクリップボード履歴である。毎日何十回も使い、ないとすぐ不便で、そのうえ通過するものすべてを保存する。ところがこの機能の危険は権限のリストに現れない。危険は権限ではなく保存そのものにある。パスワード管理ツールからコピーした値、ワンタイム認証コードがその履歴にそのまま残る。

だからクリップボード履歴はどちらに置くにせよポリシーを確認しなければならない機能になる。参考になる基準線が Windows 側に文書としてある。Microsoft は Windows のクリップボード履歴が25項目まで保持され、1項目あたり4MB までで、テキスト・HTML・ビットマップ形式に対応し、PC を再起動するたびにピン留めした項目を除いて消えると明記している。保持数と削除の時点が文書に書かれていること自体が基準だ。ツールを選ぶときに問うべきは機能一覧ではなく、こういう文があるかどうかである。

  • まとめる前に数えること — いま入れているユーティリティのうち直近一か月に実際に使ったものは何個か。使っていないものを消せばまとめる理由が半分になる
  • 権限から確認すること — 統合アプリが要求する権限の一覧を見て、そのうち自分が使わない機能のために必要なものがあるかを見る。あればその機能は切り、権限も与えない
  • 一度に全部移さないこと — 権限が弱くあまり使わない機能から移す。クリップボード履歴と整理ツールは最後だ
  • 消す前に猶予を置くこと — 個別ツールを消すのは二週間ほど統合アプリで過ごしてからにする。戻る道を残す安上がりな方法だ
  • 機能別に切れるか見ること — 統合アプリが機能を個別に無効化できるなら交換コストと権限の問題が同時に緩和される。統合アプリを選ぶ最も重要な条件に近い

OS はユーティリティを吸収し続けてきた

ユーティリティという物にはもともと一時性という性質がある。欠落を埋めるために生まれたので、欠落が埋まれば存在理由を失う。これは失敗ではなく正常な結末で、実際にここ数年で何度も起きた。

機能ユーティリティの領域だった頃いま(2026年9月時点)
ウインドウのタイリング(macOS)サードパーティのウインドウ管理ツールが担当macOS 15 Sequoia から標準。システム設定のデスクトップと Dock に、ウインドウを画面の端へドラッグしてタイリング、メニューバーへドラッグして画面を埋める、Option キーを押しながらドラッグしてタイリング、タイリングしたウインドウに余白、といった項目がある
ウインドウのスナップ(Windows)サードパーティのツールが担当Windows 11 と 10 のスナップレイアウト。Win+Z で配置候補を開き Win+方向キーで寄せる
クリップボード履歴(Windows)サードパーティのクリップボード管理ツールWin+V で有効にする標準機能。25項目、1項目あたり4MB、テキスト・HTML・ビットマップ
スタートアップ管理専用の整理ユーティリティWindows は設定とタスクマネージャー、macOS はシステム設定の一般の中にログイン項目
ユーティリティの束そのもの個人開発者たちの個別アプリMicrosoft PowerToys。25個以上の無料オープンソースユーティリティをベンダー自身が束ねて配布する

この表の最後の行が面白い。PowerToys はウインドウ配置のための FancyZones、キー再割り当てのための Keyboard Manager、一括リネームのための PowerRename、クリップボード貼り付け拡張の Advanced Paste といったものを一つの束で提供する。OS ベンダーが自ら統合ユーティリティを作った事例だ。ここで注目すべき設計が一つある。PowerToys は個々のユーティリティをそれぞれ有効化・無効化できるようになっている。まとめつつモジュールとして残した形であり、前節の交換コストと権限の問題を緩和する実際の方法がこれである。

吸収の流れは統合アプリに固有の問題を一つ作る。十の機能のうち三つが OS 標準になったとき統合アプリはその三つを外せない。個別ツールを使っていた人は三つ消せばよいが、統合アプリの利用者は重複したまま抱えていく。その三つが要求していた権限もたいていそのまま残る。

逆に吸収されない領域もある。温度やファン速度の表示、アプリを消した後に残るファイルの整理のように、OS ベンダーがあえて作る理由のないものだ。そういう場所でユーティリティは長生きする。何をまとめるか選ぶとき、この機能が吸収される側かどうかを考えてみるのは安上がりな予測である。

常駐コストを数値で測る方法

まとめれば軽くなるという言葉は検証できる形の主張だ。ところが大半は検証せずに体感で語る。体感はたいてい外れる。いま消したものが重かったと感じる偏りがあり、十個入れていた状態の記憶は正確ではない。

macOS にはアクティビティモニタがあり、ここでは二つのタブを使う。メモリタブはメモリプレッシャー、物理メモリ、使用済みメモリ、キャッシュされたファイル、使用済みスワップを見せ、使用済みメモリはさらにアプリメモリ、確保されているメモリ、圧縮に分かれる。Apple はメモリプレッシャーをメモリが処理要求をどれだけ効率的に担っているかを図で表したものと説明し、空きメモリとスワップ率、確保されているメモリ、ファイルキャッシュメモリを合わせて考慮した値だと記す。エネルギータブはアプリ別のエネルギー使用情報を四つの列で見せ、ウインドウの下に全体のエネルギー影響のグラフを置く。

読み方でよくある誤りが一つある。個々のプロセスのメモリ数値を足して合計を出すことだ。Apple 自身がプレッシャーを複数の値の合成として定義しているので、アプリメモリの合計が大きくてもメモリプレッシャーが低ければそれは問題ではない。開発ツールがメモリを多く使うことがなぜそれ自体では問題でないのかは、開発ツールはなぜメモリを食うのかで言語サーバーを例に整理した。

  • 二つの状態を比較する。統合アプリだけの10分と、個別ツールを全部入れた10分。絶対値ではなく差を見る
  • 同じ作業をする。エディタとブラウザを同じ構成で開き同じことをする。そうしないと測ったものがユーティリティではなくその日の作業になる
  • 一度のスナップショットで判断しない。常駐アプリはたいてい周期的に目覚める。その周期が観察の窓に入る必要がある
  • バッテリーはエネルギー影響で見る。残量パーセントの下がり方は画面の明るさや無線環境に大きく揺れて比較に使いにくい
  • 結論を数値で書き残す。次に同じ問いが来たとき測り直さずに済むよう、その日の値が残っている必要がある

Windows 側にも文書化された基準がある。タスクマネージャーのスタートアップアプリのタブが見せるスタートアップへの影響は CPU 時間とディスク入出力で判定され、Microsoft はその基準をこう書いている。高は起動時に CPU 1秒超またはディスク入出力3MB超、中は CPU 300ミリ秒から1000ミリ秒またはディスク300KB から3MB、低は CPU 300ミリ秒未満かつディスク300KB 未満である。こうした数値を一度見ておくと、重いという言葉がどの大きさを指すのかの感覚ができる。

ログイン項目と起動時間

常駐ユーティリティはほぼすべて自動起動を要求する。要求しなければ役に立たないからだ。だからユーティリティが増えることは、そのままログイン直後に同時に目覚めるプロセスが増えることと同じである。

macOS 13 以上ではシステム設定の一般の中にログイン項目があり、性格の違う二つのリストが入っている。一つはログイン時に開く項目で、もう一つはバックグラウンドでの実行を許可のリストだ。後者はアプリが開いていないときでもソフトウェアアップデートの確認やデータの同期といった作業をすることを許可するものだと Apple が説明する。macOS 14 以上では新しい登録フレームワークで登録された項目がこのリストに現れる。

この画面を一度は開いておく理由ははっきりしている。リストは自分が覚えているより長い。アプリを消したのに項目が残っていることもあり、インストールした記憶のない補助プロセスがあることもある。リストが長いとログイン後の最初の数十秒の間に複数のプロセスが同時にディスクと CPU を使う。

Windows は設定とタスクマネージャーの二箇所で管理する。Linux は XDG 自動起動規格に従う。ユーザー項目は ~/.config/autostart に、システム全体の項目は /etc/xdg/autostart に .desktop ファイルとして置かれる。同じ名前のファイルが複数のディレクトリにあれば優先順位の高いほうだけが使われる。Hidden=true と記されたファイルは無視されるので、システム全体の自動起動をユーザーが切る方法は同じ名前のファイルを個人のディレクトリに置くことである。OnlyShowIn と NotShowIn でデスクトップ環境別の制御もでき、この二つは一つのファイルに同時には書かない。

この点では統合アプリが明確に有利だ。ログイン項目が一つに減る。この利得は否定する理由がなく、実際に大きい。ただしこの利得を権限の和集合と一緒に天秤に載せるべきだというのがこの記事全体の論旨である。

無料・有料・サブスクリプション - 持続可能性という別の軸

小さなツールが5年後も生きているかは価格モデルと関係があるが、よく思われている方向ではない。有料が必ず長持ちするわけでも無料が必ず止まるわけでもない。軸が違うだけである。

  • 買い切り — 継続収入がない。OS のアップデートのたびにかかる対応コストを新規販売で賄う必要があり、販売が減れば対応が遅れる
  • サブスクリプション — 対応の余力ができる代わりに使わない月にも払い、決済が切れれば機能が止まる。機能を増やす理由も生まれ、小さかったツールが大きくなる傾向もある
  • 無料・オープンソース — 維持の根拠が契約ではなく開発者の時間と意志だ。代わりに止まってもソースが残り、ライセンスが許せばフォークが可能である
  • バンドル・付随サービス — 別の収益源があるのでツール自体は無料でありうる。その収益源の方向が変われば真っ先にツールが整理される

開発が止まったツールを使い続ける危険は、前に見た権限とすぐつながる。常駐ユーティリティは強い権限を持っており、脆弱性が見つかっても直されなければその権限がそのまま攻撃面として残る。個別ツール一つがそうなるのと五つの権限を持つ統合アプリがそうなるのとでは範囲が違う。

価格モデルより確実な信号は履歴のほうにある。次の五つはリポジトリや配布ページでたいてい確認できる。

  • 最近のリリース間隔 — 数か月に一度でも出ているか。最後のリリースはいつか
  • OS のメジャーアップデート対応までにかかった時間 — そのプロジェクトの実際の体力だ。発表から対応リリースまでの間隔を見る
  • issue が積もる速さと閉じる速さ — 個数より二つの速さの関係が重要である
  • メンテナが何人か — 一人ならその一人がいなくなったときの計画が書かれているか
  • ライセンスがフォークを許すか — オープンソースという言葉とフォークして維持できるという言葉はライセンス次第で違う

Windows と Linux では形が違う

ここまでの話が macOS でとりわけ鮮明に見えるのには理由がある。macOS が権限をリストで見せるからだ。何を許可したのかを画面で確認できるので、まとめることのコストも目に見える。他の OS では同じ問題が違う形をしている。

環境ユーティリティが必要とするものユーザーが統制できる地点この構造が生む結果
macOS機能別に分かれた権限を項目ごとに承認するシステム設定のプライバシーとセキュリティでアプリ単位に回収何を与えたかをリストで見られる。ただし承認が頻繁で一度に全部押してしまいやすい
Windows一般のデスクトップアプリはこの種の別途承認なしに動作するスタートアップアプリの管理と管理者権限の昇格程度何を許可したのか確認する画面自体がない。まとめることのコストが表に出ない
Linux / X11X サーバーに到達すればよいので技術的に容易だ自動起動は XDG 規格で。隔離には別途サンドボックスが要るWayland の文書が明かすとおり X11 クライアント同士には保護も隔離もない
Linux / Waylandコンポジタが提供する通路を経る必要があるコンポジタのポータル設定と権限ポリシーグローバルショートカットや画面共有のような機能が難しくなりコンポジタ別の実装に依存する

Linux 側はもう少し押さえる必要がある。Wayland の公式文書はXwayland が X11 クライアント同士を保護も隔離もしないと明記する。コンポジタがアプリごとに別の Xwayland インスタンスを立ち上げると選択しない限りそうであり、そうしない理由は多くの X11 アプリが X サーバーを介して互いに通信する必要があるからだと同じ文書が説明する。一方 X11 クライアントは Wayland クライアントからは自然に隔離されると書かれている。つまり同じ画面の中でもアプリごとに隔離の水準が違う。

だからまとめるかという問いは環境ごとに違う解け方をする。macOS では権限のリストを見て判断すればよく、リストが見えること自体が判断を容易にする。Windows では判断の根拠が画面にないので何をインストールしたかをユーザーが自分で覚えるしかなく、代わりに Microsoft が PowerToys で一次提供者が束ねて機能別に切らせる形を示した。Linux ではディスプレイサーバーの選択が答えをかなりの部分あらかじめ決める。

一つはどの環境でも同じだ。常駐するものは常駐する分の代価を払う。場所を占め、起動時間を延ばし、権限を持ち、その権限の分だけの危険を持つ。常に開いていることが何を変えるのかはターミナルが常に開いていると何が変わるのかで別の角度から扱った。

成熟度の読み方 - スター数が語らないこと

きっかけになったアプリの数字をもう一度見よう。リポジトリの作成日が2026年6月12日、2026年9月4日の照会基準でスター15,004個、フォーク527個、開いている issue 327個だ。この数字が語ることと語らないことを分けたほうがよい。

語ることははっきりしている。関心が大きく問題提起が活発だ。誰も使わないプロジェクトで issue が327個開くことはない。実際の利用者がいる証拠である。

語らないこともはっきりしている。スターは関心の指標であって安定性の指標ではない。コミュニティで紹介された直後に最も速く増え、スター数とそのアプリが次の OS アップデートを無事に越える確率の間に直接の関係はない。開いている issue の数も二通りに読める。利用者が多いからかもしれないし処理が滞っているからかもしれず、開いた数だけではどちらか分からない。見るべきは開く速さと閉じる速さの関係だ。

三か月のプロジェクトだという事実が意味することも一つある。OS のメジャーアップデートをまだ何度も経ていないということだ。強い権限を要求しシステムの動作に密着した常駐アプリにとって、その通過の履歴は他のどの数字より実質的であり、時間が経たないと生まれない情報である。

これはそのプロジェクトへの評価ではない。どんな成熟したツールも最初は三か月のプロジェクトだった。要点は、強い権限を要求するアプリを選ぶとき、時間という軸をスター数で代替できないということだけだ。そしてこの軸にはとても安上がりな対応がある。待つことだ。いま使っている個別ツールが実際に不便でないなら、アイコンが九つあるという事実自体はまだ不便ではない。

まとめ

小さなツール十個を一つにまとめると、得るものと失うものが両方とも実在する。得るものは初日に見え、失うものは事故の後に見える。この計算のすべては失う側をあらかじめ数えておくことだ。

最も大きく失うのはメモリでも場所でもなく、権限が集まる地点である。macOS はアクセシビリティを、アプリがスクリプトとシステムコマンドを実行して Mac を制御することを許可するものと書いており、Apple のセキュリティ文書はこの権限を他の保護をすり抜けうるので別途同意を得るものとして分類する。五箇所に一つずつあった権限が一箇所に五つになれば、変わるのは確率ではなく範囲だ。

判断基準は三つだ。よく使うものは専用ツールがよく、権限が強いものは分けておくほうが安全で、ないと困るものは単一障害点の中に入れない。残りはまとめてもたいてい得である。統合アプリを選ぶなら条件が一つある。機能を個別に切れるか。切れれば交換コストと権限の問題が同時に緩和され、切れなければ二つの問題が一緒に大きくなる。

最後に、ユーティリティという物の性質を覚えておくとよい。OS がまだやらない仕事を一時的に埋める物である。ウインドウ配置がそうだったしクリップボード履歴がそうだったように、いまユーティリティがやっている仕事の一部は数年後に標準機能になる。一時的に埋めるものに永続的な権限を与えていないか、それだけ一度確かめてみればよい。

確認できなかったこと

  • きっかけになったアプリの実際のメモリ・CPU・バッテリー消費は確認できなかった。この記事にその数値がない理由だ。統合がリソース面で得だという主張は各自が自分の機器で二つの状態を比較して初めて確認される
  • アクティビティモニタのエネルギータブの四つの列がそれぞれ何かは、Apple のサポート文書で名前と定義を見つけられなかった。エネルギータブがアプリ別の情報を四つの列で見せ下に全体のエネルギー影響のグラフがあるところまでを文書で確認した
  • macOS にシステムレベルのクリップボード履歴機能があるかはApple のサポート文書で該当機能を見つけられなかった。そのためクリップボードの数値は文書化されている Windows 側の値だけを引いた
  • 統合型アプリと個別ツールの間のセキュリティ事故の頻度を比較した資料は見つけられなかった。この記事の権限の議論は事故の統計ではなく権限が集まれば影響範囲が広がるという構造的な理由にのみ基づく
  • GitHub のスター・フォーク・issue の数は2026年9月4日の照会値であり、この数字とソフトウェアの品質の関係を検証した研究は確認できなかった
  • Windows で一般のデスクトップアプリがどの動作に別途のユーザー承認を求められるかの全体像は確認できなかった。本文には Microsoft が文書化したスタートアップアプリの管理とスタートアップへの影響の判定基準までを書いた
