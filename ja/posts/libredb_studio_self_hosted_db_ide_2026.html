背景 — ブラウザ型DBクライアントへの移行トレンド

企業のクラウドインフラ環境において、データベースへアクセスする従来の手法は、各開発者のPCにDBeaverやpgAdminなどのデスクトップクライアントを導入することであった。クラウドのVPC内にデータベースを構築した場合、エンジニアは外部アクセス用のポートを開放するか、個別にSSHトンネルを設定する必要があった。この運用モデルは、多数の開発者の端末内にデータベースの管理者パスワードが分散保存されるという重大なセキュリティリスクを抱えていた。

こうした運用負荷とセキュリティ上の懸念を解消する構成として、データベースが存在するプライベートネットワーク内にWebベースのSQL IDEをコンテナとして同居させるモデルが注目されている。データベースポートをパブリックインターネットに一切晒すことなく、社内イントラネット経由で安全にブラウザからデータ照会を行うアーキテクチャである。

LibreDB Studioは、「ノートPCではなく、データの隣に配置する（deploys next to your data）」という設計思想を掲げてMITライセンスで公開されたオープンソースのWeb SQL IDEである。Next.js、React 19、Monaco Editorを基盤に構築され、DockerコンテナやHelmチャートとして容易に社内インフラへ組み込むことができる。

Web型DB IDEを自社環境へホスティングするにあたり、システム管理者が確認すべき要点は3点ある。第1に、共有されるデータベースの接続情報やパスワードがどこにどのように保管されるか。第2に、読み取り専用権限を付与する際に文字列フィルタではなくデータベース側で確実に破壊的操作を遮断できるか。第3に、Claude Code等のAIエージェントと連携する際に認証情報が安全に保護されるかである。本稿では公開仕様に基づきこれらのポイントを検証する。

エンジン対応範囲と特性 — 23種類のエンジンと構文制約

公式READMEの記述によると、LibreDB Studioは単一の統合インターフェースで計23種類のデータベースおよびデータ処理エンジンをサポートしている。紹介記事等で見られる「18個のドライバで46エンジンに対応」という表現は、内部の18個のドライバモジュールを通じてMariaDBやYugabyteDBなどの派生ディストリビューションを含む数値であり、公式仕様で定義された基本エンジン群は23種である。

対応エンジンはリレーショナルDBからNoSQL、時系列、メッセージキュー、グラフ、ベクトルDBまで多岐にわたる。主要な分類は以下の通りである。

  • リレーショナルおよび分析用SQL： PostgreSQL（pg）、MySQL（mysql2）、Oracle（oracledb Thinモード）、Db2 LUW（Rust製DRDAクライアントdb2-node）、SQL Server（mssql）、SQLite（組み込み）、libSQL（Hrana HTTP）、DuckDB（@duckdb/node-api）、ClickHouse（HTTP SQL）、Trino（HTTPクライアント）。
  • ドキュメントおよびインメモリNoSQL： MongoDB（公式ドライバ）、Couchbase（HTTP Query/REST）、Redis。
  • 検索および分析ストレージ： Apache Druid（HTTP SQL）、Elasticsearch（HTTP _sql）、OpenSearch（HTTP _plugins/_sql）、Apache Cassandra（cassandra-driver）。
  • 時系列およびストリーミング： Prometheus（HTTP PromQL）、Apache Kafka（@platformatic/kafka）。
  • 分散制御・グラフ・ベクトル： etcd（gRPC）、Neo4j（neo4j-driver-lite Bolt）、Milvus（gRPC REST v2）、Qdrant（HTTP REST）。

エンジンの文法仕様に合わせた制限も設けられている。Druid、Elasticsearch、OpenSearchの3エンジンは構文自体にUPDATEやCREATE TABLEが存在しないため、自動的に読み取り専用として認識され変更操作が無効化される。

また分散クエリエンジンのTrinoは下位ストレージへのアダプタとして機能するため主キーやインデックスを保持しない。そのためER図機能ではリレーション線（edge）が表示されず、インライン編集も無効となる。Cassandraではパーティション推計値しか取得できないため、不正確な行数表示を避けるためにあえて行数表示を省略する設計が採られている。

認証情報保管とセッション分離 — クライアント保存からの脱却

簡易的なWebデータベースツールでは、接続設定やパスワードをブラウザのlocalStorageに保存する構成が見られる。しかしこの方法はXSS攻撃による漏洩リスクが高く、社員の異動や退職時に接続権限を一元剥奪することが困難である。

LibreDB Studioは、接続プロファイルやクエリ履歴をブラウザではなくバックエンドのサーバストレージに集約して管理する。バックエンドは環境変数STORAGE_PROVIDERで切り替えられる。

  • SQLiteストレージ（STORAGE_PROVIDER=sqlite）： コンテナ内のローカルSQLiteファイルに全メタデータを保管する。単一構成で追加DBを必要とせず即座に運用できる。
  • PostgreSQLストレージ（STORAGE_PROVIDER=postgres）： 外部のPostgreSQLデータベースにメタデータを保管する。複数コンテナによる冗長化や水平展開に適している。
  • 事前構成接続（Seed Connections）： 管理者が構成ファイル等で組織共通の接続設定をあらかじめ定義できる。ユーザはログインするだけでパスワードを入力することなく対象DBを利用できる。
  • クライアント側マスキングの限界： 画面上の個人情報やカード番号を伏字にするマスキング機能が用意されているが、これは画面共有用のUIレイヤ処理であり、APIのレスポンスには平文データが含まれる点に注意が必要である。

ロールベースのアクセス制御（RBAC）により、一般ユーザが管理者の登録した共有接続の接続文字列やパスワードを閲覧・変更することは禁止されている。

読み取り専用強制機構 — パーサフィルタではなくDBネイティブ制御

SQLクライアントにおいて「読み取り専用」を実現する際、正規表現でDELETEやUPDATEの単語を検出してブロックする手法は非常に脆い。コメントの挿入やCTE、ストアドプロシージャの呼び出しによって簡単にすり抜けが発生するためである。

LibreDB Studioは文字列パーサによる検知を排し、各データベースエンジン自身が備えるネイティブなトランザクション制御やセッションフラグを利用して読み取り専用を物理的に強制する（src/lib/db/operations/execution.ts）。

  • PostgreSQL（postgres.ts）： トランザクション開始時にエンジンレベルでREAD ONLYを宣言する。書き込みを伴ういかなる操作もPostgreSQL本体によって拒否される。
  • SQLite（sqlite.ts）： 実行ごとにPRAGMA query_only = ONを適用し、データベースファイルへの変更をOSレベルで防止する。
  • DuckDB（duckdb/index.ts）： ドライバの初期化時にREAD_ONLYハンドルを指定し、ファイル出力関数をブロックするSQLガードを併用する。
  • SQL Server（mssql.ts）： 読み取り専用トランザクション構文が存在しないため、プリンシパルの権限確認、オプティマイザによる実行なしコンパイル、サーバ側行数制限、そして常時ロールバックされるトランザクションを組み合わせた多重防御を行う。
  • 非SQLエンジン（Prometheus、Kafka等）： Prometheusは書き込みAPIを呼ばない経路のみを使用し、Kafkaはコンシューマ読み出しのみに限定し、Neo4jはBoltのREADセッション上でCypherを実行する。

内蔵のAIエージェント機能を利用する場合も、これらのネイティブ読み取り専用パイプライン（queryReadOnly）が実装されている4エンジン（PostgreSQL、SQLite、DuckDB、SQL Server）のみに実行が限定される。

AIエージェントとMCP連携 — 認証情報の隔離とトークン検証

LibreDB Studioはバージョン0.17.0よりModel Context Protocol（MCP）サーバを標準搭載した。Claude CodeやCursorといった外部のAI開発環境から、安全に社内データベースのスキーマやデータを参照できるよう設計されている。

AIエージェント連携における最重要要件は、AIモデルに対してデータベースのホスト名、ポート、ユーザー名、パスワードを直接渡さないことである。

外部クライアントは/api/mcpエンドポイント経由で通信を行う。この機能はデフォルトで無効化されており、有効化時も有効なBearerトークンがないアクセスには401 Unauthorizedが返される。

認証されたエージェントは、管理者が明示的に許可した接続プロファイルに対してのみスキーマ取得や読み取り専用クエリを実行できる。クエリはすべて前述のネイティブReadOnly制御と行数制限（200行）、実行時間制限（360〜900秒）の下で処理され、生のDB認証情報はサーバ内に保持される。

認証モードとアクセス制御 — OIDC SSOとPKCE保護

組織全体で共有IDEを運用するためには、既存のアイデンティティ基盤との統合が不可欠である。LibreDB Studioはオープンソース版であっても追加費用なしでOIDC SSOをサポートしている。

  • デュアル認証モード： ローカル認証とOpenID Connect（OIDC）SSOを環境変数で選択可能。
  • 汎用的なIdP対応： Keycloak、Auth0、Okta、Microsoft Entra ID（Azure AD）、Google等の標準OIDC IdPに対応。
  • PKCEによるセキュリティ： 認可コード横取り攻撃を防ぐため、S256チャレンジを用いたPKCE対応の認可コードフローを適用。
  • クレームに基づくロールマッピング： JWT内のグループ情報（例：realm_access.roles）を参照し、社内ロールに応じて管理者または一般ユーザ権限を自動割り当て。
  • Passkey対応： パスワードを使わずにFIDO2/WebAuthn規格のパスキーで安全にログイン可能。

なお、ローカルIPアドレス（http://192.168.x.x:3000等）で非HTTPS接続を行う場合、Cookie保護機能によりセッションが維持できずログイン画面に戻る事象が発生する。この場合は環境変数AUTH_COOKIE_SECURE=falseを明示的に指定する必要がある。

導入はDockerコマンド1行で実行できる。初回起動時には自動生成された管理者パスワードがログに出力される。

Node.js 24以上が導入されている環境では、npxコマンドによる起動もサポートされている。

npx @libredb/studio

従来のデスクトップクライアントとの構造比較

DBeaver等のデスクトップツールや他のWebツールと比較した際、LibreDB Studioには3つの明確な利点がある。

第1に、認証情報の一元管理である。デスクトップ製品では各社員のPCに接続パスワードが分散保存されるが、LibreDB Studioでは中央サーバで一括管理されるため、パスワード更新作業が1回で完了し、退職者のアクセスも瞬時に遮断できる。

第2に、ネットワーク境界の防衛である。デスクトップツールでは個々の端末からVPC内部へのVPNやSSHトンネルが必要となるが、LibreDB StudioをVPC内に同居させることで、DBとの通信は高速なローカルネットワーク内で完結し、外部へはHTTPSポートのみを公開すれば済む。

第3に、組織的な監査証跡（Audit Trail）の確保である。デスクトップツールでは履歴がローカルにしか残らないが、LibreDB Studioは全ユーザの実行クエリ、所要時間、実行者を一元記録し、CSVやJSONでエクスポートできる監査機能を無償で提供している。

確認できなかったこと

  • サーバ側ストレージ（SQLite/PostgreSQL）に保存される接続パスワードの暗号化方式（AES-256-GCM等のアルゴリズム）および鍵管理仕様の詳細。
  • 公式紹介文に記載された「18ドライバ・46エンジン」のうち、基本23エンジン以外の派生エンジンに関する網羅的な動作確認リスト。
  • 大規模エンタープライズ環境で多数のユーザが同時利用した際のコネクションプール負荷上限およびベンチマーク結果。
  • Db2ドライバで報告されている非ASCII文字および64ビット整数の扱いに関する修正スケジュール。
  • 組織ごとに完全に接続設定を分離するマルチテナント分離機能の対応有無。
