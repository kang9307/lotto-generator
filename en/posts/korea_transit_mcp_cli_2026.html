A Korea Transit Route & Fare MCP Server for AI Agents — When an Agent Finds the Way

What the open-source project naeryeo reveals about MCP's real value - handing subway and bus data to AI agents

Jul 3, 2026 Dev & Infra

Introduction: Why a small project like this deserves attention

In early July 2026, developer GyeongHoKim published an open-source project called naeryeo on GitHub. Named after a colloquial Korean phrase that roughly means "hop off here," the tool is a command-line (CLI) utility for looking up South Korean subway and bus routes and their estimated fares - and, at the same time, an MCP (Model Context Protocol) server. It was also featured in the Show GN section of GeekNews (news.hada.io), picking up 12 points: modest in scale, but a steady trickle of attention.

By star count or buzz alone, this is not a large project. I'm writing about it anyway for a specific reason: naeryeo shows, in a small and concrete way, what MCP actually changes. It isn't an official MCP server from a giant platform - it's a tool one developer built to solve their own annoyance (having to hand-calculate commute distance and cost when applying for youth housing subsidies), and it shows how that kind of tool can slot into the AI agent ecosystem as a genuine piece. This piece goes beyond introducing naeryeo to analyze, from my own vantage point, why the MCP protocol is spreading as fast as it is right now, and why a tool like this is specifically needed given Korea's particular transit-data landscape.

1. What is naeryeo?

1.1 What the tool actually does

naeryeo answers questions like "How do I get from Gangnam Station to Hongik University Station?" with the optimal route, transfer details, travel time, and estimated fare. As a CLI, it's a single line: naeryeo route --from "Gangnam Station" --to "Hongik Univ. Station". Registered as an MCP server, the same question can be asked in natural language from an AI client such as Claude Desktop or Claude Code. The core logic is written in Go (roughly two-thirds of the codebase), with shell scripts handling distribution and a JavaScript wrapper for the npm package. What matters architecturally is that both the CLI and MCP modes share the same internal logic (internal/core) - only the interface differs; there is one route-search engine underneath.

1.2 The API combination - ODsay + Kakao geocoding

naeryeo doesn't collect transit data itself. Instead it combines two existing commercial APIs: ODsay, a dedicated transit-routing API, handles route search, while the Kakao Local API handles geocoding - converting a building name or address (rather than a station name like "Gangnam Station") into coordinates. The project's README explains this choice by noting that Kakao Map and Naver Map don't expose transit route-search APIs to third-party developers, and that Google Maps is difficult to use for this purpose domestically due to regulation. The latter point ties into South Korea's long-standing policy of restricting the export of detailed mapping data abroad on national-security grounds - a policy that has, for years, been widely known to weaken Google Maps' domestic transit-directions feature relative to other countries. naeryeo fills that gap not by tapping the raw arrival-time feeds on Korea's public data portal, but by building on ODsay, a commercial layer that already does the route-search processing.

1.3 Two integration paths - Skills and MCP

naeryeo supports both Claude Skills (the recently established SKILL.md format, installed via npx skills add) and a standalone MCP server. Skills load into context only when needed, saving tokens; MCP is a stdio-based tool server that stays connected. Setup is a few lines added to claude_desktop_config.json: {"mcpServers": {"naeryeo": {"command": "naeryeo", "args": ["mcp"]}}}. The API key is registered once via naeryeo setup and stored encrypted in the OS's native keychain (Keychain, Credential Manager, or Secret Service) - it's never exposed in plaintext in the config file or in MCP traffic.

2. Why MCP is useful - connecting LLMs to real-time tools

2.1 The problem before MCP - the M-by-N integration mess

Large language models are inherently blind to information from after their training cutoff, and to private or real-time data that was never in their training set to begin with. How many minutes the subway takes from Gangnam Station to Hongik University Station today, and what it costs, simply isn't baked into the model's weights. Solving this requires giving the model a way to "call" external systems - and before MCP, that meant writing separate integration code for every AI application (host) and every service it wanted to connect to. With N services and M AI applications, that's, in principle, M-times-N custom integrations.

2.2 After MCP - a standard connector

MCP, which Anthropic introduced in November 2024, cuts that down to M-plus-N. A service provider wraps its capability in an MCP server exactly once; an AI application implements an MCP client exactly once and can then talk to any service that provides one. It's often compared to "USB-C for AI applications," and the analogy holds up - just as devices moved from a mess of proprietary charging ports to a single standard, MCP replaces a landscape of bespoke plugin APIs with a standard protocol (a host-client-server architecture built on three primitives: tools, resources, and prompts). naeryeo follows this structure to the letter: it wraps a single tool - route search - as an MCP server, and any MCP-compatible client, Claude Desktop or otherwise, can use it immediately without writing custom integration code.

2.3 What the pace of adoption tells us

Industry coverage suggests that, as of the first half of 2026, MCP has become a de facto standard supported not just by Anthropic but by most major AI vendors, including OpenAI, Google, Microsoft, and AWS, and that major services such as GitHub, Slack, Notion, and PostgreSQL offer official MCP servers. Specific figures for downloads or GitHub stars vary by source and measurement date, so I'd be cautious about citing an exact number - but the direction is unmistakable: multiple vendors converging on one protocol is a rare consensus in the AI tooling world.

3. What becomes possible when an agent can handle transit data

3.1 Finishing trip planning in one conversation

In a world without MCP, a chatbot asked "How long does it take from Gangnam Station to Hongdae?" could only offer a generic summary, or admit it didn't know. Once naeryeo is wired up over MCP, an agent calls the real ODsay routing data and returns exact travel time, transfers, and fare - and can then follow up on a multi-step request like "plan the shortest route to visit these three places in a day," repeatedly calling the routing tool for each leg and stitching the results together itself. That's not simple information lookup; it's agentic behavior - planning and executing multiple tool calls within a single conversational thread.

3.2 Cost optimization and a real-world use case

The real-world use case naeryeo's own materials cite is striking: using AI to calculate commute distance and cost when applying for youth housing subsidies. Several of Korea's housing-support programs for young people and newlyweds treat distance to one's workplace, or commuting cost, as a review criterion or supporting reference. Instead of looking this up by hand for every candidate listing, a user can ask an agent, "Of these five listings, which has the lowest public-transit cost to my office?" and get a direct comparison. This scenario is arguably more distinctly Korean and more practical than trip planning, and it's worth noting because it shows MCP tools being used for decision support, not just information retrieval.

3.3 The potential for combining with other tools

MCP's real power shows up not with a single server, but when multiple servers connect at once. Pair a calendar MCP server with naeryeo and you can ask, in one shot, "What time do I need to leave to make my 3pm meeting next Tuesday without being late?" Add a maps or weather server and you can get an answer that accounts for a rain-day alternate route. That's not a value naeryeo creates on its own - it's the multiplier effect that emerges as the MCP ecosystem grows and individual servers combine.

4. The value of a local, open-source tool

4.1 Movement data is sensitive

Where you're going, and where you're coming from, sits on the more sensitive end of location data. naeryeo runs locally over stdio, and states that its API key lives only in the OS keychain and is never sent to an intermediary server. In practice, that means a query like "how do I get from the office to the hospital today" never routes through naeryeo's own developer's servers or a third-party SaaS backend - it goes straight from the user's machine to the ODsay and Kakao APIs (requests still reach those two APIs themselves, but at minimum there's no separate data-collection layer sitting in between).

4.2 Cost and control

Code released under the MIT license can be audited by anyone, and forked and modified to fit specific needs if necessary. Rather than subscribing to a commercial SaaS "AI travel assistant," a single free ODsay API key lets you run the same functionality locally, indefinitely - a genuinely practical advantage. That freedom isn't free, though: you still have to go through developer-friendly steps - installing a binary, obtaining an API key, editing a config file - and it's not yet something a non-developer could use with one click.

5. What the spread of MCP reveals - the power of the long tail

Most articles about MCP reach for official servers from giant services like GitHub, Slack, or Salesforce as examples. In my view, though, the protocol's real strength shows up less in those flagship cases and more in how easily a narrow server built by one developer, specialized to one country's data, like naeryeo, can come into existence and get distributed. Without MCP, a project like this would likely have stayed "just a CLI tool." Thanks to the standard protocol, that same CLI was promoted to an AI agent's tool with essentially no extra work. As more of these long-tail servers accumulate by region, language, and industry, the MCP ecosystem stops being defined by a handful of official Big Tech integrations and puts down roots in the real data of individual countries and domains. The fact that this has already happened in a niche as narrow as Korean public transit is reasonable evidence that similar projects will keep appearing for other countries' and other domains' public data.

6. Limitations and caveats

It's important not to overstate this. There are several clear limitations. First, naeryeo depends on the commercial ODsay API, so it's exposed to free-tier rate limits or pricing changes outside its own control. Second, a local, stdio-based MCP server currently works out of the box only in desktop clients like Claude Desktop and Claude Code; using it from a mobile app or web chatbot would require a separate remote deployment (an HTTP-based MCP server, for instance). Third, installation and setup still require obtaining an API key and editing a JSON config file, so accessibility for non-developers remains low. Fourth, the accuracy of route and fare calculations ultimately depends on ODsay's own data refresh cycle (reportedly twice a month), so real-time precision isn't perfect. These are less a problem specific to naeryeo than an indicator of how mature the broader MCP ecosystem is at this point in time.

Conclusion: The big trend a small tool reveals

naeryeo itself is not a large project with hundreds of stars. But the pattern it demonstrates - thinly wrapping an existing commercial API in an MCP interface, and thereby promoting a CLI tool into a tool an AI agent can use - looks like a template likely to repeat across the AI ecosystem in the second half of 2026. For developers, it's a signal that adding a single MCP server on top of an existing API can reach a new user base: people who use AI agents. For everyday users, it's evidence of a shift where even looking up a transit route can be finished in one line of conversation. My own expectation is that this kind of narrow, practical MCP server will keep spreading into other pockets of Korean public data - real-estate transaction prices, weather, administrative records, and more. As of July 2026, this is still mostly a developer-centric, experimental stage - but as installation friction keeps dropping, for example as one-click installs become the norm, tools like this will move a lot closer to ordinary users.
