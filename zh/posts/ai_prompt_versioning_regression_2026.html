把提示词当代码来管理 - 版本管理与回归测试

改了一行，另一个用例就坏了 - 线上提示词的变更、验证与回滚设计

2026年7月27日 开发/基础设施

引言：提示词被当作配置，而不是代码

讲提示词怎么写的文章已经泛滥：给角色、加示例、写清输出格式。可是这些提示词进入生产之后的故事，几乎没人讲。三个月前是谁、为什么加了那句话，没人记得；上周改了一行，看似毫不相干的用例输出变了；厂商升级了模型，同一条提示词行为就变了。本文谈的正是这个阶段。

问题的根源很简单：提示词没有被当作代码，而是被当作配置。配置项通常没有测试。有人在后台悄悄改一下也不会有事，改的人也不认为那是一次发布。可提示词和配置项的性质完全不同。把超时从30秒改成60秒，影响范围可以预估；而在提示词里加一句表格最多保持三行，这条指令会连带改变与表格毫无关系的请求的长度、语气和格式。

也就是说，提示词的改动不是局部的。在代码里改一个函数，受影响的只有调用它的路径；在提示词里，你加的那句话会和每一条输入一起被读到。正因为这个性质，提示词需要的不是「更好的存放位置」，而是「观测变更副作用的装置」。这个装置的名字早就有了：回归测试。

但提示词的回归测试没法照搬软件那一套，因为同样的输入不会产出同样的输出。所以本文把三条线索放在一起讲：①如何为提示词这个产物本身留下历史，②如何为非确定性输出设定通过与否的标准，③模型变化时要重新测什么。至于产物生成之后的审校工序 — 语法、运行时、语义三层检查，误报管理，黄金文件 — 不属于本文范围，已在搭建AI产出物审校体系中另行讨论。这里的对象是生成产物的那份指令本身。

1. 提示词脱离管理的三条路径

即便嘴上说「我们把提示词放在仓库里」，实际上历史断掉的情况也很常见。断法大致有三种。

  • 以字符串硬编码在代码里 — 形式上受版本管理，但提交信息只有一句优化提示词，改了什么、为什么改都没留下。想回退时也不知道该回到哪个提交。
  • 在管理后台里编辑 — 非研发同事可以直接改，很方便，但这类编辑不走发布流程：没有评审、没有测试、没有生效时间记录。它与生产环境中的未授权改动在结构上无法区分。
  • 由多个片段拼装而成 — 系统提示词、工具定义、检索结果模板、用户消息模板分散在不同地方。单个片段有历史，可是「那天实际发给模型的完整字符串」的历史哪里都没有。出了事故也无法复现。

第三种最危险。片段各自带版本时，组合数是乘法增长的，而出问题的偏偏是某个特定组合。因此提示词版本管理的单位不应是片段，而应是「渲染后的最终提示词」。片段是源码，最终提示词是构建产物。不记录构建产物的哈希，就无法确定你到底运行了什么。

给一个判断标准。如果无法在30秒内回答「昨天下午3点那次请求收到的提示词全文现在能重建出来吗」，那么这个团队就没有提示词版本管理。文件放在哪里是次要问题。

2. 提示词的改动不是局部的

只要理解回归为何如此频繁，后面的设计就都能推导出来。提示词产生回归的路径可归为四条。

2.1 指令不挑用例

线上常见的一幕：客户A投诉「回复太长」，于是在提示词里加上回答不超过三句话。下一周客户B投诉「说明变得单薄」。B的请求本来就属于该长篇作答的那一类，可新指令和所有请求一起被读到了。这不是模型的缺陷。提示词里没有条件，于是被无条件地应用，这才是正常行为。

2.2 示例比显式指令更强势

附上几个示例来固定格式很有效，但示例还会把正文没说的东西一并教给模型。三个示例都用敬语，语气就被固定；都很短，长度就被固定；都来自同一行业，行业词汇就会渗出来。替换一个示例比改一行指令更危险，原因就在这里。

2.3 顺序与位置会改变结果

同样的内容放在前面还是后面，被采纳的强度并不相同。这个性质属于提示词设计的总体议题，已在上下文工程中详述；从版本管理角度看，重要的推论只有一句：「只是把句子挪了位置」的改动同样是行为改动。在差异视图里它看起来只是移动，很容易通过评审，但结果可能不同。

2.4 提示词之外的东西变了，效果等同于提示词变了

模型快照、工具定义、检索结果的分块大小、输出模式 — 其中任何一项变化都会改变最终行为。可它们通常不会被记入提示词的变更历史。「提示词没动，结果却变了」的报告里，相当一部分属于这一类。所以提示词版本要捆绑的不只是提示词正文，而是它运行时所处的整个环境。

3. 该记录什么 - 提示词元数据

把上一节的结论直接落成一份模式即可。核心原则是「仅凭这份记录能否复现当时那次运行」，复现用不上的字段就不要放。

# prompts/support_reply/v0007.yaml
id: support_reply            # 逻辑名称，不会变
version: 7                   # 单调递增。不用语义化版本的原因见下
content_hash: 9f2c1ab4       # 归一化后的哈希；相同即视为同一次运行
created_at: 2026-07-27T10:12:00+09:00
author: platform-team
status: active               # draft | canary | active | rolled_back | retired

# 运行环境 - 少了这块就无法复现
runtime:
  model: vendor-model-2026-05-14   # 写快照标识，不要写别名
  params: { max_tokens: 1024 }     # 采样参数各厂商支持情况不同
  tools_version: 3                 # 工具定义也是提示词的一部分
  output_schema: reply_v2          # 与下游解析器之间的契约

# 拼装信息 - 最终字符串是怎么构成的
compose:
  parts: [system_base@12, policy_zh@4, fewshot_support@6]
  cache_boundary_after: policy_zh  # 缓存前缀边界（见第9节）

# 变更信息 - 用于评审与回滚判断
change:
  type: add_constraint       # 第4节的变更类型
  risk: high                 # 由类型自动决定，不允许人工调低
  reason: "长回复投诉（工单 #4821）"
  reverts: null

# 验证记录 - 没有这些数字就无法做回滚判断
eval:
  suite: support_v5          # 评测集同样有版本
  runs_per_case: 5
  hard_gate: pass
  pass_rate: 0.94            # 基于180条用例
  baseline_version: 6
  delta: +0.01               # 落在置信区间内就不要称之为改善
  judge: rubric_checklist_v2 # 评判方式也纳入版本管理（见第7节）

其中若干选择是有理由的。

  • 用单调递增整数而非语义化版本 — 语义化版本要求人来判断「是否破坏了向后兼容」。提示词改一行就可能破坏兼容，这个判断根本做不出来。所以编号只表示先后顺序，影响范围由change.risk单独表示。
  • 模型写快照标识而非别名 — 别名会随厂商指向的变化而悄悄跟着走。要留下可复现的记录，就得写下当天实际被调用的那个快照字符串。
  • 把评测结果一并写进提示词元数据 — 只放在另外的看板上，回滚时就不会有人去看。打开要回退到的那个版本的文件时，它的成绩就应该在眼前。
  • 评判方式（judge）也要记录 — 评判标准一变，就无法与过去的分数比较。第7节展开。
  • 在status中保留rolled_back — 删掉回退过的版本，就等于抹去「这个方向已经失败过」的信息，几个月后又会重复同样的尝试。

4. 按变更类型划分风险等级

每改一次提示词都跑全量评测集，结果是没人愿意改提示词；反过来全部放行，回归就会累积。务实的做法是按变更类型预先规定验证强度。下表是这种映射的起点。

变更类型示例影响半径缓存影响风险等级最低验证
文字订正错别字、标点理论上没有（词元边界会变）位置靠前则整体失效低硬性门槛 + 10条冒烟用例
句子挪位同样内容移到后面中 — 采纳强度改变移动点之后失效中全量评测集跑一次
新增约束类似「不超过三句」的禁止或限制广 — 会应用到无关用例中高全量 + 反向用例
新增或替换示例改动一个少样本示例广 — 语气、长度、词汇一起移动大（篇幅大）高全量 + 反向用例
输出模式变更新增或改名字段波及下游解析器中很高全量 + 集成测试 + 兼容性确认
工具定义变更参数说明改一行整体工具选择行为最大 — 其后各层全部失效很高全量 + 工具调用用例
更换模型快照版本升级全部全部很高基线重测 + 并行运行（第8节）
采样参数变更调整温度或核采样波动幅度改变一般没有中重新测量重复运行的通过率

这张表里最值钱的一格，是「新增约束」最低验证栏里的反向用例。加入新指令时，必须同时补上一条该指令不应生效的用例。否则评测集永远只在确认「指令生效了」，而副作用要等线上由客户来发现。把这一条称为提示词回归测试的核心并不夸张。

风险等级不能让改动者自己申报。越急的时候写得越低。更现实的做法是：选定变更类型即自动确定风险等级，若要调低则需另行审批。

5. 评测集 - 用例从哪里来，要多少条

提示词回归测试的实体是评测集。可是「要建评测集」的说法很常见，用例从哪里获取却少有人答。实际可用的来源有五条。

来源能得到什么注意事项建议占比
线上日志抽样真实输入分布需去除个人信息；可能混入注入尝试40%左右
故障与投诉工单已经炸过一次的用例偏向失败一侧，通过率会显得偏低20%左右
反向用例新指令的副作用写起来麻烦，最先被漏掉20%左右
手工构造的边界用例空输入、超长文本、相互矛盾的指令、多语言混排放入不现实的用例只会扭曲通过率15%左右
合成变体补充规模会原样放大原始数据的偏差5%左右

占比不是绝对值，而是起点。真正重要的是占比这件事本身处于被管理的状态。不加管理，评测集会随时间被「过去坏过的东西」填满，越来越不像真实流量。

5.1 评测集不是设计出来的，是长出来的

一上来就想做一份完备的评测集，多半会失败。只要守住两条规则，评测集会自己长大。

  • 一次事故 = 一条用例。线上报了问题，先把那条输入加进评测集，再去修。等修完再加，就永远不会加了。
  • 一行指令 = 一条反向用例。每加一条约束，就同时加入一条该约束不应生效的输入。

用例文件最好以不绑定任何工具的形式存放。一行一条用例的文本格式，用什么都能读。

// eval/support_v5.jsonl  - 一行一条用例
{"id":"c101","kind":"positive","input":"退款什么时候到账？",
 "must":["退款","工作日"],"must_not":["账号"],"max_chars":400}

{"id":"c102","kind":"counter","input":"请结合依据解释合同第3条的含义",
 "note":"长回答才是正确的用例 - 三句限制若在此生效即为回归",
 "min_chars":600,"must":["第3条"]}

{"id":"c103","kind":"boundary","input":"",
 "note":"空输入","must":["重新输入"],"must_not":["错误代码"]}

{"id":"c104","kind":"schema","input":"告诉我3笔订单的状态",
 "expect_json":true,"required_fields":["orders","count"]}

建议把kind为counter的用例条数作为一个指标来管理。反向用例占比趋近于0的评测集抓不住回归。

5.2 要多少条 - 条数由你想要的精度决定

「评测集多少条合适」没有普适答案。反过来问就有答案了：你想区分多大的差异？估计通过率时95%置信区间的半宽大约是1.96 × √(p(1−p)/n)，在通过率0.9附近计算结果如下。

评测集规模 n通过率0.9的95%区间半宽可区分的差异适用场景
20约 ±13.1个百分点只能发现大面积损坏冒烟检查
30约 ±10.7个百分点只能发现大面积损坏改动后的快速确认
50约 ±8.3个百分点10个百分点以上日常回归测试
100约 ±5.9个百分点6个百分点以上审批门槛
300约 ±3.4个百分点3个百分点以上模型更换决策
500约 ±2.6个百分点2个百分点以上大规模迁移

这张表怎么读很简单：用100条评测集说「提升了2个百分点」在统计上没有依据。看似改善的数值可能是噪声，反过来真实的劣化也会被噪声淹没。这正是第4节把模型更换定为「很高」的原因 — 那个决策需要更大的评测集。

两点提醒。其一，上面的近似式在通过率非常接近1时不准确，那个区间宜改用其他区间估计法。其二，这个计算回答的是「要看多少条用例」，而「用抽样发现总体中稀有缺陷的概率」是另一个计算。后者已在产出物审校篇中列成表格，可参阅那一篇。

厂商文档给出的示例规模也可作参考。Anthropic关于编写评估的指南按任务性质给出了从几十组到上千条的示例，并明确了「可自动评分的大量题目优于少量人工评分的题目」这一取向。不过这是厂商自身文档的建议，会随任务与风险程度而变化。

6. 如何为非确定性输出设定通过标准

这里就是提示词回归测试与软件回归测试分道扬镳之处：同样的输入不会产出同样的输出。

6.1 温度0并不保证可复现

常见的误解是「把温度设为0就是确定性的」。实际并非如此。Thinking Machines Lab公开的技术文章报告，同一条提示词在温度0下运行1,000次产生了80种不同的完成文本，出现最多的那种为78次，最早的分歧发生在第103个词元。该文的核心主张是：原因既不是GPU并发也不是随机性，而是算子缺乏批次不变性。服务器同时处理的请求数不同，归约运算的计算顺序就不同，而浮点加法不满足结合律，末位比特因此发生漂移；这点微小差异在某一刻会翻转词元的选择。同一篇文章还补充说，改用批次不变算子后1,000次运行全部一致。需要注意的是，这是研究实验室的技术博客而非同行评审论文。

实务上的推论有两点。第一，非确定性是可控的性质，但控制权通常不在我们手里 — 使用托管API的团队无法左右服务端的批处理状况。第二，因此以可复现为前提的测试设计从一开始就不成立。

而且温度这个参数本身也不是永久的。Anthropic的文档把temperature、核采样与top-k参数标注为：在Claude Opus 4.7及之后的模型上设为非默认值会返回400错误，并建议改用提示词来引导行为。这意味着「把温度固定为0以确保可复现」这一策略，仅凭厂商的参数策略变化就可能消失。

6.2 把标准建立在分布上，而不是某一次输出上

因此判定针对的是同一条用例运行k次之后的结果分布。不同项目性质不同，标准的形式也应当不同。

判定对象标准形式重复次数 k示例失败时
格式契约硬性门槛（k次全通过）3~5JSON可解析、必填字段存在立即判不通过
禁止事项硬性门槛（k次全通过）5以上禁用词、个人信息泄露、绝对化表述立即判不通过
事实一致性通过率阈值3~5抽取字段一致率不低于0.95拆解原因后判断
主观质量与基线版本相对比较3以上是否不比上一版差列入观察
成本与延迟预算上限汇总全部运行平均词元数、p95延迟暂缓发布

设计上有三点想强调。

  • 相对比较比绝对打分更稳定。「这个回答五分制打4分」会随评判者与时间点而波动，而「基线版本与新版本哪个更好」相对不易波动。回归测试要问的本来就不是「变好了吗」，而是「有没有变差」。
  • 不要把硬性门槛和质量指标混在一起。把禁用词泄露按通过率0.98来管理，等于说一百次里出两次可以接受。格式与安全项必须是全部通过，而不是设阈值。
  • k越大，波动的代价越大。假设每条用例有1%的概率偶然失败，那么100条用例的评测集至少失败一次的概率约为63%（1 − 0.99100）。要把波动降到0.1%，这个值才会降到约10%。也就是说，会抖动的测试一定会被忽视。抖动的用例应改为通过率阈值或收窄判定标准，放着不管会毁掉整个评测集的可信度。
// 不依赖任何框架的最小判定逻辑
async function judgeCase(runModel, testCase, k = 5) {
  const outputs = [];
  for (let i = 0; i < k; i++) outputs.push(await runModel(testCase.input));

  // 1) 硬性门槛 - 违反一次即结束
  for (const out of outputs) {
    if (testCase.expect_json && !tryParse(out)) return fail('schema');
    for (const bad of testCase.must_not || []) {
      if (out.includes(bad)) return fail('forbidden:' + bad);
    }
  }

  // 2) 通过率标准 - 允许波动的项目
  const softPass = outputs.filter(out =>
    (testCase.must || []).every(t => out.includes(t)) &&
    (!testCase.max_chars || out.length <= testCase.max_chars) &&
    (!testCase.min_chars || out.length >= testCase.min_chars)
  ).length;

  return { id: testCase.id, hard: 'pass', rate: softPass / k, k };
}

这段代码不绑定任何具体工具，这一点很重要。只要替换runModel，无论换厂商还是换评测工具，判定逻辑都留在我们自己手里。第11节会再谈这件事。

7. 评判者同样是版本管理对象

把质量判定交给大模型的做法很普遍，但用在回归测试里有特有的陷阱。回归测试本质上是把两个版本的输出并排比较，而并排比较恰恰是评判者偏差表现最强烈的场景。

  • 位置偏差 — 指在提示词中先展示哪一个会改变选择的现象。一项研究考察了15种评判者，覆盖两个基准的22项任务，生成超过15万条评估实例，用重复稳定性、位置一致性与偏好公平性三个指标来度量该偏差，结论是它并非偶然而是系统性的，且随评判者与任务差异很大。同一研究还报告，该偏差受提示词各组成部分长度的影响较弱，而受两个候选之间质量差距的影响很强。也就是说，版本之间的差异越细微，顺序效应越大 — 而回归测试中比较的两个版本几乎总是细微不同。
  • 自我偏好偏差 — 指评判者对自己同源的输出打分偏高。有研究认为这种偏差的本质并非「因为是自己写的」，而在于对低困惑度、即自己熟悉的文风给出比人类更宽松的评价。这意味着在模型升级验证中，若用新旧模型之一充当评判者，结果可能偏向一方。
  • 评判者漂移 — 在实务中比前两者更容易酿成事故。用于评判的模型一变，过去的分数与新分数就无法比较。提示词没动而通过率掉了3个百分点时，你无法区分这是提示词回归还是换了评判者所致。

从本文的视角看，结论收敛为一句话：评判者不是评测基础设施，而是版本管理对象。这正是第3节的模式里放入judge字段的理由。作为实务规则，下面这些比较稳妥。

  • 固定评判模型与评判提示词，更换时整体重测基线。更换评判者属于第4节表格中的「很高」一档。
  • 比较型判定要调换顺序问两次，只有一致时才采纳。不一致按「无差异」处理。
  • 把生成模型与评判模型分开。Anthropic的文档同样建议，评分时使用与生成时不同的模型通常更好。
  • 用逐项的是/否检查表代替打分。量表分数在不同评判者之间刻度不一，难以做时间序列比较。
  • 把大模型判定用于决定人工查看的先后顺序，发布审批本身仍交给硬性门槛与人工审校。

评判偏差的一般理论与缓解办法在产出物审校篇中有更多讨论。这里强调的是版本管理层面的推论：「换掉评判者的那一刻，历史就断了」。

8. 模型升级本身就是一次回归事件

有一种情况，提示词一个字都没动，行为却变了：模型换了。而且这件事按的是厂商的日程，不是我们的。

8.1 厂商会公告什么，不会公告什么

截至2026年7月，两家厂商的公开政策如下。

  • Anthropic — 将模型生命周期定义为Active、Legacy、Deprecated、Retired四个阶段，并对公开模型写明下线前至少提前60天通知。对已下线模型的请求会失败。文档还说明可从控制台导出按API密钥、按模型的用量，用于审计仍在调用已弃用模型的位置。
  • OpenAI — 对一般可用模型给出至少6个月，对特殊变体（聊天变体、Codex、深度研究类）给出至少3个月，对预览模型则是两周左右的短得多的预告，并建议不要把预览模型放在业务关键路径上。

关键在于这些通知讲的是「下线」，而不是「行为变化」。使用别名的团队不会在下线日看到错误，而是某一天悄无声息地开始用另一个模型。错误有告警，行为变化没有告警。这就是第3节强调记录快照标识而非别名的原因。提示词与模型的锁定结构整体，已在供应商锁定退出策略中按层次整理。

8.2 更换模型的六个步骤

步骤要做什么产出常见失误
0. 清点列出哪些提示词使用哪些快照提示词×模型对照表漏掉批处理与后台里隐藏的调用
1. 冻结验证期间禁止改动提示词冻结通知同时也改提示词，导致原因无法分离
2. 重测基线在旧模型上现在再跑一次评测集基线成绩拿几个月前的数字当基线
3. 对照运行用同一套评测集在新模型上运行改善/持平/劣化的拆解只看总分，不看用例层面的移动
4. 局部修改只针对劣化用例，一次改一处修改记录一口气改多处，不知道是哪一处起了作用
5. 灰度与并行从小流量开始切换，保留回退路径迁移计划临近下线日才开始，没有回退余地

想强调第2步：基线一定要现在重测。过去的记录来自当时的评测集、评判者与运行环境；拿它去和新模型的成绩比较，根本说不清原因。比较只有在同一天、同一套评测集、同一个评判者下并排跑出的两个数字之间才有意义。

第3步的拆解同样重要。总分相同，内部的用例也可能大幅移动。十条变好、十条变差，总分不变，但如果变差的那十条位于营收路径上，那就不是改善而是事故。

# 对照运行并不难，难的是按用例逐条阅读结果。
run_eval --suite support_v5 --model old-snapshot --k 5 --out base.json
run_eval --suite support_v5 --model new-snapshot --k 5 --out cand.json

compare base.json cand.json --group-by segment
# 输出示例（仅示形式）：
#   improved  18  regressed  11  unchanged 151
#   regressed 中 segment=billing 有7条  <- 看这里，而不是看总分

9. 有提示词缓存时，前面那一行的价钱不一样

对使用提示词缓存的团队来说，改动的位置决定成本。这一事实会直接影响提示词管理规则。

按Anthropic的文档，缓存具有工具 → 系统 → 消息顺序的前缀结构，靠前的层级一变，其后的层级会一并失效。修改工具定义的名称、说明或参数会让整个缓存失效；修改系统提示词会让系统与消息缓存失效。价格结构如下。

项目相对基础输入的倍率含义运营含义
缓存写入（5分钟）1.25倍新建缓存条目时发布之后最初的那批请求要付这笔钱
缓存写入（1小时）2.0倍更长保留的选项对变更频繁的部分不划算
缓存读取0.1倍复用缓存条目时稳定前缀越大，收益越大
默认存活时间5分钟每次被使用时刷新流量稀薄时缓存经常变冷

由此得出三条实务规则。

  • 把经常变的内容往后放。正在实验的指令、按人群分支的内容、最近改动的政策文案都应放在缓存边界之后。放在前面，改一个字就会让整个前缀失效。
  • 不要把当前时间、用户名之类的变量插在系统提示词的靠前位置。那样每次请求的前缀都不同，缓存实际上就不工作了。
  • 把缓存边界的位置写进提示词元数据。第3节模式里的cache_boundary_after就是干这个的。没有这条信息，评审者无法判断「在前面加一行」的成本影响。

对发布流程也有推论：提示词发布之后成本会暂时上升，因为所有缓存都要重新写入。为避免把这段上升误判为异常而回滚，应把发布时间与成本曲线放在一起看。上面的数值与层级结构依据的是Anthropic自家文档；缓存实现与计费各厂商不同，若使用其他厂商，需按对应文档重新确认。

10. 回滚的判断依据

回滚应当是被设计好的路径，而不是一次失败。问题在于，很多团队直到事故发生后才去定「什么时候回滚」，而那一刻判断力已经被打乱了。

信号阈值处置依据
违反硬性门槛1次立即回滚格式与安全项不按概率管理
评测集通过率下降超出置信区间的下降回滚落在区间内可能只是噪声（5.2节）
仅某一人群下降即便总分持平局部回滚或分支处理总分会掩盖内部移动
成本骤增发布后持续30分钟以上先检查缓存边界再判断刚发布时的上升可能只是缓存重写（第9节）
人工审校的申诉趋势没有回落观察后再判断因一次申诉就回滚会污染历史
无法复现的报告—不要回滚，把它做成用例回滚无法复现的问题，原因就永远留不下来

回滚还有一个很少被提及的前提：要回退到的那个版本必须与它的模型一起还活着。如果提示词v6只在旧模型快照上验证过，而那个快照已经下线，那么回退到v6就是走向一个未经验证的组合。换言之，模型下线的那一刻，绑定在它上面的回滚路径也一起消失了。这才是第8节要给并行运行期留足余量的真正原因。

回滚之后必做的事也应事先定好：不要删除回退掉的版本，把它标记为rolled_back，并把坏掉的内容作为用例加进评测集。不做这两件事，同样的尝试几个月后还会再来一遍。

11. 选工具之前要回答的三个问题

截至2026年，提示词评测与回归工具的生态大致分为三类。这不是说哪一类更好，而是说它们要解决的问题不同。

  • 以文件与CI为中心 — 把评测集以文本形式放在仓库里，在CI中运行并以退出码拦截发布。目标是阻断有害变更，promptfoo是代表。
  • 以追踪与观测为中心 — 收集线上流量形成数据集并在线打分，目标是看清实际发生了什么。LangSmith、Braintrust通常被归入这一类。
  • 模型提供方内置 — 厂商平台自带的评测功能，触手可及，但与该厂商的模型和格式耦合。

比选工具更重要的是工具换掉之后还留下什么。2026年3月9日，OpenAI宣布收购promptfoo，并表示该项目将在现行许可证下继续保持开源。收购本身的好坏无需评价，但这件事清楚地说明评测工具的所有权结构同样会变。模型厂商会变，工具的主人会变，团队也会变。在这中间必须始终属于我们的资产，不是工具，而是评测集与评判标准。

因此在选工具之前先回答三个问题，日后会少疼一些。

  • 评测集能不能从自己的仓库里以纯文本导出？只存在于界面里的数据集会随工具一起消失。
  • 评判逻辑是不是自己的代码？至少要把第6节的judgeCase这一层握在手里，换工具时分数才有连续性。
  • CI能否用退出码拦住发布？拦不住的评测只是报告，不是门禁。

12. 用最小配置起步

如果要把上面所有内容都备齐才开始，那就没人能开始。定好顺序，就能拆成一两天一个的小步。

  1. 第1天 — 清点。把线上运行的提示词和各自使用的模型快照做成表格。通常这时会有人说「原来还有这个」。
  2. 第2天 — 记录最终提示词。把拼装后的最终字符串的哈希与模型标识写进请求日志。全文难以保留时，至少保留哈希。
  3. 第3天 — 10条硬性门槛用例。只挑那些绝不能抖动的项目，比如格式与禁用词，写出10条。质量评估先不碰。
  4. 第4天 — 接入CI。让提示词文件一有改动就自动跑硬性门槛，不通过就拦住合并。
  5. 第1周 — 引入反向用例规则。把「新增约束的改动必须附带反向用例」写进评审检查表。
  6. 第2周 — 把事故变成用例。每出一次线上事故，先加用例再修复。仅凭这一条规则，评测集就会自己长大。
  7. 第1个月 — 基线与相对比较。用例超过50条后开始跟踪通过率，新版本按与基线的对比来判断。
  8. 每季度 — 演练一次模型更换。在真正的下线通知到来之前，先把第8节的流程走一遍。等收到通知才第一次做就晚了。

如果只挑最便宜的一件事，那就是第3天的10条硬性门槛用例。质量评估设计困难，还会连带出评判者的问题；而「JSON能否解析」和「有没有禁用词」判定机械，可以立刻自动化。而且真实线上事故里，相当一部分正好发生在这两个项目上。

结论

把提示词当代码来管理，并不是说把提示词放进仓库。它的意思是改动附带理由、变更的副作用可被观测、回退的路径还活着。三者缺一，仓库就只是一个字符串仓库。

提示词管理之所以格外棘手，是因为三种性质叠加在一起：改动不是局部的，输出不是确定的，运行环境会在我们的掌控之外变化。针对这三点的应对分别是反向用例、基于分布的通过标准、固定快照并重测基线。本文给出的所有表格与模式，都是从这三点派生出来的。

最后把局限说清楚：这里写的任何流程都不保证提示词的质量或性能。回归测试做的不是证明「变好了」，而只是在发布前发现「以前能做到的现在做不到了」。仅此一点也足够值钱，因为在接入AI的系统里，最常发生的事故并不是新的失败，而是悄悄回来的旧失败。
