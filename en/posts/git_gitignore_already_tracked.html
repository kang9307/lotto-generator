You Added It to .gitignore and It Still Shows Up - The File Is Already Tracked

It is a question of order, not of rules. How to untrack a file, and why history keeps it anyway

2026-09-01 Dev & Infra

One config file keeps riding along in every commit. You write its name into .gitignore, edit the file, and run git status. Still there. You suspect a typo and retype it, add a slash and take it off again, throw in an asterisk. Still there.

This is where most people start searching for pattern syntax. But the majority of these cases are not a syntax problem. The rule is not wrong; it arrived too late. This piece reproduces that in a throwaway repository, then covers the command that untracks a file and, just as importantly, what that command does not do. The last part matters most.

Every output below came from actually running these commands in a fresh, empty repository in a temporary directory. Some of the commands are not reversible, so if you follow along, do it in a directory you are willing to throw away rather than in a real working repository.

The environment

Every output in this article came from the setup below. Git itself does not vary much across platforms, but a few things do depend on the shell and the operating system, such as line-ending handling and path display, so it is worth stating.

  • OS - Windows 10 Pro (build 10.0.19045)
  • Shell - Git Bash (GNU bash 5.2.37(1)-release, x86_64-pc-msys)
  • Git - git version 2.48.1.windows.1

The same commands and outputs reproduce almost exactly under bash or zsh on Linux and macOS. Two things can differ. Reproducing it - a committed file never reads the rule

Running it once beats any explanation. Create an empty repository, commit a config file, and only then write the .gitignore. That is exactly the order things happen in real life.

$ git init -b main demo && cd demo
$ echo 'API_KEY=placeholder' > config.local.json
$ git add -A && git commit -m "initial commit"

# Nothing is wrong so far. Now add the rule.
$ echo 'config.local.json' > .gitignore
$ git add .gitignore && git commit -m "add gitignore"

# And edit that file.
$ printf 'API_KEY=changed-secret\n' > config.local.json
$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   config.local.json

no changes added to commit (use "git add" and/or "git commit -a")

The rule is plainly there, and modified: config.local.json shows up anyway. Look inside the index and the reason is immediate.

$ git ls-files
.gitignore
README.md
config.local.json
src/app.js

$ git check-ignore -v config.local.json
$ echo $?
1

git ls-files prints the paths registered in the index, which is the list of currently tracked files. There sits config.local.json, in plain view. And git check-ignore, the tool for diagnosing ignore rules, says nothing at all and returns exit code 1. Not because there is no rule, but because a tracked path is not a candidate for the ignore check, so the check was skipped. That silence comes back in the diagnosis section.

  • The symptom reads as «the rule is being ignored», but the real state is the rule is never read
  • If ten edits to the pattern change nothing, more syntax fiddling is wasted time. Look at the index first
  • One line settles it. If git ls-files lists the path, the cause is confirmed

Why it was designed this way

The official documentation states this behavior in its opening sentence. The gitignore page begins by saying it specifies intentionally untracked files that Git should ignore, and that files already tracked by Git are not affected. This is not an edge case; it is declared behavior.

Imagining the opposite makes the choice easy to accept. If adding one line to .gitignore could quietly drop a file that is already part of the repository, then a line of text becomes a delete command for versioned content. One careless broad pattern like *.conf could knock dozens of tracked files out of history at once. On top of that, this file is committed and propagates to the whole team. One line added for one person's convenience should not drop files out of somebody else's repository.

So Git separated two things. What not to take in is decided by a config file, while taking out what is already in requires an explicit command. The NOTES section of the same document spells out that order: to stop tracking a file, remove it from the index with git rm --cached, and then add its name to .gitignore so it is not reintroduced.

  • A config file is a rule about the future, and it does not apply retroactively to history that already exists
  • Taking something out of history is hard to undo, so it demands its own command
  • Thanks to that split, an accidentally broad .gitignore tops out at «new files are not being picked up»

Getting it out - git rm --cached

There is one command for stopping tracking: git rm --cached. It removes the entry from the index and leaves the real file in the working directory alone. Continuing in the same repository, it goes like this.

$ git rm --cached config.local.json
rm 'config.local.json'

$ ls -1
README.md
config.local.json
src

$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	deleted:    config.local.json

$ git commit -m "stop tracking config.local.json"
$ printf 'API_KEY=another-change\n' > config.local.json
$ git status --short

$ git check-ignore -v config.local.json
.gitignore:1:config.local.json	config.local.json

Read in order: right after rm --cached the file is still on disk (it is right there in the ls -1 output) while the index stages it as a deletion. Once that is committed, editing the same file produces no output from git status --short at all. And only now does check-ignore speak up, naming the rule that caught the path, line number included.

Warning - git rm PATH without --cached deletes the file from the working directory as well as the index. If it was a local config file holding uncommitted content, there is no way to get it back. For the purpose described here, --cached is not optional.

Pulling out a whole directory needs -r. Without it Git refuses. Getting into the habit of listing the targets with --dry-run first is worth it.

$ git rm --cached node_modules
fatal: not removing 'node_modules' recursively without -r

$ git rm -r --cached --dry-run node_modules
rm 'node_modules/pkg/index.js'

$ git rm -r --cached node_modules
  • --cached - removes from the index only. The file in the working directory stays
  • -r - required when the target is a directory. Without it, Git refuses with fatal
  • --dry-run - prints the list and changes nothing
  • The removal only takes effect once you commit it. Until then it lives in the index

The sweep-it-all idiom and what it costs

When several files need untracking there is a common shortcut: empty the index completely and refill it with git add .. The .gitignore rules in effect at that moment apply during the refill, so the ignored paths simply drop out.

$ git rm -r --cached . --dry-run
rm '.gitignore'
rm 'build.log'
rm 'src/app.js'

Convenient, with one condition attached. Use it only when there are no uncommitted changes at all. Emptying and refilling the index does not merely filter by ignore rules; it captures every state present in the working directory at that instant. Below is the same idiom run while one uncommitted edit was sitting there.

$ echo 'app-edited-but-not-committed' > src/app.js
$ git status --short
 M src/app.js

$ git rm -r --cached .
$ git add .
$ git status --short
D  build.log
M  src/app.js

$ git diff --cached --stat
 build.log  | 1 -
 src/app.js | 2 +-
 2 files changed, 1 insertion(+), 2 deletions(-)

The intent was to untrack build.log and nothing else, yet an unreviewed edit to src/app.js landed in the same commit. In a repository with hundreds of files, the commit message and its actual contents diverge and tracing the cause later gets hard. So the order goes like this.

  • First confirm git status is clean. Commit or stash whatever is left over
  • Run --dry-run and read the list. More paths than you expected means the rules are too broad
  • For only a handful of targets, name the paths individually instead. Any accident stays inside those paths
  • Before committing, check what actually got staged with git diff --cached --stat

History keeps the file anyway

This is the most important part of the article. git rm --cached excludes the file only from commits made after that point. Past commits hold the content entirely intact. Reading «gone from the index» as «deleted» is a dangerous mistake.

Below, a file containing a password was committed twice, then untracked, and then read back. The values are experiment placeholders.

$ git ls-files
.gitignore
src/app.js

$ git log --oneline -- config/secrets.env
295c575 stop tracking secrets.env
dec8b71 update settings
61f23fd initial commit

$ git show HEAD~2:config/secrets.env
DB_PASSWORD=placeholder-not-a-real-secret

$ git rev-list --objects --all | grep secrets.env
c6dd1f3ef86e381a694fa8c4ad29b2ea0463e33e config/secrets.env
934ceb11a04aff62ef5aaa84c79377a41d57ba15 config/secrets.env

It is absent from the tracked list. And yet git log enumerates every commit that touched it, and a single git show COMMIT:PATH prints the contents of the day. The last command is even plainer: both versions of the blob are still sitting in the object database, and anyone who cloned the repository received them too.

Removing the file from past commits as well requires rewriting history, and that is a completely different kind of job. Every commit hash changes, so everyone who cloned the repository is affected and consistency with existing branches, tags and merge requests breaks. This article stops at the fact that such a job exists and is separate; it does not walk through the procedure. In most situations it is not the first thing to do anyway.

  • rm --cached changes future commits only. The past is untouched
  • Deleting a branch or reverting a commit does not remove objects immediately. They stay readable while the reflog holds them
  • Rewriting history changes every commit hash, so on a shared repository it presupposes coordinating with everyone
  • If it has already been pushed, assume the copies on the other side remain regardless of what you do locally

If credentials went in, rotate the key first

When you find a password or an API key inside a commit, the reflex is to reach for deleting the file. That order is backwards. However cleanly you delete it, a value that has already been read does not come back. If it was pushed, if somebody cloned it, if a copy survives in a backup, a mirror or a CI cache, treat the value as exposed.

So the priority is clear. Revoking the exposed credential and issuing a new one comes first. The moment the new value takes effect the old one is worthless and the risk evaporates, whether or not history still carries it. Go at history first and the old key stays alive for the entire duration of that work.

  • First - revoke the key, token or password and issue a new one. Invalidate the old value in the issuer's console immediately
  • Second - check the logs of whatever that credential could reach, for signs it was actually used
  • Third - use git rm --cached and .gitignore so the same thing cannot repeat
  • Fourth - plan a history rewrite if you need one, after the coordination is done

As an aside, credentials are better off not living in the repository as files at all. Use environment variables or a dedicated secret store, and keep only an example file with empty values in the repository. Splitting the names, as with config.example.json, naturally produces a setup where the example is tracked and the real file is blocked by a rule.

Reason 1 a rule fails - path patterns

If the index is not the problem, patterns are the next suspect. The confusing bits come down to two: the slash at the front and the slash at the end.

The official rule reads as follows. If a separator appears at the beginning or in the middle of a pattern, the pattern is relative to the directory holding that .gitignore; if not, it can match at any level below. And if a separator appears at the end, the pattern matches directories only, otherwise it matches both files and directories.

# Two directories exist: build/ and src/build/

$ printf '/build/\n' > .gitignore
$ git check-ignore -v build/out.o src/build/out.o
.gitignore:1:/build/	build/out.o
# src/build/out.o is absent from the output = not ignored

$ printf 'build/\n' > .gitignore
$ git check-ignore -v build/out.o src/build/out.o
.gitignore:1:build/	build/out.o
.gitignore:1:build/	src/build/out.o

One leading slash separated «only the top-level build» from «build at any depth». Next comes the trailing slash. Here the name cache was made a directory, then a file, with the same rule applied against each.

# when cache is a directory
$ printf 'cache\n' > .gitignore
$ git check-ignore -v cache/a.txt
.gitignore:1:cache	cache/a.txt

# when cache is a file - the same rule still bites
$ git check-ignore -v cache
.gitignore:1:cache	cache

# add a slash to the rule and it no longer matches the file
$ printf 'cache/\n' > .gitignore
$ git check-ignore -v cache
$ echo $?
1

# the same rule still matches the directory
$ git check-ignore -v cache/a.txt
.gitignore:1:cache/	cache/a.txt

Here are the notations in common use and what they do.

NotationMeaningMatchesDoes not match
buildAnything named build, file or directory, at any depthbuild, src/buildAnything named otherwise
build/Directories only, at any depthbuild/, src/build/A file named build
/build/The top-level build directory onlyTop-level build/src/build/
*.logThe log extension, at any deptha.log, logs/b.loglog.txt
logs/*.logDirectly under logs. The middle slash pins the locationlogs/a.loglogs/sub/a.log
logs/**/*.logEvery depth under logslogs/sub/a.logLogs outside logs
  • With no slash anywhere in the pattern, the location is free. This is where accidentally broad matching comes from
  • To target directories only, put a slash at the end. It keeps a same-named file out of the match
  • Patterns are read relative to the directory holding that .gitignore. In a subdirectory file, /foo means that directory's foo, not the repository root's

Reason 2 - where a negation cannot revive

«Ignore this whole directory but keep this one file» is a common wish. So people exclude the directory and put an exclamation mark on one file inside it. That combination does not work.

$ printf 'logs/\n!logs/error.log\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:1:logs/	logs/error.log
# the ! is written, and line 1 still won

$ printf 'logs/*\n!logs/error.log\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:2:!logs/error.log	logs/error.log
$ git check-ignore -v logs/debug.log
.gitignore:1:logs/*	logs/debug.log

The difference is logs/ versus logs/*. The first excludes the directory itself; the second excludes the entries inside it. The documentation states the reason outright: it is not possible to re-include a file if a parent directory of that file is excluded, because Git does not list excluded directories for performance reasons, so patterns on the contained files have no effect no matter where they are defined. Close a directory as a whole and Git never looks inside it.

The second trap is order. In ignore rules, the last matching pattern decides the outcome. Write the exception first and the broad rule after it, and the exception is buried.

$ printf '!logs/error.log\nlogs/*\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:2:logs/*	logs/error.log

The same two lines, swapped, and the result flips. The broad rule on line 2 buried the exception on line 1. Because of this, writing .gitignore with broad rules at the top and exceptions below has become the de facto standard.

  • If you need an exception inside a directory, write dir/* rather than dir/. One character is the whole difference
  • For deep nesting you have to open it level by level: dir/*, !dir/sub/, dir/sub/*, !dir/sub/keep.txt
  • An exclamation line always sits below the rule it is meant to reverse

Reason 3 - which file's rule won

There is more than one place to write ignore rules. The repository .gitignore, a .gitignore in each subdirectory, .git/info/exclude, and the global file named by core.excludesFile are all in play at once.

The precedence the documentation defines, highest first: patterns given on the command line; then the .gitignore files in the path's own directory and its parents, with files nearer the bottom overriding those above; then info/exclude; and lastly the global file. Within one level, the last match wins. Stacking the four levels one after another looks like this.

# 1) global ignore only (my_global_ignore contains *.log)
$ git config core.excludesFile my_global_ignore
$ git check-ignore -v logs/error.log
my_global_ignore:1:*.log	logs/error.log

# 2) .git/info/exclude beats the global file
$ printf '!logs/error.log\n' > .git/info/exclude
$ git check-ignore -v logs/error.log
.git/info/exclude:1:!logs/error.log	logs/error.log

# 3) the repository .gitignore beats info/exclude
$ printf 'logs/error.log\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:1:logs/error.log	logs/error.log

# 4) a subdirectory .gitignore beats the one above it
$ printf '!error.log\n' > logs/.gitignore
$ git check-ignore -v logs/error.log
logs/.gitignore:1:!error.log	logs/error.log

Four runs, and a different file was named as the decider each time. If you have rules spread across several places and are wondering why none of them bite, this output format is itself the answer.

Where you write itShared?PrecedenceGood for
Subdirectory .gitignoreCommitted, sharedHighestRules that apply to that directory only
Top-level .gitignoreCommitted, sharedHighBuild output, dependencies, secret file names
.git/info/excludeNot sharedMiddleScratch files only you use in this repository
core.excludesFile global fileNot sharedLowestEditor and OS by-products
  • When several rules cover one path, the subdirectory file beats the one above. Blocking above and reopening below is possible
  • The global file is the weakest. It cannot reverse what a repository explicitly declared ignored
  • If a file is ignored and you cannot find the rule, suspect the global file and info/exclude. Neither is visible inside the repository

Diagnosis - check-ignore names the culprit

The git check-ignore -v used throughout the sections above is the standard diagnostic here. Give it a path and it prints, tab-separated, which file, which line number and which pattern decided that path. Three characteristics are worth knowing before you read the output.

# 1) it says nothing about a file that is already tracked
$ git check-ignore -v kept.txt
$ echo $?
1

# 2) add --no-index and the rule becomes visible
$ git check-ignore -v --no-index kept.txt
.gitignore:1:kept.txt	kept.txt

# 3) with -v the exit code means «a pattern matched», not «ignored»
#    rules in effect: logs/* and !logs/error.log
$ git check-ignore -v logs/error.log
.gitignore:2:!logs/error.log	logs/error.log
$ echo $?
0
$ git check-ignore logs/error.log
$ echo $?
1

First, it stays silent on a file that is already tracked. That is the silence from earlier in this article. The description of the --no-index option spells out exactly this use: debugging why a path became tracked by something like git add .. So if the output is empty but appears once you add --no-index, the file is tracked and you already have your answer.

Second, if the reported pattern starts with an exclamation mark, the path is not ignored. The -v documentation says as much: if the pattern begins with «!» then it is a negated pattern, and matching it means the path is not excluded. Reading any output as «ignored» gets it exactly backwards.

Third, and consequently, read the exit code carefully. In the run above it was 0 with -v and 1 without. The verdict did not flip; -v treats «a pattern matched» as success while the plain form treats «actually ignored» as success. For a decision inside a script, use the form without -v.

Two companion tools help as well. git status --ignored shows ignored entries too, marked !!, and git ls-files -i -c --exclude-standard picks out only files that are still tracked despite matching a rule. That is precisely the list this article is about.

$ git status --short

$ git status --short --ignored
!! logs/
!! scratch.tmp

# the *.log rule was added, but build.log is already tracked
$ git ls-files -i -c --exclude-standard
build.log
  • git check-ignore -v PATH - answers which rule won in one line. The first command to run
  • If it only shows up with --no-index, the cause is tracked state. Go to git rm --cached
  • git status --ignored - see with your own eyes what is actually being ignored
  • git ls-files -i -c --exclude-standard - produces the entire cleanup list at once

Empty directories are not tracked

A companion question comes with this topic. You commit a directory structure, someone clones it, and the directory is not there. This has nothing to do with ignore rules. Git records files and does not store the concept of a directory separately. Directory names are reproduced as a side effect of the paths that contain them.

$ mkdir uploads
$ git add uploads
$ git status --short

$ touch uploads/.gitkeep
$ git add uploads
$ git status --short
A  uploads/.gitkeep

Running git add on an empty directory produces no error and no effect. Only once a file is inside does anything get staged. That is where the .gitkeep convention comes from. It is not a name Git knows about; it is just the customary name for the empty file put there to hold a directory open. A README does the same job.

  • The name is convention. No tool treats it specially, so a team can simply settle on one
  • The typical case is an uploads directory: ignore the contents but keep the directory
  • Then the rules are uploads/* and !uploads/.gitkeep. For the reason given earlier, writing uploads/ kills the exception

Do not mix repository rules with personal taste

.gitignore is a committed file, so it goes to everyone who clones the repository verbatim. What you write in it looks like a solo decision but is closer to a collaboration agreement. The moment personal editor settings go in, meaningless lines get distributed to people who do not use that editor.

The test is simple. Things that look the same on any machine go in the repository rules; things that differ per person go in personal settings. Build output and dependency directories appear under the same names on any machine, so repository rules are right for them. Which editor someone uses, on the other hand, varies.

  • Repository .gitignore - build output, dependency directories, logs, the names of real secret files
  • .git/info/exclude - things only you need in this repository. Scratch scripts, personal notes
  • Global file (core.excludesFile) - editor settings and OS by-products that recur in every repository
  • All three follow the precedence above. Personal settings are the weakest and cannot reverse a repository rule

Personal entries pile up in a repository .gitignore mostly because nobody knows where else to put them. Simply telling a team that .git/info/exclude exists visibly cleans the file up.

What to add from day one, and what to check before committing

Every problem in this article comes from order - the rule arriving later than the file. Prevention works by order too: put .gitignore in the repository's very first commit. The list differs by language and framework, but it breaks into four kinds.

KindExamplesWhy it goes inIf you leave it out
Build outputdist/, build/, target/, *.oIt can be regenerated from source at any timeEvery commit carries an enormous diff and review gets hard
Dependenciesnode_modules/, vendor/, .venv/Lock files reproduce them, so history has no reason to hold themThe repository grows dozens of times bigger and cloning slows down
Logs and temporary files*.log, *.tmp, .cache/The values differ on every runMeaningless changes pile up and hide the real ones
Credentials.env, *.pem, *_rsa, secrets.*Once in, they are hard to get out of historyNothing solves it except rotating the key

The last row is the expensive one. The first three can be caught late and cleaned with a single rm --cached; credentials cannot. Adding the .env family before the first commit does the most good.

One habit is worth adding as well. git add . is convenient but takes in every new file that has no rule yet. With a rule in place Git blocks it; without one, it slips in silently.

$ printf 'TOKEN=placeholder-not-a-real-token\n' > .env.local
$ echo 'note' > memo.txt
$ git add .
$ git status --short
A  .env.local
A  memo.txt
A  uploads/.gitkeep

# with a rule in place, this is what you get instead
$ git add logs/error.log
The following paths are ignored by one of your .gitignore files:
logs/error.log
hint: Use -f if you really want to add them.
hint: Disable this message with "git config set advice.addIgnoredFile false"

The git add . above took in .env.local without a word of warning. The one below was refused because a rule existed, with a note that -f is available if you really mean it. That contrast is the argument for putting rules in early. And either way, looking at git status once right before committing is the last safety net. Reading a few lines costs seconds.

  • Include .gitignore in a new repository's first commit. Most of this article's problem disappears
  • Add credential patterns while the project is still empty. Later is too late
  • After git add ., read git status --short to see what got staged
  • When you see the refusal message, do not reach for -f reflexively. There may be a reason it was blocked

Wrapping up

.gitignore only ignores files that are not tracked. One sentence, and most of this article follows from it. A file the rule reached too late never reads the rule, which is why no amount of pattern editing changes the result. The command to get it out is git rm --cached PATH, a directory needs -r, and dropping --cached takes the file on disk with it.

Sometimes the pattern really is the problem. A leading slash pins the location, a trailing slash narrows it to directories, blocking a parent whole prevents any inner exception from reviving, and within one level the last match wins. Rules may also be scattered across four places. In every one of these cases, one line of git check-ignore -v names the culprit. Run it before editing patterns on a hunch.

And once more: git rm --cached removes the file only from later commits. Past commits keep it, readable with one git show. If a password or key went in, before wondering how to erase the file, revoking that value and issuing a new one is the first action.

What I could not verify

  • The experiments ran only on Windows 10 Git Bash with git 2.48.1.windows.1. Other Git versions may word the output differently. The hint: lines in particular have changed across versions
  • Behavioral differences on a case-sensitive filesystem could not be checked directly. That is not reproducible on Windows
  • The actual behavior and side effects of history-rewriting tools were left out of scope. It is a job done on shared repositories, so verifying it needs a collaborative setting, and recovery is a separate subject
  • How long git rm -r --cached . takes on a large repository was not measured. The experiment repository has too few files to produce a meaningful number
