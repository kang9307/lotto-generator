Code as Agent Harness — AIエージェントの実行基盤としてのコードという新視点

UIUC・Meta・Stanford 102ページサーベイが示すパラダイム: コードは成果物ではなく、エージェントの推論・行動・検証を構造化するハーネスだ

2026-06-26 開発・インフラ

序論: コードの役割が逆転した

ここ数年、AIとコードの関係を語る文脈はほぼ一定だった。LLMがあり、そのLLMがコードを生成する。プロンプトを与えれば関数が出てきて、バグを説明すれば修正パッチが返ってくる。この関係においてコードは常に結果物だった。

2026年5月、UIUC・Meta・Stanfordの共同研究チームがarXivに公開した102ページのサーベイ(arXiv: 2605.18747)は、この図を正面から逆転させる。サーベイが提示する核心的命題は簡潔だ。「エージェントシステムにおいて、コードはもはや単なる生成目標ではない。コードは、エージェントが推論し、行動し、環境をモデル化し、実行ベースの検証を行うための運営基盤(operational substrate)として機能する。」

このポストでは、その転換が何を意味し、なぜ重要で、実務上何が変わるのかを、サーベイ内容を基に独自の視点で解説する。2026年6月時点で、エージェントAI開発の方向性をこのサーベイほど体系的にまとめた文書は少ない。

1. パラダイムシフト: コードは出力ではなく基盤だ

エージェントシステムを実際に構築した経験がある人なら、直感的にすでに知っていることがある。LLMのテキスト出力だけでは何もできない。それが実際の環境で何かをするためには、必ず実行可能な構造に包まれなければならない。その包む構造こそ、サーベイが言うハーネスだ。

サーベイはエージェントシステムにおけるコードの役割を三つに整理する。

  • 推論を実行可能に(Reasoning Executable): コードはモデルの内部推論を外部で検証可能な演算として露出する。外部インタープリター、シンボリックソルバー、実行トレースが中間ステップをチェックし精緻化する。
  • 行動をプログラム可能に(Action Programmable): コードは高レベルの意図を実行可能な操作——ツール呼び出し、ロボットポリシー、GUIコマンド——に変換する。構造化されたインターフェースを通じて意図が行動に着地する。
  • 環境状態を検査可能に(Environment State Inspectable): コードはリポジトリ・シミュレーター・テスト・実行ログを通じて世界の状態、遷移ダイナミクス、フィードバック信号を表現する。エージェントはこれを実行し、編集し、クエリして環境を理解する。

この三つが噛み合って動くとき、エージェントは単にテキストを返すのではなく、環境とループを形成するシステムになる。コードはそのループの骨格だ。

2. ハーネスの解剖: 3層構造

サーベイはエージェントハーネスを三つの連結した層に分解する。この構造を理解すると、現代のエージェントシステムがなぜ現在の形で設計されているかが明確になる。

2.1 ハーネスインターフェース — コードがエージェントと環境を繋ぐ方法

第1層はコードが推論・行動・環境モデリングにおいてインターフェースの役割を果たす方法だ。エージェントが世界を認識しその認識を行動に転換する接点がここにある。エージェントに何をすべきかを伝えるガイド(AGENTS.mdのような文書)と、何が間違っているかを伝えるセンサー(型チェッカー、リンター、テストランナー)がこの層の核心構成要素だ。

興味深いのは、Claude CodeのCLAUDE.mdやOpenAIのAGENTS.mdがすでに本番環境でこのガイド役割を果たしているという事実だ。エージェントが実行時に読む構造化された指示文書がハーネスの一部として、エージェントの行動を制約し方向づける。

2.2 ハーネスメカニズム — 長期実行を可能にするエンジン

第2層はハーネスを実際に動かすメカニズムだ。サーベイは四つを提示する。

  • 計画(Planning): 長期タスクを線形・構造基盤・探索基盤・オーケストレーション基盤の戦略で分解する。
  • メモリ(Memory): 作業状態、意味知識、経験記録、共有インタラクション履歴を維持する。
  • ツール使用(Tool Use): エージェントをAPI、検証システム、実行環境に接続する。
  • フィードバック制御・最適化(Control & Optimization): ランタイムフィードバックで「計画-実行-検証」ループを反復的に修正・適応させる。

「計画-実行-検証」ループは特に重要だ。エージェントは単に出力を出すのではなく、出力を実行し、その結果を確認し、次の行動を決定する閉じたループをコードが構造化する。コードがなければこのループは成立しない。

2.3 ハーネスのスケール — 単一エージェントからマルチエージェントへ

第3層はハーネスをマルチエージェント環境に拡張する方法だ。複数のエージェント(管理者・コーダー・レビュアー・テスター)が役割分担する際、共有コードアーティファクトが調整の基盤になる。同じリポジトリを参照し、同じテスト結果を共有し、同一の状態を基準に行動する。コードはエージェント間のコミュニケーション媒体であり共有の真実の根拠となる。

3. 良いハーネスの4属性: 何が優れたハーネスを作るか

サーベイはエージェントハーネスが備えるべき四つの属性を提示する。これはハーネス設計の要件仕様として読める。

属性意味実務例
実行可能性(Executable)意図した結果を形式的に検証可能テストランナー、コードインタープリター
検査可能性(Inspectable)構造化トレースが中間計算を露出実行ログ、ステップ別トレース
状態保持(Stateful)タスク進行状態を持続的に表現リポジトリ状態、メモリ構造
統制可能性(Governed)権限境界・サンドボックス・安全制約適用ツール権限制限、サンドボックス実行

この四属性は互いに独立ではない。実行可能性がなければ検証が不可能で、状態保持がなければ長期タスクが成立せず、統制可能性がなければ意図しない行動を防ぐ手段がない。ハーネスはこの四つを備えて初めて信頼できるエージェントシステムになる。

4. ハーネスエンジニアリングの台頭: 「エージェント = モデル + ハーネス」

サーベイとともに2026年に急速に台頭した概念がハーネスエンジニアリング(Harness Engineering)だ。公式はシンプルだ。エージェント = モデル + ハーネス。モデルが脳なら、ハーネスはその脳が動作する身体と環境だ。

従来のアプローチは「より良いモデルを使えばエージェントがより良く動作する」というモデル中心の思考だった。ハーネスエンジニアリングはこれに挑戦する。モデルの重みを固定したままでも、ハーネス——システムプロンプト、ツール定義、ミドルウェア、検証ループ、メモリ構造——を進化させるだけでエージェント性能を大幅に向上できるという主張だ。

実証がある。Agentic Harness Engineering(AHE)研究は基盤モデルを固定した状態でハーネスのみを観察ベースで進化させ、Terminal-Bench 2で84.7%という成果を達成した。GPT-5.4を10回の反復改善で69.7%から77.0%に引き上げた。ハーネス改善がモデルアップグレードを代替・補完できるという実験的証拠だ。

特に注目すべきはハーネスの可搬性だ。うまく設計されたハーネスは、モデルを交換しても大半の行動が維持される。これは特定モデルベンダーへの依存度を下げる構造的手段でもある。モデルではなくハーネスに投資するほど、エージェントシステムのポータビリティが上がる。

5. コードの新たな意味: ツール定義、AGENTS.md、実行トレース

ハーネスの観点から「コード」の範囲は、私たちが通常考えるよりはるかに広い。サーベイはコードを「実行可能または機械で確認できるアーティファクト」と定義し、以下を含む。

  • プログラム・スクリプト・形式仕様
  • 証明スクリプト・APIスキーマ・ツール定義
  • テスト・リポジトリ・シミュレーター・設定ファイル
  • 実行トレース・ログなどのコード隣接アーティファクト
  • AGENTS.mdのようなガイド文書

ツール定義がリストにある。エージェントにどのツールをどう使えるか伝えるスキーマ自体がハーネスの核心構成要素だ。サーベイが引用する2025年の実証研究はこれがどれほど重要かを示す。ツール数が10個のとき完遂できるタスクが107個では事実上失敗するという非線形性能低下が観察された。ハーネス設計ではツールの整理(tool hygiene)が性能の核心変数だ。

6. 長期実行エージェントとハーネスの役割

エージェントAIで「長期実行(long-horizon execution)」はまだ解決されていない最も難しい問題の一つだ。単発クエリは印象的に動作する。しかし数十ステップにわたって計画を立て、実行し、中間結果を反映し、目標を維持するエージェントはまだ不安定だ。

ハーネスはこの問題に構造的解法を提示する。第一に、メモリ構造がエージェントが「今どこまで来たか」を失わないようにする。第二に、計画レイヤーが長いタスクを実行可能な単位に分解する。第三に、検証ループが中間結果が正しいか確認し経路を修正する。この三つがコードで実装されたハーネスの中にある時、エージェントは構造的に自己修正しながら進行できる。

特に強調したいのは検証の位置だ。検証は最終出力を人間が確認する事後プロセスではない。ハーネスに内蔵された、実行ループの一部だ。テストが通過しなければエージェントは前進しない。これがコードハーネスが提供する自己修正能力の核心だ。

7. マルチエージェントシステムと共有コード基盤

単一エージェントを超えて複数のエージェントが協力するシステムでは、ハーネスの役割はさらに重要になる。管理者エージェント、コーディングエージェント、レビューエージェント、テストエージェントが分業する際、それらを調整するのは自然言語メッセージだけではない。共有リポジトリ状態、同一のテストスイート、共通ツール定義がその調整の構造的基盤だ。

これがサーベイが言う「共有コードアーティファクト」だ。マルチエージェントシステムで一貫した状態を維持するには、エージェントたちが同一のコード基盤を基準に行動しなければならない。そうでなければ一つのエージェントが修正したものを別のエージェントが上書きしたり、矛盾する仮定の上で各自が行動する問題が生じる。コードがエージェント間の真実の単一ソース(single source of truth)になる。

8. 未解決の課題: サーベイが示すチャレンジ

サーベイはパラダイムを提示すると同時に、まだ解決されていない課題も正直に列挙する。このリストは2026年時点でエージェントAI研究が集中すべき領域を指し示す。

  1. 最終成功を超えた評価: ハーネス中間段階の信頼性を測定する指標がまだ不足している。
  2. 不完全フィードバック下での検証: 完全なオラクルなしに意味的正しさをどう確認するか。
  3. 回帰なしのハーネス進化: ハーネスを改善する際に既存能力を低下させないにはどうすべきか。
  4. マルチエージェント間共有状態の一貫性: 複数エージェントが同時に修正する環境でトランザクション意味論をどう保証するか。
  5. 安全重要タスクにおける人間の監視: 実行可能なハーネス状態として責任所在をどう実装するか。
  6. マルチモーダル拡張: ビジョン・ロボティクス・知覚などのコード以外の領域へハーネスをどう拡張するか。

9. 実務への示唆: 何を変えるべきか

Code as Agent Harnessサーベイは学術的枠組みだが、筆者が読み取る実務的示唆は具体的だ。

9.1 モデル選択より先にハーネスを設計せよ

エージェントシステム構築時の最初の問いは多くの場合「どのモデルを使うか」だ。しかしハーネスの観点からはこの問いの順序が逆になるべきだ。まずエージェントがどのツールにアクセスできるか、どんな検証ループがあるか、どんなメモリ構造を持つかを設計し、モデルはそのハーネスに合うものを選ぶのが正しい。ハーネスが変われば同じモデルでも全く異なるエージェントになる。

9.2 AGENTS.mdとツール定義をコードとして管理せよ

AGENTS.md、システムプロンプト、ツール定義は説明文書ではない。エージェントの行動を決定する実行可能な仕様だ。バージョン管理し、テストし、レビュープロセスを経なければならない。ハーネスコードが変更されればエージェントの行動が変わるとをチーム全体が認識すべきだ。

9.3 ツールの数より質に集中せよ

ツール数107個で非線形性能低下が観察されたという実証は直感と反する。より多くのツールを与えるほどエージェントがより多くのことをできると思いがちだが、実際には選択肢が多すぎるとエージェントが迷子になる。よく定義された少数の明確なツールが、漠然と多いツールより優れている。ハーネス設計においてツールの整理(tool hygiene)が性能の核心変数だ。

結論: ハーネスエンジニアがエージェント時代のインフラ設計者だ

Code as Agent Harnessサーベイが描く世界は、コードの地位が高くなった世界ではなく、コードの役割が変わった世界だ。エージェントがコードを生成する時代に、そのコードを生成するエージェントを包み支える構造自体がコードで作られる。コードは成果物であり同時に基盤だ。

ハーネスエンジニアリングという規律の台頭はこの変化が実務に降りてきた形だ。エージェントシステムの性能はモデル単独では決まらない。モデルを包むハーネス——ツール定義、ガイド文書、検証ループ、メモリ構造、権限境界——が共に決める。このハーネスを設計し発展させることがエージェント時代のインフラエンジニアリングだ。

2026年6月時点で、エージェントAIはまだ速く変化している。しかしこのサーベイが提示するフレームは変化の方向を読む有効な羅針盤だ。コードをどう書くかと同じくらい、何をコードで包むかが重要な時代が来た。
