1. Background and Context — The Reality of AGENTS.md Support in Version 2.1.277

In general, development environments utilizing AI coding assistants rely on standard markdown documents placed within repositories to supply domain conventions and project instructions directly into model prompts.

Within the Claude Code ecosystem, CLAUDE.md has historically served as the standard filename for project instructions. In September 2026, coinciding with the release of version 2.1.277, official information was released. According to a statement transmitted via an X post, Thariq stated: 「We're adding support for AGENTS.md to Claude Code. Starting today in version 2.1.277, if there is no CLAUDE.md in a folder, Claude will check for and use AGENTS.md. You can toggle this behavior in /config.」

A secondary summary on GeekNews noted that this functionality was implemented as a built-in mod on top of Claude Code's new customization mechanism named Mods, with its complete TypeScript source published in the repository. The summary emphasized that teams would no longer need to duplicate CLAUDE.md or maintain symlinks. Initial community discussions reflected immediate enthusiasm, with developers welcoming the accommodation of existing conventions.

The primary source documentation in the official repository explicitly defines the core role of this module. The README states: 「The agents-md mod allows Claude Code to read AGENTS.md files as instruction files, similar to how it reads CLAUDE.md files.」 In the interpretation of this article, because the default configuration loads AGENTS.md only when CLAUDE.md is absent, the instructions delivered to the model vary depending on the existing repository file layout.

2. Core Fallback Principle — The Operational Boundaries of claude-md-or-agents-md

The official README specifies that the default configuration option for the mod is claude-md-or-agents-md. As stated in the technical specification, a project with no instruction files of its own gets its AGENTS.md files instead, loaded exactly where and how CLAUDE.md would be.

The documentation defines the criteria for determining what constitutes a project's 「own instruction files」 with strict precision:

  • If the engine loads a CLAUDE.md, .claude/CLAUDE.md, or CLAUDE.local.md from any directory along the path from the project root down to the current working directory.
  • When any of these three specific files are detected, the entire instruction handling responsibility remains strictly with the core engine, and the mod stays out entirely (the plugin stays out).
  • Conversely, an organization's managed file, a user's global file at ~/.claude/CLAUDE.md, a .claude/rules file, and any CLAUDE.md residing in a directory added via --add-dir do not count as project-owned files because the nested directory walk does not inspect them.
  • Only when absolutely none of the project's own files are present does every AGENTS.md and .claude/AGENTS.md along that path join the instruction files rendered by the engine.

The precedence rules within a single directory are equally uncompromising. If both CLAUDE.md and AGENTS.md coexist within the exact same folder, CLAUDE.md claims that directory, and AGENTS.md is entirely ignored. In default mode, if a repository already possesses an existing CLAUDE.md file, adding an AGENTS.md file alongside it produces zero effect on the model's instructions.

In the interpretation of this article, under default settings AGENTS.md is not loaded if even a single CLAUDE.md exists, so using both files simultaneously requires explicitly selecting merge mode.

3. Comparison of the Four instructionFiles Options and Loading Policies

According to the README, the built-in mod is controlled via a single setting named instructionFiles, which supports four distinct, mutually exclusive modes. Each value dictates how the mod interacts with the engine's internal instruction loading pipeline.

The four options defined in the official specification are:

  • claude-md: Only CLAUDE.md is loaded by the engine as in previous releases. The mod adds nothing to the context.
  • claude-md-or-agents-md: The default configuration. A project with no instruction files of its own gets its AGENTS.md files loaded in place of CLAUDE.md.
  • claude-md-and-agents-md: Every AGENTS.md file up and down the directory tree is loaded alongside CLAUDE.md, with strict deduplication for linked or imported files.
  • managed-only: The project's checked-in, private, and personal instruction files are dropped from the prompt context, leaving only organization-managed instructions and engine memory.

The following table provides an architectural comparison of the four modes, their loaded artifacts, and their operational constraints as documented in the README.

Option Value Files Loaded into Model Context Default Status and Operational Constraints
claude-md Standard CLAUDE.md files discovered by engine walk Non-default. The mod remains completely inert and adds no files
claude-md-or-agents-md AGENTS.md only if project-owned CLAUDE.md is absent Default. Replaces CLAUDE.md if missing; stays out if any project instruction exists
claude-md-and-agents-md Merges all CLAUDE.md and AGENTS.md files across the tree Non-default. Concatenates both conventions while deduplicating by path and content
managed-only Enterprise-managed CLAUDE.md and engine session memory only Non-default. Explicitly strips project-level and personal instruction files from context

The README elaborates on how these files physically reach the language model. The delivery mechanism is governed by the core engine rather than the plugin itself. The prompt.context hook supplies the mod with the array of instruction files underlying claudeMd, represented as objects with the structure { path, kind, content, parent? }, ordered by categories managed, user, project, local, and memory. The hook returns a modified list of files, which the engine then renders with standard framing, announces by name in user transcripts, and filters according to agent roles (such as Explore, Plan, or custom agents with omitClaudeMd).

In the interpretation of this article, the four options deterministically branch whether and how project instructions are incorporated into context.

4. Traversal Rules across Scenarios — Same Directory, Subdirectory Read, and Symlinks

As repository structures expand into multi-package directories, understanding when and how instruction files are discovered becomes essential. The documentation lays down explicit rules regarding directory hierarchy and symbolic link handling.

A crucial technical nuance documented in the README concerns nested instructions: 「Nested AGENTS.md files attach on text Read operations only」. When the agent executes a text Read tool against a file located within the project tree, the engine traverses the intermediate directories between the project root and the target file, attaching any encountered AGENTS.md files to that turn's context. Even under this dynamic walk, if a CLAUDE.md file exists in a given subdirectory, it claims that directory and prevents the sibling AGENTS.md from attaching.

The following table illustrates concrete directory layouts and the resulting instruction loading behavior under different operational modes.

Scenario and File Hierarchy Active Mode Actual Loading Behavior and Result
Both CLAUDE.md and AGENTS.md in project root claude-md-or-agents-md (Default) CLAUDE.md claims the root directory; AGENTS.md is completely ignored
Only AGENTS.md exists; no CLAUDE.md in project claude-md-or-agents-md (Default) AGENTS.md is loaded in the exact slot where CLAUDE.md would normally appear
Root has CLAUDE.md; subdirectory has AGENTS.md claude-md-or-agents-md (Default) Root CLAUDE.md leaves project to engine; subdirectory AGENTS.md is never loaded
Root has CLAUDE.md; subdirectory has AGENTS.md claude-md-and-agents-md (Merge) When a file in the subdirectory is read, its AGENTS.md attaches dynamically
AGENTS.md symlinked to CLAUDE.md in the same folder claude-md-and-agents-md (Merge) Path spelling and content comparison detect duplication, preventing double loading

Regarding symbolic links, the README details an implementation boundary. The mod compares file paths using literal character spellings without resolving symbolic aliases, contrasting with the engine's native filesystem resolution. If a repository references instruction files through complex symlink chains with differing relative path representations, developers should be conscious of potential divergence in deduplication logic.

In the interpretation of this article, nested AGENTS.md files are not incorporated into context during general conversation prior to a text Read operation.

5. @ Import Approvals and Deduplication in claude-md-and-agents-md Merge Mode

When enabling claude-md-and-agents-md mode, handling external file inclusions via @ import syntax requires precise deduplication rules.

The README defines a two-tiered deduplication protocol:

  • Any file that CLAUDE.md already @-imports, or points to via a filesystem link, is strictly exempted from being loaded a second time.
  • The mod executes deduplication by first evaluating the literal file path, and if the paths diverge, performing a subsequent comparison of raw file content.
  • Any @ import statements located inside AGENTS.md files are subject to mandatory external import approval mechanisms identical to those governing CLAUDE.md.
  • Unapproved external import targets are safely excluded from the framed prompt context until explicit user consent is granted.

In the interpretation of this article, duplicate loading is prevented when contents match even if paths diverge, and external imports are incorporated only after receiving approval.

6. Organizational Governance and Context Isolation in managed-only Mode

In enterprise environments, platform teams often require mechanisms to prevent repository-level files from diluting central policies. The managed-only mode provides deterministic isolation for these governance requirements.

According to the official documentation, managed-only enforces the following runtime constraints:

  • All checked-in repository instructions (both CLAUDE.md and AGENTS.md), local overrides (CLAUDE.local.md), and personal user files (~/.claude/CLAUDE.md) are stripped from the prompt context.
  • Only the organization's centrally managed CLAUDE.md and the engine's internal cross-session memory remain active in the model's instruction frame.
  • The engine's global claudeMdExcludes configuration continues to operate normally, filtering user, project, and local files across both naming conventions.
  • Any organization-level plugin prepended to the prompt.context hook sits hierarchically above this mod and maintains absolute final authority over the instruction list.

The documentation notes a specific detail regarding nested files: dynamic attachments of nested CLAUDE.md files during text Read operations are handled by engine internals that are not yet exposed as interceptable hook events, meaning those specific nested reads may still arrive (still arrive). In the source implementation within register.ts, managed-only mode registers an explicit hook on prompt.context matching Files.DROPPED_KINDS and filters the array using Files.isKeptWithoutInstructions.

In the interpretation of this article, under managed-only mode repository-level instruction files are dropped, leaving only organization-managed files and engine memory.

7. Configuration Methods and Backward Compatibility — /config, JSON Settings, and Legacy Keys

The configuration surface for the agents-md mod is exposed through both an interactive terminal interface and static configuration files. The official README outlines exact parameter names and file locations.

In interactive terminal sessions, users can execute the /config slash command to inspect settings. The option is presented as the row titled 「Project instructions」, functioning as an interactive picker over the four supported modes, each accompanied by concise descriptions.

When automating setup or maintaining dotfiles, developers can directly populate user settings at ~/.claude/settings.json, provide a custom configuration file via the --settings command-line argument, or enforce settings through managed enterprise deployment profiles. The exact JSON configuration snippet provided in the README is structured as follows:

{
  "pluginConfigs": {
    "agents-md@builtin": {
      "options": { "instructionFiles": "claude-md-and-agents-md" }
    }
  }
}

A project's local .claude/settings.json file is explicitly not read for plugin options. README notes that this option is recognized only in user global settings or managed settings. Modifying the setting reloads the module immediately, and the subsequent context constructed by the engine (such as the next conversation turn, a newly initiated session, a /clear command, or context compaction) will carry the instruction files dictated by the new mode.

If a developer manually enters an invalid string outside the four permitted values, a notification is emitted once into the session transcript, and the setting automatically defaults to claude-md-or-agents-md. Users can also inspect the built-in plugin via the /plugin command and disable it entirely, in which case the engine reverts to processing CLAUDE.md exclusively.

The documentation also details backward compatibility and key migration. The option was initially named projectInstructions, with supported values claude, agents-fallback, both, and none. While instructionFiles remains at its default, legacy keys continue to be honored according to the following mapping:

  • none → managed-only
  • claude → claude-md
  • agents-fallback → claude-md-or-agents-md
  • both → claude-md-and-agents-md

Any unrecognized value under the legacy key maps safely to claude-md, ensuring no unvetted files are injected. The initial session.start event logs how the legacy setting was interpreted. Once instructionFiles is explicitly set to any non-default value, the legacy key is completely ignored, and Claude Code prompts the user to remove it from settings.

8. Practical Verification Procedures and Caveats — Test Commands and Architectural Trade-offs

Inspection of the repository structure confirms that the mod comprises the manifest .claude-plugin, hook handlers under hooks/ (centered around register.ts), an automated test suite under tests/, and documentation in README.md. Maintainers can execute the plugin's validation suite directly using the built-in test harness specified in the README:

claude plugin test mods/agents-md

From an engineering and operational standpoint, integrating this feature into daily software delivery requires attention to several practical considerations:

  • Silent Fallback Invalidation: Under default settings, if a root CLAUDE.md exists, all nested AGENTS.md files are bypassed. Enabling AGENTS.md requires explicitly switching the configuration to claude-md-and-agents-md (in the interpretation of this article).
  • Monorepo Inspection Latency: Subpackage instructions attach only upon reading target files via text Read. Consequently, subpackage rules are not yet supplied to the model during initial high-level planning turns (in the interpretation of this article).
  • Symlink Normalization Discrepancies: Path deduplication relies on literal string spelling rather than resolved filesystem paths. Varying relative path representations may therefore bypass deduplication logic (in the interpretation of this article).
  • Configuration Drift Across Teams: Plugin options are stored in user or managed configurations rather than the repository's .claude/settings.json. Inconsistent settings among team members may thus result in divergent loaded instruction files across workstations (in the interpretation of this article).

In the interpretation of this article, because default behavior is conditional fallback rather than indiscriminate union, teams must explicitly configure instructionFiles according to their repository layout.
