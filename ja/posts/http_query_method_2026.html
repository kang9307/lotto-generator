HTTP QUERYメソッド — GET・POSTの限界を超える新しい検索標準

RFC 10008：冪等性・リクエストボディ・キャッシュ可能性をすべて兼ね備えたHTTP動詞が登場した理由と実務課題

2026-06-27 開発・インフラ

はじめに：なぜ今、新しいHTTP動詞が必要なのか

HTTPは数十年にわたり、GETとPOSTの2つの動詞でWebの読み取りと書き込みを処理してきた。シンプルなCRUD APIには十分だが、現代のRESTful APIで複雑な検索・フィルタリングリクエストを扱う際には、どちらも構造的な限界を露わにする。GETはURLにしかクエリを含められず複雑な条件では長さ制限にぶつかり、POSTはリクエストボディを自由に使えるが読み取り専用の意味をHTTPインフラに伝えられない。

2026年6月現在、RFC 10008が公式に発行され、この空白を埋めるHTTP QUERYメソッドが標準として登場した。著者はJulian Reschke、James M. Snell（Cloudflare）、Mike Bishop（Akamai）の3名だ。この記事は発表内容を転載するのではなく、なぜこのメソッドが必要だったのかを構造的に分析し、実務でどう使うべきか、そして導入の前に立ちはだかる現実的な障壁が何かを直接的な視点で整理する。

1. GETの構造的限界 — URLがクエリの牢獄になるとき

RESTful設計の基本は、照会リクエストにGETを使うことだ。単純なケースでは問題がない。しかし商品リストにカテゴリ・価格範囲・タグ配列・ソート条件・ページを全部含める検索APIを想像すると、URLがどうなるか見えてくる。

GET /products?category=electronics&price_min=100&price_max=500&tags[]=wireless&tags[]=bluetooth&tags[]=noise-cancelling&sort=price_asc&page=2 HTTP/1.1

この程度ならまだ扱える。しかし実際の検索APIにはネストされたフィルタ構造、全文検索表現、集計条件が入る。ここで複数の問題が重なる。

第一にURL長制限だ。RFC標準自体はURL長を制限しないが、ブラウザ（Chrome は約2MB）とサーバー（Apache デフォルト8KB、Nginx デフォルト8KB）がそれぞれ制限を設けている。複雑なElasticsearchクエリをURLに含めると、すぐにこの壁に当たる。

第二に非ASCIIエンコーディングの問題だ。日本語の検索語や特殊文字はパーセントエンコードが必要で、可読性が大きく下がる。

第三にログとプライバシーのリスクだ。URLはWebサーバーのアクセスログ、CDNログ、ブラウザ履歴にそのまま残る。個人情報や機密性の高い検索条件がURLパラメーターに含まれると、意図せず記録・漏洩される恐れがある。

第四に配列とネスト構造の非標準だ。tags[]=a&tags[]=bやネストオブジェクトのURL直列化はライブラリごとに異なり、サーバー・クライアント間の互換性が保証されない。

2. POSTによる回避策の落とし穴 — 意味の汚染とキャッシュの消失

この問題を避けるために多くのAPIが複雑な検索リクエストにPOSTを選んできた。GraphQLのクエリ実行が典型例で、Elasticsearchの_searchエンドポイント、OpenSearch APIも複雑なクエリにPOSTを使う。リクエストボディにJSONを自由に含められるので現実的な解決策に見える。

しかしこの回避策には見えないコストがある。

第一に意味の汚染だ。POSTはHTTP仕様上「サーバー状態を変更しうる」動詞だ。データを読み取るだけの検索にPOSTを使うと、HTTPレイヤーでこのリクエストが読み取り専用かどうかわからなくなる。ミドルウェア、プロキシ、インフラ全体がこの意図を知らずに動作する。

第二にキャッシュ不可だ。HTTPの仕様上、POSTレスポンスはデフォルトでキャッシュできない。CDNやリバースプロキシは同じ検索クエリへのレスポンスを再利用できない。人気の検索語でもリクエストが毎回サーバーまで到達する。

第三に自動リトライ不可だ。ネットワークエラー発生時にHTTPクライアントとロードバランサーは冪等なリクエストのみを自動的にリトライする。POSTは冪等性が保証されないので、リトライするとサーバー状態が変わりうると判断される。読み取り専用のクエリでも安全にリトライされない。

まとめると、POSTによる回避は短期的な便利さのために、HTTPの意味論レイヤーが持つ3つの保証（安全性・冪等性・キャッシュ可能性）をすべて放棄する取引だ。そのコストはインフラの複雑化、無駄なサーバー負荷、デバッグの困難さとして返ってくる。

3. HTTP QUERYメソッドの設計 — 3つの保証の統合

RFC 10008が定義するQUERYメソッドの核心はシンプルだ。リクエストボディを許可しながら、同時に安全（safe）・冪等（idempotent）・キャッシュ可能（cacheable）の3属性をすべて保証する。

RFCの定義を直接引用すると：「A QUERY requests that the request target process the enclosed content in a safe and idempotent manner and then respond with the result of that processing.」（同封したコンテンツを安全かつ冪等な方法で処理し、その結果でレスポンスを返すよう要求する）

実際のリクエストは次の形式を取る。

QUERY /contacts HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json

{
  "filter": {
    "country": "JP",
    "tags": ["developer", "api"],
    "joined_after": "2025-01-01"
  },
  "sort": { "field": "name", "order": "asc" },
  "limit": 20
}

POSTと変わらないように見えるかもしれない。違いはHTTP動詞の名前自体ではなく、その名前がHTTPスタック全体に伝える意味シグナルにある。

3.1 安全性（Safe）

QUERYはサーバー状態を変更しないことを明示的に宣言する。ミドルウェア、モニタリング、APIゲートウェイがこのリクエストを副作用のない読み取り専用操作として扱える。人が見ても、インフラが見ても「これは検索だ」ということが明確だ。

3.2 冪等性（Idempotent）

同じQUERYを何度実行しても結果が変わらない。ネットワークエラー発生時にHTTPクライアントとロードバランサーが自動的にリトライできる。複雑な検索リクエストがネットワーク不安定で失敗しても、インフラが自動的に処理する。

3.3 キャッシュ可能性（Cacheable）

QUERYレスポンスはキャッシュできる。ただし、キャッシュキーにはURLだけでなくリクエストボディとContent-Typeメタデータを含める必要がある。同じエンドポイントでもボディが異なれば別のクエリだ。CDNとリバースプロキシがボディを含めてキーを構成すれば、人気のクエリへのレスポンスを再利用できる。サーバーはContent-Locationヘッダーでクエリ結果に安定したURIを割り当て、以降のGETリクエストでキャッシュされた結果を取得するパターンも支援する。

4. Accept-QUERYヘッダー — クエリ形式のネゴシエーション

RFC 10008はAccept-QUERYという新しいレスポンスヘッダーも導入する。サーバーが対応するクエリ形式（Content-Type）をクライアントに広告するためのヘッダーだ。例えば：

Accept-QUERY: application/json, application/x-www-form-urlencoded

クライアントはこのヘッダーを見てサーバーがどのクエリ構文を受け付けるかを把握し、それに合った形式でQUERYリクエストを送れる。これはRESTful APIでクエリ形式がサーバーごとにバラバラだった問題を標準化する。JSONフィルター、FIQL、GraphQLクエリなど様々な形式をサーバーが明示的に宣言できるようになる。

6. 実務活用 — どこで使うべきか

QUERYが威力を発揮するシナリオは明確だ。複雑なフィルターとクエリ条件があり、かつレスポンスのキャッシングが重要な検索APIだ。

6.1 適しているケース

複雑なREST検索APIが第一候補だ。商品検索、文書検索、ユーザーリストのフィルタリングなど条件が多く構造が複雑なクエリで、QUERYはURL長の心配なくJSONボディを使いながらキャッシュの恩恵も受けられる。GraphQLも候補だ。現在GraphQLはGETとPOSTを混用する非標準の方法を使っているが、クエリ実行にQUERYを使えば意味的に正しくキャッシュも可能になる。Elasticsearch・OpenSearchのような複雑なDSLクエリをボディで送るAPIもQUERYに切り替えれば、インフラレイヤーのキャッシュとリトライの恩恵を受ける。

6.2 QUERYを使うべきでないケース

URLで共有したりブックマークしたりする必要がある検索結果にはQUERYは適さない。シンプルな1〜2条件のフィルタはGETで十分だ。QUERYはGETが本当に限界に突き当たる箇所で使うべきだ。

7. 導入状況と現実的な障壁

RFCが公式化されたからといって、明日すぐに使えるわけではない。HTTPスタックの全レイヤーが新しいメソッドを理解する必要があり、その道のりは長い。

7.1 現在の導入状況（2026年6月時点）

APIクライアントツールKreyaはバージョン1.20でQUERYサポートを追加した。RFC共同著者がCloudflareとAkamaiに所属しているため、CDNレイヤーのサポートは比較的早く実現する見込みだ。しかしブラウザのfetch() APIでQUERYを使うにはWHATWG標準の議論とブラウザ実装が必要で、Express・FastAPI・Django・Springのような主要フレームワークのルーティングサポート、curl・axiosのようなHTTPクライアントライブラリのサポートも必要だ。ファイアウォールや一部のレガシープロキシはGET・POST・PUT・DELETE以外のメソッドをブロックすることがある。

7.2 長期的な展望

IETF標準の導入には時間がかかる。HTTP/2がRFC 7540として標準化されたのは2015年だが、完全な普及には数年かかった。QUERYもプロダクションスタック全体で標準として使われるまでには3〜5年を要するかもしれない。現実的な戦略は、クライアントとサーバーを両方直接制御できる新しい内部APIでQUERYを実験し、公開エンドポイントへの全面的な導入はクライアントライブラリとCDNのサポートが成熟してからにすることだ。

8. 結論 — HTTPの意味論を正しく使うということ

HTTP QUERYメソッドが解決する問題は技術的に複雑ではない。むしろ長い間放置されてきた単純な設計上の不一致だ。複雑な検索をGETのURLに詰め込んだり、読み取り専用クエリをPOSTで送る妥協は当面機能するが、インフラ全体に意味の汚染を広げる。QUERYはその妥協をなくす。

もちろんRFCが出たからといって「今日から使える」わけではない。スタック全体のサポートを待つ必要があり、ボディを含むキャッシュキー設計という新しい課題も受け入れなければならない。しかし方向は明確だ。複雑な検索APIのHTTP意味論を正しく表現する標準が生まれた。そのシグナルはすでにクライアントツールとCDNプロバイダーに届きつつある。

今日すぐできることは2つだ。現在POSTの回避策で運用している読み取り専用検索APIをリストアップして、QUERY移行候補を把握する。そして新しい内部API開発時にルーティングにQUERYを含めて、今から慣れておく。全面導入はエコシステムが成熟すれば自然についてくる。
