LEFT JOIN에 WHERE를 걸면 INNER JOIN이 된다 - ON과 WHERE의 경계

에러 없이 10행이 4행이 되는 버그를 SQLite에서 직접 실행해 재현하고, 언제 ON이고 언제 WHERE인지 가른다

2026-07-30 개발/인프라

서론: 매달 리포트 숫자가 조금씩 작았다

지역별 월간 리포트가 있었다. 매출 합계는 회계 쪽 숫자와 맞았다. 그런데 집계 대상 고객 수만 늘 조금 작았다. 에러 로그는 비어 있었고, 그 쿼리는 몇 달째 아무도 손대지 않은 자리에 있었다. 어떤 달에는 한 지역이 표에서 아예 사라져 있었지만, 그 지역은 매출이 0이었으므로 아무도 이상하게 여기지 않았다.

원인은 한 줄이었다. LEFT JOIN으로 고객 전체를 끌어온 다음, 그 아래에 WHERE o.status = 'paid'를 붙인 것. 이 한 줄이 LEFT JOIN을 INNER JOIN으로 바꿔 놓는다. 문법 오류가 아니다. 경고도 없다. 실행 시간도 오히려 빨라진다. 줄어드는 것은 행 수뿐이다.

이런 버그가 몇 달씩 사는 데는 이유가 있다.

  • 에러가 나지 않는다. 문법도 타입도 문제가 없으니 어떤 도구도 경고하지 않는다
  • 개발 데이터베이스에서는 재현되지 않는다. 시드 데이터는 관계가 촘촘해서 결측이 거의 없다. 결측이 없으면 LEFT와 INNER의 결과가 같다
  • 줄어든 쪽이 「없는 데이터」다. 화면에서 사라진 것은 값이 0이거나 비어 있던 행이므로 시각적으로 티가 나지 않는다
  • 합계는 맞는다. 금액을 더하는 지표는 그대로이고 개수를 세는 지표만 틀리기 때문에, 회계 대조로는 걸러지지 않는다

이 글은 조인 종류를 다시 설명하지 않는다. SQLite에 표 세 개를 만들고, 같은 쿼리를 조금씩 바꿔 가며 행 수를 하나하나 세었다. 아래에 나오는 모든 숫자와 출력은 그때 화면에 찍힌 그대로다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 엔진은 SQLite 3.49.1이고, 두 경로로 접근했다. 하나는 CPython 3.13.3의 sqlite3 모듈, 다른 하나는 Node.js v22.16.0에 내장된 node:sqlite다. 두 결과를 14절에서 대조했다.

스크립트는 모두 파일로 저장해 실행했다. 쿼리와 출력을 셸 인자로 주고받으면 인용 부호가 조용히 변형된다. 표와 데이터는 전부 가상의 customers, orders, shipments다.

이 글이 다루지 않는 것. 조인 종류 자체의 개론과 기본 문법은 SQL 입문 정리에 있다. 인덱스·잠금·N+1 같은 성능 주제는 운영 데이터베이스 생존 정리에서 다뤘다. 여기서는 ON과 WHERE의 경계 한 점만 파고든다.

1. 재현 - 10행이 4행이 되는 순간

이제 요구가 하나 들어온다. 「결제 완료된 주문만 보고 싶다」. 가장 자연스러운 손놀림은 쿼리 맨 아래에 한 줄을 붙이는 것이다.

10행에서 4행이 됐다. 그리고 바로 아래 INNER JOIN으로 다시 쓴 쿼리가 완전히 같은 4행을 돌려준다. 두 쿼리는 결과가 같다. 즉 위쪽 쿼리에서 LEFT라는 단어는 아무 일도 하지 않고 있다.

사라진 6행을 나눠 보면 성격이 다르다.

  • 2행은 의도된 제거다. 5번 고객의 pending, 6번 고객의 cancelled 주문. 결제 완료만 보자고 했으니 이건 맞다
  • 4행은 의도하지 않은 제거다. 7번부터 10번 고객. 이 사람들에게는 결제 완료 주문이 없는 게 아니라 주문 자체가 없다
  • 요구는 「결제 완료 주문만」이었지 「고객을 빼라」가 아니었다. 그런데 쿼리는 고객까지 뺐다
  • LEFT라는 단어가 쿼리에 그대로 남아 있다. 코드 리뷰에서 「LEFT JOIN이니 고객 전체가 나오겠지」라고 읽히고 넘어간다
  • 개발 DB에 주문 없는 고객이 없었다면 두 쿼리는 영원히 같은 결과를 낸다. 테스트로 잡을 수 없다

2. 같은 조건을 ON으로 옮기면

같은 조건을 WHERE가 아니라 ON 뒤에 AND로 붙이면 어떻게 되는지 본다. 글자 수는 비슷하고 조건식도 똑같다.

SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o
       ON c.customer_id = o.customer_id
      AND o.status = 'paid'
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ------
  1            Ada   101       paid
  2            Ben   102       paid
  3            Cara  103       paid
  4            Dan   104       paid
  5            Eve   NULL      NULL
  6            Finn  NULL      NULL
  7            Gus   NULL      NULL
  8            Hana  NULL      NULL
  9            Ivan  NULL      NULL
  10           Joy   NULL      NULL
  rows: 10

다시 10행이다. 그런데 1절의 첫 출력과는 내용이 다르다. 5번 고객의 pending 주문과 6번 고객의 cancelled 주문이 사라진 게 아니라 NULL로 바뀌었다. 고객은 남고, 조건에 맞지 않는 주문만 떨어져 나갔다.

행 수와 NULL 개수를 나란히 세면 세 쿼리의 차이가 한눈에 보인다.

--- row counts, five spellings of nearly the same query ---
  LEFT JOIN, no filter           : 10 rows
  LEFT JOIN + WHERE status=paid  :  4 rows
  LEFT JOIN + ON   status=paid   : 10 rows
  INNER JOIN + WHERE status=paid :  4 rows
  INNER JOIN + ON   status=paid  :  4 rows

--- how many NULL order_id survive in each ---
  LEFT JOIN, no filter          : 10 rows, 4 NULL order_id
  LEFT JOIN + WHERE status=paid :  4 rows, 0 NULL order_id
  LEFT JOIN + ON   status=paid  : 10 rows, 6 NULL order_id
  • WHERE 버전은 4행, NULL 오른쪽 행 0개. 결제 완료 주문이 있는 고객만 남았다
  • ON 버전은 10행, NULL 오른쪽 행 6개. 고객 전체가 남고 조건에 맞는 주문만 붙었다
  • NULL 행이 4개에서 6개로 늘어난 것이 핵심이다. 조건에 맞지 않는 주문 2건이 제거가 아니라 NULL 처리됐다
  • 어느 쪽이 옳은지는 쿼리가 답할 수 없다. 리포트가 무엇을 세려 했는지가 정한다

표로 정리하면 이렇다. 같은 조건식이 어디에 놓였는지가 결과의 의미를 바꾼다.

쿼리 형태행 수NULL 오른쪽 행실제로 물은 질문

마지막 두 행이 중요하다. INNER JOIN에서는 ON과 WHERE의 결과가 같다. 그래서 「조건은 ON에 쓰는 게 좋다」는 조언을 INNER JOIN에서 익힌 사람은 차이를 경험할 기회가 없다. 차이는 OUTER 조인에서만 드러난다.

3. 왜 그런가 - 조인이 먼저, WHERE가 나중

이유는 순서 하나로 설명된다. 조인이 먼저 일어나 중간 결과를 만들고, WHERE는 그 중간 결과에 걸린다. 그 중간 결과를 그대로 출력하고, 각 행이 WHERE를 통과하는지 옆에 적어 봤다.

--- the intermediate result, right after the join, before WHERE ---
  cid  name  order_id  status     -> does WHERE o.status=paid keep it?
  ---  ----  --------  ---------  --------------------------------------
  1    Ada   101       paid       KEEP
  2    Ben   102       paid       KEEP
  3    Cara  103       paid       KEEP
  4    Dan   104       paid       KEEP
  5    Eve   105       pending    DROP (not paid)
  6    Finn  106       cancelled  DROP (not paid)
  7    Gus   NULL      NULL       DROP (NULL = paid is NULL, not true)
  8    Hana  NULL      NULL       DROP (NULL = paid is NULL, not true)
  9    Ivan  NULL      NULL       DROP (NULL = paid is NULL, not true)
  10   Joy   NULL      NULL       DROP (NULL = paid is NULL, not true)
  join produced 10 rows, WHERE kept 4

NULL로 채워진 네 행이 어떻게 죽는지 마지막 열에 적혀 있다. 조인이 만들어 낸 NULL이, 바로 다음 단계의 WHERE에 걸려 그 행을 지운다. LEFT JOIN이 애써 남겨 놓은 행을 WHERE가 다시 버리는 구조다.

그 판정을 실제로 하는 것은 3값 논리다. 비교식 자체를 출력해 보면 이렇다.

SELECT NULL = 'paid'            AS null_eq_paid,
       NULL <> 'paid'           AS null_ne_paid,
       NULL IS NULL             AS null_is_null,
       (NULL = 'paid') IS NULL  AS comparison_is_null;

  null_eq_paid  null_ne_paid  null_is_null  comparison_is_null
  ------------  ------------  ------------  ------------------
  NULL          NULL          1             1
  rows: 1

-- a row survives WHERE only when the predicate evaluates to TRUE (1).
-- NULL = 'paid' is neither TRUE nor FALSE. It is NULL. So the row goes away.
-- NULL <> 'paid' does not rescue it either: that is NULL too.

NULL = 'paid'는 거짓이 아니라 NULL이다. WHERE는 결과가 참인 행만 남기므로, 참도 거짓도 아닌 행은 남지 않는다. 여기서 흔한 오해가 하나 갈린다. NULL <> 'paid'로 바꿔도 구제되지 않는다. 그것도 NULL이다.

두 절이 하는 일을 항목별로 갈라 놓으면 이렇게 된다. 이 표가 이 글의 뼈대다.

항목ONWHERE
평가 시점조인을 만드는 중조인이 끝난 뒤
정하는 것무엇을 짝지을 것인가짝지은 뒤 무엇을 남길 것인가

이 예제의 결과 행 수104

실행 계획LEFT-JOIN 표시가 남는다표시가 사라진다
  • ON은 짝짓기 규칙이다. 어떤 왼쪽 행과 어떤 오른쪽 행을 한 행으로 합칠지 정한다
  • LEFT는 구제 규칙이다. 짝을 못 찾은 왼쪽 행을 NULL로 채워 살려 둔다
  • WHERE는 선별 규칙이다. 위 두 규칙이 끝난 뒤에 남은 행 중에서 조건을 만족하는 것만 통과시킨다
  • 그래서 WHERE에 오른쪽 표 컬럼 조건을 쓰면 LEFT가 방금 구제한 행을 다시 지운다. 두 규칙이 정면으로 부딪친다
  • 왼쪽 표 컬럼 조건이라면 부딪치지 않는다. WHERE c.region = 'north'는 LEFT JOIN 성질을 그대로 두고 왼쪽만 좁힌다

PostgreSQL 공식 문서도 이 순서를 명시한다. 7.2.1.1 Joined Tables 절은 ON 절에 놓인 제약은 조인 전에 처리되고 WHERE 절에 놓인 제약은 조인 후에 처리되며, 이 차이는 내부 조인에서는 문제가 되지 않지만 외부 조인에서는 크게 문제가 된다고 적고 있다. 즉 이것은 특정 제품의 성질이 아니라 조인의 정의 자체다.

4. IS NULL이라는 예외 - 같은 WHERE인데 왜 이건 되는가

여기서 자연스러운 반문이 나온다. 「그러면 WHERE o.order_id IS NULL도 다 날아가야 하지 않나?」 실제로는 반대로 주문이 없는 고객만 남는다. 세 가지를 나란히 돌려 봤다.

-- 1. customers with no order at all
SELECT c.customer_id, c.name, o.order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL
ORDER BY c.customer_id;

  customer_id  name  order_id
  -----------  ----  --------
  7            Gus   NULL
  8            Hana  NULL
  9            Ivan  NULL
  10           Joy   NULL
  rows: 4

-- 2. ON filter + IS NULL = customers with no PAID order
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.status = 'paid'
WHERE o.order_id IS NULL
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ------
  5            Eve   NULL      NULL
  6            Finn  NULL      NULL
  7            Gus   NULL      NULL
  8            Hana  NULL      NULL
  9            Ivan  NULL      NULL
  10           Joy   NULL      NULL
  rows: 6

-- 3. orders.status is declared NOT NULL, yet IS NULL matches 4 rows
SELECT c.customer_id, c.name, o.status
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status IS NULL
ORDER BY c.customer_id;

  customer_id  name  status
  -----------  ----  ------
  7            Gus   NULL
  8            Hana  NULL
  9            Ivan  NULL
  10           Joy   NULL
  rows: 4

첫 번째가 4행이다. 원리는 앞과 완전히 같다. IS NULL은 NULL을 참으로 판정하는 유일한 종류의 조건이다. 그래서 조인이 만들어 낸 NULL 행이 WHERE를 통과하고, 오히려 매칭된 행들이 떨어진다. 이것이 anti-join이라고 불리는 관용구다.

두 번째가 훨씬 유용하다. 조건은 ON에, IS NULL은 WHERE에 두면 「결제 완료 주문이 하나도 없는 고객」 6명이 나온다. 앞의 4명과 다르다. 5번과 6번 고객은 주문은 있지만 결제 완료가 없어서 여기 들어온다.

세 번째 출력은 따로 기억해 둘 만하다.

  • IS NULL은 NULL에 참을 돌려주는 조건이다. 다른 비교 연산자는 모두 NULL을 돌려준다
  • 그래서 이 조건은 조인이 만든 NULL 행을 골라내는 데 쓰인다. 관용구이지 예외가 아니다
  • ON에 조건을 두고 WHERE ... IS NULL을 붙이면 「그 조건에 맞는 짝이 없는 왼쪽 행」이 나온다. 이 예제에서는 6행
  • ON에 조건을 두지 않으면 「짝이 아예 없는 왼쪽 행」이 나온다. 4행. 두 질문은 다르다
  • NOT NULL로 선언된 컬럼에 IS NULL을 걸어도 걸린다. 그 NULL은 표에 저장된 값이 아니라 조인이 만들어 낸 것이다

5. 집계와 만나면 - COUNT(o.order_id)와 COUNT(*)

집계가 붙으면 같은 함정이 다른 얼굴로 나타난다. 조인 결과에 GROUP BY를 걸고 두 가지 COUNT를 나란히 뽑았다.

SELECT c.customer_id, c.name,
       COUNT(*)          AS count_star,
       COUNT(o.order_id) AS count_order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
ORDER BY c.customer_id;

  customer_id  name  count_star  count_order_id
  -----------  ----  ----------  --------------
  1            Ada   1           1
  2            Ben   1           1
  3            Cara  1           1
  4            Dan   1           1
  5            Eve   1           1
  6            Finn  1           1
  7            Gus   1           0
  8            Hana  1           0
  9            Ivan  1           0
  10           Joy   1           0
  rows: 10

-- grand totals over exactly the same join
  count_star  count_order_id  count_status
  ----------  --------------  ------------
  10          6               6
  rows: 1

7번부터 10번 고객에서 두 값이 갈린다. COUNT(*)는 1, COUNT(o.order_id)는 0이다. 주문이 하나도 없는 고객의 주문 건수가 1로 보고되는 것이 이 절의 사고다. 이유는 단순하다. NULL로 채워진 행도 엄연히 한 행이고, COUNT(*)는 행을 센다.

합계 행에서도 같은 차이가 나온다. 전체 COUNT(*)는 10, COUNT(o.order_id)는 6이다. 10은 고객 수이고 6은 주문 수다. 둘 다 맞는 숫자이지만, 리포트 제목이 「주문 건수」라면 10은 틀린 값이다.

집계 함수별로 매칭이 없는 그룹에서 무엇이 나오는지 정리했다.

식매칭 없는 그룹의 값왜실무에서의 결과
COUNT(*)1NULL로 채워진 행도 한 행이다주문 0건이 1건으로 보고된다
COUNT(o.order_id)0NULL 인수는 세지 않는다보통 원하는 값
SUM(o.amount)NULL더할 값이 하나도 없다0이 아니다. 상위 계산으로 번진다
COALESCE(SUM(...), 0)0집계 결과를 치환한다권장 위치
AVG(o.amount)NULL분모가 0이다상위 평균의 분모가 줄어 값이 부풀려진다
  • COUNT(*)는 행을 센다. NULL로 채워진 행도 한 행이므로 매칭이 없는 그룹에서 1이 된다
  • COUNT(o.order_id)는 NULL이 아닌 값을 센다. 매칭이 없으면 0이다. 보통 원하는 값은 이쪽
  • 어떤 컬럼을 세는지도 중요하다. COUNT(o.status)도 6이 나왔다. 오른쪽 표의 아무 NOT NULL 컬럼이나 세면 된다
  • COUNT(DISTINCT c.customer_id)는 또 다른 값이다. 12절 리포트에서 이 함수가 지역별로 다른 답을 냈다

6. SUM이 0이 아니라 NULL이 되는 것

금액 쪽은 증상이 더 조용하다. 같은 컬럼을 네 가지 방식으로 합해 봤다.

SELECT c.customer_id, c.name,
       SUM(o.amount)              AS sum_raw,
       COALESCE(SUM(o.amount), 0) AS coalesce_outside,
       SUM(COALESCE(o.amount, 0)) AS coalesce_inside,
       TOTAL(o.amount)            AS sqlite_total
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
ORDER BY c.customer_id;

  customer_id  name  sum_raw  coalesce_outside  coalesce_inside  sqlite_total
  -----------  ----  -------  ----------------  ---------------  ------------
  1            Ada   120      120               120              120
  2            Ben   80       80                80               80
  3            Cara  45       45                45               45
  4            Dan   300      300               300              300
  5            Eve   60       60                60               60
  6            Finn  210      210               210              210
  7            Gus   NULL     0                 0                0
  8            Hana  NULL     0                 0                0
  9            Ivan  NULL     0                 0                0
  10           Joy   NULL     0                 0                0
  rows: 10

-- what those NULLs do one layer further out
  from SUM(o.amount)             : sum=815  avg=135.83  count=6
  from COALESCE(SUM(o.amount),0) : sum=815  avg= 81.50  count=10
-- the totals agree, the averages do not: AVG skipped the four NULL groups.

매칭이 없으면 SUM은 0이 아니라 NULL이다. 더할 값이 하나도 없기 때문이다. 이 NULL은 그 자리에서는 별 해가 없어 보인다. 문제는 한 층 밖으로 나갈 때 생긴다.

같은 데이터인데 평균이 135.83과 81.50으로 갈렸다. 합계는 둘 다 815로 같다. AVG가 NULL 그룹을 세지 않아 분모가 6과 10으로 달라진 것이다. 「고객당 평균 구매액」 같은 지표가 이 지점에서 조용히 부풀려진다.

COALESCE를 어디에 씌우느냐도 실제로 확인했다.

  • COALESCE(SUM(o.amount), 0) - 집계 결과에 씌운다. 그룹 전체가 비었을 때 0을 만든다. 이것이 보통 원하는 자리
  • SUM(COALESCE(o.amount, 0)) - 집계 전에 씌운다. 이 예제에서는 결과가 같지만, 의미가 다르다. NULL 금액이 실제로 저장돼 있는 경우에 갈린다
  • SQLite에는 TOTAL()이 있어 빈 그룹에도 0을 돌려준다. 다른 엔진에는 없는 함수이므로 이식성 있는 쿼리에는 쓰지 않는다
  • NULL을 그대로 밖으로 내보내면 상위 집계가 조용히 틀린다. 합계는 맞고 평균만 틀리는 조합이 특히 위험하다
  • 리포트 컬럼 하나마다 「이 값이 NULL일 수 있는가」를 한 번 물어보는 것으로 대부분 막힌다

7. 조인 세 개를 연쇄하면 - 가운데 조건이 뒤쪽까지 죽인다

표가 세 개로 늘면 함정도 전파된다. 고객에서 주문으로, 주문에서 배송으로 두 번 LEFT JOIN한다.

SELECT c.customer_id, c.name, o.order_id, o.status, s.carrier
FROM customers c
LEFT JOIN orders    o ON c.customer_id = o.customer_id
LEFT JOIN shipments s ON o.order_id    = s.order_id
ORDER BY c.customer_id;

  customer_id  name  order_id  status     carrier
  -----------  ----  --------  ---------  -------
  1            Ada   101       paid       ACME
  2            Ben   102       paid       ACME
  3            Cara  103       paid       NULL
  4            Dan   104       paid       BOLT
  5            Eve   105       pending    NULL
  6            Finn  106       cancelled  ACME
  7            Gus   NULL      NULL       NULL
  8            Hana  NULL      NULL       NULL
  9            Ivan  NULL      NULL       NULL
  10           Joy   NULL      NULL       NULL
  rows: 10

10행이다. 3번 고객은 주문은 있지만 배송이 없어 carrier만 NULL이고, 7번부터 10번은 주문부터 없어 뒤쪽이 전부 NULL이다. 층마다 결측이 다른 위치에 생기는 것이 이 구조의 특징이다.

이제 조건을 두 위치에 각각 걸어 본다. 하나는 마지막 표에, 하나는 가운데 표에.

-- filter on the LAST table
... LEFT JOIN shipments s ON o.order_id = s.order_id
WHERE s.carrier = 'ACME';

  customer_id  name  order_id  status     carrier
  -----------  ----  --------  ---------  -------
  1            Ada   101       paid       ACME
  2            Ben   102       paid       ACME
  6            Finn  106       cancelled  ACME
  rows: 3

-- filter on the MIDDLE table
... LEFT JOIN shipments s ON o.order_id = s.order_id
WHERE o.status = 'paid';

  customer_id  name  order_id  status  carrier
  -----------  ----  --------  ------  -------
  1            Ada   101       paid    ACME
  2            Ben   102       paid    ACME
  3            Cara  103       paid    NULL
  4            Dan   104       paid    BOLT
  rows: 4

마지막 표에 조건을 걸면 10행에서 3행이 된다. 배송이 없던 3번 고객과 주문이 없던 네 명이 한꺼번에 사라졌다. 즉 조건을 뒤쪽에 걸면 앞쪽의 LEFT JOIN 두 개가 동시에 무력화된다.

가운데 표에 조건을 걸면 4행이다. 그런데 이쪽에는 다른 손실이 하나 더 있다. 6번 고객의 취소된 주문에는 배송 기록이 있었는데, 주문이 걸러지면서 그 배송 기록까지 결과에서 사라졌다. 조건을 걸지 않은 표의 데이터가 없어진 것이다.

두 조건을 모두 ON으로 옮기면 어떻게 되는지 본다.

SELECT c.customer_id, c.name, o.order_id, o.status, s.carrier
FROM customers c
LEFT JOIN orders    o ON c.customer_id = o.customer_id AND o.status  = 'paid'
LEFT JOIN shipments s ON o.order_id    = s.order_id    AND s.carrier = 'ACME'
ORDER BY c.customer_id;

  customer_id  name  order_id  status  carrier
  -----------  ----  --------  ------  -------
  1            Ada   101       paid    ACME
  2            Ben   102       paid    ACME
  3            Cara  103       paid    NULL
  4            Dan   104       paid    NULL
  5            Eve   NULL      NULL    NULL
  6            Finn  NULL      NULL    NULL
  7            Gus   NULL      NULL    NULL
  8            Hana  NULL      NULL    NULL
  9            Ivan  NULL      NULL    NULL
  10           Joy   NULL      NULL    NULL
  rows: 10

10행이 그대로 유지된다. 4번 고객은 결제 완료 주문이 남았지만 배송사가 다르므로 carrier만 NULL이 됐다. 층별 조건이 각각 자기 층에서만 작동한다. 이것이 「없는 것도 보고 싶다」는 의도를 세 표에 걸쳐 지키는 방법이다.

  • 조건은 자기 층에만 걸어야 한다. 뒤쪽 표 조건을 WHERE에 두면 앞쪽 LEFT JOIN까지 함께 무력화된다
  • 연쇄가 길어지면 피해도 커진다. 세 표 조인에서 마지막 표 조건 하나가 10행을 3행으로 만들었다
  • 조건을 걸지 않은 표의 데이터까지 사라진다. 가운데 표를 거르면 그 표에 매달린 뒤쪽 행도 함께 없어진다
  • ON으로 옮기면 층별로 독립한다. 4번 고객처럼 앞 층은 통과하고 뒤 층에서만 NULL이 되는 행이 나온다
  • 연쇄 조인은 프로브를 층마다 돌려야 한다. 어느 층에서 행이 줄었는지 층별 COUNT로 좁히는 것이 빠르다

8. RIGHT JOIN과 FULL OUTER JOIN - 방향만 바뀐 같은 함정

방향을 바꿔도 같은 일이 일어나는지 확인했다. SQLite는 RIGHT JOIN과 FULL OUTER JOIN을 3.39.0(2022년 6월 25일 릴리스)에서 추가했고, 이 환경은 3.49.1이므로 둘 다 실행된다.

고객 표에 없는 고객 번호를 가진 주문 하나를 넣어 방향별 차이를 뚜렷하게 만들었다.

--- SQLite 3.49.1, same data ---
  RIGHT JOIN, no filter        : 10 rows
  RIGHT JOIN + WHERE           :  4 rows
  FULL OUTER JOIN, no filter   : 10 rows
  FULL OUTER JOIN + WHERE      :  4 rows

--- now insert one orphan order (customer_id 99 does not exist) ---
INSERT INTO orders VALUES (107, 99, 'paid', 500.0, '2026-07-25');

  LEFT JOIN             : 10 rows   <- orphan invisible
  RIGHT JOIN            :  7 rows   <- 6 orders + orphan, customers 7-10 gone
  FULL OUTER JOIN       : 11 rows   <- 10 customers + orphan
  FULL OUTER + WHERE o  :  5 rows   <- WHERE on the right table
  FULL OUTER + WHERE c  :  3 rows   <- WHERE on the LEFT table also collapses it

FULL OUTER JOIN에서는 어느 쪽 조건이든 붕괴를 일으킨다. 오른쪽 표 조건을 WHERE에 두면 11행이 5행, 왼쪽 표 조건을 두면 11행이 3행이 됐다. 양쪽을 다 보존하는 조인이므로 양쪽 모두 취약하다.

방향별로 정리하면 이렇다.

조인보존되는 쪽오른쪽 표 조건을 WHERE에 두면이 환경의 지원
LEFT [OUTER] JOIN왼쪽내부 조인이 된다 (10 → 4)전 버전
RIGHT [OUTER] JOIN오른쪽내부 조인이 된다 (10 → 4)3.39.0(2022-06-25) 이후
FULL OUTER JOIN양쪽어느 쪽 조건이든 붕괴 (11 → 5, 11 → 3)3.39.0 이후
INNER JOIN없음아무 일도 일어나지 않는다전 버전
  • RIGHT JOIN은 방향만 반대다. 오른쪽 표를 보존하고, 왼쪽 표 컬럼 조건을 WHERE에 두면 같은 붕괴가 일어난다
  • FULL OUTER JOIN은 양쪽 다 취약하다. 어느 표의 컬럼이든 WHERE에 오면 그 쪽 보존이 깨진다
  • 고아 행을 하나 넣어 보면 방향별 차이가 뚜렷하다. LEFT는 10행으로 고아를 못 보고, RIGHT는 7행으로 고객 4명을 못 본다
  • SQLite에서 이 두 조인은 3.39.0 이후에만 쓸 수 있다. 오래된 빌드가 섞인 환경이라면 버전을 먼저 확인해야 한다

9. 실행 계획이 말해 주는 것

옵티마이저가 이 변환을 실제로 수행하는지, EXPLAIN QUERY PLAN으로 확인했다.

EXPLAIN QUERY PLAN <query>;

-- 1. LEFT JOIN, no filter
   SCAN c
   BLOOM FILTER ON o (customer_id=?)
   SEARCH o USING AUTOMATIC COVERING INDEX (customer_id=?) LEFT-JOIN

-- 2. LEFT JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

-- 3. LEFT JOIN + ON ... AND o.status = 'paid'
   SCAN c
   BLOOM FILTER ON o (status=? AND customer_id=?)
   SEARCH o USING AUTOMATIC PARTIAL COVERING INDEX (status=? AND customer_id=?) LEFT-JOIN

-- 4. INNER JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

2번과 4번의 계획이 완전히 같다. LEFT JOIN에 WHERE를 붙인 것과 처음부터 INNER JOIN으로 쓴 것이 글자 단위로 동일한 실행 계획을 만들었다. 그리고 결정적으로, 1번과 3번에 있던 LEFT-JOIN 표시가 2번에서는 사라졌다.

구동 순서도 뒤집혔다. 1번과 3번은 SCAN c로 고객부터 훑지만, 2번과 4번은 SCAN o로 주문부터 훑는다. 고객 전체를 보존해야 한다는 제약이 없어졌으니 더 작은 표부터 도는 것이 유리하다고 판단한 것이다. 인덱스를 만들어도 결론은 같았다.

CREATE INDEX idx_orders_customer ON orders(customer_id);

-- LEFT JOIN, no filter
   SCAN c
   SEARCH o USING COVERING INDEX idx_orders_customer (customer_id=?) LEFT-JOIN

-- LEFT JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

-- INNER JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

실무에서 이 출력을 쓰는 법은 간단하다.

  • LEFT-JOIN 표시가 계획에 남아 있는지 본다. 사라졌다면 옵티마이저가 이미 내부 조인으로 취급하고 있다는 뜻이다
  • 구동 표가 바뀌었는지 본다. 왼쪽 표부터 훑던 계획이 오른쪽 표부터 훑도록 뒤집히면 보존 제약이 없어졌다는 신호다
  • INNER JOIN으로 고쳐 쓴 쿼리의 계획과 비교한다. 두 계획이 같으면 두 쿼리는 같은 쿼리다
  • 이 확인은 데이터를 건드리지 않으므로 운영 데이터베이스에서도 안전하게 돌릴 수 있다

10. OUTER 키워드, USING, 그리고 상수 조건

주변 문법도 함께 확인했다. 먼저 OUTER 키워드가 무엇을 바꾸는가.

--- does the OUTER keyword change anything ---
  LEFT JOIN       rows: 10
  LEFT OUTER JOIN rows: 10
  result sets identical : True
  query plans identical : True

--- the inner-join spellings, same data ---
  JOIN        :  6 rows
  INNER JOIN  :  6 rows
  CROSS JOIN  :  6 rows   (SQLite accepts ON after CROSS JOIN)
  comma join  :  6 rows   (FROM customers c, orders o WHERE c.customer_id=o.customer_id)

아무것도 바꾸지 않는다. 결과 집합이 같고 실행 계획 문자열까지 같다. OUTER는 선택 키워드이고, LEFT JOIN은 이미 외부 조인이다. 반대로 JOIN, INNER JOIN, 쉼표 조인은 전부 6행으로 같았다.

USING 절도 같은 함정을 그대로 가진다.

SELECT customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o USING (customer_id)
ORDER BY customer_id;
  rows: 10

-- append the filter to WHERE and the same collapse happens
LEFT JOIN orders o USING (customer_id) WHERE o.status = 'paid'
  rows: 4

-- there is no place to put an extra predicate inside USING
LEFT JOIN orders o USING (customer_id) AND o.status = 'paid'
  ERROR: near "AND": syntax error

-- which side does the merged column come from on an unmatched row?
SELECT customer_id, c.customer_id AS from_left, o.customer_id AS from_right
FROM customers c LEFT JOIN orders o USING (customer_id)
WHERE o.order_id IS NULL;

  customer_id  from_left  from_right
  -----------  ---------  ----------
  7            7          NULL
  8            8          NULL
  9            9          NULL
  10           10         NULL
  rows: 4

두 가지가 눈에 띈다. 하나는 WHERE를 붙였을 때 역시 4행으로 줄었다는 것. 다른 하나는 USING에는 추가 조건을 넣을 자리가 없다는 것이다. AND를 붙이면 구문 오류가 난다. 즉 USING을 쓰는 순간 「조건을 ON으로 옮긴다」는 선택지가 사라진다. 조건을 살리려면 ON으로 바꿔 쓰거나 서브쿼리로 빼야 한다.

두 절의 역할 차이를 가장 선명하게 보여 주는 것은 상수 조건이다.

--- constant predicates, to isolate what each clause does ---
  ON c.customer_id=o.customer_id AND 1=1  : 10 rows
  ON c.customer_id=o.customer_id AND 1=0  : 10 rows   <- still 10
  ON 1=1 (no join key at all)             : 60 rows   <- 10 x 6 cartesian
  WHERE 1=1                               : 10 rows
  WHERE 1=0                               :  0 rows   <- everything gone
  WHERE c.region='north' (LEFT table!)    :  3 rows

--- ON ... AND 1=0 keeps every left row and nulls the right side ---
  customer_id  name  order_id
  -----------  ----  --------
  1            Ada   NULL
  2            Ben   NULL
  3            Cara  NULL
  ...
  10           Joy   NULL
  rows: 10

ON ... AND 1=0은 10행을 그대로 유지한다. 짝이 하나도 안 지어지지만 왼쪽 행은 전부 남고 오른쪽만 NULL이 된다. 반면 WHERE 1=0은 0행이다. 같은 거짓 조건이 한쪽에서는 「짝짓지 말라」로, 다른 쪽에서는 「전부 버려라」로 읽힌다.

  • OUTER는 있으나 없으나 같다. 결과 집합과 실행 계획이 모두 동일했다
  • JOIN, INNER JOIN, 쉼표 조인은 전부 같은 6행. SQLite에서는 CROSS JOIN에도 ON을 붙일 수 있었고 결과가 같았다
  • USING은 추가 조건을 받을 문법 자리가 없다. 조건을 ON으로 옮기는 대안이 막히므로, 조건이 붙을 조인에는 처음부터 ON을 쓰는 편이 낫다
  • USING으로 합쳐진 컬럼은 매칭이 없는 행에서 왼쪽 값을 돌려줬다. 그래서 그 컬럼으로는 결측 판정을 할 수 없다. 결측 판정에는 오른쪽 표의 다른 컬럼을 써야 한다
  • ON ... AND 1=0과 WHERE 1=0의 차이가 두 절의 역할 차이를 그대로 보여 준다. 10행과 0행이다

11. 서브쿼리와 CTE로 미리 거르기

조건이 길어지면 ON 절이 읽기 어려워진다. 대안은 조건을 서브쿼리나 CTE 안으로 넣고 그 결과를 조인하는 것이다.

SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN (SELECT * FROM orders WHERE status = 'paid') o
       ON c.customer_id = o.customer_id
ORDER BY c.customer_id;
  rows: 10

--- three spellings that must agree, and do ---
  ON       : 10 rows
  subquery : 10 rows
  CTE      : 10 rows
  all three identical : True

--- and four that are not the same thing ---
  WHERE o.status='paid'                        :  4 rows
  WHERE o.status='paid' OR o.order_id IS NULL  :  8 rows
  EXISTS (paid order)                          :  4 rows
  NOT EXISTS (paid order)                      :  6 rows

세 표기가 모두 10행이고 값까지 같았다. 스크립트에서 결과 집합을 직접 비교해 동일 판정을 받았다. 조건이 여러 개거나 서브쿼리 안에서 집계까지 해야 할 때는 이 형태가 읽기 쉽다.

아래 네 줄은 서로 다른 질문이라는 점을 분명히 해 둔다.

  • ON, 서브쿼리, CTE 세 표기의 결과가 같다. 읽기 좋은 쪽을 고르면 된다
  • 조건이 세 개 이상이거나 서브쿼리 안에서 집계까지 해야 하면 CTE가 압도적으로 읽기 쉽다
  • WHERE ... OR ... IS NULL은 ON으로 옮긴 것과 같지 않다. 8행이 나왔다. 조건에 맞지 않는 짝을 가진 행이 되살아난다
  • 「있는지만 알면 된다」면 EXISTS가 더 정확하다. 조인은 행을 늘릴 수 있지만 EXISTS는 늘리지 않는다

12. 날짜 범위 조건에서 유독 잦은 이유

이 버그가 유독 자주 나는 자리가 있다. 날짜 범위 조건이다. 월간·주간 리포트는 거의 예외 없이 기간 조건을 갖고 있고, 그 조건이 붙는 표는 거의 항상 오른쪽 표다.

--- a date range is the most common way to trip this ---
  no filter                                     : 10 rows
  WHERE o.ordered_at >= '2026-07-01'            :  5 rows
  ON ... AND o.ordered_at >= '2026-07-01'       : 10 rows
  WHERE o.ordered_at BETWEEN Jul01 AND Jul31    :  5 rows
  WHERE (o.ordered_at >= Jul01 OR o.id IS NULL) :  9 rows

-- the WHERE version drops two different populations at once:
--   the 4 customers with no order, and the 1 customer whose only order is from June.
-- the OR ... IS NULL version brings back the 4 but still hides the June customer.

WHERE 버전은 두 종류의 행을 한꺼번에 버린다. 주문이 아예 없는 고객 4명과, 유일한 주문이 6월이라 범위를 벗어난 고객 1명이다. 앞의 4명은 그래도 눈치챌 여지가 있지만, 뒤의 1명은 「이 달에 활동이 없었던 고객」이라서 발견이 훨씬 어렵다.

흔히 쓰이는 우회책인 OR ... IS NULL도 절반만 듣는다. 9행이 나왔다. 주문이 없는 4명은 돌아왔지만 6월 주문 고객은 여전히 빠져 있다. 조건을 ON으로 옮기는 것과 같지 않다.

실제 리포트 형태로 만들어 두 버전을 나란히 돌렸다. 서론에서 말한 증상이 여기서 그대로 재현된다.

-- the report, WHERE version
SELECT c.region,
       COUNT(DISTINCT c.customer_id) AS customers_in_report,
       COALESCE(SUM(o.amount), 0)    AS revenue
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = 'paid'
GROUP BY c.region ORDER BY c.region;

  region  customers_in_report  revenue
  ------  -------------------  -------
  east    1                    300
  north   2                    165
  south   1                    80
  rows: 3

-- the report, ON version
LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.status = 'paid'

  region  customers_in_report  revenue
  ------  -------------------  -------
  east    2                    300
  north   3                    165
  south   3                    80
  west    2                    0
  rows: 4

-- revenue per region is identical. the customer counts are not,
-- and the whole 'west' region is missing from the first report.

지역별 매출은 두 버전이 완전히 같다. 그래서 회계 검증을 통과한다. 다른 것은 고객 수다. north가 2와 3, south가 1과 3으로 갈린다. 그리고 west 지역은 WHERE 버전에서 표에 아예 없다. 매출이 0인 지역이 사라진 것을 리포트를 보는 사람이 알아채기는 어렵다.

  • 기간 조건은 거의 항상 오른쪽 표에 있다. 고객은 기간이 없고 주문에는 있다. 그래서 리포트 쿼리는 구조적으로 이 함정에 노출된다
  • 없어지는 쪽이 두 종류다. 아예 짝이 없는 행과, 짝은 있지만 기간을 벗어난 행. 후자가 훨씬 찾기 어렵다
  • OR ... IS NULL은 부분적인 우회다. 짝이 없는 행은 되살리지만 기간 밖 행은 여전히 숨긴다
  • 금액 합계는 두 버전이 같다. 그래서 회계 대조를 통과한다. 갈리는 것은 개수 지표뿐이다
  • 매출 0인 분류가 표에서 통째로 빠진다. 이 예제에서는 west 지역이 사라졌다. 없는 행을 알아채는 사람은 드물다

13. 진단법 - 이미 배포된 쿼리에서 찾아내기

이제 반대 방향이다. 이미 돌고 있는 쿼리에서 이 버그를 찾아내야 한다. 세 단계로 나눴다.

--- probe 1. how many rows does the WHERE remove? ---
  driving table rows       : 10
  after LEFT JOIN          : 10
  after WHERE              : 4
  lost by the WHERE clause : 6  (60%)

--- probe 2. unmatched ratio, straight from the join ---
SELECT COUNT(*)                                           AS joined_rows,
       SUM(CASE WHEN o.order_id IS NULL THEN 1 ELSE 0 END) AS unmatched_rows,
       ROUND(100.0 * SUM(CASE WHEN o.order_id IS NULL THEN 1 ELSE 0 END)
             / COUNT(*), 1)                               AS unmatched_pct
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;

  joined_rows  unmatched_rows  unmatched_pct
  -----------  --------------  -------------
  10           4               40
  rows: 1

--- probe 3. the one that settles it ---
SELECT (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
          ON c.customer_id=o.customer_id)                        AS rows_join_only,
       (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
          ON c.customer_id=o.customer_id WHERE o.status='paid')  AS rows_with_where,
       (SELECT COUNT(*) FROM customers c JOIN      orders o
          ON c.customer_id=o.customer_id WHERE o.status='paid')  AS rows_if_inner;

  rows_join_only  rows_with_where  rows_if_inner
  --------------  ---------------  -------------
  10              4                4
  rows: 1

-- rows_with_where equals rows_if_inner -> the word LEFT is doing nothing.

세 번째 프로브가 판정을 끝낸다. rows_with_where와 rows_if_inner가 같으면, 그 쿼리의 LEFT는 장식이다. 같은 값이 나왔다는 것은 왼쪽 표를 보존하려는 의도가 실행되지 않고 있다는 뜻이다.

두 번째 프로브의 unmatched_pct도 함께 봐야 한다. 이 예제에서는 40퍼센트였다. 개발 DB에서 이 값이 0이면 그곳에서는 버그가 절대 재현되지 않는다. 결측이 적은 데이터로 검증했기 때문에 통과한 쿼리가, 결측이 많은 운영 데이터에서만 틀린 값을 낸다.

연쇄 조인에도 같은 프로브가 그대로 통한다. 그리고 코드베이스 전체를 훑을 때는 두 단계로 좁힌다.

--- same probe on the three-table chain ---
  rows_join_only  rows_with_where  rows_if_inner
  --------------  ---------------  -------------
  10              3                3
  rows: 1

--- grep patterns for a code review sweep ---
# every LEFT JOIN in the repository, with the ten lines that follow it
grep -rn -A 10 -i 'left join' --include='*.sql' --include='*.py' .

# LEFT JOIN and WHERE in the same statement, single-line queries
grep -rn -iE 'left[[:space:]]+(outer[[:space:]]+)?join.*where' .

--- what to look at once you have the hits ---
# 1. does the WHERE mention an alias that is introduced by a LEFT JOIN?
# 2. if yes, is the predicate an IS NULL check? then it is intentional.
# 3. anything else -> run probe 3 above and compare the two numbers.

절차로 정리하면 이렇다.

확인할 것방법판정
WHERE가 오른쪽 별칭을 언급하는가쿼리 텍스트를 읽는다언급하면 후보
그 조건이 IS NULL인가조건 형태를 본다IS NULL이면 의도된 anti-join
조인 직후 행 수WHERE를 지우고 COUNT(*)기준값
WHERE 적용 후 행 수원본 그대로 COUNT(*)감소분이 결측 규모
INNER로 바꾼 행 수LEFT를 지우고 COUNT(*)WHERE 결과와 같으면 확정
  • 1단계. WHERE 절이 LEFT JOIN으로 들어온 별칭을 언급하는지 본다. 언급하지 않으면 이 버그가 아니다
  • 2단계. 언급한다면 그 조건이 IS NULL인지 본다. IS NULL이면 의도된 anti-join일 가능성이 높다
  • 3단계. 그 밖의 경우에는 프로브 3을 돌려 rows_with_where와 rows_if_inner를 비교한다. 같으면 확정이다
  • 결측 비율을 함께 기록한다. 0퍼센트인 환경에서는 이 버그가 재현되지 않으므로, 검증은 운영과 비슷한 데이터에서 해야 한다
  • 고칠 때는 둘 중 하나를 고르는 것이다. 조건을 ON으로 옮기거나, LEFT를 지워 INNER로 명시하거나. 애매하게 남겨 두는 것이 최악이다

15. 판단 표 - 의도에서 시작한다

결론은 「조건을 ON에 쓰세요」가 아니다. 두 절은 하는 일이 다르고, 그래서 각각 맞는 자리가 있다. 정하는 순서는 문법이 아니라 의도다. 하려는 말을 먼저 문장으로 만들고, 그 문장에 맞는 절을 고르면 된다.

하려는 말어느 절에 쓰는가이 예제의 행 수확인 방법
조건에 맞는 것만 보겠다WHERE + INNER JOIN으로 명시4결과에 NULL 오른쪽 행이 없어야 한다
없는 것도 0으로 보고 싶다ON10결과 행 수가 왼쪽 표 행 수와 같아야 한다
조건에 맞는 짝이 없는 쪽만 보겠다ON + WHERE ... IS NULL6오른쪽 컬럼이 전부 NULL이어야 한다
짝이 아예 없는 쪽만 보겠다WHERE ... IS NULL4NOT EXISTS와 행 수가 같아야 한다
왼쪽 표를 좁히겠다WHERE (왼쪽 표 컬럼)3NULL 오른쪽 행이 그대로 남아 있어야 한다
조건이 길어 읽기 어렵다서브쿼리 또는 CTE로 분리10ON 버전과 행 수·값이 일치해야 한다

표를 쓸 때의 기준을 한 줄로 줄이면 이렇다.

  • 「없는 것도 0으로 보고 싶다」면 ON이다. 결과 행 수가 왼쪽 표 행 수와 같아야 한다
  • 「있는 것만 보겠다」면 WHERE다. 다만 그때는 LEFT를 지우고 INNER JOIN으로 적는다. 의도가 코드에 남는다
  • 「조건에 맞는 짝이 없는 쪽만 보겠다」면 ON + WHERE ... IS NULL이다. 두 절을 함께 쓰는 유일하게 흔한 경우다
  • 왼쪽 표를 좁히는 조건은 WHERE에 그대로 둔다. LEFT JOIN 성질과 충돌하지 않는다
  • 어느 쪽인지 모르겠으면 두 버전을 다 돌려 행 수를 비교한다. 숫자를 보면 무엇을 물었는지 알게 된다

16. 체크리스트와 하지 말 것

리뷰와 자기 점검에 쓸 목록이다.

  • 리포트 쿼리마다 WHERE 절이 언급하는 별칭이 어느 조인에서 왔는지 확인했다
  • LEFT JOIN을 쓴 쿼리에서 결과 행 수가 왼쪽 표 행 수와 같은지 한 번 세어 봤다
  • 결측 비율이 0이 아닌 데이터로 검증했다. 시드 데이터만으로 통과시키지 않았다
  • COUNT(*)를 개수 지표에 그대로 쓰지 않았다. 오른쪽 표 컬럼을 세었다
  • SUM 결과에 COALESCE를 씌울지 한 번 판단했다. 상위 집계로 NULL을 흘리지 않았다
  • 조건을 WHERE에 두기로 했다면 LEFT를 지워 INNER로 적었다. 다음 사람이 오해하지 않게 했다

반대로 하지 말 것.

  • LEFT JOIN 아래에 오른쪽 표 조건을 WHERE로 붙이는 것 - 의도가 있다면 INNER로 적는다
  • 「LEFT JOIN이니 왼쪽은 다 나온다」고 읽고 넘어가는 것 - 아래 WHERE를 먼저 본다
  • 결측 없는 시드 데이터로 리포트 쿼리를 검증하는 것 - 그 환경에서는 이 버그가 재현되지 않는다
  • 행 수를 세지 않고 「줄어든 것 같다」로 보고하는 것 - 숫자 두 개를 나란히 적는다
  • OR ... IS NULL을 ON과 같은 것으로 취급하는 것 - 8행과 10행은 다른 결과다
  • USING을 쓴 조인에 조건을 붙이려 하는 것 - 문법 자리가 없다. ON으로 바꿔 쓴다

# LEFT JOIN + WHERE 함정 — 판단표·진단 SQL·재현 데이터

> 출처: braindetox.kr — LEFT JOIN에 WHERE를 걸면 INNER JOIN이 된다
> 근거: Windows 10 / SQLite 3.49.1 (CPython 3.13.3 sqlite3, Node.js v22.16.0 node:sqlite) 실행 검증
> 이 파일을 그대로 AI에 붙여 「이 기준으로 우리 리포트 쿼리를 점검해줘」라고 쓰면 됩니다.
> ⚠ 이 버그는 에러를 내지 않습니다. 행 수만 줄어들고, 결측이 적은 개발 DB에서는 재현되지 않습니다.

## 0. 한 문장 요약

**ON은 「무엇을 짝지을 것인가」, WHERE는 「짝지은 뒤 무엇을 남길 것인가」.**
조인이 먼저 일어나 NULL 행을 만들고, WHERE가 그 NULL을 검사해 행을 지운다. 그래서 오른쪽 표의 컬럼 조건을 WHERE에 두면 LEFT JOIN이 INNER JOIN이 된다.

## 1. 판단표 — 의도에서 시작한다

| 하려는 말 | 어느 절에 쓰는가 | 예제 행 수 | 확인 방법 |
|---|---|---|---|
| 조건에 맞는 것만 보겠다 | `WHERE` + `INNER JOIN`으로 명시 | 4 | 결과에 NULL 오른쪽 행이 없어야 한다 |
| 없는 것도 0으로 보고 싶다 | `ON ... AND` | 10 | 결과 행 수 = 왼쪽 표 행 수 |
| 조건에 맞는 짝이 없는 쪽만 | `ON` + `WHERE ... IS NULL` | 6 | 오른쪽 컬럼이 전부 NULL |
| 짝이 아예 없는 쪽만 | `WHERE ... IS NULL` | 4 | `NOT EXISTS`와 행 수 일치 |
| 왼쪽 표를 좁히겠다 | `WHERE` (왼쪽 표 컬럼) | 3 | NULL 오른쪽 행이 그대로 남는다 |
| 조건이 길어 읽기 어렵다 | 서브쿼리 또는 CTE로 분리 | 10 | ON 버전과 행 수·값 일치 |

## 2. 두 절이 하는 일

| 항목 | `ON` | `WHERE` |
|---|---|---|
| 평가 시점 | 조인을 만드는 중 | 조인이 끝난 뒤 |
| 정하는 것 | 무엇을 짝지을 것인가 | 짝지은 뒤 무엇을 남길 것인가 |
| 짝이 없는 왼쪽 행 | NULL로 채워 남긴다 | 조건 불만족이면 버린다 |
| 내부 조인에서의 차이 | 없다 | 없다 |
| 실행 계획 | `LEFT-JOIN` 표시가 남는다 | 표시가 사라진다 |

## 4. 네 가지 쓰기와 실제 행 수 (검증됨)

```sql
-- 10행
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id;

-- 4행  <- LEFT가 죽는다
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = 'paid';

-- 10행 <- 의도대로
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c LEFT JOIN orders o
  ON c.customer_id = o.customer_id AND o.status = 'paid';

-- 6행  <- 결제 완료 주문이 하나도 없는 고객
SELECT c.customer_id, c.name
FROM customers c LEFT JOIN orders o
  ON c.customer_id = o.customer_id AND o.status = 'paid'
WHERE o.order_id IS NULL;
```

## 5. 진단 SQL 모음 — 이미 배포된 쿼리 판정

```sql
-- 프로브 1. 조인 직후 / WHERE 적용 후 / INNER로 바꿨을 때, 세 행 수를 한 번에
SELECT
  (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
     ON c.customer_id = o.customer_id)                          AS rows_join_only,
  (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
     ON c.customer_id = o.customer_id WHERE o.status = 'paid')  AS rows_with_where,
  (SELECT COUNT(*) FROM customers c JOIN      orders o
     ON c.customer_id = o.customer_id WHERE o.status = 'paid')  AS rows_if_inner;
-- 검증 결과: 10 / 4 / 4
-- rows_with_where = rows_if_inner 이면 그 쿼리의 LEFT는 장식이다.
```

```sql
-- 프로브 2. 결측 비율 (0이면 그 환경에서는 이 버그가 재현되지 않는다)
SELECT COUNT(*)                                                  AS joined_rows,
       SUM(CASE WHEN o.order_id IS NULL THEN 1 ELSE 0 END)       AS unmatched_rows,
       ROUND(100.0 * SUM(CASE WHEN o.order_id IS NULL THEN 1 ELSE 0 END)
             / COUNT(*), 1)                                      AS unmatched_pct
FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id;
-- 검증 결과: 10 / 4 / 40.0
```

## 6. 집계 치트시트 — 매칭 없는 그룹에서의 값

| 식 | 값 | 실무에서의 결과 |
|---|---|---|
| `COUNT(*)` | **1** | 주문 0건이 1건으로 보고된다 |
| `COUNT(o.order_id)` | **0** | 보통 원하는 값 |
| `SUM(o.amount)` | **NULL** | 0이 아니다. 상위 계산으로 번진다 |
| `COALESCE(SUM(o.amount), 0)` | **0** | 권장 위치 |
| `AVG(o.amount)` | **NULL** | 상위 평균의 분모가 줄어 값이 부풀려진다 |

검증된 사례: 같은 데이터에서 합계는 둘 다 815로 같았고 평균만 135.83과 81.50으로 갈렸다. **합계 검증만으로는 이 오류를 못 잡는다.**

## 7. 코드 리뷰에 그대로 쓸 문장

- 「이 WHERE가 언급하는 별칭은 어느 조인에서 왔습니까? LEFT JOIN이면 행 수가 왼쪽 표와 같은지 세어 주세요.」
- 「조건을 WHERE에 두기로 했다면 LEFT를 지우고 INNER JOIN으로 적어 주세요. 다음 사람이 의도를 오해합니다.」
- 「이 리포트의 검증 데이터에서 결측 비율이 몇 퍼센트입니까? 0이면 이 쿼리는 검증되지 않은 것과 같습니다.」
- 「COUNT(\*)가 아니라 오른쪽 표 컬럼을 세야 하는 자리 아닙니까? 매칭 없는 그룹이 1로 보고됩니다.」
- 「SUM 결과가 NULL로 나갈 수 있습니다. COALESCE를 집계 결과에 씌울지 판단해 주세요.」
- 「기간 조건이 오른쪽 표에 있습니다. 이 달에 활동이 없던 대상이 리포트에서 통째로 빠집니다.」

## 8. 체크리스트

- [ ] WHERE가 언급하는 별칭이 어느 조인에서 왔는지 확인했다
- [ ] LEFT JOIN 쿼리의 결과 행 수를 왼쪽 표 행 수와 비교해 봤다
- [ ] 결측 비율이 0이 아닌 데이터로 검증했다
- [ ] 개수 지표에 `COUNT(*)` 대신 오른쪽 표 컬럼을 세었다
- [ ] `SUM` 결과에 `COALESCE`를 씌울지 한 번 판단했다
- [ ] 조건을 WHERE에 둔 곳은 `INNER JOIN`으로 명시했다
- [ ] 연쇄 조인에서 층별로 행 수를 세어 어느 층이 줄였는지 특정했다
- [ ] `USING` 조인에 조건을 붙이려다 막혔다면 `ON`으로 바꿨다

## 9. 하지 말 것

- ❌ LEFT JOIN 아래에 오른쪽 표 조건을 WHERE로 붙이는 것 — 의도가 있다면 INNER로 적는다
- ❌ 「LEFT JOIN이니 왼쪽은 다 나온다」고 읽고 넘어가는 것 — 아래 WHERE를 먼저 본다
- ❌ 결측 없는 시드 데이터로 리포트 쿼리를 검증하는 것 — 그 환경에서는 재현되지 않는다
- ❌ 행 수를 세지 않고 「줄어든 것 같다」로 보고하는 것 — 숫자 두 개를 나란히 적는다
- ❌ `OR ... IS NULL`을 ON과 같은 것으로 취급하는 것 — 검증 결과 8행과 10행으로 달랐다
- ❌ 합계만 대조하고 검증을 끝내는 것 — 이 버그는 개수 지표에서만 드러난다
