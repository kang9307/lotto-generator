2026年9月2日 开发/基础设施

在 Pod 规格里写下 limits.memory: 1Gi，那个容器确实越不过这条线。问题在于里面跑的 JVM 怎么读这个数字。JVM 不是一个遵守上限的程序，而是一个看着上限给自己做计划的程序，计划一旦错了，守住上限的就是内核，而内核守住上限的方式是杀掉进程。

CPU 那边错得更安静。平均使用率很低，只有 p99 在跳。与此同时在 JVM 内部，收集器的选择和线程池的大小已经跟着Pod 规格里的一个数字改变了。

起因 - 设了上限仍然对不上的地方

2026 年 9 月初，一篇讲 Kubernetes 上 Java JVM 的 CPU 与内存 Request 和 Limit 的文章在韩国开发者社区被转载。论点只有一个。容器里的 Java 进程有两条内存边界。一条是堆边界，一条是容器边界，把这两条当成同一条的那一刻，事故就开始了。

CPU 那边是同样的结构。Pod 规格里的 CPU 数字既是对调度器说的话，同时也是JVM 计算自身并行度的输入，而仪表盘只显示其中一边。容器为什么以 OOMKilled 收场的一般性诊断在另一篇，故障中管控台为什么给不出答案在那一篇。这里只谈JVM 特有的问题。

JVM 本来看的是宿主机

根子在于 JVM 自己决定自己的堆大小。Oracle 的 GC 调优指南列出的默认选择是这样的。初始堆是物理内存的六十四分之一，最大堆是四分之一，收集器在服务器级机器上是 G1，其他情况是 Serial。服务器级的定义也有脚注。处理器两个以上，且物理内存不低于 1792MB 时才算。

问题就出在「物理内存」这个词上。对容器识别出现之前的 JVM 来说，它指的是整台宿主机。在 64GB 的节点上放一个 limit 为 512Mi 的 Pod，里面的 JVM 会按 16GB 的最大堆做计划。计划本身错了，于是 GC 认为还有很多余量而推迟回收，与此同时容器越过 512Mi，被内核杀掉。

修好的时间点很明确，是 JDK 10 发行说明里的 JDK-8146115 条目。JVM 被修改为能感知自己运行在容器中，不再询问操作系统，而是提取容器专有的配置信息。提取的是分配给容器的 CPU 数量和总内存。只在 Linux 上生效，默认开启，可用 -XX:-UseContainerSupport 关闭。

  • 同一变更加入了 -XX:ActiveProcessorCount。发行说明写明这个数值会覆盖 JVM 中其他所有的 CPU 自动探测逻辑
  • 同一处的 JDK-8186248 加入了 InitialRAMPercentage、MaxRAMPercentage、MinRAMPercentage，替代旧的 Fraction 形式
  • 这一条目同样出现在 Oracle JDK 8u191 的发行说明里。JDK 8 系列只要在 8u191 以上也带有容器识别
  • 反过来说8u190 以下和 JDK 9 没有。如果还在用那样的镜像，就只能照老办法把 -Xmx 钉死

容器识别实际读取的值

内存这条路径在 -XX:MaxRAM 的文档里写得很清楚。默认值是「JVM 进程可用的最大内存与 128GB 中较小的一个」，紧接着的一句才是关键。这个可用内存是机器物理内存与环境所施加的约束例如容器中较小的一个。容器的 memory limit 从这里进来，比例类的参数再压在它之上。

CPU 这边的算法不在 man page 里，而在 OpenJDK 的源码注释中。cgroupSubsystem_linux.cpp 里 active_processor_count 的说明只有三行。用 sched_getaffinity 求出可用的 CPU 数。若指定了 quota，就用 quota 除以 period。而且所有除法结果一律向上取整到下一个整数。结果不会超过活跃处理器数。

向上取整在实践中影响很大。CPU limit 是 500m 时 0.5 进位成 1，1500m 时是 2。就算给不到一个 CPU，JVM 看到的也至少是一个。反过来 2100m 这样的值会变成 3，让它创建出比实际能跑的更多的线程。

最容易漏掉的是根本没有 limit 的情况。cgroup 里没有 quota 时，上面的算法直接采用系统的活跃处理器数。在 96 核的节点上只放一个 requests.cpu: 500m 的 Pod，那个 JVM 就会按 96 核做计划。

为什么用比例而不是 -Xmx

绝对值和比例的差别不是口味，而是要维护的地方有几处。-Xmx2g 是一个与 Pod 规格分开活着的数字。把 limit 提到 3Gi 却不改 JVM 参数，多出来的内存就闲着；降到 1Gi 却不改，那个 Pod 从上线那一刻起就会死。用比例给，只有一处要改。

参数决定什么Java 21 man page 的默认值注意
-XX:InitialRAMPercentage初始堆1.5625 个百分点启动后堆很小。增长过程中 GC 会跑得很频繁
-XX:MaxRAMPercentage最大堆25 个百分点不指定时 1Gi 容器的最大堆约为 256Mi
-XX:MinRAMPercentage小堆场景下的最大堆50 个百分点不是最小值。文档说它适用于「约 125MB 以下的小堆」
-XX:MaxRAM上面这些比例的分母可用内存与 128GB 中较小的一个这里的可用内存就是容器 limit

默认值 25 个百分点在实战中出的事最多。给了容器 4Gi，堆只拿到 1Gi，剩下的 3Gi 没人用。「内存都加了为什么 GC 还是这么厉害」的一半都出在这里。MaxRAMPercentage 在容器里实际上是必填项。

还有一个命名陷阱。MinRAMPercentage 不是「至少给堆留多少个百分点」，而是小堆区间里的最大比例。250Mi 的 sidecar Java 进程里只动了 MaxRAMPercentage，然后想不通为什么不生效，就是这一条。

resources:
  requests:
    cpu: 500m
    memory: 1Gi
  limits:
    memory: 1Gi          # 作为比例分母的值
env:
  - name: JAVA_TOOL_OPTIONS
    value: >-
      -XX:MaxRAMPercentage=70.0
      -XX:InitialRAMPercentage=70.0
      -XX:+ExitOnOutOfMemoryError

70 这个数字没有依据。官方文档里任何地方都没有「堆取 limit 的百分之几」这样的推荐。引出这篇的那篇文章说从 50 到 75 之间开始再验证，这已经是相当诚实的说法。剩下的那部分用在哪里，下一节来讲。

堆并不是全部的内存

只带走这一节也够了。把 -Xmx 设成和容器 limit 一样，那个 Pod 一定会死。堆之外还有好几处 JVM 要用的内存，它们不算进 -Xmx，却原封不动地算进容器的用量。

区域由什么决定官方文档中的默认值计入容器用量
Java 堆-Xmx / MaxRAMPercentageMaxRAM 的 25 个百分点计入
元空间-XX:MaxMetaspaceSize默认不限制大小计入
JIT 代码缓存-XX:ReservedCodeCacheSize240MB，关闭分层编译则为 48MB计入
线程栈-Xss × 线程数Linux x64 为每线程 1024KB计入
直接缓冲区(NIO)-XX:MaxDirectMemorySize不指定时由 JVM 自动决定计入
GC 内部结构、JVM 自身、原生库没有参数没有文档化的固定值计入

表里最扎眼的是元空间默认不设上限。在大量生成类的框架里这个值一涨，堆看着很健康，只有容器触顶。不过预留和实际提交是两回事。表里的数字是上限，不是常态占用量。

更重要的是死法不同。堆不够时 JVM 抛出 OutOfMemoryError，留下栈轨迹和堆转储。而越过容器上限时，用 Kubernetes 文档的说法，memory limit 由内核以 OOM kill 强制执行。既没有异常也没有转储。同一份文档还补了一句，这种终止只在内核检测到内存压力时才发生，所以超额分配内存的容器未必会被立即杀掉。同样的代码、同样的负载，死的时刻却不一样，原因就在这里。

要知道堆外的内存去了哪里，JVM 自带的手段是原生内存跟踪。-XX:NativeMemoryTracking 的默认值是 off，设为 summary 就会按子系统跟踪用量。

# 堆外内存明细 (仅对启动时开启跟踪的进程有效)
jcmd 1 VM.native_memory summary

# 最大限度记录 JVM 如何识别容器
java -Xlog:os+container=trace -XX:MaxRAMPercentage=70 -version

# 查看最终确定下来的参数值
java -XX:+PrintFlagsFinal -version | grep -E 'MaxHeapSize|ActiveProcessorCount'

一个 availableProcessors 决定的东西

Runtime.availableProcessors() 的 javadoc 很短。它返回 JVM 可用的处理器数，这个值在运行期间可能变化，且不会小于 1。在容器里，它就是上一节那个向上取整的结果。这一个数字会连锁地决定下面这些。

收集器的选择与 GC 线程数

服务器级判定的条件卡在这里。处理器不足两个或内存不足 1792MB 就不算服务器级，默认收集器就变成Serial 而不是 G1。CPU limit 为 500m 的容器被算作一个处理器，正好撞上这个条件。在这种状态下再挂一堆 G1 专用的调优参数，什么都不会发生。

就算过了服务器级这一关，GC 工作线程数也跟着处理器数走。指南只写了「最大 GC 线程数受堆大小和可用 CPU 资源限制」，没有给出算式。但方向是清楚的。看到的处理器少，GC 就转得慢。

用 ActiveProcessorCount 覆盖

man page 把这个参数的范围说得很准。它覆盖的是 VM 在计算线程池大小时使用的 CPU 数，用于垃圾收集和 ForkJoinPool 之类的操作。它还补充说，即使 UseContainerSupport 没有开启这个参数也会被尊重，并写明了用途，在容器中运行多个 Java 进程时用来划分 CPU 资源。

  • 这个参数只改变 JVM 看到的值。cgroup 的 quota 一动不动。调成 1，容器照样能用满 limit
  • 所以调低会减少 GC 工作线程和并行处理，而节流一点没少。它不是节流的解药
  • 反过来调高只是多出线程而 quota 不变，节流反而更重。「就当多给了几个核」这套是不成立的
  • 真正用得上的地方是一个 Pod 里有两个以上 Java 进程时，防止各自把整个 Pod 都算成自己的

并行流也绑在同一个值上。ForkJoinPool 的 javadoc 写明无参构造器创建的池，其并行度等于 Runtime.availableProcessors()，而公共池的并行度可以通过 java.util.concurrent.ForkJoinPool.common.parallelism 属性指定。改 CPU limit 同时也是在改应用代码的并行度。

CPU Limit 为什么会制造延迟

Kubernetes 文档的句子很明确。cpu limit 由CPU 节流强制执行，容器接近 limit 时内核会把 CPU 访问限制到与该 limit 对应的量。这是内核强制的硬上限。和内存不同，不是「越过就死」，而是「想越过就停」。

停的单位才是要害。kubelet 默认用 CFS quota 强制执行 Pod 的 CPU limit，而决定周期值的选项 --cpu-cfs-quota-period 默认是 100ms。节流不是以秒为单位平滑发生的，而是在 100ms 的窗口里用完配额就停到那个窗口结束。

平均值的陷阱就在这里。CPU limit 为 1 而线程有 4 个时，100ms 的配额在 25ms 就用完，剩下的 75ms 里那个容器的所有线程都停住。按一秒平均，使用率不到百分之百，图看着很平静。哪怕那一秒里塞着好几次最长 75ms 的停顿也一样。平均使用率低而 p99 却在跳，来源多半就是这个。

和 GC 撞上会更糟。在 stop-the-world 期间配额耗尽，GC 线程也一起停住，要等下一个周期打开才恢复。本来很短的停顿被拉长到周期边界。这就是必须把 GC 日志的停顿时间和节流指标并排看的理由。

CPU limit 该设还是不该设

这个题目结论是分裂的。两边优化的东西不一样，而且两边都有文档支撑的依据。并排放着比选一边更准确。

主张不设的一方依据主张要设的一方依据
节流会制造真实的延迟内核强制的硬上限，周期默认值是 100ms这是 Guaranteed QoS 的条件所有容器的 cpu limit 必须等于 request
CPU 不够 Pod 也不会死驱逐信号只有内存、文件系统和 pid，没有 CPU在驱逐顺序里被排到后面驱逐顺序是 BestEffort、Burstable、Guaranteed
节点空闲时可以用掉富余的 CPU资源有富余时允许用超过 request 的量要做 CPU 绑定就必须有static 策略的独占 CPU 只分配给整数 request 的 Guaranteed Pod
只有 request 也能定下调度request 用于调度器决定放在哪个节点邻居的延迟变得可预测这更接近运维方针而不是文档依据

归纳起来，延迟要紧的少数服务和密度要紧的大量批处理会给出不同的答案。前者为了躲开节流而不设或放大 limit，后者为了可预测性和驱逐排序而设。判断标准不是口味而是指标。先看节流指标是不是真的在涨。

有一点必须分清。去掉内存 limit 和去掉 CPU limit 不是同一性质的决定。CPU 不够只是变慢，内存却不可压缩。没有内存 limit，那个 Pod 会把整个节点拖下水，而 JVM 会按节点内存去规划堆。

Request 和 Limit 做的是不同的事

Kubernetes 文档的定义很短。指定 request 后kube-scheduler 用这个信息决定把 Pod 放到哪个节点上。指定 limit 后kubelet 会强制执行它，让运行中的容器用不到超出的量。一个是调度阶段的数字，一个是运行阶段的数字。

从 JVM 的角度看，决定性的一点是JVM 根本不看 request。MaxRAM 参照的是「环境所施加的约束」，也就是 cgroup 的 limit。只把 request 开大而 limit 留空的 Pod，在调度器眼里是安排得很宽裕的 Pod，里面的 JVM 却按并不存在的内存在动。

QoS 等级条件驱逐顺序从 JVM 角度的含义
Guaranteed所有容器都有 CPU 与内存的 limit 和 request，且两者相等最后被驱逐堆比例的分母是确定的，最不容易跑偏
Burstable不满足 Guaranteed，但至少有一个容器有 request 或 limit排在 BestEffort 之后有 limit 就以它为分母，没有就以节点内存为分母
BestEffort没有任何容器设了 CPU 或内存的 request 与 limit最先被驱逐JVM 把整个节点算成自己的，对 Java 实际上等于禁用

文档补充的一个条件也值得知道。因资源压力发生驱逐时，成为候选的是用量超过 request 的 Pod。把 request 定得贴近现实并不是走形式，原因就在这里。

JIT 预热击垮 readiness 的地方

HotSpot 默认以 C1 和 C2 并用的分层编译器启动，而编译本身要吃 CPU。所以 Java 应用的 CPU 用量在启动之后最高，进入稳定状态后回落。可 CPU limit 大多是按稳定状态定的。最需要 CPU 的那一段被节流得最狠。

接下来是既定套路。启动一慢 readiness probe 就失败，按文档的说法 kubelet 会把容器标记为未就绪，端点控制器随即把这个 Pod 的 IP 从所有匹配的服务端点中移除。到这里都是正常行为。问题出在 liveness probe 也用了同样的阈值。liveness 一失败，容器就按重启策略被杀掉，重新启动又走一遍同一段，重启循环就此形成。

官方的处方是 startup probe。文档说这个探针保护启动缓慢的容器，让人在不影响正常 liveness 与 readiness 检查的前提下定义启动专用的成功标准。连推荐形态都给了：用与 liveness 相同的检查，只把失败阈值调高。把 liveness 本身放松，就抓不到真正的故障了。

  • 只在启动阶段多给 CPU，用标准的 request 与 limit 是做不到的。要么用 startup probe 争取时间，要么把 limit 抬上去
  • 不想抬 limit 的话，类数据共享或提前编译这类启动优化是下一个选项。它们的效果本文没有验证
  • 因启动慢导致首个请求慢，和因节流导致 p99 长期偏高，是两个问题。不把启动阶段和稳定阶段分开看就会混在一起

看什么来决定

最常见的错误是只凭一个数字下判断。用一张堆用量曲线定 limit，或者用一个 CPU 使用率判断有没有节流。下面这五个说的是不同的事。

  • GC 之后的堆用量 — 堆大小的依据是这个值。锯齿图的顶点不是「需要的大小」，而是「回收前含垃圾的大小」
  • 已提交的堆 — JVM 实际占下来的大小。取决于收集器，用不到的部分有可能还给操作系统
  • 进程 RSS — 真正驻留在物理内存里的量。减掉堆，大致能看出堆外有多少
  • 容器内存用量 — cgroup 看到的值，也是判定 OOM 的依据。里面掺着页缓存
  • CPU 节流指标 — 不看使用率，看被节流的周期数与时间。使用率会把节流藏起来

顺序很简单。先定 limit，用比例给堆，在真实流量下把上面五个一起看，再回头改。特别要注意合成压测很难暴露堆外内存。类加载和代码缓存要在真实代码路径被广泛踩到之后才会涨。

五种常见的失败

同样的失败反复出现，是因为症状离原因很远。

失败实际发生的事症状看什么
根本没设 limitJVM 按节点内存和节点 CPU 数做计划节点受压，被驱逐的却是不相干的 PodQoS 等级与节点驱逐事件
把 -Xmx 设成和 limit 一样堆外的份额变成 0没有异常的 OOMKilled，也没有转储RSS 与堆的差值、原生内存跟踪
只有 request 没有 limit变成 Burstable，JVM 按节点做计划调度看着宽裕，运行中却会死把 request 与 limit 并排确认
CPU limit 定得太低被算成一个处理器，够不上服务器级判定GC 停顿变长，调优参数不生效实际选中的收集器、GC 停顿时间、节流指标
多容器 Pod 忘了合计sidecar 与主进程分享同一个上限加了 sidecar 之后才开始死Pod 内所有容器的 request 与 limit 合计

第四条还有一个反方向的陷阱。用 -XX:ActiveProcessorCount 只把处理器数调高，收集器的选择会变，quota 却纹丝不动。线程多出来多少，节流就重多少。想换收集器的话，与其在处理器数上撒谎，不如用 -XX:+UseG1GC 这样直接指定来得诚实。

这篇是以哪个版本为准的

这个领域的行为确实随版本而不同，也是照搬旧文章最容易翻车的地方，所以先把基准说清楚。

  • JDK 8u190 以下与 JDK 9 — 没有容器识别。堆和处理器数按宿主机来定，除了手工钉死 -Xmx 没有别的办法
  • JDK 8u191 以上与 JDK 10 以上 — UseContainerSupport 默认开启，可以用 RAMPercentage 三个参数和 ActiveProcessorCount
  • JDK 19 — OpenJDK 的缺陷 JDK-8281181「Do not use CPU Shares to compute active processor count」落在这个版本。在此之前，没有 quota 时是用 cpu shares 算处理器数的，而在 Kubernetes 里 cpu shares 来自 CPU request。也就是说在旧 JDK 上，request 会影响 JVM 的并行度
  • 正文里的参数默认值 — 以 Java 21 的 java man page 为准。收集器选择与服务器级判定以 Java 25 的 GC 调优指南为准
  • Kubernetes 这一侧 — 是 2026 年 9 月时点的官方文档。cgroup v1 与 v2 的差异没有涉及

第三条尤其麻烦。升了运行时却没动 CPU 设置，并行度也可能变了。意思是把参数原样留着这件事本身，就可能是一次变更。

小结

骨架就一句话。Pod 规格里的数字既是约束容器的值，也是 JVM 给自己做计划的输入。内存 limit 成为堆比例的分母，CPU limit 成为处理器数，决定收集器的选择和线程池的大小。

落到实务上剩下三件事。不要把 -Xmx 设成和 limit 一样，不给堆外留出份额，内核会悄无声息地动手。用比例给，要维护的数字减到一个，而默认的 25 个百分点通常太小。CPU limit 要连同延迟预算一起定，100ms 周期内的停顿不会出现在按秒的平均里。还有，任何比例都不是别人能替你定的。堆外内存随框架和线程数在每个服务上都不一样。测出来再定，每次升运行时都重新看一遍。

未能确认的部分

  • 没有在 Linux 容器里实际运行验证。正文里的命令都是依据文档写的，一条执行输出也没有附上
  • ForkJoinPool 公共池默认并行度的算式不在 javadoc 里。只确认了无参构造器与 availableProcessors() 相等这一点
  • -XX:ParallelGCThreads 与 -XX:ConcGCThreads 的默认算式同样不在 man page 里。指南只写了「受堆大小和可用 CPU 资源限制」
  • JDK-8281181 有没有回合没能确认。缺陷库里记录的修复版本只有 19 一个
  • cgroup v1 与 v2 的差异对上述计算的影响没有涉及。文件名和单位都不同
  • 不重启就改 Pod 资源的功能，以及那时 JVM 会不会重新读取这些值，超出了本文核对的范围
  • 启动优化手段在被节流的区间里到底有多大帮助没有测量
