强制用受控语言写技术文档会改变什么

扣分从74降到3，词汇减少34% - 以及为什么不能套到所有文档上

2026-08-01 IT/技术

引言: 同一句话，两个人理解成了相反的意思

假设操作手册里有这么一句。「取下盖板之前必须先断开电缆。」一个人先拔了电缆，另一个人先打开了盖板。两个人都读了这句话，两个人都认为自己读对了。这句话本身没有错。它只是一句被允许有两种读法的话。

出了这种事之后，常见的处方是「把文档写得更详细」。可是写得越详细句子就越长，句子越长分叉的地方就越多。还有另一个方向的处方。事先把可用的词汇和句子结构削减掉。让有分叉余地的表达从一开始就用不出来。这就叫受控语言。

本文谈的就是这种方法，但不会讲「用简单英语写吧」。取而代之，本文做两件事。

  • 自己写检查器，用数字量。把同一段操作步骤在受控前后各送进去一次，比较句长、被动语态比例、模糊词、术语变体数量。扣分从74降到3，而且出乎意料，总词数减少了40%
  • 用同一个检查器证明哪里不该用。把一段写得很好的概念说明送进去，60%的句子违规。那不是差文，而是目的不同的文字

运行环境。下面所有数字都来自在 Windows 10 Pro (10.0.19045) 的 Node.js v22.16.0 (win32) 上运行我自己写的检查器。没有使用任何外部库。检查器的完整代码在第3节，可以直接复制运行。

规范正文我没有打开。这个领域最有代表性的规范 ASD-STE100 是通过官网的申请表以 PDF 形式分发的。我看的是官网的概述页和 FAQ，外加一份公开的解说页面，规范正文没有读过。因此本文既没有53条规则的完整清单，也没有约900个批准词汇的内容。下文引用的数字和规则来自官网与公开解说所述的范围，正文中出现的具体检查规则是我自己写的检查器的规则，不是规范的规则。

本文的例句全部是虚构的。出现的设备、步骤、文档都不存在。文档格式本身的问题在AI时代的韩国文档格式里谈过了，本文谈的不是格式而是句子。

1. 受控语言到底是什么

受控语言不是文风指南。文风指南劝你「尽量用主动语态」，受控语言则让被动语态根本用不出来。差别不在建议与禁止之间，而在有选择和没有选择之间。

最著名的案例来自飞机维修文档。官网的说明把动机讲得很直白: 复杂的技术指令可能被误解，误解可能导致事故。于是欧洲的航空公司提出需求，规范在1980年代被制定出来。在我核实的范围内，它的构成如下。

  • 53条写作规则分布在9个章节里，覆盖语法和文风
  • 约900个批准词汇。原则上每个词只有一个意思、一个词性
  • 约1,200个未批准词汇与替代词一起列出。被广泛引用的例子是 start 被批准而 begin、commence 不被批准
  • 现行版本是 Issue 9 (2025年1月)，由1983年成立的专门维护小组负责
  • 虽然起源于航空，官方 FAQ 说它也用于陆上与海上车辆、可再生能源、医疗器械领域

有一个容易漏掉的细节。900个批准词汇并不是全部。官方 FAQ 明确写着，各行业的技术名词和技术动词可以另外使用。只要来自图纸、正式文档或公司术语表，即使在批准清单之外也可以用。也就是说受控语言不是把词汇关进900个词里，而是「通用词汇固定为900个，专业术语只通过有依据的清单来增加」的结构。不了解这个区别就引入的团队，会在第一周被「这个词不让用」的抱怨压垮。

2. 禁止什么 - 四类禁止，以及各自制造的误解

不必看完53条规则。实务中出事的通常是四五条。重要的是每一条制造的是哪一种误解。

禁止对象制造什么样的误解受控前受控后
长句 (指示句超过20词、说明句超过25词)修饰关系可以挂到多个分支上。句子内部没有答案说它属于哪个名词Disconnect the cable and the sensor that is loose.Disconnect the cable. Disconnect the sensor if the sensor is loose.
被动语态施事者消失。分不清是人去做还是自动发生The unit must be restarted.Start the unit again. (或) The unit starts again automatically.
没有指代的代词 (it, this, that)可以挂到最近的名词上，也可以挂到整段上。每个读者连接的对象都不同Check the log and the counter. If it is zero, stop.Check the counter. If the counter is 0, stop the procedure.
同义词滥用换一个词读者就会读成另一件事，译者尤其如此start / begin / commence / initiate 混用只用 start

2.1 被动语态危险的真正原因

如果你以为禁止被动是因为「读起来别扭」，那只说对了一半。把同一条指令写成三种形式并排放着，问题就浮出来了。

--- 同一条指令，三种写法 ---
(1) The cable must be disconnected before the cover is removed.
(2) Disconnect the cable. Then remove the cover.
(3) Remove the cover after disconnecting the cable.

                        (1)          (2)            (3)
谁来做                   未说明       读者           未说明
哪个先                   电缆         电缆           电缆
阅读顺序与作业顺序       相反         一致           相反
一句里的指令数           2条          1条            2条
must 约束谁              不明确       不需要         不明确
  • (1) 和 (3) 阅读顺序与作业顺序相反。在紧急场合边读边动手就会把步骤颠倒过来。只有 (2) 可以照着读的顺序执行
  • (1) 里的 must 从不说这是谁的义务。是操作员、是设计、还是软件，句子里没有依据可以判断
  • (3) 的 after disconnecting 语法上没有瑕疵，但动名词可以同时表示时间关系和条件。读者会在「断开之后」和「只有断开了才」之间分裂
  • 禁止被动的实效不在文风，而在逼作者写出施事者。用祈使句写，施事者自动变成读者

3. 我做了一个检查器 - 它数什么、怎么数

用文字描述规则，和展示规则实际把文档改变了多少，是两回事。所以我写了一个检查器。它没有实现任何已发布的规范。它只数受控规则约束的四件事: 句长、被动语态、模糊指代、术语一致性。

// ste_check.js — Node 22, 无依赖。 运行: node ste_check.js doc.txt proc
const LIM = { proc: 20, desc: 25 }, PARA = 6, NOUN = 3;

const PASSIVE = /\b(?:is|are|was|were|be|been|being)\s+(?:not\s+|often\s+|normally\s+)?([a-z]+(?:ed|en)|done|set|put|kept|sent|made)\b/gi;

const VAGUE = ['as required', 'if necessary', 'as appropriate', 'properly', 'correctly',
  'regularly', 'periodically', 'normally', 'usually', 'typically', 'should', 'may',
  'might', 'could', 'various', 'relevant'];

// 一组 = 一个概念。整篇文档只能用一个词来表达
const SYN = {
  start:  ['start', 'begin', 'commence', 'initiate', 'launch'],
  stop:   ['stop', 'halt', 'cease', 'terminate', 'abort'],
  check:  ['check', 'verify', 'confirm', 'validate', 'ensure', 'make sure'],
  remove: ['remove', 'detach', 'disconnect', 'unplug'],
  fix:    ['fix', 'repair', 'correct', 'rectify']
};

核心是下面三个函数。漏掉词形变化处理，检查器就会静悄悄地失败。我第一版给 commence 加上 ed 去找 commenceed，结果在明显混用同义词的段落里返回违规0。检查器返回0的时候，未必是文档干净。可能是检查器坏了。

// 词形变化 — 要让 commence 也能匹配 commenced 就必须有它
const forms = v => { const o = new Set([v, v + 's', v + 'ed', v + 'ing']);
  if (v.endsWith('e')) o.add(v + 'd');
  if (v.endsWith('y')) o.add(v.slice(0, -1) + 'ied'); return [...o]; };

// 断句 — 只在句号后面跟着大写字母或数字时才切
const sents = t => t.replace(/\s+/g, ' ').trim()
  .split(/(?<=[.!?:])\s+(?=[A-Z0-9(])/).filter(Boolean);

// 名词堆 — 用标点、功能词和数字来切断
function runs(s) { const out = [];
  for (const c of s.split(/[,;:.()]+/)) { let cur = [];
    for (const t of c.split(/\s+/).filter(Boolean)) {
      const l = t.toLowerCase().replace(/[^a-z0-9]/g, '');
      if (!l || /\d/.test(l) || STOP.has(l) || /(?:ed|ing|ly)$/.test(l)) {
        if (cur.length > NOUN) out.push(cur.join(' ')); cur = [];
      } else cur.push(t); }
    if (cur.length > NOUN) out.push(cur.join(' ')); }
  return out; }

// 扣分 — 权重是随意定的。不看绝对值，只用于同一篇文档的前后对比
score: over * 3 + passive * 2 + vague.length + pron + varied.length * 3
     + clusters.length * 2 + longP * 2
指标数什么上限已知的局限
over超过上限的句子数指示句20词 / 说明句25词断句依赖句号。缩写里的句号可能被错误切开
passivebe 动词 + 过去分词的模式0像 is required 这种接近形容词的也会数进去，偏向过检
pronit、they、them 的出现次数0不区分形式主语的 it 和指示代词
vague与模糊词清单的匹配0清单就是全部，不在清单里的模糊词抓不到
synVar一个概念用了两个以上词的组数0过检最严重的指标。4.1节展示真实的误报
cluster四个词以上的名词堆0没有词性标注，是靠功能词清单的估算
distinct不同词的个数越低越好只是翻译成本的代理指标，不是实际报价
  • 扣分的绝对值没有意义。权重是我定的。真正有用的只有同一篇文档修改前后的变化量
  • 我特意把七个指标分开显示而不是合成一个。只看总分，你知道文档不好却不知道该修哪条规则
  • 设置 proc 和 desc 两种模式，是因为操作手册和说明文档不能共用一个上限。这个区分就是第8节结论的技术依据
  • 不到两百行代码就足以把文档质量的争论搬到数字上。这是工具在这里唯一但决定性的价值

4. 实测 - 同一段操作步骤，受控前后

我把一个虚构设备的固件更新步骤写成了两版。内容完全一样，只有句子规则不同。先看常见的那一版。

--- A. 不受控写出来的步骤 (实务中常见的文体) ---
Before the firmware update is started, it should be verified that the unit is powered
from the primary supply and that the redundant supply cable is disconnected, since the
update procedure cannot be commenced while both supplies are active. The configuration
backup file, which is normally generated by the maintenance console during the previous
session, must be copied to the removable media before proceeding, and it is recommended
that the operator confirms that the file size is not zero. If the status indicator is
flashing, the controller has not finished the previous write cycle and the operation
should be halted until the indicator becomes steady. After the media is inserted, the
update is initiated from the service menu, and the process, which typically takes about
eight minutes, must not be interrupted. The device will be restarted automatically; if
it is not restarted within two minutes, power should be removed and the unit should be
started again manually. Any configuration entries which were not migrated correctly can
be corrected later using the console, but the relevant log files should be retained for
analysis as required.
--- B. 同样的内容，套用受控规则 ---
Start this procedure only when the primary supply gives power to the unit.

Disconnect the redundant supply cable. Make sure that the backup file on the removable
media has a size of more than 0 bytes. If the status indicator flashes, wait until the
indicator is continuously on.

Put the removable media in the slot. Start the update from the service menu.
Do not stop the update. The update takes 8 minutes.

The unit starts again automatically. If the unit does not start again in 2 minutes,
remove the power. Then start the unit manually.

Keep the log files. You can correct the configuration entries with the console after
this procedure.

4.1 检查器错的地方 - 先承认误报

受控后的段落 B 里还剩下一处违规。但这是我的检查器的缺陷，不是文档的缺陷。

  B still flags: ["remove"]
  A flags       : ["start","check","remove"]

  B 正文中被抓的两个词
    "Disconnect the redundant supply cable."   -> disconnect
    "remove the power. Then start the unit."   -> remove

  我的 SYN 定义:  remove: ['remove', 'detach', 'disconnect', 'unplug']
  实际规范里:     remove 和 disconnect 是意思不同的两个独立批准词
                  (把电缆「拔下来」和把部件「拆下来」是不同的作业)
  • 我的同义词组把两个不同的概念放进了一个筐里。在真实的受控词汇里 disconnect 和 remove 是各自以不同意思被批准的两个词
  • 教训很直接。检查器报违规时，先怀疑检查器，再怀疑文档。同义词规则尤其必须用自己公司的术语表来定义，照搬别人的清单就会涌出这类误报
  • 反方向的失败也有。如第3节所写，漏掉词形变化的早期版本在段落 A 里返回了术语变体0。它把一个明显混用的段落报告成干净的。检查器给出的0不是证据

5. 翻译变容易 - 词汇减少34%意味着什么

引入受控语言最常被引用的理由就是翻译。官方 FAQ 也写着，因为原文的变异被压到最小，所以翻译变得更容易。把这句话换成数字，就是第4节的 distinct 那一列。107个词降到71个。搬运同样的内容，译者需要判断的不同表达少了三分之一。

  • 翻译单价更取决于变异而不是总量。翻译记忆库按照与已译文本的相似度给每个片段计价。句式反复，完全匹配和模糊匹配的比例就上升，需要重新翻译的份额就下降
  • 机器翻译最常犯的三类错误在受控之后消失。长句里把修饰语挂错名词、被动句里凭空造出施事者、把代词连到错误的先行词。句子短、主动语态、没有代词，这三类错误都没有发生的地方
  • 术语一致性在翻译里会加倍放大。原文里混用 start 和 commence，译者就会判断「意思不同才分开写的吧」，于是选两个不同的译词。原文里毫无意义的变异，在译文里固化成了有意义的差别
  • 不过这份收益是把原文按规则写出来换回来的。它不来自换引擎或加后处理。成本落在原文作者身上

这里有一点必须诚实。官方 FAQ 明确写着，ASD 不认证也不背书任何声称符合规范的自动工具，任何工具都不能替代规范本身。这一点对我做的检查器同样适用。它是量规则的尺，不是规则。

容易产生的错觉。「引入受控语言就能减少翻译费」这个结论只在多语言发布的文档上成立。把这个逻辑原样搬到只在国内使用的单语操作手册上就没有依据了。那种情况下的收益不是翻译费而是误读减少，而那只能用事故记录来证明。说服别人引入的时候，借来一个不适用于自己组织的依据，第一个反问就会把它推倒。

用连接词尾串起来一句话里塞进多条指令over 和平均长度上升一条指令一句话
非终结式的结尾是义务还是建议在英语里会分裂vague 里的 should必须的用祈使句，有条件的用 if 从句写明
  • D 的26个词是一句话。因为韩语原文就是一句话。译者要是认为自己无权重新断句，原文的结构就会原封不动地传过去
  • cable separation work progress 在英语里根本不成意思。可是韩语那边读起来很自然。这是原文里看不见的缺陷在翻译中暴露的典型
  • E 的词数反而比 D 少(24对26)。把堆成名词的东西用动词拆开，感觉应该变长，但 is required、must be performed by 这类包装消失了
  • 实务上的要点是把顺序倒过来。想提高英语翻译质量，要修的不是翻译环节而是韩语写作环节。只要给原文套上「一句一指令、写出主语、不省略助词」，英语侧的指标就会自己下来
  • 反过来也不能把英语式的受控规则原样套到韩语原文上。20词上限这类数值是英语的标准，韩语必须按文节数和句子成分另行制定

7. 自动强制的代价 - 好文章也会被扣分

这是本文最重要的实验。我把一段写得很好的概念说明送进了同一个检查器。不是故意写差的样本，而是为了说服读者而用心写出来的那一类文字。

--- C. 概念说明段落 (说明文模式, 上限25词) ---
Controlled language is often misunderstood as a style guide, but it is closer to a
contract between the writer and every reader who will ever open the document. When you
accept that contract, you give up a great deal: the rhythm you would use to keep a
reader interested, the aside that explains why a decision was made, and the well-placed
metaphor that makes an unfamiliar mechanism suddenly obvious. What you get in return is
narrow and valuable. Two people who read the same sentence in different rooms, in
different years, with different amounts of English, will act on it the same way.

  sents 5 / words 143 / avg 28.6 / max 42
  over 3  (全部句子的60%超限)
  passive 3   pron 3   vague 0   synVar 0   cluster 0
  score 18       (是受控步骤 B 的3的六倍)

这一段不需要修。因为破坏规则的那些部分正是这段文字在做的事。「契约」这个比喻、冒号后面并列三项的结构、最后一句长长的呼吸，都是为了说服读者的装置。把它们切到20词，意思还在，说服力没了。

  • 把强制模式挂到全部文档上，这样的文字就会在 CI 里被拦住。于是作者会做两件事之一: 为了绕开规则机械地切句子，或者干脆把检查器关掉。两种结果都让工具变得毫无意义
  • 三处被动里的 a decision was made 藏起施事者是有意为之。因为谁决定的不是重点。在操作手册里是缺陷的东西，在说明文里是功能
  • 三个 it 也一样。在说明文里代词制造与前一句的连接。把它们全都还原成名词，段落读起来就像项目清单
  • 所以检查器只能按目录启用。规则的强度由文档类型决定，不是给整个组织挂一个数值的问题

8. 用在哪里，不用在哪里

判断标准可以压缩成一句话。误读的代价是什么。代价是设备或人，就套用；代价是「再读一遍」，就不套用。

文档类型套用模式理由
作业步骤书 · 维修指令强制proc (20词)顺序颠倒就会出事故。阅读顺序必须等于作业顺序
警告语 · 安全标识强制proc (更严)在紧急场合要一次读完，不能带条件从句
安装 · 部署运行手册强制proc第一次看到的人在深夜照着做
API 参考 (参数、错误说明)强制proc会原样进入机器翻译和搜索摘要，每一项的句式必须一致
界面文案 · 错误消息强制proc既是翻译对象又有宽度限制，变异直接就是成本
规章 · 合同条款部分套用proc，只管词汇术语一致是必须的，但法律表述不能随便切短
发布说明只警告desc变更摘要越短越好，但把背景也切掉就没用了
概念说明 · 架构文档不套用-参见第7节实验。破坏规则的部分正是这类文字的功能
教程 · 新人上手文档不套用-上下文和动机占一半。只留祈使句，人跟着跟着就放弃了
设计决策记录 · 事后复盘不套用-「为什么这么做」就是正文。受控规则里没有它的位置
  • 表格上面五行有一个共同点。读者一边读一边动手。下面三行读者只是读。这个区分是实务中最贴合的分界线
  • 把「部分套用」和「只警告」单独列出来是有原因的。非全即无地推行，引入就会失败。只强制术语一致而放开句长，这个组合在现实中活得最久
  • 在同一个仓库里按路径划分是最干净的做法。只给操作手册目录挂钩子，其余部分干脆不运行检查器
  • 即使在同一份产品文档里，如果一个页面混了两类内容，最好把步骤部分单独拆成一个文件。这样才能按文件挂规则

9. 引入步骤 - 术语表、警告模式、强制模式

顺序搞错必然失败。从检查器开始点火是最常见的失败方式。用谁都没有同意过的规则给别人的文章扣分的工具，会在引入的第一周被关掉。

阶段做什么算完成的条件失败信号
1. 术语表从现有文档里把指同一概念的表达收集起来，只留一个前30个概念都定好了代表词和禁用词清单是抄别人的。4.1节那种误报会涌出来
2. 确定范围用第8节的表划分目录。先定不套用的地方路径规则写在配置文件里用「先全量挂上，以后再摘」开始
3. 警告模式只打印扣分，构建照常通过。至少4周知道现有文档的扣分分布没测分布就定阈值
4. 确定阈值从分布的中位数附近开始，每季度下调现有文档一半以上能通过先定一个理想值，然后全部挂掉
5. 强制模式只在操作手册路径上中断构建新文档以修好的状态提上来绕过注释变多。那说明规则错了
6. 维护接收误报反馈并修改规则术语表每季度更新一次收到反馈却叫人去改文档

9.1 从警告模式到强制模式

钩子越简单活得越久。按路径分模式，阈值只留一个。

# 操作手册路径 — 强制。超过阈值就中断构建
for f in docs/procedures/*.md; do
  node ste_check.js "$f" proc | tee -a report.txt
done
node ste_gate.js report.txt --max-score=10 || exit 1

# 说明文档路径 — 只警告。不中断构建
for f in docs/concepts/*.md; do
  node ste_check.js "$f" desc
done

# 不套用的路径干脆不运行
#   docs/tutorials/  docs/adr/  docs/postmortems/
  • 阈值要以单篇文档为基准。按整个仓库的总和来定，文档一多就会自动失败
  • 一定要留下绕过手段。允许用注释把某个段落排除在检查之外，然后去数这个注释被用了多少次。如果在增加，那么错的不是文档而是规则
  • 只对新文档强制，现有文档等到有人碰的时候顺手修。一上来就要求全量整改，引入本身就会流产
  • 成败取决于工具之外的第1阶段术语表。检查器只是强制术语表的手段，没有术语表就没有可强制的东西

10. 检查清单与不要做的事

如果你在考虑引入，最好先用下面的项目核对一下自己组织的状态。

  • 先把不套用的文档类型列成了清单
  • 术语表的代表词来自自己的文档而不是别人的清单
  • 操作手册和说明文档套用不同的上限
  • 检查器的指标按项目分开显示而不是一个总分
  • 用警告模式跑了4周以上，测过现有文档的分布
  • 在这个阈值下现有文档一半以上能通过
  • 有误报反馈通道，收到反馈就去修规则
  • 没有把节省翻译费当作单语文档的理由
  • 原文规则和英语规则是分开定义的
  • 检查器报违规0的时候先怀疑过检查器

10.1 不要做的事

  • 对整个仓库从强制模式开始 — 概念说明文档被拦住，人就把检查器关掉
  • 照搬别人的同义词清单 — 就像4.1节的 remove 和 disconnect，不同概念被塞进一个筐
  • 用扣分绝对值评价文档 — 权重是随意的。能用的只有同一篇文档的前后对比
  • 把英语的上限原样套到其他语言的文档上 — 20词是英语的标准
  • 想在翻译环节解决翻译质量问题 — 第6节的名词堆是在原文里造出来的
  • 没读规范正文就编造规则 — 本文也没有打开正文，所以没有写53条规则的清单
  • 给教程和事后复盘挂上受控规则 — 规则里没有写「为什么」的位置

结论回到开头的场景。两个人对盖板和电缆的顺序读出了不同的意思，不是因为文档难读，而是因为两种读法被允许了。受控语言做的事不是让文档变简单，而是消除解释的余地。所以标准只有一个。这份文档的目的是「被读到」，还是「被读成同一个意思」?前者就不要受控，后者就受控。它不是给所有文档用的。

# 引入受控语言 — 句子规则表 · 检查器 · 判断表 · 检查清单

> 来源: braindetox.kr — 强制用受控语言写技术文档会改变什么
> 依据: 在 Windows 10 Pro / Node.js v22.16.0 上运行下面这个检查器的结果
> ⚠ 规范正文 PDF 没有打开。下面的规则来自公开说明的范围和我自己的实验，
>   53条规则的完整清单和批准词汇清单不在这里。

## 0. 大前提

**文档的目的如果是「被读到」就不要受控，如果是「被读成同一个意思」就受控。**
它不是给所有文档用的。

## 1. 句子规则表

| 规则 | 值 | 为什么 |
|---|---|---|
| 指示句 一句 | **20词以内** | 消除修饰关系分叉的余地 |
| 说明句 一句 | **25词以内** | 同样的理由，只是上限放宽 |
| 一段 | **6句以内** | 一段一个主题 |
| 名词堆叠 | **3词以内** | 从4个词开始修饰关系产生歧义 |
| 一句里的指令 | **1条** | 顺序颠倒事故的最大成因 |
| 被动语态 | **禁止** | 施事者消失 |
| 无指代的代词 | **禁止** | it, this, that 每个人连的对象不同 |
| 一个概念 | **一个词** | 禁止混用 start / begin / commence |
| 模糊词 | **禁止** | properly, as required, regularly → 改成数值 |

## 2. 检查器 (Node 22, 无依赖)

```js
// ste_check.js   运行: node ste_check.js doc.txt proc
const LIM = { proc: 20, desc: 25 }, PARA = 6, NOUN = 3;
const PASSIVE = /\b(?:is|are|was|were|be|been|being)\s+(?:not\s+|often\s+|normally\s+)?([a-z]+(?:ed|en)|done|set|put|kept|sent|made)\b/gi;
const VAGUE = ['as required','if necessary','as appropriate','properly','correctly','regularly',
  'periodically','normally','usually','typically','should','may','might','could','various','relevant'];
const SYN = { start:['start','begin','commence','initiate','launch'],
  stop:['stop','halt','cease','terminate','abort'],
  check:['check','verify','confirm','validate','ensure','make sure'],
  remove:['remove','detach','disconnect','unplug'],
  fix:['fix','repair','correct','rectify'] };
const STOP = new Set(('a an the and or but if then of to in on at by for with from into over under is are was were be been ' +
  'being do does did has have had will shall can may must should would could not no this that these those it its they them ' +
  'their you your we our as than so when while after before during until up down out off about again also only very each ' +
  'who which whom whose what where why how all any some both more most other such there here one two three').split(' '));

const forms = v => { const o = new Set([v, v+'s', v+'ed', v+'ing']);
  if (v.endsWith('e')) o.add(v+'d'); if (v.endsWith('y')) o.add(v.slice(0,-1)+'ied'); return [...o]; };
const sents = t => t.replace(/\s+/g,' ').trim().split(/(?<=[.!?:])\s+(?=[A-Z0-9(])/).filter(Boolean);
const wc = s => s.toLowerCase().replace(/[^a-z0-9' ]/g,' ').split(/\s+/).filter(Boolean);

function runs(s) { const out = [];
  for (const c of s.split(/[,;:.()]+/)) { let cur = [];
    for (const t of c.split(/\s+/).filter(Boolean)) {
      const l = t.toLowerCase().replace(/[^a-z0-9]/g,'');
      if (!l || /\d/.test(l) || STOP.has(l) || /(?:ed|ing|ly)$/.test(l)) {
        if (cur.length > NOUN) out.push(cur.join(' ')); cur = [];
      } else cur.push(t); }
    if (cur.length > NOUN) out.push(cur.join(' ')); }
  return out; }

function analyze(text, mode) {
  const lim = LIM[mode || 'proc'], paras = text.trim().split(/\n{2,}/), ss = paras.flatMap(sents);
  const lens = ss.map(s => wc(s).length), total = lens.reduce((a,b) => a+b, 0);
  const low = ' ' + text.toLowerCase().replace(/[^a-z0-9' ]/g,' ').replace(/\s+/g,' ') + ' ';
  const has = w => low.includes(' ' + w + ' ');
  const passive = (text.match(PASSIVE) || []).length;
  const pron = (text.match(/\b(?:it|they|them)\b/gi) || []).length;
  const vague = VAGUE.filter(has);
  const varied = Object.entries(SYN).filter(e => e[1].filter(v => forms(v).some(has)).length > 1).map(e => e[0]);
  const cl = ss.flatMap(runs), over = lens.filter(n => n > lim).length;
  const longP = paras.filter(p => sents(p).length > PARA).length;
  return { sents: ss.length, words: total, distinct: new Set(ss.flatMap(wc)).size,
    avg: +(total/ss.length).toFixed(1), max: Math.max(...lens), over, passive, pron,
    vague: vague.length, varied, clusters: cl.length,
    score: over*3 + passive*2 + vague.length + pron + varied.length*3 + cl.length*2 + longP*2 };
}
module.exports = { analyze };
if (require.main === module) { const fs = require('fs');
  console.log(analyze(fs.readFileSync(process.argv[2], 'utf8'), process.argv[3])); }
```

| 每句平均词数 | 30.7 | **8.5** | -72% |
| 最长句 | 40 | **18** | 进入上限内 |
| 超限句子 | 6 (100%) | **0** | 全部解决 |

## 4. 适用对象判断表

| 文档类型 | 套用 | 模式 | 理由 |
|---|---|---|---|
| 作业步骤书 · 维修指令 | **强制** | proc (20词) | 顺序颠倒就出事故 |
| 警告语 · 安全标识 | **强制** | proc (更严) | 紧急时要一次读完 |
| 安装 · 部署运行手册 | **强制** | proc | 第一次看到的人照着做 |
| API 参考 | **强制** | proc | 原样进入机器翻译与搜索摘要 |
| 界面文案 · 错误消息 | **强制** | proc | 变异直接就是翻译成本 |
| 规章 · 合同条款 | 部分 (只管词汇) | proc | 法律表述不能随便切 |
| 发布说明 | 只警告 | desc | 把背景也切掉就没用了 |
| 概念说明 · 架构文档 | **不套用** | — | 破坏规则的部分正是功能 |
| 教程 · 新人上手 | **不套用** | — | 上下文和动机占一半 |
| 设计决策记录 · 事后复盘 | **不套用** | — | 规则里没有「为什么」的位置 |

**分界线: 读者是不是一边读一边动手。** 是就强制，不是就不套用。

## 5. 先在原文一侧修的东西

| 习惯 | 在英语里发生什么 | 怎么修 |
|---|---|---|
| 省略主语 | 没有施事者，变成被动 | 在原文里写出主体 |
| 省略助词 | 变成一串名词 | 把谓语补回来 |
| 名词堆叠 | 4词名词短语，修饰关系有歧义 | 用动词拆开 |
| 用连接词尾串起来 | 一句里有多条指令 | 一条指令一句话 |
| 非终结式结尾 | 是义务还是建议会分裂 | 必须用祈使句，有条件用 if 从句 |

**翻译质量在写作环节就决定了，不是在翻译环节。**

## 7. 不要做的事

- ❌ 对整个仓库**从强制模式开始** — 人会把检查器关掉
- ❌ 照搬**别人的同义词清单** — 不同概念被塞进一个筐
- ❌ 用**扣分绝对值**评价文档 — 权重是随意的
- ❌ 把英语的20词上限套到**其他语言的文档**上
- ❌ 想**在翻译环节**解决翻译质量问题
- ❌ 没读规范正文就**编造规则**
- ❌ 给教程和事后复盘挂上受控规则 — 没有写「为什么」的位置
- ❌ 把检查器给出的**0当作证据** — 少一个词形变化就会出0
