Python을 Rust로 옮긴다는 결정

자동 변환 도구가 그은 경계선과, 실무에서 그 선을 다시 긋는 방법

2026-07-29 IT/기술

서론: 「Python을 Rust로 바꿔준다」에 생략된 조건

Python 코드를 Rust로 옮겨준다는 도구는 몇 년째 나오고 있다. 2026년 7월에도 Rextio라는 프로젝트가 공개됐다. 이런 소식을 볼 때마다 반사적으로 떠오르는 질문은 「그래서 우리 코드도 옮길 수 있나」인데, 이 질문은 거의 항상 잘못된 질문이다. 옳은 질문은 내 코드의 어느 부분이 옮겨질 수 있는 성질을 가졌는가이고, 그 답은 도구의 성능이 아니라 코드의 성질이 정한다.

Rextio 저장소 문서를 열어보면 이 점이 오히려 도구 쪽에서 먼저 명시돼 있다. 이 도구는 코드 전체를 옮기지 않는다. 타입 힌트가 붙은 함수 중 미리 정해둔 부분집합에 들어오는 것만 Rust와 PyO3 코드로 낮추고, 나머지는 원래의 Python 구현으로 그대로 둔다. 저장소가 내건 계약 문장은 짧다. 확신이 없으면 추측하지 않고 폴백한다. 그리고 함수는 CPython과 동등한 의미로 네이티브 컴파일되거나, 진단과 함께 거부되어 Python 폴백에 남는다.

먼저 선을 그어둔다. 이 글은 Rextio라는 특정 도구를 추천하거나 평가하지 않는다. 저장소는 스스로를 알파 단계로 표기하고 있고, 여러 기능에 실험적이라는 딱지가 붙어 있으며, 확인 시점의 스타 수는 한 자릿수였다. 지금 프로덕션에 넣을 물건은 아니다. 이 글이 관심을 두는 것은 하나다. 기계가 옮길 수 있는 것과 없는 것의 경계선이 어디에 그어지는가, 그리고 그 경계선이 실무의 판단을 어떻게 바꾸는가.

1. Rextio가 실제로 하는 일 - 공식 문서에서 확인된 것만

먼저 도구의 성격을 정확히 해두자. Rextio는 대화형 LLM에게 코드를 던져 Rust로 다시 써달라고 하는 종류가 아니다. 정적 분석기와 코드 생성기로 구성된 결정적 도구다. Python AST를 읽어 지원 범위에 들어오는 함수만 받아들이고, 나머지는 진단 메시지를 내며 거부한다. 산출물은 순수 Rust 프로그램이 아니라 네이티브 확장과 Python 폴백이 함께 들어 있는 하이브리드 패키지다.

실행 흐름도 단순하다. 소스에서 네이티브 후보를 찾고, 부적격한 것을 거부하고, 받아들인 것만 Rust와 PyO3 코드로 생성하고, 나머지에는 Python 폴백 래퍼를 만들고, 임포트 호환 아티팩트로 빌드한다.

python -m pip install rextio

rextio check .                      # 무엇이 네이티브로 내려가고 무엇이 거부되는지 진단만
rextio build . --fallback=cpython   # 하이브리드 패키지 빌드

REXTIO_NATIVE_MODE=fallback python app.py   # 런타임에 네이티브를 끄고 순수 Python 경로로

주목할 것은 세 번째 줄이다. 네이티브를 언제든 끌 수 있는 스위치가 처음부터 설계에 들어 있다. 저장소 문서는 이를 「네이티브는 최적화이지 필수 요건이 아니다」라는 문장으로 요약한다. 네이티브 모듈이 없거나 로드에 실패해도 패키지는 Python 폴백으로 계속 돈다. 뒤에서 다시 다루겠지만, 이 스위치는 도구를 쓰든 안 쓰든 직접 구현할 때도 반드시 따라 만들어야 하는 항목이다.

동작 요구사항은 CPython 3.11 이상(문서상 3.14까지 검증)과 Rust 최소 지원 버전 1.83 이상이다. 라이선스는 MIT다. 저장소가 공개한 벤치마크는 다음과 같다. 아래 수치는 전부 저장소 문서에 실린 값을 그대로 옮긴 것이며, 필자가 재현한 값이 아니다.

측정 환경은 Apple M4 Pro, CPython 3.11.9, 2026년 7월 26일 기준으로 표기돼 있다. 이 표에서 가져갈 교훈은 상단의 큰 숫자가 아니라 하단의 1배 근처 숫자다. 저장소 문서 스스로 「결과는 워크로드에 따라 다르며 1배 근처 값은 동등이지 유의미한 향상이 아니다」라고 밝히고 있다. 이미 무거운 연산이 C나 네이티브 라이브러리로 내려가 있는 코드에서는 Python 인터프리터가 태우던 시간 자체가 작기 때문에 가져올 것이 없다. 이 한 줄이 이 글 전체의 주제이기도 하다.

2. 자동 변환이 원리상 못 하는 것

Rextio가 지원하지 않는다고 밝힌 목록을 보면 성격이 뚜렷하게 갈린다. 클래스와 인스턴스 메서드, 동적 속성 접근, 제너레이터, async와 await, 컨텍스트 매니저, 가변 컬렉션의 별칭 변형, set[float] 반복, 스타 표현식과 star import, 동적 코드 실행, 그리고 플러그인 없는 대부분의 서드파티 호출이다.

이 목록은 우연이 아니다. 특정 도구의 미완성 항목이 아니라 정적 변환이라는 접근 자체가 부딪히는 벽이다. 각 항목이 왜 벽인지 정리하면 다음 표가 된다.

표의 마지막 두 줄이 특히 실무적이다. 같은 이름의 타입이 같은 의미가 아니라는 사실이 자동 변환에서 가장 조용하게 사고를 만든다. 컴파일도 되고 테스트도 통과하는데 특정 입력에서만 값이 갈리는 유형이다.

여기서 한 가지 정리가 가능하다. 자동 변환기가 다루는 범위는 겉모습만 Python이고 실질적으로는 정적 타입 언어인 부분집합이다. 타입 힌트가 완비돼 있고, 지역 변수만 쓰고, 스칼라와 단순 컨테이너만 오가는 순수 함수. 그런 코드는 애초에 Rust로 옮기기 쉬운 코드였다. 반대로 옮기고 싶은 마음이 간절한 코드, 즉 오랫동안 자라난 업무 로직은 대체로 이 부분집합 밖에 있다.

  • 거부를 실패로 읽지 말 것 — 도구가 함수를 거부하는 것은 정상 동작이다. 거부 없이 전부 받아들이는 도구가 있다면 그쪽이 위험하다.
  • 진단 메시지가 실제 산출물이다 — rextio check 같은 명령의 가치는 변환이 아니라 내 코드가 얼마나 정적인가를 측정해주는 것에 있다. 거부율이 90퍼센트면 그 코드베이스는 이 접근의 대상이 아니다.
  • 부분집합에 맞춰 코드를 고치는 순간 비용이 시작된다 — 도구에 통과하려고 클래스를 함수로 풀고 제너레이터를 리스트로 바꾸면, 그 코드는 이미 Python 관용구에서 멀어진다. 그 대가를 계산에 넣어야 한다.
  • 서드파티 호출은 사실상 벽이다 — 지원 목록에 없는 라이브러리를 한 줄만 호출해도 그 함수는 폴백으로 내려간다. 업무 코드에서 이 조건을 만족하는 함수는 생각보다 적다.

3. 「느리다」의 원인부터 확정하라

언어를 바꾸는 결정에 앞서 반드시 통과해야 하는 관문이 있다. 지금 느린 이유가 정말 언어인가. 실무에서 성능 문제로 접수되는 사례의 상당수는 인터프리터 속도와 무관하다. 원인별로 갈라 보면 처방이 완전히 달라진다.

확인 순서는 프로파일러가 먼저다. 누적 시간이 아니라 자기 시간 기준으로 정렬해야 실제로 CPU를 태우는 지점이 보인다.

# 자기 시간 기준으로 정렬해야 실제 소각 지점이 보인다
python -m cProfile -o prof.out run_workload.py

# 대화형 뷰어에서 sort tottime 을 입력한 뒤 stats 20
python -m pstats prof.out

그다음이 더 중요하다. 핫패스가 전체에서 차지하는 비율을 재고, 개선의 상한을 먼저 계산한다. 이 계산을 건너뛰면 몇 주를 들여 한 자릿수 개선을 얻는 일이 벌어진다.

# 핫함수가 전체의 p 비율을 차지하고 그 부분이 s배 빨라졌을 때 전체 개선폭
def upper_bound(p: float, s: float) -> float:
    return 1.0 / ((1.0 - p) + p / s)

print(upper_bound(0.20, 50))   # 1.2437...  -> 전체 20% 단축이 상한
print(upper_bound(0.70, 50))   # 3.2051...  -> 여기부터 투자할 가치가 생긴다
print(upper_bound(0.20, 1000)) # 1.2496...  -> 무한히 빨라져도 1.25배를 못 넘는다

세 번째 줄이 결론이다. 핫패스 비중이 낮으면 그 부분을 무한히 빠르게 만들어도 전체는 안 빨라진다. 실무 임계값을 하나 정한다면 이렇다. 자기 시간 상위 함수들의 합이 전체 실행 시간의 40퍼센트 미만이면 언어 전환을 검토 대상에서 뺀다. 60퍼센트를 넘으면 검토할 가치가 있고, 80퍼센트를 넘으면 대개 하는 편이 낫다.

4. 실무 정답은 전면 이식이 아니라 핫패스 확장 모듈

여기까지 왔다면 선택지는 두 개다. 애플리케이션 전체를 Rust로 다시 쓰거나, 핫패스만 네이티브 확장 모듈로 떼어내고 나머지는 Python으로 두거나. 결론부터 말하면 대부분의 조직에서 두 번째가 정답이고, 첫 번째가 정당화되는 조건은 매우 좁다.

이유는 경계 비용에 있다. Python과 네이티브 코드 사이에는 넘을 때마다 값을 변환하는 비용이 붙는다. 이 비용은 함수 호출마다 발생하고, 옮기는 데이터가 복잡할수록 커진다. 그래서 잘못 설계한 확장 모듈은 순수 Python보다 느려진다. 실제로 Rextio도 이 문제를 설계에 명시적으로 반영해, 컨테이너는 네이티브 경계를 넘지 못하게 하고 int, float, bool, str, None 같은 불변 스칼라만 폴백 함수로 전달하도록 제한한다. 경계를 반복해서 넘나드는 함수는 아예 폴백으로 강등한다는 규칙까지 두고 있다.

이 제약에서 확장 모듈 설계의 원칙이 그대로 도출된다.

  • 원소 단위로 부르지 않는다 — 100만 개 원소를 100만 번 호출하면 경계 비용이 계산 비용을 압도한다. 배열 하나를 통째로 넘겨 한 번 호출한다.
  • 경계를 넘는 데이터를 단순하게 유지한다 — 중첩 딕셔너리와 사용자 정의 객체는 변환 비용이 크다. 숫자 배열, 바이트열, 평평한 문자열 목록이 이상적이다.
  • 콜백을 넘기지 않는다 — 네이티브 코드가 다시 Python 함수를 부르면 매 원소마다 경계를 왕복한다. 이 구조가 나오면 경계를 잘못 그은 것이다.
  • 경계를 상태가 아니라 순수 함수로 만든다 — 네이티브 쪽에 오래 살아 있는 가변 상태를 두면 소유권 문제와 스레드 안전 문제가 동시에 따라온다.
  • 인터페이스가 자주 바뀌는 곳에 경계를 두지 않는다 — 매주 시그니처가 바뀌는 함수를 네이티브로 내리면 매주 빌드 매트릭스를 다시 돌리게 된다.
  • 순수 Python 구현을 지우지 않는다 — 두 구현을 나란히 유지하는 비용보다, 되돌릴 수 없게 되는 위험이 훨씬 크다.

같은 문제를 다른 언어 조합에서 다룬 논의는 Go에서 Rust로 마이그레이션 쪽에 정리해 두었다. 그쪽은 두 컴파일 언어 사이의 선택이라 판단 축이 다르지만, 공존 패턴과 안티 시그널은 그대로 겹친다.

5. PyO3와 maturin - 경계를 코드로 그리는 법

핫패스를 떼어내기로 했다면 실제 도구는 PyO3와 maturin이다. PyO3는 Rust와 Python을 잇는 바인딩이고, maturin은 그 결과물을 Python 휠로 빌드해준다. 아래는 PyO3 공식 저장소 기준 최신 릴리스인 0.29 계열의 선언형 모듈 문법이다. PyO3 0.29는 CPython 3.9 이상을 지원하며, Rust 최소 지원 버전은 1.83이다.

# Cargo.toml
[package]
name = "hotpath"
version = "0.1.0"
edition = "2021"

[lib]
name = "hotpath"
crate-type = ["cdylib"]

[dependencies]
pyo3 = "0.29.0"

// src/lib.rs
#[pyo3::pymodule]
mod hotpath {
    use pyo3::prelude::*;

    /// 배열을 통째로 받아 한 번에 처리한다.
    /// 원소마다 호출하지 않는 것이 이 설계의 전부다.
    #[pyfunction]
    fn clip_and_scale(values: Vec<f64>, lo: f64, hi: f64, k: f64) -> PyResult<Vec<f64>> {
        Ok(values
            .into_iter()
            .map(|v| v.clamp(lo, hi) * k)
            .collect())
    }
}

maturin new -b pyo3 hotpath   # 프로젝트 뼈대 생성
cd hotpath
maturin develop               # 현재 가상환경에 바로 설치(반복 개발용)
maturin build --release       # target/wheels 에 배포용 휠 생성

Python 쪽에서는 네이티브 구현과 순수 구현을 같은 이름으로 감싸되, 되돌릴 수 있게 만든다. 앞에서 본 환경 변수 스위치를 직접 만드는 형태다.

# myapp/kernel.py
import os

from myapp import kernel_py   # 순수 Python 원본 구현

_impl = kernel_py

if os.environ.get("MYAPP_NATIVE", "1") != "0":
    try:
        import hotpath as _native
        _impl = _native
    except ImportError:
        pass   # 휠이 없는 플랫폼에서도 그대로 동작한다

clip_and_scale = _impl.clip_and_scale

여기서 ImportError를 삼키는 것이 핵심이다. 네이티브 확장이 없는 플랫폼에서도 패키지가 설치되고 동작해야 배포가 단순해진다. 이 구조를 갖춰두면 성능 회귀가 의심될 때 환경 변수 하나로 두 구현을 비교할 수 있고, 사고가 났을 때 재배포 없이 되돌릴 수 있다.

6. 어디까지 네이티브로 내릴 것인가 - 판단표

「이 함수를 네이티브로 내릴까」는 감으로 정할 문제가 아니다. 아래 여섯 조건을 순서대로 통과시키고, 하나라도 아니오가 나오면 내리지 않는다는 규칙이 실무에서 가장 잘 버틴다.

확인 항목통과 임계값아니오일 때의 처방
전체 실행 시간에서의 비중자기 시간 기준 20퍼센트 이상다른 곳을 먼저 본다
호출당 작업량1회 호출에 밀리초 단위 이상 계산배치 단위로 묶어 호출 횟수를 줄인다
경계를 넘는 데이터 형태스칼라 · 평평한 배열 · 바이트열인터페이스를 먼저 평평하게 만든다
인터페이스 변경 빈도분기당 1회 이하설계가 굳을 때까지 미룬다
Rust를 읽고 고칠 수 있는 인원2명 이상사람부터 확보한다. 1명이면 조직 부채다
순수 Python 대안 유지항상 유지 + 되돌림 스위치되돌릴 수 없으면 아직 넣지 않는다

다섯 번째 항목이 자주 무시된다. 확장 모듈은 그것을 만든 사람이 떠나는 순간 블랙박스가 된다. Python 개발자만 남은 팀에서 Rust 확장 모듈에 버그가 나면, 선택지는 「고칠 수 있는 사람을 구한다」와 「순수 Python으로 되돌린다」 둘뿐이다. 여섯 번째 항목을 지켜두면 후자가 30초짜리 작업이 되고, 안 지켜두면 몇 주짜리 사고가 된다.

반대로 전면 이식을 검토해도 되는 조건도 정리해 두자. 넷을 모두 만족할 때만이다. 산출물 자체가 배포 단위인 도구이거나 라이브러리 코어일 것, 외부 인터페이스가 좁고 안정적일 것, 실행 시간의 대부분이 CPU 계산일 것, 그리고 팀에 Rust를 주 언어로 다루는 인원이 이미 있을 것.

7. Rust로 다시 쓴 도구들이 실제로 증명한 것

Python 생태계에서 Rust 재작성의 성공 사례로 자주 언급되는 것들이 있다. 각각의 공식 문서가 실제로 주장하는 수치만 옮기면 다음과 같다.

프로젝트공식 자료가 밝힌 내용대상 영역
ruff기존 린터(Flake8)와 포매터(Black) 대비 10~100배 빠르다고 저장소가 명시. Rust로 작성, MIT정적 분석 도구
uv캐시 없이 pip 및 pip-tools 대비 8~10배, 웜 캐시에서 80~115배. 가상환경 생성은 python -m venv 대비 약 80배, virtualenv 대비 7배패키지 관리 도구
pydantic공식 문서가 핵심 검증 로직이 Rust로 작성됐으며 그 결과 Python에서 가장 빠른 데이터 검증 라이브러리 축에 든다고 서술라이브러리 코어
CPython 자체Rust for CPython 계획이 3.16을 목표로 확장 모듈 한 개를 Rust로 구현하는 개념 증명을 진행하고 PEP을 준비 중이라고 공식 블로그가 공지인터프리터 내부

이 목록에서 배수 자체보다 중요한 것은 공통점이다. 넷 다 업무 애플리케이션이 아니다. 개발 도구이거나, 라이브러리의 검증 코어이거나, 인터프리터 내부다. 세 가지 성질을 공유한다.

  • 인터페이스가 좁고 오래 안정적이다 — 린터의 입력은 소스 파일이고 출력은 진단 목록이다. 이 계약은 몇 년째 그대로다.
  • 실행 시간의 대부분이 CPU 계산이다 — 파싱, 규칙 매칭, 의존성 해석은 전부 인터프리터가 태우던 시간이다.
  • 배포 단위가 이미 바이너리 휠이다 — 사용자는 소스가 무슨 언어인지 알 필요가 없다. 플랫폼별 휠만 있으면 된다.

반대로 말하면, 이 세 조건을 만족하지 않는 코드에 같은 결과를 기대할 근거가 없다. 요청 하나에 데이터베이스를 세 번 왕복하는 웹 애플리케이션은 세 조건 모두에서 반대편에 있다. 성공 사례를 인용할 때는 그 사례가 어느 영역에 속하는지를 함께 봐야 한다.

참고로 AI 에이전트로 대규모 코드베이스를 통째로 Rust에 옮기는 시도도 2026년에 여럿 나왔는데, 무엇이 증명되고 무엇이 증명되지 않았는지는 Git을 Rust로 재작성한 시도에서 따로 다뤘다. 요지는 같다. 옮겨졌다는 것과 검증됐다는 것은 다른 문장이다.

8. 반대편 비용 - 학습 곡선 · 빌드 시간 · 생태계 공백

전환 논의는 대개 이득만 계산하고 끝난다. 반대편 비용은 도입 시점이 아니라 6개월 뒤부터 청구되기 때문이다. 항목별로 나눠 보자.

8.1 빌드 시간은 측정된 문제다

Rust 공식 블로그가 공개한 2025년 컴파일러 성능 설문 결과는 3,700건 이상의 응답을 담고 있고, 전반적 만족도는 10점 만점에 6점으로 보고됐다. 눈여겨볼 수치는 다음과 같다.

  • Rust 사용을 중단한 응답자의 약 45퍼센트가 중단 이유 중 하나로 긴 컴파일 시간을 꼽았다.
  • 55퍼센트가 코드를 고친 뒤 재빌드에 10초 이상 기다린다고 답했다. 병목은 워크스페이스 변경이 유발하는 불필요한 재빌드, 느린 링크 단계, 단일 크레이트 내부의 증분 컴파일 세 가지로 정리됐다.
  • 약 33퍼센트가 IDE 인라인 주석을 기다리는 것을 큰 장애로, 35퍼센트 이상이 IDE와 Cargo가 서로를 막는 문제를 큰 문제로 답했다.
  • CI 사용자 1,495명 중 약 25퍼센트가 CI 빌드 성능을 큰 문제로 꼽았는데, 그중 약 36퍼센트는 CI에서 캐싱을 전혀 쓰지 않고 있었다.
  • 전체 응답자의 약 42퍼센트는 빌드 성능 개선 수단을 하나도 시도해본 적이 없다고 답했다.

마지막 두 항목은 뒤집어 읽을 만하다. 불평의 상당 부분은 아직 손대지 않은 여지에서 나온다. 캐싱, 링커 교체, 워크스페이스 분할 같은 기본 조치를 하지 않은 상태에서 「Rust는 느리다」고 결론 내리면 잘못된 결론이 된다. 다만 팀에 그 조치를 할 사람이 없다면 실질 비용은 그대로다.

8.2 배포가 한 축 늘어난다

순수 Python 패키지는 휠 하나면 끝난다. 네이티브 확장이 붙는 순간 플랫폼 × 아키텍처 × Python 버전의 곱만큼 빌드가 필요해진다. 안정 ABI를 쓰면 Python 버전 축을 줄일 수 있지만 대신 쓸 수 있는 API가 제한된다. 여기에 크로스 컴파일, 서명, 사내 미러 등록이 따라붙는다. 이 작업은 한 번 만들면 끝이 아니라 새 Python 버전이 나올 때마다 반복된다.

8.3 사람이 가장 비싸다

  • 읽을 수 있는 사람과 고칠 수 있는 사람은 다르다 — 소유권과 수명 오류를 만나 스스로 해결할 수 있어야 고칠 수 있는 사람이다.
  • 온콜 로테이션에 들어가야 한다 — 새벽에 그 모듈이 터졌을 때 대응할 수 있는 인원이 한 명이면 그 모듈은 단일 장애점이다.
  • 리뷰 병목이 생긴다 — Rust 코드를 리뷰할 수 있는 사람이 한 명이면 그 사람의 휴가가 곧 배포 정지다.
  • 채용 조건이 바뀐다 — Python 포지션 하나가 Python과 Rust를 함께 요구하는 포지션이 되면 후보군이 줄고 기간이 늘어난다.

8.4 생태계 공백

Python 쪽에 이미 있는 것이 Rust 쪽에 없거나, 있어도 성숙도가 낮은 경우가 있다. 도메인 특화 수치 라이브러리, 특정 벤더의 클라이언트 SDK, 사내 표준 로깅·추적 계층 같은 것들이다. 핫패스만 떼어내는 접근이 유리한 이유가 여기에도 있다. 경계를 좁게 잡으면 필요한 Rust 라이브러리도 그만큼 적어진다. 메모리 안전성을 근거로 재작성을 밀어붙이는 주장과 그 반론은 메모리 안전성 절대주의 논쟁에서 별도로 정리했다.

9. 생성된 Rust 코드를 어떻게 검증할 것인가

도구가 만들어준 코드든 사람이 쓴 코드든, 두 구현이 정말 같은 답을 내는지는 별도로 증명해야 한다. 컴파일 성공은 아무것도 보장하지 않는다. 실행 가능한 형태로 정리하면 세 단계다.

9.1 차등 테스트 - 같은 입력, 두 구현

# tests/test_parity.py
import math
from hypothesis import given, settings, strategies as st

from myapp import kernel_py            # 순수 Python 원본
import hotpath                          # 네이티브 구현

FINITE = st.floats(allow_nan=False, allow_infinity=False, width=64)

@settings(max_examples=1000)
@given(st.lists(FINITE, max_size=4096), FINITE, FINITE, FINITE)
def test_same_output(values, lo, hi, k):
    if lo > hi:
        lo, hi = hi, lo
    expected = kernel_py.clip_and_scale(values, lo, hi, k)
    actual = hotpath.clip_and_scale(values, lo, hi, k)
    assert len(expected) == len(actual)
    for a, b in zip(expected, actual):
        assert math.isclose(a, b, rel_tol=1e-12, abs_tol=0.0)

부동소수를 비교할 때 허용 오차를 두는 순간 「동등」이 아니라 「근사」를 검증하고 있다는 사실을 문서에 남겨야 한다. 회계나 정산처럼 마지막 자리가 의미를 갖는 도메인이면 허용 오차를 두지 말고 정수 또는 십진 타입으로 계산을 옮기는 편이 낫다.

9.2 경계값은 무작위로 안 나온다

프로퍼티 테스트는 폭을 넓혀주지만 가장 위험한 입력은 대체로 뽑히지 않는다. 고정 목록으로 따로 관리한다.

EDGE_CASES = [
    [],                       # 빈 입력
    [0.0], [-0.0],            # 0과 음의 0은 비트가 다르다
    [float("inf"), float("-inf")],
    [float("nan")],           # 자기 자신과 같지 않다. 정렬·중복제거가 갈린다
    [1e308, -1e308],          # 오버플로 직전
    [1.0] * 1_000_000,        # 경계를 넘는 복사 비용이 드러나는 크기
]
  • 정수 오버플로 — Python 정수는 임의 정밀도이고 Rust의 i64는 고정 폭이다. 릴리스 빌드에서는 오버플로가 감싸고 돌아 조용히 틀린 값이 된다. 옮기는 함수에 큰 정수가 들어올 수 있는지 반드시 확인한다.
  • 나머지 연산의 부호 — Python의 %는 제수의 부호를 따르고 Rust의 %는 피제수의 부호를 따른다. -7 % 3은 Python에서 2, Rust에서 -1이다. Python과 같게 하려면 rem_euclid를 쓴다.
  • 정렬 안정성 — 두 원소의 키가 같을 때 원래 순서가 유지되는지 확인한다. 안정성이 다르면 결과 목록의 순서가 갈린다.
  • 딕셔너리 삽입 순서 — Python 딕셔너리는 삽입 순서를 유지한다. Rust의 해시 맵은 그렇지 않다. 순서에 의존하는 소비자가 있으면 사고가 난다.
  • 유니코드 길이 — Python 문자열의 길이는 코드 포인트 수이고 Rust의 len()은 바이트 수다. 슬라이싱 인덱스를 그대로 옮기면 깨진다.
  • 예외의 타입과 메시지 — 호출부가 예외 타입으로 분기하고 있다면 그 타입까지 같아야 한다. 메시지 문자열에 의존하는 코드가 있는지도 확인한다.

9.3 되돌림 경로를 배포 전에 시험한다

앞 절에서 만든 환경 변수 스위치는 만들어 두는 것으로 끝나지 않는다. 릴리스마다 순수 Python 경로로 전체 테스트를 한 번 더 돌려야 그 경로가 살아 있음이 보장된다. 실무에서 자주 보는 실패는 스위치를 만들어 두고 1년간 안 써서, 정작 필요한 순간에 순수 구현이 이미 인터페이스가 어긋나 있는 상황이다.

검증 항목방법통과 기준
결과 동등성차등 테스트 + 프로퍼티 테스트무작위 1,000건 이상에서 불일치 0건
경계값고정 목록 + 두 언어 규칙 차이 점검목록 전건 통과, 예외 타입까지 일치
성능대표 워크로드 벤치마크 3회 중앙값목표 배수 미달이면 경계 설계 재검토
폴백 경로네이티브 비활성화 후 전체 테스트릴리스마다 통과 확인
휠 배포지원 플랫폼 전부에서 임포트 확인미지원 플랫폼에서도 설치·동작

10. GIL이 사라지는 중이라는 변수

병렬성 때문에 Rust를 검토하는 경우라면 전제가 바뀌고 있다는 점을 계산에 넣어야 한다. CPython은 3.13부터 GIL을 끈 free threading 빌드를 제공한다. 다만 공짜는 아니다. 공식 문서는 free threading 빌드가 기본 빌드보다 오버헤드가 있으며, pyperformance 기준 평균 오버헤드가 macOS aarch64에서 약 1퍼센트, x86-64 리눅스에서 약 8퍼센트 범위라고 밝히고 있다.

여기에 확장 모듈을 만드는 쪽에서 반드시 알아야 할 조항이 하나 더 있다. 공식 문서는 확장 모듈이 있는 일부 서드파티 패키지가 free threading 빌드에서 준비되지 않았을 수 있으며 GIL을 다시 켠다고 적고 있다. free threading 지원이 명시되지 않은 C-API 확장 모듈을 임포트하면 GIL이 자동으로 다시 켜지고 경고가 출력된다.

  • 내 확장 모듈이 남의 병렬성을 죽일 수 있다 — 지원을 선언하지 않은 확장 하나가 프로세스 전체의 GIL을 되살린다. 확장 모듈을 배포한다면 이 선언은 선택이 아니다.
  • 병렬화가 목적이면 순서를 바꿔볼 만하다 — 언어를 바꾸기 전에 free threading 빌드에서 기존 코드가 어떻게 도는지 먼저 재보는 편이 비용이 적다.
  • 단일 스레드 오버헤드는 워크로드마다 다르다 — 위 범위는 벤치마크 스위트 평균이다. 자기 워크로드로 직접 재야 한다.
  • 인터프리터 자체도 Rust를 들이는 중이다 — Rust for CPython 계획은 3.16을 목표로 확장 모듈 한 개를 Rust로 구현하는 개념 증명을 진행하고 PEP을 준비 중이라고 공식 블로그가 밝혔다. 장기적으로 두 언어의 접점은 넓어진다.

11. 도입 여부를 판단하는 절차

마지막으로 옮길 수 있는 형태로 정리한다. 이 순서를 그대로 밟으면 대부분 3단계나 4단계에서 결론이 난다.

  1. 대표 워크로드를 하나 고정한다 — 실제 프로덕션 트래픽에서 뜬 것이어야 한다. 합성 벤치마크는 결론을 낙관적으로 만든다.
  2. 벽시계 시간과 CPU 시간을 나눠 잰다 — 둘의 차이가 크면 원인은 대기이고, 언어 전환은 여기서 끝난다.
  3. 자기 시간 기준으로 상위 함수를 뽑는다 — 누적 시간으로 보면 호출 스택 위쪽만 보인다.
  4. 상위 함수 합계 비중으로 상한을 계산한다 — 40퍼센트 미만이면 여기서 중단한다. 다른 곳을 고칠 때다.
  5. 알고리즘과 자료구조를 먼저 본다 — 차수를 줄이는 변경이 남아 있으면 그것이 항상 먼저다.
  6. C로 이미 내려간 부분인지 확인한다 — 수치 라이브러리 내부에서 도는 시간이면 가져올 여지가 거의 없다.
  7. 경계 후보 함수의 인터페이스를 평평하게 만든다 — 이 작업은 Rust 없이 순수 Python 상태에서 먼저 끝낸다.
  8. 정적 분석 도구로 부분집합 적합도를 재본다 — 거부율이 높으면 자동 변환은 접고 수동 이식만 검토한다.
  9. 가장 비중이 큰 함수 하나만 옮겨 실측한다 — 한 개다. 여러 개를 동시에 옮기면 무엇이 효과를 냈는지 모른다.
  10. 차등 테스트와 폴백 경로를 갖춘 뒤 배포한다 — 되돌림 스위치가 동작하는 것을 확인한 뒤에만 내보낸다.
  11. 운영 지표로 다시 잰다 — 벤치마크가 아니라 실제 지연 시간 분포로 확인한다. 꼬리 지연이 안 줄었으면 다른 원인이 남아 있다.
  12. 효과가 없으면 되돌린다 — 이미 만든 것이 아깝다는 이유로 유지하는 것이 가장 비싼 선택이다.

결론: 도구는 경계를 보여줄 뿐, 경계를 정해주지 않는다

Rextio 같은 도구가 실제로 제공하는 가장 큰 가치는 변환 자체가 아니라 진단일 가능성이 높다. 내 코드베이스의 몇 퍼센트가 정적으로 고정 가능한 형태인지, 어떤 함수가 왜 거부되는지를 알려주는 것만으로도 판단 재료가 된다. 반대로 도구가 만들어준 결과물을 그대로 프로덕션에 넣는 시나리오는, 적어도 알파 단계 도구에 대해서는 검토 대상이 아니다.

이 글에서 반복한 문장을 하나로 줄이면 이렇다. 전부 다시 쓰기와 아무것도 안 하기 사이에 실무의 답이 있고, 그 답은 경계를 어디에 긋느냐로 결정된다. 경계를 잘 그으면 코드의 5퍼센트를 옮겨 성능 문제의 대부분을 해결하고 나머지 95퍼센트는 Python의 생산성을 그대로 누린다. 경계를 잘못 그으면 두 언어의 단점만 모아 놓은 시스템이 된다. 빌드는 느리고, 고칠 수 있는 사람은 한 명이고, 되돌릴 수도 없는 상태다.

그리고 순서를 뒤집지 말자. 프로파일링이 먼저고, 알고리즘이 그다음이고, 언어는 마지막이다. 이 순서를 지키면 대부분의 경우 언어까지 갈 일이 없다는 사실을 알게 되는데, 그것이 이 검토의 가장 흔한 결론이자 가장 값싼 결론이다.
