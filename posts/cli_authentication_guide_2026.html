CLI 인증, 제대로 하는 법 — 커맨드라인 도구의 안전한 인증 설계

2026-06-22 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

왜 CLI 인증은 따로 생각해야 하나

웹 앱 인증과 CLI 인증은 표면이 다르다. 웹 앱은 브라우저가 있고, 쿠키가 있고, 세션 스토리지가 있다. CLI는 터미널만 있다. 이 차이 하나가 인증 설계 전체를 바꾼다. 2026년 6월 기준으로 Claude Code·GitHub CLI·AWS CLI·Stripe CLI 같은 도구들이 수백만 개발자의 로컬 머신에 설치돼 있고, 각각 자격증명을 다루는 방식이 다르다. 그리고 그 방식이 잘못됐을 때 터지는 피해는 웹 XSS 한 건보다 조용하고 넓다.

GitGuardian의 2026년 보고서에 따르면 2025년 한 해 동안 공개 GitHub 커밋에서 약 2,865만 건의 하드코딩된 자격증명이 발견됐고, AI 서비스 키 노출은 전년 대비 81% 증가했다. 이 중 상당수는 CLI 도구를 만들거나 쓰는 개발자의 실수다. CLI 특유의 인증 흐름을 제대로 알면 이 문제의 상당 부분을 원천 차단할 수 있다.

이 글은 두 독자를 동시에 겨냥한다. 첫째, CLI 도구를 직접 만드는 개발자. 인증을 어떻게 설계할지 선택 기준과 구현 패턴을 제공한다. 둘째, CLI 도구를 쓰는 개발자. 내가 쓰는 도구가 자격증명을 어떻게 다루는지 이해하고 리스크를 관리할 수 있도록 한다. 본인의 관점은 명확하다. 보안은 편의와 맞교환이 아니라, 올바른 추상화를 선택하면 편의와 보안이 함께 온다.

1. CLI 인증의 4가지 패턴 — 선택 지도

CLI가 서비스에 인증하는 방법은 크게 4가지다. 각각 맞는 맥락이 다르고, 잘못된 맥락에 쓰면 보안 문제가 생긴다.

1.1 OAuth 2.0 Authorization Code + PKCE (브라우저 위임)

CLI가 로컬 TCP 포트(예: localhost:8484)를 열고, 브라우저를 그 포트의 리다이렉트 URI로 구성된 Authorization 엔드포인트로 띄운다. 사용자가 브라우저에서 로그인하면 인증 서버가 code를 로컬 포트로 돌려준다. CLI는 이 코드를 액세스 토큰·리프레시 토큰과 교환한다.

여기서 PKCE(Proof Key for Code Exchange, RFC 7636)가 핵심이다. CLI는 public client이므로 client_secret을 안전하게 보관할 방법이 없다. PKCE는 이 문제를 해결한다. 세션마다 암호학적 난수 code_verifier를 생성하고, 그 SHA-256 해시를 code_challenge로 서버에 보낸다. 코드 교환 시 원본 verifier를 제출해 동일 세션임을 증명한다. 가로챈 코드만으로는 토큰을 발급받을 수 없다.

이 패턴이 맞는 조건은 사용자가 같은 머신에 앉아 있고, 브라우저를 열 수 있으며, CLI가 로컬 포트를 바인딩할 수 있을 때다. GitHub CLI(gh auth login)가 이 방식이다. 빠르고 폴링이 없으며 피싱 저항성이 높다.

1.2 OAuth 2.0 Device Authorization Grant — RFC 8628 (헤드리스 위임)

SSH 원격 세션, 컨테이너 내부, TV/임베디드 기기처럼 브라우저를 열 수 없는 환경을 위한 표준이다. CLI가 인증 서버에 device code를 요청하면, 서버는 device_code(내부 식별자), user_code(사람이 읽을 수 있는 짧은 코드), verification_uri를 반환한다. CLI는 "브라우저에서 이 URL로 가서 이 코드를 입력하세요"라는 메시지를 출력하고, 백그라운드에서 폴링하며 사용자가 다른 기기 브라우저로 인증을 완료하기를 기다린다.

이 흐름의 보안 전제는 user_code가 짧은 시간 안에 소멸하고, 인증 서버가 verification_uri에 HTTPS를 강제하며, 폴링 간격(interval 필드)을 준수해 인증 서버를 DoS로 공격하지 않는다는 것이다. Claude Code가 이 방식을 사용한다. gh codespace ssh 같은 헤드리스 환경에서도 마찬가지다.

1.3 API 키 (자동화·서비스 계정)

CI/CD 파이프라인, 크론 잡, 서비스 계정처럼 인터랙티브 로그인이 구조적으로 불가능한 환경에 적합하다. 단순하고 어디서나 쓸 수 있다는 장점이 있지만, 만료 없이 발급하면 유출 시 피해 기간이 무제한이라는 단점이 있다. 로컬 개발에서는 OAuth 플로우가 있다면 API 키보다 안전하다. OAuth 토큰은 보통 1시간에 만료되지만, API 키는 명시적으로 폐기하기 전까지 살아 있다.

1.4 기기 자격증명 / 서비스 계정 토큰 (클라우드 환경)

AWS IMDSv2, GCP Workload Identity Federation, Azure Managed Identity처럼 클라우드 인프라가 기기 자체에 단기 토큰을 부여하는 방식이다. CI/CD 환경에서 장기 시크릿을 주입하는 대신 이 패턴을 쓰면 시크릿 관리 부담이 사라진다. 2026년 기준 GitHub Actions의 OIDC 토큰 + AWS assume-role 조합이 가장 널리 권장되는 CI/CD 패턴이다.

2. PKCE 구현 — 코드 수준에서 놓치는 것들

PKCE를 "그냥 code_challenge 붙이면 되지"라고 생각하면 놓치는 함정이 있다.

2.1 code_verifier 생성

RFC 7636은 verifier를 "암호학적으로 안전한 난수, 43~128자 URL-safe 문자열"로 규정한다. Python에서는 secrets.token_urlsafe(96), Node.js에서는 crypto.randomBytes(96).toString('base64url')이 올바른 방법이다. Math.random()이나 uuid는 암호학적 난수가 아니다. 세션마다 새로 생성해야 하며, 이전 verifier를 재사용하면 공격자가 패턴을 학습할 수 있다.

2.2 S256 방식만 써야 한다

code_challenge_method=plain은 verifier를 그대로 challenge로 쓰는 방식이라 인증 서버와 CLI 사이의 MITM 공격에 취약하다. 반드시 S256(SHA-256 해시 후 base64url 인코딩)을 써야 한다. 2026년 시점에서 OAuth 2.1 초안은 S256을 강제하고 plain을 폐기할 방향이다. 인증 서버가 plain만 지원한다면 그 서버 자체가 취약한 것이다.

2.3 state 파라미터로 CSRF 방어

로컬 리다이렉트를 받을 때, state 파라미터 없이 코드를 받으면 CSRF 공격에 열려 있다. CLI가 Authorization 요청을 보낼 때 암호학적 난수 state를 생성하고, 리다이렉트 수신 시 동일 state인지 검증해야 한다. 다른 탭이나 공격자가 조작한 리다이렉트가 올 수 있다.

2.4 로컬 포트 바인딩 실패 처리

포트 8484가 이미 사용 중일 수 있다. CLI는 여러 포트를 순서대로 시도하거나, 실패 시 device flow로 graceful fallback해야 한다. 포트가 열리지 않아 인증이 무음으로 실패하는 경험은 사용자가 "내가 잘못한 건가"라고 생각하게 만드는 나쁜 UX다.

3. 토큰 저장 — "어디에 쓰느냐"가 보안의 90%

인증 플로우를 완벽하게 구현해도 토큰을 잘못 보관하면 의미가 없다. 저장 위치별 위험도를 정직하게 비교한다.

3.1 OS 암호화 자격증명 저장소 — 1순위

macOS Keychain, Windows Credential Manager, Linux Secret Service(D-Bus 기반, libsecret/gnome-keyring)는 OS가 기본 제공하는 암호화 저장소다. 공통 특성은 세 가지다. OS 수준 암호화(macOS는 Secure Enclave 연동 가능), 해당 앱의 ACL 기반 접근 제어, 하드웨어 보안 모듈(있다면) 연동이다.

CLI 개발자는 플랫폼별 분기를 직접 짜기보다 언어별 추상화 라이브러리를 쓰는 게 현실적이다. Go에서는 zalando/go-keyring, Python에서는 keyring, Node.js에서는 keytar가 이 역할을 한다. GitHub CLI는 keyring을 직접 구현하지 않고 기존 라이브러리에 위임한다. 이 방식이 맞다.

3.2 파일 기반 저장 — 조건부 허용

키체인을 쓸 수 없는 환경(예: 키체인 데몬이 없는 최소 컨테이너)에서는 파일에 저장할 수 있다. 단 조건이 있다. 파일 권한을 600(소유자만 읽기/쓰기)으로 강제해야 하고, 토큰 파일이 있는 디렉토리는 gitignore에 들어가야 하며, 평문이 아닌 OS 제공 암호화 또는 적어도 패스프레이즈 기반 암호화를 고려해야 한다. AWS CLI의 ~/.aws/credentials가 이 패턴이다. 편하지만 파일이 백업에 포함되거나 git에 실수로 추가될 위험이 항상 있다.

3.3 환경 변수 — CI/CD에만

환경 변수는 프로세스 목록(/proc/PID/environ)에 노출되고, 자식 프로세스에 자동 상속되며, 크래시 리포터가 덤프할 수 있다. 로컬 개발에서 장기 API 키를 환경 변수로 관리하면 그 값이 생각보다 많은 곳에 흘러 들어간다. CI/CD에서는 시크릿 스토어(GitHub Secrets, Vault 등)에서 주입받은 단기 값이므로 다른 얘기다.

3.4 절대 하면 안 되는 것들

소스 코드에 하드코딩하는 것은 1순위 금지다. 의도가 없어도 TOKEN=abc123이 한 줄 들어가면 그 순간 git history에 영원히 박힌다. .env 파일을 gitignore 없이 생성하는 것, 토큰을 로그에 출력하는 것(디버그 로그 포함), curl/wget 인수에 토큰을 평문으로 넣어 ps aux에 노출하는 것 모두 실제로 흔히 발생하는 실수다.

4. API 키 취급 — 실수의 90%는 여기서 난다

OAuth 플로우 없이 API 키만 사용하는 CLI를 만들거나 쓸 때의 실무 지침이다.

4.1 키 설계 원칙

CLI에서 발급하는 API 키는 최소 권한으로 시작해야 한다. "관리자 키 하나 발급해서 쓰면 편하잖아"는 편한 만큼 위험하다. 읽기 전용 작업에 쓰기 권한까지 있는 키를 노출할 필요가 없다. 키에는 만료일을 붙여야 한다. 90일 로테이션이 업계 권장 주기다. 만료 없는 키는 노출 시 피해 기간이 무한정이다. 가능하다면 키마다 사용 범위를 제한하고(특정 IP, 특정 리소스), 최소 사용 단위로 쪼개는 것이 이상적이다.

4.2 노출 사후 대응

키가 노출됐다면 첫 번째 행동은 파일 삭제가 아니라 키 즉각 폐기다. git에 이미 커밋된 경우 git rm으로 파일을 지워도 git log -S 'KEY_VALUE'를 치면 히스토리에서 찾을 수 있다. git-filter-repo로 히스토리를 재작성하더라도 이미 클론한 사람, 포크, GitHub 캐시, 서드파티 스캐너가 갖고 있을 수 있다. 노출 즉시 폐기, 새 키 발급, 로그에서 노출 키로 한 요청 감사가 순서다.

4.3 pre-commit 훅으로 예방

GitGuardian, truffleHog, detect-secrets 같은 pre-commit 스캐너를 팀 표준으로 넣으면 커밋 시점에 시크릿을 잡아준다. pre-commit 프레임워크에 detect-secrets 훅을 추가하는 것은 5분 작업이다. 이 방어선 하나가 가장 흔한 실수를 막는다.

5. 토큰 리프레시 — 사용자 경험과 보안의 교차점

액세스 토큰을 짧게 유지하는 것이 보안에 좋다. 그러나 사용자가 명령 실행할 때마다 재로그인을 강요하면 아무도 쓰지 않는다. 리프레시 토큰 패턴이 이 균형을 맞춘다.

5.1 투명한 갱신

CLI가 API 호출 전에 액세스 토큰 만료를 확인하거나, 401 응답을 받으면 자동으로 리프레시 토큰으로 새 액세스 토큰을 발급받는다. 사용자는 이 과정을 알 필요가 없다. 갱신 실패(리프레시 토큰 만료, 폐기)가 발생했을 때 처음으로 재인증 플로우를 안내해야 한다. 구현상 주의점은 CLI가 병렬로 여러 요청을 날리면 동시에 여러 갱신 시도가 생긴다는 것이다. mutex 또는 단일 갱신 고루틴 패턴으로 경합을 막아야 한다.

5.2 리프레시 토큰 로테이션

리프레시 토큰은 사용 시마다 새 것을 받고 구 것을 폐기하는 로테이션 방식이 안전하다. 구 리프레시 토큰으로 갱신 시도가 들어오면 토큰 탈취를 의심하고 세션 전체를 무효화하는 서버 정책이 이상적이다. 이 패턴을 "refresh token rotation with reuse detection"이라고 부른다. Auth0, Okta, Keycloak이 기본 지원한다.

5.3 토큰 유효기간 현실적 기준

액세스 토큰은 1시간이 업계 표준이다. 리프레시 토큰은 30일~90일이 일반적이다. 사용할 때마다 로테이션한다면 활성 사용자는 무기한 세션을 유지할 수 있고, 일정 기간 사용하지 않으면 자동 만료된다. 이 방식이 "영구 로그인"의 편의와 "탈취된 토큰의 수명 제한"을 동시에 주는 구조다.

6. 보안 함정 목록 — 실제로 잘못되는 패턴들

실무에서 실제로 보이는 잘못된 패턴들을 정리한다. 본인이 각 도구를 감사할 때 체크하는 항목이다.

6.1 client_secret을 바이너리에 포함

CLI는 공개 클라이언트다. 배포된 바이너리에서 strings 명령으로 client_secret을 추출하는 것은 10초 작업이다. CLI에서는 client_secret을 쓰면 안 된다. PKCE가 이 문제의 해답이다. 만약 서버가 client_secret을 강제한다면, 그 서버가 public client를 올바르게 지원하지 않는 것이다.

6.2 토큰을 로그에 출력

디버그 모드에서 HTTP 요청 헤더 전체를 로그에 찍으면 Authorization: Bearer {token}이 그대로 기록된다. 로그는 보통 파일로 저장되고 로그 수집 시스템으로 흘러간다. 토큰을 로그에 출력할 때는 반드시 마스킹(Bearer sk-...XXXX 등)해야 한다.

6.3 토큰 만료 후에도 로컬 캐시 유지

만료된 토큰이 로컬에 남아 있으면 공격자가 오프라인 상태의 머신에서도 토큰 파일을 읽을 수 있다. 기술적으로는 서버가 만료된 토큰을 거부하지만, 타임스탬프 조작이나 클럭 드리프트를 이용한 재사용 시도 가능성이 있다. 만료된 토큰은 갱신 즉시 파일에서 덮어쓰고, 로그아웃 시 명시적으로 삭제해야 한다.

6.4 device code 폴링 간격 무시

RFC 8628은 interval 필드(기본 5초)를 반환하고, 클라이언트가 이 간격보다 빠르게 폴링하면 slow_down 응답을 받는다고 명시한다. 폴링 간격을 무시하고 빠르게 때리면 인증 서버에 불필요한 부하를 준다. 백오프 로직을 구현해야 하고, slow_down 응답 시 interval을 5초씩 증가시켜야 한다.

6.5 리다이렉트 URI 검증 부재

인증 서버가 리다이렉트 URI를 사전 등록 없이 받아들이거나, 와일드카드(http://localhost:*)로 등록하면 공격자가 다른 포트로 코드를 가로챌 수 있다. 인증 서버 설정에서 허용 리다이렉트 URI를 정확히 고정해야 한다.

7. CI/CD 환경의 CLI 인증 — 다른 게임의 규칙

로컬 개발과 CI/CD는 인증 패턴이 달라야 한다. 많은 팀이 로컬 개발용 패턴을 CI에 그대로 이식해서 문제가 생긴다.

7.1 OIDC 토큰으로 장기 시크릿 제거

GitHub Actions의 OIDC 토큰, GitLab의 ID 토큰을 AWS/GCP/Azure 신뢰 관계에 연결하면 리포지토리에 장기 액세스 키를 넣지 않아도 된다. 워크플로 실행 시마다 플랫폼이 단기 토큰을 발급하고, 클라우드 제공자는 서명을 검증해 임시 자격증명을 준다. GitGuardian 보고서에서 2025년 시크릿 노출의 59%가 CI/CD 러너였다는 사실은 이 방향 전환의 긴박성을 말해준다.

7.2 환경별 분리

CI 환경에서 개발·스테이징·프로덕션 키를 구분하지 않으면 테스트 코드가 프로덕션 데이터를 건드릴 수 있다. 환경별로 별개의 시크릿 스토어를 유지하고, CI 파이프라인이 실행되는 환경에 따라 자동으로 올바른 자격증명을 주입하는 것이 이상적이다.

8. AI 에이전트 시대의 CLI 인증 — 새 변수

2026년 특유의 신규 변수가 있다. AI 코딩 에이전트가 CLI를 프로그래밍으로 호출하는 패턴이 급증했다는 것이다.

Claude Code, GitHub Copilot agent mode, Cursor agent가 gh, aws, stripe 같은 CLI 도구를 에이전트 루프 안에서 실행한다. 이 에이전트가 실행되는 프로세스는 환경 변수를 상속받는다. 즉 환경 변수에 있는 API 키가 에이전트 서브프로세스에도 흘러든다. 에이전트가 서드파티 코드를 실행하거나 MCP 서버를 통해 외부 도구를 호출한다면, 그 경계를 넘어 자격증명이 누출될 수 있다.

이에 대한 방어 패턴은 두 가지다. 첫째, 에이전트가 쓰는 CLI 도구의 토큰을 별도 최소 권한 토큰으로 격리한다. 둘째, 가능하다면 apiKeyHelper 패턴(에이전트가 요청할 때마다 단기 토큰을 생성하는 헬퍼 스크립트)을 쓴다. Claude Code 자체가 이 패턴을 지원한다. 장기 API 키 대신 요청 시마다 발급되는 단기 토큰을 쓰면, 토큰이 유출돼도 유효기간이 짧다.

9. 결론 — 오늘 바로 적용할 3가지

CLI 인증은 선택의 연속이다. 어떤 플로우를 쓸지, 어디에 저장할지, 어떻게 갱신할지. 그리고 각 선택에서 "편한 쪽"과 "안전한 쪽"이 종종 갈린다. 본인의 핵심 주장은 이렇다. 올바른 추상화(PKCE, OS 키체인, 토큰 로테이션)를 처음부터 쓰면 편의와 보안이 함께 온다. 나중에 보안을 덧붙이는 것은 처음부터 맞게 하는 것보다 항상 비싸다.

지금 바로 적용할 수 있는 3가지 행동이다.

9.1 기존 CLI 도구의 토큰 저장 위치를 확인하라

자주 쓰는 CLI 도구가 토큰을 어디에 저장하는지 확인하라. ~/.config/tool/ 아래 JSON 파일이 있다면 그 파일의 권한을 체크하라. ls -la로 600인지 확인하고, gitignore에 포함됐는지 확인하라. OS 키체인 연동이 있다면 그쪽으로 마이그레이션하는 것을 고려하라.

9.2 pre-commit 시크릿 스캐너를 팀 표준으로 넣어라

detect-secrets나 gitleaks 훅을 pre-commit 설정에 추가하는 것은 5분이다. 이 방어선 하나가 팀의 "실수로 키를 커밋하는" 사고의 대부분을 막는다. 개인 프로젝트라도 습관으로 들여야 한다.

9.3 새 CLI 도구를 만든다면 PKCE를 기본으로 설계하라

인증 플로우를 나중에 추가하려 하지 마라. 처음 설계 시 플로우 선택(PKCE vs Device Flow), 토큰 저장(OS 키체인 라이브러리), 리프레시 로직을 명확히 정의하라. 그리고 client_secret을 바이너리에 넣는 것은 설계 오류이지 "일단 급하니까"가 허용되는 편의 사항이 아니다.
