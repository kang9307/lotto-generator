测量方法 - 用多种途径写同一字符串，再按字节读取

编码问题在屏幕上看不出来。记事本、VS Code和终端会根据BOM和字节模式推测编码并正常显示，所以文字看起来正常并不能当证据。因此所有项目都使用同一个测试字符串한글 ab，并把整个文件按十六进制字节读出。这个字符串由U+D55C、U+AE00、空格、a、b五个字符组成，UTF-8下为9字节，CP949下为7字节（每个韩文字符2字节），UTF-16LE下为10字节。因为cmdlet会在行尾追加CRLF（0D 0A），文件长度还要加上2字节（UTF-16为4字节）以及BOM的长度。

不加载配置文件启动的会话，其默认状态如下。使用-NoProfile的原因是：如果配置文件改动了$PSDefaultParameterValues或控制台编码，同一条命令会写出不同的字节（第6节）。

Console.OutputEncoding : ks_c_5601-1987 (949)
                    Console.InputEncoding  : ks_c_5601-1987
                    $OutputEncoding        : us-ascii
                    Encoding.Default       : ks_c_5601-1987

控制台的输出和输入编码是949，$OutputEncoding是ASCII，.NET默认编码是949。这四个值是全文的背景，尤其在第9、10节中分别作用于不同的环节。

各cmdlet实测表 - 谁写UTF-16LE，谁写CP949

从表中可以读出四点。

  • 即使在同一个会话中，>写UTF-16LE，Set-Content写CP949。不存在一个可以称为5.1默认编码的单一值。
  • -Encoding utf8在所有cmdlet中都带了BOM。Out-File、Set-Content、Export-Csv分别是14、14、21字节，开头都是EF BB BF。
  • -Encoding ascii和Export-Csv的默认值，会把无法表示的字符替换成3F（问号）后保存。文件里一旦变成3F，就没有办法恢复原来的字符。
  • .NET的WriteAllText在不指定时写不带BOM的UTF-8，这是第7节规避办法的依据。

为什么不一致 - 官方文档的规则与相悖的一处

about_Character_Encoding文档（5.1版）自己就写明了这种不一致：Windows PowerShell一般使用UTF-16LE，但各cmdlet使用的默认编码并不一致。把它的写入规则压缩后是这样：Out-File以及>和>>创建UTF-16LE，这一点与Set-Content、Add-Content明显不同；Set-Content和Add-Content在目标文件为空或不存在时使用Default，即当前系统区域设置的ANSI代码页；Export-Csv创建Ascii文件；并且从5.1开始，重定向运算符会调用Out-File。上表的每一行都与这些语句相符。

相悖之处在about_Redirection文档（5.1版）的Notes一节。它写道重定向运算符使用UTF8NoBOM编码，而在5.1.19041上的实测是以FF FE开头的UTF-16LE。同为5.1版的about_Character_Encoding写的是UTF-16LE，所以实测与后者一致，与前者的说法相悖。文档没有说明那句话描述的是哪个版本，因此原因无法断定。不过PowerShell 6及更高版本默认utf8NoBOM，是about_Character_Encoding明确写出的，所以那一侧的描述混入了5.1页面的可能性仍只是推测。

实务上的结论只有一个：随版本而变的行为，应当用字节来确认，而不是只看一页文档；创建文件的脚本应显式指定编码，而不是交给默认值。

-Encoding utf8是带BOM的，utf8NoBOM在5.1中不存在

在表中，-Encoding utf8以EF BB BF开头。5.1的about_Character_Encoding把UTF8这个值描述为带BOM的UTF-8，并写明在Windows PowerShell中除UTF7之外的所有Unicode编码都会始终创建BOM。相反，在PowerShell 7.1及更高版本的取值列表中，utf8是不带BOM的UTF-8，需要BOM时使用utf8BOM。同一个词utf8在不同版本中会写出不同的字节。

那么在5.1中直接用utf8NoBOM行不行？答案是会被拒绝，如下所示。

PS> $t | Set-Content bad.txt -Encoding utf8NoBOM
                    Unknown, String, Unicode, Byte, BigEndianUnicode, UTF8, UTF7, UTF32, Ascii, Default, Oem, BigEndianUTF32

韩文区域设置下的错误信息说，无法把该值转换为Microsoft.PowerShell.Commands.FileSystemCmdletProviderEncoding类型，并在最后一行列出可接受的值；上面的输出就是那最后一行。列表里既没有utf8NoBOM，也没有utf8BOM。归纳如下。

  • 在5.1中，-Encoding utf8就是带BOM的UTF-8。cmdlet一侧没有关闭BOM的开关。
  • utf8NoBOM在参数绑定阶段就失败，所以不能原样用于需要同时在5.1和7中运行的脚本。
  • 需要不带BOM的UTF-8时，第7节的.NET调用是在此环境中确认可行的办法。

追加写入 - 沿用既有编码的cmdlet与不沿用的

比新建文件的默认值更危险的，是向已有文件追加内容。下面是用多种方式创建第一行한글 ab，再追加一行x的结果。

$t | Set-Content ap1.txt;                 'x' | Out-File ap1.txt -Append
                    $t | Set-Content ap2.txt -Encoding utf8;  'x' | Out-File ap2.txt -Append
                    $t | Set-Content ap3.txt -Encoding utf8;  'x' >> ap3.txt
                    $t | Set-Content ap4.txt -Encoding utf8;  'x' | Add-Content ap4.txt
                    $t | Out-File ap5.txt;                    'x' | Add-Content ap5.txt
                    $t | Set-Content ap6.txt;                 'x' >> ap6.txt
                    # each line above is followed by: hx

                    ap2.txt        len=20  EF BB BF ED 95 9C EA B8 80 20 61 62 0D 0A 78 00 0D 00 0A 00
                    ap3.txt        len=20  EF BB BF ED 95 9C EA B8 80 20 61 62 0D 0A 78 00 0D 00 0A 00
                    ap4.txt        len=17  EF BB BF ED 95 9C EA B8 80 20 61 62 0D 0A 78 0D 0A

结果与官方文档的语句一致。Out-File -Append和>>不会尝试匹配已有文件的编码，而是使用默认编码；Add-Content在没有指定编码参数时，会检测已有编码并应用到新内容。文档还写道，已有文件没有BOM时使用Default（ANSI）。

  • 用>>累积日志的脚本，会生成从第二行起编码就变了的文件。一个文件里混有CP949和UTF-16LE时，无论按哪种编码读取，都会有一段是乱码。
  • 需要追加时，使用Add-Content，或给Out-File -Append指定已有文件的编码。后者是文档要求的做法，但本文没有运行。

修改默认值 - 能做到的与做不到的

按文档所述，从5.1起重定向运算符会调用Out-File，所以可以用$PSDefaultParameterValues修改默认编码。下面是实际修改后再执行重定向的结果。

PS> $PSDefaultParameterValues['Out-File:Encoding'] = 'utf8'
                    PS> $t > redir2.txt; hx redir2.txt
                    redir2.txt     len=14  EF BB BF ED 95 9C EA B8 80 20 61 62 0D 0A

>从UTF-16LE变成了UTF-8。但14字节中的前3字节是EF BB BF，所以BOM仍在。这种方法能做到的只是把重定向统一为UTF-8，去不掉BOM。

这个值是整个会话的设置。文档也警告说，把它放进配置文件会影响所有未指定编码的命令和脚本，并建议在需要该行为的脚本或模块内部自行设置。这也是本文测量使用-NoProfile的原因。创建文件的脚本最好在代码里显式指定编码，使结果不受调用者配置文件的左右。文档介绍的$PSDefaultParameterValues['*:Encoding']形式没有运行，不保证其效果。

写不带BOM的UTF-8 - .NET调用与字节写入

在5.1中，生成不带BOM的UTF-8的办法在cmdlet之外。实测了三种。

[IO.File]::WriteAllText("$dir\net_nobom.txt", $t, (New-Object Text.UTF8Encoding($false)))
                    [IO.File]::WriteAllLines("$dir\wal.txt", [string[]]@('한글 ab'), (New-Object Text.UTF8Encoding($false)))
                    [byte[]]$bytes = (New-Object Text.UTF8Encoding($false)).GetBytes("한글 ab`n")
                    Set-Content bytes.txt -Value $bytes -Encoding Byte
                    # each call is followed by: hx 
net_nobom.txt  len= 9  ED 95 9C EA B8 80 20 61 62
                    wal.txt        len=11  ED 95 9C EA B8 80 20 61 62 0D 0A
                    bytes.txt      len=10  ED 95 9C EA B8 80 20 61 62 0A
  • 给WriteAllText传入UTF8Encoding($false)得到9字节，没有BOM，也不加换行。
  • WriteAllLines会在每行后加CRLF，得到11字节。只想要LF时不能使用。
  • Set-Content -Encoding Byte原样写入字节数组。5.1的取值列表中有Byte。因为换行是手工放进去的，所以只剩0A这一个字节。

.NET调用还有一个陷阱：相对路径是按进程的当前目录解析的，而不是按PowerShell的当前位置。

PS> New-Item -ItemType Directory -Force sub | Out-Null
                    PS> Set-Location sub
                    PS> [IO.File]::WriteAllText('rel.txt', 'x')
                    PS> (Get-Location).Path
                    C:\demo\work\sub
                    PS> [Environment]::CurrentDirectory
                    C:\demo
                    PS> Test-Path rel.txt
                    False

执行Set-Location sub之后，.NET的当前目录仍停留在最初启动的文件夹，rel.txt在sub中找不到（False）。文件被写到了.NET目录一侧。上面所有.NET示例都使用"$dir\文件"形式的绝对路径，原因就在这里。调用前先转换成绝对路径再传入，例如Join-Path (Get-Location) 名称，就不会有这个问题。

读取 - Get-Content把无BOM的UTF-8按CP949读取

读取方面也存在与写入对称的问题。文档说，没有BOM时Get-Content使用Default ANSI，而Import-Csv和Select-String假定为Utf8。下面用默认方式和-Encoding UTF8读取四种文件，并输出字符编码。

function codes($s) { ($s.ToCharArray() | % { '{0:X4}' -f [int]$_ }) -join ' ' }
                    foreach ($f in 'setc.txt','s_utf8.txt','net_nobom.txt','redir.txt') {
                      hx $f
                      $d1 = Get-Content $f
                      '  Get-Content                 Length=' + $d1.Length + ' ' + (codes $d1)
                      $d2 = Get-Content $f -Encoding UTF8
                      '  Get-Content -Encoding UTF8  Length=' + $d2.Length + ' ' + (codes $d2)
                    }
                    'ReadAllText on net_nobom.txt : ' + (codes ([IO.File]::ReadAllText("$dir\net_nobom.txt")))
                    'ReadAllText on setc.txt      : ' + (codes ([IO.File]::ReadAllText("$dir\setc.txt")))

                      Get-Content                 Length=5 D55C AE00 0020 0061 0062

带BOM的文件，读取方能从BOM得知编码，所以两种方式都正常。没有BOM时，默认读取按CP949解释，所以只有无BOM的UTF-8文件坏了。反过来，给CP949文件指定-Encoding UTF8也会坏。.NET的ReadAllText假定为UTF-8，所以无BOM的UTF-8读取正常，CP949文件则按乱码读入。

真正的麻烦在于把读取时已经弄坏的内容再写回去。读取配置文件、替换一些字符串后保存，就是常见的做法。

PS> Get-Content net_nobom.txt | Set-Content rt.txt -Encoding UTF8
                    PS> hx rt.txt
                    rt.txt         len=13  EF BB BF 3F EC 92 93 3F 20 61 62 0D 0A

原始字节ED 95 9C EA B8 80在读取的瞬间变成了问号和无关的字符，保存阶段又把结果记录成带BOM的UTF-8，最终留下3F EC 92 93 3F。读取时转换一次，写入时再转换一次，已经无法从这个文件恢复韩文。用Get-Content | Set-Content批量处理含韩文的无BOM文件，就会发生这样的事。读取时要加-Encoding UTF8，写入时要像第7节那样显式指定编码。

向原生程序发送时 - $OutputEncoding

$OutputEncoding与文件无关，它是PowerShell向外部程序的标准输入发送数据时使用的编码。文档说明其默认值为ASCII，并且在大多数情况下应与[Console]::InputEncoding保持一致。这里让Python把标准输入收到的字节原样打印出来进行确认。

$py = 'import sys; print(sys.stdin.buffer.read())'
                    $t = '한글'
                    $t | python -c $py
                    $OutputEncoding = [Text.Encoding]::UTF8
                    $t | python -c $py
                    $OutputEncoding = New-Object Text.UTF8Encoding($false)
                    $t | python -c $py
b'??\r\n'
                    b'\xef\xbb\xbf\xed\x95\x9c\xea\xb8\x80\r\n'
                    b'\xed\x95\x9c\xea\xb8\x80\r\n'
  • 使用默认值时，两个韩文字符以3F 3F到达。转换已在发送方完成，接收方无法恢复。
  • 赋值[Text.Encoding]::UTF8后，韩文以UTF-8到达，但最前面多了EF BB BF。如果接收程序原样解释第一行，BOM就成了数据的一部分。
  • 赋值UTF8Encoding($false)后，到达的只有ED 95 9C EA B8 80，没有BOM。
  • 无论哪种情况，末尾都会跟着0D 0A。正如文档所述，$OutputEncoding对重定向和cmdlet的文件保存编码没有影响。

接收原生程序输出时 - [Console]::OutputEncoding

反方向由[Console]::OutputEncoding决定。PowerShell把外部程序写出的字节按这个编码解释成字符串，再把字符串放进变量或用>保存。这里交替使用Python和node的输出进行确认。Python在输出被管道连接时，会按区域设置编码（此处为CP949）输出，可用PYTHONIOENCODING更改。

$x = python -c "print('한글')"
                    'Length=' + $x.Length + ' ' + (codes $x);  $x > cap1.txt; hx cap1.txt
                    $env:PYTHONIOENCODING = 'utf-8'
                    $x = python -c "print('한글')"

  • UTF-16LE文件的字符之间夹着00，所以grep ab一条也找不到。文件里明明能看到ab、搜索却是空的，就是这种症状。
  • UTF-8 BOM文件会带着开头的U+FEFF被读入，JSON加载器会以Unexpected UTF-8 BOM (decode using utf-8-sig)拒绝。用utf-8-sig打开即可解决。
  • git把UTF-16LE文件当作二进制，不显示改动内容。即使只增加了BOM，整个第一行也会显示为被修改，而肉眼看不出差别。

这些症状背后的一般原理，已整理在前面链接的BOM指南和换行指南（CRLF与LF指南）中。把韩文名称与PowerShell 5.1的默认编码放在一起讲的文章，是Shell引用与韩文文件名指南。

按场景选择表

根据上面的实测，整理5.1中按目的可选的办法。「实测」指本文确认过字节的做法。

目的使用依据
供bash、git、python、JSON、YAML读取的文本[IO.File]::WriteAllText或WriteAllLines + UTF8Encoding($false)实测，无BOM的UTF-8，9字节和11字节
用Excel打开的CSVExport-Csv -Encoding utf8实测，带BOM的UTF-8。默认是ASCII，韩文会变成3F
向已有文件追加Add-Content实测，会检测已有编码。避免使用>>
把重定向统一为UTF-8$PSDefaultParameterValues['Out-File:Encoding']实测，成为含BOM的UTF-8
读取含韩文的无BOM文件Get-Content -Encoding UTF8实测，默认读取会乱码
向原生程序输入UTF-8$OutputEncoding = New-Object Text.UTF8Encoding($false)实测，不带BOM到达
接收原生输出并保存让[Console]::OutputEncoding与程序的输出编码一致，再用.NET保存实测，不一致时保存之前就已损坏
二进制数据Set-Content -Encoding Byte或.NET字节写入文档说明经重定向的二进制数据会被当作字符串而损坏

其中混有仅限韩文版Windows的值。Set-Content的默认值是系统区域设置的ANSI代码页，所以其他区域设置会得到不同的字节。环境不确定的脚本，按表中第一行那样在代码里显式指定编码，可移植性最好。
