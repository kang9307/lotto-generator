引言 - 数字只有一个，单位却有四个

Unix时间是把自1970-01-01T00:00:00Z(纪元)以来经过的时间数成整数的值。Python文档把time模块的纪元写为在所有平台上都是1970年1月1日00:00:00(UTC)，MDN写道JavaScript的Date保存自纪元以来的毫秒数。基准时刻相同，但计数的单位分为秒、毫秒、微秒和纳秒。所以同一个整数在文件和API之间传递时一旦单位错位，日期就会飞到1970年初或几万年之后。

  • 把秒值当成毫秒读取，日期会落进1970年1月之内。
  • 把毫秒值当成秒读取，年份会跑到5万年代。
  • 用位数(10、13、16、19位)判别单位的规则只在特定时期内成立。
  • 32位整数在2038年无法容纳秒值。

本文要回答的问题如下。

  • 同一个值按秒、毫秒、微秒、纳秒读取，日期分别去哪里。
  • 位数判别规则在哪些时刻范围成立，在哪里失效。
  • 在四个工具中用同样方式写判别函数，会得到相同答案吗。
  • Python、Node、PowerShell、date的当前时间API各返回几位。
  • 32位边界和各工具的表示极限在哪里。

像Excel序列值这样基准日不同的日期数字由Excel序列值的文章讨论，时区规则的变化由时区数据的文章讨论，墙上时钟与单调时钟的区别由单调时钟的文章讨论。本文只看以Unix纪元为基准的整数的单位。

  • 把1700000000000按秒读的结果因工具而异。GNU date输出了55840-11-08T22:13:20Z，Node输出了+055840-11-08T22:13:20.000Z。Python抛出OSError: [Errno 22]，PowerShell抛出ArgumentOutOfRangeException。
  • Python文档写道，当时间戳超出平台C库localtime()或gmtime()支持的范围时fromtimestamp可能抛出OverflowError，这些函数失败时抛出OSError，并且通常被限制在1970年到2038年。这个Windows构建上出现OSError，与这句话方向一致。

计算了四个单位相互读取的完整表。行是用各单位写出同一时刻1700000000秒的整数，列是读取时使用的单位。

from datetime import datetime, timezone, timedelta
                    EPOCH = datetime(1970, 1, 1, tzinfo=timezone.utc)
                    SCALE = {'s': 1, 'ms': 10**3, 'us': 10**6, 'ns': 10**9}
                    base = 1700000000  # 2023-11-14T22:13:20Z in seconds
                    def read_as(value, unit):
                        sec = value // SCALE[unit]
                        if sec < 253402300800:
                            return (EPOCH + timedelta(seconds=sec)).strftime('%Y-%m-%d %H:%M:%S')
                        return 'year ~%d' % (1970 + value / SCALE[unit] / 31556952)
                    print('%-28s' % 'value (written as)' + ''.join('%-24s' % ('read as ' + u) for u in SCALE))
                    for u, k in SCALE.items():
                        v = base * k
                        print('%-28s' % ('%d (%s)' % (v, u)) + ''.join('%-24s' % read_as(v, r) for r in SCALE))

  • 错一级会得到1970-01-20或5万年代，错两级会得到1970-01-01 00:28:20或5千万年代，所以可以从结果日期的形态推测单位错了几级。

位数判别规则及其失效的边界

常见的规则是位数。10位当作秒，13位当作毫秒，16位当作微秒，19位当作纳秒。计算了这条规则成立的时刻范围。下面是各位数开始的时刻。

  • 在1973-03-03 09:46:40到2001-09-09 01:46:39之间，秒值是9位，毫秒值是12位。

把位数规则和阈值规则应用到从1970-01-01到2300-12-31、间隔约1.01天的119193个时刻上。阈值规则把绝对值小于1e11的当作秒，小于1e14的当作毫秒，小于1e17的当作微秒，更大的当作纳秒。先计算这些阈值对应的日期。

                    EPOCH = datetime(1970, 1, 1, tzinfo=timezone.utc)
                    def by_digits(v):
                        n = len(str(abs(v)))
                        return {10: 's', 13: 'ms', 16: 'us', 19: 'ns'}.get(n, '?')
                    def by_threshold(v):
                        a = abs(v)
                        return 's' if a < 10**11 else 'ms' if a < 10**14 else 'us' if a < 10**17 else 'ns'
                    SCALE = {'s': 1, 'ms': 10**3, 'us': 10**6, 'ns': 10**9}
                    EDGES = [0, 10**8, 10**9, 10**10, int((datetime(2301, 1, 1, tzinfo=timezone.utc) - EPOCH).total_seconds())]
                    def d(sec): return (EPOCH + timedelta(seconds=sec)).strftime('%Y-%m-%d %H:%M:%S')
                    secs = list(range(EDGES[0], EDGES[-1], 86400 + 1234))
                    print('tested instants:', len(secs))
                    for i in range(4):
                        print('window %d: %s .. %s' % (i + 1, d(EDGES[i]), d(EDGES[i + 1] - 1)))
                    for rule in (by_digits, by_threshold):

判别函数 - 四个工具能得到相同答案吗

guess_unit() {
                      local a=$(( $1 < 0 ? -$1 : $1 ))
                      if   (( a < 100000000000 ));       then echo s
                      elif (( a < 100000000000000 ));    then echo ms
                      elif (( a < 100000000000000000 )); then echo us
                      else echo ns; fi
                    }
                    for v in 0 -1 86400000 1700000000 1700000000123 1700000000123456 1700000000123456789 253402300799; do
                      u=$(guess_unit $v)
                      case $u in s) sec=$v;; ms) sec=$((v/1000));; us) sec=$((v/1000000));; ns) sec=$((v/1000000000));; esac
                      echo "bash    $v -> unit=$u  $(date -u -d @$sec '+%Y-%m-%dT%H:%M:%SZ')"
                    done

  • 253402300799是以秒写出的9999-12-31 23:59:59，但因为是12位，阈值规则把它判为毫秒，输出了1978-01-11T21:31:40Z。阈值放在哪里决定了正确的范围。

  • -1被判为秒，变成1969-12-31T23:59:59Z。因为用绝对值判定，负时刻也遵循同一规则。

  • 把毫秒放进有符号32位整数，会在2147483647毫秒(约24.86天)的1970-01-25 20:31:23处溢出。不是2038年，而是纪元之后的25天。

  • PowerShell的FromUnixTimeSeconds可到253402300799(9999-12-31 23:59:59)，253402300800会抛出ArgumentOutOfRangeException。int32的最大值和最小值分别转换为2038-01-19 03:14:07和1901-12-13 20:45:52。
  • GNU date 8.32正常转换了2147483648和-2147483648，bash的64位算术把9223372036854775807加1变成了-9223372036854775808。

如何确定单位 - 选择标准

情形判断本文中看到的依据
值在2001-09-09至2286-11-20之间，单位是秒、毫秒、微秒、纳秒之一可以用位数(10、13、16、19)判别单位第3节区间3误判为0个
可能混入1973-03-03之前的毫秒及更小单位的值位数规则和阈值规则都可能误判，应通过单独的字段或名称确定单位第3节区间1，第4节的86400000
2286年之后的秒值，或5138年之后的阈值边界规则无法判定或误判第3节区间4，第4节的253402300799
需要以异常的形式接收转换失败各工具的异常种类不同，应先做范围检查第2节的OSError、ArgumentOutOfRange、Invalid Date
把秒保存到整数列中有符号32位整数的限制是2038-01-19 03:14:07 UTC，应使用64位第6节的输出
在JavaScript中处理纳秒、微秒的值使用BigInt第4节Number转换的输出
  • 不要只看值就推测单位，而应把单位写在字段名(例如秒用sec，毫秒用ms)或模式中，因为推测规则成立的范围是固定的。
  • 不得不推测时使用阈值规则，并用代码注释和测试固定其正确范围(1973-03-03至5138-11-16)。
  • 转换结果落在1970年1月或5000年之后时，先怀疑单位错误。
  • 把时刻放进32位整数列、协议或文件格式时，2038年是限制，若是毫秒则限制是25天。
  • 各工具对超出范围的值反应不同(OSError、ArgumentOutOfRangeException、Invalid Date)，所以在一个工具中通过的值可能在另一个工具中失败。

  • 使用32位time_t的真实系统的行为。2038年的边界只通过Python的整数计算和ctypes转换展示。
  • 闰秒的影响。Python文档写道自纪元以来的秒数不包括闰秒，但没有运行含闰秒时期的值。
  • 本地时区和夏令时。所有输出都固定为UTC。
  • Python fromtimestamp在3001年之后从哪个值开始抛出OSError的精确边界。
  • Java、Go、C#和数据库时间戳类型的单位与范围。
