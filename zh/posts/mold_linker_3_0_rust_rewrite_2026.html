背景与契机 — 从C++到Rust的完全重写与Linux发行版默认链接器目标

mold 3.0.0于2026年10月5日发布，是高速链接器mold的首个Rust版本。发布说明写道，正如2.42.1发布说明中所预告的，mold已从C++重写为Rust，2.42.1是C++版本的最后一个发行版。2026年9月11日发布的2.42.1说明给出了重写的理由：到2026年，Rust已成为系统软件的实用选择，并提供内存安全之类的强安全保证。同一份说明还表示，目标是让mold 3.0在用户看来与以前完全一样地工作，改变的只是内部实现。

3.0.0说明给出的mold 3.x目标，是弥合与GNU ld之间仅存的兼容性差距，尤其是链接器脚本（linker script）支持，并为mold被Linux发行版采纳为默认链接器铺平道路。2.42.1的说明对此解释得更详细：在大多数Linux发行版上，系统链接器/usr/bin/ld仍是GNU ld，所以计划先实现缺失的链接器脚本功能，使mold不仅能链接用户态程序，也能链接内核和固件，然后通过广泛的兼容性测试以及与发行版开发者的合作，让采纳变得可行。

README另外给出了速度数字。在2026年8月的基准测试中，mold按中位数计比LLVM lld快4.9倍，比wild快1.9倍，完整结果表见README的Benchmark一节。这些数字出自README而不是3.0.0发布说明，不能当作3.0.0与2.42.1的比较来读。

按说明的措辞整理，本次发布所表明的方向如下。

  • 即插即用替代：支持相同的命令行选项和相同的目标架构，输出除说明中列出的Bug修复外保持不变。
  • 弥合与GNU ld的差距：3.x的目标是补上仅存的兼容性差异，尤其是链接器脚本支持。
  • 默认链接器采纳的基础：说明将为mold被Linux发行版采纳为默认链接器铺平道路列为目标。
  • 对损坏输入的安全性：越界读取会经过边界检查，并以Panic停止。
  • 源码构建方式的变更：CMake被Cargo取代，需要Rust 1.95或更高版本。

未曾改变的部分 — v2.42.1的即插即用替代、同等的链接性能与验证

语言重写时，用户最先关心的是选项有没有变、有没有变慢。发布说明称，mold 3.0意在成为2.42.1的即插即用替代品：接受相同的命令行选项，支持相同的目标架构，除说明中列出的Bug修复外生成相同的输出。链接性能则称与2.42.1相当（on par）。说明里没有链接时间或内存用量的数字。

支持的架构，README列为x86-64、i386、ARM 32/64、RISC-V 32/64、PowerPC 32/64、s390x、LoongArch 32/64、SPARC64、m68k和SH-4。说明的修复列表中，AArch64、ARM32、RISC-V、LoongArch、PPC32、PPC64、SH4、SPARC64、m68k都有各自的架构专项条目。

说明列出的兼容性验证有以下三项，最后一项则区分了兼容所适用的范围。

  • 在所有受支持的目标上运行测试套件：在每个受支持的目标上都运行了测试套件。
  • 在广泛的真实工作负载与选项组合下比较输出：在多种真实工作负载和选项组合下比较了链接器的输出。
  • 构建全部Gentoo软件包：构建了Gentoo的所有软件包，说明称没有发现回归（We found no regressions）。
  • 兼容的范围是链接器的选项、架构与输出：同一版本中，构建系统从CMake改为Cargo，测试运行从ctest改为cargo test。从源码构建mold一侧的脚本和CI配置不能原样沿用，需要按下文构建一节的变更调整。

安全模型的变化 — 从段错误（segfault）到Panic

说明在安全性上讲的只有一点：损坏的输入文件（corrupted input files）。遇到这类输入时，C++版本可能越界读取内存并以段错误终止。移到Rust之后的3.0对这些读取做了边界检查，mold会在出错的访问处以Panic停止。

变化的是停止的方式。按说明的叙述，损坏输入原先以段错误崩溃的地方，现在变成以Panic停止，而不是说会修复损坏使链接成功，说明里没有这样的话。对正常输入，这个变化不会显现，因为3.0的输出除Bug修复项外与2.42.1相同。

同一份说明的Bug修复列表中，另有一些条目把针对无效输入或选项组合的损坏输出、崩溃改成了报错。这与边界检查是两回事，具体条目整理在后面的输出准确性一节。

在说明所述范围内，安全性要点整理如下。

  • 对象：仅限于处理损坏输入文件时的描述。
  • 以前的行为：C++版本可能越界读取内存，并因段错误而崩溃。
  • 3.0的行为：这些读取受边界检查约束，在出错的访问处以Panic停止。
  • 说明没有谈到的：Panic信息的格式、带有边界检查的代码范围、检查带来的性能代价都没有描述，只有性能与2.42.1相当这一句。

构建与打包流程的变化 — 引入Cargo与Rust 1.95+门槛

对于从源码构建mold或为发行版制作软件包的人，最大的变化是构建系统。说明称mold现在用Cargo而不是CMake构建，需要Rust 1.95或更高版本和C编译器，CMake选项已全部移除。README补充说还需要Git；如果系统自带的Rust较旧，应通过rustup安装稳定（stable）工具链。

编译

README给出的编译步骤如下。可执行文件及其配套的preload库分别生成在target/release/mold和target/release/mold-wrapper.so。

git clone https://github.com/rui314/mold.git
                    cd mold
                    cargo build --release

安装与MOLD_LIBDIR

README说明，运行sudo ./install-mold.sh会安装到/usr/local下，若要装到其他前缀，需指定PREFIX。说明称安装脚本接受PREFIX和DESTDIR。mold-wrapper.so安装到$PREFIX/lib/mold，也可以不安装而直接运行target/release/mold。

sudo ./install-mold.sh
                    sudo PREFIX=/usr ./install-mold.sh

如果把库装到$PREFIX/lib以外的目录，例如/usr/lib64，说明和README都要求把MOLD_LIBDIR环境变量设为该目录。cargo build时和用install-mold.sh安装时都要设置，这样mold -run才能找到mold-wrapper.so。按README的描述，mold -run通过LD_PRELOAD加载配套的共享对象，拦截exec系列调用，把对ld、ld.bfd、ld.gold、ld.lld的调用替换成mold，所以这个文件的位置很重要。

构建与测试工具方面的其余变化如下。

  • 运行测试：用cargo test取代ctest。
  • 测试依赖脚本：install-build-deps.sh被install-test-deps.sh取代，后者只在运行测试时才需要。
  • 目标选择：MOLD_TARGETS这一CMake变量被Cargo features取代。说明称，与以前一样，发行版应为所有目标构建mold。
  • CMake选项移除：CMake使用的选项已全部消失，现有打包脚本中传递这些选项的部分需要改写。

依赖项的变化 — 移除oneTBB，mimalloc 3.5.3与压缩库的配置

说明称mold不再依赖oneTBB。至于取代oneTBB承担并行处理的实现是什么，说明中没有描述。其余依赖项的配置，说明逐项写明。

  • 静态链接mimalloc 3.5.3：与以前一样，静态链接mimalloc 3.5.3。
  • 选择系统分配器：用--features system-allocator构建，则使用系统的malloc。
  • 系统zlib：系统中有zlib时，就链接它。
  • 内置zstd与BLAKE3：这两个库包含在mold之中。
  • 链接系统zstd：设置ZSTD_SYS_USE_PKG_CONFIG=1，则链接系统的zstd。

输出准确性与GNU ld、lld兼容性的改进项

3.0.0说明的Bug Fixes and Compatibility Improvements一节很长，既有按GNU ld和lld的行为对齐的条目，如公共符号处理、版本脚本优先级、选项解析，也有各架构的专项修复。下表摘录其中关于选项与符号处理的代表性条目。

条目 3.0.0说明的叙述 相关选项或场景
同名公共符号（Common Symbol） 大小不同的同名公共符号取最大的大小和最严格的对齐，与GNU ld、lld的做法一致。 符号解析
输出文件同时也是输入文件 修复了像mold -r -o foo.o foo.o bar.o这样使用时出现的崩溃和输出损坏。 -r（部分链接）
节的垃圾回收 不再移除由--init和--fini指定的函数。 --gc-sections
相同代码合并 不再合并共享库导出的函数。--icf=all与--emit-relocs同用时的崩溃也已修复。 --icf=safe、--icf=all
版本脚本优先级 一个符号出现在多个版本节点中时，第一个节点优先，与GNU ld、lld一致。 版本脚本
单短横线选项的解析 按GNU ld的读法解析。例如-entry=main曾被读成-e ntry=main，现已修复。 命令行
启动时保留虚拟地址空间 启动时不再保留8 GiB的虚拟地址空间，因此在ulimit -v下也能运行。 进程启动
非确定性输出 修复了若干情形。说明列出的有--dependency-file、--repro、含大量同名COMDAT组的-r，以及部分动态重定位。 输出可复现性

非确定性输出一项只是说修复了所列的若干情形（several cases），说明并不保证在任何条件下输出都逐字节一致。另外，-r是部分链接，不是增量链接；说明修复的是使用-r时的崩溃和输出损坏。

表外还有其他条目。针对共享库中定义的符号的GOT相对重定位（R_X86_64_GOTOFF64、R_ARM_REL32），以前会悄悄得到错误地址，3.0要么正确处理，要么报错。--defsym给共享库中的符号起别名、超出64位的--defsym值、既被分配又被压缩的节、--strip-all与--emit-relocs的组合等情形，现在会报错，而不是输出损坏或崩溃。在部分链接中，第二个及以后的输入文件中C++异常被破坏的问题，以及--gc-sections丢弃重定位所引用数据的问题也已修复。在AArch64、PPC32和ARM32上，经范围扩展跳板（thunk）的调用在Chromium的ARM64调试构建这类大型程序中跳转到错误地址的问题也已修复。

各架构条目更为具体。AArch64增加了R_AARCH64_TSTBR14、R_AARCH64_GOT_LD_PREL19等重定位类型的支持，ARM32增加了对R_ARM_ALU_PC_G0和R_ARM_THM_PC12的支持。在PPC32和m68k上，GOT超出-fpic代码所用16位偏移时，现在会报错，而不是被悄悄截断。此外，--separate-debug-file生成的文件不再含有.gnu_debuglink节，不再创建无意义的__start_EHDR一类符号，MOLD_JOBS在XDG_RUNTIME_DIR为空字符串时也能工作。

mold 2.42.1（C++）与mold 3.0.0（Rust）的配置对照

下表在3.0.0说明所描述的范围内对照两个版本的配置差异。说明没有谈到的格子，标明没有叙述。

对比项 mold 2.42.1（C++最后一个发行版） mold 3.0.0（Rust首个发行版）
实现语言 C++ Rust
构建系统 CMake Cargo（CMake选项已移除）
源码构建要求 3.0.0说明中无叙述 Rust 1.95或更高版本和C编译器
是否依赖oneTBB 依赖 不再依赖
内存分配器 静态链接mimalloc（说明所称的as before） 静态链接mimalloc 3.5.3，可用--features system-allocator选择系统malloc
运行测试 ctest、install-build-deps.sh cargo test、install-test-deps.sh

总之，链接器的选项与输出得以延续，源码构建流程与内部配置则发生了变化。表中2.42.1一侧的格子是从3.0.0说明的变更叙述倒推出来的，与2.42.1自身文档的措辞可能不同。

尚未核实的事项

  • 3.0.0发布说明中没有链接时间或内存用量的数字，只有与2.42.1相当这一句叙述。README中的4.9倍、1.9倍，比较的是2026-08-28时点从源码构建的链接器，具体测的是mold的哪个版本，无法从README确认。
  • Rust代码库的整体规模和模块结构，说明与README中都没有描述。
  • 重写所用的Rust edition没有明确写出。
  • 链接器脚本支持中究竟还缺哪些功能，说明里没有清单，只写了要补上剩余差距的目标。
  • Linux发行版采纳mold为默认链接器的时间表和讨论进展，没有叙述。
  • 用3.0.0链接真实项目时，输出与2.42.1究竟差多少，没有公开的比较结果。说明只说除Bug修复项外相同。
