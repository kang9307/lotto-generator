背景 - 将繁琐配置文件修改转变为一键扩展安装的MCPB

工程博客《Desktop Extensions》写道，本地MCP服务器为Claude打开了从文件系统到数据库的各种访问能力，但反馈一直是安装太复杂：用户需要具备开发工具，要手动编辑配置文件，还常常卡在依赖问题上。博客把这些障碍归为五项：需要开发工具（安装Node.js、Python等运行时）、手动配置（每个服务器都要编辑JSON配置文件）、依赖管理（自行解决包冲突与版本不匹配）、缺少发现机制（找有用的服务器只能去GitHub搜索）、更新繁琐（保持最新意味着手动重装）。

MCPB（.mcpb）被介绍为这一问题的答案。官方文档把MCP Bundle定义为包含本地MCP服务器和manifest.json的zip归档，Claude Desktop像浏览器安装扩展那样一键安装。这种格式最初名为DXT（Desktop Extensions，.dxt）。README发布公告称项目正在从DXT更名为MCPB：dxt CLI现在是mcpb，.dxt文件现在是.mcpb文件，@anthropic-ai/dxt包将迁移（will be moved）到@anthropic-ai/mcpb。README没有说明更名的原因。博客在2025年9月11日的说明中表示，现有的.dxt扩展继续可用，新扩展建议使用.mcpb，功能保持不变。README把这种格式描述为在精神上类似Chrome扩展（.crx）或VS Code扩展（.vsix）。

用户这一侧的步骤，博客概括为三步：下载.mcpb文件，双击用Claude Desktop打开，点击Install。没有终端，没有配置文件，也没有依赖冲突。

  • 其一，安装过程不再需要手动编辑配置文件，这正是博客对比旧流程与新流程时指出的差别。
  • 其二，服务器如何运行、需要哪些设置，都在manifest.json中声明，MANIFEST.md把manifest_version、name、version、description、author和server列为必填字段。
  • 其三，敏感设置被单独处理：博客写道API密钥等敏感值保存在操作系统钥匙串中，MANIFEST.md则写明sensitive值会被遮蔽并安全存储（store securely）。
  • 其四，服务器在用户电脑上通过stdio运行，无需云基础设施，可离线工作，也不需要OAuth，这是官方文档列出的MCPB特性。

README介绍该仓库提供三样东西：MANIFEST.md中的打包规范、用于创建包的CLI工具，以及Claude for macOS和Windows用来加载并验证MCPB包的代码。

基础架构 - 在用户电脑上通过stdio运行的本地服务器

官方文档的第一段点出了架构的核心：服务器在用户的机器上通过stdio运行，因此无需任何云基础设施，就能访问本地文件、本地安装的工具以及用户防火墙后面的系统。同一页面还对比了两种方式的运行位置：MCPB在用户机器上通过stdio运行，可以访问本地和内部资源；远程连接器则在开发者的服务器上通过HTTPS运行，并经由Anthropic的基础设施访问。文档还补充说，组织常常在保持其安全架构的前提下，把MCPB用作内部MCP服务器的安全代理、内部文档访问以及开发工具的连接。

文档列出的MCPB特性共五项：在用户机器上本地运行，通过stdio传输通信，捆绑全部依赖，可离线工作，不需要OAuth。

官方文档（Build a desktop extension with MCPB）用一张表列出了各自适用的需求。下表把其中的条目重新归并为四个角度。

选型考量 本地MCPB (.mcpb) 远程连接器 (Remote Connector)
网络与防火墙 访问企业防火墙内的私有系统（工单系统、内部Wiki、私有数据库） 基于中心化云基础设施构建的公共API与公有云服务
鉴权与凭据管理 复用系统现有SSO与本地浏览器登录会话，无需独立令牌维护 OAuth流程与服务端令牌管理
数据隔离与安全 严禁数据离开本机的敏感任务，直接操作本地文件系统 面向Web、移动端及桌面端多终端统一分发与管理
运行时与基础设施 利用Claude Desktop内置的Node.js环境，零云端基础设施依赖 由中央服务器统一维护与热更新，需要持续的运维投入

原表中除上述条目外，还有更多选择MCPB的理由：用于代码编辑和Git操作的直接文件系统访问，与Docker、IDE、数据库等本地安装工具的集成，硬件集成与桌面应用控制，借助捆绑的Node.js运行时、无需管理依赖的一键安装，无需云基础设施、VPN配置或防火墙规则，自定义上传与允许列表等组织级管理员控制，以及对认证、授权和审计日志的完全控制。

对于本地stdio运行模型，文档直接写出的有以下四点。

  • 本地运行：服务器在用户的机器上运行，访问本地文件和本地安装的工具。
  • stdio传输：Claude Desktop与服务器通过stdio传输通信。
  • 离线工作：文档写明MCPB可以离线工作。
  • 认证与基础设施：不需要OAuth，使用现有SSO和浏览器会话认证即可而无需管理令牌，也不需要云基础设施。

超出这四点的解读，例如是否开放端口、进程权限边界如何，这些文档中都没有。本文对这部分也只转述到文档所说的范围。

运行时选型 - 内置Node.js环境与Python依赖处理

开发MCPB扩展时，首先要定的是实现语言。官方文档强烈推荐（strongly recommended）Node.js，并给出三条理由：macOS和Windows版Claude Desktop自带Node.js，用户无需另装运行时；与Claude Desktop的兼容性和可靠性最好；MCP SDK支持广泛。博客同样写道，Claude Desktop自带Node.js，从而消除了外部依赖。

README从安装摩擦的角度给出同样的建议：Node.js随macOS和Windows版Claude一起提供，因此包开箱即用，无需用户额外安装Python运行时，开发者也无需手动打包它。支持的平台是macOS（darwin）和Windows（win32），在manifest.json的compatibility部分声明所支持的平台。文档建议，即使主要在一个平台上开发，也要在两个平台上都测试。

README的“Bundling Dependencies”部分说明，不同服务器类型处理依赖的方式不同。

  • Node.js包：运行npm install --production生成node_modules，并把整个目录一并打进包里。要获得可复现的构建，可使用npm ci或yarn install --frozen-lockfile，服务器入口由server.entry_point指定。MANIFEST.md同样写明，Node.js扩展必须把所有依赖打包在node_modules中。
  • Python包（传统方式）：使用server.type = "python"，把所需的包放进server/lib/，或把完整的虚拟环境放进server/venv/，并通过mcp_config.env设置PYTHONPATH指向这些包。README还写明了限制：已编译的依赖（例如MCP Python SDK所需的pydantic）无法以可移植的方式打包。
  • uv类型（v0.4+）：把server.type设为"uv"，并附带列出依赖的pyproject.toml。无需打包任何包，由宿主应用自动管理Python和依赖，用户无需安装Python即可跨平台运行，README如此写道。MANIFEST.md中的uv示例，其manifest_version为0.4。
  • 二进制包：为获得最大兼容性优先静态链接，若使用动态链接则要附带全部所需的共享库，并在没有开发工具的干净系统上测试。MANIFEST.md把二进制类型描述为包含所有依赖的预编译可执行文件，并支持按平台提供的二进制。

总结来说，README把Node.js已包含在Claude中、因而无需另装或另行打包Python运行时，作为推荐Node.js的理由。但这并不意味着所有Python服务器都必须把依赖整体打包。传统的python类型需要把包放进包里，并对已编译依赖有限制，而uv类型把这一负担交给了宿主。

清单规范（v0.3） - 必填字段与用户配置UI自动生成

manifest.json是包中唯一必须存在的文件。官方文档把它描述为必需的元数据，说明MCPB做什么、如何运行、提供哪些工具以及需要什么配置。MANIFEST.md指出当前版本为0.3，最后更新日期为2025年12月2日，并且大多数字段是可选的。只含必填字段的基本清单如下。

{
                      "manifest_version": "0.3",
                      "name": "my-extension",
                      "version": "1.0.0",
                      "description": "A simple MCP extension",
                      "author": {
                        "name": "Extension Author"
                      },
                      "server": {
                        "type": "node",
                        "entry_point": "server/index.js",
                        "mcp_config": {
                          "command": "node",
                          "args": [
                            "${__dirname}/server/index.js"
                          ]
                        }
                      }
                    }

据MANIFEST.md说明，${__dirname}会被替换为扩展所在目录；博客则写道，它会变成扩展解压所在目录的完整路径。需要向用户索取值的服务器，会设置user_config块。官方文档说明，定义user_config后，Claude Desktop会为扩展自动生成设置界面。博客对示例的讲解更具体：开发者声明用户必须提供api_key后，Claude在用户提供该值之前不会启用扩展，会自动把它保存在操作系统的机密保管库中，并在启动服务器时透明地把${user_config.api_key}替换为用户提供的值。

{
                      "manifest_version": "0.3",
                      "name": "my-extension",
                      "version": "1.0.0",
                      "description": "A simple MCP extension",
                      "author": {
                        "name": "Extension Author"
                      },
                      "server": {
                        "type": "node",
                        "entry_point": "server/index.js",
                        "mcp_config": {
                          "command": "node",
                          "args": ["${__dirname}/server/index.js"],
                          "env": {
                            "API_KEY": "${user_config.api_key}"
                          }
                        }
                      },
                      "user_config": {
                        "api_key": {
                          "type": "string",
                          "title": "API Key",
                          "description": "Your API key for authentication",
                          "sensitive": true,
                          "required": true
                        }
                      }
                    }

MANIFEST.md归纳的主要字段如下。

  • manifest_version（必填，字符串）：清单所遵循的规范版本，目前示例为0.3。其余必填字段是name、version（semver）、description和author（姓名必填，邮箱和URL可选）。
  • server（必填，对象）：type为node、python、binary之一，entry_point指向主服务器文件，mcp_config中放command、args、env。同一文档介绍的uv类型由宿主管理执行，因此mcp_config可选。
  • user_config（选填，对象）：输入类型有string、number、boolean、directory、file。还可以定义title、description、required、default、multiple、min、max，字符串类型开启sensitive后会遮蔽输入并安全存储。
  • compatibility（选填，对象）：platforms可填darwin、win32、linux，runtimes写运行时版本要求。文档中的示例是node: ">=16.0.0"，省略该字段时视为支持所有平台。
  • icon（选填，字符串）：包内的相对路径或https://网址。官方文档推荐带透明度的512×512像素PNG，最小尺寸为256×256；需要明暗主题或多种尺寸时使用icons数组。

替换变量写作${user_config.KEY}，多选项会以数组形式展开为独立的参数。MANIFEST.md补充说，环境变量适合放敏感数据，命令参数适合放路径和非敏感选项。

构建工具链 - @anthropic-ai/mcpb CLI命令与打包流程

官方文档给出的流程分五步：安装MCPB CLI，用MCP SDK编写stdio MCP服务器，用mcpb init生成清单，用mcpb pack打包，最后双击生成的.mcpb文件，在Claude Desktop中安装并测试。README也说明，把本地MCP服务器做成包，只需把所有必需文件放进一个文件夹，创建manifest.json，再生成归档。此前的@anthropic-ai/dxt包，按README的说法，将迁移到@anthropic-ai/mcpb。

npm install -g @anthropic-ai/mcpb
                    
                    # 交互式初始化清单
                    mcpb init
                    
                    # 静态校验清单规范
                    mcpb validate manifest.json
                    
                    # 将当前目录打包为.mcpb归档
                    mcpb pack .

CLI.md列出了七条命令，主要的如下。

  • mcpb init [directory]：以交互方式创建新的清单。会询问扩展名称、作者、扩展ID、显示名称、版本、描述、作者邮箱与URL、服务器类型（Node.js、Python或Binary）、入口文件、工具配置，以及关键词、许可证和仓库信息。博客补充说，使用--yes参数可以快速生成最基本的清单。
  • mcpb validate <path>：依据schema校验清单。可以直接给出manifest.json的路径，也可以给出包含它的目录。
  • mcpb pack <directory> [output]：把目录打包成.mcpb文件。它会自动校验manifest.json，排除.git、node_modules/.cache、.DS_Store等常见开发文件，并生成最大压缩率的ZIP。
  • mcpb sign与mcpb verify：sign使用证书为.mcpb文件签名，选项可指定证书与密钥路径以及中间证书，另有--self-signed可创建并使用自签名证书。verify会显示签名有效性、证书主体与颁发者、有效期和指纹，若为自签名则给出警告。

其余两条命令是info（显示文件大小、签名状态和证书信息）与unsign（移除签名，用于开发和测试）。README展示的Node.js包目录结构包括manifest.json（必需）、server/index.js、打包进去的node_modules/，以及可选的package.json、icon.png和assets/。

安装体验与分发政策 - 目录登记停用与插件体系衔接

官方文档说明，用户自行把.mcpb文件安装到Claude Desktop中。安装方式如下。

  • 在文件资源管理器中双击.mcpb文件。
  • 把.mcpb文件拖放到正在运行的Claude Desktop窗口中。
  • 在Claude Desktop中进入Settings > Extensions > Advanced settings > Install Extension…，选择.mcpb文件。
  • 按用户安装：安装是以用户为单位的，每位用户各自在自己的系统上安装。

这三种方式都会打开安装界面。据文档所述，用户在该界面中查看扩展的详细信息和权限，填写必需的设置，授予权限，然后完成安装。博客把同一界面描述为：显示人类可读的扩展信息、所需权限与配置，以及一个简单的Install按钮。

分发方面出现了政策变化。官方文档同一页面中的“Distribute your MCPB”一节，先写明用户自行安装.mcpb文件，随后指出目录中的桌面扩展列表已被弃用（deprecated），目录不再接受MCPB提交。接着说明，若要通过目录分发本地MCP服务器，应把该服务器包含进插件。页面开头也写道，想要在目录中上架，应构建能触达所有界面的远程MCP服务器，或把本地服务器包含进插件。

因此，.mcpb格式用于直接传递文件的内部或私有分发，目录上架则必须走插件路径。工程博客在发布之初介绍过向目录提交扩展的流程，而现行文档写明该途径已被弃用，所以两者的表述因时间不同而有差异，本文以现行文档为准。在Team或Enterprise组织中部署扩展时的管理员控制（允许列表、策略配置）以及终端用户的安装体验，Anthropic的支持文档另有介绍。

MCPB各组件官方文档陈述与未核实事项对照

要把本地扩展真正用于工作，需要区分官方文档所说的内容与文档中没有的内容。下表按MCPB的各个组件对二者做了对照。

配置UI与机密 依据user_config自动生成UI，sensitive项会遮蔽输入并安全存储（博客：操作系统钥匙串） 各操作系统的具体存储位置与加密方式，以及file类型是否支持任意绝对路径，均未明确规范

据此设计时需要留意的几点，仅限于能从文档中直接得出的内容。

  • 平台检查：文档建议，即使主要在一个平台上开发，也要在macOS和Windows两个平台上测试。
  • 路径输入：user_config支持directory和file类型，multiple允许多选。文件选择器能在多大程度上允许任意路径，文档中没有说明，需要自行确认。
  • 分发途径：目录提交已停止，因此直接传递.mcpb文件，或将其包含进插件。自定义上传和允许列表等组织级管理员控制，由Team和Enterprise文档说明。
  • 签名：mcpb sign使用证书签名，也可以创建自签名证书，verify在自签名时会发出警告。若要引入签名，需要先确定这一警告意味着什么。

未能确认的内容

  • Claude Desktop安装包内部所捆绑的Node.js运行时的精确小版本号及其支持的最新ECMAScript特性范围。
  • 在manifest.json的user_config中将类型配置为file时，是否能够正常调起系统文件选择器并选取解压目录外部的任意文件。
  • 当开发者使用中间层包装脚本启动实际MCP服务器时，Claude Desktop在子进程退出及管道EOF处理上的底层机制。
  • Claude in Chrome浏览器扩展是否具备直接发现并复用本地Claude Desktop所加载MCPB服务器的官方协议支持。
  • 企业IT管理员在Windows组策略（GPO）或macOS MDM中批量拦截未签名.mcpb安装的具体策略键名与配置方法。
