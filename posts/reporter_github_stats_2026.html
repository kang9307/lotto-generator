GitHub 트래픽 데이터 14일 소멸 문제 - Repo-rter로 본 로컬 영구 저장 분석

GitHub Insights는 왜 14일치 데이터만 보여줄까 - 로컬 영구 저장 앱 Repo-rter로 살펴본 오픈소스 성장 지표 관리법

2026-07-13 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 스타는 남는데 트래픽은 사라진다

오픈소스 저장소를 하나라도 운영해 본 사람이라면 GitHub Insights 화면에서 한 번쯤 답답함을 느꼈을 것이다. Traffic 탭을 열면 조회수(Views)와 클론(Clones) 그래프가 뜨지만, 스크롤을 아무리 내려도 딱 14일치뿐이다. 지난달 릴리스가 실제로 얼마나 조회됐는지, 유입이 급증했던 그 주가 정확히 언제였는지는 이미 흔적도 없이 지워진 뒤다. 반면 스타(Star) 수는 몇 년 전 이력까지도 star-history 같은 외부 도구로 그래프를 그릴 수 있다. 왜 이런 비대칭이 생길까.

2026년 7월, GeekNews에는 이 문제를 정면으로 겨냥한 오픈소스 프로젝트 Repo-rter가 소개됐다. GitHub Insights의 14일 데이터를 로컬 데스크탑 앱으로 영구 보존한다는 아이디어인데, 이 글은 이 도구 자체를 홍보하기보다 그 배경에 있는 질문 - 왜 GitHub은 트래픽을 14일만 보여주는가, 그리고 그 데이터를 직접 소유한다는 것은 어떤 의미인가 - 을 파고들어 본다.

1. GitHub Insights 14일 제한이란 무엇인가

1.1 무엇이, 어떻게 사라지는가

GitHub 공식 문서에 따르면 저장소에 대해 쓰기(push) 권한이 있는 사용자는 Insights의 Traffic 페이지에서 최근 14일간의 전체 클론(Full clones)·순 방문자(Unique visitors)·조회수를 볼 수 있다. 클론·방문자 수치는 매시간 갱신되고, 인기 콘텐츠(Popular content)와 유입 경로(Referring sites)는 매일 갱신된다. 문제는 갱신 주기가 아니라 보존 기간이다. 이 모든 수치는 정확히 14일이 지나면 UI에서, 그리고 뒤에서 다룰 API 응답에서도 사라진다.

1.2 API로 조회해도 소용없는 이유

혹시 REST API를 직접 호출하면 더 긴 기간을 볼 수 있지 않을까 기대할 수 있지만, 결론부터 말하면 아니다. /repos/{owner}/{repo}/traffic/views와 /repos/{owner}/{repo}/traffic/clones 엔드포인트는 per=day든 per=week든 관계없이 응답 범위가 동일하게 최근 14일로 고정돼 있다. per=week를 쓰면 그 14일을 주 단위 두 덩어리로 묶어 줄 뿐, 더 먼 과거를 열어주는 옵션이 아니다. 게다가 이 엔드포인트는 인증 없이는 접근할 수 없고, 저장소에 쓰기 권한이 없으면 403 Forbidden이 돌아온다. 즉 API는 "더 넓은 창"이 아니라 "UI와 똑같은 창을 프로그래밍적으로 보는 방법"에 불과하다. 결국 14일보다 오래 남기려면 그 안에 있을 때 누군가 직접 값을 읽어 어딘가에 저장해 둬야 한다.

2. 오픈소스 메인테이너와 제품팀이 겪는 불편

2.1 장기 트렌드를 재구성할 수 없다

가장 직접적인 손해는 추세 분석의 단절이다. 지난 6개월간 조회수가 꾸준히 늘었는지, 특정 릴리스 이후 클론 수가 얼마나 뛰었는지를 알고 싶어도, 그 기간 내내 누군가 수동으로 스크린샷을 찍어두지 않았다면 답할 방법이 없다. 반기·연간 단위로 프로젝트 성장을 돌아봐야 하는 시점(컨퍼런스 발표, 스폰서 리포트, 채용 공고에 넣을 실적)에 정작 근거 데이터가 없는 상황이 반복된다.

2.2 원인과 결과를 연결하지 못한다

마케팅이나 커뮤니티 활동의 효과를 검증하려면 이벤트 이전과 이후를 비교해야 한다. 블로그에 소개된 날, 컨퍼런스에서 발표한 날, 메이저 버전을 릴리스한 날의 트래픽 반응을 보고 싶어도, 14일이 지나면 비교 기준점 자체가 사라진다. 결과적으로 어떤 활동이 실제로 유입을 만들었는지 사후적으로 검증하기 어렵고, 다음 활동을 계획할 때도 감에 의존하게 된다.

2.3 문서·페이지 우선순위를 데이터로 정하기 어렵다

Popular content(인기 콘텐츠) 지표는 어떤 문서 페이지나 파일이 많이 열람됐는지를 보여줘 문서화 우선순위를 정하는 데 유용하다. 하지만 이 역시 14일 스냅샷일 뿐이라, 계절적 편차나 일시적 유입(예: 특정 글이 다른 곳에서 링크됨)을 장기 패턴과 구분하기 어렵다. 결국 많은 메인테이너가 감으로 문서를 고치고, 실제 독자 행동과는 무관한 곳에 시간을 쓰게 된다.

3. Repo-rter - 로컬 영구 저장이라는 접근

3.1 무엇을 하는 도구인가

Repo-rter는 이 문제를 정면으로 겨냥해 만들어진 무료 오픈소스 데스크탑 앱이다(MIT 라이선스). 저장소 정보에 따르면 Tauri(Rust) 백엔드에 Next.js·React·TailwindCSS 프론트엔드를 얹은 구조로, macOS(Apple Silicon·Intel)·Windows·Linux를 모두 지원하는 크로스플랫폼 앱이다. 백그라운드에서 시스템 트레이에 상주하며 크론 기반으로 주기적으로 GitHub API를 호출해 조회수·클론수·스타 등을 로컬에 누적 저장하고, CSV·JSON으로 내보낼 수 있다. 즉 GitHub이 지워버리기 전에 사용자 대신 주기적으로 스냅샷을 떠서 로컬 DB에 쌓아 두는 방식이다.

3.2 왜 굳이 로컬 데스크탑 앱인가

같은 문제를 푸는 방법은 여러 가지다(4장·5장에서 비교한다). 그중에서도 로컬 데스크탑 앱을 택했다는 것은 몇 가지 설계 판단을 내포한다. 서버·클라우드 계정 없이 동작하므로 인프라 운영 부담이 없고, 수집한 데이터가 제3자 서버를 거치지 않고 사용자 기기에만 남는다. 반대로 이는 그 기기가 꺼져 있으면 수집도 멈춘다는 제약, 그리고 여러 사람이 같은 이력을 보려면 파일을 공유해야 한다는 협업상의 한계와 맞바꾼 선택이기도 하다.

4. 로컬 데스크탑 앱 방식의 장단점

4.1 API 토큰과 프라이버시

Repo-rter를 포함해 트래픽·클론 데이터를 수집하는 모든 방식은 예외 없이 해당 저장소에 대한 쓰기 권한이 있는 GitHub 토큰을 요구한다. 이는 Repo-rter만의 특수한 위험이 아니라 GitHub Traffic API 자체의 권한 모델이다. 다만 그 토큰을 어디에 어떻게 보관하느냐는 도구마다 다르다. GitHub 공식 가이드는 OS 자격 증명 관리자를 활용하고 평문 파일 저장을 피하라고 권고한다. 로컬 앱을 쓴다면 토큰의 저장 방식과 권한 범위(가급적 fine-grained PAT로 최소 범위)를 직접 확인하는 습관이 필요하다. 반대급부로 데이터 자체는 외부 SaaS 서버를 거치지 않고 내 기기에만 쌓인다는 점은 프라이버시 측면에서 분명한 이점이다.

4.2 자동 수집(백그라운드 동기화)의 득실

시스템 트레이에 상주하며 주기적으로 동기화하는 방식은 깜빡하고 안 켜서 그 사이 데이터가 빈다는, 수동 방식의 고질적 실패를 줄여준다. 반면 상시 실행되는 백그라운드 프로세스는 배터리·리소스를 조금씩 소모하고, 노트북을 며칠 꺼두면 그 구간은 여전히 비게 된다는 근본적 한계는 남는다. 서버에서 도는 크론(예: GitHub Actions)과 달리 내 컴퓨터가 켜져 있을 때만 수집된다는 제약을 이해하고 쓰는 것이 중요하다.

4.3 그 밖의 한계

로컬 저장이라는 특성상 기기를 바꾸거나 앱을 재설치하면 이력이 함께 옮겨져야 하고, 팀 단위로 공유하려면 내보낸 CSV·JSON을 별도로 취합해야 한다. 클라우드 대시보드처럼 어디서나 웹 브라우저로 즉시 확인하는 편의성과는 다른 트레이드오프다.

5. 유사 대안과 비교

같은 문제 - GitHub이 지우는 데이터를 어떻게 붙잡을 것인가 - 를 푸는 접근은 로컬 앱 말고도 여러 갈래가 있다.

5.1 GitHub Actions 크론 + 저장소 커밋

가장 흔한 셀프호스팅 대안은 저장소 안에 매일 실행되는 GitHub Actions 워크플로를 두고, Traffic API를 호출해 결과를 같은 저장소(또는 별도 데이터 저장소)에 커밋하는 방식이다. 서버가 필요 없고 GitHub 인프라 안에서 완결되며, 이력이 git 커밋 로그 자체에 남아 팀 전체가 공유하기 쉽다. 다만 퍼블릭 저장소라면 커밋된 트래픽 데이터도 그대로 공개된다는 점, 그리고 액션이 매일 정상 실행됐는지 스스로 점검해야 한다는 점은 감안해야 한다.

5.2 자체 크론 + DB(+ Grafana)

이미 사내 모니터링 인프라(Prometheus·Grafana 등)를 운영 중인 조직이라면, GitHub API를 주기적으로 호출해 자체 DB나 시계열 저장소에 적재하고 기존 대시보드에 얹는 방식이 자연스럽다. 완전한 통제와 커스터마이즈가 가능하지만, 구축·운영 부담을 조직이 그대로 떠안는다는 점에서 개인 메인테이너에게는 무겁다.

5.3 star-history류 - 스타 전용 도구

star-history.com이나 daily-stars-explorer 같은 도구는 스타 이력만 다룬다는 점에서 Repo-rter와 근본적으로 다르다. 스타는 GitHub이 이벤트 로그를 API로 공개하기 때문에 과거 이력을 소급 재구성할 수 있지만, 조회수·클론수는 애초에 집계된 요약치만 노출되고 그 집계 자체가 14일 뒤 사라지므로 소급이 불가능하다. 스타 전용 도구가 있으니 트래픽도 비슷하게 되겠지라는 기대는 성립하지 않는다.

5.4 OSSInsight류 - 호스티드 대규모 분석

OSSInsight 같은 플랫폼은 GitHub의 공개 이벤트(스타·PR·이슈·커밋)를 대규모로 수집해 분석하는 호스티드 서비스다. 설치 없이 즉시 쓸 수 있고 생태계 비교에 강하지만, 애초에 공개 이벤트 기반이라 조회수·클론수처럼 저장소 쓰기 권한이 있어야만 볼 수 있는 비공개 지표는 다루지 않는다. 이 지점이 로컬·셀프호스팅 접근과 호스티드 분석 서비스를 가르는 근본적인 경계선이다.

6. 오픈소스 성장 지표, 왜 그리고 어떻게 추적하나

6.1 왜 추적하나

메인테이너에게 트래픽·클론 이력은 스폰서·후원 제안서, 컨퍼런스 발표, 채용 공고에 쓸 실적 근거이자, 릴리스·문서·마케팅 활동의 효과를 검증하는 실험 데이터이기도 하다. 데이터가 없으면 체감상 늘어난 것 같다는 인상 비평에 머물지만, 이력이 쌓이면 구체적인 숫자로 이야기할 수 있다.

6.2 무엇을 볼 것인가 - 스타보다 클론

스타는 진입 장벽이 가장 낮은 관심 표시(즐겨찾기에 가까운 행위)라서, 실제 사용 여부와의 상관관계가 약하다는 지적이 커뮤니티에서 꾸준히 나온다. 반면 고유 클론 수(Unique clones)는 실제로 코드를 내려받아 쓰는 사람 수에 좀 더 가까운 신호다. 두 지표를 함께 보되, 의사결정에는 클론·조회수 같은 행동 지표에 더 무게를 두는 편이 합리적이다. 여기에 popular/referrers(유입 경로)까지 겹쳐 보면 어디서 사람들이 이 프로젝트를 알게 됐는가까지 추적할 수 있다.

6.3 실무 워크플로 제안

규모와 무관하게 적용 가능한 최소 워크플로는 이렇다. 첫째, 14일이 지나기 전에 반드시 어딘가로 데이터를 옮긴다(로컬 앱이든 Actions든 상관없이, 방식보다 끊기지 않고 계속 수집되는가가 핵심이다). 둘째, 릴리스·발표·블로그 게재 같은 이벤트 날짜를 별도로 기록해 두어, 나중에 트래픽 그래프와 나란히 놓고 인과를 유추할 수 있게 한다. 셋째, 월 1회 정도 주기로 이력을 훑어보는 습관을 들여, 이상 신호(급격한 유입·이탈)를 놓치지 않는다.

결론 - 데이터 소유권이라는 작은 질문

GitHub Insights의 14일 제한은 사소해 보이지만, 파고들면 내 프로젝트에 대한 데이터를 누가, 어디에, 얼마나 오래 갖고 있는가라는 더 큰 질문으로 이어진다. Repo-rter는 그 답을 로컬, 무기한, 오픈소스라는 세 단어로 제시한 사례다. 정답은 하나가 아니다. 혼자 소규모 저장소를 운영한다면 설치 한 번으로 끝나는 로컬 앱이 가장 부담이 적고, 팀·조직이라면 이미 있는 CI·모니터링 인프라에 얹는 편이 지속 가능하다. 어떤 방식을 택하든 핵심은 같다. 14일이 지나기 전에, 지금 데이터를 옮겨 두는 것 - 그 사소한 습관 하나가 나중에 프로젝트의 성장 스토리를 말해 줄 유일한 근거가 된다.
