再デプロイで送信済みのプッシュ通知が再送された - FCM通知重複配信のデバッグ

送信状態をメモリだけに置くとどうなるか - 冪等キー・アウトボックス・スケジューラーロックで防ぐ実践パターン

2026-07-23 開発・インフラ

序論: 再デプロイしたら昨日の通知がまた届いた

2026年7月時点であらためて取り上げる価値のある事例がある。サーフィン予報アプリを一人で開発・運用する開発者が経験したことだ。このアプリは波・気象条件が「危険な水準に入った瞬間だけ」通知を送るよう設計されていた。常時通知ではなく、条件が変化したときだけ発火するイベント駆動型の通知だったわけだ。ところがサーバーを再デプロイした直後、昨日すでに送信を終えていたはずの通知がユーザーに再び届くという出来事が起きた。ローカル環境ではなかなか再現できず、原因を突き止めるまでに時間がかかったという。

結論から言えば、原因は拍子抜けするほど単純だった。「この通知はすでに送った」という状態を、サーバープロセスのメモリだけに載せていたのだ。再デプロイでプロセスが新しく立ち上がると、そのメモリはまるごと消える。新しいプロセスから見れば「まだ一度も送っていない通知」なので、条件を再評価した瞬間にもう一度送信してしまうのは、むしろ当然の挙動だったわけだ。

本稿はこの一つの事例を出発点に、なぜこの種のバグが特定のアプリだけの問題ではなく、通知・メッセージングシステム全般で繰り返し起きるパターンなのかを整理する。そして「正確に1回(exactly-once)」の配信という目標がそもそもなぜ間違った目標なのか、代わりに何を目指すべきかを実践パターン中心に解説する。

1. 重複配信はなぜ繰り返し起きるのか - 4つの典型的な原因

1.1 送信状態をメモリだけに保存

最も多い原因である。「このユーザーにこの通知をすでに送った」という事実をアプリケーションのメモリ上の変数やキャッシュ(dict、Set、インメモリキャッシュ)だけに記録すると、その情報はプロセスのライフサイクルに縛られる。デプロイ、再起動、スケールダウン、コンテナの再スケジューリング、OOMによる強制終了 - このどれが起きても状態は消える。サーフィン予報アプリの事例の根本原因はまさにこれだった。厄介なのは、普段は絶対に表面化しない点だ。プロセスが長期間再起動されなければバグは眠り続け、デプロイ一回で爆発する。

1.2 at-least-onceの再試行

FCMをはじめとするほとんどのプッシュ・メッセージング基盤は「正確に1回」の配信を保証しない。代わりに「最低1回(at-least-once)」の配信を保証する。サーバーがFCMに送信リクエストを送り、応答がタイムアウトした場合、サーバーは成功したのか失敗したのかを知る術がない。この状況での安全なデフォルト動作は再試行だ。しかし実際には最初のリクエストがすでに届いており応答だけが失われていた場合、その再試行はそのまま重複送信になる。これはバグではなく、ネットワークが信頼できないという事実から必然的に生じる結果である。

1.3 スケジューラーの重複実行

通知をcronやスケジューラーで送信する構造であれば、同じジョブが複数のワーカー・複数のポッドで同時に実行されるリスクがある。特にKubernetes環境でCronJobの同時実行制御を有効にしていないと、デプロイのタイミングが重なったり、前のジョブが終わる前に次のジョブが始まったりして、同じ通知が二度作られることがある。インスタンスが一つしかなかった頃には絶対に見えなかったバグが、スケールアウトした瞬間に現れる典型的なパターンだ。

1.4 複数インスタンスの競合

送信ロジック自体が「条件確認 → 送信」の二段階でできており、その間にロックがなければ、複数のインスタンスがほぼ同時に同じ条件を確認し、それぞれが送信を実行してしまうことがある。一つのイベントを複数のワーカーが同時に取り合う競合状態(race condition)だ。送信状態をメモリに置く問題(1.1)と重なることが多いが、原因は異なる。これはデータが消える問題ではなく、そもそも「誰がこの作業をするか」を決める調整の仕組みがない問題である。

2. 「正確に1回」という目標そのものが間違っている

2.1 分散システムでexactly-onceが不可能な理由

二将軍問題(Two Generals Problem)は、信頼できない通信チャネルを介して二者がある行動を正確に同時に、確実に合意することができないことを示す古典的な思考実験だ。メッセージが失われうるネットワークでは、送信者は相手が受け取ったかどうかを確実に知る方法がない。受け取ったという応答そのものも失われる可能性があるからだ。この根本的な限界のため、ネットワーク層で「正確に1回の配信」を保証することは理論上不可能である。FCMであれKafkaであれSQSであれ、例外ではない。

2.2 だから実務の答えは「at-least-once + 冪等性」

実務においてメッセージング・イベントシステムの大半が採用する答えは、「正確に1回の配信」を諦め、「最低1回配信 + 冪等処理」で同じ効果を出すことである。つまりメッセージは重複して届きうるという前提を受け入れ、受信側で同じメッセージを二度処理しても結果が変わらないよう設計する。これはよく「effectively-once(事実上1回)」と呼ばれる。配信保証は緩く保つ代わりに、処理結果の安全性をアプリケーションレベルで確保する戦略だ。この考え方は、Kafkaが解く大規模イベント処理の3つの難題で取り上げた「順序・正確に1回・低遅延は同時には成立しない」というトレードオフと、まったく同じ結論に行き着く。

3. 解決パターン - 実際にどう防ぐか

3.1 送信履歴の永続化

まずやるべきことは、「すでに送った」という事実をプロセスのメモリではなくDB(またはRedisのような永続ストア)に記録することだ。サーフィン予報アプリの事例の解決策も結局ここに行き着いた - 起動時にDBから送信履歴を再度読み込んで状態を再構築する構造に変えたのだ。原則はシンプルだ。「一度だけ起きるべき事実」は、プロセスが死んでも生き残る場所に残さなければならない。

3.2 冪等キー(idempotency key)の設計

送信前に、この通知が何についてのものかを一意に識別するキーを作る。よくある組み合わせはユーザーID + イベント種別 + 対象エンティティ + 時間ウィンドウだ。例えば次のような形になる。

dedup_key = f"{user_id}:{event_type}:{entity_id}:{window_bucket}"

このキーにデータベースの一意制約(unique constraint)をかけておけば、同じキーで二度目の挿入を試みたとき、二度目はデータベースが自動的に拒否してくれる(INSERT ... ON CONFLICT DO NOTHING)。アプリケーションコード側で「すでに存在するか」を確認するロジックを自前で書くより、データベースの原子的な制約に任せるほうが競合状態にはるかに強い。

3.3 送信前チェックとトランザクション

「送ったか確認 → 送っていなければ送信 → 送信済みとして記録」という3段階が原子的にまとまっていないと、確認と記録の間に別のプロセスが割り込んで同じ通知をもう一度送ってしまうことがある。方法は二つある。一つは「送信予定」の状態を先にDBに原子的に記録し(冪等キーの一意制約を利用して)、その記録が成功した場合にのみ実際の送信を行う方法。もう一つは、送信するかどうか自体をDBトランザクション内で他の状態変更と一緒にまとめ、送信の判断と状態更新がひとかたまりで成功するか、ひとかたまりで失敗するようにする方法だ。

3.4 アウトボックスパターン

「DBの状態変更」と「外部への通知送信」という異なる二つの作業を一つのトランザクションのようにまとめたいときに使うパターンだ。実際の送信の代わりに、同じトランザクション内で「送信すべきイベント」をアウトボックステーブルに一緒に記録する。そうすれば状態変更と送信予約が原子的に一緒に成功するか、一緒に失敗するかのどちらかになる。別途用意したリレー(relay)プロセスがアウトボックステーブルをポーリングして実際の送信を行い、成功すればレコードを送信完了としてマークする。ただしこのリレー段階自体は依然として最低1回の配信しか保証しないため、最終的な送信ロジックは冪等でなければならない点は変わらない。アウトボックスパターンは「イベントを取りこぼさないこと」を保証するが、「重複をなくすこと」を単独では保証しない - 3.2の冪等キーとセットで初めて完成する。

3.5 スケジューラーロック

複数のインスタンスが同じスケジュールジョブを実行するリスクがあるなら、分散ロックによって「今回の実行タイミングでは一つのインスタンスだけがジョブを取得する」ことを保証しなければならない。Redisやデータベース、ZooKeeperなどをロックストアとして使うライブラリ(ShedLock系など)がこの役割を担う。原理はシンプルだ。作業開始前に「この時間帯のこの作業」に対するロックを原子的に取得しようとし、失敗すれば(すでに他のインスタンスが取得していれば)静かにスキップする。Kubernetes環境であれば、CronJobをconcurrencyPolicy: Forbidに設定することも最低限の防御線になる。

3.6 FCMのcollapse_key - 補助手段であり根本解決策ではない

FCMはcollapse_keyというフィールドをサポートしている。同じcollapse_keyを持つメッセージが複数たまると、端末が再びオンラインになったときにFCMは最新のメッセージ一つだけを配信する。一見すると重複防止のように見えるが、二つの制約がある。第一に、この機能は通知(notification)メッセージには適用されず、データ(data)メッセージにのみ動作する。第二に、これは「サーバーがすでに複数回送ったもの」をクライアント/FCM側で事後的に整理する機能であって、サーバーがそもそもなぜ複数回送ったのかを直してはくれない。つまりcollapse_keyは症状緩和のための補助装置であり、3.1〜3.5の根本対策を代替できるものではない。

4. 再デプロイ・クラッシュにも安全な設計 - 「メモリを信用しない」

これらすべてのパターンを貫く原則は一つだ。プロセスはいつでも死ぬという前提で設計すること。再デプロイ、オートスケーリングによるスケールダウン、OOMキル、ノード障害 - どれもプロセスを予告なく終わらせうる。「一度だけ起きるべき状態」をメモリ変数だけに置いた瞬間、その保証はプロセスの寿命とともに消える一時的な保証になる。本当に保証が必要な状態(送信履歴、冪等キー、ロック、アウトボックスイベント)は、常にプロセスの外側にある永続ストアになければならない。ローカル開発環境でこの種のバグがなかなか再現しない理由もここにある - ローカルはデプロイもスケールアウトもコンテナの再スケジューリングもない、安定した単一プロセスだからだ。本番環境のデプロイパイプラインこそ、こうした前提の崩壊を実際に引き起こす場所なのである。

5. すでに扱った二つの原則とのつながり

この問題は実は、このブログですでに扱った二つの原則の再確認である。トグル一つが分散システムになるでは、オフライン状態でオフにした設定が復活するバグを扱ったが、根本原因は結局、クライアントとサーバーの状態を一つの信頼できる真実にまとめる冪等な同期設計の欠如だった。FCMの重複配信も同じ種類の問題だ - 「すでに処理済み」という事実が複数の場所(メモリ、再起動前後のプロセス)で一貫していないときに問題が起きる。そしてKafkaが解く大規模イベント処理の3つの難題で扱った「正確に1回の処理」の難しさも同じ文脈にある - 大規模なイベントパイプラインであれ、個人開発者のプッシュ送信ロジックであれ、分散環境で「正確に1回」をネットワーク層に期待した瞬間、同じ罠にはまる。規模に関係なく、原則は一つに収束する。

6. ユーザー信頼の観点 - 重複通知の本当のコスト

重複配信を単なる「うっとうしいバグ」程度に扱ってはいけない。ユーザーの立場からすれば、すでに確認して済んだはずの通知が唐突にまた表示される体験は、信頼を静かに蝕む。「このアプリは状態管理ができていないのだな」という印象は、通知権限をオフにする、ひどい場合はアプリを削除するという行動につながりやすい。特にサーフィン予報アプリのように「危険な瞬間だけ」通知すると約束したサービスであれば、その約束が破られた瞬間(不要な通知が繰り返される)、通知そのものの信頼性が損なわれる。通知システムの安定性は機能要件ではなく、ユーザー信頼の問題として扱うべきである。

7. チェックリスト - デプロイ前に確認すべきこと

  • 送信の有無・履歴をプロセスのメモリではなくDB・Redisなどの永続ストアに記録しているか
  • 各通知に(ユーザー・イベント・エンティティ・時間ウィンドウ)の組み合わせによる冪等キーがあり、一意制約がかかっているか
  • 「確認してから送信」の間をロックまたは原子的な挿入で競合状態から守っているか
  • 状態変更と送信予約を一緒にまとめる必要がある場合、アウトボックスパターンを検討したか
  • スケジュールジョブが複数インスタンスで同時に動く可能性を分散ロックまたはconcurrencyPolicyで防いでいるか
  • FCMなどに再試行ロジックがある場合、再試行がそのまま重複送信になりうることを理解し、冪等処理を備えているか
  • 再デプロイ・再起動直後に通知関連のバッチ・スケジューラーがすぐ再実行され、過去のイベントを再評価していないか

結論

FCM通知の重複配信は特定のアプリ特有の奇妙なバグではなく、分散環境で状態を扱うやり方に関する非常に普遍的な失敗の一例である。原因はほとんど常に同じところに収束する - 「一度だけ起きるべきこと」の記録をプロセスのメモリだけに置いていたか、確認と実行の間に競合を防ぐ仕組みがなかったか、再試行の可能性を考慮していなかったか。目標を「正確に1回の配信」から「最低1回配信 + 冪等処理」に変えた瞬間、解決策はむしろ明確になる。送信履歴は永続化し、冪等キーに一意制約をかけ、必要であればアウトボックスパターンと分散ロックを追加する。再デプロイと再起動は日常茶飯事だ。その前でも揺るがない設計とは、結局のところメモリを信用しない設計のことである。
