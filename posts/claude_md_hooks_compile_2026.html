CLAUDE.md 규칙을 훅으로 컴파일한다

규칙이 세션 시작에 통째로 주입되는 방식의 한계와, 선언적 규칙을 결정론적 훅으로 바꾸는 접근 분석

2026-07-22 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: CLAUDE.md가 커질수록 규칙은 오히려 약해진다

AI 코딩 에이전트를 프로젝트에 맞게 길들이는 표준적인 방법은 저장소 루트에 규칙 파일을 두는 것이다. Claude Code는 CLAUDE.md, 여러 도구가 공유하는 개방형 규약은 AGENTS.md, Cursor는 자체 룰 파일을 쓴다. 이름은 달라도 하는 일은 같다. "이 프로젝트에서는 이렇게 하라"는 지침을 자연어로 적어 두면, 에이전트가 세션을 시작할 때 그 내용을 읽어 들인다.

문제는 이 파일이 커질수록 생긴다. 컨벤션이 늘고, 과거 실수에서 배운 예외 규칙이 쌓이고, 팀이 커지면서 "이것만은 반드시 지켜라"는 항목이 늘어난다. 자연스러운 방향처럼 보이지만, 최근 커뮤니티에서 반복적으로 지적되는 것은 정반대의 결과다. 규칙 파일이 커질수록 개별 규칙이 실제로 지켜질 확률은 오히려 떨어진다. 이 글은 그 역설이 왜 생기는지, 그리고 이를 "규칙을 훅으로 컴파일한다"는 방식으로 풀어보려는 시도가 무엇을 바꾸고 무엇을 바꾸지 못하는지를 다룬다. 실마리는 GeekNews에 소개된 Claude Code 커뮤니티 플러그인 사례(참고 자료 참조)지만, 이 글의 초점은 특정 도구 홍보가 아니라 AI 코딩 에이전트 전반에 적용되는 컨텍스트 엔지니어링의 구조적 문제다. 2026년 7월 기준으로 정리한다.

1. 에이전트에 규칙을 주입하는 법 - 시스템 프롬프트와 컨텍스트 파일

1.1 세 겹의 지침 표면

현재 AI 코딩 에이전트가 사용자 의도와 팀 컨벤션을 알게 되는 경로는 대략 세 겹으로 나뉜다. 첫째는 벤더가 미리 심어 둔 시스템 프롬프트로, 사용자가 손댈 수 없는 기본 행동을 정의한다. 둘째는 프로젝트 루트의 컨텍스트 파일 - CLAUDE.md, AGENTS.md, .cursor/rules/*.mdc 같은 것들로, 팀이 직접 작성해 저장소에 커밋하는 규칙이다. 셋째는 대화 중 사용자가 그때그때 주는 지시다. 이 글이 다루는 것은 두 번째 겹, 즉 저장소에 상주하며 매 세션 반복 주입되는 컨텍스트 파일이다.

1.2 t=0 통째 주입이라는 기본 패턴

기본 동작은 단순하다. 세션이 시작되는 시점(t=0)에 파일 전체를 읽어 시스템 프롬프트 격 위치에 그대로 넣는다. 파일에 100줄짜리 규칙이 있든 1000줄짜리 규칙이 있든, 그날 작업이 그중 한두 항목만 건드리든 전체가 어차피 한 번에 들어간다. 구현이 단순하고 사람이 파일을 열어 읽기도 쉽다는 장점이 있지만, 문제는 그다음부터다.

2. 이 방식의 구조적 한계

2.1 토큰 낭비와 희석

컨텍스트 윈도는 무한하지 않고, 그 안에 들어간 토큰은 전부 비용이자 주의력 예산이다. 오늘 세션에서 전혀 건드리지 않을 배포 스크립트 컨벤션, 한 번도 안 쓸 레거시 모듈의 예외 규칙까지 매번 통째로 읽어 들이면, 실제로 중요한 나머지 컨텍스트 - 지금 열려 있는 파일, 방금 실행한 명령 결과 - 와 예산을 나눠 써야 한다. 사람 개발자가 온보딩 문서를 한 번 읽고 필요할 때만 다시 찾아보는 것과 달리, 에이전트는 매 세션 처음부터 전부를 다시 읽는다.

2.2 길수록 무시된다

토큰 비용보다 더 실질적인 문제는 규칙이 실제로 지켜지는 정도다. 지침이 길어질수록 모델이 개별 항목에 쏟는 주의는 균등하게 배분되지 않는다. 게다가 실제 작업이 길어져 대화가 압축(compaction)되면, 세션 시작 시 주입된 규칙은 요약 과정에서 축약되거나 누락되기 쉽다. 규칙집이 두꺼울수록, 세션이 길어질수록 개별 규칙이 실제로 지켜질 확률이 낮아지는 구조다.

2.3 확률적이라 강제가 안 된다

가장 근본적인 한계는 따로 있다. 자연어로 적힌 지침은 언어 모델 입장에서 본질적으로 "권고"다. 모델은 그 지침을 고려해 다음 토큰을 예측하지만, 그 예측은 확률적이다. "커밋 전에는 반드시 테스트를 돌려라"라고 CLAUDE.md에 적어 두어도, 모델이 그 문장을 읽었다는 사실과 그 문장대로 행동한다는 사실 사이에는 논리적 연결 고리가 없다. 지침을 강하게, 반복해서 적으면 준수율이 올라갈 수는 있지만 100%가 되지는 않는다. 반드시 지켜야 하는 규칙에 확률적 메커니즘을 쓰는 것 자체가 범주 오류에 가깝다.

2.4 검증 불가능성

마지막으로, 규칙이 실제로 지켜졌는지 확인할 방법이 마땅치 않다. 모델이 규칙을 읽었는지, 그 규칙이 이번 응답에 실제로 영향을 미쳤는지는 대화 로그를 사람이 직접 대조해 보기 전에는 알 수 없다. "항상 이렇게 하라"는 문장은 지켜졌을 때와 지켜지지 않았을 때를 구분해 주는 신호를 남기지 않는다.

3. "규칙을 훅으로 컴파일한다"는 발상 - 커뮤니티 플러그인 사례

3.1 무엇을 바꾸려는 시도인가

이 문제에 대응하는 최근 접근 하나가 GeekNews에 커뮤니티 플러그인 형태로 소개됐다. 발상은 단순하다. CLAUDE.md에 적힌 규칙을 자연어 그대로 두는 대신, 그 규칙이 실제로 필요한 "행동"과 짝지어 별도 파일로 뽑아내고, 그 행동이 일어나려는 순간에만 규칙을 주입한다. 이 플러그인은 이 과정을 슬래시 명령으로 실행한다. CLAUDE.md와 그 안에서 참조하는 문서를 읽어 규칙과 그에 연결된 트리거(어떤 도구 호출, 어떤 명령 패턴에서 이 규칙이 필요한가)를 추론하고, 그 결과를 사람이 검토·수정할 수 있는 평문 파일로 저장한다.

3.2 트리거와 세 가지 전달 모드

각 컴파일된 규칙은 트리거 조건 - 어떤 도구인지, 명령 문자열이 어떤 정규식과 일치하는지 - 을 프런트매터로 갖는다. 개념을 단순화하면 다음과 같은 형태다.

---
name: pr-template-check
trigger:
  tool: Bash
  pattern: "gh\s+pr\s+create"
strength: require-read
source: docs/pr-rules.md
---
PR을 만들 때는 지정된 템플릿을 반드시 사용하라.

실제 강제는 도구 호출 직전 시점에 개입하는 훅을 통해 일어난다. 예컨대 gh pr create 같은 명령이 실행되려는 순간을 정규식으로 잡아내, 명령이 실행되기 전에 관련 규칙을 모델에게 보여 준다. 전달 방식도 하나가 아니라 세 갈래다. 항상 막고 이유를 보여 주는 방식, 세션당 한 번은 막고 규칙을 보여준 뒤 재시도를 허용하는 방식, 막지 않고 맥락만 곁들이는 방식이다. 강제 수준을 규칙의 성격에 따라 조절할 수 있게 한 설계다.

3.3 압축 이후에도 살아남기

앞서 지적한 "압축되면 규칙이 증발한다"는 문제에는 별도 장치를 쓴다. 세션이 압축될 때 다시 개입하는 훅을 하나 더 두어, 이미 전달했던 규칙을 재무장한다. 규칙이 한 번 전달되고 끝나는 것이 아니라, 대화가 압축을 거쳐도 다시 감시 상태로 돌아가게 만든다.

3.4 측정치가 말해 주는 것

이 플러그인이 공개한 수치는 두 방향에서 흥미롭다. 긍정적인 쪽은, 참조 문서 여러 개를 세션 시작 시 통째로 읽어 들이던 것을 이 방식으로 바꾸자 세션 시작 토큰이 40% 이상 줄었다는 점, 그리고 실제 CLAUDE.md 파일 여러 개에서 뽑아낸 규칙 대부분이 정상적인 형식으로 변환됐다는 점이다. 반면 정직하게 짚어야 할 쪽도 있다. 자체 구성한 적대적(adversarial) 골드 스탠다드 대비 규칙 추출의 재현율은 40%에 못 미쳤다고 보고된다. 자연어 규칙을 트리거 패턴으로 "번역"하는 단계 자체가 완벽하지 않다는 뜻이다. 이 숫자는 이 접근의 가능성과 한계를 동시에 보여 준다는 점에서, 문제 삼기보다 신뢰할 만한 근거로 다뤄질 가치가 있다.

4. 선언적 규칙에서 결정론적 게이트로

4.1 컴파일러라는 비유가 정확한 이유

"규칙을 훅으로 컴파일한다"는 표현은 비유가 아니라 상당히 정확한 서술이다. 소스는 사람이 자연어로 적은 선언적 규칙("PR을 만들 때는 이 템플릿을 써라")이다. 컴파일 산출물은 특정 조건(트리거)에서 특정 동작(차단·경고·주입)을 수행하는 실행 가능한 게이트다. 그리고 이 게이트는 모델 바깥, 즉 결정론적인 코드에서 돈다. 컴파일러가 사람의 의도를 기계가 실행할 수 있는 형태로 바꾸듯, 이 접근은 팀의 의도를 모델의 확률적 판단이 아니라 코드가 실행할 수 있는 형태로 바꾼다.

4.2 같은 패턴이 반복해서 나타나는 이유

이 전환은 이 사례 하나에 국한되지 않는다. 도구 호출 스키마를 엄격하게 검증하는 구조화된 출력은 "유효한 JSON을 출력해 달라"는 프롬프트 대신 스키마 자체가 출력 형태를 강제한다는 점에서 같은 발상이다. 에이전트 하네스의 허용·거부·확인 권한 시스템도 "이 명령은 위험하니 하지 말라"는 프롬프트 대신 도구 실행 계층에서 기계적으로 막는다는 점에서 같다. 학계에서도 유사한 흐름이 있다. 에이전트의 런타임 행동에 대해 트리거·조건·강제 방식을 명시하는 도메인 특화 언어로 안전 규칙을 정의하려는 연구는, 이 커뮤니티 플러그인이 실무 규모에서 시도한 것과 같은 문제의식 - 자연어 지침은 강제가 아니라는 것 - 을 형식화한 것이다. 서로 다른 표면에서 같은 결론에 도달했다는 사실 자체가, "선언적 지침에서 결정론적 실행 게이트로"의 이행이 우연한 아이디어가 아니라 구조적으로 필요한 이행이라는 신호다.

4.3 다른 도구들도 같은 문제를 겪는다

이 문제는 Claude Code에 국한되지 않는다. 여러 에이전트가 공유하는 개방형 표준 AGENTS.md는 일부 구현이 파일 크기 자체를 강제로 제한해 문제를 회피하려 한다. Cursor의 규칙 파일은 프런트매터에 파일 패턴(glob)을 적어, 특정 확장자의 파일을 열 때만 해당 규칙이 로드되도록 한다. 이 역시 "필요할 때만 불러온다"는 같은 방향이지만, 트리거 단위가 파일 단위로 성기다는 점에서 도구 호출 단위까지 내려간 훅 기반 접근보다 입자가 굵다. 업계 전반이 "규칙을 통째로 항상 로드하는 방식은 지속 가능하지 않다"는 결론에 각자 다른 정밀도로 수렴하고 있다고 보는 것이 정확하다.

5. 훅 방식의 장단점

5.1 얻는 것 - 정확성과 강제력

훅 기반 접근이 주는 것은 명확하다. 결정론적으로 실행되므로, 조건이 맞으면 항상 개입한다. 확률적으로 "대체로 지켜지는" 것과 "반드시 지켜지는" 것 사이의 차이는 실무에서 결코 작지 않다. 보안·컴플라이언스·되돌릴 수 없는 작업(삭제, 강제 푸시, 프로덕션 배포)처럼 실패 비용이 큰 규칙일수록 이 차이가 결정적이다.

5.2 치르는 것 - 표현력과 유지보수

대가도 분명하다. 첫째, 표현력의 한계다. 훅은 코드가 기계적으로 판별할 수 있는 조건에서만 작동한다. 명령 문자열의 정규식 일치, 파일 경로 패턴, 도구 이름 같은 것은 잡아낼 수 있어도, "이 코드가 프로젝트의 관용적 스타일에 맞는가" 같은 판단이 필요한 규칙은 애초에 컴파일 대상이 아니다. 이런 규칙은 여전히 자연어로 남아 모델의 판단에 맡겨야 한다.

둘째, 유지보수 부담이 코드 쪽으로 옮겨 갈 뿐 사라지지 않는다. 자연어 규칙을 트리거로 "번역"하는 단계 자체가 오류 가능성을 지닌 별도 작업이 된다. 앞서 언급한 재현율 수치가 보여 주듯, 규칙과 트리거 사이의 매핑이 완벽하지 않으면 정작 중요한 상황에서 훅이 조용히 발동하지 않는 일이 생긴다. 트리거 목록이 늘어나면 그 자체가 하나의 작은 코드베이스가 되어 버전 관리·리뷰·테스트가 필요해진다. 평문 규칙 파일은 팀원 누구나 훑어보고 고칠 수 있었지만, 훅과 정규식으로 이루어진 규칙 저장소는 그 문턱이 더 높다.

셋째, 오탐지된 안전감이다. 규칙이 한 번 "컴파일"되면 팀은 그것이 영구히 강제된다고 믿기 쉽다. 그러나 새로운 명령, 새로운 도구, 트리거가 예상하지 못한 방식으로 호출되는 상황이 생기면 규칙은 조용히 우회된다. 훅도 결국 사람이 작성한 트리거 조건만큼만 완전하다.

5.3 비교로 정리하면

구분컨텍스트 통째 주입훅 컴파일
전달 시점세션 시작(t=0) 전체트리거 조건이 맞는 순간
강제 메커니즘모델의 확률적 판단모델 바깥의 결정론적 코드
압축 내성요약 과정에서 손실 가능재무장 훅으로 재전달
표현력어떤 규칙이든 자연어로 표현 가능기계적으로 판별 가능한 조건에 한정
유지보수 대상문서 하나트리거·정규식·훅 코드

6. 에이전트 지침 설계의 일반 원칙 - 무엇을 컨텍스트에, 무엇을 훅에

이상을 종합하면, 실무에서 참고할 만한 일반 원칙은 "모든 규칙을 훅으로 옮기자"가 아니라 규칙을 세 갈래로 나누는 것이다.

6.1 판단이 필요한 것은 컨텍스트에, 단 항상 로드하지 않는다

프로젝트의 코드 스타일 취향, 아키텍처 결정의 배경, 특정 라이브러리를 왜 쓰는지 같은 것은 모델의 판단력이 필요한 영역이다. 이런 지침은 여전히 자연어로 남아야 하지만, 반드시 세션 시작에 통째로 로드될 필요는 없다. 관련 작업이 실제로 벌어질 때만 불러오는 방식(이름과 설명만 상시 노출하고 본문은 필요할 때 읽는 구조)이 토큰 낭비와 희석 문제를 동시에 줄인다.

6.2 기계적으로 검증 가능한 것은 훅·린트·CI로

"절대 강제 푸시하지 말라", "이 파일을 수정하면 반드시 이 테스트를 돌려라", "PR 제목은 이 형식을 따르라"처럼 조건과 행동이 명확히 정의 가능한 규칙은 애초에 프롬프트에 맡길 이유가 없다. 이런 규칙은 도구 호출 직전 훅, 커밋 훅, CI 게이트처럼 모델 바깥에서 결정론적으로 도는 계층으로 옮기는 편이 정확도와 강제력 모두에서 이득이다.

6.3 셋째 범주 - 억지로 강제하지 않아도 되는 것

세 번째 갈래는 종종 간과된다. 스타일 선호, 우선순위가 낮은 컨벤션처럼 어겨도 큰 비용이 없는 규칙까지 굳이 컨텍스트 예산을 쓰거나 훅을 만들어 강제할 필요는 없다. 모든 규칙을 지키게 만들겠다는 완벽주의가 오히려 컨텍스트를 비대하게 만드는 원인 중 하나였다는 점을 감안하면, 이 범주를 과감히 덜어내는 것 자체가 하나의 최적화다.

7. 실무에서 오늘 할 수 있는 것

CLAUDE.md나 AGENTS.md가 이미 길어졌다면, 다음 순서로 점검해 볼 만하다. 우선 파일을 열어 각 규칙 옆에 "이것이 실제로 몇 번이나 어겨졌는가", "어겼을 때 비용이 얼마나 큰가"를 적어 본다. 비용이 크고 조건이 명확한 규칙부터 훅이나 CI 게이트로 옮긴다. 판단이 필요한 규칙은 컨텍스트에 남기되, 세션 시작 시 통째로 읽히는 파일에서 분리해 필요할 때만 불려 오는 구조로 바꾼다. 남는 것 중 비용이 작은 규칙은 과감히 지운다. 이 순서 자체가 컨텍스트 엔지니어링이 결국 무엇을 하는 일인지 보여 준다. 프롬프트를 더 잘 쓰는 기술이 아니라, 무엇을 모델의 판단에 맡기고 무엇을 코드에 맡길지를 매번 다시 그어야 하는 설계 작업이다.

결론

CLAUDE.md가 커질수록 규칙이 오히려 덜 지켜진다는 역설은, 자연어 지침이 본질적으로 확률적이라는 사실이 뒤늦게 드러난 결과다. 규칙을 훅으로 컴파일하는 접근은 이 문제의 일부 - 토큰 낭비, 압축으로 인한 소실, 기계적으로 검증 가능한 규칙의 미준수 - 를 실질적으로 줄인다. 그러나 모든 규칙을 이렇게 옮길 수 있는 것도 아니고, 옮긴다고 유지보수 부담이 사라지는 것도 아니다. OpenWiki의 에이전트용 문서 문제나 스펙 주도 개발이 소스의 정의를 다시 묻는 흐름과 마찬가지로, 이 사례 역시 "에이전트에게 무엇을, 어떤 형태로, 언제 알려 줄 것인가"라는 질문이 AI 코딩 도구 설계에서 앞으로도 계속 다시 그어질 경계라는 점을 보여 준다. 이해가 새로운 병목이라는 관찰과 겹쳐 보면, 규칙을 어디에 어떻게 두느냐는 결국 사람이 무엇을 검증하고 무엇을 코드에 위임할지를 정하는 문제이기도 하다.
