引言 - 省略encoding的open()从哪里取值

用open('data.txt').read()读取含韩文的文本文件的代码，在开发者的电脑上运行正常，换到另一台电脑却会因UnicodeDecodeError而停止，或者没有报错但返回的字符已经变了样。代码相同而结果不同，说明代码之外还有一个输入。这个输入就是省略encoding参数时解释器补上的默认值。下面的输出展示这个默认值来自哪里、有多容易改变，以及改变后输出是什么样子。

关于编码问题的文章已有若干篇，各自的角度不同。BOM文章讲文件开头三个字节如何破坏解析器，cp949与UTF-8乱码文章讲从乱码的形状反推原因，PowerShell 5.1重定向文章讲PowerShell写文件时选定的编码，zip文件名文章讲压缩包内名称的字节。这里只限定于：Python的open()省略编码时所用的值在哪里确定、改变它的UTF-8模式、查找风险行的EncodingWarning、3.15预定的变化，以及代码中安全的写法。cp949文章第8节有一段简短的运行，显示PYTHONUTF8=1会改变open()的默认值，下面的内容在其基础上增加变量继续展开。

涉及的问题如下。

  • 不带encoding的open()默认值是什么，与哪个函数返回的值相同？
  • 用默认值读取以UTF-8写入的韩文文件，会在哪里出现哪种异常？
  • 反过来，用UTF-8读取以默认值写入的文件会看到什么？
  • 哪些情形不抛异常却改变了字符，哪些情形在写入阶段就抛异常？
  • UTF-8模式改变什么，又不改变什么？
  • EncodingWarning对哪些行发出警告，对哪些行不发？
  • PEP 686规定的3.15变化是什么？

默认值就是locale.getencoding()返回的值

首先读取运行环境的值。下面的代码一次性输出两个区域设置编码函数、UTF-8模式标志、两个相关环境变量以及标准输出编码。

import locale, os, sys
                    print('python                ', sys.version.split()[0])
                    print('getpreferredencoding  ', locale.getpreferredencoding(False))
                    print('getencoding           ', locale.getencoding())
                    print('utf8_mode             ', sys.flags.utf8_mode)
                    print('PYTHONUTF8            ', os.environ.get('PYTHONUTF8'))
                    print('PYTHONIOENCODING      ', os.environ.get('PYTHONIOENCODING'))
                    print('stdout.encoding       ', sys.stdout.encoding)
python                 3.13.3
                    getpreferredencoding   cp949
                    getencoding            cp949
                    utf8_mode              0
                    PYTHONUTF8             None
                    PYTHONIOENCODING       None
                    stdout.encoding        cp949

这台电脑的区域设置编码是cp949，UTF-8模式处于关闭状态(utf8_mode 0)，PYTHONUTF8和PYTHONIOENCODING均未设置(None)。在此状态下直接读取open()实际使用的编码。

import locale, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    f = open('probe.txt', 'w')
                    print('open(w).encoding  ', f.encoding)
                    f.close()
                    print('open(r).encoding  ', open('probe.txt').encoding)
                    print('explicit utf-8    ', open('probe.txt', encoding='utf-8').encoding)
                    print('== getencoding()  ', open('probe.txt').encoding == locale.getencoding())
open(w).encoding   cp949
                    open(r).encoding   cp949
                    explicit utf-8     utf-8
                    == getencoding()   True

写入模式和读取模式都得到cp949，写上encoding='utf-8'则得到utf-8。最后一行把文件对象的默认编码与locale.getencoding()的返回值比较，结果为True。Python官方文档的open()条目这样描述这种关系："The default encoding is platform dependent (whatever locale.getencoding() returns), but any text encoding supported by Python can be used."输出与文档中的句子一致。

  • 默认值不是Python选定的常量，而是从运行环境的区域设置读取的值，在这台电脑上是cp949。
  • 在区域设置不同的电脑上运行同样的代码，默认值也可能不同。这就是文档写作「platform dependent」的原因。
  • 文件对象的encoding属性可以直接读出实际生效的值。在推测错误原因之前，它是最先该看的值。
  • 输出中的stdout.encoding一行是标准输出的属性，与打开文件时的默认值是不同的属性。同时改变两者的设置在第6节介绍。

用默认值读取以UTF-8写入的韩文

最常见的事故是不带encoding打开UTF-8文件。编辑器、git和其他操作系统生成的文件大多是UTF-8。下面的代码把一句韩文以UTF-8写入并输出字节，然后不带encoding读取。

import os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    with open('ko_utf8.txt', 'w', encoding='utf-8') as f:
                        f.write('한글 테스트')
                    print(open('ko_utf8.txt', 'rb').read().hex(' '))
                    try:
                        open('ko_utf8.txt').read()
                    except UnicodeDecodeError as e:
                        print(type(e).__name__, e)
ed 95 9c ea b8 80 20 ed 85 8c ec 8a a4 ed 8a b8
                    UnicodeDecodeError 'cp949' codec can't decode byte 0xed in position 0: illegal multibyte sequence

第一行是实际写入文件的16个字节。一个韩文字符占3个字节(ed 95 9c是第一个字符)，空格占1个字节(20)。读取时，cp949编解码器在位置0的0xed处报出「illegal multibyte sequence」并停止。原因可以直接从输出看出：写入方明确指定了encoding='utf-8'，读取方省略了它，于是应用了上一节看到的cp949。异常信息里包含编解码器名称'cp949'，仅凭信息就能知道读取方应用了哪种编码。

  • 异常类型是UnicodeDecodeError，信息中包含编解码器名称、出问题的字节(0xed)和位置(position 0)。
  • 编解码器名称为cp949，说明读取方的编码是cp949，所以首先该怀疑的不是文件，而是读取代码的encoding参数。
  • 在相同环境中这个异常每次都能重现。写入方与读取方在同一台电脑、同样设置时看不到问题，这一点见第6节的往返输出。

反方向 - 用UTF-8读取以默认值写入的文件

不带encoding写入的文件，如果在别处按UTF-8读取，就会出现方向相反的同一问题。下面的代码依次输出：以默认值写入的韩文字节、按cp949读取的结果、按UTF-8读取的结果，以及加上errors='replace'读取的结果。直接输出韩文会牵涉控制台编码，所以用ascii()输出码点转义。

import os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    with open('ko_default.txt', 'w') as f:
                        f.write('한글 테스트')
                    print(open('ko_default.txt', 'rb').read().hex(' '))
                    print(ascii(open('ko_default.txt', encoding='cp949').read()))
                    try:
                        open('ko_default.txt', encoding='utf-8').read()
                    except UnicodeDecodeError as e:
                        print(type(e).__name__, e)
                    print(ascii(open('ko_default.txt', encoding='utf-8', errors='replace').read()))
c7 d1 b1 db 20 c5 d7 bd ba c6 ae
                    '\ud55c\uae00 \ud14c\uc2a4\ud2b8'
                    UnicodeDecodeError 'utf-8' codec can't decode byte 0xc7 in position 0: invalid continuation byte
                    '\ufffd\u0471\ufffd \ufffd\u05fd\ufffd\u01ae'

以默认值写入的同一句话，这次保存成了c7 d1 b1 db …，即每个字符2个字节的cp949字节。按cp949读取能还原原来的韩文(\ud55c\uae00 …)，按UTF-8读取则在第一个字节0xc7处以「invalid continuation byte」停止。加上errors='replace'后异常消失，但结果字符串被\ufffd(替换字符)和无关字符(\u0471、\u05fd、\u01ae)填满，原来的句子已不在字符串中。

官方文档errors条目这样描述默认行为："'strict' to raise a ValueError exception if there is an encoding error. The default value of None has the same effect."也就是说，不写errors的调用就是strict，上面的异常是这个默认行为的结果。

  • 以cp949写入的韩文每个字符2个字节，以UTF-8写入的每个字符3个字节，第3节和第4节的字节行可以对比。
  • 同一句话在两种编码下的字节不同，因此用一种编码读取另一种编码写的文件，无论方向如何，都是误读而不是转换。
  • errors='replace'掩盖了错误并抹去了信息。在这份输出中，原始字节c7变成了\ufffd，无法再从字符串中恢复。
  • 若要保留损坏的字节，可以使用errors='backslashreplace'，第9节会比较输出。

悄悄读错的情形与写入时失败的情形

并非所有误读都以异常告终。下面的代码把「UTF-8字节按cp949解释时抛异常的字符串」与「不抛异常的字符串」并排放在一起。最后几行是用默认值写入cp949无法表示的字符(U+2728)。

import os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    print('café'.encode('utf-8').hex(' '))
                    for s in ['한글 테스트', '가나다라마바사', 'abc', 'caf\u00e9', '\u2014 dash']:
                        b = s.encode('utf-8')
                        try:
                            print('silent', ascii(s), '->', ascii(b.decode('cp949')))
                        except UnicodeDecodeError as e:
                            print('error ', ascii(s), '->', e.reason, 'at byte', e.start)
                    try:
                        open('emoji.txt', 'w').write('ok \u2728')
                    except UnicodeEncodeError as e:
                        print(type(e).__name__, e)
                    print(os.path.getsize('emoji.txt'))
63 61 66 c3 a9
                    error  '\ud55c\uae00 \ud14c\uc2a4\ud2b8' -> illegal multibyte sequence at byte 0
                    error  '\uac00\ub098\ub2e4\ub77c\ub9c8\ubc14\uc0ac' -> illegal multibyte sequence at byte 2
                    silent 'abc' -> 'abc'
                    silent 'caf\xe9' -> 'caf\ucc55'
                    error  '\u2014 dash' -> illegal multibyte sequence at byte 0
                    UnicodeEncodeError 'cp949' codec can't encode character '\u2728' in position 3: illegal multibyte sequence
                    0

第一行是café的UTF-8字节63 61 66 c3 a9。韩文句子、连续韩文音节的句子和含破折号(U+2014)的字符串都以异常结束，只含ASCII字母的abc在两种编码下相同，所以原样输出。然而café却没有任何异常，被读成了caf\ucc55。末尾的两个字节c3 a9被cp949解释成了一个有效的双字节字符(U+CC55)。由于没有异常，这种误读要到有人查看屏幕或数据时才会暴露。

写入时则相反，会抛出异常。open('emoji.txt', 'w').write('ok \u2728')以UnicodeEncodeError: 'cp949' codec can't encode character '\u2728'结束，读取文件大小得到0。文件被创建了，但想写入的内容一个字节也没有进去。

省略encoding(cp949)utf-8UnicodeDecodeError，0xc7，invalid continuation byte第4节

UTF-8模式 - 改变什么、不改变什么

官方文档UTF-8 Mode条目这样描述启用方式：UTF-8模式通过-X utf8命令行选项和PYTHONUTF8环境变量开启或关闭。开启后会发生变化的内容包括：文件系统编码成为UTF-8，open()、io.open()和codecs.open()默认使用UTF-8。文档还补充说，它们仍使用strict错误处理器，所以以文本模式打开二进制文件时，更可能抛出异常，而不是产生无意义的数据。下面的代码一次性输出与这些句子对应的值。下面的输出来自同一个脚本，仅改变了选项。

import sys, locale, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    open('probe.txt', 'w').close()
                    f = open('probe.txt')
                    print('utf8_mode      ', sys.flags.utf8_mode)
                    print('open() default ', f.encoding)
                    print('stdout         ', sys.stdout.encoding)
                    print('getencoding    ', locale.getencoding())
                    print('preferred      ', locale.getpreferredencoding(False))
                    print('fs encoding    ', sys.getfilesystemencoding())
                    print('locale option  ', open('probe.txt', encoding='locale').encoding)

表中照录了五种选项下的输出。从中可以读出以下几点。

  • -X utf8与PYTHONUTF8=1结果相同。两者都使utf8_mode变为1，open()默认值和标准输出编码变为utf-8。
  • -X utf8=0与PYTHONUTF8=0的结果与无选项时相同。在这个环境中，关闭UTF-8模式的取值与默认状态无法区分。
  • locale.getencoding()在所有情况下都是cp949。PEP 686把这个函数描述为忽略UTF-8模式、返回区域设置编码的新API，输出与该描述一致。
  • locale.getpreferredencoding(False)在UTF-8模式下变为utf-8。两个都在询问「区域设置编码」的函数给出不同答案，所以用哪个函数确认值会改变结论。
  • 指定encoding='locale'时，即使在UTF-8模式下也得到cp949。需要特意使用区域设置编码的文件(例如以该编码保存的既有配置文件)会用到这个值。
  • 文件系统编码(fs encoding)无论UTF-8模式是否开启都是utf-8。

「在我的电脑上没问题」是怎么产生的，体现在下面代码的输出中。下面的代码不带encoding写入韩文，输出字节，不带encoding读回，再按cp949读取。为了能直接看到韩文，标准输出被设为UTF-8。下面是同样的代码在无选项和-X utf8下的输出。

import sys, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    sys.stdout.reconfigure(encoding='utf-8')
                    with open('m2.txt', 'w') as f:
                        f.write('한글 테스트')
                    print(open('m2.txt', 'rb').read().hex(' '))
                    print(open('m2.txt').read())
                    try:
                        open('m2.txt', encoding='cp949').read()
                    except UnicodeDecodeError as e:
                        print('cp949 read:', type(e).__name__, e)

无选项运行的输出。

c7 d1 b1 db 20 c5 d7 bd ba c6 ae
                    한글 테스트

用-X utf8运行的输出。

ed 95 9c ea b8 80 20 ed 85 8c ec 8a a4 ed 8a b8
                    한글 테스트
                    cp949 read: UnicodeDecodeError 'cp949' codec can't decode byte 0xed in position 0: illegal multibyte sequence

无选项时保存的是c7 d1 …(cp949字节)并原样读回，所以没有错误。对同样的代码只加上-X utf8，保存的字节就变成ed 95 9c …(UTF-8)，这次按cp949读取的那一行抛出UnicodeDecodeError。代码一个字符都没有改变，改变的只是一个默认值。这就是在设置不同的电脑之间交换文件时出现错位的最小重现。

UTF-8模式也会影响旧文件。用-X utf8运行的解释器不带encoding打开前面按cp949保存的文件时，出现了下面的异常。

UnicodeDecodeError 'utf-8' codec can't decode byte 0xc7 in position 0: invalid continuation byte

开启UTF-8模式并不能消除问题，只是改变了默认值的方向。在存有cp949文件的环境中，开启的瞬间这些文件就读不出来了。

用EncodingWarning找出遗漏

开启-X warn_default_encoding选项后，省略encoding参数的调用会发出EncodingWarning。下面的代码把七种使用编码的方式放在一个文件中。第4行是省略，第5行是Path.read_text()中的省略，第9行是encoding=None。

import pathlib, os, tempfile; os.chdir(tempfile.mkdtemp())
                    with open('a.txt', 'w', encoding='utf-8') as f:
                        f.write('x')
                    open('a.txt').read()
                    pathlib.Path('a.txt').read_text()
                    open('a.txt', encoding='utf-8').read()
                    open('a.txt', 'rb').read()
                    open('a.txt', encoding='locale').read()
                    open('a.txt', encoding=None).read()

                      open('a.txt').read()
                    C:\demo\warn.py:5: EncodingWarning: 'encoding' argument not specified
                      pathlib.Path('a.txt').read_text()
                    C:\demo\warn.py:9: EncodingWarning: 'encoding' argument not specified

警告只出现在第4、5、9行。写入模式下写了encoding='utf-8'的第2行、读取时写了的第6行、二进制模式('rb')的第7行、encoding='locale'的第8行都没有警告。第9行表明encoding=None被当作省略处理。把警告升级为异常，则会在第一处停止。

同样的警告也可以用环境变量PYTHONWARNDEFAULTENCODING=1开启，输出与用选项开启时相同。环境变量适合在测试运行器或CI中不改动代码就开启。与UTF-8模式(-X utf8)同时开启时，警告仍出现在同样的三行。

警告只出现在被执行到的行。从未执行的分支中的open()没有警告，所以也要配合静态检查。下面是一个用标准库ast查找不带encoding的文本模式open()和read_text()的简短检查器。

import ast, sys
                    hits = []
                    for path in sys.argv[1:]:
                        tree = ast.parse(open(path, encoding='utf-8').read())
                        for node in ast.walk(tree):
                            if not isinstance(node, ast.Call):
                                continue
                            name = ast.unparse(node.func)
                            has_enc = any(k.arg == 'encoding' for k in node.keywords)
                            if name == 'open':
                                mode = node.args[1].value if len(node.args) > 1 else 'r'
                                if 'b' not in mode and not has_enc and len(node.args) < 4:
                                    hits.append((path, node.lineno, 'open() without encoding'))
                            elif name.endswith('.read_text') and not has_enc and not node.args:
                                hits.append((path, node.lineno, name + '() without encoding'))
                    for path, line, msg in sorted(hits):
                        print(path + ':' + str(line), msg)

                    warn.py:4 open() without encoding
                    warn.py:5 pathlib.Path('a.txt').read_text() without encoding

像json.load(open('config.json'))这样嵌套在调用里的open()也被检出为legacy.py:2，二进制模式的行和写了encoding的行没有被检出。不过这个检查器漏掉了带encoding=None的第9行(列表中没有warn.py:9)，而EncodingWarning抓到了那一行。两种方法遗漏的地方不同，所以执行到的路径交给警告，未执行的分支交给静态检查。

  • EncodingWarning只对实际执行过的调用发出。
  • encoding=None与省略一样会发出警告。
  • 开启UTF-8模式后警告并没有消失。警告的目的是暴露依赖默认值的行。
  • 静态检查能看到未执行的分支，但通过变量传递的参数或encoding=None这样的情形需要另外的规则。

PEP 686 - 3.15的计划

PEP 686的摘要这样开头："This PEP proposes enabling UTF-8 mode by default. With this change, Python consistently uses UTF-8 for default encoding of files, stdio, and pipes."按2026-10-06的文档，顶部的状态为Final，目标版本为Python 3.15。规范写道「Python will enable UTF-8 mode by default from Python 3.15.」，并说明关闭的方法是PYTHONUTF8=0和-X utf8=0。UTF-8 Mode文档中关于3.15的说明只有一句："Python 3.15 will make Python UTF-8 Mode default."

把这个计划与前面的运行放在一起看，有三点。

  • 在3.13上开启-X utf8的运行(第6节)，与文档规定为3.15默认状态的行为形态相同。在3.15中，这种行为无需选项即成为默认。
  • 即使到了3.15以后，必须使用区域设置编码的文件仍使用encoding='locale'，这个值在第6节的运行中不论UTF-8模式如何都返回cp949。
  • 由于默认值的方向改变，以cp949保存且不带encoding读取的既有代码，可能以与第6节末尾异常相同的形态读取失败。

在3.15之前的版本中，依赖默认值的代码在不同环境下行为不同。有这个计划并不会让当前版本的代码变得安全。写明编码的调用按第2节和第6节的输出那样，原样使用所指定的值。

安全的读写模式

从前面的运行得出的规则只有一句：文本模式的读取和写入两边都写上encoding。第6节的往返运行中，即使开启了UTF-8模式，明确指定的cp949仍然生效。下面把各种情形的写法和本环境的输出汇总成表。

情形写法本环境的输出
普通文本文件open(path, encoding='utf-8')文件对象的encoding为utf-8(第2节)
pathlibwrite_text(s, encoding='utf-8')、read_text(encoding='utf-8')韩文保存为ed 95 9c ea b8 80
把换行固定为LFopen(path, 'w', encoding='utf-8', newline='\n')61 0a 62 0a
带BOM的UTF-8文件encoding='utf-8-sig'不含U+FEFF的\uac00
保存JSONencoding='utf-8'加ensure_ascii=False韩文值为三个字节ea b0 92
保存CSVencoding='utf-8', newline=''韩文名称为UTF-8字节，行尾为0d 0a

表中换行、BOM、JSON这几行是下面运行得到的值。先看换行。与编码无关，文本模式在写入时还会转换换行。

import pathlib, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    p = pathlib.Path('p1.txt')
                    p.write_text('한글\n둘째', encoding='utf-8')
                    print(p.read_bytes().hex(' '))
                    with open('nl_default.txt', 'w', encoding='utf-8') as f:
                        f.write('a\nb\n')
                    with open('nl_lf.txt', 'w', encoding='utf-8', newline='\n') as f:
                        f.write('a\nb\n')
                    print(open('nl_default.txt', 'rb').read().hex(' '))
                    print(open('nl_lf.txt', 'rb').read().hex(' '))
ed 95 9c ea b8 80 0d 0a eb 91 98 ec a7 b8
                    61 0d 0a 62 0d 0a
                    61 0a 62 0a

第一行是用Path.write_text()写入的한글\n둘째的字节，换行位置写入了0d 0a(CRLF)。第二行是open(..., 'w')的默认行为，a\nb\n变成了61 0d 0a 62 0d 0a，第三行加上newline='\n'后只剩0a。在这台电脑上，换行会被自动转换。

接着是BOM、JSON和CSV。

import csv, json, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    open('bom.txt', 'wb').write(b'\xef\xbb\xbf' + '가'.encode('utf-8'))
                    print(ascii(open('bom.txt', encoding='utf-8').read()))
                    print(ascii(open('bom.txt', encoding='utf-8-sig').read()))
                    with open('d.json', 'w', encoding='utf-8') as f:
                        json.dump({'k': '값'}, f, ensure_ascii=False)
                    print(open('d.json', 'rb').read().hex(' '))
                    with open('c.csv', 'w', encoding='utf-8', newline='') as f:
                        csv.writer(f).writerow(['이름', 'x'])
                    print(open('c.csv', 'rb').read().hex(' '))
'\ufeff\uac00'
                    '\uac00'
                    7b 22 6b 22 3a 20 22 ea b0 92 22 7d
                    ec 9d b4 eb a6 84 2c 78 0d 0a

把带BOM的文件按utf-8读取，第一个字符前会留下\ufeff('\ufeff\uac00')，按utf-8-sig读取则会去掉('\uac00')。BOM的用途与问题在BOM文章中有详细介绍。JSON在ensure_ascii=False时韩文以UTF-8三字节保存，CSV中的韩文名称也以UTF-8字节保存。

最后比较处理损坏字节的errors取值的输出。输入是按cp949保存的韩文被误按UTF-8读取的情形。

b = '한글'.encode('cp949')
                    print(b.hex(' '))
                    print(ascii(b.decode('utf-8', errors='replace')))
                    print(ascii(b.decode('utf-8', errors='backslashreplace')))
c7 d1 b1 db
                    '\ufffd\u0471\ufffd'
                    '\\xc7\u0471\\xdb'

replace会抹去原始字节(\ufffd)，而backslashreplace把字节值以\xc7、\xdb的形式保留在字符串中。需要为分析留线索时，后者更好。两者都不能修复误读，解决办法是写上正确的编码。

总结起来，可以用下面的条目检查代码。

  • 所有文本模式的open()是否都带有encoding？
  • Path.read_text()和write_text()是否带有encoding？
  • 打开CSV的地方是否带有newline=''？
  • 如果打算使用区域设置编码，这一意图是否以encoding='locale'体现出来？
  • 测试运行器或CI是否检查了-X warn_default_encoding下的警告为0条？
  • 交换文件的对方所用的编码是否已在文档中确定？

未能确认的内容

  • Python 3.15解释器上的行为。这台电脑只有3.13，3.15默认的UTF-8模式及实际默认值只引用了PEP 686与UTF-8 Mode文档的文字。3.15上读取cp949文件可能失败的说法，是根据3.13上UTF-8模式的输出推断的。
  • 同样的代码在Linux或macOS上的输出。区域设置为UTF-8的环境中的默认值没有运行。
  • 其他区域设置的Windows(英文、日文等)上的默认值。这台电脑只有韩文区域设置一种。
  • 开启Windows系统区域设置中「使用UTF-8」选项时的默认值。
  • sys.stdout连接到管道或文件时的编码。第6节的标准输出值是在控制台环境中得到的。
  • EncodingWarning在subprocess、io.TextIOWrapper等open()之外的调用中出现的范围。
  • -X utf8=0与PYTHONUTF8=0在这个环境中得到与默认状态相同结果的原因。除cp949区域设置之外，与其他设置的相互作用没有运行。
  • cp949与UTF-8之外的编码(UTF-16、EUC-KR变体、扩展完成型之外的字符)上的行为。
