如何读懂「快了232倍」 - 用搜索循环自动优化性能时的成立条件

倍数由分母决定，循环由判定器决定

2026年8月16日 开发/基础设施

引言：先问分母，再看倍数

打开一篇性能改进的文章，标题上总钉着一个倍数。232倍、40倍、3.5倍。可倍数是由分子和分母共同构成的值，而留在标题里的只有分子。抽掉「相对什么」这一层，这个数字就只剩下大小，没有含义。

这个区分之所以变得格外重要，是有具体原因的。近来越来越多的尝试把性能优化从人来出主意的工作改写成循环来吐候选的工作：把目标指标和检查器交给编码智能体，让它跑上几百到几千轮。这样产出的数字往往比人工调优的数字更大，而其中相当一部分原因并不在于性能提升本身，而在于分母的选择和规则的结构。

本文讨论的就是这个循环。所谓用自动搜索优化性能，究竟要具备什么它才成立，每个阶段会坏在哪里，以及这套方法能迁移到哪里、从哪里开始迁移不动。

把已公布的性能数字拆成可核查碎片的通用流程，写在AI 一个月修复的漏洞比两年还多 - 把这条公告拆成可核查的部分里；测量卫生本身写在Mac 上本地 LLM 慢的真正原因 - 确认 GPU 是否在工作并把它打开里，这里不再重复。本文集中的是循环得以运转的条件。

1.「232倍」是相对什么而言 - 基准线造出倍数

作为素材的，是一份用自动搜索优化批量方阵QR分解内核的个人记录。先把原文写明的条件整理出来。

  • 题目：实现批量方阵的 compact-Householder QR 分解
  • 硬件：Modal 上的 NVIDIA B200
  • 输入：FP32 批量方阵，n = 32、176、352、512、1024、2048、4096，以 512 为重心
  • 排名指标：在通过正确性检查的提交中，跨多种形状与条件数情形的运行时间几何平均
  • 基准线：torch.geqrf 路径约 419,000 微秒
  • 最终：1,805 微秒。232倍就是这两者之比
  • 背景：14天内提交超过 1,500 次，在 183 名参赛者中排第 12

值得留意的是最后两行。同一篇文章还并列写下了另一个分母。其中提到早期的追踪值为 108,803 微秒、最终为 1,805 微秒，降幅 98.34%。换成这个分母，同一个成果就变成约60倍。而 183 名中第 12 名意味着，在同一份规则下还有十一个更快的提交。

三个倍数出自同一份代码：232倍、60倍，以及相对第一名的某个小于1的值。变的是什么？代码一行没变，变的只有分母。

1.1 五种基准线各自在说什么

基准线的种类用这个分母算出的倍数实际在说什么为什么容易被放大阅读时该追问什么
朴素参考实现
（教科书式循环，未做优化）		只说明「做了优化」这件事本身，几乎没有性能信息量分母可以任意慢，没有下界真的有人在用这份参考实现吗
通用库的一般路径
（低层封装调用）		说明「这个问题形状与库的一般路径不太合」库为覆盖所有形状而选择一般路径，一旦针对特定形状做特化，差距就拉开那个库里是否另有针对此场景的专用接口
针对该问题调优过的内核
（专用库或已知最优实现）		真正的贡献量。以此为分母，2倍就已经是大成果难以放大那份调优实现是否在相同硬件、相同输入下测得
自己的第一个可用版本循环实际带来的改进幅度。评估方法论时这个分母更诚实第一版越粗糙，数字越大第一版本身已经到了什么水准
同一规则下的第一名成绩自己的位置。通常小于1，所以很少出现在标题里无法放大排第几，一共多少人

本例的分母属于第二行。PyTorch 文档自己就把 torch.geqrf 写作直接调用 LAPACK geqrf 的低层函数。也就是说，基准线并不是为比赛条件（批量方阵、特定尺寸集合、FP32）准备的实现，而是一般路径。批量QR在通过库调用处理时，批次维度如何被对待，会让这个分母差出很多。

引用时的最低格式。不要只搬倍数，要把四样东西一并带上 —基准线是什么、跑在什么硬件上、输入规模与分布是什么、怎么计时的。四者中只要原文缺了一个，那个倍数就是「条件未经确认的数值」。本例中原文交代到了前三样，而预热次数、重复次数、是否锁定时钟这类测量流程并未写明，这些条目集中放在第10节。

2. 自动搜索成立的三个条件

一个问题能不能挂上循环，由结构决定，而不是由领域决定。条件有三个，三个都不可少。

2.1 正确性判定必须可由机器完成

候选是对是错，必须能在没有人介入的情况下、用一个退出码回答。没有这一条，循环就不知道该提拔什么。写出「像样的代码」和写出「正确的代码」完全是两个问题，把二者分开的正是判定器。

这里关键在于判定器的严格程度。判定器一松，搜索就会把这份松弛找出来，因为优化器不尊重规格说明，它优化的是目标函数。机器能验证与不能验证之间的界线本身，写在LLM回答中机器能验证的与不能验证的 - 验证框架划下的边界线里。

2.2 测量必须可复现

同一份代码测两次若波动很大，就分不清是改进还是噪声。这时循环会跟着噪声乱走：碰巧测得好的候选被提拔，下一代又以它为父本，朝错误的方向长下去。

所以在挂上循环之前，有一个值必须先测：噪声底噪。什么都不改，把同一份基准测试跑十遍，看波动范围。如果波动是3%，而某个候选报出2%的改进，那就不是改进。

2.3 搜索空间可表达且单圈要短

候选必须能写成代码，从生成到测量的一圈也必须足够短。单圈30分钟，一天就是四十八轮，这个量级撑不起「搜索」这两个字。本例在14天内提交超过1,500次，这意味着单圈在分钟级以内。

  • 搜索空间越连续越好。有分块尺寸、展开系数、流水阶段数这类可以小步移动的轴，局部改进才能累积
  • 候选之间必须能独立评估。前一个候选不能污染下一个候选的测量
  • 失败必须便宜。编译失败最好在秒级内结束

3. GPU内核为何格外满足这些条件

数值内核几乎完美地满足上面三条，所以自动搜索的成功案例都集中在这个领域。把原因逐条看下来，也就同时看清了迁移到别的领域时会掉什么。

  • 正确答案由数学定义。就QR而言，只需检查原矩阵能否重建为QR、Q的转置乘Q是否接近单位阵、Q的转置乘原矩阵是否接近R——三条性质就结束了。原文记载的评测器也是先从Householder表示还原出Q，再确认这三条
  • 参考实现已经存在。与库的结果对照即可，不必另行制造标准答案
  • 输出是数值数组。比较只需一次范数计算，不需要有人去肉眼判断「像不像」
  • 失败是吵闹的。编译错误、非法内存访问、NaN——大多数失败不会悄悄溜过去
  • 接口很窄。输入张量进、输出张量出，没有全局状态也没有副作用，验证范围收拢在一个函数之内
  • 测量单位是微秒。单圈短，反复才成立
  • 改进余地很大。内存层级、分块、张量核心、算子融合，可动的轴很多，而且每一个都实实在在影响性能

最后一条尤其重要。搜索只在有改进余地的地方才有意义。把循环挂到已经调得很好的代码上，跑几百轮也只能挤出几个百分点。内核执行在GPU内部究竟经过哪些阶段、每个阶段又是哪些轴左右性能，写在执行CUDA内核时GPU内部发生了什么 — 逐步深度解析里。

4. 循环的结构 - 生成、编译、验证、测量、反馈

循环的骨架很简单。要紧的是每个阶段把什么信息交给下一个阶段。

# 目标：  minimize  geomean_runtime(cand)
# 约束：  check(cand) == PASS

beam = 当前排名靠前的 3~5 个候选     # 保留多个思路家族，而不是单一冠军

while 预算尚有剩余:
    parent     = 从 beam 中挑一个
    hypothesis = 生成器(parent.src, parent.profile, 失败日志)
    src        = 把假设落实成代码

    ok, log = compile(src)
    if not ok:
        record(FAIL_COMPILE, log);   continue      # 最便宜的失败

    ok, err = check(src)                           # A≈QR, QᵀQ≈I, QᵀA≈R
    if not ok:
        record(FAIL_CORRECT, err);   continue      # 正确性不达标的在这里死掉

    t = benchmark(src)                             # 预热之后反复测量，取几何平均

    if t < parent.t:
        promote(src, t); beam = 更新(beam)
    else:
        mark_negative(hypothesis.family)           # 按思路家族标记阴性

    parent.profile = profile(src)                  # 成为下一个假设的输入

这个骨架里最容易漏掉的是最后一行。性能剖析结果不回流到生成器，那这就不是搜索，而是抽奖。下一个候选必须是上一个候选的函数，才配叫搜索。本例中也是把剖析工具的访问权放进循环，逐个候选采集剖析结果并加以比较。

第二重要的一行是 beam。只抱着当前最优的一个去改进，就成了单点爬山，一个思路家族一旦在局部拿到坏结果，整条线就被整体丢弃。原文作者也留下了本该一开始就设置束这层意思的回顾。它是防止局部阴性结果过早杀掉有用素材的装置。

5. 每个阶段各自坏在哪里

循环会在五个阶段以不同方式出故障。故障的性质不同，防御方式也必须不同。

阶段典型失败如何显现防御
候选生成反复只做同一思路的变奏，卡在局部最优改进幅度收敛到零，只剩参数数值来回抖动保留束、给思路家族打标签、向更强的模型求教、注入领域知识
编译不存在的内建指令、类型不匹配、目标硬件世代不支持的指令立刻失败，是最好处理的一种失败把失败日志原文喂回下一次提示。用文档钉死目标架构
正确性验证在容差之内悄悄削精度检查能过，只在条件数差的输入上出错把病态用例纳入检查集合。把误差余量作为连续值指标一并记录，而不只记通过与否
基准测试预热、缓存、时钟波动让噪声看起来像改进重测一遍名次就翻过来分离预热、重复测量取中位数、同条件重测、与噪声底噪比对
反馈没有剖析数据，只凭文字猜测生成下一个假设无依据的假设反复出现，同一个坑再踩一遍把剖析器纳入循环。按家族累积失败日志
目标定义指标与真实目的发生偏离排行榜在涨，真实负载却没变快让输入规模与分布贴近真实使用。把指标做成集合而不是单一数值

最后一行在本例中呈现出的具体形态很有意思。原文提到靠前的内核检测并利用了输入分布。在 n 为 512 和 1024 的情形下，输入以稠密、聚簇、秩亏、混合等多种分布给出，而快的内核加入了判别分布的检测器，让各类分布各走各的路径。

在规则内部这是合法且聪明的做法。但读的人得知道一件事：把那个内核搬到自己的数据上，倍数不会跟着来。被优化的不是内核，而是内核与评测输入的组合。

6. 基准测试的陷阱 - 别把噪声当成改进

自动搜索要测量成千上万次，所以测量误差的代价远高于人工调优时。一次测错的数值会成为父本，左右接下来几百个候选的方向。

陷阱实际发生了什么症状最低限度的防御
没有预热内核准备、内存分配、惰性初始化的开销全压在首次调用上只有第一个值格外大，之后趋于稳定把预热轮次排除在测量之外
缓存状态固定重复同一输入，只在缓存已热的状态下测基准测试很好看，真实使用却没变快轮换输入、清除缓存、复现真实访问模式
时钟与功耗波动睿频与降频让同一份代码给出不同数值名次随测量顺序而变锁定时钟，或者打乱顺序后反复测量
异步未同步CUDA调用大多异步，内核还没结束表就停了出现快得不合常理的数值用CUDA事件计时；若用CPU时钟，则同步之后再停表
输入分布偏斜检查输入不能代表真实使用的分布只适配该分布的候选胜出放多个分布并按几何平均汇总，同时盯住最坏情形
把降精度误当加速把降低精度换来的变快算作优化速度上去了，误差余量却在悄悄缩小写明容差，并把实际误差与通过与否分开记入日志

异步这一条是厂商文档直接警告过的。NVIDIA 的 CUDA C++ 最佳实践指南指出，许多 CUDA API 会在工作完成之前就把控制权交还给调用线程，并说明若要用CPU计时器准确测量，就必须用 cudaDeviceSynchronize() 做同步；同时介绍事件接口提供时间戳记录与毫秒单位的换算。该文档还写道，同步点会让流水线停顿，应当节制使用——也就是说需要把计时区间设计得足够窄。

降精度这一条与本例的规则直接咬合。按原文所述，内部使用低位宽表示是被允许的，但返回的因子仍须通过 FP32 口径的 QR 检查。最终决定精度能降到哪一步的不是内核，而是检查器的容差。检查器一松，搜索必然会把这份松弛找出来。

7. 搜索停住的地方 - 局部最优与领域知识

循环转得再顺，也一定会在某处停下。原文作者写到，在从 3,000 微秒走向 1,800 微秒的区间里，模型陷入了局部最优。症状是没完没了的参数手工微调，以及同一思路的细小变形。

这一段是整套方法论里最诚实的部分。作者自己列出的与前列名次之间的差距因素，性质是一致的。

  • 靠前的解法更彻底地剥掉了库函数。比如有的提交不把三角求解交给库，而是自己实现
  • 把中间矩阵以较低精度常驻下来，就能省掉在不同表示之间来回搬运的开销，而这个想法没能进入空间
  • 没能用上更深挖该世代张量核心的最新指令
  • 束的引入太晚

四条里有三条不是搜索能发现的类型，而是懂行的人喂进去的类型。循环擅长把给定的空间扫一遍，却不擅长把空间本身撑大。所以挂上自动搜索时，真正的瓶颈不是迭代次数，而是初始空间定义得好不好。

落到实务上的含义。放进循环之前，先把这个问题的优化轴写成文档：什么可以改、每个轴的取值范围是多少、哪些组合在物理上不可能。这份文档就是搜索空间，而不在文档里的轴，循环看不见。多写一条轴，通常比把迭代预算翻倍便宜得多。

8. 迁移得过去的地方与迁移不过去的地方

这套方法能不能挂到别的问题上，基本由两个轴决定：正确性判定是否可机械化，以及测量是否可复现。

问题类型正确性判定测量可复现性与搜索循环的契合度
数值内核与数学库机械（数学性质）高非常高
压缩与序列化格式机械（往返一致）高高
构建与测试流水线耗时机械（产物相同、测试通过）中（共享执行器噪声）中
查询计划与索引调优部分（结果集合须一致）中（依赖数据与缓存）中
一般应用代码只到测试覆盖率所及之处低到中低
界面与交互设计无法机械判定—不行
架构与设计取舍无法机械判定—不行

下半部分的共同点只有一个：正确答案写不成一个函数。好的界面、好的架构、好玩的游戏，都没有把通过与失败分开的判定器。硬造一个分数，那个分数就成了目标，原本的意义随之消失。以点击率为目标，诱导点击的界面会赢；以代码行数为目标，只是行数短的代码会赢。当目标写不成规格说明时，自动化工序能推进到哪里、又在哪里卡住，写在「好玩」写不进规格书 - AI在游戏开发哪些工序有效、哪些卡住里。

中间带的处理方式是固定的：把可判定的部分切出来放进循环，其余交给人看。比如查询调优，结果集合是否一致由机器把关，而新增索引对写入性能的影响由人来判断。把大改动切成阶段、并在每个阶段设闸门与中止基准的做法，写在用AI智能体做大规模代码迁移 - 拆分·闸门·中止判断里。

9. 要给自己的代码库挂上搜索循环

大多数情况顺序是反的：先挂智能体，检查器后补。于是循环优化的是检查器的漏洞。正确顺序是判定器 → 测量 → 循环。

9.1 动手前的检查清单

  1. 要最小化的量能否用一行写清楚，连单位一起？
  2. 正确性判定能否用一条命令跑完，退出码干净地分成 0 与 1？
  3. 如果这个判定带容差，你是否把那个数值写下来了？
  4. 检查输入集合是否代表真实分布，是否包含病态用例与边界用例？
  5. 同一份代码测十次波动是多少个百分点？不知道这个值就无法判定改进
  6. 从生成到测量单圈是几分钟？
  7. 失败是吵闹的还是安静的？若存在安静的失败，先把它变吵
  8. 剖析产物能否导出成循环读得懂的形式？
  9. 有没有提拔标准与中止标准？没有停止规则就只是在烧预算
  10. 算力与费用是否设了上限？

9.2 按顺序搭起来的方法

  • 第1步 — 先做判定器。把已有实现作为参照，写一个只回答通过或失败的脚本。此时要故意塞进几个错误实现，确认判定器能抓住。跳过这道回归测试，就没有理由信任判定器
  • 第2步 — 量出噪声底噪。什么都不改测十次，记录波动范围。此后一切改进判定都只在这个值之上进行
  • 第3步 — 缩短单圈。把失败显现得晚的顺序翻过来：编译 → 正确性 → 性能，让便宜的检查排在前面
  • 第4步 — 把轴写成文档。明确哪些参数可改、范围多大、哪些组合被禁止。这就是搜索空间
  • 第5步 — 这时才挂上循环。一开始就设置束，并让剖析结果回流
  • 第6步 — 把提拔上来的候选在真实条件下重测。在基准测试里赢和在真实负载里赢，是两件事

费用这条轴也最好事先按住。本例中作者交代的配置是两份商用编码模型订阅加上GPU执行额度，14天内提交超过1,500次，原文还提到工作区的执行额度曾经耗尽。循环的瓶颈往往不是想法，而是执行预算。把机器产出交给流程而不是人手去审的整体框架，写在搭建AI产出物审校体系 - 语法检查抓不到的那些问题里。

10. 没能确认的部分

本文没有复现这个内核。正文中的数值全部来自原文的记载，以下条目无法从原文确认。

  • 正确性检查的数值容差。三个检查项目是公开的，但阈值是多少并未写明
  • 测量流程的细节。预热次数、重复次数、计时是否基于事件、是否锁定时钟，均未明示
  • 基准线的实现细节。torch.geqrf 路径如何处理批次，以及基准线测量是否与最终提交处在完全相同的条件下，无法确认
  • 第一名的成绩及相对它的倍数。只有第12名这个名次，没有领先者的数值
  • 按尺寸、按条件数分列的单项数值。公开的是几何平均
  • 实际花费的总额。所用工具配置有交代，最终支出金额没有

因此正文中每次引用232倍，都附上了条件：torch.geqrf 路径约 419,000 微秒对 1,805 微秒，NVIDIA B200，批量方阵 FP32，跨多种形状与条件数的几何平均。剥掉条件的倍数，不是一个可以引用的数值。

结论：判定器要排在循环之前

「用自动搜索优化性能」这个故事的主角不是智能体，而是判定器与计时器。这两样准确又快，那么架在上面的搜索器无论是什么都能拿出相当的结果；这两样不牢靠，再好的搜索器也只是在优化噪声和检查器的漏洞。

GPU内核之所以成为这套方法的代表案例，并不是因为这个领域特殊，而是因为正确答案由数学定义、失败是吵闹的、单圈很短。若要问这套方法能不能搬到自己的问题上，答案不在领域名称里，而在这三个条件里。

而读数字时，永远先看分母。看着232倍和60倍从同一份代码里出来，就明白把倍数做大的最省事方法究竟是什么。不要假定别人的倍数能搬进自己的环境——在性能这件事上，只守住这一条，大部分误解就消失了。
