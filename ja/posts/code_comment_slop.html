コメントはコードが言えないことを言うべきだ

コードを繰り返すコメントが請求してくる費用と、その場所に何を置くか

2026年8月30日 開発・インフラ

言葉は多いのに残らないコメントに名前が付いた

同僚が上げた変更を開いたら、関数ひとつの上にコメントが三十行付いている。真面目に読む。読み終えると下のコードが何をするかは分かるのだが、それはコードをそのまま読んでも分かることだった。肝心のところ — なぜここでもう一度ソートするのか、なぜリトライが三回なのか — は、その三十行のどこにも書かれていない。

最近、ある開発者がこの種の文章に yap という名前を付けた。意味はおおよそ「言葉のための言葉」だ。相手に届くことを期待して発する言葉ではなく、話す側が考えを進めるために漏らす言葉。その記事の提案は単純で、レビューで同じ指摘を毎回長く書き下す代わりに短い一語で呼ぼう、というものだ。その一語は「このコメントがここで実際にどんな価値を与えているのか、もう一度考えてみてほしい」という意味で使われる。ここまでが発端で、続けて扱いたいのはその先の問いのほうだ。コメントとは何のためのものなのか。

先に整理しておきたいことが一つある。コードをそのまま書き写したコメントは、新しく現れた現象ではない。人はずっと前からそういうコメントを書いてきた。新人研修で習ったとおりに、社内規約が要求するから、あるいは何の説明も付けずにコードだけ上げると手を抜いたように見えそうだから。最近変わったのは種類ではなく量であり、量が増えたことでようやく名前が付くほど目立つようになった、というだけだ。だから問うべきは誰が書いたかではなく、その場所に何が入るべきかのほうだ。

コードはすでに何をしているかを語っている — コメントが埋める三つの欄

グーグルが公開しているコードレビュー指針には、この問題に対する一文が入っている。コメントはコード自体がどうしても持ちえない情報、たとえばある判断の背景のためのものだ、という文だ。同じ文書は、コメントはたいていコードがなぜ存在するのかを説明するときに役立ち、コードが何をしているかを説明してはならない、とも添えている。

この基準を実際に使うには、「なぜ」をもう少し割る必要がある。コメントが埋めるべき欄は三つだ。

欄コードは語れるか空いていると失うもの
なぜこうしたのか語れない。選んだ結果だけ残り、選んだ理由は消える次の人が同じ検討を最初からやり直す
何をしないと決めたのか語れない。捨てた案はコードに痕跡を残さないすでに失敗した方法へ戻す変更が上がってくる
どんな前提が置かれているか一部だけ。型と検証で移せる範囲まで前提が崩れた日、原因を探すのに何日もかかる
何をしているかすでに語っている。しかもコメントより正確に失うものがない

表の最後の行がこの話の出発点だ。コードは自分が何をしているかについてつねに最新でつねに正確な説明である。コードがそのまま挙動だからだ。同じ内容を横にもう一度書けば写しが一つ生まれるが、その写しは最新でも正確でもありうるとは限らない。同じ事実について異なる二つの記述が並んだ瞬間、読む人はどちらを信じるか決めなければならなくなる。

// コードがすでに言っていること
// リトライ回数を3に設定する
const RETRY = 3;

// コードが言えないこと
// 相手のゲートウェイは4回目のリクエストから30分の遮断をかける。
// 3はその手前の最大値だ。
const RETRY = 3;

二つのコメントの文字数は似ている。ところが上は消しても何も起きず、下は消すと半年後に誰かがリトライを5に上げて遮断される。コメントの価値は長さではなく、消したときに何が失われるかで測るほうが正確だ。

コードを繰り返すコメントが請求してくる費用

繰り返しコメントの問題を「読む時間がもったいない」だけで片づけると、実際の費用のいちばん小さい部分しか語っていないことになる。時間はそのなかで最も安い項目だ。本当の費用は時間が経ってから請求される。

核心は一つだ。コードは変わるが、その横のコメントはたいてい一緒には変わらない。理由は怠慢ではない。コードを直しに来た人は挙動を直しに来たのであり、コンパイラもリンタもテストもコメントの中身は見ない。コメントが間違っていると教えてくれる装置がどこにもないので、コメントは静かに古びる。PythonのPEP 8はこの点を短く言い切っている — コードと矛盾するコメントは、コメントが無いよりも悪い。同じ文書は、当たり前のことを書いたインラインコメントは不要であるばかりか注意を散らす、とも書いている。

いつどんな費用誰が払うか
書いた直後レビュアーが読んでコードと突き合わせる時間レビュアー
数か月後コードだけ変わりコメントが古びる。間違った地図が残る次にこのファイルを開く人
障害が起きたとき古いコメントを根拠に誤った仮説を立てる対応する人全員
つねに本当に読むべき一行が繰り返しのあいだに埋もれる全員
変更履歴で挙動と無関係な行がdiffを膨らませ、レビュー密度を下げるチーム

三行目がとりわけ高くつく。無いコメントは人をコードへ戻すが、間違ったコメントは人を見当違いの場所に引き留める。「この値はキャッシュから来る」と書かれたコメントの下でキャッシュをいくら掘っても答えが出ない状況を、一度は経験した人が多いはずだ。そのコメントは半年前まで真だった。

四行目も軽くない。コメントを読む習慣は信頼の上に立っている。十のうち九がコードを書き写した文であれば、人はやがてコメントを読み飛ばしはじめ、残りの一つ — 本当に危険を警告していた一行 — も一緒に飛ばされる。繰り返しコメントが最も大きく壊すのは、そのファイルではなくコメントという仕組みそのものの信用だ。

なぜそういうコメントが生まれるのか — どちらにも悪意はない

原因を人の側と生成の側に分けてみると、二つが別々の理由で同じ結果に行き着いていることが見えてくる。

人の側の理由はたいてい三つだ。

  • 習慣 — 最初に学ぶとき「コメントはコードを説明するもの」と身につけた。学習用の例題ではそれで正しい。学ぶ人にはコードがまだ読めないからだ。問題は、その習慣が実務のコードへそのまま持ち込まれることにある。
  • 規定 — コメントのない変更は差し戻される規則があれば、コメントは必ず付く。いちばん付けやすいコメントは、コードを書き写したコメントだ。
  • 不安 — 何の説明もなくコードだけ上げると誠意がないように見えそうだ、という感覚。これは技術の問題ではなくチームの空気の問題だ。

生成の側の理由は構造的だ。文脈なしに行単位で説明を求めれば、行単位の説明が返ってくる。一行だけ見てその行がなぜ必要かは分からないので、残るのはその行が何をしているかだけになる。これは性能の問題ではなく、依頼の形が答えの形を決めたということだ。人に同じく「各行に説明を付けてください」と頼んでも結果は似たようなものになる。

両側に共通する、もっと深い理由が一つある。「何を」は目の前にあるので書きやすく、「なぜ」は頭のなかにあるので書きにくい。なぜを書くには自分が何を検討し何を捨てたかを取り出し直さねばならず、それはコードを書き終えて疲れた時点でいちばんやりたくない作業だ。だから手は楽なほうへ動く。悪意ではなく傾斜だ。

コメントをたくさん書けという古い規則が作ったもの

多くの組織に「コメントを十分に書くこと」という規約がある。趣旨は正しい。ただし十分かどうかを何で判定するかで分かれる。判定の基準が個数や比率であれば、人は個数を埋める。これは誠実さの問題ではなく計測の問題だ。数えるものがあれば、行動は数えられる側へ整列する。

  • コメント行比率を測る指標 — 比率は繰り返しコメントを付けるのがいちばん安く上がる。「なぜ」を書けば一行だが、コードを書き写せば十行になる。
  • すべての関数にコメントを要求する規則 — 名前ですでに十分な関数にも、名前を言い換えた文が付く。
  • レビュー用チェックリストのコメント項目 — 有無だけを見るなら、あれば通る。

並べてみる価値のある反対側の例がある。Go言語のドキュメントコメント規約は公開された（大文字で始まる）すべての名前はドキュメントコメントを持つべきだと要求する。形だけ見れば上の規則と似ているのに、結果は違う。Goのドキュメントコメントはツールが抽出して公開ドキュメントとして発行されるからだ。そのコメントには読む相手が決まっている — このパッケージを初めて使う外部の開発者。行き先のある規則は、埋め合わせではなく契約になる。

ここから出てくる基準はこうだ。コメント規則を作るときは個数ではなく読者を決めるほうがいい。「このコメントを誰がいつ読むのか」に答えがあればそのコメントは使えるものになり、答えがなければ個数だけが残る。保守性の観点からレビュー基準を立て直す話は保守性の観点から見たコードレビューのほうで別に扱った。

良いコメントが座る場所

ではコメントはどこに書くのか。場所はおおよそ三つだ。

  • おかしく見えるコードの横 — 慣例と違う書き方をした部分。次の人が「これはミスだろう」と直しにかかる場所には、ミスではなく意図だという印が要る。
  • 戻しやすい判断の横 — 応急処置、迂回、暫定の定数。戻す条件を一緒に書いておけば、そのコメントは後で自分から期限切れになる。
  • 外部の制約を反映した箇所 — 相手APIの仕様、規制、ハードウェアの限界のように、リポジトリの中では確かめようのない事情。

三つに共通するのは情報の出どころがリポジトリの外だという点だ。コードをいくら読んでも、テストをいくら回しても復元されない。だから人が書き残すしかない。

// もう一度ソートする理由: 相手APIが順序を保証しない。
// 仕様書には整列されると書かれているが、実際の応答が食い違う場合がある。
// 相手が直したら、この行は消してよい。
items.sort(byCreatedAt);

この三行には表で挙げた三つの欄がすべて入っている。なぜこうしたのか（順序を信用していない）、何が前提なのか（仕様書と実際が違う）、いつ戻せるのか（相手が直したら）。消せば三つとも消え、残ったsortの一行は次の人の目には重複したソートに見える。

コメントの代わりにコードへ移せるもの

コメントを書く前に、一度尋ねてみる価値のあることがある。この説明をコードに直接語らせることはできないか。移せるなら移したほうがいい。コードに移した説明は古びないからだ。コンパイラとテストが代わりに守ってくれる。

  • 名前 — 値が何なのかを説明していたコメントは、たいてい名前に吸収される。単位が紛らわしくて付けるコメントなら、名前か型に単位を入れる。
  • 関数の分割 — 一つの関数のなかに「ここからは何をする部分」というコメントが三回出てくるなら、それは関数三つに分かれろという合図だ。コメントが小見出しの役をしているなら、その小見出しがそのまま関数名になる。
  • 型と列挙 — 「この引数は0、1、2のいずれか」というコメントは、型に移せば規則になる。コメントは破ればそれまでだが、型は破るとビルドが止まる。
  • 検証とテスト — 「負の数を入れてはいけない」というコメントは、入力検証かテスト一件に置き換えられる。文は読まれてこそ守られるが、テストは読まれなくても守られる。
// 移す前 — コメントが単位を守る
// t は秒単位。ミリ秒で渡さないこと
function expire(t) { /* ... */ }

// 移した後 — 名前が単位を守る
function expire(ttlSeconds) { /* ... */ }

この節の核心は節約ではない。コメントを書きたくなる瞬間が、設計を見直す合図であることがあるということだ。「この部分は少し複雑だから説明を付けておこう」という考えが浮かんだら、説明を付ける前に複雑なほうを手当てできないか先に見る。もちろん全部は移せない。捨てた案、相手システムの事情、このコードをいつ消せるのかといったものは、コードに書く場所がない。そういう文こそコメント本来の居場所であり、繰り返しを減らす理由もその場所を空けておくことにある。

ドキュメントとコメントの境界

すべての説明がコードの横にある必要はない。境界を決める基準は二つあれば足りる。

  • このコードを直す人が必ず見なければならないか — 見なければミスにつながる文はコードの横に置く。ウィキに書いておいても見ない。
  • この文はコードと一緒に変わるか — 一緒に変わるならコードの横。別々に動くなら外へ。同じコミットで直されない文は、コードの横にあっても結局古びる。
  • 読む人がコードを見ないこともあるか — この関数を使うだけの外部開発者が相手なら、それはドキュメントコメントの場所だ。ツールが抽出して発行する層が別にある。
  • 一度読んで終わりか、毎回参照するか — 導入や運用の手順のように順を追う文章はドキュメント側が向く。コードの横では順序が見えない。
文の性格どこに理由
この行がこうなっている理由コードの横のインラインその行を直す人だけが見ればよい
関数の前提・戻り値・例外ドキュメントコメントツールが抜き出して公開ドキュメントになる
このモジュールがなぜ存在するのかモジュール最上部かリポジトリ文書ファイル一つに縛られない
システム構造・意思決定の記録リポジトリ文書複数モジュールにまたがり、別々に更新される
導入・運用の手順リポジトリ文書順序のある文章はコードの横に合わない

境界のぼやける帯はいつも残る。そのときは直されない危険が大きいほうをコードに近づけて置くのが安全だ。コードの横にあれば、少なくともそのファイルを開く人の目には入る。APIのドキュメントとコードが食い違う経路を構造的に扱った話はAPIドキュメントのガバナンスのほうに別にある。

レビューでコメントをどう扱うか

ここがいちばん気をつける場所だ。余分なコメントの指摘は、実にたやすく人への指摘として読まれる。コードのバグを指摘されれば「自分のコードが違っていた」と聞こえるが、文を指摘されると「自分の書いた文がおかしい」と聞こえ、それははるかに個人的だ。

  • 問いの向きを変える — 「なぜこう書いたのか」ではなく「この行から読む人が得るものを一行で言えますか」と尋ねる。答えが出ればその答えが新しいコメントで、出なければ消せばいい。
  • ルールをレビューの場で初めて出さない — チームの合意として先に規約へ一段落書いておく。合意が先にあれば、その後の指摘は規則の適用であって好みの争いではない。
  • 短い略称は意味が文書にあるときだけ — 同じ指摘が繰り返されるなら縮めて呼ぶほうが楽だ。ただしその略称の意味がどこにも書かれていなければ、それはただの無礼な一言として残る。
  • 差し止めと提案を分けて表示する — 余分なコメントはたいていマージを止める事案ではない。止めるものと次に直せばよいものを表示で分けておけば、指摘は軽くなる。

そして越えないほうがよい線が一つある。コメントの文体を根拠に書き手を推測しないことだ。文が長く形式的だという理由で何を使って書いたかを当てにいきはじめると、レビューはコードから人へ移っていく。そういう推測がなぜ崩れやすいかは文体移動の測定が語れることと語れないことで扱った — 要点は、集団の水準で見える傾向を個々の文書一編に当てはめると根拠が消える、ということだ。チームのなかでは代価がさらに大きい。一度読み違えれば、その人はそれ以降レビューに防御的に出てくるようになる。

レビューで問うことは一つに絞っておくほうがいい。このコメントはこの場所で価値を出しているか。誰が書いたかは、その判断に必要ではない。

生成ツールを使うとき先に決めること

ツールの話はここまでにして、決めることだけ決めよう。依頼を決めておけば結果が決まる。

  • 頼むこと — この関数が真だと仮定している条件、選ばなかった案とその理由、戻せる措置ならば戻す条件。コードに載らない項目だ。
  • 頼まないこと — 行ごとの説明、思考の過程を残すこと、関数名を言い換えた要約。頼めば出てくるし、出てくれば消さねばならない。
  • 規約ファイルに一段落 — プロジェクトの指針ファイルにコメント規則を書いておけば、毎回同じことを言い直さずに済む。人にも同じ段落が適用される点が重要だ。
  • 下書きと提出物を分ける — 作業中に残したメモは作業が終われば片づける。下書きの痕跡がそのままマージされることが問題なのであって、下書きにメモを残すこと自体は問題ではない。

最後の防衛線はツールの設定ではない。提出する前に、自分の変更を初めて見る人の目で一度読むことだ。これは新しい規律ではなく、もともと提出の一部だった。ただコードを得る速度が上がったぶん、読む時間が相対的に惜しく見えるようになっただけだ。書くのが安くなり理解が高くなった構造はコードの経済学の変化のほうでより詳しく扱った。

基準は単純だ。手で書いたものであれ受け取ったものであれ、提出した瞬間そのコードには提出した人の名前が付く。自分が読んでいない文を他人に読ませることが失礼なのであって、ツールを使ったことが失礼なのではない。

一括整理が消してしまうもの

繰り返しコメントが多いと分かると、一度に片づけたくなる。正規表現で短いコメントを全部消すとか、ツールに「不要なコメントの削除」を任せるといったやり方だ。この作業には戻しにくい危険が一つある。なぜあるのか分からないコメントを消すことと、必要ないと判断して消すことは違う。前者は判断ではなく省略だ。

  • いちばん短いコメントがいちばん重要なことがある — 「順序を変えないこと」の一行がそうだ。長さでふるいにかけると、こういう行から先に消える。
  • 消す前に問うことは一つ — この行がなければ次の人はどんなミスをするか。思い浮かぶミスがあるなら、そのコメントは残す。
  • 古いコメントは消すより直すほうを先に見る — 古びたということは一時は真だったということであり、その場所に書くに値する事実がいまも残っている可能性が高い。
  • コミットを分ける — 数百か所を一つのコミットに入れれば誰もレビューできない。レビューできない大きさで上がってきた整理作業は、整理ではなく賭けだ。

安全な順序はこうだ。ファイル単位で見ていき、古いものは直し、直す根拠がなければ消し、消した理由をコミットメッセージに残す。遅く見えるがこの作業の目的はコメントの数を減らすことではなく、残ったコメントを信じられるようにすることだ。数字だけ減らせば目的を取り逃がす。

確認できなかったこと

  • 発端となった記事の原文ページは開かず、トピックの紹介と議論スレッドに残った要約から要点だけを押さえた。原文の例示や細かい表現はここに移していない。
  • コメント密度の規則が実際の欠陥率や保守費用にどう影響するかについて、引用できる定量研究は確保できなかった。この記事の該当箇所は測定結果ではなく規則設計についての論旨だ。
  • 生成ツールごとにコメント量がどれだけ違うかについて、公開された比較資料は見つからなかった。ツール同士の優劣はここでは扱っていない。
  • 言語圏や組織ごとにコメントの慣行は異なる。とくに規制産業のコーディング標準はここに書いた基準と別の要求をする場合があるので、そうした環境では社内標準が先だ。

まとめ — コメントはコードが言えないことを言う場所だ

残る文は三つだ。コードは何をしているかをすでに語っている — しかもコメントより正確に、つねに最新で。コメントが埋める欄は、なぜそうしたか、何をしないと決めたか、どんな前提が置かれているかだ — 三つともコードを読んでは復元されない。繰り返しコメントの本当の費用は読む時間ではなく古びることだ — コードは変わりコメントは残って、無いよりも悪い地図になる。

実践は一文に縮められる。コメントを書くとき、これを消したら何が失われるかを先に思い浮かべてみる。失われるものが無ければ、その行は最初から無くてよい。失われるものがあれば、それこそがそのコメントの存在理由であり、その文を書けばいい。

付け加えることが一つある。余分なコメントを減らそうという話は、コメントを減らそうという話ではない。むしろ逆だ。たいていのリポジトリにはなぜを書いたコメントが足りない。繰り返しを取り除く目的は空き場所を作ることであり、そこに入る文はコードを書いた人の頭のなかにしかない。その文はいま書かなければ、半年後には誰も復元できない。
