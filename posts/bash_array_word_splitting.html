  7. 명령 출력을 배열에 담는 옳은 방법

  10. 배열이 없는 셸에서도 인자는 안전하게 넘길 수 있다
  11. 외울 관용구는 여섯 개면 충분하다

서론: 파일명에 공백 하나 들어갔을 뿐인데 인자가 셋에서 다섯이 된다

몇 년째 잘 돌던 정리 스크립트가 어느 날 이상하게 동작한다. 바뀐 것은 코드가 아니라 입력이다. 누군가 annual report.pdf라는 이름으로 파일을 올렸다. 공백 하나. 그 순간부터 스크립트가 세 개라고 알고 있던 대상은 다섯 개가 되고, 존재하지 않는 annual과 report.pdf에 대해 명령이 실행된다. 그 명령이 rm이면 결과는 파일 목록이 아니라 사고 보고서로 남는다.

이건 버그가 아니라 셸의 설계다. 셸은 변수를 펼친 다음 그 결과를 다시 단어로 쪼갠다. 이 두 번째 동작을 단어 분리라고 하고, 따옴표는 그것을 끄는 스위치다. 여기까지는 널리 알려져 있다. 실제로 사람을 넘어뜨리는 것은 그다음이다. "$@"와 $@가 다르고, "$*"와 "$@"가 또 다르고, "${arr[@]}"와 ${arr[@]}가 다르며, IFS는 자를 때와 붙일 때 서로 다른 규칙을 쓴다. 이 여섯 가지 중 하나만 헷갈려도 인자 경계가 무너진다.

이 글은 그 경계를 눈에 보이게 만드는 데 집중한다. 모든 예제는 printf '[%s]\n'로 인자 하나하나를 대괄호에 담아 출력한다. 개수가 몇 개인지, 어디서 잘렸는지가 그대로 보인다. 명령과 출력은 GNU bash, version 5.2.37(1)-release와 같은 환경의 dash에서 실제로 돌려 얻은 것이다.

따옴표 자체의 종류별 차단 범위는 셸 인용부호 규칙에서 이미 다뤘으니 여기서는 반복하지 않는다. 이 글의 주제는 인용부호가 아니라 인자 경계다. 프로세스 경계에서 값이 사라지는 문제는 파이프 안 while에서 변수가 사라지는 이유가, 스크립트가 어떻게 끝나든 뒤처리를 보장하는 문제는 trap으로 임시파일 확실히 지우기가 다룬다.

예제보다 먼저 읽을 것. 이 글에서 다루는 실수는 파일을 실제로 지운다. files="annual report.pdf" 상태에서 rm $files를 실행하면 rm은 annual과 report.pdf 두 개의 인자를 받는다. 두 이름 중 하나라도 실제로 존재하면 그것이 지워진다. 확장 결과에 *가 섞여 있으면 범위는 더 넓어진다. 파일 목록을 다루는 코드를 고칠 때는 삭제 명령을 echo로 바꿔 한 번 돌려 대상 목록을 눈으로 확인한 뒤 되돌린다. 그리고 rm이나 mv에는 -- 종결자를 붙이고, 파일 목록은 문자열이 아니라 배열로 담아 "${files[@]}"로 펼친다. 개행이 든 이름까지 감당해야 하면 find -print0와 read -d '' 조합을 쓴다. 이 세 가지는 뒤에서 하나씩 실행해 확인한다.

1. 같은 세 개를 넘겼는데 함수는 다섯 개를 받는다

인자 세 개를 만들고 네 가지 형태로 함수에 넘겨 개수를 센다. 대상은 공백이 든 파일명 둘과 평범한 이름 하나다.

#!/usr/bin/env bash
show() { printf '  count=%d\n' "$#"; printf '  [%s]\n' "$@"; }

f1() { show "$@"; }
f2() { show $@; }
f3() { show "$*"; }
f4() { show $*; }

set -- "annual report.pdf" "q3 data.csv" plain.txt

echo '--- "$@" ---'; f1 "$@"
echo '--- $@  ---';  f2 "$@"
echo '--- "$*" ---'; f3 "$@"
echo '--- $*  ---';  f4 "$@"
$ bash t1.sh
--- "$@" ---
  count=3
  [annual report.pdf]
  [q3 data.csv]
  [plain.txt]
--- $@  ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]
--- "$*" ---
  count=1
  [annual report.pdf q3 data.csv plain.txt]
--- $*  ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]

세 개를 넣었는데 나온 개수가 3, 5, 1, 5다. 원래 개수를 지킨 것은 첫 번째 하나뿐이다. 나머지 셋은 각각 다른 방식으로 경계를 무너뜨렸다.

1.1 네 조합이 하는 일을 한 표로

형태결과 단어 수단어 분리글로빙쓸 자리
"$@"3 (원래대로)안 일어남안 일어남인자를 그대로 넘길 때. 사실상 유일한 정답
$@5일어남일어남쓸 자리가 거의 없다
"$*"1 (하나로 합침)안 일어남안 일어남로그 한 줄에 인자를 찍을 때
$*5일어남일어남쓸 자리가 거의 없다

표에서 $@와 $*의 결과가 같아 보이는데 이건 우연이 아니다. 따옴표를 떼는 순간 둘의 차이가 사라진다. 따옴표 없는 확장은 어차피 전부 IFS로 다시 쪼개지므로 「어떻게 합쳐졌는가」가 의미를 잃는다. 그래서 $@와 $*의 차이를 논하는 것은 따옴표를 붙였을 때만 의미가 있다.

  • "$@"는 인자 개수만큼의 단어로 펼쳐진다. 인자가 0개면 단어도 0개다
  • "$*"는 항상 정확히 한 단어다. 인자가 0개여도 빈 문자열 한 개가 된다
  • $@와 $*는 결과가 같다. 둘 다 IFS 분리와 글로빙을 통과한다
  • 인자를 다른 명령에 전달하는 자리에서 "$*"를 쓰면 인자 하나로 뭉쳐서 도착한다
  • 사람이 읽을 로그 한 줄을 만드는 자리라면 "$*"가 오히려 적절하다. echo "실행: $0 $*" 같은 용도다
  • $#은 위치 인자 개수다. 위 실행에서 함수 안 $#이 3, 5, 1, 5로 찍힌 것이 그 값이다

1.2 for 문에서도 같은 규칙이 적용된다

$ bash t12.sh
--- for 루프 ---
for x in "$@"
    [annual report.pdf]
    [q3 data.csv]
for x in $*
    [annual]
    [report.pdf]
    [q3]
    [data.csv]
for x in "$*"
    [annual report.pdf q3 data.csv]
인자 목록 없는 for x 는 "$@" 와 같다
    [annual report.pdf]
    [q3 data.csv]

마지막 형태를 기억해 둘 만하다. for x; do ... done처럼 목록을 아예 안 적으면 셸이 "$@"를 쓴다. 따옴표를 빠뜨릴 여지 자체가 없어진다.

2. 셸이 확장 뒤에 조용히 하는 두 가지

왜 이런 일이 생기는지는 셸이 명령 한 줄을 처리하는 순서를 보면 정리된다. 변수를 펼치는 것은 중간 단계일 뿐이고, 그 뒤에 두 단계가 더 있다.

  1. 확장 — $var, ${arr[@]}, $(cmd) 같은 것이 값으로 바뀐다
  2. 단어 분리 — 방금 나온 값을 IFS에 든 문자로 잘라 여러 단어로 만든다
  3. 경로명 확장 — 각 단어 안에 * ? [가 있으면 실제 파일명으로 바꾼다

큰따옴표로 감싸면 2번과 3번을 건너뛴다. 1번은 그대로 일어난다. 그래서 "$var"는 값을 꺼내되 그 값을 한 단어로 유지한다. 이 한 문장이 이 글 전체의 요약이다.

중요한 것은 2번과 3번이 변수에서 나온 값에만 적용된다는 점이다. 스크립트에 직접 적은 리터럴은 대상이 아니다.

$ bash -c 'show() { echo "count=$#"; }; show annual report.pdf'
count=2                # 리터럴 두 단어. 원래부터 두 개다

$ bash -c 'x="annual report.pdf"; show() { echo "count=$#"; }; show $x'
count=2                # 변수에서 나온 뒤 잘렸다

$ bash -c 'x="annual report.pdf"; show() { echo "count=$#"; }; show "$x"'
count=1                # 따옴표가 2번을 껐다
  • 가운데 줄이 사고의 원형이다. 변수 안에서는 한 덩어리였던 값이 명령에 도착할 때는 두 개가 됐다
  • 명령 치환 $(cmd)의 결과도 똑같이 2번과 3번을 통과한다. 그래서 $(...)도 따옴표로 감싸는 것이 기본이다
  • 산술 확장 $((...))의 결과는 숫자라 실무에서 문제가 되는 경우가 드물지만 규칙 자체는 같다
  • 대입문 우변은 예외다. x=$y는 따옴표가 없어도 분리되지 않는다. 대입은 원래 단어 하나를 받는 자리이기 때문이다
  • case의 대상어와 [[ ]] 안쪽도 분리가 일어나지 않는다. 반면 옛 [ ] 안쪽은 일어난다. 이 차이 때문에 [ $x = y ]는 x가 비면 문법 오류를 낸다

3. IFS는 자르는 칼이면서 붙이는 풀이다

IFS는 두 가지 일을 하는데 규칙이 서로 다르다. 이 비대칭을 모르면 IFS를 바꾼 뒤 결과를 예측할 수 없다.

3.1 붙일 때는 첫 글자 하나만 쓴다

#!/usr/bin/env bash
set -- alpha beta gamma
echo "기본 IFS   : [$*]"
IFS=,
echo "IFS=,      : [$*]"
IFS=
echo "IFS 빈 값  : [$*]"
unset IFS
echo "IFS 해제   : [$*]"
IFS=',;|'
echo "IFS=',;|'  : [$*]"
$ bash t3.sh
기본 IFS   : [alpha beta gamma]
IFS=,      : [alpha,beta,gamma]
IFS 빈 값  : [alphabetagamma]
IFS 해제   : [alpha beta gamma]
IFS=',;|'  : [alpha,beta,gamma]

마지막 줄이 핵심이다. IFS에 세 글자를 넣었는데 사이에 들어간 것은 첫 글자 하나뿐이다. 그리고 IFS를 빈 값으로 두면 아무것도 넣지 않고 그냥 이어 붙이며, unset하면 기본값인 공백으로 되돌아간다. 빈 값과 해제는 완전히 다른 상태다.

같은 실행에서 "$@"는 IFS를 콜론으로 바꿔도 흔들리지 않았다.

IFS=: 로 바꾼 상태에서 "$@" 는 그대로:
  [alpha]
  [beta]
  [gamma]

3.2 자를 때는 든 글자 전부를 쓴다

#!/usr/bin/env bash
line="root:x:0:0:root:/root:/bin/bash"
show() { echo "  count=$#"; printf '  [%s]\n' "$@"; }
echo '--- 기본 IFS, 따옴표 없음 ---'
show $line
echo '--- IFS=: 따옴표 없음 ---'
IFS=:
show $line
echo '--- IFS=: 지만 따옴표 있음 ---'
show "$line"
$ bash t4.sh
--- 기본 IFS, 따옴표 없음 ---
  count=1
  [root:x:0:0:root:/root:/bin/bash]
--- IFS=: 따옴표 없음 ---
  count=7
  [root]
  [x]
  [0]
  [0]
  [root]
  [/root]
  [/bin/bash]
--- IFS=: 지만 따옴표 있음 ---
  count=1
  [root:x:0:0:root:/root:/bin/bash]

여기서 IFS는 필드 구분자 역할을 제대로 한다. 계정 정보 한 줄을 일곱 필드로 정확히 갈랐다. 그런데 같은 상태에서 따옴표를 붙이면 아무 일도 일어나지 않는다. IFS는 따옴표 없는 확장에만 작용한다.

3.3 IFS를 바꿀 때 지켜야 할 것

IFS를 전역으로 바꿔 놓으면 그 뒤의 모든 미인용 확장이 영향을 받는다. 한 명령에만 적용하는 방법이 있다.

$ bash t13.sh
--- 저장하고 되돌리는 방식 ---
old_IFS=$IFS; IFS=,; read -r -a parts <<< "alpha,beta,gamma delta"; IFS=$old_IFS
  3 elements
    [alpha]
    [beta]
    [gamma delta]
--- IFS=, read -a : 그 명령에만 적용 ---
  3 elements
    [alpha]
    [beta]
    [gamma delta]
  IFS after: $' \t\n'

두 번째 형태가 낫다. IFS=, read -r -a parts처럼 명령 앞에 붙인 대입은 그 명령이 실행되는 동안에만 유효하다. 실행 후 IFS를 확인하면 기본값 그대로다. 저장하고 되돌리는 방식은 중간에 return이나 오류로 빠져나가면 복원이 안 된다.

  • 기본 IFS는 공백·탭·개행 세 글자다. 위 출력의 $' \t\n'이 그 값이다
  • 이 세 글자는 특별 대우를 받는다. 연속된 공백은 하나로 취급되고 앞뒤 공백은 버려진다
  • 공백이 아닌 구분자, 예를 들어 콜론은 다르다. 연속된 콜론은 빈 필드를 만든다
  • 따라서 a::b를 IFS=:으로 자르면 필드가 셋이고 가운데는 빈 문자열이다
  • 파일을 한 줄씩 읽을 때 while IFS= read -r line으로 IFS를 비우는 이유가 여기 있다. 줄 앞뒤 공백이 잘려 나가는 것을 막는다
  • read -r의 -r은 백슬래시를 이스케이프로 해석하지 않게 한다. 경로를 읽을 때 사실상 필수다

4. 따옴표를 빼면 문자열이 파일명으로 바뀐다

단어 분리보다 덜 알려졌지만 더 위험한 쪽이 경로명 확장이다. 파일 세 개가 있는 디렉터리에서 확인한다.

#!/usr/bin/env bash
# 이 디렉터리에는 report.txt, notes.txt, archive.tar 가 있다
pattern='*.txt'
show() { echo "  count=$#"; printf '  [%s]\n' "$@"; }
echo '--- 따옴표 없는 $pattern ---'; show $pattern
echo '--- 따옴표 붙인 "$pattern" ---'; show "$pattern"
echo '--- set -f 를 켠 상태 ---'; set -f; show $pattern; set +f
$ bash t5.sh
files here: archive.tar notes.txt report.txt
--- 따옴표 없는 $pattern ---
  count=2
  [notes.txt]
  [report.txt]
--- 따옴표 붙인 "$pattern" ---
  count=1
  [*.txt]
--- set -f 를 켠 상태 ---
  count=1
  [*.txt]

변수에 든 값은 *.txt인데 명령이 받은 것은 실제 파일 두 개다. 변수 안에 저장된 문자열이 명령에 도착하기 직전에 다른 것으로 바뀌었다. 이 변환은 파일시스템의 현재 상태에 따라 달라지므로 같은 코드가 어제와 오늘 다르게 동작한다.

4.1 배열 원소에 글로브가 섞이면 두 배로 터진다

$ bash t5.sh
--- 원소에 글로브가 든 배열 ---
arr=('*.txt' 'literal name.txt')
  따옴표 없는 ${arr[@]}:
  count=4
  [notes.txt]
  [report.txt]
  [literal]
  [name.txt]
  따옴표 붙인 "${arr[@]}":
  count=2
  [*.txt]
  [literal name.txt]

원소 두 개짜리 배열이 네 개가 됐다. 첫 원소는 글로빙으로 둘이 됐고 둘째 원소는 단어 분리로 둘이 됐다. 두 단계가 순서대로 적용되기 때문에 피해가 곱해진다.

  • 글로브가 아무 파일과도 일치하지 않으면 bash 기본 설정에서는 패턴 문자 그대로 남는다. 그래서 문제가 늦게 발견된다
  • shopt -s nullglob을 켜면 일치하는 것이 없을 때 단어가 사라진다. 인자가 통째로 없어지는 또 다른 사고가 된다
  • shopt -s failglob은 일치가 없으면 오류를 낸다. 대화형 셸에서는 유용하지만 스크립트에서는 예상 밖의 중단을 만든다
  • set -f는 글로빙만 끄고 단어 분리는 그대로 둔다. 위 실행에서 [*.txt]가 한 단어로 남은 것이 그 결과다
  • set -f를 스크립트 전체에 켜 두면 정작 필요한 곳에서 글로브가 안 돌아간다. 필요한 구간만 켜고 set +f로 되돌린다
  • 근본적인 해결은 따옴표다. set -f는 남의 코드를 고칠 수 없을 때 쓰는 임시 방편에 가깝다

5. 배열 확장 네 형태의 원소 수를 세어 본다

위치 인자에서 본 네 조합은 배열에도 그대로 있다. 형태만 바뀐다.

#!/usr/bin/env bash
arr=("annual report.pdf" "q3 data.csv" plain.txt)
count() { echo "  count=$#"; printf '  [%s]\n' "$@"; }
count "${arr[@]}"
count ${arr[@]}
count "${arr[*]}"
count ${arr[*]}
echo "원소 개수: ${#arr[@]}"
echo "첫 원소의 글자 수: ${#arr[0]}"
$ bash t2.sh
--- "${arr[@]}" ---
  count=3
  [annual report.pdf]
  [q3 data.csv]
  [plain.txt]
--- ${arr[@]}   ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]
--- "${arr[*]}" ---
  count=1
  [annual report.pdf q3 data.csv plain.txt]
--- ${arr[*]}   ---
  count=5
--- 원소 개수: 3 ---
--- 첫 원소의 글자 수: 17 ---

1절의 표가 그대로 적용된다. 배열을 배열답게 쓰려면 "${arr[@]}" 하나뿐이다. 나머지 세 형태는 배열을 배열이 아닌 것으로 만든다.

마지막 두 줄도 짚고 넘어갈 만하다. ${#arr[@]}는 원소 개수 3, ${#arr[0]}는 첫 원소의 글자 수 17이다. 대괄호 안에 무엇이 들어가느냐에 따라 #의 의미가 바뀐다.

5.1 배열 이름만 쓰면 첫 원소가 나온다

$ bash t11.sh
arr=("a:b" "c d" "e")
  $arr        = [a:b]
  ${arr[0]}   = [a:b]
  ${arr[@]:1} = [c d e]

$arr는 배열 전체가 아니라 ${arr[0]}이다. 오류를 내지 않기 때문에 발견이 늦다. 원소가 하나뿐인 배열로 테스트하면 이 실수가 끝까지 드러나지 않는다. 테스트 데이터에 원소를 최소 두 개 넣는 습관이 이런 종류의 버그를 걸러 낸다.

5.2 IFS는 배열의 미인용 확장에도 작용한다

$ bash t11.sh
arr=("a:b" "c d" "e")
--- IFS=: 로 두고 따옴표 없이 ---
  count=4
  [a]
  [b]
  [c d]
  [e]
--- 같은 상태에서 따옴표를 붙이면 ---
  count=3
  [a:b]
  [c d]
  [e]
--- "${arr[*]}" 는 첫 IFS 문자로 붙인다 ---
  count=1
  [a:b:c d:e]

첫 결과가 흥미롭다. IFS가 콜론이므로 a:b는 둘로 갈라졌지만 c d의 공백은 이제 구분자가 아니라 그대로 남았다. IFS를 바꾸면 무엇이 잘리는지가 통째로 바뀐다.

5.3 슬라이싱과 희소 배열

$ bash t11.sh
--- "${arr[@]:1:2}" ---
  count=2
  [c d]
  [e]
--- 원소를 하나 지우면 번호가 다시 매겨지지 않는다 ---
s=(zero one two); unset 's[1]'
  count=2  indices=0 2
  [zero]
  [two]
--- declare -p 로 실제 모양 확인 ---
declare -a s=([0]="zero" [2]="two")
declare -a arr=([0]="a:b" [1]="c d" [2]="e")

unset으로 가운데를 지우면 번호가 다시 매겨지지 않고 구멍이 남는다. ${#s[@]}는 2인데 유효한 마지막 인덱스는 2다. 그래서 for ((i=0; i<${#s[@]}; i++)) 같은 인덱스 루프는 이런 배열에서 원소를 놓친다.

  • 배열을 순회할 때는 인덱스 루프 대신 for x in "${arr[@]}"를 쓴다. 구멍을 알아서 건너뛴다
  • 인덱스가 꼭 필요하면 ${!arr[@]}로 실제 존재하는 인덱스 목록을 받는다. 위 출력의 indices=0 2가 그것이다
  • declare -p는 배열의 실제 모양을 인덱스까지 보여준다. 배열이 이상할 때 가장 먼저 찍어 볼 것이다
  • 슬라이스 "${arr[@]:1:2}"도 따옴표 규칙이 그대로 적용된다. 따옴표를 빼면 다시 쪼개진다
  • arr+=("새 원소")는 뒤에 붙이고 arr=("새 원소")는 통째로 갈아치운다. 확인한 결과 전자는 2개, 후자는 1개가 됐다
  • 연관 배열은 declare -A로 먼저 선언해야 한다. 선언 없이 문자열 키를 쓰면 산술 평가를 거쳐 인덱스 0으로 들어간다

6. 빈 문자열과 개행이 든 원소는 어디서 사라지나

원소 세 개 중 가운데가 빈 문자열인 배열을 만들어 확인한다.

$ bash t7.sh
--- 빈 문자열 원소가 든 배열, ${#arr[@]}=3 ---
  count=3
  [first]
  []
  [third]
--- 같은 배열을 따옴표 없이 ---
  count=2
  [first]
  [third]

빈 원소가 흔적도 없이 사라졌다. 원소는 셋인데 명령에는 둘만 도착한다. 선택 항목이 비어 있을 수 있는 설정 값을 배열에 담아 명령줄로 넘기는 구조라면, 인자 위치가 통째로 밀려 다음 인자가 엉뚱한 자리에 들어간다.

$ bash t7.sh
--- 원소에 개행이 든 경우, ${#arr2[@]}=2 ---
  count=2
  [line1
line2]
  [tail]
--- 따옴표 없이: 개행도 IFS 문자라서 잘린다 ---
  count=3
  [line1]
  [line2]
  [tail]

개행은 기본 IFS에 포함된 세 글자 중 하나다. 그래서 개행이 든 파일명은 따옴표 없는 확장에서 두 개의 파일명이 된다. 리눅스 파일시스템에서 파일명에 개행을 넣는 것은 금지돼 있지 않다. 사용자 업로드나 압축 해제 결과를 다루는 코드라면 실제로 만날 수 있다.

6.1 빈 배열을 set -u 아래서 펼칠 때

$ bash t6.sh
bash 5.2.37(1)-release
--- set -u 상태에서 "${empty[@]}" ---
  OK, 아무것도 없이 확장됨: rc=0
--- "${empty[*]}" 는 다르다 ---
  count=1              # 빈 문자열 한 개가 생긴다
--- "${empty[@]}" 를 명령에 넘기면 ---
  count=0              # 인자가 아예 없다
--- ${empty[@]:-<기본값>} 관용구 ---
  [<기본값>]

bash 5.2.37에서는 set -u 아래서 빈 배열을 "${empty[@]}"로 펼쳐도 오류가 나지 않고 인자 0개로 확장됐다. 이 동작은 bash 4.4에서 바뀐 것으로, 그 이전 버전에서는 unbound variable 오류가 났다고 알려져 있다. 구버전 bash는 이 환경에 없어 확인하지 못했다. 오래된 배포판을 대상으로 하는 스크립트라면 "${empty[@]:-}" 형태로 방어하는 관용구가 아직 쓰인다.

같은 출력에서 "${empty[*]}"가 count=1을 낸 것을 주목할 만하다. 빈 배열인데 인자가 하나 생겼다. 빈 문자열 하나다. 이 상태로 명령에 넘어가면 「인자가 없음」이 아니라 「빈 인자가 있음」이 되어 명령이 다르게 동작한다.

7. 명령 출력을 배열에 담는 옳은 방법

파일 두 개가 든 디렉터리에서 네 가지 방법을 비교한다. 파일 하나의 이름에 공백이 있다.

$ bash t8.sh
files: annual report.txt|notes.txt|
--- arr=($(ls)) ---
  3 elements
  [annual]
  [report.txt]
  [notes.txt]
--- mapfile -t arr2 < <(ls) ---
  2 elements
  [annual report.txt]
  [notes.txt]
--- readarray -t arr3 < <(ls) ---
  2 elements
--- arr4=(*) ---
  2 elements
  [annual report.txt]
  [notes.txt]
--- mapfile -d '' arr5 < <(find . -maxdepth 1 -type f -print0) ---
  2 elements
  [./annual report.txt]
  [./notes.txt]

첫 방법만 틀렸다. arr=($(ls))는 명령 출력을 단어 분리와 글로빙에 그대로 통과시킨다. 배열 대입의 괄호 안은 따옴표로 감쌀 수 없는 자리다. arr=("$(ls)")로 쓰면 이번에는 출력 전체가 원소 하나가 되어 배열의 의미가 사라진다.

  • mapfile -t는 줄 단위로 읽고 -t가 줄 끝의 개행을 떼어 낸다. 대상이 줄 목록이면 이것이 기본형이다
  • readarray는 mapfile의 다른 이름이다. 같은 내장 명령이고 확인한 결과도 같았다
  • 파이프 대신 < <(cmd)를 쓰는 이유가 있다. cmd | mapfile로 쓰면 mapfile이 서브셸에서 돌아 배열이 밖으로 나오지 않는다. 서브셸 글의 문제와 같은 뿌리다
  • 대상이 파일명이라면 arr=(*)가 가장 안전하다. 셸이 직접 목록을 만들므로 어떤 이름이든 원소 하나로 들어간다
  • 다만 arr=(*)는 일치하는 파일이 없을 때 *라는 문자열 하나가 든 배열이 된다. shopt -s nullglob과 같이 쓰거나 [ -e "${arr[0]}" ]로 확인한다
  • 개행이 든 이름까지 감당해야 하면 mapfile -d ''와 find -print0 조합을 쓴다. 널 문자는 파일명에 들어갈 수 없는 유일한 문자라 구분자로 안전하다
  • mapfile은 bash 4 이상의 기능이다. POSIX sh로 돌아가야 하는 스크립트에서는 쓸 수 없다

7.1 파일 목록을 한 줄씩 도는 두 방법

$ bash t10.sh
--- find -print0 + read -d '' ---
    got [./-rf]
    got [./annual report.pdf]
    got [./keep me.txt]
  total=3
--- for f in $(find . -type f) ---
    got [./-rf]
    got [./annual]
    got [report.pdf]
    got [./keep]
    got [me.txt]
  total=5

세 개의 파일이 다섯 개로 늘었다. 아래 형태로 rm을 돌리면 존재하지 않는 report.pdf와 ./keep에 대해 삭제가 시도되고, 그 이름의 파일이 실제로 있으면 지워진다. 위 형태의 실제 코드는 이렇다.

while IFS= read -r -d '' f; do
    echo "처리: [$f]"
done < <(find . -maxdepth 1 -type f -print0)

IFS=로 비운 것, -r로 백슬래시 해석을 끈 것, -d ''로 구분자를 널 문자로 바꾼 것 세 가지가 모두 필요하다. 하나라도 빠지면 특정 이름에서 무너진다.

8. 배열은 함수에 값으로 넘어가지 않는다

배열을 함수에 넘기려 하면 도착하는 것은 배열이 아니라 인자 여러 개다.

$ bash t9.sh
--- 배열을 값으로 넘길 수 없다. 인자로 납작해진다 ---
arr=("annual report.pdf" "q3 data.csv")
takes "${arr[@]}"
  inside: $1=[annual report.pdf]  $#=2
--- 함수 안에서 배열로 되살리기 ---
h() { local -a mine=("$@"); echo "  mine=${#mine[@]}"; }
  mine=2
--- 이름만 넘기고 nameref 로 받기 (bash 4.3+) ---
byref() { local -n ref=$1; echo "  ${#ref[@]} elements, first=[${ref[0]}]"; }
byref arr
  2 elements, first=[annual report.pdf]
--- local -a 는 전역을 오염시키지 않는다 ---
  inner has 2
  inner outside: [<unset>]
--- set -- "${arr[@]}" 로 위치 인자에 갈아끼우기 ---
  $#=2
  [annual report.pdf]
  [q3 data.csv]

세 가지 방법이 각각 자리가 다르다.

  • 인자로 받아 다시 배열을 만든다. local -a mine=("$@") 한 줄이면 된다. 가장 단순하고 이식성도 가장 좋다
  • 단점은 배열을 하나만 넘길 수 있다는 것이다. 두 개를 넘기려면 구분자 역할을 하는 인자를 끼워 넣는 식의 우회가 필요하다
  • 이름만 넘기고 nameref로 받는다. local -n ref=$1은 원본을 그대로 가리키므로 함수 안에서 수정하면 밖에도 반영된다
  • nameref는 bash 4.3 이상의 기능이다. 그리고 매개변수 이름과 넘긴 배열 이름이 같으면 순환 참조 오류가 난다. ref 같은 흔한 이름 대신 접두사를 붙이는 관행이 있다
  • 위치 인자로 갈아끼운다. set -- "${arr[@]}" 뒤로는 "$@"가 그 배열이 된다. POSIX sh에서도 통하는 유일한 방법이다
  • 다만 원래 있던 위치 인자를 덮어쓴다. 나중에 필요하면 미리 다른 배열에 보관해 둔다
  • local -a로 선언한 배열은 함수 밖에서 보이지 않는다. 위 출력에서 <unset>이 찍힌 것이 그 확인이다
  • local 없이 함수 안에서 배열을 만들면 전역이 된다. 같은 이름을 쓰는 다른 함수와 조용히 충돌한다

8.1 인자를 그대로 넘기는 래퍼

$ bash t13.sh
good: wrapper_good() { inner "$@"; }
  inner sees 2 arg(s):
    [annual report.pdf]
    [q3 data.csv]
bad:  wrapper_bad()  { inner $@; }
  inner sees 4 arg(s):
    [annual]
    [report.pdf]
    [q3]
    [data.csv]
--- 옵션을 앞에 붙여 넘기기 ---
wrapper_opt() { inner --dry-run "$@"; }
  inner sees 2 arg(s):
    [--dry-run]
    [annual report.pdf]

래퍼 스크립트는 이 실수가 가장 자주 나오는 자리다. docker나 kubectl 앞에 옵션 몇 개를 붙여 주는 얇은 래퍼를 만들 때, 마지막 줄의 "$@"에서 따옴표를 빠뜨리면 공백이 든 인자를 넘기는 순간 조용히 깨진다. 평소 테스트에서는 인자에 공백이 없어서 드러나지 않는다.

9. 옵션이 붙었다 떨어졌다 하는 명령줄 조립하기

조건에 따라 옵션이 달라지는 명령을 만들 때, 문자열로 조립하면 반드시 깨진다. 배열이 정확히 이 문제를 위해 있다.

#!/usr/bin/env bash
opts=()
verbose=1
outfile="my output.log"
[ "$verbose" = 1 ] && opts+=(--verbose)
opts+=(--output "$outfile")
echo "${#opts[@]} args:"; printf '  [%s]\n' "${opts[@]}"
$ bash t12.sh
--- 배열로 조립 ---
  3 args:
    [--verbose]
    [--output]
    [my output.log]
--- 문자열로 조립하면 ---
optstr="--verbose --output $outfile"
  명령이 받는 것:
    [--verbose]
    [--output]
    [my]
    [output.log]

문자열 쪽은 파일명이 두 조각이 됐다. 명령은 --output my로 읽고 output.log를 별개의 위치 인자로 받는다. 오류 메시지가 나면 그나마 다행이고, 대개는 my라는 이름의 파일이 생긴다.

9.1 조건부 인자의 빈 문자열 함정

$ bash t12.sh
flag=""
probe "$flag" other        ->  got 2 arg(s)
probe ${flag:+"$flag"} other  ->  got 1 arg(s)

"$flag"는 값이 비어 있어도 빈 인자 하나를 만든다. 인자를 아예 넘기지 않으려면 ${flag:+"$flag"}처럼 값이 있을 때만 펼쳐지는 확장을 쓰거나, 애초에 배열에 조건부로 추가하는 편이 읽기 쉽다.

args=()
[ -n "$flag" ] && args+=("$flag")
cmd "${args[@]}" other

9.2 붙임표로 시작하는 이름과 종결자

$ ls -1
-rf
annual report.pdf
keep me.txt

$ ls -1 -rf          # -rf 를 옵션으로 읽는다
.
..

$ ls -1 -- -rf       # -- 뒤는 전부 파일 이름
-rf

이름이 붙임표로 시작하는 파일은 명령이 옵션으로 읽는다. 이건 따옴표로 막을 수 없다. 따옴표는 단어가 쪼개지는 것을 막을 뿐이고, 쪼개지지 않은 한 단어가 옵션처럼 생겼다는 사실은 그대로 남는다. 위 실행에서 ls -1 -rf는 -r과 -f 옵션으로 해석되어 파일 대신 현재 디렉터리 목록을 냈다.

  • 해결은 -- 종결자다. 그 뒤의 모든 인자는 옵션이 아닌 것으로 취급된다
  • rm -- "$file", mv -- "$src" "$dst"처럼 되돌릴 수 없는 명령에는 습관적으로 붙인다
  • 다른 방법은 경로를 ./로 시작하게 만드는 것이다. ./-rf는 더 이상 붙임표로 시작하지 않는다
  • find가 내는 경로가 ./로 시작하는 것이 이 때문에 편리하다. 7절 출력의 [./-rf]가 그 예다
  • --를 지원하지 않는 명령도 있다. 그런 경우에는 ./ 방식이 유일한 대안이다
  • 사용자 입력을 그대로 명령에 넘기는 자리라면 종결자는 선택이 아니라 필수로 본다

10. 배열이 없는 셸에서도 인자는 안전하게 넘길 수 있다

셔뱅이 #!/bin/sh인 스크립트가 배포 환경에서 dash로 실행되는 일은 흔하다. 개발 장비에서 /bin/sh가 bash로 연결돼 있으면 이 차이가 안 보인다.

$ dash -c 'arr=(a b c); echo "$arr"'
dash: 1: Syntax error: "(" unexpected

배열 문법 자체가 없다. 그런데 위치 인자는 있고, 인용 규칙도 bash와 같다.

$ dash tp.sh
--- "$@" in POSIX sh ---
  count=3
  [annual report.pdf]
  [q3 data.csv]
  [plain.txt]
--- $@ in POSIX sh ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]
--- "$*" in POSIX sh ---
  count=1
  [annual report.pdf q3 data.csv plain.txt]

bash와 정확히 같은 결과다. 따라서 배열이 없어도 목록 하나는 안전하게 다룰 수 있다. 그 목록을 위치 인자에 담고 "$@"로 펼치면 된다.

set -- "annual report.pdf" "q3 data.csv"
set -- "$@" "새로 추가한 파일.txt"     # 뒤에 붙이기
for f in "$@"; do
    echo "처리: [$f]"
done
  • set -- "$@" "새 항목"이 배열 뒤에 붙이기에 해당한다. 원소를 하나씩 쌓아 갈 수 있다
  • $#이 원소 개수를 준다. ${#arr[@]}와 같은 역할이다
  • shift로 앞에서부터 하나씩 꺼낼 수 있다. 대기열처럼 쓰는 패턴이다
  • 목록이 두 개 이상 필요하면 이 방법으로는 한계가 있다. 그때가 bash를 셔뱅에 명시할 시점이다
  • local은 POSIX에 없는 확장이지만 dash에서 동작하는 것을 확인했다. 다만 표준이 아니므로 모든 sh에서 보장되지는 않는다
  • mapfile·readarray·local -n·declare -p는 전부 bash 확장이다. 이식성이 필요하면 이 넷을 쓰지 않는다
  • 셔뱅을 #!/usr/bin/env bash로 명시하는 것이 배열을 쓰는 스크립트의 최소 조건이다. #!/bin/sh로 두고 배열을 쓰면 언젠가 다른 장비에서 문법 오류로 죽는다

11. 외울 관용구는 여섯 개면 충분하다

지금까지 나온 것을 안전한 형태와 위험한 형태로 짝지어 정리한다.

하려는 일위험한 형태안전한 형태무엇이 달라지나
인자를 그대로 넘기기cmd $@cmd "$@"공백이 든 인자가 쪼개지지 않는다
배열 펼치기cmd ${arr[@]}cmd "${arr[@]}"원소 수가 그대로 유지된다
명령 출력을 목록으로arr=($(cmd))mapfile -t arr < <(cmd)줄 단위로 끊어 공백과 글로브를 통과시키지 않는다
파일 목록 순회for f in $(find .)while IFS= read -r -d '' f; ... < <(find . -print0)공백·개행이 든 이름을 그대로 받는다

삭제·이동 대상 지정rm $filesrm -- "${files[@]}"분리·글로빙이 막히고 붙임표 이름도 안전하다

11.1 체크리스트

  • 확장에는 기본적으로 큰따옴표를 붙인다. 떼는 것이 예외이고, 뗄 때는 이유를 주석으로 남긴다
  • 목록은 문자열이 아니라 배열에 담는다. 문자열에 담는 순간 경계 정보가 사라진다
  • 배열 확장은 "${arr[@]}" 하나만 쓴다. 별표 형태는 로그 출력용으로만 쓴다
  • 명령 출력을 배열로 만들 때는 mapfile -t를 쓴다. 괄호 안 명령 치환은 쓰지 않는다
  • 파일명이 대상이면 셸의 글로브를 직접 쓴다. ls 출력을 파싱하지 않는다
  • 삭제·이동·복사 명령에는 -- 종결자를 붙인다
  • 로직을 고쳤으면 삭제 줄을 echo로 바꿔 한 번 돌려 대상 목록을 눈으로 본다
  • 테스트 데이터에 공백이 든 이름을 반드시 하나 넣는다. 이 글의 모든 결함이 그 하나로 드러났다
  • 가능하면 원소가 최소 두 개인 데이터로 시험한다. 하나짜리로는 $arr 실수가 드러나지 않는다
  • IFS를 바꿔야 하면 IFS=, read ...처럼 명령 앞에 붙여 그 명령에만 적용한다
  • 파일을 한 줄씩 읽을 때는 while IFS= read -r line 형태를 그대로 쓴다
  • 배열을 쓰는 스크립트의 셔뱅은 #!/usr/bin/env bash로 명시한다
  • 배열이 이상하면 declare -p로 인덱스까지 찍어 본다. 추측보다 빠르다
  • 정적 검사기를 붙이면 이 글의 실수 대부분이 커밋 전에 걸린다. 미인용 확장은 대표적인 검출 항목이다

12. 확인하지 못한 것

실행으로 검증하지 못하고 문서 근거로만 쓴 항목을 한자리에 모은다.

  • bash 4.4 미만의 set -u 동작. 빈 배열을 "${arr[@]}"로 펼칠 때 오류가 났다는 것은 변경 이력에 근거한 서술이고, 이 환경에 구버전 bash가 없어 재현하지 못했다. 6.1절의 방어 관용구를 권하는 근거도 그 문서다
  • zsh와 ksh의 배열 동작. zsh는 미인용 확장에서 단어 분리를 하지 않는 등 규칙 자체가 다르지만, 실행 가능한 환경이 아니어서 확인하지 못했다. 이 글의 결론을 zsh에 그대로 적용하면 안 된다
  • busybox ash. 최소 컨테이너 이미지에서 흔한 셸인데 확인하지 못했다. 10절의 POSIX 결론이 여기서도 성립하는지는 배포 대상에서 한 번 돌려 보는 편이 확실하다
  • 리눅스 glibc 환경. 실행 환경은 x86_64-pc-msys용 bash 5.2.37과 같은 환경의 dash다. 인용과 분리 규칙은 파일시스템과 무관한 셸 내부 동작이라 차이가 날 여지가 적지만, 파일명 관련 예제는 대상 환경에서 재현해 보는 편이 낫다
  • 매우 긴 배열의 한계. 인자 개수와 총 길이에는 커널 쪽 상한이 있다. 그 경계에서 "${arr[@]}"가 어떻게 실패하는지는 측정하지 않았다
  • 연관 배열의 순회 순서. declare -A로 만든 배열의 키 순서는 정해져 있지 않다고 알려져 있으나 이 글에서 실행으로 다루지 않았다
  • 로케일에 따른 글로브 문자 범위. [a-z] 같은 범위 패턴이 로케일에 따라 다르게 동작하는 문제는 이 글의 범위 밖이고 확인하지 않았다

FAQ

Q1. 그냥 모든 확장에 따옴표를 붙이면 되나?

거의 그렇다. 실무에서 따옴표를 빼야 하는 자리는 드물다. 빼야 하는 경우는 의도적으로 한 문자열을 여러 인자로 쪼개고 싶을 때인데, 그 상황이라면 애초에 배열을 쓰는 편이 낫다. 다만 몇 군데는 따옴표가 없어도 안전하다. 대입문 우변 x=$y, [[ ]] 안쪽, case의 대상어가 그렇다. 이 자리들은 단어 분리가 일어나지 않도록 셸이 보장한다. 그래도 일관되게 붙이는 편을 권한다. 예외를 기억하는 비용이 따옴표 두 개를 더 치는 비용보다 크다. 그리고 코드 리뷰에서 「여기는 안전하니 괜찮다」를 매번 검증하는 것보다 「전부 붙어 있다」를 확인하는 쪽이 빠르다.

Q2. "$*"는 언제 쓰나?

사람이 읽을 문자열 하나를 만들 때다. 로그에 「이 명령이 이런 인자로 실행됐다」를 한 줄로 남기는 자리가 대표적이다. 실행해 확인하면 "$*"는 항상 정확히 한 단어를 만들고, 원소 사이는 IFS의 첫 글자로 붙는다. 반대로 인자를 다른 명령에 전달하는 자리에서는 절대 쓰지 않는다. 세 개의 인자를 넘겼는데 받는 쪽에서는 인자 하나로 도착한다. 한 가지 더 주의할 점이 있다. 로그용으로 쓰더라도 원본 인자에 공백이 있었는지 없었는지가 합쳐진 문자열에서는 구분되지 않는다. 인자 경계까지 정확히 남기고 싶으면 printf '[%s] ' "$@"처럼 각 인자를 감싸 출력하는 편이 낫다.

Q3. 배열 대입에 따옴표를 붙일 수 없다는 게 무슨 뜻인가?

arr=($(cmd))에서 괄호 전체를 따옴표로 감쌀 방법이 없다는 뜻이다. arr="($(cmd))"로 쓰면 배열이 아니라 괄호가 든 문자열이 되고, arr=("$(cmd)")로 쓰면 명령 출력 전체가 원소 하나가 된다. 배열 대입의 괄호 안은 구조적으로 단어 분리를 통과하는 자리다. 그래서 이 구문 자체를 쓰지 않는 것이 해결책이다. 줄 목록이면 mapfile -t, 파일 목록이면 arr=(*)처럼 글로브를 직접 쓴다. 예외적으로 안전한 경우도 있다. 출력이 공백 없는 토큰뿐임이 확실하고 글로브 문자가 섞일 여지가 없다면 문제가 없다. 다만 그 확신이 나중에 깨지는 것이 사고의 전형이다.

Q4. set -f를 스크립트 전체에 켜 두면 안 되나?

글로빙만 끄고 단어 분리는 남기 때문에 절반의 해결이다. 공백이 든 파일명 문제는 그대로 남는다. 게다가 정작 글로브가 필요한 자리, 예를 들어 for f in *.log 같은 줄이 동작하지 않게 된다. 실행해 확인한 결과 set -f 상태에서 *.txt는 패턴 문자 그대로 한 단어로 남았다. 쓸 자리가 아주 없는 것은 아니다. 남의 코드를 당장 고칠 수 없는데 글로빙 사고만 막아야 하는 상황, 또는 사용자 입력을 잠깐 다루는 짧은 구간에서 set -f를 켜고 끝나면 set +f로 되돌리는 식이면 쓸 만하다. 근본적인 해결은 따옴표와 배열이다.

Q5. 파일명에 개행이 들어갈 일이 실제로 있나?

있다. 리눅스 파일시스템에서 파일명에 넣을 수 없는 문자는 널 문자와 슬래시 둘뿐이고, 개행은 금지 목록에 없다. 사용자가 올린 압축 파일을 풀거나 다른 시스템에서 옮겨 온 데이터를 다루는 코드라면 실제로 만날 수 있다. 확인해 보면 개행이 든 원소는 따옴표 없는 확장에서 두 개로 갈라진다. 개행이 기본 IFS에 든 세 글자 중 하나이기 때문이다. 감당하려면 구분자를 널 문자로 바꾸는 수밖에 없다. find -print0로 목록을 만들고 read -d '' 또는 mapfile -d ''로 받는다. 널 문자가 파일명에 들어갈 수 없는 유일한 문자라서 구분자로 쓸 수 있는 유일한 선택이 된다.

결론: 오늘 바꿀 세 가지

첫째, 목록을 문자열에 담는 것을 그만둔다. 문자열에 파일 이름 여러 개를 넣는 순간 경계 정보가 사라지고, 그 뒤로는 셸이 IFS로 추측해서 복원한다. 추측이 틀리는 순간이 사고다. 목록은 배열에 담고 "${arr[@]}"로 펼친다. 배열이 없는 셸이면 위치 인자에 담고 "$@"로 펼친다. 확인한 결과 이 두 형태만 원래 개수를 지켰다.

둘째, 명령 출력을 배열로 만들 때 괄호 안 명령 치환을 쓰지 않는다. 파일 두 개가 든 디렉터리에서 arr=($(ls))는 원소 세 개짜리 배열을 만들었고 mapfile -t는 정확히 두 개를 만들었다. 대상이 파일명이라면 arr=(*)처럼 셸의 글로브를 직접 쓰는 것이 더 낫다. 파싱 단계 자체가 없어지기 때문이다.

셋째, 삭제·이동 명령에 --를 붙이고, 로직을 고쳤으면 echo로 한 번 돌려 본다. 이름이 붙임표로 시작하는 파일은 따옴표로 막을 수 없고, 실제로 ls -1 -rf가 파일 대신 옵션으로 읽는 것을 확인했다. 삭제는 되돌릴 수 없다. 대상 목록을 눈으로 확인하는 데 드는 시간은 몇 초다.

마지막으로 하나. 이 글의 모든 결함은 테스트 데이터에 공백이 든 이름 하나를 넣는 것만으로 전부 드러났다. 다음에 파일 목록을 다루는 코드를 만들면 touch "annual report.pdf" 한 줄을 테스트에 추가해 보면 된다. 지금 잘 도는 것처럼 보이는 코드가 어디서 무너지는지 그 자리에서 알 수 있다.
