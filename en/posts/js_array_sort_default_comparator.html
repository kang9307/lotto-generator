Introduction - after sorting, 10 comes before 9

In JavaScript, calling sort() on an array of numbers without a comparator lines the numbers up by a criterion other than numeric size. The best-known shape is [1, 10, 9, 2] coming out as [1, 10, 2, 9]. This behavior is a definition rather than a bug, and once the definition is known, how to write a comparator, where each kind of value goes and what a wrongly written comparator produces all connect in one line.

The axis here is the default comparator of sort and writing comparators. The problem of Korean text and locale changing the sort order is covered tool by tool in Why Korean sorting differs from expectations, and array methods in general, with a one-line note on the numeric trap of sort, are in JavaScript Basic Syntax. Here the values a comparator receives, the values it has to return and the inputs that break it are checked one by one with output.

The questions covered are the following.

  • By what criterion does the default comparator compare numbers?
  • How does UTF-16 code unit order, the basis of string comparison, differ from code point order?
  • Where do undefined, empty slots, null and NaN go, and does the comparator receive them?
  • What must a comparator return, and what do boolean and inconsistent comparators produce?
  • Is stable sorting guaranteed by the specification, and which comparator breaks it?
  • Where do toSorted, localeCompare and Intl.Collator take the place of sort with a hand-written comparator?

The default comparator compares strings

The MDN documentation of Array.prototype.sort defines the default order as follows: the default sort order is ascending, built upon converting the elements into strings, then comparing their sequences of UTF-16 code unit values. Another sentence says that if compareFn is not supplied, all non-undefined array elements are sorted by converting them to strings and comparing strings in UTF-16 code units order. The code below prints how this definition shows up for [1, 10, 9, 2], side by side with the same array turned into strings and with a comparator supplied.

console.log('node ' + process.version);
                    const a = [1, 10, 9, 2];
                    console.log(a.sort());
                    console.log([1, 10, 9, 2].map(String));
                    console.log(['1', '10', '9', '2'].sort());
                    console.log('10' < '9', 10 < 9);
                    console.log([1, 10, 9, 2].sort((x, y) => x - y));

                    [ '1', '10', '9', '2' ]
                    [ '1', '10', '2', '9' ]

The first sort gives [1, 10, 2, 9]. The same array as strings is '1', '10', '9', '2', and sorting the string array gives '1', '10', '2', '9', the same order as the numeric array result. The string '10' comes before '9' because its first character '1' (0x31) is smaller than '9' (0x39). The comparison on the second to last line shows this directly: the string comparison '10' < '9' is true and the numeric comparison 10 < 9 is false. With the comparator (x, y) => x - y the result is [1, 2, 9, 10].

  • The default sort works on the string representation of a value, not on the value. The numbers 10 and 9 are not compared; '10' and '9' are.
  • If the array has only one-digit numbers the string order and the numeric order coincide, and a test passes. The moment two-digit numbers mix in, they diverge.
  • The comparator (x, y) => x - y subtracts the values themselves and signals the order by the sign. It does not change the definition; it changes the basis of comparison from strings to numbers.

String comparison runs in UTF-16 code unit order

Comparing strings is, by definition, comparison in units of code units. Most characters are one code unit, but characters above U+FFFF (emoji and others) are surrogate pairs of two code units. This difference creates cases where the default sort and code point order give different results. The code below mixes the emoji U+1F600 and the full-width character U+FF21 with ordinary letters and compares the default sort with a comparator based on code points.

const words = ['\u{1F600}', 'Ａ', 'z', 'Z', 'a'];
                    const hex = w => 'U+' + w.codePointAt(0).toString(16).toUpperCase();
                    console.log('default      :', [...words].sort().map(hex).join(' '));
                    console.log('code point   :', [...words].sort((x, y) => x.codePointAt(0) - y.codePointAt(0)).map(hex).join(' '));
                    console.log('first unit of U+1F600 = 0x' + words[0].charCodeAt(0).toString(16).toUpperCase() + ', of U+FF21 = 0x' + words[1].charCodeAt(0).toString(16).toUpperCase());
default      : U+5A U+61 U+7A U+1F600 U+FF21
                    code point   : U+5A U+61 U+7A U+FF21 U+1F600
                    first unit of U+1F600 = 0xD83D, of U+FF21 = 0xFF21

The default sort gives Z, a, z, U+1F600, U+FF21 and the code point order gives Z, a, z, U+FF21, U+1F600. The first code unit of the emoji is 0xD83D and that of the full-width A is 0xFF21, so in code unit order the emoji comes first. By code point 0xFF21 is smaller than 0x1F600, so it is the other way round. That the uppercase Z (0x5A) comes before the lowercase a (0x61) follows from the same criterion. With only ordinary alphanumerics this difference is invisible, so when emoji or supplementary-plane characters arrive, the sort order can part from intuition.

Where undefined, empty slots, null and NaN go

MDN says that all undefined elements are sorted to the end of the array, and for empty slots that sort() preserves empty slots: if the source array is sparse, the empty slots are moved to the end of the array and always come after all the undefined. How these two sentences meet the comparator shows up when the arguments the comparator received are recorded.

  • The first line is [1, 2, 3, undefined, empty slot]. The length stays 5 and index 4 remained an empty slot. It matches the MDN sentences: undefined first, the empty slot last.
  • The calls recorded by the comparator are number pairs only, and no call had undefined as an argument. The comparator does not receive undefined or empty slots.
  • With the descending comparator (x, y) => y - x, undefined also stayed at the end. The sign of the comparator cannot move undefined.
  • The default sort of [z, undefined, a] is a, z, undefined. String(undefined) is the string undefined, which is smaller than z, yet it was placed last, so undefined is not compared as a string and goes last under a separate rule.
  • Unlike undefined, null and NaN are turned into the strings null and NaN and take their place among other strings. In the default sort result NaN is after 3 and before a, and null is after a.

A comparator is a function that returns a negative, zero or positive number

MDN says a comparator should return a number: a negative value indicates that a should come before b, a positive value that a should come after b, and zero or NaN that a and b are considered equal. More formally, it lists properties the comparator is expected to have: pure, stable in its result for the same pair, reflexive (compareFn(a, a) === 0), anti-symmetric (compareFn(a, b) and compareFn(b, a) must both be 0 or have opposite signs) and transitive. The code below applies a correct comparator, a comparator returning booleans and comparators returning constants to the same array, and counts on a thousand pseudo-random numbers whether the sort took place.

The boolean result in this Node.js is a value from this engine and is not asserted to be the same in other engines.

Inputs that break a - b - missing keys, strings and BigInt

The comparator a - b yields a correct sign only between numbers. When a value is missing or not a number, the subtraction becomes NaN, and MDN writes that a NaN returned by the comparator means equal, like 0. MDN also states that the comparator must give consistent comparison results. The following code shows what a - b gives for objects with a missing key, for strings and for BigInt.

  • With an object lacking the p key, the output for this input is [4, none, 1, 2, 3]. The MDN sentence above and the output are set side by side, and this output does not separate a causal link between them. There is neither an exception nor a warning.
  • undefined - 1 is NaN. The NaN true on the second line is the evidence, and MDN writes that a NaN return value of the comparator means equal.
  • Using a - b on the strings [b, c, a] leaves the order as [b, c, a], because b - c is also NaN. Strings need a < b ? -1 : a > b ? 1 : 0.
  • With BigInt, a - b returns a BigInt, sort cannot convert it to a number and a TypeError (Cannot convert a BigInt value to a number) occurs. This is the one case that does not fail silently but surfaces at once.

Stable sorting and ties

MDN says that since version 10 (ECMAScript 2019) the specification dictates that Array.prototype.sort is stable. Stability is the property that elements the comparator judges equal keep their input order. The code below checks, for 1000 objects with keys 0 to 4 and for each comparator, whether the sort took place and whether the input order of ties was kept. The last line is the two-pass sort: first by a secondary key, then again by the primary key.

const make = () => Array.from({ length: 1000 }, (_, i) => ({ k: (i * 7919) % 5, i }));
                    const isStable = arr => arr.every((v, j) => j === 0 || arr[j - 1].k !== v.k || arr[j - 1].i < v.i);
                    const sorted = arr => arr.every((v, j) => j === 0 || arr[j - 1].k <= v.k);
                    const good = make().sort((x, y) => x.k - y.k);
                    console.log('k-only comparator : sorted', sorted(good), '| ties keep input order', isStable(good));
                    const tie1 = make().sort((x, y) => (x.k < y.k ? -1 : 1));
                    console.log('tie returns 1     : sorted', sorted(tie1), '| ties keep input order', isStable(tie1));
                    const tie2 = make().sort((x, y) => (x.k > y.k ? 1 : -1));
                    console.log('tie returns -1    : sorted', sorted(tie2), '| ties keep input order', isStable(tie2));
                    const two = make().sort((x, y) => x.i - y.i).sort((x, y) => x.k - y.k);
                    console.log('two passes        : sorted', sorted(two), '| ties keep input order', isStable(two));
k-only comparator : sorted true | ties keep input order true
                    tie returns 1     : sorted true | ties keep input order true
                    tie returns -1    : sorted true | ties keep input order false
                    two passes        : sorted true | ties keep input order true
  • The sound comparator that returns 0 on ties (x.k - y.k) sorted the array and kept the input order of ties. This is a result obtained on an input of 1000 elements.
  • The comparator returning -1 on ties sorted the array on this input but did not keep the input order of ties (false in the output). It returns -1 in both orders for the same pair, so it does not satisfy the anti-symmetry condition MDN lists. Whether the result is due to that violation cannot be separated by this experiment. The comparator returning 1 on ties in the next item also fails the reflexivity condition, yet kept the order.
  • The comparator returning 1 on ties kept the tie order in this Node.js. The same reflexivity violation gave a different result. Whether that difference comes from how the engine passes the arguments cannot be settled by this output, and it is not read as a guarantee.
  • The two-pass sort on the last line shows only that on this input the result was sorted and the tie order was kept (both values true). The input is already in i order, so the first pass changes nothing, and this line is not used as evidence of stability. The experiment that checked stability is the 1000-element one above.

sort changes the original and toSorted returns a copy

MDN says sort() sorts the array in place and returns a reference to the same array, and that toSorted() should be used to sort without mutating the original. The code below checks the return relationship of the two methods on this Node.js.

const a = [3, 1, 2];
                    const b = a.sort();
                    console.log('sort():     same array', b === a, a);
                    const c = [3, 1, 2];
                    const d = c.toSorted();
                    console.log('toSorted(): same array', d === c, 'original', c, 'result', d);
                    console.log(typeof Array.prototype.toSorted);
sort():     same array true [ 1, 2, 3 ]
                    toSorted(): same array false original [ 3, 1, 2 ] result [ 1, 2, 3 ]
                    function

The return value of sort() is the same array as the original (true) and the original became [1, 2, 3]. The return value of toSorted() is a different array (false); the original stays [3, 1, 2] and the result is [1, 2, 3]. The last line confirms that Array.prototype.toSorted is a function in this Node.js. Where the sorted result is written into shared state (an immutable array in a state management library, an array already drawn on screen), the copy-returning method prevents unintended changes. The rules for the comparator are the same for both methods.

When numbers and strings are mixed

Real data sometimes arrives with numbers and number-like strings mixed. The default sort compares everything as strings, and a - b gives NaN for values that cannot be turned into numbers. A comparator that first compares a rank by type is set up and the results are placed side by side. The last line is the result of using a - b on an array of number-like strings only.

const m = [10, '9', 1, 'a', 2, 'B'];
                    console.log('default      ', m.slice().sort());
                    console.log('a - b        ', m.slice().sort((x, y) => x - y));
                    const rank = v => (typeof v === 'number' ? 0 : 1);
                    const mixedCmp = (x, y) => rank(x) !== rank(y) ? rank(x) - rank(y)
                      : (x < y ? -1 : x > y ? 1 : 0);
                    console.log('typed cmp    ', m.slice().sort(mixedCmp));
                    console.log('numeric strs ', ['10', '9', '1'].sort((x, y) => x - y));
default       [ 1, 10, 2, '9', 'B', 'a' ]
                    a - b         [ 1, 2, '9', 10, 'a', 'B' ]
                    typed cmp     [ 1, 2, 10, '9', 'B', 'a' ]
                    numeric strs  [ '1', '9', '10' ]
  • The default sort gives 1, 10, 2, 9, B, a. The string order continues in which the number 10 comes before the number 2 and right after the number 1.
  • a - b sorts the numbers among themselves, but the string '9' sits between numbers (between 2 and 10) and 'a' and 'B' remain at the end in input order. When values that do not turn into numbers are mixed in, the result is sorted only partially.
  • The type-rank comparator gives 1, 2, 10, 9, B, a: numbers first in numeric order and strings after them in code unit order. It is the result of stating the rule for mixed input in the comparator.
  • With number-like strings only, a - b converts the strings to numbers and subtracts, so they sort as '1', '9', '10'. The sort is right here, but the elements remain strings.

Korean and locale-aware sorting is solved with a comparator

When code unit order differs from the order people expect in string sorting, the comparator uses localeCompare or the compare function of Intl.Collator. The same list of strings was sorted by default sort, localeCompare, Intl.Collator and the numeric option in turn. The detailed tool-by-tool comparison of collation rules is covered in the Korean sorting article.

const names = ['나', '다', '가', 'Z', 'a', 'B', 'ㄱ'];
                    console.log('default       ', [...names].sort().join(' '));
                    console.log('localeCompare ', [...names].sort((x, y) => x.localeCompare(y, 'ko')).join(' '));
                    const col = new Intl.Collator('ko');
                    console.log('Intl.Collator ', [...names].sort(col.compare).join(' '));
                    const files = ['파일10', '파일2', '파일1'];
                    console.log('default       ', [...files].sort().join(' '));
                    console.log('numeric true  ', [...files].sort(new Intl.Collator('ko', { numeric: true }).compare).join(' '));
default        B Z a ㄱ 가 나 다
                    localeCompare  ㄱ 가 나 다 a B Z
                    Intl.Collator  ㄱ 가 나 다 a B Z
                    default        파일1 파일10 파일2
                    numeric true   파일1 파일2 파일10

The default sort follows code unit order: uppercase B and Z, lowercase a, the Hangul compatibility jamo ㄱ and then the precomposed syllables 가, 나, 다. localeCompare('ko') and Intl.Collator('ko') gave the same result in this Node.js (ㄱ, 가, 나, 다, a, B, Z). That Hangul comes before Latin letters in this order is a value that depends on the ICU data of this environment. In the second list the default sort gives 파일1, 파일10, 파일2, and turning on the numeric option of Collator gives 파일1, 파일2, 파일10. That one Collator is created once and its compare reused was covered, with performance measurements, in the Korean sorting article above.

  • Return exactly 0 on ties. A comparator returning 1 or -1 violates reflexivity.
  • Do not return a boolean. The return value of a comparator is a number, and true and false become 1 and 0 with no negative value.
  • The comparator does not receive undefined or empty slots, so their position cannot be decided inside the comparator. To avoid placing them at the end, fill the values before sorting or use a substitute key.
  • If the original must be kept, use toSorted, or make a copy and then sort it.
  • After changing a comparator, check it with test data that contains mixed numbers and strings, missing keys and ties. With five-element inputs alone, even a boolean comparator can pass by chance.

What Could Not Be Verified

  • The results of boolean and inconsistent comparators and the order of comparator calls on engines other than Node.js 22 (browsers, Bun, Deno, other Node.js versions).
  • The internal reason a boolean comparator changed nothing on five inputs. The internal implementation of the sorting algorithm was not examined in this Node.js.
  • Whether the stability of a comparator returning 1 on ties holds for other input sizes and engines.
  • Sorting time and the number of comparator calls on large arrays (hundreds of thousands of elements or more).
  • Differences in mixed Korean and Latin ordering by ICU data version, and the effects of other Collator options such as sensitivity and caseFirst.
  • The default comparison of TypedArray.prototype.sort and how it differs from Array.
