서론: "Redis가 더 빠른데 왜 MySQL로?"라는 역설

개발자라면 거의 본능처럼 외우는 명제가 하나 있습니다. "Redis는 빠르고, 관계형 데이터베이스는 느리다." 인메모리 키-값 저장소인 Redis는 디스크를 거치는 데이터베이스보다 대체로 응답이 빠르고, 그래서 우리는 트래픽이 몰리는 순간 거의 반사적으로 Redis를 떠올립니다. 그런데 세계 최대급 이커머스 인프라를 운영하는 Shopify가 정반대 방향으로 움직였습니다. 2026년 5월 12일 Shopify Engineering 블로그에 실린 글 「We replaced Redis with MySQL for inventory reservations—and it scaled」(Emilie Noel)에 따르면, Shopify는 결제를 처리하는 동안 재고를 잠시 붙잡아 두는 재고 예약(inventory reservations)을 Redis에서 MySQL로 옮겼습니다.

먼저 범위를 정확히 짚어 둡니다. 옮긴 것은 재고 시스템 전체가 아니라 결제 단계의 '예약'입니다. 재고 수량의 원장(inventory ledger)은 원래부터 MySQL에 있었고, 원문은 문제를 "예약과 재고 원장이 서로 다른 두 시스템에 있었다"고 설명합니다. 그럼에도 많은 개발자가 같은 질문을 던졌을 겁니다. "더 빠른 걸 두고 왜 느린 쪽으로 가지?" 이 질문 안에는 '빠른 것이 곧 좋은 것'이라는 가정이 숨어 있습니다. 결론부터 말하면, Shopify의 선택은 후퇴가 아니라 역할의 재정의였습니다.

재고라는 데이터는 조금 특별합니다. 검색 결과가 0.1초 늦게 뜨는 것과, 장바구니에 담은 마지막 한 개가 결제 순간 두 명에게 동시에 팔리는 것은 전혀 다른 차원의 문제입니다. 전자는 사용자가 짜증을 내고 끝이지만, 후자는 주문 취소·사과·고객 신뢰 하락으로 이어집니다. 이 글은 Shopify 원문이 밝힌 사실과 이 글의 해석을 구분해 표시하면서, 캐시와 데이터베이스의 본질적 차이와 한국 이커머스 환경에 던지는 시사점까지 풀어 봅니다.

이 글의 한 줄 요약. Shopify의 결정은 "Redis가 나쁘다"가 아니라 "예약과 재고 원장은 한 트랜잭션 안에 있어야 한다"는 판단입니다. 원문 표현으로는 두 저장소에 걸친 갱신을 "하나의 원자적 단계로 묶을 수 없었다(couldn't be wrapped in a single atomic step)"는 것이 핵심이었고, 처리량은 캐시가 아니라 MySQL 8의 SKIP LOCKED를 쓴 설계와 데이터베이스 연결 사용 정리로 확보했습니다.

1. Shopify 재고 예약의 규모 - 왜 이 결정이 중요한가

이 결정이 흥미로운 이유는 Shopify의 규모 때문입니다. 원문에 따르면 Shopify는 미국 이커머스의 14% 이상을 처리하고(원문: "powers over 14% of U.S. ecommerce"), 2025년 블랙프라이데이에는 입점 상인들의 매출이 정점에서 분당 510만 달러로 사상 최고를 기록했습니다. 정점 분당 매출은 전년보다 11% 늘었습니다. 원문은 "그 모든 거래가 재고를 건드린다"고 적었고, 예약은 재고를 건드리는 모든 결제에서 실행됩니다.

실패는 양쪽 방향으로 일어납니다. 원문이 든 예로, 한쪽으로 틀리면 두 구매자가 같은 마지막 한 개를 사게 되고, 상인은 주문을 취소하고 사과 메일을 보내며 지원 비용을 떠안습니다. 반대쪽으로 틀리면 실제로는 남아 있는 상품을 품절이라고 안내해 상인이 팔 수 있었던 매출을 잃습니다. 원문은 이 규모에서 "어느 쪽 실패든 빠르게 불어난다"고 적었습니다. 그래서 이 규모에서 예약의 데이터 모델을 바꾼다는 것은 단순한 기술 취향이 아니라 결제의 신뢰성을 떠받치는 토대를 다시 까는 작업입니다.

바로 이 점이 우리가 이 사례에 주목해야 하는 이유입니다. 대규모 트래픽을 겪어 본 회사가, 여러 해 동안 잘 돌던 빠른 도구를 핵심 예약의 자리에서 빼냈습니다. 여기에는 '속도보다 중요한 무언가'에 대한 교훈이 담겨 있습니다.

2. Redis가 재고 예약에 쓰이던 이유

먼저 공정하게 짚어야 할 것이 있습니다. 원문에 따르면 이 예약 기능은 여러 해 동안 Redis 위에서 돌았고, 원문은 "Redis는 동시성을 잘 처리했다(Redis handled concurrency fine)"고 적었습니다. 오히려 예전에 MySQL로 옮기려던 시도가 실패했는데, 수량 열 하나를 둔 단일 행으로는 경합을 감당하지 못했기 때문입니다. Redis는 결코 잘못 고른 도구가 아니었습니다.

2.1 압도적인 속도

Redis는 데이터를 메모리에 올려 두기 때문에 디스크 I/O를 거치지 않습니다. 읽기와 쓰기 모두 매우 짧은 지연으로 응답하며, 재고 차감처럼 빈번하게 일어나는 연산에서 이 속도는 매력적입니다. 이는 일반론이며, 원문은 Redis의 지연 수치를 따로 들지 않았습니다.

2.2 원자적 연산

Redis는 DECR, INCR 같은 원자적 카운터 연산을 기본 제공합니다. 원문에 따르면 Shopify의 옛 모델도 품목마다 수량 키를 두고, 예약은 DECR, 해제는 INCR로 처리했습니다. 재고 수량을 하나 줄이는 동작을 단일 명령으로 처리할 수 있어 동시성 제어가 직관적입니다.

2.3 단순한 데이터 모델

'품목 → 남은 수량'은 본질적으로 키-값 구조라 Redis의 데이터 모델과 거의 완벽하게 맞아떨어집니다. 스키마 설계, 조인, 인덱스 고민 없이 곧바로 동작합니다. 초기에는 이 단순함이 개발 속도를 끌어올렸을 것으로 보입니다(이 글의 추정).

요약하면 Redis는 '재고 = 빠르게 증감하는 숫자'라는 시각에서는 거의 이상적인 도구였습니다. 문제는 재고 예약이 그것만이 아니라는 데 있었습니다.

3. Redis 모델의 한계 - 원문이 든 세 가지와 일반론 두 가지

원문이 직접 든 이유는 세 가지입니다. 아래 3.1~3.3이 그것입니다. 3.4~3.5는 원문이 언급하지 않았지만, 인메모리 저장소를 원장처럼 쓸 때 흔히 거론되는 일반적 한계로 이 글의 해석입니다. 어느 것도 Redis의 결함이 아니라 '역할이 다른 도구'를 쓸 때 생기는 구조적 마찰입니다.

3.1 두 시스템 사이의 원자성 공백 (원문의 핵심 이유)

예약은 Redis에, 재고 원장은 MySQL에 있었습니다. 결제가 끝나 재고를 영구 차감하는 '확정(claim)' 단계는 MySQL을 갱신하고 Redis를 정리해야 했는데, 원문은 이 두 작업을 "하나의 원자적 단계로 묶을 수 없었다"고 적었습니다. 순서에 따라 과매도(팔렸지만 원장에서 차감되지 않음) 또는 과소 판매(원장에서는 차감됐는데 여전히 예약된 것으로 표시됨)가 생길 수 있었습니다. 여러 단계를 한 묶음으로 성공·실패시키지 못하는 문제가 두 저장소 사이에서 벌어진 셈입니다.

3.2 다중 로케이션 인식 부재 (원문)

원문에 따르면 Redis 모델은 여러 로케이션(창고·매장)의 재고를 구분하지 못했습니다. Shopify의 요구사항에는 "주문을 이행할 수 있는 로케이션에서만 예약한다"는 조건이 들어 있었습니다. 품목당 수량 키 하나로는 이 조건을 표현하기 어렵습니다.

3.3 별도 클러스터 운영 비용 (원문)

원문은 Redis 모델이 "유지해야 할 별도 클러스터의 운영 비용"을 더했다고 적었습니다. 원문은 이 전환을 통합 데이터베이스 전략(unified database strategy)으로 가는 과정에서 나온 질문, 곧 "MySQL이 같은 규모를 감당할 수 있는가"로 소개합니다. 모든 데이터를 RAM에 올리면 데이터가 커질수록 메모리 비용이 오른다는 점도 일반적으로 거론되지만, 원문은 메모리 비용을 이유로 들지 않았습니다.

3.4 내구성·복제 지연 (일반론 - 원문 언급 없음)

Redis는 인메모리 저장소이고, RDB 스냅샷이나 AOF 로그로 영속성을 보강할 수 있지만 설정에 따라 마지막 저장 이후의 쓰기를 잃을 수 있는 창이 남습니다. 또 복제는 기본적으로 비동기라, 장애 조치 순간 아직 복제되지 않은 쓰기가 사라질 수 있습니다. 재고처럼 한 건의 불일치가 과매도로 이어지는 데이터에서는 부담이 되는 성질입니다. 다만 Shopify 원문은 데이터 유실이나 AOF·복제 문제를 이전 이유로 들지 않았습니다.

3.5 복잡한 쿼리의 부재 (일반론 - 원문 언급 없음)

재고는 단순 숫자가 아닙니다. '특정 창고에서 재고가 임계치 이하인 상품', '지난 24시간 재고 변동 이력' 같은 질의가 끊임없이 필요합니다. Redis는 키-값 구조라 이런 조인·집계·범위 쿼리를 자체적으로 잘 지원하지 못해 애플리케이션 코드에서 메우게 됩니다. 이 역시 일반론이며, 원문이 든 이유는 아닙니다.

4. 왜 MySQL인가 - Shopify가 택한 설계와 관계형 데이터베이스의 강점

원문의 요지는 이렇습니다. 예약을 원장과 같은 MySQL 데이터베이스로 옮기면 모든 것을 ACID 트랜잭션으로 묶어 위와 같은 실패 유형을 "완전히 없앨 수 있다(eliminate these failure modes entirely)". MySQL(InnoDB 엔진)이 제공하는 것은 결국 '데이터를 틀리지 않게 다루는 능력'입니다.

4.1 내구성 - 커밋되면 살아남는다 (일반론)

ACID의 D(Durability)는 한 번 커밋된 트랜잭션은 서버가 죽어도 보존된다는 약속입니다. InnoDB의 리두 로그(redo log)는 디스크에 먼저 기록되어, 충돌 후에도 커밋된 차감을 복구할 수 있습니다. 캐시의 '잃어도 되는 데이터'와 데이터베이스의 '잃으면 안 되는 데이터'를 가르는 차이입니다. 원문은 내구성 관련 설정을 따로 다루지 않았습니다.

4.2 한 단위에 한 행과 SKIP LOCKED - 경합을 줄이는 설계 (원문)

Shopify는 품목당 한 행에 수량 열을 두는 대신, 판매 가능한 단위마다 한 행을 둡니다. 10개가 있는 품목은 10행이고, 3개를 예약하면 한 트랜잭션에서 3행을 골라 옮깁니다. SELECT ... FOR UPDATE SKIP LOCKED로 다른 트랜잭션이 잠근 행은 건너뛰고 비어 있는 다른 행을 가져오므로, 같은 행을 기다리지 않아 경합이 줄어듭니다.

모든 재고를 행으로 만들면 표가 커지므로(원문 예: 10개 로케이션에 5만 개면 50만 행), 품목·로케이션 조합마다 1,000행으로 상한을 둔 풀을 유지하고 보충 프로세스가 원장에서 채웁니다. 1,000은 플래시 세일 중 관측한 품목·로케이션별 최대 예약 속도를 바탕으로 정했습니다. 풀이 비면 예약 경로가 즉시 보충을 시작하고, 잠금으로 한 트랜잭션만 보충하게 해 요청이 한꺼번에 몰리는 것을 막습니다. 원문이 밝힌 기술 결정은 다음 네 가지입니다.

  • 복합 기본 키: 자동 증가 ID를 기본 키로 쓴 첫 시제품에서는 예약마다 행 잠금이 두 개 걸렸습니다. 기본 키를 (shop_id, inventory_item_id, inventory_group_id, id)로 바꿔 행당 잠금을 하나로 줄였습니다.
  • READ COMMITTED: 보충이 필요한 빈 표에서 SELECT ... FOR UPDATE SKIP LOCKED를 실행하자 갭 잠금(supremum 의사 레코드 포함)이 보충을 막고 교착을 부를 수 있었습니다. 이 트랜잭션들의 격리 수준을 MySQL 기본값인 REPEATABLE READ에서 READ COMMITTED로 바꿨습니다.
  • 잠금 순서 통일: 예약은 항상 단위 테이블에서 먼저 DELETE한 뒤 reserved_quantities에 INSERT하고, 확정은 reserved_quantities만 건드리게 해 순환 대기를 없앴습니다.
  • UNION ALL 일괄 조회: 여러 품목이 담긴 장바구니는 예약 쿼리를 UNION ALL로 묶어 한 번의 왕복으로 필요한 단위를 가져왔습니다.

4.3 원자성 - 전부 아니면 전무

원문에 따르면 예약과 원장을 같은 데이터베이스에 두어 예약과 확정 전체에 ACID를 얻었고, "결제는 성공했는데 재고가 확정되지 않는" 경우나 그 반대처럼 Redis 시절에 가능했던 버그 유형을 고쳤습니다. 한 트랜잭션 안에서 어느 한 단계라도 실패하면 전체가 롤백되므로, '재고는 줄었는데 확정은 안 된' 유령 상태가 구조적으로 생기지 않습니다.

4.4 풍부한 쿼리와 무결성 제약 (일반론)

SQL은 조인·집계·범위 조건을 자유롭게 표현합니다. 외래 키, CHECK 제약, 유니크 제약으로 '재고가 음수가 될 수 없다' 같은 규칙을 데이터베이스가 직접 강제할 수 있어, 비즈니스 규칙을 애플리케이션에만 맡기지 않아도 됩니다. 원문이 든 장점은 아니며 관계형 데이터베이스의 일반적 성질입니다.

5. 마이그레이션의 기술적 도전 5가지 - Shopify는 어떻게 했나

옮기는 것이 옳다는 판단과 실제로 옮기는 것은 전혀 다른 문제입니다. 가동 중인 거대 시스템의 핵심 저장소를 바꾸는 일은 비행 중에 엔진을 교체하는 것에 가깝습니다. 아래는 원문이 밝힌 방식입니다.

  • 무중단(Zero-downtime): 원문에 따르면 Shopify는 스위치를 한 번에 바꾸지 않고 '섀도 모드(shadow mode)'로 두 시스템을 병행했습니다. 모든 예약을 Redis와 MySQL 양쪽에 썼고, 이 기간의 진실 원천은 Redis였습니다.
  • 데이터 정합성: 두 시스템이 모두 살아 있었으므로 옮겨야 할 진행 중 예약이 없었습니다. Redis의 예약은 계속 유효했고, MySQL은 자기 상태를 스스로 쌓아 갔습니다. 스냅샷을 떠서 옮기는 방식이 아니었다는 점이 눈여겨볼 대목입니다.
  • 성능 보장: 운영 환경에서 처리량이 목표에 크게 못 미쳤는데, P90 같은 예약 지연은 괜찮았고 CPU도 한계가 아니었습니다. 진짜 병목은 데이터베이스 연결이었습니다. SQL마다 업무 프로세스 태그(/* conn_tag:checkout_completion */)를 달고 ProxySQL 계층에서 호출자별 연결 점유 시간을 쟀더니, 예약이 아닌 결제 경로의 다른 코드가 연결을 오래 잡고 있었습니다. 결제 경로를 정리해 기본(primary) 데이터베이스의 읽기 50%와 트랜잭션 33%를 줄였고, 오래전에 보수적으로 잡힌 InnoDB 스레드 동시성 설정도 여유가 있는 곳에서 올렸습니다. 대규모 플래시 세일 동안 쓰기 노드 CPU는 50% 미만, 읽기 노드 CPU는 16% 미만에 머물렀습니다.
  • 롤백 안전망: 정확성과 성능을 확인한 뒤 진실 원천을 MySQL로 바꿨고, 문제가 생기면 킬 스위치로 Redis로 되돌릴 수 있었습니다. 듀얼 라이트 경로가 계속 살아 있어 Redis가 언제나 모든 예약을 알고 있었기 때문입니다.
  • 검증(Validation): 섀도 모드에서 실제 운영 트래픽으로 MySQL이 올바른 업무 결과를 내는지, 성능 요구를 맞추는지 두 시스템을 나란히 비교했습니다. 전환은 트래픽이 적은 파드부터 파드 단위로 점진적으로 진행해 가장 거래량이 큰 상인까지 넓혀 갔습니다.

6. 성능 트레이드오프 - 속도 vs 정확성

이 사례는 흔히 '속도를 내주고 정확성을 샀다'로 읽히지만, 원문은 조금 다릅니다. Shopify는 MySQL로 옮긴 뒤 2025년 피크 트래픽에서 높은 처리량 목표를 맞췄다고 적었습니다. 단건 응답만 보면 인메모리 저장소가 빠른 경우가 많은 것은 일반론이지만, 재고 예약에서 진짜 질문은 '얼마나 빠른가'보다 '얼마나 틀리지 않는가'입니다.

원문은 이렇게 적었습니다. "이것은 예약을 빠르게 만드는 일이 아니었다. 안전한 이웃으로 만드는 일이었다(It was about making them safe neighbors)." 예약은 장바구니 갱신·결제 처리·주문 생성과 데이터베이스를 공유하므로, 연결을 포화시키거나 잠금을 오래 쥐는 시스템은 그 모두를 위태롭게 합니다. 기준은 다른 모든 작업의 데이터베이스 건강을 해치지 않으면서 처리량을 유지하는 것이었습니다.

여기서부터는 이 글의 해석입니다. 일반적인 대규모 서비스에서는 정확성이 필요한 쓰기는 데이터베이스가 맡고, 잦은 읽기(재고 표시)는 캐시가 맡는 계층 구조가 흔합니다. 다만 Shopify 원문은 MySQL 앞에 Redis 캐시를 두었다고 말하지 않았고, 오히려 "고처리량 상호 배제를 위해 Redis나 Kafka, 별도 조정 계층을 찾고 있다면 기존 데이터베이스로 이미 충분할 수 있다"고 맺었습니다.

재고에서 1밀리초 빠른 응답은 자랑거리지만, 1건의 과매도는 사고입니다. 정확성이 깨지면 속도는 의미를 잃습니다.

결국 이 사례의 균형점은 정확성을 먼저 확보하고, 속도는 행 설계·잠금·연결 사용 같은 주변 정리로 되찾는 것이었습니다. 손해 보는 장사가 아닌 셈입니다.

7. Redis vs MySQL 의사결정 프레임워크

이 사례를 자기 프로젝트에 적용할 때 쓸 수 있는 판단 기준을 표로 정리합니다. 이 표는 이 글의 정리이며 원문에 실린 표가 아닙니다. 핵심 질문은 단 하나입니다. "이 데이터가 틀리거나 사라지면 무슨 일이 벌어지는가?"

표 1. Redis vs MySQL 선택 기준

기준Redis가 적합MySQL이 적합
속도(저지연)읽기 캐시, 세션, 순위표—
내구성—재고, 주문, 결제
일관성—금전 거래, 잔액
복잡한 쿼리—리포팅, 집계, 조인
다중 단계 트랜잭션—주문 처리 파이프라인
휘발 가능 데이터임시 큐, 속도 제한—

대부분의 실무 결론은 'OR'가 아니라 'AND'입니다. 정확성이 필요한 단일 진실 원천은 데이터베이스, 그 앞을 가속하는 캐시는 Redis. 두 도구를 경쟁이 아니라 분업으로 보는 순간 설계가 명확해집니다. 다만 Shopify 사례가 보여 주듯, 진실 원천과 그것을 바꾸는 작업이 서로 다른 저장소에 흩어져 있다면 먼저 한곳으로 모으는 것이 우선입니다.

8. 원문에 나온 다른 사례와 일반 패턴 - 캐시와 영속 저장소 분리

원문에 등장하는 다른 회사는 하나입니다. Shopify는 37signals의 '데이터베이스 기반 부하 분산' 접근에서 영감을 받아 예약을 MySQL 위에 다시 지었다고 밝혔습니다. 그 밖의 기업 사례는 원문에 없으며, 아래는 업계에서 널리 쓰이는 캐시-어사이드(cache-aside)나 라이트-스루(write-through) 같은 일반적인 계층 분리 패턴입니다.

전형적인 구성은 이렇습니다. 데이터의 진실은 관계형 데이터베이스에 있고, 읽기 부하를 줄이기 위해 그 앞에 Redis/Memcached 캐시를 둡니다. 쓰기는 데이터베이스에 먼저 반영하고 캐시를 무효화하거나 갱신합니다. 이 패턴에서는 캐시가 통째로 날아가도 원본 데이터는 데이터베이스에 남고, 캐시가 다시 채워지는 동안 잠깐 느려질 뿐입니다.

'빠른 저장소'와 '믿을 수 있는 저장소'는 다른 역할이며, 성숙한 아키텍처는 둘을 한 도구에 떠넘기지 않습니다. Shopify의 재고 예약 이전은 이 원칙을 가장 민감한 영역에 적용한 사례로 읽힙니다(이 글의 해석). 다만 Shopify는 캐시를 더하는 방식이 아니라, 두 저장소에 나뉘어 있던 예약과 원장을 한 데이터베이스로 합치는 방식으로 이 원칙을 적용했습니다.

9. 개발자가 배우는 5가지 교훈

이 사례에서 이 글이 정리한 실무 교훈은 다음과 같습니다. 3번과 4번은 원문이 직접 적은 교훈입니다.

  1. "빠르다"는 선택 기준이 아니라 하나의 속성일 뿐이다. 데이터의 성격(휘발 가능한가, 정확해야 하는가)이 도구를 먼저 정한다.
  2. 진실 원천과 그것을 바꾸는 작업은 한 트랜잭션 경계 안에 둔다. 예약과 원장이 두 시스템에 나뉘면 어느 한쪽만 갱신되는 틈이 생긴다. 캐시는 사본이지 원본이 아니다.
  3. 병목은 예상한 곳에 없을 수 있다. 원문에 따르면 몇 주 동안 쿼리와 잠금을 최적화했지만, 진짜 한계는 들여다보지도 않던 코드의 연결 사용이었다. CPU는 낮은데 대기가 길면 전체 경로를 계측하라.
  4. 오래된 결정을 다시 검토하라. 원문은 5년 전에는 불가능했던 것(이 작업에 MySQL을 쓰는 것)이 SKIP LOCKED 같은 새 기능으로 가능해질 수 있고, 스레드 한도 같은 경험칙 설정도 워크로드가 바뀌면 다시 확인할 가치가 있다고 적었다.
  5. 마이그레이션은 기술보다 검증이 전부다. Shopify도 섀도 모드의 듀얼 라이트, 나란히 비교, 킬 스위치 롤백, 파드 단위 점진 전환을 갖춘 뒤에야 진실 원천을 옮겼다.

10. 한국 이커머스 환경 적용 - 쿠팡·네이버·11번가의 시사점

이 논의는 글로벌 사례에 그치지 않습니다. 한국은 라이브커머스·타임딜·오픈런 같은 순간 폭발형 트래픽이 잦은 시장입니다. 같은 인기 상품의 마지막 재고를 많은 사람이 동시에 노리는 상황은 국내 대형 쇼핑 플랫폼에서도 충분히 벌어질 수 있습니다. 아래는 이 글의 판단입니다.

이런 환경에서 예약과 원장을 서로 다른 저장소에 나눠 두면, Shopify가 겪은 것과 같은 원자성 공백이 과매도 위험으로 드러납니다. 한국 이커머스 인프라에 주는 시사점은 다음과 같습니다.

  • 타임딜·오픈런 = 극단적 동시성: 순간적으로 같은 행에 쓰기가 몰립니다. 데이터베이스 잠금 전략과 큐잉(주문 대기열)으로 직렬화하거나, Shopify처럼 단위별 행과 SKIP LOCKED로 경합을 흩는 설계가 핵심입니다.
  • 정확한 재고 표시 ≠ 정확한 재고 차감: 화면에 보이는 재고는 캐시로 빠르게, 실제 차감은 데이터베이스 트랜잭션으로 정확하게. 이 둘을 분리해 인지해야 합니다.
  • 환불·정정 비용을 가볍게 보기 어렵다: 빠른 고객 응대에 대한 기대와 플랫폼 평판에 대한 민감도가 높아, 과매도 1건의 무형 비용이 클 수 있습니다. 정확성에 투자할 명분이 충분합니다.
  • 중소 셀러 도구도 같은 원칙: 자체 쇼핑몰을 만드는 한국 개발자라면, 재고를 Redis 카운터로만 관리하려는 유혹을 경계하고 처음부터 데이터베이스를 단일 진실 원천으로 삼는 편이 안전합니다.

11. 위험 - "빠른 게 항상 좋다"는 착각

이 사례가 들춰내는 더 큰 위험은 기술 선택의 심리입니다. 우리는 벤치마크 숫자, 곧 'X가 Y보다 N배 빠르다'는 문장에 쉽게 휘둘립니다. 하지만 벤치마크는 보통 '데이터가 절대 틀리지 않아야 한다'는 조건을 측정하지 않습니다.

속도 우선주의가 위험한 이유는 그 비용이 나중에, 그것도 가장 곤란한 순간에 청구되기 때문입니다. 트래픽이 가장 몰리는 세일 당일, 장애로 노드가 죽는 순간, 두 저장소의 갱신이 엇갈리는 찰나에 불일치가 터집니다. 평소엔 멀쩡하다가 가장 아쉬운 순간에 무너지는 것입니다.

"빠르다"에 매혹되기 전에 물어야 할 질문은 이것입니다. 이 데이터가 사라지거나 틀리면 누가, 얼마를, 어떻게 잃는가?

성숙한 엔지니어링은 빠른 도구를 자랑하는 것이 아니라, 각 데이터의 실패 비용을 정직하게 따져 도구를 배치하는 일입니다. Shopify의 선택은 바로 그 정직한 계산의 결과로 읽힙니다.

12. 결론 + 즉시 적용 가능한 3가지

Shopify가 재고 예약을 Redis에서 MySQL로 옮긴 결정은 'Redis는 틀렸다'는 이야기가 아닙니다. 그것은 '예약과 재고 원장은 한 트랜잭션 안에 있어야 한다'는 판단이었습니다. 그리고 원문은 정확성을 위해 처리량을 포기했다고 말하지 않습니다. 단위별 행과 SKIP LOCKED 설계, 결제 경로의 연결 사용 정리로 목표 처리량을 맞췄다고 말합니다. 정확성은 양보할 수 없는 상수였고, 속도는 설계로 되찾을 수 있는 변수였습니다.

오늘 바로 적용할 수 있는 세 가지로 마무리합니다.

  1. 데이터를 실패 비용으로 분류하라. 사라져도 되는 것은 캐시(Redis), 절대 틀리면 안 되는 것은 데이터베이스(MySQL/PostgreSQL)로. 이 한 줄 기준만으로 대부분의 저장소 결정이 정리됩니다.
  2. 재고·결제·잔액은 트랜잭션 데이터베이스를 단일 진실 원천으로 두고, 그것을 바꾸는 작업도 같은 트랜잭션에 넣어라. 속도가 필요하면 행 설계·잠금·연결 사용부터 점검하고, 캐시는 그다음에 검토합니다.
  3. 저장소를 옮길 땐 섀도 모드의 듀얼 라이트·나란히 비교·킬 스위치 롤백을 먼저 설계하라. 마이그레이션의 성패는 새 기술이 아니라 검증 체계가 가른다는 것을 기억하세요.

다음에 "Redis가 더 빠른데 왜?"라는 질문이 떠오른다면, 한 단계 더 들어가 보시기 바랍니다. 진짜 질문은 속도가 아니라 '이 데이터가 틀리면 무엇이 무너지는가'입니다.

자주 묻는 질문 (FAQ)

Q1. Shopify는 왜 재고 예약을 Redis에서 MySQL로 옮겼나요?

예약은 Redis에, 재고 원장은 MySQL에 있어 결제 확정 때 두 시스템을 하나의 원자적 단계로 갱신할 수 없었고, 순서에 따라 과매도나 과소 판매가 생길 수 있었습니다. 다중 로케이션을 인식하지 못하는 점과 별도 Redis 클러스터의 운영 비용도 이유였습니다. 예약을 원장과 같은 MySQL로 옮겨 ACID 트랜잭션으로 묶었습니다(Shopify Engineering, 2026-05-12).

Q2. Redis는 재고 시스템에 부적합한가요?

Redis가 나쁜 게 아니라 역할이 다릅니다. 원문도 Redis가 동시성을 잘 처리했다고 적었습니다. 다만 진실 원천이 다른 저장소에 있으면 두 곳을 한 번에 바꿀 수 없다는 구조적 한계가 생깁니다. 읽기 캐시·세션·큐처럼 속도가 핵심인 영역에서는 여전히 탁월합니다.

Q3. 언제 Redis 대신 MySQL을 써야 하나요?

데이터가 손실되면 안 되고, 정확해야 하며, 다중 단계 트랜잭션과 복잡한 쿼리가 필요하면 MySQL입니다. 휘발해도 되고 단순 키-값 조회에 극단적 저지연이 핵심이면 Redis가 낫습니다.

Q4. MySQL도 Redis처럼 높은 트래픽을 견딜 수 있나요?

원문에 따르면 Shopify는 단위별 행과 SELECT ... FOR UPDATE SKIP LOCKED, 품목·로케이션당 1,000행 풀, 복합 기본 키, READ COMMITTED, 연결 사용 정리로 2025년 피크 트래픽의 처리량 목표를 맞췄습니다. 일반적으로는 인덱싱·커넥션 풀·읽기 복제본·앞단 캐시도 함께 검토합니다.

Q5. 캐시와 데이터베이스의 차이는 무엇인가요?

데이터베이스는 단일 진실 원천으로 영구 보존·일관성·트랜잭션을 책임지고, 캐시는 빠른 재현을 위한 임시 사본입니다. 캐시가 비면 느려질 뿐이지만, 데이터베이스가 틀리면 비즈니스가 깨집니다.

# Shopify 재고 예약 Redis→MySQL 이전 - 확인표와 설계 점검표

## 1. 이 사례를 인용할 때 확인할 것

| 확인할 것 | 원문 기준 사실 | 흔한 오해 |
|---|---|---|
| 무엇을 옮겼나 | 결제 중 재고 예약(inventory reservations). 재고 원장은 원래 MySQL에 있었다 | 「재고 시스템 전체를 옮겼다」 |
| 왜 옮겼나 | 확정 단계에서 MySQL 갱신과 Redis 정리를 하나의 원자적 단계로 묶을 수 없어 과매도·과소 판매가 가능했다. 다중 로케이션 인식 부재, 별도 클러스터 운영 비용도 이유 | 「Redis가 데이터를 잃어서」(원문에 없음) |
| Redis는 어떻게 됐나 | 전환 중에는 섀도 모드의 듀얼 라이트와 킬 스위치 폴백으로 쓰였다. 이후 캐시로 쓰는지는 원문에 없다 | 「Redis는 캐시로 재배치됐다」 |
| 속도를 포기했나 | 2025년 피크 트래픽에서 높은 처리량 목표를 맞췄다 | 「정확성을 위해 느려졌다」 |
| 병목은 어디였나 | 쿼리나 CPU가 아니라 결제 경로 전체의 데이터베이스 연결 점유 | 「MySQL 쿼리가 느려서」 |
| 규모 수치 | 2025년 블랙프라이데이 정점 분당 510만 달러, 전년 대비 11% 증가, 미국 이커머스의 14% 이상 | 출처 없는 「초당 수십만 건 주문」 |

## 2. 원문의 핵심 수치와 설정

| 항목 | 값 |
|---|---|
| 예약 풀 상한 | 품목·로케이션 조합당 1,000행 |
| 행이 폭증하는 예 | 10개 로케이션에 5만 개면 50만 행 |
| 결제 경로 정리 효과 | 기본(primary) 데이터베이스 읽기 50%, 트랜잭션 33% 감소 |
| 플래시 세일 중 CPU | 쓰기 노드 50% 미만, 읽기 노드 16% 미만 |
| 격리 수준(예약 트랜잭션) | REPEATABLE READ(MySQL 기본값) → READ COMMITTED |
| 기본 키 | `(shop_id, inventory_item_id, inventory_group_id, id)` |
| 핵심 쿼리 방식 | `SELECT ... FOR UPDATE SKIP LOCKED` |

## 3. 재고 예약을 설계하거나 옮길 때 점검표

원문 사례에서 도출한 항목입니다.

- [ ] 예약과 재고 원장이 같은 트랜잭션 경계 안에 있는가
- [ ] 단일 행에 수량 열을 두는 구조라면 동시 차감 경합을 측정해 보았는가
- [ ] SKIP LOCKED를 쓴다면 풀 상한을 관측한 피크 예약 속도로 정했는가
- [ ] 풀이 비었을 때 한 트랜잭션만 보충하게 하는 경로가 있는가
- [ ] 필터 열이 기본 키에 들어가 행당 잠금이 하나인지 잠금 상태를 직접 확인했는가
- [ ] 빈 표 보충 시 갭 잠금이 문제가 되면 해당 트랜잭션의 격리 수준을 검토했는가
- [ ] 예약과 확정이 같은 순서로 테이블을 잠그는가
- [ ] 여러 품목 장바구니의 조회를 한 번의 왕복으로 묶었는가
- [ ] 호출자별 연결 점유 시간을 볼 수 있는가(SQL 주석 태그 + 프록시 집계)
- [ ] 섀도 모드의 듀얼 라이트로 운영 트래픽에서 두 시스템의 결과를 나란히 비교하는가
- [ ] 킬 스위치로 옛 경로로 즉시 되돌릴 수 있는가
- [ ] 트래픽이 적은 단위부터 점진적으로 전환하는가
