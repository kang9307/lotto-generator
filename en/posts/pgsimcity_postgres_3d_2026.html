Making a Database Visible

Where the 3D city metaphor genuinely lowers cognitive load, and where it distorts the information instead

Jul 29, 2026 Tech & IT

Introduction: why a database is so stubbornly invisible

A web server streams logs. A queue has a visible length. A container leaves a restart count behind as a number. A database, by contrast, is stubbornly invisible. It says nothing while it is healthy, and when something goes wrong it appears only as a consequence — response time — long after the fact. The cause lives inside while only the effect is visible outside. That asymmetry is the structural discomfort of running a database.

So the attempt to draw the inside as a picture comes back periodically. Recently a project that renders PostgreSQL internals as a 3D city drew attention. The metaphor is intuitive: buildings rise, traffic moves, cleaning crews make their rounds. But the question this article answers is not whether the city is pretty. It is one question only: when does visualization actually earn its keep, and when does it remain a toy?

Let me fix the yardstick first. Throughout this article, the value of visualization is measured only by how quickly it surfaces an anomaly. Beauty is not value. Every technical claim here was verified on 29 July 2026 against the PostgreSQL official documentation and the project's public repository, and anything that could not be verified was left out. No commercial monitoring product is recommended or compared. Every situational example is a generalized, hypothetical case.

1. Fixing the facts first - that 3D city is not an observability tool

The starting point is PGSimCity. Its public repository is github.com/NikolayS/PGSimCity and the running page is nikolays.github.io/PGSimCity/. The repository describes itself as an explorable 3D city that shows how PostgreSQL actually works. The license is Apache-2.0, the implementation uses three.js and TypeScript, and the build runs on Vite.

The most important fact here is not the visuals but the boundary. The repository documentation states plainly that the project is a model of PostgreSQL, not an emulator, that no PostgreSQL source code runs there, and that the numbers are scaled so a human can watch them. In other words, there is nowhere to enter a connection string. It does not read values from your instance.

That single line sets the direction of this whole article. The project is a textbook, not an instrument panel. And that is not a defect but a design decision. Drawing a real instance means reading values, and the moment you read values a different problem begins: the cost of observation. A later section deals with it separately.

To summarize:

  • What it shows - backend processes, shared buffers, write-ahead logging and checkpoints, the storage hierarchy, cleanup activity, replication and the query execution pipeline, each mapped onto a city structure.
  • Where the values come from - nowhere. They are produced by the model. It does not query real system catalogs or statistics views.
  • Maturity - an actively maintained educational project. The repository states that it has gone through several rounds of accuracy review and that tests run under continuous integration, while acknowledging limits and inviting corrections.
  • Boundary of use - concept learning, onboarding, a shared vocabulary for design discussions. Not usable for state monitoring or alerting.

So leaving it open to watch our database is a misunderstanding. Seeing real state still means querying the statistics views directly. That is what the rest of this article is about.

2. The value of visualization is not beauty but time to detection

Arguments about visualization usually collapse into taste. Avoiding that requires a measurable criterion. In operations there is only one useful one: how quickly the same anomaly is noticed.

By that criterion, visualization pays only when it does one of three things.

  1. Turning comparison into space - instead of reading a hundred numbers, you scan a hundred sizes. Humans rank visually far faster than numerically.
  2. Turning relationships into shape - who blocks whom is a graph by nature. A table hides the chain; a picture shows it at once.
  3. Turning change into motion - the anomaly signal is often the rate of change rather than the static value, and motion carries rate of change directly.

The cases where visualization pays nothing are equally clear. Any judgment that ends at a single threshold is one. If all that matters is whether a value crossed a line, a picture is slower than a number. You are handing to human eyes something an alert should have handled, which makes matters worse rather than better.

3. What you have to look at for an anomaly to become visible

On a single PostgreSQL instance, most anomalies arrive through four channels: bloat, lock waiting, buffer hits, and long-running transactions. Start by mapping which view surfaces which signal.

The column worth staring at is character. Cumulative and instantaneous values must not sit side by side on the same screen. A cumulative counter has been piling up since server start and barely reflects the last few minutes of deterioration. An instantaneous value is a photograph of the moment you asked and vanishes on the next sample. Overlay the two on one chart and the reader misjudges the time axis. This is the first place visualization distorts information.

4. Bloat - what n_dead_tup tells you and what it does not

The most common starting point is the dead row count. The short form looks like this.

SELECT relname,
       n_live_tup,
       n_dead_tup,
       last_autovacuum,
       last_autoanalyze
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC
LIMIT 10;

There is one fact here you have to know. The PostgreSQL documentation defines n_live_tup and n_dead_tup as the estimated number of live rows and the estimated number of dead rows respectively. They are estimates. Not exact counts. Using them to rank tables is therefore sound; drawing a threshold line on the absolute value is precarious.

last_autovacuum is the last time the autovacuum daemon vacuumed the table. In practice the more informative signal is not the size of n_dead_tup but whether that timestamp is still advancing. If dead rows keep accumulating while the last cleanup time has not moved for days, the problem is probably not the cleanup settings but something preventing cleanup from running.

When does automatic cleanup actually trigger

The basic shape of the formula in the documentation is base threshold plus scale factor times the number of tuples. The base is autovacuum_vacuum_threshold, the scale factor is autovacuum_vacuum_scale_factor, and the tuple count comes from pg_class.reltuples. Current documentation adds an upper cap term and takes the smaller of the computed value and that cap as the threshold.

The implication is clear. Because the scale factor multiplies, the larger the table the later cleanup begins. On a hundred-million-row table with default settings, a substantial pile of dead rows must accumulate before the condition is met. That is why cleanup on large tables was always late before the cap term existed, and it remains the reason to set per-table overrides.

VACUUM does not shrink the file

Another expectation that regularly misfires. The documentation states that the standard form of VACUUM removes dead row versions and marks the space available for future reuse, but that it will not return the space to the operating system, except in the special case where one or more pages at the end of a table become entirely free and an exclusive table lock can be easily obtained. So a file size that does not move after a cleanup is normal. The documentation adds that there is not much point in shrinking a table to its minimum with VACUUM FULL if it will just grow again.

This is exactly where you can see where visualization lies. Draw a table as building height and you almost certainly use file size. But file size does not fall after cleanup. So on screen the building stays tall and the viewer reads the cleanup failed. In reality the state is healthy: internal free space has become reusable. The same pixels stand for two different facts. That is the sharpest risk in the city metaphor.

5. Size - which number deserves the name table size

Avoiding the previous trap means splitting the word size first. The functions the documentation defines each count something different.

SELECT pg_size_pretty(pg_relation_size('orders'))       AS main_fork,
       pg_size_pretty(pg_table_size('orders'))          AS table_with_toast,
       pg_size_pretty(pg_indexes_size('orders'))        AS indexes,
       pg_size_pretty(pg_total_relation_size('orders')) AS total;
FunctionWhat it countsCommon misreading
pg_relation_sizeOne specified fork. With a single argument, the main data forkTaken for the whole table size
pg_table_sizeThe table, excluding indexes, including TOAST plus the free space map and visibility mapNobody realizes TOAST is included
pg_indexes_sizeAll indexes attached to the tableIndex bloat is never inspected separately
pg_total_relation_sizeTable plus all indexes plus TOAST. Equal to pg_table_size plus pg_indexes_sizePeople are startled by the largest number

If a metric with the same name reports different numbers on two dashboards, nine times out of ten one side uses pg_relation_size and the other uses pg_total_relation_size. This is the item to check before adding any new visualization tool. Two screens with divergent metric definitions do not help; they manufacture arguments during an incident.

For reference, the units pg_size_pretty uses are powers of two. As the documentation states, 1kB is 1024 bytes. Placed next to a decimal-unit system, the figures will not line up.

6. Estimates and exact values answer different questions

The most frequent accident on an operations screen is reading an estimate as though it were exact. The two are not substitutes; they are tools for different jobs.

-- Estimate: returns instantly. Use for ranking and trend watching
SELECT n_live_tup, n_dead_tup
FROM pg_stat_user_tables
WHERE relname = 'orders';

-- Exact: full scan. Use for reconciliation and verification only
SELECT count(*) FROM orders;

-- Exact bloat ratio: performs a full-table scan
SELECT dead_tuple_percent, free_percent
FROM pgstattuple('orders');

The documentation is unambiguous about pgstattuple: the function always performs a full-table scan and returns an exact count of live and dead tuples, their sizes, and free space. By contrast pgstattuple_approx tries to avoid the full-table scan and returns exact dead tuple statistics along with an approximation of the number and size of live tuples and free space.

So an exact bloat ratio has value, and that value carries a price tag. Wire that function to a dashboard refresh interval against a multi-hundred-gigabyte table and your observability tool becomes a load generator. Privileges are restricted by default too: the documentation grants execute permission to the pg_stat_scan_tables role.

Which table is worstRanking by n_dead_tupEffectively noneReporting an exact figure
What is this table's real bloatpgstattupleFull-table scanPeriodic automatic collection

7. Locks - pg_locks does not tell you who blocks whom

Lock waiting is the area where visualization genuinely pays, because the subject is relationships. But one view does not finish the job.

SELECT a.pid,
       a.state,
       a.wait_event_type,
       pg_blocking_pids(a.pid) AS blocked_by,
       now() - l.waitstart     AS waited,
       left(a.query, 60)       AS query_head
FROM pg_stat_activity a
JOIN pg_locks l ON l.pid = a.pid AND NOT l.granted
ORDER BY l.waitstart;

According to the documentation, a false granted means the process is currently waiting to acquire the lock, which implies that at least one other process is holding or waiting for a conflicting lock mode on the same lockable object. waitstart is the time the wait began, and the documentation warns that it can be null for a very short period after the wait started even though granted is false. Render that null as zero seconds waited on a screen and a wait that just began looks like the least urgent item on the list. The sign of the signal flips.

More importantly, this view alone cannot give you the blocking relationship. The documentation says that while it is possible to obtain information about which processes block which others by joining pg_locks against itself, this is very difficult to get right in detail, and that it is better to use the pg_blocking_pids() function. So if you are going to draw a lock graph, that function is the starting point. A chain assembled by hand-joining the view is dangerous in proportion to how convincing it looks.

This view has its own price as well. The documentation states that locking the regular and/or predicate lock manager could have some impact on database performance if this view is very frequently accessed. You would be creating locks in order to look at locks, so this screen in particular should not run on a short collection interval.

8. Buffers - the value of looking inside shared buffers and its price

What is resident in shared buffers can be inspected with the pg_buffercache extension. Per the documentation the view exposes columns such as bufferid, relfilenode, reldatabase, relblocknumber, isdirty, usagecount and pinning_backends. But understand the scale first. The documentation states that there is one row for each buffer in the shared cache. A large buffer pool means proportionally many rows.

The documentation's account of the cost structure is more nuanced than the common assumption. Because buffer manager locks are not taken to copy the buffer state data that the view will display, accessing the view has less impact on normal buffer activity, but it does not provide a consistent set of results across all buffers. The documentation adds that the information of each buffer is guaranteed to be self-consistent.

In short, the cheapness was purchased by giving up snapshot consistency. A screen built from this view is therefore closer to a blurred photograph of something in motion. Do not draw conclusions from the instantaneous state of an individual block.

If continuous collection is the goal, the documentation offers cheaper alternatives.

-- Summarize all shared buffers in one row
SELECT * FROM pg_buffercache_summary();

-- Aggregate by usage count
SELECT * FROM pg_buffercache_usage_counts();

For both functions the documentation says the view provides similar and more detailed information but these functions are significantly cheaper. It also notes that both likewise do not acquire buffer manager locks, so concurrent activity can lead to minor inaccuracies in the result. Access is restricted by default to superusers and roles with privileges of the pg_monitor role, and may be granted to others with GRANT.

The trap inside the number called hit ratio

SELECT datname, blks_hit, blks_read,
       round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS hit_pct
FROM pg_stat_database
WHERE datname = current_database();

SELECT relname, heap_blks_hit, heap_blks_read
FROM pg_statio_user_tables
ORDER BY heap_blks_read DESC
LIMIT 10;

There are two layers of trap here. First, the documentation's definition of blks_hit states that it only includes hits in the PostgreSQL buffer cache, not the operating system's file system cache. The documentation likewise says of I/O statistics generally that they do not differentiate between data which had to be fetched from disk and that which already resided in the kernel page cache, and advises using these views in combination with operating system utilities. So blks_read is not the same thing as disk reads.

Second, these are cumulative counters. If the server has been up a long time, a sharp deterioration over the last ten minutes will barely move the overall figure. Hit ratio should therefore be read as a difference between samples taken at equal intervals, not as an absolute. Putting a cumulative ratio in the middle of a screen as one big number is the distortion visualization commits most often.

9. Long transactions - the quietest and most expensive anomaly

Of the four channels, this is the one found last, because no metric spikes.

SELECT pid, state, wait_event_type, wait_event,
       now() - xact_start  AS xact_age,
       now() - query_start AS query_age,
       left(query, 60)     AS query_head
FROM pg_stat_activity
WHERE state <> 'idle'
  AND xact_start < now() - interval '5 minutes'
ORDER BY xact_start;

Per the documentation, the values state may take include, besides active and idle, idle in transaction and idle in transaction (aborted). The real trouble in production usually comes from those two states. The query does nothing while the transaction remains open. It burns no CPU and no I/O, so it appears on no resource graph at all.

Yet an open transaction prevents automatic cleanup from removing what it should remove. Discussing transaction ID exhaustion, the documentation tells you to end long-running open transactions and says you can find them by checking pg_stat_activity for rows where age(backend_xid) or age(backend_xmin) is large, and that such transactions should be committed or rolled back.

That is where the causal chain forms. One quiet open transaction leads to cleanup being unable to remove dead rows, which leads to dead rows accumulating, which leads to more pages read for the same result, which leads to a falling buffer hit ratio and slower responses. What the operator sees is the last link; the cause sits at the first.

And this is precisely where visualization earns its value. When cause and effect are scattered across different views with a time lag between them, simply placing the chain side by side on one screen genuinely lowers cognitive load. Conversely, a visualization that cannot stitch the chain together merely adds a screen.

For context, transaction ID exhaustion is a subject that easily frightens people, but the documentation is matter-of-fact about it. Transaction IDs have a limited 32-bit size, and a cluster that runs long enough to pass four billion transactions would see the counter wrap to zero so that transactions in the past suddenly appear to be in the future. To avoid this, every table in every database must be vacuumed at least once every two billion transactions.

10. Observation itself is load - what the documentation actually warns about

This is the most operationally useful section of the article. Looking has value, and value has a price. Without exaggeration, and strictly within what the official documentation states:

SubjectCost or constraint the documentation statesPractical rule
Statistics collection overallCollection of statistics adds some overhead to query execution, so the system can be configured to collect or notDo not switch on every track_* setting reflexively
pg_locksIf the view is very frequently accessed, locking the lock manager could have some impact on performanceDo not run it on a short collection interval

The conditions attached to per-query statistics

SELECT queryid, calls,
       round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2)  AS mean_ms,
       rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

pg_stat_statements is as convenient as it is conditional. The documentation states that the module requires additional shared memory, so it must be added to shared_preload_libraries, which means a server restart is needed to add or remove it. The setting that caps the number of tracked statements can only be set at server start, and when the limit is exceeded the least-executed statements are discarded.

The warning about planning time tracking is more explicit: enabling that parameter may incur a noticeable performance penalty, especially when statements with identical query structure are executed by many concurrent connections which compete to update a small number of entries.

The stability of queryid also bears directly on screen design. The documentation says there are only limited guarantees around the stability of the hash value and that it is not safe to assume it will be stable across major versions, while it can be assumed to be stable between minor releases provided instances run on the same machine architecture and the catalog metadata details match. So a design that treats queryid as a permanent identifier for long-term trend screens will snap at an upgrade. Query texts are kept in an external file, and the documentation notes that if that file grows unmanageably large the texts may be discarded, whereupon existing entries show null query fields while the statistics themselves are preserved.

Finally, a lesser known fact. The documentation states that when a server process is asked to display any of the accumulated statistics, accessed values are cached until the end of its current transaction in the default configuration. So code that repeatedly queries the same statistics view inside a single transaction to observe change may not behave as intended. If a polling script shows values that appear strangely frozen, suspect this behavior first.

11. Where the 3D city metaphor works and where it collapses

Now there is enough material to judge the metaphor itself. Spatial metaphor is not free. A metaphor grants dimensions, and granted dimensions manufacture meaning that was never there.

Where it works

  • A feel for concurrency - that several backends move simultaneously is abstract in prose and immediately obvious in motion.
  • Pipeline ordering - the stages from parsing through rewriting, planning and execution map cleanly onto spatial order. Drawing an ordered thing as order is an honest metaphor.
  • Periodic background work - cleanup and checkpoints are work that recurs on a cycle, which is exactly what looping animation is.
  • Contention for shared resources - a picture of several parties fighting over one spot is unusually strong at explaining locking.
  • Teaching efficiency - for a beginner a moving model replaces several pages of documentation. That the project defines itself as a model fits this exactly.

Where it collapses

  • Height becomes ambiguous - file size, row count, or bloat ratio? As shown, files do not shrink after cleanup, so height mapped to file size makes a healthy state look like a fault.
  • Estimates start to look exact - n_live_tup is an estimate, yet drawn as blocks it looks countable. Pictures have no error bars.
  • Cumulative and instantaneous get mixed - putting a cumulative ratio such as hit rate in the same scene as an instantaneous value such as current waits destroys the time axis.
  • Distance and layout invent meaning - two buildings close together look related. In reality only the sort order put them there.
  • The camera creates statistics - in 3D, what is occluded depends on the viewing angle, and what is hidden becomes nonexistent. That failure mode does not exist in a 2D table.
  • Animation implies causation - two motions joined in time read as cause and effect. The screen actively encourages confusing correlation with causation.
  • Information density is low - a table carries far more values in the same screen area. During investigation, density beats aesthetics.

The practical conclusion is this: 3D for learning, 2D for investigation, numbers and alerts for monitoring. Attempts to force all three into one tool usually fail because each stage demands a different information density and tolerates a different latency.

12. Visualization versus the observability stack you already have

Most teams already have a metrics collector, dashboards and alerts. The question of whether to add another screen on top should be settled by replacement, not by taste.

Cases that justify adding one

  • A question keeps recurring that existing screens cannot answer, especially one where relationships are the substance, such as a blocking chain.
  • Cause and effect are scattered across different views and a human stitches them together mentally every single time.
  • Onboarding and design discussions need a shared vocabulary. For that purpose a model that never reads a real instance is entirely sufficient.

Signals against adoption

  • Metric definitions disagree with the existing dashboard. One side uses pg_relation_size, the other pg_total_relation_size. The moment two screens report different numbers during an incident, the tool has become a source of dispute rather than a tool.
  • Keeping the screen alive forces ever-shorter collection intervals. If you are scraping pg_locks every second for smooth animation, observation is creating the problem.
  • A judgment that an alert would settle is handed to human eyes. Whether a threshold was crossed is not a thing for people to watch.
  • Nobody owns the screen. A screen with no assigned watcher is the same as a screen left switched off.
  • The only argument for adoption is that it looks good. In that case only the maintenance cost remains.
  • It requires widening privileges. Buffer-related functions are restricted by default to superusers and roles with pg_monitor privileges. Softening a privilege boundary for the sake of one screen is a bad trade.

One more thing must be decided before adoption: which decision does this screen change? If there is no answer, the screen is already decoration.

Conclusion: the standard for making something visible

PostgreSQL rendered as a 3D city is a well-made textbook. And the project says so itself: a model rather than an emulator, no real source running, numbers scaled so a human can watch. That honest line-drawing is the project's virtue. Conversely, the screens that set out to render a real instance fail so often because they never draw that line and try to build an instrument panel with a textbook's grammar.

Three things for practitioners to take away.

  1. Fix the metric definitions first. What size means, whether the number is an estimate or exact, whether it is cumulative or instantaneous. A screen without those decisions is more dangerous the prettier it is.
  2. Put observation cost into the design. Do not scrape lock views often, do not wire full-scan functions into periodic collection, use the cheap summary functions for continuous sampling. The documentation already tells you where the expense lies.
  3. Write down which decision the screen changes. If there is no answer, do not build it. Adding one more screen to work an existing dashboard already covers is not improvement but dispersion.

In the end, making something visible is not the act of drawing a picture but the act of deciding what to look at. Once that is decided a single table is often enough, and if it is not decided, you can build a whole 3D city and still see nothing.
