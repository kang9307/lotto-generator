Rust 1.99.0の概要と主要な変更点

2026年10月1日にリリースされたRust 1.99.0は、システムプログラミングおよび外部関数インターフェース（FFI）の境界において長年未解決であった重要な低水準機能を正式に安定化させた。最大の焦点は、C ABI互換の可変長引数（variadic）関数をRustコード内部で直接実装可能になった点である。これまでRust開発者がCランタイム向けの可変長引数コールバックやログ処理関数を実装する際には、プラットフォーム固有のインラインアセンブリやC言語ラッパーに依存する必要があった。今回の安定化により、これらの技術的負債がコンパイラ標準の機能として解消された。

さらに、生ポインタ（raw pointer）のメモリ配置を安全に取得するレイアウト検証API群が標準ライブラリに正式導入された。コンパイル時にサイズが決定しないunsized型（!Sized）に対する安全性要件が明確化され、メモリアロケータやシリアライザの実装における安全性が大幅に向上した。これに加え、Box::leakに関する公式ドキュメントの指針改定や、コレクション・反復子の機能拡張など、実務に直結する変更が多数盛り込まれている。

低水準メモリ安全性や言語境界に関する議論は、メモリ安全性絶対主義者たちとRustの立ち位置および多言語連携を扱ったRust移行アーキテクチャガイドでも確認できる。本稿では1.99.0で確定した事実に基づき、その技術的意義を構造化して解説する。

  • C呼び出し規約可変長引数関数の直接定義: "C"および"C-unwind" ABI環境で可変長引数本体をRustで記述可能に。
  • ABI互換のVaList型とVaArgSafeトレイト: Cのva_listと完全連携し、引数昇格規則をコンパイラが強制。
  • 生ポインタレイアウトAPI3種の安定化: Layout::for_value_raw、size_of_val_raw、align_of_val_rawの確立。
  • メモリ回収パターンの指針改定: Box::leak後の再所有権回収を非推奨とし、into_non_null等の利用を推奨。
  • コレクション機能の拡充: Box<[T; N]>のIntoIteratorやVecDeque::retain_backなどの正式安定化。

C ABI可変長引数関数定義の安定化 — 呼び出しから定義へ

可変長引数関数とは、実行時の呼び出し側によって引数の個数と型が動的に決定されるC言語由来の仕組みである。従来のRustにおいても、extern "C" { fn printf(format: *const c_char, ...) -> c_int; }のように外部ライブラリに定義済みの可変長引数関数を呼び出す（call）ことはサポートされていた。しかし、C言語やOSカーネル側から呼び出される可変長引数コールバック関数をRustで直接定義（define）することはできなかった。Rust 1.99.0では、"C"および"C-unwind"呼び出し規約において、シグネチャに...を用いた関数定義が正式にサポートされた。

可変長引数関数はコンパイル時に引数の型とサイズを固定できないため、本質的にunsafe操作を伴う。呼び出し側は関数が期待する型と個数の引数を正確に渡す義務を負い、呼び出された関数は番兵値やフォーマット文字列を通じて引数の終端を判定しなければならない。また、非C ABIのnaked可変長引数関数については、#[unsafe(naked)]属性を付与した上でインラインアセンブリによって実装することが必須要件として定められている。

/// SAFETY: must be called with (at least) 2 i32 arguments.
                    unsafe extern "C" fn sum(mut args: ...) -> i32 {
                        // SAFETY: guaranteed by the caller.
                        let a = unsafe { args.next_arg::<i32>() };
                        let b = unsafe { args.next_arg::<i32>() };
                        a + b
                    }
                    
                    fn foo() -> i32 {
                        unsafe { sum(0i32, 2i32) }
                    }

上記の公式例にある通り、引数リスト末尾のmut args: ...は関数内部でcore::ffi::VaList型として扱われる。呼び出し側はsum(0i32, 2i32)のように通常通り関数を呼び出すが、バイナリ上はターゲットアーキテクチャのC ABIレジスタおよびスタック規約に従って引数が配置される。これにより、CやC++との間で低水準な共有ライブラリを構築する開発者は、冗長なグルーコードを完全に排除できる。

  • 対象呼び出し規約: extern "C"およびスタック巻き戻しに対応したextern "C-unwind"のみで定義可能。
  • 呼び出し側の安全性責任: 引数の型や個数の不一致は未定義動作を招くため、関数シグネチャにunsafeが必須。
  • 引数リストの束縛: 引数宣言の...トークンは関数内部で操作可能なVaList構造体へと変換される。
  • Naked関数の実装規則: #[unsafe(naked)]を伴う場合は、レジスタ退避のためインラインアセンブリの実装が強制される。
  • 外部ラッパーの排除: Cヘッダーとの連携のために書かれていたC言語スタブファイルの削減が可能。

VaListとVaArgSafe — 引数抽出と型安全性

可変長引数リストから引数を順番に読み出すため、Rustはcore::ffi::VaList構造体とcore::ffi::VaArgSafeトレイトを提供する。VaListは各プラットフォームのCコンパイラが使用するva_list構造と100%のバイナリABI互換性を持つ。x86_64 System V、Windows x64、AArch64など、ハードウェアごとに異なるレジスタ退避領域（register save area）やスタックオフセットの計算をVaListが内部で抽象化している。

ここで重要な安全機構がVaArgSafeトレイトである。C言語の仕様では、可変長引数として渡された値には「既定の引数昇格（default argument promotions）」が適用され、floatはdoubleに、charやshortはintへと自動拡張される。もし開発者がargs.next_arg::<u8>()のように昇格前の型をスタックから直接取り出そうとすると、メモリのアライメントが崩れ後続の引数が破損してしまう。RustコンパイラはVaArgSafeが実装された型（i32、f64、生ポインタ等）にのみnext_arg::<T>()の呼び出しを許可することで、ABI不一致によるメモリ破壊を未然に防ぐ。

ただし、next_arg::<T>()の呼び出し自体は依然としてunsafeブロックを要求する。コンパイラが型の適合性を検証できても、呼び出し側が実際にその位置に指定された型の値を渡したかどうかは実行時データに依存するからである。したがって、フォーマット文字列や明示的なヘッダー情報に基づいた入力検証ロジックを設計することが重要である。

  • プラットフォームABIの互換性: アーキテクチャごとに異なるレジスタ退避とスタック構造を単一のVaList型で安全に操作。
  • 既定引数昇格のコンパイル時強制: C規格の昇格規則を反映したVaArgSafeにより、不適切な型抽出を静的に拒絶。
  • インバンド引数長情報の欠如: 可変長引数ストリームには引数の個数情報が含まれないため、境界検出設計が必要。
  • 型安全な抽出インターフェース: args.next_arg::<T>()を用いて目的の型を明示的に指定して展開。
  • 状態複製の整合性: 複数回パースを行うためのC言語va_copy相当の複製メカニズムもABI準拠を維持。

生ポインタレイアウト取得API3種 — Sizedおよび!Sized型の安全性要件

Rust 1.99.0では、生ポインタが指す対象のサイズとアライメントを取得するための3つの関数が安定化した。対象はcore::alloc::Layout::for_value_raw、core::mem::size_of_val_raw、core::mem::align_of_val_rawである。既存のLayout::for_valueやmem::size_of_valは共有参照（&T）を必須としていたが、メモリ解放処理やアロケータ内部では、まだ有効な参照を構築できないダングリング状態や未初期化状態の生ポインタしか手元にない場面が頻繁に生じる。

今回安定化した_raw系統のAPIは、サイズが静的に確定するSized型だけでなく、スライス（[T]）やトレイトオブジェクト（dyn Trait）のような!Sized（unsized）型に対しても統一されたクエリ機能を提供する。Sized型の場合、アドレスの妥当性に関係なくコンパイル時の型情報からサイズとアライメントが計算されるため安全性契約は自明である。一方、!Sized型の場合はファットポインタ（fat pointer）に含まれるメタデータ（スライスの長さやvtableポインタ）を読み取るため、そのメタデータ自体が有効でなければならないという要件が定められている。

use std::alloc::Layout;
                    
                    // Sized型の場合、ダングリングポインタであってもレイアウト取得は完全に安全
                    let dangling_ptr = std::ptr::NonNull::<u64>::dangling().as_ptr();
                    let layout_sized = unsafe { Layout::for_value_raw(dangling_ptr) };
                    assert_eq!(layout_sized.size(), 8);
                    
                    // !Sizedスライスの場合、メタデータ（要素数）を含むファットポインタの妥当性が必要
                    let slice_ptr: *const [u8] = std::ptr::slice_from_raw_parts(dangling_ptr as *const u8, 42);
                    let layout_unsized = unsafe { Layout::for_value_raw(slice_ptr) };
                    assert_eq!(layout_unsized.size(), 42);

このコードが示すように、Layout::for_value_rawを用いることで、不要な&*ptr参照を作ることなく安全にメモリレイアウト情報を復元できる。これにより、カスタムメモリアロケータや外部ランタイム連携コードにおけるエイリアシングルール違反のリスクが排除される。

  • core::alloc::Layout::for_value_raw: 生ポインタから直接対象のLayout（サイズとアライメント制約）を取得。
  • core::mem::size_of_val_raw: 対象が占有するメモリサイズ（バイト数）を生ポインタから直接算出。
  • core::mem::align_of_val_raw: 対象のメモリ配置に必要なアライメント値を生ポインタから直接算出。
  • 不適切な参照化の防止: アドレスや初期化状態が不完全なポインタに対する一時的な&T化による未定義動作を回避。
  • Unsized型メタデータの安全性契約: スライス長やvtableが有効な範囲に存在することを前提条件として規定。

Box::leak文書指針の改定と所有権回収パターンの代替案

Rust 1.99.0の公式ドキュメントにおける重要な方針変更として、Box::leakの推奨使用パターンの改定が挙げられる。Box::leakはヒープ上のBox<T>の所有権を手放し、静的ライフタイムを持つ可変参照（&'static mut T）を取得する手段として長年使われてきた。しかし一部のライブラリでは、一時的にリークさせて静的参照を得た後、後からBox::from_rawを呼び出して再びメモリを解放する「所有権回収パターン（round-trip）」が用いられていた。

Rustチームは1.99.0において、このようなBox::leakを用いたメモリ回収パターンを避けるよう強く推奨した。これは言語の後方互換性を破壊してコンパイルエラーにする変更ではないが、コンパイラがライフタイム情報に基づいて行う最適化前提と矛盾するためである。'static参照はプロセス終了まで生存することが仮定されるため、途中で解放されると最適化パイプラインが破壊される恐れがある。さらに、将来的にカスタムアロケータ（custom allocator）が安定化された際、Box::leakを経由することでアロケータのコンテキスト情報が失われ、解放時に異常終了を引き起こすリスクが指摘されている。

ドキュメントでは、後からメモリを回収する必要がある処理に対しては、Box::leakではなくBox::into_non_nullまたはBox::into_rawを使用することを推奨している。生ポインタ経由の変換を行うことで、所有権がライフタイム機構から外れて生メモリへと移譲されたことをコンパイラに明示でき、後からBox::from_non_null等で安全に回収できる。同様の指針はVec::leakを含む標準ライブラリの他のリーク関数にも適用される。

  • 後方互換性を維持した指針改定: 既存コードのビルドは継続して通るものの、将来の安全性確保に向けた推奨事項を更新。
  • コンパイラ最適化との衝突防止: 'static参照が永続するというコンパイラの仮定を崩さないための防御策。
  • カスタムアロケータへの布石: 将来的なアロケータAPI安定化時にメモリメタデータを維持するための設計見直し。
  • 公式推奨の代替API: メモリの所有権を一時的に切り離す際はBox::into_non_nullやinto_rawを採用。
  • 標準ライブラリ全体への適用: Vec::leakなど類似のライフタイム延長メソッドにも同一の設計基準を展開。

コレクション・文字列・ファイルシステムの追加安定化API詳細

低水準FFIやメモリアクセス機能に加え、Rust 1.99.0では日々の開発効率を高める標準ライブラリAPIが多数安定化した。コレクション領域では、固定長配列を包むBox<[T; N]>に対して反復子トレイトの実装（IntoIterator for Box<[T; N]>、&Box<[T; N]>、&mut Box<[T; N]>）が完備された。これにより、ヒープ上の固定長配列をベクタに詰め替えたりスタックへコピーしたりすることなく直接反復処理できるようになった。

さらに、双方向キューVecDequeには後方から条件判定して要素を削除するVecDeque::retain_backが追加され、リングバッファの要素シフトコストが削減された。反復子アダプタStepByにはFusedIterator for StepBy<I>が実装され、反復終了後の安全性が保証された。ベクタの内部バッファを分解・再構築するVec::into_partsおよびVec::from_parts、非NULL生ポインタを扱うBox::into_non_nullおよびBox::from_non_nullの安定化も、低水準データ構造の記述を容易にする。

文字列とファイル入出力領域でも実用的な拡張が行われた。不正なバイト列を含む場合に不要なヒープ再確保を抑えるString::from_utf8_lossy_ownedとstring::FromUtf8Error::into_utf8_lossyが導入された。ファイルシステム操作では、シンボリックリンクを追跡せずにタイムスタンプを更新可能なstd::fs::set_timesおよびstd::fs::set_times_nofollowが安定化され、バックアップツール等でのセキュリティと正確性が向上した。

  • Box固定長配列の反復処理: Box<[T; N]>の値・参照・可変参照反復を余計なベクタ変換なしにネイティブ実行。
  • VecDeque::retain_backの導入: キュー後方からの効率的な要素削除によりバッファ移動コストを最小化。
  • StepByのFusedIterator対応: イテレータ終了後に確実にNoneを返し続ける安全な動作を保証。
  • ベクタ構成要素の直接制御: Vec::into_partsとfrom_partsによりポインタ・長さ・容量の相互変換を標準化。
  • 所有権付きUTF-8損失許容変換: 既存バッファを活用してアロケーションを抑えるfrom_utf8_lossy_ownedを追加。
  • リンク追跡を防ぐファイル時刻設定: シンボリックリンク攻撃を防ぐset_times_nofollowを含むファイル時刻操作の拡充。

  • ビルド設定の簡素化: C言語で作成されていたFFIラッパーのコンパイル設定を順次整理。
  • コード監査の実施: Box::leakを用いた回収ロジックを検索し、into_non_nullへリファクタリング。

確認できなかったこと

  • 特定の組み込み向けターゲット（Tier 2/Tier 3）におけるVaListのレジスタ退避領域の詳細なメモリ配置。主要プラットフォーム（x86_64、AArch64）の挙動は公式に示されているが、特殊アーキテクチャの個別仕様は確認していない。
  • カスタムアロケータ（Allocator API）が最終的に安定化される具体的なリリースバージョン。Box::leak指針改定の背景として言及されているが、明確な日付は本文に含まれていない。
  • std::fs::set_times_nofollowを非対応の古いファイルシステムドライバ上で実行した際に返されるOS固有のエラーコード（errno）の詳細な対応表。
  • C言語コードとのクロス言語LTO（Link Time Optimization）環境において、可変長引数関数インライン化がバイナリサイズに与える実測影響。
  • 将来のClippyにおいてBox::leakの回収パターンを検知する専用リント規則が標準追加されるかどうかの予定。
