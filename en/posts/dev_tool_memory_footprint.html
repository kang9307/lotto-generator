Why Developer Tools Eat Memory - The Mechanics and Cost of Language Server Footprint

What has to sit in RAM for completion to feel instant, and what you lose when you shrink it

Aug 23, 2026 Dev & Infra

Introduction: the fan spins even when you type nothing

You leave the editor open, walk away for coffee, and come back to a warm laptop. You open one more video call window and completion that was fine a minute ago now arrives a beat late. Right after switching branches the whole editor freezes for half a minute. All three scenes come from the same place. Behind the window, a language server is reading your project and redrawing its own map of it.

In August 2026 an alternative Rust language server showed up in developer feeds under a headline about using 100 times less memory. This article is not an introduction to that tool and not a recommendation of it. It takes the question the headline touched: where does developer tool memory come from, and what exactly does it break when it grows. And what do we quietly hand over when we set out to shrink it.

The announced material comes first, with its verified conditions, and then we leave the specific tool behind and work from first principles.

1. What was announced, and what is the 100x measured against

The project drawing attention is a Rust language server implementation called Rust Glancer. The project site describes itself as taking a different approach from rust-analyzer: instead of holding everything in memory and recomputing dynamically, it uses frozen workspaces that can be offloaded to the filesystem. Accepting some performance penalty in exchange for extreme memory efficiency and instant restarts is the project's own summary, and it puts development time at roughly four months.

Before repeating the multiplier from the headline, the two sides of the comparison have to be separated. Here is what the documentation actually states.

  • The memory figure is a target. The write-up aims for under 100MB on reasonably sized projects, and what counts as reasonable is never defined.
  • The figure on the other side is an anecdote from the author: with several projects open across two copies of the same editor at once, rust-analyzer was consuming 16GB. That is the total for that setup, not the resident footprint of one instance.
  • The side-by-side table the project published has no memory column. It reports indexing time only.
  • So 100x is closer to a 100MB target divided by a 16GB anecdote. No published figure exists for opening the same repository on the same machine under both servers and measuring resident memory side by side.

The published timing comparison looks like this. It is indexing time, not memory, and it carries the condition that it was measured on two MacBooks.

  • MacBook Pro M4 Max 36GB: Glancer 5s base and 8s full, rust-analyzer 6s base and 13s full
  • MacBook Pro M1 8GB: Glancer 6s base and 9s full, rust-analyzer 7s base and 14s full

The costs are documented too. Newly written imports, structs and traits are not indexed until the document is saved. While you type, only the current body is analyzed shallowly and the previous index is reused. Information that requires actually running build scripts or procedural macros, and nightly-only features, are explicitly out of scope for now. Those sentences are a signal rather than a flaw. A multiplier only means something once conditions are attached, and to understand the conditions you have to know why that much memory was needed in the first place.

2. Why a language server spends memory - the price of immediacy

The Language Server Protocol exists to turn a multiplication problem into a division. Instead of implementing language support for every combination of M languages and N editors, each language gets one server and editors speak a standard protocol. Completion, go-to-definition, find references, rename and diagnostics all become the server's responsibility.

This is where one misconception starts: that the source code is what fills memory. The rust-analyzer architecture document is clear on the point. The analyzer keeps all its input data in memory and never does IO, because that input is source code and source code measures in tens of megabytes at most, so holding all of it is fine. What produces gigabytes is not the source but the things derived from it.

What sits in memoryWhat it makes possibleWhat happens without it
Syntax treesUnderstanding the grammatical context at the cursorCompletion degrades into string matching
Name resolution and module scope mapsDeciding which definition an identifier refers toGo-to-definition and rename become guesswork
Type inference resultsComputing what is valid after a dotMethod candidates are wrong or empty
Symbol and reverse reference indexesFind references and workspace-wide searchEvery query rescans the whole project
Dependency graphDeciding what must be recomputed on a changeOne character forces a full reanalysis
Memoized intermediate resultsNever computing the same query twiceThe same work repeats on every keystroke

That last row matters most. A modern language server is an incremental computation engine. rust-analyzer uses Salsa for this, and the core invariant of that design is that typing inside a function body never invalidates global derived data. To keep that promise it maintains per-file summary structures independent of function body edits, indexes module scopes in a separate map, and parses syntax trees only when they are needed.

The finer the structure, the narrower the recomputation, and those pieces plus their caches are exactly what memory holds. The fundamental bargain of the field appears here: you pay memory to buy fast recomputation. If completion appears in the blink of an eye, most of the ingredients for that answer were already sitting in RAM.

3. Trading accuracy for memory - the core of this article

Keeping everything loaded is accurate and fast. The problem is that accuracy, latency and memory cannot all be maximized at once. A lightweight tool has not performed magic; it has put one of the three down, and which one it put down defines its character.

3.1 What gets put down

  • Lazy loading — compute only on demand. Total memory drops but the first query slows. A three second wait that only happens the first time barely registers in average response statistics, and it is exactly the three seconds a person remembers.
  • Partial indexing — the workspace is analyzed precisely while dependencies are kept as summaries. The savings are largest on big repositories, but go-to-definition into library internals stops at some depth.
  • Disk cache — results are written to files and loaded when needed. Restarts get dramatically faster, at the cost of needing rules for when a cached result is stale; conservative rules rebuild constantly and loose ones return wrong answers.
  • Frozen snapshots — type against a shallow view and run full analysis on save. The savings are the largest of all, but a state exists in which what you just wrote does not exist yet.

3.2 What is surrendered is usually the time axis

Line the four up and the pattern appears. What a lightweight tool actually surrenders is often not a feature list but accuracy about the present moment. Code keeps changing between saves while the index stands still at the last one, and the wider that gap grows the more the tool answers questions about slightly older code.

Define a new struct, jump to another file without saving, type its name, and it is not in the candidate list. Nobody files that as a bug because pressing save makes it disappear. So the cost never shows up in benchmarks and lands completely differently depending on habit. For someone who saves every few lines it barely exists; for someone who writes a large block and saves later it is a wall met daily.

3.3 The practical answer is to separate layers

The structure chosen by clangd, the C and C++ language server, is a good example of this compromise. Rather than keeping one monolithic index it layers several and presents them as one. On top sits a dynamic index covering the files being edited right now, and beneath it a background index that sweeps the whole project. The design document explains that thanks to this, cross-references for the files you are working on are available even if the background index has not finished.

The lesson is the principle, not the implementation. The moment you separate what must be current from what need not be, the split between what belongs in memory and what belongs on disk falls out naturally. The file under your cursor must be current to the millisecond; a vendor directory untouched for six months does not. Memory explodes when everything is kept at the same freshness.

4. What actually happens when a developer machine runs short

A large memory number harms nobody by itself. What is harmful is the chain that starts when the number exceeds what is available, and that chain has an order.

  • Reclaim and swapping — the kernel evicts the least used pages first. The first trap lives here. The ps manual defines RSS as non-swapped physical memory, so the tighter memory gets, the more a process's RSS appears to shrink.
  • Compression — macOS compresses before it swaps. The Compressed figure in Activity Monitor is the amount compressed to make more RAM available. Compressed pages cost CPU on every touch, so a memory problem shows up disguised as CPU usage.
  • Working set trimming — Windows removes pages from a process working set. The working set is the set of pages in the process virtual address space currently resident in physical memory, and touching a trimmed page raises a hard page fault resolved from the backing store. That is the moment one completion request becomes a disk read.
  • Competition between tools — the editor core, the extension host, the type checker, bundler watchers, the container runtime and a browser with forty tabs share the same RAM. They evict each other's page cache, so cutting one often speeds up another.
  • Container limits — dev containers and CI put up walls with cgroup v2. Crossing memory.high throttles processes and places them under heavy reclaim pressure, and the kernel documentation states plainly that going over the high limit never invokes the OOM killer. Only when memory.max is reached and usage cannot be reduced does the OOM killer run inside that cgroup.
  • Heat and battery — compression, reclaim and reindexing are all CPU work. On a laptop a memory problem gets translated into a thermal one, which is where the advice to look at RAM capacity first when choosing a laptop comes from.

If a language server or type checker has ever vanished for no apparent reason in CI, there is a place to look before the logs. The cgroup v2 memory.events file carries low, high, max, oom and oom_kill counters, and a rising oom_kill closes the case.

There is also a metric for pressure itself. On Linux, PSI is exposed system-wide at /proc/pressure/memory and per cgroup at memory.pressure. The some line is the share of time in which at least some tasks were stalled on that resource, and the full line is the share of time in which all non-idle tasks were stalled simultaneously. A rising full line is not slowness, it is thrashing. Ten, sixty and three hundred second averages appear together, so momentary spikes and sustained trends can be told apart on one screen.

5. Monorepos and large repositories - growth is not linear

Double the files and memory looks like it should double. It climbs faster than that, and the reason is in the shape of the data structures.

  • Reference relationships are closer to symbol pairs. Symbol count scales with file count, but instant find-references and safe rename need a reverse index of who uses whom, and that index grows faster than file count.
  • Invalidation reaches further. The deeper the dependency graph, the larger the downstream range that must be recomputed when one shared type changes. That is why bigger repositories tempt you into bigger caches.
  • Generated code intervenes. Macro expansions, code generation and schema-derived types are not in the source. The real size of the analysis target drifts away from the apparent size of the repository.
  • Instances multiply. The rust-analyzer documentation notes that a single process can serve many projects, but opening one editor window per project throws that away and multiplies servers by window count. The 16GB anecdote from section one is exactly this arrangement.

The clangd design document records what happens at this scale rather plainly: background indexing a large project would typically take multiple hours and consume multiple GB of RAM. That is why clangd offers the option of attaching a prebuilt static index, and why the remote index feature was created to move the large memory overhead a global index induces onto a separate machine.

The answer for scale follows. Past a certain repository size, tuning on a personal machine stops working and moving indexing off the development machine becomes the remaining direction. A single index server eventually costs less than upgrading RAM for everyone, and that calculation wobbles again in periods when memory prices climb sharply.

6. How to measure - which number to actually read

Most memory conversations go wrong because different numbers are called by the same name. Different definitions produce different conclusions from the same situation.

MetricDefinitionWhere to read itWatch out for
RSSThe non-swapped physical memory a task has usedps, top, /proc status filesExcludes whatever went to swap; shared libraries are double counted per process
VSZVirtual memory size of the process, device mappings excludedpsReservation, not use. Mapping a large file inflates it
PSSThe process's proportional share of a mappingsmaps, smaps_rollupRight for summing across processes; understates a single process
Private_DirtyPages this process alone holds and has modifiedsmapsClosest to what actually returns when the process exits
SwapWould-be-anonymous memory that is out on swapsmapsOnly together with RSS does real usage appear
availableEstimate of memory available for new programs without swappingfreeThis column, not the free column, is the real headroom
memory.currentTotal memory used by a cgroup and its descendantscgroup v2In containers and CI this is the baseline
Working setPages of the virtual address space currently resident in physical memoryWindows Task ManagerShared pages are counted per process
CompressedMemory compressed to make more RAM availablemacOS Activity MonitorA large value already means pressure

There is an order to reading them, and keeping the order removes most misdiagnoses.

  • System headroom first — available on Linux, the memory pressure graph on macOS. If there is room here, one process using 2GB is design rather than a problem.
  • If there is no room, split the shares — use PSS totals to see who holds what. Naive RSS sums double count shared pages and can exceed physical memory.
  • For the process you singled out, read RSS with swap — either one alone reads exactly backwards under pressure.
  • Look for the tool's own instrumentation first — gopls, the Go language server, automatically writes memory debug information to the temporary directory once usage exceeds 1GB, and its debug server exposes profiles and memory state in a browser.

If what remains is lining up the moment the editor froze with reclaim records in system logs, the tooling for that overlaps directly with Linux log analysis commands.

7. Ways to shrink it, and what each one costs

The approaches to reducing memory are already well catalogued, and not one of them is free. Every one trades something from accuracy, latency or operational complexity.

ApproachWhat it doesWhat you gainWhat you pay
Offload to diskKeep analysis results in files, load on demandLower resident memory, faster restartsFirst-access latency, cache invalidation complexity, disk writes
Index on saveShallow while typing, full analysis at saveThe largest memory and CPU savingsNew items invisible to the tool before saving
Partial or lazy indexingPrecise for the workspace, summaries for dependenciesLarge effect on big repositoriesNavigation into library internals stops at some depth
Compact representationsInterning, bit packing and string poolsNo loss of accuracyImplementation complexity, a little CPU per access
Process separationIsolate indexing in a process apart from the editorLighter editor, failures do not spreadIPC cost, one more moving part
Remote indexServe a shared index from a separate serverThe team pays the indexing cost onceInfrastructure, access control, freshness management
Scope exclusionDrop build outputs and vendor directories from the indexImmediate effect at no costThe tool knows nothing about what you excluded

In practice the last row comes first. Scope exclusion is a single configuration line and usually removes things like node_modules or target that never needed analyzing. Process separation and limits come next. Compact representations and index redesign belong to whoever builds the tool, not to whoever uses it.

8. The honest other side - what that memory bought

If lighter were unconditionally better we would still be finding definitions with text search. Developer tool memory grew over the last decade because features grew, not because anyone got lazy.

  • Type-driven completion — not a list of similar-looking names but only what is actually valid at that position. Possible only with type inference results in memory.
  • Safe rename — string replacement damages comments and literals. Reference-graph rename requires a reverse index.
  • Diagnostics before saving — showing errors while you type without running a build is the work of incremental computation caches.
  • Structural navigation — find references, call hierarchy and find implementations cannot exist without a project-wide index.
  • Automated refactoring — extract method, inline and signature change are safe only when types and references are known together.

So the criterion is not the absolute number. It becomes a problem only when you cannot see what that memory bought. A language server using 2GB on an 8GB machine is taking half the machine; the same 2GB on a 64GB machine is a fine deal. And lighter is not always faster either. Holding fewer caches means recomputing on repeated queries and paying to load from disk. Indexing time, response time and memory are separate axes, and there is always a region where improving one degrades another.

9. What to actually look at when choosing a tool

Strip away the marketing and not much judgment material remains. These six are enough.

  • Conditions, not multipliers — which repository, on which machine, with which configuration. A multiplier without conditions is an impression, not information.
  • Target versus measurement — a 100MB goal and a measured 100MB are different statements. If the docs blur the two, that itself is information.
  • Are the accuracy boundaries documented — a project that states what is not indexed and from when is worth trusting. Hiding it is far more dangerous.
  • Fit with your own habits — index-on-save feels opposite to someone who saves constantly and someone who puts it off. Your own habit predicts this better than someone else's review.
  • Worst moments, not averages — the peaks during first indexing, right after a large branch switch, and right after a dependency update.
  • Is there an escape hatch — scope exclusion, a memory limit, restart cost. A tool you can cap keeps the machine alive on bad days.

Before switching tools it is usually faster to count the other things sharing that RAM. Twenty editor extensions, three or four always-on watchers, the browser. Finding 3GB there is more common than saving 1GB by replacing the language server.

What could not be verified

The items this article could not back with a source, collected in one place.

  • A published table measuring resident memory of two Rust language servers side by side on the same repository and machine. The only published side-by-side comparison covers indexing time.
  • What the reasonably sized project behind the target actually means. It is not defined by line count, crate count or dependency count.
  • An official figure for rust-analyzer's typical resident memory. The troubleshooting page in its documentation has no memory section at all.
  • A published benchmark that actually measures the memory growth curve against repository size. The claim in section five that growth is not linear is an argument from data structure properties, not a measurement.
  • Which ledger the per-process Memory column in macOS Activity Monitor reads. Apple's support document defines only the system-level items.

Conclusion: memory is a budget, not a score

Reading language server memory as a scoreboard where lower wins leads to bad decisions. That number is not a score, it is a budget. A tool with a large budget spent it on immediacy and accuracy; a tool with a small one decided not to buy some of that. Which is right depends on the machine's RAM, the size of the repository, and the personal habit of pressing save.

Three things are available today. Check what your current tool uses by reading RSS together with swap, decide whether system headroom is genuinely short using available or memory pressure, and if it is short start with the nearly costless moves such as excluding directories from the index. Replacing the tool is the option after that.

And whenever a new tool arrives with an impressive multiplier, the same three questions apply. Against what, under which conditions, and what was surrendered in exchange. A project that answers all three in its documentation is generally trustworthy, and a project that answers none leaves you without material to judge, however large the number.
