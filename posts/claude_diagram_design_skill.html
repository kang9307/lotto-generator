다이어그램 하나에도 디자인 규칙이 필요하다 - Diagram Design Claude Skill

전문 디자이너의 레이아웃 규칙을 AI 시각화에 이식하는 후처리형 디자인 시스템

2026-09-14 IT/기술

소프트웨어 아키텍처 설계서나 제품 기획서, 혹은 기술 블로그 글을 작성할 때 복잡한 분산 시스템의 흐름을 단 한 장의 명쾌한 다이어그램으로 축약하는 일은 엔지니어와 기획자 모두에게 가장 강력한 전달 수단입니다. 최근 대규모 언어 모델과 코딩 에이전트의 발전으로 텍스트 기반 프롬프트 몇 줄만 입력하면 시스템 다이어그램이나 시퀀스 차트를 뚝딱 만들어내는 자동화 환경이 일상화되었습니다. 그러나 실제 개발 현장에서 AI에게 시스템 구조도를 그려달라고 요청했을 때 돌아오는 결과물은 대다수 실망스러운 수준에 머물렀습니다. 모서리가 둥글게 깎인 무채색 직사각형 상자들, 화면 전체를 가로지르며 얽히고설킨 화살표 선, 그리고 아무런 위계 없이 흩뿌려진 원색의 배치가 뒤섞여 전문적인 출판물이나 경영진 보고용 슬라이드에 그대로 올리기에는 조잡함을 지우기 어려웠기 때문입니다.

이러한 시각적 품질 격차는 모델이 시스템 아키텍처의 논리적 연결 관계를 이해하지 못해서 발생하는 문제가 아닙니다. 근본적인 원인은 자동 생성된 시각화 결과물에 전문 디자이너가 준수하는 엄격한 레이아웃 그리드, 활자 계층 구조, 그리고 절제된 색상 시스템 규칙이 전혀 프로그래밍되어 있지 않았다는 점에 있습니다. 최근 오픈소스 생태계에서 큰 주목을 받으며 개발자 커뮤니티(Hada 등)에서 화두가 된 Diagram Design 스킬은 바로 이 시각적 품질의 결핍을 정확하게 겨냥합니다. 이 도구는 무엇을 그릴지 지시하는 생성 도구가 아니라, 이미 요청된 다이어그램 구조에 출판 편집물 수준의 정밀한 디자인 시스템을 적용하는 강력한 후처리형 프레임워크입니다.

특히 Claude 환경의 에이전트 생태계가 빠르게 성숙하면서 시각 자료 자동화의 영역도 점차 세분화되고 있습니다. 앞서 살펴본 いらすとや Claude Skill이 문서 문맥에 어울리는 일러스트 자산을 단일 호출로 검색하고 배치하는 데 집중했다면, 이번에 살펴볼 Diagram Design은 기술 문서의 뼈대를 이루는 도표와 아키텍처 다이어그램 자체에 전문적인 디자인 규격을 부여하는 또 다른 핵심 축을 담당합니다. 본 포스트에서는 Diagram Design 스킬이 채택한 5대 핵심 디자인 규칙과 39종의 편집용 다이어그램 타입 체계, 도메인 URL 기반의 자동 브랜드 온보딩 파이프라인, 그리고 기존 사내 draw.io 및 Mermaid 자산을 무손실로 재설계하는 실무 활용법을 기술적 관점에서 상세히 분석합니다.

왜 지금까지 AI가 생성한 다이어그램은 늘 조잡해 보였는가

인공지능 어시스턴트에게 클라우드 인프라 구성도나 API 인증 시퀀스를 시각화해 달라고 요청하면 대부분의 도구는 기계적인 규칙에 의존해 그래픽 요소를 캔버스 위에 배치합니다. 생성된 결과물을 열어보았을 때 느껴지는 조잡함은 주관적인 취향의 문제가 아니라, 정보 디자인 관점에서 지켜져야 할 최소한의 시각적 원칙들이 체계적으로 파괴되었기 때문에 발생합니다. 독자가 다이어그램을 마주했을 때 0.5초 안에 전체 흐름의 중심축을 파악하지 못한다면, 그 다이어그램은 시각 자료로서의 본래 목적을 상실한 셈입니다.

시각적 위계의 실종과 무분별한 색상 파티

일반적인 생성형 AI 다이어그램에서 가장 빈번하게 관찰되는 결함은 시각적 위계(Visual Hierarchy)의 완전한 붕괴입니다. LLM은 다이어그램 내에 존재하는 모든 컴포넌트(프론트엔드, API 게이트웨이, 인증 서버, 비즈니스 로직, 데이터베이스, 외부 서드파티 서비스)를 동일한 크기의 사각형 상자와 동일한 굵기의 선으로 렌더링하려는 경향이 있습니다. 그 결과 독자의 시선이 머물러야 할 핵심 진입점이나 병목 구간이 전혀 부각되지 않고, 모든 요소가 화면 전체에서 동일한 크기로 아우성을 치는 듯한 산만함을 낳습니다.

더 심각한 문제는 색상 선택에서 나타납니다. AI 도구들은 종종 어두운 배경 위에 사이안(Cyan)이나 보라색 네온 글로우 효과를 남발하며 공학적으로 그럴듯해 보이는 외양을 꾸며내려 하지만, 이는 실질적인 정보 전달과 무관한 시각적 공해에 불과합니다. 또한 파스텔 톤의 5~6가지 서로 다른 색상을 각 노드마다 임의로 채색하여 시스템 내에서 무엇이 영속 저장소이고 무엇이 일시적 캐시인지, 혹은 무엇이 보안 신뢰 경계(Trust Boundary)인지에 대한 구조적 신호를 완전히 지워버립니다. 색상이 장식적 요소로 전락하는 순간 다이어그램의 가독성은 급격히 곤두박질칩니다.

동그라미와 화살표의 한계를 넘지 못하는 자동 레이아웃

두 번째 한계는 널리 쓰이는 시각화 엔진들의 기계적인 자동 레이아웃 알고리즘에서 비롯됩니다. Mermaid나 Graphviz와 같은 기존 도구들은 그래프 이론 기반의 배치 알고리즘을 사용하므로, 노드가 7~8개를 넘어가기 시작하면 화살표 연결선이 다른 노드의 모서리를 비스듬히 가로지르거나(Diagonal Spaghetti) 텍스트 라벨과 겹치는 현상이 빈번하게 발생합니다. AI는 이러한 도구의 문법을 단순히 생성해 렌더러에 넘길 뿐이므로, 실제 인간 디자이너가 도표를 그릴 때 고려하는 여백의 리듬감이나 시선의 흐름선(Reading Flow)을 전혀 고려하지 못합니다.

이로 인해 생성된 결과물은 이른바 「동그라미와 화살표(Circles and Arrows)」의 도식적 나열에 머물게 됩니다. 노드의 가로세로 좌표와 패딩이 픽셀 단위로 미세하게 어긋나 있어 디스플레이에서 서브픽셀 번짐이 발생하고, 활자 역시 시스템 기본 서체나 모노스페이스 폰트가 무차별적으로 적용되어 제목, 컴포넌트 명칭, 포트 번호, 프로토콜 레이블 간의 타이포그래피 구분이 완전히 무너집니다. 결국 실무진은 AI가 만든 초안을 캡처해 그대로 사용하는 것을 포기하고, 피그마(Figma)나 일러스트레이터(Illustrator)를 켜서 30분 이상 손으로 직접 좌표를 정렬하는 비효율을 겪어야 했습니다.

Diagram Design의 핵심 설계: 무엇을 그릴지가 아닌 어떻게 보이게 할지의 후처리 시스템

Diagram Design 스킬의 개발자인 Cathryn Lavery(BestSelf.co 창업자)는 자신이 운영하는 기술 웹진(littlemight.com)에 게시할 아키텍처 다이어그램과 플로우차트를 AI에게 요청할 때마다 번번이 웹사이트의 디자인 톤앤매너와 어울리지 않는 둥근 상자 결과물이 반환되는 좌절감에서 이 프로젝트를 시작했습니다. 피그마와 30분씩 실랑이하거나 결국 다이어그램 삽입 자체를 포기해버리는 문제를 해결하기 위해, 에이전트 환경에서 동작하는 철저한 디자인 규격집을 코드로 구축한 것입니다.

생성기가 아닌 레이아웃·타이포 후처리 엔진

Diagram Design의 정체성은 다이어그램의 내용을 무에서 유로 상상해내는 생성 도구가 아니라, 철저하게 후처리형 디자인 시스템(Post-processing Design System)이라는 점에 있습니다. 사용자가 Claude Code, Codex, GitHub Copilot, Pi, Factory Droid 등의 AI 호스트 환경에서 자연어로 다이어그램 작성을 요청하면, 스킬은 요청된 시스템의 구조적 관계를 분석한 뒤 사전에 정의된 엄격한 레이아웃 문법과 스타일 가이드라인을 강제합니다.

이 스킬의 핵심 철학은 다음과 같은 한 문장으로 압축됩니다: 「가장 높은 품질의 조치는 대개 삭제다(The highest-quality move is usually deletion).」 모든 노드는 다이어그램 내에서 존재해야 하는 명확한 이유를 스스로 입증해야 하며, 항상 함께 이동하는 두 개의 노드는 하나의 통합 노드로 압축됩니다. 연결선 역시 레이아웃 자체로 관계가 자명하다면 과감히 제거됩니다. 다이어그램의 목표 밀도(Target Density)는 10점 만점에 4점으로 설정되어 있어, 기술적으로 완전하되 별도의 해설 가이드 없이도 한눈에 직관적으로 이해할 수 있는 여백의 균형을 유지합니다. 노드가 9개를 넘어가면 하나의 복잡한 다이어그램으로 뭉개는 대신 개요 다이어그램과 세부 다이어그램 2개로 분할할 것을 권장합니다.

시각화 도구 생태계의 역할 분담과 기존 도구와의 비교

최근 AI 엔지니어링 생태계에서 주목받는 코드베이스 시각화 도구들과의 경계를 명확히 이해하는 것이 중요합니다. 예를 들어 정적 분석과 거대언어모델을 결합해 대규모 저장소의 의존성을 스캔하고 아키텍처를 자동 추출하는 CodeBoarding 도구가 복잡한 소스코드로부터 「무엇을 도표로 표현할 것인가」라는 데이터 추출에 집중한다면, Diagram Design은 그렇게 도출된 아키텍처나 기획 의도를 「어떻게 전문 출판물 수준의 시각 양식으로 표현할 것인가」를 전담합니다.

즉, 다이어그램 추출 파이프라인의 종단에서 시각적 완성도를 결정짓는 렌더링 계층의 역할을 수행합니다. 설치 역시 각 플랫폼의 표준 패키지 매니저를 통해 손쉽게 완료할 수 있으며, Claude Code와 Codex, Copilot 등 다양한 도구에서 일관된 스타일 가이드를 공유합니다.

Diagram Design이 생성하는 최종 출력물은 별도의 렌더링 서버나 빌드 단계가 필요 없는 자체완결형 HTML+SVG 파일입니다. 브라우저에서 파일을 더블클릭하는 것만으로 오프라인 환경에서 완벽하게 열리며, 외부 자바스크립트 실행이나 이미지 다운로드 없이 Google Fonts 호출만으로 렌더링됩니다. 나아가 인쇄물이나 프레젠테이션 슬라이드 배치를 위해 Playwright를 활용한 2배 해상도 PNG 래스터화 기능과 시스템 메타데이터를 담은 JSON 레지스트리 사이드카 내보내기를 기본 지원합니다.

전문 디자이너의 감각을 수식화한 5대 핵심 디자인 규칙

Diagram Design이 일반적인 AI 다이어그램과 질적으로 차별화되는 근거는 감성적인 수식어가 아니라, 엄밀하게 수치화되어 코드로 박혀 있는 디자인 토큰 규칙에 있습니다. 스킬의 내부 파일인 `style-guide.md`와 `SKILL.md`는 도표를 그릴 때 모델이 자의적으로 디자인을 왜곡하지 못하도록 다섯 가지 강제 규칙을 규정하고 있습니다.

4의 배수 그리드 좌표계와 1px 헤어라인 테두리

모든 시각 요소의 절대 좌표, 너비, 높이, 내부 패딩, 그리고 연결선의 간격은 예외 없이 4의 배수(4px, 8px, 12px, 16px, 24px, 32px 등) 그리드에 정렬되어야 합니다. 수동 드래그로 인해 1~2픽셀씩 어긋나는 좌표 불일치는 레티나 디스플레이에서 경계면을 흐리게 만드는 서브픽셀 앤티앨리어싱 오류를 유발합니다. 4의 배수 격자계를 엄격히 준수함으로써 다이어그램 전체에 수학적 질서와 균형감이 부여됩니다.

또한 상자 요소에 부자연스러운 드롭 섀도우(Drop Shadow)나 화려한 입체 효과를 적용하는 행위는 엄격히 금지됩니다. 그림자는 시각적 소음을 가중시키고 문서 인쇄 시 지저분한 번짐을 유발하기 때문입니다. 상자의 외곽선은 투명도가 제어된 1px 헤어라인(Hairline Border)으로만 처리되며, 모서리 반경(border-radius)은 최대 6~10px 이하로 제한하거나 각진 직각을 유지합니다. 모서리를 20px 이상 둥글게 깎아내는 이른바 「캡슐형 상자」 안티패턴은 시스템의 견고한 느낌을 훼손하므로 철저히 배제됩니다.

1개의 강조색과 1~2개 초점 요소의 엄격한 절제

색상 설계에 있어서는 가장 보수적인 편집 디자인 원칙이 적용됩니다. 하나의 다이어그램에서 독자의 시선을 사로잡는 액센트 컬러(Accent Color)는 단 1종류만 허용되며, 이 강조색이 칠해지는 초점 노드(Focal Element)는 최대 1~2개로 제한됩니다. 기본 스킨의 경우 젯 블랙(Jet-black) 잉크와 화이트 스모크(White-smoke) 종이 질감을 배경으로 깔고, 어토믹 탠저린(Atomic-tangerine) 산호색 하나만을 초점 요소에 부여합니다.

만약 작업자가 다이어그램 내에서 4~5개의 요소에 강조색을 입히고 싶다면, 그것은 디자인 문제가 아니라 아직 시스템 내에서 무엇이 본질적인 핵심 경로인지 엔지니어링 관점에서 우선순위를 결정하지 못했다는 방증입니다. 나머지 일반 컴포넌트, 백엔드 API, 상태 저장소, 외부 클라우드 서비스 등은 블루 슬레이트(Blue-slate) 음영과 불투명도가 조절된 잉크 스트로크를 통해 시각적 서열이 자연스럽게 갈무리됩니다.

3개 서체 계층과 Noto Sans KR 다국어 지원

타이포그래피는 정보의 성격에 따라 명확히 구분된 3단계 폰트 스택을 사용합니다. 다이어그램의 최상단 H1 제목에는 고전적인 품격을 전달하는 Instrument Serif(1.75rem, 400 웨이트)가 사용됩니다. 사람이 식별해야 하는 시스템 컴포넌트 명칭이나 노드 레이블에는 가독성이 뛰어난 Geist Sans(12px, 600 웨이트)가 적용됩니다. 반면 포트 번호, 프로토콜, HTTP 엔드포인트, DB 필드 타입 등 정밀한 기술 메타데이터는 Geist Mono(9px, 400 웨이트)로 조판하여 기술적 속성을 명확히 분리합니다.

나아가 Geist와 Instrument Serif 서체가 한글 및 동아시아 문자를 포함하지 않는 점을 고려하여, 공식 스타일 가이드라인의 폰트 스택에는 Noto Sans KR과 Noto Serif KR(대만 번체용 TC 포함)이 기본 내장되어 있습니다. 이 덕분에 한국어 기술 문서나 한글 시스템 구성도를 작성할 때도 글꼴 깨짐이나 서체 대체 현상 없이 미려한 조판 품질을 보장받을 수 있습니다.

Diagram Design이 규정하는 5가지 시맨틱 색상 및 스트로크 토큰 계층은 다음과 같이 명확한 역할 분담을 갖습니다.

  • paper 및 paper-2 토큰: 다이어그램 전체 캔버스 배경과 컨테이너 박스의 2차 배경을 정의하며, 라이트 모드에서는 오프화이트 화이트스모크를, 다크 모드에서는 깊은 젯블랙을 채택합니다.
  • ink 토큰: 주요 텍스트 레이블과 핵심 컴포넌트의 외곽선을 담당하는 기본 잉크 색상으로, 배경과의 극명한 대비를 통해 1차 정보 가독성을 확보합니다.
  • muted 및 soft 토큰: 보조 설명 텍스트, 화살표 연결선, 시스템 경계선 라벨을 위한 감쇄 색상으로, 핵심 노드를 가리지 않는 은은한 시각적 위계를 형성합니다.
  • rule 및 rule-solid 토큰: 불투명도 0.12 수준의 섬세한 1px 헤어라인 테두리로, 상자 요소 간의 영역을 구분하되 시각적 피로도를 최소화합니다.
  • accent 및 accent-tint 토큰: 전체 다이어그램에서 독자가 가장 먼저 시선을 두어야 할 1~2개 핵심 초점 노드에만 독점적으로 부여되는 단 하나의 시그니처 강조색입니다.

39종의 편집용 다이어그램 타입과 4가지 조절 다이얼

Diagram Design 스킬은 엔지니어링 아키텍처부터 비즈니스 전략 기획까지 실무에서 사용되는 총 39종의 편집용 다이어그램 타입을 사전에 정의된 카탈로그로 완비하고 있습니다. v2.5.10 릴리스를 거치며 최종 완성된 이 라이브러리는 각각 고유한 레이아웃 문법과 시각화 규칙을 담고 있습니다.

39종 다이어그램 카탈로그와 시각 변형 체계

지원되는 39종 다이어그램은 실무의 거의 모든 요구사항을 아우릅니다. 시스템 구성요소와 연결을 표현하는 아키텍처(Architecture), 레거시 인프라와 현대화 계획을 대조하는 IT 현행 상태(IT current-state), 조건 분기 로직을 다루는 플로우차트(Flowchart), 시간 순서에 따른 액터 간 메시지 교환을 나타내는 시퀀스(Sequence), 상태 전이와 가드 조건을 명시하는 상태머신(State machine), 데이터베이스 엔티티와 필드 관계를 정의하는 ER/데이터 모델(ER/data model)이 기본 축을 이룹니다.

여기에 일정 및 프로세스를 다루는 타임라인(Timeline), 교차 기능 조직의 워크플로우를 정리하는 스윔레인(Swimlane), 2축 매트릭스 우선순위화 쿼드런트(Quadrant), 다면 역량 평가를 위한 레이더/스파이더(Radar/spider), 강화 루프와 공유 메모리 허브를 표현하는 루프/플라이휠(Loop), 포함 관계를 통한 계층 구조를 나타내는 네스티드(Nested), 부모-자식 트리(Tree), 팀 책임 및 보고 체계의 조직도(Org chart), 계층형 추상화 레이어 스택(Layer stack), 집합 겹침 벤다이어그램(Venn), 깔때기 및 순위 피라미드(Pyramid), 그리고 간트(Gantt), 산점도(Scatter plot), 하이레벨(High-level), 다자간 순차 프로세스(Process), 메달리온(Medallion), 데이터 흐름(Data flow), 데이터 플랫폼 통합(DP integration), 보안 권한 매트릭스(DP security matrix)가 포함됩니다.

최근 추가된 10종의 레이아웃 문법에는 양적 흐름 분기와 병합을 다루는 생키(Sankey), 근본 원인 분석용 피시본(Fishbone), 가치 사슬과 기술 진화를 교차하는 워들리 맵(Wardley map), 칸반(Kanban), 사용자 여정(User journey), 배포 토폴로지(Deployment), 의존성 그래프(Dependency graph), UML 클래스(UML class), 스토리 맵(Story map), 물리적 테이블과 외래키를 나타내는 데이터베이스 스키마(Database schema), 폴라 차트(Polar chart), 누적 기여분을 나타내는 워터폴(Waterfall)까지 포괄됩니다.

모든 다이어그램은 3가지 시각 변형(Minimal Light, Minimal Dark, Full-editorial)을 제공하여 웹페이지 임베드, 슬라이드 발표, 다크모드 대시보드 등 목적에 맞게 즉시 전환할 수 있습니다. 39종 다이어그램은 성격에 따라 다음의 6가지 핵심 실무 범주로 분류됩니다.

  • 시스템 및 인프라 아키텍처 군: 아키텍처(Architecture), IT 현행 상태(IT current-state), 배포(Deployment), 하이레벨(High-level) 등 분산 인프라와 컨테이너 클러스터 토폴로지를 명쾌하게 구조화합니다.
  • 실행 흐름 및 상태 제어 군: 시퀀스(Sequence), 상태머신(State machine), 플로우차트(Flowchart), 프로세스(Process) 등 이벤트 전파와 분기 조건 로직을 시각화합니다.
  • 데이터 엔지니어링 및 스키마 군: ER/데이터 모델(ER/data model), 데이터베이스 스키마(Database schema), 데이터 흐름(Data flow), 메달리온(Medallion), 생키(Sankey) 등 데이터 파이프라인과 저장소 계층을 정의합니다.
  • 프로젝트 및 조직 관리 군: 타임라인(Timeline), 간트(Gantt), 스윔레인(Swimlane), 칸반(Kanban), 스토리 맵(Story map), 조직도(Org chart) 등 일정 계획과 부서 간 협업 인계를 시각화합니다.
  • 전략 분석 및 의사결정 군: 워들리 맵(Wardley map), 쿼드런트(Quadrant), 피시본(Fishbone), 사용자 여정(User journey), 피라미드(Pyramid) 등 제품 전략과 근본 원인 분석을 위한 프레임워크를 제공합니다.
  • 추상 계층 및 정량 분석 차트 군: 레이어 스택(Layer stack), 네스티드(Nested), 트리(Tree), 벤(Venn), 레이더(Radar), 폴라(Polar), 워터폴(Waterfall), 트리맵(Treemap), 산점도(Scatter plot) 등 다차원 데이터를 정밀 조판합니다.

포맷·크기·상세도·독자층을 제어하는 4대 다이얼

Diagram Design의 변환 철학은 단순한 일대일 그래픽 포맷 변경이 아니라, 결과물이 전달될 최종 목적지에 최적화되도록 시각적 정보를 재단하는 것입니다. 이를 위해 스킬은 4가지 조절 다이얼(Dial)을 제공합니다.

다이얼 명칭 지원 파라미터 값 렌더링 시 변경되는 요소 주요 권장 용도
포맷 (Format) html, svg, png, html+png 최종 파일 확장자 및 번들 구조 (SVG는 Figma용, PNG는 슬라이드용) 웹 배포, 디자인 툴 임포트, 인쇄 자료 분기

60초 만에 끝나는 웹사이트 기반 브랜드 온보딩과 접근성 표준

엔지니어가 다이어그램 도구를 사용할 때 가장 고통스러운 과정 중 하나는 회사의 CI 가이드라인에 맞춰 색상 팔레트의 16진수 헥스 코드를 하나하나 따서 붙여넣는 일입니다. Diagram Design은 이 번거로운 과정을 단 60초 만에 끝낼 수 있는 강력한 브랜드 온보딩(Brand Onboarding) 기능을 제공합니다.

도메인 URL에서 팔레트와 폰트를 추출하는 자동화 파이프라인

사용자가 에이전트에게 onboard diagram-design to https://yoursite.com 명령을 전달하면, 스킬은 대상 웹사이트의 홈페이지를 단일 HTTP 호출로 읽어들인 뒤 헤드 영역과 CSS 스타일시트를 분석합니다. 그리고 사이트에서 가장 지배적으로 사용되는 색상과 폰트 스택을 추출하여 시맨틱 토큰 역할에 자동으로 매핑합니다.

You:     "onboard diagram-design to https://yoursite.com"
Agent:   → fetches the homepage
         → extracts the dominant palette + font stack
         → maps detected values to semantic roles:
             paper, ink, muted, accent, link
         → shows a proposed diff
         → writes your tokens to references/style-guide.md
You:     "yes, apply it"

이 매핑 과정을 거치면 웹사이트의 <body> 배경색은 다이어그램의 paper 토큰이 되고, 본문 글자색은 ink가 되며, 주요 CTA 버튼이나 링크의 강조색은 accent 토큰으로 안착합니다. H1 헤딩 서체는 다이어그램 제목으로, 본문 폰트는 노드 명칭으로 계승됩니다. 작업이 완료되면 샘플링된 URL과 정확한 색상 역할, 서체 소스 URL을 기록한 피델리티 영수증(Fidelity Receipt)이 발행되어 스타일 가이드에 영구 저장됩니다. 여러 고객사나 브랜드를 번갈아 작업하는 프리랜서나 에이전시를 위해 ~/.diagram-design/profiles/ 디렉터리에 프로젝트별 프로필을 분리 저장하고 전환할 수 있는 프로필 마커 기능도 지원됩니다.

도메인 스캔을 통해 사이트에서 자동으로 감지되어 시맨틱 토큰으로 승격되는 5대 스타일 요소는 다음과 같습니다.

  • 웹사이트 배경색(Body Background): 캔버스의 기본 바탕이 되는 paper 토큰으로 변환되어 다이어그램이 웹페이지와 단절 없이 녹아들도록 유도합니다.
  • 주요 본문 글자색(Primary Text Color): 최우선 텍스트와 노드 외곽선 획을 담당하는 ink 토큰으로 매핑되어 명확한 판독성을 확보합니다.
  • 보조 캡션 및 부차 텍스트(Secondary / Caption Text): 관계 화살표와 기술 서브라벨을 위한 muted 토큰으로 변환되어 정보의 계층을 정돈합니다.
  • 컨테이너 및 카드 배경(Cards / Containers): 시스템 경계 상자나 서브모듈 그룹을 감싸는 paper-2 보조 배경 토큰으로 치환됩니다.
  • 최다 빈도 브랜드 색상(Most-used Brand Color / CTA): 클릭을 유도하는 버튼이나 대표 헤딩 색상을 accent 토큰으로 추출하여 다이어그램의 유일한 초점으로 사용합니다.

WCAG AA 명암비 검증과 SVG 접근성 메타데이터

브랜드 온보딩 과정에는 접근성 안전장치가 기본 내장되어 있습니다. 추출된 색상 토큰을 스타일에 기록하기 전에, 스킬은 paper 배경 위에서 ink 본문과 muted 화살표 라벨이 WCAG AA 명암비 기준(최소 4.5:1 이상)을 만족하는지 수학적으로 검증합니다. 만약 고객사 웹사이트의 기본 브랜드 컬러가 다이어그램의 작은 폰트 크기(9~12px)에서 명암비 검증에 실패할 경우, 스킬은 임의로 색을 뭉개는 대신 명암비를 보정한 조정값을 제안하고 그 사유를 사용자에게 설명합니다.

더불어 생성되는 모든 인라인 SVG는 웹 접근성 표준을 충족합니다. 루트 SVG 엘리먼트에 role="img" 속성과 고유한 aria-labelledby 속성을 부여하고, 내부 첫 번째 자식 요소로 <title> 및 <desc> 슬롯을 생성하여 스크린 리더 보조 기술을 사용하는 시각 장애인 사용자도 시스템의 구조와 흐름을 음성으로 전달받을 수 있도록 설계되었습니다. 장식용 아이콘은 스크린 리더에서 자동으로 숨겨집니다.

기존 draw.io·Mermaid 자산의 무손실 재설계와 한국 실무 활용 시나리오

많은 엔지니어링 조직이 이미 수년 동안 작성해 둔 사내 다이어그램 자산을 보유하고 있습니다. Confluence 문서에 첨부된 draw.io 파일이나 GitHub 리포지토리 README에 삽입된 수백 줄의 Mermaid 블록들이 대표적입니다. Diagram Design은 이러한 기존 자산을 처음부터 다시 그릴 필요 없이, 텍스트 소스를 입력받아 동일한 내용을 브랜드 디자인 시스템으로 재설계(Redraw)하는 임포트 파이프라인을 지원합니다.

사내 레거시 자산의 단계별 압축과 디테일 래더

스킬은 draw.io의 .drawio, .drawio.xml, .drawio.svg는 물론 에디터에서 base64 압축물로 보이는 페이로드까지 직접 텍스트 레벨에서 파싱합니다. Mermaid의 .mmd, .mermaid 파일 및 마크다운 내 코드 펜스 블록, 그리고 Excalidraw의 .excalidraw JSON 씬 파일도 동일하게 지원합니다. 이때 브라우저 렌더링이나 외부 자바스크립트 실행 없이 순수 텍스트 파싱만으로 구성요소와 연결선, 그룹화 정보를 추출합니다.

# draw.io 아키텍처 파일을 임원 보고용 16:9 슬라이드로 재설계
/diagram-design:import-drawio platform.drawio --size=slide-16x9 --detail=simplified --audience=executive

# README 파일 내부의 모든 Mermaid 블록을 고품질 SVG/PNG로 일괄 재설계
/diagram-design:import-mermaid README.md --diagram=all

# 화이트보드 Excalidraw 스케치를 블로그 게재용 밸런스드 다이어그램으로 정돈
/diagram-design:import-excalidraw whiteboard.excalidraw --size=slide-16x9 --detail=balanced

재설계 과정에서는 원본 파일에 존재하던 6가지 파스텔톤 배경색, 손으로 드래그되어 삐뚤빼뚤한 좌표, 대각선으로 얽힌 스파게티 커넥터가 모두 제거됩니다. 대신 단 1개의 브랜드 액센트 컬러와 4의 배수 그리드 직각 배선으로 교체됩니다. 변환이 완료되면 원본에서 무엇이 병합되었고(Collapsed), 무엇이 불필요한 장식 스티커 메모여서 제거되었는지(Dropped), 무엇이 유지되었는지(Kept in full)를 보여주는 피델리티 원장(Fidelity Ledger)이 출력되어 변경 내역을 투명하게 검증할 수 있습니다.

한국 IT 개발팀과 기획자를 위한 2가지 실무 적용 시나리오

국내 IT 스타트업 및 엔터프라이즈 환경에서 이 도구를 실무에 즉시 도입할 수 있는 구체적인 시나리오는 다음과 같습니다.

  • 시나리오 1: 복잡한 결제 및 인증 파이프라인의 장애 분석 보고서(Post-mortem) 작성 — PG사 연동 장애나 OAuth 토큰 갱신 실패가 발생했을 때, 백엔드 개발자는 복잡한 분산 트레이스 로그를 바탕으로 장애 경로를 시각화해야 합니다. Diagram Design의 시퀀스(Sequence) 타입에 --detail=balanced 옵션을 적용하면, 수십 개의 내부 마이크로서비스 호출 중 실제로 401 Unauthorized를 유발한 게이트웨이-인증서버 간의 1개 호출에만 탠저린 강조색을 부여하고 나머지 정상 트래픽은 은은한 슬레이트 음영으로 처리한 보고서용 다이어그램을 3분 안에 완성할 수 있습니다. 경영진과 유관 부서는 복잡한 텍스트 로그 없이도 장애 원점(Root Cause)을 즉각 인지할 수 있습니다.
  • 시나리오 2: 대규모 엔터프라이즈 레거시 시스템의 클라우드 마이그레이션 제안서 작성 — 온프레미스 IDC에 분산된 수십 대의 데이터베이스와 ERP 서버를 AWS 또는 GCP 클라우드로 전환하려는 SI 프로젝트 제안서 작업에서, 기획자와 클라우드 아키텍트는 현행 시스템의 복잡도를 한눈에 보여주어야 합니다. 기존에 팀원들이 제각각 작성해 둔 draw.io 인프라 구성도를 IT current-state 타입으로 임포트하면, 부서별 레거시 영역과 현대화 타깃 영역이 명확한 레이어 스택으로 정돈되며, 사내 브랜드 컬러가 자동으로 입혀진 제안서 삽입용 고해상도 벡터 다이어그램을 일관되게 생성할 수 있습니다.
  • 일관된 시각 언어의 내재화 — 디자이너 인력이 부족한 중소규모 개발팀에서도 외주 디자이너 없이 개발자가 직접 발표 슬라이드와 기술 백서를 출판물 수준으로 제작할 수 있습니다.
  • CI/CD 문서 파이프라인 연계 — GitHub Actions 등 배포 워크플로우 내에서 마크다운 내 Mermaid 다이어그램을 Diagram Design CLI를 통해 정기적으로 고해상도 SVG로 자동 빌드하여 공식 문서 사이트에 게시할 수 있습니다.
  • 협업 커뮤니케이션 비용의 대폭 절감 — 말로 설명하기 어려운 분산 시스템의 데이터 흐름을 정형화된 시맨틱 패턴(Data Flow, Fan-in Queue)으로 즉시 가시화하여 개발자 간 싱크 회의 시간을 절반 이상 단축할 수 있습니다.
  • 접근성 법적 규정의 선제적 충족 — 공공기관이나 금융권 프로젝트에서 요구되는 웹 콘텐츠 접근성 지침(KWCAG / WCAG)을 별도의 수작업 점검 없이 SVG 메타데이터 수준에서 자동으로 만족시킬 수 있습니다.

확인하지 못한 것

본 포스트는 Diagram Design 공식 GitHub 저장소(cathrynlavery/diagram-design)의 최신 릴리스 소스코드 및 문서 명세를 정밀 대조하여 작성되었습니다. 다만 다음 항목들은 원문 명세에 수치가 기재되어 있지 않거나 외부 환경에 종속되어 있어 공식적인 수치를 확정하지 못했습니다.

  • Playwright 래스터화 시의 메모리 점유율 및 대규모 배치 변환 벤치마크: 공식 README에서는 --scale=3과 같은 옵션을 통해 2~3배 고해상도 PNG를 생성할 수 있다고 밝히고 있으나, 수백 장의 다이어그램을 CI/CD 환경에서 일괄 렌더링할 때 소요되는 구체적인 초당 변환 속도나 메모리 한계 수치는 원문에 공개되어 있지 않습니다.
  • 동아시아 CJK 폰트의 로컬 번들링 지원 일정: 스타일 가이드 내 폰트 스택에 Noto Sans KR 및 Noto Serif KR이 명시되어 있으나, 오프라인 완전 폐쇄망 환경에서 Google Fonts CDN 연결 없이 로컬 woff2 파일로 대체 번들링하는 정식 스크립트 제공 여부는 공식 문서에 수록되어 있지 않습니다.
  • 엔터프라이즈 Cowork 마켓플레이스의 향후 로드맵: 사내 프라이빗 리포지토리를 미러링하여 자동 동기화하는 설정 방식은 상세히 서술되어 있으나, 조직 단위 유료 플러그인 레지스트리 통합 계획에 대한 언급은 원문에 존재하지 않습니다.
