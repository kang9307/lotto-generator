opencodex: Use Any LLM with OpenAI Codex CLI via Local Proxy

A local protocol translator that breaks Codex free from OpenAI lock-in — practical analysis of vendor escape, cost savings, and privacy in 2026

2026-06-22 Dev & Infra

Introduction: The Problem With a Great Tool That Only Speaks One Language

OpenAI Codex CLI is one of the most capable AI coding agents available today. As of June 2026, it sits at the top of the Terminal-Bench 2.1 leaderboard at 83.4%. The architecture is clean: a terminal-native agent loop that plans, edits files, runs commands, and iterates. The problem is structural. Codex only works with OpenAI models. Running it requires a ChatGPT Plus ($20/month) or Pro ($200/month) subscription. Claude, Gemini, DeepSeek, Qwen, and local models via Ollama are simply out of reach.

This is where opencodex comes in. The project surfaced on GeekNews with 46 points and can be summarized in one sentence: a local proxy that lets you use any LLM with Codex CLI, App, and SDK. This piece is not a feature listing. It is an analysis of why this tool matters, how the protocol translation works, where it fits relative to alternatives like LiteLLM, and what risks are real. Information is as of June 2026.

1. Why This Problem Exists — The Responses API Wall

To understand opencodex you need to understand the protocol gap it fills.

1.1 OpenAI's Responses API

In early 2025, OpenAI introduced the Responses API — a successor interface to the older Chat Completions API, optimized for multi-turn conversations, tool calls, reasoning tokens, and image handling in agentic workflows. Codex CLI was built on this API from the ground up. The Responses API is better suited to the agent loop that Codex runs: plan, call tool, observe result, plan next step, repeat.

1.2 Everyone Else Speaks a Different Language

The issue: virtually every other LLM provider does not support the Responses API. Anthropic uses the Messages API. Google uses the Gemini API. Local model runners like Ollama expose an OpenAI Chat Completions-compatible endpoint. Each speaks a different protocol. Codex is a Responses API-only client. The result is a hard wall: Codex cannot talk to anything that is not OpenAI.

1.3 The Community Signal

Issue #26 on the openai/codex repository — "Support for local / other LLMs" — captures how immediate this demand was. Developers who preferred cost-efficient providers, required code privacy, or simply wanted model choice ran into the wall on day one. opencodex is the community's direct answer to OpenAI's silence on this issue.

2. How opencodex Works — A Protocol Translator

The architecture is intentionally simple. opencodex is a locally running translation proxy.

2.1 The Request Flow

Codex CLI / App / SDK
        │  (Responses API request)
        ▼
   opencodex  (local proxy)
        │  (protocol translation)
        ▼
   Target LLM Provider
   (Claude / Gemini / DeepSeek / Ollama / ...)

Codex sends a Responses API request to opencodex, which intercepts it, translates it into the target provider's native protocol, forwards it, translates the response back, and returns it to Codex as a valid Responses API response. From Codex's perspective, it is always talking to a Responses API endpoint. In reality, the backend can be anything.

2.2 Five Protocol Adapters

opencodex ships with five adapters:

AdapterTargetCoverage
anthropicClaude Messages APIAll Anthropic models (Claude 3.5, 3.7, etc.)
googleGemini APIGemini 2.0, 2.5, and future Google models
azure-openaiAzure OpenAIOpenAI models deployed on Azure
openai-responsesOpenAI Responses (passthrough)Direct OpenAI passthrough
openai-chatChat Completions-compatible endpointsDeepSeek / GLM / Kimi / Qwen / Groq / OpenRouter / Ollama / 40+ providers

The openai-chat adapter is the broadest. Any provider that exposes an OpenAI Chat Completions-compatible endpoint — which is now the de facto standard across the industry — is covered. Point opencodex at an OpenRouter URL and you have access to hundreds of models behind Codex.

2.3 Bidirectional Feature Translation

A proxy that only relays text is not enough for an agentic workflow. opencodex translates streaming, tool calls, reasoning tokens, and images bidirectionally. This matters because Codex relies on tool calls to edit files and run terminal commands. If the tool call structure is lost in translation, the agent loop breaks. The quality of this translation is what separates opencodex from simpler relay solutions.

3. Installation — Three Commands

The entry barrier is low. Prerequisites: Bun 1.1 or later. Then:

npm install -g @bitkyc08/opencodex   # or: bun install -g @bitkyc08/opencodex
ocx init    # interactive setup: choose provider, model, API key
ocx start   # start the proxy as a background service

ocx init walks through provider selection interactively and automatically injects the proxy configuration into Codex CLI, TUI, App, and SDK. No manual Codex config file editing required. ocx start runs the proxy as a background service with a real-time web dashboard for visualizing request flow. MIT licensed, open source.

4. Why Vendor Lock-in Matters Here

The structural tension opencodex addresses is not unique to Codex. It is the defining pattern of 2025-2026 AI tooling.

4.1 The Open Tool / Closed Fuel Problem

Codex CLI is Apache 2.0. The source code is open. But running it requires an OpenAI subscription — the fuel is locked. This is a deliberate product strategy: publish the tool to drive subscription demand. For developers, this creates three concrete problems. First, cost: Pro at $200/month is significant for heavy use. Second, code privacy: every codebase sent to Codex goes through OpenAI's servers. Third, model choice: a better model for a specific task is irrelevant if Codex cannot reach it.

4.2 opencodex's Answer to Each

On cost: connecting a cheaper OpenAI-compatible provider (DeepSeek V3, Qwen, local Ollama) can dramatically reduce per-token cost while keeping the Codex interface intact. On privacy: connecting a local model via Ollama means code never leaves your machine. On model choice: swap providers via ocx init — no workflow changes, no script rewrites.

4.3 The Tool-Layer Abstraction

My read of opencodex's core value: it is not "this model works better." It is that the model choice becomes a configuration parameter, not a permanent architectural decision. This is the same philosophy LiteLLM applied at the code layer, now applied at the tool layer. Provider-agnostic design compounds over time — as better and cheaper models emerge, switching costs approach zero.

5. Comparison With LiteLLM — Different Layers, Both Necessary

LiteLLM and opencodex look similar on the surface. They are not solving the same problem.

5.1 LiteLLM

LiteLLM (v1.83.8, MIT) is a Python SDK and proxy server that normalizes 100+ LLM providers behind one OpenAI-compatible interface — for your own application code. You integrate LiteLLM into your app; your code calls LiteLLM; LiteLLM routes to whichever provider you configure. The abstraction lives at the SDK level. (Note: In March 2026 LiteLLM disclosed a supply chain security incident — the team published full details and patched; it remains the most widely deployed open-source LLM gateway.)

5.2 opencodex

opencodex works at the tool layer: it intercepts requests from Codex, a tool you did not build and cannot modify. The abstraction lives between an existing tool and the network. You do not change the tool; you change what it talks to.

5.3 Chain Them

The two are composable. Point opencodex's openai-chat adapter at a LiteLLM proxy server URL. Now the chain is: Codex → opencodex → LiteLLM → any of 100+ providers. This adds LiteLLM's budget controls, fallback routing, and logging to the Codex workflow. Whether the added complexity is worth it depends on your infrastructure — but the option exists cleanly.

6. The Broader Ecosystem

opencodex is not the only project in this space. Understanding the alternatives clarifies where opencodex fits.

6.1 codex-relay

A lightweight Rust proxy that translates Responses API to Chat Completions API. Narrower scope than opencodex — only one direction of translation, no multi-adapter system — but Rust's performance characteristics make it attractive for high-throughput scenarios with OpenAI-compatible targets.

6.2 codex-glm-proxy

Single-purpose: connect Codex to GLM-5.2 (Zhipu) via their Chat API. Minimal footprint for one specific use case. If GLM is your target and you want nothing else, this is simpler than opencodex.

6.3 OpenCode — The Alternative Path

The most important alternative is not a proxy at all. OpenCode — 168,000+ GitHub stars as of June 2026 — is an open-source Codex CLI replacement that natively supports 75+ LLM providers. If your team has no attachment to the Codex interface specifically, replacing the tool is a cleaner long-term choice than proxying it. opencodex makes sense when you want to keep the Codex workflow and change only the model backend.

7. Honest Risk Assessment

Any analysis that only lists capabilities is incomplete. The real risks matter.

7.1 Terms of Service Risk

The author's own warning: "Some providers — notably Anthropic (Claude) — may suspend or restrict accounts that route API traffic through third-party proxies. Use at your own risk." This is not hypothetical. Routing Anthropic API calls through opencodex may violate Anthropic's ToS. Check the ToS of each provider before connecting. Do not assume all adapters are equally safe.

7.2 Translation Completeness

Protocol translation is not lossless. When Codex requests a feature (say, reasoning tokens in a specific Responses API schema) and the target model has no equivalent concept, the adapter must approximate or drop the feature. The result may be subtle degradation in agent behavior — missed steps, incorrect tool call parsing — that is hard to diagnose. Validate behavior on your specific workload, not general benchmarks.

7.3 API Key Handling

opencodex handles API keys through a local process. In a personal dev environment this is fine. On shared servers or multi-user machines, validate that key material is not exposed to other users or logged insecurely.

7.4 Maintenance Dependency

This is a community project. If OpenAI changes the Responses API schema or Codex updates its internal protocol, opencodex adapters need to be updated. There is no SLA. Evaluate the maintainer's activity history before relying on opencodex for production workflows.

8. Who Should Use It

8.1 Good Fit

Teams already invested in Codex CLI workflows who want model flexibility without retooling. Developers who require code privacy: local model via Ollama means zero network egress. Heavy Codex users whose primary pain is cost: cheaper Chat Completions-compatible providers cut per-token rates significantly.

8.2 Poor Fit

Teams primarily using Claude Code, Cline, or OpenCode — opencodex is irrelevant to non-Codex workflows. Anyone wanting to connect Claude specifically: the ToS risk is real. Teams building from scratch who want multi-provider support: start with OpenCode (native multi-provider) rather than adding proxy complexity to Codex.

9. Conclusion — Protocol Abstraction as Developer Freedom

opencodex is not technically novel. Proxy-based protocol translation is a solved class of problem. What it does is apply that pattern to a specific, pressing gap that OpenAI left open: Codex, the best-benchmarked terminal coding agent, locked to one provider's subscription model.

The tool's significance is not its performance claims — it makes none. Its significance is the principle: the tool you use should not permanently determine the model you use. Provider choice should be a configuration, not an architectural commitment. opencodex makes that true for Codex. The same principle is why LiteLLM exists, why OpenCode became the leading open-source alternative, and why the Responses API-to-Chat Completions translation problem spawned multiple independent projects in the same quarter.

Two concrete actions if this is relevant to you. First: if you are already using Codex CLI and have cost or privacy concerns, run ocx init and test a DeepSeek or Ollama connection — after reading that provider's ToS. Validate that your agent loop behaves correctly, specifically tool calls and streaming. Second: if you are evaluating AI coding agents from scratch, benchmark OpenCode against Codex before committing to either. The proxy is a bridge; sometimes the better move is to take a different road.
