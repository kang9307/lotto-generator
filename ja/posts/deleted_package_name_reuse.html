削除されたパッケージ名に要求が届き続ける理由 - 消えたのはコードで、残ったのは参照だ

削除は名前を空ける行為ではない。断ち切れないのはその名前を書き留めた参照だ

2026-09-11 開発・インフラ

あるパッケージが悪意あるコードと判定され、レジストリから取り下げられる。ところがそのあとも、その名前には毎週数百回のインストール要求が届く。この文が前後で噛み合わないように聞こえるなら、削除という措置が何を断ち、何は最後まで断てないのかがまだ分かれていない。

分けるべきものは一つだ。削除はその名前で新しいコードが出ていく経路を断つ措置であって、その名前を書き留めたファイルを直す措置ではない。コードが消えても参照は残る。残った参照は決まった時刻ごとに同じ要求をまた送る。その要求が集計に入り、集計された数字が「まだインストールされている」という文になって戻ってくる。

ここでもう一つが分かれる。消した場所は本当に空くのか。少なくとも npm は空けておかない。悪意判定のあとの処理手順に、その名前の場所へセキュリティの標識を立てる段階が公開文書として入っている。だからこの問題の正確な呼び名は「空いた名前が危ない」ではなく、「断ち切られていない参照がまだその名前を指している」だ。

以下で根拠に使うのは npm の公開方針文書二件と、npm がダウンロード集計の仕組みを説明した文書、そして発端になったリポジトリの一覧文書だ。悪意あると判定されたパッケージの実際の名前は書かない。名前を書けばその名前へ向かう検索が増えるからだ。特定の事業者や運営主体への評価も扱わず、本文に載せたコマンド例はすべて読み取り専用である。

発端 - 消された名前に要求が残っているという一覧

きっかけになったのは、ある公開リポジトリに上がった一覧と、その一覧を作る道具だ。作り方が結論の射程を決めるので、まず作り方から立てる。

広く使われている npm パッケージ240個を種に置き、名前がよく崩れる方式を五つ機械的に当てて候補名を作る。スコープを外し、点とハイフンを入れ替え、ハイフンを消し、プラグインの接頭辞を外し、後ろに短い接尾辞を足す。そうして作られた npm 側の候補が773個で、そのうち263個が実際にレジストリに存在した。道具の判定で危険等級が出たのが130個、そのうち一覧に公開されたのが50個だ。残りの80個は公開されていない。

公開の基準が狭く取られている点が重要になる。一覧文書は危険等級だけを対象にし、そのなかでも根拠が二種類のどちらかであるときにだけ載せると記している。一つは npm 自身が立てたセキュリティの標識であり、もう一つは実在するパッケージを名指しする廃止のお知らせ文だ。だから公開された50個は、標識が立っているもの36件と廃止のお知らせが付いているもの14件に分かれる。

そしてこの一覧には生成時刻が付いている。文書に記された生成日は 2026-09-10 で、毎週作り直されると明記されている。発端になった記事の見出しが言った値は 35 で、同じ節の行は 36 だ。二つの値はどちらかが誤りなのではなく、別の週の値と見るほうが自然だ。毎週再生成される一覧の数字を固定された事実のように引用すると、その瞬間からずれ始める。

その数字が実際に数えたもの

数字を引く前に、その数字が何を数えなかったのかから立てるほうが安全だ。調査の母集団そのものが狭く取られているからである。

  • 数えなかったもの — レジストリからこれまでに悪意ありとして取り下げられたパッケージの総数。対象集合が種240個から派生した候補なので、その派生規則に掛からない名前はそもそも候補に入らない。この数字は全数調査の結果ではないし、そう提示されてもいない。
  • 数えたもの — その候補集合のなかで、実際にレジストリに存在し、道具の判定で危険等級を受け、その根拠が npm 自身のセキュリティ標識である名前の数。三つの条件が同時に成り立つ交わりだ。
  • 動く理由 — 一覧は毎週作り直され、各行のインストール数もそのたびに引き直される。標識が新しく立てば増え、道具の判定規則が変われば別の方向に動く。こうして出た数は定数ではなく読み値だ。

だからこの一覧を正確に読むとこうなる。名前が崩れるよくある方式で作られた候補のうち、npm がセキュリティ上の理由で取り下げて標識を立てた名前が三十いくつかあり、その名前にまだ要求が届いているということだ。「悪意あるパッケージ35個がいまも流通している」とは別の文であり、その差は言葉尻の問題ではない。前者は残った配管の話で、後者は進行中の感染の話になる。

削除すると名前はどうなるのか

この記事の軸がここにある。npm が悪意あるコードの通報を処理するとき踏むと文書に記している手順は三段階だ。

  • レジストリからそのパッケージを取り除く。
  • そのパッケージの場所にセキュリティの標識となるパッケージを公開する。
  • コミュニティに知らせるセキュリティ勧告を出す。

二段目がこの記事の冒頭で立てた前提を直してくれる。消した場所は空かない。そこには「ここにあったものはセキュリティ上の理由で取り下げられた」という意味の標識が立つ。名前は開いておらず、その座標では依然として何かが応答する。

結果が二方向に分かれる。要求を送った側から見ればインストールはたいてい失敗するか、成功しても機能を持たない標識がツリーに入ってくる。一方レジストリ側から見れば、その要求は正常に応答された一件だ。あとに出てくる統計の話は、まさにこの地点で分かれる。危険が実現した件数と要求が届いた件数は同じ値ではなく、この名前群では両者が大きく離れている。

したがって「削除が名前を空ける」という言い方は、少なくともこのレジストリでは成り立たない。実際に残る問題は空いた場所ではなく、その場所を依然として指している参照のほうだ。残りの節の半分がその参照を扱う。

同じ座標を再び使わせない規則

公開取り消しの方針は名前とバージョンを別々に扱う。この区別が、ロックファイルが何を固定しているのかと直につながる。

  • 名前とバージョンの組み合わせは再利用されない。一度使われた組み合わせは二度と使えず、取り下げたあとでも新しいバージョン番号で上げなければならない、というのが方針文書の文だ。挙動からの推測ではない。
  • 全バージョンを取り下げると待ち時間が付く。その名前で新しいバージョンを上げるには24時間が過ぎなければならない。
  • 自分で取り下げられる条件そのものが狭い。上げてから72時間以内なら、ほかのパッケージがそれに依存していないかぎり取り下げられる。72時間を過ぎたあとは三条件をすべて満たす必要がある。依存するパッケージがないこと、直近一週間のダウンロードが300回未満であること、所有者が一人であることだ。

これらの規則の向きは一つに集まる。すでに配られた座標に別の中身が入り込めないようにする。ロックファイルが掴んでいる座標は名前とバージョンと解決済みアドレスと完全性ハッシュの組であり、そのうち名前とバージョンの組がレジストリの側で固定されると、「同じ座標に別の中身」という経路が大きく狭まる。

ただしこれは座標の再利用を防ぐ規則であって、参照の整理を強いる規則ではない。自分のリポジトリのロックファイルが依然としてその座標を指しているという事実は、レジストリ側の規則では変わらない。そもそも依存を減らす側の判断はソフトウェアを「より少なく」再利用するという選択で別に扱った。この記事はすでに入っている参照をどう見るかに集中する。

別のレジストリは違うやり方を選んだ

同じ状況を別のレジストリは違う方式で処理する。並べて見ると「空いた場所」という言い方がなぜ不正確なのかがさらに鮮明になる。

  • 名前の保持原則が先に立つ。Python のパッケージ索引の公開文書は、放置されたという理由だけでプロジェクトを索引から消すことはないという原則を前に置く。上がった成果物そのものに履歴としての価値があるという理由で、これは保管庫についての主張であって個々の維持者についての評価ではない。
  • ファイル名の再利用も止める。プロジェクトを消してから同じ名前で作り直しても、以前に使われたファイル名は二度と使えないと記されている。npm の名前とバージョンの組の規定と向きが同じで、別の仕組みから同じ結論に着いている。
  • 悪意の通報の処理方式は違っていた。以前は運営側が使える手段がプロジェクトをデータベースから丸ごと消すこと一つで、その措置に名前の再利用禁止がよく伴っていたと告知に書かれている。その方式の問題として挙げられたのが取り消しが事実上できないという点だった。

そこで導入されたのが隔離という中間状態だ。隔離されたプロジェクトはインストール用の索引から外れて入れられなくなるが、誤分類だった場合には戻せる。完全削除しかなかった状態に、戻せる段階が新しく作られたことになる。

二つのレジストリを並べると軸が見える。片方は場所に標識を立てる方式で、もう片方は場所を片づけて施錠する方式だ。処理の形はほぼ逆だが、共通点が一つある。どちらでもその名前は誰でも取れるように開いていない。危険の重心は名前の側ではなく参照の側にあり、それはどちらのレジストリが処理していても変わらない。

要求が届き続ける理由 - 参照が残っている

インストール要求の一件は、誰かがいまその名前を打ったという意味ではない。ほとんどはすでにどこかに書かれていた名前がそのまま読まれた結果だ。要求を作るのは人の判断ではなくファイルの中身である。

この区別が立つと「なぜまだインストールされるのか」という問いの形が変わる。答えるべきは人の不注意ではなく、どのファイルがその名前を掴んでいて、そのファイルはなぜ更新されないのかだ。更新されないことにはたいてい理由があり、その理由が技術的に妥当な場合も多い。タグは定義上書き換わらないほうがよく、過去のビルドを再現するには古い複製が残っていなければならない。どちらも怠慢ではない。

削除が直せないのがまさにこの「書かれている」ことだ。レジストリで何をしても自分のリポジトリのロックファイルの一行はそのままだ。だから対策の位置も移る。レジストリが何を消したかを追う代わりに、自分の側に残った参照を数えることが先になる。そしてそれは、読むだけで最後まで進む作業だ。

参照が残る層と、各層が更新されない理由

参照が残る場所は一か所ではない。層ごとに更新されない理由が違い、理由が違えばすべきことも変わる。

機械が読む場所

前の五つの層は人が触らなくても自分で要求を作る。集計に入る要求の大半をこれらが作っていると見るほうが自然だ。人の注意ではなく時刻表で動いているからである。

人が読む場所

後ろの三つの層は要求を直接は作らないが、新しい参照を作り続ける。文書に一行残っていれば、それを読んだ人が新しいリポジトリに同じ一行を書く。前の層が今週の要求を作るなら、後ろの層は来期の要求を作る。

残る場所そこに書かれているものなぜ更新されないのか読むだけで確かめる方法
ロックファイル名前・バージョン・解決済みアドレス・完全性ハッシュ更新は依存を上げるときにしか起きず、その更新自体が回帰の危険として扱われて先送りされるロックファイルで名前の文字列を探し、その項目のアドレスとハッシュを一緒に読む
統合されていないブランチその時点のマニフェストとロックファイル全体統合されるか削除されるまでそのまま残る。古いブランチほど主がいないいま見ているブランチだけでなく、リポジトリの全参照を対象に文字列を探す
タグとリリース出荷時点で固定された依存一式タグは定義上書き換わらないほうがよい。書き換えれば再現性が壊れるタグが指しているツリーのマニフェストを読む

表を縦に読むと規則が一つ出てくる。更新されない理由の半分は欠陥ではなく設計だ。タグが変わらないのも、プロキシが複製を掴んでいるのも、再現性のためにそう作ったものである。だからこれらの層を「片づけるべき散らかり」としてだけ見ると、衛生の名のもとに再現性を壊す方向へ行く。層ごとに別の判断が要り、その判断が「消す」であることはむしろ少ない。

週に何回という値は何を数えた数字か

npm がダウンロード集計を説明して示した定義は短い。ダウンロード数はtarball を返した HTTP 200 応答の数だ。人が何人かも数えないし、インストールが成功したかも数えない。応答の数である。

そこに何が一緒に入るのかも同じ文書が記している。自動ビルドサーバーが出した要求、ミラーが同期して出した要求、すべてのパッケージをなめていく解析用ロボットの要求が全部含まれる。除かない理由も並んでいる。自動の要求を正確に見分けること自体が難しく、ビルド道具のように自動の要求がそのまま実際の利用であるパッケージもあるからだ。そして同じ文書が釘を刺す。この値は絶対値ではなく、パッケージの利用者数と同じものでは決してない。一日50回を超えない値は背景の雑音と区別しにくい、というおおよその下限も添えられている。

要求の性格集計に入るか人のインストールかこの件で値をどちらへ押すか
開発者が新しく入れる入るそうだ基準線。本当に数えたいのはこれだ
CI がビルドごとに取ってくる入る違う大きく膨らませる。リポジトリ一つで一日数十件を作りうる
ミラー・プロキシの同期入る違う膨らませる。名前一つがミラーの数だけ掛け算される
全数収集ロボット・研究用の走査入る違う膨らませる。標識が立った名前ほど調査の対象になって増える
セキュリティ走査器のメタデータ照会tarball を取るときだけ入る違う道具によって違う。方向を決められない
ローカルキャッシュで完結したインストール入らないそうだ減らす。実際の人のインストールを数え落とす
社内プロキシがキャッシュで応答入らないそうだ減らす。組織が大きいほど多く数え落とす

最後の二行がこの表の要点だ。この値は一方向にだけずれるのではない。自動の要求のせいで膨らみながら、同時にキャッシュで済んだ実際のインストールを取りこぼして縮む。二つの誤差の大きさをそれぞれ知らない状態では、方向を決めて補正することもできない。「実際にはこれより少ないはずだ」も「実際にはこれより多いはずだ」も根拠なしには言えないということで、この二文はあまりにも簡単に書かれてしまう。

その数字から読めるものと読めないもの

だからといってこの値が無用なわけではない。何を問うかによって答えになったりならなかったりするので、両方を書き出しておく価値がある。

まず読めるものから立てる。

  • 0 ではない。これ一つは確かだ。その名前へ向かう要求の経路がまだ生きているという事実は、値がいくつであっても成り立つ。
  • 同じ方式で数えた値どうしの趨勢。先週と今週を同じ方法で数えたなら、増えているのか減っているのかは読める。絶対値は信じられなくても傾きは見える。
  • 桁の違い。週に数件と週に数千件は別の状態だ。二倍ほどの誤差があっても桁はひっくり返らない。

読めないものはこうだ。

  • 何人が晒されたのか。応答の数から人の数へ渡る換算係数が存在しない。それを勝手に作るところから、この話題の悪い報じ方はたいてい始まる。
  • いくつの組織が影響を受けたのか。一つの組織が数千件を作ることもあれば、数百の組織がキャッシュの後ろに隠れて一件も作らないこともある。
  • そのうち何件が実際にコードを走らせたのか。この件の名前群にはすでにセキュリティの標識が立っているので、要求が持ち帰ったのは悪意あるコードではなく標識だ。

三つ目の項目がこの数字の性格を変える。したがってこの値は「いま何人が感染しているのか」の指標ではなく、「いくつの経路がまだその名前を指しているのか」の代理指標として読むほうが正確だ。警告信号としての値打ちはその分類替えのあとも残る。今日標識を持ち帰る経路は、明日ほかの名前から本物のコードを持ち帰りうる経路と同じ種類の経路だからで、そこが気に掛ける理由になる。

タイポスクワッティングと同じ問題ではない

この二つはよく一括りで語られるが、狙う場所が逆だ。混ぜると対策が両方とも緩くなる。

打ち間違い狙いはまだ誰も書いていない名前へ向かう。人が手で打つときに滑りそうな場所を狙うもので、成立の条件は「誰かが新しく打ち間違える」ことだ。だからこそ類似度検査と名前リストが実際によく効く。一方この記事の状況は逆で、名前はすでに正確に書かれていて、書かれた場所が更新されない。新しく発生する打ち間違いが一件もなくても要求は出続ける。

ここに最近の軸が一つ足される。コード補助の道具が存在しないパッケージ名を作り出す現象だ。発端になったリポジトリが引いている値では、生成された名前の 19.7% が実在しない名前で、同じ要求をもう一度回したときそのうち 43% が同じ名前でまた出てきた。この軸で重要なのは割合ではなく反復性だ。毎回違う名前が出るならそれは雑音に近いが、同じ名前が繰り返し出るならその名前は事実上固定された住所になる。

軸打ち間違い狙い消された名前と残った参照道具が作り出した名前

真ん中の列と右の列が出会う場所が、この一覧が実際に立っている地点だ。道具が作り出した名前がすでにセキュリティ上の理由で下ろされた名前と重なりうるということ。だから調査の方式が「名前を崩す規則で候補を作ってレジストリと突き合わせる」であり、その結果が空白ではなくセキュリティの標識に当たったのである。

名前リストで止めると漏れる場所

「危険な名前の一覧を作って遮断する」という対策が真っ先に浮かぶが、この問題ではその手段が立つ足場が狭い。漏れる地点が四か所ある。

  • リストは過去形だ。すでに知られた名前しか入らない。新しい標識が立った瞬間からその名前はリストの外にあり、リストを更新する周期がそのまま開いた窓の幅になる。
  • リストは正確な文字列に掛かる。スコープの有無、大文字小文字、区切り文字ひとつが違うだけで抜けていく。この問題の候補名がそもそもそうした変形で作られたことを思うと、狙いがかなり根本的にずれている。
  • リストはたいてい直接依存だけをなめる。マニフェストに書かれた名前は見るが、ロックファイルの深いところから間接的に引かれてくる名前は取りこぼしやすい。実際に残っている参照のかなりの部分がそちらにある。
  • リストは名前を見て中身を見ない。同じ名前の別のバージョンが入ってくる場合、名前さえ合っていれば素通りする。

だから名前を対象にする防御は補助信号の位置に置く。軸は別のところにある。何が入ってくるかを名前ではなく中身で固定する側だ。信頼の鎖がどこから始まるのかという一段下の問いはブートストラップの信頼が崩れる場所で別に扱った。

防御手段が止めるものと止められないもの

手段ごとに止まる場所と抜ける場所が決まっている。表に立てておくと、どの二つを重ねるべきかが見えてくる。

手段止めるもの止められないもの払う代価
ロックファイルの完全性ハッシュ同じ座標に別の中身が入る場合。転送中に変わった場合最初からその中身が悪意あるものだった場合。ハッシュごと更新される場合ほぼない。ロックファイルを収めておいてそのまま使えばよい
ロックファイルどおりの再現インストールビルドごとにツリーが静かに変わることロックファイルにすでに書かれている名前依存の更新が別立ての計画された作業になる
バージョン固定と検討済みの更新予告のない上位バージョンの流入固定したそのバージョン自体の欠陥更新の遅れ。セキュリティ修正も一緒に遅れる
プライベートレジストリの許可リストリスト外の名前が組織の中へ入ってくることリストの中にすでに入っている名前リストの運用費用。新しい依存ごとに承認の手続き
インストールスクリプトの遮断インストール時点で起きるコードの実行アプリケーションの実行中に回るコードインストールスクリプトに依存するパッケージが壊れる
隔離されたビルド環境資格情報と内部網への広がり成果物そのものの汚染環境の構成と維持の費用

依存一覧との突き合わせ何が入っているのか分からない状態一覧を作ったあとに変わったもの一覧の鮮度を保つ作業

表を縦に読むと規則が一つ落ちてくる。名前を見る手段はすべて「リストの中にすでにある名前」で無力になり、中身を固定する手段はすべて「最初からその中身だった場合」で無力になる。二種類を重ねなければならない理由がこれだ。どちらか一方だけでは反対側が丸ごと開き、その隙間は狭くない。

付け加えると、更新を先送りする選択にも代価がある。何をいつ上げるかを判断する側の話はリリースノートの読み方で扱った。バージョンを掴んでいることはこの問題では安全な側だが別の問題では逆で、だから常時の規則にはできない。

読み取りだけで自分のリポジトリを点検する順序

ここからは実際の順序だ。判定に要るものはすべて読み取りから出る。インストールも、削除も、公開も要らない。

ロックファイルから読む三つ

ロックファイルの項目一つには三つが入っていて、三つを一緒に読んでこそ判定が立つ。どのバージョンで固まったのか、どこから受け取るのか、受け取ったものがそれかを検証する値は何か。

# package-lock.json の項目一つに入っている三つ
"node_modules/<名前>": {
  "version":   "1.2.3",                        # どのバージョンで固まったのか
  "resolved":  "https://registry.example/...", # どこから受け取るのか
  "integrity": "sha512-..."                    # 受け取ったものがそれかを検証する値
}

# 導入済みのツリーを読む - 何も変えない
npm ls --all              # ツリー全体の実際の名前とバージョン
npm ls <名前>              # その名前がツリーのどこに掛かっているか
npm explain <名前>         # 誰がそれを引いてきたのかを経路で

リポジトリ全体で参照を数える方法

ロックファイル一つだけを見ると、いま取り出しているブランチの状態しか見えない。残った参照はその外にある場合が多く、だから二回目は全参照へ広げる。

# 作業ツリーに残っている参照
grep -rn '"<名前>"' --include=package.json .
grep -rn '"<名前>"' --include=package-lock.json .

# 統合されていないブランチとタグまで - 取得はせず名前だけ見る
git grep -n '<名前>' -- '*.json'
git grep -n '<名前>' $(git for-each-ref --format='%(refname:short)' refs/heads)

# レジストリに何が立っているか - メタデータだけ読む
npm view <名前> --json    # 導入はしない。メタデータだけ取ってくる
npm view <名前> versions
順序何をするか何で判定するかここで止まるべき場合
1ロックファイルがリポジトリに収められているか見るファイルの存在と最後に更新された時点なければその先が全部無意味だ。ロックファイルを収めるのが先になる
2ロックファイルでその名前の文字列を探す一致する項目があるかどうかなくても終わりではない。間接依存までツリーで見直す
3その項目の解決済みアドレスを読む公開レジストリなのか社内プロキシなのかアドレスが想定と違えば依存の設定から見る
4完全性ハッシュが埋まっているか見る項目ごとのハッシュ値の有無空の項目があれば、その項目は固定されていない状態だ
5導入済みのツリーから実際の名前とバージョンを読むツリーの出力とロックファイルが一致するか食い違えばロックファイルどおりに導入されていないという意味だ
6その名前を誰が引いてくるのかを経路で見る依存経路の先頭にある直接依存経路が複数なら全部書き留める。一つだけ直しても残る
7統合されていないブランチとタグに残っているか見る全参照を対象にした文字列の検索残っていればそのブランチの扱いの方針を先に決める
8レジストリ側に何が立っているかメタデータだけ読むセキュリティ標識の有無と廃止のお知らせ文標識が立っていればその名前は参照整理の対象だ

八つの段階のどこでも状態を変えない。そしてこの順序の成果物は「安全だ」という判定ではなく、参照が残っている場所の一覧だ。一覧が出てから、層ごとに何をするかを決める作業が始まる。タグはそのままにして文書だけ直すこともできるし、プロキシのキャッシュは残したまま新しいビルドからだけ止めることもできる。それらは別の判断で、別々に下されるに値する。

まとめ - 四つの文

ここまでを四つの文に縮めるとこうなる。

  • 削除はコードを断ち、参照は断たない。レジストリで何をしても自分のロックファイルの一行はそのままだ。
  • 少なくとも npm で消された名前は空いていない。処理手順にその場所へ標識を立てる段階が文書として入っていて、それがその名前への要求が持ち帰るものを変える。
  • 週に何回という値は応答の数であって人の数ではない。自動の要求のせいで膨らみキャッシュのせいで縮むので、晒された人数の推定にそのまま使えない。
  • 名前を見る手段と中身を固定する手段は別の場所で漏れる。だから選び合うのではなく重ねる。

実務に移すと残る文は一つだ。いちばん安上がりなのは、ロックファイルを収められた状態に置き、その中の解決済みアドレスと完全性ハッシュを一度読んでみることだ。名前リストを増やすことより先に来るし、費用は比べものにならないほど低い。

確認できなかったこと

以下の項目はこの記事の調査範囲のなかで一次資料から結論を出せなかった。根拠が揃うまで断定しない。

  • セキュリティ標識が恒久的なのか — npm の公開文書は悪意判定の際に標識を公開するという段階までしか記していない。その標識が恒久的に維持されるのか、どんな条件で別の人がその名前を引き継げるのかに当たる文は方針文書に見当たらなかった。だから本文は「名前は空かない」までを確定した範囲として扱っている。
  • 一覧のインストール数がどの窓で集計された値なのか — 一覧文書には列の見出しだけがあり、出所を示す文がない。道具側の文書には npm のダウンロード照会を使い6時間のキャッシュを置くという記述があるが、一覧の各値がどの期間を取ったものかまでは文としてつながらず、確定できていない。
  • 19.7% と 43% の元の出所 — 二つの値は発端になったリポジトリが引用している値だ。元の研究の本文と測定条件は今回の調査範囲の外なので開いておらず、どのモデルとどのプロンプト集合だったのかはここでは未確認のままにする。
  • 見出しの 35 と文書の 36 のどちらがどの週の値なのか — 一覧が毎週再生成され、過去版の履歴が文書に残っていないため突き合わせられなかった。本文は二つを別の週の値として扱っている。
  • ほかの言語生態系の処理方式 — Rust・Ruby・Go 側のレジストリの削除と名前の扱いの方針は、発端になった道具が扱っておらず今回の範囲にも入れていない。この記事の比較は挙げた二つのレジストリに限られる。
  • 組織のなかで実際にどの層が要求を作っているのか — これは公開文書で答えの出る問題ではない。各組織のプロキシの接続記録とビルドの記録からしか答えは出ず、本文の層の区分はその答えを探す順序であって割合の推定ではない。
