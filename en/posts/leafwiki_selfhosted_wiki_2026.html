LeafWiki: A Self-Hosted Wiki That Runs From a Single Binary, No Server or Database

How it stacks up against MediaWiki, Wiki.js, DokuWiki, and Confluence, and where the real trade-offs are

Jul 18, 2026 Dev & Infra

Intro: Why "Lightweight Wiki" Is Back on the Table

Over the past few years, knowledge-management tools have split into two extremes. On one side sit Notion and Confluence, the do-everything SaaS suites; on the other, Obsidian and Logseq, the local-first personal note apps. What actually got squeezed out was the middle ground the word "wiki" used to occupy: something a team shares without a heavy operational tax. MediaWiki forces the stack built to run Wikipedia onto a team of eight, and Confluence trades a subscription fee for handing your documents to a vendor's servers.

Into that gap stepped LeafWiki. Built by developer perber, this open-source wiki has 837 GitHub stars and a v0.11.4 release as of July 2026, and it summarizes itself in one line: a single Go binary, SQLite, and markdown stored on disk. This piece starts from LeafWiki's appearance on GeekNews (hada.io) and steps back to ask what has actually changed across the self-hosted wiki landscape, and where the trade-offs still are. Facts here are grounded in LeafWiki's official site, its GitHub repository, and the GitHub API as of July 18, 2026.

1. What Is LeafWiki - A 1-Binary, Coding-Friendly Self-Hosted Wiki

1.1 Core Specs and Stack

LeafWiki's backend is written in Go (roughly 60.8% of the repository by language), with a TypeScript frontend built on React and Vite (about 35.4%). It uses embedded SQLite for state, but the actual page content is stored as plain markdown files on disk - meaning you can read the content with grep or a text editor even with the app turned off. That "content survives without the app" design is the project's core philosophy. The feature list is not thin either: tree-based folder navigation, full-text search with tag filtering, backlinks and broken-link tracking, a live split-screen markdown editor, [[wikilink]] autocomplete, dark mode, and Mermaid diagrams plus KaTeX math (inline math with $...$ is not yet supported, block math is). Revision history and automatic link updates on page rename are opt-in behind the --enable-revision and --enable-link-refactor flags, and as of v0.11.3 there is experimental Git backup support.

1.2 Install and Deploy - One Docker Line, One Binary

There are three install paths: a single Docker command (just set the port, data volume, and admin password), an install script for Linux/Raspberry Pi OS (curl and run), or downloading a binary directly for Linux, Windows, or macOS. A live demo is available at demo.leafwiki.com, and the license is MIT. Access control has three modes - login required, public read with login-to-edit, or authentication disabled - with role-based permissions split into admin, editor, and viewer. One notable detail: LeafWiki has announced a free hosted beta with 10 slots starting September 2026. A fully self-hosted tool experimenting with a managed option is a sign that "self-hosted versus SaaS" is no longer a strict binary.

2. Why Self-Hosted Wiki Demand Is Rising Again

2.1 The Resurgence of Team Knowledge Bases and Personal Notes

Notion's cost scales per seat as a team grows, and Obsidian was never designed with team collaboration as a first-class scenario. Tools trying to fill that gap have multiplied recently, and it is no coincidence that LeafWiki appeared around the same window as other self-hosted tools I have covered on BrainDetox, like Chatto (a self-hosted team chat app) and Odysseus (a self-hosted AI workspace). Demand for tools that are shared but operationally light is rising across notes, chat, and wikis all at once.

2.2 The AI-Era Paradox: Knowledge You Want to Search Has to Be Yours to Keep

Paradoxically, the more AI tools become part of daily work, the heavier the question "where does my knowledge actually live" gets. As more developers try to search, summarize, and query their own documents with local LLMs or RAG (retrieval-augmented generation), whether that content sits as plain markdown on disk or behind a closed SaaS API now determines how easily it can plug into an AI pipeline. A tool like LeafWiki, where content is just .md files, plugs directly into grep, local embedding indexes, and personal RAG pipelines. This is less nostalgia than a practical reversion driven by how people actually use AI today.

3. The Weight of Existing Wikis - MediaWiki, Wiki.js, DokuWiki, Confluence

3.1 MediaWiki - Overkill From the Wikipedia Engine

MediaWiki, running on PHP and MySQL/MariaDB, is the most famous wiki engine in the world. That it is the actual software behind Wikipedia is proof of its reliability - and also the price of that reliability. A stack that requires a web server, a PHP runtime, a separate database server, and extension management was built to handle millions of pages and thousands of concurrent users, not an 8-person team's runbook. Small teams that adopt MediaWiki usually spend more time learning the extension ecosystem and permission model than actually installing it.

3.2 Wiki.js - Modern but Heavy, and Recently Slower to Ship

Wiki.js is a relatively modern wiki built on Node.js and Vue.js with PostgreSQL (or another RDB). It supports multiple editors - markdown, WYSIWYG, HTML - and even Git sync, which earned it a reputation for a while as "the modern alternative to DokuWiki." But it still requires running a separate Node runtime and SQL database, so it is lighter than MediaWiki only in degree, not in kind, and remains a multi-component stack. Observers have also noted that commit activity on the core repository visibly slowed in the first half of 2026 - a maintenance risk worth weighing if you are considering adoption.

3.3 DokuWiki - The Closest Predecessor, Still Needs a PHP Runtime

DokuWiki is arguably LeafWiki's philosophical predecessor. For nearly 20 years it has stored pages as plain files with no external database, earning long-term goodwill for the simplicity of "backup is just copying a directory." But DokuWiki still needs a PHP runtime and a web server (Apache/Nginx) - it is not a true single binary in the sense of needing zero runtime installation. Its UI shows its age, too. LeafWiki can be read as the next generation of that "no database" philosophy, compressing even the PHP-and-web-server install step into one Go binary.

3.4 Confluence - SaaS Convenience Traded for Data Sovereignty

Atlassian Confluence sells both cloud and data-center editions as a commercial wiki. There is effectively no install burden - just sign up - and it brings strong enterprise features like approval workflows, fine-grained permissions, and Jira integration. The cost is the subscription fee, and the fact that as long as you run the cloud edition, your documents live on the vendor's servers. For small teams, individuals, and organizations sensitive to data leaving their premises - government, healthcare - that becomes an entry barrier.

4. What the "Single Binary" Approach Actually Gives You

4.1 Deployment Becomes Moving One File

Deploying a traditional web app means installing a runtime (Node, PHP, Python), managing dependencies (package managers, version conflicts), provisioning a database, and configuring a reverse proxy. A Go-compiled single binary pushes most of that into compile time; at runtime, all you need is one binary and a data directory. That is why LeafWiki's Docker command fits on one line and its install script is a single curl call. For a solo team or side project without much server-ops experience, that difference is the real barrier between trying it and not.

4.2 Zero Dependencies and Portability - From Raspberry Pi to Air-Gapped Networks

Go's easy cross-compilation means the same source can produce Linux, Windows, macOS, and ARM (including Raspberry Pi) binaries. That LeafWiki officially ships a Raspberry Pi OS install script means this portability is used in practice, not just theory. Being able to run it by moving a single binary file even in an air-gapped, internet-blocked environment is especially attractive to closed networks - manufacturing floors, research labs - that cannot reach external package repositories. This is not unique to LeafWiki; it is a shared strength of the Go/Rust tooling world in general, but it is still uncommon in the wiki category.

4.3 Why Backup Is Just Copying a Directory

LeafWiki manages metadata (structure, permissions, tags) in SQLite while storing page bodies as plain markdown. As a result, backup ends with copying the whole data directory - no separate mysqldump or database export step needed. The experimental Git backup feature from v0.11.3 goes a step further, letting document change history itself live as Git commits. LeafWiki inherits DokuWiki's 20-year-proven simplicity of "backup is just a copy," and layers a familiar tool - Git - on top of it.

5. Trade-offs - Scalability, Live Co-editing, Plugin Ecosystem

5.1 The Limits of Scale

LeafWiki's own documentation states it is not a fit for enterprise-grade permission management or Confluence/Notion-scale requirements. SQLite is an excellent embedded database, but it has not yet been widely proven at heavy concurrent writes or tens of thousands of pages. Compared with two decades of large-scale operational know-how behind MediaWiki, LeafWiki is still closer to an early, real-world-validation stage - a v0.x project with 837 stars.

5.2 No Real-Time Collaborative Editing

The project explicitly states that real-time collaborative editing is not a supported goal. There is auto-save and conflict detection, but that is different from the simultaneous-cursor editing you get in Google Docs or Notion. A team where multiple people edit the same document at once will hit a wall here.

5.3 No Plugin Ecosystem

MediaWiki has thousands of extensions, and Wiki.js supports multiple renderers and auth modules. LeafWiki takes the opposite bet: minimalism, doing the core well. Having almost no extension points means less maintenance burden, but it also means it is not a realistic option for organizations that need a specific workflow - SSO integration, a custom approval process - baked in.

6. Who Should Actually Use It

6.1 Where It Fits Well

Personal knowledge bases and engineering notes, internal runbooks and operations manuals for teams of roughly 5-30 people, and organizations trying to structure assets they have already accumulated in markdown or Obsidian are all a good fit. Low-power edge devices (Raspberry Pi and similar) or air-gapped, offline environments are another strong case - being able to deploy offline with one install script and one binary is especially valuable there.

6.2 Where to Be Cautious

Regulated-industry documentation that requires approval workflows, large organizational wikis with hundreds of concurrent users, teams whose actual workflow depends on real-time co-editing, and mission-critical documentation requiring years of proven maturity are all cases where sticking with a proven tool like MediaWiki or Confluence remains the safer call for now.

7. Self-Hosted vs. SaaS Wiki - Data Sovereignty and Cost

The choice between self-hosting and a SaaS wiki ultimately comes down to who is responsible for what. SaaS (Confluence, Notion, etc.) has the vendor take responsibility for availability, backup, and security patching, in exchange for your documents living on the vendor's servers and cost scaling with seat count. That structure is a burden for regulated industries, organizations wary of data leaving their premises, or simply individuals and small teams who want to know exactly where their documents are. Self-hosting flips this: data never leaves infrastructure you control and cost stays roughly flat at server rental levels, but availability, backup, and security become entirely your responsibility. A single-binary tool like LeafWiki substantially lowers that "operator responsibility" burden, which makes self-hosting a far more realistic choice than it used to be. Privacy is not free, though - someone still needs to actually run backups on a schedule, keep the server patched, and recover from failures.

8. The Markdown-Based Documentation Trend, and Where LeafWiki Sits In It

Lining up recent threads I have covered on BrainDetox reveals a pattern. My analysis of the Obsidian ecosystem conflict around Files.md, Logseq, and Excalidraw was really about whether note assets stay in an open format. My analysis of Odysseus, a self-hosted AI workspace, was an attempt to keep the AI workspace itself local. My analysis of Chatto, a self-hosted team chat app, applied the same instinct to team chat. LeafWiki applies this same current to the wiki category - arguably the oldest and heaviest of the bunch. The common thread is clear: content stays plain text, markdown, open format; execution stays minimal-dependency. That this combination is spreading beyond note apps into team chat, AI workspaces, and now wikis is not a one-off fad - it reads as one branch of the larger local-first software movement.

Conclusion: Who Should Use LeafWiki Today

LeafWiki grew out of a very practical frustration - "does a wiki really need to be this heavy?" - and it stays honest about its scope. For personal knowledge bases, runbooks for a 5-30 person team, organizations that already have markdown assets piled up, and low-power or air-gapped environments, it is an appealing option right now. On the other hand, if real-time co-editing is a requirement, or an organization needs approval workflows and fine-grained permissions, or documentation is mission-critical and needs years of proven maturity, it is still too early - sticking with a proven tool like MediaWiki or Confluence is the safer bet. With 837 stars and a v0.11.4 tag, LeafWiki is still a pre-1.0 project. But the combination of "single binary plus plain markdown" looks like one of the most compelling next-generation answers the wiki category has seen since DokuWiki. As of July 2026, if you are a small team that wants to hold your own data, a short test on the demo (demo.leafwiki.com) should tell you quickly whether it fits.
