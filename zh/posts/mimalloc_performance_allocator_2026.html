引言: 为何要关心内存分配器 - 看不见的性能杠杆

2026年5月24日，microsoft/mimalloc GitHub 仓库作为话题出现在 news.hada.io 上(当时17分)。一个在2019年公开设计的项目再次受到关注，背景是分配器选择决定性能的领域——长时间运行的服务器、高并发工作负载和语言运行时——仍在不断扩大。截至2026年9月29日，mimalloc 以 v3.5.3(2026-09-16)为推荐版本，仓库当天仍有提交合入，维护相当活跃。

大多数开发者在调用 malloc 和 free 时并不关心背后运行的是什么算法，使用 Rust、Go、Java 这类由运行时隐藏分配的语言时更是如此。但在长时间运行的服务器、高并发工作负载和对内存碎片敏感的系统中，分配器选择会同时改变 CPU 使用率、RSS(常驻内存)、尾延迟和碎片率。不过效果大小因工作负载而差异很大。mimalloc README 本身也写道：通用分配器不存在最优算法，任何分配器通常都能构造出它表现不佳的工作负载。这就是本文强调测量流程而非单一数字的原因。

1. mimalloc 是什么 - 微软研究院出品，MIT 许可证

mimalloc(读作 "me-malloc")是 Daan Leijen 最初为 Koka 和 Lean 语言运行时开发的通用内存分配器。其设计记录在2019年6月的微软研究院技术报告《Mimalloc: Free List Sharding in Action》(MSR-TR-2019-18，作者 Daan Leijen、Benjamin Zorn、Leonardo de Moura)中。官方仓库是 github.com/microsoft/mimalloc，许可证为 MIT。它直接替换标准的 malloc、free、realloc、calloc，据 README 所述代码约1万行，已移植到 Windows、macOS、Linux、WASM、多种 BSD、Haiku、MUSL 等平台。它可以构建为共享库、静态库和单个目标文件，也可以不用 cmake，直接把 src/static.c 这一个文件加入项目编译。

它与其他分配器的区别主要有三点。第一，drop-in 兼容：在 Linux 和 BSD 上用 LD_PRELOAD=/usr/lib/libmimalloc.so myprogram 即可在不重新编译的情况下接入，macOS 使用 DYLD_INSERT_LIBRARIES，Windows 使用单独的重定向 DLL。第二，free list sharding：不是每个尺寸类一个大的 free list，而是每个 mimalloc 页各有小列表，并且每页再分为本线程释放用和其他线程释放用两种列表。第三，secure 模式：用 -DMI_SECURE=ON 构建会加入保护页、随机化分配和 free list 指针编码，README 给出的性能开销是其基准测试平均约10%。

截至2026年9月29日，v3.5.3(2026-09-16)为推荐版本，v2.5.2(2026-09-12)标为 “stable, legacy”，v1.15.2(2026-09-12)为 legacy。新开发主要在 v3 上进行，v1 和 v2 以安全与缺陷修复方式维护。本文首次发布时写的是“v2.x 为稳定版、v3.x 为开发线”，如今 v3 已是推荐版本。据 README，v3 改进了线程之间的内存共享，在某些大型工作负载上可能显著减少内存占用，并支持可从任意线程分配的 first-class heap。仓库 GitHub 星标为13,410(2026-09-29，GitHub API)，2026年4至8月的发布说明多次记录了通过 LLM 审计发现的缺陷与安全修复。

3. mimalloc 的5大核心设计

把 README 和技术报告中的设计归纳为5点。

3-1) Free list sharding(按页的 free list)

不是每个尺寸类维护一个大的 free list，而是每个“mimalloc 页”维护自己的小 free list。一个页只存放同一尺寸类的块，在 64 位系统上通常为 64KiB。README 解释说，这样在时间上相近分配的对象在内存中也彼此靠近，局部性更好，碎片更少。

3-2) 多重分片与小对象路径

这是 README 称为“大想法”的部分。每页的列表再拆分：一个用于本线程的释放，另一个用于来自其他线程的并发释放。因此其他线程的释放只需一次 CAS，列表分散成数千个，竞争不会集中在一处。小对象还有专用路径：v3 README 建议在能保证大小小于 MI_SMALL_SIZE_MAX(1KiB)时使用 mi_malloc_small 和 mi_free_small，速度更快。

3-3) Secure 模式(缓解堆漏洞)

用 -DMI_SECURE=ON 构建会增加以下保护。(a) 用保护页包围内部页元数据，使缓冲区溢出无法触及元数据。(b) 用每页密钥对 free list 指针编码，防止用已知指针覆写，并检测堆损坏。(c) 检测并忽略 double free。(d) 随机化 free list 初始化顺序和分配位置。-DMI_SECURE=FULL 还会在每个 64KiB 页末尾放置保护页，但开销更大，且可能触及 Linux 的 VMA 上限，README 一般不推荐。性能开销为 README 基准测试平均约10%。README 还补充说，这些是缓解措施而非保证，应放在整体安全策略中评估。

3-4) 低碎片与 eager page purging

页变空时(分片使这种情况更常见)，其内存会被告知操作系统为未使用(reset 或 decommit)，从而降低实际内存压力和碎片，对长时间运行的程序尤其有意义。README 还说明元数据开销约为0.2%、不会出现 blowup、除操作系统调用外最坏分配时间有界。不过 README 也坦言公开基准测试没有测量超大规模的长时间运行服务器负载，因此长期运行下的碎片需要自行测量。

3-5) Drop-in 兼容(LD_PRELOAD)

README 把动态 override 作为替换标准 malloc 的推荐方式。无需重新编译现有二进制，一行 LD_PRELOAD=/usr/lib/libmimalloc.so myserver 即可生效，同时设置 MIMALLOC_VERBOSE=1 可以确认 mimalloc 确实在使用。回退只需去掉环境变量。jemalloc 和 tcmalloc 也能用同样的方式，但代码精简、可单文件构建降低了 mimalloc 的接入成本。

4. 基准测试分析 - 官方表格说了什么、没说什么

本节所有数字均出自 mimalloc README 的 “Performance” 一节。首次发布时写的“比 glibc 快 1.5~3 倍”“32~64 线程下吞吐量 2 倍以上”“比 jemalloc 快 10~30%”在原始表格中找不到，已删除。

4-1) 测试条件与局限

README 性能一节最后更新于2021-01-30。在16 核 AMD 5950x(Ubuntu 20.04、glibc 2.31、GCC 9.3.0)和36 核 Intel Xeon(AWS c5.18xlarge)上，把 mimalloc v1.7.0、v2.0.0(当时为 beta)和 secure 模式与 tcmalloc(gperftools 2.8.1)、jemalloc 5.2.1、tbb、rpmalloc 1.4.1、Hoard、Mesh、glibc 进行了比较。2026-09-01 又加了一条注释：这些结果已经较旧，其他分配器此后也有改进。基准测试套件以 mimalloc-bench 单独公开。

4-2) 各基准测试结果要点

基准测试性质README 记录的结果
cfrac单线程，大量小而短寿命的分配所有分配器都表现良好，mimalloc 略快于 tcmalloc 和 jemalloc
leanNLean 定理证明器并行编译自身标准库比 tcmalloc 快13%
redis单线程服务器大多数分配器表现良好
larsonN模拟分配与释放跨线程进行的服务器明显快于 tcmalloc 和 jemalloc
sh6bench分配密集型基准测试比 jemalloc 快 2.5 倍以上
xmalloc-testN部分线程只分配、部分线程只释放大幅领先(rpmalloc、tbb、glibc 扩展性也不错)

总体趋势是：单线程和常见模式下差距很小，对象跨线程迁移越多，mimalloc 的优势越大。这与按页设置并发释放列表的设计相吻合。

4-3) 大对象与长时间运行负载 - 公开表格未覆盖的领域

README 写明这些基准测试没有测量超大规模的长时间运行服务器负载，也没有测量分配的最坏延迟。以数 MB 缓冲区为主的负载，或存活数天的对象很多的负载，哪个分配器更好无法从公开表格判断，只能在自己的环境中直接测量。

4-4) 与 jemalloc 比较时

首次发布时“长寿命对象场景下 jemalloc 可能占优”是没有出处的倾向性描述，因此不再作为事实保留。可以确认的是，README 称 jemalloc 和 tcmalloc 为用于 Chrome、FreeBSD 等世界最大规模系统的工业级分配器，并指出大多数分配器在 xmalloc-testN 上表现不佳。两者都是经过验证的选择，哪个更快需要在目标负载上测量。

4-5) 总结

一句话概括：“跨线程的分配与释放越多，公开基准测试中 mimalloc 的优势越大；单线程和常见模式差距很小；长时间运行和大对象负载无法凭公开资料判断。”这些数字是2021年测量的，结论是用自己工作负载的 trace 跑 mimalloc-bench 或自建基准测试。

5. 值得切换 mimalloc 的5个生产场景

以下是本文整理的“值得试用 mimalloc 的5个场景”。只要符合其中之一，就值得做 staging 压力测试。它们是挑选试验对象的标准，而不是性能保证。

5-1) 跨线程对象迁移频繁的多线程服务器

接收请求的线程与处理请求的线程不同，一个线程分配的内存由另一个线程释放。这正是 README 中 larsonN 和 xmalloc-testN 模拟的模式，也是 mimalloc 结果最突出的领域。相反，单线程服务器可能差距很小，正如 README 的 redis 结果所示。如果 CPU 剖析中出现 malloc、free 竞争，就是候选。

5-2) 语言运行时与解释器环境

mimalloc 起步于 Koka 和 Lean 运行时，README 说明它为运行时系统提供心跳和延迟释放钩子。CPython 也从 3.13 起默认内置 mimalloc(含自身修改)。大量产生短寿命对象的运行时或嵌入式解释器值得评估。

5-3) 内存缓慢增长的长时间运行负载

数天到数周不重启的服务如果 RSS 持续上升，分配器碎片是可能原因之一。mimalloc 的 eager page purging 和 MIMALLOC_PURGE_DELAY 是相关机制，jemalloc 也值得一并比较。请先排除真正的内存泄漏。

5-4) 安全敏感系统(mimalloc-secure)

对网络暴露或解析不受信任输入的服务。按 README，secure 构建平均开销约10%，高于本文首次发布时写的3~5%，因此宜先从性能有余量的服务开始。2026年8月的版本(v3.4.4、v3.5.0)记录了 secure 模式下 double free 与大小检查的加强，以及 double free 检测的提速。

5-5) Rust / C++ 项目的全局分配器替换

Rust 用一行 #[global_allocator] 即可把 mimalloc 设为全局分配器；C++ 在链接阶段替换后，按 README 的建议用 mimalloc-new-delete.h 覆盖 new 和 delete。编译期集成对各部署环境中 LD_PRELOAD 配置的依赖更小。

6. 语言级集成 - C/C++/Rust/Go/Java

根据官方文档整理各语言的集成难度。

6-1) C/C++ - LD_PRELOAD 或链接

Linux 和 BSD 使用 LD_PRELOAD=/usr/lib/libmimalloc.so，macOS 使用 DYLD_INSERT_LIBRARIES=/usr/lib/libmimalloc.dylib(可能受 shell 安全限制)，Windows 使用基于 mimalloc-redirect.dll 的重定向方式。构建期集成可以用 -lmimalloc 链接，或在 cmake 中 find_package(mimalloc) 后使用 target_link_libraries(myapp PUBLIC mimalloc)，也可以按 README 推荐的方式直接调用 mi_malloc API。C++ 只需在一个源文件中包含 mimalloc-new-delete.h。

6-2) Rust - GlobalAlloc 替换

使用 crates.io 上的 mimalloc crate(截至2026年9月29日最新为 0.1.52，2026-05-22 发布)。其仓库是 github.com/purpleprotocol/mimalloc_rust，是封装 microsoft/mimalloc 的社区包装库，并非微软直接发布的 crate。默认使用 mimalloc v3，需要 v2 时指定 features = ["v2"]。名称相近的 mimalloc-rust crate(lemonhx/mimalloc-rust，0.2.1，最后更新 2023-04-27)是另一个项目。完整代码见第7节。

6-3) Go - cgo 有限支持

正如其源码注释所说，Go 运行时分配器最初基于 tcmalloc，但已有很大差异，并不是可替换的结构。mimalloc 只能影响通过 cgo 调用的 C 库一侧的分配。若要替换 Go 核心部分，就得直接修改运行时，不建议这样做。

6-4) Java - 仅 JNI 范围

JVM 拥有自己的 GC 堆。mimalloc 只能影响 JVM 进程中的本机分配(如 JNI 库)，对普通 Java 对象无效。对 Java 服务而言，应先调整 GC 和堆设置，而不是替换分配器。

7. 实战集成示例 - Rust 全局分配器替换

用代码展示最常见的 Rust 集成方式，与 mimalloc crate README 的用法示例相同。

7-1) Cargo.toml 依赖

[dependencies]
mimalloc = "0.1"

# 可选: secure 模式
# mimalloc = { version = "0.1", features = ["secure"] }
# 可选: 使用 mimalloc v2(默认 v3)
# mimalloc = { version = "0.1", features = ["v2"] }

7-2) 在 main.rs 声明全局分配器

use mimalloc::MiMalloc;

#[global_allocator]
static GLOBAL: MiMalloc = MiMalloc;

fn main() {
    // 从此 Box、Vec、String 等所有标准分配都经过 mimalloc
    let v: Vec<i32> = (0..1_000_000).collect();
    println!("sum = {}", v.iter().sum::<i32>());
}

7-3) 构建与观测

cargo build --release

# 通过 mimalloc 的输出信息确认已生效
MIMALLOC_VERBOSE=1 ./target/release/myapp

# 查看 RSS(Linux)
ps -o pid,rss,command -p $(pgrep myapp)

如 crate README 所述，构建时需要 C 编译器(gcc 或 clang)，因此 CI 镜像需预先安装 build-essential 或同等软件包。构建时间和 RSS 的变化因工作负载而异，请直接测量，不要预设数字。

提示 - 要在同一份代码上比较 mimalloc 与默认分配器，可以分别构建带 #[global_allocator] 声明和不带声明的版本，在相同负载下测量。替换和回退都如此简单，本身就是值得一试的最大理由。

9. 风险与限制 - 实话实说

mimalloc 也并不完美。主要风险如下。

9-1) RSS 可能偏高

由于线程级缓存和延迟 purge，RSS 可能看起来比 glibc malloc 高。README 记载的调节选项如下。MIMALLOC_PURGE_DELAY=N 在 N 毫秒后 purge 未使用的操作系统页(v3 默认1000；设为0立即 purge，内存更少但性能下降；设为-1则关闭 purge)。MIMALLOC_PURGE_DECOMMITS 默认为1，使用 decommit(Linux 上为 MADV_DONTNEED，RSS 立即下降)；设为0则改用 reset(MADV_FREE)。另外从 v3.5.1 起，Linux 默认构建为 -DMI_ALLOW_THP=FULL，不拆分透明大页(THP)，RSS 可能因此增加；运行时可用 MIMALLOC_ALLOW_THP=0、构建时可用 -DMI_ALLOW_THP=OFF 关闭。MIMALLOC_SHOW_STATS=1 不是调优选项，而是在程序退出时输出统计信息。

9-2) 与调试工具的相互作用

README 建议配合内存追踪工具时通常使用标准分配器。另一方面，mimalloc 可以构建为支持 Valgrind(-DMI_TRACK_VALGRIND=ON)、AddressSanitizer(-DMI_TRACK_ASAN=ON)或 Windows ETW(-DMI_TRACK_ETW=ON)的版本，README 注明 Valgrind 和 ASan 支持仍处于早期开发阶段。调试构建(-DCMAKE_BUILD_TYPE=Debug 或 -DMI_DEBUG=ON)提供按大小的详细统计、借助块尾填充的字节级溢出检测，以及 double free、非法指针释放、free list 损坏和部分 use-after-free 的检测。保护模式(-DMI_GUARDED=ON，调试构建默认开启)通过 MIMALLOC_GUARDED_SAMPLE_RATE=N 每 N 次分配在对象后放置保护页，即使在生产环境也能以抽样方式捕获溢出。

9-3) 依赖 glibc 特定行为的遗留代码

依赖 mallopt 等 glibc 专有调优或行为的遗留代码，替换后可能表现不同。另外在进程范围内 override 时，来自其他途径的指针可能被传给 mi_free；README 指出这种情况下有时需要启用会检查每个指针有效性的 -DMI_FREE_IS_CHECKED=ON(secure 模式默认开启)。嵌入式和驱动代码需要事先验证。

9-4) fork 与大页

README 警告：在使用大页(2MiB)或超大页(1GiB)时执行 fork，写时复制会在写入时复制整个页，内存可能以大块增长。启用 MIMALLOC_ALLOW_LARGE_OS_PAGES 或 MIMALLOC_RESERVE_HUGE_OS_PAGES 且 fork 频繁的负载(如 prefork 服务器)需要单独验证。

9-5) 总结

这些风险都在可管理范围内，但上线前在 staging 做至少一周的压力测试、在相同负载下把 RSS、延迟和 p99 与 glibc 定量对比，这一步最好不要省略。一周这个期限是本文的建议，并非官方标准。

10. 2026 内存分配器趋势 - mimalloc 之外

把首次发布时写的三个趋势，用2026年9月29日核实的事实重新整理。

10-1) 感知硬件的配置

mimalloc 在运行时检测 NUMA 节点，可用 MIMALLOC_USE_NUMA_NODES 调整，v3 新增了 mi_heap_set_numa_affinity。它还支持预留 1GiB 超大页(MIMALLOC_RESERVE_HUGE_OS_PAGES，指定 NUMA 节点用 _AT)、利用 THP(v3.5.1 起在 Linux 上默认开启)以及针对架构优化的构建(-DMI_OPT_ARCH：x64 为 haswell、avx2，arm64 为 armv8.1，Apple 为 armv8.3)。README 指出 NUMA 本地分配只是尽力而为，并不保证。首次发布时关于 HBM 和持久内存的预测，本次未核实依据，已删除。

10-2) 其他分配器家族与派生项目 - 先看活跃度

本文首次发布时把 snmalloc 写成 mimalloc 的变体或后继，但 snmalloc 是微软另一个仓库(microsoft/snmalloc)中设计独立的“基于消息传递的分配器”。“mi-game”之类的派生无法确认，已删除。在生产中使用派生或分叉之前先检查维护者活跃度和补丁周期，这一原则仍然有效。作为参考，GitHub API 显示的最近推送日期为 mimalloc 2026-09-29、tcmalloc 2026-09-29、jemalloc 2026-09-27、snmalloc 2026-09-23、rpmalloc 2026-07-15。

10-3) Rust 生态的全局分配器选择

Rust 可以用一行 #[global_allocator] 替换整个进程的分配器，mimalloc crate 的累计下载量已超过5,700万次。首次发布时“替换默认分配器的讨论周期性出现”是当时的观察，本次未核实依据。本文的建议是：新的 Rust 服务可以把 mimalloc 列为候选，但在定为默认之前先用自己的工作负载测量。

11. 结论 + 本周可以做的3件事

一句话总结 mimalloc：“它是易于回退的 drop-in malloc 替代品，公开基准测试显示在跨线程分配与释放多的负载上尤其强；但这些数字是2021年测量的，需要在自己的工作负载上重新测量。”马上可以做的三件事：

11-1) 动作1 - 30 分钟的 LD_PRELOAD PoC

在运行中的二进制前加上 LD_PRELOAD=/usr/lib/libmimalloc.so 和 MIMALLOC_VERBOSE=1 确认已生效，施加30分钟负载，把 RSS、CPU 和延迟与 glibc 基线对比。收益明显就进入 staging 压力测试；收益甚微，去掉环境变量即可回退。

11-2) 动作2 - 新 Rust 服务把 mimalloc 列为候选

新建 Rust 服务时，在 Cargo.toml 中加入 mimalloc = "0.1" 并声明 #[global_allocator]，与默认分配器比较一下，只需5分钟。默认是 mimalloc v3，必要时可用 v2 feature 切换。收益大小通过测量确认。

11-3) 动作3 - 对外暴露 / 解析未受信任输入的服务评估 mimalloc-secure

面向网络的服务和解析器可以评估 mimalloc-secure：按 README 平均约10%的开销，获得保护页、free list 编码、double free 检测和随机化。若目标是在生产中以抽样方式捕获溢出，保护模式配合 MIMALLOC_GUARDED_SAMPLE_RATE 也是选项。

最后，本文想强调的是：内存分配器是“看不见的性能杠杆”。改一行代码或一个环境变量就能改变性能指标的领域并不多，而 mimalloc 是其中门槛最低的工具之一。不过效果大小由工作负载决定。设计新系统时，值得至少测量一次。

## 2. 是否试用替换(符合任意一项即在 staging 试验)

- [ ] 经常由一个线程分配、另一个线程释放
- [ ] CPU 剖析中出现 `malloc`、`free` 竞争
- [ ] 是大量产生短寿命对象的语言运行时或解释器
- [ ] 数天以上不重启运行且 RSS 缓慢上升(先排除内存泄漏)
- [ ] 解析不受信任的输入，并有约10%的性能余量(secure 候选)
- [ ] 是可以替换全局分配器的 Rust 或 C++ 项目

都不符合时，默认分配器可能已经够用。

## 3. 30 分钟 PoC 步骤(Linux)

- [ ] 基线：用 glibc 在相同负载下运行30分钟，记录 RSS、CPU、延迟和 p99
- [ ] 用 `MIMALLOC_VERBOSE=1 LD_PRELOAD=/usr/lib/libmimalloc.so <程序>` 确认已生效
- [ ] 相同负载运行30分钟，记录相同指标
- [ ] 收益明显则进入 staging 压力测试(本文建议至少一周)
- [ ] 收益甚微则去掉 `LD_PRELOAD` 回退，并保留结果

macOS 使用 `DYLD_INSERT_LIBRARIES`，Windows 使用 `mimalloc-redirect.dll` 方式。

## 4. RSS 偏高时的调节表

| 选项 | 含义 | 用法 |
|---|---|---|
| `MIMALLOC_PURGE_DELAY=N` | N 毫秒后 purge 未使用的操作系统页 | 0 = 立即(内存少、性能降)，-1 = 关闭 purge |
| `MIMALLOC_PURGE_DECOMMITS` | 1 = decommit(`MADV_DONTNEED`，RSS 立即下降)，0 = reset(`MADV_FREE`) | 默认 1 |
| `MIMALLOC_ALLOW_THP=0` | 关闭透明大页 | 需要降低 RSS 时 |
| `-DMI_ALLOW_THP=OFF` | 构建时关闭 THP | 同一目的，在构建阶段 |
| `MIMALLOC_SHOW_STATS=1` | 退出时输出统计 | 用于观察，不是调优 |

## 5. 构建模式选择表

| 目的 | 构建 | 备注 |
|---|---|---|
| 缓解堆攻击 | `-DMI_SECURE=ON` | 保护页、指针编码、double free 检测、随机化，平均约10% |
| 最大程度缓解 | `-DMI_SECURE=FULL` | 每页设保护页，README 一般不推荐(VMA 上限) |
| 开发期间查错 | `-DCMAKE_BUILD_TYPE=Debug` 或 `-DMI_DEBUG=ON` | 字节级溢出、double free、部分 use-after-free |
| 生产环境抽样检测 | `-DMI_GUARDED=ON` + `MIMALLOC_GUARDED_SAMPLE_RATE=N` | 每 N 次分配放置保护页 |
| 使用 Valgrind、ASan | `-DMI_TRACK_VALGRIND=ON` / `-DMI_TRACK_ASAN=ON` | 早期开发阶段，README 通常建议使用标准分配器 |

- [ ] 是否在启用大页或超大页(`MIMALLOC_ALLOW_LARGE_OS_PAGES`、`MIMALLOC_RESERVE_HUGE_OS_PAGES`)的同时频繁 fork → 写时复制可能使内存骤增
- [ ] 若是 Go 或 Java，是否理解影响范围仅限 cgo、JNI 的本机分配
