清掉 Cookie 之后，为什么还是被当成同一个人

不是保存，而是比对 — 屏幕、字体、画布、音频在设备之间产生偏差的原理，以及为何无法彻底封死

2026年8月21日 IT/技术

引言：没有东西可删的追踪

浏览器数据全清了。Cookie、站点数据、缓存，一样没落。换成隐私窗口重新打开，也没有登录。可是几天前随手看过的那件商品，又摆在首页上。换一个网站想注册新账号，系统提示这台设备已有注册记录，要求追加验证。

这时候常见的反应是「大概还有什么没清干净」，于是继续清，结果照旧。正因为什么都没剩下，才会这样。对方并不是找到了事先埋下的标记，而是浏览器回答问题的方式和上次一模一样，于是被判为同一台设备。

这篇文章把那个判定拆到信号这一层：屏幕、字体、绘制结果、声音计算为什么会在设备之间出现细微偏差，这些偏差又是怎么变成识别信息的，以及浏览器和标准挡住了什么、挡不住什么。怎么做出来这件事不在讨论范围内。

1. 保存式追踪和辨认式追踪是两件事

Cookie 的结构很简单。服务器交出一个值，浏览器把它收着，下次请求时再附带回去。值是存在的，所以看得见；看得见，所以删得掉。浏览器设置里有删除按钮、监管也相对较早成型，原因只有一个 — 目标是一件看得见的东西。如果你关心的是 Cookie 本身的行为，另有一篇按 SameSite 取值梳理哪些请求会丢掉 Cookie 的文章。

指纹识别不制造任何东西。它只是把页面正常渲染过程中本来就会显露的值收集起来，压缩成一串字符。这串字符留在服务器上，不留在你的设备里。你这边根本不存在可以清除的对象。

W3C 面向规范作者写的那份文档，把这种能力定义为「通过配置项或其他可观测特征识别或再识别访问中的用户、用户代理或设备」。定义里出现再识别这个词很关键。第一次认出一个人并不那么值钱，把一条被刻意切断的连接重新接上，才是实际用途。

同一份文档把这种能力分成四类。设计防御时真正分岔的地方，就在这个分类上。

  • 被动型 — 只要发出请求，服务器就能知道的那部分。请求头的构成与顺序、网络层的特征都属于此类。页面上不跑任何代码它也成立，而且从外部无法观测它是否正在发生。
  • 主动型 — 必须由脚本或样式向浏览器发问才拿得到：窗口尺寸、可用字体、传感器数值。因为有代码在跑，原理上是可以被察觉的。
  • 瞬时关联 — 不依赖任何保存值。把不同来源上几乎同时发生的硬件或环境事件对上号，推断它们属于同一台设备。
  • 类 Cookie 型 — 在某处写下状态，之后再读回来。只是名字不叫 Cookie，本质仍是保存，因此删除依然能切断它。

对用户来说最难办的是被动型。浏览器里没有开关，也很难知道哪些站点在这么做。防御效果最好的反而是主动型 — 必须先有提问才会有回答，所以还有余地去修饰答案或者拦下提问。

2. 用到的是哪些信号

把常被提到的材料按性质归类，大致是下面这样，并附上每一项在设备之间产生差异的原因。

信号会暴露什么为何设备之间不同
屏幕与窗口分辨率、色深、缩放比例、扣掉任务栏或程序坞后的实际可用区域显示器组合和系统缩放设置人人不同，再把任务栏的位置与尺寸算进去，取值种类会大幅增加
字体清单装了哪些字体、渲染时能调用哪些在系统默认字体之上，办公软件、设计工具、游戏、语言包各自叠加一批。安装历史本身就成了组合
画布绘制结果画同样的文字和图形时得到的像素值显卡与驱动、抗锯齿方式、字体光栅化器不同，边缘像素就会差上一两级
显卡信息报告出来的厂商与渲染器字符串、支持的扩展列表、着色器精度上限GPU 世代和驱动版本会直接显露出来。扩展列表连排列顺序都构成组合

媒体支持构成可播放的编解码器与容器组合、受保护内容的播放能力取决于系统与浏览器版本、额外安装的编解码器、有无硬件解码

单项都很常见，为什么组合却很罕见

这里常出现一种误解：「我的分辨率是最常见的那种，怎么可能锁定到我头上。」前提没错，结论错了。识别不是靠单独一项，而是靠把多项乘在一起。

就算使用最常见分辨率的人占到四分之一，再叠上时区和语言排序，再叠上字体组合，再叠上显卡字符串，剩下的人数会急剧收缩。信息论把「每一项能把人群分开多少」称作熵，而实务上把剩下的那一撮人称为匿名集合。防御的目标不是抹掉自己的数值，而是让自己所在的匿名集合保持足够大。

这个视角之所以重要，是因为它直接决定后文的结论。把数值随机化的工具并不会扩大匿名集合，反而可能造出一个全世界只有你一个的组合。

3. 设备之间为何会出现细微偏差

把表里那一栏「为何不同」再往下挖一层，偏差其实分别产生在三个层面。

  • 硬件层 — 运算单元的构成与执行顺序不同，浮点结果的末位就会分叉。同一个算式因相加顺序不同而得出不同数值，是浮点运算的正常行为，不是缺陷。
  • 系统软件层 — 显卡驱动、字体光栅化器、音频栈各有版本，也各做各的优化。即使浏览器相同，这一层不同，结果也会分叉。
  • 配置层 — 屏幕缩放、语言顺序、无障碍选项、配色偏好这类由人亲手改动的值。这一层往往正是用户自己把自己弄得与众不同的地方。

那标准为什么放任不管？大多数 Web 规范要求结果看上去一致，并不要求逐位一致。真要求了，就得放弃硬件加速，或者强制所有实现走同一条渲染与运算路径，那等于把性能和可移植性一并舍掉。被允许的这点误差，恰恰就变成了识别信息 — 这是问题的结构性本质。

所以这更像是「允许实现既快又多样」所付的账，而不是「某家公司做了个糟糕的 API」。要修就得交出性能或功能之一。后面要看的那些浏览器防御之所以清一色以折中收场，原因就在这里。

4. 音频信号真正测量的是什么

音频类信号因为名字容易被误读。它并没有在用麦克风听什么，也不会弹出权限请求。

结构和画布那边一样：给一个已知输入、跑一段已知处理、读出来的数字。造一段成分丰富的波形（比如锯齿波）送进处理通路，末端会掉出一个数组。理论上这个数组在哪台设备上都该相同，实际却在小数点后某一位分了叉。分叉的理由就是上一节那三层 — 舍入位置、向量化方式、重采样器实现，以及系统选定的默认采样率。

这里有一个要点。Web Audio 规范里定义了不送往真实输出设备、只做计算的渲染模式。规范把普通上下文描述为「目的节点被路由到实时输出设备的音频图」，而离线渲染则在没有该设备输出的情况下完成处理。所以没接扬声器、系统静音、耳机拔掉，值照样出得来。

规范本身并非不知道这个风险。在选择渲染量大小的那一项上，附有「会暴露宿主信息、可被用于指纹识别」意味的注记，另外还专门设了隐私与安全考量的章节。也就是说，这不是一个被藏起来的漏洞，而是白纸黑字写着、就这么留着的折中。

5. 无声的计算为何能占住设备

上一节那两种模式的区别，到这里变成了实际的副作用。

如果只打算做计算，用离线渲染就够了。但也完全可以建立一个实时上下文、一路连到目的节点，只把最后一级的音量设成 0。这种情况下人耳听不到任何声音，但在浏览器看来，输出通路一直是活的。规范写道，上下文一旦建立，就会持续到没有声音可播放或页面消失为止，并说明要释放部分资源必须显式暂停。

这个差别最容易被察觉的地方是蓝牙。同时连着两台设备的多点耳机，是依据「哪一边正在实际输出音频」来判断切换的。只要主机维持着音频流，它看起来就是使用中，于是不会自然切到手机那边。标签页的静音按钮有时也帮不上忙，因为那个按钮通常是以页面内的媒体元素为对象工作的。没有媒体元素、只有一张活着的图，它就抓不到。

2026 年 8 月，有人在个人博客上记录：让某家大型购物网站一直开着，蓝牙耳机就不会切到手机。作者把原因指向页面上运行的脚本维持着一条无声音频图，并分析说同一批脚本还在一并收集绘制结果、显卡信息、屏幕尺寸、设备档次之类的数值。

这个案例该被当成事实到什么程度。以上是第三方观察并分析后公开的主张。相关网站方面的说明尚未得到确认，而这套结构为何会存在 — 是设计还是副作用 — 从外部无从判断。本文当作事实来处理的部分，只到按 Web Audio 规范这种结构在原理上是可能的为止。

推广开来说就是：屏幕上看不见任何东西的功能，照样可能占住系统资源。这与其说是指纹识别独有的性质，不如说是实时媒体 API 的普遍性质；而且与摄像头、麦克风不同，音频输出这一侧既没有权限弹窗也没有指示灯。用户几乎没有察觉的通道，这才是这件事真正的分量所在。

6. 同一项技术的另一面 — 欺诈检测与机器人拦截

只读到这里，这项技术看上去像是专为追踪而生的。并非如此。它铺得最广的地方其实是支付和登录。

用途判断什么用户得到什么问题出在哪里
支付欺诈检测被盗的卡是否正从一台完全陌生的设备构成上使用本人不知情却被划走的交易变少正常用户换了设备时会被误判拦下
账号盗用防护这次登录是否来自从未见过的设备新设备提醒与追加验证拖慢盗号重置过浏览器的本人也会被当成新设备
自动化与爬取拦截是否存在与真人使用的浏览器不同的痕迹囤货与抢票脚本减少把隐私设置调得很硬的人被误当成机器人
滥用抑制同一台设备是否在换着账号反复领取优惠一人一次的权益真的只发一次家庭共用设备被归并成同一个身份
跨站广告画像在不同站点见到的人是否同一个人用户这一侧得到的东西并不明确目的扩张、留存期拉长的典型场合

把表格横着读，有件事会浮出来：技术从头到尾都是同一套，分岔的是目的、留存期与共享范围。同一个值既能喂给风险判定，也能喂给画像积累。所以「禁止指纹识别」这种整理方式在实务上跑不通 — 禁的是技术，支付安全会一起塌；禁的是目的，从外部几乎无从验证。

用户这一侧还会撞上一个悖论：防得越硬，越像机器人。把数值藏起来、或者拼出一个罕见组合，风险分就往上走，结果是验证码更频繁、支付再被拦一次。这与其说是不公，不如说风险模型本来就是这么运作的。把拦截强度调高会坏掉什么，另有一篇按强度档位梳理代价的文章。

7. 浏览器实际做的防御

浏览器用的手段大致有四类，各自性质不同。

  • 标准化 — 让所有人在相同处境下给出相同答案。这是 W3C 指南向规范作者推荐的首选方向，数值一旦统一，该项的熵就趋近于 0。
  • 削减熵 — 砍掉精度、把连续值压成几个区间，或者干脆缩成是与否。功能保住，分辨力降下来。
  • 基于名单的拦截 — 按名字挡掉已知的指纹脚本。可靠，但名单之外的一律放行。
  • 数值归一化 — 只对特定项目回答一个平淡无奇的值。挑哪些项目动手，就等于挑了多少兼容性成本。
  • 存储分区 — 按站点隔开存储空间。对类 Cookie 型很有效，对不碰存储的主动型信号则没有直接作用。

看一个已经落地的例子，折中的形状就出来了。Mozilla 说明 Firefox 的指纹防护会限制显卡硬件细节、设备上的字体信息、处理器核心数、触屏手指支持、程序坞与任务栏尺寸、数学运算的细微差异等项目，并称被看作独一无二的用户比例几乎减半。同时它也把边界写了出来：拦得更激进必然会破坏正常的网站功能。像日历所需的时区这类正常功能要用的值，是被刻意保留的。

这里有一个方向需要说清楚：标准化优于随机化。W3C 的文档建议把规范标准化，好让遵循规范的浏览器彼此构成更大的匿名集合。每次给出不同答案这种策略，本身就是一种异常行为，既更扎眼，也会连带把站点功能弄得不稳。

而 W3C 在结论上并没有退让。它明确写道：仅凭广泛部署的技术手段就彻底消除有备而来的一方的指纹识别能力，可能性很低。作为替代，它列出四个可达成的目标：缩小暴露面、扩大匿名集合、确保可察觉性、让状态可被清除。

8. 用户能做的事，以及它的边界

在「完全阻断做不到」这个前提之上，实际剩下的选项如下。

手段实际在做什么代价与边界
浏览器内置保护模式拦下已知脚本、对部分项目做归一化有些项目按设计会保留原值，强模式还会弄坏一部分站点
隐私窗口会话结束时丢弃保存下来的状态信号本身毫无变化。只对类 Cookie 型有效
追踪拦截扩展在请求阶段切断已知的收集端点扩展组合过于特别时，它本身就可能变成新的信号
数值伪造工具对部分项目回答伪造的值扩不大匿名集合，前后对不上的组合反而更好认
VPN 与代理更换网络地址只遮住被动型信号的一部分，对主动型没有影响
把浏览器与系统保持最新自动获得新加入的缓解措施成本最低的一招，效果则是渐进的
让设备与设置保持平常留在匿名集合较大的那种构成里有时得放弃个人偏好与无障碍设置

归结起来，先要换的是目标。让自己看不见并不是一个可达成的目标。可达成的是不显眼，而这条路多半通向少折腾那一侧。比起把工具一层层叠起来，打开内置保护、不拖延更新，在匿名集合这个视角上往往更有利。

自己的浏览器有多扎眼，可以用公开的诊断工具直接查。电子前哨基金会运营的 Cover Your Tracks 在 MDN 文档里也被列为参考资料。不过要说清楚：没有任何工具能保证结果，也谈不上用了某个扩展或某款浏览器就安全了。

9. 制度层面如何看待这个问题

免责 — 本节是基于公开资料的一般性说明，不构成法律意见。具体个案的判断会因管辖地与事实情况而异，必要时宜请专业人士审阅。

欧洲方面的讨论开始得比较早。第 29 条工作组在 2014 年 11 月发布的意见书主张，即使不保存、只是读取，也可能构成对终端设备信息的访问，因此适用于 Cookie 的同意要求可能一并适用。这份文件的核心动作，是明确驳回了「没有保存所以不受约束」这一说法。此后，欧洲数据保护委员会重新梳理了 e 隐私指令第 5 条第 3 款的技术适用范围，出台了指南 2/2023，最终版于 2024 年 10 月通过。

其他法域的出发点则不同。以韩国为例，其个人信息保护法第 2 条第 1 项把个人信息定义为关于在世个人、能够识别该个人的信息，以及虽然仅凭该信息无法识别、但与其他信息容易结合即可识别的信息；是否属于容易结合，要综合考虑其他信息的可获取性以及识别所需的时间、费用与技术，作出合理判断。

在这种结构下，浏览器指纹是否属于个人信息，并不是一个可以一概而论的问题。单看那个数值确实不知道是谁，但如果同一家经营者同时握有账号、支付与订单记录，结合可能性的性质就变了。也就是说，判断来自这个数值所处的位置，而不是数值本身。本文不下定论，原因正在于此。想继续追踪用户视角的隐私争论，可以参考梳理欧洲消息扫描立法之争的那篇文章。

10. Web 标准正在走的方向

标准这一侧的应对，与其说是「把糟糕的 API 拿掉」，不如说更接近在设计新 API 的当口就先算清楚它会漏多少。把 W3C 指南对规范作者的要求提炼一下，是这样：

  • 不要扩大被动型暴露面 — 既察觉不到也躲不开，代价最大
  • 把暴露范围收窄到功能确实需要的程度
  • 用标准化而非随机化去扩大匿名集合
  • 通过限制精度、改成枚举、压成布尔值来削减熵
  • 要求服务器显式索取之后数值才发出，以保住可察觉性
  • 对齐各类存储手段的清除时机，让状态真的能被删掉
  • 不要制造在 Cookie 被清除后仍然留存的永久标识符
  • 提出新功能时把新增的暴露面一并写进设计文档 — 这被当作规范开发各个阶段都要考虑的事项

剩下的张力很清楚。为性能而报告硬件信息的 API、为无障碍而报告用户设置的 API、为媒体质量而报告编解码器支持的 API，今后还会不断出现，每一次都会把同一副天平重新架起来。这类问题不属于会被解决的那一种，而属于要被长期管理的那一种。

从实务者的角度，可以马上拿来用的标准也由此而来：加新功能时，哪怕只写一行，也把「它又多漏了什么」记下来；实时资源只在需要的时间内占住，用完显式释放。上一节那个音频案例给出的教益，不是什么华丽的漏洞，而是这条平淡的卫生守则。

未能确认的部分

本文刻意没有下断言的地方，集中列在这里。

  • 前述购物网站案例中，那个行为究竟是有意为之还是副作用 — 经营者方面的说明未获确认
  • 收集到的数值在服务器上留存多久、是否与其他服务打通 — 这是客户端之外无法观测的领域
  • 该现象在哪些浏览器、系统与耳机组合下可以复现的范围 — 没有找到梳理复现条件的独立验证资料
  • 各浏览器防御效果的第三方独立最新测量数值 — 正文引用的接近减半，是该浏览器提供方自己的说明
  • 在特定法域把浏览器指纹认定为个人信息的已定案例 — 未能确认

结语：该拿什么当尺子

整理下来，留下三条轴。

第一，有没有一个能删掉的标记。这一条区分把 Cookie 和指纹识别分开，也直接划定了用户可用手段的范围。隐私窗口之所以没有大家期待的那么管用，原因也在这里。

第二，看的是目的、留存与共享，而不是技术。拦住盗刷的判定和堆起广告画像，用的是同一批材料。把两者塞进同一个词里，哪一边都处理不好。

第三，目标是不显眼，而不是消失。标准化胜过随机化，把内置保护打开并保持更新，通常胜过堆一摞工具。凡是承诺完全阻断的说法，读到那一句就值得停一下。

给开发者的还有一句：屏幕上看不见的功能，并不因此就不花代价。实时资源占了，就得还回去。
