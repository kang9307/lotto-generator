起因 - 从二十五格抱怨出发、又自己推翻抱怨的一篇文章

2026年10月3日，MOND←TECH MAGAZINE刊出了一篇题为「Async Rust: Where does the scheduler live?」的文章，GeekNews在10月6日作了介绍，作者署名为Mond。文章开头把围绕async Rust反复出现的抱怨收集成一张5×5的宾果卡。函数着色、async闭包、Tokio默认主义、「直接用线程」、Async Drop、取消安全性、Send + Sync + 'static约束的蔓延、io_uring，一直到Pin，共二十五格，后面跟着一份为每格附上阅读材料的备忘清单。

接着是作者自己的抱怨：async Rust需要运行时，这一点让作者感到别扭。Rust的招牌是不靠垃圾回收器这类运行时就提供内存安全，回到基于运行时的模型在作者看来像是倒退。有了运行时，函数就不再由自己直接执行，而是交给引擎按它自己的规则运行。调度算法是优化问题，需要在取舍的边界上选定一个具体的点，不存在适用于所有情形的答案。为了多挤出一点性能，还得像调Java垃圾回收器那样去调Tokio运行时。

随后作者亲手收回了这段牢骚。原文的句子是「In short, that whole gripe was nonsense.」理由是，有运行时的感觉、调度器优化上的取舍以及复杂性，都不是async Rust独有的问题，而是并发代码的普遍问题。文章余下的篇幅用来展开这个转折。调度器总得待在某处，剩下的问题只是待在哪里。

下面追踪的也是这个位置。内核、内建于语言的运行时、crate，以及作者期望的第四个位置即参数，依次摆出，并在每个位置上把原文列举的成本和约束同Rust与Tokio官方文档的措辞并排。标记沿调用层级向上扩散的函数着色问题和取消的语义是另一条轴线，见同样的async代码为何在不同运行时收尾不同。

调度器不会消失 - 作者的五个步骤

作者的出发命题很短：想让代码并发运行，就需要负责调度的运行时，这实际上已包含在并发的定义之中。作者写道，避开async Rust改用线程，变化只有一处，即调度器从Tokio换成了内核；调度器仍在，同样的问题会全部或至少部分跟来。接着作者把问题所在整理成五个步骤。

  1. 并发以这样或那样的形式是必需的。
  2. 并发总是需要运行时。于是问题变成：运行时待在哪里，栈由谁管理。
  3. 想避开运行时，最好的情况只有两种。自己写事件循环，等于开始维护一个自己的运行时；选择「直接用线程」，等于把内核当运行时用，要摆弄比专门设计的Tokio任务重得多的内核线程。原文描述这种重量差距时用了夸张的说法。
  4. 像Go那样把运行时随语言一起发布，Rust就更难嵌入到别处，并要在FFI边界上付出成本。
  5. 选项都排除之后，剩下的就是今天的样子。运行时是一个crate：引入它，初始化它，必要时四处传递，再用它调度future。

作者写道，自己本想逐一翻检这些设计决策并加以抱怨，结果每一步的结论都是这样做有道理。用来收束的句子是「The scheduler has to live somewhere, and Rust doesn't get to trade performance for convenience.」这里同样带着一条保留。作者先说明不知道是否存在某种尚未发现的抽象能让async Rust的问题消失一半，然后表示倾向于认为不存在。依据是，那些问题里有许多属于并发的普遍问题。

从中值得带走的区分只有一个。作者提议把async Rust的问题分成两类：一类是并发固有的问题，另一类是处在「把调度器放进crate」这一决定下游的问题。按这一区分，可以读作前一类无论调度器放在哪里都会跟来，后一类会随位置移动而改变形状。哪些属于后一类，后文通过作者点名的三件事来讨论。

标准库规定了什么 - 到Future、poll、Waker为止，没有调度器

第五步「运行时是一个crate」是什么样子，从标准库文档中就能看出。std::future::Future是自Rust 1.36.0起稳定的trait，它的定义全部内容如下。

pub trait Future {
                        type Output;
                    
                        // Required method
                        fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
                    }

文档把future解释为一个可能尚未完成计算的值。poll是尝试把future解析为最终值的方法，值未准备好时它不阻塞；当再次轮询能取得进展时，当前任务会被安排唤醒。文档里没有哪个类型决定由谁调用poll。文档写明的是，future本身是惰性的(inert)，底层计算要取得进展就需要被主动轮询。文档还写道，使用future的一方通常不会直接调用poll，而是使用.await。

负责轮询的一方是执行器。Waker的文档把Waker定义为一个句柄：它通过通知执行器某个任务已可运行来唤醒该任务。它典型的一生是由执行器构造，包进Context，再传给Future::poll()。接下来运行哪个任务也交给执行器决定。同一份文档写道，让位给其他竞争中的任务没有保证，运行哪个任务是执行器的选择，执行器也可以选择再次运行当前任务。标准库规定到唤醒的通道为止，被唤醒的任务何时、在哪个线程上运行则留作空白。

Async Book直接写出了这样安排的理由。许多语言都提供运行时，它往往还承担内存管理、异常处理，甚至充当完整的虚拟机。Rust作为低层语言力求把运行时开销降到最低，所以它的async运行时范围比许多语言的运行时窄得多。又因为设计和实现async运行时的方式很多，Rust不提供某一个，而是让使用者按需求选择。这本书也用一句话写出了代价：开始进行async编程需要多走一步。关于运行时的结构，书中说明没有严格的规则，表里的术语和职责划分只是常见而已。spawn之所以是Tokio的函数而非标准库的函数，书中的解释是任务纯粹是运行时的概念。

第一个位置：内核 - 「直接用线程」挪动的是什么

宾果卡上有一格写的是「just use threads」。备忘清单把这种主张最常见的变体概括为：只有编写需要同时支撑一万以上连接的服务器时async才变得必要，其余情况用线程池就够了。作者的回答是，这个选择没有让调度器消失。用了线程，内核就成了调度器。

这个位置的性质整理在Rust拿掉绿色线程时撰写的RFC 230里。RFC把任务总是对应一个操作系统线程的模型称为1:1，把用户空间调度器将任务映射到工作线程上的模型称为M:N。在1:1模型中任务就是线程，因此各自要配备栈；又因为每个任务都是操作系统线程，任务可以自由阻塞而不给其他任务带来风险。在M:N模型中，操作系统意义上的阻塞意味着阻塞工作线程。RFC补充说，长时间运行的循环和缺页错误也一样。

作者为这个位置举出的成本是重量：内核线程比专门设计的Tokio任务重得多。被比较的一方，Tokio教程记有一个数值：Tokio任务在内部只需一次内存分配和64字节内存，创建几千乃至几百万个任务都不必顾虑。教程把Tokio的任务称为异步的绿色线程。内核线程一侧的大小数值，原文和上面这些文档里都没有给出。

作者还抛出一个自称辛辣的想法。与其在各门语言里反复发明运行时并为之争论，能否修好内核的线程与调度机制，或引入一种新型内核线程，让「直接用线程」变得高效？推理是：goroutine是运行在内核之上的抽象，既然能把它做得便宜又快，内核也应当能支持这类线程的某种变体。对此作者自己附了三条保留。

  • 作者写道类似的尝试以「M:N user-level threading」之类的名字出现过几次，并坦言没有就此做过调查。
  • 作者认为，内核实际上不可能像语言专属的运行时那样了解代码，这限制了它调度线程的能力；除非找到办法把额外信息交给内核，否则语言专属的运行时大概会一直占上风。原文在「always」后加了问号。
  • 即便在理想情况下，结果也只是回到人人都用线程处理一切的世界，只是性能更高。这样是否更好，作者的回答是不知道。

第二个位置：语言运行时 - Go的选择与Rust拿掉的东西

原文用来说明内建运行时的语言是Go。作者的叙述是：没有人指望Go拥有裸机级别的性能，人人都明白这里存在取舍。用一部分性能换取便利，所以Go才有goroutine，即绿色线程。备忘清单把绿色线程模型解释为语言自带运行时的模型。至于Rust，作者写道，不存在完美的调度器，不同的调度器各有用途，所以Rust无法替使用者选定调度器。在Go和Rust之间迁移的判断依据，见从Go迁移到Rust的指南。

Rust也曾站在这个位置上。RFC 230的起始日期记为2014年9月16日，它提议移除当时包含在标准库里的运行时系统。按RFC的描述，Rust最初只支持绿色线程模型，后来加入原生线程并最终成为默认。Rust的绿色线程以M:N方式调度并带有自己的栈；但最初的分段栈被移除，改为预先分配的栈，RFC写道这使它们不再轻量。RFC列出的问题共有五项。

  • 被迫共同演进。绿色线程和原生线程两种模型任何时候都得提供相同的I/O API，哪怕有些功能只适合或只在其中一种模型下才高效。
  • 开销。两种模型的混用通过trait对象实现，因此二进制体积、任务本地存储以及内存分配和动态分发上都出现了成本。对最后一项，RFC自己加了说明：与实际执行I/O的成本相比，这些成本多数情况下微不足道，算不上反对该设计的有力论据。
  • 有问题的I/O交互。原生代码一旦调用阻塞式I/O，就可能阻塞正在运行绿色调度器的工作线程。API虽然统一，却不能完全互操作。
  • 嵌入Rust。从C代码调用Rust或把Rust嵌入高级语言时，需要相当多的准备工作来提供标准库所依赖的运行时基础设施。
  • 维护负担。为了提供如此灵活的线程模型，标准库变得更加复杂。

FFI成本这一论据原文没有展开，而是交给Without Boats于2023年10月15日发表的「Why async Rust?」。该文写道，把绿色线程上执行的代码切换到操作系统线程的栈上运行，对FFI来说代价可能高得难以承受，而Go接受了这笔成本。这对Rust尤其成问题，因为Rust在设计上要支持把库嵌入其他语言编写的二进制文件，也要支持运行在没有足够时钟周期或内存来运转虚拟线程运行时的嵌入式系统上。原文作者承认嵌入式这个论点站得住脚，并补了一句观察：在async Rust的争论里搬出嵌入式，本身几乎成了一个梗。

作者从中读出的是一条设计原则。放弃绿色线程的决定，在作者看来把一条当时仍在摇摆的原则固定了下来：Rust要走的是C++替代品的路线，能够在嵌入式的no_std环境中使用，并且具备零成本抽象。作者的评价是，事后回头看，这个方向看起来是正确的判断。作者先声明无人知道Rust若在绿色线程上加倍押注的反事实世界是什么样子，再补充一个推测：那不会是Rust进入Linux内核的世界。原文在这里用的动词也是「assume」。Rust的安全保证在FFI边界上如何中断，见Rust FFI边界上中断的安全保证。

第三个位置：crate - Tokio写在文档里的调度器

运行时成了crate，调度器的行为就不写在语言规范里，而写在那个crate的文档里。Tokio 1.53.2的文档写道，异步应用程序与其他Rust程序不同，需要运行时的支持，并列出三项必需的服务：驱动I/O资源并把事件分发给任务的I/O事件循环(driver)、执行任务的调度器，以及安排工作在一段时间后运行的定时器。Tokio的Runtime把三者打包成一个类型。

文档说明Tokio提供了多种适用于不同应用的任务调度策略，并把选择的经验法则画成一棵决策树。需要work-stealing或多线程调度器，就选Multi-threaded Runtime；不需要而又要执行!Send的future，就选Local Runtime；两者都不是，则选Current-thread Runtime。文档声明这棵树并不穷尽，其他因素也可能影响决定。多线程调度器在线程池上用work-stealing策略执行future，默认为系统上每个可用的CPU核心启动一个工作线程，并且默认被选中。

文档中「Detailed runtime behavior」一节用数字描述了内部行为。两种运行时的小节标题都带着「behavior at the time of writing」字样，正文也写明这些行为在Tokio今后的版本中可能变化。下表的数值要在这个前提下读。

把原文和这份文档并排，可以读出两点。第一，作者所说的「要在取舍边界上选定一个点的优化问题」，在Tokio里就表现为31、61、256、10ms这样的数值和相应的配置项。第二，这些数值是某个crate的某个版本选定的点。标准库文档里没有对应的数值，只有Waker文档中的那一句：运行哪个任务是执行器的选择。

放在crate里的代价 - 作者点名的三件事

调度器待在crate里而产生的问题，作者直接点了名：Tokio默认主义、缺乏运行时中立性，以及Send + 'static约束。

  • Tokio默认主义(Tokio Defaultism)。按备忘清单的解释，这是把Tokio当作唯一有意义的运行时的观念。没有意识到自己所说的只适用于Tokio而不适用于整个async Rust，也属此类。Async Book称Tokio是通用运行时，也是生态中最流行的运行时，同时写道，某些情况下换用别的运行时可能获得更好的性能或更简单的代码。
  • future并不是运行时中立的。备忘清单写道，任务的创建依赖于运行时，其中烙进了各种假设，还有一些事项被烙进了trait。人们谈到「ecosystem split」时所指的问题之一就是这个；清单补充说，另一个问题是async把整个Rust生态分成了async库和非async库。
  • Send + 'static约束的扩散。作者的解释是，语言本身无法知道运行时是否会在线程之间移动任务，所以Send约束会蔓延到整片泛型代码之中。

第三项可以拿Tokio文档的措辞来对照。tokio::spawn的签名如下。

pub fn spawn<F>(future: F) -> JoinHandle<F::Output>
                    where
                        F: Future + Send + 'static,
                        F::Output: Send + 'static,

Tokio教程把两个约束的理由分开写出。'static的意思是，被创建的任务不得包含对任务之外所拥有数据的引用。Send则是为了让Tokio运行时可以在任务停在.await处时把任务在线程之间移动；跨越.await保留的数据全是Send时，任务才是Send。spawn的文档还写道，让一个!Send的值跨越.await调用保留，会得到一条不太友好的编译错误信息。

这个约束来自work-stealing这一调度选择，写在备忘清单的另一格里。work-stealing意味着任务可以从一个CPU核心移到另一个核心，确保每个线程总有活干，但要求所有任务都带Send约束；thread per core的运行时不受这一限制。让标准库把创建任务的API标准化之所以是难题，作者也在这里找到原因：各运行时的期望不同。Tokio文档决策树里单独的Local Runtime分支反映的是同一种情况。

阻塞同样是在这个位置上会改变形状的问题。标准库文档写道，poll的实现应当力求快速返回，不应阻塞；若事先知道某次调用会花一段时间，就应把工作转交给线程池之类的地方。备忘清单中spawn_blocking一格描述的正是没做到这一点时的样子：不小心阻塞了一个Tokio工作线程，余下的工作会被其他线程窃取，程序也许还能一瘸一拐地运行，但调用阻塞期间工作线程池整整少了一个线程，流量不大时很难察觉。这与Tokio的公平性保证建立在「没有任务阻塞线程」这一假设之上相呼应。

I/O接口一侧也记录着同类摩擦。按备忘清单的说法，在io_uring的API中，操作完成之前缓冲区归内核所有，这与可通过drop取消的future相冲突，要在Tokio里解决就得重新设计其API。io_uring自身的行为，见io_uring SQPOLL与无系统调用I/O。

隐式的执行器上下文 - 同一个函数因调用线程不同而panic

作者针对Tokio单独提出的不满，是它隐式的环境执行器(ambient executor)模型，语气不重，原文只说这有点让人沮丧。被创建的Tokio任务会自动附着到悬浮在线程本地上下文中的执行器上，若这样的执行器不存在，就以运行期panic的方式崩掉。原文给出的例子如下。

fn record_metric(_value: u64) {
                        tokio::spawn(async move {
                            // do stuff
                        });
                    }
                    
                    fn checksum(data: &[u8]) -> u64 {
                        let sum = data.iter().map(|&b| b as u64).sum();
                        record_metric(sum);
                        sum
                    }
                    
                    #[tokio::main]
                    async fn main() {
                        let data = vec![1u8; 1024];
                        checksum(&data); // fine
                    
                        let (tx, rx) = tokio::sync::oneshot::channel();
                        rayon::spawn(move || {
                            let _ = tx.send(checksum(&data)); // panics, process abort
                        });
                        println!("{:?}", rx.await);
                    }

单看签名，checksum是接收字节切片并返回总和的同步函数。它内部调用的record_metric使用了tokio::spawn，这一点没有体现在签名上。原文中，在#[tokio::main]之下直接调用它的那一行带着「fine」的注释，在交给rayon::spawn的闭包里调用同一函数的那一行带着「panics, process abort」的注释。

Tokio文档的措辞记录的是同一份契约。tokio::spawn需要在Tokio运行时的上下文之内调用，Panics一节写明在Tokio运行时之外调用会panic。文档同时说明，运行在Tokio运行时上的任务总是处在它的上下文之内，也可以通过Runtime::enter方法进入这个上下文。Async Book则对入门阶段的读者说，眼下可以把运行时想象成只有在async函数里才能访问的全局变量。

作者把这种情形比作所有Tokio函数都在暗中传递的「secret argument」。忘了念那句咒语，也就是试图在Tokio运行时的上下文之外使用Tokio，得到的就是运行期错误。作者反对的性质有以下几点。

  • 存在副作用。
  • 存在接近全局变量的隐藏变量。
  • 存在隐藏的动态作用域。

对照上面的例子，这个副作用没有体现在checksum的签名上，同一个函数是否成功取决于调用它的那个线程所处的上下文，错误出现在运行期而不是编译期。

作者在脚注里承认这样的要求过分了。Rust没有效果系统，连代码是否可能panic都无法追踪，更不用说副作用。即便如此，作者仍写道不喜欢这件事没有在编译期得到追踪。另一条脚注记着Tokio确实提供了Handle::spawn，而问题在于使用环境上下文的形式才是默认。

在作者描绘的理想世界里，不把执行器穿过整段代码一路传到创建任务的地方，就无法创建任务。作者自己也写道许多人会讨厌这样的世界。退而求其次：如果确实想不经传递就伸手去拿Tokio的执行器，它应该放在全局变量里，并在调用处从那里取出。标准是能否被搜索到。作者写道，这种性质应当能用grep找到，而不是隐藏起来。

「已经好到头了」的成见 - future大小的例子

原文有一段关于性能的题外话。有一种信念认为async Rust笼统地说已经「as good as it gets」，作者指出实际并非如此。作者挑出的成见是：Rust的future会被编译成大小最优的状态机，恰好等于容纳全部数据所需的大小。作者写道这确实是设计初衷，但存在好几个由来已久的问题，并举了一个例子：参数若跨越让出点保留，就要付出两倍的代价。

async fn test(arg: [u8; 8192]) {
                        wait().await;
                        drop(arg);
                    }
                    
                    async fn wait() {}
                    
                    fn main() {
                        // Expected: 8194 == 2 + 8192
                        // Actual: 16386 == 2 + 2 * 8192
                        println!("{}", std::mem::size_of_val(&test([0; 8192])));
                    }

注释里的数值就是原文给出的全部数字。对于以8192字节数组作为参数的async函数，用std::mem::size_of_val打印其future的大小，预期值是8194(2 + 8192)，实际值却是16386(2 + 2 × 8192)。原文还建议去掉drop(arg);调用看看会发生什么，但没有写出结果。原文又写道，把future当作参数传递时大小的膨胀是指数级的，并指出rust-lang/rust仓库的拉取请求135527正在着手解决这一问题。

读这个例子时要留意数值的种类。8194和16386是编译器生成的状态机的字节大小，不是任何运行时的吞吐量或延迟。原文里没有运行时之间的基准测试，也没有线程与async之间的基准测试。备忘清单另有一格，讲的是嵌套很深的async函数的future可能把栈撑爆。原文把这种成见同「存在适用于一切用途的调度器」的想法分开，当作另一种误解处理。关于调度器的误解是选哪个调度器的问题，关于future大小的误解是编译器把future做成多大的问题。

第四个位置：参数 - Zig的I/O接口与作者的保留

作者举出的合乎原则的例子是Zig。在Zig里，I/O接口被传给所有需要它的函数，是否异步以及I/O于是成了被传入的那个具体实现所带的性质。原文注明取自Loris Cro文章的例子如下。

const std = @import("std");
                    const Io = std.Io;
                    
                    fn saveData(io: Io, data: []const u8) !void {
                        const file = try Io.Dir.cwd().createFile(io, "save.txt", .{});
                        defer file.close(io);
                    
                        try file.writeAll(io, data);
                    
                        const out: Io.File = .stdout();
                        try out.writeAll(io, "save complete");
                    }

saveData的第一个参数io: Io就是那个接口。创建、关闭、写入文件的每次调用都把io传进去。作者写道，I/O接口定义了面向运行时的契约，并总结说，在所有人都严格传递接口的前提下，原理上可以得到三样东西。

  1. 可以准确追踪阻塞操作可能发生在哪里。
  2. 可以避开函数着色，因为颜色变成了函数的参数。脚注在此加了一条保留：颜色是被编码成传给函数的参数，而非特殊的语言特性；这算不算函数着色，人们恐怕永远无法达成一致。
  3. 所有库代码对执行器或调度器保持中立。传入I/O接口的另一种实现即可，所以生态不会分裂。

作者对标题之问的回答出现在这里：把调度器放进四处传递的参数里，感觉是对的。这样做虽然啰嗦，却能解决许多问题，按作者的说法能解决宾果卡上约三分之一的格子。不是内核，也不是悬浮在周围的执行上下文，而是可以作为参数传递、需要时可以替换的东西，这就是作者希望调度器待的位置。

这个回答后面接连跟着几条保留。按照原文的顺序转述如下。

  • Zig还不是稳定版，而async又非常难做对。用作者的话说，这种做法还没有在实战中得到证明。
  • 如果Zig团队能把它做成，作者确信朝这个方向演进Rust的实验值得一试。这是以条件开头的句子。
  • 全面采用需要重写std::fs这类Rust标准库API，所以作者认为这几乎可以确定不在考虑之列。
  • crate生态并不受这样的约束，所以或许是可能的。原文的说法是「Maybe it's possible.」

作者的结论不是建议Rust效仿Zig。作者保留了「放在crate里的现有选择对Rust是对的」这一评价，只说到这一步：如果Zig团队能把它做成，那么让Rust朝那个方向演进的实验是值得做的；而在crate生态里，也许是可能的。

手上的代码若属于表中第三行，从上述文档的措辞里可以直接得出一组检查项。下面的列表把原文和官方文档的表述按阅读代码的顺序重新排列。

  1. 运行时的种类与工作负载是否相符。按Tokio文档决策树的顺序看：是否需要work-stealing或多线程，不需要的话是否执行!Send的future。文档写道，大多数应用程序应当使用多线程调度器，例外是某些小众用途，比如只需运行单个线程的情况。
  2. 是否存在从运行时上下文之外抵达spawn的路径。搜索同步函数里的tokio::spawn调用，并查看这些函数是否可能被另一个线程池调用。原文例子里的panic就发生在这样的路径上。
  3. Send约束是从哪里进来的。教程写道，跨越.await保留的数据是否全是Send，决定任务是不是Send。spawn的文档载有一个例子，把!Send的值限制在没有.await的作用域内。
  4. poll里面是否有会阻塞的调用。标准库文档的建议是，把可能耗时较长的工作转交给线程池之类的地方。Tokio的公平性保证建立在没有任务阻塞这一假设之上。
  5. 是否测量过future的大小。可以像原文的例子那样用std::mem::size_of_val测量。把很大的值跨越让出点保留着的参数，是首先要看的对象。
  6. 如果是库，它假设的是哪个运行时。备忘清单的表述是，任务的创建依赖于运行时。库所假设的运行时决定了它可以被使用的范围。

若是在线程和async之间做选择，原文给出的判断依据不是数值而是一个提问。无论选哪边，调度器都在。不同之处在于它待在哪里、它的行为在哪里能读到、它能否被替换。Tokio调度器的行为如前表所示，连同版本写在crate的文档里，那份文档甚至写明这些数值可能会变。
