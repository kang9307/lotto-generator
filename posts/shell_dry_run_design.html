--dry-run을 제대로 만드는 법 - 흉내가 아니라 검증

가짜 dry-run 다섯 유형을 실행 출력으로 재현하고 plan 해시로 증명한다

2026-07-29 개발/인프라

서론: dry-run이 「하겠다」고 한 것을 실행은 하지 못했다

정리 스크립트에 --dry-run을 붙였다. 돌려 보니 would delete가 열두 줄 나왔고, 목록도 예상과 같았다. 마음이 놓여서 실제로 실행했다. 그런데 중간에서 에러가 났고, 어떤 파일은 지워졌고 어떤 파일은 남았다. dry-run은 분명히 「이렇게 하겠다」고 말했는데, 실행은 그렇게 하지 못했다.

이 상황이 특별히 나쁜 이유는 결과가 틀렸다는 것 자체가 아니다. dry-run을 돌린 사람이 그 사이에 안심했다는 데 있다. 아무 검증도 하지 않았으면 조심스럽게 실행했을 텐데, 확인했다고 믿었기 때문에 그대로 밀어 버린 것이다. 검증하지 않은 상태보다 잘못 검증한 상태가 더 위험하다. 이것이 가짜 dry-run의 본질적인 해악이다.

널리 퍼진 오해가 하나 있다. 「dry-run은 실행할 명령을 출력만 하면 되는 것」이라는 생각이다. 아니다. 출력은 결과물일 뿐이다. dry-run이 값어치를 가지려면 실제로 실행했을 때와 같은 판단 경로를 타야 한다. 같은 조건을 평가하고, 같은 검사를 통과하고, 같은 순서로 대상을 고른 다음, 마지막 한 걸음인 「쓰기」만 하지 않는 것이다. 이 마지막 한 걸음의 위치가 어디냐에 따라 dry-run은 검증이 되기도 하고 흉내가 되기도 한다.

이 글은 정의를 설명하지 않는다. 가짜 dry-run 다섯 유형을 임시 디렉터리에서 직접 재현한 출력으로 시작해서, 그것을 어떻게 고치는지까지 간다. 순서는 이렇다. 먼저 다섯 유형을 하나씩 깨뜨려 보고, 그다음 plan과 apply를 가르는 형태를 만들어 3회 실행 해시가 같음을 증명한다. 이어서 종료 코드 규약과 CI 배선을 정리하고, 마지막으로 git clean -n과 rsync -n 같은 기존 도구의 dry-run을 어디까지 믿을 수 있는지 선을 긋는다.

범위를 미리 좁혀 둔다. 「두 번 돌려도 같은 결과인가」는 이 글의 주제가 아니다. 그쪽은 두 번 돌려도 안전한 스크립트에서 따로 다뤘다. 이 글의 질문은 하나다. 「돌리기 전에 결과를 알 수 있는가.」 두 성질은 서로를 돕지만 같은 것이 아니다. 멱등한 스크립트도 얼마든지 거짓말하는 dry-run을 가질 수 있다.

1. 실행 환경과 검증 방식

이 글의 모든 주장은 실제로 돌려 본 출력이다. 재현 환경은 다음과 같다.

  • OS: Windows 10 Pro 10.0.19045 위의 MSYS2 계열 유닉스 환경(Git Bash)
  • 셸: GNU bash 5.2.37(1)-release (x86_64-pc-msys)
  • 유틸리티: GNU coreutils 8.32, GNU tar 1.35, GNU Awk 5.0.0, git 2.48.1
  • 작업 위치: 임시 디렉터리 한 곳. 실험마다 하위 폴더를 새로 만들어 격리

리눅스 배포판이 아니라 MSYS2를 쓴 것은 손에 있던 환경이기 때문이고, 여기서 보이는 동작은 대부분 셸 문법과 POSIX 유틸리티 명세에서 나오는 것이라 배포판을 옮겨도 같다. 다만 다음 두 가지는 환경 의존이라 이 글에서 다루지 않았다.

  • 파일 권한과 소유권에 걸리는 실패 — 이 환경은 POSIX 권한 비트를 완전히 흉내 내지 않아 재현이 신뢰할 수 없다
  • rsync의 실제 동작 — 이 환경에 설치돼 있지 않아 실행하지 못했다. 12절에서는 공식 문서에 적힌 경계만 인용하고, 대신 같은 성격의 분기를 git으로 재현했다
⚠ 경고 — 이 글의 예제는 임시 디렉터리 전용입니다.
본문에는 rm, sed -i, git clean -f처럼 되돌릴 수 없는 명령이 나옵니다. 전부 새로 만든 임시 디렉터리 안에서만 실행했고, 그 밖에서 돌리도록 만들어진 코드가 아닙니다. 직접 확인하실 때는 빈 임시 디렉터리를 새로 만들어 그 안에서만 돌리시고, 실제 서버 경로나 홈 디렉터리에서는 실행하지 마십시오. 특히 git clean 계열은 추적되지 않는 파일을 복구 불가능하게 지웁니다.

2. 유형 ① 출력만 하고 판단은 하지 않는다

가장 흔한 형태다. 실행 지점마다 if로 갈라서, dry면 문장을 찍고 아니면 실제로 부른다.

clean() {
  for f in "$@"; do
    if [ -n "${DRY:-}" ]; then
      echo "would delete $f"
    else
      rm "$f"
    fi
  done
}

대상 디렉터리에 a.log와 c.log는 만들고, ghost.log는 일부러 만들지 않은 채 세 개를 모두 인자로 넘겼다.

### 대상 디렉터리 상태
a.log
c.log

### DRY=1 (가짜 dry-run)
would delete a.log
would delete ghost.log
would delete c.log
exit=0

### 실제 실행
rm: cannot remove 'ghost.log': No such file or directory
exit=0

### 실행 후 남은 것
(없음)

dry-run은 존재하지도 않는 파일을 지우겠다고 말했다. 이유는 간단하다. echo 쪽 경로는 파일이 있는지 한 번도 묻지 않는다. 반면 rm은 대상을 실제로 조회한다. 두 경로가 답하는 질문이 애초에 다르다.

  • dry-run이 답한 질문: 「루프에 어떤 인자가 들어왔는가」
  • 실제 실행이 답한 질문: 「그 인자가 가리키는 대상이 지금 존재하며 지울 수 있는가」

정리하면 이 dry-run이 보여 준 것은 실행 결과의 예측이 아니라 인자 목록의 복창이다. 목록이 맞다는 것과 실행이 성공한다는 것은 완전히 다른 명제인데, 출력 형식이 would ...라서 후자로 읽힌다.

출력에 하나 더 숨어 있다. 실제 실행도 종료 코드 0을 돌려줬다. ghost.log에서 오류가 났는데도 그렇다. 루프의 마지막 명령인 rm c.log가 성공했고, 함수의 종료 상태는 마지막으로 실행된 명령의 것이기 때문이다. 이 문제는 6절에서 따로 다룬다.

고치는 방향은 「검사를 dry 쪽에도 복사해 넣기」가 아니다. 판단을 한 번만 계산하고 두 모드가 그 결과를 공유하게 만드는 것이다. 복사해 넣으면 두 벌의 조건문이 생기고, 다음 사람이 한쪽만 고친다.

3. 유형 ② 조건이 실행 경로에만 있다

①을 겪은 사람은 대개 검사를 추가한다. 그런데 검사가 실행 분기 안쪽에 들어가면 상황은 오히려 나빠진다. dry-run이 더 그럴듯해 보이면서 여전히 틀리기 때문이다.

for f in src/*.dat; do
  base=${f#src/}
  if [ -n "${DRY:-}" ]; then
    echo "would archive $base"
    continue                 # ← 여기서 나머지 검사를 전부 건너뛴다
  fi
  # ↓ 아래 두 검사는 실제 실행 경로에만 있다
  if ! mkdir "$LOCK" 2>/dev/null; then
    echo "ERROR: another run holds $LOCK" >&2; exit 3
  fi
  size=$(wc -c < "$f")
  if [ $((used + size)) -gt "$QUOTA" ]; then
    echo "ERROR: quota exceeded at $base (used=$used +$size > $QUOTA)" >&2
    rmdir "$LOCK"; exit 4
  fi
  cp "$f" "dst/$base"
  ...
done

200바이트짜리 파일 5개를 총량 상한 500바이트인 대상에 넣어 봤다.

### DRY=1 — 5건 전부 가능하다고 보고
would archive f1.dat
would archive f2.dat
would archive f3.dat
would archive f4.dat
would archive f5.dat
exit=0

### 실제 실행 — 같은 입력, 같은 순서
archived f1.dat (used=200)
archived f2.dat (used=400)
ERROR: quota exceeded at f3.dat (used=400 +200 > 500)
exit=4

### dst 실제 결과
dst/f1.dat
dst/f2.dat

dry-run은 5건을 약속했고 실제로는 2건에서 멈췄다. 게다가 부분 적용 상태가 남았다. 락도 마찬가지다. 다른 실행이 락을 잡고 있는 상태에서 다시 돌려 봤다.

### 락이 이미 잡혀 있을 때 (다른 실행 중)
-- DRY=1 --
would archive f1.dat
would archive f2.dat
would archive f3.dat
would archive f4.dat
would archive f5.dat
exit=0
-- 실제 --
ERROR: another run holds .archive.lock
exit=3

dry-run은 지금 이 스크립트가 아예 시작할 수도 없다는 사실조차 알려 주지 못했다. 락 검사가 실행 경로 안에 있기 때문이다. 실무에서 이런 조건은 생각보다 흔하다.

  • 디스크 여유 공간·inode·쿼터 — 쓰기 직전에야 확인하도록 짜기 쉽다
  • 동시 실행 락 — 「실제로 뭔가 할 때만 잡으면 되지」라는 판단으로 실행 분기에 넣게 된다
  • 대상 서비스의 헬스 체크 — dry-run에서는 굳이 붙지 않는다
  • 인증·토큰 유효성 — dry-run이 원격에 접속하지 않으면 만료를 못 잡는다
  • 누적 상태 — 위 예처럼 앞 항목을 처리해야 다음 항목의 판정이 정해지는 경우

교훈은 명확하다. 실행 가능성을 좌우하는 검사는 실행 분기가 아니라 그 앞에 있어야 한다. 락과 쿼터를 루프 밖 「사전 점검」으로 끌어올리면 두 모드가 같은 검사를 통과하게 된다. 8절의 plan 구조는 이것을 강제하는 형태다.

4. 유형 ③ dry-run이 부작용을 남긴다

「아무것도 안 바꾸는 모드」인데 파일을 만들고 지운다면 이름이 거짓말인 셈이다. 그런데 이건 부주의가 아니라 셸의 평가 순서에서 자연스럽게 생기는 사고다. 아래 스크립트를 dry-run으로만 돌렸다.

WORK=$(mktemp -d "./tmp.XXXXXX")     # ① 모드와 무관하게 생성
mkdir -p logs                         # ② 마찬가지
exec 3>> logs/run.log                 # ③ 파일이 없으면 여기서 생긴다
echo "start $$" >&3

collect() {                           # ④ 리다이렉션은 분기 밖에서 평가된다
  if [ -z "${DRY:-}" ]; then
    printf 'row-%s\n' 1 2 3
  else
    echo "would write 3 rows" >&2
  fi
} > report.csv

collect
### 실행 전 상태
./report.csv
./report.sh
--- report.csv 내용 ---
old-report-do-not-lose-me

### DRY=1 로만 실행
would write 3 rows
exit=0

### 실행 후 상태 (dry-run 이었는데)
./logs
./logs/run.log
./report.csv
./report.sh
./tmp.XlPBYU
--- report.csv 내용 ---
(0바이트 — 내용이 사라졌다)
--- logs/run.log ---
start 1945
done

dry-run 한 번으로 임시 디렉터리가 생겼고, 로그 디렉터리와 로그 파일이 생겼고, 무엇보다 기존 데이터가 들어 있던 report.csv가 0바이트가 됐다. ④가 핵심이다. 함수 뒤에 붙은 > report.csv는 함수가 실행되는 순간 셸이 먼저 여는 것이라, 안에서 어느 분기를 타든 상관없이 파일이 잘린다. 「출력할 게 없으면 안 건드리겠지」라는 직관이 정확히 틀리는 지점이다.

같은 함정이 래퍼 함수에서도 나온다. 실행을 감싸는 run 함수를 만들고 리다이렉션을 붙이면 이렇게 된다.

run(){ if [ -n "${DRY:-}" ]; then echo "+ would run: $*"; else "$@"; fi; }
run printf 'migrated=%s\n' 3 > state.txt
--- 실행 전 state.txt ---
migrated=99
--- DRY=1 실행 후 state.txt ---
+ would run: printf migrated=%s\n 3

안내 문구가 상태 파일 안으로 들어갔다. 다음 실행이 이 파일을 읽는 순간 무슨 일이 벌어질지는 상상에 맡긴다. dry-run이 남기지 말아야 할 것을 목록으로 정리하면 이렇다.

  • 대상 파일의 절단·생성·삭제 — 리다이렉션 위치를 분기 안으로 옮긴다
  • 임시 디렉터리 — 필요하면 apply 단계에서만 만들고 trap으로 정리한다
  • 로그 파일 — dry-run 출력은 표준 출력·표준 오류로 보내고 파일에 쓰지 않는다
  • 락 파일 — 읽기 전용 계획에는 필요 없다. 「락을 잡을 수 있는가」는 검사만 한다
  • 원격 상태 변경 — 토큰 갱신·세션 생성·큐 소비처럼 조회처럼 보이지만 상태를 바꾸는 호출
  • 캐시·인덱스 — 다음 실행의 판단을 바꾸므로 부작용이다
확인하는 법. dry-run 직전과 직후에 작업 트리의 파일 목록과 각 파일의 크기·해시를 찍어 비교하면 끝난다. 한 줄이라도 다르면 그 dry-run은 이름값을 못 하고 있는 것이다. 이 비교는 CI에 그대로 넣을 수 있다.

5. 유형 ④ 뒤 단계가 앞 단계 결과에 의존한다

앞의 세 유형은 코드를 고치면 없어진다. 이번 것은 다르다. 단계가 사슬로 이어져 있으면 dry-run은 원리적으로 뒤를 예측할 수 없다. 3단계 마이그레이션을 만들어 봤다. 1단계는 압축을 풀고, 2단계는 풀린 설정 파일을 치환하고, 3단계는 2단계의 건수에 따라 상태를 기록한다.

run() { if [ -n "${DRY:-}" ]; then echo "+ would run: $*"; else "$@"; fi; }

echo "[1/3] 릴리스 전개"
run mkdir -p release
run tar -xf release.tar -C release

echo "[2/3] 설정 치환"
n=0
for c in release/*.conf; do
  [ -e "$c" ] || continue
  n=$((n+1))
  run sed -i 's/^mode=old$/mode=new/' "$c"
done
echo "    대상 ${n}건"

echo "[3/3] 후처리"
if [ "$n" -gt 0 ]; then ... else echo "    변경 대상이 없어 건너뜀"; fi
### DRY=1 (계획을 물어본 결과)
[1/3] 릴리스 전개
+ would run: mkdir -p release
+ would run: tar -xf release.tar -C release
[2/3] 설정 치환
    대상 0건
[3/3] 후처리
    변경 대상이 없어 건너뜀
exit=0

### 실제 실행
[1/3] 릴리스 전개
[2/3] 설정 치환
    대상 3건
[3/3] 후처리
    state 기록
exit=0

### 실제로 바뀐 파일
release/app.conf:mode=new
release/db.conf:mode=new
release/web.conf:mode=new
--- migrate.state ---
migrated=3

dry-run은 「2단계 대상 0건, 3단계 건너뜀」이라고 답했고, 실제 실행은 3건을 바꾸고 상태 파일까지 썼다. 래퍼 함수는 완벽하게 동작했다. 문제는 래퍼가 아니라 구조다. 1단계를 실행하지 않았으므로 2단계가 볼 입력이 존재하지 않았고, 2단계의 결과가 0이었으므로 3단계 분기가 통째로 뒤집혔다.

여기서 가장 나쁜 것은 침묵이다. dry-run은 「모르겠다」고 하지 않고 「할 일이 없다」고 단언했다. 사용자가 받는 인상은 정반대다. 이 유형을 다루는 방법은 세 가지뿐이고, 모두 트레이드오프가 있다.

방법내용대가
범위 축소dry-run이 예측하는 범위를 첫 단계까지로 못 박고, 그 이후는 (예측 불가)로 표시정보량은 줄지만 거짓말은 사라진다
상태 모델링계획 단계에서 아카이브 목록을 미리 읽어 「전개 후 존재할 파일」을 계산모델과 실제가 어긋날 수 있어 모델 자체를 검증해야 한다
격리 실행임시 작업 공간에 실제로 1단계를 수행하고 그 위에서 2·3단계를 계획가장 정확하지만 비용이 크고 부작용 경계를 다시 그려야 한다

실무에서 대부분은 첫 번째를 택하는 것이 맞다. 모르는 것을 모른다고 말하는 dry-run이, 아는 척하는 dry-run보다 훨씬 쓸모 있다. 압축 해제 예시라면 tar -tf로 목록만 읽어 두 번째 방법을 싸게 흉내 낼 수도 있다.

6. 유형 ⑤ 언제나 0을 돌려준다

지금까지 나온 모든 실행에서 종료 코드를 같이 찍었다. 다시 보면 이상한 점이 있다. 2절의 실제 실행은 오류 메시지를 내고도 exit=0이었고, dry-run은 예외 없이 전부 exit=0이었다.

dry-run이 늘 0을 돌려주면 사람이 눈으로 읽어야만 정보가 전달된다. 사람이 읽는 것을 전제하는 도구는 자동화에 붙일 수 없다. CI에서 「설정 드리프트가 있으면 빌드를 세운다」를 하려면 드리프트 여부가 종료 코드로 나와야 한다.

여기서 실수하기 쉬운 지점이 있다. 0과 1만 쓰면 「변경 있음」과 「계획 실패」가 같은 값이 된다. 이 둘은 CI에서 정반대로 다뤄야 하는 사건이다. 전자는 사람이 승인하면 되는 일이고, 후자는 파이프라인이 고장 난 것이다. 그래서 세 값이 필요하다. 구체적인 규약과 배선은 10절에서 다룬다.

7. 다섯 유형 정리 - 어디를 보면 알 수 있나

여기까지 재현한 것을 한 표로 접었다. 남의 스크립트를 5분 안에 판정할 때 쓰는 표다.

유형증상코드에서 찾는 신호재현된 결과
① 판단 없는 출력없는 대상도 하겠다고 함실행 지점마다 if DRY가 반복됨없는 파일에 would delete, 실제는 오류
② 실행 경로 전용 조건락·용량 문제를 미리 못 알림dry 분기 뒤의 continue·returndry 5건 성공 예측 → 실제 2건 후 exit=4
③ 부작용 잔존dry-run인데 파일이 바뀜분기 밖 리다이렉션, mktemp, exec N>기존 파일이 0바이트로 절단
④ 연쇄 의존뒤 단계를 0건으로 오보앞 단계 산출물을 for·find로 다시 읽음dry 0건·건너뜀 → 실제 3건·상태 기록
⑤ 무의미한 종료 코드CI에서 못 씀항상 exit 0, 값 구분 없음오류를 내고도 exit=0

다섯 유형에는 공통점이 하나 있다. 전부 오류를 내지 않는다. ①~⑤ 어디에서도 스크립트가 「dry-run이 정확하지 않습니다」라고 말해 주지 않는다. 그래서 코드 리뷰에서 잡히지 않고, 사고가 난 뒤에야 발견된다.

8. 올바른 형태 - plan과 apply를 가른다

다섯 유형을 한 번에 없애는 구조가 있다. 「무엇을 할지」를 먼저 계산해 목록으로 만들고, 실행 모드는 그 목록을 소비만 하는 것이다. 인프라 도구들이 plan과 apply라고 부르는 그 구조다.

핵심 규칙은 두 줄이다.

  • plan은 상태를 읽기만 한다. 쓰기·생성·삭제·락 획득이 전혀 없다. 출력은 정렬돼 있고 시각·난수가 섞이지 않는다
  • apply는 판단하지 않는다. 계획 줄을 읽어 해당 동작만 수행한다. 조건문이 없으므로 두 모드가 갈릴 여지가 사라진다
# ---------- plan: 읽기만 한다. 어떤 파일도 만들지 않는다 ----------
make_plan() {
  [ -d "$REQ_DIR" ] || printf 'MKDIR\t%s\tarchive 디렉터리 없음\n' "$REQ_DIR"
  for f in "$ROOT"/*; do
    [ -f "$f" ] || continue
    case "$f" in
      *.tmp)  printf 'DELETE\t%s\t임시 파일\n' "$f" ;;
      *.log)  if [ -s "$f" ]; then printf 'ARCHIVE\t%s\t내용 있음\n' "$f"
              else                 printf 'DELETE\t%s\t0바이트\n' "$f"; fi ;;
      *.conf) if grep -qxF 'mode=old' "$f"; then
                printf 'PATCH\t%s\tmode=old\n' "$f"; fi ;;
    esac
  done
}

# ---------- apply: 계획만 소비한다. 스스로 판단하지 않는다 ----------
do_apply() {
  local plan="$1" action path reason
  while IFS=$'\t' read -r action path reason; do
    [ -n "${action:-}" ] || continue
    case "$action" in
      MKDIR)   mkdir -p -- "$path"  && echo "ok MKDIR   $path" ;;
      DELETE)  rm -f -- "$path"     && echo "ok DELETE  $path" ;;
      ARCHIVE) mkdir -p -- "$REQ_DIR"; mv -- "$path" "$REQ_DIR/" && echo "ok ARCHIVE $path" ;;
      PATCH)   sed -i 's/^mode=old$/mode=new/' -- "$path" && echo "ok PATCH   $path" ;;
      *)       echo "unknown action: $action" >&2; return 1 ;;
    esac
  done < "$plan"
}

case "${1:-}" in
  plan)  make_plan | LC_ALL=C sort
         n=$(make_plan | grep -c . || true)
         [ "$n" -eq 0 ] && exit 0 || exit 2 ;;
  apply) do_apply "${2:?계획 파일이 필요합니다}" ;;
esac

3회 실행해 해시가 같음을 증명한다

주장으로 끝내면 의미가 없다. 같은 상태에서 계획을 세 번 세우고 바이트 단위로 비교했다.

### plan 3회 — 출력과 해시
run#1 exit=2 sha256=072c4bfb98ee74f7be43c92b2f7824a9c5aa926211cc9df111b84d1645b7cc0f
run#2 exit=2 sha256=072c4bfb98ee74f7be43c92b2f7824a9c5aa926211cc9df111b84d1645b7cc0f
run#3 exit=2 sha256=072c4bfb98ee74f7be43c92b2f7824a9c5aa926211cc9df111b84d1645b7cc0f
--- plan 내용 (run#1) ---
ARCHIVE data/access.log 내용 있음
DELETE  data/build.tmp  임시 파일
DELETE  data/cache.tmp  임시 파일
DELETE  data/empty.log  0바이트
MKDIR   data/archive    archive 디렉터리 없음
PATCH   data/app.conf   mode=old
--- 3회 비교 ---
IDENTICAL: 3회 모두 바이트 단위로 같음

### plan 이 부작용을 남겼는가
access.log app.conf build.tmp cache.tmp db.conf empty.log

세 번 모두 072c4bfb98ee...로 같았고, 실행 후 디렉터리에는 파일이 하나도 늘지 않았다. 4절에서 본 부작용이 여기서는 구조적으로 불가능하다. plan에 쓰기 명령이 아예 없기 때문이다.

이제 계획을 소비시켜 보자.

### apply — 계획만 소비
ok ARCHIVE data/access.log
ok DELETE  data/build.tmp
ok DELETE  data/cache.tmp
ok DELETE  data/empty.log
ok MKDIR   data/archive
ok PATCH   data/app.conf
exit=0

### apply 후 다시 plan
exit=0 (0=변경 없음)
--- data 최종 상태 ---
data/app.conf data/archive data/archive/access.log data/db.conf

apply 후 다시 계획을 세우니 빈 계획과 종료 코드 0이 나왔다. 이것이 이 구조의 마지막 장점이다. 「계획이 비었다」는 사실 자체가 목표 상태에 도달했다는 증거가 된다. 별도의 검증 스크립트가 필요 없다.

plan이 결정적이려면. 출력에 date·$RANDOM·프로세스 ID·순회 순서를 넣지 마십시오. for f in dir/*의 순서는 로케일에 따라 달라질 수 있으므로 LC_ALL=C sort로 고정합니다. 계획에 이유 컬럼을 넣으면 사람이 읽을 수 있고, 해시 비교도 그대로 유지됩니다.

9. 계획이 낡았을 때 - plan 해시로 잠근다

plan과 apply를 나누면 새로운 틈이 생긴다. 계획을 세운 시점과 적용하는 시점 사이에 상태가 바뀔 수 있다. 승인 절차가 끼면 이 간격은 몇 시간이 되기도 한다. 그 사이 누군가 파일을 추가하면, 승인받은 계획과 실제로 벌어질 일이 달라진다.

해법은 앞 절에서 이미 만들어 뒀다. 계획의 해시를 함께 저장하고, apply가 실행 직전에 현재 상태로 계획을 다시 계산해 해시를 대조하면 된다. 다르면 거부한다.

apply)
  want=$(sed -n '1p' "$p.sha" 2>/dev/null || echo '')
  have=$(make_plan | LC_ALL=C sort | sha256sum | cut -d' ' -f1)
  if [ -n "$want" ] && [ "$want" != "$have" ]; then
    echo "ERROR: 계획 이후 상태가 바뀌었습니다 (plan=$want / now=$have)" >&2
    exit 1
  fi
  do_apply "$p" ;;
### 1) 계획 수립
plan exit=2
988ca65d91ce2783486a7216bdfb8dca47db67b8e1af3c0a664080c127aeab83
DELETE  data/cache.tmp  임시 파일
MKDIR   data/archive    archive 디렉터리 없음
PATCH   data/app.conf   mode=old

### 2) 계획과 실행 사이에 다른 사람이 파일을 추가
app.conf cache.tmp late.tmp

### 3) 낡은 계획으로 apply
ERROR: 계획 이후 상태가 바뀌었습니다 (plan=988ca65d... / now=84f56a62...)
exit=1

### 4) 계획을 다시 세우면 통과
plan exit=2
ok DELETE  data/cache.tmp
ok DELETE  data/late.tmp
ok MKDIR   data/archive
ok PATCH   data/app.conf
apply exit=0

3단계에서 apply가 실행을 거부했다. 승인받은 계획에 late.tmp가 없었기 때문이다. 4단계에서 계획을 다시 세우자 late.tmp가 포함됐고 통과했다. 이 한 겹으로 얻는 것이 크다.

  • 승인의 의미가 살아난다 — 사람이 승인한 목록과 실제 실행되는 목록이 같음을 기계가 보증한다
  • 경쟁 상태를 조기에 잡는다 — 두 파이프라인이 동시에 돌면 뒤엣것이 거부된다
  • 재현 가능한 사후 분석 — 계획 파일과 해시가 남으므로 「무엇을 왜 했는지」가 기록된다

주의할 점도 있다. 해시 대조는 계획을 한 번 더 계산하므로 대상이 크면 비용이 든다. 그리고 무관한 변화까지 거부한다. 위 예에서 late.tmp는 실제로 계획에 영향을 줬지만, 계획과 무관한 파일 하나가 생겨도 계획 내용이 그대로라면 해시는 같으므로 통과한다. 해시는 계획을 잠그는 것이지 디렉터리를 잠그는 것이 아니다. 이 구분이 이 방식의 실용성을 만든다.

10. 종료 코드 규약과 CI 배선

6절에서 미룬 문제로 돌아온다. 널리 쓰이는 규약은 세 값이다.

코드뜻CI 동작사람이 할 일
0변경 없음 — 목표 상태와 일치통과없음
2적용 대기 변경 있음실패 처리 또는 승인 대기계획을 읽고 승인·수정
1계획을 세우지 못함(오류)즉시 실패 + 알림파이프라인 수리

2를 「변경 있음」에 배정하는 것은 관용이다. 진단 도구들이 오랫동안 「정상」·「차이 있음」·「실행 실패」를 0·1·2로 나눠 온 흐름과 같은 발상이고, 여기서는 오류에 흔한 1을 남겨 두기 위해 2를 썼다. 무엇을 쓰든 세 상태를 구분한다는 점이 중요하다.

배선에서 실제로 걸리는 세 가지

규약을 정해도 셸 배선에서 무너진다. 세 가지를 재현했다.

### A) set -e 아래에서 그냥 호출하면
exit=2
   (「여기까지 왔습니다」가 출력되지 않았다 — 뒤 단계가 통째로 실행 안 됨)

### B) if 로 감싸면 2와 1을 구분하지 못한다
변경 있음(또는 오류)     ← 정상적인 「변경 있음」(2)
변경 있음(또는 오류)     ← 잘못된 서브커맨드로 낸 오류(1)
exit=0

### D) 파이프에 물리면 종료 코드가 tee 의 것이 된다
$?=0  PIPESTATUS=2 0

A는 가장 자주 보는 사고다. set -e는 0이 아닌 값을 전부 실패로 보므로, 「변경 있음」을 뜻하는 2가 스크립트를 죽인다. B는 더 조용하다. if는 0인지 아닌지만 보므로 2와 1이 같은 가지로 떨어진다. 위 출력에서 두 줄은 각각 정상적인 드리프트와 진짜 오류인데 메시지가 똑같다. D는 | tee로 계획을 파일에도 남길 때 걸린다. 파이프라인의 종료 상태는 마지막 명령의 것이라 tee의 0이 남는다.

세 함정을 모두 피하는 형태는 이렇다.

#!/usr/bin/env bash
set -uo pipefail
rc=0
./tidy.sh plan > plan.txt || rc=$?          # ← 실패해도 스크립트를 죽이지 않고 코드를 받는다
case "$rc" in
  0) echo "OK: 목표 상태와 일치 (변경 0건)"; exit 0 ;;
  2) echo "DRIFT: 적용 대기 $(grep -c . plan.txt)건"; sed 's/^/    /' plan.txt; exit 1 ;;
  *) echo "FAIL: 계획 수립 실패 (rc=$rc)" >&2; exit 2 ;;
esac
### C) 규약대로 세 갈래로 나누면
DRIFT: 적용 대기 3건
    DELETE  data/cache.tmp  임시 파일
    MKDIR   data/archive    archive 디렉터리 없음
    PATCH   data/app.conf   mode=old
CI 종료=1

### E) 적용 후 같은 CI 를 다시 돌리면
apply exit=0
OK: 목표 상태와 일치 (변경 0건)
CI 종료=0

드리프트가 있으면 계획을 로그에 그대로 펼쳐 놓고 빌드를 세웠고, 적용한 뒤에는 같은 잡이 통과했다. CI에 붙일 때 실무적으로 챙길 것들을 정리한다.

  • 플래그를 바꾸지 말 것 — 계획을 만든 명령줄과 적용하는 명령줄은 대상·필터·제외 규칙이 완전히 같아야 한다
  • 계획을 산출물로 저장 — 빌드 아티팩트로 남기면 승인·감사·사후 분석이 전부 이 파일 하나로 된다
  • PR에는 plan만, 병합 후에 apply — 승인 단계를 종료 코드 2에 붙인다
  • 정기 실행으로 드리프트 감시 — 하루 한 번 plan만 돌려 2가 나오면 알린다. 아무도 배포하지 않았는데 2가 나오면 손으로 바꾼 사람이 있다는 뜻이다
  • 스케줄 잡에서는 2를 실패로 올리지 말 것 — 알림은 보내되 빨간불을 상시로 켜 두면 아무도 안 본다
  • pipefail과 PIPESTATUS — 파이프에 물릴 때 어느 쪽 코드를 볼 것인지 명시적으로 정한다

11. 기존 도구의 dry-run은 어디까지 믿을 수 있나

직접 만드는 이야기를 했으니, 이미 있는 도구는 어떤지 봐야 한다. 결론부터 말하면 널리 쓰이는 도구의 dry-run은 대체로 신뢰할 수 있고, 무엇보다 스스로 경계를 문서에 적어 두었다. 문제는 도구가 아니라 사람이 두 실행 사이에 플래그를 바꾸는 순간에 생긴다.

재현 - 같은 도구, 다른 플래그

임시 저장소를 만들어 추적되지 않는 파일과 디렉터리, 무시 규칙에 걸린 디렉터리, 그리고 중첩된 별도 저장소를 넣고 확인했다.

### git clean -n (기본)
Would remove .gitignore

### git clean -nd (디렉터리 포함)
Would remove .gitignore
Would remove work/

### git clean -ndx (무시 파일까지)
Would remove .gitignore
Would remove ignored/
Would remove work/

### 실제 실행: git clean -fd
Removing .gitignore
Removing work/

### 남은 것
./ignored  ./ignored/c.txt  ./nested  ./nested/.git  ./nested/n.txt

세 dry-run의 답이 전부 다르다. 그리고 각각은 같은 플래그로 실행했을 때의 결과와 정확히 일치한다. 공식 문서가 그대로 설명하고 있다. -n은 「아무것도 실제로 제거하지 않고 무엇이 될지만 보여 준다」이고, -d는 「보통은 너무 많이 지우는 것을 피하려고 추적되지 않는 디렉터리로 재귀하지 않으며, -d를 주면 그런 디렉터리까지 재귀한다」이다.

그러니까 사고는 이렇게 난다. git clean -n으로 확인하고 git clean -fd로 실행하는 것. 위 출력에서 -n은 .gitignore 한 줄만 보여 줬는데, -fd는 파일 두 개가 든 work/ 트리를 통째로 지웠다. dry-run이 거짓말한 것이 아니라 다른 질문에 답한 것이다. 하나 더, -nd가 보여 준 Would remove work/는 한 줄이다. 그 안에 파일이 몇 개인지는 알려 주지 않는다. 지워질 개수를 알고 싶으면 --dry-run 출력을 세는 것으로는 부족하다.

중첩 저장소도 흥미롭다. -ndx는 nested/를 목록에 아예 넣지 않았고, -ndxff를 주자 그때 나타났다. 문서에 「Git은 .git 하위 디렉터리를 가진 추적되지 않는 중첩 저장소를 두 번째 -f가 주어지지 않는 한 수정하기를 거부한다」고 적혀 있다. dry-run이 실제 동작을 그대로 반영한 것이지 누락이 아니다.

도구가 스스로 밝힌 경계

이 환경에는 rsync가 없어 실행하지 못했다. 대신 공식 문서가 적어 둔 경계를 인용한다. 이 문단은 실행 검증이 아니라 문서 인용임을 밝혀 둔다.

rsync 문서는 --dry-run이 「실제 실행과 대체로 같은 출력」을 내는 시험 실행이라고 설명한다. 그러면서 dry run은 실제 데이터를 보내지 않으므로 --progress가 효과가 없고, bytes sent·bytes received·literal data·matched data 통계가 실제보다 작게 나오며, speedup 값은 전송이 필요 없었던 실행과 같아진다고 밝힌다. 반면 --itemize-changes 출력은 dry run과 이어지는 실제 실행에서 정확히 같아야 하며, 그렇지 않다면 그것은 버그라고 못 박는다.

이 서술은 잘 만든 dry-run이 어떤 모습이어야 하는지를 그대로 보여 준다. 「무엇을 바꿀 것인가」는 정확히 같고, 「얼마나 걸리고 몇 바이트가 오갈 것인가」는 다르다고 항목별로 선을 그은 것이다. 우리가 직접 만들 때도 같은 태도가 필요하다. 예측하는 축과 예측하지 못하는 축을 도움말에 적어 두는 것이 곧 신뢰다.

기존 도구를 쓸 때의 실무 규칙은 짧다.

  • 같은 명령줄을 쓴다 — 확인은 -n만 더한 형태로. 실행할 때 다른 플래그를 덧붙이지 않는다
  • 파일 목록을 산출물로 남긴다 — dry-run 출력을 파일로 저장해 실행 후 결과와 대조한다
  • 개수는 세지 말고 항목을 본다 — 디렉터리 한 줄이 파일 수백 개일 수 있다
  • 문서의 「예외」 절을 읽는다 — 잘 만든 도구는 자신이 예측 못 하는 것을 적어 둔다
  • 원격이 끼면 한 번 더 의심한다 — 권한·경로·타임스탬프 해석이 양쪽에서 다를 수 있다

12. dry-run이 끝내 예측하지 못하는 것들

아무리 잘 설계해도 남는 영역이 있다. 이 목록을 도움말에 적어 두는 것이 「정직한 dry-run」의 마지막 조건이다.

예측 못 하는 것왜완화
시간 경과계획 시점과 적용 시점이 다르다. 보존 기간·만료·크론 경계가 그 사이에 넘어간다계획에 판정 기준 시각을 박아 넣고 apply에 넘긴다
동시 변경다른 프로세스·사람이 같은 대상을 만진다9절의 계획 해시 대조 + 적용 중 락
자원 고갈디스크·inode·메모리는 쓰는 순간에야 부족해진다계획 단계에서 총량을 계산해 여유와 비교(근사치임을 표시)
권한과 정책실행 사용자·보안 모듈·마운트 옵션이 쓰기 시점에 개입한다대표 경로 하나에 시험 쓰기를 해 보거나, 예측 불가로 표시
원격 상태API 응답·서버 측 검증·요율 제한은 호출해 봐야 안다제공되면 서버의 검증 전용 모드를 쓴다
연쇄 산출물5절 — 앞 단계 결과가 뒤 단계 입력이다범위를 첫 단계로 못 박거나 목록만 미리 읽는다
부분 실패 이후중간에 멈추면 계획의 나머지는 다른 상태 위에서 실행된다실패 시 즉시 중단하고 계획을 다시 세운다

표의 마지막 줄이 특히 중요하다. 계획은 「계획을 세운 그 상태」 위에서만 유효하다. 절반쯤 적용하다 실패했다면 남은 절반을 그대로 밀어붙이면 안 된다. 계획을 버리고 다시 세우는 것이 옳고, 8절 구조에서는 그게 명령 한 번이다.

결론: dry-run은 모드가 아니라 함수다

이 글에서 재현한 다섯 유형에는 공통점이 있었다. 전부 조용히 틀린다. 없는 파일을 지우겠다고 말하고, 5건이 된다고 해 놓고 2건에서 멈추고, 아무것도 안 바꾸겠다면서 기존 파일을 비우고, 할 일이 없다고 단언한 뒤 3건을 바꾸고, 그러면서 종료 코드는 언제나 0이다. 어느 것도 「제 예측은 부정확합니다」라고 말해 주지 않는다.

그래서 판정 기준은 하나로 줄어든다. 「dry-run이 실제 실행과 같은 판단을 거쳤는가.」 같은 조건을 평가하고 같은 순서로 대상을 골랐다면 그 출력은 예측이다. 인자 목록만 복창했다면 그것은 흉내다. 그리고 이 질문에 확실히 「예」라고 답하는 방법은 지금까지 하나뿐이었다. 판단을 한 곳에만 두는 것 — 즉 plan이 혼자 판단하고 apply는 소비만 하게 만드는 것이다.

이 구조가 좋은 이유는 세 가지다. 첫째, 두 모드가 갈릴 코드가 존재하지 않는다. 유형 ①·②는 구조적으로 발생하지 못한다. 둘째, 검증이 공짜로 따라온다. 3회 실행 해시 비교로 결정성을, 적용 후 빈 계획으로 수렴을 확인할 수 있다. 셋째, 승인과 감사가 파일 하나로 된다. 계획 파일과 그 해시가 곧 기록이다.

마지막으로 오늘 할 수 있는 일 하나. 손에 있는 스크립트의 dry-run을 빈 임시 디렉터리에서 돌려 보고, 실행 전후의 파일 목록과 해시를 비교하는 것. 한 줄이라도 다르면 그 dry-run은 이미 무언가를 바꾸고 있는 중이다. 그리고 종료 코드를 찍어 보시라. 언제나 0이라면, 그 dry-run은 사람이 화면을 읽어 줄 때만 작동하는 장치다. 읽히지 않는 안전장치는 안전장치가 아니다.

# dry-run 설계 지침 — 만들기 전에 훑는 목록

> 출처: braindetox.kr — --dry-run을 제대로 만드는 법
> 근거: POSIX Issue 8 (Shell Command Language), Bash Reference Manual, git-clean(1), rsync(1)
> 이 파일을 그대로 AI에 붙여 「우리 스크립트를 이 기준으로 고쳐줘」라고 쓰면 됩니다.

## 1. plan / apply 분리 골격 — 붙여 쓰는 형태

```bash
#!/usr/bin/env bash
# usage: tool.sh plan|apply [계획파일]
#   종료 코드  0=변경 없음 · 2=변경 있음 · 1=오류
set -uo pipefail
TAB=$(printf '\t')          # ANSI-C 인용 대신 변수로 (이식성)

make_plan() {               # ★읽기만 한다. 생성·삭제·락 취득 금지
  [ -d "$REQ_DIR" ] || printf 'MKDIR%s%s%s없음\n' "$TAB" "$REQ_DIR" "$TAB"
  for f in "$ROOT"/*; do
    [ -f "$f" ] || continue
    case "$f" in
      *.tmp) printf 'DELETE%s%s%s임시 파일\n' "$TAB" "$f" "$TAB" ;;
    esac
  done
}

do_apply() {                # ★판단하지 않는다. case 에 없는 액션은 오류
  local plan="$1" action path reason
  while IFS="$TAB" read -r action path reason; do
    [ -n "${action:-}" ] || continue
    case "$action" in
      MKDIR)  mkdir -p -- "$path" ;;
      DELETE) rm -f -- "$path" ;;
      *) echo "unknown action: $action" >&2; return 1 ;;
    esac
  done < "$plan"
}

case "${1:-}" in
  plan)
    make_plan | LC_ALL=C sort
    n=$(make_plan | grep -c . || true)
    [ "$n" -eq 0 ] && exit 0 || exit 2 ;;
  apply)
    p="${2:?계획 파일이 필요합니다}"
    want=$(cat "$p.sha" 2>/dev/null || echo '')
    have=$(make_plan | LC_ALL=C sort | sha256sum | cut -d' ' -f1)
    [ -z "$want" ] || [ "$want" = "$have" ] || {
      echo "계획이 낡았습니다 (plan=$want now=$have)" >&2; exit 1; }
    do_apply "$p" ;;
  *) echo "usage: tool.sh plan|apply [planfile]" >&2; exit 1 ;;
esac
```

- [ ] plan 안에 쓰기 명령이 **한 줄도** 없다
- [ ] apply 안에 상태를 보는 **조건문이 없다**
- [ ] 계획 줄에 **이유 컬럼**이 있다 (사람이 승인할 수 있어야 한다)
- [ ] 출력을 `LC_ALL=C sort` 로 고정했다

## 2. 종료 코드 규약

| 코드 | 뜻 | CI 동작 |
|---|---|---|
| `0` | 변경 없음 — 목표 상태와 일치 | 통과 |
| `2` | 적용 대기 변경 있음 | 실패 처리 또는 승인 대기 |
| `1` | 계획을 세우지 못함 | 즉시 실패 + 알림 |

- [ ] `set -e` 아래에서 `rc=0; cmd || rc=$?` 로 받는가
- [ ] `if cmd; then` 으로 **2와 1을 뭉개지** 않는가
- [ ] 파이프에 물릴 때 `PIPESTATUS` 를 보는가
- [ ] 도움말에 코드 의미를 적었는가
- [ ] 정기 잡에서는 2를 실패로 올리지 않고 알림만 보내는가

## 3. plan 단계 부작용 금지 목록

- [ ] 대상 파일 생성·삭제·절단 (`>` 리다이렉션 포함)
- [ ] `mktemp` · `mkdir -p` 로 만드는 작업 디렉터리
- [ ] 로그 파일 열기 (`exec 3> ...` 는 **여는 순간** 파일을 만든다)
- [ ] 락 파일·락 디렉터리 취득 (「잡을 수 있는가」는 검사만)
- [ ] 원격 상태 변경 (토큰 갱신·세션 생성·큐 소비)
- [ ] 캐시·인덱스 갱신 (다음 실행의 판단을 바꾸면 부작용이다)

★ **리다이렉션은 분기 밖에서 평가된다.** `f(){ ...; } > out` 은 dry 라도 `out` 을 자른다.
★ 래퍼에 `run cmd > state` 를 쓰면 안내 문구가 **상태 파일 안으로** 들어간다.

## 4. 검증 절차 — 3회 해시 + 부작용 0

```bash
snap(){ find "$1" -type f | LC_ALL=C sort | xargs -r sha256sum | sha256sum; }

before=$(snap target)
for i in 1 2 3; do ./tool.sh plan > "p.$i"; echo "run$i $(sha256sum < "p.$i")"; done
cmp -s p.1 p.2 && cmp -s p.2 p.3 && echo DETERMINISTIC || echo "★출력이 흔들린다"
after=$(snap target)
[ "$before" = "$after" ] && echo "NO SIDE EFFECT" || echo "★plan 이 상태를 바꿨다"
```

- [ ] 3회 해시가 같다
- [ ] before/after 스냅숏이 같다
- [ ] apply 후 다시 plan 하면 **빈 계획 + 종료 코드 0**
- [ ] 낡은 계획으로 apply 하면 **거부된다**

## 5. dry-run 이 거짓말하는 조건 — 하나라도 해당하면 도움말에 적는다

- [ ] 실행 분기 **안에만** 있는 검사 (락·용량·권한·헬스 체크)
- [ ] 앞 단계 산출물을 뒤 단계가 읽는 **연쇄 구조**
- [ ] 계획과 적용 사이에 **시간이 흐르는** 운영 (승인·배치)
- [ ] 원격 API 응답·서버 측 검증에 따라 분기
- [ ] 실행 사용자·보안 정책·마운트 옵션이 다른 환경
- [ ] **부분 실패 후 재개** (남은 계획은 다른 상태 위에서 돈다)
- [ ] 시각·난수·순회 순서가 결과에 섞임

## 6. 기존 도구를 쓸 때

- [ ] 확인과 실행의 명령줄이 `-n` 하나만 다른가
- [ ] dry-run 출력을 **파일로 저장**해 실행 결과와 대조했는가
- [ ] 디렉터리 한 줄을 파일 1개로 세지 않았는가 (한 줄이 수백 개일 수 있다)
- [ ] 문서의 **예외 절**을 읽었는가 (통계·진행률은 보장 대상이 아닌 경우가 있다)
- [ ] 원격이 끼면 권한·경로·타임스탬프 해석을 한 번 더 의심했는가

## 7. 도움말에 넣을 문구 템플릿

```
--dry-run   변경을 적용하지 않고 계획만 출력합니다.
            예측 대상 : <여기에 적는다>
            예측 불가 : <여기에 적는다>
            종료 코드 : 0=변경 없음 / 2=변경 있음 / 1=오류
            이 모드는 어떤 파일도 만들거나 지우지 않습니다.
```

★ 파괴적 명령을 시험할 때는 **반드시 새로 만든 빈 임시 디렉터리 안에서만** 돌리십시오.
