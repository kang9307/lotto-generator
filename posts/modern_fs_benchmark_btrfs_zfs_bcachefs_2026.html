1. 단일 장치 벤치마크의 한계와 modern-fs-benchmark의 문제의식

일반적으로 파일시스템의 입출력 성능을 측정할 때는 단일 저장 장치 위에서 순차 처리량을 측정하는 방식이 널리 쓰여 왔다.

원문은 전통적인 파일시스템 벤치마크가 기본 생성 옵션을 적용한 단일 장치 위에서 fio를 실행하는 방식으로 이루어진다고 적는다. 원문은 이러한 고전적 방식이 현대 파일시스템이 실제 프로덕션 환경에 배포되는 본래 목적을 전혀 설명하지 못한다고 지적한다. 원문은 Bartosz Fenski(fenio)의 modern-fs-benchmark 프로젝트가 btrfs, ZFS, bcachefs 같은 다중 장치 CoW(Copy-on-Write) 파일시스템의 핵심 메커니즘을 측정하기 위해 고안되었다고 적는다.

원문은 이 벤치마크 스위트가 단일 장치 기반의 전통적 벤치마크가 다루지 않는 영역을 포괄적으로 다룬다고 설명한다. 원문은 구체적인 측정 영역으로 「redundancy layouts, snapshot aging and scaling, transparent compression, encryption (native vs LUKS), reflinks, fsync tail latency, degraded operation and rebuild, corruption self-healing, and near-full/ENOSPC behavior」를 명시한다. 원문은 비교를 위한 고전적 계층 스택 기준점으로 md 또는 LVM 기반의 ext4와 XFS를 함께 배치한다고 밝힌다.

이 글의 해석으로는, 고정된 단일 장치 환경의 처리량 숫자 놀음에서 벗어나 스토리지 장애와 노화라는 실질적 운영 위기를 계측하려는 의도로 풀이된다. 원문은 파일시스템 평가의 본질이 단순히 누가 더 빠른지를 가리는 우승대(winner's podium) 경쟁이 아니라고 강조한다. 원문은 장기 스토리지 관점에서 진정으로 던져야 할 질문은 데이터의 무결성에 대해 어느 스택이 진실을 말해주는가(which stack tells you the truth about your data)라고 적는다. 이 글의 해석으로는, 벤치마크의 목표가 최고 속도 수치를 자랑하는 것이 아니라 손상과 성능 저하 조건에서 소프트웨어의 방어 메커니즘을 검증하는 데 맞춰져 있다.

  • 기존 단일 장치 벤치마크의 한계: 기본 mkfs 옵션과 단순 fio 순차 처리량만 측정하여 복수 장치 분산 환경을 반영하지 못함
  • modern-fs-benchmark의 핵심 검증 대상: 스냅샷 누적 노화, 손상 자가 치유, 투명 압축, fsync 테일 지연, ENOSPC 거동
  • 평가 관점의 전환: 가장 빠른 파일시스템을 선정하는 것이 아니라 데이터 무결성을 정확히 보장하는 스택을 규명함

2. 기본 매트릭스 26개 구성의 레이아웃 분류

일반적으로 단일 파일시스템이라도 블록 장치를 묶는 볼륨 관리자나 중복성 설정에 따라 입출력 경로가 크게 달라진다.

원문은 공식 워크플로(.github/workflows/bench.yml)에 정의된 기본 테스트 매트릭스가 총 26개의 스토리지 구성으로 이루어져 있다고 적는다. 원문은 테스트 대상 파일시스템군으로 ext4, XFS, btrfs, bcachefs, ZFS를 망라한다고 밝힌다. 원문은 가장 기초적인 단일 장치 구성부터 계층형 RAID, 네이티브 CoW RAID, 암호화 변형 및 특수 결합 스택까지 체계적으로 분류하여 배치한다.

원문은 단일 장치 btrfs의 경우 기본값인 메타데이터 DUP 생성을 피하고 다른 단일 장치 행과의 공정한 비교를 위해 -m single 옵션을 적용했다고 적는다. 원문은 암호화 변형 테스트에서 ZFS의 네이티브 데이터셋별 AES-256-GCM(mirror-enc)과 bcachefs의 전체 파일시스템 네이티브 ChaCha20/Poly1305(replicas2-enc)를 시험한다고 적는다. 원문은 btrfs의 경우 네이티브 암호화 옵션이 없어 장치마다 LUKS 계층을 개별 적용하는 raid1-luks 방식을 사용하며, ext4는 md RAID 위에 단일 LUKS 계층을 얹는 md-raid10-luks 방식을 쓴다고 적는다.

원문은 이중 패리티(dual-parity, RAID6급) 환경에서 ZFS raidz2, btrfs -d raid6 -m raid1c3, ext4 md raid6, 그리고 bcachefs --erasure_code --replicas=3 구성을 대조한다고 밝힌다. 원문은 btrfs의 경우 패리티 메타데이터의 쓰기 구멍(write hole) 위험을 피하기 위해 메타데이터에 raid1c3를 조합했다고 적는다. 원문은 bcachefs의 이레이저 코딩(EC)이 1.37 버전 이후 안정화되었으며 쓰기가 먼저 복제된 후 백그라운드에서 스트라이핑되는 구조 덕분에 쓰기 구멍이 없도록 설계되었다고 적는다.

원문은 XFS 시맨틱을 ZFS 스냅샷과 자가 치유, 압축 기능 위에 얹어 쓰는 실무 변칙 스택인 ZFS zvol 위의 XFS 구성을 테스트 매트릭스에 포함했다고 적는다. 원문은 LVM raid10 위에 dm-integrity를 결합하여 섹터별 체크섬 탐지 및 복구를 구현한 XFS 구성을 통해 고전 스택이 치르는 성능 대가를 측정한다고 적는다. 이 글의 해석으로는, 단순히 최신 파일시스템만을 고립시켜 시험하지 않고 현업에서 타협안으로 쓰이는 다양한 레이어 조합을 포함해 비교 타당성을 높였다고 판단된다.

원문은 ZFS의 경우 기본 레코드 크기인 128KB 스트라이프 미러 쌍과 8KB로 조정한 recordsize=8k 구성을 나란히 실행한다고 적는다. 원문은 이 비교가 ZFS의 소형 무작위 쓰기 비용 중 얼마만큼이 아키텍처 설계 자체의 한계이고 얼마만큼이 설정값의 차이인지를 증명하는 단일 변수 검증이라고 설명한다. 원문은 bcachefs의 경우 버전 6.17에서 리눅스 메인라인을 벗어난 이후 apt.bcachefs.org 저장소의 DKMS를 통해 빌드된 커널 모듈을 사용한다고 명시한다. 이 글의 해석으로는, 설정값 하나가 성능 형태를 바꾸는 현실을 매트릭스에 반영하여 단편적인 수치 왜곡을 방지하려 한 조치로 보인다.

  • 단일 장치 기준점 확보: CoW 기능 자체의 오버헤드를 분리하기 위해 ext4와 XFS 단일 장치 행을 배치
  • 다양한 암호화 메커니즘 비교: 파일시스템 네이티브 암호화와 블록 계층 LUKS 암호화 간의 성능 차이를 정량화
  • 고전 스택의 무결성 확장: LVM RAID에 dm-integrity를 추가하여 체크섬 제공 시 발생하는 페널티를 산출
  • 레코드 크기 단일 변수 통제: ZFS 128KB와 8KB 설정을 나란히 두어 매개변수 최적화 효과를 명시

3. 측정 항목과 손상 시험 판정 기준

일반적으로 파일시스템 벤치마크는 캐시가 채워진 상태의 단순 읽기와 쓰기 속도에 집중하는 경향이 있다.

원문은 modern-fs-benchmark가 단일 워크로드가 아니라 호스트 캘리브레이션부터 손상 복구까지 14개 이상의 세부 측정 단계를 단계별로 실행한다고 적는다. 원문은 trivial-op 지연 측정 단계에서 200ms마다 4KB 쓰기와 fsync를 실행하여 셸 히스토리 추가나 에디터 스왑 파일 갱신 같은 일상 작업의 지연을 계측한다고 적는다. 원문은 소스트리 연산 단계에서 2만 개의 소형 파일 트리를 생성하고 콜드 cp -r 및 rm -rf를 수행하여 리눅스 커널 트리 복사 시나리오를 시뮬레이션한다고 적는다.

원문은 대형 디렉터리 확장성 단계에서 단일 디렉터리에 10만 개의 빈 파일을 생성하고 콜드 및 웜 상태에서 stat을 수행한 뒤 삭제하는 과정을 거친다고 적는다. 원문은 스냅샷 노화(snapshot aging) 단계에서 스냅샷이 누적됨에 따라 발생하는 무작위 덮어쓰기 대역폭 저하를 추적하며 기술적으로 허용되는 경우 최대 100개의 스냅샷을 생성한다고 적는다. 원문은 ZFS의 경우 128KB 기본 레코드 크기 환경에서 스냅샷마다 전체 파일에 준하는 공간이 고정되는 특성으로 인해 10개로 제한하고, 구형 LVM 스냅샷은 증폭 문제로 8개로 제한하며 이는 편의를 위한 타협이 아니라 기술적 발견이라고 적는다.

원문은 디스크가 가득 차는 near-full 및 ENOSPC 단계에서 가용 용량 95%와 99% 근방의 쓰기 처리량을 계측하고 하드 ENOSPC에 도달했을 때 파일 삭제가 가능한지를 검증한다고 적는다. 이와 관련하여 디스크 블록 할당과 아이노드 고갈 시 나타나는 시스템 거동의 차이는 디스크는 안 찼는데 No space left on device - inode와 열린 파일에서 다룬 바와 같이 파일시스템별로 상이한 양상을 보인다. 원문은 btrfs의 경우 소형 가상 디스크 환경에서 용량 지표가 목표치에 도달하기 전에 1GB 데이터 청크 할당 벽에 먼저 부딪히는 현상이 발생한다고 지적한다.

원문은 손상 시험(corruption + scrub) 단계에서 파일시스템 몰래 단일 장치에 2GB 범위의 원시 데이터를 덮어쓴 뒤 스크럽을 수행한다고 적는다. 원문은 스크럽 수행 후 추적 대상 테스트 파일의 해시를 비교하여 세 가지 명확한 판정 기준을 내린다고 적는다. 원문은 스크럽 후 추적 대상 테스트 파일을 정상적으로 읽었고 MD5 해시가 일치하면 SURVIVED로 판정한다고 적는다. 원문은 파일 내용이 손상되었거나 읽기 자체가 실패하면 FAIL로 판정한다고 적는다. 원문은 체크섬 기능이 없는 스택에서 읽기 밸런싱 등에 의해 해시가 우연히 일치한 상태를 UNPROVEN으로 분류한다고 적는다.

원문은 전통적인 md 또는 LVM RAID 스택이 디스크 분실은 방어하지만 디스크 펌웨어나 컨트롤러 장애로 인한 무음 손상(silent data corruption)에는 애플리케이션에 오류 없이 손상된 데이터를 그대로 반환했다고 지적한다. 이 글의 해석으로는, 조용히 망가진 데이터가 백업 저장소로 전파되는 치명적 재해를 방지하기 위해 손상 자가 치유 판정을 핵심 지표로 격상시킨 것으로 풀이된다. 무음 데이터 오염이 백업 세트로 누적될 때 발생하는 복구 실패 메커니즘은 백업은 단순 복사가 아니다 - 보존 주기와 무결성 검증에서 짚은 데이터 무결성 원칙과 직결된다.

4. GitHub Actions 공유 VM 환경과 신뢰도 원칙

일반적으로 클라우드 기반 CI 환경은 여러 테넌트가 동일한 물리 호스트의 자원을 공유하는 구조를 가진다.

원문은 modern-fs-benchmark의 실행 환경이 GitHub Actions의 공유 가상 머신(VM)이며 모든 가상 장치가 단일 가상 디스크 위에 생성된 루프 파일로 존재한다고 적는다. 원문은 이러한 환경적 제약으로 인해 「all 'devices' live on one virtual disk」이며 「absolute MiB/s is meaningless」, 즉 절대적인 처리량 수치 자체는 무의미하다고 명시한다.

원문은 이 스위트가 절대 처리량을 겨루는 것이 아니라 서로 다른 구성 간의 비율과 그래프의 형태(shapes and ratios)를 관찰하도록 설계되었다고 적는다. 원문은 동일한 가상 머신 작업 안에서 이루어지는 상대적 비율 비교는 동일 디스크 환경이므로 직접적인 의미를 갖는다고 적는다. 원문은 서로 다른 파일시스템 간의 비교에 대해 수십 퍼센트 수준의 작은 차이는 노이즈로 간주하고 2배 이상의 큰 격차만을 실질적인 차이로 해석하는 신뢰도 원칙을 제시한다.

이 글의 해석으로는, 클라우드 가상화의 한계를 숨기지 않고 공개적으로 인정함으로써 측정치의 신뢰 구간을 명확히 한 접근법이다. 원문은 단일 실행의 우연성을 배제하고 반복 실행을 통해 축적된 시계열 추세를 바탕으로 결론을 보강한다고 설명한다.

  • 공유 VM의 구조적 제약: 단일 가상 디스크 기반 루프 장치를 사용하여 절대 처리량은 분석 가치가 없음
  • 형태와 비율 중심 관찰: 동일 작업 내의 상대적 성능 곡선과 구성 간 비율을 핵심 결과물로 채택
  • 노이즈 판정 기준 수립: 수십 퍼센트의 작은 차이는 노이즈로 보고 2배 이상의 격차만 유의미한 차이로 인정
  • 반복 실행 기반 추세 보강: 수백 회 누적 실행의 추세선을 대조하여 일시적인 간섭을 걸러냄

5. 버전 기록 장치와 결과 대시보드

일반적으로 아웃오브트리(out-of-tree) 모듈은 실행 중인 리눅스 배포판의 커널 버전 표기만으로 내부 코드를 특정하기 어렵다.

원문은 ZFS와 bcachefs처럼 메인라인 외부에 존재하는 모듈의 경우 커널 버전만으로는 실제 실행된 코드를 식별할 수 없다고 설명한다. 원문은 「Every result records the exact tools and kernel-module versions tested — essential for ZFS and bcachefs, which are out-of-tree, where the kernel version alone doesn't identify what actually ran」이라고 명시한다. 원문은 모든 벤치마크 결과가 테스트 당시의 정확한 사용자 도구 버전과 커널 모듈 버전을 누락 없이 기록한다고 적는다.

원문은 누적된 결과가 공식 대시보드(https://bartosz.fenski.pl/modern-fs-benchmark/)를 통해 일반에 공개된다고 밝힌다. 원문은 대시보드가 지표별 최상위 정렬 차트, 스냅샷 노화 곡선, 실행 회차별 추세선을 제공하며 파일시스템군과 레이아웃별 필터링을 지원한다고 설명한다. 원문은 데이터 분석을 위해 선형 및 로그 스케일 전환 기능과 정렬 가능한 테이블을 제공하며 전체 실행 이력은 results-data 브랜치에 보존된다고 적는다. 이 글의 해석으로는, 외부 기여자가 독립적으로 결과를 검증할 수 있도록 메타데이터의 완전성을 담보하는 재현성 장치다.

  • 아웃오브트리 모듈 버전 추적: 커널 버전 외에 ZFS 및 bcachefs의 실제 빌드 버전을 JSON에 독립 보존
  • 시각화 필터링 기능: 파일시스템군 및 다중 장치 여부에 따라 차트와 표를 동적으로 필터링
  • 원시 데이터 브랜치 격리: 대시보드 화면뿐만 아니라 results-data 브랜치에 원시 실행 기록을 축적

6. 로컬 환경 재현과 실행 절차

일반적으로 오픈소스 벤치마크 도구는 의존성 패키지 설치와 스크립트 실행 명령을 간결하게 제공한다.

원문은 프로젝트 소스코드가 Apache License 2.0으로 공개되어 있으며 데이터셋은 CC-BY 4.0 라이선스를 따른다고 적는다. 원문은 로컬 환경에서 벤치마크를 재현하기 위한 실행 절차로 의존성 설치 스크립트와 실행 스크립트를 안내한다. 원문이 안내하는 명령은 다음과 같다.

sudo scripts/install-deps.sh <fs>
sudo scripts/run-bench.sh <fs> <layout>

원문은 로컬 시스템에서 테스트할 때 별도의 물리 장치 없이도 루프(loop) 장치를 기반으로 환경이 구성된다고 적는다. 원문은 실물 하드웨어 지원의 경우 별도로 배선 가능한 전용 블록 장치가 요구된다고 설명한다. 이 글의 해석으로는, 복잡한 파티셔닝 절차 없이 단일 명령으로 레이아웃 매트릭스를 검증할 수 있도록 CLI 인터페이스가 추상화되어 있다.

  • 공개 라이선스 채택: 도구 소스코드는 Apache 2.0, 누적 벤치마크 데이터셋은 CC-BY 4.0 적용
  • 2단계 실행 구조: 의존성 설치 스크립트와 벤치마크 실행 스크립트로 CLI 명령을 최소화
  • 가상 블록 장치 활용: 물리 디스크 없이도 루프백 파일을 통해 로컬 환경에서 26개 구성을 재현

7. 저자의 방법론 옹호와 커뮤니티의 비판

일반적으로 벤치마크 방법론이 공개 커뮤니티에 공유되면 테스트 환경의 유효성을 둘러싼 열띤 기술적 토론이 발생한다.

원문은 Hacker News 스레드(item?id=49768833)에서 방법론의 정밀성을 둘러싼 커뮤니티 토론이 벌어졌음을 보여준다. 이용자 Farmadupe는 베어메탈 하드웨어를 사용하지 않는다면 결과를 서로 비교하는 것 자체가 불가능한 것이 아니냐며 다른 테넌트가 동일 디스크를 사용 중일 가능성을 지적했다. Farmadupe는 「if you're not using baremetal for such tests, it's likely that the results are simply not comparable at all? What if another tenant is also using the disk?」라는 의문을 제기했다.

이에 대해 저자인 Bartosz Fenski(fenio)는 가상 머신 환경에서 이웃 테넌트의 간섭이 존재했음을 솔직하게 인정했다. fenio는 「Obviously they could and probably were noisy neighbours」라고 답변하며 공유 디스크의 노이즈 영향을 인정했다. 동시에 저자는 다수의 반복 실행을 통해 통계적 신뢰성을 확보하고 있다는 점을 강조했다.

fenio는 댓글을 통해 「there are 593 runs recorded so average should still be quite meaningful」이라며 누적 실행 횟수가 평균값의 유의미성을 뒷받침한다고 주장했다. 또한 저자는 Hetzner 머신과 SAS HDD를 투입하여 실 하드웨어 테스트를 병행하고 있다고 밝혔다. fenio는 「one run on REAL hardware takes much more time than on GH runner so it's slow」라고 언급하며 실 하드웨어 테스트가 가상 머신에 비해 훨씬 많은 시간이 소요된다고 설명했다.

이 글의 해석으로는, 완벽한 하드웨어 자원이 갖춰지기를 기다려 프로젝트를 미루는 대신 가상 환경의 한계를 인정하고 통계적 모수를 늘려 점진적으로 보완해 나가는 실용적 엔지니어링 태도를 취한 것으로 평가된다.

  • 커뮤니티의 근본적 문제 제기: 가상 머신 디스크의 이웃 테넌트 간섭으로 인한 결과 왜곡 가능성 비판
  • 저자의 솔직한 한계 시인: 공유 디스크에 노이즈가 실제로 존재했을 가능성을 투명하게 인정
  • 대규모 반복을 통한 통계 보정: 593회 이상의 누적 실행 데이터로 평균값의 신뢰성을 확보함
  • 실 하드웨어 테스트 확장: Hetzner 서버 및 SAS HDD 환경에서 장시간 소요되는 물리 검증을 병행 중

8. 확인하지 못한 것

본 글을 작성하며 1차 출처 문서와 공개된 기술 자료를 대조하는 과정에서 다음 사항들은 명확한 수치나 추가 근거를 확인하지 못하여 단정적으로 서술하지 않고 본 절에 남긴다.

  • 실시간으로 갱신되는 대시보드(bartosz.fenski.pl/modern-fs-benchmark/)의 특성상 본 분석 시점 이후 추가로 누적된 최신 총 실행 횟수와 시점별 세부 수치 변동값은 고정된 단일 수치로 확인하지 못했다.
  • 저자가 Hetzner 머신과 SAS HDD 환경에서 진행 중이라고 밝힌 실 하드웨어 테스트의 전체 항목별 벤치마크 결과 및 최종 통계는 원문 저장소와 댓글에 구체적 수치로 완결되어 있지 않아 확인하지 못했다.
  • GitHub Actions 가상 머신 인스턴스에서 벤치마크가 수행될 당시 동일 물리 호스트에서 경합한 이웃 테넌트의 실제 I/O 점유율 및 정량적 간섭 편차는 플랫폼 내부 지표로서 외부에 공개되지 않아 확인하지 못했다.
