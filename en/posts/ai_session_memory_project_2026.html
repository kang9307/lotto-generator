Turning AI Coding Sessions' Ephemeral Context Into Project Memory

Lessons from rhwp - what to keep, where to write it, and how far to automate it

Jul 23, 2026 Dev & Infra

Introduction: An AI That Has to Be Re-Briefed Every Single Time

Anyone who uses AI coding tools daily knows the scene by heart. Every new session means re-explaining the project's structure, re-justifying why a particular approach was chosen, and sometimes standing by while the model retries something that already failed last week. The models themselves keep getting better, yet felt productivity increasingly hinges not on model quality but on how much this specific project is remembered.

That feeling is not an illusion. Coding agents like Claude Code, Gemini CLI, and OpenAI Codex are isolated by session design. When a session ends, every judgment, rationale, and thread of context discussed inside it vanishes, and the next session starts from an empty context window. For a short personal project, this reset barely registers. But for a project that runs for months or years, with people and AI sessions rotating in and out, that volatility compounds into real, cumulative loss.

A recent case from the rhwp project, surfaced on GeekNews, tackles this problem head-on in practice. This piece uses that case as a starting point to work through, from a practitioner's angle, what it actually means to turn a project's context into memory - what to keep, what to throw away, and where it makes sense to write it down.

1. What rhwp Showed - "Why Doesn't This Work Here?"

rhwp is an open-source HWP (Korean word processor format) viewer and editor built in Rust and WASM. A post from one of its contributors on GitHub Discussions caught attention on GeekNews. The core observation: an AI that performs well in vibe coding - quick prompts, quick results - starts stumbling noticeably once it's dropped into a codebase that has months of accumulated history. The author argues the gap isn't model capability at all; it's whether that project's context has been preserved anywhere the AI can reach.

To address this, the original author describes applying a method called Hyper-Waterfall to rhwp for three months. The name sounds grand, but the structure is plain. A mydocs/ folder sits inside the repository, holding manual (long-lived knowledge), tech (technical documentation), orders (task assignments), plans (execution and implementation plans with archives), and a trail of step-by-step completion reports and final reports. A task director assigns work, the agent drafts an execution plan for approval, implements it while leaving step reports along the way, and closes with a final report. All of these documents get committed to the same repository as the code.

The example the author gives is memorable: a design document completed in February resurfaced during an entirely new task in July, and thanks to that document, both a new contributor and the AI could see exactly what the maintainer at the time had been wrestling with and why the design went the direction it did. That is precisely what "project memory" does. People change, AI sessions change, but the reasoning behind a decision stays inside the repository.

2. What Project Memory Actually Means - Transcript vs. Decision Record

"Keeping project memory" easily conjures an image of saving the entire session conversation as a log. But that's a transcript, not memory. A transcript mixes trial and error, tangential questions, and repeated phrasing together, so that anyone (or any AI) reading it later has to scan the whole thing just to find the one decision that actually matters. That's not compression - it's adding another burden on top.

In my view, real project memory is built from decisions, not conversation. What was decided, why that approach was chosen, which alternatives were considered and rejected, and under what conditions the decision might later be revisited. If just these four things are captured accurately, the next session can reach the same conclusion far faster even if the entire conversation is gone. Conversely, keeping the whole conversation without explicitly pulling out the decisions just means the next session - human or AI - has to re-mine those decisions from a long block of text all over again.

This is where a long-standing software engineering concept, the Architecture Decision Record (ADR), gets reused almost unchanged. ADRs were originally built for human developers: each architectural decision gets a short document capturing context, the alternatives considered, the final choice, and the trade-offs. The reason this practice is getting fresh attention in AI coding sessions is simple - an AI agent, just like a human new hire, will repeat the same debate or retry an already-discarded alternative if it doesn't know why a decision was made. An AI whose sessions evaporate is arguably the reader who needs ADR-style documents the most.

3. What to Keep and What to Discard

Keeping everything is functionally the same as keeping nothing. The value of memory comes from selection. Here is how I'd draw the line.

What to keep

  • Decisions - what was done, and why
  • Constraints - rules that must hold, and performance, security, or compatibility conditions
  • Failed attempts - what was tried and didn't work, and why. This matters especially: without a record of failure, the next session walks the same dead end again
  • Open questions - unresolved items that need revisiting later

What to discard

  • Small talk and pleasantries - natural in a session, but useless information for the next one
  • Process logs - "opened this file," "ran this test." If the result and reasoning survive, the process is reproducible anyway
  • Transient state - the current branch name, a one-off debug print, anything that's already meaningless by the next session

The real barrier to adopting this practice is that a human has to make this judgment call every time a session ends. Which is exactly why how much of this judgment can be automated is the next question worth examining.

4. Where to Write It Down - Matching the Store to the Job

Once "keep memory" is settled, the next question is "where." I see four broad candidates, and they are complements, not substitutes.

4.1 CLAUDE.md / AGENTS.md - the always-on summary at session start

A file an agent reads automatically at the start of every session. It should hold only what stays true across the whole project: stack, conventions, build and deploy rules, and warnings about recurring pitfalls. CLAUDE.md is Claude Code-specific while AGENTS.md is emerging as a tool-neutral, public convention, and more projects now run both side by side with distinct roles. If this file bloats, it only inflates the loading cost of every single session, so it should hold strictly what's needed at all times.

4.2 docs / ADR - an archive of individual decisions

The place for each architectural decision to get its own short document. If CLAUDE.md is "the summary you need right now," an ADR is "the archive of why it turned out this way." Its purpose is to be looked up when needed, not read automatically every session.

4.3 Commit messages - binding code and decision together

The only place that physically fuses a code change and its rationale into one unit. Code changes, but commit history stays, so "why is this line the way it is" can still be traced months later with git blame. That said, a commit message is scoped to a single change and isn't suited to holding the project's full picture.

4.4 A dedicated memory file - the middle ground

A MEMORY.md-style dedicated file sits between the other three. It accumulates short summaries per project or issue at the end of each session - less formal than an ADR, more flexible than reading the whole of CLAUDE.md every time. The catch is that it tends to grow indefinitely over time, requiring its own periodic summarizing and archiving of old entries.

I don't think any single one of these four is sufficient on its own. rhwp's mydocs/ structure itself combines manual (close to CLAUDE.md's always-on knowledge) with plans and reports (somewhere between an ADR and a session summary). In practice, picking as many of these four as the project's scale actually warrants is the realistic path.

5. The Automation Spectrum - From Manual Curation to Auto-Summarization

Keeping memory sits on a spectrum. One end is fully manual, the other is fully automatic.

5.1 Manual curation

rhwp's approach sits close to this end. A task director personally reviews and approves plans, and reads and confirms completion reports. Quality is highest here, but it costs human time every single round.

5.2 End-of-session hooks

A method that forces a fixed-format summary at the moment a session ends. For instance, a hook requiring "today's three decisions, the alternatives discarded, and what to check next" be filled in before the session closes guarantees a minimum structure without requiring a human to write it from scratch every time. Using Claude Code's hooks mechanism for exactly this purpose is a growing pattern.

5.3 Automatic summarization

The AI itself reads the session log and generates and stores a summary. Memory-layer tools like Cognee, Mem0, Zep, and Letta are productizing this end of the spectrum. The upside is near-zero human involvement; the downside is that handing the summarization quality and selection criteria to the AI risks blurring the judgment of what actually deserves to be kept. A summarizer that separates decisions from small talk as well as a human still isn't common.

In my judgment, there's no reason to commit to either extreme of this spectrum. A layered approach makes practical sense: big decisions (architecture, a stack swap) get written by a human as an ADR, routine session summaries get their format forced by a hook, and searching through bulk logs gets handed to automated summarization tools.

6. Connecting to Existing Threads - The Bigger Picture of Agent Documentation

This practice isn't an isolated idea - it's one branch of a much larger movement toward "documentation for agents" that has emerged simultaneously across the last half year. Tools like OpenWiki for "agent-facing documentation" started from the premise that documents meant for humans and documents meant for AI need different structures. Compiling CLAUDE.md rules directly into hooks was an attempt to turn rules from prompt text into executable, enforceable logic, cutting off drift at the source. The spec-driven development trend of committing Korean-language specs instead of code moved the question of "what counts as the source" from code to spec - which, at its root, is the same attempt to preserve "why this was built this way" in a form that outlives the code itself. And persistent-memory tools like CTX that bridge memory across Claude Code sessions can be read as a productized instance of the automatic-summarization end of the spectrum.

In other words, rhwp's mydocs/ approach (manual, structured documents), compiling CLAUDE.md into hooks (enforcing rules), committing Korean-language specs (redefining the source itself), and CTX-style persistent memory (automatic summarization) are all variations attacking the same problem - the volatility of AI coding - from different angles. None of them is the single right answer; combining a few of them to fit a project's character is the realistic path.

7. The Traps - When Memory Becomes a Burden

The practice of keeping memory has its own pitfalls. First, memory bloat. If something gets written down after every session, documentation volume grows faster than the code itself. Once reading through all that documentation in the next session takes longer than simply being re-briefed from scratch, the whole point is defeated. Without a regular cycle of summarizing, merging, and retiring old records, this trap is hard to avoid.

Second, drift. The decisions recorded in documents and the actual code diverge over time. If a "why we did it this way" record still describes code that has since been refactored away, that record stops guiding and starts misleading. Updating code and documentation in the same commit, and explicitly marking old ADRs as "superseded," both reduce this problem.

Third, noise. Recording decisions and small talk indiscriminately buries the decisions that actually matter under a pile of chatter. This is simply a failure of the "what to keep, what to discard" discipline discussed earlier, and the risk is especially acute with automatic summarization tools - if a summarizer can't tell decisions from small talk, the volume of records grows while their usefulness actually drops.

All three traps share one prescription: memory should be curated, not merely accumulated. What determines whether this practice is sustainable isn't the act of writing things down, but the criteria for filtering what gets kept and a regular cycle for cleaning up what's old.

8. A Team Perspective and a Practical Playbook

In a personal project, project memory is a nice-to-have convenience. In a team project, it's a different story. From an onboarding angle, the time it takes a newly joined person - or a newly assigned AI agent - to figure out "why was this built this way" is literally the onboarding cost. If, as in the rhwp case, a design document from five months ago can be handed straight to a new contributor, that onboarding cost compresses down to the time it takes to read one document. Without it, the moment the one person who held that knowledge steps away, the knowledge itself disappears. The same logic applies to audits. When you later have to answer "why is this code written this way" - a security audit, an incident post-mortem, a regulatory response - a decision record gives you the answer on the spot. Without one, you have to reverse-engineer intent from the code itself.

Adopting this in practice doesn't need to be elaborate. My recommended starting point is three steps. First, put a CLAUDE.md or AGENTS.md at the project root and keep it short, holding only what needs to be known at all times. Second, write a single-page document under docs/adr/ only when an architecture-level decision is made - not every time, only for decisions that would be genuinely expensive to reverse. Third, at the end of a session, leave just three lines somewhere: what was decided today, which alternatives were discarded, and what to check next. Once these three habits stick, layering on hooks or tools for automation later is never too late.

Conclusion: The Difference a Habit of Remembering Makes

AI model performance keeps improving, but what actually lets that performance land on top of a project's context is how well that project remembers itself. What the rhwp case demonstrates isn't a special tool - it's an attitude: knowing the session will vanish, and choosing to leave the decisions and their reasons inside the repository anyway. As this piece has laid out, memory should be a decision record, not a transcript; discarding matters as much as keeping; the storage location should be a combination of CLAUDE.md, ADRs, commits, and memory files rather than any single one; and automation should be approached as layers, not an all-or-nothing choice. As of July 2026, the structural fact that AI coding agents are isolated by session isn't going away anytime soon. Given that, the habit of deciding for yourself what to leave behind on top of that structure is likely to become the real difference between teams that get more out of AI and teams that don't.
