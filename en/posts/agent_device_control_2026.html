Handing a Real Phone to an Agent - Where Device Automation Works and Where It Must Stop

Exploration goes to the agent, repetition goes to the script

Introduction: the last square was always human work

The agent read the issue, changed the code and finished the build. And then a human picked up the phone to see whether it actually looks like that. Open the app, swipe through three screens, tap the button, notice the text is clipped, go back. Automation always stopped one square short, right here.

A tool that claims that square has arrived. agent-device, released by callstack, is a CLI that lets a coding agent open a running app, read its structure, tap, type and leave the result behind as evidence. It covers iOS and Android, and also tvOS, Android TV, macOS, Linux and the web behind one interface.

Here is the judgment up front. Look-and-tap control is already useful for verification and still premature for execution. What separates the two is not how clever the model is. It is whether a mistake can be undone. Misreading a screenshot and tapping the wrong tab costs you a back gesture. The same mistake landing on a payment confirmation button has nowhere to go back to.

This article draws that line. How the loop actually turns, where it breaks, what must be removed from the tool surface rather than merely discouraged, and what a heavily verified app market adds on top. The mirror image of this topic, writing code on the phone rather than driving it, was covered separately in Building and Shipping an App on Mobile with Codex.

1. The five steps of a device control loop

Every agent that drives a device turns the same wheel. Names differ per tool, but there are five steps.

  1. Acquire state. What is on the screen right now, as a screenshot or a structural dump
  2. Pick a target. Which of those elements to act on
  3. Send the action. Tap, type, scroll or gesture, delivered to the device
  4. Wait to settle. Hold until the screen stops moving
  5. Verify the result. Did the intended change actually happen

The commands in agent-device map onto these steps directly. open AppName --platform ios starts a session, snapshot dumps the accessibility tree, press @ref taps an element, fill @ref enters text, screenshot ./path.png captures evidence, and close ends the session. The option worth staring at is --settle. The fact that waiting for the UI to come to rest is surfaced as an explicit flag tells you that skipping it breaks things often enough to deserve its own name.

1.1 Each platform has its own channel

Tools like this do not invent a new channel. They ride the doors each operating system already left open.

  • iOS and tvOS — XCTest, sitting on top of Apple's UI testing stack
  • Android and Android TV — ADB, the developer channel used as is
  • Linux desktop — AT-SPI, the accessibility service interface
  • Web — browser automation running inside the same session

There is one thing to read out of that list. Every entry is a developer or accessibility channel. None of them is a route for arbitrarily driving a phone in ordinary user state. They are doors a developer opened toward their own device and their own app, and that is exactly the scope of this article.

1.2 Why a CLI

There are several ways to hand capability to an agent. You can attach an MCP server or define function-calling tools. agent-device puts a CLI at the center and ships MCP tools and a typed Node client alongside it.

The advantage of a CLI is blunt. Coding agents already use a shell. Instead of laying twenty tool definitions into the context you teach one command, and subcommands get pulled in with --help when needed. The way selection accuracy wobbles as you attach more tools was covered in How Many Tools Can an Agent Handle; wrapping a capability behind a single CLI is a way of sidestepping that problem on both the token and the selection axis.

2. Coordinates or the tree

This is the axis that splits device control agents in half. Do you see the screen as a picture or as a structure?

The coordinate approach screenshots the display, shows it to the model, and takes back an answer of the form tap this pixel. The tree approach reads the accessibility structure the operating system already builds, the one described in Android's accessibility service documentation. Each node carries text and labels, whether it is checkable, whether it is clickable, and actions such as ACTION_CLICK, ACTION_SET_TEXT and ACTION_SCROLL_FORWARD can be invoked on the node itself. No coordinate arithmetic required.

AxisCoordinate (screenshot) basedAccessibility tree based
Unit of referencePixel coordinateNode reference
Resolution or font size changeDriftsUnaffected
Layout rearrangementEverything breaksSurvives if labels hold
Unlabeled iconsCan be guessed from shapeInvisible in the tree
Canvas, games, custom renderingThe only optionTree is empty
Token costExpensive, it is an imageCheap, it is text
Tracing a failureHard, you cannot tell what was misreadEasy, the chosen node is on record
Side effectNoneAccessibility quality audit falls out for free

The table nearly answers itself. Put the tree first and keep coordinates as a fallback. A coordinate-only setup demos beautifully and has to be rewritten the moment the app ships an update. If it is not your own app, there is no way to carry that maintenance cost.

The tree has its own trap, though. Tree quality is decided by the app. If the developer never attached labels, the nodes exist without names. Icon-only toolbars, image buttons and custom drawing areas are where this bites hardest. Which makes the cheapest way to raise automation success rate, somewhat ironically, filling in accessibility labels. You do it for automation and screen reader users get a better experience out of the same work. Incentives rarely line up this neatly.

3. Six places the loop breaks

You cannot fix "it fails sometimes." Failures come in kinds, and each kind has its own remedy. Six show up regularly.

Break pointVisible symptomCommon misdiagnosisActual remedy
Capturing mid-animationReads a transition frame and picks the wrong elementThe model cannot read screensForce a settle wait after every action
Loading latencyConcludes an empty list means no resultsServer errorDeclare skeletons and spinners not done
A/B tests and feature flagsSame build, different screen than yesterdayNondeterministic bugPin flags for the test account
Layout changesEvery scenario fails after a releaseThe tool brokeTrack coordinate-dependent steps as a list
State carryoverFirst run passes, later runs failIt is flakyReset start state every run
System popups intrudingPermission, update or notification covers the appApp bugMake popup handling a standing part of the loop

3.1 Judge success by the screen and you get fooled with it

The most expensive of the six lands in the last step: verifying the result from the screen alone. A "sent" banner does not mean it was sent, and a screen that has not changed yet does not mean it failed.

AndroidWorld, Google Research's evaluation environment for mobile agents, tackles this head on. It holds 116 programmatic tasks across 20 real Android apps and derives reward signals from system state rather than from the display. That is why task phrasing can be varied endlessly without the verdict wobbling. The same principle applies to automation inside a company. Judge success outside the screen wherever you can. A database row, a file on disk, an API response, a line in the log. Keep the screen as evidence and let state decide.

3.2 The absolute level of this field

In that same work, the paper's baseline agent M3A completes 30.6 percent of AndroidWorld's tasks. How you read the number matters. Several later approaches report substantially higher success rates, so do not mistake 30.6 percent for the current state of the art. But the fact that the baseline started here tells you how easily this problem slips.

Translated into practice: a scenario that passed once proves nothing. Run the same scenario twenty times and count the passes. Automation that clears nineteen and automation that clears fourteen are entirely different objects, and the second one is not automation at all because a human has to re-check every result anyway.

4. Where to cut off irreversible actions

This is the center of the article. Device control has a wider blast radius than browser automation or file manipulation, because a logged-in real account, a registered payment method, contacts, photos and messages are all one screen away.

TierOperationsDefaultSafeguard
ReadSnapshots, screenshots, log and network captureAuto-allowMask sensitive screens
Reversible writeScroll, tap, form entry, navigationAuto-allowRecord every action
Irreversible writePayment confirmation, transfers, sending messages, posting reviews, deleting dataBlockedRemove from tool surface
Credentials and verificationLogin, identity checks, biometrics, payment PINNot an automation targetHuman performs it
Device settingsAdding or removing accounts, factory reset, permission changesBlockedIsolate on a dedicated device

4.1 A confirm dialog is not a safeguard

The most common design is "ask a human before anything dangerous," and it fails almost every time. The reason sits in people, not technology. After approving nineteen of twenty prompts, the hand moves before the eye on the twentieth. Approval fatigue is not an exception, it is the steady state.

So the order inverts.

  1. Make it physically impossible. An account with no payment method, an environment with no balance, data separated from production. Build the state where a mistake causes nothing before anything else
  2. Remove it from the tool surface. If the command list visible to the model has no path there, the action does not happen even when judgment wobbles
  3. Only then ask a human about what remains. If the prompt appears two or three times a day, people actually read it. At twenty times a day they do not

The general theory of how to slice permissions and what to leave blocked by default was covered in What Should an AI Agent Be Allowed to Do. One thing changes for device control. APIs usually have an undo path; a UI action on a physical device does not. A pressed button has been pressed.

4.2 Why capturing evidence is a feature, not a convenience

agent-device collecting screenshots, video, logs, traces, network data, performance samples and crash details is not a nicety. If no record survives of what the agent saw and what it pressed, after-the-fact verification is impossible. The first thing that disappears when human work is handed over is anyone's memory of what the screen looked like at the time, and without it a failure can be neither reproduced nor fixed.

The minimum record set — snapshot immediately before the action, the reference and label of the chosen node, the action sent, the settle duration, the snapshot immediately after, and the system state used for the verdict. With those six, most failures reproduce.

5. How this differs from Appium and XCUITest

"We already have Appium, so why" is a fair question. The answer is that the two do different jobs.

Appium is a UI automation framework aiming to cover many platforms and many languages, built as four separable pieces: core, drivers, clients and plugins. That modularity came from judging a single monolith covering every platform to be a daunting if not impossible task. XCUITest driver handles iOS, UiAutomator2 handles Android.

AxisClassic test automation (Appium, XCUITest)Agent device control
Who decides the next actionA script a human wrote firstThe model, on the spot
When the screen differsIt stopsIt routes around
How to read that traitA virtue in regression testingFatal in regression testing
SelectorsHuman-specified and maintainedRediscovered every run
Run costLow, no inferenceHigh, inference per step
ReproducibilityDeterministicCan differ run to run
Good atConfirming the known is unchangedSweeping the unknown and drafting
Bad atExploring new screens, discovering scenariosUnattended overnight regression runs

The second row is the crux. A regression test that routes around a change is not a test. Stopping and reporting when a button moved is the entire reason regression tests exist, and the agent cheerfully finds the new location, taps it, and returns a pass. The suite is neutralized by being clever.

So the combination that holds is agent for exploration, script for repetition. The agent sweeps the screens and drafts scenarios, a human confirms them, and confirmed ones get demoted to deterministic scripts. agent-device recording runs as replayable scripts and exporting to Maestro YAML is that structure written into the design. Use the agent as a test author, not a test runner — that is the most realistic use at this moment.

6. What works today and what does not

Compressed into one rule: if undoing a mistake costs more than doing the task by hand, it is not ready.

6.1 Safe to hand over now

  • Eyeballing the screen you just changed — swiping three screens while leaving screenshots as evidence. The part humans hate most, and there is nothing to undo
  • Walking through a bug report — following the reported sequence while collecting logs, network traces and crash details
  • Auditing missing accessibility labels — a tool that reads the tree exposes unlabeled elements as a byproduct, no separate audit tool needed
  • Sweeping resolutions and locales — hunting combinations where text clips or buttons overlap. Too many combinations for a human
  • Drafting test scenarios — drafting, not running. A human reviews and confirms
  • Checking the onboarding flow — from a fresh install to the first screen, counting where it stalls

6.2 Not yet

  • Whole unattended overnight regression suites — for the reason above, the test routes around itself
  • A real-account payment flow to the end — up to just before confirmation. A human presses confirm
  • Anything touching production data — deleting, sending, publishing
  • Passing authentication or identity verification — covered separately below
  • Running on your primary personal device — messages, photos and contacts enter the blast radius
  • Someone else's device or account — out of scope. Your own device, your own account, your own app is the premise

7. Constraints in tightly regulated app markets

This is where local conditions diverge. In markets like Korea, where financial and identity verification is layered into ordinary consumer apps, the workable window is after verification finishes and before payment is confirmed. Both ends close not for lack of tooling but because they were designed to.

7.1 Secure screens close the agent's eyes

Android has a flag that marks a window as a secure surface. A window carrying WindowManager.LayoutParams.FLAG_SECURE cannot be screenshotted and is not shown on non-secure displays such as casting, a TV or a projector. Android's own documentation names banking apps and password managers as the canonical use, screens handling logins and purchases. The same page attaches a caveat worth knowing: on Android 11 (API 30) and lower the flag holds reliably on roughly 70 percent of devices, because on some devices keyboard taps can still be recorded.

Banking, payment and verification apps use it routinely. An agent whose eyes are screenshots looks at that screen and sees one black rectangle, then stops. That is not a bug; it is the app doing exactly what it intended, and it is a line to stop at rather than something to get past. What automation design should do here is not route around it but hand the segment to a human and re-attach from the following screen.

7.2 Identity verification is not an automation target

Identity checks, biometrics and payment PINs exist to prove that a specific person is present at that moment. Make them pass automatically and they stop meaning anything. Before asking whether it is technically feasible, it contradicts the purpose.

Practical design starts by accepting that. Write scenarios that begin from an already-verified state, and hand off to a human when the session expires. For a test environment, keeping a staging account that does not require verification is far cleaner.

7.3 The plan to ship an internal accessibility service

"Could we just build an accessibility service app and push it internally" comes up constantly. There are two walls.

  • The user must turn it on. Accessibility services cannot auto-activate, the user must enable them explicitly in settings, and only the system may bind to them
  • Policy restricts the purpose. Android documentation frames an accessibility service as a specialized tool for building general-purpose assistive software and states it is not the standard way to make your own app accessible. The official guidance is to use standard accessibility APIs for your own app instead

So the realistic path for internal automation is the ADB and XCTest channels on development devices, not a shipped app. Gathering devices into a lab and running only there collides least with both policy and security.

7.4 Managed corporate devices

Work phones frequently have developer options and debugging channels locked by management policy. Automation devices should be booked as separate assets outside the managed fleet, which means separating them by purpose at registration time. Putting them in a different bucket from the start is always cheaper than negotiating an exception later.

8. The order to adopt it in

Change the order and you pay for it. Plenty of teams skip step 3 and start at step 5.

  1. Scope it to your own app. Do not start a setup that targets somebody else's app
  2. Separate the device. No primary personal phone. No payment method registered, test accounts only, data separated from production
  3. Open reads first. Snapshots, screenshots and log collection only. Run there for at least two weeks
  4. Fill in accessibility labels. This is where success rate moves most, and real accessibility improves as a side effect
  5. Open reversible writes. Scroll, tap, form entry. Record every action
  6. Move the verdict off the screen. Confirm success from system state and keep the screen purely as evidence
  7. Demote settled scenarios to scripts. Leaving repeated runs to the agent piles up cost and variance together
  8. Never open irreversible actions. If you think you must, that is not an automation request, it is a separate design problem

Keep measurement simple. Twenty runs of the same scenario, passes, mean duration, and number of human interventions. Plot those four weekly and within three weeks it is obvious whether adoption is working.

The most common failure pattern — building the flashy demo scenario first (login all the way through payment), watching it succeed one time in five, concluding it is premature, and shelving the whole thing. The place to start is the opposite end: read-only work where failure causes nothing.

9. What could not be confirmed

The following were not used as figures or assertions in the body because no primary source could be pinned down.

  • The current best score on AndroidWorld. The 30.6 percent in the body is the paper's baseline agent. Later work reports considerably higher success rates, but the conditions could not be compared against the paper bodies, so those numbers were left out
  • agent-device success rate on real devices versus simulators. No published comparison exists
  • The scope of restrictions on physical iOS devices. How far the XCTest path matches simulator behavior was not established
  • Which screens in which apps use the secure flag. It varies per app and no public list exists. This is something to check against the actual target app
  • Cost. How tokens for reading and judging one screen scale with scenario length varies too widely across setups to generalize

Conclusion: hand over the reversible work first

Agents that drive devices get introduced as an assistant that uses your phone for you, but that is not where the value sits right now. It sits in verification labor. Does the fix actually look like that, does the reported bug really reproduce in that order, is there a combination where the text clips. The work humans find most tedious and skip most often, and also the work where a mistake costs nothing.

At the other end sit payment confirmation, sending and deletion. What is needed there is not a better model but a narrower tool surface. Make it impossible and wobbling judgment causes no accident. The confirm dialog comes after that, and a prohibition written in prose comes after the dialog.

Two things worth trying today. One is dumping the accessibility tree of your own app once. How many unnamed nodes come back tells you almost exactly how automatable that app is. The other is listing the verification work people are currently doing by hand. The entries with nothing to undo are what you can hand over today, and there are usually more of them than expected.
