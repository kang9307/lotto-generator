爬虫的账单由谁来付 - 内核 git 托管实测出来的成本 2026

为了 2% 的正常请求而让 90 核中的 14 核长期空转的结构，以及防御依次失效的顺序

2026年9月1日 开发/基础设施

运维过公开 git 仓库网页浏览器的人，都认得这种形状的曲线。从某一天起 CPU 使用率再也降不到底，日志里的来源 IP 每次都不一样，被请求的提交哈希也不是人会关心的某个具体改动，而就是全部。2026 年 8 月 29 日，负责 Linux 内核项目 git 托管的运维者把这个情形整理成数字公开了出来。

这里值得读的不是爬虫很讨厌这个结论，那个大家早就知道。值得读的是成本究竟压在了哪一层，以及已经架好的防御是按什么顺序失效的。这两点同样适用于规模小得多的服务，只是数字变小，结构一样。

本文的数值取自某一处托管的实测与维基媒体基金会的公开报告。比例会随服务结构大幅变化，因此不能挪用为自己站点的数值。这不是对任何特定企业或服务的评价，文中列出的每种防御手段都有代价，照搬打开之前请先算清楚会失去什么。

起因 - 把一天的量数成数字之后

git.kernel.org 每天收到约 600 万次请求。它们要的是随机的提交页面，性质和一个人追查某个缺陷时打开一条提交完全不同，是一种没有顺序也没有目的、把地址空间整个刮一遍的形态。

这些请求在进入后端之前先要过一道关卡：对每个连接抛一道小的计算题，只有把答案带回来的请求才放行。在这道关卡上，66% 被当场弹回。剩下的 33% 是真的把题算出来进来的。而按运维者的估计，全部流量里正常请求只占约 2%。

把这三个数字并排放，就会得出一个不太舒服的结论：挡掉了 66%，可通过的那 33% 里绝大多数仍然是机器人。这道防御只减少了数量，没有改变性质。这正是本文抓住的地方。爬虫应对里真正难的不是把第一道防御立起来，而是防御的寿命很短这个事实。

正常请求 2%，账单却是 100%

把数字换算成硬件就是这样：这套服务跑在分布于 5 个地区的90 个核心上，其中14 到 16 个核心常年只做一件事，把提交渲染成 HTML，而产物是给爬虫的。占全部容量的 20%。

看比例时最好先确认分母。这里的 20% 不是机器人在服务器总负载中的份额，而是相对于已配置核心数、被爬虫渲染长期占住的核心比例。若按负载算，短时间冲得更高的区间当然也有。用核心来数的好处在别处：这是一个可以直接换算成金额的数字。核心是签了合同买下来的，那 14 个核心等于买下来租给了爬虫。

这个结构在公共基础设施上格外疼，是有原因的。商业服务里流量增长多少还有通向营收的路径，开源托管没有这条路径。成本按 100% 入账，收益按零入账。与此同时，真正把这些数据拿去训练的一方，从来看不到这张账单。

  • 90 核中的 14 到 16 核被持续占用。这不是瞬时峰值，而是一直保持这个状态
  • 同样这些核心如果用来服务人，那 2% 的正常请求本可以处理得宽裕得多
  • 靠扩容应对的话，扩出来的容量大部分又流向爬虫，因为比例并不会变
  • 所以这不是容量问题。要么改变请求的性质，要么把请求本身减下来

为什么偏偏是 git 浏览器 - 组合爆炸的位置

普通博客即便被完整抓走，总量也有尽头。三千篇文章就是三千个页面，拿完就结束了。git 网页浏览器没有这个性质，它的地址是按乘法增长的。

linux.git 大约有148 万个提交，同一个托管上还有它约922 个 fork。fork 共享原仓库的历史，所以同一条提交可以在 922 个仓库路径下分别请求。按原文的说法，可抓取的有效 URL 达到数十亿量级，而全部抓完拿到手的是同一份内容最多 922 份重复。

这里别误读机器人的行为。它并不是明知重复还硬要抓。爬虫大多按看见链接就跟进这样简单的规则运行，在这条规则眼里，这片 URL 空间就是一堆看不到头的新鲜页面。而在服务器这边，它意味着把同一条提交重画九百多次。

同样的陷阱在小规模服务上也很常见：把筛选组合写进 URL 的商品列表、用查询参数接收日期区间的日历、把排序选项挂在地址上的论坛，都属于同一类。页面数量有限，地址数量却不是有限的。

  • 148 万提交 × 922 个 fork，等于一片实际上没有尽头的地址空间。存储容量没变，暴涨的只有渲染请求
  • 排序、筛选、页码进入查询串之后，同样的爆炸会以小规模重现
  • 日历与归档页面很容易造出一直延伸到未来日期的无穷多个有效地址，是很老的经典陷阱
  • 第一步不是封禁，而是减少指向同一份内容的地址数量，规范网址与链接梳理都在这一格
  • 不过这只对守规矩的爬虫有效，对不守的那一边还需要另一层

工作量证明起过作用，然后被攻破

工作量证明关卡的想法很简单：在拿到页面之前，先让浏览器解一道规定的计算。一个人看几页时这点开销可以忽略，而对一天要刮几百万页的一方，它会被乘起来变得可观。目的是制造不对称。这一类里最有名的实现 Anubis，自己的说明是，通过一道或多道挑战来称量连接的分量，以保护上游资源不被抓取机器人拖垮。

一开始确实有效。然后时间一长，机器人开始解出难度 4。于是把难度提到 5。没过多久，机器人连难度 5 也解出来了。这个进程不是运气问题而是经济问题：收集训练数据的一方，恰恰就是早已囤好大量算力的那一方。要求计算的防御，对算力便宜的对手最无力。

这里有一点最好说清楚。66% 被弹回并不意味着这道防御没有意义，那 66% 确实是服务器不必渲染的。问题在于剩下的 33% 按绝对量已经很大，而当你想靠继续提高难度把它压下去时，成本会落到不该落的一边。

防御手段一开始有效的原因失效的方式
基于 User-Agent 的拦截机器人自己报了名开始伪装成普通浏览器字符串
robots.txt只需面对守规矩的一方时够用没有强制力，不守也不会怎样
IP 与网段封禁流量集中在少数来源住宅代理的一个 IP 用 4 到 5 次就消失
速率限制单一来源猛打时抓得很准一旦分散，每个来源的速率都在正常区间内
工作量证明 难度 4乘在机器人身上的算力成本很大机器人开始把它解出来
工作量证明 难度 5把成本又抬高一级机器人再次解出，而访客的设备先受罪

计算成本也会从访客口袋里出

工作量证明防御真正的局限不是会被攻破，而是代价压在两边。难度 5 在手机上要算好几秒，而手机在这几秒里会热得让人不舒服。这不是修辞，是电量与发热这种物理成本。

更要紧的是这份成本分布并不均匀。用最新高端机型的访客根本不会察觉关卡存在，用老旧低价机型的访客每页都要等好几秒。所谓提高防御等级的决定，实际上是在选择让哪一类访客更难用这个站点。

不执行 JavaScript 的客户端也会卡在这里：命令行工具、脚本、无障碍辅助技术，还有归档抓取器。做防御工具的人自己也没有把它说成温和措施。Anubis 的文档直白地写着，这种方式带有核武器式回应的性质，除了小型抓取器，也可能把互联网档案馆那样的善意机器人一并挡在外面。意思是，要打开就先弄清楚再打开。

  • 关卡难度是用同一个旋钮同时抬高机器人成本和访客成本，无法分开调节，这是结构性弱点
  • 对机器人运营者来说算力便宜，对访客来说电量昂贵。这个不对称对防守方不利
  • 没有 JavaScript 的正常客户端会被一起切掉，这常常是内部脚本或监控突然失败的原因
  • 搜索索引与归档抓取可能一起断。对公开文档站点来说，这份损失有时大于挡住机器人的收益
  • 所以关卡应该当作最后手段而非默认值，先把前面能减的减掉

IP 封禁失效的那个点

封禁的基本形态是锁定来源再把它挡住。这个前提要成立，来源就得在同一个位置停留得足够久。眼下这种采集正面打碎了这个前提。

内核那边的记录说得很准：这样的 IP 发 4 到 5 次请求，然后就再也没出现在日志里。等你判断出某个地址是机器人时，对方已经办完事了。把它加进封禁名单，挡的是一个不会再来的地址。

这里形成的状态让观测格外困难：总量在失控，可每一个来源都很安静。每 IP 请求数、每秒请求数、每会话页面数，怎么看都出不来离群值。因为规则是按来源写的，而压力并不按来源组织。

地址从哪儿来，也让问题变大。原文写到，只要应用制作方还在找赚钱的路子，就会继续把家用设备变成攻击通道。请求要是真从家庭线路出来，按网段封就会把正常用户一起切掉。不是封禁规则的精度下降了，而是用来做精细判断的材料本身没有了。

  • 每个地址 4 到 5 次请求。阈值压得再低，先被绊住的是正常访客
  • 总量与按来源的指标对不上时，就把指标按路径而不是按来源重写。哪些 URL 模式被调用了多少次，要有用得多
  • 按网段封可能切断家庭线路。公开服务上这种副作用不容易看见，反而更危险
  • 地域封禁也因为同样的理由很钝，代理出口哪里都能架

从主动报名的机器人到伪装的机器人

早期这个问题要简单得多。按原文的说法，机器人很热心地通过 User-Agent 告诉你它是谁，看字符串处理就行。后来机器人反应过来了，开始装成普普通通的浏览器。

这次转变毁掉的不只是一件趁手工具，信号的性质变了。当年主动报名的 User-Agent 是协作的产物，今天的 User-Agent 是规避的产物。按协作前提写出来的规则，没法用来对付规避。robots.txt 现在的处境正是如此。这套约定为什么始终没能超出承诺，在 robots.txt 拦不住 AI 爬虫 里另行谈过，本文不再深入。

不过 User-Agent 也不必完全丢掉。这个信号作为封禁依据很弱，作为分类依据仍然可用。空的或格式不对的字符串能说明什么、不能说明什么，整理在 空的 User-Agent 就是机器人吗 里。

这个案例里还有一点值得点出来。内核那边的文章写到，现在用的 cgit 是按互联网还属于人类和遵守 robots.txt 的爬虫的那个年代设计的。不是工具变坏了，而是前提消失了。相当多的老网页软件都处在同样的状态。

同样的账单也送到别的公共基础设施

如果这只是内核托管一家的特殊处境，故事到这里就结束了。别处的证据说明并非如此。维基媒体基金会在 2025 年 4 月发布的报告就是其中之一。

按那份报告，自 2024 年 1 月以来，用于下载多媒体内容的带宽增长了 50%。而站点上消耗资源较大的流量中，至少 65% 来自机器人，可机器人在全部页面浏览量中只占约 35%。把这两个数字并排放，正是这份报告的核心：机器人会挑贵的请求去发。

原因看缓存结构就明白。人的阅读集中在热门条目，而这些条目早就在前端缓存里；机器人的阅读则与热门程度无关地摊得很开。于是它会不断请求缓存里没有的条目，这些请求一路抵达后端源站。同样是一次页面浏览，成本要高出好几倍。

那份报告里的一句话，也正好是本文的概括：内容是免费的，基础设施不是。

指标git.kernel.org（2026-08）维基媒体（2025-04 报告）
机器人所占比重正常请求估计约 2%全部页面浏览量中机器人约 35%
在昂贵资源上的比重90 核中 14 到 16 核用于给爬虫渲染资源消耗大的流量中至少 65%

共同点两边都是免费公开数据的一方承担全部成本

为什么缓存解决不了

一提这件事，第一个反应通常是加缓存不就好了。对了一半。缓存在同一样东西被反复请求时效果最大，而麻烦在于，现在进来的请求性质恰好相反。

刮随机提交的请求，按定义每次都是不同的地址。以无序方式走遍 148 万条提交，缓存命中率会一直保持在低位。要是说把缓存无限做大，那么存储成本和更新成本就会顶上来。何况把乘上 922 个 fork 的地址空间整个塞进缓存，本来就不成立。

这里需要做个区分：爬虫造成的成本不是一种。层不同，性质不同，管用的对策也不同。

成本所在层爬虫引发的东西为什么常见对策效果有限
网络带宽大文件与图片被反复传输前端缓存是按热门资源优化的，机器人刮的是冷门资源
应用 CPU页面每次都要重新渲染地址每次都不同，命中率提不上去
存储与数据库随机访问带来的磁盘寻道访问模式没有局部性，读缓存填不起来
防御层本身关卡校验与日志记录同样消耗资源拦截这个动作本身不免费。防御做大，防御成本也跟着大
运维人力规则调整与误判处理需要持续投入就算自动化，判断还是留给人。这项成本最容易被低估

那么，成本由谁承担

把结构压成一句话：免费公开数据的一方，连数据被拿走的成本也一起付。既然公开了，被拿走本身不奇怪。奇怪的是，拿走的方式无论烧掉对方多少资源，都不会在自己的损益表上留下一行。

所以把它当礼貌问题处理是解不开的。能靠礼貌解决的一方，早就在遵守 robots.txt 了。眼下制造负载的一方没有任何减少负载的动机。正如原文所指出的，只要每天都有想要训练数据的新公司冒出来，这股压力就不会减弱。

从运维者的角度，这个认识在实务上很重要，因为它意味着这是要用设计而不是谈判来处理的问题。既然没法让对方守规矩，就只能把服务重新搭成即使对方不守规矩也不产生成本的样子。这个结论并不讨喜，但它是实际剩下的选项。

  • 公开数据的成本结构本来是按人数设计的，自动采集在这个假设之外
  • 靠捐赠与资助运转的基础设施上，这份超支会直接从本职事业的预算里扣
  • 私营服务还能用套餐或访问密钥把成本转回去，公共基础设施没有这个装置
  • 于是只剩两个旋钮：降低昂贵请求的单价，或者把昂贵请求从匿名访问里移出去。

开着门守住的折中

内核那边实际选的就是这个方向。不是全面封禁，而是减少可抓取的 URL 数量、给执行成本大的动作加上门。代价也一并讲明了：以匿名方式访问时会失去一部分功能。同时他们写到，数据本身仍会提供给任何提出要求的人下载，只是要多绕几道手续。

这个折中之所以重要，与其说在结果，不如说在他们决定守住什么。守住的是对数据的访问，让出的是网页界面的便利。反过来定也是可以的：把一切挪到登录之后，爬虫肯定会减少，但公开仓库这个性质本身也变了。

把选项列出来，就更容易决定自己的服务该站在哪一格。关键在于没有哪一格是免费的。

选择对爬虫的效果正当用户失去的东西
什么都不做没有响应时间与容量，最后所有人一起变慢
清理重复地址、梳理链接只对守规矩的一方有效几乎没有，这也是它排第一的原因
把昂贵页面移出匿名访问中到大一部分原本可以用链接分享的页面，回退很容易
工作量证明关卡中，且随时间衰减低配设备、不带 JavaScript 的客户端、归档站
整体挪到登录之后大匿名浏览本身，公开服务的性质会改变

小站点可以按这个顺序做

90 核的故事没法原样搬到个人博客上，但诊断顺序可以照用。先看看自己的站点上是否正在发生分散式采集。从访问日志里取出每个 IP 的请求数分布，立刻就能分辨。

# 统计每个 IP 的请求数并存成文件
awk '{print $1}' access.log | sort | uniq -c | sort -rn > /tmp/ip_counts

# 来一两次就消失的 IP 有多少个（分散式采集的信号）
awk '$1 <= 5' /tmp/ip_counts | wc -l

# 成批过来的 IP 有多少个（传统封禁还管用的那一侧）
awk '$1 >  5' /tmp/ip_counts | wc -l

前一个数字压倒性地大，就说明封 IP 不是答案。这时要看的不是来源而是路径：把指标挪到统计哪些 URL 模式被调用了多少次、其中哪些在服务器上是昂贵页面。关于在日志里看什么、据此判断什么的更长整理，在 与抓取器搏斗的一年 里。

  • 先从地址空间减起。确认排序、筛选、会话值是否进了 URL，把同一份内容变成了多个地址
  • 把昂贵页面列成清单。响应时间靠前的路径多半就是，爬虫恰好照着这份清单打
  • 找出无穷地址生成器。日历、无限翻页、任意日期区间查询是典型
  • 能静态化的先静态化。渲染成本趋近于零之后，被刮也不疼，这是最可靠的对策
  • 封禁放最后。前面四项做完仍然不够时再加。顺序反过来，时间会全花在处理误判上
  • 要开关卡，先确认什么会被一起切掉。搜索索引、归档站、RSS 阅读器、内部脚本都是候选
  • 做成可开可关的。难以回退的防御，一旦误伤，损失要大得多

小结

记住三个数字，这件事的形状就出来了：每天 600 万次随机提交请求，其中正常的约 2%，而 90 核里有 14 到 16 核为剩下的那部分长期运转。这不是流量变大了的故事，而是多出了一个支出科目的故事。

防御这一侧要学的不是哪种手段好，而是每种手段都有寿命。User-Agent 在机器人开始伪装时到头，IP 在用 4 到 5 次就丢的代理面前到头，工作量证明在难度 4 与 5 相继被解开之后变薄。把下一种手段也看成会画出同一条曲线，会更稳妥。

所以剩下的实务姿态只有一个：不要把不让它来当目标，而把来了也不疼当目标。减少地址空间，把昂贵页面移出匿名访问，能静态化的静态化。内核那边写下数据会继续开着，也是同一种判断——不是放弃公开，而是把公开的单价降下来。

未能确认的部分

  • 原文没有逐项列出究竟关掉了哪些 cgit 功能或路径。能确认的只是方向，即减少可抓取的 URL 并给昂贵动作加门，以及匿名访问会失去一部分功能这个表述
  • 仓库 clone 是否对匿名一直开放，按那个说法本身没能确认。原文里有的是会继续把数据提供给任何提出要求的人下载这句话，以及手续可能变多的附注，具体的访问方式没有写
  • 正常请求约 2% 是运维者的估计值，文中没有说明以什么标准区分正常与非正常
  • 14 到 16 核这个值是哪一段时间的平均没有交代，瞬时峰值可能更高
  • 数十亿量级的 URL 空间可以理解为提交数乘以 fork 数，但确切的算式并未出现在原文里
  • 这些爬虫属于哪家公司或服务无从确认。伪装的 User-Agent 加上住宅代理让来源无法锁定，本文也不做锁定
  • 维基媒体报告的数值是 2025 年 4 月的时点，之后的变化未反映在内
