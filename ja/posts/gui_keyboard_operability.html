マウス前提で作られた画面が取りこぼすもの - キーボードだけで操作できるGUI

到達と脱出という二つの基本要件、フォーカスが消える地点、そして自動チェックが判定できないもの

2026年8月30日 開発・インフラ

序論: マウスが使えなくなる日は思ったより頻繁に来る

手首が痛くて数日マウスを使えなくなったとしましょう。ふだんの業務画面を開いてタブキーだけで最後まで行ってみると、たいてい半分あたりで止まります。あるボタンにはフォーカスが届かず、ある領域に入ると出る道がなく、フォーカスがいまどこにあるのか画面のどこにも表示されません。その画面はよく作られていてレビューも通っています。ただしマウスがあるという前提の上でだけそうなのです。

この話題が最近また開発者のあいだで回りました。ある開発者が、GUI はキーボードだけでも完全に操作できるべきだと主張し、ターミナル UI がキーボード操作に本質的に向いているという通念に反論しました。GUI にできないのではなく作る側が優先順位から外しただけだという論旨で、根拠として GNOME のインターフェース指針が「すべての動作はキーボードでも可能であるべき」と述べている点と、自分が作ったアプリにショートカットを揃えて入れた経験を挙げています。マウスのほうが向いている作業があることは、その記事も認めています。

この記事が扱うのはその次です。マウス前提で作られた画面は具体的に何を取りこぼすのか。抜ける場所はほぼ決まっていて、その大半は機能ではなく状態の管理から生まれます。ターミナル側の事情は性質の異なる問題なのでここでは扱いません。テキストの格子にはそもそも構造を収める場所がないという話はターミナル UI に構造がないという意味で別に整理しました。この記事は反対側、構造を収める場所がすでにあるのにキーボードで使えなくなる理由です。

1. キーボードだけで使う人は誰か

範囲を先に広げておかないと、この話題はすぐに狭くなります。キーボードだけで操作することになる条件は四つあり、恒久的なものはそのうちのひとつです。

  • 恒久的な条件 — 手の震えや可動域の制限で小さな標的を正確に狙いにくい場合、画面を見ずに音で操作する場合。スクリーンリーダー自体がキーボードの上で動くため、キーボード操作が崩れるとその経路も一緒に崩れます。
  • 一時的な条件 — 手首や腕の怪我、ギプス、手術後の回復期間。数日から数週間だけですが、その間はまったく同じ条件です。
  • 状況的な条件 — 片腕で子どもを抱えている状態、マウスを置く場所がない移動中、画面を共有しながら話す発表中、カーソルが追いつかないリモートデスクトップ、電池の切れた無線マウス。
  • 習熟による条件 — 同じ画面を一日に数百回通る人。フォームを繰り返し埋める業務、一覧と詳細を行き来する管理画面、開発ツール。手がキーボードを離れて戻る往復そのものが費用です。

この四つを一行にまとめるとこうなります。キーボード操作は利用者の属性ではなく、その瞬間の条件から生まれる。だから「うちの利用者にそういう方はほとんどいない」という統計は答えになりません。統計が数えるのは恒久的な条件だけで、残りの三つは標本にすでに混ざっていながら調査には現れません。

習熟による条件は残りの三つと利害がぴったり一致します。速く使いたい人と、マウスを使えない人が同じものを必要とするという意味で、アクセシビリティの予算が付かない組織でも生産性という名前でなら同じ作業が通ります。

2. 基本要件は二つ - 到達と脱出

華やかなショートカットを載せる前に確認することは二つだけです。行けるか、そして出られるか。

前者が到達です。画面上で何かをする地点すべてにフォーカスが届かなければなりません。ここで最も漏れるのは、ボタンに見えてボタンではないものです。

<div class="btn" onclick="save()">保存</div>      <!-- タブでは到達しない -->
<button type="button" onclick="save()">保存</button>  <!-- 到達・活性化・役割が付いてくる -->

二つは画面上でまったく同じに見え、マウスでは同じように動きます。違いはキーボードでだけ現れます。この欠陥が静かな理由はそこにあります。作る人もレビューする人もマウスを使うので、画面をどれだけ長く見つめても見えません。

後者が脱出で、こちらのほうがはるかに致命的です。ある領域にフォーカスが入ったのに抜け出すキーがない状態をフォーカストラップと呼びます。到達に失敗すれば機能ひとつが使えないだけですが、脱出に失敗するとその地点以降の画面全体が使えなくなります。タブを押しても同じ場所を回り、シフトとタブでも戻れないなら残る選択肢はウィンドウを閉じることだけで、そうすると書きかけの内容も一緒に消えます。

点検の順序は脱出が先です。到達できないボタンは後から直せばよく、その間に利用者は別の経路を探します。しかし一度閉じ込められた利用者は、たいてい戻ってきません。

トラップが生まれる場所もおおむね決まっています。

  • 外部から埋め込んだウィジェットや挿入フレーム
  • 自前で実装したオーバーレイやドロップダウン
  • フォーカスが外れると強制的に戻すコード
  • スクロールを自前で処理するためにキーイベントをまるごと飲み込む領域。機能のために伝播を止めたことが、結果としてフォーカスの出口をふさぎます

3. フォーカスが見えなければ無いのと同じ

マウスには画面を横切るカーソルがあります。キーボードにはありません。その役目を代わりに担うのがフォーカス表示で、だからフォーカス表示は飾りではなくカーソルそのものです。表示が消えると利用者はエンターを押すときに何が押されるのか分からない状態になり、削除や決済のボタンの近くでは手が止まります。

フォーカス表示を消す慣行はかなり定着していて、理由も分かります。ブラウザ既定の輪郭線がデザインから浮き、マウスでクリックしたあとも表示が残って雑に見えるという指摘がレビューで出ます。問題は、そのとき出た解法が表示をまるごと無くす方向だったことです。

/* マウスのクリックには表示を残さず、キーボード移動には残す */
:focus-visible { outline: 3px solid #1a73e8; outline-offset: 2px; }

表示そのものを無くす以外にも、結果が同じになる経路が二つあり、実務ではこちらのほうがよく出ます。

  • 対比の低い表示 — 輪郭線の色が背景と近いとコードにはあって目にはありません。カードの内と外で背景が変わる画面なら、ひとつの色ではどちらかが必ず埋もれます。
  • 隠れた表示 — 固定された見出し、下部の同意バー、横から滑り込む引き出し。フォーカスはその後ろへ行ったのに目には何も起きず、タブを数回押すと突然現れます。その間に何を通り過ぎたかは分かりません。
  • 画面外へ出た表示 — 横にスクロールする一覧やタブ列で、フォーカスが見えない領域へ移るのにスクロールが追いつかない場合です。

三つとも利用者が受け取る結果は最初のものと同じです。そして三つともコードには表示が存在するため、静的なチェックには引っかかりにくいのです。

4. 順序が画面の配置とずれるとき

キーボードの移動には順序があります。その順序を決めるのは文書に要素が置かれた並びで、画面に見える位置を決めるのはスタイルです。二つは別のものであり、だからずれます。ずれると利用者は画面を見ながら次にどこへ行くかを予測できなくなります。マウスにはこの問題がまったくありません。順序ではなく座標を使うからです。

配置を変えるスタイルが生む問題

項目の表示順を変える属性、格子の上にマスを直接指定する配置、方向を反転させる設定は、いずれも視覚順序だけを変えます。移動順序はそのままです。レスポンシブではさらにこじれます。文書はひとつなのに広い画面と狭い画面の視覚順序が異なるなら、少なくとも一方は必ずずれます。

ここにタブ順序を正の数で指定する習慣が重なると悪化します。0 より大きい値を与えると、その要素が文書全体の自然な順序より前へ引き出されます。ひとつの部品を直すために入れた数字ひとつが、ページ全体の移動順序を定義し直すことになります。

繰り返し区間とスキップ

順序の問題のもうひとつの顔が繰り返しです。見出しにメニューが三十個あればキーボード利用者は本文に届く前に三十回通り、ページを移るたびに再び通ります。マウス利用者はこの費用を一度も払わないので、作る側が実感しにくいのです。

  • スキップリンク — 文書の先頭に置いて本文へ直接送るリンクです。ふだんは隠しておきフォーカスを受けたときだけ現れるように作りますが、現れるスタイルが抜けているとフォーカスは行ったのに画面には何もなく、あってもなくても同じになります。
  • 領域の目印 — ヘッダー・本文・サイドバー・フッターを文書構造で区別しておけば支援技術の利用者は領域単位で飛べます。すべて一般的なコンテナにするとその手段が消えます。
  • 見出しの階層 — 見出しが順に並んでいればそれ自体が目次であり移動手段です。大きさを揃えるために階層を混ぜると一緒に壊れます。
  • 折りたたまれた領域 — 折りたたまれて見えない部分がタブ順序に残っていると、利用者は見えない場所を延々と通ります。

5. 自作のウィジェットが危うい理由

標準の要素は挙動をただで与えてくれます。ボタン要素ひとつにはタブ順序への組み込み、エンターとスペースによる活性化、フォーカス表示、無効状態の処理、支援技術に伝わる役割がすでに入っています。誰も実装していないのに、ただそこにあります。

同じ見た目を一般的なコンテナで作り直すとそのすべてが消え、キーの挙動を最初から実装し直さなければなりません。実務で起きることはたいていこうです。クリック処理を付け、役割の属性を付け、タブ順序に入れる属性まで付けます。ここまでならチェックツールは通るのに、エンターの処理がありません。フォーカスは行き表示も出るのに押せません。

複数の部品が組み合わさったウィジェットは要求がさらに大きくなります。以下は W3C の ARIA デザインパターン文書が求めるキーの挙動をまとめたものです。

ウィジェット標準の要素で得られるもの自作するとき実装が要るキーの挙動
ボタンタブ到達・エンター/スペース活性・無効処理エンターとスペースの両方。スペースはページのスクロールも抑える必要がある
チェックボックス・ラジオ選択状態の伝達・グループ内の矢印移動スペースで切り替え。グループ内では矢印キーで移動し、ひとつだけをタブ順序に残す
タブリストなし（対応する標準要素がない）左右の矢印キーで前後へ移動し、端から先頭へ循環。縦配置なら上下の矢印キー。ホームとエンドで最初と最後へ
スライダー矢印キーで一段・ホーム/エンド・値の伝達矢印キーで一段ずつ、ホームは範囲の最初の値、エンドは最後の値。ページアップとダウンは大きく移動
メニューボタンなしエンターとスペースで開き最初の項目にフォーカス。下矢印で開くと最初の項目、上矢印で開くと最後の項目

表を見れば判断の基準がおのずと出ます。標準の要素でできることは作り直さないことです。見た目が気に入らないなら、要素を変えるのではなくスタイルを変えるほうがほぼつねに安く済みます。

6. モーダルとポップアップ - 行き、戻り、その間に漏れない

重なって現れる画面は、キーボード操作で最もよく壊れる部分です。要求は三つあるのに、たいていひとつしか守られません。

  • 開くときフォーカスが中に入らなければならない。開くだけでフォーカスを移さないと、利用者は新しく現れたものに気づかないまま後ろをタブで通り続けます。ARIA デザインパターンはダイアログが開くとフォーカスがその中の要素へ移ると述べ、どの要素かは内容に応じて決めつつ破壊的な操作は避けるよう案内しています。
  • 閉じるとき元の場所へ戻らなければならない。フォーカスをそのままにして閉じるとフォーカスは文書の最上部へ落ち、次のタブが画面の一番上から始まって、利用者はいた位置をまるごと失います。同じ文書は、閉じるときおおむねダイアログを開いた要素へフォーカスが戻ると述べています。
  • 開いているあいだ後ろへ漏れてはならない。タブが最後の項目から最初の項目へ循環しないと、フォーカスは後ろの画面へ移ります。よくある誤りは後ろを支援技術から隠す属性だけを掛けてタブ順序の整理を抜かすことで、そうすると音では消えフォーカスでは残ります。

付け加えると、フォーカスが当たっただけで画面が変わってはいけません。矢印キーで一覧をたどっている最中に項目ごとにページが移ったりフォームが送信されたりすると、キーボード利用者は選ぶ行為そのものが不可能になります。

7. ショートカットを足すとき生じる衝突

キーボード操作に手を付け始めると、次の段階としてショートカットを載せたくなります。ここで別の種類の問題が生じます。キーは有限で、すでに持ち主がいます。

  • ブラウザが使うキー — タブ移動、アドレスバー、検索、再読み込み、拡大と縮小。ここにアプリの機能を重ねると利用者はどちらかを失います。
  • OS が使うキー — ウィンドウ切り替え、画面ロック、キャプチャ。片方のプラットフォームで空いているからといって、もう片方でも空いているとは限りません。
  • 支援技術が使うキー — 最も忘れられがちな側です。スクリーンリーダーは読み上げモードで一文字のキーを自前の命令として使います。見出しへ移動、表へ移動といったものです。アプリが同じ文字を横取りすると、その利用者は探索手段を失います。
  • 入力中の利用者 — 一文字のショートカットはテキスト欄に文字を書いている最中にも発動します。名前を入力していて保存が実行される、という具合です。

標準はここに具体的な答えを定めています。WCAG 2.2 の達成基準 2.1.4 Character Key Shortcuts（等級 A）は、文字・句読点・数字・記号だけで構成されたショートカットに対してオフにする、割り当てを変える、フォーカスがあるときだけ動作するのうち少なくともひとつを求めます。三つとも「無くせ」ではなく「利用者が制御できるようにせよ」という形です。

8. 自動チェックが捉えられないもの、そして人がやること

この記事の核心はここです。キーボード操作の問題は自動チェックに最もかかりにくい種類です。

W3C WAI の評価ツール選定の案内はこの点を直接述べています。ツールがすべてのアクセシビリティの側面を自動で検査することはできず人の判断が必要であり、評価ツールはアクセシビリティを判定するのではなく判定を助けるものだと明記しています。誤ったり誤解を招いたりする結果が出ることがあるという警告も添えられています。

ツールが得意なことは明確です。コントラスト比の計算、代替テキストの欠落、ラベルと入力の関連付け、識別子の重複のように規則で真偽を決められるものです。反対にキーボード操作の核心はおおむね判定できません。

  • フォーカスが実際に見えるか — 輪郭線の属性が存在することまでは見えます。ところが前に挙げた三つの経路、すなわち対比の低い表示、隠れた表示、画面外へ出た表示は、いずれも属性が存在する状態です。描画後の重なりと実際の対比は静的な規則の範囲を超えます。
  • 順序が筋の通ったものか — 移動順序を列挙することはできますが、その順序が意味を保っているかは判定の対象ではありません。達成基準そのものが「意味と操作可能性を保つ順序」を求めており、意味の保存は人だけが判断します。
  • どこかで閉じ込められるか — フォーカストラップは相互作用の最中にだけ現れます。文書構造をなぞる検査では再現されず、いくつもの段階を踏んで届く画面ならツールはそこまで行けません。
  • ウィジェットが実際に押せるか — 役割とタブ順序の属性が付いていれば規則の検査は通りますが、エンターの処理がなければ動きません。最もよくある「通ってしまった失敗」の形です。

ですからツールは下限であって合格線ではありません。ツールが見つけたものを直す作業は必要ですが、それが終わったからといってキーボードで使える画面にはなりません。

マウスを片づけて一度最後まで通す

代わりになる方法は実際にやってみることだけで、必要なのはマウスを机から片づけることです。ノートパソコンならトラックパッドもふさぎます。手がそちらへ行った瞬間に観察は終わるからです。対象は代表的な流れひとつで足ります。

見るもの確認の仕方失敗の合図

9. 標準が求めるもの

ここまでの項目は、その多くが W3C のウェブコンテンツアクセシビリティ指針にすでに達成基準として入っています。以下はキーボード操作に直接関わる基準を WCAG 2.2 の文書で確認したものです。

番号・名称等級要旨
2.1.1 KeyboardAすべての機能は個々のキー入力に特定のタイミングを要さずキーボードインターフェースで操作できなければならない。終点だけでなく移動の経路に依存する入力が必要な機能は例外
2.1.2 No Keyboard TrapAキーボードでフォーカスを移せる構成要素なら、キーボードだけでそのフォーカスを再び外へ出せなければならない。標準の方法でできないなら出る方法を知らせる必要がある
2.1.4 Character Key ShortcutsA文字・句読点・数字・記号だけのショートカットには、オフにする・割り当てを変える・フォーカスがあるときだけ動作するのうち少なくともひとつが必要
2.4.1 Bypass BlocksA複数のページで繰り返されるコンテンツの塊を飛ばす手段が提供されなければならない

2.4.7 Focus VisibleAAキーボードで操作できるインターフェースには、フォーカス表示が見える動作モードがなければならない
2.4.11 Focus Not Obscured (Minimum)AA構成要素がフォーカスを受けるとき、著作者が作ったコンテンツによって完全に隠されてはならない
3.2.1 On FocusA構成要素がフォーカスを受けただけで文脈の変化が起きてはならない

表を順に読むと前の節とそのまま重なります。到達は 2.1.1、脱出は 2.1.2、フォーカス表示は 2.4.7 と 2.4.11、順序は 2.4.3、繰り返し区間は 2.4.1、ショートカットは 2.1.4 です。等級 A が六つという点も見るに値します。A はこの体系で最も基礎的な層であり、キーボード操作の大半がそこに入っているという意味です。

ひとつは明確にしておく必要があります。どの標準が誰にどの範囲で強制されるかは、管轄と対象となるサービスによって異なります。この記事は技術要件だけを扱っており、法的義務の有無は該当する管轄の現行規定で確認しなければなりません。ただし技術要件の側は管轄と関係なくおおむね同じ項目を指すので、規定を確認する前でも手を付ける場所は決まっています。

確認できなかったこと

  • 管轄ごとの法的義務の範囲と適用対象。国や部門ごとの規定を直接照合していません。
  • 自動チェックツールが全体の問題の何パーセントを捉えるかという数値。ツール提供元が示す比率はありますが、測定方法と標本が公開された中立的な資料を確認できず入れていません。
  • キーボードアクセシビリティに関する紛争や是正要求の件数の推移。調査主体と年度を特定できる資料を確認できませんでした。
  • ウェブ以外のデスクトップフレームワークごとのキーボード対応水準の比較。この記事の項目はウェブを基準にしており、ネイティブのツールキットでは既定で提供される挙動の範囲が異なります。

結論: マウスは近道であって唯一の道ではない

マウス前提で作られた画面が取りこぼすのは機能ではなく状態です。いまどこにいるか、次にどこへ行くか、ここからどう出るか。マウスはこの三つを座標ひとつで代わってくれるので、作る側はそれを管理しているという事実さえ忘れます。キーボードはその管理を画面に要求します。

ですから手を付ける順序は土台からです。閉じ込められる場所を先に無くし、フォーカスがどこかを見えるようにし、移動順序を画面と合わせ、繰り返し区間に飛ぶ道を作ること。ここまでが大半で、ショートカットはその次です。順序を逆にすると、ショートカットだけが華やかでタブでは使えない画面ができあがります。

この作業の結果はひとつの集団だけに向かうものではありません。手首を痛めた人と、発表中の人と、同じ画面を一日に数百回通る人が、まったく同じものを必要としています。マウスは便利な近道です。ただ、画面へ至る道がそれひとつである理由はありません。
