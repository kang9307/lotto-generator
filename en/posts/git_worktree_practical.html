Spreading One Repository Across Multiple Folders - What Is Shared, What Is Blocked, and How to Clean Up

2026-09-29 Dev & Infra

When an urgent bug report arrives while implementing a complex feature, developers conventionally stash their modifications and switch branches. However, in projects with heavy dependencies or long build pipelines, switching branches rewrites the changed files and may force a rebuild. Conversely, cloning the entire repository into a separate folder duplicates the object database, which can be large.

git worktree bridges this gap cleanly. It allows multiple branches to be checked out simultaneously across separate local directories while sharing a single underlying .git repository. Yet beneath this convenience lie strict operational boundaries. Understanding exactly what configuration parameters and stashes are shared, what safeguards prevent branch collisions, and how to safely purge retired working trees is essential to avoiding corrupted repository states.

This article avoids abstract branch management theories. Based entirely on direct execution logs and real console outputs from an isolated test repository, we analyze what is shared, what is blocked, and how to properly clean up when spreading a single repository across multiple folders. For fundamental branch workflows, refer to the Git Branch Collaboration Guide, and for rollback procedures, see the git Undo Decision Guide.

1. Background and Premise - Spreading One Repository Across Folders

1.1 Why Worktrees Instead of Branch Switching

In a traditional single working tree setup, only one branch can occupy the filesystem at any given instant. Shifting to an urgent hotfix requires committing or stashing in-progress modifications, and rewritten files may trigger a rebuild.

Using git worktree, developers can open parallel working folders for distinct branches without disturbing existing states. Compared to creating separate clones, worktrees offer distinct advantages:

  • Disk Space Economy: The commit history, tree objects, and blob database remain centralized inside a single .git directory, eliminating duplicate storage.
  • Instant Commit Visibility: Commits made in any folder become immediately accessible across all linked worktrees without requiring network push or pull actions.
  • Working Files Preserved: The hotfix could be made in a neighboring folder while the working files in p1 were left as they were (7.1).

1.2 Verification Environment and Notation

To verify these behaviors, an isolated repository p was initialized with a single commit (c54568b init) on branch main, and an additional branch named hotfix was prepared. All commands reflect standard terminal syntax that standard developers can invoke directly.

Under Windows environments, excessively deep folder structures can trigger file creation failures in internal git helper tools. Maintaining short base directory paths is highly recommended for stable parallel tree operations.

2. Core Mechanics - worktree add, list, and the Anatomy of the .git File

2.1 Checking Out New and Existing Branches

The core command for expanding working trees is git worktree add. To create and checkout a brand new branch, pass the -b flag along with the destination path. To deploy an existing branch, specify the path followed by the branch name.

git branch hotfix
git worktree add -b feature …/tech_lab/p1
git worktree add …/tech_lab/p2 hotfix
git worktree list

Executing these commands produced the following exact terminal output:

Preparing worktree (new branch 'feature')
HEAD is now at c54568b init
Preparing worktree (checking out 'hotfix')
HEAD is now at c54568b init
…/tech_lab/p  c54568b [main]
…/tech_lab/p1 c54568b [feature]
…/tech_lab/p2 c54568b [hotfix]

Inspecting git worktree list confirms that the primary repository p holds branch main, while linked directories p1 and p2 hold branches feature and hotfix respectively. Three distinct branches reside simultaneously on disk as active working directories.

2.2 The Linked .git Is a File, Not a Directory

Examining the inner structure of a linked worktree reveals how git separates management metadata from physical files. In the primary repository, .git is a full directory, whereas in linked trees, .git is a tiny pointer file.

ls -ld p/.git p1/.git
cat p1/.git
ls p/.git/worktrees/p1
cat p/.git/worktrees/p1/commondir

The resulting console output is as follows:

drwxr-xr-x 1 …   0 Sep 29 07:48 p/.git
-rw-r--r-- 1 … 257 Sep 29 07:48 p1/.git
gitdir: …/tech_lab/p/.git/worktrees/p1
HEAD
ORIG_HEAD
commondir
gitdir
index
logs
refs
../..

As verified by the output, p1/.git is a regular file measuring 257 bytes. It holds a single directive: gitdir: …/tech_lab/p/.git/worktrees/p1. Looking inside that target directory in the primary repository reveals several structural principles:

  • Dedicated Worktree State: Each linked tree maintains its own isolated HEAD, index (staging buffer), and logs inside the parent repository.
  • Shared Commondir Pointer: The commondir file contains a relative path ../.. pointing back to the root repository .git directory.
  • What Is Shared: According to rev-parse --git-path, hooks, config, and refs/stash resolve to the main .git (section 4).

3. Safeguards - Blocking Duplicate Checkouts on Active Branches

3.1 Fatal Error When Checking Out an Active Branch

What occurs if a developer attempts to checkout a branch that is already actively linked to another worktree? With p1 actively hosting branch feature, we attempted to add directory p3 with the same branch:

git worktree add …/tech_lab/p3 feature

Git stopped with the following fatal error (exit=128):

Preparing worktree (checking out 'feature')
fatal: 'feature' is already used by worktree at '…/tech_lab/p1'

The documentation likewise says that by default add refuses to create a new worktree when the branch is already checked out by another worktree.

3.2 Main Tree Switch Prevention and the Dangers of -f

The refusal is not limited to creating worktrees. Running git checkout feature in the main working tree was refused with the same fatal: 'feature' is already used by worktree at '…/tech_lab/p1' (exit=128). In a separate test repository, git switch hotfix on the main side produced an error of the same form.

The force flag (-f) changes that. git worktree add -f …/tech_lab/p3 feature printed Preparing worktree (checking out 'feature') and HEAD is now at c54568b init with no warning, and git worktree list showed both p1 and p3 on [feature].

  • Switching the Safeguard Off: -f turns off the check that blocks duplicate branches. The documentation says this option overrides those safeguards.
  • Cleanup: The p3 created this way was clean, so git worktree remove …/tech_lab/p3 finished without a message (exit=0).
  • Proper Workflow: Rather than forcing duplicates, always spawn a dedicated feature branch using the -b parameter.

4. Empirical Sharing Scope - What Is Shared and What Is Isolated

4.1 Verification Matrix of Shared and Isolated Resources

Determining the precise boundaries of shared configuration and temporary work is critical when operating parallel trees. Through direct experiments, commits, stashes, configuration scopes, hooks, and the HEAD/index paths were checked one by one.

After a commit in worktree p1, git log --oneline --all --graph in the main repository showed 99a62e7 feature work right away. Meanwhile rev-parse --git-path showed HEAD, index, and logs/HEAD pointing to per-worktree paths under worktrees/p1/….

Resource Item Shared Across Trees? Empirical Evidence (Command & Verified Output)
Commits & Branches Shared Commit in p1 is immediately visible in main repository log --all
Stash Storage Shared (Single Global Stack) Stash created in p1 appears in stash list of both main and p2
Standard git config Shared Setting config lab.flag fromN2 in p2 is readable from main
git config --worktree Isolated per worktree Requires extensions.worktreeConfig true; recorded in config.worktree
Hook Scripts Shared Main .git/hooks/post-commit fires on commits in both p1 and p2
HEAD / Index / Logs Isolated per worktree rev-parse --git-path points to unique worktrees/<name>/... paths

4.2 The Stash Trap and Cross-Branch Conflicts

The most dangerous pitfall identified in empirical testing is that stash storage is unified across the repository. When invoking git stash push -m "wip-in-p1" inside p1, checking git stash list from main and p2 yielded identical listings:

Saved working directory and index state On feature: wip-in-p1
stash@{0}: On feature: wip-in-p1          # Inspected from main repo
stash@{0}: On feature: wip-in-p1          # Inspected from p2 (hotfix)

A separate test applied this stash in a worktree on another branch (hotfix). The result was a conflict:

Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
On branch hotfix
…
exit=1
  • Global Stash Stack: Stashes do not belong to individual working trees; they belong to the central repository.
  • Branch Label Verification: Always inspect the On <branch> annotation in git stash list before popping changes.
  • Persistence After Removal: Deleting a worktree directory does not delete the stashes created within it; they remain stored safely.

4.3 Isolated Config via --worktree and Hook Execution Paths

By default, invoking git config alters the primary .git/config, impacting all linked trees. To assign isolated settings to a single working tree, the extensions.worktreeConfig capability must be explicitly toggled.

git config --worktree lab.only fromP2
# Fails: reports that extensions.worktreeConfig must be enabled
git config extensions.worktreeConfig true
git config --worktree lab.only fromP2

Once enabled, the value set with --worktree was written to the main .git/worktrees/p2/config.worktree; p2 read fromP2, while the main tree and p1 could not find it (exit=1).

In contrast, repository hooks located in .git/hooks remain strictly centralized. When a post-commit hook was installed in the main repository, commits made from both p1 and p2 executed that exact script, correctly recognizing the active worktree path as the current working directory.

  • Centralized Automation: Linter and pre-commit checks require installation only once in the primary repository.
  • Working Directory Awareness: Hook scripts relying on relative paths must handle execution from secondary worktree roots.
  • Per-Worktree Config Must Be Enabled: Using --worktree without extensions.worktreeConfig was refused with a fatal error (exit=128).

5. Cleanup - Worktree Remove Rejections and the Necessity of Prune

5.1 Rejection Upon Modified or Untracked Files

To discard a completed worktree, the standard command is git worktree remove. However, if uncommitted modifications or even a single untracked file exist in the directory, git strictly halts the operation.

# Attempting removal after modifying a tracked file
git worktree remove …/tech_lab/p2
# Output: fatal: '…\tech_lab\p2' contains modified or untracked files, use --force to delete it

# After stashing modifications but leaving an untracked file (untracked.txt)
git worktree remove …/tech_lab/p2
# Output: fatal: '…\tech_lab\p2' contains modified or untracked files, use --force to delete it

As verified above, an untracked file (?? untracked.txt) triggers the exact same fatal error. The documentation likewise says only clean worktrees, with no untracked files and no modifications in tracked files, can be removed. To force deletion and wipe uncommitted artifacts permanently, the --force flag must be provided.

  • Clean Removal Standard: The target tree must be completely clean of modifications and untracked files for graceful deletion.
  • Forced Removal: With --force, the folder was deleted together with the modified and untracked files (ls: cannot access 'p2': No such file or directory).
  • Branches Persist: Removing a worktree directory does not delete the branch (hotfix) itself from the repository.

5.2 Manual Folder Deletion, Prunable States, and Branch Locks

What happens if a worktree folder is deleted directly with a file explorer or rm -rf instead of git worktree remove? Worktree p4 (branch tmpbr) was created and its folder was moved elsewhere to simulate a missing folder.

git worktree list
git worktree list --porcelain

Git detects the missing path and flags the tree as prunable in administrative records:

…/tech_lab/p   c54568b [main]
…/tech_lab/p4  c54568b [tmpbr] prunable
worktree …/tech_lab/p4
HEAD c54568b49c4cf9ce2c99ccc5dff022eb0bc00495
branch refs/heads/tmpbr
prunable gitdir file points to non-existent location

In this state, the missing folder keeps holding the branch. Worktree p5 (branch tmp2) was created and moved away the same way, and then git worktree add …/tech_lab/p6 tmp2 failed with the following (exit=128):

fatal: 'tmp2' is already used by worktree at '…/tech_lab/p5'

5.3 Releasing Phantom Records with worktree prune

To release locked branch references caused by manual directory deletions, invoke git worktree prune. Previewing with -n (dry-run) and -v (verbose) is recommended before executing.

git worktree prune -n -v
# Output: Removing worktrees/p4: gitdir file points to non-existent location
git worktree prune -v
# Output: Removing worktrees/p4: gitdir file points to non-existent location

After prune, git worktree list showed only the main tree, and git worktree add …/tech_lab/p4 tmpbr succeeded with Preparing worktree (checking out 'tmpbr'). Likewise, tmp2 could be checked out in p6 after git worktree prune.

6. External Storage and Temporary Trees - Locking and Unlocking

6.1 Locking Against Accidental Pruning

The documentation says that if a worktree is on a portable device or network share which is not always mounted, you should lock it to prevent its administrative files from being pruned automatically. That is what git worktree lock does.

git worktree lock --reason "on USB disk" …/tech_lab/p4
git worktree list --porcelain

Locking records locked on USB disk in the porcelain listing. Running git worktree prune -v safely ignores the missing folder and preserves its administrative records.

6.2 Safe Unlocking and Removal of Locked Trees

A locked worktree could not be removed with git worktree remove either (exit=128):

fatal: cannot remove a locked working tree, lock reason: on USB disk
use 'remove -f -f' to override or unlock first

Following the message, git worktree unlock …/tech_lab/p4 released the lock, and git worktree prune -v then cleaned up the missing worktree with Removing worktrees/p4: gitdir file points to non-existent location. The message and the documentation also mention giving -f twice (remove -f -f), but this test cleaned up with unlock.

7. Practical Guidelines - Optimal Use Cases and Caveats

7.1 Urgent Hotfixes Alongside Long-Running Features

The uses that follow directly from the runs are these:

  • An Urgent Fix Branch in the Next Folder: Checking out the existing hotfix branch with git worktree add …/tech_lab/p2 hotfix let work continue in a side folder while p1 (feature) kept its files. The shared hook also ran for the commit made in p2.
  • Clean Up with remove When Done: Clean worktrees were removed without a message, and the branch and stash remained afterwards. Delete them separately if they are no longer needed.
  • Do Not Delete Folders by Hand: A folder removed by hand kept holding its branch until prune, so the same branch could not be checked out elsewhere.

7.2 Parallel AI Coding Agents and Worktree Isolation

Problems that arise when several AI coding sessions share one repository are covered in the Parallel AI Agents Single Repo Guide. From this article's runs, the points to keep in mind when using worktrees are these:

  • HEAD and index Are Per Worktree: As rev-parse --git-path showed, each worktree gets its own HEAD and index paths.
  • There Is One Stash: stash pop in one worktree can take out a stash pushed by another worktree. Check the On-branch label in stash list.
  • Clean Up with remove and prune: Remove finished worktrees with git worktree remove, and if a folder was deleted by hand, run git worktree prune to release the branch.

7.3 Command and Error Resolution Decision Table

The following decision table summarizes the empirical behaviors, exact error messages, and corrective steps for common worktree workflows.

Scenario Cause & Observed Output (Exact) Corrective Action
Checking out an already active branch fatal: 'feature' is already used by worktree at … Create a new branch (-b). -f switches the safeguard off
Removing a dirty or untracked tree fatal: '…' contains modified or untracked files, use --force to delete it Commit or stash changes first. Even a single untracked file halts removal
Branch locked after manual folder deletion fatal: '…' is already used by worktree at <missing path> / prunable Inspect with git worktree prune -n -v, then run git worktree prune

Unverified Items

  • Linux and macOS Specific Filesystems: Verification was conducted on Windows 10 with NTFS; specific filesystem permission semantics under Linux ext4 or macOS APFS were not directly benchmarked.
  • Network Filesystem (NFS/SMB) Lock Latency: File lock contention and caching delays across distributed network filesystems were outside the scope of this local experiment.
  • Internal Ephemeral Ref Lifecycles: The lifecycle of unshared internal references such as refs/bisect or refs/rewritten was not evaluated under an active git bisect workflow.

## 3. Pre- and Post-Operation Checklist

- [ ] **Use the official command instead of manual deletion**: Do not delete directories via file explorer or `rm -rf`; use `git worktree remove <path>`.
- [ ] **Check remaining branches and stashes**: Deleting a worktree folder leaves branches and stashes intact; clean them up separately if no longer needed.
- [ ] **Inspect branch labels before stash pop**: Because there is one stash, check `On <branch>` in `git stash list` before taking changes out.
- [ ] **Check for untracked files**: `worktree remove` refuses deletion if even one untracked file (`??`) remains in the tree.
- [ ] **Mind long paths on Windows**: In a folder with a very long path git may fail to write inside `.git`; keep the repository on a short path.
- [ ] **Run prune after deleting or moving folders by hand**: For worktrees whose folder is gone, check with `git worktree prune -n -v`, then run `git worktree prune`.
