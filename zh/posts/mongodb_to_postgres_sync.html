搬一次和一直对齐是两个问题 - 把 MongoDB 集合送进 PostgreSQL 时被迫做出的选择

文档进入表时必须决定的东西、捕获变更的方式所造成的约束，以及不该采用这套结构的场合

2026-09-05 开发/基础设施

把 MongoDB 里的一个集合搬进 PostgreSQL，通常被当作半天的活儿。读出文档、塞进列里，还能有什么难的。确实有些情况就到此为止了，那就是只需要搬一次的情况。

麻烦从下一句话开始。然后还要一直对齐。这一句被加上的瞬间，工作的性质整个变了。前一件事是数据类型转换，后一件事是分布式系统。它变成了这样一件工作：先承认两个数据库在不同时刻持有不同的状态，再决定这个差距能容忍到什么程度。

下面把这两个问题拆开。先看文档进入表时不是由口味而是由结构强加的那些决定是什么，以及每个决定日后会让什么变难。接着按断点、重复投递、删除检测的顺序，说清同步为什么远比复制难。最后是反方向：什么时候把两个数据库一直对齐的代价，会超过把它们合成一个的代价。

下文中关于 MongoDB 变更流、恢复令牌、BSON 类型，以及 PostgreSQL 的 jsonb 与 ON CONFLICT 的所有陈述，都出自 MongoDB 官方手册与 PostgreSQL 17 官方文档。凡是行为随版本而异的条目，都同时标注了版本。这里没有性能数字，因为原文里也没有。

缘起 - 难的是映射，不是同步

2026年9月初，韩国的开发者社区转载了一篇题为把 MongoDB 集合复制并同步到 PostgreSQL 的文章。原文是一个叫 VisuaLeaf 的团队的博客，记录了把一个装着就诊记录的集合搬进 PostgreSQL 表并持续对齐的过程。作者留下的一句话是本文的起点：比起同步本身，把 MongoDB 的文档结构映射到 PostgreSQL 的表上更麻烦。

先说清原文的性质比较诚实。那是一篇介绍自家产品的文章。作者用的是 VisuaLeaf Mongo Sync，理由是想把源集合、目标 PostgreSQL 表、字段映射和同步状态用可视化的方式组织起来。在一篇推荐工具的文章里，最值得相信的部分往往不是成功故事，而是卡住的地方的记录，而这篇里留下了两处。

第一处是一个报错，说目标端没有键列，因此无法幂等地执行 upsert。作者把 MongoDB 的 _id 接到一个叫 mongo_id 的 TEXT 列上，并在其上建主键，问题就解决了。第二处是字段名不一致：源端是 labResults，目标端是 lab_results，于是报出关系上不存在该列的错误。解法是逐个字段显式映射，或者在 PostgreSQL 一侧用引号保留驼峰命名。

这两个错误看上去分量相当，性质却完全不同。后者是配置失误，改一次就结束了。前者不是。它不是失误，而是结构提出的要求，本文后面出现的绝大部分约束都能追溯到这一点上。接下来有一半篇幅，是在解释那个错误为什么是必然的。

原文里没有的东西也要说清楚。数据量、文档数、处理速度、延迟，一个数字都没有。初次全量复制与其后的变更接续是按什么顺序衔接的、接缝处的空档怎么填补，也没有写。所以不能拿原文的结果去放大成这种做法通常很快或者通常安全的说法。原文展示的是一个集合、一个工具、一个场景。

把两个问题拆开 - 复制与对齐要求的东西不同

搬一次和一直对齐只是名字连在一起，要求的东西并不相同。最大的差别在于失败之后你还能做什么。前者失败了从头再来一遍就行。清空目标表再填一次即可，这个过程按定义就是幂等的。后者做不到。你得知道自己推进到了哪里，那个位置还得依然有效，而且同一个事件来两次结果必须一样。

需要权衡的点一次性复制持续同步
失败恢复整体重跑，没有副作用需要断点，而断点会过期
重复只读一次，不会发生重启区间必然出现，写入必须幂等
顺序无关，最终状态对上就行同一文档的更新一旦倒序，状态就错乱
删除源端没有目标端也没有，自动对上需要另一套机制才能知道什么消失了
模式变更下次运行用新映射重建即可需要一套在运行中修改映射的独立流程
源端负载集中在运行时刻，可预测常驻，打开的游标持续占用服务器资源
成本增长的轴数据量运行时长与变更率

最后一行在实务中最要紧。一次性复制的成本随数据变大而变大，然后就结束了。同步的成本随时间累积。令牌会过期，集合会被删除，上游会多出字段，最终会出现流悄悄停了三天却没人发现的情况。后面讨论的一切，都在这条轴上。

只有一侧发生写入这个前提也值得点明。这里讨论的是 MongoDB 为源、PostgreSQL 为副本的单向结构。两侧都写入的结构是完全不同的问题，上面还要叠加冲突消解与因果关系追踪，其骨架在把数据握在手里的代价中另行讨论过。

无模式文档进入表时被强加的五件事

有些决定在文档数据库里可以一直往后拖。关系表不给你这个方便。要建列就得定类型，要定类型就得先决定这个字段究竟是什么。所以映射工作的实质不是转换，而是把之前一直拖着的决定一次性结清。被强加的决定大体有五个。

  • 标识 - 用什么类型的列来接 _id。它如果不成为主键，后面的一切都会塌
  • 类型推断 - 同一字段在不同文档里类型不同时，往哪一边靠
  • 嵌套 - 文档里的文档是摊成列，还是整块留着
  • 数组 - 是规范化成子表，还是留成数组列或 JSONB
  • 缺失 - 字段不存在和字段为 null，这两种状态要不要区分着保存

下面逐个来看。它们的共同点是没有任何一个选择是免费的。每个选择都把现在变轻松的东西和以后变困难的东西配成了一对。

用什么来接 _id

这是最先要定、也最难回头的决定。MongoDB 默认的 _id 是 ObjectId，按官方文档它由12 字节构成。前 4 字节是以 Unix 纪元为基准、以秒计的创建时间戳，接下来 5 字节是每个客户端进程生成一次的随机值，最后 3 字节是从随机值起步的自增计数器。文档指出，时间戳和计数器高位字节在前，这与其他 BSON 值相反。

这里还有一句在实务上更重的话。文档明确写道，ObjectId 的值虽然应当随时间递增，但不一定单调。给出的理由有两个：时间分辨率只有一秒，因此同一秒内创建的值之间没有顺序保证；而且值由客户端生成，各机器的系统时钟可能不同。也就是说，把 _id 当作变更检测水位线的设计从一开始就是坏的。这条线索在讲轮询的那一节还会再出现。

接收端实际上只有两个选项。像原文那样展开成 24 个字符的十六进制字符串，用 text 主键来接；或者把 12 字节原样用 bytea 接住。前者人能读、任何工具都好处理，但存储量翻倍，索引也随之变大。后者保住了原始尺寸，但查询结果肉眼读不了，工具支持也薄。多数团队选前者，理由不是性能，而是运维过程中人需要看这个值的场合太多。

无论选哪一个，有一个条件不能让步：那一列必须是主键。原文撞上的第一个错误正是这里。没有键就没有幂等的 upsert，没有幂等的 upsert 就吞不下重启带来的重复，那样一来重启本身就不可能。再加上后面会看到的删除事件根本不带文档内容，所以没有一个由 _id 推导出来的键，就根本没有办法确定该删哪一行。

顺带一提，把随机性很强的值用作主键会对索引造成什么，是另一个主题。ObjectId 因为前段是时间，情况比完全随机的键要好，但这条轴上的通论整理在为什么不应把 UUID 作为主键里。

同一字段在不同文档里类型不同时

这是文档数据库里最常见、也最晚被发现的问题。集合建起来的头一个月，amount 全是整数，然后从某个时点开始混进了字符串，某处又是以 NumberDecimal 进来的，还有一部分文档干脆没有这个字段。MongoDB 不会拦这些。于是写入程序成了系统里第一个把这件事告诉你的东西。

// 同一个集合、同一个字段名。类型逐文档不同。
db.visits.insertMany([
  { visitId: "VIS-1", amount: 12000,                  visitDate: ISODate("2026-09-01T09:00:00Z") },
  { visitId: "VIS-2", amount: "12,000",               visitDate: "2026-09-02" },
  { visitId: "VIS-3", amount: NumberDecimal("12000"), visitDate: ISODate("2026-09-03T09:00:00Z") },
  { visitId: "VIS-4",                                 visitDate: null },
  { visitId: "VIS-5", amount: null,                   visitDate: ISODate("2026-09-05T09:00:00Z") }
]);

// VIS-4 根本没有 amount 字段，而 VIS-5 有这个字段但值是 null。
// 用同一个列来接这两者，两种状态的区别就消失了。

选项有三个，各自放弃的东西不同。第一，用最宽的类型来接。全塞进 text，写入就永远不会停。代价是排序和范围查询按字符串规则走，于是 "9000" 排在 "12000" 之上。第二，用严格类型接，不合就让它失败。数据质量守住了，但上游一旦混进一个坏值，整条同步立刻停摆。第三，正常值走类型化的列，异常值分流到另一个列或 JSONB。要写的代码变多，但同时避开了运行中停摆和静默丢失。

BSON 这一侧还要再叠一层。按官方文档，BSON 的 Date 是以 Unix 纪元为基准、以毫秒计的 64 位整数，而且带符号，所以能表示 1970 年之前。因此用 timestamptz 来接本身很自然，但值得记住的是：比毫秒更细的精度在源端从一开始就不存在。接收端的类型更精密，并不会凭空长出原本没有的信息。

数值也一样。BSON 区分 Double、32 位整数、64 位整数和 Decimal128。文档记载 Decimal128 有 34 位十进制有效数字，指数范围从 -6143 到 +6144。如果处理金额的集合用的是 Decimal128，接收端的列就必须是 numeric；一旦用 double precision 去接，为那份精度付出的成本当场作废。

嵌套文档 - 在拍平与 JSONB 之间

原文的选择很明确：简单字段进普通列，嵌套的对象和数组存成 JSONB。于是 visitId、status、visitDate 分别成为 text、text、timestamptz 列，而 patient、doctor、symptoms、prescriptions、invoice、labResults 这些则全部成了 JSONB 列。这是个合理的默认值，但这个选择买进了什么、卖出了什么，需要说清楚。

拍平占优的情形

把 patient.fullName 摊成 patient_full_name 列之后，就可以往这个列上挂约束。NOT NULL、检查约束、唯一性、外键全都可用。规划器用的统计信息也按列采集，选择率估计因此更准，普通的 B-tree 索引就够用了。如果这个值是什么已经确定，而且你打算拿它做连接或过滤，拍平就是答案。

代价是模式必须追着源端跑。在 MongoDB 一侧往嵌套文档里加一个字段是不需要发布的事，而在接收端每加一次就要跟一次 ALTER TABLE 和映射修改。当源端团队和副本团队不是同一拨人时，这个落差立刻变成运维负债。

JSONB 占优的情形

PostgreSQL 文档把 json 和 jsonb 的差别写得很清楚。json 存的是输入文本的精确副本，处理函数每次执行都得重新解析；jsonb 则以分解后的二进制格式存储，因为多了转换开销所以输入稍慢，但由于不需要重新解析，处理起来显著更快。文档的建议是明示的：除非有相当特殊的需求，例如对对象键顺序的历史假设，否则多数应用都应该优先把 JSON 数据存为 jsonb。

作为交换，jsonb 会扔掉一些东西。文档写道，它不保留空白，不保留对象键的顺序，也不保留重复键，输入里出现重复键时只保留最后一个值。json 三者都保留。如果原始文档的字段顺序或者字节级的原样以后可能会用到，这个差别就是决定性的。

文档也指出索引是 jsonb 的一大优势。不过运算符类的选择会在后面产生影响。默认的 GIN 运算符类支持键存在运算符 ?、?|、?&，包含运算符 @>，以及 jsonpath 匹配运算符 @? 和 @@。非默认的 jsonb_path_ops 不支持键存在运算符，只支持 @>、@?、@@。作为回报，文档称在同样的数据上 jsonb_path_ops 索引通常小得多，而且检索的特异性更好，尤其是查询里包含高频出现的键时。

这个选择会挡住什么，在第八节还会再遇上。需要一个询问键是否存在的查询的那一刻，你会因为当初选了更小的索引，而没法用索引来回答这个问题。

CREATE TABLE mongo_visits_sync (
    mongo_id     text PRIMARY KEY,        -- ObjectId 以 24 字符十六进制字符串接收
    visit_id     text,
    status       text,
    visit_date   timestamptz,
    -- 字段构成可变的嵌套文档与数组整块放进 jsonb
    patient      jsonb,
    lab_results  jsonb,
    -- 源文档里没有的列，承载同步过程本身的状态
    src_ts       timestamptz NOT NULL,
    deleted_at   timestamptz
);

-- 要用键存在运算符就必须是默认运算符类
CREATE INDEX ON mongo_visits_sync USING gin (patient);

-- 只用包含查询和 jsonpath 的话，这个索引要小得多
CREATE INDEX ON mongo_visits_sync USING gin (lab_results jsonb_path_ops);

值得留意这份表定义里有两个源端没有的列。src_ts 和 deleted_at 不是文档内容，而是同步这个流程本身的状态。需要这类列这件事，就是复制与同步是两个问题的最直观的证据。

数组 - 在子表与单列之间

数组比嵌套多一个选项，岔路也就更宽。答案取决于它是标量数组还是文档数组。

像标签列表这样的字符串数组，PostgreSQL 的数组类型 text[] 最自然。数组运算符能用，GIN 索引也能建。麻烦在于，日后如果每个元素要带上元数据，数组列没有地方安放。等到有人提出要给标签记录添加时间，结构就得重做。

如果是文档数组，问题就压缩成一个：这个元素是不是要被独立查询的对象。如果需要按处方项目聚合，需要找出含有某种药品的就诊记录，计划按项目粒度做连接，那么规范化成子表就是正解。这样一来关系型的全套工具都回来了。

代价出现在同步这一侧。源端一个文档发生变更的一个事件，在接收端必须被翻译成若干子行的删除与插入。这多条语句必须在一个事务里原子地完成，中途失败就会留下父行与子行状态对不上的局面。原本一次单行 upsert 就完事的活儿，变成了一套流程。

如果元素只会整块读写，那就用一个 JSONB 列更好。一个文档对应一行的关系得以保持，写入逻辑仍然是简单的 upsert。代价是每次统计元素个数或者按元素排序都要付展开的成本。判断标准不是数据的形状，而是你要向这份数据提出的问题的形状。

字段缺失和 NULL 不是一回事

这是信息流失得最安静的地方。MongoDB 文档里的某个字段可以处于三种状态：字段压根不存在、存在但值为 null、或者有值。这三者含义不同。若是问卷作答，它们分别对应没问过、问了但没答、答了。

把它拍平成普通列，前两种状态就变成了同一个 SQL NULL，没有办法还原。PostgreSQL 文档在 JSON 原始类型对照表里，在 JSON 的 null 所对应的 PostgreSQL 类型那一栏写着SQL NULL 是另一个概念。这是在警告：两个世界在用同一个词指不同的东西。

要保住这三种状态，就得把值留在 JSONB 里。这样才能通过询问键是否存在来把缺失和 null 分开。而上一节的索引选择在这里拖了后腿。询问键存在的 ? 运算符只有默认的 GIN 运算符类才支持，jsonb_path_ops 不支持。如果当初因为索引更小而选了 jsonb_path_ops，那就变成了保住三种状态却没法用索引去问它们。

同一类的陷阱还有两个。PostgreSQL 文档写道，jsonb 会拒绝超出 PostgreSQL numeric 类型范围的数值，而 json 不会。并且在 JSON 原始类型对照表中，对数值写明NaN 和无穷大不被允许，对字符串写明\u0000 不被允许，表示数据库编码中不存在字符的 Unicode 转义同样不被允许。

BSON 的 Double 可以装 NaN 和无穷大。如果计算失误让这样一个值混进了集合里的某个文档，那份文档就进不了 JSONB 列。字符串里的空字符同理。这两种情况都属于那种在初次全量复制时安静地混过去、某一天在一条变更事件上才第一次炸开的问题。如果映射阶段没有事先决定这类值的去处，那一天的同步就会停在那里等人发现。

映射决策表 - 得到什么、放弃什么

把前面五个决定汇总成一张表。每一行是一种文档结构、一个接收它的选项，以及那个选项所放弃的东西。最后一列就是这张表存在的理由。

嵌套文档，字段固定拍平成列NOT NULL、检查、外键、按列统计上游每多一个字段，DDL 就得跟一次
嵌套文档，字段可变一个 jsonb 列不改模式也能接住没法挂列级约束，统计信息被压成一个
嵌套文档，需要保真json 列空白、键顺序、重复键都保留每次查询都要重新解析，没有索引支持
标量数组text[]数组运算符与 GIN 索引没有地方给单个元素挂元数据
文档数组，元素要被查询子表加外键元素粒度的查询、聚合与连接一个文档的变更变成多行的删除与插入
文档数组，只整块使用jsonb一个文档对应一行，upsert 保持简单元素的统计与排序每次都要付展开成本
缺失与 null 之别拍平成列-两种状态变成同一个 SQL NULL，区别消亡
缺失与 null 之别jsonb 配默认 GIN三种状态全部留存必须放弃 jsonb_path_ops 那个更小的索引

贯穿全表有一条规则：现在灵活的选择会让日后的查询变贵，现在严格的选择会让日后的模式变更变贵。哪一边更好，不由数据的性质决定，而由你当初为什么把这份数据送进 PostgreSQL 决定。为了用 SQL 聚合和连接而送过去的，严格那一边对；为了不丢失原样地留存而送过去的，灵活那一边对。

怎样捕获变更 - 轮询与变更流

从这里开始就是同步特有的问题了。第一个问题很简单：怎么知道什么变了。

轮询实际漏掉的东西

最先想到的办法是定期发一条查询，只把最近的取回来。实现容易，也不需要特殊的部署形态。可这个方式有三个洞，而且三个都很安静。

第一，没有合适的列可以当水位线。用 _id 就会撞上前面说过的 ObjectId 不单调这件事。因为时间分辨率是一秒而客户端时钟各不相同，ObjectId 小于已处理位置的文档完全可能在之后才被插入。那份文档会被永久跳过。改用 updatedAt 这类应用字段，只要有一条写入路径忘了更新它，结果一模一样。

第二，删除看不见。轮询是按条件筛选当前存在的文档。已经消失的文档不匹配任何条件。于是目标表里会留下源端没有的行，并且不断堆积。

第三，延迟和负载是在做交换。周期缩短，查询就不停地扎进源端；周期拉长，副本就变旧。而且在一个周期内变了好几次的文档，只能看到最后一个状态。如果下游需要依据中间状态做判断，轮询本来就不是合适的工具。

变更流所要求的东西

MongoDB 的变更流能补上这些洞，但有前提。手册写明变更流可用于副本集和分片集群。这些部署必须使用 WiredTiger 存储引擎，并且是副本集协议版本 1。在启用静态加密的部署上同样可用，而且明确写明其可用性与多数派读关注的支持与否无关。单机部署根本没有这条通道。

手册里还有若干运维层面的注意事项，每一条晚知道都要付代价。变更流无法使用索引，而且 MongoDB 不支持在 oplog 集合上创建索引，因此文档建议避免开启大量针对特定目标的变更流，因为它们会影响服务器性能。意思是，每个集合挂一条流的设计，会随集合数量成比例地啃噬服务器。

对于含有仲裁者成员的副本集，文档说如果承载数据的成员不足以让操作达成多数派提交，变更流可能会保持空闲。故障时流不是报错，而是变安静。在分片集群上，对该集合几乎没有活动的冷分片会拖慢变更流的响应时间，因为 mongos 仍然必须去询问那些分片，才能保证变更的全序。反过来，活动量很大的分片集合上 mongos 可能跟不上所有分片的变更，文档因此建议使用通知过滤器，例如用 $match 只保留关心的操作。

需要权衡的点轮询变更流
部署要求无，单机服务器也能跑副本集或分片集群，WiredTiger，pv1
删除检测结构上不可能以删除事件的形式送达
中间状态一个周期内的变更被压平按操作粒度全部送达
重启一个水位线值，不会过期恢复令牌，只在 oplog 历史尚存时有效
顺序水位线不单调就会漏掉文档流给出顺序，分片上由 mongos 保证
源端负载与周期和查询成本成正比游标常驻打开，数量一多就影响服务器
静默失败水位线不推进也很难察觉多数派提交受阻时会保持空闲

断点 - 令牌所要求的东西

选定变更流之后，下一个问题只有一个：进程死掉又活过来，从哪里接着读。

按手册所述，变更事件通知会把恢复令牌放在 _id 字段上送达。令牌有两种：指向特定变更事件的事件令牌，以及表示一个没有对应变更事件的时间点、由服务器周期性生成以表明集群时间已推进的高水位令牌。第二种的存在在实务上比初看要重要得多，因为它意味着即便在变更稀少的集合上，也能让保存的断点持续往前推。

恢复的方式有三种，各自面向不同的处境。resumeAfter 从特定事件之后接着来。startAfter 则是在那个位置之后建立一条新的流。startAtOperationTime 在特定时间点打开游标，文档说如果指定的起点在过去，那么它必须落在 oplog 的时间范围之内。

前两者的差别在出事时才显现。文档明确写道失效事件关闭流之后不能用 resumeAfter 恢复，并指引在那种情况下改用 startAfter 开启新流。失效事件的例子里写着集合删除或改名。游标关闭的条件还包括显式关闭、连接断开或超时；在分片集群上移除分片可能会关掉已打开的游标，而且文档警告这样关闭的游标未必能完全恢复。

令牌失效的条件同样明确。文档写道oplog 中必须保留足够的历史，以便定位与该令牌关联的操作。因此可重启时间的上限就是 oplog 窗口，而那是数据库的设置，不是同步工具的设置。运维建议文档写道，如果预计会有可观的停机时间，比如升级或重大故障，就应当考虑加大 oplog 的尺寸，让操作保留的时长超过预估的停机时长。如果你打算把同步进程停上几天，那句话就是那天唯一的防线。

// 读取保存的断点。没有就从现在开始打开。
const saved = await loadResumeToken();

const options = { fullDocument: "updateLookup" };
if (saved) options.resumeAfter = saved;   // 失效事件之后这一句会失败

const stream = db.collection("visits").watch([], options);

for await (const event of stream) {
  // 每个变更事件的 _id 就是恢复令牌
  await applyToPostgres(event);           // 先落地
  await saveResumeToken(event._id);       // 然后再记录位置
  // 顺序反过来就会丢事件，按这个顺序则会产生重复。
  // 丢了没法补，重复可以靠幂等吸收，所以这个顺序才是对的。
}

注释最后两行就是这一节的结论。落地和保存令牌是对两个不同系统的两次写入，没有办法把它们裹进同一个事务。所以必须有一个在先，而无论选哪一个都会出事。先写令牌就是丢失，先落地就是重复。能补救的只有重复。

至少一次 - 幂等写入为何成为强制项

上一节的选择直接决定了投递保证的等级。既然决定先落地，这条管道就是至少一次。同一个变更可能到达不止一次，这不是缺陷而是被设计出来的性质。于是写入端要承担的东西也就定下来了。

  • 同一个事件应用两次结果必须一样 - 意思是要把操作表达成覆盖，而不是累加
  • 必须有键 - 无法确定覆盖谁，幂等性就不成立。原文撞上的第一个错误正是这个
  • 迟到的旧事件不得覆盖新状态 - 在顺序保证可能被打破的区间里，需要做版本比较

在 PostgreSQL 里表达这件事的工具是 ON CONFLICT。文档的定义很简洁：ON CONFLICT DO NOTHING 的替代动作只是回避插入这一行，而 ON CONFLICT DO UPDATE 则更新与待插入行冲突的既有行。冲突目标既可以通过唯一索引推断来指定，也可以用 ON CONSTRAINT 直接写出约束名。

这里有一条容易漏掉的规定。文档写明DO NOTHING 时指定冲突目标是可选的，而 DO UPDATE 时必须提供。用于更新的值则通过名为 excluded 的特殊表来引用。用文档自己的说法，SET 与 WHERE 子句以表名或别名访问既有行，以 excluded 访问待插入的行。

最贵的陷阱在最后。文档把带 ON CONFLICT DO UPDATE 的 INSERT 称为确定性语句，说该命令不允许对任何单个既有行作用超过一次，并警告出现这种情况时会抛出基数违规错误。这为什么重要？因为把变更流按批写入时，同一个文档的多条事件落进同一批是家常便饭。原样塞进一条语句，整批就失败了。所以写入之前必须做一次按键只留最新一条的整理。

-- 同一批里出现两次相同的 mongo_id 就会触发基数违规。
-- 所以在写入之前，按键只保留最新的一条。
INSERT INTO mongo_visits_sync AS t (mongo_id, visit_id, status, visit_date, patient, src_ts)
SELECT DISTINCT ON (mongo_id)
       mongo_id, visit_id, status, visit_date, patient, src_ts
FROM   staging_changes
ORDER  BY mongo_id, src_ts DESC
ON CONFLICT (mongo_id) DO UPDATE
SET    visit_id   = EXCLUDED.visit_id,
       status     = EXCLUDED.status,
       visit_date = EXCLUDED.visit_date,
       patient    = EXCLUDED.patient,
       src_ts     = EXCLUDED.src_ts,
       deleted_at = NULL
WHERE  t.src_ts < EXCLUDED.src_ts;   -- 阻止旧事件覆盖更新的状态

最后那个 WHERE 子句负责第三条要求：既有行的版本如果比新来的还新，就跳过更新。没有它，重启区间重放的旧事件就会抹掉这期间已经落地的最新状态。顺带一提，文档也建议，若需要在一条语句里混用 INSERT、UPDATE 和 DELETE，可以考虑 MERGE，并称它是比 ON CONFLICT 更贴近 SQL 标准的替代方案。

另外，变更流默认只返回更新操作中字段的增量这一点也和幂等性纠缠在一起。要拿到完整文档就得把 fullDocument 设为 updateLookup，而文档把它描述为从集合中重新读取最新的多数派已提交版本的一次独立查找。于是就有了附加条件：如果在更新与查找之间文档被删除或集合被删除，fullDocument 可能缺失；如果这期间还有别的多数派已提交操作改过该文档，返回的文档可能与更新时刻的文档大不相同。也就是说 updateLookup 给你的是此刻的状态，而不是当时的状态。

这个性质也有好的一面。因为查找发生在重放的时刻，所以哪怕是重放的旧事件，只要目标是收敛到最终状态，它反而会自我纠正。反过来，如果目标是原样留存变更历史，updateLookup 就不是合适的工具。6.0 起提供的前像与后像才是为那个位置准备的，文档写明插入的文档没有前像，删除的文档没有后像。

还有一条尺寸限制。运维建议文档写道，变更流的响应文档必须遵守 16MB 的 BSON 文档上限，而根据集合中文档的大小，若生成的通知文档超出该上限，通知可能失败。文中举的例子是配置为返回完整更新文档的更新操作，以及插入或替换接近上限的文档。从 6.0.9 起可以用 $changeStreamSplitLargeEvent 聚合阶段把事件拆成更小的片段。如果集合里装着大文档，最好在映射阶段就先把这个限制算清楚。等失败了才知道，那时流已经停了。

删除 - 怎样知道一个文档消失了

这是同步里最常被漏掉的一项，也是漏掉之后最晚浮上水面的一项。插入和更新出错会让值变得奇怪，所以有人会注意到。漏掉的删除表现为一行安安稳稳地待在它该在的位置上，因此没有人觉得哪里不对。

变更流的删除事件带什么，参考文档写得很准确。事件里有作为恢复令牌的 _id、对应 oplog 条目时间戳的 clusterTime、命名空间 ns、操作类型 operationType，以及 documentKey。文档把 documentKey 描述为包含该 CRUD 操作所创建或修改文档的 _id 值的一个文档，并补充说对分片集合这个字段还会显示完整的分片键，而如果 _id 已经是分片键的一部分则不会重复出现。从 6.0 起还会加上服务器日期时间 wallTime。

决定性的一句话是这个：fullDocument 被省略，因为在变更流游标把删除事件发给客户端的时刻，那份文档已经不存在了。也就是说，删除事件告诉你的只有消失者的标识符。

这一句话事后正当化了前面好几个决定。如果目标表的主键不是从 _id 推导出来的，那么收到删除事件也没有办法推断该删哪一行。想按文档内容匹配也不行，因为内容根本不会送来。原文最先撞上的没有键列因而无法幂等 upsert 的错误，看起来是插入侧的问题，实际上同时也堵死了删除。

如果确实需要删除前的内容，路是有的。从 6.0 起，通过 createCollection、create 或 collMod 在集合上启用 changeStreamPreAndPostImages，并在 watch() 里把 fullDocumentBeforeChange 设为 required 或 whenAvailable，就能一并收到删除前的文档。不过文档列出了两种拿不到前像的情况：删除操作发生时集合上并未启用该功能，以及在 expireAfterSeconds 设定的保留时间之后被清除。换句话说，这个功能只能回溯到你事先打开它的那一刻。它没法在事故之后再打开来找回过去。

-- 删除事件只带 documentKey，文档内容不会送来。
-- 所以目标端的键如果不是来自 _id，就无法定位要删除的对象。

-- 方案一。逻辑删除。把消失这件事本身作为历史留下。
UPDATE mongo_visits_sync
SET    deleted_at = $2
WHERE  mongo_id = $1
  AND  deleted_at IS NULL;

-- 方案二。物理删除。删除一个已经不存在的行不算错误，因此它本身就是幂等的。
DELETE FROM mongo_visits_sync
WHERE  mongo_id = $1;

选哪一个由副本的用途决定。如果是分析用副本，逻辑删除通常更好，因为什么时候消失的本身就是一项事实，而物理删除会把这项事实一并抹掉。代价是所有查询都得带上 deleted_at IS NULL 这个条件，而某个漏掉它的仪表盘会安安静静地给出错误的数字。如果要的是与源端一模一样的样子，物理删除才对，这时删除不存在的行不算错误这个性质本身就提供了幂等性。

无论选哪一个，比对流程都得另外准备。流悄悄断掉的那段时间、令牌过期而从头重来的那段时间、失效之后新开一条流的那段时间里，删除事件会被整段跳过。如果没有定期比对两端键列表、找出只在目标端存在的键这项工作，那些区间的遗漏就会永远留着。

什么时候不该采用这套结构

以上就是这套结构所要求的东西。现在轮到看反方向了。存在这样一个点：把两个数据库一直对齐的代价，超过了把它们并成一个的代价。

  • 副本可以旧一点的时候 - 如果几个小时的延迟可以接受，而且数据规模能装进一次重载，那么定期全量重载便宜得多。不需要恢复令牌，不需要幂等，也不需要删除检测。源端没有的东西新一轮加载里也没有，所以删除按定义自动就对上了
  • 必须在一个事务里同时读两边的时候 - 跨两个不同数据库的原子读取，任何同步方案都造不出来。如果这个需求是真的，那么需要的是整合而不是同步
  • 两侧都发生写入的时候 - 这会转到与单向副本难度不同的问题上。需要冲突消解规则与因果关系追踪，从那时起答案就由领域规则而不是工具来决定
  • 映射一直在动的时候 - 如果上游团队的文化是随意往文档里加字段，那么拍平的列会变成永久的维护税。这种情况下把副本放进一个 JSONB 列，或者干脆不做副本，都更好
  • 单机 MongoDB - 不是副本集就没有变更流，剩下的只有前面看过的那个满是洞的轮询。在这个基础上承诺实时对齐，是守不住的承诺

反过来，这套结构确实合适的位置也很清楚：MongoDB 留作真实之源，PostgreSQL 只作为只读副本存在，用来做 SQL 擅长的事情，即连接、窗口函数、接 BI 工具、临时聚合。副本上没有写入这个条件，抹掉了前面一半的难处。副本这一侧的 Postgres 在运维视角该怎么守住，创业公司的 Postgres 生存指南讲过；怎样让写入作业本身在 Postgres 内部可重试，用 Postgres 构建持久化工作流讲过。

归结起来是这样。原文作者写的比起同步，映射更麻烦只对了一半。映射之所以麻烦，是因为那些是难以回头的决定；之所以难以回头，是因为那些决定全都是同步得以成立的前提。用什么当键、要不要区分缺失与 null、数组放在哪里，表面上是模式设计问题，实际上是在当场决定重启、幂等与删除检测是否可能。正确的顺序不是先做映射再把同步接上去，而是先弄清同步要求什么，再去做映射。

未能确认的部分

  • 变更流更新事件所携带增量的确切结构未能确认。手册里确认到的只是默认只返回更新操作的增量这一句，其中的字段名与形态在另一份参考文档里，那份没有打开，因此没有写进正文
  • PostgreSQL numeric 的确切位数与指数上限未能确认。确认到的是 jsonb 会拒绝超出 numeric 范围的数值，以及 BSON Decimal128 的 34 位有效数字与 -6143 到 +6144 的指数范围。两个范围之间的包含关系没有算
  • PostgreSQL timestamp 系列的内部时间分辨率没能对着原始文档确认。正文只以 BSON Date 是毫秒这一已确认事实为依据
  • 用超出 oplog 窗口的恢复令牌尝试恢复时，服务器究竟返回什么错误未能确认。手册只写了必须有足够历史这个要求，那份文档里没有失败时的错误码
  • 高水位令牌生成得有多频繁、这个周期能否调整，未能确认。文档里只有周期性生成这一句
  • 原文所用的工具怎样把初次全量复制与变更流衔接起来未能确认。填补两段接缝处的空档正是这类工具的核心，而原文没有写这套流程
  • 原文里关于数据量、文档数、处理速度、延迟一个数字都没有。因此关于这种做法的性能特征，本文什么也没有搬运
