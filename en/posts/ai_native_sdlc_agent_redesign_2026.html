This article is based on the playbook "The AI-native SDLC playbook", which Anthropic published on August 21, 2026 and revised on September 28, 2026. The facts in the body are only those written in the playbook, and everything the playbook does not say is collected in the "Unconfirmed Details" section at the end. The playbook is a proposal that assumes the use of Anthropic's own products, Claude and Claude Code, and it does not publish measured figures for the effect of adopting it.

Shifting the Coding Bottleneck — Impact of Implementation Acceleration on SDLC

The software development lifecycle (SDLC) is the process that takes software from idea to production. The playbook notes that most organizations run some version of the same six stages, covering planning, design, building, testing, deploying, and maintaining software. Traditionally, each stage is a discrete phase owned by a different role: product managers write requirements, technical architects turn them into designs, engineers build the designs, QA teams at regulated enterprises verify the result, release teams ship it, and operations monitors what is running. Work moves between the phases through documents, tickets, and sign-offs.

The playbook explains that the traditional SDLC is process-heavy in order to ensure accountability and control at each step. It was designed to maximize efficiency in an era when the most time-consuming and expensive stage was writing and implementing code, which is no longer the case. PRDs, estimation rituals, and product security reviews all existed to force alignment during what could be weeks, months, or quarters of development work. The traditional SDLC also features controls that assume every step is performed by humans.

When code is no longer the bottleneck, and the build phase runs faster than the traditional SDLC allows for, the playbook says that three things become true.

  • The bottleneck moves: it shifts to the steps to the left and right of the build phase, mainly planning, review and test, and deploy, which still run at human speed.
  • The controls stop matching reality: reviewing each line by hand made sense when a person had written it, but it cannot keep up once agents write most of the diff.
  • Governance costs increase: exceptions still route through meetings and committees that meet weekly or monthly.

The caption of the playbook's figure summarizes the picture: human-speed stages keep their length while build collapses to hours. Using security as an example, the playbook observes that security teams are sized for human output, so when agents multiply code output, either the review queue builds or code ships under-reviewed. A regulated organization cannot accept either outcome, so its security and policy checks have to keep pace with the agents.

From Linear Handoffs to an Artifact-Driven Loop — Paradigm Transformation

The playbook defines the AI-native SDLC as a reimagined process that combines the old control objectives with new enforcement. Instead of a linear flow, the process becomes a loop, and AI is embedded at each point. It promotes automated handover and triggering of subsequent plays, which is meant to address the manual and clunky nature of handoff between the phases of the traditional SDLC. The playbook adds that the shift is also called the agentic SDLC, the AI SDLC, or simply agentic software development, and that these labels describe the same thing.

The thread running through the right-hand column of the comparison is the committed artifact. Each stage ends by writing one to version control, and the next stage begins by reading it. For the early stages, .md files are the predominant artifact, because a product owner and an agent can both read and act on the same file. From Build onward, the artifact is code and its records. The artifacts named in the playbook are the following.

  • intent.md: a proto-spec that states what is wanted, why, and under which constraints, in the originator's own words.
  • spec.md: the requirements and design spec produced from an approved intent.md, with the organization's skills for brand, security, compliance, and UX applied as constraints.
  • plan.md: the implementation plan that Claude produces in plan mode and the engineer approves, naming the files that change, the order of work, the risks, and the proof.
  • The code diff and its tests: the actual change together with the tests that demonstrate it.
  • The PR with its review findings: the review policy itself is written in REVIEW.md at the repository root.
  • The incident record: the record that is left by the maintain stage.

The chain of commits is also the audit trail: who asked for what, what the agent produced, and who approved it. The playbook states that humans remain accountable for every decision that requires judgment, and that in an agentic SDLC the human attention shifts along with the artifacts that must be reviewed.

Stages 1 and 2: Plan and Design — Compressing intent.md into spec.md

The goal of Stage 1, Plan, is that ideas stop waiting for someone to write them up. Intent is captured once, in the originator's own words, as a version-controlled artifact that the next stage can act on. When a person has an idea, they brainstorm with Claude and produce a markdown proto-spec, which is saved as intent.md. People who are not engineers can use Claude through claude.ai or Cowork, and for contributors without git experience a connector to the version-control system lets Claude commit the markdown file on their behalf. Claude asks the questions an analyst would ask, namely the scope, the users, the constraints, and what success looks like.

# Intent: claims status self-service
                    Author: J. Ortiz (claims operations). Status: draft.
                    
                    ## Problem
                    Customers phone the contact center to ask where their claim is.
                    Handlers spend roughly a third of call time on status-only queries.
                    
                    ## Proposed outcome
                    Customers see claim status, next step and expected date in the portal.
                    
                    ## Affected users and systems
                    Claims handlers, portal team, claims-core API.
                    
                    ## Constraints
                    No new PII in the portal session. Existing authentication only.
                    
                    ## Open questions
                    Do third-party loss adjusters need access too?

The playbook also says where intent lives. For a single product the simplest home is an intent/ folder in the product repo, which keeps the artifact chain next to the code derived from it; a dedicated intent repo is only worth the overhead when intent spans many repositories, and in a monorepo it is simply a directory.

The intent.md can enter through different routes: a person has an idea, a ticket is filed, or an incident is surfaced by an alert from the maintain stage. Whichever route it takes, the product owner reviews and corrects the agent-written intent.md before it is committed. An accepted intent.md triggers the requirements and design pass.

In Stage 2, Design, Claude takes the approved intent.md and produces a requirements and design spec. This is guided by the organization's skills for brand, security, compliance, and UX, which are defined as Skills and applied to the spec as constraints. The product owner reviews the spec but does not write it, and the playbook says that no engineering skill is required of this person. In the traditional model, analysts formalize the idea into requirements and designers then parse those back into a design; the playbook's assessment is that this separation exists for accountability but is slow and lossy. The prompt that the playbook gives is the following.

Read the attached intent.md and produce a requirements and design spec for integrating it into our existing codebase. Apply the skills available to you so the plan conforms to our brand guidelines, security policies and UX standards. Document the spec fully as spec.md, ready to hand to the engineering team. Describe clearly any areas of concern, especially where you cannot satisfy contradicting policies.

The playbook describes the governance of this stage as follows. Instead of being discovered in a review weeks later, the live policy is read and applied while the spec is written. The spec, the prompt that produced it, and the skill versions in force are all logged in version control. The product owner signs off the spec and routes flagged concerns to the named policy owners, which is why the prompt above asks the agent to describe clearly any areas of concern, especially where it cannot satisfy contradicting policies.

A stage ends by committing an artifact, with the commit initiating the next stage. An accepted intent.md triggers the requirements and design pass, an approved spec.md triggers plan mode, a merged PR triggers the pipeline, and a breached control band in production writes the next intent.md. The playbook adds that at first you prompt each step by hand, with the end state being a loop in which each accepted artifact fires the next gate.

Stage 3: Build — plan.md Approval, CLAUDE.md, and Skill Governance

The governing rule of Stage 3, Build, is that nothing is implemented without an accepted plan. Engineers start Claude Code sessions in plan mode, give Claude the approved spec.md from Stage 2, and let it interview them, iterating on the plan until the engineer is happy with it. In plan mode Claude can read the codebase without changing anything, and it cannot edit files until the engineer accepts the plan. The mechanism is discussed in our plan mode analysis. The approved plan is committed as plan.md, so that later stages can check against it.

# Plan: claims status self-service (from intent.md 2026-06-02)
                    
                    ## Files that change
                    portal/src/claims/StatusPanel.tsx (new), claims-api/routes/status.py,
                    claims-api/tests/test_status.py
                    
                    ## Order of work
                    1. Add the status endpoint behind existing auth.
                    2. Panel against the endpoint.
                    3. Wire into the portal nav.
                    
                    ## Risks
                    The claims-core API rate-limits at 50 rps; the panel must cache.
                    
                    ## Proof
                    test_status.py covers the four claim states; screenshot matches the
                    approved mock.

Two points in the playbook's steps deserve attention. The engineer interrogates the plan by asking what the change could break, which step is most risky, and what other options Claude chose not to do, and iterates until an engineer who has never seen the conversation could implement the change from the plan alone. When the implementation departs from the plan, plan.md is updated in the same commit, and the playbook suggests considering a hook to enforce synchronization between the two.

Institutional knowledge goes into CLAUDE.md at the repository root. The playbook describes it as giving Claude the context a new joiner would need: conventions, commands, architecture, and the mistakes the team sees most often. The steps are to run /init to generate a starting file, cut it down to what a new joiner would need on day one, check it into git so that changes are reviewed like code, and follow the working rule that when Claude makes a mistake twice, the correction goes into CLAUDE.md. Because Claude reads all of it at the start of a session, the file is kept under a page.

Skills are for institutional knowledge that must be applied consistently, and the playbook calls a skill an advisory control. A policy that must hold without exception needs something deterministic behind it, and a hook is that layer. Build-phase hooks block edits to protected paths such as generated classes or a frozen package, run the formatter and linter after file edits, and keep credentials out of the diff. Because a hook runs on each action that matches it, build-phase hooks should be fast and scoped to the file that changed, while heavier checks such as the full test suite belong at the commit or the PR. When one engineer drives several streams of work, a parallel session is another full Claude Code instance working a separate task in its own git worktree, whereas a subagent runs inside a single session as a scoped helper with its own context window and tool limits. The playbook says that two or three sessions is a sensible starting point, and that the practical ceiling is how many streams one person can review properly.

Stage 4: Test — Agent Self-Verification Feedback Loops and Continuous Evals

The principle of Stage 4, Test, is that every session checks its own work before a human sees it. The playbook says to always give Claude a way to verify its own work, whether tests, a build, or a screenshot diff. In the traditional model the signal that code works arrives late: CI minutes later, a tester days later, production weeks later. With an agent producing the code, a late signal means a person has to check all of its output, and that person becomes the bottleneck. If checking the work takes a sequence of commands and some environment knowledge, the playbook says to wrap it in a single target such as make test or npm test that exits non-zero on failure.

For bug fixes, the failing test is written first. Claude is asked to reproduce the bug as a test, the test is run to confirm it fails for the reason you expect, and that test is committed. Only then is Claude asked to make it pass without editing the test. Because an agent fixing code must not be able to weaken the check on that code, the playbook names a hook that blocks edits to test files during a fix task as the way to do this, and gives as the alternative checking the diff in review and rejecting any change that touches a test. For UI work, Claude is given a browser or screenshot tool and the mock, and it iterates through implement, screenshot, compare, and adjust; two or three rounds is normal. The CLAUDE.md verification block in the playbook is the following.

## Verifying your work
                    
                    - Build: make build (must finish with "Build succeeded")
                    - Test: make test (all green; never skip or delete a failing test)
                    - Lint: make lint (zero warnings)
                    
                    Run all three before reporting any task complete, and paste the output.
                    If a test fails, fix the code, not the test.

The playbook's governance notes for this loop are specific. What is enforced is verification before a task is reported done, and the block on the agent editing test files during a fix, both implemented as hooks where the organization wants them guaranteed. The evidence is the literal output of make test, the build log, or the screenshot diff that Claude ran and pasted, so the evidence comes from the toolchain. It is logged in the session transcript, which the OpenTelemetry export forwards to the observability stack, and in the PR's check run, and the code owner reviewing the PR can concentrate on intent and risk because the mechanical evidence is already attached.

Evals are the AI-native equivalent of stage-gate QA. In practice that means a suite that runs whenever the agent's configuration changes: when a new model is swapped in or a prompt is rewritten, the suite says whether the agent still does the work to the same standard. A platform engineer collects 20 to 50 real tasks from recent work with their expected or accepted outcomes, writes each one as a prompt plus the checks that define acceptable (tests pass, lint clean, behavior unchanged, policy followed), and runs the suite non-interactively in CI on a schedule and on any change to CLAUDE.md, skills, or hooks. Each production incident gets an eval and stays in the suite as a regression test. The playbook stresses that the evals are a live suite: as models improve, cases that once discriminated stop doing so, and new ones arising from ongoing monitoring must be added.

Stage 5: Deploy — Hook-Based Approval Gates and Environment Tiering

In Stage 5, Deploy, Claude both gives and receives reviews. It reviews incoming PRs against the organization's policies and addresses review comments on its own PRs. The tech lead writes the review policy as REVIEW.md at the repository root, divided into three passes: bugs and logical errors, security and vulnerabilities, and compliance against the spec (spec.md), the implementation plan (plan.md), and design principles. The file also defines what counts as Important as opposed to a Nit, and what to skip, and the playbook's example caps nits at five per review. Findings do not approve or block a PR on their own, and branch protection still requires approval from a code owner. Separation of duties is preserved because the agent that wrote the code has no way to approve it, and the PR history is the audit record.

Governance is enforced as the agent acts rather than in a review afterwards. The build phase used hooks as guardrails that allow or block actions with no human involved; a hook can also ask, pausing the action until a specific person approves, which is what release gating needs. Team hooks go in .claude/settings.json in git, and non-negotiable hooks go in managed settings owned by the platform or IT admin, where individual engineers cannot switch them off. A block should explain itself, so the reason and the route to approval appear in Claude's output. The production gate in the playbook is the following script.

#!/bin/bash
                    # Production deploys require a named release authorization
                    cmd=$(jq -r '.tool_input.command' < /dev/stdin)
                    if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
                       if [ -z "$RELEASE_APPROVAL" ]; then
                         echo "Production deploys need a release authorization." >&2
                         exit 2 # exit 2 blocks the action; the message goes to Claude
                       fi
                    fi
                    exit 0

The script blocks with exit code 2 when the command contains both deploy and production and RELEASE_APPROVAL is empty; as its comment says, exit code 2 blocks the action and the message goes to Claude. The playbook's managed settings example is deployed by the platform team through MDM or the admin console, and engineers cannot edit or override any of it. Five of the settings that the example explains are the following.

  • permissions.deny: denies reads of .env and ./secrets, and WebFetch and curl and wget, which keeps secrets out of the agent's context.
  • allowedDomains in the sandbox: an OS-level domain allowlist blocks network egress, whereas a tool-level deny on WebFetch does not stop a shell command from reaching the network.
  • failIfUnavailable and allowUnsandboxedCommands: Claude Code refuses to start when the sandbox cannot initialize, and a command that fails inside the sandbox cannot be retried outside it.
  • Managed-only settings such as strictKnownMarketplaces: every skill, agent, hook, and MCP server arrives through the organization's approved plugin marketplace.
  • requiredMinimumVersion: Claude Code refuses to start on a version below the approved floor.

The playbook asks readers to consider this example a starting point to tailor, rather than a recommendation to copy. Every deny trades against capability, and the right balance depends on the data classification of the repository.

Stage 6: Maintain and Closing the Loop — Deterministic Alerts and intent.md Ingestion

In Stage 6, Maintain, the loop closes. The playbook summarizes it as a trigger invoking Claude with no person in the invocation path, with what Claude finds re-entering the pipeline as intent.md. In the traditional model maintenance is reactive: every ticket or incident waits on a person, and an alert that fires at 3 a.m. can be missed. A trigger such as a control-band breach, a ticket, a channel message, or a schedule invokes Claude without a person in the path, and people triage and review that work rather than having to start it.

The detection script watches one metric with a stable rolling baseline. The playbook's examples are the CI test failure rate, the post-deploy 5xx rate, and the PR cycle time. It computes the mean and standard deviation over a rolling window and applies rules such as Western Electric, so that the bands catch slow drift as well as spikes. The script is version controlled and unit tested, and detection stays entirely deterministic, with no model involved. The response tiers are defined in version-controlled config, shown below as bands.yaml: at 1 sigma the script only logs, at 2 sigma it invokes Claude read-only to diagnose, and at 3 sigma Claude may act, though only by opening a PR into the review gate or triggering a pre-approved runbook.

metric: ci_test_failure_rate
                    baseline: rolling_30d
                    rules: western_electric
                    tiers:
                      1sigma: { action: log }
                      2sigma: { action: diagnose,
                                tools: "Read,Grep,Bash(gh run view *)" }
                      3sigma: { action: propose,
                                routes: [pull_request, runbook:rollback-deploy] }

The agent writes its diagnosis as intent.md in the Stage 1 format, covering the anomaly and its evidence, a proposed outcome, the affected systems, and any open questions, and from there the finding goes through the pipeline like anything else. The playbook gives three examples. When the CI test failure rate breaches 3 sigma, the agent quarantines the flaky test or opens a revert PR, and the review gate decides. When the post-deploy 5xx rate breaches 3 sigma with a deployment in the window, the agent triggers the existing rollback pipeline. When PR cycle time trips a drift rule, the agent writes a report for engineering leadership.

The playbook also places recurring codebase scans and channel-based response in the same loop. Claude Security is the hosted form of scheduled scanning, available in public beta to Claude Enterprise organizations; scans run on Claude Mythos 5, and each finding is validated before it is reported and has a confidence rating attached. Claude Tag, currently in public beta in Slack, makes Claude a member of the incident channels under its own identity, so each new incident gets a first responder. What the playbook leaves to people in this stage is the following.

  • The service owner or on-call engineer triages the queue, deciding to fix now, schedule, or dismiss, and routes product-facing findings to the product owner.
  • Dismissals tune the bands and help to reduce noise.
  • At 3 sigma the agent's action is limited to a PR into the review gate or a pre-approved runbook.
  • When a fix ships, an eval for the incident is added so that such issues are protected against from then on.

The table below sets the six stages side by side: the committed artifact, the automation and verification that the playbook describes, and the limits and cautions that the playbook itself states.

In its CI/CD section the playbook tiers the autonomy of the agent by environment.

  • Development: the agent deploys freely.
  • Staging: it sits somewhere in the middle.
  • Production: the agent prepares the release, the release manager authorizes it, and a hook enforces the production gate.
  • Rollback: it should be the most rehearsed path in the pipeline, a single command that the agent can run and that is exercised regularly in staging.
  • Auditability: each non-interactive run acts under the agent's own identity, so the pipeline log separates what the agent did from what the engineer who triggered it did, and every hook decision is written to the OpenTelemetry export with a timestamp and an allow or block verdict.

The playbook's governing principle is that the agent may act up to the production gate and cannot pass it. Its closing thoughts point the same way: the loop keeps running, and human judgement stays above it.

Unconfirmed Details

  • Statistical data demonstrating measured reductions in delivery lead times or defect rates after adopting the AI-native SDLC; the playbook describes only qualitative mechanisms and how to collect indicators.
  • The detailed algorithm for resolving conflicts when Jira, ServiceNow, or other existing systems are synchronized in both directions with the markdown artifacts in git; the playbook only describes how to decide which side is the source of truth.
  • The measured vulnerability detection accuracy and false positive rate of the Mythos 5 model that Claude Security uses.
  • Strategies for mitigating Git merge collisions when dozens of parallel agent sessions update plan.md at once in a large monorepo.
  • Whether skills and hooks remain compatible when the same pipeline is built on third-party models outside Anthropic.
