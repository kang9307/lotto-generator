How Do You Grade a Long-Running Agent - What It Really Means to Write Behavior Down as a Spec

Where outcome grading breaks, what makes a sentence observable, and who you put in the grader seat

Sep 1, 2026 Dev & Infra

Say an agent made twenty tool calls, produced an answer, and the answer was right. That fact carries less information than it appears to. Which of the twenty calls checked a source and which skipped the check, what the agent did after the one step it got wrong, whether it happened to land on the right answer through a path nobody would approve of — none of that survives into the final sentence. Neither does any guarantee that the next run gets there the same way. A correct outcome and a trustworthy process are different objects, and outcome grading is nearly silent about the second one.

That silence is why teams keep trying to move the center of gravity of evaluation from the result to the process. Agent Behavior, published in the summer of 2026, is one of the more blunt attempts. You write down the conduct an agent should show repeatedly over the course of a task, in a single Markdown file, and then you use that file as the grading criterion. It is not a prompt, it is an evaluation baseline. That distinction is the entire format, and it is what this article is here to examine.

This is a technical review of a published format and its specification documents, not an assessment of any product, service, or company. The figures quoted come from the repository's public metadata as of 1 September 2026. The format is early, so details may change after this is written.

The occasion - a format called a behavior spec

The braintrustdata/agentbehavior repository, published by Braintrust Data, describes itself as standards for defining and evaluating agent behavior. The license is Apache-2.0, and the specification document uses RFC 2119 keywords like MUST, SHOULD and MAY. There is a separate documentation site, a skill document for authoring specs, and three runnable example projects alongside the format itself.

It is worth being precise about scale. The repository was created on 8 June 2026. It has 15 commits, and the last push was on 29 July. There are 322 stars, 9 forks, and no open issues. Four example behavior specs ship with it. That is an early-stage project roughly three months into public life, which is also why the word standard gets its own section further down.

The format itself is small. One Markdown file with two lines of YAML frontmatter is the whole requirement. That smallness is not incidental — it is the format's only real chance. Process evaluation bills its adoption cost directly in human hours, so if the file format is heavy, the effort dies before it starts.

Where outcome-only grading breaks

Grading the final artifact works well when four things hold at once: there is one right answer, the run is short, a wrong result can be undone, and the artifact reflects the process that produced it. The places where agents actually get deployed are mostly places where two or more of those have already broken.

What breaksWhat the final artifact hidesHow it shows up in practice
There is more than one right answerWhich answer gets accepted depends on who is gradingThe same trace passes with one reviewer and fails with another
Irreversible side effects happen mid-runA lucky run and a disciplined run score identicallyNobody learns the path was dangerous until an incident happens on it
The run is longHundreds of decisions collapse into one numberA regression appears and nobody can name the step it came from
Failures are rareThe failing path never lands in the eval samplePass rates look healthy and production is where it breaks

The common reflex at this point is to go edit the prompt. But editing the prompt leaves you with no instrument for confirming what the edit fixed. The outcome score never carried that information, and the causal link between one prompt line and a score movement is mostly an artifact of small samples. How far to delegate in the first place is a separate axis, covered over in agent autonomy levels; this piece deals only with the judgment problem that remains after the delegation scope is settled.

  • Outcome grading is retrospective by construction. On work with irreversible side effects, the verdict arrives after the damage
  • On long runs, a single score is too high a compression ratio. You cannot reconstruct a cause from a compressed value
  • Where several answers are acceptable, the grading criterion itself stays tacit. Change the person and you change the standard
  • So the motive for moving to process evaluation is not taste. It comes from questions outcome grading physically cannot answer

What the file actually looks like

The layout is plain. Under .agents/behaviors/ at the repository root you create a directory named after the behavior, and put a BEHAVIOR.md inside it. Background material, if you need any, goes in a references/ directory beside it.

.agents/
└── behaviors/
    └── primary-source-tax-research/
        ├── BEHAVIOR.md      # required. the filename must be spelled this way
        └── references/      # optional. rationale, examples, background

What the specification actually mandates is two frontmatter fields. name is capped at 64 characters, allows lowercase letters, digits and hyphens, must not begin or end with a hyphen, and must match the parent directory name. description is capped at 1024 characters and must not be empty. license and metadata are optional, and clients must ignore fields they do not recognize. Tooling should scan .agents/behaviors/, and must look for that exact filename, though it may also accept case variants.

---
name: primary-source-tax-research   # lowercase, digits, hyphens; max 64; matches dir
description: ...                    # max 1024 characters; must not be empty
---

# What this spec governs

## One behavior, stated in one sentence

What must be observable once the trigger fires.
What specifically does not satisfy this behavior.

Each ___ is one occurrence.

**Why:** the reason this conduct is required.

The body is free-form, and here is the part second-hand summaries routinely drop. The six labels everyone quotes — intent, evidence to check, decision, execution, recovery, failure modes — are not a structure the specification requires. The repository states outright that those six are optional and that plain Markdown works too, and the four shipped examples are genuinely not shaped alike. The financial work verification example uses the six labels. The tax research example does not.

The one that does not is the more instructive of the two. It puts a single behavior in the heading, states in the same paragraph what does not satisfy that behavior, nails down the counting unit with a line reading that each tax research process is one occurrence, and closes with one line on why the conduct is required. Those four pieces are the minimum that makes grading possible at all. Labels come after that. What changes when a document is written for tooling rather than for people is covered in agent-facing documentation.

What it takes to not be a prompt

Every new document format meets the same first question: why not just put this in the prompt. This format answers that itself, and the answer is the core of it.

ArtifactWhat it doesAudienceWhen it changes
Behavior specDefines what counts as good behaviorReviewers, eval authors, agents reviewing tracesWhen the behavioral standard changes
System prompt · AGENTS.mdTells the agent how to actThe agent at runtimeWhen the implementation changes
EvalsTest whether the behavior actually occurredEval designersWhen what is measured changes

The last column is the real dividing line. Prompts move often, tracking implementation; behavioral standards move far more slowly. Merge the two documents and your judgment criterion shifts every time you touch the implementation. That is exactly how you end up with a trace that failed yesterday and passes today while the agent has not changed at all.

The worse case is a spec that becomes a copy of the prompt. Then grading is a loop that checks whether the prompt did what the prompt said, using the prompt. Pass rates go up and nothing is verified. Why piling on more rules stops working as a control mechanism is laid out in the limits of long policy documents. If a behavior spec gets past that limit, it does so not because it has more sentences but because its verdict demands evidence from outside the sentences.

  • Writing the same content in two documents produces drift. Keep prompt and spec in a reference relationship rather than a duplicated one
  • Put tool names and function signatures in a spec and it becomes a prompt at that moment, because it now changes when the implementation does
  • Make it too abstract in the other direction and it becomes ungradable. The corridor between those two walls is narrow, and that narrowness is the format's real difficulty
  • One working rule — if the reason a sentence changes is a code change, it belongs in the prompt; if the reason is a policy change, it belongs in the spec

The requirement that a sentence be observable

Exercise careful judgment. Verify when necessary. Respond appropriately. These sentences work in guidance written for people and are worth exactly zero as grading criteria. The problem is not that they are vague; it is that they never say when they apply. With no point of application there is no way to count occurrences, and with no count there is no pass rate.

The format's own documents push this back into an instrumentation problem. If the trace cannot expose a behavior that matters, the guidance says to improve the behavior's observability or the trace instrumentation. In other words, the spec cannot stand up until the logging does. Teams that write specs first and instrument later fail in exactly this order.

Three checks are enough for any sentence you write.

  • Can you say in one line when it applies? When answering a tax question qualifies. In important situations does not
  • Is there an event in the trace that separates satisfied from not satisfied? It has to be something recorded — a tool call, a file open, an ordering of outputs
  • Would two people reading the same trace return the same verdict? If they split, the sentence is wrong, not the people
  • One habit is worth adding on top: write the non-satisfying condition too. That is why the shipped example spells out that reading the skill after the first search does not satisfy the behavior
  • Do not leave only negatives, though. A spec made entirely of prohibitions passes a trace in which the agent did nothing at all

Triggers and occurrences - counting the unit of judgment

Grading splits into two stages. First you determine whether the behavior's trigger actually fired inside the trace. If it never fired, that trace is outside the scope of this spec, which is not a failure. If it did fire, you then look for the required conduct: visible means positive, absent or contradicted means negative.

When a trigger fires several times in one run, each firing is a separate unit of judgment. Each is judged on its own and then folded, and the usual fold marks the whole section false if any single occurrence fails. The point is to stop five good occurrences from burying the sixth. That is why the shipped example pins the counting unit down with a sentence saying each tax research process is one occurrence.

There is a clause here that is easy to miss. Missing evidence does not automatically mean out of scope. If the trigger fired and the required evidence is absent from a channel that is recorded exhaustively, that is usually a negative. This matters because it means instrumentation quality becomes the grade. In a team that logs only part of the run, the same spec produces different numbers.

  • Four conditions make a sentence gradable — the trigger is unambiguous, the required conduct is visible in the trace, the evidence boundary is clear, and the verdict does not lean on dataset labels
  • That last one is subtle. Judging by looking at the answer key is outcome grading wearing process grading's clothes, and it is the most common way this goes wrong
  • Pass rate is not the only number to watch in operation. Watch the out-of-scope rate alongside it. If a trigger never fires, the pass rate looks perfect
  • A persistently high out-of-scope rate means one of two things: the spec has drifted away from the real work, or the eval set never creates the situation

Who sits in the grader seat

However well the spec is written, if nobody has decided who renders the verdict, the document is a poster on a wall. There are three options, and they differ in cost and in which direction they misjudge.

When a human reads it

Minutes to tens of minutes per trace. Accuracy is high only early on. Somewhere past the twentieth trace the standard loosens, and the instincts formed in the first few cases quietly govern all the rest. So humans belong where they are irreplaceable: calibrating the standard at the beginning, and deciding cases where verdicts split.

When a model reads it

The only option that scales to every run. In exchange, its errors skew one way. Vague wording makes it generous, and it will mistake recitation for conduct when the agent parrots the spec's own phrasing back into the trace. To separate saying I checked the primary source from actually opening it, the spec has to point at an event rather than at words.

When a log rule reads it

Cheapest and steadiest. Call ordering, whether a specific tool was invoked, whether a field is present — anything decidable from text is better settled by a deterministic check. The limit is just as clear. It cannot distinguish having called a tool from having used its result. It is the most vulnerable of the three to conduct that satisfies the form and evades the point.

GraderWhat it costsWhich way it misjudgesWhere it belongs
HumanMinutes to tens of minutes per trace. Does not scaleLoosens over time. The first samples fix the standardCalibrating the spec, settling disputes, sampled audits
ModelPer-call cost, rising with trace lengthGenerous. Accepts a declaration as conductGrading every run, watching for regressions
Log ruleUpfront instrumentation cost, then near zeroStrict. Drops legitimate paths that took an unexpected shapeAnything decidable from text, like ordering or call presence

In practice the answer is not a choice but an arrangement. Push whatever is decidable from text down into log rules, hand the judgment calls to a model, and escalate to a person only the cases where model verdicts split or a result later flipped. And the moment a model holds the grader seat, that grader itself becomes something to verify. The repository's example attaching a test file to its judge code is a design that concedes exactly this. The problem that a broken grader raises no alarm is covered in verifying the tools that verify.

How fast a spec goes stale

Behavior specs are designed to change more slowly than prompts. Slowly is not the same as durably. There are places where the sentence stays identical and its meaning moves, and most of them arrive with a model swap.

  • The word first stops being decidable. A model that issues tool calls in parallel does not leave a linear ordering in the trace. The same spec suddenly raises its failure rate
  • Things that were observable disappear. When intermediate reasoning is summarized or hidden, the justification that only ever appeared there vanishes from the trace. The conduct is unchanged; the verdict flips to negative for want of evidence
  • Explicit steps stop being necessary. Conduct a newer model performs implicitly may not surface as a distinct event. It got better and the score went down
  • A renamed tool passes a log rule in silence. Deterministic checks sometimes cannot tell a satisfied condition from a target that no longer exists
  • The trace format itself changes. Swap the observability stack and every verdict needs recalibration even though nobody touched the spec

The response is not to pin a model name into the spec. Do that and the spec becomes a prompt and the last column of the table collapses. Instead, keep a pass-rate history per spec and treat a sharp move with no agent change as an alarm. Deciding whether the move came from behavior or from observability is the next job, and a team that cannot make that distinction ends up with a document nobody trusts within six months.

Competing with the artifacts you already have

It is worth being blunt about what this format replaces. Almost nothing. You gain a document and you gain a grading cost. What migrates into it are the questions your existing artifacts were never good at answering.

Existing artifactThe question it answeredWhat migrates hereWhat does not
Unit and integration testsDoes this code return this value for this inputNothingAll of it. The code around the agent still needs tests
Eval setsIs the final answer right for this inputThe items the final answer cannot separateGrading items with an unambiguous answer. Still cheaper there
RunbooksWhat does a person do in this situationCondition-and-conduct pairs that recurOne-off procedures, tool usage, access details
Review checklistsIs this change safe to shipThe tacit criteria that varied by reviewerThe approve-or-not verdict on a change
System promptsWhat should the agent be made to doNothingRuntime instruction stays in the prompt

The most honest cells in that table are the two that read nothing. This format does not reduce your test suite and does not reduce your prompt. The role agents play inside a test stack is its own subject, handled in agentic testing, and the two point in opposite directions. There the agent is doing the inspecting. Here the agent is the thing being inspected.

What the tooling checks and what it does not

The repository ships a CLI package with three commands: validate for structural checks, list to enumerate discovered specs, and explain to unfold one of them. The scope is stated plainly in the docs — file discovery, YAML frontmatter parsing, the name and description constraints, and the shape of metadata. The body is treated as free-form content and is not validated.

That honesty is a good signal. A tool claiming to statically check whether Markdown prose is gradable would be far more suspicious. It is also, though, a reliable source of misunderstanding in adopting teams. Passing validation means the file parses, and says precisely nothing about whether you can grade a trace with it. Quality judgment is explicitly left to a human or a model.

  • Specs that pass the linter and specs that are gradable are two sets that overlap only by accident. Do not use validation as a quality gate
  • The real gate is one question. Do two people return the same verdict on the same trace? That does not automate
  • Which is why most of the early adoption cost is not tool installation but the hours people spend reading sample traces

What the word standard means here right now

Write-ups of this format mostly reach for the word standard. It is worth splitting, sentence by sentence, what that word currently points at.

  • Established fact — the repository and the documentation site call the format a standard. The specification uses MUST, SHOULD and MAY. The license is Apache-2.0. Discovery rules and field constraints that clients are expected to honor are written down
  • Established fact — it has not been through a standards body. The repository was created on 8 June 2026, has 15 commits, was last pushed on 29 July, and shows 322 stars and 9 forks. Four example behavior specs ship with it
  • Proposal, not requirement — the six-label arrangement, the convention of splitting verdicts into positive, negative and out of scope, and the way per-occurrence verdicts are folded. The specification does not mandate these; the guidance documents recommend them
  • Not yet evidenced — outside organizations adopting the format. Stars and forks are a measure of attention, not of use

So the accurate name for this right now is an early proposed format published by one company. That is a position, not a flaw. Useful ideas usually start here, and because the file format is Markdown it is not bound to any particular stack. But if you are arguing for adoption internally, the sentence we follow the standard cannot carry weight yet. The sentence that can carry weight is we checked, across twenty traces, that our runs are gradable against this format.

The adoption call - who it pays for and who it does not

Process evaluation is not free. You have to retain traces, write specs, wire up a grader, and manage the specs as they age. The conditions under which that cost comes back are narrower than the enthusiasm suggests.

  • Irreversible side effects exist. Payments, deploys, ticket closures, outbound messages — work where a retrospective verdict arrives too late
  • Several answers are acceptable. Research, classification, prioritization, anything where more than one output is defensible
  • Runs are long. Dozens of tool calls per run, where the final artifact cannot show you the cause of anything
  • You already retain traces. Without this, the value of a spec is exactly zero. There is nothing to grade against
  • There is more than one reviewer. The state where standards vary by person and the same trace gets different verdicts
  • Regulatory or audit pressure exists. Domains where you must retroactively show not just the answer but where the basis for it came from

The cases where it is overkill are just as clear.

  • If the agent finishes in one or two steps and you can eyeball the artifact, outcome grading is still cheaper and more accurate
  • If there is no trace instrumentation, the order is wrong. Log first, spec second
  • If you are still rewriting the prompt weekly, there is no behavioral standard yet. Pinning down something that does not exist only slows the exploration
  • At the scale of one person building and reviewing alone, the main benefit of a spec — verdict agreement — never materializes
  • Write ten specs without wiring a grader and what you have is ten documents nobody reads

If you do start, the minimum viable shape is this: one spec, twenty traces, human grading. When verdicts disagree, fix the spec's wording before you touch the agent. Reverse that order and the spec's defects get recorded as the agent's defects, and those records are hard to unwind later.

Summing up

Outcome grading works well only when there is one right answer, the run is short, and mistakes are reversible. Most places agents actually get deployed sit outside those conditions, which is what pushes the center of gravity of judgment toward the process. A behavior spec is that shift expressed as a single file. Where a prompt says what to do, a spec says what must be observable.

The format itself is small and honest. Two required fields, and tooling that says out loud it only checks structure. The hard parts all sit outside the format: writing sentences that are observable, fixing the unit that occurrences are counted in, arranging graders and then verifying the grader, and catching the places where the same sentence means something different after a model swap. None of those four are solved by the file format.

So the precise thing to say about this right now is modest. A new standard has not arrived; a filename has arrived for something many teams were already improvising. Whether that name is useful takes about twenty traces to find out, and until somebody reads those twenty traces, nobody knows.

What I Could Not Verify

  • Adoption by organizations other than the publisher could not be confirmed. 322 stars and 9 forks measure attention, not use. I found no public record of a team running this format in a real pipeline
  • Whether the CLI package is published to a registry, and at what install volume, was not checked. The package name and commands are in the repository docs, but distribution statistics are outside what this article verified
  • I did not run the example evaluation code. The description of triggers, occurrences and verdicts here follows what the repository's specification and guidance documents state
  • Whether other agent runtimes actually read this format could not be confirmed. The repository includes guidance for client implementers, but no external tool implementing it was identified
  • There is no comparative data on whether specs using the six labels grade more consistently than free-form ones. That is why this article does not recommend the labels
  • The cost and misjudgment characteristics attributed to each grader here are a synthesis of general evaluation practice, not measurements taken against this format
