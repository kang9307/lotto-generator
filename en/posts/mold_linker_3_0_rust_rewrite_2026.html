Background and Motivation — Complete Rewrite from C++ to Rust and the Default-Linker Goal for Linux Distributions

mold 3.0.0, released on October 5, 2026, is the first Rust version of the high-speed linker mold. The release notes say that, as announced in the 2.42.1 release notes, mold was rewritten from C++ to Rust, and that 2.42.1 is the last release of the C++ version. The 2.42.1 notes, which were published on September 11, 2026, give the reasoning behind the rewrite: by 2026 Rust has become a practical choice for systems software, and it offers strong safety guarantees such as memory safety. The same notes state that the goal is for mold 3.0 to keep working just as before from a user's point of view, with only the implementation under the hood changed.

The goal the 3.0.0 notes give for the mold 3.x series is to close the remaining compatibility gaps with GNU ld, particularly in linker script support, and to pave the way for mold to be adopted as the default linker in Linux distributions. The 2.42.1 notes spell this out in more detail. On most Linux distributions the system linker, /usr/bin/ld, is still GNU ld, so the plan is first to implement the missing linker script features so that mold can link kernels and firmware as well as user-space programs, and then to carry out extensive compatibility testing and work with distribution developers to make adoption practical.

The README states speed figures separately. In its August 2026 benchmarks, mold linked 4.9x faster than LLVM lld and 1.9x faster than wild at the median, and the full result tables are in the README's Benchmark section. These figures come from the README, not from the 3.0.0 release notes, so they should not be read as a comparison between 3.0.0 and 2.42.1.

Arranged around the wording of the notes, the aims this release states are as follows.

  • Drop-in replacement: the same command-line options and the same target architectures are supported, and the output is the same apart from the bug fixes listed in the notes.
  • Closing the gap with GNU ld: the 3.x goal is to close the remaining compatibility differences, linker script support in particular.
  • A basis for default-linker adoption: the notes name paving the way for adoption as the default linker in Linux distributions as a goal.
  • Safety on corrupted input: out-of-bounds reads now pass through bounds checks and stop with a panic.
  • A different way to build from source: CMake is replaced by Cargo, and Rust 1.95 or later is required.

What Remains Unchanged — Drop-In Replacement for v2.42.1, Equivalent Link Performance, and Verification

The first questions users ask about a language rewrite are whether the options changed and whether it got slower. In the notes' own words, mold 3.0 is meant to be a drop-in replacement for 2.42.1: it accepts the same command-line options, supports the same target architectures, and produces the same output except for the bug fixes listed in the notes. On link performance, the notes say it remains on par with 2.42.1. The notes contain no figures for link time or memory use, so on par has to be taken as the authors' statement rather than as a measurement that can be reproduced from the notes alone. The notes pair that statement with the verification described below.

The README lists the supported architectures as x86-64, i386, ARM 32/64, RISC-V 32/64, PowerPC 32/64, s390x, LoongArch 32/64, SPARC64, m68k, and SH-4. The fix list in the notes carries separate per-architecture entries for AArch64, ARM32, RISC-V, LoongArch, PPC32, PPC64, SH4, SPARC64, and m68k among them.

The notes give the following as the compatibility checks, and the last item marks the scope in which the compatibility applies.

  • Test suite on every supported target: the test suite was run on each supported target.
  • Output compared across real-world workloads and option combinations: linker output was compared across a broad range of real-world workloads and option combinations.
  • All Gentoo packages built: every Gentoo package was built, and the notes say they found no regressions (We found no regressions).
  • The scope is the linker's options, architectures, and output: in the same release the build system moved from CMake to Cargo and the test runner from ctest to cargo test. Scripts and CI configuration that build mold from source cannot be reused unchanged and have to follow the changes described in the build section below.

Evolution of the Safety Model — From Segmentation Faults to Panics

The one thing the notes say about safety concerns corrupted input files. Given such input, the C++ version could read memory out of bounds and crash with a segmentation fault. In 3.0, written in Rust, those reads are bounds-checked, so mold stops with a panic at the faulty access.

What changes is the way mold stops. According to the notes, the place where a corrupted input used to end in a segfault now ends in a panic, and nowhere do they say that mold repairs the damage so that the link succeeds. With ordinary input the change is invisible, because the output of 3.0 is the same as that of 2.42.1 apart from the listed bug fixes.

The bug fix list in the same notes also has separate entries that turn broken output or a crash into an error for certain invalid inputs and option combinations. Those are fixes independent of the bounds checks, and the concrete items are gathered in the output correctness section below.

Within the scope of what the notes say, the safety points can be summarized as follows.

  • Scope: the statement is limited to the handling of corrupted input files.
  • Earlier behavior: the C++ version could read memory out of bounds and crash with a segmentation fault.
  • Behavior in 3.0: those reads are bounds-checked, and mold stops with a panic at the faulty access.
  • What the notes do not say: the format of the panic message, the extent of the code that carries bounds checks, and any performance cost of the checks are not described. The only statement is that performance is on par with 2.42.1.

Build and Packaging Changes — Cargo Adoption and the Rust 1.95+ Requirement

For anyone who builds mold from source or packages it for a distribution, the biggest change is the build system. The notes say mold is now built with Cargo instead of CMake and requires Rust 1.95 or later and a C compiler; their instruction is to run cargo build --release to build mold and ./install-mold.sh to install it. The CMake options have all been removed. The README adds that Git is needed, and that if the system's Rust is older, the stable toolchain should be installed with rustup.

Compiling

The README gives the following compile procedure. The executable and its companion preload library end up at target/release/mold and target/release/mold-wrapper.so respectively.

git clone https://github.com/rui314/mold.git
                    cd mold
                    cargo build --release

Installing, and MOLD_LIBDIR

The README says that running sudo ./install-mold.sh installs mold under /usr/local, and that PREFIX should be set to install under a different prefix. The notes say the install script accepts PREFIX and DESTDIR. mold-wrapper.so is installed to $PREFIX/lib/mold, and target/release/mold can also be run directly without installing.

sudo ./install-mold.sh
                    sudo PREFIX=/usr ./install-mold.sh

If the libraries go into a directory other than $PREFIX/lib, such as /usr/lib64, both the notes and the README say to set the MOLD_LIBDIR environment variable to that directory. It has to be set both for cargo build and for the install with install-mold.sh, so that mold -run can find mold-wrapper.so. As the README describes it, mold -run runs a command with LD_PRELOAD pointing at the companion shared object, which intercepts exec-family calls and replaces ld, ld.bfd, ld.gold, or ld.lld with mold, which is why the location of this file matters. A wrong or missing MOLD_LIBDIR therefore shows up not while compiling but when mold -run is used.

The remaining changes to the build and test tooling are these.

  • Running tests: the test suite runs with cargo test instead of ctest.
  • Test dependency script: install-build-deps.sh was replaced by install-test-deps.sh, which is needed only to run the tests.
  • Target selection: the MOLD_TARGETS CMake variable was replaced by Cargo features. The notes say that, as before, distributions should build mold for all targets.
  • CMake options removed: every option that used to be passed to CMake is gone, so the part of an existing packaging script that passes them has to be rewritten.

Dependency Changes — oneTBB Removed, mimalloc 3.5.3 and Compression Libraries

The notes say mold no longer depends on oneTBB, the threading library the C++ version used for parallelism. What replaced oneTBB as the parallel-processing implementation is not described in the notes. The configuration of the remaining dependencies is spelled out item by item: mold statically links mimalloc, links the system's zlib if available, and includes zstd and BLAKE3.

  • mimalloc 3.5.3, statically linked: as before, mimalloc 3.5.3 is statically linked.
  • Choosing the system allocator: building with --features system-allocator uses the system's malloc.
  • System zlib: if the system has zlib, mold links it.
  • zstd and BLAKE3 included: both libraries are included in mold.
  • Linking the system zstd: setting ZSTD_SYS_USE_PKG_CONFIG=1 links the system's zstd.

Output Correctness and GNU ld / lld Compatibility Fixes

The Bug Fixes and Compatibility Improvements section of the 3.0.0 notes is long. It combines items that align mold with the behavior of GNU ld and lld, such as common symbol handling, version script precedence, and option parsing, with per-architecture fixes. The representative items on options and symbol handling are collected in the table below. Each entry in the notes ends with the commit hashes of its fixes, and some also link issue numbers (1656, 1657, 1668, and 1671), so every item can be traced back to its change in the repository.

Item What the 3.0.0 notes say Option or context
Common symbols of the same name Common symbols of the same name with different sizes get the largest size and the strictest alignment, as in GNU ld and lld. Symbol resolution
Output file that is also an input file The crash or corrupted output when running something like mold -r -o foo.o foo.o bar.o was fixed. -r (partial link)
Section garbage collection The functions given by --init and --fini are no longer removed. --gc-sections
Identical code folding Functions exported from a shared library are no longer folded. A crash when --icf=all is used with --emit-relocs was also fixed. --icf=safe, --icf=all
Version script precedence When a symbol is listed in more than one version node, the first node takes precedence, as in GNU ld and lld. Version scripts
Single-dash option parsing Options are read as GNU ld reads them. For example, -entry=main, which had been read as -e ntry=main, is fixed. Command line
Address space reserved at startup mold no longer reserves 8 GiB of virtual address space at startup, so it works under ulimit -v. Process startup
Nondeterministic output Several cases were fixed. The notes name --dependency-file, --repro, -r with many COMDAT groups of the same name, and some dynamic relocations. Output reproducibility

The nondeterminism entry says that several cases of nondeterministic output were fixed. The notes contain no guarantee that output is identical byte for byte under every condition, and they do not say how the cases were found or how many remain. Note also that -r is a partial link, not an incremental link; what the notes fix is a crash and corrupted output when -r is used.

Some items sit outside the table. GOT-relative relocations against symbols defined in shared libraries (R_X86_64_GOTOFF64, R_ARM_REL32) used to get wrong addresses silently, and 3.0 either handles them correctly or reports an error. Cases such as --defsym aliasing a symbol defined in a shared library, a --defsym value that does not fit in 64 bits, an allocated section that is also compressed, and --strip-all combined with --emit-relocs now produce an error instead of a broken output or a crash. For partial links, C++ exceptions that broke in code from the second and later input files and --gc-sections dropping data that relocations referred to were also fixed. On AArch64, PPC32, and ARM32, calls through range extension thunks that jumped to wrong addresses in large programs such as the ARM64 debug build of Chromium were fixed.

The per-architecture entries are more specific. On AArch64, support for more relocation types such as R_AARCH64_TSTBR14 and R_AARCH64_GOT_LD_PREL19 was added, and on ARM32 support for R_ARM_ALU_PC_G0 and R_ARM_THM_PC12. On PPC32 and m68k, a GOT too large for the 16-bit offsets that -fpic code uses is now reported as an error instead of being silently truncated. Besides these, files created by --separate-debug-file no longer contain a .gnu_debuglink section, mold no longer creates the meaningless __start_EHDR family of symbols, and MOLD_JOBS now works if XDG_RUNTIME_DIR is an empty string.

mold 2.42.1 (C++) versus mold 3.0.0 (Rust) — Configuration Compared

The table compares the configuration of the two versions within what the 3.0.0 notes describe. Where the notes say nothing, the cell says that there is no description.

Item mold 2.42.1 (last C++ release) mold 3.0.0 (first Rust release)
Implementation language C++ Rust
Build system CMake Cargo (CMake options removed)
Source build requirements Not described in the 3.0.0 notes Rust 1.95 or later and a C compiler
oneTBB dependency Depends on it No longer depends on it
Memory allocator mimalloc, statically linked (the notes say as before) mimalloc 3.5.3, statically linked; --features system-allocator selects the system malloc
Running tests ctest, install-build-deps.sh cargo test, install-test-deps.sh
Corrupted input files Out-of-bounds reads and a segmentation fault crash A panic at the faulty access caught by bounds checks
Virtual address space at startup 8 GiB reserved Not reserved, so it works under ulimit -v

In short, a team that only passes options to the linker can expect the same behavior and output as before, apart from the listed fixes, while a team that builds mold itself has to redo its build, install, and test steps. The linker's options and output carry over, while the source build procedure and the internal configuration changed. The 2.42.1 cells in this table are read backwards from the change descriptions in the 3.0.0 notes, so the wording may differ from the 2.42.1 documentation itself.

Unverified Aspects

  • The 3.0.0 release notes contain no link-time or memory-use figures, only the statement that performance is on par with 2.42.1. The README's 4.9x and 1.9x figures compare linkers built from source as of 2026-08-28, and which mold version was measured cannot be confirmed from the README. For that reason the figures say nothing about how 3.0.0 compares with 2.42.1.
  • The overall size of the Rust codebase and its module layout are not described in the notes or the README, so nothing here supports a claim about how large the rewrite was.
  • The Rust edition used for the rewrite is not stated; the only toolchain requirement given is Rust 1.95 or later.
  • Which linker script features are still missing is not listed in the notes, which state only the goal of closing the remaining gaps. The 2.42.1 notes say the missing features have to be implemented first, but they do not enumerate them either.
  • The schedule for Linux distributions to adopt mold as their default linker, and how any discussion stands, are not described, and nothing in the notes should be read as a commitment from any distribution.
  • No comparison results have been published on how much the output differs from 2.42.1 when a real project is linked with 3.0.0. The notes say only that it is the same apart from the bug fixes, so the size of any difference in a given build is something to measure on that build.
