CLIの認証を正しく設計する方法 — コマンドラインツールの安全な認証設計

OAuthデバイスフロー・PKCE・トークン保存・APIキー管理・リフレッシュ戦略・セキュリティの落とし穴 — CLIを作る人・使う人のための実践ガイド

2026-06-22 開発・インフラ

なぜCLI認証は独自のアプローチが必要なのか

Webアプリの認証とCLI認証はOAuth仕様を共有しているが、実行コンテキストがまったく異なる。Webアプリにはブラウザ・クッキー・セッションストレージがある。CLIにはターミナルしかない。この一つの違いが認証設計全体を書き換える。2026年6月時点で、Claude Code・GitHub CLI・AWS CLI・Stripe CLIのようなツールが数百万の開発者のローカルマシンにインストールされており、それぞれが独自の方法でクレデンシャルを扱っている。

GitGuardianの2026年レポートによると、2025年に公開GitHubコミットで約2,865万件のハードコードされたクレデンシャルが発見され、AIサービスキーの漏洩は前年比81%増加した。その相当部分はCLIツールを作成または使用する開発者の不注意に起因している。CLI特有の認証フローを正しく理解することで、こうした問題の大半を設計段階で防ぐことができる。

このガイドはCLIツールを作る開発者と使う開発者の両方を対象としている。私の核心的な主張は明確だ：正しい抽象化（PKCE・OSキーチェーン・トークンローテーション）を最初から選べば、利便性とセキュリティは両立する。

1. CLI認証の4つのパターン — 選択マップ

CLIがサービスに認証する方法は主に4つある。それぞれ適切なコンテキストが異なり、誤ったコンテキストで使用するとセキュリティ上の問題が生じる。

1.1 OAuth 2.0 Authorization Code + PKCE（ブラウザ委任）

CLIがローカルTCPポート（例：localhost:8484）を開き、そのポートをリダイレクトURIとして構成されたAuthorizationエンドポイントにブラウザを起動する。ユーザーがブラウザでログインすると、認証サーバーがローカルポートにcodeを返す。CLIはこのコードをアクセストークン・リフレッシュトークンと交換する。

ここでPKCE（Proof Key for Code Exchange、RFC 7636）が核心だ。CLIはパブリッククライアントであり、client_secretを安全に保管する方法がない。PKCEはこの問題を解決する：セッションごとに暗号学的乱数code_verifierを生成し、そのSHA-256ハッシュをcode_challengeとしてサーバーに送る。コード交換時に元のverifierを提出して同一セッションであることを証明する。傍受されたコードだけではトークンを発行できない。

GitHub CLIのgh auth loginがこの方式を採用している。速く、ポーリングなし、フィッシング耐性が高い。

1.2 OAuth 2.0 Device Authorization Grant — RFC 8628（ヘッドレス委任）

SSHリモートセッション・コンテナ・TV/組み込み機器など、ブラウザを開けない環境向けの標準だ。CLIがデバイスコードを要求すると、サーバーはdevice_code（内部識別子）・user_code（短い人間可読コード）・verification_uriを返す。CLIは「任意のデバイスのブラウザでこのURLにアクセスしてこのコードを入力してください」というメッセージを表示し、バックグラウンドで指定間隔でポーリングしながら認証完了を待つ。Claude Codeがこの方式を採用している。

1.3 APIキー（自動化・サービスアカウント）

CI/CDパイプライン・cronジョブ・サービスアカウントなど、インタラクティブなログインが構造的に不可能な環境に適している。シンプルでどこでも使えるが、有効期限なしで発行すると漏洩時の被害期間が無制限になる。ローカル開発ではOAuthフローの方が安全だ。アクセストークンは通常1時間で失効するが、APIキーは明示的に廃棄するまで有効だ。

1.4 ワークロードアイデンティティ（クラウド環境）

AWS IMDSv2・GCP Workload Identity Federation・Azure Managed Identityのように、クラウドインフラがマシン自体に短命トークンを付与する方式だ。GitHub ActionsのOIDCトークン+AWS assume-roleの組み合わせが2026年時点で最も推奨されるCI/CDパターンだ。長期シークレットをリポジトリに保存する必要がなくなる。

2. PKCE実装 — コードレベルで見落とされがちな点

PKCEを「code_challengeを追加すればいい」と思うと見落とす落とし穴がある。

2.1 code_verifierの正しい生成方法

RFC 7636は暗号学的に安全な乱数で43〜128文字のURLセーフな文字列を規定する。Pythonではsecrets.token_urlsafe(96)、Node.jsではcrypto.randomBytes(96).toString('base64url')が正しい方法だ。Math.random()やUUIDは暗号学的に安全な乱数ではない。セッションごとに新たに生成し、再利用は禁止だ。

2.2 S256方式のみ使用すること

code_challenge_method=plainはverifierをそのままchallengeとして送るため、CLIと認証サーバー間のMITM攻撃に脆弱だ。必ずS256（SHA-256ハッシュ後base64urlエンコード）を使用する。OAuth 2.1ドラフトはS256を強制し、plainを廃止する方向だ。認証サーバーがplainのみをサポートする場合、そのサーバー自体に設計上の問題がある。

2.3 stateパラメータによるCSRF防御

stateパラメータなしにリダイレクトを受け取ると、CSRF攻撃に対してオープンになる。CLIはAuthorization要求時に暗号学的乱数のstateを生成し、リダイレクト受信時に同一stateかどうかを検証する必要がある。

2.4 ローカルポートバインド失敗時のグレースフルフォールバック

ポート8484がすでに使用中の場合がある。CLIは複数のポートを順番に試みるか、失敗時はデバイスフローにグレースフルフォールバックすべきだ。ポートが開かず認証が無音で失敗する体験は、ユーザーに「自分が何か間違えたのか」と思わせる悪いUXだ。

3. トークン保存 — 「どこに保存するか」がセキュリティの90%

完璧な認証フローも、トークンを不適切に保管すれば意味がない。保存場所別のリスクを正直に比較する。

3.1 OS暗号化認証情報ストア — 第一候補

macOS Keychain・Windows Credential Manager・Linux Secret Service（D-Bus、libsecret/gnome-keyring）はOSが提供する暗号化ストアだ。共通特性は3つ：OSレベルの暗号化（macOSはSecure Enclave連携可能）、アプリケーションごとのACLベースアクセス制御、ハードウェアセキュリティモジュール連携だ。

プラットフォームごとの実装を直接書くより、言語別の抽象化ライブラリを使うのが現実的だ：Goではzalando/go-keyring、Pythonではkeyring、Node.jsではkeytar。GitHub CLIはキーリングをライブラリに委任している。これが正しいアプローチだ。

3.2 ファイルベース保存 — 条件付き許容

キーチェーンデーモンが利用できない環境（最小限のコンテナなど）では、ファイルへの保存も可能だ。ただし条件がある：ファイルのパーミッションを600（所有者のみ読み書き）に強制すること、トークンファイルのあるディレクトリをgitignoreに含めること、そして最低限パスフレーズベースの暗号化を検討することだ。AWS CLIの~/.aws/credentialsがこのパターンだ。

3.3 環境変数 — CI/CDのみ

環境変数はプロセスリスト（/proc/PID/environ）に表示され、子プロセスに自動的に継承され、クラッシュレポーターが記録する可能性がある。長期APIキーを環境変数でローカル開発に使うと、そのキーが思いがけない多くの場所に流れ込む。CI/CDではシークレットストアから注入された短命の値なので別の話だ。

3.4 絶対にやってはいけないこと

ソースコードへのハードコードは絶対禁止だ。一度TOKEN=abc123がコミットに入ると、git履歴に永遠に残る。.envファイルをgitignoreなしで作成すること、トークンをログに出力すること（デバッグログを含む）、コマンドライン引数にトークンを平文で渡してps auxに露出させることも、実際によくある失敗だ。

4. APIキーの取り扱い — ミスの90%はここで起きる

APIキーのみに依存するCLIを構築または使用する際の実践的なガイドラインだ。

4.1 キー設計の原則

最小限の権限でAPIキーを発行する。読み取り専用の作業に書き込み権限まであるキーを使う必要はない。キーには有効期限を設定し、90日ローテーションが業界推奨の周期だ。有効期限のないキーは漏洩時の被害期間が無制限になる。

4.2 キー漏洩後の対応

キーが漏洩した場合、最初の行動はファイル削除ではなく即座の廃棄だ。git rmでファイルを削除しても、git log -S 'KEY_VALUE'で履歴から見つけられる。git履歴を書き換えても、すでにクローンした人・フォーク・キャッシュ・サードパーティスキャナーが持っている可能性がある。即座の廃棄→新キー発行→ログ監査の順が正しい対応手順だ。

4.3 pre-commitスキャナーによる予防

GitGuardian・truffleHog・detect-secretsのようなpre-commitスキャナーをチームの標準設定に加えれば、コミット時点でシークレットを検出できる。detect-secretsフックの追加は5分の作業だ。この防衛線一つが最も一般的なCLIクレデンシャルインシデントのクラスを排除する。

5. トークンリフレッシュ — UXとセキュリティの交差点

短命のアクセストークンはセキュリティに良い。しかしコマンド実行のたびに再ログインを強制すれば誰も使わなくなる。リフレッシュトークンパターンがこのバランスを取る。

5.1 透過的な更新

CLIはAPI呼び出し前にアクセストークンの有効期限を確認するか、401レスポンス受信時にリフレッシュトークンで新しいアクセストークンを取得する。ユーザーはこのプロセスを認識する必要がない。リフレッシュトークン自体が期限切れになったときのみ、再認証フローを開始する。実装上の注意点：CLIが並行して複数のリクエストを送ると、同時に複数の更新試行が生じる可能性がある。mutexまたは単一更新ゴルーチンパターンで競合を防ぐ必要がある。

5.2 リフレッシュトークンローテーション

リフレッシュトークンは使用時ごとに新しいものを発行し、古いものを廃棄するローテーション方式が安全だ。古いリフレッシュトークンで更新試行が来た場合、サーバーはトークン窃取の疑いとしてセッション全体を無効化するポリシーが理想的だ。この「リフレッシュトークンローテーションと再使用検出」はAuth0・Okta・Keycloakが標準でサポートしている。

5.3 トークン有効期間の実際的な基準

アクセストークンは1時間が業界標準。リフレッシュトークンは30〜90日でローテーションを伴う。ローテーションにより、アクティブなユーザーは無期限のセッションを維持でき、一定期間使用しないと自動で期限切れになる。これが「シームレスなログイン」の利便性と「盗まれたトークンの有効期間の制限」を同時に実現する仕組みだ。

6. セキュリティの落とし穴カタログ — 実際に失敗するパターン

CLIツールを監査する際に実際にチェックする、よくある失敗パターンを整理する。

6.1 バイナリにclient_secretを埋め込む

CLIはパブリッククライアントだ。配布バイナリからstringsコマンドでclient_secretを抽出するのは10秒の作業だ。CLIではclient_secretを使ってはならない。PKCEがこの問題の解答だ。

6.2 トークンをログに出力する

デバッグモードでHTTPリクエストヘッダー全体をログに出力すると、Authorization: Bearer {token}がそのまま記録される。ログは通常ファイルに保存され、ログ収集システムに流れる。トークンを出力する場合は必ずマスキング（Bearer sk-...XXXXなど）すること。

6.3 デバイスコードのポーリング間隔を無視する

RFC 8628はintervalフィールド（デフォルト5秒）と、それより速くポーリングした場合のslow_downレスポンスを規定している。ポーリング間隔を無視して頻繁にリクエストすると認証サーバーに不必要な負荷をかける。バックオフロジックを実装し、slow_downレスポンス時はintervalを5秒ずつ増加させること。

6.4 リダイレクトURIの検証なし

認証サーバーが事前登録なしにリダイレクトURIを受け入れたり、ワイルドカード（http://localhost:*）で登録を許可すると、攻撃者が別のポートにコードを横取りできる。認証サーバーの設定で許可されるリダイレクトURIを正確に固定すること。

7. AIエージェント時代のCLI認証 — 新しい変数

2026年特有の新しい変数がある。AIコーディングエージェントがCLIをプログラム的に呼び出すパターンが急増したことだ。

Claude Code・GitHub Copilot agent mode・CursorなどのAIエージェントがgh・aws・stripeのようなCLIツールをエージェントループ内で実行する。これらのエージェントのサブプロセスは環境変数を継承する。つまり環境変数にあるAPIキーがエージェントの実行コンテキストに流れ込む。エージェントがサードパーティコードを実行したり、MCPサーバーを通じて外部ツールを呼び出す場合、その境界を越えてクレデンシャルが漏洩する可能性がある。

防御パターンは2つだ。まず、エージェントが使用するCLI認証情報を最小権限の専用トークンで分離する。次に、apiKeyHelperパターン（エージェントが要求するたびに短命トークンを生成するヘルパースクリプト）を使う。Claude Code自体がこのパターンをサポートしている。短命トークンが漏洩しても有効期間が短いため、被害を最小限に抑えられる。

8. 結論 — 今日すぐ適用できる3つのアクション

CLI認証は選択の連続だ：どのフローを使うか、どこに保存するか、どのように更新するか。各決断において「便利な方」と「安全な方」が分かれることがある。私の核心的な主張：正しい抽象化（PKCE・OSキーチェーン・トークンローテーション）を最初から使えば、利便性とセキュリティは両立する。後からセキュリティを追加することは、最初から正しく設計することより常にコストが高い。

8.1 現在使用しているCLIツールのトークン保存場所を確認する

日常的に使うCLIツールがトークンをどこに保存しているか確認しよう。~/.config/tool/以下にJSONファイルがあれば、そのファイルのパーミッションをチェックする。ls -laで600かどうか確認し、gitignoreに含まれているか確認する。OSキーチェーン連携が利用可能ならそちらへの移行を検討しよう。

8.2 pre-commitシークレットスキャナーをチーム標準に追加する

detect-secretsやgitleaksフックをpre-commit設定に追加するのは5分の作業だ。この防衛線一つがCLIクレデンシャルインシデントの最も一般的なクラスを防ぐ。個人プロジェクトでも習慣にすべきだ。

8.3 新しいCLIツールを作るならPKCEを最初から設計に組み込む

認証を後から追加しようとするな。初期設計時にフロー選択（PKCEvsデバイスフロー）・トークン保存（OSキーチェーンライブラリ）・リフレッシュロジックを明確に定義する。そしてclient_secretをバイナリに埋め込むことは設計エラーであり、「とりあえず急ぐから」が許される利便性の問題ではない。
