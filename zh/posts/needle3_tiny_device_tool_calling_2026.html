1. 面向微型设备的专用基础模型诞生背景与设计目标

一般而言，将语言模型直接部署至嵌入式单板或低功耗硬件中运行，会面临可用内存与计算资源的物理瓶颈。

针对微型设备运行环境，Cactus Compute推出了Needle 3模型。官方代码仓库（https://github.com/cactus-compute/needle）的说明写道：Needle 3是「面向手机、穿戴设备、智能家居、机器人、汽车及微控制器的2比特、8至29MB自动化基础模型，用于执行工具调用、结构化提取和文本嵌入（Automation foundation model for tiny devices: 2-bit, 8-29 MB, tool calls, structured extraction and embeddings on phones, wearables, smart homes, robots, cars and microcontrollers）」，并以Apache-2.0协议开源。在产品主页（https://cactuscompute.com/needle）上，Cactus陈述道：「The whole model is a single 8-29 MB binary built on our Simple Attention Network, and we trade general chat capacity to beat models 10x its size on mobile tool calls and match 2-3x bigger models on extraction」。

依本文分析，原文表明该模型通过将职责收敛至工具选择与参数填充，而非宽泛闲聊写作，以维持极小二进制尺寸。产品主页（https://cactuscompute.com/needle）所列出的实际目标场景与具体英文表述如下：

  • 智能家居：「"Dim the bedroom and lock up" becomes two calls, executed offline, with no hub round trip.」
  • 机器人：「"clean the kitchen but leave the bedroom", "go back to the dock when you are done". Each becomes a sequence of moves it can execute.」
  • 智能手机：「make an album from last weekend's photos, open a site, dim the screen, find the lease in your files.」
  • 穿戴设备：「a card charge into merchant, amount and date; a message into a reply; a complaint into a sentiment flag.」
  • 车载系统（Automotive）：「Climate, media, navigation and calls from requests in the cabin, with the tool set pinned so it survives a long drive's worth of conversation.」
  • 本地检索匹配：「semantic search over notes, messages and documents; a query matched to the closest of hundreds of tools; near-duplicate alerts merged on a watch.」

2. 核心功能三项与输入输出规范 — 工具调用、结构化提取与文本嵌入

Needle 3的功能范围在README（https://github.com/cactus-compute/needle）中明确限定为工具调用（Tool calls）、结构化提取（Structured extraction）与文本嵌入（Text embedding）三项。

工具调用与语法约束提取

关于工具调用，README写道：「given the functions your app exposes, Needle picks the right ones and fills every argument from what the user said. Ask for two things and you get two calls in order; ask for something no tool covers and you get an empty list, not a guess.」它指出，遇到无工具支持的请求时，模型会返回空列表而非胡乱猜测。

关于结构化提取，原文写道：「declare a shape, hand over messy text, get typed fields back: an invoice, a booking, a notification, a form. The decode grammar guarantees the output parses, and extraction generalises to classification」。说明指出解码语法确保输出解析成功。

基于单模型的端侧向量嵌入

关于文本嵌入，原文说明道：「the same model returns a vector for a sentence, so an app can search, match and route locally: find the note you mean, pick the tool closest to a request, collapse duplicate alerts」。同一个二进制文件可直接计算句子特征向量，用于本地检索和匹配。

依本文分析，原文陈述的这三项能力将设备外设控制、数据结构解析和本地语义检索整合在单一端侧二进制文件内。

功能类别 输入规范 输出规范 运行机制与约束特征

在产品主页（https://cactuscompute.com/needle）的编写工具（Writing tools）章节中，明确提出的准则如下：

  • 工具粒度：「a narrow tool with a plain description beats a broad one. One tool per action, described by the actions it covers ("Turn a room's lights on or off") rather than a category.」
  • 枚举声明：「Name enum options after what a user says (action: ["increase", "decrease"]) and keep synonyms in the description.」
  • 参数默认值：「Give a required argument a default when a request may leave it out; a required argument with no default and no evidence in the request is withheld rather than guessed.」
  • 取值格式：「Put value formats in descriptions ("City, ST", "e.g. T-1042"). Add triggers to intents that must always reach a tool, and keep the toolset per turn small.」

3. 阶梯式简单注意力（Laddered Simple Attention）网络架构剖析

关于Needle 3的结构，README（https://github.com/cactus-compute/needle）写道：「Needle 3 is a Laddered Simple Attention Network: a Monarch Hadamard MLP in place of the FFN, GQA attention with causal conv taps, engram n-gram memory read by gather, and multi-lane hyper-connections, trained so that every depth from 2 to 20 layers is a deployable model.」

替代FFN的君主阿达马乘积与mHC通道架构

根据产品主页（https://cactuscompute.com/needle）上的架构图（Figure 1），模型拥有20层深度、768隐层维度和121M总参数量。分词器采用词表规模为8,192的SentencePiece BPE，并采用tied unembed（8,192 × 768）权重共享结构。残差连接采用读写4条通道的mHC网络并经由sandwich ZCRMSNorm约束。注意力层采用12q : 2kv比例、每通道3抽头因果卷积、窗口为1,024的GQA机制、RoPE与QK归一化，并在第4、9、14和19层设置全局注意力。

替代FFN的Monarch Hadamard模块采用32 × 32矩阵计算。在Figure 1图表说明中，Cactus写道：「The architecture spends over 2x fewer MFLOPs per token than a transformer of the same configuration」。

字符元（Engram）内存与参数结构特征

架构图标注，在121M总参数中，有70.8M参数存放在字符元查找表中（位于第3、7、11、15和19层的18,432个槽位，通过gather操作读取的哈希2元与3元内存）。README解释道：「Most of its parameters sit in the engram, so the 121M model does the arithmetic of a 50M one」。

预训练方面，产品主页陈述模型消耗了「360B tokens of proprietary structured dataset」，并仅在训练阶段挂载mtp t+2辅助预测头。模型交付形式为CQ2 2比特量化二进制文件，根据不同层数生成8MB至29MB（主页正文标注为9 to 29 MB）文件。主要特征归纳如下：

  • 阶梯子模型：从2层到20层的各级深度均被训练为可独立部署的模型
  • 尺寸范围：依据层数深度打包为8MB至29MB之间的单一CQ2 2-bit文件
  • 语法编译限制：基于目标模式编译的字节级语法限制生成空间
  • 校准输出头：专用分类头在每个推理交互轮次中给出校准置信度

4. 安装流程与基于Python的工具定义代码实现

Needle 3在README（https://github.com/cactus-compute/needle）中给出的安装指令如下。引擎包从Hugging Face（https://huggingface.co/Cactus-Compute/needle3）一次性拉取并存入本地缓存。

pip install cactus-needle

对于工具定义与运行，README阐述道：函数签名提供参数类型，Docstring充当工具说明，run()方法负责串联执行与结果回传。文档展示的代码如下：

import needle

@needle.tool
def get_weather(city: str):
    "Get the current weather for a city."
    return {"city": city, "temp_c": 27, "sky": "clear"}

agent = needle.Needle(tools=[get_weather])
print(agent.run("what's it like in Lagos right now?")["results"])
# [{'city': 'Lagos', 'temp_c': 27, 'sky': 'clear'}]

原文指出，每次交互均返回包含function_calls、reasoning与校准confidence的单个JSON对象，对于非相关意图返回空列表。若需维持已有系统运行，可通过needle.Needle(tools=[...], generation=2)继续运行Needle 2模型。

5. 官方公布的基准测试性能指标与测定条件细节

Needle 3的性能数据源自Cactus Compute在其产品主页（https://cactuscompute.com/needle）与图表中所发布的内部测定结果。

树莓派5设备上的官方测定吞吐量

Cactus表示，在物理树莓派5上，模型达到了每秒400至4,000解码词元（400-4k tokens/s decode）与每秒1,000至10,000预填充词元（1-10k tokens/s prefill）的吞吐水平。主页给出的示例JSON中，peak_ram_mb指标记录为28.5。

微调带来的子网络性能跃升

关于评测标准，README写明：「Tool calling is exact-match accuracy on the full test splits, extraction is field micro-F1 on the full test splits」。Figure 2附注说明指出，Needle 3子网络（20、16、8、4层）运行于出厂CQ2 2-bit二进制下，基准对比模型在vLLM下以f16运行，DeepSeek V4 Flash则基于其云端API评测。

Cactus宣称在DroidCall微调后，各子网络得分提升18至36点，且4层（29M参数）以上子网络得分超过DeepSeek V4 Flash（「fine-tuning on DroidCall lifts every subnetwork by 18 to 36 points, and from 4 layers up the tuned subnetwork passes DeepSeek V4 Flash, starting at 29M parameters (Figure 3)」）。产品主页所列出的六项评测集行数与标准如下：

  • Mobile Actions：961行，将手机口头指令转换为Android Intents，按完全匹配（exact call）评估
  • DroidCall：200行，包含需两次连续调用的指令，按顺序完全匹配（exact calls in order）评估
  • BFCL v4：3,641行，伯克利单轮函数调用，按AST匹配及无关指令非调用评估
  • DSTC8：1,813轮，对话槽位提取填入模式，按字段F1评估
  • SNIPS gold：700行，已知模式下的槽位填充，按字段F1评估
  • SNIPS 7-way：700行，在7个模式选项中辨别并填充槽位，按字段F1评估

6. 借助置信度门控与正则触发器实现端侧执行受控

Needle 3提供置信度（confidence）评分与正则触发器（triggers）选项，用于约束调用执行。

0.1置信度阈值底线与拒答逻辑

依据原文，模型返回的JSON包含校准置信度评分。引擎内置0.1的基础阈值底线，当评分低于0.1时，调用被转移至suppressed_calls，function_calls则返回空列表。

Cactus给出的控制模式显示：当confidence达到0.7以上时执行工具（execute），处于0.1至0.7或存在suppressed_calls时向用户确认（confirm），若无调用则给出拒答提示。此外，配置了triggers正则的工具会在输入匹配时强制约束解码范围，在低于0.1底线时仍会发出调用。

社区实测反馈中的实际局限与注意事项

在以GeekNews（https://news.hada.io/topic?id=33923）为代表的技术讨论中，早期实测提出了有别于官方宣传的如下观察：

  • 多义俚语容错局限：多义词或缩写易诱发误判（例如将本意为开灯的俚语「wee」误判为曲风检索工具）
  • 体感性能预期落差：部分用户以对话通用模型的标准评估专用工具模型时，产生不适应及宣传夸大感
  • 强依赖描述文档质量：Docstring、参数命名与模式定义的细致程度直接决定了分发准确率
  • 极小模型泛化衰减：精简至2至4层后，若缺乏针对下游场景的细致微调，基础准确率可能明显下滑
  • 单轮候选工具受限：单轮交互中暴露的活跃工具越多，误识别几率随之攀升，因而需保持单轮工具集小巧

7. 未确认事项

从公开文档及代码仓库中无法直接独立确认的事项如下：

  • 正式发布具体日期：README与主页均仅表述为「Today we release Needle 3」而未包含确切时间戳，因而无法从原文确认准确日期
  • 第三方独立复现数据：树莓派5上的吞吐量以及微调后超越DeepSeek V4 Flash的结论均为Cactus单方声明，未见独立机构复现报告
  • 预训练数据详细配比：360B词元专有结构化数据集的具体采集渠道、领域配比及版权授权情况在公开资料中未予披露
  • 专有量化（.cact）数学定义：CQ2 2-bit量化算法的详细公式推导与误差损失曲线未在公开文档中展开详述
