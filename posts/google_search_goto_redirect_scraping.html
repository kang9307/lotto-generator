2026-09-13 개발/인프라

웹 검색 엔진의 결과 페이지(SERP)는 오랜 기간 자동화된 데이터 수집기와 크롤러들에게 가장 가치 있는 진입점이었습니다. 검색어를 전달하고 반환되는 HTML 문서에서 결과 항목들의 링크 속성을 추출하는 작업은, 검색 색인이나 시장 조사, SEO 순위 추적 파이프라인의 가장 기본적인 출발점이었습니다. 검색 결과에 걸린 링크가 실제 목적지 URL을 담고 있거나 최소한 쿼리 파라미터 안에 대상 주소를 보존하고 있었기 때문에, 수집기는 추가적인 네트워크 연결 없이도 내려받은 문서 한 장에서 수십 개의 목적지 주소를 즉각 확보할 수 있었습니다.

하지만 2026년 8월 말을 기점으로 이러한 기본 전제에 중대한 구조적 균열이 관측되기 시작했습니다. Google 검색이 일반 검색 결과에 노출되는 하이퍼링크를 실제 대상 웹사이트 주소 대신 google.com/goto?url=... 형식으로 광범위하게 다시 쓰기 시작한 것입니다. 특히 이 변경점은 단순히 주소를 겉으로 감추는 데 그치지 않고, 클라이언트가 오프라인에서 대상 주소를 계산해 낼 수 없도록 만드는 독자적인 불투명 인코딩을 적용했습니다. 이로 인해 검색 결과 수집 파이프라인을 설계하고 운영하는 실무 환경 전반에서 기존의 데이터 추출 방식이 완전히 멈춰 서거나 구조적 전환을 요구받고 있습니다.

무엇이 바뀌었는가 - 결과 링크의 goto 재작성

Google 검색 결과 페이지에서 관측된 가장 핵심적인 변화는 일반 자연 검색 결과의 앵커 태그가 더 이상 최종 목적지의 웹 주소를 노출하지 않는다는 점입니다. 검색 결과 목록에 렌더링된 각 항목의 href 속성은 실제 이동 대상 사이트가 아니라 https://www.google.com/goto?url=... 형태의 내부 엔드포인트를 가리키도록 생성됩니다. 브라우저 환경에서 일반 사용자가 해당 링크를 클릭하면 브라우저는 Google 서버로 요청을 보내고, 서버가 내려주는 리디렉션 지시에 따라 자연스럽게 실제 목적지 페이지로 도달하게 됩니다.

공개된 엔지니어링 분석에 따르면 이 동작은 2026년 8월 말 기준, 사용자가 로그인하지 않은 로그아웃 상태이거나 브라우저의 시크릿 모드(비공개 브라우징) 환경에서 검색을 수행할 때 일관되게 나타나고 있습니다. 초기에는 극히 제한된 일부 검색 결과 트래픽을 대상으로 간헐적인 테스트 형태로 포착되었으나, 관측 시점이 지나면서 더 이상 극소수의 트래픽에만 머무르는 국소적 실험으로 치부하기 어려운 단계에 도달했습니다. 로그아웃 상태의 검색 환경에서는 사실상 거의 모든 일반 유기적 검색 결과의 URL이 이 goto 링크로 교체되어 제공되는 양상이 관측되었습니다.

일반적인 사용자 관점에서는 클릭 후 수십 밀리초 이내에 원래 목적하던 사이트로 전환되므로 사용 경험상의 차이를 체감하기 어렵습니다. 그러나 웹 문서를 프로그래밍 방식으로 가져와 파싱하는 크롤러나 데이터 파이프라인의 시각에서는 완전히 다른 상황이 펼쳐집니다. HTML 문서 내에서 링크 텍스트와 함께 추출하던 목적지 URL이 통째로 증발하고, 대신 구글의 내부 처리용 식별자만이 남게 되기 때문입니다.

과거의 /url 리디렉션과 무엇이 다른가

Google이 검색 결과 링크를 자사 서버의 리디렉션 주소로 감싸서 제공한 사례는 과거에도 존재했습니다. 이전부터 오랜 기간 활용되었던 대표적인 형태는 google.com/url?q=[목적지URL] 형식이었습니다. 사용자의 클릭 여부를 추적하고 이동 경로를 통제하기 위해 리디렉터 래퍼를 씌우는 방식 자체는 검색 엔진 진영에서 낯선 기술이 아니었습니다. 하지만 과거의 방식과 이번에 도입된 goto 방식 사이에는 데이터 처리 측면에서 결정적인 질적 차이가 존재합니다.

과거의 /url 래퍼는 쿼리스트링의 q 매개변수 안에 최종 대상 웹사이트의 전체 주소가 표준 URL 인코딩 형식으로 고스란히 보존되어 있었습니다. 예를 들어 대상 주소가 특정 기술 블로그였다면, 쿼리스트링에 퍼센트 인코딩된 문자열이 그대로 포함되어 전달되었습니다. 따라서 크롤러나 스크래퍼는 굳이 Google 서버에 리디렉션 요청을 추가로 보낼 필요가 없었습니다. 내려받은 검색 결과 HTML을 파싱하면서 정규식이나 URL 파서를 통해 q 파라미터 값만 뽑아내어 로컬에서 디코딩 함수를 호출하면 원래의 완전한 목적지 주소를 즉시 복원할 수 있었습니다.

반면 새롭게 등장한 goto 형식은 이러한 오프라인 추출 경로를 근본적으로 차단합니다. 링크의 구조가 달라졌을 뿐만 아니라, 파라미터에 담긴 데이터의 성격 자체가 완전히 변했기 때문입니다. 두 형식의 구조적 차이를 정리하면 다음과 같습니다.

비교 항목 기존 리디렉션 (/url) 신규 리디렉션 (/goto)
목적지 주소 보존 위치 쿼리 파라미터 (q=...) HTTP 응답 헤더 (Location)
파라미터 인코딩 형태 표준 퍼센트 URL 인코딩 Google 독자 고유 인코딩
오프라인 디코딩 가능 여부 클라이언트 단독으로 즉시 가능 오프라인 디코딩 완전 불가능
목적지 확인을 위한 추가 요청 불필요 (HTML 파싱만으로 완결) 결과 항목마다 추가 HTTP 요청 필수
수집기 식별 및 탐지 위험 HTML 1회 요청 후 오프라인 완결 단일 클라이언트의 연속 요청 노출

표에서 드러나듯 기존 방식에서는 HTML 문서를 한 번 수신한 이후의 모든 작업이 클라이언트의 로컬 메모리 안에서 해결되었습니다. 그러나 새로운 체제에서는 개별 검색 결과의 목적지를 파악하는 작업이 매번 Google 서버와의 실시간 네트워크 통신을 요구하는 종속적 작업으로 전환됩니다.

불투명한 인코딩 - 오프라인 디코딩의 종말

새로운 goto 링크에서 url= 파라미터 뒤에 붙는 데이터는 언뜻 보기에 평범한 Base64 인코딩 문자열처럼 보일 수 있습니다. 실제로 많은 엔지니어들이 초기에 해당 문자열을 단순 Base64로 디코딩하거나 압축 해제를 시도했습니다. 그러나 분석 결과 이 파라미터는 대상 URL 문자열을 단순히 부호화한 것이 아니라, Google 고유의 내부 인코딩 체계를 따르는 불투명 참조(opaque reference)라는 점이 드러났습니다.

원문의 기술적 관측에 따르면, 이 인코딩 블롭은 공개된 Protobuf 스키마나 표준적인 역직렬화 도구로 해석할 수 있는 형태가 아닙니다. 사실상 Google 검색 엔진의 색인 데이터베이스 내에서 해당 웹페이지 레코드를 가리키는 내부 식별자에 가깝습니다. 즉 목적지 URL이라는 원래의 정보 자체가 파라미터 문자열 속에 포함되어 압축되어 있는 것이 아니라, Google의 백엔드 시스템만이 해석할 수 있는 포인터 역할을 수행하고 있는 것입니다.

이러한 설계는 자동화 수집 도구에 결정타를 가합니다. 만약 복잡한 암호화나 압축이라도 클라이언트가 해독할 수 있는 키나 알고리즘이 브라우저 코드 내에 자바스크립트로 노출되어 있다면, 리버스 엔지니어링을 통해 로컬 디코더를 구현하는 일이 이론적으로 가능합니다. 하지만 데이터 자체가 외부 서버 내부의 레코드 조회를 위한 불투명 식별자라면, 외부 클라이언트가 자체적인 연산만으로 원래의 URL을 복원하는 것은 원천적으로 불가능해집니다. 결국 목적지를 알아내기 위해서는 예외 없이 Google 서버에 질의를 던져야만 하는 구조가 완성됩니다.

목적지 주소 확인의 원리 - Location 헤더와 리디렉션 미추종

그렇다면 자동화 파이프라인에서 실제 목적지 URL을 확인하는 기술적 원리는 무엇일까요. Google은 브라우저를 사용하는 실제 사람을 대상 웹사이트로 안내해야 하므로, 어딘가에서는 반드시 최종 목적지 주소를 클라이언트에게 넘겨주어야 합니다. 그 전달이 일어나는 물리적 자리가 바로 HTTP 계층의 Location 응답 헤더입니다.

클라이언트가 https://www.google.com/goto?url=... 주소로 HTTP 요청을 전송하면, Google 서버는 본문 데이터를 내려주는 대신 리디렉션 상태 코드(통상적으로 HTTP 302 Found)와 함께 최종 목적지 주소가 담긴 Location 헤더를 반환합니다. 따라서 목적지를 확인하는 올바른 네트워크 접근법은 요청을 보내되 응답의 리디렉션을 따라가지 않는 것입니다. HTTP 요청과 응답의 개념적 구조는 다음과 같이 표현됩니다.

GET /goto?url=CAES… HTTP/1.1
Host: www.google.com

HTTP/1.1 302 Found
Location: https://www.linkedin.com/in/satyanadella

여기서 중요한 점은 자동화 클라이언트가 리디렉션을 자동으로 추종(follow redirects)하도록 내버려두면 안 된다는 사실입니다. 만약 HTTP 클라이언트 라이브러리가 기본 설정대로 리디렉션을 끝까지 따라가게 되면, Google의 응답을 넘어 최종 대상 웹사이트의 서버까지 접속하여 본문 HTML 전체를 내려받게 됩니다. 이는 수집 파이프라인에 엄청난 네트워크 대역폭 낭비와 불필요한 레이턴시를 유발합니다. 목적지 주소 문자열만 확보하는 것이 목표라면, Location 헤더를 읽어내는 즉시 요청 흐름을 중단해야 합니다.

기술적으로는 본문(body)을 아예 요청하지 않고 헤더 정보만을 질의하는 HEAD 메서드를 활용하거나, GET 메서드를 사용하되 리디렉션 추종 옵션을 수동(manual)으로 비활성화하는 방식이 사용됩니다. 또한 원문에서는 Google 서버가 특정 조건에서 3xx 상태 코드가 아닌 다른 상태를 반환하더라도 Location 헤더를 함께 실어 보내는 사례가 관측되었음을 지적하며, 상태 코드의 종류에만 의존하지 않고 헤더 존재 여부를 직접 확인하는 방어적 접근이 필요하다고 설명하고 있습니다.

물론 검색 결과 페이지 내부를 세밀히 들여다보면, Google이 SERP 화면을 구성하기 위해 도메인 이름이나 파비콘, 출처 정보를 화면에 표시하는 과정에서 자바스크립트 데이터 블록이나 내부 저장소(예를 들어 페이지 스크립트 내의 데이터 객체)에 대상 URL 흔적을 남겨두는 경우가 존재합니다. 심지어 특정 브라우저에서는 마우스 커서가 올라갈 때 스크립트가 앵커의 주소를 교체하는 동작이 목격되기도 합니다. 그러나 이러한 클라이언트 측 내부 스크립트나 비공개 변수 구조는 Google이 언제든 이름을 바꾸거나 구조를 뒤엎을 수 있는 지극히 취약한 방식입니다. 안정적이고 일관된 데이터 해석을 위해서는 네트워크 레벨의 Location 응답 헤더를 다루는 것이 가장 견고한 기술적 기준이 됩니다.

Google이 노리는 방어 효과 - 수집 비용의 비대칭적 증가

Google이 이러한 링크 구조 변경을 추진하는 근본적인 동기는 무엇일까요. 공개된 기술 분석들은 이것이 AI 모델 학습용 크롤러와 대규모 SEO 스크래퍼들의 무차별적인 SERP 수집 행위를 견제하기 위한 안티 스크래핑(anti-scraping) 방어 조치의 일환이라고 입을 모읍니다. 최근 생성형 AI의 발전과 검색 엔진 대체 모델의 등장으로 인해, 웹 전반의 신선한 링크와 검색 결과 데이터를 실시간으로 대량 긁어가려는 수요가 폭발적으로 증가했습니다.

평문 링크나 오프라인 디코딩이 가능하던 시절에는, 스크래퍼가 검색 결과 페이지 1건의 HTML을 가져오는 것만으로도 내부에 포함된 10개 이상의 유효 목적지 URL을 한 번에 손에 넣을 수 있었습니다. Google 서버에 가해지는 요청은 초기 검색 1회로 끝났고, 나머지 URL 추출은 스크래퍼 내부 서버의 CPU 연산만으로 완결되었습니다. 이는 수집자에게는 극도로 저렴하고 빠른 방식이었지만, 검색 엔진 인프라 입장에서는 자사의 핵심 데이터 자산이 대량으로 유출되는 통로였습니다.

그러나 goto 체제가 도입되면서 상황은 완전히 역전됩니다. 단 한 번의 검색 결과 페이지에서 목적지 주소들을 완전히 수집하려면 다음과 같은 비용의 비대칭이 발생합니다.

  • 네트워크 왕복의 폭증: 검색 결과에 노출된 10개의 링크를 모두 확인하려면, 최초 SERP 요청 1회 외에도 Google 서버로 10회의 독립적인 HTTP 요청을 추가로 전송해야 합니다. 작업에 드는 네트워크 비용이 결과 항목 수에 비례하여 직접 증가합니다.
  • 수집 파이프라인의 속도 지연: 오프라인 문자열 파싱은 밀리초 이하의 메모리 연산으로 끝나지만, 추가적인 HTTP 요청은 각각 DNS 조회와 TLS 핸드셰이크, 서버 왕복 레이턴시를 수반합니다. 대규모 수집 작업의 처리 속도가 현저히 저하됩니다.
  • 클라이언트 행위의 명확한 가시화: 동일한 IP 주소나 동일한 세션의 클라이언트가 검색 결과를 수신한 직후, 수십 밀리초 간격으로 해당 페이지에 포함된 goto 링크들을 연속적으로 호출하는 행위는 봇 탐지 시스템에 가장 쉽게 포착되는 패턴입니다.
  • 프록시 및 인프라 유지 비용 상승: 요청 횟수가 늘어나고 봇 탐지망에 걸릴 확률이 높아짐에 따라, 수집 주체는 더 많은 프록시 IP 풀을 확보하고 세션 관리를 복잡하게 구성해야 하는 막대한 인프라 비용 부담을 안게 됩니다.

결국 Google은 스크래퍼의 접근을 완전히 원천 봉쇄하지 않더라도, 데이터를 대량으로 수집하는 단가를 급격히 끌어올림으로써 무분별한 단순 스크레이핑의 경제성을 무너뜨리는 전략을 취하고 있는 것입니다.

연속된 조치들의 맥락 - num=100 폐지와 봇가드 강화

이번 goto 리디렉션의 도입은 단독으로 불쑥 튀어나온 일회성 변경이 아닙니다. 지난 수년간 Google이 검색 서비스 전반에서 진행해 온 일련의 데이터 보호 및 봇 차단 조치들의 연장선상에 위치해 있습니다. Google은 외부 자동화 시스템이 검색 결과를 저렴하게 대량 흡수하지 못하도록 지속적으로 진입 장벽을 높여 왔습니다.

대표적인 선행 조치가 바로 검색 URL 매개변수인 num=100의 지원 중단 및 제거였습니다. 과거 스크래퍼들은 쿼리 뒤에 &num=100 파라미터를 붙여 단 한 번의 HTTP 요청으로 100위까지의 검색 결과를 통째로 긁어모을 수 있었습니다. Google이 이 옵션을 무력화하면서 수집기들은 100개의 결과를 얻기 위해 페이지를 10번 넘겨가며 10회의 독립적인 검색 요청을 수행해야만 했습니다. 이 조치 하나만으로도 스크래핑 인프라가 감당해야 하는 요청량과 차단 위험이 10배로 늘어났습니다.

이와 더불어 브라우저 핑거프린팅과 봇 탐지 프레임워크인 BotGuard 및 SearchGuard의 고도화가 병행되었습니다. 단순한 헤드리스 브라우저나 HTTP 라이브러리로 접근하는 클라이언트를 실시간으로 식별해 챌린지를 부과하거나 CAPTCHA를 띄우는 메커니즘이 지속적으로 정교해졌습니다. 최근 Google의 주요 안티 스크래핑 조치들을 비교하면 다음과 같습니다.

조치 항목 주요 기술 메커니즘 자동화 수집에 미치는 실무 영향
num=100 파라미터 제거 페이지당 노출 결과 수를 기본 10건 단위로 강제 제한 동일 데이터 확보를 위한 검색 요청 횟수 10배 증가
BotGuard / SearchGuard 고도화 브라우저 환경 지문 수집 및 동적 자바스크립트 챌린지 수행 헤드리스 브라우저 탐지율 상승, 프록시 소모율 가속
goto 리디렉션 링크 도입 결과 앵커 href를 불투명 인코딩된 내부 엔드포인트로 대체 오프라인 디코딩 원천 차단, 항목당 추가 네트워크 질의 강제

이처럼 Google의 대응은 단일 취약점을 메우는 미봉책이 아니라, 검색 결과 추출의 전체 수명 주기(검색 요청 → 브라우징 렌더링 → 결과 파싱) 전반에 걸쳐 단계별로 비용을 누적시키는 통합적인 방어선 구축의 흐름을 보여줍니다.

크롤링 및 자동화 파이프라인 설계자가 마주한 실무 과제

이러한 변화는 웹 데이터 수집 시스템을 직접 구축하거나 운영하는 엔지니어들에게 구체적인 아키텍처 수정을 요구합니다. 기존의 많은 크롤링 파이프라인은 검색 결과 문서를 비동기로 빠르게 긁어온 뒤 백그라운드 워커에서 정적 파싱을 수행하는 구조를 취해왔습니다. 그러나 이제는 파싱 단계와 네트워크 요청 단계가 분리될 수 없게 되었습니다.

실무 설계자가 마주하는 첫 번째 과제는 동시성 제어와 레이트 리밋(Rate Limit)의 재설계입니다. 검색 결과 페이지 하나에서 10개의 goto 링크가 쏟아져 나왔을 때, 이를 빠른 속도로 병렬 요청하면 단 몇 초 만에 동일 세션에서 비정상적인 트래픽 폭발이 발생합니다. 이는 곧바로 Google의 IP 차단이나 엄격한 브라우저 검증으로 이어집니다. 따라서 파이프라인은 링크 해석 요청 간에 적절한 지연 시간(jitter)을 부여하고, 요청 출처를 분산시킬 수 있는 큐 시스템을 도입해야 합니다.

두 번째 과제는 네트워크 I/O 최적화와 연결 풀 관리입니다. 앞서 언급했듯 리디렉션을 자동으로 따라가지 않도록 HTTP 클라이언트를 엄격히 제어해야 하며, 불필요한 TCP/TLS 핸드셰이크 오버헤드를 줄이기 위해 지속 연결(Keep-Alive)을 지원하는 커넥션 풀을 효율적으로 운용해야 합니다. 응답 헤더의 Location만을 안전하게 가로채고 연결을 즉시 풀로 반환하는 세밀한 라이브러리 레벨 제어가 필수적입니다.

한편 상용 SERP 수집 서비스를 판매하는 전문 벤더들 역시 발 빠른 대응에 나섰습니다. 이번 기술적 변화를 상세히 보고한 Autom 팀은 자사의 Google 검색 파이프라인을 갱신하여, 서버 내부에서 goto 링크를 자동으로 감지하고 리디렉션을 추종하지 않은 채 Location 헤더를 읽어 최종 목적지 URL을 복원하도록 파이프라인을 수정했다고 밝혔습니다. 이를 통해 자사 API를 이용하는 기존 고객들은 스키마 변경 없이 기존의 구조화된 필드(예: link 필드)로 최종 목적지 주소를 지속적으로 제공받을 수 있도록 조치했다는 설명입니다. 그러나 자체 인프라를 직접 운영하는 팀이라면 이러한 리졸브 로직을 독자적으로 구현하고 유지보수해야 하는 기술적 부담을 고스란히 떠안게 되었습니다.

인프라 방어와 데이터 수집의 지속적 긴장 관계

Google의 이번 조치를 한 걸음 물러서서 바라보면, 현대 웹 생태계 전반에서 심화되고 있는 인프라 방어자와 데이터 수집자 간의 거대한 긴장 관계를 다시금 실감하게 됩니다. 본 블로그의 이전 글인 크롤러가 물리는 청구서는 누가 받는가에서 살펴보았듯, 리눅스 커널 git 호스팅(git.kernel.org)과 같은 비영리 오픈 인프라조차 AI 크롤러와 무차별 스크래퍼들의 무작위 요청 폭격으로 인해 전체 연산 자원의 상당 부분을 방어에 쏟아붓고 있습니다.

공개 인프라를 지탱하는 소규모 운영자들은 폭증하는 대역폭 비용과 CPU 부하를 견디다 못해 작업증명(Proof of Work) 관문을 세우거나 경로 자체를 닫아거는 고육지책을 쓰고 있습니다. 반면 세계 최대의 인프라와 독점적 검색 데이터를 보유한 Google과 같은 거대 플랫폼은, 자사의 데이터 자산을 외부 AI 기업이나 경쟁사들이 무임승차하는 것을 막기 위해 goto와 같은 지능적인 프로토콜 비틀기를 동원하여 접근 단가를 통제합니다.

결국 인터넷 상의 모든 주소와 연결이 투명하게 노출되고 자유롭게 순회되던 고전적 웹의 이상은 빠르게 퇴색하고 있습니다. 방어자는 데이터를 지키거나 비용을 전가하기 위해 불투명 레이어와 검증 장벽을 계속해서 덧씌우고, 수집자는 이를 뚫어내기 위해 브라우저 에뮬레이션과 분산 프록시, 리버스 엔지니어링에 더 많은 자본을 투입하는 피로한 군비 경쟁이 일상화되고 있습니다. 이번 Google 검색 링크의 변화는 그 끝없는 공방전 속에서 방어 진영이 던진 또 하나의 계산된 수단이라 볼 수 있습니다.

확인하지 못한 것

  • Google 공식 발표 및 문서화 여부: 이번 goto 링크 도입과 관련된 기술 명세는 Google의 공식 블로그나 개발자 문서, 검색 지원 센터를 통해 공식 발표된 사실이 확인되지 않았습니다. 현재까지 알려진 모든 세부 사항은 Autom과 같은 제3자 기업 및 외부 엔지니어들의 트래픽 관측에 기반합니다.
  • 정확한 인코딩 및 직렬화 알고리즘: url= 파라미터에 전달되는 데이터 블롭의 정확한 내부 구조나 암호화 알고리즘의 세부 사항은 외부에서 확인되지 않았습니다. 원문 역시 이를 Google 색인 레코드에 대한 불투명 참조로 추정할 뿐 구체적인 복호화 키나 내부 스키마를 밝히지 못했습니다.
  • 전면 배포 및 영구 적용 여부: 2026년 8월 말 기준 로그아웃 및 시크릿 모드 검색에서 일관되게 관측되었으나, 이것이 전 세계 모든 리전과 로그인 계정, 모든 언어권 SERP에 100% 영구 롤아웃된 것인지, 아니면 장기 대규모 A/B 테스트의 연장인지 여부는 단정할 수 없습니다.
  • 1차 출처의 상업적 이해관계: 이번 변경을 가장 먼저 분석하고 기술 보고서를 발행한 Autom은 Google 검색 SERP 스크레이핑 API를 상용 판매하는 회사입니다. 스크레이핑의 기술적 장벽과 위협이 부각될수록 자체 인프라를 포기하고 자사 API 상품을 구매하도록 유도하는 강력한 상업적 유인이 존재하므로, 관찰 내용의 사실성과 별개로 분석의 서술 톤에 구조적 편향이 개입되었을 가능성을 염두에 두어야 합니다.
  • 특수 검색 모듈 및 AI Overviews 적용 일관성: 일반 자연 검색 결과 외에 AI Overviews 요약 블록이나 지식 패널, 지도 등 특수 버티컬 검색 결과에 포함된 링크들까지 동일한 goto 규칙이 예외 없이 적용되는지 여부는 완전히 확인되지 않았습니다.
  • Location 헤더 반환 정책의 지속 가능성: Google이 향후 스크래퍼들의 Location 헤더 수집 패턴을 인지하고, 단순 헤더 질의에 대해서도 챌린지나 브라우저 렌더링 검증을 추가로 요구할지 여부는 현재로서는 예측하기 어렵습니다.
