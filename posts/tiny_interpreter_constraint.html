예산을 극단적으로 줄이면 설계가 드러난다. 여유가 있을 때는 모든 계층이 나란히 놓여 있어서 무엇이 중심이고 무엇이 장식인지 구분되지 않는다. 예산이 한 자리 수 킬로바이트 아래로 내려가면 순서가 강제된다. 무언가는 먼저 잘리고 무언가는 끝까지 남는다. 그 순서가 곧 그 시스템의 우선순위 선언이다.

인터프리터는 이 실험에 특히 잘 맞는 대상이다. 갖춰야 할 계층이 교과서처럼 정해져 있기 때문이다. 어휘 분석, 구문 분석, 평가, 이름과 값을 잇는 환경, 그리고 오류 처리. 다섯 개다. 이 다섯을 1,024바이트 안에 다 넣을 수는 없다. 그래서 어느 것을 어느 순서로 깎았는지가 그대로 관측된다.

여기서 다루는 것은 그 순서다. 크기를 줄이는 기법의 목록이 아니라, 무엇을 포기할지 정하는 순서. 그리고 그 순서를 뒤집는 조건이 무엇인지까지.

수치에는 전부 조건이 붙어 있다. 1,024바이트는 C 소스 파일 하나의 크기이고, 빌드는 GCC 로 C89 표준을 지정한 뒤 경고를 끈 상태다. MicroPython 과 Lua 와 QuickJS 의 수치는 각각 다른 축을 잰 값이며, 서로 직접 비교되지 않는다. 어느 축인지 표시하지 않은 크기 수치는 대체로 쓸모가 없다.

계기 - 1,024바이트는 무엇의 크기인가

이 각도를 잡게 만든 것은 오스틴 헨리가 2026년 9월 6일에 올린 글이다. 제목은 1,024바이트로 Python 인터프리터 만들기이고, 본문 첫머리에 조건이 붙어 있다. 매크로나 라이브러리 편법 없이 C 코드 1,024바이트. 이 문장에 이미 세 가지가 들어 있는데, 소개 문구만 읽으면 셋 다 빠진다.

첫째, 1,024는 C 소스 파일의 크기다. 컴파일 결과물이 아니다. 저장소에는 읽을 수 있는 판과 골프 판이 따로 들어 있고, 골프 판이 정확히 1,024바이트, 읽을 수 있는 판은 4,800바이트를 넘는다. 두 판은 같은 언어를 구현한다. 차이는 표기뿐이다.

둘째, 그 크기는 자립한 값이 아니다. 저자가 열거한 바이트 절약 기법 안에 컴파일러가 libc 를 링크해 주는 것에 기대기가 들어 있다. 소스에서 사라진 문자 입출력 코드는 없어진 것이 아니라 다른 예산으로 옮겨 간 것이다. 이 구분을 하지 않으면 1,024바이트가 마치 실행에 필요한 전부인 것처럼 읽힌다.

셋째, 실행되는 것은 Python 이 아니다. 저자 본인이 전체 언어를 1,024바이트에 넣는 것은 불가능하다고 못 박고, 목표를 Python 처럼 보이는 것으로 다시 잡는다. 근거로 드는 것은 def 와 콜론과 들여쓰기와 괄호 없는 조건이다. 즉 문법의 외형이 목표였다.

빌드 조건도 크기의 일부다. 저장소가 제시하는 명령은 다음과 같다.

gcc-16 -std=gnu89 -w python1024.c   # C89 로 되돌리고 경고를 끈다
./a.out < fizzbuzz.py               # 실행할 프로그램은 표준 입력으로 들어간다
wc python1024.c                     # 저장소가 제시하는 크기 확인 방법

-std=gnu89 가 필요한 이유는 뒤에서 다시 나온다. 골프 기법 가운데 C89 의 암묵적 int 선언과 암묵적 반환형에 의존하는 항목이 있어서다. -w 는 그 대가로 쏟아지는 경고를 끄는 스위치다. 저장소는 GCC 를 쓰고 Clang 은 아니라고 적는다. 같은 소스가 모든 컴파일러에서 같은 결과를 내지 않는다는 뜻이다.

정리하면 이렇다. 1,024바이트는 특정 컴파일러와 특정 표준 아래에서, libc 가 링크된다는 전제 위에서, Python 을 닮은 문법 부분집합을 실행하는 C 소스 한 파일의 크기다. 이 조건 없이 1,024바이트로 Python 이 돈다고만 옮기면 네 군데에서 틀린다.

인터프리터가 최소한 갖춰야 하는 다섯 계층

구현의 종류와 무관하게 인터프리터는 다섯 가지 일을 한다. 각각을 극단적으로 줄이면 무엇이 남는지 먼저 짚어 두면, 뒤에 나올 목록이 그냥 나열이 아니라 지도로 읽힌다.

  • 어휘 분석 - 문자열을 의미 단위로 자른다. 극단으로 줄이면 문자 하나가 곧 토큰이 된다. 이름의 길이 상한을 1로 묶으면 이 계층이 통째로 사라진다.
  • 구문 분석 - 토큰의 배열이 문법에 맞는지 판정하고 구조를 만든다. 극단으로 줄이면 구조를 만들지 않고 읽는 즉시 계산한다. 재귀 하강 파서가 값을 반환하면 트리가 필요 없다.
  • 평가 - 구조를 실제 동작으로 바꾼다. 여기는 줄일 여지가 가장 적다. 이 계층이 없으면 그것은 인터프리터가 아니라 문법 검사기다.
  • 환경 - 이름과 값을 잇는다. 극단으로 줄이면 배열 한 개가 된다. 이름이 한 글자면 그 문자의 코드값이 곧 배열 첨자다.
  • 오류 처리 - 규칙에서 벗어난 입력을 붙잡아 알린다. 극단으로 줄이면 0바이트가 된다. 다섯 중 유일하게 완전히 없앨 수 있는 계층이다.

마지막 항목이 핵심이다. 다른 네 계층은 아무리 줄여도 무언가는 남는다. 평가가 0이면 실행이 안 되고, 환경이 0이면 변수가 없고, 구문 분석이 0이면 무엇을 계산할지 모른다. 오직 오류 처리만 완전히 0으로 갈 수 있다. 그래서 그것이 첫 번째로 간다.

재미있는 것은 반복문의 else 다. 원문의 지원 목록에는 while 과 for 에 붙는 else 가 들어 있는데, 같은 목록에 break 가 없다. Python 레퍼런스에서 else 절의 의미는 break 로 빠져나가지 않았을 때만 실행된다는 것이다. break 가 없으면 else 는 항상 실행된다. 문법은 남았고 그 문법이 존재하는 이유는 남지 않았다.

정상 경로에 기여하지 않는 계층이 먼저 간다

오류 처리는 올바른 프로그램에서 한 번도 실행되지 않는다. 지우면 정상 프로그램은 그대로 돈다. 이것이 1순위인 첫 번째 이유다.

두 번째 이유는 물리적이다. 진단의 알맹이는 문자열이고, 문자열은 예산을 그대로 먹는다. 로직은 압축할 수 있지만 메시지는 압축되지 않는다. 스물일곱 글자짜리 문구 하나면 1,024바이트 예산의 2.6퍼센트다. 예산 전체를 문구로만 채워도 서른여덟 줄이 한계다. 코드 골프의 어떤 기법도 이 벽을 넘지 못한다.

대가는 정확히 서술해야 한다. 오류 처리를 지우면 잘못된 입력에서 아무 일도 일어나지 않는 것이 아니라 무엇이든 일어날 수 있는 상태가 된다. 원문도 코드가 올바르다는 강한 가정 위에 서 있다고 적는다. 키워드 인식이 그 예다.

if (ch == 'w' || ch == 'i' || ch == 'f') {
    int keyword = ch;
    int loop_var = 0;

    if (keyword == 'f') {        /* "for K in range(N):" 형태 */
        pos += 2;                /* "or" 를 건너뛴다        */
        loop_var = next();
        pos += 8;                /* "inrange(" 를 건너뛴다  */
        vars[loop_var] = 0;
    } else if (keyword == 'w')
        pos += 4;                /* "hile" 를 건너뛴다      */
    else
        pos += 1;                /* "if" 의 "f" 를 건너뛴다 */

첫 글자만 보고 나머지는 세어서 건너뛴다. 실제로 그 자리에 for 가 적혀 있는지는 검사하지 않는다. fog 라고 써도 같은 경로로 간다. 이것이 오류 처리 0바이트의 실제 모습이다.

언어 밖에 있는 것이 그다음이다

표준 라이브러리는 문법을 바꾸지 않고 뺄 수 있다. 이것이 2순위인 이유다. MicroPython 이 자기 범위를 표준 라이브러리의 작은 부분집합을 포함한다고 적으면서도 여전히 Python 3 구현이라고 말하는 근거가 이 성질이다. 라이브러리를 줄여도 언어의 정체성은 흔들리지 않는다.

1,024바이트 판은 print 하나만 남겼다. 그것도 문자열 리터럴 하나 또는 정수식 하나만 받는 형태다. 여기서 놓치기 쉬운 것이 하나 있는데, Python 에서 print 와 range 는 키워드가 아니다. 레퍼런스가 나열하는 서른다섯 개 예약어에 둘 다 없다. 둘은 다시 묶을 수 있는 이름이다. 그런데 이름이 한 글자로 묶인 세계에서는 그 성질이 성립할 수 없다. 앞의 코드에서 보이듯 range 는 여덟 글자를 건너뛰는 고정 패턴이 되어 있다. 라이브러리 함수가 문법으로 굳었다.

같은 결과를 늦게 내는 것이 세 번째다

성능은 정확성의 관측 대상이 아니다. 느려진 프로그램은 여전히 옳은 답을 낸다. 그래서 3순위다. 여기서 잘려 나간 것은 컴파일 단계 전체다. 원문은 CPython 이 토큰화, 구문 트리 생성, 분석, 최적화, 바이트코드 방출, 해석의 순서로 일한다고 적고, 자기 구현은 그 파이프라인을 쓰지 않는다고 밝힌다.

다만 3순위라는 것이 언제나 참은 아니다. 실시간 제어에서는 성능이 1순위로 지켜지고 오히려 기능이 먼저 잘린다. 순서를 정하는 것은 계층의 성질이 아니라 제약의 종류다. 이 글의 순서는 크기가 상한일 때의 순서다.

문법이 마지막까지 남는 이유

문법이 마지막인 이유는 두 가지다.

첫째, 문법이 사라지면 그것이 무슨 언어인지 말할 근거가 사라진다. 저자가 512바이트에서 방향을 바꾼 대목이 이것을 보여 준다. 덧셈식부터 시작해 대입식을 넣고 조건문까지 넣었는데, 그 결과물이 Python 인터프리터가 아니라 계산기라는 판단이 나왔다. 계층은 다 있었다. 없는 것은 그것을 Python 이라고 부를 근거였다. 그래서 목표를 512에서 1,024로 옮겼다.

둘째, 문법은 구현 예산을 쓰지 않고 얻는 유일한 자산이다. 읽는 사람의 머릿속에 이미 설치되어 있기 때문이다. def 와 콜론과 들여쓰기를 보면 사람은 그것을 Python 으로 읽는다. 구현 쪽에서는 그 인식을 만들어 내는 데 한 바이트도 쓰지 않는다. 반대로 오류 메시지는 읽는 사람의 머릿속에 없어서 전부 바이트로 지불해야 한다.

그리고 실제로 잘린 것은 문법의 형태가 아니라 문법에 붙은 수량이었다. Python 레퍼런스는 비교를 임의로 연쇄할 수 있다고 명시한다. C 와 달리 모든 비교 연산의 우선순위가 같고, 세 값을 늘어놓은 식은 수학에서 쓰는 대로 해석된다는 조항이다. 1,024바이트 판의 지원 목록은 비교를 한 식에 최대 하나로 못 박는다. 연산자는 살아남았고 연쇄만 죽었다.

저자는 비교식 자체를 거의 뺄 뻔했다고 적는다. 근거는 참거짓 판정이 대신해 준다는 것이다. 나머지가 0인지 묻는 대신 나머지 자체를 조건에 넣으면 된다. 문법을 지우고 의미론으로 갚는 거래인데, 이 거래가 가능했던 이유는 Python 이 정수의 0을 거짓으로 취급하기 때문이다. 버릴 수 있는 문법의 범위를 정한 것은 의미론이었다.

Python 인터프리터라는 말이 덮는 범위

구현이 어느 층까지 같은지를 나누면 세 층이다. 문법, 의미론, 표준 라이브러리. 이 셋을 뭉뚱그리면 어떤 주장이든 참으로 보인다.

원문은 이 셋 가운데 문법의 외형만 주장한다. 그것도 부분집합이라고 스스로 적는다. Python 처럼 보이는 것이 목표라고 명시한 문장이 그 주장의 범위다. 저자는 이 선을 흐리지 않았다.

선이 흐려지는 것은 대개 옮기는 쪽에서다. 1,024바이트로 Python 인터프리터라는 문장은 세 층을 구분하지 않는다. 같은 함정이 다른 구현에도 있다. 어떤 도구는 문법만 같고, 어떤 도구는 의미론까지 맞추려다 호스트 언어와 충돌하며, 어떤 도구는 표준 라이브러리를 얼마나 옮겼는지가 실제 쟁점이다. 호스트 언어 위에 다른 언어를 얹는 구현이 어디에서 막히는지는 glojure 를 다룬 글에서 따로 다뤘고, 컴파일 언어에 대화형 실행을 붙일 때 해석 실행과 컴파일 실행이 갈라지는 지점은 Go 인터프리터를 다룬 글에 있다.

한 글자 변수명이 같이 지우는 것

이름을 한 글자로 묶는 결정은 겉보기에 크기 최적화다. 실제로는 의미론 변경이다.

얻는 것부터 보면 이렇다. Python 레퍼런스의 이름 규칙은 시작 문자와 이어지는 문자를 나누고 길이 상한을 두지 않는다. 그 규칙을 지키려면 이름을 읽는 반복문, 이름을 담을 버퍼, 이름을 비교하는 함수, 그리고 이름이 몇 개까지 늘어날지 모르므로 해시 테이블이나 그에 준하는 자료구조가 필요하다. 이름을 한 글자로 묶으면 그 전부가 사라진다.

char src[999];       /* 대부분의 공백을 뺀 프로그램 전체 */
int  vars[256];      /* 심볼 테이블                      */
int  pos;            /* src 에서 다음에 읽을 문자 위치    */
int  ch;             /* 지금 보고 있는 문자              */
int  line_start;     /* 현재 줄이 시작한 위치            */

심볼 테이블이 int vars[256] 한 줄이다. 조회는 문자의 코드값을 첨자로 쓰는 한 번의 배열 접근으로 끝난다. 해시 계산도, 충돌 처리도, 문자열 비교도, 메모리 할당도 없다.

그런데 같이 사라지는 것이 있다. 원문의 지원 목록은 들여쓰기 기반 블록을 적으면서 스코프 격리가 없다고 괄호로 덧붙인다. Python 실행 모델은 블록 안에서 이름이 묶이면 그 블록의 지역 변수라고 정한다. 전역 배열 하나가 전부인 세계에서는 이 조항이 성립할 수 없다. 함수 안에서 쓴 이름과 밖에서 쓴 이름이 같은 칸을 본다.

더 나아가 같은 칸에 종류가 다른 값이 들어간다. 함수 정의는 그 함수 본문의 소스 위치를 심볼 테이블에 저장한다. 즉 vars[k] 는 정수일 수도 있고 코드 위치일 수도 있다. 어느 쪽인지 구분하는 태그는 없다. 타입이 없는 것이 아니라 타입을 확인할 자리가 없는 것이다. 정수와 동일성 비교가 얽히는 자리는 CPython 에서도 사람을 놀라게 하는데, 그 이야기는 정수 캐싱을 다룬 글에 따로 정리해 두었다.

토큰도 구문 트리도 없이 - 되감아 다시 읽는 실행

구문 분석 계층을 줄이는 가장 강한 방법은 구조를 만들지 않는 것이다. 재귀 하강 파서는 원래 트리 노드를 반환하지만, 노드 대신 값을 반환하게 하면 트리 전체가 필요 없어진다.

int parse_sum(void) {
    int value = parse_term();
    while (ch == '+' || ch == '-') {
        if (ch == '+')
            value = value + parse_term();
        else
            value = value - parse_term();
    }
    return value;
}

반환형이 int다. 이 한 글자가 설계 전체를 정한다. 읽는 즉시 계산하므로 중간 표현이 없고, 중간 표현을 만들고 걷고 해제하는 코드도 전부 없다. 대신 소스 텍스트 자체가 실행 상태가 된다.

그래서 제어 흐름이 소스 위치를 옮기는 방식으로 구현된다. 컴파일 단계가 없으니 점프할 주소가 없고, 대신 pos 를 되감는다. 반복문은 조건식의 위치를 기억해 두었다가 본문 실행이 끝나면 그 자리로 돌아가 다시 파싱한다. 함수 호출은 호출 지점을 저장하고 함수 본문 위치로 뛴 다음, 본문이 끝나면 저장해 둔 자리로 복귀한다. pos 하나가 프로그램 카운터 노릇을 한다.

블록의 경계는 들여쓰기가 정한다.

void run_block(int min_indent) {
    for (;;) {
        int indent = read_indent();

        if (ch == '\n')
            continue;

        if (indent < min_indent || ch == 0) {
            pos = line_start;
            return;
        }

여기에 이 구현에서 가장 흥미로운 맞바꿈이 있다. Python 레퍼런스는 들여쓰기 처리를 스택으로 규정한다. 파일 첫 줄을 읽기 전에 0을 하나 넣고, 값은 아래에서 위로 항상 증가하며, 들여쓰기가 줄어들면 그 값은 반드시 스택에 이미 있는 값 가운데 하나여야 한다. 이 마지막 조항이 들여쓰기가 어긋난 코드를 잡아내는 규칙이다.

1,024바이트 판은 그 스택을 만들지 않는다. run_block 이 자기 자신을 재귀 호출하므로 C 의 호출 스택이 그 역할을 대신한다. 블록의 중첩 깊이와 재귀 깊이가 1대 1로 대응하니 자료구조를 따로 둘 이유가 없다. 언어가 요구하는 자료구조를 호스트 언어의 자료구조로 갚은 것이다.

그런데 스택을 버리면 그 스택이 하던 검증도 함께 사라진다. 이미 등장한 들여쓰기 값의 목록이 없으므로, 줄어든 들여쓰기가 유효한 값인지 물을 수가 없다. 어긋난 들여쓰기는 오류가 되는 대신 어딘가의 블록에 그냥 붙는다. 여기가 이 글에서 가장 일반화할 만한 관찰이다. 자료구조는 대개 검증을 겸한다. 무엇을 버릴지 정할 때 실제로 세어야 하는 것은 그 자료구조가 차지하는 바이트가 아니라, 그것이 조용히 수행하던 검사의 목록이다.

작음은 한 가지가 아니다

작다는 말은 최소 네 가지 서로 다른 축을 가리킨다. 축을 밝히지 않은 크기 수치는 비교에 쓸 수 없다.

축무엇을 재는가압박받는 자리줄이는 방법
소스 바이트사람이 읽고 감사할 양코드 골프, 초기 단계 부트 코드식별자와 공백과 구조 자체를 깎는다
바이너리 크기저장 장치와 플래시 점유임베디드 펌웨어, 컨테이너 이미지기능을 빌드에서 제외하고 링커로 걷어낸다
상주 메모리실행 중 램 사용량마이크로컨트롤러자료구조와 메모리 회수 전략을 바꾼다
의존성 수이식성과 공급망과 감사 비용샌드박스, 폐쇄망외부 라이브러리를 쓰지 않고 자립 구현한다

1,024바이트는 첫 번째 축만 잰 값이다. 그리고 libc 링크에 기대고 있으므로 두 번째 축과 네 번째 축에서는 오히려 나쁘다. 소스에서 빠진 것을 링커가 채워 준다.

다른 구현들이 자기 크기를 어떤 축으로 말하는지 보면 대비가 선명해진다.

  • MicroPython - 코드 공간 256k 와 램 16k 안에 들어가 돌아간다고 적는다. 두 번째 축과 세 번째 축을 따로 밝힌다. 마이크로컨트롤러에서는 둘이 다른 자원이기 때문이다.
  • Lua - 64비트 리눅스에서 모든 표준 라이브러리를 포함해 빌드한 인터프리터가 293K, 라이브러리가 484K 라고 적는다. 소스는 C 로 약 3만 2천 행이고, 배포 압축본은 390K 다. 소스 행수가 아니라 빌드 산출물로 크기를 말한다.
  • QuickJS - 파일 몇 개뿐이고 외부 의존성이 없으며 간단한 프로그램 하나가 x86 코드 367 KiB 라고 적는다. 크기와 의존성 수를 한 문장에 붙여 놓았다.

세 수치는 서로 비교되지 않는다. 축이 다르고 측정 조건도 다르다. Lua 의 293K 에는 플랫폼이 명시돼 있고, QuickJS 의 367 KiB 에는 아키텍처와 대상 프로그램이 붙어 있으며, MicroPython 의 256k 는 산출물 크기이지 소스 크기가 아니다. 크기 수치를 옮길 때 조건을 떼면 그 값은 거짓이 된다.

실제로 작게 만드는 자리들

작게 만드는 일이 취미가 아니라 요구 사항인 자리가 있다. 그런데 자리마다 요구하는 작음이 다르고, 그래서 버리는 순서도 뒤집힌다.

마이크로컨트롤러 - 상한은 램이다

여기서는 세 번째 축이 지배한다. 그리고 앞서 세운 순서가 정확히 한 자리에서 뒤집힌다. MicroPython 은 자기 특징으로 대화형 프롬프트, 임의 정밀도 정수, 클로저, 리스트 컴프리헨션, 제너레이터, 그리고 예외 처리를 든다. 1,024바이트 판이 가장 먼저 버린 계층을 MicroPython 은 자랑거리로 내세운다.

이유는 명확하다. 마이크로컨트롤러 위의 프로그램은 사람이 붙어 있지 않은 곳에서 돈다. 잘못된 입력이 들어왔을 때 무엇이든 일어날 수 있는 상태는 여기서 허용되지 않는다. 대신 다른 것을 깎는다. 표준 라이브러리를 작은 부분집합으로 줄인다고 스스로 밝히는 쪽이 그것이다. 온디바이스로 무엇을 올릴 때 램이 실제로 어디에서 상한을 거는지는 ESP32-S3 에서 작은 모델을 돌린 실측 글에 숫자로 정리해 두었다.

초기 단계 펌웨어 - 상한이 규격으로 못 박히는 유일한 자리

부팅의 첫 단계는 크기 상한이 규격에 적혀 있는 드문 경우다. 여기서는 순서 자체가 성립하지 않는다. 무엇을 버릴까가 아니라 무엇 하나만 남길까의 문제가 된다. 첫 단계는 자기가 일을 하지 않는다. 다음 단계를 불러올 수 있을 만큼만 하고 물러난다.

이 자리에서 배울 것은 기능을 버리는 것이 계층을 버리는 것보다 강하다는 사실이다. 계층을 깎으면 같은 일을 나쁘게 하지만, 기능을 옮기면 그 일을 아예 다른 곳에서 하게 된다. 앞의 libc 이야기와 같은 구조다.

샌드박스 - 작음은 감사할 수 있는 양이다

신뢰할 수 없는 코드를 돌리는 자리에서 작다는 말은 바이트가 아니라 읽을 수 있는 코드의 양을 뜻한다. QuickJS 가 파일 몇 개와 외부 의존성 없음을 앞에 내거는 이유가 그것이다. 공격면은 소스 크기가 아니라 의존성 그래프의 넓이로 늘어난다.

그런데 같은 페이지가 ES2025 를 거의 완전히 지원하고 표준 테스트 모음의 거의 100퍼센트를 통과한다고도 적는다. 즉 여기서는 문법도 의미론도 버리지 않는다. 버리는 것은 네 번째 축, 의존성뿐이다. 신뢰할 수 없는 코드를 받는 자리에서 언어 사양을 부분집합으로 줄이면, 그 부분집합의 경계 자체가 새로운 취약점이 된다.

교육 - 작음은 한 사람이 따라갈 수 있는 양이다

가르치기 위한 구현에서 작다는 것은 하루에 읽어 낼 수 있는 분량을 뜻한다. 여기서 버리는 것은 성능과 최적화다. 반대로 가장 크게 남기는 것이 단계의 이름이다. 어휘 분석과 구문 분석과 평가가 각각 눈에 보여야 한다.

대비가 극적이다. 코드 골프는 토큰과 구문 트리를 가장 먼저 지웠고, 교육용 구현은 바로 그 둘을 가장 크게 남긴다. 같은 작게 만들기인데 정반대로 간다. 목적이 축을 정하고, 축이 순서를 정한다.

코드 골프와 최소 구현은 다른 작업이다

원문에 나오는 바이트 절약 기법은 이렇다.

  • 변수와 함수 이름을 한 글자로 줄인다
  • 컴파일러가 libc 를 링크해 준다는 사실에 기댄다
  • 임시 변수 대신 전역 변수를 쓴다
  • 전역 변수가 0으로 초기화된다는 성질을 이용한다
  • C89 의 암묵적 int 선언과 암묵적 반환형을 쓴다
  • 함수 매개변수를 스택에 보존되는 임시 변수로 쓴다
  • 문자 리터럴 대신 아스키 값을 직접 적는다
  • 삼항 연산자와 쉼표 연산자를 쓴다
  • 논리 연산을 비트 연산으로 바꾼다

이 아홉 가지에 공통점이 있다. 어느 것도 언어의 동작을 바꾸지 않는다. 전부 표기 수준의 변환이다. 그래서 4,800바이트 판과 1,024바이트 판은 같은 언어를 구현한다.

/* 줄 끝까지 건너뛰는 함수 - 읽을 수 있는 판 */
void skip_to_eol(void) {
  if (ch != 0 && ch != '\n') {
    next();
    skip_to_eol();
  }
}

/* 같은 함수의 골프 판 */
Y(){c&&c-10&&Y(G());}

/* 앞에 나온 parse_sum 의 골프 판 */
e(){for(z=t();c-43u<3;)y=44-c,z+=y*t();return z;}

반면 한 글자 변수명, 오류 처리 없음, 스코프 격리 없음은 골프가 아니다. 설계 결정이다. 표기를 아무리 바꿔도 이 셋은 줄어들지 않는다.

구분하는 방법은 간단하다. 되돌렸을 때 동작이 달라지는가. 달라지지 않으면 골프이고, 달라지면 설계다. 4,800에서 1,024로 간 것은 골프이고, Python 에서 Python 을 닮은 것으로 간 것은 설계다. 두 작업을 한 이름으로 부르면 어느 쪽 교훈도 남지 않는다.

그리고 골프에는 빌드 조건이라는 숨은 비용이 붙는다. C89 의 암묵적 int 에 기대려면 표준을 되돌려야 하고, 그러면 경고가 쏟아지므로 경고를 꺼야 하고, 그 조합이 통하는 컴파일러가 제한된다. 저장소가 GCC 를 쓰고 Clang 은 아니라고 적는 이유다. 크기 수치를 옮길 때 이 조건을 떼면 재현되지 않는다. 컴파일러 뒷단을 바꿀 때 어떤 청구서가 새로 생기는지는 LLVM 기반 Go 컴파일러를 다룬 글에서 다른 각도로 짚었다.

자기 코드에서 없어도 되는 것을 찾는 순서

여기까지의 순서를 자기 코드에 옮기면 이렇게 된다. 기법의 목록이 아니라 질문의 순서다.

순위후보판별 질문되돌리는 비용
1진단과 로깅과 통계지워도 정상 경로의 결과가 같은가낮음, 다시 켜면 된다
2아무도 호출하지 않는 기능지원 목록과 호출 기록이 일치하는가낮음, 다시 넣으면 된다
3같은 결과를 빠르게 내는 경로느려져도 답이 같은가중간, 시간은 되돌릴 수 있다
4이름과 구조와 일반화규모가 커져도 버티는가높음, 읽는 사람의 시간을 쓴다
5인터페이스와 계약이것이 없어도 같은 것인가매우 높음, 정체성이다

실무에서 이 순서를 그대로 쓸 때 붙는 단서가 세 개 있다.

  • 1순위는 지우는 것이 아니라 끌 수 있게 만드는 것이다. 1,024바이트 판은 오류 처리를 아예 없앴지만, 그것이 성립하는 이유는 입력이 저자 자신의 파일 하나이기 때문이다. 남이 쓰는 코드에서 같은 결정을 하면 골프가 아니라 사고다.
  • 2순위의 판별은 문서가 아니라 기록으로 한다. 지원 목록은 대개 실제보다 넓다. 호출 기록과 대조해야 무엇이 죽은 기능인지 갈린다.
  • 4순위부터는 되돌리는 비용이 급격히 오른다. 이름을 줄이면 당장은 줄지만, 그 코드를 다시 읽는 사람의 시간으로 지불하게 된다. 그 지불이 한 번으로 끝나지 않는다는 점이 골프와 제품 코드의 차이다.

그리고 순서를 정하기 전에 먼저 적어야 할 것이 있다. 같이 딸려 나가는 것의 목록이다. 들여쓰기 스택을 지우면 들여쓰기 검증이 함께 사라지고, 심볼 테이블을 배열로 바꾸면 스코프가 함께 사라지고, 중간 표현을 지우면 정적 분석 가능성이 함께 사라진다. 세 경우 모두 지워진 것은 자료구조 한 개인데 잃은 것은 두 개다. 바이트를 세기 전에 그 자료구조가 조용히 하던 일을 세는 편이 낫다.

마지막으로 순서를 뒤집는 조건이다. 상한이 무엇으로 걸렸는지가 정한다. 램이면 자료구조부터, 감사 대상이면 의존성부터, 규격이면 기능부터 손댄다. 크기가 상한일 때만 이 글의 순서가 그대로 성립한다.

확인하지 못한 것

  • 컴파일된 실행 파일의 크기 - 원문에도 저장소에도 없다. 1,024는 소스 크기이며, 실행 파일 크기는 컴파일러와 플랫폼과 링크 방식에 따라 달라진다. 이 글에서 바이너리 크기를 말하지 않은 이유다.
  • 크기 확인 명령의 정확한 판정 - 저장소는 wc 로 크기를 보라고 적는다. 이 명령은 행과 단어와 바이트 세 값을 함께 내므로, 1,024가 그중 어느 값인지는 명령만으로 단정되지 않는다. 본문은 원문이 밝힌 바이트 수를 그대로 옮겼다.
  • gcc-16 이 가리키는 정확한 설치본 - 어느 배포판의 어떤 패키지인지, 다른 버전에서도 같은 결과가 나오는지는 저장소가 적지 않는다.
  • 주석 문법 - 지원 목록에 주석 지원이 들어 있으나, 그것이 Python 레퍼런스가 정하는 해시 기호 규칙과 같은 형태인지는 원문 서술만으로 갈리지 않는다.
  • CPython 파이프라인의 공식 서술 - 파이썬 개발자 안내서의 컴파일러 문서는 두 차례 요청에서 모두 리다이렉트 안내만 돌아왔다. 본문의 CPython 단계 서술은 원문 저자가 쓴 표현을 옮긴 것이며, 언어 규칙에 관한 서술은 전부 공식 언어 레퍼런스와 표준 라이브러리 문서에서 가져왔다.
  • 실행 속도 수치 - 되감아 다시 파싱하는 방식이 실제로 얼마나 느린지에 대한 측정값은 원문에 없다. 반복마다 다시 파싱한다는 구조적 사실만 서술했다.
  • 부팅 첫 단계의 규격상 크기 상한 - 널리 인용되는 수치가 있으나 규격 원문을 대조하지 않았으므로 숫자를 쓰지 않았다.
