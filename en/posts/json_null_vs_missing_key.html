Introduction - one field was edited and the others disappeared

A client sends {"bio":"new"} in a PATCH to change only the bio of a profile, and the response no longer contains name or nickname. The server code is an ordinary body.get(...). The root of the accident is that the server read "the key is absent" and "the value is null" as one state. In a JSON document the two states are different text: one has "x":null written in it, the other has no name x at all. Yet the read APIs of many languages return the same value for both by default.

The terms are fixed first. "null" is the JSON literal null. "Missing key" means the object has no member with that name. undefined is a JavaScript value and does not exist in the JSON grammar. The three expressions are {"x":null}, {}, and what JavaScript produces when it serializes {x: undefined}. The sections below show how Python, Node and PowerShell read and write these three, and which state change each one causes in a PATCH, using requests sent to a live local server.

The questions covered are the following.

  • How do the JSON grammar and RFC 7396 define null and a missing key?
  • Do Python dict.get, Node d.x and PowerShell $o.x tell the two states apart?
  • How is it reproduced that a get pattern which cannot tell them apart erases values in a PATCH?
  • What are the safe patterns that do tell them apart, and how does the output change?
  • Which values in which tools lose their key at the serialization step?

What the documents define - the JSON grammar, Merge Patch, language docs

The sentences that serve as the basis come first. The English sentences in the list below are verbatim.

  • RFC 8259 section 3: A JSON value MUST be an object, array, number, or string, or one of the following three literal names: false, null, true. undefined is not in the list of values.
  • RFC 8259 section 4: The names within an object SHOULD be unique. An object is a set of name/value pairs, and a member with no name is not in the object.
  • RFC 7396 introduction: Null values in the merge patch are given special meaning to indicate the removal of existing values in the target. A null inside a patch is a removal instruction, not a value.
  • RFC 7396 section 1: ...do not make use of explicit null values. The merge patch format is not appropriate for all JSON syntaxes. The RFC itself says the format does not fit documents that use explicit null as a value.
  • Python documentation for dict.get: If default is not given, it defaults to None, so that this method never raises a KeyError. The return value alone cannot separate an absent key from a key whose value is None.
  • MDN in operator: A property may be present in an object but have value undefined. Therefore, "x" in obj is not the same as obj.x !== undefined.

The pseudo-code in RFC 7396 (section 2) reduces to one line. If the value of a member in the patch is null, the name is removed from the target when it exists there; otherwise the value is merged recursively. A member whose name is not in the patch is never visited, so it stays in the target as it was. "null removes, missing changes nothing" is the whole of the format, which means that a server unable to tell the two states apart cannot implement it.

Python - the default of get applies only when the key is absent

import json

                              '| get("x", 0):', repr(d.get('x', 0)), '| "x" in d:', 'x' in d)
                    
                    # Python has no undefined; None is serialized as null and the key stays
                    print(json.dumps({'x': None}), json.dumps({}))
                    
                    MISSING = object()  # sentinel: a value no JSON document can contain
                    
                    def classify(d, key):
                        v = d.get(key, MISSING)
                        if v is MISSING:
                            return 'missing'
                        return 'null' if v is None else 'value'
                    
                    for text in ['{"x": null}', '{}', '{"x": 0}', '{"x": ""}']:
                        print(text.ljust(11), '->', classify(json.loads(text), 'x'))

d.get("x") is None for both documents. The difference shows up in the default argument. d.get("x", 0) returns 0 only when the key is absent and returns None unchanged for a key whose value is null. The default is the value for "when the key is missing", not for "when the value is empty". "x" in d answers only whether the key exists, so it splits into True and False for the two documents.

json.dumps({"x": None}) produces {"x": null}. Python has no undefined, so "empty" is always None, and the key stays as null after serialization. To produce a missing key, the key must be left out of the dict or deleted from it. classify, which uses the sentinel MISSING = object() as the default, sorts the four inputs into null, missing, value and value. An empty string and 0 are values, not null.

In objects built by JSON.parse, d.x is null for {"x": null} and undefined for {}. Node therefore separates the two states by value already at read time: d.x === undefined means a missing key, d.x === null means null. in and Object.hasOwn answer whether the key itself exists and split into true and false for the two documents.

The distinction disappears in default-value syntax. The default in destructuring, { x = "DEFAULT" }, applies only to undefined, so it returns DEFAULT for {} and {x: undefined} and null for {x: null}. ??, in contrast, replaces both null and undefined with the default and merges the two states into one. Two syntaxes with the same "default" name differ in whether they separate or merge.

The PATCH endpoint - a 127.0.0.1 server implementing RFC 7396 semantics

One server hosts three handlers. /naive deletes a field when body.get returns None, /skipnull skips the field when it is None, and /merge uses merge_patch, a direct transcription of the RFC 7396 pseudo-code. The state is a dict in memory and POST /reset restores it. All files were created only inside a temporary folder, the socket is opened on the loopback (127.0.0.1) only, and a safety timer makes the process exit by itself after 180 seconds.

import json, os, sys, threading
                    from http.server import BaseHTTPRequestHandler, HTTPServer
                    
                    INITIAL = {'name': 'kim', 'nickname': 'kk', 'bio': 'hello'}
                    FIELDS = ['name', 'nickname', 'bio']
                    STATE = {'naive': dict(INITIAL), 'skipnull': dict(INITIAL), 'merge': dict(INITIAL)}
                    
                    
                    def apply_naive(user, body):
                        # get() returns None for a missing key and for an explicit null alike
                        for k in FIELDS:
                            v = body.get(k)
                            if v is None:
                                user.pop(k, None)
                            else:
                                user[k] = v
                    
                    
                    def apply_skipnull(user, body):
                        for k in FIELDS:
                            v = body.get(k)
                            if v is not None:
                                user[k] = v
                    
                    
                    def merge_patch(target, patch):
                        # the MergePatch pseudo-code of RFC 7396 section 2
                        if isinstance(patch, dict):
                            if not isinstance(target, dict):
                                target = {}
                            for name, value in patch.items():
                                if value is None:
                                    if name in target:
                                        del target[name]
                                else:
                                    target[name] = merge_patch(target.get(name), value)
                            return target
                        return patch
                    
                    
                    class H(BaseHTTPRequestHandler):
                        def log_message(self, *a):
                            pass
                    
                        def _send(self, code, obj):
                            raw = json.dumps(obj, sort_keys=True).encode()
                            self.send_response(code)
                            self.send_header('Content-Type', 'application/json')
                            self.send_header('Content-Length', str(len(raw)))
                            self.end_headers()
                            self.wfile.write(raw)
                    
                        def _which(self):
                            first = self.path.strip('/').split('/')[0]
                            return first if first in STATE else None
                    
                        def do_GET(self):
                            w = self._which()
                            self._send(200, STATE[w]) if w else self._send(404, {'error': 'unknown path'})
                    
                        def do_POST(self):
                            if self.path != '/reset':
                                return self._send(404, {'error': 'unknown path'})
                            for k in STATE:
                                STATE[k] = dict(INITIAL)
                            self._send(200, {'reset': True})
                    
                        def do_PATCH(self):
                            w = self._which()
                            if w is None:
                                return self._send(404, {'error': 'unknown path'})
                            body = json.loads(self.rfile.read(int(self.headers.get('Content-Length', 0))))
                            if w == 'naive':
                                apply_naive(STATE[w], body)
                            elif w == 'skipnull':
                                apply_skipnull(STATE[w], body)
                            else:
                                STATE[w] = merge_patch(STATE[w], body)
                            self._send(200, STATE[w])
                    
                    
                    if __name__ == '__main__':
                        srv = HTTPServer(('127.0.0.1', int(sys.argv[1])), H)  # loopback only
                        print('pid', os.getpid(), 'listening on 127.0.0.1:' + sys.argv[1], flush=True)
                        t = threading.Timer(180, lambda: os._exit(0))  # safety: exit by itself after 180 s
                        t.daemon = True
                        t.start()
                        srv.serve_forever()

The client is curl. The same three requests go to the three handlers in turn: {"bio":"new"}, which changes one field; {"nickname":null}, which deletes one field; and {}, which changes nothing. Before each request the state is reset to the initial values (name=kim, nickname=kk, bio=hello).

Sending {"bio":"new"} to /naive returns just {"bio": "new"}. name and nickname, which were not in the request, are gone. The handler walks the field list and reads body.get(k); a name missing from the request becomes None, and None is treated as a deletion. The code and the output above show this directly. Sending {} also returns {}: a request that changes nothing deletes every field.

/skipnull shows the opposite error. It is safe for a missing key, but nickname stays kk even after {"nickname":null} is sent. The request to delete is silently ignored. Only /merge behaves as intended for all three requests: only bio changes, only nickname disappears, and {} changes nothing. For nested objects too, {"extra":{"a":null,"b":2}} removes only a inside extra.

Safe patterns that tell them apart - sentinel, in, object spread

The merge_patch of the previous section tells them apart with name in target and for name, value in patch.items(). Iterating over the patch object by name visits only the keys in the request, so a missing key cannot be touched. The rule is a single one: ask in (or iterate) about the existence of the key, and only then ask whether the value is null. Existence is not inferred from the value.

A sentinel puts, in the default slot, a value that JSON can never produce. A Python object() cannot come out of any JSON document, so when d.get(key, MISSING) returns MISSING the key is absent. Object defaults show up in spread syntax. Below is code that lays the request body over a defaults object, with its output; Python's {**defaults, **body} works the same way.

const defaults = { name: 'kim', nickname: 'kk' };
                    console.log(JSON.stringify({ ...defaults, ...JSON.parse('{}') }));
                    console.log(JSON.stringify({ ...defaults, ...JSON.parse('{"nickname": null}') }));
                    const undef = { ...defaults, ...{ nickname: undefined } };
                    console.log(undef, 'nickname' in undef, JSON.stringify(undef));
{"name":"kim","nickname":"kk"}
                    {"name":"kim","nickname":null}
                    { name: 'kim', nickname: undefined } true {"name":"kim"}
import json
                    defaults = {'name': 'kim', 'nickname': 'kk'}
                    print({**defaults, **json.loads('{}')})
                    print({**defaults, **json.loads('{"nickname": null}')})
                    print(json.dumps({**defaults, **{'nickname': None}}))
{'name': 'kim', 'nickname': 'kk'}
                    {'name': 'kim', 'nickname': None}
                    {"name": "kim", "nickname": null}

Laying {} over the defaults keeps the defaults, and laying {"nickname": null} turns nickname into null, so the distinction is preserved. In JavaScript, however, laying {nickname: undefined} overwrites the default kk with undefined, and after serialization nickname disappears altogether, leaving {"name":"kim"}. Spread overwrites by the presence of the key, and the line where in prints true shows exactly that.

  • Sentinel: put a value JSON cannot produce in the default slot, as in get(key, MISSING).
  • in, Object.hasOwn, the property list: ask for the existence of the key before reading the value.
  • Iterating the patch object: only names in the request are visited, so absent names are never targets of a change.
  • Object defaults plus spread: a missing key leaves the default, but a JavaScript undefined value counts as a present key and overwrites it.

The MDN documentation of JSON.stringify says: undefined, Function, and Symbol values are not valid JSON values. If any such values are encountered during conversion, they are either omitted (when found in an object) or changed to null (when found in an array). The output shows exactly that. x: undefined in an object disappears together with its key, while undefined and a function in an array become null. A top-level undefined returns the value undefined rather than JSON text. The Object.assign result on the last line is { x: undefined } with the key still present, yet its serialization is {}.

What this difference becomes in a PATCH is checked by sending the bodies the three tools produced straight to /merge on the same server. All three tools were coded with the same intent, to clear nickname.

From symptom to cause - an inspection order and neighbouring posts

The earlier outputs give a mapping from symptom to cause. The inspection narrows down one step per symptom.

  • Editing one field erases others: check whether the server handler uses the None of get as a deletion (the symptom of /naive).
  • A request to clear a value is ignored: check whether null is handled as skip (the symptom of /skipnull).
  • A delete request from a JavaScript client does nothing on the server: check whether the body holds undefined and whether the key is in the JSON.stringify result.
  • A field must store null as a value: in the RFC 7396 pseudo-code null always means removal, so that field cannot be expressed with Merge Patch. Use another format or an explicit value per field.
  • A request changes only part of an array: in the pseudo-code a non-object patch replaces the whole target, so the array is sent in full.

Neighbouring topics are covered elsewhere. How a document with the same name twice is read by each parser is in the JSON duplicate keys post, and what happens to large integers passing through JSON is in the JSON number precision post. How SQL NULL changes comparisons is in the NOT IN and NULL post, and the operators for partially updating a JSONB column are in the PostgreSQL JSONB post. The idiom of using None as a sentinel for default arguments connects to the Python mutable default argument post. The scope here is null and missing keys inside a JSON document, and the meaning of PATCH.

What could not be confirmed

  • How JSON libraries of other languages such as Go, Java or Rust read the two states. Only Python, Node and PowerShell 5.1 were run on this PC.
  • How ConvertFrom-Json reads the two states in PowerShell 7 (pwsh). pwsh is not installed on this PC.
  • A run comparing against RFC 6902 (JSON Patch). Only RFC 7396 is treated in the body.
  • Server behavior when the PATCH body is not an object (array, string). The RFC pseudo-code replaces the whole target, but that path of this server was not run.
  • PATCH bodies with duplicate keys, and bodies carrying large integers or decimals. These are topics of the neighbouring posts.
  • How production web frameworks (Django REST framework, Express and others) interpret a PATCH body. Only the small server built here was run.
  • Output on Linux or macOS. All output here came from Windows 10.
