git worktree 실무 가이드 - 한 저장소를 여러 폴더에 펼치기

한 저장소를 여러 폴더에 동시에 펼치기 - 무엇이 공유되고, 무엇이 막히고, 어떻게 치우나

2026-09-29 개발/인프라

개발 도중 다른 브랜치의 긴급 버그를 수정해야 할 때 가장 흔히 쓰는 방법은 현재 작업을 git stash 로 임시 보관하고 브랜치를 바꾸는 것이다. 하지만 빌드 캐시가 날아가거나 수많은 의존성 모듈을 다시 설치해야 하는 프로젝트에서는 브랜치를 한 번 전환하는 것 자체가 적지 않은 시간을 소모한다. 그렇다고 같은 저장소를 별도의 디렉터리에 통째로 다시 git clone 하자니 큰 저장소라면 객체 데이터베이스가 중복으로 디스크를 차지한다.

git worktree 는 이 간극을 해결하는 핵심 기능이다. 하나의 .git 저장소를 그대로 공유하면서, 서로 다른 브랜치를 디스크의 서로 다른 디렉터리에 동시에 체크아웃하여 나란히 작업할 수 있게 해준다. 그러나 편리함 뒤에는 분명한 경계가 존재한다. 어느 범위까지 설정과 임시 작업이 공유되는지, 동일 브랜치를 건드릴 때 어떤 차단 장치가 작동하는지, 그리고 작업이 끝난 폴더를 어떻게 정리해야 참조가 꼬이지 않는지 정확히 알지 못하면 치명적인 충돌에 부딪힌다.

이 글은 브랜치 전략의 이론을 설명하지 않는다. 독립된 테스트 저장소에서 명령어를 직접 실행하고 발생한 콘솔 출력을 토대로, 한 저장소를 여러 폴더에 펼쳤을 때 무엇이 공유되고 무엇이 막히며 어떻게 정리해야 하는가를 실측 데이터 중심으로 다룬다. 앞서 다룬 브랜치 흐름의 기초는 Git 브랜치 협업 가이드를, 변경 사항의 복원 절차는 git 되돌리기 결정표를 함께 참고하기 바란다.

1. 배경과 전제 - 한 저장소를 여러 폴더에 펼친다는 것

1.1 왜 브랜치 전환 대신 워크트리인가

전통적인 단일 작업 디렉터리 환경에서는 한 번에 하나의 브랜치만 체크아웃할 수 있다. 기능 개발 브랜치에서 긴급 핫픽스 브랜치로 넘어가려면 변경 중인 파일을 커밋하거나 스태시에 넣어야 하고, 브랜치를 오가면 바뀐 파일이 다시 쓰여 빌드를 다시 해야 할 수도 있다.

반면 git worktree 를 사용하면 기존 작업 공간을 건드리지 않고 옆 디렉터리에 원하는 브랜치를 즉시 펼칠 수 있다. 저장소 복제(clone)와 비교할 때 다음과 같은 명확한 이점을 가진다.

  • 디스크 용량 절감: 전체 커밋 히스토리와 블롭 데이터를 담은 .git 저장소는 하나만 유지되므로 중복 복제가 발생하지 않는다.
  • 즉각적인 브랜치 공유: 한 폴더에서 커밋을 생성하면 다른 워크트리 폴더에서도 별도의 push나 pull 없이 즉시 해당 커밋을 참조할 수 있다.
  • 작업 파일 보존: p1의 작업 파일은 그대로 둔 채 옆 폴더에서 핫픽스를 고칠 수 있었다(7.1).

1.2 검증 환경과 명령 표기 기준

실습을 위해 메인 브랜치와 초기 커밋(c54568b init)이 존재하는 테스트 저장소 p 를 생성하고, 사전 점검용으로 hotfix 브랜치를 미리 분기해 두었다. 모든 명령은 일반 독자가 터미널에서 사용하는 표준 문법을 기준으로 기술하였다.

Windows 환경에서 디렉터리 경로 길이가 극단적으로 길어질 경우 git 내부 프로세스가 파일 시스템 접근에 실패하는 현상이 관찰되었다. 따라서 안정적인 워크트리 운영을 위해서는 저장소 기준 경로를 가급적 짧은 깊이에 배치하는 것이 권장된다.

2. 심장 - worktree add, list와 .git 파일의 정체

2.1 새 브랜치와 기존 브랜치 꺼내기

워크트리를 추가하는 기본 명령은 git worktree add 다. 새로운 브랜치를 생성하면서 동시에 펼치려면 -b 옵션을 지정하고, 기존에 이미 존재하는 브랜치를 꺼내려면 디렉터리 경로 뒤에 브랜치명을 전달한다.

git branch hotfix
git worktree add -b feature …/tech_lab/p1
git worktree add …/tech_lab/p2 hotfix
git worktree list

위 명령을 실행했을 때 출력된 실제 결과는 다음과 같다.

Preparing worktree (new branch 'feature')
HEAD is now at c54568b init
Preparing worktree (checking out 'hotfix')
HEAD is now at c54568b init
…/tech_lab/p  c54568b [main]
…/tech_lab/p1 c54568b [feature]
…/tech_lab/p2 c54568b [hotfix]

git worktree list 를 확인하면 메인 저장소 p 는 main 브랜치를, 새로 생성된 p1 과 p2 디렉터리는 각각 feature 와 hotfix 브랜치를 물고 있는 것을 볼 수 있다. 한 저장소에서 세 개의 서로 다른 브랜치가 파일 시스템 상에 독립된 작업 공간으로 동시에 공존하는 상태가 완성된다.

2.2 워크트리의 .git은 폴더가 아니라 파일이다

새로 생성된 워크트리 폴더 내부 구조를 살펴보면 일반 저장소와의 결정적인 차이가 드러난다. 메인 저장소의 .git 은 실제 디렉터리이지만, 연결된 워크트리의 .git 은 작은 텍스트 파일이다.

ls -ld p/.git p1/.git
cat p1/.git
ls p/.git/worktrees/p1
cat p/.git/worktrees/p1/commondir

명령 실행 결과는 다음과 같다.

drwxr-xr-x 1 …   0 Sep 29 07:48 p/.git
-rw-r--r-- 1 … 257 Sep 29 07:48 p1/.git
gitdir: …/tech_lab/p/.git/worktrees/p1
HEAD
ORIG_HEAD
commondir
gitdir
index
logs
refs
../..

출력에서 확인되듯 p1/.git 은 파일 크기가 257바이트에 불과한 일반 파일이며, 내부에는 메인 저장소 내부의 관리 폴더인 gitdir: …/tech_lab/p/.git/worktrees/p1 경로가 적혀 있다. 또한 메인 저장소의 해당 디렉터리를 열어보면 다음과 같은 구조적 특성이 관찰된다.

  • 독립 메타데이터: 각 워크트리는 고유한 HEAD, index(스테이징 영역), logs(참조 기록)를 메인 저장소 내부의 하위 디렉터리에 격리하여 보관한다.
  • 공통 디렉터리 연결: commondir 파일에 기록된 ../.. 상대 경로를 통해 메인 저장소의 루트 .git 을 가리킨다.
  • 공유되는 부분: rev-parse --git-path 로 보면 hooks·config·refs/stash 는 메인 .git 경로를 가리켰다(4장).

3. 충돌 방지 장치 - 같은 브랜치 중복 체크아웃 차단

3.1 이미 열려 있는 브랜치를 꺼내려 할 때의 fatal 오류

만약 다른 워크트리가 이미 체크아웃하여 작업 중인 브랜치를 또 다른 폴더에서 다시 꺼내려 하면 어떤 일이 일어나는가? 실제로 feature 브랜치를 물고 있는 p1 이 존재하는 상태에서 p3 폴더에 동일한 feature 브랜치를 추가해 보았다.

git worktree add …/tech_lab/p3 feature

git 은 다음 fatal 오류를 내고 멈췄다(exit=128).

Preparing worktree (checking out 'feature')
fatal: 'feature' is already used by worktree at '…/tech_lab/p1'

문서도 기본적으로 add 는 브랜치가 이미 다른 워크트리에 체크아웃되어 있으면 새 워크트리 만들기를 거부한다고 적는다.

3.2 메인 작업트리에서의 switch 차단과 -f 강제 옵션의 위험

이 거부는 워크트리를 만들 때만이 아니다. 메인 작업 트리에서 git checkout feature 를 실행해도 같은 fatal: 'feature' is already used by worktree at '…/tech_lab/p1' 로 거부됐다(exit=128). 다른 실험 저장소에서는 메인 쪽 git switch hotfix 도 같은 형식의 오류를 냈다.

-f(강제) 옵션을 주면 사정이 다르다. git worktree add -f …/tech_lab/p3 feature 는 경고 없이 Preparing worktree (checking out 'feature')·HEAD is now at c54568b init 을 출력했고, git worktree list 에서 p1 과 p3 가 모두 [feature] 로 나왔다.

  • 막는 장치를 끄는 것: -f 는 같은 브랜치 중복을 막는 장치를 끈다. 문서도 이 옵션이 그런 안전장치를 무시한다고 적는다.
  • 정리: 이렇게 만든 p3 는 깨끗한 상태여서 git worktree remove …/tech_lab/p3 가 메시지 없이 끝났다(exit=0).
  • 올바른 대안: 동일 브랜치를 중복으로 꺼내지 말고, 목적에 맞는 별도의 파생 브랜치(-b)를 생성하여 작업해야 한다.

4. 공유 범위 실측 - 무엇이 공유되고 무엇이 격리되나

4.1 커밋·stash·설정의 공유 범위 대조표

워크트리 환경을 운용할 때 가장 혼란스러운 부분은 리소스의 공유 경계다. 실제 실험을 통해 커밋, stash, config, hook 과 HEAD·index 경로를 하나씩 확인했다.

워크트리 p1 에서 파일을 수정하고 커밋하자 메인 저장소의 git log --oneline --all --graph 에 99a62e7 feature work 가 바로 나타났다. 반면 rev-parse --git-path 로 보면 HEAD·index·logs/HEAD 는 worktrees/p1/… 아래의 워크트리별 경로를 가리켰다.

항목 공유 여부 실측 근거(명령 및 확인 결과)
커밋 및 브랜치 공유 p1 커밋이 메인 log --all 에 즉시 노출됨
stash 목록 공유 (단일 레퍼런스) p1 에서 생성한 stash 가 메인 및 p2 의 stash list 에 표시됨
기본 git config 공유 p2 에서 config lab.flag fromN2 설정 시 메인에서 조회 가능
git config --worktree 워크트리별 격리 extensions.worktreeConfig true 활성화 시 독립 설정 파일에 기록
hooks 스크립트 공유 메인 .git/hooks/post-commit 이 p1, p2 커밋 시 모두 실행됨
HEAD / index / logs 워크트리별 격리 rev-parse --git-path 확인 시 각 워크트리 전용 경로 반환

4.2 stash가 하나라는 함정과 다른 브랜치 적용 충돌

실측에서 가장 주의해야 할 지점으로 드러난 것은 stash 저장소가 하나라는 사실이다. 워크트리 p1 에서 git stash push -m "wip-in-p1" 을 실행했을 때, 메인 저장소와 p2(hotfix 브랜치)에서 각각 git stash list 를 조회한 결과는 다음과 같았다.

Saved working directory and index state On feature: wip-in-p1
stash@{0}: On feature: wip-in-p1          # 메인 저장소 확인
stash@{0}: On feature: wip-in-p1          # p2(hotfix) 워크트리 확인

이 stash 를 다른 브랜치(hotfix) 워크트리에서 적용하면 어떻게 되는지도 따로 실험했다. 결과는 다음과 같이 충돌이었다.

Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
On branch hotfix
…
exit=1
  • 단일 stash 공간: 스태시 스택은 워크트리 단위로 분리되지 않으며 저장소 전체가 공유한다.
  • 브랜치 라벨 점검 필수: git stash list 출력에서 On feature: ... 처럼 대상 브랜치 명칭을 반드시 확인하고 복원해야 한다.
  • 워크트리 삭제 후 보존: 워크트리 디렉터리를 제거하더라도 해당 트리에서 생성해 둔 stash 는 사라지지 않고 보존된다.

4.3 워크트리 전용 설정 --worktree 와 hooks 실행 위치

기본적으로 git config 로 추가한 설정값은 메인 저장소의 .git/config 에 저장되어 모든 워크트리에 공유된다. 만약 특정 워크트리에서만 다른 설정을 적용하고 싶다면 extensions.worktreeConfig 기능을 활성화해야 한다.

git config --worktree lab.only fromP2
# 실패: extensions.worktreeConfig 가 필요하다는 fatal 에러 발생
git config extensions.worktreeConfig true
git config --worktree lab.only fromP2

기능을 켠 뒤 --worktree 로 넣은 값은 메인 .git/worktrees/p2/config.worktree 파일에 기록됐고, p2 에서는 fromP2 가 읽혔지만 메인과 p1 에서는 조회되지 않았다(exit=1).

반면 커밋 검증 등을 담당하는 .git/hooks 는 저장소 전체에 하나만 존재한다. .git/hooks/post-commit 스크립트를 작성한 뒤 각 워크트리에서 커밋을 실행한 결과, 훅 스크립트는 호출된 해당 워크트리의 작업 디렉터리를 현재 작업 경로(pwd)로 인식하며 정상 실행되었다.

  • 중앙 집중식 훅 관리: 커밋 린트나 테스트 훅을 각 워크트리마다 중복 설치할 필요가 없다.
  • 실행 컨텍스트 주의: 훅 스크립트 내부에서 상대 경로를 다룰 때는 훅이 메인이 아닌 각 워크트리 폴더에서 발화될 수 있음을 고려해야 한다.
  • 워크트리별 설정은 켜야 된다: extensions.worktreeConfig 없이 --worktree 를 쓰면 fatal(exit=128)로 거부됐다.

5. 정리하기 - worktree remove 거부와 prune의 필요성

5.1 변경 사항이나 미추적 파일이 있을 때의 삭제 거부

작업이 끝난 워크트리를 제거할 때는 git worktree remove 명령을 사용한다. 이때 해당 디렉터리에 커밋되지 않은 파일 변경이 있거나, 아직 추적되지 않는 새 파일(untracked file)이 단 하나라도 남아 있으면 git 은 작업을 즉시 거부한다.

# 파일 수정 후 제거 시도
git worktree remove …/tech_lab/p2
# 출력: fatal: '…\tech_lab\p2' contains modified or untracked files, use --force to delete it

# 수정 파일을 stash 에 넣고 새 파일(untracked.txt)만 남겨둔 상태에서 시도
git worktree remove …/tech_lab/p2
# 출력: fatal: '…\tech_lab\p2' contains modified or untracked files, use --force to delete it

실측에서 확인된 바와 같이, ?? untracked.txt 처럼 새로 생성된 미추적 파일이 하나만 존재해도 동일한 fatal 메시지가 반환된다. 문서도 추적 안 하는 파일도, 수정도 없는 깨끗한 워크트리만 지울 수 있다고 적는다. 완전히 버려도 무방한 작업이라면 --force 옵션을 부여하여 강제로 폴더를 지울 수 있다.

  • 정상 제거 조건: 작업 트리가 완벽하게 깨끗한 상태(clean)여야 추가 옵션 없이 삭제된다.
  • 강제 삭제: --force 를 주자 수정 파일·새 파일과 함께 폴더가 지워졌다(ls: cannot access 'p2': No such file or directory).
  • 브랜치는 남는다: 워크트리 디렉터리가 삭제되더라도 해당 브랜치(hotfix)와 스태시는 저장소에 그대로 유지된다.

5.2 폴더를 손으로 지웠을 때 발생하는 prunable 상태와 브랜치 잠김

git worktree remove 대신 파일 탐색기나 rm -rf 로 워크트리 폴더를 직접 지우면 어떻게 되는지 보았다. p4 워크트리(브랜치 tmpbr)를 만든 뒤 폴더를 다른 곳으로 옮겨 「없어진」 상태를 만들었다.

git worktree list
git worktree list --porcelain

git 은 폴더가 물리적으로 사라졌음에도 관리 장부에서 해당 워크트리를 지우지 않고 다음과 같이 prunable 상태로 표시한다.

…/tech_lab/p   c54568b [main]
…/tech_lab/p4  c54568b [tmpbr] prunable
worktree …/tech_lab/p4
HEAD c54568b49c4cf9ce2c99ccc5dff022eb0bc00495
branch refs/heads/tmpbr
prunable gitdir file points to non-existent location

이 상태에서는 없어진 폴더가 브랜치를 계속 붙잡고 있다. 같은 방법으로 p5(브랜치 tmp2)를 만들고 폴더를 옮긴 뒤 git worktree add …/tech_lab/p6 tmp2 를 실행하자 다음 오류가 났다(exit=128).

fatal: 'tmp2' is already used by worktree at '…/tech_lab/p5'

5.3 worktree prune으로 찌꺼기 레코드 청소하기

수동 삭제로 인해 꼬여버린 참조는 git worktree prune 명령으로 해제해야 한다. 실제 삭제를 수행하기 전에 -n(드라이 런)과 -v(상세 출력) 옵션을 주어 정리 대상 항목을 미리 검토하는 습관이 바람직하다.

git worktree prune -n -v
# 출력: Removing worktrees/p4: gitdir file points to non-existent location
git worktree prune -v
# 출력: Removing worktrees/p4: gitdir file points to non-existent location

prune 뒤에는 git worktree list 에 메인만 남았고, 같은 브랜치를 다시 꺼내는 git worktree add …/tech_lab/p4 tmpbr 가 Preparing worktree (checking out 'tmpbr') 로 성공했다. tmp2 도 git worktree prune 뒤 p6 에 꺼내졌다.

6. 외장 드라이브와 임시 보관 - lock과 unlock

6.1 lock 설정과 자동 prune 방지

문서는 워크트리가 늘 마운트되어 있지 않은 이동식 장치나 네트워크 공유에 있을 때, 관리 파일이 자동으로 prune 되지 않도록 잠그라고 적는다. 이 기능이 git worktree lock 이다.

git worktree lock --reason "on USB disk" …/tech_lab/p4
git worktree list --porcelain

잠금을 설정하면 list --porcelain 출력에 locked on USB disk 라는 라벨이 추가된다. 이 상태에서는 해당 폴더가 디스크에서 사라지더라도 git worktree prune -v 가 해당 항목을 건드리지 않고 건너뛴다.

6.2 잠긴 워크트리의 안전한 해제 및 삭제

잠긴 워크트리는 git worktree remove 로도 지워지지 않았다(exit=128).

fatal: cannot remove a locked working tree, lock reason: on USB disk
use 'remove -f -f' to override or unlock first

메시지대로 먼저 git worktree unlock …/tech_lab/p4 로 잠금을 풀자, 폴더가 없는 이 워크트리는 git worktree prune -v 로 Removing worktrees/p4: gitdir file points to non-existent location 과 함께 정리됐다. 메시지와 문서는 -f 를 두 번 주는 방법(remove -f -f)도 적지만, 이 실험에서는 unlock 으로 정리했다.

7. 실무 적용 지침 - 쓰기 좋은 자리와 주의할 자리

7.1 긴급 핫픽스와 옆 폴더 병행 작업

실행 결과에서 바로 이어지는 쓰임새는 다음과 같다.

  • 긴급 수정 브랜치를 옆 폴더에: 이미 있는 hotfix 브랜치를 git worktree add …/tech_lab/p2 hotfix 로 꺼내면 p1(feature)의 작업 파일은 그대로 둔 채 옆 폴더에서 고칠 수 있었다. p2 에서 한 커밋에도 공유 hooks 가 실행됐다.
  • 끝나면 remove 로 치우기: 깨끗한 워크트리는 메시지 없이 지워졌고, 지운 뒤에도 브랜치와 stash 는 남았다. 필요 없으면 따로 정리한다.
  • 폴더를 손으로 지우지 않기: 손으로 없앤 폴더는 prune 전까지 브랜치를 붙잡아 같은 브랜치를 다른 곳에 꺼낼 수 없었다.

7.2 병렬 AI 코딩 에이전트와 워크트리 격리

여러 AI 코딩 세션이 한 저장소를 함께 쓸 때 생기는 문제는 병렬 AI 에이전트 다중 실행 분석에서 다뤘다. 워크트리를 쓸 때 이 글의 실행 결과에서 챙길 점은 다음과 같다.

  • HEAD·index 는 워크트리별: rev-parse --git-path 결과처럼 워크트리마다 HEAD·index 경로가 따로 잡힌다.
  • stash 는 하나: 한 워크트리에서 stash pop 을 하면 다른 워크트리가 넣은 stash 를 꺼낼 수 있다. stash list 의 「On 브랜치」 표시를 확인한다.
  • 정리는 remove·prune: 작업이 끝난 워크트리는 git worktree remove 로 지우고, 손으로 지운 폴더가 있으면 git worktree prune 을 실행해 브랜치 점유를 푼다.

7.3 상황별 명령어 및 에러 메시지 결정표

실제 작업 도중 마주치는 주요 상황과 git 의 반응, 그리고 올바른 대응 절차를 하나의 결정표로 정리하였다.

상황 원인 및 발생 메시지(실측) 대응 조치
이미 사용 중인 브랜치 재체크아웃 fatal: 'feature' is already used by worktree at … 새 브랜치 생성(-b)으로 꺼낸다. -f 는 막는 장치를 끄는 것
작업물이 남은 상태에서 워크트리 삭제 fatal: '…' contains modified or untracked files, use --force to delete it 수정분 커밋 또는 스태시 보관 후 재시도. 미추적 새 파일이 하나만 있어도 거부됨
수동 폴더 삭제 후 브랜치 재사용 불가 fatal: '…' is already used by worktree at <없는 경로> / list 에 prunable git worktree prune -n -v 로 확인 후 git worktree prune 실행
이동식 저장소 또는 외장 디스크 보관 list 에 locked / remove 시 fatal: cannot remove a locked working tree, lock reason: on USB disk git worktree lock --reason "사유" 로 보호(폴더가 없어도 prune 이 건드리지 않음). 지울 땐 unlock 후 정리하거나 remove -f -f

확인하지 못한 것

  • Linux 및 macOS 전용 파일시스템 동작: 본 검증은 Windows 10 및 NTFS 파일시스템 환경에서 수행되었으므로, Linux ext4 나 macOS APFS 환경에서의 세부 파일시스템 권한 처리 특성은 직접 대조하지 못했다.
  • 네트워크 파일시스템(NFS/SMB) 락 안정성: 원격 네트워크 드라이브에 워크트리를 배치했을 때 다중 클라이언트 동시 접근 환경에서의 파일 락 경합 및 지연 양상은 테스트 범위에 포함되지 않았다.
  • 비공개 내부 레퍼런스 격리: refs/bisect 나 refs/rewritten 등 특수 작업 시 git 내부에서 생성되는 비공유 레퍼런스의 실제 라이프사이클은 별도의 bisect 실험을 진행하지 않아 실측에서 다루지 못했다.

# git worktree 실무 점검표 - 브랜치 병행 작업과 격리

검증 환경: Windows 10 Pro 10.0.19045, Git Bash(GNU sed 4.9, GNU Awk 5.0.0), curl 8.12.1(Schannel), git 2.48.1.windows.1, Windows PowerShell 5.1, Python 3.13.3, Node 22.16.0 (관리자 권한 아님).
아래 값은 이 환경에서 실제로 실행해 확인한 출력에 근거한다. 다만 잠근 워크트리의 `remove -f -f` 는 git 메시지와 문서가 적는 방법으로, 실행하지 않았다(잠금은 `unlock` 으로 풀어 정리했다). 경로는 `…/tech_lab/` 으로 줄였다.

## 1. 워크트리 간 공유 범위 대조표 (실측 확인)

| 항목 | 공유 여부 | 실측 근거(명령 및 출력) | 실무 영향 |
|---|---|---|---|
| 커밋·브랜치 | 공유 | 워크트리 p1 커밋이 메인 저장소 `log --all` 에 즉시 표시됨 | 어느 폴더에서 커밋하든 다른 워크트리에서 바로 보인다 |
| stash 목록 | **공유 (하나)** | p1 에서 넣은 stash 가 메인 및 p2 `stash list` 에 그대로 보이고, 워크트리 삭제 후에도 남음 | 다른 워크트리의 `stash pop` 이 남의 작업을 꺼낼 수 있다(다른 브랜치에 적용 시 CONFLICT 실측) |
| git config (기본) | 공유 | p2 에서 설정한 키(`lab.flag`)를 메인에서 조회함 | 저장소 단위 설정 변경은 모든 워크트리에 적용된다 |
| git config --worktree | 워크트리별 | `extensions.worktreeConfig true` 를 켠 뒤에만 됨(없으면 fatal), 값은 메인 `.git/worktrees/p2/config.worktree` 에 기록 | 워크트리별 설정이 필요할 때만 켠다 |
| hooks 스크립트 | 공유 | 메인 `.git/hooks/post-commit` 이 p1·p2 커밋 시 실행됨 | 훅은 메인 한 곳에 두면 된다 |
| HEAD / index / logs | 워크트리별 | `rev-parse --git-path` 가 `worktrees/p1/...` 경로를 반환 | HEAD·index 경로가 워크트리마다 따로다 |

## 2. 상황별 명령과 git 반응 (실측 메시지)

| 상황 | 실행 명령 예시 | git 출력 메시지(실측) | 대응 조치 |
|---|---|---|---|
| 다른 워크트리가 쓰는 브랜치 꺼내기 | `git worktree add …/tech_lab/p3 feature` | `fatal: 'feature' is already used by worktree at '…/tech_lab/p1'` | 새 브랜치(`-b`)로 꺼낸다. `-f` 는 막는 장치를 끄는 것 |
| 변경·새 파일이 남은 채 워크트리 제거 | `git worktree remove …/tech_lab/p2` | `fatal: '…\tech_lab\p2' contains modified or untracked files, use --force to delete it` | stash 나 커밋 후 remove. 추적 안 하는 새 파일 하나만 있어도 거부 |
| 폴더를 손으로 없앤 뒤 브랜치 재사용 | `git worktree add …/tech_lab/p6 tmp2` | `fatal: 'tmp2' is already used by worktree at '…/tech_lab/p5'` | `git worktree prune -n -v` 로 확인 후 `git worktree prune` 실행 |
| 잠근 워크트리 제거 | `git worktree remove …/tech_lab/p4` | `fatal: cannot remove a locked working tree, lock reason: on USB disk` | `git worktree unlock` 후 정리, 또는 `remove -f -f`. 잠금은 `lock --reason "on USB disk"` 로 걸고 `list --porcelain` 에 `locked on USB disk` 로 보인다 |

## 3. 작업 전후 체크리스트

- [ ] **폴더 삭제 대신 정식 명령 쓰기**: 파일 탐색기나 `rm -rf` 로 지우지 말고 `git worktree remove <경로>` 로 제거한다.
- [ ] **제거 후 잔여 브랜치·stash 확인**: 워크트리 폴더를 지워도 브랜치와 stash 는 남으므로 필요 없는 항목은 따로 정리한다.
- [ ] **stash pop 전 브랜치 표시 점검**: stash 가 하나이므로 `git stash list` 에서 `On <브랜치명>` 을 확인한 뒤 꺼낸다.
- [ ] **추적 안 하는 파일 확인**: `worktree remove` 는 추적되지 않는 새 파일(`??`)이 하나만 있어도 삭제를 거부한다.
- [ ] **Windows 긴 경로 주의**: 경로가 매우 긴 폴더에서는 git 이 `.git` 안에 쓰지 못해 실패할 수 있으므로 저장소를 짧은 경로에 둔다.
- [ ] **손으로 지우거나 옮긴 뒤에는 prune**: 폴더가 없어진 워크트리는 `git worktree prune -n -v` 로 확인하고 `git worktree prune` 으로 정리한다.
