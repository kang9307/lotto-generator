乱数 API を設計し直すなら - 再現性・安全性・一貫性

統計用と安全用、シード、範囲、シャッフル、グローバル状態を実際に走らせて確かめ、設計原則にまとめた

2026-08-01 開発/インフラ

はじめに: 再現しない失敗と、名前が同じ二つの関数

生成した入力で回す検査が、ある日一度だけ引っかかった。ログには期待値と違うとしか出ていない。もう一度回すと通った。さらに十回回しても通った。どの入力がそれを壊したのかは、プロセスが終わると同時に消えていた。

原因を探していて、先に別のものを見つけた。その入力を作るコードと、パスワード再設定リンクに付くトークンを作るコードが、ほとんど同じ名前の関数を呼んでいた。片方は統計用の生成器で、もう片方は安全用だった。呼び出し箇所だけを見てもどちらがどちらか区別できなかった。

この二つは別々の事故に見えるが、根は一つである。乱数 API の難所はアルゴリズムではなく名前と既定値である。どの生成器を使うか、シードを受け取るか、範囲をどう切るか。すべて表面の設計の問題であり、その表面が曖昧なら使う側で必ず事故が起きる。

そこで実際に走らせた。以下の数値はすべてこのランタイムで直接実行して得たものである。確かめたのは四つである。

  • 名前が種類を隠す。統計用と安全用が同じ語を共有すると、呼び出し箇所からは区別できない
  • シードがなければ不具合を二度見られない。再現性は便利機能ではなくデバッグの前提である
  • 範囲を切った瞬間に分布が傾く。そしてその傾きは元値の幅によって見えたり、永久に見えなかったりする
  • グローバル生成器一つが再現性を人質に取る。シードを固定しても消費順序が変われば結果が変わる

実行環境。以下の出力はすべて Windows 10 Pro (10.0.19045) 上の Node.js v22.16.0 (win32 x64) で実際に実行した結果である。統計用の生成器は 32 ビットの状態を持つ splitmix32 を自分で実装して使い、安全用はこのランタイムが提供する暗号論的乱数の口をそのまま使った。スクリプトはすべてファイルに保存して実行した。標本の大きさは項目ごとに本文に書いた。

この記事が扱わないこと。予測可能性をどう悪用するかは扱わない。統計用は予測できるという性質だけを確かめ、その性質を利用する手順は書かない。サーバーがわざとぼかした値を返す場合と、無作為な識別子を主キーに使ったときの保存コストはそれぞれ別の記事にある。検査が実行順に依存するかを見分ける問題もここでは扱わない。この記事は乱数 API そのものの表面だけを見る。

1. 名前は一つなのに種類は二つある

まずこのランタイムが提供する乱数まわりの呼び出しを並べ、どれがどの種類かを表にした。そのうえで実際のコード一行だけを置いて、種類が分かるかを確かめた。

--- 1-1. every one of these has "random" in the name ---
call                          family        seedable  sample output
--------------------------------------------------------------------------------------------
Math.random()                 statistical   no        0.4962049585478472
crypto.randomInt(0, 100)      security      no        57
crypto.randomBytes(4).hex     security      no        16ca5c5e
crypto.getRandomValues(u32)   security      no        4091828560
crypto.randomUUID()           security      no        9ba23fe3-3912-4644-9d45-3025617158a5
seeded splitmix32(42)         statistical   YES       551831576

--- 1-2. can you tell the family from the call site alone? ---
const pick   = Math.random();                           statistical   
const nonce  = crypto.randomInt(0, 1e9);                security-grade
const shard  = Math.random() * 16 | 0;                  statistical   
const token  = crypto.randomBytes(16).toString("hex");  security-grade
const jitter = Math.random() * 200;                     statistical   
const id     = crypto.randomUUID();                     security-grade

六つの呼び出し箇所のうち統計用が三つ、安全用が三つである。そして六つとも名前に同じ語を含んでいる。コードレビューでこれらの行を流し読みするとき、どちらかを判断するには呼び先の名前を一つずつ覚えている必要がある。

  • 表の seedable 列が決定的である。シードを入れられるのは統計用だけで、安全用にはシードを入れる場所そのものがない
  • ところがこの性質は名前にまったく現れない。文書を見なければ分からず、文書を見なければ分からないままである
  • 変数名が token か jitter かが唯一の手がかりだが、変数名は強制されない
  • 静的解析で捕まえようとしても、その値が外に出るかを追う必要があり、一般には難しい

1.1 なぜ二種類必要なのか - このランタイムで測った処理量

二つに分かれているのには理由がある。その理由が実際にどれだけ大きいかを測った。あわせて、二つの系統が不正な引数を受けたときにどう反応するかも確かめた。

--- 1-3. why both exist: throughput in this runtime ---
Math.random()                        2,000,000 draws       30.6 ms       65,425,972 /s
seeded splitmix32                    2,000,000 draws       34.6 ms       57,830,211 /s
crypto.randomInt(0, 256)               200,000 draws       11.9 ms       16,771,910 /s
crypto.getRandomValues(1 word)         200,000 draws      537.1 ms          372,338 /s
getRandomValues, 4096 batched        2,000,000 draws       39.8 ms       50,269,065 /s

ratio Math.random / crypto.randomInt      : 3.9 x
ratio Math.random / getRandomValues(1)    : 175.7 x
ratio Math.random / getRandomValues(batch): 1.3 x
batching closes most of the gap; per-call overhead was the cost, not the algorithm

--- 1-4. the security call has limits the statistical one does not ---
getRandomValues(65536 bytes)      ok
getRandomValues(65537 bytes)      QuotaExceededError: The requested length exceeds 65,536 bytes
getRandomValues(Float64Array)     TypeMismatchError: The data argument must be an integer-type TypedArray
crypto.randomInt(10, 5)           RangeError: The value of "max" is out of range. It must be greater than the value of "min" (10). Received 5
Math.random(10, 5)                0.00437523505103643   <- extra arguments accepted and ignored
Math.random("seed")               0.8035145788730187   <- a seed argument is silently dropped

差は確かにある。ただしその差の正体が面白い。安全用を一語ずつ呼ぶと 175 倍遅かったが、4,096 個ずつまとめて受け取ると 1.3 倍差まで縮んだ。費用の大半はアルゴリズムではなく呼び出しごとの間接費だったということである。

  • 安全用は遅いから統計用を使うという判断は、多くの場合に根拠が弱い。まとめて受け取れば大半の負荷で差は消える
  • 安全用の呼び出しには一度に 65,536 バイトという上限があり、超えると例外を投げる。この上限自体がまとめて受け取れという設計意図を表している
  • 安全用は整数型でない配列を渡すと拒否し、最小値が最大値を超えていればその場で例外を投げる
  • 一方で統計用の呼び出しは引数を余分に渡しても黙って無視した。シードらしき文字列を渡しても何も起きない。これをシードと勘違いしたコードは永久に再現しない

2. シードは便利機能ではなくデバッグの前提である

はじめの症状に戻る。生成した入力で回す検査が引っかかったのに、どの入力だったか分からない状況である。シードがあればこの状況自体が成立しない。

区間の幅が 0 になると割り算が無限大を返す関数を用意し、その関数を生成した入力で 500 回検査した。シードを報告に残した場合と残さない場合を並べて回した。

--- 2-1. same seed, two independent generators, same sequence ---
seed 20260801, run A : 266 648 876 913 47 571
seed 20260801, run B : 266 648 876 913 47 571
seed 20260802, run C : 944 290 515 272 128 899
A equals B : true     A equals C : false

--- 2-2. a data-driven check finds a failing input ---
seed recorded in the failure report : 424242
iterations run                      : 500
failures                            : 14
first failing input                 : iteration 92, lo=30 hi=30

--- 2-3. replay: rerun with the recorded seed, get the identical failure ---
replay 1 : first failure at iteration 92, lo=30 hi=30
replay 2 : first failure at iteration 92, lo=30 hi=30
replay 3 : first failure at iteration 92, lo=30 hi=30
the failing input is now a fixed, quotable value; you can attach it to the fix

再実行三回がすべて同じ反復回、同じ入力を指した。この時点で失敗はもはや無作為な出来事ではなく、引用できる固定値になる。修正のコミットにその値をそのまま書けるし、直ったかを確かめるときも同じ値で確かめる。

2.1 シードがなければ同じ検査が毎回違う話をする

--- 2-4. the same check without a seed: five runs, five different stories ---
run     failures / 500    first failing input
--------------------------------------------------------
1       19                iteration 8, lo=10 hi=10
2       9                 iteration 52, lo=34 hi=34
3       9                 iteration 119, lo=10 hi=10
4       11                iteration 14, lo=25 hi=25
5       13                iteration 32, lo=16 hi=16
first-failure iteration across runs : 8, 52, 119, 14, 32
nothing here is quotable: the input that broke it is gone the moment the process exits

--- 2-5. what a seed buys, measured ---
property                              seeded    unseeded
----------------------------------------------------------------------------
can rerun the exact input set         yes       no
failure report is a fixed value       yes       no
fix can be proven against the case    yes       not the same case
unpredictable to an outside party     no        no (both are statistical)
safe for tokens and secrets           no        no

同じ検査を五回回すと、最初の失敗の回が 8、52、119、14、32 とすべて違った。失敗の回数も 9 から 19 の間で揺れた。この状態では直ったことを証明する方法がない。次の実行で引っかからなかったのが、直したからか運が良かったからか区別できないためである。

  • シードは失敗報告の一部でなければならない。記録に残さなければ、あっても無いのと同じである
  • 最後の表の下二行が重要である。シードの有無にかかわらず統計用は予測でき、どちらの形も秘密の値を作るのには使えない
  • つまりシードの有無は再現性の軸の問題であって安全性の軸の問題ではない。二つの軸を混ぜると判断がぼやける
  • 実務ではシードを後で必要になったら足すものとして先送りしがちだが、必要になる時点はすでに遅い時点である

3. 範囲を作った瞬間に分布が傾く

乱数を望む範囲に移す最も一般的な方法は剰余演算である。8 ビットの値を 100 で割った余りを百万回取り、分布を見た。さいころのような小さい範囲も一緒に見た。

--- 3-1. modulo on an 8-bit source, bound = 100 ---
256 = 2 * 100 + 56   -> values 0..55 have 3 preimages, 56..99 have 2
theoretical p(low)  = 1.1719%   p(high) = 0.7813%   ratio = 1.500
measured  mean(0..55) = 11715.7   mean(56..99) = 7816.4   ratio = 1.499
measured  min = 7615  max = 11917  expected if fair = 10000
chi-square (df 99) = 37546   (fair sample lands near 99)
first 8 buckets  : 11623 11596 11859 11710 11869 11676 11634 11520
buckets 56..63   : 7949 7884 7659 7807 7886 7615 7881 7824

--- 3-2. same bug, small bound = 6 (a dice roll) ---
256 = 42 * 6 + 4
face       :         1        2        3        4        5        6
count      :    167301   167670   168621   167747   164466   164195
share      :   16.730%  16.767%  16.862%  16.775%  16.447%  16.419%
expected fair share 16.667% each
chi-square (df 5) = 104.1   (fair sample lands near 5)
theoretical excess of faces 1..4 = 2.38%

理由は算数一行である。256 を 100 で割ると商が 2、余りが 56 になる。0 から 55 までは出る経路が三つ、56 から 99 までは二つである。だから前者がちょうど 1.5 倍多く出る。実測の 1.499 が理論と合った。

さいころも同じ構造である。256 を 6 で割ると余りが 4 なので、1 から 4 が 2.38% 多く出る。目で見れば誤差に思える差だが、カイ二乗は 104.1 で自由度 5 の期待値を二十倍以上外れている。

3.1 広い元値では同じ不具合が永久に見えない

ここがこの節の核心である。まったく同じ剰余演算を 32 ビットの値に掛け、同じ百万回を回した。あわせて偏りを消す方法とその代償も測った。

--- 3-3. same "% 6" on a 32-bit source: bias still there, invisible ---
2^32 = 715827882 * 6 + 4
theoretical excess of faces 1..4 = 1.397 parts per billion
count      :    166645   166580   166318   167237   166273   166947
chi-square (df 5) = 4.1   -> indistinguishable from fair
draws needed to see this bias at all: about 512410 x 10^12

--- 3-4. rejection sampling removes the bias at a measurable cost ---
accept only bytes < 200 (= 256 - 256 % 100), then take % 100
measured  min = 9708  max = 10279  expected = 10000
chi-square (df 99) = 104   (fair sample lands near 99)
rejected 280146 of 1280146 bytes = 21.88%  (theory 21.88%)
worst-case rejection rate for an 8-bit source is just under 50% (bound = 129)

32 ビット側はカイ二乗 4.1 で公平な標本と区別できなかった。偏りが消えたのではなく、十億分の 1.4 程度なので見えないだけである。この偏りを統計的に捉えるには 10 の 17 乗規模の標本が要る。つまり検査では絶対に引っかからない不具合になる。

元値の幅範囲小さい値の超過確率百万回で見えるか実務判断
8 ビット62.38%見えるすぐ露見し、直しやすい
8 ビット10050%見える最も危険な組み合わせ
8 ビット1000744 個の値が出ない見える範囲が元値より広い
16 ビット10001.54%見える境目
32 ビット60.00000014%見えない検査で捕まらない
32 ビット10000.0000233%見えない検査で捕まらない
53 ビット10000.0000000000111%見えない事実上無害

表はこう読む。上の三行はすぐ露見する不具合で、下の二行は永久に露見しない不具合である。ところがコードは両側でまったく同じ形をしている。だから今まで問題なかったという事実は根拠にならない。

  • バイト単位の元値に狭い範囲を掛ける組み合わせが最も事故を起こす。抽選、さいころ、カード引きがすべてここに当たる
  • 棄却抽出は範囲のちょうど倍数までだけを受け入れ、残りの尾を捨てる。8 ビットに 100 を掛けると 21.88% を捨てる代わりに偏りが 0 になる
  • 32 ビットの元値では棄却の代償が平均 1.00 回、最悪 2.00 回である。実務で問題になる水準ではない
  • 最も確実な解はこの関数をライブラリが提供することである。呼び出し側が毎回作り直せば半分は間違える
// unbiased bounded integers - the code a caller should never have to write again
function intBelow(next, n) {                     // next() returns a uint32
  if (!Number.isInteger(n) || n <= 0) throw new RangeError('bound must be a positive integer');
  if (n > 4294967296) throw new RangeError('bound exceeds source width (2^32)');
  const limit = 4294967296 - (4294967296 % n);   // largest exact multiple of n
  let v;
  do { v = next(); } while (v >= limit);         // drop the ragged tail
  return v % n;
}

function intBetween(next, lo, hi) {              // closed range, both ends included
  if (!Number.isInteger(lo) || !Number.isInteger(hi)) throw new TypeError('intBetween takes integers');
  if (hi < lo) throw new RangeError('intBetween(lo, hi) needs hi >= lo');
  return lo + intBelow(next, hi - lo + 1);
}

4. 0 以上 1 未満の実数を整数に変える境界

多くの乱数 API は 0 以上 1 未満の実数を返す。それを整数に変える瞬間に境界の問題が生じる。1 のすぐ下にある最大の実数を直接与えて、よくある書き方がどう反応するかを見た。

--- 4-1. the two endpoints of [0, 1) ---
largest double below 1 : 0.99999999999999988898
is it really < 1       : true
next double up         : 1

--- 4-2. does floor(r * n) ever reach n? feed it the worst possible r ---
n                     r * n                     floor                 reaches n?
------------------------------------------------------------------------------------
6                     5.999999999999999         5                     no
100                   99.99999999999999         99                    no
1000                  999.9999999999999         999                   no
65536                 65535.99999999999         65535                 no
1000000000            999999999.9999999         999999999             no
4503599627370496      4503599627370495.5        4503599627370495      no
9007199254740992      9007199254740991          9007199254740991      no
the multiply rounds down here for every n up to 2^53: floor stays at n-1

--- 4-3. the same worst-case r through the usual range idioms ---
idiom                     r = 0   r = 0.5 r = max<1  intended range
----------------------------------------------------------------------------------------
Math.floor(r * n)         0       5       9          0..9   inclusive-exclusive
Math.round(r * n)         0       5       10         0..10  endpoints half-weight
Math.ceil(r * n)          0       5       10         0..10, 0 almost never
Math.floor(r * (n + 1))   0       5       10         0..10  inclusive, correct
(r * n) | 0               0       5       9          0..9   32-bit truncation

まず安心できることが一つある。切り捨てを使う限り最大値が飛び出すことはなかった。1 直前の最大の実数を掛けても積が下に丸められ、n には届かない。n が 2 の 53 乗以下のすべての場合でそうだった。問題は他の書き方である。

書き方実際の範囲1 直前の値で判定
Math.floor(r * n)0 以上 n 未満、一様n-1正しい（半開区間）
Math.floor(r * (n + 1))0 以上 n 以下、一様n正しい（閉区間）
Math.round(r * n)0 以上 n 以下、両端が半分n誤り

四捨五入側の分布が目を引く。両端が 5.01%、中央が 10.00% である。ちょうど半分である。四捨五入は 0 と n を幅が半分の区間に対応させるからである。抽選や等級の割り当てにこの書き方を使うと、両端の等級だけが静かに希少になる。

  • 0 以上 1 未満は半開区間である。五百万回でちょうど 0 もちょうど 1 も出なかった。最小の観測値は 1.8e-7 だった
  • ビット演算で切り捨てる書き方は2 の 31 乗を超える範囲で負の数を出す。幅 50 億で -544,967,296 が出た
  • 実数一つが担う情報は最大 53 ビットである。それより広い範囲を求めると永久に出ない値が生じる
  • 両端を含めたいなら四捨五入ではなく、区間の数を一つ増やして切り捨てる。表の二行目がそれである
  • これらすべてを呼び出し側が毎回判断しないで済むように、API が開区間か閉区間かを名前で明かすべきである

5.1 なぜ誤ったシャッフルは原理的に一様になれないのか

--- 5-3. why broken Fisher-Yates cannot be fair, by counting ---
length 3 :       27 equally likely swap paths spread over    6 permutations           27 / 6 = 4.5000  <- not an integer, cannot be uniform
length 4 :      256 equally likely swap paths spread over   24 permutations         256 / 24 = 10.6667  <- not an integer, cannot be uniform
length 5 :     3125 equally likely swap paths spread over  120 permutations       3125 / 120 = 26.0417  <- not an integer, cannot be uniform
length 6 :    46656 equally likely swap paths spread over  720 permutations      46656 / 720 = 64.8000  <- not an integer, cannot be uniform
correct Fisher-Yates draws from 0..i, giving exactly n! paths for n! outcomes

--- 5-4. the comparator version also depends on the sort algorithm and length ---
length   2 : P(element 0 stays at index 0)  comparator   49.84%   Fisher-Yates   50.02%   fair value 50.00%
length   3 : P(element 0 stays at index 0)  comparator   43.62%   Fisher-Yates   33.35%   fair value 33.33%
length   4 : P(element 0 stays at index 0)  comparator   35.96%   Fisher-Yates   25.06%   fair value 25.00%
length   8 : P(element 0 stays at index 0)  comparator   22.13%   Fisher-Yates   12.45%   fair value 12.50%
length  16 : P(element 0 stays at index 0)  comparator   13.26%   Fisher-Yates    6.26%   fair value 6.25%

数えるだけで証明できる。交換相手を配列全体から引くと経路が n の n 乗通りになるが、結果は n の階乗通りである。4 要素なら 256 を 24 で割って 10.667 になり整数にならない。同じ確率の経路を整数個ずつ配れないので一様が不可能である。正しい形は交換相手を 0 から現在位置までだけから引くことで、そうすれば経路がちょうど n の階乗通りになる。

  • 比較関数のシャッフルは配列が長いほど悪くなる。長さ 16 で先頭要素が動かない確率が 13.26% と、公平値 6.25% の二倍だった
  • 同じコードが並べ替えの実装によって違う分布を出す。ランタイムが変われば結果も変わるということである
  • 比較関数は同じ二要素を比べれば常に同じ答えという前提の上で動くが、無作為な比較関数はその前提を壊す
  • 結論は 3 節と同じである。シャッフルもライブラリが提供すべきである。提供しなければ比較関数の裏技が必ず現れる

6. 安全用を使うべき場所

ここからは二つの系統の違いが結果にどう現れるかを見る。同じトークン生成関数を統計用と安全用の上にそれぞれ載せた。

先に断っておく。この節は統計用は予測できるという性質だけを確かめる。その性質をどう利用するか、どんな手順で次の値を導くかは扱わない。

この記事が書かないこと。予測可能性を利用する手順は書かなかった。必要な判断には性質だけで足りるからである。この値は状態が定まれば一緒に定まるという事実一つで、その値を秘密に使わない理由になる。逆方向の安全の主張、つまり導き出しにくいという主張は技法が進めば崩れるが、構造的に定まっているという事実は変わらない。

7. グローバル生成器一つが再現性を壊す

2 節ではシードを付けて再現性を得た。ところがその再現性は思ったより簡単に壊れる。シードを固定したグローバル生成器一つを二つの部品で分け合い、消費の順序だけを三通りに変えてみた。

--- 7-1. one global generator, two consumers, two interleavings ---
order                 component A sees      component B sees
------------------------------------------------------------------
A A A B B B           201 652 582           38 515 449
B B B A A A           38 515 449            201 652 582
A B A B A B           201 582 515           652 38 449

same seed, same code, three different results for A: 3 distinct sequences out of 3
the seed pins the stream. it does not pin who draws from it, or when.

B B B A A A           876 436 698           745 310 389
A B A B A B           876 436 698           745 310 389

同じシード、同じコードなのに部品 A が見た数列は三通りとも違った。シードは数列そのものを固定するだけで、誰がいつ何個を取るかは固定できない。生成器を分けて渡すと三通りの順序で結果がすべて一致した。

タイミングだけを変えた二回の実行が違う結果を出した。自分の生成器を持つ側はタイミングが変わっても結果が同じだった。グローバル生成器はすべての利用者を互いの隠れた依存にする。コードのどこかで乱数をもう一度引く変更だけで、無関係な別の場所の結果が変わる。

配置単独で再現並列で再現順序が変わっても依存するもの

  • 実務で勧める形は作業単位ごとに子の生成器を派生させることである。上位のシードと作業識別子を組み合わせて作る
  • そうすれば作業が並列に走っても、順序が変わっても各作業の数列はそのまま保たれる
  • グローバル生成器を提供する API は楽に見えるが、便利さ一つのために再現性全体を手放させる
  • この問題はシードをどれだけ丁寧に管理しても解けない。構造の問題であって値の問題ではない

8. 設計し直すなら - 名前、シード、範囲、既定値

前の七節で出た落とし穴をすべて塞ぐ表面を実際に作って走らせた。規則は四つである。名前で種類が分かるように、シードを明示的に、範囲関数を提供し、既定値を慎重な側に。

// the family is in the constructor name, and the seed is not optional
function statisticalRng(seed) {
  if (!Number.isInteger(seed)) throw new TypeError('statisticalRng(seed) requires an explicit integer seed');
  const api = core(splitmix32(seed));    // deterministic engine
  api.seed = seed;                       // the value that goes into a failure report
  api.kind = 'statistical';
  return api;                            // an instance, never a module-level singleton
}

const secureRandom = (() => {
  const pool = new Uint32Array(1024);    // batched: per-call overhead was the cost, not the algorithm
  let i = pool.length;
  const u32 = () => { if (i >= pool.length) { crypto.getRandomValues(pool); i = 0; } return pool[i++]; };
  const api = core(u32);
  api.kind = 'security';
  api.token = (chars = 22) => { /* ... */ };     // exists only on this object
  return api;                            // no seed parameter, so none can be passed
})();

// one shared surface, so range and collection helpers read the same on both
function core(u32) {
  return {
    intBelow:     (n) => bounded(u32, n),                      // [0, n)  half-open, the name says below
    intBetween:   (lo, hi) => lo + bounded(u32, hi - lo + 1),  // [lo, hi] closed, the name says between
    unitInterval: () => u32() / 4294967296,                    // [0, 1)  named after its range
    pick:         (arr) => arr[bounded(u32, arr.length)],      // no index arithmetic at the call site
    shuffled:     (arr) => { /* Fisher-Yates on a copy */ },   // past tense: returns a copy
  };
}

肝心なのは二つの生成器の形そのものが違うことである。統計用はシードなしでは作れず、安全用にはシードを入れる場所がない。文書を読まなくても表面が強制する。この表面で先の三つの落とし穴を通し直した。

  • 配列を扱う関数はその場で書き換えず複製を返す。過去分詞の名前がそれを知らせる
  • 再現性の契約も文書に書くべきである。版が上がっても同じシードが同じ数列を返すかは決定的な用途で重要な約束である
  • 速い経路が要るなら提供してよいが、名前を長く明示的にして誤って選ばれないようにする

9. まとめ - 難所はアルゴリズムではなく名前と既定値

ここまでの実行で確かめたことを一文にすればこうなる。乱数で間違える地点は、たいてい乱数の生成ではなくその値を扱う表面である。アルゴリズムには既に答えがあり、ライブラリが肩代わりできる。ところがそのライブラリがどんな名前で何を出すかが事故の頻度を決める。

とくに二つが決定的である。第一に、統計用と安全用が似た名前を持てば事故は必ず起きる。実測では六つの呼び出しが三つずつに分かれたが、名前だけでは区別できなかった。これは使う側の不注意ではなく表面の欠陥である。

第二に、再現性はあれば良いものではなくデバッグの前提である。シードがなければ失敗を引用できず、引用できなければ直したことを証明できない。シードを省略可能な引数にすれば誰も渡さない。だから必須引数でなければならない。

  • 見知らぬ相手がその値を知って何かを得るか。この一行で系統を分ける
  • 剰余演算で範囲を切らない。狭い元値ではすぐ露見し、広い元値では永久に露見しない
  • 四捨五入で整数範囲を作らない。両端が半分の重みになる
  • 比較関数で混ぜない。並べ替えの実装と配列の長さで結果が変わる
  • グローバル生成器を共有しない。再現性が呼び出し順に人質を取られる
  • シードを後から付けない。必要になる時点はすでに遅い時点である

# 乱数 API チェックリスト — 統計用と安全用、範囲、シャッフル、シード

> 出典: braindetox.kr — 乱数 API を設計し直すなら
> 根拠: Windows 10 / Node.js v22.16.0 (win32 x64) で実行して検証、2026-08-01

## 1. 一行で分ける

**見知らぬ相手がその値を握ったら何かを得るか。**

- はい → **安全用**。トークン、セッション、パスワード再設定リンク、招待コード、一時ファイル名、抽選
- いいえ → **統計用**。サンプリング、ジッター、A/B 振り分け、検査用の合成データ、視覚効果

迷ったら安全用を選ぶ。統計用で足りる場所に安全用を使って失うのは速度だけで、
逆方向の失敗は取り返しがつかない。

## 2. 用途別の選択表

| 生成するもの | 種類 | シード | 理由 |
|---|---|---|---|
| セッション識別子 | 安全用 | なし | 値そのものが権限 |
| パスワード再設定トークン | 安全用 | なし | 値そのものが権限 |
| API キー・招待コード | 安全用 | なし | 値そのものが権限 |
| CSRF トークン・ノンス・ソルト | 安全用 | なし | 新しさが安全性 |
| 一時ファイル・ディレクトリ名 | 安全用 | なし | 他人に予見される名前は危険 |
| 抽選・景品 | 安全用 | なし | 金銭と外部の当事者が絡む |
| 検査用の合成データ | 統計用 | **必須** | シードを失敗報告に残す |
| A/B バケット割り当て | 統計用 | **必須** | 同じ利用者は同じバケットへ |
| ログのサンプリング | 統計用 | 推奨 | 監査できるようになる |
| リトライのバックオフ・ジッター | 統計用 | 不要 | 負荷を散らすだけ |
| アニメーション・パーティクル | 統計用 | 任意 | 速度がすべて |

## 3. 範囲 — 偏りのない整数

`%` で切ると、元になる値の幅が狭いほど分布が傾く。8 ビットの元値に `% 100` を掛けると
下位 56 個の値が **50% 多く**出る（実測比 1.499）。

```js
// 偏りのない [0, n) — 棄却抽出
function intBelow(next, n) {
  if (!Number.isInteger(n) || n <= 0) throw new RangeError('bound must be a positive integer');
  if (n > 4294967296) throw new RangeError('bound exceeds source width');
  const limit = 4294967296 - (4294967296 % n);
  let v;
  do { v = next(); } while (v >= limit);   // next() は uint32 を返す
  return v % n;
}

// 両端を含む [lo, hi]
function intBetween(next, lo, hi) {
  if (hi < lo) throw new RangeError('intBetween(lo, hi) needs hi >= lo');
  return lo + intBelow(next, hi - lo + 1);
}
```

- 32 ビットの元値では棄却の代償が平均 **1.00 回**、最悪でも **2.00 回**（実測）
- 8 ビットの元値に `% 100` なら棄却率 21.88%、その代わり偏りはゼロ
- 元値の幅が狭いほど偏りは大きい。8 ビットの `% 6` は 2.38%、32 ビットの `% 6` は 0.00000014%

## 4. 実数から整数への境界

| 書き方 | 実際の範囲 | 判定 |
|---|---|---|
| `Math.floor(r * n)` | 0..n-1 が一様 | **正しい**（半開区間） |
| `Math.floor(r * (n + 1))` | 0..n が一様 | **正しい**（閉区間） |
| `Math.round(r * n)` | 0..n、両端が半分の重み | **誤り** — 実測 5.01% 対 10.00% |
| `Math.ceil(r * n)` | 0..n、0 がほぼ出ない | **誤り** |
| `(r * n) \| 0` | 2^31 を超えると負になる | **誤り** — 幅 5e9 で -544967296 |

`[0, 1)` は半開区間である。500 万回の実測でちょうど 0 もちょうど 1 も出なかった。
1 の直前にある最大の実数を `floor(r * n)` に渡しても、n が 2^53 以下なら n-1 で止まる。

## 5. シャッフル

```js
// Fisher-Yates — j は 0..i からのみ引く
function shuffled(next, arr) {
  const x = arr.slice();
  for (let i = x.length - 1; i > 0; i--) {
    const j = intBelow(next, i + 1);
    const t = x[i]; x[i] = x[j]; x[j] = t;
  }
  return x;
}
```

4 要素、24 通りの順列、それぞれ 24 万回の実測:

| 方法 | 最小 | 最大 | 最大/最小 | カイ二乗 (df 23) |
|---|---|---|---|---|
| `sort(() => Math.random() - 0.5)` | 3,671 | 45,021 | **12.26** | 277,371 |
| 誤った Fisher-Yates（j を全範囲から） | 7,420 | 13,939 | 1.88 | 6,952 |
| Fisher-Yates（j を 0..i から） | 9,782 | 10,197 | 1.04 | **24** |

- 比較関数によるシャッフルは元の並びを **11 倍**残した（45,021 に対して期待値 10,000）
- 誤った Fisher-Yates は n^n 通りの経路を n! 通りの結果に分ける。n=4 なら 256/24 = 10.667 で整数にならず、一様は **不可能**
- 配列が長いほど偏りが表に出る。長さ 16 では先頭要素が動かない確率が 13.26%（公平な値は 6.25%）

## 6. シード

```js
// シードは省略可能な引数ではなく必須の引数
function statisticalRng(seed) {
  if (!Number.isInteger(seed)) throw new TypeError('statisticalRng(seed) requires an explicit integer seed');
  // ...
}
```

- 生成した入力で回す検査は、**シードを失敗報告に一緒に残す**
- シードがあれば失敗した入力が固定値になり、引用できる（実測: 再実行 3 回とも iteration 92, lo=30 hi=30）
- シードがなければ同じ検査 5 回が 5 通りの話をする（初回失敗は 8, 52, 119, 14, 32）
- **シードは再現のためであって安全のためではない。** シードを持つ生成器は定義上予測できる

## 7. グローバルな生成器を置かない

| 配置 | 単独で再現 | 並列で再現 | 順序が変わっても | 依存するもの |
|---|---|---|---|---|
| グローバルに 1 つ | いいえ | いいえ | いいえ | 呼び出し順とタイミング |
| 部品ごとに 1 つ | はい | はい | 部分的 | 部品内部での消費量 |
| 作業単位ごとに 1 つ | はい | はい | はい | なし |

同じシード、同じコードでも消費の順序を 3 通りに変えると、A が見た数列は
**3 通りとも違った**。生成器を分けて渡すと 3 通りとも一致した。作業単位ごとに
`シード + 作業 ID` から子の生成器を導けば、並列に回しても再現性が保たれる。

## 8. API 設計チェックリスト

- [ ] 関数の **名前に種類が現れている**（statistical / secure）
- [ ] 統計用は **シードが必須引数**。引数なしの形を作らない
- [ ] 安全用には **シード引数がそもそも存在しない**
- [ ] 範囲関数をライブラリが提供する（`intBelow`、`intBetween`）
- [ ] 範囲の名前が **開区間か閉区間かを述べる**（`below` は含まない、`between` は含む）
- [ ] シャッフルをライブラリが提供し、比較関数の裏技が現れる余地をなくす
- [ ] 生成器は **インスタンス**。グローバルな単一実体を公開しない
- [ ] 不正な引数は **投げる**。静かに変な値を返さない
- [ ] トークン生成は **安全用オブジェクトにのみ**存在する
- [ ] 既定値は慎重な側。速い側は意図して選ばせる
- [ ] 再現性の契約を文書に書く（版が上がっても同じ数列か）
- [ ] 配列は **変更せず複製を返す**（`shuffled` と過去分詞で示す）

## 9. やってはいけないこと

- 名前だけで種類を推測すること — 実測では 6 つの呼び出しが統計用 3、安全用 3 に分かれ、そのすべてに `random` が含まれていた
- トークンを統計用の生成器で作ること — 同じシードなら別の機械でも同じトークンが出る
- `%` で範囲を切ること — 元値が狭ければすぐ露見し、広ければ永久に露見しない
- `Math.round` で整数範囲を作ること — 両端が半分の重みになる
- `| 0` で切り捨てること — 2^31 を超える範囲で負の数が出る
- 比較関数で混ぜること — 並べ替えアルゴリズムと配列長で結果が変わる
- グローバルな生成器を複数箇所で共有すること — 再現性が呼び出し順に人質を取られる
- シードを「後で足せばよいもの」と後回しにすること — 再現はデバッグの前提である
