boring — Lightweight SSH Tunnel Manager with TOML Config: Practical Analysis

Replace long ssh -L/-R/-D one-liners with declarative TOML — local, remote, SOCKS5 explained and compared against autossh

2026-06-25 Dev & Infra

Introduction: Why SSH Tunnels Are Still Painful

SSH port forwarding is a daily tool for infrastructure engineers and developers alike. Reaching a DB behind a firewall, exposing a local dev service to a remote machine, or routing traffic through a SOCKS5 proxy — these are common tasks. Yet as of June 2026, the experience of managing them is still surprisingly primitive.

The typical workflow is: recall a 50-character ssh command, dig through shell history, paste it in, verify the PID, and repeat whenever the tunnel drops. When multiple tunnels are needed simultaneously, you check which ones are alive with ps aux | grep ssh, and reconnect each one manually. For team environments, sharing tunnel setup means writing out the full command in a Slack message or a README section that quickly goes stale.

boring, developed by alebeck on GitHub, targets this friction directly. Its tagline is "a simple command line SSH tunnel manager that just works." The core idea: declare all your tunnels in a single TOML file, then open or close any of them — or entire groups — with one short command. This analysis examines what that idea delivers in practice, where it beats existing tools, and where it does not.

1. What boring is — a Go-Based SSH Tunnel Daemon

boring is written in Go (95.5% of the codebase), MIT-licensed, and as of June 2026 is at v0.16.0 with 1,600+ GitHub stars, 266 commits, and Coveralls-tracked test coverage — signals of an actively maintained, production-ready project.

The architecture is minimal. When you first run a boring open command, it spawns a background daemon (boringd). Subsequent CLI calls communicate with that daemon via a Unix socket ($BORING_SOCK, defaulting to /tmp/boringd.sock). The daemon owns all SSH connections and handles reconnection; the CLI is just its thin front-end.

1.1 Installation

On macOS: brew install boring. On Linux and Windows, download a pre-built binary from the GitHub releases page and place it anywhere in $PATH. Source builds use make (Go 1.25+ required; Windows has a dedicated build_win.bat). Homebrew installations wire up bash, zsh, and fish shell completions automatically.

1.2 Config File Location

The config lives at ~/.boring.toml on macOS and Windows, or $XDG_CONFIG_HOME/boring/.boring.toml on Linux. Override with $BORING_CONFIG to maintain multiple environment-specific configs and swap between them.

2. Declarative TOML Configuration — What It Actually Looks Like

The real differentiator is the TOML file. SSH tunnels stop being ad-hoc commands you memorize and become named, version-controllable artifacts.

2.1 Basic Structure

# ~/.boring.toml

[[tunnels]]
name    = "dev-db"
local   = "5432"
remote  = "localhost:5432"
host    = "bastion"
mode    = "local"

[[tunnels]]
name     = "prod-redis"
local    = "6379"
remote   = "cache-01:6379"
host     = "prod-bastion"
user     = "deploy"
identity = "~/.ssh/id_prod"
group    = "prod"

[[tunnels]]
name       = "socks-proxy"
local      = "1080"
host       = "jump-server"
mode       = "socks"
keep_alive = 60

Each tunnel is a [[tunnels]] array entry. Fields are intentionally minimal. name is the CLI identifier; local and remote are addresses (port alone, host:port, or Unix socket path); host is the SSH target; mode picks the forwarding type.

2.2 Field Reference

FieldRequiredDefaultPurpose
nameYes—Tunnel identifier (used in CLI)
localYes*—Local bind address/port or Unix socket path
remoteYes*—Remote destination address/port or Unix socket path
hostYes—SSH target (ssh_config alias or hostname)
modeNolocallocal / remote / socks / socks-remote
userNossh_config → $USERSSH username
identityNodefault key filesPath to SSH private key
portNo22SSH port
groupNo—Group label for batch open/close
keep_aliveNo120Keep-alive interval in seconds

(*) remote is optional for socks mode since there is no fixed destination.

2.3 Why Declarative Config Matters Beyond Convenience

This is more than just "commands stored in a file." Because the config is a file, it lives naturally in version control. You can track when a tunnel was added, audit changes, and diff environments. Sharing with teammates is a file copy or a repo URL, not a wall of text in a chat message. And because the config is checked once at startup, typos surface before your workday begins — not mid-debugging session when a tunnel silently did not exist.

3. The Three Forwarding Modes — Differences and Real-World Use

boring's mode field maps directly to SSH's -L, -R, and -D flags. Understanding what each does is prerequisite to writing a useful TOML file.

3.1 Local Forwarding (mode = "local", SSH -L)

The most common pattern. Traffic arriving at a port on your local machine is forwarded through the SSH server to a specified remote destination. Direction: your machine → SSH server → remote target.

Practical scenario: a PostgreSQL instance at 192.168.1.100:5432 is only reachable from within the company network. With a local forward, localhost:5432 on your laptop connects directly to that DB.

[[tunnels]]
name   = "internal-db"
local  = "5432"
remote = "192.168.1.100:5432"
host   = "bastion"
mode   = "local"

Equivalent ssh command: ssh -L 5432:192.168.1.100:5432 -N bastion

3.2 Remote Forwarding (mode = "remote", SSH -R)

The reverse direction. Traffic arriving at a port on the remote SSH server is forwarded back to a local service. Direction: remote server → SSH tunnel → your machine.

Practical scenario: a web app running on your laptop (localhost:3000) needs to be accessible from a QA server for a demo. Remote forwarding exposes it without opening firewall rules or paying for ngrok. Anyone hitting qa-server:9000 reaches your local app.

[[tunnels]]
name   = "expose-dev"
local  = "3000"
remote = "0.0.0.0:9000"
host   = "qa-server"
mode   = "remote"

3.3 Dynamic Forwarding / SOCKS5 (mode = "socks", SSH -D)

Local and remote forwarding map one port to one destination. Dynamic forwarding turns the SSH server into a SOCKS5 proxy. Applications route traffic through this proxy, and the SSH server handles onward delivery to any host and port — no fixed destination is set at tunnel-open time.

Practical scenarios: browsing over public Wi-Fi with traffic encrypted via your trusted server; accessing multiple internal services without opening a separate tunnel for each; appearing to egress from a specific geographic IP.

[[tunnels]]
name  = "proxy"
local = "1080"
host  = "remote-server"
mode  = "socks"

Equivalent ssh command: ssh -D 1080 -N remote-server. Point your browser's SOCKS5 proxy setting to localhost:1080.

3.4 Unix Socket Support

The local and remote fields accept Unix socket paths instead of host:port. This makes Docker socket tunneling straightforward:

[[tunnels]]
name   = "docker-remote"
local  = "/tmp/remote-docker.sock"
remote = "/var/run/docker.sock"
host   = "remote-host"

With this tunnel open: DOCKER_HOST=unix:///tmp/remote-docker.sock docker ps operates against the remote daemon as if it were local.

4. CLI Commands — open, close, list

boring's CLI is intentionally compact. The commands you will use daily are few.

CommandShortDescription
boring open [name]oStart the named tunnel. -a starts all; -g group starts a group.
boring close [name]cStop the named tunnel. -a stops all.
boring listlShow all tunnels and their current status (open/closed). -g group to filter.
boring editeOpen the config file in $EDITOR.
boring versionvPrint version information.

The group feature pays dividends in multi-environment workflows. Tag all dev tunnels with group = "dev" and all prod-readonly tunnels with group = "prod-ro". Switching from dev to a prod investigation is two commands: boring close -g dev, boring open -g prod-ro. No command recollection required.

5. Comparison with autossh

autossh is the go-to tool for keeping SSH tunnel processes alive. The two tools are not in direct conflict — their strengths live in different operating contexts.

5.1 The autossh Approach

autossh wraps an SSH command and restarts it when the connection drops. For persistent always-on tunnels, the standard pattern is one systemd service unit per tunnel, each with ExecStart=autossh -M 0 ... and Restart=always. Adding a new tunnel means creating a new unit file, running systemctl daemon-reload and systemctl enable. It is robust but operationally verbose for dynamic usage.

5.2 The boring Approach

boring consolidates all tunnel definitions into one file and handles reconnection inside its own daemon. Adding a tunnel is a TOML edit — no unit file, no reload. boring open -a or targeted opens work immediately. The tradeoff is that boring does not integrate with systemd's dependency graph or boot-time startup without additional configuration (a launchd plist or a systemd user service wrapping the boring daemon).

5.3 When to Use Which

ScenarioBetter Choice
Server — tunnels that must survive reboots, boot on startupautossh + systemd
Developer workstation — many tunnels opened/closed throughout the dayboring
Team-shared, version-controlled tunnel definitionsboring (TOML in a repo)
Minimal dependencies, only standard toolsautossh

6. Integration with ssh_config

boring does not implement its own SSH stack. It reads and respects your existing ~/.ssh/config. The host field in TOML accepts any Host alias defined in ssh_config — ProxyJump chains, ProxyCommand directives, IdentityFile settings, and HostName rewrites all apply automatically.

This is a meaningful design choice. It means boring does not duplicate authentication logic. If your bastion already has multi-hop proxy config in ssh_config, boring inherits it for free. ssh-agent compatibility follows the same logic: if a key is loaded in the agent, tunnels open without a passphrase prompt.

7. A Practical Developer Workstation Config

Here is a representative ~/.boring.toml for a developer working across dev and production environments as of June 2026.

# ~/.boring.toml

# Dev environment group
[[tunnels]]
name   = "dev-pg"
local  = "5432"
remote = "pg-dev.internal:5432"
host   = "dev-bastion"
group  = "dev"

[[tunnels]]
name   = "dev-redis"
local  = "6379"
remote = "redis-dev.internal:6379"
host   = "dev-bastion"
group  = "dev"

[[tunnels]]
name   = "dev-api"
local  = "8080"
remote = "api-dev.internal:8080"
host   = "dev-bastion"
group  = "dev"

# Production read-only access
[[tunnels]]
name     = "prod-pg-ro"
local    = "15432"
remote   = "pg-prod.internal:5432"
host     = "prod-bastion"
user     = "readonly"
identity = "~/.ssh/id_prod_ro"
group    = "prod-readonly"

# General SOCKS5 proxy
[[tunnels]]
name       = "office-proxy"
local      = "1080"
host       = "office-gateway"
mode       = "socks"
keep_alive = 30

Morning workflow: boring open -g dev starts DB, Redis, and API tunnels in one shot. End of day: boring close -a. Production incident: boring open prod-pg-ro, investigate, boring close prod-pg-ro. No command memorization, no history digging.

8. Limitations to Know

8.1 Daemon Lifecycle Requires External Wiring for Auto-Start

boring's daemon does not register itself with the OS init system. For tunnels that must auto-start on login or system boot, you need a launchd plist (macOS) or a systemd user service (Linux) that starts the boring daemon. This is not hard to set up, but it is a step that autossh + systemd handles more naturally out of the box.

8.2 Single-User, Single-File Design

boring is designed for personal workstation use. There is no concept of centrally-managed tunnel policies, role-based access control, or audit logging across a team. For those requirements, SSH certificate authorities, Vault SSH, or similar infrastructure-level tools are appropriate.

8.3 socks-remote Mode Is Niche

The socks-remote mode (opens a SOCKS5 listener on the remote server side rather than locally) covers a narrow use case. The vast majority of workflows are served by local, remote, and socks. Knowing it exists prevents confusion when reading documentation, but do not expect to use it often.

9. Conclusion — Reducing Daily Friction Through Declarative Configuration

boring is not a paradigm shift. It does not change how SSH tunnels work. What it changes is how you think about them: from ephemeral commands you keep in your head to named artifacts you declare once and reference by name.

As of June 2026, boring at v0.16.0 is stable, cross-platform, and actively maintained. For developers and infrastructure engineers who manage a non-trivial number of SSH tunnels across environments, the investment in setting up a ~/.boring.toml pays back quickly. The friction reduction per week, multiplied across a career, is not trivial.

The right mental model: autossh + systemd owns server-side, always-on tunnel infrastructure. boring owns developer-workstation, context-switching tunnel management. They are complementary, not competing.
