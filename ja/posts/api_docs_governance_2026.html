序論: 文書が間違ったのではなく、間違えられる形に作ってあった

連携担当者からメールが届く。添付は API仕様書_v3_最終_最終2_修正版.xlsx。シートは十二枚、生きているのは四枚で、残りは消したことにしようと決めたものだ。パートナー企業はこのファイルを見てコードを書く。ところがサーバーは二か月前のリリースで応答フィールドの名前を一つ変えており、その事実はエクセルのどこにも反映されていない。連携は結合試験の最終日に壊れる。そして会議でこう言われる。「文書管理をもう少しきちんとやりましょう」。

この結論が間違っているという地点からこの記事は始まる。担当者が怠けたから起きた事故ではない。文書とコードがずれ得る構造をそのままにして、ずれないことを人の誠実さに委ねたことが事故の原因だ。誠実さは拡張しない。エンドポイントが三十個のときに通用したやり方は、三百個になれば必ず崩れる。

API文書が他の社内文書と違う点が一つある。読み手が人間だけではないことだ。API仕様は二つのプログラムの間の約束であり、約束は機械が突き合わせられて初めて強制される。エクセルとPDFの本当の問題は古臭さではなく突き合わせ不可能性にある。表計算に書かれた orderStatus: string は、サーバーが実際に何を出しているかと一度も比較されない。比較できないのだからずれても誰も気づかず、誰も気づかないのだからずれたまま数か月が過ぎる。

だからこの記事は「文書をうまく書く方法」を扱わない。ずれたら即座に露呈する設計を扱う。主張は三行だ。

  • 文書がコードとずれるのは人の怠慢ではなく更新の引き金が分離した構造の必然的な結果である。
  • 解決の第一歩は道具の導入ではなく単一の情報源をどこに置くか決め、残り全部を派生物へ格下げすることだ。
  • 自動化が捕まえられるものと捕まえられないものの境界は思ったより明確だ。境界を知らないまま道具を買っても同じ事故が起きる。

この記事が扱わないこと。 RAGの索引対象になる社内文書一般の老朽化とガバナンスは社内ナレッジベースは静かに腐るで扱った。この記事はそのうち機械が読むAPI契約という狭い軸だけを掘る。二つの記事に共通する所有者・有効期限・廃止手順はここでは繰り返さない。ツール間の通信規約そのものはMCP完全ガイドとMCPは終わったのかが、証券会社の公開API事例はトス証券OpenAPIが担う。

1. エクセル・PDF仕様が実際に失うもの - 媒体ではなく検証可能性

まず誤解を取り除こう。エクセルでAPIを整理する組織が遅れているわけではない。エクセルは参入障壁がほぼゼロで、表の編集が自由で、誰でも開ける優れた道具だ。初期のチームがエクセルで始めるのは合理的な選択である。問題はその選択を見直さないまま規模が大きくなるときに生じる。

1.1 機械可読でなければ検証もできない

OpenAPI仕様は自らをこう定義する。HTTP APIのための、プログラミング言語に依存しない標準インターフェース記述。要は標準と機械可読だ。形式が標準なら、その形式を読む道具が存在し、道具が存在すれば次の三つをパイプラインに載せられる。

  • 構文・規約検査 - この記述自体が有効か、社内の命名規則を守っているか
  • 版間の差分比較 - 前回のリリースから何が変わり、そのうち何が利用者を壊すか
  • 実装との突き合わせ - 記述したとおりにサーバーが実際に応答するか

エクセルとPDFはこの三つのどれも提供しない。正確に言えばできないのではなく誰も作らない。セル結合と自由書式が混ざった表からフィールド定義を安定して抽出するパーサーを保守するより、標準形式へ移すほうが安いからだ。

1.2 添付ファイルは配布ではなく複製だ

二つ目の損失はもっと静かだ。仕様をメールに添付した瞬間、正本は消えて写しだけが残る。パートナーAは三月に受け取ったファイルを、パートナーBは五月のファイルを見る。両方とも自分が最新を見ていると信じている。どちらが最新かを確かめる手段はファイル名しかなく、ファイル名は 最終 という単語を何回繰り返したかで決まる。

URLで配布すればこの問題の半分は消える。一つのアドレスが常に現行を指し、版タグ付きのアドレスが過去を保存する。残り半分、すなわち「そのURLの中身が実際のサーバーと同じか」は次節以降で扱う。

2. 文書がコードとずれる五つの経路

ずれは一つの原因では生じない。実務で繰り返し観察される経路は五つあり、経路ごとに塞ぎ方が違う。原因を分けずに道具から導入すると、見当違いの経路を塞ぐことになる。

2.1 経路① 更新の引き金の分離

最も多く、最も致命的だ。コード変更はマージという強制イベントを通るが、文書更新はそのイベントに紐づいていない。別のリポジトリ、別の担当者、別のスケジュールなら、遅れは確率ではなく時間の問題だ。処方は一つしかない。仕様ファイルをコードと同じリポジトリ、同じ変更要求の中に置くこと。OpenAPI Initiativeの学習文書も、仕様文書を運用コードと並べてバージョン管理すべき一級の原本ファイルとして扱えと記している。

2.2 経路② 写しの拡散

前節で扱った問題だ。正本の識別子がなければ、ずれを見つけてもどの写しを直すべきかが分からない。直しても他の写しはそのまま残る。

2.3 経路③ 形式が持てない取り決め

この経路は標準形式へ移しても残る。記述形式が表現できない約束は常にある。たとえばこういうものだ。

  • 金額フィールドが主単位か補助単位か、小数点は何桁まで有効か
  • 時刻文字列のタイムゾーンがUTCか現地時間か、オフセット表記は必須か
  • 再試行時の冪等キーをどう作り、どれだけ保持するか
  • 一覧取得のページング規約がオフセットかカーソルか、カーソルはいつ失効するか
  • 部分失敗のときどれが成功したかを応答のどこで読むか

これらの項目はスキーマに型としては書かれない。説明文に自然言語で書かれるか、書かれないまま口頭合意として残る。だから仕様を導入した組織もこの層では相変わらず事故を起こす。対策は二つ。説明フィールドを空のままにできないようリンターで強制すること、そしてこれらの規約を全社共通ルール一枚に固定して個別のAPIがそれを参照するようにすることだ。

2.4 経路④ 自動生成が作る錯覚

コードの注釈から文書を生成すればずれが消えると期待されがちだ。半分だけ正しい。生成器が読むのはコードではなく注釈であり、注釈は人が手で維持する。応答オブジェクトにフィールドを追加しながら注釈の更新を忘れれば、文書は自動生成物という理由でより強い信頼を得ながら間違ったまま配布される。手作業の文書より危険になり得る理由がここにある。

OpenAPI Initiativeがデザインファーストを勧める理由もこの結果の側にある。コードで作れるAPIの範囲がOpenAPIで記述できる範囲より広いため、先に実装してから合わせると直感的でなく不完全な記述が残りやすいというわけだ。

2.5 経路⑤ 消せないから膨らむ文書

最後の経路は時間が作る。古いエンドポイントと古いフィールドを消せないまま新しいものが積み上がる。消せない理由は誰が使っているか分からないからだ。使用量を計測していないので消したとき何が壊れるか分からず、分からないからそのまま置く。結果として仕様は現行と過去の混合物になり、読む人は何が生きているのか判別できない。この経路は文書ツールでは塞げない。廃止方針と使用量計測が必要だ。8節と9節で扱う。

3. 機械が読む契約とは何か - OpenAPIが標準化するものとしないもの

OpenAPI仕様はHTTP APIのインターフェースを言語中立に記述する標準だ。パスとメソッド、要求パラメータ、要求・応答本体のスキーマ、認証方式、エラー応答の形を定型構造に収める。ここで重要なのは収まらないものだ。業務ルールの意味、呼び出し順序、性能特性、料金方針は記述対象ではない。仕様は形の契約であって意味の契約ではない。

3.1 3.0と3.1の実質的な違い

版の選択で実務的に分かれる点はスキーマ言語だ。3.0はJSON Schemaの変形された部分集合を使っており、そのため nullable のような独自キーワードが生まれて道具の互換に混乱を招いた。2021年2月に公開された3.1はJSON Schema 2020-12と完全に整合し、有効なJSON Schema 2020-12文書はそのまま3.1のスキーマとして使える。ウェブフックの記述も3.1で正式に入った。

仕様自体の版体系は major.minor.patch であり、major.minorが機能集合を定め、patchは誤りの修正と説明の明確化だけを担う。つまり3.1.0と3.1.1は同じ機能集合だ。社内のツールチェーンが3.1を十分に支えるか確認しないまま上げると、道具のほうが先に壊れる。2026年7月時点でも3.1の対応度は道具ごとに差があるので、導入前に実際に使う生成器・文書化ツール・モックサーバーで試すほうが安全だ。

3.2 廃止表示はスキーマ層にもある

OpenAPIは操作オブジェクトに真偽値の deprecated フィールドを置き、その操作が廃止されたことを宣言する。利用者は使用を控えるべきだと規定されている。3.1ではスキーマがJSON Schema 2020-12に従うためフィールド単位の廃止も表現できる。JSON Schemaの deprecated は検証に影響しない注釈キーワードなので、値は依然として通過する点は知っておく必要がある。表示は信号であって強制ではない。

4. 単一の情報源をどこに置くか - 判断表

道具を選ぶ前に決めるべきは正本の位置だ。OpenAPI Initiativeの指針は単純である。情報は一か所にだけ存在すべきで、重複すれば必ずどちらかが分岐する。やむを得ず二か所に置くなら継続的統合のテストで一致を強制せよ、と付け加えている。

候補は五つだ。組織の状況によって正解が違うので表で整理する。

「この変更は大丈夫か」という問いを毎回勘で答えると、判定が人ごとに変わる。公開された指針を基準にするほうがよい。ここではグーグルのAPI設計指針AIP-180とストライプの公開方針を根拠に整理する。

5.1 表から読み取るべきこと

この表の値打ちは項目の暗記ではなく二つの原理にある。

  • 追加はおおむね安全で、削除と変更はおおむね危険だ。だから成熟したAPIはフィールドを消す代わりに増やし続け、代わりに廃止手順で整理する。
  • 安全かどうかはサーバーではなく利用者の寛容度にかかっている。未知フィールドを無視し未知の列挙値に耐えるクライアントを前提にして初めて「追加は安全」が成り立つ。だからこの寛容規則を利用者側の文書にも明記しなければならない。

5.2 ストライプ式の日付版が与える教訓

ストライプはメジャーリリースにだけ非互換の変更を入れ、月次リリースは互換の変更のみを含むと公表している。同社のブログには新しい応答を古い形式へ戻す小さく独立した変換モジュールを積み上げて過去の版を維持しているという説明がある。この方式の代価は明確だ。変換層が永遠に積み上がる。大半の組織には過剰な選択だが、ここから持ち帰る原則は一つ。非互換の変更をいつでも流さず、一点に集めること。

6. 契約テストは何を保証し、何を保証しないのか

仕様があってもサーバーが仕様どおりに応答するかは別の問題だ。この隙間を埋める代表的な手法が利用者主導の契約テストである。

6.1 定義から正確に

Pactの公式文書は契約テストを連携点を各アプリケーション単独で検査し、送受信するメッセージが契約に文書化された共通理解に適合するかを確かめる手法と定義する。利用者側のテストを実行する間にテストダブルとやり取りした相互作用が記録されて契約が作られ、提供者側はその契約を再生して検証する。二つのサービスを同時に立ち上げずに連携を検査できる点が核心の利点だ。

6.2 境界をはっきりさせる

同じ文書は限界も明確に記している。この部分が実務で最もよく誤解される。

  • 契約はあらゆる状態を記述するスキーマとは違う。具体的な要求・応答の組を複数実行することで強制される。
  • したがって利用者が実際に使う部分だけが検査される。誰も呼ばないフィールドは契約になく、なければ守られない。
  • 提供者側の契約テストだけでは利用者が正しい方法で呼び出しているという保証は得られない。
  • 利用者の参加があって初めて成立する。誰が使っているか分からない公開APIにはそのまま適用しにくい。

まとめると契約テストは仕様リンティングや破壊的変更検出を置き換えない。層が違う。仕様は広く浅く、契約は狭く深く覆う。両方なければ何も覆われず、片方だけならその側だけが覆われる。

7. CIで自動検証できるものとできないもの

この節がこの記事の実質的な核心だ。境界を知らないまま道具を導入しても同じ事故が起きる。項目ごとに自動化の可否を分ける。

検証項目自動化道具の種類残る危険
仕様文書の構文的妥当性完全に可能仕様検証器なし。通らなければマージを止めればよい
社内スタイル規約の遵守完全に可能リンター(Spectralなど)ルールにない慣行は検査されない
説明・例の欠落可能リンター規則埋まっているかが分かるだけで内容が正しいかは分からない

実装が仕様どおり応答するか部分的に可能属性ベーステスト(Schemathesisなど)生成しにくい状態や副作用が必要な経路は未検査

7.1 リンターが捕まえるものと捕まえないもの

Spectralは自らをAPIスタイルガイドの強制装置であり柔軟なJSON・YAMLリンターと紹介している。OpenAPI 2.0・3.0・3.1、AsyncAPI 2.x、Arazzo 1.0を標準で支え、ルール束を定義して社内規約を強制する。組み込み関数でパターン検査、パラメータ検査、アルファベット順、文字数、特定キーの存在を確認でき、必要なら関数を自作できる。

ここで決定的な限界が一つ。リンターは仕様文書しか見ない。サーバーが何を応答するかは知らない。リントで満点を取ってもその仕様が現実と違い得る。この点をチームに明確に共有しないと、リント通過が正確性の保証のように消費される錯覚が生まれる。

7.2 差分比較と実装の突き合わせ

oasdiffは二つの仕様の差分を機械可読な形で出し、利用者を壊す可能性のある変更を規則で表示する。プロジェクトは破壊的・非破壊的な変更506種を識別すると述べており、破壊的変更があれば終了コード1を返してCI段階を失敗させられる。GitHubアクションは変更要求の時点で基準ブランチと比較してインライン注釈を残す。

Schemathesisは方向が違う。OpenAPI・GraphQLスキーマからテスト事例を自動生成して実際に呼び出し、応答がスキーマに適合するかを検査する。スキーマが文書化していないフィールドをコードが返したり、文字列を約束した場所にnullが来る遅い漂流を捕まえる点がこの手法の要旨だ。

# 例示パイプライン - コマンドの形は道具の版によって違うので公式文書の確認が必要

# 1) 仕様の構文・社内スタイル検査
spectral lint openapi.yaml --ruleset .spectral.yaml

# 2) 基準ブランチに対する破壊的変更の検出 (発見時は終了コード1)
oasdiff breaking base/openapi.yaml head/openapi.yaml

# 3) ステージングサーバーが仕様どおり応答するかの突き合わせ
schemathesis run openapi.yaml --url https://staging.example.com

7.3 導入の順序を間違えると反発だけを買う

三段階を一度に遮断条件として有効にすると既存の仕様から数百件があふれ、チームはルールを切る方向で対応する。実戦で通用する順序はこうだ。

  • 1週目: 構文検証だけを遮断条件に。残りは警告としてのみ出力
  • 2〜4週目: リンター規則を新規の変更分にだけ適用。既存の違反は一覧として固定し漸進的に返済
  • 5週目以降: 破壊的変更の検出を遮断条件に。ただし承認手順を同時に作り、意図した非互換の変更は通す
  • 実装の突き合わせと契約テストは最も重要なエンドポイント数個から始める

8. 廃止方針に必ず入れる項目

文書が膨らむのを止める唯一の仕掛けが廃止手順だ。方針文書に入るべき項目を公開事例と標準文書を基準に整理する。

  • 宣言の場所 - 廃止は仕様の中に表示する。Zalandoの公開指針は、エンドポイント・入力引数・オブジェクト・プロパティを廃止する際に deprecated: true を設定し説明項目に理由を書くよう求めている。
  • 最短告知期間 - 業界標準の数字はない。グーグルクラウドの利用規約はサービス終了や顧客向けAPIの後方互換でない重大な変更の前に少なくとも12か月の通知を記し、マイクロソフトグラフの文書は正式提供APIの削除少なくとも24か月前の廃止宣言を明記している。自社の基準は利用者の性格に合わせて決めればよい。
  • 応答ヘッダーの信号 - RFC 9745が定義した Deprecation ヘッダーとRFC 8594が定義した Sunset ヘッダーを併用する。Sunsetの時刻はDeprecationの時刻より前にできない。
  • 案内リンク - 二つのRFCはいずれもリンク関係型を定義している。方針・移行案内の文書を rel 値でつなぐ。
  • 代替の明示 - 何へ移るべきか、フィールドの対応がどうなるかを書く。Zalandoの指針も代替手段と移行方法を詳細に文書化するよう求めている。
  • 使用量の計測 - 同じ指針はAPI所有者が移行の進み具合を観測して制御不能な波及を防ぐよう求めている。利用者別の残存呼び出し量が見えなければ終了時点を決められない。
  • 外部利用者との合意 - 外部パートナーがいる場合は廃止後の維持期間を定めて当事者の同意を得ておく。
  • 終了の方式 - ある日突然切るのか、短時間だけ遮断して残存利用者に信号を送るのか、エラー率を段階的に上げるのかを事前に決める。
  • 例外条項 - 保安上の脆弱性や法令遵守の事由があれば期間が短縮され得ることを明記する。グーグルクラウドの規約も同じ例外を置いている。

8.1 仕様とヘッダーにはどう書かれるか

# openapi.yaml - 操作単位の廃止表示
paths:
  /v1/orders/{orderId}:
    get:
      operationId: getOrderV1
      deprecated: true
      summary: 注文詳細の取得 (廃止予定)
      description: |
        2026-09-01に終了予定。代替パスは GET /v2/orders/{orderId} である。
        marketing_agree フィールドは consents[].marketing へ移動した。
        移行案内: https://api.example.com/docs/migrate/orders-v2
      responses:
        '200':
          description: 注文詳細
HTTP/1.1 200 OK
Content-Type: application/json
Deprecation: @1785196800
Sunset: Tue, 01 Sep 2026 00:00:00 GMT
Link: <https://api.example.com/docs/migrate/orders-v2>; rel="deprecation"

Deprecation ヘッダーの値は構造化フィールド形式の日付なので @ の後に秒単位の整数が来る。Sunset ヘッダーの値はHTTP日付形式だ。RFC 8594はSunsetの時刻をヒントとして扱うべきであり、そのときまで可用性が保証されるわけではないと明記している。つまりヘッダーは約束ではなく信号だ。約束は方針文書と合意が作る。

9. 文書の鮮度指標 - 何を計測すればずれが見えるか

ずれは障害を起こさない。警報も鳴らない。だから計測しなければ永遠に見えない。以下の指標はほとんどが既存のリポジトリとアクセスログだけで計算できる。

指標計算読み方
仕様の遅れハンドラーコードの最終変更日 − 該当パスの仕様の最終変更日正の区間が長いほど漂流。パス別の最大値を週次で見る
幽霊パス数仕様にあるがルーティング表にないパスの数0でなければ文書を信じて書いた利用者が壊れる
未文書化パス数ルーティングにあるが仕様にないパスの数内部用の臨時パスが外部に開いている危険も同時に露呈する
説明欠落率説明が空の操作・フィールド ÷ 全体リンターで毎日算出。傾向を見るだけでも十分だ
例の保有率要求・応答の例がある操作の比率パートナーの導入時の問い合わせ量とよく連動する
契約テスト適用率利用者契約が存在するパス ÷ 外部公開パス適用外の領域が実際に事故の起きる場所だ
廃止の残存呼び出しdeprecated表示のパスの利用者別の日次呼び出し数0に収束しなければ終了時点を先送りすべきだ
廃止からの経過日宣言日からの経過日数と残存呼び出しの交差期間だけ満たして終了すると事故になる
差分比較の警告件数変更要求あたりに検出された破壊的変更の件数急に増えたら設計合意が崩れている信号

全部を見る必要はない。始めは二つで十分だ。幽霊パス数と未文書化パス数である。この二つはルーティング表のダンプと仕様ファイルさえあれば計算でき、値が0でない瞬間にいまこの文書が間違っているという事実を異論なく示す。会議で優先順位を得るのに最も効く数字でもある。

10. エクセル・PDFで管理している組織の移行順序

最もよくある失敗は全数移行だ。200のエンドポイントを一度に移そうとして三か月後に中断し、エクセルへ戻る。順序を変えれば違う。

10.1 0段階 - 正本を一つ決める (数日)

  • 出回っている写しを集めて現行の正本を一つ指定し、残りに廃止の表示を残す。削除は後で行う。
  • アクセスログで実際の呼び出し量の上位20パスを抜き出す。移行対象はこの20だ。
  • 利用者の一覧を作る。社内チーム、外部パートナー、正体不明の呼び出しの三つに分ける。

10.2 1段階 - 上位20だけを仕様へ (2〜3週)

  • 既存文書と実際のトラフィックを突き合わせ実際の動作を基準に書く。エクセルの記載と違えば実際が正解だ。
  • 仕様ファイルをサーバーコードと同じリポジトリに置く。この一つが経路①を塞ぐ。
  • 3.0で始めるか3.1へ行くかは使う道具が支える範囲で決める。最新が常に正解ではない。

10.3 2段階 - パイプラインへ載せる (2週)

  • 構文検証をマージの遮断条件にする。
  • リンターは警告段階だけで有効にする。この時点で遮断すると反発が来る。
  • 仕様から文書ページを生成してURLで配布する。ここからエクセルの添付をやめる。

10.4 3段階 - 変更統制 (3〜4週)

  • 変更要求で基準ブランチとの差分比較を回し、破壊的変更を表示する。
  • 非互換の変更の承認手順を作る。承認なしに通らないようにしつつ、承認経路は短く保つ。
  • 5節の分類表をチームのウィキに貼り判定基準を共有する。

10.5 4段階 - 実装の突き合わせと契約 (4週以上)

  • ステージング環境にスキーマ適合検査を付けて実際の応答と仕様を突き合わせる。
  • 最も協力的な利用者一チームと契約テストを試験導入する。全面導入はその次だ。
  • 廃止方針を文書化しヘッダーの信号を付ける。同時に残存呼び出しの計測を始める。

10.6 やってはいけないこと

  • 道具から選ぶこと。正本の位置が決まらなければどの道具も居場所を得られない。
  • 全パスの同時移行。呼び出し量の上位2割がたいてい事故の大半を作る。
  • 初週から全面遮断。ルールを切る文化ができると戻すのが難しい。
  • エクセルを併存させること。二つの正本は必ず分岐する。移したら古いファイルは読み取り専用で施錠する。

11. この仕組みが防げないこと

誇張せずに整理する。ここに書いたことを全部やってもずれは消えない。変わるのはずれが露呈する速さと費用だ。残る穴はこうだ。

  • 意味は相変わらず人が守る。仕様は形の契約だ。金額の単位、タイムゾーン、冪等の規約のように説明文へ自然言語で書かれる約束は、どの検査器も検証できない。
  • デザインファーストが常に正しいわけではない。OpenAPI Initiativeもコードファーストのほうが始めやすい点は認めている。要件が揺れる初期段階で仕様から確定すると、仕様を直すことに時間を全部使う。
  • 自動生成は不正確な実装をそのまま文書化する。生成されたという事実は正確さを意味しない。
  • 契約テストは参加者がいて成立する。利用者が誰か分からない公開APIには別の手法が要る。
  • リント通過は正確性の保証ではない。スタイルしか見ない。
  • 所有者がいなければ道具は無力だ。警報が鳴っても受け取る人がいなければ警報は雑音になる。

だから目標をずれ0に置くと失敗する。現実的な目標はこうだ。ずれが配布の時点で露呈し、露呈してから直す費用が結合試験の最終日に発見する費用よりはるかに安くなるようにすること。

結論: 誠実さの代わりに構造へ委ねよう

エクセル仕様を使う組織に必要なのは訓戒ではない。担当者はすでに十分に誠実だ。問題は誠実さが唯一の防衛線だという点にある。防衛線が一つなら、その一つが休む日に破られる。

変えるべきものは三つだけだ。第一に正本を一か所へ固定し残りを派生物へ格下げする。第二に正本をコードと同じ変更要求の中に入れて更新の引き金を合わせる。第三に機械が突き合わせられる形式へ変えてずれが自動的に露呈するようにする。この三つをやれば、リンターも差分比較も契約テストもその上に載せるだけのものになる。順序を逆にして道具から買えば同じ事故がより高い形で再発する。

最後にこの記事から一番長く残したい一文。文書が間違うのは事故ではなく設計の結果だ。間違え得る構造をそのままにすればいつか必ず間違う。逆に間違えば即座に露呈する構造を作っておけば、人が怠けてもシステムが耐える。文書管理は誠実さの問題ではなく構造の問題だ。

来週の月曜にやることは一つ。ルーティング表をダンプして現在の仕様と突き合わせ、どちらかにないパスの数を数えてみること。その数字が0でなければ、答えはすでに出ている。

# API 廃止(Deprecation)ポリシー チェックリスト

> 出典: braindetox.kr — APIドキュメントはなぜ常にコードより遅れるのか
> 規格根拠: RFC 8594(Sunsetヘッダー)、RFC 9745(Deprecationヘッダー)
> このファイルをそのままAIに貼り、「自社の基準で埋めて」と指示できます。

## 1. ポリシー文書に必ず明記すること
- [ ] 廃止予告期間(例: GAは最低__か月 / プレビューは最低__週)
- [ ] 予告開始時点の定義(告知日か、ドキュメント反映日か)
- [ ] 互換変更と非互換変更の境界(下の表2で合意)
- [ ] 例外条項 — 脆弱性対応で予告期間を短縮できるか
- [ ] 廃止後の応答(410 Goneか、200を返し続けるか)
- [ ] 通知手段(ヘッダー / 変更履歴 / メール / ダッシュボードのどれが正式か)

## 2. 変更種別の分類 — 決めておかないと毎回もめる
| 変更 | 分類 | 廃止手続き |
|---|---|---|
| 任意フィールドの追加 | 互換 | 不要 |
| フィールド削除 | 非互換 | 必要 |
| フィールド型の変更 | 非互換 | 必要 |
| enum値の追加 | **論点** | 利用側が厳格にパースしていれば非互換 |
| 必須パラメータ追加 | 非互換 | 必要 |
| エラーコード追加 | **論点** | コードで分岐する利用者がいれば非互換 |
| 並び順の変更 | **論点** | 保証を明記していなければ互換 |

## 3. 機械が読む信号(人向け告知だけでは足りない)
- [ ] `Deprecation` レスポンスヘッダー — RFC 9745
- [ ] `Sunset` レスポンスヘッダー — RFC 8594、実際の終了時刻
- [ ] `Link` ヘッダーに `rel="deprecation"` で案内文書を接続
- [ ] OpenAPI仕様に `deprecated: true`
- [ ] 上記3つが **異なる日付を指していないか** をCIで検査

## 4. 停止する前に確認すること
- [ ] 直近30日の残存呼び出し数(ゼロでなければ止めない)
- [ ] 残った呼び出し元を特定できるか(APIキー / User-Agent / 契約単位)
- [ ] このエンドポイントを使う社内システム — 事故はたいていここで起きる
- [ ] 代替経路が **同等の機能** を提供するか(部分的なら廃止不可)
- [ ] ロールバック手段 — 止めた後に戻せるか

## 5. よくある失敗
- ドキュメントに「非対応」と書いただけでヘッダーを送っていない → 誰も気づかない
- 予告はしたが **残存呼び出しを数えずに** 停止した
- 代替APIは作ったが **移行ガイドがない**
- 廃止日を複数の文書に書き、日付が食い違っている
