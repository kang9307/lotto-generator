起因 — 发现#[derive(...)]隐式携带的#[inline]

在Rust中，实现Debug、Display、Clone等核心trait最常见的办法就是#[derive(...)]。yossarian在2026年10月3日的TIL文章中写道，他直到最近才知道Rust目前会在这些派生代码中一并生成#[inline]。他说这看起来并没有被保证，但reference的示例暗示了这一点，展开宏也能亲眼看到。Rust Reference的derive一章在讲解#[automatically_derived]的示例里，Clone实现上方确实带着#[inline]。

原文并不是在抱怨这一行为，反而认为它几乎总是我们想要的：#[inline]只是提示，派生出的Debug、Clone等实现通常内容很简单，能从内联中受益。不过他也指出并非总是如此，并举了一个字段众多、层层包裹的错误层级作为反例。这类类型的Debug实现若在每个日志调用处都被内联，代码就会膨胀，这正是全文的要点。

本文把资料分成三层来读。第一层是原文直接说的内容，即展开结果和uv缩小约160KB的经验。第二层是rust-lang/rust的PR页面上留下的记录，即PR #117727和#118031（原文并未提到这两个编号）。第三层是直接从当前rustc源码读到的事实。只有在这几层交汇之处才加入解读，并逐句注明是谁说的。

通过宏展开查看编译器生成的真实代码

验证方法原文已经给出：把宏展开来看。原文从最简单的结构体开始。

#[derive(Debug)]
                    struct Widgets {
                        foo: u32,
                        bar: usize,
                    }

原文展示，在Playground中展开后得到如下实现。

struct Widgets {
                        foo: u32,
                        bar: usize,
                    }
                    #[automatically_derived]
                    impl ::core::fmt::Debug for Widgets {
                        #[inline]
                        fn fmt(&self, f: &mut ::core::fmt::Formatter) -> ::core::fmt::Result {
                            ::core::fmt::Formatter::debug_struct_field2_finish(
                                f,
                                "Widgets",
                                "foo",
                                &self.foo,
                                "bar",
                                &&self.bar,
                            )
                        }
                    }

值得注意的是fmt正上方的#[inline]。开发者并没有写，是derive加上的。整个函数体就是一次debug_struct_field2_finish调用，宏自己并不做任何格式化，只是把类型名、字段名和字段值的引用转交给Formatter上的辅助方法，真正的格式化由辅助方法完成。只有最后一个字段多了一层引用（&&self.bar）。rustc源码里的注释解释了原因：大小不定（unsized）的类型需要多一层间接，而这种类型只允许出现在最后一个字段。

#[inline]到底起什么作用，各来源的说法略有不同。原文称它只是提示（just a hint）。在Lobste.rs的讨论中，tsion反驳说并不只是提示：泛型函数始终可以跨crate内联，非泛型函数默认则不行，#[inline]使它成为可能。在PR #117727的评论中，saethlin也给出类似的说明：这个属性只是给LLVM加上inlinehint，最终是否内联由LLVM决定，但同时它会让函数成为MIR内联的候选，被延迟lowering，有时还会被lowering多次。

再交代一下范围。Rust Reference列出了九个内置derive：Clone、Copy、Debug、Default、Eq、Hash、Ord、PartialEq、PartialOrd，并说明它们生成的实现带有automatically_derived属性。至于编译器是否会自动给很小的函数加#[inline]，Lobste.rs上ralfj的回答是会：真正很小的函数会被自动加上。

深度嵌套错误类型与内联膨胀机制

两个字段的结构体，其Debug函数体只有一次调用，内联几乎没有负担。原文说情况并不都是这样，请读者设想如下的错误层级。

  • ErrorA: 含7个String字段（lots, of, chunky, fields, within, this, type）的结构体。
  • ErrorB: 以inner字段持有ErrorA的结构体。
  • ErrorC: 以inner字段持有ErrorB的结构体。
  • Errors: 含A(ErrorA)、B(ErrorB)、C(ErrorC)三个变体的枚举。
  • Default: 原文的展开结果中只出现了ErrorA的default实现，它同样带有#[inline]。输入代码的derive行里只写了Debug，所以原文内部的输入与输出并不一致。

在原文给出的展开结果中，ErrorA的fmt先构造字段名字符串切片数组（names）和&dyn Debug值数组（values），再调用debug_struct_fields_finish。ErrorB和ErrorC各只调用一次debug_struct_field1_finish，Errors用match分支，为每个变体调用debug_tuple_field1_finish。只有7个字段的类型使用数组，原因在rustc源码里：deriving/debug.rs中的CUTOFF常量为5，字段不超过5个时不建数组，直接调用与字段数对应的专用方法（如debug_struct_field2_finish），超过5个才构造数组。

原文担心的是，这些代码可能在每个调用Errors的Debug的地方被内联。原文写道，这样的调用例如会在debug或trace日志中反复出现。脚注补充说，这个层级是大幅简化过的，现实中的Rust应用常有字段数不少、嵌套很深的错误枚举。原文没有给出这种内联会增加多少行汇编，因此本文也不去估计这个数字。

uv实践案例：缩减约160KB与缺失的基准条件

原文最核心的数字只有一句话：这么多代码可能占到Rust二进制总体积中不可忽视的一部分，在uv中，阻止rustc内联某个Debug实现后，二进制缩小了约160KB。原文用词是a given Debug implementation，所以这160KB是针对指定的那个实现，而不是所有Debug实现。

做法写在脚注里：团队新增了一个自己的过程宏，也就是接收条目的token并返回新代码的编译器插件，derive本身也是用同样的机制实现的。它的行为与derive(Debug)相同，只是带上#[inline(never)]。另外，160KB是一个没有分母的绝对数字：原文没有写uv二进制本身有多大，因此无法换算成比例。原文说自己吃惊的地方有两点：体积成本很快累积，以及rustc（看上去）没有对Debug实现被内联的大小或次数设限。紧接着作者补充说，他怀疑这在许多程序中是正确的决定。这不是在批评编译器的默认值，而是对一个案例的报告。

编译器视角下的权衡 — 2023年PR与基准测试

给派生Debug加上#[inline]的改动是rust-lang/rust的PR #117727（标题为「Emit #[inline] on derive(Debug)」）。这个PR由saethlin于2023年11月8日提出，次日9日合并。原文没有提到这个PR，所以以下内容全部基于PR页面。PR正文很短：在处理PR #116583时，作者注意到cross_crate_inlinable查询把许多派生的Debug实现识别为「不过是一次调用而已（little more than a call）的MIR函数体」，这暗示它们可能是#[inline]的好候选，于是单独实现了这一改动，看起来对build times有不错的改善。下面引用的对比数据来自rust-timer机器人：它用rustc-perf对该PR的try构建做基准测试，并与父提交比较。机器人自己说明，instruction count是用来判定总体结果的高可靠性指标，而max RSS、cycles和二进制大小是没有用于判定的较不可靠的指标。

  • perf结果：首次try构建的instruction count中，primary基准111项里有107项改善（平均-2.4%），4项回归（平均+0.5%）。机器人的总评是回归与改善并存。二进制大小指标在primary中为改善113项（平均-2.7%）、回归26项（平均+0.9%）。instruction count的secondary中为改善163项（平均-3.4%）、回归4项（平均+2.7%）。引导构建从663.159秒变为673.479秒，慢了1.56%，产物体积从308.75MiB增至308.99MiB，增加0.08%。
  • 审阅者的反应：nnethercote说，fmt上原先没有inline是有意为之，想法是它不是热点代码，不应该被内联。但他无法反驳perf结果，写下「faster and smaller binaries」，并补充说引导构建慢了10秒、编译器产物略微变大这点令他不解。
  • 原因假说：Noratrieb猜测提速的原因很简单。带#[inline]的函数会在下游才生成代码，如果是死代码则根本不会生成，而Debug实现常常是死代码。他以hello world基准的链接明显变快作为依据。这是评论里的假说，不是PR正文的内容。
  • 另一种假说：scottmcm认为这是改用debug_tuple_field4_finish之类辅助函数后的一个幸运结果。这些辅助函数不是#[inline]，所以被内联的fmt只是做指针投影和vtable指针复制，然后调用一次。他还表示，不做代码生成的check构建为何会快这么多，令他困惑。
  • 合并之后：合并后的perf运行里，primary的instruction回归有5项（平均3.1%，最大13.7%），改善有110项（平均-2.3%）。saethlin判断大的回归似乎是收集器变慢所致，并加上了perf-regression-triaged标签。

按字段数区分的建议，是在合并之后的PR #117727评论中提出的。RalfJung问，能否只对字段不超过5个的结构体加这个属性（枚举和更大的结构体不加），saethlin在11月18日以PR #118031试了一下。该PR的实际标题是「Try not applying #[inline] to big structs」，状态是未合并就关闭。改动是只对字段超过5个的结构体去掉#[inline]，枚举保持不变。结果是全面回归：instruction count的primary中回归54项（平均+1.5%），改善为0项。同一次运行中，cycles的primary回归33项（平均+2.3%），改善0项；二进制大小的primary回归66项（平均+2.4%），改善4项（-0.2%）；引导构建时间几乎不变（-0.19%）。saethlin回答说这是「huge regression」，并总结说死代码效应和MIR优化效应似乎都很重要。因此，「5个字段以内」是一次尝试后被关闭的实验的阈值，而不是已合并的策略。

把两个PR并排看，能看出一点。两者都是用同一套基准测试判定的，都没有测量uv这种形态的二进制。PR #117727的二进制大小指标本身也是有的基准改善、有的回归，所以整套基准的整体改善与某个具体程序中缩小160KB并不矛盾。

Lobste.rs上也出现了针对同一现象的假说。ralfj猜测，原因之一是许多Debug实现从未被调用，加了#[inline]就根本不必为它们生成代码，这与Noratrieb的假说方向一致。evmar则问，从不被调用的函数不是反正会从最终二进制中去掉吗，这对编译时间有影响，但与运行时间有何关系。yshui认为这是Rust过程宏基于token而不是实际类型工作所带来的局限：如果有类型信息，就可以看嵌套有多深，太深时不再加#[inline]。这些都是假说或疑问。

表中值得注意的是Eq。源码注释解释说这个方法从不被调用，所以这里加#[inline]的目的是避免代码生成，可见同一个属性在不同的derive里性质并不相同。另外在Lobste.rs上，kornel写道，Ord和Eq、也许Clone带内联在他意料之中，Debug带内联则出乎意料，他自己会给fmt实现加#[cold]。在同一讨论中，ralfj解释说内联默认值之所以难选，是因为要在代码体积、编译时间和运行时间之间取舍。原文作者也回应了类似的意思：他认为Rust在这里选不出完美的默认值或启发式。

原文与讨论提供的应对办法

原文本身直接给出的应对只有一条，其余是同一话题的讨论中出现的意见。下面每条都注明是谁说的。

  • 展开查看：这是原文使用的方法。在Playground或宏展开工具中展开可疑类型的derive，看带#[inline]的函数体有多长。字段在6个以上时会采用建数组的形式，这一点由上面的源码核对说明。
  • 自定义过程宏：这是uv采取的做法。自己写一个行为类似derive(Debug)但带#[inline(never)]的宏并应用。原文没有写宏的名称，也没有说是否公开。
  • 使用#[cold]：这是Lobste.rs上的kornel说自己在fmt实现上采用的方式。derive生成的代码无法手工添加，所以这指的是手写实现。
  • 向编译器方面反馈：Lobste.rs上ralfj说，这值得在rust-lang/rust提一个bug报告。内联默认值过去改过，将来也可以再改，如果收到多份说启发式不佳的反馈，就有理由重新调整平衡。原文作者回复说这周会提交。
  • 拆到crate中：Lobste.rs上的schneems认为这个选择可以推给crate，分别提供cold和inline版本的Debug派生，或用容器属性来选择。尚未实现，只是一个人的设想。
  • 在自己的构建中直接对比：160KB是uv的数值，原文没有写目标平台和设置。同样的效果在自己的二进制中是否存在，只能针对一个可疑类型实测前后体积来判断。
