databow와 ADBC 분석 - 컬럼형 zero-copy로 여러 DB를 쿼리하는 커맨드라인 도구

Apache Arrow가 만든 ADBC 표준이 ODBC·JDBC의 row 지향 병목을 걷어낸다 - psql·usql·DuckDB CLI와 무엇이 다른가

2026-07-06 개발/인프라

서론: 왜 지금 databow와 ADBC인가

데이터 엔지니어나 분석가라면 익숙한 장면이 있다. 운영 DB는 PostgreSQL, 분석용 웨어하우스는 Snowflake나 BigQuery, 로컬 실험은 DuckDB나 SQLite. 쿼리 하나 돌리려면 매번 다른 클라이언트를 열고, 다른 접속 문법을 외우고, 결과 포맷도 제각각이다. 2026년 7월 기준 이 문제를 정면으로 겨냥한 도구가 databow다. GeekNews에 소개된 이 도구는 Columnar라는 회사가 만든 Rust 기반 커맨드라인 SQL 클라이언트로, ADBC(Arrow Database Connectivity)라는 Apache Arrow 프로젝트의 표준 위에서 동작한다.

이 글은 databow 자체보다 그 밑에 깔린 ADBC라는 발상을 더 비중 있게 다룬다. CLI 도구는 얼마든지 나왔다 사라지지만, DB마다 다른 프로토콜을 컬럼형 Arrow 데이터로 통일한다는 아이디어는 앞으로 몇 년간 데이터 도구 생태계 전반에 영향을 줄 구조적 변화라고 본다. 커맨드라인에서 여러 DB를 오가는 실무자 관점에서, 이 도구가 psql·usql·DuckDB CLI와 근본적으로 어떻게 다른지, 그리고 지금 당장 실무에 투입해도 되는지를 냉정하게 짚어본다.

1. ADBC란 무엇인가 - Apache Arrow의 DB 커넥티비티 표준

1.1 왜 만들어졌나

ADBC는 Apache Arrow 프로젝트가 2023년 초 공개한 API 표준이다. 목적은 단순하다. 서로 다른 데이터베이스에서 데이터를 가져올 때, 클라이언트마다 제각각인 프로토콜을 거치지 않고 Arrow 컬럼형 포맷으로 직접 데이터를 주고받는 단일 API를 제공하는 것이다. Arrow 자체는 언어와 프로세스 경계를 넘나들며 데이터를 복사 없이 공유하도록 설계된 인메모리 컬럼형 포맷이라, ADBC는 그 Arrow 생태계를 DB 접속 계층까지 확장한 셈이다.

1.2 ODBC·JDBC와 근본적으로 다른 지점

ODBC와 JDBC는 수십 년간 DB 연결의 사실상 표준이었지만 둘 다 row(행) 지향으로 설계됐다. JDBC는 API 자체가 행 단위로 값을 꺼내도록 짜여 있어 Arrow 같은 컬럼형 포맷으로 효율적으로 연결하기가 구조적으로 어렵다. ODBC는 블록 커서로 벌크 조회를 지원해 그나마 낫지만, null 값을 정수 인디케이터로 표현하는 등 세부 규약이 컬럼형 데이터와 맞지 않아 변환 비용이 든다. ADBC는 이 지점을 처음부터 컬럼형으로 설계해 우회한다. 분석 쿼리처럼 대량의 행을 통째로 끌어와야 하는 워크로드에서, 행 단위로 포장했다 다시 컬럼으로 풀어헤치는 왕복 비용 자체를 없애는 것이 핵심이다. 다만 ADBC가 ODBC·JDBC를 완전히 대체하는 것은 아니다. Apache Arrow 팀도 밝혔듯 ADBC는 대량 컬럼형 조회·적재에 특화된 보완재에 가깝고, 트랜잭션 처리 같은 일반 워크로드에서는 여전히 기존 표준이 쓰인다.

1.3 Flight SQL과의 관계

ADBC와 자주 같이 언급되는 것이 Flight SQL이다. Flight SQL은 DB 개발자를 겨냥한 클라이언트-서버 프로토콜이고, ADBC는 그 프로토콜을 포함해 다양한 DB 클라이언트 기술을 하나의 API로 감싸는 애플리케이션 쪽 표준이다. 즉 DB가 Flight SQL을 구현하면 ADBC·JDBC·ODBC 클라이언트를 모두 지원할 수 있는 구조다. Snowflake와 DuckDB가 ADBC 도입 이후 몇 개월 내로 이를 채택했고, 일부 사례에서는 결과 조회 시간이 90% 이상 줄었다는 보고도 나왔다(벤더·커뮤니티 보고 기준이라 각 환경에서 재검증이 필요하다).

2. databow 소개 - ADBC 위에서 동작하는 Rust CLI

2.1 무엇을 하는 도구인가

databow는 Columnar가 만들고 Apache-2.0 라이선스로 공개한 커맨드라인 도구다. 명령 히스토리와 SQL 문법 강조를 지원하는 대화형 셸, 열 너비를 자동으로 맞추는 정렬된 테이블 출력, 그리고 결과를 JSON·CSV·Arrow IPC 파일로 그대로 내보내는 기능을 제공한다. 대화형 모드와 비대화형(단발 쿼리) 모드를 둘 다 지원해 스크립트에 끼워 넣기도, 손으로 탐색하기도 편하다.

2.2 설치와 기본 사용법

설치는 uv tool install databow 또는 cargo install databow 두 가지 경로가 안내된다. DuckDB를 예로 들면, 먼저 dbc install duckdb로 해당 ADBC 드라이버를 받고, databow --driver duckdb로 대화형 셸을 열거나 databow --driver duckdb --query 'SELECT 42 AS the_answer'처럼 단발 쿼리를 바로 실행한다. --file로 SQL 파일을 읽고 --output으로 결과를 파일로 떨어뜨리는 흐름은 psql이나 usql을 써 본 사람에게는 낯설지 않은 UX다. 다른 점은 그 아래에서 오가는 데이터가 행이 아니라 Arrow 컬럼 배치라는 것뿐이다.

3. 실무 가치 - 데이터 엔지니어·분석가에게 왜 중요한가

3.1 여러 DB를 오가는 게 일상인 사람들

본인이 보기에 databow류 도구의 진짜 수요는 한 프로젝트 안에서 서로 다른 DB 엔진을 오가며 탐색·검증·이관을 반복하는 사람들이다. 운영계 Postgres에서 샘플을 뽑아 로컬 DuckDB에 붙여 보고, 결과를 Snowflake 적재 전 형식과 맞춰보는 식의 작업은 흔하다. 이런 흐름에서 매번 클라이언트를 바꿔가며 접속 문자열과 출력 포맷을 다시 익히는 비용은 생각보다 크다. 하나의 CLI, 하나의 셸 문법으로 여러 엔진을 오갈 수 있다는 것만으로도 컨텍스트 전환 비용이 줄어든다.

3.2 컬럼형 zero-copy가 실제로 주는 이득

성능 이득은 추상적인 얘기가 아니라 워크로드에 달려 있다. 수백만 행을 뽑아 pandas나 Polars 같은 컬럼형 분석 도구로 넘기는 작업이라면, 처음부터 Arrow로 받아 그대로 넘기는 경로가 행으로 받았다가 다시 컬럼으로 변환하는 경로보다 확실히 빠르다. 반대로 몇 줄짜리 트랜잭션 조회나 단건 갱신처럼 애초에 컬럼형 이득이 없는 워크로드에서는 ADBC의 장점이 체감되지 않는다. 즉 databow의 가치는 대량 분석 데이터를 다른 컬럼형 도구로 넘기는 파이프라인에서 극대화된다.

4. 아직 제한적인 드라이버 생태계 - 냉정하게 보기

4.1 드라이버별 성숙도는 균일하지 않다

여기서부터는 경계할 대목이다. ADBC 드라이버 문서를 보면 성숙도가 드라이버마다 크게 다르다. Snowflake 드라이버는 Stable로 표기돼 있어 가장 신뢰할 만하다. PostgreSQL 드라이버는 C/C++·C#·Go·R·Ruby·Rust 등 여러 언어 바인딩을 통해 실사용 가능한 수준이다. 반면 BigQuery는 C# 드라이버가 Beta, Go 드라이버가 Experimental 단계로 아직 유동적이고, SQLite 드라이버는 개발 과정에서 쓰인 참조용 구현이라 최적화가 덜 됐다고 공식 문서에 명시돼 있다.

4.2 실무 리스크로 옮겨보면

즉 ADBC 드라이버가 있다는 사실만으로 프로덕션에 바로 투입할 수 있다는 뜻은 아니다. Snowflake처럼 성숙한 드라이버는 안심하고 쓸 수 있지만, 아직 Beta·Experimental 단계인 드라이버는 엣지케이스에서 예상 밖의 동작을 만날 수 있다. databow의 공식 예시가 DuckDB에 집중돼 있는 것도, 현재 생태계의 무게중심이 어디에 있는지를 보여주는 신호로 읽힌다. 새 표준의 숙명이지만, 이 시점에는 쓸 수 있는가보다 이 특정 드라이버가 내 DB에서 얼마나 성숙했는가를 하나씩 확인하는 태도가 필요하다.

5. psql·usql·DuckDB CLI와 비교

5.1 psql - 검증됐지만 단일 DB, row 지향

psql은 PostgreSQL 전용 클라이언트로 안정성과 기능 완성도에서 여전히 기준점이다. 다만 애초에 다중 DB를 겨냥한 도구가 아니고, 프로토콜도 row 지향이다. Postgres 하나만 쓴다면 지금도 최선의 선택에 가깝다.

5.2 usql - 범용이지만 컬럼형은 아니다

usql은 psql에서 영감을 받아 만들어진 범용 CLI로, PostgreSQL·MySQL·Oracle·SQL Server·SQLite는 물론 ClickHouse·CockroachDB·Presto·Trino·BigQuery까지 Go 언어의 database/sql 인터페이스를 통해 아우른다. 여러 DB를 하나의 셸에서 오간다는 목표는 databow와 같지만, 내부적으로는 각 DB의 표준 드라이버(대개 row 지향)를 그대로 감싸는 구조다. 즉 여러 DB를 하나의 UX로 묶는 넓이는 usql이 현재 더 넓지만, 컬럼형 zero-copy 전송이라는 축에서는 databow·ADBC와 설계 철학 자체가 다르다.

5.3 DuckDB CLI - 자체 엔진으로 끌어와 계산한다

DuckDB CLI는 postgres_scanner·mysql_scanner 같은 확장으로 외부 DB에 붙어 크로스 DB 쿼리를 실행할 수 있다. 다만 이 방식은 여러 DB의 데이터를 DuckDB 자체 분석 엔진 안으로 끌어와 계산한다는 접근이다. DuckDB가 강력한 인프로세스 분석 엔진이라는 점에서 로컬 분석에는 매우 강력하지만, 그 DB의 네이티브 실행 결과를 그대로 컬럼형으로 받는다는 ADBC의 접근과는 방향이 다르다. 목적이 DuckDB로 계산이냐 각 DB의 결과를 그대로 빠르게 옮긴다냐에 따라 선택이 갈린다.

5.4 databow/ADBC - 네이티브 결과를 zero-copy로 옮긴다

정리하면, databow가 다른 세 도구와 다른 지점은 각 DB 엔진이 이미 계산한 결과를 행으로 포장하지 않고 Arrow 컬럼 배치 그대로 받는다는 것이다. usql이 UX의 통일성에, DuckDB CLI가 계산 엔진의 통합에 방점을 찍는다면, databow/ADBC는 전송 계층의 효율에 방점을 찍는다. 세 접근은 경쟁 관계라기보다 서로 다른 문제를 푼다고 보는 편이 정확하다.

6. 언제 무엇을 쓸 것인가

본인의 실무 판단 기준은 이렇다. 단일 DB만 쓴다면 그 DB의 네이티브 클라이언트(psql 등)가 여전히 안전한 기본값이다. 여러 DB를 오가되 UX 통일과 넓은 드라이버 커버리지가 우선이라면 usql이 현재 더 실전적이다. 로컬에서 여러 소스를 붙여 빠르게 분석하고 싶다면 DuckDB CLI가 적합하다. 그리고 대량의 컬럼형 데이터를 여러 DB에서 뽑아 pandas·Polars·Arrow 기반 파이프라인으로 곧바로 흘려보내는 작업이 핵심이라면, 그 지점에서만 databow와 ADBC를 진지하게 검토할 가치가 있다. 다만 대상 DB의 ADBC 드라이버가 Stable 단계인지부터 확인하는 것이 먼저다.

결론

databow 자체는 아직 작은 도구다. 그러나 그 아래 깔린 ADBC는 DB 커넥티비티를 row에서 컬럼형으로 재설계한다는, 방향성이 뚜렷한 표준이다. Snowflake·DuckDB가 빠르게 올라탄 것도 이 방향이 분석 워크로드의 실제 병목을 짚었기 때문일 것이다. 다만 2026년 7월 기준으로는 드라이버 성숙도가 DB마다 크게 갈리는 초기 단계다. 지금 당장 psql·usql을 걷어내고 databow로 옮겨 갈 이유는 없지만, 대량 컬럼형 데이터를 자주 옮기는 파이프라인을 운영한다면 지켜볼 가치가 있는 흐름이다.
