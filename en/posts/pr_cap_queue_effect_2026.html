A Cap on Open Items Will Not Shorten Your Review Queue - Caps and Queue Dynamics

Caps of 3, 5, 10 and 20 run against a 900-day queue model, measured for blocked share and waiting-time tail

2026-07-31 Dev & Infra

Opening: the cap went in, the backlog did not move

Suppose a repository has more than 200 items waiting for review. The conclusion that comes out of the meeting is familiar. Let us limit each person to three open at a time. The rule goes in, a month passes, and the backlog is exactly as long as it was.

Two reactions usually follow. Either the rule was too loose and the cap should be tighter, or rules like this never work and the whole thing is quietly dropped. This post is about a third possibility: the point where the cap was applied was never the bottleneck.

The starting point was a topic posted on news.hada.io on 30 July 2026, reporting that a limit on pull request counts blocks only 2 to 13% of an actual queue. Rather than restate that report, I decided to run the same question myself. What a particular product decides internally, and under what conditions, is not visible from outside, so this post builds one generic queue model and speaks only about what happens inside it. Every number below carries the qualifier: in this model.

The conclusion first. A low blocked share is not evidence that the rule is loose. A queue grows long because service is slow, not because arrivals are many, and a cap delays arrivals without making service any faster. That is why tightening the cap does not shorten the wait. This does not make caps useless. Under certain conditions they clearly bite, and those conditions can be stated numerically too.

This post does not re-explain how to open a pull request or how to leave a review comment. That material is in Pull Requests and Code Review. What follows is about queue dynamics.

1. The model - what was built

The model is deliberately small, so that every number can be traced back to what produced it.

  • 40 authors. Each creates items and puts them into one shared queue
  • New items arrive at 9.6 per day on average, drawn from a Poisson distribution
  • Which author created an item is drawn from a Zipf distribution with s=1.0, to produce the realistic concentration where a few people open most of the work
  • The review side can hold 30 items at once, and each item occupies a slot for 3.0 days on average, drawn from a geometric distribution
  • Service rate is therefore 10.0 items per day (30 divided by 3.0) and utilisation is 0.96 (9.6 divided by 10.0)
  • The cap is defined as the maximum number of items one author may have open at the same time. It acts at that point and nowhere else
  • 900 days are simulated and the first 300 are discarded as warm-up. Only the remaining 600 are counted
// sim.js - node v22.16.0 / win32. fixed seed, so every number below reproduces.
const SEED = 20260731;

function mulberry32(a) {                        // deterministic PRNG
  return function () {
    a |= 0; a = (a + 0x6D2B79F5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
function poisson(rng, lambda) {                 // Knuth
  const L = Math.exp(-lambda); let k = 0, p = 1;
  do { k++; p *= rng(); } while (p > L);
  return k - 1;
}
function geom(rng, p) {                         // support 1,2,3,... mean 1/p
  const u = rng();
  return Math.max(1, Math.ceil(Math.log(1 - u) / Math.log(1 - p)));
}

// A       how many authors
// lambda  new items per day          R  concurrent review slots
// S       mean days one review occupies a slot   =>  service rate mu = R / S
// cap     how many items one author may have open at the same time
function simulate({ A = 40, s = 1.0, lambda = 9.6, R = 30, S = 3.0,
                    days = 900, warmup = 300, cap = Infinity,
                    retry = false, seed = SEED }) {
  const rng = mulberry32(seed), cum = zipfCum(A, s), p = 1 / S;
  const open = new Int32Array(A);
  let queue = [], active = [], deferred = [];

  for (let d = 0; d < days; d++) {

    // 1. reviews whose duration has elapsed give their slot back
    const still = [];
    for (const it of active) {
      if (it.endsAt <= d) { open[it.author]--; record(it, d); }
      else still.push(it);
    }
    active = still;

    // 2. today's items, plus anything blocked earlier if retry is on.
    //    author and review duration are drawn HERE and never re-drawn, so
    //    changing cap does not shift the random stream.
    const todays = retry ? deferred.splice(0) : [];
    for (let i = 0, n = poisson(rng, lambda); i < n; i++)
      todays.push({ author: pick(rng, cum), dur: geom(rng, p), born: d, tries: 0 });

    // 3. the cap is applied here and nowhere else
    for (const ev of todays) {
      if (open[ev.author] >= cap) {             // blocked
        ev.tries++;
        if (retry) deferred.push(ev);           // comes back tomorrow
        continue;                               // otherwise dropped
      }
      open[ev.author]++;
      ev.opened = d;
      queue.push(ev);
    }

    // 4. free review slots pull from the head of the shared FIFO
    while (active.length < R && queue.length) {
      const it = queue.shift();
      it.started = d;
      it.endsAt = d + it.dur;
      active.push(it);
    }
  }
}

[3, 5, 10, 20, Infinity].forEach(cap => report(simulate({ cap })));

One design decision mattered more than the rest. Changing the cap must not shift the arrival stream or the review durations. If an item draws both its author and its review duration at the moment it is created, then whether the cap later blocks or admits it does not change how many random numbers get consumed. Without this, each cap value is compared against a different world, and there is no way to tell whether a difference came from the cap or from luck. I made exactly this mistake in the first version, and noticed it only when the total arrival count wobbled between 5,645 and 5,793 as the cap changed.

What this post does not claim. This model is not an implementation of any product. What a specific service blocks, under what conditions, and to whom the rule applies are not covered here. What is covered is how a rule shaped like a per-author concurrent-open cap behaves in a generic queue, and nothing more.

First, the new-items column reads 5,764 on all five rows. That is the design point confirming itself: the same arrival stream with only the cap swapped, so every difference below belongs to the cap.

A cap of 20 stopped 8 items out of 5,764. The difference between having the rule and not having it is three finished items. A cap of 10 blocks 2.52% and still finishes 5,584, which is 98% of baseline. Both of these are decoration rather than policy.

Down at a cap of 3, 22.62% is blocked. Here the finished column has to be read alongside it. It fell from 5,699 to 4,436. Blocking that much meant that much did not get through; the wait did not get shorter. That is because this table discards blocked items. Section 5 shows what happens when they come back instead.

The five-seed table underneath matters as much. A cap of 3 lands between 20% and 23%, a cap of 5 between 10% and 12%, a cap of 10 between 1% and 3%, and a cap of 20 between 0% and 0.4%. The ordering and the magnitudes hold. This is not an artefact of one random stream.

One number explains most of it. 57.03% of author-days have nothing open at all. Including one open item takes it to 81.34%, and two takes it to 89.84%. The first point a cap of 3 can touch is the remaining 10.16%.

A median of 0, a p90 of 3, a p99 of 10 and a maximum of 24 is the shape here. The tail is long but the body sits almost entirely at zero. A cap is a rule that reaches only that tail.

  • The busiest author alone produces 24.4% of all items, keeps 9.60 open on average and peaked at 25. Even a cap of 10 catches this person regularly
  • The second produces 11.7% and averages 4.69 open. A cap of 5 starts to catch them
  • Ranks 9 through 40, thirty-two people, average 0.42 open. For them a cap of 3 is a rule that does not exist
  • Across the measured window, 13 of 40 authors ever touched a cap of 3, 8 touched a cap of 5, 2 touched a cap of 10 and 1 touched a cap of 20

This is what a low blocked share really is. The rule is not loose; the set of people it can touch is small. Reported as a share of the total it reads as a weak effect, when the accurate phrasing is a narrow population. And the fact that this narrow population also produces a large share of the throughput becomes a problem further down.

4. Pushing the concentration to the extreme

The obvious objection is that a real team is far more concentrated than this. I swept the Zipf exponent from 0.4 to 2.4 to check.

  • At exponent 0.4 the busiest author produces 6.6% and the blocked share is 1.08%
  • At the baseline of 1.0 the busiest produces 24.4% and the blocked share is 11.57%
  • At exponent 2.4 the busiest produces 72.7% and the blocked share is 57.76%

Concentration does raise the blocked share. But look at where it rises. To push past 30%, one person has to produce more than 40% of all the work. In a group of 40, one person producing 40% of everything is not a queue design problem, it is a different problem. Across the realistic band, where the busiest author produces 6% to 25%, the blocked share stays between 1% and 12%.

The p90 column moving the other way is the interesting part. As concentration rises, p90 falls from 3 to 1, because the more work funnels to one person, the more of everyone else sits at zero. The typical author drifts further from the cap while one person hits it every day. The aggregate share averages over that population, flattening one person hitting a wall daily and everyone being mildly inconvenienced into the same number. That is exactly why a cap discussion cannot run on the aggregate share alone.

The same trap on the metrics side is covered in averaging the p99 of ten servers. Folding populations with different distributions into a single number destroys information in the same structural way.

5. Blocking and reducing are not the same thing

Every table so far discarded blocked items. Reality does not discard them. They come back later. So blocked items now retry the following day.

  • Cap 10: 628 items were blocked, and 5,695 finished, four short of baseline. Yet mean open-to-finish improved from 4.05 days to 3.80 days. End-to-end latency for the same run went from 4.05 to 4.06 days, that is, nowhere
  • Cap 3: finished work fell to 4,450 and mean end-to-end latency reached 31.66 days

The cap 10 row is the heart of this section. Open-to-finish improved while end-to-end did not move. All the cap did was shorten the interval during which an item counts as open. It pressed the start button of the clock later; it did not move the finish line closer. And most dashboards measure open-to-finish. This rule improves the metric while changing nothing.

The last-day inventory makes it plain. Under a cap of 3, 1,289 items sit held outside the queue. Under a cap of 5 it is 618. That work did not vanish. It moved to a place the queue dashboard does not look at.

There is a harsher implication here. In this model the busiest author creates 2.34 items a day and a review takes 3 days on average. With a cap of 3, the most that person can push through is 1 item a day. When the cap sits below the rate someone needs, their personal backlog grows forever. That is why finished work fell 22% at a cap of 3. That is not reduction, that is starvation.

With utilisation above 1, a cap is not a treatment. It is a device for moving the symptom off screen.

It also matters that the mean barely shows any of this. Mean open-to-finish under a cap of 3 is 3.02 days against a baseline of 4.05, a difference of one day. End-to-end p99 is 13 days against 476. The average completely hides the worst cases this rule creates.

Adding a single slot, that is, raising capacity by 3.4%, cut the mean wait before pickup from 3.16 days to 1.04. A 67% reduction. The next slot buys 41%, and the one after that 35%.

  • Going from utilisation 0.993 to 0.960 drops the mean queue from 30.7 to 10.2
  • Reaching utilisation 0.900 brings the mean queue to 3.9. That took two extra slots
  • Below utilisation 0.800 the gains shrink sharply, because there is barely any waiting left to remove

This non-linearity has a name. Waiting time grows roughly in proportion to one over one minus utilisation. At 0.993 that factor is 143; at 0.960 it is 25. Capacity went up 3% and the factor fell to a fifth. That is why small changes matter so much near saturation, and why the same 3% at a utilisation of 0.8 does almost nothing.

The final equal-effort comparison summarises the whole post. A cap of 3 with 30 slots gives open-to-finish 3.02 days, end-to-end 31.66 days and 4,450 finished. No cap with 32 slots gives open-to-finish 3.40 days, end-to-end also 3.40 days, and 5,723 finished. The cap wins narrowly on one metric and loses on every other.

A rule falls out of this. A cap bites only when it sits below the p90 of the per-author open count. In the baseline that p90 was 3, which is why a cap of 3 blocked 22.62%, a cap of 5 blocked 11.57% and a cap of 10 blocked 2.52%. In the six-author team the p90 was 15, so even a cap of 5 blocked 34.21%. Measure that distribution before picking a number.

There is also a use for caps that this model cannot reproduce. The table below separates the cases.

GoalWhat the cap really doesEvidence in this modelLook at this instead
Shorten the backlogShrinks only the visible queue and relocates the totalAt utilisation 1.15 the queue went 1,323 to 50 while throughput went 5,610 to 5,639Service rate and utilisation
Shorten review waiting timeMoves the measurement start and improves the metric aloneAt cap 10, open-to-finish 4.05 to 3.80 days while end-to-end went 4.05 to 4.06End-to-end p90 and p99

The fourth row matters. The effect of a cap on human behaviour is outside what this model can measure. Authors here do not split work into smaller pieces when blocked; they simply retry the same thing tomorrow. If a cap in a real organisation works as the discipline of finishing one thing before starting another, that is a genuine effect this simulation cannot see. But if that is the reason for the cap, the stated goal should not be shortening the queue.

10. What to measure

Measuring the following makes the argument about the cap value disappear on its own.

MetricDefinitionValue in this modelWhy measure it
Service rateReviews completed per unit time10.0 per dayThis is the side that sets queue length
Arrival rateNew items opened per unit time9.6 per dayAbove service rate the queue grows without bound
UtilisationArrival rate divided by service rate0.96Past 0.9 waiting rises non-linearly
Waiting tailp90 and p99 of open-to-finish8 days and 13 daysThe mean hides the worst cases
End-to-end latencyFrom ready to finished4.05 days baseline, 31.66 days at cap 3Includes the time a cap pushed out
Open-item distributionp50, p90, p99 per author0, 3, 10Tells you how large the population a cap can touch is
Queue length trendWeekly slopeRising at utilisation 1.04A single snapshot cannot show divergence

Translated into a checklist:

  • Measured service rate and utilisation before debating a cap
  • Know the p90 of per-author open items and checked the cap sits below it
  • Read queue length as a weekly slope, not a single snapshot
  • Read waiting time as p90 and p99, not the mean
  • Measure open-to-finish and end-to-end separately. A cap only improves the first
  • Have a view that shows where blocked work accumulates
  • Consider adding service capacity first when utilisation passes 0.9
  • Wrote down whether the cap exists to shorten the queue or to force focus

11. What this model does not reproduce

Without stating the limits, the numbers above read stronger than they are. Here is what was left out.

  • Reviewer assignment and areas of expertise. There is one shared first-in-first-out queue here. Bottlenecks caused by only one person being able to review a given area are not reproduced
  • Priority and expedite lanes. Nothing jumps the queue. In reality urgent items go first and lengthen everyone else's tail
  • Rework after review comments. There is no rework loop. Adding one lowers effective service rate and raises utilisation
  • Variation in item size. Every item draws its duration from the same distribution, so the effect of mixing large and small work is absent
  • The behavioural effect of a cap. Authors here do not split work into smaller pieces when blocked. The most plausible benefit of a cap is missing from this model
  • Items that decay while open. No conflicts, no moving baselines, no lost context. In reality the longer something stays open the harder it gets to finish
  • Weekly cycles and holidays. Arrivals and service follow the same distribution on every day

The third and fifth of these could push the conclusion the other way. A rework loop lowers service rate and strengthens the case for a cap, and the behavioural effect means this post underestimates what a cap can do. So the conclusion here is not that caps are bad. It is that a cap is not an instrument for shortening a queue, and used for that purpose it improves the metric and nothing else.

# Caps and Queues — What to Measure and What to Fix

> Source: braindetox.kr — A cap on open items will not shorten your review queue
> Verified on: node v22.16.0 / win32, fixed seed 20260731, 900 simulated days (300 warm-up, 600 measured)
> Every number here holds inside this model only. It is not a claim about any product's internals.

## 1. The model in one block

```
40 authors · new items ~ Poisson(9.6 per day) · author drawn from Zipf(s=1.0)
review side holds 30 items at once · each for Geometric(mean 3.0 days)
service rate mu = 30 / 3.0 = 10.0 per day · utilisation rho = 9.6 / 10.0 = 0.96
cap = how many items one author may have open at the same time
```

## 2. Reproduction code (core loop)

```js
const SEED = 20260731;

function geom(rng, p) {                  // support 1,2,3... mean 1/p
  const u = rng();
  return Math.max(1, Math.ceil(Math.log(1 - u) / Math.log(1 - p)));
}

for (let d = 0; d < days; d++) {
  // 1. reviews whose duration has elapsed give their slot back
  const still = [];
  for (const it of active) {
    if (it.endsAt <= d) { open[it.author]--; record(it, d); }
    else still.push(it);
  }
  active = still;

  // 2. today's items. author and review duration are drawn HERE, once,
  //    so changing cap does not shift the random stream.
  const todays = retry ? deferred.splice(0) : [];
  for (let i = 0, n = poisson(rng, lambda); i < n; i++)
    todays.push({ author: pick(rng, cum), dur: geom(rng, p), born: d, tries: 0 });

  // 3. the cap is applied here and nowhere else
  for (const ev of todays) {
    if (open[ev.author] >= cap) {         // blocked
      ev.tries++;
      if (retry) deferred.push(ev);       // comes back tomorrow
      continue;                           // otherwise dropped
    }
    open[ev.author]++;
    ev.opened = d;
    queue.push(ev);
  }

  // 4. free review slots pull from the head of the shared FIFO
  while (active.length < R && queue.length) {
    const it = queue.shift();
    it.started = d; it.endsAt = d + it.dur;
    active.push(it);
  }
}
```

## 7. Measure these instead of arguing about the cap value

| Metric | Definition | Why measure it |
|---|---|---|
| Service rate mu | Reviews completed per unit time | This is what sets queue length |
| Arrival rate lambda | New items opened per unit time | Above mu the queue grows without bound |
| Utilisation rho | lambda / mu | Past 0.9 waiting rises non-linearly |
| Wait tail | p90 / p99 of open-to-finish | The mean hides the pathology |
| End-to-end latency | Ready-to-finish, not open-to-finish | Includes the time a cap pushed out |
| Per-author open distribution | p50 / p90 / p99 | Tells you the population a cap can touch |
| Queue length trend | Weekly slope | Rising means rho crossed 1 |

## 8. Checklist

- [ ] Measured **service rate (mu) and utilisation (rho)** before debating a cap
- [ ] Know the **p90** of per-author open items and checked the cap sits below it
- [ ] Read queue length as a **weekly slope**, not a single snapshot
- [ ] Read waiting time as **p90 / p99**, not the mean
- [ ] Measure **open-to-finish and end-to-end separately** (a cap only improves the first)
- [ ] Can see **where blocked work piles up**
- [ ] Consider adding review capacity first when utilisation passes 0.9
- [ ] Wrote down whether the cap exists to **shorten the queue** or to **force focus**

## 9. What not to do

- Adding a cap because the queue is long — queue length is set by service, not arrivals
- Tightening the cap because the blocked rate is low — it is low because that point is not the bottleneck
- **Reporting improvement from open-to-finish alone** — the clock start may simply have moved
- Reaching for a cap while utilisation is above 1 — only the visible queue shrinks
- Using a cap to punish the few prolific authors — they are producing much of the throughput

## 10. What this model does not reproduce

- Reviewer assignment and areas of expertise (one shared FIFO here)
- Priority, expedite lanes, queue jumping
- Rework loops after review comments
- Variation in item size (all items draw from the same duration distribution)
- Behavioural effects of a cap (smaller items, less context switching)
- Items that decay while open (conflicts, moving baselines)
- Weekly cycles and holidays
