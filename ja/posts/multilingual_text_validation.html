序論: 翻訳は終わったはずなのに、どこかに残っている

製品ドキュメントを五言語で出すとしよう。ファイルは四千個、半分は人が、半分は機械が訳した。レビュー担当は二十個ほど開いて問題なしと判断する。そして二か月後、英語ページのど真ん中に韓国語の一文が見つかる。その頃にはどのバッチで入ったものか誰にも分からない。

この欠陥が厄介なのは難しいからではない。機械なら数秒で見つけるのに、人はまず見つけられないという非対称性が理由だ。人はドキュメント四千個を読まない。二十個を読み、目についた一つを直し、残りの三千九百八十個はそのまま出る。

だからこれはレビューの問題ではなくチェッカーの問題だ。そしてチェッカーを作るときの本当に難しい部分は、混入を見つける側ではない。見つけたものの中から残っていて正しいものを選り分ける側だ。製品名は原語のままが正しく、コード例の中の文字列は訳してはならず、用語併記はわざと二言語を並べる。これを区別できないチェッカーは警告を数百件吐き、人は三日で無視し始める。

結論から書く。文字コードで捕まえられるものは思ったより多く、Unicodeブロック範囲を手で書くよくある方式はその半分を取りこぼしながら、同時にまともな文をも誤って拾う。スクリプト属性に替えれば二つとも消える。その後に残るのが例外設計で、ここから先は正解ではなく代償を選ぶ問題になる。

1. 人の目では捕まえられない理由

言語混入は目につく場所には生じない。見出しに丸ごと別の言語があれば誰でも気づく。問題はそこではない。

  • 段落の途中に一文。前後が自然につながっているので、スクロールしながら読むと素通りする
  • 表の三行目。十行のうち一行だけ原文が残っていても、表全体を見渡す視線には引っかからない
  • 画面に出ない場所。画像の代替テキスト、フォームの入力ヒント、エラーメッセージ、アクセシビリティラベルは通常の閲覧では描画すらされない
  • 単語の一部だけが変わった場所。用語辞書で置換する方式の翻訳は、単語の内側だけを書き換えることがある。一語の中で文字体系が変わる形なので、流し読みでは通過する
  • 記号に見える文字。長音符や中黒のように他言語であまり使わない約物が残った場合、文字ではなく書式として読まれて誰も疑わない

さらにもう一つある。レビュー担当は自分が読める言語しかレビューしない。タイ語ページにロシア語が混ざれば、韓国語担当も英語担当も捕まえられない。機械翻訳パイプラインが見当違いの言語を吐くことは珍しくなく、その言語を読める人が組織にいなければそのまま配信される。文字体系チェックはこの区間で人より圧倒的に強い。読めなくても捕まえられるからだ。

2. 文字に言語は書かれていない

まず用語を整理する必要がある。このチェックが扱うのは言語ではなく文字体系だ。両者は違う。英語とフランス語は言語が違うが文字体系はどちらもラテンである。文字コードだけではこの二つを分けられない。

逆に韓国語・日本語・ロシア語のように文字体系が異なる組み合わせは、コードだけで分かれる。だからこのチェックが実際にやることはここまで狭まる。対象言語に出現し得ない文字体系がドキュメントにあるか。この狭い問いには機械がほぼ完璧に答える。

2.1 Unicodeがすでに答えを持っている

すべてのコードポイントにはScript属性が付いている。UAX #24が定義する値で、Hangul・Hiragana・Katakana・Han・Cyrillic・Latinといった名前を持つ。JavaScriptの正規表現はこの値を\p{Script=Hangul}の形で直接書ける。MDNのドキュメントが明かすとおりuまたはvフラグが必須で、フラグがなければ\pは単に文字pとして解釈される。静かに失敗するので注意する値打ちがある。

二つの特殊値を知っておく必要がある。Commonは複数の文字体系が共有する文字(数字・約物など)に、Inheritedは前の文字から性質を受け継ぐ結合記号に付く。UAX #24は、CommonやInheritedが付いた文字の多くが実際にはすべての文字体系と使われるわけではなく限られた一部とだけ使われると指摘し、その関係を別に記録したScript_Extensions属性を定義している。

ここから実務的な判断が一つ出る。混入チェックにはScriptを使い、Script_Extensionsは使うな。Script_Extensionsは「この文字をこの文字体系で使うこともある」という広い関係なので、汚染チェックに使うと複数言語が共有する約物まで全部引っかかる。次節3の実測表がこの差をそのまま示す。

2.2 漢字は言語を教えてくれない

この節がこの記事で最も重要だ。漢字があるという事実は、その文書が中国語だという根拠にならない。

Unicodeは中国語・日本語・韓国語で使われる漢字を一つの統合集合としてエンコードした。Unicode標準 第18章はこの統合集合の存在を明示しつつ、標準が漢字の言語をエンコードしようとはしないとし、言語タグ付けと単語認識を上位層のソフトウェアに委ねると記している。つまりコードポイントには、その字が中国語か日本語かが入っていない。最初から入れないと決めたのだ。

具体的に確かめるとこうなる。日本で使う新字体の国と中国簡体字の国は同じコードポイントU+56FDだ。会もU+4F1Aで両方同じである。二言語のドキュメントを並べて漢字だけ抜き出しコードポイントを比べても、区別のつく点がない。

// 新字体と簡体字が同じコードポイントかを確認
for (const ch of ['国', '会', '發', '发']) {
  console.log(ch, 'U+' + ch.codePointAt(0).toString(16).toUpperCase(),
              /\p{Script=Han}/u.test(ch));
}
// 国 U+56FD true   ← 日本の新字体 = 中国の簡体字
// 会 U+4F1A true   ← 両方同じ
// 發 U+767C true   ← 繁体字のみ
// 发 U+53D1 true   ← 簡体字のみ

そこでルールをこう分ける。

  • 英語ドキュメントの漢字 — 混入とみなしてよい。ラテン文字圏の文書に漢字が出る理由はほぼない
  • 日本語ドキュメントの漢字 — 当然正常だ。ルール自体を作ってはいけない
  • 中国語ドキュメントの漢字 — 正常。代わりにどの系統の漢字かを別に見る(6節)
  • 韓国語ドキュメントの漢字 — 正常だ。韓国語は漢字を併記用途で使う。ここに漢字禁止ルールを掛けると法律・学術文書で誤検知が溢れる

同じ理由で日本語ドキュメントの中で漢字だけからなる区間は判別不能区間である。会社名や見出しのようにカナが一つもない短い文字列は、中国語と区別する手段がない。これはチェッカーの欠陥ではなくエンコーディング設計の性質なので、ルールで解こうとせず「この区間は検査対象外」として扱うほうが正しい。

3. ブロック範囲とスクリプト属性 - 実際の判定差

現場で最もよく見るコードは、Unicodeブロック範囲を手で書く形だ。ハングルはAC00–D7A3と1100–11FF、カナは3040–30FF、キリルは0400–04FF、漢字は4E00–9FFF。この範囲自体は正しい。問題はこの範囲だけでは足りず、同時に行き過ぎている点にある。

以下はNode 22で同じ文字に二方式を適用した結果だ。自分で確かめるにはこのコードをファイルに保存して実行すればよい。

const BLOCK  = { hangul: /[가-힣ᄀ-ᇿ]/u, kana: /[぀-ヿ]/u };
const SCRIPT = { hangul: /\p{Script=Hangul}/u,
                 kana:   /[\p{Script=Hiragana}\p{Script=Katakana}]/u };

for (const ch of ['한', 'ㄱ', '㉮', 'ｻ', '・', 'ー', 'の']) {
  console.log(ch,
    'U+' + ch.codePointAt(0).toString(16).toUpperCase().padStart(4, '0'),
    'block:',  BLOCK.hangul.test(ch)  || BLOCK.kana.test(ch),
    'script:', SCRIPT.hangul.test(ch) || SCRIPT.kana.test(ch));
}

表から読むべきことは二つだ。ブロック範囲は散らばった文字を取りこぼす。半角カナが代表例である。自動変換器を通ったドキュメントには半角カナがしばしば残るが、3040–30FFしか見ないチェッカーはこれを通してしまう。そしてブロック範囲は共有文字を誤って拾う。中黒U+30FBはカナブロックの中にあるが、韓国語・中国語のドキュメントでも並列記号として使われる。この一文字のせいで韓国語ドキュメント数百件が「日本語混入」として報告される事態が起きる。

3.1 同じ標本に二方式を通した結果

汚染六件と正常八件、合計十四個の標本に二方式を適用するとこう分かれる。汚染標本には正常な文書のあとにハングル・カナ・キリルの残骸を仕込み、正常標本には中黒や波ダッシュのように誤検知を招く文字を入れた。

方式検出(TP)見逃し(FN)誤検知(FP)正常通過(TN)
ブロック範囲6314
スクリプト属性9005

ブロック範囲が取りこぼした三つは互換字母・丸付き形・半角カナで、誤って拾った一つは中黒を使った韓国語の文だった。十四個の小さな標本なので比率そのものに意味を持たせてはいけないが、失敗の型はそのまま読んでよい。ブロック範囲方式は「境界の外に散らばった文字」と「ブロック内の共有文字」の両方で崩れる。そして標本を増やしても同じ場所で崩れ続ける。

UTS #18も同じ方向を指す。この文書は文字の識別にUnicodeブロックを使うことには非常に重大な但し書きが付くと明示し、ブロックを文字体系識別の代替物として扱わないよう促している。手で書いた範囲が動くコードであっても、標準が別途Script属性を用意したのには理由がある。

ただしブロック範囲が必要な場面もある。正規表現エンジンがスクリプト属性に対応しない環境(旧いランタイム、一部データベースの正規表現、シェルツール)では選択肢がない。その場合は最低限半角カナ FF65–FF9Fとハングル互換字母 3130–318Fを範囲に足し、U+30FBとU+30FCは明示的に除外すること。この三点だけでも上表でブロック方式が外した五箇所のうち四つが消える。残る一つは丸付き形だが、本文に出ることは稀なので許容できる。

4. チェッカーを殺すのは見逃しではなく誤検知だ

ここからが本当に難しい部分だ。ここまでの話は文字コードさえ知っていればできる機械的な作業である。これからは残っていて正しい原語を選り分けねばならず、これには判断が入る。

原語が残るのが正当な場面は思ったより多い。

  • 固有名詞とブランド。社名・製品名・人名・地名は訳さないほうが原則に合う場合が多い
  • 引用。原文をそのまま引くときに訳したら引用でなくなる
  • コード例。変数名・文字列リテラル・コマンドは翻訳対象ではない。訳せばコードが動かない
  • 用語併記。「かな(かな)」のように原語を括弧で併記するのは翻訳品質が良い印であって欠陥ではない
  • この記事のように文字自体を扱う文書。例に複数の文字体系が入ることが本文の内容だ
  • UI文字列の意図的な原語維持。法的告知や商標表記は原語維持が求められることもある

これを区別できないとどうなるかが核心だ。チェッカーは警告を300件吐き、人が開いてみると280件がブランド名とコード例である。三日目には誰も開かない。一週間目にはCIからこの検査を外す。そして本物の汚染20件はそのまま配信される。

だからこの二つの失敗は重さが同じではない。見逃し一件はドキュメント一箇所を壊すが、誤検知の蓄積はチェッカーごと無力化する。チェッカーを新しく作るときはこの非対称性を既定値として敷いて始めるべきだ。捕まる範囲を広げる方向ではなく、報告されるもの一つ一つが本物であるように締める方向である。取りこぼした型は後でルールを一つ足せば済むが、一度消えたチェッカーは二度と点かない。

5. 例外を扱う四つの手段とそれぞれの代償

手段は四つだ。ただのものはなく、どれをどれだけ使うかが設計になる。

手段やること代償いつ使うか
検査範囲の縮小 コードブロック・URL・属性値・メタデータを検査前に除去 除去した区間が恒久的な死角になる まず最初に。安くて効果が大きい
許可リスト 特定の文字列を検査対象から外す 人が埋め続けねばならず、長くなると本物の汚染を隠す 固有名詞・ブランドのようにリストが有限のとき
比率しきい値 総文字数に対する割合が一定以上のときだけ報告 長い文書の一文の未翻訳を取りこぼす 機械翻訳バッチの大量未翻訳の検出
ファイル単位の除外 ファイル一つを丸ごと除外 最も危険。そのファイルは二度と見ない 最後の手段。必ず期限とともに

5.1 検査範囲の縮小 - 最初にやること

コードブロックとURLを除去するだけで誤検知のかなりの部分が消える。順序が重要だ。除去を先に、検査を後にやらねばならない。

function stripUncheckable(text) {
  return text
    .replace(/```[\s\S]*?```/g, ' ')            // フェンスコードブロック
    .replace(/`[^`\n]*`/g, ' ')                 // インラインコード
    .replace(/<code[\s\S]*?<\/code>/gi, ' ')   // HTMLのcode
    .replace(/<pre[\s\S]*?<\/pre>/gi, ' ')
    .replace(/https?:\/\/\S+/g, ' ');           // URL
}

注意すべき点が一つある。除去した区間は永遠に見なくなる。コードブロック内のコメントに未翻訳の説明が残っていても捕まらない。だから除去対象は最小に取り、「コードブロック内のコメントは検査しない」という決定を文書として残すほうがよい。あとでその区間から欠陥が出たときに、チェッカーのバグではなく合意された範囲だったと確認できねばならない。

5.2 許可リスト - 有限のときだけ

許可リストは正確だが人手を食い続ける。二つの原則で管理コストを減らせる。

  1. リストは全体ではなくルール別に。「enドキュメントで許される漢字」と「koドキュメントで許されるカナ」は別のリストだ。一つにまとめるとenで許した項目がzhでも通ってしまう
  2. 項目ごとに理由を書く。理由のない項目は半年後に消すことも残すこともできなくなり、そうやってリストが永久に膨らむ
const ALLOW = {
  en: [
    { term: '任天堂',  why: 'brand name, kept in original' },
    { term: '한글',    why: 'subject of the article itself' },
  ],
  ko: [
    { term: 'かな',    why: 'term gloss in parentheses' },
  ],
};

実際の判定はこう分かれる。ブランド名の入った英文は許可リストなしではHan3字として報告され、リストに入れれば消える。用語併記の入った韓国語の文も同様にHiragana2字からゼロに落ちる。コード例の中の正規表現は範囲縮小だけですでにゼロになる。

5.3 比率しきい値 - 絶対個数より安定する

同じ二文字が文書の長さによってまったく違う意味を持つ。英語ドキュメントにハングル二文字が残っているとしよう。

  • 全815文字の文書で → 0.25パーセント。ブランドか引用の可能性が高い
  • 全6文字の文書で → 33.33パーセント。翻訳自体がされていない

だからしきい値は個数ではなく比率で取る。ただし比率一つでは足りない。長い文書に一文だけ未翻訳が残った場合が比率に埋もれる。二つのルールを併せて掛ける構成が実務では正しい。比率が一定水準を超えれば大量未翻訳とみなして遮断し、比率が低くても連続した汚染区間の長さが一定を超えれば別途報告する。文が丸ごと残れば連続長が長くなるので二つ目のルールに掛かる。

// 連続区間で報告すれば位置まで一緒に出る
const doc = 'The runner reads the tree. 접근성 트리를 읽고 반환한다. Then it exits.';
const re = /\p{Script=Hangul}+/gu;
let m;
while ((m = re.exec(doc)) !== null) {
  console.log(`offset ${m.index}: ${JSON.stringify(m[0])}`);
}
// offset 27: "접근성"
// offset 31: "트리를"
// offset 35: "읽고"
// offset 38: "반환한다"

報告形式について一つ付け加える。文字数で報告せず、位置と原文の断片で報告せよ。上の例で「ハングル12字を検出」は直せない情報であり、「offset 27に접근성」はすぐ直せる情報だ。人が開く費用が低いほどチェッカーは長く生きる。

5.4 ファイル単位の除外 - 期限なしでは使うな

ファイル全体を検査から外すのは最後の手段だ。一度入れればそのファイルは二度と検査されず、リストに入れた理由は半年で忘れられる。あえて使うなら期限を必須項目に置き、期限切れの項目があればチェッカーがその事実自体を報告するようにせねばならない。例外リストを管理対象にしておかないと、例外リストがそのまま死角リストになる。

5.5 単語の中で文字体系が変わる場合

別途扱うべき型が一つある。用語辞書で置換する翻訳が単語の内側だけを書き換える形だ。これは文書全体を走査するルールでは捕まらない。正常な韓国語ドキュメントにも漢字は出るし、正常な文書にハングルが出るのは当然だからだ。引っかかる点は二つがくっついているという事実である。

ここに一つ罠がある。単語単位で切って一単語の中に二つの文字体系があるかを見る接近が自然に思えるが、実際にはうまくいかない。単語分割器は文字体系が変わる位置を単語境界として扱うからだ。

const seg = new Intl.Segmenter('ko', { granularity: 'word' });
console.log([...seg.segment('会원 가입')].map(p => p.segment));
// [ '会', '원', ' ', '가입' ]   ← 会 と 원 が別トークンに分かれる

そこで単語ではなく隣接を見る。漢字のすぐ後にハングルが来る、あるいはその逆の位置を直接探す。

const adj = /(\p{Script=Han}\p{Script=Hangul}|\p{Script=Hangul}\p{Script=Han})/gu;

[...'会원 가입 절차'.matchAll(adj)];    // [ '会원' ]   ← 捕まる
[...'新규 등록'.matchAll(adj)];         // [ '新규' ]   ← 捕まる
[...'민법(民法) 제839조'.matchAll(adj)]; // []          ← 併記は捕まらない
[...'한자 漢字 병기'.matchAll(adj)];     // []          ← 空白入り併記も捕まらない

このルールが良いのは正当な併記を自動的に避ける点にある。括弧併記も空白併記も間に別の文字が挟まるので隣接条件が成立しない。許可リストを一つも使わずに誤検知がゼロになる稀なルールなので、作る値打ちがある。

5.6 目で区別できない文字

キリル文字とラテン文字には形の同じ字がいくつもある。大文字のА(U+0410、キリル)とA(U+0041、ラテン)は画面上で区別できない。機械翻訳パイプラインやコピー&ペーストの過程でこうした文字が混ざると、レビュー担当がいくら見ても捕まえられない。

これはむしろ機械が楽に捕まえる。韓国語ドキュメントにキリル文字を禁じるルール一つで引っかかる。ここに一つのトークンの中にラテンとキリルが同居する場合を足せば精度がさらに上がる。正常な文書で一単語が二つのアルファベット体系からなる理由がないからだ。

function scriptsOf(token) {
  const s = new Set();
  for (const ch of token) {
    if (/\p{Script=Latin}/u.test(ch))    s.add('Latin');
    if (/\p{Script=Cyrillic}/u.test(ch)) s.add('Cyrillic');
  }
  return [...s];
}
scriptsOf('Аpple');  // [ 'Cyrillic', 'Latin' ]  ← 先頭がU+0410
scriptsOf('Apple');  // [ 'Latin' ]

6. 同じ文字体系の中の汚染 - 簡体字・繁体字・新字体

ここまでのルールは文字体系が異なるときにだけ働く。ところが実際のローカライズでよく出る欠陥は同じ文字体系の中で生じる。簡体字の文書に繁体字が混ざる、中国語の文書に日本式の字体が残る、翻訳メモリが二系統を混ぜて返す、といった場合だ。

2節で見たとおりコードポイントだけでは系統が分からない。そこで別の方法を使う。片方の系統にしか存在しない字を標本として集め、個数を数える。発と發、国と國、会と會、門と门、時と时のように簡繁で異なる字だけを選んで二つの集合を作り、文書にそれぞれ何個出るかを数える。

const HANS = new Set([...'这么无发国际会议们个东车马门问题时间实现体系统计龙凤业务产资总']);
const HANT = new Set([...'這麼無發國際會議們個東車馬門問題時間實現體系統計龍鳳業務產資總']);

function variant(t) {
  let s = 0, r = 0;
  for (const c of t) { if (HANS.has(c)) s++; if (HANT.has(c)) r++; }
  return { simplified: s, traditional: r };
}
variant('这是国际会议的问题');  // { simplified: 7, traditional: 0 }
variant('這是國際會議的問題');  // { simplified: 0, traditional: 7 }
variant('这是國際会议的问题');  // { simplified: 5, traditional: 2 }  ← 混用
variant('中文');                // { simplified: 0, traditional: 0 }  ← 判定不能

この方式の性質を正確に把握しておけば誤解がない。

  • 混用はよく捕まる。片方だけが期待される文書に反対側の標識が出れば、その位置がそのまま欠陥の位置だ
  • 判定不能区間が必ず残る。両系統で同じ字だけからなる短い文字列はどちらか分からない。上の例の中文がそれである
  • 標本の大きさがそのまま感度だ。標識の字を20字しか使わなければ短い文書はほとんど判定不能に落ちる。実務で使うなら数百字規模の表を用意するほうがよい
  • 日本の新字体は別問題だ。新字体の中には中国簡体字と同じ字もあれば違う字もある。中国語文書に残った日本式の字体を捕まえるには「新字体にはあり簡体字にはない字」で三つ目の標本を別に作る必要がある

判断を一つ書く。このルールは警告に置き、遮断に上げてはならない。引用文に原文の系統がそのまま入る場合、固有名詞が繁体字で定着している場合、標識の字が偶然別の意味で使われた場合が、すべて正当な例外だからだ。文字体系の異なる混入とは違い、ここでは人の判定が必要な割合が有意に高い。

7. 文字化けと言語混入は別の問題だ

二つの欠陥はしばしば一つのチェッカーに押し込められる。分けねばならない。原因が違い、直し方が違うからだ。

  • 言語混入 — 文字は完全に正常だ。あるべき場所でないだけである。原因は翻訳工程にある
  • 文字化け — 文字そのものが誤って作られている。原因はエンコーディング処理にある

区別は難しくない。化けには指紋がある。

// UTF-8バイトを西欧エンコーディングで読んだとき
Buffer.from('한글', 'utf8').toString('latin1');
// 'íê¸'  →  U+ED U+95 U+9C U+EA U+B8 U+80
//   Hangulスクリプトはゼロ個、ラテン補助領域の記号が並ぶ

// cp949バイトをUTF-8で読んだとき
Buffer.from([0xC7, 0xD1, 0xB1, 0xDB]).toString('utf8');
// '�ѱ�'  →  置換文字U+FFFDが刺さる
症状文字化け言語混入
U+FFFD置換文字よく出る出ない
ラテン補助領域の記号が連続典型的出ない
人が読めるか読めない読める。別の言語なだけ
スクリプト属性の判定元の文字体系が消える正常な文字体系として検出される
直す場所ファイル読み書き地点のエンコーディング翻訳工程と原本ファイル

U+FFFDについてはUnicode標準 第5章が不正なバイト列に出会ったときの処理原則を定めている。置換文字が文書にあるということはどこかでデコードが失敗したという確定信号なので、これは言語チェックとは別に常に遮断してよい数少ないルールの一つだ。

エンコーディングの誤りがどの段階で生じたかを特定する方法はハングルが壊れる地点を特定する方法で別に扱った。この記事では、その欠陥が言語混入チェックに混ざり込まないようルールと報告メッセージを分離せよというところまでを述べる。二つの欠陥が同じ名前で報告されると、直す人が毎回見当違いの場所を先に見ることになる。

8. 正規化を検査の前に置くか後に置くか

正規化形式によって同じチェッカーが違う答えを出す。これが実際に判定を覆す。

const doc = 'The word 한글 appears here.'.normalize('NFD');

/[가-힣]/.test(doc);              // false  ← 取りこぼす
/\p{Script=Hangul}/u.test(doc);   // true   ← 捕まえる
/[가-힣]/.test(doc.normalize('NFC'));  // true  ← NFCに直せば捕まる

理由は単純だ。NFDに分解されたハングルは完成形の音節ではなく字母の並びである。[가-힣]は完成形音節の領域しか見ないので一つも引っかからない。スクリプト属性は字母にもHangulが付いているのでそのまま捕まえる。UAX #15が定義する四つの正規化形式のどれで入ってくるかによって結果が分かれるわけだ。

互換正規化のほうでは方向が逆に働く。

const s = 'ko 文書の中の ｻｰﾊﾞｰ';
/[぀-ヿ]/.test(s);                   // false  ← 半角なので取りこぼす
/[぀-ヿ]/.test(s.normalize('NFKC')); // true   ← NFKCが全角に畳んでくれる

'ｻｰﾊﾞｰ'.normalize('NFKC');  // 'サーバー'
'ＡＢＣ'.normalize('NFKC');   // 'ABC'
'㈱'.normalize('NFKC');      // '(株)'

ここから実務ルールが出る。

  1. 検査対象のテキストは検査直前にNFCへ揃える。字母分解形で入ってきたテキストがルールを通過する事故を防ぐ
  2. やむを得ずブロック範囲方式を使うならNFKCまで適用する。半角カナが全角に変わって範囲に入る
  3. スクリプト属性方式ならNFKCは不要だ。半角カナにもKatakanaスクリプトが付いているので正規化なしで捕まる
  4. 正規化したテキストをそのまま保存するな。検査用の複製にだけ適用する。NFKCは情報を消す変換なので、原本に適用すると戻せない

最後の項目は一般的な原則の特殊な場合だ。値を変える時点と検査する時点の順序が食い違うと検査結果自体が無意味になるが、この軸は検証した後に値を変えると検証は無効になるで詳しく扱った。ハングルがNFCとNFDの間でどう変わるか、どの境界で形が変わるかはハングルが字母に分解される瞬間のほうが詳しい。

9. チェッカーを信じるには汚染を仕込め

チェッカーが何も報告しないとき、それが綺麗だという意味なのかチェッカーが壊れたという意味なのかを区別する方法が要る。これは実際によく起きる失敗だ。正規表現のフラグを落とす、ファイル拡張子のフィルタがずれる、範囲縮小が広すぎて本文全体が除去される、どれでも結果は同じく「異常なし」になる。

解決は一つしかない。わざと汚染を仕込み、チェッカーが捕まえるか確かめる。これはチェッカーの単体テストではなく感度テストだ。仕込む標本は実際に出る型でなければならない。

  1. 対象言語と違う文字体系の一文 — 最もよくある型
  2. 半角カナ — ブロック範囲方式が取りこぼす代表例
  3. ハングル互換字母 — 字母範囲しか見ないチェッカーが取りこぼす
  4. NFDに分解された文字列 — 正規化順序の欠陥を露わにする
  5. キリル文字一単語 — パイプライン事故の型
  6. 漢字とハングルがくっついた単語 — 隣接ルールが生きているかの確認
  7. 簡体字・繁体字が混用された文 — 標識の標本が十分かの確認

そして反対側も一緒に仕込む。正当な例外を入れて静かかどうかを確かめねばならない。ブランド名の入った文、括弧併記、コードブロック内の正規表現、中黒を使った並列。誤検知が一つでも出れば、そのルールはまだ配れない。

このテストは回帰テストとして固定しておくことが要点だ。標本ファイルをリポジトリに入れ、チェッカーが汚染標本を全部捕まえ正常標本を全部通すかを毎回確かめる。ルールを一つ直すたびに以前捕まえていたものを取りこぼすようになる事態は実際に起き、それはこのテストなしには表に出ない。

標本を作るときに一つ。汚染標本ファイル自体が検査対象フォルダの中にあると、チェッカーがそのファイルを欠陥として報告する。標本は検査範囲の外に置くか、ファイル名規則で明確に除外すること。そしてその除外規則のせいで本物の文書まで一緒に抜けていないか、もう一度確かめる必要がある。

10. 何を遮断し、何を警告だけにするか

ルールを全部同じ重さで扱ってはいけない。遮断に上げる条件は三つで、三つが同時に成立するときだけ上げる。

  1. 誤検知が事実上ゼロ。正常な文書で引っかかる場合を説明できてはならない
  2. 判定根拠をすぐ確認できる。位置と原文の断片が報告に入っていること
  3. 直し方が自明。「この文を訳せ」のように行動が一つに定まること
ルール判定理由
U+FFFD置換文字の存在遮断デコード失敗の確定信号。正当な場合がない
enドキュメント内のハングル・カナ・キリル遮断範囲縮小と許可リストを通した後なら誤検知がほぼない
zhドキュメント内のカナ遮断同上
jaドキュメント内のハングル遮断同上
どの言語であれ想定外のキリル遮断パイプライン事故の型。正常な文書に入る経路がない
漢字とハングルがくっついた単語遮断併記の形を構造的に避けるので誤検知が低い
比率しきい値の超過警告しきい値自体が判断だ。文書の種類ごとに正当な差がある
簡体字・繁体字の混用警告引用・固有名詞という正当な例外が実在する
koドキュメント内の漢字ルールを作らない併記が正常だ。ルールを作れば誤検知しか生まない
漢字だけの短い文字列の言語ルールを作らない判定不能区間。検査対象から外す

表の最後の二行が重要だ。ルールを作らないことも設計判断である。捕まえられないものを捕まえようとすれば、そのルールは必ず誤検知として戻ってきて、誤検知は4節で見たとおりチェッカー全体を引きずり下ろす。

警告等級にも条件を一つ付けるほうがよい。警告件数が増えること自体を指標として見る。先週12件だった警告が今週80件なら、個別の件を全部開かなくてもどこかのバッチで何かが変わったと分かる。警告を「あとで見るリスト」ではなく趨勢を読む計器として使えば、無視される速度が遅くなる。

10.1 導入の順序

一度に全部点けると初日に警告が数百件出て、そのまま消される。順序を分ける。

  1. まず報告だけする。遮断なしで一、二週間回し、現状の実際の規模を見る
  2. 誤検知の型を分類する。ブランド・コード・併記・その他に分け、その他が何かを必ず確認する
  3. 範囲縮小と許可リストで誤検知をゼロ近くまで下げる。この段階が大半の時間を食う
  4. 既存の欠陥を一度に片づける。残したまま遮断を点けると無関係な変更まで全部止まる
  5. 誤検知ゼロのルールだけ遮断に上げる。残りは警告に置く
  6. 回帰標本を付ける。この時点で付けてこそ以後のルール変更で感度が維持される

4段階を飛ばす場合が多いが、これが導入失敗の最もよくある原因だ。既存の欠陥が残っている状態で遮断を点けるとこの欠陥と何の関係もない変更まで全部止まる。すると人はチェッカーを直す代わりに抑制コメントを書き始め、そのコメントが増えた瞬間にルールはすでに死んでいる。

11. 確認できなかったこと

以下の項目は根拠を特定できなかったため、本文で数値や断定として使わなかった。

  • 他のランタイムでのスクリプト属性の挙動。本文の実行結果はNode 22基準だ。正規表現の\p{Script=…}はランタイムが内蔵するUnicodeデータのバージョンによって結果が変わり得るし、特に国際化データを削ってビルドした環境でどうなるかは確認できなかった
  • Python・Java・Goなどでの同等の表現。各言語の正規表現エンジンがスクリプト属性をどの文法で支援するか、支援範囲が同じかは照合していない
  • 統計的言語判別ライブラリとの比較。n-gram基盤の言語判別器が短い文字列でどの程度正確か、文字体系チェックと組み合わせたときの利得がどれほどかは測定していない
  • 簡繁の標識文字の適正規模。本文の例は20字台の標本だ。実務で何字入れれば短い文書でも判定が立つかは文書の性格によって変わるので数値を提示していない
  • 日本の新字体専用の字集合。新字体にはあり簡体字にはない字の完全な一覧は確認できなかった
  • 東南アジア文字圏とアラビア文字圏の例外類型。タイ語・クメール語のように分かち書きのない文字圏、アラビア文字のように双方向テキストが入る場合にどんな正当な例外が追加で要るかは扱えなかった
  • 誤検知率の絶対値。本文3.1の十四個の標本は失敗の型を示すためのものであり、精度の測定ではない。実際の文書集合での誤検知率は文書の性格に大きく左右される

結論: 捕まる範囲を広げず、報告を締めよ

多言語ドキュメントの言語混入チェックは二つの部分に分かれる。前半は機械的だ。Unicodeがすでにすべての文字に文字体系を記録してあるので、スクリプト属性を読んで対象言語に出現し得ない値を探せばよい。ブロック範囲を手で書くよくある方式よりこちらが明らかに優れており、替える費用も大きくない。

後半が設計だ。固有名詞とコードと併記を選り分けられなければチェッカーは誤検知の山になり、誤検知の山になったチェッカーは消される。だからルールを作るときの基本方向は「もっと多く捕まえる」ではなく「報告されるものが全部本物であるように締める」である。取りこぼした型は後でルールを一つ足せば済むが、一度信頼を失ったチェッカーは蘇らせにくい。

今すぐ試す値打ちのあることを二つだけ残す。一つは今使っている検査ルールに半角カナとハングル互換字母を入れてみることだ。何か出てくれば、その型を丸ごと取りこぼしていたということである。もう一つは正常なドキュメント十個にチェッカーを回してみることだ。ここで出る警告がそのチェッカーの寿命であり、一つでも出れば締める番だ。
