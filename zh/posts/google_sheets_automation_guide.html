Google表格自动化完全指南 - 从公式到Apps Script、表单联动与提醒

从公式层面到脚本层面,用实例梳理如何减少Google表格里的重复劳动

2026年7月24日 IT/技术

引言: 把重复劳动交给表格去做

每周把同一个公式重新复制到新的行里,从另一个表格里手动搬运数值,每次收到回复都要有人去核对再发邮件——这类重复劳动,很大一部分都可以在Google表格内部自动完成。有些靠公式就能搞定,有些则真的需要触发器和脚本。

本文以2026年7月的信息为准,按照实操顺序依次讲解公式自动化(ARRAYFORMULA·QUERY·IMPORTRANGE·FILTER)、数据验证与条件格式、Apps Script入门(触发器与简单脚本)、表单与表格的联动、webhook与API等外部集成、自动邮件提醒、协作时的注意事项,以及大数据量下的局限与替代方案。

1. 公式自动化 - ARRAYFORMULA·QUERY·IMPORTRANGE·FILTER

1.1 ARRAYFORMULA - 只需输入一次,套用到整列

普通公式只作用于单个单元格,要向下自动扩展就得拖拽复制。ARRAYFORMULA能把这个公式一次性套用到指定的整个区域,即使之后新增行,也会自动参与计算。

=ARRAYFORMULA(IF(A2:A="", "", B2:B*C2:C))

这个公式会对A列不为空的每一行,把B列和C列相乘。只要有新订单加进A列,结果列就会自动填上数值。不过像QUERY、FILTER、SORT、IMPORTRANGE这类本身就会返回数组的函数,不需要再用ARRAYFORMULA包裹。

1.2 QUERY - 用类SQL语法做汇总

QUERY使用一种类似SQL的语法,即Google可视化API查询语言。

=QUERY(订单!A:E, "SELECT A, SUM(D) WHERE C = '已完成' GROUP BY A ORDER BY A", 1)

这个公式只从订单表里挑出状态为已完成的行,再按负责人汇总金额。SELECT用来选列,WHERE用来设置条件,GROUP BY确定汇总的分组依据,ORDER BY负责排序。需要选取多列或做汇总时,QUERY比FILTER更强大。

1.3 IMPORTRANGE - 导入另一个电子表格的数据

IMPORTRANGE可以从完全独立的另一个电子表格文件中导入数据。

=IMPORTRANGE("https://docs.google.com/spreadsheets/d/文档ID/edit", "源表!A:D")

第一次使用时需要先授权访问,之后只要源数据变化,导入的数据也会自动更新。把它和QUERY结合,可以在导入另一个文件数据的同时进行筛选。

=QUERY(IMPORTRANGE("文档URL", "源表!A:D"), "SELECT Col1, Col2 WHERE Col3 = '已完成'")

1.4 FILTER - 简单提取符合条件的行

FILTER是一个只返回符合条件行的简洁函数。

=FILTER(A2:D, C2:C="已完成", D2:D>=10000)

这个公式只返回状态为已完成且金额不低于10000的行。条件简单时,FILTER比QUERY更易读。搭配IMPORTRANGE,还能在导入外部表格数据的同时只筛选出符合条件的行。

2. 数据验证与条件格式

数据验证(数据→数据验证)用来限制单元格里能输入的值,比如从下拉列表中选择、限定数字范围、强制日期格式,并可以选择违反规则时直接拒绝输入还是仅弹出警告。这在多人共同填写的表格里,能从源头堵住错别字和格式不一致的问题。

条件格式(格式→条件格式)会根据数值自动改变单元格的背景色或字体颜色。比如可以设定,截止日期早于今天就标红,状态为已完成就标灰。使用自定义公式条件,还能引用其他列的值,表达更复杂的逻辑。

=AND($C2="进行中", $D2 < TODAY())

把这个公式作为条件格式里的自定义公式,就能给状态为进行中且已过截止日期的整行应用格式。

3. Apps Script入门 - 触发器与简单脚本

3.1 触发器的种类

Apps Script的触发器大致分两种。简单触发器如onOpen(e)、onEdit(e),只要写出对应名称的函数就会自动运行,但无法使用需要授权的服务(比如发送外部邮件、发起URL请求),执行时长也受限较短。可安装触发器需要在脚本编辑器的触发器菜单里手动注册,但可以使用需要授权的服务,还能按时间驱动运行(比如每天固定时间、每周固定星期几等)。用来检测表单提交的onFormSubmit,也需要注册为可安装触发器才能稳定工作。

3.2 限制条件

一个脚本最多可以创建20个时间驱动触发器,单次触发运行最长允许6分钟。每天所有触发器运行时长的总和,个人账号上限为90分钟,Workspace账号上限为6小时。一旦超过这个限额,脚本就会默默失败,因此应避免设计成以非常短的周期(比如每分钟一次)去跑很重的任务。

3.3 简单脚本示例 - 给新行打上时间戳

function onFormSubmit(e) {
  const sheet = SpreadsheetApp.getActiveSpreadsheet().getActiveSheet();
  const lastRow = sheet.getLastRow();
  sheet.getRange(lastRow, 6).setValue(new Date());
}

把这个函数注册为onFormSubmit可安装触发器,每当表单回复作为新行进来,就会自动在第6列记录处理时间。

4. 表单→表格联动

在Google表单编辑界面打开回复选项卡,点击表格图标,可以新建一个用来保存回复的表格,或关联到已有表格。关联之后,每次提交回复都会自动新增一行。在此基础上加上前面提到的onFormSubmit触发器,就能在每次收到回复时实时自动完成后续处理——校验数值、把符合特定条件的回复转存到另一个表格,或自动给负责人发送提醒邮件。

5. 外部集成 - webhook与API的概念

借助Apps Script的UrlFetchApp服务,表格可以向外部网络服务发送HTTP请求。利用它,可以在表格新增一行或某个数值发生变化时,通过webhook把通知发到Slack或Discord频道,也可以调用内部系统的API来交换数据。

function notifySlack(message) {
  const url = "https://hooks.slack.com/services/你的webhook地址";
  const payload = { text: message };
  UrlFetchApp.fetch(url, {
    method: "post",
    contentType: "application/json",
    payload: JSON.stringify(payload)
  });
}

反过来,如果想把表格当作API对外暴露,可以把Apps Script部署成网页应用,通过doGet(e)、doPost(e)函数接收外部请求,读写表格数据。不过对于认证和流量都很关键的服务而言,专用后端API会比这种方式更稳妥。

6. 自动提醒 - 发送邮件

利用Apps Script的MailApp或GmailApp服务,只要出现符合条件的行,就可以自动发送邮件。

function sendDailyReport() {
  const sheet = SpreadsheetApp.getActiveSpreadsheet().getSheetByName("订单");
  const data = sheet.getDataRange().getValues();
  const pending = data.filter(row => row[2] === "待处理");
  if (pending.length > 0) {
    MailApp.sendEmail("负责人@example.com", "有" + pending.length + "条订单待处理", "请及时查看确认。");
  }
}

把这个函数注册为时间驱动的可安装触发器,设定每天上午9点运行,就能得到一套只在有待处理订单时才发邮件的每日提醒系统。MailApp在个人账号下每天有发送数量上限,如果需要大批量发送,应考虑改用Workspace账号或专用邮件服务。

7. 协作时的注意事项 - 权限与版本

多人同时编辑同一个表格时,应明确划分共享权限。权限大致分为查看者(只读)、可评论、可编辑三个级别,包含公式的关键列最好加上范围保护(数据→保护工作表和范围),以防连编辑者也不小心把公式删掉。此外,文件→版本历史记录可以回到某个历史版本,或给特定版本命名保存;但如果表格上挂着Apps Script自动化,一旦不小心重复注册了触发器,或者脚本引用的表格名称、列位置发生变化,整套自动化都可能悄悄失效,因此在改动结构之前,养成先检查触发器列表和脚本代码的习惯很有必要。

8. 性能局限与替代方案 - 数据量大时考虑数据库

Google表格对每个文件有单元格数量上限(大致一千万个左右),而且远未触及这个上限之前,随着数据增多,公式重新计算和界面渲染就会明显变慢。尤其是把QUERY或数组公式挂在很大的区域上时,每次打开表格或编辑数值都会产生延迟。Apps Script触发器也只能在前面提到的执行时长和次数限额内运行,因此把很重的批量处理设计成密集周期执行,迟早会碰到瓶颈。

如果数据会持续增长到超过数万行、需要多个用户同时大量写入,或者需要严格一致性的事务处理,比起Google表格,迁移到关系型数据库或专用后端会更稳定。这种情况下,表格不再是原始数据的存放处,而是收窄为在数据库之上、借助QUERY或API集成搭建的报表与看板层,这种结构在实际使用中更经得起时间考验。

结论

对Google表格自动化,分阶段推进是比较合理的做法。先确认ARRAYFORMULA、QUERY、FILTER、IMPORTRANGE这类公式能否解决问题,再用数据验证和条件格式减少输入错误,最后只在真正需要脚本的环节——表单联动后的处理、定期提醒、外部系统集成——引入Apps Script触发器。而当数据规模开始逼近表格的极限时,与其硬撑在表格里,不如尽早决定迁移到数据库、让表格收窄为报表角色,这个决定不宜一拖再拖。
