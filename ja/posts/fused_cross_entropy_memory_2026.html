メモリを節約してCross Entropyを計算する - LM HeadがGPUメモリを食い尽くす理由と対策

長いコンテキスト・大きなvocabのLLM学習でロジットがボトルネックになる理由と、Fused Linear Cross Entropyがそれを避ける仕組み

2026-07-07 IT・技術

序論: 学習が落ちるのはAttentionではなく最後の一行だ

LLMを学習させたことがある人なら、一度は経験する状況がある。モデルサイズもバッチもシーケンス長もすべて計算し、GPUメモリは十分だと確信していたのに、実際に学習が落ちるのはAttentionでもフィードフォワードでもなく、最後の一行、損失(loss)を求める瞬間だ。2026年7月初め、Trillion Labsが公開した分析記事はこの現象を正面から扱った。16B規模のモデルを8K前後のシーケンスで学習していた際、Cross Entropy損失を求めるたった一度の呼び出しで30GBを超えるメモリが一気に消費され、学習が落ちたという実際の障害事例を紹介したのだ。

本稿はその分析記事の数字をそのまま転記するのではなく、なぜLM headの直後にある損失計算がメモリボトルネックになるのか、そしてロジットを丸ごと作らずに同じ損失を求めるアイデアが何なのかを、概念中心に自分自身の解釈を加えて整理する。2026年7月現在、この最適化はすでに複数の学習ライブラリに組み込まれた実務的な手法になっている。

1. なぜLM HeadとCross Entropyがボトルネックになるのか

1.1 隠れ状態は小さく、ロジットは大きい

トランスフォーマー本体を通過した結果はトークン一つあたり隠れ状態ベクトル一つで、その大きさは通常数千次元(D)程度だ。しかし次のトークンを予測するには、このベクトルを語彙サイズ(V)分のスコア、つまりロジットに変換しなければならない。問題はVがDよりはるかに大きいことだ。最近のモデルのvocabは13万から26万トークン規模まで大きくなっており、隠れ次元はその数十分の一に過ぎないことが多い。トークン一つごとにD次元のベクトルがV次元のロジットへと膨らむため、シーケンス全体・バッチ全体で掛け合わせると、ロジットテンソル一つがモデル重み自体より大きくなるという逆転現象が起きる。

1.2 vocabも大きくなり、コンテキストも長くなった

vocabが大きくなった理由は多言語・コード・特殊トークンをより細かく扱うためであり、コンテキストが長くなった理由は文書・コードベース・会話履歴を丸ごと入れたいという要求のためだ。どちらもそれぞれ理にかなっているが、この二つが同時に大きくなると、ロジットテンソル(バッチ×シーケンス×vocab)の体積は二つの軸で同時に膨れ上がる。実際、十数万規模のvocabとそれに匹敵するシーケンスを組み合わせると、ロジットテンソル一つだけで数十GBに達するケースも珍しくないと報告されている。

1.3 一瞬しか使わないのに問題になる理由

さらに厄介なのは、この巨大なテンソルがずっと必要な値ではないという点だ。損失一つを計算するために一瞬作られ、すぐに捨てられる値であるにもかかわらず、その一瞬の間GPUメモリの中で最大の塊を占める。学習フレームワークにとっては、AttentionやフィードフォワードよりもむしろこのLM head後の一行でメモリ予算が破裂するという逆説が生まれる。

2. 単純に分ければよいのでは - naive chunkingが失敗する理由

2.1 シーケンスを分けて計算すると

直感的な最初の対応は、シーケンスを複数の断片(チャンク)に分け、断片ごとにロジットと損失を別々に計算してから捨てることだ。こうすれば一度に作られるロジットの大きさは確実に減る。しかし実際に測定してみると、この方式では学習ステップ全体の最大メモリ使用量が期待ほど減らないという報告がある。

2.2 計算グラフがそのまま残る

理由は逆伝播にある。ディープラーニングフレームワークは各断片の順伝播結果を逆伝播時の勾配計算に使う必要があるため、断片ごとの計算グラフを逆伝播が実行されるまで持ち続けなければならない。つまり断片をどれだけ細かく分けても、すべての断片のグラフが一度にメモリに積み上がったまま最終的な逆伝播を待つ構造であれば、最大メモリ使用量はほとんど減らない。関連する実験でも、断片数を増やしても最大メモリはある水準でほぼ変わらず、むしろ断片を細かく分けるほど遅延だけが増えたという。「分けて計算する」という方向性自体は正しいが、そのグラフをいつ手放すかが本当の鍵だということだ。

方式ロジットテンソル計算グラフ
一度に計算全体を一度に生成全体をそのまま保持
naiveなシーケンスchunking断片ごとに生成後破棄すべての断片のグラフが逆伝播まで蓄積
Fused Linear CE断片ごとに生成し即座に勾配へ置換断片グラフを逆伝播まで保持しない

3. Fused Linear Cross Entropyのアイデア

3.1 射影と損失を一つにまとめる

FLCEの核心は、最終線形層(LM head)の射影とその結果に対するCross Entropy計算を一つの演算単位に統合することだ。断片一つを処理する際、その断片のロジットを求めた瞬間に損失も同時に計算してしまい、ロジット自体は次の断片に移る前に未練なく捨てる。

3.2 ロジット全体なしで損失を求める方法

Cross Entropyを求めるには理論上、語彙全体に対するソフトマックス正規化が必要だ。しかし正規化に必要な値(最大値と指数和)は、語彙を断片ごとに巡りながら累積的に更新できる。この「流れるような値の更新」方式はFlashAttention系のAttention最適化でも使われる馴染みのあるアイデアで、全体を一度に広げなくても同じ結果にたどり着ける。その結果、ロジット全体をどこかに並べる必要なく、小さな断片だけを一瞬GPUに載せては流していく方式で損失を計算できる。

3.3 勾配もその場で計算して流す

本当の妙手は逆伝播の準備方法にある。FLCEは順伝播の段階で断片ごとのロジットに対する勾配まですぐに計算してしまう。その勾配を直ちに入力方向(隠れ状態に対する勾配)とLM head重み方向(重みに対する勾配、断片ごとに累積)へ移し替えてしまえば、断片のロジットとその勾配はもはや保持しておく理由がない。逆伝播が実際に実行される際は、こうして事前に計算しておいた、はるかに小さな結果をスケーリングするだけで済む。結局、ロジットという名の大きく寿命の短いテンソルが計算グラフに長く登録されない構造になるわけだ。これは数式を変えたのではなく、どの中間結果をいつまで保持するかを再設計したことに近い。

4. 実際の実装はどう流れるか

4.1 Liger Kernel

このアイデアが実務で最も広く触れられる形は、LinkedInが公開したオープンソースのTritonカーネル集Liger KernelのFusedLinearCrossEntropyだ。Hugging Faceモデルに数行加えるだけで適用でき、PyTorch FSDPやDeepSpeedのような分散学習スタックとも噛み合って動作するよう作られているという。公開資料では十万台のvocab帯で数倍のメモリ削減効果を報告しているが、こうした数値はモデル構造・GPU・設定によって大きく変わりうるベンチマーク値である点は考慮すべきだ。

4.2 学習フレームワークに組み込まれた最適化

Liger Kernelだけでなく、複数のファインチューニングツールも似たアイデアの独自実装を出している。あるファインチューニングフレームワークは、チャンク単位のfused lossを適用して同じハードウェアで扱えるコンテキスト長が目に見えて伸びたと報告している。こうした事例はいずれも「断片単位で計算し、断片の中で勾配まで終わらせる」という同じ骨組みを共有している。

4.3 より低層のカーネル

Trillion Labsが自前のFLCE実装の参照としたのはLigerではなく、Tri Dao研究室(Dao-AILab)が公開したCUTLASS・CuTeベースの低層カーネル集QuACKだ。QuACKはRMSNorm・ソフトマックス・Cross Entropyといった数種類の演算を、最新のGPUアーキテクチャ(H100・B200級)に合わせて極限まで最適化することに焦点を当てている。同じ概念であっても、どのハードウェアにどれだけ密着して書くかによって異なる実装が並存するエコシステムがすでに形成されているわけだ。

5. 実務で体感する効果

5.1 より長いコンテキスト、より大きなバッチ

この最適化が実務にもたらす意味は単純だ。損失計算の段階で節約したメモリの分だけ、同じGPUでより長いコンテキストを学習したり、バッチサイズを大きくしたりする余裕が生まれる。実際、あるファインチューニングツールはfused・chunked cross entropyを適用した後、同じGPU一枚で扱えるコンテキスト長が目に見えて伸びたと報告した。vocabが大きく、コンテキストが長いモデルほど、この効果はより鮮明に現れる傾向がある。

5.2 削減幅はワークロードごとに異なる

ただし、この削減幅を固定された数値として覚えるのは危険だ。vocabサイズ、隠れ次元、シーケンス長、バッチサイズ、そしてどのカーネル実装を使うかによって体感効果はかなり異なる。複数の公開ベンチマークが数倍から80〜90%前後までのメモリ削減を報告しているが、これは特定の条件下で観測された数値であり、あらゆる状況にそのまま当てはまる保証値ではない。

6. トレードオフと限界

6.1 タダ飯ではない

チャンク単位で分けて計算する分、完全に一度に計算する方式よりもカーネル呼び出し回数やオーバーヘッドが増える余地がある。教育目的で単純に書かれた実装では、こうしたオーバーヘッドのために標準実装よりむしろ遅くなるケースも報告されている。実務で使われる完成度の高いカーネルはこのオーバーヘッドを最小化するよう別途精巧にチューニングされているが、「メモリは減り、速度は常に変わらない」と断定はできない。

6.2 数値安定性という宿題

ソフトマックス正規化値を断片ごとに流れるように更新する方式は、一度に計算する方式より実装が難しい。浮動小数点誤差が蓄積する箇所を誤って扱うと、損失値や勾配が微妙にずれる可能性があるため、カーネルを自前で実装するなら精度検証が欠かせない。

6.3 万能薬ではない

この手法が減らすのはあくまでLM headと損失計算区間のメモリだ。AttentionのKVキャッシュ、中間活性値、オプティマイザ状態といった他のメモリ消費源はそのまま残る。FLCEは学習メモリ問題全体を解く万能の鍵ではなく、vocabとコンテキストが同時に大きくなるときに際立つ特定のボトルネック一つを正確に狙った最適化と見るのが正確だ。

7. 結論 - 今日確認すべきこと

今回の分析から得られる実用的な結論はこうだ。自前で学習ループを書いていて、vocabやコンテキストが大きいなら、ロジットテンソルがメモリ使用量グラフのどこで最大の山を作っているかからまず点検してみる価値がある。すでにHugging Face TrainerやAxolotlのような馴染みの学習スタックを使っているなら、Liger Kernelのようなfused cross entropyオプションがすでに組み込まれているかを先に確認する方が、カーネルを自分で書くよりはるかに実用的だ。そしてどんな削減数値を見ても、自分のモデルサイズ・vocab・コンテキスト長で実際に測定してみるまでは参考値として受け止めるのが安全だ。
