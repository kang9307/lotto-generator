glojure — Go 위에서 동작하는 Clojure 인터프리터, 왜 만들었나

JVM을 버리고 Go를 호스트로 선택한 Clojure 인터프리터의 의미와 기술적 도전 — 2026년 6월 기준 분석

2026-06-21 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 왜 Go에 Clojure를?

프로그래밍 언어를 보면 대개 두 종류로 나뉜다. 처음부터 자체 VM 위에서 동작하도록 설계된 언어와, 기존 런타임을 호스트로 삼아 그 생태계를 통째로 끌어다 쓰는 언어. Clojure는 후자의 철학을 명시적으로 천명한 언어다. Rich Hickey가 Clojure를 설계할 때 JVM을 호스트로 선택한 것은 취향이 아니었다. Java 생태계의 방대한 라이브러리, 검증된 GC, 성숙한 스레드 모델을 그대로 쓰겠다는 실용적 판단이었다.

그렇다면 glojure는 무엇을 하는 프로젝트인가. 한 줄로 말하면 이렇다. JVM 대신 Go 런타임을 호스트로 삼아 Clojure를 실행한다. 2026년 6월 기준 v0.6.5이며, GeekNews에도 소개된 이 프로젝트는 왜 존재하는가, 그리고 기술적으로 무엇이 어려운가를 이 글에서 짚는다. 찬사를 늘어놓기보다, 왜 이런 선택을 했고 무엇을 포기했는지 정직하게 본다.

1. Clojure의 "호스팅 언어" 철학부터

glojure를 이해하려면 먼저 Clojure 설계 철학을 알아야 한다. Clojure는 의도적으로 호스팅 언어(hosted language)다. Rich Hickey가 공식 문서에서 밝혔듯, Clojure는 "JVM 언어"가 아니라 "JVM에서 호스팅되는 언어"다. 이 차이는 미묘하지만 중요하다.

호스팅 언어 모델에서는 호스트의 타입 시스템, 값, GC, 스레드가 그대로 언어의 일부가 된다. JVM에서 Clojure를 쓸 때 Java 객체는 그냥 Clojure 값이고, 반대도 마찬가지다. 별도의 변환 계층 없이 Java 라이브러리를 (.method object args) 문법으로 바로 호출한다. ClojureScript도 같은 철학을 JavaScript에 적용한다. JS의 DOM API, Node.js 모듈 전체가 ClojureScript 코드에서 직접 접근된다.

glojure는 이 패턴을 Go에 적용한다. Go의 값이 Clojure 값이고, Clojure 값이 Go 값이다. 별도의 FFI 브리지가 아니라 런타임 수준의 통합이다. 이것이 단순한 "Go로 만든 Clojure 파서"와 근본적으로 다른 점이다.

2. 왜 Go를 호스트로 선택했나 — 현실적 이유

JVM에서 이미 잘 돌아가는 Clojure를 굳이 Go 위에서 돌리려는 이유는 무엇인가. 이상론 말고 현실적인 이유가 있다.

2.1 배포의 단순함: 단일 정적 바이너리

Go의 가장 큰 실용적 강점은 단일 정적 바이너리 빌드다. 외부 런타임 의존성 없이 하나의 파일로 배포된다. JVM은 다르다. Java 프로그램을 배포하려면 JRE나 JDK가 설치돼 있어야 하고, 도커 이미지는 OpenJDK 기반 레이어만 수백 MB다. Go 기반 컨테이너 이미지는 멀티스테이지 빌드와 scratch 베이스 이미지를 쓰면 5~20MB까지 떨어진다.

기동 시간 차이는 더 극적이다. 표준 Spring Boot(JVM)는 기동에 약 3.8초가 걸린다. 동급 Go 바이너리는 180ms 내외다. 약 20배 차이다. 서버리스 함수, 쿠버네티스 파드의 빠른 스케일아웃, Lambda 콜드 스타트 환경에서 이 차이는 운영 비용과 직결된다.

glojure와 Gloat(AOT 도구)를 결합하면 Clojure 코드를 Go 소스로 컴파일하고 최종적으로 네이티브 바이너리를 만들 수 있다. 즉, Clojure 문법으로 작성한 코드가 Go의 배포 이점을 그대로 가져간다.

2.2 Go 생태계 접근

Go에는 JVM이나 JavaScript에 없는 강점이 있는 영역이 있다. 특히 클라우드 인프라, DevOps 도구, 네트워킹 스택에서 Go 라이브러리 생태계가 두텁다. Kubernetes, Docker, Prometheus, Terraform이 모두 Go로 작성됐다. 이 생태계를 Java interop처럼 JNI 수준의 복잡함 없이 Clojure 문법으로 직접 쓸 수 있다면 인프라 자동화 스크립팅에서 강점이 생긴다.

실제로 glojure는 fmt, net:http, os, time 등 20개 이상의 Go 표준 라이브러리를 기본 내장한다. (require '[glojure.core :as glj]) 수준의 익숙한 Clojure 문법으로 Go HTTP 서버를 올릴 수 있다.

2.3 Clojure 사용자의 JVM 기피

Clojure 커뮤니티 일부는 JVM 자체를 부담으로 여긴다. JVM 튜닝의 복잡함, 메모리 오버헤드, 개발 환경 의존성을 피하고 싶은데 Clojure의 불변 데이터 구조와 매크로 시스템은 계속 쓰고 싶은 개발자에게 glojure는 탈출구가 된다. Babashka(GraalVM 기반 네이티브 Clojure)가 같은 니즈를 다른 방식으로 해결하는 것과 비슷한 맥락이다.

3. 기술적 도전: 호스팅 언어 구현이 왜 어려운가

아이디어는 매력적이다. 그러나 Clojure를 Go 위에서 제대로 돌리는 것은 단순한 파서 작성과 차원이 다른 문제다.

3.1 Java 호환성 계층 문제

현실 Clojure 코드는 JVM에 깊이 의존한다. Math/sqrt, System/getenv, java.lang.String, java.util.UUID, 정규식 클래스, 숫자 래퍼 타입. 이것들은 Clojure 표준 라이브러리가 직접 호출한다. Go는 이런 Java API를 전혀 모른다.

glojure는 이 문제를 해결하기 위해 gojava라는 Go 네이티브 Java 호환성 계층을 만들었다. Math, System, String 등 주요 클래스의 동작을 Go로 재구현한 것이다. 이 작업 없이는 기존 Clojure 코드 대부분이 glojure에서 실행되지 않는다. 2026년 6월 기준으로 Clojure 호환성 테스트 스위트를 9개(JVM 전용 기능) 빼고 모두 통과했다는 것은 이 계층이 상당히 완성됐다는 신호다.

3.2 패키지 네임스페이스 충돌

Clojure에서 /는 네임스페이스 구분자다. clojure.core/map처럼 쓴다. 그런데 Go 패키지 경로에도 /가 쓰인다. net/http, encoding/json처럼. 두 규칙이 충돌한다. glojure는 Go 패키지의 /를 :로 치환해 이 문제를 해결한다. net:http.Get처럼 쓰는 것이다. 우아한 해결책은 아니지만 실용적인 타협이다.

3.3 STM과 동시성 모델의 차이

Clojure의 atom, ref, STM(소프트웨어 트랜잭셔널 메모리)은 JVM의 메모리 모델 위에서 설계됐다. Go는 다른 동시성 모델, 즉 고루틴과 채널을 쓴다. 이 두 모델을 매끄럽게 연결하는 것은 이론적으로도 구현적으로도 까다롭다. glojure는 atom과 기본 동시성 프리미티브를 지원하지만, JVM 기반 Clojure의 전체 STM을 Go 고루틴 모델 위에 완전히 구현하는 것은 여전히 진행 중인 과제다.

3.4 AOT 컴파일과 Gloat

인터프리터 모드로는 성능과 배포가 제한된다. glojure 팀은 Gloat(Glojure Automation Tool)을 별도 개발해 AOT 컴파일 파이프라인을 만들었다. .clj → .glj → .go → 네이티브 바이너리/WASM 단계를 거쳐 실제 배포 가능한 바이너리를 생성한다. 20개 이상의 OS/아키텍처, WebAssembly 모듈, 공유 라이브러리 출력이 가능하다. JVM 기반 GraalVM native-image가 분 단위 컴파일 시간인 데 비해 Gloat는 초 단위로 빌드되는 것이 장점으로 내세워진다.

4. 생태계 위치: let-go, Babashka, ClojureScript와의 비교

glojure는 Clojure 대안 런타임 중 하나다. 비슷한 목적의 프로젝트와 어떻게 다른지 짚어 보면 각각의 의도가 더 선명해진다.

프로젝트호스트 런타임배포 방식성숙도주 용도
Clojure(공식)JVMJAR + JVM프로덕션범용
ClojureScriptJavaScript(V8 등)JS 번들프로덕션브라우저/Node
BabashkaGraalVM 네이티브단일 바이너리성숙스크립팅/CLI

let-go와 glojure는 둘 다 Go 위의 Lisp 계열이지만 방향이 다르다. let-go는 독자적인 Clojure 유사 방언을 설계한다. glojure는 기존 Clojure 코드 호환성을 최대한 유지하면서 Go를 호스트로 쓰는 것을 목표로 한다. 2026년 6월 기준 GitHub 스타 증가 속도는 let-go가 두 달간 407개로 glojure의 35개보다 훨씬 빠르다. 커뮤니티 관심은 let-go 쪽이 더 높지만, 기존 Clojure 코드와의 호환성은 glojure가 더 진지하게 추구한다.

Babashka와 비교하면 어떤가. Babashka는 Clojure 스크립팅 도구로서 훨씬 성숙하고 커뮤니티도 크다. GraalVM native-image로 빌드되어 JVM 없이 실행되지만 GraalVM의 AOT 제약(동적 클래스 로딩 제한 등)을 받는다. glojure는 Go 런타임 자체를 호스트로 삼아 Go interop이 더 자연스럽다는 점이 차별점이다.

5. 실제로 어떻게 쓰나 — REPL, CLI, 임베딩

glojure는 두 가지 사용 모드를 지원한다. 독립형 CLI 도구(glj)와 Go 애플리케이션 내 임베딩이다.

5.1 glj CLI와 REPL

설치는 Go 모듈 시스템으로 한 줄이다.

go install github.com/glojurelang/glojure/cmd/glj@latest

Go 1.24 이상이 필요하다. glj를 실행하면 REPL이 뜨며, vi/emacs 편집 모드, 멀티라인 표현식, 탭 자동완성, 기록 유지, 스마트 들여쓰기를 지원한다. 기존 Clojure 개발자라면 낯설지 않은 환경이다.

5.2 Go 애플리케이션에 Clojure 임베딩

더 흥미로운 용도는 기존 Go 애플리케이션에 Clojure를 스크립팅 레이어로 추가하는 것이다. Go로 구현된 서버나 CLI 도구에 런타임 설정·정책 로직·플러그인을 Clojure 코드로 작성하는 패턴이다. Lua를 임베딩하는 것처럼 Clojure를 Go 앱의 스크립팅 엔진으로 쓸 수 있다.

5.3 Go interop 문법

Go 표준 라이브러리를 Clojure 문법으로 쓰는 예시다. (import '[go:net:http Client])처럼 패키지를 불러오고, (.Do client req)처럼 메서드를 호출한다. 콜론 표기법(net:http)이 Clojure의 슬래시 네임스페이스와 공존한다. 처음엔 어색하지만 패턴을 이해하면 Go 코드를 Clojure 스타일로 쓰는 감각이 생긴다.

6. 한계와 현실적 평가

매력적인 아이디어지만 현시점의 한계를 직시해야 한다.

6.1 아직 v1 이전 — 하위 호환성 없음

개발팀이 명시한다. v1 이전까지는 API 변경이 예고 없이 일어날 수 있다. 즉 지금 glojure로 작성한 코드가 다음 릴리즈에서 깨질 수 있다. 프로덕션 크리티컬 경로에 쓰기엔 아직 이르다.

6.2 성능 제한

인터프리터 모드에서의 성능은 JVM 기반 Clojure에 비해 열세다. JVM은 수십 년간 쌓인 JIT 최적화가 있다. Go도 컴파일 언어로서 빠르지만, 그 속도를 인터프리터 모드 glojure가 온전히 활용하지는 못한다. AOT 컴파일(Gloat)로 어느 정도 해소되지만 여전히 성능이 중요한 워크로드에선 검증이 필요하다.

6.3 생태계 미성숙

Clojure의 방대한 라이브러리 생태계(Ring, Compojure, core.async, spec 등)는 JVM 기반이다. 이 라이브러리들을 glojure에서 그대로 쓸 수는 없다. Go interop이 강점이지만 Clojure 사용자가 기대하는 라이브러리 생태계는 아직 형성 중이다.

6.4 진짜 틈새는 어디인가

필자가 보기에 glojure가 가장 설득력 있는 자리는 인프라 도구 스크립팅과 Go 앱 임베딩이다. Kubernetes 운영자, 인프라 자동화 도구, DevOps 파이프라인을 작성하면서 Go 생태계에 이미 발을 걸친 개발자가 Clojure의 표현력과 REPL-driven 개발을 가져오고 싶을 때. Babashka로 커버 안 되는 Go-native interop이 필요할 때. 그 틈새는 좁지만 실재한다.

7. 2026년 6월 현재 진행 상황

Clojurists Together의 2026년 6월 업데이트에 따르면 glojure는 최근 중요한 이정표를 넘었다. 포크 기반으로 진행하던 개발이 공식 업스트림 저장소(glojurelang/glojure)로 복귀했다. Clojure 호환성 테스트 스위트를 (JVM 전용 9개 제외하고) 전부 통과했다. gojava(Java 호환성 계층)이 Math, System, String 등 핵심 클래스를 커버한다. Gloat v0.1.50까지 릴리즈됐으며 WebAssembly REPL도 웹사이트에서 제공된다.

남은 과제로는 더 작고 빠른 바이너리, 실제 Clojure 프로그램 호환성 개선, 런타임 성능 최적화가 명시돼 있다. 취미 프로젝트에서 내부 도구로 쓸 수 있는 수준은 됐지만 프로덕션 주력으로 쓰기엔 아직 단계를 밟아야 한다.

결론: 호스팅 언어 철학의 또 다른 실험

glojure는 "Clojure를 다른 런타임으로 이식한다"는 아이디어의 Go 버전이다. ClojureScript가 JavaScript 생태계를 Clojure로 열었듯, glojure는 Go 생태계를 Clojure로 열려 한다. 기술적으로는 실현 가능하고 실제로 진행 중이며, 2026년 6월 기준으로 의미 있는 이정표를 통과했다.

다만 현실적 판단도 필요하다. Babashka는 이미 스크립팅 도구로서 성숙했고, ClojureScript는 브라우저와 Node에서 프로덕션 검증이 끝났다. glojure가 진짜 채워주는 틈새는 Go 런타임과의 깊은 통합이 필요한 인프라·시스템 도구 영역이다. 그 틈새가 당신의 상황에 해당한다면 지금 REPL을 열어볼 가치는 충분히 있다. 아니라면 v1을 기다리는 것이 합리적이다.

가장 흥미로운 점은 glojure 자체보다 이 프로젝트가 던지는 질문이다. 언어의 정체성은 런타임에 있는가, 문법과 의미론에 있는가. Go 위의 Clojure는 과연 Clojure인가. 그 답은 사용자가 정의한다.
