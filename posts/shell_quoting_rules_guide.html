셸 인용부호 규칙 - 어느 따옴표가 무엇을 막는가

작은따옴표·큰따옴표·ANSI-C 인용을 실행 출력으로 갈라 본다

2026-07-29 개발/인프라

서론: 따옴표 하나가 디렉터리를 비웠다

빈 임시 디렉터리를 만들고 파일 세 개를 넣었다. 두 개는 평범한 이름이고, 하나는 이름 자체가 별표 한 글자다. 그 별표 파일만 지우려고 변수에 이름을 담아 rm에 넘겼다. 결과는 다음과 같다.

$ ls -1
*
keep1.txt
keep2.txt

$ f='*'
$ rm $f
$ ls -1
(비어 있음)

지우려던 것은 파일 하나였는데 디렉터리가 통째로 비었다. 명령을 잘못 친 것이 아니다. rm이 이상한 것도 아니다. 셸이 $f를 *로 바꾼 다음, 그 *를 다시 한 번 파일 이름 목록으로 부풀렸을 뿐이다. 따옴표 두 개만 붙였으면 일어나지 않았다.

이런 사고를 겪은 사람에게 흔히 돌아오는 조언은 「변수에는 따옴표를 붙이세요」다. 맞는 말이지만 규칙이 아니다. 어느 따옴표를 붙여야 하는지, 그 따옴표가 무엇을 막고 무엇을 통과시키는지 말해 주지 않기 때문이다. 그래서 같은 사람이 다음에는 awk 프로그램을 큰따옴표로 감쌌다가 달러 기호가 먹히는 사고를 낸다. 방향은 반대인데 원인은 같다. 인용이 무엇을 끄는 스위치인지 모르는 것이다.

이 글은 정의를 나열하지 않는다. 작은따옴표·큰따옴표·백슬래시·ANSI-C 인용이 각각 무엇을 막는지를 전부 실행해서 출력으로 보여 준다. 문법 규정은 GNU Bash Reference Manual과 POSIX 사양에서 확인했고, 동작은 임시 디렉터리에서 직접 돌렸다. 본문의 모든 출력은 실제로 화면에 나온 것이다. 마지막에는 상황 → 써야 할 인용 → 이유를 한 장의 판단 표로 정리한다.

범위를 미리 좁혀 둔다. 공백이 든 파일 이름을 find와 xargs로 다루는 실무 조합은 find·xargs 공백과 개행 함정에서 따로 다뤘다. 이 글의 관심은 인용부호 문법 자체다. 같은 스크립트를 두 번 돌려도 되는지는 두 번 돌려도 안전한 스크립트, 돌리기 전에 결과를 알 수 있는지는 --dry-run을 제대로 만드는 법에 있다.

2. 셸이 한 줄을 읽는 순서 - 인용은 어느 단계를 끄는가

인용이 헷갈리는 이유는 「따옴표가 문자열을 만든다」고 생각하기 때문이다. 셸에서 따옴표는 문자열을 만들지 않는다. 이미 정해진 처리 단계 중 몇 개를 끄는 스위치다. 그래서 어느 스위치가 어느 단계를 끄는지만 알면 전부 예측할 수 있다.

bash가 명령 한 줄을 실행하기 전에 거치는 순서는 대략 다음과 같다.

한 줄 입력
  1. 중괄호 확장          a{1,2}   →  a1 a2
  2. 틸드 확장            ~        →  홈 디렉터리
  3. 매개변수 확장 · 명령 치환 · 산술 확장
                          $var  $(cmd)  `cmd`  $((1+1))
  4. 단어 분할            IFS 기준으로 필드 쪼개기      ← 여기서 공백 사고
  5. 경로명 확장(글로빙)   *  ?  [...]  →  파일 이름들   ← 여기서 별표 사고
  6. 인용 제거            남아 있는 따옴표 문자를 떼어냄
  → 실행

핵심은 4단계와 5단계가 3단계 뒤에 온다는 것이다. 변수를 펼친 결과가 다시 쪼개지고 다시 부풀 수 있다는 뜻이다. 서론의 사고가 정확히 이것이다. $f가 *가 되고(3단계), 그 *가 파일 목록이 됐다(5단계).

인용은 이 순서 어딘가를 끈다. 어느 것이 어디를 끄는지가 이 글의 전부다.

구분$ 확장백틱백슬래시! 히스토리단어 분할글로빙
인용 없음통과통과통과통과일어남일어남
작은따옴표 '...'차단차단차단차단차단차단

표에서 눈여겨볼 칸은 맨 오른쪽 두 개다. 작은따옴표든 큰따옴표든 단어 분할과 글로빙은 똑같이 막는다. 실무 사고의 90퍼센트는 이 두 칸에서 난다. 그래서 「어느 따옴표를 쓸까」로 고민이 시작되면 이미 절반은 해결된 것이고, 진짜 문제는 따옴표를 아예 안 쓴 자리다.

3. 작은따옴표 - 예외 없는 리터럴

작은따옴표는 규칙이 하나뿐이다. 안에 든 모든 문자가 글자 그대로다. 예외가 없다. Bash Reference Manual은 이렇게 적는다.

Enclosing characters in single quotes preserves the literal value of each character within the quotes. A single quote may not occur between single quotes, even when preceded by a backslash.

실행해서 확인했다. 같은 문자열을 작은따옴표로 감싸 printf에 넘겼다.

$ printf '%s\n' '$name'
$name
$ printf '%s\n' '`printf ran`'
`printf ran`
$ printf '%s\n' '\n  \t  \\'
\n  \t  \\
$ printf '%s\n' '!!'
!!
$ printf '%s\n' 'a "b" c'
a "b" c
$ printf '%s\n' '${name}  $(printf ran)  $((1+1))'
${name}  $(printf ran)  $((1+1))

확장이 하나도 일어나지 않았다. 백슬래시조차 특별하지 않다는 점이 중요하다. \\가 \\ 그대로 나왔다. 큰따옴표에서는 이것이 \ 하나로 줄어든다(4절 참조).

그래서 작은따옴표는 다른 프로그램의 문법을 셸로부터 보호할 때 쓴다. awk 프로그램, sed 표현식, 정규식, find의 패턴, 원격에 넘길 명령 문자열이 전부 여기 해당한다.

대신 대가가 있다. 작은따옴표 안에는 작은따옴표를 넣을 수 없다. 백슬래시로 탈출시키려는 시도가 왜 실패하는지 실행으로 보면 이렇다.

$ printf '%s\n' 'it\'"'"'s'
it\'s

$ bash -c "printf '%s\n' 'it\'s'"
bash: -c: line 1: unexpected EOF while looking for matching `''

첫 줄이 이상하게 보이겠지만 사실은 단순하다. 'it\'에서 문자열이 백슬래시 뒤의 따옴표에서 끝났고, 백슬래시는 문자로 남았다. 두 번째 예에서는 그 뒤에 따옴표 짝이 맞지 않아 파싱이 아예 실패했다. 규정 그대로다. 백슬래시는 작은따옴표 안에서 탈출 문자가 아니다.

따라서 작은따옴표 안에 작은따옴표를 넣으려면 일단 닫고 다른 방식으로 한 글자를 붙인 뒤 다시 여는 수밖에 없다. 네 가지 방법이 있고 결과는 모두 같다.

$ printf '%s\n' 'it'"'"'s'      # 닫고, 큰따옴표로 한 글자, 다시 열기
it's
$ printf '%s\n' 'it'\''s'       # 닫고, 백슬래시로 한 글자, 다시 열기
it's
$ printf '%s\n' "it's"          # 아예 큰따옴표로 감싸기
it's
$ printf '%s\n' $'it\'s'        # ANSI-C 인용 (8절)
it's

$ printf '%s' 'it'\''s' | od -c
0000000   i   t   '   s
0000004

마지막 od -c가 증거다. 셸이 실제로 넘긴 바이트는 it's 네 글자다. 흔히 「따옴표 탈출 관용구」로 불리는 '\''는 마법이 아니라 닫기·한 글자·열기 세 조각이 붙어 있는 것뿐이다.

4. 큰따옴표가 통과시키는 네 가지

큰따옴표는 작은따옴표에서 딱 네 개를 뚫어 준다. Bash Reference Manual의 서술은 이렇다.

Enclosing characters in double quotes preserves the literal value of all characters within the quotes, with the exception of $, `, \, and, when history expansion is enabled, !.

3절과 똑같은 문자열을 큰따옴표로 바꿔 돌린 결과다.

$ name=world
$ printf '%s\n' "$name"
world
$ printf '%s\n' "`printf ran`"
ran
$ printf '%s\n' "\n  \t  \\"
\n  \t  \
$ printf '%s\n' "!!"
!!
$ printf '%s\n' "a "b" c"
a b c
$ printf '%s\n' "${name}  $(printf ran)  $((1+1))"
world  ran  2

줄별로 보자.

  • $name이 world가 됐다 — 매개변수 확장 통과
  • 백틱 안이 실행돼 ran이 됐다 — 명령 치환 통과
  • \\가 \ 하나로 줄었다 — 백슬래시 일부 통과
  • \n과 \t는 그대로다 — 백슬래시는 아무 문자 앞에서나 특별하지 않다
  • "a "b" c"가 a b c가 됐다 — 큰따옴표가 중간에서 끊겼다가 다시 열렸다

세 번째와 네 번째가 초보자를 가장 많이 잡는다. 큰따옴표 안에서 백슬래시는 정해진 다섯 문자 앞에서만 탈출 문자로 동작한다. 매뉴얼이 목록을 명시한다.

The backslash retains its special meaning only when followed by one of the following characters: $, `, ", \, or newline. Within double quotes, backslashes that are followed by one of these characters are removed. Backslashes preceding characters without a special meaning are left unmodified.

그래서 "\n"은 개행이 아니라 백슬래시와 n 두 글자다. 개행을 넣고 싶으면 printf의 형식 문자열에 맡기거나 8절의 ANSI-C 인용을 쓴다.

네 번째 항목인 느낌표는 조건부다. 히스토리 확장은 기본적으로 대화형 셸에서만 켜진다. 스크립트에서는 꺼져 있어 문제가 없지만, 터미널에 직접 친 명령에서는 지금도 터진다. 명령 두 줄을 대화형 bash에 먹여 확인했다.

$ echo hello there
hello there
$ echo "wow!!"
wowecho hello there          ← 큰따옴표 안의 !! 가 직전 명령으로 치환됨
$ echo 'wow!!'
wow!!                        ← 작은따옴표는 막는다

같은 두 줄을 POSIX 모드 대화형 셸에 먹이면 결과가 달라진다. 매뉴얼이 적은 예외 그대로다.

$ bash --norc -i
$ echo "wow!!"
wowecho hello there

$ bash --norc --posix -i
$ echo "wow!!"
wow!!

정리하면 큰따옴표는 「값은 넣고 싶지만 쪼개지지는 않게」를 위한 도구다. 변수·명령 치환을 안에 두고 싶을 때 쓰고, 그 외에는 작은따옴표가 안전하다.

5. 인용 없는 전개 - 여기서 대부분의 사고가 난다

여기가 이 글의 중심이다. 앞의 두 절은 「무엇이 들어가느냐」를 다뤘고, 이 절은 「몇 개로 나뉘느냐」를 다룬다. 실무 사고는 거의 전부 이쪽이다.

확인 방법은 단순하다. 인자를 받아 개수와 내용을 찍는 함수를 하나 만들고, 같은 변수를 인용해서 한 번, 안 하고 한 번 넘긴다.

count() {
  printf 'argc=%d\n' "$#"
  local i=1
  for a in "$@"; do printf '  [%d] <%s>\n' "$i" "$a"; i=$((i+1)); done
}

디렉터리에는 my report.txt, notes.txt, keep.txt 세 파일이 있다.

$ f='my report.txt'

$ count $f
argc=2
  [1] <my>
  [2] <report.txt>

$ count "$f"
argc=1
  [1] <my report.txt>

$ wc -c $f
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 total
exit=1

$ wc -c "$f"
0 my report.txt
exit=0

값 하나가 인자 두 개로 갈라졌고, 그 결과 wc는 존재하지 않는 파일 두 개를 찾았다. 종료 코드도 1이다. 이건 그나마 나은 경우다. 에러가 눈에 보이기 때문이다. 진짜 위험한 것은 조용히 성공하는 경우다.

$ pat='*.txt'

$ count $pat
argc=3
  [1] <keep.txt>
  [2] <my report.txt>
  [3] <notes.txt>

$ count "$pat"
argc=1
  [1] <*.txt>

$ empty=''
$ count $empty
argc=0
$ count "$empty"
argc=1
  [1] <>

세 가지가 한꺼번에 보인다.

  • 인용하지 않은 $pat은 파일 세 개로 부풀었다. 값은 분명히 한 개였다
  • 재미있게도 my report.txt는 쪼개지지 않고 한 필드로 남았다. 단어 분할이 글로빙보다 먼저 일어나므로, 글로빙 결과는 다시 쪼개지지 않는다
  • 인용하지 않은 빈 값은 인자 목록에서 사라진다. 인용하면 빈 문자열 인자 하나로 남는다

마지막 항목이 조건문에서 어떻게 터지는지가 유명한 함정이다.

$ empty=''
$ if [ -n $empty ]; then echo 'NON-EMPTY'; else echo 'empty'; fi
NON-EMPTY          ← 틀렸다

$ if [ -n "$empty" ]; then echo 'NON-EMPTY'; else echo 'empty'; fi
empty              ← 맞다

$ two='a b'
$ [ -n $two ]
bash: [: a: binary operator expected
exit=2
$ [ -n "$two" ]
exit=0

첫 번째는 [ -n ]이 되어 버렸다. 인자가 하나뿐인 test는 그 인자가 빈 문자열이 아니면 참이므로, -n이라는 문자열 자체가 참으로 평가됐다. 두 번째는 [ -n a b ]가 되어 문법 오류다. 값의 내용에 따라 거짓 참·문법 오류·정상이 오가는 것이다.

그리고 서론의 사고다. 인용 없는 전개가 글로빙까지 타면 되돌릴 수 없는 결과가 나온다.

### 디렉터리 상태 (별표는 파일 이름 그 자체)
*
keep1.txt
keep2.txt

### A) rm $f    (f='*')
$ rm $f
$ ls -1
    (비어 있음)

### B) rm -- "$f"    같은 값, 인용만 다름
$ rm -- "$f"
$ ls -1
    keep1.txt
    keep2.txt

A와 B의 차이는 따옴표 두 개와 --뿐이다. 결과는 전부 삭제와 한 개 삭제다. 참고로 --는 인용과 별개 장치로, 「여기부터는 옵션이 아니라 피연산자」라는 표시다. 이름이 대시로 시작하는 파일을 막아 준다.

루프 변수도 같은 규칙을 받는다. 목록을 문자열 하나에 담으면 이미 진 게임이다.

$ list='keep1.txt keep2.txt'
$ for f in $list; do printf ' <%s>' "$f"; done
 <keep1.txt> <keep2.txt>

$ arr=('quarterly report.txt' 'keep1.txt')
$ for f in "${arr[@]}"; do printf ' <%s>' "$f"; done
 <quarterly report.txt> <keep1.txt>

문자열 목록은 공백이 든 이름을 표현할 방법이 없다. 목록이 필요하면 배열을 쓴다(7절). 참고로 파일 이름에 개행이 들어가면 줄 단위로 세는 방식 자체가 무너진다. 이건 이 글의 범위를 벗어나므로 find·xargs 공백과 개행 함정에 맡긴다. 다만 셸이 보는 개수와 ls가 찍는 줄 수가 다르다는 것만 확인해 둔다.

$ ls -1 | cat -A
    *$
    keep1.txt$
    keep2.txt$
    two$
    lines.txt$

$ n=0; for f in *; do n=$((n+1)); done; echo "count=$n"
    count=4

줄은 다섯인데 파일은 넷이다. Bash 매뉴얼의 Word Splitting 절은 분할 대상을 이렇게 한정한다.

The shell scans the results of parameter expansion, command substitution, and arithmetic expansion that did not occur within double quotes for word splitting. Words that were not expanded are not split.

「큰따옴표 안에서 일어나지 않은」이라는 조건이 전부다. 큰따옴표 하나가 4단계를 통째로 건너뛰게 한다.

6. 위치 매개변수 네 형태 - 인자를 세어 본다

스크립트가 받은 인자를 다른 명령에 그대로 넘기는 일은 매일 한다. 그런데 넘기는 방법이 네 가지고, 결과가 전부 다르다. 인자 네 개를 함수에 넘겨 $#로 세어 봤다. 인자는 'a b', 'c', ''(빈 문자열), 'd*e'다.

$ pass 'a b' 'c' '' 'd*e'

quoted @:  argc=4 | <a b> <c> <> <d*e>
bare @:    argc=4 | <a> <b> <c> <d*e>
quoted *:  argc=1 | <a b c  d*e>
bare *:    argc=4 | <a> <b> <c> <d*e>

인용한 "$@"만 원본 네 개를 그대로 넘겼다. 인용 없는 $@도 개수는 4지만 내용이 어긋났다. a b가 둘로 쪼개지고 빈 인자가 사라져, 우연히 개수만 맞은 것이다. 이런 우연이 버그를 오래 숨긴다.

같은 실험을 IFS를 쉼표로 바꾸고 다시 했다.

$ IFS=,
$ pass 'a b' 'c' '' 'd*e'

quoted @:  argc=4 | <a b> <c> <> <d*e>
bare @:    argc=4 | <a b> <c> <> <d*e>
quoted *:  argc=1 | <a b,c,,d*e>
bare *:    argc=4 | <a b> <c> <> <d*e>

### 인자가 하나도 없을 때
quoted @:  argc=0 |
bare @:    argc=0 |
quoted *:  argc=1 | <>
bare *:    argc=0 |

두 가지가 드러난다. 첫째, "$*"의 이어 붙이는 글자가 IFS의 첫 글자로 바뀌었다. 둘째, 인자가 없을 때 "$@"는 인자 0개지만 "$*"는 빈 문자열 인자 1개다. 이 차이가 set -u나 인자 개수 검사에서 조용히 다른 결과를 만든다.

실제 명령에 물리면 이렇게 된다.

$ set -- 'my report.txt' 'notes.txt'

$ wc -c "$@"
0 my report.txt
0 notes.txt
0 total

$ wc -c $@
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 notes.txt
0 total

$ wc -c "$*"
wc: 'my report.txt notes.txt': No such file or directory
형태결과 필드 수빈 인자공백 든 인자쓸 자리
"$@"인자 개수 그대로보존보존인자 전달의 기본값
$@분할·글로빙 후 개수사라짐쪼개짐쓸 일 거의 없음
"$*"항상 1보존(빈 칸으로)보존로그 한 줄로 합칠 때
$*분할·글로빙 후 개수사라짐쪼개짐쓸 일 거의 없음

규칙은 짧다. 인자를 넘길 때는 "$@", 사람에게 보여 줄 한 줄을 만들 때는 "$*". 인용 없는 두 형태는 실무에서 쓸 자리가 거의 없다.

7. 배열과 인용 - 원본을 지키는 건 하나뿐

배열도 구조가 같다. 네 가지 펼치기 방식이 있고, 원본을 지키는 것은 하나다. 원소 네 개짜리 배열로 확인했다.

$ arr=('my report.txt' 'notes.txt' '' 'a*b')

"${arr[@]}"      argc=4 | <my report.txt> <notes.txt> <> <a*b>
${arr[@]}        argc=4 | <my> <report.txt> <notes.txt> <a*b>
"${arr[*]}"      argc=1 | <my report.txt notes.txt  a*b>
${arr[*]}        argc=4 | <my> <report.txt> <notes.txt> <a*b>

$ echo "${#arr[@]}"     # 원소 개수
4
$ echo "${#arr[0]}"     # 0번 원소의 글자 수
13

${#arr[@]}와 ${#arr[0]}이 전혀 다른 값을 준다는 점도 함께 봐 두면 좋다. 앞은 개수, 뒤는 길이다.

명령줄을 조립할 때 배열이 왜 필요한지는 다음 대비가 보여 준다.

$ opts=(-c)
$ files=('my report.txt' 'notes.txt')

$ wc "${opts[@]}" "${files[@]}"
0 my report.txt
0 notes.txt
0 total

$ wc ${opts[*]} ${files[*]}
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 notes.txt
0 total

그리고 배열 대신 명령줄 전체를 문자열 변수에 담는 흔한 안티패턴이 있다. 이게 왜 안 되는지가 인용의 본질을 가장 잘 보여 준다.

$ cmdline='wc -c "my report.txt"'
$ $cmdline
wc: '"my': No such file or directory
wc: 'report.txt"': No such file or directory
exit=1

따옴표를 분명히 넣었는데 왜 안 될까. 인용은 변수 값 안에서 작동하지 않기 때문이다. 셸은 소스 코드를 읽을 때 따옴표를 처리하고, 그 처리는 이미 끝났다. 변수 안에 남은 따옴표는 그냥 글자다. 그래서 wc가 받은 인자에 따옴표 문자가 그대로 붙어 있는 것이다.

기억할 한 문장
따옴표는 값이 아니라 코드에 붙는다. 변수 값에 들어 있는 따옴표는 셸에게 아무 의미도 없다. 명령줄을 동적으로 만들어야 한다면 문자열이 아니라 배열을 쓰고, 그래도 안 되면 printf %q(12절)로 셸이 직접 인용을 붙이게 한다.

참고로 bash 4.4 이전에는 set -u 아래에서 빈 배열을 "${arr[@]}"로 펼치면 오류가 났다. 지금 환경(5.2.37)에서는 다음처럼 정상이다.

$ empty=()
$ set -u
$ show "${empty[@]}"
argc=0 |
survived: exit=0

8. ANSI-C 인용 - 작은따옴표에 뚫린 구멍 하나

작은따옴표는 전부 막는다고 했다. 그 규칙에서 벗어나는 형태가 하나 있다. 앞에 달러 기호를 붙인 $'...'다. 매뉴얼의 표현으로는 「특별한 종류의 작은따옴표」이며, 변수는 여전히 확장하지 않지만 백슬래시 이스케이프는 해석한다.

$ printf '%s' 'A\tB\nC' | od -c
0000000   A   \   t   B   \   n   C
0000007

$ printf '%s' $'A\tB\nC' | od -c
0000000   A  \t   B  \n   C
0000005

같은 문자열이 7바이트와 5바이트다. $'...' 쪽은 진짜 탭과 진짜 개행으로 바뀌었다. 매뉴얼이 지원 목록을 명시한다. 여덟 진수 \nnn, 십육 진수 \xHH, 유니코드 \uHHHH와 \UHHHHHHHH, 그리고 \a \b \e \f \n \r \t \v \\ \' \" \?다. 실제로 돌려 확인했다.

$ printf '%s' $'\x41\x42' | od -c
0000000   A   B
$ printf '%s' $'\101\102' | od -c
0000000   A   B
$ printf '%s' $'é' | od -c
0000000 303 251
$ printf '%s' $'\e[0m' | od -c
0000000 033   [   0   m
$ printf '%s' $'\cG' | od -c
0000000  \a

변수는 확장하지 않는다는 점을 반드시 기억해야 한다.

$ name=world
$ printf '%s\n' $'hello $name'
hello $name

쓸 자리는 분명하다. 구분자로 탭이나 개행을 넣어야 할 때다. IFS 설정, sort -t, cut -d, join -t 같은 곳이다. 다만 $'...'는 POSIX 사양에 없다. dash에서 돌려 보면 확장이 아예 일어나지 않는다.

$ dash -c "printf '%s' \$'A\tB' | od -c"
0000000   $   A   \   t   B
0000005

달러 기호가 글자로 남고 \t도 두 글자 그대로다. 이식성이 필요하면 printf로 만들어 변수에 담는 우회를 쓴다. 결과가 같음을 바이트로 확인했다.

$ TAB=$(printf '\t')
$ NL=$(printf '\nx'); NL=${NL%x}
$ printf '%s' "A${TAB}B${NL}C" | od -c
0000000   A  \t   B  \n   C
0000005

NL을 만들 때 x를 붙였다 떼는 이유는 명령 치환이 끝의 개행을 전부 없애기 때문이다(9절). 이 두 줄이 없으면 NL은 빈 문자열이 된다.

9. 명령 치환과 백틱 - 안쪽 인용은 바깥과 무관하다

$(...) 안의 인용은 바깥 인용과 완전히 별개다. 큰따옴표 안에 있어도 안쪽은 새 문맥이다.

$ printf '%s\n' "outer $(printf '%s' 'inner literal $HOME') outer"
outer inner literal $HOME outer

$ printf '%s\n' "$(printf '[%s]' "$(printf '%s' 'deep')")"
[deep]

바깥이 큰따옴표인데 안쪽 작은따옴표가 정상 작동해 $HOME이 살아남았고, 큰따옴표를 세 겹 겹친 중첩도 그대로 통과했다. 중첩할 때 따옴표를 세지 않아도 된다는 것이 $(...)의 실용적 장점이다.

백틱은 다르다. 같은 중첩을 백틱으로 쓰면 파싱이 실패한다.

$ bash -c 'printf "%s\n" "`printf "[%s]" "`printf "%s" deep`"`"'
bash: command substitution: line 1: unexpected EOF while looking for matching `"'
bash: command substitution: line 1: unexpected EOF while looking for matching `"'
printf %s deep

백틱은 여는 기호와 닫는 기호가 같은 글자라 중첩 경계를 알 수 없다. 게다가 백틱 안에서는 백슬래시가 한 겹 더 벗겨진다. 이 차이는 실제로 값을 바꾼다.

$ printf '%s\n' "$(printf '%s' 'a\tb')"
a\tb
$ printf '%s\n' "`printf '%s' 'a\tb'`"
a\tb

$ printf '%s\n' "$(printf 'a\\b')"
a\b
$ printf '%s\n' "`printf 'a\\b'`"
a

마지막 두 줄이 갈렸다. $(...)는 a\b, 백틱은 a다. 백틱이 백슬래시 하나를 먼저 먹어 printf 'a\b'가 됐고, printf가 그것을 백스페이스로 해석했다. 정리하면 백틱을 피할 이유는 셋이다.

  • 중첩할 수 없다 — 여는 기호와 닫는 기호가 같은 글자라 경계를 알 수 없고, 위 실행처럼 파싱이 실패한다
  • 백슬래시를 한 겹 더 먹는다 — 같은 인자를 넘겼는데 결과 문자열이 달라졌다
  • 읽기 어렵다 — 백틱과 작은따옴표가 폰트에 따라 거의 구분되지 않는다

POSIX 사양은 두 형태를 모두 규정하고 있고 dash에서도 $(...)는 잘 돈다. 새 코드에서 백틱을 쓸 이유는 없다.

명령 치환 결과도 인용하지 않으면 쪼개지고 부푼다. 변수와 똑같은 규칙이다.

$ show $(printf '%s\n' 'my report.txt')
argc=2 | <my> <report.txt>
$ show "$(printf '%s\n' 'my report.txt')"
argc=1 | <my report.txt>

$ show $(printf '%s\n' '*.txt')
argc=1 | <my report.txt>
$ show "$(printf '%s\n' '*.txt')"
argc=1 | <*.txt>

### 끝의 개행은 인용 여부와 무관하게 전부 잘린다
$ printf '%s' "$(printf 'x\n\n\n')" | od -c
0000000   x
0000001

세 번째 예가 특히 위험하다. 명령이 *.txt라는 글자열을 출력했는데, 인용을 빠뜨리자 그것이 디렉터리에 있던 파일 이름으로 바뀌었다. 원본 문자열은 화면 어디에도 남지 않는다.

10. IFS - 무엇이 경계인지 정하는 변수

단어 분할의 기준은 IFS다. 기본값은 공백·탭·개행이고, 바꾸면 분할 결과가 통째로 달라진다. 그런데 큰따옴표로 감싼 값은 IFS를 아무리 바꿔도 영향을 받지 않는다. 분할 자체가 일어나지 않기 때문이다.

$ line='root:x:0:0::/root:/bin/bash'

### 기본 IFS
$ show $line
argc=1 | <root:x:0:0::/root:/bin/bash>

### IFS=:
$ IFS=:
$ show $line
argc=7 | <root> <x> <0> <0> <> </root> </bin/bash>
$ show "$line"
argc=1 | <root:x:0:0::/root:/bin/bash>

인용한 쪽은 IFS가 무엇이든 언제나 1개다. 이것이 「의심되면 큰따옴표」가 성립하는 이유다. 주변 코드가 IFS를 어떻게 바꿔 놓았든 인용한 전개는 흔들리지 않는다.

공백류 IFS와 그 외 IFS의 동작이 다르다는 점도 알아 둘 만하다.

$ gaps='a   b'
$ show $gaps
argc=2 | <a> <b>                     ← 공백 연속은 하나로 뭉친다

$ path='/usr/bin:/bin::/usr/local/bin'
$ IFS=:
$ show $path
argc=4 | </usr/bin> </bin> <> </usr/local/bin>   ← 빈 필드가 살아남는다

$ IFS=
$ show $line
argc=1 | <root:x:0:0::/root:/bin/bash>             ← IFS가 비면 분할 없음

매뉴얼의 설명 그대로다. IFS가 공백류로만 이뤄지면 연속된 공백이 하나의 경계이고 빈 필드는 인용으로만 생긴다. 공백이 아닌 문자가 IFS에 있으면 그 문자 하나하나가 경계라 연속하면 빈 필드가 생긴다.

IFS는 "$*"의 이어 붙이는 글자도 정한다.

$ set -- one two three
$ IFS=:
$ printf '%s\n' "$*"
one:two:three
$ for a in "$@"; do printf ' <%s>' "$a"; done
 <one> <two> <three>

실무에서 IFS를 쓰는 올바른 방법은 한 명령에만 걸어 주는 것이다. 전역으로 바꿔 놓으면 그 뒤의 모든 인용 없는 전개가 영향을 받는다.

$ printf '%s\n' "$line" | { IFS=: read -r user pw uid gid gecos home shell
    printf 'user=<%s> uid=<%s> home=<%s> shell=<%s>\n' "$user" "$uid" "$home" "$shell"; }
user=<root> uid=<0> home=</root> shell=</bin/bash>

### 전역으로 바꿔 놓고 잊은 경우
$ IFS=,
$ files='a,b'
$ show $files
argc=2 | <a> <b>         ← 의도한 곳이 아닐 수도 있다
$ show "$files"
argc=1 | <a,b>

IFS=: read -r ...처럼 명령 앞에 붙인 할당은 그 명령에만 적용된다. read에 -r을 붙이는 것도 인용과 같은 성격의 방어다. -r이 없으면 입력의 백슬래시가 탈출 문자로 해석돼 사라진다.

11. 인용이 필요 없는 자리, 오히려 벗겨야 하는 자리

「전부 인용하라」도 규칙이 아니다. 인용이 의미가 없는 자리가 있고, 인용하면 동작이 바뀌는 자리가 있다. 실행해서 구분했다.

$ v='my report.txt'
$ star='*.txt'

### A) 대입의 오른쪽: 분할도 글로빙도 일어나지 않는다
$ a=$v
$ b=$star
$ printf 'a=<%s>\n' "$a"
a=<my report.txt>
$ printf 'b=<%s>\n' "$b"
b=<*.txt>

대입의 오른쪽은 인용하지 않아도 안전하다. 그래도 습관으로 인용을 붙이는 편이 낫다는 의견이 많은데, 이유는 안전이 아니라 일관성이다. 예외를 하나 만들어 두면 다음 사람이 그 예외가 어디까지인지 다시 판단해야 한다.

반대로 case와 [[ ]]의 패턴 자리는 인용 여부가 의미를 바꾼다.

$ v='my report.txt'
$ p='my*'

$ case "$v" in
    $p)  echo '패턴 인용 없음 → 글로브로 해석, 매치' ;;
    *)   echo '매치 안 됨' ;;
  esac
패턴 인용 없음 → 글로브로 해석, 매치

$ case "$v" in
    "$p") echo '패턴 인용 → 글자 그대로, 매치' ;;
    *)    echo '매치 안 됨 (글자 그대로의 my* 는 이 이름이 아니다)' ;;
  esac
매치 안 됨 (글자 그대로의 my* 는 이 이름이 아니다)

[[ ]]도 같다. 왼쪽은 분할되지 않아 인용이 필요 없지만, 오른쪽은 패턴이라 인용하면 리터럴이 된다.

$ [[ $v == 'my report.txt' ]]  && echo '왼쪽 인용 없음: 문제없음'
왼쪽 인용 없음: 문제없음
$ [[ $v == $p ]]   && echo '오른쪽 인용 없음: 글로브 매치'
오른쪽 인용 없음: 글로브 매치
$ [[ $v == "$p" ]] || echo '오른쪽 인용: 매치 안 됨 (의도대로)'
오른쪽 인용: 매치 안 됨 (의도대로)

### 같은 비교를 홑대괄호로 하면
$ [ $v == 'my report.txt' ]
bash: [: too many arguments

[[ ]]는 셸 문법이라 내부에서 단어 분할을 하지 않는다. [ ]는 명령이라 인자를 받는다. 그래서 같은 코드가 한쪽은 통과하고 한쪽은 인자 개수 오류를 낸다.

글로빙 결과가 다시 분할되지 않는다는 사실도 여기서 정리해 둔다.

$ show *.txt
argc=2 | <my report.txt> <notes.txt>
$ show "$star"
argc=1 | <*.txt>
$ show $star
argc=2 | <my report.txt> <notes.txt>

코드에 직접 쓴 *.txt는 인용하지 않는 것이 정상이다. 인용하면 글로브가 아니라 글자열이 된다. 그러니 「인용을 벗기는」 정당한 경우는 두 가지뿐이다. 의도적인 단어 분할과 의도적인 글로빙이다. 그 외에는 전부 붙인다.

  • 글로브 패턴을 코드에 직접 쓸 때: for f in *.log — 인용하지 않는다
  • 글로브 패턴이 변수에 들어 있고 그것을 글로브로 쓰고 싶을 때: case·[[ ]]의 오른쪽
  • 옵션 문자열을 여러 인자로 쪼개고 싶을 때 — 다만 배열이 더 안전하다
  • 그 외 전부: 큰따옴표를 붙인다
벗겼으면 한 줄 남긴다
인용을 일부러 벗긴 자리에는 # 의도적 분할 같은 주석을 붙이는 편이 좋다. 그러지 않으면 다음 사람이 「빠뜨린 것」으로 보고 따옴표를 붙여 동작을 바꾸거나, 반대로 진짜 누락을 「의도한 것」으로 넘긴다.

12. eval과 두 겹 셸 - 인용이 한 번 더 벗겨질 때

지금까지는 셸이 문자열을 한 번 읽는 상황이었다. eval이나 원격 셸, 컨테이너 실행처럼 같은 문자열을 두 번 읽는 상황에서는 인용이 한 겹 더 벗겨진다.

$ greeting=hello
$ v='$greeting'

$ printf 'plain : %s\n' "$v"
plain : $greeting

$ eval "printf 'eval  : %s\n' \"$v\""
eval  : hello

같은 변수인데 eval을 거치자 값이 한 번 더 해석됐다. 값이 명령 구분자를 품고 있으면 그다음은 예측 가능하다.

$ name='keep.txt; echo INJECTED'

$ printf '%s\n' "$name"
keep.txt; echo INJECTED

$ eval "printf '%s\n' $name"
keep.txt
INJECTED

인용해서 출력하면 값 하나지만, eval을 태우면 세미콜론 뒤가 별개의 명령으로 실행된다. eval이 위험하다고 하는 이유가 이것이다. 안전 조건은 하나다. eval에 넘기는 문자열이 전부 자기가 만든 것일 때만 쓴다.

같은 일이 두 번째 셸에 명령을 넘길 때도 일어난다. 아래는 bash -c로 재현했지만, 원격 실행이나 컨테이너 실행도 원리가 같다. 문자열이 저쪽 셸에서 다시 파싱된다.

$ target='my report.txt'

$ bash -c "wc -c $target"
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 total

$ bash -c "wc -c \"$target\""
0 my report.txt

$ bash -c "wc -c $(printf '%q' "$target")"
0 my report.txt

어느 층이 달러 기호를 먹는지도 실행으로 확인해 두면 헷갈리지 않는다.

$ name=outer

$ bash -c "printf 'A: %s\n' $name"
A: outer          ← 바깥 셸이 확장한 뒤 문자열에 박아 넘겼다

$ bash -c 'printf "B: %s\n" $name'
B:                ← 안쪽 셸이 확장했는데 그쪽에는 name 이 없다

$ bash -c 'printf "C: %s\n" "$0"' "$name"
C: outer          ← 값을 인자로 넘겼다. 문자열 조립을 하지 않았다

C번이 정답 형태다. 값을 문자열에 박아 넣지 말고 인자로 넘기면 인용 문제가 아예 생기지 않는다.

박아 넣을 수밖에 없다면 손으로 따옴표를 겹치지 말고 셸에게 시킨다. printf %q와 bash 4.4 이상의 ${var@Q}가 그 도구다.

$ bad='my report.txt'
$ weird=$(printf 'a b\tc*d')

$ printf 'raw : %s\n' "$bad"
raw : my report.txt
$ printf 'q   : %q\n' "$bad"
q   : my\ report.txt
$ printf 'q   : %q\n' "$weird"
q   : $'a b\tc*d'

$ printf 'atQ : %s\n' "${bad@Q}"
atQ : 'my report.txt'
$ printf 'atQ : %s\n' "${weird@Q}"
atQ : $'a b\tc*d'

### 왕복: 인용을 붙였다가 다시 파싱해 본다
$ q=$(printf '%q' "$bad")
$ eval "wc -c $q"
0 my report.txt

탭이 든 값에는 셸이 알아서 ANSI-C 인용을 골랐다는 점을 눈여겨볼 만하다. 인용 방식을 사람이 고르는 것보다 정확하다. 다만 %q도 ${var@Q}도 bash 확장이라 POSIX sh에는 없다(13절).

마지막으로, 확장 결과를 눈으로 확인하고 싶으면 set -x가 가장 빠르다. 셸이 실제로 넘긴 인자를 인용까지 붙여 보여 준다.

$ set -x
$ wc -c $bad
+ wc -c my report.txt
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 total
$ wc -c "$bad"
+ wc -c 'my report.txt'
0 my report.txt

추적 줄에서 'my report.txt'처럼 bash가 따옴표를 붙여 보여 주면 인자 하나고, 그냥 my report.txt로 나오면 둘로 쪼개진 것이다. 이 한 가지만 알아도 디버깅 시간이 크게 준다.

13. POSIX sh와 bash가 갈리는 지점

#!/bin/sh로 시작하는 스크립트를 쓴다면 bash 확장을 쓸 수 없다. 어디까지가 공통이고 어디부터가 bash 전용인지 dash와 나란히 돌려 확인했다.

### printf %q

반대로 bash가 더 엄격한 지점도 있다. 리다이렉션 대상이 두 단어로 갈라질 때다.

$ v="r 1.txt"; echo hi > $v          # 그냥 bash

exit=1

기본 bash는 거부하고, POSIX 모드 bash와 dash는 받아들여 파일을 만들었다. POSIX 사양이 이 자리에 대해 적은 내용은 다음과 같다.

Pathname expansion shall not be performed on the word by a non-interactive shell; an interactive shell may perform it, but if the expansion would result in more than one word it is unspecified whether the redirection proceeds without pathname expansion being performed or the redirection fails.

즉 이 자리는 구현마다 다르게 굴어도 되는 구간이다. 그러니 결론은 하나다. 리다이렉션 대상도 인용한다. 어느 셸에서 돌든 같아진다.

결론: 따옴표는 값이 아니라 코드에 붙는다

인용을 규칙으로 만들면 문장 셋이다.

  • 작은따옴표는 전부 막는다. 다른 언어의 문법을 셸로부터 지킬 때 쓴다. 안에 작은따옴표는 못 넣고, 우회는 닫기·한 글자·열기다
  • 큰따옴표는 네 개를 통과시킨다. 달러 기호, 백틱, 특정 문자 앞의 백슬래시, 그리고 대화형에서의 느낌표. 그 대신 단어 분할과 글로빙은 작은따옴표와 똑같이 막는다
  • 인용을 안 붙인 자리가 사고 지점이다. 값 하나가 여러 개가 되고, 없던 파일 이름이 생기고, 빈 값은 아예 사라진다

실행으로 확인한 것을 다시 정리하면 이렇다. 값에 공백이 있으면 인자가 둘로 갈라졌다. 값에 별표가 있으면 파일 목록으로 부풀어 rm 한 줄이 디렉터리를 비웠다. 빈 값은 인자 목록에서 사라져 [ -n ]이 참이 됐다. "$@"만 인자 넷을 그대로 넘겼고 나머지 셋은 전부 달랐다. IFS를 바꾸면 인용 없는 전개만 갈라졌고 인용한 쪽은 언제나 하나였다. 명령줄을 문자열에 담자 따옴표가 글자가 되어 wc에게 그대로 넘어갔다.

마지막이 이 글의 요점이다. 따옴표는 값에 붙는 것이 아니라 코드에 붙는다. 셸은 소스를 읽을 때 인용을 처리하고, 그 뒤로는 값 안의 따옴표를 다시 보지 않는다. 그래서 명령줄을 문자열로 조립하는 방식은 원리적으로 고칠 수 없고, 배열이나 "$@"로 구조를 유지한 채 넘기는 것이 유일한 해법이다.

기본값을 하나 정해 두자. 의심되면 "$var". 벗겨야 할 이유가 분명할 때만 벗기고, 벗긴 자리에는 이유를 한 줄 남긴다. 이 규칙 하나로 대부분의 셸 사고가 사라진다.

# 셸 인용 규칙 — 붙여 쓰는 판단 체크리스트

> 출처: braindetox.kr — 셸 인용부호 규칙
> 근거: GNU Bash Reference Manual (Single Quotes / Double Quotes / ANSI-C Quoting / Word Splitting), POSIX Issue 8 (Shell Command Language 2.2.2 · 2.2.3 · 2.6.5 · 2.7)
> 이 파일을 그대로 AI에 붙여 「우리 스크립트를 이 기준으로 고쳐줘」라고 쓰면 됩니다.

## 0. 기본값 한 줄

**의심되면 `"$var"`.** 벗기는 것은 예외이고, 예외에는 이유를 주석으로 남긴다.

## 1. 어느 인용이 무엇을 막나

| 형식 | 달러 확장 | 백틱 | 백슬래시 | 느낌표(히스토리) | 단어 분할 | 글로빙 |
|---|---|---|---|---|---|---|
| 인용 없음 | 통과 | 통과 | 통과 | 통과 | **일어남** | **일어남** |
| `'...'` | 차단 | 차단 | 차단 | 차단 | 차단 | 차단 |
| `"..."` | **통과** | **통과** | **일부 통과** | **대화형에서 통과** | 차단 | 차단 |
| ANSI-C 인용 | 차단 | 차단 | **해석함** | 차단 | 차단 | 차단 |
| `\x` | 차단 | 차단 | 차단 | 차단 | 차단 | 차단 |

- [ ] 작은따옴표와 큰따옴표는 **단어 분할·글로빙을 똑같이 막는다**는 것을 알고 있다
- [ ] 큰따옴표 안의 백슬래시는 달러 기호·백틱·큰따옴표·백슬래시·개행 **다섯 앞에서만** 특별하다는 것을 알고 있다
- [ ] `"\n"` 은 개행이 아니라 두 글자라는 것을 알고 있다

## 2. 상황 → 써야 할 인용

| 상황 | 써야 할 형태 | 이유 |
|---|---|---|
| 변수를 명령 인자로 | `"$var"` | 단어 분할과 글로빙을 둘 다 막는다 |
| 스크립트 인자 전달 | `"$@"` | 개수·빈 인자·공백을 전부 보존 |
| 인자를 로그 한 줄로 | `"$*"` | IFS 첫 글자로 이어 붙인 문자열 하나 |
| 목록 다루기 | `"${arr[@]}"` | 문자열 목록은 공백 든 원소를 못 담는다 |
| 리다이렉션 대상 | `> "$var"` | 셸 구현마다 다르게 굴 수 있는 자리 |
| 테스트·비교 | `[ -n "$var" ]` | 빈 값이 인자 목록에서 사라지는 것을 막는다 |
| awk·sed·정규식 프로그램 | `'...'` | 달러 기호를 셸에서 보호 |
| find 패턴 | `-name '*.log'` | 인용 안 하면 셸이 먼저 먹는다 |
| 탭·개행을 값으로 | `TAB=$(printf '\t')` | 큰따옴표 안 백슬래시는 해석되지 않는다 |
| 코드에 직접 쓴 글로브 | `*.log` (인용 없음) | 인용하면 글자열이 된다 |
| case·`[[ ]]` 패턴 변수 | `$p` (인용 없음) | 인용하면 리터럴 비교가 된다 |
| 다른 셸에 명령 전달 | 값을 **인자로** | 문자열 조립 자체를 피한다 |
| 그래도 조립해야 하면 | `printf %q` / `${var@Q}` | 인용을 사람이 아니라 셸이 붙인다 |

## 3. 자주 터지는 패턴과 교정

```bash
# ── 1) 값에 공백이 있으면 인자가 쪼개진다
wc -c $f                      # ✗ my report.txt → 인자 2개
wc -c -- "$f"                 # ✓ 1개

# ── 2) 값에 글로브 문자가 있으면 파일 이름으로 부푼다
rm $f                         # ✗ f='*' 이면 디렉터리가 비어버린다
rm -f -- "$f"                 # ✓ 그 파일 하나만

# ── 3) 빈 값은 인자 목록에서 사라진다
[ -n $DEBUG ]                 # ✗ [ -n ] 이 되어 항상 참
[ -n "${DEBUG:-}" ]           # ✓

# ── 4) 목록을 문자열에 담지 않는다
list='a.txt b.txt'; for f in $list      # ✗ 공백 든 이름 표현 불가
files=('a b.txt' 'c.txt'); for f in "${files[@]}"   # ✓

# ── 5) ls 를 루프에 물리지 않는다
for f in $(ls "$src")         # ✗ 분할·글로빙 두 번 탄다
for f in "$src"/*; do [ -e "$f" ] || continue       # ✓

# ── 6) 명령줄을 문자열에 담지 않는다 (인용이 글자가 된다)
cmd='wc -c "a b.txt"'; $cmd   # ✗ wc 가 따옴표 문자를 받는다
cmd=(wc -c 'a b.txt'); "${cmd[@]}"                  # ✓

# ── 7) 인자 전달은 항상 이 형태
run() { real_cmd "$@"; }      # ✓  ($@ · "$*" · $* 는 결과가 다르다)

# ── 8) 리다이렉션 대상도 인용한다
echo hi > $out                # ✗ bash 는 ambiguous redirect, sh 는 통과
echo hi > "$out"              # ✓ 어느 셸에서도 같다

# ── 9) 두 번째 셸에 넘길 때는 값을 인자로
ssh host "wc -c $file"        # ✗ 저쪽에서 다시 파싱된다
ssh host 'wc -c "$0"' "$file" # ✓ 조립하지 않는다
```

## 4. 인용을 벗겨도 되는 유일한 두 경우

- [ ] **의도적 단어 분할** — 옵션 문자열 쪼개기 (배열이 더 안전하다)
- [ ] **의도적 글로빙** — `case` · `[[ ]]` 의 패턴 자리, 코드에 직접 쓴 글로브
- [ ] 위 둘 중 하나가 아니면 **무조건 인용한다**
- [ ] 벗긴 자리에는 `# 의도적 분할` 같은 주석을 남겼다

## 5. 점검 명령 — 봐야 할 줄을 찍어 준다

```bash
F=script.sh

# 명령 뒤에 오는 인용 없는 전개
grep -nE '(^|[[:space:]|(&;])(cp|mv|rm|wc|cat|cd|mkdir|source)[[:space:]]+[^|;&]*\$[A-Za-z_{]' "$F"

# 대괄호 테스트 안의 인용 없는 전개
grep -nE '\[[^]]*\$[A-Za-z_{][^]"]*\]' "$F"

# 명령 출력이나 변수를 for 로 도는 형태
grep -nE 'for[[:space:]]+[A-Za-z_]+[[:space:]]+in[[:space:]]+(\$\(|\$[A-Za-z_{])' "$F"

# 인용하지 않은 리다이렉션 대상
grep -nE '(^|[[:space:]])[12]?>>?[[:space:]]*\$[A-Za-z_{]' "$F"

# 실제 전개 결과를 눈으로 확인
bash -n "$F"                      # 문법만 (인용 누락은 잡히지 않는다)
bash -x "$F" "인자 하나" out       # 추적 줄의 따옴표 유무로 판단
```

**추적 줄 읽는 법**: bash 가 `'my report.txt'` 처럼 **따옴표를 붙여 보여 주면 인자 하나**,
그냥 `my report.txt` 로 나오면 **둘로 쪼개진 것**이다.

## 6. 재현용 시험 데이터 — 빈 임시 디렉터리에서만

```bash
d=$(mktemp -d) && cd "$d" || exit 1
: > 'my report.txt'          # 공백
: > 'keep.txt'
printf 'junk\n' > '*'        # 이름이 글로브 문자 그 자체
touch -- "-dash.txt"         # 대시로 시작
./your_script.sh "$d" out    # 여기서 깨지면 인용 문제다
```

★ 위 시험은 **반드시 새로 만든 빈 임시 디렉터리 안에서만** 돌리십시오. 홈 디렉터리나 실제 서버 경로에서는 실행하지 마십시오.

## 7. POSIX sh 로 옮길 때

| 기능 | POSIX sh | bash | 이식 대안 |
|---|---|---|---|
| 작은·큰따옴표 규칙 | 동일 | 동일 | 그대로 |
| 단어 분할·글로빙·IFS | 동일 | 동일 | 그대로 |
| `"$@"` / `"$*"` | 동일 | 동일 | 그대로 |
| ANSI-C 인용 | 없음 | 있음 | `TAB=$(printf '\t')` |
| 배열 | 없음 | 있음 | `set --` 로 위치 매개변수 |
| `[[ ]]` | 없음 | 있음 | `[ ]` + 인용 철저히 |
| `printf %q` | 없음 | 있음 | 값을 인자로 넘겨 조립 회피 |
| 두 단어 리다이렉션 대상 | 허용 | 거부 | 항상 `> "$v"` |

## 8. 마무리 한 문장

**따옴표는 값이 아니라 코드에 붙는다.** 변수 값 안의 따옴표는 셸에게 아무 의미도 없다.
그래서 명령줄을 문자열로 조립하는 방식은 원리적으로 고칠 수 없고, 배열이나 `"$@"` 로 구조를 유지한 채 넘기는 것만이 답이다.
