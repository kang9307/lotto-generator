계기 — 그래프·벡터·전문 검색을 한 파일에 담는 임베디드 데이터베이스

로컬 지식 도구나 Graph RAG 파이프라인, AI 에이전트의 영속 메모리를 구축하는 개발 환경에서 데이터 저장소 파편화는 지속적인 문제로 지적되어 왔다. 문맥 사이의 의미적 유사도를 판별하기 위한 벡터 데이터베이스, 엔티티 사이의 다중 홉 관계망을 추적하기 위한 그래프 데이터베이스, 특정 키워드나 식별자를 정확히 추출하기 위한 전문 검색(Full-Text Search) 엔진이 각각 별도의 시스템으로 요구되었기 때문이다. 개발자는 로컬 환경에서 단 하나의 기능을 구현하기 위해서도 세 종류의 데몬을 띄우거나, 서로 다른 저장소 라이브러리를 바인딩한 뒤 애플리케이션 계층에서 분산 트랜잭션을 흉내 내야 했다.

2026년 9월 오픈소스로 공개된 LatticeDB는 이러한 저장소 파편화 문제를 정면으로 다루는 임베디드 데이터베이스다. 저장소의 공식 설명에 따르면 LatticeDB는 단일 로컬 파일 안에서 연결된 관계 데이터, 의미적 벡터 데이터, 텍스트 키워드 데이터를 모두 수용하고 단일 질의 계층을 통해 조회할 수 있도록 설계되었다. 별도의 서버 프로세스나 외부 종속성 없이 애플리케이션에 임베드되어 동작하며, 단일 파일 단위로 데이터를 백업하고 이동할 수 있는 로컬 퍼스트(local-first) 지향 구조를 표방한다.

단일 저장소에 세 가지 검색 모달리티를 통합하려는 시도는 클라우드 분산 환경에서도 활발히 진행되어 왔으나, LatticeDB는 서버 아키텍처가 아닌 SQLite와 유사한 임베디드 단일 파일 엔진을 선택했다는 점에서 기술적 위치가 구분된다. 임베디드 환경은 IPC(프로세스 간 통신)나 TCP/IP 네트워크 스택의 지연시간을 원천적으로 배제할 수 있는 장점을 가지지만, 운영체제 프로세스 간의 파일 잠금 메커니즘과 단일 프로세스 메모리 제약이라는 엄격한 경계 조건을 동반한다. 본 글에서는 LatticeDB가 채택한 다중 엔진 결합 설계의 원리와 Cypher 질의 확장 방식, 공식 README가 제시하는 벤치마크의 측정 조건, 그리고 단일 작성자 모델이 가지는 명확한 아키텍처적 한계를 사실에 기반해 검토한다.

엔지니어링 관점에서 로컬 단일 파일 데이터베이스의 가치는 운영 단순성에 있다. 클라우드 관리형 데이터베이스나 마이크로서비스 형태의 저장소 군집은 유지보수 인력과 지속적인 네트워크 연결을 전제한다. 반면 단일 파일 데이터베이스는 파일 시스템의 표준 경로에 데이터베이스 파일 하나를 생성하는 것만으로 초기화가 완료된다. 데이터의 백업은 해당 파일을 복사하는 작업으로 치환되며, 테스트 환경 구성 역시 임시 디렉토리에 빈 파일을 할당하는 방식으로 단순화된다. LatticeDB는 이러한 SQLite식 단순성을 그래프와 벡터, 전문 검색이라는 현대적 RAG 요구사항과 결합하고자 시도한다.

분리된 저장소 아키텍처가 유발하던 파편화와 동기화 비용

AI 애플리케이션과 Graph RAG 워크로드에서 여러 검색 엔진을 분리 운영할 때 발생하는 구조적 문제는 데이터 정합성과 트랜잭션 경계의 붕괴에서 출발한다. 전형적인 로컬 RAG 시스템의 작동 방식을 살펴보면 아래와 같은 다단계 동기화 오버헤드가 발생한다.

  • 문서 조각(Chunk)을 생성할 때 텍스트 임베딩 벡터는 전용 벡터 인덱스에 저장된다.
  • 문서와 작성자, 상위 문서, 인용 관계는 관계형 DB나 로컬 그래프 저장소에 노드와 에지로 기록된다.
  • 특정 고유명사나 코드 식별자 조회를 위해 역색인 기반 전문 검색 인덱스가 별도 파일로 관리된다.
  • 세 저장소가 서로 다른 스토리지 엔진과 파일 포맷을 사용하므로 원자적 쓰기(ACID)가 보장되지 않는다.
  • 데이터 수정이나 삭제 시 세 인덱스 중 하나라도 실패하면 참조 무결성이 깨진 고아 데이터가 남는다.
  • 저장소 간 스키마 변경 시 각 엔진의 마이그레이션 스크립트를 개별적으로 실행하고 검증해야 한다.
  • 단일 사용자 데스크톱 소프트웨어 배포 시 각 엔진에 종속된 다수의 네이티브 바이너리를 패키징해야 한다.

이러한 아키텍처는 개발자에게 무거운 조정 비용을 부과한다. 질의 시점에도 벡터 검색으로 상위 K개의 청크 ID를 추출한 뒤, 그래프 저장소를 열어 해당 ID의 부모 노드를 조회하고, 다시 텍스트 필터 엔진을 거쳐 결과를 걸러내는 다단계 파이프라인 코드를 작성해야 한다. 각 단계마다 메모리 복사와 직렬화·역직렬화 비용이 누적되며, 저장소 간 불일치를 해결하기 위한 재색인 작업이 주기적으로 요구된다. 특히 애플리케이션이 비정상 종료되는 상황에서 각 저장소 엔진의 충돌 복구(Crash Recovery) 루틴이 각기 다르게 동작하면, 시스템 재시작 시 어떤 저장소가 최신 상태인지 판별하기 어렵다.

메모리 점유율 측면에서도 분리 운영은 비효율적이다. 각 검색 엔진은 독립적인 메모리 버퍼 풀과 캐시 계층을 유지한다. 운영체제 입장에서는 세 개의 독립된 프로세스나 런타임이 동일한 물리 메모리를 두고 경쟁하는 상황이 발생하며, 이는 메모리가 제한적인 클라이언트 디바이스나 엣지 컴퓨팅 환경에서 심각한 스왑(Swap) 지연을 초래한다. 각 엔진이 자체적인 사전 할당 풀을 고집할 경우 실제 데이터 크기보다 훨씬 큰 메모리가 상시 점유된다.

LatticeDB는 이러한 계층 파편화를 제거하기 위해 노드와 에지, 벡터 임베딩, BM25 역색인을 동일한 저장 파일 구조 안에 배치했다. 단일 파일 내부에서 트랜잭션 로그(WAL)를 공유함으로써 그래프 구조의 변경과 벡터 갱신, 텍스트 역색인 추가가 단일 커밋 단위로 처리된다. 이는 분산 저장소 간 동기화 로직을 애플리케이션에서 완전히 제거할 수 있음을 의미하며, 단일 버퍼 풀이 전체 데이터 모달리티의 캐싱을 통합 관리할 수 있게 만든다.

단일 파일 안의 세 가지 검색 모델과 Cypher 확장 문법

LatticeDB는 그래프 탐색 질의 표준으로 자리 잡은 Cypher 언어를 기반으로 삼고, 여기에 벡터 유사도 검색과 전문 검색을 위한 고유 연산자를 결합하는 방식을 택했다. 서로 다른 검색 패러다임이 별도의 API 호출로 쪼개지지 않고 단일 질의문 안에서 표현된다.

// 유사 청크 탐색 후 문서 및 작성자 노드로 다중 홉 탐색, 텍스트 키워드 필터링 결합
                    MATCH (chunk:Chunk)-[:PART_OF]->(doc:Document)-[:AUTHORED_BY]->(author:Person)
                    WHERE chunk.embedding <=> $query_vector < 0.3 AND doc.content @@ "neural networks"
                    RETURN doc.title, chunk.text, author.name
                    ORDER BY chunk.embedding <=> $query_vector
                    LIMIT 10

위 질의문에서 확인되는 핵심 설계 요소는 두 가지 확장 연산자다. <=> 연산자는 벡터 사이의 코사인 거리(cosine distance)를 계산하는 연산자로, HNSW 인덱스를 활용한 근사 최근접 이웃 탐색 조건을 WHERE 절 및 ORDER BY 절에 직접 주입한다. @@ 연산자는 BM25 알고리즘 기반의 전문 검색 연산자로, 대상 속성에 구축된 역색인에서 형태소 토큰화 및 어간 추출을 거친 텍스트 매칭 점수를 평가한다. 질의 엔진은 단일 실행 계획 안에서 벡터 조건으로 후보 노드를 우선 선별하거나, 역색인 조건을 먼저 평가한 후 그래프 관계를 순회하는 방식으로 하이브리드 필터링을 단일 패스에서 처리한다.

파이썬 바인딩 환경에서 데이터베이스를 생성하고 그래프와 인덱스를 구축하는 표준 워크플로는 단일 컨텍스트 매니저를 통해 완결된다. 아래는 공식 README에 수록된 파이썬 사용 예시 코드의 기본 골격이다.

from latticedb import Database
                    from latticedb.embedding import hash_embed
                    
                    with Database("knowledge.db", create=True, enable_vectors=True, vector_dimensions=128) as db:
                        db.create_node_fts_index("Chunk", "text")
                        with db.write() as txn:
                            alice = txn.create_node(labels=["Person"], properties={"name": "Alice", "field": "ML"})
                            doc = txn.create_node(labels=["Document"], properties={"title": "Attention Is All You Need"})
                            chunk = txn.create_node(labels=["Chunk"], properties={"text": "The transformer architecture uses self-attention..."})
                            txn.set_vector(chunk.id, "embedding", hash_embed("transformer", dimensions=128))
                            txn.create_edge(chunk.id, doc.id, "PART_OF")
                            txn.create_edge(doc.id, alice.id, "AUTHORED_BY")
                            txn.commit()
                    
                        results = db.query("""
                            MATCH (chunk:Chunk)-[:PART_OF]->(doc:Document)-[:AUTHORED_BY]->(author:Person)
                            WHERE chunk.embedding <=> $query < 0.5
                            RETURN doc.title, chunk.text, author.name
                            ORDER BY chunk.embedding <=> $query LIMIT 5
                        """, parameters={"query": hash_embed("attention", dimensions=128)})

코드에서 사용된 hash_embed 헬퍼 함수는 외부 서드파티 임베딩 서비스 없이 테스트를 구동하기 위한 결정론적 해시 플레이스홀더다. 공식 문서에서는 이 함수가 실제 의미적 유사도를 생성하지 않으므로 실제 운영 환경에서는 OpenAI나 Ollama 같은 정규 임베딩 모델을 HTTP 클라이언트로 연동해야 한다고 명시하고 있다. 클라이언트 개발자는 create_node_fts_index를 통해 원하는 노드 레이블과 속성에 대해 즉시 역색인을 활성화할 수 있으며, 이 작업 역시 단일 트랜잭션 수명주기 안에서 안전하게 지속된다.

언어 바인딩의 제공 범위 또한 다채롭다. C 네이티브 헤더(lattice.h)를 기초로 Python(pip wheel 배포), TypeScript/Node.js(npm 패키지 배포), Go(cgo 워크플로), Java(JDK 21+ JNI 브리지) 공식 바인딩이 제공된다. Electron과 같은 데스크톱 웹 기술 환경에서는 메인 프로세스에서 바인딩을 로드하여 네이티브 라이브러리를 직접 호출하는 구조를 권장한다.

벤치마크 측정 조건과 공개된 수치의 해석 경계

LatticeDB README는 성능 검증을 위해 다양한 워크로드에 대한 벤치마크 수치를 제시하고 있다. 기술 블로그와 오픈소스 생태계에서 벤치마크 수치는 측정 조건과 하드웨어 환경에 종속되므로, 제공된 조건을 분리하여 엄밀하게 읽어야 한다. 모든 측정은 Apple M1 프로세서 환경에서 단일 스레드, 자동 확장 버퍼 풀 조건으로 수행되었다.

위 벤치마크 표를 해석할 때 주의할 기술적 경계는 세 가지다. 첫째, 그래프 탐색 비교에서 SQLite와의 비교는 동일한 단일 머신 테스트 하네스에서 직접 측정되었으나, 표에 언급되는 Kuzu나 Neo4j의 비교 수치는 통제되지 않은 제3자 블로그 포스트의 결과를 인용한 자릿수 참조값에 불과하다. 각 시스템이 동작한 하드웨어 스펙과 캐시 설정, JVM 웜업 상태가 통일되지 않았으므로 동등한 벤치마크로 간주할 수 없다.

둘째, Weaviate나 Qdrant 같은 분산 벡터 데이터베이스와의 지연시간 비교는 네트워크 홉(network hop)과 소켓 오버헤드가 배제된 임베디드 라이브러리 특유의 구조적 이점이 반영된 수치다. 클라이언트-서버 시스템은 최소 0.5~2ms의 네트워크 RTT를 기본 부하로 안고 가지만 수평 확장이 가능하다. 반면 LatticeDB의 0.83ms는 순수한 동일 메모리 공간 내 함수 호출 비용을 측정한 것이다.

셋째, B+Tree 포인트 룩업의 0.13 마이크로초 지연시간은 인접 캐시와 버퍼 풀이 예열된 상태에서의 캐시 히트 워크로드 측정값이다. 디스크 I/O가 실제로 발생하는 콜드 스타트 상황이나 버퍼 풀 용량을 초과하는 대규모 무작위 읽기 상황에서는 운영체제 페이지 캐시와 디스크 컨트롤러 성능에 따라 지연시간이 달라진다. 따라서 사용자는 이 수치를 단일 프로세스 캐시 최적화의 상한선으로 이해해야 한다.

스토리지 엔진 구조 — B+Tree, HNSW 패킹, WAL과 이벤트 로그

LatticeDB가 다중 모델을 단일 파일에 결합하면서 성능을 확보한 기술적 배경은 Zig 언어로 작성된 스토리지 엔진 내부 설계에 있다. 외부 C/C++ 런타임 종속성 없이 저수준 메모리 관리와 디스크 레이아웃을 직접 제어한다.

  • HNSW 연결 페이지 패킹: 그래프 기반 벡터 인덱스인 HNSW는 메모리 점유율이 높은 단점이 있다. LatticeDB는 휴리스틱 이웃 선택(Algorithm 4) 알고리즘을 적용하고 연결 리스트를 페이지 단위로 패킹하여 원문 기준 메모리 사용량을 약 4.5배 절감했다.
  • 사전 정규화 내적 연산: 128차원 벡터 검색에서 코사인 거리 계산의 부동소수점 연산 부하를 줄이기 위해 벡터 삽입 시 사전 정규화를 거쳐 빠른 내적(dot product) 연산으로 대체한다.
  • 비트셋 방문 추적 그래프 탐색: Cypher 탐색 시 인접 리스트 캐시와 비트셋(bitset) 방문 추적 구조를 결합한 너비 우선 탐색(BFS)을 수행하여, SQLite의 관계형 재귀 CTE가 유발하는 UNION 중복 제거 연산 부하를 회피한다.
  • 통합 트랜잭션 WAL과 이벤트 스트림: 쓰기 작업은 단일 WAL(Write-Ahead Log)에 기록된다. 데이터 변경과 동시에 영속 명명 스트림(durable named streams) 및 그래프 체인지피드(changefeed)를 동일한 트랜잭션 경로로 발행하여, 데이터 변경과 이벤트 발행의 불일치를 차단한다.
  • 물리적 공간 회수와 무중단 백업: 파일 단편화를 방지하기 위해 온라인 프리리스트(freelist) 재사용 메커니즘을 갖추고 있으며, lattice compact 명령으로 파일 후미 공간을 안전하게 회수한다. 또한 데이터베이스 파일을 닫지 않고도 스냅숏을 생성하는 lattice backup 핫 백업 기능을 지원한다.
  • 인메모리 휘발성 데이터베이스 지원: 디스크 파일을 전혀 생성하지 않고 순수 메모리 공간에서만 실행되는 :memory: 모드를 지원하여 고속 임시 테스트와 격리된 단위 검증을 지원한다.
  • 바이트 스트림 직렬화 및 클라우드 동기화: 로컬 데이터베이스 전체 상태를 바이트 배열로 직렬화하거나 바이트로부터 복원하는 기능을 제공하여, S3 등 오브젝트 스토리지와의 스냅숏 교환을 간소화한다.

이러한 내부 구조는 관계형 RDBMS에 가상 테이블이나 확장 플러그인(Extension) 형태로 벡터와 그래프를 얹는 방식과 차별화된다. 스토리지 엔진의 최소 단위에서부터 노드 ID와 벡터 ID, 전문 검색 문서 ID가 일체화된 B+Tree 키 공간에 매핑되므로 다중 엔진 간 상호 참조 오버헤드가 최소화된다. 특히 버퍼 풀 관리자가 데이터 페이지와 벡터 인덱스 페이지, FTS 전치 페이지를 동일한 캐시 정책(LRU/Clock) 하에서 공평하게 조율할 수 있어 메모리 누수를 원천 차단한다.

트랜잭션 복구 측면에서도 WAL 기반의 단일 로깅 경로는 강력한 안정성을 제공한다. 프로세스가 예기치 않게 종료되더라도, 재시작 시점에 단일 로그 파일의 체크포인트를 검사하여 커밋되지 않은 그래프 변경, 벡터 삽입, 텍스트 토큰 추가를 일괄 롤백한다. 이는 다중 저장소를 이어 붙였을 때 필연적으로 마주치는 분산 불일치 복구 문제를 완벽히 해결하는 아키텍처적 기반이다.

도입 판단 기준 — 적합한 워크로드와 다른 도구를 골라야 하는 조건

LatticeDB 공식 문서는 프로젝트의 장점뿐만 아니라, 시스템을 도입해서는 안 되는 상황(When to Use Something Else)을 문서에 명시하고 있다. 기술 선택의 관점에서 LatticeDB가 가장 빛을 발하는 환경과 대안 저장소를 선택해야 하는 경계는 아래와 같다.

  • 로컬 에이전트 메모리 및 개인 지식 베이스: 단일 사용자 환경에서 데스크톱 앱(Electron, Tauri 등)에 내장되어 메모, 문서 인용 관계, 텍스트 검색, 의미 유사도 검색을 동시에 처리해야 할 때 최적의 성능을 제공한다. 서버 관리 부담이 없으며 단일 파일 복사만으로 마이그레이션이 완료된다.
  • 단일 머신 파이프라인 프로토타이핑: 클라우드 벡터 DB나 Neo4j 서버를 띄우기 번거로운 개발 환경이나 CI/CD 테스트 환경에서 단일 파일 기반으로 동일한 Cypher 로직을 신속히 검증할 수 있다.
  • 다중 프로세스 동시 쓰기 환경에서의 부적합: LatticeDB는 단일 프로세스가 파일을 점유하는 단일 작성자(single-writer) 모델이다. 여러 백엔드 인스턴스나 마이크로서비스가 네트워크를 통해 동시에 쓰기를 수행해야 한다면 Neo4j, PostgreSQL, Qdrant 등 클라이언트-서버 기반 데이터베이스를 선택해야 한다.
  • 정형 테이블 위주의 데이터: 매출 전표, 사용자 계정 목록, 시계열 로그 등 데이터의 본질이 행과 열의 2차원 관계인 경우, 그래프 모델링은 불필요한 인덱스 오버헤드를 유발한다. 이 경우 SQLite나 PostgreSQL 같은 표준 관계형 데이터베이스가 단순하고 효율적이다.
  • 수십억 단위 분산 클러스터링: 샤딩이나 읽기 복제본 노드 분산, 멀티 리전 동기화가 필요한 대규모 워크로드는 LatticeDB의 설계 범위를 벗어난다. 단일 머신 디스크 용량을 초과하는 데이터는 분산 그래프/벡터 엔진(Dgraph, Milvus, AWS Neptune 등)을 고려해야 한다.
  • 완전한 Cypher 질의 지원 필요성: OPTIONAL MATCH, 복잡한 패턴 컴포지션, 서브쿼리 프로시저(CALL)에 의존하는 기존 엔터프라이즈 그래프 질의는 LatticeDB에서 직접 실행되지 않을 수 있다.
  • 풍부한 GUI 관리 및 모니터링 생태계 요구: Neo4j Bloom이나 프로덕션 급 관리자 웹 콘솔, 성숙한 APM 모니터링 도구가 필수적인 환경이라면 신생 프로젝트인 LatticeDB는 운영 도구 생태계 측면에서 불리하다.
  • 초경량 임베디드 풋프린트 요구: 순수 관계형 쿼리만 필요하고 수 메가바이트의 바이너리 용량조차 극도로 제한되는 초경량 마이크로컨트롤러 환경에서는 수십 년간 정제된 순수 SQLite 엔진이 여전히 우위에 있다.

결국 LatticeDB는 모든 저장소 요구를 대체하려는 범용 데이터베이스가 아니라, 단일 머신 로컬 환경에서 관계망과 의미 검색을 결합하려는 AI 애플리케이션의 운영 부담을 제거하기 위해 튜닝된 특수 목적 엔진으로 규정할 수 있다. 분산 클러스터의 기능을 포기한 대신 단일 파일의 간결성과 임베디드 수준의 저지연을 달성한 것이 이 아키텍처의 본질적인 거래(trade-off)다.

도입을 검토하는 팀은 먼저 자사 애플리케이션의 아키텍처 토폴로지를 점검해야 한다. 만약 서비스가 단일 호스트 내에서 독립적으로 실행되는 데스크톱 소프트웨어이거나, 사용자 디바이스에 데이터 주권을 부여하는 로컬 퍼스트 소프트웨어라면 LatticeDB는 인프라 관리 비용을 획기적으로 낮출 수 있는 강력한 후보가 된다. 반대로 클라우드 컨테이너 환경에서 수평 확장을 전제로 설계된 웹 백엔드라면 단일 작성자 파일 잠금 제약이 치명적인 병목으로 작용할 수 있음을 인지해야 한다.

확인하지 못한 것

  • Apple M1 이외의 아키텍처(x86_64 리눅스 서버 환경 등)에서의 공식 벤치마크 결과 및 분산 메모리 환경 성능.
  • 초대용량 데이터셋(1억 개 이상의 벡터 또는 수천만 개의 노드) 환경에서 버퍼 풀 자동 확장의 메모리 한계 동작.
  • OPTIONAL MATCH 및 CALL 프로시저의 향후 구체적인 로드맵 및 지원 일정.
  • Windows 환경에서의 Zig 네이티브 빌드 안정성 및 JNI/cgo 바인딩의 프로덕션 수준 안정성 보고.
  • 대규모 동시 읽기 스레드 상황에서의 버퍼 풀 경합 및 락 프로파일링 데이터.
