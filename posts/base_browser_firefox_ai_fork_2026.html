1. Firefox의 AI 통합과 '완전 삭제'를 향한 문제의식

현대 웹 브라우저 엔진은 수천만 줄에 달하는 거대한 코드베이스 위에서 작동한다. 일반적으로 소프트웨어 생태계가 성숙해지면 상위 벤더는 수익화 모델과 새로운 기술 유행을 흡수하며 브라우저 내부에 복잡한 부가 계층을 추가하기 마련이다. 오픈소스 커뮤니티의 오랜 보루로 여겨져 왔던 Firefox 역시 예외가 아니었으며, 최근 몇 년 동안 기기 내부 및 원격 연동을 아우르는 인공지능 보조 도구와 자동화 인터페이스를 지속적으로 엔진 심층부에 통합해 왔다.

이러한 변화에 대해 보안 연구원이자 독립 개발자인 Sarah Jamie Lewis는 2026년 9월 19일 공개한 글 「Thoughts on the Future of Web Browsers」에서 근본적인 문제의식을 제기했다. 원문은 지난 7월 저자가 마스토돈 스레드에서 작성했던 글을 인용하며, 독립적이고 군더더기 없는 웹의 미래가 남아 있다면 지금이야말로 모든 Firefox 포크 프로젝트들이 Mozilla로부터 격리된 하드포크를 유지하기 위해 협력해야 할 때라고 지적한다. 원문은 소규모 프로젝트 하나가 홀로 감당하기에는 지나치게 거대한 작업이지만, Mozilla와 같은 조직의 지도 아래 방치하기에는 너무나 중대한 과제라고 규정한다.

원문에서 저자는 Mozilla와 Firefox가 지난 10년 동안 자신들이 나아가고자 하는 방향을 일관되게 추진해 왔다고 진단한다. 원문은 "Mozilla and, by extension, Firefox have laid out the direction they want to go - and have consistently moved in that direction over the last decade. There is no redemption arc there, they are not going to turn the ship around - and every week and month that goes by, Firefox gains more slop and drifts further from the visions that founded it."라고 밝힌다. 즉 상위 프로젝트가 스스로 방향을 되돌릴 가능성이 없다고 보고, 코드베이스 자체를 분리해야 한다는 결론에 도달한 것이다.

이 글의 해석으로는, 설정 메뉴에서 체크박스를 해제하는 형태의 수동적 저항은 브라우저 코어가 재편되는 속도를 따라갈 수 없다는 위기감이 작용한 것으로 풀이된다. 상위 프로젝트가 브라우저 창 전체를 인공지능 에이전트와의 상호작용 창구로 재정의하려는 시점에 이르면, 단순한 플래그 조정은 임시변통에 불과해진다. 이 글의 추측으로는, 저자가 제기한 '격리된 하드포크'라는 구상은 이러한 기능 추가가 웹 렌더링 엔진의 신뢰성을 근본적으로 훼손하고 있다는 기술적 평가에서 출발했다.

2. Base Browser의 정체성 — 설정 비활성화가 아닌 코드 도려내기

마스토돈 스레드에서 시작된 논의는 Codeberg 플랫폼 위에 구축된 Base Browser Project로 구체화되었다. 원문은 이 프로젝트가 아이디어와 방향성을 모으고 토론할 수 있는 공간을 마련하기 위해 시작되었다고 설명한다. 원문에 기술된 현재 Base Browser의 명확한 정의는 다음과 같다. 원문은 "A set of patches, based around the current Firefox 153 ESR, that strip user hostile features completely out of the code base (as opposed to the common soft-fork approach of disabling these.)"라고 서술한다.

여기서 핵심적인 차별점은 '기능의 비활성화(disabling)'와 '코드의 완전한 제거(strip completely out)' 사이에 존재한다. 일반적인 오픈소스 브라우저 파생 프로젝트들은 배포판을 구성할 때 설정 파일이나 빌드 플래그를 통해 불필요한 원격 측정이나 외부 연동 기능을 꺼두는 소프트 포크 방식을 택한다. 그러나 Base Browser는 기능을 비활성화하는 데 그치지 않고, 사용자에게 적대적이라고 판단되는 모듈 자체를 소스코드 수준에서 물리적으로 삭제하는 접근을 취한다.

원문에서 저자는 이처럼 기능들을 코드베이스에서 완전히 삭제하는 방식이야말로 올바른 접근법이라고 단언한다. 저자는 원문에서 "I believe that deleting these features entirely is the correct approach for exactly the reasons that make it a pain - these features are large, and increasingly tightly integrated into the core browser. They also account for an increasingly percentage of the total firefox code base and quite frankly: I do not believe that these features should be anywhere near the core base of a web browser"라고 강조한다. 작업이 고통스러운 바로 그 이유 때문에 완전한 삭제가 필수적이라는 역설이다.

이 글의 해석으로는, 코드가 잔존하는 한 브라우저 내부의 예기치 않은 통신 경로나 라이브러리 간 의존성이 언제든 활성화될 위험이 존재하기 때문에 삭제를 택한 것으로 해석된다. 복잡도가 높은 브라우저 환경에서는 비활성화 플래그가 상위 버전 갱신 과정에서 무력화되거나 기본값이 변경되는 사고가 일어날 수 있다. 이 글의 추측으로는, Base Browser 팀이 삭제라는 가장 과격하고 유지비용이 높은 수단을 택한 것은 잠재적 유입 가능성을 소스 트리 단위에서 차단하겠다는 단호한 설계 의도다.

3. 초기 AI 제거 패치의 규모와 압축 과정

Base Browser 프로젝트의 첫걸음으로 저자가 직접 작성한 초기 작업물은 인공지능 관련 모듈을 도려내는 거대한 패치였다. 원문은 이 작업의 결과물에 대해 "a ridiculous patch impacting 1605 files changed with 852297 deletions, totalling 37 megabytes"라고 적는다. 단일 기능 제거를 위한 diff 파일 하나가 37MB에 달하고, 1,605개 파일에서 85만 라인 이상의 코드가 지워진 전례 없는 규모였다.

원문은 이 초기 diff가 Base Browser 프로젝트의 정식 공식 배포판 diff 그 자체를 의미하는 것은 아니며, Firefox 내부에서 AI 연동 코드를 통째로 제거하려 했을 때 마주친 초기 패치의 실제 규모를 보여주는 지표라고 기술한다. 브라우저 엔진 전반에 걸쳐 인공지능 관련 호출부와 보조 모듈이 얼마나 광범위하게 침투해 있었는지를 수치로 증명하는 대목이다. 이후 수 주 동안 저자와 소수의 자원봉사자 팀은 추가 패치를 작업하고 거대 패치를 개선하는 과정을 거쳤다.

원문에 따르면 이 작업에는 cliffmccarthy와 gellge라는 기여자가 구체적으로 참여했으며, 패치를 테스트하고 토론하는 자원봉사자들이 힘을 보탰다. 팀은 37MB에 달하는 방대한 diff를 실용적인 크기인 1MB 미만으로 압축하는 스크립트를 고안해 냈다. 원문은 Git의 기존 irreversible-delete 플래그와 사용자 정의 파이썬 스크립트를 결합하여 파일에 다시 패치를 적용할 수 있도록 처리함으로써 용량을 대폭 줄였다고 설명한다.

이 글의 해석으로는, 37MB에서 1MB 미만으로의 용량 감소는 순수 텍스트 diff 내에 포함된 대규모 파일 삭제 이력을 메타데이터 수준으로 최적화한 결과로 판단된다. 전체 파일을 통째로 지우는 변경 내역을 일반 텍스트 패치로 다루면 바이너리 수준의 용량 팽창이 발생한다. 이 글의 추측으로는, 프로젝트 팀이 배포와 버전 관리의 현실성을 확보하기 위해 전용 도구를 작성해야만 했을 만큼 삭제 대상의 규모가 통상적인 범위를 넘어섰음을 시사한다.

4. 기존 포크(Tor Browser·Waterfox)의 완화 방식과의 대조

원문에서 저자는 독립적인 브라우저 생태계의 대표 주자인 Tor Browser와 Waterfox의 현행 대응 방식을 구체적으로 거론하며 비교한다. 원문은 "Projects like Tor Browser and Waterfox are painstakingly disabling / patching out the worst - but every release becomes more expensive, and things do slip through."라고 서술한다. 기존 프로젝트들이 취하고 있는 방식은 가장 치명적인 기능들을 공들여 비활성화하거나 선별적으로 패치하는 노선이다.

이러한 선별적 비활성화는 상위 브라우저의 새로운 릴리스가 나올 때마다 막대한 유지보수 비용을 초래한다. 원문이 지적하듯 매 릴리스마다 패치 작업의 비용은 점점 더 비싸지고 있으며, 촘촘한 감시망에도 불구하고 원치 않는 기능이나 원격 측정 코드가 미처 걸러지지 못한 채 유입되는 문제가 발생한다. 상위 벤더의 코드 변경량이 방대할수록 비활성화 패치가 깨지거나 무력화될 가능성은 비례하여 증가한다.

원문 서술에 나타난 두 접근 방식의 대비는 다음과 같은 구체적 함의를 갖는다.

  • Tor Browser와 Waterfox는 상위 Firefox 릴리스와의 기능 동기화를 유지하기 위해 공들여 비활성화하는 방식을 채택했다.
  • 선별적 패치 방식은 릴리스 주기가 거듭될수록 충돌 해결과 검증에 들어가는 엔지니어링 비용이 누적된다.
  • Base Browser는 브라우저 코어와 깊게 얽히는 기능들을 원천적으로 배제하기 위해 물리적 코드 절제를 선택했다.
  • 완전 삭제 방식은 잠재적 유입 위험을 원천 제거하지만, 상위 코드베이스가 변할 때마다 감당해야 할 패치 유지보수 난이도를 대폭 상승시킨다.

이 글의 해석으로는, 기존 프로젝트 메인테이너들이 완전 삭제의 이점을 몰라서 취하지 않은 것이 아니라, 매달 쏟아지는 업스트림 보안 패치를 추적해야 하는 현실적 제약 때문에 비활성화에 머물렀던 것으로 해석된다. 코드를 잘라내는 순간 업스트림과의 머지 베이스가 완전히 틀어지기 때문이다. 이 글의 추측으로는, Base Browser의 시도는 기존 포크들이 감내해 온 타협의 한계를 정면으로 돌파하려는 시도이자 동시에 가장 험난한 가시밭길을 자처한 셈이다.

5. 브라우저의 방향성에 대한 저자의 진단 — Smart Window와 AI 에이전트

저자가 이처럼 극단적인 코드 절제에 착수한 배경에는 상위 프로젝트인 Firefox의 미래 로드맵에 대한 깊은 불신이 자리 잡고 있다. 원문에 따르면 Firefox는 단순한 인공지능 기능 통합 수준을 훨씬 넘어서는 방향으로 이미 나아가고 있다. 원문은 Firefox가 브라우저 컨텍스트 전체를 사람뿐만 아니라 서드파티 인공지능 에이전트를 위해 구축된 이른바 "smartwindow"로 구상하고 있다고 마스토돈 링크를 통해 짚는다.

브라우저 창 전체가 사용자의 시각적 탐색 도구가 아니라 자율 에이전트의 실행 환경으로 변모할 때, 웹 브라우저의 본질적인 성격은 근본적으로 뒤바뀐다. 과거 Mistral과 Mozilla의 Smart Window 제휴가 밝힌 것과 밝히지 않은 것에서 살펴보았듯, 탭 내부의 맥락과 사용자의 탐색 흐름을 모델에 제공하는 아키텍처는 브라우저 벤더와 제휴사 간의 긴밀한 데이터 순환을 전제로 한다. 이러한 구조는 필연적으로 브라우저 엔진 내부에 무거운 상태 추적기와 분석기를 상주시킨다.

원문에서 저자는 "I don't want the web to go in that direction and, frankly, I cannot follow."라고 선언한다. 웹 생태계가 인공지능 에이전트 중심의 상호작용으로 변모하는 방향을 원하지 않으며, 그러한 흐름을 따라갈 수 없다는 단호한 거부 의사다. 또한 저자는 자신 역시 이러한 거대한 작업을 이끌기에 적합한 사람이 아니라고 스스로 밝히면서도, 적어도 이런 일이 일어날 수 있도록 시도하기 위해 무언가 해야만 했다고 술회한다.

이 글의 해석으로는, 상위 벤더가 브라우저의 주인을 '사용자'에서 '에이전트'로 교체하려 한다는 위기감이 완전 삭제라는 강경책을 이끌어낸 핵심 동력으로 풀이된다. 브라우저 셸이 에이전트의 제어판이 되는 순간, 기존의 보안 경계와 샌드박스 정책은 흔들릴 수밖에 없다. 이 글의 추측으로는, 저자가 Base Browser를 통해 지키고자 한 것은 단순한 메모리 절약이 아니라 웹을 인간 사용자의 통제 아래 온전히 남겨두겠다는 주권의 문제다.

6. 소비를 넘어 창작의 도구로 — Amaya, Flock, 그리고 대안 프로토콜

원문은 단순히 거부와 삭제에 머무르지 않고 웹 브라우저가 과거에 품었던 이상적인 비전을 소환한다. 저자는 원문에서 "I often think about the visions put forth by browsers like Amaya and, much later Flock. That a browser should be a tool for creation as much as consumption."라고 적는다. 브라우저는 단순히 완성된 웹 문서를 소비하는 수동적인 뷰어가 아니라, 문서를 직접 생산하고 공유하는 창작의 도구여야 한다는 철학이다.

W3C가 웹의 초기 표준을 실험하기 위해 만들었던 Amaya는 브라우저이자 동시에 위지윅 HTML 편집기였다. 또한 2000년대 중반 등장했던 Flock은 블로깅, 소셜 미디어 연동, 분산 태깅을 브라우저 차원에서 지원하며 읽고 쓰는 웹의 르네상스를 꿈꿨다. 원문은 2000년대 초반 Firefox가 브라우저 르네상스를 촉발했을 당시 피드, 블로깅 통합, 집단 태깅, 열린 댓글 등 브라우저가 무엇이 될 수 있는지에 대한 흥분이 넘쳐났던 시기를 회고한다.

원문이 짚는 과거 브라우저의 이상과 현대 표준의 괴리는 다음과 같은 요소들로 정리된다.

  • Amaya가 추구했던 것처럼 웹 문서를 읽는 것과 동시에 작성할 수 있는 양방향 저작 도구로서의 지향성.
  • Flock이 보여주었던 피드와 분산 블로깅 연동처럼 탈중앙화된 소통 창구로서 브라우저 셸의 역할.
  • 경제적 이해관계와 거대 상업 벤더들의 요구에 맞춰 규격이 극도로 비대해진 현대 웹 표준의 피로감.
  • 순수한 철학적 비전과 상업적 투자 회수 압박 사이에서 매 페이지 로드마다 발생하는 구조적 긴장감.

원문에 따르면 저자는 이러한 창작 도구로서의 비전을 여전히 마음에 품고 있으며, 지난 몇 년 동안 대규모 언어 모델이 아닌 gemini 프로토콜(geminiprotocol.net)과 RSS를 지원하는 소형 브라우저를 직접 제작하는 실험을 진행해 왔다. 현대 상업적 표준에 오염되지 않은 대안 기술을 통해 웹의 새로운 가능성을 모색해 온 셈이다. 저자는 이것이 확실한 미래인지는 확신할 수 없으나 하나의 대안적 미래는 될 수 있다고 적으며, "we need new noise"라는 과거의 구호를 인용한다.

7. 웹 의존도를 낮추기 위한 세 가지 임시 조치

완전한 대안 브라우저를 구축하는 일은 시간이 걸리는 장기적인 과제다. 이에 따라 저자는 원문에서 Firefox 및 거대 브라우저에 대한 일상적 의존도를 줄이기 위해 자신이 실천하고 있는 세 가지 구체적인 임시 조치를 공개했다. 원문에 나열된 세 가지 조치는 브라우저 바깥으로 작업 환경을 분산시키는 실천적 전략들이다.

  1. 오프라인으로 가능한 한 많이 이동하기: 원문은 기본적인 웹 브라우징 작업을 코어 브라우저로부터 분리하기 위해 openzim 리더(Kiwix 등)를 활용하고 있다고 밝힌다. OpenZIM 파일은 더 단순한 브라우저로도 구동 가능한 최소한의 HTML/CSS/JS 서브셋을 지향하므로 복잡한 렌더링 엔진 없이도 오프라인 읽기가 가능하다.
  2. 가능한 곳에서 독립형 데스크톱 애플리케이션으로 전환하기: 원문은 웹 브라우저 안에서 구동되는 웹 애플리케이션보다 독립형 애플리케이션을 선호한다고 적는다. 저자는 마스토돈처럼 오프라인 리더로 대체할 수 없는 온라인 서비스들을 전용 클라이언트로 분리하는 실험을 진행하고 있다고 설명한다.
  3. 가능한 곳에서 피드 리더(Feed Reader)로 전환하기: 원문은 독립 애플리케이션과 같은 맥락에서 피드(RSS/Atom)를 활용하면 전체 브라우저 엔진을 구동하지 않고도 온라인 시스템과 직접 소통하고 정보를 수신할 수 있다고 기술한다.

이 글의 해석으로는, 이러한 조치들은 현대 웹이 요구하는 과도한 클라이언트 연산과 원격 추적 환경으로부터 사용자를 물리적으로 격리하는 방어 기제로 평가된다. 렌더링 엔진 전체를 띄우지 않고 텍스트 기반 피드나 사전 패키징된 문서를 소비하는 방식은 브라우저 벤더의 상업적 정책 변경에 흔들리지 않는 가장 안전한 도피처다. 이 글의 추측으로는, 저자가 이러한 개인적 우회로를 병행하는 것은 Base Browser와 같은 코어 분리 작업이 완료되기 전까지 일상의 생산성을 보존하려는 현실적 타협안이다.

8. 지속가능성의 현실적 한계와 커뮤니티 결집의 필요성

원문의 가장 솔직하고 냉철한 대목은 이 거대한 도전이 마주한 현실적인 한계를 숨기지 않는다는 점이다. 원문에서 저자는 이 싸움에서 질 준비가 되어 있다고 고백한다. 원문은 "Now, I am well prepared to lose this battle. I do not believe that there is enough funding, or enough developer effort to maintain something like this long term. Unless we all pool our efforts into making a base like this possible."라고 적는다. 장기적으로 이러한 베이스 프로젝트를 유지하기에는 자금도, 개발 인력도 턱없이 부족하다는 인정이다.

브라우저를 개발하고 보안 취약점을 패치하며 웹 표준의 변경 사항을 추적하는 일은 막대한 자본과 전임 엔지니어링 조직을 요구한다. 원문은 지난 10여 년 동안 웹 표준이 상업적 이해관계의 우선순위로 과포화되었으며, 어떤 수준의 품질 보증과 보안을 갖춘 웹 브라우저를 유지하려면 자금이 풍부한 팀이 필요하거나 의존성 트리에 그러한 팀을 두어야만 한다고 설명한다. 그러나 자금에는 필연적으로 대가가 따르며, 이는 브라우저의 독립성을 갉아먹는 요인이 된다.

원문이 제시하는 Base Browser의 지속가능성 조건과 저자의 심경은 다음과 같이 요약된다.

  • 상위 브라우저가 지속적으로 구조를 변경하고 있어 프로젝트의 기반이 흔들리는 모래 위에 서 있는 것과 같다.
  • 장기적인 유지를 위해서는 개별적으로 흩어져 있는 포크 프로젝트들과 커뮤니티가 힘을 합쳐 단일 베이스를 유지해야 한다.
  • 이 노력의 결과로 소수의 사람들이 Firefox를 소스코드로부터 직접 빌드하는 방법을 배우기만 하더라도 승리로 여길 것이다.
  • 어떤 오픈소스 프로젝트든 이 패치 세트를 공식적으로 채택하거나 활용하게 된다면 대단히 기쁠 것이라는 희망을 품고 있다.

이 글의 해석으로는, Base Browser의 진정한 가치는 단독 완성형 상용 브라우저의 출시에 있는 것이 아니라, 파편화된 비-크로미움 생태계의 포크들에게 공유 가능한 청정 업스트림 베이스를 제공하려는 '기준점' 제시에 있다. 혼자서는 불가능하지만, 여러 프로젝트가 하나의 베이스 패치를 공동 관리한다면 업스트림 추적 비용을 분담할 수 있기 때문이다. 이 글의 추측으로는, 저자의 담담한 패배 선언은 무력감의 표현이 아니라 기여자들이 현실을 직시하고 결집하기를 촉구하는 일종의 신호탄이다.

9. 확인하지 못한 것

원문 서술과 공개 저장소 기록을 바탕으로 분석을 진행했으나, 자료의 공개 범위 한계로 인해 확인하지 못한 사항들은 다음과 같다.

  • Base Browser의 정식 바이너리 배포 일정 및 구체적 릴리스 로드맵: 원문은 코드 패치 세트와 압축 방식을 설명하지만, 일반 사용자를 위한 독립 빌드 실행 파일 배포 계획이나 릴리스 일정은 공개하지 않았다.
  • LibreWolf, Zen, Floorp 등 타 Firefox 포크들의 참여 여부: 원문은 Tor Browser와 Waterfox의 방식만 비교 대상으로 언급했을 뿐, 다른 유명 포크 프로젝트들의 Base Browser 협력 의사나 참여 여부를 밝히지 않았다.
  • 삭제된 1,605개 파일의 세부 디렉터리 경로 및 구체적 모듈 목록: 원문은 1,605개 파일과 85만 라인 삭제라는 총량 수치만 밝혔으며, 삭제 대상이 된 개별 C++ 또는 JavaScript 파일의 구체적 경로는 명시하지 않았다.
  • 압축 스크립트에 사용된 사용자 정의 파이썬 도구의 소스코드: 원문은 git의 irreversible-delete 옵션과 custom Python을 사용해 1MB 미만으로 줄였다고 서술했으나, 해당 파이썬 스크립트의 구체적 구현 코드는 글에 첨부되지 않았다.
