Choosing a Compressor Is a Decision About What You Trade for What - The Five Axes BZip3 Exposes, and the Last Axis Nobody Benchmarks

Ratio, compression speed, decompression speed, then memory and parallelism behind them, and finally whether it still opens in twenty years

2026-09-08 Dev & Infra

The decision to switch compressors is usually made on the strength of a single number. The same file comes out thirty percent smaller, and that seems to settle it. The number may well be true. The trouble is that it is one of five pieces of information the decision needs, and the other four rarely appear in the sentence that sells the change.

A compressor gives up one axis to gain another. Push the ratio and compression time grows; some designs drag decompression down with it while others hold that side steady. Enlarge the block and the ratio improves, but the memory demanded of whoever unpacks the file grows in step. That demand is fixed the moment you compress, written into the file, and cannot be renegotiated afterwards by the person on the receiving end.

There is one more axis. Does the party who has to read the format actually possess a tool that speaks it? That is not a property of the algorithm at all. It is the state of an ecosystem, and for anything meant to outlive a hardware generation it weighs more than the other four combined.

Every figure below carries a source and a timestamp. The repository values are the GitHub API response as of 2026-09-08 08:11 KST (2026-09-07 23:11 UTC). The algorithmic description comes from the 1994 original paper and from each tool's official manual. Every performance number is a measurement the project author took himself. Self-measured figures have to be read together with their conditions, because a multiplier with no stated corpus, hardware, thread count and block size is not a value at all.

The prompt - when three adjectives share one sentence

The opening line of the BZip3 repository introduces the project as a better, faster and stronger spiritual successor to BZip2. Anyone who has spent time with compression will split that sentence before believing it. Better means ratio. Faster splits immediately into compression speed and decompression speed, which are different quantities that often move in opposite directions. Stronger usually points at large blocks and multiple threads. The three adjectives are true on three different axes, and each is true only under its own conditions.

The angle taken here is not a tool review. By following which axes one successor bought and which it sold, the aim is to lay out what choosing a compressor actually trades against what. The theoretical question of why compression ratio and prediction accuracy measure the same thing has been handled separately. What matters here is not that theory but the decision.

The three axes compressors fight over, and the two behind them

Three axes come first: compression ratio, compression speed and decompression speed. They are not welded together. Improving the ratio requires a more elaborate model, and a more elaborate model makes compression slower, but what happens on the decompression side depends entirely on the family. LZ-style formats decompress far more cheaply than they compress, because the decoder never rebuilds a dictionary; it copies where it is told to copy. Context-modelling formats have to run the same model in the same order in both directions, which makes the two sides nearly symmetric in cost.

Two more axes attach behind those: memory footprint and parallelism. Both were treated as secondary for a long time, yet in current practice these are the axes that most often overturn a decision. A container memory limit, the core count of a CI runner, or the RAM on a rescue image tends to bind long before a few percent of ratio does.

The last column is the important one. The same compressor can be an excellent choice for distribution and a poor one for log ingestion. Unless you first decide which axis your workload actually binds on, every comparison collapses into a single line about ratio, and the decision comes out wrong.

Asymmetry as a baseline property

Most lossless compressors decompress faster than they compress. The 1994 paper states in its conclusions that, like the Lempel and Ziv algorithms, its own algorithm decompresses faster than it compresses. That asymmetry carries real weight in practice. A distribution artifact is compressed once and unpacked thousands of times, so compression time is very nearly free there and only decompression time and decompression memory are genuine costs. A nightly backup is the mirror image: compression time eats the maintenance window directly, and nobody may ever decompress the result at all.

A 1994 paper already published the trade as a table

The origin of block-sorting compression is SRC Research Report 124, published by Michael Burrows and David Wheeler at the Digital Equipment Systems Research Center on 10 May 1994. The paper records that the transform was discovered by one of the authors, Wheeler, in 1983 while he was at Bell Laboratories, and that it had not been published before.

The real value of that report is less the transform than Table 3: the same fourteen files compressed four different ways on the same hardware.

The paper states its measurement conditions. The fourteen files of the Calgary Compression Corpus were compressed individually and the results totalled; the hardware was a DECstation 5000/200 with a 25 MHz MIPS R3000 processor and a 64 kilobyte cache; and CPU time rather than elapsed time was reported specifically so that time spent on input and output would be excluded. The bits-per-character column is the mean of the per-file values.

Here is how to read that table. compress is five times faster than block sorting and produces a result 45 percent larger. At the opposite end, comp-2 spends twelve times the compression CPU and sixty-five times the decompression CPU and still lands at 2.47 mean bits per character against block sorting's 2.43. On total bytes comp-2 is marginally smaller, but the margin is 0.9 percent and the price is an order-of-magnitude change in time.

The reason a table from 32 years ago still reads correctly is that the number of axes has not changed. The absolute figures moved with the hardware, but the structure — push one axis and another gives way — did not.

What the block-sorting transform does - easy to parallelise, hard to stream

Algorithm C in the paper is defined this way. For a string S of N characters, form the N rotations of S, sort them lexicographically, and collect the last character of each rotation into a string L. Record as I the index of the row that holds the original S in the sorted list. The output of the transform is that pair and nothing else, and Algorithm D reconstructs S from L and I alone.

The paper's worked example is the whole explanation in miniature. With S equal to abraca and N equal to 6, sorting the six rotations gives L equal to caraab and I equal to 1. Same length, same multiset of characters. The transform does not remove a single byte.

Why reordering alone makes the data compressible

The paper's account fits in two sentences. Sorting brings together the rotations that begin with the same character. Because these are rotations, the character immediately to the left of that first character is the last character of the row. Consecutive characters in L are therefore characters that sat next to similar strings inside the original S. If context is a good predictor of the character that follows it, L becomes a string in which identical characters clump, and that clumping can be removed cheaply by a simple locally adaptive scheme such as move-to-front coding.

The paper is equally explicit about the limitation, and it sits in the same place: the technique uses the context on only one side of each character. The implementation described applied Huffman or arithmetic coding after the move-to-front step, and in practice recomputed its Huffman trees for every 16 kilobytes of input rather than building one tree for the whole stream.

Two consequences of being block-based

The paper states that its algorithm does not process its input sequentially but instead processes a block of text as a single unit. Two things follow from that single sentence.

  • Parallelisation is easy. Because blocks carry no dependency on each other, one thread can own one block outright, and adding cores shortens wall clock time almost linearly until memory or bandwidth binds. The bzip3 manual defines its worker-count option in exactly those terms: parallel workers that each process one block.
  • Partial recovery is possible. The bzip2 manual states that each block is handled independently, that a 48-bit pattern delimits blocks, and that every block carries its own 32-bit CRC. The bzip2recover utility, which searches a damaged file for blocks and writes each into its own file, exists because the format is cut into independent pieces in the first place.
  • Streaming is hard. Sorting cannot begin until the block is full, which means the delay before the first output byte is tied to the block size rather than to throughput. The BZip3 format overview does not soften this at all; it states the property as block level compression, no streams.
  • That last property is what divides the use cases. Anywhere a byte written now has to leave now — a pipeline pushing logs in real time, a protocol framing responses — a block design is out of the running no matter how good its ratio is. Anywhere a finished tarball gets compressed overnight, the same property costs nothing whatsoever.

Block size - ratio and memory hang from the same lever

Block size is very nearly the only lever a user of this family gets to turn. Table 2 of the paper draws the shape of that lever.

The paper's judgement runs as follows. Compression keeps improving as the block grows, even when the block is already quite large, but increasing it beyond a few tens of millions of characters has only a small effect. It adds that even an unbounded block would not reach the theoretical optimum, because the byte-wise move-to-front coder introduces loss of its own.

On the other end of that lever hangs memory. Both manuals give explicit formulas.

The row worth staring at is the third from the bottom. bzip2 at its largest block still needs under four megabytes to decompress. The reason a 32-year-old default is still running on rescue media and embedded targets is that number, not its ratio. Use bzip3 at its maximum block and the party unpacking the file needs something on the order of three gigabytes to do so.

Both manuals stress the same sentence. The memory needed to decompress is fixed at compression time, by the block size chosen then. The bzip2 manual notes that the value is read back out of the file header, and the bzip3 format specification places the maximum block size in the four bytes right after the signature. Compressing feels like a decision made for your own convenience, but it is in fact the act of specifying, today, the machine that will be required to open this file later.

The four places the successor actually changed

The BZip3 manual summarises its own pipeline as run length encoding and Lempel Ziv prediction, followed by the Burrows-Wheeler transform and arithmetic coding. The repository description adds that the entropy stage is an order-zero context mixing coder and that the transform is built on suffix arrays. Set beside the arrangement in the original paper, the changed positions become visible.

The pre-pass is the most conspicuous change, and the corpus table in the repository shows how far it can swing on repetitive material. An audio tarball of 115,742,720 bytes comes out at 95,526,840 bytes under bzip2, or 82.5 percent, and at 41,187,299 bytes under bzip3, or 35.6 percent. In the same table a DNA tarball of 685,619,200 bytes goes to 180,075,480 bytes against 157,642,102 bytes, a gap of only about twelve percent. The same tool wins by wildly different margins depending on the character of the data.

What was sold to buy that is equally clear. As the benchmark section below shows, compressing the same material takes bzip2 eight megabytes and takes bzip3, under some of the published settings, eighteen gigabytes. This is a design that hands over the memory axis wholesale in exchange for ratio and parallelism.

Same tools, different data, opposite conclusions

In the Silesia set, bzip3 at a 16 mebibyte block on a single thread spent 17.42 seconds at a peak of 98 megabytes and produced 47,227,855 bytes. Under the same conditions lzma -9 spent 76.88 seconds at 675 megabytes for 48,761,670 bytes, and zstd -19 spent 83.43 seconds at 237 megabytes for 53,000,145 bytes. That is the rare case where all three axes lean the same way.

The Linux kernel set turns the picture around. bzip3 produced 129,023,171 bytes in 76.93 seconds, while lzma -9 spent 397.30 seconds and came out smaller, at 125,725,455 bytes. The same two tools swapped places on the ratio axis the moment the input changed. Strip the corpus name from either sentence and the two read as a contradiction.

The Calgary set orders the speed axis. bzip2 -9 is fastest at 172.9 milliseconds, then gzip -9 at 224.3, bzip3 -b 3 at 265.3, and lzma -9 at 787.9. Memory in the same set runs gzip 5 megabytes, bzip2 8, bzip3 17, lzma 95. Output size runs the other way: bzip3 807,959 bytes, lzma 853,112, bzip2 891,321, gzip 1,062,584. Three of the five axes name three different winners in one set of runs.

Where the Perl set exposes the memory axis

The most widely quoted figures come from the Perl set. Compressed sizes run 546,456,978 bytes for bzip3 at a 511 mebibyte block, 1,001,957,587 bytes for bzip3 at 256 mebibytes, 2,056,645,240 for xz, 3,076,143,660 for zstd and 3,441,163,911 for bzip2. Read on their own, those numbers look decisive.

Read the memory column of the same records and the picture changes. bzip2 did its work in 8 megabytes. bzip3 used 18,301 megabytes at a 256 mebibyte block with 12 threads and 12,178 megabytes at a 511 mebibyte block with 4 threads. xz used 14,658 megabytes across 16 threads. The axes bzip3 won in that table are ratio and wall clock time; the axis it sold is memory, and the margin against bzip2 is more than two thousandfold.

Decompression wall clock times are recorded as 3 minutes 51 seconds for zstd, 4 minutes 6 seconds for parallel bzip3, 4 minutes 40 seconds for xz and 9 minutes 22 seconds for bzip2. Those were taken against a WD Blue class hard disk, so a substantial share of each figure is time spent reading and writing the disk rather than CPU work. The throughput the project description states separately is up to 17 MiB/s compression and 23 MiB/s decompression per thread for an x64 Linux build made with clang13, with the same sentence adding that Windows and 32-bit builds may be considerably slower. The asymmetry holds there too: decompression runs faster than compression.

Is the format frozen - BZ3v1 and the checksum incident

For anything intended to last, whether the format is frozen ranks ahead of ratio. BZip3 brings favourable material to that question. There is a written specification, it carries a version number, and it ships with example parser code.

  • The file header is 9 bytes: a five-byte signature reading BZ3v1 and a four-byte maximum block size. The frame header used by the library's high-level functions adds a four-byte block count, making 13 bytes.
  • Integers are little-endian and unaligned throughout, and the specification supplies portable read and write helpers so no implementation has to guess.
  • The valid range for the maximum block size runs from 65,536 bytes to 535,822,336 bytes. The specification states that a parser must reject anything outside it.
  • Each chunk is prefixed by a four-byte compressed size and a four-byte original size. When the original is under 64 bytes no compression is attempted; the data is stored as is with a CRC32 and a 0xFFFFFFFF marker in place of the transform index.
  • A model byte in each block announces which stages ran, as bit flags: 0x02 for LZP and 0x04 for RLE.
  • The manual puts the fixed overhead at 9 bytes per file and 9 to 17 bytes per block, and states that expansion on random data is generally under 0.8 percent.

And yet an archive still lost its future

The release notes carry the following under version 1.3.2. A programming mistake reversed the shift direction in the CRC32 check function, and as a result versions 1.3.0 and 1.3.1 introduced a breaking change to the checksum calculation. The change was reverted in 1.3.2. The same entry then adds the consequence: archives created with those two versions fail to decompress normally with a checksum error, and only the recovery option restores their original contents.

What that incident demonstrates is unambiguous. A written specification does not save the files if the implementation wobbles. The implementation was the truth, not the document, and every file written in the window between those releases became a healthy file that insists it is corrupt.

The notes record movement at another layer as well. Version 1.5.0 states that the signatures of the block encode and decode functions changed and that the release is not ABI-compatible with its predecessors, and 1.5.1 changed the shared library name to signal that difference. That is the library interface rather than the file format, and it is the layer where most of the motion happened. The same 1.5.0 entry separately notes that tighter LZP and RLE bounds in the decoder improved compression slightly with no observable format change. The habit of recording format and implementation as distinct things is itself material for a judgement.

The address moved too. The 1.5.3 entry records that the project relocated to a new account. Redirects work, but the old address stays embedded in papers, package metadata and older documentation. For long-term preservation, a link is part of the format.

Why new compressors fail to spread - it is the toolchain, not the format

This is the heart of the piece. New compressors rarely fail because the algorithm is bad. Choosing a compressor is choosing to bind your data to an environment that can read that format, and that environment moves far more slowly than code does.

There are four layers you can actually check.

First layer - does the standard archiver know it

The compression options of GNU tar 1.35 list dedicated flags for gzip, bzip2, xz, lzma, lzop, zstd and compress. There is none for bz3. There is an escape hatch: the option that nominates an external program as the compression filter will attach any compressor at all. For that option to work, however, the machine doing the unpacking has to have the binary installed. The option that infers the compressor from the file suffix works only for suffixes present in the internal mapping table.

Second layer - does the common library know it

The filter constants defined in the public libarchive header are none, gzip, bzip2, compress, external program, lzma, xz, uuencode, rpm, lzip, lrzip, lzop, grzip, lz4 and zstd. There is no bzip3 entry. That list matters because libarchive has more than one consumer: bsdtar, the tar shipped on macOS, build tooling and several package managers all reach compressed formats through it. Absence there means every one of those tools does not recognise the extension.

Third layer - does the language standard know it

The Python 3.13 standard library ships gzip, bz2, lzma and zlib. There is no bz3 module, and the compression modes tarfile accepts are gz, bz2 and xz only. Wherever an archive is opened by one line of script, a new format introduces a threshold called installing an extra dependency. That threshold is low in a development environment and high in production, and higher still in somebody else's environment where you do not control what gets installed.

Fourth layer - is the version in hand the same version

By aggregate package listing, bzip3 appears in 148 entries and is carried by most major distributions. The problem is which version. Debian 12 stable carries 1.2.2, Ubuntu 24.04 carries 1.4.0, Fedora 43 and later along with Arch, openSUSE Tumbleweed, nixpkgs, FreeBSD and MSYS2 carry 1.5.3, and Homebrew and Gentoo carry 1.5.4. Three years separate the oldest from the newest. A mismatch between the machine that compressed and the machine that decompresses is the default state, not an edge case, and the checksum incident described above happened precisely in that gap.

Will it still open in twenty years

On that question the material BZip3 leaves behind is not bad. The format is specified in writing, the header layout and integer representation are defined, an example parser is published, the source is available under LGPLv3, and the five-byte fixed signature means a file can be identified on sight. In principle the current documents are enough to reimplement it from scratch.

But being reimplementable and having a tool in hand at the moment you need it are different propositions. gzip and bzip2 are everywhere today not because of their ratios. They are everywhere because they were already everywhere, and each year of that presence compounds. What the person opening an archive twenty years from now needs is not the optimal ratio; it is one command that is already installed on the machine in front of them.

Format selection is therefore not a ratio calculation but a dependency contract. Data that circulates only inside your own estate has a narrow contract and a controlled set of versions. Data that leaves the building, or that has to outlive a decade, has a contract whose counterparty you cannot name. The discussion of whether a backup actually comes back and the account of what a twenty-year-old encoding legacy does inside a zip both point at the same spot. Formats persist; the environments that read them do not.

Choosing by workload - from condition to property

A table that recommends specific products does not age well, because versions change and defaults change under them. What ages well is the arrow that runs from a condition to a property.

The table is read left to right. Decide first which axis your workload binds on, keep only the candidates whose properties favour that axis, and measure against your own data last. Run it in the other direction and you end up choosing the winner of somebody else's benchmark table, and that winner usually has nothing to do with the axis your work actually sits on.

What you can check with read-only commands

Everything below reads. Nothing creates or deletes a file, and nothing places load on a running system.

Start with what the toolchain in front of you already knows. These commands reproduce the first and third of the four layers above in your own environment.

# Which compressors this machine's tar knows about internally
tar --help | sed -n '/Compression options/,/^$/p'

# Compression modules present in the Python standard library
python3 -c "import gzip, bz2, lzma, zlib; print('stdlib ok')"

# A missing module answers with an exception. That is the correct result
python3 -c "import bz3" ; echo "exit=$?"

Reading the head of a file tells you the format and the decompression demand in advance. A bzip3 file header is a five-byte signature followed by a four-byte maximum block size, so the first nine bytes are enough.

# Five signature bytes. BZ3v1 means this is a bzip3 file
head -c 5 sample.bz3 | od -An -c

# The next four bytes are the maximum block size, little-endian unsigned 32-bit
head -c 9 sample.bz3 | od -An -t u4 -j 5 -N 4

# For bzip2, the digit after BZh is the block size in units of 100 kilobytes
head -c 4 sample.bz2 | od -An -c

Once the block size is known, the memory needed to decompress can be worked out ahead of time. The formulas come straight from the manuals.

# bzip3 needs about six times the block size. A 511 MiB block means roughly 3 GB
python3 -c "b=511*1024*1024; print(round(b*6/1024/1024), 'MiB')"

# bzip2 needs 100k plus four times the block size, under 4 MB even at maximum
python3 -c "b=900*1000; print(round((100*1000+4*b)/1024/1024,2), 'MiB')"

Measuring against your own data is the real answer. Take one representative sample and record all the axes together under identical conditions. Recording size alone reproduces exactly the trap described in the benchmark section above.

# Record output size, peak resident memory and time on one line
/usr/bin/time -v gzip  -9 -k -c sample.tar | wc -c
/usr/bin/time -v bzip2 -9 -k -c sample.tar | wc -c
/usr/bin/time -v xz    -9 -k -c sample.tar | wc -c

# Measure the decompression axis separately. For distribution it is the only cost
/usr/bin/time -v gzip  -dc sample.tar.gz | wc -c

What could not be verified

  • The hardware behind the Perl benchmark is not in the project description. No CPU model, core count or memory capacity appears; only the thread counts on the command lines and the hard disk model used for decompression. Those absolute times cannot serve as a comparison against any other environment.
  • In the same benchmark, the row for a 511 mebibyte block with 4 threads records 17.65 seconds of user CPU time, while the other rows of the same table sit in the hundreds to thousands of seconds and that row's own wall clock reads 7 minutes 8 seconds. The reason for the mismatch in magnitude lies outside what the description states, so it could not be settled here.
  • The 17-item corpus size table carries no block size, thread count or hardware. Other sections of the same document do give command lines, but whether those conditions also applied to the size table is not settled by the document. That table is used here for size comparison only.
  • Third-party reproduction benchmarks were not taken as evidence. The external benchmark repository the description points to was not opened, so every performance statement in this piece is a measurement by the project author.
  • An attempt to check the suffix mapping table behind the automatic compressor detection of GNU tar against the upstream source failed because that path did not respond. Statements about tar here are limited to the help output of GNU tar 1.35.
  • Per-distribution package versions come from an aggregation site rather than from a check against each distribution's own repository, and may have moved since the query.
  • The internals of the order-zero context mixing predictor are not covered. Describing how the contexts are defined and how the mixing works requires reading the source, and the description and manual go only as far as naming context mixing and arithmetic coding.
  • Which variant libsais actually uses could not be settled. That library's description cites four induced-sorting papers as its basis and says nothing about which path bzip3 takes through it.
  • What replaced the move-to-front stage is not settled by any document. Neither the project description nor the manual names that step at all, which is why the corresponding cell in the pipeline table above is left unnamed.
