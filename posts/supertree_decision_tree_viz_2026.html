supertree - 결정 트리를 줌·팬으로 탐색하는 인터랙티브 시각화 도구

MLJAR가 만든 파이썬 라이브러리로 보는 설명 가능한 AI의 다음 단계 - plot_tree·graphviz·dtreeviz와 무엇이 다른가

2026-07-03 개발/인프라

서론: 정적 이미지로 그린 트리, 이제는 인터랙티브로 뜯어본다

결정 트리(decision tree)는 머신러닝에서 가장 오래되고 가장 사랑받는 화이트박스 모델이다. 회귀·분류 어느 쪽이든 예측 과정을 사람이 눈으로 따라갈 수 있다는 것이 최대 무기다. 문제는 그 트리를 실제로 "보는" 방법이다. 지금까지 파이썬 생태계에서 결정 트리를 시각화하는 표준 루틴은 sklearn.tree.plot_tree()나 Graphviz로 정적 이미지 한 장을 뽑아내는 것이었다. 노드가 수십 개만 넘어가도 이미지는 감당 안 되는 크기로 불어나고, 결국 캡처해서 잘라 보거나 PDF로 뽑아 확대해 보는 수밖에 없었다.

2026년 7월 기준, 이 불편함을 정면으로 겨냥한 파이썬 라이브러리 supertree가 GeekNews를 통해 다시 주목받고 있다. AutoML 도구 mljar-supervised로 알려진 폴란드 회사 MLJAR가 만든 오픈소스 프로젝트로, 결정 트리를 Jupyter 노트북 안에서 줌·팬·노드 접기가 가능한 살아있는 위젯으로 렌더링한다. 이 글은 supertree의 기능을 그대로 옮기는 소개가 아니라, 결정 트리 해석(XAI) 도구로서 무엇이 실질적으로 달라졌고, 어디까지가 진짜 가치이고 어디부터는 과장인지를 따져보는 분석이다.

1. supertree란 무엇인가

1.1 기본 개요

supertree는 GitHub mljar/supertree 저장소에 공개된 Apache License 2.0 오픈소스 라이브러리다. pip install supertree로 설치하고, scikit-learn·XGBoost·LightGBM·ONNX로 학습한 트리 모델을 받아 시각화한다. 2026년 7월 기준 GitHub 스타는 600여 개, 최신 릴리스는 2026년 6월 초에 나온 v1.0.0으로 정식 버전 1.0에 막 도달한 상태다. 리포지토리 언어 구성을 보면 JavaScript가 80% 이상을 차지하는데, 이는 렌더링의 핵심이 파이썬 계산이 아니라 브라우저에서 돌아가는 D3.js 기반 시각화 엔진에 있다는 뜻이다.

1.2 핵심 기능

기능 자체는 단순하게 요약된다. 트리를 확대·축소(zoom)하고 이동(pan)하며, 하위 서브트리를 접었다 펼치는(collapse) 것이 가능하고, 특정 샘플이 루트에서 리프까지 어떤 경로를 탔는지 추적할 수 있다. GitHub 저장소는 이를 짧게 "Zoom, pan, collapse"라 표현한다. 이 네 가지 동작만으로도 정적 이미지가 못 하던 일이 가능해진다 - 깊이 8~10짜리 트리를 처음엔 축소된 전체 형태로 보고, 관심 있는 가지만 펼쳐 확대하는 탐색적 워크플로다.

1.3 실행 환경

Jupyter Notebook, JupyterLab, Google Colab, VS Code, MLJAR 자체 제품인 MLJAR Studio에서 동작한다고 안내한다. HTML을 렌더링할 수 있는 노트북 환경이면 대체로 호환된다는 뜻이다. 별도 서버나 대시보드 배포 없이, 코드 셀 하나로 위젯이 뜬다는 점이 진입장벽을 낮춘다.

2. 결정 트리 해석이 왜 중요한가 - 설명 가능한 AI의 관문

2.1 화이트박스 모델의 자리

설명 가능한 AI(XAI) 논의에서 결정 트리는 거의 항상 "본질적으로 해석 가능한(interpretable-by-design)" 모델의 대표 사례로 언급된다. 선형회귀·로지스틱회귀와 함께, 예측 로직을 사후 근사가 아니라 모델 구조 자체에서 그대로 읽어낼 수 있는 몇 안 되는 축에 속한다. 딥러닝이나 대형 앙상블처럼 SHAP·LIME 같은 사후 설명 기법을 덧붙여야 하는 모델과는 출발선이 다르다.

2.2 그런데 "보는 방법"이 해석 가능성을 갉아먹는다

여기서 본인이 강조하고 싶은 지점이 있다. 결정 트리가 구조적으로 해석 가능하다는 것과, 그 구조를 사람이 실제로 편하게 읽을 수 있다는 것은 별개의 문제다. 트리가 깊어지고 노드가 늘어나면 정적 이미지는 실질적으로 못 읽는 그림이 된다. 이론적으로는 "화이트박스"인데 실무에서는 도로 "읽기 힘든 상자"가 되어버리는 역설이다. supertree 같은 도구의 존재 이유는 정확히 이 틈, 즉 모델의 이론적 해석 가능성과 사람이 실제로 소화할 수 있는 해석 가능성 사이의 간극을 좁히는 데 있다.

2.3 규제·신뢰·감사 관점

금융 신용평가, 의료 진단 보조, 채용 스크리닝처럼 결정 근거를 설명해야 하는 영역에서는 모델 선택 단계에서부터 결정 트리·규칙 기반 모델이 우선 고려된다. 이런 도메인에서 트리를 실제로 들여다보고 검증하는 사람은 데이터 과학자만이 아니라 감사·컴플라이언스 담당자, 도메인 전문가인 경우가 많다. 이들에게 코드로 파고들라고 요구하기보다, 브라우저에서 줌·팬으로 직접 탐색하게 하는 편이 훨씬 현실적이다.

3. 기존 시각화 도구 대비 무엇이 다른가

3.1 plot_tree - 가장 쉬운 기본값, 그러나 정적

scikit-learn 내장 plot_tree()는 별도 설치 없이 matplotlib만으로 동작하는 가장 손쉬운 선택이다. 다만 노드마다 임계값·지니 불순도·샘플 수·클래스 분포를 텍스트로 욱여넣다 보니, 깊이가 늘면 글자가 겹치거나 그림 전체를 알아보기 어려워진다. 결과물은 한 장의 고정된 PNG/SVG이며, 큰 트리에서는 사실상 확대경 없이는 못 보는 그림이 된다.

3.2 Graphviz(export_graphviz) - 유연하지만 여전히 정적

Graphviz는 dot 파일을 직접 다뤄 스타일을 세밀하게 조정할 수 있고 레이아웃도 자동으로 잡아준다는 장점이 있다. 하지만 시스템에 Graphviz 바이너리를 별도로 설치해야 하고, 결과물은 여전히 정적 이미지다. 트리를 탐색하려면 결국 이미지 뷰어의 확대·축소 기능에 의존해야 한다.

3.3 dtreeviz - 정보 밀도는 최고, 설치는 까다롭다

dtreeviz는 셋 중 정보량이 가장 풍부하다. 각 분기 노드에 클래스별 분포를 겹친 히스토그램으로 보여주고, 특정 샘플 하나가 지나간 경로를 트리 전체에서 굵은 선으로 하이라이트해준다. "왜 이 샘플이 이 클래스로 분류됐는가"를 시각적으로 설명하는 데는 세 도구 중 가장 강력하다. 다만 이 역시 결과물은 정적 이미지이고, Graphviz 의존성과 PATH 설정 문제로 설치 과정에서 막히는 사례가 꾸준히 보고된다.

3.4 supertree의 실질적 차별점

세 도구 모두 "그림 한 장을 더 예쁘고 정보 밀도 높게 그리는" 경쟁을 했다면, supertree는 아예 다른 축으로 움직인다. 결과물이 이미지가 아니라 브라우저 안에서 상태를 유지하는 위젯이라는 점이다. 큰 트리를 전체 축소 뷰로 먼저 보고, 관심 가지만 펼쳐 확대하고, 다시 접어 전체 구조로 돌아오는 것이 가능해진다. dtreeviz의 정보 밀도나 Graphviz의 스타일 유연성을 그대로 이기는 것은 아니지만, "큰 트리를 실제로 탐색 가능한 상태로 유지한다"는 점에서는 세 도구가 채우지 못한 자리를 채운다.

4. 모델 디버깅·교육·이해관계자 소통에서의 실무 가치

4.1 디버깅 시나리오

본인이 트리 기반 모델을 튜닝할 때 가장 답답한 순간은 특정 리프가 왜 이상한 예측을 뱉는지 역추적할 때다. 정적 이미지로는 그 리프까지 가는 경로를 찾느라 이미지를 여러 번 새로 저장해 확대해야 했다. 인터랙티브 위젯이라면 문제가 되는 샘플의 경로를 추적해 바로 그 리프까지 파고들 수 있어, 과적합된 분기나 데이터 누수로 의심되는 조건을 훨씬 빠르게 찾을 수 있다.

4.2 교육 활용

결정 트리는 머신러닝 입문 강의에서 가장 먼저 등장하는 모델 중 하나다. 학생이 직접 트리를 확대·축소하며 "이 조건에서 왜 왼쪽으로 갈라지는가"를 눈으로 따라가 볼 수 있다면, 정적 슬라이드 한 장보다 개념이 훨씬 빨리 잡힌다. 노트북 하나로 실습·설명이 동시에 되는 것도 강의 자료 제작 부담을 줄여준다.

4.3 비개발자 이해관계자 소통

제품 책임자나 도메인 전문가에게 "이 모델이 왜 이런 판단을 내리는가"를 설명해야 하는 자리에서, 코드나 SHAP 값 표보다 실시간으로 조작 가능한 트리 그림 쪽이 훨씬 설득력이 있다. 다만 이 장점은 트리가 너무 깊지 않을 때 성립한다. 깊이가 지나치게 크면 비개발자에게는 결국 "복잡한 그림"일 뿐이라는 점은 분명히 해둘 필요가 있다.

5. 트리 기반 앙상블(랜덤포레스트·XGBoost) 해석에서의 의의와 한계

5.1 앙상블은 왜 해석이 어려운가

랜덤포레스트는 수백 개, XGBoost는 수십~수백 라운드의 부스팅 트리를 합산해 예측한다. 트리 하나하나는 해석 가능해도, 그 합은 더 이상 사람이 손으로 따라갈 수 있는 대상이 아니다. 이것이 트리 기반 앙상블이 "성능은 좋지만 해석은 딥러닝만큼이나 불투명하다"고 평가받는 이유다.

5.2 supertree로 개별 트리를 보는 것의 의미

supertree는 앙상블 안의 개별 트리 하나를 골라 인터랙티브하게 보여줄 수 있다. 이는 분명 유용하다 - 특정 트리가 어떤 분기를 학습했는지 감을 잡거나, 트리 간 구조가 얼마나 다양한지 눈으로 확인하는 용도로는 좋다. 그러나 여기서 분명히 짚어야 할 한계가 있다. 개별 트리 하나를 보는 것은 앙상블 전체의 의사결정을 설명하는 것이 아니다. 최종 예측은 수백 개 트리의 투표 또는 가중합이며, 트리 한 그루의 분기 구조만으로는 "왜 이 샘플이 이렇게 예측됐는가"에 답할 수 없다.

5.3 SHAP·LIME과의 역할 분담

앙상블 전체의 예측 근거를 설명하려면 SHAP(Shapley 값 기반)이나 LIME(국소 근사) 같은 모델 애그노스틱 사후 설명 기법이 필요하다. 본인이 정리하는 역할 분담은 이렇다 - supertree는 트리 구조를 이해하고 개별 트리를 디버깅하는 도구이고, SHAP·LIME은 앙상블 전체의 특정 예측 하나를 설명하는 도구다. 둘은 경쟁 관계가 아니라 보완 관계이며, "앙상블도 해석 가능해졌다"는 식으로 supertree를 과대 해석하는 것은 경계해야 한다.

6. 실무 도입 시 고려사항

6.1 언제 유용한가

단일 결정 트리를 실제 의사결정 근거로 쓰는 경우(신용평가 규칙, 트리아지 규칙), 트리 기반 모델 강의·워크숍, 랜덤포레스트에서 대표 트리 몇 개를 골라 구조를 점검하는 디버깅 세션에서 supertree는 확실한 시간 절약이 된다.

6.2 한계

몇 가지는 분명히 짚어야 한다. 첫째, 깊이가 극단적으로 큰 트리(예: 완전 성장한 미가지치기 트리)는 인터랙션이 있어도 결국 사람이 한 번에 소화할 수 있는 정보량을 넘어선다. 둘째, 브라우저에서 D3.js로 큰 노드 수를 렌더링하다 보니 트리 규모가 커지면 렌더링 성능이 떨어질 수 있다(공개 벤치마크 수치는 확인되지 않는다). 셋째, supertree는 어디까지나 노트북 안 탐색 도구이지, 프로덕션 모니터링 대시보드나 자동화된 모델 문서화 도구는 아니다. v1.0.0이 2026년 6월에야 나온 비교적 젊은 프로젝트라는 점도 감안해야 한다.

6.3 도입 가이드

본인이 권하는 순서는 이렇다. 먼저 이미 쓰고 있는 트리 기반 모델의 노트북에 pip install supertree 한 줄을 추가해 최소 예시로 감을 잡는다. 그다음 디버깅이나 발표 자료가 필요한 순간에 plot_tree 대신 꺼내 쓰며 실제로 시간이 줄어드는지 확인한다. 앙상블 전체 설명이 목적이라면 SHAP을 주력으로 두고, supertree는 그 안의 개별 트리를 들여다보는 보조 도구로 위치시키는 것이 정확한 사용법이다.

결론 - 작은 도구지만 XAI 워크플로의 빈틈을 채운다

supertree는 결정 트리 알고리즘 자체를 바꾸지 않는다. 바뀌는 것은 "그 트리를 어떻게 보느냐"뿐이다. 그런데도 이 변화가 의미 있는 이유는, 결정 트리의 최대 장점인 해석 가능성이 실무에서는 정적 이미지의 한계 때문에 자주 낭비돼 왔기 때문이다. 2026년 7월 기준 v1.0.0에 막 도달한 젊은 프로젝트이고 앙상블 전체를 설명해주는 만능 해결사도 아니지만, "결정 트리를 실제로 탐색 가능하게 만든다"는 좁고 명확한 문제 하나는 확실히 잘 푼다. 단일 트리를 다루거나 앙상블 속 개별 트리를 점검할 일이 있다면, 노트북에 한 줄 추가해볼 가치는 충분하다.
