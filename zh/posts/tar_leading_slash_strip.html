引言 - 归档里的路径就是打包时给出的字符串

tar归档会把名称字符串和文件内容一起保存。解包时，tar把这个名称解释为当前目录(或指定的基准目录)之下的路径，并在那里创建文件。因此打包时传入什么字符串，决定了解包后文件的位置。像 tar -cf out.tar app 这样传入相对路径，名称以 app/... 开头；传入 /home/user/app 这样的绝对路径，整条路径都会进入名称。此时tar会去掉开头的斜杠并给出警告。

问题出现在之后。被去掉的只有开头的斜杠，上级目录名仍然保留，所以解包到别处时，生成的不是 app，而是整条嵌套的上级路径。下面用同一棵演示目录树的输出展示这一现象，并依次说明基准目录 -C、保留绝对路径的 -P、含有 .. 成分的条目、解包前查看列表，以及只用一个顶层目录打包的惯例。末尾斜杠会改变rsync源含义的问题，见rsync末尾斜杠的文章；这里只讨论tar的开头斜杠和路径名称。

涉及的问题如下。

  • 用绝对路径打包时，tar会输出什么，退出码是多少。
  • 把该归档解包到另一个目录，文件会出现在哪里。
  • -C 与相对路径会生成相同的归档吗，-C 的位置规则是什么。
  • -P 只影响打包吗，解包时又如何表现。
  • 含有 .. 成分的条目和绝对路径条目在解包时如何处理。
  • 解包前应检查什么，归档应打包成什么形状才不会散落。

演示环境与安全框架

所有演示都只在用 mktemp -d 新建的临时文件夹里创建文件，结束时只删除该文件夹。使用绝对路径的示例，目标也只是该临时文件夹内的路径。show 函数是把输出中的临时文件夹路径替换为 /tmp/demo 的显示用过滤器，与tar的行为无关。演示目录树是 src/app 下的三个文件。

D=$(mktemp -d) && cd "$D" || exit 1
                    show() { sed -e "s#$D#/tmp/demo#g" -e "s#${D#/}#tmp/demo#g"; }
                    mkdir -p src/app/bin src/app/conf src/app/data
                    echo 'echo run' > src/app/bin/run.sh
                    echo 'port=8080' > src/app/conf/app.conf
                    echo 'alpha' > src/app/data/a.txt
                    tar --version | head -1
tar (GNU tar) 1.35

tar的种类和版本由 tar --version 的第一行区分。这台电脑的Git Bash中是GNU tar 1.35，之后的输出都来自这个tar。

解包时 - 整条上级路径都会出现

mkdir restore1
                    tar -C restore1 -xf abs.tar
                    (cd restore1 && find . -type f | sort) | show
./tmp/demo/src/app/bin/run.sh
                    ./tmp/demo/src/app/conf/app.conf
                    ./tmp/demo/src/app/data/a.txt

虽然用 -C restore1 指定了基准目录，文件并没有出现在 restore1/app/...，而是出现在 restore1/tmp/demo/src/app/...。名称里带有上级路径，所以解包时也会原样创建嵌套目录。这就是「解包后文件出现在意外位置」这一问题在这次演示中出现的样子。文件并没有丢失，只是在基准目录下很深的地方。

先 cd src 再用 tar -cf ../rel.tar app 生成的归档，与 tar -C src -cf c.tar app 生成的归档，cmp 判定为逐字节相同。成员名以 app/... 开头，没有警告，解包后得到 restore2/app/...。GNU tar手册页对 -C 的说明是：「Change to DIR before performing any operations. This option is order-sensitive, i.e. it affects all options that follow.」(出处：man.archlinux.org/man/tar.1.en)

                    tar -tf dot.tar

                    echo A > pos/a/fa.txt
                    echo B > pos/b/fb.txt
                    tar -cf pos1.tar -C pos/a fa.txt -C ../b fb.txt

                    tar -cf pos2.tar fa.txt -C pos/a

  • -C src/app -cf dot.tar . 生成的成员名以 ./ 开头，名称中没有 app 这样的顶层目录。顶层名称的问题在第8节讨论。
  • 在 -C pos/a fa.txt -C ../b fb.txt 中，第二个 -C 的 ../b 以第一个 -C 切换到的位置(pos/a)为基准解释，结果是 pos/b。列表里 fa.txt 和 fb.txt 都只剩下纯名称。
  • 把 -C 放在名称之后的 tar -cf pos2.tar fa.txt -C pos/a，先输出 fa.txt: Cannot stat，接着输出 -C 'pos/a' has no effect，以退出码2结束。-C 只作用于它之后的名称。

-P - 保留绝对路径会让 -C 失效

GNU tar手册页中 -P 的条目只有一行：「-P, --absolute-names: Don't strip leading slashes from file names when creating archives.」这句话讲的是创建时，但在下面的输出中，列表和解包时也出现了影响。该归档是用 -P 打包与前面各节相同的对象。

tar -P -cf p.tar "$D/src/app"
                    echo "exit=$?"
                    echo '--- list without -P'
                    tar -tf p.tar 2>&1 | show | head -3
                    echo '--- list with -P'
                    tar -P -tf p.tar | show | head -3
exit=0
                    --- list without -P
                    tar: Removing leading `/' from member names
                    /tmp/demo/src/app/
                    /tmp/demo/src/app/bin/
                    --- list with -P
                    /tmp/demo/src/app/
                    /tmp/demo/src/app/bin/
                    /tmp/demo/src/app/bin/run.sh

用 -P 打包时没有警告，退出码为0。列表输出有两种形式。不带 -P 执行 tar -tf，会再次输出警告，但仍按存储的原样显示名称，如 /tmp/demo/src/app/ 以斜杠开头。加上 -P 则不带警告地给出同样的列表。因此，列表中名称的第一个字符是否为斜杠，就是辨认 -P 归档的线索。

接着用 -P 加 -C restore3 解包这个归档。事先把原来的 src 移到 src_before，让原位置为空，所有解包目标都在临时文件夹之内。

mv src src_before
                    mkdir restore3
                    tar -P -C restore3 -xf p.tar
                    echo "exit=$?"
                    echo "files under restore3: $(find restore3 -type f | wc -l)"
                    find src -type f | sort
                    diff -r src src_before && echo "recreated src is identical to src_before"
                    mkdir restore4
                    tar -C restore4 -xf p.tar
                    (cd restore4 && find . -type f | sort) | show
exit=0
                    files under restore3: 0
                    src/app/bin/run.sh
                    src/app/conf/app.conf
                    src/app/data/a.txt
                    recreated src is identical to src_before
                    tar: Removing leading `/' from member names
                    ./tmp/demo/src/app/bin/run.sh
                    ./tmp/demo/src/app/conf/app.conf
                    ./tmp/demo/src/app/data/a.txt

结果有三点。第一，用 -P -C restore3 解包后，restore3 下的文件为0个，文件被重新创建在腾空的原位置 src/app。-C 对带绝对名称的条目没有起作用。第二，重新创建的 src 与 src_before 经 diff -r 判定相同。第三，不加 -P 把同一归档解包到 -C restore4，会连同警告一起嵌套在 restore4/tmp/demo/src/app/... 下。

  • 用 -P 解包时忽略 -C，直接写入记录的绝对位置。该位置与解包命令的 -C 无关，所以仅看解包命令，无法知道文件会出现在哪里。
  • 因此 -P 适合把自己的文件还原到同一位置；对于来源不明的归档，解包前先看列表的第一个字符(第8节)。
  • 在这次演示中，-P 写入的位置是临时文件夹内的原位置，没有写入系统或主目录路径。

含 .. 成分的条目与绝对名称条目 - 解包时的处理

先看tar在打包以 .. 开头的路径时怎么做。从子文件夹中打包上一级的文件 ../outside.txt。

mkdir -p work/sub
                    echo 'outside content' > work/outside.txt
                    (cd work/sub && tar -cf ../dd.tar ../outside.txt)
                    tar -tf work/dd.tar
tar: Removing leading `../' from member names
                    outside.txt

打包时tar输出了警告 Removing leading `../' from member names，并把名称缩短为 outside.txt。所以开头的 ../ 在用GNU tar打包时会被去掉，没有产生 .. 条目。要观察解包行为，需要能原样写入名称的工具；下面用Python标准库 tarfile 做了两个演示归档。一个包含 ok/inside.txt 和 ../escape.txt，另一个包含临时文件夹内的绝对名称 .../ext/abs_target.txt。加上 MSYS_NO_PATHCONV=1 是为了让Git Bash不要改写作为参数传入的路径，该前缀只适用于Git Bash。

mkdir craft ext
                    cat > craft/make.py <<'PYEOF'
                    import io, sys, tarfile
                    target = sys.argv[1]
                    def add(tf, name, data):
                        info = tarfile.TarInfo(name)
                        info.size = len(data)
                        tf.addfile(info, io.BytesIO(data))
                    with tarfile.open('craft/dotdot.tar', 'w') as tf:
                        add(tf, 'ok/inside.txt', b'inside')
                        add(tf, '../escape.txt', b'escaped')
                    with tarfile.open('craft/abs.tar', 'w') as tf:
                        add(tf, target + '/ext/abs_target.txt', b'absolute')
                    PYEOF
                    MSYS_NO_PATHCONV=1 python craft/make.py "$D"
                    tar -tf craft/dotdot.tar
                    tar -tf craft/abs.tar 2>&1 | show
ok/inside.txt
                    tar: Removing leading `../' from member names
                    ../escape.txt
                    tar: Removing leading `/' from member names
                    /tmp/demo/ext/abs_target.txt

在这两个归档的列表中，tar -tf 也会对 ../ 和开头斜杠给出警告。现在在临时文件夹内的 ext/inner 中解包。.. 条目的目的地是上一级的 ext，仍在临时文件夹之内。

mkdir ext/inner
                    (cd ext/inner && tar -xf ../../craft/dotdot.tar; echo "exit=$?")
                    find ext | sort
                    (cd ext/inner && tar -P -xf ../../craft/dotdot.tar; echo "exit=$?")
                    find ext | sort
tar: Removing leading `../' from member names
                    tar: ../escape.txt: Member name contains '..'
                    tar: Exiting with failure status due to previous errors
                    exit=2
                    ext
                    ext/inner
                    ext/inner/ok
                    ext/inner/ok/inside.txt
                    exit=0
                    ext
                    ext/escape.txt
                    ext/inner
                    ext/inner/ok
                    ext/inner/ok/inside.txt

在默认设置下，../escape.txt 因错误 Member name contains '..' 没有被解出，退出码为2。同一归档中的正常条目 ok/inside.txt 被解出。加上 -P 后以退出码0结束，ext/escape.txt 被创建在 ext/inner 的外面。这段输出直接显示了两点：一个条目被拒绝并没有阻止其余条目解包，而 -P 连 .. 检查也一并放开了。

绝对名称条目用同样的方式解包。下面的 find 只输出 abs_target.txt 所在的位置。

(cd ext/inner && tar -xf ../../craft/abs.tar)
                    find ext -name abs_target.txt | show
                    (cd ext/inner && tar -P -xf ../../craft/abs.tar)
                    find ext -name abs_target.txt | show
tar: Removing leading `/' from member names
                    ext/inner/tmp/demo/ext/abs_target.txt
                    ext/abs_target.txt
                    ext/inner/tmp/demo/ext/abs_target.txt

默认设置下，文件连同警告一起嵌套在 ext/inner/tmp/demo/ext/abs_target.txt，加上 -P 的第二次解包则在记录的绝对位置 ext/abs_target.txt 也创建了文件。总结：默认设置会去掉开头斜杠并拒绝 ..，而 -P 把两者都放开。

解包前的检查与只用一个顶层目录的惯例

第7节的两种风险可以在列表阶段筛出。下面的 grep 只挑出以斜杠开头或含有 .. 成分的名称。这个正则表达式仅用于演示，并不是tar提供的功能。

tar -tf p.tar 2>/dev/null | grep -E '^/|(^|/)\.\.(/|$)' | show | head -2
                    tar -tf craft/dotdot.tar 2>/dev/null | grep -E '^/|(^|/)\.\.(/|$)'
                    tar -tf rel.tar | grep -cE '^/|(^|/)\.\.(/|$)'
/tmp/demo/src/app/
                    /tmp/demo/src/app/bin/
                    ../escape.txt
                    0

用 -P 生成的 p.tar 因以斜杠开头的名称被筛出，dotdot.tar 因 ../escape.txt 被筛出，用相对路径生成的 rel.tar 为0条。解包前由人阅读该列表或由脚本检查，就能在触及第7节的行为之前把归档筛掉。读取列表不会创建文件，所以没有需要撤销的东西。把列表检查当作解包的预演，也出现在Shell脚本预演设计的文章中。

顶层条目有几个，同样可以从列表得知。把同样的文件分别以 bin conf data 三个名称打包的归档和只以 app 一个名称打包的归档作比较，并解包到已有文件(mine.txt)的目录里。

tar -C src/app -cf bomb.tar bin conf data
                    tar -tf bomb.tar | cut -d/ -f1 | sort -u
                    tar -C src -cf one.tar app
                    tar -tf one.tar | cut -d/ -f1 | sort -u
                    mkdir spill
                    echo keep > spill/mine.txt
                    (cd spill && tar -xf ../bomb.tar && ls)
                    mkdir clean
                    (cd clean && tar --one-top-level=out -xf ../bomb.tar && find . | sort)
bin
                    conf
                    data
                    app
                    bin
                    conf
                    data
                    mine.txt
                    .
                    ./out
                    ./out/bin
                    ./out/bin/run.sh
                    ./out/conf
                    ./out/conf/app.conf
                    ./out/data
                    ./out/data/a.txt
  • 以 bin conf data 打包的归档有三个顶层名称，解包后 bin、conf、data 混进了已有 mine.txt 的目录。
  • 只以 app 一个名称打包的归档只有一个顶层名称，所以无论解包到哪里，文件都会集中在 app 之下。
  • --one-top-level=out 是接收方使用的保护措施。手册页的说明是「Extract all files into DIR, or, if used without argument, into a subdirectory named by the base name of the archive」，输出中文件集中在 out/ 之下。
  • 打包方的惯例是用 -C 切换到上级目录，只传入一个目录名(tar -C src -cf one.tar app)。

最后是名称与已有文件重复时的默认行为。在 ow/note.txt 中写入 OLD，再解包内容为 NEW 的同名文件。手册页对 -k 的描述是「Don't replace existing files when extracting.」。

mkdir ow t1
                    echo OLD > ow/note.txt
                    echo NEW > t1/note.txt
                    tar -C t1 -cf note.tar note.txt
                    (cd ow && tar -k -xf ../note.tar; echo "exit=$?"; cat note.txt)
                    (cd ow && tar -xf ../note.tar; echo "exit=$?"; cat note.txt)
tar: note.txt: Cannot open: File exists
                    tar: Exiting with failure status due to previous errors
                    exit=2
                    OLD
                    exit=0
                    NEW

加上 -k 会出现错误 note.txt: Cannot open: File exists 和退出码2，内容仍是 OLD。不加选项解包，退出码为0，内容变成了 NEW。默认行为是不经询问直接覆盖，也没有任何提示。在可能存在同名文件的目录中解包时，新建一个空目录并用 -C 指定它，可以避免这种结果。

总结 - 打包时与解包时的顺序

  • 打包时用 -C 指定作为基准的上级目录，只传入一个目录名(tar -C 上级路径 -cf out.tar 名称)。不会出现警告，成员名以 名称/... 开头(第5节)。
  • 如果看到 Removing leading 警告，说明已经按绝对路径打包，解包该归档时应预期上级路径会被嵌套(第3、4节)。
  • 对于收到的归档，解包前用 tar -tf 读取列表，检查以斜杠开头的名称、.. 成分和顶层名称的数量(第8节)。
  • 解包时用 -C 指定新建的空目录。同名的已有文件在默认设置下会不经询问被替换(第8节)，空目录可避免这种情况。
  • -P 在解包时忽略 -C，直接写入记录的绝对位置。只在把自己的文件还原到同一位置时使用，不要用于来源不明的归档(第6、7节)。
  • Windows上的Git Bash tar与自带tar.exe在消息和退出码上不同，因此读取输出字符串的脚本应先确定使用哪个tar(第9节)。

归档文件名的编码问题不在这里讨论，zip内韩文文件名的文章连同tar没有编码声明这一点一起讨论了。把备份归档解包到临时目录检查能否恢复的步骤，见备份与恢复策略的文章。
