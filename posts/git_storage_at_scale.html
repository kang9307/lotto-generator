Git이 대규모에서 느려지는 자리 - 깊이·폭·크기는 서로 다른 문제다

객체 저장과 델타 압축이 전제한 것, 그 전제가 깨지는 지점, 그리고 덜 받는 방법들이 각각 무엇을 대신 내주는가

2026-08-28 개발/인프라

서론: 저장소가 무거워지는 방식은 하나가 아니다

새 장비에서 저장소를 받는 데 20분이 걸린다. git status 한 번에 몇 초가 흐른다. 증상은 비슷해 보이지만 원인은 전혀 다른 곳에 있을 수 있고, 그래서 남이 쓴 대책을 그대로 가져다 쓰면 대개 듣지 않는다.

이 이야기가 다시 떠오른 계기가 있다. 2026년 8월, Cursor 가 자사 Git 호스팅의 저장 계층을 다시 설계한 Continuity 를 공개했다. 회사 설명에 따르면 로컬 Git 저장소를 진실의 원천으로 두는 대신 S3 호환 객체 스토리지에 올린 선행 기록(WAL) 을 원천으로 삼고, 로컬 NVMe 디스크의 Git 저장소는 언제든 다시 만들 수 있는 캐시로 취급한다. 푸시 순서는 객체 스토리지의 원자적 비교-교환(CAS)으로 정렬한다는 것이 골자다. 같은 글에서 회사는 초당 푸시 처리량, 복제본을 100개까지 늘렸을 때의 읽기 확장, 복제본 정합성 확인 지연 같은 수치를 함께 밝혔는데, 이는 해당 회사가 자사 환경에서 측정해 발표한 값이고 하드웨어와 배치 조건은 글에 명시돼 있지 않다. 이 글에서 그 숫자를 성능 근거로 쓰지 않는 이유다.

제품 이야기는 여기까지다. 흥미로운 건 그들이 풀려던 문제 쪽이다. 왜 Git 을 대규모로 호스팅하는 일이 어렵고, 왜 거대한 단일 저장소와 수많은 작은 저장소가 정반대 방향으로 시스템을 괴롭히는가. 그 답은 특정 회사의 아키텍처가 아니라 Git 이 무엇을 전제하고 설계됐는지에 들어 있다. 아래에서는 그 전제를 따라간 다음, 전제가 깨지는 자리를 하나씩 짚는다. 도구 쪽이 궁금하다면 히스토리를 파고드는 Git 명령 정리를, 호스팅 지형 쪽이라면 Cursor 의 Git 포지 발표 분석을 옆에 두면 좋다.

1. Git이 실제로 저장하는 것 - 객체 네 종류와 내용 주소 지정

Git 을 파일 변경분(diff)의 목록으로 이해하고 있다면 절반은 틀렸다. Git 은 변경분이 아니라 스냅숏을 저장한다. 그리고 저장의 최소 단위는 파일이 아니라 객체다.

  • blob — 파일의 내용만 담는다. 파일 이름도, 권한도, 경로도 들어 있지 않다.
  • tree — 디렉터리에 해당한다. 모드·타입·이름과 대상 객체의 해시를 줄줄이 담는다. 이름은 여기 있다.
  • commit — 최상위 tree 하나, 부모 커밋들, 작성자·커미터 정보, 메시지를 담는다.
  • tag — 특정 객체를 가리키며 서명과 메시지를 붙일 수 있는 주석 태그다.

핵심은 이 객체들의 이름이 내용에서 나온다는 점이다. Git 은 타입과 길이를 담은 짧은 머리말을 내용 앞에 붙인 뒤 그 전체의 해시를 계산하고, 그 해시를 그대로 객체의 이름으로 쓴다. 저장 경로도 그 해시로 결정된다 — 앞 두 글자가 디렉터리, 나머지가 파일 이름이다. 내용은 zlib 로 압축해 넣는다.

여기서 사람들이 흔히 놀라는 성질이 나온다. 같은 내용은 저장소 안에서 한 번만 저장된다. 같은 파일이 열 군데 디렉터리에 복사돼 있어도 blob 은 하나다. 백 번의 커밋 동안 손대지 않은 파일은 백 번 저장되지 않는다. 커밋마다 tree 는 새로 만들어지지만, 바뀌지 않은 하위 tree 와 blob 은 이전 해시를 그대로 가리킨다. 중복 제거를 위한 별도 장치가 있는 게 아니라, 이름이 내용이라서 중복이 애초에 생기지 않는다.

이 설계는 조용한 대가도 낸다. 이름이 내용이므로 내용이 바뀌면 이름이 바뀐다. 커밋에는 부모 커밋의 해시가 들어 있으니, 과거 어느 지점을 고치면 그 뒤 모든 커밋의 이름이 연쇄적으로 바뀐다. 뒤에서 다룰 히스토리 재작성의 위험은 정책이 아니라 이 저장 구조에서 곧장 따라 나온다.

2. 팩파일과 델타 압축 - 묶으면 무엇이 싸지고 무엇이 비싸지는가

객체 하나가 파일 하나인 상태를 느슨한 객체(loose object) 라고 부른다. 이해하기는 쉽지만 오래 두기에는 나쁘다. 22KB 짜리 파일에 한 줄을 더해 커밋하면 내용이 거의 같은 22KB 짜리 객체가 하나 더 생기고, 둘은 각자 압축돼 각자 자리를 차지한다.

그래서 Git 은 객체가 일정 수준 이상 쌓이거나 git gc 를 돌리거나 원격에 푸시할 때 객체들을 팩파일 하나로 묶는다. 이때 비슷한 객체끼리 델타 압축이 붙는다. 앞의 예에서 새 버전은 통째로 저장되고, 이전 버전은 새 버전을 가리키는 몇 바이트짜리 차이만 남는다. Git Book 의 예시에서는 22,054 바이트 객체가 온전히 저장되고 22,044 바이트 객체는 9 바이트의 델타로 줄었다.

방향에 주목할 만하다. 최신 버전을 온전히 두고 과거를 델타로 만든다. 최근 것을 가장 자주 꺼내 보는 실제 사용 양상에 맞춘 선택이다. 대가는 명확하다.

  • 델타로 저장된 객체를 읽으려면 사슬을 거슬러 올라가 복원해야 한다. 읽기가 순수한 파일 읽기에서 계산이 섞인 작업으로 바뀐다.
  • 그래서 Git 은 델타 사슬의 깊이를 제한한다. 무한정 길어지면 디스크는 줄지만 읽기가 느려지기 때문이다.
  • 델타 상대를 찾는 일 자체가 CPU와 메모리를 쓴다. 큰 저장소의 리패킹이 무거운 이유가 여기 있다.
  • 팩파일 안의 객체 배치는 논리적 인접성을 따르므로, 접근 패턴이 디스크 위에서는 흩어진 읽기가 되기 쉽다.

정리하면 팩파일은 용량과 전송량을 CPU와 임의 접근으로 바꾸는 거래다. 대부분의 저장소에서 이 거래는 압도적으로 남는 장사다. 문제는 저장소가 커지면서 거래의 양쪽이 함께 커진다는 데 있다.

3. 커진다는 말은 세 가지다 - 깊이·폭·크기

여기가 이 글의 중심이다. 저장소가 크다는 한 마디 안에는 독립적인 세 축이 섞여 있다. 셋은 원인이 다르고 증상이 다르고, 무엇보다 대책이 다르다.

  • 히스토리 깊이 — 커밋과 그에 딸린 tree 객체의 누적 개수. 10년 된 저장소는 파일이 몇 개든 깊다.
  • 트리 폭 — 한 커밋이 담는 파일과 디렉터리의 개수. 어제 만든 저장소도 파일이 50만 개면 넓다.
  • 파일 크기 — 개별 객체의 덩치. 압축과 델타가 잘 듣는지가 여기서 갈린다.
축무엇이 느려지는가주로 듣는 대책그 대책이 내주는 것
히스토리 깊이초기 clone, 도달성 계산, 리비전 순회, 서버 협상shallow clone, 커밋 그래프 캐시, 필요시 히스토리 분리과거를 묻는 작업(로그·blame·bisect)이 막히거나 재요청을 부른다
트리 폭체크아웃, 상태 확인, 인덱스 갱신, 브랜치 전환sparse-checkout, 파일시스템 감시, 희소 인덱스도구 호환성·운영 복잡도, 그리고 범위 밖을 건드릴 때의 혼란
파일 크기전송량, 디스크, 팩 시간, 메모리대용량 파일 외부화(LFS 등), 애초에 넣지 않기별도 저장소 운영·인증·백업, 그리고 도구 체인 의존

세 축을 섞으면 진단이 어긋난다. clone 이 느리다고 --depth 1 을 붙였는데 여전히 느리다면 깊이가 아니라 폭이나 크기 문제였을 가능성이 높다. 커밋 수는 적은데 한 커밋에 파일이 40만 개라면, 깊이를 잘라도 받아야 할 tree 와 blob 의 양은 그대로다. 반대로 파일 수가 적은데 clone 이 무겁다면 히스토리 어딘가의 큰 바이너리부터 의심한다.

판단 기준은 단순하다. 어느 축이 지배적인지 하나를 고르고, 그 축의 대책만 적용한 뒤 다시 측정한다. 셋을 한꺼번에 걸면 무엇이 들었는지도, 문제가 생겼을 때 무엇을 되돌려야 하는지도 알 수 없다.

4. 큰 바이너리가 특히 나쁜 이유

텍스트 소스 코드는 Git 이 가장 잘하는 대상이다. 줄 단위로 조금씩 바뀌고, 압축이 잘 듣고, 델타가 아주 잘 듣는다. 큰 바이너리는 정확히 그 반대편에 있다.

  • 델타가 잘 듣지 않는다. 이미 압축된 형식(이미지·동영상·아카이브)은 한 픽셀만 바뀌어도 바이트 배열 전체가 달라진다. 새 커밋마다 사실상 새 파일 하나가 통째로 들어간다.
  • 압축도 잘 듣지 않는다. 압축된 것을 다시 압축하면 거의 줄지 않는다. 팩파일의 이점 하나가 사라진다.
  • 메모리를 크게 요구한다. 객체 하나를 다루는 작업 공간이 파일 크기에 비례해 늘어난다.
  • 한 번 들어가면 남는다. 다음 커밋에서 지워도 그 blob 은 과거 커밋에 도달 가능한 상태로 남아 있다. clone 하는 모든 사람이 계속 받는다.

마지막 항목이 가장 비싸다. 실수로 커밋된 500MB 짜리 빌드 산출물은 다음 커밋에서 삭제한다고 사라지지 않는다. 삭제 커밋은 그 파일이 없는 새 tree 를 만들 뿐이고, 이전 커밋은 여전히 그 blob 을 가리킨다. 저장소에서 진짜로 빼려면 과거를 다시 쓰는 수밖에 없다. 그 대가는 뒤에서 따로 다룬다.

그래서 대용량 자산에는 포인터로 바꿔 외부에 두는 접근이 널리 쓰인다. Git LFS 가 대표적인데, 커밋에는 가벼운 포인터 파일만 들어가고 실제 내용은 별도 저장소에 놓인다. 저장소는 가벼워진다. 대신 확장 기능 설치가 전제되고, 별도 저장소의 인증·용량·백업을 따로 운영해야 하며, 그 저장소가 사라지면 포인터만 남는다. 무게가 사라진 게 아니라 옮겨 간 것이다.

5. 덜 받는 세 가지 방법 - 각각 무엇을 받지 않는가

대규모 저장소 대책의 상당수는 덜 받기로 요약된다. 다만 셋은 서로 다른 것을 덜 받고, 미룬 값은 대개 나중에 청구된다.

방법받지 않는 것나중에 무엇이 느려지는가같이 봐야 할 것
shallow clone(--depth)지정한 깊이 밖의 과거 커밋과거를 묻는 작업. 필요해지면 히스토리를 더 받아야 한다기본적으로 단일 브랜치로 좁혀진다
partial clone(--filter)blob 전부 또는 일정 크기 이상, 설정에 따라 tree 까지누락 객체가 필요한 순간의 즉시 인출. 문서는 이 인출이 느린 편이라고 적는다원격이 살아 있어야 하고, 인증이 여러 번 일어날 수 있다
sparse-checkout아무것도 덜 받지 않는다. 작업 트리에 펼칠 경로만 좁힌다범위를 넓히는 순간, 그리고 범위 밖 변경을 다룰 때cone 모드 권장. 비-cone 패턴 방식은 문서에서 권장되지 않는다

세 번째 줄이 자주 오해받는다. sparse-checkout 은 다운로드 절감 기능이 아니다. 인덱스의 skip-worktree 비트로 작업 트리에 파일을 펼치지 않을 뿐, 객체는 이미 받아 둔 상태다. 다운로드까지 줄이려면 partial clone 과 함께 써야 하고, 그때는 그쪽 대가가 따라온다. Git 문서는 이 명령이 실험적이며 동작이 바뀔 수 있다고 밝히고, 희소 인덱스가 외부 도구가 이해하지 못하는 방식으로 인덱스를 바꾼다는 주의도 함께 적는다.

partial clone 문서가 적어 둔 주의도 그대로 읽을 값어치가 있다. 누락 객체는 필요할 때 약속자 원격(promisor remote) 에서 가져오는데, 항목마다 인출이 일어나 객체가 많으면 상당한 오버헤드와 여러 번의 인증 요청을 부른다. 오프라인 작업 성격이 약해지고, 네트워크가 나쁜 자리에서는 초기 clone 이 빨라진 대신 일상 작업이 불규칙하게 멈춘다.

6. 서버 쪽에서 보이는 것 - 참조 개수, 협상, 리패킹

클라이언트에서만 보면 놓치는 축이 있다. 참조(ref) 개수다. 브랜치와 태그는 해시 하나를 담은 작은 항목이라 용량으로는 무시할 만하다. 비용은 다른 데서 나온다.

  • 참조 광고 — 구 프로토콜에서는 연결할 때마다 서버가 가진 참조를 모두 보냈다. partial clone 문서도 참조가 많으면 이 부분에서 상당한 오버헤드가 생길 수 있다고 적는다.
  • 협상 — 클라이언트와 서버는 무엇을 이미 갖고 있는지 주고받으며 보낼 객체를 정한다. 참조와 커밋이 많을수록 이 왕복이 무거워진다.
  • 도달성 계산 — 어떤 객체가 살아 있는지는 참조에서 출발해 그래프를 훑어야 안다. 정리(gc)와 리패킹의 실제 비용이 여기 있다.

프로토콜 v2 는 이 중 첫 번째를 정면으로 손봤다. 참조 광고를 요청하지 않으면 생략하고, ls-refs 에 ref-prefix 를 붙여 필요한 접두사의 참조만 받도록 했다. 그래서 브랜치를 방치하면 clone 이 느려진다는 오래된 경험칙은 오늘날 조건부다. 양쪽이 v2 로 동작하면 광고 비용은 크게 줄지만, 도달성 계산과 리패킹 부담은 그대로 남는다.

운영 관점에서 더 흥미로운 건 정반대의 두 부하가 같은 시스템에 동시에 온다는 점이다. 한쪽 끝에는 수백 개의 복제본으로 CI 를 감당해야 하는 거대한 단일 저장소가 있고, 다른 쪽 끝에는 자동화가 만들어 낸, 몇 번 쓰이고 잊히는 작은 저장소가 수없이 쌓인다. 앞쪽은 읽기 확장을 요구하고 뒤쪽은 저장소 하나당 고정 비용이 0에 가까울 것을 요구한다. Continuity 공개 글이 다루는 문제도 결국 이 두 방향의 동시 요구였다. Git 을 라이브러리로 다시 쓰려는 시도가 나오는 배경에도 비슷한 압력이 있다.

7. 파일시스템과 상태 확인 - 파일 수에 비례하는 일

git status 가 느린 저장소는 대개 히스토리가 아니라 폭이 문제다. Git 은 작업 트리가 인덱스와 어긋났는지 알기 위해 파일들의 상태를 확인해야 하고, 이 확인은 기본적으로 파일 개수에 비례한다. 파일이 수십만 개면 아무 일도 하지 않은 상태에서도 확인 자체가 일이 된다.

Git 은 이 비용을 줄이는 장치를 두 가지 갖고 있다.

  • 추적되지 않은 파일 캐시 — 디렉터리의 수정 시각을 기록해 두고, 그 시각이 그대로면 안을 다시 읽지 않는다. 운영체제와 파일시스템이 디렉터리의 수정 시각을 제대로 갱신해 주어야 성립하므로, Git 은 이를 미리 시험해 보는 방법을 함께 제공한다.
  • 파일시스템 감시 — 외부 감시자에게 무엇이 바뀌었는지 물어, 모든 파일을 일일이 확인하는 일 자체를 없앤다. 둘을 함께 켜면 변경 탐지와 새 파일 탐색을 모두 건너뛸 수 있다.

다만 문서가 붙여 둔 단서를 같이 읽어야 한다. 모든 명령이 이 표시를 존중하지는 않는다. 어떤 명령은 빨라지고 어떤 명령은 그대로다. 상시 감시 프로세스가 하나 더 생기는 것도 비용이고, 네트워크 파일시스템이나 컨테이너 안에서는 전제 조건 자체가 흔들릴 수 있다.

8. 모노리포와 멀티리포는 답이 아니라 선택

저장소가 무거워지면 구조를 바꾸자는 이야기가 나온다. 그런데 이 결정은 성능 문제라기보다 비용을 어디로 옮길지에 대한 결정이다. 어느 쪽도 총량을 줄여 주지 않는다.

관점모노리포에서 일어나는 일멀티리포에서 일어나는 일
변경 단위여러 모듈을 한 커밋으로 원자적으로 바꾼다저장소 경계마다 변경이 쪼개지고 순서를 사람이 맞춘다
의존성하나의 그래프. 버전 정합 문제가 줄어든다버전 고정과 배포 순서가 상시 업무가 된다
Git 부하폭과 참조 개수가 한곳에 모인다. 도구 투자가 필수가 된다저장소 하나하나는 가볍다. 대신 저장소 수 자체가 관리 대상이 된다
권한경로 단위 접근 제어를 별도 계층에서 풀어야 한다저장소 단위로 자연스럽게 갈린다
빌드·CI영향 범위 계산이 필수. 안 하면 매 변경이 전체 빌드가 된다빌드는 단순하지만 통합 검증 자리가 사라진다
릴리스한 지점에서 전체 상태를 특정할 수 있다여러 태그의 조합으로 상태를 재구성해야 한다

어느 쪽도 권하지 않겠다. 대신 판단 기준을 하나 두자면, 변경의 모양을 보라. 하나의 기능 변경이 습관적으로 세 개 이상의 저장소를 동시에 건드린다면, 저장소 경계가 실제 결합도와 어긋나 있다는 신호다. 그때 저장소를 합치는 것은 선택지 중 하나일 뿐이고, 경계를 다시 긋거나 인터페이스를 안정시키는 쪽이 먼저일 때가 많다. 반대로 각 저장소가 독립적으로 배포되고 서로의 내부를 모른다면, 합쳐서 왼쪽 열 비용을 새로 떠안을 이유가 없다. 분기 방식 자체도 팀 규모와 릴리스 주기에 따라 값이 달라지는데, 그쪽은 브랜치 전략 정리에서 따로 다뤘다.

9. 히스토리를 줄이는 일의 위험

이 절은 방법 안내가 아니다. 착수 전에 알아야 할 것을 적는다.

1절에서 본 성질이 여기서 값을 청구한다. 객체 이름이 내용에서 나오므로, 과거의 어느 커밋을 고치면 그 뒤 모든 커밋의 해시가 바뀐다. git filter-branch 문서는 이를 명시적으로 경고한다. 재작성된 히스토리는 모든 객체에 대해 다른 이름을 갖게 되며 원래 브랜치와 합류하지 않는다는 것이다. 같은 문서는 이 명령 자체에 대해서도 함정이 많고 성능이 나쁘다며 git filter-repo 같은 대체 도구를 쓰라고 권한다.

실제로 무엇이 깨지는지 목록으로 두는 편이 낫다.

  • 서명 — 커밋 서명은 그 커밋의 내용에 대한 서명이다. 내용이 바뀌면 검증이 통과하지 않는다.
  • 태그 — 옛 커밋을 가리키던 태그는 새 히스토리 밖을 가리키게 된다. 함께 옮기지 않으면 옛 그래프가 참조로 살아남는다.
  • 외부에 박힌 해시 — 이슈 트래커·배포 기록·문서·잠금 파일에 적힌 커밋 해시가 전부 가리키는 곳을 잃는다.
  • 동시 작업자 — 문서는 협업자가 자기 변경을 새 히스토리 위로 다시 얹거나 저장소를 지우고 다시 받아야 한다고 적는다. 사람 수만큼 사고 가능성이 늘어난다.
  • 자동화 — 커밋 해시를 캐시 키나 배포 식별자로 쓰는 파이프라인은 조용히 다른 것을 가리키기 시작한다.

그래서 최소 전제는 이렇다. 완전한 복제본으로 먼저 예행하고, 작업 전 상태를 별도로 보존하고, 재작성이 이뤄지는 동안 아무도 쓰기를 하지 않도록 창구를 닫고, 끝난 뒤 모두가 어떻게 다시 받을지를 미리 합의한다. 되돌리기 경로가 없으면 착수하지 않는다. 그리고 이 작업의 유일한 정당한 이유는 대개 셋 중 하나다 — 비밀 정보가 들어갔거나, 법적 삭제 의무가 있거나, 다른 방법으로는 손댈 수 없는 크기의 자산이 박혀 있거나. 단순히 저장소를 가볍게 하고 싶다는 이유라면, 앞 절들의 덜 받기 대책을 먼저 다 써 보는 편이 낫다.

10. 무엇을 측정할 것인가

느리다는 인상만으로는 축을 고를 수 없다. 볼 것은 총 시간이 아니라 시간이 어느 단계에서 쓰이는가다.

  • clone 의 단계 분해 — 서버가 객체를 세고 압축하는 시간, 전송 시간, 받은 뒤 풀고 인덱싱하는 시간, 마지막 체크아웃 시간은 완전히 다른 원인을 가리킨다. 전송이 짧은데 총 시간이 길면 문제는 네트워크가 아니다.
  • 체크아웃과 상태 확인 — 이 둘만 유독 느리면 폭이 지배적이다.
  • 객체 구성 — 팩 안에서 어떤 객체가 자리를 차지하는지, 큰 blob 이 몇 개 있는지, 그것이 어느 경로에서 왔는지.
  • 참조와 커밋의 개수 — 협상이 무거운지 판단하는 첫 지표다.
  • 작업 트리 파일 수 — 폭 축의 가장 단순한 대리 지표다.
  • 재현 조건 — 캐시가 데워진 상태와 차가운 상태를 구분하지 않으면 비교가 성립하지 않는다.

대책을 넣은 뒤에도 같은 자리를 다시 잰다. 한 번에 하나씩 바꾸고, 바꾼 것과 잰 것을 남긴다. 기록이 없으면 반년 뒤 누군가가 같은 문제를 처음부터 다시 진단한다.

확인하지 못한 것

  • Continuity 공개 글에 실린 처리량·지연 수치의 측정 조건(하드웨어, 객체 크기 분포, 동시성 수준)은 글에 명시돼 있지 않아 확인하지 못했다. 본문에서 이 수치를 비교나 근거로 쓰지 않은 이유다.
  • 같은 글이 다른 시스템의 설계를 설명한 부분 역시 공개한 쪽의 서술이며, 그 시스템 운영 주체의 자료로 교차 확인하지 못했다.
  • 덜 받기 대책들이 실제로 몇 퍼센트를 줄여 주는지는 저장소마다 편차가 커서 일반화할 수치를 제시하지 않는다.
  • 파일시스템 감시가 어떤 명령에서 효과가 있고 어떤 명령에서 없는지는 버전·플랫폼에 따라 달라, 쓰는 Git 버전의 문서에서 직접 확인해야 한다.

정리

Git 은 내용으로 이름을 짓는 객체 저장소다. 그 전제 덕분에 중복이 저절로 사라지고, 그 전제 때문에 과거를 고치면 그 뒤가 전부 바뀐다. 팩파일과 델타 압축은 용량을 CPU와 임의 접근으로 바꾸는 좋은 거래지만, 저장소가 커지면 거래의 양쪽이 함께 자란다.

가져갈 것은 세 가지다. 첫째, 커진다는 말을 깊이·폭·크기로 쪼개라. 대책은 축마다 다르고, 축을 잘못 짚으면 아무것도 나아지지 않는다. 둘째, 덜 받는 방법들은 비용을 없애지 않고 미룬다. 미룬 값이 언제 어떤 모양으로 돌아오는지를 알고 선택해야 한다. 셋째, 히스토리 재작성은 마지막 수단이며, 되돌리기 경로와 합의 없이 시작할 일이 아니다.

구조 선택도 마찬가지다. 모노리포와 멀티리포는 성능 처방이 아니라 비용의 위치를 바꾸는 선택이고, 근거는 유행이 아니라 우리 변경이 실제로 어떤 모양인지다. 다음에 저장소가 무겁다는 말이 나오면, 대책을 고르기 전에 어느 축인지부터 한 문장으로 답해 보자.
