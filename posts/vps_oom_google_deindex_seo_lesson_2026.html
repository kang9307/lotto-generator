월 6달러 VPS의 교훈 - OOM 503 에러가 부른 구글 디인덱싱

Lessons from a $6 VPS - How OOM 503 Errors Led to Google Deindexing

2026-06-10 IT/기술

서론: 6달러짜리 서버가 검색에서 사라지던 날

월 6달러. 커피 한두 잔 값으로 빌린 최소 사양 VPS 위에, 바이브 코딩으로 뚝딱 만든 주식 스크리너가 돌아가고 있었습니다. 처음 몇 주는 평화로웠습니다. 검색에서도 조금씩 노출되기 시작했고, 작은 사이트가 자기 자리를 찾아가는 듯했습니다. 그러다 어느 날 트래픽이 조금 늘자 사이트가 간헐적으로 먹통이 되더니, 브라우저에 503 Service Unavailable이 뜨기 시작했습니다. 며칠 뒤, 구글 검색 결과에서 페이지들이 조용히 사라졌습니다. 디인덱싱이었습니다.

이 글은 최근 개발자 커뮤니티에서 회자된 한 운영자의 경험담 — 저사양 VPS의 메모리 부족(OOM)이 반복된 503을 낳고, 그 503이 구글 디인덱싱으로 이어진 사건 — 을 출발점 삼아, 왜 이런 일이 일어나는지를 운영과 SEO 두 축에서 차분히 해부합니다. 그저 '서버를 키워라'로 끝나는 이야기가 아닙니다. 메모리·스왑·OOM killer가 어떻게 맞물리는지, 503이 검색엔진에는 왜 그토록 위험한 신호인지, 그리고 같은 6달러 예산에서도 사고를 피하는 설계와 사고 후 복구 방법까지를 실무 교훈으로 정리하겠습니다. 작은 사이트일수록, 이 메커니즘을 아느냐 모르느냐가 생존을 가릅니다.

1. 무슨 일이 있었나 - 사건의 타임라인

먼저 사건을 시간 순으로 재구성해 보겠습니다. 세부는 다를 수 있지만, 저사양 VPS에서 반복적으로 관찰되는 전형적인 붕괴 패턴입니다.

  • 1단계 — 출시: 1 vCPU, 1GB 안팎의 최소 사양 VPS에 애플리케이션을 올립니다. 스왑은 설정하지 않았고, 리소스 한계도 따로 두지 않았습니다.
  • 2단계 — 잠복: 트래픽이 적을 때는 멀쩡합니다. 메모리가 빠듯하긴 해도 터지지 않는 수준이라 문제를 체감하지 못합니다.
  • 3단계 — 방아쇠: 검색 노출이나 외부 링크로 동시 접속이 늘면, 애플리케이션이 요청마다 메모리를 더 쓰면서 RAM이 한계에 닿습니다.
  • 4단계 — OOM: 스왑마저 없으니 커널이 메모리를 더 줄 수 없고, OOM killer가 가장 무거운 프로세스(대개 웹 앱)를 강제 종료합니다. 서버는 살아 있지만 앱은 죽습니다.
  • 5단계 — 503 반복: 앱이 죽은 동안 리버스 프록시는 백엔드에 연결하지 못해 503을 반환합니다. 재시작과 죽음이 반복되며 503이 간헐적으로 계속 뜹니다.
  • 6단계 — 크롤러 후퇴: Googlebot이 방문할 때마다 503을 마주치자 크롤 빈도를 낮춥니다.
  • 7단계 — 디인덱싱: 503이 며칠 이상 이어지자 구글은 해당 URL을 접근 불가로 판단해 색인에서 제거합니다.

핵심은 단일 원인이 아니라 연쇄라는 점입니다. 메모리 부족이라는 인프라 문제가 503이라는 HTTP 신호로 번역되고, 그 신호가 검색엔진의 신뢰 판단으로 이어집니다. 한 고리만 끊어도 디인덱싱까지는 가지 않습니다.

2. 메모리 부족의 해부 - RAM, 스왑, OOM killer

왜 앱이 '죽는지'를 이해하려면 리눅스가 메모리를 다루는 방식을 알아야 합니다. 자료를 종합하면, 리눅스의 사용 가능 메모리는 세 층으로 이뤄집니다.

구성 역할 고갈 시
물리 RAM 실제 빠른 메모리. 활성 데이터를 담음 가장 먼저 압박
페이지 캐시 파일 기반 데이터 캐시 회수 가능, 먼저 비워짐
스왑(Swap) 비활성 페이지를 디스크로 내보내는 완충 여기까지 차면 OOM 임박

스왑은 안전망입니다. 순간적인 메모리 급증이나 백그라운드 사용량을 흡수해 주고, 메모리 누수나 설정 실수에 대응할 시간을 벌어 줍니다. 문제의 VPS에 스왑이 없었다는 점은 그래서 치명적이었습니다. 완충이 통째로 빠진 셈입니다.

2.1 OOM killer는 언제, 무엇을 죽이나

OOM killer는 물리 메모리와 스왑이 모두 고갈되어 할당 요청을 만족시킬 수 없을 때 커널이 발동하는 마지막 방어선입니다. 메모리가 완전히 0이 될 때까지 기다리지 않고, 할당을 충족할 수 없다고 판단하면 선제적으로 작동합니다. 대상 선정은 각 프로세스의 badness 점수로 정합니다. 메모리 사용량, 실행 시간, 권한, nice 값, 그리고 oom_score_adj 조정값을 종합해 가장 높은 점수의 프로세스를 종료합니다.

또 하나의 규칙은 '자식 우선 희생(sacrifice child)'입니다. 부모와 자식 프로세스 중에서는 자식을 먼저 죽여 핵심 부모를 살립니다. 워커를 띄우는 웹 서버 구조에서, 메모리를 많이 쓰는 워커가 표적이 되는 이유가 여기에 있습니다. 운영자는 /proc/<pid>/oom_score_adj(-1000은 절대 죽이지 않음, +1000은 먼저 죽임)로 어떤 프로세스를 보호할지 어느 정도 조절할 수 있습니다.

# OOM 발생 흔적 확인 (dmesg)
$ dmesg | grep -i -E "killed process|out of memory"
[12345.678] Out of memory: Killed process 813 (gunicorn) ...

# 현재 메모리/스왑 상태
$ free -h
              total   used   free  shared  buff/cache  available
Mem:          957Mi  812Mi   72Mi    8Mi       72Mi        41Mi
Swap:            0B     0B     0B   <-- 스왑 없음: 완충 부재

# 특정 프로세스 보호 (예: 절대 죽이지 않기 직전 수준)
$ echo -900 > /proc/$(pgrep -o nginx)/oom_score_adj

위 free -h 출력에서 Swap: 0B가 보이면, 이 서버는 메모리 급증을 흡수할 완충이 전혀 없다는 뜻입니다. available이 수십 MB까지 떨어진 상태라면 OOM은 시간문제입니다.

3. 503은 왜 SEO에 치명적인가

이제 인프라에서 검색으로 넘어갑니다. 흥미롭게도 503 자체는 나쁜 응답이 아닙니다. 구글에게 503은 '지금은 안 되니 잠시 후 다시 오라'는 일시적 신호이며, 올바르게 쓰이면 SEO에 해롭지 않습니다. Googlebot은 503을 만나면 페이지가 사라졌다고 단정하지 않고, 시간을 두고 다시 크롤하려 합니다. 합리적인 선에서 인내심을 갖도록 설계되어 있습니다.

문제는 지속 시간과 반복입니다. 구글 지원 커뮤니티의 가이드를 종합하면 대략 다음과 같은 임계가 거론됩니다.

  • 24시간 이내: 일반적으로 안전. 10~15분 단위의 간헐적 503은 '장기적'으로 보지 않습니다.
  • 1~7일: 모니터링하면 위험은 최소화되지만, 크롤 빈도는 줄기 시작합니다.
  • 7일 초과: 디인덱싱 위험 구간. 구글이 해당 URL을 사실상 영구 접근 불가로 간주할 수 있습니다.
503은 하루치 감기라면 괜찮지만, 몇 주를 끄는 만성 질환이 되면 구글은 그 사이트를 '믿을 수 없는 곳'으로 학습한다.

특히 사건의 케이스처럼 불규칙하게 반복되는 503은 단순한 점검보다 더 나쁩니다. 크롤러 입장에서는 '이 사이트는 언제 살아 있을지 알 수 없다'는 지속적 불안정으로 읽히고, 이는 크롤 압력을 장기적으로 낮추도록 학습시키는 가장 빠른 길입니다. 그 결과는 발견 지연, 갱신 지연, 사이트 전반의 재크롤 주기 둔화로 번집니다.

3.1 5xx가 색인에 미치는 직접 효과

구글 입장에서 5xx 페이지는 색인 자체가 불가능합니다. 검색 결과에 나타날 수 없고, 잦은 5xx는 사이트가 불안정하다는 신호가 되며, 실패한 요청에 크롤 예산이 낭비됩니다. Googlebot은 5xx를 많이 만나면 사이트를 압박하지 않으려 크롤 빈도를 낮춥니다. 작은 사이트일수록 크롤 예산이 빠듯하므로, 503에 예산을 까먹는 것은 곧 정상 페이지의 색인 기회를 잃는 것과 같습니다.

4. 결정적 한 끗 - Retry-After 헤더

같은 503이라도 Retry-After 헤더가 있느냐 없느냐가 운명을 가릅니다. 서버는 503 응답에 Retry-After로 '언제 준비되는지'를 초 단위나 HTTP 날짜로 알려줄 수 있습니다. 이 헤더가 있으면 Googlebot은 페이지를 사라진 것으로 보지 않고, 명시된 시점에 맞춰 크롤을 다시 예약합니다.

# 의도된 점검 시 올바른 503 응답 (예: 2분 뒤 재시도 요청)
HTTP/1.1 503 Service Unavailable
Retry-After: 120
Content-Type: text/html

<!-- nginx에서 점검 페이지를 503 + Retry-After로 내려보내는 예 -->
location / {
    return 503;
}
error_page 503 @maintenance;
location @maintenance {
    add_header Retry-After 120 always;
    # 정적 점검 안내 페이지
    try_files /maintenance.html =503;
}

다만 주의할 점은, 사건의 케이스에서 발생한 503은 의도된 점검이 아니라 OOM으로 인한 비정상 503이었다는 것입니다. 이런 경우 리버스 프록시가 Retry-After를 붙여 줄 여유조차 없이 백엔드가 죽어 있는 경우가 많습니다. Retry-After는 계획된 점검에는 훌륭한 안전장치지만, 근본 원인인 OOM을 해결하지 않는 한 만병통치약이 아닙니다.

5. 예방책 - 6달러 예산을 지키면서 503을 없애기

핵심 질문은 '서버를 키워라'가 아니라 '같은 예산에서 어떻게 안정시키나'입니다. 비용 순으로 정리하면 다음과 같습니다.

5.1 스왑부터 — 가장 싸고 즉효

스왑이 없다면 가장 먼저, 무료로 할 수 있는 일이 스왑 추가입니다. 1GB RAM이라면 1~2GB 스왑이 순간 급증을 흡수해 OOM killer 발동을 늦춰 줍니다. 디스크 기반이라 느리지만, '앱이 죽는 것'보다는 '잠깐 느린 것'이 훨씬 낫습니다.

# 2GB 스왑 파일 생성·활성화
$ sudo fallocate -l 2G /swapfile
$ sudo chmod 600 /swapfile
$ sudo mkswap /swapfile && sudo swapon /swapfile

# 웹 워크로드에 맞춘 스왑 성향 조정 (RAM 우선, 스왑은 나중)
$ sudo sysctl vm.swappiness=10

참고로 swappiness는 스왑을 얼마나 적극적으로 쓸지를 정하는데, VPS 웹 워크로드에서는 10~20 정도가 권장됩니다. RAM을 우선 쓰고 스왑은 나중에 동원해 디스크 I/O 부담을 줄입니다.

5.2 애플리케이션의 메모리 한계와 워커 수 제한

두 번째는 앱이 RAM을 넘어서지 않도록 한계를 명시하는 것입니다. 1GB 서버에서 워커를 무한정 띄우면 동시 요청이 늘 때 메모리가 폭발합니다. 워커 수를 RAM에 맞춰 보수적으로 고정하고, 컨테이너라면 메모리 한계와 재시작 정책을 둡니다.

  • 워커 수 고정: 1GB RAM이면 워커 2~3개처럼 메모리 예산 안에서 상한을 둡니다.
  • 프로세스당 메모리 한계: 누수가 누적되기 전에 워커를 주기적으로 재기동(max-requests 등)합니다.
  • cgroup/컨테이너 한계: 한 프로세스의 폭주가 시스템 전체를 끌어내리지 않도록 격리합니다.

5.3 헬스체크와 자동 재시작

앱이 죽었을 때 스스로 살아나게 만드는 것이 503 지속 시간을 줄이는 핵심입니다. 프로세스 관리자(systemd, supervisor 등)에 자동 재시작을 걸고, 리버스 프록시에는 헬스체크를 두어 죽은 백엔드로 트래픽을 보내지 않게 합니다. 죽음과 재시작이 빨라질수록 크롤러가 503을 마주칠 확률이 낮아집니다.

5.4 CDN과 정적화 — 원본 부하를 80~95% 흡수

읽기 위주의 사이트라면 CDN 캐시가 가장 효과적인 방패입니다. 자료에 따르면 CDN은 읽기 트래픽의 80~95%까지 흡수해, 본래라면 503을 유발했을 원본 서버 압력을 크게 줄입니다. 30~60초의 짧은 TTL만으로도 트래픽 급증 시 백엔드 부하가 극적으로 떨어집니다. 정적으로 만들 수 있는 페이지를 미리 빌드해 두면, 동적 서버가 흔들려도 CDN이 '마지막 정상 버전'을 계속 내줍니다. 사이트의 응답 성능을 끌어올리는 더 넓은 맥락은 UUID 기본 키와 SQLite 성능 같은 데이터 계층 최적화와도 이어집니다.

5.5 503 대신 graceful degradation

가장 성숙한 해법은 실패를 우아하게 낮추는(graceful degradation) 설계입니다. 동적 앱이 과부하로 응답하지 못할 때 503을 뱉는 대신, 캐시된 정적 버전을 읽기 전용으로 내주는 것입니다. CI/CD가 실패하거나 원본 저장소에 장애가 나도, CDN이 마지막 정상 스냅샷을 살려 두어 '가용성 완충'을 제공합니다. 사용자에게는 약간 오래된 페이지가 보일지언정, 크롤러에게는 200 응답이 돌아갑니다. 503을 200으로 바꾸는 것 — 이것이 디인덱싱을 막는 가장 본질적인 전환입니다. 이러한 안정적 운영 사고방식은 SRE에서의 AI와 신뢰성 운영의 원칙과도 맞닿아 있습니다.

6. 복구 방법 - 디인덱싱된 사이트 되살리기

이미 디인덱싱이 일어났다면? 순서가 중요합니다. 원인을 먼저 고치고, 그다음 구글에 알려야 합니다. 거꾸로 하면 재크롤 때 또 503을 만나 신뢰가 더 깎입니다.

  1. 근본 원인 해결: 위의 예방책(스왑·워커 제한·헬스체크·CDN)으로 503을 먼저 멈춥니다. 서버가 안정적으로 200을 반환하는지 확인합니다.
  2. 오류 클러스터 확인: Search Console의 색인 생성 보고서에서 '서버 오류(5xx)'로 묶인 URL 클러스터를 찾습니다.
  3. 핵심 페이지 색인 요청: URL 검사 도구로 중요한 페이지부터 색인을 요청해 재크롤을 앞당깁니다.
  4. 수정 사항 확인: 오류 클러스터에서 '수정 사항 확인(Validate Fix)'을 눌러 구글이 재크롤·재검증하도록 유도합니다.
  5. 모니터링: 크롤 통계 보고서에서 5xx 비율과 응답 시간이 정상화되는지 지켜봅니다. 검증은 보통 며칠에서 약 2주, 길면 그 이상 걸리며 결과는 이메일로 통지됩니다.

회복은 가능하지만 즉시는 아닙니다. 사이트 규모·인기·503이 지속된 기간에 따라 재크롤이 다시 올라오는 속도가 달라집니다. 길게 방치할수록 회복도 더디므로, 이상 신호를 빨리 잡는 모니터링 자체가 최선의 보험입니다.

7. 소규모 사이트 운영자를 위한 교훈

이 사건이 작은 사이트 운영자에게 남기는 교훈을 정리하면 이렇습니다.

  • 저사양은 죄가 아니지만, 무방비는 죄다. 6달러 VPS도 스왑·워커 제한·헬스체크만 갖추면 충분히 견딥니다. 문제는 사양이 아니라 완충의 부재였습니다.
  • 인프라 장애는 SEO 장애로 번역된다. 메모리 부족은 개발자만의 문제가 아닙니다. 503을 거쳐 검색 가시성으로, 곧 트래픽과 수익으로 직결됩니다.
  • 200을 지키는 것이 모든 SEO의 토대다. 콘텐츠·키워드·백링크 이전에, 크롤러가 방문할 때 사이트가 살아 있어야 합니다. graceful degradation으로 503을 200으로 바꾸는 설계가 가장 본질적입니다.
  • 모니터링 없는 운영은 눈 감고 운전하기다. Search Console 알림과 간단한 업타임 모니터만 있어도 디인덱싱 전에 손을 쓸 수 있었습니다.
  • 바이브 코딩의 사각지대는 운영이다. AI로 기능을 빨리 만드는 것과, 그것을 안정적으로 운영하는 것은 다른 역량입니다. 데이터 계층의 내구성 설계는 PostgreSQL 기반 내구성 워크플로처럼 별도의 고민을 요구합니다.

결론: 503을 200으로 바꾸는 설계가 SEO의 시작

월 6달러 VPS의 디인덱싱 사건은 화려한 해킹이나 알고리즘 페널티가 아니라, 메모리 한 칸이 모자라 시작된 연쇄의 결과였습니다. RAM이 차고, 스왑이 없어 OOM killer가 앱을 죽이고, 죽은 앱이 503을 뱉고, 반복된 503이 크롤러의 신뢰를 깎아 끝내 색인에서 사라졌습니다. 다행히 이 연쇄는 어느 고리에서든 끊을 수 있습니다.

마지막으로 오늘 바로 점검할 세 가지로 마무리합니다.

  1. 지금 free -h로 스왑을 확인하라. Swap: 0B라면 가장 싸고 즉효인 안전망이 빠져 있는 것입니다. 스왑부터 추가하세요.
  2. 과부하 시 무엇이 나가는지 결정하라. 503을 뱉을지, 캐시된 정적 페이지(200)를 내줄지를 미리 설계하세요. CDN과 정적 폴백이 디인덱싱을 막는 핵심 방패입니다.
  3. Search Console을 켜 두라. 5xx 오류 알림과 크롤 통계는 공짜 조기경보입니다. 사라진 뒤 복구하는 것보다, 사라지기 전에 막는 비용이 비교할 수 없이 쌉니다.
