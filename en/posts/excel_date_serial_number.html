When a Date Column Turns Into 46233 - Excel Serial Numbers and the 1900 Leap Year Bug

A day that never existed, 1900-02-29, is still alive inside the cell - what a compatibility decision costs today

2026-07-30 Dev & Infra

Opening: the date column had turned into numbers like 46233

You open the report and the contract date column is full of five-digit numbers: 46233, 46235. Yesterday those cells read 2026-07-30. The usual reaction is one of two things. People decide the file is broken and ask the sender for a fresh copy, or they clear the column and retype everything by hand. Neither is necessary. Not one byte of data was lost.

In a spreadsheet a date has always been a number. What the cell stores is a single integer counting how many days have passed since an epoch, and the rule that makes it look like a date lives in an entirely separate layer called the cell format. Lose the format and the screen reverts to a number while the value stays exactly where it was. Seeing 46233 is not damage; it is the absence of formatting.

That much is widely known. What this article digs into is what comes next. There is a day inside that number system that never existed.

  • Serial 59 is 28 February 1900. A real date
  • Serial 60 is 29 February 1900. There was no such day. 1900 was not a leap year
  • Serial 61 is 1 March 1900. From here up everything is exact

So every date before 1 March 1900 is off by one. A compatibility decision made more than thirty years ago is what makes the weekday and duration maths in your file wrong today. And that defect has never been fixed, because leaving it in was judged to be the better trade.

This article does not tell you to stop using spreadsheets. That advice is useless to somebody already holding the file. Instead it lays out why it ended up this way, exactly what breaks at the boundary, and what you should exchange data in, using numbers I confirmed by running everything.

Environment. Every output below was produced on Windows 10 Pro (10.0.19045). The calculation engine is Excel 16.0 (build 20228), and on the language side Python 3.13.3, Node.js v22.16.0, XlsxWriter 3.2.9, with GNU bash 5.2.37 (MSYS2) as the shell. Every script was saved to a file and executed.

An honest note on how this was verified. The spreadsheet output was not read off a screen driven by a mouse; values and formulas were pushed into the same calculation engine through COM automation and the results were read back. Cell values, displayed strings, format codes and function return values were all measured that way. By contrast the ribbon layout, the checkboxes in the options dialog and the screens of the import wizard were not examined. Those items are not asserted here, only mentioned on documentary grounds.

2. The 29 February 1900 that never existed

That 1900 was not a leap year falls straight out of the rule. Divisible by four means leap, divisible by one hundred is an exception, divisible by four hundred is leap again.

1900 divides by four, but it also divides by one hundred and not by four hundred. It is not a leap year. The year 2000 divides by four hundred so it is one, and 2100 will not be. Python's date type throws on the spot if you try to build 1900-02-29. The date does not exist, so it cannot be constructed.

The spreadsheet, however, accepts it. I asked the functions directly.

These five lines are decisive. For serial 60 it answers day 29, month 2, year 1900. This is not merely a display quirk; the entire date function family believes that day exists.

The last three lines settle it as a deliberate exception rather than a display problem. Pass the string 1900-02-29 and it returns 60 and accepts it. Yet hand the same function 1901-02-29 or 2026-02-29 and it refuses with an error. It does not permit nonexistent 29 February dates generally; it lets exactly one year through. The exception is pinned to a single cell of the number line.

One more angle. Ask about the length of that February indirectly and you get this.

--- 16-8. DATE() with an out-of-range day ---

DATE(1900,0,1)           : #NUM!
DATE(1899,12,31)         : 3799-12-31

Feeding 30 February 1900 yields 1 March. Overflowing days roll into the next month, so day 30 of February landing on 1 March means it is counting that February through to the 29th. February 1900 really ended on the 28th, so day 30 should have been 2 March. A month with one extra day is being used in the arithmetic.

The third line causes real trouble too. Passing 1899 as the year to the date function returned 3799-12-31, because years below 1900 are interpreted by adding 1900. That is how you end up with the year 3799 while trying to handle 1899 data and expecting something around 1900.

  • The practical implication is clear. Any duration spanning early 1900 comes out one day too long. Tenure, maturity and age calculations are what get caught

4. Why it was never fixed - a deliberate defect

This is the most important angle in the article. This is not an undiscovered bug. The official documentation states both the history and the reasoning explicitly.

According to that documentation, early Lotus 1-2-3 assumed 1900 was a leap year, which made leap year handling easier for the program and caused no harm to almost all of its date calculations. Later, when Microsoft Multiplan and Excel were released, they adopted the same assumption. The reason is stated outright: to use the same serial date system as Lotus 1-2-3 and provide greater compatibility with it, and to make it easier for users to move worksheets from one program to the other.

Correcting it now is technically possible but the documentation judges the disadvantages to outweigh the advantages. The grounds it gives are these.

  • Almost all dates in existing worksheets and documents would decrease by one day. Correcting that shift would take considerable time and effort, especially in formulas that use dates
  • Some functions, such as the weekday function, would return different values. Formulas in worksheets might work incorrectly
  • It would break serial date compatibility with other programs that use dates
  • Leaving it alone produces only one problem: the weekday function returns incorrect values for dates before 1 March 1900, and since most users do not use dates that early, the documentation calls this rare
  • The documentation states that all other leap years are handled correctly, including century years that are not leap years such as 2100. Only 1900 is handled differently

So the summary is this. Leaving a nonexistent day in place was a choice, not a mistake. It was kept in order to match numbers with a widely used program of the era, and that choice became the standard. Once it was the standard, fixing it cost more than living with it. Compatibility beat correctness, and thirty years on that judgement still stands.

What to take from this. This defect is not a blemish on old software; it is a case study in how once a format spreads widely, its errors harden along with it. If you design data formats the lesson is blunt: a simplification made for early convenience becomes a permanent constraint. If you consume formats the lesson runs the other way: oddities written into a specification usually have a reason, and you should handle them as they are rather than wait for a fix.

  • 1900-01-01 becomes the number 1. That is the lower bound
  • Type 1900-02-29 and it is accepted as the number 60. A nonexistent day handled as a normal date
  • 9999-12-31 is 2958465 at the top, and 10000-01-01 goes back to being a string
  • The practical implication is large. Out-of-range dates raise no error and quietly become strings. Numbers and strings then mix in one column, and sorting, comparison and duration maths all break at that point
  • For genealogy, historical records or nineteenth-century birth dates it is safer to abandon the date type and manage a string column from the start

9. Writing a corrected converter yourself

Now the code. The key is that a single epoch is not enough and you need a branch at 60 and below. Here it is in Python.

import datetime as dt

EPOCH_SHIFTED = dt.date(1899, 12, 30)   # correct for serial 61 and up
EPOCH_TRUE    = dt.date(1899, 12, 31)   # correct for serials 1..59
EPOCH_1904    = dt.date(1904, 1, 1)

def serial_to_date(n, date1904=False):
    if date1904:
        return EPOCH_1904 + dt.timedelta(days=n)
    if n >= 61:
        return EPOCH_SHIFTED + dt.timedelta(days=n)
    if n == 60:
        raise ValueError('serial 60 is 1900-02-29, a date that never existed')
    if n >= 1:
        return EPOCH_TRUE + dt.timedelta(days=n)
    raise ValueError('serial %r has no calendar date' % n)

def serial_to_datetime(x, date1904=False):
    whole = int(x // 1)
    d = serial_to_date(whole, date1904)
    seconds = round((x - whole) * 86400)      # round, never truncate
    return dt.datetime.combine(d, dt.time()) + dt.timedelta(seconds=seconds)

I wrote the same thing in Node, placing an uncorrected naive implementation next to it for comparison.

const MS_DAY = 86400000;

// uncorrected: built only on the fact that 25569 is the Unix epoch
function naiveSerialToDate(n) {
  return new Date(Math.round((n - 25569) * MS_DAY));
}

// corrected: give the day back below 60
function serialToDateUTC(n) {
  if (n < 1)   throw new RangeError('serial ' + n + ' has no calendar date');
  if (n === 60) throw new RangeError('serial 60 is the phantom 1900-02-29');
  const shifted = n < 60 ? n + 1 : n;
  return new Date(Math.round((shifted - 25569) * MS_DAY));
}

function dateToSerialUTC(d) {
  const raw = Math.round(d.getTime() / MS_DAY) + 25569;
  return raw < 61 ? raw - 1 : raw;
}

Here are the rules you can generalise from this table. I describe the classes of value rather than asserting any specific real-world case.

  • Input with no year gets the current year filled in. MAR1 became 2026-03-01. Which means reopening the same file next year and retyping the same value produces a different number. Data built on year-less codes changes value annually
  • Three-part values are read with a two-digit year. 1/2/3 became 2003-01-02. Version numbers and specification codes get caught here
  • Month-name abbreviations followed by a digit are dangerous. Short alphabetic prefixes combined with numbers easily take that shape
  • Short codes containing a single hyphen or slash are also in the danger zone. Two or more, or two dots, and they usually stay strings

  • There is no way to undo it afterwards. The original text is not stored, so fetching the source again is the only option

All the defence has to happen before input. Format the column as text in advance, prefix an apostrophe, or set that column's type to text at the import stage. The specific click-by-click procedure in the import screen was not verified here, so it is not asserted. What the output above does establish beyond doubt is that after coercion nothing can be done.

  1. Read the container flag. For an xlsx this settles it. Unpack and look for the date1904 attribute in xl/workbook.xml. Absent or 0 means 1900, 1 means 1904. It is the only definitive evidence
  2. Match one anchor row. Pick a record whose true date you know, convert under both systems and see which matches. As above, one row settles it
  3. Filter by business range. This is weak evidence. Rule out whichever reading lands on a year your business cannot produce. Never use it alone
  4. Use the gap tell to find boundary values. If the gap between the two conversions is 1461 days rather than 1462, that serial is 60 or below and the row sits in the leap bug region
  5. If all you have is a CSV and none of the above works, do not guess. Ask the sender for three things: the date system, the list of date columns, and whether times are included

Two more things to check. If serial 60 appears in the data, flag and report that row separately. Let it pass silently and you will never trace where the missing day came from later. And count how many rows predate 1 March 1900. If the answer is zero, half of this article is something you can ignore.

## 0. The premise — a date is a number inside the cell

| Layer | What is stored | Where it lives |
|---|---|---|
| Value | Days elapsed from an epoch (integer) | The cell value |
| Time | Fraction of a day (0.5 = noon) | Decimal places of the same number |
| Display | A rule that makes the number look like a date | The cell format, separate from the value |

Lose the format and the value stays intact while the screen reverts to a number. **If you see 46233, the data is not corrupt; the format is gone.**

## 1. Serial to date lookup table (1900 system)

| Serial | Date | Note |
|---|---|---|

| 1 | 1900-01-01 | Lower bound. Really a Monday, but Excel answers Sunday |
| 58 | 1900-02-27 | Below the boundary |
| 59 | 1900-02-28 | Below the boundary. Really Wednesday, Excel says Tuesday |
| **60** | **1900-02-29** | **A day that never existed. This is the bug** |
| 61 | 1900-03-01 | Everything from here up is correct |
| 366 | 1900-12-31 | |

| 45000 | 2023-03-15 | |

- Negatives are not dates. `TEXT(-1,...)` returns an error
- Type 1899-12-31 into a cell and it stays a **string**, not a date
- 10000-01-01 becomes a string for the same reason

## 2. The arithmetic of the three boundary cells

| Serial | Excel shows | Real Gregorian date | 1899-12-30 + n |
|---|---|---|---|
| 58 | 1900-02-27 | 1900-02-27 | 1900-02-26 (a day early) |
| 59 | 1900-02-28 | 1900-02-28 | 1900-02-27 (a day early) |
| 60 | 1900-02-29 | does not exist | 1900-02-28 |
| 61 | 1900-03-01 | 1900-03-01 | 1900-03-01 (matches) |
| 62 | 1900-03-02 | 1900-03-02 | 1900-03-02 (matches) |

→ **The epoch 1899-12-30 is only correct at serial 61 and above.** At 60 and below it lands a day early. That single off-by-one is the whole bug.

Measured downstream symptoms:

- `=DATE(1900,3,1)-DATE(1900,1,1)` → **60** (the real count is 59)
- `=DATEDIF(DATE(1900,1,1),DATE(1900,3,1),"d")` → **60**
- `=DATE(1901,3,1)-DATE(1900,3,1)` → 365 (both sides above the boundary, so correct)
- `=DATE(1900,2,30)` → 1900-03-01 (proof it counts 29 days in that February)
- `=DATEVALUE("1900-02-29")` → 60 (accepted) / `=DATEVALUE("2026-02-29")` → error (refused)

## 3. The 1900 system vs the 1904 system

| Item | 1900 system | 1904 system |
|---|---|---|
| Epoch | 1900-01-01 = 1 | 1904-01-01 = 0 |
| Leap bug | Present (serial 60) | Absent |
| 2026-07-30 | 46233 | 44771 |
| 2000-01-01 | 36526 | 35064 |
| 2011-07-05 | 40729 | 39267 |
| Difference | — | Always 1462 lower |

- 1462 days = 4 years plus one leap day
- Flip the system on an existing file and **the stored numbers do not change while the displayed dates move by 1462 days**
  - 46233: 2026-07-30 → 2030-07-31
  - 36526: 2000-01-01 → 2004-01-02
- The gap between the two readings is **1461 days**, not 1462, only when the serial is 60 or below. That is your tell for boundary values

## 4. Time is the fractional part

| Clock | Fraction | x 86400 |
|---|---|---|
| 00:00:00 | 0 | 0 |
| 06:00:00 | 0.25 | 21600 |
| 12:00:00 | 0.5 | 43200 |

- 2026-07-30 09:30:00 = **46233.3958333333** (46233 + 34200/86400)

## 5. Fractional error — where a second disappears

Round-tripping all 86400 seconds of one day:

- Seconds that fail when you round: **0 out of 86400**
- Largest absolute error: **3.13855707645e-07 s (0.313856 microseconds)**, at second 238
- **Seconds that fail when you truncate (int/INT): 43136 out of 86400 — half of them**

| Operation | Result | True value |
|---|---|---|
| `INT((46233.3958333333-46233)*86400)` | **34199** | 34200 |
| Node `new Date((46233.3958333333-25569)*86400000)` | **09:29:59.999Z** | 09:30:00 |
| Excel `TEXT(46233.3958333333,"hh:mm:ss.000")` | 09:30:00.000 | 09:30:00 |
| 1/24 accumulated 24 times, minus 1 | **-0.00000000000000044** | 0 |

→ **Rule: always round when converting a fraction back to seconds. Truncating puts half your rows a second behind.**
→ Excel rounds at display time, so the screen hides it. It surfaces in code that pulls the value out and computes.

## 6. Corrected converter (Python)

```python
import datetime as dt

EPOCH_SHIFTED = dt.date(1899, 12, 30)   # correct for serial 61 and up
EPOCH_TRUE    = dt.date(1899, 12, 31)   # correct for serials 1..59
EPOCH_1904    = dt.date(1904, 1, 1)

def serial_to_date(n, date1904=False):
    if date1904:
        return EPOCH_1904 + dt.timedelta(days=n)
    if n >= 61:
        return EPOCH_SHIFTED + dt.timedelta(days=n)
    if n == 60:
        raise ValueError('serial 60 is 1900-02-29, a date that never existed')
    if n >= 1:
        return EPOCH_TRUE + dt.timedelta(days=n)
    raise ValueError('serial %r has no calendar date' % n)

def date_to_serial(d, date1904=False):
    if date1904:
        return (d - EPOCH_1904).days
    if d >= dt.date(1900, 3, 1):
        return (d - EPOCH_SHIFTED).days
    if d >= dt.date(1900, 1, 1):
        return (d - EPOCH_TRUE).days
    raise ValueError('dates before 1900-01-01 have no serial in this system')

def serial_to_datetime(x, date1904=False):
    whole = int(x // 1)
    d = serial_to_date(whole, date1904)
    seconds = round((x - whole) * 86400)        # round, never truncate
    return dt.datetime.combine(d, dt.time()) + dt.timedelta(seconds=seconds)
```

Verified values: `date_to_serial(2011-07-05)` = 40729, the 1904 system gives 39267, difference 1462. Excel and the documentation produce the same numbers.

## 7. Corrected converter (Node)

```javascript
const MS_DAY = 86400000;

// uncorrected: round-trips perfectly and is still a day wrong
function naiveSerialToDate(n) {
  return new Date(Math.round((n - 25569) * MS_DAY));
}

// corrected
function serialToDateUTC(n) {
  if (n < 1) throw new RangeError('serial ' + n + ' has no calendar date');
  if (n === 60) throw new RangeError('serial 60 is the phantom 1900-02-29');
  const shifted = n < 60 ? n + 1 : n;
  return new Date(Math.round((shifted - 25569) * MS_DAY));
}

function dateToSerialUTC(d) {
  const raw = Math.round(d.getTime() / MS_DAY) + 25569;
  return raw < 61 ? raw - 1 : raw;
}

// with a time component: round to ms so truncation cannot eat a second
function serialToInstantUTC(x) {
  const whole = Math.floor(x);
  const base = serialToDateUTC(whole).getTime();
  return new Date(base + Math.round((x - whole) * MS_DAY));
}
```

| Serial | Uncorrected | Corrected | Agree |
|---|---|---|---|
| 1 | 1899-12-31 | 1900-01-01 | no |
| 30 | 1900-01-29 | 1900-01-30 | no |
| 59 | 1900-02-27 | 1900-02-28 | no |
| 60 | 1900-02-28 | (refused) | no |
| 61 | 1900-03-01 | 1900-03-01 | yes |
| 46233 | 2026-07-30 | 2026-07-30 | yes |

→ **The trap: the uncorrected version passes its own round-trip test 100%.** Checked across 730 serials with zero round-trip errors. Yet the very first serial produces the wrong date. **A round-trip test can never catch this bug. You have to compare against the real calendar.**

## 8. What survives an export to CSV

Six cells holding the same number, differing only in format, saved as CSV:

| Cell format | Cell value | What actually landed in the CSV |
|---|---|---|
| `yyyy-mm-dd` | 46233 | `2026-07-30` |
| (no format) | 46233 | `46233` ← **the raw serial leaks out** |
| `mm/dd/yyyy` | 46233 | `07/30/2026` |
| `yyyy-mm-dd` | 58 | `1900-02-27` |
| `yyyy-mm-dd hh:mm:ss` | 46233.3958333333 | `2026-07-30 09:30:00` |
| `@` (text) | `2026-07-30` (string) | `2026-07-30` |

- **The cell format, not the value, decides what goes into the CSV**
- The last two rows are **byte-identical** in the file. The receiver cannot tell a formatted number from a real string
- One unformatted column is enough to ship raw serials. That is where 46233 in a date column comes from
- Every CSV cell arrives at the receiver as **text**. That is a separate layer from any encoding problem

## 9. When text is coerced into a date or a number

Measured in Excel, in 2026, on strings that were typed in and not left alone:

| Input | Result type | Stored value | Resolved date | On screen |
|---|---|---|---|---|
| `MAR1` | number | 46082 | 2026-03-01 | 01-Mar |
| `SEPT2` | number | 46267 | 2026-09-02 | 02-Sep |
| `12-Jan` | number | 46034 | 2026-01-12 | 12-Jan |
| `1-3` | number | 46025 | 2026-01-03 | (locale date) |
| `3/4` | number | 46085 | 2026-03-04 | (locale date) |
| `1/2/3` | number | 37623 | 2003-01-02 | 2003-01-02 |
| `007` | number | 7 | — | 7 |
| `1E5` | number | 100000 | — | 1.00E+05 |
| `A-001` | string | A-001 | — | A-001 |
| `0.1.2` | string | 0.1.2 | — | 0.1.2 |

- **Input with no year gets the current year filled in.** Re-enter the same value next year and you get a different number
- Any short code containing a single hyphen or slash sits in the danger zone
- What is lost does not come back. The leading zero of `007`, the notation of `1E5`, the original text of `1-3` are all gone
- The survival rule is clear: **two dots (`0.1.2`) or a leading letter (`A-001`)** and no coercion happens
- The defence has to happen before input. Format the column as text, prefix an apostrophe, or set the column type in the import wizard
- After coercion there is no undo. You have to fetch the source again

## 10. What is actually inside an xlsx

An xlsx is a zip full of XML. Unpack it and look at `xl/worksheets/sheet1.xml`:

```xml
<!-- a date cell: a number carrying a style index s="1" -->
<c r="B2" s="1"><v>46233</v></c>

<!-- a plain number cell: identical value, no s attribute -->
<c r="B4"><v>46233</v></c>

<!-- date and time -->
<c r="B3" s="2"><v>46233.39583333334</v></c>

<!-- a date below the boundary, 1900-02-27 -->
<c r="B6" s="1"><v>58</v></c>

<!-- a string: t="s" points into the shared string table -->
<c r="B5" t="s"><v>6</v></c>
```

The display rule sits separately in `xl/styles.xml`:

```xml
<numFmt numFmtId="164" formatCode="yyyy-mm-dd"/>
<numFmt numFmtId="165" formatCode="yyyy-mm-dd hh:mm:ss"/>
<cellXfs count="3">
  <xf numFmtId="0"   fontId="0" fillId="0" borderId="0" xfId="0"/>
  <xf numFmtId="164" fontId="0" fillId="0" borderId="0" xfId="0" applyNumberFormat="1"/>
  <xf numFmtId="165" fontId="0" fillId="0" borderId="0" xfId="0" applyNumberFormat="1"/>
</cellXfs>
```

→ **The only difference between a date cell and a number cell is the `s` attribute.** Both values are `46233`. The fact that it is a date lives nowhere in the value, only in the style.

The date system lives in `xl/workbook.xml`:

```xml
<!-- 1900 system (default): the attribute is simply absent -->
<workbookPr defaultThemeVersion="124226"/>

<!-- 1904 system -->
<workbookPr date1904="1" defaultThemeVersion="124226"/>
```

## 11. Triage — which system is this file using

Work from the strongest evidence down.

1. **Read the container flag (definitive for xlsx)**
   - `unzip -p book.xlsx xl/workbook.xml` and look for the `date1904` attribute
   - Absent or `0` means the 1900 system; `1` means the 1904 system
   - This is the only definitive evidence there is
2. **Match one anchor row**
   - Pick a record whose true date you already know
   - Convert under both systems and see which one matches
   - One row settles it
3. **Filter by a plausibility window (weak evidence)**
   - See which reading lands on a year your business cannot produce
   - Both readings landing inside a plausible range is genuinely common. Never use this alone
4. **Use the gap tell to find boundary values**
   - If the gap between the two readings is **1461 days** rather than 1462, that serial is 60 or below
   - That row sits inside the leap bug region
5. **If all you got is a CSV and none of the above works**
   - Numbers alone cannot settle it. Do not guess; ask the sender
   - Ask for: the date system, the list of date columns, and whether times are included

## 12. What to exchange data in

| Format | Self-describing | Needs an epoch | Timezone | Sorts as text |
|---|---|---|---|---|
| Serial number | no | yes | none | numeric sort only |
| `YYYY-MM-DD` | yes | no | none | yes |
| `YYYY-MM-DDTHH:MM:SSZ` | yes | no | carries it | yes |
| `MM/DD/YYYY` | partly | no | none | no |
| Unix seconds | no | yes (fixed) | UTC | numeric sort only |

**Recommendation: exchange ISO 8601 strings between systems.** The cost was measured.

- One column, 200,000 rows: serials 1,200,000 bytes → ISO 8601 2,200,000 bytes (**+83.3%**)
- Parse time: serials 0.2127 s vs ISO 8601 **0.0554 s**. **The strings were 3.8x faster**
- So the cost is **size only**, and speed actually favours strings. The instinct that numbers are lighter and therefore faster is wrong here
- What ISO 8601 does not fix: a value with no offset still leaves the timezone unknown. But that ambiguity becomes **visible**, which is the real gain over a bare number
- If the time of day carries meaning, include the offset (`Z` or `+09:00`)
- Sending a spreadsheet to a human end user is the exception. Send xlsx and ship the formats with it

## 13. Decision table by situation

| Situation | Risk | Response |
|---|---|---|
| Data contains dates before 1900-03-01 | Off by one day. Weekday and duration maths all wrong | Use a corrected converter; flag and report serials at 60 or below |
| Subtracting two dates across the boundary | Result is one day too large | Recompute spans that cross the boundary against the real calendar |
| Times are included | Truncating the fraction puts half the rows a second behind | Always round the fraction; convert to integer seconds before comparing |
| Adding times repeatedly | Accumulated drift remains (-4.4e-16 measured) | Accumulate in integer seconds, convert to a fraction once at the end |
| Received a file from another system | Off by four years and a day (1462) | Check `date1904` in `workbook.xml`, then verify one anchor row |
| Changing a file's date system | Stored numbers stay put; only the dates move 1462 days | Never change the system on a file that already holds data |
| Exporting to CSV | Unformatted columns leak raw serials | Check date column formats before export; agree the format with the receiver |
| Receiving a CSV | No way to know a numeric column is a date | Get column meanings in writing. Suspect integers near 46000 |
| Typing or pasting codes and part numbers | Coerced into dates or numbers, irreversibly | Format the column as text first; set column types on import |
| Handling short codes with no year | The current year is filled in, so values change annually | Pin them as text. Do not re-enter |
| Handling dates before 1899 | No serial exists; the value stays a string | Give up the date type and manage an ISO string column |
| Format lost, only numbers visible | Easy to misdiagnose as data corruption | The values are intact. Reapplying the format restores everything |

## 14. Checklist

- [ ] The serial converter has a **branch for 60 and below**
- [ ] Serial 60 is **refused or warned about**, never passed through silently
- [ ] The converter was validated **against real calendar dates**, not just round trips
- [ ] Any path that can receive a 1904 file has a **`date1904` check**
- [ ] Fractions are **rounded** back to seconds, not `int()` or `INT()`
- [ ] Time accumulation happens in **integer seconds**, converted once at the end
- [ ] Date column **formats are verified before CSV export**
- [ ] Incoming CSVs have integer columns near 46000 **screened as date candidates**
- [ ] The exchange spec states **ISO 8601 and the offset rule**
- [ ] Code and part-number columns are **typed as text on import**
- [ ] Someone has **counted** how many rows predate 1900-03-01
- [ ] A missing format is **not misdiagnosed as corruption**

## 15. Do not

- Fix the epoch at 1899-12-30 alone — every serial at 60 or below comes out a day wrong
- Trust a converter because it round-trips — a wrong implementation passes 100%
- Truncate the fraction with `int()` — 43136 of 86400 seconds land a second behind
- Change the date system on a file that already contains data — numbers stay, dates move
- Pick serial exchange because numbers feel lighter and faster — string parsing measured faster
- Paste codes and part numbers without setting the column type — coercion cannot be undone
- Infer the system from serials alone — both readings are often equally plausible
- Declare a numeric-looking date column corrupt and request the source again — just reapply the format
