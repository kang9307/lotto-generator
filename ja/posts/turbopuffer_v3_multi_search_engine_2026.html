契機 — ベクトル主導構造の限界とv3アーキテクチャの発表

2026年9月30日、検索インフラを提供するturbopufferは公式技術ブログにおいて「RIP, vector database」と題した記事を公開した。初期のサーバレスベクトルデータベースとして出発した同社が、ストレージ層の根本的な再設計を行い、バージョン3（v3）アーキテクチャへと移行していることを明らかにした。この発表の本質は、刺激的なタイトルが示唆するようなベクトル検索の廃止ではなく、システムの根幹であった近似最近傍（ANN）ベクトル索引をプライマリ索引から外し、セカンダリ索引へと再配置するという構造的決断にある。

turbopufferは、オブジェクトストレージを信頼できる唯一の情報源（source of truth）とし、NVMe SSDとメモリキャッシュを階層化することで、優れたコスト効率と低レイテンシを両立させ、CursorやNotionをはじめとする主要顧客の本番環境を支えてきた。しかし、全文検索、正規表現検索、属性フィルタリング、集計（aggregation）といった非ベクトルクエリの需要が急増するにつれ、全データがベクトル索引の物理配置に従属していた初期の設計は、ストレージ増幅、書き込み増幅、ベクトル化実行の制限という3つの物理的限界に直面した。公式技術文書に掲げられた主要目標は次の通りである。

  • ベクトル索引に束縛されていた文書保存構造を切り離し、複数ベクトル環境におけるデータの物理的重複を完全排除する
  • バックグラウンドでのベクトルクラスタ再編成時に発生する、数百件規模の転置索引や属性の連鎖書き換えを遮断する
  • ANNクラスタ長に囚われていた分析クエリの処理ブロックを解放し、近代的なベクトル化CPU実行パイプラインを加速する
  • ベクトル検索にとどまらず、複雑なSQL分析や大容量スキャン処理をturbopuffer基盤へ集約して超高速に処理する

すなわち今回のv3移行は、単なる性能改善パッチにとどまらず、単一目的の特化型ベクトルデータベースという枠組みを脱し、ベクトル・全文・構造化データを単一基盤で統合提供する複合検索エンジン（multi-search query engine）への構造的転換を意味している。

v1の設計 — オブジェクトストレージと階層型クラスタリングの統合

turbopuffer v1の設計思想は、極めて安価でありながら実用的な応答速度を持つサーバレスベクトルデータベースの実現であった。ローンチ当時、業界で標準的だったのはHNSWなどのグラフベースのベクトル索引であったが、グラフ探索はポインタのランダムアクセスを多用するため、オブジェクトストレージの高いネットワーク遅延と大ブロック読み込み特性には不向きであった。そこでturbopufferは、オブジェクトストレージと相性の良い階層型クラスタリング（hierarchical clustering）を採用した。

初期実装にはマイクロソフトのSPANNアルゴリズムを採用していたが、データの動的な追加と更新に対応するため、増分インデックスをサポートするSPFreshアルゴリズムへと移行した。ベクトルをグループごとに束ね、各グループの重心（centroid）を上位層でさらにクラスタリングする操作を繰り返し、単一のルートを持つ木構造を構成する。ストレージ層はソートされた一意のキーを提供するキー・バリューストアであり、各クラスタにClusterId、内部の個別ベクトルに密なLocalIdを割り当てた。この2つの識別子を結合したC0L1のような値をANNアドレスと呼ぶ。

// turbopuffer v1: ANNアドレスをキーとするソート済みキー・バリューストア構造
                    // 単一リーフクラスタC0内部のベクトルデータとドキュメントID
                    K::Vector(C0L0) = vec![0.45, 0.32, ...];
                    K::Id(C0L0)     = 7;
                    
                    K::Vector(C0L1) = vec![-0.28, 0.96, ...];
                    K::Id(C0L1)     = 13;
                    
                    // 上位ツリー層でクラスタC0の重心ベクトルをインデックス化
                    K::Vector(C1L4) = vec![0.64, -0.48, ...];
                    K::Id(C1L4)     = C0; // 下位クラスタの識別子を参照

v1アーキテクチャの根幹を成す設計原則と物理的特性は、以下の4点に集約される。

  • オブジェクトストレージを単一の真実源として維持コストを抑えつつ、階層化NVMeキャッシュによりアクセス遅延を抑制
  • ポインタ探索を排除し、クラウドストレージからの大容量順次ブロック読み出しに特化した階層型クラスタ構造を採用
  • ソート済みキー・バリューストア上でClusterIdとLocalIdを統合したANNアドレスをデータの主キーとして活用
  • 上位クラスタの重心が下位クラスタを参照する木構造探索により、探索空間を絞り込み最小限のネットワークI/Oを実現

上記コードに示されているように、ベクトル値だけでなく元文書のIDまでもが、ClusterIdとLocalIdで構成されるANNアドレスを物理キーとして保存されていた。すなわち、データベース内でデータが格納される場所を決める唯一の基準（プライマリ索引）がベクトル索引そのものであった。この構造は、オブジェクトストレージから必要なクラスタブロックだけを最小限のI/Oで読み出す用途には極めて洗練されていた。

v2の拡張 — 転置索引による属性フィルタとBM25全文検索の追加

ベクトル検索の用途が単純な類似度検索を超えて業務システム全般へと広がるにつれ、属性値によるフィルタリングとBM25による全文検索（FTS）への需要が急速に高まった。turbopufferは、非公式にv2と呼ばれる段階で属性索引と転置索引（inverted index）をエンジンに統合した。高速な絞り込みと高い再現率を維持するため、属性索引は属性値をその値を持つ文書のANNアドレスのリストへとマッピングする設計をとった。

例えば鳥類データにおいて特定の科（family）や属（genus）で絞り込む場合、エンジンは該当キーに紐づくANNアドレス一覧を即座に取得してベクトル探索空間を縮小する。また、include_attributesパラメータによって検索結果とともに属性データを返す必要があるため、各文書のメタデータ属性もベクトルやIDと同様に同一のANNアドレス配下に物理的に並置された。

// turbopuffer v2: 属性転置索引およびBM25全文検索インデックス構造
                    // 属性値を文書のANNアドレス一覧へマッピング
                    K::AttrIndex("family", "Alcidae")    -> vec![C0L3, C1L2, C1L3, ...];
                    K::AttrIndex("genus", "Fratercula")  -> vec![C0L3, C1L2, C1L9, ...];
                    
                    // include_attributes射影のためANNアドレス配下に属性データを並置
                    K::Vector(C0L0)          = vec![0.45, 0.32, ...];
                    K::Id(C0L0)              = 7;
                    K::Attr(C0L0, "family")  = "Alcidae";
                    K::Attr(C0L0, "genus")   = "Fratercula";
                    
                    // BM25ポスティングリスト: ANNアドレスと共に出現頻度と文書長を格納
                    K::FTS("description", "Atlantic")    -> vec![(C0L0, 2, 37), (C9L4, 1, 42), ...];
                    K::Attr(C0L0, "description")         = "A sharply dressed seabird with a multicolored bill...";

その後、turbopufferは高度なエンタープライズワークロードに対応するため、多様なクエリエンジンとインデックス構造を順次リリースした。公式に確認された機能拡張は以下の通りである。

  • 転置属性フィルタリング: 属性条件を満たすANNアドレス集合を瞬時に特定し、検索空間を効率的に事前縮小
  • BM25全文検索: 単語ごとのポスティングリストに出現頻度と文書長を保持し、TF-IDF/BM25適合度スコアリングを実行
  • 正規表現およびあいまい一致: 自由形式のテキスト探索や入力ゆらぎ、タイポに対応する柔軟な文字列照合
  • スパースベクトル検索: SPLADEなどの語彙重み付きスパース表現と密ベクトルを組み合わせたハイブリッド検索
  • 属性基準ソートと集計: 特定フィールドに基づく高速な並び替えおよび基本的な統計値算出クエリの提供

これらの拡張を経て、課題管理ツールLinearの差分同期エンジン（delta sync read path）のように、検索以外の高信頼データ同期基盤としても採用が広がった。しかし、これほど機能が拡張された後も、基盤となるストレージ構造は依然としてANNアドレスを軸とするベクトル優先配置構造に固定されたままであった。

構造的ボトルネック① — 複数ベクトル表現に伴うストレージ容量増幅

全データがANNアドレスに従属する設計は、1文書につき正確に1つのベクトルが存在する環境では破綻しなかった。文書とANNアドレスが1対1に対応し、非ベクトル属性も1度しか保存されないためである。しかし、近代的なRAGや情報検索の進展により、1つの文書を単一のベクトルだけで表現する手法の限界が浮き彫りになった。

長文を段落ごとに分割してインデックス化するドキュメントネスティングや、トークン単位の埋め込みを保持して検索精度を大幅に向上させるLate Interaction（ColBERT等）が普及し、1つの文書に複数のベクトルを割り当てるケースが一般化した。しかしturbopufferのv1/v2構造では、各ベクトルが別々のクラスタに割り振られ、独立したANNアドレスを持つため、以下のような深刻な無駄が生じた。

  • 1つの文書に10個のベクトルが生成されると、同一のメタデータ属性や本文データが10箇所の異なるANNアドレス配下に10回重複して保存される。
  • 本文や属性データのサイズが大きいワークロードでは、ベクトル自体のデータ量よりも重複保存された属性データがストレージの大半を占有する。
  • 容量の肥大化はオブジェクトストレージの課金とローカルNVMeキャッシュの枯渇を招く。
  • キャッシュヒット率の低下がネットワーク帯域を逼迫させ、マルチテナント環境下での同時クエリ処理能力を大きく阻害した。
  • このため、同社はネームスペースあたりに定義できるベクトル列（vector columns）の最大数に厳格な上限を課さざるを得なかった。

構造的ボトルネック② — SPFresh再編成が引き起こす書き込み連鎖増幅

第2の致命的なボトルネックは、データの挿入・更新・削除時に発生する書き込み増幅（write amplification）である。階層型クラスタリング索引では、データの出入りに伴ってクラスタの重心バランスが崩れ、そのまま放置すると検索の再現率が著しく低下する。これを防ぐため、SPFreshアルゴリズムはバックグラウンドで定期的にベクトルを再配置する。

しかし、文書の全属性や索引がANNアドレスをキーとしていたため、ベクトルの再配置は単なるベクトルの移動にとどまらなかった。ベクトルがクラスタAからクラスタBへ移り、新たなANNアドレス（例: C0L3からC2L8）が付与されると、そのアドレスにぶら下がっていた全属性データ、本文、さらにはその文書を参照していた数百の属性索引やBM25転置索引までもが一斉に書き換えの対象となった。

  • 単一のベクトル位置の調整に伴い、数百もの属性や索引エントリが物理的に連鎖移動（cascading move）する。
  • データ更新が頻繁な環境では、実際の流入データ量に対して数十倍から数百倍のディスクおよびオブジェクトストレージへの書き込みが発生する。
  • インデックス作成のスループットを改善しようとする試みが、過度な連鎖書き込みによって効果逓減に直面した。
  • 過剰な書き込みI/Oはバックグラウンドコンパクションを遅延させ、リアルタイム読み取りの遅延スパイクを引き起こす主因となった。
  • 結果としてデータ取り込み処理が滞留し、システム全体の運用コストが急激に跳ね上がる要因となった。

構造的ボトルネック③ — クエリ別最適ブロック長とベクトル化実行の制約

第3の課題は、近代的なクエリエンジンの根幹であるベクトル化実行（vectorized execution）の制限である。分析エンジンは、SIMD命令とCPUパイプラインを飽和させるため、一定のブロック単位でループを回してデータを処理する。しかし、最適なブロック長はクエリの種類によって大きく異なる。

エンジンおよびクエリ種別最適な処理ブロック長実行特性とハードウェア最適化の狙い
DuckDB（ベクトル化OLAP）2,048行単位CPU L1/L2キャッシュ適合とSIMDベクトル演算の最大化
ClickHouse（大規模集計）最大約65,000行単位列スキャン処理量の極大化と高密度データ圧縮
Apache Lucene（全文検索ポスティング）256文書単位ブロック整数のビットパッキング圧縮（PForDelta）と高速スキップ
turbopuffer ANNベクトルクラスタ約100〜200文書単位重心計算の精度維持とオブジェクトストレージI/O局所性
turbopuffer FTS v1（旧設計）中央値約1.5ポスティングANNクラスタ境界で分割されブロックの極端な断片化が発生

上表の通り、turbopufferのANN索引はクラスタあたり100〜200文書の規模でオブジェクトストレージにおいて最も優れた性能を発揮する。しかし文書データ自体がこのクラスタ単位に固定されていたため、数千行を一気にスキャンして集計（GROUP BYなど）したい分析クエリも、100〜200行という微小なブロックに細切れにされた状態で実行せざるを得なかった。

ブロック長が性能に与える劇的な影響は、turbopufferが全文検索エンジンをv1からv2へと改修した際にすでに実証されていた。FTS v1ではポスティングリストをANNクラスタ境界で分割していたため、ブロック長の中央値がわずか1.5件に過ぎなかった。FTS v2でポスティングリストをクラスタから切り離し、約256文書の固定長ブロックへと再構築したところ、索引サイズは10分の1に縮小し、クエリ速度は最大20倍へと跳ね上がった。ポスティングリストは文書の参照を保持するだけでよいためクラスタ境界から脱却できたが、文書本体を走査する集計処理は依然として100〜200件の制約に囚われていた。

v3の解決策 — 主索引の分離とセカンダリ索引体系への刷新

これら3大ボトルネックを根本から解決するためのturbopuffer v3の設計指針は明快である。ANNアドレスを主キーとして使用するのをやめることである。v3では、文書の配置、コンパクション、走査を、ベクトル索引のツリー構造から完全に切り離した。これにより達成された革新点は以下の通りである。

  • 文書ストレージの独立化: 文書はベクトルクラスタの境界と無関係に、独立した文書識別子を基準として最適な列指向ブロックサイズでまとめて保存される。複数ベクトルが存在しても本文は1度しか保存されず、ストレージ増幅が解消される。
  • ANN索引のセカンダリ化: ベクトル索引はシステム唯一の主軸ではなく、属性索引や転置索引と並ぶ1つの「セカンダリ索引」として位置づけ直される。
  • 連鎖書き込みの遮断: SPFreshがベクトルクラスタを再編成しても、更新されるのはベクトル索引内部のポインタのみである。文書本体や属性索引は定位置に留まるため、書き込み増幅が大幅に抑止される。
  • ベクトル化実行の解放: 集計処理やスキャン処理は100〜200件というクラスタの制約から脱却し、CPUパイプラインを飽和させる数千行単位の最適ブロックでデータを一括処理できる。
  • 汎用SQLへの基盤形成: 文書ストレージの正規化により、単純な類似度検索を超え、多様なSQL分析クエリをturbopuffer上で超高速に実行するための基盤が確立された。
  • コンパクション周期の分離: 文書データのマージ処理とベクトルツリーの再編成を別個の独立したスケジュールで制御可能となり、運用安定性が向上した。

現在turbopufferが公表している稼働規模は、全クラスタ合計で1兆件以上の文書（1T+ documents）をホストし、秒間1,000万件以上の書き込み（10M+ writes/s）と秒間25,000件以上のクエリ（25k+ queries/s）を処理している。また、単一索引で1,000億件以上のベクトル（100B+ vectors）を運用し、1,000以上のQPS環境において99パーセンタイル（p99）読み取りレイテンシ200msを維持している。

公式発表によると、v3は2026年9月上旬の段階で自動化テストスイート（CI）を100%通過し、データ処理の正確性（correctness）を検証完了した。同社エンジニアリングチームは、v2と同等以上の性能を達成するための公開ベンチマークを実施中であり、性能確認が完了次第、本番環境へと順次展開される予定である。

確認できなかった事項

  • v3で採用された独立文書ストレージの具体的なファイルフォーマット（例: Apache Parquetや独自の列指向バイナリ形式など）の詳細仕様。ブログではストレージの論理的分離についてのみ述べられており、物理フォーマットは明示されていない。
  • v3の本番環境への正式展開予定日。CI 100%通過とベンチマーク進行中である旨のみが公表されており、確定したリリース日は明らかにされていない。
  • 既存のv2ネームスペースからv3ストレージへのオンライン移行手順およびダウンタイムの有無。
  • v3アーキテクチャ下で測定された集計（GROUP BY）クエリの具体的なレイテンシ短縮率。（本文中の10倍縮小・20倍高速化はv2 FTS改修時の実績値である）
  • すでに公開されている顧客企業（Cursor、Notion、Linear）以外の、v3先行テストに参加しているエンタープライズ顧客の構成。
  • v3においてセカンダリ化されたANNベクトル索引が利用するノード間キャッシュ方針および追加のメモリオーバーヘッド。
