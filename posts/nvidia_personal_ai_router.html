로컬 AI 추론의 병목과 분산 라우팅의 필요성

로컬 컴퓨팅 하드웨어에서 대규모 언어 모델을 운용할 때 가장 먼저 맞닥뜨리는 기술적 장벽은 바로 단일 시스템의 메모리 대역폭과 연산 자원의 물리적 포화 상태입니다. 상용 클라우드 서비스의 경우 거대한 데이터센터 인프라와 고도화된 글로벌 로드밸런싱 계층을 통해 수만 명의 동시 접속자가 유입되더라도 탄력적으로 인스턴스를 확장하여 지연시간을 방어합니다. 하지만 온프레미스 환경이나 로컬 데스크톱에서는 단 한 장의 그래픽 카드나 통합 메모리 컨트롤러가 모든 연산 부하를 홀로 감당해야 합니다. 단일 머신 구조에서는 동시성 처리가 극도로 제한되며, 여러 작업이 한꺼번에 유입되는 순간 전체 개발 파이프라인이 멈춰 서는 현상이 발생합니다.

단일 머신의 한계와 멀티 에이전트 워크로드의 폭증

자율 코딩 에이전트 프레임워크나 복합 RAG 시스템의 실행 메커니즘을 들여다보면, 단일 태스크를 완료하기 위해 필수적으로 거치는 추론 횟수가 기하급수적임을 알 수 있습니다. 사용자가 「레거시 인증 모듈을 최신 표준으로 리팩토링하고 관련 테스트 코드를 작성하라」는 단일 프롬프트를 전송하면, 백그라운드에서는 프로젝트 구조 탐색 에이전트, 함수 호출 이력 추출 에이전트, 보안 취약점 점검 에이전트, 단위 테스트 작성 에이전트가 동시에 깨어납니다. 이들 에이전트가 단일 머신에 설치된 로컬 Ollama 백엔드로 일제히 추론 요청을 전송하면 백엔드 엔진 내부에서는 극심한 큐잉 지연(Queueing Delay)과 헤드오브라인 블로킹(Head-of-Line Blocking)이 발생합니다.

특히 트랜스포머 아키텍처 기반의 모델 추론에서는 이전 토큰들의 연산 상태를 유지하는 KV 캐시(Key-Value Cache)가 비디오 메모리(VRAM)의 상당 부분을 차지합니다. 여러 에이전트가 서로 다른 긴 컨텍스트의 프롬프트를 동시에 밀어 넣을 경우, 단일 GPU의 메모리가 고갈되어 엔진은 새로운 요청을 처리하기 위해 기존 세션의 캐시를 디스크로 내리거나 아예 대기열에 묶어둘 수밖에 없습니다. 그 결과 토큰 생성 속도는 급격하게 곤두박질치며, 평소 초당 수십 토큰 이상 나오던 모델이 단 몇 초만에 한 자릿수 미만으로 떨어져 전체 자동화 워크플로가 사실상 마비되는 사태에 이릅니다.

NVIDIA Personal AI Router가 위치하는 계층

이러한 병목 문제를 해결하기 위해 NVIDIA Personal AI Router(이하 PAIR)가 자리 잡는 계층은 명확합니다. PAIR는 복잡한 분산 연산 프레임워크를 밑바닥부터 새로 작성하는 대신, 이미 개발자들이 친숙하게 사용하고 있는 로컬 백엔드 앞단에 상주하는 지능형 로컬 추론 프록시 게이트웨이 역할을 자처합니다. 동일한 서브넷에 연결된 여러 대의 PC와 Mac을 하나의 논리적인 서비스 풀로 묶어내고, 유입되는 모든 추론 요청의 목적지를 실시간으로 판단하여 최적의 머신으로 교통정리를 수행합니다.

개발자 입장에서의 인터페이스 단순성은 PAIR의 가장 큰 장점 중 하나입니다. 각각의 클라이언트 애플리케이션이나 에이전트 스크립트는 네트워크 상에 존재하는 수많은 기기들의 개별 IP 주소를 알 필요가 없습니다. 오직 로컬 머신에서 구동 중인 PAIR의 프록시 포트만을 단일 진입점으로 바라보며 요청을 보내면, PAIR가 현재 참여 중인 노드들의 상태를 점검하여 부하가 적고 해당 모델을 즉시 구동할 수 있는 적격 노드로 투명하게 트래픽을 중계합니다. 결과적으로 애플리케이션의 아키텍처 복잡도를 전혀 높이지 않으면서도 로컬에 방치되어 있던 유휴 연산력을 완벽하게 가동할 수 있게 됩니다.

가장 먼저 알아야 할 구조적 한계: 분산 추론(Sharding)이 아니다

NVIDIA가 새로운 로컬 AI 분산 도구를 출시했다는 소식을 접할 때 수많은 엔지니어와 사용자가 가장 먼저 떠올리는 시나리오는 다음과 같은 기대일 것입니다: 「내 데스크톱의 16GB RTX 그래픽 카드와 보조 노트북의 16GB 메모리를 네트워크로 합치면, 최소 32GB의 VRAM이 필요한 거대 70B 파라미터 모델을 로컬에서 구동할 수 있지 않을까?」 하지만 이러한 기대는 완전히 잘못된 것이며, 도구의 구조적 설계 목적을 오해한 데서 비롯됩니다. 이 기술적 한계를 글의 초두에서 명확하게 짚고 넘어가지 않으면 불필요한 시스템 구축 실패를 겪게 됩니다.

NVIDIA 공식 저장소 README 명시 원문 직결 경계:
PAIR는 각각의 독립된 요청을 단 하나의 노드로 라우팅합니다. GPU 메모리를 풀링하지 않으며, 여러 GPU를 결합하여 하나의 더 큰 논리적 GPU로 만들지 않고, 단일 모델을 여러 머신에 걸쳐 분할(샤딩)하지 않으며, 처리 중인 단일 추론 요청을 여러 노드 간에 쪼개어 분담하지 않습니다. 즉, 하나의 독립된 추론 요청은 처음부터 끝까지 반드시 단 한 대의 컴퓨터 안에서만 완결됩니다.

흔한 오해: VRAM 통합 및 텐서 병렬화의 부재

엔터프라이즈 데이터센터 환경에서 여러 대의 GPU를 하나로 묶어 거대 모델을 서빙하는 기술은 텐서 병렬화(Tensor Parallelism)나 파이프라인 병렬화(Pipeline Parallelism)로 불립니다. vLLM이나 TensorRT-LLM 클러스터 같은 전문 분산 추론 런타임은 단일 계층의 행렬 곱셈 연산을 쪼개어 여러 GPU에 분산시킨 뒤, 매 레이어마다 중간 연산 결과를 동기화하는 과정을 거칩니다. 이러한 방식이 성립하려면 GPU 간의 통신 대역폭이 초당 수백 기가바이트(GB/s)에 달하는 초고속 전용 인터커넥트, 즉 NVLink나 400Gbps InfiniBand 네트워크가 물리적으로 구축되어 있어야만 합니다.

반면 일반적인 가정이나 소규모 사무실의 네트워크 인프라는 기가비트 이더넷이나 Wi-Fi 환경에 의존합니다. 만약 일반 LAN 환경에서 거대 모델의 가중치 행렬 연산을 노드 간에 샤딩하여 동기화하려 시도한다면, 토큰 하나를 생성할 때마다 네트워크 전송 병목으로 인해 수 초 이상의 극심한 통신 지연이 발생하게 됩니다. NVIDIA PAIR는 이러한 로컬 네트워크의 물리적 현실을 철저히 인정하고 출발한 프로젝트입니다. 초고속 인터커넥트가 없는 일반 가정용 이종 컴퓨터 환경에서는 모델 자체를 분할하는 것이 불가능에 가까우므로, 가중치를 쪼개는 대신 완전한 독립 요청 단위(Per-Request Basis)의 부하 분산에만 전념하도록 설계되었습니다.

단일 요청-단일 노드 할당 원칙

이러한 아키텍처 특성으로 인해 PAIR 환경에서는 엄격한 단일 노드 완결 원칙이 적용됩니다. 클러스터 내에 참여한 어떤 컴퓨터도 특정 모델을 단독으로 적재할 수 있는 충분한 물리적 메모리를 갖추고 있지 못하다면, 그 모델은 PAIR 클러스터 전체에서 결코 구동될 수 없습니다. 예를 들어 특정 모델을 안정적으로 서비스하기 위해 일정 용량 이상의 비디오 메모리가 필요하다면, 클러스터에 묶인 노드들 중 적어도 하나는 그 모델 전체를 완전히 적재할 수 있는 물리적 메모리를 단독으로 확보하고 있어야 합니다.

결국 PAIR가 제공하는 가치는 「단일 거대 모델의 구동 한계 돌파」가 아니라, 「동일한 적격 모델을 적재한 여러 대의 기기를 통해 동시 처리량(Throughput)과 동시 요청 수용력(Concurrency)을 선형적으로 확장하는 것」에 있습니다. 멀티 에이전트 시스템에서 발생하는 무수한 병렬 쿼리를 처리할 때, 기기 한 대가 모든 연산을 떠안고 멈추는 대신 2대, 3대의 컴퓨터가 각자 독립된 요청을 병렬로 쳐내는 구조를 만들어내는 것이 PAIR의 본질입니다.

지원 플랫폼과 환경별 설치 절차

NVIDIA 공식 저장소는 소스 코드 빌드 외에도 개발자와 일반 사용자가 복잡한 빌드 도구 체인을 설치하지 않고도 즉시 시스템에 적용할 수 있는 공식 릴리스 바이너리를 권장 설치 방식으로 제공합니다. 공식 배포 인스톨러는 디지털 서명이 완료되어 있으며, 백그라운드에서 동작하는 코어 라우팅 서비스와 직관적인 데스크톱 관리 애플리케이션을 통합 구성합니다. 특히 Windows 환경에서는 인바운드 및 아웃바운드 통신에 필요한 방화벽 규칙을 설치 과정에서 자동으로 등록하여 네트워크 탐색 실패를 방지합니다.

운영체제 및 하드웨어 아키텍처 지원 범위

PAIR의 가장 돋보이는 강점 중 하나는 완벽한 크로스 플랫폼 및 이종 아키텍처 지원입니다. 특정 운영체제나 전용 하드웨어에 종속되지 않으며 다음과 같은 광범위한 환경을 공식 지원합니다:

  • Windows: Windows 11 환경을 공식 지원하며, 전통적인 x64 아키텍처뿐만 아니라 최신 arm64 아키텍처까지 포괄합니다.
  • Linux: 널리 사용되는 주요 배포판을 지원하며, 데비안 계열 환경을 위한 공식 Debian 패키지(.deb)를 x64 및 arm64용으로 제공합니다.
  • macOS: Apple Silicon 및 Intel 기반 x64 Mac 시스템을 모두 지원하며, 공식 .dmg 디스크 이미지 형태로 배포됩니다.
  • 이종 플랫폼 간 자유로운 페어링: Windows 11 데스크톱, 우분투 홈 서버, macOS 노트북이 단일 클러스터 내에서 아무런 프로토콜 충돌 없이 완벽하게 상호 연결됩니다.

플랫폼별 공식 패키지 설치 방법

공식 GitHub 릴리스 페이지에서 각 운영체제에 맞는 최신 빌드를 다운로드하여 설치를 진행합니다. Windows와 macOS 사용자의 경우 일반적인 데스크톱 소프트웨어의 설치 흐름과 동일합니다. Windows에서는 내려받은 .exe 실행 파일을 실행하여 안내에 따라 설치를 완료하면 되며, macOS에서는 마운트된 .dmg 이미지 안의 애플리케이션 아이콘을 시스템의 Applications(응용 프로그램) 폴더로 드래그하여 배치를 완료합니다.

Linux 환경의 경우 공식 브리프 및 저장소에 명시된 대로 다운로드한 Debian 패키지를 패키지 관리자를 통해 설치합니다:

sudo apt install ./NVPAIR-Setup-*.deb

만약 동일한 다운로드 디렉터리 내에 여러 버전의 패키지 파일이 함께 보관되어 있다면, 셸 와일드카드 확장 오류를 방지하기 위해 구체적인 전체 파일명을 직접 지정하여 실행하는 것이 안전합니다.

데스크톱 GUI와 무두(Headless) 환경을 위한 터미널 인터페이스

가정이나 오피스에서 상시 가동 중인 리눅스 기반 홈 랩 서버, 미니 PC, 혹은 전용 워크스테이션 중에는 모니터나 데스크톱 디스플레이 환경(X11/Wayland)이 설치되어 있지 않은 무두(Headless) 머신이 많습니다. PAIR는 이러한 서버 환경을 클러스터 노드로 손쉽게 편입시킬 수 있도록 전용 터미널 인터페이스(TUI)를 기본 내장하고 있습니다.

터미널 인터페이스는 백그라운드 라우팅 데몬을 자동으로 가동하면서 콘솔 창 전체를 활용하는 TUI 화면을 렌더링합니다. 관리자는 SSH 세션 안에서 화살표 키와 단축키를 통해 현재 연결된 클러스터 노드 목록을 실시간으로 감시하고, 백엔드 추론 엔진의 가동 상태와 GPU 사용률 신호를 직관적으로 확인할 수 있습니다. GUI가 없는 순수 서버 환경에서도 데스크톱 앱과 동일한 관리 권한을 행사할 수 있다는 점은 홈 랩 엔지니어들에게 대단히 실용적인 배려입니다.

스케줄링 알고리즘과 요청 분배 메커니즘

네트워크 내에 복수의 컴퓨팅 노드가 활성화되어 있을 때, 클라이언트로부터 인입된 추론 요청을 어느 기기로 전달할 것인가는 라우터의 처리 성능과 응답성을 결정짓는 핵심 알고리즘입니다. 만약 단순한 라운드로빈 방식으로 요청을 균등 분배한다면, 복잡한 코딩 태스크를 수행하느라 100% 연산 부하에 걸린 머신으로 새로운 요청이 배정되어 심각한 지연을 초래할 수 있습니다.

대기 작업량과 완만하게 평활화된 GPU 사용률 결합

NVIDIA 공식 README 문서가 명시한 바에 따르면, 현재 PAIR 릴리스는 「대기 중인 작업량(Queued Work)과 완만하게 평활화된 GPU 사용률 신호(Coarse, Smoothed GPU-Utilization Signal)」를 결합한 단일 스케줄링 정책을 채택하고 있습니다. 여기서 주목할 부분은 GPU 사용률 신호를 원시 데이터 그대로 사용하지 않고 완만하게 평활화(Smoothed)하여 다룬다는 점입니다.

GPU의 실시간 연산 점유율은 트랜스포머 레이어의 연산 구간이나 프롬프트 인제스천 단계에서 순간적으로 100%까지 치솟았다가 토큰 생성 대기 상태에서 급격히 떨어지는 스파이크 노이즈를 동반합니다. PAIR는 이러한 순간적 변동성에 즉각적으로 반응하여 라우팅 진동(Thrashing)이 발생하는 현상을 방지하기 위해, 시간 축에 따른 평활화 필터를 거친 사용률 신호를 현재 처리 큐에 쌓여 있는 대기 작업 수와 가중 결합합니다. 이를 통해 현재 실질적으로 유휴 상태에 머물고 있는 노드를 안정적으로 선별하여 트래픽을 분기합니다.

현재 스케줄러가 고려하지 않는 요소와 최적 클러스터 조건

그러나 엔지니어링 관점에서 현 단계 스케줄러의 미반영 요소들을 정확하게 파악하는 것은 매우 중요합니다. 공식 문서가 명확하게 밝힌 바와 같이, 현재 배포된 단일 스케줄링 정책은 다음 네 가지 핵심 변수를 계산에 포함하지 않습니다:

  • GPU 칩셋 모델 및 절대 연산 능력: 플래그십 데스크톱 GPU와 보급형 노트북의 모바일 GPU가 지닌 절대적인 연산 속도 차이를 가중치로 보정하지 않습니다.
  • 물리적 가용 비디오 메모리(VRAM) 잔여량: 각 노드가 현재 확보하고 있는 잔여 메모리의 절대적인 기가바이트(GB) 용량을 스케줄링 점수에 직접 반영하지 않습니다.
  • 모델의 메모리 캐시 상주 여부(Model Warmness): 해당 노드의 백엔드 엔진 메모리에 목표 모델이 이미 로드되어 즉각 응답 가능한 웜(Warm) 상태인지, 디스크에서 새로 읽어와야 하는 콜드(Cold) 상태인지 구분하지 않습니다.
  • 인입된 요청의 예상 연산 비용: 프롬프트 토큰의 길이가 수천 토큰에 달하는 대용량 문서인지, 수십 토큰 수준의 단순 질의인지 사전에 프로파일링하지 않습니다.

이러한 한계로 인해, 연산 성능 차이가 극단적으로 벌어지는 이종 기기들을 하나의 클러스터로 묶을 경우 비효율이 발생할 수 있습니다. 예를 들어 빠르게 응답을 뱉을 수 있는 고성능 데스크톱 대신, 완만한 사용률 수치상 여유가 있어 보이는 저사양 노트북으로 긴 프롬프트가 배정되어 응답 지연이 길어질 가능성이 존재합니다. 따라서 현시점의 PAIR 환경에서는 비슷한 연산 체급을 지닌 기기들끼리 클러스터를 구성할 때 가장 예측 가능하고 이상적인 부하 분산 효율을 기대할 수 있습니다.

Ollama 및 LM Studio 연동과 표준 API 프록시 구조

NVIDIA Personal AI Router는 개발자들에게 새로운 독자 프레임워크나 전용 SDK 도입을 요구하지 않습니다. 이미 로컬 거대 언어 모델 커뮤니티에서 사실상의 표준(De Facto Standard)으로 굳건히 자리 잡은 Ollama 호환 엔드포인트와 OpenAI 호환 프록시 엔드포인트를 그대로 외부에 개방하며, 응답은 표준 OpenAI JSON 형식을 취합니다. 결과적으로 개발자는 기존에 작성해 둔 수많은 파이썬, 노드JS, 러스트 기반의 에이전트 코드베이스에서 베이스 URL 한 줄만 수정하는 것으로 즉각적인 클러스터 부하 분산 혜택을 누릴 수 있습니다.

로컬 추론 엔진 생명주기 관리

PAIR 데스크톱 애플리케이션을 실행하면 첫 화면의 Overview 탭에서 현재 노드에 감지된 하드웨어 정보와 추론 엔진 상태가 카드로 정리되어 나타납니다. 만약 시스템에 아직 아무런 엔진이 설치되어 있지 않다면, 카드 내의 Engine settings를 열고 Ollama 또는 LM Studio 옆의 Install 버튼을 클릭하기만 하면 됩니다. PAIR가 시스템에 적합한 공식 실행 파일을 직접 백그라운드에서 다운로드하고 초기 구동 설정을 자동으로 마칩니다. 반대로 사용자가 사전에 수동으로 설치하여 백그라운드 서비스나 포트로 운용 중이던 기존 엔진이 있다면, PAIR는 기동 즉시 해당 인스턴스를 감지하여 관리 목록에 안전하게 연동시킵니다.

엔진이 준비되면 Add model 메뉴를 통해 원하는 오픈소스 모델 가중치를 각 노드에 내려받을 수 있습니다. 공식 문서에서는 특정 고정 모델만을 강제하지 않으며, 사용자가 환경에 맞는 모델을 자유롭게 선택하여 설치하도록 안내합니다. 특정 노드가 클러스터 내에서 특정 추론 요청의 수신 후보로 등록되려면 호환 엔진이 활성화되어 있어야 하며, PAIR의 라우팅 레이어는 해당 모델 가중치를 이미 로컬 디스크에 보유하고 있는 것으로 확인된 노드를 최우선 후보군으로 삼아 요청을 분배합니다.

OpenAI 및 Ollama 호환 엔드포인트 호출 구조

시스템 설정과 모델 준비가 완료되면 클라이언트는 PAIR가 제공하는 프록시 엔드포인트를 통해 일반적인 OpenAI 규격의 HTTP 요청을 전송하여 추론을 개시할 수 있습니다. 요청을 전송하면 PAIR 라우팅 계층이 네트워크 내의 최적 노드로 트래픽을 넘겨 추론을 수행한 뒤, 표준 OpenAI 규격의 JSON 응답을 클라이언트에게 투명하게 반환합니다.

호출이 성공적으로 처리되면 데스크톱 애플리케이션의 Jobs 탭에 해당 작업의 트랜잭션 기록이 실시간으로 추가되며, 어떤 물리적 노드가 해당 요청을 맡아 처리했는지가 명시됩니다. 구체적인 포트 번호나 세부 URL 경로는 사용자의 네트워크 환경 및 선택한 백엔드 엔진에 따라 달라질 수 있으므로, 데스크톱 애플리케이션의 Endpoints 메뉴에 명시된 안내 주소를 직접 확인하여 복사하는 것이 가장 정확합니다.

한국 개발자 및 소규모 스튜디오 관점의 실전 구축 전략

한국의 소프트웨어 엔지니어링 및 스타트업 생태계에서는 최근 클라우드 AI 서비스 비용의 급격한 상승과 더불어 데이터 보안 규제가 중요한 화두로 떠올랐습니다. 매달 수백만 원에 달하는 상용 LLM API 토큰 비용을 감당하기 어려운 1인 개발사나 독립 게임 개발 스튜디오, 그리고 사내 기밀 소스코드나 고객의 민감한 개인정보를 외부 해외 서버로 전송할 수 없는 엔터프라이즈 사내 랩 환경에서는 로컬 온프레미스 인프라의 가치가 매우 높게 평가받고 있습니다.

개발용 PC와 유휴 랩톱을 결합한 멀티 에이전트 인프라

PAIR가 가장 빛을 발하는 실전 아키텍처는 사무실이나 작업실 내에 흩어져 있는 이종 하드웨어 자원을 하나로 엮어내는 시나리오입니다. 예를 들어 고성능 그래픽 카드가 탑재된 주력 윈도우 워크스테이션이 메인 코딩 작업을 담당하고, 평소 회의용이나 문서 작업용으로 책상 한구석에 거치되어 있는 맥북, 그리고 백업용으로 상시 켜져 있는 미니 PC를 PAIR 클러스터로 묶는 구성입니다.

이러한 구성을 갖춘 상태에서 사내 메인 에이전트 시스템이 대규모 코드 리팩토링 작업을 시작하면 엄청난 시너지가 발생합니다. 메인 데스크톱이 복잡한 로직 생성과 리팩토링 초안 작성이라는 무거운 추론 작업을 처리하는 동안, 지속적으로 쏟아지는 단위 테스트 코드 검증 질의나 함수 단위 문서화 요청은 PAIR 스케줄러에 의해 유휴 상태인 보조 PC로 매끄럽게 우회됩니다. 단일 머신만 사용할 때 발생하던 심각한 대기열 지체 현상이 완전히 사라지며, 값비싼 전용 클러스터 구축 비용 없이도 체감 개발 생산성이 비약적으로 향상됩니다.

프라이버시 보호와 데이터 주권 유지

국내의 엄격한 개인정보보호법과 금융권 및 공공기관의 망분리 규제 환경을 고려할 때, PAIR가 제공하는 로컬 네트워크 완결성은 강력한 기술적 방어막이 됩니다. 클라이언트 애플리케이션, 라우팅 게이트웨이, 다운로드된 오픈소스 모델 파일, 그리고 실제 연산을 수행하는 노드 하드웨어가 동일한 물리적 로컬 서브넷 내에 완전히 격리되어 운용될 수 있기 때문입니다.

프롬프트에 포함된 사내 기밀 비즈니스 로직, 내부 API 스키마, 고객 데이터는 단 한 패킷도 공용 인터넷망으로 빠져나가지 않습니다. 외부 SaaS 의존도를 원천적으로 차단하면서도 사내에 분산된 컴퓨팅 파워를 통합 운영할 수 있다는 점은 강력한 데이터 주권(Data Sovereignty)과 보안 감사 요건을 충족해야 하는 테크 스타트업에게 독보적인 인프라적 이점을 선사합니다.

클러스터 노드 라이프사이클 관리와 안전한 제거

다수의 컴퓨터를 하나의 클러스터로 연결하고 유지 관리하는 운영 편의성 역시 PAIR의 핵심 설계 장점입니다. 복잡한 SSH 키를 생성하여 호스트 간에 복사하거나, OpenSSL을 사용해 자체 서명 루트 인증서를 발급하고 각 기기의 트러스트 스토어에 수동으로 등록하는 고통스러운 인프라 작업이 완전히 배제되어 있습니다.

6자리 PIN 기반 상호 인증과 노드 탈퇴

신규 머신을 기존 클러스터에 편입시키는 과정은 일반 소비자용 스마트 기기를 페어링하는 수준으로 단순화되어 있습니다:

  1. 먼저 기준 노드가 될 컴퓨터의 데스크톱 앱에서 Settings → Cluster 메뉴로 이동하여 새로운 노드 초대를 활성화합니다.
  2. 화면에 일회성으로 생성되어 표시되는 6자리 숫자 PIN을 육안으로 확인합니다.
  3. 새롭게 클러스터에 합류시키고자 하는 대상 기기의 앱에서 초대 수락을 누르고, 해당 6자리 PIN을 정확하게 입력하여 상호 인증을 완료합니다.
  4. 노드 간의 보안 채널이 수립되면 클러스터 토폴로지에 즉시 반영되며, 이후 발생하는 추론 트래픽의 분배 대상 노드로 자동 편입됩니다.
  5. 특정 노드를 클러스터에서 안전하게 탈퇴시키고자 할 때는 해당 기기의 Settings → Cluster 메뉴에서 Leave를 누르거나, 터미널 인터페이스의 Cluster 탭에서 단축키를 누르면 즉시 연결이 종료됩니다.
  6. 만약 특정 기기가 갑작스럽게 전원이 꺼지거나 네트워크에서 영구 이탈한 경우라도, 클러스터에 남아 있는 다른 정상 노드의 클러스터 관리 목록에서 해당 오프라인 노드를 직접 클릭하여 영구 제거할 수 있습니다.

앱 데이터 리셋과 플랫폼별 완전 삭제 절차

개발 환경을 재정비하거나 소프트웨어를 시스템에서 완전히 제거할 때, PAIR는 라우터 관리 메타데이터와 실제 모델 가중치 파일의 라이프사이클을 철저하게 분리하여 관리합니다. 클러스터 구성이 꼬였거나 엔진 설정에 오류가 발생하여 초기 상태로 되돌리고 싶다면, 앱을 재설치할 필요 없이 Settings → Service → Reset app data 메뉴를 실행하면 됩니다. 이 기능은 내부 설정값, 시스템 로그, 클러스터 인증서, 그리고 PAIR가 자동으로 내려받았던 엔진 바이너리만을 깔끔하게 삭제한 뒤 갓 설치된 상태로 서비스를 재기동합니다. 이때 사용자가 추론 엔진을 통해 내려받았던 모델 가중치 라이브러리는 엔진 자체의 저장소에 안전하게 유지됩니다.

운영체제별로 시스템에서 애플리케이션을 완전히 제거하는 절차는 다음과 같이 공식 안내를 따릅니다:

  • Windows: Windows 설정의 「설치된 앱」 메뉴나 시작 메뉴의 언인스톨 항목을 통해 제거를 수행합니다. 인스톨러가 백그라운드 서비스를 정리하고 방화벽 규칙을 청소합니다.
  • Linux 및 macOS: 시스템 패키지 관리자나 공식 안내에 따른 제거 방식을 따르며, 백그라운드 헬퍼 서비스나 설정 데이터를 완전히 정리하는 구체적인 스크립트 경로 및 상세 옵션은 사용 환경에 맞춰 공식 저장소 안내를 참고해야 합니다.

확인하지 못한 것

NVIDIA 공식 GitHub 저장소의 공개 기술 문서와 소스 코드 검토 과정에서 명확하게 사실 확인을 완료하지 못했거나, 아키텍처 특성상 추후 검증이 필요한 항목들은 다음과 같습니다:

  • GPU 하드웨어 체급 차이에 따른 동적 가중치 스케줄링 지원 여부: VRAM 용량과 연산 속도가 극단적으로 차이나는 이종 GPU 환경에서 각 기기의 벤치마크 점수나 VRAM 잔여량에 비례하여 부하 가중치를 동적으로 조절하는 기능의 공식 지원 여부는 확인하지 못했습니다. 공식 README는 현 버전이 GPU 모델과 잔여 메모리를 고려하지 않는 단일 정책만을 탑재하고 있다고 밝히고 있어 향후 로드맵 과제로 분류됩니다.
  • 단일 클러스터 내 최대 노드 연결 수의 기술적 한계: 하나의 로컬 클러스터에 공식적으로 권장되거나 네트워크 브로드캐스트/패킷 오버헤드 관점에서 기술적으로 제한되는 최대 허용 머신 수는 공식 문서에 명시되지 않아 확인하지 못했습니다.
  • Windows 10 환경에서의 구동 보장 여부: 공식 README의 지원 운영체제 항목에는 Windows 11만이 명시적으로 기재되어 있으며, 이전 세대인 Windows 10의 특정 빌드에서의 정상 구동 여부나 공식적인 지원 정책은 확인하지 못했습니다.
  • LAN 외부 원격 노드(가상 사설망/VPN) 구성의 공식 지원 여부: PAIR는 동일 로컬 서브넷 탐색(LAN discovery)을 전제로 설계되었으며, Tailscale, ZeroTier, WireGuard 등 사설 VPN 터널을 경유하여 지리적으로 분리된 원격 머신을 클러스터 노드로 안전하게 페어링할 수 있는지에 대한 공식 가이드는 확인하지 못했습니다.
  • 공식 기본 예시 모델 및 포트 번호 고정 여부: 공식 문서에는 특정 모델 태그가 고정된 표준으로 규정되어 있지 않으며, 프록시 포트 역시 환경과 엔진 설정에 따라 가변적이므로 고정된 포트 규격 여부는 확인하지 못했습니다.
  • 플랫폼별 제거 스크립트의 절대 경로 및 영속 옵션: 리눅스와 맥OS 환경에서 시스템 헬퍼 서비스와 잔여 데이터를 완전 삭제하기 위한 구체적인 스크립트 절대 경로 및 퍼지 옵션의 정합성은 릴리스 버전에 따라 다를 수 있어 공식 저장소 문서 외에는 확인하지 못했습니다.
