リモートURLにトークンが埋まっている - git の資格情報が漏れる場所

ファイルを消せば済む話ではない。六つの場所を実際の出力で確認し、事故のあとの順序を決める

2026年9月1日 開発・インフラ

資格情報の漏洩の話は、たいていコミットしたファイルから始まってコミットしたファイルで終わる。.env をうっかり入れてしまった、履歴から抜いた、終わり。ところが実務でトークンが外へ出ていく経路を数えてみると、ファイルは六つのうちの一つにすぎない。残りの五つは、ファイルの管理をどれだけうまくやっても引っかからない。

いちばんよく引っかかる場所はリモートURL だ。一度急いで https://ユーザー:トークン@ホスト/... の形でクローンしておくと、その文字列はリポジトリの設定ファイルに平文で居座り、以後 git remote -v と打つたびに画面へ戻ってくる。画面共有の最中にも出るし、貼り付けたログにも出る。

ここではその六つの場所を一つずつ押さえ、それぞれ実際に実行して確認した出力を貼る。そして最後にいちばん重要なものを整理する。すでに漏らしたあとの順序だ。その順序において、ファイルを消す作業は一番目ではない。

この記事の例はすべて明らかに偽の値と存在しないホスト(.invalid)だけを使う。実習は一時ディレクトリで HOME を別に取って隔離した状態で走らせ、貼った出力ではホームのパスだけを ~ に縮めた。攻撃の方法ではなく、自分の環境を点検する方法を扱う。

漏れる場所はファイルだけではない

まず地図を描いておく。下の六つは性格がそれぞれ違う。あるものはリポジトリの中にあり、あるものは外にある。あるものは自分の手で消せるが、あるものは他人のサーバーにある。防ぎ方が場所ごとに違うというのがこの表の要点だ。

漏れる場所どこに残るか自分の手で消せるか防ぎ方
コミットしたファイルコミットオブジェクト。クローンしたすべての複製書き換えても他人の複製までは無理コミット前に止める。無視ルールを先に置く
リモートURL のトークン.git/config。画面に出力されるたび可能。値が丸ごと入れ替わるset-url で資格情報のない URL に
.git/config作業ディレクトリ内の平文ファイル可能ヘルパーに任せ、URL には入れない
シェル履歴ホームディレクトリの履歴ファイル可能。ただし忘れやすいコマンドラインに秘密を置かない
CIログCI 提供者のサーバー保存ポリシーによって変わるトレース出力をオンにしない
コミットメッセージ・課題コミットオブジェクト、reflog、課題管理サーバーreflog は可能。サーバーは別問題貼り付ける前に一度読む

この記事は二行目と三行目にいちばん多くの紙幅を使う。一行目、つまりすでに追跡されているファイルを外す手順は、無視ルールをあとから追加しても、すでに追跡中のファイルは外れないという話で別に扱った。その記事の結論がここの出発点になる。外しても履歴には残る。だから鍵の交換が先だ。

確認した環境

以下の出力はすべて実際に実行して出たものだ。作った行はない。ただし偽のトークンと存在しないホストを使ったので、ネットワークが必要なコマンドは名前解決の段階で止まる。その点がむしろ都合よく、資格情報が接続の前にすでにどこへ記録されるのかだけを綺麗に見ることができる。

  • git — 2.48.1.windows.1
  • シェル — GNU bash 5.2.37(1)-release, Git Bash
  • プラットフォーム — MINGW64_NT-10.0-19045 (Windows 10 上の MSYS 環境)
  • 時点 — 2026年9月
  • 隔離 — 一時ディレクトリに新しいリポジトリを作り、HOME をその中へ向けて、実際のホームの設定と資格情報ファイルには触れていない

プラットフォームが Linux や macOS なら違って出る箇所が二つある。ファイル権限の表示と、OpenSSH の秘密鍵に対する権限チェックだ。それぞれ該当する節で押さえる。

git remote -v がトークンをそのまま表示する

いちばんよくある始まりはこうだ。対話的な認証が面倒か、自動化スクリプトから接続する必要があって、トークンを URL の中に入れてクローンする。動きはする。問題はその値がどこに残るかだ。

$ git remote add origin "https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git"

$ git remote -v
origin  https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git (fetch)
origin  https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git (push)

$ cat .git/config
[core]
        repositoryformatversion = 0
        filemode = false
        bare = false
        logallrefupdates = true
[remote "origin"]
        url = https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git
        fetch = +refs/heads/*:refs/remotes/origin/*

$ git config --get remote.origin.url
https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git

三つのことが一度に露わになる。第一に、remote -v はトークンを隠さない。fetch 行と push 行の二度出る。第二に、.git/config は暗号化されていないテキストファイルで、その中にトークンがそのまま入る。第三に、git config --get のようなありふれた照会コマンドも同じ値を吐く。

危険はコマンドそのものではなく、そのコマンドが実行される状況にある。git remote -v は問題が起きたときにいちばん先に打つコマンドの一つだ。つまり助けを求める瞬間、画面を共有する瞬間、課題にログを貼る瞬間に実行される。トークンが外へ出やすい条件が、ちょうどそのときに揃う。

  • 同じ値がバックアップと同期フォルダにも付いていく。作業ディレクトリを丸ごとバックアップすれば .git/config も一緒に行く
  • リモートを複数登録していると、忘れたほうに残る。upstream や古い backup リモートがよくある場所だ
  • エディタや IDE のリポジトリ情報画面も同じ値を読んで表示する

リモートURL を直す方法

直すコマンド自体は一行だ。git remote set-url で資格情報のない URL を入れ直せばよい。確認する値打ちがあるのは古い値が本当に消えるのかのほうだ。設定ファイルを手で直していると、古い行がコメントとして残ったり別のキーにコピーされたりすることがあるからだ。

$ git remote set-url origin "https://git.example.invalid/demo/demo.git"

$ git remote -v
origin  https://git.example.invalid/demo/demo.git (fetch)
origin  https://git.example.invalid/demo/demo.git (push)

$ cat .git/config
[remote "origin"]
        url = https://git.example.invalid/demo/demo.git
        fetch = +refs/heads/*:refs/remotes/origin/*

# .git ディレクトリ全体に古い値が残っていないか確認
# (リモートの追加と set-url だけを行った綺麗なリポジトリで)
$ grep -rl 'ghp_EXAMPLE' .git/
(出力なし)

綺麗に入れ替わる。set-url は url の値を丸ごと差し替えるので古い文字列は残らず、コミットオブジェクトとも無関係だ。リモートを追加した直後に検索すれば .git/config の一件が引っかかり、set-url のあとは一件も引っかからない。

ただしここで安心してはいけない。リポジトリの中が綺麗になったのであって、そのトークンが綺麗になったわけではない。その URL をコマンドラインに打ったならシェル履歴にあり、CI で使ったならログにある可能性がある。値がどこまで行ったのか確信できないなら、片づけより失効が先だ。

  • リモートが複数あるなら全部確認する。git remote -v は登録されたすべてのリモートを見せてくれる
  • サブモジュールがあれば各サブモジュールの設定も別だ。.gitmodules と各サブモジュールのディレクトリを一緒に見る
  • 変えたあとは認証をどうするか決めておく必要がある。ヘルパーに任せるのが基本で、自動化なら SSH 鍵のほうがよい

資格情報ヘルパーは何をどこに残すのか

URL にトークンを入れなければ、git は資格情報ヘルパーに尋ねる。ここで選択が分かれる。公式ドキュメントを基準にすると、git が自分で抱えているヘルパーは二つで、残りは OS 側の安全な保管領域と連携するものだ。

ヘルパーどこに置くか持続平文か似合う場所
storeホームの .git-credentials ファイル消すまでそうだ勧められる場所がほとんどない
cacheメモリ。補助プロセスが抱えている指定した時間ディスクには書かない共有マシン、短い作業
OS キーチェーン連携OS の安全な保管領域アカウントに紐づく違う個人の作業マシンの既定
URL に直接.git/config消すまでそうだない。この記事の主題

store が正確に何を残すのかは、実際に入れてみればはっきりする。ヘルパーは標準入力でキーと値を受け取る単純な規約なので、ネットワークに接続しなくても保存と照会をそのまま再現できる。

$ git config --global credential.helper store

# ヘルパーの規約どおりに偽の資格情報を一件入れる (ネットワーク接続なし)
$ printf 'protocol=https\nhost=git.example.invalid\nusername=demo-user\npassword=ghp_EXAMPLE0000000000000000000000000000\n\n' \
    | git credential-store store

$ stat -c '%a %n' ~/.git-credentials
644 ~/.git-credentials

$ cat ~/.git-credentials
https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid

# 読み戻しもそのまま通る
$ printf 'protocol=https\nhost=git.example.invalid\n\n' | git credential-store get
username=demo-user
password=ghp_EXAMPLE0000000000000000000000000000

ファイルの一行がそのまま https://ユーザー:パスワード@ホスト の形だ。つまりリモートURL にトークンを埋め込むのと保存形式が事実上同じである。違うのは場所だけだ。git の公式ドキュメントもこのヘルパーについて、パスワードを暗号化せずディスクに保存し、ファイルシステムの権限だけで保護されると書き、その妥協が受け入れられないなら cache を使うか、OS の安全な保管領域と連携するヘルパーを探すよう勧めている。

権限の数字には注意が要る。上の出力の 644 はこの Windows・MSYS 環境で stat がそう報告した値だ。公式ドキュメントはこのファイルの権限が他のユーザーに読めないよう設定されるとだけ書き、具体的な数字は明示していない。Linux で同じ値になるかは確認していない。どちらにせよ結論は変わらない。ファイルを読める主体には、トークンがそのまま見える。

  • 保存場所はホームの .git-credentials が優先で、なければ設定ディレクトリ配下の git/credentials も使われる。バックアップの対象から外しておくほうがよい
  • 消すときはファイルを手で開く代わりに、ヘルパーへ erase を渡せば該当の項目だけが抜ける
  • Git for Windows はシステム設定に manager が既定で入っている。この環境に一緒にインストールされていたヘルパーは cache、store、manager、そして選択器が一つだった
  • ヘルパーを重ねて指定すると、git は答えを得るまで順に尋ねる。古い store の設定が残っていれば、そちらが先に答えることがある

SSH 鍵の側で分かれるもの

SSH で接続すれば URL にトークンを入れる用事がなくなるので、前の問題のほとんどが消える。代わりに別の場所が生まれる。秘密鍵ファイルそのものだ。ここで分かれるのはただ一つ、パスフレーズがあるかどうかだ。

# パスフレーズなしで開くか (-y は秘密鍵から公開鍵を導出する)
$ ssh-keygen -y -P "" -f ~/.ssh/id_nopass >/dev/null 2>&1 \
    && echo "パスフレーズなし" || echo "パスフレーズが必要"
パスフレーズなし

$ ssh-keygen -y -P "" -f ~/.ssh/id_pass >/dev/null 2>&1 \
    && echo "パスフレーズなし" || echo "パスフレーズが必要"
パスフレーズが必要

# このホストに実際どの鍵が使われるのか (設定を解釈した結果)
$ ssh -G demo | grep -E '^(hostname|user|identityfile)'
user git
hostname git.example.invalid
identityfile ~/.ssh/id_demo

パスフレーズのない鍵はファイルを手に入れた側がすぐ使えるが、ある鍵にはもう一枚ある。この差はノートPCの紛失やバックアップの流出のようにファイルが丸ごと渡る状況でしか現れないが、それが実際に起きる状況だ。毎回入力するのが負担なら、エージェントに一度載せておけばよい。

二つ目のコマンドのほうが実用的だ。ssh -G は設定ファイルを解釈した最終結果を見せてくれる。鍵が複数あるとき、どのホストにどの鍵が使われるのかは推測せず、こうして確認するほうが早い。

権限も一つ押さえておく。この環境で秘密鍵を 644 に変えて接続を試みたとき、OpenSSH は権限を問題にせず、そのままホスト名の解決失敗へ進んだ。MSYS が権限を真似ているためと見られ、Linux や macOS の挙動は確認していない。どちらにせよ、秘密鍵を他のユーザーに読める状態で置いてよいことは何もない。

資格情報範囲既定の権限寿命使う場所
個人の SSH 鍵そのユーザーが届くすべてのリポジトリユーザーの権限すべて自分で消すまで人の作業マシン
デプロイキーリポジトリ一つ読み取り専用が既定。書き込みは付与可能自分で消すまでサーバー一台、リポジトリ一つ
細分化されたトークンユーザーまたは組織一つ、指定したリポジトリ項目ごとに指定既定30日、最大366日または無期限自動化、外部連携
クラシックトークン届く組織のすべてのリポジトリ広い範疇単位任意。1年未使用で自動削除減らしていく場所

デプロイキーが有用な理由がこの表にある。個人の鍵はその人が届くすべてのリポジトリへ開くのに対し、デプロイキーはリポジトリ一つに付き、既定が読み取り専用だ。サーバー一台がリポジトリ一つを取得するだけでよい、よくあるデプロイ構成において、個人の鍵をコピーして入れることとデプロイキーを作ることは、事故が起きたときの被害範囲がまるで違う。

トークンの寿命と範囲

ここまでが漏らさないための話だったとすれば、この節は漏れても小さくするための話だ。漏洩事故の大きさを決めるのは、たいてい漏洩そのものではなく、その資格情報に何ができたのか、いつまで有効なのかである。この二つは、トークンを作る画面ですでに決まっている。

2026年9月時点の GitHub ドキュメントを見ると、細分化された個人アクセストークンはユーザーまたは組織一つが所有する資源に限定され、その中でも指定したリポジトリにだけ届き、権限を項目単位で与える。一方クラシックトークンは広い範疇単位で動作し、そのユーザーが届く組織のすべてのリポジトリへ開く。同じドキュメントが有効期限の設定を強く推奨すると書いており、細分化されたトークンは既定が30日で、最大366日または無期限まで選べる。クラシックトークンも有効期限は任意だが、1年のあいだ使われなかったトークンは自動的に削除される。

組織単位で見ると、もう一層ある。組織のオーナーは、細分化されたトークンが組織の資源へアクセスする際に承認を求めるようにでき、クラシックトークンの組織アクセスを制限でき、最大寿命のポリシーを掛け、組織に掛かったトークンを確認して失効させられる。個人が作ったトークンが個人の中で終わらないという意味であり、組織の側から見ると、これが事故対応の唯一の梃子である場合が多い。

  • 無期限は利便ではなく負債だ。今が楽になる代わりに、失効の時点を永久に先送りする
  • 権限は今必要なものだけ与える。あらかじめ広く与えると、狭める契機が生まれない
  • 用途ごとにトークンを分ける。一つをあちこちで使うと、失効させるときに何が一緒に止まるのかが分からず、失効を先送りすることになる
  • トークンに用途の分かる名前を付ける。事故が起きたとき、一覧から選び出す速さが変わる
  • 人が使う資格情報と自動化が使う資格情報を混ぜない。人が辞めれば自動化も一緒に止まる

CI で漏れる仕組み

CI は資格情報がいちばん多く通り、しかも出力が自動で保管される場所だ。この組み合わせが危ない。ローカルならスクロールを上げないと見えないものが、CI ではリンク一つとして残る。

いちばんよくある事故は、デバッグしようとトレースオプションをオンにしたまま置くことだ。シェルの set -x は実行直前のコマンドを変数を展開したまま打ち出す。

$ cat ci_demo.sh
#!/bin/bash
set -x
TOKEN="ghp_EXAMPLE0000000000000000000000000000"
git ls-remote "https://x-access-token:${TOKEN}@git.example.invalid/demo/demo.git"

$ bash ci_demo.sh
+ TOKEN=ghp_EXAMPLE0000000000000000000000000000
+ git ls-remote https://x-access-token:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git

代入する行で一度、使う行でもう一度打ち出される。変数に入れておいたからといって隠れはしない。set -x の目的そのものが展開された値を見せることだからだ。

git 自身の出力はどうか。ここで結果が分かれる。エラーメッセージは資格情報を消して見せるが、トレース出力はそうしない。

# git 自身のエラーメッセージは資格情報の部分を消す
$ git ls-remote "https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git"
fatal: unable to access 'https://git.example.invalid/demo/demo.git/': Could not resolve host: git.example.invalid

# しかし GIT_TRACE は消さない
$ GIT_TRACE=1 git ls-remote "https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git"
trace: built-in: git ls-remote https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git
trace: run_command: GIT_DIR=.git git remote-https https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/...
trace: exec: git-remote-https https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/...

エラーメッセージから demo-user:ghp_...@ の部分が丸ごと抜けているのが見える。逆にトレースをオンにすると、同じ URL が複数行にわたってそのまま出る。問題が解けなくてトレースをオンにする瞬間はたいてい急いでいる瞬間であり、急いでいる瞬間の出力がそのまま CI の記録に残る。

CI 提供者のマスキングがあるから大丈夫だと考えやすいが、その機能には境界がある。GitHub のドキュメントは、シークレットではない機微な値は別の指示子で自分で隠す必要があると書き、大きなシークレットをファイルとして扱う迂回方法を説明する箇所では、ログに出力されたシークレットは隠してくれないと明記している。コマンドラインでシークレットを渡す方式も、プロセス一覧に見えうると警告している。

  • マスキングは登録された文字列と正確に一致するときに働く。値を切って使ったりエンコードしたりすれば、同じ値でも別の文字列になる
  • だからマスキングは安全網であって設計ではない。そもそも打ち出さないほうが先だ
  • トレースオプションは必要な区間だけオンにする。スクリプトの先頭に置けば全体が対象になる
  • 資格情報はコマンドライン引数の代わりに、環境変数か標準入力で渡す
  • 失敗した実行のログのほうが危ない。成功したログはあまり開かれないが、失敗ログはあちこちに貼って共有される
  • フォークから来た実行にはシークレットが渡されないのが既定だ。この制約を迂回しようとする設定が事故につながる

シェル履歴とプロセス一覧

トークンの入ったコマンドを一度でも打てば、その行は履歴ファイルへ行く。この場所がよく忘れられるのはリポジトリの外だからだ。リポジトリをどれだけ綺麗に片づけても、ホームディレクトリの履歴ファイルはそのまま残る。

この環境の Git Bash では HISTCONTROL が設定されていなかった。この変数に ignorespace が入っていれば空白で始まるコマンドは履歴に残らないのだが、既定として期待してよい挙動ではないという意味になる。シェルやディストリビューションごとに違うので、自分の環境で確認するほうがよい。

  • トークンをコマンドラインに直接打つ代わりに、ファイルか標準入力で渡す。履歴とプロセス一覧の両方を一度に避けられる
  • すでに打ったなら履歴からその行を消す。ただし消すのは二番目の仕事であり、失効が一番目の仕事だ
  • リモート接続ツールがセッションログをファイルに残す設定になっていれば、そちらにも同じ行がある。ターミナルの記録はよく忘れられる場所だ

コミットメッセージ - reflog という二つ目の複製

ファイルではなくコミットメッセージに値を書いてしまう場合がある。一時的に何を試したのかを書いておくうちに、値をそのまま移してしまう形だ。ファイルの検査器はこれを見られない。メッセージはファイルではなく、コミットオブジェクトの一部だからだ。

ここでもう一枚ある。reflog だ。git は参照が動いた履歴を .git/logs/ の下に別に記録するのだが、その記録にコミットメッセージの一行目が一緒に入る。つまりコミットを書き直したり戻したりしても、複製がもう一つ残っている。

$ git commit --allow-empty -m "oops ghp_EXAMPLE0000000000000000000000000000"

$ grep -rl 'ghp_EXAMPLE' .git/
.git/logs/HEAD
.git/logs/refs/heads/main

$ git reflog --format='%gd %gs' | head -2
HEAD@{0} commit: oops ghp_EXAMPLE0000000000000000000000000000
HEAD@{1} commit (initial): init

# reflog を失効させて整理を走らせたあと
$ git reflog expire --expire=now --all
$ git gc --prune=now
$ grep -rl 'ghp_EXAMPLE' .git/
(出力なし)

二つのファイルに残っていたものが、失効と整理を経れば消える。この実験から学ぶべきはreflog を消す方法ではなく、その逆だ。コミットを整えてログが綺麗に見えても、リポジトリの中に複製が残りうるという事実である。そしてこの整理は自分のリポジトリでだけ有効だ。すでにプッシュしていれば、サーバーと他人の複製にはそのまま残る。

  • 同じ理由で、課題やプルリクエストの本文とコメント、チャットに貼ったログもそれぞれ別の複製だ。編集しても編集履歴が残るサービスは多い
  • メッセージに値を書かなければならない状況は事実上ない。何をしたのかは書いて、どの値を使ったのかは書かない
  • 整理のコマンドは元に戻せない。reflog は事故復旧の最後の手段でもあるので、急いでいないならむやみに失効させない

コミット前に捕まえる方法

ここまでの対応はすべて、すでに起きたあとの話だ。費用がはるかに安いのは入る前に止めることである。順序は三つ。無視ルールを先に置き、フックでステージを検査し、自動検査に任せる。

フックは思ったより短い。以下はステージに上がった追加行だけを見て、資格情報の入った URL の形と秘密鍵のヘッダを見つけたらコミットを中断する例だ。

$ cat .git/hooks/pre-commit
#!/bin/sh
if git diff --cached -U0 \
   | grep -nE '^\+.*(://[^/@[:space:]]+:[^/@[:space:]]+@|-----BEGIN [A-Z ]*PRIVATE KEY-----)'; then
  echo "pre-commit: 資格情報らしき文字列がステージにある。中断する。" >&2
  exit 1
fi
exit 0

$ git add deploy.conf && git commit -m "add deploy conf"
7:+url = https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git
pre-commit: 資格情報らしき文字列がステージにある。中断する。
$ echo $?
1

# 同じファイルから資格情報だけ抜いた場合
$ git add deploy.conf && git commit -m "add deploy conf"
committed OK

引っかかる行を行番号とともに見せ、終了コード 1 でコミットを止める。資格情報を抜いた同じファイルは通る。

ただし限界ははっきりしている。フックはリポジトリごとに置くものなのでクローンしても付いてこないし、迂回もでき、パターンにない形は取り逃がす。ミスを減らす装置であって保証ではない。組織単位ではサーバー側でプッシュを検査する機能と専用のシークレットスキャナを併用するのが一般的で、そうしたツールは提供者ごとのトークンの形を知っているので、手で書いたパターンより幅が広い。

  • 無視ルールはファイルを作る前に置く。作ったあとで追加すると、すでに追跡中のファイルは外れない
  • 設定ファイルは例示用のものだけコミットする。実際の値が入るファイルは最初から無視の対象にしておく
  • フックが捕まえてくれたなら、ファイルだけ直して済ませない。その値がどこから来たのかも一緒に見る
  • フックを強制的に飛ばす選択肢があることをチームが知っておく必要がある。こっそり止める装置はこっそり迂回される
  • エージェントや自動化ツールにリポジトリを任せるときは、シークレットをそもそも渡さない構成がフックより先に来る

漏らしたあとの順序

この節がこの記事でいちばん重要だ。漏洩を見つけた瞬間に人がまずやることは、たいていファイルを消すことである。それが目に見える問題だからだ。ところがそれは一番目ではない。

GitHub のドキュメントも同じ順序を明示している。消すべき機密データがパスワードやトークンのような秘密であれば、最初の手順としてそれを失効または交換すべきだと書き、失効させればもうアクセスには使えないので、それだけで問題が解決する場合もあると付け加えている。理由は単純だ。履歴の整理には数時間かかることがあり、そのあいだそのトークンは有効なままである。

順序何をなぜこの順序なのか先送りすると起きること
1該当の鍵・トークンを直ちに失効させ、新しく発行する失効すればその値はもう鍵ではない整理しているあいだ有効なままだ
2その資格情報で何ができたのか範囲を確認する対応の大きさを決めるどこを見ればよいか分からないままログを漁る
3アクセスログと活動記録を確認する実際に使われたかどうかで分かれる保存期限が過ぎれば見られない
4他の場所にも同じ値がないか点検する同じトークンを複数の場所に入れている例が多い一か所だけ直して終わったと信じてしまう
5そのあとでようやく履歴の整理協力者全員に影響する急いでやって他のものを壊す

2番は飛ばしやすいのだが、これが対応の大きさを決める。読み取り専用のデプロイキー一つが漏れたのと、組織全体に書き込み権限のあるトークンが漏れたのとでは、以後やるべきことがまったく違う。前の節で範囲を狭めておけと言った理由が、ここで表に出る。

  • 失効がサービスを止めるのではないかと心配して先送りしがちだが、その心配自体が一つのトークンを複数の場所で使った結果だ
  • 新しいトークンは古いトークンと同じ権限で作らない。事故を契機に範囲を狭める
  • 記録を残す。いつ何がどこへ漏れ、何を失効させたのか
  • 一人で判断しない。組織の資格情報なら決められた報告経路があり、遅れて知らせるほうがたいてい悪い

なぜ履歴の整理だけでは足りないのか

履歴の書き換えは目に見える結果が確かなので解決した感じを与える。ログを開けばそのコミットがない。しかしそのコミットは、すでに複数の場所へ複製されている可能性がある。

GitHub のドキュメントは、履歴だけを書き換えて強制プッシュした場合に、機密データを含むコミットが依然としてアクセス可能な場所を三つ挙げている。リポジトリのクローンとフォーク、SHA-1 ハッシュで直接アクセスされるキャッシュされた表示、そしてそのコミットを参照するプルリクエストだ。フォークに残ったものはフォークの所有者と別に調整する必要があるとも書かれている。

より現実的な危険は再汚染だ。同じドキュメントはこう書いている。同僚が書き換え前のクローンを持っていて、書き換え後にそのまま pull して push すれば、機密データが戻ってくる。整理を終えたあとでも、チームの一人の習慣的な動作で元どおりになりうるという意味だ。

  • 公開リポジトリならクロールとミラーが加わる。公開した時点から整理の時点までに何が持っていったのかは、知る方法がない
  • 社内リポジトリもバックアップのスナップショットと検索インデックスに複製が残る。保存ポリシーを確認しなければ、消したとは言えない
  • だから履歴の整理は衛生作業であって復旧ではない。復旧は1番ですでに終わっていなければならない

個人リポジトリでも守る理由

一人で使う非公開のリポジトリなら、わざわざ気にする必要があるのかという反問は自然だし、実際に危険の大きさは違う。ただし非公開という状態が永久ではないのが問題だ。

  • 公開設定は変わる。オープンソースに切り替えたり、ポートフォリオとして公開したりした瞬間、履歴全体が一緒に公開される。そのとき過去のコミットを一つずつ見ていく人はまれだ
  • 協力者が追加される。一人を招待した瞬間、その人は履歴全体を受け取る。最近のコミットだけを渡す方法はない
  • バックアップが別の場所へ行く。リポジトリを丸ごと圧縮してクラウドへ上げたり、別のマシンへ移したりすれば .git も一緒に行く
  • アカウントが危うくなりうる。アカウント一つが破られれば、そのアカウントのすべての非公開リポジトリが一度に開く。非公開はアカウントのセキュリティに乗っかっている状態だ
  • マシンが変わる。ノートPCの交換や紛失の際、作業ディレクトリとホームの資格情報ファイルが一緒に動く
  • ツールが読む。エディタの拡張、分析ツール、エージェントが作業ディレクトリを読む。何がどこへ行くのかはツールごとに違う

まとめると、非公開リポジトリの安全は今この瞬間の設定に頼っており、その設定は数年のあいだに何度も変わる。一方、履歴に入った値はそのまま残る。時間は片方の味方しかしない。

予防の習慣リスト

新しいツールを導入しなくても守れるものだけを集めた。順序は効果の大きいものからだ。

  • リモートURL に資格情報を入れない。認証はヘルパーか SSH 鍵に任せる。これ一つで三つの場所が同時にふさがる
  • トークンに有効期限を掛ける。無期限を選ばないだけで、事故に有効期間が生まれる
  • 権限を今必要な分だけ与える。あとで増やすほうがよい。広く与えた権限は狭める契機がない
  • 用途ごとに資格情報を分ける。失効させるとき何が止まるのかが分かって初めて、実際に失効させられる
  • サーバーにはデプロイキーを使う。個人の鍵をコピーして入れない。読み取りだけ必要なら読み取り専用にしておく
  • 秘密鍵にパスフレーズを掛ける。ファイルが丸ごと渡る状況で唯一残る一枚だ
  • 平文で保存するヘルパーを既定にしない。OS の安全な保管領域と連携するほうを選ぶ
  • トレースオプションを常時オンにしない。必要な区間だけ、終わったら切る
  • 無視ルールをファイルより先に作る。順序が逆になれば追跡はすでに始まっている
  • フックでステージを検査する。完璧でなくても、いちばんよくあるミスは捕まえる
  • 画面を共有する前にリモートURL を確認する。数秒で済む
  • 定期的にトークンの一覧を開いてみる。使っていないものを消す

最後に自己点検用の三行を置く。リポジトリの中でそのまま貼り付けて走らせればよい。三つの場所を一度に見る。

# ① リモートURL に資格情報が埋まっているか
git remote -v | grep -E '://[^/@]+@' && echo "リモートURL に資格情報がある"

# ② 履歴の変更内容に同じ形があるか
git log --all -p | grep -cE '://[^/@[:space:]]+:[^/@[:space:]]+@'

# ③ コミットメッセージにあるか
git log --all --format='%B' | grep -cE '://[^/@[:space:]]+:[^/@[:space:]]+@'

②と③は個数を数える。0 ならその形はないという意味だ。この検査はユーザー名とパスワードの付いた URL の形だけを見る。ファイルの中に別途書かれた鍵や、提供者ごとのトークンの形は捕まえられないので、そちらは専用のスキャナに任せるほうがよい。大きなリポジトリでは②に時間がかかる。

まとめ

資格情報が漏れる場所はコミットしたファイル一つではなく六つで、そのうちいちばんよく引っかかるのはリモートURL に埋まったトークンだ。その値は .git/config に平文で座っていて、git remote -v と打つたびに画面へ戻ってくる。直すのは git remote set-url 一行だ。

漏れても小さくするほうは、トークンを作る画面で決まる。有効期限を掛け、範囲を狭め、用途ごとに分ける。

すでに漏らしたのなら順序がすべてだ。失効、範囲の確認、ログの確認、そのあとに履歴の整理。ファイルを消す作業は四番目か五番目である。履歴をどれだけ綺麗に書き直しても、クローンとフォークとキャッシュに残った複製は回収されず、書き換え前のクローンを持った同僚が一人 pull して push すれば戻ってくる。整理は後始末であって解決ではない。解決は一行目で終わる。

確認できなかったこと

  • .git-credentials ファイルの権限は、この Windows・MSYS 環境で stat が 644 と報告した値だ。公式ドキュメントは他のユーザーが読めないよう権限が設定されるとだけ書き数字を明示しておらず、Linux で実際にどの値になるのかは確認していない
  • 秘密鍵を 644 にして接続を試みたとき、この環境の OpenSSH は権限を問題にしなかった。MSYS が権限を真似ているためと見られるが、Linux・macOS で同じ状態がどう扱われるのかは確認していない
  • エラーメッセージから資格情報が消えていたのは、名前解決の失敗段階で git が自ら出したメッセージについての観察だ。実際のサーバーが認証失敗で返す応答の本文が何を含むのかは確認していない
  • トレース出力のうち HTTP 通信層のヘッダ隠蔽の挙動は、実際の接続をしていないので観察できなかった。上の出力は GIT_TRACE のコマンド実行記録に限られる
  • シークレットスキャナ製品の実際の検出率と誤検出率は試験していない。ツールがあるという事実だけを書き、特定の製品を評価してはいない
  • GitHub 以外のホスティングサービスのトークン有効期限の既定値と組織ポリシーは確認していない。上の数値は2026年9月時点の GitHub ドキュメントに限られる
