이모지 하나가 11글자로 세진다 - ZWJ 시퀀스와 글자 수 검증

문자열의 길이는 하나가 아니다. 다섯 개의 숫자 중 무엇을 세야 하는지 정하는 법

2026-07-30 개발/인프라

서론: 「20자 제한」이 이모지 하나에 뚫린다

닉네임 입력란에 「최대 20자」라고 적혀 있다. 사용자가 열두 글자를 쓰고 이모지 두 개를 붙였다. 화면의 카운터는 14를 보여주는데 저장 버튼을 누르면 「20자를 초과했습니다」가 나온다. 사용자는 열네 글자를 세었고 서버는 다른 것을 세었다.

이 신고는 재현이 안 된다고 닫히기 쉽다. 개발자가 자기 이름으로 테스트하면 문제가 없기 때문이다. 그리고 그게 정확히 이 버그가 몇 년씩 살아남는 이유다.

원인은 하나뿐이다. 문자열의 길이는 하나가 아니다.

  • UTF-8 바이트 — 저장과 전송이 보는 숫자
  • UTF-16 코드유닛 — JavaScript .length가 돌려주는 숫자
  • 코드포인트 — Python len()이 돌려주는 숫자
  • 그래핌 클러스터 — 사람이 세는 「한 글자」
  • 표시 폭 — 화면에서 차지하는 칸 수

다섯 개다. 그리고 대부분의 입력에서는 다섯 숫자가 전부 같다. 영문과 숫자만 들어오면 hello world는 어느 자로 재도 11이다. 한글이 들어오면 바이트만 갈린다. 이모지가 들어오는 순간 다섯 개가 전부 흩어진다.

「20자 제한」이라는 문장은 이 다섯 중 무엇인지 안 적어서 규격이 아니다. 이 글은 다섯 숫자를 직접 세어 보이고, 마지막에 목적별로 무엇을 세야 하는지 정하는 표를 놓는다. 결론은 「이모지를 막으세요」가 아니다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 런타임은 Node.js v22.16.0 (win32/x64, V8 12.4, ICU 77.1, Unicode 16.0)과 Python 3.13.3 (unicodedata 15.1.0)이다. Intl.Segmenter는 사용 가능했고, Python 쪽 서드파티 regex 모듈은 설치되어 있지 않았다. 없는 것은 없다고 적었다.

코드포인트는 U+XXXX로 병기한다. 이 글의 소재가 이모지라서, 브라우저나 터미널이 글리프를 못 그리면 아무것도 확인할 수 없다. 그래서 모든 표본은 코드포인트 목록을 함께 싣는다. 실제로 검증 과정에서도 눈으로 본 모양이 아니라 16진수 출력으로 판단했다. 문자열은 전부 String.fromCodePoint와 chr()로 코드포인트에서 조립했고, 소스 리터럴과 일치하는지 대조해 확인했다.

이 글이 다루지 않는 것. 한글이 유니코드 안에서 두 가지 코드포인트열이 되는 정규화 원리는 NFC와 NFD에서 다뤘다. 여기서는 5절에서 길이가 갈린다는 숫자만 보인다. 문자셋을 잘못 읽어 글자가 깨지는 인코딩 진단은 cp949와 UTF-8에 있고, 8절에서는 바이트 길이만 다룬다. 한글 음절을 정규식 범위로 다루는 산술은 한글 정규식 함정에 있고, 7절은 이모지에 대한 점과 플래그만 본다.

1. 이모지 하나를 해부한다 - 네 개의 숫자

가족 이모지 하나를 놓고 네 가지 방식으로 세어 봤다. 표본은 U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466, 화면에는 👨‍👩‍👧‍👦 하나로 보이는 것이다.

왜 이렇게 되는지는 코드포인트별로 쪼개 보면 바로 보인다.

  U+200D       1              3             ZERO WIDTH JOINER

  • 그림문자 네 개가 각각 UTF-16 코드유닛 2개를 차지한다. U+1F468 같은 문자는 U+FFFF보다 위에 있어서 UTF-16에서 한 자리에 안 들어간다. 두 개의 코드유닛(서로게이트 페어)으로 표현된다. 4 곱하기 2는 8
  • 접착제 U+200D 세 개가 각각 1개를 차지한다. 이 문자는 U+FFFF 아래라 한 자리로 들어간다. 8 더하기 3은 11
  • UTF-8에서는 그림문자가 4바이트, 접착제가 3바이트다. 4 곱하기 4에 3 곱하기 3을 더하면 25
  • 코드포인트는 그냥 개수를 센 것이라 7이다
  • 그래핌 클러스터는 1이다. 유니코드 표준 부속서 29가 정한 규칙으로 나눈 결과이고, 사람이 세는 수와 같다

여기서 각 단위의 이름을 정확히 붙여 두면 나머지가 쉬워진다.

마지막 줄에 답이 두 개인 이유는 11절에서 따로 다룬다. 표시 폭은 데이터의 성질이 아니라 렌더러의 성질이기 때문이다.

2. ZWJ가 접착제다 - U+200D를 빼면 하나가 넷이 된다

이 글의 제목에 있는 ZWJ는 U+200D ZERO WIDTH JOINER다. 폭이 0인 눈에 보이지 않는 문자이고, 하는 일은 앞뒤의 그림문자를 하나로 붙이는 것이다. 정말 그런지 빼 보면 된다.

with    U+200D : cps=7  units=11  bytes=25  graphemes=1
without U+200D : cps=4  units=8   bytes=16  graphemes=4
without U+200D code points : U+1F468 U+1F469 U+1F467 U+1F466
grapheme split             : [U+1F468] [U+1F469] [U+1F467] [U+1F466]

one glue character removed -> 1 grapheme becomes 4.
the utf-8 byte count only dropped from 25 to 16.

접착제 세 개를 빼자 그래핌이 1에서 4가 됐다. 화면에 한 덩어리로 보이던 가족이 남자·여자·여아·남아 넷으로 흩어진다. 그런데 바이트는 25에서 16으로 조금 줄었을 뿐이다. 이 대비가 중요하다. 저장 용량으로 보면 큰 변화가 없는데 「글자 수」는 4배가 됐다.

사슬을 한 칸씩 늘려 가면 구조가 더 분명해진다.

growing the chain, one link at a time:
  cps units bytes graphemes  code points
  ----------------------------------------------------------------------
  1    2     4      1          U+1F468
  2    3     7      1          U+1F468 U+200D
  3    5     11     1          U+1F468 U+200D U+1F469
  5    8     18     1          U+1F468 U+200D U+1F469 U+200D U+1F467
  7    11    25     1          U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466

note row 2: U+1F468 U+200D is a DANGLING joiner, an invalid sequence,
and it still counts as 1 grapheme.
  • 그래핌은 계속 1이다. 코드포인트가 1에서 7로, 바이트가 4에서 25로 여섯 배 늘어나는 동안 사람이 세는 수는 변하지 않는다
  • 두 번째 줄이 실무에서 중요하다. U+1F468 U+200D는 아무것도 잇지 않는 접착제가 매달린 상태다. 유니코드 규격상 유효한 시퀀스가 아니지만 그래핌 개수는 여전히 1이고, 어느 층에서도 오류가 나지 않는다
  • 이 상태는 문자열을 잘랐을 때 실제로 생긴다. 5절에서 그 지점을 본다
  • 부속서 29의 규칙 GB11이 이 동작을 정의한다. 그림문자와 접착제와 그림문자 사이는 자르지 않는다는 규칙이다. 그래서 매달린 접착제도 앞 글자에 붙는다

유니코드 기술 표준 51은 이 방식을 emoji ZWJ sequence라고 부르고, 구현이 이 시퀀스를 하나의 글리프로 처리하기 위한 장치라고 설명한다. 즉 이건 버그도 부작용도 아니고 설계된 동작이다. 이모지를 늘리려면 새 코드포인트를 계속 만들어야 하는데, 접착제를 쓰면 기존 문자를 조합해 새 그림을 만들 수 있다. 그 대가가 길이의 폭발이다.

3. 피부색과 국기 - 붙어서 하나가 되는 다른 방식들

접착제 말고도 여러 코드포인트가 하나로 뭉치는 방식이 세 가지 더 있다. 각각 확인했다.

3.1 피부색 변경자는 별도 코드포인트다

label                  cps  units  bytes  graphemes  code points
------------------------------------------------------------------------------
thumbs up bare         1    2      4      1          U+1F44D
thumbs up tone-2       2    4      8      1          U+1F44D U+1F3FC
thumbs up tone-3       2    4      8      1          U+1F44D U+1F3FD
thumbs up tone-5       2    4      8      1          U+1F44D U+1F3FF
modifier alone         1    2      4      1          U+1F3FD
man + tone-3           2    4      8      1          U+1F468 U+1F3FD

toned couple with a variation selector - the realistic worst case:
  U+1F468 U+1F3FB U+200D U+2764 U+FE0F U+200D U+1F469 U+1F3FF
  cps=8  units=12  bytes=28  graphemes=1
  U+FE0F is VARIATION SELECTOR-16, 3 more bytes that draw nothing.
  • 피부색은 원래 문자에 색을 칠하는 것이 아니다. 뒤에 변경자 코드포인트를 하나 더 붙인다. 그래서 길이가 정확히 두 배가 된다. 코드포인트 1에서 2, 바이트 4에서 8
  • 다섯 단계 어느 것을 붙여도 길이는 같다. U+1F3FB부터 U+1F3FF까지 전부 4바이트다
  • 변경자 혼자서도 하나의 그래핌이다. 기반 문자 없이 U+1F3FD만 남으면 색 견본 같은 것이 그려진다
  • 마지막 표본이 실무에서 만날 최악에 가깝다. 피부색 두 개에 접착제 두 개, 그리고 U+FE0F가 붙어 코드포인트 8개, 28바이트가 한 글자다
  • U+FE0F는 VARIATION SELECTOR-16이다. 앞 문자를 그림 형태로 그리라는 지시일 뿐 아무것도 그리지 않으면서 3바이트를 쓴다. 길이 계산에서 자주 빠뜨리는 값이다

3.2 국기는 지역 표시 문자 두 개다

label        cps  units  bytes  graphemes  code points
----------------------------------------------------------------------
KR flag      2    4      8      1          U+1F1F0 U+1F1F7
JP flag      2    4      8      1          U+1F1EF U+1F1F5
US flag      2    4      8      1          U+1F1FA U+1F1F8

a single regional indicator U+1F1F0 alone:
  cps=1  units=2  bytes=4  graphemes=1
  it is not half a flag - it is a boxed letter K.

pairing is greedy, left to right:
  2 RI  U+1F1F0 U+1F1F7   graphemes=1   [U+1F1F0 U+1F1F7]
  3 RI  + U+1F1FA         graphemes=2   [U+1F1F0 U+1F1F7] [U+1F1FA]
  4 RI  + U+1F1F8         graphemes=2   [U+1F1F0 U+1F1F7] [U+1F1FA U+1F1F8]

deleting ONE regional indicator re-pairs everything after it.

tag sequence flag (black flag + 5 tag letters + terminator):
  U+1F3F4 U+E0067 U+E0062 U+E0073 U+E0063 U+E0074 U+E007F
  cps=7  units=14  bytes=28  graphemes=1

국기에는 전용 코드포인트가 없다. 알파벳에 대응하는 지역 표시 문자 두 개를 나란히 놓으면 렌더러가 국기로 그린다. 한국 국기는 K에 해당하는 U+1F1F0과 R에 해당하는 U+1F1F7이다.

  • 하나만 남기면 반쪽 국기가 되지 않는다. 네모 안에 든 글자 K가 보인다. 데이터로는 완전히 유효한 하나의 그래핌이다
  • 짝짓기는 왼쪽부터 탐욕적이다. 세 개를 놓으면 앞 두 개가 국기가 되고 세 번째는 혼자 남는다. 부속서 29의 규칙 GB12와 GB13이 홀수 번째 앞에서만 자른다고 정의한 결과다
  • 그래서 가운데 하나를 지우면 뒤에 있던 국기들이 전부 다른 나라로 바뀐다. 국기를 여러 개 쓰는 입력에서 백스페이스 한 번이 이런 일을 한다
  • 마지막 표본은 태그 시퀀스다. 검은 깃발 하나에 태그 문자 다섯 개와 종료자가 붙어 코드포인트 7개, 28바이트가 한 글자다. 국가 하위 지역 깃발이 이 방식을 쓴다
  • 기술 표준 51은 유효한 국기 시퀀스만 규격 데이터 파일에 등재된 것이라고 못 박는다. 즉 임의의 두 글자를 붙이면 국기가 아니라 글자 두 개로 보인다

이모지가 길어지는 방식을 정리하면 네 가지다.

4. 이모지만의 문제가 아니다 - 한글 NFD와 결합 악센트

여기까지 읽고 「이모지를 막으면 되겠다」고 생각하기 쉽다. 그런데 이모지가 없어도 길이는 갈린다. 확인해 봤다.

숫자만 읽으면 된다. 화면에 똑같이 「한글」로 보이는 두 글자가 한쪽은 .length 2, 다른 쪽은 6이다. 바이트는 6 대 18로 세 배 차이가 난다. 그런데 그래핌은 양쪽 모두 2다.

  • 같은 글자가 완성형 코드포인트 하나로도, 자모 세 개로도 표현된다. 어느 쪽이든 유효한 유니코드다
  • 왜 이렇게 되는지의 원리와 어디서 생기는지는 이 글의 범위가 아니다. NFC와 NFD에 정리해 뒀다. 여기서는 길이가 갈린다는 사실만 필요하다
  • 라틴 문자도 같다. U+00E9 하나와 U+0065 U+0301 둘이 화면에 같은 글자로 보인다
  • 결합 문자는 개수 제한이 없다. 세 개를 쌓아도 그래핌 1이고, 뒤에서 보듯 200개를 쌓아도 1이다
  • 결론이 중요하다. 코드유닛과 그래핌이 갈리는 현상은 이모지가 만든 것이 아니다. 이모지는 그 격차를 25배까지 벌려 눈에 보이게 만든 것뿐이다

부속서 29가 이 문제를 정면으로 언급한다. 하나의 코드포인트가 사용자가 생각하는 「한 글자」와 항상 같지는 않다는 것이고, 문서가 드는 예도 문자에 악센트를 결합한 경우다. 그래핌 클러스터는 그 격차를 메우려고 정의된 단위다.

8. 저장과 전송 - 4바이트 문자가 걸리는 벽

길이 계산이 맞아도 저장 계층에서 다시 막힌다. 경계가 정확히 어디인지 확인했다.

--------------------------------------------------------------------------
ascii            9    1               9           stores fine

grinning         1    4               4           REJECTED - needs 4 bytes

the boundary is exact:
  U+FFFF  utf-8 length = 3   last BMP code point
  U+10000 utf-8 length = 4   first code point above it

label            utf8 bytes  cp949 encode          shift_jis encode
----------------------------------------------------------------------
ascii            9           ok 9 B                ok 9 B

경계는 U+FFFF다. 그 아래는 UTF-8에서 최대 3바이트, 그 위는 4바이트다. 그리고 모든 이모지는 U+FFFF 위에 있다. 그래서 문자당 3바이트까지만 받는 문자셋은 이모지를 하나도 담지 못한다. 대표적인 사례가 이름은 UTF-8인데 3바이트까지만 저장하는 오래된 데이터베이스 문자셋이고, 레거시 문자셋인 cp949와 shift_jis는 아예 인코딩 예외를 던졌다.

여기서 컬럼 길이를 문자 수로 잡는 것과 바이트로 잡는 것이 갈린다. 같은 닉네임으로 계산해 봤다.

column arithmetic for the nickname, four definitions of "20"
  declared as        needs   verdict
  ----------------------------------------
  20 bytes           39      OVERFLOW
  20 utf-16 units    25      OVERFLOW
  20 code points     21      OVERFLOW
  20 graphemes       15      fits

how many bytes must you reserve for "20 characters"?
  20 code points, worst case utf-8   : 80 bytes
  20 family emoji                    : 500 bytes (cps=140, units=220)
  20 kiss sequences                  : 700 bytes (cps=200, units=300)
  1 grapheme, 200 combining marks    : 401 bytes (cps=201, graphemes=1)
  20 graphemes of stacked marks      : 8020 bytes
  -> "20 graphemes" has NO byte upper bound.

이 계산이 이 절의 핵심이다.

「20자」의 정의필요한 UTF-8 바이트상한이 있나컬럼 크기로 쓸 수 있나
20 바이트20있음쓸 수 있다 (정의 자체가 바이트)
20 UTF-16 코드유닛최대 80있음쓸 수 있다 (80으로 잡을 것)
20 코드포인트최대 80있음쓸 수 있다 (80으로 잡을 것)
20 그래핌가족 이모지 500 / 결합 문자 8,020없음쓸 수 없다
  • 그래핌으로 컬럼 크기를 잡으면 안전한 값이 존재하지 않는다. 그래핌 하나에 들어갈 코드포인트 개수에 상한이 없기 때문이다. 결합 문자 200개를 쌓아도 그래핌은 1이고 바이트는 401이다
  • 실제로 20그래핌짜리 문자열이 8,020바이트까지 커지는 것을 확인했다. VARCHAR(20)에 들어갈 수 있는 값이 아니다
  • 그래서 표시용 한도와 저장용 한도를 분리해야 한다. 화면 카운터는 그래핌, 컬럼 크기는 바이트다. 하나로 합치려는 시도가 이 버그의 원인이다
  • 검증도 두 조건을 모두 걸어야 한다. 그래핌 20 이하이면서 바이트 상한 이하일 때만 통과시킨다
  • 거부할 때 어느 조건에 걸렸는지 사용자에게 알려야 한다. 「20자를 초과했습니다」만 나오면 15자를 센 사용자는 이해할 수 없다

9. JSON과 URL - 같은 이모지가 몇 배로 부푸나

  • Base64가 가장 효율적이지만 사람이 읽을 수 없다. 로그와 디버깅 비용을 생각해야 한다

9.1 반쪽 이모지는 계층마다 다르게 반응한다

what happens to a half emoji downstream:
  JSON.stringify(lone high surrogate) : "\ud83d"
  JSON.parse of that                  : succeeds, isWellFormed=false
  encodeURIComponent(...)             : THROWS URIError - URI malformed
  Buffer.from(...,"utf8")             : EF BF BD   silently replaced by U+FFFD
  -> JSON accepts it, the URL layer throws, the byte layer corrupts it.
     three layers, three different behaviours, no error at the source.

이것이 진단을 어렵게 만드는 구조다. 발생 지점에서는 아무 오류도 나지 않는다.

  • JSON은 통과시킨다. 직렬화도 되고 역직렬화도 성공한다. 다만 결과가 isWellFormed()에서 false다
  • URL 계층은 예외를 던진다. 이 지점에서야 처음으로 오류가 보인다. 그런데 잘라 낸 코드와는 멀리 떨어져 있어서 원인 추적이 어렵다
  • 바이트 계층은 조용히 망친다. 대체문자로 바꿔 놓고 성공으로 보고한다. 가장 위험한 동작이다
  • 그래서 자른 직후에 검증해야 한다. isWellFormed() 한 줄이 세 계층의 문제를 발생 지점에서 잡는다

11.1 표시 폭은 데이터의 성질이 아니다

가족 이모지의 폭이 특히 흥미롭다. 코드포인트별로 더하면 그림문자 4개가 2칸씩 8칸, 접착제 3개가 0칸이라 합이 8이다. 그런데 시퀀스를 지원하는 터미널은 한 글리프를 2칸에 그린다.

  • 같은 데이터가 2칸이거나 8칸이다. 렌더러가 그 시퀀스를 아는지에 달려 있다
  • 어떤 라이브러리도 이것을 확정할 수 없다. 폰트를 모르면 계산이 불가능하다. 다섯 개 중 유일하게 데이터만으로 결정되지 않는 값이다
  • 그래서 고정폭 정렬은 이모지 앞에서 원리적으로 깨진다. 표 폭을 이모지가 든 문자열로 맞추려 하면 어느 터미널에서는 어긋난다
  • 실무 대응은 두 가지다. 이모지가 든 열은 고정폭 정렬을 포기하거나, 표시 전에 이모지를 자리표시자로 치환하는 것이다

11.2 문자 메시지 과금은 또 다른 자다

  --------------------------------------------------------------
  ascii only                 GSM-7     93     93         1

  the ascii message is 93 characters, GSM-7, ONE segment (limit 160).
  adding ONE emoji forces UCS-2, where the limit is 70 units.

how many "characters" fit in one UCS-2 segment of 70 units:
  ascii or ideographs   70 of them
  grinning              35 of them
  KR flag               17 of them
  thumb + tone          17 of them
  family                6 of them

이 표가 과금과 직결된다.

  • 아스키만 있으면 GSM-7로 인코딩되고 한 세그먼트가 160자다. 93자 메시지는 한 세그먼트다
  • 비아스키 문자가 하나라도 들어가면 메시지 전체가 UCS-2로 바뀐다. 그 순간 한 세그먼트 한도가 70유닛으로 줄어든다
  • 그래서 이모지 하나를 붙이자 93자 메시지가 두 세그먼트가 됐다. 사용자는 한 글자를 더했다고 생각하는데 요금은 두 배다
  • 한 세그먼트에 들어가는 가족 이모지는 6개다. 사용자 눈에는 여섯 글자인데 그것으로 문자 하나가 꽉 찬다
  • 여기서 세야 하는 것은 UTF-16 코드유닛이다. 그래핌으로 세면 요금 계산이 틀린다

12. 무엇을 세야 하는가 - 목적별 판단표

이 글의 결론은 「이모지를 막으세요」가 아니다. 당신이 세려는 「글자」가 무엇인지 정하라는 것이다. 목적이 단위를 정한다.

목적세야 할 단위왜 그것인가검증 방법
화면의 「n자 남음」 카운터그래핌사람이 세는 수와 일치해야 한다가족 이모지 하나가 1로 세지는지 확인
DB 컬럼 크기 결정바이트저장 한도의 단위가 바이트다최악 케이스 바이트로 계산했는지
입력 폼 하드 리밋그래핌 + 바이트 둘 다표시 한도와 저장 한도가 다르다두 조건 모두 걸고, 어느 쪽에 걸렸는지 안내
문자 메시지 과금UTF-16 코드유닛UCS-2 세그먼트가 유닛 단위다70유닛 경계와 세그먼트 수 계산
고정폭 화면 배치표시 폭레이아웃은 칸 수로 결정된다실제 폰트로 확인, 확정 불가를 전제로 설계
언어 간 API 계약바이트모든 언어에서 같은 값이 나오는 유일한 단위양쪽에서 같은 표본으로 같은 수가 나오는지
중복 검사·해시·정렬 키정규화 후 바이트같은 글자가 다른 바이트일 수 있다정규화를 먼저 하는지
검색 색인 토큰 길이코드포인트대부분의 색인기가 코드포인트로 동작색인기 문서에서 단위 확인

표를 쓸 때의 핵심은 세 번째 줄이다. 실무의 입력 검증은 단위를 하나만 고르는 문제가 아니다. 표시용과 저장용을 따로 두고 둘 다 검사해야 한다. 이 둘을 하나로 합치려는 시도가 서론의 버그를 만든다.

  • 규격 문서에 단위를 적어라. 「닉네임 최대 20자」가 아니라 「닉네임 최대 20 그래핌, 저장 한도 80바이트」로 적는다
  • 프런트와 백엔드가 같은 단위를 쓰는지 같은 표본으로 확인하라. 언어가 다르면 length의 뜻이 다르다
  • 거부 메시지에 단위와 초과량을 넣어라. 「20 글자를 초과했습니다」는 15자를 센 사용자에게 무의미하다
  • 자르지 말고 거부하라. 조용히 자르면 데이터가 손상되고 사용자는 눈치채지 못한다. 자를 수밖에 없다면 그래핌 단위로 자르고 검증한다
  • 저장 계층이 4바이트 문자를 받는지 먼저 확인하라. 길이 계산이 맞아도 여기서 막히면 전부 무의미하다

13. 조용히 지나가는 이유와 테스트 표본

마지막으로 이 버그의 성질을 정리한다. 왜 몇 년씩 살아남는가.

  • 대부분의 입력에서 다섯 숫자가 같다. 아스키 11자는 바이트·코드유닛·코드포인트·그래핌이 전부 11이다. 개발자가 자기 이름으로 테스트하면 아무 문제가 없다
  • 재현 조건이 좁다. 특정 종류의 이모지, 특정 길이, 특정 자르기 지점이 맞아야 터진다. 신고가 「재현 불가」로 닫힌다
  • 실패가 조용하다. 반쪽 서로게이트는 JSON을 통과하고, 대체문자는 오류 없이 저장된다. 로그에 아무것도 안 남는다
  • 보이는 곳과 터지는 곳이 멀다. 자른 코드와 예외를 던지는 URL 계층이 서로 다른 모듈이다
  • 눈으로 검수해도 안 잡힌다. U+200D 잔해와 U+FEFF는 화면에 아무것도 그리지 않는다

그래서 필요한 것은 표본이다. 테스트 데이터에 아래를 넣으면 이 글의 모든 사고가 개발 단계에서 잡힌다.

  • ZWJ 시퀀스 — U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466 (그래핌 1, 코드유닛 11, 바이트 25)
  • 국기 — U+1F1F0 U+1F1F7과 국기 세 개를 연달아 놓은 표본 (짝짓기 재배열 확인)
  • 피부색 변경자 — U+1F44D U+1F3FD
  • U+FE0F가 든 시퀀스 — 폭 0의 3바이트가 계산에서 빠지지 않는지
  • 한글 NFD — U+1112 U+1161 U+11AB (그래핌 1, 코드포인트 3)
  • 결합 악센트 — U+0065 U+0301과 마크를 여러 개 쌓은 표본
  • 태그 시퀀스 — 근사치 정규식이 틀리는 것을 확인하는 표본
  • 짝 잃은 서로게이트가 든 문자열 — 검증 함수가 실제로 잡는지 확인
  • 경계 길이 표본 — 한도 직전, 한도, 한도 직후에서 자르기 지점이 이모지 중간에 오도록 맞춘 것
  • 아스키만 든 표본 — 대조군으로. 여기서는 모든 단위가 같아야 한다

마지막 항목이 의외로 중요하다. 아스키 표본만 통과하는 테스트는 아무것도 검증하지 않는다. 다섯 숫자가 같은 구간에서만 확인한 것이기 때문이다.

# 이모지 글자 수 — 다섯 가지 길이 대조표와 안전한 세기·자르기

> 출처: braindetox.kr — 이모지 하나가 11글자로 세진다
> 근거: Windows 10 / Node.js v22.16.0 (ICU 77.1, Unicode 16.0) / Python 3.13.3 실행 검증
> 이 파일을 그대로 AI에 붙여 「이 기준으로 우리 입력 검증을 점검해줘」라고 쓰면 됩니다.
> ⚠ 결론부터: 「20자 제한」은 문장이 아니라 **단위를 적어야** 규격이 됩니다.

## 0. 30초 요약

문자열의 길이는 **하나가 아니다.** 같은 이모지 하나(👨‍👩‍👧‍👦)를 세면 숫자가 이렇게 갈린다.

| 단위 | 값 | 이 숫자를 보는 곳 |
|---|---|---|
| UTF-8 바이트 | 25 | DB 저장, 네트워크, Go·Rust의 len |
| UTF-16 코드유닛 | 11 | JavaScript `.length`, Java, C#, SMS UCS-2 |
| 코드포인트 | 7 | Python `len()`, Swift `unicodeScalars` |
| 그래핌 클러스터 | 1 | 사람이 세는 「글자」, 커서 이동, 백스페이스 |
| 터미널 표시 폭 | 2 (렌더러가 지원할 때) | 고정폭 정렬, 표 레이아웃 |

대부분의 입력에서는 이 다섯 숫자가 같다. **이모지가 들어오는 순간에만 갈린다.** 그래서 조용히 지나가다가 어느 날 터진다.

## 1. 측정값 (직접 실행)

| 문자열 | 바이트 | UTF-16 | 코드포인트 | 그래핌 |
|---|---|---|---|---|
| `hello world` | 11 | 11 | 11 | 11 |
| 漢字 (U+6F22 U+5B57) | 6 | 2 | 2 | 2 |
| é NFC (U+00E9) | 2 | 1 | 1 | 1 |
| é NFD (U+0065 U+0301) | 3 | 2 | 2 | 1 |
| 😀 (U+1F600) | 4 | 2 | 1 | 1 |
| 🇰🇷 (U+1F1F0 U+1F1F7) | 8 | 4 | 2 | 1 |
| 👍🏽 (U+1F44D U+1F3FD) | 8 | 4 | 2 | 1 |
| 👨‍👩‍👧‍👦 (ZWJ 4인) | 25 | 11 | 7 | 1 |
| `DevTeam01 👨‍👩‍👧‍👦2026` | 39 | 25 | 21 | 15 |

마지막 줄이 핵심이다. **「20자 이하」 규칙에 이 닉네임을 넣으면 어느 단위로 세는지에 따라 결과가 갈린다.**

- 바이트로 세면 39 → 거부
- UTF-16으로 세면 25 → 거부
- 코드포인트로 세면 21 → 거부
- 그래핌으로 세면 15 → 통과

## 2. 이모지가 길어지는 네 가지 방식

| 방식 | 구조 | 예 | 코드포인트 |
|---|---|---|---|
| ZWJ 시퀀스 | 그림문자 사이에 U+200D | 👨‍👩‍👧‍👦 | 7 |
| 변경자 시퀀스 | 기반 + 피부색 변경자 | 👍🏽 | 2 |
| 국기 시퀀스 | 지역 표시 문자 2개 | 🇰🇷 | 2 |
| 태그 시퀀스 | 검은 깃발 + 태그 문자 + 종료자 | 스코틀랜드 깃발 | 7 |

- **U+200D(ZWJ)가 접착제다.** 4인 가족에서 U+200D 세 개를 빼면 그래핌이 1에서 **4로** 늘어난다. 바이트는 25에서 16으로 조금만 줄어든다
- **U+FE0F(VS16)는 폭 0의 3바이트**다. 아무것도 그리지 않으면서 길이를 늘린다
- **국기 짝짓기는 왼쪽부터 탐욕적**이다. 지역 표시 문자를 하나 지우면 그 뒤가 전부 다시 짝지어진다
- 피부색·국기·태그도 전부 그래핌 1개다

## 3. 목적별로 세야 할 단위

**이 표가 이 문서의 핵심이다.** 「무엇을 세는가」는 요구사항이 정한다.

| 목적 | 세야 할 단위 | 이유 | 검증 방법 |
|---|---|---|---|
| 사용자에게 보여줄 「n자 남음」 | **그래핌** | 사람이 세는 수와 일치 | 이모지 1개를 1로 세는지 확인 |
| DB 컬럼 크기 결정 | **바이트** | 저장 한도는 바이트다 | 최악 케이스 바이트로 계산 |
| 입력 폼 하드 리밋 | **바이트 + 그래핌 둘 다** | 표시용과 저장용이 다르다 | 두 조건을 모두 걸어라 |
| SMS 과금 | **UTF-16 코드유닛** | UCS-2 세그먼트는 유닛 단위 | 70유닛(연결 시 67) 경계 |
| 고정폭 화면 배치 | **표시 폭** | 셀 개수가 레이아웃을 정한다 | 실제 폰트로 눈으로 확인 |
| 언어 간 API 계약 | **바이트** | 유일하게 모든 언어에서 같다 | 양쪽에서 같은 수가 나오는지 |
| 로그·해시·중복 검사 | **정규화 후 바이트** | NFC/NFD가 다른 바이트다 | 정규화를 먼저 |

## 4. 바로 쓰는 코드 (JavaScript)

`Intl.Segmenter`는 Node 16 이상과 최신 브라우저에서 쓸 수 있다. 검증 환경(Node v22.16.0, ICU 77.1)에서 정상 동작을 확인했다.

```js
const seg = new Intl.Segmenter('ko', { granularity: 'grapheme' });

// 세기 — 이모지 하나를 1로 센다
function countGraphemes(s) {
  return [...seg.segment(s)].length;
}

// 자르기 — 이모지를 절대 반으로 가르지 않는다
function sliceGraphemes(s, n) {
  return [...seg.segment(s)].slice(0, n).map(function (x) { return x.segment; }).join('');
}

// 뒤집기 — 국기가 다른 나라가 되지 않는다
function reverseGraphemes(s) {
  return [...seg.segment(s)].map(function (x) { return x.segment; }).reverse().join('');
}

// 바이트 기준 자르기 — 컬럼 한도를 지키면서 이모지를 보존한다
function sliceByBytes(s, maxBytes) {
  const enc = new TextEncoder();
  let outStr = '';
  let used = 0;
  for (const part of seg.segment(s)) {
    const n = enc.encode(part.segment).length;
    if (used + n > maxBytes) break;
    outStr += part.segment;
    used += n;
  }
  return outStr;
}

// 검증 — 반쪽 서로게이트가 섞였는지
function isIntact(s) {
  if (typeof s.isWellFormed === 'function') return s.isWellFormed();
  const paired = s.replace(/[\uD800-\uDBFF][\uDC00-\uDFFF]/g, '');
  return !/[\uD800-\uDFFF]/.test(paired);
}
```

**확인된 동작**

- `countGraphemes` 로 👨‍👩‍👧‍👦 를 세면 **1**
- `DevTeam01 👨‍👩‍👧‍👦2026` 을 12그래핌으로 자르면 이모지가 온전하고 `isWellFormed()` 가 true
- 같은 문자열을 `.slice(0, 20)` 으로 자르면 `isWellFormed()` 가 **false**, UTF-8 인코딩 시 마지막이 `EF BF BD`(U+FFFD)가 된다

## 5. Intl.Segmenter 가 없는 환경

정규식 근사치를 쓸 수 있다. **완전하지 않다는 것을 알고 써라.**

```js
const RX = new RegExp(
  '(?:\\p{RI}\\p{RI})' +
  '|(?:\\p{Extended_Pictographic}(?:\\p{Emoji_Modifier}|\\uFE0F)?' +
  '(?:\\u200D\\p{Extended_Pictographic}(?:\\p{Emoji_Modifier}|\\uFE0F)?)*)' +
  '|(?:\\P{M}\\p{M}*)|.', 'gu');

function approxCount(s) { return (s.match(RX) || []).length; }
```

실측 정확도

| 대상 | 근사치 | 정답 |
|---|---|---|
| 👨‍👩‍👧‍👦 | 1 | 1 |
| 🇰🇷 | 1 | 1 |
| 👍🏽 | 1 | 1 |
| `DevTeam01 👨‍👩‍👧‍👦2026` | 15 | 15 |
| 한글 NFD (U+1112 U+1161 U+11AB) | 3 | 1 |
| 태그 시퀀스 깃발 | 7 | 1 |

이모지는 맞히고 **한글 NFD와 태그 시퀀스에서 틀린다.** UAX #29 는 규칙이 16개인데 이 정규식은 4개다. 근사치는 대체품이 아니다.

## 6. Python 쪽

- `len()` 은 **코드포인트**를 센다. 👨‍👩‍👧‍👦 는 **7**이다. JavaScript 의 11 과 다르다
- 표준 라이브러리에 **그래핌 API가 없다.** 검증 환경에서 확인: `hasattr(str, 'graphemes')` 는 False, 표준 `re` 는 `\X` 를 거부(`PatternError: bad escape \X`)
- 서드파티 `regex` 모듈의 `\X` 가 필요하다. 검증 환경에는 **설치되어 있지 않았다**
- 슬라이싱은 반쪽 서로게이트를 만들지 않지만 **ZWJ 사슬은 그대로 끊는다.** `NICK[:16]` 은 마지막이 U+200D인 「아무것도 잇지 않는 접착제」가 된다

```python
# 그래핌이 필요하면 서드파티 모듈이 필요하다
import regex
def count_graphemes(s):
    return len(regex.findall(r'\X', s))

# 바이트 한도를 지키며 자르기 (표준 라이브러리만)
def slice_by_bytes(s, max_bytes):
    b = s.encode('utf-8')[:max_bytes]
    return b.decode('utf-8', 'ignore')   # 경계에서 잘린 조각은 버린다
```

`decode(..., 'ignore')` 는 잘린 조각을 조용히 버린다. 로그가 필요하면 `strict` 로 잡아서 직접 처리하라.

## 7. 저장·전송 계층 계산

- 이모지는 전부 **U+FFFF 위**에 있다. U+FFFF 는 UTF-8 3바이트, U+10000 은 **4바이트**다
- 문자당 최대 3바이트까지만 받는 문자셋은 **이모지를 하나도 담지 못한다.** 검증에서 cp949 와 shift_jis 모두 😀 를 거부했다(`UnicodeEncodeError`)
- 「20자」를 바이트로 환산할 때 **반드시 최악 케이스로** 잡아라

| 「20자」의 뜻 | 필요한 UTF-8 바이트 |
|---|---|
| 20 코드포인트 | 최대 80 |
| 20 그래핌 (가족 이모지) | 500 |
| 20 그래핌 (결합 문자 200개짜리) | 8,020 |
| 20 그래핌 (일반) | **상한 없음** |

**그래핌으로 컬럼 크기를 잡지 마라.** 그래핌 하나에 들어갈 코드포인트 개수에는 상한이 없다.

## 8. JSON·URL 팽창률

| 변환 | 결과 | 배율 |
|---|---|---|
| 👨‍👩‍👧‍👦 UTF-8 | 25 바이트 | 1.0x |
| JSON `{"nick":"..."}` UTF-8 | 36 바이트 | — |
| JSON ASCII 이스케이프 | 77 바이트 | 2.14x |
| `encodeURIComponent` | 75 ASCII 문자 | 3.0x (바이트당 3) |
| Base64 | 36 문자 | 1.44x |

- JSON 의 `\u` 이스케이프는 UTF-16 기반이라 **U+1F468 하나가 이스케이프 두 개**(`\uD83D` 와 `\uDC68`)가 된다
- URL 쿼리 길이 2048 예산이면 20그래핌 가족 문자열은 **하나**밖에 못 넣는다
- 반쪽 서로게이트는 계층마다 다르게 반응한다: JSON 은 **통과**시키고, `encodeURIComponent` 는 **URIError 를 던지고**, UTF-8 인코딩은 **조용히 U+FFFD 로 바꾼다**. 발생 지점에서는 아무 오류도 안 난다

## 9. SMS 과금 (별도 규칙)

- ASCII 만 있으면 GSM-7, 한 세그먼트 **160자**
- 비-GSM 문자가 **하나라도** 들어가면 전체가 UCS-2 로 바뀌고 한 세그먼트 **70유닛**(연결 시 67)
- 실측: 93자 ASCII 메시지는 GSM-7 1세그먼트. **이모지 하나를 붙이면 UCS-2 로 전환되어 2세그먼트**가 된다
- 한 세그먼트(70유닛)에 들어가는 개수: 일반 문자 70개 / 😀 35개 / 🇰🇷 17개 / 👨‍👩‍👧‍👦 **6개**

사용자는 「한 글자」를 더했다고 생각하는데 요금은 두 배가 된다.

## 10. 정규식으로 이모지를 막으려 할 때

| 패턴 | 👨‍👩‍👧‍👦 매치 횟수 |
|---|---|
| `/./g` | 11 |
| `/./gu` | 7 |
| `/./gv` | 7 |
| `\p{Emoji}` | 4 |
| `\p{Emoji_Presentation}` | 4 |
| `\p{Extended_Pictographic}` | 4 |
| `\p{RGI_Emoji}` (v 플래그) | **1** |

- `u` 플래그가 없으면 `.` 이 **코드유닛**을 센다. 11번 매치한다
- `u` 플래그를 붙이면 코드포인트 단위가 되어 7번이다. **여전히 1이 아니다**
- 하나로 세려면 **`v` 플래그와 `\p{RGI_Emoji}`** 가 필요하다. 검증 환경에서 둘 다 지원됐다
- `\p{Extended_Pictographic}` 로 지우면 **U+200D 세 개가 남는다.** 눈에 안 보이는 잔해다
- `\p{Emoji}` 는 **숫자와 `#`, `*` 도 매치한다.** 이걸로 이모지를 막으면 주문번호가 거부된다

- [ ] 화면 카운터와 서버 검증이 **같은 단위**를 쓴다
- [ ] 프런트(JavaScript)와 백엔드(Python·Java·Go)의 길이 계산이 **일치하는지 같은 문자열로 확인**했다
- [ ] DB 컬럼을 **바이트 최악 케이스**로 계산했다 (그래핌 기준으로 잡지 않았다)
- [ ] 저장 계층이 **4바이트 문자를 받는 문자셋**이다
- [ ] 자르기에 `slice`·`substring`·바이트 슬라이싱을 **직접 쓰지 않는다**
- [ ] 자른 결과를 `isWellFormed()` 로 **검증**한다
- [ ] 뒤집기·자르기 테스트에 **ZWJ 시퀀스·국기·피부색·한글 NFD 표본**이 들어 있다
- [ ] 이모지 필터가 **U+200D 잔해를 남기지 않는다**
- [ ] 이모지 차단 정규식이 **숫자와 `#`, `*` 를 오검출하지 않는다**
- [ ] SMS 발송 경로에서 **UCS-2 전환과 세그먼트 수를 계산**한다
- [ ] 중복 검사·해시 전에 **정규화를 먼저** 한다
- [ ] 검증 실패 메시지가 사용자에게 **어느 단위로 몇 자 초과인지** 알려준다

## 12. 하지 말 것

- ❌ **「이모지를 막으세요」로 끝내는 것** — 세려는 단위를 정하지 않으면 규칙은 계속 깨진다
- ❌ `.length` 를 「글자 수」라고 부르는 것 — UTF-16 코드유닛이다
- ❌ 그래핌으로 **DB 컬럼 크기를 잡는 것** — 상한이 없다
- ❌ 프런트는 그래핌, 서버는 바이트로 세면서 **같은 숫자를 기대하는 것**
- ❌ `.slice()` 로 자른 뒤 **검증 없이 저장하는 것** — 반쪽 서로게이트가 흘러간다
- ❌ 배열 뒤집기로 문자열 역순 만드는 것 — 국기가 **다른 나라**가 된다
- ❌ `\p{Emoji}` 로 이모지를 차단하는 것 — 숫자를 막는다
- ❌ 정규식 근사치를 **완전한 그래핌 분할이라고 믿는 것** — 한글 NFD 와 태그 시퀀스에서 틀린다
- ❌ 테스트 표본에 **ASCII 만 넣는 것** — 다섯 숫자가 전부 같아서 아무것도 못 잡는다
