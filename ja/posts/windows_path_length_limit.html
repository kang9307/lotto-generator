Windows MAX_PATH 260文字制限とツール別失敗パターン

パスが長いとツールごとに異なる形で失敗する — エラーなく静かに除外される挙動をまず疑え

2026-09-29 開発・インフラ

序論：ファイルはそこに存在するのにツールは「ない」と答える

Windows環境においてファイル操作を伴う自動化処理を運用していると、直感に反する不可解な現象に遭遇することがある。ストレージ上に確実に保存されており、特定のツールからは何の問題もなく閲覧できるファイルであるにもかかわらず、一部のスクリプトやコマンドラインツールは「ファイルが見つからない」と通知するか、エラーを出すことすらなく静かに偽（False）を返す。多くのエンジニアはこの瞬間、アクセス権限や同期の遅延、文字コードの破損を疑いがちである。しかし、その背景にはWindowsオペレーティングシステムの歴史的遺産であるMAX_PATH（260文字）パス長制限が、ツールごとに全く異なる挙動として表面化しているという実態がある。

本記事は、一般的なレジストリ変更の解説集ではない。パスが260文字を超過した際、各ツールが全く異なる形で失敗し、とりわけエラーメッセージを出さずに静かに一覧からファイルを除外する挙動が最も危険な死角であることを、実測データによって明らかにするものである。実際にWindows 10環境において全長322文字の深層ファイルパスを作成し、PowerShell 5.1、cmd.exe、Python 3.13、Git Bash、Node.js 22、Git 2.48を交差実行して確認した実録である。

先行する関連テーマとの境界を整理しておく。バッチファイルやPowerShellによるWindows自動化の基礎はWindows自動化入門ガイドで解説している。シェルごとの文字エスケープや文字化けの境界はシェルごとにファイル名が異なる理由に、アーカイブ内部のエンコーディングフラグ解析はzip内ファイル名が壊れる分岐点にまとめている。本稿では一貫してパス文字列の物理的な長さに焦点を絞る。

1. 実行環境とMAX_PATH(260文字)の実際の境界線

1.1 260文字の内訳と248文字のディレクトリ上限

マイクロソフトの公式技術文書（Naming Files, Paths, and Namespaces）によると、Windows APIにおける従来の最大パス長はMAX_PATH定数で定義され、その長さは正確に260文字である。この構成には、ドライブ文字（例: C: の2文字）、区切り文字のバックスラッシュ（\ の1文字）、ファイルやフォルダの各階層名、そして終端文字であるヌル文字（\0 の1文字）が含まれる。したがって、実質的に指定可能なパス文字列は259文字までとなる。

しかし見落とされがちな重要な仕様がある。それはディレクトリ自体の作成上限は260文字ではなく248文字（MAX_PATH - 12）であるという点である。公式文書にはディレクトリパス長がMAX_PATH minus 12を超えてはならないと明記されている。これは、そのディレクトリの直下に従来の8.3形式のファイル名（8文字＋ドット1文字＋拡張子3文字＝12文字）を最低1つ作成できる名前空間の余白を予約しなければならないためである。後述の実験において、231文字のディレクトリ作成は成功したが、252文字のディレクトリ作成では直ちにWinError 206が発生して失敗したのは、まさにこの規定に合致している。

1.2 レジストリ LongPathsEnabled の現在値確認

近年のWindows 10やWindows Serverには、システム全体で長いパス制限を解除するレジストリ設定（LongPathsEnabled）が用意されている。実測を開始するにあたり、対象PCの初期状態を確認した。

reg query "HKLM\SYSTEM\CurrentControlSet\Control\FileSystem" /v LongPathsEnabled
Get-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem' -Name LongPathsEnabled | Select-Object LongPathsEnabled

実際のコマンド出力結果は以下の通りである。

HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\FileSystem
    LongPathsEnabled    REG_DWORD    0x0

LongPathsEnabled
----------------
               0

確認の結果、この環境におけるLongPathsEnabledの値は0であった。すなわち、従来の260文字パス制限が緩和されることなく完全に適用されている標準状態である。以下のすべての実験結果はこの条件下で取得された。

2.3 Git Bash と Node が322文字を処理できた理由

注目すべきは、すべてのツールが失敗したわけではないという事実である。Git Bash(MSYS2ランタイム)とNode.js 22は、レジストリのLongPathsEnabledが0のままであっても、322文字のパスを何ら支障なく処理した。

cat lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/long_file_name_for_test.txt
find lp -type f
cat "$PWD/lp/…/long_file_name_for_test.txt"
echo bash-made > lp/…/cccccccccccccccccccc/bash_made_file.txt

exit=0

Git Bashは相対パスおよびPOSIX絶対パスの双方で322文字のファイルを読み取ることができ、echo bash-made > ... コマンドによってその配下に新規ファイル（bash_made_file.txt）を作成することにも成功した。Node.js 22も通常パスで読み取りと一覧取得に成功した（書き込みは試していない）。

3. cmd dir /s の暗黙の欠落 — 終了コード0が隠蔽する死角

今回の実測実験において最も致命的な落とし穴となったのは、コマンドプロンプト（cmd.exe）における再帰検索コマンドdir /sの挙動であった。

cmd /c "dir `"$d`""            # 単一フォルダの通常パス指定
cmd /c "dir `"\\?\$d`""        # プレフィックス指定
cmd /c "type `"$f`""
cmd /c "type `"\\?\$f`""
cmd /c "dir /s /b `"$b\lp`""   # 再帰探索
# 終了コードを $LASTEXITCODE で確認

コンソールに出力された内容と終了コードは以下の通りである。

=== cmd dir plain dir
The system cannot find the path specified.
=== cmd dir prefixed dir
 Volume in drive \\?\C: has no label.
 Directory of \\?\C:\…\tech_lab\lp\aaaaaaaaaaaaaaaaaaaa\bbbbbbbbbbbbbbbbbbbb\cccccccccccccccccccc
2026-09-29  ?? 07:38                16 long_file_name_for_test.txt
               1 File(s)             16 bytes
=== cmd dir /s lp
…\tech_lab\lp\aaaaaaaaaaaaaaaaaaaa
…\tech_lab\lp\aaaaaaaaaaaaaaaaaaaa\bbbbbbbbbbbbbbbbbbbb

dir plain exit=1
dir prefixed exit=0
type plain exit=1
hello long path
type prefixed exit=0
dir /s lp exit=0

3.1 単一フォルダ dir と再帰探索 dir /s /b の決定的な違い

単一の長いパスを対象としてdirやtypeを実行した場合、システムはexit=1とともにThe system cannot find the path specified.という明白なエラーを返す。失敗が直ちに判明するため、後続のリカバリ処理が可能である。

しかし、上位フォルダから配下を走査するdir /s /bを実行した際には、全く異なる事態が発生した。252文字のフォルダ（aaaaaaaa...）と273文字のフォルダ（bbbbbbbb...）までは出力されたが、その奥に確実に存在する294文字のフォルダ（cccccccc...）と322文字の検証ファイル（long_file_name_for_test.txt）は、一覧から完全に消失していた。そしてコマンドの終了コードは0であった。

3.2 探索スクリプトやバッチ処理における運用リスク

これが深刻な問題である理由は、たとえば以下のようなループ（本稿では実行していない例示パターン）がdir /s /bの出力をそのまま処理対象の一覧として扱うためである。

FOR /F "delims=" %%F IN ('dir /s /b "C:\Backup\*"') DO (
    call :ProcessFile "%%F"
)

dir /sは一切のエラーメッセージを出力せず、終了コードも0を返すため、スクリプトは一覧が完全だと判断する。今回のcccc…フォルダのように一覧から抜けたパス配下のファイルは処理対象に載らないまま静かに飛ばされる。出力と終了コードだけでは、ファイルが欠落していることに気付けない。

4. PythonとPowerShellにおける \\?\ 拡張パスの扱い方

深い階層のパスを確実に操作しなければならない場合、Windows APIのUnicode関数が受け付ける拡張長パスプレフィックス \\?\の適用が不可欠となる。

4.1 \\?\ プレフィックスの意義と絶対パスの制約

マイクロソフトの公式ドキュメントによれば、Windows APIのUnicode関数は\\?\プレフィックスを付けた拡張長パスを受け付け、パス全体の長さは最大32,767文字まで許される。文書は、このプレフィックス付きパスが最小限の変更だけでシステムに渡されると説明しており、そのためスラッシュ（/）を区切りに使ったり、.・..で現在・親フォルダを表したりはできない。

ただし、ここには厳格な制約が存在する。相対パスには \\?\ プレフィックスを一切付与できない。文書には「相対パスには\\?\プレフィックスを使えないため、相対パスは常にMAX_PATHに制限される」とある。したがって、プレフィックスを用いる際は、必ずC:\...のような完全修飾絶対パスと組み合わせなければならない。

4.2 shutil.rmtree の失敗とボトムアップ削除の実装

検証用ディレクトリツリーを消去するプロセスにおいても、典型的な二次障害が確認された。Pythonの標準削除関数であるshutil.rmtree()を通常のパスで実行した結果である。

# t1_clean.py 抜粋
shutil.rmtree(targets[0])                 # 通常パスでの削除試行
os.path.exists(P + targets[0])
for root, dirs, files in os.walk(P + t, topdown=False):
    os.remove(...)
    os.rmdir(...)
os.rmdir(P + t)

実際の出力結果は以下の通りである。

plain rmtree lp: OSError winerror= 145 filename_len= 252
still exists (prefixed check): True
prefixed delete lp files= 2 dirs= 4 exists after= False
prefixed delete g\lp files= 1 dirs= 4 exists after= False
prefixed delete gr1\lp files= 1 dirs= 4 exists after= False

通常のパスで呼び出されたshutil.rmtreeは、WinError 145 (ディレクトリが空ではありません)を出して停止した。内部的に322文字の末端ファイルを列挙・削除できず、中身が残ったフォルダを削除しようとして失敗したためである。今回は、プレフィックスを付加した\\?\C:\...パスでos.walk(topdown=False)を実行し、最も深い末端のファイルから順次削除して親ディレクトリへと遡るボトムアップ削除を行ったところ、3つのツリーとも何も残らず削除された（exists after= False）。

5. Gitとcore.longpaths — 作業ツリー救済と深いリポジトリの限界

バージョン管理ツールであるGitにおいても、Windows上でのパス長問題は日常的に発生する。Git for Windowsにはcore.longpathsオプションが存在するが、その適用範囲を正確に把握しておく必要がある。

5.1 core.longpaths の初期値とスコープ

まずGitのcore.longpathsのデフォルト設定状況を確認した。

git init -q .
git config --show-origin --show-scope --get-all core.longpaths
git config --system --show-origin --get core.longpaths
GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1 git config --get core.longpaths

このPCではユーザーがグローバル設定にcore.longpaths=trueを入れていたが、システム設定の照会は終了コード1で、グローバル・システム設定を両方除外した照会も終了コード1だった。すなわち、設定しなければ長いパスのサポートは無効(既定値false)である。Git for Windows同梱の文書は、Windows Explorer、cmd.exe、Git for Windowsのツール群（msys、bash、tcl、perl…）が長いパスをサポートしないため既定で無効にしていると説明している。

5.2 作業ツリーにおける長いファイルのステージングと復元

作業ツリー内に330文字のファイルが存在する場合、core.longpathsの有無は成否を直接分ける。この実験ではグローバル設定を外し（GIT_CONFIG_GLOBAL=/dev/null）、オブジェクトフォルダだけをGIT_OBJECT_DIRECTORYで短いパスに回して、作業ツリー側の長いファイルだけを切り分けた。

--- longpaths unset: add long file
warning: could not open directory 'lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/': Filename too long
fatal: pathspec 'lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/long_file_name_for_test.txt' did not match any files
exit=128
--- longpaths=true: add long file
exit=0
lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/long_file_name_for_test.txt
s.txt
--- restore (checkout) longpaths unset
fatal: cannot create directory at 'lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb': Filename too long
exit=128
--- restore longpaths=true
exit=0
hi

設定がない場合、Gitはフォルダを開けずにFilename too longの警告を出し、fatal: pathspec did not matchで終了する。一方、-c core.longpaths=trueを付与すると、正常にステージングされ、チェックアウトによる復元も問題なく成功する。

5.3 リポジトリ配置が深い場合の .git/objects 書き込み失敗

しかし、core.longpaths=trueにも限界がある。Gitリポジトリのルートフォルダ自体が232文字という深い位置にある状態でgit addを試行した結果である。このPCのグローバル設定core.longpaths=trueが有効なまま実行した。

--- git add (no longpaths)
error: unable to write file .git/objects/45/b983be36b73c0788dc9cbcb76cbb80fc7bb057: No such file or directory
error: lp/…/long_file_name_for_test.txt: failed to insert into database
error: unable to index file 'lp/…/long_file_name_for_test.txt'
fatal: adding files failed
exit=128
--- -c core.longpaths=true add short.txt
error: unable to write file .git/objects/1d/3aaf18909062b31aeeeb3b683f1c2fad3e304e: No such file or directory
error: short.txt: failed to insert into database
error: unable to index file 'short.txt'
fatal: adding files failed
exit=128

短い名前のファイル（short.txt）を追加しようとした場合でも、core.longpaths=trueを指定しているにもかかわらずunable to write file .git/objects/...: No such file or directoryとして失敗した。Gitはステージングの際に.git/objects/xx/38文字ハッシュという内部ファイルを書き出す。リポジトリのルートが232文字のこの実験では、オブジェクトフォルダ.git/objects/45が248文字、オブジェクトファイルのパスが291文字となり260文字を超えた。この環境（Git 2.48.1.windows.1）ではcore.longpaths=trueを付けても、エラー文言が「Filename too long」から「unable to write file … No such file or directory」に変わっただけで失敗は変わらなかった。すなわち、core.longpathsは作業ツリーのファイルを救済するが、リポジトリ自体のメタデータ書き込みを無制限に保護するわけではない。

6. 8.3形式の短縮パス(ShortPath)を用いた回避と対照実験

失敗の原因が純粋にパス長にあることを検証するため、同一のフォルダを指しながらパス文字列の長さを劇的に短縮するWindows 8.3短縮パス（ShortPath）を用いた対照実験を行った。

6.1 8.3短縮パスの基本原理

この環境のフォルダにはPROGRA~1形式の8.3短縮名があった。PowerShellからScripting.FileSystemObjectのShortPathプロパティを取得すると、232文字におよぶ深いパスがC:\Users\<ユーザー>\…\tech_lab\ctlのように約87文字へと大幅に圧縮される。

6.2 GIT_DIR 環境変数の直接注入による対照実験

単に短縮パスへcd移動するだけでは解決しなかった。git rev-parse --show-toplevelは長い名前に戻して出力し、git addも同じエラーで失敗した。GIT_DIRに短縮名を直接渡した場合のみ成功した。

# (Scripting.FileSystemObject).GetFolder(...).ShortPath → C:\Users\<ユーザー>\…\tech_lab\ctl  (約87文字)
$env:GIT_DIR = "$s\.git"; $env:GIT_WORK_TREE = $s
git add a.txt; "exit=$LASTEXITCODE"
git ls-files -s

実行結果は以下の通りである。

exit=0
100644 b88e8890e5b4d028a6d3849b4f4979cad8b07d3c 0	a.txt

バイナリもリポジトリ内容も変更せず、パス長を圧縮しただけで即座に完全な成功（exit 0）へと反転した。これにより、先ほどの障害原因が権限やロックではなく、純粋なパス長超過であったことが立証された。

7. 「ファイルが存在しない」と断定する前の5段階判断手順

Windows環境において自動化処理がファイル不存在を報告してきた場合、現場で実践すべき体系的なトラブルシューティング手順を整理する。

  • ステップ1: パス文字列全体の長さを計測する — 不在や権限を疑う前に、PowerShellの$path.LengthやPythonのlen(path)を用いて、フル絶対パス長が248文字または260文字に近接していないか確認する。
  • ステップ2: 表面的なエラーメッセージの文面を疑う — does not exist、No such file or directory、The system cannot find the path specified、そしてWinError 145（空ではない）は、すべてパス長超過に起因する見かけ上のエラーである可能性がある。
  • ステップ3: 再帰探索ツールの終了コードと出力をクロスチェックする — cmdのdir /s /bは長いパスの項目を暗黙に除外しながら終了コード0を返すため、Git BashのfindやNode.jsスクリプトを用いて実際のディスク内容と比較する。
  • ステップ4: ファイル操作に \\?\ プレフィックスを組み合わせる — スクリプトによる保守やディレクトリ削除処理では相対パスを避け、\\?\C:\...形式の完全絶対パスを用いてOS APIを直接呼び出す。
  • ステップ5: Gitリポジトリ自体の配置階層を点検する — core.longpaths=trueを有効にしてもオブジェクトの書き込みに失敗する場合、リポジトリのルート階層が深すぎないか確認し、浅い階層へ配置換するか8.3短縮パスをGIT_DIRへ注入する。

7.1 パス長測定と検証の優先順位

パス長を評価する際は、相対パスではなく現在の作業ディレクトリを含む完全な正規パスを基準にしなければならない。今回の実験でも基準フォルダ自体が228文字で、その長さが結果（gitリポジトリの失敗）に直接影響した。作業フォルダが深い場所に置かれる環境なら、ジョブの開始時にパス長をログへ出力しておくと安全である。

7.2 安全な自動化スクリプト作成の指針

Windowsバッチスクリプト（.bat）において、dir /sによるファイル列挙に頼ることは極めて危険である。重要な業務処理では、今回長いパスを正しく一覧できた方法 — \\?\プレフィックス付きのGet-ChildItem -LiteralPath（単一フォルダ）、プレフィックス付きのPython os.listdir、Git Bashのfind、Node.jsのfs.readdirSync — で一覧を照合してから渡すことを勧める。

8. よくある質問 (FAQ)

実務で長いパス制限に直面した際によく寄せられる疑問点をまとめた。

  • Q1. Windowsでパスが260文字を超えるとすべてのプログラムが失敗するのか？
    A. そうではない。この環境での実測では、322文字のパスに対してcmd、PowerShell、Pythonは失敗したが、Git Bash(MSYS2)はエラーなく読み取りと新規ファイルの書き込みができ、Node.js 22はエラーなく読み取りと一覧取得ができた。結果はツールごとに異なる。
  • Q2. cmdのdir /sコマンドが長いパスの探索において特に危険な理由は何か？
    A. 今回の実験でdir /s /bコマンドは、294文字のフォルダと322文字のファイルをエラーなしで一覧から除外しながら（273文字のフォルダまでは表示）、終了コード0を返した。自動化スクリプトがこれを信じると、ファイルが存在しないと誤認することになる。
  • Q3. gitでcore.longpaths=trueを設定してもaddが失敗するのはなぜか？
    A. この設定は作業ツリーのファイルのみを保護する。リポジトリ自体の配置が深い場合、内部オブジェクトパス（.git/objects/xx/...）が260文字を超過して書き込みに失敗する。リポジトリ自体を浅い階層に置くか、8.3短縮パスを使用する必要がある。
  • Q4. \\?\拡張パスプレフィックスは相対パスにも適用できるか？
    A. 適用できない。公式文書によれば、\\?\プレフィックスは相対パスには使えず、そのため相対パスは常にMAX_PATH（260文字）に制限される。
  • Q5. WindowsレジストリのLongPathsEnabledを1に設定すればすべての問題は解決するか？
    A. 解決しない。レジストリの設定に加え、アプリケーションのマニフェストにlongPathAwareが宣言されている必要があり、値はプロセスの存続中は再読み込みされないため、再起動が必要になる場合がある。文書は、この設定が新機能を利用するよう修正されたアプリケーションにのみ影響すると述べている（この環境では有効化していない）。

9. 確認できなかった事項

今回の検証において、環境上の制約により直接確認できなかった項目を記録する。

  • LongPathsEnabled=1 変更後の実測検証: 本稿ではこの値を変更していないため、レジストリ値を1に変更して再起動した後の各ツールの詳細な挙動変化は直接確認できなかった。これらはマイクロソフト公式技術文書の仕様に基づき記述している。
  • Git Bash 内部変換処理のバイナリ解析: Git for Windowsの公式文書にはmsysおよびbashツールチェーンが長いパスをサポートしないと記載されているが、実測では322文字のパスを正常に処理した。MSYS2ランタイム層が内部でどのようにパスを変換しているかについて、バイナリレベルの詳細な解析までは至っていない。
  • 異種オペレーティングシステムとの対照実験: 同一の322文字パスに対するLinuxやmacOS環境との実機比較は、検証端末がWindows 10単一環境であったため直接の対照実行は実施していない。

| 画面に表示された症状 | ツールが下した表面的な結論 | 内部の真の原因 | 点検と対処法 |
|---|---|---|---|
| `False` 返却 (エラーなし) | ファイルが存在しない | PowerShell や Python が260文字超のパスを不在と判定 | `$f.Length` や `len(f)` でパス文字列の長さを測定 |

## 3. 長いパスのトラブルシューティング 5段階点検表

- [ ] **1. パス長を測定する**: 「ファイルがない」という通知や `False` が返された場合、不在を疑う前にまず絶対パスの全長を計測する (`len(path)` または `$path.Length`)。
- [ ] **2. 248文字のディレクトリエラー境界を確認する**: Windows API の仕様通り、ディレクトリパスは 260文字ではなく `MAX_PATH - 12` (248文字) で制限される (実測 252文字で失敗)。
- [ ] **3. `dir /s` の結果を過信しない**: cmd の `dir /s /b` は終了コード 0 を返しながら、294文字のフォルダと322文字のファイルを一覧から暗黙のうちに除外した (273文字のフォルダまでは表示)。
- [ ] **4. ファイル操作には `\\?\` ＋ 絶対パスを使用する**: Windows 拡張プレフィックス `\\?\` は最大 32,767文字まで許容するが、相対パスには使用できない。
- [ ] **5. 深い Git リポジトリは 8.3 短縮パスで回避する**: `core.longpaths=true` が救済したのは作業ツリーのファイルのみだった。リポジトリ自体の配置が深い場合は短いパスに置くか、この実験のように `GIT_DIR` と `GIT_WORK_TREE` に 8.3 短縮パスを直接渡す (`cd` だけでは失敗した)。
