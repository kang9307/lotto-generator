1. Firefox的AI集成与走向“彻底移除”的问题意识

现代网络浏览器引擎构建在包含数千万行源代码的庞大代码库之上。通常情况下，随着软件生态走向成熟，上游厂商倾向于吸纳商业变现模型与技术热点，在浏览器内部层层堆叠附加功能。长期被开源社区视作重要阵地的Firefox亦未能例外，近年来持续将包括本地模型调用及远程协同在内的人工智能辅助组件深深织入渲染与操作系统的核心架构之中。

针对这一趋势，安全研究员兼独立开发者Sarah Jamie Lewis于2026年9月19日发表了题为《Thoughts on the Future of Web Browsers》的深度随笔。原文援引其7月在Mastodon发表的帖子指出，如果独立、纯净的网络环境尚存未来，那么当下正是所有Firefox分支项目必须联合起来、共同维护一个与Mozilla物理隔离的硬分叉的时刻。原文强调，这项工程规模过于宏大，任何单一小型项目都无法独自承担，但其重要性又绝不容许继续交由Mozilla这样的机构来主导。

原文指出，Mozilla以及Firefox在过去十年中明确设定了自身期望前行的方向，并坚定不移地朝着该方向推进。原文写道：“Mozilla and, by extension, Firefox have laid out the direction they want to go - and have consistently moved in that direction over the last decade. There is no redemption arc there, they are not going to turn the ship around - and every week and month that goes by, Firefox gains more slop and drifts further from the visions that founded it.”这意味着期待上游项目主动回头的想法是不切实际的，代码库的分离已成为必然选择。

在本文的分析看来，仅凭在高级偏好设置中取消勾选某些开关的消极防守，已经完全无法跟上浏览器核心重构的演进节奏。当上游厂商逐步将整个浏览器窗口定位为第三方智能代理的调度沙盒时，参数微调只是一种临时抱佛脚的做法。在本文的推测看来，作者提出“物理隔离硬分叉”的设想，源自对深度功能集成已在实质上动摇渲染引擎底层安全与纯粹性的技术研判。

2. Base Browser的定位 — 剥离代码而非禁用配置

源自Mastodon的探讨随后落实在Codeberg平台上成立的Base Browser项目之中。原文解释称，该项目旨在为社区提供一个可以汇聚创意与探讨技术方向的阵地。原文给出了目前Base Browser的明确项目定义：原文表述为“A set of patches, based around the current Firefox 153 ESR, that strip user hostile features completely out of the code base (as opposed to the common soft-fork approach of disabling these.)”。

这里的关键技术分野在于“通过配置禁用特性（disabling）”与“将模块从代码库中彻底剥离（strip completely out）”之间的本质区别。常规的社区衍生版本通常采取软分叉路线，通过定制编译标志或在构建时注入配置脚本来默认关闭遥测与外部集成。然而Base Browser拒绝了这种妥协方案，选择将所有被判定为对用户不友好的组件及其相关实现代码从源码树中彻底抹去。

原文中作者坚决捍卫彻底删除的必要性，指出这正是解决问题的正确道路。作者在原文中强调：“I believe that deleting these features entirely is the correct approach for exactly the reasons that make it a pain - these features are large, and increasingly tightly integrated into the core browser. They also account for an increasingly percentage of the total firefox code base and quite frankly: I do not believe that these features should be anywhere near the core base of a web browser”。正是由于这些代码庞大且盘根错节，彻底剔除才显得痛苦而又不可或缺。

在本文的分析看来，只要相关代码依旧潜伏在二进制程序内部，潜在的IPC通信路径与依赖关系就依然存在。在复杂的浏览器架构中，禁用标志很容易在上游版本迭代与接口重构过程中失效或被意外重置。在本文的推测看来，Base Browser团队选择付出极高的维护成本去执行源码剥离，反映了从根源上阻断潜在逻辑渗透的严苛设计哲学。

3. 初始AI移除补丁的规模与压缩过程

作为该项目的首次实践，作者亲自编写了一套旨在完整剥离AI集成逻辑的原型补丁。原文用极其详尽的指标记录了这一初期补丁的庞大规模：“a ridiculous patch impacting 1605 files changed with 852297 deletions, totalling 37 megabytes”。为了彻底清除相关模块，该补丁影响了1605个源文件，删除了超过85万行代码，生成的纯文本diff体积高达37MB。

原文严谨地澄清，这一庞大的初期diff反映的是在Firefox中全面剔除AI模块时所触及的实际代码广度，而非Base Browser项目的最终官方发行包本身。这一数据以极具冲击力的方式证实了辅助框架与分发接口在代码库中扎根之深。在此之后的数周内，作者与一个小型志愿者团队持续对补丁展开打磨、拆分与流程优化。

根据原文，贡献者cliffmccarthy与gellge对这项工作提供了实质支持，许多志愿者也参与了测试与论证。为了解决37MB补丁在分发与合并时的技术困难，团队编写了专门的脚本将其压缩至1MB以下。原文介绍，这一压缩方案是通过结合Git原生的不可逆删除机制与定制的Python处理工具实现的，确保在保持补丁极小体积的同时依然支持顺利重放。

在本文的分析看来，将37MB压缩至不足1MB的核心原理，在于将大批量整文件删除的冗余文本差分重构为简洁的文件系统元数据指令。当成百上千个源文件被整体抹除时，常规diff会逐行打印负号内容，导致文件体积失控膨胀。在本文的推测看来，团队不得不自研Python脚本以实现轻量化，侧面印证了清理涉及的模块规模早已超越了常规维护的工作量层级。

4. 与Tor Browser和Waterfox现有缓解路径的对比

在论述Base Browser的技术依据时，原文直接对标了隐私浏览器领域具有代表性的现有项目，特别是Tor Browser和Waterfox。作者在原文中对其维护路径进行了客观评价：“Projects like Tor Browser and Waterfox are painstakingly disabling / patching out the worst - but every release becomes more expensive, and things do slip through.”这些项目采取的策略是费心费力地禁用或针对最糟糕的部分进行局限性修补。

这种选择性禁用的做法会伴随上游版本的每次推进产生不断攀升的维护税。正如原文所警示的，每次新版发布时维护补丁的开销都会变得更为昂贵，而且即便投入严密审查，依然难免会有未被过滤的集成代码遗漏进入稳定构建版。上游变动越频繁，局部禁用补丁发生损坏或逻辑失效的风险就越高。

原文基于这两条不同路径的对比，提炼出若干深刻的技术启示：

  • Tor Browser和Waterfox为了确保安全漏洞修复的快速跟进，长期依赖于标志位控制与温和修补。
  • 随着上游功能复杂度的持续指数级增长，验证和修补禁用逻辑所需的时间成本正在不断堆叠。
  • Base Browser采取激进的源码剔除方案，旨在确保核心库中绝不残留任何与AI调度相关的底层逻辑。
  • 彻底删除虽然阻断了意外启用的可能，但导致分支基线严重分化，显著放大了后续合并的工程难度。

在本文的分析看来，现有衍生项目的维护者并非不理解彻底剔除的优势，而是受到每月必须跟进上游CVE安全补丁的现实约束，被迫做出了妥协。一旦在源码层面大举动刀，后续变动的对齐难度将呈指数级上升。在本文的推测看来，Base Browser的尝试既是对传统妥协路线的彻底反思，也是主动选择了一条充满荆棘的高难度道路。

5. 作者对浏览器发展方向的研判 — Smart Window与AI代理

作者决心采取如此决绝的代码剥离方案，其根本原因在于对Firefox未来长期演进愿景的深层分歧。原文指出，Firefox的战略野心早已超越了在界面旁侧增加一个摘要按钮等简单集成的层面。通过引述Mastodon讨论，作者指出Firefox正在勾勒这样一种未来场景：整个浏览器上下文将被重构为一个名为“smartwindow”的执行载体，其设计初衷既面向人类用户，也同样服务于第三方的AI代理。

当浏览器视窗从单纯的人类文档查看器转变为第三方自动化代理的调度中枢时，浏览器的底层安全假设将发生根本性位移。正如先前在《Mistral与Mozilla Smart Window合作公开与未公开之处 — 拆解AI浏览助手的隐私承诺》中所论证的，将标签页上下文持续提供给推理模型，需要建立在客户端对页面DOM和用户轨迹进行无休止的监听之上。这种模式不可避免地导致庞大的数据采集与分发模块长期驻留在引擎深处。

作者在原文中给出了斩钉截铁的态度宣言：“I don't want the web to go in that direction and, frankly, I cannot follow.”作者明确表示不愿看到网络生态滑向由代理中介主导的局面，并坦言自己无法追随这种变化。尽管作者自认并非主持这一宏大抵抗工程的最理想人选，但依然坚信必须有人迈出行动的第一步，以促成改变的发生。

在本文的分析看来，这一交锋触及了客户端主权的核心：浏览器究竟应是人类意志的忠实执行工具，还是充当商业模型平台的中介。一旦浏览器内核内置了面向外部代理的常驻感知机制，传统的进程隔离与隐私沙盒将面临严峻考验。在本文的推测看来，Base Browser的物理剥离行动，实际上是一场捍卫个人计算主权免受商业自动化全面接管的预防性工程。

6. 超越消费走向创作的工具 — Amaya、Flock与替代协议

原文并未仅仅停留在抗拒与删除等消极防御层面，而是深情回溯了网络浏览器发展史上曾闪烁过的理想主义火花。作者在原文中写道：“I often think about the visions put forth by browsers like Amaya and, much later Flock. That a browser should be a tool for creation as much as consumption.”在作者看来，浏览器不仅应是单向接收并消费网页的查看器，更应当是赋能个人直接参与创作与发布的交互工具。

W3C为验证早年网页规范而打造的Amaya，本质上是一个将浏览与所见即所得HTML文档编辑融为一体的工具。而2000年代中期诞生的Flock，则大胆尝试将博客发布、富媒体分享及分布式标签直接内嵌在客户端中。原文深情回忆起2000年代初Firefox引发浏览器文艺复兴的时期，当时围绕Feed聚合、博客协作与开放评论，人们对浏览器的形态充满了无限的探索激情。

原文指出，历史理想与当今商业化标准之间的脱节表现在以下几个关键维度：

  • 早期网络所倡导的不仅可读、同样应当可写与可自由共享的双向参与构架。
  • 随着商业巨头垄断的形成，原本充满探索性的草根创造精神逐渐被工业化、标准化的消费品包装所取代。
  • 现代网页标准组织在过去十余年间严重受制于跨国商业集团的利益偏好，导致规范极其臃肿。
  • 在每一次页面加载过程中，用户都能清晰感受到纯粹技术理想与商业回报诉求之间激烈的拉扯。

基于这套关于创作工具的理念，作者透露其近年来一直在开展个人技术实验，自主编写轻量化客户端，用于支持Gemini协议（geminiprotocol.net，作者特别注明“是协议而非大型语言模型”）及RSS聚合。通过不受现代商业标准污染的替代技术，探索网络交互的新路径。作者坦承无法确定这是否就是终极未来，但坚信这至少代表了一种可能的替代方向，并借用历史名言呼吁“我们需要全新的声音（we need new noise）”。

7. 降低网页依赖的三项临时措施

由于构建一套成熟的独立浏览器核心需要跨越漫长的周期，作者在原文中披露了其为了摆脱对Firefox及现代庞大浏览器的日常依赖而采取的三项务实临时措施。这些做法旨在将计算工作流分散到单体浏览器之外，实现实用的操作隔离。

  1. 尽可能将内容获取迁移至离线环境： 原文表示正在探索借助openzim离线阅读器（如Kiwix）将日常的基础网页浏览任务移出核心浏览器。OpenZIM文件往往倾向于采用极简的HTML/CSS/JS子集，使得简单的无渲染负担客户端即可流畅解析海量离线资料。
  2. 在条件允许时转向原生独立应用程序： 作为将绝大部分工作时间投入桌面端的用户，作者明确表示相比沉重的网页应用，更偏好独立的原生桌面软件。作者正在积极探索为Mastodon等无法被离线阅读器替代的在线服务寻找专门的原生客户端。
  3. 在条件允许时充分利用Feed阅读器： 与独立应用同理，借助RSS/Atom等聚合Feed，用户完全可以在无需打开整个动态渲染引擎的前提下，直接接收结构化数据并与线上服务顺畅互动。

在本文的分析看来，这些临时规避手段构成了一套实用的个人防御工事，帮助用户避开现代网页引擎过载的脚本开销与追踪环境。无需加载庞大的渲染主线程即可消费静态知识，是对抗浏览器厂商单方面策略变动的稳妥方案。在本文的推测看来，作者分享这一套工作流，是为了在Base Browser等底层改造项目走向完全成熟前，为广大同路人提供切实可行的过渡指南。

8. 长期维护的现实瓶颈与社区汇聚的必要性

原文最为坦诚和理性的篇章，在于其丝毫不避讳这项宏大计划所面临的残酷现实。作者在原文中直言已经做好了在这一战场上落败的心理准备。原文写道：“Now, I am well prepared to lose this battle. I do not believe that there is enough funding, or enough developer effort to maintain something like this long term. Unless we all pool our efforts into making a base like this possible.”作者承认，要长期维持这样一个清洁基座，现有的资金支持和开发者资源都是远远不够的。

维护一款现代浏览器、跟进上游海量漏洞补丁并适应标准演化，需要极其高昂的资本投入与专业的全职工程师团队。原文深刻指出，过去十余年中网络规范已被商业利益过度充斥，维持具备质量保证与安全防线的浏览器，要么需要自建高成本团队，要么必须在依赖链中依附于某个具备雄厚资金的巨头。然而资本的注入往往伴随着商业对价，最终反噬产品的独立性。

原文阐明的Base Browser生存前提与作者心迹可以概括为以下要点：

  • 上游引擎处于频繁重构之中，使得项目本身的技术基座犹如建立在不断流动的流沙之上。
  • 若无法将分散在各处的下游分支力量聚合在一起共同分担维护重任，长效维持在工程上将难以为继。
  • 哪怕本次探索的唯一成果仅仅是让几名开发者学会了如何从源码完整构建Firefox，作者也将其视为一场胜利。
  • 若有任何现存的社区分支项目最终愿意接纳或采纳这套清洁补丁，团队将感到无比欣慰。

在本文的分析看来，Base Browser的核心使命并非在于立即交付一款开箱即用的商业级终端产品，而是为分崩离析的非Chromium生态提供一个可供对齐的“干净基线”。若各分支继续各自为战、在局部修修补补，终将被上游狂暴的发布节奏逐个击垮。在本文的推测看来，作者看似悲观的坦白实则是一记响亮的战略警钟，意在唤起社区正视危机、汇聚力量。
