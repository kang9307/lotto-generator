Introduction: Isolating Slow Requests by the Numbers

When an outbound HTTP request to an API endpoint or remote web server slows down noticeably, developers and infrastructure operators immediately face an attribution problem. It is rarely clear from subjective observation whether the bottleneck stems from domain resolution at the DNS layer, network latency across intermediate routers during the TCP three-way handshake, TLS certificate validation and cipher negotiation, or server-side application processing waiting for the first byte of payload data (TTFB).

The standard tool to settle these questions with concrete figures is command-line curl. However, running a plain curl https://example.com/ or wrapping the command inside the shell time utility yields only one composite number: the total elapsed duration. Only by combining curl diagnostic flags—specifically -w (--write-out) and -v (--verbose)—can an engineer decompose that total time into millisecond-accurate network intervals.

This article is not an exhaustive encyclopedia of all curl parameters. Instead, it focuses squarely on how to isolate exactly where and why a request stalled using verifiable timing differences and exit codes. We examine the unexpected behavior where physical newlines in format files are silently stripped, the arithmetic required to extract stage durations from cumulative time variables, the distinctive logging characteristics of Windows Schannel builds, and how to reliably handle exit codes 28, 6, and 22 within automated pipelines.

For underlying protocol architectures, related aspects have been explored across several foundational guides. For recursive DNS caching, see What DNS Caching Teaches; for TLS negotiation lifecycles, refer to What SSL Taught Us and Why It Is Outdated; for shell exit code propagation, consult Shell Exit Codes and set -e; and for interactive terminal HTTP clients, see Slumber Terminal HTTP Client.

3. The Format File Newline Trap - How curl Strips Real Line Breaks

The -w option directs curl to output transfer telemetry according to a custom template string after the transfer completes. When monitoring multiple parameters, the command-line argument becomes uncomfortably long. The official documentation recommends loading the template from an external text file using the @filename syntax.

3.1 Line Concatenation When Using Physical Newlines

When drafting a format file for the first time, engineers naturally insert physical line breaks (by pressing Enter) after each metric. Below is an actual test where a 9-line template named curl-format.txt was generated and invoked:

printf 'namelookup:    %%{time_namelookup}\nconnect:       %%{time_connect}\n…remote_ip:     %%{remote_ip}\n' > curl-format.txt
cat curl-format.txt
curl -s -o /dev/null -w @curl-format.txt https://example.com/

Despite the file clearly containing 9 separate lines, curl rendered the following unexpected output on stdout:

namelookup:    %{time_namelookup}
connect:       %{time_connect}
…(file contains 9 distinct lines)
=== run 1
namelookup:    0.023826connect:       0.150990appconnect:    0.571661pretransfer:   0.571741starttransfer: 0.711580total:         0.734726http_code:     200size_download: 713remote_ip:     172.66.147.243=== run 2

Every physical newline character in the file was discarded, compressing the entire output into a single unbroken string. Any downstream script expecting line-delimited records failed immediately.

3.2 The Source-Level Rationale for Explicit \n Sequences

This behavior is not an artifact of shell quoting; it is explicitly engineered into curl itself. Examining the implementation of file2string() within src/tool_paramhlp.c of the curl 8.12.1 source repository reveals how files are parsed.

The loader calls memcrlf() while reading bytes from disk into memory. The source comment states: countcrlf FALSE - return number of bytes from the start that DO NOT include any CR or LF or NULL. In short, curl deliberately skips CR and LF bytes when assembling the writeout buffer.

To preserve line boundaries in the rendered output, the template file must contain the literal two-character string \n (a backslash followed by the character n). As documented in the Everything curl writeout specification: You can also output a newline by using \n, a carriage return with \r and a tab space with \t.

Accordingly, the revised format file curl-format2.txt was prepared as follows:

namelookup:    %{time_namelookup}\n
connect:       %{time_connect}\n
appconnect:    %{time_appconnect}\n
pretransfer:   %{time_pretransfer}\n
starttransfer: %{time_starttransfer}\n
total:         %{time_total}\n
http_code:     %{http_code}\n
size_download: %{size_download}\n
remote_ip:     %{remote_ip}\n

Inspection with od -c confirmed that literal \ and n bytes were physically stored prior to each line break.

4. The Nature of -w Time Variables - Cumulative Values and Deltas

Using curl-format2.txt, two sequential requests were issued against https://example.com/:

for i in 1 2; do echo "=== run $i"; curl -s -o /dev/null -w @curl-format2.txt https://example.com/; done

The resulting stdout telemetry produced clean, line-delimited measurements:

=== run 1
namelookup:    0.016839
connect:       0.148093
appconnect:    0.476784
pretransfer:   0.476995
starttransfer: 0.619743
total:         0.619873
http_code:     200
size_download: 713
remote_ip:     172.66.147.243
=== run 2
namelookup:    0.016120
connect:       0.143699
appconnect:    0.463794
pretransfer:   0.463936
starttransfer: 0.600572
total:         0.603125
http_code:     200
size_download: 713
remote_ip:     172.66.147.243

4.1 Request Lifecycle Across Six Cumulative Time Metrics

Reading these values chronologically demonstrates that they increase monotonically from top to bottom. In run 1, namelookup is 0.0168 s, connect is 0.1481 s, appconnect reaches 0.4768 s, and total finishes at 0.6199 s.

This progression underscores a fundamental principle: all time_* write-out variables in curl represent cumulative elapsed timestamps measured from the very beginning of the request (0.000 s) until the conclusion of that specific phase. The 0.148093 s reported for time_connect is not the duration of the TCP handshake alone; it includes the preceding DNS lookup as well.

4.2 Subtraction Formulas for Isolated Stage Durations

To determine how many milliseconds were consumed by each discrete step, one must compute the difference between adjacent timestamps. Converting the run 1 raw seconds into milliseconds yields the following isolated durations:

  • DNS Resolution: time_namelookup = 16.8 ms (run 2: 16.1 ms)
  • TCP Connection: time_connect - time_namelookup = 148.1 - 16.8 = 131.3 ms (run 2: 127.6 ms)
  • TLS Handshake: time_appconnect - time_connect = 476.8 - 148.1 = 328.7 ms (run 2: 320.1 ms)
  • Pre-transfer Setup: time_pretransfer - time_appconnect = 477.0 - 476.8 = 0.2 ms (run 2: 0.1 ms)
  • Server Response Wait (TTFB): time_starttransfer - time_pretransfer = 619.7 - 477.0 = 142.7 ms (run 2: 136.6 ms)
  • Body Content Download: time_total - time_starttransfer = 619.87 - 619.74 = 0.1 ms (run 2: 2.6 ms)

Out of the ~620 ms total transaction, the single largest consumer of time was the TLS handshake, taking approximately 328.7 ms (over 50% of the entire request). An identical pattern appeared in the initial unformatted trial, where appconnect - connect took 0.30 to 0.42 seconds in all three runs, the largest phase each time. Note that these values reflect a single point-in-time test across a specific routing path and must not be interpreted as universal constants.

5. Phase-by-Phase Breakdown and Bottleneck Diagnosis Table

Arranging these delta formulas into a structured reference table allows on-call engineers to map latency spikes directly to root-cause network domains. The following table pairs our run 1 empirical measurements with the standard network failure modes associated with an inflated delta.

Inflated Stage Calculation Formula (Cumulative Deltas) Empirical Measurement (Run 1, single run) Primary Suspects Under Latency Spikes
DNS Resolution namelookup 16.8 ms Local resolver cache misses, overloaded upstream nameservers, high DNS RTT
TCP Handshake connect - namelookup 131.3 ms Physical geographic distance, packet loss on SYN packets, stateful firewall delays
TLS Negotiation appconnect - connect 328.7 ms Large certificate chains, multi-round-trip cipher negotiation, OCSP validation stalls
Server Wait (TTFB) starttransfer - pretransfer 142.7 ms Application database queries, backend lock contention, cold start or cache misses
Body Download total - starttransfer 0.1 ms (713 B) Payload data volume, egress bandwidth saturation, TCP receive window bottlenecks

Applying this arithmetic transforms a vague complaint that an API is slow into a precise operational diagnostic: DNS 17 ms, TCP 131 ms, TLS 329 ms, server first-byte wait 143 ms (a single run in this environment).

6. Interpreting -v Verbose Output and Schannel Limitations

While -w delivers structured telemetry, -v (--verbose) exposes the underlying protocol conversation as an interactive trace.

6.1 Prefix Indicators (*, >, <, {) for Trace Parsing

Executing curl -v -o /dev/null https://example.com/ 2>&1 yields the following representative sequence (progress meter lines removed; there were no cookie or tracking headers):

* IPv6: (none)
* IPv4: 172.66.147.243, 104.20.23.154
*   Trying 172.66.147.243:443...                      ← TCP SYN attempt
* schannel: disabled automatic use of client certificate   ← TLS (Schannel)
* Connected to example.com (172.66.147.243) port 443
* using HTTP/1.x
> GET / HTTP/1.1                                      ← Outbound Request Headers (>)
> Host: example.com
> User-Agent: curl/8.12.1
> Accept: */*
>
* Request completely sent off
< HTTP/1.1 200 OK                                     ← Inbound Response Headers (<)
< Date: Mon, 28 Sep 2026 22:43:27 GMT
< Content-Type: text/html; charset=utf-8
< Transfer-Encoding: chunked
< Connection: keep-alive
< Server: cloudflare

The leading symbol categorizes each line:

  • *: Internal curl diagnostic messages (socket setup, IP selection, TLS lifecycle)
  • >: Outbound HTTP request headers sent to the remote host
  • <: Inbound HTTP response headers returned by the server
  • {: Amount of data received (here { [725 bytes data])

6.2 --trace-time Timestamps and Phase Boundaries

Appending --trace-time prepends wall-clock timestamps to every line:

07:43:32.016000 * Host example.com:443 was resolved.
07:43:32.018000 * IPv6: (none)
07:43:32.018000 * IPv4: 172.66.147.243, 104.20.23.154
07:43:32.018000 *   Trying 172.66.147.243:443...
07:43:32.146000 * schannel: disabled automatic use of client certificate
07:43:32.450000 * Connected to example.com (172.66.147.243) port 443
07:43:32.450000 * using HTTP/1.x
07:43:32.450000 > GET / HTTP/1.1

Two distinct characteristics appear in this trace. First, the sub-second fractions end in 000, indicating that this Windows build resolves timestamps only to millisecond precision.

Second, notice when Connected to is printed. The TCP socket connection began at .018, followed by Schannel initialization at .146, but the Connected to log line was printed at .450—after TLS had effectively finished. In this Schannel build, the connection log appears to mark the end of TLS rather than the raw TCP socket. Relying on log text spacing to deduce phase boundaries is deceptive; the explicit -w metrics (time_connect and time_appconnect) provide far more reliable timing boundaries.

Furthermore, this Schannel build did not print TLS protocol versions (such as TLS 1.3), negotiated cipher suites, or certificate expiry details under -v, and specifying --trace-config tls,dns yields no additional records. We could not check the -v output of OpenSSL builds common on Linux and macOS in this environment, so keep in mind only that other builds may print differently.

7. Two Timeout Types (--connect-timeout vs -m) and Exit Codes

Unbounded network calls are a frequent source of cascading failures in automation. curl provides two distinct timeout mechanisms: --connect-timeout, which bounds socket establishment, and -m (--max-time), which bounds the entire operation.

7.1 Bounding the Connection Phase with --connect-timeout

Targeting the unresponsive IP 10.255.255.1 with --connect-timeout 2 produced the following result:

time curl -sS --connect-timeout 2 -o /dev/null http://10.255.255.1/; echo "exit=$?"
curl: (28) Connection timed out after 2011 milliseconds
real	0m2.122s
exit=28

After exactly 2.011 seconds, curl aborted with exit code 28. According to the curl manpage, --connect-timeout limits only the connection phase; if the socket connects within the allotted window, the transfer proceeds without further constraint.

7.2 Operation-Wide Limits with -m (--max-time)

In contrast, -m (--max-time) governs the total transaction duration. When both options are supplied simultaneously, their interaction follows strict precedence:

curl -sS --connect-timeout 5 -m 0.2 -o /dev/null https://example.com/; echo "exit=$?"
curl: (28) Connection timed out after 204 milliseconds
exit=28

Although the connection limit was set to 5 seconds, the overall operation timeout of 0.2 seconds aborted the attempt after 204 milliseconds. When -m is shorter than --connect-timeout, -m wins even during initial socket establishment.

Although both failures return exit code 28, curl varies its diagnostic error string depending on the phase where the timeout struck:

  • Failure during socket establishment: curl: (28) Connection timed out after 204 milliseconds
  • Failure while waiting for response data (-m 0.5): curl: (28) Operation timed out after 514 milliseconds with 0 bytes received (with http_code returning 000)

When the ceiling was expanded to -m 0.58 (allowing the 0.578 s transfer to finish), curl completed successfully with exit code 0 and HTTP 200.

8. Scripting Integration: -sS, -f, and JSON Output

In automated pipelines, default curl behaviors can mask catastrophic network failures.

8.1 Preserving Errors with -sS and Trapping Failures with -f

Attempting to query a nonexistent host demonstrates the risk of naive silencing:

curl -sS -o /dev/null https://nonexistent.invalid/; echo "exit=$?"
curl -s  -o /dev/null https://nonexistent.invalid/; echo "exit=$?"
curl: (6) Could not resolve host: nonexistent.invalid
exit=6
=== -s alone hides error
exit=6

Using -s alone silences both the transfer meter and stderr, leaving only exit code 6 without context. Automated tasks should always specify -sS (--silent --show-error) to hide meters while preserving critical error messages on stderr.

An even more dangerous trap occurs with HTTP error codes:

curl -s  -o /dev/null -w '%{http_code}\n' https://example.com/no-such-page; echo "exit(no -f)=$?"
curl -sf -o /dev/null https://example.com/no-such-page; echo "exit(-f)=$?"
404
exit(no -f)=0
exit(-f)=22

In this test, a 404 response still gave exit code 0 without -f. Scripts checking only $? will interpret a 404 as success. Adding -f (--fail) forces curl to fail fast on HTTP status codes 400 and above, yielding exit code 22. To inspect response headers without downloading content, use -I (which issues an HTTP HEAD request), and combine with -L to track redirects to their ultimate destination.

The following table summarizes the exit codes and messages confirmed during these tests.

Test Scenario Options Passed Exit Code Actual Error Message Returned
Unresponsive private IP --connect-timeout 2 28 Connection timed out after 2011 milliseconds
Connection aborted by global limit -m 0.2 28 Connection timed out after 204 milliseconds
Transfer stalled waiting for TTFB -m 0.5 28 Operation timed out after 514 milliseconds with 0 bytes received
Unresolvable domain query -sS (with -s alone: 6, no message) 6 Could not resolve host: nonexistent.invalid
HTTP 404 response received Without -f 0 (None; treated as successful transfer)
HTTP 404 response received With -f 22 — (no message; hidden by -s)

8.2 Modern JSON Telemetry with %{json} in curl 8.12

For modern environments that ingest metrics programmatically, curl 8.12.1 supports native JSON serialization via %{json} and %{header_json}:

curl -s -o /dev/null -w '%{json}' https://example.com/ | python -c "…print key count and some keys…"
curl -s -o /dev/null -w '%{header_json}' https://example.com/ | head -c 120

What Could Not Be Verified

While the findings in this guide are anchored in empirical command executions and primary source documentation, certain behaviors could not be directly verified due to environment constraints:

  • OpenSSL-Specific Verbose TLS Lines: All tests used curl 8.12.1 (x86_64-w64-mingw32 build) with the Schannel TLS backend. How OpenSSL-based curl builds common on Linux or macOS print TLS lines under -v could not be checked in this environment.
  • libcurl Official C API Documentation Text for time_*: While the Everything curl manual and curl manpage were reviewed, the complete normative C API manpage descriptions for individual CURLINFO_* timing metrics could not be checked, so our subtraction model relies on the cumulative observations from Experiment 2.
  • HTTP/2 Multiplexed Timing Characteristics: Because the test curl binary lacked HTTP/2 capabilities (reverting to using HTTP/1.x), multiplexed stream timing behaviors across shared TCP connections could not be measured.

## 1. Isolating Bottlenecks - Calculation via Deltas

In curl, `time_*` variables report **cumulative elapsed timestamps** from the start of the transfer. Stage durations must be calculated by subtracting the previous stage timestamp.

| Inflated Phase | Formula (Cumulative Deltas) | Empirical Measurement (1 Run) | Primary Suspects Under Latency Spikes |
|---|---|---|---|
| DNS Resolution | `time_namelookup` | 16.8 ms | Local cache miss, recursive resolver stalls |
| TCP Connection | `time_connect - time_namelookup` | 131.3 ms | Network RTT, firewall packet delay/drop |
| TLS Handshake | `time_appconnect - time_connect` | 328.7 ms | Certificate chain validation, cipher negotiation (dominant) |
| Server Wait (TTFB) | `time_starttransfer - time_pretransfer` | 142.7 ms | Server CPU load, database query stall, cache miss |
| Content Transfer | `time_total - time_starttransfer` | 0.1 ms (713 B) | Response payload size, network bandwidth ceiling |

## 3. Operational Checklist

- [ ] **Format File Newline Trap**: Inside format files (`@curl-format.txt`), you must write literal `\n` characters rather than physical newlines (physical line breaks are stripped by `file2string()`).
- [ ] **Baseline Scripting Flags**: Always use `-sS` (`--silent --show-error`) in scripts to suppress meters while preserving stderr diagnostics.
- [ ] **HTTP Error Detection**: Without `-f` (`--fail`), a 404 response exited with code 0 in our test (per docs, `-f` returns 22 on 400 or greater); always include `-f` or check `%{http_code}`.
- [ ] **Timeout Precedence**: When using both `--connect-timeout` and `-m`, a shorter `-m` cut the transfer even during the connect phase.
- [ ] **Schannel Build Limitations**: This environment's Schannel build (curl 8.12.1, x86_64-w64-mingw32) printed no TLS version, cipher or certificate lines in `-v`; rely on `-w`'s `time_appconnect` for TLS timing.
- [ ] **Protocol Support Check**: Always inspect `curl -V` beforehand to verify protocol availability such as HTTP2.
