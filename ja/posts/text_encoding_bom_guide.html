EF BB BF の3バイトがどこで何を壊すのか、すべて実際に動かして確認した

2026年9月1日 IT・技術

昨日まで動いていたスクリプトが今日は No such file or directory を吐く。ファイルはそこにあり、先頭行も #!/bin/bash のままだ。エディタで開いても妙なところはない。こういうとき疑う場所がひとつある。ファイル先頭の3バイトだ。

以下の出力はすべて Windows 10 (10.0.19045) の Git Bash 環境で実際に実行したものである。使った道具は GNU bash 5.2.37 (MINGW64/MSYS2)、GNU sed 4.9、GNU grep 3.0、GNU coreutils 8.32、GNU libiconv 1.18、dos2unix 7.5.2、file 5.46、xxd 2024-12-07、Node.js v22.16.0、Python 3.11.9、Windows PowerShell 5.1.19041.6456 である。プラットフォームやバージョンが違えばメッセージの文言や挙動が変わりうる。

BOM はもともとバイト順の印だった

名前が答えである。Byte Order Mark、バイト順の印。これは UTF-16 や UTF-32 のように複数バイトをまとめて一単位として読む符号化方式のために作られた。そうした方式では同じ値でも上位から格納するか下位から格納するかでバイトが逆転する。だからファイル先頭に U+FEFF をひとつ置き、読む側がその2バイトが FE FF で来るか FF FE で来るかを見て順序を判断できるようにした。

ユニコードコンソーシアムの FAQ はこの点を明確に書いている。BOM はデータストリーム先頭の U+FEFF であり、バイト順と符号化形式を定義する署名として使われる、と。そしてすぐに UTF-8 を切り分けて説明する。UTF-8 はバイト指向なのでその問題自体が存在しない。常に同じバイト順を持つからだ。したがって UTF-8 における先頭の BOM は順序を知らせるものではなく、印のないテキストファイルが UTF-8 であることを示す署名としてのみ使われると書かれている。同じ文書はすぐに注意をひとつ添える。UTF-8 データを受け取る側には BOM を想定していないものがある、と。

ではなぜこんなによく見かけるのか。Windows 系の道具の古い慣行のせいである。コードページが地域ごとに違った時代、拡張子だけではそのテキストが UTF-8 なのか地域コードページなのかを知る手立てがなかった。先頭に3バイト付ければ少なくとも自分たちの道具どうしでは区別がついた。メモ帳がそう保存し、PowerShell の -Encoding utf8 も長らくその意味だった。Linux 側は最初から UTF-8 を既定に据えたのでこの署名は要らなかった。二つの慣行がひとつのリポジトリで出会うと、そこから事故が始まる。

  • UTF-16 / UTF-32 — バイト順の問題が実在する。BOM が本来やろうとした仕事はここにある
  • UTF-8 — 順序の問題がない。付いた BOM は順序の印ではなく、ただの署名だ
  • 署名が要る状況 — 符号化方式を伝える別の経路がないとき。拡張子とローカルコードページだけで判断せざるをえない道具たち
  • 署名が邪魔になる状況 — 先頭バイトがそのまま文法である形式。シェバン、JSON、XML 宣言、CSV のヘッダがすべてこれに当たる

見えないということの実際の意味

同じ内容のファイルを二つ作り、片方にだけ BOM を付けて並べてみると、この問題がなぜ長く気づかれないのかがすぐ見える。cat は二つを同じに見せる。大きさだけが3バイト違う。

$ printf 'hello\n'              > plain.txt
$ printf '\xef\xbb\xbfhello\n'  > bom.txt

$ cat plain.txt; cat bom.txt
hello
hello                      # 二行がまったく同じに見える

$ ls -l plain.txt bom.txt
-rw-r--r-- 1 user user 6 Sep  1 10:25 plain.txt
-rw-r--r-- 1 user user 9 Sep  1 10:25 bom.txt

$ xxd plain.txt
00000000: 6865 6c6c 6f0a                           hello.
$ xxd bom.txt
00000000: efbb bf68 656c 6c6f 0a                   ...hello.

$ od -c bom.txt
0000000 357 273 277   h   e   l   l   o  \n
0000011

$ file plain.txt bom.txt
plain.txt: ASCII text
bom.txt:   Unicode text, UTF-8 (with BOM) text

xxd の右欄に打たれた点三つが ef bb bf だ。file は「with BOM」とまで書いてくれる。ここまでは道具が親切である。問題は比較の道具だ。

$ diff plain.txt bom.txt
1c1
< hello
---
> hello                    # 画面上は同じ文字なのに違うと出る
$ echo $?
1

$ cmp plain.txt bom.txt
plain.txt bom.txt differ: char 1, line 1

$ wc -c < bom.txt
9
$ LC_ALL=en_US.UTF-8 wc -m < bom.txt
7                          # バイト9、文字7 (BOM 1 + hello 5 + 改行 1)

diff は正確に仕事をしている。二行が違うと言い、実際に違う。ただ人に見せた画面にはその違いがない。コードレビューで「なぜこの行が変更扱いなのか」と首をかしげて通してしまう変更は、こうして生まれる。

シェバンがシェバンでなくなる

実行ファイルの先頭2バイトが #! なら、カーネルはその後ろをインタプリタのパスとして読む。その2バイトがファイルの先頭バイトであることが条件だ。前に3バイト挟まれば、その行はもはやシェバンではなく単なる最初のコマンド行になる。

$ printf '#!/bin/bash\necho ok\n'              > ok.sh
$ printf '\xef\xbb\xbf#!/bin/bash\necho ok\n'  > bomshebang.sh
$ chmod +x ok.sh bomshebang.sh

$ ./ok.sh
ok

$ ./bomshebang.sh
./bomshebang.sh: line 1: #!/bin/bash: No such file or directory
ok
                           # 上のメッセージの #! の前に見えない BOM がそのまま出力されている

$ head -c 16 bomshebang.sh | xxd
00000000: efbb bf23 212f 6269 6e2f 6261 7368 0a65  ...#!/bin/bash.e

この出力には読むべき箇所が二つある。ひとつはエラーメッセージがファイル名ではなくシェバン行そのものを指していることだ。bash が消えたのかと思って which bash を叩いてみるが、bash はちゃんとある。実行されなかったのは <BOM>#!/bin/bash という名前のコマンドである。

もうひとつは次の行に ok が出ていることだ。この環境(MSYS2 の bash 5.2.37)ではシェバンの解釈に失敗したあと、シェル自身が残りを読んで実行した。つまりスクリプトは死なず、先頭行だけ失敗したまま進む。こちらのほうが悪い。終了コードが 0 なので CI も通る。

$ printf '\xef\xbb\xbf#!/bin/bash\nset -e\necho reached\n' > strict.sh
$ bash strict.sh
strict.sh: line 1: #!/bin/bash: No such file or directory
reached
$ echo $?
0                          # set -e を掛けても先頭行の失敗は捕まらない

set -e はその行以降に適用されるので、1行目の失敗には手が届かない。この組み合わせのせいで「ビルドは成功したのに成果物がおかしい」という形で数日後に見つかることがある。

設定ファイルでは先頭行だけが消える

シェルが読み込むのはスクリプトだけではない。.env のように KEY=value を並べて source で読み込むファイルも同じ規則に乗る。そしてここで現れる症状はずっと静かだ。ちょうど先頭行ひとつだけが入らない。

$ printf 'API_HOST=example.internal\nAPI_PORT=8080\n'             > plain.env
$ printf '\xef\xbb\xbfAPI_HOST=example.internal\nAPI_PORT=8080\n' > bom.env

$ bash -c '. ./plain.env; echo "HOST=[$API_HOST] PORT=[$API_PORT]"'
HOST=[example.internal] PORT=[8080]

$ bash -c '. ./bom.env; echo "HOST=[$API_HOST] PORT=[$API_PORT]"'
./bom.env: line 1: API_HOST=example.internal: command not found
HOST=[] PORT=[8080]
$ echo $?
0                          # 二行目からは正常だ。先頭行だけが空である

API_PORT はきちんと入り、API_HOST だけが空文字列だ。ファイルには確かに値が書いてあるのに変数だけが空なので、たいていは打ち間違いを探したり読み込み順を疑ったりして時間を使う。command not found の一行がどこかのログに流れていたとしても、その行の左端に見えない文字があるという事実は画面からは分からない。

同じことが YAML でも起きる。自前で解析するコードなら、先頭キーの名前が変わる。

$ printf '\xef\xbb\xbfname: demo\nport: 8080\n' > app.yaml
$ node -e "
const s = require('fs').readFileSync('app.yaml', 'utf8');
const m = {};
for (const line of s.split(/\r?\n/)) {
  if (!line) continue;
  const i = line.indexOf(':');
  m[line.slice(0, i)] = line.slice(i + 1).trim();
}
console.log('keys :', JSON.stringify(Object.keys(m)));
console.log('name :', m.name);
console.log('port :', m.port);
"
keys : ["name","port"]     # 先頭キーの前に U+FEFF が付いている
name : undefined
port : 8080

キー一覧を出力しても ["name","port"] に見える。ところが m.name は undefined だ。目で見るものとプログラムが比較するものが分かれる典型的な場所である。

JSON - 標準は付けるなと言っている

JSON はこの問題について標準文書に答えが書かれている数少ない例だ。RFC 8259 の 8.1 節、文字符号化の項は二つの文を並べて置いている。ひとつは強制である。ネットワークで送信する JSON テキストの先頭に BOM を付けてはならない(MUST NOT)。もうひとつは許容だ。相互運用性のために、JSON テキストを解析する実装は BOM をエラーとして扱う代わりに無視してもよい(MAY)。

この非対称が現場の混乱をそのまま説明する。付ける側はしてはならず、取り除く側はしてもしなくてもよい。つまりあるパーサは通し、あるパーサは投げる。同じファイルが道具を変えると違う動きをする理由がここにある。Node.js v22.16.0 では、ひとつのランタイムの中でも分かれる。

// jsontest.js
const fs = require('fs');
for (const f of ['plain.json', 'bom.json']) {
  const raw = fs.readFileSync(f, 'utf8');
  console.log(f, 'first char U+' +
    raw.codePointAt(0).toString(16).toUpperCase().padStart(4, '0'));
  try   { console.log('  OK', JSON.stringify(JSON.parse(raw))); }
  catch (e) { console.log('  ' + e.name + ': ' + e.message); }
}

$ node jsontest.js
plain.json first char U+007B
  OK {"name":"demo","port":8080}
bom.json first char U+FEFF
  SyntaxError: Unexpected token '', "{"name":""... is not valid JSON

$ node -e "console.log(JSON.stringify(require('./bom.json')))"
{"name":"demo","port":8080}
                           # 同じファイルなのに require では通る

JSON.parse は投げ、require は通る。モジュールローダ側が BOM を取り除いて渡すからだ。だから「ローカルでは動くのにデプロイすると動かない」という形で現れるが、実際に分かれたのは環境ではなくそのファイルを読むコード一行である。require('./config.json') で読んでいたものを JSON.parse(fs.readFileSync(...)) に変えた瞬間に壊れる。

もうひとつ付け加えることがある。SyntaxError のメッセージで Unexpected token の後の引用符の中が空に見える。そこに U+FEFF が入っている。エラーメッセージすら原因を見せてくれない。

CSV の逆説 - ここでは BOM が解法だ

ここまで読むと BOM を無条件に消すのが答えのように見える。ところがちょうど逆の場所がひとつある。Excel で開く CSV だ。UTF-8 で保存した CSV を Excel でそのままダブルクリックして開くと文字が化けることが多く、ファイル先頭に BOM を付けると UTF-8 と認識してきちんと開く場合が多い。CSV の書き出し機能を作るときに BOM をわざわざ付けるコードが溢れている理由である。

つまりこの3バイトは人が開くファイルではヒントであり、プログラムが読むファイルではゴミだ。問題は同じ CSV が両方の用途に使われる点である。Excel 用に BOM を付けて書き出したファイルが後で別のシステムの入力になると、先頭列の名前が変わる。

// csv.js — trim() を使わないパーサ
const fs = require('fs');
const text  = fs.readFileSync(process.argv[2], 'utf8');
const lines = text.split(/\r?\n/).filter(l => l.length > 0);
const cols  = lines[0].split(',');
const rows  = lines.slice(1).map(r =>
  Object.fromEntries(r.split(',').map((v, i) => [cols[i], v])));

console.log('cols[0]         :', JSON.stringify(cols[0]));
console.log('cols[0].length  :', cols[0].length);
console.log('cols[0] === "id":', cols[0] === 'id');
console.log('row0.id         :', rows[0].id);

$ node csv.js plain.csv
cols[0]         : "id"
cols[0].length  : 2
cols[0] === "id": true
row0.id         : 1

$ node csv.js bom.csv
cols[0]         : "id"     # 画面には同じに見える
cols[0].length  : 3        # ところが長さが3だ
cols[0] === "id": false
row0.id         : undefined

cols[0].length が 2 と 3 である。この一行がなければ何も見えない。失敗の仕方も悪い。例外は出ず、undefined が静かに流れ込む。十万行の取り込み作業が「全件成功、先頭列はすべて空値」で終わる。

どちらを直すべきかはファイルの最終的な消費者が決める。人が Excel で開くのが目的なら付け、プログラムがまた食べる予定なら付けない。両方の用途が重なるなら、ファイルを二通り作るほうがよい。

なぜ一部のコードは無事なのか - trim() の正体

上の例を作るとき、最初はヘッダ行を text.trim().split('\n') で切っていた。すると BOM のファイルがそのまま通った。パーサの書き方が悪かったのではなく、JavaScript の trim() が U+FEFF を空白として扱って取り除いたからだ。

// t7.js — '\ufeff' は BOM 文字そのものを表すエスケープだ
const s = '\ufeffid';
console.log('length          :', s.length);
console.log('trim().length   :', s.trim().length);
console.log('trim() === id   :', s.trim() === 'id');
console.log('/\\s/ matches?   :', /\s/.test('\ufeff'));
console.log('Number()        :', Number('\ufeff42'));
console.log('parseInt()      :', parseInt('\ufeff42'));

$ node t7.js
length          : 3
trim().length   : 2
trim() === id   : true
/\s/ matches?   : true
Number()        : 42
parseInt()      : 42

/\s/ が U+FEFF にマッチし、Number() と parseInt() は先頭の BOM を無視して 42 を返す。この寛容さが問題を断続的にする。あるフィールドは trim() を経て無事で、あるフィールドは経ずに壊れる。同じファイル、同じコードベース、違う結果だ。

  • オブジェクトのキーとして使う経路はたいてい trim() を通らない。だからヘッダ名で壊れる
  • 数値に変換する経路はほぼ常に通る。だから数値検証ではこのバグを捕まえられない
  • 正規表現の検証も \s を使っていれば通る。「値に空白があってはならない」の類の検査は BOM を捕まえない
  • つまり普通の検証器では引っかからない。先頭3バイトを直接見る検査を別に置く必要がある

比較と検索とハッシュが静かにずれる

BOM の付いた行は、行頭にアンカーを掛けた検索から漏れる。^ の次に来るのが i ではなく U+FEFF だからだ。ログのフィルタ、バッチスクリプト、移行の検証クエリがここで静かに 0 件を返す。

$ grep -c '^id' plain.csv
1
$ grep -c '^id' bom.csv
0                          # アンカーを掛けた瞬間に引っかからない
$ grep -c 'id' bom.csv
1                          # アンカーを外せば引っかかる

$ grep -Fxc 'id' list_a.txt
1
$ grep -Fxc 'id' list_b.txt
0                          # 行全体の一致も同じだ

$ cat v1.txt v2.txt | sort -u | xxd
00000000: 616c 7068 610a efbb bf61 6c70 6861 0a    alpha....alpha.
                           # sort -u が同じ語を二つ残す

$ sha256sum plain.html bom.html
904ee45b2e532f436f4c05f8d809365538b9bf9843030bc01d0f9079deb0cbe7 *plain.html
a3369d9b5f62004281debdaccdc69395cc94af732b19023258576308ce7cbc35 *bom.html

ハッシュが違うことは配布の検証で即座に問題になる。「成果物が以前と同一か」をチェックサムで確かめるパイプラインなら、誰かがエディタの設定を変えただけで全件変更ありと出る。

もうひとつ。BOM はファイル先頭にだけあるものではない。BOM 付きのファイルを複数そのまま連結すると途中に埋まる。

$ cat part1.csv part2.csv > merged.csv
$ grep -c $'\xef\xbb\xbf' merged.csv
2
$ xxd merged.csv
00000000: efbb bf69 642c 760a 312c 610a efbb bf69  ...id,v.1,a....i
00000010: 642c 760a 322c 620a                      d,v.2,b.
                           # 二つ目の BOM がデータの真ん中に入っている

途中の U+FEFF は古いユニコードで zero-width no-break space としても使われていた文字なので、描画しても何も見えない。ログ収集器や分割ダウンロードの結果を結合するバッチでこういうファイルが作られると、追跡がとりわけ長引く。

ウェブで現れる症状

HTML ファイルの先頭に BOM があると、文書の最初の文字が < でなくなる。バイトで見るとこうだ。

$ head -c 24 bom.html | xxd
00000000: efbb bf3c 2144 4f43 5459 5045 2068 746d  ...<!DOCTYPE htm
00000010: 6c3e 0a3c 6874 6d6c                      l>.<html

$ node -e "
const s = require('fs').readFileSync('bom.html', 'utf8');
console.log('indexOf   :', s.indexOf('<!DOCTYPE'));
console.log('startsWith:', s.startsWith('<!DOCTYPE'));
"
indexOf   : 1
startsWith: false

ここから先は実行で確認しておらず、構造だけを書く。サーバサイドのテンプレートを使う環境でよく報告される形は二つある。ひとつは本文の一番上に正体不明の空行や余白ができることだ。文書が始まる前に文字がひとつ出力されたので、パーサがそれを本文の内容として処理する。もうひとつはヘッダ送信の失敗だ。PHP のようにファイルの内容をそのまま出力ストリームに流す構造では、<?php タグの前の3バイトがすでに出力なので、その後のヘッダ設定やリダイレクトが「すでにヘッダが送信された」の類の警告とともに失敗する。

こういう場合に使える手は、症状の側ではなくファイルの側から絞ることだ。読み込まれるファイルが数十個あっても、先頭3バイトが EF BB BF のものだけを抜き出せばたいてい一つ二つで済む。

あるかどうかを確かめる方法

道具は複数あるが、やることは同じだ。ファイルの先頭3バイトを見る。状況に応じて楽なものを使えばよい。

$ file config.json run.sh clean.txt
config.json: Unicode text, UTF-8 (with BOM) text
run.sh:      POSIX shell script, Unicode text, UTF-8 (with BOM) text executable
clean.txt:   ASCII text

$ xxd config.json | head -1
00000000: efbb bf7b 2261 223a 317d 0a              ...{"a":1}.

$ grep -rlI $'\xef\xbb\xbf' .
./config.json
./sub/run.sh

$ grep -rlI $'^\xef\xbb\xbf' .    # 行頭にあるものだけ
./config.json
./sub/run.sh

$ cat -A bom.txt
M-oM-;M-?hello$

$ sed -n l bom.txt
\357\273\277hello$

cat -A の M-oM-;M-? と sed -n l の \357\273\277 は、同じ3バイトをそれぞれメタ表記と8進数で見せたものだ。端末で目視確認するときはこの二つが一番速い。ただし grep -rlI はファイル途中の BOM も一緒に拾うことを知って使う必要がある。アンカーを付ければ絞れるが、それも「ある行の先頭」であって「ファイルの先頭」ではない。正確に先頭3バイトだけを見るなら、プログラムで開くほうがよい。

// bomcheck.js — 先頭3バイトだけ読んで確認する。CI に掛けやすい
const fs = require('fs'), path = require('path');
const BOM = Buffer.from([0xEF, 0xBB, 0xBF]);

function walk(dir, out = []) {
  for (const e of fs.readdirSync(dir, { withFileTypes: true })) {
    const p = path.join(dir, e.name);
    if (e.isDirectory()) walk(p, out); else out.push(p);
  }
  return out;
}

let bad = 0;
for (const f of walk(process.argv[2] || '.')) {
  const fd = fs.openSync(f, 'r');
  const head = Buffer.alloc(3);
  fs.readSync(fd, head, 0, 3, 0);
  fs.closeSync(fd);
  if (head.equals(BOM)) { console.log('BOM: ' + f); bad++; }
}
console.log(bad ? bad + ' file(s) with a UTF-8 BOM' : 'no BOM found');
process.exit(bad ? 1 : 0);

$ node bomcheck.js ./tree
BOM: tree\config.json
BOM: tree\sub\run.sh
2 file(s) with a UTF-8 BOM
$ echo $?
1

$ node bomcheck.js ./cleantree
no BOM found
$ echo $?
0

PowerShell 側では ReadAllBytes で先頭を出力すればよい。注意がひとつある。Get-Content で読むとBOM がすでに取り除かれた文字列が来る。Windows PowerShell 5.1.19041.6456 で BOM 付きのファイルを Get-Content -Raw で読んで最初の文字を出すと U+006C、つまり本文の最初の文字が出る。文字列のレベルでは何も問題がないように見えるので、確認は必ずバイトのレベルで行う。

PS> $b = [System.IO.File]::ReadAllBytes('config.json')
PS> ($b[0..2] | ForEach-Object { $_.ToString('X2') }) -join ' '
EF BB BF

PS> (Get-Content -Path config.json -Raw)[0]
{                          # 文字列として読むと BOM はすでにない

消す方法、そして消して壊す方法

消すこと自体は難しくない。難しいのは消してはいけないファイルまで触らないことだ。一括処理には取り消しがないので、バックアップを取ってから始める。

$ sed '1s/^\xEF\xBB\xBF//' in.csv > out.csv     # 新しいファイルへ (最も安全)
$ sed -i.bak '1s/^\xEF\xBB\xBF//' in.csv        # その場編集 + 原本のバックアップ

$ xxd in.csv | head -1
00000000: 6964 2c6e 616d 650a 782c 790a            id,name.x,y.
$ xxd in.csv.bak | head -1
00000000: efbb bf69 642c 6e61 6d65 0a78 2c79 0a    ...id,name.x,y.

$ awk 'NR==1{sub(/^\xef\xbb\xbf/,"")}1' in.txt > out.txt
$ perl -pi -e 's/^\x{ef}\x{bb}\x{bf}// if $.==1' in.txt

1s/ で対象を先頭行だけに絞ったのが重要だ。範囲を指定しないと、本文の途中に正当に入っているかもしれない U+FEFF まで消してしまう。そして -i に接尾辞を付ければ GNU sed 4.9 は原本を .bak として残す。数百のファイルを一度に回す作業なら、こちらを既定にするほうがよい。

次は専用の道具だ。ここに罠がひとつある。

$ xxd before.csv
00000000: efbb bf61 0d0a 620d 0a                   ...a..b..     # BOM + CRLF

$ dos2unix --remove-bom before.csv
dos2unix: converting file before.csv to Unix format...

$ xxd before.csv
00000000: 610a 620a                                a.b.          # BOM も CR も消えた

$ dos2unix -m -n a.csv a.bom.csv          # -m は逆に BOM を付ける
$ xxd a.bom.csv
00000000: efbb bf61 0a62 0a                        ...a.b.

dos2unix --remove-bom は BOM だけを消すのではない。名前のとおり改行まで LF に変える。上の出力で 0d0a の二組がすべて 0a になっている。Windows 専用として保たなければならないファイルにこれを掛けると、BOM の問題をひとつ直そうとして改行の問題を新しく作る。逆に付ける側は -m で、-n を渡せば原本を残して新しいファイルに書く。

iconv はこの用途では期待どおりに動かない。

$ iconv -f UTF-8 -t UTF-8 in.csv > out.csv
$ xxd out.csv | head -1
00000000: efbb bf69 642c 6e61 6d65 0a78 2c79 0a    ...id,name.x,y.
                           # UTF-8 から UTF-8 へは BOM がそのまま残る

$ iconv -f UTF-8-BOM -t UTF-8 in.csv
iconv: conversion from UTF-8-BOM unsupported

$ iconv -f UTF-8 -t UTF-16 ab.txt | xxd
00000000: feff 0041 0042 000a                      ...A.B..      # BOM が付く
$ iconv -f UTF-8 -t UTF-16LE ab.txt | xxd
00000000: 4100 4200 0a00                           A.B...        # 付かない

GNU libiconv 1.18 では UTF-8-BOM という名前は認識されない。ただ最後の二行は覚えておく価値がある。UTF-16 に変換すると BOM が付き、UTF-16LE に変換すると付かない。エンディアンを名前に明示すれば順序を知らせる必要がなくなるからだ。

最後に、最もよく提案されるが最も危険な方法である。

$ printf '\xef\xbb\xbfhi\n' > a.txt
$ tail -c +4 a.txt | xxd
00000000: 6869 0a                                  hi.           # きれいに消えた

$ printf 'hi there\n' > b.txt                                    # BOM のないファイル
$ tail -c +4 b.txt | xxd
00000000: 7468 6572 650a                           there.        # 'hi ' を食べた

tail -c +4 は先頭3バイトを無条件に捨てる。BOM のあるファイルにだけ回せば正しいが、ディレクトリ全体にループで回した瞬間、BOM のないファイルの先頭3文字が消える。上の例では hi  がなくなっている。この方式を使うなら必ず前にBOM の有無を確かめる条件を付けなければならない。

読む側で解決する道もある。ファイルを直せない状況ならこちらがよい。Python 3.11.9 はこの用途のコーデックを標準で持っている。

>>> open('bom.json', encoding='utf-8').read()[0]
'\ufeff'
>>> json.load(open('bom.json', encoding='utf-8'))
json.decoder.JSONDecodeError: Unexpected UTF-8 BOM (decode using utf-8-sig): line 1 column 1 (char 0)

# csv.DictReader — 符号化名ひとつで先頭列の名前が変わる
utf-8      fieldnames: ['\ufeffid', 'name', 'qty']   row.get('id') -> None
utf-8-sig  fieldnames: ['id', 'name', 'qty']         row.get('id') -> 1

Python のエラーメッセージはこの記事で見たなかで最も親切だ。原因と解法を一行に一緒に書いてくれる。utf-8-sig は BOM があれば取り除き、なければそのまま通すので、入力ファイルを制御できないコードでは既定にしてよい値である。

方法道具・バージョン一緒に起きること使う場面
sed '1s/^\xEF\xBB\xBF//'GNU sed 4.9先頭行だけ触る。それ以外の変化なし既定。-i.bak を付けて使う
dos2unix --remove-bomdos2unix 7.5.2CRLF が LF になるどのみち LF に統一するファイルにだけ
dos2unix -mdos2unix 7.5.2BOM を付ける。改行も変換するExcel 用の CSV を作るとき
iconv -f UTF-8 -t UTF-8GNU libiconv 1.18何も起きない。BOM が残るこの用途には使わない
tail -c +4coreutils 8.32BOM がなければ本文3バイトを食べる条件検査なしには使わない
encoding='utf-8-sig'Python 3.11.9ファイルを直さない。読むときだけ取り除く他人のファイルを受け取って読むとき

付けるべき場所と付けてはいけない場所

規則はひとつにまとまる。先頭バイトがそのまま文法である形式には付けない。シェバン、JSON の開き波括弧、XML 宣言、CSV の先頭列名は、すべてその先頭バイトの位置が意味を持つ。逆に符号化方式を伝える別の経路がなく、人が開くのが目的のファイルなら付けるほうがよい。

ファイルの種類BOM理由
シェルスクリプト (.sh, .bash)付けないシェバンがシェバンでなくなる。先頭行だけ失敗して回り続ける形なのでなお悪い
JSON (.json)付けないRFC 8259 が送信時の追加を禁じている。パーサが無視してくれる義務はない
YAML・設定ファイル (.env 含む)付けない先頭キーの名前が変わる。例外なく静かに失敗する
ソースコード全般付けないハッシュが変わり、diff が見えない変更を作る
Excel で開く CSV付けるBOM がないと文字化けして開くことが多い。人が開くファイルだ
プログラムが読む CSV付けない先頭列の名前が id でなくなる。例外なく undefined が流れる
Windows 専用のテキスト (メモ帳など)付けてもよい符号化方式を伝える他の手段がない。他のシステムへ渡す予定がないときだけ
UTF-16 / UTF-32 のファイル付けるバイト順の問題が実在する。BOM の本来の用途がここだ
HTML付けない<meta charset> や HTTP ヘッダがすでに符号化方式を伝えている

あいまいな場合の判断基準もひとつに減らせる。このファイルを最後に開くのは人かプログラムか。人なら付けるほうに得があり、プログラムならほぼ常に損だ。両方なら、ファイルを分ける。

チームで再発を止める方法

一度消すことより、二度と生まれないようにするほうが難しい。ほとんどは人ではなく道具の設定が生み出すからだ。最もよくある発生源は PowerShell である。

PS> "line one" | Set-Content a_default.txt
PS> "line one" | Set-Content b_utf8.txt   -Encoding utf8
PS> "line one" | Out-File   c_outfile.txt -Encoding utf8
PS> [System.IO.File]::WriteAllText("$pwd\d_nobom.txt", "line one`n",
      (New-Object System.Text.UTF8Encoding($false)))

a_default.txt   len=10   first bytes: 6C 69 6E 65 20 6F 6E 65
b_utf8.txt      len=13   first bytes: EF BB BF 6C 69 6E 65 20
c_outfile.txt   len=13   first bytes: EF BB BF 6C 69 6E 65 20
d_nobom.txt     len= 9   first bytes: 6C 69 6E 65 20 6F 6E 65

PS> "x" | Set-Content f.txt -Encoding utf8NoBOM
Cannot bind parameter 'Encoding'. Cannot convert value "utf8NoBOM" to type
"Microsoft.PowerShell.Commands.FileSystemCmdletProviderEncoding".

Windows PowerShell 5.1.19041.6456 では -Encoding utf8 がBOM を付ける。そして utf8NoBOM という値はこの版に存在せず、パラメータのバインド段階で拒否される。この版で BOM なしの UTF-8 を書くなら、UTF8Encoding($false) を直接渡すのが確実な方法だ。配布スクリプトが設定ファイルを生成する構造なら、ここが最初の点検対象になる。

エディタ側は .editorconfig である程度制御できる。仕様に charset 属性があり、値として latin1、utf-8、utf-8-bom、utf-16be、utf-16le が使える。仕様自体が utf-8-bom の使用は推奨しないと書いている。ただしこれはエディタが読んで従うときにのみ成立する取り決めだ。対応していない道具がファイルを書けばそのまま抜ける。

# .editorconfig
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true

[*.csv]
charset = utf-8-bom          # Excel で開く書き出しファイルだけ例外にする

ここではっきりさせておくことがある。git は BOM を正規化してくれない。gitattributes の文書が扱う text と eol は改行の変換であり、working-tree-encoding は UTF-16 系のようにリポジトリと作業ツリーの符号化方式が違うときに使うものだ。UTF-8 の BOM を付けたり外したりする属性はない。改行は .gitattributes の一行でチーム全体が揃うが、BOM にはそういう仕掛けがないということだ。

だから最後の防衛線は検査である。前節の bomcheck.js は BOM を見つけると終了コード 1 を返すので、CI の段階にそのまま掛けられる。シェルしかない環境なら一行でも足りる。

# BOM がひとつでもあれば失敗させる (GNU grep 3.0)
! grep -rlI $'^\xef\xbb\xbf' --include='*.sh' --include='*.json' \
                            --include='*.yaml' --include='*.yml' . \
  || { echo "BOM found in the files above"; exit 1; }
  • 発生源から止める — PowerShell の -Encoding utf8、メモ帳、一部の Windows エディタがほとんどを作る
  • .editorconfig に合意を書いておく — 強制力はないが、道具が対応していれば自動的に揃う
  • git には期待しない — 改行と違ってリポジトリが揃えてくれない
  • CI で止める — 先頭3バイトを見る検査ひとつで足りる。拡張子で対象を絞って CSV の例外を残す
  • 一括削除はひとつのコミットで — 他の変更と混ぜると、後から何が変わったのか区別できなくなる

BOM と改行は別の問題だ

この二つは常に一緒に語られるが、原因も解法も違う。同じ場所で現れ、同じ道具で直すことが多いせいでひとまとめにされただけだ。実際には次の表ほど違う。

項目UTF-8 BOMCRLF / LF
位置ファイル先頭の3バイト、一度だけすべての行末、ファイル全体
バイトEF BB BF0D 0A または 0A
git が正規化するかしない。該当する属性がないする。text・eol 属性で揃う
代表的な症状先頭行だけ失敗。シェバン・先頭キー・先頭列名bad interpreter: /bin/bash^M の類の即時失敗
見つけにくさ高い。画面には何も見えない低い。エラーメッセージに ^M が出る
直す道具sed 1s、utf-8-sig、先頭3バイトの検査dos2unix、.gitattributes

実務で重要な違いは三行目だ。改行はリポジトリの設定でチーム全体を一度に揃えられるが、BOM はそれぞれのエディタとそれぞれのスクリプトから生まれ続ける。だから改行は方針で解き、BOM は検査で解くのが正しい。dos2unix が二つを一度にやってくれるという事実がこの区別をぼやけさせるが、先に見たとおりその便利さは望まない変換を一緒に連れてくる。

符号化方式そのものが食い違って文字が化ける問題 — たとえば cp949 で保存されたファイルを UTF-8 で読んで ????? や ìëíì になる側 — は別の層の話であり、この記事の主題ではない。そちらは ハングルが壊れる地点を特定する方法 にまとめてある。圧縮ファイル内のファイル名が壊れる場合は zip の中のファイル名が壊れる地点 が、ハングルの文字列を正規表現で扱って外す問題は ハングル正規表現の罠 が該当する。

確認できなかったこと

  • Excel の実際の挙動 — BOM があれば UTF-8 の CSV をきちんと開くというのは広く使われる対処だが、この記事では Excel で開いていない。バージョンや地域設定によって結果が違うという報告もあるので、導入前に実際の利用環境の Excel で直接確認するほうがよい。確認したのはプログラムがそのファイルを読むときに先頭列の名前が変わるという側だけである
  • PowerShell 7 系 — この環境に pwsh が入っておらず確認できなかった。本文の -Encoding utf8 が BOM を付けるという結果と utf8NoBOM がないという結果は Windows PowerShell 5.1.19041.6456 限定である。版が違えば既定値も違いうるので、使う版でバイトを直接出力して確かめてほしい
  • PHP のヘッダ送信失敗 — この環境に PHP がなく再現できなかった。9節の該当箇所は構造の説明であって実行結果ではない。実際に確認したのは HTML ファイルで文書の最初の文字が < でなくなるところまでである
  • BSD 系の道具 — ここで使った sed は GNU sed 4.9 である。\xEF のような16進エスケープと -i の接尾辞の扱いは GNU 実装に依存し、macOS 既定の sed では異なる動作をすると知られているが、確認できる環境がなかった
  • git の実際の挙動 — BOM を正規化する属性がないというのは gitattributes の文書で確認した内容であり、リポジトリでコマンドを実行して試したわけではない
  • シェバン失敗後の挙動 — 先頭行の失敗のあと残りがそのまま実行されたのは MSYS2 の bash 5.2.37 で観察した結果である。Linux ディストリビューションのシェルや別のカーネルで同じフォールバックが起きるかは確認できなかった
