备份面板显示绿色，多数团队就把这一天的活儿算完了。作业以退出码 0 结束，文件按预期大小落进了存储，通知也到了。可这盏绿灯真正证明的命题只有一个：转储程序完成了它自己的工作。

「能恢复」是另一个命题。要有一个空数据库接住它，架构要在里面立起来，数据要穿过约束进去，序列、权限和扩展要各就各位，排序规则要与索引的前提相符，最后应用要在这之上起来。这条链子上没有任何一环是备份作业检查过的。

两个命题之间的距离，在事故发生之前没人去量。而量它的办法只有一个，就是真的做一次恢复。麻烦在于，「做过恢复测试」这句话要成立，条件比看上去苛刻。本文把这些条件拆成层来排。

本文出现的每个选项和默认值都带版本。PostgreSQL 指 18（文档中为 18.6），MySQL 指 8.4。同名选项在不同引擎家族和不同版本之间行为不一致是常事，因此按自己环境的版本重新对一遍更稳妥。凭记忆写下的选项，通常已经落后两代。

缘起 - 「验证到真实恢复」实际覆盖多大范围

促成这个角度的，是一款自托管备份工具把「验证到真实恢复」摆在了最前面。碰上这类说法，该看的地方是固定的：恢复完成之后比对了什么。

该项目 README 记录的流程是这样：每次备份结束后，或者按小时、天、周、月乃至 cron 表达式定义的周期，启动一个数据库容器，在里面跑一次恢复，把恢复后的体积与备份比对，然后产出一份列出每张表及其行数的报告。还可以选择只推送失败告警。

这句宣传不算夸大。它没有停在文件完整性检查，而是真的跑了恢复。但这份验证抵达的位置是恢复完成了，并且给出了每张表的行数。应用能否在其上起来是更高一层的问题，而下文会看到，有好几类缺陷能原封不动地通过行数比对。本文要谈的正是那一层。

退出码 0 观测到什么，又没观测到什么

逻辑备份也就是转储，是向服务端发查询、把结果写成 SQL 语句的过程。直接搬用 MySQL 8.4 的分类：逻辑备份在服务端运行的状态下进行，并且不包含日志文件、配置文件以及其他不属于数据库的相关文件。至于哪些东西没被包含，转储文件里任何地方都没有记录。

当备份作业报告成功时，真正被观测到的信号大约三个：进程退出码、输出文件大小、传输是否完成。没有被观测到的是下面这些。

  • 转储内容是否代表某一个时间点上一致的状态
  • 架构与数据是否彼此对得上
  • 目标环境是否具备接住这份转储的前提条件
  • 打开这个文件所需的密钥是否还活在别处
  • 恢复所需的时间是否落在能承受的范围里

这五项有一个共同点：在备份时刻它们的取值都无法确定，只有到恢复时刻才被定下来。备份流水线上的那盏绿灯，在原理上没有办法替代这五项中的任何一项。

成功的备份说谎的六个地方

1. 转储进行期间架构发生变更

MySQL 提供 --single-transaction，让 InnoDB 表可以不加表锁地在线转储。但文档附了条件：转储进行期间，其他连接不应使用 ALTER TABLE、CREATE TABLE、DROP TABLE、RENAME TABLE、TRUNCATE TABLE，因为一致性读并不与这些语句隔离。若这类语句落在正被转储的表上，读取可能取到错误内容，或者干脆失败。

值得盯住的是「失败」的反面。取到错误内容并不是失败。转储正常结束，文件是语法有效的 SQL，日后恢复也不会报错，出错的只有内容。在架构迁移的发布时间与夜间备份窗口重叠的组织里，这个条件不是理论。

PostgreSQL 这边情况不同。pg_dump 即使在并发使用中也能产出一致的导出，按文档的措辞，转储代表pg_dump 开始运行那一刻的数据库快照。这不等于别处没有同类风险，而是两个家族的失效方式不同，也正因如此，一份为两者共用的公司流程往往对其中一方是错的。

2. 只有架构，或者只有数据

用 --schema-only 取的转储恢复之后，所有表都在，行数是 0，不报任何错。反过来，用 --data-only 取的转储灌进空目标会因为没有表接住而失败，灌进已有架构的目标则会在约束和装载顺序上部分失败。

PostgreSQL 文档明确写着大对象被视为数据：--data-only 会包含，--schema-only 不会。在把架构转储和数据转储分开取、事后再拼起来的运维方式里，两个文件的时刻一旦错开，落在这段间隙里的行两边都不存在。而这种缺失在恢复日志里不留下任何痕迹。

3. 默认不会被带走的东西

在 mysqldump 里，--triggers 默认开启，所以转储表时会带上这张表的触发器。相比之下 --routines 与 --events 默认关闭，必须显式指定才会被带走。存储过程、存储函数和事件调度器条目都落在这一侧。

这个默认值造成的缺陷形态很特别：它在恢复阶段完全不露面。表都在，行数也对得上。缺的是夜间汇总事件和存储过程，而它们要等到各自的执行时刻到了，缺席才会被人知道。能通过行数比对的缺陷，第一个例子就出现在这里，后面还会反复出现。

4. 活在数据库之外的东西

pg_dump 只转储一个数据库。角色和表空间这类横跨整个集群的对象不在其中，那一侧归 pg_dumpall 管。往没有角色的目标里恢复，设置属主的语句就会卡住。pg_restore 默认会发出 ALTER OWNER 或 SET SESSION AUTHORIZATION，而按文档所述，除非首个连接由超级用户、或者由拥有全部对象的那个用户建立，否则这些语句会失败。

扩展的性质也一样。转储带走的是「创建这个扩展」的指令，而不是扩展的实现。目标主机上没装对应的包，恢复就停在那里。序列则相反，属于安静的一侧：值确实会跟着走，但在只单独装载数据的做法里，序列会带着落后的位置被恢复，而这个事实要等到下一次插入撞上主键冲突时才被知道。

5. 字符集与排序规则 - 不会随数据一起搬走的东西

转储默认以源数据库的字符集生成。搬走的是字节和它的字符集声明，而不是目标服务端的配置。因此创建目标数据库时选什么字符集，本身就是恢复的一部分；而这个选择通常写在目标准备脚本而非恢复脚本里，归属也就变得模糊。

排序规则安静得多。PostgreSQL 在创建排序规则对象时把提供方的版本记进系统目录，每次使用时与当前版本比对，不一致就发警告。文档的解释很直白：排序规则定义一旦变化，可能导致索引损坏以及其他问题，因为数据库依赖已存储对象具有某种确定的排序顺序。

而且这件事不只在异常路径上发生。文档举出的正常情形，是把操作系统升级到新的主版本，以及用 pg_upgrade 升级到链接了更新 ICU 的服务端二进制。恢复目标主机与原机跑着不同发行版，在灾难恢复里不是例外，反而更接近默认。

上面还叠着一个陷阱。消掉警告的 ALTER COLLATION ... REFRESH VERSION 只更新目录里记录的版本。文档钉死了一句话：该命令并不会真的检查所有受影响的对象是否已被正确重建。消警告和修索引是两件事，顺序上 REINDEX 在前。

6. 密钥与介质 - 文件在，却读不了

加密备份的解密密钥若只存在于与备份源相同的系统上，那么摧毁这套系统的事故会把备份一并带走。这个缺陷在备份阶段绝对看不见，因为加密是成功的。它现身的时刻是恢复尝试的头一分钟，这反而算好的一类，因为它立刻暴露。

介质损坏则相反。PostgreSQL 给每个数据页带上校验和，写入时更新、读取时校验，从 18 起这项保护默认开启。但保护范围文档写得很清楚：只有数据页受保护，内部数据结构与临时文件不在其中。再说，这讲的是一个活着的集群，而不是在对象存储里躺了半年的转储文件。那一侧要靠存储层提供的完整性机制，加上针对备份产物本身的清单。

恢复工具的默认行为是「继续」

表里倒数第二行是最常被漏掉的地方。在主要的恢复路径上，出错时的默认处理是继续而不是停下。

pg_restore 中 --exit-on-error 的说明把这个默认值原样写了出来：默认是继续执行，并在恢复结束时显示错误计数。「显示」这个动作，只有在有人盯着屏幕时才成立。如果调度器只读退出状态，那么出了 40 个错的恢复和一个错都没有的恢复，送达的是同一个信号。

用 psql 装载纯文本转储也一样。按文档的措辞，默认情况下 psql 脚本在遇到 SQL 错误之后会继续执行；设置 ON_ERROR_STOP 变量则会在出错时以退出码 3 退出。而文档随后补的那句话才是结论：无论哪种方式，你拿到的都只是一个部分恢复的数据库。区别只在于你是否知道这件事。

单事务恢复适合用于验证，理由就在第二行：要么全部成功、要么什么都不落盘，判定因此变成二值。验证性恢复的目的不是救数据，而是取得一个真或假。

还有一个与格式相关的陷阱。pg_restore 无法恢复纯文本格式的转储，归档必须是自定义、目录或 tar 格式之一。把验证流程按 pg_restore 来设计、备份却实际以纯文本产出的组合，可能在验证一次都没跑过的状态下持续很久。

恢复验证真正要求什么

隔离的目标，以及不依赖原库的资源

「做过恢复测试」要成立，恢复目标必须与原库分离。分离到只是换个数据库名是不够的。若共用同一个服务进程、同一块磁盘、同一套凭据、同一条网络路径，那么这场验证正靠着原库还活着这件事撑着。为原库消失而准备的流程如果依赖原库，那它就不是准备。

PostgreSQL 文档给恢复目标附的条件也属同类：如果集群对 template1 有过本地追加，就必须恢复到一个真正为空的数据库，为此要以 template0 为模板来创建。目标不干净，成功与失败就会混在一起，而混在一起的结果给不出判定。

每次起一个新容器来做恢复之所以成为通行做法，原因就在于初始状态永远相同。不过容器只是隔离的一个轴。若这个容器与原库处在同一台主机、同一套存储、同一个云账号之上，隔离就停在进程层面。资源隔离要做到什么程度，应当按所要防备的事故规模来定。

比对什么

行数便宜又好用。但如前所述，有若干缺陷能通过行数比对：存储例程缺失、事件缺失、序列落后、排序顺序错位，全都属于此类。

校验和高一个层次，但附带条件。MySQL 的 CHECKSUM TABLE 正是为了确认备份或回滚前后内容是否一致而设的语句。文档给它附了两条限定：其值依赖表的行格式，行格式一变校验和也跟着变；而且哈希函数并不保证无碰撞，两张并不相同的表在原理上可能给出同一个值。文档甚至举了例子：时间类型的存储格式曾在某个版本边界发生变化，升级后的表校验和可能因此改变。

结论很清楚：在跨版本进行的验证性恢复里，校验和不一致未必是损坏的证据。只有在两侧运行同一版本时它才成为信号。因此比对最好按层来搭。

  • 第 1 层，对象数量 — 表、索引、序列、扩展、例程、事件、触发器。因默认值而整类丢失的东西在这里被抓住。
  • 第 2 层，分表行数 — 抓部分装载和被中断的恢复。足够便宜，每次恢复都跑。
  • 第 3 层，核心表的聚合值 — 求和、最大值、最近时间戳。行数一致而内容有偏差的情况在这一层暴露。
  • 第 4 层，应用真正会发出的几条查询 — 要挑带连接和排序的，否则索引与排序规则的问题永远不会现身。

分层是因为成本不同。第 1、2 层便宜到可以每次恢复都跑，第 4 层不是。把什么放在哪一层，直接接上下一节的自动化边界。

文件能打开，与服务能活着

把这条边界写得最清楚的，是 PostgreSQL 自家备份校验工具的文档。pg_verifybackup 把 pg_basebackup 取得的备份，与服务端在备份时生成的清单比对，检查其完整性。而文档紧接着写道：该工具执行的校验并不包含、也不可能包含运行中的服务端在真正使用这份备份时会做的全部检查。即便使用了这个工具，仍应执行测试恢复，确认得到的数据库按预期工作、并且看起来包含正确的数据。

同一页还把限度写得更细：这种程度的校验足以发现文件缺失或内部校验和不匹配之类的明显问题，但不足以发现恢复时可能出现的每一种问题。它举的例子是校验和正确、却指定了毫无意义动作的日志记录。形式正确而含义错误，正是任何校验器的盲区。

再往前一步，连测试恢复也不是最后一层。数据库起来和服务起来之间，还横着架构迁移的版本、应用期待的扩展、连接账号的权限、放在外部存储里的附件、以及只存在于缓存中的会话。一份从未穿过这一层的恢复计划，会在真实事故中抵达那一层之后才遇上新问题。可恢复性是设计的产物而非事后努力这个论点，此前已在设备固件那一侧梳理过，数据库也没有不同。

把目标定成数字 - RPO 与 RTO

没有这两个数，备份设计无从开始，因为判断哪个周期够用、需要多快的恢复速度都缺少依据。被引用得最多的定义来自 NIST SP 800-34 Rev. 1。

术语定义决定什么若未确定
RPO，恢复点目标故障之后数据必须被恢复到的时间点备份周期与写入日志的保留方式周期之争沦为技术口味之争
RTO，恢复时间目标系统组件在对组织使命或业务流程产生负面影响之前可以停留在恢复阶段的总时长备份的格式与恢复路径的结构恢复花上几天也不算违反任何规格

RPO 是 24 小时，夜间转储就够。RPO 是 5 分钟，转储够不着，必须有东西持续外送写入日志：PostgreSQL 这边是 WAL，MySQL 这边是二进制日志。MySQL 8.4 默认开启二进制日志，而时间点恢复的素材是在全量备份之后生成的那批二进制日志文件。如果习惯在备份结束后清理日志来腾磁盘，RPO 就只剩下纸面上的数字。把二进制日志当作可回退历史来用的思路，已在讨论可回退数据时光机的文章里单独整理过。

RTO 决定备份的格式，逻辑备份的代价在这里浮出来。MySQL 文档对 mysqldump 的自我描述是它并非为备份大量数据而设计的快速或可扩展方案，并补充说数据量大时恢复可能非常慢。理由也写在旁边：重放 SQL 语句这件事伴随着插入和建索引所需的磁盘 I/O。

这里有个常见的误判：用转储文件的大小去估 RTO，几乎总是偏乐观。取转储的时间和灌回去的时间并不对称，而这个不对称的幅度由索引结构决定。恢复时间只能靠测量得知，不能靠估算。

最后，这两个数没定下来会发生什么，和数字本身同样重要。「备份周期定几小时」是一场永远得不出结论的技术争论。换成「这个服务能承受丢多少分钟的订单」，能拍板的人就确定了。这两个值不是工程参数，而是业务同意承受的损失规模，所以它们不属于基础设施工程师一个人能定的那类数字。这种性质在小团队如何守住 Postgres 里也出现在同一个位置。

3-2-1 是标准还是惯例

3-2-1 常被称作规则或标准：三份副本、两种介质、一份异地。顺着出处追下去，通向的不是标准文档，而是摄影师彼得·克罗格在《The DAM Book》（O 社出版）中整理出的经验法则。它被广泛引用、大体也站得住，但并不是标准化组织作为要求条款发布的规定。叫惯例比叫规则更准确。

标准那一侧真正要求的句子形状不同。NIST 网络安全框架 2.0 的子类别 PR.DS-11 写的是：数据的备份被创建、保护、维护和测试。随附的实现示例包含以下条目。

  • 对关键数据进行近实时的持续备份，其他数据按约定的日程频繁备份
  • 对所有类型的数据源，至少每年测试一次备份与恢复
  • 把部分备份安全地保存在离线且异地的位置，使事故或灾害不会损坏它们
  • 对备份存储实施地理分离与地理位置限制

读下来会发现，测试和隔离排在副本数量之前。一个把 3-2-1 执行得完美却一次都没恢复过的组织，和一个只有两份副本但每季度做一次恢复演练的组织，哪一个能在真实事故中活下来是显而易见的。副本好数，所以审计先数它；测试难数，所以往后拖。这个顺序是反的。

补一句，异地这个条目也常被读得太窄。要点不只是物理距离，而是信任边界是否不同。同一个云账号下的另一个区域在地理上是分开的，但一套凭据就能把两边一起抹掉。把保管交给别人时如何不丢掉访问权本身，已在归档访问权与厂商锁定那一侧从合同角度梳理过。

自动化的边界 - 每次做的与偶尔做的

在恢复验证里，区分能自动化与不能自动化的标准只有一个：基准值在哪里。

条目执行者频度基准值所在
恢复是否无错完成机器每次备份退出状态，单事务判定
对象数量是否与上次一致机器每次备份上一次成功恢复的取值
分表行数是否落在预期区间机器每次备份源库同一时刻的聚合
应用是否启动并响应健康检查机器每周至少一次健康检查端点
恢复耗时的趋势机器测量，人判定每次记录，每季度评审测量自动，阈值来自 RTO
全量恢复演练人每季度或每半年业务定下的 RTO 与 RPO
手册的时效性人每次架构变更当前配置与文档之间的差
负责人不在时的流程人每半年组织架构与授权规定
保留期限与合规要求的一致性人每年合同与法规

机器侧条目的共同点，是基准值在数据内部。它们能在没有人判断的情况下分出真假，分出来的结果还能转成告警。人侧条目的共同点，是基准值在组织内部。恢复演练耗时 40 分钟这个事实本身既不真也不假，只有当业务判定这 40 分钟是否落在 RTO 之内，它才产生意义。

处在边界上的是表里第五行。恢复耗时的趋势由机器测量，但这条趋势何时变得危险由人来定。数据变大，恢复时间必然跟着变长，而变长的时间越过 RTO 的那一天不会带任何告警到来。每次都记录恢复耗时之所以便宜，理由在此；这些记录之所以容易堆着没人看，理由也在此。收集了却无人阅读的数据，与收集来的观测数据为何没人读里谈的是同一个形状。

硬要把机器代替不了的东西自动化，也是常见的尝试。校验器能判定与不能判定的一般界线，已在校验框架划下的那条线那边整理好。要旨相同：机器守住下限，上限由人来定。

自托管的代价 - 那个工具的备份由谁来做

自己把备份工具立起来，就多出一个问题：那个工具的状态由谁来备份。

备份工具握着日程、连接信息、保留策略、存储凭据、加密密钥，以及执行历史。丢掉这份状态，即便备份文件一个不少，恢复流程也少了一半。尤其当「哪个文件对应哪个时点的哪个数据库」「用哪把密钥打开」这些映射只存在于那个工具内部时，更是如此。

循环依赖就是在这里生成的。工具把自己的状态备份进自己的存储，而那套存储凭据又只存在于工具内部，这就画成了一个圆。事故当中，圆上任何一点断掉，整体就停住。切开它的办法并不特别。

  • 把工具配置以人可读的格式导出到工具之外，纳入配置管理。以代码形式管理，即便重新立一套工具也能复现同一状态。
  • 把解密密钥放在与备份产物不同的信任边界里。同一个存储桶、同一个账号、同一个容器之内，一次事故就会把两者一起带走。
  • 把「工具不在时如何打开一个备份文件」的流程写进文档，并且真的走一遍。能在没有 Web 界面的情况下恢复，这个工具才不再是单点故障。
  • 让备份清单在工具之外也能读到。存储侧的文件命名规则加上清单文件就能担起这个角色。

这份代价不构成放弃自托管的理由。用托管服务并不会让问题消失，只是把它转移给了供应商，同时换来合同与访问权这另一层的问题。无论走哪条路，圆在哪里被切开，得由自己心里有数。把部署平台放到自己服务器上会消掉哪些成本、又会新增哪些成本，已在讨论自托管部署平台的文章里以同样的方式拆开过。

只靠只读命令能确认的事

以下全部属于只读与检查一类，没有放入会修改或删除目标的命令。主机、账号、模式名都是占位符，替换成各自的取值即可。

不做恢复，只看归档目录

# 归档目录。不执行恢复，只列出里面有什么。
pg_restore --list /PATH/TO/backup.dump

# 把物理备份与服务端生成的清单做比对。
pg_verifybackup /PATH/TO/basebackup

# 只查询页校验和是否已启用。
psql -h HOST -U USER -d DBNAME -c 'SHOW data_checksums'

数一数恢复库里到底来了什么

-- 按模式统计表数量。先抓整类丢失的东西。
SELECT table_schema, count(*) AS tables
  FROM information_schema.tables
 WHERE table_schema NOT IN ('pg_catalog', 'information_schema')
 GROUP BY 1 ORDER BY 1;

-- 转储里只带了创建扩展的指令。看它在目标主机上是否真的立住了。
SELECT extname, extversion FROM pg_extension ORDER BY 1;

-- 序列带着落后的位置被恢复，下一次插入就会撞上主键冲突。
SELECT schemaname, sequencename, last_value
  FROM pg_sequences ORDER BY 1, 2;

找出排序规则版本已经对不上的对象

-- PostgreSQL 文档中给出的查询，仅把比较运算符写成了 !=。
SELECT pg_describe_object(refclassid, refobjid, refobjsubid) AS collation_name,
       pg_describe_object(classid, objid, objsubid)          AS object_name
  FROM pg_depend d
  JOIN pg_collation c
    ON refclassid = 'pg_collation'::regclass AND refobjid = c.oid
 WHERE c.collversion != pg_collation_actual_version(c.oid)
 ORDER BY 1, 2;

数一数 MySQL 这边被默认值落下的东西

-- 触发器默认会带，例程和事件不会。源库与恢复库各数一遍。
SELECT routine_type, count(*) AS n
  FROM information_schema.routines
 WHERE routine_schema = 'APPDB' GROUP BY routine_type;

SELECT count(*) AS events   FROM information_schema.events
 WHERE event_schema   = 'APPDB';
SELECT count(*) AS triggers FROM information_schema.triggers
 WHERE trigger_schema = 'APPDB';

-- 内容指纹。取值依赖行格式与版本，所以只在同版本之间比较。
CHECKSUM TABLE APPDB.ORDERS;

最后那条语句虽属只读，却不是免费的。在大表上它会整表扫描，因此不是营业时段对着源库跑的东西。对着恢复库跑才是正确形态，而这也正是隔离目标在上一节先行出现的原因。

未能确认的部分

  • 促成本文的那款工具，其恢复验证在体积与分表行数之外还比对什么，超出 README 的描述范围之后未能确认。它是否检查约束、索引、例程的存在，能否挂上应用层检查，这里不作断言。
  • 同一仓库的 GitHub 说明只称它为 PostgreSQL 工具，README 却列出四个引擎家族。哪一个反映当下的意图，未能确认。
  • mysql 客户端在读取脚本时遇到 SQL 错误的默认行为未能敲定。选项文档把继续执行选项写作「即使发生 SQL 错误也继续」，却没有显式陈述默认值。可以反推，但无法凭文档句子确定。
  • 没有找到把 3-2-1 作为要求条款发布的标准或政府文件。常被引用的出处是一本书，而 NIST CSF 2.0 的 PR.DS-11 要求的是创建、保护、维护与测试，不是副本数量。
  • MariaDB 与 MongoDB 家族的转储默认值未被纳入本文依据，只使用了 PostgreSQL 18 与 MySQL 8.4 的官方文档。
  • 无法给出恢复耗时的通用数值。它受数据规模、硬件、索引结构左右，RTO 的判断只能依据各自环境的实测。
