Reuse Less Software - The Supply Chain Security Paradox of Code Reuse

Why cheaper reuse makes supply chain risk more expensive

June 13, 2026 Tech & IT

Reuse used to be a virtue - until some point

Software engineering stood for half a century on a single belief. Don't write the same code twice (DRY). Don't rebuild what someone has already built. The principle was right. Rewriting sorting algorithms, date parsing, HTTP clients, and JSON serialization every time was a waste and a breeding ground for bugs. Package managers - npm, PyPI, Cargo, Maven - industrialized this virtue. A single npm install pulls code vetted by thousands into your project. Productivity exploded.

Then the hada.io topic posted on June 12, 2026 - topic 16, ReuseLessSoftware - asked the opposite question. Shouldn't we reuse less software? As distribution costs converge to zero and code generation gets automated, the dependency graph has ballooned out of control, and with it supply chain security concerns. The core paradox is this: the very infrastructure that made reuse cheap also became the channel through which an attacker can poison millions of downstream projects at once.

This article does not merely translate the short hada.io prompt. It re-examines the two faces of code reuse from an accounting standpoint, dissects the structure of the attack surface created by npm and PyPI dependency explosion, and lays out real supply chain attacks - xz, event-stream, Shai-Hulud - in fact-first terms. It then unpacks what "reuse less" actually means - the trade-offs of dependency minimization, vendoring, and self-implementation - and presents a practical defense line of SBOM, lockfile, auditing, and minimal dependencies. Finally it offers concrete decision rules for balancing productivity and security.

The accounting of code reuse - asset or liability?

The debate begins with a simple shift in perception. Every dependency is a liability, not a free asset. The moment you add a dependency you gain a productivity benefit immediately, but you also book a permanent liability: tracking security patches, handling breaking changes, license obligations, and the heaviest item of all - outsourced trust.

Traditional accounting only counted the benefit. "This library saves me two weeks." But the liability ledger was empty. The probability that those two saved weeks would, five years later, halt the entire company through one supply chain breach; the probability that the library's maintainer would one day burn out, hand off the project, and a new maintainer would inject malicious code; the probability that somewhere in the transitive tree a critical CVSS 9.0+ vulnerability would erupt - these were all liabilities, but nobody recorded them.

The ReuseLessSoftware view is to reopen that liability ledger. Every time you add a dependency, ask: "what am I outsourcing with this one line?" Accepting outsourced trust for a one-line utility is accounting nonsense. Accepting it for OpenSSL or a well-maintained core framework is rational. The difference is the size of the benefit against the size of the liability.

Dependency explosion - how npm and PyPI lost control

The core problem of modern package ecosystems is not the absolute number of dependencies but the invisible explosion of transitive dependencies. A developer might directly choose five dependencies. But follow what each of those five pulls in, and what those pull in, and the graph balloons into the hundreds.

Reports indicate that the overwhelming majority of real security threats in the npm ecosystem come from indirect dependencies the developer never installed. Five direct dependencies are visible and reviewed; the 500+ transitive ones beneath them effectively are not. Attackers target precisely this blind spot. Compromising a small, unwatched transitive dependency that a popular package quietly pulls in is far more efficient than attacking the popular package directly.

The pressure of scale matters too. Reports indicate that in 2025 alone more than three million releases were added to major package ecosystems, and in some repositories a substantial share of vulnerable releases scored CVSS 9.0 or above. No human can review updates flooding in at that rate. Automated dependency-update tools relieve the burden while creating a new risk: code entering without review.

Anatomy of the attack surface - typosquatting, dependency confusion, malicious packages

The attack surface created by dependency explosion breaks into a few patterned techniques. Each is shockingly cheap to attempt.

1) Typosquatting

Publishing a malicious package one letter off from a popular one. Put lod4sh next to lodash, request next to requests, and wait for the typo. The cost is essentially zero, and one tired developer or one automated install script is enough.

2) Dependency confusion

Publishing the name of a company's internal private package to the public registry with a higher version number. If the build system checks the public registry first, the attacker's package installs instead of the internal one. In 2021 this technique was proven to work against many large companies.

3) Malicious packages and account takeover

The most direct attack. Either build a new package malicious from the start, or seize the maintainer account of an existing popular package through phishing or credential theft and publish a malicious version. Many of the attacks that hit the npm ecosystem in 2025 targeted packages sharing one profile: single maintainer, dormant account, high downloads but low scrutiny.

The common thread is clear. The more dependencies you have, and the less each one is reviewed, the higher the odds an attack succeeds. The attack surface is roughly proportional to the dependency count. That is why "reuse less" is not a minimalist aesthetic but a quantitative security strategy.

Case study 1: event-stream (2018) - the transfer of trust

The textbook supply chain case is the event-stream incident of November 2018. event-stream was a popular npm package downloaded nearly eight million times a month at the time. The original maintainer, dominictarr, had lost interest, and when a new person named right9ctrl offered "I'll help maintain it," he handed over publishing rights.

The new maintainer soon added a malicious transitive dependency named flatmap-stream. The code was carefully targeted to activate only in the build environment of a specific Bitcoin wallet app, attempting to steal private keys. It shipped millions of times over about two and a half months before being caught.

The lesson of event-stream is social, not technical. The trust model of open source rests on trust in an individual maintainer. The moment that individual burns out and hands the project to a stranger, the millions of downstream projects that trusted them suddenly trust the newcomer unconditionally - with no code review and no identity verification.

Case study 2: the xz backdoor (2024) - the most sophisticated near-miss

The xz Utils backdoor, tracked as CVE-2024-3094, raised the sophistication of supply chain attacks to a new level. xz Utils is a core compression library included in nearly every Linux distribution.

Reports indicate that an unidentified contributor known as "Jia Tan" began contributing to the xz project in late 2021 and methodically built the trust of the original author, Lasse Collin, over roughly two to three years. Along the way, social engineering involving pressure emails reportedly nudged the original author into granting co-maintainer rights. In February 2024 the attacker shipped version 5.6.0, which contained a backdoor that injected obfuscated object code into liblzma through an M4 macro in the build system. Under specific conditions it enabled unauthorized remote access and arbitrary payload execution via SSH.

Just before this could spread broadly across the world's Linux servers, in March 2024 a Microsoft engineer, Andres Freund, found his SSH logins slightly slower than usual, investigated, and stumbled on the backdoor. It was almost pure luck.

The shock of xz is twofold. First, a trusted maintainer can be the attacker. This was not an external intrusion but a backdoor planted from the inside through a normal contribution process. Second, its discovery was nearly accidental. Not an automated tool, not a scheduled audit, but one individual's curiosity saved global infrastructure. That reveals how fragile current defenses are.

Case study 3: the Shai-Hulud worm (2025) - the age of self-replication

The Shai-Hulud worm, disclosed in September 2025, opened a new chapter: the automation of supply chain attacks. Where earlier attacks poisoned one package at a time by hand, Shai-Hulud was a worm that replicated and spread on its own.

Reports indicate the attack began with a phishing campaign impersonating npm that lured maintainers into "updating" their MFA settings, harvesting their credentials. Once it held a maintainer's credentials, the malware automatically identified other packages that developer owned, injected malicious code, and published new versions. Because no further human intervention was needed, the infection spread exponentially. In the first wave alone more than 500 packages were poisoned, including @ctrl/tinycolor.

The attack kept evolving. Reports indicate a "Shai-Hulud 2.0" wave that began around November 2025 was far wider in scope, affecting tens of thousands of GitHub repositories and slipping malicious code into packages from major organizations such as Zapier, ENS, PostHog, and Postman. The U.S. CISA issued a dedicated alert.

The lesson of Shai-Hulud is clear. Once an attack propagates automatically, human manual response cannot keep up. The arc from event-stream through xz to Shai-Hulud shows supply chain attacks evolving from manual to sophisticated to automated. And this evolution will likely accelerate as code generation and distribution automation accelerate.

What "reuse less" means - decision-making, not minimalism

So what, concretely, does "reuse less" tell you to do? It is not the extreme of rejecting every library and building everything yourself - that invites a different risk (the "roll your own crypto" problem). The core is deliberately computing the trade-off for every dependency.

Dependency minimization

The most direct method. Before adding a new dependency, ask: "do I really need this, can the standard library or an existing dependency solve it?" One-line utility functions in particular (the lesson of the old left-pad incident) are almost always better implemented directly. Remember that every node in the dependency graph is a potential attack surface, so cutting unnecessary nodes is itself a security gain.

Vendoring

Instead of pulling a dependency through the package manager every time, copy the source of a specific vetted version directly into the project repository. The Go ecosystem embraced this for a while. The upside is that runtime dependence on external registries disappears and you can review exactly what came in via git diff. The downside is that updates become manual and the repository grows. It works especially well for core dependencies that rarely change.

The trade-off of self-implementation

Self-implementation removes supply chain risk but creates self-bug risk. Subtle domains like cryptography, authentication, and parsers should not be built by hand; use vetted libraries (this looks like the exact opposite of the principle covered in The "Don't Roll Your Own" Principle 2026 - Why Web UI Should Stop Replacing Browser-Native Features, but the two are two sides of the same coin). The rule is simple: when domain complexity and security sensitivity are high, choose a vetted library; when they are low, choose self-implementation or vendoring.

Defense line 1: lockfiles and build reproducibility

The first line of defense is pinning exactly what came in. Lockfiles like package-lock.json, pnpm-lock.yaml, and Cargo.lock record the exact dependency tree - including transitive ones - with versions, integrity hashes, and download locations.

The core value of a lockfile is build reproducibility. Commit the lockfile and install in CI with a command that strictly follows it, such as npm ci, and you can guarantee that yesterday's build and today's build are composed of exactly the same code. If an integrity hash does not match, the install fails - so you can detect attacks where a package is quietly swapped in the registry. Not committing the lockfile, or ignoring it in CI, is tearing down this defense line yourself.

Defense line 2: SBOM and dependency visibility

An SBOM (Software Bill of Materials) is a list of every component included in a build. It makes the dependency graph - transitive ones included - visible, so you can answer the question "what exactly is inside my build?"

The practical value of an SBOM shows up when an incident hits. When a breach like xz is disclosed, an organization with SBOMs can query "which of our builds contains this vulnerable version?" within minutes. Without one, the same question takes days, and exposure continues throughout. Best practice is to generate an SBOM on every build in CI/CD and, at minimum, regenerate it when dependencies change, before releases, after security patches, and during audits. npm has shipped npm sbom since v9, and other ecosystems can generate them with tools like Syft, cdxgen, and Trivy. There is an active debate over whether a lockfile is essentially an SBOM already.

Defense line 3: auditing, review gates, and least privilege

After visibility comes active verification. Embed the following four into the CI pipeline and team process.

  • Automated dependency auditing: integrate npm audit or tools like Socket.dev and Snyk into CI to block dependencies with known vulnerabilities from being merged.
  • New-dependency review gate: require that any PR adding a new dependency have a human check the maintainer count, recent activity, scrutiny relative to downloads, and number of transitive dependencies. The combination of single maintainer + dormant account + high privilege is a warning sign.
  • Provenance and signature verification: use metadata such as npm provenance that proves where and how a package was built, and where possible trust only signed packages.
  • Least privilege and isolation: minimize the privileges that dependency install scripts can hold in the build environment, and merge automated updates only after verifying them in an isolated environment. postinstall scripts that run at install time deserve special caution.

None of these is complete alone. The lockfile pins what came in, the SBOM makes it visible, and auditing verifies it. Only when the three layers work together does the dependency graph become something you can control.

How developers strike the balance - five decision rules

Productivity and security are not zero-sum. These five rules help you deliberately strike the balance between them.

  1. Account for dependencies as liabilities. Before adding one, ask "what am I outsourcing with this line, and how big is the liability?" Don't only see the benefit; book the liability too.
  2. Implement one-liners yourself. Pulling in transitive dependencies for a trivial utility is an accounting loss. Remember the left-pad lesson.
  3. Use vetted libraries for core, sensitive domains. Don't build crypto, auth, or parsers yourself - but manage those vetted dependencies rigorously with lockfiles, SBOMs, and audits.
  4. Automate visibility. Committing lockfiles, CI auditing, and SBOM generation work forever once set up. Defenses that don't depend on human willpower are the strongest.
  5. Verify updates before merging. Accept the convenience of automated updates, but reject unreviewed auto-merges. Manually review the first update from a package whose maintainer has changed.

The shared spirit of these rules matches the heart of ReuseLessSoftware: returning reuse from an unconditional virtue to a conscious choice. The era when reusing more was always right is over. Now you must decide, each time, what to reuse, how much, and through which verification.

Conclusion and three things you can do now

The core in one sentence: the infrastructure that enabled code reuse simultaneously became the channel for supply chain attacks, and this paradox is solved only by reusing less but more consciously. The transfer of trust in event-stream, the near-successful insider backdoor in xz, and the self-replicating worm of Shai-Hulud all send the same message. The dependency count is the attack surface, and unreviewed dependencies are the most dangerous.

Three things you can do now.

  1. Check your lockfile commit and CI audit today. In 30 minutes, verify the lockfile is committed and CI runs npm ci and npm audit. If they're missing, fill them in this week.
  2. Print your dependency tree once. Count how many transitive dependencies sit beneath your direct ones. That number is your attack surface and the starting point for finding candidates to cut.
  3. Add a review gate to your next new-dependency PR. Put a one-line checklist - maintainer count, activity, transitive count - into the PR template. Once it sticks, every future dependency passes through review.
