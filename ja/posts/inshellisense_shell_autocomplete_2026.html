inshellisense - ターミナルにIDE風自動補完を持ち込むマイクロソフトのオープンソース

600以上のCLIスペックで8つのシェルを束ねる自動補完 - bash-completion・fzfと何が違うのか

2026年7月5日 開発・インフラ

はじめに: なぜターミナルはIDEより一世代遅れていたのか

ターミナルでコマンドを一つ打つだけでも、ダッシュの後にどんなオプションが来るのか、このサブコマンドが引数をいくつ取るのか思い出せず、何度も--helpに戻った経験は誰にでもあるはずだ。統合開発環境(IDE)ではこの問題はとうに解決済みだ。関数名を数文字打つだけでシグネチャと説明が出るIntelliSense系の自動補完のおかげである。ところが一日に何度も開くターミナルシェルは、この体験から一世代取り残されていた。

2026年7月時点でも活発にコミットが続くマイクロソフトのオープンソースプロジェクトinshellisenseは、まさにこの溝を埋めようとするツールだ。名前どおり、シェル(shell)の中にIntelliSenseを持ち込むという意味である。GeekNewsでも紹介され11ポイントを獲得したこのプロジェクトは、話題性だけを見れば大きくはないが、ターミナル自動補完という古い課題をどのようなアプローチで解いているのかを分解してみる価値がある。本稿は発表資料をなぞる代わりに、実際のGitHubリポジトリ・API経由で自ら確認した数値・公開されている技術資料をもとに、inshellisenseが何をどう動かしているのか、そしてbash-completionやfzfのような既存ツールと何が違うのかを筆者自身の視点で分析する。

1. inshellisenseとは何か - マイクロソフト版IDE風自動補完

1.1 何をするツールなのか

inshellisenseはマイクロソフトが2023年10月にGitHubで公開したオープンソースプロジェクトで、ターミナルシェルにIDEスタイルの自動補完を追加する。TypeScriptで書かれており(全コードの87%以上)、MITライセンスで配布されている。筆者がGitHub APIで直接確認したところ、2026年7月時点でスター10,073、フォーク224を記録しており、直近のコミットも本稿執筆の数日前と、今なお着実に保守が続いている。インストールはnpm install -g @microsoft/inshellisenseの一行、またはHomebrew(brew tap microsoft/inshellisense && brew install inshellisense)で完了し、シェルでisコマンドを打てば自動補完が有効なセッションが始まる。

1.2 8つの対応シェルとクロスプラットフォーム

対応範囲の広さがこのプロジェクトの実質的な強みだ。bash・zsh・fishといったUnix系シェルはもちろん、PowerShell Core(pwsh)とWindows PowerShell、実験的にcmdまで、さらに比較的知名度の低いxonsh・nushellまで合計8つのシェルをサポートする。Windows・Linux・macOSをすべて包含するクロスプラットフォームツールということだ。特にPowerShell・cmdへの対応は、後述するこのプロジェクトの系譜を理解するうえで重要な手がかりになる。

1.3 設定とカスタマイズ

設定はホームディレクトリの.inshellisenserc、またはXDG準拠の~/.config/inshellisense/rc.tomlという一つのファイルで管理される。候補を確定するキー(既定はTab)、次/前の候補への移動(矢印キー)、キャンセル(Escape)といったキーバインドを変更でき、useAliasesオプションでbash・zshのエイリアスまで認識させたり、useNerdFontでNerd Fontアイコンを有効にしたり、maxSuggestionsで一度に表示する候補数を制限したりできる。設定スキーマがJSON Schemaとして公開されており、エディタの補完を受けながら設定ファイル自体を書けるという配慮も行き届いている。

2. どう動作するのか - PTYラッパーとカスタムOSCプロトコル

2.1 シェルにパッチを当てずに包み込む方式

inshellisenseの興味深い点は、何を見せるかよりもどう作り出しているかにある。このツールはbashやzshといったシェル自体にパッチを当てたりフォークしたりしない。代わりにnode-ptyライブラリを使ってユーザーの実際のシェルプロセスを疑似端末(pseudo-terminal, PTY)の中でそのまま実行し、その上に薄いラッパーとして乗る。ユーザーの目には普段どおりのシェルに見えるが、実際にはinshellisenseが入出力を中継し、必要な瞬間に自動補完UIを重ねる構造になっている。

2.2 プロンプトの状態を追うカスタムOSC

問題は、ラッパーが今プロンプトが始まったのか、ユーザーがコマンドを実行したのか、カレントディレクトリはどこかを、シェルごとに異なる文法を解析せずに知る必要があるという点だ。inshellisenseは各シェル用に配布するシェル統合スクリプトが、プロンプト開始(OSC 6973;PS)・コマンド送信(OSC 6973;PE)・カレントディレクトリ(OSC 6973;CWD)といったカスタムOSC(オペレーティングシステムコマンド)エスケープシーケンスを送出する方式でこれを解決する。性質の異なる8つのシェルを一つのコードベースで支えられるのは、シェル固有の文法を直接解析する代わりに、この薄く共通した信号規約に頼っているからだ。

2.3 スペック駆動の提案エンジン - withfig/autocomplete 600以上

実際の補完候補は、ユーザーが入力している間に内部のSuggestionManagerがスペックベースのランタイムに問い合わせて得ている。このランタイムが参照しているのが、Figが元々作ったオープンソースのスペックライブラリ@withfig/autocompleteだ。inshellisenseのpackage.jsonはこのパッケージをバージョン2.675.0に明示的に固定しており、このバージョン番号自体が、このスペックライブラリがこれまでどれほど密に更新されてきたかを物語っている。ここに収められた600以上のCLI定義のおかげで、git・npm・docker・kubernetesといったツールのサブコマンド・オプション・引数の型に説明まで添えて、コマンドラインのすぐ下にANSIエスケープでインライン表示できる。

3. 既存のシェル自動補完と何が違うのか - bash-completion・zshとの比較

bash-completionやzshのcompinit・compdef、fishの内蔵completionsディレクトリは、実は昔からある解決策だ。ただしこれらは根本的に、シェルごと・ツールごとに補完スクリプトを個別に書いて配布する必要がある構造だ。あるツールはbash用の補完スクリプトはよくできているのにzshやfish用は貧弱だったり存在しなかったりすることが珍しくなく、あったとしても結果はたいていオプション名だけを並べた素っ気ない一覧にとどまる。

inshellisenseはこの断片化を別の方法で回避する。シェルごとに個別の補完スクリプトを書く代わりに、gitでもdockerでも一つの共有スペック(withfig形式)さえあれば、対応する8つのシェルすべてで同じ補完結果を出す。しかもスペックにはオプションの説明や、引数がファイルパスなのかブランチ名なのかといった型情報まで含まれており、候補の横に短い説明を添えるIDE風の表示が可能になる。

ツール役割補完候補の生成対応シェルの範囲説明・型メタデータ
bash-completion / zsh compinitシェル内蔵の補完システムシェルごと・ツールごとの補完スクリプトシェルごとに個別スクリプトが必要基本的になし(オプション名のみ)
fzf(-tab)候補を絞り込むあいまい検索なし - 既存の補完結果を再利用シェルの既存補完システムに依存既存システムのまま

4. fzfとはどう違うのか - 競合ではなく補完

fzfはこの議論でしばしば一緒に語られるが、正確には別の層のツールだ。fzf自体は汎用のあいまい検索ツールであり、fzf-tabのようにシェル補完にfzfを接ぎ木するプラグインは、自ら補完候補を生成しない。代わりにシェルの既存の補完システム(前述のbash-completionのようなもの)がすでに作り出した候補リストを受け取り、その中から欲しい項目を素早く絞り込めるよう手助けする役割を担う。

一方inshellisenseはそれ自体が補完エンジンだ。何を候補として見せるか自体をwithfigのスペックを参照して決め、トリガーキーを押さなくても入力と同時にインラインで表示する。fzfはすでにある候補をより見つけやすくする検索レイヤーであり、inshellisenseはそもそもどんな候補がどんな説明とともに存在するのかを定義する生成レイヤーだ。だから両者は代替関係というより、別の課題を解く道具同士に近い。

5. 生産性と学習曲線 - 実際に何がよくなるのか

この構造が実務にもたらす利点は明確だ。gitだけでもサブコマンドとオプションが数十に及び、docker・kubectl・ghのようによく使うCLIも事情は似ている。毎回--helpを漁ったりman pageを検索したりする代わりに、入力した瞬間にオプション名と短い説明が目の前に出れば、認知負荷は確実に下がる。これは熟練者にも助けになるが、特にCLIツールを学び始めたばかりの人にとって学習曲線を緩やかにする効果が大きい。Tabで確定し矢印で移動する操作自体は既存のシェル補完と大きく変わらないため、手に馴染んだ習慣を捨てる必要もない。

ただしこの利点はスペックが存在するツールに限られるという点もはっきりさせておくべきだ。社内だけで使う独自CLIや、まだwithfigのスペックが作られていない新しいツールであれば、inshellisenseも特段の助けにはならず、シェル標準の補完に戻ることになる。

6. 系譜をさかのぼると - Figの終焉とスペックの second life

6.1 Figとは何だったのか

inshellisenseが依存する@withfig/autocompleteスペック形式は、実はマイクロソフトが最初に作ったものではない。元祖は2020年頃に登場したmacOS(後にLinuxベータ)向けのネイティブなターミナル自動補完アプリ、Figである。Figは自前のスペック形式と600以上のCLI定義をオープンソース(withfig/autocomplete、MITライセンス)として公開しコミュニティの貢献を募っており、筆者がAPIで確認したところ、このリポジトリは現在もスター25,190、フォーク5,455を保持している。

6.2 アマゾンによる買収、sunset、そしてWindowsという空白

Figチームは2023年8月にアマゾンへ合流し、その年の11月には早くもアマゾンのCodeWhisperer(現Amazon Q Developer)にコマンドライン向け機能を移植した。その後2024年9月1日、Figアプリ自体は完全にサービスを終了(sunset)し、ユーザーにはAmazon Q Developerへの移行が案内された。興味深いのは、マイクロソフトのinshellisenseがこのsunsetよりも前の2023年10月にすでにリポジトリを公開していたという点だ。つまりinshellisenseはFigが潰れて急ごしらえで出てきた代替品ではなく、Figのスペックライブラリがオープンソースとして独立していたからこそ、最初から別エンジンとして再利用できた事例に近い。ここにマイクロソフトが突いた明確な空白が一つある - Figはそもそも一度もWindowsをサポートしたことがなかった。inshellisenseがpwsh・PowerShell・cmdまで取り込んだのは、まさにFigのエコシステムが届かなかった場所を埋める選択として読める。

6.3 スペックライブラリの鮮度という注意点

ただし注意すべき点がある。筆者がGitHub APIで直接確認したところ、スペックの原本があるwithfig/autocompleteリポジトリの直近コミットは2025年5月で、inshellisense本体の直近コミット(2026年6月)より1年以上古い。Figアプリが消えたあと、スペックリポジトリへのコミュニティ貢献のペースが目に見えて落ちたと読める。inshellisenseはこのスペックを引き続き取り込んではいるものの、ごく最近登場したCLIツールの補完品質は、結局この上流リポジトリがどれだけ早く新しいスペックを受け入れるかにかかっているということでもある。

7. 限界と注意点

長所だけを並べるのは誠実ではない。第一に、az・gcloud・awsのように膨大なサブコマンドを持つCLIは、スペックファイル自体が大きくなりすぎるという理由で公式にはサポートされない。クラウドインフラを扱うユーザーにとっては惜しい欠落だ。第二に、2026年3月に出た最新安定版でさえバージョン番号は0.0.1のままだ。2023年10月からほぼ3年近く開発が続き、スターも1万を超えたにもかかわらず、プロジェクト自身は依然として1.0未満の実験段階と位置づけている。第三に、前述のとおり土台となるスペックリポジトリの更新ペースが落ちている。第四に、PTYでシェル全体を包み込む構造である以上、極端に遅いネットワークやリモートセッション、一部のターミナルマルチプレクサとの組み合わせで想定外のレンダリング上の問題が起きる余地も理論上は排除できない(これは筆者自身が再現検証したものではなく、アーキテクチャ上あり得るリスクとして受け止めるべきだ)。

結論: 今日試す価値はあるか

inshellisenseは華やかな新発明というより、すでに実証済みのアイデアであるFigのスペック駆動自動補完を、マイクロソフトがクロスプラットフォーム・オープンソースの形で組み直したツールに近い。その組み直しが意味を持つ理由は二つある。一つはFigがついに届かなかったWindowsシェルまで同じエンジンで取り込んだこと、もう一つはシェルごとに散らばっていた自動補完体験を一つのスペック・一つのエンジンに統一したことだ。

2026年7月時点で、このツールを今日試す価値があるかを判断する三つの基準を挙げておく。第一に、普段からgit・docker・kubectl・npmのようにオプションの多いCLIをよく使い、毎回--helpに戻る頻度が高いなら、npm install -g @microsoft/inshellisenseの一行ですぐに体感できる利点がある。第二に、az・gcloud・awsのようなクラウドCLIが主戦場なら、まずスペック未対応の問題から確認すべきだ。第三に、まだ0.0.1というバージョンであることと、スペックリポジトリの更新ペースを踏まえ、本番のワークフローに強く依存するよりは、まずローカルの開発環境で軽く試してみることを勧める。開発者向けツールのエコシステムにおいて、オープンソースのスペック資産が買収やサービス終了を越えて別のベンダーの手で second life を得るという今回の事例は、今後も繰り返されうるパターンとして見ておいてよいだろう。標準コネクタでツールをつなぐ流れに関心があれば、MCPサーバーで韓国の公共交通データをAIエージェントに接続したnaeryeoの分析も併せて参考にしてほしい。
