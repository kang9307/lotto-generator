这个扩展是干什么的 — 把外部数据带进 PostgreSQL

运营数据库是 PostgreSQL、分析用的原始数据以 Parquet 堆在 S3 里，这种架构很常见。连接两个世界的办法早就有好几种：装外部数据包装器（FDW），用单独的 ETL 任务把 CSV 拉下来再 COPY 进去，或者干脆另起一个分析引擎。每一种都在安装难度、格式支持和速度上付出不同的代价。

pg_chdb 是 ClickHouse 为这个位置给出的答案。核心思路是把嵌入式 ClickHouse 引擎 chDB 放进 PostgreSQL 进程里运行。读外部文件、解析、转换格式本来就是 ClickHouse 擅长的事，扩展只负责把结果流进 PostgreSQL 表的那个接缝。仓库的一句话描述是「执行 chDB 查询并把外部来源的数据复制到 PostgreSQL 表的 PostgreSQL 扩展」。

本文在 README 给出的范围内整理这个扩展的结构、覆盖范围、安装、性能数字与限制，最后对照现有选项判断它适合什么位置。许可为 Apache-2.0，截至2026年9月15日仓库有星标16个、提交84次、开放 issue 4个。先说明一点：这是一个早期项目，不是成熟项目。

两个部件 — chdb_query() 与 chdb_hook

扩展由两个部件组成，角色不同，分开看。

  • chdb_query() 函数。接收字符串形式的 ClickHouse SQL，用 chDB 引擎执行，把结果作为 PostgreSQL 的行集返回。可以直接使用 ClickHouse 的表函数（如 s3()），外部文件就成了表。返回列的类型由调用方用 AS (…) 声明。
  • chdb_hook 模块。用 LOAD 'chdb_hook' 加载后会拦截 COPY … FROM。在 FROM 后面写 S3 之类的外部 URL 而不是本地路径，钩子就用 chDB 读文件并导入表中。沿用现有的 COPY 语法，只把来源换成外部。
  • 两者的分工。只需要查询就用函数，需要永久导入表就用钩子。扩展还提供一条路径：只给文件 URL，就推断列结构，一次完成建表和导入。

设计上值得注意的是，扩展没有发明新的 SQL 语法，而是搭在函数调用和 COPY 这两个 PostgreSQL 既有语法之上。学习成本低，能直接放进现有的工具链（psql 脚本、调度器）。

覆盖范围 — 5类存储、14种格式、模式推断

维度README 给出的覆盖范围
存储S3、GCS、Azure Blob、HTTP URL、本地文件（5类）
格式TSV、CSV、JSON、BSON、Prometheus、Protobuf、Avro、Parquet、Arrow、XML、CapnProto、Markdown、MsgPack、ORC（14种）
模式给文件 URL 即可自动推断列结构、建表并填入数据
路径模式COPY 的 FROM 支持 {prefix1,prefix2}、{1..3} 这样的 glob 模式一次指定多个文件
许可Apache-2.0

格式列表之广是 chDB 的功劳而非扩展的功劳，它原样继承了 ClickHouse 支持的输入格式。反过来说，列表里的格式在映射到 PostgreSQL 类型的过程中会有什么损失，README 没有涉及。日期、时区、小数精度这些两个引擎类型体系不一致的地方，不实际导入一次是不知道的。

安装 — PostgreSQL 15、chDB 26.7、Linux 与 macOS

  • PostgreSQL 15 以上。14 及以下不在支持列表里。
  • chDB v26.7.0 以上。与扩展分开、先行安装。README 给的方法是 curl -sL https://lib.chdb.io | bash。这是把远程脚本通过管道直接执行的方式，生产服务器上更稳妥的做法是先下载脚本、看过内容再执行。
  • 仅 Linux 与 macOS。从源码构建安装，Windows 不在列表里。
  • 构建顺序。make → make installcheck → make install。使用 gmake 的系统或 pg_config 路径不同的环境，用 env PG_CONFIG=/path/to/pg_config make 的形式指定。

安装要求中实务上会卡住的是对 chDB 的依赖。它是嵌入式引擎，等于把 ClickHouse 运行时装进了 PostgreSQL 进程。内存占用与库冲突都不是 README 里的条目，是放进生产实例之前要在单独实例上先测的东西。

用法 — 直接查询与 COPY 导入

README 的第一个例子是用函数直接读 S3 上的 CSV。把 ClickHouse SQL 用美元引号（$$ … $$）包起来传入，并声明返回列。

SELECT * FROM chdb_query($$
                      SELECT * FROM s3('s3://bucket/file.csv')
                    $$) AS (id int, months int, days int);

第二个例子是加载钩子后用 COPY 一次导入多个文件。glob 模式把两个前缀与编号1到3组合，也就是一条语句指定六个文件。

LOAD 'chdb_hook';
                    COPY times FROM 's3://bucket/{prefix1,prefix2}/file_{1..3}.csv';

两个例子的差别就是用法的差别。第一个是不在 PostgreSQL 里留下结果的一次性查询，第二个是导入到表里。走模式推断路径时不必预先建表，但推断出的类型可能与预期不符，生产表还是先给出显式模式再导入更安全。

性能 — 100万行实测中比 pg_duckdb、pg_lake 快2到3倍

README 以 NYC 出租车数据约100万行为基准，比较了与竞争扩展的导入时间。原文给出的结果如下。

比较对象README 的表述
chdb_hook（pg_chdb）表现最为一致
pg_duckdb、pg_lakeCSV、JSON、Parquet 导入耗时2到3倍
aws_s3接近 chDB 的性能，但支持的格式少得多

读这些数字时要同时记住两点。第一，测量者是项目自己。厂商自测能告诉你方向，不保证幅度。第二，硬件、网络、文件大小、竞争扩展的版本这些条件 README 里都没有。100万行对分析负载来说偏小，到几十 GB 级别倍数是否保持，是另一个问题。

不过方向本身说得通。ClickHouse 的输入解析器为大批量读取列式格式优化了很多年，嵌入式执行又去掉了网络往返。「有理由快」和「这个倍数在我的环境里也会出现」是两句话，后者得用自己的数据去测。

限制 — 每条查询完全隔离

README 明确写出的已知限制只有一条：每条查询与其他所有查询完全隔离地运行。原文的说法是「不要建了表就指望在下一条查询里查到它」。

  • chDB 一侧的状态不保留。在 chdb_query() 里建的临时表、设置、视图，调用一结束就没了。分成多段的转换要么合并进一次调用的 SQL，要么把中间结果落到 PostgreSQL 表里再交给下一段。
  • PostgreSQL 一侧的状态正常。隔离针对的是 chDB 的执行。用 COPY 导入的表当然会留下。
  • 很可能是设计的结果。每次调用都从干净的引擎状态开始，并发调用之间没有干扰，资源回收也简单。对需要保持状态的负载不方便，但只要当作导入工具用就不是大问题。

该用在哪里、不该用在哪里

  • 合适 — 定期把多种格式的外部文件导入 PostgreSQL 的管道。Parquet、ORC、Avro 混着进来的数据湖，用一条 COPY 导入，这是这个扩展的本行。
  • 合适 — 没有余力单独运营分析引擎的团队。不用另建 ClickHouse 集群，在 PostgreSQL 里用 ClickHouse 的解析器。
  • 不合适 — 想在 chDB 里串起多段转换的负载。查询隔离导致中间状态留不下来。
  • 不合适 — Windows 服务器、PostgreSQL 14 及以下。在支持列表之外。
  • 不合适 — 不经验证直接上生产实例。这是星标16、提交84次的早期项目，嵌入式引擎的内存与稳定性不是 README 里的条目。先在单独实例上用自己的数据测。

未能证实的事项

  • 基准测试的硬件、网络、文件大小与竞争扩展的版本。README 里没有。
  • chDB 引擎在 PostgreSQL 进程内的内存上限，以及并发调用时的行为。
  • ClickHouse 类型到 PostgreSQL 类型的映射规则及是否有损失（时区、小数、嵌套结构）。
  • S3 凭证如何传递 — README 示例里没有认证部分。
  • pg_duckdb、pg_lake、aws_s3、FDW 的当前功能范围。在 README 的比较语境之外。
  • 项目的维护计划与发布节奏。
