Graphify Explained - Turning a Codebase Into a Queryable Knowledge Graph

A code knowledge graph beyond grep and vector RAG - AI context, onboarding, how it differs from GraphRAG, and the price of upkeep

2026-07-25 Dev & Infra

Introduction: AI Still Doesn't Know Your Codebase

There's a wall you hit repeatedly even while using AI coding assistants every day. The model handles a single file beautifully, but the relationships across the whole codebase - where this function is called, which module that config touches - have to be rediscovered from scratch every session. You grep for strings, shove whole files into context, pull similar chunks with vector RAG, and still the structure itself - what connects to what - stays empty. graphify, which I saw on GeekNews (news.hada.io), targets exactly that gap: the memory layer that has been missing from AI coding tools.

This piece isn't a feature list. It's a stress test of the idea that you can "turn a codebase into a knowledge graph." What graphify actually does, why grep and vector RAG fall short, how it differs inside the already-hot lineage of GraphRAG, RepoGraph, and CodeGraph, what a Korean team gains and must watch out for when adopting it, and above all whether the cost of building and maintaining the graph, plus inference accuracy, cancels out the value. My conclusion up front: graphify's direction is right, but it only pays off when treated as a verifiable auxiliary map, not a source of truth.

1. What Is graphify - A Local Skill That Turns Code Into a Graph

graphify is an open-source tool that converts not just a codebase but also docs, SQL schemas, config files, PDFs, images, and video into a single queryable knowledge graph. Install it with uv tool install or pipx, register the skill with graphify install, and inside 20+ tools - Claude Code, Cursor, Codex, Gemini CLI, plus GitHub Copilot, Aider, OpenCode, Factory Droid and others - a single /graphify . turns the current folder into a graph.

1.1 Code: No LLM, Local, Deterministic

The core design is that code is parsed locally with tree-sitter AST. No LLM is involved, and the code never leaves the machine. The repository says it supports 20-plus languages, including Python, TypeScript, Go, Rust, Java, and C++. Because it doesn't depend on LLM extraction, it guarantees determinism - the same input yields the same graph - and if you only handle code, it runs fully offline with no API key.

1.2 A Real Graph, Not Embeddings

The differentiator graphify emphasizes is that it is not a vector index. No embeddings, no vector store. It merges extracted nodes and edges into a NetworkX graph, applies the Leiden algorithm for meaningful communities, and finds answers by traversing the graph rather than by similarity search. That's what makes it possible to trace the path between A and B, or explain how a node connects to others - queries where the relationship itself is the answer.

1.3 Three Outputs and a Verification Tag

Running it produces three things: an interactive graph.html you explore in a browser, a graph.json you query programmatically, and a human-readable audit report, GRAPH_REPORT.md. Crucially, every edge carries a confidence tag. Connections explicit in the source are marked EXTRACTED; connections graphify inferred are marked INFERRED. graphify query runs a natural-language query, graphify path A B traces the path between two concepts, and graphify explain details a node's connections and confidence.

2. Why a Knowledge Graph - The Context and Token Problem

The reason tools like graphify keep appearing is simple: feeding an entire codebase to an AI is expensive and imprecise.

2.1 What grep and Vector RAG Miss

grep answers "where is this string" but stays silent on "why, and because of what, does this function tie into that module." Vector RAG pulls semantically similar chunks by similarity but can't reconstruct how those chunks connect. In situations where the answer is a relationship, not a paragraph - a policy referencing another policy, a bug propagating through a call chain across files - both hit a ceiling.

2.2 Token Efficiency - Don't Read the Whole Source

The graph's practical payoff shows up in tokens. Per an example in graphify's docs, on a 52-file corpus mixing code, papers, and images, one query costs about 123,000 tokens when reading the raw files versus about 1,700 tokens when querying the graph - roughly a 71x reduction. Instead of stuffing whole files into context on every query, you pass only a compressed, relationship-focused map. This figure is from one specific corpus and should be read as directional, but the principle of the saving is sound.

2.3 Verifiability - Separating Inference From Fact

In my view, graphify's most underrated strength is the EXTRACTED/INFERRED tag. Most AI search leaves users unable to tell whether a result was read directly from the source or plausibly made up by the model. graphify marks each connection as fact (EXTRACTED) or inference (INFERRED), exposing how far you can trust it and where a human must check. Leaving room to verify rather than blindly trusting a black box makes this a reliability design, not a UI ornament.

3. How It Differs From GraphRAG and Existing Code Search

graphify didn't appear from nowhere. The trend of strengthening search with knowledge graphs already has Microsoft's GraphRAG, the repository-level code graph RepoGraph, and tools like CodeGraph and Understand-Anything. You have to line them up to see where graphify actually sits.

3.1 What Differs From GraphRAG

The GraphRAG lineage that Microsoft sparked in 2024 mostly builds graphs by having an LLM extract entities and relationships from text. Powerful in expressiveness, but early on it was expensive enough that indexing large datasets reportedly ran into tens of thousands of dollars, and being LLM-driven, its output varied slightly each run. Later research cut the cost sharply, but the fundamental character remains. graphify sidesteps both by extracting deterministically via tree-sitter AST for code. For non-code assets (docs, PDFs, images), though, it still uses an LLM - so in that territory graphify inherits GraphRAG's cost and non-determinism.

3.3 Who Wins Where

My read: if code-structure understanding and verifiability are the priority and data must not leave, graphify leads. If the goal is semantic integration of a heterogeneous document pile, a mature GraphRAG stack may be better. For quick ad-hoc lookups, grep and vector RAG are still fast and enough. The three are less competitors than three tools answering different questions.

4. Practical Scenarios

Stripping away abstraction, here are three places graphify actually earns its keep.

4.1 Providing AI Context - A Complement to RAG

The most direct use is injecting compressed relationship context into an AI coding assistant. Instead of loading whole related files on every query, you extract just the relevant subgraph and pass it - saving tokens while still answering structural questions like "what does this change affect." Realistically it complements rather than replaces vector RAG, layering relationship information onto the chunks similarity found.

4.2 Onboarding and Code Comprehension

When a new teammate lands in unfamiliar legacy code, a graphify graph becomes a map of "where to start reading." Skim a core module's connections with graphify explain, trace the path between an entry point and core logic with graphify path, and you can shorten the days-long process of getting a feel for a codebase. GRAPH_REPORT.md itself is a first draft of human-readable onboarding docs.

4.3 Team Sharing via an MCP Server

graphify can expose the generated graph as an MCP server so an entire team shares it through one URL. This is where it grows from a personal tool into a shared team code knowledge base. From this point on, though, who owns keeping the graph fresh becomes an operational question.

5. An Adoption Lens for Teams With Strict Data Rules

From the standpoint of a development org with strict security requirements, graphify's strengths and traps carry different weight.

5.1 Data Residency and Air-Gapped Networks

In finance, public-sector, and security-heavy environments, the design where code never leaves the machine is a decisive advantage. Even where uploading source to an external LLM is outright banned, a code-only graph can be built inside an air-gapped network with no API key. For teams blocked from AI tooling over leak concerns, this is a real entry point.

5.2 Multimodal Calls an External LLM

Conversely, there's a trap you must flag. Code is local, but concept extraction from docs, PDFs, and images calls an external LLM backend like Gemini, Claude, or OpenAI. If you trust the "fully local" impression and casually drop internal design docs or screen captures into the graph, the code may not leave but those documents can. On adoption, draw a clear boundary between code-only and multimodal, and attach only approved backends to the latter.

6. Limits and Criticism - A Graph Has a Price

A right direction isn't free. graphify (and every code knowledge graph) comes with four real-world costs.

6.1 Upkeep - The Danger of a Stale Graph

This is the heaviest burden. Code changes daily, but a graph is a snapshot. Without regeneration or incremental updates, the graph goes stale, and feeding a stale graph as AI context produces the worse outcome of presenting wrong relationships as fact. That's why "self-updating" pipelines that wire graph refresh into CI keep appearing. The graph isn't a build-once asset; it's one you must keep feeding.

6.2 Accuracy - How Far to Trust INFERRED

EXTRACTED has source backing, but an edge marked INFERRED is graphify's interpretation and isn't always right. Tagging the distinction is honest, but if users don't actually check it and consume everything as fact, the verification mechanism is moot. The more convenient the automation, the easier it is to wave INFERRED through - and that has to be guarded against.

6.3 Visualization and Scale

The docs themselves note the graph.html interactive visualization struggles past 5000 nodes. It's excellent for small-to-medium repositories, but trying to view an entire giant monorepo as one graph is impractical. You need an operational strategy of scoping into partial graphs.

6.4 Determinism Applies Only to Code

graphify's determinism advantage is confined to the code that tree-sitter covers. The more multimodal input you add, the larger the LLM-extraction share grows, and the more graphify's own advantages - determinism, cost, privacy - get diluted. The choice of "what goes into the graph" effectively defines the tool's character.

7. A Pre-Adoption Checklist

Whether it's graphify or a similar code knowledge graph, check at least these four before adopting.

  • Refresh strategy - When and how will you rebuild the graph? Decide up front whether it's manual, CI-wired for auto-refresh, or supports incremental updates. A graph without refresh becomes debt.
  • Data boundary - Spell out the line between code-only (local) and multimodal (external LLM). Keep a list of which assets go to which backend.
  • Verification habit - Establish a team rule to confirm EXTRACTED backing for key decisions so INFERRED edges aren't consumed as fact.
  • Scale scope - If the target repository far exceeds 5000 nodes, plan up front to split the graph by module or service rather than the whole thing.

8. Conclusion - Three Things You Can Apply Today

graphify puts its finger on a real problem: the codebase relationship context missing from AI coding tools. Local, deterministic tree-sitter extraction, a real graph without embeddings, and EXTRACTED/INFERRED verification tags are clear strengths in this lineage. But the graph isn't build-and-done; it's an asset you must maintain and verify, and it only pays off when you accept that price.

8.1 Try Code-Only First

Build the graph first in code-only mode, where there's no leak concern, and measure real token savings and accuracy against your own repository for onboarding and AI context. Multimodal expansion comes after. Related: turning AI coding sessions' context into project memory covers the same problem.

8.2 Put Graph Refresh in the Pipeline

A stale graph is more dangerous than no graph. Whether manual regeneration or CI integration, build the refresh cadence into the design from the start. Treat the graph as a living asset, not a one-off document.

8.3 Don't Wave INFERRED Through

Verification tags matter only when you check them. Make it a team rule to handle inferred edges separately from fact on key decisions. For wider context, see local LLM agent development and our OmniRoute analysis.
