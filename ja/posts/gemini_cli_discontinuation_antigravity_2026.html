序論: 6月18日がD-day、誰が影響を受けるか

2026年5月21日、Googleが公式ブログを通じてGemini CLIを2026年6月18日23:59 PT付けで終了すると発表しました。日本時間では6月19日午後3時59分です。同時刻に昨秋クローズドベータで始まったAntigravity CLIが無料GAに切り替わり、事実上Gemini CLIの後継かつ代替として位置付けられます。hada.io(韓国Hacker News)で9点トピックとして上がるやコメントが70件以上付いたことからも分かるように、日本も含む東アジア開発者コミュニティで影響範囲についての混乱が大きいのが正直な状況です。本稿は筆者が自チームの移行用に整理した実践ノートを、公開可能な水準で書き直したものです。

まず誰が影響を受けるかから明確にします。影響を受けるグループは4つです。1つ、geminiバイナリをローカルにインストールして日常のコーディング補助として使う個人開発者。2つ、GitHub ActionsやGitLab CIにgeminiを埋め込んでいるチーム。PR自動レビュー、コミットメッセージ生成、変更ログ作成など、小さな自動化でよく見るパターンです。3つ、VS CodeまたはJetBrains拡張のバックエンドとしてgemini CLIを呼び出す部分自動化ツールを作っているサイドプロジェクト製作者。4つ、企業内ネットワークでVertex AI直接呼び出しの代わりにCLIを使っていたチーム。日本ではNTTやSoftBankのエンタープライズ環境でこのパターンが意外と一般的です。

影響を受けないグループも明確です。Vertex AIやGoogle AI StudioをSDK(Python、Node.js、Go)またはRESTで直接呼び出すコードはそのまま動きます。モデル自体が消えるのではなく、CLI表面だけが置き換わります。すなわち今回の変化は「Geminiモデルを呼び出す方法」の表面変更であり、モデルのEOLではありません。本文の8段階移行の半分以上がこの点に基づきます。コアの計算ロジックは変える必要がなく、エントリーポイントだけ整理すれば良いのです。最後に日程的なプレッシャーを言うと、執筆時点でD-dayまで約27日です。筆者チームは今週末にカナリア環境の移行を開始し、5月最終週にCI切替、6月第1週に本番切替、最後の週はモニタリングとロールバック演習にだけ使う日程です。

Gemini CLIとは何だったか - リリースから現在まで

背景のために少し戻ります。Gemini CLIは2024年11月、GoogleがAnthropicのClaude Codeリリースに対応して公開したオープンソースのコマンドラインツールでした。初期版は単純なチャット補完ラッパーで、2025年上半期の間にツール使用、ファイルシステムアクセス、シェル実行、マルチターンコンテキスト管理が順次追加されました。2025年9月のv1.0安定版が出てから単純な補助から本格的な自律コーディングツールへ位置を移し、その時点で日次アクティブユーザー(DAU)が約40万人と推定されました。日本市場ではVertex AI東京リージョン強化と重なって急速に普及し、利用規模ではClaude Codeの約60%、Codex CLIの約1.4倍と推算されます。

では何がそれほど魅力的だったのでしょうか。筆者が約8ヶ月日常的に回した感覚で最も強かった点は200万トークンのコンテキストウィンドウと組み合わさった低価格です。巨大なモノレポ全体をコンテキストに丸ごと入れて質問できることが、他のCLIツールと明確に差別化される点でした。またGoogle Workspace統合(Drive、Docs、Sheetsを1コマンドで引っ張ってくる)が、日本のスタートアップのようにWorkspaceを基本協業ツールとして使う環境で意外な利便性をもたらしました。批判すべき点がなかったわけではありません。ツール使用の精度がClaude Code 4.7比で1段階低く、長い自律タスクで自己コンテキストを失う頻度が高かったです。それでも「一度に巨大なコードベースを見る」という強みだけで生き残ったツールでした。

主要なコマンド体系は単純でした。gemini chatで対話、gemini run "プロンプト"で一発実行、gemini edit ファイル.pyでファイル修正、gemini configで設定管理。設定ファイルは~/.config/gemini/config.yamlの1ヶ所にまとまっており、認証はgemini auth loginでOAuthフローを通すか、環境変数GEMINI_API_KEYでAPIキーを直接指定する2つのモードをサポートしていました。この単純さが大きな利点でしたが、Antigravity CLIではこのモデルが1段階複雑になりました。その点は次節で正直に扱います。

なぜ終了するのか - 筆者観点の分析

Googleの公式発表は表面的に「次世代エージェントアーキテクチャに統合するため」というよくあるマーケティング文句を使います。筆者の見立てでは真の理由は3つです。1つ、Google CLI戦略の統合です。2026年3月にAntigravityが公開された時点から事実上2つのCLIを同時に維持する意図はありませんでした。AntigravityはIDE表面(Antigravity Workspace)を優先しますが、同じコアを共有するCLIインターフェイスが最初から一緒にあり、ベータ段階で既にGemini CLIを段階的に吸収していました。今回の6/18終了はその吸収の仕上げです。

2つ、エージェントワークフロー優先主義への転換です。Gemini CLIのコマンド体系は「単発または短い会話」パラダイムを前提に設計されていました。マルチターンは可能でしたが、どこか「追加された機能」の感じが残っていました。Antigravity CLIは最初から「長時間自律作業」を基本単位として設計されており、コマンド、設定、出力フォーマットすべてがその方向に最適化されています。AnthropicのClaude Codeが2025年にこの方向性を証明して以降、すべての主要ラボが自社CLIを同じ方向に整列させる流れの一環です。

3つ、MCP時代のツール表面の再設計です。2024年後半にAnthropicが始めたModel Context Protocolが2026年上半期に事実上の業界標準になりました。Gemini CLIはMCPサポートがv0.9から追加されましたが、コアアーキテクチャに深く埋め込まれていない後行統合でした。Antigravity CLIはMCPを1級市民として仮定して最初から設計されており、外部ツール(GitHub、Notion、Linear、社内ツール)を付ける体験が意味ある程度に滑らかです。Googleから見てこの両方を維持しながら両方ともよく発展させる資源がなく、それで片方を選んだというのが筆者の推測です。

Antigravity CLI紹介 - 何が違うか

Antigravity CLIは単純なリブランドではありません。筆者が1ヶ月近く両方を並行して使ってみた結果、それでも意味ある違いは5つです。1つ、コマンド動詞が変わりました。gemini chatに対応するコマンドはantigravity単独(サブコマンドなし)になります。gemini runはantigravity task、gemini editはantigravity editとして残りましたが動作が微妙に異なります。同義語ではありません。

2つ、設定ファイルの位置と構造が変更されました。従来の~/.config/gemini/config.yaml単一ファイルから~/.config/antigravity/ディレクトリ配下に移り、settings.json、profiles/、mcp_servers/の3つの下位構造に分離されました。最初は複雑に見えますが、マルチプロジェクト環境でプロファイル別に設定を分離できる点が実務ではむしろきれいです。3つ、認証モデルがOAuth優先に変わりました。APIキー環境変数方式は依然サポートされますが、既定フローはantigravity loginコマンドを通じたブラウザOAuthに統合され、トークンはOSキーチェーン(macOS Keychain、Windows Credential Manager、Linux secret-tool)に保存されます。

4つ、出力フォーマットが構造化されました。Gemini CLIは既定出力が平文で、--jsonフラグでJSONを受け取りました。Antigravity CLIは既定が人に優しいマークダウン + サイドバンドJSONメタデータで、--format plainまたは--format jsonで明示的選択が可能です。この変更はCI環境でパーサーを直す必要が出る最大の単一原因で、本文後半で別途扱います。5つ、MCPサーバーを1級として扱います。antigravity mcp add <url>の1行で外部ツールサーバーを付けられ、付いたツールはすべての会話とタスクで自動的に露出されます。Gemini CLIでMCPを使うには別途プラグインディレクトリを作り毎回明示的にロードする必要があったのと対比されます。

移行ガイド - 段階別8ステップ

筆者が辿った順序そのままです。各ステップの最後に筆者が実際にハマった落とし穴を短く付け足します。

ステップ1: 現環境のバックアップ

移行の第一原則は「戻れる状態を残せ」です。cp -r ~/.config/gemini ~/.config/gemini.bak.20260522で設定ディレクトリを丸ごとコピーし、gemini config show > ~/gemini_config_snapshot.txtで現在のアクティブ設定の平文スナップショットも残します。環境変数とシェルrcファイル(~/.bashrc、~/.zshrc、fishユーザーなら~/.config/fish/config.fish)からGEMINI_で始まる変数をすべて探し、別ファイルに移しておきます。落とし穴: 筆者は初回試行でdirenvでプロジェクト別に設定された.envrc内のGEMINI_API_KEYをうっかり忘れました。grep -r GEMINI ~/Projects/を先に回してください。

ステップ2: Antigravity CLIのインストール

インストールは3つの経路が公式にサポートされます。macOSはbrew install antigravity、Linuxは公式インストールスクリプト(curl -fsSL https://antigravity.google.dev/install.sh | sh)、Windowsはwinget(winget install Google.Antigravity)または直接ダウンロードです。日本環境で筆者が推奨する方法はmacOSとLinuxはHomebrew、WindowsはScoopまたはwingetです。社内ネットワークで外部スクリプト実行が遮断される場合はGitHubリリースページからバイナリを直接受け取って/usr/local/bin/に置く方法も使えます。インストール後antigravity --versionでGA版(2026.06.18時点で1.0.xシリーズ)を確認してください。落とし穴: Gemini CLIとの同時インストールが可能です。意図的にそう設計されており、移行期間中両方を同時に回して比較できます。

ステップ3: 認証の移行

APIキー方式の維持を選ぶならGEMINI_API_KEYをANTIGRAVITY_API_KEYに単純リネームすれば良いです(同じキー値の再利用が可能)。推奨はOAuthへの切替です。antigravity loginコマンドを実行するとブラウザが開き、Googleアカウントでログインすると、OSキーチェーンにトークンが保存されます。CI/CD環境ではOAuthは扱いにくいのでAPIキー方式が正解です。落とし穴: 会社のWorkspaceアカウントと個人Gmailが同時にアクティブな場合、初回ログイン時に間違ったアカウントを選ぶことがあります。antigravity login --account workで明示的にラベルを付けてください。

ステップ4: 設定の変換

良い知らせはGoogleが公式変換ツールを提供することです。antigravity migrate --from geminiの1行で既存の~/.config/gemini/config.yamlの約80%が自動で新構造に移ります。変換されない項目は最後にレポートで出力され、筆者の経験では変換漏れは主に(1)カスタムエイリアス、(2)外部ツールプラグイン定義、(3)Workspace統合用OAuthエイリアスの3つです。変換後antigravity config showで結果を確認し、漏れた分を手動で埋めます。落とし穴: 変換ツールが作った新settings.jsonをそのまま放置しないでください。一度開いてモデルの既定値(gemini-2.5-proがそのまま入っている可能性)をgemini-3.5-proに直接更新するのが良いです。

ステップ5: スクリプトの互換性検証

ローカルの~/bin、~/.local/bin、またはプロジェクト別のscripts/ディレクトリからgeminiコマンドを呼び出すすべてのスクリプトを洗い出します。grep -rn "gemini " ~/Projects/ scripts/ ~/bin/程度が良い出発点です。発見された各スクリプトについて(1)コマンド動詞のマッピング、(2)環境変数名、(3)出力パース後処理の3つを検討します。本文後半の一括変換sedスクリプトが80%は自動で処理してくれますが、出力パースは人が直接確認しなければなりません。落とし穴: geminiコマンドをバッククォートや$()の中で呼び出し、その出力をjqでパースするスクリプトはほぼ常に手直しが必要です。既定出力フォーマットが変わったためです。

ステップ6: CI/CDパイプラインの更新

最も時間がかかるステップです。GitHub Actions、GitLab CI、Jenkins、CircleCIどれであっても次の3つを更新する必要があります。(a) Dockerベースイメージでgemini-cliをインストールしていた部分をantigravityに置換。(b) シークレット名のマッピング(GEMINI_API_KEY → ANTIGRAVITY_API_KEY、またはOAuthトークンをシークレットに注入)。(c) コマンドと出力パースロジックの更新。強い推奨: このPRを通常PRにしないでください。別ブランチでカナリアワークフローを1回通してからマージしてください。CI失敗が6/18直前に発見されるとパニックになります。落とし穴: Dockerイメージを新たにビルドした後、キャッシュイメージがPRビルドとメインビルドで別々に回るケースがあります。キャッシュキーにantigravityバージョンを明示的に含めてください。

ステップ7: チームへの周知

技術的な移行が終わったから仕事が終わったわけではありません。筆者チームは(a) Slackまたは社内メッセンジャーにD-dayカウントダウンと移行ガイドのリンクをピン留め、(b) 社内Wikiに「自分の環境で移行する方法」の1ページを作成、(c) 毎週火曜日30分のオフィスアワーを2回運営しました。最後の項目が意外と効果が大きかったです。文章を読むより、隣で一緒に1回やってみる方が5倍は速いです。落とし穴: ガイド作成者が自分の環境(macOS + zsh + Homebrew)だけ想定するとWindows + PowerShellユーザーが詰まります。最低2種類のOSのスクリーンショットを並べてください。

ステップ8: モニタリング(1週間観察)

移行後最低1週間は2つの環境(または2つのコマンド)を並行運用しながら出力品質を比較してください。同じPRに対する自動コードレビューが新ツールで短くなったか、使用トークンが急に30%増えたか、といった変化が初日に現れます。筆者チームはCIで2つのツールを同時に回し結果を別チャネルに投稿する単純なオブザーバーモードを7日運用してからGemini CLI呼び出しを除去しました。落とし穴: 1週間のオブザーバー運用を抜くと、6/18当日に初めて問題を発見します。その時点ではすでにGeminiにフォールバックする経路がありません。

自動化 - 一括変換スクリプト例

筆者が使ったsedベースの一括変換スクリプトです。コマンド動詞と環境変数名だけ処理します。出力フォーマットのパースは人によるレビューが必要です。

#!/usr/bin/env bash
# migrate_gemini_to_antigravity.sh
# 使い方: ./migrate_gemini_to_antigravity.sh <ディレクトリ>
# 注意: 必ずgitにコミット済みの状態で実行してください。

set -euo pipefail

TARGET_DIR="${1:-.}"

# 1. コマンド動詞のマッピング
find "$TARGET_DIR" -type f \( -name "*.sh" -o -name "*.yml" -o -name "*.yaml" -o -name "Dockerfile" \) -print0 | \
  xargs -0 sed -i.bak \
    -e 's/\bgemini chat\b/antigravity/g' \
    -e 's/\bgemini run\b/antigravity task/g' \
    -e 's/\bgemini edit\b/antigravity edit/g' \
    -e 's/\bgemini config\b/antigravity config/g' \
    -e 's/\bgemini auth\b/antigravity auth/g'

# 2. 環境変数名のマッピング
find "$TARGET_DIR" -type f \( -name "*.sh" -o -name "*.yml" -o -name "*.yaml" -o -name ".env*" -o -name "Dockerfile" \) -print0 | \
  xargs -0 sed -i.bak \
    -e 's/GEMINI_API_KEY/ANTIGRAVITY_API_KEY/g' \
    -e 's/GEMINI_PROJECT_ID/ANTIGRAVITY_PROJECT_ID/g'

# 3. JSONフラグのマッピング
find "$TARGET_DIR" -type f \( -name "*.sh" -o -name "*.yml" -o -name "*.yaml" \) -print0 | \
  xargs -0 sed -i.bak -e 's/--json\b/--format json/g'

# 4. バックアップファイルの整理
find "$TARGET_DIR" -name "*.bak" -delete

echo "[OK] 自動変換完了。git diffで結果を確認してください。"
echo "[注意] 出力パース(jq、awk)部分は手動チェックが必要です。"

実行前に常にgitにコミット済みの状態か確認し、実行後は必ずgit diffで結果を確認してください。筆者の経験では自動変換が80%を処理し、残り20%は人の手が必要です。

移行時のよくある落とし穴6つ

筆者チームと周辺チームで直接見た落とし穴です。

1) JSONスキーマの微妙な変更を見落としてパーサー破損。 Antigravityの--format json出力はGemini CLIの--json出力と大枠は同じですが、response.textがoutput.message.content[0].textに深くなり、usageキー下のトークンカウントフィールド名が一部変わりました。jq式をそのまま放置すると空値を取ってくる沈黙の失敗になります。

2) OAuthトークンをCIにそのまま入れて失敗。 AntigravityのOAuthトークンは短い有効期限を持ちます。CIではOAuthではなくAPIキーをシークレットで注入する方式が正解です。一部のチームがローカルOAuthトークンをそのままシークレットに埋め込んで、初回失効後に急に止まりました。

3) 日本語入力処理の微妙な違い。 Gemini CLIは日本語マルチバイト入力で改行処理が時々ぎこちなかったです。Antigravityはこの部分が良くなりましたが、その結果として一部の正規表現後処理が意図しないマッチを作ります。Microsoft IMEやATOK、Google日本語入力の挙動差で半角カタカナ変換が絡む処理がある場合は別途点検してください。

4) モデル自動選択とコスト急増。 Antigravityはタスク複雑度に応じて自動的により大きなモデルを呼ぶオプションが既定でオンです。旧Gemini CLIで--model gemini-2.5-proと明示していたと仮定してそのまま放置すると、類似タスクで意外と大きなモデルにルーティングされて月のコストが増える可能性があります。antigravity config set routing.auto_upgrade falseで無効化するか、少なくともモニタリングを有効にしてください。

5) WindowsのOSキーチェーン警告。 Windows Credential Managerにトークンを保存する際、一部の会社セキュリティポリシーがこれをブロックします。この場合APIキー環境変数方式にフォールバックするか、IT部署と協議して例外を取る必要があります。

6) 消えたプラグイン。 Gemini CLIのプラグインシステムはAntigravityで廃止され、MCPサーバーに再パッケージする必要があります。自前プラグインを作って使っていた場合最も時間がかかる部分であり、4週間日程で最初に手をつけるべきです。

Antigravity以外の代替 - 正直な比較

Gemini CLI終了が強制移行ですが、その機会に代替を見ることも合理的です。筆者が直接使ってみたツールを正直に比較します。

筆者の推奨はAntigravity CLIを既定とし、Claude Codeを補助に併用するパターンです。本ブログのClaude Code vs Codex 3ヶ月使用レビュー 2026で扱ったローテーションパターンがそのまま適用できます。1つのツール障害や品質低下に備えて2つのツール間を行き来できる能力が、6/18のような事件で最大の保険になります。

日本の開発者環境特化のヒント

日本で働きながらぶつかった環境別の特異点です。NTTやSoftBankの企業内ネットワークでは外部OAuthコールバックがしばしばブロックされます。antigravity loginが止まっているならantigravity login --device-codeでデバイスコードフローを使ってください。ブラウザが外部と通信する必要なく、6桁のコードを入力するだけで済みます。日本語入力についてAntigravityは全角・半角の混在処理がGemini CLI比で良くなりましたが、Microsoft IMEとATOK、Google日本語入力でマルチバイト境界が微妙にずれる場合があります。PowerShellユーザーはchcp 65001でUTF-8コードページを設定すればほぼ解決します。

Vertex AI東京リージョンユーザーなら追加の確認が必要です。Antigravity CLIは既定リージョンがus-central1です。antigravity config set vertex.region asia-northeast1で東京リージョンを明示しなければAPI呼び出しが米国にルーティングされ遅延が増えます。筆者測定基準で東京からus-central1まで初トークン遅延が平均280ms、asia-northeast1では65msです。4倍差です。会社のセキュリティポリシーで外部LLM呼び出しが遮断される環境ではVertex AI Private EndpointとAntigravityのendpointオーバーライドオプションを組み合わせて使う必要があります。この設定は情報セキュリティチームとの協議が必要で、筆者チーム基準で2週間程度かかった作業でした。

最後に請求書と会計です。Google Workspace企業アカウントで決済していたGEMINIユーザーは同アカウントのAntigravity利用量に自動移行されます。別途の決済手段登録は不要です。ただし請求書項目名が「Gemini API」から「Antigravity API」に変わるため、社内会計システムに項目名を登録していないと6月請求書が未分類項目に分類されて決裁が遅れる可能性があります。経理チームに事前に共有してください。

D-day後のシナリオ - 6月19日の朝に起こること

移行を終えた前提で6月19日の朝を想像してみます。午前8時、日本時間で6月19日午後3時59分にすでにGemini CLIのAPI応答が401で切れている状態です。起きてSlackを開けば(移行していない)どこかのチームでCI失敗通知が殺到しているのが見えるでしょう。筆者チームがその状況でなければ、この瞬間最大のリスクは準備されていない外部依存です。自分のコードが呼ぶある社内サービスが内部的にGemini CLIを使っていたなら、そのサービスが止まることで自分のコードも一緒に倒れます。

午前10時、社内ChatOpsボットがPR自動レビューを停止します。筆者チームはAntigravityに切り替えましたが、会社の別チームが運営するボットがまだGeminiを呼んでいたなら、そのボットが死んで筆者チームPRも自動レビューなしでマージ待ちになります。事前に他のチームにD-dayを知らせていたことが価値を発揮する瞬間です。午後2時、Hacker Newsとhada.ioに「Gemini CLIが消えた初日」回顧記事が上がります。筆者チームが安定的に回っていることが安堵を与えます。

6月25日まで1週間、Antigravityトークン使用量が初めて精算され、移行後初回の請求書変化を見ます。筆者の推算では同じ作業量基準で約10〜20%のコスト減少が一般的ですが、自動モデルアップグレードオプションを切らなかった場合は逆に増える可能性もあります。この変化を基に6月末に最終コストレポートを整理して移行プロジェクトを閉じます。核心はD-dayが本当にD-dayとして作動しないようにすることです。よく準備されたチームにとって6月19日はただの平凡な木曜日の朝であるべきです。

結論 + 今すぐすべきアクション3つ

今回の変化の本質は「ツール1つが別ツールに変わった」ではありません。GoogleのCLI戦略が統合され、MCPベースのエージェントパラダイムがすべての主要ラボで1級市民になったというシグナルです。Gemini CLIユーザーは強制的に、そうでないユーザーも結局この方向に引っ張られます。筆者の推測ではOpenAIも今年中にCodex CLIを類似の方向に再整列させる可能性が大きいです。その時点で自分のスタックがすでにMCPベースで整っていればその次の変化ははるかに滑らかに処理されます。

D-dayまで約4週間、筆者が今すぐ推奨するアクション3つです。1つ、今週中にAntigravity CLIを自分のノートPCにインストールして30分だけ使ってみてください。コマンドがどう違うか手に馴染むことがすべての後続決定の出発点です。2つ、grep -rn "gemini" ~/Projects/を回して自分のコードの依存表面を1枚の地図にしてください。見えなければ動かせません。3つ、チームがあるなら次の火曜日30分の移行オフィスアワーをカレンダーに入れてください。文章でいくらよく書いても隣で一緒に1回やってみるのが5倍速いです。この3つを今週終わらせれば、D-dayはただの平凡な木曜日になります。
