Macでローカル LLM が遅い本当の理由 - GPU を使っているか確かめて有効にする方法

デバイスが認識されることと、実際に動いていることは別の問題だ

2026年8月4日 IT/技術

序論: Mac が遅いのではなく GPU が遊んでいる

MacBook でローカル LLM を動かしている。ファンは回り、バッテリーは溶けていくのに、トークンは一文字ずつしか降ってこない。この状態で次に取る手はたいてい決まっている。小さいモデルに替え、量子化をもっと強くかけ、それでも駄目なら「やはり Mac では無理か」で終わる。

ところがこの状態でアクティビティモニタを開き GPU 履歴ウインドウを出してみると、GPU 使用率がほぼ床のままという場面がよくある。Apple シリコンの GPU は遊んでいて、CPU コアだけが全部振り切れている図だ。モデルが大きいのではなく、計算が違うデバイスで動いている。

この状況はとくにパイプラインを自分で組み立てた場合に起きやすい。モデル読み込みのコードはどこかからコピーしてきたもので、そのコードは CUDA があれば GPU を使い、なければ CPU に落ちるように書かれている。Mac に CUDA はないので、条件分岐は何のエラーも出さずに CPU 経路を通る。失敗ではなく静かなフォールバックなので、ログには何も残らない。

この記事はその地点を扱う。いま GPU を使っているか確かめる手順、フレームワークごとに実際に存在するスイッチ、そして有効にしても速くならない五つのケースだ。ハードウェアを新しく選ぶ話はローカル LLM ハードウェア選択ガイドで、量子化フォーマットをどこまで詰めるかはローカル LLM 実行ガイド - ハードウェア要件と GGUF 量子化のトレードオフで扱ったので、ここでは繰り返さない。ここで扱うのはすでに手元にある Mac に GPU を使わせることだ。

ちなみにこの話題が再び注目されたきっかけは、ある個人のパイプライン最適化の記録がコミュニティに投稿されたことだった。一行の修正で実行時間が半分近くまで減ったという内容だが、その倍率をそのまま持ち込むことに意味はない。理由は後半でまとめて整理した。

1. 統合メモリ - Mac で「GPU に移す」の意味が違う理由

まず構造を正確に押さえると、その後の話が通る。NVIDIA のカードが載った PC で GPU を使うとは、データを VRAM にコピーすることを指す。システムメモリと VRAM は物理的に別のチップで、その間を行き来するコピーが費用になる。だから CUDA のコードは、どこに何があるかを常に気にしている。

Apple シリコンはここが違う。MLX のドキュメントが整理した表現どおり、CPU と GPU が同じメモリプールに直接アクセスする。配列はどこに置くかを指定する必要なく統合メモリにあり、代わりに演算のほうがどのデバイスで実行されるかを選ぶ。この違いが実務で生む結果は三つある。

  • コピーの費用がない。CPU の前処理と GPU の推論を混ぜても、その境界で転送が発生しない
  • モデルサイズの上限が VRAM ではなく本体メモリ全体で決まる。16GB のカード一枚では載らなかったモデルが、統合メモリ 64GB の機体には載る
  • 代わりに競合が生じる。ブラウザや IDE が食うメモリは、そのままモデルが使えないメモリだ。VRAM が分離しているときにはなかった問題である

PyTorch 側の用語でこのデバイスを呼ぶ名前が MPS だ。公式ドキュメントの説明は、機械学習の計算グラフとプリミティブを Metal Performance Shaders Graph フレームワークと Metal Performance Shaders が提供するチューニング済みカーネルにそれぞれマッピングする新しいデバイスを導入する、というものだ。要するにApple の GPU 計算スタックに PyTorch をつなぐバックエンドである。

ここでよく食い違う期待が一つある。統合メモリは「メモリを潤沢に使える」という意味であって「メモリ帯域が潤沢だ」という意味ではない。LLM のデコードはトークンごとに重みをなめるメモリ帯域律速の作業なので、同じ統合メモリ容量でもチップの等級によって毎秒トークン数が大きく開く。容量は載せられるかを決め、帯域はどれだけ速いかを決める。二つの軸を混ぜないこと。

2. フレームワーク別のスイッチ - PyTorch・llama.cpp・MLX

実際に存在するスイッチだけを整理する。フレームワークごとに既定値が違うという点が重要だ。有効にすべきものと、すでに有効になっているものがある。

スタックGPU の既定有効にする方法比較のため無効にする方法
PyTorchオフ。明示しなければ CPUデバイス文字列 "mps"device="cpu" に変えて同じコードを実行
llama.cppオン。macOS では Metal が既定で有効特に何もしなくてよい--device none
MLXGPU が既定の実行デバイス特に何もしなくてよい演算に stream=mx.cpu を指定

2.1 PyTorch - 移すものが二つある

PyTorch は明示しなければ CPU だ。だからコードでデバイスを直接指定する必要がある。

import torch

print(torch.backends.mps.is_available())  # いまこのマシンで使えるか
print(torch.backends.mps.is_built())      # インストールしたビルドに MPS が入っているか

device = "mps" if torch.backends.mps.is_available() else "cpu"
model = model.to(device)
inputs = inputs.to(device)   # ← ここを忘れる例が最も多い

最もよくある失敗が最後の行だ。モデルだけ移して入力テンソルを CPU に残すと、デバイス不一致のエラーが出るか、ライブラリが静かに合わせてくれる場合は毎ステップ転送が挟まる。確認関数を二つ使う理由もはっきりしている。is_available() が偽ならマシンか macOS のバージョンの問題、is_built() が偽ならインストールした PyTorch のビルドに MPS がない。後者は入れ直せば解決し、前者は入れ直しても絶対に解決しない。

動かないときに PyTorch が出す文言も、この二つをそのまま区別して教えてくれる。一つは 「MPS not available because the current PyTorch install was not built with MPS enabled.」 で、もう一つは 「MPS not available because the current macOS version is not 14.0+ and/or you do not have an MPS-enabled device on this machine.」 だ。メッセージを最後まで読めば、どちらなのかはすでに書いてある。

2.2 llama.cpp - すでに有効なので、切るほうを覚える

GGUF モデルを llama.cpp で動かす構成なら、スイッチを探す必要はない。公式のビルドドキュメントがmacOS では Metal が既定で有効になると明記している。ここで覚えるべきは逆方向、つまり比較対象を作るために切る方法だ。

# GPU レイヤー数を 0 に: GPU 推論は切れるが、一部の演算はなお GPU を使いうる
llama-cli -m model.gguf -ngl 0 -p "こんにちは"

# 完全に切る: GPU アクセラレーションをすべて無効化する
llama-cli -m model.gguf --device none -p "こんにちは"

二つのオプションの違いが重要だ。ドキュメントは -ngl 0 でも一部の計算は GPU で加速されうると書いている。だから「GPU なしでどれだけかかるか」を正直に測るには --device none を使う必要がある。これを知らずに -ngl 0 だけで比較すると、基準線がすでに GPU の助けを受けた値になるため、倍率が実際より小さく出る。

ビルド段階で外す方法もある。CMake に -DGGML_METAL=OFF を渡せば Metal なしでビルドされる。自分でビルドしたバイナリが遅いなら、このフラグがどこかに入っていないかを確認するのが先だ。

2.3 MLX - デバイスを移す代わりに演算に指定する

Apple が公開した MLX は統合メモリを前提に設計されているので、発想そのものが違う。配列を移す API はなく、演算に stream 引数で実行デバイスを指定する。

import mlx.core as mx

a = mx.random.normal((4096, 512))
b = mx.random.uniform(shape=(512,))

c = mx.add(a, b, stream=mx.gpu)   # GPU で
d = mx.add(a, b, stream=mx.cpu)   # 同じ配列を CPU で

同じ配列 a、b をコピーなしで両側から使う点が要点だ。依存関係があれば MLX のスケジューラがストリーム間に依存性を自動で挿入して順序を保証する。ドキュメントは、重い演算を GPU に、軽い演算を CPU に振り分けて並列に走らせる例でおよそ 2 倍が出た事例を示している。ただしこれはドキュメントの例題ワークロードで出た値であり、LLM 推論でそうだという意味ではない。

3. いま GPU を使っているか確かめる三つの手順

ここがこの記事の核心だ。三つの層を別々に確認する必要がある。一つだけ見ると必ず誤った結論にたどり着く。

3.1 第一 - デバイスが認識されるか

コードレベルの確認だ。先ほどの is_available() と is_built() を両方出力する。ここまではたいてい通る。そしてここを通ったからといって GPU を使っているわけではない。デバイスが存在することと、自分のコードがそのデバイスを使うことは別だ。

3.2 第二 - 実際に動いているか

システムレベルの確認だ。推論を走らせたまま、次のどちらかを見る。

  • アクティビティモニタを開き、上部メニューのウインドウ項目から GPU 履歴ウインドウを出す。推論が始まるときにグラフが上がるはずだ
  • ターミナルで sudo powermetrics --samplers gpu_power -i 1000 -n 5 を実行して GPU 関連の数値を見る。管理者権限が要る

判読の基準は単純だ。推論中なのに GPU のグラフが平らで CPU コアだけが埋まっているなら、デバイス確認を通っていても計算は CPU で動いている。逆に GPU のグラフは上がるが使用率が低く揺れるなら、次節の CPU フォールバックを疑う番だ。

3.3 第三 - メモリを確保しているか

PyTorch はこれを直接見られる関数を提供している。三つを一緒に出力すると状態が一目で分かる。

import torch

# テンソルが実際に占有している GPU メモリ(バイト)
print(torch.mps.current_allocated_memory())

# Metal ドライバがこのプロセスに割り当てた GPU メモリ総量(バイト)
print(torch.mps.driver_allocated_memory())

# 推奨される最大ワーキングセットサイズ(バイト)
print(torch.mps.recommended_max_memory())
  • current_allocated_memory() がゼロに近い → モデルが GPU に載っていない。デバイス指定を見直すこと
  • driver_allocated_memory() が recommended_max_memory() に近づいている → 次節のメモリ圧迫の領域だ
  • どちらも正常なのに遅い → デバイスの問題ではない。測定方法かワークロードの形を見ること

この三層を順に通すことが診断のすべてだ。「GPU を有効にしたのに速くならない」という質問の半分以上は、実は 3.2 の時点で引っかかっている。

4. 正しく測る方法 - 倍率を語る前に整えるべき条件

スイッチを入れたら、次はどれだけ速くなったかを測る番だ。ところがここで間違える例が、スイッチを入れられない例と同じくらい多い。とくに MPS は非同期なので、時計の位置を誤ると実際よりはるかに良い数字が出る。

4.1 同期なしで測るとカーネルの完了前に時計が止まる

torch.mps.synchronize() のドキュメント上の説明は、MPS デバイスのすべてのストリームにあるすべてのカーネルが完了するまで待つというものだ。この関数を使わないと、Python はカーネルをキューに入れた瞬間に次の行へ進み、時計は投入時間を測ることになる。

import torch, time

def timed(fn, warmup=1, runs=3):
    for _ in range(warmup):          # 初回実行のコストを捨てる
        fn()
    torch.mps.synchronize()

    times = []
    for _ in range(runs):
        torch.mps.synchronize()
        t0 = time.perf_counter()
        fn()
        torch.mps.synchronize()      # 完了まで待ってから止める
        times.append(time.perf_counter() - t0)

    times.sort()
    return times[len(times) // 2]    # 中央値

4.2 固定すべき条件

倍率を語るには、以下をすべて同じにしてデバイスだけを変える必要がある。一つでも揺れたら、その数字は何も証明しない。

  • 同じプロンプト、同じ最大生成トークン数。出力の長さが違えば時間が違うのは当たり前だ
  • 同じシード。PyTorch なら torch.mps.manual_seed() で固定する
  • ウォームアップを 1 回以上捨て、3 回以上の中央値をとる。平均ではなく中央値を使う理由は、バックグラウンド作業一回が平均を丸ごと壊すからだ
  • 電源状態を固定する。アダプタの接続有無と低電力モードを両方の測定で同一にする
  • バックグラウンドプロセスを整理する。会社支給機のセキュリティエージェントやバックアップデーモンが走っていた回は捨てる
  • プリフィルとデコードを分けて見る。最初のトークンまでの時間と、その後の毎秒トークン数はボトルネックが違う。合わせて一つの数字にすると何が改善したのか分からない

4.3 他人に数字を語るとき併記すべきもの

同じ理由で、どこかで見た倍率を引用するときも以下が併記されていなければその値は参考にならない。自分の結果を共有するときも同じだ。

  • チップの等級と GPU コア数、統合メモリ容量
  • モデル名とパラメータ規模、量子化の種類
  • コンテキスト長と実際に生成したトークン数、バッチサイズ
  • 比較対象が何か(CPU 実行なのか、-ngl 0 なのか、--device none なのか)
  • パイプライン全体の時間を語るなら、そのうち GPU に移せる区間が元は何パーセントだったか

最後の項目が決定的だ。全体 8 分のパイプラインで GPU 区間が元は 6 分だったなら半分に減らすことは可能だが、2 分だったならどれだけ頑張っても 2 分より下には行かない。倍率はスイッチではなく、そのパイプラインの構成が作る。

5. 有効にしても速くならない五つのケース

スイッチを正確に入れ、GPU のグラフも上がるのに体感が変わらない場合が残る。原因はたいていこの五つのどれかだ。

5.1 CPU フォールバック - 楽だが無料ではない

MPS がまだ実装していない演算に当たると PyTorch はエラーを出す。このとき使うのが PYTORCH_ENABLE_MPS_FALLBACK だ。ドキュメントの説明は、1 に設定すると MPS が対応していない演算を CPU にフォールバックさせるというものである。

export PYTORCH_ENABLE_MPS_FALLBACK=1
python app.py

これを入れればとりあえず動く。ところが動くことと速くなることは違う。フォールバックがかかった演算ごとに CPU と GPU を行き来する往復が生まれ、その演算がループの中にあれば倍率が丸ごと消える。だから順序はこう組むのが正しい。まずフォールバックを切って走らせ、どの演算が問題かの名前を確保してから、その演算を迂回できるかを見て、迂回が難しいときだけフォールバックを有効にしたまま運用する。最初から入れておくと、何が足を引っ張っているのか永遠に分からない。

この変数はプロセスの環境から読まれる。Python コードの中で os.environ により設定するなら import torch より前でなければならず、安全なのはシェルで export するほうだ。PyTorch のイシュートラッカーやフォーラムには、import の後に設定して何の効果もなかったという報告が繰り返し上がっている。

5.2 バッチ 1 という構造的な限界

GPU が CPU を大きく引き離す条件は、同じ演算を大量に並列処理するときだ。ところが対話的なローカル LLM はまさにその逆で、バッチ 1、短いプロンプト、一度に一トークン。デコード区間は計算量よりもメモリから重みを読み出す速度に縛られる。

そのため同じマシンでもプリフィル区間は大きく速くなり、デコード区間はあまり速くならないという非対称が生じる。長い文書を入れて短く答えさせる作業なら体感が大きく、短く尋ねて長く答えさせる作業なら体感が小さい。これは設定でひっくり返せるものではなく作業の性質だ。デコード自体を構造的に速くしようとするアプローチは投機的デコーディング側の手法で扱った。

6. 統合メモリ容量とモデルサイズ - まず算数でふるいにかける

「16GB の MacBook で何が動くのか」という問いには算数で答えられる。重みが占める容量はパラメータ数 × パラメータあたりのバイト数だ。16 ビットはパラメータあたり 2 バイト、8 ビットは 1 バイト、4 ビットは 0.5 バイトになる。

モデル規模16ビット8ビット4ビット快適に動かすなら
3B約 6GB約 3GB約 1.5GB8GB 以上
7〜8B約 16GB約 8GB約 4GB16GB
13〜14B約 28GB約 14GB約 7GB16GB は厳しい・24GB 推奨
30〜32B約 64GB約 32GB約 16GB32GB は厳しい・48GB 推奨
70B約 140GB約 70GB約 35GB64GB 以上

表の数字は重みだけを計算した算術値だ。実際にはここに三つが加わる。

  • OS と常駐アプリの取り分。macOS 自体、ブラウザ、エディタが常に数 GB を確保している
  • KV キャッシュ。コンテキスト長におおよそ比例して増える。長い文書を入れた瞬間にまずここで破綻する
  • 量子化の種類による余剰。4 ビット級の GGUF でも一部のテンソルはより高い精度で残すので、ファイルサイズが算術値より大きい。算術値ではなく実際のファイルサイズで計算すること

だから「32GB だから 32B の 4 ビットが 16GB、半分残る」は成り立たない。実際にそう載せるとその Mac で他の作業がほとんどできなくなる。表の最終列は「可能な最大」ではなく「他の作業をしながらでも使える線」と読むほうが正しい。量子化の段階ごとの品質低下をどこまで受け入れるかはGGUF 量子化トレードオフの整理を参考にするとよい。

統合メモリは後から増やせない。Apple シリコンのメモリは SoC パッケージに一緒に載っているため、購入後の増設が不可能だ。中古を含めて機体を選ぶとき、この項目だけは取り返しのつかない選択だという意味である。いまは 8B で十分だと判断して最小構成を選ぶと、一年後に 30B を動かしてみたくなったときに手がない。

チューニングのつまみエンジンのオプション中心 (-ngl、--device など)カーネル・コンパイラ水準まで開いている
中古市場での対応メモリ増設不可。機体交換が唯一の道カードだけ交換・追加できる

ここから出てくる実務的な結論が一つある。Mac は「大きいモデルをとにかく載せてみること」に強く、「載せたモデルを最大速度まで絞り出すこと」には弱い。統合メモリ 64GB の機体に 70B 級を載せることはカード一枚では真似できないが、載せた後の毎秒トークン数をカーネル水準で引き上げる余地は CUDA 生態系のほうがはるかに広い。この非対称を知っていれば、Mac で何をして何をしないかが整理される。

8. ローカルをやめて API に移る判断基準

スイッチをすべて入れて正しく測定した後でも、目標のレイテンシに届かない場合がある。そのとき同じ機体からさらに絞り出せる余地はたいてい大きくない。残る選択肢は三つだけで、それぞれ代償がはっきりしている。

  • モデルを小さくする → 品質を差し出す
  • 機体を変える → 費用を差し出す。しかも統合メモリは増設できないので丸ごと交換になる
  • API に移る → データが外に出て、呼び出しごとの費用がつく

どちらが正しいかは条件で分かれる。以下の基準ならローカルを維持するほうだ。

  • データが組織の外に出てはいけない。この条件では速度は交渉の対象ではない
  • 呼び出し頻度が高くプロンプトが短い反復作業だ。分類・タグ付け・抽出のようなもの
  • オフラインか、ネットワークが不安定な環境で動く必要がある
  • レイテンシは遅くてよいが予測可能でなければならない。外部 API の混雑時間帯の変動のほうが困る場合だ

逆に以下の基準ならAPI に渡すほうだ。

  • モデルの品質が成果物の価値を直接決める。最終原稿、顧客対応の文面のようなもの
  • 必要な規模が本体メモリを超える。32GB の機体で 70B が必要な状況
  • コンテキストが長い。KV キャッシュが統合メモリを食う構造なので、ローカルで最初に崩れる軸だ
  • 複数人が同時に使う。Mac 一台は同時リクエストに弱い

現実的な答えはたいてい二つを混ぜることだ。前処理・分類・一次要約はローカルで回し、最終生成だけ外に送れば、呼び出し数を減らしながら品質が必要な地点にだけ費用を使える。この構成でモデルをどう差し替えてルーティングするかはLLM ルーターで複数モデルを単一 API として扱う方式で扱い、ローカルモデルをエージェントとして回すときの別の制約はローカル LLM エージェント開発にツール検索と HITL が必要な理由に整理してある。

9. 日本語圏で Mac のローカル LLM を動かすとき

9.1 毎秒トークン数が同じでも体感速度は違う

速度の指標はほとんど毎秒トークンで表記されるが、同じ文がいくつのトークンに分かれるかは言語とトークナイザによって異なる。だから英語基準で発表された毎秒トークン数を日本語作業の体感にそのまま移すとずれる。自分が実際に入れる日本語の文が、自分のモデルのトークナイザで何トークンになるかをまず数えてみるほうが早い。トークン数のおおよその見当をつけるには、下の道具一覧のトークン計算機を使えばよい。

9.2 閉域網ではスイッチの点検は性能の問題ではない

金融や官公庁のように外部 API の呼び出しが塞がれた環境では、ローカルは選択肢ではなく前提だ。このとき GPU を使っているかどうかは「もっと速く」の問題ではなく「使い物になるか」の問題になる。CPU で動いている状態で導入検討をすると性能が要件に届かないという結論が出るが、その結論はモデルではなく設定のせいかもしれない。導入判断の前に 3 章の三層を必ず通すこと。順序が逆になると、まともな候補を落としてしまう。

9.3 会社支給機という変数

社内支給の Mac にはセキュリティエージェントや資産管理ツールが常駐している場合が多い。これらが周期的に CPU を占有すると、測定値が回ごとに揺れる。4 章で平均ではなく中央値を使えと書いた理由がここにもかかる。測定中に予期しない跳ねがあれば、その回を捨てて測り直すのが正しい。

9.4 中古の Mac を買うときの確認順序

ローカル LLM が目的なら、中古市場で Mac を選ぶときの確認順序は決まっている。

  • 統合メモリ容量が第一だ。増設が不可能なので、取り返しのつかない唯一の項目である
  • チップの等級が第二だ。同じ容量でもメモリ帯域が違い、デコード速度がここに縛られる
  • ストレージは第三だ。モデルファイルは大きいが外付けで賄える
  • 世代の差は上の三つを決めた後に見る項目だ。メモリが小さい最新世代より、メモリが大きい前世代のほうが載せられるモデルの範囲では上になる

10. 確認できなかったこと

以下の項目は一次的な根拠を確保できなかったため、本文で数値や方法として使わなかった。

  • この記事の発端となった最適化記録の倍率。コミュニティで共有された個人のパイプライン記録で、一行の修正で実行時間が半分近くまで減ったという内容だ。どのチップ・統合メモリ・モデル・量子化・コンテキスト長で出た値かを特定できず、本文に数値として持ち込まなかった。原文は参考資料にリンクしてある
  • Apple による推奨ワーキングセットサイズの定義原文。torch.mps.recommended_max_memory() が返す値の根拠となる Metal 側の定義を Apple の公式ドキュメントで開けなかった。そのため「全体メモリの何パーセントまで GPU が使えるのか」に当たる具体的な数値は書いていない。関数が返す値を自分の機体で直接出力するほうが確実だ
  • GPU 利用可能メモリの上限を sysctl で引き上げる方法。コミュニティに広く出回っているが、Apple の一次文書を特定できなかった。システム全体の設定に触れる措置なので、根拠なしには勧めない
  • MLX ドキュメントのおよそ 2 倍。ドキュメントが示した例題ワークロードで出た値であり、LLM 推論で測定された値ではない。本文でもその範囲でのみ引用した
  • Ollama や LM Studio のようなランチャーの内部スイッチ。これらが下位エンジンの Metal 関連設定をどこまで露出するかはバージョンによって異なるため、各配布物のドキュメントを確認する必要がある。この記事の表には公式ドキュメントで確認した三つのスタックだけを入れた
  • チップ等級別の毎秒トークン数。機器・モデル・量子化・コンテキストの組み合わせごとに変わり、条件が明示された公開測定を確保できなかったので入れていない。4 章の手順で自分の機体で測るほうが正確だ

11. 結論: スイッチ一つではなく順序だ

Mac でローカル LLM が遅いとき、まず疑うべきはモデルの大きさではなく計算がどこで動いているかだ。そしてこれは推測することではなく、3 分あれば確認できることである。

順序を整理するとこうなる。

  1. デバイスが認識されるか確認する。PyTorch なら is_available() と is_built() を両方出力する。二種類の失敗メッセージは原因がまったく違う
  2. 実際に動いているか見る。推論中にアクティビティモニタの GPU 履歴が上がるか。ここで引っかかる場合が最も多い
  3. メモリを確保しているか見る。driver_allocated_memory() がゼロに近ければモデルは GPU にない
  4. 正しく測る。torch.mps.synchronize() で挟み、ウォームアップを捨て、中央値を使う。この段階を飛ばすと以降の判断がすべて揺らぐ
  5. それでも速くならなければ五つを順に消す。CPU フォールバック、初回実行のコスト、バッチサイズ、メモリ圧迫、測定の誤り

最後に倍率の話を整理して終わろう。「一行で何倍」という形の数値は、方向だけ持ってきて大きさは捨てるのが正しい。GPU を使っていなかったパイプラインが GPU を使うようになれば大きく速くなるという結論は構造から出るので揺らがない。しかしその倍率は、その人のチップと、その人のモデルと、その人のパイプラインで GPU 区間が占めていた割合が作った値だ。

いますぐやることは一つだ。動いている推論の横にアクティビティモニタの GPU 履歴ウインドウを出してみること。グラフが平らなら、変えるべきはモデルではない。
