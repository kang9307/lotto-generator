모델은 텍스트만 내놓는다 - 나머지를 전부 정하는 것은 하네스다

도구를 부르는 것도, 언제 멈출지도, 실패를 다시 시도할지도 모델의 결정이 아니다

2026-09-05 개발/인프라

에이전트가 파일을 지웠다면, 그 파일을 지운 것은 모델이 아니다. 모델이 한 일은 지우는 도구를 이런 인자로 부르는 것이 적절하다는 내용의 구조화된 텍스트를 한 덩어리 생성한 것뿐이다. 그 텍스트를 읽고 실제 시스템 콜을 부른 것은 그 바깥의 프로그램이다.

이 구분이 사소해 보이지만, 에이전트를 운영해 본 쪽이면 여기서 갈리는 문제가 대부분이라는 것을 안다. 같은 모델이 어떤 도구 모음에서는 멀쩡히 돌고 다른 곳에서는 같은 조회를 열 번 반복한다. 어떤 환경에서는 실패한 도구를 한 번 더 부르고 다른 환경에서는 곧장 포기한다. 모델을 바꿨더니 동작이 달라졌다는 보고의 상당수도 실제로는 모델을 감싼 층의 계약이 달라진 것이다.

그 층에 붙은 이름이 하네스다. 아래에서는 하네스가 실제로 무엇을 결정하는 자리인지를 벤더 문서의 원문 필드로 확인하고, 그 결정을 빼먹었을 때 어떤 증상이 나오는지를 항목별로 정리한다. 프레임워크 소개나 비교는 여기서 다루지 않는다. 코드에서 에이전트를 어떤 모양으로 표현할지의 문제는 클래스·그래프·설정 파일이 각각 가리는 것에서 따로 다뤘다.

아래에 나오는 필드 이름과 기본값은 전부 Claude API 문서, OpenAI 함수 호출 가이드, Gemini API 타입 레퍼런스, MCP 사양과 그 JSON 스키마의 원문 표기다. 도구 호출 규격은 벤더마다 다르고 같은 벤더 안에서도 개정되므로, 남이 옮겨 적은 필드 이름을 다시 옮겨 적는 것이 이 주제에서 가장 흔한 오류다.

계기 - 저장소 하나가 하네스라는 말을 앞세웠다

2026년 9월 초 국내 개발자 커뮤니티에 TrueForge 라는 저장소가 소개됐다. 소개 문구는 LLM 을 실제 에이전트로 실행하는 오픈소스 하네스였다. 프레임워크도 아니고 라이브러리도 아니고 하네스라는 낱말을 앞세운 것이 눈에 띄는 지점이다.

저장소의 공개 지표는 2026년 9월 5일 04시 22분 UTC 시점의 값으로 다음과 같다. 별 5,221개, 포크 374개, 열린 이슈 91개, 커밋 약 515개, 기여자 약 31명, 언어는 TypeScript, 라이선스는 MIT, 저장소 생성일은 2026년 7월 23일이고 마지막 푸시는 하루 전인 9월 4일이다. 태그된 릴리스는 8월 27일 자 @truefoundry/trueforge@0.2.0-rc.0 계열이 최신이며, 네 개의 npm 패키지가 모두 1.0 이전 릴리스 후보 단계에 있다. README 는 Node 22.14 이상을 요구한다.

별 개수는 성숙도가 아니다. 생성 6주 만에 5천 개가 붙은 것은 화제성의 지표이지 안정성의 지표가 아니며, 0.2.0-rc 라는 버전 표기와 91개의 열린 이슈가 같은 시점의 사실로 나란히 있다. 이 값들의 해석은 각자의 몫으로 두고, 여기서는 이 저장소가 스스로 정의한 하네스의 범위만 가져온다. 문서는 하네스를 LLM 주위를 감싸 그것을 신뢰할 수 있는 장기 실행 에이전트로 만드는 런타임 계층이라 적고, 그 책임으로 계획, 도구 라우팅과 실행, 긴 작업을 위한 컨텍스트 관리, 샌드박스와 사람의 승인 같은 보안 경계, 재접속과 재시작을 넘겨 살아남는 세션 상태를 든다.

이 목록이 흥미로운 이유는 여기에 모델이 하는 일이 하나도 없다는 점이다. 계획도 하네스가 관리하고, 도구 라우팅도, 컨텍스트도, 승인도, 상태도 하네스다. 그렇다면 모델은 무엇을 하는가.

모델이 실제로 내놓는 것 - 텍스트와 멈춘 이유

모델 API 를 한 번 부르면 돌아오는 것은 두 가지다. 콘텐츠 블록의 배열과 왜 생성을 멈췄는지다. 그게 전부다. 스트리밍을 쓰든 안 쓰든, 도구를 붙였든 안 붙였든 달라지지 않는다.

도구를 붙이면 그 배열 안에 텍스트 블록 말고 tool_use 블록이 섞여 들어올 수 있다. Claude API 문서는 이 블록이 id, name, input 세 필드를 갖는다고 적는다. 각각 이 호출을 나중에 결과와 짝지을 식별자, 부를 도구의 이름, 그리고 도구 정의의 input_schema 를 따르는 인자 객체다. 여기 어디에도 실행은 없다. 블록이 도착한 시점에 파일은 아직 그대로다.

멈춘 이유를 담는 stop_reason 은 하네스가 다음에 무엇을 할지 정하는 유일한 신호다. 값마다 요구하는 처리가 다르고, 그중 몇 개는 빼먹기 쉽다.

책임의 경계 - 누가 무엇을 정하는가

여기서 한 번에 정리하는 편이 낫다. 아래 표의 왼쪽 열은 에이전트를 돌릴 때 반드시 누군가는 정해야 하는 항목이고, 가운데는 그 결정이 실제로 어디서 이뤄지는지, 오른쪽은 그것을 아무도 정하지 않았을 때 나오는 증상이다.

결정 항목모델의 몫인가 하네스의 몫인가안 정했을 때의 증상
어떤 도구를 부를지 고르기모델. 단 후보 목록과 설명문을 정하는 것은 하네스다설명이 부실하면 엉뚱한 도구를 고르거나 아예 안 부른다
도구를 실제로 실행하기전적으로 하네스모델은 계속 부르는데 아무것도 일어나지 않는다
실행 결과를 대화에 다시 넣기전적으로 하네스같은 도구를 무한히 다시 부른다. 결과가 안 보이니 안 불렀다고 판단한다
언제 멈출지전적으로 하네스단계 수가 늘어나고 비용이 새며, 정상 종료와 방치를 구분할 수 없다
실패를 재시도할지전적으로 하네스일시 장애로 과제 전체가 죽거나, 반대로 인증 실패를 스무 번 재시도한다
부작용의 중복 방지전적으로 하네스결제나 발송이 두 번 나간다. 재시도한 순간 확정된다
사람의 승인을 받을 지점전적으로 하네스되돌릴 수 없는 조작이 통보 없이 실행된다
대화 상태를 어디에 두는가전적으로 하네스프로세스가 죽으면 진행 중이던 작업이 사라진다
컨텍스트를 언제 어떻게 잘라내는가전적으로 하네스긴 작업 중간에 초반 지시를 잊거나, 창을 넘겨 요청이 실패한다
무엇을 기록할 것인가전적으로 하네스사고 후에 무슨 도구를 무슨 인자로 불렀는지 답할 수 없다
인자의 스키마 적합성양쪽. 모델이 생성하고 하네스가 검증한다필수 인자가 빠진 호출이 그대로 실행된다
도구 결과를 신뢰할지하네스. 모델은 들어온 텍스트를 구분하지 못한다외부 콘텐츠에 섞인 지시가 그대로 먹힌다

오른쪽 열을 세로로 읽으면 익숙한 장애 목록이 된다. 그리고 그 목록의 어느 것도 모델을 더 좋은 것으로 바꿔서 해결되지 않는다. 마지막 줄은 특히 그렇다. Claude API 문서는 도구 결과가 웹 페이지, 수신 메일, 사용자 업로드, 서드파티 API 처럼 통제 밖의 출처에서 오는 경우가 많으므로 신뢰할 수 없는 내용으로 취급하고, 시스템 프롬프트나 일반 사용자 텍스트 블록이 아니라 tool_result 블록 안에 두라고 적는다. 이것은 배치의 문제이지 모델 능력의 문제가 아니다.

도구 호출은 실행이 아니라 요청이다

모델이 도구를 부른다는 표현이 오해를 만든다. 실제로 벌어지는 일은 요청서 작성에 가깝다. 모델은 도구 이름과 인자를 적은 구조를 생성하고 거기서 턴을 끝낸다. 그다음은 전부 바깥의 일이다.

이 요청서를 처리하는 과정에서 하네스가 내리는 결정이 최소 여섯 개다.

  • 이름 해석 - 모델이 적은 이름에 해당하는 실제 함수가 무엇인가. 같은 이름이 여러 MCP 서버에 있으면 어느 쪽인가
  • 인자 검증 - 스키마에 맞는가. 안 맞으면 실행할 것인가 되돌릴 것인가
  • 권한 판정 - 이 세션이 이 도구를 부를 수 있는가. 승인이 필요한 등급인가
  • 실행 환경 - 하네스 프로세스 안에서 도는가, 격리된 샌드박스에서 도는가
  • 타임아웃 - 얼마나 기다릴 것인가. MCP 사양은 클라이언트가 도구 호출에 타임아웃을 두라고 적는다
  • 결과 가공 - 반환값이 크면 그대로 넣을 것인가, 요약하거나 파일로 빼고 미리보기만 넣을 것인가

마지막 항목은 특히 결과에 직접 영향을 준다. 300KB 짜리 로그를 그대로 컨텍스트에 넣으면 다음 턴부터 모델은 그 로그에 짓눌린다. 미리보기만 넣으면 필요한 줄이 잘려 나갈 수 있다. 어느 쪽을 고르든 모델이 보는 세계는 하네스가 편집한 결과물이다. 도구를 많이 붙였을 때 선택 자체가 무너지는 지점과 카탈로그를 좁히는 방법은 도구를 몇 개까지 붙일 수 있나에서 다뤘다.

같은 개념, 다른 필드 - 벤더별 계약

도구 호출이라는 개념은 공통이지만 계약은 벤더마다 다르다. 그 차이가 하네스 코드의 분기가 되고, 이식할 때 사고가 나는 지점이 된다.

스키마 강제도구 정의의 strict: truestrict - 모든 필드 필수, additionalProperties 는 falseVALIDATED 모드outputSchema 를 주면 서버는 반드시 그에 맞는 구조화 결과를 낸다

표에서 가장 먼저 눈에 걸리는 줄은 인자의 형태다. OpenAI 의 arguments 는 JSON 으로 인코딩된 문자열이고 나머지는 객체다. 이 한 줄 때문에 하네스에는 파싱 실패 경로가 하나 더 생긴다. 모델이 문법적으로 깨진 JSON 을 내면 그것은 도구 실패가 아니라 인자 디코딩 실패이고, 이 둘을 같은 통로로 처리하면 재시도 정책이 엉킨다.

결과를 어디에 넣느냐도 갈린다. Claude API 는 별도의 tool 역할을 두지 않고 사용자 메시지 안에 tool_result 블록을 넣는 방식이며, 문서는 이 점을 다른 API 와의 차이로 명시한다. 여기에는 지키지 않으면 400 이 나는 규칙이 붙는다. 도구 결과 블록은 그 도구 사용 메시지 바로 다음에 와야 하고, 결과를 담은 사용자 메시지에서는 결과 블록이 배열의 맨 앞에 와야 한다. 텍스트를 앞에 두면 거부된다.

도구 정의가 공짜가 아니라는 점도 계약의 일부다. Claude API 문서는 도구를 붙이면 도구 사용을 활성화하는 시스템 프롬프트가 자동으로 들어가며 그 토큰 수가 모델과 tool_choice 설정에 따라 다르다고 적고 표를 제공한다. Claude Opus 5 기준으로 auto 나 none 이면 286 토큰, any 나 특정 도구 지정이면 406 토큰이다. 여기에 도구 이름과 설명과 스키마의 토큰이 더해진다.

실패를 모델에 어떻게 돌려주는가

도구는 실패한다. 문제는 그 실패를 모델이 어떤 모양으로 보게 되는가이고, 이것은 전적으로 하네스가 정한다. 벤더 규격이 정해 주는 부분은 생각보다 좁다.

구분규격이 정해 주는 것하네스가 정해야 하는 것
Claude APItool_result 에 is_error: true. 문서는 무엇이 잘못됐고 다음에 무엇을 시도하면 되는지 적으라고 권한다메시지 문구. 실패라고만 적을지, 재시도 가능 여부와 대기 시간을 적을지
OpenAI전용 오류 필드 없음. output 의 형식은 JSON, 오류 코드, 평문 무엇이든 호출자에게 맡긴다오류 표기 규약 전부. 모델이 성공과 실패를 구분할 단서를 직접 만들어야 한다
GeminifunctionResponse 의 response 객체오류를 그 객체 안에 어떤 키로 담을지
MCP프로토콜 오류와 도구 실행 오류를 분리한다. 없는 도구나 잘못된 인자는 JSON-RPC 오류로, 실행 중 실패는 결과의 isError: true 로어느 실패를 어느 쪽으로 보낼지의 판정 기준

MCP 가 둘을 나눈 이유가 하네스 설계에 그대로 쓰인다. 모델이 봐야 하는 실패와 모델이 볼 필요가 없는 실패는 다르다. 존재하지 않는 도구를 부른 것은 프로토콜 위반이고 클라이언트가 처리할 문제다. API 가 429 를 냈다면 그것은 모델이 알아야 하는 상황이다. 다음에 다른 도구를 쓰거나 잠시 뒤에 다시 시도하는 판단의 재료가 되기 때문이다.

여기서 흔한 실수 하나. 오류 문자열을 그대로 넣는 것이다. 스택 트레이스 전체를 content 에 붓으면 컨텍스트가 잠식되고, 그 안에 내부 경로나 자격증명 조각이 섞여 들어갈 수 있다. 값이 아니라 참조를 넘기는 원칙은 에이전트에게 자격증명을 주지 않고 일을 시키는 법에서 따로 다뤘다. 오류도 같은 원칙이 적용되는 자리다.

병렬 호출 - 파라미터 하나가 가르는 것

모델이 한 턴에 도구를 여러 개 부를 수 있는가. 벤더는 대체로 허용하고, 끄는 방법을 제공한다. Claude API 는 tool_choice 안의 disable_parallel_tool_use 를 true 로 두면 한 턴에 도구 호출이 최대 하나가 된다. OpenAI 는 parallel_tool_calls 를 false 로 두면 정확히 0개 또는 1개가 호출된다. Gemini 는 병렬 호출과 여러 턴에 걸친 연쇄 호출을 모두 기본 지원한다고 문서에 적는다.

이 스위치 하나가 하네스 구조를 크게 바꾼다.

  • 켜면 지연이 줄고 왕복 횟수가 준다. 대신 하네스는 여러 결과를 전부 모아 되돌려야 하고, 그중 하나만 실패했을 때의 처리를 정해야 한다
  • 켠 채로 부작용 있는 도구를 열어 두면 순서 보장이 사라진다. 읽고 쓰는 두 도구가 같은 턴에 나가면 어느 쪽이 먼저 끝날지는 하네스의 실행 방식이 정한다
  • 끄면 추적이 쉬워지고 승인 흐름이 단순해진다. 대신 같은 과제에 필요한 모델 호출 횟수가 늘어 비용과 시간이 는다
  • Claude API 문서는 서버 측 도구와 클라이언트 도구가 같은 병렬 묶음에 섞이는 경우를 따로 설명한다. 이때 사용자 메시지는 결과 블록만 담아야 하고, 뒤에 텍스트를 붙이면 턴이 일찍 끝나며 400 이 난다

여기서 중요한 것은 어느 쪽이 낫다는 결론이 아니라, 이 선택을 안 한 하네스는 벤더 기본값을 그대로 쓰고 있다는 사실이다. 그리고 기본값은 벤더마다 다르다.

모델을 바꿨더니 동작이 달라졌다의 정체

이제 처음의 관찰로 돌아온다. 모델 교체 후 에이전트가 다르게 굴 때, 그 차이의 어디까지가 모델이고 어디부터가 하네스인가.

모델 능력은 분명히 영향을 준다. 문서는 필수 인자가 빠졌을 때 Claude Opus 가 그것을 알아채고 되물을 가능성이 훨씬 높은 반면 Claude Sonnet 은 그럴 수도 있고 그럴듯한 값을 채워 넣을 수도 있다고 적는다. 이런 차이는 실재한다. 다만 그 위에 계약의 차이가 겹쳐 있고, 후자가 훨씬 크게 작용하는 경우가 많다.

  • 도구 스키마 표현 - 같은 도구라도 설명문 한 줄이 다르면 선택 빈도가 달라진다. 벤더별 어댑터가 설명을 자르거나 스키마를 평탄화하면 모델이 보는 것이 달라진다
  • 강제 수준 - auto 로 두느냐 required 로 두느냐는 모델 설정이 아니라 하네스 설정이다. 어댑터가 이를 다르게 매핑하면 같은 프롬프트가 다르게 작동한다
  • 병렬 허용 - 위 절 그대로다. 기본값이 다른 두 벤더 사이를 옮기면 호출 패턴 자체가 바뀐다
  • 오류 표현 - 실패를 is_error 로 알리는 하네스와 그냥 문자열로 넣는 하네스에서 모델의 복구 행동은 다르게 나온다
  • 컨텍스트 잘라내기 - 어느 시점에 무엇을 요약해 버리는지가 다르면 후반부 행동이 통째로 달라진다
  • 시스템 프롬프트 주입 - 도구를 붙이는 것만으로 벤더가 자동으로 넣는 시스템 프롬프트가 있고, 그 내용과 크기는 벤더와 설정에 따라 다르다

실무적으로 이것이 뜻하는 바는 하나다. 모델 비교를 하려면 하네스를 고정해야 한다. 하네스가 다른 두 환경에서 나온 숫자를 모델 성능 비교라고 부르면, 재현되지 않는 결론이 남는다. 검증 자체를 자동화할 때 어디까지 기계가 판정할 수 있는지의 경계는 검증 하네스가 그은 경계선에서 따로 정리했다.

중단 조건 - 언제 멈출지 정하지 않으면

여기서부터가 하네스가 반드시 정해야 하는 항목들이다. 정하지 않으면 기본값이 없는 것이 아니라, 암묵적으로 제한 없음이 기본값이 된다.

모델에는 예산 개념이 없다. 매 턴 도구를 하나 더 부르는 쪽이 그럴듯해 보이면 그렇게 한다. 그 판단은 남은 비용이나 경과 시간을 재료로 삼지 않는다. 그것을 재는 자리는 바깥뿐이다.

상한무엇을 재는가없을 때의 증상걸렸을 때 무엇을 하는가
최대 단계 수모델 호출 왕복 횟수같은 조회를 변형해 가며 반복한다. 결과는 정상으로 보인다중단하고 지금까지의 진행을 요약해 사용자에게 넘긴다
비용 상한누적 입출력 토큰과 환산 금액청구서로만 사후에 알게 된다중단하거나 더 싼 모델로 낮춘다
벽시계 상한세션 시작부터의 실제 경과 시간사용자가 응답을 기다리는 채로 방치된다부분 결과를 내보내고 이어 하기 여부를 묻는다
도구별 호출 횟수같은 도구를 몇 번 불렀는가한 도구에서만 루프가 돈다. 전체 단계 수는 아직 여유가 있다그 도구를 이번 세션에서 잠그고 모델에 알린다
무진전 감지연속으로 같은 인자의 호출이 몇 번인가단계 수는 늘지만 상태는 그대로다같은 호출임을 결과로 알려 다른 경로를 찾게 한다

실무에서 더 자주 문제가 되는 것은 무한 루프가 아니라 조용한 낭비다. 스무 단계면 끝날 과제를 여든 단계로 도는 에이전트는 최종 결과가 맞기 때문에 아무도 이상을 느끼지 못한다. 그 차이는 관측 기록을 붙이기 전까지 드러나지 않는다. 자율 에이전트가 예산을 태우는 방식의 극단적인 사례는 AI 에이전트의 청구서 사고에 정리해 뒀다.

실패의 분류 - 다시 부를 것과 아닌 것

도구가 실패했을 때 하네스가 답해야 하는 질문은 두 개다. 다시 부를 것인가, 그리고 모델에게 알릴 것인가. 이 둘은 별개다.

  • 일시 실패 - 네트워크 타임아웃, 502, 429. 하네스가 조용히 재시도하는 것이 맞다. 백오프를 두고, 횟수 상한을 두고, 그래도 실패하면 그때 모델에 알린다. 매 시도를 모델에 알리면 컨텍스트만 낭비한다
  • 영구 실패 - 404, 인증 거부, 존재하지 않는 리소스. 재시도해도 같은 결과다. 모델에 즉시 알려 다른 경로를 찾게 하는 것이 맞다
  • 인자 오류 - 스키마 위반, 필수 값 누락, JSON 파싱 실패. 모델이 고칠 수 있는 유일한 분류다. 무엇이 빠졌는지 적어 되돌린다. Claude API 문서는 이 경우 모델이 정보를 채워 두세 번 다시 시도한 뒤 포기한다고 적는다
  • 정책 거부 - 승인 거절, 권한 부족. 재시도 대상이 아니며 모델에 알려야 한다. 다만 거부 사유를 그대로 전달할지는 별도 판단이다
  • 부분 성공 - 열 건 중 세 건 실패. 가장 다루기 까다롭다. 전체를 실패로 볼지, 성공분을 확정하고 실패분만 알릴지가 도구마다 다르다

이 분류를 안 하면 두 방향으로 망가진다. 전부 재시도하면 인증 실패를 스무 번 반복하고, 전부 모델에 넘기면 일시적인 502 하나에 과제 전체가 방향을 튼다. 어느 쪽도 모델이 나빠서 생긴 일이 아니다.

멱등성 - 두 번 불러도 되는 도구인가

재시도를 도입하는 순간 새 질문이 따라온다. 그 도구를 두 번 불러도 되는가. 결제, 메일 발송, 티켓 생성, 배포는 두 번 부르면 두 번 일어난다. 첫 호출이 타임아웃으로 끝났다고 해서 실행되지 않았다는 뜻이 아니다. 응답을 못 받은 것과 실행이 안 된 것은 다르다.

MCP 는 도구가 자기 성질을 표시할 자리를 마련해 뒀다. ToolAnnotations 의 네 필드다. 다만 스키마의 설명문이 그 위상을 분명히 못 박는다.

  • readOnlyHint - 참이면 환경을 바꾸지 않는 도구다. 기본값은 거짓
  • destructiveHint - 참이면 파괴적 갱신을 할 수 있다. 거짓이면 추가만 한다. readOnlyHint 가 거짓일 때만 의미가 있다. 기본값은 참
  • idempotentHint - 참이면 같은 인자로 반복 호출해도 추가 효과가 없다. 역시 readOnlyHint 가 거짓일 때만 의미가 있다. 기본값은 거짓
  • openWorldHint - 참이면 외부 개체들의 열린 세계와 상호작용한다. 웹 검색은 열린 세계이고 메모리 도구는 닫힌 세계라는 것이 스키마의 예시다. 기본값은 참
  • 그리고 결정적인 문장 - ToolAnnotations 의 모든 속성은 힌트이며 도구 동작을 충실히 설명한다는 보장이 없다. 스키마는 신뢰할 수 없는 서버에서 받은 값으로 도구 사용 결정을 내리지 말라고 명시한다

기본값의 방향이 전부 보수적이라는 점을 눈여겨볼 만하다. 아무 표시가 없는 도구는 파괴적이고 멱등하지 않으며 열린 세계와 상호작용하는 도구로 취급하라는 뜻이다. 그리고 힌트는 힌트이므로, 재시도 안전성은 결국 하네스가 자기 쪽에서 보장해야 한다. 방법은 셋 중 하나다. 호출마다 멱등 키를 만들어 도구에 넘기거나, 재시도 전에 조회로 상태를 확인하거나, 부작용 있는 도구는 애초에 재시도 대상에서 빼는 것이다. 마지막 선택지가 가장 자주 정답이다.

승인 지점 - 사람이 끼어드는 자리

MCP 사양은 신뢰와 안전을 이유로 도구 호출을 거부할 수 있는 사람이 항상 루프 안에 있어야 한다고 적고, 애플리케이션에 세 가지를 권한다. 어떤 도구가 모델에 노출됐는지 분명히 보이는 UI, 도구가 호출될 때의 시각적 표시, 그리고 확인 프롬프트다. 서버를 부르기 전에 도구 입력을 사용자에게 보여 주라는 조항도 따로 있다. 악의적이거나 실수에 의한 데이터 유출을 막기 위해서다.

승인을 어디에 둘 것인가는 하네스의 정책 문제다. 위치는 대체로 네 곳 중 하나다.

  • 도구 단위 - 특정 도구는 항상 승인. 구현이 가장 단순하고 예측 가능하다
  • 인자 단위 - 같은 도구라도 인자에 따라 갈린다. 임시 디렉터리 삭제는 자동, 그 밖의 경로는 승인 같은 식이다
  • 누적 단위 - 이번 세션에서 이미 N번 승인했으면 그다음부터는 자동. 승인 피로를 줄이지만 경계가 흐려진다
  • 결과 단위 - 실행은 하되 확정 전에 멈춘다. 드라이런이 가능한 도구에서만 성립한다

승인 지점을 아예 안 두면 되돌릴 수 없는 조작이 통보 없이 실행된다. 반대로 전부에 두면 사람이 내용을 안 보고 누르기 시작한다. 두 축으로 등급을 나누는 방법은 권한 설계와 사고 차단선에 정리해 뒀으므로 여기서는 되풀이하지 않는다. 하네스 관점에서 덧붙일 것은 하나다. 승인 대기 중인 세션의 상태를 어디에 두는가. 메모리에만 있으면 배포 한 번에 대기 중이던 작업이 전부 사라진다.

관측 - 무슨 도구를 무슨 인자로 불렀는가

사고가 나면 답해야 하는 질문은 정해져 있다. 무슨 도구를, 무슨 인자로, 몇 시에, 누구의 요청으로 불렀고, 결과가 무엇이었나. 이 질문에 답할 수 있는 기록은 하네스만 만들 수 있다. 모델은 자기가 무엇을 불렀는지 기억하지 않는다. 대화 이력에 남아 있는 것을 다시 읽을 뿐이다.

MCP 사양은 클라이언트에 감사 목적의 도구 사용 로깅을 권하고, 결과를 모델에 넘기기 전에 검증하라고 적는다. 최소한 남겨야 하는 항목은 다음과 같다.

  • 호출 식별자와 그에 대응하는 결과 - 짝이 맞아야 사후 재구성이 된다
  • 도구 이름과 인자 전문 - 요약본만 남기면 사고 조사에서 쓸모가 없다. 다만 인자에 민감한 값이 들어갈 수 있으므로 마스킹 규칙이 함께 필요하다
  • 실행 시각과 소요 시간 - 어느 도구가 지연의 원인인지는 이것 없이 알 수 없다
  • 실패 분류와 재시도 횟수 - 위 절의 분류가 기록으로 남아야 정책이 맞았는지 판정할 수 있다
  • 토큰 사용량과 누적 비용 - 단계별로 남겨야 어느 구간이 비쌌는지 나온다
  • 컨텍스트 편집 이력 - 무엇이 잘려 나갔는지 남지 않으면 모델이 왜 그 판단을 했는지 재구성할 수 없다

마지막 항목이 가장 자주 빠진다. 요약과 잘라내기는 하네스가 조용히 하는 일이라 로그에 남기지 않는 경우가 많은데, 그 결과 같은 입력으로 다시 돌려도 같은 결과가 안 나오는 상태가 된다. 세션 실행을 토큰 낭비 관점에서 해부하는 방법은 에이전트 블랙박스 분석에, 프로덕션에서 실수를 추적하는 구성은 LLM 옵저버빌리티 실무 가이드에 있다.

상태와 컨텍스트 - 잘라 낼 때 사라지는 것

긴 과제는 컨텍스트 창을 넘긴다. 그때 하네스가 하는 일이 잘라내기다. TrueForge 문서는 이 기능을 기본으로 켜 두고 발동 조건을 모델 컨텍스트 길이의 80퍼센트, 그 값을 모를 때는 입력 토큰 5만으로 잡는다고 적는다. 함께 적어 둔 문장이 더 중요하다. 압축은 작업 컨텍스트에서는 손실이 있으며, 전체 세션 이력은 API 로 조회할 수 있다.

이 두 문장이 상태 설계의 핵심을 담고 있다. 모델이 보는 것과 시스템이 보관하는 것은 다른 물건이다. 앞의 것은 매 호출마다 재구성되는 편집본이고, 뒤의 것은 append-only 인 기록이다. 이 둘을 같은 것으로 취급하는 하네스는 두 방향 중 하나로 망가진다. 편집본만 있으면 사후 재구성이 불가능하고, 기록만 있으면 창을 넘겨 요청이 실패한다.

잘라내기 방식마다 잃는 것이 다르다.

  • 오래된 것부터 버리기 - 구현이 가장 쉽다. 잃는 것은 초반의 지시와 제약 조건이다. 긴 작업 후반에 원래 요구사항을 어기는 전형적인 증상이 여기서 나온다
  • 요약으로 대체 - 분량은 줄지만 요약이 무엇을 남길지는 또 하나의 모델 호출이 정한다. 요약 단계에서 사라진 정보는 되돌아오지 않는다
  • 큰 결과를 밖으로 빼기 - 도구 반환값을 파일로 저장하고 미리보기만 넣는 방식이다. 모델이 필요하면 다시 읽을 수 있으므로 손실이 적지만, 다시 읽는 호출이 단계 수를 늘린다
  • 도구 스키마를 나중에 싣기 - 이름과 설명만 먼저 주고 스키마는 필요할 때 불러오는 방식이다. TrueForge 문서는 이 기능의 기본값이 미리 싣지 않음이라고 적는다
  • 하위 에이전트로 격리 - 세부 작업을 별도 컨텍스트에서 돌리고 최종 결과만 위로 올린다. 전달 손실과 조정 비용이 새로 생기며, 그 경계는 역할 분담 시뮬레이션의 경계에서 따로 다뤘다

어느 방식이든 모델은 자기가 무엇을 잊었는지 모른다. 잘려 나간 자리에 표시가 남지 않기 때문이다. 그래서 잘라내기 정책은 관측 항목이어야 한다.

루프를 코드로 보면

앞의 항목들을 하나의 흐름에 얹으면 이런 모양이 된다. 아래는 특정 SDK 의 API 가 아니라 결정 지점을 드러내기 위한 골격이다. 실제 필드 이름은 위 표의 벤더별 계약을 따른다.

// 하네스 루프의 골격 - 결정 지점에 주석을 달았다
async function runAgent(task, tools, limits) {
  const messages = [{ role: 'user', content: task }];
  let steps = 0, spent = 0;
  const startedAt = Date.now();

  while (true) {
    // 결정 1: 중단 조건. 모델은 이것을 재지 않는다
    if (steps >= limits.maxSteps) return stop('MAX_STEPS', messages);
    if (spent >= limits.maxCost) return stop('BUDGET', messages);
    if (Date.now() - startedAt >= limits.maxWallClockMs) return stop('TIMEOUT', messages);

    const res = await model.call({ messages, tools, toolChoice: limits.toolChoice });
    steps += 1;
    spent += estimateCost(res.usage);
    record({ steps, usage: res.usage, stopReason: res.stopReason });  // 결정 6: 관측

    // 결정 2: stop_reason 분기. 하나만 빠져도 그 조건에서 멈춘 것처럼 보인다
    if (res.stopReason === 'end_turn') return finish(res);
    if (res.stopReason === 'refusal') return handleRefusal(res);
    if (res.stopReason === 'max_tokens') return handleTruncated(res);
    if (res.stopReason === 'pause_turn') { messages.push(asAssistant(res)); continue; }

    const calls = res.content.filter((b) => b.type === 'tool_use');
    if (!calls.length) return finish(res);

    // 결정 3: 병렬로 실행할 것인가 순차로 할 것인가
    const results = limits.parallel
      ? await Promise.all(calls.map(execute))
      : await runSequentially(calls, execute);

    messages.push(asAssistant(res));
    messages.push(asToolResults(results));   // 결과 블록이 배열의 맨 앞에 와야 한다

    // 결정 4: 컨텍스트가 임계에 닿으면 무엇을 버릴 것인가
    if (estimateTokens(messages) >= limits.compactAt) await compact(messages);
  }
}

도구 하나를 실행하는 부분에는 승인과 실패 분류가 들어간다. 아래에서 classify 가 돌려주는 값이 재시도 여부를 정하고, 멱등 키가 부작용의 중복을 막는다.

// 도구 실행 - 승인, 멱등성, 실패 분류가 모두 여기 모인다
async function execute(call) {
  // 결정 5: 승인 지점. 인자를 보여 준 뒤에 묻는다
  if (needsApproval(call)) {
    const verdict = await askUser(call.name, call.input);   // 대기 상태는 영속 저장소에
    if (verdict !== 'allow') return toolError(call.id, 'POLICY_DENIED: 사용자가 거부함');
  }

  // 부작용 있는 도구에는 호출마다 고정된 키를 준다.
  // 표시가 없는 도구는 파괴적이고 멱등하지 않은 것으로 취급한다
  const key = isSideEffecting(call) ? idempotencyKey(call) : null;

  let attempt = 0;
  while (true) {
    try {
      const out = await invoke(call.name, call.input, { key, timeoutMs: TOOL_TIMEOUT_MS });
      return toolResult(call.id, truncateOrOffload(out));   // 큰 결과는 밖으로 뺀다
    } catch (err) {
      const kind = classify(err);   // TRANSIENT / PERMANENT / BAD_ARGS / DENIED
      // 일시 실패만 조용히 다시 부른다. 그 외에는 모델이 판단하도록 넘긴다
      if (kind === 'TRANSIENT' && key && attempt < MAX_RETRY) {
        await backoff(attempt++);
        continue;
      }
      return toolError(call.id, redact(summarize(err, kind)));   // 원문 대신 요약과 마스킹
    }
  }
}

  { "type": "tool_result", "tool_use_id": "TOOL_USE_ID",
    "content": "RateLimited: 60초 후 재시도 가능", "is_error": true } ] }

// OpenAI - 전용 오류 필드가 없다. 표기 규약은 하네스가 정한다

  "output": "{\"ok\":false,\"code\":\"rate_limited\",\"retry_after_s\":60}" }

직접 만들 것인가 가져다 쓸 것인가

하네스는 얇아 보인다. 루프 하나에 분기 몇 개면 되는 것처럼 보이고, 실제로 첫 버전은 반나절이면 나온다. 문제는 위에서 나열한 항목들이 곧 하네스라는 점이다. 중단 조건, 실패 분류, 멱등성, 승인, 관측, 컨텍스트 편집, 세션 영속화를 다 넣고 나면 얇지 않다.

판단 축직접 만드는 쪽이 맞는 조건가져다 쓰는 쪽이 맞는 조건
도구 개수서너 개로 고정돼 있고 늘어날 계획이 없다MCP 서버를 계속 붙일 예정이다
부작용전부 읽기 전용이다쓰기와 결제와 발송이 섞여 있다
실행 시간한 요청 안에서 끝난다재접속과 재시작을 넘겨 이어져야 한다
사용자만든 사람만 쓴다여러 사람이 쓰고 누가 무엇을 했는지 남아야 한다
벤더한 곳으로 고정이다여러 벤더를 오간다. 어댑터 층이 어차피 필요하다
승인 흐름필요 없거나 전부 자동이다사람이 중간에 끼어들고 그 상태가 살아남아야 한다
관측 요구표준 출력으로 충분하다감사 기록과 비용 분해가 요구된다
운영 부담한 프로세스로 족하다여러 복제본과 데이터베이스를 운영할 여력이 있다

오른쪽 열에 두 개 이상 해당하면 직접 만드는 비용이 생각보다 크다. 반대로 왼쪽 열에 다 해당하면 남의 추상화를 끌어오는 쪽이 오히려 손해다. 여러 에이전트를 한 저장소에 동시에 풀었을 때 생기는 격리 문제는 하네스 선택과는 또 다른 축이며 병렬 코딩 에이전트의 충돌과 격리에서 다뤘다.

계기가 된 저장소로 돌아가면, 그 문서가 광고하는 기능 목록은 위 표의 오른쪽 열과 거의 겹친다. 샌드박스를 도구로 두는 방식, 하위 에이전트, 도구 스키마 지연 로딩, 큰 결과 오프로딩, 압축, 도구 승인, 되묻기, 생성형 UI, 그리고 로컬 모드의 SQLite 와 호스티드 모드의 Postgres 및 Redis 다. README 는 로컬 모드는 내 컴퓨터 전용이며 기본적으로 로그인이 없고 프로덕션이나 인터넷 노출용이 아니다라고 직접 적는다. 이런 문장이 문서에 있는지 없는지가 도입 판단의 재료가 된다.

저장소는 자체 벤치마크도 공개한다. DevRev 의 Enterprise-Bench 에서 뽑은 14개 과제를 같은 모델, 같은 세 개의 MCP 서버, 같은 시스템 프롬프트로 구성마다 3회씩 돌리고 별도의 LLM 심사자가 채점하는 방식이며, 상대는 폐쇄형 하나와 오픈소스 하나다. 다만 이 측정은 프로젝트 자신이 수행한 것이고 제3자 재현 결과는 함께 제시되지 않는다. 자체 벤치마크는 설정을 공개했다는 점에서 의미가 있지만 독립 검증과는 다른 물건이다.

확인하지 못한 것

  • Gemini 함수 호출 문서에서 표기가 두 갈래로 보인다. 타입 레퍼런스는 functionCall 과 functionResponse 파트에 args 와 response 객체를 쓰는 형태를 적는데, 가이드 페이지 쪽은 function_call 과 function_result 에 call_id 를 쓰는 형태로 읽힌다. 어느 쪽이 어느 SDK 버전의 정본인지는 문서만으로 갈리지 않아 본문 표에는 타입 레퍼런스 표기를 실었다
  • Gemini 의 functionResponse 에 오류 전용 필드가 있는지는 타입 레퍼런스에서 찾지 못했다. 본문에는 response 객체 안에 담는다고만 적었다
  • OpenAI 문서에는 도구 실행 오류를 표시하는 전용 필드가 없고 output 형식이 호출자 재량이라고만 되어 있다. 모델이 실패를 어떤 형태로 인식하도록 훈련됐는지는 문서에 없으므로, 오류 표기 규약의 효과는 각자 측정할 문제로 남는다
  • Claude API 의 pause_turn 기본 한도 10회를 요청 단위로 조정할 수 있는지는 해당 문서에서 명시를 찾지 못했다
  • TrueForge 의 재시도 정책, 최대 단계 수 기본값, 비용 상한 설정 위치는 공개 문서 목차의 항목명만으로는 특정되지 않았다. 본문에서 인용한 것은 압축 임계값과 지연 로딩 기본값처럼 문서에 수치가 적힌 항목뿐이다
  • 저장소 지표는 2026년 9월 5일 04시 22분 UTC 시점의 값이다. 별 5,221개와 커밋 약 515개, 기여자 약 31명 같은 수치가 운영 안정성과 어떤 관계인지는 이 값들만으로 말할 수 없다
  • MCP 사양은 클라이언트에 도구 호출 타임아웃을 두라고 적지만 권장 값은 제시하지 않는다
  • Claude API 문서의 도구 사용 시스템 프롬프트 토큰 수 표는 모델별로 값이 다른데, 그 차이가 무엇에서 오는지는 문서에 설명이 없다
