시연은 Windows 10 의 Git Bash(bash 5.2.37)에서 GNU tar 1.35 로 실행했고, 출력은 실행 결과 그대로이되 임시 폴더 경로만 /tmp/demo 로 바꿨다. 같은 PC 의 Windows 기본 tar.exe(bsdtar 3.5.2)는 9절에서 따로 비교한다. 리눅스·macOS 의 tar 는 실행하지 않았으므로 아래 동작은 「이 PC 의 tar 출력」이며, 이유 설명은 출력이 직접 보여 주는 것과 GNU tar 매뉴얼 페이지(man.archlinux.org)의 문장으로 한정한다.

서론 - 아카이브 안의 경로는 묶을 때 준 문자열이다

tar 아카이브는 파일 내용과 함께 이름 문자열을 저장한다. 풀 때는 그 이름을 현재 디렉터리(또는 지정한 기준 디렉터리) 아래의 경로로 해석해 파일을 만든다. 따라서 묶을 때 어떤 문자열을 넘겼는지가 풀었을 때의 위치를 정한다. tar -cf out.tar app 처럼 상대 경로를 넘기면 이름이 app/... 로 시작하고, /home/user/app 같은 절대 경로를 넘기면 경로 전체가 이름에 들어가려 한다. 이때 tar 는 앞 슬래시를 제거하고 경고를 낸다.

문제는 그 뒤에 나온다. 앞 슬래시만 떼였을 뿐 상위 디렉터리 이름은 그대로 남아 있어서, 다른 위치에 풀면 app 이 아니라 상위 경로 전체가 중첩된 채로 생긴다. 이 현상을 같은 더미 트리 하나의 출력으로 보이고, 기준 디렉터리 -C, 절대 경로 보존 -P, .. 성분이 든 항목, 풀기 전 목록 확인, 최상위 디렉터리 한 개로 묶는 관례를 차례로 다룬다. 후행 슬래시가 대상을 바꾸는 rsync 쪽 사정은 rsync 후행 슬래시 글이 다루므로, 여기서는 tar 의 앞 슬래시와 경로 이름만 다룬다.

다루는 질문은 다음과 같다.

  • 절대 경로로 묶을 때 tar 는 무엇을 출력하고, 종료 코드는 어떻게 되는가.
  • 그 아카이브를 다른 디렉터리에 풀면 파일은 어디에 생기는가.
  • -C 와 상대 경로는 같은 아카이브를 만드는가, 그리고 -C 의 위치 규칙은 무엇인가.
  • -P 는 만들 때만 영향을 주는가, 풀 때는 어떻게 동작하는가.
  • .. 성분이 든 항목과 절대 경로 항목은 풀 때 어떻게 처리되는가.
  • 풀기 전에 무엇을 확인하고, 아카이브를 어떤 모양으로 묶어야 흩어지지 않는가.

시연 환경과 안전 틀

모든 시연은 mktemp -d 로 만든 새 임시 폴더 안에서만 파일을 만들고, 끝에서 그 폴더만 지운다. 절대 경로를 쓰는 예제도 그 임시 폴더 안의 경로만 대상으로 한다. show 함수는 출력에 나오는 임시 폴더 경로를 /tmp/demo 로 바꾸는 표시용 필터이며 tar 의 동작에는 관여하지 않는다. 더미 트리는 src/app 아래 파일 세 개다.

D=$(mktemp -d) && cd "$D" || exit 1
                    show() { sed -e "s#$D#/tmp/demo#g" -e "s#${D#/}#tmp/demo#g"; }
                    mkdir -p src/app/bin src/app/conf src/app/data
                    echo 'echo run' > src/app/bin/run.sh
                    echo 'port=8080' > src/app/conf/app.conf
                    echo 'alpha' > src/app/data/a.txt
                    tar --version | head -1
tar (GNU tar) 1.35

종류와 버전은 tar --version 첫 줄로 구분한다. 이 PC 의 Git Bash 에서는 GNU tar 1.35 이며, 이후 출력은 모두 이 tar 의 것이다.

절대 경로로 묶으면 - 경고와 목록

tar -cf abs.tar "$D/src/app"
                    echo "exit=$?"
                    tar -tf abs.tar | show
tar: Removing leading `/' from member names
                    exit=0
                    tmp/demo/src/app/
                    tmp/demo/src/app/bin/
                    tmp/demo/src/app/bin/run.sh
                    tmp/demo/src/app/conf/
                    tmp/demo/src/app/conf/app.conf
                    tmp/demo/src/app/data/
                    tmp/demo/src/app/data/a.txt

첫 줄은 stderr 로 나온 경고 Removing leading `/' from member names 이다. 종료 코드는 0 이므로 실패가 아니라 경고다. 목록(tar -tf)의 멤버 이름은 슬래시로 시작하지 않지만 tmp/demo/src/app/... 처럼 상위 경로 전체가 이름에 들어 있다. 시연 경로를 /tmp/demo 로 바꿨을 뿐, 실제 이름은 묶을 때 넘긴 절대 경로에서 앞 슬래시 하나만 뺀 문자열이다.

풀었을 때 - 상위 경로가 통째로 생긴다

mkdir restore1
                    tar -C restore1 -xf abs.tar
                    (cd restore1 && find . -type f | sort) | show
./tmp/demo/src/app/bin/run.sh
                    ./tmp/demo/src/app/conf/app.conf
                    ./tmp/demo/src/app/data/a.txt

-C restore1 로 기준 디렉터리를 정했는데도 파일은 restore1/app/... 이 아니라 restore1/tmp/demo/src/app/... 에 생겼다. 이름 안에 상위 경로가 들어 있으므로 풀 때도 그대로 중첩 디렉터리가 만들어진다. 이것이 「풀었더니 엉뚱한 곳에 생긴 파일」이 이 시연에서 나타난 모양이다. 파일이 사라진 것이 아니라 기준 디렉터리 아래 깊은 곳에 있다.

상대 경로와 -C - 기준 디렉터리를 정하고 담는다

(cd src && tar -cf ../rel.tar app)
                    tar -C src -cf c.tar app
                    tar -tf c.tar
                    cmp rel.tar c.tar && echo "rel.tar and c.tar are byte-identical"
                    mkdir restore2
                    tar -C restore2 -xf c.tar
                    (cd restore2 && find . -type f | sort)
app/
                    app/bin/
                    app/bin/run.sh
                    app/conf/
                    app/conf/app.conf
                    app/data/
                    app/data/a.txt
                    rel.tar and c.tar are byte-identical
                    ./app/bin/run.sh
                    ./app/conf/app.conf
                    ./app/data/a.txt

cd src 후 tar -cf ../rel.tar app 로 만든 것과 tar -C src -cf c.tar app 로 만든 것은 cmp 가 byte-identical 이라고 답했다. 멤버 이름은 app/... 로 시작하고 경고도 없으며, 풀면 restore2/app/... 이 된다. GNU tar 매뉴얼 페이지는 -C 를 이렇게 설명한다. 「Change to DIR before performing any operations. This option is order-sensitive, i.e. it affects all options that follow.」 (출처: man.archlinux.org/man/tar.1.en)

「order-sensitive」라는 문장은 다음 출력에 그대로 나타난다. 명령은 같은 이름을 . 로 담는 형태, -C 를 여러 번 쓰는 형태, -C 를 이름 뒤에 둔 형태이다.

tar -C src/app -cf dot.tar .
                    tar -tf dot.tar
                    mkdir -p pos/a pos/b
                    echo A > pos/a/fa.txt
                    echo B > pos/b/fb.txt
                    tar -cf pos1.tar -C pos/a fa.txt -C ../b fb.txt
                    tar -tf pos1.tar
                    tar -cf pos2.tar fa.txt -C pos/a
                    echo "exit=$?"
./
                    ./bin/
                    ./bin/run.sh
                    ./conf/
                    ./conf/app.conf
                    ./data/
                    ./data/a.txt
                    fa.txt
                    fb.txt
                    tar: fa.txt: Cannot stat: No such file or directory
                    tar: The following options were used after non-option arguments.  These options are positional and affect only arguments that follow them.  Please, rearrange them properly.
                    tar: -C 'pos/a' has no effect
                    tar: Exiting with failure status due to previous errors
                    exit=2
  • -C src/app -cf dot.tar . 는 멤버 이름이 ./ 로 시작하고, 이름에 app 같은 최상위 디렉터리가 없다. 최상위 이름의 문제는 8절에서 다룬다.
  • -C pos/a fa.txt -C ../b fb.txt 에서 두 번째 -C 의 ../b 는 첫 번째 -C 가 옮겨 놓은 위치(pos/a)를 기준으로 해석되어 pos/b 가 되었다. 목록에는 fa.txt 와 fb.txt 가 모두 이름만 남았다.
  • -C 를 이름 뒤에 둔 tar -cf pos2.tar fa.txt -C pos/a 는 fa.txt: Cannot stat 에 이어 -C 'pos/a' has no effect 를 출력하고 종료 코드 2 로 끝났다. -C 는 자기 뒤의 이름에만 적용된다.

-P - 절대 경로를 보존하면 -C 가 무력해진다

GNU tar 매뉴얼 페이지의 -P 항목은 한 줄이다. 「-P, --absolute-names: Don't strip leading slashes from file names when creating archives.」 문장은 만들 때를 말하지만, 아래 출력에서는 목록과 풀기에도 영향이 나타났다. 아카이브는 앞의 절과 같은 대상을 -P 로 묶은 것이다.

tar -P -cf p.tar "$D/src/app"
                    echo "exit=$?"
                    echo '--- list without -P'
                    tar -tf p.tar 2>&1 | show | head -3
                    echo '--- list with -P'
                    tar -P -tf p.tar | show | head -3
exit=0
                    --- list without -P
                    tar: Removing leading `/' from member names
                    /tmp/demo/src/app/
                    /tmp/demo/src/app/bin/
                    --- list with -P
                    /tmp/demo/src/app/
                    /tmp/demo/src/app/bin/
                    /tmp/demo/src/app/bin/run.sh

-P 로 만들 때는 경고가 없고 종료 코드는 0 이다. 목록 출력은 두 가지다. -P 없이 tar -tf 를 하면 경고를 다시 내면서도 이름은 /tmp/demo/src/app/ 처럼 슬래시로 시작하는 저장된 모양 그대로 보여 준다. -P 를 붙이면 경고 없이 같은 목록이 나온다. 따라서 목록 이름의 첫 글자가 슬래시인지가 -P 로 만든 아카이브를 가려내는 단서가 된다.

이어서 이 아카이브를 -P 와 -C restore3 를 함께 주고 풀었다. 먼저 원본 src 를 src_before 로 옮겨 두어 원래 자리가 비도록 했고, 풀기 대상은 모두 임시 폴더 안이다.

mv src src_before
                    mkdir restore3
                    tar -P -C restore3 -xf p.tar
                    echo "exit=$?"
                    echo "files under restore3: $(find restore3 -type f | wc -l)"
                    find src -type f | sort
                    diff -r src src_before && echo "recreated src is identical to src_before"
                    mkdir restore4
                    tar -C restore4 -xf p.tar
                    (cd restore4 && find . -type f | sort) | show
exit=0
                    files under restore3: 0
                    src/app/bin/run.sh
                    src/app/conf/app.conf
                    src/app/data/a.txt
                    recreated src is identical to src_before
                    tar: Removing leading `/' from member names
                    ./tmp/demo/src/app/bin/run.sh
                    ./tmp/demo/src/app/conf/app.conf
                    ./tmp/demo/src/app/data/a.txt

결과는 세 가지다. 첫째, -P -C restore3 로 풀었을 때 restore3 아래 파일은 0개이고, 파일은 비워 둔 원래 자리 src/app 에 다시 만들어졌다. 절대 이름을 가진 항목에는 -C 가 작용하지 않았다. 둘째, 다시 만들어진 src 는 src_before 와 diff -r 로 같았다. 셋째, -P 없이 같은 아카이브를 -C restore4 로 풀면 경고와 함께 restore4/tmp/demo/src/app/... 에 중첩된다.

묶은 방식푸는 방식파일이 생긴 곳경고
-P 없이 절대 경로-C restore1restore1/tmp/demo/src/app/... (중첩)만들 때만
-P 로 절대 경로-C restore4 (-P 없음)restore4/tmp/demo/src/app/... (중첩)풀 때 출력
-P 로 절대 경로-P -C restore3원래의 절대 경로 src/app (restore3 는 비어 있음)없음
  • -P 로 풀 때는 -C 를 무시하고 기록된 절대 위치에 쓴다. 그 위치는 풀기 명령의 -C 와 무관하게 정해지므로, 풀기 명령만 보고는 파일이 어디에 생길지 알 수 없다.
  • 그래서 -P 는 자기 파일을 같은 자리에 복원하는 용도로 쓰고, 출처가 불분명한 아카이브에는 풀기 전 목록의 첫 글자를 먼저 본다(8절).
  • 이 시연에서 -P 로 풀린 위치는 임시 폴더 안의 원래 자리였고, 시스템·홈 경로에는 쓰지 않았다.

.. 성분이 든 항목과 절대 이름 항목 - 풀 때의 처리

먼저 .. 로 시작하는 경로를 묶을 때의 tar 동작이다. 하위 폴더에서 상위 파일 ../outside.txt 를 묶었다.

mkdir -p work/sub
                    echo 'outside content' > work/outside.txt
                    (cd work/sub && tar -cf ../dd.tar ../outside.txt)
                    tar -tf work/dd.tar
tar: Removing leading `../' from member names
                    outside.txt

만들 때 tar 는 Removing leading `../' from member names 경고를 내고 이름을 outside.txt 로 줄였다. 그래서 이름 앞쪽의 ../ 는 GNU tar 로 묶는 과정에서 제거되어 .. 항목이 만들어지지 않았다. 풀 때의 동작을 보려면 이름을 그대로 적는 도구가 필요하며, 아래에서는 Python 표준 라이브러리 tarfile 로 시연용 아카이브 둘을 만들었다. 하나는 ok/inside.txt 와 ../escape.txt 를 담고, 다른 하나는 임시 폴더 안의 절대 이름 .../ext/abs_target.txt 를 담는다. 임시 폴더 경로가 인자로 전달될 때 Git Bash 가 경로를 바꾸지 않도록 MSYS_NO_PATHCONV=1 을 붙였으며, 이 접두는 Git Bash 전용이다.

mkdir craft ext
                    cat > craft/make.py <<'PYEOF'
                    import io, sys, tarfile
                    target = sys.argv[1]
                    def add(tf, name, data):
                        info = tarfile.TarInfo(name)
                        info.size = len(data)
                        tf.addfile(info, io.BytesIO(data))
                    with tarfile.open('craft/dotdot.tar', 'w') as tf:
                        add(tf, 'ok/inside.txt', b'inside')
                        add(tf, '../escape.txt', b'escaped')
                    with tarfile.open('craft/abs.tar', 'w') as tf:
                        add(tf, target + '/ext/abs_target.txt', b'absolute')
                    PYEOF
                    MSYS_NO_PATHCONV=1 python craft/make.py "$D"
                    tar -tf craft/dotdot.tar
                    tar -tf craft/abs.tar 2>&1 | show
ok/inside.txt
                    tar: Removing leading `../' from member names
                    ../escape.txt
                    tar: Removing leading `/' from member names
                    /tmp/demo/ext/abs_target.txt

두 아카이브의 목록에서도 tar -tf 는 ../ 와 앞 슬래시에 대한 경고를 낸다. 이어서 임시 폴더 안의 ext/inner 에서 푼다. .. 항목의 목적지는 한 단계 위인 ext 이며, 모두 임시 폴더 안이다.

mkdir ext/inner
                    (cd ext/inner && tar -xf ../../craft/dotdot.tar; echo "exit=$?")
                    find ext | sort
                    (cd ext/inner && tar -P -xf ../../craft/dotdot.tar; echo "exit=$?")
                    find ext | sort
tar: Removing leading `../' from member names
                    tar: ../escape.txt: Member name contains '..'
                    tar: Exiting with failure status due to previous errors
                    exit=2
                    ext
                    ext/inner
                    ext/inner/ok
                    ext/inner/ok/inside.txt
                    exit=0
                    ext
                    ext/escape.txt
                    ext/inner
                    ext/inner/ok
                    ext/inner/ok/inside.txt

기본 설정에서 ../escape.txt 는 Member name contains '..' 오류로 풀리지 않았고 종료 코드는 2 였다. 같은 아카이브의 정상 항목 ok/inside.txt 는 풀렸다. -P 를 붙이자 종료 코드 0 으로 끝났고 ext/escape.txt 가 ext/inner 의 바깥에 만들어졌다. 한 항목의 거부가 나머지 항목의 추출을 막지 않았다는 점과, -P 가 .. 검사까지 풀어 버렸다는 점이 아래 출력이 직접 보여 준다.

절대 이름 항목은 같은 방식으로 풀었다. 아래 find 는 abs_target.txt 가 놓인 위치만 출력한다.

(cd ext/inner && tar -xf ../../craft/abs.tar)
                    find ext -name abs_target.txt | show
                    (cd ext/inner && tar -P -xf ../../craft/abs.tar)
                    find ext -name abs_target.txt | show
tar: Removing leading `/' from member names
                    ext/inner/tmp/demo/ext/abs_target.txt
                    ext/abs_target.txt
                    ext/inner/tmp/demo/ext/abs_target.txt

기본 설정에서는 경고와 함께 ext/inner/tmp/demo/ext/abs_target.txt 로 중첩되었고, -P 를 붙인 두 번째 풀기에서는 기록된 절대 위치 ext/abs_target.txt 에도 파일이 만들어졌다. 정리하면 기본 설정은 앞 슬래시를 떼고 .. 를 거부하며, -P 는 둘 다 풀어 준다.

풀기 전 확인과 최상위 디렉터리 한 개 관례

7절의 두 가지 위험은 목록 단계에서 가려낼 수 있다. 아래 grep 은 슬래시로 시작하거나 .. 성분을 가진 이름만 골라낸다. 이 정규식은 시연용이며 tar 가 제공하는 기능이 아니다.

tar -tf p.tar 2>/dev/null | grep -E '^/|(^|/)\.\.(/|$)' | show | head -2
                    tar -tf craft/dotdot.tar 2>/dev/null | grep -E '^/|(^|/)\.\.(/|$)'
                    tar -tf rel.tar | grep -cE '^/|(^|/)\.\.(/|$)'
/tmp/demo/src/app/
                    /tmp/demo/src/app/bin/
                    ../escape.txt

-P 로 만든 p.tar 는 슬래시로 시작하는 이름이, dotdot.tar 는 ../escape.txt 가 걸렸고, 상대 경로로 만든 rel.tar 는 0건이었다. 풀기 전에 이 목록을 사람이 읽거나 스크립트가 검사하면 7절의 동작에 도달하기 전에 아카이브를 걸러 낼 수 있다. 목록을 읽는 일은 파일을 만들지 않으므로 되돌릴 것이 없다. 목록 확인을 풀기의 예행 연습으로 삼는 방식은 셸 스크립트의 예행 연습 설계 글에도 나온다.

최상위 디렉터리가 몇 개인지도 목록으로 알 수 있다. 같은 파일을 bin conf data 세 이름으로 묶은 아카이브와 app 하나로 묶은 아카이브를 비교하고, 이미 파일(mine.txt)이 있는 디렉터리에 풀었다.

tar -C src/app -cf bomb.tar bin conf data
                    tar -tf bomb.tar | cut -d/ -f1 | sort -u
                    tar -C src -cf one.tar app
                    tar -tf one.tar | cut -d/ -f1 | sort -u

  • bin conf data 로 묶은 아카이브는 최상위 이름이 세 개이고, 풀면 mine.txt 가 있는 디렉터리에 bin·conf·data 가 섞여 들어갔다.
  • app 하나로 묶은 아카이브는 최상위 이름이 하나뿐이므로 어디에 풀어도 app 아래로 모인다.
  • --one-top-level=out 는 받는 쪽에서 쓰는 보호 장치다. 매뉴얼 페이지는 「Extract all files into DIR, or, if used without argument, into a subdirectory named by the base name of the archive」 라고 설명하며, 출력에서는 out/ 아래로 모였다.
  • 묶는 쪽의 관례는 상위 디렉터리로 -C 를 옮겨 놓고 디렉터리 이름 하나를 넘기는 것이다(tar -C src -cf one.tar app).

마지막으로 기존 파일과 이름이 겹칠 때의 기본 동작이다. ow/note.txt 에 OLD 를 적어 두고, NEW 를 담은 같은 이름의 파일을 푼다. 매뉴얼 페이지는 -k 를 「Don't replace existing files when extracting.」 이라고 적는다.

mkdir ow t1
                    echo OLD > ow/note.txt
                    echo NEW > t1/note.txt
                    tar -C t1 -cf note.tar note.txt
                    (cd ow && tar -k -xf ../note.tar; echo "exit=$?"; cat note.txt)
                    (cd ow && tar -xf ../note.tar; echo "exit=$?"; cat note.txt)
tar: note.txt: Cannot open: File exists
                    tar: Exiting with failure status due to previous errors
                    exit=2
                    OLD
                    exit=0
                    NEW

-k 를 주면 note.txt: Cannot open: File exists 오류와 종료 코드 2 가 나오고 내용은 OLD 로 남았다. 옵션 없이 풀면 종료 코드 0 에 내용이 NEW 로 바뀌었다. 기본 동작은 확인 없이 덮어쓰며 메시지도 없다. 같은 이름이 있을 수 있는 디렉터리에 풀 때는 빈 디렉터리를 만들어 -C 로 지정하는 쪽이 이 결과를 피한다.

같은 PC 의 두 tar - GNU tar 와 Windows 기본 tar.exe

Windows 10 에는 C:\Windows\System32\tar.exe 가 있고, Git Bash 의 tar 와 종류가 다르다. 같은 더미 트리와 같은 시연용 아카이브로 동작을 비교했다. 절대 경로는 cygpath -m 으로 얻은 C:/... 형태로 넘겼고, 출력의 경로는 showw 필터로 치환했다.

BSD=/c/Windows/System32/tar.exe
                    "$BSD" --version
                    DM=$(cygpath -m "$D")
                    showw() { sed -e "s#${DM#?:/}#demo#g" -e "s#$DM#C:/demo#g"; }
                    "$BSD" -cf bsd_abs.tar "$DM/src/app"
                    "$BSD" -tf bsd_abs.tar | showw | head -3
                    mkdir ext/bsd
                    (cd ext/bsd && "$BSD" -xf ../../craft/dotdot.tar; echo "exit=$?")
                    (cd ext/bsd && "$BSD" -xf ../../craft/abs.tar; echo "exit=$?")

case "$D" in "${TMPDIR:-/tmp}"/*) cd / && rm -rf "$D" ;; esac

정리 - 묶을 때와 풀 때의 순서

  • 묶을 때는 기준이 될 상위 디렉터리를 -C 로 지정하고 디렉터리 이름 하나를 넘긴다(tar -C 상위경로 -cf out.tar 이름). 경고가 나오지 않고 멤버 이름이 이름/... 으로 시작한다(5절).
  • Removing leading 경고가 보이면 이미 절대 경로로 묶였다는 뜻이므로, 그 아카이브를 풀 때 상위 경로가 중첩되는 것을 예상한다(3절·4절).
  • 받은 아카이브는 풀기 전에 tar -tf 로 목록을 읽고, 슬래시로 시작하는 이름·.. 성분·최상위 이름의 개수를 확인한다(8절).
  • 풀 때는 새로 만든 빈 디렉터리를 -C 로 지정한다. 같은 이름의 기존 파일은 기본 설정에서 확인 없이 바뀌므로(8절), 빈 디렉터리가 그 경우를 막는다.
  • -P 는 풀 때 -C 를 무시하고 기록된 절대 위치에 쓴다. 자기 파일을 같은 자리에 복원할 때만 쓰고, 출처가 불분명한 아카이브에는 쓰지 않는다(6절·7절).
  • 윈도우의 Git Bash tar 와 기본 tar.exe 는 메시지와 종료 코드가 달라서, 출력 문자열을 읽는 스크립트는 사용할 tar 를 먼저 정한다(9절).

압축 파일 이름의 인코딩 문제는 다루지 않으며 zip 안의 한글 파일명 글이 tar 의 이름 인코딩 선언 부재까지 포함해 다룬다. 백업 아카이브를 임시 디렉터리에 풀어 복구 여부를 점검하는 절차는 백업과 복구 전략 글에 있다.

확인하지 못한 것

  • GNU tar 공식 매뉴얼(gnu.org)은 이 PC 에서 접속이 거부되어 열지 못했다. 인용한 문장은 GNU TAR 매뉴얼 페이지로 표시된 man.archlinux.org 판의 것이며, 그 판에는 패키지 표기 1.35-5 가 보인다.
  • tar 가 앞 슬래시를 제거하도록 설계된 목적에 대한 개발자 측 설명. 본문의 이유 부분은 실행 출력이 보여 준 동작(경고, 중첩, -C 무시, .. 거부)에 한정했다.
  • 리눅스·macOS 의 tar 출력. 이 PC 에서 실행한 것은 Git Bash 의 GNU tar 1.35 와 Windows 의 bsdtar 3.5.2 뿐이다.
  • 다른 GNU tar 버전에서의 경고 문구와 .. 검사 방식, 심볼릭 링크·하드 링크 멤버를 가진 아카이브의 풀기 동작.
  • --strip-components·--transform 같은 이름 가공 옵션과 압축 형식(gz·xz)과의 조합.
  • bsdtar 의 -P 동작과 Windows 의 긴 경로·드라이브 문자가 섞인 이름에서의 풀기 결과.
