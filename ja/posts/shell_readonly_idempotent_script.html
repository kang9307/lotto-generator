二度実行しても壊れないスクリプト - 冪等性の設計と実際に壊れる六つのパターン

概念ではなく再現 - 実行出力と3回のハッシュ比較で確かめた安全な書き方

2026年7月29日 開発・インフラ

序論: 「もう一度回してもいいですか」に答えられないスクリプト

デプロイスクリプトが途中で落ちた。ログを見ると8段階のうち5段階までは進んでいる。原因はすぐに掴めた。残った問いは一つだけだ。「これ、そのままもう一度回していいですか」

この問いに即答できない瞬間、その夜は長くなる。スクリプトを頭から読みながらこの行は二度回るとどうなるのかを一行ずつ手で追わなければならないからだ。そしてたいていは全部を追いきれないまま「とりあえず5段階から手作業でやります」で終わる。手でやった部分は記録に残らず、次の担当者はサーバーの状態がなぜスクリプトと違うのか分からなくなる。

冪等性とは、この問いに0.5秒で「はい」と答えられるようにする性質だ。定義を暗記する問題ではなく、自分のスクリプトの各行が二度目の実行で正確に何をするのかを知っている問題である。だからこの記事は定義から始めない。実際に二度回して壊してみた出力から始める。

扱う順序はこうだ。まず実際に壊れる六つのパターンを一つずつ再現し、それぞれに安全な書き方を添える。次にマーカーブロックという汎用の解法と、再実行の結果が同じであることをハッシュで証明する手順を示す。最後に部分的な失敗からの再開の設計とロックが必要になる条件を整理する。

その前に用語を一つだけ整理しておこう。現場で「冪等」と一括りに呼んでいるものは、実は三つの層に分かれる。この区別をしておくと後の議論がずっと簡単になる。

水準保証すること保証しないこと代表的な手段
①再実行安全二度回しても壊れない(エラーで中断しない)結果が同じになることmkdir -p, rm -f
②結果の収束何度回しても同じ最終状態に到達する人が作ったドリフトの除去存在を確認してから変更、マーカーブロック
③自己修復状態がずれたら目標状態へ戻す宣言していない項目ブロック全体の差し替え、ファイル全体の生成

事故の大半は①だけやっておいて②をやったと信じ込むときに起きる。mkdir -pに書き換えて「冪等に直した」と言ってしまう場合だ。以下の再現で、その隙間がどこにあるのかがはっきり見える。

実行前の安全上の注意。 この記事のすべての再現は新しく作った一時ディレクトリの中だけで行った。本文にrm -rfが登場する箇所は、その一時ディレクトリ、またはその配下のパスを消す用途に限られる。実際のサーバーで真似しないこと。 とくにrm -rf "$DIR"の形は$DIRが空だとrm -rf ""になり、意図しない場所をさらう可能性があるため、変数を消すコマンドに使うときは[ -n "$DIR" ] && [ "$DIR" != "/" ]のような防御を必ず前に置く。cronやCIに入れる前には--checkのような試験実行で対象パスを目で確かめるほうが安全だ。

1. 実行環境と検証の方法

以下の出力はすべて実際に走らせた結果をそのまま貼ったものだ。再現環境は次のとおりである。

===== T0 ENVIRONMENT =====
MINGW64_NT-10.0-19045 3.5.7-882031da.x86_64
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)
sed (GNU sed) 4.9
grep (GNU grep) 3.0
sha256sum (GNU coreutils) 8.32

Windows 10上のMSYS2/Git Bash環境だ。GNUツール系なのでLinuxと挙動は同じだが、三つはこの環境に固有の制約なので先に明記しておく。読む側が結果を判断するために必要な情報である。

  • シンボリックリンクは既定の設定ではファイルのコピーとして処理される。本物のリンクを作るためにMSYS=winsymlinks:sysを設定した状態で実行した。
  • POSIXのパーミッションビットはNTFS上でそのまま反映されない。実際にchmod 600の後もモードは644と表示された。そのためパーミッションに関する冪等性はこの記事では実行結果として主張しない。該当する項目はチェックリストに規則としてだけ残した。
  • crontabとflockのバイナリが無い。cronはcrontab -lが出力するはずのテキストをファイルで模して行操作のロジックだけを検証し、ロックはflockの代わりにmkdirの原子性を使う方式で実証した。

検証は三つを混ぜた。終了コード(コマンドが成功したか)、ファイルの内容(何が残ったか)、SHA-256ハッシュ(繰り返した実行の結果が同じか)。とくにハッシュは「同じに見える」と「同じである」を分ける唯一の道具なので繰り返し使う。

2. パターン① appendが静かに積み上がる

最も多く、最も遅く見つかる。エラーにならないからだ。.bashrcにPATHを一行入れるスクリプトを二度回してみよう。

-- run 1 --
export PATH=/opt/tool/bin:$PATH
-- run 2 (same command again) --
export PATH=/opt/tool/bin:$PATH
export PATH=/opt/tool/bin:$PATH
lines: 2

終了コードは二度とも0だ。誰も失敗したとは言ってくれない。この行がPATHなら経路が重複するだけだが、同じファイルを毎回少しずつ伸ばすcronが付くと、数か月後に設定ファイルが数千行になる。実際の事故はたいていこの形で来る。

2.1 安全な書き方 - 存在を確認してから入れる

LINE='export PATH=/opt/tool/bin:$PATH'
grep -qxF -- "$LINE" safe.conf || printf '%s\n' "$LINE" >> safe.conf

3回実行した結果だ。行数もハッシュも固定される。

run1 -> 1 line(s) | sha=0a0746b7d8c9bd1f
run2 -> 1 line(s) | sha=0a0746b7d8c9bd1f
run3 -> 1 line(s) | sha=0a0746b7d8c9bd1f

2.2 罠 - grepのオプション一つで結果がひっくり返る

ここで-qxFのxとFは飾りではない。二つを外すと正反対の方向の事故がそれぞれ起きる。

罠A - コメントを「設定済み」と誤判定する。配布先のファイルに該当の行がコメントアウトされたまま入っている場合だ。よくある。誰かが一時的に切って忘れたのである。

file: #export PATH=/opt/tool/bin:$PATH
grep -qF  -> found (skips append) ... setting is never applied
grep -qxF -> not found (correct: a comment is not an active setting)

部分一致の-Fだけを使うとコメント行にも引っかかる。スクリプトは毎回「もう入っている」と静かに素通りし、設定は永遠に適用されない。エラーが出ないので数か月続く。-x(行全体の一致)がこれを防ぐ。

罠B - 正規表現メタ文字のせいで重複が積み上がる。逆の方向だ。入れようとする行に[、]、.、*のような文字があると、grep -qはそれを正規表現として読む。

file: PATH=/opt/tool[1]/bin
grep -q   -> NOT found ([1] read as a character class) -> duplicate append
grep -qxF -> found (correct)
after 3 runs: grep -q => 4 lines | grep -qxF => 1 lines

[1]は「文字1が一つ」を意味する文字クラスなので、リテラルの[1]とは一致しない。だから毎回「無い」と判定し、3回の実行で4行になる。-F(固定文字列)がこれを防ぐ。

2.3 もっと静かな罠 - grepの終了コード2

これは文書を見ないと分からない。grepは三つの終了コードを返す。実際に確認した値だ。

match      -> 0
no match   -> 1
read error -> 2  (|| append treats this like 'no match')

grep -qxF ... || appendの形は1(不一致)と2(エラー)を区別できない。ファイルを読む権限が無かったり、パスが間違っていたりすると、スクリプトは「無いんだな」と判断して追加を続ける。正確にやるには終了コードを分けて受け取る必要がある。

grep -qxF -- "$LINE" "$F"; rc=$?
case $rc in
  0) : ;;                                   # 既にある
  1) printf '%s\n' "$LINE" >> "$F" ;;       # 無い -> 追加
  *) echo "grep失敗(rc=$rc): $F" >&2; exit 1 ;;   # エラー -> 中断
esac

3. パターン② mkdir・rmの終了コードがスクリプトを真っ二つにする

最も広く知られた項目なので短く触れ、あまり知られていない副作用に紙面を使う。

-- mkdir d1 (run 1) --
exit=0
-- mkdir d1 (run 2) --
mkdir: cannot create directory 'd1': File exists
exit=1
-- mkdir -p d1 (run 3) --
exit=0

-- rm f1 (run 1) --
exit=0
-- rm f1 (run 2) --
rm: cannot remove 'f1': No such file or directory
exit=1
-- rm -f f1 (run 3) --
exit=0

POSIX仕様がこの挙動を定めている。mkdir -pについて「既に存在するディレクトリを名前として持つ各dirオペランドはエラーなしで無視される」と記し、rm -fについて「存在しないオペランドの場合、診断メッセージを書いたり終了ステータスを変えたりしない」と記す。オプションがやることは正確にそれだけだ。

3.1 本当の被害はset -eと出会ったときに出る

終了コード1そのものは大したことではない。問題はset -eの掛かったスクリプトでその後の段階が丸ごと消えることだ。3段階のスクリプトを二度回した結果である。

-- seq.sh run 1 --
  [step 2] place config files
  [step 3] restart service
exit=0
-- seq.sh run 2 --
mkdir: cannot create directory '.../s/stage': File exists
exit=1  <- steps 2 and 3 never ran

再実行するとディレクトリを作る1段階で止まり、設定の配置もサービスの再起動も起きない。ところがスクリプトは「失敗」としか言わない。どこまで進んだのかは教えてくれない。運用担当はログの最終行だけを見て「ディレクトリの問題」と判断し、肝心のサービスが古い設定で動いている事実は後から発見する。

3.2 オプションが肩代わりしてくれないもの

  • mkdir -pは存在の有無だけを無視する。既にあるディレクトリの所有者やパーミッションを目標値に合わせてはくれない。-mは新規に作るときしか適用されないので、パーミッションを保証したいならchmod・chownを別の行で明示する必要がある。(前述のとおり、この環境ではパーミッションビットを検証できないため実行出力としては提示しない。)
  • rm -fは存在しないファイルだけを見逃す。消そうとした対象がディレクトリなら依然として失敗する。
  • どちらも内容には関与しない。ディレクトリがあることと、その中が目標状態であることは別の話だ。

4. パターン③ ln -sは二度目にリンクの中へ潜り込む

この項目がこの記事で最も再現する価値がある。失敗しないまま見当違いの結果を残すからだ。無停止デプロイでcurrentシンボリックリンクを新しいリリースへ移す、あのコードである。

-- ln -s rel_a current (run 1) --
exit=0 | readlink=rel_a
-- ln -s rel_b current (run 2) --
exit=0

2回目が終了コード0だ。成功したように見える。実際に何ができたのかを確かめよう。

## ln -sf on a symlink that points to a directory
ln -sf exit=0
readlink current = rel_a   <- still points at rel_a
ls current/:
FROM_A
rel_b
what was actually created: lrwxrwxrwx 1 Karyu 197121 5 Jul 29 05:13 rel_a/rel_b -> rel_b
  -> it did not repoint the link; it created a new link INSIDE the target directory

肝心なのは最後の行だ。currentがディレクトリを指すシンボリックリンクのとき、ln -sf rel_b currentはcurrentをディレクトリとして辿り、その中にrel_bという新しいリンクを作る。readlink currentは依然としてrel_aのままだ。

運用でこれが何を意味するのか考えてみよう。デプロイスクリプトは成功を返し、監視も緑のままで、サービスは古いバージョンで動き続ける。おまけに以前のリリースディレクトリの中には正体不明のリンクが一つずつ溜まっていく。デプロイのたびに。

4.1 安全な書き方 - ln -sfn

GNU coreutilsのlnは-nを「リンク名がディレクトリを指すシンボリックリンクである場合、それを通常のファイルとして扱う」と説明する。辿るなという意味だ。3回実行した結果である。

## correct: ln -sfn (3 runs, same result)
run1 -> readlink=rel_b | rel_a contains: FROM_A
run2 -> readlink=rel_b | rel_a contains: FROM_A
run3 -> readlink=rel_b | rel_a contains: FROM_A

三度ともrel_bに固定され、rel_aの中にはFROM_A以外何も追加されなかった。実務の規則は一つにまとまる。ディレクトリを指すシンボリックリンクを差し替えるときは常に-nを付ける。-T(--no-target-directory)を使えば、もっと厳密に強制することもできる。

もっと安全な方法。 シンボリックリンクの差し替えを本当に原子的にやるには、一時的な名前でリンクを作ってからmv -Tで差し替える2段階が必要だ。ln -sfnは内部的に消してから作り直す瞬間があり、その一瞬currentが存在しない時点が生じ得る。トラフィックの多い経路なら、この差は意味を持つ。

5. パターン④ sed -iは成功を返しながら嘘をつく

sed -iの再実行安全性はパターンによって三つに分かれる。一つずつ再現した。

5.1 ケースA - 結果がパターンと重ならなければ安全

sed -i 's/^timeout = 30$/timeout = 60/' a.conf

run1 sha=ca1a53713b3fbd1d | timeout = 60 retries = 3
run2 sha=ca1a53713b3fbd1d | timeout = 60 retries = 3
run3 sha=ca1a53713b3fbd1d | timeout = 60 retries = 3

置換の結果であるtimeout = 60はパターン^timeout = 30$と重ならない。だから2回目からはマッチが無く、ファイルは変わらない。ハッシュが3回とも同一である。これが運良く冪等になっている場合だ。

5.2 ケースB - 結果が再びパターンを満たすと無限に積み上がる

sed -i 's#PATH=#PATH=/opt/bin:#' b.conf

run1: PATH=/opt/bin:/usr/bin
run2: PATH=/opt/bin:/opt/bin:/usr/bin
run3: PATH=/opt/bin:/opt/bin:/opt/bin:/usr/bin

置換の結果にPATH=がそのまま残っているので、次の実行でもまた引っかかる。回すたびに経路が一つずつ増える。先ほどのappend累積よりずっと目立たない。行数が増えないからだ。ファイルを開いて一行を最後まで読まないと見つからない。

5.3 ケースC - 何もせずに成功を返す

sed -i 's/^debug = true$/debug = false/' c.conf
exit=0 | content=debug = false  <- exit code is not evidence that it applied

ファイルには既にdebug = falseが入っていて、パターンは一つもマッチしなかった。ところがsedは終了コード0を返す。これは欠陥ではなく設計だ。sedは「置換を何件したのか」を終了コードで教えてくれない。

ここから出てくる実務の規則が重要だ。sed -iの終了コードは「適用された」ことの証拠ではない。設定が実際に反映されたか確かめたければ、置換の後に結果をもう一度読んで検査しなければならない。静かな失敗が最も恐ろしい理由は、ファイルパスの打ち間違いやアンカーの不一致も同じく0を返すからだ。

5.4 安全な書き方 - 目標状態を先に検査し、事後に検証する

TARGET='PATH=/opt/bin:/usr/bin'
grep -qxF "$TARGET" d.conf || sed -i 's#^PATH=/usr/bin$#PATH=/opt/bin:/usr/bin#' d.conf
grep -qxF "$TARGET" d.conf || { echo "適用に失敗"; exit 1; }

run1: PATH=/opt/bin:/usr/bin
run2: PATH=/opt/bin:/usr/bin
run3: PATH=/opt/bin:/usr/bin
post-check: target state reached (0)

三つを同時にやった。①目標状態を先に検査して既に到達していれば触らず、②アンカーを^...$で囲んで結果が再びパターンを満たさないようにし、③置換の後にもう一度読んで実際に到達したことを確認した。この三つが揃えばsed -iも安全に使える。

6. パターン⑤ crontabの登録が実行のたびに倍になる

広く出回った慣用句がある。(crontab -l; echo "$JOB") | crontab -。三度回した結果だ。

run1 -> sync.sh lines: 1
run2 -> sync.sh lines: 2
run3 -> sync.sh lines: 3
*/5 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1
*/5 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1
*/5 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1
  -> a job meant to run every 5 minutes now starts 3 times per tick

この結果の危険度は他のパターンとは格が違う。先のものはファイルが散らかる問題だったが、これは同じ作業が同時に複数立ち上がる問題だ。同期スクリプトなら互いに同じファイルを触り、バックアップなら帯域を分け合って両方とも遅くなり、DBの整理作業ならロックの競合が起きる。しかもプロビジョニングを三度回しただけで負荷が正確に3倍になるので、原因を突き止めるのも難しい。

6.1 安全な書き方 - 消してから入れ直す

「あればスキップ」ではなく「当該スクリプトを参照する行を全部消して新しく入れる」が正解だ。理由はすぐ説明する。

{ crontab -l 2>/dev/null | grep -vF '/opt/app/bin/sync.sh'
  printf '%s\n' "$JOB"; } | crontab -

run1 -> lines: 1 | sha=7352c0d47610f2d1
run2 -> lines: 1 | sha=7352c0d47610f2d1
run3 -> lines: 1 | sha=7352c0d47610f2d1

3回とも1行で、ハッシュが同じだ。「あればスキップ」方式よりこちらが優れている理由はスケジュールの変更にある。存在だけを確認する方式は*/5を*/10に変えても「もうある」と言って古い行をそのまま残す。消して入れる方式はそうならない。他のジョブを触らないかも一緒に確認した。

-- schedule change is absorbed too (*/5 -> */10), and other jobs survive --
0 3 * * * /opt/other/backup.sh
*/10 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1

backup.shの行はそのまま残り、sync.shの行だけが新しいスケジュールに更新された。ここではフィルタの文字列をどれだけ狭く取るかが要になる。sync.shのようなありふれた名前で除くと、他チームの/opt/legacy/sync.shまで消えかねない。絶対パス全体を使うか、後述のマーカーブロック方式を使うほうが安全だ。

できればcrontabを直接書かない選択肢もある。 /etc/cron.d/にファイルを一つ丸ごと配置すれば、それ自体が「全体の差し替え」なので重複が原理的に起こらない。一時ファイルに書いてmvで差し替えれば原子性まで得られる。ただしディストリビューションごとにファイル名の規則(ドットを含む名前は無視されるなど)やユーザーフィールドの有無が異なるので、該当するディストリビューションの文書を確認してから適用する。

7. パターン⑥ 冪等に見えて実はそうでないもの

ここまでが「知られた罠」だとすれば、この節は大半の人が冪等だと思い込んでいるコマンドたちだ。

7.1 cp -r - 初回と再実行で結果の構造が違う

cp -r src dst   # を3回

run1: dst dst/a.txt
run2: dst dst/a.txt dst/src dst/src/a.txt
run3: dst dst/a.txt dst/src dst/src/a.txt
  -> run 1 produced dst/a.txt; from run 2 on, dst/src/a.txt appeared as well

原因は対象が存在するかどうかでcp -rの意味が変わるからだ。dstが無ければdstをsrcのコピーとして作る(dst/a.txt)。dstがあればsrcをdstの中へ入れる(dst/src/a.txt)。同じコマンドなのに新規サーバーと再配布サーバーで結果が違う。「新規インストールはうまくいくのに、更新すると変になる」という症状の定番の原因だ。

安全な書き方はディレクトリではなく中身を指定することである。

cp -r src/. dst2/   # を3回

run1: dst2 dst2/a.txt
run2: dst2 dst2/a.txt
run3: dst2 dst2/a.txt

7.2 mv - 二度目はただ失敗する

run1 exit=0
mv: cannot stat 'mvsrc/data.bin': No such file or directory
run2 exit=1

mvは本質的に再実行できないコマンドだ。出発点が消えるからである。再実行できるようにするには[ -e "$SRC" ] && mv ...のように出発点の存在を条件に掛けるか、そもそもmvの代わりに目標状態を記述する方式(コピーしてから検証する、あるいは行き先を基準に判断する)へ変えなければならない。

7.3 sedの「行の追加」 - aコマンドはappendと同じ

sed -i '/^\[core\]$/a\    autocrlf = input' gitcfg.ini   # を3回

run1: [core]|    autocrlf = input|
run2: [core]|    autocrlf = input|    autocrlf = input|
run3: [core]|    autocrlf = input|    autocrlf = input|    autocrlf = input|

sedを使ったからといって置換になるわけではない。a(append)コマンドは名前のとおり追加なので、>>と性質が同じだ。安全な書き方は「あれば置換、無ければ挿入」の二分岐である。

if grep -q '^[[:space:]]*autocrlf[[:space:]]*=' f.ini; then
  sed -i 's/^[[:space:]]*autocrlf[[:space:]]*=.*/    autocrlf = input/' f.ini
else
  sed -i '/^\[core\]$/a\    autocrlf = input' f.ini
fi

run1 sha=94ff19468316c369 | [core]|    autocrlf = input|
run2 sha=94ff19468316c369 | [core]|    autocrlf = input|
run3 sha=94ff19468316c369 | [core]|    autocrlf = input|

7.4 タイムスタンプと乱数 - 冪等の検証そのものを不可能にする

ファイルの中にdateの出力や$RANDOMが入ると、そのファイルは回すたびにハッシュが変わる。ロジックが冪等かどうかとは無関係に検証の手段を失う。規則は単純だ。状態ファイルと監査ログを分離する。いつ何をしたのかは別のログに残し、スクリプトが管理する設定ファイルには決定的な内容だけを書く。

7.5 まとめ - 再実行安全性の3段階で見直す

  • mkdir -p、rm -fは①再実行安全までしか与えない。
  • grep -qxFの後のappend、ln -sfnは②結果の収束に到達する。
  • マーカーブロックの差し替えとファイル全体の生成は③自己修復まで行く。人がブロックの中を書き換えても元に戻す。
  • cp -r、mv、sed ... a\はどの層にも属さない。包まなければそのまま事故だ。

8. マーカーブロック - 三度回してもハッシュが同じになる理由

ここまでの防御策は行単位だった。管理する行が五つを超えると、この方式は急激に散らかる。そのときに使うのがマーカーブロックだ。Ansibleのblockinfileモジュールが既定値として# BEGIN ANSIBLE MANAGED BLOCKと# END ANSIBLE MANAGED BLOCKを使う、まさにあの方式である。

発想は単純だ。「自分が管理する区間」をマーカーで示し、その間を丸ごと差し替える。行ごとに存在を確認する必要が無くなる。

apply_block(){
  local file="$1" tag="$2" body="$3"
  local begin="# BEGIN ${tag}" end="# END ${tag}"
  [ -e "$file" ] || : > "$file"
  if grep -qxF "$begin" "$file"; then
    awk -v b="$begin" -v e="$end" -v body="$body" '
      $0==b { print b; printf "%s", body; skip=1; next }
      $0==e { print e; skip=0; next }
      skip==1 { next }
      { print }' "$file" > "$file.new" && mv "$file.new" "$file"
  else
    { printf '%s\n' "$begin"; printf '%s' "$body"; printf '%s\n' "$end"; } >> "$file"
  fi
}

人が手で管理している3行が既に入っているファイルに、この関数を3回適用した。

run1 sha256=5d22eee7c5ef0991451ca494fdff31a15f39c10ab6a1626136c7d990f0beb8b6
run2 sha256=5d22eee7c5ef0991451ca494fdff31a15f39c10ab6a1626136c7d990f0beb8b6
run3 sha256=5d22eee7c5ef0991451ca494fdff31a15f39c10ab6a1626136c7d990f0beb8b6
-- resulting file --
# hand-maintained section
Port 22
PermitRootLogin no
# BEGIN braindetox-keepalive
ClientAliveInterval 60
ClientAliveCountMax 3
# END braindetox-keepalive
OK: the hand-maintained 3 lines are untouched

3回実行のハッシュが完全に同一で、マーカーの外にある既存の設定は壊れていない。これが②結果の収束だ。

8.1 値が変わればブロックだけが更新される

## value change updates the block in place (60 -> 30, 3 more runs)
run4 sha256=1a402ffc0e2c088220b5e90471c69c330f6e4925ab579c3f0db1dc17271f3b18
run5 sha256=1a402ffc0e2c088220b5e90471c69c330f6e4925ab579c3f0db1dc17271f3b18
run6 sha256=1a402ffc0e2c088220b5e90471c69c330f6e4925ab579c3f0db1dc17271f3b18
total lines: 7 (no accumulation)

新しい値で新しいハッシュに再び固定される。行数は7のまま保たれる。ブロックが積み上がらない。

8.2 append方式に絶対できないこと - 項目の削除

ここがマーカーブロックの真価だ。管理する項目を2行から1行へ減らしてみよう。

# BEGIN braindetox-keepalive
ClientAliveInterval 30
# END braindetox-keepalive
  -> append-based approaches cannot do this: a removed entry would linger

ClientAliveCountMaxが消えた。「存在すればスキップ」方式ではこれが不可能だ。スクリプトからその行を消しても、既に配布されたサーバーのファイルには永遠に残る。何年か経つと、誰も理由を知らない設定がサーバーごとに違う形で溜まっていく。マーカーブロックはブロック全体がそのまま宣言なので、この問題が構造的に発生しない。

8.3 マーカーブロックを使うときの注意点

  • タグは固有に取る。同じファイルに複数のスクリプトがブロックを入れることがある。# BEGIN myapp-nginx-upstreamのように所有者と用途を併記する。
  • コメント文字はファイルごとに違う。#ではなく;や//を使う形式なら、マーカーもその文法に従わなければならない。そうしないとパーサーが落ちる。
  • マーカーを人が消すと次の実行でブロックが新しく追加され、重複が生じる。「触らないでください」という案内をブロックの先頭行に一緒に入れておくと役に立つ。
  • 構造のある形式(JSON・YAML)には使わない。行ベースの挿入はこうした形式を壊す。専用のパーサーで読み書きする必要がある。
  • ブロックの中だけを管理する。スクリプトがマーカーの外を触り始めると、このパターンの利点は消える。

9. 再実行を証明する方法 - 状態ハッシュとdry-run

「冪等に書いた」という主張は検証できなければならない。最も安い方法は対象ツリー全体をハッシュ一つに畳むことだ。

state_hash(){
  ( cd "$1" && {
      find . -type f | LC_ALL=C sort | xargs sha256sum
      find . -type l | LC_ALL=C sort | while read -r l; do echo "$(readlink "$l")  $l"; done
    } | sha256sum | awk '{print $1}' )
}

通常のファイルは内容のハッシュで、シンボリックリンクはreadlinkの結果で畳む。LC_ALL=C sortで並び順を固定するのが重要だ。ロケールによって順序が変われば、ハッシュも変わる。プロビジョニング関数を3回回した結果である。

provision run1  state_hash=219dd1b402f930f92ce94faa467761005c47cb12d740c452e7609d3d6d0d4526
provision run2  state_hash=219dd1b402f930f92ce94faa467761005c47cb12d740c452e7609d3d6d0d4526
provision run3  state_hash=219dd1b402f930f92ce94faa467761005c47cb12d740c452e7609d3d6d0d4526

9.1 ドリフトを入れて回し直すと - 正直な結果

ここで都合の悪い結果が一つ出たので、そのまま載せる。状態をわざとずらしてから再実行した。

after drift   state_hash=74c1a29f825801f98c4d235c47df56ad943e386df4697f5ffd3b1709e7d3785b
after re-run  state_hash=3e25756382253f698945962c75d2fd19bc1455d5dc20b79aa672057b3220cb81
-- app.env --
MODE=production
TZ=Asia/Seoul
MODE=debug

再実行の後のハッシュが元の値(219dd1...)に戻らなかった。何が復旧して何が残ったのかを見てみよう。

  • 復旧した - 人が作ったobsolete.confはrm -fで消えた。
  • 復旧した - currentシンボリックリンクはln -sfnでreleases/v2を指し直した。
  • 残った - 人が手で入れたMODE=debugの行はそのまま残った。

理由ははっきりしている。grep -qxF ... || append方式は「自分が望む行があるか」だけを尋ね、「自分が望まない行があるか」は尋ねない。つまり②結果の収束には到達したが、③自己修復ではない。アプリがファイルを後の行を優先して読むなら、このサーバーはproductionだと宣言しておきながらdebugで動く。

これを防ぐにはappendを捨ててファイル全体かマーカーブロックを宣言しなければならない。再実行の検証を「ハッシュが3回同じ」で止めると、この穴が見えない。ドリフトをわざと入れて回してみる手順が必要な理由だ。

9.2 dry-run - 変える前に何が変わるかを見る

運用で実際によく使うのは、ハッシュより試験実行だ。--checkモードは二つを与える。何が変わるかを先に見ることと収束したかを判定することである。

-- --check (nothing exists yet) --
  would add to app.env: MODE=production
  would add to app.env: TZ=Asia/Seoul
  changed=1
-- apply --
  changed=1
-- --check again --
  changed=0 (already at target state)

二度目の--checkがchanged=0を返す。これが冪等性の運用上の定義だ。「二度目の実行で変えるものが無いと自分で言えるか」。CIに入れるのも簡単だ。適用の直後に--checkをもう一度回してchanged=1が出たら、そのスクリプトは収束していないのでビルドを落とせばよい。

実装の核心はすべての変更を一つの関数に集めることだ。上の例ではwant_line一つだけがCHECKフラグを見ればよいようにした。変更の箇所がコードのあちこちに散らばっていると、dry-runは維持されない。

10. 部分的な失敗からの再開 - ステップマーカーとその罠

序論の問いに戻ろう。8段階のうち5段階で落ちたときどうするべきか。

10.1 悪い設計 - 前の段階が冪等でなければ永久に通過できない

-- bad.sh run 1 (forced failure) --
  step 3 failed
exit=3
-- remove the cause, run 2 --
mkdir: cannot create directory 'rbad/data': File exists
exit=1  <- blocked at step 1 forever

失敗の原因を直したのに1段階で止まる。この状態で運用担当にできることは、スクリプトを開いて前半をコメントアウトして回すことだけだ。その瞬間、「スクリプトでデプロイする」という前提が崩れる。

10.2 良い設計 - 各段階を冪等に + 完了マーカー

run_step(){
  local name="$1"; shift
  if [ -f "$S/$name.done" ]; then echo "  [skip] $name"; return 0; fi
  "$@" && : > "$S/$name.done" && echo "  [done] $name"
}
run_step schema s1 && run_step seed s2 && run_step release s3
-- good.sh run 1 (step 3 fails) --
  [done] schema
  [done] seed
   markers: schema.done seed.done
-- remove the cause, run 2 --
  [skip] schema
  [skip] seed
  [done] release
  completed
-- run 3 (should do nothing) --
  [skip] schema
  [skip] seed
  [skip] release
  completed
seed.csv lines: 1 | version: v1

2回目は失敗した地点から続けて完走し、3回目は何もせずに完走した。seed.csvが1行なのも重要だ。各段階そのものが冪等なので、マーカーが無くても安全である。

10.3 ステップマーカーの罠 - マーカーは収束を保証しない

このパターンには罠がある。人が成果物を消してから再実行してみた。

a human deleted 'version'; re-run:
  [skip] schema
  [skip] seed
  [skip] release
  completed
version present? no - the marker made it skip

スクリプトは「完走」と報告したのに、成果物は無い。マーカーだけを見て実際の状態を見なかったからだ。ここから出てくる原則ははっきりしている。

  • ステップマーカーは再開の速度最適化であって、収束の保証ではない。重い段階(大容量のダウンロード、マイグレーション)を飛ばす用途にだけ使う。
  • 軽い段階にはマーカーを付けない。毎回確認するほうが安全で、コストも無い。
  • マーカーは入力が変われば無効化する。ファイル名に入力のハッシュを入れれば(release.$(sha256 of config).done)、設定が変わったときに自動で再実行される。
  • 最後には状態を直接検証する。マーカーとは無関係に[ -f "$R/version" ]のような最終確認を付ける。
  • マーカーの保存場所を慎重に決める。対象のサーバーに置けばサーバー交換のときに消え、中央に置けばサーバーごとの状態を反映できない。

11. ロックが必要な条件、必要ない条件

ここまでのすべての防御策には共通の前提があった。一度に一つだけ走るということ。この前提が崩れると「確認してから変更」そのものが崩れる。いわゆるcheck-then-act問題だ。

11.1 再現 - 8つが同時に「無ければ作る」

round1: no lock SEED=5 | mkdir lock SEED=1 (expected 1)
round2: no lock SEED=4 | mkdir lock SEED=1 (expected 1)
round3: no lock SEED=4 | mkdir lock SEED=1 (expected 1)
round4: no lock SEED=5 | mkdir lock SEED=1 (expected 1)
round5: no lock SEED=4 | mkdir lock SEED=1 (expected 1)

5回の繰り返しすべてで4本から5本の行ができた。期待値は1である。grepで確認する瞬間と>>で追加する瞬間の間に、他のプロセスが割り込んだからだ。前の節であれだけ念入りに作ったgrep -qxF || appendが、同時実行の前では無力である。

実際にこういう状況がいつ起きるのかが重要だ。cronの周期が5分なのに実行に6分かかるとき、デプロイのパイプラインがリトライで同じジョブを二度立ち上げるとき、複数のノードが共有ストレージの同じファイルを触るときだ。三つとも珍しくない。

11.2 ロックが必要ない場合 - 全体の差し替え

すべての場合にロックが必要なわけではない。ファイル全体を一時ファイルに書いてからmvで差し替える方式は、8つが同時に押し寄せても無事だった。

printf 'value=42\n' > ".atomic.$i.tmp" && mv ".atomic.$i.tmp" atomic.txt

lines=1 | content=value=42 | sha=72cc615c7f451bd5

根拠はrename(2)の保証だ。マニュアルは「newpathが既に存在する場合は原子的に置き換えられ、他のプロセスがnewpathへアクセスしようとするときに、それが存在しない時点は存在しない」と記す。一時ファイルと行き先が同じファイルシステムにあること、という条件だけ守ればよい(別のファイルシステムならコピーになり、原子性が崩れる)。

11.3 ロックが必ず必要な場合 - 読んで直して書き戻す

### 8 processes increment count by 1 concurrently
final count=2  (expected count=8)

8回の加算が2回に失われた。読んだ値が書く前に古くなる、典型的な更新の喪失だ。判断表にまとめるとこうなる。

作業の形ロックの要否理由代替
ファイル全体を書き直して差し替え不要renameが原子的一時ファイル + mv(同じファイルシステム)
ディレクトリの作成 mkdir -p不要カーネルが原子的に処理そのまま使う
行の存在を確認してからappend必要検査と変更の間に隙間ロック、または全体の差し替えへ切り替え
読んで直して書き戻す(カウンター・一覧)必要更新の喪失ロック、またはappend-onlyの後に集計
長時間ジョブの二重起動の防止必要周期より実行が長くなり得るジョブの入口でロックを取得
マーカーブロックの差し替え必要読んで直して書き戻す構造ロック + 一時ファイルmvの併用

11.4 何でロックするか

Linuxならutil-linuxのflockが標準的な選択だ。マニュアルはスクリプト自身をロックする慣用句を示している。

[ "${FLOCKER}" != "$0" ] && exec env FLOCKER="$0" flock -en "$0" "$0" "$@" || :

-n(非ブロッキング)でロックを取れなければ、既定の終了コード1を返す(-Eで変更できる)。cronに入れるときは、この値を「正常な二重起動の防止」として扱うのか「失敗」と見るのかを決めておかないと、通知が騒がしくなる。

flockが無い環境ならmkdirの原子性を使える。今回の再現で、5回すべて正確に1行を保った方式だ。

if mkdir "$LOCKDIR" 2>/dev/null; then
  trap 'rmdir "$LOCKDIR"' EXIT INT TERM
  ... クリティカルセクション ...
else
  echo "他のインスタンスが実行中"; exit 0
fi
  • trapで必ず解放する。入れないと異常終了のときにロックが残り、次の実行が永遠に塞がれる。
  • ロックのディレクトリにPIDと時刻を残す。残ったロックが生きているプロセスのものかを判断する根拠になる。
  • 孤児ロックの回収方針を決める。時間を基準に自動で回収すれば楽だが、遅いだけの正常な実行を殺す危険がある。
  • NFSなどネットワークファイルシステムではロックの意味が変わる。複数のノードが参加するなら、ファイルロックではなく専用の調整手段を検討する。
  • ロックは冪等性の代替品ではない。ロックは同時実行だけを防ぐ。逐次の再実行で壊れるコードは、ロックを掛けても依然として壊れる。

12. コマンド別 安全な書き方の対照表

ここまで再現した内容を一枚に畳んだ。スクリプトを書いていて手が止まったとき、この表だけ見ればよい。

結論: 冪等性は性格ではなく設計だ

この記事で再現した事故には共通点がある。大半がエラーを出さない。ln -sfは0を返して古いバージョンを提供し続け、sed -iは0を返して何もせず、コメントに引っかかったgrep -qFは数か月にわたって設定を適用しなかった。終了コードが0であることと、目標状態に到達したことは別の話だ。この一文だけ残しても、この記事は元が取れる。

だから実務の規則は三行に縮む。第一に、「このコマンドが既に済んだ状態で実行されたら何をするのか」を行ごとに問う。事故の大半は、この問いを一度もしないことから生まれる。第二に、「やったか」ではなく「目標状態か」を検査する。作業の履歴ではなく、現在の状態が基準だ。第三に、主張せずに証明する。三度回してハッシュを比べるのにかかる時間は1分で、その1分が午前3時の2時間を節約する。

規模が大きくなれば、結局Ansibleのような道具へ行き着く。その道具たちが「冪等だ」と言っているものの正体こそ、この記事で手作りしたものだ。lineinfileは存在を確認してからの変更であり、blockinfileはマーカーブロック、--checkはdry-run、changedの値は収束したかどうかである。道具を使っても、この原理を知らなければshellモジュール一行で同じ事故を起こす。実際、道具を導入した後も事故が続く組織は、たいていこの地点にいる。

最後に、今日できることを一つ。最も頻繁に回っているスクリプトを一時ディレクトリで三度回し、状態ハッシュを出してみること。三つの値が違うなら、そのスクリプトは既に毎日少しずつ何かを変え続けている。まだ誰も気づいていないだけだ。

# 冪等スクリプト チェックリスト — 書く前に目を通す一覧

> 出典: braindetox.kr — 二度実行しても壊れないスクリプト
> 根拠: POSIX Issue 8 (mkdir/rm), GNU coreutils (ln -n), rename(2), flock(1)
> このファイルをそのままAIに貼って「うちのスクリプトをこの基準で直して」と書けます。

## 1. コマンド別の安全な形 — そのまま貼る形

| やりたいこと | この形で書く |
|---|---|
| ディレクトリ作成 | `mkdir -p "$D"` + 権限は `chmod 0750 "$D"` を別行で |
| ファイル削除 | `rm -f "$F"`（ディレクトリなら `rm -rf` — 変数の防御必須） |
| 行の追加 | `grep -qxF -- "$L" "$F" \|\| printf '%s\n' "$L" >> "$F"` |
| 行の削除 | `grep -vxF -- "$L" "$F" > "$F.t" && mv "$F.t" "$F"` |
| シンボリックリンク | `ln -sfn "$TARGET" "$LINK"` |
| 値の置換 | `grep -qxF "$WANT" "$F" \|\| sed -i "s#^$OLD\$#$WANT#" "$F"` |
| 行の挿入 | あれば `sed -i 's/^key=.*/key=v/'`、なければ `a\` で分岐 |
| cron 登録 | `{ crontab -l 2>/dev/null \| grep -vF "$ABS_PATH"; echo "$JOB"; } \| crontab -` |
| ディレクトリ複製 | `cp -r "$SRC/." "$DST/"`（`cp -r src dst` ではない） |
| ファイル移動 | `[ -e "$S" ] && mv "$S" "$D"` |
| ファイル全体の書き込み | `... > "$F.tmp" && mv "$F.tmp" "$F"`（同一ファイルシステム） |

## 2. 書く前の自問（一行ずつ）
- [ ] この行は**すでに済んだ状態**で実行されたら何をするか
- [ ] 「やったか」ではなく**「目標状態か」**を検査しているか
- [ ] `grep` の確認に `-x`（行全体）と `-F`（固定文字列）が両方あるか
- [ ] `grep` の終了コード **2（エラー）** を 1（不一致）と区別しているか
- [ ] `sed` の置換結果が**パターンに再び一致**しないか
- [ ] `sed -i` の終了コードを「適用された」の根拠にしていないか
- [ ] シンボリックリンクの張り替えに **`-n`** が付いているか
- [ ] `set -e` の下で前段の失敗が**後続を丸ごと飲み込んで**いないか
- [ ] ファイルに**タイムスタンプ・乱数**を入れてハッシュ比較を潰していないか
- [ ] 管理項目を**減らしたとき**、配布済みのファイルからも消えるか

## 3. マーカーブロック テンプレート — 管理行が5本を超えたらこれ

```bash
apply_block(){                     # apply_block <ファイル> <タグ> <本文>
  local file="$1" tag="$2" body="$3"
  local begin="# BEGIN ${tag}" end="# END ${tag}"
  [ -e "$file" ] || : > "$file"
  if grep -qxF "$begin" "$file"; then
    awk -v b="$begin" -v e="$end" -v body="$body" '
      $0==b { print b; printf "%s", body; skip=1; next }
      $0==e { print e; skip=0; next }
      skip==1 { next }
      { print }' "$file" > "$file.new" && mv "$file.new" "$file"
  else
    { printf '%s\n' "$begin"; printf '%s' "$body"; printf '%s\n' "$end"; } >> "$file"
  fi
}
apply_block /etc/ssh/sshd_config "myapp-keepalive" \
  $'ClientAliveInterval 30\nClientAliveCountMax 3\n'
```

- [ ] タグに**所有者と用途**を入れた（`myapp-nginx-upstream`）
- [ ] ファイルの**コメント文字**に合わせた（`#` / `;` / `//`）
- [ ] JSON・YAML など**構造のある形式には使わない**
- [ ] スクリプトが**マーカーの外に触れない**

## 4. 再実行の検証手順 — コミット前の1分

```bash
state_hash(){
  ( cd "$1" && {
      find . -type f | LC_ALL=C sort | xargs sha256sum
      find . -type l | LC_ALL=C sort | while read -r l; do echo "$(readlink "$l")  $l"; done
    } | sha256sum | awk '{print $1}' )
}
for i in 1 2 3; do ./provision.sh "$ROOT"; echo "run$i $(state_hash "$ROOT")"; done
```

- [ ] 3回のハッシュが**すべて同じ**（違えばどこかで累積している）
- [ ] `LC_ALL=C sort` で並び順を固定した
- [ ] **わざとドリフトを入れて**再実行した（設定を1行追加・リンク張り替え・余分なファイル）
- [ ] `--check` の2回目が **changed=0** を返す
- [ ] 試験は**一時ディレクトリ**でのみ行った

## 5. ロックが必要な条件

| 状況 | ロック | 代替 |
|---|---|---|
| ファイル全体の置換 | 不要 | 一時ファイル + `mv` |
| `mkdir -p` | 不要 | そのまま |
| 確認してから追記 | **必要** | 全体置換に切り替える |
| 読んで直して書く | **必要** | 追記のみにして後で集計 |
| 周期より長いcronジョブ | **必要** | 入口でロック取得 |
| マーカーブロック置換 | **必要** | ロック + 一時ファイル `mv` |

```bash
# flock がある場合
[ "${FLOCKER}" != "$0" ] && exec env FLOCKER="$0" flock -en "$0" "$0" "$@" || :

# ない場合は mkdir の原子性を使う
if mkdir "$LOCKDIR" 2>/dev/null; then
  trap 'rmdir "$LOCKDIR"' EXIT INT TERM
else
  echo "別のインスタンスが実行中"; exit 0
fi
```

- [ ] `trap` で必ずロックを解放する
- [ ] ロックディレクトリに **PID・時刻**を残す
- [ ] **取り残しロックの回収方針**を決めた
- [ ] ロックは**同時実行だけ**を防ぐ — 逐次再実行の欠陥はそのまま残る

## 6. 部分失敗からの再開
- [ ] 各ステップが**それ自体で冪等**（目印がなくても安全）
- [ ] 目印は**重い工程だけ**に付ける
- [ ] 目印の名前に**入力ハッシュ**を入れ、設定変更で自動的に無効化する
- [ ] 最後は目印ではなく**実際の状態**を検証する
