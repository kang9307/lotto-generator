npm 314个包遭入侵事件 - 22分钟内发布637个恶意版本,2026供应链攻击分析与防御指南

22分钟内npm上发生的事件,以及开发团队今日应执行的11项行动

2026年5月22日 IT/技术

引言: 22分钟内发生的事 - npm生态系统的定时炸弹

2026年5月,npm注册表中314个正常包在仅22分钟内被637个恶意版本一次性覆盖的事件被报告。换算到每分钟,约有29个恶意版本被推送。这是人工操作绝对无法达到的速度,可以确定是预先准备的自动化脚本利用维护者凭据和令牌集中一次性执行publish。"22分钟"本身就是本次事件的核心,它清晰地展示了JavaScript生态系统对维护者单一凭据这一单点失败的暴露程度。

这并非孤立事件。如本文所整理,npm在2018年的event-stream、2021年的ua-parser-js、2022年的colors/faker、2024年的lottiefiles事件中几乎每年都经历大型供应链事故,每次都重复类似的结构。2026年的不同之处在于自动化批量发布的精度和影响范围。314个包中很多深嵌于其他包的依赖关系中,即使你从未听说过这些名字也可能受到影响。

本文以news.hada.io 5月21日的5分文章为起点,基于笔者的运维经验,整理JavaScript开发团队今日内应执行的4项紧急应急措施和7项长期防御策略。重点不在事件的技术细节,而在中文开发环境中可立即应用的行动。

事件概述 - 发生了什么、何时、如何

按时间顺序梳理目前已报告的事件轮廓。本文不直译安全advisory,而以笔者的视角重新组织公开信息。

  • 时间: 2026年5月中旬,约22分钟的短时间窗口。
  • 规模: 涉及314个npm包,共发布637个恶意版本。
  • 速度: 平均每分钟约29个版本推送,确认为自动化脚本而非人工操作。
  • 推测入侵路径: 预先收集多位维护者的npm publish令牌或凭据 → 自动化批量发布。
  • 恶意代码性质: 多数报告显示通过postinstall脚本或构建时环境变量泄露收集令牌和密钥。
  • 检测与响应: 安全社区和npm方快速封禁,大部分版本在发布后数小时内被unpublish。

值得关注的是"22分钟"这一短时间窗口。这是有意的设计。太短则在安全监控触发之前结束,适度长则世界各地多个CI流水线在该时段刚好获取并应用新版本,被害面自然增加。22分钟接近这一平衡点。

攻击机制分析 - 凭据入侵 + 自动化批量发布

本次事件的技术核心不是华丽的零日漏洞,而是"窃取的凭据 + 自动化"这一非常平凡的组合。平凡正是核心,这意味着npm生态系统的认证发布模型存在单点失败,以至于不需要华丽的漏洞就能造成大规模影响。

1) 凭据收集阶段(事前准备)

攻击者似乎在事件发生前的数月通过各种渠道收集了npm令牌、邮箱、绕过OTP的会话cookie。收集渠道包括钓鱼、维护者PC恶意软件、过去泄露数据的复用、.npmrc文件意外公开等。即便启用了2FA,如果令牌本身泄露仍可被绕过,因此即使多位维护者启用了2FA,攻击本身仍可能成功。

2) 批量发布阶段(22分钟窗口)

攻击者使用收集的凭据,将预先准备的恶意变体批量publish到314个包。通过自动化调用npm publish API,每分钟数十次publish完全可行。22分钟内发布637个版本与此推测一致。批量发布时间很可能选在维护者们不同时在线的时段。

3) 载荷执行阶段(受害方)

多数恶意版本通过postinstall钩子运行,或在构建时收集环境变量发送到外部服务器。在中国企业环境中,这一阶段的威胁分两类。(a) 本地开发PC入侵: 开发者不经意运行npm install后令牌、cookie泄露。(b) CI/CD入侵: GitHub Actions或公司Jenkins在构建时密钥外泄。CI令牌通常权限范围较广,从笔者视角来看后者更危险。

类似事件的历史 - 同样结构反复出现

npm供应链攻击并非首次。整理笔者印象较深的主要事件如下。

  • 2018 event-stream: 维护者更替后新维护者植入恶意载荷,影响比特币钱包库。首次让公众了解到"信任转让"是单点失败。
  • 2021 ua-parser-js: 维护者账户被入侵后发布恶意版本。该包下载量极高,影响范围极广。
  • 2022 colors/faker: 维护者本人故意破坏代码。再次提醒"信任是自愿合作"。
  • 2023 typosquatting多发: 大量与热门包名仅差一个字符的恶意包被注册。
  • 2024 lottiefiles等: 通过SDK包入侵试图窃取用户令牌和钱包信息。
  • 2026年5月 314个包一次性入侵: 本次事件,规模和速度都进入新阶段。

这份清单的模式明确: 每次"维护者凭据"被攻破,每次以相同方式被npm基础设施允许发布。每次事件都有临时应对,但结构性解决方案的引入依然缓慢。provenance、sigstore等长期方案虽已问世,但采用率仍然偏低。

为什么npm反复被攻击 - 5个结构性弱点

1) 单一维护者模型

npm大多数包由1~2位维护者运营。这一人的凭据被攻破,数百万下载量级的包就会直接暴露。PyPI、crates.io等其他注册表也是类似结构,但npm的平均依赖深度最深,放大效应最大。

2) 深度依赖树

你的项目直接依赖10个包,展开依赖树后实际安装的包通常超过1000个。这意味着你听都没听过的包能在你的构建环境中执行任意代码。

3) postinstall钩子的任意代码执行

npm允许在postinstall时运行任意脚本。虽然有合法用途(如原生构建),但对攻击者来说也是载荷自动执行的通道。部分其他包管理器默认禁用此钩子。

4) 维护者信任转让的无防护

维护者将包交给他人的流程实际上只是一封邮件。对新维护者的身份、履历、恶意意图缺乏强验证,用户也无法自动获知。

5) provenance采用速度缓慢

npm provenance虽于2023年引入,但热门包采用率仍处于个位数到十位数初期。如果全员采用,本次这类事件的攻击面会大幅缩小,但瓶颈在于维护者侧缺乏引入动机。

今日内应执行的4项紧急应急措施

本节是本文最贴近实务的部分。中文开发团队应在今日(最迟本周)内处理的4项工作。

1) 立即检查可疑包 - npm audit

首先在所有活跃项目中执行以下命令。

npm audit --audit-level=high
npm audit signatures   # provenance/签名验证
npm outdated

npm audit signatures是相对少为人知的命令,用于验证包的npm签名和provenance有效性。如有在事件发生前后24~48小时内接收的包,使用该命令再次确认。

2) lock文件变更历史验证

用git历史查看package-lock.json或yarn.lock的最近变更。

git log --since="2026-05-20" -- package-lock.json
git diff HEAD~5 -- package-lock.json | grep -E "^\+.*\"version\""

如果在可疑时间点lock文件发生变更,需将该版本与npm官方advisory对照确认是否正规。开发者不经意执行npm install后将lock文件一并提交的情况常见,因此需要按PR单位排查。

3) 立即失效构建缓存

清除本地、CI、企业内部npm镜像中可能缓存的恶意版本。

npm cache clean --force
rm -rf node_modules
npm ci   # 基于frozen lockfile的干净重装

GitHub Actions的actions/cache、GitLab CI cache、内部Nexus/Verdaccio镜像也要一并失效。如果缓存中残留恶意版本,所有应急措施都失去意义。

4) 立即轮换可能泄露的令牌和密钥

postinstall载荷的主要目标是环境变量、令牌、cookie。以下项目若在5月21日之后任意一次出现在构建中,均应轮换。

  • npm publish令牌(若CI中使用最优先)
  • GitHub PAT和Actions OIDC令牌
  • AWS、GCP、Azure访问密钥
  • Slack、Discord webhook URL
  • 数据库连接字符串、内部API密钥

轮换工作虽然繁琐,但单个令牌的成本相比一次入侵事件的成本可以忽略不计。如果有任何曾以明文出现在构建环境中的密钥,趁此机会全部重新生成。

7项长期防御策略 - 阻止下一次事件的系统

1) 使用npm provenance

如果你自己向npm发布包,请立即启用provenance。在GitHub Actions中,只需添加permissions: id-token: write并将npm publish改为npm publish --provenance即可启用。在使用方,可用npm audit signatures强制要求provenance。

2) 强制Frozen lockfile(--frozen-lockfile / npm ci)

本地可以用npm install,但CI中必须强制使用npm ci或yarn install --frozen-lockfile。lock文件不一致则构建失败的门禁是核心。仅此一项就能基本阻断"夜间有人发布新版本而你的CI悄悄获取"的路径。

3) SBOM生成与管理

每次构建自动生成SBOM(软件物料清单)并存档。格式可选CycloneDX或SPDX。使用cyclonedx-bom或@cyclonedx/cyclonedx-npm等工具,1分钟内即可引入。有SBOM后,下一次事件发生时,"我们是否用了那个包"5分钟内即可回答。

4) 引入Dependabot / Renovate

依赖更新不靠人的意志,而以自动PR的形式完成。但绝不开启自动合并。生成PR即强制了人工审查环节。审查时通过npm view查看新版本的维护者、发布时间、下载趋势。

5) 定期依赖审计周期

每季度举行一次依赖审计会议。议题三项: (a) 移除不再使用的包,(b) 替换deprecated包,(c) 评估维护者活动停滞的包是否需要fork或替换。笔者经验,这一小时能将1年后事故响应时间缩短百倍。

6) 极简依赖策略

将"为这一功能添加100行的包是否值得"作为PR审查阶段的必问问题。坐标库、字符串工具、日期格式等小功能很多时候10~30行自有代码就够用。依赖越少,攻击面越小。

7) 引入基于行为的扫描器(Socket.dev、Phylum等)

传统npm audit对照已知advisory,而Socket.dev、Phylum等工具基于行为检测包代码中的可疑行为(网络调用、eval、postinstall模式等)。捕获未知新型入侵的概率更高。以PR评论形式集成到CI是中文团队中最顺滑的引入方式。

CI/CD流水线强化 - GitHub Actions示例

将以上7项策略组装到实际GitHub Actions工作流中,形态如下。仅摘录关键门禁。

name: secure-build
on: [push, pull_request]
permissions:
  contents: read
  id-token: write
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      # 1) frozen lockfile - lock不一致立即失败
      - run: npm ci

      # 2) audit门禁
      - run: npm audit --audit-level=high
      - run: npm audit signatures

      # 3) SBOM生成
      - run: npx @cyclonedx/cyclonedx-npm --output-file sbom.json
      - uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.json

      # 4) 行为扫描(Socket.dev示例)
      # - uses: socket-security/socket-cli-action@v1

      - run: npm test
      - run: npm run build

该工作流的核心是"任意一步失败,构建本身中断"。不将应急响应交给人的意志,而是以CI门禁系统化,是本文最后的关键信息。

监控工具对比 - Snyk、Socket.dev、Phylum、npm audit

实务中常被对比的工具,从笔者视角整理如下。

工具检测方式优势不足
npm audit已知advisory对照免费,内置零日和行为检测薄弱
Snykadvisory+许可证+部分行为UI/报表优秀,企业功能丰富核心功能在付费版
Socket.dev行为(eval/postinstall/网络)可检测未知入侵,PR评论UX佳有假阳性,中文案例较少
Phylum行为+维护者声誉维护者身份分析引入曲线略陡
GitHub Dependabotadvisory+自动PRGitHub原生集成,免费更接近更新而非检测

对中文团队的推荐组合: (1) 基础是npm audit + Dependabot(免费,立即引入)。(2) 在此之上将Socket.dev或Snyk其一作为PR评审阶段辅助门禁。(3) 时间允许时加上Phylum看维护者声誉,构成三层结构。

中国企业和创业环境的应用

将上述策略迁移到中国环境时,笔者常遇到的摩擦点整理如下。

  • 创业公司: 通常没有专职安全人员。仅免费工具(npm audit、Dependabot、Socket.dev免费版)就能覆盖80%风险,先引入再说。不追求完美,以"开始做以前没做的事"为目标。
  • 中大型企业: 如果有公司内部npm镜像(Nexus、Verdaccio),在镜像层直接配置allowlist/blocklist。紧急事件时在镜像处封禁可同时影响全体开发者。
  • 金融/政务: 即使是网络隔离环境,通过npm镜像引入外部包的路径也相同。将SBOM和签名验证作为公司内部标准更有效。
  • 自由开发者/个人: 你的PC就是基础设施。立即放弃将令牌以明文存放在.env的习惯,引入1Password CLI或doppler等密钥管理工具。

开发者个人责任的边界与生态系统责任

即便完整执行本文整理的11项(应急4+长期7),供应链攻击也无法100%被阻止。这是现实。个人和团队层面的努力存在明确边界,超出这一边界的是生态系统级别的变化。

笔者认为生态系统的责任有三点: (1) npm Inc.(GitHub)对维护者安全认证的强化 - 强制WebAuthn和硬件密钥。(2) 针对热门包提高provenance采用率的激励。(3) 提供postinstall钩子默认禁用选项。这些都不是个人努力能解决的部分,需要npm/GitHub的政策变更。

2026下半年供应链安全趋势 - 笔者预测

笔者预测的2026下半年供应链安全走向。

  • provenance采用加速: 热门包维护者在事件后自发引入的可能性。采用率从个位数升至十位数中段的预期。
  • 行为扫描器的标准化: Socket.dev/Phylum以免费版为中心扩散。
  • SBOM义务化的趋势: 受美国EO 14028走向影响,中国政务/金融招投标中SBOM要求可能增加。
  • AI代码审查+依赖分析的结合: PR审查时AI以自然语言评论新依赖风险的流程。
  • npm以外注册表选项的关注上升: deno、jsr、bun自有注册表的关注上升。但短期取代npm困难。

结论 + 15项检查清单

本文核心一句总结: 供应链安全不是工具而是系统,系统由今日就能开始的小门禁累积而成。22分钟下次会更短。阻止下次22分钟的,是你团队的应急4项和长期7项的系统化。

最后分享笔者使用的15项检查清单。打印贴在桌边,一行一行处理。

  1. 对所有活跃项目执行npm audit --audit-level=high
  2. 执行npm audit signatures检查provenance/签名
  3. 用git核对5月20~22日lock文件变更历史
  4. 失效npm缓存、CI缓存、公司内部镜像缓存
  5. 轮换5月21日后曾在构建中暴露的所有令牌和密钥
  6. 最小化npm publish令牌的权限范围,设置过期时间
  7. 在CI中强制npm ci / --frozen-lockfile
  8. 在CI中将npm audit设为门禁(高危发现即失败)
  9. 引入SBOM生成工作流(推荐CycloneDX)
  10. 启用Dependabot或Renovate(不开自动合并)
  11. 在日历上注册每季度1次依赖审计会议
  12. 对自己发布的包启用npm provenance
  13. 引入Socket.dev或Snyk的免费版本
  14. 审查使用postinstall钩子的包白名单
  15. 运营公司内部npm镜像时制定allowlist/blocklist策略
