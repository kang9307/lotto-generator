왜 2026년에 로컬 단일 노드 S3를 다시 고민해야 하는가

현대 클라우드 네이티브 애플리케이션과 데이터 파이프라인 엔지니어링에서 객체 스토리지는 선택적 인프라가 아닌 필수 전제 조건입니다. AWS S3 API는 지난 10여 년간 사실상의 글로벌 표준 스토리지 프로토콜로 자리 잡았으며, 애플리케이션 프레임워크부터 데이터 분석 엔진에 이르기까지 수많은 시스템이 S3 API 호환 계층을 기본 인터페이스로 전제하고 개발됩니다. 특히 개발자 워크스테이션이나 지속적 통합(CI/CD) 러너 환경에서는 실제 클라우드 비용, 네트워크 지연, 보안 인증 문제를 우회하기 위해 로컬 머신에서 가볍게 띄울 수 있는 독립형 S3 에뮬레이션 스토리지의 필요성이 절실합니다.

최근 들어 Apache Iceberg, Delta Lake 같은 개방형 테이블 포맷과 DuckDB, ClickHouse 등의 현대적 임베디드 분석 쿼리 엔진이 로컬 개발 및 데이터 엔지니어링 파이프라인에 대거 도입되었습니다. 이제 개발자들은 로컬 환경에서 복잡한 파티셔닝, Parquet 데이터 파일 쓰기, 메타데이터 커밋과 스냅샷 관리가 원격 S3 버킷과 동일하게 동작하는지 검증하기를 원합니다. 이러한 검증 단계에서 로컬 S3 컨테이너는 전체 데이터 파이프라인의 성패를 가르는 출발점이 됩니다.

지난 수년간 이 영역의 압도적 표준은 MinIO였습니다. docker run 명령어 단 한 줄이나 Docker Compose의 서비스 정의 한 토막만으로 완벽한 S3 API 엔드포인트와 직관적인 웹 브라우저를 즉시 구동할 수 있었기 때문입니다. 수많은 오픈소스 프로젝트의 공식 튜토리얼, 핸즈온 데모, 기업의 CI 파이프라인 전체가 MinIO를 기본 축으로 삼아 설계되었습니다.

그러나 원문에 따르면, 2025년 말 MinIO 프로젝트를 운영하는 주체가 다른 상업적 사업을 추구하기로 결정하면서 프로젝트를 사실상 방치(abandon)하는 방향으로 급선회했습니다. 웹 기반 인터페이스인 Object Browser의 비공개 전환 논란, 공식 GitHub 저장소 이슈 댓글(Issue #21647), 그리고 코어 저장소의 급격한 커밋 변화를 통해 이러한 방향 전환이 명확히 드러났습니다. 이는 MinIO를 단일 노드 로컬 S3의 당연한 기본값으로 신뢰해 온 수많은 소프트웨어 데모와 호환성 검증 파이프라인에 즉각적인 혼란을 불러왔습니다. 이에 따라 기존 설정을 최대한 유지하면서도 최소한의 변경으로 가볍게 교체할 수 있는 실질적인 단일 노드 대안을 모색해야 하는 과제가 대두되었습니다.

평가 기준 3가지와 평가 제외 범위

로컬 개발 및 테스트용 S3를 선정하는 작업은 페타바이트급 데이터를 안전하게 보존하고 극도로 높은 내구성을 확보해야 하는 엔터프라이즈 프로덕션 분산 스토리지를 설계하는 작업과는 완전히 궤를 달리합니다. 분산 합의 알고리즘이나 디스크 페일오버의 정교함보다는, 개발자의 로컬 환경과 자동화 빌드 스크립트에서 얼마나 군더더기 없이 마찰 없이 기동되는가가 절대적인 평가 기준입니다.

필수 3대 조건: Docker·S3 호환·무료 오픈소스

원문에서 Robin Moffatt는 단일 노드 로컬 S3 교체 후보를 선별하기 위해 타협할 수 없는 세 가지 필수 조건을 엄격히 설정했습니다.

  • 공식 Docker 이미지 제공: 대부분의 현대적 개발자 데모와 로컬 실습 환경은 Docker Compose 파일 하나로 배포됩니다. 개발자가 직접 소스 코드를 클론하여 빌드 환경을 꾸리거나 별도의 전용 Dockerfile을 자체 제작해야 한다면 가벼운 로컬 도구로서의 가치가 급격히 떨어집니다. 레지스트리에서 즉시 풀링 가능한 공식 컨테이너 이미지가 반드시 존재해야 합니다.
  • S3 API 호환성: AWS SDK, boto3, s3cmd, 그리고 기존 MinIO CLI(mc) 등의 표준 클라이언트 도구가 클라이언트 측 코드 수정 없이 엔드포인트 URL과 키만 전달받아 버킷 생성, 객체 읽기/쓰기/삭제 작업을 완벽히 수행할 수 있어야 합니다.
  • 무료 및 오픈소스(OSI 정의 준수): 상업적 제약이나 숨겨진 라이선스 비용 없이 자유롭게 활용할 수 있어야 합니다. 특히 Apache 2.0 라이선스처럼 오픈소스 정의(OSD)에 완전하게 부합하는 영구적인 개방형 라이선스를 강력하게 선호합니다.

기준 검증 환경: DuckDB와 Iceberg REST Catalog 연동

도구의 적합성을 평가하기 위해 원저자는 현실적인 모던 데이터 엔지니어링 스택으로 기준 테스트베드를 구성했습니다. 단순한 텍스트 파일 몇 개를 올리고 내려받는 기본 스모크 테스트를 넘어, 실제 데이터 레이크하우스 아키텍처에서 발생하는 복잡한 메타데이터 조작과 Parquet 파일 입출력을 시뮬레이션했습니다.

기준 Docker Compose 구성과 파이프라인 흐름

기준 환경은 세 가지 핵심 컴포넌트의 유기적인 결합으로 이루어집니다.

  • 객체 스토리지 계층: 기준점 역할을 하는 MinIO 컨테이너 (대안 테스트 시 각 후보 컨테이너로 1:1 교체)
  • 카탈로그 계층: Apache Iceberg REST Catalog 서비스 컨테이너
  • 분석 쿼리 및 클라이언트 계층: DuckDB 및 MinIO Client(mc) CLI 컨테이너

이 구성에서 mc 컨테이너는 스토리지가 기동되면 가장 먼저 엔드포인트 헬스체크를 수행한 후 데이터를 저장할 타깃 버킷을 자동 생성합니다. 이어서 DuckDB는 Iceberg REST Catalog와 통신하며 S3 엔드포인트를 타깃으로 설정하고, Iceberg 포맷의 테이블을 생성한 뒤 샘플 데이터를 직접 INSERT합니다. 이 과정에서 순수 데이터는 압축된 Parquet 파일로 저장되며, 트랜잭션과 스키마 변경 이력은 Avro 및 JSON 메타데이터 파일로 버킷 내에 계층적으로 기록됩니다.

검증 절차(test.sh)와 mc CLI 활용

각 후보 스토리지의 유효성은 동일한 자동화 검증 스크립트인 test.sh를 통해 엄격하게 판정되었습니다.

  • 1단계: 스토리지 컨테이너 기동 후 HTTP 포트 응답 확인 및 타깃 S3 버킷 정상 생성 검증
  • 2단계: DuckDB 클라이언트가 Iceberg REST Catalog를 통해 테이블을 정의하고 레코드를 삽입하는 쓰기 작업 검증
  • 3단계: DuckDB에서 해당 Iceberg 테이블을 조회(SELECT)하여 데이터 일관성과 쿼리 결과 무결성 검증
  • 4단계: 스토리지 내부 파일 시스템에 기록된 Parquet 데이터 파일과 메타데이터 객체들의 실제 파일 경로 및 크기 확인

기존 데모 구성을 깨뜨리지 않는 것이 핵심 목표였으므로, 버킷을 초기화하는 도구로는 기존에 널리 쓰이던 mc CLI를 그대로 유지하여 하위 호환성을 시험했습니다. 만약 MinIO와 관련된 도구 자체를 프로젝트에서 완전히 배제하고자 한다면 표준 aws CLI나 s3cmd를 활용하여 버킷을 초기화하도록 스크립트를 변경할 수 있습니다.

즉시 채택 가능한 대안: S3Proxy와 SeaweedFS

원문의 실측 검증을 거쳐 단일 노드 로컬 S3 데모 환경에 가장 적합한 대안으로 최종 「Yes」 판정을 받은 프로젝트는 S3Proxy와 SeaweedFS 두 가지입니다.

S3Proxy 3.0.0: 단순성과 의존 프레임워크 은퇴

S3Proxy 3.0.0은 Apache 2.0 라이선스로 배포되는 자바 기반의 경량 S3 프록시 게이트웨이입니다. 로컬 파일 시스템이나 기존 스토리지 앞단에서 표준 S3 API 요청을 수신하여 로컬 디렉터리 구조로 매핑해 주는 역할을 합니다.

  • 구현의 극단적 단순성: S3Proxy의 가장 큰 강점은 단순함입니다. 복잡한 분산 데몬이나 메타데이터 데이터베이스가 필요 없으며, 공식 Docker 이미지(andrewgaul/s3proxy)에 환경 변수 몇 줄만 지정하면 곧바로 로컬 파일 시스템을 백엔드로 하는 S3 엔드포인트가 열립니다.
  • 실측 검증 결과: DuckDB와 Iceberg REST Catalog 연동 테스트에서 아무런 오류나 호환성 문제없이 모든 검증 단계를 완벽하게 통과했습니다.
  • 구조적 주의점: S3Proxy의 내부 스토리지 추상화 계층인 Apache jclouds 프로젝트가 2025년 중반 Apache Attic으로 이관되어 공식적으로 은퇴(Retirement)했습니다. 로컬 디렉터리를 매핑하는 기본 파일 시스템 프로바이더 기능은 여전히 잘 동작하지만, 장기적인 버그 수정과 상위 자바 런타임 호환성 측면에서 커뮤니티의 직접적인 유지보수가 필요해진 상태입니다.

실제 검증에 쓰인 Docker Compose 정의는 원문 저자의 저장소 rmoff/minio-alternatives의 s3proxy/docker-compose.yml에 공개돼 있습니다. S3Proxy 컨테이너와 버킷을 만드는 mc, Iceberg REST Catalog, DuckDB가 한 파일에 묶여 있어 내려받아 그대로 기동할 수 있습니다.

SeaweedFS 4.06: 검증된 안정성과 내장 UI 제공

SeaweedFS 4.06은 수십억 개의 작은 파일을 효율적으로 저장하도록 설계된 Go 언어 기반의 성숙한 분산 객체 스토리지입니다. 페이스북의 Haystack 아키텍처 논문을 모태로 발전하였으며, 2018년 v0.91 릴리스부터 공식 S3 API 호환 계층을 충실히 구현해 왔습니다.

  • 손쉬운 교체와 기본 웹 UI: 기존 MinIO 설정을 대체하기에 가장 매끄러운 경험을 제공합니다. 공식 컨테이너 이미지(chrislusf/seaweedfs) 하나로 마스터, 볼륨 스토리지, 필러(filer), 그리고 S3 게이트웨이를 동시에 기동할 수 있습니다. 특히 버킷 목록과 저장된 객체를 웹 브라우저로 확인할 수 있는 내장 관리 UI를 기본 탑재하고 있어 시각적 확인이 필요한 데모 환경에 매우 유리합니다.
  • 실측 검증 결과: weed mini 간이 모드를 기반으로 구성한 환경에서 DuckDB 및 Iceberg 테스트의 모든 단계(테이블 생성, 데이터 적재, 쿼리 조회)를 흠잡을 데 없이 통과했습니다.
  • 설정상의 과도기적 이슈: 원문 작성 당시에는 S3 접근 자격 증명을 설정하기 위해 별도의 설정 파일을 작성하여 Docker Compose 내에 인라인으로 주입해야 하는 번거로움이 있었습니다. 이에 대해 SeaweedFS 메인테이너는 원문 발행 당일 댓글로, 이 추가 요구 사항을 없애는 수정이 이미 끝났고 다음 주간 릴리스에 포함될 것이라고 답했습니다.
  • 오해하기 쉬운 외관: 공식 웹사이트에 접속하면 첫 화면에 Enterprise 브랜딩과 가격 메뉴가 노출되어 상용 솔루션으로 오해하기 쉬우나, 핵심 프로젝트 전체는 완전한 Apache 2.0 오픈소스로 유지되고 있습니다.

SeaweedFS 구성도 같은 저장소의 seaweedfs/docker-compose.yml에 있습니다. SeaweedFS 서버와 mc, Iceberg REST Catalog, DuckDB가 동일한 형태로 묶여 있어 S3Proxy 구성과 나란히 비교할 수 있습니다.

RustFS 1.0.0-alpha.79: 알파 단계와 보안 권고 사항

Rust 언어의 고성능과 메모리 안정성을 전면에 내세운 신생 오픈소스 객체 스토리지 프로젝트입니다. 현대적인 웹 대시보드와 Apache 2.0 라이선스를 갖추고 있습니다.

  • 장점: Docker Compose 파일 작성이 직관적이며 가벼운 메모리 점유율과 미려한 웹 대시보드를 기본 지원합니다.
  • 성숙도 한계: 평가 시점 기준 버전이 1.0.0-alpha.79로 여전히 알파 단계의 릴리스입니다. 공식 문서 웹사이트의 주요 링크들이 동일한 페이지로 순환 참조되는 등 프로젝트 전반에 아직 완성되지 않은 부분들이 다수 관찰되었습니다.
  • 보안 권고(Security Advisory): 최근 심각한 보안 취약점(Security Advisory GHSA-h956-rh7x-ppgj)이 공식 등록된 이력이 존재합니다. 외부 인터넷과 격리된 일회성 로컬 데모에서는 큰 위험이 아닐 수 있으나, 공용 네트워크에 노출되는 팀 공유 테스트베드에서는 도입을 주저하게 만드는 주요 요인입니다.

Zenko CloudServer 9.2.8: 기능 적합성과 브랜딩 혼선

스토리지 전문 기업인 Scality가 주도하는 오픈소스 프로젝트로, 과거 「S3 Server」라는 이름으로 널리 사용되었던 유서 깊은 S3 에뮬레이터입니다. 현재는 Zenko 멀티클라우드 오케스트레이션 도구 모음의 일부로 제공됩니다.

  • 장점: Apache 2.0 라이선스로 오랜 기간 유지되어 온 코드베이스 덕분에 S3 API 호환성이 매우 탄탄하며 MinIO의 대체 동작을 훌륭히 수행합니다.
  • 브랜딩 및 문서화 혼선: Scality, Zenko, CloudServer라는 명칭이 혼재되어 사용자가 실행해야 할 독립형 컨테이너 이미지를 판별하기 어렵습니다. 공식 문서가 가리키는 Docker Hub 레지스트리에는 오래된 구버전 이미지가 남아 있어 최신 이미지를 찾기 위해 GitHub 컨테이너 레지스트리를 별도로 확인해야 했습니다.
  • 스위트 종속에 대한 우려: 상위 제품군인 Zenko의 복잡한 멀티클라우드 관리 구조를 모두 이해해야 하는 것이 아닌가 하는 심리적 장벽이 존재합니다.

로컬 데모 목적에서 제외된 후보들: Garage, Apache Ozone, Ceph RGW

아래 솔루션들은 기술적 완성도가 떨어져서 배제된 것이 아닙니다. 오히려 분산 스토리지로서 매우 강력한 기능을 제공하지만, 「단일 컨테이너로 즉시 기동되는 로컬 데모 환경」이라는 이번 평가의 목적과 방향성이 맞지 않았기 때문입니다.

Garage 1.0.0: 엄격한 초기화 설정과 로컬 진입 장벽

Garage는 프랑스의 Deuxfleurs가 개발하고 유럽 NGI/NLnet 재단의 재정적 지원을 받는 Rust 기반 경량 분산 객체 스토리지입니다. AGPLv3 라이선스를 따르며 네트워크 지연이 심하고 이종 인프라가 섞인 엣지 환경에서 탁월한 복원력을 발휘하도록 정밀하게 설계되었습니다.

  • 설정 복잡도 장벽: 단일 컨테이너 하나로 즉시 서비스가 시작되는 MinIO와 달리, Garage는 초기화 과정이 매우 엄격합니다. 노드 등록, 토폴로지 레이아웃 승인, 버킷 생성, 키 할당 등의 과정을 수행하기 위해 별도의 초기화 컨테이너(garage-init)를 띄워야 했습니다.
  • 설정 파일 및 포맷 제약: Docker Compose 내에 인라인으로 주입해야 하는 상세한 TOML 설정 파일이 요구되며, API 접근 키 ID도 반드시 GK로 시작하는 12바이트 16진수 문자열이어야 하는 등 엄격한 규칙이 강제됩니다.
  • 프로덕션 분산 스토리지로서의 가치: 이러한 엄격함은 프로덕션 클러스터 운영에서는 데이터 손실을 원천 차단하는 강력한 무기가 됩니다. Garage의 아키텍처와 실제 분산 운영 모범 사례는 본 블로그의 Garage S3 스토리지 완전 가이드에서 상세히 다루고 있습니다. 다만 간단한 로컬 데모 목적에는 진입 장벽이 높았습니다. (참고로 최신 v2.3.0에서는 garage server --single-node --default-bucket 플래그가 추가되어 단일 노드 초기화가 대폭 간소화되었습니다.)

Apache Ozone과 Ceph RGW: 다중 노드 요구와 로컬 경량화의 한계

빅데이터 플랫폼과 대규모 프라이빗 클라우드 인프라를 지탱하는 엔터프라이즈급 분산 스토리지들은 로컬 단일 노드 환경에서 명확한 한계를 보였습니다.

  • Apache Ozone 2.1.0: 2020년 Apache Hadoop 생태계에서 공식 분리된 차세대 분산 객체 스토리지입니다. S3 호환성은 훌륭하지만, 최소 배포 요구조건이 4개 이상의 노드로 구성됩니다. 스토리지 컨테이너 매니저(SCM), 오존 매니저(OM), 데이터노드(DataNode), S3 게이트웨이(S3G) 컨테이너가 모두 떠야만 S3 요청을 처리할 수 있어 로컬 개발 머신에 띄우기에는 지나치게 무겁습니다.
  • Ceph Object Gateway (RGW): 오픈소스 분산 스토리지의 사실상 표준인 Ceph의 S3 호환 서브시스템입니다. Ceph의 견고한 구조와 엔터프라이즈 활용법은 Ceph 스토리지 핵심 기능 가이드 및 Ceph RBD vs CephFS 비교 가이드에서 확인할 수 있습니다. 그러나 Cephadm, 모니터(MON), 매니저(MGR), OSD 등 방대한 선행 의존성으로 인해 단일 컨테이너 로컬 데모라는 목적에는 맞지 않아 원저자가 설치 요구사항 검토 후 실측 대상에서 제외했습니다.

거버넌스 위험: 1인 관리자 의존과 재단 부재라는 구조적 한계

개발 도구를 선정할 때 기능 호환성만큼이나 냉정하게 따져보아야 하는 요소가 바로 프로젝트의 거버넌스와 지속 가능성입니다. MinIO 사태가 개발 생태계에 큰 충격을 준 근본적인 이유 역시 단일 영리 기업이 오픈소스의 주도권을 쥐고 있다가 상업적 이해관계에 따라 일방적인 정책 변경을 단행했기 때문입니다.

버스 팩터(Bus Factor)와 방향 전환 리스크

위 거버넌스 비교에서 확인되는 가장 중요한 시사점은 비영리 중립 재단이 소유한 로컬 친화적 S3 프로젝트가 전무하다는 현실입니다.

  • 위험한 버스 팩터(Bus Factor): 가장 실용적인 대안으로 꼽힌 S3Proxy와 SeaweedFS는 지난 10년 이상 안정적으로 코드가 릴리스되어 왔지만, 여전히 단 한 명의 핵심 관리자(Andrew Gaul, Chris Lu)의 헌신에 의존하고 있습니다. 핵심 개발자의 개인적 사유나 이탈 시 프로젝트가 포크되지 못하면 즉각적인 유지보수 공백이 발생할 수 있습니다.
  • 방향 급변 위험의 상존: 중립 재단에 지적재산권이 기증되지 않은 프로젝트들은 단일 기업이나 개발자의 결정에 따라 언제든지 유지보수를 접거나 상용으로 방향을 틀 수 있습니다. 이는 MinIO의 행보와 정확히 일치하는 구조적 취약점입니다.
  • CNCF S3 표준의 공백: 클라우드 네이티브 컴퓨팅 재단(CNCF)에서 수많은 분산 시스템과 모니터링 도구가 표준화되었음에도 불구하고, 정작 현대 인프라의 핵심인 객체 스토리지 영역에서 공인된 중립 오픈소스 표준이 부재하다는 점은 엔지니어링 생태계 전반의 숙제로 남아 있습니다.

실무 환경별 로컬 S3 선택 결정 규칙

단 하나의 정답이 모든 프로젝트에 맞을 수는 없습니다. 엔지니어링 조직의 목표, 자동화 환경의 인프라 제약, 그리고 프로젝트의 수명 주기에 맞춘 실무적 결정 규칙이 필요합니다.

사내 CI/CD 파이프라인과 폐쇄망(에어갭) 적용 시나리오

실제 기업 엔터프라이즈 환경에서는 개발 편의성 외에도 다음과 같은 인프라 운영 제약이 발생합니다.

  • CI/CD 자동화 러너의 경량성 극대화: GitHub Actions, GitLab CI 등에서 매 커밋마다 통합 테스트를 수행할 때는 컨테이너 시작 속도와 메모리 사용량이 빌드 대기 시간과 클라우드 비용을 직접 좌우합니다. 초기화 컨테이너나 다중 노드 오케스트레이션이 필요한 도구는 부적합하며, S3Proxy처럼 단일 프로세스로 즉시 소켓을 바인딩하는 구조가 절대적으로 유리합니다. 이때 컨테이너의 데이터 보존과 네트워크 연결은 Docker 네트워크 및 볼륨 바인드 가이드의 원칙을 적용해야 합니다.
  • 에어갭(폐쇄망) 환경의 단일 이미지 반입: 사내 보안 정책상 인터넷 연결이 차단된 폐쇄망 환경에서는 수많은 하위 의존성을 가진 다중 컨테이너 이미지를 반입하고 보안 감사를 통과시키는 작업이 막대한 부담입니다. 단일 바이너리로 컴팩트하게 패키징된 공식 이미지를 내부 프라이빗 레지스트리에 한 번 적재하여 공유하는 방식이 훨씬 안전하고 경제적입니다.

확인하지 못한 것

본 문서에서 다룬 내용 중 원문 자료의 한계나 외부 제약으로 인해 실측 검증을 완료하지 못한 항목들은 다음과 같습니다.

  • 후보군 간의 정량적 I/O 처리량 및 지연 시간 벤치마크: 원문 기술 블로그는 단일 노드 데모 환경에서의 설정 용이성과 기능 호환성 검증에 집중하였으며, 초당 입출력 연산(IOPS), 데이터 전송 대역폭, 쿼리 지연 시간 등 정량적 성능 수치는 측정하지 않았습니다. 따라서 본 글에서도 인위적인 성능 비교 수치를 기재하지 않았습니다.
  • Ceph Object Gateway의 실제 Docker 단일 노드 기동 시험: Ceph RGW는 방대한 설치 요구조건과 데몬 의존성 검토 단계에서 원저자에 의해 시험 대상에서 제외되었으므로, 실제 단일 컨테이너 구성 시의 구체적 실패 로그는 직접 확인하지 못했습니다.
  • Zenko CloudServer 구버전 이미지의 실제 기능 호환성 한계: Docker Hub에 잔존하는 구버전 공식 이미지와 GitHub 컨테이너 레지스트리(GHCR)의 9.2.8 이미지 간의 세부 API 호환성 차이 내역은 원문에 기술되어 있지 않습니다.
  • RustFS 보안 권고(Security Advisory)의 실제 공격 재현 여부: 공식 발행된 보안 취약점 번호는 확인되었으나, 공격 우회 절차나 재현 코드는 보안 및 안전성 원칙에 따라 검증 및 기술하지 않았습니다.
