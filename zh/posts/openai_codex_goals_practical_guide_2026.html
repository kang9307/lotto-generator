引言:Codex Goals 是什么,如今走到了哪一步

Codex Goals 的作用是:只要一次性告诉 Codex「工作完成时应当成立的状态」,它就会把这个目标保存在线程里,并在多个回合中持续朝它推进。入口只有一个 /goal 命令。该功能最早出现在 2026年4月30日发布的 Codex CLI 0.128.0(当时为实验性功能),在 2026年5月21日的 0.133.0 中改为默认开启,并去掉了实验性标记。本文首次发布于 2026年5月20日,正好处在这两个版本之间。韩国开发者社区 GeekNews(news.hada.io)很快就开始讨论,goal-setter 这类社区包装工具也随之出现,“它在实际工作中真的能用吗”这个务实问题随即被提了出来。

本文不是 OpenAI 官方文档的翻译,而是从实务角度梳理 Codex Goals 适合哪些任务、在哪里容易空转、与 Claude Code 的工作方式有何不同 的分析。在 2026-09-29 的更新中,运作方式的说明已按 OpenAI 官方文档和 GitHub 发布说明重写。先说结论:对于完成条件可以用测试或测量值判定的迁移、重构,它很合适;对于说不清「怎样才算完成」的工作,它并不合适。

1. Codex Goals 出现的背景 - 一次性生成的极限

2023~2024年 GPT-4 时代的编程助手,本质上是 “一次只帮你写一个函数的朋友”。让它“写个 JWT 解码函数”,会返回干净的 Python,但这个函数该放进我们仓库认证中间件的哪个位置、和现有 session 处理代码如何冲突,它一无所知。结果是每次提问都要由用户重新解释一遍上下文。

2025年,随着 Cursor、Windsurf、Claude Code 等工具普及,把整个仓库作为上下文 的能力大幅提升。但用户仍需一步步指挥:“先做这个,再做那个”。这种逐步指挥的成本累加起来,用 AI 反而比直接手写还慢。

Codex Goals 针对这一局限采用了另一种方式:“目标和完成条件只需设定一次,下一步由 Codex 根据进展自行决定”。OpenAI Cookbook 建议在终点明确、但通往终点的路径不确定时使用 Goals,举的例子包括性能剖析、打补丁、基准测试、复现不稳定的测试等——下一步取决于上一步所了解到的情况。

2. Goals 功能的运作方式(依据官方文档)

首次发布时,本节把流程描述为四个阶段:“输入目标 → 以清单形式自动拆解子任务(4~10 个)→ 失败达到一定次数后上报的验证循环 → 复盘报告”。2026-09-29 与 OpenAI 官方文档核对后发现,清单式自动拆解、按失败次数上报、复盘报告在官方文档中都无法得到确认。官方文档描述的流程如下。

  1. 设定目标:用 /goal <目标> 设定目标。官方示例为 /goal Finish the migration and keep tests green。
  2. 查看与控制:只输入 /goal 会显示当前目标,/goal pause、/goal resume、/goal clear 分别用于暂停、恢复和清除。
  3. 跨回合继续:目标保存在线程中,在多个回合间保持。但当另一个回合正在进行、有用户输入在排队,或线程中还有其他待处理工作时,Codex 不会继续推进。
  4. 停止条件:达到成功、暂停、清除、中断、预算上限、需要用户输入的阻塞之一时停止。
  5. 开启方式:从 0.133.0 起默认开启。如果斜杠命令列表中看不到 /goal,官方文档建议在 config.toml 中加入 features.goals = true,或运行 codex features enable goals。

关键在于 由谁来定义验证标准。官方 Cookbook 列出了一个好目标应包含的六个要素:完成时应当成立的结果(Outcome)、证明它的测试·基准·报告等验证手段(Verification surface)、工作过程中不得退化的约束(Constraints)、可以使用的文件·工具·仓库范围(Boundaries)、每次尝试后决定下一次尝试的方式(Iteration policy)、无路可走时停止并报告的条件(Blocked stop condition)。也就是说,验证循环不是系统替你自动搭好的,而是 由用户写进目标描述里的。

ChatGPT 桌面应用的斜杠命令文档把 /goal 描述为设定持久目标的命令,并建议先用 /plan 打磨目标。目标运行期间,输入框上方会显示进度,以及暂停、恢复、编辑、清除按钮。先做计划这种方式的利弊,另在 计划模式已死？ 中讨论。

3. 三大实战场景(自行设计的示例)

下面三个场景并非 OpenAI 官方示例,而是以韩国 SI 项目、初创公司和个人项目中常见的模式为假设设计的示例。首次发布时它们被介绍为“预计子任务分解”,但官方并没有说明 Codex 会把目标拆成这样的列表展示出来。下面的列表是人事先勾画的工作顺序,目标描述中则一并写上了完成条件和验证手段。

场景 A. 旧版 REST API v1 → v2 迁移

目标:“将 v1 REST API 迁移到 v2,v1 客户端保持 6 个月兼容。现有集成测试在 v1 和 v2 上都通过即为完成”。

工作流程示例(假设):

  1. 扫描所有 v1 端点(提取 routes/v1/*.py 之类的文件清单)
  2. 生成 v1 与 v2 的差异矩阵(请求/响应 schema 对比)
  3. 搭建 v2 路由骨架(FastAPI prefix=/v2)
  4. 实现 v1→v2 适配层(旧客户端调用 v1,内部转向 v2)
  5. 添加兼容性测试用例(将既有集成测试在 v2 prefix 下复制)
  6. 用 Markdown 编写迁移指南

注意:适配层一旦映射错误,会直接演变为生产事故,这一部分必须单独由人工进行代码审查。

场景 B. JWT 认证 → 基于 Session 的认证

目标:“将用户认证从 JWT token 切换为 session cookie,使用 Redis 作为 session 存储。登录/登出集成测试通过即为完成”。

工作流程示例(假设):

  1. 定位当前 JWT 签发与校验代码
  2. 添加 Redis 客户端模块与连接配置
  3. 实现 session ID 生成、存储与校验逻辑
  4. 把 JWT 校验中间件替换为 session 校验中间件
  5. 修改登录/登出端点(token 响应改为 Set-Cookie)
  6. 整理前端调用层需调整的内容(去掉 Authorization 头,加上 credentials 选项)
  7. 编写迁移策略文档(渐进式与一次性切换的取舍)

注意:涉及安全敏感操作,仅靠自动测试通过是不够的。需要单独安全评审的部分,不要写进目标交给它完成。

场景 C. 把类型安全率提升到 95% 以上

目标:“将 TypeScript 类型覆盖率从 60% 提升到 95% 以上,优先消除 any。type-coverage 结果达到 95% 以上且现有测试仍然通过即为完成”。

工作流程示例(假设):

  1. 分析 type-coverage 工具的输出(测量当前覆盖率)
  2. 给 any 使用点排优先级(库边界 > 核心业务逻辑 > 测试代码)
  3. 补全外部库的类型定义(补 @types 或写 ambient 声明)
  4. 明确工具函数签名(挑出可引入泛型的位置)
  5. 逐步启用 strict 模式(noImplicitAny → strictNullChecks → 完整 strict)
  6. 最终覆盖率测量与剩余 any 列表报告

这是与 Goals 的设计最契合的一类工作。完成条件可以写成数字,因此很容易判断何时该停、何时该继续。

4. Codex Goals vs Claude Code task(2026-09-29 核对)

表中 Codex 一栏已于 2026-09-29 依据 OpenAI 官方文档和 GitHub 发布说明重新核对。Claude Code 一栏大体保留首次发布时的表述,本次未能核对的格子已注明。这张表用于比较两者的运作方式,而不是排名。

对比维度 OpenAI Codex Goals Claude Code task
推进方式设定目标和完成条件后,由 Codex 决定下一步并跨多个回合推进(清单式自动拆解在官方文档中未能确认)用户显式定义 task 并逐步指挥
目标保持保存在线程中,跨回合保持(0.133.0 起使用专用存储)以会话为单位,受上下文窗口限制

使用方式用 ChatGPT 账号登录,在 Plus、Pro、Business、Edu、Enterprise 方案中使用。官方文档中未找到按 Goal 单独计费的说明订阅方案(Pro/Max)- 2026年5月时的情况(未能核实更新)
停止条件成功、暂停、清除、中断、预算上限、需要用户输入的阻塞建议每个 task 由用户确认

简而言之,“把终点可由测试或测量值判定的工作长时间交给它”符合 Goals 的设计,而“需要人在每一步做判断的工作”用逐步指挥的方式更好处理。 首次发布时表中关于韩语处理质量的比较,因找不到支持它的官方资料已删除。Claude Code 的可用环境,来自同日更新的 2026年开发者真正在用的工具 中依据官方文档核对的内容。

5. 落地过程中的注意事项

首次使用 Codex Goals 时常踩的四个坑:

  • 目标定得太宽:像“把整个代码库清理干净”这种目标无法判定何时完成,也就没有停下来的依据。官方文档同样要求在开始前定义「完成是什么」。每个 Goal 最好收窄到 能用测试或测量值说明完成的粒度。
  • 没有验证手段就交出去:在没有测试的仓库里,无法确认目标是否达成,工作可能一直朝错误方向推进。导入前至少要有一套最小集成测试或测量命令。
  • 敏感信息泄露风险:在代码里硬编码 API key 或数据库密码的仓库,工作过程中这些值有可能被发送到外部模型。先检查 .gitignore 与环境变量的使用,再开始使用。
  • 没有回滚计划:长时间运行的结果不理想时,如果没有在独立分支上工作,就很难撤回。务必先建新分支再启动,并把允许改动的范围(Boundaries)写进目标描述。
推荐工作流:小步起步 → 验证结果 → 逐步扩大。第一次可以选“补齐测试代码”这种风险低、完成条件明确的任务,学习曲线最平滑。

6. 韩国开发者的场景适配性

6.1 政府/公共 SI 项目

外部 AI 服务经常被安全策略屏蔽。在网络隔离环境下直接使用 Codex Goals 很困难,需要考虑本地化替代方案(例如基于本地 LLM 的自研 agent)。不过,在 RFP 撰写、技术规格起草这类非代码工作上,仍可能有部分价值。

6.2 初创/B2B SaaS

这是最容易看到效果的领域,因为节省一名资深工程师的时间价值很高。不过,最佳导入时机是 “代码质量的一致性比纯粹的开发速度更重要” 的阶段。MVP 阶段可能用不上这么多,到了整治技术债的阶段用处会更大。

6.3 个人项目/单兵开发

性价比取决于使用方式。Codex 基本上是作为 ChatGPT 方案的一部分来使用的,首次发布时写到的“按 Goal 计的附加费用”在官方文档中无法确认。不过,官方文档把预算上限列为停止条件之一,因此在挂上一个长目标之前,先定好这项工作可以使用的预算会更稳妥。如果你已经在用别的工具,只在完成条件明确的大任务上试用 Goals 负担最小。

7. goal-setter 等社区包装工具与可选方案

社区做的 goal-setter 这类包装工具,是在首次发布前后于 GeekNews 上被介绍的。本文最初把它描述为“OpenAI API 直调与 Codex Goals 之间的抽象层”,但本次更新未能确认该工具的当前状态与功能。因此改为以官方文档可以确认的事实为准,重新划分可选方案。

运行目标驱动型工作的方式可以分为以下三种:

  • API 直接调用:需要自己实现目标保持、迭代、停止判断的逻辑。光是搭工具就要花时间。
  • Codex Goals:目标保存、跨回合继续、暂停·恢复·清除都内置在 Codex 中,可以立即开始。验证标准仍需用户写进目标描述。
  • 包装工具:帮助撰写目标描述或估算成本的辅助工具。使用前,请在其代码仓库中亲自确认它以什么权限执行什么操作。

把外部工具接入 Codex 的官方途径是 MCP。Codex 的文档说明可以通过 config.toml 中的 [mcp_servers.名称] 表和 codex mcp 命令连接 MCP 服务器,因此可以和 Claude Code 的 MCP 生态放在同一标准上比较。

8. 结论 - 谁该用,谁该再等等

适合的人:

  • 迁移与大规模重构频次高的资深工程师
  • 负责改造遗留代码库的技术 lead
  • 一人维护多个仓库的运维型开发

暂时观望:

  • 以单一函数编写为主的初级开发(工具过重、学习机会减少)
  • 几乎没有测试的仓库(没有判定完成的手段)
  • 网络隔离或合规要求屏蔽外部 AI 的环境

当时的展望(2026年5月):当时认为 Codex Goals 与 Claude Code task 的功能差距会越来越小,用户的决策因素将从“功能”转向 “定价模式的稳定性”。从 2026-09-29 回看,Goals 已于 5月21日成为默认功能,Codex 应用也已并入 ChatGPT 桌面应用。Codex 基本上作为 ChatGPT 方案的一部分使用,当时写下的“定额制对按量制”这一框架并不准确。

最后,无论选哪个工具,最重要的能力是 “自己能设计验证标准”。官方文档把结果、验证手段、约束、范围列为好目标的首要要素,也是出于同样的原因。工具越自主,人的角色就越从“下指令”转向“设计完成标准”。更换模型时原有指令无法原样沿用的问题,另在 直接沿用旧配置会发生什么 中讨论。

| 未能确认 | IDE 扩展、Codex 网页端(云端任务)是否支持 `/goal` |
| 方案 | 用 ChatGPT 账号登录,在 Plus、Pro、Business、Edu、Enterprise 方案中使用。官方文档中未找到按 Goal 单独计费的说明 |

## 3. 目标描述检查表(官方建议的六要素)

- [ ] **结果(Outcome)**:用一句话写明完成时应当成立的状态
- [ ] **验证手段(Verification surface)**:指定证明它的测试、基准、命令输出或报告
- [ ] **约束(Constraints)**:写明工作中不得退化的内容(如现有测试持续通过)
- [ ] **范围(Boundaries)**:写明可以使用的文件、工具、仓库
- [ ] **迭代方式(Iteration policy)**:写明每次尝试后如何决定下一次尝试
- [ ] **受阻时的停止条件(Blocked stop condition)**:写明无路可走时停止并报告

## 4. 开始前的检查

- [ ] 仓库中至少有一套最小集成测试或测量命令(否则无法判定完成)
- [ ] 在新分支上开始
- [ ] 代码中没有明文的 API 密钥或数据库密码(检查 .gitignore 与环境变量)
- [ ] 需要安全评审的部分已从目标中移除
- [ ] 已先定好这项工作可用的预算(预算上限是官方文档列出的停止条件之一)

## 5. 停止条件(官方文档)

| 条件 | 含义 |
|---|---|
| 成功 | 达成目标 |
| 暂停 / 清除 | 用户执行 `/goal pause` 或 `/goal clear` |
| 中断 | 运行被中断 |
| 预算上限 | 达到设定的预算 |
| 阻塞 | 需要用户输入 |

当另一个回合正在进行、有用户输入在排队,或线程中还有其他待处理工作时,不会继续推进。

## 6. 适合 / 不适合的工作

| 适合的工作 | 不适合的工作 |
|---|---|
| 终点明确、路径不确定的工作 | 说不清「怎样才算完成」的工作 |
| 遗留 API 迁移、提升类型覆盖率 | “把整个代码库清理干净”这类宽泛目标 |
| 性能改进、复现不稳定的测试 | 几乎没有测试的仓库 |
