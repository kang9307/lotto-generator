테스트는 통과하는데 운영에서만 조건이 안 맞는 이유 - 최적화는 사양이 아니다

2026-08-01 개발/인프라

서론: 테스트는 통과했는데 운영에서만 조건이 안 맞았다

상태 코드가 특정 값인지 검사하는 함수가 있었다. 단위 테스트에서는 전부 통과했다. 그런데 운영에 올리자 그 분기가 한 번도 타지 않았다. 코드를 다시 읽어도 로직에는 아무 문제가 없어 보인다. 값을 로그로 찍어 보면 분명히 기대한 그 숫자다. 그런데 조건이 거짓이다.

원인은 비교 연산자 하나였다. == 를 써야 할 자리에 is 가 들어가 있었다. 그리고 이 실수가 무서운 이유는 테스트가 통과했다는 것이다. 테스트는 코드에 숫자를 직접 적어 넣었고, 운영은 그 값을 소켓과 문자열 파싱을 거쳐 받았다. 같은 숫자인데 결과가 갈렸다.

이 글의 논지는 「is 를 쓰지 마세요」가 아니다. is 는 멀쩡한 연산자이고 반드시 필요한 자리가 있다. 정확한 논지는 이렇다.

  • is 는 「같은 객체인가」를 묻는다. 「값이 같은가」를 묻는 것이 아니다. 두 질문은 다른 질문이다
  • 같은 값이 같은 객체인지는 인터프리터의 최적화가 정한다. 자주 쓰이는 객체를 재사용하는 것은 성능을 위한 구현 선택이지 언어가 약속한 것이 아니다
  • 최적화는 사양이 아니므로 결과에 기대면 안 된다. 구현이 바뀌면 답이 바뀐다
  • 작은 수에서 우연히 참이 나오는 것이 오히려 위험하다. 우연히 맞는 답 때문에 테스트가 통과해 버리기 때문이다

마지막 항목이 핵심이다. 항상 틀리는 버그는 즉시 발견된다. 가끔만 맞는 버그가 배포까지 살아남는다. 아래는 그 「가끔」의 경계가 어디인지 직접 실행해서 찾은 기록이다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 인터프리터는 CPython 3.13.3이고 빌드는 tags/v3.13.3:6280bb5, Apr 8 2025, 14:47:33 [MSC v.1943 64 bit (AMD64)]이다. 스크립트는 전부 파일로 저장해 실행했다.

이 글에 나오는 캐시 범위 숫자는 사양이 아니다. 「어디부터 어디까지가 공유된다」는 값은 이 인터프리터, 이 버전에서 측정한 결과일 뿐이다. 다른 구현이나 다른 버전에서는 다를 수 있다. 이 글은 그 숫자를 외우라고 쓴 것이 아니라, 그런 숫자에 기대는 코드가 왜 위험한지를 보이려고 쓴 것이다.

이 글이 다루지 않는 것. 함수 기본 인자가 언제 평가되는지는 기본 인자가 계산되는 시점에서 다뤘다. 주제는 다르지만 교훈은 이어진다. 구현 세부에 기대면 안 된다는 것이다.

1. 재현 - 어떤 수는 참이고 어떤 수는 거짓이다

먼저 증상을 그대로 재현한다. 주의할 점이 하나 있다. 코드에 숫자를 직접 적으면 캐시가 아니라 컴파일러의 상수 처리가 결과에 끼어든다(3절에서 자세히 본다). 그래서 값을 실행 시점에 문자열에서 만들어 비교했다.

여기서 반드시 짚어야 할 것. 위의 「-5부터 256까지」는 측정값이지 규격이 아니다. 파이썬 언어 참조는 이 지점을 명확히 적어 놓았다. a = 1; b = 1 이후에 두 이름이 같은 객체를 가리킬 수도 있고 아닐 수도 있으며, 구현에 따라 다르므로 여기에 기대서는 안 된다고 되어 있다. 같은 문서는 리터럴 여러 개를 평가할 때 같은 객체를 얻을 수도 있고 값만 같은 다른 객체를 얻을 수도 있다고도 적고 있다.

그러니 이 글에서 가져갈 것은 숫자 두 개가 아니다. 「어떤 범위에서는 우연히 맞는다」는 사실 자체다. 그 우연이 테스트를 초록으로 만든다.

2. id로 들여다보기 - 같은 값, 다른 주소

is 가 실제로 무엇을 보는지 확인한다. 파이썬 문서는 is 가 객체의 아이덴티티를 비교하며 그 아이덴티티는 id() 로 얻는다고 정의한다. 그래서 id() 를 직접 찍어 봤다.

--- 2-1. id() of two equal values ---
n        id(a)              id(b)              same  a==b
------------------------------------------------------------------
5        140735027553320    140735027553320    True  True
100      140735027556360    140735027556360    True  True
256      140735027561352    140735027561352    True  True
257      1406444444016      1406444443248      False True

--- 2-2. the same object every time you ask for it ---
distinct ids for the value 7 across 5 builds : 1
distinct ids for the value 777 across 5 builds: 3
  (777 ids can repeat by accident: a freed object's address gets reused)

주소 자릿수를 보면 흥미로운 것이 보인다. 캐시된 값들은 140735…로 시작하는 구역에 몰려 있고, 캐시 밖 값들은 1406…으로 시작하는 다른 구역에 있다. 앞쪽은 인터프리터가 시작할 때부터 존재하는 영역이고, 뒤쪽은 필요할 때마다 할당되는 영역이다.

그런데 2-2의 마지막 줄에 함정이 있다. 값 777을 다섯 번 만들었더니 서로 다른 주소가 세 개만 나왔다. 5회 중 2회는 앞서 만든 객체가 사라진 자리에 새 객체가 들어앉은 것이다. 이것을 더 극단적으로 보였다.

--- 2-3. id reuse makes id() alone untrustworthy ---
id of a dead 999999 : 1406444443312
id of a fresh 888888: 1406444443312
addresses equal     : True  <- equal ids, different values

--- 2-4. keeping a reference changes the answer ---
both alive at once  : id equal = False  a is b = False

--- 2-6. sys.getrefcount on a cached object ---
refcount of 1  : 4294967295
refcount of 777: 1
  a cached object is referenced from everywhere in the process
  • 값이 999999인 객체와 888888인 객체가 같은 주소를 보고했다. 첫 객체가 소멸한 뒤 그 자리를 둘째가 재사용했기 때문이다. 파이썬 문서도 id() 는 객체의 수명 동안에만 유일하고, 수명이 겹치지 않는 두 객체는 같은 값을 가질 수 있다고 명시한다
  • 그래서 id() 값을 어딘가에 저장해 두고 나중에 비교하는 코드는 원리적으로 틀렸다. 저장한 순간 그 객체가 살아 있다는 보장이 사라진다
  • 2-4에서 두 객체를 동시에 살려 두자 주소가 갈렸다. 즉 같은 코드라도 참조를 잡고 있느냐에 따라 답이 달라진다
  • 마지막 블록의 참조 카운트가 눈에 띈다. 캐시된 1의 카운트가 42억대다. 이 인터프리터에서 상시 재사용되는 객체는 회수 대상에서 아예 빠지도록 표시된다. 반면 777은 1이었다

그런데 여기서 예상 밖의 결과가 하나 나왔다. 캐시 범위 밖인 257을 연산으로 만들어 비교했더니 참이 나온 것이다.

--- 2-5. two address regions, and an unexpected True ---
200 + 56 = 256  300 - 44 = 256  x is y = True
200 + 57 = 257  300 - 43 = 257  p is q = True
  the second pair is OUTSIDE the cache yet still True.
  the cache is not the only thing that makes 'is' true - see experiment 3.
  compare with values built at run time:
  make(257) is make(257) = False

같은 257인데 연산식으로 쓰면 참, 실행 시점에 만들면 거짓이다. 캐시만으로는 설명이 안 된다. 두 번째 원인이 있다.

3. 같은 코드인데 실행 방식에 따라 답이 다르다

두 번째 원인은 컴파일러의 상수 처리다. 코드를 컴파일할 때 같은 리터럴이 여러 번 나오면 컴파일러가 그것을 하나의 객체로 합쳐 코드 객체의 상수 목록에 넣는다. 200 + 57 같은 식도 컴파일 시점에 미리 계산되어 상수가 된다. 실행 중에는 그 상수를 꺼내 쓸 뿐이므로 두 이름이 같은 객체를 가리키게 된다.

--- 3-1. module level, one file, two statements ---
a = 257 ; b = 257   ->  a is b = True

--- 3-2. inside a function, same code object ---
same function body  -> True
two function bodies -> True

--- 3-3. what the compiler stored ---
co_consts of f() : (None, 257)
g1 const id      : 140735026668016
g2 const id      : 140735026668016
same object      : True

bytecode of f():
 13           RESUME                   0

 14           LOAD_CONST               1 (257)
              STORE_FAST               0 (a)

 15           LOAD_CONST               1 (257)
              STORE_FAST               1 (b)

 16           LOAD_FAST_LOAD_FAST      1 (a, b)
              IS_OP                    0
              RETURN_VALUE

바이트코드가 전부 말해 준다. 두 줄 모두 LOAD_CONST 1이다. 상수 목록의 같은 칸을 두 번 읽었으니 같은 객체일 수밖에 없다. 게다가 서로 다른 두 함수의 상수마저 같은 객체였다. 한 모듈을 컴파일하는 동안 상수가 공유되기 때문이다.

그렇다면 컴파일 단위를 쪼개면 어떻게 되는가.

--- 3-4. exec: one string vs two strings ---
exec, single string  -> True
exec, three strings  -> False

--- 3-5. compile() separately then exec ---
separate code objects -> False
const in c1 : [257]
const in c2 : [257]
same object : False

--- 3-6. a real REPL, statement by statement (code module) ---
REPL, line by line  -> False
REPL, small number -> True

결과가 완전히 갈렸다. 3-5를 보면 두 코드 객체가 각자 257이라는 상수를 가지고 있는데 그 둘이 서로 다른 객체다. 3-6이 실무에서 가장 중요하다. 대화형 인터프리터는 한 줄이 곧 하나의 컴파일 단위라 상수가 공유되지 않는다. 그래서 대화형에서는 거짓이 나온다.

프로세스를 나눠서도 확인했다.

--- 3-7. child process: python -c, script file, piped stdin, -i ---
python -c            -> True
script file          -> True
piped stdin (python) -> True
piped stdin (-i)     -> False
  stderr tail of -i  : >>> >>> >>> >>>

--- 3-8. the same test written so the compiler cannot help ---
module level, run-time values -> make(257) is make(257) = False
module level, literal values  -> 257 is 257 (via consts)  = True

같은 두 줄에 대해 결과를 표로 모으면 이렇다. 이것이 이 글에서 두 번째로 중요한 표다.

실행 방식a = 257; b = 257 뒤 a is b이유
스크립트 파일True파일 전체가 한 컴파일 단위

실무적 함의가 크다. 대화형에서 확인한 결과와 스크립트의 동작이 다를 수 있다. 대화형에서 is 가 거짓이라 「역시 쓰면 안 되는구나」 하고 == 로 고쳤다면 다행이지만, 반대로 스크립트에서 참이 나와 「되네」 하고 넘어갔다면 그 코드는 값의 출처가 바뀌는 순간 조용히 무너진다.

4. 문자열도 똑같다

정수만의 이야기가 아니다. 문자열도 같은 원리로 공유된다. 다만 조건이 조금 다르다.

--- 4-1. literals in one compilation unit ---
s1 = "total" ; s2 = "total"      -> s1 is s2 = True
with a space in it               -> t1 is t2 = True

--- 4-2. built at run time ---
"to" + "tal"        is base : True   == base : True
parts[0] + parts[1] is base : False   == base : True
"".join(parts)      is base : False   == base : True
percent format      is base : False   == base : True
f-string            is base : False   == base : True

--- 4-3. length matters for run-time strings ---
built            is-literal   len
----------------------------------------
''               True         0
'x'              True         1
'xx'             False        2
'xxx'            False        3
'xxxx'           False        4
'xxxxx'          False        5

4-2의 첫 줄과 둘째 줄의 차이가 중요하다. 리터럴끼리의 덧셈은 컴파일 시점에 합쳐져 상수가 되지만, 리스트에서 꺼낸 조각을 더한 것은 실행 시점에 새 객체가 된다. 값은 똑같은데 is 만 갈린다.

4-3은 빈 문자열과 한 글자짜리만 공유된다는 것을 보여 준다. 이것도 자주 쓰이는 객체를 미리 만들어 두는 최적화다. 이제 컴파일 단위를 쪼개고 다시 본다.

--- 4-4. identifier-shaped vs not, from a REPL (separate units) ---
  identifier-shaped     -> True
  with a space          -> False
  with a hyphen         -> False
  empty string          -> True
  single ascii char     -> True

--- 4-5. sys.intern forces sharing ---
run-time built, two copies       : False
after sys.intern on both         : True
interned is the literal          : True

--- 4-6. slicing produces new objects ---
name[:] is name       : True    (full slice can return self)
name[0:7] is name     : True
name[1:] is "ser_id"  : False
name[1:] == "ser_id"  : True

4-4가 「식별자 형태 문자열은 인터닝된다」는 이야기의 실체다. 컴파일 단위가 서로 다른데도 user_id 는 참이 나왔고, 공백이나 하이픈이 들어간 순간 거짓이 됐다. 변수명으로 쓸 수 있는 형태의 문자열만 자동으로 공유되기 때문이다.

  • 그래서 키 이름처럼 식별자 형태인 문자열은 is 가 우연히 맞을 확률이 높다. 이것이 이 버그를 특히 잘 숨긴다
  • 반대로 사용자 이름, 문장, 하이픈 섞인 코드값은 거의 항상 거짓이 된다. 같은 코드가 데이터에 따라 다르게 동작한다
  • 강제로 공유시키고 싶다면 인터닝 함수를 명시적으로 호출해야 한다. 4-5에서 그 결과가 참으로 바뀌었다. 다만 이것은 메모리 절약이 목적이지 비교를 위한 도구가 아니다
  • 4-6의 첫 줄도 함정이다. 전체 슬라이스가 같은 객체를 돌려주기도 한다. 「슬라이스는 항상 새 객체」라는 짐작도 틀린다

실무에서 이 문제가 어디서 터지는지가 마지막 조각이다. 값이 바깥에서 들어오는 순간이다.

--- 4-7. where this bites: values that came from outside ---
json value  is literal : False   == literal : True
csv  value  is literal : False   == literal : True

--- 4-8. the same for other immutable types ---
() is ()            : True
tuple() is tuple()  : True
(1,2) built vs lit  : False
0.0 is 0.0 (consts) : True
float('0.0') twice  : False

같은 문자열인데 직렬화 형식에서 꺼낸 값은 리터럴과 다른 객체다. 설정 파일, API 응답, 표 형식 파일, 사용자 입력 전부 마찬가지다. 서론의 시나리오가 정확히 이것이다. 테스트는 코드에 값을 적었고 운영은 바깥에서 받았다.

5. == 과 is 는 서로 다른 질문을 한다

이제 정리한다. 두 연산자는 대체재가 아니라 서로 다른 질문이다.

--- 5-1. the two questions are different ---
a == b : True    same value
a is b : False   different objects
a is c : True    same object
after b.append(4)  a = [1, 2, 3]  b = [1, 2, 3, 4]
after c.append(9)  a = [1, 2, 3, 9]  c = [1, 2, 3, 9]   <- c IS a

--- 5-2. equal but not identical, identical but not equal ---
x = float('nan')
  x is x : True    same object
  x == x : False   a value that is not equal to itself
  x in y : True    'in' tries 'is' first, then '=='
  any(v == x for v in y) : False

--- 5-3. __eq__ can say anything; 'is' cannot be overridden ---
p == q : True   __eq__ decides
p is q : False  identity is not overridable
p == 5 : True
p is p : True

--- 5-4. objects that define no __eq__ fall back to identity ---
m == n : False   default __eq__ IS identity
m is n : False

5-2가 두 질문이 완전히 독립임을 증명한다. 같은 객체인데 자기 자신과 같지 않은 값이 존재한다. 그리고 목록에 들어 있는지 묻는 연산은 동일성을 먼저 확인하기 때문에 참이 나오는데, 값 비교로만 확인하면 거짓이다. 같은 질문이었다면 이런 일이 생길 수 없다.

5-4는 이 버그가 왜 늦게 발견되는지 설명한다. 등호 동작을 정의하지 않은 클래스는 기본값이 곧 동일성 비교다. 그래서 그런 클래스에서는 두 연산자가 항상 같은 답을 낸다. 나중에 그 클래스에 등호 동작이 추가되는 순간, 그때까지 잘 돌던 is 비교가 갑자기 틀린다.

연산자묻는 것구현클래스가 바꿀 수 있나쓸 자리
a == b값이 같은가클래스의 등호 동작바꿀 수 있다값 비교 전부
a is b같은 객체인가아이덴티티 비교바꿀 수 없다싱글턴, 센티넬, 공유 여부
a != b값이 다른가클래스의 부등호 동작바꿀 수 있다값 비교 전부
a is not b다른 객체인가아이덴티티 비교바꿀 수 없다싱글턴, 센티넬

「바꿀 수 없다」가 is 의 유일한 강점이다. 그리고 그 강점이 필요한 자리가 실제로 있다.

--- 5-5. when 'is' is the right tool: singletons ---
None is None            : True
Ellipsis is Ellipsis    : True
NotImplemented is itself: True
  fetch('a' ) -> None
  fetch('b' ) -> 0
  fetch('c' ) -> ''
  fetch('zz') -> 'MISS'
  note 'a' holds None and 'b' holds 0: a truthiness check would lose both

--- 5-6. the falsy trap that 'is SENTINEL' avoids ---
  bad('a' )   -> 'MISS'
  bad('b' )   -> 'MISS'
  bad('c' )   -> 'MISS'
  bad('zz')   -> 'MISS'
  three stored values were reported as missing

두 블록을 나란히 보라. 같은 저장소에 대해 하나는 정확히 답했고 하나는 세 건을 잃었다. 저장된 값이 「없음」이거나 0이거나 빈 문자열일 때, 참·거짓만 보는 검사는 그것을 전부 「없다」로 판정한다. 이럴 때 필요한 것이 세상에 하나뿐인 표식 객체이고, 그것을 확인하는 유일한 방법이 is 다.

6. is None 은 왜 안전하고 is True 는 왜 아닌가

「None 비교에는 is 를 써라」는 규칙은 널리 알려져 있다. 그 이유를 실행으로 확인했다.

--- 6-1. None is a singleton: try to make a second one ---
type(None)          : <class 'NoneType'>
type(None)() worked : True  <- it returns the same object
copy.copy(None) is None      : True
copy.deepcopy(None) is None  : True
pickle round trip is None    : True
id(None) stable in a loop    : True

--- 6-2. None across a process boundary ---
id(None) here      : 140735026668016
id(None) in child  : 140735026668016

--- 6-3. why 'is None' and not '== None' ---
w == None : True   <- a class talked its way into looking like None
w is None : False  <- identity cannot be talked into anything

a column-style 'missing' object:
  m == None : True
  m is None : False
  if m == None: would take the branch; if m is None: would not
  • 두 번째 것을 만들 방법이 없다. 타입을 직접 호출해도 원래 객체가 돌아왔다. 복사, 깊은 복사, 직렬화 왕복 전부 같은 객체였다
  • 그래서 x is None 은 인터프리터의 최적화와 무관하게 항상 정확하다. 1절의 캐시 이야기와는 성격이 완전히 다르다
  • 6-3이 == 를 쓰면 안 되는 이유다. 클래스가 등호 동작을 재정의하면 None 이 아닌 객체가 None 과 같다고 대답한다. 표 형식 데이터를 다루는 라이브러리들이 실제로 이런 「결측치」 객체를 쓴다
  • 6-2는 흥미롭지만 오해하기 쉽다. 부모와 자식 프로세스에서 같은 주소가 나온 것은 이 객체가 실행 파일 안에 고정된 자리를 갖기 때문이다. 그렇다고 해서 id() 값을 프로세스 사이에 비교해도 된다는 뜻은 아니다. 2절에서 봤듯 일반 객체의 주소는 재사용된다

그렇다면 참·거짓도 하나뿐인 객체이니 is True 도 괜찮은가. 문법적으로는 안전하지만 의미가 어긋난다.

--- 6-4. True is a singleton too, but the comparison is still wrong ---
bool(1) is True     : True
True is True        : True

value    type           == True    is True    if value:
--------------------------------------------------------
1        int            True       False      True
1.0      float          True       False      True
True     bool           True       True       True
'1'      str            False      False      True
[1]      list           False      False      True

--- 6-5. a function returning 1 instead of True ---
legacy_flag    -> 1      if v:True    v == True:True    v is True:False
modern_flag    -> True   if v:True    v == True:True    v is True:True

표의 마지막 열을 보라. 다섯 값이 전부 참이다. 그런데 is True 열은 하나만 참이다. 즉 「참인가」를 is True 로 물으면 참인 값의 대부분을 거짓으로 판정한다.

6-5가 실무 시나리오다. 오래된 함수가 1을 돌려주다가 참으로 바뀌거나 그 반대가 되면, 진리값 검사와 등호 비교는 그대로인데 is True 분기만 뒤집힌다. 변경 이력에 「부울로 정리」라고만 적혀 있어서 원인을 찾기가 어렵다.

이제 서론의 사고를 그대로 재현한다.

--- 6-6. 'is 0' and friends: run-time values break the spell ---
  value 0       v == 0:True   v is zero:True   | v == 257:False  v is big:False
  value 1       v == 0:False  v is zero:False  | v == 257:False  v is big:False
  value 256     v == 0:False  v is zero:False  | v == 257:False  v is big:False
  value 257     v == 0:False  v is zero:False  | v == 257:True   v is big:False
  value 1000    v == 0:False  v is zero:False  | v == 257:False  v is big:False

--- 6-7. the dangerous shape: a test that passes for the wrong reason ---
status_code_ok(200)          : True   <- literal 200, same const pool
status_code_ok(int('200'))   : True   <- 200 is inside the cache
status_code_ok(199 + 1)      : True
status_code_ok2(500)         : True   <- literal, const pool again
status_code_ok2(int('500'))  : False   <- outside the cache: FALSE
status_code_ok2(499 + 1)     : True

6-7이 이 글 전체의 요약이다. code is 200 이라고 쓴 함수는 세 가지 호출 방식 모두에서 통과했다. 200이 캐시 범위 안이기 때문이다. 그런데 같은 모양으로 쓴 code is 500 함수는 문자열에서 만든 값을 넣자 거짓이 됐다.

여기가 이 글의 핵심이다. 두 함수는 완전히 같은 실수를 저질렀다. 그런데 하나는 통과하고 하나는 실패한다. 차이는 오직 상태 코드 숫자가 캐시 범위 안이냐 밖이냐다.

그리고 이것이 왜 위험한가. 200번대 성공 코드로 짠 테스트는 전부 초록으로 나온다. 오류 처리 경로를 테스트하지 않았다면 400번대·500번대에서만 터지는 버그가 배포된다. 실패 경로가 테스트 커버리지가 낮은 곳이라는 점까지 겹쳐서, 이 버그는 정확히 가장 발견하기 어려운 자리에 숨는다.

7. 부울은 정수다 - 딕셔너리 키가 겹친다

참·거짓과 정수의 관계는 별개 주제처럼 보이지만 뿌리가 같다. 어떤 것이 같은 것으로 취급되는가의 문제다.

--- 7-1. bool is a subclass of int ---
issubclass(bool, int) : True
isinstance(True, int) : True
int(True), int(False) : 1 0
True + True           : 2
sum([True, True, False]): 2

--- 7-2. equality and hashing ---
expression       value    hash
--------------------------------------
True             True     1
1                1        1
1.0              1.0      1
False            False    0
0                0        0
0.0              0.0      0

True == 1     : True
True is 1     : False
False == 0    : True
hash(True) == hash(1) : True

--- 7-3. dict keys collapse ---
d after three assignments : {1: 'float one'}
len(d)                    : 1
type of the surviving key : int
insert True first         : {True: 'int one'}  key type: bool

파이썬 문서는 부울 타입이 정수의 하위 클래스이며 더 이상 상속할 수 없고 인스턴스가 참과 거짓 두 개뿐이라고 정의한다. 그 결과가 7-2다. 값이 같고 해시도 같다. 그러니 사전에서 같은 칸을 차지한다.

7-3의 마지막 두 줄이 정확한 동작을 보여 준다. 먼저 넣은 키가 남고 값만 덮인다. 정수를 먼저 넣으면 키의 타입이 정수로 남고, 부울을 먼저 넣으면 부울로 남는다. 즉 남는 키의 타입이 삽입 순서에 달려 있다.

--- 7-4. the same collapse in sets and counters ---
{1, True, 1.0}            : {1}
len({0, False})           : 1
Counter([1, True, 1, True]): Counter({1: 4})

--- 7-5. a config table that quietly loses a row ---
declared 5 entries, got   : 3 -> {0: 'disabled', 1: 'enabled', 2: 'verbose'}
LEVELS[False]             : disabled
LEVELS[0]                 : disabled  <- same slot

--- 7-6. list membership and index ---
True in row               : True
row.index(True)           : 1
False in row              : True
row.count(1)              : 1
[True, 1].count(1)        : 2

7-5가 실제로 사고가 나는 모양이다. 다섯 줄을 적었는데 세 줄만 남았다. 오류도 경고도 나지 않는다. 코드 리뷰에서도 다섯 줄이 그대로 보이기 때문에 알아채기 어렵다. 설정 표에 0과 거짓을 함께 쓰는 순간 이 일이 벌어진다.

7-6의 계수 결과도 눈여겨볼 만하다. 목록에 참과 정수 1이 함께 들어 있으면 1의 개수가 2로 센다. 집계 로직이 여기서 틀린다.

--- 7-7. so how do you actually distinguish them? ---
  True   -> is-check:bool    type() is bool:True    isinstance int:True
  False  -> is-check:bool    type() is bool:True    isinstance int:True
  1      -> is-check:int     type() is bool:False   isinstance int:True
  0      -> is-check:int     type() is bool:False   isinstance int:True
  1.0    -> is-check:float   type() is bool:False   isinstance int:False

--- 7-8. JSON round trip keeps them apart, dict keys do not ---
json.dumps({'a': True, 'b': 1}) : {"a": true, "b": 1}
json.dumps({True: 'x', 1: 'y'}) : {"true": "y"}

7-7이 해법이다. 타입 자체가 부울인지 확인해야 한다. 정수인지 묻는 검사는 참·거짓을 통과시킨다. 「숫자만 받는다」는 검증을 그렇게 짜 놓으면 부울이 그대로 흘러들어간다.

7-8의 둘째 줄은 그 결과를 보여 준다. 두 항목을 적었는데 직렬화 결과에는 하나만 남았고 키가 문자열 참으로 바뀌었다. 직렬화 함수가 잘못한 것이 아니다. 그 함수가 보기 전에 이미 사전에서 합쳐진 뒤였다.

8. 위험한 is 를 찾아내는 법

원리를 알았으니 이제 기존 코드에서 찾아내야 한다. 먼저 이 환경에 무엇이 있는지 확인했다.

--- 8-1. which static checkers are installed here ---
  ruff       on PATH: False   importable: False
  flake8     on PATH: False   importable: False
  pylint     on PATH: False   importable: False
  pyflakes   on PATH: False   importable: False
  mypy       on PATH: False   importable: False

널리 쓰이는 정적 검사 도구가 하나도 설치되어 있지 않았다. 그래서 이 글은 그 도구들의 동작을 확인하지 못했고, 확인하지 못한 것을 확인한 것처럼 적지 않는다. 대신 인터프리터에 들어 있는 것만으로 두 단계를 만들었다.

8.1 첫 단계 - 인터프리터 자신이 이미 경고한다

리터럴과 is 를 비교하면 컴파일 단계에서 경고가 나온다. 일부러 틀리게 짠 표본 파일로 확인했다.

--- 8-2. the compiler already warns. turn the warning into an error ---
  bad_sample.py:6: SyntaxWarning: "is" with 'int' literal. Did you mean "=="?
    if code is 200:                    # BAD: int literal
  bad_sample.py:8: SyntaxWarning: "is not" with 'int' literal. Did you mean "!="?
    if code is not 500:                # BAD: int literal
  bad_sample.py:14: SyntaxWarning: "is" with 'str' literal. Did you mean "=="?
    if name is "admin":                # BAD: str literal
  bad_sample.py:16: SyntaxWarning: "is" with 'tuple' literal. Did you mean "=="?
    if name is ():                     # BAD: tuple literal

  with -W error::SyntaxWarning  -> returncode 1
      if code is 200:                    # BAD: int literal
         ^^^^^^^^^^^
  SyntaxError: "is" with 'int' literal. Did you mean "=="?

경고를 오류로 승격시키니 종료 코드가 1이 됐다. 즉 서드파티 의존 없이 빌드 단계에서 실패시킬 수 있다. 다만 이 경고의 사각지대를 반드시 알아야 한다.

--- 8-3. what the built-in warning does NOT catch ---
    a is b           -> warned: False
    flag is True     -> warned: False
    v is SMALL       -> warned: False
    code is CONST    -> warned: False
    x is ()          -> warned: True

다섯 가지 중 넷이 조용히 통과했다. 이름에 묶인 상수와 비교하는 형태를 못 잡는 것이 특히 뼈아프다. 실무 코드는 숫자를 직접 적기보다 상수 이름을 쓰기 때문이다. 참고로 마지막 줄은 경고가 나왔는데, 빈 튜플은 리터럴로 취급되기 때문이다.

8.2 둘째 단계 - 구문 트리를 직접 훑는다

사각지대를 메우려면 코드를 구조로 읽어야 한다. 표준 라이브러리의 구문 트리 모듈로 검사기를 만들었다. 핵심 부분은 이렇다.

SAFE = {"None", "True", "False", "Ellipsis", "NotImplemented"}

class Checker(ast.NodeVisitor):
    def classify(self, node):
        if isinstance(node, ast.Constant):
            if node.value is None or isinstance(node.value, bool):
                return None                       # 싱글턴이므로 정상
            return "LITERAL", "리터럴 비교"
        if isinstance(node, (ast.Tuple, ast.List, ast.Dict, ast.Set)):
            return "LITERAL", "표시식 리터럴"
        if isinstance(node, ast.BinOp):
            return "EXPR", "연산 결과"
        if isinstance(node, ast.Call):
            fn = getattr(node.func, "id", None)
            if fn in ("int", "float", "str", "bytes", "tuple", "list"):
                return "EXPR", "변환 결과"
            return None
        if isinstance(node, ast.Name):
            if node.id in SAFE:
                return None                       # 싱글턴 이름이므로 정상
            if node.id in self.consts:
                return "CONSTNAME", "리터럴에 묶인 이름"
        return None

    def visit_Compare(self, node):
        for op, right in zip(node.ops, node.comparators):
            if not isinstance(op, (ast.Is, ast.IsNot)):
                continue
            for side in (node.left, right):
                got = self.classify(side)
                if got:
                    self.hits.append((node.lineno, got[0], got[1]))
                if isinstance(side, ast.Constant) and isinstance(side.value, bool):
                    self.hits.append((node.lineno, "BOOLSINGLETON", "is True/False"))
        self.generic_visit(node)

9. 팀 규약과 점검 목록

도구는 코드에 이미 있는 것을 찾을 뿐이다. 새로 들어오는 것을 막으려면 규약이 필요하다. 아래는 위 실행 결과에서 곧바로 도출되는 것만 적었다.

9.1 규약

  1. is 는 싱글턴 전용이다. None, 명시적으로 만든 표식 객체, 열거형 멤버. 이 셋 밖에서 is 를 봤다면 리뷰에서 이유를 묻는다
  2. 값 비교는 예외 없이 ==. 정수, 문자열, 상태 코드, 설정값 전부 해당한다. 「작은 수라 괜찮다」는 근거가 되지 않는다
  3. 「값 없음」 판정에 참·거짓 검사를 쓰지 않는다. 5-6에서 봤듯 0과 빈 문자열이 함께 사라진다. 표식 객체를 만들어 is 로 확인한다
  4. is True 는 「정확히 그 객체인가」를 물을 때만. 그런 의도라면 왜 그런지 주석을 남긴다. 주석 없는 is True 는 실수로 간주한다
  5. 타입 판별은 타입을 직접 본다. 정수인지 묻는 검사는 참·거짓을 통과시킨다(7-7)
  6. 사전과 집합의 키에 0과 거짓, 1과 참을 섞지 않는다. 7-5처럼 줄이 조용히 사라진다
  7. 테스트에 리터럴만 넣지 않는다. 이것이 가장 중요하다. 문자열 파싱, 직렬화 왕복, 실제 입출력을 거친 값으로도 같은 검증을 한다. 6-7이 그 이유다
  8. id() 값을 저장하거나 프로세스 사이에 비교하지 않는다. 2-3에서 봤듯 주소는 재사용된다

9.2 점검 목록

  • 인터프리터 경고를 오류로 승격시키는 단계를 빌드에 넣었다
  • 구문 트리 검사기를 저장소 전체에 한 번 돌렸고 결과를 검토했다
  • == None 을 is None 으로 전부 바꿨다
  • 남아 있는 is True · is False 에 전부 사유 주석이 달려 있다
  • 상수 이름과 is 로 비교하는 곳이 없다(인터프리터 경고가 못 잡는 형태다)
  • 「값 없음」 판정에 표식 객체를 쓰고 있고, 그 객체가 모듈 밖으로 새지 않는다
  • 정수 검증에서 참·거짓이 통과해도 되는지 각 지점에서 판단했다
  • 사전·집합 키에 0 과 거짓이 함께 쓰인 곳이 없다
  • 집계·계수 로직에 참·거짓과 정수가 섞여 들어오지 않는다
  • 테스트가 바깥에서 들어온 값으로도 같은 분기를 검증한다
  • 성공 코드뿐 아니라 실패 코드 경로도 테스트한다(6-7의 함정이 여기 있다)
  • 주석이나 문서에 캐시 범위 숫자를 근거로 적은 곳이 없다
  • 대화형에서 확인한 결과를 스크립트 동작의 근거로 쓴 곳이 없다
  • 열거형·표식 객체 같은 의도적 싱글턴에만 is 가 남아 있다

10. 이 글에서 확인하지 못한 것

확인하지 않은 것을 확인한 것처럼 적으면 다음 사람을 잘못 이끈다. 한계를 명확히 밝힌다.

  • 다른 구현. 모든 측정은 하나의 인터프리터 구현, 하나의 버전, 하나의 운영체제에서 이뤄졌다. 다른 구현에서 같은 결과가 나온다고 주장하지 않는다. 오히려 이 글의 논지는 그것이 달라질 수 있다는 쪽이다
  • 다른 버전. 같은 구현이라도 버전에 따라 최적화가 바뀔 수 있다. 2-6에서 본 참조 카운트 동작도 버전마다 다를 수 있는 영역이다
  • 정적 검사 도구의 실제 동작. 8-1에서 밝혔듯 이 환경에는 하나도 설치되어 있지 않았다. 규칙 번호를 언급하지 않은 이유가 이것이다
  • 다중 스레드·다중 인터프리터 환경. 객체 공유 방식이 달라질 수 있는 영역인데 이 글에서 다루지 않았다
  • 성능 영향. is 가 == 보다 빠른 것은 사실이지만 그 차이를 측정하지 않았다. 그리고 틀린 답을 빨리 내는 것에는 가치가 없다
  • 다른 언어의 동일성 비교. 비슷한 함정이 있다고 알려져 있으나 이 글에서 실행하지 않았다

다만 확인하지 못한 것들에는 공통점이 있다. 전부 「구현이 어떻게 하는가」에 관한 질문이다. 그리고 이 글의 결론은 구현의 동작을 알아야 성립하는 것이 아니다. 구현이 무엇을 하든 값 비교에는 == 를 쓰면 된다. 그것이 구현을 몰라도 되게 만드는 유일한 방법이다.

결론: 통과하는 테스트가 가장 위험하다

정리하면 이렇다. is 는 「같은 객체인가」를 묻는다. 값 비교에 그것을 쓰면 답이 맞을지는 인터프리터의 최적화가 정한다. 이 인터프리터에서 측정한 공유 범위는 -5부터 256까지였고, 짧은 문자열과 식별자 형태 문자열도 공유됐다. 그런데 그 범위는 측정값이지 규격이 아니다.

그리고 원인이 하나가 아니라는 것이 이 문제를 더 어렵게 만든다. 캐시가 하나, 컴파일 단위 안의 상수 공유가 또 하나다. 후자 때문에 같은 코드가 스크립트에서는 참, 대화형에서는 거짓이 됐다. 확인하는 방법에 따라 결론이 뒤집히는 것이다.

가장 중요한 것은 마지막 대목이다. 이 버그는 항상 틀리지 않는다. 가끔 맞는다. 200번 상태 코드로 짠 테스트는 통과하고 500번대에서만 무너진다. 값을 코드에 적은 테스트는 통과하고 바깥에서 받은 값에서만 무너진다. 그래서 이 버그는 테스트를 통과해 배포된 뒤, 가장 확인하기 어려운 경로에서 처음 모습을 드러낸다.

규칙은 짧다. is 는 None 과 표식 객체와 열거형 멤버에만 쓴다. 나머지 전부는 == 다. 이 규칙을 지키면 캐시 범위가 몇부터 몇까지인지 알 필요가 없어진다. 구현 세부를 몰라도 되게 만드는 것이 좋은 규칙의 조건이다.

지금 당장 할 수 있는 일이 하나 있다. 저장소에서 is 를 검색해, None 이 아닌 것과 비교하는 줄을 세어 보라. 그중 상수 이름과 비교하는 것이 있다면 인터프리터 경고로는 절대 잡히지 않는다. 그리고 그 코드의 테스트가 초록이라면, 초록인 이유가 코드가 맞아서인지 값이 작아서인지 확인해 볼 만하다.

# `==` 와 `is` — 판단표·재현 코드·검출기·점검 목록

> 출처: braindetox.kr — is로 비교했더니 어떤 수는 참, 어떤 수는 거짓
> 측정 환경: Windows 10 Pro (10.0.19045) / CPython 3.13.3 (MSC v.1943 64bit AMD64)
> 이 파일을 그대로 AI에 붙여 「이 기준으로 우리 코드베이스를 점검해줘」라고 쓰면 됩니다.
> 아래에 나오는 캐시 범위 수치는 **이 인터프리터에서 측정한 값**이고 언어 사양이 아닙니다. 다른 구현·다른 버전에서는 달라질 수 있습니다.

## 0. 한 줄 요약

`is` 는 「같은 객체인가」를 묻고 `==` 는 「같은 값인가」를 묻는다.
값을 비교하고 싶은데 `is` 를 쓰면, 답이 맞을지 틀릴지는 **인터프리터의 최적화**가 정한다.
최적화는 사양이 아니므로 **결과에 기대면 안 된다.**

## 1. 판단표 — 무엇을 쓸 것인가

| 하고 싶은 것 | 쓸 것 | 쓰면 안 되는 것 | 이유 |
|---|---|---|---|
| 값이 같은지 | `a == b` | `a is b` | 같은 값이 같은 객체라는 보장이 없다 |
| None 인지 | `x is None` | `x == None` | `__eq__` 는 클래스가 재정의할 수 있다 |
| None 이 아닌지 | `x is not None` | `x != None` | 같은 이유 |
| 참인지 (일반) | `if x:` | `x is True` | `1`, `[1]`, `'a'` 는 참이지만 `is True` 는 거짓 |
| 정확히 `True` 객체인지 | `x is True` | — | 이 의도라면 맞다. 다만 의도를 주석으로 남길 것 |
| bool 타입인지 | `type(x) is bool` | `isinstance(x, int)` | `bool` 은 `int` 의 하위 클래스다 |
| 「값이 없음」 구분 | `x is SENTINEL` | `if not x:` | `0`, `''`, `[]` 를 없는 값으로 오인한다 |
| 같은 객체를 공유하는지 | `a is b` | `a == b` | 이럴 때가 `is` 의 본래 용도다 |
| Enum 멤버 비교 | `x is Color.RED` | `x == 'RED'` | Enum 멤버는 싱글턴이다 |
| 문자열 값 비교 | `s == 'admin'` | `s is 'admin'` | 런타임 문자열은 공유되지 않는다 |

## 2. 재현 코드 — 그대로 붙여 실행

```python
# repro.py
import sys

def make(n):
    """실행 시점에 정수를 만든다. 컴파일 상수 재사용을 피하기 위한 장치."""
    return int(str(n))

print(sys.version)

for n in (0, 5, 256, 257, 1000):
    a, b = make(n), make(n)
    print(n, "is:", a is b, " ==:", a == b)

def shared(n):
    return make(n) is make(n)

lo, hi = 0, 1 << 20
while hi - lo > 1:
    mid = (lo + hi) // 2
    if shared(mid):
        lo = mid
    else:
        hi = mid
print("공유되는 마지막 값 :", lo)

lo2, hi2 = -(1 << 20), 0
while hi2 - lo2 > 1:
    mid = (lo2 + hi2) // 2
    if shared(mid):
        hi2 = mid
    else:
        lo2 = mid
print("공유되는 첫 값     :", hi2)
print("측정된 범위        :", hi2, "..", lo)
```

측정 결과(CPython 3.13.3 / Windows): 공유 범위 `-5 .. 256`, 262개 객체.
다시 강조하면 이것은 **측정값**이지 규격이 아니다.

## 3. 실행 방식에 따라 답이 갈린다

같은 두 줄인데 결과가 다르다. 실측 결과:

| 실행 방식 | `a = 257; b = 257` 뒤 `a is b` |
|---|---|
| 스크립트 파일 | `True` |
| `python -c` | `True` |
| 표준 입력으로 흘려 넣기 | `True` |
| `exec()` 에 문자열 하나로 | `True` |
| `exec()` 에 문자열 세 개로 | `False` |
| `compile()` 을 따로 두 번 | `False` |
| 대화형 인터프리터 (한 줄씩) | `False` |
| 실행 시점에 만든 값 `make(257)` | `False` |

교훈: **같은 컴파일 단위 안의 같은 리터럴은 하나의 객체로 합쳐진다.**
대화형에서 확인한 결과와 스크립트에서 확인한 결과가 다를 수 있다.

## 4. 위험 패턴 검출 코드

### 4-1. 표준 라이브러리만으로 — 컴파일러 경고를 오류로

```bash
# 리터럴과 is 를 비교하면 인터프리터가 SyntaxWarning 을 낸다
python -W error::SyntaxWarning -c "import py_compile,sys; py_compile.compile(sys.argv[1], cfile=None, doraise=True)" target.py
```

- 잡히는 것: `x is 200`, `x is 'admin'`, `x is ()`
- **못 잡는 것**: `x is CONST`, `flag is True`, `a is b`
- 서드파티 의존 없이 빌드 단계에서 실패시킬 수 있다

### 4-2. ast 로 직접 훑기 (`is_lint.py`)

```python
#!/usr/bin/env python3
"""위험한 is 사용을 찾는다. 발견 시 종료 코드 1."""
import ast, os, sys

SAFE = {"None", "True", "False", "Ellipsis", "NotImplemented"}

def module_consts(tree):
    out = {}
    for stmt in tree.body:
        if isinstance(stmt, ast.Assign) and isinstance(stmt.value, ast.Constant):
            v = stmt.value.value
            if isinstance(v, (int, float, str, bytes)) and not isinstance(v, bool):
                for t in stmt.targets:
                    if isinstance(t, ast.Name):
                        out[t.id] = v
    return out

class Checker(ast.NodeVisitor):
    def __init__(self, consts):
        self.consts, self.hits = consts, []

    def classify(self, node):
        if isinstance(node, ast.Constant):
            if node.value is None or isinstance(node.value, bool):
                return None
            return "LITERAL", "%s 리터럴 %r" % (type(node.value).__name__, node.value)
        if isinstance(node, (ast.Tuple, ast.List, ast.Dict, ast.Set)):
            return "LITERAL", "표시식 리터럴"
        if isinstance(node, ast.JoinedStr):
            return "LITERAL", "f-string"
        if isinstance(node, ast.BinOp):
            return "EXPR", "연산 결과"
        if isinstance(node, ast.Call):
            fn = getattr(node.func, "id", None)
            if fn in ("int", "float", "str", "bytes", "tuple", "list"):
                return "EXPR", fn + "() 결과"
            return None
        if isinstance(node, ast.Name):
            if node.id in SAFE:
                return None
            if node.id in self.consts:
                return "CONSTNAME", "리터럴에 묶인 이름 %r" % (self.consts[node.id],)
        return None

    def visit_Compare(self, node):
        for op, right in zip(node.ops, node.comparators):
            if not isinstance(op, (ast.Is, ast.IsNot)):
                continue
            for side in (node.left, right):
                got = self.classify(side)
                if got:
                    self.hits.append((node.lineno, got[0], got[1]))
                if isinstance(side, ast.Constant) and isinstance(side.value, bool):
                    self.hits.append((node.lineno, "BOOLSINGLETON",
                                      "is %r 대신 진리값 검사나 == 를 쓸 것" % side.value))
        self.generic_visit(node)

def scan(path):
    src = open(path, encoding="utf-8").read()
    tree = ast.parse(src, filename=path)
    ck = Checker(module_consts(tree))
    ck.visit(tree)
    return sorted(set(ck.hits))

def main(root):
    total = 0
    for dirpath, dirnames, filenames in os.walk(root):
        dirnames[:] = [d for d in dirnames
                       if d not in ("__pycache__", ".git", ".venv", "node_modules")]
        for fn in sorted(filenames):
            if not fn.endswith(".py"):
                continue
            p = os.path.join(dirpath, fn)
            try:
                hits = scan(p)
            except SyntaxError as exc:
                print("%s: 파싱 실패 %s" % (p, exc))
                continue
            for lineno, kind, detail in hits:
                print("%s:%d: %s %s" % (p, lineno, kind, detail))
                total += 1
    print("총 %d건" % total)
    return 1 if total else 0

if __name__ == "__main__":
    sys.exit(main(sys.argv[1] if len(sys.argv) > 1 else "."))
```

검출 종류:

| 표시 | 의미 | 조치 |
|---|---|---|
| `LITERAL` | 리터럴과 `is` 비교 | 즉시 `==` 로 교체 |
| `EXPR` | 연산·변환 결과와 `is` 비교 | 즉시 `==` 로 교체 |
| `CONSTNAME` | 숫자·문자열 상수 이름과 `is` 비교 | 값 비교면 `==`, 싱글턴 의도면 `object()` 센티넬로 |
| `BOOLSINGLETON` | `is True` / `is False` | 진리값 검사 또는 `==` 로. 의도적이면 주석 |

### 4-3. 서드파티 도구를 쓸 수 있다면

- `flake8` 계열: `F632`(리터럴과 is 비교), `E712`(`== True` 비교)
- `pylint`: `literal-comparison`, `singleton-comparison`
- `ruff`: `F632`, `E711`, `E712`
- 이 환경에는 어느 것도 설치되어 있지 않아 4-1·4-2로 대신했다

## 5. 부울과 정수 — 겹치는 것들

| 식 | 결과 | 비고 |
|---|---|---|
| `issubclass(bool, int)` | `True` | 부울은 정수의 하위 클래스다 |
| `True == 1` | `True` | 값이 같다 |
| `True is 1` | `False` | 다른 객체다 |
| `hash(True) == hash(1)` | `True` | 딕셔너리에서 같은 칸에 들어간다 |
| `{1: 'a', True: 'b', 1.0: 'c'}` | `{1: 'c'}` | **먼저 넣은 키가 남고 값만 덮인다** |
| `{1, True, 1.0}` | `{1}` | 집합도 마찬가지 |
| `sum([True, True, False])` | `2` | 정수로 더해진다 |
| `type(True) is bool` | `True` | 타입 판별은 이렇게 |
| `isinstance(True, int)` | `True` | 정수 검사로는 부울을 못 걸러낸다 |

## 6. 점검 목록

- [ ] 값 비교에 `is` 를 쓴 곳이 없다 (`is_lint.py` 통과)
- [ ] `-W error::SyntaxWarning` 을 CI 에 넣었다
- [ ] `x == None` 을 `x is None` 으로 바꿨다
- [ ] `x is True` 는 「정확히 True 객체」를 뜻할 때만 남겼고 주석을 달았다
- [ ] 「값 없음」 판정에 `if not x:` 대신 센티넬(`object()`)을 썼다
- [ ] 정수 검사에 `isinstance(x, int)` 를 쓰는 곳에서 부울이 통과해도 괜찮은지 확인했다
- [ ] 딕셔너리·집합 키에 `0/False`, `1/True` 를 섞어 쓰지 않는다
- [ ] 테스트가 리터럴만 넣고 있지 않다. **문자열 파싱·직렬화·소켓을 거친 값**으로도 검증한다
- [ ] `is` 결과를 캐시 범위에 기대는 주석이나 문서가 없다
- [ ] `id()` 값을 저장하거나 프로세스 사이에 비교하지 않는다
- [ ] Enum·센티넬처럼 **의도적 싱글턴**에만 `is` 를 쓴다
- [ ] 코드 리뷰 규약에 「`is` 는 싱글턴 전용」을 적었다

## 7. 하지 말 것

- 캐시 범위 수치를 **언어 사양처럼** 문서에 적는 것 — 구현 세부다
- 대화형에서 확인한 `is` 결과를 스크립트 동작의 근거로 삼는 것 — 컴파일 단위가 다르다
- `id()` 가 같으니 같은 객체라고 결론짓는 것 — 수명이 겹치지 않는 두 객체는 같은 `id()` 를 가질 수 있다
- `is True` 로 「참인지」를 묻는 것 — 참인 값 대부분이 걸러진다
- `isinstance(x, int)` 로 부울을 배제하려는 것 — 통과한다
- 테스트가 초록이라는 이유로 `is` 비교를 그대로 두는 것 — **작은 값에서 우연히 통과했을 뿐일 수 있다**
