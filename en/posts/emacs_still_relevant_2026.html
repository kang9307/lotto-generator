Does Anyone Still Use Emacs? — The Vitality of a 50-Year-Old Editor in 2026

Why some developers still choose Emacs over VS Code and AI-native editors — extensibility, org-mode, hacker culture, and AI integration analyzed

2026-06-22 Dev & Infra

Introduction: The Question That Sparked a Debate

A question posted on GeekNews — "Does anyone still use Emacs?" — earned 29 points and sparked a surprisingly lively thread. In a world where VS Code commands 75.9% of developers and AI-native editors like Cursor are on a steep growth trajectory, a 50-year-old text editor generating real discussion is worth examining. Not out of nostalgia, but because the question reveals something important about how developers choose their tools.

Emacs was first written by Richard Stallman at the MIT AI Laboratory in 1976. GNU Emacs, launched as part of the GNU Project in 1984, has been under continuous active development ever since. As of June 2026, the current stable release is GNU Emacs 30.2, published on August 14, 2025. Half a century after its creation, it is still shipping new versions.

This analysis is neither an Emacs advocacy piece nor a dismissal. The aim is to answer honestly: why does this editor persist, and what does it mean for a modern developer to choose it in the age of AI coding tools?

1. Why Emacs Survived 50 Years — A Platform, Not an Editor

1.1 A Lisp Interpreter Disguised as an Editor

Calling Emacs a text editor is already slightly misleading. More precisely, it is a text editing environment built on top of an Emacs Lisp interpreter. This distinction is the root of its longevity.

VS Code can be configured through JSON settings and extensions, but you cannot fundamentally rewrite how the editor behaves — its core model is fixed. Emacs is different. Every event — cursor movement, keypress, file save — is a hook point where you can inject Lisp functions. Any behavior in the editor can be replaced, augmented, or composed with other behaviors. This is what "Emacs is a platform" actually means: users can redesign the tool itself to match exactly how they think.

This structure has produced things that go far beyond typical editor plugins: Magit (a Git client that many Git users consider the best interface to Git, period), mu4e (email), elfeed (RSS), dired (file manager), and org-mode (a productivity system discussed at length below). These behave less like plugins and more like standalone applications that share a unified keybinding model and buffer system.

1.2 Using Emacs as an Operating System

In the GeekNews discussion, one user described their computing workflow as: Git → Magit, Email → mu4e, RSS → elfeed, Notes/TODO/Calendar → org mode, File browsing → dired. Virtually all non-browser computing happens inside Emacs. At this level, Emacs is not an editor — it is a personal computing environment.

For such users, "switch to VS Code" is not a simple tool change. It means abandoning years of accumulated configuration, keybinding muscle memory, an org-mode database, and custom automation workflows. The switching cost is enormous. This is both the source of its loyal user base and the reason deeply invested users stay: the inertia is rational, not just sentimental.

2. org-mode — The Killer App With No Substitute

2.1 What org-mode Actually Is

When you ask Emacs users why they use it, the answer is almost always org-mode. org-mode is a plain-text productivity system developed over decades by the community, led by Bastien Guerry. A flat list of its capabilities:

  • Structured note-taking (headings, links, tables)
  • Project and task management (TODO states, priorities, tags)
  • Time tracking (CLOCK IN/OUT recorded automatically)
  • Calendar and agenda views (deadlines, recurring schedules)
  • Executable code blocks (org-babel — Python, Shell, SQL, and more)
  • Export to multiple formats (HTML, PDF, LaTeX, Markdown, EPUB)

All of this operates on a single plain-text file system. Because it is text, you can version-control it with Git, search it with grep, and open it in any editor. But only in Emacs with org-mode does the full functionality come alive.

2.2 Why It Has No Real Substitute

Notion, Obsidian, Roam Research, Logseq — all are excellent tools. But each replicates only part of what org-mode does. The combination that remains unique: executing code blocks inside documents and embedding the output (org-babel), an agenda that aggregates tasks from across all org files with CLOCK time tracking, and the ability to program any part of that system in Emacs Lisp. No single tool outside Emacs combines these three in a fully programmable way.

For developers, org-babel deserves special mention. You can fetch data with Python, format it as a table, and export the document as LaTeX — all within one org file, in a reproducible, version-controlled workflow. This is not a note-taking app; it is a practical implementation of literate programming.

3. Learning Curve vs. Reward — An Honest Calculation

3.1 Why It Is Genuinely Hard

Emacs has a notoriously steep learning curve for concrete reasons. First, the keybinding model diverges from modern conventions: C-x C-s to save, C-x C-f to open a file. Hands trained on Ctrl+S and Ctrl+O initially rebel. Second, configuration is Lisp code. Unlike JSON or YAML settings in modern tools, Emacs configuration means writing Emacs Lisp. Power grows with the language, but the barrier to entry is real. Third, there are too many starting points: vanilla Emacs, Doom Emacs, Spacemacs, or a custom setup from scratch — no obvious on-ramp.

3.2 How Doom Emacs and Spacemacs Changed the Entry Experience

Pre-configured distributions significantly lower the initial barrier. Doom Emacs ships with Vim-style keybindings (Evil mode) and a curated, optimized package set. Spacemacs integrates Vim and Emacs in a layer-based configuration. With either, you do not need to write Lisp from day one. Vim users can enter the Emacs ecosystem with familiar muscle memory intact via Evil mode.

In 2026, AI assistance has added another dimension. Using gptel to query an LLM about Emacs Lisp configuration turns what was once a deep mailing-list dive into a conversational exchange. The barrier to customizing your setup has dropped meaningfully.

3.3 The Return on Investment Calculation

One developer's concrete estimate: saving 15 minutes per day with Emacs produces approximately 65 hours — nearly three full days — per year. Over a decade-long career, that compounds to 30 days recovered. The calculation is not outlandish. Experienced Emacs users navigate files, search, replace, switch buffers, and run Git operations entirely from the keyboard without touching a menu. But realizing this ROI requires an upfront investment of 100+ hours. It is the right choice for a developer thinking in decades; it is the wrong choice when immediate delivery is the priority.

4. Hacker Culture and Philosophy — What Emacs Represents

4.1 The Free Software Movement's First Killer App

GNU Emacs is not just software — it is a statement. When Richard Stallman launched the GNU Project in 1983, Emacs was the first major tool he built. It was the first demonstration that free software could match or exceed commercial software quality. Stallman has described himself as a survivor of the MIT AI Lab hacker culture of the 1970s: the belief that software should be shared, inspected, and modified by anyone.

Using Emacs carries that history. The Emacs community has an unusual cohesion precisely because choosing the editor also implies endorsing a technical ethic. This is neither evangelism nor gatekeeping — it is simply context. The philosophy is baked into the GPL license, the development model, and the culture around the mailing lists.

4.2 Keyboard Autonomy and Remote Work

A common thread among Emacs users is the emphasis on working entirely from the keyboard. This is not aesthetic preference — it is a productivity argument. The physical time spent moving hand from keyboard to mouse and back, multiplied across a full workday and a full career, is not negligible. Emacs keybindings are designed to minimize that context switch. Long-time users describe the keyboard as "an extension of thought rather than a tool they are operating."

This autonomy becomes critical in SSH environments. On a remote server over a slow connection, Emacs operates with full functionality in a terminal without any GUI layer. VS Code's Remote SSH extension has addressed this significantly, but in resource-constrained or unstable connection scenarios, a terminal-native editor retains real advantages. Many infrastructure engineers and system administrators run Emacs persistently on remote servers for exactly this reason.

5. Current Usage Numbers — The Honest Picture

5.1 Market Share Reality

The numbers are unambiguous. VS Code sits at 75.9% in Stack Overflow's 2025 Developer Survey. Emacs registers at 8–9% in LinuxQuestions polls — and that is dwarfed by Vim/Neovim at 37–38%. In the AI-native editor segment, Cursor debuted at 17.9% and Claude Code reached 9.7% in its first year, while Emacs does not appear as a measurable category. By popularity metrics, there is no case to make for Emacs.

5.2 Active Development Tells a Different Story

Development activity is a different metric. GNU Emacs 30.2 shipped in August 2025 with changes that reflect a project investing in modernization, not maintenance:

  • Native compilation now default: Emacs Lisp compiled to machine code via libgccjit, delivering substantial performance gains for Magit, org-mode, and Lisp-heavy packages
  • which-key built in: keybinding hints without a third-party package
  • EditorConfig built-in support
  • Tree-Sitter modes expanded: Elixir, HEEx, HTML, Lua, PHP and more
  • Native Android support with touchscreen input
  • JSON parsing and subprocess handling performance improvements

This is not a project coasting on legacy. It is actively absorbing features that previously required external packages and extending to new platforms.

6. Emacs in the AI Coding Era

6.1 The AI Integration Ecosystem

AI coding tools have become a decisive variable in editor choice by 2026. Emacs's response is more coherent than expected:

  • gptel: LLM chat client supporting Claude, GPT, Gemini, Ollama, and others — usable in any Emacs buffer, with MCP (Model Context Protocol) integration. Native Anthropic support since version 0.9.
  • copilot.el: Connects directly to the GitHub Copilot language server for inline ghost-text completions. Upgraded to the official Node package in early 2025.
  • ellama: Task-specific LLM commands (summarize, refactor, translate) backed by Ollama or other local models.
  • aider.el: Emacs integration for the Aider AI pair programming tool.
  • Claude Code: Terminal-based, editor-agnostic — Emacs users run it alongside their editor and review results in Emacs buffers.

The extensibility that defines Emacs applies here too. Combining gptel with org-babel lets you record AI responses directly into an org document, or immediately execute AI-generated code in a buffer — workflows that are difficult to replicate in more rigid environments.

6.2 Where AI-Native Editors Win

Honest assessment: for inline AI coding experience, Cursor and VS Code with Copilot are smoother out of the box. Cursor is designed from the ground up with AI as the core interaction model — multi-file context, codebase-wide queries, and one-click application are unified. Emacs AI tooling is powerful but requires assembly. It is a kit of parts, not a finished product. This is consistent with Emacs philosophy, but it is a genuine tradeoff for users who want the best AI coding experience without configuration work.

7. Who Should Choose Emacs in 2026 — and Who Should Not

7.1 Emacs Is the Right Choice When

  • You want to manage personal knowledge the way you manage code — org-mode is the answer
  • You want to fully redesign editor behavior to match your thinking — Emacs Lisp extensibility
  • You work heavily over SSH, on remote servers, or in low-resource environments
  • You want to maintain one tool across a decades-long career
  • You align with free software philosophy (GNU GPL)

7.2 Emacs Is Not the Right Choice When

  • Your team is standardized on VS Code and collaborative extensions matter
  • You want the best out-of-the-box AI inline coding experience — use Cursor
  • You need to be productive immediately — the learning curve is a real cost
  • You prefer GUI-driven configuration over writing Lisp

7.3 A Spectrum, Not a Binary

The editor wars are "over" in the sense that VS Code won the popularity contest decisively. But that does not mean Emacs was wrong. A craftsperson choosing hand tools over automated machinery for specific work is not being irrational — for certain tasks and certain workers, that is the optimal choice. Emacs provides its users with "an editor you spend a lifetime learning," and for the developers who value that — the process of building the tool as much as using it — Emacs is not a productivity instrument but an extension of the craft of programming itself.

8. Conclusion — Someone Will Still Use Emacs in 50 More Years

To answer the GeekNews question directly: yes, people still use Emacs. And they will continue to. Not because of popularity — but because the specific needs Emacs fills have not disappeared: managing knowledge as programmable text through org-mode, reshaping the editor to match exactly how you think with Emacs Lisp, and working in any environment with the same keyboard system.

As of June 2026, GNU Emacs 30.2 is under active development, new developers are picking it up, and AI integration packages are shipping regularly. The vitality of a 50-year-old editor does not come from market share. It comes from irreplaceable functionality and unlimited customizability. That is a durable foundation — enough to still be standing when the next generation of AI editors makes Cursor look dated.
