git 되돌리기 결정표 - reset·revert·restore·checkout 중 무엇을 쓸 것인가

대상이 어디에 있나, 이미 공유했나. 이 두 질문이 명령을 거의 정한다

2026-09-01 개발/인프라

되돌리기가 어려운 이유는 명령이 많아서가 아니다. 선택지가 서로 비슷하게 생겼는데 결과는 전혀 다르기 때문이다. reset 은 커밋을 없애고 revert 는 커밋을 더한다. restore 는 브랜치를 건드리지 않고 checkout 은 둘 다 한다. 이름만 보고는 구분이 안 된다.

그래서 이 글은 명령어 목록이 아니라 결정 절차다. 먼저 두 가지를 묻고, 그 답에서 명령이 나온다. 아래 예제는 전부 빈 임시 저장소를 새로 만들어 직접 실행한 것이고, 붙인 출력은 그때 실제로 나온 것이다.

이 글의 명령 중 일부는 되돌릴 수 없는 파괴적 동작이다. 각 절에 「되살릴 수 있나」를 따로 적어 뒀다. 처음 보는 명령은 실제 작업 저장소가 아니라 git init 으로 만든 빈 저장소에서 먼저 돌려 보기를 권한다.

되돌리기 전에 물어야 할 두 가지

손이 먼저 나가기 전에 물어야 할 것은 두 개뿐이다. 이 두 답이 정해지면 쓸 수 있는 명령은 대개 하나로 좁혀진다.

  • 첫째, 되돌릴 대상이 어디에 있나. 아직 저장만 한 상태인가(작업트리), git add 까지 했나(인덱스), 아니면 git commit 까지 했나(HEAD). 여기가 정해지면 restore 를 쓸지 reset 을 쓸지가 갈린다
  • 둘째, 그 커밋을 이미 공유했나. 푸시했거나 남이 가져갔다면 그 커밋은 더 이상 내 것이 아니다. 여기가 정해지면 reset 을 쓸지 revert 를 쓸지가 갈린다
  • 세 번째 질문은 사실 확인용이다. 이 변경이 한 번이라도 커밋된 적이 있나. 없다면 어떤 명령으로 날려도 되살릴 방법이 없다

많은 사고가 두 번째 질문을 건너뛰어서 생긴다. 로컬에서 reset --hard 로 커밋을 지우는 것은 아무 문제가 없다. 같은 동작을 이미 푸시한 커밋에 하면, 그 브랜치를 가진 모든 사람의 저장소가 어긋난다. 명령은 같은데 대가가 다르다. 이 비대칭이 잘 안 보이는 이유는 명령을 치는 순간에는 Git 이 아무 경고도 하지 않기 때문이다. 결과는 며칠 뒤 남의 장비에서, 그 사람이 평소처럼 git pull 을 했을 때 처음 드러난다.

세 영역 - 작업트리, 인덱스, HEAD

Git 에서 한 파일의 내용은 동시에 세 군데에 있을 수 있다. 편집기로 저장한 작업트리, git add 로 올려 둔 인덱스(스테이지), 그리고 마지막 커밋인 HEAD다. 되돌리기 명령은 이 셋 중 몇 개를 건드리느냐로 성격이 갈린다.

세 영역이 서로 다른 상태일 때 git status 가 어떻게 보이는지 먼저 봐 두면 나머지가 쉬워진다. 파일 하나는 수정만 했고, 하나는 새로 만들어 add 했고, 하나는 그냥 만들어만 뒀다.

$ cd /tmp/demo
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	new file:   b.txt

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   a.txt

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	c.txt

$ git status --short
 M a.txt
A  b.txt
?? c.txt

--short 출력의 두 칸이 그대로 두 영역이다. 앞칸은 인덱스, 뒷칸은 작업트리를 뜻한다. A  b.txt 는 인덱스에만 변화가 있다는 뜻이고,  M a.txt 는 작업트리에만 있다는 뜻이다. 둘 다 바뀌면 MM 이 된다. 이 두 글자를 읽을 줄 알면 어떤 명령을 써야 하는지가 화면에 이미 적혀 있는 셈이다.

친절하게도 git status 는 각 묶음 아래에 해법까지 적어 준다. 스테이지에서 내리려면 git restore --staged, 작업트리 변경을 버리려면 git restore 라고 말이다. 아래 표가 그 대응을 정리한 것이다.

영역무엇이 들어 있나status --short 표시여기 있는 것을 되돌리는 명령
작업트리편집기로 저장한 지금 파일 내용뒷칸의 M·D, 추적 안 되면 ??git restore <파일>, 추적 안 되면 git clean
인덱스(스테이지)git add 로 올려 둔, 다음 커밋에 들어갈 내용앞칸의 M·A·Dgit restore --staged <파일>, git reset
HEAD(커밋)이미 기록된 히스토리git log 로만 보인다미공유면 git reset, 공유했으면 git revert

결정표 - 어디에 있나 곱하기 공유했나

이 글의 중심은 이 표다. 세로축이 첫 번째 질문, 가로축이 두 번째 질문이다. 나머지 절은 이 칸들을 하나씩 실행해 확인한 기록이라고 봐도 된다.

되돌릴 대상이 어디에 있나아직 내 저장소에만 있다이미 푸시했다되살릴 수 있나
작업트리 수정 (add 안 함)git restore <파일>해당 없음 - 공유된 적이 없다아니오. 커밋된 적 없으면 끝이다
인덱스에 올린 변경 (add 함)git restore --staged <파일>해당 없음예. 파일 내용은 그대로 남는다
마지막 커밋의 메시지·구성git commit --amend쓰지 않는다. git revert 로예. reflog 에 옛 커밋이 남는다
마지막 커밋 자체git reset --soft/--mixed/--hard HEAD~1쓰지 않는다. git revert HEAD커밋은 예(reflog), 작업트리는 아니오
여러 커밋git reset --hard <커밋>git revert <오래된>..<최신>커밋은 예(reflog)
추적되지 않은 파일git clean -n 으로 확인 후 -fd해당 없음아니오. Git 이 모르는 파일이다
브랜치를 잘못 골랐다git switch -c <브랜치> 후 원래 브랜치를 resetgit revert 후 올바른 브랜치에서 다시예

표에서 「이미 푸시했다」 열에 reset 이 한 번도 나오지 않는다는 점이 핵심이다. 예외를 만들 수는 있지만, 그 예외는 팀 전체가 동의하고 시점을 맞춰야 성립한다. 혼자 결정할 일이 아니다.

표의 상당 부분이 첫째 열만으로 결정된다는 것도 볼 만하다. 아직 내 저장소에만 있다면 무엇을 해도 대체로 괜찮다. 불편해질 사람이 나뿐이고, 뒤에는 reflog 가 받쳐 주기 때문이다. 두 번째 질문의 답이 「예」로 바뀌는 순간 쓸 수 있는 명령은 사실상 하나로 줄어드는데, 이유는 기술적 순수함이 아니다. 그 줄의 다른 명령들은 예고 없이 남의 책상에 일거리를 만든다는 것이 이유다.

git restore - 파일 단위로 되돌린다

restore 는 Git 2.23 에서 checkout 으로부터 갈라져 나왔다. 하는 일이 좁아서 오히려 쓰기 쉽다. Git 공식 문서의 Reset, restore and revert 절은 이 명령을 「작업트리의 파일을 인덱스나 다른 커밋으로부터 복원하는 것」이라고 설명하고, 곧바로 「이 명령은 브랜치를 갱신하지 않는다」고 못을 박는다. 히스토리를 건드리지 않는다는 뜻이다.

중요한 것은 --staged 하나로 성격이 완전히 달라진다는 점이다. 아래는 같은 파일에 대해 스테이지에 beta 를 올려 두고, 작업트리에만 gamma 를 더한 상태에서 두 명령을 차례로 실행한 것이다.

$ git status --short
MM note.txt

# 1) 인덱스만 되돌린다 - 파일 내용은 그대로
$ git restore --staged note.txt
$ git status --short
 M note.txt
$ cat note.txt
alpha
beta
gamma

# 2) 작업트리를 되돌린다 - 여기서 내용이 사라진다
$ git restore note.txt
$ git status --short
$ cat note.txt
alpha

두 번째 명령이 실행된 순간 beta 와 gamma 는 없어졌다. 한 번도 커밋된 적이 없으므로 돌아올 길이 없다. restore 가 순해 보이는 이름을 달고 있지만 파괴적 명령인 이유가 이것이다. 반대로 --staged 만 붙인 첫 번째 명령은 파일을 전혀 건드리지 않았다.

  • git restore --staged <파일> - 언스테이지. 되돌릴 수 있다. 파일 내용은 그대로다
  • git restore <파일> - 작업트리 변경 폐기. 되돌릴 수 없다. 커밋 전 내용은 사라진다
  • git restore --staged --worktree <파일> - 둘 다. 실행하면 MM 이 한 번에 사라진다
  • git restore --source=<커밋> <파일> - 그 커밋 시점의 파일을 가져온다. 히스토리는 그대로다
  • 실수로 rm 한 추적 파일도 git restore <파일> 로 그대로 돌아온다. 이쪽은 안전한 용법이다

마지막 용법이 의외로 자주 쓰인다. 히스토리는 그대로 두고 파일 하나만 옛 버전으로 되돌리고 싶을 때다. 커밋 세 개짜리 저장소에서 한 단계 전 버전을 꺼내면 이렇게 된다.

$ git log --oneline
1beb864 add delta
4fb8d79 add beta
96d2ca7 add note

$ git restore --source=HEAD~1 note.txt
$ cat note.txt
alpha
beta
$ git status --short
 M note.txt

브랜치는 add delta 에 그대로 있고, 파일만 이전 상태가 되어 수정된 것으로 잡힌다. 여기서 커밋하면 「되돌리는 새 커밋」이 하나 생긴다. revert 를 파일 단위로 흉내 내는 셈이다.

git reset - 세 모드가 어디까지 되돌리는가

reset 은 세 명령 중 유일하게 브랜치의 끝을 옮기는 명령이다. 공식 문서의 표현대로 「커밋을 브랜치에서 더하거나 빼기 위해 끝을 움직이는 것」이고, 그래서 커밋 히스토리가 바뀐다. 세 모드는 HEAD 를 옮긴 뒤 인덱스와 작업트리를 어디까지 따라 옮기느냐로만 다르다.

같은 저장소를 세 벌 만들어 각각 HEAD~1 로 되돌렸다. 커밋은 C1 base, C2 feature, C3 oops 순이고 파일은 매번 한 줄씩 늘어난다.

$ git log --oneline
2152c39 C3 oops
3e571a5 C2 feature
44cb882 C1 base

$ git reset --soft HEAD~1
$ git log --oneline
3e571a5 C2 feature
44cb882 C1 base
$ git status --short
M  app.txt
$ cat app.txt
v1
v2
v3

--soft 는 커밋만 없앴다. C3 가 담고 있던 변경은 앞칸 M, 즉 스테이지에 그대로 올라와 있다. 커밋 메시지만 다시 쓰고 싶거나 커밋 여러 개를 하나로 합치고 싶을 때 쓰는 모드다.

$ git reset --mixed HEAD~1
Unstaged changes after reset:
M	app.txt
$ git log --oneline
17b85e8 C2 feature
d42f7bf C1 base
$ git status --short
 M app.txt
$ cat app.txt
v1
v2
v3

--mixed 는 인덱스까지 되돌렸다. 같은 변경이 뒷칸 M 으로 내려왔다. 파일 내용은 여전히 v3 까지 그대로다. 옵션을 생략한 git reset 이 이 모드이고, 인자 없이 git reset 만 치면 --mixed HEAD 가 되어 스테이지에 올린 것이 전부 내려온다.

$ git reset --hard HEAD~1
HEAD is now at add35e9 C2 feature
$ git log --oneline
add35e9 C2 feature
453f0e3 C1 base
$ git status --short
$ cat app.txt
v1
v2

--hard 만 파일을 실제로 바꿨다. status 는 비었고 v3 는 사라졌다. 문서도 이 모드에 대해서만 「추적 파일의 변경은 폐기된다」고 적는다. 세 모드 중 커밋되지 않은 내용을 잃을 수 있는 것은 이것뿐이다.

모드HEAD인덱스작업트리실행 후 status --short잃을 수 있는 것
--soft옮긴다그대로그대로M  app.txt (앞칸)없음
--mixed (기본)옮긴다되돌린다그대로 M app.txt (뒷칸)스테이지 구성만
--hard옮긴다되돌린다되돌린다비어 있음커밋 안 한 변경 전부

git revert - 되돌리는 새 커밋을 만든다

revert 는 앞의 둘과 성격이 다르다. 문서의 첫 문장이 그대로 정의다. 「주어진 커밋들이 넣은 변경을 되돌리고, 그것을 기록하는 새 커밋을 만든다」. 옛 커밋은 그 자리에 남는다. 히스토리가 짧아지는 게 아니라 길어진다.

$ git log --oneline
e4285bf C3 enable debug
b1fe989 C2 add timeout
f001827 C1 add config

$ git revert --no-edit HEAD
[main 83f6fc6] Revert "C3 enable debug"
 1 file changed, 1 deletion(-)
 delete mode 100644 debug.txt

$ git log --oneline
83f6fc6 Revert "C3 enable debug"
e4285bf C3 enable debug
b1fe989 C2 add timeout
f001827 C1 add config
$ git status --short

C3 는 그대로 있고 그 위에 Revert "C3 enable debug" 가 쌓였다. 결과 파일은 C2 시점과 같아졌지만, 기록상으로는 「했다가 물렀다」가 둘 다 남는다. 감사 추적이 필요한 저장소에서 이것은 단점이 아니라 장점이다.

다만 revert 가 늘 조용히 끝나지는 않는다. 되돌리려는 커밋 이후에 같은 자리를 건드린 커밋이 있으면 충돌한다. 같은 파일의 인접한 줄을 계속 고친 히스토리에서 가운데 커밋을 되돌리면 이렇게 된다.

$ git revert --no-edit HEAD~1
Auto-merging config.txt
CONFLICT (content): Merge conflict in config.txt
error: could not revert 17a5abe... C2 enable debug
hint: After resolving the conflicts, mark them with
hint: "git add/rm <pathspec>", then run
hint: "git revert --continue".
hint: You can instead skip this commit with "git revert --skip".
hint: To abort and get back to the state before "git revert",
hint: run "git revert --abort".

$ git status --short
UU config.txt

$ git revert --abort
$ git log --oneline
08823c4 C3 enable cache
17a5abe C2 enable debug
9b96f25 C1 add config
$ git status --short

여기서 눈여겨볼 것은 git revert --abort 다. 충돌 상태에서 이 한 줄이면 저장소가 시작 전 상태로 완전히 돌아간다. revert 는 실패해도 안전하게 물러설 길이 있는, 이 글에서 가장 되돌리기 쉬운 명령이다.

  • git revert <커밋> - 새 커밋을 만든다. 되돌릴 수 있다. 그 새 커밋을 다시 revert 하면 원상복구다
  • --no-edit 을 붙이면 기본 메시지로 바로 커밋한다. 편집기가 뜨지 않는다
  • 충돌하면 멈춘다. --abort 로 전부 취소, --continue 로 해결 후 진행, --skip 으로 그 커밋만 건너뛴다
  • 여러 개를 되돌릴 때는 git revert <오래된>..<최신> 처럼 범위를 준다. 최신 것부터 차례로 처리된다
  • 작업트리가 깨끗해야 시작한다. 문서에 명시된 전제 조건이다

공유한 커밋을 고쳐 쓰면 남에게 무슨 일이 생기는가

「푸시한 커밋에는 revert 를 쓰라」는 말은 자주 들리지만 이유를 겪어 보기 전에는 잘 와닿지 않는다. 저장소 하나를 만들고 그것을 복제해 동료 쪽을 흉내 낸 뒤, 두 가지 방식으로 같은 실수를 되돌려 봤다. 아래 출력에서 저장소 경로만 /tmp/demo/upstream 으로 바꿔 적었다.

# 동료의 클론 - 문제의 커밋을 이미 갖고 있다
$ git log --oneline
97b65d9 C2 bad change
2135f94 C1 base

# 내 쪽에서 revert
$ git revert --no-edit HEAD
[main 7085b16] Revert "C2 bad change"
 1 file changed, 1 deletion(-)

# 동료가 pull
$ git pull
From /tmp/demo/upstream
   97b65d9..7085b16  main       -> origin/main
Updating 97b65d9..7085b16
Fast-forward
 app.txt | 1 -
 1 file changed, 1 deletion(-)

Fast-forward 한 줄로 끝났다. 동료는 아무것도 하지 않았고 충돌도 없다. 이번에는 같은 상황에서 커밋을 지우고 다시 만들어 봤다.

# 동료의 클론 - 같은 출발점
$ git log --oneline
689d5e6 C2 bad change
f43e101 C1 base

# 내 쪽에서 C2 를 지우고 제대로 다시 만든다
$ git reset --hard HEAD~1
HEAD is now at f43e101 C1 base
$ printf 'v1\ngood change\n' > app.txt
$ git add app.txt && git commit -q -m "C2 good change"
$ git log --oneline
2727247 C2 good change
f43e101 C1 base

# 동료가 pull
$ git pull
From /tmp/demo/upstream
 + 689d5e6...2727247 main       -> origin/main  (forced update)
Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
Automatic merge failed; fix conflicts and then commit the result.

$ git status --short
UU app.txt
$ cat app.txt
v1
<<<<<<< HEAD
bad change
=======
good change
>>>>>>> 272724744769a515b2d1fc26330c4883201016a3

같은 목적, 같은 최종 상태인데 동료 쪽 결과가 전혀 다르다. forced update 가 뜨고 충돌 표식이 파일에 박혔다. 내가 아낀 커밋 하나가 팀 인원수만큼의 충돌 해결로 바뀐 것이다. 그것도 그 사람들은 무슨 일이 있었는지 모른 채로.

강제 푸시(git push --force)는 여기에 더 큰 위험을 얹는다. 내가 마지막으로 가져온 뒤 남이 올린 커밋이 있으면 그것까지 지워 버린다. --force-with-lease 는 원격의 현재 값이 내가 아는 값과 같을 때만 밀어 넣어 그 사고를 막아 주지만, 「지워도 된다」는 허락은 아니다. 공유 브랜치에서는 어느 쪽도 기본 선택지가 아니다.

git checkout 은 왜 헷갈렸나

checkout 이 어려운 것은 이 명령이 성격이 다른 두 일을 겸했기 때문이다. 브랜치를 옮기는 일과 파일을 복원하는 일은 위험도가 완전히 다른데 이름이 같았다. 그래서 인자에 따라 결과가 달라지고, 이름이 겹치면 어느 쪽인지 알기 어려워진다.

실제로 겹치게 만들어 보면 결과가 분명하다. app.txt 라는 파일이 있는 저장소에 app.txt 라는 브랜치를 만들고, 파일을 고친 다음 checkout 을 실행했다.

$ git branch app.txt
$ printf 'v2\n' > app.txt
$ git checkout app.txt
M	app.txt
Switched to branch 'app.txt'
$ git branch --show-current
app.txt
$ cat app.txt
v2

# 2.23 이후: 이름이 겹쳐도 뜻이 하나뿐이다
$ git switch app.txt
Switched to branch 'app.txt'
$ git restore app.txt
$ cat app.txt
v1

파일을 되돌리려던 사람은 브랜치가 바뀐 것을 나중에야 알게 된다. Git 2.23 의 릴리스 노트는 이 문제를 정면으로 다뤘다. 「브랜치를 체크아웃해 히스토리를 진전시키는 일」과 「인덱스나 트리에서 경로를 체크아웃하는 일」을 하나의 git checkout 에서 떼어 내기 위해 switch 와 restore 를 도입했다는 것이다.

checkout 의 또 다른 얼굴은 커밋을 직접 지정했을 때다. 브랜치가 아닌 커밋으로 가면 detached HEAD 가 된다. 여기서 커밋하면 어느 브랜치에도 속하지 않는 커밋이 생긴다.

$ git checkout HEAD~1
Note: switching to 'HEAD~1'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.
...
HEAD is now at f91e4ef C1 base

$ git status | head -2
HEAD detached at f91e4ef
nothing to commit, working tree clean

$ git switch main
Previous HEAD position was f91e4ef C1 base
Switched to branch 'main'

이 상태가 위험한 것은 아니다. 안내문이 말하는 대로 둘러보고 실험하기에 좋은 자리다. 문제는 여기서 만든 커밋을 브랜치로 옮기지 않고 떠날 때다. 그때도 reflog 가 남지만, 애초에 git switch -c <이름> 으로 이름을 붙여 두는 편이 훨씬 낫다.

git reflog - 날린 커밋이 살아나는 길

이 글에서 하나만 기억한다면 이 절이다. reset --hard 로 커밋을 날려도 대개는 되살릴 수 있다. Git 은 HEAD 가 거쳐 간 모든 위치를 reflog 에 적어 두기 때문이다. 커밋 세 개짜리 저장소에서 두 개를 날린 뒤 되살리는 전 과정이다.

$ git log --oneline
78b8ce0 C3 more work
f1acddb C2 two days of work
7810949 C1 base

# 사고
$ git reset --hard HEAD~2
HEAD is now at 7810949 C1 base
$ git log --oneline
7810949 C1 base
$ cat work.txt
v1

# 구조: 지워진 커밋이 여기 있다
$ git reflog
7810949 HEAD@{0}: reset: moving to HEAD~2
78b8ce0 HEAD@{1}: commit: C3 more work
f1acddb HEAD@{2}: commit: C2 two days of work
7810949 HEAD@{3}: commit (initial): C1 base

$ git reset --hard HEAD@{1}
HEAD is now at 78b8ce0 C3 more work
$ git log --oneline
78b8ce0 C3 more work
f1acddb C2 two days of work
7810949 C1 base
$ cat work.txt
v1
v2
v3

HEAD@{1} 은 「한 단계 전에 HEAD 가 있던 곳」이라는 뜻이다. reset --hard 직전 위치가 거기 그대로 있다. 이 사실을 알고 나면 reset --hard 에 대한 공포가 절반쯤 줄어든다. 나머지 절반은 다음 절에서 다룬다.

직전 위치는 이름으로도 잡힌다. ORIG_HEAD 는 reset 이나 merge 같은 큰 이동 직전의 HEAD 를 가리킨다. 브랜치별 이동만 보고 싶으면 git reflog show <브랜치> 를 쓴다.

$ git reset --hard HEAD~2
HEAD is now at f1c8944 C1
$ git rev-parse --short ORIG_HEAD
4d26ce7
$ git reset --hard ORIG_HEAD
HEAD is now at 4d26ce7 C3

$ git reflog show main
4d26ce7 main@{0}: reset: moving to ORIG_HEAD
f1c8944 main@{1}: reset: moving to HEAD~2
4d26ce7 main@{2}: commit: C3
b8efd2c main@{3}: commit: C2
f1c8944 main@{4}: commit (initial): C1
  • reflog 는 저장소마다 로컬이다. 클론에는 따라가지 않고, 남의 사고를 내 reflog 로 구할 수는 없다
  • 영구 보존이 아니다. 설정 문서 기준 gc.reflogExpire 기본값은 90일, 현재 브랜치에서 닿지 않는 항목을 다루는 gc.reflogExpireUnreachable 은 30일이다
  • 후자가 더 짧은 이유도 문서에 적혀 있다. commit --amend 나 rebase 로 생기는 옛 커밋들이라 더 일찍 지워도 된다고 본 것이다
  • 그러니 「나중에 reflog 로 찾지」는 몇 달짜리 계획이 못 된다. 사고를 알아챘으면 그날 처리한다

되살릴 수 없는 것

reflog 는 커밋을 기록하는 장치다. 작업트리를 기록하는 장치가 아니다. 그래서 한 번도 커밋된 적 없는 변경은 어떤 명령으로 날려도 돌아오지 않는다. 한 시간 동안 고쳤지만 커밋하지 않은 파일 위에 reset --hard 를 돌리면 이렇게 된다.

$ cat draft.txt
committed line
an hour of work that was never committed
$ git status --short
 M draft.txt

$ git reset --hard HEAD
HEAD is now at 371a5ec C1 base
$ cat draft.txt
committed line

$ git reflog
371a5ec HEAD@{0}: reset: moving to HEAD
371a5ec HEAD@{1}: commit (initial): C1 base

$ git fsck --lost-found
$

reflog 에는 커밋 하나와 reset 기록밖에 없다. git fsck --lost-found 도 아무것도 내놓지 않는다. 그 한 시간은 Git 이 한 번도 본 적이 없는 내용이었기 때문이다. 여기에 예외가 하나 있다. git add 까지 했다면 그 내용은 객체로 저장돼 있어 fsck 로 찾을 여지가 생긴다. 스테이지에 올리는 습관이 안전망이 되는 자리다.

명령무엇을 지우나되살릴 길먼저 할 것
git reset --hard커밋 + 커밋 안 한 변경커밋은 reflog, 변경은 없음git stash push -u
git restore <파일>그 파일의 커밋 안 한 변경없음git diff 로 무엇이 사라질지 확인
git clean -fd추적되지 않은 파일·디렉터리없음git clean -nd 로 목록 확인
git commit --amend직전 커밋(대체된다)reflog푸시했는지 확인
git revert아무것도 지우지 않는다다시 revert작업트리를 깨끗이

git stash - 위험한 명령 앞에 한 줄

앞 절의 사고를 막는 가장 값싼 방법은 stash 다. 커밋할 만큼 정리되지 않은 변경을 잠시 치워 두고, 작업트리를 깨끗하게 만든다. 치워 둔 내용은 Git 객체로 저장되므로 커밋과 같은 수준으로 안전해진다.

$ git status --short
 M tracked.txt
?? newfile.txt

$ git stash push -m wip
Saved working directory and index state On main: wip
$ git status --short
?? newfile.txt

# 새로 만든 파일은 담기지 않았다. -u 를 붙여야 한다
$ git stash push -u -m wip2
Saved working directory and index state On main: wip2
$ git status --short
$ git stash list
stash@{0}: On main: wip2

$ git stash pop
...
Dropped refs/stash@{0}

첫 번째 stash push 뒤에도 newfile.txt 가 그대로 남은 것이 핵심이다. stash 는 기본적으로 추적되지 않은 파일을 담지 않는다. 「스태시했으니 안전하다」고 믿고 reset --hard 나 clean -fd 를 돌리면 새로 만든 파일만 골라서 사라진다. 습관으로 -u 를 붙이는 편이 낫다.

  • git stash push -u -m <메모> - 추적 파일과 새 파일을 함께 담는다. 메모를 남기면 나중에 목록에서 알아볼 수 있다
  • git stash list 로 확인, git stash pop 으로 꺼내면서 삭제, git stash apply 로 꺼내되 남겨 둔다
  • 스태시도 reflog 를 갖는다. 실수로 drop 했다면 git fsck 나 git stash list 이전 기록에서 찾을 여지가 있다
  • 다만 영구 보관함이 아니다. 며칠 넘게 둘 것이라면 임시 브랜치에 커밋하는 편이 안전하다

git clean - 되돌릴 수 없는 삭제

clean 은 이 글에서 가장 단순하고 가장 위험하다. 문서 그대로 「버전 관리 아래에 있지 않은 파일을 재귀적으로 지워 작업트리를 청소」한다. Git 이 모르는 파일이므로 지운 뒤에는 Git 안에 아무 흔적도 없다.

$ git status --short
?? build/
?? notes.md
?? out.log

# -n 은 지우지 않는다. 목록만 보여 준다
$ git clean -n
Would remove notes.md
Would remove out.log

# 디렉터리는 -d 를 붙여야 보인다
$ git clean -nd
Would remove build/
Would remove notes.md
Would remove out.log

$ git clean -fd
Removing build/
Removing notes.md
Removing out.log
$ ls
keep.txt

-n 과 -nd 의 결과가 다른 것을 눈여겨봐야 한다. -d 없이는 디렉터리가 목록에 아예 나오지 않는다. -n 만 보고 안심한 뒤 -fd 를 실행하면 예상보다 많이 지워진다. 순서는 하나뿐이다. -nd 로 먼저 보고, 목록을 읽고, 그다음 -fd 다.

-x 는 여기서 한 발 더 나간다. .gitignore 로 무시되는 파일까지 지운다. 빌드 산출물을 정리할 때는 유용하지만, 무시 목록에는 .env 같은 로컬 설정이 들어 있는 경우가 흔하다. 같이 사라진다.

메시지가 틀렸거나 파일을 빠뜨렸을 때

커밋 직후에 발견하는 실수는 대부분 두 가지다. 메시지에 오타가 있거나, 넣었어야 할 파일을 빠뜨렸거나. 둘 다 git commit --amend 하나로 처리된다. 새 커밋을 쌓는 것이 아니라 직전 커밋을 새 커밋으로 대체하는 동작이다.

$ git log --oneline
d8ed825 fix bugg
689816b C1 base

# 1) 메시지만 고친다
$ git commit --amend -m "fix bug"
$ git log --oneline
ca1558d fix bug
689816b C1 base

# 2) 빠뜨린 파일을 넣는다
$ git add c.txt
$ git commit --amend --no-edit
$ git show --name-only --oneline HEAD
5ef662d fix bug
b.txt
c.txt

$ git reflog
5ef662d HEAD@{0}: commit (amend): fix bug
ca1558d HEAD@{1}: commit (amend): fix bug
d8ed825 HEAD@{2}: commit: fix bugg
689816b HEAD@{3}: commit (initial): C1 base

해시가 d8ed825 → ca1558d → 5ef662d 로 매번 바뀐 것이 중요하다. amend 는 커밋을 고치는 것이 아니라 새로 만들어 갈아 끼우는 것이다. 그래서 이미 푸시한 커밋에 쓰면 앞 절에서 본 forced update 상황이 그대로 재현된다. 원칙은 하나다. 푸시 전에만 쓴다.

amend 자체를 무르고 싶으면 reflog 를 쓴다. 위 상태에서 git reset --hard HEAD@{1} 을 실행하면 파일을 넣기 전의 ca1558d 로 정확히 돌아간다.

잘못된 브랜치에 커밋했을 때

main 에서 작업하다 커밋까지 해 버린 상황은 흔하다. 이때 손이 먼저 나가면 reset --hard 로 커밋을 날리고 처음부터 다시 하게 되는데, 그럴 필요가 없다. 커밋은 그대로 두고 이름표만 옮기면 된다.

$ git log --oneline --decorate
501da69 (HEAD -> main) C2 feature work
032adf6 C1 base

# 1) 지금 자리에 브랜치를 새로 만든다 - 커밋이 따라온다
$ git switch -c feature
Switched to a new branch 'feature'
$ git log --oneline --decorate
501da69 (HEAD -> feature, main) C2 feature work
032adf6 C1 base

# 2) main 으로 돌아가 한 칸 물린다
$ git switch main
$ git reset --hard HEAD~1
HEAD is now at 032adf6 C1 base
$ git log --oneline --decorate
032adf6 (HEAD -> main) C1 base
$ git log --oneline --decorate feature
501da69 (feature) C2 feature work

순서가 중요하다. 먼저 브랜치를 만들고, 그다음에 main 을 되돌린다. 반대로 하면 커밋이 어느 브랜치에도 속하지 않게 되고, 되찾으려면 reflog 를 뒤져야 한다. 그리고 이 절차는 main 을 아직 푸시하지 않았을 때만 쓴다. 이미 푸시했다면 revert 로 되돌리고 올바른 브랜치에서 다시 커밋한다.

아직 커밋하지 않았다면 더 간단하다. 브랜치를 바꿔도 커밋되지 않은 변경은 따라온다. 그리고 따라올 수 없는 상황이면 Git 이 알아서 멈춘다.

# 커밋 전이라면 그냥 옮겨 가면 된다
$ git status --short
 M app.txt
$ git switch -c feature
Switched to a new branch 'feature'
$ git status --short
 M app.txt

# 대상 브랜치가 같은 파일을 건드렸다면 Git 이 막는다
$ git switch other
error: Your local changes to the following files would be overwritten by checkout:
	app.txt
Please commit your changes or stash them before you switch branches.
Aborting

이 거절은 기능이다. switch 와 checkout 은 커밋 안 한 변경을 덮어써야 하는 상황에서 스스로 멈춘다. 안내문에 적힌 대로 커밋하거나 스태시하면 된다. 참고로 --discard-changes 를 붙이면 그 보호가 꺼지고 변경은 사라진다. 이름이 정직한 편이다.

실행 환경과 재현 방법

이 글의 모든 출력은 아래 환경에서 실제로 실행해 얻은 것이다. 커밋 해시와 시각은 실행할 때마다 달라지므로 그 부분은 재현되지 않는다.

$ git --version
git version 2.48.1.windows.1

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

운영체제는 Windows 10(빌드 19045)이고 셸은 Git for Windows 에 딸린 Git Bash(MSYS2)다. 명령 자체는 리눅스·macOS 와 같지만, 붙인 안내문·힌트 문구는 Git 버전에 따라 달라진다. 특히 git status 가 권하는 명령은 예전 버전에서 git reset HEAD <파일> 이었고 지금은 git restore --staged 다. 오래된 문서와 화면이 어긋나 보이는 이유가 대개 이것이다.

  • 재현은 어렵지 않다. 빈 디렉터리에서 git init 하고 파일 몇 개로 커밋을 세 개쯤 만들면 이 글의 예제는 거의 그대로 돌아간다
  • 실제 작업 저장소에서 연습하지 않는다. 이 글의 절반은 파일을 지우는 명령이다
  • 실행 중 한 가지가 걸렸다. 경로가 아주 깊은 디렉터리에서는 Git 이 객체를 쓰지 못하고 unable to write file ...: Invalid argument 로 멈췄다. Windows 의 경로 길이 제한 때문이고, 짧은 경로로 옮기니 그대로 해결됐다
  • 같은 상황에서 core.longpaths 를 켜 봤지만 이 오류는 없어지지 않았다. 리눅스·macOS 에서는 나타나지 않는 문제다

정리 - 증상에서 명령으로

마지막으로 증상에서 곧장 명령으로 가는 표를 둔다. 앞의 결정표가 원리라면 이쪽은 손에 익히는 용도다.

지금 상황쓸 명령파일 내용이 사라지나
파일을 고쳤는데 없던 일로 하고 싶다git restore <파일>사라진다
add 를 잘못했다git restore --staged <파일>아니오
add 를 전부 취소하고 싶다git reset아니오
커밋 메시지에 오타가 있다 (푸시 전)git commit --amend -m "..."아니오
파일 하나를 빠뜨리고 커밋했다 (푸시 전)git add 후 git commit --amend --no-edit아니오
마지막 커밋을 취소하되 내용은 남기고 싶다git reset --soft HEAD~1아니오
마지막 커밋을 통째로 없던 일로 (푸시 전)git reset --hard HEAD~1사라진다
이미 푸시한 커밋을 되돌린다git revert <커밋>아니오
실수로 파일을 지웠다 (커밋된 파일)git restore <파일>아니오
reset --hard 로 커밋을 날렸다git reflog 후 git reset --hard HEAD@{n}커밋은 돌아온다
빌드 찌꺼기를 치우고 싶다git clean -nd 확인 후 -fd사라진다
잘못된 브랜치에서 커밋했다git switch -c <브랜치> 후 원래 브랜치 reset --hard HEAD~1아니오

결국 두 질문으로 돌아온다. 어디에 있나, 그리고 공유했나. 앞 질문이 restore·reset·clean 중 하나를 고르고, 뒤 질문이 reset 과 revert 를 가른다. 그 위에 reflog 라는 안전망이 있고, 그 안전망이 닿지 않는 곳이 한 번도 커밋된 적 없는 변경이라는 것까지 알면 나머지는 대부분 응용이다.

히스토리를 조사하는 쪽 명령이 궁금하다면 제대로 안 쓰는 Git 히스토리 명령어 에 bisect·log -S·reflog 를 실무 관점에서 정리해 뒀고, 기본기부터 다시 보고 싶다면 Git 기초 - 버전 관리의 시작 이 출발점이다.

확인하지 못한 것

  • 모든 예제는 Git 2.48.1 하나에서만 실행했다. 다른 메이저 버전에서 힌트 문구나 기본 동작이 다를 수 있다. 특히 git pull 이 갈라진 히스토리를 만났을 때의 기본 처리는 버전에 따라 달라져 온 부분이다
  • 리눅스·macOS 에서 같은 스크립트를 돌려 비교하지는 못했다. 명령의 의미는 같지만 경로 길이 제한 문제는 Windows 고유이고, 셸이 다르면 예제의 printf 부분이 달라질 수 있다
  • 원격 저장소 실험은 같은 디스크의 로컬 복제본으로 했다. 실제 서버·호스팅 서비스에서는 보호 브랜치 설정 때문에 강제 푸시가 아예 거부될 수 있고, 그 동작은 확인하지 못했다
  • git restore·git switch 가 실험적이라는 문구는 2.48.1 에 동봉된 문서에서 확인한 것이다. 온라인 최신 문서에서는 같은 문구를 확인하지 못했으므로, 판본에 따라 달라졌을 수 있다
  • reflog 보존 기간은 설정 문서에 적힌 기본값을 옮긴 것이고, 90일·30일이 실제로 지나 항목이 사라지는 것을 관찰하지는 않았다
  • git fsck 로 스테이지에만 올렸던 내용을 되찾는 경로는 원리상 가능하다고 적었을 뿐, 이 글에서는 실행해 확인하지 않았다

참고 자료

  • git(1) - Reset, restore and revert - 이름이 비슷한 세 명령의 역할을 Git 공식 문서가 직접 갈라 놓은 절. revert 는 새 커밋을 만들고, restore 는 브랜치를 갱신하지 않으며, reset 은 브랜치 끝을 옮겨 히스토리를 바꾼다
  • Git 2.23.0 릴리스 노트 - switch 와 restore 가 checkout 의 두 역할을 갈라내기 위해 도입됐다는 원문
  • git-restore 문서 - --staged 는 인덱스만, --worktree 는 작업트리를, 둘 다 주면 양쪽을 복원한다는 옵션 정의
  • git-reset 문서 - 세 모드의 정의. --soft 는 인덱스와 작업트리를 건드리지 않고, --mixed 는 기본값이며, --hard 는 추적 파일의 변경을 폐기한다
  • git-revert 문서 - 되돌리는 새 커밋을 기록한다는 정의와, 시작 전에 작업트리가 깨끗해야 한다는 전제
  • git-clean 문서 - 버전 관리 아래에 있지 않은 파일을 재귀적으로 지운다는 정의와 -x 의 범위
  • git-config 문서 - gc.reflogExpire 90일, gc.reflogExpireUnreachable 30일. 이 글의 값은 Git 2.48.1 에 동봉된 같은 문서에서 확인했다
  • git-push 문서 - --force-with-lease 가 원격의 현재 값이 예상과 같을 때만 갱신을 허용한다는 설명
