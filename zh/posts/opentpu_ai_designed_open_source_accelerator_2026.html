起因 — 「由AI开发的加速器」这一行话所说的范围

openTPU仓库的README在第一行把项目介绍为「由AI开发的开源AI加速器(An open-source AI accelerator, developed by AI)」。接下来的一句是项目提出的两个问题：AI智能体在硬件设计上能走多远，以及它们能否造出运行自身推理的芯片。README写道，这个项目把前作auto-arch-tournament的经验带到了AI加速器上。GeekNews于2026年10月7日介绍了它。

这一行话容易被读得过宽。README为「开发」一词附的说明只有上面两句。智能体写了哪些部分、人做了什么、用了哪些智能体和模型，README都没有写，因此「AI独自设计了芯片」这样的句子并不出自README。README中「芯片」一词只出现在上面那个问题里，结果一节描述的是运行在FPGA卡上的设计：它在Inspur YPCB-00338卡(Xilinx Kintex-7 xc7k480t，两个DDR3通道)上运行10种使用真实权重的模型。README里没有关于制造ASIC或流片的表述。

README实际拿出来的东西有三样。

  • 仓库：整个加速器放在一个可以从头读到尾的小型单体仓库里。
  • 测量：在卡上测得的解码与预填充速度、DRAM带宽，按模型和量化方式列成表格。
  • 验证：卡输出的token与模拟器逐比特相同。

仓库里有什么 — 设计、指令集、模拟器、编译器、主机

README还把openTPU介绍为学习项目。仓库里放着硬件设计(SystemVerilog)、指令集、逐比特精确(bit-exact)的模拟器、内核语言及其编译器，以及驱动真实PCIe卡的主机软件。按README的说法，想弄清AI加速器从Python里的矩阵乘法到连线如何工作，这里是不错的起点。

组成部分 在仓库中的位置 README所写的作用
内核 opentpu/kernels 用ol语言写成的mlp、attention和完整模型层，带有@ol.jit装饰器
语言与编译器 docs/compiler.md 布局、仿射循环寻址、融合(fusion)，把内核变成指令
指令集(ISA) docs/isa.md 每条指令为8个32位字，其余一切都建立在它之上
ISA模拟器 opentpu/isasim.py(Python) 「它就是规范」，由测试检查它与RTL给出相同的比特
硬件(RTL) rtl/，入口为rtl/top/otpu_top.sv(SystemVerilog) 生成Vivado比特流，加载到FPGA卡上
主机 otpu-chat、otpu-smi、otpu-lens 通过PCIe驱动卡

README的结构图把这些层次从上到下画了出来。

  Kernels in ol              mlp, attention, full model layers
                            |  @ol.jit
                      Language + compiler        layouts, affine loop addressing, fusion
                            |
                      ISA                        8 x 32-bit words per instruction
                            |
                      ISA simulator  <======>  RTL          same bits, checked by the tests
                      (Python)                 (SystemVerilog)
                                                |  Vivado bitstream
                                               FPGA card    Kintex-7 xc7k480t
                                                |  PCIe
                                               Host         otpu-chat, otpu-smi, otpu-lens

README写道，这台机器是有意做得简单的。定序器每个周期向几个单元发出一条指令：DMA搬运数据，矩阵单元对从DRAM流入的int8权重做乘法，向量单元做fp32运算，量化器把结果变回int8。没有缓存，也没有隐藏的调度。README称，由于每一次数据搬运都是一条指令，执行轨迹能直接显示周期花在了哪里。README中给出的内核示例如下(注释说明这是简化版，原始代码在kernels/mlp.py中)。

from opentpu import language as ol
                    
                    @ol.jit
                    def mlp(h, gamma, w_gate, w_up, w_down, out, eps):   # simplified; see kernels/mlp.py
                        x = ol.load(h)
                        xs = ol.quantize(rmsnorm(x, ol.load(gamma), eps))
                        g = ol.dot(xs, w_gate)
                        u = ol.dot(xs, w_up)
                        a = ol.all_gather(silu(g) * u)
                        y = ol.all_gather(ol.dot(a, w_down))
                        if ol.program_id() == 0:
                            ol.store(out, x + y)

性能剖析器Lens可以记录RTL、模拟器或卡上的任意一次运行，并在浏览器中以屋顶线图、时间线和逐指令表格的形式打开。主机命令在README的表格中归纳为四项。

  • otpu-chat：与模型对话。默认是Qwen3-0.6B，用--model可以选择lfm2(LFM2.5-230M)、qwen35(Qwen3.5-0.8B)、lfm2-2.6b、smollm3、phi4-mini、qwen35-2b或qwen35-4b。
  • otpu-smi：显示温度、功耗、DRAM带宽和各单元的利用率。
  • otpu-lens：记录一次运行并在剖析器中打开。
  • otpu-selftest、otpu-diag：检查卡是否正常工作。

卡与构建 — Inspur YPCB-00338、Kintex-7、两个DDR3通道

进行测量的硬件是一块FPGA卡。README的结果一节和docs/board.md所写的配置如下。

  • 卡：Inspur YPCB-00338。FPGA为Xilinx Kintex-7 xc7k480t(board.md中写作xc7k480t-ffg1156-2)，带两个DDR3通道，每个2 GiB，卡上内存共4 GiB。
  • 镜像：main e698dcd，133.33 MHz，所有模型共用一个比特流。其中包含由内存核内一个小CPU校准的LiteDRAM控制器、四列脉动(systolic)矩阵单元和流引擎。
  • 内存速度：DDR3-1066，峰值17.1 GB/s。board.md把这个峰值按两个x64通道之和(不计ECC位)计算，写作17.07 GB/s。
  • 主机：卡插在一台名为opentpu的PC(Intel Core i7-4790)上，链路是使用Xilinx XDMA的PCIe Gen2 x8。
  • 时序：设计在133.33 MHz下时序收敛，但按README的说法是「勉强」收敛(WNS +0.032 ns)。133.33 MHz是128字节端口与两个DDR3通道相匹配的时钟。
  • 校准：镜像启动后，核内的CPU在没有主机参与的情况下用12秒校准两个DDR3通道。

构建比特流是有条件的。按board.md的说明，需要带有覆盖xc7k480t的许可证的Vivado 2026.1；免费版不包含这款器件，因此要使用付费许可证或AMD的30天评估许可证。文档写道，一次构建预计需要1.5到3小时。另一个用SystemVerilog把硬件放到FPGA上的例子见在FPGA上重现3dfx Voodoo Graphics与DOS PC。

「逐token一致」所指的内容 — 模拟器对卡

README结果一节的第一句话是：卡输出的token与模拟器相同，逐比特(bit for bit)相同。表格下方的注释把范围说得更具体：每一种配置都与模拟器逐token一致，按位置逐一比对如此，用常驻解码程序运行时也是如此。

这句话比较的双方是卡和模拟器。docs/isa.md把ISA文档称为编译器、逐比特精确的指令集模拟器和RTL三者之间的契约，写明三者在写入TMEM或DRAM的每个比特上都要一致。README把模拟器称为「规范本身」，原因在此。这种一致应在以下范围内理解。

  • 验证的是什么：验证的是硬件实现(RTL和卡)给出与规范(模拟器)相同的结果，并不是关于模型回答的质量或准确性的主张。
  • 为什么能做到：isa.md把fp32运算规定为IEEE-754 binary32、就近舍入到偶数、下溢刷新为零，并把复合函数定义为add和mul的固定序列，使所有实现都逐比特相同。
  • 另一项比对：部分模型另外写有与Hugging Face实现的比对。Gemma 4 E2B在三个提示上与Hugging Face的贪心token一致，Qwen3.5-35B-A3B与Hugging Face的16个贪心token一致。写明的提示数量和token数量就是这项比对的范围。
  • 质量方面的数字：量化对模型输出的影响，由docs/quant.md用困惑度另行报告。

贡献规则也在同一条线上。对ISA、模拟器或RTL的修改要保持python3 -m pytest -q通过，性能方面的主张要说明是如何测量的。

4位权重与超过4 GiB的模型 — 速度及其代价

4位权重采用FP4数值加两级块缩放的格式，每个权重4.25位，为保证准确性LM头保留为int8。按README的说法，每个token的字节数减少约三分之一，解码速度提高40%(Qwen3.5)到45%(Qwen3、LFM2)。表中LFM2.5-230M的设备解码从59.0升到85.8 tok/s、Qwen3-0.6B从21.6升到31.3 tok/s，对应的就是这个数值。代价是困惑度：README称之为「可测量的代价」，各模型的数字见docs/quant.md。quant.md写道，Qwen3-0.6B上书籍样本的困惑度从fp32和int8的23.5升到4位的28.3(模拟中测得)。

如果在卡运行的同时把logits流式传回(tools/decode_profile.py，96个token)，4位解码还会更快。按设备/挂钟的tok/s计，LFM2为89.5/84.5，Qwen3为33.7/33.3，Qwen3.5为24.6/24.2。

比卡上4 GiB更大的MoE(混合专家)模型，靠从主机存储流式传入专家权重来运行。卡为每个token做路由并计算所有专家，把专家放在DRAM的逐层槽位里。主机只把缺失的专家从池文件复制到槽位。以下数值于2026年10月1日用构建B测得，条件是卡自身的解码循环选出每个token，专家为4位，头为int8。

  • LFM2.5-8B-A1B(8.5B参数，活跃1.7B)：在160个token上为10.6 tok/s。98.5%的专家调用命中槽位，每个token流式传入5.2 MB。
  • Qwen3.5-35B-A3B(34.7B参数，活跃3.0B)：3.95 tok/s。62%的专家调用命中，每个token有153 MB通过PCIe以1.41 GB/s流式传入。
  • 验证：两种模型都与模拟器逐比特一致。

主机所占的份额很小。对于LFM2和Qwen3，卡运行只编译一次的解码程序，主机每个token增加的时间在开发用PC omarchy上为0.17到0.30 ms，在opentpu上为0.45到1.3 ms。Qwen3.5的解码方式相同，但预填充仍要在主机上为每个分块编译程序。

复现步骤与前作auto-arch-tournament

README写道，除了卡以外的一切都能在笔记本电脑上运行。「试一试」一节中的命令如下。

pip install -e .
                    pip install pytest torch transformers
                    python3 -m pytest -q          # RTL tests also need Verilator 5
                    
                    hf download LiquidAI/LFM2.5-230M --local-dir models/LFM2.5-230M
                    otpu-chat --model lfm2 --backend isa    # chat on the simulator

如果有卡，就在boards/ypcb-00338中用make bit构建比特流，通过JTAG加载，然后运行sudo otpu-setup和otpu-chat --backend board。完整流程写在docs/board.md里。贡献一节写道，大部分工作只需要Python和Verilator，不需要FPGA。许可证为Apache License 2.0。

前作auto-arch-tournament的README把该项目介绍为针对SystemVerilog RV32IM CPU的自主研究循环。每一轮由智能体提出微架构假设，在隔离的git工作树中实现，再经过riscv-formal、Verilator协同仿真和3个种子的FPGA布局布线。只有在CoreMark/MHz上胜过当前冠军的假设才会合并。该README写明的内容如下。

  • 结果：73个假设，挂钟时间9小时51分。锁定的基线为301 iter/s(2.23 CoreMark/MHz)，冠军达到577 iter/s(2.91 CoreMark/MHz)。被采纳的有10个，被验证器否决的有63个。
  • 智能体可以改动的范围：只有目标核心的rtl/和test/test_*.py。编排器是硬编码的，模型不能修改它。
  • 评估一侧不在范围内：智能体一旦改动formal/、tools/、fpga/等目录，路径沙箱会在任何评估运行之前否决这一轮。README写道，智能体无法把自己的评分器调松。
  • 作者的结论：循环并不是护城河；越过63次否决、以10次胜出留下来的成果不是智能体，而是验证器。
  • 智能体：默认是Codex CLI，也可以使用Claude Code。

openTPU的README关于前作只写了一句话，即把那些经验带到了AI加速器上。openTPU是否用同样的循环和同样的沙箱规则构建，README没有写。不过，README「接下来」一节里有一句话：一场由多次Vivado运行组成的锦标赛仍在继续改进时序裕量和面积。另一个把LLM用于芯片设计的例子，以及其中人工介入的范围，见OpenAI借助自研LLM设计Jalapeño芯片分析。

未能确认的事项

  • 人与智能体的分工。在README、board.md、isa.md和quant.md中，没有找到关于谁写了哪一部分的表述。所用智能体和模型的名称、开发周期也是如此。
  • 是否原样沿用了前作的循环。openTPU的README只写了把经验带了过来。假设数量、否决数量之类的运行记录，在openTPU一侧的文档中未能确认。
  • 功耗。文档写明otpu-smi会显示功耗，但README没有给出卡的实测功耗数字。board.md中的Vivado功耗估算针对的是较早的构建，并带有「置信度低」的说明，因此没有转述。
  • 与其他硬件的比较。README中没有用相同模型与GPU、CPU或其他加速器对比的数字。
  • 各模型的质量数字。quant.md中各模型的完整困惑度表格，以及对表中模型输出质量的评估，都没有转述。只引用了Qwen3-0.6B的一个数值。
