让数据库变得「可见」

3D城市比喻真正降低认知负担的地方，以及反而扭曲信息的地方

2026年7月29日 IT/技术

引言：数据库为什么如此看不见

Web服务器有日志在流动。队列有可见的长度。容器会把重启次数留成一个数字。唯独数据库格外看不见。运行顺畅时它一言不发，出问题时又只在为时已晚之后，以响应时间这个结果显现出来。原因在里面，外面却只看得到结果。这就是数据库运维在结构上的不便。

因此「把内部画出来」的尝试会周期性出现。最近一个把PostgreSQL内部机制画成3D城市的项目引起了讨论。城市比喻很直观：楼房拔地而起，车辆穿行，清扫车按时巡回。但本文要回答的问题不是「那座城市好不好看」。问题只有一个：可视化在什么时候真的有用，在什么时候只是玩具。

先把尺子定死。本文中可视化的价值只用「多快能发现异常」来衡量。好看不算价值。文中的技术性陈述均于2026年7月29日在PostgreSQL官方文档与该项目的公开仓库中直接核实，无法核实的说法一律不写。本文不推荐也不比较任何商业监控产品。文中出现的情境示例全部是一般化的虚构案例。

1. 先把事实确定下来 - 那座3D城市不是观测工具

作为出发点的项目是PGSimCity，公开仓库为github.com/NikolayS/PGSimCity，运行页面为nikolays.github.io/PGSimCity/。仓库的说明把自己定义为「一座可以走进去探索、展示PostgreSQL实际如何工作的3D城市」。许可证为Apache-2.0，实现使用three.js与TypeScript，构建使用Vite。

这里最重要的事实不是画面而是边界。仓库文档明确写道，该项目是PostgreSQL的模型而不是模拟器，那里不运行PostgreSQL源代码，数值也经过缩放以便人类观看。也就是说没有填写连接串的地方。它不会从你的实例读取任何值。

这一句决定了全文的方向。这个项目是教材，不是仪表盘。而这并非缺陷，而是设计决定。要画出真实实例就必须读取数值，而一旦开始读取，另一个问题就随之开始：观测成本。后文会单独讨论。

归纳如下。

  • 展示什么 - 后端进程、共享缓冲区、预写日志与检查点、存储层次、清理动作、复制以及查询执行流水线等内部机制，被一一映射为城市中的构造物。
  • 数值从哪里来 - 不从任何地方来。它们由模型生成，不查询真实的系统目录或统计视图。
  • 成熟度 - 一个持续更新的教育类项目。仓库表示它经过多轮准确性审阅、测试挂在持续集成上，同时也承认存在局限并欢迎指正。
  • 使用边界 - 概念学习、新人培训、设计讨论中的共同语言。不能用于状态监控与告警。

所以「把它开着就能看见我们的数据库」是误解。要看真实状态，最终仍然要直接查询统计视图。下面讲的就是这件事。

2. 可视化的价值不是「好看」而是「发现所需的时间」

关于可视化的争论通常滑向审美之争。要避免这一点，就需要一个可测量的标准。运维中能用的标准只有一个：发现同一个异常需要多久。

按这个标准衡量，可视化只有在做到下面三件事之一时才有价值。

  1. 把比较转换成空间 - 不必读一百个数字，而是扫一百个尺寸。人用眼睛做排序比较要快得多。
  2. 把关系转换成形状 - 谁在阻塞谁本质上是一张图。表格藏住了链条，图形一眼就能看到。
  3. 把变化转换成运动 - 异常信号往往是变化率而非静止值，而运动能直接传达变化率。

反过来，可视化产生不了价值的情形也很清楚。一个阈值就能了结的判断就是如此。如果全部意义只在于值有没有越线，那么图形比数字更慢。把本该交给告警处理的事交给人眼，只会更糟。

3. 要看什么，异常才会显现 - 四个信号

在单个PostgreSQL实例上，大多数异常从四条线路进来：膨胀、锁等待、缓冲命中、长事务。先梳理它们分别在哪个视图中以什么信号出现。

症状类别主要查看的视图与扩展要读的信号性质
表膨胀pg_stat_user_tables, pgstattuplen_dead_tup, last_autovacuum, dead_tuple_percent累计、缓慢
锁等待pg_locks, pg_stat_activitygranted, waitstart, pg_blocking_pids()急性、瞬时
缓冲命中pg_stat_database, pg_statio_all_tables, pg_buffercacheblks_hit, blks_read, heap_blks_hit累计比率
长事务pg_stat_activitystate, xact_start, backend_xmin安静、波及广
单条查询成本pg_stat_statementscalls, total_exec_time, mean_exec_time累计、需安装

表中最值得盯住的是性质那一列。累计值与瞬时值不能并排放在同一块屏幕上。累计值自服务器启动以来一直在堆积，几乎反映不出最近几分钟的恶化；瞬时值是查询那一刻的照片，下一次采样就消失了。把两者叠在同一张图上，看的人会把时间轴弄错。这是可视化扭曲信息的第一个地方。

4. 膨胀 - n_dead_tup说了什么，又没说什么

最常见的起点是死元组数量。简短地说，这样看。

SELECT relname,
       n_live_tup,
       n_dead_tup,
       last_autovacuum,
       last_autoanalyze
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC
LIMIT 10;

这里有一个必须知道的事实。PostgreSQL文档把n_live_tup与n_dead_tup分别定义为存活行的估算数量与死行的估算数量。它们是估算值，不是精确数。因此用它们排序是合理的，而在绝对值上画阈值线则很危险。

last_autovacuum是自动清理守护进程最后一次处理该表的时间。实际工作中更重要的信号不是n_dead_tup有多大，而是这个时间是否还在推进。如果死元组不断堆积而最后处理时间已经几天没动，那么问题多半不在清理配置，而在于某种东西挡住了清理。

自动清理什么时候触发

文档给出的判定式基本形态是基准值 + 系数 × 表的元组数。基准值是autovacuum_vacuum_threshold，系数是autovacuum_vacuum_scale_factor，元组数取自pg_class.reltuples。现行文档在此基础上加入一个上限项，取计算值与上限中较小的那个作为阈值。

这个式子的含义很明确：由于系数是乘上去的，表越大清理开始得越晚。在一亿行的表上使用默认系数，必须积累相当多的死元组条件才会成立。在没有上限项的年代大表清理总是滞后，原因就在这里；今天需要按表单独设置参数的原因也在这里。

VACUUM不会让文件变小

还有一个常常落空的期待。文档写道，标准形式的VACUUM会移除死行版本并把空间标记为将来可复用，但除了表尾若干页整体变空且能轻易取得排他表锁这一特殊情形外，它不会把空间归还给操作系统。所以清理跑完而文件大小没变是正常的。文档还补充说，如果表反正还会再长大，用VACUUM FULL把它压回最小尺寸意义不大。

在这里可以清楚看到可视化究竟在哪里撒谎。把表画成建筑高度时，多半用的是文件大小。可文件大小在清理后并不下降。于是屏幕上的楼继续高耸，看的人读出的是清理失败了。而实际上这是内部空闲空间已经变得可复用的健康状态。同一批像素指向了两个不同的事实。城市比喻最大的风险就在这一点。

5. 尺寸 - 究竟把哪个数字叫做「表大小」

要避开上一节的陷阱，必须先把尺寸这个词拆开。文档定义的这些函数各自统计的东西并不相同。

SELECT pg_size_pretty(pg_relation_size('orders'))       AS main_fork,
       pg_size_pretty(pg_table_size('orders'))          AS table_with_toast,
       pg_size_pretty(pg_indexes_size('orders'))        AS indexes,
       pg_size_pretty(pg_total_relation_size('orders')) AS total;
函数统计范围常见误解
pg_relation_size指定的单个分支。只给一个参数时为主数据分支被当成整张表的大小
pg_table_size表本身，不含索引，但包含TOAST以及空闲空间映射与可见性映射不知道TOAST被算了进去
pg_indexes_size挂在该表上的全部索引从不单独查看索引膨胀
pg_total_relation_size表 + 全部索引 + TOAST，等于pg_table_size加pg_indexes_size因为数值最大而惊讶

如果仪表盘上同名指标在两块屏幕上给出不同数字，十有八九一边用的是pg_relation_size，另一边用的是pg_total_relation_size。这是在新增任何可视化工具之前必须核对的项目。指标定义不一致的两块屏幕非但帮不上忙，反而会在故障过程中制造争论。

顺带一提，pg_size_pretty使用的单位是2的幂。正如文档所写，1kB等于1024字节。与采用十进制单位的其他系统并排放置时会对不上。

6. 估算值与精确值 - 两个数字回答的是不同的问题

运维屏幕上最常发生的事故是把估算值当成精确值来读。两者不是替代品，而是用途不同的工具。

-- 估算：立即返回。用于排序比较与趋势观察
SELECT n_live_tup, n_dead_tup
FROM pg_stat_user_tables
WHERE relname = 'orders';

-- 精确：全表扫描。仅用于对账与校验
SELECT count(*) FROM orders;

-- 精确膨胀率：会执行全表扫描
SELECT dead_tuple_percent, free_percent
FROM pgstattuple('orders');

文档关于pgstattuple的表述非常明确：该函数始终执行全表扫描，返回存活元组与死元组的精确数量和大小，以及空闲空间。相比之下pgstattuple_approx会设法避免全表扫描，死元组统计仍然精确，而存活元组的数量、大小与空闲空间则以近似值给出。

也就是说精确的膨胀率有价值，而这个价值贴着价签。把这个函数按仪表盘刷新周期挂在几百GB的表上，观测工具当场就变成压力生成器。权限默认也受限，文档中把执行权限授予pg_stat_scan_tables角色。

问题合适的工具成本不该用在哪里
哪张表最糟按n_dead_tup排序几乎为零汇报精确数值
这张表的真实膨胀率pgstattuple全表扫描周期性自动采集
只要大致的膨胀率pgstattuple_approx中等精密对账
精确行数count(*)扫描刷新界面的计数器
磁盘占用pg_total_relation_size低当作膨胀率的替代

7. 锁 - pg_locks不会告诉你「谁在阻塞谁」

锁等待的本质是关系，因此这是可视化确实能产生价值的领域。但一个视图并不能收尾。

SELECT a.pid,
       a.state,
       a.wait_event_type,
       pg_blocking_pids(a.pid) AS blocked_by,
       now() - l.waitstart     AS waited,
       left(a.query, 60)       AS query_head
FROM pg_stat_activity a
JOIN pg_locks l ON l.pid = a.pid AND NOT l.granted
ORDER BY l.waitstart;

按照文档，granted为假意味着该进程正在等待获取该锁，这隐含着至少还有一个进程正持有或同样在等待同一对象上互相冲突的锁模式。waitstart是开始等待的时刻，而文档警告在等待刚开始的极短时间内，即使granted为假该值也可能为空。如果在屏幕上把这个空值画成等待0秒，刚刚开始的等待就会显得最不紧急。这是符号被翻转的扭曲。

更重要的是仅凭这个视图无法得到阻塞关系。文档指出，把pg_locks与自身连接确实可以得到哪个进程阻塞哪个进程的信息，但要在细节上完全做对非常困难，并建议改用pg_blocking_pids()函数。所以如果要画锁关系图，起点必须是那个函数。手工自连接拼出来的链条，看起来越像样就越危险。

这个视图同样有代价。文档明确写道，如果该视图被非常频繁地访问，对常规锁管理器和谓词锁管理器加锁可能会对数据库性能产生一定影响。这等于为了看锁而制造锁，所以这块屏幕尤其不应设置过短的采集周期。

8. 缓冲区 - 窥视共享缓冲区的价值与代价

共享缓冲区里装着什么，可以用pg_buffercache扩展查看。文档中该视图包含bufferid、relfilenode、reldatabase、relblocknumber、isdirty、usagecount、pinning_backends等列。不过要先理解规模。文档写道共享缓存中的每一个缓冲区对应一行。共享缓冲区越大，行数就相应越多。

文档对成本结构的描述比常见的想当然更细致：由于复制该视图要显示的缓冲区状态数据时不获取缓冲区管理器锁，访问它对正常缓冲区活动的影响较小，但它不能提供跨所有缓冲区一致的结果。文档补充说每个缓冲区自身的信息保证是自洽的。

归纳起来，这是用放弃快照一致性换来便宜的结构。因此用这个视图做出来的画面更接近把运动物体拍糊了的照片。不要凭单个数据块的瞬时状态下结论。

如果目的是常态采集，文档给出了更便宜的替代方案。

-- 把所有共享缓冲区汇总为一行
SELECT * FROM pg_buffercache_summary();

-- 按使用计数聚合
SELECT * FROM pg_buffercache_usage_counts();

文档对这两个函数都写道，视图提供的信息更详细，但这些函数显著更便宜。同时也说明二者同样不获取缓冲区管理器锁，因此并发活动可能导致结果出现细微偏差。访问权限默认限制为超级用户以及拥有pg_monitor角色权限的角色，必要时可用GRANT授予他人。

命中率这个数字里的陷阱

SELECT datname, blks_hit, blks_read,
       round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS hit_pct
FROM pg_stat_database
WHERE datname = current_database();

SELECT relname, heap_blks_hit, heap_blks_read
FROM pg_statio_user_tables
ORDER BY heap_blks_read DESC
LIMIT 10;

这里有两层陷阱。第一，文档对blks_hit的定义明确写道，该值只包含PostgreSQL缓冲区缓存中的命中，不包含操作系统的文件系统缓存。文档在谈到I/O统计时同样指出，它不区分必须从磁盘取回的数据与已经驻留在内核页缓存中的数据，并建议结合操作系统工具一起观察。所以blks_read并不等同于磁盘读取。

第二，这些都是累计值。如果服务器已经运行很久，最近十分钟的急剧恶化几乎无法撼动总体数字。因此命中率应当读取等间隔采样之间的差值，而不是绝对值。把累计比率作为一个大数字摆在屏幕正中，是可视化最常犯的扭曲。

9. 长事务 - 最安静也最昂贵的异常

四条线路中最晚被发现的就是它，因为没有任何指标会跳动。

SELECT pid, state, wait_event_type, wait_event,
       now() - xact_start  AS xact_age,
       now() - query_start AS query_age,
       left(query, 60)     AS query_head
FROM pg_stat_activity
WHERE state <> 'idle'
  AND xact_start < now() - interval '5 minutes'
ORDER BY xact_start;

文档中state可能取到的值除了active与idle之外，还有idle in transaction与idle in transaction (aborted)。生产中真正惹麻烦的通常正是这两个状态。查询什么也没做，事务却一直开着。它不耗CPU也不耗I/O，因此在任何资源曲线上都不会出现。

然而开着的事务会让自动清理无法清掉本该清掉的东西。文档在讨论事务ID耗尽问题时要求结束长时间开启的事务，并说明查找方法是在pg_stat_activity中检查age(backend_xid)或age(backend_xmin)数值很大的行，这类事务应当提交或回滚。

由此形成一条因果链：一个安静开着的事务 → 清理无法删除死元组 → 死元组堆积 → 得到同样结果需要读更多页 → 缓冲命中率下降与响应变慢。运维人员看到的是链条的最后一格，而原因在第一格。

而这里正是可视化真正产生价值的位置。当原因与结果散落在不同视图中且中间隔着时间差时，仅仅把整条链并排放在同一屏就能实实在在地降低认知负担。反过来说，连不起链条的可视化只是多了一块屏幕。

顺带说明，事务ID耗尽这个概念本身很容易吓到人，但文档的表述相当平实。事务ID的大小限定为32位，运行时间长到超过40亿个事务的集群会遇到计数器回绕到零，于是过去的事务突然看起来像是未来的。为避免这一点，每个数据库中的每张表至少要每20亿个事务清理一次。

10. 观测本身就是负载 - 文档实际警告的范围

这是本文最贴近实务的一节。观看有价值，而价值有价格。不作夸张，只在官方文档写明的范围内整理。

对象文档指明的成本与约束实务原则
统计采集整体采集统计会给查询执行增加一定开销，因此可以配置是否采集不要不加区分地把track_*全部打开
pg_locks该视图被非常频繁访问时，对锁管理器加锁可能影响性能不要把采集周期设得过短
pg_buffercache视图每个缓冲区一行。不取锁所以影响较小，但整体结果并不一致只在排查时手动打开
缓冲区汇总函数比视图显著便宜，但并发活动可能带来细微偏差常态采集使用汇总函数
pgstattuple始终执行全表扫描不要挂进周期性自动采集
pg_stat_statements必须加入shared_preload_libraries，因此需要重启服务器在计划内的维护窗口引入
计划时间追踪启用该参数可能带来明显的性能损失仅在需要时临时开启

单条查询统计的前提条件

SELECT queryid, calls,
       round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2)  AS mean_ms,
       rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

pg_stat_statements有多方便，前提条件就有多多。文档写道，该模块需要额外的共享内存，因此必须加入shared_preload_libraries，这也意味着添加或移除模块都需要重启服务器。决定追踪条目上限的设置只能在服务器启动时指定，超出上限时会从执行次数最少的条目开始丢弃。

关于计划时间追踪的警告更为明确：启用该参数可能带来明显的性能损失，尤其是当结构相同的语句被大量并发连接执行、竞相更新少量条目时。

queryid的稳定性同样直接影响界面设计。文档写道，围绕这个哈希值稳定性的保证是有限的，不能安全地假定它在大版本之间保持稳定；另一方面在同一机器架构且目录元数据一致的前提下，可以假定它在小版本之间是稳定的。因此把queryid当作永久标识符来搭建长期趋势界面的设计会在升级时断掉。此外查询文本保存在外部文件中，文档指出若该文件增长到难以管理，文本可能被丢弃，届时既有条目的查询列全部变为空值，但统计本身仍然保留。

最后是一个不太为人所知的事实。文档写道，在默认配置下，当服务器进程被要求显示任何累计统计时，被访问的值会缓存到当前事务结束为止。因此在同一个事务内反复查询同一统计视图以观察变化的代码可能不会按预期工作。如果轮询脚本显示出奇怪地冻住的数值，应当首先怀疑这个行为。

11. 3D城市比喻奏效的地方与崩塌的地方

现在有足够材料来评价比喻本身了。空间隐喻并不免费。隐喻会赋予维度，而被赋予的维度会制造出本不存在的含义。

奏效的地方

  • 并发的直观感受 - 多个后端同时运行这件事，读文字很抽象，看运动则立刻理解。
  • 流水线的顺序 - 从解析到重写、计划、执行的各阶段与空间顺序相当契合。把有顺序的东西画成顺序，是诚实的隐喻。
  • 周期性后台工作 - 清理与检查点这类按周期反复的工作，与循环动画性质相同。
  • 共享资源争用 - 多方争抢同一位置的画面，在解释锁的概念上尤其有力。
  • 教学效率 - 对初学者而言会动的模型可以替代好几页文档。这个项目把自己定义为模型，也正与此相符。

崩塌的地方

  • 高度到底代表什么变得含混 - 是文件大小、行数还是膨胀率。如前所述清理后文件并不缩小，把高度映射为文件大小会让健康状态看起来像故障。
  • 估算值看起来像精确值 - n_live_tup是估算值，画成方块却像是可以数清的东西。图形没有误差棒。
  • 累计与瞬时被混在一起 - 把命中率这类累计比率与当前等待这类瞬时值放进同一场景，时间轴就崩了。
  • 距离与布局制造出不存在的含义 - 两栋楼靠得近就显得有关联，实际上可能只是排序把它们摆到了一起。
  • 镜头会制造统计 - 在3D中什么被遮挡取决于观察角度，被遮住的东西就等于不存在。这是二维表格里没有的失败类型。
  • 动画会暗示因果 - 在时间上被接在一起的两个动作会被读成因果。相关与因果的混淆是被画面推着走的。
  • 信息密度低 - 同样的屏幕面积，表格承载的数值多得多。在排查阶段密度胜过美学。

实务上的结论是：学习用3D，排查用2D，监控用数字与告警。试图把这三者塞进同一个工具之所以多半失败，是因为每个阶段所需的信息密度和可接受的延迟各不相同。

12. 可视化与既有观测体系 - 不应引入的信号

大多数团队已经有了指标采集器、仪表盘与告警。判断是否要在其上再加一块屏幕，依据应当是可替代性而不是喜好。

值得加的情形

  • 反复出现现有界面答不出的问题，尤其是阻塞链这种以关系为本质的问题。
  • 原因与结果散落在不同视图中，每次都要靠人在脑子里拼接。
  • 新人培训与设计讨论需要共同语言。就这个目的而言，一个从不读取真实实例的模型完全够用。

不应引入的信号

  • 指标定义与现有仪表盘不一致。一边用pg_relation_size，另一边用pg_total_relation_size。故障过程中两块屏幕说出不同数字的那一刻，它就不再是工具而成了争端的源头。
  • 为了维持画面而必须不断缩短采集周期。如果为了动画流畅而按秒抓取pg_locks，那就是观测在制造问题。
  • 把告警足以处理的判断交给人眼。是否越过阈值不是该由人盯着看的事。
  • 没有明确的人负责看这块屏幕。没有值班人的屏幕等于关着。
  • 引入的理由只有「好看」。这种情况下剩下的只有维护成本。
  • 需要放宽权限。缓冲区相关函数默认限制为超级用户与拥有pg_monitor权限的角色。为了一块屏幕而软化权限边界是笔糟糕的交易。

再补充一点引入前必须先定下来的事：这块屏幕改变了哪个决定？如果答不上来，那它已经是装饰品了。

13. 判断表 - 从症状到视图，从视图到解读

最后压缩成可以直接使用的形式。陷阱那一列才是这张表的要点。

症状要看的视图与函数解读陷阱
磁盘持续增长pg_total_relation_size, n_dead_tup, last_autovacuum把含索引与TOAST的总量和死元组趋势一起看只看pg_relation_size会整个漏掉索引膨胀
清理过了文件却没变小文档中VACUUM的动作定义标准清理只把空间标记为可复用，不归还给操作系统把正常行为读成失败并直奔VACUUM FULL
只有某张表变慢pg_statio_user_tables, pg_stat_user_tables把块读取上升与死元组堆积相互对照块读取并不等同于磁盘读取
瞬间全部卡住pg_locks, pg_blocking_pids()把等待中的会话与阻塞者连成链条用视图自连接拼出的链条容易出错。不要把为空的waitstart画成0秒
命中率下降了pg_stat_database用等间隔差值只比较最近的区间累计比率会掩盖最近的恶化，且不含操作系统缓存
膨胀莫名其妙地增长pg_stat_activity的state与xact_start找出开着却闲着的事务它们在资源曲线上完全不出现
不知道是哪条查询的问题pg_stat_statements从总执行时间最高的开始看需要重启，且queryid在大版本之间并不稳定
需要精确的膨胀率pgstattuple得到精确的死元组比例与空闲空间始终是全表扫描。不要按仪表盘周期运行
缓冲区里装着什么优先用汇总函数，必要时用视图汇总看趋势，视图做一次性排查视图是每个缓冲区一行，且没有整体一致性

结论：「让它可见」的标准

画成3D城市的PostgreSQL是一份做得很好的教材。而且那个项目自己就是这么说的：它是模型而不是模拟器，并不运行真实源码，数值经过缩放以便人看。这种诚实的划界恰恰是这个项目的美德。反过来，那些声称要画出真实实例的界面之所以常常失败，正是因为没有划下这条线，却试图用教材的语法去做仪表盘。

实务者可以带走三点。

  1. 先把指标定义固定下来。尺寸指的是什么，那个数字是估算还是精确，是累计还是瞬时。没做这些决定的界面，越好看越危险。
  2. 把观测成本纳入设计。不要频繁抓取锁视图，不要把全表扫描的函数挂进周期采集，常态采集用便宜的汇总函数。文档已经告诉了你哪里贵。
  3. 写下这块屏幕改变了哪个决定。答不上来就不要做。在现有仪表盘已能覆盖的事情上再加一块屏幕，不是改进而是分散。

归根结底，让某样东西可见不是画图的工作，而是决定要看什么的工作。看什么定下来了，一张表格往往就够；没定下来，哪怕建起一整座3D城市，依旧什么也看不见。
