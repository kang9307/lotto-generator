智能体最多能挂多少工具 - 工具选择崩掉的临界点与收窄方法

把挂上去和摊出来分开,问题就少了一半

2026年8月3日 IT/技术

引言:只接一个服务器的时候明明很好用

只接了GitHub MCP的时候,这个智能体跑得很顺。后来加上Slack,加上内部数据库查询,加上浏览器自动化,最后又把公司API网关包了进来。于是它在昨天还做得好好的任务上开始犯怪毛病。让它开issue,它去做检索;让它检索,它漏掉必填参数;有些请求里它干脆不碰工具,直接用自身知识作答。

换模型基本没用。在系统提示里加一句「请谨慎选择工具」用处更小。到这一步,多数团队会往写更长提示词的方向走。这个方向几乎不奏效。

先说结论。能挂的工具总数没有实质上限。有上限的是一轮开始时摊在模型面前的那一批。把这两件事分开的那一刻,问题就少了一半。剩下一半来自命名与描述,以及工具之间的前置关系。

本文讲这条界线在哪里、越过之后什么按什么顺序坏掉,以及四种收窄手段该按什么顺序落地才不吃亏。MCP本身的概念和它的局限之争,已经在MCP完全指南和MCP已死?里讲过,这里不再重复。

1. 什么先坏掉 - 失败的五张面孔

「工具多了准确率就下降」这句话没错,但没用。实务上需要的是把哪种失败来自哪种原因分清楚。五种失败源头各异,混在一起看就永远找不到原因。

失败类型日志里的样子常见误判原因真正所在
参数错误漏必填参数、类型不符、格式不对「模型太笨」参数描述与示例,与数量无关
调错工具调用了与意图不同名的工具「提示词不够」命名与描述重叠,数量涨了才出现
不用工具工具就在那儿却用自身知识作答「模型偷懒」定义把工作上下文挤出去了
过度调用反复调列表查询类工具却原地打转「循环bug」找不到目标工具而在乱转
缺前置工具目标工具选对但没有输入值,执行失败「检索准确率问题」工具之间缺少依赖关系

顺序很重要。参数错误在只有十个工具时也会发生。这不是数量问题,是schema描述问题。在Anthropic公开的数据里,加上工具使用示例后,复杂参数处理的准确率从72%升到90%。这个提升不是靠减工具得来的。

相反,调错工具和过度调用要等数量上去才会出现。所以如果你在五个工具的环境里被参数错误困住,引入延迟加载或路由不会改善任何事,该修的是参数描述。反过来,如果接上第五个服务器之后调错突然变多,那么提示词再怎么打磨也解决不了根因。

2. 工具定义究竟吃掉多少上下文

看数字会改变直觉。下面是Anthropic工程博客举的五服务器配置。

MCP服务器工具数定义token(约)单个工具
GitHub35约26,000约740
Slack11约21,000约1,900
Sentry5约3,000约600
Grafana5约3,000约600
Splunk2约2,000约1,000
合计58约55,000—

58个工具并不会让人觉得「很多」。五个服务器在2026年是很平常的配置。可是光定义就约55,000 token。若窗口是200K,那就意味着用户一个字都还没输入,四分之一以上已经没了。同一篇文章提到,Anthropic内部环境在优化前,仅工具定义就占了134,000 token。

2.1 个数与token不成比例

表里真正重要的是最右一列的离散度,不是合计。Slack只有11个工具,开销却与35个的GitHub相当,折算下来单个工具约1,900 token。参数schema一深、枚举值一多,就会这样。

所以按工具个数设上限的策略会失败。定下「工具最多20个」的内部规矩,然后挂上20个schema很深的工具,个数守住了,token却过了40K。该数的单位是定义token,个数只是衡量选择难度的代理指标。两者分开各测一遍。

现在就能测。在工具都接好的状态下随便发一个请求,看第一次响应的输入token数。然后把工具全部摘掉,再发同一个请求。两者之差就是你的工具定义成本,而这笔钱每个请求、每一轮都要重付一次。

3. 为什么数量一多就选错

原因分三支,处方各不相同,分开记着有好处。

3.1 命名空间太窄

能放进工具名的动词就那么几个:search、find、query、list、get。五个服务器合起来,同义工具就有十个。站在模型这边,当search_issues、query_issues和list_issues并排出现时,仅凭名字没有任何依据判断哪个才对。

3.2 描述是按单独使用写的

这一条更根本。每个MCP服务器的作者都假定只有自己这台服务器会被接上来写描述。在那个语境下「检索消息」就够了。五个服务器凑到一起,这条描述什么也区分不了。Anthropic的工具编写指南把整合功能重叠的工具、打磨描述放在靠前位置,原因就在这里。你遇到的问题里有相当一部分不来自模型,而来自别人写的说明文字。

3.3 上下文预算被侵蚀

定义吃掉窗口,真正的工作上下文就被挤出去:对话历史、文件内容、中间结果。不用工具的现象由此而来。不是工具看不见,而是让它有理由被调用的那段上下文被截掉了。为什么靠加长提示词去管住这件事会失败,已在长篇政策文档管不住智能体里单独讲过。

4. 收窄手段一 - 用延迟加载把目录和上下文分开

这是杠杆最大的一招。目录里工具照放,上下文里只装需要的。Claude API的工具检索工具是把它做在服务端的版本,OpenAI的函数调用指南也指向同一方向。

4.1 工作方式

  • 在工具列表里放一个检索工具,其余工具加上defer_loading: true
  • 至少要留一个不延迟的工具。全部延迟会返回400
  • 初始上下文里只有检索工具和未延迟的工具
  • 模型需要时执行检索,命中结果以工具引用块返回并展开成定义
  • 检索默认返回最多5个,每次请求最多允许1万个延迟工具
  • 检索范围不只是名字,还包括描述、参数名和参数描述

4.2 最常见的误解:请求不会变小

defer_loading控制的是什么进入上下文窗口,而不是请求体里放什么。所有工具的完整定义,连同被延迟的那些,每次请求都要照常发送,因为服务端要靠它跑检索、展开引用。如果你是为了减少网络负载才开这个功能,那就找错了功能。

4.3 提示缓存为什么不会失效

这是该设计在运维上最重要的一点。被延迟的工具会从系统提示的前缀中排除,被发现时以引用块的形式追加在对话内部。前缀不变,所以提示缓存得以保留。这与那些在对话中途动态替换工具数组、每次都把缓存打掉的自研实现形成对比。有一个注意点:被延迟的工具不能同时带缓存控制标记,带了会返回400。缓存断点要放在未延迟的工具上。

4.4 能提升多少,以及什么时候不该开

公开的提升幅度是这样:开启工具检索后,MCP评测中Opus 4从49%升到74%,Opus 4.5从79.5%升到88.1%。token通常减少85%以上,只加载真正需要的3到5个。

反向条件文档里也写明了。工具少于10个、每个请求都会用到全部工具、或者定义总量还不到100 token,这几种情况都不要开。因为你多付一次检索往返,却没有可省的token。该开的条件是:工具10个以上、定义超过10K token,或把多个MCP服务器聚合到200个以上。

5. 收窄手段二 - 光有检索解决不了的部分

加了检索之后仍有一类失败留着。这是第二层。

设想「把我的订单退款」这个请求。检索会精确找到refundOrder,因为它语义上最近,这很正常。可这个工具要订单号,而生成订单号的findOrdersByEmail与提问语义相距较远,根本进不了候选。检索准确率满分,可执行计划却拼不出来。这正是前面表里归类为「缺前置工具」的失败。

韩国开源项目graph-tool-call瞄准的就是这里。它的思路是不把工具当作孤立候选,而是把执行链整条召回。

  • 工具之间的关系建成前置(PRECEDES)、必需(REQUIRES)、互补(COMPLEMENTARY)的有向图
  • 检索用倒数排名融合合并四路信号:BM25关键词、图遍历、可选的嵌入相似度,以及MCP注解
  • 注解记录只读、破坏性、幂等等性质。把它当作排序信号这一点在实务上分量很重:你在检索阶段就有了把不可撤销工具往后压的抓手
  • 输出不是一堆工具,而是带完整前置链的有序执行计划
  • 可接入OpenAPI/Swagger、MCP服务器、LangChain与LangGraph,以及普通Python函数。核心引擎零依赖,许可证为MIT

5.1 它给出的数字,以及这些数字有多大

仓库给出的值是:在七例确定性电商回归中,可执行候选方案覆盖率从47.6%升到100%,必需前置工具召回率也达到100%。在248个工具的目录上token减少79%,采用LangChain网关方式则为92%。另有一例把6个工具收窄到2个,schema token从1,476降到160。

不过要诚实地看这个量级。七例确定性测试证明的是行为,不是性能。它并不意味着案例增多后仍能维持100%。评价这个库的地方不是基准表,而是你的工具之间是否真的存在前置关系。在查询与动作成对出现的业务域,比如订单、支付、发货、审批,它的价值是实打实的;若环境里全是互不相干的只读查询工具,那就没有图可画。

6. 收窄手段三 - 直接把目录本身拆开

前两种是「让一个智能体把大目录用好」,第三种则是把目录分开,让每个智能体只看到一小份清单。OpenAI那边的指引也提到,工具面很大时可以拆成按角色分工的子智能体,每个约4到6个工具。

什么时候该拆?只看个数就拆是亏的。标准是边界。

  • 权限边界不同的时候。只读查询和写入删除混在同一份清单里,光是拆开就能缩小事故半径
  • 失败影响范围不同的时候。不要把调错也无害的工具与不可撤销的工具混在一起
  • 上下文不重叠的时候。代码仓库作业与内部文档检索几乎不引用彼此的中间结果
  • 反过来,需要来回传递中间结果时不要拆。每次往返都要重新装载上下文,花的比省下的token更多

拆几个合适在子智能体究竟设几个合适里讲过,同时跑多个智能体的协调成本则在Orch term - 在一个窗口中协调多个AI编程智能体的终端里。

7. 收窄手段四 - 命名与描述,最便宜也最被拖延的活

几乎不花钱,却大多数人放到最后才做。这个顺序该反过来。先做这件事,其余三种的效果会更大;不做,三种效果都会打折。原因是结构性的:检索读的就是名字、描述和参数描述。

  • 用前缀统一命名空间。按服务或资源加前缀,比如github_、slack_,一次检索就能把整组捞出来
  • 把用户的说法写进描述。「登记bug、任务或工单」比「创建issue」更贴近真实提问
  • 在系统提示里加一行类目。先告诉模型有哪几类工具可检索,能减少空转的检索
  • 把参数描述补齐。参数错误只有在这里才会下降。加上工具使用示例后,复杂参数处理从72%升到90%
  • 合并重复工具。做同一件事的两个工具是纯粹成本,只会抬高选择难度
  • 观察哪些工具真的被检索到。检索总是错过的工具,就是描述写坏了的工具

正则方式的检索由模型自己写re.search()模式,不区分大小写做子串匹配。模式长度上限200字符,自然语言查询上限500字符。也就是说,名字和描述里没出现过的词,永远检索不到那个工具。光知道这一条,写描述的方式就会变。

8. 先做哪一步 - 按规模的判断表

没必要四种手段一起上。不同规模下划算的动作不一样。

规模先做暂时别做原因
10个以内 / 不足10K token补强参数描述与示例延迟加载检索往返是净亏
10到30个统一命名空间、删除重复工具子智能体拆分重叠是主因,拆分代价更高
30到50个引入延迟加载,保留常用的3到5个建图这是选择准确率开始下滑的区间
50到200个延迟加载必做,并按权限边界考虑拆分—事故半径的管理变得与准确率同样重要
200个以上检索是前提,再加前置关系与执行链—检索对了却执行不了的失败成为主流

表中30到50这一段,正是Anthropic文档明确点出选择能力开始退化的位置。OpenAI那边更保守,建议一轮开始时少于20个,并自己补充说这只是宽松建议而非硬性规则。两个值不同这件事很重要。这个数字不是普适常数。在自己的目录上逐级加数量、亲手去测,这是两家厂商共同的说法。

9. 韩国开发环境里特别容易踩的坑

9.1 把REST一比一包装会让工具数爆炸

这是最常见的事故。从内部API网关的OpenAPI规范自动生成MCP服务器,每个CRUD端点都会变成一个工具。一个有50个API的系统会生出200个工具,而智能体真正用得上的大概只有十个左右。自动生成很省事,而这份省事的代价要用每次请求的token来还。

对策很简单:别把生成出来的工具原样暴露,按业务单元重新打包。与其让智能体去拼「查订单 → 看状态 → 取消」这三次调用,不如包成一个「取消订单」,在token和准确率两边都更划算。

9.2 工具名是英文,描述是本地语言

内部工具里这种组合很普遍。由于检索会把名字、描述、参数名和参数描述一起读,这个组合本身并不必然出问题。但在正则方式下,模型构造的模式往往依赖英文词根。如果描述只用本地语言写,那个工具可能就是匹配不到。

稳妥的做法是在描述里同时放入两种语言的关键词:用本地语言写句子,后面用括号补上英文关键词,比如在内部wiki查询的描述后加上「(wiki document search)」。这样两种模式都能命中。文档建议的「把用户描述任务时的用词写进描述」,落到非英语环境就是这个样子。这一点对中文环境同样适用。

9.3 隔离网里用不了服务端检索

在金融、公共部门这类外部API调用被切断的环境里,厂商提供的服务端工具检索开不了。这时有两条路。一条是自己实现客户端检索:当你自定义的检索工具返回工具引用时,API会以同样方式把它展开成定义,基于嵌入的召回也可以挂在这条路上。另一条是用像graph-tool-call这样在本地运行的库,在模型之外把目录收窄。如果同时使用本地模型,可以一并参考本地LLM智能体开发 - 为何需要工具搜索与HITL。

9.4 审批、发送这类不可撤销的工具

电子审批提交、通知发送、面向客户的消息,内部目录里必然混着一旦执行就无法撤回的工具。在这里,工具数量问题就越过准确率,变成了安全事故问题。至少做两件事:用注解明确标注破坏性属性,让排序和曝光把它们往后压;并在执行前强制人工确认。写成句子的禁令很少被真正遵守。

10. 这些数字该怎么看

本文引用的提升幅度,多数是厂商自评或仓库自报的回归结果。这不是丢弃它们的理由,而是判断该信哪一部分的依据。

  • 方向可信。减少曝光会改善选择这个结论,在厂商不同、方法不同的多份材料里指向同一边
  • 幅度不能照搬。49%到74%是那次评测的目录跑出来的值,不是你的目录会跑出来的值
  • 要连绝对水平一起看。RAG-MCP论文用基于召回的选择,把工具选择准确率从13.62%提到43.13%。这是三倍多的提升,但43%仍然不到一半。准确的读法不是「加了检索就解决了」,而是「不加检索连起步都做不到」
  • 连界线数字都因厂商而异。30到50与20这两个值并存本身,就说明该值会随模型、目录和任务而移动

测量并不难:在自己的目录上逐级增加工具数量,测同一组任务的成功率。OpenAI的文档也是这么建议的。做过一次之后,面对「工具挂到几个还安全」这个问题,你就能用自己的数字而不是别人的数字来回答。

11. 没能确认的部分

以下项目因为找不到一手依据,正文里没有当作数值使用。

  • 位置偏置。「长列表中间位置的工具比首尾更少被选中」这一说法在多处被提及,但没能锁定可验证的一手资料
  • graph-tool-call回归测试的基线。必需前置工具召回率的改进前数值,在仓库说明与介绍文里写法不同。改进后为100%这一点两边一致
  • MCP评测的构成。得出49%到74%与79.5%到88.1%的那次评测,其工具数量与任务数量并未公开
  • 工具数量对准确率的独立大规模测量。没有找到与厂商无关的第三方在同一条件下只改变数量的公开结果

12. 结论:这不是让你少挂工具

本文的主张不是让你少挂工具,而是把挂上去和摊出来分开。目录里可以有几百个,而一轮开始时摆在模型面前的可以在十个以内。正因为过去把这两者绑成同一个数字,才有了「工具一多就又慢又错」的体感。

按这个顺序落地就不会吃亏。

  1. 去重。删掉做同一件事的工具。零成本,立刻见效
  2. 命名与描述。统一前缀、吸收用户用词、补齐参数描述
  3. 延迟加载。过了30个,这一步单项收益最大
  4. 前置关系。只在还剩下「检索对了却执行不了」的失败时才做
  5. 拆分目录。依据权限边界与事故半径,而不是个数

最后点一个最常见的错觉:「我们的智能体才20个工具,没问题」。如前表所示,11个工具的服务器能吃掉21K token。个数少、token多,名字还可能撞车。把现在挂着的工具的定义token量一遍,再把名字相似的工具列成一张清单。这两件事,排在挑选引入哪个库之前。
