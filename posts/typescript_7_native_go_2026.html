TypeScript 7.0 RC — Go로 재작성된 네이티브 컴파일러와 10배 빠른 빌드 속도 분석

Project Corsa가 빌드 78초를 7.5초로 바꾼 방법, 그리고 JS 생태계 네이티브화의 신호탄

2026-06-25 IT/기술

서론: 컴파일러가 자기 언어를 버렸다

2026년 6월 18일, Microsoft는 TypeScript 7.0 RC를 발표했다. 단순한 버전 업이 아니다. TypeScript 컴파일러가 TypeScript 자신으로 작성된 상태를 버리고 Go로 다시 작성됐다. 코드명 Project Corsa로 불려온 이 작업은 약 1년간 진행됐고, RC 단계에서 npm으로 즉시 설치 가능한 형태로 공개됐다.

헤드라인 수치는 "약 10배 빠른 빌드"다. VS Code의 약 150만 줄짜리 TypeScript 코드베이스 빌드 시간이 약 78초에서 약 7.5초로 떨어졌다. 언어 서버에서는 실패 명령이 TypeScript 6.0 대비 20배 이상 줄었다. 숫자만 보면 선전처럼 들릴 수 있지만, 이 결과가 어떤 구조적 선택의 산물인지, 그리고 그것이 TypeScript 사용자와 JS 생태계 전체에 무엇을 의미하는지가 더 흥미로운 질문이다. 이 글은 그 질문을 따라간다. 2026년 6월 기준 공식 발표 사실을 바탕으로, 과장 없이 의미를 분석한다.

1. 무엇이 바뀌었나 — 포팅의 의미

TypeScript 팀이 이 작업을 설명하는 방식에 한 가지 중요한 표현이 있다. "처음부터 다시 쓴 것이 아니라 기존 구현에서 방법론적으로 포팅했다(methodically ported from our existing implementation rather than rewritten from scratch)." 이 구분이 핵심이다.

1.1 재작성이 아닌 포팅

재작성이었다면 설계 결정, 알고리즘, 데이터 구조를 처음부터 다시 정의했을 것이다. 포팅은 다르다. 기존 TypeScript 코드베이스를 파일 단위로 Go 코드로 옮기면서 동일한 알고리즘과 데이터 구조를 보존했다. 타입 검사 논리는 TypeScript 6.0과 구조적으로 동일하다고 공식 블로그는 밝혔다. 결과적으로 TypeScript 6.0에서 stableTypeOrdering 플래그를 켜고 더 이상 사용되지 않는 기능 없이 깨끗하게 컴파일되는 코드는 7.0에서도 동일하게 컴파일돼야 한다는 것이 핵심 호환성 보장이다.

이 선택은 신뢰를 먼저 확보하는 방법이다. 새 언어로 다시 짜면 미묘한 타입 추론 차이가 생길 수 있다. 포팅은 "새 구현이 기존 구현과 같은 답을 낸다"는 것을 수년간 쌓인 테스트 스위트로 검증할 수 있게 해 준다. TypeScript 팀은 수십 년 치 테스트 스위트와 이미 내부에서 수백만 줄 코드베이스에 TypeScript 7.0을 적용한 결과를 근거로 내세웠다. Bloomberg, Canva, Figma, Google, Slack, Vercel 등이 프리릴리스 버전을 테스트했다는 사실도 이 신뢰 기반의 일부다.

1.2 Go의 코드베이스 점유율

현재 Go 코드베이스는 전체의 약 85%를 차지한다. 남은 부분의 처리 방향은 이후 버전에서 명확해질 것이다. 중요한 것은 tsgo라는 독립 실행 파일명이 RC 단계에서는 더 이상 쓰이지 않는다는 점이다. RC부터는 일반 TypeScript 패키지로 설치하고 tsc를 바로 실행하면 된다.

2. 왜 Go인가 — Rust나 C++이 아닌 이유

이 선택은 단순한 선호가 아니다. Microsoft가 공개한 이유를 분석하면 세 가지 구조적 근거가 드러난다.

2.1 코드베이스 구조와의 정합

가장 실용적인 이유다. Go의 프로그래밍 방식이 기존 TypeScript 코드베이스 구조와 유사해 논리를 보존하며 포팅하기 적합했다. 이것은 "우리가 Go를 좋아한다"는 감정적 선택이 아니라, 포팅 방식을 택했을 때 구현 충실도를 지키기 가장 쉬운 언어가 Go였다는 기술적 판단이다.

2.2 AST 순회와 그래프 탐색

컴파일러의 핵심은 추상 구문 트리(AST)를 순회하며 타입 정보를 전파하는 작업이다. Go는 복잡한 트리와 그래프를 순회하는 데 인체공학적이다. Rust는 소유권 모델로 인해 트리 순회에서 이 작업을 구현하기 훨씬 번거롭고, C++은 정밀하게 제어할 수 있지만 이 규모의 포팅 작업에서 생산성 비용이 크다.

2.3 메모리 관리와 병렬성

Go는 가비지 컬렉션으로 메모리를 자동 관리하되, 메모리 할당 패턴에 대한 세밀한 제어도 가능하다. 그리고 결정적으로 공유 메모리 병렬성(shared memory parallelism)을 지원한다. TypeScript 7.0은 기본 4개의 타입 검사 워커로 병렬 검사를 지원하고, --checkers 플래그로 이 수를 조정할 수 있다. 모노레포 환경에서는 --builders 플래그로 프로젝트 단위 병렬 빌드도 가능하다. JavaScript 엔진은 구조적으로 이런 공유 메모리 병렬성을 갖기 어렵다. Go는 이것을 자연스럽게 지원한다는 점에서 JS 런타임과 근본적으로 다른 출발점에 있다.

3. 10배 성능의 실제 체감 — 빌드와 에디터

수치는 수치다. 중요한 건 그것이 어떤 맥락에서 나왔고 어떻게 해석해야 하는지다.

3.1 빌드 속도

공식 발표 기준 수치: VS Code 코드베이스(약 150만 줄 TypeScript) 빌드 시간이 약 78초에서 약 7.5초로 단축됐다. Microsoft는 "종종 약 10배 빠르다(often about 10 times faster)"는 표현을 공식적으로 사용했다. '종종'이라는 단어에 주목해야 한다. 10배는 보장된 하한이 아니라 대형 코드베이스에서 관측된 범위의 대표값이다.

파일 감시(--watch) 모드도 다시 구현됐다. Parcel 번들러의 C++ 파일 감시기를 Go로 포팅해 사용한다. 기존 Node.js 기반 감시는 변경 감지에 폴링을 사용하거나 OS 이벤트 API의 플랫폼별 차이로 인한 불안정성이 있었다. 새 감시기는 "상당한 리소스 개선"과 안정적인 크로스플랫폼 지원을 제공한다고 발표됐다.

3.2 에디터 응답성

언어 서버(LSP) 측면에서 실패 명령어가 TypeScript 6.0 대비 20배 이상 감소했다. 에디터 경험은 두 가지로 나뉜다. 빌드 속도는 직접적으로 CI 파이프라인과 배포 대기 시간을 줄인다. 에디터 응답성은 개발자가 코드를 타이핑하는 순간의 경험을 바꾼다. 자동완성, 타입 오류 표시, 리팩토링 제안이 눈에 띄게 빨라지면 개발 흐름 자체가 달라진다. 대형 모노레포에서 VS Code가 느린 이유 중 상당 부분이 TypeScript 언어 서버의 부하였다는 점을 고려하면, 이 개선의 실용적 가치는 크다.

3.3 체감 차이가 코드베이스 크기에 비례한다

작은 프로젝트(수천 줄 수준)라면 이미 빌드가 몇 초 안에 끝나 10배 개선이 체감상 무의미할 수 있다. 그러나 수십만~수백만 줄 규모의 대형 프로젝트, 그리고 여러 패키지로 구성된 모노레포에서는 차이가 확실히 느껴진다. 78초 빌드를 7.5초로 줄이는 것은 CI 봇이 기다리는 시간의 문제가 아니라 개발자가 피드백을 받기까지의 루프 전체가 달라지는 문제다.

4. 무엇이 달라지고 무엇이 그대로인가 — 호환성과 주요 변경점

성능 이야기만큼 중요한 것이 "그래서 내 코드는 어떻게 되는가"다.

4.1 타입 시스템은 동일하다

반복하지만, 이것이 핵심 보장이다. 타입 검사 논리는 TypeScript 6.0과 구조적으로 동일하다. 포팅이기 때문에 가능한 보장이다. 새로운 타입 연산자나 언어 문법이 추가된 것이 아니라, 기존 타입 시스템을 더 빠른 실행 환경으로 옮긴 것이다.

4.2 기본값 변경과 하드 에러

TypeScript 7.0은 TypeScript 6.0의 새 기본값을 채택하고, TypeScript 6.0에서 더 이상 사용되지 않는다고 표시된 플래그와 구문에 대해 경고를 에러로 격상한다. 구체적으로 에러가 되는 항목들은 다음과 같다.

  • target: es5 — es5 다운컴파일 지원 종료
  • downlevelIteration
  • moduleResolution: node / node10
  • module: amd, umd, systemjs, none
  • baseUrl (대신 paths 사용)
  • esModuleInterop: false, allowSyntheticDefaultImports: false
  • 네임스페이스 module 키워드, JSDoc의 클로저 스타일 함수 문법

새 기본값은 strict: true, module: esnext, target: current(현행 안정 ECMAScript), noUncheckedSideEffectImports: true, stableTypeOrdering: true 등이다. 특히 stableTypeOrdering은 비활성화가 불가능하다는 점을 유의해야 한다.

4.3 Unicode 처리 개선

템플릿 리터럴 타입에서 유니코드를 자연스럽게 처리한다. 예를 들어 이모지 "😀"가 서로게이트 쌍(surrogate pair) 두 개가 아니라 하나의 코드 포인트로 취급된다. 타입 수준에서 문자열 길이 계산이 인간이 직관적으로 기대하는 방식과 일치하게 된다.

4.4 RC에서 빠진 것: 프로그래매틱 API

안정적인 프로그래매틱 API는 TypeScript 7.0 RC에 포함되지 않았다. 이는 TypeScript 7.1에서 제공 예정이다. TypeScript의 프로그래매틱 API를 직접 호출하는 빌드 도구, 코드 변환 플러그인, 커스텀 언어 서버 통합은 7.0에서 호환성 문제가 생길 수 있다. 이 의존성이 있는 도구 체인은 사전에 점검이 필요하다.

5. 마이그레이션 경로 — 단계적 접근

바로 뛰어드는 것보다 단계적 접근이 안전하다. TypeScript 팀도 그 경로를 명확히 제시했다.

5.1 TypeScript 6.0이 전제 조건

TypeScript 6.0이 의도적으로 7.0의 징검다리로 설계됐다. 6.0은 7.0에서 에러가 될 기능들에 대해 미리 경고를 표시한다. 6.0에서 경고 없이 빌드되는 상태를 먼저 확보하면, 7.0으로 올라갈 때 예상 못 한 에러를 크게 줄일 수 있다.

5.2 나란히 비교 테스트

RC 단계에서는 TypeScript 6.0을 typescript@npm:@typescript/typescript6로 설치해 tsc6 바이너리를 유지하면서, TypeScript 7.0 RC(npm install -D typescript@rc)와 나란히 실행해 결과를 비교할 수 있다. CI 파이프라인에서 두 컴파일러를 병렬 실행해 동작 차이를 먼저 파악하는 것이 권장 패턴이다.

5.3 병렬 워커 활용

--checkers 8처럼 워커 수를 늘리면 멀티코어 환경에서 타입 검사 병렬성을 더 높일 수 있다. 대형 모노레포라면 --builders 플래그로 프로젝트 단위 병렬 빌드도 실험해볼 만하다. 단 워커가 많다고 무조건 빠른 것은 아니고 I/O 병목이나 의존 순서에 따라 최적값이 달라진다.

6. 생태계 영향 — JS 도구의 네이티브화 흐름

TypeScript 7.0 RC는 단독 사건이 아니다. JS/TS 생태계에서 이미 진행 중인 큰 흐름의 한 부분이다.

6.1 번들러와 트랜스파일러의 선례

esbuild(Go), SWC(Rust), Bun(Zig+C++)은 이미 JS 도구 스택에서 네이티브 언어로 성능 한계를 돌파한 선례다. esbuild는 Webpack 대비 수십~수백 배 빠른 번들링을 보여줬고, SWC는 Babel을 대체하는 속도로 Next.js 등에 채택됐다. 이 흐름의 공통 맥락은 "JavaScript로 JavaScript 도구를 만드는 데 구조적 한계가 있다"는 인식이다. Node.js의 단일 스레드 이벤트 루프, JS 엔진의 JIT 웜업 시간, 공유 메모리 병렬성 부재는 도구가 커질수록 병목으로 작동한다.

6.2 TypeScript 7.0이 이 흐름에서 갖는 의미

esbuild와 SWC는 "빌드를 빠르게" 해주는 도구였다. TypeScript 7.0은 TypeScript 컴파일러 자체가 네이티브화된 것이다. 타입 검사의 원천이 달라진다. 이는 단순히 빌드 툴을 교체하는 것과 다르다. TypeScript 언어 서버를 통해 에디터 플러그인, IDE 통합, 코드 리뷰 도구 등 타입 정보를 소비하는 모든 상위 도구가 영향을 받는다. 장기적으로는 타입 검사를 실시간으로 하는 비용이 낮아지면서 더 야심찬 정적 분석, 더 정밀한 리팩토링 도구, 더 지능적인 IDE 기능이 가능해질 수 있다.

6.3 도구 생태계의 적응 과제

하지만 낙관 일색이어서는 안 된다. TypeScript 생태계에는 TypeScript API에 직접 의존하는 도구가 많다. ts-jest, ts-loader, ts-node, 각종 ESLint TypeScript 플러그인, 사내 코드 생성 도구들이 그것이다. 프로그래매틱 API가 TypeScript 7.1 이전까지 안정화되지 않는다는 점은 이 도구들이 7.0을 즉시 지원하기 어렵다는 의미다. 특히 TypeScript 컴파일러를 라이브러리로 사용하는 도구는 API 변경이 확정된 뒤 업데이트를 기다려야 한다.

7. 본인의 해석 — 이 변화를 어떻게 읽어야 하나

사실을 옮기는 것과 의미를 해석하는 것은 다르다. 여기서 본인의 관점을 밝힌다.

7.1 '10배'는 목표가 아니라 결과다

Microsoft가 Go를 선택한 것은 "10배 빠르게 만들기"가 목표였기 때문이 아니라, 포팅 방식으로 타입 시스템 동등성을 보장하면서도 네이티브 병렬 실행이 가능한 최선의 선택이 Go였기 때문이다. 결과가 10배였을 뿐, 시작점이 "10배 속도 목표"였던 것은 아니다. 이 구분은 왜 팀이 Rust나 C++이 아닌 Go를 택했는지를 이해하는 데 중요하다. 빠름보다 포팅 충실도와 개발 생산성이 선행 제약이었다.

7.2 중요한 것은 타입 검사의 지위가 달라진다는 것

타입 검사가 더 빠르다는 것은 "CI가 조금 빠르다"는 이야기가 아니다. 타입 검사의 비용이 낮아지면 이를 더 자주, 더 촘촘하게 쓸 수 있다. 예를 들어 에디터에서 파일을 저장할 때마다 전체 프로젝트 타입 검사가 수 초 안에 끝난다면, 현재는 "저장 후 수십 초 기다림"을 감수해 터미널에서 수동 실행하는 방식이 IDE 네이티브로 통합될 수 있다. 이는 개발 루프의 성격 자체를 바꾼다.

7.3 마이그레이션은 서두를 필요 없다

RC는 아직 프로덕션 추천이 아니다. 특히 TypeScript API를 직접 사용하는 도구 의존성이 있거나, 더 이상 사용되지 않는 플래그를 많이 쓰고 있다면 7.0 마이그레이션은 2단계 작업(먼저 6.0으로 정리 → 7.0 업그레이드)이 필요하다. 안정 릴리스는 RC 발표 후 약 1개월 내 예정이라고 Microsoft가 밝혔다. 그때까지 도구 생태계의 7.0 대응 현황을 관망하면서 자체 테스트를 병렬로 준비하는 것이 합리적이다.

8. 결론 — JS 도구 네이티브화의 이정표

TypeScript 7.0 RC는 TypeScript 컴파일러가 자신의 언어인 TypeScript를 구현 언어로 쓰는 시대를 끝내는 변화다. 코드명 Project Corsa가 약 1년 만에 RC로 진입했다는 것은, Microsoft가 포팅 충실도를 검증하면서도 의미 있는 속도로 이 작업을 완료했음을 보여준다.

실용적 의미로 정리하면 세 가지다. 첫째, 대형 코드베이스의 빌드와 에디터 응답성이 실질적으로 빨라진다. 둘째, 타입 시스템은 동일하므로 타입 안전성 보장은 바뀌지 않는다. 셋째, 프로그래매틱 API 안정화(7.1)까지 도구 생태계의 전면 지원에는 시간이 더 필요하다. esbuild, SWC, Bun이 열어온 JS 도구 네이티브화 흐름에서, TypeScript 컴파일러 자체가 그 흐름에 합류했다는 것이 이 변화의 위치다. 도구가 빨라질수록 우리가 타입 정보를 활용하는 방식의 상상력도 넓어질 수 있다.
