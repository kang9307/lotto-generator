AgentsView 登場 - Claude Code・Cursor・Codex のセッションを一箇所に集めて検索・費用を追跡するローカルダッシュボード

複数の AI コーディングエージェントを併用する時代、セッションの分散と費用の不透明さをローカルファーストのオープンソースツールでどう解くか

2026-07-14 開発・インフラ

序論: エージェントは増えたのに、記憶は散らばった

2026 年の今、開発者一人が一日に複数の AI コーディングエージェントを行き来することは例外ではなく既定になった。ある調査は開発者の 59% が三つ以上の AI コーディングツールを併用すると報告し、65% は少なくとも二つを毎日使うと答えた。Claude Code にリファクタリングを任せ、Cursor でインライン修正を受け、Codex や Gemini CLI、OpenCode に別作業を投げる一日はもはや珍しくない。各ツールが一つの仕事に長けているために生まれる自然な分業だが、その代償として「昨日のあのバグをどのエージェントにどう指示したか」「今月 AI ツールに実際いくら使ったか」といった問いに答えるのがかえって難しくなった。

この隙間に入り込んだオープンソースプロジェクトが AgentsView だ。hada.io に 2026 年 7 月紹介されたこのツールは、Claude Code・Codex・Cursor・Gemini CLI・OpenCode など複数の AI コーディングエージェントがローカルに残すセッションログを一箇所に集め、会話検索、トークン・費用統計、活動分析、ファイル変更追跡を提供する。本稿は GitHub リポジトリ(kenn-io/agentsview)の公開文書を根拠に、このツールが実際に何をするのか、複数エージェントを併用する時代になぜこうしたツールが必要か、ローカル収集が持つプライバシー上の意味、類似アプローチとの違い、そして実務活用と限界までを 2026 年 7 月時点で分析する。

1. AgentsView とは何か - ローカルファーストのセッション分析ダッシュボード

1.1 40 以上のエージェントを一つの索引に

AgentsView が認識するエージェントの一覧は短くない。Claude Code、Codex、Cursor、GitHub Copilot CLI、Windsurf、Zed といった主要ツールから、Devin CLI、OpenCode、Gemini CLI、DeepSeek TUI、Qwen Code のような特化ツール、Aider(リポジトリ単位のオプトイン)・Forge・gptme・OpenHands・Kiro・Mistral Vibe のような比較的知られていないツールまで 40 以上を扱う。各エージェントは自分専用のセッション保存パスを持つが(例えば Claude Code は ~/.claude/projects/)、AgentsView はこれらのパスをそれぞれ解析し、一つのローカル SQLite データベースへ統合する。

1.2 検索・費用・活動・変更、四つの中核機能

中核機能は四つに要約される。第一に 統合検索。FTS5 ベースの全文検索で複数エージェントの会話内容を一度に探せ、任意で埋め込みエンドポイントを繋げば意味ベースの検索も可能だ。第二に トークン・費用集計。LiteLLM の価格データを参照してセッション・モデル別のトークン使用量と費用を計算し、オフラインフォールバックにも対応、プロンプトキャッシュを反映した費用計算まで扱う。ファイルを毎回解析し直す方式より 100 倍速い照会を謳う。第三に 活動分析。セッションを自動化・クイック・標準・ディープ・マラソンのような類型に自動分類し、セッション時間・コンテキスト使用量・ツール呼び出し分布を可視化する。第四に ファイル変更追跡。最近エージェントが修正したファイルをフィード形式で示す。結果は HTML や GitHub Gist へ書き出せる。

1.3 アーキテクチャ - Go 単一バイナリと任意のチーム共有

バックエンドは Go(コードベースの約 83.8%)、フロントエンドは Svelte 5 と TypeScript で書かれ、Tauri で包んだデスクトップアプリも提供される。ストアは既定で書き込み可能な SQLite(FTS5 インデックス付き)で、チームと共有したいなら SQLite から読み取り専用で流し込む PostgreSQL を、大規模分析向けには DuckDB ミラーを任意で追加できる。インストールは curl -fsSL https://agentsview.io/install.sh | bash、Homebrew キャスク、あるいは Docker イメージ(ghcr.io/kenn-io/agentsview)で行え、agentsview serve でフォアグラウンド実行するか、デーモンモードで 15 分ごとに自動同期できる。Web UI は既定で 127.0.0.1:8080 に開く。ライセンスは MIT だ。

2. 問題の根源 - 複数エージェントを併用する時代の三つの痛み

2.1 セッションの分散 - ツールごとに割れた記憶

AgentsView が狙う第一の痛みはセッションの分散だ。GitHub Copilot が依然として最も広いユーザー層(約 67.9%)を持ち、Claude Code がわずかな差で続き(約 62.9%)、OpenAI Codex も 34.5% 水準まで上がってきたという 2026 年の調査結果がある。複数ツールを同時に使うことが例外ではなく標準になったという意味だ。問題は各エージェントが自分専用のセッションファイル・形式・UI を持つため、「先週このリファクタリングをどのエージェントにどう指示したか」を確認するにはツールを一つずつ開かねばならない点だ。ツールが増えるほど、この記憶はより細かく砕かれる。

2.2 費用の不透明さ - 見えない支出

第二の痛みは費用だ。エージェントは計画・実行・再確認を繰り返しながら各ステップごとにコンテキストを再送するため、一般的なチャットボットに比べトークンをはるかに速く消費するという指摘が複数ある。ある調査によれば、エージェント型コーディングツールを使う開発者の月平均支出は 400〜1,500 ドル水準で、極端な場合は数日で 4,000 ドルを超えることもある。35 人規模のあるスタートアップが Claude Code・Cursor・自前のバグトリアージエージェントを併用し、月 8 万 7 千ドルの請求を受けた事例、マイクロソフトがエンジニア一人当たり月 500〜2,000 ドル水準の費用を確認し一部の Claude Code ライセンスを縮小したという報道もある。ツールごとのダッシュボードが別々にあると、この全体像はなかなか見えてこない。

2.3 何をいつ指示したかを追いにくい

第三の痛みは振り返りと監査だ。コードレビューで「この部分はなぜこう書いたのか」という問いに答えるには、その時エージェントに与えたプロンプトを遡らねばならないが、セッションがツールごとに散らばっているとこの遡り自体が仕事になる。チーム単位で見れば、「今スプリント AI が実際どれだけ、どこに貢献したか」を説明する根拠資料がないということでもある。セッションの分散、費用の不透明さ、振り返り不能という三つの痛みは、実は一つの根から生じている。エージェントごとに閉じたログがあるだけで、それを横断する一つの視野がないということだ。

3. AgentsView が与える可視性 - どこに価値があるか

3.1 検索可能な共同記憶

AgentsView の第一の価値は単純だ。複数エージェントの会話ログを一つの検索窓の後ろに置くだけで、「あの時何を指示したか」を探す作業が、複数のアプリを巡回する作業から検索語を一つ入力する作業へ変わる。FTS5 全文検索は正確な文言を、任意の埋め込み検索は「あの認証関連のリファクタリングは何だったか」のような意味ベースの問い合わせを支える。

3.2 費用・トークンを一画面に

第二の価値は費用の可視性だ。ツールごとに散らばった請求書を突き合わせる代わりに、LiteLLM の価格データを基にセッション・モデル・期間別のトークンと費用を一画面で見られる。プロンプトキャッシュを反映した計算という点も重要だ。キャッシュヒットが多いセッションと毎回全体のコンテキストを新しく燃やすセッションでは実際の費用構造が異なるが、この差を単純なトークン数の乗算より正確に近似する。

3.3 活動分析と変更追跡 - パターンを見る目

第三の価値は活動を類型化しパターンを浮かび上がらせることだ。セッションを自動化・クイック・標準・ディープ・マラソンに分類すれば、「このプロジェクトは短いクイックセッションがほとんどなのに、この一つのモジュールだけマラソンセッションが集中している」といった観察が可能になる。最近編集されたファイルのフィードは、「ここ数日エージェントが実際どこを触ったか」をコードレビューなしでも一目で確認できるようにする。こうした類型化は個々のセッションログだけでは見えにくい、蓄積された利用パターンを示すという点で、単純なログビューアとは異なる層の価値だ。

4. ローカル収集が持つプライバシー上の意味

4.1 既定はローカルホスト、外部送信なし

AgentsView はアカウント作成が不要で、セッションデータが既定で自分の端末の外へ出ないことを前面に押し出す。サーバーは既定で 127.0.0.1 にのみバインドされ、セッション内容を外部へ送信しない。コードとプロンプトがそのまま残るログを扱うツールである以上、この既定値は些細な設計選択ではない。クラウドダッシュボードへセッションをアップロードする方式だったなら、社内コードベース全体がベンダーのサーバーを経由するという新たな問題が生じていただろう。

4.2 最小限のテレメトリ、無効化できるオプション

ただし完全な無通信ではない。アプリバージョン・OS・CPU のような匿名情報が起動時と 24 時間ごとに PostHog へ送信される。セッション内容ではなく利用統計という点で性質が異なるが、AGENTSVIEW_TELEMETRY_ENABLED=0 環境変数で無効化できることは知っておくとよく、セキュリティポリシーが厳格な組織ならこのオプションを確認するのが安全だ。

4.3 チーム共有を望んでも自前のインフラの中で

チームと共有したい場合も、AgentsView はベンダーのクラウドではなく自前インフラ内の PostgreSQL を選択肢として示す。SQLite から読み取り専用でデータを流し込む構造のため、チーム共有の状態でも「データがどこにあるか」という問いの答えは依然として自前のサーバーだ。これは セルフホスティング AI エージェント OpenTag の分析で扱ったデータ主権の論理と同じ軸の上にある。

5. 類似アプローチとの比較 - 何が重なり、何が違うか

5.1 エージェント内蔵ログ - あるが閉じ込められている

最も基本的な代替はすでに各エージェントが提供する自前の履歴だ。Claude Code も Cursor も自分のセッションをどこかに残し、それぞれの UI や CLI で覗けるようにしている。問題はこれが一つのツールに閉じ込められている点だ。ツールを二つ、三つ使えば「全体を横断する検索」という機能そのものが存在しない。

5.2 似たセッション管理ツール群 - 重なるが焦点が違う

AgentsView が唯一の試みではない。Mantra は Claude Code・Cursor・Gemini CLI・Codex のセッションを一つに集めつつ、会話ログをコードが変化してきた過程を辿り直せる再生型タイムラインとして見せる点に強みがあり、MCP サーバー・権限の統合管理と API キー・シークレットを自動検出して一括整理する機能まで備える。coding_agent_session_search は 11 以上のプロバイダーを横断するローカル TUI/CLI 検索ツールで、Agent Sessions も Codex・Claude・OpenCode・Cursor・Copilot などのセッション管理に焦点を置く。これらと並べると AgentsView の位置がはっきりする。検索とリプレイに強いツール群の隣で、AgentsView は費用・トークン分析とチーム共有用 DB バックエンド(PostgreSQL・DuckDB)まで備えた、より分析志向の組み合わせを選んでいる。

5.3 LLM オブザーバビリティプラットフォーム - 異なる製品カテゴリー

LangSmith・Helicone・Langfuse のようなツールを思い浮かべるかもしれないが、これらは根本的に異なる問題を解く。これらのプラットフォームは自分が作った LLM アプリケーションに SDK を組み込み API トレースを計測する 本番オブザーバビリティツールだ。LangSmith はトレース数で課金し(無料枠は月 5,000 トレース、以降有料枠)、Helicone はリクエスト数で課金しつつ 300 以上のモデルの費用をゲートウェイ側で計算する。一方 AgentsView には計測コードを組み込む対象アプリケーションがそもそもない。すでにローカルディスクに溜まっているコーディングエージェント CLI のセッションログファイルを事後に読み込み索引するだけだ。月間 LLM 支出 3 万ドル以下では Helicone が、3 万〜20 万ドル区間では Langfuse が、それ以上で LangGraph に深く投資した組織なら LangSmith が適するというのが業界の大まかな評価だが、このスペクトラム自体がそもそも「自分が作ったプロダクトの API トラフィック」を前提にしている。AgentsView は「自分が使うコーディングエージェント」を対象にするという点で出発点が異なる。

5.4 費用特化ツール群 - 支出管理に集中

LMSpend・DevOS・CodeBurn のようなツールは、チーム単位の支出追跡、予算アラート、財務レポート出力のように費用という一軸により集中する。こうしたツールは支出管理には強いが、会話検索やセッションリプレイのような機能は相対的に浅いことが多い。AgentsView はこのスペクトラムの中で、検索・費用・活動・変更追跡を一つのツールにまとめたゼネラリストに近い。

6. 実務活用 - チームの費用配分、プロンプト振り返り、監査

6.1 チームの費用配分

複数人がそれぞれ異なるエージェントを使うチームなら、SQLite を PostgreSQL へ読み取り専用同期し、チーム全体のセッション・費用データを一つのストアに集められる。これにより「今スプリント AI ツールに実際いくら使い、どのプロジェクト・どのモデルに集中したか」を財務報告やスプリント振り返りの根拠資料として提示できる。

6.2 プロンプトの振り返り

個人レベルでも価値がある。うまくいったリファクタリングとそうでなかったものを後から検索して比較すれば、どのプロンプトパターンがより良い結果を生んだかを遡って確認できる。これは「なぜこう書いたのか」という問いに「その時こう指示した」という答えを即座に取り出せるという点で、コードレビューと振り返りの両方に実質的に役立つ。

6.3 監査の観点での限界 - ガバナンスの門番ではない

ただし監査目的で使う際には境界が必要だ。AgentsView はすでに起きたことを事後に索引するツールであって、特定の行動を事前に阻止したり予算をリアルタイムで強制したりする門番ではない。「この要求は承認なしに実行されない」「このチームは今月の予算を超えれば自動遮断される」といった統制が必要なら、エンジニアとモデル提供者の間に立ちすべての要求をログ記録・帰属・統制するプロキシゲートウェイ型ツールが別途必要になる。AgentsView はその前段階、すなわち「何があったかを見えるようにする」可視性レイヤーだと理解するのが正確だ。

7. 限界と注意点

7.1 事後分析であってリアルタイム統制ではない

先に述べた通り、AgentsView はすでに溜まったログを読むツールだ。費用が急騰した瞬間に通知したり要求そのものを遮断したりする機能はこのツールの役割ではない。リアルタイムの予算強制が必要なら、別途ゲートウェイ・プロキシ層を併せて設計せねばならない。

7.2 価格データの正確さは外部ソース次第

費用計算が LiteLLM の価格データに依存する構造のため、モデル価格が頻繁に変わる昨今の環境では、オフラインフォールバックデータが実際の請求書とわずかにずれる可能性がある。正確な金額が絡む意思決定(予算承認、請求書の照合)には、依然としてベンダーの公式請求内訳を基準に検証する手続きが必要だ。

7.3 ローカル DB にも機微情報は溜まる

ローカルにのみ置く構造は外部への流出は防ぐが、セッションログ自体に API キーや社内 URL、顧客データが混ざっている可能性はそのまま残る。Mantra のようにシークレットを自動検出して整理する機能は AgentsView には標準で提供されていないようなので、索引されたデータベースファイルをチームと共有したりバックアップしたりする際は、別途機微情報を点検する手続きを設けるのが安全だ。

7.4 エージェントのログ形式が変われば保守が必要になる

40 以上のエージェントに対応するということは、それだけ多くのログ形式に追随し続けねばならないということでもある。各エージェントベンダーがセッション保存方式を変えればパーサーも合わせて更新せねばならず、この保守負担はオープンソースコミュニティの活力に左右される。導入前にリポジトリの直近のコミット頻度とイシュー対応速度を確認するのがよい。

8. 結論 - 今日できる 3 つのこと

AgentsView が示す方向は明確だ。AI コーディングエージェントが増えるほど、個々のツールの性能よりその上に置かれる可視性レイヤーが重要になるということだ。セッション検索、費用集計、活動分析を一箇所に集めるだけで「何をいつ指示したか」を遡る作業が格段に楽になり、ローカルファースト設計のおかげでこの可視性を得る代償としてコードをベンダーのクラウドへ渡す必要もない。ただしこれは事後分析ツールであってリアルタイムのガバナンスツールではないこと、監査・予算統制が目的なら別のレイヤーが必要であることは明確にしておくべきだ。

8.1 今週、自分のエージェント利用状況を直接点検せよ

AgentsView でも類似ツールでもよいのでインストールし、この一か月実際どのエージェントにいくら使ったかをまず確認せよ。想像と実データが異なる場合は珍しくない。

8.2 チームなら費用配分と監査を分けて設計せよ

費用の可視性は AgentsView のようなツールで確保しつつ、予算強制や要求遮断が必要ならプロキシゲートウェイを別途検討せよ。二つのレイヤーを一つと錯覚すると、統制の抜けたダッシュボードだけが残る。

8.3 機微情報の点検手続きを先に立てよ

セッションログを索引する前に、API キーや社内 URL のような機微情報がログに混ざっている可能性をまず点検せよ。チームと共有したりバックアップしたりする前にもう一段濾過する手続きを入れるのが安全だ。関連して セルフホスティング AI エージェント OpenTag の分析と ローカル CLI ツール QAMap の分析も参考になる。
