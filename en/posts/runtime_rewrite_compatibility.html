Rewriting a Running Runtime - Bun 1.4 From Zig to Rust

What is at stake when you rewrite software people already run, and what the word compatibility actually means

Aug 21, 2026 Dev & Infra

Introduction: a runtime that worked fine changed the language it is written in

When you bump the runtime version of a service in production, you check roughly two things. Is any API breaking, and did latency get worse. Bun 1.4, published on August 20, 2026, added an unfamiliar third item. The implementation language of the runtime itself changed. The API surface you see is unchanged, but everything underneath moved from Zig to Rust.

By version number this is a minor update. By size it is not. According to the vendor posts, 1,448 .zig files were ported to Rust, and a change on the order of a million lines landed in a single merge. That work was finished in eleven days, from May 3 to May 14, 2026.

This article is not a translation of release notes. The interesting question sits elsewhere. Why is the decision to rewrite software that other people already depend on so heavy, and what does compatibility — the only practical criterion by which such a decision is judged — actually mean. Along the way we look at the conditions under which the multipliers and percentages in a release announcement should be read. The theme of a language-swapping rewrite also came up in TypeScript 7.0 RC and the Go-native compiler and Grit, the attempt to rewrite Git in Rust with AI agents, but those were a tool and an experiment. This one is a runtime in production.

What was announced - the confirmed scope as of August 2026

First the facts, briefly. Everything below appears in the official vendor blog, checked in August 2026.

  • Language port — Bun 1.4 is the first stable release of the Rust port. The porting work started on May 3, 2026 and was merged on May 14.
  • Not a redesign — the maintainers pinned the goal to a mechanical port. Architecture, data structures, and the bindings to C and C++ libraries such as JavaScriptCore, OpenSSL, SQLite and uWebSockets were kept as they were.
  • Node.js test counts — passing Node test files went from 1,450 at v1.2.0 to 3,743 at v1.4.0, with 1,517 newly passing in this release.
  • Standard library absorption — features equivalent to fifteen npm dependencies, covering image processing, headless browsing, cron, markdown, XML and archives, moved into built-in APIs.
  • Explicitly experimental — HTTP/3 in Bun.serve() is experimental and the maintainers themselves say not to enable it in production. HTTP/2 and HTTP/3 in fetch() sit behind a feature flag.

That is the announcement. The interesting part comes next. The claim that a change of this size finished in eleven days, and the nineteen known regressions disclosed in the same post, are two sides of one fact. Read only one and you have half a picture.

The weight of deciding to rewrite in a different language

Choosing a language for a new project is a matter of taste and team circumstance. Rewriting software that is already running in production in a different language is a different kind of act. What is at stake is not the code but accumulated trust.

Running software carries assets that appear in no document. Edge-case handling hardened by years of bug reports, workarounds users built and then relied on, behaviour that is not in the spec but has become a de facto contract. None of this is written down explicitly in the source. The moment you move to a new language, the unwritten part goes first.

So the same question always follows a rewrite. What are you risking, and what do you get.

  • Risk 1 — feature freeze: new work stops while the rewrite runs. Users feel that stall immediately, while the payoff arrives much later.
  • Risk 2 — reintroduced bugs: defects the old implementation fixed over years reopen in the new one. The nineteen regressions the maintainers acknowledged are exactly this item.
  • Risk 3 — reset trust: from the user side, the verification history goes back to zero. The sentence this version has been fine for two years has to be earned all over again.
  • The payoff — a structural fix: instead of chasing individual bugs, you make that entire class of bug fail to compile in the first place. This is the one decisive reward a language change offers.

My own read is this. A rewrite is justified when the goal is to eliminate a class of bug structurally, not when the goal is speed. If performance is the only motive, changing the hot path is almost always far cheaper. That distinction is the same axis as the signals and anti-signals in the Go to Rust migration decision framework.

Why teams rewrite - four motives

In practice a language change gets considered for one of four reasons. Where this case falls is noted with each.

  • Memory safety — you want use-after-free, double-free, and forgotten frees on error paths to become compile errors rather than recurring incidents. This is exactly the stated primary reason here. Zig has no destructors, so cleanup had to be spelled out at each call site with defer; the team tried a homegrown smart pointer and described the result as worse ergonomics than Rust with none of the guarantees. Rust's Drop takes that role.
  • Ecosystem — do the libraries you need already exist there. The weight grows in areas such as cryptography, parsers and serialization, where writing your own is dangerous.
  • Hiring and handover — can you find people who write that language. The more niche it is, the smaller the bus factor.
  • Tooling — are debuggers, profilers, static analysis and dependency auditing mature. This is really a question of whether you can identify a root cause when something breaks.

What matters is that these four carry different weights. Memory safety is the only one you can obtain solely through a rewrite; ecosystem, hiring and tooling are largely reachable through partial adoption. In practice only the first one is strong enough to justify rewriting everything.

Why it is risky - where rewrites break

The process used here was reasonably tight. By the vendor's own description, the team first wrote porting rules and a lifetime mapping table, ran a trial on three files, then scaled to the full set. Implementation and review contexts were separated, with two reviewers per implementer, verification ran against a language-independent test suite, and no test was skipped or deleted. After the merge, coverage-guided fuzzing ran continuously across the parsers.

Even so, the places where this kind of work breaks are predictable.

  • Behaviour no test checks — the reported regressions show the character of the problem well. The result of slicing a UTF-16 string at an odd byte offset; a change in a parser's stack usage. Neither is API surface, both are implementation by-products, and both are hard to catch with tests.
  • The safety boundary that remains — the maintainers state that about 4 percent of the Rust code, roughly 13,000 sites, sits in unsafe blocks, and that 78 percent of those are single-line pointer conversions. As long as C and C++ libraries such as JavaScriptCore stay in the picture, that region does not disappear.
  • Review debt created by speed — when a very large amount of code lands in a short window, the share a human actually read necessarily drops. Public criticism was raised on precisely this point. One external analysis pointed to more than five thousand open pull requests and an unusually long gap between stable releases, and questioned both the substance of the safety improvement and the code quality.
  • Attributing the gains — another external analysis judged the change a net positive for users while arguing that the announcement overstates by bundling improvements genuinely driven by Rust together with engineering that needed no rewrite at all.

The reason to carry these objections is not to render a verdict. It is that the success of a rewrite is not decided at announcement time. What settles it is not a multiplier but elapsed time, and as of August 2026 that time has not passed yet.

What Node.js compatibility actually means

This is the most practical part of the article. Node.js compatibility is the first thing anyone checks when evaluating an alternative runtime, and the word bundles at least four distinct layers. Which layer breaks changes the remediation cost by an order of magnitude.

LayerWhat it meansWhere it breaksHow to check
1. API presenceDoes the module and function, such as node:fs, existCalling an unimplemented module throws immediatelyThe per-module status table in the official compatibility docs
2. Behavioural paritySame input, same output and same errorUnsupported options, differing error codes and messages, encoding edge behaviourNode test suite pass rate, plus your own tests
3. Native addonsDo C and C++ built .node modules loadN-API version gaps, missing prebuilt binaries, build toolchainPull native packages out of the dependency tree and run them individually
4. Timing and private APIsEvent loop ordering, code relying on internal symbolsAPM and instrumentation libraries, monkey patching, test runner hooksReal integration tests. Static analysis will not find this

Layer 1 is solved by documentation. Layer 2 is largely covered by the test suite. The trouble is layers 3 and 4. Migrations in the field almost always fail here, and a compatibility percentage reflects these two layers barely at all.

  • The official docs list node:node-api as implemented, but which N-API versions are covered and whether prebuilt packages actually run are separate questions.
  • node:crypto is backed by BoringSSL, and the docs state that certain key types and ciphers are missing. Certificate and signature code trips here.
  • node:cluster documents that distributing HTTP requests across processes is supported on Linux only. If your development machine is macOS, things may look fine only locally.
  • Worker threads ignore some options and lack specific APIs. Single-executable packaging (node:sea) is listed as not implemented.

How to read a compatibility percentage

A published compatibility rate is usually the pass ratio against the test suite Node.js ships. That number has structural limits.

  • The population is not your code. The Node test suite exists to verify Node itself; it does not represent your dependency tree.
  • File counts and case counts get mixed. 3,743 passing test files and 1,517 newly passing cases are different units. Losing that distinction inflates the figure when quoted.
  • Per-module variance disappears into the total. If some modules are at 100 percent and others at 97, and your code happens to use that 3 percent, the total tells you nothing.
  • The vendor itself writes that it is not 100 percent. That sentence is in this release post. Dropping the caveat the publisher attached is not accurate quoting.

So I treat compatibility rates as an entry condition only. Passing the mid-nineties is a signal that evaluation is worth starting, and the adoption decision comes only from whether install and the test suite pass in my own repository. That holds no matter which runtime is being evaluated.

Read performance numbers together with the publisher and the conditions

Runtime announcements always come with multipliers. That does not make the multiplier false; it means a multiplier and its conditions are one object. Below are the figures published in this release along with the conditions stated in the same post. All of them are vendor self-measurements, not third-party verification.

ItemPublished valueConditions stated in the postHow to read it

The bottom row is the point of the table. The vendor itself puts the performance effect of the port at 2 to 5 percent. The large multipliers above it came from individual feature optimizations, work that in principle did not require a port at all. That is precisely where the external analysis quoted earlier says the announcement overstates.

  • Identify the publisher first. Is it a self-measurement, a third-party benchmark, or something with a reproducible script published alongside.
  • If conditions are not stated, write that they are not stated. A multiplier carried without its conditions is not a citation, it is redistribution.
  • Check the comparison version. Whether the competing runtime was its latest stable or several releases old changes the picture entirely.

The axes that actually decide a runtime

Benchmarks are only the starting point. Adoption is decided on the axes below, listed with how to measure each in your own project.

AxisWhat differsHow to measure it in your projectThe trap
Startup timeWhether cold start lands directly in user-visible latencyStart your real entry point 100 times and record median and p95 togetherMeasuring an empty script is meaningless; dependency loading dominates
Package installCI duration and lockfile compatibilityOne full install with the cache cleared, one with the cache warmA different lockfile format means the whole team must standardize on one tool
Test runnerWhether existing test assets move over as they areRun your most complex test file first. Check mocking, snapshots and timer control earlyPassing only the simple tests hides a wall at the end of the migration
Built-in bundlerNumber of build tools and config filesCompare build output byte by byte. Verify sourcemaps and tree shakingA built-in bundler is convenient until you need fine-grained configuration
Deployment support★The axis that blocks migrations most oftenRead the official support docs of your PaaS, serverless platform and container base imageWorking locally and being supported by your deployment target are different things
Native addonsWhether C and C++ dependent packages loadExtract only native packages from the dependency tree and run them individuallyWithout prebuilds, the whole build toolchain moves into CI
Long term supportHow many years security patches keep comingFind the end-of-support date in the official release policyIf service life exceeds the support window, the next migration is already scheduled

If you can only pick one row, pick deployment support. The other axes have workarounds; this one does not. If your deployment target does not support it, every other advantage is moot.

Not switching is a reasonable choice too

Every time a new runtime appears, the discussion drifts toward when to move. My read leans the other way. For most services, replacing the runtime is a low priority. Here is the honest reasoning.

  • Maturity can only be bought with time. Independent of code quality, a track record of years without incident on a given combination cannot be produced by money or by rewriting. A first stable release by definition has none.
  • The support policy has to match your service life. If it is unclear how long security patches will arrive, you have effectively scheduled the next migration on the day you adopt.
  • House standards exist for reasons. CI images, security scanners, APM agents and incident procedures are all built around a specific runtime. Change the runtime and everything attached to it moves too.
  • The bottleneck is usually not the runtime. If most of your latency is database round trips and outbound API waits, halving startup time changes nothing a user can feel.

None of that makes new runtimes worthless. For workloads where cold start is the cost, repositories where CI time directly taxes the team, and greenfield projects whose goal is collapsing the tool chain, the arithmetic is entirely different. The point is not who won but under what conditions. Asking which runtime wins is usually a badly posed question.

If you do move - test order and rollback points

If you decide to evaluate, order matters. The principle is to test whatever fails cheapest and fastest first. The sequence below applies to any runtime migration.

  • Step 1 — dependency install only. Without touching production code, install with the new runtime's package manager. If it stops here, nothing else matters. Extract the list of native packages at this step.
  • Step 2 — swap only the test runner. Keep the execution runtime as it is and run the tests with the new runner. Look at the character of the failures, not the pass rate. Breakage in mocking, timers or snapshots is a layer 4 problem and therefore expensive.
  • Step 3 — one non-critical service. Pick a service with real traffic but limited blast radius and actually run it. A batch job or an internal tool works well.
  • Step 4 — compare observability. Put resident memory, p95 and p99 latency, restart frequency and exception types side by side in the same window before and after. Averages hide a worsened tail.
  • Rollback point 1 — make the runtime configuration, not code. One container image tag or one pipeline variable should return you to the old runtime. Embedding runtime-specific APIs in your source erases this point.
  • Rollback point 2 — write the abort criteria in advance. Put them in numbers: abort if p99 degrades by X percent, abort if any native dependency lacks a prebuild. The further a migration goes, the more sunk cost bends the criteria.

One more thing. Adopting the new runtime's built-in APIs — image processing, cron, archives — early in a migration is not something I would recommend. It is convenient, and it is also erasing your own rollback point. Moving them over one at a time after the migration has settled is not too late.

What I could not confirm

Collected in one place, the items for which I could not secure evidence.

  • A baseline for the unsafe site count. I could not find a public baseline that would tell whether roughly 13,000 is high or low compared with hand-written Rust projects of similar size. Without a comparison, neither claim can be made.
  • The real coverage of native addons. The official docs mark N-API as implemented, but the supported N-API versions and whether widely used prebuilt packages actually run are not documented.
  • Consistency of the measurement environment per item. Hardware is stated for stream throughput, but for items such as HTTP server memory and Windows startup time I could not confirm a stated machine.
  • Third-party reproduction. I found no independent benchmark reproducing this release's figures. The external posts cited above analyse the announcement rather than measuring it themselves.
  • Official support status per cloud vendor. When major serverless and PaaS providers officially support this version has to be checked in each vendor's documentation. I did not check it for this article.

Conclusion: what runtime competition leaves users

What remains from this episode is not which runtime is faster. It is that the cost of rewriting running software has been documented in public. Eleven days, nineteen regressions, a 4 percent safety boundary, a 2 to 5 percent pure performance effect, and the public objections raised against all of it. That combination is a fairly concrete reference point for any team weighing a similar decision.

The benefit to users is also real. When runtimes compete, startup times fall, tool chains consolidate, and defaults improve. That effect reaches the side that does not migrate as well, because an established runtime tends to move along the same axes once a competitor appears.

To summarize. Read published multipliers with their conditions, use compatibility rates as an entry condition only, and make the adoption decision from install and tests in your own repository. And deciding not to switch is an equally well-grounded conclusion. If the runtime is not your bottleneck today, that judgement will not change when the next release lands.
