A Denylist Is Always Late - How to Flip It Into an Allowlist

From counting what to block to deciding what to handle, with measured numbers and a four-phase migration

2026-08-01 Development/Infrastructure

Introduction: another line went onto the list of things to block

There was an incident yesterday, and this morning one more line went onto the list. The same thing happened last month, and the month before that. The list is past forty lines now, and nobody can explain what every line was originally meant to stop. And yet there is a distinct feeling that the same meeting will happen again next month. That feeling is accurate.

This article does not begin with the advice「use an allowlist」. That advice has been repeated hundreds of times, and every time people nod and then go back to adding one more line to the denylist. The reason it does not stick is that almost nobody has seen numbers for why a denylist is late by construction.

The claim is a single one. A denylist is late not because attacks are fast, but because the world moves first. New file formats appear, new characters enter the standard, new devices send new values. A list of bad things therefore cannot be finished, as a matter of principle. Meanwhile the list of things we can handle is decided by us. Its size is not set by the outside world; it is set by us.

Which is why an allowlist is a specification before it is a security technique. It is a written record of what we are able to process, and validation is simply that record moved into code. The article proves that claim with eight runs, and closes with a four-phase procedure for turning around a system that already runs on a denylist.

Environment. Every output below was produced by actually running the code on Windows 10 Pro (10.0.19045). The runtimes are Node.js v22.16.0 (win32) and Python 3.13.3, the shell is GNU bash 5.2.37 (MSYS2/MinGW64). Every simulation uses a fixed-seed linear congruential generator, so the same code yields the same numbers.

There are no bypass techniques here. This is not an article that shows how to break something; it shows the structure of why a list of bad things can never be completed. All example values were chosen to be harmless: file extensions, sort column names, an order id format and page numbers.

What this article does not cover. The question of ordering normalization and validation, where one value has several spellings, is handled separately in Change the Value After Validating It and the Validation Is Void. Section 3 touches on spelling variants but does not repeat the ordering argument. A broad map of web security lives in Web Security and OWASP Top 10. This article digs into one point only: the direction of the list.

1. Count the two sets and the argument is already over

The first thing to do is arithmetic, not debate. Suppose the rule is that file upload accepts only csv, png and pdf. How many lines does the same rule need as a denylist? I walked this machine's disk and counted the extensions that actually exist on it.

  • The size of an allowlist is decided by us. Fix it at three and it stays three
  • The size of a denylist is decided outside. Every new format that appears creates the need for one more line
  • So the two lists are not the same kind of object. One is a specification we write, the other is an attempt to transcribe the world's inventory

2. Adding one line per incident still widens the hole

Real denylists are not written all at once. They grow one line at a time, after each incident. I simulated exactly that process. The value universe grows by four each period, and we diligently add one line per incident.

--- 2-1. a denylist that grows one line per incident ---
period  new values  universe  denylist  values still admitted  admitted %
---------------------------------------------------------------------------
     1           4       124         1                    123        99.2
     4           4       136         4                    132        97.1
     8           4       152         8                    144        94.7
    12           4       168        12                    156        92.9
    16           4       184        16                    168        91.3
    20           4       200        20                    180        90.0
    24           4       216        24                    192        88.9

--- 2-2. the same 24 periods, with the allowlist instead ---
allowlist entries written : 3 (unchanged since period 1)
universe at period 24     : 216
values still admitted     : 3
admitted %                : 1.4

Read the percentage alone and it looks like an improvement, from 99.2 to 88.9. But the absolute count moved the other way. Admissible values went from 123 to 192. Nobody slacked for 24 periods, and the doors left open ended up 69 more than at the start.

--- 2-3. the race, stated as a rate ---
denylist entries added per period : 1.0
new values arriving per period    : 4.0
net change in admitted values     : +2.9 per period
after 24 periods of diligent work, the hole is BIGGER than when we started (123 -> 192)

--- 2-4. how many entries would the denylist need to catch up? ---
  adding 1 entries/period -> net -3 /period : never closes
  adding 2 entries/period -> net -2 /period : never closes
  adding 4 entries/period -> net +0 /period : never closes
  adding 6 entries/period -> net +2 /period : closes in 96 periods

That is the precise meaning of「late」. Lateness is not a question of anyone's diligence but of the growth rates of two sequences. If four new values arrive per period and you add four lines per period, you stand still forever. Only at six lines does the gap start to shrink, and even then it takes 96 periods to close.

Over the same 24 periods the allowlist stayed at three lines. While the universe swelled to 216 values, no work was done at all and the admitted share actually fell to 1.4 percent. A growing world works in the allowlist's favour. That asymmetry is the whole article.

3. One meaning, seventeen spellings

The second structural reason is the gap between spelling and meaning. A list records spellings, but what we want to control is meaning. I took a three-letter value and mechanically produced other ways to write the same thing: case, leading and trailing whitespace, a tab, a trailing dot, fullwidth Latin letters, an inserted zero-width character, and a percent form.

node v22.16.0
--- 3-1. how many ways can you write three letters? ---
spellings generated for tmp : 17
spellings generated for csv : 17
and this generator is not exhaustive -- it uses 9 tricks, not all of them

--- 3-2. a few of them, printed as codepoints ---
  [tmp]           U+0074 U+006D U+0070
  [TMP]           U+0054 U+004D U+0050
  [tmp ]          U+0074 U+006D U+0070 U+0020
  [tmp.]          U+0074 U+006D U+0070 U+002E
  [ｔｍｐ]           U+FF54 U+FF4D U+FF50
  [t​mp]          U+0074 U+200B U+006D U+0070
  [t­mp]          U+0074 U+00AD U+006D U+0070
  [%74%6d%70]     U+0025 U+0037 U+0034 U+0025 U+0036 U+0064 U+0025 U+0037 U+0030

Then came the decisive experiment. I pushed the exact same list of spellings through both rules. One is a denylist saying「block this value」, the other an allowlist saying「accept only this value」.

--- 3-3. the same spellings through the two rules ---
rule       input meaning   spellings  matched  unmatched  what unmatched means
---------------------------------------------------------------------------------
denylist   a bad value            17        1         16  it got through
allowlist  a good value           17        1         16  it got rejected

denylist hit rate  : 5.9 %  -> 16 spellings of the SAME meaning passed
allowlist hit rate : 5.9 %  -> 16 spellings of the SAME meaning were refused

--- 3-4. identical arithmetic, opposite consequence ---
both rules matched exactly 1 spelling out of 17.
the denylist turned 16 misses into 16 openings.
the allowlist turned 16 misses into 16 complaints.
a complaint arrives with a name, a timestamp and a person attached. an opening does not.

The hit rates are identical. Both matched 1 of 17, both missed 16 times. What differs is what the misses turn into. The denylist's 16 misses become open doors; the allowlist's 16 misses become complaints.

A complaint arrives with a name, a timestamp and a person attached. An open door arrives with nothing attached. The direction of a list does not change its accuracy. It changes which way the errors fall.

--- 3-5. do the variants collapse under a canonical form? ---
tmp spellings 17 -> distinct canonical forms : 3
   [tmp] [tmp.] [%74%6d%70]
csv spellings 17 -> distinct canonical forms : 3
   [csv] [csv.] [%63%73%76]
the percent form survives: it is a different encoding layer, not a different spelling
  • Standard normalization, whitespace trimming, zero-width removal and lowercasing collapse 17 spellings into 3
  • The trailing dot and the percent form survive. The percent form is not a different spelling but a different encoding layer, and layers do not collapse under one normalization pass
  • Doing that normalization before validation matters a great deal, but that ordering question belongs to a separate article and is not repeated here
  • The point to keep is one. Even perfect normalization leaves the direction problem untouched. Normalization reduces the number of spellings; it does not reduce the number of new values the world invents

4. An allowlist fails by refusing good input

The most common objection to allowlists is that legitimate requests get blocked. That is true. It is the allowlist's failure mode, and the point of this section is that it is the survivable one. I ran 20,000 synthetic requests with a long tail through a three-entry allowlist.

Four extra lines lifted the pass rate from 78.83 percent to 94.43 percent. The list is still seven lines. Set that against section 2, where a denylist spent 24 lines and fell further behind.

The third row is the heart of it. An allowlist can print how many times it was wrong; a denylist cannot.「How many did our denylist miss last month」is not a hard question but a structurally unanswerable one, because you cannot count what you did not look for.

A classic says the same thing. In 1975 Saltzer and Schroeder listed「base access decisions on permission rather than exclusion」among their protection design principles, for the same reason. A mistake in a mechanism that grants explicit permission tends to fail by refusing permission, a safe situation because it will be quickly detected, whereas a mistake in a mechanism that explicitly excludes tends to fail by allowing access, a failure which may go unnoticed in normal use. The 4,234 above, set against「not countable」, is the numeric edition of that sentence.

5. Describe the shape, not the list

Here the argument has to turn. An allowlist is not always the answer. If the set of acceptable values is open, a list does not even get off the ground. Take an order id: three uppercase letters, a hyphen, eight digits.

python 3.13.3 / win32
--- 5-1. the good set is not listable ---
order id form              : 3 uppercase letters, a hyphen, 8 digits
how many valid values      : 1,757,600,000,000
bytes to store them as a list at 13 B each : 22,848,800,000,000 B
lines of code for the shape rule           : 6

There are 1,757,600,000,000 valid values. Writing them down as a list costs over 22 terabytes. Writing the shape costs six lines: length, character set, separator position, range. That is what「describe the shape, not the list」means.

The usual tool for a shape is a regular expression. But a regex has places where it drifts quietly. I put the same inputs through three regex habits that express the same intent.

python 3.13.3 / win32
--- 5-2. three regex habits, same intent, different answers ---
input                              match+$   search    fullmatch+\d
-------------------------------------------------------------------
  'ABC-12345678'                      yes      yes      yes
  'ABC-12345678\n'                    yes      yes       no
  'note: ABC-12345678 thanks'          no      yes       no
  'abc-12345678'                       no       no       no
  'ABC-1234567'                        no       no       no
  'ABC-1234567\u0669'                  no       no      yes
  'ABC\u201312345678'                  no       no       no
  ''                                   no       no       no

row 2: $ also matches just before a final newline, so match()+$ says yes
row 3: search() has no anchors, so any surrounding text is fine
row 6: \d is not [0-9]; it accepts every decimal digit in Unicode
  • Row two. Despite the end anchor, a value with a trailing newline passed. That behaviour is documented: the end anchor matches at the end of the string and just before a final newline
  • Row three. A search function without anchors matches even when the value is buried inside a sentence
  • Row six. The shorthand digit class does not mean ASCII digits. It accepts the entire Unicode decimal digit category, so a digit from another writing system passes
  • Row seven. A value whose dash is an en dash rather than a hyphen was refused by all three. But none of them says why

Which is why a shape rule is better served by a parser. I wrote a function that takes the same input apart in order, length, separator, character set, and returns a reason for refusing.

--- 5-3. the same inputs through a parser that returns a REASON ---
input                              parsed              reason
---------------------------------------------------------------------------
  'ABC-12345678'                   ('ABC', 12345678)   ok
  'ABC-12345678\n'                 -                   length is 13, must be 12
  'note: ABC-12345678 thanks'      -                   length is 25, must be 12
  'abc-12345678'                   -                   prefix has a character outside A-Z
  'ABC-1234567'                    -                   length is 11, must be 12
  'ABC-1234567\u0669'              -                   serial has a character outside 0-9
  'ABC\u201312345678'              -                   separator is U+2013, must be U+002D
  ''                               -                   length is 0, must be 12

Every result is the same「refused」, yet every reason is different. In practice that reason does three jobs. It becomes the message shown to the user, it becomes an operational metric, and it pinpoints human mistakes such as「the separator was an en dash」. A regex returns only true or false and can do none of the three.

The other face of a shape rule is a range. Page numbers cannot be captured by a list at all.

--- 5-4. a range is a shape too ---
page number rule : integer, 1..100
  '1'       accept   in range
  '100'     accept   in range
  '0'       refuse   out of range
  '101'     refuse   out of range
  '1e2'     refuse   not made of 0-9
  '07'      refuse   leading zero, two spellings for one number
  ' 5'      refuse   not made of 0-9
  '+5'      refuse   not made of 0-9
  '5.0'     refuse   not made of 0-9
  '\u0665'  refuse   non-ascii digit

a denylist of bad page numbers would have to name every integer except 100 of them.
the shape rule names 2 bounds. this is not a security trick, it is arithmetic.

Look at row six. The leading zero was refused not because it is dangerous but because it gives one number two spellings. Unique spelling is what keeps cache keys from splitting and log aggregation from drifting. A shape rule is a data rule before it is a security rule.

6. Where a list is the right answer: the closed set

There is also a place where a list is the easiest and most certain tool: when user input corresponds to a set whose size we know. List sorting is the archetype, with six sortable columns and two directions.

node v22.16.0
--- 6-1. the set of things the user may ask for ---
sortable fields  : 6
directions       : 2
combinations     : 12
this number does not grow when the world invents a new file format.
it grows when WE add a column. that is a code review, not an incident.

--- 6-2. every possible output, printed in full ---
   1. created_at ASC
   2. created_at DESC
   3. customer_name ASC
   4. customer_name DESC
   5. order_status ASC
   6. order_status DESC
   7. store_code ASC
   8. store_code DESC
   9. total_amount ASC
  10. total_amount DESC
  11. updated_at ASC
  12. updated_at DESC
distinct clauses the program can ever emit : 12

That last line is the definition of a closed set. Every string the program can ever emit can be printed in full. There are 12. This list does not grow when the world invents a new file format. It grows only when we add a column, and that is a code review rather than an incident.

--- 6-3. exhaustive test: all valid pairs ---
valid pairs tested : 12   accepted : 12   rejected : 0
coverage of the input space : 100 %
an exhaustive test is possible here. that is what closed means.

--- 6-4. things that are not in the map ---
input               accepted   clause emitted
-------------------------------------------------------------
  "Date"                no         created_at DESC
  "date "               no         created_at DESC
  "created_at"          no         created_at DESC
  "amount desc"         no         created_at DESC
  "total_amount"        no         created_at DESC
  ""                    no         created_at DESC
  "DATE"                no         created_at DESC
  "amount;"             no         created_at DESC
  "price"               no         created_at DESC

Look at rows three and five. Even the internal column names were refused, because the mapping runs one way. The string the user sends is only ever a key, never a value. That is the real reason an allowlist is strong on a closed set: not that validation passed, but that the user's string never reaches the output at all.

--- 6-5. the same field through a denylist, for contrast ---
input               clause emitted
-------------------------------------------------------------
  "date"                ORDER BY date
  "Date"                ORDER BY Date
  "price"               ORDER BY price
  "nonexistent_column"  ORDER BY nonexistent_column
  "created_at"          ORDER BY created_at

the denylist version emits a clause built from text it has never seen before.
the allowlist version can only emit one of 12 strings written by us.
same feature, same effort, and one of them has an output set you can print.
  • The feature is identical. Sorting works and the user experience is the same. The effort is comparable too
  • The only difference is the output set: twelve strings on one side, whatever the user sent on the other
  • On a closed set there is nothing to deliberate. Use a list, build it as a mapping, attach an exhaustive test
  • Do not forget a default. Falling back to the default sort rather than an error when nothing matches keeps the user experience intact

7. Where to keep the list

Once the direction is settled, the next question is location. Code, config file or table changes who changes it and when. I put the same list in all three places and applied the same change.

--- 7-1. three homes, same three entries ---

  config   ["csv","png","pdf"]   fingerprint 9657f79fbb4e
  db       ["csv","png","pdf"]   fingerprint 9657f79fbb4e

--- 7-2. the same change applied to each ---
  code     ["csv","png","pdf","xlsx"]   fingerprint 5484a20a7ba7
  config   ["csv","png","pdf","xlsx"]   fingerprint 5484a20a7ba7
  db       ["csv","png","pdf","xlsx"]   fingerprint 5484a20a7ba7

The results are identical, fingerprints included. The difference is not in the result but in what remains afterwards. Ask the one question that always arrives after an incident.

HomeCan you answer「the list yesterday at 14:00」WhyTakes effectWho can change it
CodeYesThe diff and its review are the recordOn deployEngineers

Keeping it in a table is not wrong in itself. If operators must change the list without a deploy, a table is right. But you have to write the history yourself. I attached a scheme that records time, actor, reason, fingerprint before and fingerprint after as a single row.

--- 7-4. the fix for the table case: write the history yourself ---
when      actor        before -> after             added      removed   reason
-----------------------------------------------------------------------------------------------------
  10:00:00  ops-oncall  5484a20a7ba7->2dfe277b36e2  jpg        -         reject log: 1232 refusals for jpg
  11:00:00  data-team   2dfe277b36e2->9508ed61a09c  tsv        -         weekly export is tab separated
  12:00:00  ops-oncall  9508ed61a09c->2dfe277b36e2  -          tsv       tsv rolled back, importer not ready

audit rows written : 3
current fingerprint: 2dfe277b36e2
and it matches the last after_fp : true
  • The third row is a rollback. The fingerprint returned exactly to the second row's previous value. Without audit rows that round trip vanishes without trace
  • As the last line shows, you can mechanically verify that the current fingerprint matches the last audit row. A quiet change made through the console shows up right here
  • Notice that the reason column carries a count from the refusal log. The feedback loop from section 4 arrives here
  • A list with no change history is not a control. Knowing what it blocks now is not enough; if you cannot say what it blocked then, incident investigation is impossible
--- 7-5. what each home is actually good for ---
home         use it when                               example                        change speed
---------------------------------------------------------------------------------------------------
  in code      the set is closed and rarely changes      sort fields, roles, currencies slowest, safest
  in config    differs per environment                   upload types per tenant        medium
  in a table   operators must change it without a deploy per-customer overrides         fastest, needs an audit row

the rule is not where, it is this: a list nobody can reconstruct is not a control.

8. The migration: observe, derive, warn, block

Now the most practical part. How do you turn around a system that already runs on a denylist? Do not start with blocking, because as section 4 showed, 21 percent goes down on day one. I walked the four phases in order over 90 days of synthetic traffic.

Phase one is observation. Log the value and stop nothing. There is one number to watch: how many previously unseen values arrive per day.

node v22.16.0
--- 8-1. phase 1, observe only: does the value set settle down? ---
day   requests   new values today   distinct so far   volume covered by top 8
--------------------------------------------------------------------------------
   1        900                 27                27                   96.89 %
   2        900                  5                32                   96.72 %
   3        900                  4                36                   96.52 %
   4        900                  1                37                   96.67 %
   5        900                  0                37                   96.49 %
   7        900                  0                37                   96.51 %

  21        900                  0                37                   96.45 %
gate to leave phase 1: zero new values for 7 straight days, or a full business cycle.

Twenty-seven arrived on day one, one on day four, zero from day five. The curve itself is the justification for the observation window. Instead of「a week should do」you can say「we confirmed seven consecutive days with zero new values」. That said, when there is work on a long cycle such as month-end settlement or quarterly reporting, one full cycle must pass through. This simulation has no such cycle, hence the convergence within five days, but in a real service it must be checked.

Phase two is derivation. Rank the collected values by frequency, and then judge them one line at a time, by hand.

Here sits the most common trap. It is tempting to adopt the 12 values the data produced. But on inspection five of them were merely present in traffic, never something anyone agreed to accept. Frequency is not a reason. Automation produces candidates; people make the judgement. Nothing moves to the next phase until every entry carries an owner and a reason.

Phase three is warning. Apply the list but block nothing. Record only what you would have refused.

gate to leave phase 3: the would-refuse rate is flat, and every entry in it has been read by a person.
  • The would-refuse rate flattened around 7 percent. That flatness is the signal that you may proceed
  • The last column of previously unseen values keeps producing entries from day 22 to day 25 and then stops. Wait until that column starts coming up empty
  • The purpose of warn mode is to widen the list, never to narrow it. It exists to find values that are legitimate but would be blocked
  • Skip this phase and you hand the day-one 21 percent from section 4 straight to your users

The final two lines matter. Leave the denylist in place throughout the migration. Cases will appear where the new allowlist admits something the old denylist blocks, and that is not a conflict but a finding: one of the two is wrong, and now you have something to investigate. Remove the denylist last, or never.

As for that 6.93 percent refusal rate: it is not a defect. It is the part of the world we decided not to handle, and what changed is that it used to be a tacit assumption and is now written down. That is what the introduction meant by「an allowlist is a specification」.

9. List or shape: the decision table

Compressed into a single judgement, everything above says: countable means list, uncountable means shape. Applied to real input fields, it looks like this.

InputSetUseWhy
Sort column nameClosed (6)Allowlist plus mappingThe user string is only a key, never a value
Sort directionClosed (2)Allowlist12 combinations, exhaustive testing finishes
Currency and country codeClosedAllowlistAn external standard hands you the list
Role names and status valuesClosedAllowlist (in code)An enumeration we defined ourselves
Upload extensionHalf closedAllowlist (in config)Only what we can process, widened in operation

One caution when using the table. When in doubt, fix the shape first. Nail down length and character set and you can layer a list inside it later, but start from a list and retrofitting a shape is awkward. And the two are not exclusive. An upload extension can be run through a shape rule first, one to five alphanumeric characters, with the list applied inside it.

Finally, note where a denylist earns its keep. When a specific known value must be stopped in a hurry, it works as a temporary fence while the allowlist is being widened. But even then you must record why it was put up and when it comes down. Failing to record that is how a list gets to forty lines.

10. What this article did not verify

  • A simulation is a simulation. The traffic in sections 2 and 8 is synthetic data from a fixed seed. I chose the value distribution and the arrival rate of new values, so a real service will produce different numbers. Take the structure, not the figures
  • The 115 in section 1 belongs to this machine. Another disk gives another value. What matters is not the ratio of 3 to 115 but the property that one side is fixed while the other grows
  • Regex anchor behaviour varies by language. The end-anchor issue in section 5 was verified in Python. Other languages may behave differently, so test the trailing-newline case in your own runtime
  • Which layer validation belongs in is not covered here. Whether it sits at the edge or inside the domain, and how many times each layer should check, is a separate and large subject
  • The ordering of normalization for spelling variants belongs to another article. Section 3 only showed the variants collapsing to three; when to collapse them is discussed there
  • Performance was not measured. Whether a list lookup or a parser call is faster is not this article's concern. Neither is a problem at production scale

Conclusion: an allowlist is a specification before it is a security technique

Eight runs reduce to one sentence. A denylist and an allowlist do not differ in accuracy; they differ in which way the errors fall. In section 3 their hit rates matched to the decimal. What differed was whether 16 misses became 16 open doors or 16 complaints.

And that direction decides whether recovery is possible. A complaint lands in a log, a person reads it, and the list widens. Section 4's four extra lines lifting the pass rate from 78.83 percent to 94.43 percent is that circuit at work. Open doors have no such circuit. There is no function that counts how many of them are standing open.

But do not stop at「use an allowlist」. On a closed set, as in section 6, a list is overwhelmingly the easier tool; on an open set, as in section 5, a list does not even get off the ground. With 1,757,600,000,000 values behind a single order id format, trying to build a list is a failure of judgement rather than of direction. There you write length, character set, separator and range, which is to say the shape.

There is one thing you can do today. Open one list you currently maintain and write on its first line whether it is an allowlist or a denylist. If that line will not come out, the list never had a direction. And if you wrote denylist, write next to it why it was left as one. If the only reason is「there was an incident that time」, you can begin phase one from section 8 today. It only logs values, so it blocks nothing and can be switched on this afternoon.

# Allowlist Instead of Denylist — Decision Table, Migration Steps, Checklist

> Source: braindetox.kr — A denylist is always late
> Evidence: figures produced by running the code on Windows 10 Pro / Node.js v22.16.0 / Python 3.13.3
> How to use: paste this file into an AI tool and say「check our input validation against these criteria」.
> ⚠ When you flip a list, do not start with blocking. Observe → derive → warn → block. Any other order stops the service before it protects it.

## 0. One-line summary

| Item | Denylist | Allowlist |
|---|---|---|
| Who decides the size | The world (it keeps growing) | Us (fixed) |
| When the rule misses | It passes — nobody finds out | It is refused — visible in logs and tickets |
| Measured, same conditions | 1 of 17 spellings matched → 16 passed | 1 of 17 spellings matched → 16 refused |
| Question after an incident | 「How many did we miss」 — unanswerable | 「How many did we refuse」 — it is in the log |
| Arithmetic | Identical (5.9 % hit rate) | Identical (5.9 % hit rate) |

Same arithmetic, opposite consequence. Only the direction changed.

## 1. Why a denylist is late by construction

- Not because attackers are fast, but because **the world moves first**
- New file formats, new characters, new devices and new clients keep appearing
- Measured: with the value universe growing by 4 per period and one line added per incident, after 24 periods the set of admissible values grew from 123 to **192**
- To catch up you must add 6 or more lines per period, and even then it takes 96 periods (measured)
- The other side: a 3-line allowlist went 24 periods **without a single edit** and admitted 1.4 %

## 2. Decision table — list or shape

**An allowlist is not always the answer.** If the target set is closed, use a list. If it is open, describe its shape.

| Input | Set | Use | Why |
|---|---|---|---|
| Sort column name | Closed (6) | **Allowlist + mapping** | The user string is only a key, never a value |
| Sort direction | Closed (2) | Allowlist | 12 combinations, exhaustive testing finishes |
| Currency / country code | Closed | Allowlist | An external standard hands you the list |
| Role names, status values | Closed | Allowlist (in code) | An enumeration we defined ourselves |
| Upload extension | Half closed | Allowlist (in config) | Only what we can process, widened in operation |
| Order id, employee id | Open (1.7 trillion) | **Shape rule + parser** | Cannot be enumerated; fix length, charset, separator |
| Page number, page size | Open (integers) | **Range rule** | You cannot list the bad integers |
| Date and time | Open | Shape rule + parsing | Successful parsing is the validation |
| Free-form text | Open | Shape (length, character category) plus output-side handling | The area a list cannot close |

The one-line rule: **countable means list, uncountable means shape.** When unsure, fix the shape first, then put a list inside it.

## 3. What belongs in a shape rule

- **Length** — set both a floor and a ceiling (a ceiling alone lets the empty value through)
- **Character set** — `0-9` and「every Unicode digit」are different things. Measured: `\d` also accepts Arabic-Indic digits
- **Format** — separator position and count. Check whether the dash is a hyphen (U+002D) or an en dash (U+2013)
- **Range** — numeric bounds; for dates, how far into the past and future
- **One spelling per value** — refuse leading zeros, plus signs and padding spaces, the second spelling of the same number
- **A parser beats a regex** — measured: `re.match` with a trailing end anchor **accepts a value that carries a trailing newline**. `re.fullmatch` and a hand-written parser refuse it
- A parser **returns a reason**. A regex returns true or false. In operations that difference is large

## 4. Where to keep the list

| Home | Use it when | Takes effect | Who can change it | History |
|---|---|---|---|---|
| Code | The set is closed and rarely changes | On deploy | Engineers | The diff and its review are the record |
| Config file | It differs per environment or tenant | Restart or reload | Engineers and operators | Only if the file is under version control |
| Table | Operators must change it without a deploy | Instantly | Anyone with console access | **None, unless you write the audit row yourself** |

- After an incident exactly one question arrives — **「what was that list yesterday at 14:00」**
- A list that cannot answer it is not a control
- If it lives in a table, record time, actor, reason, fingerprint before and fingerprint after **as one row**
- With fingerprints you can mechanically verify that the current value matches the last audit row

## 5. Migration — four gates

| Phase | What you do | What you watch | Move on when |
|---|---|---|---|
| 1 Observe | Log the value, change nothing | New values seen per day | Zero for 7 straight days, or one full business cycle |
| 2 Derive | Rank by frequency, then **review every line by hand** | Entries with an owner and a reason | All of them have both |
| 3 Warn | Record what you would have refused, refuse nothing | Would-refuse rate | Flat for 7 days and every entry read by a person |
| 4 Block | Refuse, and **put the reason in the response** | Refusal rate and support tickets | No surprise in the first week |

- Phase 1 measured: 27 new values on day 1, 1 on day 4, 0 from day 5 — that curve is your evidence for how long to observe
- Phase 2 trap: **frequency is not a reason.** Of 12 candidates picked by volume, a human removed 5
- Phase 3 exists to widen the list, not to narrow it
- Phase 4 measured: 7 entries passed 93.07 % and refused 6.93 %. That 6.93 % is **not a bug but the part of the world we decided not to handle**
- Keep the denylist through all four phases. Two rules that disagree is a **finding**, not a conflict

## 6. Checklist

- [ ] Every list states its **direction** (is this allow or deny)
- [ ] Every surviving denylist records **why it was kept**
- [ ] Each input has been **judged and recorded** as a closed or open set
- [ ] Open sets use a **shape rule**, not a list
- [ ] Every shape rule has a **minimum length**
- [ ] Character sets are written as **explicit ranges**, not `\d` or `\w`
- [ ] Anchoring was verified with `fullmatch` (the trailing-newline case was actually tested)
- [ ] Refusals **return a reason**, not just true or false
- [ ] Closed sets use the user string **only as a key**, never as a value
- [ ] Closed sets have an **exhaustive test**
- [ ] The home of the list (code, config, table) was **chosen deliberately**
- [ ] Lists kept in a table have an **audit row** (time, actor, reason, before, after)
- [ ] 「The list as of yesterday at 14:00」 **can be reconstructed**
- [ ] Somebody **reads the refusal log** on a schedule
- [ ] There is a **path to widen the list** when a legitimate value shows up in that log
- [ ] The migration ran observe → derive → warn → block
- [ ] Warn mode was **not skipped**
- [ ] Spelling variants are normalized once before validation (mind the order)

## 7. Do not

- ❌ Add one more line to the denylist after every incident and stop there — measured, the hole gets bigger
- ❌ Decide to「use an allowlist」and then **turn on blocking immediately** — 20 % of normal traffic stops that minute
- ❌ Freeze the list from **observed frequency alone** — a common value is not automatically an acceptable one
- ❌ Pass the user string through as an internal name in a closed set — it must only be a key into a mapping table
- ❌ Try to enumerate an open set — one order-id shape holds 1.7 trillion values
- ❌ Let one regex stand in for a parser — no reasons come back and the anchors drift silently
- ❌ Keep the list in a table **without audit rows** — nothing can be reconstructed afterwards
- ❌ Build a refusal log **that nobody reads** — it is the allowlist's only feedback path
- ❌ Delete the denylist on day one of the migration — delete it last, or never

## 8. Prompt you can paste as is

```
Review our input validation against the criteria below.

1) List every place that accepts user input and judge whether the
   target set is closed or open.
2) Find closed sets that are currently handled with a denylist.
3) Find open sets that someone tried to enumerate. Propose a shape rule instead.
4) Find regex checks that do not anchor with fullmatch, and character
   sets written as shorthand classes instead of explicit ranges.
5) Produce a table of where each list lives (code, config, table) and
   whether its changes leave a history.
6) Propose a schedule for the items that need migrating, using the four
   phases observe, derive, warn, block.
```
