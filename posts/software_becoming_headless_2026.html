사용자가 더 이상 인터페이스를 보지 않는다 - Headless Software가 SaaS의 다음 형태가 되는 이유

2026-05-23 IT/기술

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 사용자가 인터페이스를 보지 않는 시대의 신호

2026년 들어 SaaS 업계 분석가들 사이에서 조용히 도는 표현이 하나 있다. "우리 제품의 화면 사용량이 줄고 있다." 매출은 늘고, API 호출은 늘었는데, 정작 사람 사용자가 클릭한 횟수는 감소했다는 것이다. 처음에는 단순히 자동화 도구의 보급이 늘었기 때문이라고 해석되었다. 그러나 2025년 후반부터 AI 에이전트가 본격적으로 업무에 투입되기 시작하면서 이 현상의 근원이 바뀌었다. 사용자가 인터페이스를 직접 보지 않는 이유는, 사용자를 대신해 에이전트가 호출하기 때문이다. 사람이 화면을 보지 않아도 결과는 만들어지고, 그 결과는 다시 다른 에이전트의 입력이 된다. 이 흐름이 이어지면, 소프트웨어에서 "화면"이라는 부품은 부수적이 된다.

news.hada.io 2026년 5월 22일자에 올라온 "Is Software Becoming Headless?" 토픽은 이 변화에 처음으로 적절한 이름을 붙였다. Headless Software. 머리가 없는 소프트웨어. GUI라는 머리를 잘라내고 API라는 몸통만 남긴 형태. 이 표현은 단순한 비유가 아니라 SaaS 산업의 다음 단계가 어떤 모양일지를 정확히 예고한다. 본 글은 hada.io의 분석을 단순 번역하지 않고, 그 출발점 위에 한국 IT 시장에서 실제로 일하는 입장에서 얻은 관찰과 예측을 더해 12개 챕터로 풀어 본다.

핵심 질문은 셋이다. 첫째, 헤드리스화는 모든 소프트웨어에 일어나는가 아니면 특정 영역에 국한되는가. 둘째, 헤드리스 소프트웨어가 되는 데 필요한 설계 조건은 무엇인가. 셋째, 한국의 SaaS와 플랫폼 사업자들은 이 흐름에서 어디에 서 있는가. 이 세 질문에 답하기 위해 Stripe Agent Toolkit·Cal.com·HubSpot AI·Mixpanel·Contentful 5개 영역을 사례로 다루고, MCP와 Function Calling이 만든 에이전트 호환성 표준을 분석하며, 마지막으로 즉시 적용 가능한 세 가지 행동을 제시한다.

"Headless"의 짧은 역사 - CMS에서 commerce, 그리고 software로

Headless라는 용어 자체는 2015년 전후 Contentful·Sanity 같은 헤드리스 CMS 진영에서 처음 일반화되었다. 발상은 단순하다. 콘텐츠 저장과 콘텐츠 표현을 분리한다. WordPress 시절에는 두 영역이 한 덩어리였고, 그래서 모바일 앱·키오스크·스마트 디스플레이 등 새 채널이 등장할 때마다 코어를 또 깎아야 했다. 헤드리스 CMS는 콘텐츠를 JSON으로 노출하고 프런트엔드는 개발자가 자유롭게 짜라는 분리를 도입해 이 비용을 없앴다.

두 번째 단계는 2018년 전후 commercetools·Shopify Hydrogen으로 대표되는 Headless commerce다. 카트·주문·결제·재고가 API로 노출되고 스토어프런트는 React든 Next든 Unity든 자유다. 옴니채널이라는 단어가 결정적으로 의미를 가진 시점이 이때다. 그러나 두 단계 모두 호출 주체는 사람이 만든 프런트엔드라는 가정이 유지되었다. 모바일 앱이든 웹이든 어쨌든 마지막에는 사람이 본다는 전제가 있었다.

2026년의 세 번째 단계가 결정적으로 다른 지점은 호출 주체가 사람의 손이 아니라 AI 에이전트라는 점이다. Headless software는 단순히 프런트를 떼어내는 게 아니다. 호출하는 쪽 자체가 비결정적이고 자연어 기반인 LLM이라는 새로운 클라이언트 종이 탄생한 사건이다. 이 단계에서는 API 설계 원칙·문서화 방식·에러 메시지·트랜잭션 모델 모두가 LLM의 사용 패턴에 맞춰 다시 검토되어야 한다. CMS와 commerce에서 익숙해진 헤드리스라는 단어가 같은 글자를 유지하면서 의미는 한 단계 더 무겁게 변한 셈이다.

AI 에이전트가 가져온 본질 변화 - 인간 UI와 에이전트 UI의 분리

본질 변화는 단순하다. 인터페이스의 사용자가 둘로 분리되었다. 인간 사용자와 에이전트 사용자. 인간은 시각적·맥락적·감정적 정보를 동시에 처리하면서 클릭한다. 에이전트는 텍스트와 스키마만으로 의사 결정한다. 같은 결제 기능이라도 인간에게 보여줘야 할 것과 에이전트에게 노출해야 할 것이 다르다는 의미다.

실무적으로 가장 큰 함의는 "UI는 사용자 인터페이스가 아니다"라는 사실이다. 정확히 말하면 GUI는 인간 사용자 인터페이스이고, 에이전트 사용자 인터페이스(AUI)는 API·도구 스키마·자연어 명세의 묶음이다. 같은 SaaS가 두 종류의 사용자 인터페이스를 함께 운영해야 한다는 의미고, 그 둘은 동일한 비즈니스 로직을 공유하되 표현 방식이 완전히 다르다. 잘 설계된 헤드리스 소프트웨어는 GUI를 만들지 않는 게 아니라, GUI를 비즈니스 로직과 분리된 외부 클라이언트의 하나로 본다.

이 관점이 무서운 이유는, 에이전트가 더 똑똑해질수록 GUI의 가치가 줄어드는 게 아니라 GUI의 사용자가 점차 "결정해야 하는 순간"으로 좁혀진다는 데 있다. 평소 운영은 에이전트가 자동으로 처리하고, 사람은 예외·승인·예산·전략 같은 결정 노드에서만 화면을 본다. 이 구조에서는 GUI를 줄이는 게 아니라 GUI의 의미를 바꿔야 한다. "조회와 입력" 도구에서 "결정과 승인" 도구로의 재정의다.

헤드리스 소프트웨어의 5가지 특징 - 정의를 정확히 한다

이쯤에서 헤드리스 소프트웨어가 무엇인지 정의를 정확히 잡아 둔다. 모호한 채로 두면 마케팅 용어로 휘발될 위험이 크다. 본인이 정리한 5가지 특징은 다음과 같다.

  1. API가 1차 인터페이스다. 어떤 기능도 우선 API로 노출되고, 그 위에 GUI가 얹힌다. 거꾸로가 아니다. 신규 기능 출시 시점도 GUI보다 API가 먼저거나 동시다.
  2. GUI는 부수적이거나 없다. GUI 없이도 서비스가 완결적으로 동작해야 한다. 본질적 워크플로 중 "GUI에서만 가능한 작업"이 존재하면 헤드리스가 아니다.
  3. 자연어 인터페이스를 LLM 경유로 제공한다. 사용자가 자연어로 명령하면 LLM이 그것을 API 호출 시퀀스로 번역한다. 자연어가 또 하나의 인터페이스 채널이라는 의미다.
  4. 도구로서의 일관성을 유지한다. 명명 규칙·에러 코드·페이지네이션·인증이 모든 엔드포인트에서 동일하다. LLM의 학습/추론 비용을 낮추는 게 목표다.
  5. 에이전트 호출 가능성을 1급 시민으로 둔다. MCP 서버나 Function Calling 명세가 별도 작업이 아니라 빌드 파이프라인의 기본 산출물이다.

이 5가지 중 3개 이상을 충족하면 일단 헤드리스 후보로 본다. 5개 전부를 충족하는 SaaS는 2026년 5월 현재 손에 꼽는다. 그러나 후보군이 가파르게 늘고 있고, 향후 18개월 안에 주요 카테고리마다 헤드리스 1위 사업자가 정해질 가능성이 높다. 헤드리스 전환에 늦은 사업자는 그 카테고리의 기본값 자리에서 밀려난다.

실제 사례 - 헤드리스로 가는 5가지 영역

이론은 충분하다. 실제로 헤드리스화가 빠르게 진행되는 5개 영역을 본다.

1) 결제: Stripe API → Stripe Agent Toolkit

Stripe는 본래 API 우선 회사다. 그런데 2025년 후반 발표된 Stripe Agent Toolkit은 한 단계 더 나갔다. LangChain·OpenAI·Anthropic SDK에서 곧바로 호출 가능한 에이전트 친화 함수들을 묶어 배포한 것이다. 결제·구독·환불·인보이스 발급이 자연어 명령 한 줄에서 시작해 트랜잭션 완결까지 도달할 수 있다. 결제는 헤드리스화의 가장 명확한 모범 사례다.

2) 마케팅 자동화: HubSpot → AI 마케팅 에이전트

HubSpot은 캠페인 빌더·이메일 에디터 같은 GUI 도구로 성장했다. 2026년 들어 발표된 Breeze 계열 AI 에이전트는 GUI 없이도 캠페인 기획부터 발송, A/B 테스트, 리포팅까지 자동화한다. GUI는 여전히 있지만, 일부 고객사에서는 GUI 사용 시간이 절반 이하로 줄었다는 보고가 들린다. 마케팅 자동화는 본질적으로 규칙 기반이라 LLM 위임이 효율적인 영역이다.

3) 회의 관리: Calendly → Cal.com API

Cal.com은 오픈소스 + API 우선 모델로 Calendly를 대체하기 위해 등장했다. 회의 일정 조율은 본래 사람이 화면에서 시간을 클릭해 잡는 작업이었으나, 에이전트가 캘린더 충돌을 비교하고 후보를 자동 제안해 확정까지 처리하는 구조로 빠르게 바뀌고 있다. Cal.com이 노출하는 booking API는 LLM이 이해하기 쉬운 시맨틱으로 정돈되어 있어 헤드리스 호환성이 좋다.

4) 분석: Mixpanel → AI 인사이트 직통

Mixpanel·Amplitude 같은 제품 분석 도구는 본래 대시보드 중심이었다. 2025년부터 자연어 질의가 결합되면서 사용자는 "지난주 가입 전환율을 채널별로 보여줘"라는 문장을 입력하기만 한다. 차트는 부수적으로 생성되며, 더 흥미로운 변화는 에이전트가 직접 분석 도구의 API를 호출해 인사이트를 보고서 형태로 정리해 다른 도구로 전달하는 흐름이다. 분석 대시보드는 인간이 보는 게 아니라 에이전트가 읽는 시대로 이동 중이다.

5) 콘텐츠 관리: Contentful, Sanity

헤드리스 CMS는 이미 정착했지만, 2026년의 변화는 콘텐츠 생성 자체가 에이전트 손에 넘어간다는 점이다. 에디터가 키보드로 타이핑하는 게 아니라, 에이전트가 외부 데이터를 모아 초안을 만들고 CMS API로 게시한다. 사람은 검수와 승인을 담당한다. Contentful의 새 AI 액션 기능은 이 흐름의 빠른 적응 사례다.

개발자가 알아야 할 4가지 - API 우선 설계 방법

헤드리스 소프트웨어를 설계해야 하는 개발자에게 가장 자주 받는 질문은 "어디부터 시작해야 하느냐"이다. 본인 답은 4가지 영역이다.

  • 자기설명적 스키마: OpenAPI 3.1·JSON Schema·gRPC reflection 중 하나로 모든 엔드포인트가 자기 자신을 설명할 수 있어야 한다. LLM은 사람보다 명세를 더 자주, 더 많이 읽는다. description 필드 한 줄이 모델 호출 정확도를 5~10% 끌어올린다.
  • 일관된 도메인 명명: create_invoice, refund_payment, cancel_subscription처럼 동사_명사 패턴을 모든 엔드포인트에 통일한다. LLM은 명명에서 의미를 추정하므로 일관성은 토큰 비용과 직결된다.
  • 멱등성과 재시도 안전성: LLM은 같은 호출을 반복하기 쉽다. Idempotency-Key 헤더·재시도 가이드라인·트랜잭션 롤백을 1순위로 설계한다. Stripe가 십 년 전부터 멱등키를 강조해 온 이유가 이 시대에 와서야 보편적 필수 조건이 되었다.
  • 에러 메시지의 행동지향성: 400 Bad Request로 끝내지 말고 "next_action": "retry_with_field_x" 같은 행동 단서를 포함한다. LLM은 자연어로 에러를 해석하므로 사람에게 친절한 에러는 모델에게도 친절하다.

네 영역 모두 새로운 기술이 아니다. 다만 그동안 "있으면 좋은" 항목이었던 것이 헤드리스 시대에는 "없으면 못 쓰는" 항목으로 격상되었다. 신규 API 설계 시 이 4가지를 인수 조건에 추가하는 것이 헤드리스 전환의 첫 걸음이다.

MCP·Function Calling 표준의 의미 - 에이전트 호환성이 곧 시장 점유율

헤드리스 소프트웨어가 산업으로 자리잡으려면 표준이 필요하다. 2024년 말 Anthropic이 발표한 MCP(Model Context Protocol)와 2023년 OpenAI가 보편화한 Function Calling이 그 두 축이다. MCP는 도구·리소스·프롬프트를 모델에 노출하는 공통 프로토콜이고, Function Calling은 모델 출력에서 함수 호출을 안전하게 추출하는 메커니즘이다. 둘은 경쟁 관계가 아니라 보완 관계로 굳어지는 중이다.

중요한 사실은, 2026년 현재 어떤 SaaS의 시장 점유율 추세를 봐도 MCP 서버나 Function Calling 호환 SDK를 빨리 제공한 쪽이 호출량·신규 통합·파트너십 모든 지표에서 앞선다는 점이다. 즉 에이전트 호환성이 곧 시장 점유율이다. 이는 과거 모바일 SDK 제공 여부가 점유율을 갈랐던 흐름과 정확히 같은 구조다. 다음 12개월 동안 MCP 서버 부재는 곧 채택 누락으로 이어질 것이다.

한국 SaaS 사업자에게 즉시 의미가 있는 함의는 두 가지다. 첫째, 외산 도구가 한국 워크플로에 침투하기 전에 자체 MCP 서버를 공개해야 한다. 둘째, 기존 OpenAPI 명세를 MCP 매니페스트로 자동 변환하는 빌드 파이프라인을 두면 운용 비용을 최소화할 수 있다. 둘 다 단순한 기술 결정이 아니라 시장 결정이다.

GUI는 사라지지 않는다 - 하이브리드 미래

이쯤에서 균형을 잡아야 한다. GUI는 사라지지 않는다. 다만 위치가 바뀐다. 본인 예측은 다음 세 가지 영역에서 GUI는 오히려 더 정교해진다.

  • 결정 인터페이스: 예산 승인, 인사 결정, 법적 서명, 대외 공시. 사람이 책임을 져야 하는 모든 액션은 GUI에서 명시적으로 확인된다.
  • 탐색 인터페이스: 디자인 도구, 데이터 시각화, 지리 정보. 시각적 패턴 인식이 결과 품질에 결정적인 영역은 사람의 눈을 거친다.
  • 협업 인터페이스: 화이트보드, 문서 공동편집, 코드 리뷰. 여러 사람과 에이전트가 같은 컨텍스트를 보면서 합의에 이르는 도구다.

이 세 영역에서는 GUI가 더 깊어지고, 그 외 운영 영역에서는 GUI가 얇아진다. 결과적으로 평균 SaaS의 GUI는 절반 이하로 작아지지만, 핵심 GUI는 두 배 이상 정교해진다. "GUI의 종말"이라는 표현은 정확하지 않고, "GUI의 재배치"가 더 적절하다. GUI가 자동화되지 못한 영역에만 잔존한다는 의미가 아니라, GUI 본연의 가치인 결정·탐색·협업이 강화된다는 의미다.

비즈니스 모델 변화 - API 호출당 과금이 부상한다

헤드리스 소프트웨어는 가격 모델까지 바꾼다. 전통 SaaS의 시트 기반 과금은 사람 사용자가 GUI를 본다는 가정 위에 만들어졌다. 그런데 호출자가 에이전트라면 시트 개념이 흐려진다. 한 에이전트가 100명 분의 일을 할 수도, 한 사람이 50개 에이전트를 운용할 수도 있다. 이미 일부 SaaS는 시트 + API 호출 + 토큰 사용량을 결합한 하이브리드 과금으로 이동했다.

본인 예측은 다음 두 가지 모델이 헤드리스 시대 표준으로 자리잡는다는 것이다.

  • 호출당 변동 과금: API 호출량과 사용한 데이터 양에 비례한 단가. AWS·Stripe가 오래 사용해 온 모델이 SaaS 전반으로 확산.
  • 결과 기반 과금: 처리된 거래액 1%, 완료된 작업 1건당 X원처럼 결과량에 비례하는 모델. 마케팅·세일즈·운영 자동화에서 빠르게 등장.

두 모델은 사용자의 가치 인식과 가깝다는 공통점이 있다. 시트 과금은 "기능을 살 권리" 가격이었지만, 헤드리스 과금은 "실행된 가치"의 가격이다. 이 전환은 단순 가격 정책 변경이 아니라 영업·재무·법무까지 모두 영향을 미치는 구조적 사건이다.

한국 IT 기업의 헤드리스 전환 - 네이버, 카카오, 토스의 현 위치

한국 시장으로 시선을 돌려보면 헤드리스 전환은 이미 시작되었으나 속도는 분야별로 큰 차이가 있다.

네이버 클라우드는 HyperCLOVA X 기반 에이전트 플랫폼을 통해 내부 도구의 API 우선 설계를 강화하고 있다. 검색·지도·번역·문서 등 핵심 자산이 API로 노출되어 있어 헤드리스 후보가 풍부하다. 다만 MCP 서버 공식 지원은 2026년 5월 현재 부분적이며, 외부 에이전트가 곧바로 사용하기에는 통합 비용이 남아 있다.

카카오는 카카오 i 계열의 자연어 인터페이스 기술을 가지고 있고, 카카오톡·맵·페이의 API 자체는 안정적이다. 그러나 카카오 생태계의 강점은 GUI 트래픽이라서 헤드리스 전환은 결제·알림 영역에서 먼저 발생하고 채팅 영역은 마지막에 변화할 가능성이 높다. 카카오 i 챗봇 빌더가 MCP 호환 어댑터를 제공한다면 빠르게 헤드리스 진영으로 합류할 수 있다.

토스는 한국에서 가장 적극적으로 API 우선 설계를 추구해 온 사업자다. 토스페이먼츠와 토스인증의 API 품질은 글로벌 수준에 근접해 있고, 자연어 명령 지원 실험도 진행 중이다. 본인 평가로는 한국 SaaS·핀테크 중 헤드리스 전환에 가장 가깝게 와 있는 회사가 토스이며, 그다음이 채널톡·뤼이드·센드버드 같은 글로벌 지향 SaaS다.

한국 사업자에게 공통으로 권하는 세 가지가 있다. 첫째 자사 핵심 워크플로의 MCP 서버를 빠르게 공개하라. 둘째 OpenAPI 명세의 description 품질을 정성적으로 점검하라. 셋째 에이전트가 사용할 sandbox·테스트 키를 무료로 제공하라. 이 세 가지를 갖춘 사업자가 헤드리스 시장의 기본값이 된다.

위험과 한계 - 디버깅·트러스트·UX 통제 상실

헤드리스 소프트웨어가 만능은 아니다. 본인이 운영 경험에서 본 주요 위험은 다음 다섯이다.

  • 디버깅 난도 상승: 사용자가 GUI에서 직접 조작했을 때보다 에이전트가 호출한 시퀀스를 추적하기 어렵다. trace ID·prompt log·tool call log를 동시에 보지 않으면 원인 파악이 불가능에 가깝다.
  • 트러스트와 책임: 잘못된 결제·잘못된 이메일 발송이 발생했을 때 책임이 사용자·에이전트 운영자·SaaS 사업자 중 누구에게 있는지가 모호하다. 약관·감사 로그·승인 워크플로가 필수다.
  • UX 통제 상실: 에이전트가 다른 회사의 화면을 그리기 시작하면 브랜드 경험이 균질화된다. "내 제품 같지 않다"는 사용자 피드백이 빈번해진다. 이 경우 일관된 음성·문체 가이드를 자연어 명세에 포함하는 것이 부분적 해결책이다.
  • 비용 폭증 가능성: 한 사용자가 한 번의 자연어 명령으로 수천 호출을 트리거할 수 있다. rate limit·budget cap·cost alert가 운영 도구의 1순위 항목이 된다.
  • 보안 표면 확장: 에이전트의 토큰이 유출되면 사람보다 빠르게 막대한 작업을 자동 수행할 수 있다. scope 최소화, 단기 토큰, 재인증 트리거가 표준이 되어야 한다.

다섯 위험 모두 "결국 운영의 문제"라는 공통점이 있다. 헤드리스 전환은 코드 변경보다 운영 체계 변경의 비중이 더 크다는 점을 기억해야 한다. 신규 기술 도입 시 흔히 발생하는 함정으로, 만든 것은 빨라도 운영이 따라가지 못해 사업 전체가 흔들리는 시나리오를 미리 막아야 한다.

결론과 즉시 적용 가능한 3가지

본문 핵심을 한 문장으로 정리한다. 2026년 소프트웨어 산업의 분기선은 GUI 우선이냐 API 우선이냐가 아니라, 에이전트가 호출할 수 있느냐 없느냐다. 헤드리스 전환은 모든 SaaS에 동일한 속도로 일어나지 않지만, 결제·마케팅·일정·분석·콘텐츠 다섯 영역에서 먼저 정착하고 그 뒤를 협업·디자인·법률 영역이 따른다. GUI는 사라지지 않으나 결정·탐색·협업이라는 본연의 가치 쪽으로 재배치된다.

즉시 적용 가능한 행동 세 가지를 정리한다.

  1. 자사 API의 description 품질을 점검하라. OpenAPI 명세의 모든 endpoint에 사람이 읽을 수 있는 한 문장 설명이 있는지, 그 문장이 LLM에게도 명확한지 본다. 이것 하나만 정비해도 외부 에이전트의 채택률이 즉시 오른다.
  2. 핵심 워크플로 1개에 대해 MCP 서버 또는 Function Calling 스키마 시제품을 만들라. 전체를 한 번에 헤드리스화하지 않고, 가장 자주 호출되는 워크플로 하나를 골라 시제품을 구축한다. 1주일 안에 결과를 본다.
  3. 가격 모델에 호출 기반 옵션을 추가하라. 기존 시트 과금은 유지하되, 호출 또는 결과 기반 옵션을 병행 출시해 헤드리스 사용자가 자연스럽게 정착할 수 있는 결제 경로를 만든다.
