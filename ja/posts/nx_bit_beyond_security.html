実行禁止ビットはほとんどいつも攻撃と防御の文脈で紹介される。バッファに機械語を押し込んでもその場では実行されないという話、データ領域とコード領域を分ける線という話だ。その説明が誤っているわけではない。ただ、そのビットがページテーブルで実際に規定している範囲はもっと広く、その広さは攻撃者が一人も出てこない場面でこそはっきり現れる。

きっかけ - 起動しなかったハイパーバイザを直したのはセキュリティのビットだった

きっかけとなった記事は purplesyringa のブログに Sonya という書き手が寄せた客員記事である。対象は postmarketOS 向けのベアメタル ARM64 ハイパーバイザだった。症状は一行で言える。特定のシステムレジスタの読み取りを横取りする機能を有効にすると、電話が止まってリセットされる。同じコードが QEMU では問題なく回る。

記事の半分は仮説が一つずつ脱落していく音で埋まっている。例外ハンドラがレジスタを壊しているという仮説は、QEMU での単一ステップ追跡で崩れた。命令キャッシュとデータキャッシュの一貫性の問題だという仮説は、ソート処理をビルド時へ移すことで片付いた。ハードウェアが仕様の外で動いているという仮説をつかまえようと例外ハンドラを追加したが、何一つ引っかからなかった。

突破口はバイナリの比較から出た。動く版と死ぬ版の違いが意味の上ではまったく同じ二つの形だったのである。行き先が命令の中に埋め込まれている静的な直接分岐は生き残り、行き先をレジスタから読む間接分岐は死んだ。この対比が指す先は一つしかない。分岐予測である。

予測器はアドレス 0 へ誤って予測していた。そしてハイパーバイザの一対一マッピングでは、その位置にロックされた bootrom が置かれていた。著者が選んだ解法はその領域に実行禁止を付けることで、その瞬間に電話が初めて起動した。記事の最後の一文がこの案件の性格を要約している。実行不可のマッピングを作る道はどのみち通す必要があったので、ペイロードを除く全部を実行不可でマッピングし、その結果ハイパーバイザに多層防御が少し備わった、というのだ。セキュリティは目的ではなく副産物として来た。

実行権限とは何か - ページ一つに付くビット

権限はページ単位で付く

仮想メモリにおいてアドレス変換の最小単位はページである。変換表の各エントリには、そのページがどの物理フレームに対応するかだけでなく、そのページをどう扱ってよいかが併せて書かれる。読んでよいか、書いてよいか、そしてそこに入っているバイトを命令としてフェッチしてよいかである。

アプリケーション側でこの三つに触れる窓口が mmap と mprotect の prot 引数だ。man page は各値を一文ずつで定義している。PROT_READ はメモリを読めること、PROT_WRITE は変更できること、PROT_EXEC は実行できること、PROT_NONE はまったくアクセスできないことである。mprotect の原型は int mprotect(void *addr, size_t size, int prot); であり、開始アドレスはページ境界に合っている必要がある。

フラグman page の定義実務で意味するもの
PROT_READメモリを読めるデータとしてアクセス可能。ロード命令が通る
PROT_WRITEメモリを変更できるストア命令が通る。i386 では読み取りを含意する
PROT_EXECメモリを実行できる命令フェッチが許される。ハードウェアが軸を分けてくれるときにだけ意味を持つ
PROT_NONEメモリにまったくアクセスできないどんなアクセスもフォルトになる。境界ページを作るのに使われる

実行の軸がないハードウェアで起きること

ここで man page が慎重に付けている但し書きが効いてくる。PROT_EXEC が PROT_READ と異なる効果を持つかどうかは、プロセッサのアーキテクチャとカーネルのバージョンとプロセスの状態次第だという一文である。同じ文書は、READ_IMPLIES_EXEC のパーソナリティが掛かったプロセスでは PROT_READ を指定するだけで PROT_EXEC が暗黙に付く、とも書いている。

つまり API にフラグが三つあるからといって、ハードウェアにも軸が三つあるわけではない。API はずっと三つを受け取ってきたが、そのうち実行の軸はハードウェアがそれを別枠で表現できるようになって初めて実際の意味を持つようになった。それまで実行の軸は読み取りの軸に乗っていた。

その以前 - 読めるなら実行できた

なぜそうだったのかは席の問題として説明できる。32 ビット x86 の伝統的なページテーブルエントリは 32 ビットである。アドレスと各種の状態ビットでその幅はすでに埋まっており、実行権限のために新しく割く席がなかった。実行禁止ビットがページテーブルに入ってきたのは、エントリの幅が広がったあとのことだ。

この事情は Linux カーネルのソースにそのまま残っている。x86 側のページ型ヘッダは実行禁止ビットを 63 番として確保し、その横に cpuid の検査を通ったあとにだけ有効だというコメントを添えている。そして実際のマスクは、64 ビットまたは PAE のときだけそのビット値を使い、それ以外の構成では ゼロとして定義される。ビットのないハードウェアではマスクが何も立てない値になるわけだ。

だから実行禁止ビットの導入は、保護機能が一つ増えた出来事というより変換表が表現できる状態が一つ増えた出来事である。それ以前には、読めるページと実行できるページを区別して書き留める方法そのものがなかった。データとコードの区別はプログラムの取り決めであって、ハードウェアが強制する性質ではなかった。

この違いが以降のすべての話の根になる。状態が表現できるようになると、その表現はもともと意図した用途一つにとどまらない。実行禁止は攻撃防御のために導入されたが、いったん変換表に席を占めるや、プロセッサがそのページをどう扱ってよいかに関する一般的な規定として使われはじめた。

W^X - 二つの権限を同じ瞬間に与えない

実行の軸ができるとすぐに続いた原則が W^X である。どのページも書き込み可能と実行可能を同時に持たない、という規則だ。実行禁止ビット自体はこの原則を強制しない。ビットは状態を書けるようにするだけで、組み合わせを禁じるのはその上に乗った方針である。だから W^X をどの層でどれだけ強く掛けるかはシステムごとに異なる。

もっとも強く掛けているのが OpenBSD だ。man page は書き込みと実行を同時に要求するマッピングが許されないと明言し、例外の通路を二重に絞っている。ファイルシステムが wxallowed でマウントされ、かつプロセスがリンク時に wxneeded でタグ付けされている必要がある。違反は ENOTSUP として返り、どこで引っかかったかを見るための kern.wxabort という取っ手まで文書に書かれている。

Apple シリコンも強い側である。Apple の開発者文書は、メモリ保護が Hardened Runtime を採用しているかどうかに関係なくすべてのアプリに掛かると書いている。Hardened Runtime を採用したアプリにだけ掛かっていた Intel ベースの Mac と対比される。その保護が有効なときの規則も一文で書かれている。スレッドはある領域に書き込みながら同時にその領域の命令を実行することはできない。

Linux は別の場所を突く。mmap と mprotect の文書には、書き込みと実行の組み合わせを拒否するという記述がない。代わりに別の層に取っ手がある。ファイルシステムを no-exec でマウントしておけば、そのファイルを PROT_EXEC でマッピングしようとする要求そのものが EPERM で拒否されると mmap の man page が書いている。後述するメモリファイルの実行禁止封印も同じ系統だ。

きっかけの記事が実際に主張していること - 投機的命令フェッチ

同じ意味なのに片方だけが死んだ

デバッグの転換点となった対比を形に移すとこうなる。

    bl   get_ctr_el0     // 静的な直接分岐 — 行き先が命令の中に埋め込まれている
    blr  x1              // 間接分岐 — 行き先を実行時にレジスタから読む

二行は同じ関数を呼ぶ。違うのは行き先がいつ決まるかだけである。直接分岐は命令をフェッチする時点で行き先がすでに決まっている。間接分岐はレジスタの値が用意される前にプロセッサが行き先を予測する。予測が外れれば結果は後で捨てられるが、その経路の命令はすでにフェッチされたあとだ。

Device と書いても塞がらないもの

ARM ではメモリマップ入出力の領域を Normal ではなく Device メモリとして表示する。ここでよくある思い違いが生まれる。Device と書いておけばプロセッサがその領域をむやみに触らない、という理解だ。きっかけの記事が引用した ARM 文書の一文は、その理解をちょうど一段だけ狭める。見落としやすい微妙な区別があり、ある領域を Device として表示することは投機的なデータアクセスだけを防ぎ、投機的な命令アクセスを防ぐにはその領域を実行不可として表示しなければならない、というものである。

記事の状況はまさにその隙間に落ちていた。一対一マッピングだったのでアドレス 0 がロックされた bootrom であり、誤予測された間接分岐がそこから命令をフェッチしようとした。データの軸は Device 表示ですでに閉じていたが、命令の軸は開いたままだった。だから解法が実行禁止だったのである。減らしたのは攻撃面ではなくプロセッサが予測だけで触れうる範囲だった。

ここがきっかけの記事の題が指している地点だ。実行禁止ビットは防御装置である前に投機動作を規定するアーキテクチャ属性として働く。データ実行防止をスタックオーバーフローの対策としてだけ読んでいると、同じビットが捕まえてくれるハードウェア側の故障をまるごと取り逃がすことになる。

カーネルソースにすでに埋まっているもの - デバイスマッピングの実行禁止

汎用のオペレーティングシステムはその結論をすでに既定値として敷いている。Linux の arm64 ページ保護ヘッダを見れば答えが一目で入ってくる。

#define PROT_DEFAULT		(PTE_TYPE_PAGE | PTE_MAYBE_NG | PTE_MAYBE_SHARED | PTE_AF)

#define PROT_DEVICE_nGnRnE	(PROT_DEFAULT | PTE_PXN | PTE_UXN | PTE_WRITE | PTE_ATTRINDX(MT_DEVICE_nGnRnE))
#define PROT_DEVICE_nGnRE	(PROT_DEFAULT | PTE_PXN | PTE_UXN | PTE_WRITE | PTE_ATTRINDX(MT_DEVICE_nGnRE))
#define PROT_NORMAL		(PROT_DEFAULT | PTE_PXN | PTE_UXN | PTE_WRITE | PTE_ATTRINDX(MT_NORMAL))

基本属性である PROT_DEFAULT には実行禁止ビットが入っていない。その上に PTE_PXN と PTE_UXN を両方とも載せたものがデバイスマッピングであり、カーネルが使う通常メモリのマッピングも同じである。そして各マクロの末尾にはメモリタイプを指定する項目が別に付く。実行の軸とメモリタイプの軸が別々に埋められるという事実が、コード一行の中にそのまま現れている。

ここから二つが見える。第一に、arm64 の実行禁止ビットは一つではなく二つだ。権限レベルごとに分かれているので、カーネルは実行できないがユーザ空間は実行できるページのような状態を表現できる。第二に、実行可能なカーネルコードの領域はそのビットを外して作られる。既定が禁止で、許可が例外である。順序がこうなっている点が重要だ。

きっかけの記事の開発者が手で実装しなければならなかった性質を、汎用のカーネルはすでに既定値として敷いていたわけである。ベアメタルでページテーブルを直接書く側はその既定値を受け継がない。オペレーティングシステムが代わりに守ってくれていた慣習が消えた場所で、アーキテクチャ文書の微妙な区別がそのまま起動失敗として現れた。

フォルトを信号として使う技法 - 同じ機械、違うビット

ページ権限に違反するとフォルトが起き、フォルトはカーネルに入る。ところがそのフォルトを誤りではなく通知として使う系統が別にある。保護装置を観測装置として使い回すのだ。Linux でその系統の代表が userfaultfd である。

man page はこれを、ページフォルトの処理をユーザ空間のアプリケーションへ委譲する仕組みとして定義している。文書が挙げる用途は、チェックポイントと復元の仕組みにおける遅延復元、そして仮想マシンやコンテナをホスト間で移す際にほぼ途切れずに実行を続けるためのポストコピーマイグレーションである。動作の仕方も明示されている。登録された領域でフォルトが起きるとフォルトを起こしたスレッドが眠り、イベントがファイルディスクリプタを通じて上がってきて、ユーザ空間がそれを読んで処理する。

登録モードは三つだ。存在しないページにアクセスしたとき、書き込み保護されたページに書いたとき、そしてページはあるがページテーブルエントリがないとき。文書はこの仕組みが SIGSEGV シグナルに頼っていた従来のユーザ空間ページング技法の代替だと書いている。

ここでこの記事の軸に関わる重要な事実が一つ出てくる。その一覧に実行の軸がない。フォルトを信号として使う系統は読み取りと書き込みの軸の上で回る。実行権限は通知を作り出す側よりも、そもそもそのアクセスが起きないように塞ぐ側で使われる。きっかけの記事の事例もまさにその方向だ。フォルトを受けて処理したのではなく、フォルトが起きる状況そのものを消した。

セキュリティ機能が別の仕事に使われるようになる構造は、こうして二筋に分かれる。一つはフォルトというイベントを借りる側であり、もう一つは権限ビットが規定するハードウェアの振る舞いの範囲を借りる側である。実行禁止ビットは後者に属する。

JIT は W^X をどう守るのか

実行コードを実行中に作り出すプログラムは W^X と正面から衝突する。機械語を書いたあとで実行しなければならないのに、原則はその二つを同じ瞬間に持つことを禁じる。実行時コンパイルという方式そのものが何を狙っているかは TypeScript を LLVM 機械語へ直接コンパイルする Perry を扱った記事に整理してあるので、ここでは権限をどう扱うかだけを見る。

権限をひっくり返す方式

/* 書き込み窓口を開き、機械語を詰め、実行可能に変える */
void *p = mmap(NULL, len, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
if (p == MAP_FAILED) return -1;

emit_code(p, len);                       /* ここまでこのページは実行不可 */

if (mprotect(p, len, PROT_READ | PROT_EXEC) != 0) return -1;
/* この時点から同じページは書き込み不可でありながら実行可能 */

もっとも単純な形だ。無名マッピングを読み取りと書き込みで開き、機械語を詰め、mprotect で読み取りと実行の組み合わせにひっくり返す。ひっくり返す前は実行できず、返したあとは書けないので、どの瞬間にも書き込みと実行が同じページに並び立つことはない。

マッピングを二つに分ける方式

/* 同じ物理ページに権限の異なる二つの仮想アドレスを付ける */
int fd = memfd_create("jit", MFD_CLOEXEC);
if (fd == -1) return -1;
ftruncate(fd, len);

void *rw = mmap(NULL, len, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
void *rx = mmap(NULL, len, PROT_READ | PROT_EXEC,  MAP_SHARED, fd, 0);

emit_code(rw, len);   /* 書き込みは rw からだけ、実行は rx からだけ */

同じファイルディスクリプタを共有マッピングで二度載せる。mmap の man page は、共有マッピングへの更新が同じ領域をマッピングした他の側にも見えると書いている。だから rw 側で書いたバイトは rx 側で命令として読まれる。物理ページは一つのままで、仮想アドレスだけが二つになり、権限は互いに異なる。

切り替えのシステムコールが消える代わりに別のものを背負う。アドレスを二組持ち歩く必要があり、相対アドレスで計算される分岐の行き先がどちらの窓口を基準にしたものかという問題が繰り返し戻ってくる。そして後述する実行禁止の封印が効いていれば、この方式自体が成り立たない。

Apple シリコン - スレッド単位でひっくり返す

Apple は三つ目の筋を作った。JIT 用の領域は mmap に MAP_JIT フラグを渡して作る。Hardened Runtime を採用したアプリなら com.apple.security.cs.allow-jit の権利設定があって初めてそのフラグ付きで mmap を呼べるようになり、採用していないアプリは権利設定なしでもそのフラグを使えると文書が書いている。ただし Hardened Runtime とその権利設定を併せて使う組み合わせでは、MAP_JIT の領域を一つだけ作れる。

切り替えは pthread_jit_write_protect_np で行う。加えて文書は新しい経路を案内している。com.apple.security.cs.jit-write-allowlist の権利設定を付けると pthread_jit_write_with_callback_np を通じて JIT 領域へ書くことになり、その権利設定が付いたアプリは pthread_jit_write_protect_np をもう呼べない。動的に読み込まれるライブラリのために一覧を実行中に更新する別の権利設定もある。

構造上もっとも興味深いのは切り替えの範囲だ。文書は、コールバック方式がその領域を書き込み可能で実行不可にするが現在のスレッドについてだけそうすると書き、戻すときも現在のスレッドについて実行可能で書き込み不可にすると書いている。前節の mprotect はそうではない。あれはアドレス空間のマッピングを変えるので、切り替えが開いている間は同じプロセスのすべてのスレッドがそのページを書き込み可能な状態として見る。スレッド単位の切り替えはその窓を一つのスレッドまで狭める。

そして権限だけ扱えば終わりではない。Apple の文書は、更新したばかりのページの命令を実行する前に必ず sys_icache_invalidate を呼べと釘を刺している。Apple シリコンでは命令キャッシュがデータキャッシュと一貫しておらず、無効化せずに実行すると予期しない結果になりうるからだ。同じ関数を Intel ベースの Mac で呼んでも安全で、そちらでは何もしないと付け加えている。

この箇所がきっかけの記事と重なる。あの記事で脱落した仮説の一つも命令キャッシュとデータキャッシュの一貫性だった。機械語を自分で作り出す側は権限とキャッシュを一緒に扱わなければならない。二つのうち一方だけ合わせておくと、症状はどちらでも同じ再現不能な停止として現れる。

代価の正体 - システムコール、ページ単位、キャッシュ

W^X を守る値段はいくつかに分かれる。どの方式を選んでも、このうちいくつかは必ず払う。

  • システムコール — 切り替え方式は機械語の束を一つ作るたびにカーネルへ入って出てくる。コード生成の単位が細かく割れているほどこの費用が頻繁に発生する。
  • ページ単位 — 権限はバイトではなくページまるごとで変わる。小さなコード片をいくつも一つのページにまとめておくと、そのうち一つを直すために開いた瞬間に残り全部が一緒に書き込み可能になる。
  • アドレス空間全体 — mprotect はプロセスのマッピングを変える。マルチスレッドのプログラムでは、切り替えが開いている区間はすべてのスレッドに対して開いている区間である。
  • 仮想アドレスの二重化 — 二重マッピングはシステムコールを減らす代わりにアドレスを二つにする。コード内のアドレス計算がどちら基準なのかを一貫して管理しなければならない。
  • 命令キャッシュ — 書いたばかりのバイトを命令として実行する前にキャッシュを片付ける段階が、プラットフォームによっては必須である。
  • 方針の衝突 — 堅牢化の取っ手が有効だと、上の方式のいくつかはそもそも成り立たない。次節の実行禁止の封印がその例だ。

ここでよく食い違う感覚が一つある。実行禁止ビット自体を立てたり下ろしたりするのに掛かる値段はほとんどない、という点だ。値段が掛かるのはその状態を変える作業であり、変えなければならない理由はプログラムが実行中にコードを作り出すからである。静的にコンパイルされたコードだけが回るプロセスでは、この費用は事実上ゼロだ。

アーキテクチャごとに違う点

x86 側の定義は先に触れたとおりである。形を見れば条件がどこに掛かっているかがはっきりする。

#define _PAGE_BIT_NX		63	/* No execute: only valid after cpuid check */

#if defined(CONFIG_X86_64) || defined(CONFIG_X86_PAE)
#define _PAGE_NX	(_AT(pteval_t, 1) << _PAGE_BIT_NX)
#else
#define _PAGE_NX	(_AT(pteval_t, 0))
#endif

ビット番号は一つに固定されているが、そのビットが実際に存在するかどうかは構成次第である。64 ビットまたは PAE の場合にだけマスクが立ち、それ以外ではゼロだ。コメントの但し書きも同じ話をしている。cpuid で問い合わせたあとにだけ有効だということは、この機能が最初からあったのではなく後から追加された選択肢だったことを意味する。

arm64 は構造が違う。実行禁止が権限レベルごとに二つあり、そこにメモリタイプという別の軸が並んで付く。前節のマクロで二つの軸が一行の中に一緒に埋められていたのがその証拠である。

アーキテクチャ実行禁止の表現Linux ソースでの名前一緒に見るべき軸
x86-64 および PAEページテーブルエントリの 63 番ビット一つ_PAGE_BIT_NX と _PAGE_NXなし。実行の軸は単一である
32 ビット x86 の非 PAE該当するビットが存在しない_PAGE_NX がゼロとして定義される読み取りの軸が実行の軸を兼ねる
arm64 の特権レベル特権レベルでの実行を禁じるビットPTE_PXNメモリタイプの軸が別にある
arm64 の非特権レベル非特権レベルでの実行を禁じるビットPTE_UXNメモリタイプの軸が別にある
arm64 のデバイス領域デバイスマッピングに二つのビットが既定で入るPROT_DEVICE_nGnRnE と PROT_DEVICE_nGnREDevice 表示はデータの軸だけを閉じる

表の最後の行が、きっかけの記事がぶつかった地点である。Device と書いたからといって実行の軸が自動的に閉じるわけではない。二つの軸は違うものを規定している。

オペレーティングシステムごとに違う点

同じハードウェアのビットを前にしても、オペレーティングシステムは互いに異なる方針を重ねる。文書に書かれているとおりにだけ整理すると次のようになる。

システム書き込みと実行を同時に要求するマッピング例外の通路付随する仕組み
OpenBSD許されない。拒否は ENOTSUPファイルシステムが wxallowed でマウントされプロセスが wxneeded でタグ付けされることkern.wxabort で失敗地点を突き止める
macOS の Apple シリコンスレッドが同じ瞬間に書きながら実行することはできないMAP_JIT の領域と専用の権利設定切り替えがスレッド単位。命令キャッシュの無効化が必須
macOS の IntelHardened Runtime を採用したアプリにだけ保護が掛かる同じ権利設定の体系キャッシュ無効化の呼び出しは何もしない
Linuxmmap と mprotect の文書に組み合わせ禁止の記述がない方針は別の層で掛けるno-exec マウントとメモリファイルの実行禁止封印

Linux の行を読み違えないことが大切だ。組み合わせ禁止の記述が文書にないというのは基本のシステムコール層でその組み合わせを拒否しないという意味であって、Linux で W^X を掛けられないという意味ではない。Linux はその決定をマウントオプションとオブジェクト単位の封印、そして別立てのセキュリティモジュールの側へ移してある。方針の位置が違うだけだ。信頼境界をどこに引くかという同じ問いがウェブ側でどう現れるかは クライアントを信用してはいけない理由を扱った記事に別途整理してある。

実行権限を方針として扱う - 実行禁止の封印

実行権限がページのビットを超えてオブジェクトの性質になった事例が Linux のメモリファイルにある。カーネル文書は三つの取っ手を定義している。

  • 実行禁止の封印フラグ — このビットを立てるとメモリファイルが実行禁止の状態で作られ、実行の封印が一緒に掛かるので、後から実行権限を付けるように変えることができなくなる。
  • 実行許可フラグ — このビットを立てると実行権限を持ったまま作られる。
  • システム全体の設定 — 値がゼロならどちらも指定しない呼び出しが実行許可の側で動き、1 なら実行禁止の封印の側で動き、2 なら封印を指定していない呼び出しそのものを拒否する。

カーネル文書が明かしている背景も明確だ。実行可能なメモリファイルは混乱した代理人の形の悪用や実行禁止方針の迂回の通路になりうるが、コンテナランタイムがバイナリを実行するような正当な用途も確かにあるので、その二つを見分ける方法が必要だった、というのである。

この設計が示すものが、この整理の軸とちょうど重なる。実行権限が一度決めたら取り消せない状態になった。ページテーブルのビット一つだったものが、いまやファイルディスクリプタというオブジェクトに付いてその残りの生涯を規定する性質になっている。保護装置として入ってきたビットが資源管理の語彙へ昇格したのだ。

そして前節の二重マッピング JIT と正面から衝突する。システム全体の設定がもっとも厳しい値になっていると、JIT 用のメモリファイルはそもそも作られない。堅牢化の取っ手一つが正常な機能一つを止めるのである。どちらが正しいかはそのシステムが何を動かしているか次第であり、その判断を代わりにしてくれる既定値は存在しない。

きっかけの記事とこの整理が分かれる地点

きっかけの記事が主張する範囲は狭くて明確だ。ARM64 ベアメタルハイパーバイザ一件のデバッグ記録であり、結論は Device の表示と実行禁止の表示が違うものを防ぐという事実である。著者はその事実を見落として数週間を使い、それを知った途端に問題が解けた。

その記事にないものもはっきりさせておく必要がある。実行禁止ビットの導入経緯、W^X 方針のシステムごとの違い、JIT の実装方式、x86 側の事情はあの記事の主題ではない。上の各節でその箇所を埋めた根拠はすべて各文書とソースの原文であり、きっかけの記事の主張を伸ばして取ったものではない。

一般化してはいけない線も一本引いておく価値がある。あの記事の結論はDevice と表示したから命令の軸まで閉じたと見てはいけないということであって、実行禁止を有効にすれば投機的実行に関わる問題が一般に解決するということではない。後者はまったく別の主張であり、あの記事はそんなことを言っていない。

残る文は一つだ。セキュリティ機能として入ってきた仕組みが、実はアーキテクチャの別の規定を代わりに表現していた。そしてその規定を必要とした開発者にとってセキュリティは副産物として来た。導入の目的と実際の使われ方がずれるのは失敗ではない。表現できる状態が一つ増えれば、その表現はいつでも元の場所より遠くまで行く。

確認できなかったこと

  • ARM 開発者サイトのアーキテクチャ文書のページはスクリプトで描画される作りのため、本文を開けなかった。きっかけの記事が引用した ARM 文書の一文はその記事を通じてのみ突き合わせており、マニュアルの節番号と版番号までは確定できなかった。
  • Intel と AMD のアーキテクチャマニュアルの PDF 原本は開けなかった。x86 の 63 番ビットと条件付きの定義は Linux カーネルヘッダの定義とコメントでのみ突き合わせている。ベンダが使う名称表記はそのヘッダにないので、本文でベンダ名称を使わなかった。
  • PXN と UXN という名前の読み解きはマクロ名から読んだものであり、ARM マニュアルの原文で確定できなかった。本文では権限レベルごとの実行禁止という機能の説明だけを書いた。
  • きっかけの記事のディスアセンブリで間接分岐が使うレジスタ番号は、引用によって異なって見えた。論旨は静的分岐と間接分岐の対比なので、本文の記述では番号を外して形だけ残した。
  • 権限の切り替えと二重マッピングの実際の費用を表す数値は一次資料で見つからなかった。代価の種類だけを書き、大きさは書いていない。
  • Apple のコールバック方式の書き込み API が導入された macOS のバージョンは確認できなかった。文書には権利設定と動作だけが書かれており、バージョン表記が見当たらない。
  • メモリファイルの実行封印に関する記述は man page 側で見つからず、カーネル文書の側で突き合わせた。二つの文書の改訂時期の差と見られる。
  • Linux カーネルソースの引用は主開発ブランチの時点を基準としており、特定のリリースタグに固定していない。マクロの構成はバージョンによって変わりうる。
