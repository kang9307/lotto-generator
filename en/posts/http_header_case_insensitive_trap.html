The Header Was Sent but the Server Cannot See It - Field Names Ignore Case, Code Does Not

Names are case-insensitive, data structures are case-sensitive - catching the bug that lives in that gap

2026-07-31 Development/Infrastructure

Opening: it was definitely sent, and it is definitely not there

The team you are integrating with gets in touch. We put X-Request-Id on every request. We checked it in the browser dev tools. And yet your server logs have no such value. You open the code and the line that reads the header is plainly there. Nothing throws. The status code is 200. The value is simply absent.

What makes this situation so nasty is that nothing fails. A typo would have raised an error. A dropped network would have timed out. But reading a missing key from an object is not an error. An empty value comes back quietly, that empty value flows into the logger, and no line appears in the log at all. Days later the same question comes back: why is the trace id never recorded?

The cause is a single gap between the specification and the code. This one paragraph is the whole article.

  • HTTP field names are case-insensitive. X-Request-Id, x-request-id and X-REQUEST-ID are the same header. The specification says so directly
  • But the data structures that hold them are case-sensitive. Object keys, dictionary keys, set members, string equality operators — all of them treat X and x as different things
  • So two names that must be equal become different inside the code. That misaligned seam is where the bug lives

The usual prescription is just write everything lowercase. It is not wrong, but it is a rule that only holds inside code you own. You do not get to decide what spelling the other side sends, and by the specification any spelling they choose is legitimate. So this article does not stop at the advice. It walks through exactly where and by whom the name gets rewritten, one layer at a time, and then separates out why values must be treated differently.

Environment. Every output below is from a real run on Windows 10 Pro (10.0.19045). The runtimes are Node.js v22.16.0 (win32) and Python 3.13.3 (win32), and both used the standard library only. No external packages were installed. Every server was bound to 127.0.0.1 on a high port (starting at 18080) and closed when the run finished. Scripts were saved to files and executed, never passed as shell arguments or heredocs.

What could not be measured. This machine has no commercial reverse proxy or gateway product installed, so the relay in section 6 is a minimal proxy written for the test and does not generalise to any particular product. The specification text for the HTTP/2 name rule could not be opened either, so section 5 is written from measurements only with no clause quoted. HTTP/3 has no implementation on this machine and was not measured at all.

Out of scope. Which security headers to enable and with what values is covered in web security basics. Configuring the reverse proxy itself is in reverse proxy setup. Here we look only at how the string that is a header name gets transformed as it crosses layers.

1. Reproduction - the name sent and the key stored are different

First, see the problem directly. To control the bytes exactly, the client used no library at all and wrote the request lines straight into a socket. The server is the standard library HTTP server.

node v22.16.0 / win32
server listening on 127.0.0.1:18080

--- 1-0. exact bytes the client sent ---
"GET /order HTTP/1.1\r\nHost: 127.0.0.1:18080\r\nX-Request-Id: req-4821\r\nContent-Type: application/json\r\nACCEPT: */*\r\nConnection: close\r\n\r\n"

--- 1-1. what the server code tried ---
req.headers['X-Request-Id'] : undefined
req.headers['x-request-id'] : req-4821
req.headers['X-REQUEST-ID'] : undefined

--- 1-2. the keys actually stored in req.headers ---
  key=[host]  value=[127.0.0.1:18080]
  key=[x-request-id]  value=[req-4821]
  key=[content-type]  value=[application/json]
  key=[accept]  value=[*/*]
  key=[connection]  value=[close]

Three lines tell the whole story. The client wrote X-Request-Id and the value arrived at the server intact. Yet looking it up as X-Request-Id reports nothing, and only x-request-id finds it. The list of stored keys makes the reason obvious: every name has been rewritten in lowercase.

The third line is worth a second look. All-uppercase finds nothing either. In other words, this is not match the case somehow but it must be exactly lowercase. Exactly one spelling is valid in this dictionary.

The ACCEPT the client sent likewise became accept. This normalization is not applied to particular headers, it is applied to all of them.

2. The runtime rewrites the name - where did the original spelling go

So is the original spelling gone for good? Dig a little further into the same request and something interesting turns up.

--- 1-3. req.rawHeaders keeps the bytes as they arrived ---
  raw[0]=[Host]  raw[1]=[127.0.0.1:18080]
  raw[2]=[X-Request-Id]  raw[3]=[req-4821]
  raw[4]=[Content-Type]  raw[5]=[application/json]
  raw[6]=[ACCEPT]  raw[7]=[*/*]
  raw[8]=[Connection]  raw[9]=[close]

--- 1-4. lookup by property vs by normalized key ---
  direct  req.headers[X-Request-Id]            : undefined
  normalized req.headers[x-request-id] : req-4821
  Object.hasOwn(req.headers, X-Request-Id)  : false
  Object.hasOwn(req.headers, x-request-id)  : true

Next to the normalized dictionary sits a separate array listing names and values in arrival order. Here X-Request-Id and ACCEPT both survive exactly as they were sent. Even indices are names, odd indices are values.

This tells us two things. First, the runtime did not discard information, it normalized only one side. It built a lowercase dictionary for convenience and kept the original as well. Second, that means it is possible to investigate what spelling the other side actually used. When debugging an integration, dumping this array is the fastest way to find out.

There is a large caveat attached, though. This original array can only be trusted on a direct connection. As section 6 shows, a single relay in the path rewrites its contents entirely.

2.1 The existence check goes wrong the same way

  • Presence checks fall into the same trap. An own-property check with X-Request-Id was false, while x-request-id was true
  • So a branch of the form if the header exists do A, otherwise B always flows to B. It decides nothing arrived even though the value is there
  • If that branch guards authentication or authorization, the feature dies outright. Conversely, in a fail-open shape, the check is silently disabled
  • If the test code uses the same spelling, the tests are wrong in the same way. This is the classic shape where tests pass and only production breaks
  • The worst combination is a test client sending lowercase while the real client sends uppercase. The direction is inverted, so guessing the cause takes even longer

3. The sending side preserves it - names on the wire

If the receiving side normalizes, what about the sending side? Response headers were set deliberately in mixed case, and the bytes that actually landed on the client socket were printed verbatim.

--- 1-5. res.getHeader is case-insensitive (Node normalizes the lookup) ---
  res.getHeader('X-Trace-Id')  : trace-9f2c
  res.getHeader('x-trace-id')  : trace-9f2c
  res.getHeader('X-TRACE-ID')  : trace-9f2c
  res.getHeaderNames()         : ["x-trace-id","x-lower-name","content-type"]

--- 1-6. exact bytes that came back (wire) ---
  |HTTP/1.1 200 OK
  |X-Trace-Id: trace-9f2c
  |x-lower-name: set-in-lowercase
  |Content-Type: text/plain
  |Date: Thu, 30 Jul 2026 20:22:49 GMT
  |Connection: close
  |Content-Length: 3

What emerges here is that the same runtime applies two different policies.

  • Response header lookup ignores case. All three spellings returned the same value. Request headers did not behave that way, but response headers do
  • The name list comes back lowercase. That means the internal store is keyed in lowercase
  • And yet the bytes that actually went out carry the spelling I wrote. X-Trace-Id left uppercase, x-lower-name left lowercase
  • In short, the internal index is lowercase and the emitted representation is the original. Two layers, managed separately

The fact that one lookup in the same codebase is case-sensitive and another is not explains why this problem is never solved by memory. The rule differs per API.

3.1 The names three client types put on the wire

The sending side was probed further. A TCP listener that records bytes and parses nothing was started, and the same three headers were sent by three different clients.

node v22.16.0 / win32
raw TCP sink on 127.0.0.1:18087 (records bytes, never parses them)

--- 7-1. A. node http.request ---
  request line   : GET /a HTTP/1.1
  names on wire  : ["X-Request-Id","X-API-Key","Accept-Language","Host","Connection"]

--- 7-2. B. global fetch (undici) ---
  request line   : GET /b HTTP/1.1
  names on wire  : ["host","connection","X-Request-Id","X-API-Key","Accept-Language","accept","sec-fetch-mode","user-agent","accept-encoding"]

--- 7-3. C. hand-written bytes ---
  request line   : GET /c HTTP/1.1
  names on wire  : ["Host","X-Request-Id","X-API-Key","Accept-Language","Connection"]

--- 7-4. the same three names, side by side ---
  client                    x-request-id      x-api-key         accept-language
  A. node http.request      X-Request-Id      X-API-Key         Accept-Language
  B. global fetch (undici)  X-Request-Id      X-API-Key         Accept-Language
  C. hand-written bytes     X-Request-Id      X-API-Key         Accept-Language

The result differed slightly from expectation. All three clients put the spelling I wrote onto the wire unchanged. Even the second client, which uses the standards-conformant headers object, left user-specified header spellings alone.

Something else shows up in the second client's list instead. Every header the library added on its own is lowercase. What the user supplied is original, what it generated itself is lowercase. So one message goes out carrying two conventions at once.

  • That mixture is entirely legal, because the receiver is supposed to treat names case-insensitively
  • But the assumption our client sends lowercase so the server only needs to look at lowercase breaks right here. The user-specified headers were not lowercase
  • In other words, no decision may rest on the spelling seen on the wire. It is a coincidence, not a contract
  • For HTTP/1.1 all you need to remember is that the sender's spelling flows through as written. The trouble starts at the next layer

4. The data structure differs per framework

Now switch languages. The same request was received by the Python standard library HTTP server, and the result is entirely different.

python 3.13.3 / win32 / Windows 10
--- 2-1. self.headers type ---
  type      : http.client.HTTPMessage

--- 2-2. case-insensitive lookup on the SAME object ---
  headers[X-Request-Id]   -> 'req-4821'
  headers[x-request-id]   -> 'req-4821'
  headers[X-REQUEST-ID]   -> 'req-4821'
  headers[x-ReQuEsT-iD]   -> 'req-4821'

--- 2-3. but the stored names keep the original bytes ---
  key=[Host]  value=[127.0.0.1:18081]
  key=[X-Request-Id]  value=[req-4821]
  key=[ACCEPT]  value=[*/*]
  key=[X-Tag]  value=[alpha]
  key=[x-tag]  value=[beta]
  key=[Connection]  value=[close]

--- 2-4. keys() is NOT normalized, so naive set logic still misses ---
  list(headers.keys())        : ['Host', 'X-Request-Id', 'ACCEPT', 'X-Tag', 'x-tag', 'Connection']
  'x-request-id' in keys      : False
  'X-Request-Id' in keys      : True
  headers.get(x-request-id)   : 'req-4821'
  '__contains__' on the object: True True

--- 2-5. duplicate names collapse differently ---
  get_all(X-Tag)              : ['alpha', 'beta']
  get(X-Tag)   [first only]   : 'alpha'

The design is the exact opposite. Python holds headers not in a plain dictionary but in a mail message object, and that object compares names case-insensitively on lookup. All four spellings returned the value. Even a scrambled spelling like x-ReQuEsT-iD works.

At the same time the stored names keep the original. What Node solved by keeping a lowercase dictionary and a raw array separately, Python solved by merging both into one object. It is fair to say this design looks safer.

4.1 And yet the same trap exists here

It is safe only while you go through that object. The moment you pull out the list of names, it becomes an ordinary list of strings again.

  • Extract the name list and ask whether x-request-id is in it and the answer is false, because the list members are the original spellings
  • Ask the object the same name directly and it is true. In other words, the same data yields two answers
  • So code that iterates the list and filters misses in Python exactly as it does elsewhere. Changing language does not solve it
  • Duplicate handling differs too. Sending X-Tag and x-tag separately kept both as distinct entries, while the call that fetches all of them ignored case and returned both values
  • The call that fetches one, by contrast, returned only the first that arrived. The later value disappears silently

Node reacts differently in the same situation. As section 7 shows, it merges the two into a single comma-joined string. The specification permits combining multiple field lines with the same name using commas, and this runtime made that choice. Which means the same input yields three different results.

The table in one line: whatever offers a lookup is generally safe, and whatever exposes a list is generally dangerous. And either way, carrying one language's rule over to another gives the wrong answer.

5. In HTTP/2 an uppercase name is a protocol error

Everything so far was HTTP/1.1. Change the transport and the story changes. First, an uppercase name sent through an ordinary client library.

node v22.16.0 / win32  (http2 module, cleartext h2c)

--- 3-1. client sends the name written as X-Request-Id ---
  request({X-Request-Id}) : accepted by the API (no throw)

--- 3-2. what the HTTP/2 server received ---
  key=[:path]  value=[/order]
  key=[:method]  value=[GET]
  key=[:authority]  value=[127.0.0.1:18082]
  key=[:scheme]  value=[http]
  key=[x-request-id]  value=[req-4821]
  stream.session.alpnProtocol : h2c

--- 3-4. response header names the HTTP/2 client sees ---
  key=[:status]  value=[200]
  key=[x-trace-id]  value=[trace-h2]
  key=[content-type]  value=[text/plain]

Three things stand out. First, the API accepted the uppercase name and threw nothing. Second, the name that arrived at the server was lowercase. Third, a response header the server set in uppercase reached the client in lowercase.

So the library quietly rewrote it. Nothing goes wrong here. The problem is that this leniency hides the real rule.

5.1 Writing an uppercase name into the compression layer by hand

The library was removed to check. HTTP/2 does not send headers verbatim; it carries them in a dedicated compressed form. Those bytes were built by hand and transmitted with an uppercase letter in the name. For comparison the identical request was also sent in lowercase.

node v22.16.0 / win32  (raw HPACK over cleartext h2c)

--- 8-1. field name written as x-request-id (lowercase) ---
  server stream event  : names = [":method",":scheme",":path",":authority","x-request-id"]
  frames from server   : ["SETTINGS stream=0","SETTINGS stream=0","HEADERS stream=1","DATA stream=1"]
  server saw a stream  : true

--- 8-2. same request, field name written as X-Request-Id ---
  frames from server   : ["SETTINGS stream=0","SETTINGS stream=0","RST_STREAM stream=1  errorCode=1"]
  server saw a stream  : false

--- 8-3. and as ACCEPT ---
  frames from server   : ["SETTINGS stream=0","SETTINGS stream=0","RST_STREAM stream=1  errorCode=1"]
  server saw a stream  : false

The result is unambiguous. The lowercase name was processed normally and a response came back. Changing only the spelling of the name in the same request made the server tear the stream down immediately with error code 1. The second case, with the name changed to ACCEPT, behaved identically.

The most important line is the last. The server's request handler was never invoked once. The application code does not even know the request arrived.

  • So in HTTP/2 an uppercase name is not a problem of an invisible value but of an invalid request
  • The symptom presents as a dropped connection rather than one missing header. That sends the investigation in a completely different direction
  • Using a normal library makes this state hard to reach, because the library lowercases the name first
  • Conversely, code that builds bytes by hand, or assembles the name string somewhere, hits it
  • One family of the integration worked on HTTP/1.1 and broke only after switching to HTTP/2 reports is exactly this

Stating the measurement boundary. The result above was measured against one HTTP/2 implementation on this machine. Since the specification text could not be opened, this article does not claim the specification requires this. The confirmed fact stops at: this implementation resets the stream with a protocol error when it receives a name containing uppercase letters. HTTP/3 has no implementation here and was not measured at all. The practical guidance is the same either way: pinning names to lowercase is safe across all three transports.

6. One proxy hop rewrites every name

Section 2 showed the original spelling surviving in an array. Time to see whether it can be trusted. A minimal relay server was written, doing what is done everywhere: pass the received header dictionary straight to the next hop.

node v22.16.0 / win32
origin on 127.0.0.1:18083   proxy on 127.0.0.1:18084

--- 4-0. field names the client put on the wire ---
  X-Request-Id / X-API-Key / ACCEPT

--- 4-1. DIRECT to origin: names as received ---
  ["Host","X-Request-Id","X-API-Key","ACCEPT","Connection"]

--- 4-2. THROUGH one proxy hop: names as received by the SAME origin ---
  ["host","x-request-id","x-api-key","accept","connection"]

--- 4-3. diff ---
  identical name lists : false

--- 4-4. response names the client sees ---
  direct        : |X-Origin-Marker: origin-1
  through proxy : |x-origin-marker: origin-1

Same client, same bytes, same final server. Inserting a single relay made every arriving name lowercase. The contents of the array that was supposed to hold the original spelling changed along with it.

The reason is simple. What the relay forwarded was a dictionary already normalized to lowercase, and when it built the next request those keys were written straight onto the wire. The relay did not forward bytes, it reassembled a parsed result.

The response direction is the same. A header the final server attached as X-Origin-Marker reached the client as x-origin-marker.

  • This is not a bug, it is correct relay behaviour. Names are case-insensitive, so rewriting them in any spelling violates nothing
  • Which is why logic depending on the original spelling breaks only in production. Development environments connect directly, with no proxy
  • Load balancers, CDNs and service meshes all sit in exactly that position. It would not be strange for any of them to change the representation
  • Worse, if an intermediary receives HTTP/2 and forwards HTTP/1.1, the original spelling never existed to begin with, as section 5 showed
  • There is only one conclusion. The spelling of a name is not a contract. Code that treats header names case-sensitively will eventually be wrong

7. Comparison code that silently misses

Now for how real code goes wrong. Three common shapes were measured simultaneously within one request.

--- 5-1. equality and membership on the NAME ---
  keys                        : ["host","x-request-id","authorization","cookie","x-api-key","content-type","x-tag","connection"]
  seen.includes('X-Request-Id'): false
  seen.includes('x-request-id'): true
  Set built from a written spec: ["X-Request-Id","X-API-Key","Authorization"]
  matched by that Set          : []
  matched after normalizing    : ["x-request-id","authorization","x-api-key"]

--- 5-2. the strip list that does not strip ---
  after delete ['Authorization'] : authorization still present = true
  value that would be forwarded  : Bearer sK9xQz
  cookie still present           : true
  normalized filter -> keys      : ["host","x-request-id","content-type","x-tag","connection"]

The first block is the most common shape. A list of names is built with the spellings written in the integration document, put into a set, and arriving headers are filtered against it. The result was an empty array. All three had in fact arrived, and not one was selected.

The second block is more dangerous. It is code that removes sensitive headers before forwarding outward. It deletes Authorization and Cookie exactly as the document spells them. But the actual keys were lowercase, so the deletion did nothing and the credential stayed put.

The nature of this incident. When the stripping fails, the feature still works. The request forwards fine and the response comes back fine. There is not one visible symptom. That is why this failure is not caught by monitoring. It appears in no metric and no log, and cannot be known without actually inspecting the content of the outbound call. Code that maintains a strip list is safer when it also carries an assertion that the header is genuinely gone afterwards.

7.1 The shape where the log records nothing

--- 5-3. the log line that logs nothing ---
  log ctx rid = {}
  log ctx rid = {"rid":"Req-4821"}
  fallback chain               : Req-4821
  fallback with ?? (nullish)   : MISSING

--- 5-4. WHATWG Headers vs a plain object, same data ---
  Headers.get('X-Request-Id')  : Req-4821
  Headers.get('x-request-id')  : Req-4821
  Headers.has('X-API-KEY')     : true
  [...Headers.keys()]          : ["authorization","content-type","cookie","host","x-api-key","x-request-id","x-tag"]
  plain object same lookups    : undefined / Req-4821

--- 5-6. duplicate names arriving with different casing ---
  x-tag                        : [alpha, beta]

The first line explains this article's opening exactly. A value was put into a log context object and the result is an empty object. A property holding an empty value loses its key entirely during serialization.

So the screen shows not the value looks wrong but that field is not there at all. Whoever searches the logs cannot find the line and naturally concludes the header must not have arrived. This is the point at which the investigation heads in exactly the wrong direction.

  • The common workaround of listing several spellings does find the value. But however many you write, you cannot write them all. It is a stopgap
  • Using an operator that only substitutes for empty values is worse. The preceding lookup genuinely is empty, so it falls straight through to the fallback, and the run printed the placeholder in that slot
  • With the standards headers object, the lookup is safe. Every spelling returned the value and the presence check worked
  • But even that object hands back a name list normalized to lowercase. Code comparing that list against original spellings misses here too
  • Duplicate names were merged into one, ignoring case. The two values sent as X-Tag and x-tag became a single comma-joined string. Different from the Python result in section 4

8. Names ignore case, values do not

This is the point most often blurred in practice: taking the sentence HTTP headers are case-insensitive and applying it to values too. Measurement says otherwise entirely.

--- 5-5. the NAME is case-insensitive, the VALUE is not ---
  value as received            : [Req-4821]
  rid === 'REQ-4821'           : false
  rid === 'req-4821'           : false
  authorization as received    : [Bearer sK9xQz]
  startsWith('Bearer ')        : true
  startsWith('bearer ')        : false
  token                        : [sK9xQz]
  token.toLowerCase() === token: false   <- lowercasing a value destroys it
  content-type                 : [application/json; charset=UTF-8]
  ct === 'application/json'    : false
  ct.split(;)[0].trim().toLowerCase() : [application/json]

Three cases, three different lessons.

  • Identifier values. The value that arrived was Req-4821. Comparing against either casing is false. A value means exactly what is written, so normalizing it produces a different value
  • Authorization headers. The leading scheme name may be compared case-insensitively, but the credential that follows is exact to the character. In the run, the lowercased credential differed from the original. Lowercasing the whole value breaks authentication outright
  • Media types. Comparing the whole value including its trailing parameter is false. What is actually needed is cutting off the leading part and trimming whitespace before comparing
  • In short, apply normalization unconditionally to names, and to values only after checking that header's definition
  • Keeping the function that handles values entirely separate from the one that handles names reduces mistakes. Touch both in one function and they will eventually get mixed

9. The safe way to read - normalize, then look up

The correction is simple. Always normalize the name at the lookup site. Two more things must be handled alongside it before it is genuinely safe.

--- 6-1. one getter, every spelling ---
  getHeader(X-Request-Id)    -> "req-4821"
  getHeader(x-request-id)    -> "req-4821"
  getHeader(X-REQUEST-ID)    -> "req-4821"
  getHeader(x-ReQuEsT-iD)    -> "req-4821"
  getHeader(X_Request_Id)    -> undefined

--- 6-2. the prototype trap of a plain-object lookup ---
  Object.getPrototypeOf(h) === null  : false
  naive h['constructor']             : function Object() { [nat
  naive h['toString']                : function
  getHeader(h,'constructor')         : undefined
  getHeader(h,'toString')            : undefined

The first block behaves as hoped. One function returned the same value for four spellings. The last line is correct behaviour: a name written with underscores really is a different header, so having no value is right.

The second block is the less known trap. The header dictionary is a plain object and is linked to a parent prototype. So reading a name directly without normalizing produces a function for a name that never arrived. A check that only tests true or false will pass on that.

  • That is, code that looks headers up using an externally supplied string gets surprising answers from its presence check
  • A safe getter verifies own-property first and closes that path. In the run, both names returned nothing
  • The target may also be a standards headers object, so adding a branch that prefers a dedicated lookup method when one exists covers both cases in one function
  • Name normalization needs nothing beyond a plain lowercase conversion, because the characters allowed in a header name are restricted to ASCII

9.1 Mixing spellings on the sending side

--- 6-3. send side: two spellings of one name ---
  after setHeader('X-Tag','first')   : getHeaderNames = ["x-tag"]
  after setHeader('x-tag','second')  : getHeaderNames = ["x-tag"]
  res.getHeader('X-TAG')             : second

--- 6-4. names the runtime refuses outright ---
  setHeader("X Request Id") : ERR_INVALID_HTTP_TOKEN
  setHeader("X-Request-Id:") : ERR_INVALID_HTTP_TOKEN
  setHeader("X-Request-Id\n") : ERR_INVALID_HTTP_TOKEN
  setHeader("") : ERR_INVALID_HTTP_TOKEN

--- 6-5. what actually went out on the wire ---
  |HTTP/1.1 200 OK
  |x-tag: second
  |X-Trace-Id: trace-9f2c
  |Content-Type: text/plain

On the sending side, the same name was set with two spellings. The result was not two headers but an overwrite. The name list holds one entry and the value is the later one.

And the representation that went out was the spelling written last. Write it uppercase first and lowercase later and it leaves lowercase. In other words, the emitted representation is decided by the final write.

  • In a codebase where several modules set the same header with their own spellings, which representation goes out is unpredictable
  • The overwrite of the value matters just as much. Nobody knows that two modules are erasing each other's value
  • Names containing spaces, colons or newlines are refused by the runtime. Code that drops user input straight into the name slot dies with an exception here
  • An empty string is refused too. Code that assembles names must check the paths where assembly can yield an empty string
  • Refusal surfacing as an exception is the fortunate case. Unlike the other incidents in this article, at least it is visible

9.2 A lookup function to take away

// Header names ignore case. Normalize at the lookup site.
// One function covering a plain object and a standards headers object.
function getHeader(headers, name) {
  if (!headers || typeof name !== 'string') return undefined;
  const key = name.toLowerCase();
  if (typeof headers.get === 'function') return headers.get(key);
  return Object.prototype.hasOwnProperty.call(headers, key)
    ? headers[key]
    : undefined;
}

// Normalize the strip list too. Fixing only the lookup is half a fix.
const DROP = new Set(['authorization', 'cookie', 'x-api-key']);
const forwarded = Object.fromEntries(
  Object.entries(req.headers).filter(([k]) => !DROP.has(k.toLowerCase()))
);
# Python. The standard header object already looks up case-insensitively.
# What is dangerous is code pulling out the name list and comparing strings.

DROP = {"authorization", "cookie", "x-api-key"}

def get_header(headers, name):
    return headers.get(name)          # finds it regardless of case

def forwardable(headers):
    # keys() holds the original spellings, so always normalize before comparing
    return {k: v for k, v in headers.items() if k.lower() not in DROP}

# The same name may have arrived several times. Fetching one drops the rest
tags = headers.get_all("X-Tag") or []

10. Team convention and checklist

Fixing the code alone will not stop recurrence. This problem keeps being reborn at the point where a human copies a spelling out of a document. Here is what to pin down by convention.

  • Always write names in lowercase. Integration documents, code constants, tests, log keys, all of them. Do not mix in capitals to make it look tidy
  • Do not scatter name strings through the code. Gather them into one set of constants and there is no place for spellings to diverge
  • Make one path for reading headers. Allow only the getter function, and have review reject code that indexes the dictionary directly
  • Fix the strip list and the lookup together. Fix only the lookup and the side that leaks sensitive headers remains
  • Never normalize values. If a value needs normalizing, do it for that one header after checking its definition
  • Make the test client deliberately mix spellings. A test that only ever sends lowercase can never catch this bug
  • Test at least once through a shape with an intermediary. Testing only on direct connections hides the transformation from section 6
  • Do not depend on the original spelling. The raw array is for debugging, not an input to logic

10.1 Checklist

  • Does every place that reads a header use normalize-then-look-up
  • Is there anywhere left that indexes the dictionary with a string containing capitals
  • Does code that compares names with an equality operator or puts them in a set normalize first
  • Is the strip list of sensitive headers written with normalized names
  • Is there an assertion that they are genuinely gone after stripping
  • Does the team know that a value put into a log context loses its key entirely when empty
  • Is the path where a presence branch turns wrongly true via an inherited property closed off
  • Is there anywhere applying blanket lowercasing to values
  • Are values holding credentials left untransformed before comparison
  • Does media type comparison strip the parameter first
  • Has the case of the same header arriving several times been handled
  • Is there any path where user input lands directly in the header name slot
  • Do the tests send requests with uppercase spellings too
  • Is there code assembling names by hand on the HTTP/2 path

10.2 What not to do

  • Copying the spelling from a document straight into a code key — every incident here starts there
  • Blocking it by listing several spellings — you cannot list them all, so it is a stopgap
  • Treating the original spelling as grounds for logic — one relay makes it vanish
  • Applying blanket normalization to values — credentials and identifiers get destroyed
  • Running tests in lowercase only — it breaks in production alone
  • Keeping a strip list and never verifying the result — failure has no symptom
  • Leaning on the assumption that we all send lowercase — the other side is under no such obligation

# HTTP Header Name Case — Safe Lookup and Checklist

> Source: braindetox.kr — The header was sent but the server cannot see it
> Basis: Windows 10 / Node.js v22.16.0 / Python 3.13.3 standard library runs (HTTP/1.1 + h2c)

## 0. The premise — where the gap is

| Layer | Case | Basis |
|---|---|---|
| **Header name** | **Ignored** | RFC 9110 5.1 |
| **Header value** | **Significant** (per-field definition) | RFC 9110 5.5 |
| Object keys, sets, string comparison in code | **Significant** | Language rules |

**The bug appears the moment a case-insensitive name is put into a case-sensitive data structure.**

## 1. Thirty-second diagnosis — when the value is missing

1. Dump the keys actually stored, in full (do not guess)
2. Look it up again with the lowercase name
3. Dump the raw name array if one exists (trust it only on a direct connection)
4. Check whether there is an intermediary — if so, the original spelling is already gone
5. On an HTTP/2 path the name is lowercase, without exception

## 2. Safe lookup (JavaScript)

```js
function getHeader(headers, name) {
  if (!headers || typeof name !== 'string') return undefined;
  const key = name.toLowerCase();
  if (typeof headers.get === 'function') return headers.get(key);
  return Object.prototype.hasOwnProperty.call(headers, key)
    ? headers[key]
    : undefined;
}
```

- The `hasOwnProperty` check is **required**. The header dictionary is linked to a parent prototype, so reading without normalizing **produces a function for a name that never arrived**
- A check that only tests true or false **will pass on that function**

```js
// Normalize the strip list too. Fixing only the lookup is half a fix.
const DROP = new Set(['authorization', 'cookie', 'x-api-key']);
const forwarded = Object.fromEntries(
  Object.entries(req.headers).filter(([k]) => !DROP.has(k.toLowerCase()))
);
```

## 3. Safe lookup (Python)

```python
DROP = {"authorization", "cookie", "x-api-key"}
```

## 4. Behaviour by layer (measured)

| Layer | Name storage | Case on lookup | Original spelling | Duplicate names |
|---|---|---|---|---|
| Node request header dict | **Lowercase normalized** | **Sensitive** | Kept in a separate array | Joined with commas |
| Node raw name array | Arrival order, verbatim | — | **Intact** | Each kept |
| Node response headers | Lowercase index | **Insensitive** | Original on output | Overwritten |
| Standards headers object | Lowercase index | **Insensitive** | List is lowercase | Joined with commas |
| Python header object | Original spelling kept | **Insensitive** | **Intact** | Each kept |
| Python name list | Original spelling strings | **Sensitive** | Intact | Each listed |
| HTTP/2 transport | **Lowercase only** | — | **None** | Per transport rule |

→ **Whatever offers a lookup is generally safe; whatever offers a list is generally dangerous.**

## 5. Name versus value — what may be normalized and what may not

| Target | Normalization | Reason |
|---|---|---|
| Header name | **Always lowercase** | Case-insensitivity is the spec |
| Trace id value | **Never** | Changing it makes a different value |
| Auth scheme name | Only when comparing | Separate from the credential |
| Credential body | **Never** | Touch it and authentication fails |
| Media type prefix | Prefix only | Strip the parameter first |
| Path and query string | **Never** | Not a header |

## 6. Incident shapes confirmed by measurement

- Filtering with a set built from document spellings selected **none of them** (all had arrived)
- A strip list written in uppercase **removed nothing** → **the credential was forwarded intact**
- Putting an empty value into a log context made **the key vanish entirely**, printing an empty object
- A **single relay hop** turned every name lowercase in both directions
- An uppercase name over HTTP/2 **got the stream reset as a protocol error** (the application never saw the request)
- Setting one name with two spellings produced not two headers but **an overwrite**

- [ ] **Every place** that reads a header uses normalize-then-look-up
