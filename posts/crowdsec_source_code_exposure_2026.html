1. 공급망 보안의 역설 — 탐지와 통보 사이의 4개월 시차

사이버 보안 생태계에서 가장 엄격한 방어 훈련을 거치고 일상적인 침투 테스트(red-team pentesting)를 수행하는 전문 보안 기업조차도 자신이 직접 작성하지 않은 외부 소프트웨어의 결함 앞에서는 취약해질 수 있습니다. 협업형 침입 방지 시스템이자 글로벌 위협 인텔리전스 네트워크를 운영하는 프랑스의 대표적 보안 소프트웨어 기업 CrowdSec이 자사 소스 코드 저장소 노출 사실을 공식 시인했습니다. 2026년 9월 17일 게시된 공식 성명에 따르면, 유출 사건 자체는 2026년 5월에 일어났으며 회사가 이 사실을 인지하게 된 것은 외부 보안 제보자로부터 통보를 받은 2026년 9월 16일이었습니다.

본 사이트에서는 앞서 GitHub 대규모 악성코드 유포 캠페인과 오픈소스 공급망 방어 전략을 다루며 의존성 생태계의 취약점을 분석한 바 있습니다. 당시 분석이 광범위한 패키지 생태계에서 벌어지는 대량 악성코드 유포 수법을 조망했다면, 이번 CrowdSec 사례는 보안 전문 기업 자체가 상류(upstream) 라이브러리 오염의 직접적인 피해자가 된 구체적 사건이라는 점에서 질적으로 다른 교훈을 던집니다. 침해 발생 시점과 피해 인지 시점 사이에 무려 4개월이라는 공백이 발생했다는 사실은 내부 침투 탐지 시스템이나 엔드포인트 보안 장비만으로는 상류 소프트웨어 공급망을 통한 자격 증명 탈취를 사전에 포착하기가 얼마나 어려운지를 극명하게 보여줍니다.

보안 업계의 관점에서 소스 코드 유출은 제품의 기술적 경쟁력 상실이나 공격자에 의한 제로데이 취약점 분석으로 이어질 수 있는 중대한 사건입니다. 하지만 CrowdSec의 이번 발표를 면밀히 살펴보면 단순한 자산 유출 소식 이상의 구조적 질문들이 자리하고 있습니다. 침해의 근본 원인이 CrowdSec 자체 코드베이스의 허점이 아니라 널리 사용되는 프런트엔드·풀스택 생태계 컴포넌트인 Tanstack 침해였다는 점, 유출된 대상과 애초에 공개 설계되어 영향을 받지 않은 오픈소스 엔진이 명확히 갈린다는 점, 그리고 고객 데이터를 수집·저장하지 않는 아키텍처 덕분에 피해가 사내 자산에 국한될 수 있었다는 사실이 그것입니다. 이 사건의 구체적인 경과와 아키텍처적 방어선을 분석하는 작업은 모든 소프트웨어 개발 조직에 중요한 지침을 제공합니다.

2. 타임라인 재구성 — 2026년 5월 침해에서 9월 공식 발표까지

보안 사고를 올바르게 평가하기 위해서는 사건의 진행 과정을 시간순으로 정밀하게 재구성해야 합니다. CrowdSec이 밝힌 공식 타임라인에 따르면 침해 행위가 일어난 시점과 악용 가능했던 시간창, 그리고 외부 제보 접수 및 공식 대응까지의 일정은 명확한 대비를 이룹니다. 공격자가 시스템에 머물며 장기적으로 활동한 것이 아니라 특정 시점에 토큰을 탈취해 비공개 저장소를 복제한 뒤 사라졌음을 시사합니다.

사건의 발단은 2026년 5월로 거슬러 올라갑니다. 당시 조직 내부의 개발 워크플로에서 사용되던 서드파티 컴포넌트가 침해되면서 내부 비공개 코드베이스를 읽을 수 있는 권한을 가진 API 키가 외부로 유출되었습니다. CrowdSec 공식 발표에 따르면 이 유출은 2026년 5월의 짧은 시간대 동안만 악용 가능한(only exploitable during a short timeframe) 상태였습니다. 이후 4개월 동안 침해 사실은 사내 모니터링에 잡히지 않은 채 잠복해 있었습니다.

일시 주요 사건 공식 확인 내용 및 성격
2026년 5월 상류 공급망 컴포넌트 침해 및 API 키 유출 Tanstack 컴포넌트 백도어를 통한 비공개 저장소 읽기 토큰 탈취, 단기 악용 창 발생
2026년 5월 ~ 9월 4개월간의 침해 미인지 및 코드베이스 진화 내부 탐지 체계에서 이상 징후 미검출 상태 지속, 해당 기간 동안 사내 소스 코드 대폭 변경
2026년 9월 16일 외부 제보 접수 및 사내 긴급 검증 착수 외부 제보자 「Fuites Infos」의 전문적 통보 수신, CrowdSec 보안팀의 즉각적인 유출 사실 확인
2026년 9월 17일 공식 성명 게시 및 자격 증명 전면 교체 공식 블로그를 통한 노출 시인, 모든 관련 토큰 및 인증서 즉각 교체(rotated) 완료 공표

2026년 9월 16일, 프랑스의 유출 정보 전문 제보 플랫폼인 「Fuites Infos」가 CrowdSec 측에 소스 코드 유출 정황을 전달했습니다. CrowdSec은 이 제보가 시의적절하고 매우 전문적인(professional outreach) 방식으로 이루어졌음을 확인하고 감사를 표했습니다. 통보를 받은 CrowdSec 보안 엔지니어들은 당일 즉각 사실 확인 작업을 벌여 5월에 유출된 코드베이스의 존재를 확인했고, 다음 날인 9월 17일 공식 블로그를 통해 사고 경위와 범위를 투명하게 공개했습니다.

3. 침해 경로 분석 — 제3자 컴포넌트 Tanstack 침해와 API 키 탈취

이번 사고에서 가장 핵심적인 부분은 공격 벡터의 성격입니다. CrowdSec의 인프라 서버나 방화벽이 뚫린 것이 아니라, 개발 환경에서 의존하던 외부 오픈소스 라이브러리가 오염된 것이 침해의 출발점이었습니다. 공식 성명에 따르면 이번 유출의 경로로는 **Tanstack 침해(Tanstack compromise)**가 가장 유력하게 지목되었습니다.

Tanstack 생태계는 웹 및 소프트웨어 애플리케이션 개발에서 상태 관리, 라우팅, 테이블 렌더링, 쿼리 캐싱 등을 위해 수많은 조직이 광범위하게 사용하는 핵심 프레임워크입니다. CrowdSec에 따르면 이와 유사한 공급망 침해 공격은 앞서 프랑스의 인공지능 기업 Mistral AI 사례에서도 나타난 바 있으며, 사이버 보안 인텔리전스 기업 CybelAngel의 기술 분석에서도 Tanstack 컴포넌트 오염이 SDK 오염으로 이어진 메커니즘이 보고된 바 있습니다.

  • 상류 패키지 변조: 개발 과정에서 설치되는 정상적인 패키지 배포판 내부에 악의적 코드가 주입되었습니다.
  • 빌드·실행 환경 메모리 접근: 컴포넌트 실행 과정에서 CI/CD 파이프라인이나 로컬 개발자 환경의 환경 변수 및 토큰을 탐색했습니다.
  • 비공개 저장소 읽기 키 추출: 조직의 GitHub 저장소에 접근하여 소스 코드를 읽을 수 있는 권한을 보유한 API 키가 백도어를 통해 외부 공격 서버로 전송되었습니다.
  • 제한된 악용 시간창: 해당 키는 비공개 저장소를 읽는 데 악용되었으나, CrowdSec 측의 설명에 따르면 장기간 지속되지 않고 2026년 5월 중 매우 짧은 기간 동안만 동작했습니다.

이러한 침해 수법은 오늘날의 모던 개발 스택이 가진 구조적 위험을 방증합니다. 현대의 애플리케이션은 수백 개 이상의 직간접적 패키지 의존성을 가집니다. 개발팀이 아무리 엄격한 코드 리뷰와 정적 분석을 거쳐 자체 코드를 작성하더라도, 빌드 도구나 개발 라이브러리가 의존하는 단 하나의 하위 패키지가 손상되면 해당 환경에서 취급되는 비밀 값(secret)은 손쉽게 외부로 새어 나갈 수 있습니다.

4. 노출 범위 실측 — 300개 저장소의 내역과 비공개 컴포넌트

사건 발표 직후 언론과 커뮤니티에서는 「CrowdSec의 300개 저장소가 유출되었다」는 자극적인 헤드라인이 확산되었습니다. 그러나 CrowdSec 공식 성명에 따르면 이 300개라는 숫자는 코드베이스의 모듈 분할 구조를 나타내는 수치일 뿐, 전체 시스템이 완전히 장악되었다는 의미와는 거리가 있습니다. 중요한 것은 숫자의 크기가 아니라 **어떤 성격의 저장소가 포함되었는가**입니다.

우선 300개 저장소 가운데 **130개 이상은 애초에 완전한 공개(public) 오픈소스 저장소**였습니다. CrowdSec의 주력 제품인 Security Engine은 처음부터 공개 소스 코드로 배포되어 전 세계 커뮤니티가 함께 개발하고 검증하는 소프트웨어입니다. 따라서 공개 저장소는 설계상 누구나 볼 수 있는 것이 기본 전제이므로 유출로 인한 비밀성 침해가 발생할 여지가 없습니다.

구분 포함된 구성 요소 위험성 평가 및 영향 분석
노출된 비공개 자산 SaaS 콘솔 소스코드, 일부 AWS 클라우드 루틴, 커넥터 및 사내 자동화 스크립트 사내 비즈니스 로직 및 클라우드 연동 코드가 노출되었으나 독자적인 데이터 환경에 종속되어 외부 활용 가능성 낮음
노출된 인증 정보 CI/CD 컴포넌트 자체에서 사용되던 API 토큰 빌드 파이프라인 연동 토큰이 노출되었으며 인지 직후 즉각적인 전면 무효화 및 교체 조치 완료
유출 대상 제외 자산 Security Engine(보안 탐지 엔진 본체) 애초에 오픈소스로 공개 설계(public by design)된 무료 소프트웨어로 유출 범위에서 원천 제외
보호된 데이터 자산 고객 데이터, 로그인/비밀번호 계정, 조직명, 개인식별정보(PII) CrowdSec 아키텍처가 고객 로그와 PII를 사내에 저장하지 않으므로 고객 데이터 침해 0건
확인되지 않은 침해 내부 개발 자료, 별도 문서 파일, 횡적 이동용 고권한 자격 증명 코드 외 별도 내부 문서 유출은 없으며 내부 침투 및 인프라 장악을 가능케 하는 자격 증명 누출 부재

실제 유출 피해를 입은 영역은 비공개(private)로 유지되던 나머지 저장소들이었습니다. 여기에는 CrowdSec의 웹 기반 관리 화면인 SaaS 콘솔(Console)의 프런트엔드 및 백엔드 코드, 일부 AWS 클라우드 운영 루틴, 다양한 로그 수집기 및 방화벽과 연동되는 커넥터(connector) 코드, 그리고 사내 빌드·배포를 보조하는 자동화 스크립트가 포함되어 있었습니다.

5. 비공개 코드 유출의 실질적 영향 — AWS 클라우드 루틴과 SaaS 콘솔

비공개 저장소의 코드가 외부로 노출되었다는 사실은 결코 가볍게 넘길 수 없는 사안입니다. 보안 엔지니어링 관점에서 비공개 코드 유출이 야기할 수 있는 위험은 크게 세 가지로 분류됩니다. 첫째는 코드 내에 하드코딩된 자격 증명이 존재하는가, 둘째는 클라우드 아키텍처 루틴을 통해 공격자가 인프라로 침투할 수 있는가, 셋째는 소프트웨어 자체의 로직 취약점이 공격자에게 분석될 수 있는가입니다.

CrowdSec 보안팀의 자체 조사 결과에 따르면, 이번에 노출된 비공개 저장소 안에서 클라우드 인프라의 내부로 침투하여 권한을 상승시키거나 다른 시스템으로 건너갈 수 있는(lateral movement) 민감한 자격 증명은 발견되지 않았습니다. 노출된 API 관련 정보는 CI/CD 컴포넌트 자체가 빌드와 테스트 자동화를 위해 사용하던 제한된 토큰에 국한되었습니다.

  • 코드 자체의 고립성: 유출된 콘솔 및 클라우드 루틴은 CrowdSec 고유의 데이터베이스 및 사내 도구 체계와 긴밀히 맞물려 동작하도록 설계되어 있습니다. 외부 제3자가 이 코드를 가져가더라도 동일한 데이터 파이프라인 없이는 독립적으로 가동하기 어렵습니다.
  • 정기적 보안 감사 이력: SaaS 콘솔 소스 코드는 사내에서 지속적으로 정기 보안 감사를 받아왔기 때문에, 코드 공개만으로 즉각적인 원격 코드 실행 등의 치명적 제로데이가 발생할 가능성은 낮다고 CrowdSec 측은 설명했습니다.
  • 4개월간의 코드 진화: 2026년 5월에 복제된 코드와 9월 현재 프로덕션 환경에서 실행 중인 코드는 4개월 동안 대규모 기능 개선과 리팩터링을 거쳐 구조적 차이가 상당합니다.
  • 모니터링 강화: 과거 버전의 코드를 기반으로 한 비정상적 API 호출이나 잠재적 악용 시도를 탐지하기 위해 프로덕션 인프라 전반의 감시 체계가 상향 조정되었습니다.

이러한 정황은 코드베이스가 유출되었을 때 기업이 감당해야 할 실질적 피해의 범위를 판단하는 중요한 잣대가 됩니다. 하드코딩된 비밀 정보가 없었고, 아키텍처가 전용 인프라에 결합되어 있었으며, 지속적인 코드 진화가 이루어졌다는 조건들이 겹치면서 유출된 코드가 공격자의 손에서 치명적인 무기로 돌변하는 시나리오를 억제한 것입니다.

6. 고객 데이터와 횡적 이동 — PII 미저장 원칙과 자격 증명 전면 교체

보안 사고가 터졌을 때 고객과 시장이 가장 먼저 묻는 질문은 「내 데이터가 안전한가」입니다. CrowdSec의 이번 발표에서 가장 확고하게 선을 그은 대목 역시 사용자 및 고객 데이터의 안전성이었습니다. 성명서에 따르면 고객 데이터, 사용자 로그인 계정 및 비밀번호, 담당자 이름, 소속 조직 정보 등은 일절 유출되지 않았습니다.

이러한 결과는 우연한 행운이 아니라 **데이터 최소화 수집(Data Minimization) 아키텍처** 덕분입니다. CrowdSec은 서비스 설계 초기부터 고객 환경의 시스템 로그나 개인식별정보(PII)를 중앙 클라우드로 가져와 저장하지 않는 구조를 채택했습니다. 탐지와 차단은 각 고객 환경에 설치된 로컬 Security Engine에서 로컬로 수행되며, 중앙 네트워크로는 오직 공격 징후를 나타내는 IP 주소 평판 데이터(시그널)만이 익명화되어 전송됩니다.

  • 고객 데이터베이스 비접근: 유출된 저장소는 애플리케이션 소스 코드 저장소였으며, 실서버의 고객 데이터베이스나 사용자 세션 저장소에 대한 접근 권한이 포함되어 있지 않았습니다.
  • PII 부재: 시스템 자체가 고객의 개인정보나 원시 로그를 수집·보관하지 않으므로 유출될 수 있는 개인 데이터 자체가 원천적으로 부재했습니다.
  • 자격 증명 즉시 순환(Rotation): CrowdSec은 9월 16일 제보 접수 즉시 필요한 모든 토큰과 자격 증명을 교체해 추가 사고를 예방했다고 공식 발표에서 밝혔습니다.
  • 횡적 이동 흔적 부재: 사내 포렌식 조사 결과, 유출된 CI/CD 토큰을 이용해 내부 사내 네트워크로 추가 침입하거나 다른 클라우드 리소스로 횡적 이동을 시도한 정황은 발견되지 않았습니다.

결과적으로 이번 사건의 영향은 외부 고객이나 파트너사가 아닌 CrowdSec 내부 자산 영역으로 국한되었습니다. 개인정보 유출 신고나 고객 통지 의무가 발생하는 일반적인 엔터프라이즈 데이터 침해와는 구별되는 양상입니다.

7. 오픈소스 보안 엔진과 네트워크 효과 — 탐지 효율성이 유지되는 구조

보안 소프트웨어 벤더의 코드가 유출되었을 때 제기되는 또 다른 본질적인 질문은 「과연 그 탐지 제품을 앞으로도 믿고 쓸 수 있는가」입니다. 만약 탐지 로직과 시그니처, 우회 방어 알고리즘이 소스 코드의 비밀성에 의존하고 있었다면, 코드 노출은 제품의 방어력 상실을 의미할 것입니다.

하지만 CrowdSec 제품군의 핵심인 Security Engine은 이미 오픈소스로 전 세계에 공개되어 투명하게 운영되는 소프트웨어입니다. 이 엔진의 방어 능력은 비밀스러운 독점 알고리즘이 아니라, 전 세계 수만 대의 노드에서 수집되는 공격자 IP 주소들의 합의된 위협 인텔리전스, 즉 **분산 방어 네트워크의 네트워크 효과(Network Effect)**에서 비롯됩니다.

공격자가 SaaS 콘솔이나 클라우드 루틴의 소스 코드를 들여다본다고 하더라도, 전 세계 수많은 서버에서 실시간으로 생성되고 검증되는 거대한 차단 목록(Blocklist)과 위협 평판 데이터를 위조하거나 무력화할 수는 없습니다. 코드 자체는 누구나 복제할 수 있을지언정, 수년간 구축된 대규모 사용자 네트워크가 제공하는 방대한 위협 데이터의 크기와 처리 파이프라인의 실시간성은 코드 복제만으로 재현될 수 없기 때문입니다.

결국 이번 사고는 SaaS 콘솔이라는 부가 서비스의 관리 코드 유출일 뿐, 고객의 서버 최전선에서 트래픽을 방어하는 Security Engine 자체의 신뢰성이나 방어 효율성에는 실질적 타격을 주지 않는다는 기술적 결론에 도달합니다. 비공개 백오피스 계층과 공개 탐지 계층을 구조적으로 분리해 둔 아키텍처가 최악의 위기 속에서 핵심 제품의 무결성을 지켜낸 셈입니다.

8. 보안 조직의 상류 의존성 관리 — CI/CD 토큰의 최소 권한과 생애주기

CrowdSec의 이번 소스 코드 노출 사고는 특정 기업의 불운을 넘어 현대 소프트웨어 산업 전체가 직면한 공급망 보안의 취약점을 적나라하게 드러냅니다. 보안 기업조차도 제3자 라이브러리 오염을 피하지 못했다면, 일반적인 엔터프라이즈와 스타트업 환경은 동일한 공격에 훨씬 더 무방비로 노출되어 있을 가능성이 높습니다.

특히 주목해야 할 대목은 CI/CD 환경 및 개발자 도구에서 사용되는 **토큰의 권한 범위(Scope)와 유효 기간(TTL)** 문제입니다. 이번 사건에서 공격자가 손에 넣은 것은 비공개 저장소를 읽을 수 있는 API 키였습니다. 만약 이 키에 비공개 저장소 쓰기 권한이나 클라우드 인프라 배포 권한까지 부여되어 있었다면, 단순한 코드 유출을 넘어 악성 코드가 정식 릴리스에 심겨 고객들에게 배포되는 최악의 소프트웨어 공급망 중독 사고로 번졌을 것입니다.

  • 세분화된 토큰 권한 분리: 소스 코드를 읽는 권한, 코드를 푸시하는 권한, 패키지를 배포하는 권한은 단일 토큰에 부여되지 않아야 하며 각각 엄격히 분리된 역할 기반 접근 제어(RBAC)를 적용해야 합니다.
  • 단기 유효 자격 증명(Ephemeral Tokens): 장기간 유효한 정적 API 키 대신, 워크플로가 실행될 때만 발급되고 작업 종료 시 즉시 파기되는 임시 자격 증명(OIDC 연동 등)을 채택해야 합니다.
  • 의존성 격리와 빌드 환경 봉쇄: npm이나 pip, yarn 등의 패키지 설치 단계에서 외부 네트워크와 통신하는 임의의 포스트 인스톨 스크립트 실행을 제한하고, 신뢰할 수 있는 프라이빗 미러 레지스트리를 경유하도록 강제해야 합니다.
  • 외부 침해 모니터링 및 취약점 제보 수용: 사내 탐지만을 맹신하지 않고, 외부 보안 연구자나 전문 제보 창구를 공식 운영하여 침해 징후가 보고되었을 때 신속하게 대응할 수 있는 책임 있는 공개(Responsible Disclosure) 채널을 상시 유지해야 합니다.

보안은 완벽한 무결성을 달성하는 것이 아니라, 특정 계층이 뚫렸을 때 피해가 다음 계층으로 전이되지 않도록 방화벽을 세우는 심층 방어(Defense in Depth)의 예술입니다. CrowdSec의 사례는 토큰 권한이 읽기 전용에 머물렀고 고객 데이터가 격리되어 있었기 때문에 파국을 면할 수 있었습니다.

9. 검증 절차 — 조직의 서드파티 의존성 무결성과 자격 증명 감사

이 사고를 교훈 삼아 각 개발팀과 인프라 조직이 자체 시스템의 공급망 안전성을 직접 점검해볼 수 있는 구체적인 절차를 수립해야 합니다. 단순히 백신을 돌리는 수준을 넘어 서드파티 라이브러리의 유입 경로와 CI/CD 비밀 값의 노출 가능성을 체계적으로 추적해야 합니다.

  • 저장소 접근 토큰 전수 조사: GitHub, GitLab 등 소스 코드 호스팅 서비스에 등록된 모든 Personal Access Token(PAT), Deploy Key, OAuth App 연동 목록을 조회하고, 불필요한 비공개 저장소 읽기/쓰기 권한이 부여되어 있는지 검사합니다.
  • 빌드 스크립트의 네트워크 아웃바운드 차단: CI/CD 빌드 러너 환경에서 의존성 다운로드 이후 단계에서는 외부 임의 IP로의 아웃바운드 트래픽을 엄격히 차단하여, 악성 패키지가 환경 변수를 외부 C2 서버로 빼돌리지 못하도록 네트워크 정책을 구성합니다.
  • 락파일(Lockfile) 및 서명 검증 강제: package-lock.json, pnpm-lock.yaml 등의 무결성 해시 검증을 빌드 시 필수화하고, 검증되지 않은 상류 버전이 자동으로 업그레이드되어 배포 파이프라인에 진입하는 상황을 방지합니다.
  • 정기적인 자격 증명 자동 순환: 사람이 수동으로 키를 관리하는 방식을 탈피하여 30일 또는 90일 주기로 프로덕션 및 CI/CD 토큰이 자동 갱신되도록 수명 주기를 강제합니다.

소프트웨어 공급망 공격은 점점 더 교묘해지고 있으며, 정상적인 개발 라이브러리의 배포 채널을 장악하는 방식이 일상화되고 있습니다. 조직이 관리하는 모든 외부 의존성을 잠재적 침해 벡터로 간주하고 최소 권한의 원칙을 적용하는 것만이 상류 오염이 발생했을 때 사내 핵심 자산을 지키는 유일한 방파제입니다.

10. 확인하지 못한 것

본 문서에서 다룬 사실관계 외에 원문 발표 및 공개된 1차 자료를 통해 추가로 확인되지 않은 항목들은 다음과 같습니다.

  • Tanstack 컴포넌트의 구체적 패키지명 및 취약점 번호: CrowdSec의 공식 블로그 성명은 Tanstack 침해(Tanstack compromise)를 주요 공격 경로로 지목했으나, 침해된 컴포넌트의 정확한 패키지 이름, 배포된 버전 번호, CVE 식별자 등 세부 기술 내역은 본문에 명시되지 않았습니다.
  • 유출된 API 키의 정확한 형태와 부여 범위: 탈취된 키가 GitHub 개인 액세스 토큰(PAT)이었는지, GitHub App 설치 토큰이었는지, 혹은 CI/CD 서비스 전용 연동 키였는지에 대한 구체적인 메커니즘은 원문에 서술되지 않았습니다.
  • 300개 저장소의 개별 명칭 및 비공개 코드 라인 수: 노출된 300개 저장소(공개 130개 이상 포함) 가운데 유출 대상이 된 비공개 저장소들의 개별 프로젝트 명칭이나 구체적인 코드 라인 수, 커밋 이력 규모는 대외에 공개되지 않았습니다.
  • 제보자 Fuites Infos의 구체적 탐지 경위: 제보 플랫폼인 Fuites Infos가 어떤 다크웹 모니터링 경로 혹은 제3자 유출 데이터베이스를 통해 CrowdSec의 유출 코드를 최초로 확보하고 제보했는지에 대한 상세 배경은 원문에 기재되지 않았습니다.
