git 撤销决策表 - reset、revert、restore、checkout 该用哪一个

它在哪里，是否已经共享。这两个问题几乎就决定了命令

2026年9月1日 开发/基础设施

撤销之所以难，不是因为命令太多，而是因为这些选项长得很像，结果却完全不同。reset 删掉提交，revert 加上提交。restore 不碰分支，checkout 两件事都干。光看名字分不出来。

所以这篇文章不是命令清单，而是一套决策流程。先问两个问题，答案会把命令交到你手上。下面的例子全部是在为此新建的空临时仓库里实际执行的，贴出来的输出就是当时真实返回的内容。

本文中有些命令是无法撤销的破坏性操作。每一节都单独写明了「能不能救回来」。第一次接触的命令，建议先在 git init 建出来的空仓库里试，而不是在真正干活的仓库里试。

动手撤销之前要问的两件事

在手先动起来之前，要弄清楚的只有两件事。这两件事一定下来，可用的命令通常就收敛到一个。

  • 第一，要撤销的东西在哪里。是只在编辑器里保存了（工作区），还是已经 git add 过了（暂存区），或者已经 git commit 了（HEAD）。这一点定下来，就分出了用 restore 还是 reset
  • 第二，那个提交共享出去了吗。如果推送过，或者别人已经拉走了，那个提交就不再只属于你。这一点定下来，就分出了用 reset 还是 revert
  • 第三个问题其实是核对用的。这次改动有没有被提交过哪怕一次。如果没有，那么它一旦消失，任何命令都救不回来

大多数事故都是跳过第二个问题造成的。在本地用 reset --hard 删掉提交没有任何问题。同样的操作用在已经推送的提交上，持有那个分支的所有人的仓库都会错位。命令一样，代价不一样。这种不对称之所以不容易被看见，是因为你敲下命令的那一刻，Git 什么警告都不会给。后果要等到几天后，在别人的机器上，那个人像平常一样执行 git pull 时才第一次显形。

三个区域 - 工作区、暂存区、HEAD

在 Git 里，同一个文件的内容可以同时存在于三个地方：编辑器里保存的工作区、被 git add 放上去的暂存区，以及最后一个提交，也就是 HEAD。撤销类命令的性格差别，就在于它们碰这三者中的几个。

先看清三个区域各不相同时 git status 是什么样子，后面就好办了。下面有一个文件只是改了，一个是新建后 add 了，还有一个只是建出来放着。

$ cd /tmp/demo
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	new file:   b.txt

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   a.txt

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	c.txt

$ git status --short
 M a.txt
A  b.txt
?? c.txt

--short 输出里的两个字符位，正好就是那两个区域。左边是暂存区，右边是工作区。A  b.txt 表示只有暂存区发生了变化， M a.txt 表示只有工作区变了。两边都变就成了 MM。会读这两个字符，屏幕上其实已经写着该用哪个命令了。

贴心的是，git status 还在每一组下面写出了解法：要从暂存区拿下来用 git restore --staged，要丢掉工作区的改动用 git restore。下面这张表就是这个对应关系。

区域里面装着什么status --short 的显示撤销它的命令
工作区编辑器里保存的当前文件内容右位的 M、D，未跟踪则是 ??git restore <文件>，未跟踪则用 git clean
暂存区git add 放上去、将进入下次提交的内容左位的 M、A、Dgit restore --staged <文件>、git reset
HEAD（提交）已经记录下来的历史只能通过 git log 看到未共享用 git reset，已共享用 git revert

决策表 - 在哪里 乘以 是否共享

本文的核心就是这张表。纵轴是第一个问题，横轴是第二个问题。后面各节可以看作是把表里的每一格逐一执行并核对下来的记录。

要撤销的东西在哪里还只在我的仓库里已经推送出去了能救回来吗
工作区的修改（没有 add）git restore <文件>不适用 - 它从未被共享不能。没提交过就是终点
已放进暂存区的改动（add 过）git restore --staged <文件>不适用能。文件内容原封不动
最后一个提交的信息或组成git commit --amend不要用。改用 git revert能。旧提交留在 reflog 里
最后一个提交本身git reset --soft/--mixed/--hard HEAD~1不要用。改用 git revert HEAD提交能（reflog），工作区不能
多个提交git reset --hard <提交>git revert <较旧>..<较新>提交能（reflog）
未跟踪的文件先用 git clean -n 确认，再 -fd不适用不能。Git 从来不认识它们
选错了分支git switch -c <分支>，再把原分支 resetgit revert，然后在正确的分支上重做能

这张表最关键的一点是，reset 在「已经推送出去了」那一列里一次都没出现过。例外当然可以有，但那种例外要整个团队都同意并对齐时间点才成立，不是一个人能决定的事。

另一个值得注意的地方是，表里相当大一部分只靠第一列就定下来了。只要还在自己的仓库里，怎么折腾大体都行，因为被折腾到的只有自己，后面还有 reflog 兜着。而第二个问题的答案一旦变成「是」，可用的命令基本上只剩一个，理由并不是什么技术洁癖，而是那一行里其他命令都会在毫无预告的情况下把活儿丢到别人桌上。

git restore - 以文件为单位撤销

restore 是在 Git 2.23 里从 checkout 中分出来的。它管的事窄，反而更好用。Git 官方文档的 Reset, restore and revert 一节把它描述为「从暂存区或另一个提交恢复工作区中的文件」，紧接着就钉死了一句：这个命令不会更新你的分支。也就是说它不碰历史。

要紧的是，一个 --staged 就能让这条命令的性质完全变样。下面是同一个文件，暂存区里放着 beta，工作区里又加了 gamma，然后依次执行两种写法。

$ git status --short
MM note.txt

# 1) 只回退暂存区 - 文件内容不动
$ git restore --staged note.txt
$ git status --short
 M note.txt
$ cat note.txt
alpha
beta
gamma

# 2) 回退工作区 - 内容就是在这里消失的
$ git restore note.txt
$ git status --short
$ cat note.txt
alpha

第二条命令一执行，beta 和 gamma 就没了。它们一次都没被提交过，所以没有回头路。restore 顶着一个温和的名字，却属于破坏性命令，原因就在这里。反过来，加了 --staged 的第一条命令完全没有碰文件。

  • git restore --staged <文件> - 取消暂存。可以撤销。磁盘上的文件毫发无损
  • git restore <文件> - 丢弃工作区改动。不能撤销。未提交的内容会消失
  • git restore --staged --worktree <文件> - 两个区域一起来。执行一次 MM 就干净了
  • git restore --source=<提交> <文件> - 把那个提交时点的文件取过来，历史保持原样
  • 不小心用 rm 删掉的已跟踪文件，用 git restore <文件> 就原样回来了。这种用法是安全的

最后那种用法出场比想象中多：历史不动，只把某个文件回退到旧版本。在只有三个提交的仓库里取出上一版是这样的。

$ git log --oneline
1beb864 add delta
4fb8d79 add beta
96d2ca7 add note

$ git restore --source=HEAD~1 note.txt
$ cat note.txt
alpha
beta
$ git status --short
 M note.txt

分支还稳稳停在 add delta 上，只有文件回到了先前的状态，于是被算作已修改。在这里提交，就产生了一个「抵消用的新提交」，等于用手工在文件粒度上做了一次 revert。

git reset - 三种模式各退到哪一步

reset 是这三条命令里唯一会移动分支尖端的。官方文档的说法是「通过移动尖端来给分支增删提交」，因此提交历史会改变。三种模式的差别只在于移动 HEAD 之后，暂存区和工作区跟着走多远。

把同一个仓库建了三份，各自回退到 HEAD~1。提交依次是 C1 base、C2 feature、C3 oops，文件每次多一行。

$ git log --oneline
2152c39 C3 oops
3e571a5 C2 feature
44cb882 C1 base

$ git reset --soft HEAD~1
$ git log --oneline
3e571a5 C2 feature
44cb882 C1 base
$ git status --short
M  app.txt
$ cat app.txt
v1
v2
v3

--soft 只删掉了提交。C3 装的那些改动仍然原样躺在暂存区里，也就是左位的 M。想重写提交信息，或者把几个提交合成一个，用的就是这个模式。

$ git reset --mixed HEAD~1
Unstaged changes after reset:
M	app.txt
$ git log --oneline
17b85e8 C2 feature
d42f7bf C1 base
$ git status --short
 M app.txt
$ cat app.txt
v1
v2
v3

--mixed 连暂存区一起回退了，同样的改动落到了右位的 M。文件内容依然保留到 v3。省略选项的 git reset 就是这个模式，而不带任何参数直接敲 git reset 等于 --mixed HEAD，会把暂存的东西全部撤下来。

$ git reset --hard HEAD~1
HEAD is now at add35e9 C2 feature
$ git log --oneline
add35e9 C2 feature
453f0e3 C1 base
$ git status --short
$ cat app.txt
v1
v2

只有 --hard 真的改动了文件。status 是空的，v3 也没了。文档里那句「已跟踪文件的改动会被丢弃」，也只写在这一个模式下。三者之中，唯一可能让你损失未提交内容的就是它。

模式HEAD暂存区工作区执行后的 status --short可能失去的东西
--soft移动不动不动M  app.txt（左位）没有
--mixed（默认）移动回退不动 M app.txt（右位）只有暂存的组织方式
--hard移动回退回退空所有未提交的改动

git revert - 造一个抵消用的新提交

revert 和前两个性格不同，它文档的第一句话就是定义：给定若干已有提交，撤销这些补丁引入的改动，并记录下若干新提交来记载这件事。旧提交原地不动。历史不会变短，只会变长。

$ git log --oneline
e4285bf C3 enable debug
b1fe989 C2 add timeout
f001827 C1 add config

$ git revert --no-edit HEAD
[main 83f6fc6] Revert "C3 enable debug"
 1 file changed, 1 deletion(-)
 delete mode 100644 debug.txt

$ git log --oneline
83f6fc6 Revert "C3 enable debug"
e4285bf C3 enable debug
b1fe989 C2 add timeout
f001827 C1 add config
$ git status --short

C3 还在，上面叠了一个 Revert "C3 enable debug"。结果文件回到了 C2 时的样子，但记录上「做过」和「撤回」两件事都留下来了。在需要审计追踪的仓库里，这不是累赘而是优点。

不过 revert 并不总是安静收场。如果要撤销的提交之后还有别的提交动过同一处，就会冲突。在一个不断修改同一文件相邻行的历史里撤销中间那个提交，结果是这样。

$ git revert --no-edit HEAD~1
Auto-merging config.txt
CONFLICT (content): Merge conflict in config.txt
error: could not revert 17a5abe... C2 enable debug
hint: After resolving the conflicts, mark them with
hint: "git add/rm <pathspec>", then run
hint: "git revert --continue".
hint: You can instead skip this commit with "git revert --skip".
hint: To abort and get back to the state before "git revert",
hint: run "git revert --abort".

$ git status --short
UU config.txt

$ git revert --abort
$ git log --oneline
08823c4 C3 enable cache
17a5abe C2 enable debug
9b96f25 C1 add config
$ git status --short

这里值得留意的是 git revert --abort。在冲突当中，这一行就能把仓库完整地退回到开始之前的状态。revert 即便失败也留有安全的退路，是本文里最好撤销的命令。

  • git revert <提交> - 造一个新提交。可以撤销。把那个新提交再 revert 一次就复原了
  • 加上 --no-edit 就用默认信息直接提交，不会打开编辑器
  • 冲突时会停下。--abort 全部取消，--continue 解决后继续，--skip 跳过那一个提交
  • 要撤销多个时给出范围，写成 git revert <较旧>..<较新>，会从最新的开始依次处理
  • 开始时工作区必须是干净的，这是文档里写明的前提条件

改写已共享的提交会给别人带来什么

「推送过的提交要用 revert」这句话常听到，但没亲历过就不容易体会。建了一个仓库，再克隆一份充当同事那边，然后用两种方式撤销同一个失误。下面的输出里只把仓库路径换成了 /tmp/demo/upstream。

# 同事的克隆 - 已经拿到了那个有问题的提交
$ git log --oneline
97b65d9 C2 bad change
2135f94 C1 base

# 我这边执行 revert
$ git revert --no-edit HEAD
[main 7085b16] Revert "C2 bad change"
 1 file changed, 1 deletion(-)

# 同事执行 pull
$ git pull
From /tmp/demo/upstream
   97b65d9..7085b16  main       -> origin/main
Updating 97b65d9..7085b16
Fast-forward
 app.txt | 1 -
 1 file changed, 1 deletion(-)

一行 Fast-forward 就结束了。同事什么都没做，也没有冲突。这次换成在同样的情形下把提交删掉再重建。

# 同事的克隆 - 同样的起点
$ git log --oneline
689d5e6 C2 bad change
f43e101 C1 base

# 我这边删掉 C2 并好好重做一遍
$ git reset --hard HEAD~1
HEAD is now at f43e101 C1 base
$ printf 'v1\ngood change\n' > app.txt
$ git add app.txt && git commit -q -m "C2 good change"
$ git log --oneline
2727247 C2 good change
f43e101 C1 base

# 同事执行 pull
$ git pull
From /tmp/demo/upstream
 + 689d5e6...2727247 main       -> origin/main  (forced update)
Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
Automatic merge failed; fix conflicts and then commit the result.

$ git status --short
UU app.txt
$ cat app.txt
v1
<<<<<<< HEAD
bad change
=======
good change
>>>>>>> 272724744769a515b2d1fc26330c4883201016a3

目的一样，最终状态一样，同事那边的结果却完全不同。出现了 forced update，冲突标记直接嵌进了文件里。我省下的那一个提交，变成了按团队人数计算的一次次冲突解决，而且那些人根本不知道发生了什么。

强制推送（git push --force）会在这上面再加一层更大的风险：如果在我最后一次拉取之后有人推了新提交，那些提交也会被一并抹掉。--force-with-lease 只在远端的当前值和我所知的值一致时才推入，可以挡住这类事故，但它不是「可以覆盖」的许可。在共享分支上，两者都不是默认选项。

git checkout 为什么让人混淆

checkout 难用，是因为这条命令把两件轻重完全不同的事放在了一个名字下。移动分支和恢复文件的危险程度天差地别，名字却一样。于是结果取决于参数，而名字一撞就分不清到底是哪一边。

故意让它撞一次，结果就很清楚了。在一个有 app.txt 这个文件的仓库里建一个叫 app.txt 的分支，改一下文件，然后执行 checkout。

$ git branch app.txt
$ printf 'v2\n' > app.txt
$ git checkout app.txt
M	app.txt
Switched to branch 'app.txt'
$ git branch --show-current
app.txt
$ cat app.txt
v2

# 2.23 之后：名字撞了，含义也只有一个
$ git switch app.txt
Switched to branch 'app.txt'
$ git restore app.txt
$ cat app.txt
v1

本想撤销文件改动的人，是过后才发现分支被换掉了。Git 2.23 的发行说明正面处理了这个问题：为了把「检出分支以推进其历史」和「从索引或树对象中检出路径」这两件事从单一的 git checkout 里拆出来，引入了 switch 和 restore。

checkout 的另一副面孔出现在你直接指定提交的时候。去到一个提交而不是分支，就进入了 detached HEAD。在这里提交，会产生不属于任何分支的提交。

$ git checkout HEAD~1
Note: switching to 'HEAD~1'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.
...
HEAD is now at f91e4ef C1 base

$ git status | head -2
HEAD detached at f91e4ef
nothing to commit, working tree clean

$ git switch main
Previous HEAD position was f91e4ef C1 base
Switched to branch 'main'

这个状态本身并不危险。正如提示所说，它是个适合四处看看和做实验的位置。问题在于把在这里做的提交留在原地就走掉。那时 reflog 里当然还有，但一开始就用 git switch -c <名字> 起个名字要省事得多。

git reflog - 被删提交的活路

本文如果只记住一节，就记这一节。用 reset --hard 删掉的提交多半还能救回来，因为 Git 把 HEAD 走过的每一个位置都写进了 reflog。下面是在三个提交的仓库里删掉两个再恢复的完整过程。

$ git log --oneline
78b8ce0 C3 more work
f1acddb C2 two days of work
7810949 C1 base

# 事故
$ git reset --hard HEAD~2
HEAD is now at 7810949 C1 base
$ git log --oneline
7810949 C1 base
$ cat work.txt
v1

# 救援：被删的提交就在这里
$ git reflog
7810949 HEAD@{0}: reset: moving to HEAD~2
78b8ce0 HEAD@{1}: commit: C3 more work
f1acddb HEAD@{2}: commit: C2 two days of work
7810949 HEAD@{3}: commit (initial): C1 base

$ git reset --hard HEAD@{1}
HEAD is now at 78b8ce0 C3 more work
$ git log --oneline
78b8ce0 C3 more work
f1acddb C2 two days of work
7810949 C1 base
$ cat work.txt
v1
v2
v3

HEAD@{1} 的意思是「上一步 HEAD 所在的位置」，那正是执行 reset --hard 之前的地方。知道这一点，对 reset --hard 的恐惧就少了一半。剩下的一半在下一节。

上一个位置还有名字可用。ORIG_HEAD 指向 reset、merge 这类大动作之前的 HEAD。只想看某个分支的移动，就用 git reflog show <分支>。

$ git reset --hard HEAD~2
HEAD is now at f1c8944 C1
$ git rev-parse --short ORIG_HEAD
4d26ce7
$ git reset --hard ORIG_HEAD
HEAD is now at 4d26ce7 C3

$ git reflog show main
4d26ce7 main@{0}: reset: moving to ORIG_HEAD
f1c8944 main@{1}: reset: moving to HEAD~2
4d26ce7 main@{2}: commit: C3
b8efd2c main@{3}: commit: C2
f1c8944 main@{4}: commit (initial): C1
  • reflog 是每个仓库本地的。克隆不会带走它，你也无法用自己的 reflog 去救别人的事故
  • 它不是永久保存。按配置文档，gc.reflogExpire 的默认值是 90 天，处理从当前尖端不可达条目的 gc.reflogExpireUnreachable 是 30 天
  • 文档里也写了后者更短的理由：这类条目通常由 commit --amend 或 rebase 产生，因此被认为可以更早清掉
  • 也就是说，「回头去 reflog 里找」撑不起以月为单位的计划。发现事故就当天处理掉

救不回来的东西

reflog 是记录提交的装置，不是记录工作区的装置。所以从未被提交过的改动，用任何命令抹掉都不会回来。在改了一小时却没提交的文件上跑一次 reset --hard，结果是这样。

$ cat draft.txt
committed line
an hour of work that was never committed
$ git status --short
 M draft.txt

$ git reset --hard HEAD
HEAD is now at 371a5ec C1 base
$ cat draft.txt
committed line

$ git reflog
371a5ec HEAD@{0}: reset: moving to HEAD
371a5ec HEAD@{1}: commit (initial): C1 base

$ git fsck --lost-found
$

reflog 里只有一个提交和一条 reset 记录，git fsck --lost-found 也什么都拿不出来，因为那一小时的内容 Git 从来没见过。这里有一个例外值得知道：如果你 git add 过，那份内容就已经作为对象存下来了，fsck 才有东西可找。把东西放进暂存区的习惯，常常在这种时候变成安全网。

命令它抹掉什么能怎么找回先做什么
git reset --hard提交，加上未提交的改动提交靠 reflog，改动没有git stash push -u
git restore <文件>那个文件未提交的改动没有用 git diff 看清将要消失的内容
git clean -fd未跟踪的文件和目录没有用 git clean -nd 读一遍清单
git commit --amend上一个提交（被替换掉）reflog确认是否已经推送
git revert什么都不抹再 revert 一次把工作区弄干净

git stash - 危险命令之前的一行

避免上一节那种事故，最便宜的办法是 stash。它把还没整理到可以提交的改动暂时挪开，让工作区变干净。挪开的内容会作为 Git 对象保存下来，因此安全程度和提交是一个级别的。

$ git status --short
 M tracked.txt
?? newfile.txt

$ git stash push -m wip
Saved working directory and index state On main: wip
$ git status --short
?? newfile.txt

# 新建的文件没有被收进去，需要加 -u
$ git stash push -u -m wip2
Saved working directory and index state On main: wip2
$ git status --short
$ git stash list
stash@{0}: On main: wip2

$ git stash pop
...
Dropped refs/stash@{0}

关键在于第一次 stash push 之后 newfile.txt 还留在那里。stash 默认不收未跟踪的文件。以为「已经 stash 了所以安全」，接着跑 reset --hard 或 clean -fd，消失的恰恰就是刚建好的文件。把 -u 变成习惯更稳妥。

  • git stash push -u -m <备注> - 把已跟踪文件和新文件一起收走。留个备注，以后在清单里才认得出来
  • 用 git stash list 查看，用 git stash pop 取出并删除，用 git stash apply 取出并保留
  • stash 自己也有 reflog。万一误 drop 了，还有机会从 git fsck 或先前的记录里找回来
  • 但它不是长期仓库。打算放好几天的东西，还是提交到一个临时分支上更安全

git clean - 没有退路的删除

clean 是本文里最简单也最危险的命令。文档的说法是「递归删除不在版本控制之下的文件，以清理工作区」。因为 Git 从来没跟踪过它们，删掉之后 Git 内部不会留下任何痕迹。

$ git status --short
?? build/
?? notes.md
?? out.log

# -n 不删任何东西，只列清单
$ git clean -n
Would remove notes.md
Would remove out.log

# 目录要加 -d 才看得到
$ git clean -nd
Would remove build/
Would remove notes.md
Would remove out.log

$ git clean -fd
Removing build/
Removing notes.md
Removing out.log
$ ls
keep.txt

要留意 -n 和 -nd 结果的差别：不加 -d，目录根本不会出现在清单里。只看了 -n 就放心执行 -fd，删掉的会比你以为的多。正确顺序只有一个：先用 -nd 看，读一遍清单，然后才是 -fd。

-x 在这基础上又进一步，连 .gitignore 忽略的文件也一起删。清理构建产物时很方便，但忽略清单里常常放着 .env 这类本地配置。它们也会一起没了。

提交信息写错，或者漏了文件

提交完立刻发现的失误，基本上就两种：信息里有错字，或者该放进去的文件漏了。两种都能用 git commit --amend 一条解决。它不是往上叠一个新提交，而是用一个新提交把上一个替换掉。

$ git log --oneline
d8ed825 fix bugg
689816b C1 base

# 1) 只改信息
$ git commit --amend -m "fix bug"
$ git log --oneline
ca1558d fix bug
689816b C1 base

# 2) 补上漏掉的文件
$ git add c.txt
$ git commit --amend --no-edit
$ git show --name-only --oneline HEAD
5ef662d fix bug
b.txt
c.txt

$ git reflog
5ef662d HEAD@{0}: commit (amend): fix bug
ca1558d HEAD@{1}: commit (amend): fix bug
d8ed825 HEAD@{2}: commit: fix bugg
689816b HEAD@{3}: commit (initial): C1 base

关键是哈希每次都在变：d8ed825 → ca1558d → 5ef662d。amend 不是在修改提交，而是造一个新的换上去。所以用在已经推送的提交上，就会原样重现上一节那个 forced update 的局面。原则只有一句：只在推送之前用。

想把 amend 本身撤掉，就用 reflog。在上面的状态下执行 git reset --hard HEAD@{1}，会精确回到补文件之前的 ca1558d。

提交到了错误的分支

在 main 上干活并且顺手提交了，这种情形很常见。这时候手先动起来，往往就是用 reset --hard 把提交毁掉从头再来，其实没有必要。提交原地不动，挪动标签就行了。

$ git log --oneline --decorate
501da69 (HEAD -> main) C2 feature work
032adf6 C1 base

# 1) 就在当前位置新建分支 - 提交会跟过来
$ git switch -c feature
Switched to a new branch 'feature'
$ git log --oneline --decorate
501da69 (HEAD -> feature, main) C2 feature work
032adf6 C1 base

# 2) 回到 main 往回退一格
$ git switch main
$ git reset --hard HEAD~1
HEAD is now at 032adf6 C1 base
$ git log --oneline --decorate
032adf6 (HEAD -> main) C1 base
$ git log --oneline --decorate feature
501da69 (feature) C2 feature work

顺序很重要。先建分支，再把 main 退回去。反过来做，提交就不属于任何分支了，要找回来就得去翻 reflog。而且这个流程只在 main 还没推送时才用。如果已经推送了，就用 revert 抵消掉，再到正确的分支上重新提交。

还没提交的话更简单：切换分支时未提交的改动会跟着你走，而在跟不过去的情况下，Git 会自己停下来。

# 提交之前直接切过去就行
$ git status --short
 M app.txt
$ git switch -c feature
Switched to a new branch 'feature'
$ git status --short
 M app.txt

# 如果目标分支动过同一个文件，Git 会拦住
$ git switch other
error: Your local changes to the following files would be overwritten by checkout:
	app.txt
Please commit your changes or stash them before you switch branches.
Aborting

这个拒绝是一项功能。switch 和 checkout 在必须覆盖未提交改动的情况下会自行停住，照提示去提交或 stash 就行。顺带一提，加上 --discard-changes 这层保护就关掉了，改动会消失。这个选项的名字算是诚实的。

执行环境与复现方法

本文的所有输出都是在下面这个环境里实际执行得到的。提交哈希和时间每次运行都不一样，那部分不会复现。

$ git --version
git version 2.48.1.windows.1

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

操作系统是 Windows 10（版本 19045），shell 是 Git for Windows 自带的 Git Bash（MSYS2）。命令本身和 Linux、macOS 上一样，但贴出来的提示文字会随 Git 版本变化。尤其是 git status 推荐的命令，早期版本是 git reset HEAD <文件>，现在是 git restore --staged。旧教程和屏幕对不上，多半就是这个原因。

  • 复现并不难：在空目录里 git init，用几个文件做三个左右的提交，本文的例子基本上就能照着跑
  • 不要在真正干活的仓库里练习。本文有一半是删文件的命令
  • 执行过程中碰到过一件事：在路径非常深的目录里，Git 写不了对象，停在 unable to write file ...: Invalid argument。原因是 Windows 的路径长度限制，换到短路径就立刻好了
  • 同样的情况下试着打开 core.longpaths，这个错误并没有消失。在 Linux 和 macOS 上不会遇到这个问题

小结 - 从症状到命令

最后放一张从症状直接到命令的表。前面的决策表讲的是原理，这张是拿来练手感的。

当前情形该用的命令文件内容会消失吗
改了文件，想当作没改过git restore <文件>会消失
add 错了git restore --staged <文件>不会
想把 add 全部取消git reset不会
提交信息有错字（推送之前）git commit --amend -m "..."不会
漏了一个文件就提交了（推送之前）git add 之后 git commit --amend --no-edit不会
想撤销最后一个提交但保留内容git reset --soft HEAD~1不会
想把最后一个提交整个抹掉（推送之前）git reset --hard HEAD~1会消失
撤销已经推送出去的提交git revert <提交>不会
不小心删了文件（已提交的文件）git restore <文件>不会
用 reset --hard 把提交删掉了git reflog 之后 git reset --hard HEAD@{n}提交会回来
想清理构建残留先 git clean -nd 确认，再 -fd会消失
在错误的分支上提交了git switch -c <分支>，再把原分支 reset --hard HEAD~1不会

说到底还是回到那两个问题：它在哪里，以及你共享过没有。前一个问题在 restore、reset、clean 之间做选择，后一个问题把 reset 和 revert 分开。这之上还有 reflog 这张安全网，而这张网够不到的地方，就是从未被提交过的改动。想明白这些，剩下的大多是举一反三。

如果更关心查历史那一侧的命令，被低估的 Git 历史命令 从实务角度整理了 bisect、log -S 和 reflog；想从基础重新过一遍，Git基础 - 版本控制入门 是起点。

未能确认的部分

  • 所有例子都只在 Git 2.48.1 上执行过。其他大版本的提示文字和默认行为可能不同，尤其是 git pull 遇到分叉历史时的默认处理方式，这一块历来有过变化
  • 没有在 Linux 或 macOS 上跑同样的脚本做对照。命令含义相同，但路径长度限制是 Windows 特有的，换一种 shell，例子里的 printf 写法也可能要调整
  • 远程仓库的实验用的是同一块磁盘上的本地副本。在真实的服务器或托管服务上，受保护分支的设置可能会直接拒绝强制推送，这种行为没有验证过
  • git restore 和 git switch 标注为实验性这一点，是在 2.48.1 随附的文档里确认的。在线的最新文档中没有确认到同样的措辞，因此可能随版本发生了变化
  • reflog 的保留期限是照抄配置文档里写的默认值，并没有真的观察到 90 天、30 天过去之后条目消失的过程
  • 关于用 git fsck 找回只进过暂存区的内容，本文只是按原理写下来，并没有实际执行验证
