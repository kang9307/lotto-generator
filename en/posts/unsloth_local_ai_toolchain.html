Running and Training Models Locally - What It Demands and What It Gives Back

Inference takes thirty minutes. Training stalls on data.

2026-08-16 Dev & Infra

Intro: Thirty minutes to install, and then the real problem

Put a machine with one GPU in front of you, install a single app, and within thirty minutes a model is answering questions. That part genuinely got easy. Where Python versions, CUDA toolkits, and drivers used to tear each other apart, there is now an installer.

The problem starts right after. The moment someone says let us train it on our own data so it answers our way, the difficulty jumps not one notch but two. And nearly all of that increase comes from data, not from the GPU.

Tools that bundle local execution, training, and agent connectivity into one app have multiplied lately. Unsloth Desktop, released in early August 2026, is one of them, and it is the starting point for this piece. What follows, though, is not a feature list for any particular app. It is what the decision to move models onto your own hardware actually charges you, and what it pays back. Tools change; this calculation does not.

Choosing a runtime stack and picking a GGUF quantization format were covered in Running LLMs Locally in 2026, and the buying matrix lives in the Local LLM Hardware Selection Guide. Rather than repeat those, this focuses on the requirements that appear only when you cross from inference into training.

1. Three reasons to go local - their weights are not equal

Most arguments for local list three things side by side: data never leaves, no per-call price, works offline. All three are true. But they carry wildly different weight, and in most situations exactly one is decisive while the other two are garnish.

  • Data cannot leave — this axis becomes overwhelming only when a contract or regulation explicitly forbids it. In that case local is the only answer no matter how bad the other conditions are. Plenty of teams also go local with no such clause, just on unease. That is a valid choice too, but what you pay for it is operational burden, and you should know that going in
  • Per-call cost — the advantage exists only if the hardware stays busy. For something used a few times a day, the price of the GPU and the electricity are pure loss
  • Offline — decisive only where there genuinely is no network: air-gapped sites, vessels, field equipment. An office whose internet occasionally drops does not qualify

A fourth axis gets skipped constantly: latency. The network round trip disappears, but your machine's throughput becomes the hard ceiling. Run a large model on a consumer GPU and there are clearly regions where it is slower than the API, and teams that miss this end up reversing the migration.

So: if a no-export clause exists, no further calculation is needed. If it does not, every remaining axis collapses into one question — how high is utilization? The separate question of whether internal data may go into an external model at all is worked through in Can You Put Company Data Into an LLM?.

2. VRAM sets the ceiling - inference and training use different formulas

What is possible locally is mostly decided by one number: memory capacity. And here is where expectations go wrong. A model you can run is not necessarily a model you can train, because the terms in the equation are different.

Inference loads weights into memory and reads them. So the weights are nearly all of it, plus a KV cache that scales with context length. Training stacks gradients and optimizer states on top. Multiple copies of a value exist per parameter, so the same model suddenly needs several times the memory.

PurposeBytes per param (approx)For an 8B modelWhat else is added
Inference (4-bit class)~0.5 bytes~4GBKV cache (scales with context)
Inference (8-bit class)~1 byte~8GBKV cache
Inference (16-bit)~2 bytes~16GBKV cache
Adapter training (4-bit base)0.5 base + adapterroughly 6-12GBActivation buffers (batch, length)
Full fine-tune (mixed-precision Adam)~16 bytes~128GB rangeActivation buffers, master weights

The last two rows are the fork in the road. The 16 bytes for a full fine-tune is the usual arithmetic of 4 for weights, 4 for gradients, 8 for two Adam moments, and activation buffers push it higher in practice. What 128GB for an 8B model means is unambiguous: a plan to full fine-tune on one consumer GPU is already dead at the arithmetic stage.

# Conceptual example - arithmetic for ruling candidates out.
# These are not measured figures from any specific build.
def rough_bytes(params_b, mode):
    per_param = {
        "infer_4bit": 0.5,
        "infer_16bit": 2.0,
        "full_finetune_adam": 16.0,   # weights + gradients + optimizer states
    }[mode]
    return params_b * 1e9 * per_param / (1024 ** 3)   # GiB

print(rough_bytes(8, "infer_4bit"))          # about 4
print(rough_bytes(8, "full_finetune_adam"))  # about 119

Arithmetic filters candidates; it does not confirm them. Batch size and sequence length move real usage a lot through the activation buffers. Use the calculation to delete the obviously impossible combinations first, then confirm what survives by running a single step. Passing the arithmetic and then failing at runtime is common. Failing the arithmetic and then passing at runtime does not happen.

3. What quantization changes - and what shifts in training

Quantization represents weights in fewer bits. Three things change, and the whole trick is that they do not all move in the same direction.

  • Memory and speed — both improve predictably. Memory drops roughly in proportion to bit width, and since LLM decoding is memory-bandwidth bound (every token sweeps the weights), fewer bytes to read means faster output. The speed gain only materializes if the kernels are optimized for that bit width
  • Quality — this is the one that moves the other way, and how far it drops depends on the task. Casual chat and summarization tolerate it well, while long reasoning chains, code generation, and precise numeric recall break first
Bit widthMemoryPerceived qualityWhere to use itAs a training base
16-bitbaselinebaselineQuality reference, deployment after adapter mergePossible, but memory does not allow it
8-bit classhalfUsually hard to distinguishStepping down one notch while protecting qualityWorkable
4-bit classquarterTask dependentEveryday chat, summarization, classification. The de facto local standardStandard pairing for adapter training
3-bit and belowone fifth or lessVisibly unstableOnly when you must force a large model onto small hardwareNot recommended

One thing shifts in training. In inference, quantization is a trade: give up some quality, gain memory. In training it is closer to the mechanism that makes an impossible thing possible. Freeze the base weights at 4-bit and stack small trainable matrices on top. The QLoRA paper reported finetuning a 65B parameter model on a single 48GB GPU with full 16-bit finetuning task performance preserved, using three components: the 4-bit NormalFloat data type, double quantization that quantizes the quantization constants, and paged optimizers to manage memory spikes.

Note that the figure comes from that paper's models and settings. Change batch size or sequence length and it does not transfer. When reading someone else's numbers, check first whether model size, quantization method, sequence length, and batch size are stated alongside. If they are not, take the direction and discard the magnitude.

4. What CPU-only can and cannot do

Whether you can skip the GPU has to be answered per use case. The conclusion flips entirely depending on where the bottleneck sits.

4.1 Practical on CPU

  • Interactive use of small models — 3B class and below at 4-bit fits in system memory. Responses are slow but not unusable
  • Embeddings and non-urgent batch work — small models that batch well put the CPU at less of a disadvantage. If you can start a job at night and read results in the morning, speed becomes secondary
  • The entire data preparation pipeline — collection, cleaning, format conversion, deduplication. This is most of the working hours in a fine-tuning project, and it needs no GPU at all

4.2 Effectively impossible on CPU

  • Interactive response from mid to large models, and long contexts — the memory bandwidth gap shows up directly as tokens per second. Bandwidth is the wall, not capacity, and even reading the prompt in becomes noticeably slow
  • Training — possible, but the wall clock stretches into days or weeks, which removes it from the list of real options

That yields one genuinely useful conclusion: do the data preparation before you buy a GPU. That stage runs entirely on the laptop you already have, and it is usually where the project's fate is decided anyway.

5. Inference is easy - fine-tuning is 80 percent data prep

When execution and training sit side by side in the same app, they look comparably hard. They are entirely different kinds of work.

Inference is a problem with a known answer. Download the model file, pick a quantization that fits the machine, run it. When it breaks, the causes are finite and most are searchable. Half a day.

Fine-tuning is not. The training command is one line, and modern tools have turned even that into a button — everything that matters happens before you press it.

  • Collection and selection — the examples are scattered across ticket systems, wikis, chat, and someone's head. And not every past case is a good case. Train on bad handling and you get a model that handles things badly, consistently
  • De-identification — personal data and contractual secrets have to be stripped. If data protection was the reason for going local, skipping this step destroys the justification
  • Alignment and splitting — inputs and outputs must lock together as pairs, and operational records rarely arrive in that shape. Then split train and evaluation without overlap. Overlap raises the score and leaves real performance untouched
  • Writing the evaluation set — this is the actual deliverable, which is worth repeating below
// Conceptual example - the typical shape of an instruction/response pair.
// Field names and schemas differ per tool; follow the docs for whatever you use.
{"messages": [
  {"role": "system",    "content": "You are an internal infrastructure operator."},
  {"role": "user",      "content": "The nightly batch failed at 3am. Where do I start?"},
  {"role": "assistant", "content": "1) Job log exit code 2) Whether the upstream job finished 3) ..."}
]}

The last item is what matters most. Write the evaluation set first. Without a way to judge whether things improved or degraded after training, the fine-tune becomes an experiment with no readable result. And if you get stuck writing fifty evaluation questions, the task is not ready to be fine-tuned, because you have not yet defined what a good answer is. The break-even and total cost structure of fine-tuning is worked out separately in When a $500 Fine-Tune Beats a Frontier API.

6. What LoRA solves and what it does not

Local training became realistic because not training everything became standard practice. LoRA freezes the original weights and trains only two update matrices produced by low-rank decomposition. In transformers these typically attach to attention blocks, and the rank r sets their size. When training finishes, the adapter weights can be merged back into the original as a single model, and after merging inference latency does not increase.

6.1 Works well - how the model speaks

  • Locking output format — always the same JSON schema, always the same field order. Narrow repetitive work like classification and extraction, finished without calling a large model, comes from here
  • Tone and vocabulary adaptation — internal document voice, customer-facing phrasing, the terms your industry actually uses. Anything where consistency is the quality
  • Refusal boundary tuning — internalizing where to answer and where to hand off to a human

6.2 Works poorly - what the model knows

  • Factual knowledge injection — trying to memorize a hundred internal policies. Even when it appears to work there is no way to verify coverage, and trained knowledge cannot point at a source
  • Frequently changing information — price lists, stock levels, org charts. The moment retraining is required per update, the design is already wrong
  • Fundamental reasoning gains — an adapter will not make the base model solve what it cannot solve

The criterion reduces to one line. If what you are changing is how it speaks, train. If it is what it knows, retrieve. These are not exclusive; fixing format with an adapter while attaching facts through retrieval is usually the combination that works best.

An underrated property of adapters. They are tiny relative to the base, so you can keep several and swap them in. Different adapters per team or per task sharing one base is a viable topology. Full fine-tuning duplicates the entire model per task, so that topology never forms. In a local environment where storage and memory are tight, that difference matters more than it first appears.

7. One box for every tool - the gain and what gets hidden

Having execution, training, data prep, agent wiring, and API serving in a single app is genuinely good. But abstraction is not free, and using it knowing what it hides gives different results than using it blind.

7.1 What you gain

  • No more version hell — the days spent reconciling drivers, runtimes, and libraries vanish. That alone lowers the barrier dramatically
  • Time to first success — you learn quickly whether this works at all, and killing a doomed project early is a win. The pre-wired path from trained model to serving and evaluation contributes here too
  • Quality of defaults — a well-built tool's default hyperparameters generally beat what a newcomer picks by hand

7.2 What gets hidden

  • Which values were actually used — rank, learning rate, schedule, target modules. When results look wrong and you cannot see these, you cannot narrow the cause
  • Where it broke — an integrated tool's error usually gets caught one layer up, masking the real cause underneath. And when training starts with one click, you lose all sense of whether this is a two-hour job or a two-day one
  • Portability — build results on settings that only exist inside that tool and moving environments means starting over

So the practical test is this: check whether the output lands in a standard format. If training produces GGUF or safetensors that anything outside the tool can read, the tool is a convenience layer, not a prison. If the output is app-specific, the time you saved now gets repaid later with interest. And it is worth touching the lower layer by hand at least once. Not every time — but you cannot notice that automation went wrong when you do not know what was automated.

8. Open weight is not open source

This section is legal rather than technical, and it produces the problem that gets discovered latest and reversed hardest in local projects. Being able to download weights and being free to use them are completely different things.

Llama is the canonical case. Its community license requires the following.

  • Products or services exceeding 700 million monthly active users in the preceding calendar month must request a separate commercial license from Meta
  • Built with Llama has to be displayed prominently on the website, UI, or documentation
  • Distributed derivative models must have a name beginning with Llama, the copyright notice must be retained, and a separate acceptable use policy applies

The Open Source Initiative states explicitly that these terms do not meet the Open Source Definition. The cited failures are restricting the freedom to use the model for any purpose, discriminating against users, and restricting fields of endeavour. OSI calls this framing open washing.

Not every open-weight model looks like this, of course. Some families ship under Apache 2.0 or MIT with far looser conditions. The point is that lineages differ completely, which is exactly why it has to be checked each time. The technical side of that gap is covered in Open-Weight vs Closed LLM Gap.

8.1 Three layers to verify

  1. The tooling license — terms on the execution and training framework itself. Mixed licensing is common, and which clauses apply depends on which components you use
  2. The model weight license — commercial use, derivative distribution, attribution duties, field restrictions. A permissive tool does not drag the model along with it
  3. Rights over the training data — your legal basis for processing the internal documents and customer records you feed in. Keeping data off the network does not automatically create a right to train on it

The third gets skipped wholesale precisely because everything is local. The feeling that it is fine because it happens inside my own server is not a legal basis.

9. When local is the wrong answer

By this point the decision axes are clear. The table below maps conditions to conclusions.

SituationRecommendedWhy
Contract or regulation forbids data exportLocalThere is no alternative regardless of other costs
Sites with genuinely no networkLocalThe alternative does not exist
Narrow repetitive task with high utilizationLocal + adapterThe only combination where the cost advantage is real
Current frontier quality drives the outcomeAPIOpen weights lag and local cannot close the gap
Usage is irregular and low volumeAPIDepreciation and electricity become pure loss
No named operations ownerAPIIn six months you have a server nobody can touch
Early exploration with shifting requirementsAPI firstLocal investment before the target is fixed becomes sunk cost
You cannot state why local in one sentenceAPIWith no reason, all that remains is the operational burden

One axis does not fit in the table. Operational burden grows over time. At the start you run one model; six months later driver updates, model swaps, adapter retraining, disk cleanup, and access control are all somebody's job. That line item is almost always missing from the cost comparison made at adoption time.

10. Current status of the tools, and what was not verified

Status as of 2026-08-16. Labels in this space change often, so read this together with the date.

  • Unsloth Desktop, the starting point for this piece, is labeled Beta in its official documentation. The version string shown in the repository, 0.1.800-beta, is likewise a beta designation
  • Supported platforms are listed as macOS, Windows, Linux, and WSL, with a Docker path available. Hardware coverage mentions NVIDIA, AMD, and Intel GPUs plus Apple Silicon, with CPU noted for chat and data work. Training output can be exported to GGUF and 16-bit safetensors, which satisfies the portability test from the previous section
  • Licensing is dual: Apache 2.0 for the core package, AGPL-3.0 for the studio UI and certain optional components. If you plan to offer AGPL components as a service, read those clauses directly

What was not verified is collected below. No statement in the body rests on any of these.

  • Vendor performance figures — claims like 2x faster training, 70% less VRAM, up to 12x on MoE, and 500K-context training of a 20B model are published, but the comparison baseline, model, sequence length, and batch size are not stated alongside them. None of it was used in the tables or arithmetic above
  • Beta stability and per-platform differences — long-run reliability was not tested, and the documentation states no platform-specific limitations. Whether training on Apple Silicon and AMD behaves identically to NVIDIA was not confirmed
  • The adapter training memory range in the table — the 6-12GB figure is a commonly cited approximation rather than a measurement, and batch and length push it outside that band

Conclusion: Do not invert the order

Local projects tend to fail one way. The hardware is bought first and the data is examined later. Then the GPU idles while people grind through data cleaning, and about six months in there is a server nobody touches.

The order should be reversed.

  1. Write the reason for going local in one sentence. A no-export clause, utilization, or offline. If none of the three applies, stopping here is the profitable move
  2. Write fifty evaluation questions first. If they will not come, a good answer has not yet been defined, and in that state training produces a result you cannot judge
  3. Try prompting and retrieval before training. If that suffices, no fine-tune is needed. A large share of cases end right here
  4. Filter candidates with arithmetic. Full fine-tuning is usually eliminated at that stage, leaving adapter training on a 4-bit base
  5. Check all three license layers. Tooling, weights, training data. This belongs before any code is written

Better tooling really has lowered the barrier for steps one through four. But what dropped is the barrier to execution, not the barrier to judgment. What to train, and how you will know it worked, are still yours to decide, and no installer does that part for you.
