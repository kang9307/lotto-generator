Bento 登場 - ファイル1つがオフィスアプリになる単一ファイル実験

570KBのHTMLファイル1つに編集機・データ・共同編集まで収めたBentoから見る、単一ファイルアプリとローカルファーストオフィスの可能性と限界

2026-07-24 IT・技術

序論: ファイル1つがアプリになるということ

2026年7月、GeekNewsにBentoというプロジェクトが上がった。紹介文はシンプルだ。「ファイル1つに収まるオフィススイート」。実際に確認すると、より正確にはこうだ。開発者nyblnetが手がけたこのプロジェクトは、プレゼン文書と編集機、ビューア、データを1つの.bento.htmlファイルに圧縮して詰め込んでおり、そのファイルサイズは約560~570KBだ。bento.pageからこのファイルを落として好きなブラウザで開けばそれが編集機になり、保存すると同じファイルが新しい内容を抱えて自らを書き直す。Hacker NewsのShow HN投稿は977ポイントを獲得し、GitHubリポジトリは公開から数日で1,000を超えるスターを集めた。MITライセンスだ。

ただし押さえておくべき点がある。2026年7月時点で実際に出ているのはSlides(プレゼン)だけだ。DocsとSheetsはそれぞれ別の.bento.html配布物として「今後公開予定」と案内されているだけで、まだ出ていない。したがって「オフィススイート」という名称は今の完成品ではなく、ロードマップ宣言に近い。本稿はhada.ioの議論をそのまま訳すのではなく、Bentoが今日実際に何を示しているのか、そして「単一ファイルアプリケーション」という発想そのものがなぜ今また注目されるのかを、本人の視点でひも解く。

1. Bentoが実際にやっていること - ファイルがそのままソフトウェアになる仕組み

Bentoの技術的な核を事実ベースで整理するとこうだ。

1.1 データとコードが1つのファイルの中に

ファイル冒頭には、スライド内容が人が読める平文のJSONブロックとして入っている。その下には編集機・ビューア・発表モードを実装するアプリコードがBase64で圧縮されており、ブラウザのDecompressionStreamでその場で展開される。フォント、画像、チャート、アニメーションまで全てこの1ファイルの中で完結し、実行時に外部ファイルを要求する必要はないと説明される。内部的にはreveal.jsをスライドのナビゲーション基盤として使い、その上に自作のアニメーションエンジンとチャートエンジンを載せた構造だ。

1.2 保存とは自分自身を書き直すこと

保存ボタンを押すとブラウザのFile System Access APIが同じファイルパスに新しい内容を上書きする。このAPIに対応していない環境では通常のダウンロードに切り替わる。更新はECDSAで署名され、新しいバージョンを書く際に以前のファイルがそのままロールバック用として残る方式だと説明されている。リアルタイム共同編集はCloudflare Durable Objectsをブラインドリレーとして使うエンドツーエンド暗号化CRDTで実装され、サーバーは暗号化されたデータしか見られないと紹介される。Show HNのスレッドではこの構造への好評とともに、同時編集時に入力フォーカスがリセットされる問題やFirefoxでアニメーションがカクつくという性能面の指摘も出ていた。まだ磨かれている最中の初期プロジェクトというサインだ。

2. 「単一ファイルアプリケーション」という発想そのもの

Bentoで本当に興味深いのは個々の機能よりもその前提だ。私たちはこれまで「ソフトウェア」と「文書」を分けて考えることに慣れてきた。Wordの文書を開くにはWordがインストールされている必要があり、Googleドキュメントを見るにはGoogleアカウントとインターネットが要る。ソフトウェアはインストールするもので、文書はそのソフトウェアが生み出す副産物という序列が当たり前だった。

Bentoはこの序列をひっくり返す。ファイル自体が編集機であり、ビューアであり、データでもある。この発想自体が全く新しいわけではない。TiddlyWikiは以前からWiki全体を単一HTMLファイルとして配布してきたし、draw.ioのようなツールも似た試みをしてきた。Bentoが新しく加えるのは、この発想をオフィス文書に、しかもリアルタイム暗号化共同編集まで含めた形で押し進めた点だ。プロジェクト紹介に登場する「The file is the software」という一文が、この発想全体を要約している。

3. なぜ魅力的なのか - 携帯性・オフライン・アーカイブ・エアギャップ・プライバシー

3.1 携帯性とオフライン

単一ファイルはどこへでもそのまま移動できる。USBドライブ、メッセンジャー添付、オフラインのハードディスクバックアップ、どこに置いても開き方は同じだ。Bentoはオフラインモードを備えており、これを有効にすると端末の外へ何も出ず、更新・共同編集機能がハードブロックされると説明される。インターネット接続を前提としない点は、クラウドオフィスとは根本的に出発点が異なる。

3.2 エアギャップ・隔離ネットワークでの意味

これまで携わってきた社内のセキュリティ隔離網や閉域網を思い浮かべると、「インストーラー不要の文書型アプリ」という概念は実務上かなり魅力的だ。もちろん最初の持ち込み自体は持ち込み審査を経る必要があるが、一度持ち込まれた後は別途のインストーラーやライセンスサーバー、インターネット接続なしにファイルだけで文書作成・閲覧が完結するという点は、閉域網運用の負担を減らす方向だ。ただしこれはあくまで方向性であり、実際の隔離網持ち込み審査ではファイル自体にコードが含まれているという事実こそが検討対象になり得る点は冷静に見るべきだ。

3.3 プライバシー - サーバーが見ないデータ

クラウドオフィスは利便性のためにサーバーが文書内容を把握する必要がある。Bentoの共同編集構造はサーバー(Cloudflare Durable Objects)を、暗号化されたデータだけを中継するブラインドリレーとして設計したと説明される。テレメトリもないと案内される。この設計が実際に検証されたセキュリティ監査を経たかは別問題だが、少なくとも目指す方向は「サーバーが内容を知らない共同編集」というプライバシー優先設計だ。

4. Web技術でローカルアプリを作る流れ - 単一HTML+JS、WASM、ローカルファースト

4.1 ブラウザがランタイムになる時代

Bentoは別途のアプリストアやインストールなしに、ブラウザ自体をランタイムとして使う。Hacker Newsにはこの流れを支持する独立開発者の事例が絶えず上がってくる。オフラインで動きバックエンドを必要としない単一HTMLツールをいくつも作ったという開発者の投稿が最近話題になったほど、「インストール不要のローカルWebアプリ」は1つの小さな潮流になっている。

4.2 WASMへ向かうもう1つの分岐

同じ目標(ブラウザ内で完結するオフィス作業、サーバーへデータが出ない構造)を別の技術で解こうとする試みもある。ONLYOFFICEの文書エンジンをWebAssemblyにコンパイルし、Word・Excel・PowerPoint形式をブラウザ内で直接処理するオープンソースプロジェクトが2026年初めに公開された事例がそれだ。Bentoが独自フォーマットと独自レンダラーで軽く行った一方、WASMベースのアプローチは既存オフィス形式との互換性という重い荷物を背負う代わりに、実際の.docx・.xlsx・.pptxファイルを扱えるという違いがある。方向は同じで折り合いのつけ方が異なる2つの分岐というわけだ。

4.3 ローカルファースト(local-first)ソフトウェアの潮流

この流れを理論的に支える概念がlocal-first softwareだ。2019年にInk & Switch研究所が出したエッセイがこの用語を整理したが、その核となる原則のいくつかがBentoとぴったり重なる。「ネットワークは選択肢であるべきだ」「共同編集者は互いの変更を見られるべきだ」、そして何より「The Long Now」 - 特定のベンダーが消えてもサービスが終了しても、ソフトウェアは動き続けるべきだという原則だ。Bentoはこれらの原則を、最も日常的で最も長く保存すべきファイル形式であるオフィス文書にそのまま適用した実験として読める。

5. 既存オフィスとの位置関係と限界 - MS 365・Googleドキュメント・LibreOffice

Bentoを既存のオフィススイートと並べてみると位置が明確になる。強みと限界を同時に認めるのが正直な評価だ。

5.1 共同編集の深さの差

MS 365やGoogleドキュメントのリアルタイム共同編集は、億単位のユーザーを経て検証されたインフラだ。Bentoの暗号化CRDT共同編集は方向としては興味深いが、まだShow HNの段階でフォーカスリセットのようなバグが報告される初期実装だ。

5.2 機能の深さと拡張性

今日のBentoはプレゼン1つに集中している。ワープロの脚注・索引・校正ツール、表計算の関数・ピボットテーブルのような深い機能は、まだこのプロジェクトの範囲外だ。DocsやSheetsが出たとしても、数十年積み上がった既存オフィスの機能面に短期間で追いつくのは容易ではないだろう。

5.3 互換性と容量の限界

Bentoは独自形式だ。既存の.pptx・.docx・.xlsxファイルとの相互変換がどれほど滑らかかは確認されていない。また、ファイル1つに全てを詰め込む構造は、文書が大きくなるほど(画像やチャートが増えるほど)ファイル自体が重くなるという生まれつきのトレードオフを抱えている。

6. 実際に使えそうなシナリオ

6.1 オフライン環境と隔離ネットワーク

インターネットのない現場作業、船舶・航空機など接続が不安定な環境、あるいはクラウドログイン自体が禁じられた社内隔離網のような場所では、「ファイル1つで完結するプレゼンツール」が現実的な選択肢になり得る。ただし先述の通り、閉域網への持ち込み審査は別途経る必要がある。

6.2 一時的な作業と教育現場

アカウントを作る必要なくリンク1つで発表資料を開き、その場で修正できる点は、単発のワークショップやハッカソンのデモ、教育現場で有用だ。学生や参加者がノートPCにソフトウェアをインストールする権限を持たない共用PC環境でも、ファイルさえ実行すればよいという方式は参入障壁を下げる。

6.3 一時的な共同編集と迅速な共有

クラウドアカウントを共有せずとも、ファイルのリンクや添付だけでチームメンバーがすぐに開いてコメントを残せる点も、短い会議やワークショップ用資料には向いている。ただし3節で触れたように共同編集機能自体はまだ実験段階なので、会社の正式な共同編集ワークフローを置き換えるより補助手段として使う方が安全だ。

7. 文書保存の観点 - 20年後にも開けるファイル

7.1 フォーマットが朽ちるという問題

古いワープロ形式や、終息したソフトウェア専用のファイルが開けずに困った経験は珍しくない。クラウド文書はさらに脆弱だ。サービスが終了すれば文書自体が丸ごと消えてしまうこともある。「このファイルは20年後も開けるだろうか」という問いは、オフィスソフトウェアの古くからの宿題だ。

7.2 Bentoの答え - 平文データと署名付き自己書き換え

Bentoのアプローチはこうだ。データをバイナリではなく人が読めるJSONとしてファイル内にそのまま置く。特定企業のサーバーやアカウントに依存しない。新しいバージョンが出ても以前のファイルを上書きせず、署名済みの新しいファイルを作って以前のバージョンを保存する。こうした設計全体は、先述のローカルファースト原則の「The Long Now」を文書フォーマットのレベルで実現しようとする試みとして読める。

7.3 残る前提 - ブラウザというプラットフォームへの依存

ただしこの構造にも前提は残る。Bentoファイルが将来も開けるためには、結局HTML5・JavaScriptを解釈するブラウザが存在し続ける必要がある。Webの標準がこれまで長く後方互換を守ってきたことを踏まえれば、この前提はかなり安全な部類に入るが、特定企業のクラウドより安全というだけで、前提が全くないわけではない点は冷静に押さえておくべきだ。

8. 結論 - 完成形のオフィスではなく方向性への実験

Bentoを今の時点で正直にまとめるとこうなる。2026年7月時点で実際に出ているのはプレゼンツール1つだけで、文書・表計算は予告にとどまっている。共同編集機能は興味深い設計を持っているが、まだ初期段階のバグを抱えている。既存オフィス御三家(MS 365・Googleドキュメント・LibreOffice)を今すぐ置き換えられる水準ではない。

それでもこのプロジェクトが短期間で1,000超のスターと977ポイントの注目を集めた理由は、機能ではなく発想にあると見る。インストール・アカウント・サーバーなしにファイル1つで完結するソフトウェア、そのファイルがオフラインでも完全に動作し、20年後もブラウザさえあれば開けるという約束。これはクラウド中心に流れてきたここ十数年のオフィスソフトウェアの潮流への小さな反論だ。完成された代替を探している人なら今はまだ既存ツールを使い続ける方が正解であり、ローカルファーストソフトウェアという方向性そのものに関心があるなら、Bentoは今注視する価値のある実験だ。
