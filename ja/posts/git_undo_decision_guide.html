git 取り消し判断表 - reset・revert・restore・checkout のどれを使うか

どこにあるか、すでに共有したか。この二つの問いがコマンドをほぼ決める

2026年9月1日 開発・インフラ

取り消しが難しいのはコマンドが多いからではない。選択肢が似た顔をしているのに結果がまるで違うからだ。reset はコミットを消し、revert はコミットを足す。restore はブランチに触れず、checkout は両方をやる。名前だけでは区別がつかない。

だからこの記事はコマンド一覧ではなく判断手順である。先に二つを問い、その答えからコマンドが出てくる。以下の例はすべて空の一時リポジトリを新しく作って実際に実行したもので、貼った出力はそのとき実際に返ってきたものだ。

この記事のコマンドの一部は取り消しのきかない破壊的な操作である。各節に「戻せるかどうか」を明記した。初めて見るコマンドは実際の作業リポジトリではなく、git init で作った空のリポジトリで先に試すことをすすめる。

取り消す前に問うべき二つのこと

手が動く前に確かめることは二つしかない。この二つが決まれば、使えるコマンドはたいてい一つに絞られる。

  • 一つめ、戻したい対象はどこにあるか。まだ保存しただけか（ワークツリー）、git add までしたか（インデックス）、それとも git commit までしたか（HEAD）。ここが決まると restore か reset かが分かれる
  • 二つめ、そのコミットをすでに共有したか。プッシュしたか、誰かが取っていったなら、そのコミットはもう自分だけのものではない。ここが決まると reset か revert かが分かれる
  • 三つめは確認用だ。この変更は一度でもコミットされたことがあるか。ないなら、どのコマンドで消しても戻す手立てはない

多くの事故は二つめを飛ばして起きる。ローカルで reset --hard によりコミットを消すのは何の問題もない。同じ操作をすでにプッシュしたコミットに対して行えば、そのブランチを持つ全員のリポジトリが食い違う。コマンドは同じでも代償が違う。この非対称が見えにくいのは、コマンドを打つ瞬間に Git が何も警告しないからだ。結果は数日後、他人の端末で、その人がいつもどおり git pull をしたときに初めて表に出る。

三つの領域 - ワークツリー、インデックス、HEAD

Git では一つのファイルの内容が同時に三か所に存在しうる。エディタで保存したワークツリー、git add で上げたインデックス（ステージ）、そして最後のコミットである HEAD だ。取り消し系のコマンドは、この三つのうちいくつに触れるかで性格が分かれる。

三つがそれぞれ違う状態のとき git status がどう見えるかを先に押さえておくと、あとが楽になる。一つは修正しただけ、一つは新しく作って add し、一つは作っただけにしてある。

$ cd /tmp/demo
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	new file:   b.txt

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   a.txt

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	c.txt

$ git status --short
 M a.txt
A  b.txt
?? c.txt

--short の出力の二つの桁がそのまま二つの領域だ。左がインデックス、右がワークツリーを表す。A  b.txt はインデックスだけに変化があるという意味で、 M a.txt はワークツリーだけという意味だ。両方が変われば MM になる。この二文字を読めるようになると、どのコマンドを使うべきかは画面にすでに書いてあることになる。

親切なことに git status は各まとまりの下に解法まで書いてくれる。ステージから降ろすなら git restore --staged、ワークツリーの変更を捨てるなら git restore という具合だ。次の表がその対応である。

領域何が入っているかstatus --short の表示ここにあるものを戻すコマンド
ワークツリーエディタで保存した今のファイル内容右桁の M・D、追跡外なら ??git restore <ファイル>、追跡外なら git clean
インデックス（ステージ）git add で上げた、次のコミットに入る内容左桁の M・A・Dgit restore --staged <ファイル>、git reset
HEAD（コミット）すでに記録された履歴git log でしか見えない未共有なら git reset、共有済みなら git revert

判断表 - どこにあるか かける 共有したか

この記事の中心はこの表だ。縦軸が一つめの問い、横軸が二つめの問いである。残りの節は、この表の各マスを一つずつ実行して確かめた記録だと思ってよい。

戻したい対象がどこにあるかまだ自分のリポジトリだけすでにプッシュ済み戻せるか
ワークツリーの修正（add していない）git restore <ファイル>該当なし - 共有されたことがないいいえ。コミットされていなければ終わりだ
インデックスに上げた変更（add 済み）git restore --staged <ファイル>該当なしはい。ファイルの内容はそのまま残る
最後のコミットのメッセージや構成git commit --amend使わない。git revert ではい。reflog に古いコミットが残る
最後のコミットそのものgit reset --soft/--mixed/--hard HEAD~1使わない。git revert HEADコミットははい（reflog）、ワークツリーはいいえ
複数のコミットgit reset --hard <コミット>git revert <古い>..<新しい>コミットははい（reflog）
追跡されていないファイルgit clean -n で確認してから -fd該当なしいいえ。Git が知らないファイルだ
ブランチを間違えたgit switch -c <ブランチ> のあと元のブランチを resetgit revert のあと正しいブランチでやり直すはい

表で肝心なのは「すでにプッシュ済み」の列に reset が一度も現れないことだ。例外は作れるが、その例外はチーム全員が合意してタイミングを合わせないと成り立たない。一人で決める話ではない。

表のかなりの部分が一つめの列だけで決まるのも見どころだ。まだ自分のリポジトリにしかないなら、何をしてもたいてい構わない。困るのは自分だけで、後ろには reflog が控えているからだ。二つめの問いの答えが「はい」に変わった瞬間、使えるコマンドは事実上一つに減るのだが、その理由は技術的な潔癖さではない。その行の他のコマンドは、予告なしに他人の机に仕事を作るというのが理由である。

git restore - ファイル単位で戻す

restore は Git 2.23 で checkout から分かれて出てきた。やることが狭いぶん、かえって使いやすい。Git 公式ドキュメントの Reset, restore and revert の節はこのコマンドを「インデックスや別のコミットからワークツリーのファイルを復元するもの」と説明し、そのすぐあとに「このコマンドはブランチを更新しない」と釘を刺している。履歴には触れないという意味だ。

大事なのは --staged 一つで性格がまるごと変わるという点である。以下は同じファイルについて、ステージに beta を上げ、ワークツリーにだけ gamma を足した状態で二つの形を順に実行したものだ。

$ git status --short
MM note.txt

# 1) インデックスだけ戻す - ファイルの中身はそのまま
$ git restore --staged note.txt
$ git status --short
 M note.txt
$ cat note.txt
alpha
beta
gamma

# 2) ワークツリーを戻す - ここで中身が消える
$ git restore note.txt
$ git status --short
$ cat note.txt
alpha

二つめのコマンドが走った瞬間に beta と gamma は消えた。一度もコミットされていないので戻る道はない。restore という穏やかな名前でありながら破壊的なコマンドである理由がこれだ。逆に --staged を付けた一つめは、ファイルに一切触れていない。

  • git restore --staged <ファイル> - アンステージ。戻せる。ファイルの内容はそのままだ
  • git restore <ファイル> - ワークツリーの変更を破棄。戻せない。コミット前の内容は消える
  • git restore --staged --worktree <ファイル> - 両方。実行すると MM が一度に消える
  • git restore --source=<コミット> <ファイル> - そのコミット時点のファイルを持ってくる。履歴はそのままだ
  • うっかり rm した追跡ファイルも git restore <ファイル> でそのまま戻る。こちらは安全な使い方だ

最後の使い方は思いのほか出番が多い。履歴はそのままにして、ファイル一つだけを古い版に戻したいときだ。コミット三つのリポジトリで一段前の版を取り出すとこうなる。

$ git log --oneline
1beb864 add delta
4fb8d79 add beta
96d2ca7 add note

$ git restore --source=HEAD~1 note.txt
$ cat note.txt
alpha
beta
$ git status --short
 M note.txt

ブランチは add delta にそのままあり、ファイルだけが以前の状態になって修正扱いになる。ここでコミットすれば「打ち消す新しいコミット」が一つできる。revert をファイル単位で手作りしたようなものだ。

git reset - 三つのモードはどこまで戻すのか

reset は三つのコマンドのうち唯一ブランチの先端を動かすものだ。公式ドキュメントの言い方では「コミットをブランチに足したり外したりするために先端を動かすこと」であり、だからコミット履歴が変わる。三つのモードはHEAD を動かしたあとインデックスとワークツリーをどこまで連れていくかだけが違う。

同じリポジトリを三つ作り、それぞれ HEAD~1 へ戻した。コミットは C1 base、C2 feature、C3 oops の順で、ファイルは毎回一行ずつ増える。

$ git log --oneline
2152c39 C3 oops
3e571a5 C2 feature
44cb882 C1 base

$ git reset --soft HEAD~1
$ git log --oneline
3e571a5 C2 feature
44cb882 C1 base
$ git status --short
M  app.txt
$ cat app.txt
v1
v2
v3

--soft はコミットだけを消した。C3 が抱えていた変更は左桁の M、つまりステージにそのまま上がっている。コミットメッセージを書き直したいときや、複数のコミットを一つにまとめたいときに使うモードだ。

$ git reset --mixed HEAD~1
Unstaged changes after reset:
M	app.txt
$ git log --oneline
17b85e8 C2 feature
d42f7bf C1 base
$ git status --short
 M app.txt
$ cat app.txt
v1
v2
v3

--mixed はインデックスまで戻した。同じ変更が右桁の M に降りている。ファイルの内容は依然として v3 まである。オプションを省いた git reset がこのモードで、引数なしで git reset だけを打つと --mixed HEAD となり、ステージに上げたものが全部降りる。

$ git reset --hard HEAD~1
HEAD is now at add35e9 C2 feature
$ git log --oneline
add35e9 C2 feature
453f0e3 C1 base
$ git status --short
$ cat app.txt
v1
v2

--hard だけがファイルを実際に変えた。status は空で v3 は消えている。ドキュメントも「追跡ファイルの変更は破棄される」という文言をこのモードにだけ書いている。三つのうちコミットしていない内容を失いうるのはこれだけだ。

モードHEADインデックスワークツリー実行後の status --short失いうるもの
--soft動かすそのままそのままM  app.txt（左桁）なし
--mixed（既定）動かす戻すそのまま M app.txt（右桁）ステージの構成だけ
--hard動かす戻す戻す空コミットしていない変更すべて

git revert - 打ち消す新しいコミットを作る

revert は前の二つと性格が違う。ドキュメントの最初の一文がそのまま定義だ。「与えられたコミットが入れた変更を打ち消し、それを記録する新しいコミットを作る」。古いコミットはその場に残る。履歴が短くなるのではなく長くなる。

$ git log --oneline
e4285bf C3 enable debug
b1fe989 C2 add timeout
f001827 C1 add config

$ git revert --no-edit HEAD
[main 83f6fc6] Revert "C3 enable debug"
 1 file changed, 1 deletion(-)
 delete mode 100644 debug.txt

$ git log --oneline
83f6fc6 Revert "C3 enable debug"
e4285bf C3 enable debug
b1fe989 C2 add timeout
f001827 C1 add config
$ git status --short

C3 はそのままあり、その上に Revert "C3 enable debug" が積まれた。結果のファイルは C2 時点と同じになったが、記録としては「やった」と「戻した」の両方が残る。監査の追跡が要るリポジトリでは、これは欠点ではなく利点だ。

ただし revert がいつも静かに終わるとはかぎらない。戻したいコミットより後に同じ場所を触ったコミットがあれば衝突する。同じファイルの隣り合う行を触り続けた履歴で真ん中のコミットを戻すとこうなる。

$ git revert --no-edit HEAD~1
Auto-merging config.txt
CONFLICT (content): Merge conflict in config.txt
error: could not revert 17a5abe... C2 enable debug
hint: After resolving the conflicts, mark them with
hint: "git add/rm <pathspec>", then run
hint: "git revert --continue".
hint: You can instead skip this commit with "git revert --skip".
hint: To abort and get back to the state before "git revert",
hint: run "git revert --abort".

$ git status --short
UU config.txt

$ git revert --abort
$ git log --oneline
08823c4 C3 enable cache
17a5abe C2 enable debug
9b96f25 C1 add config
$ git status --short

ここで注目すべきは git revert --abort だ。衝突の途中でもこの一行でリポジトリは開始前の状態に完全に戻る。revert は失敗しても安全に引き返せる、この記事でいちばん取り消しやすいコマンドである。

  • git revert <コミット> - 新しいコミットを作る。戻せる。その新しいコミットをもう一度 revert すれば元どおりだ
  • --no-edit を付ければ既定のメッセージでそのままコミットする。エディタは開かない
  • 衝突したら止まる。--abort で全部取り消し、--continue で解決後に続行、--skip でそのコミットだけ飛ばす
  • 複数を戻すときは git revert <古い>..<新しい> のように範囲を渡す。新しいものから順に処理される
  • 開始にはワークツリーが綺麗である必要がある。ドキュメントに明記された前提条件だ

共有したコミットを書き換えると他人に何が起きるか

「プッシュしたコミットには revert を使え」はよく聞くが、体験する前は腑に落ちにくい。リポジトリを一つ作り、それを複製して同僚側に見立てたうえで、同じ失敗を二通りのやり方で取り消してみた。以下の出力ではリポジトリのパスだけを /tmp/demo/upstream に置き換えてある。

# 同僚のクローン - 問題のコミットをすでに持っている
$ git log --oneline
97b65d9 C2 bad change
2135f94 C1 base

# こちらで revert
$ git revert --no-edit HEAD
[main 7085b16] Revert "C2 bad change"
 1 file changed, 1 deletion(-)

# 同僚が pull
$ git pull
From /tmp/demo/upstream
   97b65d9..7085b16  main       -> origin/main
Updating 97b65d9..7085b16
Fast-forward
 app.txt | 1 -
 1 file changed, 1 deletion(-)

Fast-forward の一行で終わった。同僚は何もしていないし衝突もない。今度は同じ状況でコミットを消して作り直してみた。

# 同僚のクローン - 同じ出発点
$ git log --oneline
689d5e6 C2 bad change
f43e101 C1 base

# こちらで C2 を消してきちんと作り直す
$ git reset --hard HEAD~1
HEAD is now at f43e101 C1 base
$ printf 'v1\ngood change\n' > app.txt
$ git add app.txt && git commit -q -m "C2 good change"
$ git log --oneline
2727247 C2 good change
f43e101 C1 base

# 同僚が pull
$ git pull
From /tmp/demo/upstream
 + 689d5e6...2727247 main       -> origin/main  (forced update)
Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
Automatic merge failed; fix conflicts and then commit the result.

$ git status --short
UU app.txt
$ cat app.txt
v1
<<<<<<< HEAD
bad change
=======
good change
>>>>>>> 272724744769a515b2d1fc26330c4883201016a3

同じ目的、同じ最終状態なのに同僚側の結果がまるで違う。forced update が出て、衝突の目印がファイルに埋まった。自分が節約したコミット一つが、チームの人数ぶんの衝突解決に変わったのだ。しかもその人たちは何が起きたのか知らないままである。

強制プッシュ（git push --force）はここにもっと大きな危険を重ねる。自分が最後に取ってきたあとに他人が上げたコミットがあれば、それまで消してしまう。--force-with-lease はリモートの現在値が自分の知る値と同じときにだけ押し込むのでその事故は防げるが、「消してよい」という許可ではない。共有ブランチではどちらも既定の選択肢にはならない。

git checkout はなぜ紛らわしかったのか

checkout が難しいのは、このコマンドが性質の違う二つの仕事を兼ねていたからだ。ブランチを移る仕事とファイルを復元する仕事では危険度がまるで違うのに、名前が同じだった。だから引数によって結果が変わり、名前が重なるとどちらなのか分からなくなる。

実際に重ねてみると結果ははっきりする。app.txt というファイルがあるリポジトリに app.txt というブランチを作り、ファイルを直してから checkout を実行した。

$ git branch app.txt
$ printf 'v2\n' > app.txt
$ git checkout app.txt
M	app.txt
Switched to branch 'app.txt'
$ git branch --show-current
app.txt
$ cat app.txt
v2

# 2.23 以降: 名前が重なっても意味は一つだけ
$ git switch app.txt
Switched to branch 'app.txt'
$ git restore app.txt
$ cat app.txt
v1

ファイルを戻すつもりだった人はブランチが変わったことにあとから気づく。Git 2.23 のリリースノートはこの問題を正面から扱った。「ブランチをチェックアウトして履歴を進める仕事」と「インデックスやツリーからパスをチェックアウトする仕事」を一つの git checkout から切り離すために switch と restore を導入した、というものだ。

checkout のもう一つの顔は、コミットを直接指定したときだ。ブランチではなくコミットへ行くと detached HEAD になる。ここでコミットすると、どのブランチにも属さないコミットができる。

$ git checkout HEAD~1
Note: switching to 'HEAD~1'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.
...
HEAD is now at f91e4ef C1 base

$ git status | head -2
HEAD detached at f91e4ef
nothing to commit, working tree clean

$ git switch main
Previous HEAD position was f91e4ef C1 base
Switched to branch 'main'

この状態自体は危険ではない。案内文の言うとおり、見回したり実験したりするにはよい場所だ。問題はここで作ったコミットをブランチに移さずに離れるときである。そのときも reflog は残るが、はじめから git switch -c <名前> で名前を付けておくほうがずっと楽だ。

git reflog - 消したコミットが生き返る道

この記事で一つだけ覚えるならこの節だ。reset --hard でコミットを消してもたいていは生き返らせられる。Git は HEAD が通ったすべての位置を reflog に書き留めているからだ。コミット三つのリポジトリで二つを消してから復旧するまでの全過程である。

$ git log --oneline
78b8ce0 C3 more work
f1acddb C2 two days of work
7810949 C1 base

# 事故
$ git reset --hard HEAD~2
HEAD is now at 7810949 C1 base
$ git log --oneline
7810949 C1 base
$ cat work.txt
v1

# 救出: 消えたコミットがここにある
$ git reflog
7810949 HEAD@{0}: reset: moving to HEAD~2
78b8ce0 HEAD@{1}: commit: C3 more work
f1acddb HEAD@{2}: commit: C2 two days of work
7810949 HEAD@{3}: commit (initial): C1 base

$ git reset --hard HEAD@{1}
HEAD is now at 78b8ce0 C3 more work
$ git log --oneline
78b8ce0 C3 more work
f1acddb C2 two days of work
7810949 C1 base
$ cat work.txt
v1
v2
v3

HEAD@{1} は「一つ前に HEAD があった場所」という意味だ。reset --hard の直前の位置がそこにそのまま残っている。これを知ると reset --hard への恐怖は半分ほど減る。残りの半分は次の節で扱う。

直前の位置は名前でも取れる。ORIG_HEAD は reset や merge のような大きな移動の直前の HEAD を指す。ブランチごとの移動だけを見たいなら git reflog show <ブランチ> を使う。

$ git reset --hard HEAD~2
HEAD is now at f1c8944 C1
$ git rev-parse --short ORIG_HEAD
4d26ce7
$ git reset --hard ORIG_HEAD
HEAD is now at 4d26ce7 C3

$ git reflog show main
4d26ce7 main@{0}: reset: moving to ORIG_HEAD
f1c8944 main@{1}: reset: moving to HEAD~2
4d26ce7 main@{2}: commit: C3
b8efd2c main@{3}: commit: C2
f1c8944 main@{4}: commit (initial): C1
  • reflog はリポジトリごとにローカルだ。クローンには付いていかないし、他人の事故を自分の reflog で救うことはできない
  • 永久保存ではない。設定ドキュメントによれば gc.reflogExpire の既定値は 90日、現在の先端から到達できない項目を扱う gc.reflogExpireUnreachable は 30日だ
  • 後者が短い理由もドキュメントに書いてある。commit --amend や rebase で生じる古いコミットなので、早めに消してよいと見なされている
  • つまり「あとで reflog から探せばいい」は数か月がかりの計画にはならない。事故に気づいたらその日のうちに処理する

戻せないもの

reflog はコミットを記録する仕組みであって、ワークツリーを記録する仕組みではない。だから一度もコミットされたことのない変更は、どのコマンドで消しても戻ってこない。一時間直したがコミットしていないファイルの上で reset --hard を回すとこうなる。

$ cat draft.txt
committed line
an hour of work that was never committed
$ git status --short
 M draft.txt

$ git reset --hard HEAD
HEAD is now at 371a5ec C1 base
$ cat draft.txt
committed line

$ git reflog
371a5ec HEAD@{0}: reset: moving to HEAD
371a5ec HEAD@{1}: commit (initial): C1 base

$ git fsck --lost-found
$

reflog にはコミット一つと reset の記録しかない。git fsck --lost-found も何も出さない。その一時間は Git が一度も見たことのない内容だったからだ。ここに例外が一つある。git add までしていればその内容はオブジェクトとして保存されており、fsck で探す余地が生まれる。ステージに上げる習慣が安全網になる場面だ。

コマンド何を消すか戻す道先にやること
git reset --hardコミット + コミットしていない変更コミットは reflog、変更はなしgit stash push -u
git restore <ファイル>そのファイルのコミットしていない変更なしgit diff で何が消えるか確認
git clean -fd追跡外のファイル・ディレクトリなしgit clean -nd で一覧を確認
git commit --amend直前のコミット（置き換わる）reflogプッシュしたか確認
git revert何も消さないもう一度 revertワークツリーを綺麗に

git stash - 危険なコマンドの前に一行

前節の事故を防ぐいちばん安上がりな方法が stash だ。コミットするほど整っていない変更を一時的にどけて、ワークツリーを綺麗にする。どけた内容は Git のオブジェクトとして保存されるのでコミットと同じ水準で安全になる。

$ git status --short
 M tracked.txt
?? newfile.txt

$ git stash push -m wip
Saved working directory and index state On main: wip
$ git status --short
?? newfile.txt

# 新しく作ったファイルは預かられていない。-u が要る
$ git stash push -u -m wip2
Saved working directory and index state On main: wip2
$ git status --short
$ git stash list
stash@{0}: On main: wip2

$ git stash pop
...
Dropped refs/stash@{0}

一つめの stash push のあとにも newfile.txt が残っているのが肝心だ。stash は既定では追跡外のファイルを預からない。「スタッシュしたから安全だ」と信じて reset --hard や clean -fd を回すと、新しく作ったファイルだけが選んで消える。習慣として -u を付けるほうがよい。

  • git stash push -u -m <メモ> - 追跡ファイルと新規ファイルをまとめて預ける。メモを残せばあとで一覧から見分けられる
  • git stash list で確認、git stash pop で取り出しつつ削除、git stash apply で取り出して残す
  • スタッシュにも reflog がある。誤って drop したなら git fsck や以前のスタッシュ記録から探せる余地がある
  • ただし永久保管庫ではない。何日も置くつもりなら一時ブランチにコミットするほうが安全だ

git clean - 戻せない削除

clean はこの記事でいちばん単純で、いちばん危険だ。ドキュメントのとおり「バージョン管理下にないファイルを再帰的に削除してワークツリーを掃除する」。Git が知らないファイルなので消したあとは Git の中に何の痕跡も残らない。

$ git status --short
?? build/
?? notes.md
?? out.log

# -n は消さない。一覧を見せるだけ
$ git clean -n
Would remove notes.md
Would remove out.log

# ディレクトリは -d を付けないと見えない
$ git clean -nd
Would remove build/
Would remove notes.md
Would remove out.log

$ git clean -fd
Removing build/
Removing notes.md
Removing out.log
$ ls
keep.txt

-n と -nd の結果が違うところに注目したい。-d なしではディレクトリが一覧にまったく出てこない。-n だけ見て安心してから -fd を実行すると、思ったより多く消える。順序は一つしかない。-nd で先に見て、一覧を読んで、それから -fd だ。

-x はここからもう一歩踏み込む。.gitignore で無視されるファイルまで消す。ビルド生成物を片付けるには便利だが、無視リストには .env のようなローカル設定が入っていることがよくある。それも一緒に消える。

メッセージを間違えた、ファイルを入れ忘れた

コミット直後に気づく失敗はたいてい二つだ。メッセージに打ち間違いがあるか、入れるべきファイルを忘れたか。どちらも git commit --amend 一つで片づく。新しいコミットを積むのではなく直前のコミットを新しいコミットで置き換える動作だ。

$ git log --oneline
d8ed825 fix bugg
689816b C1 base

# 1) メッセージだけ直す
$ git commit --amend -m "fix bug"
$ git log --oneline
ca1558d fix bug
689816b C1 base

# 2) 入れ忘れたファイルを足す
$ git add c.txt
$ git commit --amend --no-edit
$ git show --name-only --oneline HEAD
5ef662d fix bug
b.txt
c.txt

$ git reflog
5ef662d HEAD@{0}: commit (amend): fix bug
ca1558d HEAD@{1}: commit (amend): fix bug
d8ed825 HEAD@{2}: commit: fix bugg
689816b HEAD@{3}: commit (initial): C1 base

ハッシュが d8ed825 → ca1558d → 5ef662d と毎回変わっているのが重要だ。amend はコミットを直すのではなく、新しく作って差し替えている。だからすでにプッシュしたコミットに使えば、前節で見た forced update の状況がそのまま再現する。原則は一つだ。プッシュ前にだけ使う。

amend 自体を取り消したいなら reflog を使う。上の状態で git reset --hard HEAD@{1} を実行すれば、ファイルを足す前の ca1558d へ正確に戻る。

別のブランチにコミットしてしまったとき

main で作業していてコミットまでしてしまう状況はよくある。ここで手が先に動くと reset --hard でコミットを消して最初からやり直すことになるが、その必要はない。コミットはそのままにして名札だけ動かせばよい。

$ git log --oneline --decorate
501da69 (HEAD -> main) C2 feature work
032adf6 C1 base

# 1) 今の場所にブランチを新しく作る - コミットが付いてくる
$ git switch -c feature
Switched to a new branch 'feature'
$ git log --oneline --decorate
501da69 (HEAD -> feature, main) C2 feature work
032adf6 C1 base

# 2) main に戻って一つ分下げる
$ git switch main
$ git reset --hard HEAD~1
HEAD is now at 032adf6 C1 base
$ git log --oneline --decorate
032adf6 (HEAD -> main) C1 base
$ git log --oneline --decorate feature
501da69 (feature) C2 feature work

順序が大事だ。先にブランチを作り、そのあとで main を戻す。逆にするとコミットがどのブランチにも属さなくなり、取り戻すには reflog を漁ることになる。そしてこの手順は main をまだプッシュしていないときにだけ使う。すでにプッシュしているなら revert で打ち消し、正しいブランチで改めてコミットする。

まだコミットしていないならもっと簡単だ。ブランチを変えてもコミットしていない変更は付いてくる。そして付いてこられない状況なら Git が自分で止まる。

# コミット前ならそのまま移ればよい
$ git status --short
 M app.txt
$ git switch -c feature
Switched to a new branch 'feature'
$ git status --short
 M app.txt

# 移り先のブランチが同じファイルを触っていれば Git が止める
$ git switch other
error: Your local changes to the following files would be overwritten by checkout:
	app.txt
Please commit your changes or stash them before you switch branches.
Aborting

この拒否は機能だ。switch と checkout はコミットしていない変更を上書きしなければならない状況で自ら止まる。案内文のとおりコミットするかスタッシュすればよい。ちなみに --discard-changes を付けるとその保護が切れて変更は消える。名前は正直なほうだ。

実行環境と再現の仕方

この記事の出力はすべて以下の環境で実際に実行して得たものだ。コミットのハッシュと時刻は実行のたびに変わるので、その部分は再現しない。

$ git --version
git version 2.48.1.windows.1

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

OS は Windows 10（ビルド 19045）、シェルは Git for Windows に付属する Git Bash（MSYS2）だ。コマンド自体は Linux や macOS と同じだが、貼った案内文やヒントの文言はGit のバージョンによって変わる。とくに git status がすすめるコマンドは以前は git reset HEAD <ファイル> で、今は git restore --staged だ。古い解説と画面が食い違って見える理由はたいていこれである。

  • 再現は難しくない。空のディレクトリで git init し、ファイル数個でコミットを三つほど作れば、この記事の例はほぼそのまま動く
  • 実際の作業リポジトリで練習しない。この記事の半分はファイルを消すコマンドだ
  • 実行中に一つ引っかかった。パスがとても深いディレクトリでは Git がオブジェクトを書けず unable to write file ...: Invalid argument で止まった。Windows のパス長制限が原因で、短いパスに移すとそのまま解決した
  • 同じ状況で core.longpaths を有効にしてみたが、このエラーは消えなかった。Linux や macOS では現れない問題だ

まとめ - 症状からコマンドへ

最後に症状からそのままコマンドへ行く表を置く。先の判断表が原理だとすれば、こちらは手に馴染ませる用だ。

今の状況使うコマンドファイルの中身が消えるか
ファイルを直したがなかったことにしたいgit restore <ファイル>消える
add を間違えたgit restore --staged <ファイル>いいえ
add を全部取り消したいgit resetいいえ
コミットメッセージに打ち間違いがある（プッシュ前）git commit --amend -m "..."いいえ
ファイルを一つ忘れてコミットした（プッシュ前）git add のあと git commit --amend --no-editいいえ
最後のコミットを取り消して内容は残したいgit reset --soft HEAD~1いいえ
最後のコミットを丸ごとなかったことに（プッシュ前）git reset --hard HEAD~1消える
すでにプッシュしたコミットを取り消すgit revert <コミット>いいえ
うっかりファイルを消した（コミット済みのファイル）git restore <ファイル>いいえ
reset --hard でコミットを飛ばしたgit reflog のあと git reset --hard HEAD@{n}コミットは戻る
ビルドの残りかすを片付けたいgit clean -nd で確認して -fd消える
別のブランチでコミットしたgit switch -c <ブランチ> のあと元のブランチを reset --hard HEAD~1いいえ

結局は二つの問いに戻る。どこにあるか、そして共有したか。前の問いが restore・reset・clean のどれかを選び、後ろの問いが reset と revert を分ける。その上に reflog という安全網があり、その網が届かない場所が一度もコミットされたことのない変更だと分かれば、残りはたいてい応用である。

履歴を調べる側のコマンドが気になるなら もっと使うべき Git 履歴コマンド に bisect・log -S・reflog を実務の視点で整理してあるし、基礎から見直したいなら Git基礎 - バージョン管理の始め方 が出発点になる。

確認できなかったこと

  • すべての例は Git 2.48.1 一つだけで実行した。ほかのメジャーバージョンではヒントの文言や既定の挙動が違いうる。とくに git pull が分岐した履歴に出会ったときの既定の処理は、バージョンによって変わってきた部分だ
  • Linux や macOS で同じスクリプトを回して比べてはいない。コマンドの意味は同じだが、パス長制限の問題は Windows 固有であり、シェルが違えば例の printf の書き方が変わりうる
  • リモートリポジトリの実験は同じディスク上のローカル複製で行った。実際のサーバーやホスティングサービスでは保護ブランチの設定により強制プッシュがそもそも拒否されることがあり、その挙動は確認できなかった
  • git restore・git switch が実験的だという記述は 2.48.1 に同梱された文書で確認したものだ。オンラインの最新文書では同じ記述を確認できなかったので、版によって変わった可能性がある
  • reflog の保持期間は設定ドキュメントに記された既定値を写したものであり、90日・30日が実際に経過して項目が消えるところを観察したわけではない
  • git fsck でステージにだけ上げた内容を取り戻す経路は原理上可能だと書いただけで、この記事では実行して確認していない
