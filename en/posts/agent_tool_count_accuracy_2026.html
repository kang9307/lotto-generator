How Many Tools Can an Agent Handle - Where Tool Selection Breaks and How to Narrow It

Separate what you attach from what you lay out, and half the problem disappears

Aug 3, 2026 IT/Tech

Introduction: it worked fine with just one server attached

The agent ran well when GitHub MCP was the only thing wired up. Then you added Slack, then an internal database lookup, then browser automation, and finally you wrapped the company API gateway. And now it does strange things on tasks it handled yesterday. You ask it to open an issue and it runs a search. You ask it to search and it omits a required parameter. On some requests it ignores the tools entirely and answers from its own knowledge.

Swapping models barely helps. Adding a line to the system prompt telling it to choose tools carefully helps even less. At this point most teams start writing longer prompts. That direction almost never works.

Here is the conclusion up front. There is no practical ceiling on how many tools you attach. The ceiling is on how many you lay out in front of the model when a turn begins. Separate those two and half the problem disappears. The other half comes from names, descriptions, and the prerequisite relationships between tools.

This article covers where that boundary sits, what breaks in what order once you cross it, and the sequence in which to apply four narrowing techniques so you do not pay for the wrong one first. The concept of MCP itself and the debate over its limits were covered in the complete guide to MCP and Is MCP dead?, so they are not repeated here.

1. What breaks first - the five faces of failure

The sentence «more tools means lower accuracy» is true but useless. What you need in practice is a way to separate which failure comes from which cause. Five distinct failures arise from different origins, and looking at them as one thing is why the cause stays hidden.

Failure typeWhat it looks like in logsCommon misdiagnosisWhere the cause actually lives
Argument errorsMissing required parameter, type mismatch, bad format«The model is dumb»Argument descriptions and examples. Independent of count
Wrong tool calledCalls a differently named tool than intended«The prompt is too thin»Name and description overlap. Appears only as count grows
Tools left unusedAnswers from parametric knowledge with tools present«The model is lazy»Definitions pushing out working context
Over-callingRepeats list and read tools without progressing«Loop bug»Wandering because the target tool was not found
Missing prerequisitesRight target tool, but no input value, so it fails«Retrieval accuracy problem»Absent dependency relationships between tools

The ordering matters. Argument errors happen even when you have only ten tools. That is not a count problem; it is a schema description problem. In figures Anthropic published, adding tool use examples raised accuracy on complex parameter handling from 72 percent to 90 percent. No tools were removed to get that gain.

By contrast, wrong tool calls and over-calling only surface once the count grows. So if you are hitting argument errors in a five tool setup, introducing deferred loading or routing will change nothing. What needs fixing is the argument descriptions. Conversely, if wrong calls spiked right after you attached the fifth server, no amount of prompt polishing will address the root cause.

2. What tool definitions really cost in context

The numbers change your intuition. Here is the five server setup Anthropic Engineering used as an example.

Fifty-eight tools does not feel like «a lot». Five servers is an ordinary setup in 2026. Yet the definitions alone run roughly 55,000 tokens. On a 200K window that means more than a quarter is gone before the user types a single character. The same piece notes that inside Anthropic, tool definitions alone consumed 134,000 tokens before optimization.

2.1 Count and tokens are not proportional

The important column in that table is the rightmost one, not the total. Slack has 11 tools and costs nearly as much as GitHub's 35. That is about 1,900 tokens per tool, which is what happens when argument schemas are deep and enums are long.

This is why governing by tool count fails. Set an internal rule of «twenty tools maximum», attach twenty tools with deep schemas, and you have honored the count while blowing past 40K tokens. The unit to measure is definition tokens; the count is a proxy for selection difficulty. Track both, separately.

How to measure it right now. With the agent wired up, send any request and read the input token count on the first response. Then detach every tool and send the same request. The difference is your tool definition cost, and you pay it again on every request and every turn.

3. Why selection degrades as the count grows

There are three distinct causes. Each has a different remedy, so it pays to keep them apart.

3.1 The name space is small

There are only so many verbs worth putting in a tool name. search, find, query, list, get. Merge five servers and you have ten tools that mean the same thing. From the model's side, with search_issues, query_issues and list_issues sitting next to each other, the names alone provide no basis for deciding which one is correct.

3.2 Descriptions were written assuming solo use

This is the deeper cause. Each MCP server author wrote descriptions assuming their server would be the only one attached. In that context «Searches messages» was sufficient. Put five servers together and that description distinguishes nothing. This is why Anthropic's guidance on writing tools puts consolidating overlapping capabilities and refining descriptions near the front. A large share of what you are experiencing comes not from the model but from prose someone else wrote.

3.3 Context budget crowding

When definitions eat the window, the actual working context is pushed out: conversation history, file contents, intermediate results. Unused tools come from here. It is not that the tool is invisible; it is that the context that would give it a reason to be called got truncated. Why trying to govern this with longer prompts fails is covered separately in a long policy document will not govern your agent.

4. Narrowing technique one - deferred loading separates catalog from context

This is the highest leverage move. Keep everything in the catalog, but load only what is needed into context. The Claude API's tool search tool implements this server side, and OpenAI's function calling guide points in the same direction.

4.1 How it works

  • Put a search tool in the tool list and mark the rest with defer_loading: true
  • At least one tool must stay non-deferred. Deferring everything returns a 400
  • The initial context holds only the search tool and any non-deferred tools
  • When the model needs more, it searches, and matches come back as tool reference blocks that expand into full definitions
  • Search returns up to 5 matches by default, and up to 10,000 deferred tools are allowed per request
  • Search covers not just names but descriptions, argument names and argument descriptions

4.2 The most common misunderstanding: request size does not shrink

defer_loading controls what enters the context window, not what you put in the request body. Every tool's full definition, deferred ones included, must be transmitted on every request, because the server needs them to run the search and expand references. If you are enabling this to reduce network payload, you have the wrong feature.

4.3 Why prompt caching survives

This is the part that matters most operationally. Deferred tools are excluded from the system prompt prefix, and when discovered they are appended as a reference block inside the conversation. Because the prefix never changes, prompt caching holds. Contrast that with hand-rolled implementations that swap the tool array mid-conversation and invalidate the cache every time. One caveat: a deferred tool cannot also carry a cache control marker, and the API returns 400 if you try. Put the cache breakpoint on a non-deferred tool.

4.4 How much it helps, and when not to enable it

The published deltas: with tool search enabled, MCP evaluations moved from 49 percent to 74 percent for Opus 4 and from 79.5 percent to 88.1 percent for Opus 4.5. Token usage typically drops by more than 85 percent, with only the 3 to 5 tools actually needed loaded.

The counter-conditions are documented too. If you have fewer than 10 tools, use every tool on every request, or your definitions total under 100 tokens, do not enable it. You add a search round trip and have no tokens to save. The conditions to enable are 10 or more tools, definitions over 10K tokens, or aggregating MCP servers past the 200 tool mark.

5. Narrowing technique two - what search alone cannot do

A class of failure survives even after search is in place. That is the second layer.

Consider the request «refund my order». Search finds refundOrder exactly, because it is the closest match semantically. But that tool requires an order id, and findOrdersByEmail, which produces one, is semantically distant from the query and never makes the candidate set. Retrieval accuracy is perfect while no executable plan exists. That is the failure classified as «missing prerequisites» in the earlier table.

The Korean open source project graph-tool-call targets exactly this. The premise is to retrieve execution chains rather than isolated candidates.

  • Tool relationships are modeled as a directed graph of PRECEDES, REQUIRES and COMPLEMENTARY edges
  • Retrieval fuses four signals with reciprocal rank fusion: BM25 keywords, graph traversal, optional embedding similarity, and MCP annotations
  • Those annotations capture read-only, destructive and idempotent properties. Using them as ranking signals is the operationally significant part: you gain a place in the retrieval stage to push irreversible tools down
  • The output is not a list of tools but an ordered execution plan with the full prerequisite chain
  • It ingests OpenAPI/Swagger, MCP servers, LangChain and LangGraph, and plain Python callables. The core engine has no dependencies and the license is MIT

5.1 The reported numbers and how big they really are

The repository states the following. On a seven-case deterministic commerce regression, executable candidate plan coverage rose from 47.6 percent to 100 percent, and required-producer recall reached 100 percent as well. Across a 248 tool catalog it reports a 79 percent token reduction, rising to 92 percent with the LangChain gateway pattern. A separate example narrows 6 tools to 2 and cuts schema tokens from 1,476 to 160.

Read the magnitude honestly, though. A seven-case deterministic suite proves behavior, not performance. It does not imply the 100 percent holds as cases multiply. The place to evaluate this library is not the benchmark table but whether prerequisite relationships genuinely exist among your tools. In domains where lookups pair with actions, such as orders, payments, shipping and approvals, the value is real. In an environment of mutually independent read tools, there is no graph to draw.

6. Narrowing technique three - split the catalog itself

Where the first two make one agent handle a large catalog well, the third divides the catalog so each agent sees a small list. OpenAI's guidance also mentions splitting into role-specific subagents with roughly 4 to 6 tools each when the tool surface is large.

When is splitting right? Splitting on count alone loses. The criterion is boundaries.

  • When permission boundaries differ. If read-only lookups sit in the same list as writes and deletes, splitting alone shrinks the blast radius
  • When failure impact differs. Do not mix harmless tools with irreversible ones
  • When contexts do not overlap. Repository work and internal document search rarely reference each other's intermediate results
  • Conversely, do not split when intermediate results must flow back and forth. Every hop re-ships context and costs more than the tokens you saved

How to size the split itself is covered in how many subagents is enough, and the coordination cost of running several agents at once in Orch term, orchestrating multiple AI coding agents in one terminal window.

7. Narrowing technique four - names and descriptions, the cheapest and most deferred work

It costs almost nothing and almost everyone does it last. That order should be flipped. Do this first and the other three get stronger; skip it and all three lose effect. The reason is structural: search reads names, descriptions and argument descriptions.

  • Unify namespaces with prefixes. Prefix by service or resource, such as github_ and slack_, so one search catches the whole group
  • Put the user's words in the description. «Register a bug, task or ticket» overlaps real queries better than «Creates an issue»
  • Add one line of categories to the system prompt. Telling the model which families of tools are searchable cuts wasted searches
  • Fill in argument descriptions. This is the only place argument errors go down. Tool use examples moved complex parameter handling from 72 percent to 90 percent
  • Consolidate duplicates. Two tools that do the same thing are pure cost that raises selection difficulty
  • Watch which tools actually get discovered. A tool that search keeps missing is a tool whose description is written wrong

The regex variant has the model write re.search() patterns and match case-insensitively on substrings. Pattern length caps at 200 characters; natural language queries cap at 500. In other words, a tool can never be found by a word that appears nowhere in its name or description. Knowing just that changes how you write them.

8. Which one first - a decision table by scale

There is no reason to adopt all four at once. Different measures pay off at different scales.

ScaleDo firstDo not do yetWhy
Up to 10 / under 10K tokensStrengthen argument descriptions and examplesDeferred loadingThe search round trip is a net loss
10 to 30Unify namespaces, remove duplicate toolsSubagent splittingOverlap is the main cause; splitting costs more
30 to 50Adopt deferred loading, keeping 3 to 5 frequent tools loadedBuilding a graphThis is where selection accuracy starts to bend
50 to 200Deferred loading is mandatory, plus splitting on permission boundaries—Blast radius becomes as important as accuracy
200 and upSearch is assumed. Add prerequisites and execution chains—Failures where retrieval is right but execution is impossible dominate

The 30 to 50 band is the point Anthropic's documentation explicitly names as where the ability to select starts to degrade. OpenAI is more conservative, recommending fewer than 20 at the start of a turn while adding that this is a soft suggestion rather than a hard rule. The divergence is the point. This number is not a universal constant. Measure it yourself by growing the count against your own catalog, which is exactly what both vendors tell you to do.

9. What bites specifically in Korean development environments

9.1 Wrapping REST one to one explodes the tool count

This is the most common accident. Generate an MCP server from your internal API gateway's OpenAPI spec and every CRUD endpoint becomes a tool. A system with 50 APIs yields 200 tools, of which the agent will realistically ever need about ten. Autogeneration is convenient, and you pay for that convenience in tokens on every request.

The remedy is simple: do not expose generated tools as they are, regroup them into business units. Instead of making the agent compose «look up order, check status, cancel», wrap that into a single «cancel order» tool. It is better on both tokens and accuracy.

9.2 English tool names with Korean descriptions

This mix is everywhere in in-house tooling. Since search reads names, descriptions, argument names and argument descriptions together, the mix is not automatically a problem. But with the regex variant, the patterns the model constructs often lean on English roots. If the description is written only in Korean, the tool may never match.

The safe handling is to include key terms in both languages in the description: write the sentence in the local language and append the English keywords in parentheses, such as adding «(wiki document search)» after a localized description of an internal wiki lookup. That way either pattern hits. This is what the documented advice about putting user-facing task keywords in descriptions looks like when applied to a bilingual environment. The same applies to any non-English tooling, not just Korean.

9.3 Air-gapped networks cannot use server-side search

In finance and public sector environments where outbound API calls are blocked, you cannot enable a vendor's server-side tool search. Two paths remain. One is to implement client-side search yourself: when your own search tool returns tool references, the API expands them into definitions the same way, which is also where embedding-based retrieval fits. The other is to use a locally running library such as graph-tool-call to narrow the catalog outside the model. If you are pairing this with local models, local LLM agent development and why tool search and human-in-the-loop matter is worth reading alongside.

9.4 Irreversible tools such as approvals and outbound messages

Approval submissions, notification sends, customer-facing messages: internal catalogs inevitably mix in tools that cannot be undone once executed. Here the tool count question stops being an accuracy question and becomes a safety question. Do at least two things. Mark destructive properties explicitly in annotations so ranking and exposure push them back, and enforce a human confirmation immediately before execution. Prohibitions written as sentences are rarely honored.

10. How to read these numbers

Most of the improvements cited here are vendor self-evaluations or repository self-reported regressions. That is not a reason to discard them; it is a reason to decide which part to trust.

  • The direction is trustworthy. The conclusion that reducing exposure improves selection points the same way across different vendors and different methods
  • The magnitude does not transfer. 49 to 74 percent came from that evaluation's catalog, not yours
  • Read absolute levels alongside deltas. The RAG-MCP paper raised tool selection accuracy from 13.62 percent to 43.13 percent. That is more than tripling, but 43 percent is still under half. The accurate reading is not «search solves it» but «without search you cannot even start»
  • The boundary number differs by vendor too. The coexistence of 30 to 50 and 20 is itself evidence that this value moves with model, catalog and task

Measuring is not hard. Grow the tool count in stages against your own catalog and measure the success rate on the same task set. OpenAI's documentation recommends the same. Do it once and you can answer «how many tools is safe» internally with your own number rather than someone else's.

11. What could not be confirmed

The following were left out of the body as figures because no primary source could be pinned down.

  • Position bias. The claim that tools placed in the middle of a long list are chosen less often than those at either end appears in several places, but no verifiable primary source was identified
  • The baseline in graph-tool-call's regression. The pre-improvement value for required-producer recall is stated differently in the repository description and in the introductory post. Both agree the post-improvement value is 100 percent
  • The composition of the MCP evaluations. The tool counts and task counts behind 49 to 74 percent and 79.5 to 88.1 percent are not published
  • Independent large-scale measurement of accuracy versus tool count. No public third-party result varying only the count under identical conditions was found

12. Conclusion: this is not an argument for fewer tools

The claim here is not that you should attach fewer tools. It is that you should separate attaching from laying out. The catalog may hold hundreds while what sits in front of the model at the start of a turn stays under ten. It is because those two were bound to the same number that «adding tools makes it slow and wrong» became the shared experience.

Apply in this order and you will not waste effort.

  1. Remove duplicates. Delete tools that do the same job. Zero cost, immediate effect
  2. Names and descriptions. Unify prefixes, reflect user vocabulary, fill in argument descriptions
  3. Deferred loading. Past 30 tools this yields the largest single gain
  4. Prerequisites. Only when failures remain where retrieval is right but execution is impossible
  5. Catalog splitting. On permission boundaries and blast radius, not on count

One last misconception worth naming. «We only have 20 tools, so we are fine.» As the table showed, an 11 tool server can cost 21K tokens. The count is low, the tokens are high, and the names may still collide. Measure the definition tokens of what is attached right now, and list out the tools whose names look alike. Those two come before choosing which library to adopt.
