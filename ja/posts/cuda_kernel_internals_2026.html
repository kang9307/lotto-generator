CUDAカーネルを実行するとGPU内部で何が起きるのか

ホスト起動からワープ実行・メモリ階層・占有率まで — ステップ別完全解析

2026-07-01 開発・インフラ

はじめに：1行のコードが起動する巨大なパイプライン

ディープラーニングモデルの学習、GPU加速シミュレーション、高品質グラフィックスのレンダリング——いずれの場面でも私たちはCUDAカーネルを実行する。コード上は1行の起動呼び出しに過ぎないが、その裏ではホストCPUのドライバ呼び出し、GPUコマンドキュー、数千スレッドの同時スケジューリング、複数階層のメモリアクセスが有機的に連動している。

本稿は2026年6月時点の情報を基に、そのパイプラインを最初から最後までステップ別に解剖する。目標は二つだ。一つはGPUがなぜこのように動作するかという開発者レベルの直感を養うこと、もう一つはディープラーニングとAI推論加速の基盤がなぜCUDA内部構造に依存しているかを理解することだ。初めてvectorAdd<<<4096, 256>>>(a, b, c, N);を書くエンジニアも、GPU最適化を学ぶMLエンジニアも、この記事から具体的なメンタルモデルを得られるはずだ。

前提として一点明記する。GPUマイクロアーキテクチャの詳細は世代によって異なり、NVIDIAが公開していない部分も多い。ここではHopper(H100)とAda(RTX 40シリーズ)を基準に、公開ドキュメントとオープンな研究に基づいて解説する。数値は方向性を理解するためのものであり、精密なベンチマーク値ではない。

ステップ1：ホストからカーネル起動まで

1.1 nvccコンパイルパイプライン

CUDAコードは.cuファイルから始まりnvccを経由する。nvccはホストコードとデバイスコードを分離し、デバイスコードを二段階でコンパイルする。第一段階はPTX(Parallel Thread Execution)という仮想ISAへの変換だ。PTXは無限の仮想レジスタを仮定し、GPUマイクロアーキテクチャから抽象化された移植性の高い中間表現だ。第二段階は実際のGPU機械語であるSASS(Shader Assembly)への変換だ。RTX 4090はsm_89対象のSASSを生成する。最終バイナリのfatbinにはcubin(機械語)とPTXが一緒に収められ、実行ファイルに埋め込まれる。

1.2 ホストスタブとドライバ呼び出し

ランタイムでkernelFunc<<>>(args...)を呼び出すと、nvccが生成したホストスタブが実行される。スタブはランタイム登録テーブルからカーネルを見つけるキーとして機能し、引数をargument bufferに整列する。最初のGPU呼び出し時にはlibcuda.soが動的ロードされGPUコンテキストが作成される。初期化コストは大きいが以降は再利用される。

1.3 QMD・pushbuffer・GPFIFO・doorbell

ドライバはQMD(Queue Meta Data)を構成する。QMDはカーネル起動ディスクリプタであり、グリッドサイズ、ブロックサイズ、スレッドあたりレジスタ数、共有メモリ要求量、プログラム開始アドレス、カーネル引数のconstant bankアドレス、完了シグナル位置を全て含む。ドライバはこのQMDをpushbufferに書き込み、GPFIFOエントリがそれを指す。最後にdoorbell MMIOへの書き込みでGPUに新しい仕事が来たことを知らせる。ここから制御はCPUからGPUへ移る。

ステップ2：グリッド・ブロック・SMの構造

2.1 3段階の階層

CUDAの実行階層はグリッド → ブロック → スレッドの3段階だ。グリッドはカーネル起動1回に対応する最上位単位だ。グリッドもブロックも1D・2D・3Dで配置できる。この多次元構造は画像処理(2D)や体積シミュレーション(3D)などの問題でインデックス計算を自然にする。スレッドIDは行優先順序で線形化されてワープに割り当てられる。

2.2 SMへのブロック割り当て

GPUの物理的な実行単位はSM(ストリーミングマルチプロセッサ)だ。H100は144個、RTX 4090は128個のSMを持つ。カーネルグリッドのブロックはSMに分配される。同じブロック内のスレッドは必ず同じSM上で実行されるというルールが核心だ。これにより同じブロックのスレッドは共有メモリを共有し、__syncthreads()で同期できる。SMが一度に収容できるブロック数は、レジスタ・共有メモリ・ハードウェア制限によって決まる。

2.3 SM内部構造

SM内にはCUDAコア(FP32/INT32実行ユニット)、特殊関数ユニット(SFU)、テンソルコア(行列演算専用)、ワープスケジューラ、レジスタファイル、L1キャッシュ/共有メモリ(統合)がある。H100 SMには128個のFP32コアと4つのワープスケジューラがある。各ワープスケジューラは毎サイクル、eligible状態のワープから命令を発行できる。SMが多くのワープをin-flight状態で保持して交互に実行することが、GPUのレイテンシ隠蔽戦略の核心だ。

ステップ3：ワープとSIMT実行

3.1 ワープとは何か

ワープ(warp)はSMがスケジューリングする基本単位で、32スレッドで構成される。ブロックのスレッドはスレッドID順に32個ずつまとめてワープになる。256スレッドのブロックは8ワープになる。ワープ内32スレッドは同じ命令を同じクロックサイクルで実行する。これがSIMT(Single Instruction Multiple Thread)モデルだ。

3.2 SIMTとSIMDの違い

CPUのSIMDはプログラマまたはコンパイラが明示的なベクトル化を行う必要がある。SIMTはスレッドごとにスカラーコードを書くだけでハードウェアが自動的に並列化する。開発者体験がはるかにシンプルだ。ただし、SIMTはワープ内全スレッドが同じパスを実行するという前提の上に性能が成り立っている。この前提が崩れるとワープダイバージェンスが発生する。

3.3 ワープスケジューリングとレイテンシ隠蔽

SMは同時実行可能なワープより遥かに多くのワープをin-flight状態で保持する。あるワープがグローバルメモリアクセス待ち(数百サイクル)に入ると、スケジューラはそのワープを一旦置いてready状態の別のワープを即座に発行する。CPUのようにレジスタを保存/復元するコストがない。ワープのレジスタは切り替え中もSMのレジスタファイルにそのまま残っているからだ。これが「ゼロオーバーヘッドコンテキストスイッチング」だ。

ステップ4：ワープダイバージェンス — 条件分岐が性能を殺す理由

4.1 ダイバージェンスが発生する状況

ワープ内32スレッドがif・for・switchなどの条件文で異なる分岐を取るとワープダイバージェンスが発生する。GPUはSIMT方式なのでワープ全体が同じ命令を実行しなければならない。分岐が分かれると、Aパスを実行する時にBパスのスレッドはマスキング(無効化)され、Bパスを実行する時にAパスのスレッドがマスキングされる。結果として2つのパスを順次実行することになり、分岐が2つあれば実行サイクルが最大2倍になる。

4.2 ダイバージェンスを減らす設計原則

核心原則は同じワープ内のスレッドが同じコードパスを取るようにデータを配置することだ。奇数偶数スレッドが異なる分岐を取るコードは最悪のケースだ。データを事前にソートしたり、分岐条件がブロック単位で均一になるようにすれば、ダイバージェンスを最小化できる。現代のGPUはThread Block Compactionなどの技法でハードウェアレベルでダイバージェンスを一部緩和する。

ステップ5：メモリ階層 — レジスタからグローバルまで

5.1 レジスタ — 最速で最も制約がある

レジスタはスレッド専用の最速ストレージで、アクセスレイテンシは約1サイクルだ。H100 SMには65,536個の32ビットレジスタがある。スレッドあたりのレジスタ使用量が増えるとSMが同時収容できるスレッド(ワープ)数が減る。レジスタが不足するとレジスタスピル(spill)が発生してローカルメモリ(実際にはグローバルメモリ)に逃げ、性能が大幅に低下する。

5.2 共有メモリ — ブロック内スレッドの協調空間

共有メモリ(shared memory)は同じブロック内スレッドが共有するオンチップメモリで、アクセスレイテンシは約25サイクルだ——グローバルメモリ(約350〜1000サイクル)より数十倍高速だ。H100ではL1キャッシュと同じSRAMを共有し、SMあたり最大228KBに設定できる。__shared__キーワードで宣言する。行列積のタイリング最適化が共有メモリを活用する代表例だ。バンクコンフリクトに注意が必要だ。共有メモリは32バンクに分割されており、同じワープの複数スレッドが同じバンクにアクセスするとシリアル化される。

5.3 グローバルメモリ — 広大だが遅い

グローバルメモリはGPUのVRAM全体に相当し、全スレッドがアクセス可能だ。H100のHBM3は約3TB/sの帯域幅を持つが、レイテンシはTLBヒット時約350サイクル、ミス時1000サイクル以上だ。このレイテンシを隠すには十分なワープをin-flight状態に保つ必要があり、合着アクセス(coalesced access)が必須だ。ワープの32スレッドが連続したメモリアドレスにアクセスすれば1回のトランザクションで処理されるが、ストライドが大きいかランダムアクセスだと複数トランザクションに分解され帯域幅が無駄になる。

ステップ6：占有率(Occupancy) — SMをどれだけ埋めるべきか

6.1 占有率の定義と制約要因

占有率(occupancy)はSMに実際に割り当てられたワープ数をSMが支持できる最大ワープ数で割った比率だ。H100 SMは最大64ワープ、2048スレッド、32ブロックを収容できる。占有率を決める3つの制約がある。第一にレジスタ数：スレッドあたりレジスタが多いほどSMに入れられるスレッドが減る。第二に共有メモリ：ブロックが多くの共有メモリを使うほどSMに載せられるブロック数が減る。第三にブロックサイズ：ブロックが小さすぎるとSMあたり最大ブロック数制限にかかる。

6.2 占有率は高ければ高いほど良いのか

直感に反して、占有率20〜40%を超えると追加ワープの性能貢献は急速に小さくなる場合が多い。占有率を上げるためにレジスタを節約しすぎるとレジスタスピルが発生してかえって遅くなる。共有メモリをより多く使ってキャッシュヒット率を高める方が、ワープを追加するより効果的な場合も多い。CUDA Occupancy CalculatorやNsight Computeで実測することが感でチューニングするより遥かに正確だ。

ステップ7：カーネル完了と結果転送

グリッドの全ブロックが完了するとGPUはcompletion semaphoreをpostする。cudaDeviceSynchronize()やストリームイベントを待つとCPUがこのシグナルを受け取る。結果データをホストに戻すにはcudaMemcpy(DtoH)が実行され、データはGPUのVRAMからPCIeバスを通じてホストメモリへ移動する。単純なベクタ加算でもNsightで実測すると約10〜11μs、DRAM使用率80%程度、ワープ発行効率は5%前後にとどまる——典型的なメモリバウンドカーネルだ。

ステップ8：AI加速の基盤としてのCUDA内部構造

8.1 なぜGPUはディープラーニングに適しているのか

ディープラーニング学習の中核は行列積演算だ。何百万もの重みと活性化の行列を繰り返し掛け合わせる演算が、GPUのSIMT構造と完璧に一致する。同じ演算を異なるデータ位置に繰り返し適用するため、ワープダイバージェンスなしに数百のSMが同時に並列実行できる。H100の144SM × 128FP32コア = 18,432コアがこの並列性を活かす。テンソルコアはFP16/BF16行列演算をハードウェアで直接加速し、同じサイクルでFP32コアより遥かに高いTFLOPSを実現する。

8.2 FlashAttentionとメモリ階層意識のカーネル設計

TransformerのAttention演算はシーケンス長の2乗に比例するメモリアクセスが発生する。素直に実装するとグローバルメモリを繰り返し読まなければならず、強烈なメモリバウンドになる。FlashAttentionはAttention演算をタイル単位で分割し、各タイルを共有メモリ内で処理して最終結果だけをグローバルメモリに書き出す。アルゴリズムは同じだがメモリ移動は劇的に減る。これが2022年以降、大規模言語モデルの学習速度を数倍向上させた理由だ。CUDA内部構造を理解しないと、このような最適化は設計できない。

8.3 カスタムCUDAカーネルが必要な時

PyTorchやJAXのようなフレームワークは標準的な演算に最適化されたcuBLASやcuDNNカーネルを使う。しかし新しい演算子、特殊なスパース性パターン、ドメイン固有のカーネルフュージョンが必要な場合はカスタムCUDAカーネルが必要になる。その際、グリッド・ブロックサイズ、共有メモリ活用、合着アクセスパターン、ワープダイバージェンス最小化を直接設計しなければならない。Nsight ComputeはSMごと、ワープごとの粒度でボトルネックを特定できる。

一般開発者のための実践的示唆

バッチサイズとワープ活用

ディープラーニングでバッチサイズが小さすぎるとSMが半分も埋まらずGPU活用率が下がる。32の倍数でバッチサイズを設定するとワープが完全に埋まる。512や1024が一般的な出発点だ。ただし大きすぎるバッチはVRAMを超えてしまう。

テンソルサイズとメモリ整列

行列演算で行・列サイズが8や16の倍数になるとテンソルコアと合着アクセスパターンを最大限活用できる。整列していないサイズはパディングが生じたり追加トランザクションが発生して効率が落ちる。

大きなGPUを買う前にプロファイリング

遅いからといって無条件に大きなGPUを購入するのは誤りだ。まずNsight ComputeやPyTorch Profilerで現在のカーネルがコンピュートバウンドかメモリバウンドかを確認する。メモリバウンドカーネルにCUDAコアを追加してもほぼ効果がない。合着アクセスを改善したりカーネルフュージョンを適用したりすれば、同じGPUで数倍の速度向上が得られることもある。

結論：抽象化の下にある構造を知ることの力

kernel<<>>(args)の1行の背後には、コンパイルパイプライン、ホストスタブ実行、QMD構成、pushbuffer記録、doorbell信号、SMブロック割り当て、ワープスケジューリング、SIMT実行、メモリ階層探索、completion semaphoreまで続く長いパイプラインがある。これを知らなくてもディープラーニングコードを実行することはできる。しかしボトルネックを見つけ、最適化を設計し、メモリ階層を意識したカーネルを実装するには、この構造が生きた知識である必要がある。

大規模言語モデルが単位時間に処理するトークン数、Attention演算の速度、推論コストの多くは、CUDAカーネルがGPUのメモリ階層をどれだけうまく活用できるかにかかっている。AIインフラの真の基盤は抽象化されたフレームワークではなく、このGPU内部構造の上にある。2026年6月時点、この構造を理解することはMLエンジニアとインフラ開発者の双方にとって、ますます必須の素養になっている。
