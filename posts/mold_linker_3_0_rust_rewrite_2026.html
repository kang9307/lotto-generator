계기와 배경 — C++에서 Rust로의 전면 재작성과 Linux 배포판 기본 링커 목표

mold 3.0.0은 2026년 10월 5일에 릴리스된 고속 링커 mold의 첫 Rust 버전이다. 릴리스 노트는 2.42.1 릴리스 노트에서 예고한 대로 mold를 C++에서 Rust로 다시 썼으며, 2.42.1이 C++ 버전의 마지막 릴리스라고 적는다. 2026년 9월 11일에 올라온 2.42.1 노트는 재작성의 이유로 Rust가 2026년에는 시스템 소프트웨어에 쓸 만한 실용적 선택이 되었고 메모리 안전성 같은 강한 안전 보장을 제공한다는 점을 든다. 같은 노트는 사용자 입장에서 mold 3.0이 이전과 똑같이 동작하고 안쪽 구현만 바뀌는 것이 목표라고도 밝힌다.

3.0.0 노트가 적은 mold 3.x의 목표는 GNU ld와 남아 있는 호환성 격차, 특히 링커 스크립트(linker script) 지원을 메우고 mold가 Linux 배포판의 기본 링커로 채택되는 길을 닦는 것이다. 2.42.1 노트는 이를 더 풀어서 설명한다. 대부분의 Linux 배포판에서 시스템 링커인 /usr/bin/ld는 여전히 GNU ld이므로, 우선 링커 스크립트 기능을 구현해 사용자 영역 프로그램뿐 아니라 커널과 펌웨어도 링크할 수 있게 하고, 그다음 폭넓은 호환성 시험과 배포판 개발자와의 협력으로 채택을 현실적으로 만들겠다는 계획이다.

README는 별도로 속도 수치를 적는다. 2026년 8월 벤치마크에서 mold가 중앙값 기준으로 LLVM lld보다 4.9배, wild보다 1.9배 빠르게 링크했다는 내용이며, 전체 결과 표는 README의 Benchmark 절에 있다. 이 수치는 3.0.0 릴리스 노트가 아니라 README의 서술이므로 3.0.0과 2.42.1의 비교로 읽으면 안 된다.

이번 릴리스가 밝힌 지향점을 노트의 문구에 맞춰 정리하면 다음과 같다.

  • 드롭인 대체: 같은 명령행 옵션과 같은 타깃 아키텍처를 지원하고, 출력은 노트에 나열된 버그 수정을 제외하면 같다.
  • GNU ld와의 격차 해소: 링커 스크립트 지원을 비롯해 남아 있는 호환성 차이를 메우는 것이 3.x의 목표이다.
  • 배포판 기본 링커 채택의 기반: mold가 Linux 배포판에서 기본 링커로 채택되는 길을 닦는 것이 목표로 적혀 있다.
  • 손상된 입력에 대한 안전성: 범위 밖 읽기가 경계 검사를 거쳐 패닉으로 멈춘다.
  • 소스 빌드 방식의 변경: CMake가 Cargo로 바뀌었고 Rust 1.95 이상이 필요하다.

무엇이 바뀌지 않았는가 — v2.42.1 드롭인 대체와 동등한 링크 성능 및 검증

언어 재작성에서 사용자가 가장 먼저 묻는 것은 옵션이 달라졌는지, 느려졌는지이다. 릴리스 노트는 mold 3.0이 2.42.1의 드롭인 대체를 의도한 것이라고 적는다. 같은 명령행 옵션을 받고, 같은 타깃 아키텍처를 지원하며, 노트에 나열된 버그 수정을 제외하면 같은 출력을 만든다. 링크 성능에 대해서는 2.42.1과 동등한(on par) 수준을 유지한다고 적는다. 노트에는 링크 시간이나 메모리 사용량 수치가 없다.

지원 아키텍처는 README가 x86-64, i386, ARM 32/64, RISC-V 32/64, PowerPC 32/64, s390x, LoongArch 32/64, SPARC64, m68k, SH-4로 나열한다. 노트의 수정 목록에는 이 가운데 AArch64, ARM32, RISC-V, LoongArch, PPC32, PPC64, SH4, SPARC64, m68k에 해당하는 아키텍처별 항목이 따로 붙어 있다.

호환성 검증으로 노트가 든 것은 다음 세 가지이며, 마지막 항목은 호환이 적용되는 범위를 구분한다.

  • 모든 지원 타깃에서 테스트 스위트 실행: 지원하는 각 타깃에서 테스트 스위트를 돌렸다.
  • 폭넓은 실제 워크로드와 옵션 조합에서 출력 비교: 다양한 실제 워크로드와 옵션 조합에서 링커 출력을 비교했다.
  • Gentoo 전체 패키지 빌드: Gentoo의 모든 패키지를 빌드했고, 노트는 회귀를 발견하지 못했다(We found no regressions)고 적는다.
  • 호환의 범위는 링커의 옵션·아키텍처·출력: 같은 릴리스에서 빌드 시스템은 CMake에서 Cargo로, 테스트 실행은 ctest에서 cargo test로 바뀌었다. 소스에서 직접 빌드하는 쪽의 스크립트와 CI 설정은 그대로 쓸 수 없고, 아래 빌드 절에서 다루는 변경을 따라야 한다.

안전성 모델의 변화 — 세그멘테이션 오류(segfault)에서 패닉(panic)으로

노트가 안전성에서 말하는 것은 손상된 입력 파일(corrupted input files) 하나이다. C++ 버전은 이런 입력을 만나면 메모리를 범위 밖에서 읽고 세그멘테이션 오류로 종료할 수 있었다. Rust로 옮긴 3.0에서는 그 읽기에 경계 검사가 걸려 있어, mold는 잘못된 접근이 일어난 지점에서 패닉으로 멈춘다.

바뀌는 것은 멈추는 방식이다. 노트의 서술에 따르면 손상된 입력에서 segfault로 죽던 자리가 패닉으로 멈추는 자리로 바뀐 것이며, 링크가 성공하도록 손상을 복구한다는 말은 어디에도 없다. 정상 입력에서는 이 변화가 드러나지 않는다. 3.0의 출력은 버그 수정 항목을 제외하면 2.42.1과 같기 때문이다.

같은 노트의 버그 수정 목록에는 잘못된 입력이나 옵션 조합에서 깨진 출력이나 크래시 대신 오류를 내도록 바꾼 항목이 따로 있다. 이는 경계 검사와는 별개의 수정이며, 구체적인 항목은 아래 출력 정확성 절에 정리한다.

안전성 항목을 노트의 서술 범위 안에서 정리하면 다음과 같다.

  • 대상: 손상된 입력 파일을 처리할 때에 한정된 서술이다.
  • 이전 동작: C++ 버전은 범위 밖 메모리를 읽고 세그멘테이션 오류로 크래시할 수 있었다.
  • 3.0의 동작: 그 읽기에 경계 검사가 적용되어 잘못된 접근 지점에서 패닉으로 멈춘다.
  • 노트가 말하지 않은 것: 패닉 메시지의 형식, 경계 검사가 걸린 코드의 범위, 검사에 따른 성능 비용은 서술되어 있지 않다. 성능은 2.42.1과 동등하다는 문장만 있다.

빌드 및 패키징 절차의 변화 — Cargo 도입과 Rust 1.95+ 요구사항

소스에서 mold를 빌드하거나 배포판 패키지를 만드는 사람에게 가장 큰 변화는 빌드 시스템이다. 노트는 mold가 이제 CMake 대신 Cargo로 빌드되며 Rust 1.95 이상과 C 컴파일러가 필요하다고 적는다. CMake 옵션은 모두 제거되었다. README는 여기에 Git이 필요하고, 시스템의 Rust가 오래되었다면 rustup으로 안정(stable) 툴체인을 설치하라고 덧붙인다.

컴파일

README의 컴파일 절차는 다음과 같다. 실행 파일과 짝이 되는 preload 라이브러리는 각각 target/release/mold와 target/release/mold-wrapper.so에 만들어진다.

git clone https://github.com/rui314/mold.git
                    cd mold
                    cargo build --release

설치와 MOLD_LIBDIR

README는 sudo ./install-mold.sh를 실행하면 /usr/local 아래에 설치되고, 다른 접두 경로에 설치하려면 PREFIX를 지정하라고 안내한다. 노트는 설치 스크립트가 PREFIX와 DESTDIR을 받는다고 적는다. mold-wrapper.so는 $PREFIX/lib/mold에 설치되며, 설치하지 않고 target/release/mold를 바로 실행해도 된다.

sudo ./install-mold.sh
                    sudo PREFIX=/usr ./install-mold.sh

라이브러리를 $PREFIX/lib이 아닌 디렉터리, 예를 들어 /usr/lib64에 설치한다면 노트와 README 모두 MOLD_LIBDIR 환경변수를 그 디렉터리로 지정하라고 한다. cargo build를 할 때와 install-mold.sh로 설치할 때 둘 다 설정해야 하며, 그래야 mold -run이 mold-wrapper.so를 찾을 수 있다. mold -run은 README의 설명대로 LD_PRELOAD로 동반 공유 객체를 올려 exec 계열 호출을 가로채고, ld, ld.bfd, ld.gold, ld.lld 호출을 mold로 바꿔 주는 기능이므로 이 파일의 위치가 중요하다.

빌드와 시험 도구의 나머지 변경점은 다음과 같다.

  • 테스트 실행: ctest 대신 cargo test로 실행한다.
  • 테스트 의존성 스크립트: install-build-deps.sh가 install-test-deps.sh로 바뀌었으며, 이 스크립트는 테스트를 돌릴 때만 필요하다.
  • 타깃 선택: MOLD_TARGETS CMake 변수가 Cargo features로 바뀌었다. 노트는 이전처럼 배포판이 모든 타깃을 빌드해야 한다고 적는다.
  • CMake 옵션 제거: CMake에서 쓰던 옵션은 모두 사라졌으므로 기존 패키징 스크립트의 옵션 전달 부분은 고쳐야 한다.

의존성의 변화 — oneTBB 제거와 mimalloc 3.5.3 및 압축 라이브러리 구성

노트는 mold가 더 이상 oneTBB에 의존하지 않는다고 적는다. oneTBB를 대체한 병렬 처리 구현이 무엇인지는 노트에 서술되어 있지 않다. 나머지 의존성의 구성은 노트가 항목별로 밝힌다.

  • mimalloc 3.5.3 정적 링크: 이전과 마찬가지로 mimalloc 3.5.3을 정적으로 링크한다.
  • 시스템 할당기 선택: --features system-allocator로 빌드하면 시스템의 malloc을 사용한다.
  • 시스템 zlib: 시스템에 zlib가 있으면 그것을 링크한다.
  • zstd와 BLAKE3 포함: 두 라이브러리는 mold에 포함되어 있다.
  • 시스템 zstd 링크: ZSTD_SYS_USE_PKG_CONFIG=1을 설정하면 시스템의 zstd를 링크한다.

출력 정확성과 GNU ld·lld 호환성 개선 사항

3.0.0 노트의 Bug Fixes and Compatibility Improvements 절에는 공통 심볼 처리, 버전 스크립트 우선순위, 옵션 해석처럼 GNU ld와 lld의 동작에 맞춘 항목과 아키텍처별 수정이 길게 이어진다. 그중 옵션과 심볼 처리에 관한 대표 항목을 표로 옮긴다.

항목 3.0.0 노트의 서술 해당 옵션·맥락
같은 이름의 공통 심볼(Common Symbol) 크기가 다른 같은 이름의 공통 심볼은 가장 큰 크기와 가장 엄격한 정렬을 갖는다. GNU ld, lld와 같은 방식이다. 심볼 해석
출력 파일이 입력 파일이기도 한 경우 mold -r -o foo.o foo.o bar.o처럼 쓸 때 일어나던 크래시와 출력 손상을 고쳤다. -r (부분 링크)
섹션 가비지 컬렉션 --init과 --fini로 지정한 함수를 더는 제거하지 않는다. --gc-sections
동일 코드 병합 공유 라이브러리가 export한 함수를 더는 병합하지 않는다. --icf=all을 --emit-relocs와 쓸 때의 크래시도 고쳤다. --icf=safe, --icf=all
버전 스크립트 우선순위 한 심볼이 여러 버전 노드에 있으면 첫 번째 노드가 우선한다. GNU ld, lld와 같다. 버전 스크립트
단일 대시 옵션 해석 GNU ld가 읽는 방식으로 읽는다. 예를 들어 -entry=main은 -e ntry=main으로 읽히던 것이 고쳐졌다. 명령행 옵션
시작 시 가상 주소 공간 예약 시작할 때 8 GiB의 가상 주소 공간을 예약하지 않으므로 ulimit -v 아래에서도 동작한다. 프로세스 시작
비결정적 출력 여러 경우를 고쳤다. 노트가 든 곳은 --dependency-file, --repro, 같은 이름의 COMDAT 그룹이 많은 -r, 일부 동적 재배치이다. 출력 재현성

비결정적 출력 항목은 나열된 여러 경우(several cases)를 고쳤다는 서술이며, 출력이 모든 조건에서 바이트 단위로 같다는 보장은 노트에 없다. -r은 부분 링크이고 증분 링크가 아니다. 노트가 고쳤다는 것은 -r 사용 시의 크래시와 출력 손상이다.

표 밖의 항목도 있다. 이전에는 공유 라이브러리에 정의된 심볼에 대한 GOT 상대 재배치(R_X86_64_GOTOFF64, R_ARM_REL32)가 조용히 잘못된 주소를 얻었는데, 3.0에서는 올바르게 처리하거나 오류로 보고한다. --defsym이 공유 라이브러리의 심볼을 별칭으로 삼는 경우, 64비트에 맞지 않는 --defsym 값, 할당되면서 압축된 섹션, --strip-all과 --emit-relocs의 조합 같은 경우는 깨진 출력이나 크래시 대신 오류가 된다. 부분 링크에서는 두 번째 이후 입력 파일의 C++ 예외 코드가 깨지던 것과 --gc-sections가 재배치가 참조하던 데이터를 버리던 것도 고쳐졌다. AArch64, PPC32, ARM32에서는 범위 확장 썽크를 거친 호출이 Chromium의 ARM64 디버그 빌드 같은 큰 프로그램에서 잘못된 주소로 점프하던 문제가 수정되었다.

아키텍처별 항목은 더 구체적이다. AArch64에서는 R_AARCH64_TSTBR14와 R_AARCH64_GOT_LD_PREL19 같은 재배치 타입 지원이 늘었고, ARM32에서는 R_ARM_ALU_PC_G0와 R_ARM_THM_PC12 지원이 추가되었다. PPC32와 m68k에서는 -fpic 코드가 쓰는 16비트 오프셋에 GOT가 너무 크면 조용히 잘리는 대신 오류로 보고한다. 그 밖에 --separate-debug-file이 만든 파일에서 .gnu_debuglink 섹션이 빠졌고, 의미 없는 __start_EHDR 계열 심볼을 더는 만들지 않으며, MOLD_JOBS가 XDG_RUNTIME_DIR이 빈 문자열일 때도 동작한다.

mold 2.42.1(C++)과 mold 3.0.0(Rust) 구성 대조

두 버전의 구성 차이를 3.0.0 노트가 서술한 범위에서 대조한다. 노트가 말하지 않은 칸에는 서술이 없다고 적었다.

비교 항목 mold 2.42.1 (C++ 마지막 릴리스) mold 3.0.0 (Rust 첫 릴리스)
구현 언어 C++ Rust

정리하면 링커의 옵션과 출력은 이어지고, 소스 빌드 절차와 내부 구성은 바뀌었다. 위 표에서 2.42.1 쪽 칸은 3.0.0 노트의 변경 서술에서 거꾸로 읽어 낸 것이므로, 2.42.1 자체의 문서와 대조하면 표현이 다를 수 있다.

확인하지 못한 것

  • 3.0.0 릴리스 노트에는 링크 시간이나 메모리 사용량 수치가 없고 2.42.1과 동등하다는 서술까지만 있다. README의 4.9배·1.9배 수치는 2026-08-28 기준 소스로 빌드한 링커를 비교한 것인데, 어느 mold 버전을 쟀는지는 README에서 확인되지 않는다.
  • Rust 코드베이스의 전체 규모나 모듈 구성은 노트와 README에 서술되어 있지 않다.
  • 재작성에 쓰인 Rust 에디션은 명시되어 있지 않다.
  • 링커 스크립트 지원에서 어떤 기능이 아직 빠져 있는지는 노트에 목록이 없고, 남은 격차를 메우겠다는 목표만 적혀 있다.
  • Linux 배포판이 mold를 기본 링커로 채택하는 일정이나 논의 진행 상황은 서술되어 있지 않다.
  • 3.0.0으로 실제 프로젝트를 링크했을 때 2.42.1과 출력이 얼마나 다른지에 대한 비교 결과는 공개되어 있지 않다. 노트는 버그 수정 항목을 제외하면 같다고만 적는다.
