WARN 为什么会变成垃圾桶 - 如何就日志级别约定达成一致

级别不是严重程度的评分，而是发给读者的信号

2026-08-01 开发/基础设施

开篇: 警告日志一天三万行，没有人看

任何服务时间久了都会走到同一个状态。在面板上挂一个 WARN 过滤器，屏幕就无止境地往下滚，而没有人去看它。问一句「既然是警告，不是该看看吗」，大家都说是，但实际打开的人一个也没有。就在这期间，那真正需要看的一行混在其中滑了过去。

此时常见的处方是「把日志减下来」。这个目标是错的。问题不在量，而在于级别已经不再具有任何含义。如果 WARN 不意味着需要人动手，那么 WARN 过滤器就什么也没有滤掉，于是也就没有地方可以挂告警了。

本文的主张只有一句。级别不是「有多糟」的评分，而是发给读者的信号。只有当 ERROR 意味着「有人现在必须看」，你才能在它上面挂呼叫。如果 WARN 什么都不意味着，过滤器就失去了意义。所以日志级别约定不是编码口味，而是与告警直接相关的设计。

下面的一切都是实际跑日志器验证过的。改变阈值反复运行同一段代码看哪些行消失，把级别名称背后的内部数字打印出来，并测量了「被过滤的日志是免费的」这个说法。

运行环境。下面所有输出都是在 Windows 10 Pro (10.0.19045) 上实际执行的结果。工具是 Python 3.13.3 标准库中的 logging 与 Node.js v22.16.0 的标准库。这台机器上没有安装任何专门的日志库。尝试加载 Node 生态中广泛使用的两个包，两个都找不到模块，因此 Node 一侧只用 console 和 util.debuglog 做验证。没有把不存在的工具说成存在。

所有脚本都先写入文件再运行。把代码通过 shell 参数或 heredoc 传递会被悄悄改形。所有日志器名称与消息都是围绕一个虚构的订单与支付服务编造的。

本文不涉及的内容。日志记录该带哪些字段、个人信息在哪一步遮蔽、如何跨请求串联标识符，各自都是独立的主题。本文只停留在级别这一个点上。

1. 级别不是重要程度，而是切断的标准

先看级别到底做了什么。同样的八行只改阈值，跑了四遍。

python 3.13.3 / win32
--- 1-1. same eight calls, four thresholds ---

threshold = DEBUG     -> 8 of 8 lines survive
   DEBUG    cache miss key=order:8821
   DEBUG    sql took 12ms rows=3
   INFO     order 8821 accepted
   INFO     payment captured amount=19900
   WARNING  retry 1/3 upstream=billing
   WARNING  config key TIMEOUT missing, using default
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: (none)

threshold = INFO      -> 6 of 8 lines survive
   INFO     order 8821 accepted
   INFO     payment captured amount=19900
   WARNING  retry 1/3 upstream=billing
   WARNING  config key TIMEOUT missing, using default
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: DEBUG

threshold = WARNING   -> 4 of 8 lines survive
   WARNING  retry 1/3 upstream=billing
   WARNING  config key TIMEOUT missing, using default
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: DEBUG, INFO

threshold = ERROR     -> 2 of 8 lines survive
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: DEBUG, INFO, WARNING

代码一个字都没改，动的只有阈值一个。可是阈值每往上一档，就多消失整整一个级别。第一个结论由此而来。

  • 级别不是记录「这一行有多重要」的标签
  • 级别决定这一行在哪个阈值上消失。机制就这么多
  • 因此决定级别，就是决定让谁看到这一行
  • 两个人用不同级别记录同一个事实，等于把这个事实发给了两拨不同的读者

把单独一行拎出来，标注它在各个阈值下是否可见，就更清楚了。

--- 1-2. the same line, seen or not seen, by threshold ---
threshold  visible    note
--------------------------------------------------------------
DEBUG      True       written out
INFO       True       written out
WARNING    True       written out
ERROR      False      the call still ran
CRITICAL   False      the call still ran

请注意右边那一列。看不见并不等于没有执行。调用照旧发生了，只是结果被丢掉。这个事实直接引出后面关于成本的一节。

2. 级别只是整数 - 自定义级别的代价

级别的本质其实很简单。把内部数字原样打印出来看看。

python 3.13.3 / win32
--- 2-1. the levels are just integers ---
name       value
------------------------
NOTSET     0
DEBUG      10
INFO       20
WARNING    30
ERROR      40
CRITICAL   50

WARNING is WARN  : True
gap between them : 10

--- 2-2. wedging a custom level in between ---
   TRACE    5    entered handler
   DEBUG    10   cache miss
   INFO     20   order accepted
   NOTICE   25   deploy finished, build 4412
   WARNING  30   retry 1/3
   ERROR    40   capture failed

级别之间每档空出 10 并不是巧合。那是留给你往中间塞自己的级别用的。实际把 TRACE 注册在 5、NOTICE 注册在 25，它们就精确地排在数字所指的位置上。

不过这是有代价的。把一个没注册过的数字反查成名称，结果是这样。

--- 2-3. what a custom level costs you ---
threshold=INFO(20), NOTICE(25) and INFO(20) both pass:
   NOTICE   deploy finished
   INFO     order accepted

an unknown name reads back as a placeholder, not an error:
   getLevelName(25)  -> NOTICE
   getLevelName(23)  -> Level 23
   getLevelName(999) -> Level 999

a receiver that only knows the five names has to guess what 23 means.
the number sorts fine. the meaning does not travel.

关键在最后两行。数字能排序，含义传不过去。收到 23 的采集端只知道它比 INFO 重，至于这个级别意味着什么则无从得知。更麻烦的是它连报错都不会，而是安静地以 Level 23 这样的占位形式流下去。

  • 自定义级别只在你自己的进程内拥有名字
  • 如果采集、检索、告警那一侧不认识那个数字，这些行就成了既无法过滤也无法告警的灰色地带
  • 广泛引用的标准严重程度定义本身就明确指出，严重程度非常主观，接收方不应假定所有发送方都持有相同的定义
  • 所以实务上的建议很简单。要么不用自定义级别，要么用了就必须在采集端的配置里登记那个数字
  • 想增加级别的冲动，多半是你需要的是一个字段而不是一个级别的信号。「部署事件」应该用挂在 INFO 上的分类字段来解，而不是新开一个级别

3. 闸门有两道 - 日志器丢掉的东西回不来

处理级别时最常见的误解就在这里。阈值不止一个。日志器上有一个，每个输出目标上还各有一个。把两者组合起来跑了一遍。

python 3.13.3 / win32
--- 9-1. there are two gates, not one ---
4 calls each time: DEBUG, INFO, WARNING, ERROR

logger=DEBUG    console_h=NOTSET   audit_h=NOTSET   -> console 4, audit 4
logger=DEBUG    console_h=INFO     audit_h=ERROR    -> console 3, audit 1
logger=WARNING  console_h=DEBUG    audit_h=DEBUG    -> console 2, audit 2
logger=ERROR    console_h=DEBUG    audit_h=DEBUG    -> console 1, audit 1

--- 9-2. the practical shape: one lenient logger, several picky sinks ---
logger=DEBUG    console_h=INFO     audit_h=ERROR    -> console 3, audit 1

--- 9-3. the blunt instrument, and why it surprises people ---
logging.disable(WARNING) is active, logger level is DEBUG:
   ERROR line at ERROR
   -> 1 of 4 survived. it is a process-wide floor that outranks every logger.
   after disable(NOTSET): 4 of 4 survive again

看第三行和第四行。输出目标要的是 DEBUG，可日志器早就把那些行切掉了，所以毫无作用。日志器这道闸门先生效，输出目标只能把已经通过的部分再收窄。

  • 「我把输出目标设成 DEBUG 了还是什么都看不到」的反馈，绝大多数就是这个。没去看日志器那一侧
  • 实务上的布局基本形态是日志器宽松、输出目标各自收窄
  • 把人实时盯着看的控制台设为 INFO，把呼叫系统或工单队列读的那一侧设为 ERROR，一次写出的行就以不同形式到达两拨读者
  • 还有一个能给整个进程铺地板的开关。它比日志器配置更高一层，所以即便日志器是 DEBUG，4 行里也只活下来 1 行。如果某个库动了这个开关，你改哪里日志都出不来

4. WARN 是怎么膨胀起来的

回到开篇的症状。把一个小服务一天的量按调用点建模并聚合。

python 3.13.3 / win32
--- 3-1. one day of a small service, simulated ---
total lines/day : 61070
  ERROR          13    0.0%
  WARNING     30057   49.2%
  INFO        31000   50.8%

--- 3-2. inside WARNING, sorted by volume ---
call site                                         lines   share     cumul
--------------------------------------------------------------------------
deprecated field 'user_name' used by client        9800   32.6%     32.6%
cache miss, falling back to db key=%s              7400   24.6%     57.2%
optional header X-Trace absent                     5100   17.0%     74.2%
retry 1/3 upstream=billing                         4200   14.0%     88.2%
slow query 340ms                                   2600    8.7%     96.8%
config key TIMEOUT missing, using default 5s        880    2.9%     99.7%
token expires in 2 days                              60    0.2%     99.9%
disk usage 91 percent on queue volume                14    0.0%    100.0%
payment webhook signature mismatch                    3    0.0%    100.0%

lines a human should act on today : 77
lines emitted at WARNING           : 30057
signal ratio                       : 1 in 390

这张表就是「WARN 如何变成垃圾桶」的全部。按顺序读一遍。

  • WARN 占了全部的 49.2 个百分点。在一半都是警告的日志里，警告没有任何意义
  • 前三个调用点制造了 WARN 的 74.2 个百分点。那三万行不是「很多种警告」，而是「同样三行的重复」
  • 那三行分别是使用了废弃字段、缓存未命中、可选头缺失。没有一个是人需要行动的对象
  • 真正需要人看的是下面三条，一天 77 件。也就是390 行里有 1 行
  • 关键在于，制造出这个状态的并不是糟糕的开发者。每一个调用点在写下的那一刻都是合理的。只是「这不算正常，所以 WARN」这个判断累积了九次

还计算了在这种状态下挂告警会发生什么。

--- 3-3. what an alert on WARNING would do ---
  a  1-minute window carries     20.9 WARNING lines
  a  5-minute window carries    104.4 WARNING lines
  a 60-minute window carries   1252.4 WARNING lines
  an alert that pages on 'any WARNING' pages every window, forever.
  an alert that pages above a threshold has to sit above 20/min noise,
  which is higher than the 3 lines/day that actually mattered.

--- 3-4. same stream after reclassifying by 'must a human act now' ---
level          before      after
--------------------------------
ERROR              13         16
WARNING         30057         74
INFO            31000      48480
DEBUG               0      12500

WARNING/day : 30057 -> 74
ERROR/day   : 13 -> 16
now 'any WARNING today' is a 74-line list a person can read.
and ERROR stays small enough to page on.

这里就是本文主张显形的地方。能不能挂告警，取决于级别定义的质量。在每分钟流过 20.9 行的通道上，挂什么阈值都没用。真正重要的只有一天 3 行，而噪声地板远远高于它。

看看重分类之后的数字。日志总量仍然是 61,070 行，一模一样。减少的只有 WARN，取而代之的是 INFO 和 DEBUG 增加了。目标不是减少日志，而是让 ERROR 和 WARN 可读这句话，就原封不动地写在这张表里。

5. 判断标准 - 现在是否需要人行动

那么到底靠什么来分。用 Node 的标准库立了一条规则，并套到真实的调用点上。

node v22.16.0 / win32
installed logging packages on this machine: none
  require("winston") -> MODULE_NOT_FOUND
  require("pino")    -> MODULE_NOT_FOUND

--- 4-1. console has level-looking names but no threshold ---
method      stream    dropped when quiet
----------------------------------------------
console.log     stdout    never
console.debug   stdout    never
console.info    stdout    never
console.warn    stderr    never
console.error   stderr    never

there is no setLevel and no threshold. nothing is ever dropped.
a debug line in a hot loop is written in production exactly as
often as on a laptop. the four names only pick a stream.

--- 4-2. the stdlib does ship one gated channel: util.debuglog ---
NODE_DEBUG              : ""
payment channel enabled : false
db channel enabled      : false
(no channel output above: both are off)

这段输出告诉我们的事实很重要。有看起来像级别的名字，不等于具备级别功能。这个运行时默认的四个控制台函数没有阈值，它们唯一决定的是落到哪个输出流。实际运行时把标准输出丢掉，只剩下 warn 和 error。也就是说，只用这些函数的代码在生产环境里会把每一行 DEBUG 一条不落地写到磁盘上。

不过这个运行时的标准库里确实有一个可以开关的通道。只有在环境变量里点名该通道时才输出，而且代码可以询问它是否开启。实际只在环境变量里指定支付通道再运行，支付通道是 true，数据库通道是 false，只有支付那一行被输出。这就是后面要讲的「按模块降低级别」的最简形态。

5.1 换个问法，答案就收敛为一个

关于级别的争论之所以没完没了，是因为问题问错了。问「这有多严重」，答案就变成口味。必须换一个问法。

这一行出现时，人要做什么，什么时候做?

这个问题只有四个答案，而这四个答案正好就是四个级别。

级别一句话定义读的人要做什么时限告警
ERROR系统没能完成它该做的事，需要我们去修立刻查看半夜也要呼叫
WARN需要人动手，但不是今晚工作时间处理本周内每日汇总
INFO没有人需要行动，它记录系统做了什么只在事后追查时读-无
DEBUG只在复现缺陷时有用复现期间才打开-无

请注意定义里一个形容词都没有。「严重的」「重大的」「重要的」这类词，每个人画的线都不一样，正是它们让约定停留在文档里。而「会不会半夜叫醒人」，两个人会给出同一个答案。

代价最高的一个习惯。「不算正常，那就先记 WARN」正是造出第 4 节那三万行的原因。这个习惯有一条明确的替代规则。拿不准时就是 INFO。WARN 必须是一个只装「人本周要动手的东西」的窄抽屉，也只有在它保持窄的时候，打开它才有价值。

6. 捕获异常后在哪里记录

级别约定最常崩塌的地方是异常处理。把每一层都捕获、记录并重新抛出的常见写法原样跑了一遍。

python 3.13.3 / win32
--- 5-1. log-and-rethrow at every layer ---
   ERROR    app.db         db call failed: connect timeout to billing-db after 3000ms
   ERROR    app.service    could not load order: connect timeout to billing-db after 3000ms
   ERROR    app.api        request failed: connect timeout to billing-db after 3000ms
   -> 3 ERROR lines, 1 actual failure, 1 user-visible 500

--- 5-2. raise once, log once at the boundary that decides ---
   ERROR    app.api        request failed order=8821
   + 8 traceback lines attached to that single record
   -> 1 ERROR line, and it carries the full stack

--- 5-3. exception that was recovered from ---
   INFO     app.service    retry 1/3 after connect timeout
   INFO     app.service    retry 2/3 after connect timeout
   result: {'order': 8821}
   nothing failed for the user, so nothing is ERROR

--- 5-4. exception deliberately ignored ---
   5 lines at DEBUG (traceback included)
   visible only when someone turns DEBUG on for this module

第一块就是问题。真实故障只有 1 件，却留下了 3 行 ERROR。用户看到的错误也是 1 件。在这种状态下统计「一天多少条 ERROR」，得到的是故障条数的三倍，而挂在上面的告警阈值会把这个倍数原样继承为误差。

第二块是解法。往上抛的那些层什么都不记，因为抛出本身就是一层告诉调用方的方式。取而代之的是，决定放弃的那一个边界附上调用栈只记一次。结果是 1 行 ERROR 带 8 行调用栈。行数降到三分之一，信息量反而上升了。

情形级别谁来记录依据
通过重试恢复INFO完成恢复的那一层对用户什么都没发生
吞掉了，没有影响DEBUG吞掉它的那一层只在复现期间才需要
重新抛给上层没有人记录-抛出本身就是消息
变成 500ERROR放弃的那一个边界需要我们去修
变成 400INFO同一个边界错的是调用方
  • 「怕以后找不到原因」而层层都记的习惯，一份调用栈就能完全取代
  • 把重试记成 WARN，正是造出第 4 节那 4,200 行的原因。既然恢复成功了，那就不是失败
  • 被记了三次的异常事后无法分辨是同一件事还是三件事，在缺少按请求的标识符时尤其如此
  • 把客户端发错的请求记成 ERROR，等于别人制造的流量在按响你的呼叫。你把一个可以呼叫你的按钮交到了外面

7. 被切掉了，但钱已经花了

把第 1 节末尾「看不见并不等于没有执行」这一点用数字确认一下。把阈值设为 WARNING，对 20 万次 DEBUG 调用用五种写法计时。

python 3.13.3 / win32
one run on one machine. treat the ratios, not the absolute numbers.

--- 6-1. cost of a DEBUG line that is thrown away (threshold=WARNING) ---
form                                  total sec    per call us   vs guard
--------------------------------------------------------------------------
f-string built up front                  0.8994          4.497
json.dumps built up front                0.8100          4.050
%-style args, lazy                       0.0416          0.208
isEnabledFor guard                       0.0226          0.113       1.0x
no logging call at all                   0.0081          0.040       0.4x

f-string form is 39.9x the guarded form
json form is     35.9x the guarded form
lazy %-args is   1.8x the guarded form

all five produced ZERO output lines. the threshold was WARNING throughout.

--- 6-2. where the money actually goes ---
building the string only        : 0.8064 sec  (4.032 us/call)
calling lg.debug('x') only      : 0.0373 sec  (0.187 us/call)
-> the call itself is cheap. the argument you built is not.

--- 6-3. at production volume ---
    1000 debug calls/sec -> eager    4.5 ms/sec of cpu, guarded   0.1 ms/sec
   20000 debug calls/sec -> eager   89.9 ms/sec of cpu, guarded   2.3 ms/sec
  and none of it reaches a file, because DEBUG is off.

--- 6-4. the same guard, when DEBUG is ON ---
threshold=DEBUG, 20000 lazy calls : 0.3750 sec (18.749 us/call)
bytes written                     : 2960000
-> once the line is kept, formatting happens anyway. lazy only helps when filtered.

这些数字是在这台机器上测了一次得到的。换一台机器、换一个构建、换一种负载，绝对值都会变。请带走比例，而不是墙钟时间。重新测一遍，你的环境里大致也会是同样的顺序。

读法是这样的。

  • 五种写法的输出都是 0 行。阈值是 WARNING，所以 DEBUG 全部被切掉了
  • 可是提前拼字符串的写法，比先检查阈值再拼的写法慢了 39.9 倍。被过滤掉的是输出，不是拼装的开销
  • 钱花在哪里由 6-2 回答。日志器调用本身每次 0.187 微秒，很便宜。而构造要传进去的字符串要 4.032 微秒。贵的是参数，不是调用
  • 把格式字符串和值分开传的延迟求值写法只要 0.208 微秒，比提前拼便宜二十倍以上，因为只有通过阈值的行才会被组装
  • 在每秒两万次的规模上，这个差距变成CPU 89.9 毫秒对 2.3 毫秒。而且这一切一个字都没有落到文件里
  • 最后一块把天平扶正了。一旦通过阈值，格式化终究会发生。延迟求值只在被丢弃时才划算，一打开 DEBUG 就跳到每次 18.749 微秒

归纳成实务规则就是三句。参数用延迟求值传递。序列化这类昂贵的参数只在确认阈值之后才构造。以及，在知道打开 DEBUG 并不免费的前提下再打开它。

8. 不重新部署也能改级别

要让约定真正落地，降低级别这件事必须容易。做得麻烦，人们就会「怕以后要看」而预先提到 WARN，那就变成了第 4 节的三万行。把日志器名称做成层级跑了一遍。

python 3.13.3 / win32
--- 7-1. baseline: root of the tree at WARNING ---
shop=WARNING  -> 1 lines
   WARNING  shop.payment.gateway retry 1/3

--- 7-2. same process, one line changes the threshold ---
shop=INFO  -> 4 lines
   INFO     shop.db            pool size 8/20
   INFO     shop.payment       capture ok order=8821
   WARNING  shop.payment.gateway retry 1/3
   INFO     shop.web           200 GET /orders/8821 12ms

--- 7-3. turn up ONE module only, leave the rest alone ---
shop=WARNING, shop.payment=DEBUG  -> 4 lines
   DEBUG    shop.payment       building capture request amount=19900
   INFO     shop.payment       capture ok order=8821
   DEBUG    shop.payment.gateway http POST /v1/charges
   WARNING  shop.payment.gateway retry 1/3
   note shop.payment.gateway inherited DEBUG from its parent

7-3 是关键。只把支付模块降到了 DEBUG，其余一概没动。可是它下面的网关日志器也跟着降了下来。为什么会这样，下一段输出给出了解释。

--- 7-4. effective level is resolved by walking up the name ---
logger                   own level    effective
--------------------------------------------------
shop                     WARNING      WARNING
shop.db                  DEBUG        DEBUG
shop.payment             NOTSET       WARNING
shop.payment.gateway     NOTSET       WARNING
shop.web                 NOTSET       WARNING
NOTSET means 'ask my parent'. that is why one name can steer a whole subtree.

--- 7-5. driving it from the environment, no redeploy ---
  LOG_LEVELS=shop=WARNING                       -> 1 lines
     WARNING  shop.payment.gateway retry 1/3

  LOG_LEVELS=shop=WARNING,shop.payment=DEBUG    -> 4 lines
     DEBUG    shop.payment       building capture request amount=19900
     INFO     shop.payment       capture ok order=8821
     DEBUG    shop.payment.gateway http POST /v1/charges
     WARNING  shop.payment.gateway retry 1/3

  LOG_LEVELS=shop=ERROR,shop.web=INFO           -> 1 lines
     INFO     shop.web           200 GET /orders/8821 12ms

--- 7-6. the safety rail: a raise-only window ---
  shop=DEBUG                         depth=0  allowed=False
  shop.payment=DEBUG                 depth=1  allowed=True
  shop.payment.gateway=DEBUG         depth=2  allowed=True
  • 把子日志器保持未设置状态就会委托给父级。这正是一个父名称能操纵整棵子树的原因
  • 反过来，在子级上钉死一个值，改父级也带不动那根枝。如果启动时有代码给每个日志器都设了级别，运行期的调整就被整个堵死了
  • 从环境变量接收 名称=级别 列表再应用，就能不重启进程地改变过滤。7-5 的三段是在同一个进程里依次执行的结果
  • 请留意 7-5 的最后一例。把顶层提到 ERROR 之后，网关的 WARNING 消失了。因为子级未设置，继承了父级的 ERROR。委托是双向起作用的
  • 需要一道护栏。拒绝把顶层名称整体降到 DEBUG 的请求，只对子模块放行。否则一个拼写错误就能让集群淹没在自己的日志里
  • 给临时降低的级别加上过期时间。忘记恢复才是默认结局

9. 制定约定 - 团队要达成一致的事

以上是材料。接下来整理团队实际要写进文档的内容，以及如何回收一个已经堆了三万行的仓库。

约定条目具体写什么不写的话
级别定义每个级别一句话，用行动表述，不用形容词每个人画的线都不一样
告警对照表哪个级别去哪里，就写在定义旁边定义会和告警分头漂移
提升级别的流程提到 ERROR 会触发呼叫 → 需要评审者签字ERROR 会悄悄膨胀
降低级别的流程任何人，和噪声反馈放在同一批改动里降级太麻烦，没人愿意做
必填字段无论什么级别，每条记录都带同一组项目不同级别的检索方式会不一样
ERROR 预算每天 N 条。超过就是约定坏了，而不是代码坏了没有基准，也就没有回收的契机
自动降级规则30 天内无人处理的行默认降级一旦提上去的级别就永远留着

  7. 在同一批改动里修告警规则。只改级别不改告警，约定就只留在文档里

9.2 检查清单

  • 级别定义写成行动句(没有形容词)
  • ERROR 的定义和告警规则在同一份文档里
  • 「重试成功」没有被记成 WARN
  • 「客户端输入错误」没有被记成 ERROR
  • 同一个异常只在一个地方记录
  • 调用栈只在放弃的边界处附加一次
  • 没有提前拼装 DEBUG 的参数
  • 昂贵的参数只在阈值检查之后构造
  • 无需重新部署即可按模块降低阈值
  • 临时降低的级别带有过期时间
  • 有机制阻止把顶层名称整体降到 DEBUG
  • 定下了 ERROR 的每日预算，并规定了超标后的应对
  • 不使用自定义级别，或者使用了但采集端知道那个数字的含义
  • 有定期巡检，找出 30 天内无人处理的 ERROR 与 WARN 行
  • 定期查看头部调用点所占的比例

结论: 级别就是告警的设计

回到开篇的问题。WARN 为什么会变成垃圾桶？不是因为开发者糟糕。而是因为「这不算正常，那就先记 WARN」这个判断，在每一次都各自合理的情况下累积了九次。结果就是第 4 节那 390 比 1。

如果只带走一件事，就带走这个。决定级别，就是决定这一行写给谁看。问「有多糟」，答案就变成口味，而口味永远达不成一致。问「谁在什么时候做什么」，答案就收敛为一个，而那个答案本身就是你的告警规则。

所以制定约定不是文书工作。只有当 ERROR 意味着「现在就看」，你才能在它上面挂呼叫；也只有在 WARN 保持窄的时候，那个抽屉才值得打开。过滤器有没有意义，全押在这一页约定上。

最后，被广泛引用的标准严重程度定义本身也承认了这一点。它写道，严重程度非常主观，接收方不应假定所有发送方都持有相同的定义。意思是连标准也不会替你写下定义。那份定义必须由团队自己来写。

# 日志级别约定 — 可直接复制的定义表、重分类步骤与检查清单

> 来源: braindetox.kr — WARN 为什么会变成垃圾桶
> 验证环境: Windows 10 / Python 3.13.3 标准 logging / Node.js v22.16.0
> 原则: 级别不是严重程度的评分，它声明的是**谁在什么时候做什么**

## 1. 级别定义表 — 用行动来写

| 级别 | 一句话定义 | 读的人要做什么 | 时限 | 告警 |
|---|---|---|---|---|
| **ERROR** | 系统没能完成它该做的事，需要我们去修 | 立刻查看 | 半夜也要 | 呼叫 |
| **WARN** | 需要人动手，但不是今晚 | 工作时间处理 | 本周内 | 每日汇总 |
| **INFO** | 没有人需要行动，它记录系统做了什么 | 只在事后追查时读 | — | 无 |
| **DEBUG** | 只在复现缺陷时有用 | 复现期间才打开 | — | 无 |

整个判断归结为一个问题。

> **这一行出现时，人要做什么，什么时候做?**

问「有多严重」，答案就变成口味。问「谁在什么时候行动」，答案就收敛为一个。

### 团队每次都会弄错的两行

| 情形 | 常见选择 | 正确选择 | 原因 |
|---|---|---|---|
| 重试后成功 | WARN | **INFO** | 对用户什么都没发生 |
| 客户端发来损坏的 JSON | ERROR | **INFO** | 返回 400 说明系统运转正常 |
| 缓存未命中 | WARN | **DEBUG** | 缓存正按设计工作 |
| 使用配置默认值 | WARN | **INFO** | 有默认值本身就是正常路径 |
| 证书还有 9 天到期 | INFO | **WARN** | 人需要在本周动手 |
| 支付扣款失败 | WARN | **ERROR** | 钱没动，而且要我们去修 |

## 2. 捕获异常后在哪里记录

| 情形 | 级别 | 谁来记录 |
|---|---|---|
| 通过重试恢复 | INFO | 完成恢复的那一层 |
| 吞掉了，没有影响 | DEBUG | 吞掉它的那一层 |
| 重新抛给上层 | **没有人记录** | 抛出本身就是消息 |
| 变成 500 | ERROR | 放弃的那一个边界 |
| 变成 400 | INFO | 边界处。错的是调用方 |

**同一个异常被记录三次**，来自每一层都捕获、记录、再抛出。
实际运行的结果是：1 次故障产生 3 行 ERROR，而用户可见的错误只有 1 个。
只在边界处记录一次并附上调用栈，ERROR 降到 1 行，信息量反而更多。

## 3. 团队必须写进文档的条目

| 条目 | 为什么需要 |
|---|---|
| 四到五条级别定义 | 用**行动**表述，而不是严重程度 |
| 提升级别的流程 | 提到 ERROR 会触发呼叫，需要评审者签字 |
| 降低级别的流程 | 任何人都可以，和噪声反馈放在同一个 PR |
| 必填字段 | 无论什么级别，每条记录都带同一组字段 |
| ERROR 预算 | 每天超过 N 条，坏掉的是约定而不是代码 |
| 自动降级规则 | 30 天内无人处理的行默认降级 |
| 哪个级别通向哪个告警 | 不写在定义旁边，定义就会漂移 |

## 4. 重分类既有日志的步骤

1. **按调用点统计，而不是按行。** 以模板聚合。前十名通常占到总量的九成。
2. **让算术完成第一轮筛选。** 一个每天触发超过 500 次的 ERROR 或 WARN 调用点，不可能是人能行动的对象。这一步不需要判断。
3. **对源码跑正则收集候选。**
   - `\.error\(.*(retry|fallback|cached)` — 已经恢复却记成 ERROR
   - `\.error\(.*(client|invalid|parse|malformed)` — 错在调用方却记成 ERROR
   - `\.(warn|warning)\(.*(cache miss|deprecated|retry)` — 没人看的 WARN
   - 正则找到的只是**候选**。判定要由人逐条确认。
4. **先降级，后升级。** 降级容易撤回，而且不触碰告警。
5. **一个 PR 只改一个模块。** 切到评审者能真正判断每一行「谁在什么时候」的大小。
6. **测量前后。** 目标不是日志更少，目标是 **ERROR 和 WARN 短到能读完**。总行数上升也没关系。
7. **在同一个 PR 里改告警规则。** 只改级别不改告警，约定就只活在文档里。

### 值得追踪的指标

| 指标 | 目标 | 含义 |
|---|---|---|
| 每日 ERROR 数 | 一个人能读完的数量 | 超过之后呼叫会被无视 |
| 每日 WARN 数 | 站会上能扫一眼的数量 | 超过之后过滤器失去意义 |
| 实际被处理的 ERROR 占比 | 越高越好 | 偏低说明 ERROR 的定义是错的 |
| 前三名调用点的占比 | 越低越好 | 偏高说明一两行吞掉了整个日志 |

## 5. 在生产环境改级别

- 阈值按**日志器名称**设置。名称用点号分层，一个父名称就能操纵整棵子树。
- 子日志器默认保持**未设置**，让它委托给父级。正因如此，改一行才能影响整棵子树。
- 从环境变量或配置端点接收 `名称=级别` 列表并应用。**不应该需要重新部署。**
- 安全护栏：拒绝把顶层名称整体降到 DEBUG 的请求，只对**子模块**放行。否则一个拼写错误就能让集群淹没在自己的日志里。
- 给临时降低的级别设置**过期时间**。忘记恢复才是默认结局。

### 不要混淆两道闸门

先是日志器的阈值生效，然后才是各个输出目标(sink)的阈值。
**日志器丢掉的东西，把 sink 调得再低也回不来。**
「我把 sink 设成 DEBUG 了，还是什么都看不到」几乎都是这个原因。

实务上的布局通常是这样。

- 日志器：宽松，先让记录被创建出来
- 控制台 sink：INFO，人实时盯着看的东西
- 告警 sink：ERROR，呼叫系统或工单队列读的东西

## 6. 成本规则

- **即使被过滤器丢弃，提前拼装参数的开销也已经付出了。** 先拼接字符串或序列化再交给日志器，那一行被扔掉与否，CPU 都花掉了。
- 参数用**延迟求值**传递。把格式字符串和值分开传，只有通过阈值的行才会被组装。
- 昂贵的参数(序列化、遍历大集合)只在**确认阈值之后**才构造。
- 一旦通过阈值，格式化终究会发生。延迟求值只在**被丢弃时**才划算。

## 7. 上线前检查清单

- [ ] 级别定义写成**行动句**(没有「严重的」「重要的」这类形容词)
- [ ] ERROR 的定义和**告警规则在同一份文档里**
- [ ] 「重试成功」没有被记成 WARN
- [ ] 「客户端输入错误」没有被记成 ERROR
- [ ] 同一个异常**只在一个地方**记录
- [ ] 调用栈只在**放弃的边界**处附加一次
- [ ] 没有提前拼装 DEBUG 的参数
- [ ] 昂贵的参数只在阈值检查之后构造
- [ ] 无需重新部署即可**按模块**降低阈值
- [ ] 临时降低的级别带有**过期时间**
- [ ] 有机制阻止把顶层名称整体降到 DEBUG
- [ ] 定下了 ERROR 的**每日预算**，并规定了超标后的应对
- [ ] **不使用**自定义级别，或者使用了但采集端知道那个数字的含义
- [ ] 有定期巡检，找出 30 天内无人处理的 ERROR 与 WARN 行
- [ ] 定期查看头部调用点所占的比例

## 8. 不要做的事

- 拿不准就写 WARN — 拿不准时答案是 INFO。WARN 只装人本周要动手的东西
- 用严重程度的形容词写定义 — 「重大」的界线人人不同
- 每一层都捕获、记录、再抛出 — 一次故障变成好几行，所有统计都被扭曲
- 因为数字能排序就塞进自定义级别 — 顺序是对的，但**含义传不到采集端**
- 只改级别却不动告警规则 — 约定只会留在纸面上
- 把日志总量当成目标 — 目标是 **ERROR 和 WARN 被人读到**
- 只调低 sink 的阈值而不看日志器 — 日志器丢掉的东西回不来
- 因为一直如此就保留旧级别 — 没人处理的行就是降级候选
