手里有一个没有格式文档的文件时 - 从字节读出结构的顺序

先怀疑什么，每个信号究竟能确定到哪一步，以及法律设下了什么条件

2026-09-05 开发/基础设施

总有那么一天，一个后缀陌生、打开不是文字、又找不到人问的文件落到手里。退役设备留下的日志、已经停服的软件的存档、没有任何交接文档就转过来的内部工具的输出，大多如此。这种时候需要的不是工具而是顺序。无论打开哪个工具，屏幕上出现的终究是同样的字节，而你先怀疑什么，决定了这件事要花多久。

本文整理的就是这个顺序。把字节泄露的信号逐个分开，对每一个划清它能确定什么、又永远确定不了什么。然后再看如何把推断出的结构重新问回文件，以及法律对这类工作设下的条件。工具只作为辅助这套流程的手段出现。

本文的法律部分仅供信息参考，不构成法律意见。条文是查阅原典后引用的，但某个行为是否落入某条，取决于对象、目的和生效的合同。具体个案的判断属于主管机关和法律专业人士。 本文也不涉及绕过保护措施的方法，那一片领域在此处整理的流程之外。

缘起 - 「未知格式」这个说法藏起的前提

2026年8月27日，开发十六进制编辑器 ImHex 的作者发表了一篇文章，讲述如何逆向一个未知的文件格式。内容是打开某款游戏的存档文件，一直做到每个字节都有名字为止，随后也被转到了韩国的开发者社区。这是一篇好文章。但只看标题就转述的人，会整个漏掉一个重要前提。

那篇文章的方法不是盯着字节看，而是去读写出这个文件的程序的代码。作者自己在开头附近就写明了：打开文件能看到明文字符串，所以既没压缩也没加密，这一点清楚；但没有识别用的魔数，工具的检测也说不出类型，没有更多信息的话到此为止。那句话之后的全部内容都是反编译。

文章最后归纳的通用流程有四步。确认它是不是已知格式，找到读写该文件的代码，分析代码找出所用的基本构件，把发现写成模式文件边记录边验证。顺序是准确的。但实务中卡住的地方，往往是第二步。有时代码不存在，有时存在却看不到，有时看得到却不该看。

到那一步，剩下的就只有字节。本文讲的正是那片地方：在看不到答案的情况下如何一步步收窄结构，以及这样得到的结论与看过答案的结论有什么不同。如果你关心工具本身，另有一篇讲为某种特定二进制格式打造的分析工具的文章；语言模型改变了这项工作的哪一部分，则在让代码变得可读与说它是对的之间的差别一文中讲过。这里不重复。

第零步 - 先排除它是已知格式

在推断结构之前该做的，是确认根本不需要推断。身份不明的文件里，相当一部分是已知格式，只不过后缀陌生，或者装在另一种格式里面。原文下面的一条评论开玩笑说，未知格式有一半是压缩包里装着嵌入式数据库。夸张归夸张，方向是对的。

排除分三层做。第一，把开头几个字节交给签名数据库去查。几乎所有十六进制编辑器和文件识别工具都带这个功能。第二，看它是不是容器。压缩归档格式的本地文件头以 50 4B 03 04 开头，但相当于目录的中央目录在文件末尾，标记末尾的那条记录以 50 4B 05 06 开头。习惯只扫开头几百字节的人，会周期性地漏掉这里。第三，看末尾和中间。前面被拼上别的数据的文件，只看开头是认不出来的。

把目录放在末尾是有原因的。在顺序写出的流里，写完之前不知道每一项最终有多大。于是先把各项流出去，最后再补上目录。知道这个设计习惯，在身份不明的文件里也有了从后往前翻的理由。格式是假定整个文件会装进内存而设计的，还是为流式写出而设计的，会改变整体结构的样子。

如果在这一步认出了身份，这天的活基本就完了。规格文档握有答案，多半还已经有现成的解析器，剩下的只是把它接起来。反过来说，跳过这一步而直接开始推断的代价，是有可能花好几天去重新发现一份别人早就写好并公开的东西。只有排除失败，才往下走。

信号一 - 魔数究竟确定了什么

文件开头的固定字节序列，是最先撞进眼里的信号。设计良好的格式会慎重使用这个位置。以 PNG 为例，数据流的前八个字节永远是 89 50 4E 47 0D 0A 1A 0A，规格写明这段签名把 PNG 与其他类型的数据流区分开，并使某些传输错误得以及早发现。同一份规格还要求解码器校验全部八个字节，并补充说：如果随后的八个字节是一个长度正确的头部分块的开始，解码器对数据流完整性可以更有把握。

换句话说，魔数说的是「意图是这种格式」而不是「就是这种格式」。这个区别在实务中会在下面这些地方咬人。

  • 能确定的 — 生产方意图使用某种格式这一事实，以及去找那份规格文档的理由
  • 不能确定的 — 内容是否真的是那种格式、版本是什么、后半段有没有被截断或改动
  • 没有魔数说明了什么 — 不等于没有格式。 从不与外部交换的内部格式，根本没有理由放识别标签
  • 常见反例 — 多种格式共用相同的开头字节，魔数不在文件起始位置，只看得到外层容器的魔数而看不到内层的
  • 开头若有人类可读的 ASCII，先去搜它。那多半是格式名或产品名，仅凭这一串字符串就查出规格文档的情况并不少见

在身份未明的状态下，即便每个文件开头都反复出现同一个值，你也还不知道它是魔数，还是第一个字段的值恰好总是一样。要分开这两者，一个文件是不够的。 这个问题后面单独再讲。

信号二 - 字节序显现在数值的形状里

多字节整数按什么顺序存放，决定了之后的所有解释。00 00 01 F4 从前往后读是 500，从后往前读是 40,894,464。不知道是哪一种，长度字段和偏移量就全都空转。

判别靠的是数值的形状。进到文件里的整数相当一部分是小数值：个数、长度、版本、索引都是。把小数值塞进四字节或八字节，高位字节就全是零。所以把看着像整数的位置凑几处，看零往哪一端聚，大多就分出来了。零聚在前面说明高位在先，聚在后面说明低位在先。

能确定的只到那个字段的字节序。整个文件用同一种字节序，这一点确定不了。事实上有规格的格式彼此之间也不一致。前面提到的压缩归档用低位在先，而 PNG 规格明确要求所有超过一个字节的整数都必须是网络字节序，也就是高位在先。同一个文件里容器用一种、装在里面的载荷用另一种的情况也很常见。做载荷的代码和做容器的代码不是同一份，自然就会这样。

反例也很清楚。数值对称就分不出来，比如 00 01 01 00 这样的排列，从哪一头读都说得通。字段其实是浮点数的话，零聚集的位置不一样。四字节的槽位也可能其实是四个单字节字段，那样的话零的分布只是碰巧看着像高位在先。所以字节序不在一处定案，要在多处得出同一结论时才定案。

信号三 - 长度字段与偏移表

这是最有力地暴露骨架的信号。某个四字节的值如果正好等于从该点起剩余的字节数，或者正好对上下一个结构开始的位置，那就不是巧合。一个值指向文件里另一处的那一刻，就确定了这个文件里有人设计过结构。

装可变长数据的办法大体有两种：在前面加长度，或者在后面加终止符。前置长度占压倒性多数。可以预先留好位置，而且数据里出现与终止符相同的值也依然安全。如果看到一个像 0x11 这样的小值后面紧跟着正好那么多个可读字符，那多半是前置长度的字符串。

当长度需要覆盖较大的值，可变长整数就登场了。广泛使用的方案是把每个字节的最高位当作还有下一个字节的旗标，剩下七位放值。原文在拆解目标程序写字符串的代码时，撞上的正是这种编码；十六进制编辑器的数据检视器里也以有符号和无符号两项列着它。小值能装进一个字节，在短字符串很多的格式里是看得见的收益。

value = 0
shift = 0
repeat:
    b      = read_u8()               // 读取一个字节
    value |= (b & 0x7F) << shift    // 低 7 位是数值
    shift += 7
until (b & 0x80) == 0                // 最高位为 0 表示这是最后一个字节

能确定的是这个值被用作长度或位置。不能确定的反而更多：单位是字节还是元素个数，基准点是文件开头还是该结构的开头，以及这个长度是否包含头部自身。这三处正是即使有规格、不写明也会导致实现分歧的地方。PNG 规格特意写明长度字段只数数据字段，不数它自己、不数分块类型、也不数 CRC，原因就在这里。写规格的人也知道读的人会在这儿出错。

00000000  4C 4F 47 32 01 00 00 00  20 00 00 00 03 00 00 00
00000010  00 00 00 00 00 00 00 00  0C 00 00 00 48 45 4C 4C

// 候选解读 (目前还只是假设)
//   +0x00  4 字节  'LOG2'    看着像魔数的 ASCII
//   +0x04  4 字节  1         版本? 按低位在先读出来的
//   +0x08  4 字节  32        头部大小? 第一条记录的偏移? 0x20 对得上
//   +0x0C  4 字节  3         记录条数?
//   +0x18  4 字节  12        第一条记录的长度? 与后面的数据对得上吗

上面这个例子里决定性的是：0x20 这个值与数据实际开始的位置对上了。找到值与位置相互吻合的那一点就是这一阶段的全部，找到一个，旁边的字段也会跟着连带解开。

信号四 - 对齐、填充与重复周期

规律地夹进来的零，大多是对齐，是为了把下一个字段落到四字节或八字节边界而插入的空档。如果这个格式是把结构体按内存里的样子直接倒进文件的，编译器插入的填充会原样留在那里。 这种情况下，填充的位置反而告诉你原结构体各字段的大小。两字节字段后面空了两字节，说明接下来那个成员多半要求四字节对齐。

文件末尾成片的零则是另一回事，那是使用固定大小缓冲区的痕迹。原文的对象正是如此：保存函数总是填满 40,960 字节，不够就用零补上，超了就抛异常。这类格式里，文件大小永远一样这件事本身就是信号。如果手头每个样本的长度都完全相同，那你看的是容器而不是内容。

重复周期是找记录结构的线头。同样的字节模式每隔固定间隔出现，那个间隔可能就是记录大小。立几个候选，然后确认文件大小减去看着像头部的前段之后，能否被各候选整除。除得干净，假设就上了一个台阶。

  • 能确定的 — 定长记录这一假设的候选大小，以及格式是把结构体原样倒出来的这种直觉
  • 不能确定的 — 头部大小。一个文件大小对两个未知数，方程解不出来。有两个大小不同的样本就能解
  • 反例其一 — 看着像对齐的零，可能其实是值为零的字段。保留字段几乎永远是零
  • 反例其二 — 看着有周期的东西可能是数据本身的性质。同样字符串排成的列表看上去就有周期
  • 反例其三 — 压缩区间里也会出现偶然的周期，所以要先用下一个信号把那些区间筛掉

信号五 - 熵画出的边界

按字节测出的信息量上限是 8 比特，因为一个字节只有 256 种取值。把文件切成区间来测这个值，性质不同的区域之间的边界就被画了出来。人读的文本和结构头部值偏低，因为用到的字节种类少而且分布偏斜。压缩或加密的区间则紧贴上限；压缩得好的数据按定义就是不可预测的样子，而压缩与预测是同一件事这一层道理，另有一篇讲压缩即预测的原因的文章。

ImHex 的数据信息界面里同时放着熵的曲线、最高值与平均值、字节种类分布，以及压缩或加密的判定。别的工具也有类似界面。界面长什么样不重要，重要的是那些数字能让你说到哪一步。

  • 能确定的 — 能读出结构的区间与读不出的区间之间的边界。仅此一项就已经值回票价，因为头部在哪结束、载荷从哪开始都看得见了
  • 不能确定的其一 — 高值区间是压缩还是加密。两者都显得均匀，光看数值分不开
  • 不能确定的其二 — 关于算法、密钥和参数，它一个字都不说
  • 反例其一 — 原样嵌着已压缩图像或音频的区间也会读出高值。格式本身可能只是普通容器，只有里面的载荷被压缩了
  • 反例其二 — 区间太短则样本太小，数值剧烈抖动。几十个字节的区间算熵几乎没有意义
  • 反例其三 — 值低也不保证是明文。使用固定表的编码和重复很多的二进制数据同样读出低值

说白了，熵是一张地图。它告诉你往哪挖能挖出东西，此外拒绝多说。把地图当成罗盘，时间就从那里开始漏。而如果某个读不出的区间之所以读不出是因为保护措施，那个区间就不是这套流程的对象，而是该停下流程的地方。

养成读第三列的习惯，这件事就成了一半。信号是收窄假设的工具，而不是结论。每个信号所能收窄的幅度比感觉上小，把收窄后的结果升格为确定，是下一节的工作。

把假设重新问回文件

留在脑子里的假设无法被证伪。含糊地放着，看到相冲突的地方也察觉不到冲突。所以推断出的结构必须写成机器能读并且能失败的形式。这才是工具在这项工作里真正做的事。

声明式写法有两种被广泛使用。一种是 ImHex 的模式语言，用类似 C++ 的语法写出结构体、数组和条件，定义会叠加显示在文件上。仓库采用 GPL-2.0，在 2026 年 9 月 5 日 03 时 26 分 UTC 查询时记录为星标 54,695、复刻 2,451、未关闭议题 394。另一种是 Kaitai Struct，用 YAML 声明结构后由编译器生成十余种语言的解析器代码；编译器是 GPLv3 及以上，运行时大多为 MIT。路子不同，但瞄准的性质完全一样。

struct Header {
    char magic[4];
    std::assert(magic == "LOG2", "magic does not match");             // 假设 1
    u32  version;
    std::assert(version == 1, "unknown version");                // 假设 2
    u32  headerSize;
    u32  recordCount;
};

struct Record {
    u32 length;                                            // 假设 3
    u8  payload[length];
};

struct File {
    Header header;
    Record records[header.recordCount];                    // 假设 4
};

这样写下来，假设错了就会看得见地错。记录大小取错，文件末尾就会多出或少掉字节；条数取错，中途就会炸开。它怎么崩，本身就是信息。

  • 末尾有多余，说明记录大小取小了，或者头部取大了
  • 末尾不够用，说明反过来，或者末尾另有目录一类的尾部结构
  • 中途炸开，说明有按条件存在或不存在的字段，前面某个值决定了它在不在
  • 只在部分文件上炸开，说明版本不止一个，先去找版本字段
  • 假设要立得强。断言某个值必须是某个数，不是的时候立刻就知道。松散的定义错了也会静悄悄地通过

原文也展示了同样的习惯。确认目标代码会检查版本值是否为 6、不是就抛异常之后，作者把同样的断言放进了自己的模式里。从代码里读到的事实，被翻译成了对文件的检查。就算看着答案，抄写过程中也可能出错，所以这个习惯在有答案时同样有效。

只有一个样本时崩塌的东西

只有一个文件时，常量和变量分不开。没有依据判断某个字节是格式规定的固定值，还是在这个文件里恰好是这个值。开头四个字节到底是魔数还是第一个字段的值，分不出来也是因为这个。这个限制无论怎样增加观察都不会消失。需要的不是观察而是对照组。

做对照组的办法原则上很简单：用生成该文件的程序只改动一个值，重新保存，然后比对两个文件。变了的字节位置就是那个值的住址。工具在这方面帮得上忙，比较两个数据源、高亮差异并列成表，是十六进制编辑器的标配。但这个办法要成立，前提是你能运行那个程序。 从这里开始，问题就不再是技术而是资格，后面两节因此而来。

即便有了对照组，仍有两处不会直接解开。其一是每次都会变的字段。时间戳是典型，什么都不改、每次保存也不一样，因此会以噪声的形式铺在比对结果上。对策是先做一对什么都不改而保存两次的文件，把那时变化的位置列为噪声清单剔除掉。时间值只要猜中基准时刻和单位就行，但每种格式各行其是；看看某个表格软件处理日期的方式，就能感受到这一行的惯例有多随意，这在日期被存成数字的来龙去脉一文里整理过。

其二是校验字段。若存在校验和或循环冗余校验值，只改一个值也会有两处同时变化。反过来说，这正是找到校验字段的办法：当你有意改动的位置之外还有一处也变了，就怀疑那里。校验字段的关键在于它是对什么算出来的，PNG 就是好例子：规格在每个分块里放一个四字节校验值，并明确写出排除长度字段，对分块类型和数据计算。即使是有规格的格式，不把这个范围写清楚，实现也会分裂。

还有一种情况是根本做不出对照组：程序没了，设备没了，或者你没有正当使用它的立场。那时得到的结论是对一个文件的描述，而不是对一种格式的描述。把这个区别写在结果文档的最上面，日后会救你一命。半年后读这份文档的人，没有办法分辨哪些是验证过的、哪些是猜的；而多数时候，半年后读它的人就是你自己。文档里最贵的一句话，往往不是某个字段的解释，而是一句「这一段没有被验证过」。

当代码在手 - 原文实际做了什么

前面那套流程是没有答案时的做法。有答案，整幅画面就完全不同。照着原文的顺序走一遍，差别就很清楚。

先是找到目标文件并用十六进制编辑器打开。看得到明文字符串，于是判断既没压缩也没加密；没有识别用的魔数，工具的识别功能也说不出类型。到这里对应本文整理的第零步和前两个信号。然后作者写道：没有更多信息就到此为止。

接下来是分岔口。目标程序的安装目录里能看到某个运行时的库，而那门语言属于容易反编译的一类。以拼出存档文件名的字符串为线索找到保存代码，看到那段代码先写时间戳，把实际内容委托给回调，再用零填到规定大小为止。从这一刻起就不是推断而是誊写了。

誊写下来的构件，都是这一行里反复遇到的东西：以 1601 年为基准计数一百纳秒间隔的 64 位时间值，读取函数会检查是否等于某个数的版本字段，单字节的真假值，前面带一个标志说明有没有内容的可选值，用可变长整数前置长度的字符串，前置条数的列表，以及在整数之上盖了名字的枚举。设计过把一切装进单个文件的格式的人，对这份清单不会陌生。写的一方本来选择就不多。

字符串一出现就会带上编码，这点值得单独提。长度算的是字符数还是字节数、用的是哪种编码、规范化形式是什么，是三个互相独立的问题。同一个字符可能以两种字节序列保存，这一点在讲谚文以两种方式保存的问题的文章里整理过。

这里剩下一个结论。那篇文章之所以能给每个字节起上名字，不是因为字节看得好，而是因为看到了答案。在看不到答案的场合，同样的流程给不出同样的把握。不承认这个差距就把成果发出去，是这项工作里最常见的失误。

也该记下那篇文章没有涉及的东西。熵分析、多样本比对、统计式结构推断，以及法律条件，那篇文章里都没有。工具里这些功能一应俱全，只是不是那篇文章的主题。不要把原文没说过的当成原文说过的搬过来，这是引用的最低条件。

分阶段检查清单

把前面的内容折成执行顺序，就是下面这样。每一阶段都写明能得到什么，以及跳过它日后要付出什么。

阶段要做的事跳过之后要付的代价
0. 确认资格先写下是否正当持有对象、目的是什么、成果要用在哪里技术上成功之后，全部都用不了
1. 排除已知格式查签名、看是否容器、检查末尾花好几天重新发现一份已有的规格
2. 收集样本尽量多，尤其要做出只差一个值的一对常量与变量到最后也分不开
3. 划分区间用熵划出能读与不能读的区间边界把压缩区间当成结构，白白烧掉几天
4. 解读开头定下魔数候选、版本候选和字节序之后所有数值全部对不上
5. 找出骨架寻找值与位置吻合的点，也就是长度与偏移最后只留下一份罗列字节而没有结构的文档
6. 写下来并跑一遍用声明式写出假设，对所有样本跑一遍永远不知道错在哪的假设固化成了结论
7. 在崩处收窄在多出、不够或炸开的位置修正假设做出只解析手头文件的解析器
8. 写明限界在文档里把验证过的和推测的分开半年后的自己把推测读成了事实

第零步排在最上面，是这张表的要点。技术流程有八步，但跳过它前面那一步，其余八步的成果就变成不能用的东西。那一步究竟在问什么，是下一节的内容。

法律设下的条件 - 著作权法第101条之4

韩国著作权法有正面处理这项工作的条文。以下引用依据著作权法 [施行 2026年8月11日] [法律第21336号，2026年2月10日部分修改]，该条于 2009 年 4 月 22 日新设，第 1 款于 2023 年 8 月 8 日修改。

定义本身已经含着目的

第 2 条第 34 项先定义术语。程序代码逆向分析，是指为了取得独立创作的计算机程序著作物与其他计算机程序之间互操作所必需的信息而复制或转换计算机程序著作物代码的行为。

这个定义不能一扫而过。目的已经写进了定义里面。 如果不是为了取得互操作所必需的信息，那从一开始就不是这个名字所指的行为，因此也不是这条所设例外的对象。人们常把它概括成「目的是互操作就没问题」，但顺序反了。互操作目的不是事后贴上的正当化理由，而是门口的条件。

第 1 款要求的四项

第 101 条之 4 第 1 款把要件叠在一起：以正当权限使用程序的人或获得其许可的人，在互操作所必需的信息不易取得且该取得不可避免的情况下，限于该程序互操作所必需的部分，可以不经程序著作财产权人许可进行程序代码逆向分析。

一句话里含着四个条件，而且四项必须同时满足。少掉任何一项，就不能依赖这条例外。

第 2 款堵住的两个出口

第 2 款另行限制所得信息的使用。其一，用于互操作以外的其他目的，或者提供给第三方。其二，用来开发、制作、销售与对象程序表达上实质相似的程序，或者用于其他侵害著作权的行为。

实务中最常撞上的是第一项的后半段。把分析结果整理后公开，可能触及提供给第三方。把格式说明发到博客或仓库是否落入其中，取决于公开了什么、到什么范围、出于什么目的，这不是本文能替你判断的问题。但做分析这个行为与散布结果这个行为会被分别评价，从条文结构上读得很清楚。

旁边的另一条

第 101 条之 3 第 1 款第 6 项从另一个角度设了例外：为了确认构成程序基础的思想与原理而以调查、研究、试验程序功能为目的进行复制的情形，并限于以正当权限使用该程序的人正在使用该程序的场合。同款的但书一并适用：依程序的种类与用途、被复制部分所占比重、复制份数等来看，不当损害著作财产权人利益的，不适用该例外。

两条的质地不同，这点需要点明。第 101 条之 3 第 1 款第 6 项讲的是观察与试验行为，第 101 条之 4 讲的是复制或转换代码。弄清文件结构的工作，视做法不同可能接近其中一边，也可能哪边都不是。

还剩一点。两条讲的都是「程序」。 数据文件本身可能并不是程序，读取其结构的行为是否落入这两条，取决于对象与行为的性质。抹平这个区别、把整件事概括成「逆向分析合法」，是这个主题上最常见的误读。

要问什么条文依据要确认的事实判断主体
我有没有这个资格第101条之4第1款是否以正当权限在使用，或获得了该人的许可个案判断，最终由法院
目的是什么第2条第34项、第101条之4第1款是否为取得与其他程序互操作所必需的信息个案判断，最终由法院
还有没有别的路第101条之4第1款该信息是否不易取得，取得是否不可避免个案判断，最终由法院
做到了哪一步第101条之4第1款是否限于互操作所必需的部分个案判断，最终由法院
结果用在了哪里第101条之4第2款第1项是否用于互操作之外或提供给第三方个案判断，最终由法院
做出了什么第101条之4第2款第2项是否做出了表达上实质相似的程序个案判断，最终由法院
是否属于功能调查试验第101条之3第1款第6项目的是否为确认思想与原理，是否在使用中，是否触及但书个案判断，最终由法院

法律之外还有合同

把条文的要件全都解释得通，也还不算完。使用条款或许可协议另行限制分析的情况很常见，法定例外与合同条款相撞时哪一方胜出，取决于管辖和条款的性质。以为法里有例外就可以无视合同，不是安全的前提；反过来，因为合同写了禁止就一概不行，同样是断言。无论哪种，结论都不是本文给出的，而是由审视那个具体个案的人给出的。

留给实务的终究是记录。先把目的写成文档，把工作范围绑在那个目的上，事先定好成果用在哪里。这三样没有落到文档上的工作，日后很难解释。而到了需要解释的时候，被问的往往是动手之前写下了什么。事后补写的说明，分量并不相同。

还有几种会多出一根轴的情况值得列一列。对象若不在自己的机器上而在别人的服务器上，信息通信网相关的规范另行适用。散布成果会另行招来对散布行为的评价。商业秘密法制也独立运作。而对象若带有技术保护措施，那完全是另一个问题，本文不予处理。管辖不止一个时这幅图会怎么变，在按管辖比较各自要件的那一节里整理过。

最后说一个常被误解的点。某项措施在技术上很弱，与法律判断无关。锁做得粗糙，和可以去开，是两回事。混淆与编码更接近拖延装置而不是保护，这层道理在讲混淆不是加密的文章里另行整理过，但那个事实永远不会变成可以随便动手的依据。

再说一遍。本节内容是查阅原典后转述的条文，不是对任何具体个案的判断。同一条文，随着对象、目的、合同以及成果的用途不同，结论会不一样。实际动手之前，应当参考主管机关的指引并请法律专业人士确认。 本文仅为提供信息而写。

未能确认的部分

  • PNG 签名八个字节逐字节的设计理由未能确认。关于第一个字节能抓住剥掉高位的传输、中间的换行组合能抓住换行转换的说法流传很广，但所查阅的规格正文里并没有这套理由。规格写到的只是：把 PNG 与其他数据流区分开，并使某些传输错误得以及早发现。因此正文没有写逐字节的理由
  • 关于第 101 条之 4 如何适用于数据文件的结构分析，未能确认韩国国内的判例。条文查阅了原典，但适用是另一个问题，正文表格中明示判断主体正是因为这一点
  • 法定例外与合同条款冲突时韩国国内以哪一方为先，也未能确认已确立的结论。因此正文对两边都没有下断言
  • ImHex 的压缩与加密判定采用什么阈值和方式未能确认。功能清单里有这一项，但没有找到关于判定标准的公开说明
  • 本文按信号所作的判断是从结构出发的梳理，不是测量值。手头没有关于各信号在真实格式中有效频率的统计
  • 原文提到的其他分析工具只确认了名字，并未逐个亲自使用。因此正文没有对工具之间的优劣作出评价
