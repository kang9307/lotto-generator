1. テキストボックスを超えた対話環境 — なぜAgent-Nativeなのか

AIエージェントをアプリケーションに組み込む最も一般的な方式は、画面の片隅にチャットウィンドウを配置することです。本稿の観点では、この方式ではエージェントが扱うコンテキストとユーザーが見ている画面が乖離しやすくなります。

Builder.ioのオープンソースプロジェクトBuilderIO/agent-nativeのREADMEは次のように始まります。「Coding agents work with more than a text box. Their environment provides context, tools, files, tests, and previews that make their capabilities and results visible.」READMEはこの視点を、エージェントと人間が共に閲覧する専用UIへと繋げています。

本稿の整理によれば、前述の関連記事（MCPステートレス移行ガイド、Claude Code MCPサーバー選定基準、OmniRoute AIゲートウェイ分析）がエージェントクライアントとツールサーバー間のプロトコルやルーティングを扱っているのに対し、本稿はアプリケーション内部で単一のアクションをUIとエージェントが共有するフレームワークを扱います。

READMEはこのプロジェクトを、自律的な作業と専用UIを組み合わせたエージェントを構築するためのオープンソースTypeScriptフレームワークであると紹介しています。本稿はREADMEが明らかにした範囲で3つの原則と6つのサーフェスを整理し、導入時に考慮すべきトレードオフを本稿の解釈として加えます。

2. 画面とツールの乖離 — 重複実装とロジック不整合の課題

この節はREADMEの記述ではなく本稿が整理した一般的な設計背景です。フルスタックWeb開発において、ユーザー体験の中核を担ってきたのは画面のイベントハンドラーでした。ボタンがクリックされるとコンポーネントのクリックハンドラーが起動し、フォームデータの妥当性をフロントエンドで検証した後にHTTPクライアント経由でバックエンドへ送信されます。バックエンドはビジネスロジックを実行してデータベースを更新し、成功レスポンスを返却して画面状態が再描画されます。

ここにLLM駆動のエージェント機能を追加しようとすると、補助的な経路を新設する場合があります。エージェントが呼び出すツール定義をスキーマ形式で別途作成し、関数の呼び出し要求を処理するための専用エンドポイントを増設する手法です。しかし、このような二重化構造では次のような管理負担が生じる可能性があります。

  • 仕様とバリデーション規則の重複：画面ボタンのハンドラーで検証される入力規則と、エージェントツールのスキーマ定義が別々の場所に記述されるため、業務ルールが変更された際に片方の修正が漏れる事態が起こり得ます。
  • 実行経路と認可検査の分離：画面操作時に通過する認証やセッション確認と、エージェント経路から入るツール実行経路の認可ロジックが分離し、セキュリティ上の死角が生じる可能性があります。
  • 画面状態とモデル認識の時間差：エージェントがツール呼び出しを通じてデータを変更したにもかかわらず、ブラウザメモリ上の状態がそれを直ちに検知できない場合、画面に古いデータが残る不一致が生じる可能性があります。
  • テストと検証コストの増加：同一の処理に対してUI操作テストとエージェントツール呼び出しテストの双方を記述する必要が生じる場合があり、テストの保守負担が増える可能性があります。

本節で整理した課題の背景に対し、READMEはこの課題を、1つのアクションがすべてのサーフェスを駆動するという形態で扱っています。

3. 3つの基本原則 — Shared Actions・Data・State

公式リポジトリREADMEは、エージェントネイティブなアプリケーションを支える3大原則を次のように定義しています。

共有原則 共有対象 READMEの記述
Shared actions エージェントツールとUIコードの機能 エージェントは各機能をツールとして呼び出し、UIはコードから呼び出します。双方の経路が同一の検証、権限、実装を使用します。
Shared data エージェントとUIで実行された作業結果 エージェントが行った作業はUIに表示され、UIで行われた作業はエージェントが利用できます。
Shared application state 現在のページ、選択されたレコード、アクティブなビュー エージェントは現在のページ、選択されたレコード、アクティブなビューなどの関連するUI状態を受け取ります。

3つの原則に関するREADMEの記述内容は次のように整理されます。

  • 第一に、Shared actions：READMEによれば、エージェントは各機能をツールとして呼び出し、UIはコードから呼び出します。双方の経路が同一の検証、権限、実装を使用するため、不整合を減らすことができます。
  • 第二に、Shared data：READMEは、エージェントが行った作業がUIに表示され、UIで行われた作業をエージェントが利用できると述べています。双方のサーフェス間でデータ作業結果が伝達される構成です。
  • 第三に、Shared application state：READMEは、エージェントが現在のページ、選択されたレコード、アクティブなビューなどの関連するUI状態を受け取ると説明しています。本稿の例示として、選択されたレコード情報がエージェントに渡されれば、ユーザーの指示を短縮できる可能性があります。READMEがこの例を挙げているわけではありません。

4. 1つのアクションが露出する6つのサーフェス — UIからCLIまで

READMEは、1つのアクションがUI、エージェント、HTTP、MCP、A2A、CLIの6つのサーフェスを駆動すると説明しています。

露出サーフェス 呼び出し主体 動作メカニズムと役割
UI UI画面コード（React） React内でuseActionQueryを用いて呼び出し
Agent tools AIエージェント エージェントがアクションをツールとして受領
HTTP API HTTPクライアント アクションのhttp項目でメソッドを指定（例はGET）
MCP MCPクライアント Model Context Protocolサーフェスとして露出
A2A 外部エージェント agent-to-agentサーフェスとして露出
CLI コマンドライン環境 コマンドラインサーフェスとして露出

以下はREADMEに基づいて本稿が整理した解釈です。

  • 実装箇所の単一化（本稿の解釈）：READMEによれば、1つのアクションが6つのサーフェスを駆動するため、同一機能をサーフェスごとに個別に作成する必要がなくなります。
  • 検証・権限の共有：READMEは、エージェント経路とUI経路が同一の検証、権限、実装を使用すると述べています。
  • 外部プロトコルサーフェス：MCPとA2Aがサーフェス一覧に含まれています。どのクライアントと連携するかはREADMEに記載されていません。
  • CLI・HTTP呼び出し（本稿の解釈）：同一のアクションをコマンドラインやHTTP経由でも呼び出せるため、再現や自動化に利用できると考えられます。
  • スキーマ共有（本稿の解釈）：アクションがdescriptionとschemaを持つため、サーフェス間で入力ルールを整合させやすくなる可能性があります。READMEはドキュメント自動生成には言及していません。
  • 移行手法：既存のアプリケーションをアクション単位で移行できるかどうかはREADMEで触れられておらず、移行事例についても本稿では確認できませんでした。

5. defineActionのコード構造 — 単一宣言とランタイム結合

READMEのコード例は次の通りです（import文は省略しています）。

export default defineAction({
  description: "Return a friendly greeting.",
  schema: z.object({
    name: z.string().default("world").describe("Name to greet"),
  }),
  http: { method: "GET" },
  run: async ({ name }) => {
    return { message: `Hello, ${name}!` };
  },
});

READMEはこの例を次のように説明しています。「The agent receives hello as a tool. React calls the same function with useActionQuery("hello", { name: "Alex" }). Agent-Native also exposes it through HTTP, MCP, A2A, and the CLI.」コードの構成は、description（説明文字列）、schema（Zodオブジェクト、nameのデフォルト値「world」と説明）、http（メソッド指定、例ではGET）、run（実行関数）です。各フィールドがランタイムで具体的にどのように利用されるかはREADMEのコード例の範囲外であり、本稿では確認できませんでした。

本稿の観察によれば、1回の宣言の中に説明、入力スキーマ、HTTPメソッド、実行ロジックがひとまとめに含まれています。

6. フレームワーク依存の代償 — TypeScriptとZodスキーマの前提

すべてのアーキテクチャ上の選択にはトレードオフが伴います。READMEはこのプロジェクトをTypeScriptフレームワークと紹介し、例の中でZodを使用しています。以下はそこから本稿が推論したトレードオフであり、README自体の記述ではありません。

  • TypeScript環境：Agent-NativeはTypeScriptフレームワークです。他言語で書かれた既存バックエンドがある場合、TypeScript層を別途設ける検討が必要になる可能性があります。
  • Zodスキーマ：READMEの例ではZodスキーマが用いられています。他のスキーマライブラリをサポートしているかはREADMEからは確認できませんでした。
  • 性能：READMEにはレイテンシやオーバーヘッドに関する記述やベンチマークがありません。低遅延システムでは実測して検証する必要があります。
  • エコシステム規模：MITライセンスであり、確認時点でのスター数は4.9k、フォーク数は462です。コミュニティ製プラグインや外部連携事例の規模は確認できませんでした。

本稿の判断としては、既存のコードベースが大きくフロントエンドとバックエンドの規約が確立された環境では、全面移行よりもエージェントとの対話が集中する新規機能から試験的に導入してみる余地があります。

READMEはこのコマンドがスタンドアロンのチャットエージェントテンプレートを開始点として作成すると説明しています。生成物の構成や動作については、本稿で直接実行していないため確認できませんでした。

8. 価値を発揮する領域と不向きなユースケース

あらゆるフレームワークと同様に、Agent-Nativeも向き不向きが存在します。この節はREADMEの勧告ではなく本稿が整理した解釈です。エージェントネイティブ設計が価値を発揮できる領域とそうでない領域を本稿の視点で分類します。

  • 価値を発揮する領域 ① — 人間とエージェントが協調する対話型ツール：デザインツールやデータ分析画面のように、利用者が画面要素を扱いながら同時にエージェントへ関連作業を指示する環境では、単一アクションと状態共有が開発作業を減らす可能性があります。
  • 価値を発揮する領域 ② — 複数インターフェースを必要とするシステム：Web画面だけでなくコマンドライン（CLI）や外部エージェント（MCP/A2A）連携を同時に視野に入れるシステムであれば、6サーフェス対応が役立つ可能性があります。
  • 不向きなユースケース ① — 画面対話のない純粋なバックエンド処理：バッチデータ処理やクローラーのようにUIが一切存在しないシステムでは、本フレームワークの画面関連機能は必要ない可能性があります。
  • 不向きなユースケース ② — 静的サイトおよび他基盤依存プロジェクト：単純な情報サイトやドキュメント拠点、あるいは他のエージェント基盤に深く結合している既存プロジェクトには、この構造が合致しない可能性があります。

  • 公式READMEにはアクション呼び出し時のスループットや遅延時間、メモリ消費量を測定した標準ベンチマーク数値が掲載されていないため、高負荷環境における性能特性は確認できませんでした。
  • 大規模な商用環境においてAgent-Nativeを全面導入して長期運用した実事例や障害報告データは公開資料からは確認できませんでした。
  • UIとエージェント間のデータ反映がリアルタイムであるか、手動リフレッシュなしで行われるかはREADMEに記載されておらず、他のツールバインディングライブラリとの定量的な比較もありません。
