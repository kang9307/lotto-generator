출력은 Windows 10의 Python 3.13.3(win32)과 Node v22.16.0에서 이 PC가 한 번 실행한 값이며, 다시 실행하면 값과 판정이 달라진다. 이유 설명은 변인을 하나만 바꾼 실행 출력과 아래에 인용한 공식 문서 문장에만 기댄다. 두 스크립트는 파일을 만들지 않고 자기 자신을 하위 프로세스로 부를 뿐이며 실행 시간은 각각 10~20초 안팎이다.

서론 - 첫 회의 숫자는 코드의 속도가 아니다

반복 측정에서 첫 호출이 이후 호출보다 몇 배에서 수천 배 느린 일은 흔하다. 이 값을 평균에 넣으면 함수의 속도가 아니라 「처음 한 번만 치르는 비용」이 평균에 섞인다. 그 비용의 정체는 하나가 아니다. 모듈 import, 정규식 컴파일 캐시, 사용자 코드의 지연 초기화, JIT 컴파일러의 단계적 최적화는 크기도 지속 시간도 다르다. 따라서 워밍업을 몇 회 버릴지는 감이 아니라 같은 함수의 회차별 시간에서 정해야 한다.

이미 모은 측정값을 합치는 문제는 백분위수 집계 오류 글이, 어떤 시계로 재야 하는지는 단조 시계와 벽시계 글이 다룬다. 여기서는 측정값이 만들어지기 전 단계, 곧 몇 번째 호출부터 측정값으로 쓸 수 있는가에 한정한다.

다루는 질문은 다음과 같다.

  • 첫 호출의 지연이 import·정규식 캐시·지연 초기화 중 무엇에서 오는지 변인을 분리해 가를 수 있는가.
  • 같은 함수를 반복 호출할 때 회차별 시간은 어떤 모양으로 내려가는가.
  • 버릴 회차를 이동 중앙값이 안정되는 지점으로 코드가 정할 수 있는가.
  • 워밍업을 포함한 평균과 버린 뒤의 평균은 안정 구간의 값에서 얼마나 벗어나는가.
  • 측정이 흔들리는 환경에서 그 판정을 믿어도 되는지 어떻게 검사하는가.

측정 도구와 공식 문서가 말하는 것

Python의 timeit 문서는 기본 타이머가 항상 time.perf_counter()라고 적는다. 같은 문서는 timeit()이 측정 중 가비지 컬렉션을 잠시 끄며, 그 이점은 독립된 측정을 더 비교하기 쉽게 만드는 것이고 단점은 GC가 측정 대상 성능의 중요한 부분일 수 있다는 것이라고 설명한다. 반복 측정 결과에 대해서는 평균과 표준편차를 구해 보고하는 것은 유용하지 않으며, 높은 값은 대개 Python의 속도 변동이 아니라 다른 프로세스가 측정을 방해해서 생기므로 min()이 거의 유일하게 볼 숫자라고 적는다.

Node 쪽 시계는 perf_hooks의 performance.now()이다. MDN은 이 메서드가 밀리초 단위의 고해상도 타임스탬프를 돌려주며 timeOrigin 이후 경과 시간을 나타낸다고 설명한다. MDN의 해상도 설명(격리된 문맥 5마이크로초, 그렇지 않은 문맥 100마이크로초)은 웹 문서의 브라우저 문맥에 대한 것이다. 아래 Node 출력은 호출 하나를 두 번의 performance.now()로 감싼 값이다.

  • Python: time.perf_counter()로 호출 하나를 감싸 마이크로초로 환산한다. 반복 측정에는 timeit.repeat()을 쓴다.
  • Node: performance.now()로 호출 하나를 감싸 마이크로초로 환산한다. 내부 최적화 옵션은 쓰지 않는다.
  • 변인 분리: 새 프로세스에서 첫 호출과 둘째 호출을 재고, 조건을 하나만 바꿔 같은 측정을 반복한다.
  • 판정: 회차별 시간에 이동 중앙값을 적용하고, 마지막으로 정상성 검사를 한다.

CPython 첫 호출 - 변인을 하나씩 바꾼 실험

아래 코드의 첫 부분은 새 인터프리터 프로세스를 띄워 같은 함수를 두 번 부르고 첫 호출과 둘째 호출의 시간을 마이크로초로 낸다. 부모 프로세스는 다섯 가지 조건을 각각 7개의 새 프로세스에서 돌리고 중앙값을 낸다. 조건끼리는 한 가지만 다르다.

import sys, time, re, subprocess, statistics, platform, random
                    
                    def us(fn, *a):
                        t = time.perf_counter(); fn(*a); return (time.perf_counter() - t) * 1e6
                    
                    # ---------- child mode: one fresh interpreter, time call 1 and call 2 ----------
                    def child(case):
                        if case == "import_cold":
                            print("sqlite3 already loaded:", "sqlite3" in sys.modules)
                            def f():
                                import sqlite3
                                return sqlite3.sqlite_version
                        elif case == "import_warm":
                            import sqlite3
                            def f():
                                import sqlite3
                                return sqlite3.sqlite_version
                        elif case == "re_cold":
                            re.purge()
                            def f(): return re.search(r"(\d{4})-(\d{2})-(\d{2})", "date: 2026-10-06 end")
                        elif case == "re_precompiled":
                            c = re.compile(r"(\d{4})-(\d{2})-(\d{2})")
                            def f(): return c.search("date: 2026-10-06 end")
                        elif case == "lazy_table":
                            box = {}
                            def f():
                                if "t" not in box:
                                    box["t"] = {i: i * i for i in range(200000)}
                                return box["t"][777]
                        a = us(f); b = us(f)
                        print("%.1f %.1f" % (a, b))
                    
                    if len(sys.argv) > 1:
                        child(sys.argv[1]); sys.exit()
                    
                    # ---------- parent ----------
                    print("python", platform.python_version(), sys.platform)
                    print("A. fresh process, call 1 vs call 2 (us), median of 7 processes")
                    print("%-16s %12s %12s %8s" % ("case", "call 1", "call 2", "ratio"))
                    for case in ["import_cold", "import_warm", "re_cold", "re_precompiled", "lazy_table"]:
                        r = []
                        for _ in range(7):
                            o = subprocess.run([sys.executable, __file__, case], capture_output=True, text=True).stdout.split()[-2:]
                            r.append((float(o[0]), float(o[1])))
                        c1 = statistics.median(x[0] for x in r); c2 = statistics.median(x[1] for x in r)
                        print("%-16s %12.1f %12.1f %8.1f" % (case, c1, c2, c1 / c2))
  • import_cold: 함수 안에서 sqlite3를 import한다. 프로세스 시작 때 sqlite3는 아직 불러오지 않은 모듈이다(출력의 loaded 줄 참조).
  • import_warm: 같은 함수이지만 시간 재기 전에 sqlite3를 미리 import해 둔다. import_cold와의 차이는 이것 하나이다.
  • re_cold: re.purge()로 정규식 캐시를 비운 뒤 문자열 패턴으로 re.search를 부른다.
  • re_precompiled: 패턴을 시간 재기 전에 re.compile로 만들어 두고 search만 부른다. re_cold와의 차이는 컴파일이 시간 안에 있는가 하나이다.
  • lazy_table: 첫 호출에서 20만 항목의 딕셔너리를 만들어 보관하고 이후에는 재사용하는 사용자 코드의 지연 초기화이다.

출력에서 읽을 수 있는 것은 세 가지이다. 첫째, import_cold와 import_warm은 함수 코드가 같고 모듈을 미리 불러 두었는가만 다르다. 첫 호출이 13248.8에서 1.8로 줄었으므로 이 PC에서 import_cold의 첫 호출 지연은 함수 안의 import가 만든 것이다. Python 문서는 import 때 모듈 이름을 sys.modules에서 먼저 찾고, 있으면 그 값이 import를 만족해 과정이 끝난다고 적는다. 문서는 캐시의 존재를 말하고, 속도 차는 import_warm·re_precompiled 대조 출력이 보여 준다.

둘째, re_cold와 re_precompiled는 컴파일이 시간 안에 있는가만 다르다. 280.7이 15.7로 내려갔다. re 문서는 re.compile()과 모듈 수준 매칭 함수에 넘긴 최근 패턴의 컴파일 결과가 캐시되고 re.purge()가 그 캐시를 비운다고 적는다. 캐시를 비운 첫 호출만 컴파일 비용을 낸 셈이다. 셋째, lazy_table의 48073.7은 20만 항목 딕셔너리를 만드는 코드가 첫 호출 안에 있어서 생긴 값이며, 표를 다시 쓰기만 하는 둘째 호출은 같은 출력에서 3.6이었다.

남는 차이도 있다. import_warm의 1.8 대 1.0, re_precompiled의 15.7 대 2.9는 한 자리에서 두 자리 마이크로초 규모의 첫 호출 초과이다. 이 규모의 차이는 아래 시계열 절의 수렴 판정이 다루는 대상이다.

같은 프로세스의 시계열 - 한 번의 스파이크가 평균을 바꾼다

코드의 둘째 부분은 한 프로세스에서 같은 함수를 160번 부른 시계열에 판정 함수를 적용한다. 판정 함수는 셋이다. settle_index는 창 5의 이동 중앙값이 안정 수준(뒤쪽 절반의 중앙값)의 25퍼센트 안에 연속 10번 머무는 첫 지점을 낸다. stationary는 뒤쪽 두 사분위 구간의 중앙값을 비교한다. spike_count는 앞 20회 중 안정 수준의 3배를 넘는 마지막 회차를 센다.

# ---------- detectors ----------
                    def settle_index(t, w=5, tol=0.25, run=10):
                        """First call index from which run consecutive moving medians (window w)
                        stay within +-tol of the steady level (median of the last half)."""
                        ref = statistics.median(t[len(t) // 2:])
                        mm = [statistics.median(t[i:i + w]) for i in range(len(t) - w + 1)]
                        for i in range(len(mm) - run + 1):
                            if all(abs(m - ref) <= tol * ref for m in mm[i:i + run]):
                                return i, ref
                        return None, ref
                    
                    def stationary(t, tol=0.25):
                        q = len(t) // 4
                        a, b = statistics.median(t[2 * q:3 * q]), statistics.median(t[3 * q:])
                        return abs(a - b) <= tol * b, a, b
                    
                    def spike_count(t, k=3.0, head=20):
                        ref = statistics.median(t[len(t) // 2:])
                        bad = [i for i, x in enumerate(t[:head]) if x > k * ref]
                        return bad[-1] + 1 if bad else 0
                    
                    random.seed(42)
                    data = [random.random() for _ in range(2000)]
                    def pure():
                        s = 0.0
                        for x in data: s += x * x
                        return s
                    def lazy_series():
                        import sqlite3
                        return sqlite3.sqlite_version
                    
                    print()
                    print("sqlite3 loaded before series:", "sqlite3" in sys.modules)
                    series = {"pure": [us(pure) for _ in range(160)],
                              "import-in-call": [us(lazy_series) for _ in range(160)]}
                    print("B. 160 calls in one process (us)")
                    for name, t in series.items():
                        idx, ref = settle_index(t)
                        ok, qa, qb = stationary(t)
                        print("%-15s first 6: %s" % (name, " ".join("%.1f" % x for x in t[:6])))
                        print("%-15s steady %.1f | settle index %s | spike count %d | stationary %s (%.1f vs %.1f)" % (
                            "", ref, idx, spike_count(t), ok, qa, qb))
                    
                    print()
                    print("C. naive mean of all 160 calls vs mean after discarding spike_count calls (us)")
                    for name, t in series.items():
                        k = spike_count(t)
                        print("%-15s naive %.2f | discard %d -> %.2f | median %.2f" % (name, statistics.mean(t), k, statistics.mean(t[k:]), statistics.median(t)))
                    
                    import timeit
                    r = timeit.repeat(pure, number=50, repeat=7)
                    print()
                    print("D. timeit.repeat(pure, number=50, repeat=7), us per call:", " ".join("%.1f" % (x / 50 * 1e6) for x in r))
                    print("   min %.1f | median %.1f" % (min(r) / 50 * 1e6, statistics.median(r) / 50 * 1e6))
  • pure: 난수 2000개의 제곱합을 구하는 순수 함수이다. 시드는 42로 고정했다.
  • import-in-call: 함수 안에서 sqlite3를 import한다. 이 시계열이 시작될 때 sqlite3는 불러와져 있지 않다(출력의 loaded 줄).
  • 창 5·허용 25퍼센트·연속 10회는 여기서 정한 값이며 문서 규정이 아니다.
  • 두 시계열은 같은 프로세스에서 이어서 측정했다.

위 B 출력은 이 PC에서 한 번 실행한 값이다. import-in-call 시계열은 12346.7, 1.7, 0.7, 0.6으로 한 번의 큰 값 뒤에 곧바로 안정됐고, 이 실행에서는 settle index 0, spike_count 1이었다. 다시 실행하면 판정이 달라진다(아래 표). 한 번의 스파이크는 창 5의 중앙값에 들기 어려워 이동 중앙값만으로는 버릴 회차로 잡히지 않을 수 있으므로, 단발성 비용에는 spike_count 같은 개별 회차 검사가 따로 필요하다.

같은 스크립트를 이 PC에서 세 번 다시 실행해 위 출력과 나란히 놓았다. 앞 두 열은 pure, 다음 두 열은 import-in-call의 판정이고, 마지막 열은 C 출력의 import-in-call 평균(naive, 버린 뒤)이다.

이 실행에서는 위 출력의 판정이 나왔고 다시 실행하면 달라진다. 판정이 갈리는 것 자체가 마이크로초 단위 측정의 잡음을 보여 준다. 바뀌지 않은 것은 네 번 모두 import-in-call의 naive 평균이 버린 뒤 평균보다 111~442배 컸고(계산) spike_count가 1 또는 2였다는 점이다.

그 영향은 C 출력(이 PC의 한 번의 실행)이 보여 준다. 160회 전체의 평균은 77.83마이크로초이고 첫 호출 하나를 버린 평균은 0.67마이크로초이다. 계산하면 약 116배 차이이며, 12346.7을 160으로 나눈 값(약 77.2)이 평균을 거의 다 설명한다. 중앙값은 0.70이라 스파이크의 영향을 받지 않는다. 그래서 워밍업을 포함한 평균은 함수의 속도를 재지 못한다.

잡음이 워밍업을 가린다 - 정상성 검사와 timeit의 최솟값

B 출력(이 PC에서의 한 번의 실행)의 pure 시계열은 앞 여섯 회가 모두 421~431마이크로초대이다. 안정 수준으로 계산된 값은 151.7이고 settle index는 16이다. 그러나 stationary는 False이며 뒤쪽 두 구간의 중앙값이 205.6 대 53.2마이크로초로 4배 가까이 벌어졌다. 같은 코드가 한 프로세스 안에서 몇 초 사이에 53에서 431마이크로초까지 움직인 것이다. 이 PC에서 이 흔들림의 원인은 출력만으로 가를 수 없다. 세 번 다시 실행했을 때는 앞 여섯 회가 80~323마이크로초였고 stationary가 False·True·False로 갈렸다.

이 경우 settle index 16은 워밍업의 증거가 아니다. 정상성 검사를 통과하지 못한 시계열에서는 버릴 회차 계산 자체를 쓰지 않고 측정을 다시 한다. D 출력은 같은 함수를 timeit.repeat로 7번 반복한 값이며, 한 번의 반복(50회 호출)당 시간이 59.5에서 255.7마이크로초로 흩어졌다(이 한 번의 실행 값이며, 세 번 다시 실행한 최솟값은 131.7, 76.8, 99.7이었다).

D. timeit.repeat(pure, number=50, repeat=7), us per call: 121.8 205.7 59.5 85.1 255.7 168.6 160.9
                       min 59.5 | median 160.9
  • 이 실행에서 최솟값 59.5와 중앙값 160.9는 2.7배 벌어져 있다. timeit 문서가 평균 대신 min을 권하는 근거가 이 흩어짐이다.
  • 높은 값이 Python의 속도 변동이 아니라 다른 프로세스의 간섭이라는 설명은 문서의 문장이며, 이 PC에서 간섭의 정체를 가려낸 것은 아니다.
  • pure 시계열의 naive 평균 202.18과 중앙값 199.90은 거의 같다. 스파이크가 없는 흔들림은 평균과 중앙값 모두에 들어간다.

Node 첫 호출 - 회차별 시간과 막대 분포

Node 스크립트는 객체를 2만 번 만들고 지나가는 함수를 1000번 호출해 호출마다 시간을 재고, 회차 구간별 중앙값과 로그 눈금 막대를 낸다. 같은 파일을 인자 child로 부르면 500번 호출한 한 프로세스의 결과를 한 줄로 낸다. 아래 코드는 판정 함수 두 개를 Python과 같은 정의로 다시 구현한다.

const { performance } = require('node:perf_hooks');
                    const { spawnSync } = require('node:child_process');
                    
                    function work(n) {
                      let s = 0, o = { a: 1, b: 2 };
                      for (let i = 0; i < n; i++) { o = { a: o.b + (i % 7), b: o.a ^ i }; s += o.a * 3 + (o.b >> 1); }
                      return s;
                    }
                    function series(n) {
                      const t = [];
                      for (let i = 0; i < n; i++) {
                        const a = performance.now(); work(20000); t.push((performance.now() - a) * 1000);
                      }
                      return t;
                    }
                    const med = a => { const b = [...a].sort((x, y) => x - y); const m = b.length >> 1; return b.length % 2 ? b[m] : (b[m - 1] + b[m]) / 2; };
                    const mean = a => a.reduce((x, y) => x + y, 0) / a.length;
                    function settle(t, w = 5, tol = 0.25, run = 10) {
                      const ref = med(t.slice(t.length >> 1));
                      const mm = [];
                      for (let i = 0; i + w <= t.length; i++) mm.push(med(t.slice(i, i + w)));
                      for (let i = 0; i + run <= mm.length; i++) {
                        if (mm.slice(i, i + run).every(m => Math.abs(m - ref) <= tol * ref)) return { idx: i, ref };
                      }
                      return { idx: null, ref };
                    }
                    function stationary(t, tol = 0.25) {
                      const q = t.length >> 2;
                      const a = med(t.slice(2 * q, 3 * q)), b = med(t.slice(3 * q));
                      return { ok: Math.abs(a - b) <= tol * b, a, b };
                    }
                    
                    if (process.argv[2] === 'child') {
                      const t = series(500);
                      const s = settle(t);
                      const k = s.idx === null ? 0 : s.idx;
                      console.log([s.idx, mean(t.slice(0, 30)).toFixed(0), mean(t.slice(k, k + 30)).toFixed(0), s.ref.toFixed(0)].join(' '));
                      process.exit(0);
                    }
                    
                    const T0 = performance.now();
                    console.log('node', process.version, process.platform);
                    const t = series(1000);
                    console.log('per-call us, calls 1-12:', t.slice(0, 12).map(x => x.toFixed(0)).join(' '));
                    console.log('');
                    console.log('calls         median(us)  bar');
                    const ranges = [[1, 1], [2, 2], [3, 5], [6, 10], [11, 20], [21, 50], [51, 100], [101, 300], [301, 1000]];
                    const top = med(t.slice(0, 1));
                    for (const [a, b] of ranges) {
                      const m = med(t.slice(a - 1, b));
                      const label = (a === b ? String(a) : a + '-' + b).padEnd(12);
                      console.log(label + String(m.toFixed(0)).padStart(10) + '  ' + '#'.repeat(Math.max(1, Math.round(40 * Math.log10(m + 1) / Math.log10(top + 1)))));
                    }
                    const s = settle(t), st = stationary(t);
                    console.log('');
                    console.log('steady level (median of last half): ' + s.ref.toFixed(0) + ' us');
                    console.log('settle index (w=5, tol=25%, run=10): ' + s.idx + ' -> discard first ' + s.idx + ' calls');
                    console.log('stationary check: ' + st.ok + ' (' + st.a.toFixed(0) + ' vs ' + st.b.toFixed(0) + ' us)');
                    
                    console.log('');
                    console.log('5 fresh processes: mean of 30 calls (us)');
                    console.log('settle  naive(1-30)  after-discard  steady-median');
                    for (let i = 0; i < 5; i++) {
                      const r = spawnSync(process.execPath, [__filename, 'child'], { encoding: 'utf8' });
                      const p = r.stdout.trim().split(' ');
                      console.log(p[0].padStart(6) + p[1].padStart(13) + p[2].padStart(15) + p[3].padStart(15));
                    }
                    console.log('total ms: ' + (performance.now() - T0).toFixed(0));

  • 막대는 중앙값의 상용로그에 비례해 그린 것이라 막대 길이 차이보다 숫자 차이가 훨씬 크다.

V8 블로그는 Sparkplug 도입 글에서 Ignition 인터프리터와 TurboFan 최적화 컴파일러 사이에 Sparkplug가 있다고 소개하고, 객체 형태 피드백이 아직 안정되지 않아 더 일찍 최적화를 시작할 수 없다고 적는다. 첫 회가 수천 마이크로초이고 수십 회 뒤 수백 마이크로초가 되는 출력은 이 설명과 방향이 맞는다. 출력은 첫 호출이 느림을 보여 주며 원인은 이 실험으로 가를 수 없다.

몇 회를 버릴 것인가 - 수렴 판정 규칙

steady level (median of last half): 282 us
                    settle index (w=5, tol=25%, run=10): 15 -> discard first 15 calls
                    stationary check: true (274 vs 295 us)

이 실행에서 안정 수준(뒤쪽 절반의 중앙값)은 282마이크로초이고, 이동 중앙값 판정은 처음 15회를 버리라고 낸다. 정상성 검사는 True이며 뒤쪽 두 구간이 274 대 295마이크로초로 같은 수준이다. 이 시계열은 판정에 쓸 수 있다. 이 값들은 이 PC 한 번의 실행에서 나온 것이다.

중요한 것은 이 숫자가 실행마다 같지 않다는 점이다. 같은 스크립트를 새 프로세스에서 다섯 번 돌린 아래 출력(이 PC 한 번의 실행)에서 판정 회차가 1, 94, 25, 18, 4로 갈렸다. 단정할 수 있는 것은 프로세스마다 판정이 크게 갈린다는 방향뿐이고, 구체 숫자는 실행마다 다르다. 한 프로세스의 한 번 측정으로 버릴 회차를 단정할 수 없다는 뜻이다.

  • 창 크기: 작으면 단발 잡음에 흔들리고 크면 짧은 워밍업을 흐린다. 여기서는 5를 썼다.
  • 허용 폭: 안정 수준의 25퍼센트를 썼다. 환경의 평소 흔들림보다 좁게 잡으면 판정이 영영 나오지 않는다.
  • 연속 횟수: 창 평균이 허용 폭 안에 10번 연속 머물 때를 안정으로 본다.
  • 안정 수준: 시계열 뒤쪽 절반의 중앙값이다. 뒤쪽이 아직 내려가는 중이면 이 기준 자체가 틀린다.

  • 이 실행에서는 버린 뒤의 평균이 0.88배에서 1.26배로 안정 수준에 가까웠고 모든 프로세스에서 naive보다 가까웠다. 반례가 나올 수 있다. settle이 작을 때는 버린 뒤의 평균이 naive보다 안정 수준에서 더 멀어질 수 있다.
  • 판정 회차가 1인 프로세스 1은 버린 뒤에도 1.26배였다. 판정 회차가 너무 작으면 워밍업이 덜 잘린다.
  • 프로세스 4의 steady-median이 174로 다른 프로세스의 270~282보다 낮다. 프로세스마다 안정 수준 자체가 다르다.

실전 절차 - 버릴 회차를 정하는 순서

위의 실행에서 얻은 규칙을 순서로 묶으면 다음과 같다. 각 항목은 앞 절의 출력에 근거가 있으며, 큰 쪽을 쓰는 항목만 이 글의 제안이다.

  • 새 프로세스에서 호출마다 시간을 기록한다. 측정 구간 안에 import·컴파일·초기화가 들어 있는지 코드를 먼저 읽는다.
  • 의심되는 비용은 조건을 하나만 바꿔 분리한다. 모듈 미리 불러오기, 패턴 미리 컴파일하기가 그 예이다.
  • 시계열을 충분히 길게 잡는다(여기서는 160~1000회). 시간이 길면 반복 횟수를 줄여 총 실행 시간을 10초 안팎으로 맞춘다.
  • 정상성 검사를 먼저 한다. 탈락하면 워밍업 판정을 보류하고 환경을 정리해 다시 측정한다.
  • 이동 중앙값으로 판정 회차를 구하고, 단발 스파이크는 개별 회차 검사로 따로 센다.
  • 새 프로세스를 여러 개 돌려 판정 회차를 비교한다. 큰 쪽을 버릴 회차로 쓰는 것은 이 글이 제안하는 규칙이며 문서 근거는 없다. 근거는 판정이 갈린다는 데까지이다(이 PC 한 번의 실행에서 1에서 94).
  • 버린 뒤의 구간에서 중앙값과 최솟값, 그리고 흩어짐을 함께 보고한다. 평균 하나만 적지 않는다.
  • 보고서에 환경을 적는다. 여기 실린 모든 값은 이 PC의 Windows 10, Python 3.13.3, Node v22.16.0 값이다.

확인하지 못한 것

  • Node 첫 호출의 지연이 JIT 단계 전환 때문이라는 인과. V8 블로그 문장과 출력의 방향이 맞을 뿐 JIT만 끈 대조 실험은 하지 않았다.
  • pure 시계열이 한 프로세스 안에서 53에서 431마이크로초까지 움직인 원인. CPU 클럭·OS 스케줄링·인터프리터 내부 동작 중 무엇인지, 그리고 재실행마다 판정이 갈린 이유도 출력으로 가르지 못했다.
  • import_warm과 re_precompiled에 남은 첫 호출 초과(1.8 대 1.0, 15.7 대 2.9)의 원인.
  • OS 파일 캐시의 영향. 캐시를 비우려면 관리자 권한이 필요해 실행하지 않았다.
  • Linux·macOS와 다른 버전의 Python·Node에서의 값. 이 PC의 Windows 10에서만 실행했다.
  • Node의 performance.now()가 실제로 내는 해상도. MDN의 해상도 문장은 브라우저 문맥의 것이며 Node 문서는 열지 않았다.
  • 창 5·허용 25퍼센트·연속 10회라는 판정 매개변수가 다른 함수에서도 알맞은지.
  • GC를 켠 상태와 끈 상태의 차이. timeit 문서가 설명하는 GC 비활성화는 여기서 쓴 perf_counter 측정에는 적용되지 않았다.
