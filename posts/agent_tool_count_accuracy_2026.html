도구를 몇 개까지 붙일 수 있나 - 에이전트 툴 선택이 무너지는 지점과 좁히는 법

붙이는 것과 펼치는 것을 분리하면 문제의 절반이 사라진다

2026-08-03 IT/기술

서론: 하나만 붙였을 때는 잘 되던 것이

GitHub MCP 하나만 붙였을 때는 잘 돌던 에이전트다. 거기에 Slack을 붙이고, 사내 데이터베이스 조회를 붙이고, 브라우저 자동화를 붙이고, 마지막으로 사내 API 게이트웨이를 감싸 올렸다. 그러자 어제까지 잘 하던 일에서 이상한 짓을 하기 시작한다. 이슈를 만들라고 했는데 검색을 하고, 검색을 하라고 했는데 필수 파라미터를 빼먹고, 어떤 요청에서는 도구를 아예 쓰지 않고 자기 지식으로 답해 버린다.

모델을 바꿔 봐도 크게 나아지지 않고, 시스템 프롬프트에 「도구를 신중하게 고르라」는 문장을 추가해도 마찬가지다. 이 시점에서 대부분 프롬프트를 더 길게 쓰는 쪽으로 간다. 그 방향은 거의 통하지 않는다.

결론부터 말하면 이렇다. 붙일 수 있는 도구의 총 개수에는 실질적인 상한이 없다. 상한이 있는 것은 한 턴이 시작될 때 모델 앞에 펼쳐 두는 개수다. 이 둘을 분리하는 순간 문제의 절반이 사라진다. 나머지 절반은 이름과 설명, 그리고 도구 사이의 선행 관계에서 온다.

이 글은 그 경계선이 어디인지, 넘어가면 무엇이 어떤 순서로 망가지는지, 그리고 좁히는 방법 네 가지를 어떤 순서로 적용해야 손해가 없는지를 다룬다. MCP 자체의 개념과 한계 논쟁은 MCP 완벽 가이드와 MCP는 죽었는가에서 이미 다뤘으므로 여기서는 반복하지 않는다.

1. 무엇이 먼저 망가지나 - 실패의 다섯 가지 얼굴

「도구가 많으면 정확도가 떨어진다」는 문장은 맞지만 쓸모가 없다. 실무에서 필요한 것은 어떤 실패가 어떤 원인에서 오는지 가르는 일이다. 다섯 가지가 서로 다른 원인에서 나오고, 섞어서 보면 원인을 영영 못 찾는다.

실패 유형로그에서 보이는 모습흔한 오진실제 원인이 있는 곳
인자 오류필수 파라미터 누락, 타입 불일치, 형식 어긋남「모델이 멍청하다」인자 설명과 예시. 개수와 무관
엉뚱한 도구 호출의도와 다른 이름의 도구를 부름「프롬프트가 부족하다」이름·설명 겹침. 개수가 늘어야 생김
도구 미사용도구를 두고 자기 지식으로 답변「모델이 게으르다」정의가 컨텍스트에서 밀려남
과호출목록·조회 도구를 반복 호출하며 정체「루프 버그」목표 도구를 못 찾아서 헤매는 것
선행 도구 누락목표 도구는 맞는데 입력값이 없어 실패「검색 정확도 문제」도구 간 의존 관계 부재

순서가 중요하다. 인자 오류는 도구가 열 개뿐일 때도 난다. 이건 개수의 문제가 아니라 스키마 설명의 문제다. Anthropic이 공개한 수치에서 도구 사용 예시를 붙이자 복잡한 인자 처리 정확도가 72퍼센트에서 90퍼센트로 올랐다. 도구를 줄여서 나온 개선이 아니다.

반면 엉뚱한 도구 호출과 과호출은 개수가 늘어야 비로소 나타난다. 그러니 도구 다섯 개짜리 환경에서 인자 오류를 겪고 있다면 지연 로딩이나 라우팅을 도입해도 아무것도 나아지지 않는다. 고쳐야 할 것은 인자 설명이다. 반대로 서버 다섯 개를 붙인 뒤 갑자기 엉뚱한 호출이 늘었다면, 그건 프롬프트를 아무리 다듬어도 근본에서 해결되지 않는다.

2. 도구 정의가 컨텍스트에서 실제로 얼마를 먹는가

숫자를 보면 감각이 달라진다. Anthropic 엔지니어링 글이 예로 든 다섯 서버 구성은 이렇다.

도구 58개는 「많다」는 감각을 주지 않는다. 서버 다섯 개면 요즘 흔한 구성이다. 그런데 정의만으로 약 55,000 토큰이다. 200K 창이라면 사용자가 한 글자도 입력하기 전에 4분의 1 이상이 사라진 상태로 시작한다. 같은 글은 Anthropic 내부 환경에서 최적화 전 도구 정의만 134,000 토큰을 차지했다고 적는다.

2.1 개수와 토큰은 비례하지 않는다

표에서 진짜 중요한 것은 합계가 아니라 맨 오른쪽 열의 편차다. Slack은 도구가 11개인데 35개짜리 GitHub와 토큰이 엇비슷하다. 도구 하나가 1,900 토큰씩 먹는 것이다. 인자 스키마가 깊고 열거형 값이 많으면 이렇게 된다.

그래서 도구 개수를 상한으로 관리하는 정책은 실패한다. 「도구는 20개까지」라는 사내 규칙을 세워 놓고 스키마가 깊은 도구 20개를 붙이면, 개수는 지켰는데 토큰은 40K를 넘긴다. 세어야 하는 단위는 정의 토큰이고, 개수는 선택 난이도를 재는 대리 지표일 뿐이다. 두 가지를 따로 재라.

지금 바로 재는 법. 에이전트를 붙인 상태에서 아무 요청이나 하나 보내고 첫 응답의 입력 토큰 수를 본다. 그 다음 도구를 전부 떼고 같은 요청을 보낸다. 두 값의 차이가 당신의 도구 정의 비용이고, 이 값은 모든 요청, 모든 턴에 다시 지불된다.

3. 왜 개수가 늘면 선택이 틀리나

원인은 세 갈래다. 셋 다 처방이 다르므로 구분해 두면 좋다.

3.1 이름 공간이 좁다

도구 이름으로 쓸 만한 동사는 몇 개 되지 않는다. search, find, query, list, get. 서버를 다섯 개 합치면 같은 뜻의 도구가 열 개가 된다. 모델 입장에서는 search_issues와 query_issues와 list_issues가 나란히 놓인 상황에서 어느 것이 정답인지 판단할 근거가 이름만으로는 없다.

3.2 설명이 단독 사용을 전제로 쓰여 있다

이게 더 근본적이다. 각 MCP 서버의 저자는 자기 서버만 붙는 상황을 가정하고 설명을 썼다. 그 맥락에서는 「메시지를 검색합니다」로 충분했다. 다섯 서버가 모이면 그 설명은 아무것도 구분해 주지 못한다. Anthropic이 도구 작성 지침에서 기능이 겹치는 도구를 정리하고 설명을 다듬는 것을 앞세우는 이유가 여기 있다. 당신이 겪는 문제의 상당 부분은 모델이 아니라 남이 쓴 설명문에서 온다.

3.3 컨텍스트 예산 잠식

정의가 창을 먹으면 실제 작업 맥락, 즉 대화 이력과 파일 내용과 중간 결과가 밀린다. 도구 미사용이 여기서 나온다. 도구가 안 보이는 게 아니라 도구를 쓸 이유가 되는 맥락이 잘려 나간 것이다. 긴 프롬프트로 통제하려는 시도가 왜 실패하는지는 긴 정책 문서로는 에이전트가 통제되지 않는다에서 따로 다뤘다.

4. 좁히는 방법 ① 지연 로딩 - 카탈로그와 컨텍스트를 분리한다

가장 효과가 큰 조치다. 카탈로그에는 도구를 다 두되 컨텍스트에는 필요한 것만 올린다. Claude API의 도구 검색 도구가 이 방식을 서버 쪽에서 구현한 것이고, OpenAI 함수 호출 가이드도 같은 방향을 권한다.

4.1 동작 방식

  • 도구 목록에 검색 도구를 하나 넣고, 나머지 도구에 defer_loading: true를 붙인다
  • 최소 하나는 지연하지 않은 상태로 남겨야 한다. 전부 지연시키면 400 오류다
  • 초기 컨텍스트에는 검색 도구와 지연하지 않은 도구만 들어간다
  • 모델이 필요할 때 검색을 실행하고, 결과가 도구 참조 블록으로 돌아와 정의로 펼쳐진다
  • 검색 결과는 기본 최대 5개, 지연 대상은 요청당 최대 1만 개까지
  • 검색 대상은 이름뿐 아니라 설명·인자명·인자 설명까지 포함한다

4.2 가장 많은 오해 - 요청 크기는 줄지 않는다

defer_loading은 요청 본문에 무엇을 보내는지가 아니라 컨텍스트에 무엇이 들어가는지를 제어한다. 모든 도구의 완전한 정의는 지연 대상까지 포함해 매 요청마다 그대로 실어 보내야 한다. 서버가 검색을 돌리고 참조를 확장하려면 정의가 필요하기 때문이다. 네트워크 페이로드를 줄이려고 이 기능을 켜는 것이라면 방향이 틀렸다.

4.3 프롬프트 캐시가 깨지지 않는 이유

이 설계에서 실무적으로 가장 중요한 부분이다. 지연된 도구는 시스템 프롬프트 앞부분에서 제외되고, 발견된 시점에 대화 안쪽에 참조 블록으로 붙는다. 앞부분이 바뀌지 않으니 프롬프트 캐시가 유지된다. 도구를 대화 중에 동적으로 갈아 끼우는 자체 구현이 캐시를 매번 깨뜨리는 것과 대비되는 지점이다. 단, 지연 대상 도구에는 캐시 제어 표시를 함께 붙일 수 없고 붙이면 400이 난다. 캐시 분기점은 지연하지 않은 도구 쪽에 둔다.

4.4 켜면 얼마나 좋아지나, 그리고 언제 켜지 말아야 하나

공개된 개선 폭은 이렇다. 도구 검색을 켜자 MCP 평가에서 Opus 4가 49퍼센트에서 74퍼센트로, Opus 4.5가 79.5퍼센트에서 88.1퍼센트로 올랐다. 토큰은 전형적으로 85퍼센트 이상 줄고 실제 필요한 3~5개만 올라온다.

반대 조건도 문서에 명시돼 있다. 도구가 10개 미만이거나, 매 요청에 모든 도구를 쓰거나, 정의 전체가 100 토큰도 안 되면 켜지 않는 편이 낫다. 검색 왕복이 지연으로 더해지는데 아낄 토큰이 없기 때문이다. 켤 조건은 도구 10개 이상, 정의 10K 토큰 초과, MCP 서버 여러 개를 합쳐 200개를 넘어가는 경우다.

5. 좁히는 방법 ② 검색만으로 안 되는 것 - 선행 관계

검색을 붙였는데도 실행이 안 되는 상황이 남는다. 이게 두 번째 층이다.

「주문을 환불해 줘」라는 요청을 생각해 보자. 검색은 refundOrder를 정확히 찾아낸다. 의미가 가장 가까우니 당연하다. 그런데 그 도구는 주문 번호를 요구하고, 주문 번호를 만들어 주는 findOrdersByEmail은 질의어와 의미가 멀어 후보에 들어오지 않는다. 검색 정확도는 만점인데 실행 가능한 계획은 만들어지지 않는다. 앞의 표에서 「선행 도구 누락」으로 분류한 실패다.

국내에서 공개된 graph-tool-call이 겨냥한 지점이 정확히 여기다. 도구를 개별 후보로 보지 않고 실행 사슬로 회수한다는 발상이다.

  • 도구 사이 관계를 선행(PRECEDES)·필요(REQUIRES)·보완(COMPLEMENTARY)의 방향 그래프로 둔다
  • 검색은 네 신호를 상호 순위 융합으로 합친다. BM25 키워드, 그래프 순회, 임베딩 유사도(선택), 그리고 MCP 어노테이션
  • 어노테이션은 읽기 전용·파괴적·멱등 여부를 담는다. 이걸 랭킹 신호로 쓴다는 점이 실무적으로 크다. 되돌릴 수 없는 도구를 뒤로 미는 장치를 검색 단계에 넣을 수 있다
  • 결과는 개별 도구가 아니라 선행 사슬이 포함된 순서 있는 실행 계획이다
  • OpenAPI/Swagger, MCP 서버, LangChain·LangGraph, 파이썬 함수를 받아들인다. 핵심 엔진은 외부 의존성이 없고 라이선스는 MIT다

5.1 제시된 수치와 그 수치의 크기

저장소가 밝힌 값은 이렇다. 7건짜리 결정적 커머스 회귀에서 실행 가능한 후보 구성 비율이 47.6퍼센트에서 100퍼센트로 올랐고, 필수 선행 도구 회수율도 100퍼센트에 도달했다. 도구 248개 환경에서 토큰 79퍼센트 감소, LangChain 게이트웨이 방식에서는 92퍼센트 감소다. 별도 예시로 도구 6개를 2개로 좁히며 스키마 토큰이 1,476에서 160으로 줄었다.

다만 크기를 정직하게 읽자. 7건짜리 결정적 시험은 성능 증명이 아니라 동작 증명에 가깝다. 사례를 늘렸을 때도 100퍼센트가 유지된다는 뜻은 아니다. 이 라이브러리를 평가할 자리는 벤치마크 숫자가 아니라 당신의 도구들 사이에 실제로 선행 관계가 존재하는가다. 조회와 실행이 짝을 이루는 업무 도메인, 즉 주문·결제·발송·승인 계열이면 값어치가 크고, 서로 독립적인 조회 도구만 모아 둔 환경이면 그래프를 그릴 게 없다.

6. 좁히는 방법 ③ 카탈로그 자체를 쪼갠다

앞의 둘이 「한 에이전트가 큰 카탈로그를 잘 다루게 하는」 접근이라면, 세 번째는 카탈로그를 나눠 각자에게 작은 목록만 주는 접근이다. OpenAI 쪽 안내에서도 큰 도구 표면을 다룰 때 역할별 서브에이전트로 쪼개 각 4~6개씩 주는 방식이 언급된다.

언제 쪼개는 게 맞나. 개수만 보고 쪼개면 손해다. 기준은 경계선이다.

  • 권한 경계가 다를 때. 읽기 전용 조회와 쓰기·삭제가 한 목록에 있으면, 나누는 것만으로 사고 반경이 줄어든다
  • 실패의 영향 범위가 다를 때. 잘못 불러도 무해한 도구와 되돌릴 수 없는 도구를 섞지 않는다
  • 맥락이 겹치지 않을 때. 코드 저장소 작업과 사내 문서 검색은 서로의 중간 결과를 거의 참조하지 않는다
  • 반대로 중간 결과를 계속 주고받아야 하면 쪼개지 말 것. 왕복마다 맥락을 다시 실어 보내야 해서 아낀 토큰보다 더 든다

개수 설계 자체를 어떻게 잡을지는 서브에이전트는 몇 개가 적당한가에서, 여러 에이전트를 동시에 굴릴 때의 조율 비용은 Orch term - 여러 AI 코딩 에이전트를 한 창에서 조율하는 터미널에서 다뤘다.

7. 좁히는 방법 ④ 이름과 설명 - 가장 싸고 가장 미루는 일

비용이 거의 들지 않는데 대부분 마지막에 손댄다. 순서를 바꾸는 게 맞다. 이걸 먼저 하면 나머지 셋의 효과가 커지고, 안 하면 셋 다 효과가 깎인다. 검색이 이름과 설명과 인자 설명을 훑는 구조이기 때문이다.

  • 접두사로 네임스페이스를 통일한다. github_, slack_처럼 서비스나 자원 이름을 앞에 붙이면 검색 한 번에 그 그룹이 통째로 잡힌다
  • 설명에 사용자가 쓰는 말을 넣는다. 「이슈를 생성합니다」보다 「버그·과업·티켓을 등록한다」가 실제 질의어와 겹친다
  • 시스템 프롬프트에 카테고리 한 줄. 어떤 계열의 도구를 검색할 수 있는지 미리 알려 주면 헛도는 검색이 준다
  • 인자 설명을 채운다. 인자 오류는 여기서만 줄어든다. 도구 사용 예시를 붙였을 때 복잡한 인자 처리가 72퍼센트에서 90퍼센트로 올랐다
  • 중복 도구를 통폐합한다. 같은 일을 하는 도구 두 개는 선택 난이도를 올리는 순수 비용이다
  • 어떤 도구가 실제로 발견되는지 관찰한다. 검색이 계속 헛짚는 도구는 설명이 잘못 쓰인 도구다

정규식 방식의 검색은 모델이 re.search() 패턴을 직접 만들어 대소문자 구분 없이 부분 일치를 본다. 패턴 길이는 200자, 자연어 질의 방식은 500자가 상한이다. 즉 이름과 설명에 들어 있지 않은 단어로는 그 도구가 절대 검색되지 않는다. 이 사실 하나만 알아도 설명을 쓰는 방식이 달라진다.

8. 어느 것부터 - 규모별 판단표

네 가지 방법을 한꺼번에 도입할 이유는 없다. 규모에 따라 이득이 나는 조치가 다르다.

규모먼저 할 것아직 하지 말 것이유
~10개 / 10K 토큰 미만인자 설명·예시 보강지연 로딩검색 왕복이 순손해
10~30개네임스페이스 통일, 중복 도구 제거서브에이전트 분리겹침이 주원인, 분리 비용이 더 큼
30~50개지연 로딩 도입. 자주 쓰는 3~5개는 남김그래프 구축선택 정확도가 꺾이기 시작하는 구간
50~200개지연 로딩 필수 + 권한 경계로 분리 검토—사고 반경 관리가 정확도만큼 중요해짐
200개 이상검색은 전제. 선행 관계·실행 사슬—검색이 맞아도 실행이 안 되는 실패가 주류

표의 30~50 구간이 Anthropic 문서가 선택 능력이 떨어지기 시작한다고 명시한 지점이다. OpenAI 쪽은 더 보수적이어서 한 턴의 시작 시점에 20개 미만을 목표로 하라고 권하고, 스스로 이것이 강한 규칙이 아니라 느슨한 제안이라고 덧붙인다. 두 값이 다르다는 사실이 중요하다. 이 숫자는 보편 상수가 아니다. 자기 카탈로그에서 개수를 늘려 가며 직접 재라는 것이 두 벤더가 공통으로 하는 이야기다.

9. 한국 개발 환경에서 특히 걸리는 것

9.1 REST를 1:1로 감싸면 도구가 폭증한다

가장 흔한 사고다. 사내 API 게이트웨이의 OpenAPI 명세에서 MCP 서버를 자동 생성하면 CRUD 엔드포인트가 그대로 도구가 된다. API 50개짜리 시스템이면 도구 200개가 만들어지고, 그중 에이전트가 실제로 쓸 일이 있는 것은 열 개 안팎이다. 자동 생성은 편하지만 그 편함의 대가를 매 요청 토큰으로 지불한다.

대응은 단순하다. 생성된 도구를 그대로 노출하지 말고 업무 단위로 다시 묶어라. 「주문 조회 → 상태 확인 → 취소」 세 호출을 에이전트가 조합하게 하는 대신 「주문 취소」 하나로 감싸는 편이 토큰과 정확도 양쪽에서 낫다.

9.2 도구 이름은 영문, 설명은 한국어

사내 도구에서 흔한 조합이다. 검색이 이름·설명·인자명·인자 설명을 함께 훑는 구조라 이 조합 자체가 곧바로 문제는 아니다. 다만 정규식 방식에서 모델이 만드는 패턴은 영문 어근에 기대는 경우가 많다. 설명이 한국어로만 쓰여 있으면 그 도구가 걸리지 않을 수 있다.

안전한 처리는 설명에 두 언어의 핵심어를 함께 넣는 것이다. 「사내 위키 문서를 검색한다 (wiki document search)」처럼 쓰면 어느 쪽 패턴에도 걸린다. 문서가 권하는 「사용자가 과업을 말하는 방식의 키워드를 설명에 넣으라」를 한국어 환경에 적용하면 이렇게 된다.

9.3 폐쇄망에서는 서버 쪽 검색을 못 쓴다

금융·공공처럼 외부 API 호출이 막힌 환경에서는 벤더가 제공하는 서버 측 도구 검색을 켤 수 없다. 이 경우 경로는 둘이다. 하나는 클라이언트 측 검색을 직접 구현하는 것으로, 자체 검색 도구가 도구 참조를 반환하면 API가 같은 방식으로 정의를 펼쳐 준다. 임베딩 기반 회수를 붙일 수 있는 것도 이 경로다. 다른 하나는 graph-tool-call처럼 로컬에서 도는 라이브러리로 모델 바깥에서 카탈로그를 좁히는 것이다. 로컬 모델을 함께 쓰는 구성이라면 로컬 LLM 에이전트 개발, 툴 검색과 HITL이 필요한 이유도 같이 보면 된다.

9.4 결재·발송처럼 되돌릴 수 없는 도구

전자결재 상신, 알림 발송, 고객 대상 메시지처럼 실행되면 되돌릴 수 없는 도구가 사내 카탈로그에는 반드시 섞인다. 여기서 도구 개수 문제는 정확도 문제를 넘어 사고 문제가 된다. 최소한 두 가지는 하자. 파괴적 속성을 어노테이션으로 명시해 랭킹과 노출에서 뒤로 밀고, 실행 직전에 사람 확인을 강제하는 것이다. 문장으로 적어 둔 금지는 잘 지켜지지 않는다.

10. 이 수치들을 어떻게 받아들일 것인가

이 글에 나온 개선 폭은 대부분 벤더 자체 평가이거나 저장소 자체 회귀 시험이다. 이 사실은 수치를 버릴 이유가 아니라 어떤 부분을 믿을지 가르는 근거다.

  • 방향은 신뢰할 만하다. 노출을 줄이면 선택이 나아진다는 결론은 벤더가 다르고 방식이 다른 여러 자료에서 같은 쪽을 가리킨다
  • 폭은 그대로 옮겨 쓸 수 없다. 49→74퍼센트는 그 평가의 카탈로그에서 나온 값이지 당신의 카탈로그에서 나올 값이 아니다
  • 절대 수준을 함께 보라. RAG-MCP 논문은 회수 기반 선택으로 도구 선택 정확도를 13.62퍼센트에서 43.13퍼센트로 끌어올렸다. 3배가 넘는 개선이지만 43퍼센트는 여전히 절반이 안 된다. 「검색을 붙이면 해결된다」가 아니라 「검색 없이는 시작조차 안 된다」로 읽는 편이 정확하다
  • 경계선 숫자도 벤더마다 다르다. 30~50과 20이라는 두 값이 공존한다는 사실 자체가, 이 값이 모델과 카탈로그와 과업에 따라 움직인다는 증거다

측정 방법은 어렵지 않다. 자기 카탈로그에서 도구 개수를 단계적으로 늘려 가며 같은 과업 묶음의 성공률을 재는 것이다. 이 방식은 OpenAI 문서도 권한다. 한 번 해 두면 사내에서 「도구 몇 개까지 괜찮나」라는 질문에 남의 숫자 대신 자기 숫자로 답할 수 있다.

11. 확인하지 못한 것

다음 항목은 1차 근거를 확보하지 못해 본문에서 수치로 쓰지 않았다.

  • 위치 편향. 긴 도구 목록의 가운데에 놓인 도구가 앞뒤보다 덜 선택된다는 주장이 여러 곳에서 언급되지만, 검증 가능한 1차 자료를 특정하지 못했다
  • graph-tool-call 회귀 시험의 기준선. 필수 선행 도구 회수율의 개선 전 값이 저장소 설명과 소개 글에서 서로 다르게 적혀 있다. 개선 후 값이 100퍼센트라는 점은 양쪽이 같다
  • MCP 평가의 구성. 49→74퍼센트와 79.5→88.1퍼센트가 나온 평가의 도구 개수와 과업 수는 공개돼 있지 않다
  • 도구 개수 대비 정확도의 독립 대규모 측정. 벤더와 무관한 제3자가 동일 조건에서 개수만 바꿔 가며 측정한 공개 결과를 찾지 못했다

12. 결론: 줄이라는 얘기가 아니다

이 글의 주장은 도구를 적게 붙이라는 것이 아니다. 붙이는 것과 펼치는 것을 분리하라는 것이다. 카탈로그는 수백 개여도 되고, 한 턴의 시작 시점에 놓이는 것은 열 개 안쪽이어도 된다. 이 둘을 같은 값으로 묶어 두었기 때문에 「도구를 늘리면 느려지고 틀린다」는 체감이 생겼다.

적용 순서는 이렇게 잡으면 손해가 없다.

  1. 중복 제거. 같은 일을 하는 도구를 없앤다. 비용 0, 효과 즉시
  2. 이름과 설명. 접두사 통일, 사용자 어휘 반영, 인자 설명 채우기
  3. 지연 로딩. 30개를 넘어가면 여기서 가장 큰 폭이 나온다
  4. 선행 관계. 검색은 맞는데 실행이 안 되는 실패가 남을 때만
  5. 카탈로그 분리. 개수가 아니라 권한 경계와 사고 반경을 기준으로

마지막으로, 가장 흔한 착각 하나를 짚고 끝내자. 「우리 에이전트는 도구가 20개밖에 안 되니 괜찮다」는 판단이다. 앞의 표에서 봤듯 도구 11개짜리 서버가 21K 토큰을 먹는다. 개수는 적은데 토큰은 많고 이름은 겹칠 수 있다. 지금 붙어 있는 도구의 정의 토큰을 한 번 재 보는 것, 그리고 이름이 비슷한 도구를 목록으로 뽑아 보는 것. 이 두 가지가 어떤 라이브러리를 도입할지 고르는 일보다 먼저다.
