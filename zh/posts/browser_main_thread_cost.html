浏览器主线程为什么只有一条 - 谁在分用这一条，什么又能被移出去

脚本与渲染互相阻塞的机制、三个指标各自测的东西，以及最终出不去的那些工作的边界

2026-09-05 开发/基础设施

网页卡顿时，最先冒出来的诊断多半是代码太慢。于是改算法、换库、削减打包体积。可这些做完之后体感照旧的情况并不少见。问题从来不是速度，而是位置。

在一个浏览器标签页里，与画面有关的工作几乎全部发生在仅有的一条线程上。JavaScript 在那里跑，样式计算在那里做，布局和绘制指令的生成也在那里。就连判定某个坐标下压着哪个元素这件事也在那里。这份清单上的每一项都在等其他项。只要有一项抓着线程，其余就得排队。

本文不是优化技巧集。它要看的是这一条线程被谁分用着、卡顿这种体感会被哪些指标捕捉到，以及线程上的工作里，哪些能被移出去、哪些永远出不去，那条界线画在哪里。知道界线在哪，也就同时看清了哪些优化从一开始就不可能成立。

以下的指标定义与阈值，全部与 web.dev、Chrome for Developers、W3C 草案、MDN 及 WHATWG HTML 标准原文所载一致。性能指标的阈值是会被修订的，而把旧文章里的数字原样搬过来，正是最常见的错误。下表中的数值同样需要连同引用时点一起读。

缘起 - 问题不在代码的速度而在它的位置

2026 年 9 月初，韩国开发者社区出现了一篇题为浏览器的主线程很贵的文章。原文用韩语写成，主旨压缩成一句话就是：问题不在于代码慢，而在于这段代码偏偏抓着主线程。原文在这个判断之上叠了七条处方：切分、合并、优先级、推迟、交给合成线程、送进 Worker，以及干脆把工作本身去掉。原文写道，其中最后一条通常留下的收益最大。

处方清单是有用的。但清单不解释这些处方为什么有效。切分明明没让任何东西变快，为什么响应会变好？能送进 Worker 的工作和不能送的，分界线是什么？交给合成线程这句话，具体跳过了哪个阶段？这些只有看结构才会浮出来。

所以本文用结构与边界取代处方。其中也包括原文没有涉及的内容。Long Animation Frames、OffscreenCanvas 和 requestIdleCallback 在原文里没有出现。反过来，原文提到的 content-visibility、INP 与 TBT 这里也会讲，但会把官方文档的定义原样附上。性能话题里最常见的事故，就是把别人抄过的数字再抄一遍。

主线程实际背着的工作清单

Chromium 的渲染架构文档用一句话列举了渲染进程内主线程承担的工作：运行脚本、渲染事件循环、文档生命周期、命中测试、脚本事件派发，以及 HTML 和 CSS 等数据格式的解析。同一份文档还写明，渲染进程里另有合成线程和若干辅助线程。也就是说浏览器并不是单线程的，只是计算画面真相的地方只有一处。

这份清单值得注意的地方在于，条目在性质上完全是不同的事，却站在同一条队里。一个排序算法、一次样式重算和一次点击回调之间毫无关系，但一旦共用执行座位，就互相成了对方迟到的原因。

主线程承担的工作具体指什么这里堵住时出现的症状
脚本执行事件处理函数、定时器回调、网络响应处理、框架内部逻辑期间到达的输入只能在队列里等
渲染事件循环与文档生命周期样式计算、布局、预绘制、绘制指令生成帧迟到，画面看上去像卡死了
命中测试判定某个坐标下压着哪个元素按下去却什么反应都没有
脚本事件派发沿捕获与冒泡路径调用已注册的处理函数输入延迟原样累积
HTML 与 CSS 等的解析解释文档、样式表以及其他数据格式首次渲染被往后推

表格右列是用户真正遭遇的东西，左列是开发者在代码里看到的东西。在这两列之间搭桥，就是下一节要做的事。

一次只能一件 - 任务跑完才让出座位

这个结构之所以成为问题，真正的原因不是线程只有一条，而是执行单元不可被抢占。JavaScript 任务一旦开始就会跑到底。中途来了更急的事，浏览器也没法把它切开插进去。操作系统调度器会在时间片耗尽时强制切换上下文，事件循环里没有这种机制。

所以当一个耗时 300 毫秒的函数正在跑、用户按下按钮时，这次点击会以已经存在但还没人知道的状态待在队列里。函数结束派发才开始，处理函数结束才轮到渲染更新。这段等待正是后面要讲的 INP 的第一段，即输入延迟。

这里有一个常见误解需要澄清：异步不等于并行。async 函数、Promise 链、fetch 的响应处理，最终都会作为主线程上的任务或微任务回来。等网络确实会放开线程，但响应到达之后的解析、状态更新和列表重绘，全都发生在同一个座位上。用异步写法并不会把繁重计算搬到别处去。

帧预算 - 16.6 毫秒里真正属于你的部分

画面要看起来顺滑，帧就得规律地产出。web.dev 的渲染性能文档写道，在 60Hz 屏幕上浏览器制作一帧有 16.66 毫秒。紧接着它就补了一句限定：浏览器每帧都有自己的开销，所以你的全部工作必须在 10 毫秒内完成。

这个数字重要的地方在于比例而不是绝对值。刷新率上去了，预算就等比缩水。120Hz 屏幕上帧间隔减半，可用时间也减半。设备越高端似乎越宽裕，但刷新率一起提高之后，实际上反而更紧。

而且这 10 毫秒并不是 JavaScript 独享的预算。样式计算、布局、绘制指令生成都要装进去。脚本用掉 8 毫秒，剩下的全部就得在 2 毫秒内结束。重绘列表的代码看起来很快，但只要跟在它后面的布局成本超了预算，帧照样会掉。

互相阻塞的方式 - 五个阶段的依赖关系

web.dev 把一帧的生成过程称为五个阶段：JavaScript、样式、布局、绘制、合成。JavaScript 制造视觉变化，样式阶段匹配哪些 CSS 规则作用于哪些元素并算出计算值。布局决定元素的尺寸和屏幕位置，这个阶段的特点是一个元素的变化可能扩散到整棵树。绘制把结果变成填充像素的指令，合成则把画好的图层按正确顺序放到屏幕上。

这个顺序本身就是依赖关系。没有布局结果就无法绘制，没有样式计算就无法布局。由此引出两点。

  • 改哪个属性，决定了进入管线的入口在哪。改宽度或位置就要从布局重来，只改颜色则跳过布局从绘制开始
  • 有些属性能把布局和绘制一起跳过。web.dev 明确写道，如果改的属性既不需要布局也不需要绘制，浏览器可以直接跳到合成阶段，并称这是管线中最廉价也最理想的路径
  • 在同一帧里交替进行读和写，浏览器为了返回最新的布局值会把计算提前执行。所谓先把要读的全读完、再把要写的集中写，习惯的由来就在这里
  • 这种强制计算在代码里很难看出来。一个询问元素尺寸或位置的属性就会当场触发布局，如果它待在循环里，布局就会跑上和条目数一样多的次数

归结起来，主线程上的这些工作不只是分用一个座位，它们互为输入与输出。所以一处的延迟会蔓延到另一处，一处的节省也会救活另一处。

测量卡顿的三个指标及其阈值

结构清楚了，下一步是测量。卡顿这个词本身不携带任何信息，不先定好测什么、怎么测，连有没有改善都判断不了。网页上通行的轴有三条。

INP - 从按下去到画面改变

Interaction to Next Paint 通过观测整次访问期间发生的所有点击、轻触与键盘交互的延迟，来表示该页面的整体响应性。一次交互被拆成三段：处理函数开始执行前等待的输入延迟、各个回调运行的处理时长，以及回调结束后到下一帧被绘制出来的呈现延迟。滚动、悬停和缩放不计入 INP。INP 在 2024 年成为稳定的核心网页指标，取代了 FID。

TBT - 加载期间主线程被堵住的总量

Total Blocking Time 指 First Contentful Paint 之后，主线程被占用到足以妨碍输入响应的时间总和。算法简单到值得直接背下来：在主线程上运行超过 50 毫秒的任务叫长任务，每个长任务只把超出 50 毫秒的那部分累加。一个 120 毫秒的任务贡献 70 毫秒，一个 45 毫秒的任务贡献 0。TBT 是实验室指标。web.dev 写道，在真实环境中测量虽然可行，但用户交互会让数值大幅波动、报告方差变大，因此不推荐。

LoAF - 按帧看延迟，并附上肇事者

Long Animation Frames 数的是帧而不是任务。W3C 草案把持续时间超过 50 毫秒的两种情形定义为长动画帧：一个之后不需要更新渲染的任务，以及一个之后需要更新渲染的任务直到渲染真正被更新为止的区间。条目里包含 startTime、duration、renderStart、styleAndLayoutStart、blockingDuration、firstUIEventTimestamp，以及归因脚本数组 scripts。

指标测的是什么在哪里测官方文档给出的良好值
INP点击、轻触或按键之后到下一次绘制的延迟，覆盖整次访问真实用户现场数据，用于核心网页指标判定200 毫秒以内为良好。超过 200 且不超过 500 需要改进。超过 500 为差。按 75 百分位数判定
TBTFCP 之后长任务超出 50 毫秒部分的总和实验室工具。web.dev 不推荐现场测量在中等移动硬件上小于 200 毫秒
LoAF渲染更新被拖延超过 50 毫秒的每一帧，以及肇事脚本用 PerformanceObserver 观测。Chrome 123 及以上、Edge 123 及以上没有单一阈值。帧的持续时间超过 50 毫秒即被记录
参考：核心网页指标三项LCP 看加载，INP 看交互，CLS 看视觉稳定性现场数据，移动端与桌面端分开汇总LCP 2.5 秒以内、INP 200 毫秒以内、CLS 0.1 以内，均取 75 百分位数

三个指标从不同角度看同一件事。TBT 是加载区间的总量，INP 是真实用户遭遇的响应性，LoAF 则告诉你哪一帧出了问题、是谁干的。当作改进流程来用，就是：用 LoAF 找出肇事者，用 TBT 防止回归，用 INP 确认修复真的落到了用户身上。

为什么只有长任务是不够的

Long Tasks API 长期是观察主线程占用的基本工具。但这个 API 有个结构性的盲区：只有单个任务超过 50 毫秒才会被记录。五个 40 毫秒的任务接连堵住一帧长达 200 毫秒，长任务一个都抓不到。用户等了 200 毫秒，仪表盘却安静如常。

LoAF 以帧为粒度补上了这个盲区。Chrome for Developers 的文档说明，因为 LoAF 看的是整帧而不是单个任务，所以能捕捉到多个小任务合起来阻塞渲染的情形，并且在时序拆解和脚本归因上都好得多。这里 blockingDuration 的算法很有意思。W3C 草案写道，把帧内任务的持续时间降序排列，如果发生了渲染就把渲染时长并入最长的那个任务，然后把每一项超出 50 毫秒的部分加起来。这是把 TBT 的计算规则挪进了一帧的内部。

脚本归因在实务中的体感也很大。PerformanceScriptTiming 条目里带有调用方信息 invoker 与 invokerType、执行起始时刻 executionStart、指向源码位置的 sourceURL 与 sourceFunctionName 与 sourceCharPosition，以及该脚本强制触发的样式与布局耗时 forcedStyleAndLayoutDuration。最后这一项，正是把前面说的读写交错成本以数字形式还给你的地方。

但支持范围很窄。它只在 Chrome 123 及以上和 Edge 123 及以上工作，Firefox 与 Safari 目前都没有。因此 LoAF 是诊断工具，不是覆盖全体用户的仪表盘。把这个区别弄模糊，在 Safari 用户占比较大的服务上就会产生错误的安心感。

让出 - 放开线程再重新抓住的技艺

既然没有抢占，剩下的办法就只有主动放手。把长活切成若干任务，在碎片之间留出让浏览器插进来的缝隙。这里有一点必须挑明：让出并不会减少总工作量。恰恰因为任务切换的开销，整体时间还会略微变长。换来的是中间多出了输入处理和渲染可以进入的位置。这是一笔做同样多的活、只买响应性的交易。

让出的手段有好几种，性质各不相同。用 setTimeout 推迟，任务会被挂到队列最末尾。如果期间涌进了大量其他任务，自己的活就要等很久才恢复。而且嵌套一深还会被钳制。WHATWG HTML 标准规定，当嵌套层级大于 5 且超时值小于 4 时，把超时值提升为 4。

scheduler.yield() 正面处理了这个问题。web.dev 说明它就是一个返回 Promise 的函数，而且当前任务的后续部分会先于其他同类任务执行。也就是说让出但不用排到队尾。支持情况为 Chrome 129 及以上、Edge 129 及以上、Firefox 142 及以上，Safari 不支持。

// 分批处理长列表，每帧都把主线程放开一次。
async function processInChunks(items, work) {
  const CHUNK_BUDGET_MS = 5;        // 一次抓住线程的时长 (经验值)
  let start = performance.now();

  for (let i = 0; i < items.length; i++) {
    work(items[i]);

    // 预算还没用完就继续抓着。
    if (performance.now() - start < CHUNK_BUDGET_MS) continue;

    // 有 scheduler.yield 就用它。
    // 后续部分会先于其他同类任务回来。
    if (typeof scheduler !== 'undefined' && 'yield' in scheduler) {
      await scheduler.yield();
    } else {
      // 兜底路径。会排到队尾，嵌套过深还会被钳制到 4ms。
      await new Promise((resolve) => setTimeout(resolve, 0));
    }
    start = performance.now();
  }
}

这里有一条已被废弃的建议需要点出来。只在有输入等待时才让出、因而使用 isInputPending() 的写法曾经流传了一阵。web.dev 现在不再推荐这个 API，并明确建议无论是否有输入在等待都应当让出，理由是可能出现假阴性且覆盖范围不完整。旧博客文章里残留的代码最好不要照搬。

给工作贴上优先级

光靠让出有时还不够，因为放开的座位由谁先占仍然没有定。Prioritized Task Scheduling API 负责这一块。scheduler.postTask() 接受三档优先级，MDN 写道执行会按优先级顺序、同优先级内按声明顺序进行。

优先级怎么指定贴给什么样的工作
user-blocking在选项里显式写明用户正在等结果、且挡住了画面更新的工作
user-visible省略时就是它 (默认值)画面上看得见但没那么即时的工作
background在选项里显式写明没人在等的工作，比如预计算或日志上报

如果优先级以后可能需要改，就不能把值直接写进选项。MDN 建议，可变的优先级要创建 TaskController、把它的信号传给选项，再用 setPriority() 调整。原本从容预算的工作因为用户点了一下而突然变急，正是这种情形。

相邻的位置上还有 requestIdleCallback。MDN 说明它把函数排进浏览器的空闲期，从而能够在不影响动画和输入响应这类延迟敏感事件的前提下，在主线程上跑后台低优先级工作。回调会收到 IdleDeadline，用 timeRemaining() 询问剩余时间，用 didTimeout 确认自己是不是因为超时才被调用的。有两条限定：对于必须执行的工作强烈建议使用 timeout 选项；而一旦超时到期，即便冒着造成负面性能影响的风险回调也会被排入队列。可用性并不宽，MDN 标注它因为在部分最广泛使用的浏览器上无法工作而不属于 Baseline。这个 API 在原文里没有出现。

能移出去的一 - 交给 Worker 的计算

从这里开始才是本文的正题：主线程上的工作里，真正能出去的是什么？第一条通道是 Web Worker。

Worker 的边界画得异常清晰。MDN 明确指出，在 Worker 内部无法直接操作 DOM，也无法使用 window 对象的部分默认方法和属性。Worker 里做不到的核心是直接影响父页面，其中就包括操作 DOM 和使用该页面的对象。因为全局作用域是 DedicatedWorkerGlobalScope 而不是 Window，所以没有 window、没有 document、没有 parent。反过来，fetch、XMLHttpRequest、定时器、标准内置对象和 importScripts() 都可以用。

第二件要知道的事是数据怎么过去。默认是复制。照搬 MDN 的表述：主页面与 Worker 之间传递的数据是被复制而不是共享的，对象在交出时被序列化、在另一端被反序列化，页面与 Worker 不共享同一个实例，结果是两边各自多出一份副本。这就是结构化克隆。所以每帧来回搬运大数组，会让搬进 Worker 得到的收益被序列化成本抵消掉。

可转移对象解决了这个问题。所有权整体移交，所以不发生复制。MDN 写道，把 ArrayBuffer 转移给 Worker 之后，原来的 ArrayBuffer 会被清空、不再可用，内容是字面意义上被转移走了。

// main.js - 大缓冲区不要复制，把所有权整个交出去。
const worker = new Worker('./heavy.js');
const pixels = new Uint8ClampedArray(width * height * 4);
// ... 填充 pixels ...

worker.postMessage(
  { buffer: pixels.buffer, width, height },
  [pixels.buffer]                 // 第二个参数是转移列表
);
// 这一行之后 pixels.buffer 就空了 (byteLength === 0)

worker.onmessage = (e) => {
  const out = new ImageData(new Uint8ClampedArray(e.data.buffer), e.data.width);
  ctx.putImageData(out, 0, 0);    // 碰 DOM 的活在这里，在主线程上
};

// heavy.js - 这里没有 DOM。只进数据，只出数据。
self.onmessage = (e) => {
  const { buffer, width, height } = e.data;
  const buf = new Uint8ClampedArray(buffer);
  for (let i = 0; i < buf.length; i += 4) {
    const g = (buf[i] * 0.299 + buf[i + 1] * 0.587 + buf[i + 2] * 0.114) | 0;
    buf[i] = buf[i + 1] = buf[i + 2] = g;
  }
  self.postMessage({ buffer: buf.buffer, width, height }, [buf.buffer]);
};

画布在这条边界上开了一扇例外的门。OffscreenCanvas 把 DOM 与 Canvas API 解耦，让 <canvas> 元素不再完全依赖 DOM。MDN 说明渲染操作可以在 Worker 上下文中运行，从而把繁重的工作从主线程挪走。用法是通过 transferControlToOffscreen() 摘下控制权并转移给 Worker，而且在 Worker 里连 requestAnimationFrame() 都能用。文档标注它自 2023 年 3 月起已在各浏览器上普遍可用。这个 API 同样没有出现在原文里。

能移出去的二 - 交给合成线程的动效

第二条通道性质不同。你不是在搬运代码，而是在把条件凑齐，让浏览器自己把活放到另一条线程上处理。

Chromium 文档写道，渲染进程里的合成线程负责处理输入、执行滚动与动画，并协调图像解码和光栅任务。它还明确指出，把主线程与合成线程分开，对于把动画和滚动从主线程工作中做性能隔离至关重要。更具体地说：视觉效果动画与滚动可以跳过布局、预绘制和绘制，而只要这三个阶段能被跳过，它们就能完全在合成线程上运行并跳过主线程。

落到实务上，规则就很简单了。用 left 和 top 做位移动画，每帧都要跑布局，而布局属于主线程。同样的位移改用 transform，布局和绘制都被跳过，只剩合成。不透明度也是一样。主线程再忙也依旧顺滑的动画和一行脚本就卡死的动画，分野就在这里。

滚动适用同一原理，但这里有个开发者自己把好处退回去的常见陷阱：事件监听器的 passive 选项。MDN 说明把 passive 设为 true，就是声明该监听器不会取消默认动作，因而浏览器可以不等监听器执行完就立即开始默认动作。反过来，只要挂着可取消的监听器，浏览器无从知道 preventDefault() 会不会被调用，就必须等。那段等待就是滚动延迟。

默认值需要记准。MDN 写道，未指定时 passive 为 false，但在 Safari 以外的浏览器中，对于挂在 Window、Document、Document.body 这些文档级节点上的 wheel、mousewheel、touchstart、touchmove，默认为 true。也就是说挂在具体元素而非文档级节点上的触摸监听器，默认仍然是 false。这是应当养成显式写 { passive: true } 习惯的地方。

移不出去的 - 边界画在哪里

现在看另一侧。有些工作无论怎么折腾都出不去，原因不在性能而在定义。

必须碰 DOM 的工作

Worker 里没有 document，这是设计而不是实现未完成。DOM 是一棵多线程同时触碰就无法保持一致性的可变树，所以访问被收拢到一条线程上。接受这个决定，样式计算与布局就一并被收拢了，因为两者都得读 DOM 树和样式表。Chromium 文档把文档生命周期写成主线程的工作，说的正是这个意思。

必须保留可取消性的输入

命中测试与事件派发同理。要知道某个坐标下压着哪个元素就需要最新的布局，而布局在主线程上。再者，监听器有可能调用 preventDefault() 这一可能性本身就会让浏览器等待。即便滚动正由合成线程处理，只要出现可取消的监听器，判定就得回头问主线程。

想做的事能否移出主线程为什么
解析、压缩、排序、图像像素处理这类纯计算能 — Web Worker不使用 DOM，输入输出只有数据
往画布上绘制能 — OffscreenCanvas 加 Worker画布可以从 DOM 上摘下来，只把控制权交给 Worker
transform 与 opacity 动画能 — 合成线程布局、预绘制和绘制都能跳过
滚动多数情况能 — 合成线程但挂上可取消的监听器就得回头问主线程
读写 DOM不能Worker 里没有 window、document、parent
样式计算与布局不能文档生命周期被定义为主线程的工作
运行输入事件处理函数不能脚本事件派发本身就发生在主线程上
命中测试不能必须读到最新布局才能判定

这张表给出的结论相当干脆：腾空主线程的最好办法不是搬走而是减少。能搬的只有表格上面那四行，而真实网页应用里最吃时间的通常是下面那四行。

直接减少工作 - 隔离与跳过

减少工作的办法里最具结构性的是 CSS 隔离。MDN 说明 CSS containment 能把页面的子树与其余 DOM 隔离开，从而让浏览器通过优化这些独立部分的渲染来提升性能。contain 属性的各个值各自关住不同的东西：size 把元素的尺寸计算与其内容切开，layout 把布局重算约束在该元素及其后代之内，style 对应样式重算，paint 把绘制关在元素边界之内。content 是 layout、style、paint 三者的简写，不含尺寸。strict 在此之上再加 size，是最强的形态。

隔离真正变成收益的代表性场景是 content-visibility。web.dev 文档写道，带有 content-visibility: auto 的元素会获得布局、样式和绘制隔离，处于屏幕外时还会获得尺寸隔离。在此期间浏览器只对元素盒本身做样式和布局，不绘制内容也不做命中测试。同一份文档的旅行博客示例里，渲染时间从 232 毫秒降到 30 毫秒，文档称之为 7 倍提升。

/* 跳过屏幕外卡片的样式、布局与绘制 */
.feed-card {
  content-visibility: auto;

  /* 跳过期间使用的占位尺寸。
     没有它，屏幕外元素高度会塌成 0，
     滚动条长度会不停乱跳。 */
  contain-intrinsic-size: auto 480px;
}

/* 只在连尺寸也可以隔离的地方才用 strict。
   strict = size + layout + style + paint */
.widget-frame {
  contain: strict;
  width: 320px;
  height: 240px;
}

contain-intrinsic-size 指定的是元素受尺寸隔离影响时所使用的自然尺寸。没有它，屏幕外元素会塌成零高度，滚动条大小随之抖动。web.dev 把这个属性称作替代已渲染内容的占位尺寸。

有一点需要留意。被 content-visibility: auto 跳过的内容仍然可以被页内查找搜到并跳转过去，无需等待其加载完成。这既是它与 display: none、visibility: hidden 的区别，也是它的优点。但也正因如此，屏幕外的地标元素会照样出现在无障碍树里，所以文档建议在需要时加上 aria-hidden 来整理。也就是说，拿到性能的同时还要另外照顾不把无障碍树弄乱这一平衡。

走到这里，原文为什么说最大的收益通常来自把工作删掉，也就说得通了。能搬的本来就少，搬运本身还有成本，而压根没做的工作在任何线程上都不占时间。

本文与那篇引子文章分岔的地方

原文给的是处方。它把该做什么分成七支，配上例子展示出来，是实务中可以直接取用的形态，尤其切分、合并、优先级这三支具体到不用框架也能落地。原文列出的数字与本文也不冲突：16.6 毫秒的帧预算、50 毫秒的长任务标准，以及同时提到 INP 与 TBT 的部分都是如此。

本文画的是边界。在处方之前先把什么因为什么原因必须待在什么位置定下来，日后出现新处方时就能自己判断它该放在哪里。为此，下面三样是从原文之外拿来补上的。

  • Long Animation Frames — 原文里没有。只靠长任务标准抓不到小任务合起来堵住一帧的情形，补上这个盲区的正是这个 API
  • OffscreenCanvas — 原文里没有。它是 Worker 不能碰 DOM 这条规则上唯一实用的缺口，讲边界时无法略过
  • requestIdleCallback — 原文里没有。它处在优先级话题的另一端，是处理最低档位的老手段，可用范围狭窄这一事实也要一起看
  • 反过来 content-visibility 原文是提到的。原文把它简短介绍为用一行 CSS 追求类似效果的属性，而本文把它获得的隔离种类以及必须搭配使用的属性都摊开了讲

关于测量再补一句：感受到的迟滞与仪表盘上的数值经常对不上。处理这段落差的文章是可以慢下去的共识是怎么形成的，而画面状态一致性如何转化为信任，则由每一帧都要完美来讲。把渲染搬进画布会失去什么，写在把 HTML 画进 canvas 的 API 里；用虚拟化扛住海量列表的具体案例，已经在 Trees 文件树渲染库整理过，这里就不重复了。

最后提一个顺序建议。动代码之前先看是哪一帧迟到、为什么迟到。用 LoAF 找出肇事脚本，再确认这个脚本做的事属于上面表格的哪一行。属于上面四行就搬走，属于下面四行就减少。光是把这个判断做对，把时间花在根本不成立的优化上这件事就会消失。

未能确认的部分

  • 嵌套定时器的最小延迟值在不同文档里写法不一致。WHATWG HTML 标准规定嵌套层级大于 5 且超时值小于 4 时提升为 4，而 web.dev 的长任务文档写的是5 毫秒。正文采用了标准一侧的数值，但两份文档为何不同未能确认
  • IdleDeadline.timeRemaining() 返回值是否存在50 毫秒之类的上限，在 MDN 文档里没有找到明确说明。这是被频繁引用的数字，但因为没有直接确认到规范原句，正文里没有采用
  • INP 取代 FID 的确切日期未能确认。确认到的只是核心网页指标文档中「2024 年成为稳定指标」的表述，以及公告文章里只写着「今天就是这一天」这一事实
  • Long Animation Frames 的 50 毫秒标准是否可调，以及这个指标今后是否有升格为核心网页指标的计划，都未能确认
  • OffscreenCanvas 是否支持 WebGPU 上下文，在 MDN 概览文档里未能确认。该文档给出的示例只有 2D 与 WebGL
  • 原文提出的每帧 5 毫秒的分块预算是经验值而非规范。这个数值的出处或依据原文没有写，因而无法确认。正文示例中也标注了它是经验值
  • Safari 对 requestIdleCallback 与 scheduler.yield() 的支持情况，只确认到 MDN「在部分最广泛使用的浏览器上无法工作」的表述与 web.dev「Safari 不支持」的说明，逐版本兼容性表没有直接打开查看
  • WHATWG HTML 标准中「update the rendering」子步骤的顺序虽然打开了文档，但相关章节被截断因而未能确认。正文的管线顺序依据的是 web.dev 与 Chromium 架构文档的表述
