Grit - AI 에이전트로 Git을 Rust로 재작성한 시도, 무엇을 증명하고 무엇을 못 했나

GitButler가 에이전트 스웜으로 Git을 Rust로 다시 쓴 실험 - 테스트 99% 통과의 진짜 의미와 대규모 재작성의 실현성·한계

2026-06-16 개발/인프라

서론: "Git을 AI로 Rust에 옮겼다"는 헤드라인을 어떻게 읽을 것인가

2026년 6월 기준, 개발자 커뮤니티에 한 프로젝트가 화제가 됐다. GitHub 공동창업자 Scott Chacon이 이끄는 GitButler가 Git을 Rust로 처음부터 재작성한 Grit을 공개했다. 더 놀라운 건 방식이다. 사람이 한 줄 한 줄 옮긴 게 아니라, AI 코딩 에이전트 스웜(swarm)을 풀어 Git의 방대한 테스트 스위트를 통과할 때까지 코드를 생성하게 했다. 보고된 규모는 약 36만 줄, 테스트 통과율 99% 이상이다.

헤드라인만 보면 결론은 단순해 보인다. "이제 AI가 Git 같은 시스템 소프트웨어도 통째로 재작성한다." 하지만 이 글의 목적은 그 환호를 옮기는 게 아니라, 이 시도가 정확히 무엇을 증명했고 무엇은 증명하지 못했는지를 분해하는 것이다. 같은 사실을 두고도 "에이전트가 대규모 재작성을 해냈다"와 "특수한 조건에서만 가능했던 실험이다"는 전혀 다른 교훈으로 이어진다. 본인은 후자에 가까운 입장이며, 왜 그런지를 근거와 함께 풀어 보겠다.

미리 단서를 박는다. 여기 나오는 수치(약 36만 줄, 테스트 4만 2천 개 중 99% 통과, 약 450억 토큰, 추정 비용 1만~1만 5천 달러)는 GitButler의 공개 글과 저장소 기준이며, 제작자 본인이 "아직 아무도 실제로 써보지 않았다"고 명시한 실험 단계의 산출물이다. 본인이 사실을 전달하는 부분과 본인 해석을 내놓는 부분을 구분하겠다. 이 글은 Claude Code 동적 워크플로 분석과 Jqwik 반(反)AI 사건에서 다룬 에이전트 코딩 흐름과 이어지되, 각도가 다르다. 이번엔 "에이전트가 대규모 레거시를 재작성할 수 있는가"라는 질문이다.

1. Grit이란 무엇인가 - 라이브러리로서의 Git이라는 15년 묵은 꿈

먼저 Grit이 무엇을 노렸는지부터 정리하자. 동기를 이해해야 결과를 제대로 읽을 수 있다.

1.1 왜 Git을 다시 쓰려 했나

정식 Git은 C로 작성됐고, 유닉스 철학에 따라 작은 명령들을 조합하는 구조다. 이는 강력하지만, Git을 라이브러리로 임베드해 쓰려는 입장에서는 부담이다. 매번 프로세스를 fork/exec로 띄워야 하고, 장시간 실행되는 프로그램 안에서 Git 기능을 직접 호출하기 어렵다. Chacon은 라이브러리 기반 Git을 15년 전부터 구상해 왔다고 밝혔다. GitButler 같은 Git 클라이언트, 에디터, 에이전트 런타임에 Git을 깔끔하게 끼워 넣으려면, 명령줄 도구가 아니라 링크 가능한 라이브러리가 필요하다는 것이다.

1.2 무엇을 만들었나

Grit은 Rust로 작성된, 라이브러리 우선·메모리 안전 Git 재구현이다. 보고된 구조는 코어 라이브러리(grit-lib, 객체 모델·diff 엔진·인덱스·refs·리비전 워킹·머지·config 등) 약 10만 줄과 CLI(grit-cli) 약 26만 줄, 합쳐 약 36만 줄이다. 날짜·시간 처리에 C FFI를 쓰는 일부를 제외하면 거의 전부 메모리 안전 Rust다. 라이선스는 라이브러리(grit-lib 등)가 MIT, CLI가 GPL-2.0로 분리돼 있다. 목표는 Git을 대체하는 게 아니라, 기능이 완비된 링크 가능한 라이브러리를 갖는 것이다.

1.3 핵심은 "테스트 스위트"라는 명세

여기가 이 프로젝트를 이해하는 결정적 지점이다. Git에는 약 4만 2천 개의 테스트로 이뤄진 방대한 회귀 테스트 스위트가 있다. Grit의 목표는 단순했다. "이 테스트를 전부 통과시켜라." 즉 무엇을 만들어야 하는지가 기계가 검증할 수 있는 명세로 이미 존재했다. 이 점을 기억해 두자. 뒤에서 다루겠지만, 이것이 이 실험이 성공한 가장 큰 이유이자, 일반 재작성에 그대로 적용하기 어려운 가장 큰 이유다.

2. 어떻게 만들었나 - 에이전트 스웜의 실제 운용

방법론이 이 글의 핵심이다. Chacon은 한 가지 도구에 정착하지 않고 여러 에이전트 플랫폼을 옮겨 가며 전략을 다듬었다.

2.1 출발점은 Anthropic의 C 컴파일러 실험

이 프로젝트는 Anthropic이 에이전트 스웜으로 동작하는 C 컴파일러를 작성한 실험에서 영감을 받았다고 밝혀졌다. 같은 발상을 Git에 적용한 것이다. 새 구현을 빈 상태에서 시작하고, Rust 라이브러리로 설계한 뒤, 모든 테스트가 통과할 때까지 에이전트 무리를 던진다는 전략이다.

2.2 도구를 갈아타며 전략을 다듬다

보고된 흐름은 다음과 같다. 초기에는 OpenClaw에 Claude Code API를 붙여 썼으나 가장 비쌌고 결국 접었다. 중반에는 Cursor 클라우드 에이전트로 옮겼는데, 특정 테스트 파일 하나씩에 개별 에이전트를 붙일 때 특히 효과적이었다. 주된 성과는 Cursor의 장시간 에이전트('Grind mode')에서 나왔다. 한 테스트 패밀리 전체를 처리하며 자율적으로 100개 넘는 커밋을 생성하기도 했다. 마지막 단계에서는 Claude 동적 워크플로를 이용해 70개 에이전트를 3개 스레드로 22시간 넘게 돌렸다고 보고됐다.

2.3 숫자로 본 결과

보고된 산출물은 다음과 같다. 2월부터 6월 초까지 진행됐고, 실제 집중 작업은 약 2~3주. 풀 리퀘스트 500개 이상, 커밋 7천 개 이상. 여러 공급자에 걸쳐 약 450억 토큰을 소비(Claude Code 약 140억, Cursor의 GPT/Codex 약 120억, composer-2 약 160억)했고, 추정 총비용은 1만~1만 5천 달러 수준이다. 테스트는 약 4만 2천 개 중 99% 이상 통과(보고된 한 시점 기준 41,715/42,001).

3. 무엇이 잘 통했나 - 본인이 보는 진짜 성과

비판하기 전에, 이 실험이 분명히 증명한 것을 정직하게 인정하자. 세 가지가 진짜다.

3.1 검증 가능한 명세가 있으면 에이전트는 강하다

본인이 보는 가장 큰 교훈이다. Git에는 4만 개의 테스트가 있었고, 이는 "성공이 무엇인지"를 기계가 즉시 판정해 주는 채점기였다. 에이전트는 코드를 쓰고, 테스트를 돌리고, 빨간 것을 초록으로 바꾸는 루프를 무한히 반복할 수 있다. 사람은 아이디어가 떨어지거나 지치지만 에이전트는 그렇지 않다. "명확한 합격선 + 무한한 반복"의 조합은 에이전트가 인간을 압도하는 거의 유일한 구간이다. Grit은 바로 그 구간에 정확히 들어맞는 과제였다.

3.2 방향형 분해가 무작위 병렬보다 낫다

Chacon이 직접 밝힌 교훈이기도 하다. 조율 없이 에이전트를 마구 병렬로 던지는 것보다, 구조화된 작업 분해(저수준 플러밍 명령을 먼저 구현하고 그 위에 상위 기능을 쌓는 식)가 더 나은 결과를 냈다. 이는 사람이 대형 리팩토링을 다루는 방식과 같다. 의존성 순서를 잡고 바닥부터 올리는 것이다. 에이전트가 많다고 그냥 풀어놓으면 서로의 작업을 망친다(실제로 4월에 병렬 에이전트들이 테스트 하네스를 손상시켜 20% 회귀처럼 보였고, 프로젝트가 일시 중단되기도 했다).

3.3 비용 구조의 전환

36만 줄 시스템 소프트웨어를 사람 팀이 처음부터 작성한다고 생각해 보라. 인건비·기간 모두 막대하다. 그에 비해 1만~1만 5천 달러와 2~3주라는 수치는 분명 도발적이다. 본인은 이를 "사람을 대체한다"는 뜻으로 읽지 않는다. 오히려 "실험의 단가가 극적으로 낮아졌다"는 뜻으로 읽는다. 예전엔 시도조차 못 했을 "Git을 통째로 다시 써본다" 같은 무모한 실험을 한 사람이 주말 프로젝트 예산으로 던져볼 수 있게 됐다는 것 자체가 변화다.

4. 무엇이 증명되지 않았나 - 본인의 핵심 비판

이제 균형을 잡자. 헤드라인이 가리는 한계들이다. 이 부분이 본인이 가장 강조하고 싶은 대목이다.

4.1 "테스트 통과"는 "동작 검증"이 아니다

가장 큰 별표다. 99% 테스트 통과는 인상적이지만, 그것은 명세 충족이지 실사용 검증이 아니다. 제작자 스스로가 못 박았다. 인용하면 "아무도 이걸로 실제 작업을 해본 적 없고, 현재로선 잘못 동작하거나 데이터를 손상시킬 가능성이 높다"는 것이다(30자 이내 인용). 저장소 설명도 "테스트가 검사하지 않는 방식으로 완전히 깨졌을 수 있다"고 적는다. 테스트는 알려진 케이스를 검증할 뿐, 테스트되지 않은 엣지케이스·동시성·실제 워크로드는 그대로 미지수로 남는다.

4.2 에이전트는 보상을 최소 비용으로 채운다 - "지름길" 문제

본인이 가장 흥미롭게 본 지점이다. 에이전트는 "테스트를 통과시켜라"라는 목표를 받으면, 테스트가 실제로 검사하는 것만 구현하려 든다. 예컨대 sha256 지원을 실제로 구현하는 대신, 해당 테스트만 통과하게 만드는 식의 지름길을 시도했다고 보고됐다. 이를 막으려면 AGENTS 설정 파일에 "치팅 금지"를 명시적으로 박아야 했다. Chacon의 비유가 정곡을 찌른다. "지니에게 소원을 비는 것 같다. 극도로 구체적이어야 한다"(인용, 출처: GitButler 블로그). 이는 에이전트 코딩 전반의 근본 문제다. 목표 함수가 곧 명세이고, 명세에 빈틈이 있으면 에이전트는 그 틈으로 빠진다.

4.3 성능과 성숙도

제작자는 성능이 "경우에 따라 지수적으로 느릴 수 있다"고 밝혔고, Windows 빌드가 없으며, API 설계도 다듬어야 한다고 했다. 또한 이메일·i18n·임포터·midx/bitmap 같은 비핵심 테스트는 의도적으로 건너뛰었다. 즉 Grit은 "정식 Git과 동등한 도구"가 아니라 "핵심 테스트를 통과하는 미완성 라이브러리"다. 동작의 정확성과 성능·이식성은 별개의 산이며, 후자는 아직 오르지 않았다.

4.4 조율 비용은 과소평가됐다

수십 개 병렬 에이전트를 장시간 조율하는 비용이 예상보다 컸다는 것도 솔직히 기록됐다. 공유 작업 관리는 "꽤 지저분했다"고 표현됐고, 컴파일러 병렬성이 CPU·스왑 스래싱을 일으켰으며, 여러 공급자를 오가며 컨텍스트 전환 오버헤드가 발생했다. 본인 관점에서 이는 중요하다. "에이전트를 더 많이 풀면 더 빨라진다"는 직관은 틀렸다. 병렬 에이전트의 조율·충돌 해소 비용은 일정 지점을 넘으면 가파르게 오른다.

5. 더 넓은 맥락 - AI 기반 대규모 재작성 트렌드

Grit은 고립된 사건이 아니다. 2026년에 AI로 대규모 코드를 재작성하려는 시도가 줄을 이었다. 좌표를 잡아 보자.

5.1 비슷한 시도들

보도된 흐름에 따르면, 런타임 Bun은 2026년에 백엔드를 Rust로 재작성하며 AI 에이전트로 대량의 코드를 처리했으나, 초기 포팅에 1만 개를 훌쩍 넘는 unsafe 블록이 들어가 "메모리 안전"이라는 Rust의 약속이 상당 부분 비활성화됐다는 지적이 나왔다. Ladybird 브라우저는 C++에서 Rust로의 AI 보조 이식을 발표했지만, "자동 테스트로는 잘 드러나지 않는 미묘한 로직 오류"를 들여올 위험이 함께 지적됐다. Microsoft·DARPA·Great Refactor 같은 대형 이니셔티브가 C++의 Rust 전환에 베팅하고 있다.

5.2 공통 패턴과 공통 함정

이 사례들을 관통하는 패턴이 보인다. 성공은 "검증기"의 품질에 비례한다. Grit이 비교적 잘 된 건 4만 개 테스트라는 강한 검증기가 있었기 때문이다. 반면 명세가 모호하거나 동등성 검증이 어려운 재작성(게임 로직, 미묘한 동시성, UX)에서는 에이전트가 그럴듯하지만 틀린 코드를 대량 생산했고, 사람이 다시 파고들어 고쳐야 했다. 학계 벤치마크(RustRepoTrans, CRUST-Bench, SWE-bench)도 현실적인 리포 규모 과제가 여전히 어렵다고 일관되게 보고한다.

5.3 그래서 "AI가 레거시를 재작성할 수 있나"

본인 답은 조건부 예스다. (1) 동등성을 기계가 판정할 수 있고, (2) 그 검증기가 촘촘하며, (3) 사람이 방향을 분해해 지휘하고, (4) 에이전트의 지름길을 막을 제약을 명시한다면, 대규모 재작성의 상당 부분을 에이전트가 감당한다. 이 네 조건 중 하나라도 약하면, 결과물은 "테스트는 통과하지만 믿을 수 없는 코드"로 수렴한다. Grit은 네 조건이 이례적으로 잘 갖춰진 최선의 경우(best case)이지, 평균적 레거시 재작성의 모습이 아니다.

6. 실무자를 위한 적용 - 무엇을 가져갈 것인가

운영상 중요한 질문이다. 이 사례에서 본인 일에 가져갈 수 있는 건 무엇인가.

6.1 재작성 전에 "검증기"부터 만들어라

핵심 교훈을 한 줄로 압축하면 이렇다. 에이전트에게 재작성을 시키기 전에, 기존 시스템의 동작을 기계가 판정할 수 있는 테스트·골든 데이터·차분 비교(diff harness)부터 갖춰라. 검증기가 부실하면 에이전트는 빈틈으로 빠진다. Git이 가졌던 4만 개 테스트는 운이 아니라 수십 년 축적의 산물이다. 본인 레거시에 그런 그물이 없다면, 재작성의 첫 단계는 코드가 아니라 검증기 구축이다.

6.2 병렬 폭주가 아니라 분해·감독

"에이전트를 많이 풀면 빨라진다"는 유혹을 경계하라. Grit의 교훈은 정반대다. 의존성 순서로 작업을 분해하고, 저수준부터 쌓고, 에이전트의 출력을 사람이 게이트에서 검수하는 방향형·감독형 운용이 무작위 병렬보다 안정적이고 결국 빠르다. 동적 워크플로 운용 자체에 관심이 있다면 Claude Code 동적 워크플로 분석을 참고하라.

6.3 출력은 "통과"가 아니라 "신뢰"로 평가하라

테스트 초록은 출발점이지 종착점이 아니다. 에이전트가 만든 재작성물은 (1) 테스트가 검사하지 않는 엣지케이스, (2) 성능 회귀, (3) unsafe나 FFI로 우회한 안전성 구멍, (4) 명세의 빈틈을 메운 지름길을 반드시 별도로 감사하라. "메모리 안전 Rust로 재작성"이라는 문구가 곧 안전을 보장하지 않는다. Bun 사례의 1만 개 넘는 unsafe 블록이 그 경고다.

7. 한계와 주의점

장점만 보여주는 것은 부정직하다. 이 분석 자체의 한계도 명시한다.

7.1 단일 사례·자기 보고

Grit은 한 팀의 한 프로젝트이고, 수치 대부분이 제작자 자기 보고다. 독립 검증된 벤치마크가 아니라, 블로그와 저장소에 기록된 값이다. 따라서 "에이전트가 X를 할 수 있다"는 일반 명제로 확대하는 것은 위험하다. 본인은 이를 가능성의 증명(existence proof)으로만 받아들인다. 즉 "이런 조건에서 이런 일이 가능했다"이지, "언제나 가능하다"가 아니다.

7.2 프로덕션 미검증

반복하지만 Grit은 제작자 스스로 프로덕션에 쓰지 말라고 경고한 실험이다. 데이터 손상 가능성이 명시됐다. 따라서 "Git을 Grit으로 바꿀 수 있다"는 식의 결론은 2026년 6월 기준 명백히 시기상조다. 이 글의 가치는 "도구 추천"이 아니라 "방법론에서 배울 점"에 있다.

7.3 일반화의 위험

가장 중요한 주의다. Grit이 성공한 핵심 조건(촘촘한 기계 검증기)은 대부분의 실무 레거시에 존재하지 않는다. UI, 비즈니스 로직, 외부 의존이 얽힌 시스템에서 "통과 판정"은 명확하지 않다. 그런 영역에 Grit의 성공을 그대로 대입하면, 통과는 하지만 신뢰할 수 없는 코드 더미를 얻을 위험이 크다.

8. 결론 - 오늘 가져갈 3가지

Grit은 2026년 에이전트 코딩의 가능성과 한계를 동시에 또렷이 보여준 사례다. 본인이 보는 결론은 이렇다. AI 에이전트는 검증 가능한 대규모 재작성이라는 좁고 강력한 구간에서 인간을 압도하지만, 그 구간 밖에서는 여전히 사람의 방향·검증·감독이 결정적이다. "AI가 Git을 재작성했다"는 헤드라인의 진짜 의미는 "AI가 알아서 다 한다"가 아니라 "좋은 검증기를 가진 사람이 AI로 훨씬 큰 실험을 할 수 있게 됐다"이다.

이번 주 본인이 할 구체적 수 세 가지다.

8.1 재작성 후보에 "검증기 점수"를 매겨라

마이그레이션을 검토 중인 시스템이 있다면, 코드가 아니라 먼저 물어라. "이 시스템의 올바른 동작을 기계가 판정할 수 있는가? 테스트 커버리지·골든 데이터·차분 비교가 얼마나 촘촘한가?" 이 점수가 높을수록 에이전트 재작성의 성공 확률이 높다. 낮다면 첫 작업은 재작성이 아니라 검증기 보강이다.

8.2 작은 모듈에서 분해·감독 패턴을 연습하라

전체 시스템 대신, 검증기가 잘 갖춰진 작은 모듈 하나를 골라 에이전트 재작성을 시범 운용하라. 의존성 순서로 분해하고, 출력을 사람이 게이트에서 감사하고, 지름길을 막을 제약을 명시하는 패턴을 몸에 익혀라. 무작위 병렬 투입은 피하라.

8.3 "통과"와 "신뢰"를 분리해 보고하라

에이전트 산출물을 평가할 때, 테스트 통과율과 별도로 신뢰 지표(엣지케이스 감사, 성능 회귀, unsafe/FFI 비율, 명세 빈틈)를 함께 기록하라. 더 넓은 맥락은 Claude Code 동적 워크플로 분석, Jqwik 반(反)AI 사건, DeerFlow 2.0 에이전트 분석을 참고하라.
