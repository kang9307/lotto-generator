Having a Backup and Being Able to Restore Are Two Different Claims - Where a Successful Backup Lies, and What Restore Verification Actually Demands

What exit code 0 covers, the isolated target and independent resources a real test needs, and whether the application actually comes up

2026-09-07 Dev & Infra

When the backup dashboard is green, most teams treat the day as done. The job exited with code 0, the file landed in storage at roughly the expected size, and the notification arrived. But that green light certifies exactly one proposition: the dump program finished its own work.

Being restorable is a different proposition entirely. There has to be an empty database ready to receive the data. A schema has to stand up inside it. Rows have to pass the constraints on their way in. Sequences, privileges and extensions have to land in the right places. Collation order has to match what the indexes assume. And at the end of all of it, the application has to come up on top. Not one link in that chain is inspected by the backup job.

The distance between those two propositions goes unmeasured until an incident forces the issue. There is only one way to measure it, which is to actually perform a restore. The catch is that the conditions under which someone can honestly say they restore tested a backup are stricter than they look. This article separates those conditions into layers.

Every flag and default value quoted here carries a version. PostgreSQL means 18 (18.6 in the documentation header) and MySQL means 8.4. Options with identical names frequently behave differently across engine families and across releases, so the safer reading is to re-check each item against the release running in your own environment. Flags written from memory are usually two generations out of date.

The trigger - how much ground verified all the way to restore actually covers

What prompted this angle was a self-hosted backup tool putting the phrase verified by an actual restore front and centre. When a claim like that shows up, there is exactly one place to look: what gets compared after the restore finishes.

The procedure documented in that project README goes like this. After every backup, or on an hourly, daily, weekly, monthly or cron-defined schedule, it spins up a database container, runs the restore inside it, checks the restored size against the backup, and produces a report listing every table with its row count. There is an option to send only failure alerts rather than the full report.

The phrase is not an exaggeration. It does not stop at a file integrity check; it genuinely runs a restore. But the point that verification reaches is the restore completed and per-table row counts were produced. Whether the application comes up on top of that is a question one layer higher, and as the rest of this article shows, there are several defects that pass a row-count comparison untouched. That layer is precisely what this article is about.

What exit code 0 observes and what it does not

A logical backup, meaning a dump, is a procedure that issues queries to the server and writes the results down as SQL statements. Using the MySQL 8.4 classification directly: a logical backup is performed with the server running, and it does not include log files, configuration files or other database-related files that are not part of databases. Nothing in the dump file records which of those things were left out.

When a backup job reports success, roughly three signals were actually observed: the process exit code, the size of the output file, and whether the transfer completed. Here is what was not observed.

  • Whether the dump contents represent a consistent state at any single point in time
  • Whether the schema and the data are matched to each other
  • Whether the target environment has the prerequisites needed to accept this dump
  • Whether the key required to open this file still exists somewhere else
  • Whether the time the restore takes falls within a range anyone can absorb

Those five share one property. None of them has a determinable value at backup time; each acquires a value only at restore time. There is no way in principle for a green light in the backup pipeline to stand in for any of them.

Six places where a successful backup lies

1. When the schema changes while the dump is running

MySQL offers --single-transaction so that InnoDB tables can be dumped online without taking table locks. The manual attaches a condition. While that dump is in progress, no other connection should use ALTER TABLE, CREATE TABLE, DROP TABLE, RENAME TABLE or TRUNCATE TABLE, because a consistent read is not isolated from those statements. If one of them lands on a table being dumped, the read can retrieve incorrect contents or fail outright.

The branch worth staring at is the opposite of failing. Retrieving incorrect contents is not a failure. The dump terminates normally, the file is syntactically valid SQL, and restoring it later raises no error. Only the contents are off. In any organization where schema migration deploys and the nightly backup window overlap, this condition is not theoretical.

PostgreSQL is in a different position. pg_dump produces consistent exports even while the database is in concurrent use, and in the wording of the documentation the dump represents a snapshot of the database at the time pg_dump began running. That does not mean the same class of risk is absent everywhere; it means the two families do not fail the same way, which is exactly why one company-wide procedure written for both tends to be wrong for one of them.

2. Schema only, or data only

Restore a dump taken with --schema-only and every table appears with zero rows. No error is raised. Restore one taken with --data-only into an empty target and it fails because there is nothing to receive the rows; restore it into a target that already has a schema and it partially fails on constraints and load ordering.

The PostgreSQL documentation states explicitly that large objects are considered data. They are included under --data-only and excluded under --schema-only. In shops that take the schema dump and the data dump separately and stitch them together later, any drift between the two capture times means rows that arrived in that gap exist in neither file. That omission leaves no trace whatsoever in the restore log.

3. The things that are not included by default

In mysqldump, --triggers is enabled by default, so tables come with whatever triggers they have. By contrast --routines and --events are disabled by default and must be specified explicitly. Stored procedures, stored functions and Event Scheduler events all fall on that side of the line.

The defect this default produces has an unusual shape: it does not surface during the restore at all. Every table is present and every row count matches. What is missing is the nightly aggregation event and the stored procedures, and their absence only becomes visible when their own scheduled moment arrives. This is the first instance in this article of a defect that passes a row-count comparison. It will not be the last.

4. The things that live outside the database

pg_dump dumps a single database. Cluster-wide objects such as roles and tablespaces are not included, and covering them is the job of pg_dumpall. Restore into a target where the roles do not exist and the ownership statements catch. By default pg_restore emits ALTER OWNER or SET SESSION AUTHORIZATION, and per the documentation those statements will fail unless the initial connection is made by a superuser or by the user who owns all of the objects.

Extensions behave the same way. What the dump carries is an instruction to create the extension, not the implementation of the extension. If the package is not installed on the target host, the restore stops there. Sequences sit on the quiet side instead. Their values do travel with the dump, but in workflows that load data separately the sequence comes back behind where it should be, and that fact announces itself the first time an insert collides on the primary key.

5. Encoding and collation - what does not travel with the data

A dump is created in the database encoding by default. What travels is the bytes plus a declaration of their encoding, not the target server configuration. That makes the encoding chosen when creating the destination database part of the restore, and that choice usually lives in the target provisioning script rather than in the restore script, which is how it ends up unowned.

Collation is far quieter. PostgreSQL records the provider-specific version of a collation in the system catalog when the collation object is created, then compares the recorded version against the current one every time the collation is used, warning on a mismatch. The explanation in the documentation is blunt: a change in collation definitions can lead to corrupt indexes and other problems, because the database system relies on stored objects having a certain sort order.

And this does not only happen through abnormal paths. The legitimate circumstances the documentation names are upgrading the operating system to a new major version, and using pg_upgrade to move to server binaries linked against a newer ICU. A restore target running a different distribution from the original is not an edge case in disaster recovery; it is closer to the default.

There is one more trap layered on top. The command that makes the warning go away, ALTER COLLATION ... REFRESH VERSION, updates only the recorded version in the catalog. The documentation nails this down in a single sentence: that command does not actually check whether all affected objects have been rebuilt correctly. Silencing the warning and repairing the indexes are separate acts, and the order matters, with REINDEX coming first.

6. Keys and media - the file is there but cannot be read

If the decryption key for an encrypted backup exists only on the same system as the backup source, the incident that takes out that system takes out the backup with it. This defect is absolutely invisible at backup time, because the encryption succeeds. It becomes visible in the first minute of a restore attempt, which puts it among the better failure modes, precisely because it shows up immediately.

Media corruption is the opposite. PostgreSQL carries a checksum on each data page, updated when the page is written and verified when it is read, and from 18 onward that protection is on by default. The scope, though, is stated in the documentation: only data pages are protected, and internal data structures and temporary files are not. Beyond that, this is a story about a live cluster, not about a dump file that has been sitting in object storage for six months. That side belongs to whatever integrity machinery the storage layer provides, plus a manifest covering the backup artifact itself.

The default for restore tools is to keep going

The second-to-last row of that table is the one most often missed. On the main restore paths, the default error handling is to continue rather than to stop.

The description of --exit-on-error in pg_restore states the default verbatim: the default is to continue and to display a count of errors at the end of the restoration. Displaying a count is a proposition that holds when a human is watching the screen. If a scheduler is reading only the exit status, a restore with forty errors and a restore with zero errors arrive as the same signal.

Loading a plain-text dump through psql behaves the same way. In the documented wording, by default the psql script will continue to execute after an SQL error is encountered; setting the ON_ERROR_STOP variable makes it exit with status 3 instead. And the sentence the documentation adds afterwards is the actual conclusion: either way, you will only have a partially restored database. The difference is whether you know it.

Restore pathDefault behaviour on errorHow to make it stopNature of the verdict
pg_restore with an archive formatContinues and prints an error count at the endThe exit-on-error optionAt the default, partial success reads as success
pg_restore in a single transactionEither everything commits or nothing is appliedImplies exit-on-error alreadyThe verdict becomes binary, which suits verification
psql with a plain-text dumpKeeps executing after an SQL errorSet ON_ERROR_STOP, exit status 3The same file is judged differently depending on the setting
mysql reloading a dumpThe default is not spelled out in the manual pageInferred from the existence of a continue optionNot confirmable from a documented sentence, so it is listed below

The reason a single-transaction restore fits verification is in the second row. Either everything succeeds or nothing is applied, which makes the verdict binary. The purpose of a verification restore is not to save data; it is to obtain one true or false.

There is a format trap attached as well. pg_restore cannot restore plain-text dumps; the archive has to be in the custom, directory or tar format. A shop whose verification procedure is written around pg_restore while its backups are actually taken in plain text can sit for a long time in a state where verification has never once run.

What restore verification actually demands

An isolated target with resources independent of the original

For the claim of having restore tested a backup to hold, the restore target has to be separated from the original. Separation by database name is not enough. If it shares the same server process, the same disk, the same credentials or the same network path, then that verification is leaning on the original still being alive. A procedure meant to prepare for the original disappearing cannot depend on the original and still be preparation.

The condition the PostgreSQL documentation attaches to the restore target is of the same kind. If the cluster has any local additions to template1, the dump must be restored into a truly empty database, which means creating it with template0 as the template. When the target is not clean, successes and failures mix together, and a mixed result produces no verdict at all.

This is why spinning up a fresh container for every restore has become the common shape: the initial state is always identical. That said, a container is only one axis of isolation. If that container sits on the same host, the same storage and the same cloud account as the original, isolation stops at the process boundary. How far to push resource isolation should be set by the size of the incident being prepared for, not by convenience.

What gets compared

Row counts are cheap and useful. But as shown above, several defects pass a row-count comparison: missing stored routines, missing events, a sequence left behind, and a collation ordering mismatch all do.

Checksums are one step up, with conditions attached. The MySQL CHECKSUM TABLE statement exists precisely so contents can be verified as identical before and after a backup or a rollback. The manual attaches two caveats. The value depends on the table row format, so if the row format changes the checksum changes too, and the hashing function is not guaranteed to be collision-free, so two tables that are not identical can in principle produce the same value. The manual even gives an example where the storage format for temporal types changed across a version boundary, so an upgraded table can report a different checksum.

The conclusion is clear. In a verification restore that also crosses a version boundary, a checksum mismatch is not necessarily evidence of corruption. It is a signal only when both sides run the same release. So comparison is better built in layers.

  • Layer 1, object counts — tables, indexes, sequences, extensions, routines, events, triggers. This is where whole categories dropped by a default get caught.
  • Layer 2, per-table row counts — catches partial loads and interrupted restores. Cheap enough to run on every restore.
  • Layer 3, aggregates on the core tables — sums, maximums, most recent timestamps. This is where the counts match but the contents do not.
  • Layer 4, a handful of queries the application actually issues — pick ones with joins and ordering, or index and collation problems will never show themselves.

The layering exists because the costs differ. Layers 1 and 2 are cheap enough to run on every restore; layer 4 is not. Deciding what belongs where leads directly into the automation boundary in a later section.

A file opening versus a service living

The clearest statement of this boundary comes from PostgreSQL own backup verification tool. pg_verifybackup checks the integrity of a cluster backup taken with pg_basebackup against the backup_manifest the server generated at backup time. And the documentation immediately continues: the validation performed by the tool does not and cannot include every check which will be performed by a running server when attempting to make use of the backup. Even if you use this tool, you should still perform test restores and verify that the resulting databases work as expected and appear to contain the correct data.

The same page narrows the limitation further. This level of verification is sufficient to detect obvious problems such as a missing file or one whose internal checksums do not match, but it is not extensive enough to detect every possible problem that might occur during recovery. The example given is a log record with a correct checksum that specifies a nonsensical action. Correct in form and wrong in meaning is the blind spot of any verifier.

Push one step further and even a test restore is not the last layer. Between the database coming up and the service coming up sit the schema migration version, the extensions the application expects, the privileges on the connecting account, attachments living in external storage, and sessions that only ever existed in a cache. A recovery plan that has never once passed through that layer will meet those problems for the first time in a real incident, after it has already reached that point. The idea that recoverability is a product of design rather than after-the-fact effort was worked out earlier on the device firmware side, and databases are no different.

Setting the target as a number - RPO and RTO

Without these two numbers, backup design cannot begin, because there is no basis on which to judge which interval is sufficient or what restore speed is needed. The most widely cited definitions come from NIST SP 800-34 Rev. 1.

TermDefinitionWhat it fixesIf left undefined
RPO, recovery point objectiveThe point in time to which data must be recovered after an outageThe backup interval and the write-log retention schemeInterval debates degenerate into arguments about taste
RTO, recovery time objectiveThe overall length of time an information system component can be in the recovery phase before negatively impacting the organization mission or business processesThe backup format and the shape of the restore pathA restore taking days violates no specification

If the RPO is twenty-four hours, a nightly dump suffices. If it is five minutes, dumps cannot reach it and something has to stream the write log continuously: WAL on the PostgreSQL side, the binary log on the MySQL side. Binary logging is enabled by default in MySQL 8.4, and the source of information for point-in-time recovery is the set of binary log files generated subsequent to the full backup operation. A habit of clearing the logs once the backup finishes, to reclaim disk, leaves the RPO as a number that exists only on paper. Using the binary log as a rewindable history was worked through separately in the piece on a reversible data time machine.

RTO fixes the backup format, and this is where the price of logical backups appears. The MySQL manual says of mysqldump that it is not intended as a fast or scalable solution for backing up substantial amounts of data, and adds that with large data sizes restoring can be very slow. It even gives the reason: replaying the SQL statements involves disk I/O for insertion, index creation and so on.

There is a common error here. Estimating an RTO from the size of the dump file is nearly always optimistically wrong. The time to take a dump and the time to put it back are asymmetric, and the size of that asymmetry is governed by the index layout. Restore time is knowable by measurement, not by estimation.

Finally, what happens when these two go undefined matters as much as the numbers themselves. How many hours between backups is a technical debate that never concludes. How many minutes of orders this service can afford to lose moves the question to someone who can actually answer it. These are not engineering parameters but the size of the loss the business has agreed to absorb, which is why they are not the sort of number an infrastructure engineer can set alone. That same character shows up in the guide to how small teams keep Postgres alive.

Is 3-2-1 a standard or a convention

3-2-1 is routinely called a rule or a standard: three copies, two media types, one offsite. Follow the attribution and it leads not to a standards document but to a heuristic set down by the photographer Peter Krogh in The DAM Book, published by O Reilly. It is widely cited and broadly sound, but it is not a requirement clause issued by a standards body. Convention is the more accurate word.

What the standards side actually requires has a different shape. Subcategory PR.DS-11 of the NIST Cybersecurity Framework 2.0 reads: backups of data are created, protected, maintained, and tested. Its implementation examples include the following.

  • Continuously back up critical data in near-real-time, and back up other data frequently at agreed-upon schedules
  • Test backups and restores for all types of data sources at least annually
  • Securely store some backups offline and offsite so that an incident or disaster will not damage them
  • Enforce geographic separation and geolocation restrictions for data backup storage

Read it and testing and isolation come before the number of copies. Between an organization that satisfies 3-2-1 perfectly and has never once restored, and an organization with only two copies that rehearses a restore every quarter, it is obvious which one survives a real incident. Copies are easy to count, so audits count them first; testing is hard to count, so it slides to later. That ordering is backwards.

The word offsite is also read too narrowly. What matters is not only physical distance but whether the trust boundary differs. Another region in the same cloud account is geographically distant, yet a single set of credentials can erase both. The related problem of not losing access rights when custody is handed to someone else was covered from the contractual angle in the piece on archive access and vendor lock-in.

The boundary of automation - every time versus occasionally

One criterion separates what can be automated in restore verification from what cannot: where the reference value lives.

ItemPerformed byCadenceWhere the reference value lives
Did the restore finish without errorsMachineEvery backupExit status, single-transaction verdict
Do object counts match the previous runMachineEvery backupThe last successful restore
Are per-table row counts in the expected rangeMachineEvery backupAggregates taken from the source at the same moment
Does the application start and answer a health checkMachineAt least weeklyThe health check endpoint
The trend in restore durationMachine measures, human judgesRecorded every run, reviewed quarterlyMeasurement automatic, threshold from the RTO
Full recovery drillHumanQuarterly or half-yearlyThe RTO and RPO set by the business
Currency of the runbookHumanOn every configuration changeThe gap between current config and the document
Procedure when the owner is unavailableHumanHalf-yearlyThe org chart and delegation rules
Retention aligned with regulatory requirementsHumanAnnuallyContracts and legislation

The machine-side items share the property that the reference value lives inside the data. They split into true and false without human judgement, and the split can be turned into an alert. The human-side items share the property that the reference value lives inside the organization. The fact that a recovery drill took forty minutes is neither true nor false on its own; it acquires meaning only once the business decides whether forty minutes fits inside the RTO.

The fifth row sits on the boundary. A machine can measure the trend in restore duration, but a human decides when that trend becomes dangerous. As data grows, restore time necessarily grows with it, and the day the grown number crosses the RTO arrives without any alert at all. That is why recording the restore duration on every run is cheap and worth doing, and also why it so easily becomes a pile of records nobody reads. Collected-but-unread telemetry has the same shape as the problem discussed in why gathered observability data goes unread.

Attempts to force automation onto things machines cannot judge are common too. The general criterion separating what a verifier can and cannot rule on was set out in the piece on the line a verification harness draws. The gist is identical. Machines hold the floor. Humans set the ceiling.

The cost of self-hosting - who backs up the backup tool

Running the backup tool yourself adds exactly one question. Who backs up the state of that tool.

A backup tool holds schedules, connection details, retention policies, storage credentials, encryption keys and an execution history. Lose that state and half the recovery procedure disappears even though every backup file survives. That is especially true when the mapping from file to point in time to source database, and the mapping from file to the key that opens it, existed only inside the tool.

This is where circular dependency appears. If the tool backs up its own state into its own storage, and the credentials for that storage exist only inside the tool, the whole thing traces a circle. In an incident, a circle stops entirely when any single point on it breaks. Cutting it is not exotic.

  • Export the tool configuration outside the tool in a human-readable format and keep it under configuration management. Managed as code, the same state can be reproduced on a freshly built instance.
  • Keep decryption keys in a different trust boundary from the backup artifacts. Same bucket, same account or same container means one incident takes both.
  • Write down the procedure for opening a single backup file with the tool absent, then walk through it once. Being able to restore without the web UI is what stops the tool from being a single point of failure.
  • Make the list of backups readable from outside the tool. Naming conventions on the storage side plus a manifest do that job.

None of this is an argument against self-hosting. Using a managed service does not remove the question; it relocates it to the provider, and adds a different layer of questions about contracts and access rights instead. Either way, the point at which the circle gets cut has to be something you know yourself. The structure of costs removed and costs introduced by hosting a deployment platform yourself was split the same way in the article on self-hosted deployment platforms.

Things you can check with read-only commands

Everything below is read or inspect only. Nothing here modifies or deletes a target. Hosts, accounts and schema names are placeholders, so substitute your own values.

Read the table of contents without restoring anything

# Archive table of contents. Lists what is inside without performing a restore.
pg_restore --list /PATH/TO/backup.dump

# Compare a physical backup against the manifest the server produced.
pg_verifybackup /PATH/TO/basebackup

# Read whether page checksums are enabled. Query only.
psql -h HOST -U USER -d DBNAME -c 'SHOW data_checksums'

Count what actually arrived in the restored copy

-- Tables per schema. Catches whole categories that went missing.
SELECT table_schema, count(*) AS tables
  FROM information_schema.tables
 WHERE table_schema NOT IN ('pg_catalog', 'information_schema')
 GROUP BY 1 ORDER BY 1;

-- The dump carries only the instruction to create an extension. Check it stood up here.
SELECT extname, extversion FROM pg_extension ORDER BY 1;

-- A sequence restored behind its true position collides on the next insert.
SELECT schemaname, sequencename, last_value
  FROM pg_sequences ORDER BY 1, 2;

Find objects whose collation version no longer matches

-- The query from the PostgreSQL documentation, with the comparison operator written as !=.
SELECT pg_describe_object(refclassid, refobjid, refobjsubid) AS collation_name,
       pg_describe_object(classid, objid, objsubid)          AS object_name
  FROM pg_depend d
  JOIN pg_collation c
    ON refclassid = 'pg_collation'::regclass AND refobjid = c.oid
 WHERE c.collversion != pg_collation_actual_version(c.oid)
 ORDER BY 1, 2;

Count what the MySQL defaults left behind

-- Triggers are included by default, routines and events are not. Count on both sides.
SELECT routine_type, count(*) AS n
  FROM information_schema.routines
 WHERE routine_schema = 'APPDB' GROUP BY routine_type;

SELECT count(*) AS events   FROM information_schema.events
 WHERE event_schema   = 'APPDB';
SELECT count(*) AS triggers FROM information_schema.triggers
 WHERE trigger_schema = 'APPDB';

-- A content fingerprint. Value depends on row format and release, so compare like with like.
CHECKSUM TABLE APPDB.ORDERS;

That last statement is read-only but not free. On a large table it scans the whole thing, so it is not the sort of thing to run against a production source during business hours. Running it against the restored copy is the right shape, which is exactly why an isolated target appeared as a prerequisite two sections earlier.

What could not be confirmed

  • Whether the restore verification in the tool that prompted this article compares anything beyond size and per-table row counts could not be confirmed past what the README describes. Whether it inspects constraints, indexes or routines, and whether an application-layer check can be attached, is not asserted here.
  • The GitHub description for that repository calls it a PostgreSQL tool while the README lists four engine families. Which of the two reflects the current intent could not be confirmed.
  • The default behaviour of the mysql client when it hits an SQL error while reading a script could not be pinned down. The options page documents the continue option as continue even if an SQL error occurs, but does not state the default explicitly. It can be inferred by contrast, but not confirmed from a documented sentence.
  • No standards or government document publishing 3-2-1 as a requirement was found. The commonly cited source is a book, and NIST CSF 2.0 PR.DS-11 asks for creation, protection, maintenance and testing rather than a number of copies.
  • Dump defaults for the MariaDB and MongoDB families were not used as evidence here. Only the official PostgreSQL 18 and MySQL 8.4 documentation was drawn on.
  • No general figure for restore duration can be offered. It depends on data size, hardware and index layout, so an RTO judgement is possible only from measurements taken in your own environment.
