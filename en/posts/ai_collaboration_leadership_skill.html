Delegating Work to AI

Break the handoff into five parts and it becomes obvious what to fix — goal, context, boundaries, checkpoints, undo

Aug 16, 2026 Dev & Infra

Opening: The Instructions Tripled and the Output Got Worse

You hand off the same task a second time and rewrite the brief. Everything that went wrong last time is now an explicit item, plus ten more lines of things not to do. And the result that comes back is worse than the first one. It follows the instructions, sure, but it also touched files nobody asked about, and the exact thing you flagged last time is wrong again.

Almost everyone reacts the same way here. Write the instructions more precisely. Add another rule, add another example, add emphasis. And the run after that is a little worse still.

That is the wrong direction. The problem is not the precision of your sentences, it is the structure of the handoff. Delegating work has always been five separate decisions, and when we hand work to a tool we make the first one and skip the other four entirely. Then we try to compensate for the four we skipped by doing the first one harder. That is why the brief keeps growing.

An essay published on August 15 named this feeling precisely. The author argues that working with AI is closer to leadership than to coding, and notes that a good prompt helps but a shared working context helps more. The same piece draws the boundary of the analogy just as clearly: this is a claim about working methods, not a claim that the tool is a person, and lived experience, accountability and judgment do not transfer.

This is not an essay about leadership in general. How to run a team is covered separately in the way engineering leadership rules get rewritten. Here I only look at what one person actually decides when handing one task to a tool.

1. Breaking a Handoff Into Five Parts

When you delegate to a person you settle five things. What the finished state looks like, what the background is, how far they can decide alone, when they report back, and how you fold if it goes wrong. With practice all five get handled inside a three-minute conversation, which makes it feel like a single motion. It is five different decisions.

Delegating to a tool needs the same five. What changes is where each one lives.

PartWith a personWhere it lives with a toolSymptom when skipped
GoalState the finished state and the pass criteriaCompletion conditions, artifact format, a command that judges itPlausible output you cannot actually use
ContextExplain the background, constraints and whyConvention files, reference docs, examples, prior decisionsTechnically correct, operationally wrong choices
BoundariesHow far they decide aloneEnabled tools, writable paths, actions requiring approvalSide effects that are hard to undo
CheckpointsWhen and how they report mid-wayStage splits, stop conditions, size of each delivered unitYou learn the direction was wrong only at the end
UndoThe criteria for folding and restartingBranches, snapshots, dry runs, discard rulesRepairing costs more than redoing

Read the third column again and one thing stands out. Only two of the five live inside the prompt. Goal and context are written as text, but boundaries, checkpoints and undo are not sentences at all, they are the environment. Which tools are enabled, how many chunks the work was split into, whether the working directory is clean right now.

So anyone who only touches the prompt keeps hitting the same wall. They are trying to solve five problems with an instrument that reaches three of them not at all.

2. Defining the Goal — Between Do It and Done Looks Like This

Most requests end in a verb. Clean this up, fix this, build this. That is a direction, not a goal. A goal is a finished state, and a finished state has at least three parts: the shape of the artifact, the method for judging it passed, and the things that do not need doing.

2.1 A Criterion That Exists Only in Prose Cannot Judge Anything

「Make it readable」 cannot be judged. 「Keep functions in this file under 40 lines」 can. The difference matters less for the tool's comprehension than for you, because it decides what you will look at when the result lands. A request with no pass criterion forces you to reread the whole thing from the top.

The best criterion is a command. A test command, a lint command, a file to diff against. If running something answers the question, review drops from minutes to seconds. When the artifact is a document or an analysis rather than code, no command exists, so instead write out what has to be present for it to pass.

2.2 The Do-Not-Bother List Is What Bounds the Scope

Leave this part out and scope inflates. Ask for one function to be fixed and the tests get touched, the formatting shifts, nearby comments get rewritten. None of those is a bad change on its own, but together the diff you have to review is three times bigger. And once review gets expensive the whole handoff turns into a loss.

  • Weak goal — 「clean up the login area」
  • Better goal — 「extract session validation from the auth middleware into its own function. Leave the public API signatures unchanged. Passing the existing test suite is the pass criterion. Do not touch the routing or config files」
  • The second one looks long but takes eight seconds to read, while the first one costs you a twenty-minute review
  • If the goal will not fit in three sentences, usually the goal is not complex, there are two tasks

3. Context — Shared Working Context Beats a Good Prompt

The word the original author leans on is shared. It means not what you say each time but what stays. That distinction produces the biggest practical difference of anything here. An explanation typed into a chat lives for that session; an explanation written into a file is still there next week.

3.1 Context Is Not an Unlimited Resource

This is where 「then just include everything」 breaks. Anthropic's engineering write-up on context tells you to treat it as a finite resource with diminishing marginal returns. It points at accuracy degrading as token count grows and uses the phrase attention budget, and the cause is architectural: every token attends to every other token, so length inflates those relationships quadratically.

The conclusion is simple. Irrelevant context is not neutral, it is a cost. Pasting whole file contents to a tool that can open the file itself, or transcribing general programming common sense into the brief, spends the budget and buys nothing.

3.2 What Goes In and What Comes Out

  • In — why this work is needed. Where the goal alone leaves the call ambiguous, this is the tiebreaker
  • In — what must not be touched, and the reason. Without the reason the same mistake reappears somewhere similar
  • In — approaches already tried and abandoned. Without this you walk the same dead end again
  • In — conventions of this codebase that reading the files will not reveal, like why one area deliberately breaks the pattern
  • Out — anything the tool can verify itself. File contents, directory layout, dependency versions
  • Out — rules you have confirmed are never followed. A dead rule discounts the weight of the live ones next to it
  • Out — instructions that fight each other. 「Be concise」 next to 「cover every exception」 means a different one wins each run

3.3 The Third Time You Give the Same Correction, It Is a Convention

The same document talks about the altitude of guidance. Instructions pitched as fine-grained conditionals are brittle; instructions pitched as abstract principles do not change behavior. The easiest way to find that altitude in practice is to use repetition as the signal. If you have given the same correction three times, it does not belong in a conversation, it belongs in a convention file or a checker.

Writing it down has its own limits, though. Why adding more policy does not stop the same incident recurring is laid out in the limits of policy documents as a control. The short version is that guidance and enforcement are different objects, and anything that must be enforced belongs in code that runs, not in prose.

4. Boundaries — Decide What It Must Not Do First

Two questions to answer right before handing off. What is the worst side effect this task could produce on its own? And if that happens, do I find out within minutes? If the answer to the second one is 「no idea」, fix observability before you touch permissions.

Ordering it this way makes the decision easier. Start from what you want done and the list of required permissions keeps growing; start from what must not happen and the rest settles itself. In practice that list is short. Deleting things, calls that leave the building, paths holding credentials, files that carry someone else's work in progress.

  • Gate approvals too finely and approval fatigue sets in, at which point everything gets a yes and the boundary may as well not exist
  • Put approvals only where the cost of undoing spikes. Everywhere else, after-the-fact review is enough
  • Narrowing permissions is not the same as narrowing capability. Read wide, write narrow is the default shape
  • Running several tasks at once means checking whether the boundaries overlap first. Two agents editing one file gives you two unusable results

Grading permissions into levels and attaching sandboxes and audit logs is a design problem that needs its own space. Permission design and blast containment works the grade table out along the two axes of reversibility and blast radius. Here I only cover the decision you make in thirty seconds before handing off.

5. Same as Delegating to a Junior, and Where It Differs

The analogy is useful because the five parts genuinely do transfer. The analogy is dangerous because if you do not know exactly where it breaks you form the wrong expectations. The shared parts first, briefly.

  • Given a vague goal, both fill the blanks with their own reading. And that reading is usually not yours
  • Given no context, both produce something technically correct and situationally wrong. The code runs, it is just not how this team does it
  • Neither is fire-and-forget. You have to respond to what comes back for the next round to improve
  • The first few handoffs cost more to review than doing it yourself. That is normal. The question is what happens after that

And that last item is exactly where the two split.

AccountabilityShares responsibility for the resultCarries none. It all stays with youThe sign-off is always a human act

5.1 What It Means That Confidence Says Nothing About Competence

Reviewing a person, we use a lot of signals that are not the words. Hesitation, the number of questions, taking longer than usual. Those signals are what make 「I should look harder here」 fire automatically. With a tool that channel is missing entirely. A well-grounded sentence and a baseless one arrive in the same register.

There is an argument that this is structural rather than incidental. Research on why language models hallucinate points at training and evaluation regimes that have rewarded a plausible guess over saying I do not know. That is not a calibration measurement for any particular model, but it is reason enough to stop treating tone as a trust signal.

5.2 What It Means That the Review Cost Curve Is Flat

Investing time in a junior rests on 「expensive now, cheaper in three months」. That calculation is why organisations hire juniors at all. Why companies expect more from a junior than task completion is covered separately in a rereading of Kent Beck's essay.

A tool has no such calculation. Review time spent this round does not reduce the next round. Exactly one thing does: the conventions and verification machinery you build this round. So 「review is expensive now but it will get better once I am used to it」 has nothing behind it, and making review cheap has to become explicit work. Where the line between trusting and verifying falls is worked out in why the same model produces different outcomes.

Some people use a lazy senior developer model rather than a junior one. Which analogy is correct does not really matter. Either way the six axes above stay exactly where they are.

6. Symptoms of a Broken Handoff

The signal that delegation is failing shows up in the shape of your own hours before it shows up in output quality. The table below is reverse-engineered from failure modes.

SymptomUsual causeCommon wrong fixActual fix
Longer instructions, worse outputContext budget blown plus rule conflictsWrite one more ruleSplit the task and halve the brief
Review takes longer than doing itArtifact shaped badly for reviewLook at it more carefullyShrink the delivery unit, turn judgment into a command
Same correction every single timeThe correction lives somewhere volatileAdd it to the brief againPush it into convention files, linters, tests
Same request, different result each runThe goal has no pass criterionChange the model or settingsWrite the pass condition in executable form
「Almost done」 keeps repeatingNo definition of done, no stop conditionJust one more attemptSet an attempt cap and a discard rule up front
Output is right, nobody can explain whyIt ran to the end with no checkpointMerge it anywayPull checkpoints earlier and require a decision record

6.1 Why the First Symptom Is Not a Paradox

Longer instructions producing worse results looks counterintuitive but it is expected. Context is finite, as above, and there is a point where an added sentence spends more budget than it earns. A second effect compounds it: the longer the brief, the more items collide.

Put 「be concise」 and 「cover every exception exhaustively」 into the same twenty-line brief and a different one wins each run. People given that brief do the same thing. So growing a brief has to come with the habit of deleting from it. The rules that have never once been violated since you added them are the deletion candidates.

6.2 Why the Second Symptom Gets Tolerated for Months

If review time exceeds the original task time, that handoff is a loss. Arithmetic, not taste. Yet this state persists for months routinely, because perceived speed and actual speed are different things. A draft appearing in three minutes feels fast. The forty minutes that follow get filed under 「work I was doing anyway」 and never counted against the handoff. A year of watching that gap is recorded in a year with AI coding tools.

The remedy is plain. Measure the total elapsed time to merge, not to first draft. One week of that is enough to see which tasks are losses.

7. Designing Checkpoints — When to Stop and What to Look At

Checkpoints are the part of the five that goes missing most often. With people they appear on their own: someone is sitting nearby, progress is visible, they come and ask when stuck. A tool has none of that, so unless you place them deliberately, zero checkpoints exist. There is a start and an end.

7.1 Where to Cut — Three Places

  • Right before the cost of undoing spikes. Before files are actually written, before a migration runs, before any call that leaves the building
  • Where an assumption forks. The moment a requirement admits two readings. Skip this one and thirty minutes accumulate on top of the wrong branch
  • Where the artifact changes form. Design to code, code to deployment. Once the form changes, errors from the previous stage get much harder to see

7.2 What to Look At — Cheapest First

Checking usually brings to mind rereading the output from the top, but that is the most expensive check available and belongs last. Several cheaper ones exist, and most direction errors get caught by them.

The most valuable row is the first. A one-page plan takes one or two minutes to read and tells you the direction is wrong right now instead of thirty minutes from now. Better still, if a single unexpected file appears in that plan it is a signal that your brief was ambiguous, which tells you where to fix the brief as well.

7.3 How Many Checkpoints Is Right

There is no general number. There is a test, though. If you keep adding checks to buy quality, at some point it becomes more expensive than doing the work yourself. Past that line the answer is not more checks, it is that the task was never a delegation candidate.

The adjustment runs the other way too. When undo is very cheap you can afford fewer checkpoints; the two axes substitute for each other. How to raise autonomy in stages, and how being in the loop differs from being on it, is worked out in the five levels of agent autonomy.

8. Securing the Undo Path Before You Hand Off

Undo is not something you go looking for after an accident, it is something you secure before handing off. Only the order needs to change, and the reason it does not is that the moment you need it is always the moment of 「just this one quick thing」.

One thirty-second rule before execution blocks most of it. Can you say in one line how to get back to the current state? If the answer does not come out in one line, build that first and then start.

  • Cannot be undone — outbound mail, payments, notifications, external API calls. These need a compensating procedure, not a rollback
  • Cannot be undone — deleted data and schema changes already applied. These need roll-forward design rather than rollback
  • Cannot be undone — a messy working directory. This is where it breaks most often in practice
  • Why that last one is dangerous — undoing from a state that holds someone else's changes takes their work with it. It is the one case where the undo itself causes the incident
  • So the discipline is single. Start from a clean state. Check for leftover changes before starting and clear them first if anything is mixed in
  • Cheap undo loosens every other decision. Permissions can open wider, checkpoints can thin out, failed attempts can be discarded instead of repaired
  • The habit of repairing a failed result is the expensive one. Repair is cheaper for work a person produced; here discarding and re-running is usually cheaper

How to attach version control and auditability at the tooling layer is covered in version control built for agents. What matters here is not tooling but sequence: secure it first, or go looking once you need it.

9. The Trap of Acting Like a Manager

Accept the analogy and you start wanting to import people-management advice. There is an asymmetry here, and getting its direction wrong makes the whole analogy harmful.

Doing to a tool what you must never do to a person is fine. Discarding five results in a row and starting over, cutting the work off with no explanation, running the same task in three places and keeping only the best. All of them are insults to a person and normal operation for a tool, and the more common failure is not doing them. Sinking another forty minutes into repairing a result because you already spent twenty on it.

The reverse does not hold. A great deal of good people-management advice becomes wrong on the way across.

  • 「Delegate it, then trust them to finish」 — with a person this is about trust and growth; here it is about reversal cost. The reason to let it run to the end cannot be trust, it has to be whether you can undo it
  • 「Let them fail, that is how they learn」 — nothing is learned. The failure just stays as cost. That advice works on people because learning accumulates, and that premise is absent
  • 「Motivate them」 — there is no subject. Phrasing that stresses urgency or importance shifts the output distribution without raising capability. Adding 「this is very important」 to a brief is exactly this move
  • 「Build psychological safety」 — again no subject. What belongs in this slot is not the tool's comfort but a verification path that tells you quickly when you were wrong
  • 「Trust compounds」 — it does not. Ten good runs are not grounds for the eleventh. With a person that is a sample; here it is not a sample
  • 「Give feedback one-on-one」 — feedback left in a conversation leaves with the conversation. Feedback has to go into a file to survive
  • 「Autonomy creates ownership」 — no ownership appears, only autonomy. Autonomy is not good in itself, it only means something paired with a reversal cost

Contamination runs the other way too. Someone fluent in retry, discard and parallel execution carries that rhythm into working with people. Why the human-side principles have to stay intact is covered in the way leadership rules get rewritten. The original essay drawing the limit of the analogy up front is presumably for the same reason. The methods rhyme, but experience, accountability and judgment do not transfer.

10. What I Could Not Verify

  • The source essay is a personal observation, not an experiment. It does not state what scale of organisation or work the observation comes from
  • No public measurement of productivity differences between delegation styles was available. The symptom table and checkpoint placement here are reverse-engineered from failure modes, not measured
  • No general figure is offered for the optimal number of checkpoints, since it moves with the task, the tooling and the reversal cost
  • The claim that confidence and accuracy are unrelated rests on analysis of training and evaluation incentives, not on calibration metrics for any specific model
  • The context budget material comes from one provider's published engineering guidance. Whether it applies to the same degree across all models and tools was not verified

Conclusion: Move the Checkpoints Before You Add Instructions

Reaching for the brief when results are bad is natural. It is visible, it is fixable right now, and editing it feels like doing something. But only two of the five parts of a handoff live in the brief, and the failure is usually in the other three.

Change the order and most of it resolves. Secure the undo path before handing off, decide what must not happen first, and choose where to look before it runs to the end. Do that and the brief actually gets shorter, because you no longer have to restate in sentences what the environment already handles.

If you change one thing tomorrow, make it this. Next time you hand something off, get a one-page plan before execution. Files to touch, order, assumptions — three lines is enough. It costs one or two minutes, and if a single unexpected file shows up you just saved thirty. Why that file made the list also points straight at which part of your brief was ambiguous.
