황금 못과 Valen 언어의 부활 — C ABI를 건너뛰고 Rust 컴파일러와 직결한 이유

rustc 패치와 그룹 빌림으로 언어 경계를 넘는 제네릭을 시도한 6개월의 기록과 대가

2026-09-19 개발/인프라

시스템 프로그래밍 언어가 다른 언어의 라이브러리를 가져다 쓰는 방식은 수십 년간 거의 바뀌지 않았다. 가장 널리 쓰이는 표준 경계는 C ABI(응용 프로그램 이진 인터페이스)다. 어떤 언어든 C 함수 시그니처 형태로 래퍼를 깎아내고, 원시 포인터와 정수형을 주고받으며, 호출 규약(calling convention)에 맞춰 스택과 레지스터를 정돈한다. 이 방식은 운영체제와 하드웨어가 지원하는 가장 보편적인 규격이라는 장점이 있지만, 타입 시스템이 가진 모든 표현력을 가장 낮은 공통분모 수준으로 강등시키는 대가를 치른다.

Rust와의 언어 경계 문제를 다른 각도에서 다룬 적이 있다(Rust FFI 경계에서 끊기는 안전 보증 - extern fil-c 제안이 겨냥한 것 2026). 그 글은 C와의 경계(extern C, FFI)에서 컴파일러의 수명과 소유권 추적이 단절되는 현상을 짚고, C 측 런타임 자체를 안전화하여 경계의 위험을 완화하려는 시도를 분석했다. 그러나 이번에 다루는 사례는 출발점과 도달 목표가 완전히 다르다. 기존 언어와의 안전한 바인딩 계층을 만드는 수준을 넘어, 완전히 새로운 언어가 다른 성숙한 언어의 컴파일러 심장부를 직접 패치해 양방향 제네릭과 안전성을 유지하려는 시도다.

개발자 Evan Ovadia는 자신의 이전 언어 프로젝트인 Vale의 설계 자산을 바탕으로, Rust와의 완전한 상호운용을 지향하는 새 시스템 프로그래밍 언어 Valen의 실증 결과를 공개했다. 그가 제시한 기술적 경로는 일반적인 FFI 래퍼 작성이 아니라, rustc_driver를 내장하고 Rust 컴파일러에 약 100줄의 패치를 적용하여 두 언어의 컴파일러가 제네릭 인스턴스화 과정에서 직접 대화하도록 만든 구조다. C ABI라는 안전하고 관례적인 다리를 놓지 않고, 왜 컴파일러 내부를 직접 건드리는 위험한 침습적 방식을 선택했는지, 그리고 그 선택이 어떤 구조적 대가를 요구하는지 살펴본다.

1. 서론: C ABI라는 관례적 우회로를 거부한 이유

새로운 프로그래밍 언어가 시장에 진입할 때 마주치는 가장 거대한 장벽은 문법의 우수성이나 컴파일러의 성능이 아니라 기존 생태계의 부재다. 아무리 정교한 타입 시스템과 안전성을 갖추었더라도, 실무에서 필수적인 그래픽 렌더링, 네트워크 통신, 파일시스템 제어, 수학 연산 라이브러리를 처음부터 밑바닥까지 새로 구현하는 것은 불가능에 가깝다. 대다수의 신생 언어는 이 문제를 해결하기 위해 C 언어와의 호환성(C FFI)을 먼저 구현하고, 기존 C/C++ 라이브러리를 호출하는 래퍼를 씌우는 경로를 밟는다.

그러나 C ABI를 가교로 삼는 순간, 현대적인 고급 타입 시스템이 공들여 구축해 둔 추상화는 경계면에서 전부 분해된다. C 언어의 호출 규약은 제네릭 타입을 이해하지 못하며, 소유권 이전 규칙이나 수명(lifetime) 제약도 알지 못한다. Rust로 작성된 고성능 그래픽 라이브러리나 병렬 처리 프레임워크가 존재하더라도, 이를 C ABI로 노출하면 복잡한 구조체는 void*로 뭉개지고, 제네릭 컨테이너는 구체적인 타입마다 수동으로 단형화 함수를 선언해야 하며, 컴파일러가 보장하던 메모리 안전성은 프로그래머의 주의력에 전적으로 의존하는 수동 계약으로 전락한다.

전통적인 C FFI 경계면에서 필연적으로 발생하는 네 가지 핵심 정보 손실은 다음과 같은 구조적 제약을 낳는다.

  • 제네릭 메타데이터의 소실: C ABI에는 템플릿이나 제네릭 타입 파라미터를 동적으로 해석하는 규약이 없으므로 언어 경계를 넘나드는 제네릭 타입 확장이 불가능하다.
  • 수명 및 소유권 보증의 단절: 호출자 언어와 수신자 언어가 각자 엄격한 수명 검사기를 갖추고 있더라도, C 경계를 통과하는 순간 원시 포인터로 환원되어 양쪽 검사기의 추적 범위에서 벗어난다.
  • 트레잇 및 가상 메서드 테이블의 불일치: Rust의 Fat Pointer(데이터 포인터와 vtable 포인터의 쌍) 구조는 C 언어의 단일 포인터 규약과 호환되지 않아 정교한 래핑 오버헤드를 유발한다.
  • 단형화 인스턴스화의 분리: 호출 측에서 전달한 임의의 타입에 맞춰 상대 언어의 컴파일러가 해당 코드를 즉석에서 생성하는 협동 인스턴스화가 원천적으로 차단된다.

Valen의 설계자 Evan Ovadia는 신생 언어가 성숙한 Rust 생태계의 풍부한 인프라(특히 고성능 그래픽스 스택)를 실질적으로 활용하기 위해서는, C ABI라는 좁은 문을 우회하는 우회로가 아니라 컴파일러와 컴파일러가 직접 소통하는 침습적 직결 통로가 필수적이라는 결론에 도달했다. 이는 타입 시스템의 언어 경계를 허물기 위해 컴파일 파이프라인의 가장 깊은 지점을 직접 연결하는 극단적인 엔지니어링 선택이었다.

2. 황금 못의 비유: 완전히 다른 두 컴파일러를 직접 잇는 도전

1869년 5월 10일, 미국 유타주 프로몬토리 서밋(Promontory Summit)에서는 대륙 동부에서 뻗어 나온 철도망과 서부 태평양 연안에서 출발한 철도망이 하나로 만나는 역사적인 완공식이 열렸다. 수천 킬로미터의 험준한 산악 지형과 사막을 뚫고 마침내 두 철로가 맞닿았을 때, 사람들은 그 마지막 연결 지점에 17.6캐럿의 기념 황금 못(Golden Spike)을 박아 넣어 대륙횡단철도의 완성을 선언했다.

Evan Ovadia는 자신의 블로그 글에서 이 역사적 사건을 직접 인용하며 다음과 같이 회고했다. 「내게 'golden spike'라는 문구는, 멀리 떨어진 두 개의 별개 시스템을 잇는 극도로 어려운 작업을 의미한다」. 컴파일러 엔지니어링의 세계에서 서로 다른 두 언어의 컴파일러는 물리적인 지리적 거리 이상으로 아득하게 멀리 떨어져 있다. 각 컴파일러는 자신만의 고유한 구문 트리(AST), 중간 표현(IR), 타입 추론 엔진, 심볼 테이블, 최적화 패스, 그리고 코드 생성 백엔드를 구축하고 있어, 다른 컴파일러의 내부 상태를 들여다보거나 간섭하는 것이 통상적으로 허용되지 않는다.

두 개의 독립적인 컴파일러를 컴파일 타임에 직접 결합하고자 할 때 마주하는 아키텍처적 간극은 다음 네 가지로 요약된다.

  • 타입 시스템 표현의 이질성: 두 언어가 채택한 타입 검사 알고리즘과 내부 심볼 구조체가 전혀 다른 메모리 레이아웃을 가진다.
  • 컴파일 단계와 수명의 불일치: 파싱, 타입 검사, 단형화, 코드 생성으로 이어지는 파이프라인의 진행 속도와 단계별 중간 데이터의 생존 주기가 서로 다르다.
  • 빌드 오케스트레이션의 복잡도: 하나의 소스 코드를 해석하기 위해 두 개의 서로 다른 컴파일러 드라이버가 락-스텝(lock-step) 방식으로 동기화되어 상호 질의를 주고받아야 한다.
  • 내부 API의 비안정성: 외부에 공식적으로 노출된 안정적 인터페이스가 전무하여, 내부 컴파일러의 비공개 함수와 자료구조를 직접 호출해야 하는 유지보수 리스크가 발생한다.

Valen 프로젝트가 정의한 황금 못의 목표는 단순한 바이너리 링크가 아니었다. Valen 소스 코드에서 Rust 라이브러리의 구조체와 함수를 마치 자기 언어의 것인 양 자연스럽게 참조하고, Valen의 고유 타입을 Rust의 제네릭 파라미터로 넘겼을 때, 양측 컴파일러가 이를 인지하고 적절한 기계어를 함께 만들어내는 완전한 단일 파이프라인의 결속을 의미했다.

3. Vale에서 Valen으로: 메모리 안전 기법의 진화와 그룹 빌림

Valen이라는 언어의 정체성을 이해하기 위해서는 Evan Ovadia의 이전 프로젝트인 Vale를 살펴볼 필요가 있다. Vale는 가비지 컬렉터(GC)를 사용하지 않으면서도 C++처럼 댕글링 포인터나 Use-After-Free 취약점을 일으키지 않는 고성능 시스템 언어를 표방했다. 당시 Vale가 내세운 핵심 무기는 세대별 참조(generational references)와 영역 빌림(region borrowing)의 결합이었다.

3.1 Vale의 접근법: 세대별 참조와 영역 빌림

Vale의 세대별 참조는 힙 할당 시 메모리 청크에 세대 번호(generation number)를 부여하고, 그 객체를 가리키는 포인터에도 동일한 세대 번호를 저장하는 방식이다. 객체가 해제되면 힙 슬롯의 세대 번호가 증가하므로, 기존 포인터가 접근을 시도할 때 세대 번호가 불일치함을 감지하여 즉시 안전하게 오류를 포착한다. 이는 가비지 컬렉터의 멈춤 현상(Stop-The-World) 없이 결정론적인 메모리 해제를 제공하지만, 포인터를 역참조할 때마다 세대 번호를 비교해야 하는 런타임 오버헤드가 일부 존재한다.

이를 보완하기 위해 Vale는 영역 빌림(region borrowing) 기법을 병행했다. 특정 함수나 코드 블록 내에서 객체가 해제되지 않는다는 것이 보장되는 안전한 영역(region)을 컴파일러가 인식하면, 그 영역 안에서는 세대 번호 검사를 생략하고 네이티브 포인터와 동일한 속도로 역참조를 수행하도록 최적화하는 구조였다. 하지만 이 조합은 런타임 메타데이터 관리와 컴파일 타임 분석이 복합적으로 얽혀 있어, Rust처럼 순수하게 컴파일 타임에 모든 소유권과 빌림을 증명하는 시스템 언어와 1:1로 매끄럽게 맞물리기에는 구조적 이질감이 컸다.

3.2 Valen의 선택: 순수 컴파일 타임의 그룹 빌림

새 언어 Valen에서 Evan Ovadia는 세대별 참조와 런타임 세대 검사를 과감히 내려놓았다. 대신 연구자 Nick Smith의 제안에 기반한 그룹 빌림(group borrowing) 기법을 채택하여, 100% 순수 컴파일 타임 메모리 안전성을 달성하는 방향으로 뱃머리를 돌렸다.

그룹 빌림은 개별 포인터나 참조마다 수명 매개변수를 엄격하게 붙여 전파하는 기존 Rust 방식의 인지적 복잡성을 완화하면서도, 컴파일 타임에 데이터 레이스를 차단하고 유효성을 검증하는 혁신적인 빌림 모델이다. 객체들을 논리적인 그룹으로 묶어 관리하고, 특정 그룹에 속한 메모리에 대한 배타적 접근과 공유 접근의 경계를 컴파일러가 정적으로 분석한다. 이를 통해 런타임 세대 번호 검사 비용을 0으로 만들면서, Rust의 소유권 모델과 본질적으로 호환 가능한 컴파일 타임 안전 보증을 확보할 수 있게 되었다.

Rust 생태계 상호운용성 C ABI를 경유한 제한적 바인딩에 국한 컴파일러 직접 결합을 통한 네이티브 수준 상호운용 및 제네릭 공유

그룹 빌림이 해결하고자 하는 컴파일 타임 안전성의 핵심 요건은 다음과 같은 엔지니어링 목표에 집중된다.

  • 런타임 페널티 없는 결정론적 메모리 관리: 추가적인 메모리 할당 헤더나 역참조 분기문 없이 기계어 수준의 최대 실행 효율을 유지한다.
  • Rust 타입 시스템과의 의미론적 정합: Rust의 & 및 &mut 참조 규칙과 정적 개념이 자연스럽게 대응되도록 설계한다.
  • 코드 복잡도의 완화: 함수 시그니처 전반에 복잡한 수명 주석을 수동으로 달아야 하는 개발자의 부담을 컴파일러의 그룹 추론으로 흡수한다.
  • 언어 경계면에서의 일관된 안전성: Valen과 Rust 간에 객체가 오갈 때 어느 한쪽의 안전 불변식이 훼손되지 않도록 보장한다.

4. 기술적 구현: rustc를 라이브러리로 호출하고 컴파일러를 패치하다

Valen과 Rust를 하나의 실행 흐름 안에서 묶기 위해 선택된 아키텍처는 통상적인 독립 실행형 바이너리 호출이 아니다. 일반적인 빌드 시스템에서는 cargo나 rustc 바이너리를 하위 프로세스로 실행하고 그 산출물(오브젝트 파일이나 정적 라이브러리)을 링커로 합치는 방식을 쓴다. 그러나 이런 프로세스 분리 모델에서는 상대방 컴파일러의 내부 AST나 타입 심볼 테이블에 실시간으로 접근할 수 없다.

4.1 rustc_driver와 run_compiler를 통한 컴파일러 내장

Evan Ovadia는 Rust 컴파일러의 핵심 진입점 패키지인 rustc_driver를 Valen 컴파일러(valenc) 내부로 직접 링크하여 가져왔다. Rust 컴파일러는 독립 실행 파일 형태로도 제공되지만, 내부적으로는 rustc_driver::run_compiler 함수를 노출하여 다른 Rust 프로그램 안에서 라이브러리 형태로 구동될 수 있는 구조를 갖추고 있다.

Valen 컴파일러는 run_compiler 함수를 호출하면서 Rust 컴파일러에 전달할 컴파일러 인자(rustc_args)와 함께, 컴파일러의 생명주기 곳곳을 가로챌 수 있는 콜백 객체(Callbacks 트레잇 구현체)를 주입했다. 이를 통해 외부 Rust 크레이트의 메타데이터를 메모리로 로드하고, Rust 컴파일러가 파싱과 매크로 확장 및 타입 검사를 마친 뒤의 중간 상태를 Valen의 타입 검사기가 직접 질의할 수 있는 통로를 열었다.

4.2 100줄 패치와 MIR 우회 LLVM 백엔드 파이프라인

그러나 표준 rustc_driver가 제공하는 콜백만으로는 Valen의 타입이 주입된 Rust 제네릭 함수를 동적으로 컴파일하도록 유도하기에 역부족이었다. Rust 컴파일러는 자신이 알지 못하는 외부 언어의 AST를 스스로 처리하도록 설계되지 않았기 때문이다. 여기서 Evan Ovadia는 Rust 컴파일러 소스 코드 자체에 약 100줄에 달하는 정밀한 패치를 적용했다.

이 패치의 목적은 Rust 컴파일러의 단형화(monomorphization) 및 LLVM IR 로워링 단계에 특수한 콜백 훅(hook)을 추가하는 것이다. Rust 컴파일러가 특정 제네릭 함수를 구체적인 기계어로 인스턴스화하려 할 때, 파라미터로 주어진 타입이 Valen에서 정의된 타입이라면 Valen 컴파일러에 신호를 보내 해당 타입의 레이아웃과 접근 규약을 협상하도록 만든 것이다.

또한 이 아키텍처는 Rust의 중간 표현인 MIR(Mid-level Intermediate Representation)을 거치지 않는 설계를 택했다. Valen 코드를 굳이 불완전하게 Rust MIR로 변환하여 Rust의 복잡한 대여 검사기(Borrow Checker)를 속이려 드는 대신, Rust 컴파일러가 생성한 LLVM 모듈과 Valen 자체 LLVM 백엔드가 생성한 LLVM 모듈을 LLVM IR 수준에서 직접 병합하고 최적화하는 백엔드 파이프라인을 구축했다.

이 패치와 컴파일 단계 결합 구조가 갖는 기술적 특징은 다음과 같이 정리할 수 있다.

  • 단형화 단계의 콜백 주입: 제네릭 파라미터가 치환되는 순간 Rust 컴파일러가 Valen의 타입 시스템에 질의를 던져 상호 인스턴스화를 완결한다.
  • MIR 우회를 통한 복잡성 차단: 불안정하고 변경 폭이 큰 Rust MIR 변환 계층을 건너뛰고 LLVM IR 수준에서 기계어를 통합한다.
  • 자체 LLVM 백엔드와의 직접 통합: Valen이 소유한 LLVM 코드 생성기가 Rust의 LLVM 모듈과 동일한 컨텍스트 안에서 인라인 최적화를 수행한다.
  • 단 100줄의 최소 침습 패치: Rust 컴파일러의 근본적인 아키텍처를 뒤흔들지 않고, 필요한 연결 고리만을 외과수술처럼 정확하게 도려내어 콜백을 심었다.

5. 언어 경계를 넘는 제네릭: C 바인딩 대비 얻은 것과 치른 대가

Valen이 감행한 컴파일러 내부 패치는 단순한 실험적 호기심의 산물이 아니었다. 그것은 C 바인딩으로는 절대로 불가능한 언어 경계를 넘는 제네릭(Cross-Language Generics)을 달성하기 위해 반드시 지불해야만 했던 필연적 대가였다.

5.1 제네릭 단형화와 타입 정보의 보존

C++이나 Rust 같은 현대 시스템 언어에서 제네릭의 본질은 단형화(Monomorphization)다. Vec<T>라는 제네릭 컨테이너가 있을 때, T가 i32인지, MyStruct인지에 따라 컴파일러는 완전히 다른 메모리 레이아웃과 인라인 기계어 코드를 생성한다. 이는 런타임 타입 분기나 힙 박싱 오버헤드를 없애고 극한의 실행 속도를 보장하는 핵심 원리다.

만약 Valen 프로그램에서 정의한 구조체 PlayerState를 Rust의 제네릭 컬렉션 Vec<PlayerState>에 담고 싶다면, Rust 컴파일러는 PlayerState의 정확한 크기, 정렬 바이트(alignment), 복사(copy) 및 해제(drop) 시맨틱을 알아야만 단형화 코드를 구울 수 있다. C ABI는 이러한 단형화 과정에 개입할 수 있는 메커니즘을 제공하지 않는다. Valen의 컴파일러 직결 방식만이 valenc와 rustc가 서로의 심볼을 주고받으며 양쪽의 제네릭 함수를 실시간으로 단형화하는 기적을 가능하게 만든다.

표 2: 일반적인 C ABI 연동 vs Valen의 컴파일러 내부 연동 아키텍처 비교
비교 항목 일반적인 C ABI 연동 방식 (C FFI) Valen의 컴파일러 내부 직접 연동 (rustc 패치)
연동 메커니즘 C 호환 헤더 작성 및 외장 링커를 통한 심볼 결합 rustc_driver 내장 및 컴파일러 단형화 콜백 100줄 패치
언어 간 제네릭 지원 불가능 (타입이 void*로 소실되거나 수동 단형화 함수 필요) 완전 지원 (Rust 제네릭에 Valen 타입 전달 및 상호 인스턴스화)
타입 안전성 보증 경계면에서 안전 보증 소실 (unsafe 선언 및 수동 검증 필수) 컴파일러 간 대화를 통해 타입 불변식 및 빌림 규칙 보존
유지보수 안정성 매우 높음 (표준 C ABI는 수십 년간 불변의 공개 규약) 취약함 (Rust 컴파일러 내부 버전 갱신 시 패치 재조정 위험)

5.2 컴파일러 내부 변경에 종속되는 유지보수 부담

그러나 이 뛰어난 표현력과 통합성의 이면에는 가혹한 아키텍처적 부채가 도사리고 있다. C ABI는 수십 년간 안정성이 검증된 운영체제 수준의 불변 계약이다. 반면 rustc의 내부 API는 Rust 언어 팀이 공식적으로 안정성을 보장하지 않는 내부 구현 세부사항에 불과하다.

Rust 컴파일러는 6주마다 새로운 마이너 버전을 릴리스하며, 내부의 AST 구조, 타입 컨텍스트(TyCtxt)의 수명 관리, 단형화 수집기(monomorphization collector)의 구현 세부사항은 아무런 예고 없이 완전히 뒤바뀔 수 있다. 약 100줄에 불과한 작은 패치라 할지라도, Rust 컴파일러의 코어 파이프라인이 리팩터링되는 순간 빌드가 깨지거나 침묵하는 버그를 낳을 수 있다. 이는 Valen 프로젝트가 성장하는 내내 Rust 컴파일러의 내부 변화를 추적하고 패치를 지속적으로 유지보수해야 하는 영구적인 엔지니어링 오버헤드로 작용할 수밖에 없다.

이 침습적 방식이 지불해야 하는 네 가지 주요 구조적 대가는 다음과 같다.

  • Rust 컴파일러 버전 고정 리스크: 특정 rustc 내부 커밋에 패치가 종속되어 Rust 생태계의 최신 컴파일러 기능을 즉각 따라가지 못할 가능성이 존재한다.
  • 컴파일 시간의 누적 증가: 두 개의 방대한 컴파일러 인스턴스가 메모리에 상주하며 상호 질의를 처리하므로 단일 언어 빌드 대비 컴파일 타임이 길어진다.
  • 디버깅 및 심볼 추적의 난도 상승: 오류가 발생했을 때 그것이 Valen 컴파일러의 결함인지, Rust 패치의 오작동인지, LLVM IR 생성 불일치인지 규명하기 어렵다.
  • 도구 생태계와의 격리: 일반적인 Rust 분석 도구(rust-analyzer, Clippy 등)가 패치된 내부 컴파일러 흐름을 온전히 인지하지 못할 수 있다.

6. 첫 실증의 성과: Rust wgpu 그래픽 라이브러리와 Valen 클로저의 결합

컴파일러를 패치하고 두 시스템을 결합한다는 구상이 단순한 이론적 백서에 그치지 않음을 증명하기 위해, Evan Ovadia는 극도로 까다로운 실전 시나리오를 검증 대상으로 삼았다. 바로 Rust 생태계의 대표적인 현대적 그래픽 라이브러리인 wgpu를 기반으로 한 그래픽스 렌더링 파이프라인의 구동이었다.

그래픽스 라이브러리는 언어 간 상호운용성 검증에서 가장 넘기 힘든 장벽으로 꼽힌다. 운영체제의 네이티브 창 핸들을 제어해야 하고, 비동기 이벤트 루프가 계속해서 돌아가며, GPU 명령 버퍼를 실시간으로 제출해야 하기 때문이다. 특히 이벤트 기반 그래픽 시스템에서는 운영체제나 창 관리자가 보내오는 이벤트를 처리하기 위해 콜백(callback) 함수를 Rust의 이벤트 루프에 등록하는 패턴이 필수적이다.

Evan Ovadia가 달성한 첫 성공적 실증의 핵심 구조는 다음과 같았다. Valen으로 작성된 메인 프로그램이 Rust로 작성된 wgpu 기반 그래픽 라이브러리를 호출한다. 그리고 창의 이벤트 루프가 실행될 때, Rust의 트레잇(trait)을 구현하는 Valen의 클로저(closure)를 콜백으로 Rust 이벤트 루프에 직접 전달했다. Rust의 이벤트 루프는 자신이 호출하는 콜백이 다른 언어로 작성된 것인지 의식하지 못한 채 정해진 트레잇 규약에 따라 실행했고, Valen 클로저는 매 프레임마다 GPU 렌더 패스를 지시하여 화면에 도형을 그려냈다.

렌더링 창이 뜨고 화면에 프레임이 정상적으로 출력되었을 때, 저자는 원문에서 감격스러운 한 문장을 남겼다. 「마침내, 첫 렌더링을 얻었다(At last, I got my first render)」. 이는 서로 다른 메모리 관리 모델을 가진 두 언어의 컴파일러가 단형화 단계와 LLVM 코드 생성 단계를 완벽히 공유하여 실제 작동하는 인터랙티브 GUI 프로그램을 만들어냈음을 증명한 결정적 이정표였다.

이 첫 실증이 입증해 낸 기술적 유효성의 지표는 다음과 같이 요약할 수 있다.

  • Rust 트레잇과 Valen 클로저의 무마찰 매핑: Rust가 요구하는 고차 함수 시그니처와 트레잇 객체 인터페이스를 Valen 런타임이 오차 없이 충족했다.
  • 이벤트 루프 콜백 생명주기의 안정적 유지: Rust의 수명 주기 안에서 구동되는 이벤트 루프에 Valen 클로저의 힙 참조가 메모리 오염 없이 유지되었다.
  • wgpu 하드웨어 가속 파이프라인의 정상 제어: 저수준 GPU 파이프라인 상태 객체와 버퍼 바인딩이 두 언어의 경계를 왜곡 없이 통과했다.
  • 단일 바이너리로의 완벽한 링킹: 두 컴파일러가 생성한 LLVM IR이 하나의 네이티브 실행 파일로 결합되어 충돌 없이 구동되었다.

7. 실험적 단계의 한계와 실무적 관점: 반 년의 탐색이 남긴 질문

이 성과는 분명 컴파일러 설계 분야에서 기념비적인 시도이지만, 실무 엔지니어의 관점에서는 냉정한 기술적 평가가 필요하다. 저자 스스로 명확히 밝혔듯이, 이 프로젝트는 이제 막 첫 렌더링에 도달한 극초기 실험 단계에 머물러 있다. 이론화, 설계, 해킹, 리팩터링, 그리고 재설계로 이어진 약 반 년(half a year)의 집중적인 개발 기간이 투입되었으며(주로 2026년에 집중됨), 이는 프로덕션 환경에서 사용할 수 있는 안정성을 뜻하지 않는다.

현재 상태의 Valen 컴파일러는 정상적인 경로(happy path)에 대한 개념 증명(Proof-of-Concept)을 완료한 수준이다. 실제 소프트웨어 개발에서는 수많은 예외 처리, 컴파일러 오류 메시지의 정밀한 진단, IDE 지원, 패키지 의존성 해결, 그리고 멀티스레드 동시성 모델 검증이 수반되어야 한다. 컴파일러에 100줄의 패치를 적용하여 동작시키는 것과, 수천 개의 외부 크레이트가 얽힌 대규모 프로젝트에서 충돌 없이 동작하도록 보장하는 것은 차원이 다른 문제다.

실무 엔지니어링 생태계로 진입하기 위해 Valen이 마주하고 있는 과제들은 다음과 같다.

  • 컴파일 에러 진단성(Diagnostics)의 부재: 언어 경계면에서 제네릭 타입 불일치나 소유권 위반이 일어났을 때 명확하고 친절한 에러 메시지를 제공하기 어렵다.
  • 비동기 런타임(async/await)과의 결합 미검증: wgpu의 동기식 콜백 루프 외에 Rust의 Tokio 등 복잡한 비동기 리액터와의 상호운용은 아직 검증되지 않았다.
  • 업스트림 병합 가능성의 희박함: Rust 공식 프로젝트 측에서 단일 외부 언어를 위해 rustc 코어에 이 패치를 영구적으로 수용해 줄 가능성은 현실적으로 낮다.
  • 빌드 시스템 파편화: Cargo 중심의 견고한 Rust 빌드 생태계와 Valen 고유의 빌드 툴체인을 어떻게 이질감 없이 융합할 것인가의 문제가 남아 있다.

따라서 현시점에서 Valen은 상용 프로젝트에 즉시 도입할 수 있는 도구가 아니라, 프로그래밍 언어의 상호운용성이 도달할 수 있는 새로운 아키텍처적 지평을 제시한 연구적 성과로 해석하는 것이 정확하다.

8. 시스템 언어 생태계에서의 위치와 시사점

Valen의 도전은 프로그래밍 언어 생태계 전체에 매우 의미심장한 화두를 던진다. 수십 년 동안 새로운 시스템 언어를 만들고자 했던 수많은 시도들이 C 언어의 거대한 중력에 갇혀 있었다. C ABI를 통해 연결하는 한, 새로운 언어는 C 언어가 가진 낡고 위험한 메모리 모델의 한계로부터 결코 완전히 자유로울 수 없었다.

Evan Ovadia가 보여준 접근법은, 차세대 시스템 언어가 기댈 수 있는 새로운 거인으로 Rust 컴파일러 그 자체를 상정할 수 있음을 입증했다. C 언어 대신 Rust를 기반 인프라로 삼고, 그 위에 더 진보된 타입 시스템(예: 그룹 빌림이나 선형 타입)을 얹어 생태계를 확장할 수 있다는 가능성을 구체적인 기계어 수준에서 보여준 것이다.

물론 컴파일러 내부를 직접 해킹하는 방식이 모든 언어가 따라야 할 표준적인 해법이 될 수는 없다. 하지만 컴파일러가 점차 모듈화되고 라이브러리화(Library-first compiler architecture)되는 현대의 추세 속에서, 언어 간의 경계가 바이너리 레벨이 아닌 AST와 단형화 레벨에서 만날 수 있다는 이 아이디어는 향후 언어 툴체인 설계자들에게 귀중한 참조 모델이 될 것이다. 프로그래밍 언어의 역사는 불가능해 보이던 아득한 두 세계 사이에 박아 넣은 작은 황금 못 하나로부터 새로운 대륙이 연결되는 길을 찾아왔기 때문이다.

9. 확인하지 못한 것

본 글을 작성하며 1차 출처 문서와 기술적 세부 사항을 확인하는 과정에서 아래 항목들은 원문에 명시적인 언급이나 수치가 없어 단정적으로 서술하지 않고 본 절에 남긴다.

  • Valen 언어의 향후 안정화 릴리스 시점이나 정식 배포 일정에 관한 구체적인 로드맵은 원문에 명시되어 있지 않아 확인하지 못했다.
  • Rust 컴파일러의 향후 버전 갱신에 대응하여 100줄 패치를 지속적으로 유지보수하기 위한 자동화된 테스트 파이프라인의 구체적 구성 방식은 공개된 소스 외에 상세 서술이 없어 확인하지 못했다.
  • Nick Smith의 그룹 빌림(group borrowing) 기법에 대한 형식적 수학적 증명(formal proof)이나 대규모 벤치마크 지표의 정량적 측정 결과는 원문에서 다루지 않아 확인하지 못했다.
  • Valen 컴파일러 자체의 공개 저장소 코드베이스 외에, Cargo와 같은 별도의 독립된 패키지 관리자나 서드파티 레지스트리가 함께 구축될 계획인지 여부는 원문에 언급이 없어 확인하지 못했다.
