이 글은 Tencent Zhuque Lab이 GitHub에 공개한 오픈소스 저장소(Tencent/AI-Infra-Guard)의 README, 릴리스 노트(v4.6.0~v4.6.2), 기술 문서 및 GeekNews 요약을 바탕으로 작성되었다. 공격 절차나 익스플로잇 재현 방법을 일체 다루지 않으며, 인프라 방어자가 자사 AI 환경을 점검할 때 이해해야 할 5개 진단 층위와 도구의 구조적 한계, 안전한 격리 운용 원칙만을 서술한다.

계기 — 모델 서버에서 자율 에이전트까지 아우르는 AI 보안 점검

생성형 AI가 단순한 단일 프롬프트 질의응답을 넘어 모델 서빙 인프라, MCP(Model Context Protocol) 커넥터, 자율 에이전트 스킬, 다중 에이전트 워크플로로 확장되면서 시스템이 노출하는 공격 표면도 다층화되었다. 기존의 웹 취약점 진단 도구는 추론 엔진 특유의 프로토콜이나 에이전트의 도구 오용(tool misuse), 프롬프트 탈옥(jailbreak) 위험을 온전히 포착하기 어려웠다.

2026년 가을, Tencent 산하의 보안 연구 조직인 Zhuque Lab은 이러한 다계층 AI 공격 표면을 사내에서 자체 점검할 수 있도록 설계된 오픈소스 레드팀 플랫폼 AI-Infra-Guard(A.I.G)를 공개했다. Apache-2.0 라이선스로 배포되는 이 도구는 서빙 인프라부터 에이전트 런타임까지 포괄하는 종합 진단 기능을 전면에 내세웠다.

GeekNews 등 기술 커뮤니티에서는 146개 AI 컴포넌트와 2,000개 이상의 CVE를 지원한다는 집계 수치와 에이전트 워크플로 자동 점검 기능에 주목했다. 그러나 보안 실무자 입장에서는 수치적 규모보다 각 점검 층위가 실제로 검사하는 대상이 무엇이고, 무엇을 검사하지 못하는지, 그리고 도구 자체를 안전하게 구동하기 위한 전제 조건이 무엇인지를 냉정하게 구분해야 한다.

AI-Infra-Guard의 5개 점검 층과 진단 범위

AI-Infra-Guard의 아키텍처는 AI 시스템 스택을 5개의 명확한 검사 층위로 구분하여 각각 서로 다른 검사 엔진과 입력 형식을 부여한다. 저장소 문서에 규정된 5대 기능 축은 인프라 취약점 스캔, MCP 서버 스캔, 에이전트 스킬 스캔, 에이전트 워크플로 런타임 스캔, LLM 탈옥 및 모델 변조 평가이다.

아래 표는 README 및 기술 문서에 명시된 5개 점검 층의 실제 대상과 검사 메커니즘, 그리고 탐지 한계를 비교한 것이다.

점검 층README 명시 설명실제 확인되는 것확인되지 않는 것 (한계)
1. AI 인프라 스캔실행 중인 서비스 주소 입력 기반 취약점 탐지기지의 2,000+ CVE 핑거프린트 매칭규칙에 미등록된 제로데이 및 비인가 설정
2. MCP 서버 스캔GitHub URL 또는 업로드 소스 정적 분석도구 오염, 자격 증명 유출, 명령 주입 패턴런타임 동적 입력에 의한 우회적 동작
3. 에이전트 스킬 스캔SkillTrustBench T01~T09 기반 보안 감사파이썬 바이트코드 우회, 권한 상승 패턴복합 에이전트 상호작용 중 발생하는 논리적 오류
4. 에이전트 런타임 스캔Dify·Coze 등 워크플로 다중 에이전트 평가에이전트 제어권 상실, 도구 오용, 데이터 유출모든 비정형 프롬프트 조건에 대한 안전성 보증
5. 탈옥 및 API 감사공격 프롬프트 내성 시험 및 멀티 프로브 감사벤치마크 기준 탈옥 방어율, 모델 바꿔치기 징후운영 중 발생하는 완전히 새로운 적대적 기법

표에서 확인되듯, 각 계층은 고유한 진단 방식을 취하고 있으며 어느 한 계층도 다른 계층의 안전을 보증하지 않는다. 1층의 인프라 스캔이 안전하다고 해서 2층의 MCP 도구가 안전한 것은 아니며, 모델 자체의 탈옥 내성이 높다고 해서 에이전트가 도구를 오용하지 않는 것은 아니다.

1층: 실행 중인 AI 서비스 핑거프린팅과 알려진 CVE 매칭

첫 번째 층위인 AI Infra Scan은 네트워크상에서 동작 중인 추론 서버와 워크플로 플랫폼을 대상으로 한다. 사용자가 검사 대상 IP와 포트 번호(예: Ollama의 11434, vLLM의 8000, ComfyUI의 8188 등)를 입력하면, 스캐너는 HTTP 응답 헤더와 엔드포인트 응답 형태를 분석해 소프트웨어의 종류와 버전을 식별한다.

  • 식별 대상 컴포넌트. v4.6.0 기준 vLLM, Ollama, ComfyUI, n8n, LangFlow, llama-cpp, MLflow 등 146개 이상의 주요 AI 관련 서비스 컴포넌트를 지원한다.
  • CVE 규칙 매칭. 핑거프린팅으로 특정된 버전 정보를 데이터베이스 내 2,000개 이상의 CVE 규칙과 대조하여 취약 버전 여부를 판정한다.
  • 점검 방식의 성격. 대상 서비스에 파괴적 페이로드를 직접 전송해 공격을 성사시키는 방식이 아니라, 서비스가 공개하는 식별 정보를 통한 비침투적 시그니처 대조 방식이다.
  • 운영상의 주의점. 네트워크 대역(CIDR 표기 등)을 지정해 일괄 스캔할 경우 사내 운영 중인 정상 추론 노드에 다수의 진단 트래픽이 유입될 수 있으므로 지정된 테스트 인스턴스만을 대상으로 지정해야 한다.

이 계층의 한계는 명확하다. 알려진 취약점 데이터베이스에 등록된 CVE만을 탐지할 수 있으므로, 소스 코드에서 직접 빌드한 커스텀 빌드나 공개되지 않은 설정 오류, 제로데이 취약점은 식별 정보 대조만으로 드러나지 않는다.

2·3층: MCP 서버와 Agent Skill 소스 코드 정적 분석

두 번째와 세 번째 층위는 모델이 외부 시스템과 상호작용하기 위해 장착하는 도구(Tool) 계층에 대한 검사이다. MCP(Model Context Protocol) 서버와 에이전트 스킬(Agent Skill)은 파일 시스템 접근, 쉘 명령어 실행, 외부 네트워크 통신 등 높은 권한을 부여받는 경우가 많아 최근 공급망 공격의 주요 표적으로 부상했다.

  • 입력 형태의 특성. 실행 중인 서버 주소가 아니라, GitHub 저장소 URL이나 로컬에 다운로드된 소스 코드 압축 파일을 입력값으로 받는다.
  • 정적 패턴 및 바이트코드 분석. 파이썬 소스 코드 내의 하드코딩된 API 키와 자격 증명 유출 패턴, 쉘 주입(Command Injection) 취약점, .pyc 바이트코드를 활용한 검사 우회 시도를 분석한다.
  • SkillTrustBench 분류 체계 준용. Tencent Zhuque Lab이 정의한 SkillTrustBench의 T01부터 T09까지 9개 위험 범주(도구 오염, 권한 상승, 비인가 네트워크 전송 등)에 맞춰 위험도를 등급화한다.
  • CLI 기반 파이프라인 연동. 웹 UI 외에도 독립 CLI 도구인 aig-skill-scan(PyPI 등록) 및 mcp-scan을 제공하여 소프트웨어 개발 파이프라인(CI/CD)의 커밋 단계에서 도구의 안전성을 자동 검증할 수 있도록 지원한다.

이 계층 역시 정적 분석이 가지는 본질적 한계를 공유한다. 난독화된 코드나 런타임에 동적으로 다운로드되는 2차 페이로드, 모델의 해석 방식에 따라 달라지는 프롬프트 기반 도구 유도 공격을 코드 수준에서 100% 사전에 걸러내는 것은 불가능하다.

4·5층: 에이전트 워크플로 런타임 감사와 LLM 탈옥·백도어 평가

네 번째와 다섯 번째 층위는 모델과 에이전트가 실제 사용자 입력을 받아 작업을 수행하는 동적 실행 단계의 위험을 검증한다.

  • 에이전트 런타임 제어권 상실 평가(Agent Scan). Dify나 Coze 등 워크플로 기반 에이전트 환경에서 다중 에이전트 간 업무 전달(Handoff) 시 발생하는 위험을 평가한다. Zhuque Lab의 연구 결과물인 RogueHandoff-20 및 FORGE-Bench(arXiv:2609.11024) 벤치마크를 활용해 에이전트가 정상 목표를 수행하는 과정에서 제약 조건을 어기고 비인가 도구를 호출하거나 데이터를 외부로 유출하는지를 시뮬레이션한다.
  • 탈옥 내성 평가(Jailbreak Evaluation). 대상 LLM의 API 엔드포인트를 연결하고 Many-Shot, PAIR, GOAT, ActorAttack 등 학계에 보고된 적대적 공격 데이터셋을 순차 질의하여 모델의 안전 필터가 무력화되는 비율을 산출한다.
  • API 릴레이 블랙박스 감사(Model & API Checker). 중계 서버나 서드파티 프록시를 거쳐 제공되는 LLM API에 대해 여러 차례의 핑거프린팅 프로브를 전송하여, 원래 계약된 모델(예: Gemini, GLM 등) 대신 저가형 모델로 은밀히 바꿔치기되었거나 백도어 응답 징후가 있는지를 통계적으로 대조한다.

이 동적 평가 계층은 모델의 현재 방어 수준을 가늠하는 상대적 벤치마크를 제공하지만, 점검 통과가 모든 미지의 공격에 대한 절대적 면역을 의미하지는 않는다. 에이전트의 제어권 상실 및 악용 가능성에 관한 일반적 위험 구조는 Anthropic GLM-5.3 취약점 공격 역량 분석 2026에서도 다루어진 바 있다.

아키텍처와 독립 CLI 구성 및 배포 절차

AI-Infra-Guard는 전체 기능을 통합 제공하는 웹 대시보드와 각 점검 영역별로 경량화된 독립 CLI 도구로 분리된 구조를 채택하고 있다. 사내 인프라의 여건과 자동화 수준에 따라 배포 방식을 선택할 수 있도록 설계되었다.

아래 표는 공식 README가 규정한 주요 구성 요소별 실행 형태와 입력 대상, 운영 시 유의 사항을 정리한 것이다.

기본 통합 웹 플랫폼의 구동 절차는 공식 문서에 안내된 Docker Compose 방식을 따른다.

# 공식 이미지 기반 컨테이너 구동 (README 권장 절차)
                    git clone https://github.com/Tencent/AI-Infra-Guard.git
                    cd AI-Infra-Guard
                    docker compose -f docker-compose.images.yml up -d
                    # 구동 후 http://localhost:8088 접속

컨테이너가 기동되면 로컬 8088 포트에서 웹 대시보드와 Swagger 기반 API 문서(/docs/index.html)가 활성화된다.

「자체 인증 부재」 경고와 사내 내부망 격리 원칙

AI-Infra-Guard를 도입하려는 엔지니어가 가장 먼저 숙지해야 할 보안 제약은 공식 README의 설치 안내(Other Installation Methods) 섹션에 명시된 다음 문언이다.

Note: The AI-Infra-Guard project is positioned as an AI red teaming platform for internal use by enterprises or individuals. It currently lacks an authentication mechanism and should not be deployed on public networks.

이 문서는 도구 자체가 로그인 세션, 다중 사용자 권한 분리, 접근 제어 메커니즘을 내장하고 있지 않음을 분명히 경고하고 있다. 만약 이 웹 대시보드를 공인 IP나 외부 인터넷에 그대로 노출할 경우 다음과 같은 치명적인 위험이 발생한다.

  • 스캐닝 도구의 악용. 비인가 외부 공격자가 인증 없이 대시보드에 접근하여 사내 임의 IP 대역을 향해 무차별 스캔을 유발할 수 있다.
  • 진단 결과 및 자산 정보 노출. 사내 AI 모델 서버의 버전, 포트 현황, 취약점 진단 결과 보고서가 외부에 무단 열람될 수 있다.
  • API 키 유출. 탈옥 평가 및 API 검사를 위해 관리자가 입력해 둔 고가의 상용 LLM API 키가 평문으로 탈취될 수 있다.
  • 내부망 격리 조치 필수. 따라서 이 도구는 사내 폐쇄망, VPC 내부 서브넷, 또는 VPN을 통해서만 접근 가능한 관리자 전용 호스트에서 구동되어야 하며, 외부 연동이 필요할 경우 리버스 프록시(Nginx 등) 앞단에 mTLS나 사내 SSO 인증을 필수적으로 결합해야 한다.

또한 점검 행위의 법적·윤리적 한계로서, 본 도구를 통한 취약점 스캔과 탈옥 평가는 반드시 자사가 소유하거나 서면으로 사전 허가를 득한 인프라와 모델에 한해서만 수행되어야 한다. 인가받지 않은 외부 대상에 대한 진단 패킷 송출은 관할 법률상 사이버 침해 시도로 간주될 수 있다.

블루팀 관점에서 본 점검 도구의 효용과 맹점

방어자(블루팀) 입장에서 AI-Infra-Guard와 같은 통합 레드팀 플랫폼은 분산되어 있던 AI 인프라 자산을 일원화하여 식별하고, 기본적인 위생 상태를 빠르게 점검하는 기준선(Baseline) 도구로 활용 가치가 높다. 기존 브라우저 자동화 도구와 에이전트의 권한 경계에 대해서는 Tencent BrowserSkill 분석 — 로그인된 실제 브라우저를 에이전트에게 넘기는 설계와 권한 경계 2026에서 설명한 바와 같이, 도구 권한의 적절한 제한이 보안의 선결 과제다.

그러나 방어 전략을 이 도구의 결과에 전적으로 의존해서는 안 되는 구조적 맹점 또한 존재한다.

  • 시그니처 매칭의 사각지대. 146개 컴포넌트와 2,000개 CVE는 방대한 수치이지만, 오픈소스 AI 생태계의 변경 주기가 매우 빨라 신규 라이브러리의 취약점이 규칙에 반영되기 전까지는 탐지 공백이 발생한다.
  • 정적 검사의 과탐과 오탐. 소스 코드 정적 분석은 맥락을 고려하지 못해 정상적인 개발 유틸리티를 위험 코드로 분류하거나, 복잡한 난독화 기법을 놓칠 가능성이 상존한다.
  • 탈옥 평가의 정량적 착시. 특정 벤치마크 데이터셋에서 90% 이상의 방어율을 기록했다고 해서 실사용 환경의 사용자가 입력하는 교묘한 프롬프트 인젝션을 모두 막아낼 수 있는 것은 아니다.
  • 심층 방어 체계의 필수성. 취약점 스캐너는 문제점을 지적하는 계측기일 뿐 방어벽이 아니다. 네트워크 세그멘테이션, WAF, 도구 호출 시 권한 최소화 원칙, 출력 검증 필터 등 다계층 방어 체계가 뒷받침되어야 한다.
  • 주기적 룰셋 갱신 필요. 데이터베이스가 정적으로 머무르면 보안 효용이 급격히 저하되므로, 저장소의 룰셋 디렉터리(data/vuln/, data/mcp/)를 주기적으로 동기화하는 관리 체계가 수반되어야 한다.

결국 AI 보안 도구는 자동화된 점검을 통해 명백한 결함을 걷어내는 용도로 활용하되, 최종적인 시스템 신뢰성과 권한 격리는 아키텍처 설계와 최소 권한 원칙이라는 기본 위생 위에서 완성되어야 한다.

확인하지 못한 것

  • 온라인 프로 버전(aigsec.ai)의 세부 기능 및 초대 코드 발급 기준. 공식 문서는 초대 코드가 필요하다고만 기술하고 있으며 내부 검사 엔진의 상용판 차이점을 열어보지 못했다.
  • SkillTrustBench 벤치마크의 전체 리더보드 데이터셋. README에 링크된 웹페이지(matrix.tencent.com)의 세부 수치는 조회하지 못해 문서 내 기재된 T01~T09 범주 체계까지만 확인했다.
  • Docker 환경 외에 베어메탈 Linux나 Windows 직접 빌드 시 요구되는 세부 파이썬 및 Go 종속 라이브러리 간 버전 충돌 여부.
  • 2,000여 개 CVE 규칙 중 실제 익스플로잇 가능성이 높은 고위험군(CVSS 9.0 이상)의 세부 비율.
  • 중국 외 글로벌 클라우드 환경(AWS, GCP 등)의 매니지드 AI 서빙 서비스(Bedrock, Vertex AI 등)에 대한 호환성 및 스캔 지원 여부.
