きっかけ - 構造の説明ではなく設計判断を問う記事

2026年7月28日にstock-engineer.comに「Claude Codeスキルパターン」という記事が掲載され(9月29日に更新)、GeekNewsには2026年10月4日登録の項目として紹介された。元記事は七つの章に分かれる。同じ作業をなぜ毎回最初から説明しなければならないのかという問いから出発し、スキルをコマンドの集まりではなく作業の判断基準として見る視点を立て、Anthropicのスキル設計から読み取った四つの原則、規模別の構成方式、公開コレクション三つの設計思想、筆者が実務で得た五つの経験、そして最後に別のスキルとして分ける価値があるかを判断する六つの質問を順に扱う。筆者紹介によれば、組み込みソフトウェア開発の経歴を持つエンジニアで、実務経験はその開発業務とブログ運営から出たものとして書かれている。

この主題の基本構造と書き方は、すでにClaude Code SkillsのA-Zガイドに整理されており、特定のスキルが実際にどう作られているかはArchifyの分析にある。規則をコンテキストに置く方式とフックに変える方式の構造的な比較は、CLAUDE.mdの規則をフックにコンパイルする手法の分析が扱っている。ここではそれらが直接答えていない問い、つまり設計判断に限る。いつスキルに分けるのか、descriptionに何を書いて呼び出しの時点を合わせるのか、どの規則をスキルに置き、どの規則をフックに渡すのか。

設計判断は、根拠の種類が混ざりやすい領域である。公式ドキュメントが確定した事実、公式ドキュメントが推奨すること、一人が実務で得たと述べる経験が一つの段落に混ざると、読者はどこまでが規則なのか分からなくなる。そこで以下では、元記事の各主張を公式ドキュメントと照合し、確認できるもの、一部だけ確認できるもの、筆者の経験としてのみ残るものに分ける。元記事のフックの節には終了コード2の説明がなく、具体的な設定と終了コードの落とし穴は規制産業の二重ゲートの記事にまとめたと、別の記事へ回す言及があるだけだということも、先に述べておく。PreToolUseイベントと終了コード2は公式のフックのドキュメントから持ってきて、別の項目として示した。

descriptionは説明文ではなくトリガーである

元記事が四番目の原則として挙げるのがこの項目である。元記事は、descriptionが利用者向けの説明文ではなく、エージェントがスキルを有効にするかを決める信号だと述べ、何をするかといつ使うかを一緒に書くよう求める。例は、API変更後の互換性テストとマイグレーション検証が必要な作業に使う、である。公式の資料も同じ方向を向いている。ベストプラクティスは、descriptionがスキル発見の基準であり、100個以上になりうるスキルの中から適切なものをClaudeが選ぶときにこのフィールドを使うと説明する。Claude Codeのドキュメントも、Claudeがこのフィールドでスキルを適用する時点を決め、省略した場合は本文の最初の空でない行を代わりに使うと書いている。

下のコードは、Claude Codeのドキュメントが示すSKILL.mdのヘッダーの形式で、現在のドキュメントの例をそのまま写したものである。

---
                    name: my-skill
                    description: What this skill does
                    disable-model-invocation: true
                    allowed-tools: Read Grep
                    ---
                    Your skill instructions here...

この例で、トリガーに関わるフィールドは二つ以上ある。descriptionが呼び出し時点の判断材料で、disable-model-invocationをtrueにすると、Claudeがそのスキルを自動で読み込まなくなる。同じドキュメントの表には、descriptionの後ろに付け加わるwhen_to_use、Claudeだけが呼び出すようにするuser-invocable、有効範囲をグロブで限定するpathsもある。呼び出し時点を合わせることが、一つの文言だけにかかっているわけではないという意味である。

  • 何といつを一緒に - ベストプラクティスの良い例は、PDFのテキストと表の抽出、フォーム入力といった機能の後ろに、PDFファイルを扱うときやユーザーがPDF、フォーム、文書抽出に言及したときに使う、という一文を付ける。
  • あいまいな説明は失敗する - ベストプラクティスが悪い例として挙げるのは、Helps with documentsやProcesses dataのような文である。何も指さず、他のスキルと区別がつかない。
  • 三人称で - ベストプラクティスは、descriptionがシステムプロンプトに注入されるため視点が混ざると発見に問題が出うるとして、三人称を勧める。
  • 上限はドキュメントごとに違う - スキル作成のベストプラクティスはdescriptionを最大1,024文字とし、Claude Codeのドキュメントはdescriptionとwhen_to_useを合わせた文がスキル一覧で1,536文字で切られると書く。二つの数値は別々のドキュメントの記述であり、一つにまとめられない。
  • 中心の用途を先に - 一覧で切られることがあるため、Claude Codeのドキュメントは中心となる使用例を先に置くよう述べる。
  • 手順は本文に - 上限のあるフィールドに手順まで入れると、呼び出し時点の信号が押し出される。これは二つの上限から導かれる解釈で、元記事がそう述べたわけではない。
  • 除外条件 - 使わないときを書く方法についての指針は、参照した公式ドキュメントの範囲にはなかった。重なるスキルがあるときに設計者が決める部分である。

SKILL.mdは目次であり、詳細は外に出す

元記事の二番目と三番目の原則は、同じ方向を指す。段階的開示のためにSKILL.mdを目次として使い、詳細はreferences、実行コードはscripts、テンプレートはassetsに置く。そして指示は、必ず守る順序・完了条件・禁止事項だけを残し、背景の説明は別の文書に移す。公式ドキュメントでこれに当たるのが500行の推奨である。Claude Codeのドキュメントは、SKILL.mdを500行未満に保ち、詳細な参考内容は別ファイルに移すよう書いている。スキル作成のベストプラクティスも、最適な性能のために同じ基準を示している。

この原則で設計判断が必要なのは二か所である。一つは何を外に出すかで、もう一つはどれだけ深く出すかである。公式のベストプラクティスは後者に具体的である。参照ファイルはSKILL.mdから一段の深さで直接つなぐということだ。参照が別の参照を指すと、Claudeがファイルの冒頭だけを先読みして終わることがあり、情報が不完全になると説明する。100行を超える参照ファイルの先頭に目次を置くという推奨も、同じ理由から出ている。

  • 500行は推奨である - 二つの公式ドキュメントとも「保て」「最適な性能のために」と書いており、超過すると自動的に拒否されるという記述はない。
  • 一段の深さ - SKILL.mdから参照ファイルへ直接つなぎ、その参照ファイルからさらに別のファイルを指す構造は避ける。
  • 長い参照ファイルには目次 - 100行を超えたら先頭に置き、部分的に読んでも全体の範囲が見えるようにする。
  • 実行か参照かを明示 - スクリプトは読むものか実行するものかを指示に書く。実行すればスクリプトの出力だけがトークンを使い、内容はコンテキストに入らない。
  • 自由度を作業に合わせる - 複数の方法が有効ならテキストの指示、好ましいパターンがあるならパラメータ付きのスクリプト、作業が壊れやすく順序が固定なら「このスクリプトをそのまま実行」のように狭く指示する。
  • 既定は一つと例外 - 多くのツールを並べず、既定のツールを一つ決め、例外的な状況だけを付け加える。

パイプラインスキルとツールスキルを分ける基準

元記事が実務経験の最初に挙げるのが、この分離である。筆者は、パイプラインスキルがチケットを読むところから、分析、テスト作成、実装、検証、PR作成まで複数の段階をつなぎ、その中の個々の動作であるビルド・テスト・フォーマット・リントはツールスキルが担うと述べている。公式ドキュメントにはこの二つの用語がない。したがってこの分離は、筆者の設計経験として扱う必要がある。ただし、根拠となる隣接した推奨はある。スキル作成のベストプラクティスは、決定論的な動作にはスクリプトを使うよう述べ、その理由として、生成されたコードより信頼でき、トークンと時間を節約し、使用ごとの一貫性を保てることを挙げている。

分離が意味を持つ条件は二つにまとめられる。一つ目は、同じ動作が複数の手順で繰り返されるときである。ビルドやテストのように、どのパイプラインも通る動作をツールスキルとして切り離しておけば、手順が変わっても動作の定義は一か所に残る。二つ目は、手順は頻繁に変わるが動作は固定のときである。この二つの条件は元記事が直接書いたものではなく、筆者の記述から読み取れる設計上の解釈であり、元記事が示した根拠は分離したという経験そのものである。

  • パイプラインスキル - 段階の順序、段階間の完了条件、禁止事項を持つ。元記事の例はチケットの読み取りからPR作成までである。
  • ツールスキル - ビルド・テスト・フォーマット・リントのように、入力と出力が比較的固定された動作を担う。
  • つなぎ方 - パイプラインがツールスキルを呼び出す構造である。呼び出し方法の詳細は元記事にない。
  • 適用の限界 - この区分がすべてのチームに合うという根拠はない。元記事は、筆者自身の開発パイプラインとブログ運営から得た経験だと述べている。

落とし穴の一覧はどこに置くか

元記事の最初の原則は、良いスキルが正常な手順だけでなく、よくある間違いと失敗のパターンを明示するということである。例として挙げられる文が、テストが通っただけで要件を満たしたと断定しない、である。この原則は、実務経験の二番目の項目で問題にぶつかる。筆者は、落とし穴の一覧がスキル本文の担える速度より速く増えると述べ、対処としてスキルの外の知識ファイルに落とし穴を分けたという。スキル本文は手順だけを持ち、知識ファイルはセッションごとに得た教訓を、レビュー・フォーマット・ビルド・テスト・CI・設計のような接頭辞で分類して積む。

公式ドキュメントでこれに近いのは、参照ファイルの分離と、時間に敏感な情報の扱い方である。ベストプラクティスは、すぐに古くなる情報を本文に置かず、old patternsの節に畳んでおくよう述べている。落とし穴は古くなる速さがそれぞれ違うという点で、この推奨と接する。ただし接頭辞による分類と、セッションごとに積む運用の方法は、公式ドキュメントにはない筆者の方式である。

  • 本文に置く落とし穴 - 手順を飛ばすとただちに失敗する禁止事項。元記事の三番目の原則である、必須の順序・完了条件・禁止事項に当たる。
  • 知識ファイルに置く落とし穴 - セッションを重ねて増え続ける個別の事例。接頭辞で分類して、必要な分類だけを読ませる。
  • 古くなる落とし穴 - 特定のバージョンや時点に結びついた落とし穴は、old patternsのような区画に集めて本文と分ける。
  • どこまでが経験か - 本文と知識ファイルを分ける基準は上のように解釈したもので、元記事が基準を数値で示したわけではない。

スキルは指示し、フックは止める - 役割分担

元記事の四番目の経験が、この分担である。筆者は、レビュー文書を作ってからpushするという指示をスキルに書くより、レビュー文書がなければpushコマンドそのものを止めるClaude Codeのフックで強制するほうがよいと述べている。要約すれば、スキルは「やれ」と言い、フックは「やらせない」。元記事はフックのイベントや終了コードを説明せず、具体的な設定と終了コードの落とし穴は規制産業の二重ゲートの記事にまとめたと別の記事へ回している。以下は、公式のフックのドキュメントが確認している部分である。

公式のフックのドキュメントで、終了コード2はブロッキングエラーである。ブロックできるイベントでは、JSONを出力したかどうかに関係なく終了コード2がブロックし、JSONのpermissionDecisionがallowでもそれを上書きできない。PreToolUseで終了コード2はツール呼び出しを止める。ブロックのメッセージは、JSONがあればその理由、なければ標準エラーのテキストが使われる。終了コード0は成功で、それ以外の終了コードは、ほとんどのイベントでそれだけではブロックしない。

{
                      "hookSpecificOutput": {
                        "hookEventName": "PreToolUse",
                        "permissionDecision": "deny",
                        "permissionDecisionReason": "Destructive command blocked by hook"
                      }
                    }

上のJSONは、公式ドキュメントが終了コード2の代わりとして示すPreToolUseの構造化出力である。permissionDecisionに使える値はallow、deny、ask、deferである。フックはsettings.jsonのようなJSON設定ファイルやプラグインで定義し、matcherフィールドでどのツールに反応するかを絞り込む。公式のフックのリファレンスは、フックをシェルコマンド、HTTPエンドポイント、MCPツール呼び出し、LLMプロンプト、またはサブエージェントとして説明している。「決定論的(deterministic)」という表現はフックのガイドにあり、フックがLLMの選択に頼らず決まった時点で常に実行されるという意味である。この性質が、元記事の分担、つまり破ってはならない規則はフックに任せるという判断を裏づける。

  • スキルに置く規則(解釈) - 判断と順序が必要で、破っても元に戻せるもの。エージェントが読んで従う手順である。
  • フックに置く規則 - 破ってはならないもの(元記事の分担)。ツール呼び出しの直前に条件を検査して止める。元記事の例は、レビュー文書がないときのpushの遮断である。
  • 終了コードの落とし穴 - ブロックするには終了コード2か、構造化出力でのdenyが必要である。他の異常終了コードは、ほとんどのイベントでそれだけではブロックしないため、スクリプトがエラーで終了したから止まったと仮定してはならない。
  • ブロック理由の伝達 - ブロックのメッセージはエージェントが読む情報なので、何が足りなくて止めたのかを具体的に書くほうが次の行動に役立つ。これはドキュメントの記述から導かれる解釈である。
  • スキルとフックの接点 - 公式ドキュメントのフックを定義できる場所の一覧には、スキルとサブエージェントのフロントマターもあり、その場合はスキルの実行中に適用される。
  • より深い比較 - 規則をコンテキストに注入する方式の限界と、それをフックに変える手法は、先の分析記事が扱っている。

スキルが増えるほど大きくなるコスト

元記事の五番目の経験は、スキルが増えるとセッションごとのコストも増えるということである。筆者は、スキルの説明の全文と、スキル約50個、エージェント約20個、ツール約60個の一覧がコンテキストに入ったと述べ、エージェントオーケストレーションのプラグイン二つを切って、既定の設定に戻したと書いている。プラグインの名前は元記事に書かれていない。使わないスキルの多いカタログはそれ自体がコストだというのが、筆者の結論である。

公式ドキュメントと照合すると、コストの正体がより正確になる。スキル作成のベストプラクティスは、起動時にすべてのスキルの名前と説明だけが事前に読み込まれ、SKILL.mdはスキルが関連するときに読まれると述べる。Claude Codeのドキュメントも、説明は常にコンテキストにあり、スキル全体は呼び出されたときに読み込まれ、スキル本文は使うときだけ読み込まれるので、長い参考資料は必要になるまでコストがほとんどかからないと書いている。つまり、使わないスキルが占めるのは本文ではなく説明である。そして説明の部分も、一覧では1,536文字で切られる。

  • 常時のコスト - 名前と説明(メタデータ)。スキルの数に比例して増える。
  • 呼び出し時のコスト - SKILL.mdの本文。呼び出されたときだけ読み込まれ、500行の推奨はこのコストを狙っている。
  • 筆者の数値の読み方 - 元記事はスキル約50個、エージェント約20個、ツール約60個を別々に数えている。50がスキルの数なので、スキルの一覧だけで約50件が毎セッションのコンテキストに入ったという記述である。エージェントとツールの一覧、ツール使用ごとの案内文は別のコストである。
  • 減らす方法 - 説明を短く、重ならないように書き、自動呼び出しが不要なスキルにはdisable-model-invocation: trueを置く選択がある。公式のスキルのドキュメントの表は、この場合を「Description not in context, full skill loads when invoked」、つまり説明がコンテキストにないと記し、ドキュメントはこの設定をスキルをClaudeのコンテキストから完全に取り除く方法(removes the skill from Claude's context entirely)と説明している。代わりにClaudeは自分では呼び出せず、ユーザーが直接呼び出す必要がある。

別のスキルに分けるか判断する表

元記事の七番目の章は、スキルに分ける価値があるかを六つの質問で点検する。下の表はその質問と信号を写し、三列目に公式ベストプラクティスの隣接する推奨を付けたものである。三列目は、つなげられる項目だけを書いた。

確認の質問元記事が示す信号公式ドキュメントの隣接する推奨
繰り返しの頻度似た指示を複数のセッションで繰り返している-
手順の複雑さ三段階以上の固定された作業順序がある複雑な作業は順序のある段階とチェックリストに分ける

この表で公式ドキュメントが直接述べているのは、分離の時点ではなく、分離した後の品質である。ベストプラクティスは、広範な文書を書く前に評価を先に作るよう述べ、スキルなしで代表的な作業を回して失敗を記録し、その穴を埋める最小限の指示を書くという順序を示す。評価は最低三つ、使うすべてのモデルで試すという点検項目もある。元記事の締めくくりも方向は同じである。成功の指標はスキルの数ではなく、同じ間違いが減ったか、必要なときに正確に呼び出されるかにあるという趣旨だ。

  • 表の信号はすべて現在の状態を問う質問である。繰り返しているか、固定の順序があるか、完了を判定できるか、といった具合だ。
  • 分離した後は、同じ間違いが減ったかと呼び出しが正確かを指標にするというのが、元記事の基準である。
  • 評価を先に作る順序はベストプラクティスの推奨であり、元記事の六つの質問は、その評価より前の分離の判断に当たる。
