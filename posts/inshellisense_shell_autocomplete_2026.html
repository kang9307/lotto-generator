inshellisense — 터미널에서 IDE처럼 자동완성하는 마이크로소프트 오픈소스 도구

600개 이상 CLI 스펙으로 8개 셸을 아우르는 자동완성 - bash-completion·fzf와 무엇이 다른가

2026-07-05 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 터미널은 왜 IDE보다 한 세대 뒤처져 있었나

터미널에서 명령어 하나 치는 데도 대시 뒤에 어떤 옵션이 오는지, 이 서브커맨드가 인자를 몇 개나 받는지 기억이 안 나 매번 --help로 되돌아간 경험은 누구에게나 있다. 통합개발환경(IDE)에서는 이런 문제가 오래전에 해결됐다. 함수 이름 몇 글자만 쳐도 시그니처와 설명이 뜨는 인텔리센스류 자동완성 덕분이다. 그런데 정작 하루에도 몇 번씩 여는 터미널 셸은 이 경험에서 한 세대 뒤처져 있었다.

2026년 7월 기준으로도 여전히 활발히 커밋되고 있는 마이크로소프트의 오픈소스 프로젝트 inshellisense는 바로 이 격차를 메우겠다는 도구다. 이름 그대로 셸(shell) 안에 인텔리센스를 넣겠다는 뜻이다. GeekNews에도 소개되며 11점을 받은 이 프로젝트는 화제성만 보면 크지 않지만, 터미널 자동완성이라는 오래된 문제를 어떤 접근으로 풀고 있는지 뜯어볼 값어치가 있다. 이 글은 보도자료를 옮기는 대신, 실제 GitHub 저장소·API로 직접 확인한 지표와 공개된 기술 자료를 근거로 inshellisense가 무엇을 하고 어떻게 동작하는지, 그리고 bash-completion이나 fzf 같은 기존 도구와 어떻게 다른지를 본인 관점에서 따져본다.

1. inshellisense란 무엇인가 - 마이크로소프트가 만든 IDE식 자동완성

1.1 무엇을 하는 도구인가

inshellisense는 마이크로소프트가 2023년 10월 GitHub에 공개한 오픈소스 프로젝트로, 터미널 셸에 IDE 스타일의 자동완성을 붙여준다. TypeScript로 작성됐고(전체 코드의 87% 이상), MIT 라이선스로 배포된다. 본인이 GitHub API로 직접 확인한 결과 2026년 7월 기준 스타 1만 73개, 포크 224개를 기록하고 있고, 가장 최근 코드 반영이 이 글을 쓰는 시점 며칠 전이었을 만큼 지금도 꾸준히 유지보수되고 있다. 설치는 npm install -g @microsoft/inshellisense 한 줄이나 Homebrew(brew tap microsoft/inshellisense && brew install inshellisense)로 끝나고, 셸에서 is 명령 하나로 자동완성이 켜진 세션이 시작된다.

1.2 지원 셸 8종과 크로스플랫폼

지원 범위가 넓다는 점이 이 프로젝트의 실질적인 강점이다. bash·zsh·fish 같은 유닉스 계열 셸은 물론, PowerShell Core(pwsh)와 Windows PowerShell, 실험적으로 cmd까지, 여기에 상대적으로 덜 알려진 xonsh·nushell까지 총 8개 셸을 지원한다. Windows·Linux·macOS를 모두 아우르는 크로스플랫폼 도구라는 뜻이다. 특히 PowerShell·cmd 지원은 뒤에서 다룰 이 프로젝트의 계보를 이해하는 데 중요한 단서가 된다.

1.3 설정과 커스터마이즈

설정은 홈 디렉터리의 .inshellisenserc나 XDG 규격을 따르는 ~/.config/inshellisense/rc.toml 파일 하나로 관리된다. 후보를 받아들이는 키(기본 Tab), 다음/이전 후보 이동(화살표), 취소(Escape) 같은 키바인딩을 바꿀 수 있고, useAliases 옵션으로 bash·zsh의 별칭까지 인식하게 하거나, useNerdFont로 Nerd Font 아이콘을 켜고, maxSuggestions로 한 번에 보여줄 후보 수를 제한할 수 있다. 설정 스키마가 JSON 스키마로 공개돼 있어 에디터에서 자동완성을 받으며 설정 파일 자체를 작성할 수 있다는 점도 세심하다.

2. 어떻게 동작하는가 - PTY 래퍼와 OSC 프로토콜

2.1 셸을 패치하지 않고 감싸는 방식

inshellisense가 흥미로운 지점은 무엇을 보여주느냐보다 어떻게 만들어내느냐에 있다. 이 도구는 bash나 zsh 같은 셸 자체를 패치하거나 포크하지 않는다. 대신 node-pty 라이브러리로 사용자의 실제 셸 프로세스를 의사 터미널(pseudo-terminal, PTY) 안에 그대로 실행시키고 그 위에 얇은 래퍼로 올라앉는다. 사용자 눈에는 평소 쓰던 셸과 똑같이 보이지만, 실제로는 inshellisense가 입출력을 중계하며 필요한 순간에 자동완성 UI를 얹는 구조다.

2.2 프롬프트 상태를 추적하는 커스텀 OSC

문제는 래퍼가 지금 프롬프트가 시작됐는지, 사용자가 명령을 실행했는지, 현재 작업 디렉터리가 어디인지를 셸마다 다른 문법을 파싱하지 않고 알아내야 한다는 점이다. inshellisense는 각 셸용으로 배포하는 셸 통합 스크립트가 프롬프트 시작(OSC 6973;PS)·명령 제출(OSC 6973;PE)·현재 디렉터리(OSC 6973;CWD) 같은 커스텀 OSC(운영체제 명령) 이스케이프 시퀀스를 내보내는 방식으로 이를 해결한다. 서로 다른 8개 셸을 하나의 코드베이스로 지원할 수 있는 것은, 셸 고유 문법을 직접 파싱하는 대신 이런 얇고 공통된 신호 규약에 기댔기 때문이다.

2.3 스펙 기반 제안 엔진 - withfig/autocomplete 600+

실제 자동완성 후보는 사용자가 타이핑하는 동안 내부 SuggestionManager가 스펙 기반 런타임에 물어 얻는다. 이 런타임이 참조하는 것이 바로 Fig가 원래 만든 오픈소스 스펙 라이브러리 @withfig/autocomplete다. inshellisense의 package.json은 이 패키지를 2.675.0 버전으로 명시적으로 고정해 두고 있는데, 이 버전 번호 자체가 스펙 라이브러리가 그동안 얼마나 촘촘하게 갱신되어 왔는지를 보여준다. 여기 담긴 600개 이상의 CLI 명세 덕분에 git·npm·docker·kubectl 같은 도구의 서브커맨드·옵션·인자 타입에 설명까지 곁들여 명령줄 바로 아래에 ANSI 이스케이프로 인라인 렌더링할 수 있다.

3. 기존 셸 자동완성과 무엇이 다른가 - bash-completion·zsh 비교

bash-completion이나 zsh의 compinit·compdef, fish의 내장 completions 디렉터리는 사실 오래전부터 있던 해법이다. 다만 이들은 근본적으로 셸별·도구별 완성 스크립트를 따로 짜고 배포해야 하는 구조다. 어떤 도구는 bash용 완성 스크립트만 잘 만들어져 있고 zsh나 fish용은 부실하거나 아예 없는 경우가 흔하고, 있다 해도 결과는 대개 옵션 이름만 나열하는 밋밋한 목록이다.

inshellisense는 이 파편화를 다른 방식으로 우회한다. 셸마다 별도 완성 스크립트를 짜는 대신, git이든 docker든 하나의 공유 스펙(withfig 포맷)만 있으면 이를 지원하는 8개 셸 전체에서 동일한 완성 결과를 낸다. 게다가 스펙에는 옵션 설명이나 인자가 파일 경로인지 브랜치 이름인지 같은 타입 정보까지 들어 있어, 후보 옆에 짧은 설명을 곁들이는 IDE식 표시가 가능하다.

4. fzf와는 어떻게 다른가 - 경쟁이 아니라 보완

fzf는 이 논의에서 자주 함께 언급되지만 정확히는 다른 계층의 도구다. fzf 자체는 범용 퍼지 파인더이고, fzf-tab처럼 셸 완성에 fzf를 접붙이는 플러그인들은 스스로 완성 후보를 만들어내지 않는다. 대신 셸의 기존 완성 시스템(위에서 말한 bash-completion 같은 것)이 이미 만들어낸 후보 목록을 받아, 그중 원하는 항목을 빠르게 좁혀 찾도록 도와주는 역할을 한다.

반면 inshellisense는 그 자체가 완성 엔진이다. 무엇을 후보로 보여줄지 자체를 withfig 스펙을 참조해 결정하고, 트리거 키를 누르지 않아도 타이핑과 동시에 인라인으로 띄운다. fzf는 이미 있는 후보 목록을 더 잘 찾게 해주는 검색 레이어이고, inshellisense는 애초에 어떤 후보가 어떤 설명과 함께 존재하는가를 정의하는 생성 레이어다. 그래서 둘은 대체재가 아니라 서로 다른 문제를 푸는 도구에 가깝다.

5. 생산성과 러닝커브 - 실제로 무엇이 좋아지나

이런 구조가 실무에 주는 이득은 명확하다. git만 해도 서브커맨드와 옵션이 수십 개에 달하고, docker·kubectl·gh처럼 자주 쓰는 CLI들도 사정은 비슷하다. 매번 --help를 뒤지거나 맨페이지를 검색하는 대신, 타이핑하는 즉시 옵션 이름과 짧은 설명이 눈앞에 뜨면 인지 부하가 확실히 줄어든다. 숙련자에게도 도움이 되지만, 특히 이제 막 CLI 도구들을 익히기 시작한 사람에게 러닝커브를 낮춰주는 효과가 크다. Tab으로 받아들이고 화살표로 넘기는 조작 자체는 기존 셸 완성과 크게 다르지 않아 손에 익은 습관을 버릴 필요도 없다.

다만 이 이득은 스펙이 존재하는 도구에 한정된다는 점도 분명히 해야 한다. 회사 내부에서만 쓰는 사설 CLI나 아직 withfig 스펙이 만들어지지 않은 신생 도구라면 inshellisense도 별다른 도움을 주지 못하고 기존 셸의 기본 완성으로 돌아간다.

6. 뿌리를 거슬러 올라가면 - Fig의 몰락과 스펙의 두 번째 삶

6.1 Fig란 무엇이었나

inshellisense가 의존하는 @withfig/autocomplete 스펙 포맷은 사실 마이크로소프트가 처음 만든 게 아니다. 원조는 Fig라는, 2020년 무렵 등장한 macOS(이후 리눅스 베타)용 네이티브 터미널 자동완성 앱이었다. Fig는 자체 스펙 포맷과 600개 이상 CLI 명세를 오픈소스(withfig/autocomplete, MIT 라이선스)로 공개해 커뮤니티가 기여하게 했고, 본인이 API로 확인한 결과 이 저장소는 현재도 스타 2만 5,190개, 포크 5,455개를 보유하고 있다.

6.2 아마존 인수, sunset, 그리고 Windows라는 빈틈

Fig 팀은 2023년 8월 아마존에 합류했고, 곧이어 그해 11월 아마존 CodeWhisperer(현 Amazon Q Developer)에 커맨드라인용 기능을 이식했다. 이후 2024년 9월 1일 Fig 앱 자체는 완전히 서비스를 종료(sunset)하며 사용자들에게 Amazon Q Developer로 이전하라고 안내했다. 흥미로운 점은 마이크로소프트의 inshellisense가 이 sunset보다도 앞선 2023년 10월에 이미 저장소를 공개한 상태였다는 것이다. 즉 inshellisense는 Fig가 망해서 급하게 나온 대체품이 아니라, Fig의 스펙 라이브러리가 오픈소스로 독립돼 있었기에 처음부터 별도 엔진으로 재활용할 수 있었던 사례에 가깝다. 여기에 마이크로소프트가 파고든 확실한 빈틈이 하나 있다 - Fig는 애초에 Windows를 지원한 적이 없다. inshellisense가 pwsh·PowerShell·cmd까지 끌어안은 것은, 정확히 Fig 생태계가 닿지 못했던 자리를 메운 선택으로 읽힌다.

6.3 스펙 라이브러리의 유지보수 신선도

다만 주의할 부분이 있다. 본인이 GitHub API로 직접 확인한 결과, 스펙 원본이 있는 withfig/autocomplete 저장소의 최근 커밋은 2025년 5월로, inshellisense 본체의 최근 커밋(2026년 6월)보다 1년 이상 오래됐다. Fig 앱이 사라진 뒤 스펙 저장소에 대한 커뮤니티 기여 속도가 눈에 띄게 느려졌다는 뜻으로 읽을 수 있다. inshellisense가 이 스펙을 계속 받아쓰고 있긴 하지만, 아주 최근에 나온 CLI 도구의 완성 품질은 결국 이 상류 저장소가 얼마나 빨리 새 스펙을 받아들이느냐에 달려 있다는 뜻이기도 하다.

7. 한계와 주의점

장점만 나열하는 건 정직하지 않다. 첫째, az·gcloud·aws처럼 방대한 서브커맨드를 가진 CLI는 스펙 파일 자체가 너무 커진다는 이유로 공식적으로 지원되지 않는다. 클라우드 인프라를 다루는 사용자에게는 아쉬운 공백이다. 둘째, 2026년 3월에 나온 최신 안정판조차 버전 번호가 0.0.1이다. 2023년 10월부터 거의 3년 가까이 개발돼 왔고 스타도 1만 개를 넘었지만, 프로젝트 스스로는 여전히 1.0 이전의 실험적 단계로 규정하고 있는 셈이다. 셋째, 앞서 짚은 대로 근간 스펙 저장소의 갱신 속도가 느려졌다. 넷째, PTY로 셸 전체를 감싸는 구조이니만큼 극단적으로 느린 네트워크·원격 세션이나 일부 터미널 멀티플렉서 조합에서는 예상치 못한 렌더링 이슈가 생길 여지도 이론적으로 배제할 수 없다(본인이 직접 재현 검증한 것은 아니며 아키텍처상 가능한 리스크로 봐야 한다).

결론: 오늘 써볼 가치가 있는가

inshellisense는 화려한 신제품이라기보다, 이미 검증된 아이디어인 Fig의 스펙 기반 자동완성을 마이크로소프트가 크로스플랫폼·오픈소스 형태로 다시 조립한 도구에 가깝다. 그 재조립이 의미 있는 이유는 두 가지다. 하나는 Fig가 끝내 닿지 못했던 Windows 셸까지 같은 엔진으로 끌어안았다는 것이고, 다른 하나는 셸마다 흩어져 있던 자동완성 경험을 하나의 스펙·하나의 엔진으로 통일했다는 것이다.

2026년 7월 기준으로 이 도구를 오늘 써 볼 가치가 있는지 판단하는 세 가지 기준을 제안한다. 첫째, 평소 git·docker·kubectl·npm처럼 옵션이 많은 CLI를 자주 쓰면서 매번 --help로 되돌아가는 빈도가 잦다면, npm install -g @microsoft/inshellisense 한 줄로 바로 체감할 이득이 있다. 둘째, az·gcloud·aws 같은 클라우드 CLI가 주력이라면 스펙 미지원 문제부터 확인해야 한다. 셋째, 아직 0.0.1 버전이라는 점과 스펙 저장소의 갱신 속도를 감안해, 프로덕션 워크플로에 강하게 의존하기보다는 로컬 개발 환경에서 먼저 가볍게 테스트해 보는 편을 권한다. 개발자 도구 생태계에서 오픈소스 스펙 자산이 인수·서비스 종료를 넘어 다른 벤더의 손에서 다시 살아나는 이번 사례는 앞으로도 반복될 만한 패턴으로 봐도 좋을 것이다. 표준 커넥터로 도구를 잇는 흐름에 관심이 있다면 MCP 서버로 대중교통 데이터를 에이전트에 연결한 나어려(naeryeo) 분석도 함께 참고할 만하다.
