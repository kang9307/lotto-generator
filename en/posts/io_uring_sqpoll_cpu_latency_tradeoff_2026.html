1. The Anxious Attachment Metaphor and the Emergence of io_uring SQPOLL

io_uring is an asynchronous I/O interface in Linux where user space and the kernel exchange requests via ring buffers. Among its operating modes, SQPOLL (Submission Queue Polling) allows a kernel thread to poll the submission queue so applications can issue I/O without system calls, in exchange for consuming CPU resources.

Recently featured on the GeekNews community, the blog article titled 「SQPOLL Is an Anxious-Attachment Girlfriend」 by gg582 on oborona.zip explained this technology using an everyday metaphor. The original post organized its discussion into four sections: 「What on Earth Is io_uring?」, 「Default Mode / Interrupt-Driven Mode」, 「What Is SQPOLL and Why Is It Called an 'Anxious Girlfriend'?」, and 「A Somewhat Amusing Summary」. The author explains the operation of io_uring through attachment style analogies.

The blog compares the default mode (interrupt-driven mode) to 「a securely attached girlfriend with her own life」 and SQPOLL to 「an anxious girlfriend」. According to the man page, specifying the SQPOLL flag creates a kernel thread to perform submission queue polling, allowing the application to submit and reap I/O without issuing system calls. The blog describes this state with the phrasing: 「Oppa, where are you right now? My heart is burning, where are you?」

The blog also mentions IORING_SETUP_SQ_AFF using expressions such as 「a slight stalker tendency also develops」 and 「the CPU is burning up」. The central question of this article is under what conditions choosing to spend CPU cores to eliminate system calls is appropriate.

2. Structural Differences Between Interrupt-Driven Mode and Polling Mode

The general descriptions in this section represent this article's summary, with primary source basis established in the SQPOLL paragraphs below. In default mode, an application submits requests and notifies the kernel via io_uring_enter(2), allowing the CPU to perform other tasks while waiting.

In this article's analysis, this mechanism offers high CPU efficiency because other processes can utilize the processor during idle waiting. The blog's summary also notes: 「If you want to burn less CPU rather than chasing performance, pick the secure girlfriend」.

The man page describes SQPOLL as follows: 「When this flag is specified, a kernel thread is created to perform submission queue polling. An io_uring instance configured in this way enables an application to issue I/O without ever context switching into the kernel. … the application can submit and reap I/Os without doing a single system call.」 Neither source provides numerical measurements regarding exact system call costs.

In essence, the core of SQPOLL is that a kernel thread polls the submission queue so that applications can submit and reap I/O without making system calls. The exact name of this kernel thread is not stated in the man page.

3. Shared Ring Buffers: SQE Submission and CQE Retrieval Mechanics

The ring buffer structure described in this section represents this article's summary of general io_uring architecture and is not direct quotation from the two sources. io_uring utilizes shared ring buffers between user space and the kernel, comprising a Submission Queue (SQ) and a Completion Queue (CQ). The general flow of processing requests is structured as follows:

  • The application populates an available slot in the Submission Queue (SQ) with a Submission Queue Entry (SQE) describing the operation.
  • After filling the SQE, the application updates the tail of the SQ ring to signal the presence of a new request.
  • Under SQPOLL, the kernel thread polls the submission queue to process the new SQE (man page: a kernel thread is created to perform submission queue polling).
  • When processing completes, results return as Completion Queue Entries (CQEs) in the Completion Queue (CQ), and the application inspects the completion queue (man page: watching for completions on the completion queue).

In this article's summary, submissions and completions under SQPOLL occur through shared memory operations, avoiding the need to invoke system calls. However, if the kernel thread enters sleep, the wakeup procedure described in the following section becomes necessary.

4. The sq_thread_idle Parameter and the NEED_WAKEUP Handshake

The man page explains that if the kernel thread is idle for more than sq_thread_idle milliseconds, it sets the IORING_SQ_NEED_WAKEUP bit in the flags field of struct io_sq_ring. In this article's deduction, without this idle handling, the polling thread would continuously check empty queues and consume CPU. The man page does not directly address idle CPU consumption.

sq_thread_idle is a field within struct io_uring_params specified in milliseconds. The man page does not specify a default value.

In this article's deduction, if the thread goes to sleep, it cannot detect subsequent submissions appended by the application on its own, making a wakeup handshake necessary. The procedure specified in the man page proceeds as follows:

  • The kernel thread sets IORING_SQ_NEED_WAKEUP in the flags field when idle duration exceeds sq_thread_idle milliseconds.
  • The application updates tail and subsequently reads flags. The man page states 「Ensure that the wakeup flag is read after the tail pointer has been written」, instructing the use of load-acquire semantics for the flags read.
  • If NEED_WAKEUP is set, the application invokes io_uring_enter(fd, 0, 0, IORING_ENTER_SQ_WAKEUP) (man page code example).
  • The man page does not describe what occurs if this check is omitted. In this article's deduction, omitting wakeup may prevent submitted I/O from being processed.

The man page notes that when using an SQPOLL ring, applications typically do not call io_uring_enter(2) directly, as this is usually handled by liburing's io_uring_submit(3).

That developers handling raw system calls directly must implement this verification manually is this article's interpretation.

5. IORING_SETUP_SQ_AFF and the Price of Burning Dedicated CPU Cores

According to the man page, IORING_SETUP_SQ_AFF binds the polling thread to the CPU specified in the sq_thread_cpu field of struct io_uring_params, and is only meaningful when combined with IORING_SETUP_SQPOLL. The man page also notes that in container environments, when cgroup cpuset.cpus changes, the bounded CPU set may change as well.

In this article's deduction, binding the polling thread to a specific core makes that core less available for other computational work. The blog expresses this condition by stating that 「the CPU is burning up」.

In this article's assessment, in services with infrequent requests, the cost of dedicating a core to polling can exceed the performance benefit. Neither source provides quantitative figures on this trade-off.

6. Evolution of Linux Kernel Privileges — From CAP_SYS_NICE to Unprivileged Access

The man page states that SQPOLL operating requirements changed across kernel versions.

  • Prior to 5.11: Applications had to register a set of files using io_uring_register(2) with IORING_REGISTER_FILES, or submitted I/O would fail with EBADF. The absence of this restriction can be detected by the IORING_FEAT_SQPOLL_NONFIXED flag.
  • 5.11: File pre-registration was no longer required, and users with CAP_SYS_NICE capability could use SQPOLL without root privileges.
  • 5.13 and newer: This requirement was relaxed so that no special privileges are needed in newer kernels. The man page notes that certain stable kernels older than 5.13 may also support unprivileged SQPOLL.

In this article's interpretation, as privilege hurdles have lowered, the decision to adopt SQPOLL rests on users evaluating their specific workloads. Actual industry adoption rates or usage statistics are not covered by either source.

8. Architectural Decision Criteria — Where SQPOLL Pays Off and Where It Fails

This section reflects this article's interpretation rather than recommendations from the two sources. The blog's summary states: 「If you want to burn less CPU rather than chasing performance, pick the secure girlfriend; if you want performance at all costs, pick the anxious girlfriend」. This can be interpreted as evaluating default mode when CPU efficiency is prioritized, and evaluating SQPOLL when peak performance is paramount.

In this article's estimation, the cost of a polling core may be justified in workloads where latency is of highest importance and I/O traffic is continuous. Specific industry sectors or benchmark figures are not present in either source.

Conversely, SQPOLL may be unsuitable under the following conditions (all representing this article's deductions):

  • Services with long idle periods between requests: Polling consumes CPU, and if the thread sleeps, the required wakeup handshake may diminish performance gains.
  • Environments with limited CPU cores: If allocated vCPUs are few, a polling thread occupying a core leaves less CPU available for other threads. The man page notes container cpuset.cpus adjustments may alter bounded CPU sets.
  • Environments where CPU utilization directly determines costs: The polling thread's CPU consumption may register on billing or auto-scaling metrics. Neither source covers cloud billing.
  • Power-sensitive devices: Continuous polling can increase power consumption. The man page does not address electrical power.

9. Practical Verification: Benchmarking Workloads in Isolated Environments

The procedures below represent suggestions from this article rather than guidelines found in the two sources. Because the blog contains no benchmark metrics, users must test within their own environments.

  • Step 1: Baseline interrupt-driven profiling — One can record CPU utilization and I/O throughput in default mode.
  • Step 2: SQPOLL deployment and sq_thread_idle tuning — After applying IORING_SETUP_SQPOLL, one can adjust sq_thread_idle while monitoring the frequency of NEED_WAKEUP occurrences.
  • Step 3: System call frequency tracking — One can verify whether the rate of io_uring_enter(2) system call invocations decreases.
  • Step 4: Latency and core impact evaluation — When binding a core via IORING_SETUP_SQ_AFF, one can compare latency improvements against the impact on other running tasks.

10. Unverified Technical Aspects

This article consulted only the blog post and io_uring_setup(2). Aspects that could not be verified include:

  • The blog article (oborona.zip/post/sqpoll) addresses qualitative analogies and structural concepts without providing quantitative benchmark metrics regarding IOPS, microsecond latency, or CPU utilization, preventing verification of empirical numbers.
  • The official manual page io_uring_setup(2) does not state the kernel's internal fallback default timeout in milliseconds when sq_thread_idle is left unassigned by the caller.
  • While the man page notes that certain pre-5.13 stable kernels may support unprivileged SQPOLL, it does not provide an exhaustive list of specific kernel release versions. The exact name of the polling kernel thread is also not stated in the man page.
  • Quantitative differences in sq_thread_idle thresholds or electrical power consumption between network socket I/O and block storage I/O fall outside the scope of both sources.
