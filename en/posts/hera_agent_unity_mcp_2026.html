hera-agent-unity - A CLI Alternative to MCP for Controlling Unity

Making AI agents measure the game engine instead of guessing it - what is new and what it means for developers

2026-06-16 Dev & Infra

Intro: AI writes code without knowing the game engine

Ask an AI coding agent to work in Unity and something strange happens. The model confidently writes code, but that code targets some Unity it remembers, not your project. It assumes old APIs from training time, scene structures that are not in context, and packages that are not actually installed. Because a game engine changes APIs between versions and decides scene and component state at runtime, that guessing turns straight into compile errors or subtly wrong behavior.

As of June 2026, a tool that aims squarely at this problem drew attention on GeekNews and elsewhere: hera-agent-unity. To borrow a short phrase from the project, its philosophy compresses into one line - "guessing is expensive, measurement is the command." Rather than rehashing the repo README or the GeekNews thread, this article works through what the tool's design choices actually mean, and what practical lessons they hold for anyone who wants to use AI agents in real game development.

Let me set the disclaimer up front. The tool specs here are based on the public repository docs and the GeekNews writeup, not on my own long-term production validation of every command. So I separate "what is claimed" from "why it is reasonable, and where it could wobble."

1. The real problem - not hallucination but context starvation

When AI writes wrong code, we usually call it "hallucination." But in an environment like Unity, the more accurate diagnosis is context starvation.

1.1 What the model does not know

A large language model invents bad API calls because it has not seen enough examples to know the real API. In game development this is especially acute. The Unity API changes between versions, and the same feature can shift signatures across major updates. When the model's training point and your version diverge, the model writes code for "the Unity of that era." More fundamentally, which scene is open and which components are attached to which GameObject are runtime state of your project, not general knowledge. The model has no way to know it, so it assumes.

1.2 Context is truncated and errors compound

Most codebases do not fit in a context window. So the agent sees only part of the code, often a misleading slice. The small errors that arise on top of it compound over the agent's long run time, and by the end those mistakes are baked into the code. In an environment like Unity, where "scene state to component to code" are entangled, one wrong assumption spreads in a chain.

1.3 The fix - make it queryable

The core of the fix is clear: make the agent query the project instead of guessing it. If it can directly ask which scene is active, which GameObjects exist, which components are attached, and which packages are installed, hallucination drops and tokens are saved, because the model verifies what is true instead of assuming it. That is exactly what hera-agent-unity sets out to do.

2. What hera-agent-unity is - driving Unity with a single binary

The tool's architecture is deliberately minimal. In one line, it is a bridge that lets an AI agent control a live Unity editor over a CLI.

2.1 Core makeup

The client side is a single Go binary, and the Unity side is one C# UPM package. The two talk over local HTTP. Open Unity and the connector starts automatically, listening on a localhost port (8090 or above per the docs). To borrow the repo's phrasing, "one Go CLI, one C# UPM package, zero runtime dependencies, MIT" is the whole thing. No Python, no WebSocket relay, no resident middleware process, no JSON-RPC daemon.

2.2 What it can do

The command surface is broad. The main categories, as I read them, are:

  • Editor and runtime: play/pause/refresh, run arbitrary C#, console access
  • Scene and GameObject: load scenes, create/delete objects, manage components, filter by name, tag, layer, or component
  • Assets and materials: create materials, inspect shaders, manage import settings
  • Packages: list, add, remove, and embed Unity packages (with async job tracking across domain reloads)
  • uGUI and UI: export a live UI hierarchy to a JSON intermediate representation (IR), build UI from IR, render it, and visually diff against a reference image
  • Introspection: describe types, search methods across the assembly, look up offline Unity docs
  • Batch and profiler: bundle multi-step commands as JSON for CI automation, read frame hierarchy

2.3 Measurement as a command

The philosophy is consistent. Before the AI assumes a play-mode result, the tool actually enters play mode and waits. Before it assumes which API exists in your Unity version, it reflects into the live assemblies. Before it guesses UI anchor numbers, it compares the built result against a reference image and corrects. This loop of replacing guessing with measurement is the tool's identity.

3. Compared with MCP - what you give up and what you gain

The best way to understand this tool is to set it beside the standard approach to the same goal, MCP (Model Context Protocol).

3.1 Unity and MCP today

As of 2026 the Unity ecosystem already has several MCP servers. Unity ships MCP integration in its official Assistant package, and community implementations like CoplayDev/unity-mcp and CoderGamester/mcp-unity bridge the editor to Claude, Cursor, Codex and more. The idea is the same: put Unity behind MCP and the agent can query the project instead of hallucinating it, asking which scene is active and which objects, components, and packages exist, cutting hallucination and saving tokens. hera-agent-unity has the same goal.

3.2 What differs is the delivery

The difference is in "how you deliver that context." MCP servers usually require a Python runtime, a FastMCP-style framework, a resident process or relay, and per-client config files. hera-agent-unity drops the whole middleware layer and leaves only a single binary and stateless HTTP. Here is the contrast as I read it (per the public docs).

Itemhera-agent-unity (CLI)Typical Unity MCP
InstallSingle binary + UPM packagePython, framework, config files
Runtime depsNoneRelay, resident process
CallerAny agent or script with a shellMostly MCP clients
Domain reloadStateless via filesystem busNeeds reconnect logic
Standards and governanceWeak (direct calls)Strong (protocol, permission model)

3.3 The hard problem statelessness solves

One design point worth noting is domain-reload resilience. Unity reloads the domain when it recompiles scripts, and in that moment in-memory state like an HTTP server is wiped out entirely. The MCP approach loses its connection at that instant, which makes reconnect logic complex. hera-agent-unity sidesteps this with a filesystem-based cross-process bus of heartbeat files and result files. Even if the server is destroyed, the files survive, and an editor-init hook reattaches the watcher. Putting state in files rather than memory meshes well with the physiology of a Unity editor that dies and respawns on every compile. I see this as the cleverest part of the tool.

4. Measurement-based UI - the ui_doc pipeline

UI is where AI guesses wrong most often. Anchors, pivots, colors, and spacing cannot be judged from code alone. hera-agent-unity's ui_doc pipeline meets this head-on with measurement.

4.1 A loop that removes guessing

The flow goes like this. Export a live UI to a JSON IR, apply that IR under a parent and build it, capture it to PNG, sample the actual hex colors from a reference image, and generate procedural sprites with no external dependency. The agent builds a design on top of real project structure, renders exactly what it built, diffs against the target image, and corrects itself.

4.2 Why it matters

This loop turns "a human eyeballing and fixing every AI-built UI" into the agent's own self-correction loop. It renders even overlay canvases that screenshots miss, and it takes colors from measured pixel values rather than guesses. In a domain like game UI where pixel-level accuracy matters, reducing "look and fix" to a single tool call is practical. That said, the quality of the visual diff hinges on the reference image and the comparison algorithm, so I note that it is not a silver bullet.

5. Token economy and custom tools

The practicality of an agent tool ultimately resolves into cost. Two design choices stand out.

5.1 Keep responses light

By the public smoke test, it is around 26 tokens per call on average, and 88% of the cost comes not from the response but from the code the agent writes. This suggests the tool is designed not to eat context with verbose responses. In an agent loop, bloated tool responses pollute context every step and inflate cost, so keeping responses compact is a sensible priority. (These figures are vendor-provided, so it is safest to measure them on your own workload.)

5.2 Extend tools in one line

The other choice is extensibility. A C# class annotated with the [HeraTool] attribute is auto-discovered and becomes callable, with no code generation and no separate registration. In game development, where every project has its own workflows, the ability for a team to add their own tools on the spot extends the tool's lifespan. It becomes a channel to expose in-house pipelines that standard commands cannot reach to the agent.

6. A real case - an indie game driven by AI

One clue to a tool's credibility is what its author built with it. Per the repo, the author developed a solo indie game called NoMoreRolls primarily with this tool. In a project with a three-tier architecture and several combat systems, the AI agent drove the live editor directly rather than generating code blind - scene composition, component wiring, and play-mode iteration among the examples.

My reading is this. The value of this case is not the marketing line "AI made a game," but the evidence that a measurement-based loop actually ran at indie scale. Indie and small-scale development values friction-free speed over governance, and is an environment where a single developer iterates fast with an agent. A CLI-based, dependency-free approach targets exactly that grain.

7. Limits and cautions

Listing only the upsides would be dishonest. The CLI approach does not beat MCP on every front.

7.1 The gap in standards and governance

MCP provides not just a transport but standardized tool discovery, a permission model, and ecosystem compatibility. In 2026 Unity is moving toward an official AI Gateway that treats connectivity, permissions, and enterprise safety as design-time concerns, not afterthoughts. For teams where multi-client approval, auditing, and org-level control matter, a standard path is safer than direct CLI calls. The simplicity of hera-agent-unity also means the absence of these governance mechanisms.

7.2 The double edge of arbitrary C# execution

Being able to run arbitrary C# is powerful but also means a wide permission boundary. If the agent can run anything in the editor, one wrong command can corrupt project state. You must put in safeguards yourself on the operations side - version control and backups, plus human confirmation before risky actions. With no standard permission model, more responsibility falls on the user.

7.3 The limit of verification

The technical description here is based on public docs and writeups. Claims like token figures, domain-reload resilience, and visual-diff accuracy suggest a direction, but reliability on your project, Unity version, and agent combination must be verified directly. As a young open-source project, ecosystem maturity and long-term maintenance are also unknowns.

8. Conclusion - what it means for game-dev AI

The message hera-agent-unity sends goes beyond a single tool. As of June 2026 it clearly shows that the real bottleneck for AI coding agents is not the model's intelligence but the accuracy of the reality the model sees. The more an environment decides state at runtime, like a game engine, the more a channel that forces the agent to "measure, not guess" decides output quality.

Here are three practical lessons as I sum them up.

8.1 Give the agent a measurement channel

In Unity or any environment, the first thing to do when wiring up an AI agent is to let the model query the project's real state. MCP or CLI, the means is secondary. The crux is whether a measurement path that reduces hallucination exists. Without it, even a smarter model writes code toward the old Unity.

8.2 Choose MCP vs CLI by workload

For a single developer or small indie, a friction-free, dependency-free CLI approach favors fast iteration. Conversely, for teams where multi-client, permission management, and auditing matter, standard MCP or the official gateway is safer. The answer is not a single method but a per-workload placement. The two are less competitors than options aimed at different friction points.

8.3 Design safeguards alongside the automation

The more the agent drives the editor directly, the larger the blast radius of one wrong move. Version control, frequent commits, confirmation before risky actions, and dry-runs for batch automation should be designed with the same weight as adopting the tool. Even if a measurement-based approach raises accuracy, the permission boundary is still a human job.
