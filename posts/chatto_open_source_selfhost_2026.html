서론: Chatto가 왜 지금 주목받는가

2026년 7월 8일, 독일 개발자 헨드릭 만스(Hendrik Mans)가 만든 그룹·팀 채팅 애플리케이션 Chatto가 오픈소스로 전환됐다는 소식이 개발자 커뮤니티에 퍼졌다. 제목만 보면 또 하나의 AI 챗봇이나 LLM 프런트엔드가 오픈소스로 공개된 줄 오해하기 쉽지만, 원문과 GitHub 저장소를 직접 확인한 결과 Chatto는 그런 종류가 아니다. Slack, Microsoft Teams, Discord와 같은 자리를 놓고 경쟁하는 셀프호스팅 그룹 채팅 도구다.

본인이 이 토픽에 주목한 이유는 단순하다. "오픈소스로 전환된 셀프호스팅 채팅 앱"이라는 헤드라인 뒤에는, AI 열풍 속에서 오히려 다시 부상하고 있는 오래된 질문 - 팀 커뮤니케이션 도구를 남의 클라우드에 맡길 것인가, 내가 소유할 것인가 - 가 그대로 걸려 있기 때문이다. 이 글은 원문과 저장소, 관련 보도를 교차 확인해 Chatto의 실체를 먼저 정리하고, 그 위에서 오픈소스·셀프호스팅의 가치와 현실을 본인 관점으로 분석한다.

1. Chatto는 정확히 무엇인가 - AI 챗봇이 아니라 팀 채팅 앱

1.1 무엇을 표방하는가

GitHub 저장소 chattocorp/chatto의 설명을 보면 Chatto는 팀과 커뮤니티를 위한, 무료로 손쉽게 셀프호스팅할 수 있는 채팅 애플리케이션이라고 스스로를 정의한다. 텍스트 그룹 메시징은 물론 화면 공유를 포함한 음성·영상 통화까지 지원한다. UI는 Slack, Teams, Discord 사용자가 낯설지 않게 느끼도록 설계됐고, 만든 이는 반응 속도를 핵심 차별점으로 내세운다. 새로운 상호작용 모델을 제시하는 혁신형 제품이 아니라, 빠르고 안정적인 실용형 대안을 표방하는 셈이다. 이 포지셔닝은 그 자체로 흥미롭다. 요즘 화제가 되는 오픈소스 프로젝트 다수가 AI 관련인 상황에서, Chatto는 오히려 AI 이전 시대의 숙제 - 무겁고 비싸고 데이터 주권이 불투명한 그룹 채팅 SaaS - 를 다시 겨냥한다.

1.2 기술 스택과 배포 형태

저장소 언어 구성을 보면 Go가 백엔드(약 40퍼센트대), TypeScript·Svelte가 프런트엔드(약 50퍼센트대)를 차지한다. 공개된 기술 설명에 따르면 백엔드는 Go로 작성된 protobuf 기반 API로 실시간 메시징을 처리하며, 메시지 브로킹과 스트림 영속화에는 NATS를, 음성·영상·화면 공유에는 LiveKit(Apache-2.0)을, 첨부파일 저장에는 S3 호환 오브젝트 스토리지를, 푸시 알림에는 Web Push/VAPID를 쓴다. 가장 눈에 띄는 설계 선택은 배포 방식이다. 최소 구성에서는 외부 데이터베이스·메시지 브로커·캐시 서버 없이 실행 파일 하나가 자체 프런트엔드까지 서빙하며 곧바로 동작한다. 리눅스(x86_64/ARM64), macOS, 윈도우용 바이너리가 제공돼 "일단 켜서 써 본다"의 문턱을 극단적으로 낮췄다. 다만 이는 최소 구성 이야기이고, 프로덕션 단계에서 NATS·LiveKit·S3·Web Push까지 갖추면 이야기가 달라진다는 점은 4장에서 따로 짚는다.

2. 오픈소스·셀프호스팅이 주는 가치

2.1 데이터 소유와 프라이버시

Chatto는 모든 개인정보·채팅 데이터를 사용자별 키로 저장 시 암호화하고, 계정을 삭제하면 해당 키를 파기해 데이터를 복구 불가능하게 만든다고 밝힌다. 다만 정확히 구분해야 할 지점이 있다. 통화는 LiveKit을 통해 진짜 종단 간 암호화(E2EE)되는 반면, 텍스트 메시지 자체는 완전한 E2EE가 아니라 저장 데이터 암호화(encryption at rest) 방식이다. 서버 운영자가 검색·모더레이션 등을 위해 평문에 접근할 여지가 구조적으로 남아 있다는 뜻이다. Matrix나 Signal급 메시지 E2EE를 기대한다면 이 차이를 반드시 인지해야 한다. 다만 셀프호스팅 자체가 주는 가치는 암호화 방식과 별개다. 데이터가 애초에 제3자 서버에 저장되지 않고 본인 인프라 안에 머문다는 사실 자체가 관리형 SaaS 대비 통제권의 원천적 차이를 만든다.

2.2 락인 회피 - AGPL과 셀프호스팅 이전 옵션

Chatto의 라이선스 구성은 눈여겨볼 만하다. 기본은 AGPL-3.0-or-later이고, 독립 프런트엔드·연동·문서·예제 일부에는 Apache-2.0 예외가 붙는다. AGPL은 수정본을 네트워크 서비스로 운영해 타인에게 제공할 경우 소스 공개 의무가 따르는 강한 카피레프트 라이선스다. 이는 개발사가 향후 폐쇄형으로 선회하거나 코드베이스를 잠그기 어렵게 만드는 구조적 장치로 읽힌다. 게다가 Chatto Cloud(관리형 호스팅)에 대해서도 언제든 셀프호스팅으로 내보낼 수 있다는 방침이 명시돼 있다. 관리형 서비스를 쓰다가도 마음이 바뀌면 데이터를 들고 자체 서버로 옮길 수 있다는 뜻이며, 벤더 락인을 구조적으로 낮추는 설계다. 다만 라이선스가 락인을 낮추는 것과 실제 데이터 이관 도구가 매끄럽게 성숙해 있는 것은 별개 문제이므로, 이 부분은 제품이 1.0에 가까워지며 검증돼야 할 대목이다.

2.3 비용 구조

셀프호스팅의 직접적 이득은 좌석당 과금이 사라진다는 점이다. Slack이나 Teams처럼 인원수에 비례해 매달 청구되는 구조 대신, 비용이 본인이 이미 보유했거나 임대한 서버 자원으로 옮겨간다. 소규모 팀이라면 최소 구성만으로도 충분해 사실상 서버 임대비 정도로 운영이 가능하다. 다만 팀이 커지고 통화·화면공유·첨부파일까지 활발히 쓰면 NATS·LiveKit·S3 등 부가 인프라 비용과 그것을 관리할 사람의 시간이 숨은 비용으로 따라붙는다. 무료라는 말은 소프트웨어 라이선스 비용에 한정된 이야기이지, 총소유비용까지 0이라는 뜻은 아니다.

2.4 커스터마이징의 실제 한계

오픈소스라는 사실이 곧 자유로운 커스터마이징을 보장하지는 않는다. 외부 보도에 따르면 Chatto는 이 글 작성 시점 외부 기여(pull request)를 받지 않고 있다고 알려졌다(저장소에는 pull request 6건, 열린 이슈 151건이 관측된다). 즉 코드를 들여다보고 포크해서 직접 고칠 자유는 있지만, 자신의 수정을 본체에 반영해 커뮤니티와 공유하는 통로는 아직 제한적이다. 초기 단계 프로젝트에서 흔한 선택이지만, "오픈소스니까 커스터마이징이 쉬울 것"이라는 기대와는 다소 거리가 있다는 점을 짚어 둘 필요가 있다.

3. 관리형 서비스(Chatto Cloud)의 편의 vs 셀프호스팅

개발사는 셀프호스팅과 별개로 Chatto Cloud라는 관리형 유럽 호스팅 서비스를 준비 중이다. 자동 스케일링, 야간 백업, 무중단 업데이트를 제공하며, 부가 구독이나 광고 없이 순수 호스팅 요금만 받는다는 방침을 밝혔다. 이는 셀프호스팅의 근본 딜레마를 정확히 겨냥한다. 데이터를 자체 인프라에 두고 싶지만 NATS·LiveKit·S3·업데이트까지 직접 챙길 여력은 없는 팀이 분명히 존재하기 때문이다. 본인이 보기에 이 구도는 합리적이다. 완전한 자체 운영과 완전한 위탁 사이에 다양한 팀의 리소스 수준이 존재하고, Chatto는 그 스펙트럼 양 끝에 옵션을 두고 있다. 다만 Chatto Cloud는 2026년 7월 기준 공개 베타 전 단계이며 구체적 가격이 공개되지 않아, 관리형 옵션의 실제 경쟁력은 가격표가 나온 뒤에야 판단할 수 있다.

4. 셀프호스팅 도입의 현실 - 운영·업데이트·보안 부담

4.1 실행 파일 하나의 함정

실행 파일 하나만 켜면 끝이라는 소개 문구는 진입 장벽을 낮추는 데는 성공하지만, 이것이 프로덕션 운영의 전부라고 받아들이면 곤란하다. 실제 팀 규모에서 통화 품질, 알림 안정성, 첨부파일 저장 신뢰성을 확보하려면 결국 NATS·LiveKit·S3·Web Push 각각을 별도로 구성하고 모니터링해야 한다. 도커 컴포즈로 어느 정도 자동화할 수 있지만, 장애가 났을 때 어느 구성 요소가 문제인지 진단하는 역량은 여전히 운영자 몫이다.

4.2 0.x 시절의 리스크

Chatto는 이 글 작성 시점 버전 0.4.x로, 프로덕션에 쓸 만한 수준이라고 소개되지만 정식 1.0까지는 6~12개월이 더 걸릴 것으로 예상된다고 알려졌다. 즉 1.0 전까지는 호환성이 깨지는 변경이 발생할 수 있다는 뜻이다. 셀프호스팅 팀이라면 업그레이드 시마다 릴리스 노트를 확인하고, 필요하면 스테이징 환경에서 먼저 검증하는 습관을 들여야 한다. SaaS라면 이런 부담이 대부분 벤더 쪽으로 넘어가지만, 셀프호스팅은 이 검증 비용을 팀이 그대로 떠안는다.

4.3 보안 감사 부재

Chatto는 프라이버시와 보안을 강하게 내세우지만, 이 글 작성 시점 기준 공개된 제3자 보안 감사 결과는 확인되지 않았다. 저장 데이터 암호화, 통화 E2EE 같은 설계 의도는 명확하나, 그 구현이 독립 검증을 거쳤는지는 아직 알 수 없다. 신생 오픈소스 프로젝트 대부분이 겪는 공통 리스크이며, 민감한 조직 커뮤니케이션을 맡기기 전에 최소한 자체 코드 리뷰나 침투 테스트를 검토해 볼 가치가 있다.

5. 유사 오픈소스 대안과 비교

셀프호스팅 그룹 채팅 시장에는 이미 여러 성숙한 오픈소스 대안이 있다. Mattermost는 오랜 기간 검증된 Slack 대체재이지만 SSO 같은 기능이 유료 등급에 묶여 있는 경우가 있고, Chatto는 이런 기능을 기본 제공하는 대신 아직 플러그인 생태계가 얕다. Zulip은 토픽 기반 스레딩으로 비동기 소통에 강점이 있어, 실시간성보다 정리된 논의를 중시하는 팀에는 여전히 Zulip이 나은 선택일 수 있다. Rocket.Chat은 옴니채널 고객 대응 기능까지 포괄해 세일즈·고객지원 조직에 적합하지만 그만큼 무겁다. Matrix/Element는 서버 간 연합과 진짜 메시지 E2EE를 지원해 개방형 프로토콜을 중시하는 커뮤니티에 강하지만, Chatto가 강조하는 속도와 단순함에서는 상대적으로 무겁다는 평가가 있다. 정리하면 Chatto의 자리는 연합이나 옴니채널 같은 무거운 기능 없이, 빠르고 가벼운 UI로 Slack급 경험을 셀프호스팅하고 싶은 팀이라는 좁지만 뚜렷한 틈새다.

6. 어떤 팀에 적합한가

본인 결론은 이렇다. 좌석당 과금 SaaS의 비용·데이터 주권 문제에 지쳤고, 통화·화면공유까지 한 번에 해결하고 싶으며, 초기엔 단일 바이너리로 가볍게 시작해 필요하면 프로덕션급으로 키워갈 수 있는 소규모~중견 팀에 Chatto는 매력적인 선택지다. 특히 유럽 등 데이터 거주지 규정이 중요한 조직, 혹은 관리형(Chatto Cloud)과 셀프호스팅 사이를 나중에 자유롭게 오가고 싶은 팀에 라이선스·이관 정책이 유리하게 작용한다. 반대로 외부 커뮤니티와 서버 간 연합이 필요하거나, 메시지 자체의 완전한 E2EE가 필수 요건이거나, 방대한 서드파티 통합·플러그인 생태계가 있어야 하는 대기업이라면 각각 Matrix, Signal 계열, Mattermost나 Slack이 더 안전한 선택이다. 그리고 어느 경우든, 아직 1.0 이전 소프트웨어라는 점은 도입 규모와 무관하게 감안해야 한다.

결론

2026년 7월 기준으로 Chatto는 AI 열풍 속에서 오히려 AI 이전 시대의 오래된 질문 - 팀 커뮤니케이션 도구를 어디에 둘 것인가 - 를 다시 던지는 프로젝트다. 단일 바이너리로 시작할 수 있는 낮은 문턱, AGPL 기반의 락인 회피 설계, 관리형·셀프호스팅을 오갈 수 있는 유연성은 분명한 강점이다. 다만 완전한 메시지 E2EE는 아니라는 점, 프로덕션 확장 시 운영 복잡도가 커진다는 점, 아직 외부 기여를 받지 않는 초기 생태계라는 점, 독립 보안 감사가 없다는 점은 도입 전에 냉정하게 따져야 할 현실이다. 결국 선택은 무엇을 위해 셀프호스팅하는가에 달려 있다. 데이터 소유와 비용 통제가 목적이라면 Chatto는 지금도 시도해 볼 가치가 있고, 완전한 암호화나 성숙한 생태계가 최우선이라면 조금 더 지켜보거나 다른 대안을 함께 검토하는 편이 합리적이다.
