Postgresで耐久性のあるワークフローを作る 2026 - 専用キューなしで信頼性を確保

本当にKafkaは必要か - すでにあるPostgresだけで信頼性の高いバックグラウンドジョブを作る

2026年5月31日 IT・技術

序論：信頼性の高いワークフローに本当にKafka・Temporalは必要か

「バックグラウンドジョブを信頼性高く処理するには、メッセージキューが必要だ」。多くの開発者がほとんど反射的に受け入れる命題です。メールを送り、決済後処理を回し、通知を送り、データパイプラインを動かす瞬間、私たちはすぐにKafkaやRabbitMQ、あるいはTemporalといった専用ツールを思い浮かべます。そしてそのために専用クラスタを立て、運用人員を割き、監視体制をもう一つ増やします。

しかし、一度立ち止まって問う価値があります。本当にそうでなければならないのでしょうか。2026年の今、ますます多くのチームが正反対の結論に至っています。すでに使っているPostgres一つだけで、耐久性のあるワークフローは十分に作れるのです。新しいインフラを追加せず、新しい障害点を作らず、新しい学習コストをチームに強いることなく。

本記事は、その可能性を少人数で素早く動く必要のあるスタートアップの視点から真剣に検討します。Postgresベースのワークフローがどのような原理で信頼性を確保するのか、どんな中核パターンがあるのか、そして何よりいつPostgresで十分で、いつ専用ツールが必要なのかをバランスよく扱います。先に結論を言えば、答えは「Postgresが万能」でも「Kafkaが正解」でもなく、データと規模の性質次第です。

この記事の一行まとめ。 多くの中小サービスで、バックグラウンドジョブの信頼性は専用ブローカーではなくPostgresのトランザクションから生まれます。ジョブ登録をビジネストランザクションにまとめ、SKIP LOCKEDでワーカーを分配し、冪等性で重複を無害化すれば、新しいインフラなしで耐久性が手に入ります。

1. 「Durable Workflow」とは - 耐久性のある実行の定義

本格的な議論の前に用語を整理します。「耐久性のあるワークフロー（durable workflow）」とは何でしょうか。核心は文字通り耐久性（durability）です。一度始まったジョブが、サーバーが落ちようと、プロセスが再起動しようと、ネットワークが切れようと、最終的に最後まで実行されるか、少なくとも失われずに再試行されるという保証です。

より具体的に言うと、耐久性のあるワークフローは次の性質を持ちます。

  • ジョブの消失なし：一度受け付けたジョブは、いかなる障害でも消えません。ディスクに安全に記録されます。
  • 最低一回実行（at-least-once）：ジョブは少なくとも一度は必ず実行されます。途中でワーカーが落ちても別のワーカーが引き継ぎます。
  • 中断後の再開：実行中に止まっても、最後に記録された地点から続けるか、安全に最初から再試行できます。
  • 状態の永続性：ジョブの進行状態が揮発性メモリではなく永続ストレージに残ります。

ここで決定的な洞察が現れます。これらの性質は実はリレーショナルデータベースがすでに提供しているACID保証とほぼ正確に重なるのです。「コミットされれば生き残る」は耐久性（D）、「同時作業が互いを壊さない」は分離性（I）、「全か無か」は原子性（A）。ワークフローエンジンが苦労して作ろうとする保証の多くを、Postgresは30年以上磨いてきた機能でそのまま提供します。

2. なぜPostgresか - すでにあるDBで十分な理由

では、なぜほかでもなくPostgresなのでしょうか。理由は三つに集約されます。トランザクション、耐久性、そして単純さです。

2.1 トランザクション - 信頼性の土台

Postgresの最強の武器はトランザクションです。ビジネスデータの変更とバックグラウンドジョブの登録を一つのトランザクションにまとめられる点が核心です。たとえば「注文を作成し → 確認メール送信ジョブを登録」という二つの動作を一つのトランザクションで処理すれば、両者は一緒に成功するか一緒に失敗します。注文はできたのにメールジョブが抜ける、ということが構造的に不可能になります。専用ブローカーを使うとまさにこの地点、つまり「DBのコミットは成功したがメッセージの発行は失敗した」という隙間が生まれますが、Postgres内部にジョブを置けばその隙間そのものが消えます。

2.2 耐久性 - コミットされればディスクに残る

PostgresはWAL（先行書き込みログ）を通じて、コミットされたデータをまずディスクに安全に記録します。サーバーが突然落ちてもコミット済みのジョブは復旧されます。インメモリキューが障害時に失いうる「最後の数件」を、Postgresは失いません。ジョブの信頼性がそのままデータベースの信頼性と等しくなります。

2.3 単純さ - 運用すべきシステムが一つだけ

現実的には最大の利点かもしれません。ジョブキューをPostgresに置けば、運用すべきシステムが増えません。バックアップ、監視、障害対応、セキュリティパッチを、すでに行っているデータベース一つにすべて吸収できます。新しいブローカーの学習も、新しい障害モードも、新しいオンコール負担もありません。少人数チームにとって、この「一つで完結する」単純さは、しばしばスループットの数値よりはるかに価値があります。

3. Postgresベースのワークフローの5つの中核パターン

理論は十分です。実際にPostgresで信頼性の高いワークフローを組むとき繰り返し登場する五つの中核パターンを、私なりに整理しました。この五つを理解すれば、実質的に半分は終わったようなものです。

3.1 ジョブテーブル（Job Table）

すべての出発点です。処理すべきジョブを一行ずつ収めるテーブルを作ります。状態（待機/処理中/完了/失敗）、ペイロード（JSON）、リトライ回数、予約実行時刻などのカラムを置きます。ジョブがそのままデータ行になるので、SQLで照会・フィルタ・集計が自由にできます。

3.2 トランザクショナルアウトボックス（Transactional Outbox）

ビジネス変更とジョブ登録を同じトランザクションにまとめるパターンです。外部に送るイベントを直ちに発行せず、同じDBのアウトボックス（ジョブ）テーブルにまず記録します。別のワーカーがそのテーブルを読んで実際の発行を担当します。こうすることで「DBはコミットされたのにイベントは消えた」という二重書き込み問題が消えます。

3.3 SELECT FOR UPDATE SKIP LOCKED

複数のワーカーが同じジョブテーブルから競合なくジョブを取得できるようにするロック技法です。すでに別のワーカーがロックした行はスキップし、ロックされていない次の行だけを取得します。ワーカー同士が待ち合ったり同じジョブを重複取得したりすることがなくなり、きれいな並列分配が可能になります。Postgresジョブキューの心臓部です。

3.4 冪等性（Idempotency）

最低一回実行の保証は、すなわち「同じジョブが二度実行されうる」という意味でもあります。したがってジョブハンドラは二度実行されても結果が同じになるよう冪等に設計する必要があります。冪等性キー（例：注文ID＋ジョブ種別）をユニーク制約として掛け、重複した副作用を遮断するのが定石です。

3.5 リトライ（Retry）とバックオフ

一時的な失敗（ネットワークエラー、外部APIタイムアウト）は自然なことです。ジョブ行にリトライ回数と次回試行時刻を持たせ、失敗したら指数バックオフで再予約します。定めた回数を超えたらデッドレター（dead-letter）状態に移し、人が検討するようにします。この四つ（リトライ・バックオフ・上限・デッドレター）が失敗管理の標準構成です。

4. コード例 - 簡単なジョブキューを作る

パターンは実際のコードで見るとずっと明確になります。最も単純なジョブキューをSQLと疑似コードで描いてみます。まずジョブテーブルです。

CREATE TABLE jobs (
    id           BIGSERIAL PRIMARY KEY,
    kind         TEXT        NOT NULL,            -- ジョブ種別 (例: send_email)
    payload      JSONB       NOT NULL,            -- ジョブデータ
    status       TEXT        NOT NULL DEFAULT 'pending', -- pending/running/done/failed
    run_at       TIMESTAMPTZ NOT NULL DEFAULT now(),     -- 予約実行時刻
    attempts     INT         NOT NULL DEFAULT 0,  -- 試行回数
    max_attempts INT         NOT NULL DEFAULT 5,
    idem_key     TEXT        UNIQUE,              -- 冪等性キー
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ワーカーが次のジョブを速く見つけるための部分インデックス
CREATE INDEX idx_jobs_ready
    ON jobs (run_at)
    WHERE status = 'pending';

ジョブ登録はビジネスロジックと同じトランザクションの中で起こります。これがトランザクショナルアウトボックスの核心です。

BEGIN;
  -- 1) ビジネス変更
  INSERT INTO orders (user_id, amount) VALUES (42, 19900);
  -- 2) 同じトランザクションでジョブ登録
  INSERT INTO jobs (kind, payload, idem_key)
  VALUES ('send_email', '{"order_id": 1001}', 'email:order:1001');
COMMIT;  -- 両者は一緒にコミットされるか一緒にロールバックされる

ワーカーは次のような疑似コードでジョブを取得します。ここでSKIP LOCKEDが登場します。

繰り返し:
    トランザクション開始
      ジョブ = 次の準備済みジョブ1件をSKIP LOCKEDでロックして取得
      ジョブがなければ: 少し待って続行
      ジョブ状態を 'running' に、attempts += 1
    コミット

    試行:
      ハンドラ実行(ジョブ.payload)   # 冪等に設計
      ジョブ状態を 'done' に
    失敗時:
      attempts >= max_attempts なら 'failed'(デッドレター)
      そうでなければ run_at = now() + バックオフ、状態 'pending' に戻す

核心は、これらすべてが普通のSQLとトランザクションで完結する点です。新しいインフラも、新しいプロトコルもありません。すでに知っている道具で信頼性を組み立てるのです。

5. SKIP LOCKEDを使った並行処理

五つのパターンの中でも最も魔法のように感じられるのがSKIP LOCKEDです。もう少し深く覗く価値があります。

複数のワーカーが同時に同じジョブテーブルから仕事を取りに行くと想像してみましょう。素朴にSELECT ... FOR UPDATEだけ使うと、ワーカーBはワーカーAがロックした行を取ろうとしてロックが解放されるまで止まってしまいます。ワーカーが増えるほど互いを待つ渋滞がひどくなります。事実上直列化されるのです。

ここにSKIP LOCKEDを加えると動作が完全に変わります。

SELECT id, kind, payload
FROM jobs
WHERE status = 'pending' AND run_at <= now()
ORDER BY run_at
FOR UPDATE SKIP LOCKED
LIMIT 1;

今やワーカーBは、ワーカーAがすでにロックした行に出会っても待たず、そのままスキップして次のロックされていない行を取ります。結果として、N個のワーカーがN個の異なるジョブを同時に、衝突なく、重複なく取得します。ロック待ちが消えるので、ワーカーを増やすほどスループットが線形に近く増加します。

SKIP LOCKEDは「Postgresをジョブキューに使えるか」という問いを「Postgresをジョブキューに使わない理由があるか」へと裏返した機能です。

この一行のロックオプションのおかげで、外部メッセージブローカーが誇っていた「競合のないジョブ分配」をPostgresの中でそのまま再現できます。それもトランザクションの安全性を一切譲ることなく、です。

6. Postgres vs 専用ツールの比較

とはいえ、Postgresがすべての専用ツールを代替するわけではありません。公正な比較が必要です。代表的な四つのツールを複雑度・スループット・適した環境の軸で整理しました。

表1. ワークフロー・メッセージングツール比較

ツール複雑度スループット適した環境
Postgres低中中小規模、単純なインフラ、トランザクション結合
RabbitMQ中高メッセージング中心、複雑なルーティング
Kafka高非常に高い大規模ストリーミング、イベントログ、ファンアウト
Temporal高高複雑な長時間ワークフロー、補償処理

表を貫くメッセージはこうです。Postgresは複雑度が最も低い一方で、スループットは「中」まで担います。そして多くのサービスが実際に必要とするスループットは、まさにその「中」の帯域の中にあります。KafkaとTemporalは強力ですが、その力には運用複雑度という値札が付きます。問題は、多くのチームが「いつか必要かもしれない」スループットのために、今この瞬間その複雑度コストを前払いしている点です。

7. いつPostgresで十分で、いつ専用ツールが必要か

核心的な問いに到達しました。境界線はどこにあるのでしょうか。私が判断基準とする信号を整理します。

7.1 Postgresで十分な信号

  • スループットが毎秒数十〜数千件規模で、急増してもその中で動く。
  • ジョブが、ジョブ登録と同じDBのデータ変更と強く結びついている（トランザクション結合が得）。
  • 運用人員が少なく、新しいシステムを増やすコストが負担になる。
  • ワークフローの段階が比較的単純（送信、後処理、通知レベル）。

7.2 専用ツールが必要な信号

  • スループットが毎秒数万〜数十万件を継続的に超える（Kafka領域）。
  • 同じイベントを複数のコンシューマーグループが独立して消費する必要がある（ファンアウト、Kafka）。
  • ワークフローが数日にわたって実行され、複雑な分岐・補償・リプレイが必要（Temporal）。
  • イベントを長期保存するログへ再び流す必要がある（Kafka）。

私の推奨は明確です。Postgresで始め、上の「専用ツール信号」が実際に点灯したときに移行してください。逆に、信号が点灯してもいないのに先回りしてKafkaを敷くのは、たいてい早すぎる最適化です。

8. 実務適用シナリオ5つ

抽象的な原則を具体的な場面に移してみます。韓国・日本のサービスでよくある五つのバックグラウンドジョブに、Postgresワークフローがどう当てはまるかです。

  • メール・SMS送信：会員登録のウェルカム、注文確認メール。送信ジョブを登録・注文トランザクションにまとめれば「登録はできたのにメールが届かない」事故が消えます。外部送信APIの失敗はリトライで吸収します。
  • 決済後処理：決済承認後の領収書発行、ポイント付与、精算記録。冪等性キーで重複付与を防ぎ、段階ごとのジョブで部分的失敗を安全に再試行します。
  • データパイプライン：夜間集計、レポート生成、外部データ同期。予約実行時刻（run_at）でスケジューリングし、重い処理を小さな単位ジョブに分けてワーカーが並列処理します。
  • 通知（プッシュ・Webhook）：大量プッシュ送信、外部システムへのWebhook。SKIP LOCKEDで複数ワーカーが分けて送り、失敗したWebhookはバックオフで再試行します。
  • 予約・スケジューリング：サブスクリプション更新、リマインダー、有効期限処理。run_atに未来時刻を入れておけば、その時点でワーカーが自然に取得します。専用のcronインフラが要りません。

五つのシナリオの共通点は、どれもKafka級のスループットやTemporal級のワークフロー複雑度を要求しないことです。そしてこの五つが、実質的にほとんどのサービスのバックグラウンドジョブの大半を占めます。

9. 性能とスケーラビリティの限界

バランスのため、Postgresワークフローの限界も正直に指摘します。このパターンは無限にスケールするわけではありません。

  • スループットの天井：ジョブキューは結局DBの書き込み負荷です。毎秒数万件以上のジョブが継続すると、同じDBの本業（サービスクエリ）と資源を奪い合います。専用ブローカーが輝く区間です。
  • テーブル膨張とバキューム：完了・失敗ジョブが溜まるとテーブルが膨れ、インデックスが肥大化します。定期的なアーカイブ（完了ジョブの削除・移管）とautovacuumのチューニングが必須です。放置すると照会が遅くなります。
  • ポーリング負荷：ワーカーが短い間隔で空のキューをポーリングすると、不要なクエリが積み重なります。LISTEN/NOTIFYで通知ベースの起床を加えると緩和されます。
  • 本業への影響：ジョブキューの負荷が中核サービストランザクションの遅延を引き起こすことがあります。負荷が大きくなれば、キューを別のPostgresインスタンスに分離するのも手です。

要点は、Postgresワークフローは「無限スケール」ではなく「十分に広い区間を単純にカバーする」解だということです。その区間を超える瞬間を認識し、移行する準備さえしておけばよいのです。

10. スタートアップ環境への適用 - インフラ単純化とコスト削減

この議論はスタートアップ環境で特に説得力を持ちます。理由があります。

第一に、人員構造です。初期のスタートアップは多くの場合、少数のフルスタック開発者がインフラまで兼ねます。KafkaクラスタやTemporalサーバーを別途立てて運用するのは、それ自体で一人分の仕事です。Postgres一つでジョブキューまで吸収すれば、運用すべきシステムが減り、オンコール負担が軽くなります。

第二に、コストです。クラウド上でマネージドKafkaや別のワークフロークラスタを動かすコストは無視できません。トラフィックがまだ小さい初期段階で、「いつかの規模」のために今そのコストを払うのは、ランウェイを削る行為です。すでに支払っているPostgresの中にジョブキューを置けば、追加インフラコストはゼロに収束します。

第三に、速度です。スタートアップの競争力はしばしば実行速度から生まれます。新しいブローカーを学習し統合する数日〜数週間を、すでに馴染みのあるSQLでジョブキューを組む数時間に置き換えられるなら、その時間はそのまま製品開発に投入されます。

現実的なアドバイス。 シード〜シリーズAの段階なら、Postgresジョブキューで始めることをお勧めします。トラフィックが検証され「専用ツール信号」が点灯した後にKafka・Temporalを導入しても遅くありません。早期導入の複雑度コストが、その利益をほぼ常に上回ります。

11. リスク - 「Postgres万能」の罠

公正を期すため、逆方向の警告も明確にしなければなりません。「Postgresで十分」というメッセージが「Postgresが万能」へと変質した瞬間、本記事は別の早すぎる決定を後押しすることになります。

Postgres万能主義の典型的な罠はこうです。

  • 限界信号を無視する：スループットが明らかに天井を打っているのに「うちはPostgresで全部やる」というプライドのために移行しないこと。このとき本業DBまで一緒に遅くなります。
  • 運用負担を過小評価する：ジョブキューをPostgresに置けばインフラは減りますが、バキューム・アーカイブ・インデックス管理・監視という新しい運用項目が生まれます。「無料」ではなく「別のコスト」です。
  • ワークフロー複雑度を無理に押し込む：数日がかりの多段補償トランザクションをジョブテーブル一つで真似ようとして、コードがスパゲッティになります。その地点がTemporalを真剣に見るときです。
  • 本業とジョブキューの資源競合：中核サービストランザクションがジョブキュー負荷に押されて遅くなっているのに、同じインスタンスに固執すること。

健全な態度は単純です。Postgresは優れたデフォルトであって永遠の正解ではありません。出発点としてはほぼ常に正しいですが、限界信号を正直に読み、適時に移行する規律が共にあってこそです。

12. 結論 + すぐに適用できる3つ

最初の問いに戻ります。ワークフローの信頼性のために本当にKafka・Temporalは必要でしょうか。多くの中小サービスで答えは「いいえ」です。信頼性の真の源は華やかなブローカーではなくPostgresのトランザクションであり、私たちはすでにそれを手にしています。ジョブをデータとして扱い、トランザクションでまとめ、SKIP LOCKEDで分配し、冪等性で重複を無害化するだけで、メッセージブローカーに劣らない耐久性が生まれます。

同時にこれは「常にPostgres」という教条ではありません。規模と複雑度が閾値を超える瞬間を認識し、適時に専用ツールへ移行するバランスが核心です。すぐに適用できる三つで締めくくります。

  1. ジョブ登録をビジネス変更と同じトランザクションにまとめよ。これ一つで、最もよくある事故であるジョブの消失が構造的に消えます。
  2. ワーカー分配はSELECT FOR UPDATE SKIP LOCKEDで実装せよ。競合のない並列処理を、外部ブローカーなしでPostgresの中でそのまま得られます。
  3. すべてのジョブハンドラを冪等に設計せよ。最低一回実行の世界で重複実行を無害にすることが、信頼性の最後の一片です。

次に「バックグラウンドジョブだからキューが必要だ」という考えが浮かんだら、一度立ち止まって問うてみてください。本当に新しいインフラが必要なのか、それともすでにあるPostgresがその仕事をもっと単純に、もっと安全にこなせるのか。

よくある質問（FAQ）

Q1. Postgresで耐久性のあるワークフローを作れますか？

はい。PostgresはACIDトランザクションとディスク永続性を保証するので、ジョブテーブルとSKIP LOCKED、冪等性キー、リトライ用カラムを組み合わせれば、信頼性の高いジョブキューとワークフローエンジンを作れます。毎秒数十〜数千ジョブ規模の中小サービスなら、専用ブローカーなしでほとんどのバックグラウンド処理を扱えます。

Q2. Kafkaは必須ですか、Postgresで足りますか？

毎秒数万件超のストリーミング、複数コンシューマーグループのファンアウト、長期保存イベントログが必要ならKafkaです。しかしメール・決済後処理・通知などの一般的な処理はPostgresキューで十分です。Postgresで始め、限界が来たら移行するのが合理的です。

Q3. SELECT FOR UPDATE SKIP LOCKEDとは何ですか？

複数のワーカーが同時にジョブを取得する際、すでに別のワーカーがロックした行はスキップし、ロックされていない次の行だけを取得させるPostgresのロックオプションです。ロック待ちや重複処理なしに競合のない並列分配を可能にします。

Q4. Temporalの代わりにPostgresを使う方が良いのはいつですか？

ワークフローが単純で、専用クラスタの運用人員が足りず、すでにPostgresを使っているならPostgresが適します。逆に数日にわたる長時間ワークフローで、複雑な分岐・補償・決定論的リプレイが必要ならTemporalが向きます。

Q5. Postgresのジョブキューはどれくらい信頼できますか？

ジョブ登録をビジネストランザクションにまとめればジョブの消失が構造的に消えます。さらに冪等性キーで重複を無害化し、リトライ・デッドレターで失敗を管理すれば、メッセージブローカーに劣らない信頼性を得ます。トランザクションこそが耐久性の土台です。
