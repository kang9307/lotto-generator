以鼠标为前提的界面漏掉了什么 - 仅用键盘也能完整操作的GUI

到达与退出这两项基本要求、焦点消失的地方，以及自动检查无法判定的部分

2026年8月30日 开发/基础设施

引言：用不了鼠标的日子来得比想象中频繁

假设手腕疼，有几天用不了鼠标。打开平时用的业务界面，只用 Tab 键往下走，多数人会在一半左右卡住。有些按钮焦点根本落不上去，进了某个区域就没有出路，而焦点此刻在哪里，屏幕上任何地方都没有显示。那个界面做得不错，评审也通过了。只不过它是建立在有鼠标这个前提上才成立。

这个话题最近在开发者社区里又转了一圈。一位开发者主张 GUI 应当仅凭键盘就能完整操作，并对终端界面在键盘操作上天然更优这一通行看法提出反驳。他的论点是 GUI 并非做不到，而是做的人把它从优先级里拿掉了，依据是 GNOME 的界面指南写明「每一个动作也应当能用键盘完成」，以及他为自己做的应用配齐快捷键的经历。鼠标在某些任务上更合适这一点，那篇文章也承认。

本文要谈的是接下来那一步。以鼠标为前提做出来的界面，具体漏掉了什么。漏的地方基本是固定的，而且大多出在状态管理而非功能上。终端那边属于性质不同的问题，这里不展开。文字栅格里本来就没有地方安放结构这件事，我在终端 UI 没有结构意味着什么里另作了整理。本文站在另一侧，讲的是明明已经有地方安放结构，却仍然用不了键盘的原因。

1. 只用键盘的人是谁

不先把范围拉开，这个话题马上就会变窄。导致只能用键盘操作的条件有四类，永久性条件只是其中之一。

  • 永久性条件 — 手抖或活动范围受限，难以准确瞄准小目标；或者不看屏幕、靠声音操作。屏幕阅读器本身就跑在键盘之上，键盘操作一旦崩掉，那条路径也会跟着崩。
  • 临时条件 — 手腕或手臂受伤、打石膏、术后恢复期。只持续几天到几周，但在此期间条件完全相同。
  • 情境条件 — 一只手抱着孩子、在没有地方放鼠标的路途中、一边共享屏幕一边讲解的演示中、光标跟不上的远程桌面、没电的无线鼠标。
  • 熟练条件 — 一天要经过同一个界面几百次的人。反复填表的工作、在列表与详情之间来回的管理后台、开发工具。对他们来说，手离开键盘再回来这一趟往返本身就是成本。

把这四类压成一句话就是：键盘操作不来自用户的属性，而来自那一刻的条件。所以「我们的用户里这样的人几乎没有」这类统计根本答不上来。统计数的只有永久性条件，另外三类早已混在样本里，却在调查中显不出来。

熟练条件与另外三类的利害完全一致。想用得更快的人和用不了鼠标的人需要的是同一样东西，而在无障碍拿不到预算的组织里，同样的工作换成生产力这个名义就能通过。

2. 基本要求有两项 - 到达与退出

在叠上花哨的快捷键之前，要确认的只有两件事：能不能进去，以及能不能出来。

前者是到达。界面上凡是要做点什么的位置，焦点都得能落上去。这里漏得最多的，是长得像按钮却不是按钮的东西。

<div class="btn" onclick="save()">保存</div>      <!-- Tab 到不了 -->
<button type="button" onclick="save()">保存</button>  <!-- 到达、激活、角色都自带 -->

两者在屏幕上一模一样，用鼠标的表现也一样。差别只在键盘上显现。这个缺陷之所以安静，原因就在这里：做的人和评审的人都用鼠标，所以盯着屏幕看再久也看不出来。

后者是退出，而这一项要致命得多。焦点进了某个区域却没有能把它带出来的按键，这叫焦点陷阱。到达失败只是一个功能用不了，退出失败则是那个位置之后的整个界面都用不了。按 Tab 在原地打转，按 Shift 加 Tab 也退不回去，剩下的选项就只有关窗口，而正在写的内容也会一起消失。

检查顺序上退出优先。够不到的按钮以后再修就好，这期间用户会找别的路径。但被困住过一次的用户，大多不会再来。

陷阱出现的位置也基本固定。

  • 从外部嵌入的组件与内嵌框架
  • 自己实现的浮层与下拉菜单
  • 焦点一离开就强行拉回去的代码
  • 为了自行处理滚动而把按键事件整个吞掉的区域。为功能而阻止事件传播，结果堵住了焦点的出口

3. 焦点看不见就等于不存在

鼠标有一个横穿屏幕的光标，键盘没有。替代那个位置的是焦点显示，所以焦点显示不是装饰，而是光标本身。显示一旦消失，用户按回车时就不知道会按到什么，而在删除或支付按钮附近，人会直接停手。

去掉焦点显示这个做法相当根深蒂固，理由也能理解。浏览器默认的轮廓与设计格格不入，而且用鼠标点完之后轮廓还留着，评审时会被指出显得杂乱。问题在于，当时给出的解法是把显示整个去掉。

/* 鼠标点击不留显示，键盘移动保留显示 */
:focus-visible { outline: 3px solid #1a73e8; outline-offset: 2px; }

除了直接去掉之外，还有两条通向同样结果的路径，实务里这两条出现得更频繁。

  • 对比过低的显示 — 轮廓颜色与背景接近，代码里有、眼睛里没有。卡片内外背景不同的界面，只用一种颜色必然有一侧被淹掉。
  • 被遮住的显示 — 固定的页头、底部的同意横条、从侧边滑入的抽屉。焦点移到了它们后面，眼睛里却什么也没发生，再按几次 Tab 才会突然冒出来。中间到底掠过了什么，无从得知。
  • 移出可视区的显示 — 横向滚动的列表或标签条上，焦点进入了看不见的区域，滚动却没有跟上。

三种情况下用户得到的结果与第一种相同。而且三种情况代码里都存在显示，所以静态检查很难抓到。

4. 顺序与画面布局对不上的时候

键盘移动是有顺序的。决定这个顺序的是元素在文档里的排列，决定画面位置的是样式。两者是不同的东西，因此会对不上。一旦对不上，用户看着屏幕也无法预测下一步会去哪里。鼠标完全没有这个问题，因为它用的是坐标而不是顺序。

改变布局的样式带来的问题

改变项目显示次序的属性、在网格上直接指定格位的排布、把方向反过来的设置，都只改变视觉顺序，移动顺序原封不动。响应式布局会更纠结：文档只有一份，而宽屏与窄屏的视觉顺序不同，那么至少有一侧必然对不上。

再叠上把 Tab 顺序设成正数这个习惯，情况会更糟。给出大于 0 的值，该元素就会被拉到整份文档自然顺序的前面。为修一个部件而加进去的一个数字，等于重新定义了整页的移动顺序。

重复区段与跳过

顺序问题的另一副面孔是重复。页头里有三十个菜单项，键盘用户在到达正文之前就要经过三十次，每换一个页面又要重来一遍。鼠标用户一次都不用付这份成本，所以做的人很难有体感。

  • 跳过链接 — 放在文档最前面、直接把焦点送到正文的链接。常见做法是平时隐藏、获得焦点时才显示，可一旦显示的样式漏掉了，焦点是过去了、画面上却什么也没有，等于形同虚设。
  • 地标区域 — 把页头、正文、侧栏、页脚用文档结构区分开，辅助技术用户就能按区域跳转。全都做成普通容器，这个手段就没有了。
  • 标题层级 — 标题按顺序排列，本身就是目录，也是移动手段。为了统一字号而把层级打乱，这个功能会一起坏掉。
  • 折叠区域 — 折叠后看不见的部分仍留在 Tab 顺序里，用户就会在看不见的地方走上很久。

5. 自己做的组件为什么危险

原生元素把行为白送给你。一个按钮元素里已经包含了进入 Tab 顺序、回车与空格激活、焦点显示、禁用状态处理，以及传给辅助技术的角色。没有人去实现，它们本来就在。

把同样的外观用普通容器重做一遍，这一切都会消失，按键行为必须从头再实现一次。实务中发生的事大致是这样：挂上点击处理，加上角色属性，再加上进入 Tab 顺序的属性。做到这一步检查工具就通过了，可是没有回车处理。焦点过去了、显示也出来了，就是按不动。

由多个部件组合的组件要求更高。下面是 W3C 的 ARIA 设计模式文档对各模式所要求按键行为的摘要。

组件原生元素自带的东西自己做时必须实现的按键行为
按钮Tab 到达 · 回车/空格激活 · 禁用处理回车与空格都要。空格还要同时阻止页面滚动
复选框 · 单选选中状态传达 · 组内方向键移动空格切换。组内用方向键移动，且只保留一个留在 Tab 顺序里
标签页列表没有（没有对应的原生元素）左右方向键在前后之间移动，到末尾循环回第一个。纵向排列则用上下方向键。Home 与 End 跳到首尾
滑块方向键逐级 · Home/End · 值的传达方向键每次移动一级，Home 设为范围内第一个值，End 设为最后一个值。Page Up 与 Page Down 大幅移动

看着这张表，判断标准自己就出来了：原生元素能做到的事不要重做。外观不满意的话，改样式几乎总比换元素便宜。

6. 模态与弹层 - 进得去、回得来、其间不外漏

叠加出现的界面，是键盘操作中最常坏的部分。要求有三条，通常只守住一条。

  • 打开时焦点必须进到里面。只打开而不移动焦点，用户就会在没意识到新东西出现的情况下继续用 Tab 走后面那层。ARIA 设计模式写明对话框打开时焦点会移到其中的元素，具体落在哪个元素依内容而定，同时要避开破坏性操作。
  • 关闭时必须回到原来的位置。关闭时不管焦点，焦点会掉到文档最顶端，下一次 Tab 便从页面最上方开始，用户等于整个丢失了刚才所在的位置。同一份文档写明，关闭时焦点通常会回到唤起对话框的那个元素。
  • 打开期间不能向后外漏。如果 Tab 不能从最后一项循环回第一项，焦点就会跑到后面那层去。常见的错误是只给背后加上对辅助技术隐藏的属性，却漏掉了 Tab 顺序的整理，结果是声音里没了、焦点上还在。

再补一点：光是焦点落上去，画面不能因此改变。用方向键在列表里逐项浏览时，如果每一项都会跳转页面或提交表单，键盘用户连挑选这个动作本身都做不成。

7. 加快捷键时产生的冲突

开始认真对待键盘操作之后，下一步就想叠上快捷键。这里会冒出另一类问题：按键是有限的，而且早有主人。

  • 浏览器占用的按键 — 标签切换、地址栏、查找、刷新、放大与缩小。把应用功能叠上去，用户就会失去其中之一。
  • 操作系统占用的按键 — 窗口切换、锁屏、截图。在一个平台上空着，不等于在另一个平台上也空着。
  • 辅助技术占用的按键 — 这是最常被忘掉的一侧。屏幕阅读器在朗读模式下把单个字符键当作自己的命令使用，比如跳到标题、跳到表格。应用把同一个字母截走，那位用户就失去了导航手段。
  • 正在输入的用户 — 单字符快捷键在文本框里打字的过程中也会触发，比如正在输入姓名却执行了保存。

标准对此给出了具体的答案。WCAG 2.2 的成功准则 2.1.4 Character Key Shortcuts（等级 A）要求，仅由字母、标点、数字或符号构成的快捷键，至少要提供关闭、重新映射、仅在获得焦点时生效三者之一。三者都不是「去掉它」，而是「让用户能够控制」的形态。

8. 自动检查抓不到的东西，以及必须由人来做的事

本文的核心在这里。键盘操作的问题，是最不容易被自动检查抓到的一类。

W3C WAI 关于选择评估工具的说明直接写了这一点：工具无法自动检查全部无障碍方面，需要人的判断；评估工具并不能判定无障碍性，只能协助判定。文中还附有警告，说工具有时会给出错误或具有误导性的结果。

工具擅长的事很清楚：对比度计算、替代文本缺失、标签与输入的关联、标识符重复，都是规则能定真假的项目。反过来，键盘操作的核心它大多判定不了。

  • 焦点是不是真的看得见 — 轮廓属性是否存在，工具看得到。可是前面提到的三条路径，也就是对比过低的显示、被遮住的显示、移出可视区的显示，都是属性存在的状态。渲染之后的遮挡与实际对比，超出了静态规则的范围。
  • 顺序说不说得通 — 移动顺序是什么，工具可以列举，但那个顺序是否保住了含义并不在判定范围内。成功准则本身要求的是「保住含义与可操作性的顺序」，而含义是否保住只有人能判断。
  • 会不会在某处被困住 — 焦点陷阱只在交互过程中出现。扫描文档结构复现不了，而如果那个界面要走好几步才能到，工具连去都去不到。
  • 组件是不是真的按得动 — 挂了角色与 Tab 顺序属性，规则检查就能通过，可没有回车处理就不会有反应。这是「通过了的失败」里最常见的形态。

所以工具是下限，不是及格线。修掉工具找出来的问题是必要的，但那一项做完并不等于得到了一个能用键盘操作的界面。

把鼠标收起来，从头到尾走一遍

能替代的方法只有实际去做，而需要的只是把鼠标从桌上拿走。笔记本还要把触控板一起关掉，因为手一伸过去，观察就结束了。对象取一条有代表性的流程即可。

看什么怎么确认失败信号
焦点位置每按一次 Tab 就用眼睛找一次在哪里哪怕只有一段说不清在哪
移动顺序先预测下一站再按下去预测经常落空。上下来回跳
退出在每个区域都按 Tab 与 Shift 加 Tab在原地打转。退不回去
叠加出现的界面打开 · 在里面绕一圈 · 用 Escape 关闭焦点漏到外面。关闭后跳回最顶端

激活对长得像按钮的东西按回车与空格焦点过去了却什么也没发生

发现的问题最好按功能缺陷记录。归到无障碍条目里就会被推成单独的工作项，而单独的工作项通常会顺延到下个季度。「保存按钮按不动」就是普通的缺陷。

9. 标准要求的是什么

到这里为止的条目，大多已经作为成功准则写进了 W3C 的网页内容无障碍指南。下面是在 WCAG 2.2 文档中确认过的、与键盘操作直接相关的准则。

编号 · 名称等级要点
2.1.1 KeyboardA所有功能都必须能通过键盘接口操作，且不要求单次按键有特定时序。依赖移动路径而非仅依赖起止点的输入属于例外
2.1.2 No Keyboard TrapA如果焦点能用键盘移到某个组件上，就必须能仅用键盘把焦点移走。若标准方式做不到，必须告知用户离开的方法
2.1.4 Character Key ShortcutsA仅由字母、标点、数字或符号构成的快捷键，必须提供关闭、重新映射、仅在获得焦点时生效三者之一
2.4.1 Bypass BlocksA必须提供跳过在多个页面上重复出现的内容块的机制
2.4.3 Focus OrderA页面可顺序导航且该顺序影响含义或操作时，焦点必须按保住含义与可操作性的顺序移动
2.4.7 Focus VisibleAA任何可用键盘操作的界面，都必须有一种能看见焦点指示的操作模式
2.4.11 Focus Not Obscured (Minimum)AA组件获得键盘焦点时，不得被作者创建的内容完全遮挡
3.2.1 On FocusA组件仅仅获得焦点，不得因此引发上下文变化

把表按顺序读下来，会发现它与前面各节完全重合。到达是 2.1.1，退出是 2.1.2，焦点显示是 2.4.7 与 2.4.11，顺序是 2.4.3，重复区段是 2.4.1，快捷键是 2.1.4。其中有六条属于等级 A 这一点也值得留意。A 是这套体系里最基础的一层，也就是说键盘操作的大部分都落在那里。

有一点必须说清楚。哪套标准对谁、在多大范围内具有强制力，因司法辖区与所涉服务而异。本文只谈技术要求，是否构成法律义务须以相关辖区的现行规定确认。不过技术要求这一侧与辖区基本无关，指向的大体是同一批条目，所以在查清规定之前，要动手的地方其实已经定下来了。

未能确认的部分

  • 各辖区法律义务的范围与适用对象。没有直接比对国家与行业层面的规定。
  • 自动检查工具能抓到全部问题中多大比例的数字。工具厂商给出的比例是有的，但没有确认到公开了测量方法与样本的中立资料，因此没有写入。
  • 与键盘无障碍相关的争议或整改要求的数量趋势。没有确认到能明确调查主体与年份的资料。
  • 非网页的桌面框架之间键盘支持水平的比较。本文条目以网页为基准，原生工具包默认提供的行为范围有所不同。

结论：鼠标是捷径，不是唯一的路

以鼠标为前提的界面漏掉的不是功能，而是状态。此刻在哪里、下一步去哪里、从这里怎么出去。鼠标用一个坐标替它代劳了这三件事，于是做的人连自己正在管理状态这件事都忘了。键盘则把这份管理要求回给界面。

所以动手的顺序要从底层开始。先消掉会被困住的地方，让焦点在哪里看得见，把移动顺序与画面对齐，再给重复区段开出一条跳过的路。到这里就是大半，快捷键排在后面。顺序反过来，得到的就是快捷键很漂亮、Tab 却用不了的界面。

这项工作的成果不只流向一个群体。手腕受伤的人、正在演示的人、一天要经过同一个界面几百次的人，需要的恰好是同一样东西。鼠标是方便的捷径，只不过通往界面的路没有理由只有这一条。
