デフォルト引数に空リストを置いたら呼び出すたびに積み上がる - Python のデフォルト値が評価される時点

「None を使え」 で止まらず、なぜこの設計がこうなっているのかまで

2026-07-31 開発/インフラ

はじめに: 二回目の呼び出しから他人のデータが混ざっていた

注文をひとつずつ受け取ってリストに入れて返す関数があった。テストは通り、最初のリクエストも正常だった。ところが二回目のリクエストの応答に 一回目の注文番号がそのまま残っていた。 三回目には前の二つが両方入っていた。データベースを調べても異常はなく、グローバル変数を探しても見つからず、キャッシュ層はそもそも付けていなかった。

犯人は関数シグネチャの一行だった。引数のデフォルト値として空リストを書いていたのである。この落とし穴は広く知られていて、検索すれば 「None を使え」 という答えが三秒で出てくる。ところがその処方だけを覚えると、同じ原因から出てくる残り二つの症状を永遠に見分けられなくなる。

この記事の軸は処方ではなく原因である。原因はたった一文だ。

デフォルト値の式は def 文を実行するときに一度だけ計算され、その結果のオブジェクトが関数に貼り付いて生きる。

「呼び出すたびに新しく作られるだろう」 という直感が間違っているのであって、リストが可変であることが原因ではない。可変性はその事実を 目に見えるようにする条件 にすぎない。この区別がなぜ重要かは、下の三つの症状を並べると見えてくる。

  • 症状 A. 空リストのデフォルトに呼び出すたび値が積もる → 原因: 定義時に一度だけ評価
  • 症状 B. デフォルトに入れた 「今日の日付」 が何日経っても同じ → 原因: 定義時に一度だけ評価
  • 症状 C. クラス本体に置いたリストが全インスタンスで共有される → 原因: クラス本体が一度だけ実行

見た目がまったく違う三つが実は同じ顔である。B は 不変型 で起きるので 「可変だから」 では説明がつかない。だからこの記事は処方の前に原因を先に立てる。

実行環境。 以下のすべての出力は Windows 10 Pro (10.0.19045) で実際に動かした結果である。インタプリタは Python 3.13.3 (tags/v3.13.3:6280bb5, 2025-04-08) [MSC v.1943 64 bit (AMD64)]、プラットフォーム識別子は win32 である。すべてのスクリプトはファイルに保存して実行した。 インデントが意味を持つ言語をシェル引数やヒアドキュメントで渡すと静かに変形する。

この記事が扱わないこと。 Python の文法一般と入門的な内容は Python 自動化入門 の連載にある。この記事は デフォルト引数の評価時点 という一点だけを最後まで掘る。実行に使った例のコードはすべて架空のものである。

1. 再現 - 三回呼ぶと三回とも違う

もっとも短い形で作った。名前を受け取ってかごに入れ、かごを返す関数である。かごを渡さなければ空のかごから始まる - と 読めるが そうではない。

python 3.13.3 / win32

--- 1-1. three calls, one function ---
call 1 -> ['apple']
call 2 -> ['apple', 'banana']
call 3 -> ['apple', 'banana', 'cherry']

--- 1-2. two unrelated callers share one list ---
order_a = ['A-1001', 'B-2002']
order_b = ['A-1001', 'B-2002']
order_a is order_b : True

1-1 は教科書的な再現である。三回の呼び出しがそれぞれ違う結果を返し、後になるほど前のものが残っている。 関数は毎回 「空のかごにひとつ入れる」 をしたように見えるが、実際には 「同じかごに入れ続ける」 をしていた。

1-2 が実務で本当に痛いほうである。互いに何の関係もない二つの呼び出し側が同じオブジェクトを受け取った。 order_a is order_b が真だということは、二つが同じリストを指す別の名前だという意味だ。ウェブのリクエストが二つこの関数を通ると あるユーザーのデータが別のユーザーの応答に混ざる。 はじめにの症状がまさにこれである。

  • 最初の呼び出しは 常に正常 である。だから単体テストが関数を一度しか呼ばなければ絶対に引っかからない
  • テストの順序を変えると結果が変わる。「うちのテストは順序に依存する」 という報告のかなりの部分がこの形だ
  • プロセスを再起動すると症状が消える。だから 「再起動したら直りました」 で終わり、また再発する
  • 例外が出ない。ログに痕跡がなくエラー率の指標も動かない

2. デフォルト値はどこにあるか - そのオブジェクトを直接取り出す

推測せずに現物を取り出そう。関数オブジェクトにはデフォルト値を入れておく場所がある。

--- 1-3. the default object itself ---
add_item.__defaults__      : (['apple', 'banana', 'cherry'],)
type of default[0]         : list
len of default[0]          : 3

--- 1-4. identity across calls ---
id(default) before call    : 1997832273600
id(returned) call 1        : 1997832273600  same: True
id(returned) call 2        : 1997832273600  same: True
id(default) after 2 calls  : 1997832273600
r1 is r2                   : True

--- 1-5. mutating through the returned reference ---
probe.__defaults__         : (['touched from outside'],)
a caller that never passed anything now sees : ['touched from outside']

1-3 が決定的である。三回の呼び出しが終わったあとに関数のデフォルト値を覗くと、その中に三つ入っていた。 「空のリスト」 と書いておいた場所にデータが積もっている。関数は本当に自分のデフォルト値を直していたのである。

1-4 がその理由を確定させる。呼び出す前のデフォルト値のアドレスと、呼び出しが返したオブジェクトのアドレスが完全に同じだ。 二回目の呼び出しも同様である。新しく作るのではなく 同じひとつを渡し続けている。

1-5 はこの構造のもっとも不快な面である。関数が返したリストを呼び出し側が外から直したところ 関数のデフォルト値が変わった。 それ以降、引数を省略したすべての呼び出し側が他人の植えた値を見ることになる。関数の中のコードをいくら読んでもこの経路は見えない。

診断のこつ。 原因不明の状態汚染に出会ったとき最初にすべきことは、疑わしい関数のデフォルト値をそのまま出力してみることだ。そこに 空であるべき場所にデータがあれば 診断は終わりである。グローバル変数を探しキャッシュを疑う前にこれを見る。この確認は一行で済み、プロセスを止める必要もない。

3. いつ計算されるのか - def 文が実行されるとき、ちょうど一度

ここから原因を直接観測する。デフォルト値の位置に 副作用のある関数呼び出し を入れると、それが何回実行されるかを目で数えられる。

--- 2-1. the default expression runs at def time, not call time ---
about to execute the def statement
    [side effect] make_default() ran
def statement finished
now calling f() three times:
make_default ran exactly once, before any call

順序をよく見よう。デフォルト値を作る呼び出しが def 文の内側で、関数を一度も呼ぶ前に実行された。 そのあと関数を三回呼んだが、その呼び出しは二度と起きなかった。

ここでよくある誤解がひとつ片付く。def は 「関数を宣言する印」 ではなく 実行される文 である。Python がその行に到達するとデフォルト値の式を左から計算し、その結果を持った関数オブジェクトを作って名前に束ねる。デフォルト値の計算は関数の本体ではなく def 文そのものの仕事だ。

--- 2-2. defaults are attached to the function object ---
g.__defaults__        : (1, [])
g.__kwdefaults__      : {'d': 2, 'e': {}}
g.__code__.co_varnames: ('a', 'b', 'c', 'd', 'e')

--- 2-3. the default is writable state ---
before : (1, [])
after  : (99, ['patched'])
g('x') : ('x', 99, ['patched'], 2, {})

2-2 は格納の構造を見せている。位置引数のデフォルト値とキーワード専用引数のデフォルト値は別々の場所に入る。 前者はタプル、後者は辞書だ。点検スクリプトを自分で書くときはこの両方を見ないと漏れが出る。

2-3 はこれが 読み取り専用のメタデータではなく書き換えられる状態 であることを示す。外からデフォルト値をまるごと入れ替えたところ、以降の呼び出しの動作が変わった。関数オブジェクトはコードとデータを一緒に持ち歩く物であり、デフォルト値はそのデータの側に属する。

  • デフォルト値は 定義する側のスコープ で計算される。あとでその名前が指す値を変えても、すでに計算されたデフォルト値は追随しない
  • デフォルト値の式は 左から右へ 計算される。前の引数のデフォルト値を後ろの引数のデフォルト式から参照することはできない
  • デコレータを被せてもこの計算はすでに終わったあとだ。デコレータは作られた関数オブジェクトを受け取る
  • モジュールをインポートした瞬間にこの計算が起きる。つまり デフォルト値の年齢はプロセスの年齢 である

4. 時間が固まる - デフォルト値に入れた今日の日付

ここからがこの記事の値打ちである。上の原理が分かれば 可変型と何の関係もない 二つ目の症状が予測できる。デフォルト値の位置に 「今の時刻」 を計算する呼び出しを入れてみた。

--- 3-1. today captured in a default never moves ---
bad  ('row0', '2026-07-31 05:25:19.168606')
good ('row0', '2026-07-31 05:25:19.569502')
bad  ('row1', '2026-07-31 05:25:19.168606')
good ('row1', '2026-07-31 05:25:19.969964')
bad  ('row2', '2026-07-31 05:25:19.168606')
good ('row2', '2026-07-31 05:25:20.370294')

--- 3-2. the frozen value, straight from __defaults__ ---
stamp_bad.__defaults__ : (datetime.datetime(2026, 7, 31, 5, 25, 19, 168606),)
same object 0.5s later : (datetime.datetime(2026, 7, 31, 5, 25, 19, 168606),)
id stays the same      : 2480663196656
datetime.now() right now: 2026-07-31 05:25:20.870691

三回の呼び出しの間にそれぞれ 0.4 秒ずつ休んだ。正しいほう (good) はマイクロ秒まで毎回違うのに、デフォルト値に入れたほう (bad) は三回とも完全に同じ時刻である。 システムの時刻は触っていない。値が更新されないだけだ。

3-2 がその理由を確定させる。関数のデフォルト値を 0.5 秒間隔で二度出力したところ 同じオブジェクトが同じ値のまま残っていた。 その間、実際の時刻は流れ続けている。最後の行がそれを示している。

--- 3-3. a date default: the day the module was imported ---
captured end date      : 2026-07-31
report_range.__defaults__: (7, datetime.date(2026, 7, 31))
date.today() now       : 2026-07-31
note: date is IMMUTABLE, yet the value is still stale
      the bug here is not mutation, it is one-time evaluation

--- 3-4. the same shape with a counter ---
{'id': 1, 'payload': 'first'}
{'id': 1, 'payload': 'second'}
{'id': 1, 'payload': 'third'}
_seq module counter    : 1   (next_id ran exactly once)

3-3 の注記がこの節の核心である。日付のオブジェクトは明らかに不変なのに値が古い。 誰もそのオブジェクトを直していない。ただインポートした瞬間の日付がそのまま刺さっているだけだ。「可変だから起きる問題」 という説明ではこの出力を解釈できない。

この症状が実務で怖い理由は 発現までに時間がかかる ことである。デプロイした日には完璧に動く。数日後の未明に 「レポートの期間がおかしい」 という報告が入り、担当者がサーバを再起動すると元に戻る。そしてまた数日後にずれる。再起動の周期が短い環境ほど発見が遅れる。

3-4 は同じ形を連番に変えたものだ。三つの行を作ったのに 番号が全部 1 である。番号の生成器はインポート時に一度回り、その結果がデフォルト値として固まった。モジュールのカウンタが 1 で止まっているのが証拠だ。

  • デフォルト値の位置に 括弧が見えたら まず疑う。呼び出し式はその場で一度実行され結果だけが残る
  • 時刻、乱数、固有識別子、設定ファイルの読み込み、接続オブジェクトの生成 - すべて同じ落とし穴にはまる
  • 「デフォルトとして現在の接続を使う」 という形は特に危ない。プロセスが生きている間ずっと最初の接続ひとつを再利用 することになる
  • 症状が デプロイ直後ではなくかなり後に 出るので、原因の指摘が見当違いの方向へ行く

5. どの型が危険か - そしてその区別の限界

ここで型ごとに分けてみよう。十二種類のデフォルト値の候補について ハッシュ可能かどうか と その場で変更できるかどうか を実際に試した。

--- 4-1. which default types can be mutated in place ---
type        hash   in-place  verdict
--------------------------------------------------------------
list        no     OK        MUTABLE  -> state leaks between calls
dict        no     OK        MUTABLE  -> state leaks between calls
set         no     OK        MUTABLE  -> state leaks between calls
bytearray   no     OK        MUTABLE  -> state leaks between calls
int         yes    Attribute immutable-> no leak, but value frozen
str         yes    Attribute immutable-> no leak, but value frozen
tuple       yes    Attribute immutable-> no leak, but value frozen
frozenset   yes    Attribute immutable-> no leak, but value frozen
bytes       yes    Attribute immutable-> no leak, but value frozen
NoneType    yes    Attribute immutable-> no leak, but value frozen
date        yes    Attribute immutable-> no leak, but value frozen
Decimal     yes    Attribute immutable-> no leak, but value frozen

真ん中の列に規則性がある。ハッシュできないものはすべてその場で変更でき、ハッシュできるものはすべてできない。 これが偶然ではない根拠が標準ライブラリの中にある。データクラスは可変デフォルトを禁じているが、その判定に ハッシュ不可能性を可変性の近似として 使うと文書に書かれている。つまり hash(デフォルト値) が例外を出せばそのデフォルトは危険だという判断は 標準ライブラリと同じ基準 なのである。

デフォルトの型ハッシュその場変更危険の種類判断
list, dict, set不可可能状態が漏れる使わないこと
bytearray不可可能状態が漏れる使わないこと
defaultdict, Counter, deque不可可能状態が漏れる使わないこと
ユーザー定義クラスのインスタンス大抵可能大抵可能状態が漏れる使わないこと (ハッシュでは弾けない)
int, float, str, bytes可能不可なしリテラルなら安全
tuple, frozenset可能不可要素が可変なら漏れる中身を確認すること
None可能不可なし推奨されるデフォルト
date, datetime, Decimal可能不可値が固まる呼び出し式なら使わないこと

この表でもっとも重要なマスは 「ユーザー定義クラスのインスタンス」 の行である。ハッシュ判定では弾かれないのに危険はそのままだ。だから ハッシュの規則は便利な近似にすぎず完全な判定ではない。 次の出力が 「不変なら安全」 という命題を正確にどこまで真にするかを示している。

--- 4-2. proof: the immutable default is REBOUND, not changed ---
bump  id-in=140731345413000 id-out=140731345413032  same=False value=1
bump  id-in=140731345413000 id-out=140731345413032  same=False value=1
bump  id-in=140731345413000 id-out=140731345413032  same=False value=1
bump.__defaults__ : (0,)  <- never moved

grow  id-in=2415089405120 id-out=2415089405120  same=True  value=[1]
grow  id-in=2415089405120 id-out=2415089405120  same=True  value=[1, 1]
grow  id-in=2415089405120 id-out=2415089405120  same=True  value=[1, 1, 1]
grow.__defaults__ : ([1, 1, 1],)  <- grew every call

二つの関数はソースがほとんど同じである。ひとつは整数のデフォルトに 1 を足し、ひとつはリストのデフォルトに要素をひとつ足す。ところが結果が正反対だ。

  • 整数の側: 演算の前後でアドレスが 変わった。 足し算の結果が新しいオブジェクトになってローカルの名前に束ね直され、関数のデフォルト値は 0 のままだ。だから三回呼んでも毎回 1 が出る
  • リストの側: 演算の前後でアドレスが 同じ。 要素を足す演算がそのオブジェクト自体を直し、関数のデフォルト値も一緒に育った
  • 同じ形の構文が 型によって再束縛にもその場修正にもなる。 これが二つの症状を分ける実際のしくみである
  • 整理すると 不変のデフォルトは 「状態が漏れない」 までしか保証しない。 「値が最新である」 ことはまったく保証しない
--- 4-3. tuple default holding a mutable member ---
call 1 -> (['x'], {})
call 2 -> (['x', 'x'], {})
call 3 -> (['x', 'x', 'x'], {})
the tuple itself never changed; its member did

--- 4-4. immutable default, still evaluated once ---
seeded.__defaults__ : (6,)
value is fixed at def time even though int is immutable
so 'immutable = safe' is only half true:
  mutable   -> shared state leaks between calls
  immutable -> value is frozen at import time

4-3 が表の 「要素が可変なら漏れる」 のマスを証明する。タプルをデフォルト値に使ったのに値が積もった。 タプル自体は一度も変わっていない。その中のリストが育ったのである。不変のコンテナは自分自身を守るだけで中身までは守らない。

4-4 は 3 節と 5 節をつなぐ。整数のデフォルト値を計算式で書いたところ、その値は定義の時点で確定した。整数は不変なので漏れる問題はないが 「一度しか計算されない」 という性質はそのまま適用される。 危険の種類が違うだけで原因はひとつだ。

6. 正しい定型 - None の番人とその周りの落とし穴

処方は簡単である。デフォルト値の位置には不変の目印だけを置き、実際のオブジェクトは関数の中で作る。 実行して累積が消えることを確認した。

--- 5-1. the None sentinel idiom ---
call 1 -> ['apple']
call 2 -> ['banana']
call 3 -> ['cherry']
add_item.__defaults__ : (None,)

--- 5-2. caller-supplied container still works ---
passed in  -> ['seed', 'apple']
passed in  -> ['seed', 'apple', 'banana']
caller list: ['seed', 'apple', 'banana']  (caller owns it, as intended)

1 節と同じ関数が今度は 三回とも要素ひとつのリスト を返す。関数のデフォルト値は None ひとつだけで、リストの生成は関数本体の中で呼び出しごとに新しく起きる。

5-2 が重要だ。この処方は 呼び出し側が自分でコンテナを渡す場合を壊さない。 渡されたリストはそのまま使われ、呼び出し側でも結果が見える。これはバグではなく 呼び出し側が自分の物を渡したのだから当然の動作 である。

--- 5-3. why 'or' is not the same as 'is None' ---
arg=[]      or-> ['a', 'DEFAULT']        is-None-> ['a']
arg=['x']   or-> ['a', 'x']              is-None-> ['a', 'x']
arg=None    or-> ['a', 'DEFAULT']        is-None-> ['a', 'DEFAULT']

--- 5-4. when None is a legitimate argument value ---
lookup('a')            : 1
lookup('b')            : None
lookup('z', None)      : None
lookup('z')            : KeyError 'z'

5-3 はよく使われる短縮形がなぜ等価でないかを見せている。最初の行で分かれる。呼び出し側が空リストを明示的に渡したのに、一方はそれを尊重し、もう一方はデフォルト値に置き換えた。 空のコンテナと 0 と空文字列がすべて偽として評価されるからである。

このずれは 例外を出さない。 「フィルタを空で送ったのに全部出てくる」 といった報告として数日後に戻ってくる。番人の判定には必ず同一性の比較を使う。

5-4 は処方そのものの限界を扱う。None が 正当な引数の値 になりうる関数なら、それを番人として使えない。出力では 「値がなくて例外」 の場合と 「値として None を受け取った」 場合が正確に分かれた。モジュールの中に専用の目印オブジェクトをひとつ作り、それと比較すればよい。

--- 5-5. copying a caller's list so you do not own their data ---
r1 tags : ['urgent', 'processed']
r2 tags : ['urgent', 'processed']
caller  : ['urgent']  (untouched)

--- 5-6. frozen empty containers as a read-only default ---
render('a')            : a({})
render('b', {'x': 1})  : b({'x': 1})
writing to the default : TypeError 'mappingproxy' object does not support item assignment

5-5 はもう一歩進んだ形だ。呼び出し側が渡したリストを関数が 黙って直さないように コピーして使う。出力では二回の呼び出しが互いに干渉せず、呼び出し側の元データもそのままである。「呼び出し側の物を関数が変えてよいか」 は別の設計判断 であり、大抵の答えは 「だめ」 だ。

5-6 は 「空のマッピング」 をデフォルト値に置きたいときの安全な形である。読み取り専用のビューをデフォルト値に置くと、うっかり直そうとした瞬間に例外が出る。直せないものを共有するのは安全だ。 共有そのものが問題なのではなく 共有されたものを直すこと が問題だったことを、この出力が改めて確認させてくれる。

7. 同じ原因の別の顔 - クラス本体の可変属性

三つ目の症状である。はじめにで予告したとおり 同じ原因がまったく違う場所に現れる。 クラス本体にリストをひとつ置いた。

--- 6-1. a mutable attribute in the class body ---
a.items : ['apple', 'banana']
b.items : ['apple', 'banana']
a.items is b.items      : True
Cart.items              : ['apple', 'banana']
id(Cart.items)          : 1409693232192
id(a.items)             : 1409693232192
'items' in a.__dict__   : False

--- 6-2. the fix: build it in __init__ ---
c.items : ['apple']
d.items : ['banana']
c.items is d.items      : False
'items' in c.__dict__   : True

別々のインスタンスを二つ作ってそれぞれひとつずつ入れたのに どちらも二つ持っている。 最後の行が正体を明かす。インスタンスにはその名前がそもそもない。 属性を読むときインスタンスになければクラスへ上がって探すので、すべてのインスタンスがクラスに貼り付いたひとつを見ていたのである。

構造はデフォルト引数とまったく同じだ。クラス本体もクラスを定義するときに一度実行され、そこで作られたオブジェクトがクラスに貼り付いて生きる。 6-2 の処方も同じである。インスタンスを作るときに新しく作れば各自が自分のものを持つ。

--- 6-3. rebinding vs mutating on a class attribute ---
p.hits : 2   q.hits : 1   Counter.hits : 0
p.log  : [1, 2, 1]
q.log  : [1, 2, 1]
the int looks per-instance because += REBINDS onto the instance
the list is shared because append MUTATES the class-level object

--- 6-4. dataclasses refuse the same shape ---
dataclass with list default : ValueError mutable default <class 'list'> for field items is not allowed: use default_factory
Good() g1.items : ['x']
Good() g2.items : []
g1.items is g2.items : False

--- 6-5. plain functions get no such protection ---
plain() -> ['x']
plain() -> ['x', 'x']
no error, no warning: dataclasses check, the interpreter does not

6-3 がこの節でもっとも紛らわしい現象を説明する。同じクラスの中で整数の属性はインスタンスごとに別々に数えられるのに、リストの属性は共有される。 コードは並んで置かれ文法も似ている。

  • 整数への加算代入は 新しい値を計算してインスタンスに束ね直す。 だからインスタンスごとに自分の値ができ、クラス側は 0 のままだ
  • リストに要素を足すのは クラスに貼り付いているそのオブジェクトを直接直す。 束ね直しが起きないので全員が同じものを見る
  • 4-2 で見た再束縛とその場修正の対比が ここでそのまま繰り返される。 関数とクラスは別の文法だが同じ規則の上に立っている
  • だから 「クラス変数は共有される」 という説明は半分しか正しくない。共有されるのはオブジェクトであり、再束縛すれば共有は切れる

6-4 で標準ライブラリがこの問題をどう扱っているかが出てくる。データクラスは可変デフォルトをそもそも拒否して例外を出す。 エラーメッセージが代替まで教えてくれる。ファクトリ関数を指定するとインスタンスごとに新しく作られ、二つのインスタンスのリストが別々のオブジェクトになった。

6-5 がこの記事でもっとも背筋の寒い部分である。通常の関数にはそうした保護がまったくない。 まったく同じ形のコードが何の警告もなく通る。データクラスが防いでくれるものを関数は防いでくれない。だから 検出を自分で付けるしかない。

8. 検出 - インタプリタは何も言わない

まずインタプリタが何をしてくれるかを確認した。答えは 「何も」 である。そしてこの環境には 専用の静的解析ツールがひとつも入っていなかった。 そこで標準ライブラリだけでスキャナを自作して回した。

$ python find_mutable_defaults.py sample_app.py
sample_app.py

  L11   MUTABLE  index(table=...)             dict literal {}
  L16   MUTABLE  dedupe(seen=...)             factory call set()
  L21   MUTABLE  buckets(store=...)           factory call defaultdict()
  L26   CALL     stamp(at=...)                time-like call now() frozen at import
  L30   CALL     window(size=...)             computed expression evaluated once at def time
  L45   CLASSATTR Worker.seen                  list literal [] shared by every instance
--------------------------------------------------------------------
findings: 7
exit=1

構文木をたどってデフォルト値の位置にあるノードの種類を見る方式である。七件が引っかかり、終了コードが 1 なのでそのまま CI に付けられる。 注目すべきは分類だ。

  • MUTABLE - リスト・辞書・集合のリテラルと内包表記、そして既知のファクトリ呼び出し。状態が漏れる側である
  • CALL - デフォルト値の位置にあるすべての呼び出し式と計算式。値が固まる側 であり、4 節で見たとおり不変型もここに引っかかる
  • CLASSATTR - クラス本体の可変属性。同じ原因なので同じ道具が捕まえる
  • 安全に書かれた関数と __init__ の中で作る形は 一件も誤検出がなかった

すでに動いているプロセスを点検するときは別の方法のほうが確実である。関数オブジェクトのデフォルト値を実行中に直接たどること だ。

--- 7-1. scanning a live module for mutable defaults ---
function               parameter    type       current value
------------------------------------------------------------------------

index                  table        dict       {}

buckets                store        defaultdict defaultdict(<class 'list'>, {})
Worker.seen            <class attr> list       []

--- 7-2. the same scan AFTER the code has run ---

------------------------------------------------------------------------

dedupe                 seen         set        {'x'}

the defaults now carry leftover data from earlier calls

二つの表を比べるのがこつである。インポート直後はすべて空だった。何度か呼んだあとに同じスキャンを回したところ デフォルト値の中に以前の呼び出しが残したデータがそのまま座っている。 これが状態漏れを目で確認するもっとも短い方法だ。

稼働中のサービスにこのスキャンを付けておけば 「今この瞬間どれだけ漏れているか」 を測れる。静的解析はソースが必要だが、この方法は 他人が作ったライブラリにもそのまま通じる。

--- 7-3. what the interpreter itself will and will not tell you ---
warnings raised by compiling a leaky def : 0
py_compile result                       : OK, no diagnostic

--- 7-4. grep-level heuristic (works anywhere, noisy) ---
  L6    def enqueue(job, queue=[]):
  L11   def index(word, table={}):
  L16   def dedupe(item, seen=set()):
misses multi-line signatures and factory calls -> use the AST scanner

7-3 がこの節の結論である。問題のある関数をコンパイルしても警告は 0 件で、バイトコードのコンパイルも何の診断もなく通る。 言語レベルの安全網がないという意味だ。この欠陥が何十年も生き残っている理由がここにある。

7-4 は道具が使えない環境の最後の手段である。正規表現でも三件は捕まえた。ただし ファクトリ呼び出しと複数行に分かれたシグネチャを見逃した。 急ぐときに使い、常設の検査は構文木のほうへ移す。

9. 意図して使う場合 - デフォルト値をキャッシュに

この動作を 知ったうえで利用する 用法がある。呼び出しの間に状態が残るという性質をそのまま使って計算結果をキャッシュするのだ。実際に動く。

--- 8-1. the deliberate version: a default used as a cache ---
fib(60)      : 1548008755920
elapsed      : 0.000050 s
cache size   : 61
cache leaks into introspection: fib.__defaults__[0][10] = 55

--- 8-2. a caller can overwrite the cache from outside ---
fib(10) normal            : 55
fib(10, {0: 0, 1: 100})   : 5500
fib(10) again             : 55
the parameter is part of the public signature; nothing hides it

8-1 はこの技法が実際に速いことを示している。再帰の計算が事実上その場で終わった。しかしキャッシュが関数のデフォルト値の位置にそのまま露出する。 最後の行では内部キャッシュの値を外から取り出して読んだ。

8-2 がこの方式を勧めない第一の理由である。キャッシュが公開シグネチャの一部なので呼び出し側が別のものを渡せる。 でたらめな初期値を渡したところ結果がまったく変わった。隠したのではなく ただ誰も使わないだろうと仮定した パラメータにすぎない。

--- 8-3b. read-modify-write on a shared default, 8 threads ---
switch interval default : 0.005
switch interval set to  : 1e-06
expected increments : 160000
observed increments : 99462
lost updates        : 60538
keys retained       : 8

第二の理由は並行性である。八つのスレッドに同じデフォルト値の辞書へ読み取り・変更・書き込みを繰り返させた。十六万回足したのに九万九千あまりしか残らず、六万回が消えた。

ここでもうひとつ重要な観測がある。既定の設定のまま回したときは消失が 0 件だった。 スレッドの切り替え間隔を既定よりはるかに小さくして初めて現れた。これがこの種のバグの怖いところである。試験機では一度も再現せず、負荷のかかった本番機で初めて現れる。 「うちの環境では問題ない」 という結論が実は 「まだ見ていない」 だったのだ。

--- 8-4. the supported alternative ---
fib2(60)     : 1548008755920
elapsed      : 0.000080 s
cache_info   : CacheInfo(hits=58, misses=61, maxsize=128, currsize=61)
signature    : None (no hidden parameter)
after clear  : CacheInfo(hits=0, misses=0, maxsize=128, currsize=0)

--- 8-5. closure: state without touching the signature ---
c1('a') -> 1  c1('a') -> 2
c2('a') -> 1
two independent instances; callers cannot reach the state

8-4 が代替である。標準ライブラリのキャッシュデコレータを使えば速度は事実上同じで 足りなかったものがすべて埋まる。

  • シグネチャがきれいだ。 包まれた元の関数のデフォルト値がそもそもない。キャッシュがパラメータとして漏れ出さない
  • 上限がある。 デフォルト値のキャッシュは決して空にならず無限に育つが、こちらは最大の大きさを決める
  • 観測できる。 ヒットとミス、現在の大きさをそのまま読める。キャッシュ効率を指標に出せる
  • 空にできる。 無効化の手段がある。8-3 で見た 「決して空にならない」 がここで解決する

8-5 は状態をそもそも隠したいときの形である。関数を作る関数の中に状態を置けば 呼び出し側から触れられずインスタンスごとに独立 だ。二つ作ってそれぞれ数えてみたところ互いに干渉しなかった。デフォルト引数をキャッシュに使う理由が 「状態をどこかに置きたい」 だったのなら、その場所はシグネチャではなくクロージャである。

10. 整理 - 症状から原因へ

この記事からひとつだけ持ち帰るならこの表である。左から始めて右へ読む。

遭遇する症状よくある誤診実際の原因確認方法処方
二回目の呼び出しから他人のデータが混ざる「キャッシュの問題」、「どこかのグローバル変数」デフォルト値が定義時に一度計算された関数.__defaults__ を出力None の番人
テストの順序を変えると結果が変わる「テストの分離不足」同じデフォルト値のオブジェクトを複数のテストが共有テストの間で __defaults__ を比較None の番人
再起動すると直り数日後に再発「メモリリーク」デフォルト値がインポート時点の値で固まったデフォルト値の時刻と現在時刻を比較本体でその都度計算
レポートの期間や連番が変わらない「日付ライブラリのバグ」デフォルト位置の呼び出し式が一度しか実行されないデフォルト位置に括弧があるか本体でその都度計算
インスタンスごとに違うはずの一覧が共有される「クラス変数だから仕方ない」クラス本体が一度しか実行されないインスタンス.__dict__ に名前があるかコンストラクタで作る

負荷時にだけ値がずれる「再現不能、環境のせい」共有デフォルト値に対する競合状態スレッド切り替え間隔を下げて再試行共有状態を取り除く
キャッシュが無限に大きくなる「メモリリーク」デフォルト値のキャッシュは空にならないデフォルト値の長さを定期的に出力上限のあるキャッシュに置換

表の二列目がこの記事の存在理由である。八つの症状すべてで最初の診断が見当違いの場所を指す。 キャッシュ、メモリリーク、テストの分離、日付ライブラリ、環境のせい - すべてもっともらしく、すべて間違っている。原因はひとつであり、確認はたいてい一行で済む。

11. チェックリスト

コードレビューでそのまま使えるように整理した。

  • シグネチャに =[], ={}, =set() がひとつもない
  • =defaultdict(...), =Counter(), =deque() のような ファクトリ呼び出し がない
  • デフォルト値の位置に 呼び出し式 がない - 時刻、乱数、固有識別子、設定の読み込み、接続の生成
  • デフォルト値の位置に 計算式 がない - インポート時点で固まる
  • タプルのデフォルトを使うなら 中に可変の要素がないか 確認した
  • 番人の判定に or ではなく is None を使った
  • None が正当な値になりうる引数には 専用の目印オブジェクト を作って使った
  • 呼び出し側が渡したコンテナを関数が 黙って直さない (必要ならコピーする)
  • クラス本体にリスト・辞書・集合の属性がない
  • データクラスのフィールドは ファクトリ関数 で指定した
  • キャッシュが必要ならデフォルト引数ではなく 標準のキャッシュデコレータかクロージャ を使う
  • 構文木スキャナを CI に組み込み 新規混入を止める
  • 長時間動くプロセスは 実行中のデフォルト値スキャン で残留状態を点検する
  • 並行性の検証は スレッド切り替え間隔を下げた状態 でも回してみる

11.1 してはいけないこと

  • 「可変型だけ気をつければよい」 - 不変のデフォルトも定義時に固まる。3 節がその反例だ
  • 「テストが通ったから大丈夫」 - 最初の呼び出しは常に正常である。二度目から現れる
  • 「スレッドの問題はインタプリタが防いでくれる」 - 切り替え間隔次第で現れも隠れもする
  • デフォルト値を外から上書きして直すこと - 2-3 で可能だと示したが、それは症状をいじる行為だ
  • 再現しない状態汚染を環境のせいにすること - まずデフォルト値を出力してみる
  • この落とし穴を 「有名な落とし穴」 としてだけ覚えること - 原因を知らなければ 3 節と 7 節の症状は永遠に別の問題に見える

# Python のデフォルト引数 — 定義時評価チェックリスト

> 出典: braindetox.kr — デフォルト引数に空リストを置いたら呼び出すたびに値が積み上がった
> 根拠: Windows 10 Pro (10.0.19045) / Python 3.13.3 (MSC v.1943, 64bit) で実行検証
> このファイルをそのまま AI に貼り、「この基準でうちのコードベースを点検して」と書けば使えます。

## 0. すべての出発点 — 一文で

**デフォルト値の式は def 文を実行するときに一度だけ評価され、その結果のオブジェクトが関数に貼り付いて生き続ける。**

呼び出しごとに再計算されることはない。この一文が、以下の三つの症状に共通する原因である。

| 症状 | 表向きの原因 | 本当の原因 |
|---|---|---|
| 空リストのデフォルトに値が積もる | リストが可変だから | 定義時に一度だけ評価 |
| デフォルトの今日の日付が更新されない | 日付キャッシュの不具合 | 定義時に一度だけ評価 |
| クラス属性がインスタンス間で共有される | クラス変数だから | クラス本体が一度だけ実行 |

## 1. 三行で再現する

```python
def add_item(name, basket=[]):
    basket.append(name)
    return basket

print(add_item("apple"))    # ['apple']
print(add_item("banana"))   # ['apple', 'banana']
print(add_item("cherry"))   # ['apple', 'banana', 'cherry']

print(add_item.__defaults__)
# (['apple', 'banana', 'cherry'],)
```

デフォルト値は `関数.__defaults__` タプルに入っている。呼び出しの前後で `id()` が同一である。
キーワード専用引数のデフォルトは `関数.__kwdefaults__` に入る。

## 2. 危険な型の判定表 (実行して分けた結果)

| デフォルトの型 | ハッシュ可能 | その場変更 | 判定 |
|---|---|---|---|
| `list` | 不可 | 可能 | **呼び出し間で状態が漏れる** |
| `dict` | 不可 | 可能 | **呼び出し間で状態が漏れる** |
| `set` | 不可 | 可能 | **呼び出し間で状態が漏れる** |
| `bytearray` | 不可 | 可能 | **呼び出し間で状態が漏れる** |
| `defaultdict` · `Counter` · `deque` | 不可 | 可能 | **呼び出し間で状態が漏れる** |
| `int` · `float` | 可能 | 不可 | 漏れなし |
| `str` · `bytes` | 可能 | 不可 | 漏れなし |
| `tuple` · `frozenset` | 可能 | 不可 | 漏れなし (要素が可変なら例外) |
| `None` | 可能 | 不可 | 漏れなし — **推奨されるデフォルト** |
| `date` · `datetime` · `Decimal` | 可能 | 不可 | 漏れはないが **値が固まる** |

**判定規則**: `hash(デフォルト値)` が `TypeError` を出すなら、そのデフォルトは危険である。
標準ライブラリのデータクラスも同じ判定をしている — ハッシュ不可を可変性の近似として使う。

**ただし不変なら安全という話ではない。** 不変のデフォルトは状態が漏れないだけで、
**定義時点で固まる。** その形が以下である。

```python
from datetime import datetime

def stamp(label, when=datetime.now()):   # 悪い例: インポートの瞬間が永久に焼き付く
    return label, when

def stamp(label, when=None):             # 良い例: 呼び出しごとに読み直す
    if when is None:
        when = datetime.now()
    return label, when
```

**デフォルトの位置に呼び出し式があれば、戻り値の型に関係なく疑う。**

## 3. 正しい定型

```python
# 標準形 — None を番人にする
def add_item(name, basket=None):
    if basket is None:
        basket = []
    basket.append(name)
    return basket

# 呼び出し側のデータを所有したくないならコピーする
def tag_all(rows, tags=None):
    tags = list(tags) if tags is not None else []
    tags.append("processed")
    return {"rows": rows, "tags": tags}

# None 自体が正当な引数値になりうる場合は専用の番人を作る
_MISSING = object()

def lookup(key, fallback=_MISSING):
    table = {"a": 1, "b": None}
    if key in table:
        return table[key]
    if fallback is _MISSING:
        raise KeyError(key)
    return fallback

# 読み取り専用マッピングをデフォルトに置く方法
from types import MappingProxyType
_EMPTY = MappingProxyType({})

def render(name, opts=_EMPTY):
    return name, dict(opts)
```

### `or` を使ってはいけない理由

```python
extra = extra or ["DEFAULT"]     # 悪い例: 空リストをデフォルトで置き換えてしまう
if extra is None:                # 良い例: None だけを弾く
    extra = ["DEFAULT"]
```

空リスト・空辞書・`0`・空文字列はすべて偽である。
呼び出し側が「空である」ことを意図して渡したのに、デフォルトに戻されてしまう。

### クラスとデータクラス

```python
class Cart:
    items = []                # 悪い例: 全インスタンスが一つを共有する

class Cart:
    def __init__(self, items=None):
        self.items = [] if items is None else list(items)   # 良い例

from dataclasses import dataclass, field

@dataclass
class Good:
    items: list = field(default_factory=list)   # 良い例
```

データクラスは可変デフォルトを `ValueError` で拒否する。**通常の関数は何も警告しない。**

## 4. 検出

専用のリンタが入っていない環境なら、標準ライブラリの `ast` で自分で走査する。

```python
# find_mutable_defaults.py — 標準ライブラリのみ
import ast, os, sys

FACTORIES = {"list", "dict", "set", "bytearray", "defaultdict",
             "OrderedDict", "Counter", "deque"}

def describe(node):
    if isinstance(node, (ast.List, ast.Dict, ast.Set)):
        return "MUTABLE", "可変リテラル"
    if isinstance(node, (ast.ListComp, ast.DictComp, ast.SetComp)):
        return "MUTABLE", "内包表記"
    if isinstance(node, ast.Call):
        f = node.func
        name = f.id if isinstance(f, ast.Name) else getattr(f, "attr", "")
        if name in FACTORIES:
            return "MUTABLE", "ファクトリ呼び出し"
        return "CALL", "定義時に一度だけ評価される呼び出し"
    if isinstance(node, ast.BinOp):
        return "CALL", "定義時に一度だけ評価される計算式"
    return None, None

def scan(path):
    tree = ast.parse(open(path, encoding="utf-8").read(), filename=path)
    for node in ast.walk(tree):
        if isinstance(node, ast.ClassDef):
            for stmt in node.body:
                value = getattr(stmt, "value", None)
                if value is not None and describe(value)[0] == "MUTABLE":
                    print(path, stmt.lineno, "CLASSATTR", node.name)
        if not isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef, ast.Lambda)):
            continue
        a = node.args
        pos = a.posonlyargs + a.args
        pairs = list(zip(pos[len(pos) - len(a.defaults):], a.defaults)) if a.defaults else []
        pairs += [(k, d) for k, d in zip(a.kwonlyargs, a.kw_defaults) if d is not None]
        for arg, default in pairs:
            kind, why = describe(default)
            if kind:
                print(path, default.lineno, kind,
                      getattr(node, "name", "lambda"), arg.arg, why)

for target in sys.argv[1:] or ["."]:
    if os.path.isdir(target):
        for root, _d, files in os.walk(target):
            for f in files:
                if f.endswith(".py"):
                    scan(os.path.join(root, f))
    else:
        scan(target)
```

すでに動いているプロセスを点検するなら、実行時スキャンのほうが確実である。

```python
import inspect

MUTABLE = (list, dict, set, bytearray)

def scan_live(module):
    for name, obj in vars(module).items():
        if not inspect.isfunction(obj):
            continue
        for pname, p in inspect.signature(obj).parameters.items():
            if p.default is not inspect.Parameter.empty and isinstance(p.default, MUTABLE):
                print(name, pname, type(p.default).__name__, repr(p.default)[:40])
```

**稼働中のサービスに対してこのスキャンを回すと、以前の呼び出しのデータがデフォルトの中に
そのまま残っているのが見える。** それが状態漏れの証拠である。

### 検出手段の比較

| 手段 | 複数行シグネチャ | ファクトリ呼び出し | クラス属性 | サードパーティ製コード |
|---|---|---|---|---|
| 正規表現 grep | 見逃す | 見逃す | 見逃す | 可能 |
| `ast` スキャナ | 捕捉 | 捕捉 | 捕捉 | ソースがあれば可能 |
| 実行時 `__defaults__` スキャン | 該当なし | 捕捉 | 捕捉 | **可能** |
| インタプリタ自身 | — | — | — | **警告は一切ない** |

## 5. デフォルトをキャッシュに使う場合 — 勧めない理由

```python
def fib(n, _memo={0: 0, 1: 1}):     # 動きはする。しかし
    if n not in _memo:
        _memo[n] = fib(n - 1, _memo) + fib(n - 2, _memo)
    return _memo[n]
```

- キャッシュが**公開シグネチャに露出する**。呼び出し側が `fib(10, {0: 0, 1: 100})` で汚染できる
- **決して空にならない。** 上限も無効化の手段もない
- **スレッドセーフではない。** 読み取り・変更・書き込みが割れると更新が消える
- ドキュメント生成ツールや型チェッカがこの枠を本物の引数として扱う

代替:

```python
from functools import lru_cache

@lru_cache(maxsize=128)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

fib.cache_info()    # ヒット・ミス・現在のサイズ
fib.cache_clear()   # 空にする
```

状態を隠したいならクロージャを使う。呼び出し側から触れず、インスタンスごとに独立する。

```python
def make_counter():
    tally = {}
    def bump(key):
        tally[key] = tally.get(key, 0) + 1
        return tally[key]
    return bump
```

## 6. 点検リスト

- [ ] 関数シグネチャに `=[]`, `={}`, `=set()` が一つもない
- [ ] `=defaultdict(...)`, `=Counter()`, `=deque()` のようなファクトリ呼び出しがない
- [ ] デフォルトの位置に**呼び出し式**がない (`datetime.now()`, `uuid4()`, `time()`)
- [ ] デフォルトの位置に**計算式**がない (インポート時点で固まる)
- [ ] 番人の判定に `or` ではなく `is None` を使っている
- [ ] `None` が正当な値になりうる引数には専用の番人オブジェクトを使う
- [ ] 呼び出し側が渡したコンテナを関数が**黙って変更しない** (必要ならコピーする)
- [ ] クラス本体にリスト・辞書・集合の属性がない
- [ ] データクラスのフィールドは `field(default_factory=...)` を使っている
- [ ] キャッシュはデフォルト引数ではなく `lru_cache` かクロージャで実現する
- [ ] CI に `ast` スキャナかリンタを組み込み、新規混入を止めている
- [ ] 長時間動くプロセスは実行時 `__defaults__` スキャンで残留状態を点検する

## 7. してはいけないこと

- 「可変型だけ気をつければよい」 — 不変のデフォルトも**定義時に固まる**
- 「テストが通ったから大丈夫」 — 最初の呼び出しは常に正常で、**二度目から現れる**
- 「スレッドの問題は GIL が防いでくれる」 — 切り替え間隔次第で**現れも隠れもする**
- `関数.__defaults__` に直接代入して直すこと — 原因ではなく症状をいじっている
- 再現しない状態汚染を「環境のせい」で片付けること — まず `__defaults__` を出力する
