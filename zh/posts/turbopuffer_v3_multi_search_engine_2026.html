背景 — 向量优先架构的局限与v3的发布

2026年9月30日，检索基础设施提供商turbopuffer在官方技术博客上发表了题为《RIP, vector database》的技术文章。作为早期无服务器向量数据库的代表，turbopuffer宣布正在对其底层存储架构进行根本性重构，全面推进至第3版（v3）架构。这一宣告的实质并非如标题所示彻底抛弃向量检索，而是一次深刻的底层架构解耦：将系统赖以立足的近似最近邻（ANN）向量索引从唯一的主索引（primary index）降级为二级索引（secondary index）。

turbopuffer以云对象存储为最终真实数据源（source of truth），结合分层NVMe SSD与内存缓存，在经济成本与低延迟之间取得了优异平衡，成功支撑了Cursor与Notion等核心客户的生产负载。然而，随着全文检索、正则匹配、属性过滤及分析聚合（aggregation）等非向量查询需求的激增，早期将所有数据挂载在向量物理聚类之下的设计，在实际运行中遭遇了存储放大、写入放大以及向量化执行受限三大物理瓶颈。官方博客明确指出了以下四大核心改造目标：

  • 解耦文档实体与向量索引的物理绑定，彻底消除多向量场景下的属性与文本数据冗余
  • 阻断后台向量聚类动态平衡过程对数百个倒排索引条目产生的级联重写迁移
  • 打破分析查询受制于ANN聚类尺寸的硬性瓶颈，释放现代向量化流水线的大块并发计算潜力
  • 将复杂SQL分析运算与大规模顺序扫描平滑迁移至turbopuffer引擎，实现端到端极速处理

这一演进绝非简单的性能调优，它标志着turbopuffer脱离了单一狭隘的专用向量数据库赛道，蜕变为能够在云对象存储上统一承载向量、全文倒排与结构化分析的通用多查询引擎（multi-search query engine）。

v1架构 — 对象存储与分层聚类索引的结合

turbopuffer v1的设计目标是打造一款极其廉价且响应迅速的无服务器向量数据库。在项目启动时，业界普遍采用HNSW等基于图的向量索引。然而，图遍历过程中高度离散的随机指针跳转，与对象存储高网络延迟和大块顺序读取的物理特性存在严重冲突。因此，turbopuffer舍弃了图索引，选择了与对象存储适配度更高的分层聚类（hierarchical clustering）索引架构。

在工程演进中，团队初期采用微软的SPANN算法，随后为了支持增量流式写入，全面切换至SPFresh算法。系统将向量聚合成组，提取中心点（centroid），再对中心点进行递归聚类，直至收敛为单根树状结构。底层存储表现为有序且键唯一的键值映射表。每个聚类被赋予一个ClusterId，聚类内部的向量被赋予稠密的LocalId。两者组合形成的C0L1形式标识符被称为ANN地址（ANN address）。

// turbopuffer v1: 以ANN地址为主键的有序键值存储结构
                    // 单个叶子聚类C0内部存储的向量数据与原始文档ID
                    K::Vector(C0L0) = vec![0.45, 0.32, ...];
                    K::Id(C0L0)     = 7;
                    
                    K::Vector(C0L1) = vec![-0.28, 0.96, ...];
                    K::Id(C0L1)     = 13;
                    
                    // 上层聚类树中索引聚类C0的中心点向量
                    K::Vector(C1L4) = vec![0.64, -0.48, ...];
                    K::Id(C1L4)     = C0; // 指向下级聚类标识符

v1架构所遵循的核心设计哲学与工程特性可以系统归纳为以下四项支柱：

  • 以对象存储作为全量唯一真源有效压缩冷存成本，通过分层NVMe缓存抵御远程访问延迟
  • 彻底摒弃内存离散指针，基于适配对象存储大块顺序读特征的分层聚类树构建存储骨架
  • 在有序键值存储中将ClusterId与LocalId拼接而成的复合ANN地址确立为记录物理主键
  • 通过自顶向下的中心点路由机制快速剪枝无关聚类，以最少量的网络I/O实现低延迟召回

如上述代码所示，不仅向量本身的嵌入值，原始文档ID也是以ClusterId与LocalId构成的ANN地址作为物理存储键。这意味着，数据库内部决定数据物理分布的主索引就是向量索引本身。在对象存储场景下，这种结构能以最少的I/O精准拉取目标聚类，展现了极高的读取效率。

v2演进 — 倒排属性过滤与BM25全文检索的扩展

随着业务场景由单一的相似度召回走向复杂的业务中台，元数据属性过滤和基于BM25的全文检索（FTS）成为刚性需求。在非正式称为v2的发展阶段，turbopuffer将属性倒排索引与全文检索深度整合至查询引擎中。为了兼顾快速过滤与高召回率，属性索引直接将属性值映射到包含该属性值的文档ANN地址列表中。

例如在鸟类数据检索中按科（family）或属（genus）进行筛选时，引擎能够瞬间获取匹配的ANN地址列表，大幅收窄后续的向量搜索空间。与此同时，由于用户常通过include_attributes参数投影返回文档属性，文档的所有非向量属性也被物理存储在对应的ANN地址下方，与向量及文档ID紧密绑定。

// turbopuffer v2: 属性倒排索引与BM25全文检索存储结构
                    // 将属性值映射至文档的ANN地址列表
                    K::AttrIndex("family", "Alcidae")    -> vec![C0L3, C1L2, C1L3, ...];
                    K::AttrIndex("genus", "Fratercula")  -> vec![C0L3, C1L2, C1L9, ...];
                    
                    // 紧贴ANN地址存储文档元数据属性，以支持属性投影返回
                    K::Vector(C0L0)          = vec![0.45, 0.32, ...];
                    K::Id(C0L0)              = 7;
                    K::Attr(C0L0, "family")  = "Alcidae";
                    K::Attr(C0L0, "genus")   = "Fratercula";
                    
                    // BM25倒排列表: 存储ANN地址及计算评分所需的词频与文档长度
                    K::FTS("description", "Atlantic")    -> vec![(C0L0, 2, 37), (C9L4, 1, 42), ...];
                    K::Attr(C0L0, "description")         = "A sharply dressed seabird with a multicolored bill...";

为满足日益复杂的企业级检索诉求，turbopuffer随后连续推出了多项高级算子与执行机制：

  • 属性倒排过滤：将布尔过滤条件瞬时解析为ANN地址集合，大幅提升混合检索剪枝效率
  • BM25全文检索：在倒排项中持久化词频与文档长度元数据，精准执行文本相关度打分
  • 正则表达式与模糊匹配：为非结构化文本分析提供通配正则扫描与抗拼写误差模糊比对
  • 稀疏向量检索：支持SPLADE等词表加权稀疏表示，实现与稠密向量的混合多模态检索
  • 属性排序与指标聚合：基于结构化标量字段提供高效的结果集重排与多维基础统计汇总

随后，turbopuffer持续扩充执行能力，先后支持了正则检索、数据聚合、模糊匹配、稀疏向量检索以及属性排序。它甚至超越了搜索范畴，被项目协作软件Linear选作数据增量同步引擎（delta sync read path）的底层存储。但在所有这些繁复的查询功能之下，系统底层依然维系着以ANN地址为绝对核心的向量优先存储布局。

结构性瓶颈 ① — 多向量表示导致的存储空间膨胀

将全部数据挂载在ANN地址之下的方案，在单文档仅对应单个向量嵌入的时代运行良好。因为此时文档与ANN地址一一对应，非向量属性在磁盘上仅需写入一次。然而，现代信息检索与RAG技术的演进彻底打破了单向量假设。

将长文档分块嵌入的文档嵌套（document nesting）技术，以及为每个token保留嵌入以大幅提升检索精度的晚期交互（late interaction，例如ColBERT模型）技术被广泛应用。这类方法使单篇文档拥有多个向量表示。在turbopuffer原有的物理架构下，每个向量被分配至不同的聚类并拥有独立的ANN地址，引发了严重的存储冗余：

  • 若单篇文档生成10个向量嵌入，其完整的非向量属性与文本正文必须在10个不同的ANN地址下完整复制10次。
  • 在正文较长或属性繁多的业务场景中，冗余存储的文档数据量迅速压倒了向量本身的数据量。
  • 存储空间的非理性膨胀推高了对象存储账单，并导致本地高速NVMe缓存被无效数据频繁驱逐。
  • 缓存命中率的下降直接引发远程带宽拥塞，严重限制了多租户环境下的并发查询承载力。
  • 为了控制成本，turbopuffer被迫在命名空间层面严格限制单文档允许创建的向量列数量上限。

结构性瓶颈 ② — SPFresh再平衡引发的级联写入放大

第二个关键瓶颈是在数据增删改过程中形成的灾难性写入放大（write amplification）。在分层聚类索引中，持续的数据写入与删除会导致各聚类规模失衡，若不加以调整，搜索召回率将急剧下降。为此，turbopuffer的SPFresh算法会在后台持续运行向量聚类再平衡。

由于所有文档属性与索引均以ANN地址为主键，向量在聚类间的迁移产生了严重的连锁反应。当某个向量从聚类A移动至聚类B并获得新的ANN地址（如由C0L3变更为C2L8）时，不仅该向量本身的存储位置发生变化，挂载在其下方的所有文档属性、文本，以及所有指向旧地址的属性倒排索引和BM25词表都必须被级联重写。

  • 单一向量的微小位置调迁，会导致数以百计的属性与索引条目产生级联物理迁移（cascading move）。
  • 在高频写入与更新的工作负载下，系统施加在磁盘与对象存储上的物理I/O达到了实际写入数据量的数十乃至数百倍。
  • 通过工程调优提升索引吞吐量的努力，由于级联写入的加剧而遭遇明显的边际效用递减。
  • 过载的写入I/O阻塞了后台数据合并压实（compaction），成为实时读取长尾延迟抖动的首要诱因。
  • 数据摄取流水线因底层I/O拥堵出现反压积压，致使基础设施运营成本急剧上升。

结构性瓶颈 ③ — 查询最优块大小与向量化执行约束

第三个瓶颈直接制约了现代数据库查询引擎的核心引擎：向量化执行（vectorized execution）。现代分析引擎通过紧凑循环批量处理固定大小的数据块，以充分饱和CPU流水线并利用SIMD向量指令集。然而，不同查询算子所需的最佳数据块大小存在巨大差异。

计算引擎及查询算子最佳处理块大小执行特性与硬件优化目标
DuckDB（向量化OLAP）每批2,048行适应CPU L1/L2缓存容量，实现SIMD向量计算吞吐最大化
ClickHouse（海量分析）最高约65,000行每块最大化列式顺序扫描吞吐并实现高密度数据压缩
Apache Lucene（全文检索倒排）256文档每块基于整型位压缩（PForDelta）的高速跳表扫描
turbopuffer ANN向量聚类约100至200文档每聚类保持中心点距离计算精度与对象存储读取局部性
turbopuffer FTS v1（旧版设计）中位数约1.5条记录每块按ANN聚类边界硬性切分导致倒排块极度碎片化

如上表所示，turbopuffer的ANN索引在聚类规模为100至200篇文档时能够在对象存储上达到最优效率。然而，因为文档本身被绑定在聚类内，需要顺序扫描数千行数据的聚合分析（如GROUP BY、SUM、COUNT）也被迫在100至200行的小碎片块上低效运转。

块大小对性能的决定性影响，在turbopuffer将全文检索由v1重构至v2时已得到充分验证。在FTS v1中，倒排列表沿ANN聚类边界切分，块大小中位数仅为1.5条记录。在FTS v2中，倒排列表脱离聚类限制，重构成约256篇文档的固定大小数据块，索引体积瞬间缩减至十分之一，查询吞吐激增最高达20倍。倒排列表由于仅保存文档引用因而得以解绑，但直接读取文档实体的聚合与扫描算子仍深陷百行小块的桎梏之中。

v3方案 — 文档存储解耦与二级索引体系重塑

为了从根本上消除上述三大瓶颈，turbopuffer v3确立了清晰的重构原则：不再以ANN向量地址作为数据主键。在v3中，文档的存储布局、压实合并以及扫描逻辑，与向量聚类树彻底解耦，达成了以下技术革新：

  • 文档存储完全独立： 文档脱离向量聚类边界，基于独立的文档唯一标识符以列式连续大块集中存储。即使文档包含多个向量，正文仅存一份，彻底根除了存储放大。
  • 向量索引降为二级索引： 向量索引不再是全局支配性的骨架，而是与属性倒排索引、全文检索索引处于同等地位的二级索引。
  • 阻断写入放大级联： 当SPFresh进行向量聚类调整时，仅需更新向量索引内部的树节点指针。文档正文与属性倒排索引保持原位，写入放大被严格收敛。
  • 释放向量化计算性能： 聚合与扫描算子摆脱了100至200行的小块限制，能够以数千行为单位批量加载连续内存，全面激活现代CPU的向量化指令与流水线能力。
  • 奠定通用SQL分析基石： 文档存储的规范化使得turbopuffer能够超越相似度搜索的界限，承载更多通用SQL分析查询的高性能执行。
  • 实现压实调度周期解耦： 文档合并整理与向量索引重构可基于不同负载特征独立调度执行，系统整体稳定性大幅提升。

目前，turbopuffer公布的生产运营规模包括：全系统托管超过1万亿篇文档（1T+ documents），承载每秒超过1,000万次写入（10M+ writes/s），并支撑每秒超过25,000次查询（25k+ queries/s）。在单索引向量检索方面，支持超过1,000亿个向量（100B+ vectors），并在超过1,000 QPS的高并发负载下维持200毫秒的99分位（p99）读取延迟。

根据官方披露，v3已于2026年9月上旬以100%的通过率完成全套持续集成（CI）自动化测试，率先锁定了功能与逻辑的正确性（correctness）。工程团队目前正集中开展性能基准测试，在全面达成并超越v2各项性能基准后，分阶段推向生产集群。

未能核实的事项

  • v3独立文档存储所采用的具体底层文件格式（例如是否采用Apache Parquet或自研的列式二进制格式）。官方博客仅阐述了逻辑解耦原理，未公开物理存储容器规范。
  • v3正式推向生产环境的确定时间表。官方目前仅确认CI 100%通过并处于性能测试阶段，未公布确切的上线日期。
  • 从现有v2命名空间平滑热迁移至v3独立存储的具体在线迁移方案与停机窗口要求。
  • v3架构下聚合分析（GROUP BY）查询延迟的具体提升百分比数据。（文中提及的索引缩小10倍与加速20倍系早期FTS v2重构时的历史实测值）。
  • 除已公开的标杆客户（Cursor、Notion、Linear）外，参与v3早期内测的其他企业名单。
  • v3中降级为二级索引的ANN向量索引在各节点所采用的内存缓存淘汰策略与额外开销。
