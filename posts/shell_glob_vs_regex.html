글롭과 정규식은 다르다 - * 가 서로 다른 뜻인 순간

ls 와 grep 에 같은 패턴을 넣으면 다른 답이 나온다. 직접 돌려 확인한 갈림길

2026-09-01 개발/인프라

ls ab* 는 ab 로 시작하는 이름을 준다. 같은 네 글자를 grep 'ab*' 에 넣으면 ab 가 아예 없는 줄까지 딸려 나온다. 오타도 아니고 버전 문제도 아니다. 두 자리에서 * 가 서로 다른 문법에 속해 있다.

파일 이름을 고르는 쪽 문법을 글롭(glob), 또는 명세 용어로 패턴 매칭 표기라고 부른다. grep·sed·awk 쪽은 정규식이다. 겹치는 기호가 많아서 — *, ?, [...] 가 양쪽에 다 있다 — 한쪽 감각으로 다른 쪽을 쓰면 오류 없이 틀린 결과가 나온다. 이게 성가신 이유다. 에러는 알아차리지만, 조용히 다른 것이 잡히는 일은 배포된 뒤에야 드러난다.

돌려 본 환경

셸 패턴은 「어느 셸의 몇 버전이냐」에 따라 답이 바뀌는 영역이다. 그 정보가 빠지면 아래 출력은 근거가 되지 못한다.

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

$ uname -o -r
Msys 3.5.7-882031da.x86_64

$ find --version | head -1
find (GNU findutils) 4.10.0

$ grep --version | head -1
grep (GNU grep) 3.0

$ sed --version | head -1
sed (GNU sed) 4.9

Windows 10 위의 Git Bash(MSYS2) 환경이고, 셸은 GNU bash 5.2.37, 유틸리티는 GNU 계열이다. 리눅스 배포판에서 돌리면 대부분 같은 출력이 나오지만, macOS 기본 grep·sed·find 는 BSD 계열이라 옵션 이름부터 다르다. 그 차이는 정규식 방언과 도구 간 호환성 쪽 주제이므로 여기서는 파고들지 않는다.

실험용 디렉터리는 이렇게 만들었다. 이후 나오는 모든 출력은 이 디렉터리 안에서 받은 것이다.

$ mkdir -p /tmp/demo/sub && cd /tmp/demo
$ touch a.txt ab.txt abb.txt b.txt notes.log report.log .hidden .bashrc
$ touch sub/deep.txt sub/deep.log

$ shopt nullglob failglob dotglob extglob globstar nocaseglob
nullglob        off
failglob        off
dotglob         off
extglob         off
globstar        off
nocaseglob      off

shopt 상태를 먼저 찍어 둔 데는 이유가 있다. 이 글에서 다루는 동작의 절반쯤은 저 스위치가 정한다. 비대화형 스크립트에서는 저 여섯 개가 전부 꺼진 상태가 기본값이고, 대화형 셸에서는 배포판 초기화 파일이 extglob 같은 것을 켜 두기도 한다. 「내 터미널에서는 되던데 스크립트에서는 안 된다」의 상당수가 여기서 나온다.

* — 「아무 문자열」과 「앞 것의 0회 이상」

가장 많이 쓰는 기호부터 본다. 같은 ab* 를 양쪽에 넣어 봤다.

# 글롭 - 셸이 파일 이름과 맞춘다
$ ls ab*
ab.txt
abb.txt

# 정규식 - grep 이 각 줄과 맞춘다
$ printf '%s\n' a.txt ab.txt abb.txt b.txt | grep 'ab*'
a.txt
ab.txt
abb.txt

글롭 쪽은 두 개, 정규식 쪽은 세 개다. 늘어난 하나가 a.txt 인데, 이게 핵심이다. 글롭에서 ab* 는 「a, b, 그리고 아무 문자열」이다. 정규식에서 ab* 는 「a, 그리고 b 가 0회 이상」이다. b 가 0회여도 되니까 b 없는 이름이 걸린다.

정리하면 이렇다. 글롭의 * 는 혼자서 뜻을 갖는 기호다. 정규식의 * 는 앞에 붙은 것을 반복시키는 연산자라서 혼자서는 뜻이 없다. 정규식에서 글롭의 * 에 해당하는 표기는 .* 다. 「아무 문자 하나가 0회 이상」이라고 풀어 써야 같은 뜻이 된다.

확장자를 뗀 짧은 목록으로 한 번 더 확인하면 차이가 더 선명해진다.

$ printf '%s\n' a ab abb xabz | grep 'ab*'
a
ab
abb
xabz

$ printf '%s\n' a ab abb xabz | grep -E '^ab*$'
a
ab
abb
  • 글롭 * = 아무 문자열. 빈 문자열도 포함한다. 그래서 ab* 는 ab 자체와도 맞는다
  • 정규식 * = 바로 앞 요소의 0회 이상 반복. 앞 요소가 없으면 문법 오류거나 리터럴로 취급된다
  • 정규식에서 「아무 문자열」을 쓰려면 .*. . 이 「아무 한 글자」, * 가 「그것의 반복」
  • xabz 가 걸린 것은 * 때문이 아니라 부분 일치 때문이다. 이건 다음다음 절에서 따로 다룬다

? 와 . — 한 글자를 가리키는 두 방식

양쪽 다 「아무 한 글자」를 표현하는 기호가 있는데, 쓰는 문자가 다르다. 글롭은 ?, 정규식은 . 이다. 그리고 글롭에서 . 은 그냥 마침표다. 특별한 뜻이 전혀 없다.

# 글롭의 ? - 딱 한 글자
$ ls ?.txt
a.txt
b.txt

# 글롭에서 ? 는 점도 잡는다. 점은 글롭에서 평범한 문자다
$ ls a?txt
a.txt

# 정규식의 . - 여기서도 한 글자, 그래서 점 아닌 것도 잡힌다
$ printf '%s\n' a.txt axtxt aatxt | grep 'a.txt'
a.txt
axtxt
aatxt

마지막 출력이 실무에서 자주 사고를 낸다. grep 'a.txt' 라고 쓰면 사람은 「a.txt 라는 파일 이름」을 찾는다고 생각하지만, grep 은 「a, 아무 글자, txt」로 읽는다. 파일 이름이나 도메인처럼 점이 든 문자열을 정규식으로 찾을 때는 a\.txt 로 점을 escape 해야 한다. 반대로 글롭에서는 점을 escape 할 일이 없다. 애초에 특수문자가 아니다.

  • 글롭 ? — 정확히 한 글자. 0글자는 안 되고 2글자도 안 된다
  • 글롭 . — 문자 그대로의 마침표. escape 불필요
  • 정규식 ? — 「앞 것이 0회 또는 1회」. 기본 정규식(BRE)에서는 \? 로 써야 하고, grep -E 에서는 ? 그대로 쓴다
  • 즉 ? 라는 글자 하나가 양쪽에서 완전히 다른 일을 한다. 글롭에서는 「한 글자 소비」, 정규식에서는 「앞 것을 선택적으로」

앵커링 — 이름 전체냐 부분이냐

이 차이가 * 의 뜻 차이보다 더 자주 사람을 헷갈리게 한다. 글롭은 이름 전체와 맞춰진다. 암묵적으로 앞뒤가 고정돼 있다. 정규식은 기본이 부분 일치다. 줄 어딘가에 있기만 하면 걸린다.

# 글롭 - 이름 전체가 txt 여야 한다. 그런 파일은 없다
$ ls txt
ls: cannot access 'txt': No such file or directory

# 정규식 - 줄 안 어디에든 txt 가 있으면 걸린다
$ printf '%s\n' a.txt notes.log | grep 'txt'
a.txt

그래서 정규식에서 「이름 전체가 이것」을 표현하려면 ^ 와 $ 를 직접 붙여야 한다. 앞 절의 grep -E '^ab*$' 가 xabz 를 떨군 이유가 이것이다. 반대로 글롭에서 「어딘가에 포함」을 표현하려면 양쪽에 * 를 붙여 *txt* 라고 써야 한다.

대응 관계를 표로 두면 머리에 남는다. 왼쪽과 오른쪽이 같은 뜻이 되는 짝이다.

하고 싶은 것글롭정규식(ERE)주의
이름 전체가 abab^ab$글롭은 앵커가 기본, 정규식은 붙여야 함
ab 로 시작ab*^ab글롭 * 는 .* 에 대응
.log 로 끝남*.log\.log$정규식은 점을 escape
어딘가에 txt*txt*txt정규식은 부분 일치가 기본
아무 한 글자?.기호가 서로 뒤바뀌어 있다
앞 것을 0회 이상표현 불가x*기본 글롭에는 반복 연산자가 없다
a 또는 b[ab] 또는 @(a|b)a|b@(...) 는 extglob 필요
a 가 아닌 한 글자[!a][^a]부정 기호가 다르다

[...] 는 부정에서 갈라진다

대괄호는 양쪽에서 가장 닮은 부분이다. [abc], [a-z], [[:digit:]] 같은 표기는 글롭에서도 정규식에서도 같은 뜻으로 동작한다. POSIX 문자 클래스까지 공유한다. 그런데 부정 표기 하나에서 갈라진다.

# 글롭의 표준 부정은 [!...]
$ ls [!a]*.txt
b.txt

# bash 는 글롭에서 [^...] 도 부정으로 받아 준다
$ ls [^a]*.txt
b.txt

# 정규식의 부정은 [^...]
$ printf '%s\n' a.txt ab.txt b.txt | grep '^[^a]'
b.txt

# 정규식에서 [!...] 는 부정이 아니라 「! 또는 a」라는 집합이다
$ printf '%s\n' a.txt ab.txt b.txt '!x.txt' | grep '^[!a]'
a.txt
ab.txt
!x.txt

마지막 출력을 보면 상황이 분명해진다. 정규식에 [!a] 라고 쓰면 「a 가 아닌 것」이 아니라 「! 또는 a」가 된다. 의도와 정확히 반대로 동작하면서 오류는 나지 않는다.

bash 가 관대한 것이 이식성 문제가 된다

ls [^a]*.txt 가 잘 돌았으니 글롭에서도 [^...] 를 써도 되겠다고 생각하기 쉽다. 그건 bash 의 확장이다. 같은 패턴을 dash 에 주면 이렇게 된다.

$ dash -c 'cd /tmp/demo; echo [!a]*.txt'
b.txt

$ dash -c 'cd /tmp/demo; echo [^a]*.txt'
a.txt ab.txt abb.txt

완전히 뒤집혔다. dash 에서 [^a] 는 부정이 아니라 「문자 ^ 또는 문자 a」라는 집합이라서, a 로 시작하는 이름을 전부 골라 온다. 배제하려던 것을 정확히 선택해 온 셈이다. 그리고 여기서도 경고 한 줄 나오지 않는다.

배포 대상 시스템에서 /bin/sh 가 dash 로 연결돼 있는 일은 드물지 않다. 지우거나 옮기는 스크립트에서 이 뒤집힘이 일어나면 결과가 조용히 최악으로 간다.

  • 글롭에는 [!...], 정규식에는 [^...]. 이 둘만 쓰면 어느 셸에서도 뜻이 안 바뀐다
  • bash 가 [^...] 를 받아 준다는 것이 그걸 써도 된다는 뜻은 아니다. 테스트를 통과시키는 관대함이 이식성에서는 위험이 된다
  • 범위 [a-z] 는 로케일 정렬 순서를 탄다. 안전하게 가려면 [[:lower:]] 같은 문자 클래스를 쓴다
  • [[:digit:]] 같은 POSIX 클래스는 양쪽에서 그대로 통한다. ls *[[:digit:]]*.txt 와 grep '[[:digit:]]' 둘 다 동작한다

글롭은 파일명 전용 문법이 아니다

글롭을 「명령줄에서 파일 고를 때 쓰는 것」으로만 알고 있으면 절반이다. bash 안에서 글롭이 쓰이는 자리는 넷이고, 그중 셋은 파일이 전혀 개입하지 않는다.

case 문의 각 분기

$ for v in report.log a.txt sub README; do
>   case "$v" in
>     *.log)  echo "$v -> log" ;;
>     *.txt)  echo "$v -> text" ;;
>     [A-Z]*) echo "$v -> uppercase-start" ;;
>     *)      echo "$v -> other" ;;
>   esac
> done
report.log -> log
a.txt -> text
sub -> other
README -> uppercase-start

case 의 각 분기 레이블은 글롭이다. 마지막 *) 가 「그 외 전부」로 동작하는 것도 글롭 * 가 아무 문자열과 맞기 때문이다. 여기에 정규식을 넣으면 대개 아무 분기도 안 걸린다. case $v in ^ab.*$) 는 「^ab 로 시작해 $ 로 끝나는 문자열」을 찾게 된다.

파라미터 확장의 패턴 자리

$ p="/var/log/app/server.access.log"

$ echo "${p##*/}"
server.access.log

$ echo "${p%.*}"
/var/log/app/server.access

$ echo "${p%%.*}"
/var/log/app/server

$ n="v1.2.3-rc4"
$ echo "${n//[!0-9]/}"
1234

${v#pat}·${v##pat}·${v%pat}·${v%%pat}·${v/pat/rep}·${v//pat/rep} 의 pat 자리는 전부 글롭이다. 여기서도 * 는 「아무 문자열」이고, 한 글자짜리와 두 글자짜리(# 대 ##)는 각각 가장 짧게와 가장 길게 잘라 낸다는 차이다.

마지막 예의 ${n//[!0-9]/} 가 「숫자가 아닌 문자를 전부 지운다」로 동작하는 것도 글롭의 [!...] 부정 덕분이다. 참고로 dash 에는 ${v//pat/rep} 자체가 없어서 Bad substitution 으로 죽는다. ${v#pat} 과 ${v%pat} 은 POSIX 라서 dash 에서도 동작한다.

== 는 글롭, =~ 만 정규식

bash 안에서 정규식을 쓰는 자리는 [[ x =~ re ]] 하나뿐이다. 바로 옆에 있는 [[ x == pat ]] 는 글롭이다. 두 연산자가 같은 대괄호 안에 나란히 있으면서 문법이 다르다는 것이 이 대목을 어렵게 만든다.

$ s="aXbXc"

$ [[ $s == a*c ]] && echo true || echo false
true

$ [[ $s =~ a*c ]] && echo true || echo false
true

$ [[ $s =~ ^a*c$ ]] && echo true || echo false
false

$ t="aaac"
$ [[ $t =~ ^a*c$ ]] && echo true || echo false
true

두 번째 줄이 함정이다. =~ 에 a*c 를 넣었는데 true 가 나왔다. 글롭처럼 동작해서가 아니라, 정규식 a*c 가 「a 가 0회 이상 뒤에 c」이고 이건 문자열 안의 c 한 글자만으로도 성립하기 때문이다. 부분 일치라서 우연히 참이 됐다. 앵커를 붙인 세 번째 줄에서 비로소 false 가 나온다.

우연히 맞는 결과가 가장 나쁘다. 테스트를 통과해 배포된 다음, 입력 형태가 조금 달라졌을 때 처음 틀린다. =~ 에는 앵커를 습관적으로 붙이는 편이 낫다.

대신 =~ 만 할 수 있는 일도 있다. 매치된 부분을 꺼내 오는 것이다.

$ v="v2.10.3"
$ [[ $v =~ ^v([0-9]+)\.([0-9]+)\.([0-9]+)$ ]] &&
>   echo "major=${BASH_REMATCH[1]} minor=${BASH_REMATCH[2]} patch=${BASH_REMATCH[3]}"
major=2 minor=10 patch=3

$ [[ $v == v*.*.* ]] && echo "matched, but no captured parts"
matched, but no captured parts

글롭에는 캡처가 없다. == 는 참·거짓만 준다. 버전 문자열을 쪼개거나 로그 줄에서 필드를 뽑아야 하면 그건 정규식의 일이고, BASH_REMATCH 배열이 그 결과를 담는다. 0번 원소는 매치된 전체, 1번부터가 괄호 그룹이다.

따옴표가 문법을 정한다

같은 줄에서 따옴표 하나로 뜻이 바뀐다. 이 절은 셸 인용부호 규칙 전반이 아니라, 글롭과 정규식이 갈리는 부분만 본다.

$ f='report.log'
$ pat='*.log'

$ [[ $f == $pat ]]   && echo true || echo false
true

$ [[ $f == "$pat" ]] && echo true || echo false
false

$ re='^rep.*\.log$'

$ [[ $f =~ $re ]]    && echo true || echo false
true

$ [[ $f =~ "$re" ]]  && echo true || echo false
false

규칙은 하나다. == 와 =~ 의 오른쪽을 따옴표로 감싸면 패턴이 아니라 리터럴 문자열이 된다. [[ $f == "*.log" ]] 는 「파일명이 정확히 별표점로그 여섯 글자인가」를 묻는 것이고, 그런 이름은 없으므로 false 다.

=~ 쪽은 더 자주 당한다. 정규식 안에 공백이 있어서 따옴표로 감쌌더니 갑자기 아무것도 안 맞는 상황이다. 정규식을 변수에 담고 따옴표 없이 쓰는 것이 표준 관용구다.

  • [[ $f == *.log ]] — 오른쪽이 글롭 패턴. 참
  • [[ $f == "*.log" ]] — 오른쪽이 리터럴. 거짓
  • [[ $f =~ $re ]] — 정규식으로 해석. 이것이 권장 형태
  • [[ $f =~ "$re" ]] — 리터럴로 강등. 정규식 메타문자가 전부 죽는다
  • 반대로 리터럴 비교를 원할 때는 일부러 따옴표를 씌운다. 사용자 입력을 그대로 비교할 때 유용하다
  • grep·find 에 넘기는 패턴은 반드시 따옴표로 감싼다. 안 그러면 셸이 먼저 글롭으로 전개한다

맞는 게 없으면 패턴이 그대로 남는다

글롭에만 있는 동작이고, 스크립트 사고의 단골이다. 패턴에 맞는 파일이 하나도 없으면 셸은 패턴 문자열을 그대로 남겨 둔다.

$ ls *.csv
ls: cannot access '*.csv': No such file or directory

$ for f in *.csv; do
>   echo "loop sees: [$f]"
>   [ -e "$f" ] && echo "  exists" || echo "  DOES NOT EXIST"
> done
loop sees: [*.csv]
  DOES NOT EXIST

.csv 파일이 없는데도 반복문이 한 번 돈다. 그리고 $f 에는 *.csv 라는 다섯 글자가 들어 있다. 이걸로 rm 이나 mv 를 하면 무슨 일이 벌어지는지는 굳이 실험하지 않았다.

방법은 셋이다.

$ shopt -s nullglob
$ cnt=0; for f in *.csv; do cnt=$((cnt+1)); done; echo "iterations: $cnt"
iterations: 0

$ shopt -u nullglob; shopt -s failglob
$ for f in *.csv; do echo "$f"; done
bash: no match: *.csv

$ shopt -u failglob
$ for f in *.csv; do [ -e "$f" ] || continue; echo "processing $f"; done

마지막 것이 옵션에 의존하지 않는 방법이라서 남의 환경에서 도는 스크립트에는 이게 낫다. nullglob 은 편하지만 전역 스위치라서, 스크립트 중간에 켜 두면 다른 데서 기대하던 동작까지 바꿔 버린다. failglob 은 대화형 셸에서 오타를 잡는 데 유용하다.

  • 기본값(nullglob off) — 안 맞으면 패턴 그대로. 가장 위험한 기본값이지만 POSIX 가 그렇게 정해 놨다
  • nullglob on — 안 맞으면 아무것도 남지 않는다. 반복이 0회가 된다
  • failglob on — 안 맞으면 오류로 멈춘다. no match 메시지가 나오고 종료 상태가 0이 아니다
  • 수동 방어 — 반복문 첫 줄에 [ -e "$f" ] || continue. 어느 셸에서도 같게 동작한다
  • 정규식에는 이 문제가 아예 없다. grep 이 못 찾으면 출력이 비고 종료 상태가 1이 될 뿐, 패턴이 데이터로 둔갑하지 않는다

점으로 시작하는 이름

글롭에는 정규식에 없는 규칙이 하나 더 있다. 맨 앞의 점은 명시적으로 맞춰야 한다. * 는 「아무 문자열」이라면서 .bashrc 를 안 잡는다.

$ echo *
a.txt ab.txt abb.txt b.txt notes.log report.log sub

$ echo .*
.bashrc .hidden

$ shopt -s dotglob; echo *
.bashrc .hidden a.txt ab.txt abb.txt b.txt notes.log report.log sub

$ shopt -u dotglob
$ shopt globskipdots
globskipdots    on

$ shopt -u globskipdots; echo .*
. .. .bashrc .hidden

세 가지가 한 번에 보인다. 첫째, * 는 숨김 파일을 건너뛴다. 이건 셸의 특별 규칙이지 * 의 뜻에서 유도되는 게 아니다. 둘째, dotglob 을 켜면 그 규칙이 사라져서 * 가 전부를 잡는다. 셋째, echo .* 가 . 과 .. 없이 나온 것은 bash 5.2 에서 추가된 globskipdots 가 기본으로 켜져 있기 때문이다. 꺼 보면 옛 동작이 돌아온다.

마지막 항목이 중요하다. 예전에는 rm -rf .* 같은 명령이 상위 디렉터리까지 건드리는 사고로 이어졌다. bash 5.2 이상에서는 기본적으로 막히지만 오래된 셸에서는 여전히 열려 있다.

  • 글롭 — 맨 앞 점은 특별 취급. .bashrc 를 잡으려면 패턴이 점으로 시작해야 한다
  • 정규식 — 그런 규칙 없음. grep '.*' 는 .bashrc 를 그냥 잡는다
  • dotglob — 켜면 * 가 숨김 파일까지 포함. 백업 스크립트에서 종종 켠다
  • globskipdots — bash 5.2 신설, 기본 on. . 과 .. 를 글롭 결과에서 뺀다
  • 슬래시도 비슷하다. 글롭의 * 는 / 를 넘지 않는다. 하위 디렉터리를 잡으려면 */*.log 처럼 층을 명시하거나 globstar 를 켠다

find -name 은 글롭, find -regex 는 정규식

find 는 두 문법을 한 명령 안에 다 갖고 있어서 가장 헷갈리는 자리다. -name·-path 는 글롭, -regex 는 정규식이다. 그리고 맞추는 대상까지 다르다.

$ find . -name '*.log' | sort
./notes.log
./report.log
./sub/deep.log

$ find . -name 'deep.log'
./sub/deep.log

$ find . -regex 'deep\.log'

$ find . -regex '.*/deep\.log'
./sub/deep.log

$ find . -name 'sub/*'

세 번째 명령이 아무것도 출력하지 않은 게 함정이다. -regex 는 탐색이 만들어 낸 경로 문자열 전체와 맞춰지고, 부분 일치가 아니라 전체 일치다. 실제 경로가 ./sub/deep.log 이므로 deep\.log 로는 절대 안 맞는다. 앞을 .*/ 로 열어 줘야 한다.

다섯 번째도 비슷하다. -name 은 경로의 마지막 조각만 보므로 슬래시가 든 패턴은 구조적으로 절대 맞지 않는다. 경로 모양으로 거르려면 -path '*/sub/*' 를 쓴다.

여기에 따옴표 문제가 겹치면 에러 메시지가 난해해진다.

$ find . -name *.log
find: paths must precede expression: `report.log'
find: possible unquoted pattern after predicate `-name'?

$ find . -name '*.log' | sort
./notes.log
./report.log
./sub/deep.log

첫 명령이 실패한 것은 find 의 문제가 아니다. 셸이 먼저 *.log 를 전개해 find . -name notes.log report.log 로 만들어 넘겼기 때문이다. find 는 두 번째 인자를 경로로 착각하고 항의한다. 친절하게도 두 번째 줄에서 원인을 짚어 주는데, 이 메시지를 본 적 없으면 알아보기 어렵다.

더 나쁜 경우는 에러조차 안 나는 것이다. 현재 디렉터리에 .log 파일이 딱 하나면 find . -name *.log 는 그 하나만 조용히 찾아 준다. 그러다 파일이 둘로 늘어난 날 깨진다.

  • -name — 글롭, 파일명(경로 마지막 조각)만 대상. 슬래시는 절대 안 맞음
  • -path — 글롭, 경로 전체 대상. * 가 / 를 넘는다는 점이 셸 글롭과 다르다
  • -regex — 정규식, 경로 전체 대상, 전체 일치. GNU find 의 기본 방언은 emacs 계열이고 -regextype posix-extended 로 바꿀 수 있다
  • BSD·macOS 의 find 는 -regextype 대신 -E 를 쓴다. GNU findutils 4.10.0 에서 -E 를 주면 unknown predicate 로 거부된다
  • 결과를 다른 명령에 넘길 때의 공백·개행 문제는 find·xargs 공백 함정 쪽에서 따로 다뤘다

확장 글롭과 globstar

기본 글롭에는 반복 연산자도 교체(alternation)도 없다. bash 는 이를 extglob 으로 보충하는데, 기본은 꺼져 있다.

$ shopt extglob
extglob         off

$ ls !(*.log)
ls: cannot access '!(*.log)': No such file or directory

$ shopt -s extglob
$ ls @(a|b).txt
a.txt
b.txt

$ ls +(a)b*.txt
ab.txt
abb.txt

$ ls a*(b).txt
a.txt
ab.txt
abb.txt

꺼진 상태에서 !(*.log) 는 패턴이 아니라 그냥 그 이름의 파일을 찾는 문자열이 된다. 켜고 나면 a*(b).txt 가 a.txt·ab.txt·abb.txt 를 다 잡는다. *(b) 가 「b 가 0회 이상」이라서 정규식의 b* 와 같은 일을 한다. 괄호 위치가 반대라는 점만 다르다.

globstar 도 같은 사정이다.

$ shopt globstar
globstar        off

$ echo **/*.log
sub/deep.log

$ shopt -s globstar
$ echo **/*.log
notes.log report.log sub/deep.log

$ echo **
a.txt ab.txt abb.txt b.txt notes.log report.log sub sub/deep.log sub/deep.txt

꺼진 상태의 ** 는 그냥 * 두 개라서 */*.log 와 똑같이 정확히 한 층 아래만 본다. 켜면 **/ 가 0층 이상을 가로질러서 현재 층의 notes.log 까지 포함된다. 이걸 모르고 ** 를 쓴 스크립트가 「왜 하위 디렉터리를 안 뒤지지」로 시간을 잡아먹는다.

확장 글롭 표기뜻정규식 대응필요한 옵션
?(p)p 가 0회 또는 1회(p)?extglob
*(p)p 가 0회 이상(p)*extglob
+(p)p 가 1회 이상(p)+extglob
@(a|b)a 또는 b 중 정확히 하나(a|b)extglob
!(p)p 가 아닌 것부정 룩어헤드 등extglob
**/0층 이상의 디렉터리대응 없음globstar
[[:digit:]]숫자 한 글자[[:digit:]]불필요

!(p) 의 정규식 대응이 깔끔하지 않은 것은 「무언가가 아닌 문자열」이 정규식에서 원래 까다로운 요구라서다. 부정 룩어헤드를 쓰는데 그 자체가 별도 주제라 룩어헤드 실전 쪽에 정리해 뒀다.

어디가 글롭이고 어디가 정규식인가

기호보다 자리를 외우는 편이 실무에서 빨리 듣는다. 패턴을 쓰기 전에 「여기가 어느 쪽인가」만 판별하면 나머지는 따라온다.

자리문법맞추는 대상앵커링
명령줄의 ls *.log글롭파일 이름전체 일치
for f in *.txt글롭파일 이름전체 일치
case $v in *.log)글롭문자열(파일 무관)전체 일치
[[ $v == pat ]]글롭문자열전체 일치
${v#pat} ${v%pat} ${v//pat/}글롭문자열앞·뒤·전역
[[ $v =~ re ]]정규식(ERE)문자열부분 일치
grep re / grep -E re정규식(BRE/ERE)줄부분 일치
sed 's/re/rep/'정규식(BRE)줄부분 일치
awk '/re/'정규식(ERE)줄 또는 필드부분 일치
expr s : re정규식(BRE)문자열앞에서만
find -name / -path글롭파일명 / 경로전체 일치
find -regex정규식경로 전체전체 일치

표의 마지막 열도 같이 봐야 한다. grep 은 부분 일치인데 find -regex 는 전체 일치라서, 같은 정규식을 옮겨 붙이면 결과가 달라진다. expr 은 또 달라서 문자열 앞에서만 맞추고 매치된 길이를 숫자로 돌려준다.

$ printf '%s\n' a ab abb | sed 's/ab*/X/'
X
X
X

$ printf '%s\n' a ab abb xyz | awk '/ab*/'
a
ab
abb

$ expr 'abb' : 'ab*'
3

sed 가 a 를 X 로 바꾼 것도, awk 가 a 를 출력한 것도 같은 이유다. 정규식 ab* 는 b 없는 a 와 맞는다. expr 의 3 은 abb 세 글자가 매치됐다는 뜻이다.

어느 쪽을 쓸 것인가

고민할 필요가 없는 경우가 대부분이다. 자리가 정해져 있으면 문법도 정해져 있다. 선택지가 생기는 것은 같은 일을 두 방법으로 할 수 있을 때인데, 이때는 글롭이 대개 낫다.

  • 파일을 고르는 일이면 글롭. ls *.log 를 ls | grep '\.log$' 로 바꿀 이유가 없다. 후자는 공백·개행이 든 파일명에서 깨진다
  • 확장자·접두사·접미사 판별이면 글롭. [[ $f == *.tar.gz ]] 가 [[ $f =~ \.tar\.gz$ ]] 보다 짧고 escape 도 필요 없다
  • 경로에서 조각을 떼는 일이면 파라미터 확장. ${p##*/} 는 외부 프로세스를 안 띄운다. basename 호출보다 빠르고 $(...) 도 필요 없다
  • 부분을 꺼내야 하면 정규식. 캡처가 필요한 순간 글롭은 후보에서 빠진다. 버전 문자열 분해, 로그 필드 추출이 여기 해당한다
  • 수량이 관여하면 정규식. 「숫자 3~5자리」 같은 조건은 {3,5} 없이 표현하기 어렵다. extglob 으로도 개수 지정은 안 된다
  • 이식성이 걸리면 글롭 쪽이 안전하다. 정규식은 도구마다 방언이 갈리지만 기본 글롭은 POSIX 셸 전체에서 거의 같다. 단 [^...] 와 extglob 은 예외다

한글이 섞인 데이터를 정규식으로 다룰 때는 또 다른 문제가 붙는다. 음절 단위 매칭이 직관과 어긋나는 대목인데, 한글 정규식 함정 쪽에 따로 정리했다.

정리

같은 * 인데 답이 다른 이유는 하나다. 글롭의 * 는 스스로 「아무 문자열」을 뜻하고, 정규식의 * 는 앞에 있는 것을 반복시키는 연산자다. 여기서 ? 와 . 의 역할이 뒤바뀌고, 앵커링 기본값이 갈리고, 대괄호 부정 기호가 갈린다.

실무에서 기억할 것은 기호표보다 자리다. bash 안에서 case·[[ == ]]·${}·파일명 전개는 전부 글롭이고, 정규식은 [[ =~ ]] 하나뿐이다. 밖으로 나가면 grep·sed·awk·expr 이 정규식이고 find -name 은 다시 글롭이다.

그리고 이 영역은 shopt 한 줄로 동작이 바뀐다. nullglob·failglob·dotglob·extglob·globstar·globskipdots 가 각각 무엇을 켜고 끄는지 알고 있으면 「어제는 되던 게 오늘 안 된다」의 절반은 미리 짐작할 수 있다. 확인은 한 줄이다. shopt 를 인자 없이 쳐 보면 전부 나온다.

확인하지 못한 것

  • 모든 출력은 Windows 10 위의 Git Bash(MSYS2), GNU bash 5.2.37 한 환경에서만 받았다. 리눅스 네이티브 bash 나 macOS 에서 동일한지는 대조하지 않았다. 특히 파일시스템이 대소문자를 구분하지 않는 환경에서는 [a-z] 범위나 nocaseglob 관련 결과가 달라질 수 있다
  • zsh 와 ksh 는 이 기계에 설치돼 있지 않아 돌려 보지 못했다. zsh 는 글롭 문법이 상당히 확장돼 있어(수식자·정규식 글롭 등) 이 글의 「기본 글롭에는 반복 연산자가 없다」는 서술이 그대로 적용되지 않는다. 본문의 다른 셸 비교는 dash 하나로만 확인한 범위다
  • globskipdots 가 bash 5.2 에서 추가됐다는 것은 이 기계의 5.2.37 에서 옵션이 존재하고 기본 on 이라는 사실까지만 확인했다. 5.1 이하에서 옵션이 없다는 것은 직접 돌려 보지 않았다. 오래된 서버에 접속할 일이 있으면 shopt globskipdots 로 각자 확인하는 편이 낫다
  • GNU find 4.10.0 의 -regex 기본 방언은 -regextype 없이 .+ 를 받아들였다. 문서상 기본값은 emacs 계열인데, 어느 문법까지 통과하는지 경계를 전수로 시험하지는 않았다. 이식성이 필요하면 -regextype posix-extended 를 명시하는 편이 낫다
  • 로케일에 따른 [a-z] 범위 변화는 실측하지 않았다. 문자 클래스를 권한 것은 널리 알려진 권고를 따른 것이지 자체 실험 결과가 아니다
  • POSIX 명세 원문의 Pattern Matching Notation 절은 직접 열지 못했다. 표기 규칙은 GNU bash 매뉴얼의 해당 절로 대조했고, 명세 조문 자체를 인용하지는 않았다

참고 자료

  • Bash Reference Manual — Pattern Matching — *·?·[...] 의 정의, 대괄호 부정에 ! 와 ^ 를 모두 받는다는 서술, 맨 앞 점 규칙, extglob 의 다섯 표기
  • Bash Reference Manual — Filename Expansion — 파일명 전개가 언제 일어나는지, 맞는 것이 없을 때 패턴이 그대로 남는 동작과 nullglob·failglob 의 역할
  • Bash Reference Manual — The Shopt Builtin — dotglob·extglob·globstar·globskipdots·nocaseglob·nocasematch 각각의 기본값과 효과
  • GNU Findutils Manual — -name 이 파일명만 본다는 것, -regex 가 경로 전체와 전체 일치한다는 것, -regextype 으로 방언을 고르는 법
  • GNU Grep Manual — BRE 와 ERE 의 차이, 문자 클래스, 앵커 ^·$ 의 의미
  • POSIX Shell Command Language (The Open Group Base Specifications) — 셸 문법의 규범 문서. 파라미터 확장과 case 의 패턴 규정이 여기에 있다
  • 어디서나 동작하는 정규표현식 — 언어·도구 간 호환성 함정과 해법 — BRE·ERE·PCRE 방언 차이를 다룬 글. 이 글에서 다루지 않은 정규식 쪽 이식성 문제
  • 셸 인용부호 규칙 - 어느 따옴표가 무엇을 막는가 — 작은따옴표·큰따옴표·백슬래시가 각각 무엇을 차단하는지 전반
  • find·xargs 공백과 개행 함정 - 파일명 하나가 스크립트를 부순다 — -print0 과 -0 이 필요한 이유
  • 룩어헤드는 자리만 본다 - 너비 0으로 푸는 정규식 문제 — 「무언가가 아닌 것」을 정규식으로 표현하는 방법
  • 한글 정규식 함정 - 「아닙니다」 안에 「아니」가 없다 — 한글 데이터에서 정규식이 직관과 어긋나는 자리
