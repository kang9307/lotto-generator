과금된 56건 중 33건의 의심 행동, 4대 판별 신호와 전환 목표 재설계

2026-09-12 개발/인프라

모바일 애플리케이션을 출시한 개발자가 마케팅을 시작할 때 가장 직관적으로 선택하는 목표는 신규 이용자의 유입, 즉 「설치(Install)」다. 광고 플랫폼의 대시보드에 숫자가 찍히고 단말기에 앱이 깔리는 그래프가 우상향을 그리면 프로덕트가 성장하고 있다는 착각에 빠지기 쉽다. 그러나 플랫폼이 청구한 광고비만큼 설치 수가 늘어났음에도 불구하고, 활성 이용자 지표나 인게임 플레이 세션이 얼어붙은 듯 요지부동이라면 엔지니어링 관점에서 전혀 다른 가설을 세워야 한다.

이 글은 퍼즐 게임 Dayzle의 독립 개발자가 겪은 실제 앱 광고 집행 사례를 바탕으로, 과금된 설치 지표의 이면에 숨겨진 자동화 봇 팜의 생태계를 파헤친다. 광고 캠페인을 켜고 예산이 소진되는 과정에서 왜 스토어 다운로드가 아닌 구버전 바이너리가 실행되었는지, 플랫폼의 머신러닝이 어떻게 허위 설치를 우수 고객으로 착각해 예산을 낭비하게 만드는지, 그리고 소규모 개발자가 자동화 공격의 단가를 높여 방어선을 구축하려면 어떤 신호와 아키텍처를 준비해야 하는지 분석한다.

이 분석에서 인용하는 수치와 정황은 캐나다의 독립 개발자 Nick Abe가 2026년 9월 11일 공개한 Dayzle 게임 개발 기록에 근거한다. 특정 광고 플랫폼이 부정 행위를 방조하거나 공모한다는 결론을 내리기 위함이 아니며, 기록된 현상은 소규모 표본에서 확인된 엔지니어링 관측치다. 특히 전체 관측 모수가 2주간 과금된 설치 56건이라는 점을 명확히 밝히며, 개발자가 접수한 무효 트래픽 신고(Invalid Traffic Form)의 플랫폼 심사 결과 및 환불 확정 여부는 원문 작성 시점 기준으로 아직 발표되지 않은 상태다.

1. 관측된 수치 - 일 예산 CA$40에서 과금된 56건과 220달러의 실험

숫자와 논리를 다루는 퍼즐 앱 Dayzle을 운영하는 개발자 Nick Abe는 Android 사용자를 유치하기 위해 Google 앱 캠페인(Google Ads App campaign)을 시작했다. 일일 지출 예산은 40 캐나다 달러(CA$40)로 책정되었고, 초기 최적화 목표는 설치당 비용(Target Cost Per Install, tCPA) 1.50달러로 설정되었다. 캠페인 시작 후 며칠 동안은 예산이 거의 소진되지 않았다. 설정된 1.50달러라는 낮은 단가 내에서는 플랫폼 알고리즘이 적절한 설치 지면을 찾아내지 못했기 때문이다.

개발자는 테스트 차원에서 설치당 목표 단가 제한을 완전히 해제했다. 제한이 풀리자마자 알고리즘은 가속 페달을 밟았고, 하루 예산의 두 배에 달하는 CA$80가 순식간에 소진되면서 광고 관리자 화면에는 당일 21건의 신규 설치가 발생했다는 성공적인 지표가 보고되었다. 이후 2주간 캠페인이 지속되는 동안 총 220달러의 광고비가 집행되었으며, 플랫폼은 총 56건의 설치에 대해 과금을 청구했다.

과금된 56건의 실제 트래픽 분해

원시 분석 데이터를 통해 과금된 56건의 설치를 역추적했을 때 드러난 실제 구성은 기대와 완전히 달랐다. 56건이라는 작은 표본 안에서 이용자의 성격은 극단적인 세 그룹으로 갈라졌다.

  • 봇 의심 설치 33건: 과금된 전체 56건 중 33건(약 58.9%, 원문에서는 약 60%로 반올림하여 표기)이 인간의 조작으로 볼 수 없는 일관된 기계적 패턴을 보였다. 단 한 번 실행된 후 단 0초 동안 머물렀으며 다시는 앱을 열지 않았다.
  • 타깃 외 국가 유입 7건: 광고 캠페인의 타깃팅 설정에 전혀 포함되지 않은 국가에서 발생한 설치였다. 프록시 망이나 VPN 출구 노드를 통한 비정상 접속으로 분류되었다.
  • 실제 인간 이용자 13명: 전체 과금 설치 중 단 13명만이 실제 인간 사용자로 확인되었다. 이 13명의 유저는 2주 동안 총 92회의 게임 플레이를 완수하며 프로덕트를 정상적으로 소비했다.

여기서 주목해야 할 점은 표본의 절대적인 크기다. 전체 설치가 56건에 불과한 소규모 관측치라는 한계는 분명히 존재한다. 대형 모바일 게임사라면 일일 수만 건의 설치 데이터 속에서 33건의 이상치는 오차 범위 안의 잡음으로 묻혀 지나갔을 것이다. 그러나 1인 개발자의 작은 예산 환경이었기 때문에, 역설적으로 모든 개별 설치 이벤트의 타임스탬프와 기기 정보를 한 화면에서 1:1로 검증할 수 있었고 설치형 광고가 가진 구조적 취약점이 가감 없이 드러났다.

2. 대시보드 괴리의 실체 - Google 보고 21건과 관리자 1건의 충돌

문제가 수면 위로 드러난 결정적 계기는 광고 플랫폼의 보고서와 자체 서버 관리자 화면(Admin Panel) 사이의 심각한 불일치였다. 단가 제한을 풀고 CA$80가 소진된 날, Google Ads는 21건의 설치가 일어났다고 표시했으나 개발자의 자체 관리자 대시보드에는 신규 설치가 단 1건만 집계되어 있었다. 20건의 차이는 단순한 네트워크 지연이나 집계 배치 주기 차이로 설명할 수 없는 규모였다.

자체 관리자 대시보드가 20건을 누락시킨 기술적 원인을 추적한 결과, 관리자 화면의 실시간 집계 로직이 앱 클라이언트가 전송하는 「설치 일자(install date)」 파라미터에 의존하고 있다는 점이 확인되었다. 그런데 당시 유입된 클라이언트들은 이 설치 일자 필드를 아예 전송하지 않았다. 집계 대시보드를 건너뛰고 원시 이벤트 로그(Raw Analytics Export)를 직접 열어보자, 당일 21대의 새로운 Android 기기가 서버에 접속한 원시 로그 자체는 실재했다.

20대의 단말이 공유하던 기이한 프로필

원시 로그에 찍힌 21대의 단말기 중 대시보드에서 누락되었던 20대에는 소름 돋을 정도로 동일한 네 가지 특성이 각인되어 있었다.

  • 스토어 배포 중단 버전 실행: 20대의 단말은 모두 공식 구글 플레이 스토어가 며칠 전에 이미 배포가 중단되어 내려간 「구버전 앱 빌드」를 실행하고 있었다.
  • 출처 위장: 모든 기기의 패키지 인스톨러 속성(Installer Package Name)에는 정상적인 설치 경로인 com.android.vending(Google Play Store)이 적혀 있었다.
  • 화면 체류 0초: 앱을 최초 기동한 후 어떤 씬(Scene)이나 화면에서도 0초를 초과하여 머무르지 않았다.
  • 단 1회 실행 후 영구 이탈: 최초 실행 이벤트를 서버에 던진 이후 단 한 대도 두 번째 세션을 생성하지 않았다.

공식 스토어인 구글 플레이는 이미 새로운 버전이 릴리스된 상태에서 일반 사용자에게 이전 버전을 선택하여 내려받을 수 있는 인터페이스나 API를 제공하지 않는다. 일반적인 사용자라면 스토어에서 최신 빌드를 내려받았어야 한다. 그럼에도 불구하고 20대의 기기가 일제히 과거 버전을 실행했다는 사실은, 이 단말들이 스토어 망을 거치지 않고 외부 저장소에 미리 확보해 둔 바이너리를 강제로 밀어 넣었음을 뜻한다.

더욱 인위적인 점은 단말기의 하드웨어 파편화였다. 동일한 기계적 동작을 완수한 20대의 기기는 19개 주에 걸쳐 무려 28가지 서로 다른 스마트폰 제조사 및 모델 명칭을 달고 접속했다. 실제 단말기가 20대인데 모델명이 28종으로 기록되고 지역이 미국 전역으로 쪼개진 현상은, 가상 에뮬레이터 환경에서 프로필 속성(Device Fingerprint)을 무작위로 치환하는 봇 팜의 전형적인 흔적이다.

3. 가짜 설치의 작동 방식 - 구버전 APK 사이드로딩과 스토어 사칭

봇 팜은 왜 공식 플레이 스토어에서 앱을 정식으로 내려받지 않고 로컬에 저장해 둔 과거 버전의 APK를 사이드로딩(Sideloading)하는 방식을 취했을까? 여기에는 봇 팜 운영자들의 철저한 비용 계산과 탐지 회피 전략이 깔려 있다.

속도, 대역폭 비용, 그리고 스토어 탐지망의 우회

수천 대의 가상 인스턴스를 돌리는 봇 팜 입장에서 매번 수십 메가바이트의 APK 파일을 플레이 스토어 통신망을 통해 새로 내려받는 것은 막대한 외부 네트워크 대역폭 비용을 발생시킨다. 또한 스토어 CDN으로부터 파일을 다운로드하는 속도는 로컬 스토리지에서 패키지 매니저로 직접 파일을 밀어 넣는 속도에 비해 훨씬 느리다. 무엇보다 동일한 가상 단말 지문이나 데이터센터 IP 대역에서 구글 플레이 계정 로그인이 반복되고 대량 다운로드가 발생하면 구글의 기기 무결성 검증과 비정상 계정 탐지 시스템에 걸려 계정 풀 전체가 차단될 위험이 커진다.

따라서 봇 팜은 최초 1회 확보해 둔 대상 앱의 APK 파일을 로컬 디스크에 저장해 두고, 안드로이드의 패키지 관리자 명령을 이용해 기기 내부에서 고속으로 앱을 설치한다. 이때 패키지 인스톨러 메타데이터를 조작하여 마치 플레이 스토어가 설치를 주관한 것처럼 속인다. 스토어의 감시망은 피하면서 로컬 자원만으로 초고속 설치 사이클을 완성하는 것이다.

시청 전환(Engaged-view / View-through Conversion)의 악용

앱을 로컬에서 임의로 설치했다고 해서 광고 플랫폼이 이를 해당 광고 캠페인의 전환으로 자동으로 인정해 주지는 않는다. 봇 팜은 광고 플랫폼이 전환을 인정하는 귀속(Attribution) 메커니즘의 규칙을 정확히 파고든다.

  1. 최단 동영상 광고 시청: 봇 팜의 스크립트는 광고 그룹에 등록된 에셋 중 재생 시간이 가장 짧은 동영상 광고를 백그라운드에서 끝까지 시청한다.
  2. 광고 클릭 회피: 광고 화면을 터치하여 스토어 페이지로 넘어가는 링크를 클릭하지 않는다. 클릭은 웹뷰를 실행시키거나 외부 리디렉션을 거치므로 브라우저 레벨의 핑거프린팅이나 추가 탐지에 노출될 위험이 있다.
  3. 로컬 APK 강제 설치: 동영상 조회가 완료된 직후, 기기 내부의 로컬 경로에 캐시되어 있던 구버전 APK 파일을 무음 설치(Silent Install)한다.
  4. 앱 기동 및 첫 세션 신호 방출: 설치 완료 즉시 앱의 메인 액티비티를 강제 실행하여 광고 추적 SDK가 「앱 최초 실행」 이벤트를 서버로 전송하게 만든다.

Google Ads의 앱 캠페인 정책상, 사용자가 동영상 광고를 일정 시간 이상 시청한 후 특정 기간 내에 해당 앱이 기기에 설치되어 실행되면 이는 유효한 시청 전환(Engaged-view Conversion)으로 집계된다. 봇 팜은 동영상 재생과 로컬 바이너리 설치라는 두 가지 저비용 동작을 결합하여, 플랫폼 알고리즘에게 완벽하게 합법적인 전환이 일어난 것처럼 위장하고 과금을 유도한 것이다.

4. 정상 이용자와 봇을 가르는 4대 판별 신호와 오탐 분석

모바일 광고 트래픽에서 가짜 설치를 걸러내기 위해서는 단일 지표에 의존해서는 안 된다. 봇 팜은 개별 지표를 우회하는 데 능숙하지만, 복합적인 행동 신호가 결합될 때 기계적 한계를 드러낸다. Dayzle 사례에서 확인된 핵심 판별 신호는 크게 네 가지로 요약되며, 각 신호는 정상적인 인간 이용자에게서도 극히 드물게 발생할 수 있으므로 오탐(False Positive) 가능성을 함께 고려해야 한다.

신호 1: 화면 참여 시간 0초 (Zero Screen Engagement Time)

인간 사용자가 앱을 설치하고 처음 실행했을 때, 환영 화면이나 튜토리얼 텍스트를 인식하고 터치 조작을 수행하기까지는 최소 수 초의 인지적 지연 시간이 소요된다. 반면 봇 스크립트는 전환 확인 신호(Launch Ping)를 쏘자마자 즉시 프로세스를 백그라운드로 돌리거나 강제 종료한다. 원시 분석에서 체류 시간이 0.0초로 기록되는 세션의 집단 발생은 가장 강력한 기계적 징후다.

신호 2: 단 1회 실행 후 영구 이탈 (Zero Retention)

신규 유입된 사용자 집단 중 실제 사람이 섞여 있다면 앱에 실망하더라도 최소한 몇 초간 메뉴를 탐색하거나 며칠 뒤 다시 켜보는 잔존(Retention) 곡선이 완만하게 형성된다. 그러나 봇 단말 33대는 단 한 대의 예외도 없이 1회 기동 후 다시는 서버와 통신하지 않았다. 봇의 목적은 전환 인정과 리워드 획득일 뿐, 앱을 유지할 유인이 전혀 없기 때문이다.

신호 3: 스토어 미서빙 구버전 클라이언트의 집단 유입

스토어 배포 파이프라인에서 이미 폐기된 과거 버전의 해시값을 가진 바이너리가 광고 집행 시점에 갑자기 수십 대 단위로 실행되는 현상이다. 일반 이용자가 구버전을 쓰려면 백업 앱을 복원하거나 외부 사설 APK 사이트에서 수동으로 파일을 구해 깔아야 하는데, 광고를 본 직후 이런 복잡한 수작업을 집단으로 수행할 확률은 수학적으로 0에 수렴한다.

신호 4: 타깃팅 지역 외 국가에서의 기형적 유입

광고주는 특정 국가나 지역을 한정하여 캠페인을 집행한다. 그럼에도 불구하고 타깃 외 국가의 IP가 다수 잡히는 것은 봇 팜의 프록시 인프라가 완벽하게 통제되지 않았음을 의미한다. 봇 운영자가 전 세계에 흩어진 저가 프록시 풀이나 주거용 IP를 돌려가며 단말 지문을 변조하는 과정에서 물리적 네트워크 위치의 파편이 튀어나온 것이다.

표 1: 4대 판별 신호별 기술적 특징과 오탐(False Positive) 위험도 분석

위 표에서 보듯 개별 신호는 정상적인 예외 케이스를 가질 수 있다. 하지만 네 가지 신호가 한꺼번에 중첩되어 나타나는 순간, 그것은 더 이상 사용자의 자연스러운 이탈이 아니라 조작된 트래픽으로 확정할 수 있다.

5. 왜 「설치」는 구조적으로 실패하는 전환 목표인가

경제학에는 「어떤 척도가 목표가 되는 순간, 그 척도는 더 이상 좋은 척도가 되지 못한다」는 굿하트의 법칙(Goodhart's Law)이 있다. 앱 마케팅에서 이 법칙이 가장 잔혹하게 적용되는 영역이 바로 「설치」 목표 캠페인이다. 설치는 본질적으로 자동화 비용이 거의 0에 수렴하는 극도로 취약한 행위다.

자동화 비용이 0인 지표의 비극

현대 모바일 운영체제에서 앱의 설치와 최초 기동은 명령줄 인터페이스(CLI) 수준에서 단 몇 줄의 스크립트로 제어할 수 있다. 루팅된 단말이나 에뮬레이터 환경에서 adb install 명령으로 APK를 주입하고, monkey 도구로 패키지의 메인 인텐트를 호출하는 데는 1초도 걸리지 않으며 연산 자원도 거의 소모되지 않는다. 공격자 입장에서 달성 비용이 사실상 0원인 행위를 광고 플랫폼이 수 달러짜리 성과로 인정해 준다면, 그 행위는 필연적으로 시장에서 거래되고 사기의 대상이 된다.

머신러닝 알고리즘의 자기강화적 악순환 (Feedback Loop)

더 심각한 문제는 현대 프로그래머틱 광고 플랫폼의 머신러닝 엔진이 작동하는 방식이다. 광고 알고리즘은 광고주가 지정한 목표(설치)를 가장 저렴하고 빠르게 달성할 수 있는 사용자 세그먼트를 향해 노출을 집중하도록 설계되어 있다.

  1. 신호 감지: 봇 팜의 가상 단말들은 동영상 광고를 시청한 뒤 광고를 클릭하지 않고, 저장해 둔 설치 파일로 앱을 설치한 뒤 실행한다.
  2. 우수 세그먼트 오판: 광고 플랫폼의 머신러닝 엔진은 이 비정상적인 전환율을 감지하고, 해당 IP 대역과 지면을 「광고 반응도가 극도로 뛰어난 황금 잠재 고객군」으로 분류한다.
  3. 예산 몰아주기: 알고리즘은 광고주의 일일 예산을 봇 팜이 서식하는 지면으로 더욱 공격적으로 배분한다.
  4. 가짜 설치의 양산과 예산 고갈: 봇 팜은 몰려드는 광고를 바탕으로 가짜 설치를 무한 복제하고, 광고주의 통장에서는 광고비가 실시간으로 빠져나간다.

이것이 바로 개발자가 목표 CPA 제한을 풀자마자 하루 예산의 두 배가 증발해 버린 기술적 배경이다. 인간은 동영상 광고를 보고도 설치하지 않을 확률이 높지만, 봇은 기계적으로 설치를 완료한다. 알고리즘은 인간과 봇을 구분하지 못한 채 표면적인 전환율 지표만 추종하므로, 사기성 트래픽이 알고리즘을 훈련시키고 알고리즘이 사기 트래픽에 돈을 공급하는 치명적인 악순환의 루프가 완성된다.

6. 목표 후진 배치의 원리와 대가 - 「앱 실행」에서 「퍼즐 승리」로

봇 팜의 사기 루프를 끊어내기 위해 개발자 Nick Abe가 선택한 대응은 방어의 기준선을 근본적으로 뒤로 이동시키는 것이었다. 전환 목표를 단순히 앱을 켜는 단계인 「앱 오픈(Opened the app)」에서, 실제 게임을 플레이하여 승리 상태를 달성하는 「퍼즐 승리(Won a puzzle)」로 변경한 것이다.

공격 비용의 비대칭성 유발

이 전략의 핵심은 공격자가 지불해야 하는 자동화 비용을 강제로 끌어올리는 것이다. 앱을 켜고 빈 화면을 터치하는 스크립트는 범용 도구로 누구나 5분이면 짤 수 있다. 그러나 스도쿠나 논리 퍼즐의 화면 상태를 이미지나 뷰 계층으로 파싱하고, 게임 규칙에 맞는 정답을 계산하여, 정확한 셀을 터치해 승리 화면을 띄우는 봇을 만드는 것은 차원이 다른 작업이다.

봇 운영자가 특정 인디 퍼즐 앱 하나에서 가짜 전환을 뜯어내기 위해 전용 알고리즘을 개발하고 머신러닝 모델을 붙이는 것은 수지타산이 전혀 맞지 않는다. 보안의 목적은 난공불락의 성벽을 쌓는 것이 아니라, 「우리 앱을 터는 비용을 옆에 있는 다른 앱을 터는 비용보다 훨씬 비싸게 만들어 공격자의 시선을 돌리는 것」이다. 작은 규모의 앱에서는 전환 이벤트를 핵심 게임플레이 뒤로 숨기는 것만으로도 대다수의 범용 봇 팜을 자연 탈락시킬 수 있다.

방어자가 치러야 하는 대가 (Trade-offs)

하지만 전환 목표를 뒤로 미루는 설계가 장점만을 갖는 것은 아니다. 엔지니어링에는 공짜 점심이 없으며, 방어자는 다음과 같은 실질적인 대가를 치러야 한다.

  • 전환 모수의 극단적 감소: 설치한 모든 사용자가 첫 퍼즐을 끝까지 풀어 승리하지는 않는다. 실제 인간 이용자 가운데 첫 퍼즐을 끝까지 푸는 비율은 그보다 훨씬 낮다. 그 비율은 앱마다 다르고, 이 기록에도 수치는 없다. 전체 전환 이벤트 발생 건수가 급감한다.
  • 머신러닝 최적화 지연: 광고 플랫폼의 머신러닝 엔진이 유의미한 타깃팅 모델을 확립하려면 일정 기간 동안 충분한 건수의 전환 데이터가 꾸준히 공급되어야 한다. 모수가 줄어들면 알고리즘이 학습을 완료하는 데 훨씬 오랜 시간이 걸린다.
  • 표면적 획득 단가의 급등: 설치 1건을 기준으로 표기되던 단가가 승리 1건 기준으로 바뀌면서 표면 단가가 크게 오른다. 비즈니스 대시보드상의 표면 지표가 악화되어 마케팅 의사결정권자에게 심리적 저항을 줄 수 있다.

결국 최적의 전환 지점을 선택하는 것은 보안성과 마케팅 머신러닝 학습 속도 사이의 정교한 줄타기다. 자본이 풍부한 대형 서비스라면 초기 데이터를 희생하고 결제나 고급 레벨 달성으로 목표를 밀어붙일 수 있지만, 하루 수십 달러 단위로 생존해야 하는 인디 개발자에게는 「1회 퍼즐 승리」 정도의 진입 장벽이 경제학적으로 가장 합리적인 타협점이 된다.

7. 자체 계측과 교차 검증 - 소규모 개발자가 할 수 있는 것과 없는 것

이번 사건이 던지는 가장 뼈아픈 교훈은 「광고 플랫폼이 제공하는 대시보드만 바라보고 있는 개발자는 눈이 먼 상태와 다름없다」는 사실이다. 광고 관리자 화면은 플랫폼의 귀속 모델에 의해 계산된 집계 숫자만을 보여준다. 그 숫자가 진짜 사람의 손가락에서 나온 것인지, 가상 머신의 스크립트가 쏘아 올린 허상인지는 오직 개발자 자신의 오리진 서버와 클라이언트 원시 로그를 교차 검증해야만 밝혀낼 수 있다.

클라이언트 및 서버 측 최소 계측 구현 예시

소규모 개발자라도 앱 초기화 시점에 다음과 같은 최소한의 무결성 검증과 체류 시간 측정 로직을 구현해 두면, 이상 징후가 발생했을 때 즉각 원시 데이터를 추출할 수 있다.

// 클라이언트 초기화 및 세션 무결성 원시 텔레메트리 전송 개념 예시
function trackAppSessionIntegrity() {
    const sessionStart = Date.now();
    const clientBuildVersion = AppConfig.BUILD_VERSION; // 클라이언트 번들 빌드 버전
    const installerPackage = Platform.getInstallerPackageName(); // 설치자 패키지 속성

    let firstUserInteractionTime = null;

    // 첫 터치 또는 화면 전환 이벤트 발생 시 인지 시간 기록
    const registerInteraction = () => {
        if (!firstUserInteractionTime) {
            firstUserInteractionTime = Date.now();
            const timeToFirstTouchMs = firstUserInteractionTime - sessionStart;
            
            // 첫 상호작용까지의 시간이 비정상적으로 0에 가깝거나 지연된 경우 태깅
            Telemetry.sendEvent('session_engagement_start', {
                engagement_delay_ms: timeToFirstTouchMs,
                client_version: clientBuildVersion,
                installer: installerPackage
            });
        }
    };

    window.addEventListener('touchstart', registerInteraction, { once: true });
    window.addEventListener('click', registerInteraction, { once: true });

    // 프로세스 종료 또는 백그라운드 전환 시 총 체류 시간 산출
    window.addEventListener('visibilitychange', () => {
        if (document.visibilityState === 'hidden') {
            const totalDurationSec = (Date.now() - sessionStart) / 1000;
            
            // 참여 시간이 0초이거나 상호작용 없이 종료된 경우 무효 의심 플래그 설정
            Telemetry.sendBeacon('/analytics/raw_session_close', {
                session_duration_sec: totalDurationSec,
                had_interaction: firstUserInteractionTime !== null,
                client_version: clientBuildVersion,
                installer_source: installerPackage,
                is_zero_engagement: totalDurationSec <= 0.1 && !firstUserInteractionTime
            });
        }
    });
}

위와 같은 원시 이벤트가 저장소에 쌓여 있어야만 플랫폼이 "21건 설치 완료"라고 주장할 때 "자체 로그상 체류 0초 세션 20건, 구버전 바이너리 실행 20건"이라는 구체적인 팩트로 반박하고 대응할 수 있다.

할 수 있는 것과 할 수 없는 것의 경계

소규모 팀이 가용 자원의 한계를 인정하고 명확히 선을 긋는 것 또한 엔지니어링 전략의 핵심이다.

  • 소규모 개발자가 지금 할 수 있는 것:
    1. 전환 이벤트를 단순 설치에서 '핵심 게임 루프 1회 완료'로 격상하기.
    2. 관리자 집계 화면 외에 원시 분석 로그(Raw Event Export)를 확보하고 매일 교차 대조하기.
    3. 스토어에서 내린 과거 버전의 네트워크 요청을 백엔드 API 게이트웨이에서 즉시 426(Upgrade Required)으로 차단하기.
    4. 이상 징후 포착 시 주저 없이 광고 캠페인을 일시 정지하고 무효 트래픽 공식 조사 양식을 접수하기.
  • 소규모 개발자가 할 수 없는 것:
    1. 전 세계에 분산된 거대 주거용 프록시 및 에뮬레이터 봇 팜 네트워크를 원천 차단하기.
    2. 광고 플랫폼 내부의 머신러닝 입찰 알고리즘 로직을 직접 수정하거나 제어하기.
    3. 무효 트래픽 접수 건에 대한 환불 승인 여부를 플랫폼 승인 전에 임의로 확정 짓기.

8. 광고 생태계의 비대칭과 웹 트래픽 방어와의 본질적 차이

외부 트래픽의 위협을 다룬다는 점에서 앱 광고 봇 탐지는 웹 인프라의 DDoS 공격 방어와 자주 비교된다. 본 블로그의 선행 분석인 공개 문서 사이트의 DDoS 방어와 정상 트래픽의 경계에서 다루었듯, 웹 인프라 방어의 핵심은 공격 트래픽의 볼륨 속에서 정상적인 CI 도구나 독자의 요청을 살려내어 「서비스 가용성(Availability)」을 지키는 데 있다. 웹 DDoS는 서버의 CPU와 대역폭을 고갈시켜 사이트를 다운시키는 것이 목적이다.

그러나 앱 광고 봇 사기(App Install Ad Fraud)는 작동 메커니즘과 파괴의 경로가 정반대다.

  • 자원 소모의 부재: 봇 팜은 오리진 서버에 대규모 트래픽을 퍼붓지 않는다. 설치 1건당 단 몇 번의 API 호출만 발생시키므로 서버 CPU 사용률이나 네트워크 대역폭 모니터링에는 아무런 경보도 울리지 않는다.
  • 현금의 직접적 탈취: 웹 공격이 인프라 청구서를 늘린다면, 광고 봇은 광고주의 지갑에서 마케팅 예산을 직접 빨아먹는다. 서버가 가장 평온하고 한가할 때 비즈니스는 가장 빠르게 파산한다.
  • 정상성의 가면: 웹 DDoS 방어에서는 비정상적인 헤더나 캐시 우회 패턴을 찾아내 차단하면 되지만, 광고 봇은 플랫폼이 요구하는 '성공적인 고객의 모습'을 완벽하게 연기한다. 플랫폼 알고리즘에게 봇은 차단해야 할 적이 아니라 우대해야 할 VIP로 비친다.

결국 앱 광고 환경에서의 방어는 인프라 수준의 트래픽 필터링이 아니라, 「비즈니스 규칙의 설계와 경제적 유인의 차단」으로 이루어져야 한다. 자동화 비용이 0인 행동에 돈을 거는 시스템을 방치하는 한, 어떤 첨단 보안 장비도 광고비의 증발을 막아내지 못한다.

9. 확인하지 못한 것

투명한 기술 보고를 위해 이 글에서 기술적으로 완결 짓지 못하고 열어두는 사실 관계는 다음과 같다.

  • Google 무효 트래픽 조사 양식의 최종 판정 및 환불 결과: 개발자 Nick Abe는 공식 무효 트래픽 신고 양식(Invalid Traffic Form)을 제출하고 결과를 기다리는 중이라고 밝혔으나, 환불 승인 액수 및 플랫폼 측의 최종 회신 내용은 원문 발표 시점 기준으로 공개되지 않았다.
  • 봇 팜의 구버전 APK 파일 수집 경로 및 배포망: 봇 팜이 공식 스토어에서 내려간 과거 특정 빌드의 APK 바이너리를 어떤 경로로 사전 스크래핑하여 보관했는지, 그리고 가상 단말 클러스터에 이를 동기화한 구체적인 배포 호스트 주소는 원문 분석 데이터에 명시되어 있지 않다.
  • Android 플레이 인스톨 리퍼러 라이브러리의 런타임 페이로드 규격: 구글 개발자 포털의 실시간 렌더링 제약으로 인해 최신 Play Install Referrer API가 반환하는 내부 암호화 토큰과 응답 속성의 완전한 필드 명세를 원문 정적 수집 단계에서 교차 검증하지 못했다.
