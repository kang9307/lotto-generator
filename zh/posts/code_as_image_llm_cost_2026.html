把代码渲染成图片能降低LLM Token成本?pxpipe与视觉Token计价的漏洞

文本Token与图像Token为何计价方式不同 - 原理、准确率局限与提示缓存对比

2026-07-06 IT/技术

引言: 一张图片比文本更便宜,这个说法奇怪吗

降低AI API费用最常见的办法,是把提示词写短一点,或者打开缓存。但2026年7月初,一个在GeekNews(hada)上被推荐的开源项目pxpipe走了完全不同的路线: 把代码、日志这类体积庞大的文本上下文渲染成PNG图片,再把这张图片通过LLM的视觉(图像识别)通道发送出去。项目仓库的简介把这件事概括为「通过把上下文渲染成图片来削减token用量」(来源: GitHub)。实测数字也不小 —— 有报告称,在真实流量上端到端成本出现了相当幅度的下降。

本文不打算照搬宣传数字,而是从token计价结构的角度拆解这个技巧为何可能成立,分析它的可信边界,并把它放到提示缓存、上下文压缩等既有正统手段旁边,讨论应该如何在实践中定位这项技术。需要先说明: 截至2026年7月,这项技术仍处于实验阶段,本文引用的数字仅在特定模型、特定工作负载上得到过验证,这一前提贯穿全文。

1. 文本Token与图像Token,本就用不同的尺子计量

理解这项技术的起点,是认清两种模态的计价基础存在本质差异。

1.1 文本token: 与字符数老老实实成正比

LLM处理文本时,BPE(字节对编码)系的分词器会把字符串切成子词单元。token数量基本上与字符、子词片段的数量成正比。把100行代码以文本形式发送,计费就大致对应这100行的量——不管代码密不密,字符数就是成本。

1.2 图像token: 由像素面积和分块数量决定

图像输入遵循完全不同的规则。主流提供商计算图像token数时,依据的不是「图里画了什么」,而是「这张图有多少像素、被切成多少个分块(tile)」。

提供商图像token计算方式(据公开文档,截至2026年7月)
Anthropic(Claude)大致与像素面积成正比,约为(宽×高)/750
Google(Gemini)384px以下固定258 token,超过则按768×768分块计算,每块258 token
OpenAI(GPT)缩放后按分块或patch切分,每个分块/patch固定token数加基础成本

具体数值会随模型代际调整,这里仅供参考方向,不代表精确值。

1.3 核心差异: 计价与内容密度无关

只要像素尺寸相同,不管图片里塞满文字还是几乎空白,图像token的成本都一样。而文本token的成本则老老实实地随字符数增长。正是这种计算方式上的差异,构成了pxpipe所利用的漏洞。

2. 把代码画成图片为何更便宜 - 机制分析

pxpipe的核心洞察很简单: 把代码、JSON、工具执行日志这类字符密集的文本,用小字号渲染进一张图片,就能用远少于文本token的图像token传递同样的信息量。

2.1 把文本密度塞进像素里

据项目方描述,在真实流量中,密集的代码/JSON/工具输出每个图像token约能承载3.1个字符,而文本token每个约只承载1个字符。也就是说,把同样的文本渲染成图片发送,理论上能以约三分之一的token数传递相同的字符量。

2.2 已公开的实测压缩比

公开的实测数据也支持这一点。在对约1.3万条真实请求的观察中,端到端成本据报下降约59%(从100美元降到约41美元);随后在约8,900条应用了压缩的请求区间里,降幅据报达到约70%。有一个案例提到,原本以文本形式约需2.5万token的内容,压缩成图像后仅约2,700 token —— 大致是9倍的压缩比。不过这些数字是在编程智能体反复出现的上下文这一特定工作负载上优化得到的,换成别的工作负载,降幅可能相差很大。

2.3 本质上是钻价格体系空子的套利

冷静地看,这与其说是压缩技术本身的进步,不如说更接近一种钻价格体系空子的套利(arbitrage): 各家提供商设计图像计价体系时,默认的是「照片那样信息密度较低的图像」,并未把「画满密集等宽字体文本的图像」纳入考量。pxpipe实质上是把视觉输入通道挪用成了一套事实上的文本压缩编解码器。

3. 准确率的代价 - 视觉不等于OCR

这里有一个必须明确的区分: 模型「读出」图像中的文字,和扫描仪对文档做OCR并不是一回事。

3.1 patch嵌入与「看似合理的自信」

视觉编码器把图像切成一个个patch并转成嵌入向量,语言模型再从这些嵌入向量中重建出「看起来合理」的文本。当字号偏小或文字密集时,某个像素patch可能与多个候选字符产生模糊重叠,模型便会填入语境上最说得通的那个字符。对大多数散文或代码逻辑而言,这种「合理性」与原文是一致的,但并非总是如此。

3.2 实测: 精确字符串还原的差异

相关测试中,让模型从图像还原随机生成的12位十六进制字符串,结果显示不同模型之间差异很大。有的模型在15个样本中答对13个,而另一个模型15个里一个都没能精确还原。更麻烦的是,这种失败不会以「不知道」的报错形式出现,而是自信地给出一个看似合理却错误的字符串——项目方将这类失败称为「静默虚构(silent confabulation)」。

3.3 压缩比与准确率的曲线

这种权衡并非pxpipe独有,学界已经对其做过量化研究。2025年底发布的一项光学上下文压缩研究(DeepSeek-OCR)指出,当文本token数在图像token数的10倍以内(压缩比不超过10倍)时,还原精度可维持在约97%;但把压缩比推高到20倍,精度会跌落到约60%左右。也就是说,压缩程度越高,准确率不是缓慢下滑,而是断崖式下跌。

3.4 为何「静默」失败更危险

文本API一旦超过token上限,会明确报错或出现肉眼可见的截断。而从图像中被误读的字符串,在响应格式上看起来完全正常——除非专门去核对这个值,否则根本无从察觉错误。如果是需要人工再看一遍的工作流,这种风险相对较低;但如果结果会直接流入自动化流水线,风险就会不断累积。

4. 哪些场景值得用,哪些场景有风险

这项技术的价值,最终取决于如何对工作负载做分诊。

4.1 适合的场景

系统提示词、工具文档这类大体固定、只需传达大致意思即可的背景上下文;跨多轮累积的对话历史中,精确数值已不再重要的较早片段;以及只是用来粗略参考、只需抓住「大意」的海量日志或文档,都比较适合这种方式。

4.2 有风险的场景

哈希值、API密钥、密钥、精确的行号、坐标、补丁(diff)这类只要错一个字符含义就完全不同的值,以及这些值会被直接用于后续字符串比对或自动应用的工作负载,都与这种方式不太兼容。pxpipe自身也是通过把最近的对话轮次、用户消息、模型输出以及不在白名单内的模型统统保留为文本、不做图像化,来管理这部分风险的。

4.3 「依赖特定模型」这一风险

这个技巧的实际效用,完全取决于特定模型读取图像中文字的准确程度。据报道,该项目默认只对图像误读率较低的少数模型自动启用图像化,而误读率相对较高的其他顶尖模型则仅作为可选项开放。今天在某个模型上行得通的技巧,换到该模型的下一版本或另一家提供商的模型上,误读率可能完全不同,结果也会随之改变——这是一种可能因为厂商一次更新就悄悄失效的优化手段。

5. 与正统的提示成本优化手段对比

把图像渲染和提示缓存、上下文压缩放在一起比较,三者的性质差异就很清楚了。

5.1 提示缓存: 无损,但要求重复

当多个请求共享同一个前缀(系统提示词、固定文档等)时,服务端复用已经计算好的注意力键值张量,省去该部分的重复计算成本。主流提供商普遍支持这项功能,据公开资料,命中缓存时该部分的单价通常会大幅下降(常见报道在标准输入价的九成左右)。关键条件是把「静态内容放前面、可变内容放后面」以保证前缀能够重复出现,而在这个过程中原文不会损失任何一个字符。

5.2 上下文/语义压缩: 受控的损失

基于摘要的压缩工具会有意剔除或改写那些被判定为「不那么重要」的句子和token。这同样会造成损失,但这种损失是按重要度评分等受控标准来决定「丢弃什么」的结果。

5.3 图像渲染: 难以受控的损失

它与上述两种方式性质不同。它不丢弃也不概括信息,而是保持内容原样不变,只是把承载它的模态从文本换成图像。压缩确实发生了,但损失会出现在哪里,使用者很难控制——哪个字符会被误读,取决于字体、排版和模型当时的状态,难以预测。不过与缓存不同的是,它也能用于从不重复的内容(每次都是全新的代码或日志),因此更适合理解为瞄准了缓存触及不到的那部分场景。

6. 结论 - 实践中该如何取舍

成本优化比较合理的顺序是先缓存 → 再语义压缩 → 最后才是图像渲染。缓存和压缩要么无损、要么损失可控,验证成本也低。图像渲染应放在最后,而且只在不需要精确数值的场景中谨慎试验较为安全。

如果决定采用,务必用自己的实际工作负载搭建一个黄金测试集,衡量图像化前后实际数值出错的比例是否上升。截至2026年7月,能良好支持这项技术的模型有限,而且不同厂商之间,甚至同一厂商的下一代模型,误读率都可能不同,这一点必须提前假设。哈希、密钥、精确坐标和行号这类内容所在的区段,绝不应该图像化,而应保留为文本——为了省一点成本,却让错误的数值悄悄流入下游系统,才是这项技术最现实的风险。
