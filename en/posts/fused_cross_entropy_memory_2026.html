Saving Memory on Cross Entropy Loss - Why the LM Head Eats GPU Memory in LLM Training

Why logits become the memory bottleneck in long-context, large-vocab LLM training, and how Fused Linear Cross Entropy avoids it

Jul 7, 2026 Tech & IT

Intro: Training Doesn't Blow Up at Attention - It Blows Up at the Last Line

If you have ever trained an LLM, you have probably hit this moment. You sized the model, the batch, and the sequence length carefully, convinced GPU memory was comfortably enough - and then training died not in attention, not in the feed-forward block, but at the very last line: computing the loss. An analysis published by Trillion Labs in early July 2026 tackled exactly this. While training a 16B-scale model on sequences around 8K tokens, a single call to compute the cross-entropy loss consumed over 30GB of memory at once, killing the run - a real incident the post walks through in detail.

Rather than repeat that post's numbers verbatim, this piece unpacks, in my own words and concept-first, why loss computation right after the LM head becomes a memory bottleneck, and what idea lets you compute the same loss without ever materializing the full logits tensor. As of July 2026, this optimization is no longer a lab curiosity - it is already baked into several training libraries in everyday use.

1. Why the LM Head and Cross Entropy Become the Bottleneck

1.1 The Hidden State Is Small; the Logits Are Huge

What comes out of the transformer body is one hidden-state vector per token, typically a few thousand dimensions (D). But predicting the next token requires turning that vector into a score for every entry in the vocabulary (V) - the logits. The catch is that V dwarfs D. Recent models carry vocabularies of 130K to 260K tokens, while the hidden dimension is often only a fraction of that. Every single token's D-sized vector balloons into a V-sized row of logits, and once you multiply across the whole sequence and batch, the logits tensor can end up larger than the model weights themselves - a strange inversion.

1.2 Vocabularies Grew, and So Did Context

Vocabularies grew to handle multilingual text, code, and special tokens more precisely; context grew because people want to feed in whole documents, codebases, and conversation histories. Both trends make sense on their own, but when they grow together, the logits tensor (batch × sequence × vocab) balloons along two axes at once. When a vocabulary in the low hundred-thousands meets a sequence length of similar scale, it is not unusual for the logits tensor alone to reach tens of gigabytes, per reported cases.

1.3 Why a Fleeting Tensor Still Causes Trouble

What makes this worse is that this giant tensor is not something you actually need to keep around. It exists briefly to compute a single loss value and is meant to be thrown away immediately - but during that brief moment, it is the single largest chunk of memory on the GPU. The paradox is that, for many training setups, the memory budget blows not in attention or the feed-forward layers but in this last line.

2. Why Not Just Chunk It? - Where Naive Chunking Falls Short

2.1 Splitting the Sequence Into Pieces

The intuitive first fix is to split the sequence into chunks, computing logits and loss for each chunk separately and discarding them right away. This clearly shrinks the size of the logits materialized at any one instant. But measured in practice, this approach reportedly fails to cut peak memory for the whole training step by as much as you would expect.

2.2 The Computation Graph Sticks Around

The reason lies in backpropagation. A deep learning framework needs each chunk's forward-pass results to compute gradients during the backward pass, so it has to hold every chunk's computation graph until backward actually runs. In other words, no matter how finely you chunk, if every chunk's graph piles up in memory waiting for the final backward pass, peak memory barely moves. Related experiments reportedly found that increasing the chunk count left peak memory nearly flat while latency kept climbing instead. The direction - "split it up" - is right; what actually matters is when you let go of the graph.

3. The Idea Behind Fused Linear Cross Entropy

3.1 Fusing the Projection and the Loss

FLCE's core move is to fuse the LM head's final linear projection with the cross-entropy computation on its output into a single operation. As each chunk is processed, the loss is computed the instant that chunk's logits are produced, and the logits themselves are discarded without hesitation before moving to the next chunk.

3.2 Computing Loss Without the Full Logits

Cross entropy, in theory, requires a softmax normalization over the entire vocabulary. But the values that normalization needs - a running maximum and a running sum of exponentials - can be accumulated incrementally by sweeping through the vocabulary piece by piece. This "streaming update" idea is the same one used in FlashAttention-style attention optimizations: it reaches the same result without ever laying the whole thing out in memory at once. As a result, loss can be computed by momentarily loading a small chunk onto the GPU and letting it flow through, with no need to lay out the full logits anywhere.

3.3 Computing and Flushing Gradients on the Spot

The real trick is in how backward is prepared. FLCE computes the gradient with respect to each chunk's logits right there in the forward pass. Once that gradient is immediately routed into the input direction (the gradient with respect to the hidden state) and the LM head weight direction (the weight gradient, accumulated chunk by chunk), there is no longer any reason to hold onto that chunk's logits or its gradient. When backward actually executes, it merely scales these already-computed, far smaller results. The upshot is that the large, short-lived tensor called "logits" never gets registered in the computation graph for long. This is not a change to the math - it is a redesign of which intermediate results get held, and for how long.

4. How This Actually Gets Implemented

4.1 Liger Kernel

The most common way this idea reaches practitioners is LinkedIn's open-source Triton kernel collection, Liger Kernel, and its FusedLinearCrossEntropy. It reportedly applies with just a few lines added to a Hugging Face model, and is built to work alongside distributed training stacks like PyTorch FSDP and DeepSpeed. Public materials report memory savings of several times over at vocabularies in the low hundred-thousands - figures that can vary substantially by model architecture, GPU, and configuration.

4.2 The Optimization Baked Into Training Frameworks

Beyond Liger Kernel, several fine-tuning tools have shipped their own implementations of a similar idea. One fine-tuning framework reported a noticeable increase in the context length it could handle on the same hardware after applying a chunked, fused loss. Across these examples, the same skeleton keeps showing up: compute chunk by chunk, and finish the gradient inside each chunk.

4.3 Lower-Level Kernels

Trillion Labs's own FLCE implementation reportedly used not Liger but QuACK as its reference - a collection of low-level CUTLASS/CuTe kernels from Tri Dao's lab (Dao-AILab). QuACK focuses on pushing a handful of operations - RMSNorm, softmax, cross entropy - to the limit on recent GPU architectures (H100/B200-class). Even for the same underlying concept, an ecosystem of distinct implementations already coexists, differing in how tightly they are hand-tuned to a given hardware generation.

5. The Practical Payoff

5.1 Longer Context, Bigger Batches

What this optimization means in practice is simple: whatever memory you save at the loss-computation stage, you get to spend on a longer context or a bigger batch on the same GPU. One fine-tuning tool reportedly reported a noticeable increase in the context length it could fit on a single GPU after adopting a fused, chunked cross entropy. The effect tends to be more pronounced the larger the vocabulary and the longer the context.

5.2 The Savings Vary by Workload

That said, it is risky to treat any single savings figure as a fixed constant. Vocabulary size, hidden dimension, sequence length, batch size, and which kernel implementation you use all shift the practical effect considerably. Various public benchmarks report savings ranging from several-fold to roughly 80-90%, but these are figures observed under specific conditions - not a guarantee that transfers to every setup.

6. Trade-offs and Limits

6.1 Not a Free Lunch

Because computation is split into chunks, there is room for more kernel launches and overhead than a single, one-shot computation. Simple, education-oriented implementations reportedly can even run slower than the standard approach because of this overhead. Production-grade kernels are carefully tuned to minimize that cost, but it is not safe to assume memory always drops while speed stays exactly the same.

6.2 The Homework Called Numerical Stability

Updating a softmax normalization value in a streaming, piece-by-piece fashion is trickier to implement correctly than computing it all at once. Mishandling where floating-point error accumulates can subtly throw off the loss value or the gradients, so validating accuracy is essential if you implement a kernel yourself.

6.3 Not a Silver Bullet

What this technique reduces is strictly the memory used by the LM head and the loss computation. Other consumers - the attention KV cache, intermediate activations, optimizer states - are untouched. FLCE is best understood not as a universal fix for training-memory pressure, but as an optimization aimed precisely at one specific bottleneck that stands out exactly when vocabulary and context both grow large together.

7. Conclusion - What to Check Today

The practical takeaway from this analysis is straightforward. If you are writing your own training loop and working with a large vocabulary or long context, it is worth checking whether the logits tensor is what forms the tallest peak on your memory-usage graph. If you are already on a familiar stack like Hugging Face Trainer or Axolotl, checking whether a fused cross-entropy option such as Liger Kernel is already integrated is far more practical than writing a kernel yourself. And whatever savings figure you come across, treat it as a reference point rather than a promise until you measure it against your own model size, vocabulary, and context length.
