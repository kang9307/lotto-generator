아직도 Emacs를 쓰는 사람이 있나요? — 50년 된 에디터의 생명력

VS Code·Cursor·AI 에디터가 득세하는 2026년에도 Emacs를 선택하는 이유 — 확장성, org-mode, 해커 문화, 그리고 AI 통합

2026-06-22 개발/인프라

서론: "아직도 Emacs 써요?"

GeekNews에 올라온 토픽 하나가 조용한 파문을 일으켰다. "아직도 Emacs를 쓰는 사람이 있나요?" 29점이라는 점수는 숫자 이상의 의미를 담고 있다. VS Code가 개발자의 75.9%를 흡수하고, Cursor·Claude Code 같은 AI 네이티브 에디터가 급부상하는 시대에, 50년 된 텍스트 에디터를 들고 나온 질문이 반향을 얻었다는 것은 단순한 향수가 아니다.

Emacs는 1976년 Richard Stallman이 MIT AI 연구실에서 처음 만들었다. 이후 GNU Emacs로 발전해 지금도 개발이 계속되고 있다. 2026년 6월 기준 최신 안정 버전은 GNU Emacs 30.2(2025년 8월 14일 출시)다. 50년 된 소프트웨어가 여전히 새 버전을 내놓고, 새로 입문하는 개발자가 있다. 왜인가?

이 글은 Emacs 예찬론이 아니다. 또 Emacs는 낡았다는 비판론도 아니다. "왜 이 에디터가 아직 살아 있는가"라는 질문을 진지하게 들여다보고, 2026년 AI 코딩 시대에 에디터 선택이 무엇을 의미하는지 분석한다. 특정 에디터를 권하기보다, 에디터 선택이라는 결정의 본질을 짚는다.

1. 50년 생존의 이유 — 에디터가 아닌 플랫폼

1.1 에디터가 아닌 Lisp 인터프리터

Emacs를 텍스트 에디터라고 부르면 이미 틀렸다. 정확히는 Emacs Lisp 인터프리터 위에 구축된 텍스트 편집 환경이다. 이 차이가 50년 생존의 핵심이다.

VS Code는 JSON 설정과 플러그인으로 동작을 바꿀 수 있지만, 에디터의 핵심 동작 방식 자체를 재작성하기는 어렵다. Emacs는 다르다. 커서가 움직일 때, 키를 누를 때, 파일을 저장할 때 — 이 모든 이벤트에 Lisp 함수를 끼워 넣을 수 있다. 에디터의 어떤 동작이든 프로그래밍으로 교체하거나 확장할 수 있다. 이것이 "Emacs는 플랫폼"이라는 말의 의미다. 사용자가 원하는 방향으로 에디터 자체를 다시 설계할 수 있는 것이다.

이 구조 때문에 Emacs 생태계에는 일반 에디터 플러그인 수준을 넘는 것들이 생겨났다. Magit(Git 클라이언트), mu4e(이메일 클라이언트), elfeed(RSS 리더), dired(파일 관리자), org-mode(생산성 시스템). 이것들은 Emacs 안에서 동작하는 별개 앱에 가깝다. 그리고 이 모든 것이 동일한 키바인딩 체계와 버퍼 모델로 연결된다.

1.2 OS처럼 쓰는 사람들

GeekNews 토론에서 한 사용자는 자신의 컴퓨팅 흐름을 이렇게 설명했다. Git → Magit, 이메일 → mu4e, RSS → elfeed, 노트·TODO·캘린더 → org-mode, 파일 관리 → dired. 개발 외 작업 대부분이 Emacs 안에서 이루어진다. 이쯤 되면 Emacs는 에디터가 아니라 개인 컴퓨팅 환경 그 자체다.

이런 사용자에게 "VS Code로 바꿔라"는 말은 단순한 에디터 교체가 아니다. 수년간 축적한 설정, 키바인딩 근육 기억, org-mode 데이터베이스, 커스텀 워크플로 전체를 버리는 것이다. 전환 비용이 엄청나게 높다. 이것이 충성도의 원천이기도 하지만, 이미 깊이 투자한 사람들이 계속 머무는 이유이기도 하다.

2. org-mode — 대체재 없는 킬러 앱

2.1 org-mode는 무엇인가

Emacs 사용자들이 꼽는 최대 장점은 거의 항상 org-mode다. org-mode는 Bastien Guerry를 비롯한 커뮤니티가 수십 년에 걸쳐 발전시킨 평문 기반 생산성 시스템이다. 단순히 나열하면 이렇다.

  • 노트 작성 및 구조화(헤딩, 링크, 표)
  • 프로젝트·태스크 관리(TODO 상태, 우선순위, 태그)
  • 시간 추적(CLOCK IN/OUT 자동 기록)
  • 캘린더·어젠다 뷰(기한, 반복 일정)
  • 코드 블록 실행(org-babel — Python, Shell, SQL 등 다중 언어)
  • 다양한 포맷 내보내기(HTML, PDF, LaTeX, Markdown, EPUB)

이 모든 것이 단일 평문 파일 체계에서 동작한다. 텍스트이므로 Git으로 버전 관리하고, grep으로 검색하고, 어떤 에디터로도 열 수 있다. 그러나 Emacs의 org-mode에서 열었을 때만 모든 기능이 살아난다.

2.2 왜 대체재가 없는가

Notion, Obsidian, Roam Research, Logseq — 모두 훌륭한 도구다. 그러나 이것들은 각각 org-mode의 일부를 구현할 뿐이다. 코드 블록을 실행하고 그 결과를 문서에 바로 삽입하는 것(org-babel), 어젠다에서 태스크를 뽑고 CLOCK으로 시간을 재는 것, 모든 것이 Emacs Lisp으로 프로그래밍 가능한 것 — 이 세 가지를 함께 갖춘 도구는 아직 없다.

개발자에게 특히 의미 있는 것은 org-babel이다. Python으로 데이터를 가져오고, 그 결과를 표로 정리하고, 그 표를 LaTeX로 내보내는 일련의 과정이 하나의 org 파일 안에서 재현 가능하게 기록된다. 이것은 노트 앱이 아니라 문학적 프로그래밍(literate programming)의 실용적 구현이다.

3. 학습 곡선과 보상 — 정직한 계산

3.1 왜 어려운가

Emacs의 학습 곡선이 악명 높은 데는 이유가 있다. 첫째, 키바인딩 체계가 현대 관습과 다르다. C-x C-s로 저장, C-x C-f로 파일 열기 — 이것은 수십 년 전에 설계된 체계다. 현대 Ctrl+S, Ctrl+O에 익숙한 손가락은 처음에 반란을 일으킨다. 둘째, 설정이 Lisp이다. JSON이나 YAML로 설정하는 현대 도구와 달리, Emacs 설정은 Emacs Lisp 코드 작성이다. 배울수록 강력해지지만 진입 장벽이 높다. 셋째, "올바른 방법"이 너무 많다. 순정 Emacs, Doom Emacs, Spacemacs, 직접 구성 — 어디서 시작할지 막막하다.

3.2 Doom Emacs와 Spacemacs가 바꾼 것

이 진입 장벽을 낮춘 것이 사전 구성 배포판이다. Doom Emacs는 Vim 스타일 키바인딩(Evil mode)과 함께 현대적 패키지를 최적화 구성해 제공한다. Spacemacs는 Vim과 Emacs를 통합한 레이어 기반 구성이다. 이것들을 쓰면 처음부터 Lisp 설정을 쓰지 않아도 된다. Vim 유저라면 Evil mode 덕분에 손가락이 익숙한 채로 Emacs 생태계에 진입할 수 있다.

2026년에는 AI 도움도 등장했다. gptel로 LLM에게 Emacs Lisp 코드를 물어보면 설정 작성 장벽이 낮아진다. "이 기능을 어떻게 설정하나"를 물어보고 결과를 init.el에 붙이면 된다. 예전에는 매뉴얼과 mailing list를 뒤지던 일이 대화형 도움으로 바뀌었다.

3.3 투자 대비 수익 계산

한 개발자의 계산이 현실적 기준점을 제공한다. Emacs로 하루 15분을 절약한다면 연간 약 65시간, 3일에 가까운 시간이 확보된다. 10년이면 30일이다. 이것은 과장된 수치가 아니다. 근육 기억이 형성된 Emacs 사용자는 메뉴 탐색 없이 키보드만으로 파일 탐색, 검색, 치환, 버퍼 전환, Git 조작 전부를 한다. 다만 이 30일의 절약이 실현되려면 초기에 100시간 이상의 투자가 선행된다. 장기 경력을 생각하는 개발자에게는 수지가 맞는 계산이지만, 빠른 생산성이 필요한 지금 당장의 프로젝트에는 맞지 않는 전략이다.

4. 해커 문화와 철학 — Emacs가 상징하는 것

4.1 자유 소프트웨어 운동의 첫 킬러 앱

GNU Emacs는 단순한 소프트웨어가 아니다. Richard Stallman이 1984년 GNU 프로젝트를 시작할 때 첫 번째로 만든 도구다. 프리 소프트웨어가 상용 소프트웨어에 필적할 수 있음을 처음으로 입증한 사례로 꼽힌다. Emacs를 쓰는 것에는 이 역사와 철학이 따라온다.

Stallman은 MIT AI 연구실의 해커 문화에서 왔다. 소스를 공개하고, 다른 사람이 수정할 수 있게 하고, 소프트웨어는 공유돼야 한다는 철학이다. GNU Emacs는 그 철학의 구현체다. 이것이 Emacs 커뮤니티가 독특한 결속력을 가지는 이유다. 단지 에디터를 쓰는 것이 아니라, 특정 기술 윤리에 동의하는 것이기도 하다.

4.2 키보드 위의 자율성

Emacs 사용자들이 공통적으로 강조하는 것은 마우스 없이 일할 수 있다는 것이다. 이것은 취향 문제가 아니라 생산성 문제다. 손이 키보드에서 마우스로, 마우스에서 키보드로 이동하는 시간은 반복되면 상당한 낭비가 된다. Emacs의 키바인딩 체계는 이 전환을 최소화하도록 설계됐다. 익숙해진 사용자는 "키보드가 손가락의 연장"이라고 표현한다.

이 자율성은 SSH 환경에서 더 빛난다. 서버에 SSH로 접속한 터미널에서, 그것도 느린 연결에서 Emacs는 GUI 없이 완전한 기능을 발휘한다. VS Code는 Remote SSH 익스텐션으로 이를 보완했지만, 연결이 끊기거나 리소스가 제한된 환경에서는 여전히 터미널 기반 에디터가 유리하다. Emacs를 원격 서버의 상시 편집 환경으로 쓰는 개발자들이 많은 이유다.

5. 현황 수치 — Emacs는 얼마나 쓰이나

5.1 솔직한 점유율

수치는 냉정하다. 2026년 6월 기준으로 보면, Stack Overflow 2025 개발자 설문에서 VS Code는 75.9%의 사용률을 기록했다. Emacs는 LinuxQuestions 폴에서 8~9% 수준이며, 이 수치조차 Vim/Neovim의 37~38%에 한참 못 미친다. 한때 Vim과 에디터 전쟁을 벌이던 Emacs는 이제 비교가 무색한 소수파가 됐다.

AI 네이티브 에디터로 넘어가면 격차는 더 크다. Cursor가 단숨에 17.9%를 점유하고 Claude Code가 9.7%를 기록한 반면, Emacs는 통계에 잡히지 않을 만큼 작은 숫자다. 인기 측면에서 Emacs를 변호할 방법은 없다.

5.2 그래도 활발한 개발

그러나 개발 활동은 다른 이야기다. GNU Emacs 30.2는 2025년 8월에 출시됐다. 주요 업데이트 내역을 보면 소수 취미 프로젝트가 아님을 알 수 있다.

  • 네이티브 컴파일 기본화: Emacs Lisp를 기계어로 AOT 컴파일(libgccjit 활용), Magit·org-mode 실행 속도 대폭 향상
  • which-key 내장: 외부 패키지 없이도 키바인딩 힌트 표시
  • EditorConfig 내장 지원
  • Tree-Sitter 지원 확대: Elixir, HEEx, HTML, Lua, PHP 등 새 언어 모드
  • 안드로이드 네이티브 실행 지원(터치스크린, 가상 키보드)
  • JSON 파싱, 서브프로세스 처리 성능 개선

이 목록은 주류 에디터에 뒤지지 않는 현대화 노력이다. 옛 방식을 그대로 고수하는 것이 아니라, 현대 개발 환경에 맞게 진화하고 있다.

6. AI 코딩 시대 — Emacs는 어떻게 대응하나

6.1 Emacs의 AI 통합 생태계

AI 코딩 도구가 에디터 선택의 결정적 변수가 된 2026년, Emacs는 어떻게 대응하고 있나. 예상외로 견고하다.

  • gptel: Claude, GPT, Gemini, Ollama 등 다양한 LLM을 Emacs 임의 버퍼에서 대화 형식으로 사용. MCP(Model Context Protocol) 통합도 지원한다. Anthropic 백엔드는 버전 0.9부터 네이티브 지원된다.
  • copilot.el: GitHub Copilot 언어 서버에 직접 연결, 인라인 자동완성 제공. 2025년 초부터 공식 Node 패키지 기반으로 업그레이드됐다.
  • ellama: Ollama 등 로컬 LLM을 활용한 코드 요약·리팩토링·번역 등 특화 명령 제공.
  • aider.el: AI 페어 프로그래밍 도구 Aider를 Emacs 내에서 통합 사용.
  • Claude Code: 터미널에서 동작하므로 에디터 무관. Emacs 사용자는 터미널에서 Claude Code를 병행하고, 결과를 Emacs 버퍼에서 검토한다.

Emacs의 "무엇이든 확장 가능하다"는 특성은 AI 통합에서도 통한다. gptel을 org-babel과 결합해 AI 응답을 org 문서에 자동 기록하거나, AI가 생성한 코드를 버퍼에서 즉시 실행하는 워크플로는 VS Code에서 쉽지 않은 조합이다.

6.2 그러나 AI 네이티브에는 밀린다

솔직히 말하면, 인라인 AI 코딩 경험에서는 Cursor나 GitHub Copilot가 통합된 VS Code가 Emacs보다 매끄럽다. Cursor는 에디터 전체가 AI를 전제로 설계됐고, 멀티파일 컨텍스트 이해, 코드베이스 전체 질의, 즉각 적용이 단일 환경에서 완결된다. Emacs의 AI 통합은 강력하지만 직접 조립해야 하는 측면이 있다. "완성된 제품"이 아니라 "부품을 조합해 만드는 것"에 가깝다. 이것이 Emacs 철학의 장점이자, 처음 쓰는 사람에게 진입 장벽이 되는 이유다.

7. 2026년에 Emacs를 선택해야 하는 사람, 하지 말아야 하는 사람

7.1 Emacs가 맞는 경우

다음 조건이 겹치는 개발자에게 Emacs는 지금도 최선의 선택일 수 있다.

  • 개인 지식 관리 시스템을 코드처럼 다루고 싶다 → org-mode
  • 에디터를 완전히 자신에게 맞게 설계하고 싶다 → Emacs Lisp 확장성
  • 원격 서버, SSH, 낮은 리소스 환경에서 일한다 → 터미널 Emacs
  • 수십 년간 같은 도구를 유지하고 싶다 → Emacs의 역사적 안정성
  • 자유 소프트웨어 철학에 동의한다 → GNU GPL

7.2 Emacs가 맞지 않는 경우

반대로 이런 상황이라면 Emacs 투자를 권하지 않는다.

  • 팀 전체가 VS Code 생태계에 있고 협업 확장이 중요하다
  • AI 인라인 코딩을 가장 매끄럽게 쓰고 싶다 → Cursor가 적합
  • 지금 당장 생산적이어야 한다 → 학습 곡선 감당이 어렵다
  • 설정을 직접 관리하기 싫다 → VS Code의 GUI 설정이 맞다

7.3 이진 선택이 아닌 스펙트럼

에디터 전쟁은 이미 끝났다는 말이 있다. VS Code가 압도적 점유율을 가져간 결과다. 그러나 그것은 "Emacs가 틀렸다"는 뜻이 아니다. 같은 논리로 장인이 현대 공장 생산 도구 대신 손도구를 고집하는 것을 "비효율"로만 볼 수 없다. 특정 종류의 작업과 특정 종류의 장인에게는 그 선택이 최적이다.

Emacs는 그 사용자들에게 "에디터를 평생 배우는 과정"을 제공한다. 완성된 제품을 받는 것이 아니라, 자신이 원하는 도구를 직접 만들어 가는 과정이다. 이 과정 자체를 즐기는 사람에게 Emacs는 단순히 생산성 도구가 아닌, 프로그래밍의 연장이다.

8. 결론 — 50년 뒤에도 누군가는 Emacs를 쓸 것이다

GeekNews 토픽의 질문에 답하자면: 그렇다, 아직도 Emacs를 쓰는 사람이 있다. 그리고 앞으로도 있을 것이다. 이유는 인기가 아니다. Emacs가 채우는 특정 니즈가 사라지지 않기 때문이다 — org-mode로 지식을 코드처럼 관리하는 것, Emacs Lisp으로 에디터를 완전히 자기화하는 것, 어떤 환경에서도 같은 키보드 체계로 일하는 것.

AI 코딩 시대가 에디터 선택의 판을 바꾸고 있는 것은 사실이다. 그러나 그 흐름에서도 Emacs는 AI를 흡수하는 방향으로 진화하고 있다. 점유율로 보면 작은 틈새지만, 그 틈새 안에서 Emacs는 50년째 자기 역할을 하고 있다. 주류가 되지 못한 것이 실패가 아니듯, 소수가 계속 쓴다는 것이 잘못된 선택도 아니다.

2026년 6월 기준, GNU Emacs 30.2는 여전히 개발 중이고, 새로 입문하는 개발자가 있으며, AI 통합 패키지가 나오고 있다. 50년 된 에디터의 생명력은 인기가 아니라 교체 불가능한 기능과 완전한 커스터마이즈 가능성에서 온다. 그리고 그것만으로 충분히 살아남을 이유가 된다.
