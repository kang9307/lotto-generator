The Workarounds CSS Deleted - When the Browser Takes Over Work the Preprocessor and JavaScript Were Doing

Feature by feature: what disappeared, what is still here, and how to read a support table

Aug 16, 2026 Dev & Infra

Introduction: the lines that quietly left your stylesheet

Open a project that has been sitting for a few years and three things almost always turn up together. A preprocessor wired into the build pipeline. A handful of JavaScript lines that add and remove a class on a parent element. And media query breakpoints scattered across a dozen files. They look like three unrelated pieces of machinery, but they share a single origin story. All three exist to cover something CSS could not do.

A large share of those workarounds moved into the browser over the past few years. Nesting is parsed directly. There is a selector that picks a parent based on what it contains. You can ask about the width of a container instead of the width of the screen. And the fight over which rule wins now has an explicit, named mechanism. Which means the useful question today is not what got added to CSS, but what exactly did it remove. New syntax you can learn whenever you need it; code you were allowed to delete but never did will stay forever.

This piece walks through five features and the specific workaround each one retires, marks the places nothing has been retired, then covers how to read support status and how to decide what to adopt. Every statement about browser support here reflects what was checked on August 16, 2026. CSS support status changes faster than almost any other subject on this blog, so if you are reading this six months later, open the badge at the top of each MDN page again.

The twenty-year arc of frontend as a whole is covered in What Happened to Frontend - A 20-Year Journey From jQuery to AI Coding, and the argument for not reimplementing browser-native behavior lives in The Don't Roll Your Own Principle 2026. This article stays in the CSS layer only.

1. What the preprocessor was for - nesting and variables

Ask why a preprocessor is in the project and you generally get three answers: nesting, variables, mixins. Two of those three have been absorbed into the language.

1.1 Nesting - the parser reads it directly

The browser parses nesting itself, so nothing needs to be compiled ahead of time. The core of the syntax is a single character, &, standing for the parent.

/* Before: meaningless until the preprocessor compiled it */
.card { .title { font-weight: 700; } }

/* Now: the browser reads it as written */
.card {
  padding: 1rem;
  & .title { font-weight: 700; }
  &:hover { border-color: currentColor; }
}
  • Gone - the build step. Spinning up a watch process to change one declaration, gitignoring compiled output, and hunting for the original line number by hand when the source map drifts all disappear.
  • Still there - mixins and loops. Code that generates color ramps or spacing scales through iteration, compile-time color math, and import ordering across many files remain preprocessor work.
  • Careful - specificity still climbs. Nesting makes selectors longer in a way you cannot see. That trap did not disappear when the feature became standard. Two or three levels of depth is a safe ceiling.

1.2 Custom properties - not the same object as a preprocessor variable

Both get called variables, which is why they get treated as the same thing, and they are not. A $gap is gone once compilation finishes; only the computed value survives into the output. A --gap is alive at runtime. Everything else follows from that one difference.

:root { --gap: 1rem; --brand: #2c6fdb; }
@media (min-width: 48rem) { :root { --gap: 2rem; } }
.grid { gap: var(--gap); }
.btn  { background: var(--brand); }
/* the fallback value goes in the second argument */
.card { border-radius: var(--radius, 6px); }
  • It inherits, and it changes inside conditions. Change the value on a parent and everything below follows; swap a single value inside a media query or container query instead of duplicating the rule set for each condition.
  • Gone - the duplicated theme file. Building a second complete stylesheet for dark mode, or rewriting every rule under a .theme-dark ancestor, collapses into a few redeclared custom properties at the root.
  • Gone - injected inline styles. Instead of JavaScript writing style attributes onto individual elements, it hands down one value with element.style.setProperty('--x', v). The rules stay in the stylesheet where they belong.
  • The boundary. Declaring a type for a value so it can be animated belongs to @property, and this article did not check its support status.

2. :has() - the place you used to call JavaScript to pick a parent

The situation is always similar. If the card contains a thumbnail, switch to a two-column layout. If the input has a value, float the label upward. If the list is empty, show the empty state. Back when selectors only flowed downward there was exactly one answer: add a class to the parent at render time.

That one class costs more than it looks. Something has to update it whenever the content changes. The same decision logic has to exist in both the server render and the client render. Tests accumulate around that logic. And eventually it becomes a class nobody can delete, because nobody can trace what put it there.

/* float the label when the input has a value - no JS */
.field:has(input:not(:placeholder-shown)) label {
  transform: translateY(-1.2em);
  font-size: 0.8rem;
}

/* only cards with a thumbnail get two columns */
.card:has(> img) { grid-template-columns: 8rem 1fr; }

The verified support picture is unusually clear. MDN marks :has() as Baseline widely available and states it has been available across browsers since December 2023 (checked August 16, 2026). The documentation also lists several constraints, and one of them has a failure mode harsh enough that you should not use the selector without knowing it.

  • :has() cannot be nested inside another :has().
  • Pseudo-elements are not valid as arguments to :has(), and cannot serve as its anchor either.
  • In a browser without support, the entire rule block containing that selector is invalidated. Every other declaration you wrote alongside it dies too. Putting it inside a forgiving selector list such as :is() or :where() discards only that part and lets the rest survive.
  • Specificity follows the most specific selector among its arguments, the same rule as :is() and :not().
  • The performance guidance is in the docs as well: do not anchor to body, :root or the universal selector, and narrow the traversal with the child (>) and adjacent sibling (+) combinators.

3. Container queries - asking about the slot, not the viewport

The limitation of media queries was never syntax. It was the subject of the question. A media query only knows how wide the screen is. What you actually need to know is how wide the slot holding this card is, and when the same card component goes into a narrow sidebar and also into a three-column content grid, screen width tells you nothing.

So the component had to be told where it was. That knowledge usually arrived as a variant="compact" prop, or as a ResizeObserver measuring the width and toggling a class. Both approaches duplicate layout knowledge outside the component.

.sidebar, .main-grid > * { container-type: inline-size; }

@container (width > 30rem) {
  .card { display: grid; grid-template-columns: 8rem 1fr; }
}

MDN marks @container as Baseline widely available and dates it to February 2023. But there is an asterisk attached, meaning some parts of this feature may have varying levels of support. That is because the same document covers style queries, scroll-state queries and anchor-related queries alongside size queries, and you should not collapse all four into one sentence about container query support.

  • A container has to be declared explicitly. An element without a container-type is not queryable. The values are inline-size (inline axis only), size (both axes) and normal (the default, not a size query container).
  • Most real work uses inline-size. With size, containment applies on both axes so content cannot generate height, and the element collapses unless you set a height yourself.
  • An element cannot query itself. Queries only resolve against an ancestor container, which is why an extra wrapper outside the card is such a common shape.
  • Gone. The ResizeObserver and its class toggling, the props that carry layout information into components, and the breakpoint constants duplicated across CSS and JavaScript waiting to drift apart.

4. @layer - turning a specificity fight into a rule

You want to tweak a design system button on one page and it will not take. You lengthen the selector. Still nothing. You add !important. Six months later somebody arrives to fix that page and repeats the same sequence. This staircase comes out of specificity being an implicit competition.

@layer replaces that competition with an explicit rule: declaration order. MDN marks it as Baseline widely available since March 2022.

/* declare the order once, at the top */
@layer reset, vendor, base, components, utilities;

@layer vendor { /* third-party CSS goes here */ }
@layer components { .btn { padding: .5rem 1rem; } }
@layer utilities { .mt-0 { margin-top: 0; } }

Three rules are worth memorizing, and the second one decides your architecture.

  • Layers declared first are weaker; layers declared later are stronger. Order wins, not specificity.
  • Styles that are not in any layer beat styles in every layer. Confine third-party CSS to a low layer and your own styles win simply by staying outside any layer at all.
  • !important inverts the order. Among important declarations, the layer declared first becomes the strongest. Put !important in your reset layer and it flattens everything above it.
  • Gone. The !important staircase, specificity inflation such as .app .page .card .btn.btn-primary, and editing bundler configuration to protect load order.
  • Careful - it fails silently. Miss a layer declaration or misspell a name and the rule lands in an anonymous layer or outside layers entirely, flipping precedence with no error at all. Keep a list of screens to eyeball right after adoption.

5.1 Where JavaScript still lives

The boundary fits in one sentence. CSS applies styles; it does not return values. Split any candidate feature along that axis and you will usually predict correctly whether it can remove JavaScript.

  • Reading measurements. Any logic that needs to know as a number how many pixels wide an element is, or how many lines the text wrapped to, is still JavaScript. A container query restyles at that width; it does not tell you the width. Comparing A and B to decide C belongs here too.
  • Conditions that live outside the DOM. In a rule like turn red when stock drops below three, the condition sits in a server response and CSS has no way to see it. But the moment you hand that value down as a data- attribute or a custom property, it becomes CSS work. The boundary is who computes the value, not who applies the style.
  • Updating accessibility state. Changing an attribute like aria-expanded is JavaScript. CSS can read that attribute to style against it, but cannot change it. Focus trapping and keyboard order management are the same.
  • Time-bound logic and list manipulation. Code that runs after an animation finishes, lazy loading when an element enters the viewport, and sorting, filtering or virtual scrolling. :has() can show an empty state when there are no children, but it cannot reorder items.
  • The content and timing of form validation. Which message appears when is the constraint validation API. What CSS took over is only the display of valid and invalid states.

To put it plainly, the segment CSS took over is condition to style. Data to condition and style to value are exactly where they were. How frameworks handle that same boundary is covered separately in Foldkit - A New Frontend Framework Built for Correctness.

6. The layers of supported - how to read browser support

Is that feature supported sounds like one question but contains at least four. If you do not separate the layers you either ship fallbacks you never needed, or skip one where it mattered, and then maintain the mistake indefinitely.

LayerMeaningPractical callExamples verified here (2026-08-16)
Widely availableWell established across many devices and browser versions. MDN states since whenSafe to use with no fallback:has() since December 2023 / @container since February 2023 (asterisked) / @layer since March 2022
Recent versions onlyPresent in current major engines but absent from older versionsProgressive enhancement only. Fallback required for locked corporate browsers or older mobileNo example verified in this article
Some engines onlyAvailability splits by engineKeep it off the critical layout pathAnchor positioning - no Baseline badge shown on the MDN overview page
Flagged or experimentalThe user has to enable a settingNot for production. Demos and learningNo example verified in this article
  • Read since when, not supported. The older the date, the higher the odds your users devices have already moved past that version. The date is where the actual information lives.
  • Do not skip the asterisk. When a page like @container carries a note that some parts may have varying levels of support, that is a signal to check each sub-feature grouped under that name individually.
  • Separate module names from property names. One specification module holds many properties and each landed at a different time. The unit you verify is the property and value you will actually write, not the module.
  • Compare against your own version distribution. Present in current browsers and present in your visitors browsers are different facts. If your service runs behind a corporate network with pinned versions, or gets heavy traffic from messenger in-app browsers, global averages are weak evidence and your analytics browser version report is the only measurement you have.
  • Write the check date down. Without a line in the team wiki saying checked 2026-08-16, you will research the same set of features from scratch six months from now.

6.1 @supports - designing the fallback

@supports asks, from inside CSS, whether the browser understands a given declaration or selector. The syntax comes in three shapes.

/* baseline outside, enhancement inside */
.card { display: block; }

@supports (container-type: inline-size) {
  .card-wrap { container-type: inline-size; }
  @container (width > 30rem) { .card { display: grid; } }
}

@supports selector(:has(*)) { /* selector support */ }
@supports not (anchor-name: --a) { /* negated condition */ }
  • It asks about parsing, not behavior. @supports only confirms the browser understands the declaration. It cannot filter out partial implementations, so a passing test is not a reason to skip looking at the screen.
  • Keep the direction right. A very old browser that does not know @supports itself ignores the whole block. So baseline styles go outside the block and enhancements go inside. Wrapping your fallback in not means some browsers lose the fallback entirely.
  • Wrap :has(). Because an unsupporting browser throws away the whole rule block, writing :where(.card:has(img)) lets the surrounding declarations survive. The tradeoff is that :where() zeroes out specificity, so the rule loses to others more easily.
  • Pick one of three fallback strategies and give it an expiry. First, progressive enhancement, when the default state is already usable and you are only layering on top. Second, equivalent substitution, approximating with media queries and refining with container queries. Third, wait, because when the feature carries core layout the cost of maintaining two versions usually exceeds the benefit. Whichever you choose, if you do not leave a comment saying under what condition this gets deleted, that code outlives the condition by years.

7. Reading survey numbers - respondents are not the average developer

The annual CSS surveys are good material for seeing what is being discussed. But when you copy a number out of one, you have to copy the character of the sample with it. State of CSS 2026 is a public web survey with 4,902 respondents, fielded May 15 to June 29, 2026. Strip that line away and what remains is not evidence but atmosphere.

  • Responses are self-selected. This is not a random sample; it is whoever heard about the survey and felt like answering. Someone who spends time on a CSS survey is by definition on the more CSS-invested end of the distribution.
  • The recruitment channel shapes the result. Which communities it spread through changes the composition of respondents entirely. This article could not confirm the recruitment channel from the public pages, and in that case the fact that the field is blank belongs in the citation.
  • Overall N and per-question N are different. 4,902 is the total respondent count, and not every question carries that denominator. Free-text questions carry far less. The top entries for the favorite new feature question were anchor positioning at 168, :has() at 158, size container queries at 126 and CSS nesting at 116, which are mention counts, not percentages, against a denominator that is not 4,902.
  • Check what usage counted, and subtract sample drift from year-over-year changes. Have tried it, am running it in production, and have heard of it are three different questions, and that distinction vanishes if you copy from a summary. A statement that adoption rose also blends real diffusion with a change in who answered.

Read with those caveats attached, the trends worth taking from the 2026 edition look like this. Browser compatibility was named the biggest barrier to adoption, and anchor positioning came up as the flagship example of something people want but cannot ship. In the framework question Tailwind held first place, and no framework moved past Bootstrap into second. The share of CSS written with AI assistance averaged around 28%, notably lower than other areas of development, and the most frequently raised concern was cognitive overload.

And there is a sentence these numbers do not support. Everyone uses :has() now does not follow from this data. What follows goes exactly this far: within this sample, :has() was among the new features most often reported as used. If the difference sounds trivial, consider what breaks when you delete a fallback on the strength of the first sentence.

8. What to adopt now and what to defer

Four axes are enough. What breaks and how badly when support is missing, the cost of maintaining two versions, the distance between the verified support date and your own user distribution, and the cost of reversing later. The first carries the most weight. A failure that looks slightly worse and a failure that collapses the layout do not belong on the same scale.

FeatureSymptom without supportFallback difficultyCall
NestingRule ignored, so no styling at allLow - zero if you keep compilingAdopt after verifying. If you have not confirmed the date, keeping compilation is the safer position

:has()Whole rule block invalidated - neighboring declarations die with itMedium - wrap in :where() plus a fallback ruleUse it now, and make wrapping a habit because the failure is harsh
Container queries (size)Rules inside the container never apply, default layout remainsMedium - approximate with media queriesUse it now. Verify style and scroll-state queries separately
@layerTreated as unlayered, so precedence invertsMedium - adjust load orderUse it now, but the failure is quiet, so keep a check list right after adoption
Anchor positioningPosition never resolves, so tooltips and popovers land in the wrong placeHigh - you keep the JS positioning libraryDefer. No Baseline badge on MDN, and the survey named support gaps as an adoption barrier

It is worth naming the cost on the deferring side too. A team maintaining two versions eventually only ever looks at the fallback path. Without a procedure that confirms the enhanced path actually renders somewhere, that code is dead code, and it sits on the maintenance list without anyone knowing it died. When you add a new feature, decide at the same time which browser you will verify the enhanced path in.

Frequently asked questions

Can I drop my preprocessor now?

If nesting and variables were all you used, you have a real case. Mixins, loops that generate utilities, compile-time color math, and file splitting with import ordering are still preprocessor work. Make the call from a list rather than a preference — grep your preprocessor files for the syntax actually in use, sort each item into replaceable or not, and the answer falls out immediately.

Does :has() hurt performance?

The selector is not slow; the scope you make it traverse is what costs. MDN's guidance is explicit — do not anchor to body, :root or the universal selector, and constrain traversal with the child and adjacent sibling combinators. Asking whether one card contains an image is fine. If you are unsure, measuring style recalculation on a real page beats guessing.

Do container queries replace media queries?

They divide the work. Page-level decisions — column count, whether the sidebar collapses — stay with media queries. Container queries handle the parts inside that shell responding to the width of the slot they landed in. You end up using both, which makes keeping breakpoint values in one place more important, not less.

Will adopting @layer break my existing CSS?

It can, and it breaks quietly. One rule predicts most of it — styles outside any layer beat styles inside every layer. Sweep your whole stylesheet into a layer and rules that used to win start losing. The safe order is the reverse: put resets and third-party CSS into low layers first, leave your own styles unlayered, and watch.

Should survey numbers drive technical decisions?

A survey tells you where attention is going, not what adoption looks like. Public web surveys are self-selected, so respondents skew toward people invested in the topic. A high usage figure is therefore not evidence that your users browsers support the feature. Use it to build an evaluation shortlist; make the call from compatibility documentation and your own version distribution.

Conclusion: three calls to make today

Compress the last few years of CSS into one sentence and you get deciding conditions moved out of scripts and into stylesheets. The state of a parent, the width of the slot, the ranking between rules — all three used to be computed outside CSS and injected as class names. Now that computation happens inside the selector. Which means the payoff is not in the new syntax; it is in the code you are allowed to delete.

  • Start by counting the class toggles you have. Code that adds and removes classes on parents, ResizeObservers measuring width, theme class sets. That list is the list of recoverable code.
  • Judge by failure mode, not by feature. A feature that degrades gracefully and one that kills an entire rule block deserve different adoption bars. The habit of wrapping :has() in a forgiving list comes straight out of that distinction.
  • Leave the check date. Support status shifts within six months. Without per-feature check dates in the team documentation you either repeat the research or keep running on a stale decision.

One last line about surveys. Material like this is useful for deciding what goes on the shortlist, and that is where its usefulness ends. Adoption gets decided by compatibility documentation and by the version distribution of your own traffic. A figure quoted without its respondent count and survey window is not evidence, whatever the figure says.
