1. Context and Design Purpose of a Foundation Model Built for Tiny Devices

Generally, deploying language models directly onto embedded microcontrollers and tiny hardware appliances encounters severe physical limitations in available memory and computational throughput.

Addressing this operational environment, Cactus Compute introduced Needle 3. According to the description on its official GitHub repository (https://github.com/cactus-compute/needle), Needle 3 is an: 「Automation foundation model for tiny devices: 2-bit, 8-29 MB, tool calls, structured extraction and embeddings on phones, wearables, smart homes, robots, cars and microcontrollers.」 It is distributed under the Apache-2.0 open-source license. On the product page (https://cactuscompute.com/needle), Cactus writes: 「The whole model is a single 8-29 MB binary built on our Simple Attention Network, and we trade general chat capacity to beat models 10x its size on mobile tool calls and match 2-3x bigger models on extraction.」

In this article's interpretation, the original documentation indicates that the model narrows its scope from general conversational writing to device tool selection and argument filling to maintain a compact binary. On the product page (https://cactuscompute.com/needle), Cactus lists target environments and specific phrasing as follows:

  • Smart home: 「"Dim the bedroom and lock up" becomes two calls, executed offline, with no hub round trip.」
  • Robots: 「"clean the kitchen but leave the bedroom", "go back to the dock when you are done". Each becomes a sequence of moves it can execute.」
  • Phones: 「make an album from last weekend's photos, open a site, dim the screen, find the lease in your files.」
  • Wearables: 「a card charge into merchant, amount and date; a message into a reply; a complaint into a sentiment flag.」
  • Automotive: 「Climate, media, navigation and calls from requests in the cabin, with the tool set pinned so it survives a long drive's worth of conversation.」
  • Search and matching: 「semantic search over notes, messages and documents; a query matched to the closest of hundreds of tools; near-duplicate alerts merged on a watch.」

2. Core Capabilities and I/O Specifications — Tool Calling, Extraction, and Embeddings

The operational capabilities of Needle 3 are explicitly defined in the README (https://github.com/cactus-compute/needle) across three categories: tool calls, structured extraction, and text embedding.

Tool Calling and Grammar-Constrained Extraction

Regarding tool calls, the README states: 「given the functions your app exposes, Needle picks the right ones and fills every argument from what the user said. Ask for two things and you get two calls in order; ask for something no tool covers and you get an empty list, not a guess.」 It explicitly notes that unsupported requests return an empty list rather than an ungrounded guess.

Regarding structured extraction, the text documents: 「declare a shape, hand over messy text, get typed fields back: an invoice, a booking, a notification, a form. The decode grammar guarantees the output parses, and extraction generalises to classification.」 The documentation states that the decode grammar guarantees that output parses successfully.

On-Device Vector Embeddings via a Single Model

Regarding text embedding, the documentation states: 「the same model returns a vector for a sentence, so an app can search, match and route locally: find the note you mean, pick the tool closest to a request, collapse duplicate alerts.」 The exact same binary yields sentence vector embeddings utilized for local search, tool matching, and routing.

In this article's interpretation, the three features described in the documentation bundle device control, data parsing, and local semantic routing into a single on-device binary package.

In the Writing tools section on the product page (https://cactuscompute.com/needle), Cactus outlines guidelines as follows:

  • Tool scoping: 「a narrow tool with a plain description beats a broad one. One tool per action, described by the actions it covers ("Turn a room's lights on or off") rather than a category.」
  • Enum definitions: 「Name enum options after what a user says (action: ["increase", "decrease"]) and keep synonyms in the description.」
  • Argument handling: 「Give a required argument a default when a request may leave it out; a required argument with no default and no evidence in the request is withheld rather than guessed.」
  • Value formats: 「Put value formats in descriptions ("City, ST", "e.g. T-1042"). Add triggers to intents that must always reach a tool, and keep the toolset per turn small.」

3. Architecture Analysis of the Laddered Simple Attention Network

Regarding architecture, the README (https://github.com/cactus-compute/needle) writes: 「Needle 3 is a Laddered Simple Attention Network: a Monarch Hadamard MLP in place of the FFN, GQA attention with causal conv taps, engram n-gram memory read by gather, and multi-lane hyper-connections, trained so that every depth from 2 to 20 layers is a deployable model.」

Monarch Hadamard MLP and Multi-Lane Hyper-Connections

According to the architecture schematic (Figure 1) on the product page (https://cactuscompute.com/needle), the model features 20 layers, a 768 hidden dimension, and 121M total parameters. Tokenization uses a SentencePiece BPE vocabulary of 8,192 tokens with tied unembedding weights (8,192 × 768). Residual propagation employs a 4-lane mHC structure with sandwich ZCRMSNorm. Attention projections use a 12q : 2kv ratio with per-channel 3-tap causal convolutions, a 1,024-token window GQA attention, RoPE, QK-norm, and global attention positioned at layers 4, 9, 14, and 19.

The Monarch Hadamard block replacing the FFN utilizes 32 × 32 matrix operations. In the Figure 1 caption, Cactus writes: 「The architecture spends over 2x fewer MFLOPs per token than a transformer of the same configuration.」

Engram n-Gram Memory and Parameter Structure

Figure 1 indicates that 70.8M of the 121M parameters reside in engram tables (sites 3, 7, 11, 15, 19 with 18,432 slots, hashed 2- and 3-gram memory read by gather). The README explains: 「Most of its parameters sit in the engram, so the 121M model does the arithmetic of a 50M one.」

Regarding training, the product page states that 「360B tokens of proprietary structured dataset」 was utilized, with an mtp t+2 aux head active during training only. The deployment binary is formatted as a CQ2 2-bit quantization artifact scaling from 8 MB to 29 MB (noted as 9 to 29 MB in page body text). Key summary points include:

  • Ladder subnetworks: Trained such that every depth from 2 to 20 layers functions as an independently deployable model
  • Binary footprint: Formatted as a single CQ2 2-bit binary scaling between 8 MB and 29 MB depending on layer depth
  • Grammar enforcement: A byte-level grammar compiled from target schemas constrains generation choices at every token step
  • Calibrated scoring: Outputs a calibrated confidence score computed by a dedicated learned head on every turn

4. Installation and Python-Based Tool Definition Implementation

The installation procedure documented in the README (https://github.com/cactus-compute/needle) requires running the package manager command below. The inference engine is downloaded once from Hugging Face (https://huggingface.co/Cactus-Compute/needle3) and cached locally.

pip install cactus-needle

Regarding tool declaration and invocation, the README explains that the function signature gives argument types, the docstring provides the tool description, and run() completes execution and returns results. The official weather lookup example is:

import needle

@needle.tool
def get_weather(city: str):
    "Get the current weather for a city."
    return {"city": city, "temp_c": 27, "sky": "clear"}

agent = needle.Needle(tools=[get_weather])
print(agent.run("what's it like in Lagos right now?")["results"])
# [{'city': 'Lagos', 'temp_c': 27, 'sky': 'clear'}]

The documentation states that every turn returns one JSON object containing function_calls, reasoning, and calibrated confidence, returning an empty list for off-topic queries. Existing deployments can continue running Needle 2 via the needle.Needle(tools=[...], generation=2) configuration option.

5. Vendor-Reported Benchmark Metrics and Measurement Conditions

Performance metrics for Needle 3 represent internal measurements published by Cactus Compute on its product overview (https://cactuscompute.com/needle) and evaluation plots.

Raspberry Pi 5 Token Speeds Reported by the Vendor

Cactus reports decoding throughput of 400 to 4,000 tokens per second (400-4k tokens/s decode) and prefill throughput of 1,000 to 10,000 tokens per second (1-10k tokens/s prefill) on a Raspberry Pi 5. The sample JSON response on the product page records a peak_ram_mb measurement of 28.5.

Subnetwork Scaling and Downstream Task Fine-Tuning

Regarding evaluation methodology, the README states: 「Tool calling is exact-match accuracy on the full test splits, extraction is field micro-F1 on the full test splits.」 The Figure 2 caption notes that Needle 3 subnetworks (20, 16, 8, 4 layers) were evaluated using the shipped CQ2 2-bit binary, baselines at f16 under vLLM, and DeepSeek V4 Flash through its cloud API.

Cactus asserted that fine-tuning on DroidCall raises subnetwork scores by 18 to 36 points, with subnetworks from 4 layers (29M parameters) onward exceeding DeepSeek V4 Flash (「fine-tuning on DroidCall lifts every subnetwork by 18 to 36 points, and from 4 layers up the tuned subnetwork passes DeepSeek V4 Flash, starting at 29M parameters (Figure 3)」). Row counts and evaluation criteria across the six benchmark suites listed on the product page are:

  • Mobile Actions: 961 rows, converting phone commands to Android intents, evaluated via exact call match
  • DroidCall: 200 rows, containing multi-call instructions, evaluated via exact calls in order
  • BFCL v4: 3,641 rows, Berkeley single-turn function calling, evaluated via AST match and irrelevant query non-call
  • DSTC8: 1,813 turns, dialogue slot filling into schemas, evaluated via field F1
  • SNIPS gold: 700 rows, slot filling against a provided schema, evaluated via field F1
  • SNIPS 7-way: 700 rows, schema selection among seven options followed by slot filling, evaluated via field F1

6. Execution Control via Confidence Gating and Regex Triggers

To control execution accuracy, Needle 3 provides calibrated confidence scores alongside regular expression trigger configurations.

The 0.1 Confidence Floor and Refusal Logic

According to the documentation, each response JSON includes a confidence score from a calibrated head. The engine applies an internal floor of 0.1, below which calls are withheld into suppressed_calls and function_calls is returned empty.

Cactus describes a control pattern where applications execute calls when confidence reaches or exceeds 0.7, confirm with the user when calls or suppressed_calls exist within the 0.1 to 0.7 band, and issue a refusal when no call is generated. Additionally, assigning triggers regex patterns ensures that matching inputs strictly constrain decoding to the matching tool, forcing invocation even below the 0.1 confidence floor.

Community Testing Observations and Practical Limitations

Developer reports from technical discussions including GeekNews (https://news.hada.io/topic?id=33923) highlight practical observations that contrast with vendor claims:

  • Vulnerability to ambiguous phrasing: Slang or shortened expressions causing misrouting (such as the term 「wee」 intended for bathroom lights being interpreted as a music genre search tool)
  • Perception of marketing overstatement: User friction when applying broad conversational expectations to a specialized tool router
  • Dependency on schema quality: System accuracy remains heavily reliant on developer-written docstrings, parameter names, and schema precision
  • Subnetwork capacity trade-offs: Compressing models to 2 or 4 layers without downstream fine-tuning risking drops in zero-shot routing accuracy
  • Tool set size constraints: Increasing the number of active tools exposed per turn increases misrouting likelihood, requiring small toolsets

7. Unverified Items

Technical points that could not be independently verified from public documentation and repositories include:

  • Exact official release date: The README and product page state 「Today we release Needle 3」 without timestamp metadata, preventing date verification from the source
  • Independent benchmark replication: Performance figures on Raspberry Pi 5 and benchmark comparisons against DeepSeek V4 Flash are vendor-reported without third-party replication
  • Pretraining dataset composition: Domain distributions and licensing terms for the 360B tokens of proprietary structured data remain unreleased
  • Proprietary .cact quantization specification: Mathematical formalisms and error profiles for the CQ2 2-bit quantization format are not detailed in public documentation
