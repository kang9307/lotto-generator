韩文被拆成字母的瞬间 - NFC 与 NFD，在边界上崩掉的东西

文件名、grep、排序、长度校验、压缩各自在哪里崩掉，全部用实跑的输出说明

2026-07-30 IT/技术

引言: 同名的两个文件出现在同一个目录里

我打印目录列表，同一个名字出现了两次。사진.png 和 사진.png。一个字都不差，没有多余空格，扩展名也一样。放大屏幕也分辨不出来。可是操作系统把它们当作两个不同的文件，而且内容确实不同。

把文件名按字节打印出来就有了答案。一个是 19 字节，另一个是 10 字节。同样三个字的名字，存储的字节数却差了近一倍。一个把韩文音节存成预先合成的一个字，另一个把初声、中声、终声分开存储。Unicode 允许两种做法。它们只有在屏幕上被绘制出来时才变成同一个形状。

这就是 Unicode 规范化问题。而这个问题的实质并不是「没有做规范化」，而是没有人规定在哪里、由谁来做规范化。网页表单到服务器，服务器到数据库，数据库到文件系统，文件系统到压缩包，压缩包到另一个操作系统。字符串要多次跨越这些边界。如果没有定好每次跨越时形式是被保留还是被改变、由谁来统一，那么总会在某处崩掉。

这篇文章逐个跨越那些边界，用我实际执行并观察到的输出指出什么会崩掉。先说结论：存储大体是安全的，危险的是边界。而韩语服务里最频繁发生的事故并不是文件名，而是 [가-힣] 正则。

执行环境。下面所有输出都是在 Windows 10 Pro (10.0.19045) / NTFS 上实际执行的结果。工具为 Node.js v22.16.0 (win32)、Python 3.13.3、GNU bash 5.2.37 (MSYS2/MinGW64)、GNU tar 1.35 与 Windows PowerShell 5.1。示例路径已改写为 /tmp/demo 这样的占位符。

所有脚本都保存成文件再执行。把混有韩文和反斜杠的代码作为 shell 参数传递会被静静改变。那个陷阱在韩文正则的陷阱里讲过。

本文不涉及的内容。词尾一加上前一个字就变掉背后的音节合成算术与按词尾的安全模式在上面那篇里讲过。文件名里混入空格与换行导致管道崩掉的问题在find 与 xargs 的空白陷阱里讲过。本文只深挖同一个名字变成两串不同字节这一个问题。正则的方言与可移植性在到处都能跑的正则表达式里。

1. 看起来一样的两个字符串并不一样 - 「字符数」有三个答案

先做事实核对。我把 한 造成预合成形与分解形，并排量了三种长度。

node v22.16.0 / win32
대상            .length  [...s].length  utf8 byte
-------------------------------------------------
NFC 한                1              1          3
NFD 한                3              3          9
NFC 한글              2              2          6
NFD 한글              6              6         18
NFC 대한민국          4              4         12
NFD 대한민국         11             11         33
NFC 가                1              1          3
NFD 가                2              2          6
-------------------------------------------------
NFC 한 : U+D55C
NFD 한 : U+1112 U+1161 U+11AB
NFC 가 : U+AC00   (종성 없음)
NFD 가 : U+1100 U+1161   (2 코드포인트)

读法是这样的。预合成的 한 是单一的 U+D55C。分解形的 한 是三个：初声 hieuh（U+1112）、中声 a（U+1161）、终声 nieun（U+11AB）。所以字节长度分成 3 和 9。

  • 没有终声的 가 分解后只有两个码点。也就是说膨胀比例每个字都不同，有时两倍，有时三倍
  • 대한민국 从 4 变成 11。四个音节里有三个带终声，所以不是四乘三
  • 因此「字符数乘三」这种估算是行不通的。必须实际去量
  • 在 UTF-8 里预合成音节和分解形字母都是每个三字节。膨胀来自码点的个数

1.1 所有比较运算符都说它们不同

--- 1-4. 비교 ---
nfc === nfd                : false
nfc == nfd                 : false
Object.is(nfc, nfd)        : false
nfc.localeCompare(nfd)     : 0
JSON.stringify 동일        : false
Set([nfc,nfd]).size        : 2
Map 키 충돌하는가          : false

要盯住的是第四行。=== 给出 false，而 localeCompare 返回 0，也就是「相等」。两个函数给出了互相矛盾的答案。

关键在于这种不一致在实务中如何发作。排序看起来正常，去重却失败。用 localeCompare 排序，两个 한 会挨在一起。人一看就发现重复了。可是 Set 和数据库唯一索引看的是字节，所以把两者当作不同项放过去。「排序时明明挨在一起，去重却去不掉」这种现象就是这么来的。

1.2 Unicode 标准如何定义这件事

Unicode 标准附件 15 定义了四种规范化形式。照原样抄下来是这样。

形式标准定义在韩文里的结果主要用处
NFC正规分解后再正规组合每音节一个码点存储、比较、传输的默认值
NFD正规分解拆成字母初声检索等字母级处理
NFKC兼容分解后再正规组合兼容字母变组合用字母，全角变半角检索索引的规范化
NFKD兼容分解同上但保持分解状态少见，特殊索引

标准里有一句话直接关系到韩文。韩文音节的分解与组合是算术算法，不是查表。这个设计让实现可以在代码里计算而不必存查找表。实务含义很直白：没有例外。不是某些字才受影响，而是每一个韩文音节都可以被分解。这和英语世界里规范化只是几个带重音字母的问题在性质上不同。韩语是整篇文本都在范围内。

2. 规范化能解决 - 但「在哪里」的问题还在

处方很短：让两边处于同一种形式。我在 JavaScript 和 Python 两边都做了确认。

码点名称把结构完全摊开了。一个 HANGUL SYLLABLE HAN 分成 CHOSEONG HIEUH 加 JUNGSEONG A 加 JONGSEONG NIEUN 三个。Python 的 unicodedata.is_normalized 只判定形式而不做规范化，所以在记录传入字符串的状态时很有用。

到这里都不难。难的是把 normalize 写在哪一行。这才是本文的正题。常见的失败呈现两个方向。

  • 哪里都不做 - 最常见。开发环境里一次都不会有分解形传进来，所以问题浮不上来。只在特定用户、特定设备、特定上传路径上复现
  • 到处都做 - 出事之后匆忙应对就会变成这样：在每次比较之前都挂一个 normalize。能跑，但总会漏掉一处，而找到那一处要花上好几周
  • 各层对是否规范化的认知不一致 - 更糟。存储是预合成，缓存键是原始值，检索索引又是第三种形式。三处互相对不上
  • 以为做了其实没做 - normalize() 返回的是新字符串。只调用而不使用返回值，什么都不会发生。这个错误在代码评审里很难看出来

标准附件 15 提出的策略也指向同一个方向：让各组件在系统边界保证规范化的输入与输出，从而保持某种形式。换句话说规范化应该是边界契约，而不是零散的防御。下面几节是逐个真正跨越那些边界的记录。

3.1 shell 字面量无法表达分解形的名字

在只有那个分解形文件的目录里，我直接把名字敲进 shell 去访问。

--- 3-11. 이 디렉터리에는 NFD 이름 파일 하나만 있다 ---
보고서.txt
--- 3-12. 셸 리터럴(NFC)로 접근 시도 ---
[ -e "보고서.txt" ]  : 없음 (NFC 리터럴로는 못 찾음)
cat "보고서.txt" : cat: '보고�'$'\204\234''.txt': No such file or directory
--- 3-13. 글로브로는 잡힌다 ---
cat *.txt : NFD 이름으로 쓴 파일

三行各说了一件不同的事。

  1. 敲出来的名字是预合成形。因为输入法和编辑器产出的是预合成文本。于是它变成了和实际文件不同的字符串
  2. 错误信息把名字显示成读不出来的样子。shell 会把匹配失败的字节转义打印，所以人很难猜到原因。你会以为是自己打错了，反复重敲好几次
  3. 通配符却成功了。因为通配符用的是文件系统交出来的名字，而不是人造的字符串。如果通配符能用而显式指定不行，这就是怀疑此问题的依据

还有一种只发生在内存里的半失败。我对混有两种形式的列表做了前缀过滤。

--- 3-5. 목록 필터가 절반만 걸리는 경우 ---
목록 길이                             : 3
filter(startsWith('보고서')) 결과      : 1 ← 2여야 하는데
정규화 후 filter 결과                 : 2
정규화 전 Set.size                    : 3
정규화 후 Set.size                    : 2

列表里有两项以 보고서 开头，却只匹配到一项。如果有个批处理靠这个过滤器挑选要移动或删除的目标，那么一半会被静静漏掉。没有异常，没有错误日志。除非去数处理条数，过好几天都不会发现。

3.2 那么 macOS 呢

这里有一个流传的说法：macOS 的文件系统以分解形一类的方式存储名字，因此在 macOS 上做的压缩包在别的操作系统上解开会出现坏掉的名字。

本文无法验证这一点。测试环境只有 Windows 与 NTFS，没有办法用执行去验证 macOS 的行为。所以我不下断言。文件系统类型与操作系统版本都可能带来不同行为，必须在你自己使用的环境里直接确认。方法就是上面那套：用分解形的名字创建文件，读取列表，把返回名字的码点打印出来。三行就够了。

把没有验证的事写下来，就成了下一个人的判断依据。这个问题里真正有风险的不是「哪个系统怎么做」这种知识，而是自己的代码能否两种情况都撑住。让它撑住只有一个办法：在读取列表的那一行做规范化。

// 파일 목록을 읽는 경계에서 한 번
const names = fs.readdirSync(dir).map(n => n.normalize('NFC'));
// 이 아래로는 전부 NFC라고 가정하고 쓴다

4. 检索边界 - [가-힣] 一个分解形韩文都抓不到

这是本文最实用的部分。文件名问题碰上的人是有限的，而这个问题几乎存在于所有处理韩语的代码里。

node v22.16.0 / win32
--- 5-1. [가-힣]가 NFD를 못 잡는다 ---
대상            [가-힣] test    개수   Script=Hangul
----------------------------------------------------
NFC 한글              O 잡힘       2               2
NFD 한글              X 놓침       0               6
NFC 서울시            O 잡힘       3               3
NFD 서울시            X 놓침       0               7
--- 5-5. 정규식 문자 클래스 전수 비교 ---
패턴                       NFC 개수   NFD 개수
----------------------------------------------
[가-힣]                           3          0
[ㄱ-ㅎㅏ-ㅣ가-힣]                 3          0
\p{Script=Hangul}/u               3          9
[ᄀ-ᇿ]                   0          9

[가-힣] 的匹配数从 2 变成 0，从 3 变成 0。不是少匹配一些，而是整整为零。原因就是范围本身。[가-힣] 只覆盖预合成音节区 U+AC00 到 U+D7A3，而分解形字母位于 U+1100 一带，在范围之外。

第三行还展示了一个陷阱。把字母加进去扩宽范围的 [ㄱ-ㅎㅏ-ㅣ가-힣] 同样是 0。「既然把字母也打开了，分解形应该能抓到」这个期待是错的。为什么错留到第 9 节讲。现在需要的结论只有一句：加字母解决不了。

4.1 校验器在两个方向上都静静地出错

--- 5-2. 검증기가 조용히 통과한다 ---
NFC 사용자이름  ^[가-힣]+$ 통과 : true    | 한글 섞임 탐지 : true
NFD 사용자이름  ^[가-힣]+$ 통과 : false   | 한글 섞임 탐지 : false

两行是方向相反的两种事故。同一个名字，只有形式不同。

  • 「只允许韩文」的校验器 - 拒绝分解形的名字。用户输入的是完全正常的韩文名字，却收到「请只输入韩文」的错误。屏幕上明明就是韩文，用户根本不知道哪里有问题。就算来反馈也无法复现
  • 「检测韩文混入」的过滤器 - 抓不到分解形韩文。检查多语言页面是否混入韩语的工具、违禁词过滤器、语言判别器都栽在这里。检查器返回「无异常」，没人怀疑
  • 后者危险得多。前者用户会抗议，总有一天会被发现，而后者没有人会抗议。结果穿着成功的外衣，而不是失败的样子
  • 同一个根源还长出违禁词过滤绕过。把要拦的词用分解形输入，就能原样通过基于预合成形的过滤器。屏幕上那个词照样清清楚楚

4.2 查询词与正文形式不一致时

--- 5-3. NFD 텍스트에서 NFC 패턴으로 검색 ---
본문 형식        : NFD (코드포인트 26개)
검색어 형식      : NFC (코드포인트 3개)

양쪽 NFD 정규화 후 includes              : true

要注意最后两行。把两边都对齐到预合成形或都对齐到分解形，检索都会成功。也就是说选哪种形式并不是这个问题的本质，两边是否处于同一形式才是全部。所以与其把「NFC 是正确答案」背下来，不如养成追问「要比较的两个值是否走过同一个边界」的习惯，那在实质上更有力。

4.3 grep 的字符类还有一个陷阱

LC_ALL=C  nfc.txt : 30
LC_ALL=C  nfd.txt : 72

正文里的韩文是 10 个字，而 grep -o "[가-힣]" 数出了 30。30 正是那十个字的 UTF-8 字节数。也就是说这个 grep 把方括号范围当成字节范围而不是字符范围在解释。72 也是同样方式得出的分解形那边的字节数。

  • 因此这些数字不能当作韩文字符数来读。依 locale 设置，工具可能把多字节字符看作字符，也可能看作字节
  • 如果目的是数字符，不要依赖 shell 工具，改在懂 Unicode 的运行时里数。上面输出里 Node 给的 10 和 0 是明确的
  • 固定字符串检索（-F）与 locale 无关，是字节比较。所以形式不同就一定找不到。这一点反倒是可预测的
  • 教训是先确认工具是否把一个韩文音节当成一个字符，再拿来用。确认办法是喂进已知数量的样本再核对结果

5. 排序与去重边界 - 分解形永远排在最前面

我把两个分解形混进预合成形的列表里排序。只有 나 和 마 是分解形。

node v22.16.0 / win32
--- 4-2. 기본 sort() (코드포인트 순) ---
결과 : 나 마 가 다 라 바
기대 : 가 나 다 라 마 바
--- 4-3. localeCompare 정렬 ---
결과 : 가 나 다 라 마 바
--- 4-5. 정규화 후 기본 sort() ---
결과 : 가 나 다 라 마 바
--- 4-6. 왜 기본 sort가 어긋나나 ---
항목      첫 코드포인트
가               U+AC00
나               U+1102
다               U+B2E4
라               U+B77C
마               U+1106
바               U+BC14

默认的 sort() 给出了 나 마 가 다 라 바。两个分解形被拖到了前面。原因就摆在码点表里。预合成音节在 U+AC00 以上，而分解形初声在 U+1100 一带，所以在按码点排序时分解形无一例外都排在预合成形之前。

  • 症状不复现。如果列表大部分是预合成形，排序看起来是对的。只有在混入分解形条目的那一天，那一条才会跳到最上面
  • 分页会错位。排序基准一晃动，基于游标的分页就会重复或跳过条目
  • 用 localeCompare 排序顺序是对的。所以很容易只看排序就判断「没问题」
  • 可是顺序对与当作同一条目是两个不同的问题。第 1 节里看到的 Set.size = 2 还原封不动地在那儿
--- 4-7. 비교 결과 ---
a     b       a<b (기본)  localeCompare   lc('ko')
가    나           false             -1         -1
다    나           false              1          1
한    한           false              0          0
--- 4-8. Intl.Collator 로 중복 판정 ---
Collator 비교 '한' vs NFD '한' : 0

第三行是本节的结论。localeCompare 和 Intl.Collator 返回 0，即「相等」。这两个会考虑规范化。可是 Set、Map、对象键、数据库唯一索引、缓存键都不考虑。

说白了，比较层已经裂成了两半。给人看的排序与检索考虑规范化，而守护数据完整性的同一性判定只看字节。在两层给出不同答案的系统里，「列表上看起来是一条，存储里却有两条」这种状态会作为正常状态一直维持下去。重复账号、重复标签、重复分类就是这么诞生的。

6. 长度校验边界 - 「十字以内」被数成三倍

输入校验位于表单与服务器之间的边界。我看了那里有什么会错位。

node v22.16.0 / win32
--- 6-1. 네 가지 「글자 수」 ---
대상                  .length  코드포인트  utf8 byte  Segmenter
---------------------------------------------------------------
NFC 홍길동                  3           3          9          3
NFD 홍길동                  9           9         27          3
NFC 대한민국만세            6           6         18          6
NFD 대한민국만세           16          16         48          6
abc                         3           3          3          3
--- 6-2. 「10자 이내」 검증기 ---
NFC 대한민국만세       .length 통과        Segmenter 통과
NFD 대한민국만세       .length 거부(16)    Segmenter 통과
NFC 서울특별시강남구   .length 통과        Segmenter 통과
NFD 서울특별시강남구   .length 거부(21)    Segmenter 통과

只有 Intl.Segmenter 这一列在两边给出相同的值。与人所数的字符数一致的只有这一列。其余三列都随形式晃动。

计数方式单位在 NFD 下会怎样合适的用途
s.lengthUTF-16 代码单元最多膨胀三倍内存估算、索引
[...s].length码点最多膨胀三倍按码点遍历
Buffer.byteLength字节最多膨胀三倍存储容量、字段宽度
Intl.Segmenter字素簇不变用户看见的字符数

6.1 反方向也会被穿透

--- 6-3. 「3자 이상」 검증이 NFD를 뚫는다 ---
NFC 「가」 .length     : 1  → 3자 이상 통과? false
NFD 「한」 .length     : 3  → 3자 이상 통과? true

最小长度校验放过了一个字的输入。因为分解形 한 的代码单元长度是 3。最大长度校验会拒绝正常输入，用户会抗议；而最小长度校验放进了不合格输入，所以没有人会抗议。和第 4 节同样的结构。安静的那一侧才危险。

6.2 截断造成无法挽回的损伤

--- 6-4. 자르기가 글자를 반토막 낸다 ---
NFD 한국어 slice(0,2)  : "하"  ← 종성이 떨어져 나갔다
NFD 자른 뒤 NFC 정규화 : "하"  ← 정규화해도 복구되지 않는다
--- 6-5. Segmenter 단위로 안전하게 자르기 ---
권장 순서 : NFC 정규화 → Segmenter 로 자르기
정규화 먼저 한 결과 : "한" (코드포인트 1)

한 变成了 하。终声 nieun 被切掉了。而第二行很重要：截断之后再规范化并不会复原。规范化无法让消失的终声复活。这正是它与本文其他陷阱性质不同的原因。

  • 比较、检索、排序的失败之后规范化就能修好，因为数据还在
  • 截断是把数据丢掉。之后修不了。预览文本、摘要、通知消息、日志截断全都属于这一类
  • 所以顺序是定死的：先规范化，后截断。这个顺序不容商量
  • 要安全处理表情符号、国旗、组合字符，必须按字素簇边界切。Intl.Segmenter 就是为此而生

6.3 数据库字段的算法

--- 6-6. DB 컬럼 바이트 계산 ---
NFD 홍길동전이야기 utf8 바이트 : 54
NFC 홍길동전이야기 utf8 바이트 : 21

七个字是 21 字节和 54 字节。在按字节定字段的环境里，VARCHAR(30) 对预合成形很宽裕，对分解形则会溢出。数据库抛出的错误只说「数据太长」，并不会指向规范化。七个字的名字收到超过 30 字节的错误，就是怀疑规范化的依据。

7. 序列化与传输边界 - 这里什么都不会被修好

到目前为止看的都是会崩掉的边界。接下来该确认一个不会崩掉的边界了。而本节的要点是：不崩掉并不是好消息。

node v22.16.0 / win32
--- 7-1. JSON.stringify / parse 왕복 ---
원본 nfd 코드포인트 수     : 8
왕복 후 nfd 코드포인트 수  : 8
nfd 보존됨                 : true
--- 7-3. 파일 저장·읽기 왕복 (utf8) ---
파일 크기 (byte)           : 52
읽은 뒤 nfd 보존됨         : true
--- 7-4. 바이트로 확인 ---
파일 안에 NFD 초성 U+1112(e1 84 92) 바이트가 있는가 : true
파일 안에 NFC 한(U+D55C, ed 95 9c) 바이트가 있는가   : true

JSON 序列化与文件读写把形式原样放过去。以分解形放进去，就以分解形出来。直接看字节，两种形式并排躺在同一个文件里。

为什么这是坏消息？因为这意味着往返过程中任何一处都没有发生规范化。「存一遍再读出来应该就整理好了」这种模糊期待被证实毫无依据。分解形一旦进来，就会一直存在到离开系统为止。它不会因为经过存储层而自行统一。

7.1 对象键一分为二，值就被埋掉

--- 7-2. JSON 객체 키가 NFC/NFD로 갈리면 ---
키 개수                    : 2 ← 같은 이름인데 2개
키 목록 코드포인트 수      : 3, 8
parse 후에도 키 2개인가    : true
obj['한국어'] 로 읽으면    : NFC 값 ← NFD 값은 조용히 묻힌다

同名的键被造出了两个，用预合成形去读只会得到预合成形的值。分解形的值存在于对象里却无法访问。配置文件、翻译词典、映射表、缓存全是这个结构。「配置明明填了却不生效」的原因可能就在这里。打开文件键确实在那儿，所以很难追踪。

7.2 URL 与哈希把形式原样暴露出来

--- 7-6. URL 인코딩 ---
NFC URL : %ED%95%9C%EA%B5%AD%EC%96%B4
NFD URL : %E1%84%92%E1%85%A1%E1%86%AB%E1%84%80%E1%85%AE%E1%86%A8%E1%84%8B%E1%85%A5
--- 7-7. 해시가 갈린다 ---
sha256(NFC 한국어) : ea3252281bc3bcec
sha256(NFD 한국어) : 4cbdf1837a1d7592
해시가 같은가      : false
정규화 후 해시 같은가 : true

同一个查询词变成完全不同的 URL。后果随之而来。

  • 缓存被劈开 - CDN 与应用缓存把两个 URL 视为不同资源。命中率下降而原因看不见
  • 分析指标被劈开 - 同一查询词的流量被统计成两行。在热门查询榜上排名下滑，真实热度被低估
  • 规范 URL 晃动 - 同一份文档有了两个地址，搜索曝光就被分掉
  • 哈希被劈开 - 完整性校验、签名、重复文件判定全部失败。变成「同一个文件哈希却不同」
  • 凡是用哈希的地方都必须用约定把形式定死。不把「签名前用 NFC 规范化」写进文档，签名方与验证方就会给出不同答案

8. 压缩边界 - tar 和 zip 到底做了什么

文件在操作系统之间穿行的通道就是压缩包。我把分解形名字与预合成形名字的文件一起打包来确认。

  • 如果你是制作压缩包的一方，在打包前统一名字更好。消费者有多个时，在一处修更便宜

  • 不同工具与版本行为可能不同。有些压缩格式带有与名字编码相关的选项，所以应当用自己使用的工具直接确认。确认方式就是像上面那样打印码点

9. 字母的种类与 NFKC - 想扩宽反而丢得更多

该回答第 4 节留下的问题了：把字母加进去扩宽范围的 [ㄱ-ㅎㅏ-ㅣ가-힣] 为什么抓不到分解形？

node v22.16.0 / win32
--- 9-1. 세 종류의 「ㄱ」 ---
구분                    출력    [가-힣]   Hangul   utf8
-------------------------------------------------------
호환 자모 (U+3131)      ㄱ            X        O      3
조합용 초성 (U+1100)    ᄀ            X        O      3
조합용 종성 (U+11A8)    ᆨ              X        O      3
--- 9-2. NFD는 호환 자모를 쓰지 않는다 ---
NFD('가') 첫 글자 : U+1100  ← 조합용 초성
호환 자모 ㄱ      : U+3131
둘이 같은가       : false
NFD('가나다') 에서 [ㄱ-ㅎㅏ-ㅣ] 매칭 수 : 0
NFD('가나다') 에서 [ᄀ-ᇿ] 매칭 수 : 6

答案出来了：ㄱ 有三种。键盘上只按辅音键打出来的是兼容字母 U+3131，分解形使用的是组合用初声 U+1100，终声位置又是另一个 U+11A8。三者在屏幕上看着相似，却是彼此不同的字符。

  • 在正则里写 [ㄱ-ㅎ] 是打开了兼容字母的范围，与分解形无关
  • 要抓分解形必须打开 [ᄀ-ᇿ] 这一带。上面输出里抓到了 6 个
  • 初声与终声是不同码点这一点也是陷阱。用初声的 ㄱ 去检索终声的 ㄱ 是匹配不上的
  • 开得最宽的办法是 \p{Script=Hangul}。在第 4 节的表里它是唯一两边都抓到的
  • 不过开得最宽并不总是对的。做用户名校验时，也许需要拒绝正在组合中的字母。先定下要放行什么才是顺序

9.1 NFKC 额外会改掉什么

到这里会冒出「那用 NFKC 全部统一不就行了」的想法。必须实际看看会改掉什么。

--- 9-3. NFC/NFD는 호환 자모를 건드리지 않는다 ---
입력        NFC       NFD       NFKC      NFKD
U+3131 ㄱ   U+3131    U+3131    U+1100    U+1100
U+3158 ㅘ   U+3158    U+3158    U+116A    U+116A
--- 9-4. NFKC가 추가로 바꾸는 것들 ---
구분                원본    NFC     NFKC      변경됨
----------------------------------------------------
전각 영문 ＡＢＣ    ＡＢＣ  ＡＢＣ  ABC       O
전각 숫자 １２３    １２３  １２３  123       O
로마숫자 Ⅷ          Ⅷ       Ⅷ       VIII      O
원문자 ㈜           ㈜      ㈜      (주)      O
단위 ㎉             ㎉      ㎉      kcal      O
합자 ﬁ              ﬁ       ﬁ       fi        O
--- 9-5. NFKC는 되돌릴 수 없다 ---
'㈜'.normalize('NFKC') = (주)  (코드포인트 3개)
원본으로 되돌릴 방법이 있는가 : 없다 (정보가 손실된다)

第一张表说出了一个重要事实：NFC 与 NFD 不动兼容字母。U+3131 在正规分解里原样保留。会改它的只有 NFKC 和 NFKD。

再看第二张表就知道 NFKC 会顺手改掉多少东西。带圈的「㈜」变成三个字 (주)，单位「㎉」变成 kcal。没有办法还原。标准附件 15 也明确写了这一点：不得把兼容规范化形式盲目套用到任意文本上，因为它会抹掉大量格式上的区别。

  • NFKC 用于检索索引是有用的，它能让全角输入的查询词命中半角的正文
  • 但不要用在存储与展示的原文上。公司名里的「㈜」被存成 (주) 就再也回不去了
  • 实务上的做法是原文用 NFC 存储，另外用 NFKC 生成索引，两个值一起持有
  • 换言之规范化形式可以按层不同。关键是每一层都要说明自己持有哪种形式

9.2 这不是韩文独有的问题

--- 9-6. 이모지·결합 문자도 같은 문제 ---
구분                      .length  코드포인트   자소
é 합성형 (U+00E9)               1           1      1
é 분해형 (e + U+0301)           2           2      1
가족 이모지                     8           5      1
국기 KR                         4           2      1
정규화 후 같은가                        : true

字母 é 也是同样的结构。有一个预合成的码点，也有 e 加组合用锐音符的两个码点。屏幕上看着一样，=== 是 false。本文的所有处方原样适用。

表情符号那边稍有不同。家庭表情符号是代码单元 8、码点 5、字素簇 1。这不是规范化能统一的问题，而是从一开始就由多个码点构成的一个字。所以需要 Intl.Segmenter 的理由，除了规范化之外又多了一个。「数用户看见的字符数唯一安全的办法是字素簇」这个结论从两边都成立。

10. 边界判断表 - 在哪里只做一次规范化

我把至今跨越过的边界汇总成一张表。如果本文只带走一样东西，就带这张表。

边界什么会崩规范化位置
网页表单到服务器长度校验数成三倍，韩文正则校验在通过与拒绝之间反转服务器收到后立刻 NFC。信任边界内侧第一行
外部 API 接收无法控制发送方的形式解析之后立刻 NFC
读取目录列表条目可能以分解形到来，前缀过滤只匹配一半对 readdir 结果立即 NFC
写入文件会造出两个看起来一样的名字拼接路径之前 NFC
压缩到解压名字会被保留，在下一个消费者处崩掉打包之前 NFC，或解开之后立刻
数据库写入唯一索引把同一个名字看成两个假定已规范化。做不到就在写入前
构建检索索引分解形文档从索引里漏掉索引前 NFC，必要时另建 NFKC 索引
生成 URL 与查询串同一查询词变成两个 URL，缓存与指标被劈开生成链接前 NFC
哈希与签名同样的字得到不同哈希，验证失败用约定定死形式，签名前 NFC
截断与摘要终声被切断，字被弄坏。不可复原先规范化，后截断
渲染到屏幕什么都不会崩不要做。已经太晚了

10.1 为什么是「只做一次」

在多个地方规范化有什么问题？即使它能跑，也有不推荐的理由。

  1. 一定会出现漏掉的点。在每个比较处挂上规范化，意味着每次新增代码都得重新挂一遍。漏掉一处，那一处就静静地错
  2. 你会失去陈述不变式的能力。在边界规范化一次，你就能写下「这内侧的字符串全是预合成形」这一句。散着做就写不出这句话，读代码的人每次都要自己追踪
  3. 是否规范化本身变成了分支。一旦开始出现追问「这里规范化了吗」的代码，设计就已经塌了
  4. 会与需要保留原文的地方冲突。签名验证或原文再现需要另存规范化前的值。规范化点只有一个时，你才能说「它之前就是原文」
  5. 成本其实不是问题。规范化是幂等的，对已规范化的字符串再做一次结果相同。所以理由不是性能，而是责任归属

10.2 诊断顺序

真的碰到可疑情况时，顺序是这样。自上而下三步大体就能判明。

  1. 打印字节。用 od 看字符串或文件名，或者输出码点。以 e1 84 开头的三字节块连续出现就是分解形；以 ec 或 ed 开头就是预合成形
  2. 用三种方式数长度。看代码单元、码点、字素簇是否互相矛盾。前两者大于字素数就是分解形
  3. 把两边规范化后比较。规范化后变成相等，原因就确定了。这一行就是诊断的终点
  4. 原因确定后，从上面的表里挑修复位置。要修的不是症状出现的地方，而是那个值进来时经过的边界

11. 本文未能确认的部分

为了平衡，把局限说清楚。把没验证的事写成验证过的，这篇文章就会误导下一个人。

  • macOS 及其他文件系统的行为。测试环境只有 Windows 与 NTFS。关于 macOS 以分解形一类方式存储的流行说法无法验证，所以我不下断言。照 3.2 节的方法各自确认才是对的
  • Linux 的各种文件系统。没有测试。一般说法是把文件名当作字节串处理，但我没有用执行确认过
  • zip 命令的行为。这个环境里没有 zip，改用 PowerShell 代替。不同 zip 与 unzip 实现对名字编码的处理可能不同
  • 各数据库的行为。某个具体数据库是否在写入时做规范化，没有测试。可能随排序规则设置而不同，应当在你使用的产品上确认
  • 各浏览器输入法的行为。哪些输入路径会产出分解形，没有用执行确认。不过既然处方是无论哪种都要撑住，实务上知道与否影响不大
  • 规范化的性能。在大量文本上规范化的开销是否显著，没有测量。不做测量就以性能为理由省掉规范化，我不推荐

不过这些未能确认的事项有一个共同点：它们全都是关于「对面那侧怎么做」的问题。而本文的处方并不需要知道对面的行为才能成立。在边界做规范化，对面送来哪种形式就都无关了。这就是写边界契约的理由。

结论: 问题不在存储，而在边界

本文的起点是同一个目录里两个同名的文件。原因不是编码设置，不是文件系统的缺陷，也不是某个工具的毛病。而是Unicode 允许同一个字有两种表示，而没有人决定在哪里统一。

把执行确认到的东西整理一下：存储层大体是忠实的。JSON、文件读写、tar、zip 都把形式原样运过去，什么都不弄坏。正因如此，分解形一旦被放进来，就会一直活到离开系统为止。事故发生在它遇到期待预合成形的代码那一刻——查找文件的那一行、跑正则的那一行、数长度的那一行、算哈希的那一行。

其中在韩语服务里发作得压倒性地频繁的，是[가-힣] 一个分解形都抓不到。2 变 0，3 变 0。把字母加进去扩宽范围依然是 0。而这个失败不抛异常。校验器放行，过滤器抓不到，检查器返回「无异常」。结果穿着成功的外衣，而不是失败的样子。

所以结论不是「去做规范化」，而更接近定下一个规范化点，并把它写进文档。在每次比较前防御的做法一定会漏掉一处。在边界统一一次，你就能对内侧写下一句话：这里面的字符串全是预合成形。有这句话的代码与没有这句话的代码之间的差别，就是这个问题的全部。

现在马上就能做一件事：在仓库里找出用 [가-힣] 检查韩语字符串的代码，往那个位置喂一个分解形样本跑一下。如果本该通过的被拒绝，或者本该被抓住的通过了，那这个校验器一直只干了一半的活。而要修的地方不是那个正则，而是那个字符串进来时经过的边界。

# Unicode 规范化边界检查清单 (NFC / NFD)

> 来源: braindetox.kr — 韩文被拆成字母的瞬间，NFC 与 NFD
> 标准依据: Unicode UAX #15（规范化形式）、UAX #29（字素簇）
> 用法: 沿着韩文经过的路径自上而下过一遍。任何一个边界上答不出「由谁做规范化」，那里就是事故点。
> 也可以把这份文件直接贴给 AI，说「按我们的代码来检查一遍」。

## 0. 三十秒判定 — 命中任意一条就通读全篇

- [ ] 会比较、检索或排序韩文字符串
- [ ] 韩文来自用户输入、文件名或外部 API
- [ ] 会数「字符数」或截断字符串
- [ ] 会按名字查找文件
- [ ] 韩文会进入哈希、签名或缓存键
- [ ] 会收发压缩文件

## 1. 三行核心事实

1. 同一个「한」可能是一个码点（U+D55C），也可能是三个（U+1112 U+1161 U+11AB）
2. 渲染出来的结果完全一样。人眼绝对分辨不出来
3. 韩文音节的分解与组合是算术算法，因此**没有例外**。每一个音节都在范围内

## 2. 边界判断表 — 什么在哪里崩

| 边界 | 什么会崩 | 规范化位置 |
|---|---|---|
| 网页表单到服务器 | 长度校验数成三倍，正则校验反转 | 服务器收到后立刻 NFC |
| 外部 API 接收 | 发送方的形式不受你控制 | 解析之后立刻 NFC |
| 读取目录列表 | 条目以分解形到来，前缀过滤只匹配一半 | 对 readdir 结果立即 NFC |
| 写入文件 | 造出两个看起来一样的名字 | 拼接路径之前 NFC |
| 压缩到解压 | 名字被保留，在下一个消费者处崩掉 | 打包之前 NFC，或解开之后立刻 |
| 数据库写入 | 唯一索引把同一个名字看成两个 | 假定已规范化，否则写入前 |
| 构建检索索引 | 分解形文档从索引里漏掉 | 索引前 NFC |
| 生成 URL 与查询串 | 同一查询词变成两个 URL，缓存与指标被劈开 | 生成链接前 NFC |
| 哈希与签名 | 同样的字得到不同哈希 | 用约定定死，签名前 NFC |
| 截断与摘要 | 终声被切断，**不可复原** | 先规范化，后截断 |
| 渲染到屏幕 | 什么都不会崩 | 不要做（已经太晚了） |

## 3. 诊断命令 — 查看字节与码点

### 3.1 在 shell 里看文件名字节

```
# 查看文件名字节
for f in *; do printf '%s : ' "$f"; printf '%s' "$f" | od -An -tx1; done

# 判读方法
#   以 e1 84 / e1 85 / e1 86 开头的三字节块反复出现 -> 分解形（NFD）
#   以 ec / ed 开头的三字节                          -> 预合成形（NFC）
```

### 3.2 判定字符串状态 (Node)

```
const cps = s => [...s].map(c => 'U+' + c.codePointAt(0).toString(16).toUpperCase()).join(' ');
console.log(cps(s));
console.log('代码单元', s.length);
console.log('码点', [...s].length);
console.log('字节', Buffer.byteLength(s, 'utf8'));
console.log('字素', [...new Intl.Segmenter('zh', {granularity:'grapheme'}).segment(s)].length);
console.log('是否已是 NFC', s === s.normalize('NFC'));
```

### 3.3 判定字符串状态 (Python)

```
import unicodedata
print(len(s), len(s.encode('utf-8')))
print(unicodedata.is_normalized('NFC', s))
print([unicodedata.name(ch) for ch in s])
```

### 3.4 确认目录列表的形式

```
const fs = require('fs');
for (const f of fs.readdirSync(dir)) {
  console.log(f, [...f].length, f === f.normalize('NFC') ? 'NFC' : 'NFD');
}
```

## 4. 决定规范化位置的规则

- [ ] 是否**只定下了一种形式**（一般是 NFC）
- [ ] 是否**把这种形式写进了文档**（口头共识会被忘掉）
- [ ] 规范化点是否**位于边界**（而不是每次比较之前）
- [ ] 能否**写下这句话**：这内侧的字符串全是 NFC
- [ ] 是否有必须保留规范化前原文的地方（签名、原文再现）
- [ ] 是否**使用了 `normalize()` 的返回值**（只调用什么都不会发生）
- [ ] 若检索索引需要 NFKC，**原文是否另外以 NFC 保存**

### 为什么只做一次

1. 在每个比较处挂上，**每次新增代码都有漏掉的风险**
2. 在边界做，就**能把不变式写成一句话**
3. 一旦出现追问「这里规范化了吗」的代码，设计就已经塌了
4. 规范化点只有一个时，才能说「它之前就是原文」
5. 规范化是幂等的，成本不是问题。理由是**责任归属**

## 5. 常崩的模式与修正

| 症状 | 原因 | 修正 |
|---|---|---|
| 看到两个同名文件 | 两种形式各创建了一次 | 拼接路径前统一为 NFC |
| 存在的文件报不存在 (ENOENT) | 以分解形存储，以预合成形查询 | 直接使用 readdir 的结果 |
| `[가-힣]` 校验拒绝正常名字 | 输入是分解形 | 校验前做 NFC 规范化 |
| 韩文混入过滤器抓不到 | 对象是分解形，`[가-힣]` 无力 | 规范化后再检查，或用 Script 属性 |
| 违禁词过滤被绕过 | 绕过输入是分解形 | 在输入边界做 NFC |
| grep 在日志里找不到 | 正文与模式的形式不一致 | 把两边放成同一形式 |
| 去重失效 | Set 与唯一索引按字节比较 | 把键规范化为 NFC |
| 排序时只有几条跳到最上面 | 分解形初声位于 U+1100 一带 | 排序前 NFC |
| 「十字以内」拒绝正常名字 | 按代码单元数会变三倍 | 按字素簇计数 |
| 「至少三字」放过了一个字 | 分解形单字长度为 3 | 按字素簇计数 |
| 预览文字坏掉 | 终声被切掉了 | 先规范化，后截断 |
| 配置填了却不生效 | 对象键分裂成两种形式 | 把键规范化为 NFC |
| 同一个文件哈希却不同 | 形式不同 | 签名前 NFC，并写明约定 |
| 同一查询词在指标里成两行 | URL 有两个 | 生成链接前 NFC |
| 七个字的名字撑爆字段 | 分解形字节是三倍 | 写入前 NFC，字段按字节计算 |

## 6. 规范化形式的选择

| 形式 | 做什么 | 用在哪里 | 注意 |
|---|---|---|---|
| NFC | 正规分解后再正规组合 | 存储、比较、传输的默认值 | 多数情况统一到它 |
| NFD | 正规分解 | 初声检索等字母级处理 | 只在那一段里限定使用 |
| NFKC | 兼容分解后再正规组合 | 检索索引 | **不可逆**，不要用在原文上 |
| NFKD | 兼容分解 | 少见 | 与上同样注意 |

- `[가-힣]` 只抓**预合成音节**。对分解形的匹配是 0
- `[ㄱ-ㅎㅏ-ㅣ]` 是**兼容字母**范围。与分解形无关，同样是 0
- 分解形字母位于 `U+1100`~`U+11FF` 一带
- 想开到最宽就用 Script 属性转义，并且必须加上 `u` 标志
- 开得最宽并不总是对的。**先定下要放行什么**
