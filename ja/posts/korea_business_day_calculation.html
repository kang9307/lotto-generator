1. 「3営業日以内」が単純なカレンダー演算ではない理由

電子商取引における注文キャンセル返金処理、フィンテックサービスの決済代金精算サイクル、官公庁の電子民願受付や許認可の処理期限、カスタマーサポートの問い合わせ回答SLA（Service Level Agreement）など、エンタープライズバックエンドソフトウェア全般において最も頻繁に登場する業務要件の一つが「営業日基準でN日以内完了」という条件です。要件定義書や契約書に一行で記されたこの文言は、エンジニアにとって一見すると単なる日付オブジェクトへの整数加算のような極めて単純な処理に見えます。

初級開発者や業務ドメイン分析が不十分なプロジェクトチームは、現在の日付に整数を足し合わせるだけの単純な算術関数を作成したり、ループを回しながら土曜日（Saturday）または日曜日（Sunday）である場合にカウンタをスキップするような安易なアプローチで機能を実装しがちです。しかし、このような甘い実装は、本番環境にデプロイされた直後、旧正月（ソルラル）連休、秋夕（チュソク）連休、5月のゴールデンウィーク期間に直面した途端、精算遅延障害、法定処理期限違反のアラート発報、決済データ不整合といった致命的なシステムトラブルを引き起こします。

大韓民国において「営業日」をコードで正確に計算するタスクが、決して単純なカレンダーアルゴリズムにとどまらない本質的な理由は以下の通りです。

  • 休日の法的定義が単一の条文で完結しない構造：カレンダーから除外すべき休日は単なる赤字の日ではなく、大統領令が規定する固有の法体系の中で複雑に機能しています。
  • 振替休日の発動条件における非対称性と不均一性：すべての祝日が週末と重なった際に一律で翌週月曜日に振り替えられるわけではありません。特定の祝日は日曜日と重なった場合のみ振り替えられ、特定の祝日は土曜日と重なっても一切振り替えられません。
  • 振替休日同士の重複と連鎖的な前進移動：複数の振替休日が重なったり、振替休日自体が土曜日に落ちた際に発生する再帰的なスライド現象は、静的な固定オフセット加算を完全に無力化します。
  • 数式では予測不可能な国家行政判断の介入：アルゴリズムによって100年先まで事前計算できる天文学的暦法領域とは異なり、国務会議の審議を経て随時指定される臨時休日は、純粋なソースコードの外部に存在する非決定的な変数です。

このように営業日計算は、純粋な数学的日付演算ではなく、実定法の条文解釈と行政的な非決定性を包摂するソフトウェアアーキテクチャ設計の問題です。法令が厳格に規定しているアルゴリズムの領域と、法令の枠外に存在する企業の自律的な業務方針領域を峻別できなければ、システムは例外事象のたびに障害を発生させることになります。

2. 法定公休日11種の体系と法的根拠：官公署休日規定第2条

大韓民国において官公庁が業務を休む日、そしてこれを準用して金融機関の電算ネットワークや産業界全体が非営業日の基礎基準として採用している休日の唯一の法的根拠は、大統領令として制定された**「官公署の休日にかんする規定」（人事革新処所管）**です。同令第2条は、官公署の公休日を以下の11種類の号に明確に限定して列挙しています。

条文原本に明示された法定公休日の11種の類型と詳細な定義は以下の通りです。

号番号 公休日の名称 指定基準および日付 振替休日の適用対象
第1号 日曜日 毎週日曜日 非該当（基準となる定期休日）
第2号 国慶日 「国慶日に関する法律」に基づく国慶日（3・1節、光復節、開天節、ハングルの日） 該当（土・日重複時）
第3号 1月1日 太陽暦1月1日（新年） 非該当（規定上の適用対象外）
第4号 旧正月連休 旧正月の前日、旧正月、旧正月の翌日（太陰暦12月末日、1月1日、2日） 該当（日曜日重複時のみ）
第5号 釈迦誕生日 太陰暦4月8日（仏誕節） 該当（土・日重複時）
第6号 メーデー 太陽暦5月1日（労働節） 該当（土・日重複時）
第7号 こどもの日 太陽暦5月5日 該当（土・日重複時）
第8号 顕忠日 太陽暦6月6日（戦没者追悼日） 非該当（規定上の適用対象外）
第9号 秋夕連休 秋夕の前日、秋夕、秋夕の翌日（太陰暦8月14日、15日、16日） 該当（日曜日重複時のみ）
第10号 基督誕生記念日 太陽暦12月25日（クリスマス） 該当（土・日重複時）
第10号の2 選挙日 「公職選挙法」第34条に基づく任期満了による選挙の選挙日 非該当（規定上の適用対象外）
第11号 随時指定日 その他政府において随時指定する日（臨時公休日） 事案ごとに決定（国務会議の審議）

この対照表においてバックエンドエンジニアが最も注視すべき核心的事実は、日常会話において漠然と「赤い日（祝祭日）」と一括りに呼んでいる日付が、ソフトウェアの内部ロジックにおいては全く異なるルールで処理されなければならないという点です。

例えば太陽暦1月1日（第3号）や顕忠日（第8号）は、間違いなく第2条に列挙された国家法定公休日です。しかし後述する第3条（振替公休日）の条文を精査すると、この2つの日は振替休日の適用対象号のリストから明示的に除外されています。つまり1月1日や6月6日が土曜日や日曜日と重なったとしても、現行法令上、振替休日は1日たりとも発生しません。この法的な事実を把握せず「祝日が週末と重なれば無条件で翌週月曜日に繰り延べる」という一般化されたルールを適用した瞬間、カレンダーエンジンは存在しない架空の振替休日を作り出し、システム全体の精算日や納期を1日後ろへずらしてしまう重大なバグを引き起こします。

3. 振替休日の3分岐による非対称条件：第3条第1項の分析

営業日演算ロジックにおいて最も多くの不具合が集中するポイントは、間違いなく振替休日（Alternative Holiday）の算出処理です。現場の開発者は振替休日の規則を極度に単純化し、「週末と重なれば直後の月曜日」という単一の条件分岐で済ませようとする強い誘惑に駆られます。しかし「官公署の休日にかんする規定」第3条第1項は、振替休日の発動要件を3つの号に明確に分割しており、各号ごとに適用対象となる祝日が異なっています。

条文第3条第1項における3分岐条件の詳細は以下の通りです。

分岐区分 適用対象条文 発動要件の基準 法的な結果
第1号類型 第2号（国慶日）、第5号（釈迦誕生日）、第6号（労働節）、第7号（こどもの日）、第10号（クリスマス） 該当公休日が土曜日または日曜日と重なる場合 その公休日の直後の最初の非公休日
第2号類型 第4号（旧正月連休3日間）、第9号（秋夕連休3日間） 該当公休日が日曜日と重なる場合（土曜日は除外） その公休日の直後の最初の非公休日
第3号類型 第2号、第4号〜第7号、第9号、第10号 土曜・日曜ではない平日に他の公休日と重なる場合 その公休日の直後の最初の非公休日

この分岐構造において最も決定的な非対称性は、第1号と第2号における週末処理の差異に存在します。国慶日、釈迦誕生日、メーデー、こどもの日、クリスマスは、土曜日と日曜日の両方に対して振替休日の発生を認めます。これに対して、大韓民国の二大伝統名節連休である旧正月連休（太陰暦12月末日、1月1日、2日）と秋夕連休（太陰暦8月14日、15日、16日）は、唯一「日曜日」と重なった場合のみ振替休日が発動すると法律上厳格に規定されています。

これがソフトウェアに意味するものは明白です。旧正月連休の3日間のうちいずれか1日が土曜日と重なったとしても、第3条第1項第2号の要件を満たさないため振替休日は発生しません。例えば旧正月の当日が金曜日で翌日の連休最終日が土曜日であった場合、土曜日の連休に対して法的な振替休日は付与されません。連休3日間のいずれかが日曜日と重複した場合に限り、連休直後の最初の非公休日が振替休日として指定されます。この条文上の非対称性を無視して旧正月や秋夕連休まで土曜日重複時に繰り延べるコードを組むと、実際の法定営業日よりも1日多く営業日をスキップしてしまい、業務処理遅延を招くことになります。

また第3号条件は、平日に公休日同士が偶然重複する天文学的・暦法的な衝突ケースを防衛します。例えば太陽暦5月5日のこどもの日と太陰暦4月8日の釈迦誕生日が同一の火曜日に重複した場合、1日分の休日が消失しないよう、直後の最初の非公休日を振替休日として確保するための規定です。これら3つの独立した分岐要件を単一のブール式に縮約することは、法解釈上明白な誤りです。

4. 連鎖衝突と土曜日処理：第3条第2項・第3項と再帰的前進

振替休日が発動して「その公休日の直後の最初の非公休日」を探索するプロセスは、単なる1日加算（`current_date + 1`）では完結しません。振替休日自体がすでにカレンダー上に存在する他の公休日と衝突したり、算出されたスライド先が土曜日であった場合、連鎖的な衝突が発生するためです。規定はこれを解決するために第3条第2項および第3項を設けています。

「第3条② 第1項による代替公休日が同日に重複する場合には、その代替公休日の直後の最初の非公休日までを代替公休日とする。」
「第3条③ 第1項および第2項による代替公休日が土曜日である場合には、その直後の最初の非公休日を代替公休日とする。」

これらの条項は、計算機科学の観点から見れば完全な再帰的前進（Recursive Roll-Forward）演算を要求しています。第1項によって導出された振替休日の候補日 $D$ がもし土曜日であれば、第3項によってその翌日である日曜日（非公休日ではない）を経て、さらに翌日の月曜日へと前進探索しなければなりません。もしその月曜日すらも別の事由による振替休日やすでに固定された祝日と重複していた場合、第2項によってさらに翌日へと玉突きで押し出される必要があります。

この連鎖条件をソフトウェアで実装する際の核心的なアルゴリズム構造は以下のように記述できます。

// 官公署の休日にかんする規定第3条に基づく振替休日の連鎖解決関数
function resolveAlternativeHolidays(
    baseHolidays: Set<string>,
    tentativeAltHolidays: string[]
): Set<string> {
    const finalAltHolidays = new Set<string>();
    const occupiedDates = new Set<string>(baseHolidays);

    for (const altTarget of tentativeAltHolidays) {
        let candidate = getNextDay(altTarget);

        // 第3条第2項（重複時前進）および第3条第3項（土曜日判定時前進）の評価ループ
        while (true) {
            const dayOfWeek = getDayOfWeek(candidate);
            const isSaturday = dayOfWeek === 6;
            const isSunday = dayOfWeek === 0;
            const isOccupiedHoliday = occupiedDates.has(candidate);

            // 土曜日、日曜日、または既に他の公休日・振替休日として占有されている場合は翌日へ前進
            if (isSaturday || isSunday || isOccupiedHoliday) {
                candidate = getNextDay(candidate);
            } else {
                // 非公休日である最初のクリーンな平日を確定
                finalAltHolidays.add(candidate);
                occupiedDates.add(candidate);
                break;
            }
        }
    }

    return finalAltHolidays;
}

このアルゴリズムが保証する不変条件（Invariant）は、「確定された振替休日は、土曜日、日曜日、既存の法定公休日、および先行して確定された他の振替休日のいずれとも重複しない純粋な非公休日でなければならない」という点です。この連鎖探索ロジックを欠いたカレンダーエンジンは、5月上旬の飛び石連休や秋夕連休のように複数の公休日と振替休日が連続して噛み合うサンドイッチ連休期間において、必ず日付の二重カウント判定エラーを引き起こします。

連鎖衝突の構造を確実に制御するためには、以下の4つの状態遷移ステップをコードレビューの必須チェックリストとして管理する必要があります。

  • 単一振替候補の土曜日落下検証：振替休日として算出された候補日が土曜日である場合、単純に2日足して月曜日にジャンプするのではなく、日曜日の公休日性を含めて厳密に最初の非公休日を再探索しているか
  • 複数振替休日の同日競合検証：異なる2つの祝日が同一の翌平日を振替先として指定した場合、2件目の振替先がさらにその翌日の非公休日へと順次玉突き配分されるか
  • 既存固定祝日との干渉検証：繰り延べられた振替休日候補地が、たまたま5月5日のこどもの日など既存の他の法定祝日と重複した場合に、ループを停止せず探索を継続できるか
  • 暦法上の非公休日確定終了条件：ループの終了条件が単なる週末判定だけでなく、登録された全公休日セットとの積集合が空集合である状態を正確に判定しているか

5. 決定的アルゴリズムと非決定的政策の境界：臨時休日と第4条

ここまで考察した第2条第1号から第10号までの法定公休日と第3条の振替休日規定は、複雑ではあるものの、原則として**決定的（Deterministic）**な領域に属します。グレゴリオ暦の太陽暦算出法、韓国天文研究院が算出する太陰暦対照データ、そして公職選挙法の任期満了規定さえ与えられれば、2026年であれ2030年であれ、数式と静的ルールだけで100%事前に算出可能です。

しかし、ソフトウェア開発者が決して静的コードに還元できない絶対的な境界線が、第2条第11号および第4条に規定されています。

「第2条 11. その他政府において随時指定する日」
「第4条（臨時公休日の指定） 第2条第11号による公休日を指定しようとする場合には、国務会議の審議を経なければならない。」

第4条が明示している通り、臨時公休日（Temporary Public Holiday）は、国務会議（内閣に相当）の審議を経て行政府が随時決定する高度な政策的判断です。飛び石連休をつないで内需喚起を図ったり、国家的な記念行事のために特定日を臨時休日に指定する行為には、事前に定められた暦法上の周期や規則性が一切存在しません。国務会議で可決され、大統領令の改正または官報への掲載を経て公式に公布されるまでは、世界中のいかなる優れたカレンダーライブラリもその日が休日になるかどうかを事前に判定することは不可能です。

これがソフトウェアエンジニアリングに対して持つ意味は極めて重大です。多くの開発チームが犯す典型的な過ちは、オープンソースのカレンダー計算ライブラリを導入したり、ソースコード内部に静的なユーティリティクラスとして公休日データをハードコーディングした時点で「祝日計算機能の開発は完了した」と思い込むことです。どれほど精巧に条文を実装していても、9月下旬に政府が国務会議を開いて10月1日を臨時休日に指定した瞬間、静的アルゴリズムに依存するシステムは破綻します。臨時休日の指定情報が反映されないまま稼働を続け、システムは10月1日を平日と誤認して顧客へ自動引き落とし案内を発信したり、SLA遅延アラートを誤検知することになります。

したがって営業日計算システムの設計者は、「アルゴリズムによって完全に決定可能な領域」と「政府の行政行為によって非決定的に注入される領域」の間に明確な境界線を引き、アーキテクチャを設計しなければなりません。

6. アーキテクチャ設計：ハードコーディング脱却と動的データソース分離

臨時休日の非決定性から本番システムを守るために採用すべきアーキテクチャの原則は唯一無二です。公休日判定ロジックをアプリケーションバイナリの静的コードから切り離し、動的に更新可能な外部データソースへと分離することです。

最も推奨される設計パターンは、2層ハイブリッド判定エンジン（Two-Tier Hybrid Judgment Engine）です。基底層では第2条および第3条に基づく決定的な公休日・振替休日をアルゴリズムで自動生成しつつ、上位層では毎年政府の発表や公共データポータルの特日情報API（韓国天文研究院の祝日APIなど）を通じて更新されるオーバーレイデータベースを結合するアプローチです。

// 静的ルールと動的オーバーレイを結合する堅牢な営業日計算エンジンインターフェース
interface HolidayDataSource {
    getHolidaysForYear(year: number): Promise<Set<string>>;
}

class ResilientBusinessDayEngine {
    constructor(private holidaySource: HolidayDataSource) {}

    public async isBusinessDay(targetDate: Date): Promise<boolean> {
        const dateStr = formatDateToYYYYMMDD(targetDate);
        const dayOfWeek = targetDate.getDay();

        // 1. 週末（土曜日=6、日曜日=0）を即座に除外
        if (dayOfWeek === 0 || dayOfWeek === 6) {
            return false;
        }

        // 2. 動的に更新される該当年度の公休日セット（臨時休日を含む）を照会
        const holidays = await this.holidaySource.getHolidaysForYear(targetDate.getFullYear());
        if (holidays.has(dateStr)) {
            return false;
        }

        return true;
    }

    public async addBusinessDays(startDate: Date, businessDaysToAdd: number): Promise<Date> {
        let current = new Date(startDate);
        let added = 0;

        while (added < businessDaysToAdd) {
            current = getNextCalendarDay(current);
            if (await this.isBusinessDay(current)) {
                added++;
            }
        }

        return current;
    }
}

このようなアーキテクチャをミッションクリティカルな高トラフィック決済基盤で運用する場合、以下の運用指針を厳格に遵守する必要があります。

  • 公休日データのインメモリキャッシングと無停止即時破棄機構：日付判定は決済や注文処理のクリティカルパス上で毎秒数千回呼び出されるため、毎回外部DBやAPIを叩いてはならず、メモリ上にキャッシュしつつ、国務会議の議決直後に管理画面からキャッシュを破棄（Eviction）できるエンドポイントを用意する
  • 公共API障害に備えたローカル永続化フォールバック：外部の政府特日APIのネットワーク障害やタイムアウト時にも決済エンジンが停止しないよう、同期済みデータは必ずRDBMSや検証済みJSONスナップショットとして最低2年分ローカルに永続化しておく
  • 臨時休日の遡及適用に対するスケジュール再計算パイプライン：臨時休日は施行日のわずか数週間前に決定されることが多いため、休日テーブルの更新時に影響を受ける未来のバッチ処理や満了日スケジュールを再計算（Recalculate）するパイプラインを設計しておく
  • タイムゾーン不変条件の徹底：日付文字列（YYYY-MM-DD）のパースや境界判定は、クライアントブラウザや実行コンテナのUTC設定に影響されず、必ず韓国標準時（KST, UTC+09:00）の深夜0時を基準として一貫して処理されるよう保証する

7. 締め切り時刻と営業日の起算点：法令が定めるものと内部方針の分離

実務の現場において営業日計算に関して最も激しい契約上・法務上の紛争が発生するポイントの一つが、**当日の受付締め切り時刻（Cut-off Time）**と**起算日（Day Zero）**の問題です。

例えばあるECサービスが「注文受付後3営業日以内に発送」というポリシーを掲げているとします。ユーザーが金曜日の午後11時55分に決済を完了した場合、「3営業日」はいつまでを指すのでしょうか。金曜日を1日目としてカウントして火曜日までに発送すべきか、それとも金曜日夜間はすでに業務時間外であるため翌週月曜日から起算して木曜日までに発送すべきでしょうか。

ここで開発者が極めて明確に認識すべき事実があります。「官公署の休日にかんする規定」には、午後5時や午後6時といった1日の受付締め切り時刻に関する規定は一切存在しません。 この大統領令はあくまで丸1日（0時から24時まで）の日付単位で公休日であるか否かを定めるのみであり、1日の中の時刻境界はこの法令の守備範囲外です。

期間計算に関する大韓民国の一般法である**民法第157条**は、期間の起算点について以下のように定めています。

「民法第157条（期間の起算点） 期間を日、週、月または年で定めたときは、期間の初日は算入しない。しかし、その期間が午前零時から始まるときは、この限りではない。」

法律上の大原則は**初日不算入（初日は数えない）**です。午前0時ちょうどに開始された取引でない限り、イベントが発生した当日は除外され、翌日から起算して1日目とするのが民法の大原則です。しかし実際の商取引や金融標準約款では、各金融機関や企業が自社の利用規約を通じて「営業日午後4時までの受付は当日起算、それ以降は翌営業日受付とみなす」という**自社固有のカットオフ規定**を有効に定めています。

したがってソフトウェア設計においては、以下の2つの独立したレイヤーを峻別しなければなりません。

  • 法令の領域（公休日判定）：カレンダー上の特定の日付が公休日であるかどうかは、大統領令に基づき客観的かつ厳格に決定される。
  • 約款と方針の領域（起算点およびカットオフ判定）：受付時刻が締め切りを過ぎた場合に当日を起算から外すか、あるいは民法の初日不算入を適用して翌営業日からカウントするかは、サービス利用規約や契約条件によって決定される。

この2つのレイヤーを混同してカレンダーライブラリの中にカットオフ時刻をハードコーディングしてしまうと、配送キャリアや決済代行会社ごとに異なる締め切り時刻（宅配便は18時、決済精算は15時など）に対応できなくなります。締め切り判定ロジックは、公休日判定エンジンの前段に位置する独立したポリシーパイプラインとして分離設計すべきです。

8. 営業日計算エンジンの実装時に検証すべき核心チェックリスト

ここまで分析してきた実定法の条文解釈とアーキテクチャ設計原則を総括し、本番環境に営業日計算モジュールをリリースする前に開発チームが検証すべき5つの必須チェックリストを提示します。

  • 条文別振替休日非対称性の単体テスト構築：旧正月連休および秋夕連休が土曜日と重なったテストケースを作成し、振替休日が生成されないことを機械的にアサーションしているか
  • 1月1日および顕忠日の週末重複における非代替性検証：新年と顕忠日が土・日に落ちた際、翌月曜日が通常の営業日として正しく認識されるテストが存在するか
  • 再帰的連鎖探索ループの脱出および上限保証：複雑な飛び石連休と複数振替休日が重複する極限ケースにおいても、無限ループに陥らず最短の非公休日へと正しく収束するか
  • 臨時休日のランタイム動的注入インターフェース完備：コンテナの再デプロイを伴わずに、運用中に国務会議指定の臨時休日を即時システムへ反映できるデータ構造を備えているか
  • 受付締め切り方針と初日算入ルールの分離性：注文、精算、CS等の各業務ドメイン別のカットオフ時刻設定が、カレンダーエンジンと密結合せず独立した設定パラメータとして注入可能か

数式上どれほど美しく整ったコードであっても、法律と行政の現実が持つ繊細な境界線を反映できなければシステムの信頼性を担保することはできません。「官公署の休日にかんする規定」の条文一つ一つを正確に読み解き、それを堅牢なアーキテクチャへと昇華させることこそが、信頼性の高いエンタープライズバックエンドを構築するための第一歩となります。

確認できなかった事項

本記事は大韓民国の大統領令である「官公署の休日にかんする規定」の条文分析およびソフトウェア工学的示唆を中心に執筆されました。公式法令原本に明記されていない事項や、法令の適用範囲を超える事項として本文中で確定的に記述しなかった項目は以下の通りです。

  • 「営業日」そのものの普遍的・法律的定義：「官公署の休日にかんする規定」は官公庁が業務を休む公休日のみを限定列挙しており、一般商取引や民間部門で広く用いられる「営業日（Business Day）」という用語自体の法的定義は規定していません。土曜日の営業日性や具体的な起算基準は、個別法令、金融監督機関の標準約款、個別契約ごとに異なるため、本稿では単一の基準として一般化していません。
  • 民間事業所全体における法定有給休日の運用実態：本規定は「官公署」の公休日を規律する大統領令です。勤労基準法第55条第2項に基づき常時5人以上の事業所では官公署の公休日が有給休日として義務付けられていますが、交代制勤務事業所や週6日制の民間企業における個別の就業規則や約定休日の運用慣行は本規定の範囲外であるため扱っていません。
  • 企業および金融機関別の業務受付締め切り時刻（Cut-off Time）の統一基準：本規定には16時や17時といった時間単位の受付締め切り時刻に関する基準は存在しません。機関別、業務別のカットオフ時刻は各社の内部規約および運用ポリシーに委ねられているため、特定の時刻を普遍的基準として断定していません。
  • 海外株式および外国為替決済システムにおける多国間複合営業日（T+2, T+3）のクロスボーダー精算規則：本稿は大韓民国の官公署休日規定のみを対象として分析を行っているため、米国など海外市場の休場日と韓国の休場日が食い違う複合決済網のクロスボーダー精算ルールについては扱っていません。
  • 国務会議による臨時公休日指定の年間平均頻度および事前予告期間の統計：臨時休日の指定は歴代政府の政策的判断により随時決定されてきたものであり、法令自体に指定周期や事前の予告期限が定められていないため、任意の予測統計数値は記載していません。
