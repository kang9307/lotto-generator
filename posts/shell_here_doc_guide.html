히어독 실전 - 변수 확장을 끄고 켜기, 들여쓰기 함정

구분자에 씌운 따옴표 하나가 본문 전체의 해석을 바꾼다. 전부 돌려서 나온 출력을 그대로 붙였다

2026-09-01 개발/인프라

설정 파일 열 줄을 스크립트에서 만들어야 할 때, echo 를 열 번 쓰는 사람과 히어독을 쓰는 사람의 차이는 취향이 아니다. 열 줄 중 한 줄에 겹따옴표가 들어가는 순간 앞쪽은 무너진다. 히어독은 그 자리를 대신하려고 있는 문법이고, 그래서 본문을 셸이 어디까지 건드리는가가 이 문법의 전부다.

그 경계는 딱 한 곳에서 정해진다. 구분자에 따옴표가 붙었는가 아닌가. 이 한 글자가 $ 와 백틱과 백슬래시의 운명을 동시에 바꾼다. 나머지 함정 대부분은 여기서 파생되거나, 종료 구분자를 못 찾는 문제로 수렴한다.

아래 출력은 전부 Windows 의 Git Bash 환경, GNU bash 5.2.37(1)-release (x86_64-pc-msys) 에서 실제로 실행해 나온 것을 그대로 옮긴 것이다. 비교가 필요한 대목은 같은 상자에 들어 있는 dash 로도 돌려 봤고, 결과가 갈리는 자리는 그때그때 적었다.

셸의 동작은 구현과 버전에 따라 달라진다. 이 글의 출력은 위에 적은 한 조합에서 나온 것이며, 특히 히어독의 내부 저장 방식과 줄바꿈 처리는 MSYS 계열과 glibc 리눅스가 다를 수 있는 대목이다. 확인하지 못한 부분은 뒤쪽에 따로 모아 두었다.

히어독이 대신하는 자리

여러 줄 문자열을 만드는 방법은 여럿이다. echo 를 반복하거나, printf 에 개행을 박아 넣거나, 변수 하나에 \n 을 이어 붙이거나. 이 셋은 내용에 따옴표가 없는 동안만 편하다. 설정 파일이나 SQL 이나 JSON 처럼 따옴표가 내용의 일부인 텍스트가 들어오면 바깥 인용과 안쪽 인용이 겹치면서 읽을 수 없는 줄이 된다.

# 인용부호가 내용에 들어오는 순간
echo "{"                     # 이건 되고
echo "  \"name\": \"$app\","  # 여기서부터 눈이 아프다
echo "  \"debug\": false"
echo "}"

# 같은 것을 히어독으로
cat <<EOF
{
  "name": "$app",
  "debug": false
}
EOF

히어독이 해결하는 것은 정확히 이 자리다. 본문 안의 따옴표는 아무 의미도 갖지 않는다. 셸이 그 줄을 단어로 쪼개지 않기 때문이다. 개행도 그대로 살아 있고, 들여쓰기도 그대로 간다. 따옴표 일반 규칙 자체가 헷갈린다면 셸 인용부호 규칙 쪽이 먼저다. 여기서는 구분자에 붙는 따옴표만 다룬다. 성격이 완전히 다른 물건이다.

  • 본문 안의 " 와 ' 는 이스케이프하지 않는다. 인용부호로 취급되지 않는다
  • 개행은 문자 그대로 보존된다. \n 을 쓸 일이 없다
  • 본문은 명령의 표준 입력으로 들어간다. 인자가 아니다. 그래서 인자 길이 제한과 무관하다
  • 대신 표준 입력을 쓰므로, 표준 입력을 이미 쓰고 있던 자리와 충돌한다. 7절에서 다룬다
  • 구분자로 관례상 EOF 를 많이 쓰지만 아무 단어나 된다. 본문에 나올 리 없는 단어가 좋다

구분자의 따옴표 한 글자

이 글에서 하나만 가져간다면 이것이다. <<EOF 와 <<'EOF' 는 같은 본문을 전혀 다르게 해석한다. 여덟 가지 입력을 한 파일에 넣고 두 형태로 돌려 봤다.

name=world

# A: 따옴표 없는 구분자
cat <<EOF
plain: $name
cmdsub: $(echo hi)
backtick: `echo hi`
backslash-dollar: \$name
backslash-n: \n
backslash-backslash: \\
tilde: ~
star: *
EOF

# B: 본문은 한 글자도 다르지 않고, 구분자만 따옴표로 감쌌다
cat <<'EOF'
plain: $name
cmdsub: $(echo hi)
backtick: `echo hi`
backslash-dollar: \$name
backslash-n: \n
backslash-backslash: \\
tilde: ~
star: *
EOF

나온 출력이다.

=== A: <<EOF (unquoted) ===
plain: world
cmdsub: hi
backtick: hi
backslash-dollar: $name
backslash-n: \n
backslash-backslash: \
tilde: ~
star: *

=== B: <<'EOF' (quoted) ===
plain: $name
cmdsub: $(echo hi)
backtick: `echo hi`
backslash-dollar: \$name
backslash-n: \n
backslash-backslash: \\
tilde: ~
star: *
본문에 적은 것<<EOF 출력<<'EOF' 출력무엇이 일어났나
$nameworld$name매개변수 확장
$(echo hi)hi$(echo hi)명령 치환
백틱 echo hihi백틱 그대로옛 형태의 명령 치환
\$name$name\$name백슬래시가 달러를 막고 자신은 사라진다
\n\n\n둘 다 그대로. n 은 특수문자가 아니다
\\\\\앞쪽만 백슬래시 한 겹이 벗겨진다
~~~둘 다 그대로. 물결 확장은 일어나지 않는다
***둘 다 그대로. 경로 확장은 일어나지 않는다

끄는 표기는 세 가지다

홑따옴표만 쓸 수 있는 것이 아니다. POSIX 규격은 구분자 단어의 어느 한 부분이라도 인용되면 본문을 확장하지 않는다고 적고 있다. 그래서 아래 셋은 전부 같은 효과다. 세 형태 모두 bash 5.2.37 과 dash 양쪽에서 확장이 꺼지는 것을 확인했다.

  • <<'EOF' — 가장 흔하고 가장 눈에 띈다. 이걸 쓰면 된다
  • <<"EOF" — 겹따옴표여도 마찬가지로 꺼진다. 겹따옴표라서 반쯤 켜질 것 같지만 아니다
  • <<\EOF — 백슬래시 한 글자로도 꺼진다. 짧아서 오히려 못 알아보기 쉽다

히어독이 하지 않는 확장

표의 마지막 두 줄이 자주 오해받는다. 따옴표 없는 히어독이라도 단어 분리와 경로 확장과 물결 확장은 일어나지 않는다. 본문은 처음부터 단어가 아니라 한 덩어리의 텍스트로 취급되기 때문이다. 일어나는 것은 매개변수 확장, 명령 치환, 산술 확장 셋뿐이고 백슬래시는 겹따옴표 안에서와 같은 규칙을 따른다.

  • 따라서 *.log 를 본문에 적어도 파일 목록으로 펼쳐지지 않는다. 리모트에서 펼치라고 넘길 때 이게 편하다
  • ~/bin 도 홈 경로로 바뀌지 않는다. 홈 경로를 로컬 값으로 박고 싶으면 $HOME 을 쓴다
  • 본문 안의 공백은 그대로다. 여러 칸 띄운 정렬이 깨지지 않는다
  • 산술 확장 $(( )) 는 켜져 있다. 원격에서 계산하게 하려면 \$(( )) 로 막는다

반만 확장하고 싶을 때

실무에서 가장 자주 나오는 요구는 대부분은 그대로 두고 몇 개만 지금 값으로 박는 것이다. 따옴표 없는 히어독을 쓰고 나머지를 전부 \$ 로 막으면 된다. 되기는 되는데, 아래를 보면 왜 금방 지저분해지는지도 같이 보인다.

LOCAL_DIR=/tmp/demo

cat <<EOF
cd $LOCAL_DIR
for f in *.log; do
  echo "\$f"
done
total=\$(( 1 + 2 ))
echo "\$total \$HOME"
EOF
cd /tmp/demo
for f in *.log; do
  echo "$f"
done
total=$(( 1 + 2 ))
echo "$total $HOME"

의도한 대로 $LOCAL_DIR 하나만 값으로 바뀌었다. 문제는 비율이다. 이 예제는 여섯 줄에 이스케이프가 다섯 개다. 스무 줄을 이렇게 넘기면 백슬래시가 스무 개 넘게 붙고, 하나만 빠뜨려도 조용히 잘못된 값이 박힌다.

  • 이스케이프 개수가 서너 개를 넘어가면 방향을 뒤집는다. 구분자를 따옴표로 감싸고, 필요한 값은 인자로 넘긴다
  • 인자로 넘기는 방법은 9절에 있다. 로컬에서 확장되는 자리를 "$1" 한 곳으로 몰아넣는 방식이다
  • 중간 형태로, 본문 맨 위에 VAR=값 몇 줄만 따옴표 없는 히어독으로 먼저 내보내고 본문은 따옴표 있는 히어독으로 잇는 방법도 쓴다
  • 어느 쪽이든 원칙은 하나다. 확장되는 자리를 세어서 셀 수 있는 개수로 유지한다

붙임표는 탭만 지운다

<<-EOF 는 들여쓰기를 지워 준다고 알려져 있다. 정확히는 선행 탭 문자만 지운다. POSIX 규격의 문장이 그렇게 적혀 있고, 종료 구분자 줄에도 같은 규칙이 적용된다. 스페이스는 대상이 아니다.

탭이면 된다

# cat -A 로 본 원본. ^I 가 탭이다
if true; then$
^Icat <<-EOF$
^I^Iline one$
^I^Iline two$
^IEOF$
fi$
echo "after: $?"$

# 실행 결과
line one
line two
after: 0

스페이스면 안 된다

편집기 설정 하나가 이걸 뒤집는다. 같은 파일을 탭 대신 스페이스 네 칸으로 저장하고 돌린 결과다.

# cat -A 로 본 원본. 탭이 하나도 없다
if true; then$
    cat <<-EOF$
        line one$
        line two$
    EOF$
fi$
echo "after"$

# 실행 결과
e2b.sh: line 7: warning: here-document at line 2 delimited by end-of-file (wanted `EOF')
e2b.sh: line 8: syntax error: unexpected end of file
exit=2

여기서는 fi 가 있어서 문법 오류로 터졌다. 운이 좋은 경우다. 감싸는 블록이 없으면 오류 없이 조용히 지나간다. 5절에서 그 쪽을 본다.

탭이 내용일 때

규격의 문장은 「선행 탭 문자를 모두 제거한다」이다. 들여쓴 만큼만이 아니다. 그래서 탭이 의미를 갖는 내용을 붙임표 형태로 내보내면 그 탭까지 사라진다. Makefile 레시피 줄이 대표적이다.

# 원본 (^I 는 탭)
cat <<-EOF$
^Iall:$
^I^Igcc -o app main.c$
^IEOF$

# 출력 — 레시피 줄의 탭이 사라졌다. 이 Makefile 은 동작하지 않는다
all:$
gcc -o app main.c$

# 같은 내용을 붙임표 없이
cat <<EOF$
all:$
^Igcc -o app main.c$
EOF$

# 출력 — 탭이 남는다
all:$
^Igcc -o app main.c$
  • 붙임표 형태는 내용에 탭이 없을 때만 안전하다. 있으면 들여쓰기를 포기하고 왼쪽 끝에 붙인다
  • Makefile, TSV, 탭 정렬된 표를 내보낼 때는 붙임표를 쓰지 않는다
  • 편집기의 「탭을 스페이스로」 설정과 정면으로 충돌한다. 이 한 파일만 예외 규칙을 걸든지, 붙임표를 안 쓰든지 골라야 한다
  • 대안은 왼쪽 끝에 붙여 쓰는 것이다. 보기에는 지저분해도 편집기 설정에 의존하지 않는다
  • 또 다른 대안은 확장 가능한 형태로 내보낸 뒤 sed 's/^ *//' 로 스페이스를 지우는 것이다. 내용에 선행 공백이 없을 때만 쓴다

종료 구분자를 못 찾으면

종료 구분자 줄의 조건은 셋이다. 구분자와 개행만 있어야 하고, 그 사이에 공백이 없어야 하고, 붙임표 형태가 아니면 줄 맨 앞에서 시작해야 한다. 하나라도 어긋나면 셸은 파일 끝까지를 본문으로 삼는다.

실패는 조용히 온다

감싸는 블록이 없으면 문법 오류조차 나지 않는다. 아래는 스페이스로 들여쓴 붙임표 형태에 뒤따르는 명령을 붙인 것이다.

# 원본
cat <<-EOF$
    body line$
    EOF$
echo "THIS SHOULD PRINT"$
touch /tmp/demo/marker$

# 실행 결과
e2c.sh: line 5: warning: here-document at line 1 delimited by end-of-file (wanted `EOF')
    body line
    EOF
echo "THIS SHOULD PRINT"
touch /tmp/demo/marker
exit=0

# marker 는 만들어지지 않았다
ls: cannot access '/tmp/demo/marker': No such file or directory

이게 이 문법에서 제일 위험한 모양이다. 종료 코드는 0 이고, 경고는 표준 오류로만 나가고, 뒤따르던 명령들은 실행되는 대신 문자열로 출력된다. 로그를 표준 출력만 모으고 있었다면 성공한 실행과 구분되지 않는다. CI 에서 이 스크립트는 초록불이 뜬다.

종료 코드가 무엇을 놓치는지는 셸 종료 코드와 set -e 쪽에 있다. 이 사고는 표준 오류를 버리지 않는 것으로만 잡힌다.

어긋난 조건bash 5.2.37 의 반응종료 코드잡히는가
구분자 뒤에 공백 한 칸경고 후 파일 끝까지 삼킴0표준 오류를 봐야만
스페이스 들여쓰기 + 붙임표같음0표준 오류를 봐야만
위와 같으나 if 블록 안경고 + syntax error: unexpected end of file2잡힌다
철자·대소문자 불일치같은 경고. eof 는 EOF 가 아니다0 또는 2위와 같음
구분자 앞에 다른 글자 (xEOF)본문의 한 줄로 취급0출력이 길어져서

같은 스페이스 들여쓰기 파일을 dash 로 돌리면 메시지가 다르다. Syntax error: end of file unexpected (expecting "fi") 만 나오고, bash 가 내주던 「어느 줄의 히어독이 어떤 구분자를 기다렸는가」라는 친절한 문장은 없다. 진단이 필요할 때 bash 쪽 경고문이 훨씬 쓸모 있다.

  • 구분자 뒤의 보이지 않는 공백이 원인일 때가 많다. cat -A 로 EOF$ 인지 EOF $ 인지 본다
  • 본문에 구분자 단어가 나올 가능성이 있으면 EOF 대신 __CONFIG_END__ 같은 단어를 쓴다
  • 구분자 매칭은 대소문자를 구분한다. 본문 안의 eof, Eof, MARKERX, 들여쓴 MARKER 는 모두 종료로 취급되지 않는 것을 확인했다
  • 스크립트를 하나로 이어 붙이는 생성기를 쓴다면 여기가 가장 먼저 깨진다. 이어 붙인 뒤 bash -n 으로 문법만 검사한다

리다이렉션과 파이프의 순서

히어독은 리다이렉션의 한 종류다. 그래서 다른 리다이렉션과 같은 줄에 놓일 때 순서가 궁금해진다. 답은 순서는 상관없다이다. 둘 다 명령이 실행되기 전에 처리되고, 서로 다른 파일 서술자를 건드리기 때문이다.

# 리다이렉션이 앞
cat > out1.txt <<'EOF'
one
two
EOF

# 리다이렉션이 뒤
cat <<'EOF' > out2.txt
one
two
EOF

# 파이프로 잇기 — 본문은 파이프 왼쪽 명령의 입력이다
cat <<'EOF' | tr 'a-z' 'A-Z'
alpha
beta
EOF
out1.txt:
one
two

out2.txt:
one
two

ALPHA
BETA

세 형태 모두 의도대로 동작한다. 다만 읽기 쉬운 쪽은 정해져 있다. 리다이렉션을 앞에 두면 명령 줄만 읽고도 어디로 나가는지 알 수 있다. 뒤에 두면 히어독 본문 열 줄을 지나서야 > out.txt 가 보인다.

  • 같은 줄에 히어독 두 개도 된다. 본문은 적은 순서대로 다음 줄부터 차례로 읽힌다
  • 파이프와 섞을 때 헷갈리는 지점은 하나다. 히어독은 왼쪽 명령의 표준 입력이지 파이프 전체의 입력이 아니다
  • 파일 이름을 요구하는 명령에는 - 나 /dev/stdin 을 쓰거나 프로세스 치환 <(...) 으로 감싼다
  • 프로세스 치환은 서브셸을 만든다. 그 안에서 변수를 바꿔도 밖에 남지 않는 이유는 파이프 안 while 에서 변수가 사라지는 이유 쪽에 있다

표준 입력을 먹는다

히어독은 표준 입력을 채우는 문법이다. 그러니 표준 입력을 이미 쓰고 있던 자리와 부딪히는 것은 예정된 일이다. 가장 유명한 사고가 루프 안의 ssh 다. 표준 입력을 끝까지 읽는 프로그램을 대역으로 놓고 세 줄짜리 목록으로 재현해 봤다.

printf 'host-a\nhost-b\nhost-c\n' > hosts.txt

# ssh 처럼 표준 입력을 통째로 읽는 대역
drain() { echo "  [$1] draining stdin..."; cat > /dev/null; }

# 1. 그냥 쓰면
while read -r h; do
  echo "visiting $h"
  drain "$h"
done < hosts.txt

# 2. 안쪽 명령의 표준 입력을 막는다
while read -r h; do
  echo "visiting $h"
  drain "$h" < /dev/null
done < hosts.txt

# 3. 목록을 다른 파일 서술자로 넘긴다
while read -r h <&3; do
  echo "visiting $h"
  drain "$h"
done 3< hosts.txt
=== 1. loop body drains stdin (the ssh problem) ===
visiting host-a
  [host-a] draining stdin...

=== 2. same loop, stdin closed for the inner command ===
visiting host-a
  [host-a] draining stdin...
visiting host-b
  [host-b] draining stdin...
visiting host-c
  [host-c] draining stdin...

=== 3. same loop, list fed on fd 3 instead ===
visiting host-a
  [host-a] draining stdin...
visiting host-b
  [host-b] draining stdin...
visiting host-c
  [host-c] draining stdin...

1번은 첫 줄만 처리하고 끝난다. 오류도 없고 종료 코드도 정상이다. 서버 세 대에 배포하는 스크립트가 한 대만 건드리고 성공을 보고하는 모양이 이것이다. 실제 ssh 는 -n 옵션으로 같은 것을 하고, ffmpeg 이나 일부 패키지 관리자도 같은 습성이 있다.

흥미로운 것은 히어독을 붙이면 이 문제가 저절로 사라진다는 점이다. 히어독이 그 명령의 표준 입력을 대체해 버리므로, 안쪽 명령이 바깥 목록에 손을 댈 수 없다. 같은 루프에서 drain "$h" <<EOF ... EOF 형태로 바꾸면 세 줄이 전부 처리되는 것을 확인했다.

  • 원인은 항상 같다. 루프의 입력과 명령의 입력이 같은 서술자다
  • 해법 1: 안쪽 명령에 < /dev/null. 가장 짧고, 안쪽이 입력을 안 쓰는 것이 확실할 때 쓴다
  • 해법 2: 목록을 3< 로 넘기고 read -r h <&3. 안쪽 명령이 표준 입력을 정상적으로 쓸 수 있게 남겨 둔다
  • 해법 3: 안쪽 명령에 히어독을 붙인다. 어차피 원격에 스크립트를 넘길 참이면 이게 자연스럽다
  • 해법 4: 애초에 while read 대신 배열을 미리 채워 for 로 돈다. 목록이 크지 않으면 이게 제일 안전하다

히어스트링은 한 줄일 때

<<< 는 히어독의 한 줄짜리 친척이다. bash 확장이고 POSIX 규격에는 없다. dash 에서 돌리면 Syntax error: redirection unexpected 로 즉사한다. 이식성이 필요한 스크립트라면 여기서 갈린다.

# 히어스트링은 끝에 개행을 붙인다
printf 'abc' | wc -c     # => 3
wc -c <<< 'abc'          # => 4

# 인용을 안 해도 단어로 쪼개지지 않는다
v='a b'
cat <<< $v      # => a b
cat <<< "$v"    # => a b
cat <<< '$v'    # => $v

# read 와 붙이면 서브셸이 생기지 않는다
read -r first rest <<< "alpha beta gamma"
echo "first=$first rest=$rest"      # => first=alpha rest=beta gamma

# 파이프로 하면 변수가 남지 않는다
echo "alpha beta gamma" | read -r f2 r2
echo "f2=[$f2] r2=[$r2]"            # => f2=[] r2=[]

세 번째 블록이 히어스트링을 쓰는 진짜 이유다. echo ... | read 는 read 가 서브셸에서 돌아 변수가 사라지지만, 히어스트링은 리다이렉션이라 서브셸을 만들지 않는다. 같은 이유로 while ... done <<< "$var" 형태도 안전하다.

  • 끝에 개행 한 개가 붙는다. 바이트 수를 세는 곳에서는 이 한 글자가 결과를 바꾼다
  • 변수가 비어 있어도 개행 한 줄은 들어간다. wc -l <<< "$empty" 는 0 이 아니라 1 이다
  • 따옴표 없이 써도 단어 분리가 일어나지 않는다. 그래도 "$v" 로 쓰는 편이 낫다. 읽는 사람이 헷갈린다
  • 여러 줄짜리 값을 넣어도 된다. $'one\ntwo\nthree' 를 넣으면 wc -l 이 3 을 돌려준다
  • 본문에서 확장을 끄고 싶으면 값 쪽을 홑따옴표로 감싼다. 구분자 따옴표 규칙과는 다른 이야기다

원격으로 넘길 때 어디서 확장되는가

ssh host bash -s <<EOF 형태에서 사고가 나는 이유는 하나다. 본문이 두 번 해석된다. 한 번은 로컬 셸이 히어독을 만들 때, 또 한 번은 원격 셸이 그 텍스트를 스크립트로 읽을 때. 어느 쪽에서 확장할지를 정하는 것이 이 자리의 전부다. 원격 접속 없이도 bash -c 를 두 번째 셸로 세우면 같은 구조가 나온다.

export TAG=local-tag

# A: 따옴표 없는 구분자 — 전부 이쪽에서 확장된다
bash -c 'export TAG=remote-tag; exec bash -s' <<EOF
echo "TAG seen = \$TAG"
echo "TAG baked = $TAG"
echo "PID of the second shell = \$\$"
EOF

# B: 따옴표 있는 구분자 — 전부 저쪽에서 확장된다
bash -c 'export TAG=remote-tag; exec bash -s' <<'EOF'
echo "TAG seen = $TAG"
echo "PID of the second shell = $$"
EOF

# C: 필요한 값만 인자로 넘긴다
bash -c 'export TAG=remote-tag; exec bash -s -- "$1"' _ "$TAG" <<'EOF'
echo "argument from the local side = $1"
echo "value from the remote side  = $TAG"
EOF
=== A ===
TAG seen = remote-tag
TAG baked = local-tag
PID of the second shell = 1780

=== B ===
TAG seen = remote-tag
PID of the second shell = 1781

=== C ===
argument from the local side = local-tag
value from the remote side  = remote-tag

(참고: 이 실험을 돌린 바깥 셸의 PID 는 1777 이었다)

A 의 두 줄이 이 절의 요약이다. \$TAG 는 원격 값 remote-tag 를 내주고, $TAG 는 로컬 값 local-tag 가 텍스트에 박혀서 건너갔다. C 는 그 둘을 뒤섞지 않는 방법이다. 본문은 통째로 확장을 끄고, 로컬 값은 인자 자리로만 들어온다. 확장되는 자리가 눈에 보이는 개수로 줄어든다.

sudo 는 결이 조금 다르다. 여기서 흔한 실수는 sudo cat > /etc/some.conf <<'EOF' 다. 리다이렉션은 sudo 가 아니라 그것을 호출한 셸이 처리한다. 권한이 없는 쪽이 파일을 여는 것이다. 같은 구조를 권한 대신 없는 디렉터리로 확인해 봤다.

cat > /nonexistent_dir/x.conf <<'EOF'
payload
EOF
# => e12.sh: line 3: /nonexistent_dir/x.conf: No such file or directory

tee /nonexistent_dir/x.conf <<'EOF'
payload
EOF
# => tee: /nonexistent_dir/x.conf: No such file or directory

오류를 내는 주체가 다르다. 앞쪽은 스크립트 이름과 줄 번호가 붙은 셸의 메시지고, 뒤쪽은 tee 자신의 메시지다. 그래서 관리자 권한으로 파일을 쓸 때는 sudo tee 를 쓴다. 파일을 여는 주체가 sudo 아래로 들어간다.

  • ssh 에 히어독을 붙일 때는 기본을 따옴표 있는 구분자로 잡는다. 새는 쪽이 아니라 막는 쪽이 기본이어야 한다
  • 로컬 값이 필요하면 bash -s -- "$v1" "$v2" 로 넘기고 원격에서 $1, $2 로 받는다
  • 원격에서 실행할 스크립트가 길어지면 히어독 대신 파일을 scp 로 보내고 실행하는 편이 낫다. 15절에서 다시 본다
  • 관리자 권한 쓰기는 sudo tee file > /dev/null 또는 sudo sh -c 'cat > file'. 앞쪽이 읽기 쉽다
  • 어느 쪽이든 두 번 해석된다는 사실을 잊지 않는다. 원격 로그에 실제로 실행된 줄을 남겨 두면 진단이 빨라진다

파일을 만드는 세 가지 관용구

히어독의 절반 이상은 파일을 만드는 데 쓰인다. 결과가 같은 세 형태를 같은 본문으로 돌려 해시를 맞춰 봤다.

# 1. 가장 흔한 형태
cat > a.conf <<'EOF'
key = $VALUE
EOF

# 2. 권한이 필요하거나 화면에도 보고 싶을 때
tee b.conf > /dev/null <<'EOF'
key = $VALUE
EOF

# 3. 외부 명령 없이 셸만으로
while IFS= read -r line; do printf '%s\n' "$line"; done <<'EOF' > c.conf
key = $VALUE
EOF
254b9d772669ad5fc3e7724fe7fe623e *a.conf
254b9d772669ad5fc3e7724fe7fe623e *b.conf
254b9d772669ad5fc3e7724fe7fe623e *c.conf

세 파일이 바이트 단위로 같다. 그러면 무엇을 고르는가. cat 형태가 압도적으로 읽기 쉽고, 프로세스 하나를 아끼자고 3번을 쓰는 것은 대개 손해다. 다만 cat 도 tee 도 외부 명령이라, 최소 환경의 초기 부팅 스크립트처럼 /bin 이 아직 없는 자리에서는 3번이 유일한 선택이 된다.

  • 기본은 cat > file <<'EOF'. 따옴표를 습관적으로 붙이고, 확장이 필요할 때만 뗀다
  • 권한이 필요하면 sudo tee. 표준 출력이 화면으로 새므로 > /dev/null 을 붙인다
  • 덧붙이기는 cat >> file 또는 tee -a. 두 번 돌아도 안전한지는 별개 문제다. 두 번 돌려도 안전한 스크립트 쪽에서 다뤘다
  • 파일을 만들기 전에 기존 파일을 백업하려면 히어독 앞에 조건을 붙인다. 히어독은 리다이렉션이므로 if 안에서도 그대로 쓴다
  • 생성한 파일의 권한이 중요하면 install -m 0644 /dev/stdin file <<'EOF' 형태도 쓸 만하다. 만들면서 권한을 함께 정한다

변수에 담으면 끝이 잘린다

히어독을 변수에 담는 관용구는 var=$(cat <<'EOF' ... EOF ) 다. 여기에는 조용한 손실이 있다. 명령 치환이 결과 끝의 개행을 전부 지운다. 19 바이트짜리 본문으로 네 가지 방법을 재 봤다.

# 원본은 19 바이트: "line one\nline two\n\n"

v=$(cat <<'EOF'
line one
line two

EOF
)

read -r -d '' v2 <<'EOF'
line one
line two

EOF

IFS= read -r -d '' v3 <<'EOF'
line one
line two

EOF

mapfile -t arr <<'EOF'
line one
line two

EOF
=== the source text is 19 bytes ===
19

$(cat <<EOF)        exit=0 bytes=17
read -r -d ''       exit=1 bytes=17
IFS= read -r -d ''  exit=1 bytes=19
mapfile -t          elements=3

네 줄에서 읽을 것

첫 줄은 예상대로다. 개행 두 개가 사라져 17 바이트다. 두 번째 줄이 함정이다. read -r -d '' 는 개행을 살리려고 쓰는 형태인데, IFS 를 비워 두지 않으면 결국 17 바이트가 된다. read 가 마지막 필드의 앞뒤 IFS 공백을 잘라 내기 때문이고, 기본 IFS 에는 개행이 들어 있다. 세 번째 줄만 19 바이트를 지켰다.

그리고 두 번째와 세 번째 모두 종료 코드가 1 이다. 구분자를 널 문자로 잡았는데 입력에 널이 없으니 read 는 「구분자를 못 만나고 입력이 끝났다」를 보고한다. 값은 정상적으로 들어갔는데도 그렇다. 즉시 종료 설정이 켜져 있으면 여기서 스크립트가 죽는다.

( set -e; read -r -d '' z <<'EOF'
payload
EOF
echo "NEVER REACHED" )
# => subshell exit code = 1   (echo 는 실행되지 않았다)

( set -e; read -r -d '' z <<'EOF' || true
payload
EOF
echo "reached, z=[$z]" )
# => reached, z=[payload]
# => subshell exit code = 0
담는 방법끝의 개행종료 코드서브셸언제 쓰는가
$(cat <<'EOF')잘린다 (19→17)0생긴다끝 개행이 상관없는 대부분의 경우
read -r -d ''잘린다 (19→17)1안 생긴다쓰지 않는 편이 낫다. 중간 형태다
IFS= read -r -d ''보존 (19)1안 생긴다바이트 단위로 정확해야 할 때
mapfile -t배열 3원소0안 생긴다줄 단위로 다룰 때. bash 4 이상
  • read 는 앞쪽 공백도 잘라 낸다. read -r a b <<< " x y " 는 a=[x] b=[y] 를 준다
  • 같은 입력에 IFS= read -r c 를 쓰면 c=[ x y ] 로 공백이 살아 있다. 습관적으로 IFS= 를 붙일 이유다
  • -r 을 빼면 백슬래시가 이스케이프로 먹힌다. 히어독에서 백슬래시를 살려 왔는데 read 에서 잃는 일이 생긴다
  • 종료 코드 1 은 || true 로 막는다. 대안으로 read ... ; : 도 되지만 의도가 덜 보인다
  • mapfile 은 bash 4 이상이고 dash 에는 없다. 이식성이 필요하면 후보에서 뺀다

함수 안에서, 한 줄에 둘

히어독 본문이 시작되는 위치는 연산자가 적힌 줄의 다음 줄이지 연산자 바로 뒤가 아니다. 이 규칙이 있어서 한 줄에 히어독을 두 개 쓸 수 있고, 히어독 뒤에 다른 명령을 이어 붙일 수도 있다.

# 함수 안에서 — 지역 변수도 정상적으로 확장된다
emit() {
  local target=$1
  cat <<EOF
[unit]
target=$target
EOF
}
emit alpha

# if 안에서, case 안에서도 그대로
if [ -n "$HOME" ]; then
  cat <<'EOF'
inside an if
EOF
fi

# 한 줄에 둘 — 본문은 적은 순서대로 다음 줄부터 읽힌다
diff <(cat <<'A'
same
left
A
) <(cat <<'B'
same
right
B
)

# 히어독 뒤에 다른 명령을 잇기
cat <<'EOF' ; echo "<- this ran after the heredoc"
body of the heredoc
EOF
[unit]
target=alpha
---
inside an if
---
2c2
< left
---
> right
diff exit=1
---
body of the heredoc
<- this ran after the heredoc

마지막 블록이 규칙을 가장 잘 보여 준다. ; echo ... 가 히어독 연산자와 같은 줄에 있는데도 본문에 삼켜지지 않았고, 본문이 끝난 뒤에 실행됐다. 셸은 그 줄을 끝까지 읽어서 명령으로 파싱한 다음, 다음 줄부터 본문을 수집한다.

  • 함수 안에서도 들여쓰기 문제는 똑같다. 종료 구분자를 함수 본문에 맞춰 들여쓰려면 붙임표 형태 + 탭이어야 한다
  • case 안에서 쓸 때는 ;; 가 종료 구분자 다음 줄에 와야 한다. 같은 줄에 붙이면 구분자가 아니게 된다
  • 파이프라인의 각 단계마다 히어독을 따로 붙일 수 있다. 다만 그 지점에서 읽는 사람이 길을 잃는다
  • 본문 안에 구분자와 같은 단어가 줄 맨 앞이 아닌 곳에 있으면 문제없다. xEOF 나 들여쓴 EOF 는 그냥 본문이다

본문은 파이프인가 임시 파일인가

히어독 본문이 실제로 어디에 담겨 명령에 전달되는지는 규격이 정하지 않는다. 구현이 알아서 한다. bash 5.2.37 에서 실행 중인 명령의 표준 입력을 들여다보면 크기에 따라 갈리는 것이 보인다.

# 작은 본문
ls -l /proc/self/fd/0 <<'EOF'
payload
EOF
# => /proc/self/fd/0 -> pipe:[8589943248]

# 큰 본문 (약 350KB)
# => /proc/self/fd/0 -> /tmp/sh-thd.6MTpiD (deleted)

# 경계를 좁혀 본 결과
body=65000    pipe:[4294982180]
body=66000    /tmp/sh-thd.ib1lXH (deleted)
body=70000    /tmp/sh-thd.NCKE8B (deleted)

작은 본문은 파이프로 건네지고, 파이프 용량을 넘어서면 이름이 지워진 임시 파일로 바뀐다. 경계는 6만 5천 바이트와 6만 6천 바이트 사이였다. 리눅스의 기본 파이프 버퍼 크기가 64KiB 이니 값이 맞는다. 오래된 bash 는 크기와 무관하게 임시 파일을 썼고, 파이프를 쓰는 동작은 비교적 최근에 들어온 것이다.

실무에서 걸리는 자리는 둘이다. 표준 입력을 되감아 두 번 읽는 프로그램은 파이프에서 실패한다. 임시 디렉터리가 가득 차거나 읽기 전용이어도 큰 히어독이 실패한다.

경계 근처에서 이상한 것을 하나 봤다. 본문이 정확히 65,536 바이트와 65,537 바이트일 때 이 빌드의 bash 는 영영 멈춘다. 8초 제한을 걸어 두 번 재현했다. 그보다 크면 임시 파일로 넘어가서 정상 동작한다. 아주 좁은 구간이고 MSYS 쪽 파이프 용량 판정과 관련이 있어 보이지만, 다른 환경에서 같은지는 확인하지 못했다.
  • 큰 데이터를 넘길 때는 히어독보다 파일을 만들어서 경로로 넘기는 편이 예측 가능하다
  • 표준 입력을 다시 읽어야 하는 도구라면 /dev/stdin 대신 실제 파일을 만들어 준다
  • 임시 파일 이름이 (deleted) 로 보이는 것은 정상이다. 만들자마자 지워서 다른 프로세스가 볼 수 없게 한 것이다
  • 같은 이유로 히어독 본문은 ps 나 명령행 인자로 노출되지 않는다. 비밀값을 넘길 때 인자보다 나은 이유다
  • 다만 임시 파일 경로가 잠깐이라도 존재하므로, 진짜 비밀값은 파이프 구간 안에 들어가는 크기로 유지하는 편이 낫다

엄격 모드와 부딪히는 자리

스크립트 맨 위에 set -euo pipefail 을 거는 습관이 있다면 히어독과 만나는 지점을 알아 둘 필요가 있다. 두 가지가 있다.

# 1. set -u 와 따옴표 없는 히어독
( set -u; cat <<EOF
value = $DEFINITELY_NOT_SET
EOF
)
# => e12.sh: line 14: DEFINITELY_NOT_SET: unbound variable
# => unquoted exit=1

( set -u; cat <<'EOF'
value = $DEFINITELY_NOT_SET
EOF
)
# => value = $DEFINITELY_NOT_SET
# => quoted exit=0

# 2. 짝이 안 맞는 백틱
cat <<EOF
a `oops
EOF
# => bash: line 1: bad substitution: no closing "`" in `oops
# => exit=1

cat <<'EOF'
a `oops
EOF
# => a `oops
# => exit=0

첫 번째는 오히려 반가운 실패다. 원격에 넘기려던 변수 이름을 오타 냈을 때 조용히 빈 문자열이 박히는 대신 여기서 멈춘다. 두 번째는 성가시다. 본문에 명령 예시나 마크다운을 넣으면 짝 없는 백틱 하나로 스크립트가 죽는다. 둘 다 구분자에 따옴표를 씌우면 사라진다.

  • 본문에 코드 예시, 정규식, 마크다운, 윈도우 경로가 들어가면 거의 항상 따옴표 있는 구분자가 정답이다
  • set -e 와 부딪히는 것은 11절의 read -r -d '' 다. || true 를 잊지 않는다
  • set -u 아래에서 따옴표 없는 히어독을 쓸 거라면 ${VAR:-기본값} 형태로 방어한다
  • 진단할 때 bash -n script.sh 로 문법만 검사하면 종료 구분자 문제 상당수가 실행 전에 잡힌다
  • bash -x 는 히어독 본문을 추적에 찍어 주지 않는다. 본문 확인은 cat 으로 한 번 내보내 보는 편이 빠르다

히어독을 쓰지 말아야 할 때

히어독이 편해지면 전부 히어독으로 하고 싶어진다. 그런데 아래 경우는 다른 도구가 낫다. 기준은 단순하다. 본문이 스크립트보다 오래 사는가.

  • 본문이 30줄을 넘어가면 별도 파일로 둔다. 스크립트를 읽을 때 로직이 본문에 파묻힌다. 문법 강조도 안 되고, 그 파일만 따로 검사할 수도 없다
  • 치환할 자리가 다섯 곳을 넘어가면 템플릿 도구를 쓴다. envsubst 는 기본 환경에 있는 경우가 많고, 치환 대상을 명시적으로 제한할 수도 있다
  • 같은 본문을 여러 스크립트가 쓴다면 파일로 뺀다. 히어독을 복사해 두면 두 벌이 서서히 갈라진다
  • JSON 이나 YAML 을 만든다면 값에 특수문자가 들어올 가능성을 먼저 본다. 사용자 입력이 섞이는 순간 히어독은 이스케이프 책임을 지지 않는다. jq -n 이나 yq 가 맞다
  • 원격에서 실행할 스크립트가 길면 파일을 보내고 실행한다. 두 번 해석되는 구간이 사라지고, 실패했을 때 원격에 파일이 남아 재현할 수 있다
  • 한 줄이면 히어독을 쓰지 않는다. printf '%s\n' '...' 나 히어스트링이 짧다
  • 반대로 설정 파일 열 줄 안팎, 원격에 넘기는 짧은 스크립트, 인용부호가 많은 텍스트는 히어독의 정확한 자리다

확인하지 못한 것

  • 이 글의 출력은 전부 MSYS 기반 bash 5.2.37 에서 나온 것이다. glibc 리눅스의 같은 버전에서 전부 동일한지는 확인하지 못했다. 특히 파이프와 임시 파일이 갈리는 경계값, 그리고 65,536 바이트 부근에서 멈추는 현상은 다른 환경에서 재현되는지 알 수 없다
  • CRLF 로 저장한 스크립트를 이 빌드에서 돌렸을 때 히어독이 정상 동작했고 출력에 캐리지 리턴이 남지 않았다. MSYS 의 파일 읽기 방식일 가능성이 크며, glibc 리눅스에서 같은 결과가 나올 것이라고 보지 않는다
  • 비교 대상으로는 같은 상자의 dash 만 썼다. zsh, ksh, BusyBox ash 는 설치돼 있지 않아 돌려 보지 못했다
  • dash 는 패키지 정보를 조회할 수 없어 정확한 버전 번호를 적지 못했다
  • sudo 관련 서술은 권한 없는 디렉터리 대신 존재하지 않는 디렉터리로 확인한 것이다. 리다이렉션을 누가 처리하는가라는 구조는 같지만, 실제 권한 거부 상황의 메시지는 확인하지 못했다
  • 원격 실행은 실제 ssh 가 아니라 bash -c 로 세운 두 번째 셸로 재현했다. 두 번 해석된다는 구조는 동일하지만, ssh 가 인자를 합쳐 원격 셸에 넘기는 방식에서 오는 추가적인 인용 문제는 다루지 않았다
