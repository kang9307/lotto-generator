The Weights Arrived and the Rest Did Not - What an Open Driving Model Actually Released

Separating what is in the repository from what is not, and asking what sits between a benchmark waypoint and a car on a road

2026-09-10 Tech & IT

The weights of a driving model have been posted to a public repository. Three-dimensional perception, scene question answering and path generation are bundled inside a single model, and the licence is Apache 2.0. Coverage summarised the release in a sentence about a model that understands road situations and plans a driving path.

That sentence is not wrong. What it does not tell you is how far the release actually extends. Between the fact that weights exist and the claim that a car can be driven with them, several layers are stacked. Whether each of those layers is present in the repository is what this article is about.

There is no point repeating a model introduction. The axis here is a single question. What did an open-weight driving model actually release, and what remains unreleased? Writing down what is absent is worth more here than counting what is present.

This is general information and not legal advice. Repository values reflect a reading on 10 September 2026 and may already differ, since the repository is under active development. Statutory numbering and wording are taken from the article-level text served by the Korean national law information service. No product or maker is evaluated here, and no judgement is offered on whether any particular use is lawful or unlawful; that judgement belongs to the competent ministry and the courts. Methods for putting any of this on a public road are outside the scope of this article.

The trigger - how far the word released reaches

What was released is a repository named Qwen-Drive-1.0. The subtitle it gives itself describes an initial step towards a vision-language foundation model for autonomous driving. The phrase initial step sitting at the top of the document is itself informative. It does not say finished driving software, and it does not claim a product.

The base is Qwen3.5-4B, a four-billion-class vision-language model, with a bird-eye-view perception head and a planning expert attached on top. Four checkpoints are distributed. The vision-language body is 9.1 GB, the two planning expert variants are 2.1 GB each, and the perception head is 0.5 GB. The recommended hardware is a single graphics card with 24 GB or more of memory.

That much is what usually travels. But open weights is a phrase that has already, on several occasions, exposed the gap between receiving weights and receiving source. With a driving model the gap widens further. For a language model, weights plus inference code let you run the thing end to end. Moving a car is not closed by a model alone.

What planning a path actually emits

Start by pinning down the output. The specification written in the model documentation reads as follows.

ItemValue stated in the documentation
Output formA sequence of waypoints. Each point carries x, y and a heading
Count and horizonFifty points filling a five-second window at 10 Hz
Coordinate frameEgo-centric. The x axis points forward, the y axis to the left
InputsCamera images from the current and preceding frames, plus the ego vehicle history of pose, speed and acceleration
Generation methodFlow matching, sampled over ten Euler steps
Control signalsNone. No steering angle and no acceleration or braking command appears in the output

The two layers the word planning covers

Planning points at two layers at once. One is drawing where to go. The other is turning the wheels so that the drawing happens. This model does the first. It emits the ego trajectory for the next five seconds as coordinates. The layer that takes those coordinates and converts them into steering and acceleration is not in the repository.

If that distinction sounds academic, put it next to the places where the model was scored. All three planning benchmarks are either simulators or already-recorded driving data. Nowhere in the documentation is there a description of an evaluation on a real vehicle or a public road. In other words, the path planning of this model is an output on a research benchmark, and no statement in the repository documentation connects it to real-vehicle control. That is precisely where the summarised sentence and the actual scope of the repository part company.

The four rows where absent weighs most

Of the fifteen rows, four are the ones that decide practice: training data, safety evaluation procedure, on-road validation record and failure case list. They share a property. None of them can be filled in merely by running the model. The other absent items can be built with enough time and hardware. These four can only come from the party that made the thing.

The doors that missing training code closes

The absence of training code and training data is usually discussed as a reproducibility issue. For a driving model it closes three narrower and more practical doors.

  • Domain transfer is blocked — road signage, pavement markings and lane rules differ from country to country. Without training code there is no official route for reflecting those differences inside the model. What remains is working around it outside the model, adjusting inputs or filtering outputs, and each workaround creates its own risk at another layer
  • Out-of-distribution behaviour cannot be anticipated — if you do not know which scenes were seen and how often, you have no thread to follow when the model answers strangely on something new. A benchmark score is a result inside a sample and vouches for nothing outside it
  • The provenance of the weights cannot be interrogated — questions about where the data came from, how rights were cleared and how footage containing personal information was handled do not close on the documentation. In adoption reviews these questions often arrive before any performance item

These three overlap with the general question of what to check before adopting an open-weight model, but the weight of the consequence differs. When a text model is wrong you fix the text. When a driving model is wrong, the thing to be fixed is not text.

The real difference between open loop and pseudo closed loop

In an open-loop evaluation the decision of the model does not change the next frame. Recorded driving footage is fed in order, and the deviation between the drawn path and the actual drive is measured. If the model says it will turn left, the next frame still shows the scenery from the original right-hand turn. As a result, the process by which small errors accumulate and alter the situation never enters this evaluation.

A pseudo closed loop goes one step further. The simulator takes the decision of the model, advances the ego state accordingly and scores the outcome. Even so, the evaluation document itself prefixes the word pseudo. That signals a different layer from a full simulation in which surrounding vehicles and pedestrians react to what the ego vehicle decides.

Reproduction conditions are part of the figure too. The evaluation document says to fix the seed, says that changing frame resolution changes the result and says that each benchmark needs its own temporal resolution conversion. On top of that, map data and official implementations are not in the repository and must be assembled by the user. Receiving the same weights guarantees the same number only after the conditions have been matched.

Where the number 90.7 actually stands

It is worth setting down what a single number does and does not support. Here is where 90.7 stands.

What can be said is roughly this. Under the stated conditions of the stated benchmark, the planning expert refined with reinforcement learning produced that score, according to the repository. It is a value usable for comparison against other methods on the same benchmark. It is also usable in a research discussion about whether an architectural choice translates into a result.

What cannot be said is a longer list. The value does not connect directly to safety on a road. Even where a scoring item carries the word safety, that is a metric defined inside a simulator, not the validation demanded of something operating on a public road. A high number and permission to use a function on a road are entirely different sentences, and the criterion for the second is set by regulation rather than by a benchmark.

There is also something in the mere fact that two planning experts are distributed side by side. As the names indicate, one belongs to the supervised family and one to the reinforcement-learning family, and the documentation says the two are interchangeable. That the choice is left open to the user means the consequences of the choice also sit on the user side.

In between, part one - sensors and the coordinate frame

What the model receives is camera images. More important than the images themselves is which camera they came from. Because the output is waypoints in an ego-centric frame, where the camera is mounted on the body and at what angle is what gives those coordinates their meaning.

Two cameras can photograph the same scene, and if their positions and angles differ the same pixel points at a different place in the world. The bird-eye-view perception head transforms images from several viewpoints onto a single plane, and what enters that transform is exactly the calibration values. That is why a calibration file accompanies every scene in the demo samples.

Yet no requirement stating what must be aligned, and how, for a different vehicle and a different camera layout appears in the documentation. The model documentation lists the kinds of input but not the conditions of calibration. This is not a defect of the model; it is a question of scope. A research artefact holds on the sensor configuration that its dataset fixed, and a product has to hold again every time that configuration changes.

In between, part two - does an answer arrive inside the cycle

In driving software, time sits beside accuracy as a requirement. If a result does not arrive inside a fixed cycle, that result is an answer about a moment already past. A car travelling at 60 km/h covers roughly 16.7 metres per second. A slip of 100 milliseconds means a judgement made 1.6 metres back.

The only time-related statement in the repository documentation is a count of computation steps. Sampling runs over ten Euler steps, and how long that takes is not written down. The recommended 24 GB is a memory requirement, not a timing requirement.

Three things follow from this gap in practice.

  • Accuracy does not substitute for it — a benchmark score comes out the same whether the computation is bounded in time or not. Whether the cycle is met is a separate axis, and the published numbers do not carry that axis
  • It must be measured again on each set of hardware — latency varies with the device, the deployment method and the batch size. A number measured on somebody else machine is a reference point, not evidence that a requirement is met
  • The worst case matters more than the average — even when average latency fits inside the cycle, a long tail produces frames that miss it. Requirements of this kind are usually written as ceilings rather than averages

In between, part three - where it goes when it is wrong

A model always outputs something. If the input is odd, if the scene falls outside the training distribution, if one camera is occluded, fifty waypoints still come out. That an output appears and that the output is usable are two different events.

In a product this place is filled by transition to a safe state on fault. Something has to detect the fault, and once detected, something has to take over. That layer is not inside the model. What the repository contains is the model and the code that runs it; monitoring, arbitration and degraded operation sit outside it.

The layers that have to live outside the model

Four, in summary. A layer that checks whether the input is sane, a layer that checks whether the output is physically plausible, a fallback behaviour to move to when an anomaly is caught, and a channel through which a human can cut in at any moment. None of them is solved by making the model larger. The discussion of what to watch when raising a level of autonomy repeats here with the same structure.

In between, part four - validation is not substituted by accuracy

Accuracy is a statistic and validation is a procedure. The two are different kinds of sentence. Accuracy speaks about a sample; validation speaks about what was done regarding everything outside the sample.

The distinction is unusually sharp in vehicle software because changing one thing means demonstrating everything again. Swap a model checkpoint and every result established on top of it reopens. The point where the argument for swapping software inside a car runs aground is exactly this. Swapping is not the hard part. Demonstrating again after the swap is.

Published weights do not change that situation. If anything, more variants mean more combinations to demonstrate. Two of the four checkpoints being interchangeable planning experts is a convenience and simultaneously a multiplier on the number of combinations.

What Apache 2.0 settles and what it leaves open

The licence file in the repository is Apache 2.0. The model card carries the same designation, and neither carries an out-of-scope use section or a safety notice.

Splitting what Apache 2.0 settles from what it does not, by layer, gives this.

The sentence the licence never says

One thing needs separating here. The absence of a use restriction is not permission to use it for anything. A licence is a document that handles copyright and patents at the contractual layer between distributor and user. What may be done on a road is not a subject that document addresses at all.

A recommendation printed on a model card and a clause written into a licence also differ in kind. The first is a statement by the distributor; the second is a condition. This repository carries neither. So the place where control attaches passes straight from the contractual layer to the legal layer.

The gate in Korea - what the statutes enumerate

The overall structure of the Korean regime, along with safety standards and self-certification, was covered article by article in a separate piece. Rather than repeat that here, only the two provisions that bear directly on the fact of an open-weight release are set out. Everything in this section is Korean law; requirements differ where the jurisdiction differs.

The first is Article 27 of the Motor Vehicle Management Act. The main text of paragraph 1 requires a party operating a vehicle temporarily without registration to obtain a temporary operation permit from the Minister of Land, Infrastructure and Transport or from a metropolitan or provincial governor. The proviso to that same paragraph then opens a separate door for autonomous vehicles. A party intending to operate one for testing or research purposes must meet the safe operation requirements prescribed by ministerial ordinance and obtain the permit of the Minister.

The items the proviso enumerates in connection with those safe operation requirements land exactly on the axis of this article.

  • Scope of the permit — what the permit is granted in respect of
  • Fault detection and warning devices — devices that notice a fault and announce it
  • Function disengagement device — a device that turns the autonomous function off
  • Operating area — where it may be run
  • Driver obligations — duties that remain on the human side

Two of those five are the layer identified in the earlier sections. What the statute requires is not model accuracy but a device that detects a fault and a device that disengages the function. Neither layer is inside the published repository. That a benchmark score, however high, does not substitute for these requirements can be read directly off the statutory wording.

The second is Article 7 of the Act on Promotion of and Support for Commercialization of Autonomous Vehicles. Its heading concerns designation of pilot operation districts, and its paragraphs cover the designation power and procedure of the Minister, joint application where two or more metropolitan or provincial areas are involved, alteration and revocation, and publication in the official gazette with notification. In other words, where something may be operated is settled through a separate designation procedure.

A line is drawn here. The provisions above show where jurisdiction and requirements sit; this article does not judge whether any particular use is lawful or unlawful. Which requirement a specific case falls under belongs to the competent ministry and to the courts.

Records that must exist before liability can be argued

The party that took the weights, the party that distributed them, the party that integrated them into a vehicle. Deciding in advance how liability divides among those three after an incident is not the work of this article. What can be done is to change the question. What has to exist as a record before that judgement is even possible?

The judgement itself is made afterwards by somebody else. But the material for the judgement has to be designed before the incident. A record that does not exist cannot be created later.

What the integrating party has to keep

The point is that the right-hand column mostly reads nothing. What was released is a model, and the records are kept by the system that uses the model. Publishing the weights drove the cost of obtaining a model sharply down, while the cost of designing and keeping the records did not fall at all. If anything, more versions and more combinations mean more that has to be kept.

What releasing the weights actually changed

To summarise. Placing what this release changed beside what it did not sharpens the axis.

  • Changed, the starting point for comparison — three-dimensional perception, scene question answering and path generation can now be examined together inside one model. The effect of an architectural choice can be argued from code rather than from somebody announcement
  • Changed, the checkability of the numbers — evaluation scripts came with the release, so published scores can be measured again on your own hardware. Matching the conditions remains work, but that work is possible in principle
  • Unchanged, the opacity of training — what the model learned from remains unknowable. Neither training code nor a dataset name appears in the documentation
  • Unchanged, the requirements on a road — fault detection devices, function disengagement devices and operating areas are set by statute. A model score does not stand in for those requirements

Compressed into a sentence: releasing the weights pulled the starting line of research forward without pulling the finish line of a product forward. What moved is the cost of beginning an experiment. What stayed put is the number of gates to pass before anything reaches a road.

And the repository already said as much about itself. The first words of its subtitle are initial step. Not carrying into circulation things that the documentation does not contain, as though it did, is the most basic courtesy owed to a released model.

What could not be confirmed

The items below were not written into the body as fact because their wording could not be separated out from primary sources. Reasons are given alongside.

  • The contents of the technical report — the citation entry of the repository points to a separate technical report. That document falls outside the primary sources relied on here, so no value from it was carried into the body. Descriptions of the architecture and the training procedure may well sit inside it; only what the repository documentation states was used
  • Where lidar input sits — the input description in the model documentation lists cameras and ego state, and says nothing about lidar. Yet the perception samples in the demo data include a point cloud file for every scene. How each is used in the perception module and in the planning path does not separate out from the documentation wording, so no claim was made in the body
  • The exact definition of each metric — the three planning figures were carried over as written in the repository table. How each value is computed depends on the definition set by the benchmark organisers, and that document is outside the source range of this article, so no formula was explained
  • How the two planning experts differ in training — the names and the performance table separate a supervised family from a reinforcement-learning family. The model documentation, however, says only that the two are interchangeable and does not describe the difference in procedure, so nothing beyond what the names imply was written
  • Inference latency — no published measurement of how long a single frame takes on any given device appears in the repository documentation. The recommended specification is a memory requirement and was therefore not used as evidence about timing
  • Joint development — secondary coverage describes joint development with a particular university, but that is not corroborated in the repository documentation and so was left out of the body
  • The detailed ministerial requirements — the substance of the safe operation requirements delegated by the proviso to Article 27 paragraph 1 sits in a ministerial ordinance. This article went only as far as the items the statute enumerates; the detailed criteria in the ordinance were not confirmed and were therefore not used as values
