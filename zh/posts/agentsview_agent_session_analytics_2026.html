AgentsView 发布 - 将 Claude Code、Cursor、Codex 会话汇总一处以搜索并追踪成本的本地看板

在多个 AI 编程智能体并用的时代，本地优先的开源工具如何解决会话分散与成本不透明的问题

2026-07-14 开发/基础设施

引言: 智能体多了，记忆却散了

2026 年的今天，一名开发者一天之内在多个 AI 编程智能体之间切换，已不是例外而是常态。有调查显示，59% 的开发者同时并用三种以上 AI 编程工具，65% 每天至少使用两种。让 Claude Code 做重构、让 Cursor 提供行内修改建议、再把另一项任务丢给 Codex、Gemini CLI 或 OpenCode，这样的一天已经很常见。这是各工具各有所长带来的自然分工，但代价是「昨天那个 bug 到底让哪个智能体、怎么修的」「这个月在 AI 工具上实际花了多少钱」这类问题，反而变得更难回答。

切入这个缝隙的开源项目就是 AgentsView。这款工具于 2026 年 7 月在 hada.io 被介绍，它把 Claude Code、Codex、Cursor、Gemini CLI、OpenCode 等多个 AI 编程智能体在本地留下的会话日志汇总到一处，提供对话搜索、Token/成本统计、活动分析与文件变更追踪。本文以 GitHub 仓库(kenn-io/agentsview)的公开文档为依据，梳理这款工具实际做了什么、为何在多智能体并用的时代这类工具变得必要、本地采集对隐私意味着什么、它与类似方案有何异同，以及实务用法与局限，均截至 2026 年 7 月。

1. AgentsView 是什么 - 本地优先的会话分析看板

1.1 把 40 多个智能体纳入一个索引

AgentsView 能识别的智能体清单不短。从 Claude Code、Codex、Cursor、GitHub Copilot CLI、Windsurf、Zed 这类主流工具，到 Devin CLI、OpenCode、Gemini CLI、DeepSeek TUI、Qwen Code 这类专门工具，再到 Aider(按仓库自愿开启)、Forge、gptme、OpenHands、Kiro、Mistral Vibe 这类相对小众的工具，共覆盖 40 多种。每个智能体都有自己的会话存储路径(例如 Claude Code 使用 ~/.claude/projects/)，AgentsView 分别解析这些路径，并合并进同一个本地 SQLite 数据库。

1.2 搜索、成本、活动、变更 — 四大核心功能

核心功能可以概括为四点。第一，统一搜索: 基于 FTS5 的全文搜索可一次性查找跨智能体的对话内容，若选配嵌入端点，还能做语义搜索。第二，Token 与成本汇总: 参照 LiteLLM 的价格数据计算按会话、按模型的 Token 用量与成本，支持离线回退，还能计入提示词缓存对成本的影响，官方宣称查询速度比每次重新解析文件快 100 倍。第三，活动分析: 自动把会话归类为自动化、快速、标准、深度、马拉松等类型，并将会话时长、上下文占用、工具调用分布可视化。第四，文件变更追踪: 以信息流形式展示智能体近期修改过的文件。结果可导出为 HTML 或 GitHub Gist。

1.3 架构 - Go 单一二进制与可选的团队共享

后端用 Go 编写(约占代码库 83.8%)，前端为 Svelte 5 加 TypeScript，还提供以 Tauri 打包的桌面应用。默认存储是可写的 SQLite(带 FTS5 索引)；若想与团队共享，可以选择把 SQLite 数据只读推送到 PostgreSQL，面向更大规模分析时还可镜像到 DuckDB。安装方式包括 curl -fsSL https://agentsview.io/install.sh | bash、Homebrew cask，或 Docker 镜像(ghcr.io/kenn-io/agentsview)，可用 agentsview serve 前台运行，也可用守护进程模式每 15 分钟自动同步一次。Web 界面默认在 127.0.0.1:8080 打开。许可证为 MIT。

2. 问题的根源 - 多智能体并用时代的三种痛点

2.1 会话分散 - 被工具割裂的记忆

AgentsView 瞄准的第一个痛点是会话分散。据 2026 年一项调查，GitHub Copilot 仍拥有最广的用户群体(约 67.9%)，Claude Code 以微弱差距紧随其后(约 62.9%)，OpenAI Codex 也已升至 34.5% 的水平。这意味着同时使用多个工具已成为常态而非例外。问题在于，每个智能体都有自己的会话文件、格式与界面，要确认「上周这项重构到底让哪个智能体、怎么做的」，就得把工具一个个打开查看。工具越多，这份记忆就被切得越碎。

2.2 成本不透明 - 看不见的支出

第二个痛点是成本。多份报道指出，智能体在规划、执行、复核间反复循环，每一步都要重新携带上下文，因而比普通聊天机器人消耗 Token 快得多。据一项报道，使用智能体型编程工具的开发者月均支出在 400 至 1,500 美元区间，极端情况下几天内就能超过 4,000 美元。另有报道称，一家 35 人规模的初创公司并用 Claude Code、Cursor 与自研的 bug 分诊智能体，收到过一个月 8.7 万美元的账单；微软也被报道发现每位工程师每月 500 至 2,000 美元的成本，并因此削减了部分 Claude Code 许可证。各工具的看板各自独立时，这幅全貌很难被看清。

2.3 难以追溯当时对谁下达了什么指令

第三个痛点是复盘与审计。代码评审中要回答「这部分为什么这样写」,就得回溯当时给智能体下达的具体提示词，而当会话分散在各个工具里时，这种回溯本身就成了一项额外工作。放到团队层面，这也意味着缺少依据来说明「这个迭代 AI 到底贡献了多少、贡献在哪里」。会话分散、成本不透明、无法复盘这三种痛点，其实同出一源: 每个智能体各自留有一份封闭日志，却没有一个能横跨全部日志的统一视角。

3. AgentsView 带来的可见性 - 价值在哪里

3.1 可搜索的共同记忆

AgentsView 的第一重价值很简单: 把多个智能体的对话日志放在同一个搜索框之后，「当时到底让它做了什么」这件事，就从「挨个打开多个应用」变成「输入一个搜索词」。FTS5 全文搜索能精确匹配原话，可选的嵌入式搜索则能应对「那个和认证有关的重构叫什么来着」之类基于语义的查询。

3.2 把成本与 Token 放到同一屏幕

第二重价值是成本可见性。不必再去核对散落在各工具里的账单，基于 LiteLLM 的价格数据，就能在同一屏幕上看到按会话、按模型、按时间段划分的 Token 与成本。计算中考虑了提示词缓存这一点也很关键——缓存命中频繁的会话与每次都重新烧掉全部上下文的会话，实际成本结构并不相同，这比简单的 Token 数乘法更精确地逼近了这一差异。

3.3 活动分析与变更追踪 - 看见模式的眼睛

第三重价值是把活动归类，从而显现出模式。把会话分为自动化、快速、标准、深度、马拉松等类型后，就能得出诸如「这个项目大多是短小的快速会话，唯独这一个模块总是扎堆出现马拉松会话」这样的观察。最近编辑文件的信息流，让人无需打开代码评审也能一眼扫过「过去几天智能体实际动过哪里」。这种归类展现的是仅看单条会话日志很难察觉的累积使用模式，这是它与普通日志查看器不同的一层价值。

4. 本地采集对隐私意味着什么

4.1 默认本地主机，不对外发送

AgentsView 突出强调无需注册账号，会话数据默认不离开自己的设备。服务默认只绑定 127.0.0.1，不会把会话内容发送到外部。既然这是一款处理完整保留代码与提示词的日志的工具，这个默认设置就不是无关紧要的设计选择。如果它被设计成需要把会话上传到云端看板的方式，整个内部代码库经由厂商服务器传输，就会成为一个新问题。

4.2 最低限度的遥测，且可关闭

不过它并非完全静默。应用版本、操作系统、CPU 等匿名信息会在启动时以及每 24 小时发送给 PostHog。这与会话内容性质不同，但值得留意的是，可以通过 AGENTSVIEW_TELEMETRY_ENABLED=0 环境变量关闭；安全策略严格的组织更应确认这一选项。

4.3 即便团队共享，也留在自有基础设施内

即使想与团队共享，AgentsView 给出的选项也是自有基础设施内的 PostgreSQL，而非厂商云端。由于结构是从 SQLite 只读推送，「数据究竟在哪里」这个问题，在团队共享状态下答案依然是自己的服务器。这与我在自托管 AI 智能体 OpenTag 分析中讨论过的数据主权逻辑，处在同一条轴线上。

5. 与类似方案的比较 - 哪些重叠，哪些不同

5.1 智能体自带日志 - 存在，但被锁在各自工具里

最基本的替代方案，是每个智能体本就提供的自身历史记录。Claude Code 和 Cursor 都会把自己的会话留存在某处，并通过各自的界面或 CLI 供人查看。问题在于这被锁在单一工具内。一旦同时使用两三个工具，「跨全部工具搜索」这个功能本身就不存在。

5.2 类似的会话管理工具 - 有所重叠，侧重不同

AgentsView 并非唯一的尝试。Mantra 同样把 Claude Code、Cursor、Gemini CLI、Codex 的会话汇总在一起，但它的强项在于把对话日志呈现为可回放的时间线，供人逐步回看代码的演变过程，并配有 MCP 服务器与权限的集中管理，以及自动检测并一键清理 API 密钥等敏感信息的功能。coding_agent_session_search 是一款覆盖 11 个以上供应商的本地 TUI/CLI 搜索工具，Agent Sessions 同样专注于 Codex、Claude、OpenCode、Cursor、Copilot 等的会话管理。与这些工具并列，AgentsView 的定位就清晰了: 在长于搜索与回放的工具旁边，它选择了一条更偏分析的路线，把成本/Token 分析与可供团队共享的数据库后端(PostgreSQL、DuckDB)结合在一起。

5.3 LLM 可观测性平台 - 不同的产品类别

可能有人会联想到 LangSmith、Helicone、Langfuse 这类工具，但它们解决的是根本不同的问题。这些平台是生产级可观测性工具，通过 SDK 在你自己搭建的 LLM 应用中埋点，采集 API 追踪。LangSmith 按追踪数计费(免费额度每月 5,000 条追踪，之后为付费档位)，Helicone 按请求数计费，同时在网关层计算 300 多个模型的成本。相比之下，AgentsView 根本没有需要埋点的目标应用——它只是对编程智能体 CLI 本就写在本地磁盘上的会话日志文件做事后读取与索引。业界大致的评估是: 每月 LLM 支出 3 万美元以下适合 Helicone，3 万到 20 万美元区间适合 Langfuse，超过这一区间且对 LangGraph 有深度投入的组织适合 LangSmith——但这整条光谱本身，前提就是「自己搭建的产品所产生的 API 流量」。AgentsView 的出发点不同，它面对的是「自己在用的编程智能体」本身。

5.4 成本特化工具 - 专注支出管理

LMSpend、DevOS、CodeBurn 这类工具，更集中在成本这一个维度上，如团队级支出追踪、预算预警、财务导出。这类工具在支出管理上较强，但在对话搜索或会话回放上往往相对薄弱。在这一光谱中，AgentsView 更接近一个通才型工具，把搜索、成本、活动、变更追踪捆绑进同一个产品里。

工具部署方式强项备注
AgentsView本地(团队共享为可选 PostgreSQL)搜索+成本/Token+活动+变更追踪一体Go 单一二进制，MIT
Mantra本地桌面应用会话回放、MCP 中枢、自动检测敏感信息Claude Code、Cursor、Gemini CLI、Codex
coding_agent_session_search本地 TUI/CLI覆盖 11+ 供应商的统一搜索轻量、单一用途
LangSmith / Langfuse / HeliconeSaaS/自托管生产级 LLM 应用追踪可观测性需 SDK 埋点，按追踪/请求计费

6. 实务用法 - 团队成本分摊、提示词复盘、审计

6.1 团队成本分摊

若团队里不同成员使用不同的智能体，可以把 SQLite 只读同步到 PostgreSQL，把整个团队的会话与成本数据汇总进一个存储。这样就能在财务报告或迭代复盘中，拿出「这个迭代实际在 AI 工具上花了多少、集中在哪个项目、哪个模型」的依据。

6.2 提示词复盘

个人层面同样有价值。事后搜索并比较一次成功的重构与一次不那么顺利的重构，就能回溯是哪种提示词模式带来了更好的结果。这意味着面对「这里当初为什么这样写」的疑问时，能立刻给出「当时是这样吩咐的」这一确切答案——对代码评审和复盘都实实在在有帮助。

6.3 审计视角下的局限 - 它不是治理关卡

不过用于审计目的时需要划清边界。AgentsView 是对已经发生之事做事后索引的工具，而不是能事先阻止某个动作、或实时强制预算的关卡。如果需要「未经批准该请求不得执行」或「本团队一旦超出本月预算即自动切断」之类的管控，还需要另一套代理网关型工具，站在工程师与模型提供方之间，对每一次请求做日志记录、归属与管控。更准确的理解是，AgentsView 处在那一层之前——它是让「发生了什么」变得可见的可见性层。

7. 局限与注意事项

7.1 是事后分析，不是实时管控

如前所述，AgentsView 读取的是已经积累下来的日志。在成本骤增的瞬间发出告警，或直接拦截请求本身，都不是这款工具的职责。若需要实时预算强制，就必须另行设计网关或代理层。

7.2 价格数据的准确性取决于外部数据源

由于成本计算依赖 LiteLLM 的价格数据，在模型价格频繁变动的当下环境中，离线回退数据可能与实际账单存在细微出入。涉及精确金额的决策(预算审批、账单核对)仍需以厂商官方账单为准做一道核实。

7.3 本地数据库同样会积累敏感信息

只留在本地的结构能阻止对外泄露，但会话日志本身混入 API 密钥、内部 URL 或客户数据的可能性并未消失。AgentsView 似乎并未内置类似 Mantra 那种自动检测并清理敏感信息的功能，因此在与团队共享或备份已索引的数据库文件之前，最好另外加一道敏感信息核查程序。

7.4 智能体日志格式一变，就需要持续维护

支持 40 多种智能体，也意味着要持续跟上这么多种日志格式的变化。一旦某个智能体厂商改变了会话存储方式，解析器就得随之更新，而这份维护负担取决于开源社区的活跃程度。采用前最好先查看仓库近期的提交频率与议题响应速度。

8. 结论 - 今天就能做的三件事

AgentsView 指出的方向很明确: AI 编程智能体越多，凌驾于各工具性能之上的可见性层就越重要。仅仅把会话搜索、成本汇总、活动分析集中到一处，就能让「当时到底让它做了什么」的追溯变得容易得多，而本地优先的设计，意味着获得这份可见性并不需要把代码交给厂商云端。但也应说清楚: 这是一款事后分析工具，而非实时治理工具，若目的是审计或预算管控，仍需另一层工具。

8.1 本周先亲自核查一下自己的智能体使用情况

不论用 AgentsView 还是类似工具，先装上，确认过去一个月自己在哪个智能体上实际花了多少钱。想象与实际数据不符的情况并不少见。

8.2 团队应把成本分摊与审计分开设计

用 AgentsView 这类工具确保成本可见性，但若需要预算强制或请求拦截，应另行评估代理网关。把这两层混为一谈，最后留下的只会是一个没有实际管控力的看板。

8.3 先建立敏感信息核查流程

在索引会话日志之前，先核查其中是否混入 API 密钥或内部 URL 之类的敏感信息。在与团队共享或备份之前多加一道过滤，会更稳妥。相关内容可参阅自托管 AI 智能体 OpenTag 分析与本地 CLI 工具 QAMap 分析。
