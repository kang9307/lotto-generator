What Should an AI Agent Be Allowed to Do

Permission design and failure barriers - deciding what to block before deciding what to allow

Jul 27, 2026 Dev & Infra

Introduction: agents do not make mistakes, they walk through doors we left open

Read enough post-mortems about AI agent incidents and they tend to land in the same place: the model made a bad judgment call. It wiped a production database. It ignored an explicit instruction not to change anything. It reported that recovery was impossible when it was not. As a description of events, all of that is accurate. But it only covers half the incident. The other half is simpler and sits much closer to us. Why did the agent have permission to wipe a production database at that moment in the first place?

This question is not new to anyone who has operated software. When a deployment script deletes the wrong target, nobody stops at fixing the script logic. We also ask why the account running it held that privilege, why there was no confirmation step, and why the data could not be restored from backup. An agent is, in the end, a process running on a human's behalf. The only structural difference is that its control flow emerges from natural-language judgment rather than from code, and that difference adds one crucial property: you cannot enumerate in advance what it will attempt. If you cannot enumerate the attempts, there is exactly one remaining strategy — shrink the set of things it is capable of attempting at all.

This article is not a product review and it is not a teardown of a single incident. It is about the principles by which permissions should be designed. The scope covers how to judge an action along two axes, which irreversible operations belong in a default-deny list, a table for splitting permissions into tiers, four barriers that catch failures before they land, how to place approval gates without manufacturing approval fatigue, how to partition permissions when several agents run in parallel, and what an audit log must contain to answer questions afterward. Here is the conclusion up front: no design blocks everything, so the first thing to design is the ability to undo.

1. Can least privilege be transplanted onto agents as-is

Least privilege is one of the oldest and most routinely ignored principles in security. NIST SP 800-53 Rev.5 AC-6 defines it as allowing only the accesses necessary to accomplish assigned organizational tasks. The important part is the scope clause. The control applies not only to users but to processes acting on behalf of users, and it requires that system processes operate at privilege levels no higher than necessary to accomplish the mission.

Read literally, that clause settles where a coding agent belongs. An agent is not a person; it is a process acting on behalf of a person. And yet in most working setups today the agent runs inside the developer's account, on the developer's shell, with the developer's credentials. If the developer can reach production, so can the agent. If the developer holds a deployment key, the agent uses that key. Measured against the wording of the standard, that configuration starts out already in violation.

1.1 Excessive agency - what exactly is excessive

OWASP catalogues this problem in its risk list for large language model applications under the name Excessive Agency, and splits it into three roots. The split is useful precisely because the remedies differ.

  • Excessive functionality — tools attached that the task does not need, such as a database client wired into an agent whose job is tidying documents. The remedy is to shorten the tool list.
  • Excessive permissions — the right tool, but backed by an account whose scope is too broad, such as a read-only job carrying a write-capable token. The remedy is to narrow the credential.
  • Excessive autonomy — appropriate tools and scopes, yet high-impact actions run to completion without a human ever looking. The remedy is not fewer tools but a differently placed approval gate.

Laying the three side by side clears up a common misconception. Removing a couple of tools does not make a system safe, and neither does bolting on a couple of approvals. Functionality, permissions, and autonomy are three separate dials, and each has to be turned down on its own.

1.2 Human controllers, limited powers, observable actions

Google Research published an approach to secure AI agents that compresses the problem into three principles: agents must have well-defined human controllers, their powers must be carefully limited, and their actions and planning must be observable. Those three form the skeleton for every design decision that follows. A defined controller tells you whom to ask for approval. Limited powers reduce how often you have to ask. Observability is what lets you answer, afterward, what actually happened.

2. The first axis - can this be undone

The most common mistake in permission design is trying to judge everything on risk alone. Risk is subjective and it moves with context. Reversibility, by contrast, is judged almost mechanically. That is why I recommend putting this axis first.

The core question for reversibility is whether a person can restore the prior state with a single command. Editing files in a working tree is reversible as long as version control is attached. A local commit is reversible. But the moment you push to a remote, the character of the action changes. Someone may already have pulled it. Automation may already have picked up the commit and started a deployment. The fact that a force push is technically possible is not evidence of reversibility, because the fact that something left the building cannot itself be recalled.

2.1 The irreversible actions that belong in default-deny

The six categories below are better handled as blocked by default than re-litigated case by case. You open them explicitly when you need them.

Action typeWhy it cannot be undoneDefault policy
Push to remote repositoryOthers may have already pulled, or automation has fired. A force push is not an undo, it is a second incidentBlock, then human approval
Deploy or releaseUser traffic has already passed through the new version. Rolling back leaves behind the data created in betweenBlock
Delete files, records, or resourcesAnything changed since the last backup is gone, and teams often discover the backup gap only after deletingBlock, substitute a soft delete
Payments and metered spendSpending is hard to reverse, and in usage-based billing the alert arrives after the charge has accumulatedBlock, plus hard limits and alerts
External sends: email, messages, publishingIt is already on the recipient's device. Recall features are partial at bestBlock
Permission and configuration changesIf the original value is unknown, restoration is impossible, and it becomes the path by which the agent opens its own barriersBlock

I want to underline that last row. The permission to change permissions neutralizes every other barrier. If editing one configuration file can release the agent's own constraints, the five rows above it are decoration. Putting the permission definition files themselves on the write-deny list inside the agent's workspace is therefore not a minor housekeeping detail.

3. The second axis - how far does the blast radius reach

The second axis is blast radius: how far does the damage spread when this fails. Swapping the vague word risk for the concrete word reach makes the judgment dramatically easier.

  • Level 0 - the agent itself: changes confined to a scratch directory or the current session. If it fails you throw the session away.
  • Level 1 - my workspace: the checked-out branch, the local working tree. Easy to undo and invisible to everyone else.
  • Level 2 - shared team resources: shared branches, shared dev servers, team databases. Now you can break someone else's work.
  • Level 3 - external exposure: deployed services, sent email, public repositories. People outside the organization have already seen it.
  • Level 4 - financial or legal consequences: billing, contracts, personal data processing. Parts of this level have no meaningful notion of undo at all.

The point teams most often miss is the blast radius of cost. Permission to create cloud resources looks tamer than permission to delete them, but under usage-based billing, creation is spending. Worse, spending surfaces asynchronously. It shows up on an invoice after the incident is over, so nothing sounds an alarm while it is happening. Whenever you classify create-type operations as low risk, verify in the same breath that limits and alerts are already in place.

4. Overlay the two axes - auto-allow, ask, and default-deny

Putting reversibility and blast radius on two axes produces four quadrants. I consider this table the most practical part of the article. Permission design is finished when every tool call can be assigned to one of these four cells.

Small blast radius (levels 0-1)Large blast radius (levels 2-4)
ReversibleAuto-allow
Reading files, editing inside the working tree, local commits, running tests, linting, building, searching		Conditional allow with after-the-fact notice
Restarting a shared dev environment, staging deploys, cache invalidation - only where the undo procedure is documented
IrreversibleAsk a human
Deleting scratch resources, calls to metered external APIs, installing new dependencies		Default-deny
Remote pushes, production deploys, data deletion, payments, external sends, permission changes

One rule governs the use of this table: when in doubt, move up a cell. If you are unsure whether something is reversible, treat it as irreversible. If you do not know the blast radius, assume it is large. The cost of judgment errors in permission design is asymmetric. Over-blocking is inconvenient; under-blocking is an incident.

5. A permission tier table - from L0 to L4

If the quadrant table judges individual actions, a tier table describes the bundle of permissions granted to an agent as a subject. Writing a bespoke policy for every action is unrealistic, so it is far easier to operate a handful of defined tiers and assign agents to them.

TierWhat it allowsTypical useRequired conditions
L0 read-onlyReading files, docs, and logs; searching. Writing and execution fully blockedCode analysis, review comments, summarizationNone. The only tier that makes sense as a default
L1 workspace writeCreating and modifying files inside a designated directory, local commitsFeature work, refactoringMust be under version control; paths outside the tree blocked
L2 isolated executionRunning arbitrary commands inside an isolated environment, tests and buildsTest-driven development, debuggingFile system and network isolated together; no credentials injected
L3 shared resourcesAccess to shared dev or staging environments, operations on team branchesIntegration checks, staging deploysDedicated account, time-limited credentials, notification after the fact
L4 productionAccess to the operating environmentAs a rule, not grantedIf granted: human approval, audit logging, and instantly revocable tokens

The value of a tier table is that promotion becomes an explicit event. Moving from L1 to L2 forces an isolated environment to exist. Moving to L3 forces dedicated accounts and short-lived tokens. Without tiers, permissions widen quietly. An access granted once for convenience becomes the default on the next task, and a few months later nobody can explain why it is there. A tier table structurally reminds you that permissions are far easier to grant than to reclaim.

5.1 How to handle L4

Production access is better treated as an exception rather than a tier. Instead of a standing grant, issue it at the moment of need, keep the validity window short, and record its use separately. This is just the temporary privilege elevation procedure that already exists for human operators. That there is not much to invent is itself the point: a large share of agent permission design is not novel work but the application of existing access control practice.

6. Split tools down to single verbs

From here the discussion gets more concrete. In tool-calling agents, the most common way least privilege collapses is that one tool bundles several verbs.

Suppose a tool called manage_repository handles reads, updates, and deletes. The instant you attach that tool, delete permission comes with it, and there is no way to withhold deletion from an agent that only needs to read. The reason is structural: the tool interface is the smallest unit of permission. Split it into read_file, write_file, and delete_file and you can expose only the first two.

Security guidance around the Model Context Protocol points the same way. The official security documentation recommends that clients prompt for user confirmation on sensitive operations and that tool origins and inputs be made visible to the user. Practitioner guides go a step further and advise annotating tools with a destructive or irreversible classification and enforcing approval flows based on that annotation. Declaring risk at tool-definition time means the quadrant judgment does not have to be re-made by a human on every single call.

  • One verb per tool: never combine reads and mutations behind a single function.
  • Pin the scope arguments: fix the target path, table, or project on the server side rather than letting the model choose freely.
  • Annotate risk: mark irreversibility in tool metadata and let the client gate on that value.
  • Authorize outside the model: never let the decision about what is permitted depend on model output. The check belongs to the tool server or the system behind it.
  • Manage the inventory: pin the list and versions of connected tool servers and close off the path where auto-updates silently change tool definitions.

That last item matters most from a supply chain perspective. In a case reported in July 2025, an outside contribution to the repository of a widely used developer assistant extension resulted in a briefly published version containing text instructing the assistant to delete files and cloud resources. The vendor subsequently issued a security bulletin, replaced the affected version, and stated that the injected content was improperly formatted so it did not function and no customer resources were affected. What deserves attention there is not the outcome but the path. User input is not the only channel through which an agent receives instructions. Tool definitions, extensions, and external documents are all entrances, and if you do not pin those entrances your permission design fails at its premise.

7. Four barriers - dry run, isolation, pre-confirmation, undo path

Narrowing permissions does not make incidents disappear. A precisely correct command can still be aimed at the wrong target inside the allowed scope. So you need a separate layer of devices that catch an allowed action before it touches real state. I recommend four.

7.1 Dry run - make it print the plan first

Split mutating work into two phases. The first phase emits only the list of what would change and modifies nothing. The second applies that exact list. The real value of this pattern is not that a human reads the list. It is that the size of the target set becomes machine-checkable. If a task that was supposed to touch three files suddenly resolves to two thousand, you can halt automatically before a human ever looks.

7.2 Isolation - move execution somewhere else entirely

The second barrier is environment separation, which gets its own section below.

7.3 Pre-confirmation - show what will change, then ask

When you request approval, present it in a form where the reviewer can tell what they are approving. The literal command about to run, the number of affected targets, and whether it can be undone should all be on one screen. An approval dialog that only says something like proceed with this operation turns approval into a formality. Without material to judge on, people do not judge; they pass it through.

7.4 Undo path - prepare recovery before execution

The fourth is the one most often skipped: securing the means of reversal before you act. Make a commit before editing files. Export before deleting data. Record the original value before changing configuration. In the July 2025 case referenced earlier, the part that made response hardest was not the deletion itself but an incorrect report about whether recovery was possible, which delayed the response. An agent's self-report must never be your evidence of recoverability. The recovery path has to live outside the agent, and a human has to be able to verify it directly.

8. How tightly should the isolation be

Isolation is not a single switch. The strength you need depends on what you are trying to prevent, and every step up costs money and convenience. Define the threat model first.

ApproachWhat it preventsWhat it does notWhen it fits
Separate working tree or branchContaminating code under active work, collisions between parallel tasksSystem-wide changes, network access, credential exposureRunning several tasks against the same repository at once
Separate OS user accountDamage to home directories, personal settings, and other accounts' filesAnything reachable by that same account, kernel-level problemsThe cheapest first line of defense, deployable almost anywhere today
ContainerHost file system access, package contaminationShares the kernel, so kernel vulnerabilities remain an escape routeReproducing an execution environment for code you trust
User-space kernelMost system calls that would otherwise reach the host kernelNoticeable throughput loss on I/O-heavy workloadsYou need more than a container but a full VM is overkill
Micro virtual machineA dedicated kernel per workload, raising the bar for escape considerablyHigher operational complexity and resource overheadServices that execute large volumes of untrusted code

One principle recurs across isolation guidance: the file system and the network must be restricted together. Restrict only one and the other becomes the bypass. With the network open, reachable credentials can be exfiltrated; with the file system open, configuration can be rewritten to re-establish a network path. A second limitation matters just as much: the scope of what isolation covers. The official documentation for a widely used coding agent, for example, states that its operating-system-level sandbox applies only to shell commands and their child processes. File edits or network requests the agent performs through other tool calls may sit outside that sandbox. If you adopt isolation, read the documentation and confirm exactly what is inside the boundary.

9. Where to put approvals - gates that do not manufacture fatigue

Human approval is a powerful device, but it is not free. When prompts appear often, people click through without reading. This is not a failure of willpower; it is a structurally predictable outcome. Security operations has documented the same phenomenon for years under the name alert fatigue: as alert volume rises, the review quality of each alert falls, and industry reporting has repeatedly found that a substantial share never gets properly investigated.

The goal of approval design is therefore not to add approvals but to reduce their number. It sounds backwards, but the logic is simple. Approvals must be rare for people to actually read them, and they must be read for the gate to function. There are three ways to cut the count.

  • Push down — take reversible, small-radius actions out of the approval queue entirely. Prompting on every file edit does not raise safety; it dilutes what approval means.
  • Push up — an action you could not live with even after approving is not an approval candidate, it is a denial candidate. Handling production data deletion through a dialog box hands the last line of defense to a tired human.
  • Batch — handle sequences of similar actions with a scoped approval instead of individual ones: edits within this directory are allowed for the duration of this task. The condition is that scope and expiry are stated explicitly.

Tooling is moving in this direction too. Widely used coding agents now ship multiple permission modes so the approval frequency can be tuned to the phase of work: a mode that blocks changes while exploring, a mode that auto-accepts edits during repetitive editing. More recently, an intermediate mode has appeared in which a classifier evaluates each request first and lets only the safe ones through automatically. The direction is sensible, but leaning on it deserves caution. A classifier is also a probabilistic judgment, so it is safer not to make a classifier the final barrier for irreversible actions. Use probabilistic machinery to widen the auto-allow band, and keep the deny line on deterministic rules.

The conditions on the person receiving the request are part of the design as well. That is where Google's principle of a well-defined human controller lands. The approver should be the person accountable for the outcome and should hold the context needed to judge. If approval authority is open to anyone in reach, the gate is ceremonial.

10. Concurrency - partitioning permissions across parallel agents

Once you run several agents at once, the nature of the permission problem changes. With a single agent the question was what it can do. In parallel the question becomes whether two of them can touch the same thing at the same time. You start seeing outcomes that break even though each agent individually used only permissions it legitimately held.

The typical failures look like this. Two agents edit the same file and the later write erases the earlier one. Two agents restart the same dev server and break each other's tests. Two agents commit to the same branch and tangle the history. Two agents try to bind the same port and one fails quietly. The common thread is that the permission check passed but exclusivity was missing.

The fix is to partition permissions not only by subject but also by resource. Practical mechanisms include the following.

  • Path ownership — assign each agent a non-overlapping set of writable directories. If overlap is required, that work is not a parallelization candidate.
  • Separate working trees — give each agent its own tree at the repository level so they never physically share the same file.
  • Write leases — put a lock or a time-bounded lease on shared resources so only one holder writes at a time. Without the lease, the agent waits or fails.
  • Inventory the shared resources — explicitly enumerate the invisible shared resources such as ports, databases, caches, and external API quotas, and set an exclusivity policy for each.
  • Single integration point — let everyone work in isolation and funnel the merge step through one place, sequentially.

At this point it becomes clear that isolation and permissions were always the same problem. Isolation is a permission boundary implemented physically. Giving two agents separate working trees is not a convenience measure; it removes each one's write permission over the other's files. The more you scale parallel execution, the more it pays to depend on physical separation rather than on policy documents. A rule can be violated. Something you cannot reach cannot be violated.

11. Audit logs - records that can answer questions later

This is where Google's third principle, observability, lands. Incidents eventually happen, and what you need at that moment is a record from which the sequence of events can be reconstructed. Log design already has an established baseline: NIST SP 800-92 lists the minimum elements of a log entry as timestamp, event and status or error codes, the service or command name, the associated user or system account, and the device used.

Agents need several additions before the log becomes usable in practice. In the table below, the top five rows are the general baseline and the bottom five are agent-specific.

FieldWhy it is needed
Timestamp in a standard time baseThe common axis for merging logs from several agents and systems in order
Acting accountDistinguishes a human account from a dedicated agent account. Shared accounts make this row meaningless
Command or tool name executedThe minimum unit of what was done
Result code and errorSeparates what was attempted and blocked from what succeeded
Source device and session identifierTraces which execution environment the action originated from
Instruction source and task identifierLinks an action back to the request that produced it. Without it you keep isolated commands and lose the context
Verbatim tool argumentsA tool name reveals nothing about target or scope. The deleted path lives in this field
Approval status and approverDistinguishes auto-allow from human approval. This is the evidence that the gate actually functioned
Before and after referencesCommit hashes, snapshot identifiers, backup locations - the coordinates needed to undo

A few operational cautions. First, logs must live somewhere the agent cannot delete. Pile them in the same workspace and a deletion incident takes the evidence with it. Second, tool arguments can carry secrets, so a masking rule has to be designed alongside them. Third, the purpose of the log is not surveillance but recovery and improvement. Looking at which approvals are always waved through and which blocks keep firing gives you the evidence to adjust the permission design itself.

12. Design failures that keep repeating

Inverting the principles above produces a short list of common failure patterns. The five below look safe on the surface but do not actually defend anything.

  • Prohibiting things in the prompt — writing do not do this in an instruction file is not permission control. Instructions are followed probabilistically, dilute over long sessions, and compete with other instructions arriving from outside. Prohibition has to be enforced at the execution layer.
  • Reusing the human account — the most common and most fundamental failure. If the agent runs on a person's credentials, least privilege cannot hold and the audit log cannot separate human actions from agent actions.
  • Over-issuing approvals — gate everything and approval becomes a formality. It looks like more defenses, but in practice the one approval that mattered is buried under a hundred that did not.
  • Never testing the backup — the assumption of reversibility left unverified. A backup whose restore procedure has never been executed is a belief that a backup exists, not a backup.
  • Turning on the global bypass for convenience — an option that disables permission checks wholesale is only meaningful inside an isolated environment. Enabling it on a personal development machine voids every design decision above it in a single line.

All five share one structure: mistaking something that is not control for control. Instruction text, ceremonial approvals, and untested backups are all devices that provide reassurance merely by existing. The question to ask when auditing a permission design is this: what would be different if this device were absent? If no answer comes, it is not a control.

Conclusion: design for undo, not only for prevention

Sit with agent permission design long enough and the original goal shifts a little. At the start, reducing incidents to zero looks like the objective. But in a system where execution derives from natural-language judgment, the set of attempts cannot be enumerated in advance, and what cannot be enumerated cannot be fully blocked. The reachable goal lies elsewhere: ensuring that when incidents happen, they happen only within a range you can reverse.

Order matters, then. Before deciding what to allow, enumerate and close what cannot be undone, tier by blast radius, attach isolation physically to each tier, and gate only the small remainder behind approval. And whatever you do, secure the recovery path before execution. Follow that order and permission design compresses from an endless rule list into a handful of judgment criteria.

As of July 2026, the standards and the industry guidance point the same way. NIST's least privilege applies verbatim to processes acting on behalf of people. OWASP splits excessive agency into functionality, permissions, and autonomy and tells you to lock each separately. Google offers human controllers, limited powers, and observability as the skeleton. Almost none of this is new. What changed is only that the subject of these principles is no longer a person, but a process running overnight under a person's name. Before writing the sentence about how the agent made a mistake, the question worth asking one more time is unchanged: who left that door open?
