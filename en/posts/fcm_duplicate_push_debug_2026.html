A Redeploy Resent Already-Sent Notifications - Debugging FCM Duplicate Push

What Happens When Send-State Lives Only in Memory - Fixing It With Idempotency Keys, the Outbox Pattern, and Scheduler Locks

2026-07-23 Dev & Infra

Introduction: A Redeploy Brought Back Yesterday's Notifications

As of July 2026, there's a case worth revisiting. A solo developer running a surf-forecast app ran into this: the app was designed to send a notification only "the moment conditions cross into dangerous territory" - an event-triggered alert, not a recurring one. Right after a server redeploy, though, notifications that had already gone out the day before landed on users' phones again. It barely reproduced locally, so tracking down the cause took a while.

The cause, once found, was almost embarrassingly simple: the fact that "this notification has already been sent" was tracked only in the server process's memory. When the redeploy spun up a fresh process, that memory vanished entirely. To the new process, the notification looked like it had never gone out, so re-evaluating the condition and firing again was, from its point of view, the correct behavior.

This piece uses that one case as a starting point to unpack why this class of bug isn't specific to one app - it's a pattern that recurs across notification and messaging systems in general. It also walks through why chasing "exactly-once" delivery is the wrong goal to begin with, and what to aim for instead, through a set of practical patterns.

1. Why Duplicate Sends Keep Happening - Four Typical Causes

1.1 Send-State Kept Only in Memory

This is the most common cause. If the fact that "this notification was already sent to this user" lives only in an in-process variable or cache (a dict, a Set, an in-memory cache), that information is tied to the process's lifecycle. A deploy, a restart, a scale-down, a container reschedule, an OOM kill - any of these wipes the state clean. This was exactly the root cause in the surf-forecast app case. The insidious part is that it never surfaces under normal conditions. As long as the process stays up for weeks, the bug sleeps quietly - until one deploy sets it off.

1.2 At-Least-Once Retries

FCM, like most push and messaging infrastructure, does not guarantee "exactly-once" delivery. It guarantees at-least-once delivery instead. If a server sends a request to FCM and the response times out, the server genuinely doesn't know whether it succeeded or failed. The safe default in that situation is to retry. But if the first request actually went through and only the response was lost, that retry becomes a duplicate send. This isn't a bug - it's an unavoidable consequence of an unreliable network.

1.3 Duplicate Scheduler Execution

If notifications are sent by a cron job or scheduler, the same job can end up running on multiple workers or pods at once. In Kubernetes especially, if a CronJob's concurrency controls aren't configured, overlapping deploy timing or a previous run not finishing before the next one starts can produce the same notification twice. This is the classic bug that never shows up when you're running a single instance and only appears the moment you scale out.

1.4 Multi-Instance Race Conditions

If the send logic itself is a two-step "check condition, then send" flow with no lock between the steps, multiple instances can check the same condition nearly simultaneously and each fire off its own send. This is a race condition where several workers grab the same event at once. It often overlaps with 1.1 (state kept in memory), but the root cause is different - this isn't data disappearing, it's the absence of any coordination mechanism to decide who owns the job in the first place.

2. "Exactly-Once" Was the Wrong Goal All Along

2.1 Why Exactly-Once Is Impossible in a Distributed System

The Two Generals Problem is the classic thought experiment showing that two parties communicating over an unreliable channel can never reach certain, simultaneous agreement on an action. On a network where messages can be lost, a sender has no way to be certain the other side received anything - because the acknowledgment itself can also be lost. Because of this fundamental limitation, guaranteeing "exactly-once delivery" at the network layer is theoretically impossible. FCM, Kafka, SQS - none of them are exceptions.

2.2 So the Practical Answer Is "At-Least-Once Plus Idempotency"

The answer most messaging and event systems settle on in practice is to give up on "exactly-once delivery" and instead combine at-least-once delivery with idempotent processing to produce the same effect. You accept up front that messages may arrive more than once, and you design the receiving side so that processing the same message twice changes nothing. This is commonly called "effectively-once": you relax the delivery guarantee and instead secure the safety of the outcome at the application level. This is exactly the same conclusion reached in Three Hard Problems Kafka Solves at Scale, which covers the tradeoff that ordering, exactly-once processing, and low latency can't all be had at once.

3. Solution Patterns - How to Actually Fix This

3.1 Persist the Send Record

The first thing to do is record the fact that "this was already sent" in a database (or a persistent store like Redis) instead of process memory. The surf-forecast app case's fix landed exactly here - the state was rebuilt by reloading the send history from the database at boot time instead of trusting in-memory state. The principle is simple: any fact that "must happen only once" needs to live somewhere that survives the process dying.

3.2 Designing an Idempotency Key

Before sending, build a key that uniquely identifies what this notification is about. A common combination is user ID + event type + target entity + time window, for example:

dedup_key = f"{user_id}:{event_type}:{entity_id}:{window_bucket}"

Putting a database unique constraint on this key means a second insert attempt with the same key gets automatically rejected by the database (INSERT ... ON CONFLICT DO NOTHING). Letting the database's atomic constraint handle this is far more resilient to race conditions than writing your own "check if it already exists" logic in application code.

3.3 Pre-Send Checks and Transactions

If the three steps "check if sent, send if not, mark as sent" aren't bound together atomically, another process can slip in between the check and the mark and send the same notification again. There are two ways to fix this. One is to atomically write a "send pending" record to the database first (using the idempotency key's unique constraint) and only perform the actual send if that write succeeds. The other is to wrap the send decision itself inside a database transaction together with any other state change, so the decision and the state update succeed or fail as one unit.

3.4 The Outbox Pattern

This pattern is for when you need "changing database state" and "sending a notification externally" to behave like a single transaction. Instead of sending directly, you write the event that needs to be sent into an outbox table within the same transaction. That way, the state change and the scheduled send succeed or fail together, atomically. A separate relay process polls the outbox table, performs the actual send, and marks the record as sent once it succeeds. Note that this relay step still only guarantees at-least-once delivery, so the final send logic still needs to be idempotent. The outbox pattern guarantees you won't lose events - it does not, on its own, guarantee you won't get duplicates. It's only complete when paired with the idempotency key from 3.2.

3.5 Scheduler Locks

If multiple instances risk running the same scheduled job, a distributed lock is what guarantees that only one instance claims the job for a given run. Libraries that use Redis, a database, or ZooKeeper as a lock store (ShedLock and similar tools) serve this role. The principle is simple: before starting, atomically attempt to acquire a lock for "this job at this scheduled time," and if that fails (because another instance already holds it), skip silently. In Kubernetes, setting concurrencyPolicy: Forbid on a CronJob is a minimal additional safeguard.

3.6 FCM's collapse_key - A Supplement, Not a Root Fix

FCM supports a field called collapse_key. When multiple messages sharing the same collapse_key pile up, FCM delivers only the newest one once the device comes back online. It looks like deduplication at first glance, but it has two limits. First, it only applies to data messages, not notification messages. Second, it's a cleanup mechanism that runs on the client/FCM side after the server has already sent duplicates - it does nothing to fix why the server sent them in the first place. In short, collapse_key is a symptom-relief tool, not a substitute for the root fixes in 3.1 through 3.5.

4. Designing for Redeploys and Crashes - "Don't Trust Memory"

One principle runs through every pattern above: design on the assumption that a process can die at any moment. A redeploy, an autoscaler scaling down, an OOM kill, a node failure - any of these can end a process without warning. The moment you keep a "must happen only once" state in a memory variable, that guarantee becomes a temporary one that expires along with the process's lifetime. State that needs a real guarantee - send history, idempotency keys, locks, outbox events - always belongs in a persistent store outside the process. This is also why these bugs rarely reproduce in local development: local environments are stable single processes with no deploys, no scale-out, no container rescheduling. A production deploy pipeline is precisely where these broken assumptions actually get triggered.

5. The Connection to Two Principles We've Covered Before

This problem is, in fact, a re-confirmation of two principles this blog has already covered. One Toggle Becomes a Distributed System covered a bug where a setting turned off offline came back on, and the root cause ultimately traced back to the absence of an idempotent synchronization design that reconciles client and server state into a single trustworthy truth. FCM duplicate sends are the same kind of problem - things break when the fact "already processed" isn't consistent across multiple locations (memory, the process before and after a restart). Three Hard Problems Kafka Solves at Scale covers the same difficulty with "exactly-once processing" - whether it's a large-scale event pipeline or a solo developer's push-send logic, expecting the network layer to deliver "exactly once" leads to the same trap, regardless of scale. The principle converges to one, independent of size.

6. The User-Trust Angle - What Duplicate Notifications Really Cost

Duplicate sends shouldn't be treated as a mere annoying bug. From a user's perspective, having a notification you already dismissed reappear out of nowhere quietly erodes trust. The impression that "this app can't manage its own state" easily leads to users turning off notification permissions, or in worse cases, deleting the app. For a service like a surf-forecast app that specifically promised to alert only "at the moment of real danger," breaking that promise (by repeating an unnecessary alert) undermines the credibility of the notifications themselves. Notification-system reliability isn't a feature requirement - it's a matter of user trust.

7. Checklist - What to Verify Before You Deploy

  • Is send status/history recorded in a database or Redis, not just in process memory?
  • Does each notification have an idempotency key combining (user, event, entity, time window), backed by a unique constraint?
  • Is the gap between "check" and "send" protected by a lock or an atomic insert against race conditions?
  • If a state change and a scheduled send need to happen together, has the outbox pattern been considered?
  • Is the risk of a scheduled job running on multiple instances at once blocked by a distributed lock or a concurrencyPolicy?
  • If FCM (or similar) has retry logic, is it understood that a retry can become a duplicate send, and is processing idempotent as a result?
  • Right after a redeploy or restart, do notification-related batches/schedulers avoid immediately re-evaluating past events?

Conclusion

Duplicate FCM notifications aren't some quirky bug specific to one app - they're one instance of an extremely common mistake in how state is handled in distributed environments. The cause almost always converges on the same handful of things: the record of something that "must happen only once" was kept only in process memory, there was no mechanism to prevent a race between checking and executing, or the possibility of retries was never accounted for. The moment you change the goal from "exactly-once delivery" to "at-least-once delivery plus idempotent processing," the fix becomes obvious. Persist the send record, put a unique constraint on the idempotency key, and add the outbox pattern and a distributed lock where needed. Redeploys and restarts are a daily occurrence. A design that doesn't flinch in the face of them is, in the end, a design that doesn't trust memory.
