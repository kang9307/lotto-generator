ハングルが壊れる地点を特定する方法 - cp949とUTF-8、2種類のエンコーディングエラー

壊れた見た目から原因を逆追跡し、復旧できる損傷とできない損傷を分ける方法

2026-07-30 開発・インフラ

序論: 「壊れた」は診断ではない

取引先から受け取ったCSVを開いたらハングルが全部見慣れない文字になっている。このときの対応はたいてい2つだ。エンコーディング設定をあれこれ変えてみるか、相手に送り直してもらう。どちらも間違いではないが順序が逆だ。まず知るべきなのはこのファイルが直せる状態なのかどうかである。

エンコーディングエラーは2種類しかない。この区別がこの記事のすべてだと言ってもよい。

  • ① バイトは正しいのに解釈を間違えたもの。ファイルの中には元のバイトがそのまま入っていて、読む側が見当違いのエンコーディングを適用して画面上でだけ異常に見える状態だ。完全に復旧できる。
  • ② 変換の過程で情報が消えたもの。誰かがすでに誤読した結果を保存したか、変換先のエンコーディングにない文字を疑問符に変えてしまった。原文は戻ってこない。

見た目だけならどちらも「文字が壊れた」で同じだ。ところが①はコマンド1行で終わり、②は元のファイルをもらい直すしか手がない。どちらなのかを先に判別しなければ、すでに死んだファイルを抱えて一日を費やすことになる。

この記事はその判別法を扱う。「UTF-8を使いましょう」のような話はしない。その助言はすでに壊れた画面の前に座っている人には何の役にも立たず、官公庁や銀行が今もcp949でファイルを送ってくる現実も変えられない。代わりに壊れた見た目から原因を逆追跡する表を作り、その表のすべてのマスを実際に実行して埋めた。

実行環境。以下のすべての出力はWindows 10 Pro (10.0.19045)で実際に実行した結果だ。シェルはGNU bash 5.2.37 (MSYS2/MinGW64)、ツールはNode.js v22.16.0 (win32)、Python 3.13.3、GNU libiconv 1.18である。システムのANSI/OEMコードページはどちらも949で、シェルのロケールはLANGが空の値でLC_CTYPE=C.UTF-8だ。

スクリプトはすべてファイルに保存して実行した。ハングルとバックスラッシュが混ざったコードをシェル引数やヒアドキュメントで渡すと静かに変形する。引用規則そのものが気になるならシェルの引用規則を見よ。例示パスは/tmp/demo、~/workのようなプレースホルダに置き換えた。

この記事が扱わないもの。同じ文字がUnicodeの中で2通りのコードポイント列になる正規化の問題はNFCとNFDで扱った。この記事はUnicodeとレガシーエンコーディングの間の変換だけを掘る。ハングル音節を正規表現の範囲で扱う算術はハングル正規表現の罠に、ファイル名に空白や改行が混ざってパイプラインが壊れる問題はfindとxargsの空白の罠にある。ここではファイル名をエンコーディングの側面だけ見る。

  • 簡体中国語は収容できない。cp949の漢字は繁体系なので「简体」が拒否された

  • 方向B (UTF-8をcp949として)。cp949は2バイトずつ切って読むので、3バイト単位で書かれたものを次々とずれた位置で拾い上げる。ところがその組み合わせが偶然に有効な漢字やハングルへマッピングされる場合が多い。だから「湲덉븸」のように読める文字に見えるのに意味がない結果が出る

この非対称が診断で決定的だ。置換文字がうごめいていれば方向A、漢字とハングルが入り混じっていれば方向Bである。

2つのブロックの違いを正確に見よう。3-1では再エンコードしたバイトが元と完全に一致した(True)。バイトがそのままだったので、正しいエンコーディングで読み直すだけで原文が戻ってきた。

3-2では11バイトが27バイトに増えた。置換文字1個がUTF-8で保存されるときEF BF BDの3バイトを占めるからだ。そして決定的に、この3バイトにはもともとどのバイトを代わりに置いたのかという情報がない。すべての失敗が同じ値に潰される。だから復旧が原理的に不可能なのだ。

実務の規則。置換文字を見ることは問題ない。画面に一瞬現れただけでファイルは無事だ。危険なのはその状態を保存することである。誤読した結果を書き戻した瞬間に①が②に変わり、その時点で元は死ぬ。だからエンコーディングが疑わしいファイルは読み取り専用で開き、確信が持てるまで保存ボタンを押さないことが第一の防御だ。

  • どちらにしても変換先のエンコーディングがその文字を知らないという事実そのものは変わらない。根本的な解決は変換しないことだ

5. 「占쏙옙」の正体 - 二重の損傷の証拠

韓国でエンコーディングの事故に遭ったことのある人なら、この文字を見たことがある。これがどこから来るのかを段階別に再現した。

--- 3-6. where the infamous string comes from ---
step 1. real cp949 text
  한글 -> cp949 C7 D1 B1 DB
step 2. some layer decodes it as UTF-8 with replacement
  -> [�ѱ�]   U+FFFD U+0471 U+FFFD
step 3. that string is saved as UTF-8
  -> EF BF BD D1 B1 EF BF BD
step 4. a later reader opens those bytes as cp949
  -> [占싼깍옙]

the replacement char alone, put through the same two steps:
  U+FFFD as utf-8 : EF BF BD
  x2              : EF BF BD EF BF BD -> [占쏙옙]
  x3              : EF BF BD EF BF BD EF BF BD -> [占쏙옙占�]
  x4              : [占쏙옙占쏙옙]
  odd counts leave a dangling byte: cp949 eats 2 at a time, UTF-8 wrote 3

構造は明確だ。置換文字2個がUTF-8で保存されるとEF BF BD EF BF BDの6バイトになる。cp949は2バイトずつ読むのでEF BF、BD EF、BF BDの3つの対に切られる。3バイト単位で書いたものを2バイト単位で読んだので3文字が出る。6と3の最小公倍数が6なので、このパターンが正確に繰り返される。

実務的な結論が重要だ。この文字列を見たら復旧の試みを止めるべきである。これは損傷が二度重なった証拠であり、最初の段階ですでに元のバイトが消えている。2番目の誤読を正しても出てくるのは置換文字だけだ。

--- 3-7. how to tell single damage from double damage ---
what you see          U+FFFD present  recoverable   meaning
------------------------------------------------------------------------------
ÇÑ±Û                  False           True          misread only, bytes intact
replacement run       True            False         bytes already destroyed
the infamous one      False           False         bytes already destroyed

3行目に罠がある。二重に損傷した文字列には置換文字が残っていない。2番目の誤読の過程で正常な漢字やハングルへマッピングされたからだ。だから「置換文字がないから大丈夫だ」という判断が間違う。置換文字の不在は無事であることの証拠ではない。特定のパターンを別に見分ける必要がある。

  • 根本的な解決は検索のオプションではなくリポジトリを1つのエンコーディングに統一することだ

[PYTHONIOENCODING=cp949]

[PYTHONUTF8=1]

  • 画面の出力が壊れる問題はPYTHONIOENCODINGで直る
  • ファイルを読み書きするエンコーディングが問題ならこの変数は何の効果もない。症状だけを見てこの変数をいじると時間を無駄にする
  • ファイル側までまとめてUTF-8に合わせるにはPYTHONUTF8=1が必要だ。実行してみるとopen()の既定値がutf-8に変わった
  • 最も確実な方法は環境変数に頼らずファイルを開くコードでエンコーディングを明示することである。環境変数はデプロイ環境ごとに変わる

8.3 LANGとLC_ALLは何を変えるのか

  • ko_KR.UTF-8でだけ文字単位で数えて2が出た
  • ko_KR.eucKRはUTF-8のバイトを2バイト文字として解釈し、3という見当違いの答えを出した。そして並び替えは出力を出せなかった
  • つまりロケールはツールがバイトを文字にまとめる方式を決める。文字数、並び替え、大文字小文字の変換がすべてここに掛かっている

10. 境界で一度だけ変換する

レガシーと共に生きる現実的な方法は1つだ。ファイルが入ってくる地点で一度変換し、その内側はすべてUTF-8だと仮定すること。問題はその一度の変換が静かに失敗しうるという点である。

=== 9-1. plain UTF-8 to CP949, one file at a time ===
emoji.txt    FAILED: iconv: emoji.txt:1:7: cannot convert
euro.txt     OK
ext.txt      OK
zh.txt       FAILED: iconv: zh.txt:1:7: cannot convert

=== 9-2. exit codes matter. a silent pipeline loses this ===
exit code             : 1
bytes actually written:  ba b8 b0 ed bc ad 20
what got through     : 보고서
iconv stopped at the offending char and kept the prefix. truncation, not an empty file

これが最も危険な挙動だ。変換が失敗したのに出力ファイルはすでに作られている。その中には失敗した地点の前の部分だけが入っている。ファイルが存在し内容も正常に読めるので、切断されたという事実に気づく手がかりが終了コードだけになる。

  • 変換を自動化したパイプラインが終了コードを確認しなければデータの一部が静かに消える
  • 切断はファイルの末尾で起きるので先頭だけを開いて見る検査は絶対にこれを捕まえられない
  • パイプでつないだ場合は途中のコマンドの失敗が隠れることがある。終了コードとパイプで扱った問題と正確に同じ構造だ

10.1 失敗を切り抜ける3つの方法

=== 9-3. the three escape hatches ===
-c           rc=1  result=[보고서 ]  bytes= ba b8 b0 ed bc ad 20 0a
//TRANSLIT   rc=0  result=[보고서 :-D]  bytes= ba b8 b0 ed bc ad 20 3a 2d 44 0a
//IGNORE     rc=0  result=[보고서 ]  bytes= ba b8 b0 ed bc ad 20 0a
-c drops it, //TRANSLIT approximates or drops, //IGNORE drops and still reports failure

//TRANSLITの結果が印象的だ。絵文字がASCII3文字で近似表記された。人が読むことはできるが原本ではない。

オプションなし失敗した地点で中断1後ろの部分が全部消失なし。必ず終了コードを確認
-c移せない文字だけを捨てる1その文字だけ消失失敗を知りながら進めるとき
//IGNORE捨てる0その文字だけ消失勧めない。失敗を隠す
//TRANSLIT近似表記に置換0原本ではない、読むことはできる人が読むログ類

最も危険な組み合わせは//IGNOREと終了コードの未確認だ。文字が消えたのに成功として報告される。逆にオプションなしで回すと失敗は知らせてくれるが、すでに切断されたファイルが残る。どちらも安全ではないので検証を別に付ける必要がある。

10.3 変換を検証する方法

結論は単純だ。変換したものを逆に変換して、元とバイトが同じか比べればよい。

=== 9-6. round trip integrity check you can run in CI ===
original md5      : f765f0504efec35848a3c116a1c98d10
after round trip  : f765f0504efec35848a3c116a1c98d10
VERDICT: lossless

now the same check on a file that cannot survive:
original md5      : 4db91275cca0367a7fe3823751f802e8
after round trip  : 918226859d33c495cb4acde0bafc7e30
VERDICT: LOSSY - do not ship
diff             : 1c1 < 보고서 😀 --- > 보고서

最初のファイルにはユーロ記号が入っていたがハッシュが完全に一致した。cp949にユーロ記号があるので損失がない。2番目は絵文字があってハッシュが変わり、差分を出力してみると正確にその文字だけが消えていた。

この検査は数行で終わり判定が明確だ。変換を自動化するすべての場所にこの検査を付けることが、静かなデータ損失を防ぐ唯一の方法である。

12.1 レガシーと共に生きる方法

官公庁や銀行が送ってくるファイルは、これからもcp949だろう。その現実で守るべき原則を整理するとこうなる。

  1. 変換は境界で一度だけ。ファイルを受け取る地点でUTF-8に変えて保存し、その後のすべてのコードはエンコーディングを知らないようにする。「ここはcp949なのか」と問うコードが生まれ始めたら、設計が崩れたのだ
  2. 元を消した後に検証しない。変換したファイルと元を一緒に置いて、往復の検査を通した後に整理する
  3. 送り出すときは相手のエンコーディングで。相手がcp949を期待するなら、送り出す境界で再び変換する。このときcp949にない文字が混ざって入りうるので、往復の検査がより重要になる
  4. 内部では絶対に混ぜない。リポジトリの中に2つのエンコーディングが共存すると、7節で見たように検索が半分しか引っかからない
  5. 絵文字と簡体中国語を警戒する。ユーザの入力にこれが混ざると、cp949で送り出すとき必ず損失が出る。入力の段で弾いて知らせる方が、後で疑問符を発見するよりよい
  6. エンコーディングを文書に書く。6.4節で見たようにバイトだけでは確定できない。受け渡す規格に明記することが唯一の根本的な解決だ

13. この記事で確認できなかったこと

確認していないことを確認したように書けば、この記事が次の人を誤らせる。限界を明確に明かす。

  • スプレッドシートのプログラムの実際の挙動。6節で「レガシーリーダー」と表現したものはcp949でデコードする挙動を直接再現したものであり、特定のスプレッドシート製品を実行して確認したものではない。製品とバージョン、地域の設定によって違う可能性がある
  • ブラウザの文書レンダリング。9節の結果はスクリプトが本文を取得する経路についてのものだ。meta charsetとHTTPヘッダの優先順位、ブラウザのエンコーディング推測の挙動は実行で検証していないので断定しない
  • データベースの境界。カラムの文字セットとコネクションの文字セットが食い違うとき何が保存されるのかは確認していない。この記事の原則(境界で一度変換、往復の検証)はそのまま適用されるが、具体的な挙動は使う製品で確認する必要がある
  • 圧縮ファイルの名前のエンコーディング。zipの項目名をどのエンコーディングで保存するのかはツールごとに違うと知られているが、この記事では実行していない
  • 他のOS。7節のファイル名の再エンコードの結果は、この環境固有のものである可能性がある。ファイル名をバイト列として扱うシステムでは結果が違うと見られるが確認していない
  • メールのヘッダと添付ファイル名。別のエンコーディング規則がある領域であり扱わなかった
  • エンコーディング自動判定ライブラリの精度。6.4節で原理的な限界を見せたが、実際のツールが統計的にどれだけよく当てるのかは測定していない

ただし確認できなかったものには共通点がある。すべて「あちら側がどうするか」に関する問いだ。そしてこの記事の診断法は、あちら側の挙動を知らなければ成立しないものではない。バイトを直接見る方法はどの環境でも同じである。それが推測の代わりにバイトを見よと言う理由だ。

結論: まず問うべきは「直せるのか」だ

壊れた画面を見るとエンコーディングの設定からいじりたくなる。ところが順序が違う。最初の問いは、このファイルが直せる状態なのかだ。その答えによってやることが完全に変わる。

実行して確認したことを要約するとこうなる。バイトが無傷な誤読はすべて復旧できた。cp949のバイトをlatin-1で読んでいても、再エンコードしてバイトが元と一致することを確認し、正しいエンコーディングで読めば原文がそのまま戻ってきた。画面がどれほど醜く見えてもそうだ。

一方置換文字が介入した瞬間に、復旧は原理的に不可能になる。11バイトが27バイトに増え、増えたバイトには元の値についての情報がない。そしてその状態を再び誤読すると特定の3文字のパターンが出るが、それを見たなら復旧の試みをやめて元をもらい直すことが唯一の答えだ。その判別のためにバイトからEF BF BDを数えることが、診断の5番目の段階だった。

だから結論は「全部UTF-8に変えよう」ではない。それは無理だ。相手は変わらず、有効性の検査だけではエンコーディングを確定することもできない。現実的な結論は変換の地点を1つ決めて、その変換が損失なく終わったかを往復で検証し、その内側はエンコーディングを知らないようにすることである。そして何より推測する前にバイトを見ることだ。

今すぐできることが1つある。エンコーディングを変換するコードやスクリプトを探し、その変換の終了コードを確認しているか見よ。確認していなければ、そのパイプラインは今まで静かにデータを切ってきた可能性がある。そしてその事実は、ファイルの先頭だけを開いて見る検査では絶対に露わにならない。

## 0. 大前提 — エンコーディングのエラーは二種類しかない

| 種類 | 何が起きたか | 復元 |
|---|---|---|
| **① 誤読** | バイトは無傷で、読む側が誤ったエンコーディングを適用した | **完全に可能** |
| **② 消失** | 誤読の結果を保存した、または変換先に無い文字を置換した | **不可** |

## 1. 30秒判定 — エディタで開く前にバイトを見る

## 3. 復元 — 誤読だけが起きた場合

```python
# repair.py — 誤って表示されている文字列を原文に戻す
import sys

seen = sys.argv[1]              # 誤って見えている文字列
raw = seen.encode('latin-1')    # バイトをそのまま復活させる
print(raw.decode('cp949'))      # 正しいエンコーディングで読み直す
```

```bash
python repair.py "ÇÑ±Û ÀÎÄÚµù"      # -> 한글 인코딩
```

- **必ず `latin-1` を使う。**256個のバイト値すべてを往復させる
- `cp1252` は5個のバイト(`81 8D 8F 90 9D`)に定義文字が無く、**復元の途中で逆に失う**
- UTF-8バイトが化けていた場合は最後の行を `decode('utf-8')` に変える
- ファイル単位なら `iconv -f ISO-8859-1 -t UTF-8` で戻してから再判定する

## 4. 復元不能の判定 — ここで止める

```bash
# 代替文字が保存されていれば原本のバイトはすでに消えている
od -An -tx1 "$FILE" | tr -d ' \n' | grep -c efbfbd

# 二重破損の痕跡(代替文字がcp949で読み直された結果)
grep -c '占쏙옙' "$FILE"
```

どちらかが引っかかれば**復元を試みない。**理由は次の通り。

- 代替文字は保存時に `EF BF BD` の3バイトになるが、**元がどのバイトだったかの情報を持たない**
- あらゆる失敗が同じ値に潰れる。11バイトの原本が27バイトに膨らんだ事例を確認した
- `占쏙옙` 系には代替文字が**もう残っていない。**二度目の誤読で通常の文字に対応づけられたためだ → **代替文字が無いことは無事の証拠にならない**

## 5. 境界で一度だけ変換する — 切り捨てを防ぐ形

```bash
# 悪い例: 失敗してもファイルは作られる(先頭部分だけの切り捨てファイル)
iconv -f CP949 -t UTF-8 in.csv > out.csv

# 良い例: 失敗したら成果物を残さない
set -Eeuo pipefail
TMP=$(mktemp)
if iconv -f CP949 -t UTF-8 in.csv > "$TMP"; then
  mv "$TMP" out.csv
else
  rm -f "$TMP"
  echo "変換失敗 — 原本を確認してください" >&2
  exit 1
fi
```

**終了コードを確認しなければデータが静かに消える。**切り捨てはファイルの末尾で起こるので、先頭だけ開く検査では絶対に見つからない。

| 方式 | 失敗時 | 実測の終了コード | データ | 判断 |
|---|---|---|---|---|
| オプション無し | 失敗地点で中断 | 1 | **それ以降がすべて消失** | 終了コードの確認が必須 |
| `-c` | 移せない文字を捨てる | 1 | その文字だけ消失 | 承知の上で進めるとき |
| `//IGNORE` | 捨てる | 0 | その文字だけ消失 | **推奨しない**(失敗を隠す) |
| `//TRANSLIT` | 近似表記に置換 | 0 | 原本ではない | 人が読むログ類のみ |

## 6. 往復検証 — 変換するすべての場所に付ける

```bash
# 変換が無損失で終わったか確認する
roundtrip_ok() {
  local src="$1"
  iconv -f UTF-8 -t CP949 "$src" 2>/dev/null | iconv -f CP949 -t UTF-8 | cmp -s - "$src"
}

if roundtrip_ok data.csv; then
  echo "無損失 — 出力してよい"
else
  echo "損失発生 — どの文字が消えるか確認せよ" >&2
  iconv -c -f UTF-8 -t CP949 data.csv | iconv -f CP949 -t UTF-8 | diff - data.csv
fi
```

cp949へ出力するとき**必ず消えるもの**: 絵文字、簡体字中国語、字母に分解されたハングル。
**意外に生き残るもの**: ユーロ記号(`A2 E6`)、日本語の仮名。「韓国語以外の文字はすべて化ける」という当て推量は誤りだ。

## 7. CSVとBOM

```bash
# BOMを付ける(表計算にUTF-8だと知らせる)
printf '\xEF\xBB\xBF' | cat - body.csv > with_bom.csv

# BOMを外す
sed '1s/^\xEF\xBB\xBF//' with_bom.csv > no_bom.csv

# 先頭3バイトを確認
od -An -tx1 -N 3 with_bom.csv
```

```python
# BOMが先頭列名にU+FEFFとして付く事故を防ぐ
import csv

with open('report.csv', encoding='utf-8-sig', newline='') as f:   # sig が要点
    for row in csv.DictReader(f):
        print(row['이름'])        # utf-8 で開くとこの参照が None を返す
```

- BOMは**UTF-8の目印**だ。cp949ファイルに付けるとUTF-8としてもcp949としても妥当でないファイルになる
- 正しくUTF-8でデコードしてもBOMは `U+FEFF` 文字として**先頭列名の前に残る**
- 症状が**最初の列にだけ**出る。二列目・三列目は正常なので原因が見つけにくい
- `U+FEFF` は空白類ではないので、**前後の空白除去では取れない**

## 8. 妥当性検査だけでエンコーディングは確定できない

ハングル音節の**345字**は、cp949のバイト列がそのまま妥当なUTF-8でもある。どちらのエンコーディングでもエラーなく読めるテキストが実際に作れる。

```
징 -> cp949 C2 A1   同じバイトをUTF-8として読むと U+00A1
징짖짙짚 -> C2 A1 C2 A2 C2 A3 C2 A4   (utf-8 妥当 · cp949 妥当 · 両方)
```

→ 「UTF-8で試して失敗したらcp949」は**当て推量**だ。BOMが無ければ残りは確率にすぎない。**やり取りの仕様書にエンコーディングを明記することが唯一の根本解決だ。**

## 9. 境界ごとの責任 — 誰がエンコーディングを決めるか

| 境界 | 誰が決めるか | 罠 |
|---|---|---|
| ファイル保存 | 書くプログラム | 同じマシンでPythonはcp949、NodeはUTF-8で書いた |
| ファイル名 | オペレーティングシステム | 名前は境界で**再エンコードされる。**中身のようにバイトが保存されない |
| シェル出力 | コードページとプログラム | コードページとロケールが同じマシンで食い違うことがある |
| **パイプ** | **誰も決めない** | **宣言する場所が無い。**両端の合意をコードに書き込むしかない |
| HTTPヘッダ | サーバが宣言する | クライアントが**無視できる。**本文をバイトで受け取り自分でデコードする |
| CSVの先頭 | 書く側 | BOMが唯一のシグナル |
| 変換ツール | 実装 | **同じ名前でも動作が違う**(下記) |

## 10. エンコーディング名を信用しないこと

| 名前 | Python | GNU libiconv | 判断 |
|---|---|---|---|
| `cp949` | 拡張音節を2バイトで | 成功 | **韓国語にはこれを使う** |
| `euc-kr` | 拡張音節を**8バイト**の組み合わせ形で | **拒否** | 名前だけで信用しないこと |
| `johab` | 2バイト、別体系 | 成功 | ほとんど使われない |
| `utf-8` | 3バイト | 成功 | **内部標準にすること** |

同じ「EUC-KR」という名前で、一方は拒否し他方は8バイトに変換した。損失は無いが**バイト数が4倍**なので、桁数制限のある場所で切れる。**パイプラインで実際に使うツールに標本を通してみるべきだ。**

## 11. シェルと出力エンコーディング

| 設定 | 変えるもの | 変えないもの |
|---|---|---|
| `PYTHONIOENCODING` | 標準出力のエンコーディングだけ | **ファイルを開くときの既定エンコーディング** |
| `PYTHONUTF8=1` | 出力と `open()` の既定値 | — |
| `LC_ALL` / `LANG` | ツールがバイトを文字にまとめる方法(文字数、並び替え) | ファイルの中身 |
| `chcp` | コンソールのコードページ | パイプを流れるバイトの意味 |

- 画面出力だけが化けるなら `PYTHONIOENCODING`、ファイルの読み書きが問題なら**この変数は効かない**
- 最も確実なのは環境変数に頼らず、**ファイルを開くコードでエンコーディングを明示すること**
- 表現できない出力エンコーディングを指定すると化けるのではなく**プログラムが死ぬ。**終了コードが0でなく出力が空なら**データは無傷だ**
- Nodeにはこのスイッチが無く常にUTF-8で書いた → Pythonとパイプでつなぐとそこが事故地点になる

## 13. やってはいけないこと

- ❌ 化けた画面を見て**エンコーディング設定からいじること** — まず復元可否を判定する
- ❌ 疑わしいファイルをエディタで開いて**保存すること** — ①が②に変わる
- ❌ `//IGNORE` と**終了コード未確認**の組み合わせ — 文字が消えたのに成功と報告される
- ❌ 「例外が出なかったからUTF-8だ」 — あの345字の区間で静かに間違う
- ❌ エンコーディング名だけ合わせて**ツールの動作を確認しないこと**
- ❌ ファイルの**先頭だけ開く検査** — 切り捨ては末尾で起こる
- ❌ 復元不能と判定されたファイルに時間を使うこと — 原本を再取得する
