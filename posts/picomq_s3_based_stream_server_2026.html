계기 — 로컬 디스크 없는 분산 스트림의 재구성

전통적인 메시지 큐와 이벤트 스트리밍 플랫폼은 브로커 머신의 로컬 블록 디스크에 강력하게 결합되어 왔다. Apache Kafka를 비롯한 1세대 분산 로그 시스템은 고속 순차 쓰기(Sequential Write)와 OS 페이지 캐시의 제로 카피(Zero-Copy) 전송을 활용하여 처리량을 극대화했다. 그러나 이러한 설계는 클러스터 운영 측면에서 상당한 관리 비용을 요구한다. 브로커 노드가 교체되거나 장애를 겪을 때 파티션 데이터를 다른 디스크로 복제하는 리밸런싱(Rebalancing) 과정에서 막대한 네트워크 대역폭과 I/O 경합이 발생하며, 장기 보관을 위해 디스크 용량을 지속해서 프로비저닝해야 한다.

실무 엔지니어들이 로컬 브로커 디스크 기반 스트리밍에서 직면해 온 구조적 부담은 크게 세 가지로 요약된다.

  • 파티션 재분배 대역폭 소모: 노드 장애나 클러스터 축소 시 기가바이트에서 테라바이트에 달하는 과거 로그를 복제하느라 실시간 트래픽 처리가 지연된다.
  • 스토리지 용량 사전 프로비저닝: 트래픽 급증이나 장애로 인한 소비 지연에 대비해 브로커마다 넉넉한 고비용 블록 스토리지를 할당해 두어야 한다.
  • 인스턴스와 스토리지의 강한 결합: 컴퓨팅 리소스(CPU·메모리) 증설과 보관 용량 증설을 독립적으로 스케일링하기 어렵다.

클라우드 네이티브 환경에서 객체 스토리지(Object Storage)가 사실상 무한한 확장성과 저렴한 기가바이트당 비용, 99.999999999%에 달하는 높은 내구성을 검증받으면서, 스토리지 계층을 객체 스토리지로 완전히 이전하려는 시도가 이어지고 있다. 최근 발표된 Cloudflare K2가 전역 분산 엣지에서 R2를 직접 백엔드로 사용하는 서버리스 로그를 지향했듯이, 오픈소스 진영에서도 자체 인프라에서 운영할 수 있는 객체 스토리지 기반 스트리밍 엔진에 대한 관심이 고조되고 있다.

2026년 10월 GitHub에 공개된 PicoMQ는 Rust 언어로 작성된 실시간 스트림 서버로, 모든 이벤트 레코드와 쓰기 선행 로그(WAL, Write-Ahead Log)를 S3 호환 객체 스토리지에 직접 영속화하는 아키텍처를 채택했다. 서버 노드에는 교체 가능한 일시적 캐시만 남기고, 클러스터 합의와 메타데이터 관리는 외부 SQL 데이터베이스에 위임함으로써 브로커 상태를 완전히 걷어냈다. 이 글은 PicoMQ 저장소와 엔진의 공식 명세를 통해 객체 스토리지 위에 순서 있는 분산 스트림을 구축하는 설계 원리와 제약조건을 분석한다.

s3stream 엔진 — 객체 스토리지 파이프라인과 WAL 계층

PicoMQ의 핵심 데이터 저장은 독립된 엔진 저장소인 s3stream에 의해 제어된다. 객체 스토리지는 본질적으로 임의 위치 덮어쓰기나 원자적 추가(Append) 연산을 기본 API로 제공하지 않는다. 전통적인 S3 API는 전체 객체의 업로드(PutObject)나 멀티파트 업로드(Multipart Upload)만을 지원하므로, 개별 메시지가 들어올 때마다 객체를 생성하면 막대한 API 호출 비용과 지연시간이 발생한다.

s3stream 엔진은 계층화된 파이프라인을 통해 이 문제를 해결한다. 저장소 README에 명시된 내부 모듈 구성은 다음과 같은 계층 구조를 갖는다.

s3stream (facade: Config, builder)
                      └── s3stream-core (S3Storage pipeline, cache, compaction)
                            ├── s3stream-wal (object WAL, memory WAL)
                            └── s3stream-object (object format, ObjectStorage over object_store)
                                  └── s3stream-codec (record codec)

이 구조에서 데이터 흐름은 메모리 WAL에서 객체 WAL, 그리고 최종 객체 저장으로 이어진다.

  • s3stream (facade): 상위 호스트 계층이 손쉽게 엔진을 초기화할 수 있도록 Config 인터페이스와 빌더 패턴을 제공한다.
  • s3stream-wal (memory WAL): 들어오는 쓰기 레코드를 인메모리 버퍼에 즉각 수집하고 순차 오프셋 번호를 할당한다.
  • s3stream-wal (object WAL): 메모리에 누적된 레코드들을 S3 호환 스토리지의 WAL 세그먼트 객체로 신속하게 밀어내어 지속성을 확보한다.
  • s3stream-core: S3Storage 파이프라인을 총괄하며, 최근 기록된 이벤트의 고속 조회를 위한 인메모리 캐시를 관리한다.
  • s3stream-core (compaction): 다수의 작은 WAL 세그먼트 객체들을 주기적으로 읽어 대형 데이터 세그먼트로 병합 압축함으로써 S3 GET 비용을 절감한다.
  • s3stream-object: Rust 생태계의 표준 object_store 크레이트를 추상화하여, AWS S3, MinIO, RustFS, 로컬 파일 시스템(file://) 등 다양한 호환 스토리지 위에서 세그먼트 객체 형식을 균일하게 제어한다.
  • s3stream-codec: 직렬화된 이벤트 레코드의 헤더, 페이로드, 오프셋 체크섬을 인코딩 및 디코딩한다.

엔진은 호스트 환경에 대해 StreamManager와 ObjectManager 트레이트를 요구한다. 스트림 메타데이터와 객체 위치 관리를 엔진 외부로 완전히 분리하여, 호스트 계층이 저장소 선택과 분산 조정 로직을 자유롭게 결정할 수 있도록 설계되었다.

메타데이터 플레인 — SQLite 단일 노드에서 Postgres 클러스터까지

분산 스트리밍 시스템에서 가장 까다로운 영역은 스트림의 파티션 할당, 오프셋 번호의 단조 증가 보장, 그리고 노드 간 리더십 관리다. Apache Kafka는 초기에 Apache ZooKeeper에 의존하다가 KRaft라는 자체 Raft 합의 프로토콜로 전환했다. 이러한 자체 합의 계층은 외부 의존성을 줄여주지만, 브로커 프로세스 자체가 무거운 분산 합의 알고리즘을 수행해야 한다는 운영 부담을 수반한다.

PicoMQ는 자체 합의 프로토콜을 밑바닥부터 구현하는 대신, 이미 검증된 SQL 데이터베이스의 트랜잭션 보장을 메타데이터 플레인의 기반으로 삼았다. 이는 시스템의 실행 환경에 따라 극단적인 유연성을 제공한다.

단일 노드 모드: 임베디드 SQLite

개발 환경이나 소규모 독립 엣지 기기에서는 외부 데이터베이스 서버 없이 로컬 SQLite 파일 하나만으로 완결된 스트림 서버를 구동할 수 있다. pico serve --meta-url sqlite:./data/meta.db --storage=-2@file://./objects 명령은 로컬 SQLite에 오프셋 메타데이터를 기록하고, 로컬 디렉터리를 가상 객체 스토리지로 사용하여 어떠한 외부 인프라 없이도 완전한 스트림 API를 제공한다.

다중 노드 클러스터 모드: PostgreSQL

다중 노드로 확장할 경우 메타데이터 URL을 PostgreSQL로 지정한다(postgres://user:pass@host:5432/picomq). 클러스터에 참여하는 모든 PicoMQ 노드는 공유된 PostgreSQL 테이블을 참조하여 스트림의 등록 상태, 현재 오프셋 진행 상황, 노드별 소유권(Ownership)을 동기화한다.

  • 무상태 노드 구조: 스트림 데이터를 관리하는 워커 노드는 언제든지 강제 종료되거나 새로 추가될 수 있다. 모든 영구 상태는 SQL과 S3에 격리되어 있으므로 노드 자체의 디스크 백업이나 복구가 불필요하다.
  • 분산 잠금과 소유권: 특정 스트림에 대한 동시 쓰기 충돌을 방지하기 위해 노드는 SQL 트랜잭션을 통해 소유권을 획득한다. 소유권 전환 시 세대 번호(Epoch)를 갱신하여 이전 소유 노드가 지연된 쓰기 연산으로 데이터를 오염시키는 스플릿 브레인(Split-Brain) 현상을 원천 방지한다.
  • 신속한 장애 복구: 노드가 비정상 종료되면 다른 노드가 SQL 상에서 만료된 소유권을 인수하여 클라이언트 트래픽을 즉각 수용한다.
  • 수평적 처리 확장: 스트림 수가 증가할 때 새로운 PicoMQ 노드를 투입하면 SQL 테이블의 스트림 소유권이 자연스럽게 분산된다.
  • 계약 검증 테스트: 공식 소스코드에는 picomq-sql 크레이트의 pg_contract 및 pg_e2e 테스트가 포함되어 있어, PostgreSQL의 트랜잭션 격리 수준에서 소유권 이전과 오프셋 갱신이 계약대로 엄격하게 유지되는지 검증한다.

프로토콜 프론트엔드 — HTTP·Durable Streams·Kafka 와이어 프로토콜

PicoMQ의 프로토콜 프론트엔드는 단일 엔진 위에서 복수의 전송 프로토콜을 동시에 수용하도록 설계되었다. picomq/ 호스트 계층은 HTTP API와 표준 카프카 프로토콜을 병행하여 서비스한다.

# pico CLI를 통한 스트림 생성 및 레코드 추가
                    pico create /streams/orders --content-type text/plain
                    seq 1 1000 | pico append /streams/orders --batch 100
                    
                    # 스트림 내용 조회 및 실시간 tail
                    pico read /streams/orders
                    pico tail /streams/orders -f
                    
                    # 스트림 종료 및 삭제
                    pico close /streams/orders && pico delete /streams/orders

클라이언트 관점에서 접근 가능한 인터페이스는 세 가지 갈래로 나뉜다.

  • 선언적 스트림 관리 (PUT): PUT /streams/{name} 엔드포인트를 호출하여 컨텐츠 타입과 함께 새로운 스트림을 즉시 생성한다.
  • 배치 레코드 추가 (POST): POST /streams/{name}을 통해 바이너리 또는 텍스트 데이터를 배치 단위로 전송하여 네트워크 오버헤드를 줄인다.
  • 오프셋 기반 읽기 (GET): GET /streams/{name} 요청에 시작 오프셋을 지정하여 과거 이벤트 기록을 순차적으로 읽어온다.
  • 실시간 이벤트 스트리밍 (SSE 및 롱 폴링): Server-Sent Events(SSE)나 롱 폴링을 통해 새로운 이벤트가 도착하는 즉시 클라이언트에게 푸시한다.
  • Durable Streams 개방형 규격: 웹 생태계에서 점진적으로 논의되는 영속 스트림 인터페이스 표준을 준수하여 상호운용성을 확보한다.
  • Kafka Wire Protocol 지원: 기존 엔터프라이즈 환경의 Kafka 클라이언트 라이브러리가 PicoMQ 서버를 Kafka 브로커로 인식하고 직접 통신할 수 있다.

PicoMQ 공식 README와 s3stream 명세가 공식적으로 약속하는 속성과, 그로 인해 발생하는 아키텍처적 한계를 비교 정리한다.

시스템 속성 README 명세 설명 아키텍처적 의미 미확인 항목
영속성 계층 S3 호환 객체 스토리지에 모든 레코드와 WAL 저장 브로커 로컬 디스크 불필요, 스토리지 내구성을 S3로 전면 위임 단일 객체의 최대 크기 및 기본 세그먼트 롤링 기준
메타데이터 합의 SQLite (단일 노드) 또는 PostgreSQL (클러스터) 자체 Raft/Paxos 프로토콜을 배제하고 관계형 DB 트랜잭션으로 대체 PostgreSQL 커넥션 풀 고갈 시 클러스터 처리량 한계
장애 복구 모델 노드 장애 시 데이터 재분배 없이 라우팅 전환으로 수 초 내 복구 데이터가 노드에 묶여 있지 않아 소유권 재할당만으로 복구 완결 장애 감지 하트비트 타임아웃 기본 설정값
스트림 단위 설계 세션·주문·기기마다 작은 스트림을 분리하여 수백만 개 운영 지향 광범위한 단일 파티션 샤딩 대신 다수 세분화 스트림 모델 권장 수백만 스트림 구동 시 실제 메모리 및 DB 인덱스 오버헤드
프로토콜 호환성 Pico HTTP, Durable Streams, Kafka Wire Protocol 제공 다양한 생태계 클라이언트와의 연결 장벽 제거 지원되는 Kafka API 버전 목록 및 미구현 연산자

위 표가 나타내는 핵심적인 통찰은 스트림의 생명주기와 소유권이 물리적 인프라와 철저하게 분리되어 있다는 점이다. 전통적인 브로커 클러스터에서는 토픽과 파티션 수가 수천 개를 넘어가면 메타데이터 관리와 파일 디스크립터 한계로 인해 성능 저하가 발생한다. 반면 PicoMQ는 사용자 세션이나 개별 작업 단위로 스트림을 쪼개어 수백만 개를 운영하는 마이크로 스트림 모델을 전제하고 있다.

단일 바이너리와 Docker Compose — lite에서 cluster까지의 배포 구성

PicoMQ는 Rust 언어로 컴파일된 단일 바이너리(pico) 안에 서버 엔진, 클라이언트 CLI, 벤치마크 도구, 그리고 관리자 대시보드(Admin Dashboard)를 모두 통합했다. 배포의 복잡도를 낮추기 위해 저장소의 harness/aio 디렉터리에 다양한 Docker Compose 템플릿을 사전 정의해 두었다.

배포 프로파일 메타데이터 백엔드 객체 스토리지 계층 노드 구성 및 기본 포트
compose.lite.yml SQLite (로컬 파일) 로컬 파일시스템 (file://) 단일 노드, 의존성 제로 로컬 테스트 환경
기본 compose (aio) PostgreSQL 컨테이너 RustFS (S3 호환 고성능 엔진) 1개 노드, 포트 4437 (Pico API), 포트 9090 (대시보드)
compose.cluster.yml PostgreSQL 컨테이너 RustFS 컨테이너 2개 노드 클러스터, 포트 4437 및 4438 동시 노출
compose.connectors.yml 공유 메타데이터 공유 객체 스토리지 외부 커넥터 런타임 추가 바인딩, 포트 8081
harness/byo 외부 기존 PostgreSQL 외부 기존 S3/호환 스토리지 운영 환경 사내 인프라 연결 프로파일 (.env 설정)

실제 로컬 클러스터를 구동하는 절차는 간결하다.

cd harness/aio
                    cp .env.example .env
                    
                    # PostgreSQL과 RustFS를 포함한 2개 노드 클러스터 실행
                    docker compose -f compose.cluster.yml up --build
                    
                    # 부하 테스트 실행 (HTTP/2 기준 4개 연결, 4개 스트림, 60초간 벤치마크)
                    pico --http2 bench -b 1024 -w 512 --connections 4 --streams 4 -d 60

배포 환경 구성 시 숙지해야 할 세부 운영 규칙은 다음과 같다.

  • 환경 변수 일대일 매핑: 모든 CLI 플래그는 동일한 이름의 PICO_* 환경 변수로 완벽히 대체 가능하다.
  • 관리 인터페이스 분리: 헬스체크 및 관리자 대시보드는 기본적으로 9090 포트에 격리되어 데이터 트래픽과의 간섭을 방지한다.
  • BYO(Bring Your Own) 프로파일: 기존 사내 RDS PostgreSQL과 AWS S3 버킷 정보를 .env 파일에 주입하여 즉시 클라우드 운영 환경으로 전환할 수 있다.
  • 자체 완결형 벤치마크 도구: 별도의 외부 부하 생성기 없이 pico bench 명령으로 스트림 처리량과 커넥션 포화도를 직접 측정할 수 있다.

보안과 운영 한계 — 기본 비활성화된 인증과 지연시간 트레이드오프

PicoMQ 아키텍처의 강력한 단순성 이면에는 실무 엔지니어가 반드시 숙지해야 할 명확한 트레이드오프가 존재한다.

  • 인증 기본 비활성화와 원격 바인딩 위험: 공식 README에 명시되었듯이 PicoMQ는 기본적으로 인증(Authentication)이 꺼져 있다. 노드를 루프백 주소(127.0.0.1)가 아닌 공용 인터페이스에 바인딩할 경우, 명시적으로 --auth required 플래그를 추가하거나 --insecure-allow-remote 플래그를 선언해야만 구동된다. 인가되지 않은 엔드포인트 노출 시 악의적인 쓰기 및 스트림 파괴 공격에 노출될 수 있으므로, 실무 환경에서는 반드시 TLS 종료 프록시나 mTLS 인증 체계 뒷단에 배치해야 한다.
  • 네트워크 왕복에 따른 쓰기 지연시간: 로컬 NVMe SSD에 직접 기록하는 Kafka와 달리, 객체 스토리지와의 네트워크 I/O 왕복이 쓰기 확정(Acknowledge) 경로에 관여한다. 인메모리 WAL과 배치 처리를 통해 처리량을 확보하더라도, 단일 쓰기의 p99 지연시간은 수 밀리초에서 수십 밀리초 수준으로 로컬 디스크 기반 시스템보다 높을 수밖에 없다. 따라서 마이크로초 단위의 초저지연(Ultra Low Latency)을 요구하는 고빈도 매매 시스템보다는, 높은 내구성과 손쉬운 확장이 중요한 사용자 세션 로그, 감사 추적, AI 에이전트 대화 이력 보관에 적합하다.
  • 관리 포트 분리: 헬스체크(/health)와 준비 상태 검사(/ready), 그리고 웹 대시보드는 --admin-listen(기본값 127.0.0.1:9090)으로 별도 분리되어 있어, 데이터 트래픽과 운영 트래픽의 간섭을 최소화하도록 설계되었다.
  • PostgreSQL 쓰기 병목 가능성: 스트림 메타데이터와 오프셋 상태가 매우 높은 빈도로 갱신되는 워크로드의 경우 메타데이터 RDBMS가 확장성의 병목이 될 수 있으므로 세심한 커넥션 풀링과 인덱스 튜닝이 요구된다.

확인하지 못한 것

  • README 본문 상의 정량적 지연시간(밀리초) 및 초당 레코드 처리량 공식 벤치마크 수치. 공식 README에는 벤치마크 명령(pico --http2 bench)만 기술되어 있으며 확정된 측정 결과표는 기재되어 있지 않다.
  • Kafka Wire Protocol의 세부 지원 API 목록. 프로토콜 지원 여부는 명시되었으나, 트랜잭션 API나 압축 코덱 등 상세 사양의 구현 완성도는 확인하지 못했다.
  • s3stream 엔진의 세그먼트 압축(Compaction) 트리거 주기 및 임계치 설정의 기본값.
  • PostgreSQL 메타데이터 플레인에서 수백만 개 이상의 스트림 테이블이 생성되었을 때의 쿼리 지연시간 특성.
  • RustFS 외에 Google Cloud Storage나 Azure Blob Storage 호환 계층에서의 공식 테스트 통과 여부.
