シェルのクォート規則 - どの引用符が何を止めるのか

シングルクォート・ダブルクォート・ANSI-C クォートを実行出力で切り分ける

2026-07-29 開発・インフラ

はじめに: 引用符二つの欠落がディレクトリを空にした

空の作業用ディレクトリを作り、ファイルを三つ置いた。二つは普通の名前で、一つは名前そのものがアスタリスク一文字である。そのアスタリスクのファイルだけを消そうとして、名前を変数に入れて rm に渡した。結果はこうなった。

$ ls -1
*
keep1.txt
keep2.txt

$ f='*'
$ rm $f
$ ls -1
(空)

消すつもりだったのはファイル一つなのに、ディレクトリが丸ごと空になった。打ち間違えたわけではない。rm がおかしいわけでもない。シェルが $f を * に置き換え、その * をもう一度ファイル名の一覧に膨らませただけである。引用符を二つ付けていれば起きなかった。

この種の事故のあとによく返ってくる助言が「変数には引用符を付けなさい」だ。正しいが規則ではない。どの引用符を付けるべきか、その引用符が何を止めて何を通すのかを教えてくれないからである。だから同じ人が次は awk のプログラムをダブルクォートで囲み、ドル記号が食われる事故を起こす。方向は逆だが原因は同じだ。クォートがどのスイッチなのかを知らないのである。

この記事は定義を並べない。シングルクォート・ダブルクォート・バックスラッシュ・ANSI-C クォートがそれぞれ何を止めるのかを、すべて実行して出力で示す。文法の根拠は GNU Bash Reference Manual と POSIX 仕様で確認し、挙動は作業用ディレクトリで直接動かした。本文の出力はすべて実際に画面に出たものである。最後に状況 → 使うべきクォート → 理由を一枚の判断表にまとめる。

範囲をあらかじめ狭めておく。空白入りのファイル名を find と xargs で扱う実務的な組み合わせはfind・xargs の空白と改行の罠で別に扱った。この記事の関心はクォート構文そのものである。同じスクリプトを二度実行してよいかは二度実行しても壊れないスクリプトに、実行前に結果を知れるかはまともな --dry-run の作り方にある。

2. シェルが一行を読む順序 - クォートはどの段階を切るのか

クォートがややこしく感じるのは「引用符が文字列を作る」と考えているからだ。シェルにおいて引用符は文字列を作らない。もともと決まっている処理段階のいくつかを切るスイッチである。だからどのスイッチがどの段階を切るのかさえ分かれば、すべて予測できる。

bash がコマンド一行を実行する前に通る順序は、おおよそ次のとおりだ。

一行の入力
  1. ブレース展開          a{1,2}   ->  a1 a2
  2. チルダ展開            ~        ->  ホームディレクトリ
  3. パラメータ展開・コマンド置換・算術展開
                           $var  $(cmd)  `cmd`  $((1+1))
  4. 単語分割              IFS を基準にフィールドへ分割   <- 空白事故はここ
  5. パス名展開(グロブ)     *  ?  [...]  ->  ファイル名群   <- アスタリスク事故はここ
  6. クォート除去          残っている引用符文字を取り除く
  -> 実行

要点は4段階と5段階が3段階の後に来ることだ。変数を展開した結果が、さらに分割され、さらに膨らみうるという意味である。はじめに挙げた事故がまさにこれだ。$f が * になり(3段階)、その * がファイル一覧になった(5段階)。

クォートはこの順序のどこかを切る。どれがどこを切るのかが、この記事のすべてである。

形式$ 展開バッククォートバックスラッシュ! 履歴単語分割グロブ
クォートなし通す通す通す通す起きる起きる
シングル '...'止める止める止める止める止める止める
ダブル "..."通す通す一部通す対話時のみ通す止める止める
ANSI-C $'...'止める止める解釈する止める止める止める
バックスラッシュ \x止める止める止める止める止める止める

表で注目すべきは右端の二列だ。シングルであれダブルであれ、単語分割とグロブは同じように止める。現場の事故の九割はこの二列で起きる。だから「どの引用符を使うか」で悩み始めた時点で半分は解決しており、本当の問題は引用符をまったく付けていない箇所である。

3. シングルクォート - 例外のないリテラル

シングルクォートの規則は一つだけだ。中のすべての文字が文字どおりになる。例外はない。Bash Reference Manual はこう書いている。

Enclosing characters in single quotes preserves the literal value of each character within the quotes. A single quote may not occur between single quotes, even when preceded by a backslash.

実行して確かめた。同じ文字列をシングルクォートで囲んで printf に渡している。

$ printf '%s\n' '$name'
$name
$ printf '%s\n' '`printf ran`'
`printf ran`
$ printf '%s\n' '\n  \t  \\'
\n  \t  \\
$ printf '%s\n' '!!'
!!
$ printf '%s\n' 'a "b" c'
a "b" c
$ printf '%s\n' '${name}  $(printf ran)  $((1+1))'
${name}  $(printf ran)  $((1+1))

展開は一つも起きていない。バックスラッシュすら特別でない点が重要だ。\\ が \\ のまま出ている。ダブルクォートではこれが \ 一個に減る(4節)。

だからシングルクォートはほかのプログラムの文法をシェルから守るときに使う。awk のプログラム、sed の式、正規表現、find のパターン、別のシェルに渡すコマンド文字列がすべてここに当たる。

代わりに代償がある。シングルクォートの中にシングルクォートは入れられない。バックスラッシュで逃がそうとする試みがなぜ失敗するのかを実行で見るとこうなる。

$ printf '%s\n' 'it\'"'"'s'
it\'s

$ bash -c "printf '%s\n' 'it\'s'"
bash: -c: line 1: unexpected EOF while looking for matching `''

一行目は奇妙に見えるが単純だ。'it\' で文字列がバックスラッシュの後ろの引用符で終わり、バックスラッシュは文字として残った。二つ目の例ではその後ろで引用符の対応が取れず、解析そのものが失敗した。規定どおりである。バックスラッシュはシングルクォート内で退避文字ではない。

したがってシングルクォートの中にシングルクォートを入れるには、いったん閉じて別の方法で一文字を足し、また開くしかない。四つの書き方があり、結果はすべて同じだ。

$ printf '%s\n' 'it'"'"'s'      # 閉じて、ダブルクォートで一文字、また開く
it's
$ printf '%s\n' 'it'\''s'       # 閉じて、バックスラッシュで一文字、また開く
it's
$ printf '%s\n' "it's"          # いっそダブルクォートで囲む
it's
$ printf '%s\n' $'it\'s'        # ANSI-C クォート (8節)
it's

$ printf '%s' 'it'\''s' | od -c
0000000   i   t   '   s
0000004

最後の od -c が証拠である。シェルが実際に渡したバイトは it's の四文字だ。よく「引用符退避のイディオム」と呼ばれる '\'' は魔法ではなく、閉じる・一文字・開くの三片がくっついているだけである。

4. ダブルクォートが通す四つ

ダブルクォートはシングルクォートにちょうど四つの穴を開ける。Bash Reference Manual の記述はこうだ。

Enclosing characters in double quotes preserves the literal value of all characters within the quotes, with the exception of $, `, \, and, when history expansion is enabled, !.

3節とまったく同じ文字列をダブルクォートに替えて動かした結果である。

$ name=world
$ printf '%s\n' "$name"
world
$ printf '%s\n' "`printf ran`"
ran
$ printf '%s\n' "\n  \t  \\"
\n  \t  \
$ printf '%s\n' "!!"
!!
$ printf '%s\n' "a "b" c"
a b c
$ printf '%s\n' "${name}  $(printf ran)  $((1+1))"
world  ran  2

行ごとに見る。

  • $name が world になった — パラメータ展開は通る
  • バッククォートの中が実行されて ran になった — コマンド置換は通る
  • \\ が \ 一個に減った — バックスラッシュは一部通る
  • \n と \t はそのままだ — バックスラッシュは任意の文字の前で特別になるわけではない
  • "a "b" c" が a b c になった — ダブルクォートが途中で切れて開き直した

三つ目と四つ目が最も多くの人をつまずかせる。ダブルクォートの中でバックスラッシュは決まった五文字の前でだけ退避文字として働く。マニュアルが一覧を明示している。

The backslash retains its special meaning only when followed by one of the following characters: $, `, ", \, or newline. Within double quotes, backslashes that are followed by one of these characters are removed. Backslashes preceding characters without a special meaning are left unmodified.

だから "\n" は改行ではなくバックスラッシュと n の二文字である。改行を入れたいなら printf の書式文字列に任せるか、8節の ANSI-C クォートを使う。

四つ目の感嘆符は条件付きだ。履歴展開は既定では対話シェルでのみ有効になる。スクリプトでは切れているので問題ないが、端末に直接打ったコマンドでは今も起きる。二行を対話 bash に食わせて確かめた。

$ echo hello there
hello there
$ echo "wow!!"
wowecho hello there          <- ダブルクォート内の !! が直前のコマンドに置換された
$ echo 'wow!!'
wow!!                        <- シングルクォートは止める

同じ二行を POSIX モードの対話シェルに食わせると結果が変わる。マニュアルが書いている例外そのものだ。

$ bash --norc -i
$ echo "wow!!"
wowecho hello there

$ bash --norc --posix -i
$ echo "wow!!"
wow!!

まとめるとダブルクォートは「値は入れたいが分割はされたくない」ための道具である。変数やコマンド置換を中に置きたいときに使い、それ以外はシングルクォートが安全だ。

5. クォートなしの展開 - 事故の大半はここで起きる

ここがこの記事の中心である。前の二節は「何が入るか」を扱い、この節は「いくつに分かれるか」を扱う。現場の事故はほぼすべてこちらだ。

確かめ方は単純である。引数を受け取って個数と中身を出す関数を一つ作り、同じ変数をクォートして一度、しないで一度渡す。

count() {
  printf 'argc=%d\n' "$#"
  local i=1
  for a in "$@"; do printf '  [%d] <%s>\n' "$i" "$a"; i=$((i+1)); done
}

ディレクトリには my report.txt・notes.txt・keep.txt の三ファイルがある。

$ f='my report.txt'

$ count $f
argc=2
  [1] <my>
  [2] <report.txt>

$ count "$f"
argc=1
  [1] <my report.txt>

$ wc -c $f
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 total
exit=1

$ wc -c "$f"
0 my report.txt
exit=0

値一つが引数二つに割れ、その結果 wc は存在しないファイルを二つ探した。終了コードも1である。これはまだましなほうだ。エラーが目に見えるからである。本当に危険なのは静かに成功する場合だ。

$ pat='*.txt'

$ count $pat
argc=3
  [1] <keep.txt>
  [2] <my report.txt>
  [3] <notes.txt>

$ count "$pat"
argc=1
  [1] <*.txt>

$ empty=''
$ count $empty
argc=0
$ count "$empty"
argc=1
  [1] <>

三つのことが一度に見える。

  • クォートしていない $pat がファイル三つに膨らんだ。値は明らかに一個だった
  • 面白いことに my report.txt は分割されず一フィールドのまま残った。単語分割がグロブより先に起きるので、グロブの結果は再分割されない
  • クォートしていない空の値は引数リストから消える。クォートすれば空文字列の引数一つとして残る

最後の項目が条件文でどう爆発するかが有名な罠である。

$ empty=''
$ if [ -n $empty ]; then echo 'NON-EMPTY'; else echo 'empty'; fi
NON-EMPTY          <- 誤り

$ if [ -n "$empty" ]; then echo 'NON-EMPTY'; else echo 'empty'; fi
empty              <- 正しい

$ two='a b'
$ [ -n $two ]
bash: [: a: binary operator expected
exit=2
$ [ -n "$two" ]
exit=0

一つ目は [ -n ] になってしまった。引数が一つだけの test はその引数が空文字列でなければ真なので、-n という文字列そのものが真と評価された。二つ目は [ -n a b ] になって構文エラーだ。値の中身しだいで偽の真・構文エラー・正常が入れ替わる。

そしてはじめに挙げた事故である。クォートなしの展開がグロブまで到達すると、取り返しのつかない結果になる。

### ディレクトリの状態 (アスタリスクはファイル名そのもの)
*
keep1.txt
keep2.txt

### A) rm $f    (f='*')
$ rm $f
$ ls -1
    (空)

### B) rm -- "$f"    同じ値、クォートだけが違う
$ rm -- "$f"
$ ls -1
    keep1.txt
    keep2.txt

A と B の違いは引用符二つと -- だけだ。結果は全削除と一件削除である。なお -- はクォートとは別の仕組みで、「ここからはオプションではなく被演算子」という印だ。名前がダッシュで始まるファイルを守ってくれる。

ループ変数も同じ規則を受ける。一覧を文字列一つに入れた時点で負けている。

$ list='keep1.txt keep2.txt'
$ for f in $list; do printf ' <%s>' "$f"; done
 <keep1.txt> <keep2.txt>

$ arr=('quarterly report.txt' 'keep1.txt')
$ for f in "${arr[@]}"; do printf ' <%s>' "$f"; done
 <quarterly report.txt> <keep1.txt>

文字列の一覧は空白入りの名前を表現する方法がない。一覧が必要なら配列を使う(7節)。なおファイル名に改行が入ると行単位で数える方式そのものが崩れる。これはこの記事の範囲外なのでfind・xargs の空白と改行の罠に譲る。ただしシェルが見る個数と ls が出す行数が違うことだけは確かめておく。

$ ls -1 | cat -A
    *$
    keep1.txt$
    keep2.txt$
    two$
    lines.txt$

$ n=0; for f in *; do n=$((n+1)); done; echo "count=$n"
    count=4

行は五つ、ファイルは四つだ。Bash マニュアルの Word Splitting 節は分割対象をこう限定している。

The shell scans the results of parameter expansion, command substitution, and arithmetic expansion that did not occur within double quotes for word splitting. Words that were not expanded are not split.

「ダブルクォートの中で起きなかった」という条件がすべてである。ダブルクォート一組が4段階を丸ごと飛ばす。

6. 位置パラメータの四形式 - 引数を数える

スクリプトが受け取った引数をほかのコマンドにそのまま渡す作業は毎日ある。ところが渡し方が四通りあり、結果はすべて違う。引数四つを関数に渡して $# で数えた。引数は 'a b'・'c'・''(空文字列)・'d*e' である。

$ pass 'a b' 'c' '' 'd*e'

quoted @:  argc=4 | <a b> <c> <> <d*e>
bare @:    argc=4 | <a> <b> <c> <d*e>
quoted *:  argc=1 | <a b c  d*e>
bare *:    argc=4 | <a> <b> <c> <d*e>

クォートした "$@" だけが元の四つをそのまま渡した。クォートなしの $@ も個数は4だが中身が食い違っている。a b が二つに割れ、空の引数が消えたので、偶然に数だけが合ったのである。この種の偶然がバグを長く隠す。

同じ実験を IFS をカンマに変えてもう一度行った。

$ IFS=,
$ pass 'a b' 'c' '' 'd*e'

quoted @:  argc=4 | <a b> <c> <> <d*e>
bare @:    argc=4 | <a b> <c> <> <d*e>
quoted *:  argc=1 | <a b,c,,d*e>
bare *:    argc=4 | <a b> <c> <> <d*e>

### 引数が一つもないとき
quoted @:  argc=0 |
bare @:    argc=0 |
quoted *:  argc=1 | <>
bare *:    argc=0 |

二つのことが表れる。第一に "$*" がつなぐ文字がIFS の先頭文字に変わった。第二に引数がないとき "$@" は引数0個だが "$*" は空文字列の引数1個である。この差が set -u や引数個数の検査で静かに違う結果を生む。

実際のコマンドに当てるとこうなる。

$ set -- 'my report.txt' 'notes.txt'

$ wc -c "$@"
0 my report.txt
0 notes.txt
0 total

$ wc -c $@
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 notes.txt
0 total

$ wc -c "$*"
wc: 'my report.txt notes.txt': No such file or directory
形式生じるフィールド数空の引数空白入りの引数使う場所
"$@"引数の個数そのまま保存保存引数転送の既定値
$@分割・グロブ後の個数消える割れるほぼ出番なし
"$*"常に1空白として保存保存ログ一行にまとめるとき
$*分割・グロブ後の個数消える割れるほぼ出番なし

規則は短い。引数を渡すときは "$@"、人に見せる一行を作るときは "$*"。クォートなしの二形式は実務でほとんど使い道がない。

7. 配列とクォート - 原型を守るのは一つだけ

配列も構造は同じだ。四つの展開方法があり、原型を守るのは一つである。要素四つの配列で確かめた。

$ arr=('my report.txt' 'notes.txt' '' 'a*b')

"${arr[@]}"      argc=4 | <my report.txt> <notes.txt> <> <a*b>
${arr[@]}        argc=4 | <my> <report.txt> <notes.txt> <a*b>
"${arr[*]}"      argc=1 | <my report.txt notes.txt  a*b>
${arr[*]}        argc=4 | <my> <report.txt> <notes.txt> <a*b>

$ echo "${#arr[@]}"     # 要素の個数
4
$ echo "${#arr[0]}"     # 要素0の文字数
13

${#arr[@]} と ${#arr[0]} がまったく違う値を返すことも合わせて見ておくとよい。前者は個数、後者は長さである。

コマンドラインを組み立てるとき配列がなぜ必要かは、次の対比が示す。

$ opts=(-c)
$ files=('my report.txt' 'notes.txt')

$ wc "${opts[@]}" "${files[@]}"
0 my report.txt
0 notes.txt
0 total

$ wc ${opts[*]} ${files[*]}
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 notes.txt
0 total

そして配列の代わりにコマンドライン全体を文字列変数に入れるという、よくあるアンチパターンがある。これがなぜ動かないのかが、クォートの本質を最もよく示す。

$ cmdline='wc -c "my report.txt"'
$ $cmdline
wc: '"my': No such file or directory
wc: 'report.txt"': No such file or directory
exit=1

引用符は確かに入れたのに、なぜ動かないのか。クォートは変数の値の中では働かないからである。シェルはソースコードを読むときに引用符を処理し、その処理はもう終わっている。変数の中に残った引用符はただの文字だ。だから wc が受け取った引数に引用符がそのまま付いている。

覚えておく一文
引用符は値ではなくコードに付く。変数の値に入っている引用符はシェルにとって何の意味もない。コマンドラインを動的に作る必要があるなら文字列ではなく配列を使い、それでも足りなければ printf %q(12節)でシェル自身にクォートを付けさせる。

なお bash 4.4 より前は set -u の下で空の配列を "${arr[@]}" と展開するとエラーになった。今回の環境(5.2.37)では次のとおり正常である。

$ empty=()
$ set -u
$ show "${empty[@]}"
argc=0 |
survived: exit=0

8. ANSI-C クォート - シングルクォートに開いた唯一の穴

シングルクォートはすべてを止めると書いた。その規則から外れる形式が一つある。前にドル記号を付けた $'...' である。マニュアルの表現では「特別な種類のシングルクォート」で、変数は依然として展開しないがバックスラッシュの退避表記は解釈する。

$ printf '%s' 'A\tB\nC' | od -c
0000000   A   \   t   B   \   n   C
0000007

$ printf '%s' $'A\tB\nC' | od -c
0000000   A  \t   B  \n   C
0000005

同じ文字列が7バイトと5バイトである。$'...' のほうは本物のタブと本物の改行に変わった。マニュアルが対応表記を明示している。八進 \nnn、十六進 \xHH、Unicode の \uHHHH と \UHHHHHHHH、そして \a \b \e \f \n \r \t \v \\ \' \" \? だ。実際に動かして確かめた。

$ printf '%s' $'\x41\x42' | od -c
0000000   A   B
$ printf '%s' $'\101\102' | od -c
0000000   A   B
$ printf '%s' $'é' | od -c
0000000 303 251
$ printf '%s' $'\e[0m' | od -c
0000000 033   [   0   m
$ printf '%s' $'\cG' | od -c
0000000  \a

変数は展開しないという点は必ず覚えておく必要がある。

$ name=world
$ printf '%s\n' $'hello $name'
hello $name

使いどころははっきりしている。区切り文字にタブや改行を入れる必要があるときだ。IFS の設定、sort -t、cut -d、join -t といった場所である。ただし $'...' はPOSIX 仕様にない。dash で動かすと展開そのものが起きない。

$ dash -c "printf '%s' \$'A\tB' | od -c"
0000000   $   A   \   t   B
0000005

ドル記号が文字として残り \t も二文字のままだ。移植性が必要なら printf で作って変数に入れる回避策を使う。結果が同じであることをバイトで確認した。

$ TAB=$(printf '\t')
$ NL=$(printf '\nx'); NL=${NL%x}
$ printf '%s' "A${TAB}B${NL}C" | od -c
0000000   A  \t   B  \n   C
0000005

NL を作るとき x を付けて外しているのは、コマンド置換が末尾の改行をすべて取り除くからである(9節)。この二行がないと NL は空文字列になる。

9. コマンド置換とバッククォート - 内側のクォートは外と無関係

$(...) の中のクォートは外側のクォートとまったく別である。ダブルクォートの中にあっても、内側は新しい文脈だ。

$ printf '%s\n' "outer $(printf '%s' 'inner literal $HOME') outer"
outer inner literal $HOME outer

$ printf '%s\n' "$(printf '[%s]' "$(printf '%s' 'deep')")"
[deep]

外側がダブルクォートなのに内側のシングルクォートが正常に働き $HOME が生き残った。ダブルクォートを三重に重ねた入れ子もそのまま通った。入れ子にするとき引用符を数えなくてよいのが $(...) の実用的な利点である。

バッククォートは違う。同じ入れ子をバッククォートで書くと解析が失敗する。

$ bash -c 'printf "%s\n" "`printf "[%s]" "`printf "%s" deep`"`"'
bash: command substitution: line 1: unexpected EOF while looking for matching `"'
bash: command substitution: line 1: unexpected EOF while looking for matching `"'
printf %s deep

バッククォートは開く記号と閉じる記号が同じ文字なので、入れ子の境界が分からない。そのうえバッククォートの中ではバックスラッシュがもう一枚剥がれる。この差は実際に値を変える。

$ printf '%s\n' "$(printf '%s' 'a\tb')"
a\tb
$ printf '%s\n' "`printf '%s' 'a\tb'`"
a\tb

$ printf '%s\n' "$(printf 'a\\b')"
a\b
$ printf '%s\n' "`printf 'a\\b'`"
a

最後の二行が分かれた。$(...) は a\b、バッククォートは a である。バッククォートがバックスラッシュを一つ先に食って printf 'a\b' になり、printf がそれをバックスペースとして解釈した。整理するとバッククォートを避ける理由は三つだ。

  • 入れ子にできない — 開く記号と閉じる記号が同じ文字なので境界が決まらず、上の実行のように解析が失敗する
  • バックスラッシュをもう一枚食う — 同じ引数を渡したのに結果の文字列が変わった
  • 読みにくい — バッククォートとシングルクォートはフォントによってほとんど区別できない

POSIX 仕様は両方の形式を規定しており、dash でも $(...) は問題なく動く。新しいコードでバッククォートを使う理由はない。

コマンド置換の結果もクォートしなければ分割され膨らむ。変数とまったく同じ規則である。

$ show $(printf '%s\n' 'my report.txt')
argc=2 | <my> <report.txt>
$ show "$(printf '%s\n' 'my report.txt')"
argc=1 | <my report.txt>

$ show $(printf '%s\n' '*.txt')
argc=1 | <my report.txt>
$ show "$(printf '%s\n' '*.txt')"
argc=1 | <*.txt>

### 末尾の改行はクォートの有無に関係なくすべて切られる
$ printf '%s' "$(printf 'x\n\n\n')" | od -c
0000000   x
0000001

三つ目の例がとりわけ危険だ。コマンドは *.txt という文字列を出力したのに、クォートを外したせいでそれがディレクトリにあったファイル名に変わった。元の文字列は画面のどこにも残らない。

10. IFS - 何が境界かを決める変数

単語分割の基準は IFS である。既定値は空白・タブ・改行で、変えれば分割結果が丸ごと変わる。ところがダブルクォートで囲んだ値は IFS をいくら変えても影響を受けない。分割そのものが起きないからだ。

$ line='root:x:0:0::/root:/bin/bash'

### 既定の IFS
$ show $line
argc=1 | <root:x:0:0::/root:/bin/bash>

### IFS=:
$ IFS=:
$ show $line
argc=7 | <root> <x> <0> <0> <> </root> </bin/bash>
$ show "$line"
argc=1 | <root:x:0:0::/root:/bin/bash>

クォートしたほうは IFS が何であれ常に1個だ。これが「迷ったらダブルクォート」が成り立つ理由である。周囲のコードが IFS をどう変えていようと、クォートした展開は揺れない。

空白系の IFS とそれ以外の IFS で挙動が違う点も知っておく価値がある。

$ gaps='a   b'
$ show $gaps
argc=2 | <a> <b>                     <- 連続した空白は一つにまとまる

$ path='/usr/bin:/bin::/usr/local/bin'
$ IFS=:
$ show $path
argc=4 | </usr/bin> </bin> <> </usr/local/bin>   <- 空フィールドが残る

$ IFS=
$ show $line
argc=1 | <root:x:0:0::/root:/bin/bash>             <- IFS が空なら分割なし

マニュアルの説明そのままだ。IFS が空白系だけで構成されていれば連続した空白が一つの境界で、空フィールドはクォートによってしか生じない。空白でない文字が IFS にあるとその文字一つ一つが境界なので、連続すれば空フィールドが生じる。

IFS は "$*" がつなぐ文字も決める。

$ set -- one two three
$ IFS=:
$ printf '%s\n' "$*"
one:two:three
$ for a in "$@"; do printf ' <%s>' "$a"; done
 <one> <two> <three>

実務で IFS を使う正しい方法は一つのコマンドにだけ掛けることである。全体を変えてしまうと、そのあとのすべてのクォートなしの展開が影響を受ける。

$ printf '%s\n' "$line" | { IFS=: read -r user pw uid gid gecos home shell
    printf 'user=<%s> uid=<%s> home=<%s> shell=<%s>\n' "$user" "$uid" "$home" "$shell"; }
user=<root> uid=<0> home=</root> shell=</bin/bash>

### 全体を変えたまま忘れた場合
$ IFS=,
$ files='a,b'
$ show $files
argc=2 | <a> <b>         <- 意図した場所ではないかもしれない
$ show "$files"
argc=1 | <a,b>

IFS=: read -r ... のようにコマンドの前に置いた代入はそのコマンドにだけ適用される。read に -r を付けるのもクォートと同じ性格の防御だ。-r がないと入力のバックスラッシュが退避文字として解釈され消えてしまう。

11. クォートが不要な場所、むしろ外すべき場所

「すべてクォートせよ」も規則ではない。クォートが意味を持たない場所があり、クォートすると動作が変わる場所がある。実行して区別した。

$ v='my report.txt'
$ star='*.txt'

### A) 代入の右辺: 分割もグロブも起きない
$ a=$v
$ b=$star
$ printf 'a=<%s>\n' "$a"
a=<my report.txt>
$ printf 'b=<%s>\n' "$b"
b=<*.txt>

代入の右辺はクォートしなくても安全である。それでも習慣としてクォートを付けるほうがよいという意見が多いが、理由は安全ではなく一貫性だ。例外を一つ作ると、次の人がその例外の範囲を判断し直さなければならなくなる。

逆に case と [[ ]] のパターン位置はクォートの有無が意味を変える。

$ v='my report.txt'
$ p='my*'

$ case "$v" in
    $p)  echo 'パターンをクォートしない -> グロブとして解釈、一致' ;;
    *)   echo '一致せず' ;;
  esac
パターンをクォートしない -> グロブとして解釈、一致

$ case "$v" in
    "$p") echo 'パターンをクォート -> 文字どおり、一致' ;;
    *)    echo '一致せず (文字どおりの my* はこの名前ではない)' ;;
  esac
一致せず (文字どおりの my* はこの名前ではない)

[[ ]] も同じだ。左辺は分割されないのでクォートは不要だが、右辺はパターンなのでクォートするとリテラルになる。

$ [[ $v == 'my report.txt' ]]  && echo '左辺クォートなし: 問題なし'
左辺クォートなし: 問題なし
$ [[ $v == $p ]]   && echo '右辺クォートなし: グロブ一致'
右辺クォートなし: グロブ一致
$ [[ $v == "$p" ]] || echo '右辺クォートあり: 一致せず (意図どおり)'
右辺クォートあり: 一致せず (意図どおり)

### 同じ比較を単一角括弧で行うと
$ [ $v == 'my report.txt' ]
bash: [: too many arguments

[[ ]] はシェル構文なので内部で単語分割をしない。[ ] はコマンドなので引数を受け取る。だから同じコードが一方では通り、他方では引数個数のエラーになる。

グロブの結果が再分割されないという事実もここで整理しておく。

$ show *.txt
argc=2 | <my report.txt> <notes.txt>
$ show "$star"
argc=1 | <*.txt>
$ show $star
argc=2 | <my report.txt> <notes.txt>

コードに直接書いた *.txt はクォートしないのが正しい。クォートするとグロブではなく文字列になる。したがって「クォートを外す」正当な場合は二つだけである。意図的な単語分割と意図的なグロブだ。それ以外はすべて付ける。

  • グロブのパターンをコードに直接書くとき: for f in *.log — クォートしない
  • グロブのパターンが変数に入っていてそれをグロブとして使いたいとき: case・[[ ]] の右辺
  • オプション文字列を複数の引数に割りたいとき — ただし配列のほうが安全
  • それ以外はすべて: ダブルクォートを付ける
外したなら一行残す
わざとクォートを外した場所には # 意図的な分割 のようなコメントを付けるとよい。そうしないと次の人が「付け忘れ」と見て引用符を足し動作を変えるか、逆に本当の抜けを「意図したもの」として見過ごす。

12. eval と二重のシェル - クォートがもう一度剥がれるとき

ここまではシェルが文字列を一度読む状況だった。eval やリモートシェル、コンテナ実行のように同じ文字列を二度読む状況では、クォートがもう一枚剥がれる。

$ greeting=hello
$ v='$greeting'

$ printf 'plain : %s\n' "$v"
plain : $greeting

$ eval "printf 'eval  : %s\n' \"$v\""
eval  : hello

同じ変数なのに eval を通すと値がもう一度解釈された。値がコマンド区切りを含んでいれば、その次は予測できる。

$ name='keep.txt; echo INJECTED'

$ printf '%s\n' "$name"
keep.txt; echo INJECTED

$ eval "printf '%s\n' $name"
keep.txt
INJECTED

クォートして出力すれば値一つだが、eval に載せるとセミコロンの後ろが別のコマンドとして実行される。eval が危険と言われる理由がこれである。安全な条件は一つだ。eval に渡す文字列がすべて自分で作ったもののときだけ使う。

同じことが二つ目のシェルにコマンドを渡すときにも起きる。以下は bash -c で再現したが、リモート実行やコンテナ実行も原理は同じである。文字列が向こう側のシェルで再び解析される。

$ target='my report.txt'

$ bash -c "wc -c $target"
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 total

$ bash -c "wc -c \"$target\""
0 my report.txt

$ bash -c "wc -c $(printf '%q' "$target")"
0 my report.txt

どの層がドル記号を食うのかも実行で確かめておけば迷わない。

$ name=outer

$ bash -c "printf 'A: %s\n' $name"
A: outer          <- 外側のシェルが展開して文字列に埋め込んで渡した

$ bash -c 'printf "B: %s\n" $name'
B:                <- 内側のシェルが展開したが、そちらに name はない

$ bash -c 'printf "C: %s\n" "$0"' "$name"
C: outer          <- 値を引数として渡した。文字列の組み立てをしていない

C が正解の形だ。値を文字列に埋め込まず引数として渡せばクォートの問題そのものが生じない。

埋め込むしかないなら手で引用符を重ねずシェルにやらせる。printf %q と bash 4.4 以降の ${var@Q} がその道具である。

$ bad='my report.txt'
$ weird=$(printf 'a b\tc*d')

$ printf 'raw : %s\n' "$bad"
raw : my report.txt
$ printf 'q   : %q\n' "$bad"
q   : my\ report.txt
$ printf 'q   : %q\n' "$weird"
q   : $'a b\tc*d'

$ printf 'atQ : %s\n' "${bad@Q}"
atQ : 'my report.txt'
$ printf 'atQ : %s\n' "${weird@Q}"
atQ : $'a b\tc*d'

### 往復: クォートを付けてから再解析してみる
$ q=$(printf '%q' "$bad")
$ eval "wc -c $q"
0 my report.txt

タブの入った値にはシェルが自分で ANSI-C クォートを選んだ点に注目したい。クォート方式を人が選ぶより正確だ。ただし %q も ${var@Q} もbash 拡張なので POSIX sh にはない(13節)。

最後に、展開結果を目で確かめたいなら set -x が最も速い。シェルが実際に渡した引数をクォート付きで見せてくれる。

$ set -x
$ wc -c $bad
+ wc -c my report.txt
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 total
$ wc -c "$bad"
+ wc -c 'my report.txt'
0 my report.txt

トレース行で 'my report.txt' のようにbash が引用符を付けて見せれば引数一つ、そのまま my report.txt と出れば二つに割れている。この一点を知るだけでデバッグ時間が大きく減る。

13. POSIX sh と bash が分かれる箇所

#!/bin/sh で始まるスクリプトを書くなら bash 拡張は使えない。どこまでが共通でどこからが bash 専用かを dash と並べて動かして確認した。

### ANSI-C クォート
bash : A	B
sh   : $A\tB

### [[ ]]
bash : ok
sh   : dash: 1: [[: not found

### 配列
bash : x|y z|
sh   : dash: 1: Syntax error: "(" unexpected

### printf %q
bash : a\ b
sh   : dash: 1: printf: %q: invalid directive

逆にbash のほうが厳しい箇所もある。リダイレクト先が二語に割れるときだ。

$ v="r 1.txt"; echo hi > $v          # 素の bash
bash: $v: ambiguous redirect
exit=1

$ v="r 2.txt"; echo hi > $v          # bash --posix
exit=0

$ v="r 3.txt"; echo hi > $v          # dash
exit=0

### 実際に作られたファイル
$ ls
r 2.txt
r 3.txt

素の bash は拒否し、POSIX モードの bash と dash は受け入れてファイルを作った。POSIX 仕様がこの箇所について書いている内容は次のとおりである。

Pathname expansion shall not be performed on the word by a non-interactive shell; an interactive shell may perform it, but if the expansion would result in more than one word it is unspecified whether the redirection proceeds without pathname expansion being performed or the redirection fails.

つまりこの箇所は実装ごとに違って振る舞ってよい区間である。ならば結論は一つだ。リダイレクト先もクォートする。どのシェルで動かしても同じになる。

幸いクォートの中核規則はどこでも同じである。同じコードを二つのシェルで動かして確かめた。

$ v="a b"; set -- $v;   printf 'unquoted=%d ' "$#"
$ set -- "$v"; printf 'quoted=%d\n' "$#"

bash  : unquoted=2 quoted=1
dash  : unquoted=2 quoted=1
機能POSIX shbash移植のための代替
シングル・ダブルクォートの規則同じ同じそのまま使う
単語分割・グロブ・IFS同じ同じそのまま使う
"$@" / "$*"同じ同じそのまま使う
ANSI-C クォート $'...'なしありTAB=$(printf '\t')
配列なしありset -- で位置パラメータを使う
[[ ]]なしあり[ ] + クォートを徹底
printf %q, ${var@Q}なしあり値を引数で渡し組み立てを避ける
二語になるリダイレクト先許容拒否常に > "$v"

14. 判断表 - 状況からクォートへ

規則を一つに圧縮するとこうなる。迷ったら "$var"。そして外す場合を例外として明示する。

状況使うべき形式理由
変数をコマンドの引数として渡す"$var"単語分割とグロブの両方を止める
スクリプトの引数をそのまま転送する"$@"個数・空の引数・空白をすべて保存する
引数をログ一行にまとめる"$*"IFS の先頭文字でつないだ文字列一つ
一覧を扱う"${arr[@]}"文字列の一覧は空白入りの要素を表現できない
リダイレクト先> "$var"実装ごとに違って振る舞いうる箇所である
テスト・比較[ -n "$var" ]空の値が引数リストから消えるのを防ぐ
ほかの言語のプログラムを渡す'...'awk・sed・正規表現のドル記号をシェルから守る
find のパターン-name '*.log'クォートしないとシェルが先に食う
タブ・改行を値として入れる$'\t' または $(printf '\t')ダブルクォート内のバックスラッシュは解釈されない
グロブをコードに直接書く*.log (クォートなし)クォートするとグロブでなく文字列になる
case・二重角括弧のパターン変数$p (クォートなし)クォートするとリテラル比較になる
コマンド文字列を別のシェルに渡す値を引数として渡す組み立て自体を避けるのが最も安全である
それでも組み立てが必要ならprintf %q / ${var@Q}クォートを人ではなくシェルに付けさせる

実際にどう変わるかをスクリプト一つで締めくくる。以下はクォートをすべて落としたよくある形だ。構文エラーは一つもないので bash -n は通る。

#!/usr/bin/env bash
src=$1
dst=$2
for f in $(ls $src); do
  cp $f $dst
done
if [ -n $DEBUG ]; then
  echo "copied $f"
fi
rm -f $dst/*.tmp
wc -c $src/report.txt

ディレクトリ名に空白を一つ入れて bash -x で動かした結果である。

$ bash -x ./copy.sh "in box" out
+ src='in box'
+ dst=out
++ ls in box
ls: cannot access 'in': No such file or directory
ls: cannot access 'box': No such file or directory
+ '[' -n ']'
+ echo 'copied '
copied
+ rm -f 'out/*.tmp'
+ wc -c in box/report.txt
wc: in: No such file or directory
wc: box/report.txt: No such file or directory
0 total

#!/usr/bin/env bash
set -u

  [ -e "$f" ] || continue

  echo "copied from $src"
fi

トレース行ごとにbash が引用符を付けて見せている。引数が一つのまま保たれた証拠だ。ls をループに掛けていたのをグロブに替えた点も合わせて見ておくとよい。一覧をテキストにしなければ、クォートの問題は半分消える。

三行で問題箇所を五つすべて指した。余裕があれば静的解析器を導入するほうが正確だが、ツールを入れられない環境でもこの程度はすぐに動かせる。

結論: 引用符は値ではなくコードに付く

クォートを規則にすると三文になる。

  • シングルクォートはすべてを止める。ほかの言語の文法をシェルから守るときに使う。中にシングルクォートは入れられず、回避策は閉じる・一文字・開く
  • ダブルクォートは四つを通す。ドル記号、バッククォート、特定の文字の前のバックスラッシュ、そして対話時の感嘆符。その代わり単語分割とグロブはシングルクォートと同じように止める
  • クォートを付けていない箇所が事故の現場だ。値一つが複数になり、なかったファイル名が生まれ、空の値はまるごと消える

実行で確かめたことをもう一度整理するとこうなる。値に空白があれば引数が二つに割れた。値にアスタリスクがあればファイル一覧に膨らみ、rm 一行がディレクトリを空にした。空の値は引数リストから消え [ -n ] が真になった。"$@" だけが引数四つをそのまま渡し、残る三つはすべて違った。IFS を変えるとクォートなしの展開だけが割れ、クォートしたほうは常に一つだった。コマンドラインを文字列に入れると引用符が文字になり wc にそのまま渡った。

最後が本記事の主旨である。引用符は値ではなくコードに付く。シェルはソースを読むときにクォートを処理し、その後は値の中の引用符を二度と見ない。だからコマンドラインを文字列で組み立てる方式は原理的に直せず、配列や "$@" で構造を保ったまま渡すことだけが唯一の解決策になる。

既定値を一つ決めておこう。迷ったら "$var"。外す理由が明確なときだけ外し、外した場所には理由を一行残す。この規則一つで、シェルの事故のほとんどが消える。

# シェルのクォート規則 — そのまま貼って使う判断チェックリスト

> 出典: braindetox.kr — シェルのクォート規則
> 根拠: GNU Bash Reference Manual (Single Quotes / Double Quotes / ANSI-C Quoting / Word Splitting), POSIX Issue 8 (Shell Command Language 2.2.2 · 2.2.3 · 2.6.5 · 2.7)
> このファイルをそのまま AI に貼って「うちのスクリプトをこの基準で直して」と書けば使えます。

## 0. 既定値を一行で

**迷ったら `"$var"`。** 外すほうが例外であり、例外には理由をコメントで残す。

## 1. どのクォートが何を止めるか

| 形式 | ドル展開 | バッククォート | バックスラッシュ | 感嘆符(履歴) | 単語分割 | グロブ |
|---|---|---|---|---|---|---|
| クォートなし | 通す | 通す | 通す | 通す | **起きる** | **起きる** |
| `'...'` | 止める | 止める | 止める | 止める | 止める | 止める |
| `"..."` | **通す** | **通す** | **一部通す** | **対話時のみ通す** | 止める | 止める |
| ANSI-C クォート | 止める | 止める | **解釈する** | 止める | 止める | 止める |
| `\x` | 止める | 止める | 止める | 止める | 止める | 止める |

- [ ] シングルとダブルは**単語分割とグロブを同じように止める**ことを理解している
- [ ] ダブルクォート内のバックスラッシュはドル記号・バッククォート・ダブルクォート・バックスラッシュ・改行の**五つの前でだけ**特別だと理解している
- [ ] `"\n"` は改行ではなく二文字だと理解している

## 2. 状況 → 使うべきクォート

| 状況 | 使うべき形式 | 理由 |
|---|---|---|
| 変数をコマンド引数に | `"$var"` | 単語分割とグロブの両方を止める |
| スクリプト引数の転送 | `"$@"` | 個数・空の引数・空白をすべて保存 |
| 引数をログ一行に | `"$*"` | IFS の先頭文字でつないだ文字列一つ |
| 一覧を扱う | `"${arr[@]}"` | 文字列の一覧は空白入りの要素を持てない |
| リダイレクト先 | `> "$var"` | 実装ごとに違って振る舞いうる箇所 |
| テスト・比較 | `[ -n "$var" ]` | 空の値が引数リストから消えるのを防ぐ |
| awk・sed・正規表現 | `'...'` | ドル記号をシェルから守る |
| find のパターン | `-name '*.log'` | クォートしないとシェルが先に食う |
| タブ・改行を値に | `TAB=$(printf '\t')` | ダブルクォート内のバックスラッシュは解釈されない |
| コードに直接書くグロブ | `*.log` (クォートなし) | クォートすると文字列になる |
| case・`[[ ]]` のパターン変数 | `$p` (クォートなし) | クォートするとリテラル比較になる |
| 別のシェルへコマンドを渡す | 値を**引数として** | 文字列の組み立て自体を避ける |
| それでも組み立てるなら | `printf %q` / `${var@Q}` | クォートを人ではなくシェルに付けさせる |

## 3. よく壊れるパターンと修正

```bash
# ── 1) 値に空白があると引数が割れる
wc -c $f                      # ✗ my report.txt → 引数2個
wc -c -- "$f"                 # ✓ 1個

# ── 2) 値にグロブ文字があるとファイル名に膨らむ
rm $f                         # ✗ f='*' ならディレクトリが空になる
rm -f -- "$f"                 # ✓ そのファイル一つだけ

# ── 3) 空の値は引数リストから消える
[ -n $DEBUG ]                 # ✗ [ -n ] になり常に真
[ -n "${DEBUG:-}" ]           # ✓

# ── 4) 一覧を文字列に入れない
list='a.txt b.txt'; for f in $list      # ✗ 空白入りの名前を表現できない
files=('a b.txt' 'c.txt'); for f in "${files[@]}"   # ✓

# ── 5) ls をループに掛けない
for f in $(ls "$src")         # ✗ 分割とグロブの両方を通る
for f in "$src"/*; do [ -e "$f" ] || continue       # ✓

# ── 6) コマンドラインを文字列に入れない (クォートが文字になる)
cmd='wc -c "a b.txt"'; $cmd   # ✗ wc が引用符文字を受け取る
cmd=(wc -c 'a b.txt'); "${cmd[@]}"                  # ✓

# ── 7) 引数の転送は常にこの形
run() { real_cmd "$@"; }      # ✓  ($@ · "$*" · $* は結果が違う)

# ── 8) リダイレクト先もクォートする
echo hi > $out                # ✗ bash は ambiguous redirect、sh は通る
echo hi > "$out"              # ✓ どのシェルでも同じ

# ── 9) 二つ目のシェルには値を引数で渡す
ssh host "wc -c $file"        # ✗ 向こうで再解析される
ssh host 'wc -c "$0"' "$file" # ✓ 組み立てない
```

## 4. クォートを外してよい唯一の二つ

- [ ] **意図的な単語分割** — オプション文字列の分割 (配列のほうが安全)
- [ ] **意図的なグロブ** — `case` · `[[ ]]` のパターン位置、コードに直接書くグロブ
- [ ] 上のどちらでもないなら**必ずクォートする**
- [ ] 外した場所には `# 意図的な分割` のようなコメントを残した

## 5. 点検コマンド — 見るべき行を指してくれる

```bash
F=script.sh

# コマンドの後ろに来るクォートなしの展開
grep -nE '(^|[[:space:]|(&;])(cp|mv|rm|wc|cat|cd|mkdir|source)[[:space:]]+[^|;&]*\$[A-Za-z_{]' "$F"

# 角括弧テスト内のクォートなしの展開
grep -nE '\[[^]]*\$[A-Za-z_{][^]"]*\]' "$F"

# コマンド出力や変数を for で回す形
grep -nE 'for[[:space:]]+[A-Za-z_]+[[:space:]]+in[[:space:]]+(\$\(|\$[A-Za-z_{])' "$F"

# クォートしていないリダイレクト先
grep -nE '(^|[[:space:]])[12]?>>?[[:space:]]*\$[A-Za-z_{]' "$F"

# 実際の展開結果を目で確かめる
bash -n "$F"                       # 構文だけ (クォート抜けは検出されない)
bash -x "$F" "引数 ひとつ" out       # トレース行の引用符の有無で判断
```

**トレース行の読み方**: bash が `'my report.txt'` のように**引用符を付けて見せれば引数一つ**、
そのまま `my report.txt` と出れば**二つに割れている**。

## 6. 再現用の試験データ — 空の一時ディレクトリでのみ

```bash
d=$(mktemp -d) && cd "$d" || exit 1
: > 'my report.txt'          # 空白
: > 'keep.txt'
printf 'junk\n' > '*'        # 名前がグロブ文字そのもの
touch -- "-dash.txt"         # ダッシュで始まる
./your_script.sh "$d" out    # ここで壊れるならクォートの問題
```

★ 上の試験は**必ず新規に作った空の一時ディレクトリの中だけで**動かしてください。ホームディレクトリや実サーバのパスでは実行しないでください。

## 7. POSIX sh へ移すとき

| 機能 | POSIX sh | bash | 移植のための代替 |
|---|---|---|---|
| シングル・ダブルの規則 | 同じ | 同じ | そのまま |
| 単語分割・グロブ・IFS | 同じ | 同じ | そのまま |
| `"$@"` / `"$*"` | 同じ | 同じ | そのまま |
| ANSI-C クォート | なし | あり | `TAB=$(printf '\t')` |
| 配列 | なし | あり | `set --` で位置パラメータ |
| `[[ ]]` | なし | あり | `[ ]` + クォート徹底 |
| `printf %q` | なし | あり | 値を引数で渡し組み立てを回避 |
| 二語のリダイレクト先 | 許容 | 拒否 | 常に `> "$v"` |

## 8. 最後に一文

**引用符は値ではなくコードに付く。** 変数の値の中の引用符はシェルにとって何の意味もない。
だからコマンドラインを文字列で組み立てる方式は原理的に直せず、配列や `"$@"` で構造を保ったまま渡すことだけが答えになる。
