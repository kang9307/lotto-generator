Why a Filename Looks Different in Every Shell

Where Git Bash and PowerShell disagree about the same file

Aug 10, 2026 Dev & Infra

Introduction: the same folder, two different names

Running scripts in Git Bash, deploying from PowerShell and building inside WSL is an ordinary setup on a Windows workstation. Handle file names with spaces or non-ASCII characters in that mix and something inexplicable eventually happens. A file that Git Bash lists without complaint is reported missing by a PowerShell script.

# In Git Bash
$ ls -1
x?y.txt

# In PowerShell — same folder, same file
PS> Test-Path -LiteralPath '.\x?y.txt'
False

The file is there. It was not deleted or hidden. The two shells simply know the same file by two different names. And this class of mismatch is not limited to one question mark in a name. Case sensitivity, locale, Unicode normalization and the encoding of a list file all diverge at their own boundaries, and every divergence is silent. No error is raised; only the result is wrong.

This article walks those boundaries one at a time. Quoting syntax itself is covered in Shell Quoting Rules - What Each Quote Actually Blocks, and the practical business of pushing names with spaces and newlines through find and xargs is in The find and xargs whitespace trap. What follows is the layer after that: the places where the name changes even though you quoted everything correctly.

2. A name is a byte string, and each layer has its own rules

A file name passes through at least three layers before it reaches the screen. Each layer stores and interprets the name differently, and conversion happens at the boundaries.

  • File system — NTFS stores names as sequences of UTF-16 code units. It does not normalize, and it forbids certain characters.
  • Shell and utilities — POSIX-style tools treat a name as a byte string. Which encoding those bytes represent is decided by the locale.
  • Screen — the font draws it. Different bytes can produce the identical picture.

That third point runs through the whole article. What you see is not evidence. When a name is suspect, look at the bytes, and the method is the same everywhere.

$ printf '%s' "회의 자료.txt" | od -An -tx1
 ed 9a 8c ec 9d 98 20 ec 9e 90 eb a3 8c 2e 74 78 74

Making that one line a reflex cuts diagnosis time dramatically. Compare bytes, not glyphs.

3. PowerShell cannot find what Git Bash created - the 0xF000 remap

Windows defines a set of characters that cannot appear in a file name. The Cygwin documentation describes them as the ASCII control characters from 1 to 31, plus characters with special meaning in the Win32 API, and lists " * : < > ? | \. Yet in Git Bash such names are created with no resistance at all.

$ for c in '<' '>' ':' '"' '|' '?' '*'; do printf 'x\n' > "x${c}y.txt"; done
$ ls -1
x"y.txt
x*y.txt
x:y.txt
x<y.txt
x>y.txt
x?y.txt
x|y.txt

Dump the bytes of those names from the Git Bash side and they are exactly what was typed: 3a for the colon, 3f for the question mark. But read the same files from the Windows side and different code points come back.

PS> Get-ChildItem | ForEach-Object {
      ($_.Name.ToCharArray() | ForEach-Object { 'U+{0:X4}' -f [int]$_ }) -join ' '
    }
U+0078 U+F009 U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F00A U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F022 U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F02A U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F03A U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F03C U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F03E U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F03F U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F07C U+0079 U+002E U+0074 U+0078 U+0074

The rule is visible at a glance. 0xF000 is added to the code point of each forbidden character, moving it into the private use area. The Cygwin guide states exactly this — all of those characters except the backslash are converted to special UNICODE characters in the range 0xf000 to 0xf0ff, the private use area, when creating or accessing files by adding 0xf000 to the forbidden characters' code points. The backslash is exempt because it is the path separator.

Git Bash reverses the mapping when it reads a directory, so nothing looks wrong from that side. The problem is the tools that do not reverse it.

PS> Test-Path -LiteralPath '.\x?y.txt'
False

PS> Test-Path -LiteralPath '.\x|y.txt'
Test-Path : Illegal characters in path.

PS> $pua = 'x' + [char]0xF03F + 'y.txt'
PS> Test-Path -LiteralPath ".\$pua"
True

A name containing a vertical bar does not return false — it throws. The Windows API refuses that character in a path, so the query never happens. Only the name assembled from the private use area character returns true. The file effectively has two names.

Where this bites in practice
It shows up when a Git Bash script produces a log or report file and a PowerShell deployment script picks it up. Stamping a time into the name with a %H:%M format inserts a colon, and from that moment the two shells see different files. The habit of using hyphens instead of colons in timestamped names is not superstition; it is the rule that avoids exactly this.

The Cygwin guide separately covers DOS device names (AUX, COM1, LPT1, PRN and friends) and trailing dots or spaces. Device names cannot be used as a file name or extension by a native Win32 application, and trailing dots and spaces are all removed before the file is created. Cygwin-family programs can bypass those constraints and create such files, and once created they are awkward to remove with ordinary Windows tools. That is not something to reproduce for fun. The answer is to not create them.

4. Case - create two files, keep one

This is the classic spot where a script that runs fine on Linux quietly loses a file on Windows.

$ printf '대문자\n' > "README.txt"
$ printf '소문자\n' > "readme.txt"
$ ls -1
README.txt
$ cat README.txt
소문자

There is one file. The name came from the first write and the content from the second. NTFS in its default configuration is case-insensitive but case-preserving. The second redirection did not create a new file; it opened the existing one and overwrote it.

  • A repository holding two paths that differ only in case loses one of them on a Windows checkout.
  • A script writing Config.json while another reads config.json fails only on Linux. The failure surfaces late, which is the worse direction.
  • Names in scripts that have no case distinction sidestep this one entirely — and then inherit every problem in the following sections.

5. Git Bash path conversion - the argument changes in flight

When Git Bash invokes a native Windows executable it rewrites arguments that look like POSIX paths into Windows paths. Shell builtins get no such treatment.

$ node -e 'console.log(JSON.stringify(process.argv.slice(1)))' "/usr/bin" "a/b" "-Dfoo=/bar"
["C:/Program Files/Git/usr/bin","a/b","-Dfoo=C:/Program Files/Git/bar"]

$ printf '%s\n' "/usr/bin"
/usr/bin

Three things surface at once. First, /usr/bin was reinterpreted under the Git installation root. Second, a/b without a leading slash was left alone. Third and most awkward — the value after the equals sign in -Dfoo=/bar was converted too. It makes no difference that this was an application option rather than a path.

Passing a container volume mount or a REST route as an argument is where this quietly corrupts the value. One environment variable turns it off.

$ MSYS_NO_PATHCONV=1 node -e 'console.log(JSON.stringify(process.argv.slice(1)))' \
      "/usr/bin" "a/b" "-Dfoo=/bar"
["/usr/bin","a/b","-Dfoo=/bar"]
  • To scope it to a single command, prefix it as above. Setting it for a whole script also stops conversion of arguments that genuinely are paths, so narrow scope is usually better.
  • Starting an argument with a double slash (//c) is a known way to slip past the conversion, provided the receiving program accepts that form.
  • The conversion applies only to native executable invocations. Bash builtins and MSYS-built utilities are untouched, so the same string arrives differently depending on the command.

6. PowerShell 5.1 - no word splitting, but arguments disappear

Crossing into PowerShell removes one bash problem entirely. There is no word splitting. A variable holding spaces arrives as a single argument even unquoted.

PS> $f = '회의 자료.txt'
PS> node -e 'process.argv.slice(1).forEach(function(a,i){console.log(i+String.fromCharCode(32)+a)})' $f 'a b.txt'
0 회의 자료.txt
1 a b.txt

The value that would split into two arguments in bash without quotes travels as one here. But something else goes missing instead.

PS> $s = 'a"b'
PS> $s.Length
3
PS> node -e 'console.log(JSON.stringify(process.argv.slice(1)))' $s
["ab"]

PS> node -e 'console.log(JSON.stringify(process.argv.slice(1)))' '' 'x'
["x"]

A three-character string arrived as two. The double quote silently vanished. The empty string argument dropped out of the list entirely. No error, no warning.

The cause is documented. When calling a native command, PowerShell states that the parsed arguments are then joined into a single string with each parameter separated by a space, and quote handling breaks during that join. PowerShell 7.3 changed the argument passing behaviour, and the documentation flags that change as a breaking change from the Windows PowerShell 5.1 behaviour, noting that in the new mode embedded quotes are now preserved and empty strings as arguments are now preserved. In other words, the 5.1 result above is documented behaviour rather than a bug.

Stuck on 5.1, there are three options.

  • The stop-parsing token --% — passes the remaining text literally. As the documentation notes, %variable% environment references are still expanded, it is effective only until the next newline or pipe, and redirection inside it is passed along as an argument.
  • Start-Process — takes an argument array so the command line assembly is under explicit control.
  • Move to PowerShell 7 or later — the new mode is the default on Windows, with batch files and cmd.exe calls falling back to the legacy style.
The trap is that it is the mirror image of bash. In bash you get extra arguments because you did not quote. In PowerShell 5.1 you lose arguments because you did. Porting a script between the two means the fix points in opposite directions.

7. Path versus LiteralPath - one bracket opens another file

The bash accident where an unquoted variable inflates into a glob is well known. PowerShell has the same class of trap, except it is decided by the parameter name rather than by quoting.

With two files of different content, star1.txt and star[1].txt, reading the bracketed one looks like this.

# bash — quoting decides
$ g='star[1].txt'
$ cat $g
star1 내용
$ cat "$g"
대괄호 파일 내용
# PowerShell — the parameter name decides
PS> Get-Content -Path 'star[1].txt'
star1 내용
PS> Get-Content -LiteralPath 'star[1].txt'
대괄호 파일 내용

Neither case asked for a file that does not exist. Both opened a different file and succeeded quietly. That is the worst kind of failure; an error would have told you immediately.

  • PowerShell's -Path interprets wildcards. *, ? and [ ] are all pattern characters.
  • Names arriving from user input or a list file go through -LiteralPath without exception. Brackets in real-world file names are common — something like [final]report.xlsx gets created every day.
  • The equivalent defence in bash is quoting, or turning off just pathname expansion for a moment with set -f.
$ v='star[1].txt'
$ echo $v          # globbing on
star1.txt
$ set -f
$ echo $v          # globbing off
star[1].txt
$ set +f

8. Default encodings - CP949 inside PowerShell 5.1

There is also a boundary where the name arrives intact and the content breaks. A file written as UTF-8 by Git Bash, read by PowerShell 5.1:

PS> Get-Content -LiteralPath 'star1.txt'
star1 ?댁슜
PS> Get-Content -LiteralPath 'star1.txt' -Encoding UTF8
star1 내용

The file is fine. The reader chose the wrong encoding. Windows PowerShell 5.1 reads a file with no byte order mark using the system ANSI code page. On a Korean Windows install that is:

PS> [System.Text.Encoding]::Default.WebName
ks_c_5601-1987

Writing is symmetric. Storing the same string both ways and dumping the bytes makes the difference plain.

PS> Set-Content -LiteralPath 'a.txt' -Value '한글 저장'
PS> Set-Content -LiteralPath 'b.txt' -Value '한글 저장' -Encoding UTF8

a.txt : c7 d1 b1 db 20 c0 fa c0 e5 0d 0a
b.txt : ef bb bf ed 95 9c ea b8 80 20 ec a0 80 ec 9e a5 0d 0a
  • The default file starts with c7 d1 — two bytes per character, which is CP949.
  • The UTF-8 file starts with ef bb bf. A byte order mark is prepended. The -Encoding UTF8 of 5.1 is not BOM-less UTF-8.
  • Both end lines with 0d 0a. That CRLF becomes the raw material for the next section.

Reading the cause backwards from the shape of the garbled text is tabulated in Locating Where Hangul Breaks - cp949 and UTF-8. Names garbled inside an archive follow a different rule set again, and that belongs to zip filename encoding.

9. Passing a list as a file - BOM and CR stick to the name

Handing over a list of files to process as a text file is common. Feed a list made in a spreadsheet or Notepad into a bash loop and suddenly not a single file exists. There are three reasons, and none of them is visible.

$ while IFS= read -r f; do
      printf '읽은 값=[%s]  존재=%s\n' "$f" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"
  done < list_cp949.txt
읽은 값=[ȸ�� �ڷ�.txt]  존재=없음

$ … < list_utf8.txt      # UTF-8 with BOM
읽은 값=[﻿회의 자료.txt]  존재=없음

The first line is CP949 bytes, so the name is garbled. The second looks correct to the eye but carries a zero-width byte order mark at the front, making it a different name. The third cause, the carriage return, is clearer on its own.

$ printf '회의 자료.txt\r\n' > list_crlf.txt
$ while IFS= read -r f; do printf '길이=%d 존재=%s\n' "${#f}" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"; done < list_crlf.txt
길이=18 존재=없음

$ while IFS= read -r f; do f=${f%$'\r'}; printf '길이=%d 존재=%s\n' "${#f}" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"; done < list_crlf.txt
길이=17 존재=있음

One byte of difference, and nothing shows on screen. A script that consumes lists is better off normalizing all three up front.

$ iconv -f CP949 -t UTF-8 list.txt | sed '1s/^\xEF\xBB\xBF//' | tr -d '\r' \
  | while IFS= read -r f; do
        printf '읽은 값=[%s]  존재=%s\n' "$f" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"
    done
읽은 값=[회의 자료.txt]  존재=있음
  • If the list is already UTF-8, drop iconv but keep the BOM and CR stripping. Both can appear regardless of encoding.
  • When you control the producer, prefer NUL-separated exchange. It is the one byte that cannot occur in a name, so the boundary never breaks. That form is laid out in The find and xargs whitespace trap.
  • Dropping -r from read eats backslashes, which is fatal for scripts handling Windows paths — C:\temp\새 폴더 becomes C:temp새 폴더.

10. Three places where the locale changes bash itself

This is the least discussed axis. The same bash running the same script behaves differently depending on the locale. It shows in three places.

10.1 Unicode escapes in ANSI-C quoting

The Bash manual defines \uHHHH inside $'string' as a Unicode character escape. The actual result depends on the locale.

$ LC_ALL=C.UTF-8 bash -c "printf '%s' \$'\u00E9\uD55C' | od -An -tx1"
 c3 a9 ed 95 9c

$ LC_ALL=C bash -c "printf '%s' \$'\u00E9\uD55C' | od -An -tx1"
 e9 5c 75 44 35 35 43

Under the UTF-8 locale the two characters come out as c3 a9 and ed 95 9c. Under the C locale é collapses to the single byte e9, and the second escape is not converted at all, staying as the six literal characters \uD55C (5c 75 44 35 35 43). No error is raised. It quietly becomes a literal.

In a default Git for Windows install LANG is empty, which means the default state is the trap side. Any script that builds characters from Unicode escapes has to declare its locale.

10.2 The output of printf %q

This is the idiom for logging a name in a safe form, and its output shape varies by locale.

$ LC_ALL=C.UTF-8 bash -c "printf '%q\n' '회의 자료.txt'"
회의\ 자료.txt

$ LC_ALL=C bash -c "printf '%q\n' '회의 자료.txt'"
$'\232\214\235\230 \236\220\214.txt'

Both forms round-trip correctly if fed back to the shell, so functionally either is right. The problem is the log. A log line in the second shape cannot be read by a human, and pasting it into a ticket tells nobody which file it was.

10.3 Bracket ranges over a non-ASCII script

Filtering with a bracket range such as [가-힣] is a widespread habit. That range is interpreted as a byte range rather than a code point range in some locales.

$ for loc in C C.UTF-8 en_US.UTF-8 ko_KR.UTF-8; do
      a=$(printf '%s\n' "$NFC" | LC_ALL=$loc grep -cE '^[가-힣]+\.txt$')
      b=$(printf '%s\n' "$NFD" | LC_ALL=$loc grep -cE '^[가-힣]+\.txt$')
      echo "LC_ALL=$loc  composed=$a  decomposed=$b"
  done
LC_ALL=C          composed=1  decomposed=1
LC_ALL=C.UTF-8    composed=1  decomposed=0
LC_ALL=en_US.UTF-8 composed=1  decomposed=0
LC_ALL=ko_KR.UTF-8 composed=1  decomposed=0

Under the C locale the decomposed name matches as well. That is a false positive. Under UTF-8 locales it does not match — correct behaviour, but the separate problem of missing decomposed names remains. Either way, one bracket range cannot express the idea of only these names.

Literal searches, by contrast, are locale independent. Running grep '한글' over the same two lines returns 1 of 2 in every locale. The reason literals are safe while ranges are not leads into the next section.

11. Composed and decomposed forms in one folder

NTFS does not normalize names. Which means two files that look identical on screen can coexist in one folder.

$ ls -1
한글.txt
한글.txt

$ for f in *; do printf '%s  ' "$f"; printf '%s' "$f" | od -An -tx1 | tr -s ' ' | tr -d '\n'; echo; done
한글.txt   e1 84 92 e1 85 a1 e1 86 ab e1 84 80 e1 85 b3 e1 86 af 2e 74 78 74
한글.txt   ed 95 9c ea b8 80 2e 74 78 74

The lower one is composed (NFC): three bytes per syllable, ten bytes for the whole name. The upper one is decomposed (NFD), with leading, vowel and trailing jamo taking three bytes each, for twenty-two. Unicode Standard Annex #15 defines the normalization forms, and Hangul is called out as the case that is decomposed and composed algorithmically.

How this surfaces in the shell is what matters operationally.

$ find . -maxdepth 1 -name '한글*' | wc -l
1

$ n=0; for f in 한글*; do n=$((n+1)); done; echo "$n"
1

$ ls -1 | sort | uniq | wc -l
2
  • Both the shell glob and find -name catch only the composed one, because a pattern typed on a keyboard is composed.
  • sort always places the decomposed form first; jamo code points (U+1100 range) sort below precomposed syllables (U+AC00 range).
  • uniq counts them as two distinct lines, so a de-duplication script reports no duplicates.
  • A backup script building its list with find skips the decomposed file entirely. It is an omission, not a failure, so no alert fires.

Why the two forms arise, and what breaks at the search, sort, length-validation and serialization boundaries, is covered in When Hangul Falls Apart Into Jamo - NFC and NFD. The shell-side conclusion is short. Decide where in the pipeline normalization happens, and write that point down. Undecided, every tool normalizes at its own moment into its own form.

12. Crossing a boundary in a form that holds

Every failure so far happened in the same place: putting a name into a string and handing it to another tool. Not putting it there does not break.

Within one shell, receive them as an array. Whatever the name contains, one element is one file.

$ mapfile -d '' files < <(find . -maxdepth 1 -type f -print0)
$ echo "${#files[@]}"
$ printf '  [%s]\n' "${files[@]}"

Previewing the arguments a command will actually receive before running it is equally cheap and equally reliable. Put printf where the command would go.

$ target="회의 자료.txt"
$ printf '  인자[%s]\n' $target       # unquoted
  인자[회의]
  인자[자료.txt]
$ printf '  인자[%s]\n' "$target"     # quoted
  인자[회의 자료.txt]

If a command that moves or removes files had run while the upper result was in effect, it would have targeted two names that do not exist. Failing on a missing target is the lucky outcome; if a file happens to carry one of those names, the wrong thing becomes the target. Running the same line through printf first costs a few seconds.

Empty values and values beginning with a dash surface the same way.

$ empty=""
$ set -- $empty;  echo "unquoted argument count=$#"
unquoted argument count=0
$ set -- "$empty"; echo "quoted argument count=$#"
quoted argument count=1

$ opt="-n"
$ echo $opt x
x

On the last line -n was not printed. echo consumed it as an option rather than a value. Where a value may start with a dash, close the option section with -- or prefix it with ./.

$ touch "-n.txt"
touch: unknown option -- n
$ touch -- "-n.txt"      # close the option section
$ touch ./-n.txt         # make it a path

15. What was not verified

The following could not be established by running anything in this environment. Rather than filling the gaps by guessing, they are left open.

  • How WSL handles file names. wsl.exe is installed but no distribution is (wsl -l -q exits with status 1), so nothing could be run. How WSL treats forbidden characters and case when mounting a Windows drive, and whether it is compatible with the MSYS2 0xF000 remap, was not verified. Anyone mixing all three environments is better off dumping the bytes in their own setup the way section 3 does.
  • Automatic decomposition on macOS. The claim that macOS file systems store names in a decomposed form is widely repeated, but there is no macOS here to run it against. The section 11 results are limited to two forms coexisting on NTFS.
  • Trailing dots and spaces, and device names. Only the Cygwin documentation is cited; nothing was reproduced. Such names are hard to clean up with ordinary Windows tools once created, which is reason enough not to make them for a demonstration.
  • The new argument passing in PowerShell 7.x. Only 5.1 exists here. Behaviour from 7.3 onward is written from the official documentation and was not checked against a run.
  • Network file systems. The Cygwin guide notes that some network file systems treat trailing dots and spaces differently. Only local NTFS was examined.

Conclusion: names change as they cross tools

Reduced to one sentence, every failure here has the same shape. A name is data that gets converted every time it crosses a tool boundary, and the conversion rules differ per tool. Git Bash moves forbidden characters into the private use area and back. PowerShell 5.1 joins arguments into a string and re-splits them. Text files pass through a code page. Unicode permits two forms. Each conversion is correct within its own domain, and the mismatch appears only at the seams.

That fixes the diagnostic order too. When a name does not match, check three things in sequence.

  1. Dump the bytes. od -An -tx1 or a code point listing. Do not compare by eye.
  2. Count the boundaries crossed. How many shells did it pass through, how many times did it go out to a file and come back.
  3. Check that boundary's defaults. Locale, code page, whether wildcards are interpreted, how arguments are passed.

Prevention is simpler still. Reduce the number of times a name travels as a string. Receive arrays, separate with NUL, pipe directly instead of via a list file. And keeping colons, question marks and vertical bars out of names at creation time means section 3 never happens at all. Avoiding the characters you can avoid is the cheapest defence there is.
