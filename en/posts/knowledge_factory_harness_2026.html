Building a Knowledge Factory - What Happens When You Apply Harness Engineering to Knowledge Production

Moving the software-factory blueprint into research, writing, and content surfaces a verification problem code never had

Jul 23, 2026 Trends & Culture

Introduction: From a One-Off Prompt to a Knowledge Pipeline

As of July 2026, the center of gravity in AI engineering discourse keeps shifting. It moved from writing good prompts, to designing what context a model gets, and now to designing the deterministic execution layer that actually runs the model - what the industry calls harness engineering. A companion idea to that shift is the software factory: the notion that AI agents take over writing code while developers move into designing the factory that produces it reliably, over and over.

A recent, and genuinely interesting, experiment took both ideas somewhere other than code. A developer building a personal wiki-style knowledge base - while implementing Andrej Karpathy's LLM Wiki concept - says he arrived independently at essentially the same structure as a software factory. He calls the result the Knowledge Factory project. This piece takes that project's blueprint as a starting point and builds its own analysis on top of it: what happens, and what changes, when the idea of mass-producing code gets applied instead to research, documents, analysis, and content?

1. What Is Harness Engineering - Designing Around the Model, Not the Model Itself

A harness, in its original sense, is the gear strapped onto a horse. Dru Knox at the AI dev-tools company Tessl brought that metaphor to AI agents, calling the entire framework that actually controls and runs an agent its harness. The industry shorthand for this today reads: agent equals model plus harness. The model probabilistically proposes a plausible next action; the harness is the deterministic execution layer that verifies that proposal, authorizes execution, and keeps a log.

What matters in this definition is direction. Harness engineering isn't about making the model smarter - it's about making sure a failure that already happened once can't structurally happen again. That's exactly the same point made by the wrapping concept covered here earlier: instead of trying to eliminate an unpredictable core, you wrap deterministic layers - input preparation, verification loops, quality gates - around it, preserving the strength while containing the risk. Harness engineering can be read as that same idea of wrapping, given a practical name and applied to the specific case of a coding agent.

The Knowledge Factory project turns this harness into four cyclical loops. An inner loop where the agent checks itself in real time while drafting; an outer loop where a mechanical rule check and a qualitative review both have to pass before publication; a meta loop that promotes recurring error patterns into system rules; and a reground loop that feeds published output back in as input to fight staleness. From input preparation through verification to iterative improvement, nearly every element harness engineering talks about is already present here.

2. The Software Factory - Turning Code Production Into an Assembly Line

The core of the software factory concept is a shift in the developer's role. An AI agent that carries out multi-step work on its own takes over writing source code, and the developer moves into designing and managing the factory that makes that code reliably, repeatably. The identity shifts from someone who writes code line by line to someone who designs the line that keeps producing it.

There's a reason this idea surfaced in code first. Code has a mechanically checkable answer: whether it compiles, whether it passes tests, whether it breaks a lint rule. That let a harness earn substantial trust with a rule as simple as "run it, and reject it if it fails." It's no accident that code was the first case where a one-off generation, done and forgotten, turned into a pipeline that reproduces the same quality again and again.

3. The Knowledge Factory - Moving the Pipeline Into a Newsroom Metaphor

The metaphor the Knowledge Factory project reaches for is a newspaper newsroom. AI agents take the roles of the reporter, who gathers outside material into source pages, and the columnist, who synthesizes multiple sources into deeper analysis. Above that sits a two-layer check: a copy editor that statically checks links, citations, and document structure against deterministic rules, and a desk that evaluates things hard to reduce to rules - bias, information density, readability - from a reader's point of view. The design worth noticing here is that the project confines independent AI judgment to exactly one seat: the desk. Everything else is either a rule or final human approval, and an orchestrator plays the role of editor-in-chief, coordinating the whole flow.

What's baked into this is the standard skeleton of a knowledge production pipeline: source gathering (reporter, columnist) → verification (the copy editor and desk's dual gate) → synthesis (the columnist's integration) → review (desk plus human) → publication. Where humans step in is also explicit: mandatory human approval is reserved for decisions that are hard to reverse or that change the system itself - the same error repeating three times, publishing a top-level synthesis page, changing a core structure in the writing guidelines, or making something public. Everything else - the low-risk, repetitive work - flows through automatically.

4. Code vs. Knowledge - Why Automating Knowledge Production Is Harder

From here on, this is my own analysis - a point the Knowledge Factory project doesn't directly address. A code factory and a knowledge factory share a similar skeleton, but the nature of verification is fundamentally different. Code has a mechanical judge: the compiler and the test suite. Passing gives you grounds to call it correct. Knowledge has no such judge. Whether something is factual, whether it's current, whether the framing fits the context - taste and interpretation - is territory a compiler simply cannot rule on. The Knowledge Factory project's deliberate split between the copy editor (rules) and the desk (qualitative judgment) is best read as exactly this: a distinction code never needed, but knowledge absolutely does.

The other difference is staleness. Well-written code stays correct as long as requirements don't change. Knowledge, on the other hand, goes stale on its own as long as the world keeps moving - what was true yesterday can be wrong today. That's why the Knowledge Factory project keeps a separate reground loop that feeds published output back in as input: a layer that a code factory simply has no need for. To put it plainly, verifying code output is close to a machine confirming "is this correct," while verifying knowledge output means handling three questions at once - correct, current, and appropriate. Port a code factory's harness straight over to knowledge without acknowledging this difference, and the pipeline will run, but the trustworthiness of its output is not guaranteed.

5. Generalizing to Practice - Research Automation, Reports, Newsletters, Internal Wikis

The Knowledge Factory's skeleton - source gathering → verification → synthesis → review → publication - has no reason to stay locked inside one wiki project. In research automation, it maps directly: a reporter role that scans multiple sources into a draft, a copy editor that mechanically checks citation and link validity, and a desk that flags bias and omission from a human vantage point. For recurring reports or newsletters, the format and checks that repeat weekly - was the same metric computed the same way, was a sharp week-over-week swing double-checked - get nailed down as rules, while qualitative calls like tone and emphasis stay with a human or an AI desk. Internal wikis work the same way: the more documents pile up, the more stale information collides with new information, and without a periodic re-verification cycle equivalent to the reground loop, trust erodes faster than content gets produced.

In this generalization, where a human sits needs to be explicit. Anything mechanically verifiable - is the link alive, does the number match the source - gets left to rules. A human steps in only where a machine can't rule: is this conclusion balanced, does this document fit the organization's context, is this the right moment to cover this topic. A structure where a human reviews every single sentence cancels out the whole benefit of automating in the first place. The opposite extreme - a human intervening nowhere at all - leads straight into the traps covered next.

6. The Traps - Hallucination Pipelining and Verification-Free Mass Production

Get the design wrong, and neither a harness nor a pipeline eliminates a problem - it scales the problem up. The most dangerous trap is hallucination pipelining. When verification gates are weak or purely formal, a factual error the model produces flows straight into the next stage as input, and more output gets stacked on top of it - so the error is no longer an isolated incident but a repeated output of the system itself. 2026 industry benchmarks keep reporting that even top-tier models produce a meaningful hallucination rate depending on the task and setup, and the same result keeps showing up: combining retrieval grounded in source documents with sampled human review is what actually cuts that rate sharply.

The second trap is verification-free mass production. Automation's appeal is throughput, but when the speed of clearing a gate outpaces the precision of what that gate actually catches, low-quality content piles up fast. This is nearly identical to the problem covered in The Human in the Loop Is Tired - human approval that can't keep pace with machine speed degrading into a purely formal step. The third trap is accumulating quality decay. Verification budget isn't infinite, so the consensus in 2026 practitioner discussion is to allocate it unevenly: strong deterministic gates before publication, continuous monitoring after, weighted toward whichever point has the highest cost of failure. Apply the same level of checking to every stage, and the genuinely risky points end up relatively under-guarded.

7. The Human Role - From Editor, Curator, and Verifier to Architect

The Knowledge Factory project makes a striking claim: the operator isn't someone who writes content directly, but someone who designs and upgrades the newsroom system that produces knowledge. The upside of this shift is clear. Fixing one output directly only improves that one result; promoting the desk's recurring critique into a rule lifts the quality of every output produced from then on, all at once. The roles of editor, curator, and verifier don't disappear - what they act on shifts from an individual document to the system that makes documents.

Still, something in this shift clearly doesn't get replaced. As I noted in Wes McKinney on the Future of Data Systems in the AI Era, code keeps getting closer to free, but taste doesn't. The same holds for knowledge production. Deciding what's worth covering, what a balanced conclusion looks like, what emphasis is honest to the reader - none of that reduces fully to a rule. Confining independent AI judgment to a single seat, the desk, reads as a deliberate design choice to keep exactly this irreducible judgment somewhere explicit in the system.

8. The Future of Knowledge Work - Outlook and Limits

The direction this structure points in is clear. The more knowledge work is produced repeatedly - research, reports, newsletters, internal wikis - the more a well-designed pipeline, built once, becomes an asset that outlasts any individual's skill. But the limits deserve equal attention. Knowledge is harder to verify than code, staleness moves at different speeds across domains, and no number of loops fully replaces a human's final say wherever taste and judgment are required. Designing the pipeline itself is far from easy, either - deciding where and how much verification to place, and which errors deserve promotion into a rule, demands real domain knowledge and a fair amount of trial and failure.

Conclusion

The software factory and harness engineering were both born for code, but their skeleton - a deterministic layer wrapped around the model, a hard split between mechanical checks and qualitative judgment, self-improvement that promotes recurring errors into rules - carries over to knowledge production in large part intact. Knowledge, though, carries two burdens code never had: no machine can confirm its correctness, and it goes stale on its own as time passes. Design without acknowledging both, and a knowledge pipeline raises throughput while eroding trust. As of July 2026, efforts to automate knowledge work look like they're only just beginning to take this difference seriously.
