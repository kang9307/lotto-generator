AI 산출물 검수 체계 만들기 - 문법 검사가 놓치는 것들

구문·런타임·의미 3층 검사 설계와 오탐 관리, 그리고 일괄 치환의 함정

2026-07-27 개발/인프라

서론: 「검사 통과」는 「정상」이 아니다

AI에게 문서를 쓰게 하고, 설정 파일을 만들게 하고, 번역을 맡기는 일이 일상이 됐다. 여기서 진짜 병목은 생성이 아니라 검수다. 하루에 한 건을 손으로 만들던 시절에는 전부 읽어보고 내보낼 수 있었지만, 하루에 수십 건이 쏟아지면 전수 육안 검사는 물리적으로 불가능하다. 그래서 검사기를 붙인다. node --check가 통과하고, JSON이 파싱되고, 태그 개폐 수가 맞으면 초록불이 켜진다.

문제는 그 초록불이 켜진 산출물이 운영에서 터진다는 것이다. 원인은 대체로 검사기의 버그가 아니다. 검사기가 애초에 보지 않는 영역에서 결함이 났을 뿐이다. 검사 통과는 「이상이 없다」는 뜻이 아니라 「그 검사가 보는 범위 안에서 이상이 없다」는 뜻인데, 우리는 이 두 문장을 자꾸 같은 뜻으로 읽는다.

이건 도구 품질의 문제가 아니라 원리적 한계다. 라이스 정리(Rice's theorem)는 프로그램의 자명하지 않은 모든 의미적 성질이 결정 불가능하다고 말한다. 「이 프로그램이 모든 입력에서 종료하는가」 같은 동작에 관한 질문은, 「if-else 문을 포함하는가」 같은 형태에 관한 질문과 근본적으로 다르다. 따라서 코드만 보고 옳음을 일반적으로 판정하는 도구는 만들 수 없다. 실무 도구들은 이 벽을 우회한다. 건전한(sound) 분석기는 과대근사해서 오탐을 감수하고 미검출을 없애고, 완전한(complete) 분석기는 과소근사해서 미검출을 감수하고 오탐을 없앤다. ESLint나 SonarQube 같은 휴리스틱 도구는 둘 중 어느 보장도 포기하고 실용성을 택한다. 즉 우리가 매일 쓰는 검사기는 설계상 무언가를 반드시 놓치도록 만들어져 있다.

그렇다면 실무자가 할 일은 「완벽한 검사기 찾기」가 아니라 「무엇을 못 보는지 알고, 못 보는 영역을 다른 층으로 덮는 공정을 짜는 것」이다. 이 글은 산출물 전반 — 문서·번역·설정 파일·데이터 — 을 대상으로 그 공정을 어떻게 설계하는지 다룬다. 모델 성능을 평가하는 문제나 코드 리뷰를 자동화하는 문제와는 다른 축이다. 여기서 다루는 건 이미 만들어진 결과물을 내보내기 전에 거르는 공정이다.

1. 검사에는 층이 있다 - 구문·런타임·의미

검수를 하나의 덩어리로 보면 설계가 안 된다. 세 층으로 쪼개야 각 층이 무엇을 책임지는지 말할 수 있다.

  • 1층 구문(syntax) — 질문은 「파싱되는가」. 문자열이 규칙에 맞는 구조인지만 본다. 가장 싸고, 가장 빠르고, 가장 얕다.
  • 2층 런타임(runtime) — 질문은 「실제로 값이 되고 실행되는가」. 파싱된 결과를 평가하거나 실행하거나 렌더링해서, 살아 있는 상태를 관찰한다.
  • 3층 의미(semantic) — 질문은 「내용이 맞는가」. 값이 사실과 일치하는지, 문서가 말이 되는지, 번역이 원문과 같은 것을 말하는지 본다.

세 층의 성질을 표로 정리하면 다음과 같다.

층핵심 질문대표 수단잘 잡는 것원리적으로 못 잡는 것비용
구문파싱되는가node --check, JSON 파서, XML 스키마, 린터닫히지 않은 태그, 깨진 JSON, 오타 난 키워드실행해야 드러나는 동작, 값의 타당성매우 낮음(초 단위)
런타임값이 되고 실행되는가실제 파싱·평가, 헤드리스 렌더링, 단위 시험무한 재귀, 예외, 잘못된 부모에 들어간 요소, 깨진 참조실행 경로에 들어오지 않는 결함, 사실관계중간(분 단위)

여기서 가장 중요한 성질은 세 층이 병렬이 아니라 직렬이라는 점이다. 구문 검사를 백 개 추가해도 런타임 결함은 한 건도 줄지 않는다. 층이 올라갈수록 비용은 오르고 자동화율은 떨어지며, 아래층은 위층을 절대 대체하지 못한다. 검수 체계가 무너지는 전형적인 이유는 구문층만 촘촘하게 만들어 두고 「검사가 있으니 괜찮다」고 믿는 것이다.

2. 구문층이 절대 못 잡는 네 가지 사고

추상적으로 말하면 와닿지 않으니, 실제로 자주 나는 사고 유형 네 가지를 보자. 넷 다 구문 검사를 100% 통과한다.

2.1 문법은 완벽한데 무한 재귀로 죽는 경우

아래 함수는 파서 입장에서 흠잡을 데가 없다. 괄호도 맞고, 예약어도 맞고, 세미콜론도 맞다.

function resolveRoot(node) {
  // 의도: 최상위 노드를 찾아 올라간다
  return resolveRoot(node.parent || node);
}

node.parent가 null이 되는 순간 node 자기 자신이 다시 인자로 들어가고, 종료 조건이 없어 스택이 터진다. 구문 검사로는 절대 못 잡는다. 실행해 봐야만 드러난다. 이것이 런타임층이 필요한 가장 단순한 이유다.

2.2 태그 개폐는 맞는데 요소가 엉뚱한 부모에 들어간 경우

다음 조각은 여는 태그와 닫는 태그가 정확히 짝을 이룬다. 태그 개수를 세는 검사기는 그대로 통과시킨다.

<table>
  <li>첫째 항목</li>
  <li>둘째 항목</li>
</table>

그러나 li는 ul이나 ol의 자식이어야 한다. 브라우저 HTML 파서는 표 안에 들어온 이 요소들을 표 바깥으로 끌어내 버린다(foster parenting). 결과는 레이아웃이 조용히 무너진 페이지다. 검사는 초록불인데 화면은 깨져 있다. 개폐 짝만 세는 검사와 부모·자식 규칙을 아는 검사는 완전히 다른 물건이다.

2.3 숫자 형식은 맞는데 값이 사실과 다른 경우

{"unitPrice": 1200}은 JSON 스키마 입장에서 완벽한 정수다. 실제 단가가 12,000원이어도, 1,200달러여도, 아예 존재하지 않는 상품이어도 검사는 통과한다. 형식 검증기는 값의 타당성에 대해 아무 말도 하지 않는다. AI가 만든 설정 파일에서 특히 위험한 지점이 여기다. 구조는 학습된 패턴대로 완벽하게 나오는데, 그 안에 들어간 숫자는 근거가 없을 수 있다.

2.4 번역이 문법적으로 완벽한데 원문에 없는 내용이 생긴 경우

번역 품질을 재는 국제 표준 격인 MQM(Multidimensional Quality Metrics) 오류 유형을 보면, 정확성(Accuracy) 차원 아래에 Addition(원문에 없는 내용이 번역문에 들어감), Omission(원문에 있는 내용이 번역문에서 빠짐), Mistranslation(오역, 그 하위 항목에 기계번역 환각이 별도로 들어 있다)이 각각 독립된 오류 항목으로 정의돼 있다. 즉 번역 실패의 큰 축은 문법이 아니라 정보량 불일치다. 실제로 과·소번역을 다룬 연구는 현행 신경망 번역 시스템이 여전히 단어를 잘못 추가하거나 누락하며, 누락이 추가보다 더 자주 일어난다고 보고한다.

문법 검사기에 이 문장을 넣으면 아무 문제가 없다. 원문과 대조해야만, 혹은 원문·번역문의 숫자 집합을 비교해야만 드러난다.

3. 런타임층 설계 - 실행해야 드러나는 것

런타임층은 「파싱된다」와 「값이 된다」를 구분하는 층이다. 실무에서 효과가 큰 기법 다섯 가지를 정리한다.

  • 재직렬화 왕복(round-trip) — 파싱한 뒤 다시 문자열로 만들어 원본과 구조를 비교한다. 파서가 조용히 고쳐 준 부분이 차이로 드러난다. 관대한 파서일수록 이 기법의 가치가 크다.
  • 구조 규칙 검사 — 부모·자식 관계, 필수 필드, 상호 배타 필드처럼 형식이 아니라 문법 이상의 규칙을 검사한다. 2.2절의 사고가 여기서 잡힌다.
  • 개수 불변식(invariant) — 「같은 문서의 4개 언어 판본은 h2 개수·표 개수·목록 항목 수가 같아야 한다」 같은 규칙. 사실 확인 없이도 통째 누락을 잡아 준다.
  • 격리 실행 — 타임아웃과 메모리 상한을 걸고 실제로 돌려본다. 무한 재귀는 오직 여기서만 잡힌다. 반드시 별도 프로세스에서 돌려 본체가 같이 죽지 않게 한다.
  • 렌더 후 검사 — 헤드리스 브라우저로 그린 뒤 DOM을 다시 읽는다. 소스에서 옳아 보였지만 렌더 결과가 다른 경우를 잡는 마지막 그물이다.

세 층을 한 줄씩 명령으로 옮기면 차이가 분명해진다.

# 1층 구문 - 파싱되는가
node --check build/report.js

# 2층 런타임 - 값이 되는가 (타임아웃을 걸고 실제로 평가한다)
timeout 10 node -e "JSON.parse(require('fs').readFileSync('data/config.json','utf8'))"

# 2층 런타임 - 불변식을 함께 확인한다
node -e "const d=require('./data/config.json');
         if (!(d.retries >= 0 && d.retries <= 10)) throw new Error('retries 범위 이탈: '+d.retries);
         if (!d.endpoint.startsWith('https://')) throw new Error('endpoint 비보안: '+d.endpoint);"

2.2절의 부모 규칙 검사는 이렇게 짠다. 태그 개수를 세는 대신 파서가 인정한 트리를 순회한다.

const { JSDOM } = require('jsdom');
const doc = new JSDOM(html).window.document;

// li는 ul 또는 ol의 직계 자식이어야 한다
for (const li of doc.querySelectorAll('li')) {
  const parent = li.parentElement.tagName;
  if (parent !== 'UL' && parent !== 'OL') {
    throw new Error(`li가 ${parent} 안에 있음: ${li.textContent.slice(0, 30)}`);
  }
}

// 표의 각 행은 열 수가 같아야 한다
for (const table of doc.querySelectorAll('table')) {
  const widths = [...table.querySelectorAll('tr')].map(tr => tr.children.length);
  if (new Set(widths).size > 1) throw new Error('표 열 수 불일치: ' + widths.join(','));
}

중요한 것은 이 검사들이 전부 기계적 판정이라는 점이다. 사람 판단이 개입하지 않으므로 전수 자동화가 가능하고, 오탐도 거의 없다. 검수 예산은 이런 항목에 먼저 써야 한다.

4. 의미층 - 사람·교차 출처·LLM 판정의 분업

의미층에는 판정자가 셋 있고, 셋 다 결함이 있다. 어느 하나로 몰아주면 반드시 뚫린다.

4.1 교차 출처 대조

같은 사실을 독립된 두 출처에서 확인하는 방식이다. 의미 검사 가운데 자동화에 가장 가깝다. 다만 함정이 하나 있는데, 두 출처가 같은 원본을 인용하고 있으면 독립이 아니다. 언론 기사 두 개가 같은 보도자료를 옮긴 것이라면 교차 확인이 아니라 같은 정보를 두 번 본 것이다. 기관 원문·1차 자료까지 내려가야 실제 교차가 된다.

4.2 LLM 판정(LLM-as-judge)의 한계

싸고 빠르지만 편향이 있다. 「Judging the Judges」 연구는 LLM 판정자 15종을 MT-Bench와 DevBench 두 벤치마크, 22개 과제, 약 40개 생성 모델에 걸쳐 15만 건 이상 평가로 조사했다. 결론은 위치 편향(position bias)이 우연이 아니라 체계적이며 판정자와 과제에 따라 크게 달라진다는 것이다. 프롬프트 길이의 영향은 약했던 반면 후보 간 품질 격차가 클수록 편향이 강하게 나타났다. 별도 연구는 모델이 자기 출력을 과대평가하는 자기 선호 편향(self-preference bias)을 보고한다. 이 밖에 긴 답변을 선호하는 장황성 편향도 알려져 있다.

그렇다고 못 쓸 도구는 아니다. 한계를 알고 설계를 바꾸면 된다.

  • 순서를 뒤집어 두 번 묻는다. 두 번의 답이 일치하는 건만 채택한다. 위치 편향은 이 한 가지로 상당 부분 걸러진다.
  • 생성 모델과 판정 모델을 분리한다. 자기 선호 편향에 대한 가장 단순한 방어다.
  • 점수 대신 체크리스트를 쓴다. 「10점 만점에 몇 점」보다 「원문에 없는 문장이 있는가: 예/아니오」가 훨씬 재현성이 높다.
  • LLM 판정은 정렬 용도로만 쓴다. 합격·불합격을 결정하는 게이트가 아니라, 사람이 볼 순서를 정하는 우선순위 매기기로 쓴다. 상위 20건만 사람이 보면 되는 상황을 만드는 것이 목적이다.
  • 판정 결과를 표본으로 재검한다. 판정자도 검수 대상이다. 판정 결과 중 무작위 표본을 사람이 다시 보고 일치율을 기록한다.

4.3 사람 검수

가장 정확하지만 가장 비싸고, 무엇보다 표본이 작으면 못 본다. 이 한계는 감이 아니라 계산으로 말할 수 있다(9장). 사람 시간은 유한한 자원이므로 어디에 쓸지를 설계하는 것이 검수 체계의 절반이다.

5. 오탐이 검사기를 죽인다 - 경보 피로의 구조

정적 분석 연구 문헌은 도구가 버그라고 보고한 경고 가운데 대략 35~91%가 실제로는 조치 불가능(unactionable)하다고 정리한다. 범위가 이토록 넓다는 사실 자체가 「도구·프로젝트·설정에 따라 천차만별」이라는 뜻이고, 뒤집어 말하면 설정을 어떻게 하느냐가 결과를 좌우한다는 뜻이기도 하다.

오탐의 진짜 비용은 확인에 드는 시간이 아니다. 경보 피로(alert fatigue) — 경고가 잦으면 사람이 둔감해지고, 결국 진짜 경고까지 함께 무시된다. 늑대를 열 번 부른 검사기는 열한 번째 진짜 늑대를 막지 못한다. 실제로 개발자들이 시간 압박이나 경고 피로 때문에 경고를 무시하거나 억제한다는 관찰이 여러 연구에서 보고돼 왔고, 억제(suppression) 건수가 프로젝트 수명에 따라 계속 늘어나는 경향도 관찰됐다.

겪어 본 사례. 다국어 사이트 검증기가 「모든 언어 판본에 특정 공유 SDK가 있어야 한다」는 규칙을 걸고 있었다. 그런데 그 SDK는 애초에 한국어 페이지에만 넣는 것이 정책이었다. 그래서 매 실행마다 나머지 세 언어에서 같은 경고가 떴다. 늘 뜨는 경고라 아무도 읽지 않았고, 같은 줄에 함께 출력되던 진짜 오류(CSS 경로 오류)가 두 달간 묻혔다. 규칙을 「한국어 판본에만 요구」로 좁히자 그날 바로 진짜 오류가 눈에 들어왔다. 검사기가 늘 노란불이면 그건 검사기가 아니라 배경 소음이다.

여기서 팀이 흔히 내리는 선택 네 가지를 비교해 보면, 무엇이 최악인지 분명해진다.

대응단기 효과탐지력에 미치는 영향평가
규칙을 끈다경고가 사라짐해당 결함 유형을 영구히 못 잡음최악. 되돌릴 계기가 없다
임계값을 느슨하게 한다경고가 줄어듦경계선 결함이 조용히 통과나쁨. 어디까지 놓치는지 아무도 모름
경고를 그냥 무시한다없음경보 피로 심화, 진짜 경고까지 매몰나쁨. 검사기 자체가 무력화
적용 범위를 정확히 좁힌다해당 조건의 경고만 사라짐탐지력 유지, 신호 대 잡음비 개선정답. 다만 조건 파악에 품이 든다

핵심 원칙은 한 문장이다. 오탐의 해법은 규칙을 끄는 것이 아니라 규칙이 참인 조건을 정확히 기술하는 것이다. 「A 검사가 오탐을 낸다」는 말은 대개 「A 검사의 전제가 실제보다 넓게 잡혀 있다」는 뜻이다.

6. 규칙을 좁힌 다음에는 회귀 시험을 걸어라

규칙을 좁히면 반대 방향의 위험이 생긴다. 너무 좁혀서 진짜도 못 잡게 되는 것. 검사기가 조용해진 이유가 「결함이 없어서」인지 「검사기가 죽어서」인지 구분할 방법이 없으면, 좁히기는 규칙 끄기와 실질적으로 같아진다.

소프트웨어 시험 분야에 이미 답이 있다. 변이 시험(mutation testing) — 소스에 인공 결함(mutant)을 심고 테스트가 그것을 잡아내는지(kill) 확인해 테스트 자체의 결함 탐지력을 측정하는 기법이다. 잡아낸 비율이 변이 점수(mutation score)이고, 이 지표가 코드 커버리지보다 실제 결함 탐지력과 관계가 깊다고 보고된다. 커버리지는 「코드가 실행됐다」만 말하지만, 변이 점수는 「망가뜨렸을 때 실패했다」를 말하기 때문이다.

검수 파이프라인에도 그대로 옮길 수 있다. 이름을 붙이자면 회귀 시험(결함 심기)이다.

#!/usr/bin/env bash
# 검사기가 살아 있는지 확인한다 - 일부러 결함을 심고 잡히는지 본다
set -euo pipefail

WORK=$(mktemp -d)                       # 반드시 사본에서 작업한다
cp posts/sample.html "$WORK/sample.html"

# 결함 1: 닫는 태그 하나 제거
node -e "const fs=require('fs'); const p=process.argv[1];
         fs.writeFileSync(p, fs.readFileSync(p,'utf8').replace('</ul>',''));" "$WORK/sample.html"

if node validate.js "$WORK/sample.html"; then
  echo "FAIL: 검사기가 심어 둔 결함을 잡지 못했다"
  exit 1
else
  echo "OK: 정상 탐지"
fi

rm -rf "$WORK"                          # 원본은 손대지 않았다

심어 볼 만한 결함 목록은 팀마다 다르지만, 출발점으로 쓸 만한 것들은 다음과 같다.

  • 닫는 태그 하나 제거 — 구문층이 잡아야 한다
  • 속성 값의 닫는 따옴표 제거 — 구문층
  • JSON 배열 마지막 원소 뒤에 쉼표 추가 — 구문층
  • 목록 항목을 표 안으로 옮기기 — 런타임층(구조 규칙)
  • 재귀 함수의 종료 조건 삭제 — 런타임층(격리 실행)
  • 필수 메타 태그 삭제 — 구문층 또는 규칙 검사
  • 링크 도메인에 오타 한 글자 — 런타임층(HTTP 확인)
  • 숫자 자릿수 하나 변경 — 의미층(범위 불변식으로 일부만 잡힘)
  • 한 언어 판본에서 표 하나 통째 삭제 — 런타임층(개수 불변식)
  • 번역문에 원문에 없는 문장 한 줄 추가 — 의미층

이 목록을 돌리는 시점은 두 가지다. 정기(월 1회)와 규칙을 손댈 때마다. 안 잡히는 항목이 나오면 그것이 곧 다음에 뚫릴 구멍이다. 잡히지 않는 항목을 발견하는 것이 이 시험의 성공이라는 점을 팀에 미리 합의해 두는 편이 좋다. 그러지 않으면 아무도 이 시험을 돌리고 싶어 하지 않는다.

안전 수칙. 결함은 반드시 사본에 심는다. 원본에 심고 원복하는 방식은, 원복이 실패하는 순간 그 자체가 사고다. 임시 디렉터리에 복사해 돌리고 끝나면 통째로 지우는 편이 안전하다. 버전 관리 아래에 있다고 방심하지 말 것 — 원복 실패와 커밋이 겹치면 결함이 이력에 남는다.

7. 골든 파일과 스냅샷 - 「달라졌다」를 잡는 층

지금까지의 검사는 「규칙 위반인가」를 물었다. 여기에 하나를 더 얹을 수 있다. 「전과 달라졌는가」다. 기준 산출물을 저장해 두고 이후 산출물을 그것과 비교하는 방식으로, 부르는 이름이 여럿이다.

  • 골든 마스터(golden master) — 음반 마스터링에서 온 말. 기준이 되는 원본이라는 뜻이다.
  • 스냅샷 테스트(snapshot test) — Jest가 대중화한 이름. 첫 실행 때 만들어진 파일이 승인본이 된다.
  • 특성화 테스트(characterization test) — 마이클 페더스가 『레거시 코드 활용 전략』에서 쓴 말. 목적은 「바라는 동작」이 아니라 「지금의 실제 동작」을 기록하는 것이라고 정의된다.
  • 승인 테스트(approval test) — 르웰린 팔코가 제안한 이름. 스냅샷 테스트와 거의 같되 사용하기 전에 사람이 승인한다는 점이 다르다.

네 이름이 가리키는 기법은 사실상 같고, 목표도 하나다. 시스템이 다르게 동작하면 실패하는 시험을 갖는 것. AI 산출물 검수에서는 특히 「같은 입력에 대해 지난번과 구조가 달라졌다」를 잡는 데 유용하다.

다만 이 기법에는 널리 알려진 약점이 있다. 깨지기 쉽다는 것이다. 의도한 변경에도 계속 실패하므로 기준 파일을 끊임없이 갱신해야 하고, 갱신이 습관이 되면 실패를 읽지 않고 갱신부터 하는 상태가 된다. 그 순간 이 시험은 무의미해진다. 완화책은 다음과 같다.

  • 스냅샷을 코드처럼 다룬다. 코드 리뷰 대상에 포함시키고, 갱신 커밋을 그냥 통과시키지 않는다. 문헌이 권하는 가장 중요한 실천이다.
  • 스냅샷 대상을 좁힌다. 전체 HTML을 통째로 저장하면 공백 한 칸에도 깨진다. 대신 정규화한 구조 요약을 저장한다.
  • 자동 갱신을 기본값에서 뺀다. 승인 테스트 방식으로, 갱신에 명시적 의사표시를 요구한다.
  • 각 스냅샷에 설명을 붙인다. 「이 파일이 무엇을 보장하는가」를 한 줄 적어 두면, 나중에 깨졌을 때 갱신할지 고칠지 판단할 수 있다.

구조 요약 스냅샷은 이런 형태다. 문장 하나 고쳤다고 깨지지 않으면서, 표가 사라지거나 절이 통째로 빠지면 반드시 깨진다.

// 전체 본문이 아니라 구조만 뽑아 저장한다
function structureDigest(doc) {
  return {
    h2: [...doc.querySelectorAll('h2')].map(el => el.textContent.trim()),
    tables: doc.querySelectorAll('table').length,
    listItems: doc.querySelectorAll('li').length,
    codeBlocks: doc.querySelectorAll('pre code').length,
    links: [...doc.querySelectorAll('a[href]')].map(a => a.getAttribute('href')).sort()
  };
}

8. 일괄 처리의 위험 - 범위 기반 치환이 만드는 오염

검수를 자동화하면 다음 욕심이 반드시 생긴다. 교정도 자동화하고 싶어진다. 여기서 가장 큰 사고가 난다. 검사기는 잘못 짜면 시끄러워질 뿐이지만, 일괄 교정기는 잘못 짜면 수백 파일을 조용히 오염시킨다.

8.1 가장 흔한 실패 - 문자 오프셋으로 범위를 잡는 것

// 나쁜 예: 앞 2000자 안에서만 바꾼다
const head = html.slice(0, 2000).replace(/2025/g, '2026');
html = head + html.slice(2000);

2000자라는 경계는 문서 구조와 아무 관계가 없다. 어떤 파일은 그 안에 본문이 시작되고, 어떤 파일은 외부 스크립트 URL이 들어 있고, 어떤 파일은 헤드가 2000자를 넘겨 정작 바꿔야 할 대상이 범위 밖으로 나간다. 이 방식으로 수백 파일을 처리하면 반드시 예외가 생기고, 그 예외는 조용히 잘못된 값으로 남는다. 더 나쁜 건 결과물이 여전히 문법적으로 완벽하다는 점이다. 구문·런타임층 모두 통과한다.

8.2 두 번째 실패 - 경계 없는 정규식

단어를 바꾸는 치환에서 경계를 빼먹으면 다른 단어의 일부에 걸린다. 실제로 다국어 문서에서 특정 한자어를 우리말로 바꾸는 사전 치환을 돌렸다가, 경계가 없어 다른 단어 내부에 적중해 한자와 한글이 한 낱말로 붙은 문자열이 수백 건 생긴 사례를 겪었다. HTML은 멀쩡하고, 파싱도 되고, 렌더링도 된다. 사람이 읽어야만 이상한 글이었다. 이후 이 유형은 「한 낱말 안에 서로 다른 문자 체계가 섞였는가」를 보는 기계적 대리 지표로 상시 검출하도록 바꿨다. 의미 검사를 못 하면, 의미와 상관관계가 높은 기계적 지표를 찾는다 — 10장의 원칙이 여기서 나온다.

8.3 안전하게 일괄 처리하는 법

// 나은 예: 대상을 태그·속성으로 특정하고 경계를 명시한다
html = html.replace(
  /(<meta property="article:published_time" content=")[^"]*(")/,
  '$12026-07-27$2'
);

// 돌리기 전에 반드시 세어 본다
const hits = [...html.matchAll(/<meta property="article:published_time"[^>]*>/g)];
if (hits.length !== 1) throw new Error(`예상 1건, 실제 ${hits.length}건 - 중단`);

일괄 작업 안전 수칙을 표로 정리하면 다음과 같다. 이 표는 그대로 체크리스트로 써도 된다.

9. 표본 검수의 통계적 한계 - 스무 개 봐서 안 나오면 없는 건가

「스무 개 뽑아 봤는데 문제가 없었다」는 흔히 안심의 근거로 쓰인다. 계산해 보면 생각보다 약한 근거다.

결함률이 p인 모집단에서 무작위 표본 n개를 뽑았을 때, 결함을 하나라도 발견할 확률은 1 − (1 − p)n이다. 아래 표는 이 식을 그대로 계산한 값이다.

실제 결함률표본 5개표본 20개표본 50개표본 100개
10% (열에 하나)41.0%87.8%99.5%99.99%
5% (스물에 하나)22.6%64.2%92.3%99.4%
1% (백에 하나)4.9%18.2%39.5%63.4%
0.5% (이백에 하나)2.5%9.5%22.2%39.4%

표를 읽는 법은 이렇다.

  • 결함률 10%면 20개만 봐도 약 88% 확률로 걸린다. 흔한 결함은 작은 표본으로 충분히 잡힌다.
  • 결함률 1%면 20개를 봐도 18%다. 다섯 번 중 네 번은 그냥 통과한다. 드문 결함은 표본 검수로 사실상 안 잡힌다.
  • 1% 결함률을 95% 수준으로 확인하려면 약 300개를 봐야 한다. 이른바 3의 법칙(필요 표본 수가 대략 3 ÷ 결함률)이다.
  • 「앞에서 다섯 개만 본다」는 습관은 표본이 아니다. 무작위가 아니면 위 계산이 성립하지 않는다. 대개 앞쪽 산출물이 더 정성 들여 만들어져 있어 결과를 낙관 쪽으로 왜곡한다.

여기서 결론이 두 갈래로 갈린다.

  • 드물지만 치명적인 항목(공개 URL, 금액, 법적 문구, 개인정보 노출, 잘못된 연락처)은 표본 검수를 믿지 말고 전수 자동 검사를 만든다. 다행히 이런 항목은 판정 기준이 기계적이라 자동화도 상대적으로 쉽다.
  • 흔하지만 치명적이지 않은 항목(문체, 표현의 자연스러움, 제목 어감)은 무작위 표본으로 충분하다. 여기에 전수 검사를 붙이면 비용만 나가고 얻는 게 적다.

제조 품질관리는 이 균형을 이미 표로 만들어 두었다. ISO 2859-1(미국 규격으로는 ANSI/ASQ Z1.4)의 AQL 표는 로트 크기별로 뽑을 표본 수와 합격 판정 개수를 규정한다. 소프트웨어 산출물에 그대로 쓰기는 어렵지만, 「표본 수가 정해지는 순간 검출력도 함께 정해진다」는 사고방식은 그대로 가져올 만하다. 표본 수를 먼저 정하고 검출력을 나중에 묻는 순서는 거꾸로다.

10. 무엇을 자동화하고 무엇을 눈으로 볼 것인가

자동화 판단은 두 축으로 갈린다. 판정 기준이 기계적인가, 그리고 반복되는가.

반복 빈도 낮음반복 빈도 높음
판정 기준이 기계적일회성 스크립트로 처리하고 버린다최우선 자동화 대상. 여기부터 예산을 쓴다
판정 기준이 주관적사람이 직접 본다. 자동화 시도 자체가 낭비대리 지표 + 체크리스트 + 무작위 표본

비용 계산에서 자주 빠뜨리는 항목들이 있다.

  • 제작비보다 유지비가 크다. 산출물 형식이 바뀌면 규칙은 즉시 낡는다. 따라가지 못한 규칙은 오탐 공장이 된다.
  • 오탐 1건의 비용을 곱해서 넣어라. 하루 30건 오탐 × 확인 2분 = 하루 1시간이다. 여기에 경보 피로로 새어 나가는 진짜 결함의 비용이 더해진다.
  • 미검출 1건의 비용도 넣어라. 잘못된 공개 URL 하나, 틀린 금액 하나의 비용이 오탐 100건보다 클 수 있다. 두 비용의 크기 비교가 임계값 설정의 근거가 된다.
  • 자동화가 어려우면 대상을 바꿔라. 「번역이 정확한가」는 자동화가 어렵지만 「원문과 번역문의 숫자 목록이 일치하는가」는 쉽다.

마지막 항목이 실무에서 가장 값어치가 크다. 의미 검사를 직접 못 하면, 의미와 상관관계가 높은 기계적 대리 지표를 찾는다. 쓸 만한 대리 지표는 다음과 같다.

  • 숫자·URL·고유명사 집합 대조 — 원문과 번역문에서 추출해 집합으로 비교한다. 정보 추가·누락을 값싸게 잡는다.
  • 구조 개수 일치 — 언어별 판본의 절 수, 표 수, 목록 항목 수가 같은지 본다. 통째 누락 탐지에 강하다.
  • 분량 비율 이상치 — 언어별 길이 비율이 평소 범위를 벗어나면 표시한다. 언어마다 밀도가 다르므로 절대 길이가 아니라 평소 비율과 비교해야 한다.
  • 링크 상태 코드 전수 확인 — 깨진 링크는 판정이 완전히 기계적이라 자동화 효율이 가장 높은 축에 든다.
  • 문자 체계 혼입 검사 — 한 낱말 안에 서로 다른 문자 체계가 섞였는지 본다. 치환 사고·번역 사고를 동시에 잡는다.
  • 금칙어·폐지된 값 검사 — 바뀐 제도명, 폐지된 연락처처럼 「한때 옳았던 값」을 목록으로 관리한다. 사실 검증 중 유일하게 값싸게 자동화되는 부분이다.

11. 검수 공정을 조립하는 순서

처음부터 3층을 다 만들려고 하면 대개 실패한다. 순서가 있다.

  1. 사고 목록부터 만든다. 지난 3개월에 실제로 나간 결함을 적는다. 검사기는 상상한 결함이 아니라 실제로 났던 결함부터 막아야 한다. 이 목록이 없으면 만든 규칙의 우선순위를 정할 근거가 없다.
  2. 각 사고를 3층에 배치한다. 구문층에서 잡히는 것, 런타임층이 필요한 것, 의미층뿐인 것으로 나눈다. 2장의 표를 그대로 쓰면 된다.
  3. 구문·런타임층부터 전수 자동화한다. 싸고 빠르고 오탐이 적다. 여기서 걸리는 항목은 사람 손에 아예 가지 않게 만든다.
  4. 의미층은 대리 지표 + 무작위 표본으로 짠다. 치명 항목만 전수, 나머지는 표본. 표본 수를 정할 때 9장의 계산을 근거로 쓴다.
  5. 회귀 시험을 달력에 넣는다. 월 1회, 그리고 규칙을 수정할 때마다. 이 단계가 빠지면 위 네 단계는 시간이 지나며 조용히 썩는다.

운영 단계에서 지킬 규칙도 몇 가지 있다.

  • 결과는 두 값이 아니라 세 값으로 둔다. 통과 / 실패 / 확인 필요. 확인 필요를 실패로 취급하면 사람이 규칙을 끄고 싶어진다.
  • 새 규칙은 경고로 먼저 넣는다. 오탐률이 충분히 낮아진 것을 확인한 뒤 차단으로 승격한다. 처음부터 차단으로 넣으면 첫 오탐에 규칙이 삭제된다.
  • 억제를 쓸 때는 이유를 함께 남긴다. 이유 없는 억제는 시간이 지나면 아무도 손대지 못하는 지뢰가 된다. 억제 건수가 계속 늘고 있다면 그 자체가 규칙을 손봐야 한다는 신호다.
  • 어느 층까지 검사했는지 산출물에 기록한다. 사고가 났을 때 「검사를 안 했다」와 「검사했는데 못 잡았다」는 대응이 완전히 다르다. 후자만이 규칙 개선으로 이어진다.
  • 검사기 자체를 버전 관리한다. 규칙이 언제 어떻게 좁혀졌는지 이력이 남아야, 뒤늦게 발견한 미검출의 원인을 추적할 수 있다.

결론: 검사기는 통과 도장이 아니라 관측 장비다

검사기를 통과 도장으로 쓰면 반드시 진다. 도장은 「괜찮다」고 말하지만, 검사기는 그런 말을 할 능력이 없다. 검사기가 할 수 있는 말은 「내가 보는 범위 안에서는 이상이 없었다」뿐이고, 이 문장은 보는 범위가 명시돼 있을 때만 쓸모가 있다.

그래서 검사기는 관측 장비로 다뤄야 한다. 관측 장비의 사양서에는 측정 범위와 오차가 적혀 있다. 우리 검수 체계에도 같은 것이 필요하다. 어떤 층이 무엇을 보는지, 각 층이 무엇을 못 보는지, 그 사각을 무엇으로 덮는지, 그리고 장비가 아직 고장 나지 않았음을 어떻게 확인하는지. 마지막 항목이 회귀 시험이고, 대개 이것이 가장 먼저 빠진다.

정리하면 이렇다. 구문층은 싸니까 전부 켠다. 런타임층은 사고 유형의 상당수를 여기서만 잡을 수 있으니 반드시 만든다. 의미층은 전수를 포기하는 대신 치명 항목 전수 + 나머지 무작위 표본 + 기계적 대리 지표로 쪼갠다. 오탐이 나면 규칙을 끄지 말고 조건을 좁힌다. 좁힌 뒤에는 결함을 심어 탐지력이 살아 있는지 확인한다. 일괄 교정은 오프셋이 아니라 노드를 대상으로, 먼저 세어 보고, 멱등으로, 되돌릴 수 있게 한다.

AI가 만드는 산출물의 양은 계속 늘어난다. 그 흐름에서 병목은 언제나 검수 쪽에 생기고, 병목을 없애겠다며 검사를 얕게 만들면 초록불의 신뢰도만 떨어진다. 얕은 검사 백 개보다 층이 나뉜 검사 열 개가 낫다. 2026년 7월 기준으로, 잘 돌아가는 팀과 사고가 잦은 팀을 가르는 것은 모델 선택이 아니라 이 공정의 설계인 경우가 많다.
