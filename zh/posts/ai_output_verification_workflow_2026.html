搭建AI产出物审校体系 - 语法检查抓不到的那些问题

语法、运行时、语义三层的设计，误报的处置，以及批量替换的陷阱

2026年7月27日 开发/基础设施

引言：「检查通过」不等于「正常」

让AI写文档、生成配置文件、承担翻译已经成为日常。这套流程真正的瓶颈不是生成，而是审校。一天手工产出一件时，可以全部读完再发布；一天涌进几十件，全量人工过目在物理上就不可能了。于是我们挂上检查工具。node --check通过、JSON能解析、标签开闭数量对得上，绿灯就亮了。

问题在于，亮着绿灯的产出物照样会在生产环境出事。原因往往不是检查工具有缺陷，而是缺陷恰好落在检查工具根本不看的区域。检查通过并不表示「没有问题」，而是表示「在这项检查所看的范围内没有问题」，可我们总是把这两句话当成同一句读。

这不是工具质量问题，而是原理上的限制。赖斯定理指出，程序的一切非平凡语义性质都是不可判定的。「这个程序对所有输入都会停机吗」这类关于行为的提问，与「它是否包含if-else语句」这类关于形式的提问有本质区别。因此不可能造出仅凭读代码就普遍判断正确性的工具。实际工具都在绕开这堵墙：健全(sound)的分析器采用过近似，接受误报以消除漏报；完备(complete)的分析器采用欠近似，接受漏报以消除误报；而ESLint、SonarQube这类启发式工具干脆两种保证都放弃，选择实用性。换句话说，我们每天使用的检查工具，在设计上就注定会漏掉一些东西。

既然如此，从业者该做的不是「寻找完美的检查工具」，而是「弄清它看不到什么，再用另一层去覆盖看不到的区域」。本文以产出物整体为对象 — 文档、译文、配置文件、数据 — 讨论如何设计这条流水线。它与评估模型性能或自动化代码评审属于不同的轴。这里讨论的是把已经生成的成果在发布前筛一遍的工序。

1. 检查是分层的 - 语法、运行时、语义

把审校当成一整块看，就无法设计。拆成三层，才说得清每一层各自负责什么。

  • 第一层 语法(syntax) — 问题是「能否解析」。只看字符串是否符合结构规则。最便宜、最快、也最浅。
  • 第二层 运行时(runtime) — 问题是「是否真的成为值并运行」。对解析结果求值、执行或渲染，观察它活着的状态。
  • 第三层 语义(semantic) — 问题是「内容是否正确」。数值是否与事实相符，文档是否讲得通，译文是否与原文表达同一件事。

三层的性质整理成表格如下。

层核心问题典型手段擅长抓到原理上抓不到成本
语法能否解析node --check、JSON解析器、XML模式、Lint工具未闭合标签、损坏的JSON、拼错的关键字只在运行时显现的行为、数值是否合理极低（秒级）
运行时能否求值并运行真实解析与求值、无头渲染、单元测试无限递归、异常、放错父元素的节点、失效引用不在执行路径上的缺陷、事实层面的对错中等（分钟级）
语义内容是否正确人工审阅、交叉出处核对、LLM判定、代理指标事实错误、信息缺失或增添、表述别扭、脱离语境抽样之外的全部，且易受判定者偏差影响高（人力工时）

这里最重要的性质是三层是串联而非并联。再加一百条语法检查，运行时缺陷也不会减少一条。层级越高成本越高、自动化率越低，而且下层绝不能替代上层。审校体系崩塌的典型原因，就是把语法层做得密密麻麻，然后相信「有检查就没事」。

2. 语法层永远抓不到的四类事故

抽象地讲没有实感，下面看四种在实务中常见的事故形态。四种都能满分通过语法检查。

2.1 语法完美却因无限递归而崩溃

在解析器看来，下面这个函数无可挑剔。括号配对、关键字合法、分号齐全。

function resolveRoot(node) {
  // 意图：一路向上找到最顶层节点
  return resolveRoot(node.parent || node);
}

当node.parent变成null的那一刻，node自身又被当作参数传回去，没有终止条件，栈随即溢出。语法检查绝对看不到这一点，它只有在执行时才会暴露。这就是需要运行时层最朴素的理由。

2.2 标签开闭对得上，元素却挂在错误的父节点下

下面这段的开始标签与结束标签严格配对，数标签的检查工具会直接放行。

<table>
  <li>第一项</li>
  <li>第二项</li>
</table>

然而li必须是ul或ol的子元素。浏览器的HTML解析器会把落进表格里的这些元素拖到表格外面（即foster parenting）。结果就是悄然塌掉的页面布局。检查是绿灯，画面却是坏的。只数配对数量的检查，与懂得父子规则的检查，完全是两种东西。

2.3 数字格式正确但数值与事实不符

对JSON模式而言，{"unitPrice": 1200}是一个完美的整数。无论真实单价是12,000、货币单位不同，还是这件商品压根不存在，检查都会通过。格式校验器对数值是否合理只字不提。在AI生成的配置文件里，这一点尤其危险：结构会按学到的模式完美地输出，而其中的数字可能毫无依据。

2.4 译文语法完美却凭空多出原文没有的内容

翻译质量事实上的参照标准MQM(Multidimensional Quality Metrics)错误分类中，在准确性(Accuracy)维度之下分别定义了Addition（译文中出现原文没有的内容）、Omission（原文中有而译文缺失的内容）与Mistranslation（误译，其子项中还单列了机器翻译幻觉）这几类独立的错误。也就是说，翻译失败的一大主轴不是语法，而是信息量的不一致。研究过度翻译与欠额翻译的论文也报告，现行神经翻译系统仍会错误地增添与遗漏词语，而且遗漏比增添更常发生。

把这样的句子丢进语法检查器不会有任何问题。只有与原文逐一对照，或者比较原文与译文中的数字集合，它才会浮现。

事故形态语法层运行时层语义层最省钱的检测方式
无限递归或死循环抓不到抓得到不需要带超时的真实执行
元素挂在错误的父节点下抓不到抓得到不需要DOM解析后做父子规则校验
格式正确但数值错误抓不到基本抓不到抓得到取值范围不变式加交叉出处核对
译文内容的增添与遗漏抓不到抓不到抓得到数字、URL、专有名词的集合比对
失效链接抓不到抓得到不需要全量核对HTTP状态码
某个语言版本整张表缺失抓不到基本抓不到抓得到跨语言的结构计数不变式

3. 运行时层的设计 - 只有执行才会显现的东西

运行时层负责区分「能解析」与「能成为值」。实务中效果最大的五种手法如下。

  • 再序列化往返(round-trip) — 解析之后再序列化回字符串，与原文比较结构。解析器悄悄替你修好的部分会以差异的形式浮现。解析器越宽容，这一手法越有价值。
  • 结构规则校验 — 父子关系、必填字段、互斥字段等超出格式、属于文法之上的规则。2.2节的事故正是在这里被抓住。
  • 计数不变式(invariant) — 例如「同一篇文档的四个语言版本，h2数量、表格数量、列表项数量必须一致」。不做任何事实核对，也能抓出整块缺失。
  • 隔离执行 — 加上超时与内存上限，真的跑一遍。无限递归只有在这里才抓得到。务必放在独立进程中运行，避免主程序被一起拖垮。
  • 渲染后校验 — 用无头浏览器绘制之后再读回DOM。这是针对「源码看着没问题、渲染结果却不同」的最后一道网。

把三层各写成一行命令，差别就一目了然。

# 第一层 语法 - 能否解析
node --check build/report.js

# 第二层 运行时 - 能否成为值（加超时，真实求值）
timeout 10 node -e "JSON.parse(require('fs').readFileSync('data/config.json','utf8'))"

# 第二层 运行时 - 同时校验不变式
node -e "const d=require('./data/config.json');
         if (!(d.retries >= 0 && d.retries <= 10)) throw new Error('retries超出范围: '+d.retries);
         if (!d.endpoint.startsWith('https://')) throw new Error('endpoint不安全: '+d.endpoint);"

2.2节的父子规则校验这样写。不去数标签，而是遍历解析器认可的那棵树。

const { JSDOM } = require('jsdom');
const doc = new JSDOM(html).window.document;

// li必须是ul或ol的直接子元素
for (const li of doc.querySelectorAll('li')) {
  const parent = li.parentElement.tagName;
  if (parent !== 'UL' && parent !== 'OL') {
    throw new Error(`li位于${parent}之内: ${li.textContent.slice(0, 30)}`);
  }
}

// 表格每一行的列数必须一致
for (const table of doc.querySelectorAll('table')) {
  const widths = [...table.querySelectorAll('tr')].map(tr => tr.children.length);
  if (new Set(widths).size > 1) throw new Error('列数不一致: ' + widths.join(','));
}

关键在于这些校验全都是机械判定。不掺入人的判断，因此可以全量自动化，误报也极少。审校预算应当优先花在这类项目上。

4. 语义层 - 人、交叉出处与LLM判定的分工

语义层有三个判定者，三个都有缺陷。把担子压在其中任何一个身上，都必然被突破。

4.1 交叉出处核对

就是在两个独立出处确认同一事实。在语义检查中，这一项最接近可自动化。但有一个陷阱：如果两个出处引用的是同一份原始材料，它们并不独立。两篇新闻若都转述同一份通稿，那不是交叉核对，只是把同一条信息看了两遍。必须下沉到机构原文或一手资料，交叉才算成立。

4.2 LLM判定(LLM-as-judge)的局限

便宜又快，但带偏差。名为「Judging the Judges」的研究考察了15种LLM判定模型，覆盖MT-Bench与DevBench两个基准、22项任务、约40个生成模型，产生了超过15万条评估记录。结论是位置偏差(position bias)是系统性的而非随机的，并且因判定者与任务而差异显著。提示词长度的影响较弱，而候选之间质量差距越大，偏差越强。另有研究报告了模型高估自身输出的自我偏好偏差(self-preference bias)。此外还有偏爱长答案的冗长性偏差。

这并不意味着它不能用。知道局限，改一改设计即可。

  • 调换顺序问两次。只采纳两次答案一致的结果。仅此一招就能滤掉相当一部分位置偏差。
  • 把生成模型与判定模型分开。这是应对自我偏好偏差最朴素的防线。
  • 用清单替代打分。「是否存在原文没有的句子：是/否」比「满分十分打几分」的可复现性高得多。
  • LLM判定只用于排序。不作为决定放行与否的门禁，而作为决定人工先看哪一份的优先级排序。目标是造出「只看前二十条就够」的局面。
  • 对判定结果做抽样复核。判定者本身也是审校对象。从判定结果中随机抽样交由人复看，并记录一致率。

4.3 人工审阅

最准确，也最贵，而且抽样一小就看不见。这个局限可以用计算而非直觉来陈述（见第9章）。人的时间是有限资源，因此设计它花在哪里就占了审校体系的一半。

5. 误报会杀死检查工具 - 告警疲劳的结构

静态分析的研究文献归纳指出，工具报告为缺陷的告警中大约35%至91%实际上无需处理(unactionable)。区间跨度如此之大，本身就说明「因工具、项目与配置而千差万别」；反过来说，也意味着配置方式决定结果。

误报真正的代价不是确认它所花的时间，而是告警疲劳(alert fatigue) — 告警一频繁，人就会麻木，最后连真告警也一并被忽略。喊过十次狼来了的检查工具，拦不住第十一次真正的狼。多项研究观察到开发者会因时间压力或告警疲劳而忽略、压制告警，也观察到压制(suppression)的数量会随项目寿命持续增加。

我亲历的一个例子。某个多语言站点的校验工具设了一条规则：「所有语言版本都必须包含某个分享SDK」。可那个SDK按方针本来就只加在韩语页面上。于是每次运行，其余三种语言都会冒出同一条告警。因为它总在那儿，没人再去读，结果同一行里一起输出的真实错误（CSS路径错误）被埋了两个月。把规则收窄为「仅对韩语版本要求」之后，当天就看见了那个真错误。一个永远亮着黄灯的检查工具，不是检查工具，而是背景噪音。

把团队常见的四种应对方式放在一起比较，最差的那种就很清楚了。

应对方式短期效果对检测能力的影响评价
关掉规则告警消失该类缺陷从此再也抓不到最差。没有任何契机让人再打开它
调松阈值告警减少处于边界的缺陷悄悄通过差。没人知道究竟漏掉了多少
直接无视告警无告警疲劳加深，真告警一并被埋差。检查工具本身被架空
精确收窄适用范围只有该条件下的告警消失检测能力保留，信噪比改善正解。只是弄清条件要花力气

原则一句话就够。误报的解法不是关掉规则，而是准确写出这条规则成立的条件。「A检查会误报」这句话，多半意味着「A检查的前提被设得比现实更宽」。

6. 收窄规则之后，要给它挂上回归试验

收窄会带来反方向的风险：收得太窄，连真缺陷也抓不到了。如果无法区分检查工具安静下来是因为「没有缺陷」还是因为「它已经死了」，那么收窄与关掉在实质上就是一回事。

软件测试领域早有答案。变异测试(mutation testing) — 在源码中植入人造缺陷(mutant)，看测试是否能杀死它，从而衡量测试自身的缺陷检出能力。被杀死的比例就是变异得分，据报告这一指标与真实缺陷检出能力的相关性强于代码覆盖率。覆盖率只能说「这段代码跑过了」，而变异得分能说「我把它弄坏时，有东西失败了」。

这套思路可以原样搬到审校流水线上。给它起个名字，就叫回归试验（植入缺陷）。

#!/usr/bin/env bash
# 确认检查工具还活着 - 故意植入缺陷，看它是否被抓到
set -euo pipefail

WORK=$(mktemp -d)                       # 一律在副本上操作
cp posts/sample.html "$WORK/sample.html"

# 缺陷1：删掉一个结束标签
node -e "const fs=require('fs'); const p=process.argv[1];
         fs.writeFileSync(p, fs.readFileSync(p,'utf8').replace('</ul>',''));" "$WORK/sample.html"

if node validate.js "$WORK/sample.html"; then
  echo "FAIL: 检查工具没有抓到植入的缺陷"
  exit 1
else
  echo "OK: 正常检出"
fi

rm -rf "$WORK"                          # 原件从未被动过

值得植入的缺陷清单因团队而异，下面这些可以作为起点。

  • 删掉一个结束标签 — 语法层应当抓到
  • 删掉属性值的右引号 — 语法层
  • 在JSON数组最后一个元素后加逗号 — 语法层
  • 把列表项挪进表格里 — 运行时层（结构规则）
  • 删除递归函数的终止条件 — 运行时层（隔离执行）
  • 删除必需的meta标签 — 语法层或规则校验
  • 在链接域名里插入一个错别字符 — 运行时层（HTTP核对）
  • 改动数字的某一位 — 语义层（取值范围不变式只能抓到一部分）
  • 从某个语言版本中整张删掉一个表格 — 运行时层（计数不变式）
  • 在译文中加一句原文没有的话 — 语义层

跑这份清单有两个时机：定期（每月一次），以及每次改动规则时。凡是没被抓到的项，就正是下一次会被突破的口子。最好事先与团队约定：发现没被抓到的项，才是这项试验的成功。否则没人愿意去跑它。

安全须知。缺陷务必植入副本。在原件上植入再还原的做法，一旦还原失败，本身就成了事故。复制到临时目录里跑，跑完整个删掉更安全。不要因为文件在版本管理之下就掉以轻心 — 还原失败若与一次提交撞上，缺陷就留在历史里了。

7. 黄金文件与快照 - 抓住「变了」的那一层

到目前为止的检查问的都是「是否违规」。这里还可以再加一问：「与之前相比是否变了」。做法是保存一份基准产出物，把之后的产出物与它比对。这套技术有好几个名字。

  • 黄金母带(golden master) — 源自唱片母带制作，意为作为基准的原件。
  • 快照测试(snapshot test) — Jest带火的名字，首次运行生成的文件成为被批准的版本。
  • 特征化测试(characterization test) — 迈克尔·费瑟斯在《修改遗留代码的艺术》中使用的说法，其目的被定义为记录「系统当下的实际行为」而非「你希望它有的行为」。
  • 批准测试(approval test) — 卢埃林·法尔科提出的名字，与快照测试几乎相同，区别在于使用之前需由人批准。

这四个名字指向的其实是同一种技术，目标也只有一个：拥有一组「系统行为一变就失败」的测试。在AI产出物的审校中，它尤其擅长抓住「同样的输入，这次的结构与上次不同了」。

但这套技术有个众所周知的弱点：易碎。有意的改动也会让它失败，于是基准文件必须不断更新；一旦更新成了习惯，就会进入不读失败信息直接更新的状态。那一刻起，这项测试就失去意义了。缓解办法如下。

  • 把快照当作代码对待。纳入代码评审，不让更新提交直接通过。文献将其列为最重要的实践。
  • 收窄快照的对象。整份HTML照单全存，一个空格就会让它崩。改存归一化之后的结构摘要。
  • 把自动更新移出默认行为。参照批准测试的做法，要求更新必须有明确的意思表示。
  • 给每份快照写一句说明。写清「这份文件保证的是什么」，日后失败时才判断得出该更新还是该修复。

结构摘要快照长这样。改一句话不会让它崩，但表格消失或整节缺失时它必然会崩。

// 不存正文全文，只抽出结构
function structureDigest(doc) {
  return {
    h2: [...doc.querySelectorAll('h2')].map(el => el.textContent.trim()),
    tables: doc.querySelectorAll('table').length,
    listItems: doc.querySelectorAll('li').length,
    codeBlocks: doc.querySelectorAll('pre code').length,
    links: [...doc.querySelectorAll('a[href]')].map(a => a.getAttribute('href')).sort()
  };
}

8. 批量处理的风险 - 按范围替换所造成的污染

把审校自动化之后，下一个念头必然冒出来：修正也想自动化。最大的事故就发生在这里。检查工具写砸了顶多变吵，批量修正工具写砸了会悄无声息地污染几百个文件。

8.1 最常见的失败 - 用字符偏移量圈定范围

// 坏例子：只在前2000个字符里替换
const head = html.slice(0, 2000).replace(/2025/g, '2026');
html = head + html.slice(2000);

2000这个边界与文档结构毫无关系。有的文件正文在这个范围内就开始了，有的文件这里放着外部脚本的URL，还有的文件头部超过2000字符、真正要改的目标反而落在范围之外。用这种方式处理几百个文件，必然产生例外，而这些例外会作为错误的值悄悄留下来。更糟的是，结果在语法上依然完美，语法层与运行时层都会放行。

8.2 第二种失败 - 没有边界的正则表达式

做词一级的替换时若漏掉边界，就会命中另一个词的一部分。我确实在多语言文档中跑过一次词典替换，想把某些汉字词换成更通俗的写法，结果因为没有边界而击中了无关词语的内部，产生了几百处把两种文字体系粘成一个词的字符串。HTML完好无损，能解析，也能渲染，只有人读起来才觉得不对劲。此后这一类问题被改为用「一个词内是否混入了不同文字体系」这一机械代理指标常态化检出。做不了语义检查，就去找与语义高度相关的机械指标 — 第10章的原则正出自这里。

8.3 如何安全地做批量处理

// 好例子：把对象锁定到具体标签与属性，并写明边界
html = html.replace(
  /(<meta property="article:published_time" content=")[^"]*(")/,
  '$12026-07-27$2'
);

// 跑之前一定先数一遍
const hits = [...html.matchAll(/<meta property="article:published_time"[^>]*>/g)];
if (hits.length !== 1) throw new Error(`预期1处，实际${hits.length}处 - 中止`);

批量作业的安全守则整理成表如下。这张表可以直接当作检查清单使用。

守则具体做法可以避免的事故
以节点为对象以标签、属性、段落为对象，而不是字符位置范围之外的污染
在正则里写明边界属性值用引号边界围住，词用词边界围住命中另一个词的内部
先数一遍输出待改动的数量，与预期不符就中止范围判断失误
用眼睛看一处打印首个匹配前后各40个字符确认后再全量执行规则本身设计错误
做成幂等跑第二遍若还有改动，说明规则有问题重复施加与累积损坏
保证可回退作业前单独提交一次，或保留副本无法恢复
结束后重跑三层尤其要重做语义层的随机抽样审阅修正所引入的新缺陷

9. 抽样检查的统计极限 - 看了二十件没问题，就等于没有吗

「抽了二十件都没问题」常被当作放心的依据。算一下就会发现，这个依据比想象中弱得多。

在缺陷率为p的总体中随机抽取n件时，至少发现一个缺陷的概率是 1 − (1 − p)n。下表就是这个公式的直接计算结果。

实际缺陷率抽5件抽20件抽50件抽100件
10%（十件一件）41.0%87.8%99.5%99.99%
5%（二十件一件）22.6%64.2%92.3%99.4%
1%（百件一件）4.9%18.2%39.5%63.4%
0.5%（两百件一件）2.5%9.5%22.2%39.4%

这张表该这样读。

  • 缺陷率10%时，只看20件就有约88%的概率命中。常见缺陷用小样本就足以抓到。
  • 缺陷率1%时，看20件也只有18%。五次里有四次就这么过去了。罕见缺陷靠抽样检查实际上抓不到。
  • 要以95%的水平确认1%的缺陷率，大约需要看300件。这就是所谓的三倍法则（所需件数约为3除以缺陷率）。
  • 「只看开头五件」的习惯根本不是抽样。不随机，上面的计算就不成立。靠前的产出物通常做得更用心，会把结果朝乐观一侧扭曲。

结论从这里分成两支。

  • 罕见但致命的项目（公开URL、金额、法律措辞、个人信息外泄、已废止的联系方式）不要指望抽样，要建立全量自动检查。所幸这类项目的判定标准是机械的，自动化也相对容易。
  • 常见但不致命的项目（文风、表述是否自然、标题的语感）用随机抽样就够了。在这里加全量检查，花费很大而收益很小。

制造业的质量管理早就把这种平衡做成了表。ISO 2859-1（美国规格为ANSI/ASQ Z1.4）的AQL抽样表规定了不同批量下应抽取的件数与合格判定数。它未必能原封不动地套到软件产出物上，但「抽样件数一确定，检出能力也就随之确定」这种思路完全可以拿来用。先定抽样件数、事后才问检出能力，顺序是反的。

10. 什么该自动化，什么该用眼睛看

自动化的判断沿两个轴展开：判定标准是否机械，以及是否重复发生。

重复频率低重复频率高
判定标准机械写个一次性脚本处理完就丢最优先自动化。预算从这里开始花
判定标准主观人直接看。试图自动化本身就是浪费代理指标＋检查清单＋随机抽样

成本核算中经常被漏掉的项目有这些。

  • 维护成本高于建设成本。产出物格式一变，规则立刻过时，跟不上的规则会变成误报工厂。
  • 把单条误报的成本乘出来。一天30条误报×每条确认2分钟＝一天1小时，还要加上告警疲劳所漏掉的真缺陷的代价。
  • 也要把单次漏检的成本算进去。一个错误的公开URL、一个错误的金额，代价可能超过一百条误报。这两项成本孰大孰小，正是设定阈值的依据。
  • 自动化难就换个对象。「译文是否准确」难以自动化，「原文与译文的数字列表是否一致」却很容易。

最后这一条在实务中最值钱。直接检查语义做不到时，就去找与语义高度相关的机械代理指标。好用的代理指标如下。

  • 数字、URL、专有名词的集合比对 — 从原文与译文中抽取后按集合比较，能以很低的成本抓出信息的增添与遗漏。
  • 结构计数一致性 — 检查各语言版本的小节数、表格数、列表项数是否相同，对整块缺失的检出很强。
  • 篇幅比例离群 — 某语言的长度比例偏离常态区间时予以标记。各语言密度不同，因此要比较的是平日的比例而非绝对长度。
  • 链接状态码全量核对 — 失效链接的判定完全机械，属于自动化收益最高的一类。
  • 文字体系混入检查 — 检查一个词内是否混入了不同的文字体系，能同时抓住替换事故与翻译事故。
  • 禁用词与失效值检查 — 把更名的制度、已停用的联系方式这类「曾经正确的值」做成清单管理。这是事实核查中唯一能廉价自动化的部分。

11. 组装审校流水线的顺序

一上来就想把三层全部建好，多半会失败。它是有顺序的。

  1. 先列事故清单。写下最近三个月真正流出去的缺陷。检查工具应当优先堵住真实发生过的缺陷，而不是想象中的缺陷。没有这份清单，就没有排定规则优先级的依据。
  2. 把每个事故归入某一层。分成语法层能抓的、需要运行时层的、只有语义层才行的。第2章那张表可以直接拿来用。
  3. 先把语法层与运行时层全量自动化。它们便宜、快、误报少。凡是在这里被抓住的项目，就不要让它流到人手里。
  4. 语义层用代理指标加随机抽样来搭。只对致命项目做全量，其余抽样；确定抽样件数时以第9章的计算为依据。
  5. 把回归试验写进日程。每月一次，外加每次修改规则时。少了这一步，上面四步会随时间悄悄腐烂。

进入运营阶段还有几条规矩要守。

  • 结果要有三个值而不是两个。通过 / 不通过 / 待确认。把「待确认」当成不通过，人就会想去关掉规则。
  • 新规则先以告警形式引入。确认误报率已足够低，再升级为拦截。一开始就设成拦截，第一次误报就会让规则被删掉。
  • 使用压制时一并写下理由。没有理由的压制，时间一长就成了没人敢碰的地雷。压制数量持续上升本身，就是该动一动规则的信号。
  • 把检查到了哪一层记录在产出物上。出事时，「压根没检查」与「检查了却没抓到」的应对完全不同，而只有后者能带来规则改进。
  • 把检查工具本身纳入版本管理。唯有留下规则何时、如何被收窄的历史，才能追查日后才发现的漏检的成因。

结论：检查工具不是合格章，而是观测仪器

把检查工具当合格章用，必输。章子说的是「没问题」，而检查工具没有能力说这句话。它能说的只有「在我所看的范围内没有异常」，而这句话只有在所看范围被写明时才有用。

所以检查工具应当被当作观测仪器来对待。仪器的规格书上写着测量范围与误差。我们的审校体系也需要同样的东西：哪一层看什么，各层看不到什么，盲区靠什么覆盖，以及如何确认仪器还没坏。最后这一项就是回归试验，而它通常是最先被省掉的。

总结起来是这样。语法层便宜，全部打开。运行时层是相当一部分事故形态唯一能被抓住的地方，必须建。语义层放弃全量，改为拆成致命项目全量＋其余随机抽样＋机械代理指标。出现误报时不要关规则，而要收窄条件。收窄之后要植入缺陷，确认检出能力还活着。批量修正要以节点而非偏移量为对象，先数一遍，做成幂等，并保证可回退。

AI产出物的数量还会继续增长。在这股洪流中，瓶颈总会出现在审校一侧；而为了疏通瓶颈把检查做浅，只会让绿灯的可信度下降。一百项浅检查不如十项分好层的检查。截至2026年7月，把运转顺畅的团队与事故不断的团队区分开的，往往不是模型选型，而是这条流水线的设计。
