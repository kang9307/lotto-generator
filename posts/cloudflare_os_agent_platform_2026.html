서론: 발표문에서 먼저 읽어야 하는 문장

에이전트 플랫폼 발표는 대체로 같은 얼굴을 하고 있다. 대화창이 있고, 사내 데이터에 연결되고, 자동화가 된다는 이야기다. 이번 것도 겉모습은 다르지 않다. 다만 Cloudflare OS에는 다른 문장이 하나 붙어 있다. 서버 코드가 글로벌 아웃바운드 네트워킹이 꺼진 상태의 Dynamic Worker에서 돈다는 문장이다.

이 한 줄이 제품 소개가 아니라 배치 결정의 시작점이다. 아웃바운드가 기본으로 닫혀 있다는 건 보안 설명이기도 하지만, 동시에 이 플랫폼이 받아 줄 수 있는 작업의 모양을 이미 정해 버렸다는 뜻이기도 하다. 임의의 외부 호출이 필요한 코드는 여기서 그냥 안 돈다. 그리고 그 자리를 메우려고 나온 것이 Gatekeeper다.

Cloudflare는 2026년 8월 5일 Agents Week 기간에 Cloudflare OS를 오픈소스로 공개했다. 사내에서 쓰던 도구를 다시 만들어 내놓은 것이고, 라이선스는 Apache-2.0이며, 자기 Cloudflare 계정에 직접 배치해서 자기 Access 정책과 AI Gateway 설정으로 돌릴 수 있다.

이 글은 기능 목록을 따라가지 않는다. 대신 「내 워크로드를 여기 올릴 이유가 있나」 하나로 착지한다. 무엇이 묶였는지, 실행 모델이 무엇을 강제하는지, 어떤 작업이 맞고 어떤 작업이 구조적으로 안 맞는지, 그리고 지금 시점에 운영에 올리면 안 되는 이유까지 간다.

같은 회사, 반대 방향의 제품과 헷갈리지 말 것. Cloudflare는 사이트에 들어오는 AI 에이전트를 가려내는 쪽 기술도 따로 내놓고 있다. 그쪽은 Precursor 등장 - Cloudflare가 세션 전체 행동으로 AI 에이전트를 가려내는 이유에서 다뤘다. 이 글은 정반대 축, 즉 에이전트를 굴리는 쪽 런타임 이야기다. 같은 회사가 같은 주에 양쪽을 다 내놓았다는 사실 자체가 이 시장의 지금 상태를 보여 준다.

1. Cloudflare OS가 실제로 묶은 세 덩어리

이름이 OS라 오해하기 쉬운데, 새 운영체제도 아니고 새 인프라 계층도 아니다. 성격을 정확히 잡아야 검토 방향이 안 어긋난다.

1.1 신제품인가, 재편인가

둘 다 아니다. Cloudflare가 사내에서 쓰던 애플리케이션을 다시 만들어 오픈소스로 공개한 것이다. 발표문의 표현 그대로 「오늘 우리는 Cloudflare OS의 새 버전을 오픈소스로 공개한다」이고, 첫 버전은 같은 해 5월에 전 직원에게 열어 둔 사내 도구였다. 엔지니어링 밖의 사람들이 문서를 쓰고 슬라이드를 만들고 반복 업무를 자동화하는 데 쓰기 시작했다고 밝혔다.

  • Cloudflare 계정 안에 배치하는 애플리케이션이지, 새로 구독하는 클라우드가 아니다
  • 그래서 검토의 첫 질문이 「새 벤더를 쓸 것인가」가 아니라 「우리 Cloudflare 계정 안에 이걸 놓을 것인가」로 바뀐다
  • 이미 Workers와 Access를 쓰고 있다면 검토 비용이 확연히 낮고, 안 쓰고 있다면 계정 개설부터 Access 정책 설계까지가 전부 선행 작업이 된다
  • 사내 배포 실적이 있다는 점은 근거로 값어치가 있다. 데모용으로 만든 것이 아니라 수천 명이 매일 쓰던 것을 다시 만든 결과물이다

1.2 세 덩어리로 나눠 보면

발표는 이것을 세 부분의 결합으로 설명한다. 이 셋은 서로 독립적으로 값어치를 갖는 것이 아니라, 앞의 것이 뒤의 것을 필요로 하는 순서로 쌓여 있다.

  • 에이전트 작업 공간. 회사가 큐레이션한 맥락과 스킬이 미리 실려 있고, 에이전트가 코드를 쓰고 실행할 수 있는 격리 런타임이 붙어 있다
  • 보안과 거버넌스 프레임워크. 사내 데이터와 서비스에 안전하게 닿기 위한 층이다. 모든 에이전트와 앱이 아무 접근 권한 없이 시작한다는 것이 출발점이다
  • 개인이 고칠 수 있는 앱 플랫폼. 사람들이 만들고 공유하고 계속 고칠 수 있는 앱을 위한 실행 기반이다
  • 첫 덩어리만 있으면 사내 데이터에 붙는 순간 위험해지고, 둘째 덩어리만 있으면 쓸 데가 없다. 셋째는 앞의 둘이 있어야 결과물이 남는 형태가 된다
  • 조사와 질의는 데이터 전체를 모델 컨텍스트 창에 밀어 넣는 대신 코드 실행으로 검색하고 분석하는 방식을 쓴다고 밝혔다. 컨텍스트 창 예산을 자원 규모와 분리하려는 설계다
  • 생성된 문서와 스프레드시트는 원본 데이터 소스에 연결된 상태로 남아 원본이 바뀌면 같이 갱신된다. 필요하면 익숙한 형식으로 내보낼 수도 있다

1.3 구성 요소와 각자의 역할

발표에 실제로 등장한 구성 요소만 정리하면 이렇다. 이 표에 없는 제품은 이 발표에서 언급되지 않았다.

구성 요소맡는 일이 선택이 만드는 성질
Cloudflare Workers서버 코드가 도는 런타임 기반V8 격리 기반이라 기동이 빠른 대신 런타임 한도가 그대로 앱 한도가 된다
Dynamic Workers앱별 서버 코드를 필요할 때 적재앱마다 별도 배포 절차가 사라진다
Durable Object Facets앱 인스턴스와 상태의 거처앱마다 자기 SQLite를 갖고, 런타임 저장소와 분리된다
Cloudflare Access작업 공간 진입 인증과 인가기존 사내 아이덴티티 정책을 그대로 쓴다
AI Gateway모델 라우팅, 비용 통제, 사용 귀속모든 추론이 한 지점을 지나므로 예산과 한도를 걸 수 있다
Gatekeeper외부 서비스별 권한 중개 Worker자격 증명이 에이전트 쪽으로 넘어가지 않는다
MCP · MCP Server Portals이미 쓰던 MCP 서버 연결기존 도구 연결 자산을 버리지 않아도 된다
Cap'n Web브라우저와 서버 사이 RPC사람이 만든 인터페이스를 에이전트가 그대로 호출한다

여기서 눈여겨볼 것은 마지막 열이다. 구성 요소 하나하나가 편의 기능이 아니라 제약을 하나씩 만들어 낸다. 그리고 제약의 합이 곧 이 플랫폼에 올릴 수 있는 작업의 모양이다.

2. 에이전트 실행 모델 - 앱 하나가 Worker 하나다

실행 모델을 한 문장으로 줄이면 이렇다. 에이전트가 만든 앱은 전부 Worker다. 이 문장에서 나머지가 전부 따라 나온다.

2.1 클라이언트 코드와 서버 코드가 함께 생성된다

작업 공간에 앱을 만들어 달라고 하면 에이전트는 두 부분을 쓴다. 브라우저에서 화면을 그리는 클라이언트 코드, 그리고 상태를 저장하고 동작을 구현하는 서버 코드다. 서버 쪽은 필요할 때 Dynamic Worker로 적재되고 Durable Object Facet으로 인스턴스화된다. 각 앱은 자기 SQLite 데이터베이스를 갖는데, 이 데이터베이스는 앱을 관리하는 Cloudflare OS 런타임과 분리되어 있다.

브라우저
  └─ 클라이언트 코드 (샌드박스 프레임)
        │  Cap'n Web RPC
        ▼
Dynamic Worker  ← 요청 시 적재
  └─ Durable Object Facet
        └─ 앱 전용 SQLite  (런타임 저장소와 분리)

바깥으로 나가는 길은 Gatekeeper가 준 케이퍼빌리티뿐

클라이언트에서 서버를 부르는 모양은 원격 호출처럼 보이지 않는다. 발표에 실린 예시는 이런 형태다.

const issues = await app.listIssues({
  status: "done",
});
  • 브라우저 클라이언트는 Cap'n Web으로 서버와 이야기한다. Cloudflare가 공개한 오브젝트 케이퍼빌리티 방식 RPC다
  • 덕분에 사람이 만든 인터페이스와 에이전트가 부르는 인터페이스가 같은 것이 된다. 에이전트 전용 API를 따로 만들 필요가 없다
  • 앱마다 데이터베이스가 분리되어 있으니 앱 하나의 스키마 사고가 다른 앱으로 번지지 않는다
  • 반대로 앱 사이에 데이터를 공유하려면 명시적으로 그 경로를 만들어야 한다. 편의 대신 격리를 고른 설계다

2.2 아웃바운드가 기본으로 닫혀 있다는 뜻

이 플랫폼의 성격을 가장 크게 정하는 제약이다. 서버 코드는 글로벌 아웃바운드 네트워킹이 비활성화된 Dynamic Worker에서 돌고, 클라이언트 코드는 브라우저의 샌드박스 프레임에서 돈다. 양쪽 모두 명시적으로 제공된 케이퍼빌리티를 통해서만 외부 시스템에 닿는다.

  • 에이전트가 만든 코드가 임의의 주소로 데이터를 보낼 수 없다. 프롬프트 주입으로 생성 코드가 오염되어도 유출 경로 자체가 없다
  • 동시에, 아무 외부 API나 부르는 코드는 여기서 안 돈다. 필요한 연결은 전부 먼저 Gatekeeper로 만들어 둬야 한다
  • 그래서 도입 비용의 실체가 드러난다. 플랫폼을 배치하는 것보다 연결할 서비스마다 Gatekeeper를 쓰는 것이 진짜 작업량이다
  • 공개 저장소의 안내문도 외부 서비스 설정 도구를 계속 다듬고 있다고 적으면서, 많은 서비스 제공자가 이 과정을 의도적으로 쉽게 만들지 않는다는 점을 함께 적어 두었다

2.3 코드를 실행하는 런타임은 어디까지인가

같은 주에 Cloudflare는 @cloudflare/computer라는 에이전트 런타임도 얼리 프리뷰로 공개했다. 격리와 컨테이너를 상황에 따라 골라 쓰는 오픈소스 런타임이고, 가벼운 작업은 Dynamic Worker 격리에서, 네이티브 바이너리나 특정 시스템 도구가 필요한 작업은 컨테이너에서 돌린다. 상태는 SQLite로 뒷받침되는 가상 파일 시스템으로 양쪽 사이를 오간다. Cloudflare는 컨테이너가 필요한 작업이 전체의 10퍼센트 미만이 되는 것을 목표로 잡았다고 밝혔다.

다만 이 둘을 붙여 읽지 말 것. Cloudflare OS 발표문과 @cloudflare/computer 발표문 어느 쪽에도 둘이 같은 것이거나 하나가 다른 하나의 구성 요소라는 언급은 없다. 같은 주에 나온 서로 다른 발표다. 「컨테이너까지 알아서 붙어 있겠지」라고 가정하고 설계하면 안 된다는 뜻이다.

3. Gatekeeper - 자격 증명을 주지 않고 권한만 주는 방법

아웃바운드를 닫아 놓았으니 어딘가에 문을 내야 한다. 그 문의 이름이 Gatekeeper다.

3.1 자격 증명은 에이전트에 가지 않는다

Gatekeeper는 Cloudflare OS와 외부 서비스 사이에 놓이는 서비스별 Worker다. OAuth를 처리하고, 자격 증명을 보관하고, 정책을 집행하고, 무엇을 읽었는지 기록한다. 에이전트가 만든 코드가 받는 것은 자격 증명이 아니라 타입이 붙은 바인딩이다.

const issues = await env.PROJECT.listIssues({
  teamId: "ENG",
  state: "open",
});
  • 발표는 사람과 에이전트에게 API 키를 넘기는 것이 위험하다는 점을 명시적으로 짚는다. 키는 범위를 쪼갤 수 없고 회수 흔적도 남지 않는다
  • Gatekeeper는 저장소 하나 단위로 권한을 줄 수 있고, 이슈는 읽되 소스 코드는 못 읽게 나눌 수 있다
  • 모든 에이전트와 앱은 아무 접근 권한도 없는 상태로 시작한다. 필요한 자원을 그때그때 요청하는 구조다
  • 외부에 부수 효과를 일으키는 동작도 전부 이 층을 지난다. 그래서 「누가 무엇을 했는가」가 애플리케이션 로그가 아니라 권한 층에 기록으로 남는다

3.2 관찰 기록이 공유를 제한한다

여기가 기존 권한 모델과 가장 크게 갈리는 지점이다. Cloudflare OS는 에이전트가 관찰한 모든 자원을 기록하고, 그 관찰 기록은 에이전트와 그 결과물에 계속 붙어 다닌다. 다른 사람이 그 작업 공간을 열거나 에이전트와 상호작용하거나 결과물을 보려고 하면, Gatekeeper가 그 사람이 관찰된 자원에 접근할 수 있는지 확인한다.

  • 대시보드를 공유하는 것이 그 안에 들어간 원본 테이블을 공유하는 우회로가 되면 안 된다는 것이 설계 목표다
  • 민감한 데이터를 읽은 뒤에는 특정 대상으로의 쓰기가 막히기도 한다. 읽기 이력이 이후의 쓰기 권한을 좁히는 방향으로 작동한다
  • 이 성질은 편리함과 정면으로 부딪친다. 결과물을 공유했는데 상대가 못 보는 상황이 버그가 아니라 정상 동작이라는 걸 조직이 먼저 이해해야 한다
  • 사내 데이터 등급 체계가 없는 조직이라면 이 층을 켜는 순간 등급 체계를 만들게 된다. 도입 부작용이 아니라 도입 전제에 가깝다

3.3 MCP만으로는 왜 부족한가

Cloudflare OS는 조직이 이미 쓰는 MCP 서버를 MCP Server Portals로 연결해서 쓸 수 있다. 그런데 발표는 MCP를 대체하지 않으면서도 그 위에 층을 하나 더 얹은 이유를 분명히 적었다. MCP만으로는 에이전트가 어떤 기저 자원을 관찰했는지 알 수 없다는 것이다.

  • MCP는 도구를 노출하는 규격이다. 도구가 무엇을 반환했는지, 그 데이터가 어느 원본에서 왔는지는 규격 밖이다
  • 그래서 「이 결과물을 볼 수 있는 사람이 누구인가」를 MCP 층에서는 답할 수 없다. 관찰 기록은 별도로 쌓아야 한다
  • 이미 MCP 서버를 여러 개 운영 중이라면 그 자산을 버리지 않아도 된다는 점은 도입 비용을 낮추는 요소다
  • 반대로 MCP 서버가 하나도 없는 조직이라면, 이 플랫폼을 켜기 전에 연결 대상마다 도구 정의를 만드는 작업이 먼저 온다

4. 기존 서버리스와 갈라지는 두 지점

Workers 위에 올라가 있으니 서버리스의 성질을 그대로 물려받는다. 다만 두 곳에서 확실히 다르다.

4.1 배포 단위가 사라진다

보통의 서버리스는 함수를 배포한다. 코드를 고치면 배포 파이프라인을 다시 태우고, 버전이 생기고, 롤백 대상이 생긴다. Cloudflare OS의 앱은 그 절차를 지나지 않는다. Dynamic Worker로 요청 시점에 적재되기 때문이다.

  • 덕분에 엔지니어가 아닌 사람이 기능 요청서를 쓰는 대신 자기 앱을 AI로 직접 고칠 수 있다. 발표가 강조하는 지점이 여기다
  • 공유 방식이 두 가지다. 앱 자체를 공유해 실시간으로 함께 쓰거나, 청사진을 공유해 각자 독립된 사본을 만들게 하거나
  • 청사진 사본은 원본 코드를 담고 있지만 상태와 연결된 자원은 독립적이다. 남의 도구를 가져다 자기 데이터로 돌리는 데 적합하다
  • 대신 잃는 것이 있다. 배포 파이프라인이 없다는 건 코드 리뷰와 승인 게이트를 걸 지점도 없다는 뜻이다. 사내 규정이 배포 승인을 요구한다면 이 성질부터 협의 대상이 된다

4.2 상태가 앱에 붙어 있다

일반적인 함수형 서버리스는 무상태를 전제하고 상태를 외부 저장소로 밀어낸다. 여기는 반대다. 앱마다 Durable Object Facet과 SQLite가 붙어 있어 상태가 실행 단위와 같은 곳에 산다.

  • 작은 내부 도구를 만들 때 별도 데이터베이스를 프로비저닝하지 않아도 된다. 착수 비용이 크게 낮아진다
  • 동시 편집이 자연스럽다. 팀원 여러 명이 같은 앱 안에서 동시에 작업하는 형태를 전제로 설계되었다
  • 대신 규모가 커지면 문제가 뒤집힌다. 상태가 실행 단위에 묶여 있으니 수평 확장 축이 앱 단위로 고정된다
  • 결정적 워크플로도 같은 축 위에 있다. 요청이 있을 때, 정해진 일정에, 혹은 외부 이벤트가 발생할 때 실행되는 형태를 지원한다

5. 숫자로 된 한도가 이미 정해 놓은 것

여기가 배치 결정에서 제일 먼저 봐야 할 곳이다. Cloudflare OS 발표문에는 자체 한도 수치가 없다. 그런데 앱이 전부 Worker이므로 Workers의 플랫폼 한도가 그대로 앱의 한도가 된다.

5.2 이 한도가 실제로 잘라 내는 작업

표를 읽는 법은 간단하다. 위에서부터 우리 작업을 대 보고 하나라도 걸리면 그 작업은 여기 올릴 게 아니다.

  • 장시간 GPU 학습과 대형 모델 자체 서빙. 애초에 계산 자원의 종류가 다르다. 추론은 AI Gateway를 지나 외부 모델로 나가는 구조이지, 여기서 도는 것이 아니다
  • 수 GB 데이터를 메모리에 올려 두는 분석. 128MB 한도가 정면으로 막는다. 스트리밍으로 쪼개거나 애초에 다른 곳에서 돌려야 한다
  • 수십 개 백엔드를 동시에 때리는 팬아웃 집계. 동시 아웃바운드 연결이 요청당 6개라 병렬성이 그 선에서 끊긴다
  • 수십 분짜리 단일 배치. Cron 계열이 15분에서 끊기므로 작업을 쪼개고 이어 붙이는 설계가 필수다
  • 네이티브 바이너리에 의존하는 도구 체인. V8 격리에서는 안 돈다. 컨테이너가 필요한 작업이라면 이 플랫폼의 앱 모델 밖이다
  • 반대로 수백 밀리초 안에 끝나는 조회와 정리 작업은 이 한도 전부를 여유 있게 통과한다. 그리고 사내 업무 자동화의 상당수가 실제로 여기 든다

6. 데이터 지역성 - 규제가 걸린 워크로드의 갈림길

사내 데이터를 다루는 플랫폼이므로 데이터가 어디 앉는지가 도입 가부를 가른다. 앱 상태는 Durable Object에 들어가고, Durable Object의 위치 규칙은 이미 문서화되어 있다.

6.1 관할권과 위치 힌트는 다른 물건이다

  • 관할권(jurisdiction)은 규제 준수를 위해 특정 지역 안에서만 실행하고 저장하도록 강제하는 장치다. eu, us, fedramp 세 가지가 제공된다
  • 위치 힌트(location hint)는 관할권 강제가 필요 없을 때 초기 배치 위치를 유도하는 값이다. wnam, enam, sam, weur, eeur, apac, apac-ne, apac-se, oc, afr, me가 있다
  • 둘을 섞어 쓰면 안 된다. 힌트는 최선의 노력일 뿐 보장이 아니다. 문서가 힌트한 위치에 반드시 만들어지는 것은 아니라고 명시한다
  • Durable Object는 한 번 만들어지면 다른 데이터센터로 옮겨 가지 않는다. 최초 get() 호출만 위치 결정에 관여한다
  • 식별자는 과금과 디버깅 목적으로 지정한 관할권 밖에도 기록된다. 식별자 자체가 민감 정보가 되는 설계라면 이 점을 먼저 검토해야 한다

6.2 한국 규제 환경에서 확인해야 할 것

제공되는 관할권 목록에 한국은 없다. 그러니 국내 데이터를 국내에만 두어야 하는 요건이 걸려 있다면 이 축부터 정리해야 한다.

  • 관할권 목록에 없다는 것과 국내 데이터센터가 없다는 것은 다른 이야기다. 다만 강제 장치로 제공되지 않는다는 사실은 그대로다
  • 위치 힌트 apac-ne는 아시아 북동 지역을 유도할 뿐 국가 단위 보장이 아니다. 규제 대응 근거로 쓸 수 없다
  • 추론 요청은 AI Gateway를 지나 외부 모델 제공자로 나간다. 모델 제공자 쪽의 데이터 처리 위치가 별도 검토 대상이 된다
  • Gatekeeper가 남기는 관찰 기록도 데이터다. 무엇을 읽었는지의 목록이 남는다는 건 감사 자산이자 동시에 보관 정책이 필요한 대상이라는 뜻이다

7. 비용은 어디서 발생하나

먼저 분명히 해 둘 것이 있다. Cloudflare OS 자체의 가격 체계는 발표에 없다. 오픈소스로 공개되었고 자기 계정에 배치하는 형태이므로, 비용은 소프트웨어 사용료가 아니라 그 계정에서 소비하는 자원에서 나온다.

7.1 과금 축은 최소 세 갈래로 갈린다

  • 컴퓨트와 상태. Workers 실행과 Durable Objects 저장·요청이 여기 든다. 앱 수가 늘면 Durable Object 수가 늘고, 그 축이 함께 늘어난다
  • 모델 추론. AI Gateway를 지나는 모든 추론 요청이다. 실제 청구는 대체로 이 축이 가장 크게 움직인다
  • 아이덴티티. Cloudflare Access로 진입을 통제하므로 사용자 규모가 이 축을 정한다
  • 여기에 눈에 안 보이는 넷째가 있다. Gatekeeper를 쓰고 유지하는 사람 시간이다. 연결 대상이 늘 때마다 코드가 늘고, 그 코드는 권한 층이라 아무나 고치게 둘 수 없다

7.2 발표가 비용 통제에 대해 실제로 말한 것

가격표는 없지만 통제 장치는 명확하게 설명되어 있다. 모든 추론 호출이 AI Gateway를 지나므로, 조직은 어떤 모델을 쓸 수 있게 할지 고르고 사람 단위나 팀 단위로 지출을 추적하고 예산과 속도 제한을 걸 수 있다. 모든 요청은 그 요청을 만든 사람, 팀, 작업 공간에 귀속된다.

  • 귀속이 요청 단위로 이뤄진다는 건 비용을 부서 단위로 되돌릴 수 있다는 뜻이다. 사내 도입에서 이 성질은 기술 사양이 아니라 정치 사양이다
  • 모델 선택권이 조직에 있다는 점도 같은 맥락이다. 작업 성격에 맞는 모델을 지정해 두면 비싼 모델이 사소한 작업에 붙는 상황을 구조적으로 막는다
  • 다만 예산 초과 시의 동작, 즉 거절할지 저렴한 모델로 내릴지는 발표에 없다. 운영 정책으로 정해 둘 항목이다

8.3 판단을 세 질문으로 줄이면

  1. 이 작업이 128MB와 CPU 5분 안에 들어가는가. 안 들어가면 나머지 논의는 의미가 없다
  2. 연결해야 할 외부 시스템이 몇 개이고, 각각 Gatekeeper를 쓸 사람이 있는가. 이 숫자가 실제 도입 비용이다
  3. 결과물 공유가 권한으로 막히는 상황을 조직이 받아들일 수 있는가. 못 받아들이면 이 플랫폼의 핵심 장치를 꺼야 하고, 그러면 남는 게 별로 없다

9. 지금 운영에 올리면 안 되는 이유

공개 저장소의 안내문이 스스로 밝히고 있는 내용이다. 이 부분을 건너뛰고 검토하면 판단이 통째로 어긋난다.

  • 안내문은 v2가 상당히 쓸 만하지만 거친 부분이 여전히 많다고 적었고, 활발한 개발 상태라고 표현했다. 운영 준비 완료 선언이 아니다
  • 자체 호스팅 배포 방식은 준비 중으로 표시되어 있다. 지금 배치하는 경로는 Cloudflare 계정을 쓰는 쪽이다
  • 외부 서비스 연결 설정 도구도 계속 다듬는 중이라고 적혀 있다. 연결 대상이 많은 조직일수록 이 미완성 구간을 직접 메우게 된다
  • 라이선스는 Apache-2.0이다. 사내 개조와 재배포에 걸림돌은 없지만, 라이선스가 열린 것과 운영에 올릴 준비가 된 것은 다른 문제다
  • 그래서 지금 값어치 있는 접근은 세 가지로 좁혀진다. 시범 계정에 배치해 Access·AI Gateway 설정이 사내 규정과 맞물리는지 보기, Gatekeeper를 한두 개 직접 써 권한 분해 단위를 잡아 보기, 우리 실제 작업이 한도 안에 들어가는지 재 보기다

10. 도입한다면 먼저 정해 둘 것들

  • 데이터 등급 체계를 먼저 만들어라. 관찰 기록 기반 공유 제한은 등급이 없으면 켤 수 없다. 이건 플랫폼 설정이 아니라 조직 합의다
  • Gatekeeper 소유자를 지정하라. 권한 층 코드이므로 누구나 고치게 두면 안 된다. 리뷰 없이 배포되지 않는 유일한 코드 경로가 되어야 한다
  • 모델 허용 목록과 예산 초과 시 동작을 문서에 적어라. 거절할지 저렴한 모델로 내릴지는 발표에 없으니 조직이 정해야 한다
  • 앱 폐기 정책을 처음부터 두어라. 앱마다 Durable Object와 SQLite가 붙으므로 방치된 앱이 그대로 비용과 데이터로 남는다
  • 관찰 기록의 보관 기간을 정하라. 감사 자산인 동시에 그 자체가 민감 정보다. 운영 데이터와 감사 기록의 보존 정책을 겸용하지 마라
  • 청사진 공유와 앱 공유를 구분해 교육하라. 앞은 상태가 분리된 사본이고 뒤는 실시간 공동 작업이다. 이 차이를 모르면 데이터가 섞인다
  • 배포 승인 규정과의 충돌을 먼저 해소하라. 배포 단위가 없다는 성질은 나중에 협의할 수 없다. 규정을 고치든 이 플랫폼의 적용 범위를 좁히든 둘 중 하나다
  • 탈출 경로를 확인해 두어라. 앱별 SQLite에 쌓인 데이터를 밖으로 빼는 경로가 있어야 한다. 오픈소스라는 사실이 이동 가능성을 자동으로 보장하지는 않는다

11. 확인하지 못한 것

근거를 확보하지 못한 항목을 한자리에 모은다.

  • Cloudflare OS 자체의 가격. 발표에 가격 정보가 없다. 계정 자원 소비로 청구된다는 구조만 확인된다
  • 정식 출시 단계 표기. 발표는 오늘 이용 가능하다고 적었고 저장소는 거친 부분이 많다고 적었다. 베타·GA 같은 공식 단계 표기는 확인하지 못했다
  • Dynamic Workers와 Durable Object Facets의 개별 한도. 이 글의 한도 표는 Workers 플랫폼 문서 기준이며, 이 두 기능에 별도 한도가 있는지는 확인하지 못했다
  • 동시 실행 앱 수와 작업 공간당 상한. 발표와 저장소 안내문 어디에도 수치가 없다
  • 사내 배포 규모의 구체값. 모든 직능에 걸쳐 수천 명이 매일 쓴다는 표현만 있고, 정확한 인원과 앱 개수는 공개되지 않았다
  • SLA와 지원 체계. 오픈소스 배포 형태에서 장애 대응 책임이 어디까지인지는 확인하지 못했다
  • 모델 제공자 쪽 데이터 처리 위치. AI Gateway를 지난 뒤의 처리 지역은 제공자별 계약 사항이며 이 발표의 범위 밖이다
  • R2·D1·Containers·Workers AI와의 관계. 이 발표문에는 이들 제품이 구성 요소로 등장하지 않는다. 연동 가능 여부는 확인하지 못했다

12. 자주 묻는 질문

Cloudflare OS는 새 제품인가 기존 제품군의 재편인가?

둘 다 아니다. Cloudflare가 사내에서 쓰던 애플리케이션을 다시 만들어 오픈소스로 공개한 것이다. 발표문의 표현 그대로 「오늘 우리는 Cloudflare OS의 새 버전을 오픈소스로 공개한다」이며, 첫 버전은 같은 해 5월에 전 직원에게 열어 두고 운영해 온 사내 도구였다. 그러니 새 인프라 계층이 생긴 것이 아니다. Workers, Durable Objects, Access, AI Gateway 같은 기존 구성 요소 위에 올라가는 애플리케이션이 하나 열린 것이고, 그 애플리케이션이 요구하는 권한 위임 방식이 Gatekeeper라는 이름으로 같이 나왔다. 그래서 도입 검토의 첫 질문도 「새 클라우드를 쓸 것인가」가 아니라 「Cloudflare 계정 안에 이 애플리케이션을 배치할 것인가」가 된다.

에이전트가 만든 앱은 어떻게 실행되고 상태는 어디에 남나?

앱 하나가 Worker 하나다. 에이전트는 브라우저에서 화면을 그리는 클라이언트 코드와 상태를 다루는 서버 코드를 함께 쓰고, 서버 쪽은 필요할 때 Dynamic Worker로 적재되어 Durable Object Facet으로 인스턴스화된다. 각 앱은 자기 SQLite 데이터베이스를 갖는데, 이 데이터베이스는 앱을 관리하는 Cloudflare OS 런타임의 저장소와 분리되어 있다. 브라우저 클라이언트와 서버 사이 통신은 Cap'n Web이라는 오브젝트 케이퍼빌리티 방식 RPC로 이뤄진다. 여기서 중요한 성질은 배포 단위가 따로 없다는 점이다. 앱을 고치는 데 별도 배포 절차가 끼지 않으므로, 엔지니어가 아닌 사람도 기능 요청서를 쓰는 대신 자기 앱을 직접 고칠 수 있다.

Gatekeeper는 기존 API 키 방식과 무엇이 다른가?

자격 증명이 에이전트 쪽으로 넘어가지 않는다는 점이 다르다. Gatekeeper는 Cloudflare OS와 외부 서비스 사이에 놓이는 서비스별 Worker이고, OAuth를 처리하고 자격 증명을 보관하며 정책을 집행하고 무엇을 읽었는지 기록한다. 에이전트가 만든 코드는 자격 증명 대신 타입이 붙은 바인딩을 받는다. 그래서 권한을 저장소 하나 단위, 이슈는 읽되 소스는 못 읽는 단위로 쪼갤 수 있다. 여기에 더해 관찰 기록이 붙는다. 에이전트가 본 자원이 그 에이전트와 결과물에 계속 붙어 다니고, 다른 사람이 그 결과물을 열려고 하면 Gatekeeper가 그 사람의 접근 권한을 확인한다. 민감한 데이터를 읽은 뒤에는 특정 대상으로의 쓰기가 막히기도 한다.

어떤 워크로드가 이 플랫폼에 맞고 어떤 것이 안 맞나?

맞는 쪽은 짧고 분산된 실행이다. 사내 시스템 여러 곳을 오가며 조회하고 정리하는 작업, 사람이 몇 지점에서만 판단하면 되는 반복 절차, 팀 단위로 쓰는 작은 내부 도구가 여기 든다. 안 맞는 쪽은 세 가지로 갈린다. 첫째 장시간 GPU 학습이나 대형 모델 자체 서빙이다. 둘째 대용량 상태다. Workers 격리는 자바스크립트 힙과 웹어셈블리 할당을 합쳐 128MB이므로 큰 데이터를 메모리에 올려 두는 방식은 애초에 못 들어간다. 셋째 임의 아웃바운드가 필요한 작업이다. 서버 코드는 글로벌 아웃바운드 네트워킹이 꺼진 채로 돌기 때문에, 외부로 나가려면 그 경로를 케이퍼빌리티로 명시해 두어야 한다.

지금 바로 사내에 도입해도 되나?

운영 도입은 이르다. 공개 저장소의 안내문 자체가 v2는 상당히 쓸 만하지만 거친 부분이 많고 활발한 개발 중이라고 적고 있다. 자체 호스팅 배포 도구도 준비 중으로 표시되어 있다. 라이선스는 Apache-2.0이라 사내 개조와 재배포에 걸림돌은 없지만, 라이선스가 열려 있다는 것과 운영에 올릴 준비가 되었다는 것은 다른 이야기다. 지금 시점에 값어치 있는 접근은 세 가지다. 하나, 자기 Cloudflare 계정에 시범 배치해서 Access 정책과 AI Gateway 설정이 사내 규정과 맞물리는지 본다. 둘, Gatekeeper 한두 개를 직접 써 보면서 권한 분해 단위를 잡는다. 셋, 128MB와 CPU 한도에 우리 작업이 실제로 들어가는지 잰다.

결론: 오늘 가져갈 세 가지

첫째, 이 플랫폼의 성격은 기능 목록이 아니라 제약이 정한다. 아웃바운드 기본 차단과 격리당 128MB, 두 줄이면 어떤 작업이 여기 들어오고 어떤 작업이 못 들어오는지 거의 다 정리된다. 발표문의 화려한 부분보다 이 두 줄을 먼저 우리 작업에 대 보는 편이 훨씬 빠르다.

둘째, 도입 비용은 플랫폼 배치가 아니라 Gatekeeper 개수다. 배치는 계정 하나면 되지만, 연결할 외부 시스템마다 권한 중개 Worker를 쓰고 유지해야 한다. 그리고 그 코드는 권한 층이라 아무나 못 고친다. 연결 대상 목록을 먼저 세어 보면 도입 규모의 실체가 나온다.

셋째, 관찰 기록 기반 공유 제한은 기술이 아니라 조직 결정이다. 결과물을 공유했는데 상대가 못 보는 상황이 정상 동작이라는 걸 받아들일 수 있어야 이 플랫폼의 핵심이 작동한다. 못 받아들이면 그 장치를 끄게 되고, 그러면 그냥 또 하나의 사내 챗봇이 된다.

마지막으로 하나. 이번 발표에서 오래 남는 건 Cloudflare OS라는 이름이 아니다. 에이전트에게 자격 증명을 주는 대신 케이퍼빌리티를 주고, 무엇을 읽었는지를 권한 판단의 입력으로 삼는다는 방향이다. 이 방향은 어느 플랫폼을 고르든 사내 에이전트 설계에서 다시 만나게 된다. 지금 쓸 수 있는지와 별개로, 그 설계 원칙만은 지금 읽어 둘 값어치가 있다.
