This article relies only on what is written in the DebugBear post "Example.com Just Launched The Biggest Redesign In Decades", in the responses that example.com, example.org and example.net returned between 13:25 and 13:28 UTC on October 6, 2026, in the two IANA guidance pages on example domains, and in the text of RFC 2606 and RFC 6761. Every figure is labelled as either a value from the source article or a value measured on the received response, and derived values such as totals and percentages are marked as calculated.

The trigger - a page that changed on September 28 and again on October 3

example.com is a name that was set aside so that documentation would have something to use as an example. The DebugBear article opens by introducing it as a reserved domain name set aside by the Internet Assigned Numbers Authority (IANA) for documentation purposes, and says it has been available as an example URL for developers and writers since the late nineties. The same article summarises the history in one line: the overall messaging of the page has been consistent over time, while the visual appearance has received several major overhauls.

The article reports two recent changes. Until September 28, 2026, example.com was a static English-language page. The redesign introduced multi-language support using JavaScript, showing the content in a new language every 5 seconds, and the languages are English, Arabic, Chinese, French, Russian and Spanish, six in all. The JavaScript code also inserted an SVG book icon. Then, under a heading dated October 3, the source article says that example.com has now removed the animation and shows all languages right from the start. The GeekNews summary covers the story up to the 5-second rotation of the September 28 version. What the server returns today is the version described under the October 3 heading.

The phrase in the title of the source article, "The Biggest Redesign In Decades", is the author's own wording. The article does not present a figure showing by what measure this redesign is the biggest, and its own entry for 2019 refers to the July 2013 redesign as "the biggest change in the website's history". Both phrases are best read as the author's assessment.

The question that matters in practice is a different one from the redesign itself. It is whether there are places where the example domain is called from running code rather than merely written in documentation, and where something is expected of the response body. Typical places are a request sent to check connectivity, an assertion in an HTTP client example, and a target address entered in a monitoring tool. The sections below set out in turn what the response actually looks like, what changed and when, and how far the standards and the IANA guidance ever promised anything. The risks on the side of domains that carry real services belong to the axis covered in the article on country risk in country-code domains; the subject here is a single name that nobody can register.

What it returns now - 577 bytes of HTML and a single script file

The block below is the complete response body returned by https://example.com/ at 13:25:35 UTC on October 6, 2026. Without compression being requested its size is 577 bytes, and it is a single line with no line breaks.

The following can be read directly from this markup.

  • Document language. A single language, English, is declared through <html lang=en>.
  • Body text. There is one <p> element holding two English sentences. One says the domain is for use in documentation examples without needing permission, and the other says it is not a service and asks readers to avoid relying on it for testing and monitoring purposes.
  • Title. The title is <title>Example Domain</title>. The HTML contains no <h1> element and no <a> element.
  • Style. There is one inline <style> element. It separates the background for light and dark screens with color-scheme:light dark and light-dark(#eee,#222), and it limits the body to a width of 26em and centres it.
  • Favicon. An empty value is specified through <link rel=icon href=data:,>. The source article explains that this tag was added on June 9, 2026 and that it avoids a lot of unnecessary requests, because otherwise browsers look for a favicon at /favicon.ico.
  • External resources. The only reference is <script src=/s.js>. There is no reference to an image, an external stylesheet or a font.
  • Notation. Most attribute values are written without quotation marks, and there are no spaces or line breaks between elements. The source article notes that the HTML was minified in the redesign of October 9, 2025.

What the script does - it appends five paragraphs and lifts the browser language to the top

s.js is a single-line file of 1,963 bytes. Counted in characters it is 1,579 long; the byte count is larger because the file contains characters that take several bytes each, such as Arabic, Chinese and Russian text. Its behaviour falls into three parts.

  • It appends paragraphs and a link. Immediately after the first element of the body, which is the English paragraph, it inserts five paragraphs and one link. The paragraphs come in the order <p lang=ar dir=rtl>, <p lang=zh>, <p lang=fr>, <p lang=ru> and <p lang=es>, and the link is a Learn more link pointing to https://iana.org/help/example-domains.
  • It moves the paragraph matching the browser language to the top. It collects the six paragraphs, sets lang="en" on the first one, and then walks through navigator.languages, the browser's list of preferred languages, from the front, looking for a paragraph whose lang equals the part of the language code before the hyphen. The paragraph it finds, or the English paragraph if it finds none, is moved to the very start of the body.
  • It inserts a style and an icon. At the very start of the body it inserts a <style> element and an SVG. The style lowers the font size of every paragraph after the first to 0.875em and its opacity to 0.6. The SVG is 44 wide and 44 high and carries aria-hidden=true.

The code that corresponds to the second part is the following portion of the file. Earlier in the file, B is defined as document.body.

P=[...B.querySelectorAll("p")];P[0].lang="en";navigator.languages.some(l=>p=P.find(p=>p.lang==l.split("-")[0]));p=p||P[0];B.prepend(p);

The file contains no timer call such as setInterval or setTimeout, no code that wraps characters in span elements, and no transition declaration. That matches what the source article says under October 3, namely that the animation has been removed and all languages are shown right from the start. From top to bottom the screen becomes the book icon, the one paragraph that matches the browser language, the remaining five paragraphs in smaller and fainter text, and the link. In a browser whose preferred languages are not among the six, for example a browser set to Korean only, the English paragraph stays at the top.

The transition effect of the September 28 version survives only as a description in the source article. According to that description, the version did not simply replace the content when showing the next language; there was a gradual opacity transition. The opacity animation itself used transition: opacity .4s;, and each character was wrapped in its own span element, with each span given a slightly larger transition-delay than the one before it, so that the opacity animation of each character happened at a slightly different time.

For a client that reads only the response HTML, example.com is a page with a single English paragraph. The five additional language paragraphs, the Learn more link and the icon are not in that response. In a browser that runs the script all six paragraphs are visible, and which paragraph sits at the top depends on the language settings of the browser. Each paragraph carries a lang attribute, and the Arabic paragraph also carries dir=rtl.

There are two places where the description in the source article and the received response do not line up.

  • Punctuation in the English wording. A difference of one character in the wording and one day in the date means nothing to a person reading the page. For code that compares the response body as a string, or asserts on its hash or its length, a difference of that size is enough to change the outcome.

What IANA said - bandwidth, and a service run as a courtesy

The reason for the change is not something to fill in with speculation. The DebugBear article says that IANA provided a statement explaining the reasoning behind the recent changes, and it reproduces three paragraphs. They are quoted below as they appear in the article.

The changes we make to the site from time-to-time are usually informed by a desire to either reduce the overall bandwidth demands of serving the site, or improve its utility. At its heart it is a placeholder for a site no-one should be accessing, but we have historically showed a message there to inform visitors about why the domain is registered and how they may use it.

As it tends to be heavily trafficked, the overall bandwidth is a key consideration, and to that end one of the changes we made this week was to split the page content into a more basic page, augmented by a separate Javascript file with additional content beyond that. Since most of the traffic to the site is automated it tends not to fetch the Javascript file, reducing overall data requirements.

The fundamental purpose of the domain is for use in documentation, such as illustrative examples you may find in instructions. We know that people may, for example, cut-and-paste a sample configuration file and forget to customize entries that contain an example domain, and we expect we get some incidental traffic from that. However, the domain isn't intended to be a general purpose endpoint for things like availability testing so we do not encourage that kind of usage. There is no requirement there is a HTTP service present on the host in order to fulfill its purpose, we just operate it as a courtesy.

What deserves attention in the statement is where the qualifiers sit. The motive for changes is "usually" bandwidth or utility, automated traffic "tends not to" fetch the JavaScript file, and the statement gives no number for the share of traffic that is automated. The passage about splitting the page into a basic page and a separate JavaScript file corresponds to the 577-byte HTML and the 1,963-byte s.js described in the previous sections. The two sentences of the last paragraph, that the domain is not intended to be a general purpose endpoint and that there is no requirement for an HTTP service to be present, are the ones that bear directly on anything that leaned on the response body.

The "Example Domains" guidance page on the IANA site carries sentences that point in the same direction. The page says that a number of domains such as example.com and example.org are maintained for documentation purposes, that they may be used as illustrative examples in documents without prior coordination, and that they are not available for registration or transfer. It goes on to say that the web service on the example domain hosts is there to provide basic information on the purpose of the domain, and that these web services are provided as best effort but are not designed to support production applications. Its last sentence states that IANA strongly recommends that applications not be designed in a way that requires the example domains to have operating HTTP service. The revision date at the bottom of the page is 2026-09-27, one day before September 28, the date the source article gives for the redesign.

The response body itself says the same thing. The second sentence of the English paragraph tells readers that this is not a service and asks them to avoid relying on it for testing and monitoring purposes. The source article notes that a message against operational use ("Avoid use in operations") was first introduced in 2025.

What the standards guarantee and what they never guaranteed

The reservation rests on two RFCs. RFC 2606 ("Reserved Top Level DNS Names", June 1999, BCP 32) says in its abstract that, to reduce the likelihood of conflict and confusion, a few top level domain names are reserved for use in private testing, as examples in documentation, and the like, and that a few second level domain names reserved for use as examples are documented as well. Section 2 reserves four names, .test, .example, .invalid and .localhost, and says that .test is recommended for use in testing of current or new DNS related code and .example for use in documentation or as examples. Section 3 is a single sentence: IANA also currently has the second level domain names example.com, example.net and example.org reserved, which can be used as examples.

RFC 6761 ("Special-Use Domain Names", February 2013, Standards Track) updates RFC 2606 and requires any document that reserves a special-use name to answer, for seven categories running from users to registries, what treatment is expected of each. Section 6.5 gives the answers for example., example.com., example.net., example.org. and any names falling within those domains. The route of reserving a name as a special-use domain is itself discussed in the analysis of the .self TLD.

Wording, markup, size and headers of the response body—No such sentence in RFC 2606, RFC 6761 or the two IANA guidance pages

The bottom three rows of the table are the subject here. What the standard binds with MUST NOT is registration: the name does not pass to another party. That name resolution proceeds normally, without special treatment, is written at the SHOULD level. What comes back when an HTTP request is sent to that name is not something either RFC sets out to define. The sentence about the web server in RFC 6761 carries the word "currently", and section 5 of the same document, while explaining the seventh category, mentions in a parenthetical example that there is even a web site at the name www.example.org which states "circularly" that the name is reserved for use in documentation and cannot be registered. Neither sentence requires a web page; both point at one that happens to exist.

The Security Considerations section of RFC 2606 contains sentences that run in the same direction as the present situation. Test and experimental software can escape and end up being run against the global operational DNS, it says, and even examples used "only" in documentation can end up being coded and released. The traffic from cut-and-pasted configuration files that the IANA statement mentions is one form of that.

There is also one difference in the scope of the list. The source article says that on July 30, 2010 example.edu came to point at the same landing page, whereas the second level names written in section 3 of RFC 2606 and in section 6.5 of RFC 6761 are the three under .com, .net and .org.

Regrouped by the purpose of the call, the picture is as follows.

  • A request sent to see whether the network is alive. The only thing leaned on is the fact that a response arrives. The IANA statement says this kind of usage is not encouraged, and the guidance page recommends against designs that require the HTTP service to be operating.
  • An example or test for an HTTP client, crawler or proxy that asserts on a string in the body. There is a record of the wording and the punctuation changing, and there is the case of the h1, an element that existed in the 2013 version and is absent from the HTML today.
  • A check that the response is unchanged, by snapshot, hash or length. By the timeline in the source article it changed three times in 2026 alone.
  • A comparison of screenshots taken with a headless browser. The first paragraph depends on the language settings of the browser, and the number of paragraphs is one or six depending on whether the script is fetched.
  • An example that identifies the kind of server from a response header. What the source article records about the serving server changed four times. It does not state the header value for the EdgeCast period.

In its conclusion the source article observes that changes to example.com happen sporadically. Sometimes a couple of small tweaks happen in back-to-back months, and at other times the website remains untouched for periods of up to seven years. DebugBear adds that it has been monitoring the page for several years in its public demo project, and that Chrome UX Report (CrUX) data shows how page speed has changed over time.

For anyone leaning on the response body, the thing to notice in the timeline is the variety of kinds of change. There is a time when the wording changed, a time when the markup structure changed, a time when the serving infrastructure changed, and a time when a redirect was returned instead of a page of its own. By the account in the source article, the period from January 2011 to July 2013 is one in which example.com did not serve its own page and sent visitors on to a page on the IANA website.

What to use for tests and monitoring - within what the source and IANA actually said

The recommendation in the source article is one sentence long: using infrastructure that your organization controls can be more reliable. Before that sentence the article acknowledges that, for developers, it is tempting to use example.com to check whether the network is working or to test HTTP requests, and it adds that the example server likely receives a lot of traffic through this.

On the side of the standards, the distinction that can be put to use is in section 2 of RFC 2606. It says .example is for documentation or examples, .test is for testing DNS related code, and .invalid is for constructing domain names that are sure to be invalid and are obviously invalid at a glance. That distinction is a basis for choosing a name, and the section contains no sentence about a server that would return a response.

Turned into an order of checks, the facts above come out as follows.

  • Split the occurrences into two groups. Wherever example.com, example.org or example.net appears in a repository, separate the documentation, comments and sample values from the targets to which a request really goes out at run time. The first group is the purpose the domain exists for, and nothing there needs to change.
  • Mark the tests that assert on the body. Among the real request targets, these are the ones asserting on a string, the length, a hash or the presence of an element in the response body. They overlap with the items that have a change record in the table of the previous section.
  • Move the target to something under your control. Change it to an endpoint the organization controls, for instance a server the test itself starts. That is as far as the recommendation in the source article goes.
  • Look at the target addresses of connectivity checks and uptime probes. If they are set to an example domain, change them in the same way. This is the usage the IANA statement says it does not encourage.
  • Look at deployed configuration files. Check whether an example domain from a sample has been left in place without being customized. This is the case the IANA statement names as a source of incidental traffic.
  • Write down the difference between tools. A tool that runs the script and a tool that does not see different bodies at the same URL: one paragraph on one side, six paragraphs and a link on the other.

After the move, the URLs written in documentation and example code can stay as example.com. That is what the reservation is for, and item 7 of section 6.5 of RFC 6761 says that requests to register this name must not be granted in the normal way. What changes is not the notation but the request that really goes out at run time.

What could not be confirmed

  • The actual HTML and script of the September 28 version. The server on October 6 returns only the later version, and the 5-second rotation, the .4s transition and the per-character span are carried over from the description in the source article.
  • The byte size and the number of requests for the version before September 28. The source article gives no figures.
  • The time at which the follow-up change was actually deployed. The source article gives October 3 and the last-modified headers point to October 2 and October 4, and there is no material to tell which value is the time of what.
  • The channel through which the IANA statement was delivered, and its date. The source article says only that IANA provided the statement, and whether the same text is published on the IANA site was not examined.
  • The measure behind "the biggest redesign in decades". The source article offers no metric for the comparison.
  • The launch date of January 1, 1999. It is a value the source article cites from Wikipedia, and the Wikipedia article was not opened.
  • The share of automated traffic and any uptime figure. Neither the IANA statement nor the text of the source article gives a number, and the monitoring screen in the source article is an image.
  • The point at which the h1 element disappeared. Its introduction in 2013 is in the source article, but the time of its removal is not stated.
  • The real number of requests in a browser, the way a screen reader reads the six paragraphs, and whether search crawlers index the paragraphs inserted by the script. What was read is the markup and the script text; none of this was measured with a browser or with assistive technology.
  • Responses at other times and from other regions. The values come from one location over three minutes.
  • The current response of example.edu. No request was sent to it.
  • Whether the dates in the timeline of the source article are deployment dates or the dates on which a change first appears in an archive. The source article does not draw the distinction.
