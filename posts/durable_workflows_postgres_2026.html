Postgres로 내구성 있는 워크플로 만들기 2026 - 별도 큐 없이 신뢰성 확보하기

정말 Kafka가 필요할까 - 이미 있는 Postgres만으로 신뢰성 있는 백그라운드 작업 만들기

2026-05-31 IT/기술

서론: 워크플로 신뢰성을 위해 꼭 Kafka·Temporal이 필요한가

"백그라운드 작업을 신뢰성 있게 처리하려면 메시지 큐가 필요하다." 많은 개발자가 거의 반사적으로 받아들이는 명제입니다. 이메일을 발송하고, 결제 후처리를 돌리고, 알림을 보내고, 데이터 파이프라인을 돌려야 하는 순간 우리는 곧바로 Kafka, RabbitMQ, 혹은 Temporal 같은 전용 도구를 떠올립니다. 그리고 그 도구를 위해 별도 클러스터를 세우고, 운영 인력을 붙이고, 모니터링 체계를 또 하나 늘립니다.

그런데 잠시 멈춰서 물어볼 가치가 있습니다. 정말 그래야만 할까요? 2026년 현재, 점점 더 많은 팀이 정반대의 결론에 도달하고 있습니다. 이미 쓰고 있는 Postgres 하나만으로 내구성 있는 워크플로를 충분히 만들 수 있다는 것입니다. 새 인프라를 추가하지 않고, 새 장애 지점을 만들지 않고, 새 학습 곡선을 강요하지 않고 말입니다.

이 글은 그 가능성을 한국 개발자, 특히 소수 인력으로 빠르게 움직여야 하는 스타트업 관점에서 진지하게 따져 봅니다. Postgres 기반 워크플로가 어떤 원리로 신뢰성을 확보하는지, 어떤 핵심 패턴이 있는지, 그리고 무엇보다 언제 Postgres로 충분하고 언제 전용 도구가 필요한지를 균형 있게 다루겠습니다. 결론부터 말하면, 답은 "Postgres가 만능"도 "Kafka가 정답"도 아닌, 데이터와 규모의 성격에 달려 있습니다.

이 글의 한 줄 요약. 대부분의 중소 서비스에서 백그라운드 작업의 신뢰성은 별도 메시지 브로커가 아니라 Postgres의 트랜잭션에서 나옵니다. 작업 등록을 비즈니스 트랜잭션과 묶고, SKIP LOCKED로 워커를 분배하고, 멱등성으로 중복을 무해화하면 새 인프라 없이 내구성을 얻습니다.

1. "Durable Workflow"란 - 내구성 있는 실행의 정의

본격적인 논의에 앞서 용어를 정리하겠습니다. "내구성 있는 워크플로(durable workflow)"란 무엇일까요? 핵심은 단어 그대로 내구성(durability)입니다. 한 번 시작된 작업이 서버가 죽든, 프로세스가 재시작되든, 네트워크가 끊기든 결국 끝까지 수행되거나, 최소한 잃어버리지 않고 다시 시도된다는 보장입니다.

좀 더 구체적으로 풀면, 내구성 있는 워크플로는 다음 속성을 갖습니다.

  • 작업 유실 없음: 일단 받아들인 작업은 어떤 장애에도 사라지지 않습니다. 디스크에 안전하게 기록됩니다.
  • 최소 한 번 실행(at-least-once): 작업은 적어도 한 번은 반드시 실행됩니다. 중간에 워커가 죽어도 다른 워커가 이어받습니다.
  • 중단 후 재개 가능: 실행 도중 멈춰도, 마지막으로 기록된 지점부터 다시 진행하거나 안전하게 처음부터 재시도할 수 있습니다.
  • 상태의 영속성: 작업의 진행 상태가 휘발성 메모리가 아니라 영속 저장소에 남습니다.

여기서 결정적인 통찰이 나옵니다. 이 속성들은 사실 관계형 데이터베이스가 이미 제공하는 ACID 보장과 거의 정확히 겹친다는 것입니다. '커밋되면 살아남는다'는 내구성(D), '동시 작업이 서로를 망치지 않는다'는 격리성(I), '전부 아니면 전무'라는 원자성(A). 워크플로 엔진이 힘들게 만들어 내려는 보장의 상당 부분을 Postgres는 30년 넘게 다듬어 온 기능으로 그냥 제공합니다.

2. 왜 Postgres인가 - 이미 있는 DB로 충분한 이유

그렇다면 왜 하필 Postgres일까요? 이유는 세 가지로 압축됩니다. 트랜잭션, 내구성, 그리고 단순성입니다.

2.1 트랜잭션 - 신뢰성의 토대

Postgres의 가장 강력한 무기는 트랜잭션입니다. 비즈니스 데이터의 변경과 백그라운드 작업의 등록을 하나의 트랜잭션으로 묶을 수 있다는 점이 핵심입니다. 예를 들어 '주문을 생성하고 → 확인 이메일 발송 작업을 등록'하는 두 동작을 한 트랜잭션으로 처리하면, 둘은 함께 성공하거나 함께 실패합니다. 주문은 생겼는데 이메일 작업이 누락되는 일이 구조적으로 불가능해집니다. 별도 메시지 브로커를 쓰면 바로 이 지점, 즉 'DB 커밋은 성공했는데 메시지 발행은 실패한' 틈이 생기는데, Postgres 내부에 작업을 두면 그 틈 자체가 사라집니다.

2.2 내구성 - 커밋되면 디스크에 남는다

Postgres는 WAL(Write-Ahead Log)을 통해 커밋된 데이터를 디스크에 먼저 안전하게 기록합니다. 서버가 갑자기 죽어도 커밋된 작업은 복구됩니다. 인메모리 큐가 장애 시 잃을 수 있는 그 '마지막 몇 건'을, Postgres는 잃지 않습니다. 작업의 신뢰성이 곧 데이터베이스의 신뢰성과 같아집니다.

2.3 단순성 - 운영해야 할 시스템이 하나뿐

현실적으로 가장 큰 이점일지 모릅니다. 작업 큐를 Postgres에 두면 운영해야 할 시스템이 늘지 않습니다. 백업, 모니터링, 장애 대응, 보안 패치를 이미 하고 있는 데이터베이스 하나에 모두 흡수됩니다. 새 브로커의 학습, 새 장애 모드, 새 온콜 부담이 없습니다. 소수 인력 팀에게 이 '하나로 끝난다'는 단순성은 종종 처리량 수치보다 훨씬 가치 있습니다.

3. Postgres 기반 워크플로의 5가지 핵심 패턴

이론은 충분합니다. 실제로 Postgres로 신뢰성 있는 워크플로를 짤 때 반복해서 등장하는 다섯 가지 핵심 패턴을 제 방식으로 정리했습니다. 이 다섯 개를 이해하면 사실상 절반은 끝난 셈입니다.

3.1 작업 테이블(Job Table)

모든 것의 출발점입니다. 처리할 작업을 한 행씩 담는 테이블을 만듭니다. 상태(대기/처리중/완료/실패), 페이로드(JSON), 재시도 횟수, 예약 실행 시각 같은 컬럼을 둡니다. 작업이 곧 데이터 행이 되므로 SQL로 조회·필터·집계가 자유롭습니다.

3.2 트랜잭셔널 아웃박스(Transactional Outbox)

비즈니스 변경과 작업 등록을 같은 트랜잭션으로 묶는 패턴입니다. 외부로 보낼 이벤트를 곧바로 발행하지 않고, 같은 DB의 아웃박스(작업) 테이블에 먼저 기록합니다. 별도 워커가 그 테이블을 읽어 실제 발행을 담당합니다. 이렇게 하면 'DB는 커밋됐는데 이벤트는 유실된' 이중 쓰기 문제가 사라집니다.

3.3 SELECT FOR UPDATE SKIP LOCKED

여러 워커가 같은 작업 테이블에서 경쟁 없이 작업을 집어가게 하는 잠금 기법입니다. 이미 다른 워커가 잠근 행은 건너뛰고 잠기지 않은 다음 행만 가져옵니다. 워커들이 서로 기다리거나 같은 작업을 중복으로 가져가는 일이 사라져, 깔끔한 병렬 분배가 가능합니다. Postgres 작업 큐의 심장입니다.

3.4 멱등성(Idempotency)

최소 한 번 실행 보장은 곧 '같은 작업이 두 번 실행될 수 있다'는 뜻이기도 합니다. 따라서 작업 핸들러는 두 번 실행돼도 결과가 같도록 멱등하게 설계해야 합니다. 멱등성 키(예: 주문 ID + 작업 종류)를 유니크 제약으로 걸어 중복 부수효과를 차단하는 것이 정석입니다.

3.5 재시도(Retry)와 백오프

일시적 실패(네트워크 오류, 외부 API 타임아웃)는 자연스럽습니다. 작업 행에 재시도 횟수와 다음 시도 시각을 두고, 실패하면 지수 백오프로 재예약합니다. 정해진 횟수를 초과하면 데드레터(dead-letter) 상태로 옮겨 사람이 검토하게 합니다. 이 네 가지(재시도·백오프·상한·데드레터)가 실패 관리의 표준 구성입니다.

4. 코드 예시 - 간단한 작업 큐 만들기

패턴을 실제 코드로 보면 훨씬 분명해집니다. 가장 단순한 작업 큐를 SQL과 의사코드로 그려 보겠습니다. 먼저 작업 테이블입니다.

CREATE TABLE jobs (
    id           BIGSERIAL PRIMARY KEY,
    kind         TEXT        NOT NULL,            -- 작업 종류 (예: send_email)
    payload      JSONB       NOT NULL,            -- 작업 데이터
    status       TEXT        NOT NULL DEFAULT 'pending', -- pending/running/done/failed
    run_at       TIMESTAMPTZ NOT NULL DEFAULT now(),     -- 예약 실행 시각
    attempts     INT         NOT NULL DEFAULT 0,  -- 시도 횟수
    max_attempts INT         NOT NULL DEFAULT 5,
    idem_key     TEXT        UNIQUE,              -- 멱등성 키
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 워커가 빠르게 다음 작업을 찾도록 부분 인덱스
CREATE INDEX idx_jobs_ready
    ON jobs (run_at)
    WHERE status = 'pending';

작업 등록은 비즈니스 로직과 같은 트랜잭션 안에서 일어납니다. 이것이 트랜잭셔널 아웃박스의 핵심입니다.

BEGIN;
  -- 1) 비즈니스 변경
  INSERT INTO orders (user_id, amount) VALUES (42, 19900);
  -- 2) 같은 트랜잭션에서 작업 등록
  INSERT INTO jobs (kind, payload, idem_key)
  VALUES ('send_email', '{"order_id": 1001}', 'email:order:1001');
COMMIT;  -- 둘은 함께 커밋되거나 함께 롤백된다

워커는 다음과 같은 의사코드로 작업을 집어갑니다. 이 부분에서 SKIP LOCKED가 등장합니다.

반복:
    트랜잭션 시작
      작업 = 다음 준비된 작업 1건을 SKIP LOCKED로 잠그고 가져온다
      작업이 없으면: 잠시 대기 후 계속
      작업 상태를 'running'으로, attempts += 1
    커밋

    시도:
      핸들러 실행(작업.payload)   # 멱등하게 설계
      작업 상태를 'done'으로
    실패 시:
      attempts >= max_attempts 이면 'failed'(데드레터)
      아니면 run_at = now() + 백오프, 상태 'pending'으로 복귀

핵심은 이 모든 것이 평범한 SQL과 트랜잭션으로 끝난다는 점입니다. 새 인프라도, 새 프로토콜도 없습니다. 이미 알고 있는 도구로 신뢰성을 조립하는 것입니다.

5. SKIP LOCKED를 이용한 동시성 처리

다섯 패턴 중에서도 가장 마법처럼 느껴지는 것이 SKIP LOCKED입니다. 조금 더 깊이 들여다볼 가치가 있습니다.

여러 워커가 동시에 같은 작업 테이블에서 일거리를 가져가려 한다고 상상해 봅시다. 순진하게 SELECT ... FOR UPDATE만 쓰면, 워커 B는 워커 A가 잠근 행을 가져가려다 잠금이 풀릴 때까지 멈춰 버립니다. 워커가 많아질수록 서로를 기다리는 정체가 심해집니다. 사실상 직렬화되는 것입니다.

여기에 SKIP LOCKED를 더하면 동작이 완전히 달라집니다.

SELECT id, kind, payload
FROM jobs
WHERE status = 'pending' AND run_at <= now()
ORDER BY run_at
FOR UPDATE SKIP LOCKED
LIMIT 1;

이제 워커 B는 워커 A가 이미 잠근 행을 만나면 기다리지 않고 그냥 건너뛰어 다음으로 잠기지 않은 행을 집습니다. 결과적으로 N개의 워커가 N개의 서로 다른 작업을 동시에, 충돌 없이, 중복 없이 가져갑니다. 잠금 대기가 사라지므로 워커를 늘릴수록 처리량이 선형에 가깝게 증가합니다.

SKIP LOCKED는 'Postgres를 작업 큐로 쓸 수 있는가'라는 질문을 'Postgres를 작업 큐로 안 쓸 이유가 있는가'로 뒤집은 기능입니다.

이 한 줄의 잠금 옵션 덕분에, 외부 메시지 브로커가 자랑하던 '경쟁 없는 작업 분배'를 Postgres 안에서 그대로 재현할 수 있습니다. 그것도 트랜잭션 안전성을 한 치도 양보하지 않으면서 말입니다.

6. Postgres vs 전용 도구 비교

그렇다고 Postgres가 모든 전용 도구를 대체한다는 뜻은 아닙니다. 공정한 비교가 필요합니다. 네 가지 대표 도구를 복잡도·처리량·적합 환경 축으로 정리했습니다.

표 1. 워크플로·메시징 도구 비교

도구복잡도처리량적합 환경
Postgres낮음중간중소 규모, 단순 인프라, 트랜잭션 결합
RabbitMQ중간높음메시징 중심, 복잡한 라우팅
Kafka높음매우 높음대규모 스트리밍, 이벤트 로그, 팬아웃
Temporal높음높음복잡한 장기 워크플로, 보상 트랜잭션

표를 관통하는 메시지는 이렇습니다. Postgres는 복잡도가 가장 낮으면서 처리량은 '중간'까지 책임집니다. 그리고 대부분의 서비스가 실제로 필요로 하는 처리량은 바로 그 '중간' 구간 안에 있습니다. Kafka와 Temporal은 강력하지만 그 힘에는 운영 복잡도라는 값이 붙습니다. 문제는 많은 팀이 '언젠가 필요할지 모를' 처리량을 위해 지금 당장 그 복잡도 비용을 선불로 치른다는 점입니다.

7. 언제 Postgres로 충분하고 언제 전용 도구가 필요한가

핵심 질문에 도달했습니다. 경계선은 어디일까요? 제가 판단 기준으로 삼는 신호들을 정리합니다.

7.1 Postgres로 충분한 신호

  • 처리량이 초당 수십~수천 건 규모이고, 폭증해도 그 안에서 움직인다.
  • 작업이 작업 등록과 같은 DB의 데이터 변경과 강하게 묶여 있다(트랜잭션 결합이 이득).
  • 운영 인력이 적어 새 시스템을 늘리는 비용이 부담스럽다.
  • 워크플로 단계가 비교적 단순하다(발송, 후처리, 알림 수준).

7.2 전용 도구가 필요한 신호

  • 처리량이 초당 수만~수십만 건을 지속적으로 넘어선다(Kafka 영역).
  • 같은 이벤트를 여러 컨슈머 그룹이 독립적으로 소비해야 한다(팬아웃, Kafka).
  • 워크플로가 며칠에 걸쳐 실행되고, 복잡한 분기·보상·재생이 필요하다(Temporal).
  • 이벤트를 장기 보존하는 로그로 다시 흘려보내야 한다(Kafka).

제 권고는 분명합니다. Postgres로 시작하고, 위의 '전용 도구 신호'가 실제로 켜질 때 옮기십시오. 거꾸로, 신호가 켜지지도 않았는데 미리 Kafka를 까는 것은 대개 조숙한 최적화입니다.

8. 실무 적용 시나리오 5가지

추상적인 원칙을 구체적인 장면으로 옮겨 보겠습니다. 한국 서비스에서 흔한 다섯 가지 백그라운드 작업에 Postgres 워크플로가 어떻게 들어맞는지입니다.

  • 이메일·SMS 발송: 회원가입 환영, 주문 확인 메일. 발송 작업을 가입·주문 트랜잭션과 묶으면 '가입은 됐는데 메일은 안 간' 사고가 사라집니다. 외부 발송 API 실패는 재시도로 흡수합니다.
  • 결제 후처리: 결제 승인 후 영수증 발행, 포인트 적립, 정산 기록. 멱등성 키로 중복 적립을 막고, 단계별 작업으로 부분 실패를 안전하게 재시도합니다.
  • 데이터 파이프라인: 야간 집계, 리포트 생성, 외부 데이터 동기화. 예약 실행 시각(run_at)으로 스케줄링하고, 무거운 작업을 작은 단위 작업으로 쪼개 워커가 병렬 처리합니다.
  • 알림(푸시·웹훅): 대량 푸시 발송, 외부 시스템으로의 웹훅. SKIP LOCKED로 여러 워커가 나눠 보내고, 실패한 웹훅은 백오프로 재시도합니다.
  • 예약·스케줄링: 구독 갱신, 리마인더, 만료 처리. run_at에 미래 시각을 넣어 두면 그 시점에 워커가 자연스럽게 집어갑니다. 별도 크론 인프라가 필요 없습니다.

다섯 시나리오의 공통점은, 어느 것도 Kafka급 처리량이나 Temporal급 워크플로 복잡도를 요구하지 않는다는 것입니다. 그리고 이 다섯 가지가 사실상 대부분 서비스의 백그라운드 작업 대부분을 차지합니다.

9. 성능과 확장성 한계

균형을 위해 Postgres 워크플로의 한계도 정직하게 짚겠습니다. 이 패턴이 무한히 확장되는 것은 아닙니다.

  • 처리량 천장: 작업 큐는 결국 DB의 쓰기 부하입니다. 초당 수만 건 이상의 작업이 지속되면 같은 DB의 본업(서비스 쿼리)과 자원을 다투게 됩니다. 전용 브로커가 빛나는 구간입니다.
  • 테이블 팽창과 베큠: 완료·실패 작업이 쌓이면 테이블이 부풀고 인덱스가 비대해집니다. 주기적 아카이빙(완료 작업 삭제·이관)과 autovacuum 튜닝이 필수입니다. 방치하면 조회가 느려집니다.
  • 롱 폴링 부하: 워커가 짧은 간격으로 빈 큐를 폴링하면 불필요한 쿼리가 누적됩니다. LISTEN/NOTIFY로 알림 기반 깨우기를 더하면 완화됩니다.
  • 본업 영향: 작업 큐 부하가 핵심 서비스 트랜잭션의 지연을 유발할 수 있습니다. 부하가 커지면 큐를 별도 Postgres 인스턴스로 분리하는 것도 방법입니다.

요점은, Postgres 워크플로는 '무한 확장'이 아니라 '충분히 넓은 구간을 단순하게 커버'하는 해법이라는 것입니다. 그 구간을 넘어서는 순간을 인지하고 옮길 준비만 해 두면 됩니다.

10. 한국 스타트업 환경 적용 - 인프라 단순화와 비용 절감

이 논의는 한국 스타트업 환경에서 특히 설득력을 갖습니다. 이유가 있습니다.

첫째, 인력 구조입니다. 한국의 초기 스타트업은 대개 소수의 풀스택 개발자가 인프라까지 겸합니다. Kafka 클러스터나 Temporal 서버를 별도로 세우고 운영하는 것은 그 자체로 한 사람 몫의 일입니다. Postgres 하나로 작업 큐까지 흡수하면, 운영해야 할 시스템이 줄고 온콜 부담이 가벼워집니다.

둘째, 비용입니다. 클라우드 위에서 매니지드 Kafka나 별도 워크플로 클러스터를 돌리는 비용은 무시할 수 없습니다. 트래픽이 아직 작은 초기 단계에서, '언젠가의 규모'를 위해 지금 그 비용을 지불하는 것은 런웨이를 깎는 일입니다. 이미 결제하고 있는 Postgres 안에 작업 큐를 두면 추가 인프라 비용이 0에 수렴합니다.

셋째, 속도입니다. 한국 스타트업의 경쟁력은 종종 실행 속도에서 나옵니다. 새 브로커를 학습하고 통합하는 데 드는 며칠~몇 주를, 이미 익숙한 SQL로 작업 큐를 짜는 몇 시간으로 대체할 수 있다면, 그 시간은 곧 제품 개발에 투입됩니다.

현실적 조언. 시드~시리즈A 단계라면 Postgres 작업 큐로 시작하길 권합니다. 트래픽이 검증되고 '전용 도구 신호'가 켜진 뒤에 Kafka·Temporal을 도입해도 늦지 않습니다. 조기 도입의 복잡도 비용이 그 이득을 거의 항상 앞섭니다.

11. 위험 - "Postgres 만능"의 함정

여기서 반대 방향의 경고도 분명히 해야 공정합니다. 'Postgres로 충분하다'는 메시지가 'Postgres가 만능'으로 변질되는 순간, 이 글은 또 다른 조숙한 결정을 부추기는 셈이 됩니다.

Postgres 만능주의의 전형적인 함정은 이렇습니다.

  • 한계 신호를 무시하기: 처리량이 명백히 천장을 치고 있는데도 '우린 Postgres로 다 한다'는 자존심 때문에 옮기지 않는 것. 이때는 본업 DB까지 함께 느려집니다.
  • 운영 부담을 과소평가하기: 작업 큐를 Postgres에 두면 인프라는 줄지만, 베큠·아카이빙·인덱스 관리·모니터링이라는 새 운영 항목이 생깁니다. '공짜'가 아니라 '다른 비용'입니다.
  • 워크플로 복잡도를 억지로 구겨 넣기: 며칠짜리 다단계 보상 트랜잭션을 작업 테이블 하나로 흉내 내려다 코드가 스파게티가 됩니다. 그 지점이 Temporal을 진지하게 볼 때입니다.
  • 본업과 작업 큐의 자원 경합: 핵심 서비스 트랜잭션이 작업 큐 부하에 밀려 느려지는데도 같은 인스턴스를 고집하는 것.

건강한 태도는 단순합니다. Postgres는 훌륭한 기본값이지 영원한 정답이 아닙니다. 시작점으로는 거의 항상 옳지만, 한계 신호를 정직하게 읽고 제때 옮기는 규율이 함께 있어야 합니다.

12. 결론 + 즉시 적용 가능한 3가지

다시 처음의 질문으로 돌아갑니다. 워크플로 신뢰성을 위해 꼭 Kafka·Temporal이 필요할까요? 대부분의 중소 서비스에서 답은 '아니오'입니다. 신뢰성의 진짜 원천은 화려한 브로커가 아니라 Postgres의 트랜잭션이며, 우리는 이미 그것을 손에 쥐고 있습니다. 작업을 데이터로 다루고, 트랜잭션으로 묶고, SKIP LOCKED로 분배하고, 멱등성으로 중복을 무해화하는 것만으로 메시지 브로커 못지않은 내구성이 만들어집니다.

동시에 이것은 '항상 Postgres'라는 교조가 아닙니다. 규모와 복잡도가 임계를 넘는 순간을 인지하고 제때 전용 도구로 옮기는 균형이 핵심입니다. 오늘 바로 적용할 수 있는 세 가지로 마무리합니다.

  1. 작업 등록을 비즈니스 트랜잭션과 같은 트랜잭션으로 묶어라. 이 한 가지만으로 작업 유실이라는 가장 흔한 사고가 구조적으로 사라집니다.
  2. 워커 분배는 SELECT FOR UPDATE SKIP LOCKED로 구현하라. 경쟁 없는 병렬 처리를 외부 브로커 없이 Postgres 안에서 그대로 얻습니다.
  3. 모든 작업 핸들러를 멱등하게 설계하라. 최소 한 번 실행 환경에서 중복 실행을 무해하게 만드는 것이 신뢰성의 마지막 한 조각입니다.

다음에 "백그라운드 작업이니까 큐가 필요해"라는 생각이 떠오른다면, 한 번 멈춰서 물어보시기 바랍니다. 정말 새 인프라가 필요한가, 아니면 이미 있는 Postgres가 그 일을 더 단순하고 안전하게 해낼 수 있는가.

자주 묻는 질문 (FAQ)

Q1. Postgres로 내구성 있는 워크플로를 만들 수 있나요?

네. Postgres는 ACID 트랜잭션과 디스크 영속성을 보장하므로, 작업 테이블과 SKIP LOCKED, 멱등성 키, 재시도 컬럼을 조합하면 신뢰성 있는 작업 큐와 워크플로 엔진을 만들 수 있습니다. 수십~수천 TPS 규모의 중소 서비스라면 별도 브로커 없이 대부분의 백그라운드 작업을 안정적으로 처리합니다.

Q2. Kafka가 꼭 필요한가요, Postgres로 충분한가요?

초당 수만 건 이상 스트리밍, 다중 컨슈머 그룹 팬아웃, 장기 보존 이벤트 로그가 필요하면 Kafka입니다. 그러나 이메일·결제 후처리·알림 같은 일반 작업은 Postgres 큐로 충분합니다. Postgres로 시작하고 한계가 올 때 옮기는 편이 합리적입니다.

Q3. SELECT FOR UPDATE SKIP LOCKED가 무엇인가요?

여러 워커가 동시에 작업을 가져갈 때, 이미 다른 워커가 잠근 행은 건너뛰고 잠기지 않은 다음 행만 가져오게 하는 Postgres 잠금 옵션입니다. 잠금 대기와 중복 처리 없이 경쟁 없는 병렬 분배를 가능하게 합니다.

Q4. Temporal 대신 Postgres를 쓰는 게 나은 경우는 언제인가요?

워크플로가 단순하고, 별도 클러스터 운영 인력이 부족하며, 이미 Postgres를 쓴다면 Postgres가 낫습니다. 반대로 여러 날에 걸친 장기 워크플로, 복잡한 분기·보상·결정론적 재생이 필요하면 Temporal이 적합합니다.

Q5. Postgres 작업 큐는 얼마나 신뢰할 수 있나요?

작업 등록을 비즈니스 트랜잭션과 묶으면 작업 유실이 구조적으로 사라집니다. 여기에 멱등성 키로 중복을 무해화하고 재시도·데드레터로 실패를 관리하면 메시지 브로커 못지않은 신뢰성을 얻습니다. 트랜잭션이 곧 내구성의 토대입니다.
