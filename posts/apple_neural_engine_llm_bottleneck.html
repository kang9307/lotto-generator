LLM의 병목은 연산이 아니라 데이터 이동이다 - Apple Neural Engine 역공학이 보여준 것

M5의 ANE 통합 배경부터 2,048개 MAC 레인, 커널·타일 DMA의 직렬화 지연까지 하드웨어 심층 분석

2026-09-13 개발/인프라

인공지능 가속기 시장에서 하드웨어 사양을 나타낼 때 가장 흔히 내세우는 지표는 연산 처리량, 즉 초당 테라 연산 수치(TOPS, Tera Operations Per Second)다. 모바일 스마트폰부터 노트북과 전문 워크스테이션에 이르기까지 반도체 제조사들은 새로운 세대의 칩이 발표될 때마다 신경망 처리 장치(NPU)의 연산 능력이 몇 배로 증가했는지를 대대적으로 홍보한다. 고정 소수점이나 부동 소수점 곱셈-누산 유닛이 실리콘 다이 위에 빽빽하게 채워질수록 거대 모델의 추론 속도 역시 선형적으로 비례해 빨라질 것이라는 기대를 독자에게 심어주기 쉽다.

하지만 현대 대규모 언어 모델(LLM)을 장비 위에서 직접 구동해보는 순간 이러한 기대는 번번이 어긋난다. 수십 TOPS를 상회하는 NPU를 장착했다고 자부하는 칩셋에서도 매개변수가 수십억 개에 달하는 트랜스포머 모델을 실행하면 초당 생성 토큰 수는 기대치에 한참 못 미치는 한 자릿수나 턱걸이 수준의 두 자릿수에 머무는 현상이 일어난다. 연산 유닛의 점유율은 절반도 채우지 못한 채 하드웨어는 끊임없이 무언가를 기다린다. 이 미스터리를 풀기 위해서는 연산 블록 자체의 이론적 피크 수치가 아니라, 데이터가 칩 내부와 외부 메모리를 오가는 물리적 경로를 분해해 보아야 한다.

시스템 소프트웨어 엔지니어 Eileen Yoon이 공개한 Apple Neural Engine(ANE) 심층 역공학 분석은 바로 이 괴리의 원인을 실리콘 단위의 아키텍처와 계측 데이터로 명쾌하게 드러낸다. 16개의 연산 코어와 2,048개의 병렬 곱셈-누산(MAC) 레인을 탑재한 애플 실리콘의 전용 신경망 블록이 어째서 최신 LLM 추론 환경에서 연산 장치가 아니라 데이터 이동의 구조적 족쇄에 묶이게 되었는지, 그리고 애플이 최신 M5 프로세서에서 ANE 코어를 GPU 내부로 접어 넣는 중대한 설계를 단행한 배경이 무엇인지 명료한 인과관계를 제시한다.

본 분석은 2026년 8월 10일 Eileen Yoon이 발표한 ANE 역공학 기술 분석 보고서에 기반합니다. 특정 제조사의 설계 실패를 비난하기 위한 목적이 아니며, 2017년 합성곱 신경망(CNN) 시대에 확정된 실리콘 가정이 2026년 트랜스포머 워크로드와 부딪히며 발생하는 구조적 불일치를 하드웨어 계측치에 근거해 객관적으로 추적합니다.

M5가 ANE를 GPU 속으로 접어 넣은 이유 — 독립형 NPU 시대의 변곡점

오픈소스 생태계에서 애플 실리콘의 리눅스 지원을 개척해온 Eileen Yoon은 3년 전 ANE 리눅스 드라이버 개발 작업을 중단했던 배경을 회고하며 글을 시작한다. 당시 그가 내린 소결은 "이 블록은 그렇게 유용하지 않다"는 것이었다. ANE 하드웨어의 아키텍처는 지나치게 특정한 연산 스타일에 종속되어 있어 범용 가속기 플랫폼을 구축하기에는 지나치게 폐쇄적이었고, 드라이버를 통해 하드웨어 인터페이스를 열어주더라도 ANE가 수행할 수 있는 워크로드의 범주를 넓히지 못했다. 심지어 애플 자체의 데스크톱 운영체제인 macOS조차 파인더(Finder)에서 미리보기 이미지를 고해상도로 업샘플링하는 식의 제한적인 백그라운드 작업 외에는 ANE를 일상적으로 활발하게 가동하지 않는 상태였다.

그러나 2025년 등장한 M5 칩의 설계 변경은 이 하드웨어 블록의 생태계에 결정적인 마침표를 찍었다. 애플은 M5의 헤드라인 기능으로 당당하게 "LLM 성능"을 전면에 내세웠으며, 그와 동시에 독립적인 블록으로 존재하던 ANE 코어들을 물리적으로 GPU 코어 내부로 접어 넣었다(conveniently folded inside the GPU cores). 저자는 이 구조 변화를 목격하며 이를 가리켜 "독립형 NPU의 종말의 시작"이라고 표현했다.

별도의 실리콘 면적을 차지하던 고정형 가속기가 사라지고 범용 병렬 프로세서인 GPU 내부의 기능 유닛으로 흡수되었다는 사실은 시사하는 바가 크다. 그것은 ANE의 곱셈-누산 연산 자산 자체가 무가치해졌다는 뜻이 아니라, 독립형 NPU가 고수해왔던 독자적인 데이터 경로와 고정된 스케줄링 방식이 트랜스포머 중심의 LLM 워크로드와 더 이상 양립할 수 없음을 제조사 스스로 인정한 결과이기 때문이다. 저자가 3년 만에 M1의 ANE 하드웨어를 다시 분해해 연산, 데이터패스, 스케줄러, 메모리 및 실행 모델의 전모를 역공학으로 밝혀낸 동기는 바로 여기에 있었다.

  • 독립형 NPU의 생태계 한계: 범용 연산 플랫폼으로의 확장이 불가능한 고정 데이터 흐름 구조로 인해 리눅스 드라이버 개방 이후에도 지원 가능한 워크로드의 확장이 정체되었다.
  • M5의 아키텍처 흡수: M5 세대에 이르러 애플은 LLM 처리량을 핵심 마케팅으로 설정하고 독립된 ANE 블록을 GPU 코어의 연산 유닛 내부로 통합했다.
  • 실리콘 설계 철학의 전환: 고정형 하드웨어 파이프라인에서 벗어나 GPU의 유연한 고대역폭 메모리 서브시스템과 결합하는 방향으로 온디바이스 AI 하드웨어의 중심축이 이동했다.

A11 Bionic에서 시작된 실리콘 유산 — 2017년의 CNN 최적화 설계

하드웨어 아키텍처의 의사결정을 이해하기 위해서는 그 설계가 최초로 물리적인 실리콘으로 박제된 시점의 맥락을 돌아보아야 한다. 오늘날 우리가 애플 실리콘 M 시리즈 맥북에서 마주하는 ANE의 내부 뼈대는 완전히 새로운 백지에서 출발한 것이 아니다. 이 설계의 기원은 바로 2017년 아이폰 X에 탑재된 A11 Bionic 칩으로 거슬러 올라간다.

2017년 당시 모바일 기기에서 인공지능 워크로드의 절대적인 주류는 조밀한 이미지 처리를 담당하는 합성곱 신경망(CNN)이었다. 페이스 ID를 위한 얼굴 인식, 카메라 센서로 들어오는 프레임의 실시간 노이즈 제거, 피사체와 배경을 분리하는 시맨틱 분할 등이 칩 설계자들에게 주어진 최우선 과제였다. 이러한 CNN 연산은 매우 뚜렷한 특징을 지닌다. 필터 역할을 하는 커널 가중치 텐서가 한 번 로드되면, 수백만 픽셀로 구성된 2차원 공간 상의 입력 슬라이딩 윈도우 전역에 걸쳐 수없이 반복적으로 재사용된다.

따라서 2017년의 실리콘 설계자들은 가중치를 칩 내부로 가져오는 비용이 다소 발생하더라도, 일단 코어 내부의 로컬 메모리에 적재해두면 막대한 수치의 공간적·시간적 데이터 재사용(Predictable Reuse)을 통해 메모리 대역폭의 압박을 완전히 상쇄할 수 있다고 가정했다. 모바일 기기의 엄격한 전력 및 발열 한계 안에서 배터리를 절약하며 수 TOPS의 성능을 달성하기 위한 최적의 엔지니어링 선택이었던 셈이다. ANE의 모든 데이터 경로와 캐시 계층 구조는 바로 이 2017년의 가정을 완벽하게 만족시키도록 하드웨어 레벨에서 고착화되었다.

  • 설계 원형의 탄생: 2017년 A11 Bionic 칩에서 최초 구현된 2코어 NPU 구조가 확장되어 M1의 16코어 대형 복합 블록으로 계승되었다.
  • 타깃 워크로드의 특성: dense tensor reduction과 입력 평면 전체에 걸친 높은 수준의 가중치 재사용을 전제로 하는 비전 중심의 CNN 모델에 맞춰 최적화되었다.
  • 모바일 제약 조건: 극도로 제한된 모바일 배터리 용량과 수동 냉각 환경에서 메모리 접근 횟수를 최소화하기 위해 특화된 로컬 버퍼 구조를 채택했다.

16개 코어와 2,048개 병렬 MAC 레인의 실제 구조

그렇다면 ANE의 연산 코어 자체는 어떤 규모로 구성되어 있는가. M1 ANE의 내부를 들여다보면 16개의 병렬 연산 코어가 균등하게 배열되어 있다. 그리고 각각의 연산 코어는 내부에 128개의 FP16 병렬 곱셈-누산(MAC) 레인을 갖추고 있다. 정밀도를 INT8로 낮출 경우에는 레인의 폭이 두 배로 늘어나 256개의 INT8 레인으로 동작한다. 따라서 칩 전체로 계산하면 다음과 같은 병렬 연산 규모가 도출된다.

16개 코어 × 128개 레인/코어 = 총 2,048개의 병렬 MAC 레인

이 2,048개의 레인은 매 단일 클럭 사이클마다 2,048회의 스칼라 곱셈과 누산을 공간적으로 동시에 실행한다. 원문 저자가 지적하듯, 개별 MAC 레인은 자신이 지금 계산하고 있는 값이 행렬의 어느 차원인지, 혹은 텐서의 어떤 축을 따라 축약되고 있는지 전혀 알지 못한다. 레벨 2 캐시나 외부 메모리로부터 피연산자(Operand a와 b)가 공급되면, 16비트 곱셈기를 거친 뒤 32비트 가산기로 전달되고, 루프 사이클 동안 32비트 누산기 레지스터(Accumulator)에 결과를 계속 더해나간다.

┌────────────────────── core ─────────────────────┐
│ ┌───────── 256× MACs ─────────┐  ┌────────────┐ │
│ │ MAD ─► add ─► accumulator   │─►│ activation │ │
│ │        ▲          │         │  └────────────┘ │
│ │        └──────────┘         │                 │
│ └─────────────────────────────┘                 │
└─────────────────────────────────────────────────┘

이 연산 구조에서 핵심적인 하드웨어적 최적화는 피연산자 누산의 피드백 루프가 레인 내부의 로컬 레지스터에서 완결된다는 점이다. 연산 주기 중간마다 외부 메모리로 부분합(Partial Sum)을 읽고 쓰는 라운드트립이 발생하지 않으므로, 순수한 연산 집약적 계측에서는 극도로 높은 에너지 효율을 자랑한다.

operand a ──┐   ┌────────────┐   p[31:0]   ┌──────────────┐   s_next[31:0]  ┌─────────────┐
            ├──►│ MULTIPLIER │────────────►│ 32-BIT ADDER │────────────────►│ ACCUMULATOR │
operand b ──┘   └────────────┘             └──────▲───────┘                 └──────┬──────┘
                                                  │                                │ s[31:0]
                                                  └────────────────────────────────┘

정밀도 제어 측면에서 ANE는 고정 소수점 연산으로 중간 과정을 유지하다가 최종 출력 시점에 FP16으로 변환해 읽어낸다. 곱셈기는 16비트로 동작하고, 32비트 레지스터 내부에서는 Q16.16 고정 소수점 형태로 누적된다. 원문 저자가 CoreML 프로그램을 통해 누산기의 범위를 측정한 실험에 따르면, 누산기 값은 2의 15제곱(32,768) 위치에서 포화(Saturate) 클램프가 발생하며, 이는 정확히 부호 있는 32비트 고정 소수점 레지스터의 수학적 동작과 일치했다.

  • 압도적인 공간 병렬성: 클럭마다 2,048개의 곱셈-누산이 동시에 터져 나오는 순수 연산력은 11 TOPS라는 강력한 사양을 충족한다.
  • 로컬 피드백 루프: 부분합을 저장하는 32비트 레지스터가 연산기 바로 옆에 배치되어 반복 연산 중 외부 버스 트래픽을 유발하지 않는다.
  • 고정 소수점 누산과 FP16 변환: Q16.16 기반의 정밀한 내부 누산을 거친 후 최종 단계에서 하드웨어 변환을 거쳐 부동소수점으로 데이터를 인출한다.

워크로드의 불일치 — 합성곱 재사용 패턴과 트랜스포머 디코딩의 충돌

문제는 이 훌륭한 2,048개의 연산 레인이 트랜스포머 기반의 거대 언어 모델을 만나는 순간 무력화된다는 데 있다. 합성곱 신경망에서 점곱(Dot Product)을 수행하는 연산자나, 트랜스포머의 어텐션 메커니즘에서 쿼리(Query)와 키(Key) 벡터 사이의 점곱을 수행하는 연산자는 수학적으로 동일한 MAC 작업이다. 연산 장치 자체는 자신이 CNN을 돌리는지 LLM을 돌리는지 구분하지 않는다.

하지만 피연산자가 언제, 어디서 들어오고, 어디에 머무르며, 어떻게 빠져나가는가를 결정하는 데이터 흐름(Dataflow)으로 시선을 돌리면 이야기는 완전히 달라진다. 트랜스포머의 추론은 크게 두 가지 국면으로 나뉜다. 프롬프트를 한 번에 밀어 넣는 사전 충전(Prefill) 단계와, 토큰을 하나씩 연쇄적으로 생성하는 자기회귀적 디코딩(Autoregressive Decode) 단계다. 실제 사용자가 챗봇을 사용하거나 코드를 자동 완성할 때 체감 성능을 좌우하는 것은 바로 이 디코딩 단계다.

자기회귀적 디코딩에서는 매 스텝마다 오직 단 하나의 토큰 벡터가 입력으로 들어온다. 수십억 개에 달하는 모델의 전체 가중치 행렬은 이 단 하나의 토큰 벡터와 행렬-벡터 곱셈(GEMV)을 수행하기 위해 메인 DRAM 메모리로부터 칩 내부로 몽땅 스트리밍되어야 한다. 그리고 방금 생성된 토큰을 바탕으로 다음 토큰을 계산하려면, 가중치 행렬 전체를 외부 메모리에서 또다시 처음부터 끝까지 읽어와야 한다. 즉, 2017년 CNN 설계가 그토록 신뢰했던 "가중치의 공간적·시간적 반복 재사용"이라는 전제 조건이 트랜스포머 디코딩에서는 단 1%도 성립하지 않는다.

  • 가중치 재사용의 붕괴: CNN은 하나의 가중치를 수만 번 재활용하지만, LLM 디코딩에서는 1토큰 생성당 가중치 재사용 횟수가 사실상 1회에 수렴한다.
  • 산술 강도(Arithmetic Intensity)의 급락: 바이트당 수행하는 연산 횟수가 극단적으로 낮아지면서 시스템은 연산 바운드가 아닌 전형적인 메모리 대역폭 바운드로 전락한다.
  • 아키텍처 가정의 배반: 연산 장치는 가중치가 들어오기만을 기다리며 놀고 있고, 메모리 버스만 비명을 지르는 구조적 불일치가 실리콘 레벨에서 고착된다.

실측 DMA 대역폭 — Kernel과 Tile, 그리고 GPU 읽기 성능의 격차

이러한 구조적 불일치는 추상적인 이론에 그치지 않는다. Eileen Yoon은 ANE의 내부 직접 메모리 접근(DMA) 엔진과 GPU의 메모리 읽기 성능을 정밀하게 계측하여 그 구체적인 수치를 숫자로 증명했다. 측정 방식은 CoreML 환경에서 커널 및 타일의 크기를 실행 시간으로 나누는 방식을 취했으며, GPU는 Metal 버퍼 읽기 셰이더를 통해 통합 메모리 접근 대역폭을 측정했다.

실측 결과는 충격적인 하드웨어 성능 격차를 보여준다. ANE 내부에서 가중치를 적재하는 커널 DMA(Kernel DMA)의 대역폭은 37.99 GB/s에 불과했다. 또한 입력 활성화 텐서를 DRAM에서 L2 캐시로 나르는 타일 DMA(Tile DMA)의 대역폭은 59.08 GB/s로 측정되었다. 반면 동일한 실리콘 다이 위에 존재하는 GPU의 읽기 대역폭은 77.70 GB/s에 달했다.

단순히 단일 경로의 수치만 보더라도 ANE의 가중치 전송 통로는 GPU에 비해 절반 수준에 불과하다. ANE가 아무리 2,048개의 MAC 레인으로 11 TOPS의 연산력을 뽐내더라도, 가중치를 메인 메모리에서 퍼 올리는 수도관의 굵기 자체가 GPU보다 훨씬 가늘게 뚫려 있었던 것이다.

  • 가중치 적재 통로의 협소함: 커널 DMA의 37.99 GB/s는 GPU의 77.70 GB/s에 비해 현저히 낮아 매 토큰마다 방대한 모델 파라미터를 읽어오기에 태생적으로 불리하다.
  • 타일 전송의 한계: 입력 활성화를 처리하는 타일 DMA 역시 59.08 GB/s에 머물며 통합 메모리 컨트롤러의 최대 성능을 온전히 이끌어내지 못한다.
  • 단일 경로의 열세: 전용 하드웨어라는 수식어가 무색하게 데이터 인출 속도에서 범용 GPU 파이프라인에 완전히 밀리는 양상이 계측되었다.

병목의 정체 — 합산 대역폭이 아니라 두 DMA 경로의 직렬화(Serialization)

하지만 진정한 병목의 정체는 개별 대역폭의 절대 수치보다 훨씬 더 치명적인 곳에 숨어 있었다. 커널 DMA(37.99 GB/s)와 타일 DMA(59.08 GB/s)의 요구 대역폭을 산술적으로 단순히 합산하면 약 97.07 GB/s(약 98 GB/s)가 나온다. 이는 테스트 대상이었던 M3 프로세서의 시스템 DRAM 대역폭 상한선인 100 GB/s에 근접하지만 넘어서지는 않는 수준이다.

만약 ANE의 메모리 하위 시스템이 정상적으로 설계되어 두 DMA 엔진이 동시에(concurrently) 비동기 메모리 요청을 컨트롤러에 밀어 넣을 수 있었다면, 이론적으로는 98 GB/s 안팎에서 병렬 중첩 처리가 일어났어야 한다. 하지만 실제로 커널과 타일 전송을 동시에 요구하는 복합 워크로드를 계측했을 때 드러난 결합 실행 시간은 두 경로의 개별 실행 시간의 단순한 물리적 합산과 정확히 일치했다.

이것이 의미하는 기술적 사실은 명백하다. ANE 내부의 두 DMA 경로는 병렬로 동작하지 못하고 순차적으로(serially) 직렬화되어 요청을 보낸다. 커널 가중치를 다 읽어올 때까지 타일 데이터 전송은 대기하고, 타일 데이터가 다 들어온 뒤에야 다음 단계가 진행된다. 원문 저자는 이 뼈아픈 계측 결과를 두고 ANE의 DRAM 처리량이 "이중으로 불리하다(doubly penalized)"고 평가했다. GPU보다 개별 경로의 처리 속도도 느린 데다, 그 느린 두 경로의 지연 시간이 병렬로 중첩되지 못하고 고스란히 덧셈으로 쌓이기 때문이다.

  • 요청의 직렬화: 독립적으로 존재해야 할 두 DMA 채널이 하드웨어 내부에서 상호 배타적으로 실행되며 지연시간을 그대로 누적시킨다.
  • 이중 불이익의 굴레: 느린 전송 속도와 순차적 대기 시간이 곱절로 작용하여 실효 DRAM 활용 효율을 바닥으로 끌어내린다.
  • DRAM 버스의 기아: 칩셋 전체의 메모리 컨트롤러는 100 GB/s를 받아줄 준비가 되어 있음에도, ANE 스스로의 직렬화 제약으로 인해 버스를 절반밖에 쓰지 못한다.

루프라인 한계와 온디바이스 LLM 추론 설계에 주는 실무적 함의

컴퓨팅 아키텍처의 성능 한계를 분석할 때 널리 쓰이는 도구는 루프라인 모델(Roofline Model)이다. 시스템의 이론적 연산 최고봉(Peak Compute)과 메모리 대역폭의 기울기가 만나는 지점에서, 현재 실행하려는 알고리즘의 산술 강도가 어디에 위치하는지를 통해 병목의 본질을 진단한다.

M1 ANE는 공식 사양으로 68 GB/s 시스템 DRAM 대역폭 환경에서 11 TOPS의 연산 성능을 내도록 설계되어 있다. 이 하드웨어에서 토큰당 수십억 번의 연산이 단 몇 바이트의 데이터 재사용 없이 일어나는 LLM 디코딩을 수행하면, 동작 지점은 루프라인의 평평한 상단(연산 바운드)이 아니라 가파르게 치솟는 좌측 하단(메모리 대역폭 바운드)에 확고하게 갇혀버린다.

원문 저자가 도출한 계산에 따르면, ANE에서 자기회귀적 디코딩을 수행할 때 현재의 메모리 루프라인 제약 아래에서 초당 토큰 생성 속도를 초당 10토큰에서 25토큰으로 2.5배 개선하고자 한다면, ANE의 연산 코어를 늘리거나 MAC 레인을 확장하는 것은 아무런 소용이 없다. 오직 메모리 스트리밍 대역폭을 정확히 2.5배 늘려야만 그에 비례해 디코딩 속도가 증가한다.

이러한 분석이 온디바이스 AI 애플리케이션을 개발하고 인프라를 설계하는 실무 엔지니어들에게 주는 교훈은 매우 뼈아프다. 하드웨어 벤더가 제공하는 칩셋 사양표의 "NPU TOPS" 숫자는 LLM 추론 환경에서 아무런 성능 보증 수표가 되지 못한다. 모델 가중치가 어떤 버스를 타고 들어오는지, 엔진 내부의 메모리 접근이 병렬화되어 있는지, 그리고 통합 메모리의 실효 읽기 대역폭이 얼마나 보장되는지를 확인하지 않은 채 NPU 전용 추론 엔진을 도입하는 것은 연산기가 굶주린 채 멈춰 서 있는 하드웨어에 과도한 기대를 거는 일에 불과하다.

  • 사양표의 허상: 11 TOPS라는 거대한 연산력은 초당 가중치 전체를 읽어와야 하는 LLM 디코딩 환경에서 대부분 잠들어 있다.
  • 선형적 대역폭 비례: 디코딩 속도를 두 배로 올리고 싶다면 칩의 클럭이나 코어가 아니라 메모리 파이프라인의 물리적 처리량을 두 배로 넓혀야 한다.
  • 실무 선택의 기준: 온디바이스 서빙 프레임워크를 선택할 때 고정 NPU 백엔드보다 유연하고 대역폭이 높은 GPU 백엔드(예: Metal)가 오히려 훨씬 높은 토큰 처리량을 기록하는 현실의 근거가 여기에 있다.

제어 파이프라인과 데이터 경로 — ControlDMA에서 활성화 함수까지

ANE의 아키텍처를 온전히 복기하기 위해서는 메모리 파이프라인의 입구인 작업 디스크립터(Task Descriptor)부터 연산 출구인 활성화 함수 계층까지의 전체 데이터패스를 조망해야 한다. ANE의 작업 실행은 정교하지만 철저하게 격리된 3단계 DMA 흐름으로 개시된다.

가장 먼저 ControlDMA가 동작하여 호스트로부터 전달받은 태스크 디스크립터(TD)를 ANE의 하드웨어 구성 레지스터 파일로 복사한다. 이어서 KernelDMA가 활성화되어 DRAM에 저장된 가중치 텐서 W를 개별 연산 코어에 딸린 로컬 커널 메모리(KMem)로 로드한다. 마지막으로 TileDMA가 실행되어 추론 대상 입력 데이터 X를 외부 DRAM에서 칩 내부의 공유 L2 캐시로 스트리밍한다. 각 코어의 MAC 유닛들은 이 데이터를 바탕으로 행 단위의 점곱 축약을 수행하여 출력 행렬 Y의 한 행을 완성한다.

여기서 주목해야 할 치명적인 아키텍처 제약은 공유 L2 캐시와 코어별 KMem 사이에는 하드웨어적으로 직접적인 데이터 연결 경로가 존재하지 않는다는 점이다. KMem은 오직 KernelDMA를 통해서만 채워질 수 있고, L2 캐시는 오직 TileDMA를 통해서만 채워진다. 가중치와 입력 데이터가 칩 내부에서 상호 교환되거나 유연하게 캐시 공간을 공유할 수 없도록 물리적 벽이 쳐져 있는 것이다.

한편 연산이 완료된 이후의 후처리 단계인 활성화 함수(Activation)는 매우 독특한 방식으로 최적화되어 있다. 점곱 계산이 끝난 직후 메모리로 결과를 내보내지 않고 연산 코어 말단에 붙은 활성화 블록으로 결과가 직결된다. Eileen Yoon이 CoreML의 활성화 레이어를 역공학하여 레지스터 파일(hwx)을 덤프한 결과, 하드웨어 주소 0x4288부터 시작되는 33개의 연속된 FP16 단어가 발견되었다.

이 33개의 상수는 하드웨어 수준에서 tanh 함수를 32개 구간으로 균등 분할해 저장해둔 양자화 샘플 테이블이었다. ANE는 복잡한 초월함수 연산기를 코어마다 직접 내장하는 대신, 33개 엔트리를 갖는 조각별 선형 보간(Piecewise-linear LUT) 하드웨어를 통해 활성화 값을 즉각 산출하는 방식을 택했다. 비선형 활성화 함수를 단일 사이클에 가깝게 해결하려 했던 이러한 디테일은 CNN 추론에서는 눈부신 하드웨어 효율을 뽐냈지만, 전단부 메모리 파이프라인의 직렬화 병목 앞에서는 빛이 바랠 수밖에 없었다.

  • 격리된 3단계 DMA: ControlDMA, KernelDMA, TileDMA로 엄격하게 분리되어 하드웨어 레지스터와 로컬 버퍼를 채운다.
  • 캐시 간 직접 경로의 부재: L2 캐시와 코어 로컬 KMem 사이에 데이터 패스가 없어 유연한 메모리 재구성이 불가능하다.
  • 33엔트리 조각별 선형 LUT: 복잡한 수학 함수를 33개 FP16 상수의 하드웨어 선형 보간으로 압축 처리하는 극단적 고정 파이프라인을 구축했다.

확인하지 못한 것

Eileen Yoon의 1차 역공학 분석 보고서가 다룬 연구 범위와 공개된 하드웨어 덤프의 한계에 따라, 다음 항목들은 본 분석에서 최종적으로 확인하지 못했다.

  • M5 칩에서 구현된 ANE-GPU 통합의 세부 마이크로아키텍처: 원문은 M5가 ANE 코어를 GPU 코어 내부로 흡수했다는 헤드라인 사실과 그로 인한 구조적 의미만을 언급하고 있으며, 통합된 코어의 구체적인 레지스터 맵, 공유 캐시 계층 및 실행 유닛 결합 방식에 대해서는 상세 데이터를 다루지 않았다.
  • M3 및 M4 등 후속 세대 ANE의 DMA 직렬화 유지 여부: 본문의 상세 역공학 및 하드웨어 레지스터 분석은 M1 프로세서의 ANE 블록을 기준으로 수행되었으므로, M3나 M4의 독립형 ANE에서도 커널 및 타일 DMA가 완전히 동일한 직렬화 지연을 겪는지는 원문에서 확정하지 않았다.
  • INT4 이하 초저비트 양자화 시의 실효 대역폭 변화: 계측 실험이 FP16 및 INT8 연산 레인을 중심으로 이루어졌기 때문에, 4비트 이하 극단적 가중치 양자화(AWQ, GPTQ 등)를 적용했을 때 커널 DMA의 처리량과 지연시간이 어떻게 변화하는지에 대한 실측 데이터는 포함되지 않았다.
  • CoreML 외 독자 프레임워크 구동 시의 제어 오버헤드: 실측에 사용된 도구가 애플 공식 CoreML 런타임과 hwx 레지스터 파일 컴파일러였으므로, 애플의 드라이버 스택 자체에 내재된 소프트웨어 큐잉 오버헤드가 DMA 실측 수치에 미친 미세한 영향은 분리되어 검증되지 못했다.
