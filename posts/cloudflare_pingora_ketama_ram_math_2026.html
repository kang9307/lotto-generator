1. PBR과 일관 해싱: 100TB 메모리 절감의 계기

일반적으로 대규모 분산 프록시 환경에서는 각 서버 노드가 담당하는 작업 공간을 효율적으로 격리하고 메모리 누수를 억제하는 작업이 전체 서비스의 안정성을 결정짓는 토대가 된다.

Cloudflare 공식 기술 블로그에 따르면, Cloudflare는 전 세계 수천 대의 서버에서 페타바이트 단위의 RAM과 수백만 개의 CPU 코어를 운용하고 있으며, 모든 노드에서 모든 서비스가 동시에 실행되어야 하는 아키텍처 특성상 메모리 낭비를 줄이는 작업이 중요하다고 밝혔다. 원문은 지난달 DNS 팀이 DNS 캐시 메모리 최적화를 통해 100TB의 메모리를 감축한 데 이어, 이번에는 프록시 서비스의 일관 해싱 알고리즘을 개선하여 전 세계적으로 100TB 이상의 RAM을 추가로 회수했다고 적는다.

이번 최적화의 발단은 내부 성능 팀의 Ivan 엔지니어가 등록한 티켓에서 비롯되었다. 해당 티켓에는 "Excessive memory usage from pingora-ketama in Pingora Backend Router"라는 내용이 명시되어 있었다. 원문은 Cloudflare의 내부 로드 밸런싱 서비스인 Pingora Backend Router(약칭 PBR)가 예상보다 훨씬 많은 메모리를 소비하고 있었으며, 특히 일관 해싱 처리를 담당하는 오픈소스 라이브러리 pingora-ketama와 연관된 구조체에서 극심한 메모리 사용이 관측되었다고 적는다.

원문에서 밝힌 문제의 핵심 배경 요인은 아래 3가지로 정리된다.

  • PBR 프로세스 내부에서 특정 상황에 일관 해싱 구조체 메모리가 최대 6GB까지 팽창하는 과도한 사용량이 발생했다는 사실.
  • 캐시 가능한 요청을 URL 기반으로 데이터센터 내 특정 단일 서버로 안정적으로 라우팅하기 위해 일관 해싱 알고리즘이 필수적으로 사용되고 있었다는 사실.
  • 다양한 기능 플래그와 컴플라이언스 요건이 조합되면서 복수의 해시 링이 메모리에 중복 상주해야 했다는 사실.

이 글의 해석으로는, 단일 데몬 수준에서 수 기가바이트에 달하는 라우팅 메타데이터는 대규모 엣지 서버 군집에 수천 번 복제될 때 테라바이트 단위의 유휴 자원 낭비로 직결된다. 원문은 수학적 분석과 데이터 구조 패킹이라는 두 가지 레버를 병행하여 항목당 메모리를 25% 줄이고, 서버당 해시 수를 90% 줄여 전체 100TB 이상의 RAM을 확보했다고 설명한다.

2. 일관 해싱의 기본 원리와 불균형 문제

일반적으로 로드 밸런서가 백엔드 서버 풀에 트래픽을 분산할 때 단순 나머지 연산(Modulo)을 사용하면 서버 추가나 장애 제거 시 대다수 키의 목적지가 변경되는 대규모 리해싱 문제가 발생한다.

원문은 일관 해싱이 서버의 추가나 제거가 발생하더라도 대규모 변경 없이 여러 서버에 작업을 고르게 분산시키는 널리 사용되는 기법이라고 설명한다. 내부적으로 PBR은 URL을 기반으로 캐시 가능한 요청을 서버에 라우팅하여 각 데이터센터마다 파일의 단일 사본만 저장되도록 보장하고, 각 파일의 저장 위치를 안정적으로 찾는 경로를 제공한다.

원문은 일관 해싱의 핵심 개념에 대해 해시 함수가 임의의 입력을 받아 단일 부호 없는 정수(해시 함수에 따라 32비트, 64비트, 128비트)로 제한된 출력을 생성한다는 점에 있다고 설명한다. 대부분의 일관 해싱 설명은 이 출력 공간을 최대값에서 0으로 이어지는 연속적인 원형 링(Ring)으로 표현하지만, 원문은 32비트 정수 범위를 단순한 수직선(Number Line)으로 간주하여 설명한다.

원문에서 설명하는 기본적인 일관 해싱의 배치 메커니즘은 다음과 같다.

  • 서버 집합(A, B, C)의 IP 주소와 작업 집합(t~z)의 캐시 키를 각각 해시하여 32비트 수직선 위에 배치한다.
  • 각 작업의 해시 값에서 왼쪽(또는 한쪽 방향)으로 가장 가까이 위치한 첫 번째 서버를 해당 작업의 목적지로 지정한다.
  • 마지막 구간을 담당하는 서버 C의 범위는 수직선의 끝에서 처음으로 순환 연결(wrap around)되어 링 구조를 형성한다.

그러나 원문은 이 기본 모델에서 곧바로 심각한 한계가 드러난다고 적는다. 해시 값이 본질적으로 무작위 숫자에 가깝기 때문에, 서버 A가 담당하는 구간의 길이가 서버 B나 C보다 비정상적으로 커지는 불균형이 발생한다. 각 서버가 처리하는 요청의 비율은 수직선 상에서 자신이 차지하는 구간의 크기에 비례하므로, 이상적으로는 모든 서버가 동일한 구간 길이를 가져야 하지만 무작위성으로 인해 통계적 편차가 발생하게 된다.

3. 변동계수(CV) 공식과 1차 통계적 분석

원문은 서버에 할당되는 구간 크기의 불확실성을 측정하기 위해 통계학의 두 가지 기본 지표인 기대값(Expected value)과 표준편차(Standard deviation)를 도입한다. 기대값은 분포의 중심 위치를 나타내며, 표준편차는 측정값들이 그 중심점에 얼마나 밀집되어 있는지를 나타낸다.

원문에 따르면, N대의 서버가 존재하고 서버당 1개의 해시(k=1)만 배치되는 가장 단순한 경우, 임의의 한 서버가 차지하는 구간 비율에 대한 기대값과 표준편차 공식은 다음과 같다.

Exp = 1/N

SD = (1/N)√((N-1)/(N+1))

원문은 구체적인 수치 예시로 서버 수 N=100인 경우를 제시한다. 이때 기대값은 Exp = 1/100 = 1%가 되며, 표준편차는 SD = (1/100)√(99/101) ≈ 0.99%가 된다. 원문은 각 서버가 담당할 구간의 길이가 1%를 중심으로 분포하고 대부분의 길이가 기대치에서 1% 오차 범위 내에 들어온다는 서술이 언뜻 양호해 보일 수 있지만, 이는 전체 원주 길이에 대한 0.99%라는 점을 지적한다.

목표 크기 대비 실제 오차의 크기를 올바르게 파악하려면 표준편차를 기대값으로 나눈 상대적 척도인 변동계수(Coefficient of Variation, CV)를 계산해야 한다. 원문이 제시한 변동계수 공식은 다음과 같다.

CV = SD/Exp = √((N-1)/(N+1))

원문에서 N=100을 대입했을 때 도출되는 값과 그 의미는 아래 3가지로 정리된다.

  • N=100일 때 변동계수는 CV ≈ 99%에 달한다.
  • 이는 특정 서버가 기대치의 2배에 달하는 요청(99% 과부하)을 처리할 수 있음을 의미한다.
  • 반대로 다른 서버는 거의 아무런 일도 하지 않는 유휴 상태에 머물 수 있음을 통계적으로 보여준다.

이 글의 해석으로는, 가상 노드가 없는 순수 일관 해싱은 분산 시스템에서 특정 노드의 핫스팟 장애를 유발하기에 충분할 정도로 부하 편차가 크다. 따라서 균등한 트래픽 분배를 달성하기 위해서는 단일 노드를 링 위의 여러 지점에 복제하는 확장이 불가피하다.

4. 해시 점 증설의 함정: 수익 체감

불균형 문제를 해결하기 위해 시스템 엔지니어들이 관행적으로 사용하는 해법은 서버 하나당 여러 개의 해시 점(가상 노드)을 수직선에 추가하는 것이다. 원문은 개별 구간이 큰 표준편차를 갖더라도, 이들을 무작위로 합치면 전체 구간 크기가 평활화된다는 직관이 대수의 법칙(Law of large numbers)에 부합한다고 설명한다.

원문 저자는 모친이 미적분 교사였던 배경을 언급하며 근사치나 점근 한계에 만족하지 않고 서버당 k개의 해시가 배치될 때의 실제 통계 공식을 직접 유도했다고 밝혔다. 유도된 k개 해시의 기대값, 표준편차 및 변동계수 일반식은 다음과 같다.

Exp_k = 1/N

SD_k = √[(k+1)/(N(kN+1)) − 1/N²]

CV_k = SD_k / Exp_k = √((N-1)/(N*k+1))

원문은 NGINX의 업스트림 해시 모듈에서 서버당 기본 해시 수가 160개로 하드코딩되어 있으며, Pingora 역시 기본값으로 동일하게 160개를 채택하고 있다고 설명한다. N=100일 때 서버당 점을 160개 배치하면 변동계수(오차 마진)는 약 99%에서 약 8%로 급격히 감소한다.

그러나 원문은 변동계수 곡선을 플롯했을 때 "해시 점을 무조건 추가하면 된다"는 접근법의 근본적인 한계가 드러난다고 지적한다. 원문이 밝힌 핵심 통찰은 다음과 같다: 「each step down in error margin requires (almost) an order of magnitude increase in the number of hashes per server, so adding more hashes yields less and less improvement」. 즉 오차율을 한 단계 낮추기 위해서는 노드당 해시 수를 거의 자릿수 단위(10배)로 늘려야 한다는 점이다.

원문이 제시한 스케일링의 구체적 문제점 3가지는 다음과 같다.

  • 기본값 k=160에서 서버의 저장 용량에 비례하여 가중치를 부여하면 가중치 인수 w=625일 때 k = 160 × 625 = 100,000개의 해시가 단일 서버에 할당된다.
  • 원문은 차트 분석을 통해 k=10,000에서 k=100,000으로 추가된 마지막 90,000개의 해시가 가져다준 오차 감소 효과가 고작 0.7%에 불과했다고 지적한다.
  • 오차를 미세하게 줄이기 위해 RAM 소모량은 10배로 폭증하는 전형적인 수확 체감 상태에 직면했다는 사실.

이 글의 계산으로는, N=100인 환경에서 공식을 대입했을 때 k=160에서의 변동계수는 √(99 / (100 * 160 + 1)) = √(99 / 16001) ≈ 7.87%이며, 해시 수를 10분의 1인 k=16으로 축소하더라도 변동계수는 √(99 / (100 * 16 + 1)) = √(99 / 1601) ≈ 24.87% 수준으로 계산된다.

5. 32비트 이산 공간과 생일 역설의 충돌 한계

원문은 수학적 공식이 아름다운 예측을 내놓더라도, 그것은 해시 공간이 무한히 쪼개질 수 있는 '연속적인 원형 링'일 때만 성립한다는 근본적인 결함을 폭로한다. 실제 프로덕션 소프트웨어에서 해시 값은 연속 공간이 아니라 32비트 정수 공간에 존재한다.

원문은 해시 점의 개수가 늘어남에 따라 생일 역설(Birthday paradox)에 의해 해시 충돌이 발생할 확률이 빠르게 증가한다고 설명한다. 충돌이 발생하면 일부 해시 기여분이 임의로 탈락하여 예측할 수 없는 무작위 오차가 시스템에 주입된다.

원문에서 분석한 32비트 해시 이산화의 실제 한계 3가지는 다음과 같다.

  • 이상적인 연속 공간에서는 모든 해시 점이 해당 서버의 트래픽 점유율에 온전히 기여하지만, 충돌이 발생하면 중복된 점이 덮어쓰여져 기여분이 소실된다.
  • 2048대의 서버를 보유한 대규모 데이터센터 맥락에서 시뮬레이션을 수행한 결과, 서버당 해시 수가 10,000개에서 100,000개 사이로 증가할 때 오히려 오차율이 증가하는 역전 현상이 관측되었다.
  • 수학 공식 상으로는 해시를 늘릴수록 오차가 감소해야 하지만, 32비트 정수 공간의 이산적 충돌 한계로 인해 과도한 해시 생성이 시스템 정밀도를 오히려 훼손했다는 사실.

원문은 이 역설적 발견이 메모리를 절감하려는 엔지니어링 목표에는 대단히 반가운 소식이었다고 서술한다. 32비트 공간의 충돌 문제로 인해 해시 수를 늘리는 것이 무의미할 뿐 아니라 역효과를 낳는다는 수학적 근거가 확보되었기 때문이다. 이에 따라 Cloudflare 팀은 서버당 생성하던 해시 수를 무려 90% 감축하기로 결정했다.

6. 구조체 최적화: Rust 정렬 제약과 8바이트에서 6바이트로의 패킹

해시 개수를 줄이는 통계적 접근과 더불어, 엔지니어 Zaidoon은 PBR 내부에서 해시 링 항목을 저장하는 메모리 구조체 자체의 낭비를 제거하는 최적화 안을 제시했다.

원문에 따르면, PBR에서 사용되던 기존 해시 포인트 구조체는 다음과 같은 8바이트 구조였다.

struct Point {
    hash: u32,
    index: u32,
}

이 구조체에서 4바이트는 해시 값 자체에 사용되고, 나머지 4바이트는 별도 배열에 저장된 서버를 가리키는 인덱스로 사용된다. Zaidoon의 통찰은 PBR이 단일 프로세스에서 동시에 조율해야 하는 서버 대수가 2^16 ≈ 65k 개를 초과할 가능성이 거의 없으므로, 32비트 정수 대신 16비트 정수(u16)를 사용하는 것으로 충분하다는 점이었다.

그러나 원문은 Rust 언어가 이를 단순하게 허용하지 않는다고 적는다: 「Rust doesn't make it that easy」. `index: u16`으로 단순 변경하더라도 메모리 사용량은 전혀 줄어들지 않는다. Rust의 메모리 정렬(Alignment) 규칙상 구조체의 크기는 가장 큰 필드(가장 정렬 요구가 큰 필드)의 배수여야 하기 때문이다. `hash`가 4바이트이므로 구조체 전체 크기는 4의 배수인 8바이트로 패딩된다.

원문은 구조체 크기를 6바이트로 줄이기 위한 기법과 그 선택 이유를 다음과 같이 설명한다.

  • 컴파일러 지시자인 `#[repr(packed)]`를 사용할 수 있으나, 원문은 「`#[repr(packed)]` is controversial for good reasons」라고 명시하며 미정렬 참조로 인한 위험성을 지적한다.
  • 가장 안전하면서도 동일한 기계어 코드로 컴파일되는 해결책으로 해시와 인덱스를 원시 바이트 배열 `[u8; 6]`으로 저장하고 게터(getter) 메서드를 통해 접근하는 방식을 채택했다.
  • 원시 바이트 배열 구조체를 통해 각 항목당 메모리 크기를 정확히 8바이트에서 6바이트로 줄여 25%의 메모리를 즉시 절감했다.

원문에 수록된 최종 최적화 구조체와 게터 구현 코드는 다음과 같다.

struct Point([u8; 6]);

impl Point {
   fn hash(&self) -> u32 {
	u32::from_ne_bytes(self.0[0..4].try_into().unwrap())
   }

   fn index(&self) -> u16 {
	u16::from_ne_bytes(self.0[4..6].try_into().unwrap())
   }
}

이 글의 해석으로는, 포인트 배열에서 2바이트 패딩을 제거한 것은 메모리 연속 적재 시 불필요한 메모리 낭비를 줄이는 직접적인 효과를 낸다.

표 1: 두 가지 최적화 레버 비교 (구현 최적화 vs 통계 최적화)
구분 최적화 대상 원문 수치 및 변화 핵심 메커니즘 원문 근거 및 이 글의 해석
구현 레버 (Zaidoon) Point 메모리 구조체 레이아웃 항목당 8바이트 → 6바이트 (25% 감소) index를 u16으로 축소 후 [u8; 6] 바이트 배열과 from_ne_bytes 게터 적용 원문 근거: 인덱스를 u16으로 변경 시 2^16 ≈ 65k 대 이하 서버 가정. #[repr(packed)]는 논란이 있어 raw 바이트 배열 선택. / 이 글의 해석으로는: 바이트 변환 코드가 다소 늘어남.

7. 가중치와 다중 링 폭발: 2^(handful) 조합의 메모리 압박

원문은 서버 간 사양이 상이한 환경에서 발생하는 가중치 처리와 다중 해시 링 조합이 메모리 문제를 폭발적으로 가중시켰던 메커니즘을 상세히 기술한다.

Cloudflare 인프라에서는 서버마다 디스크 용량이 상이하므로, 저장 공간이 큰 서버에 더 많은 요청이 할당되도록 Ketama 알고리즘을 사용한다. 원문은 두 서버 S_1, S_2가 있고 S_1이 w배 더 많은 요청을 처리하도록 하려면 S_1의 해시 수 H_1이 w * H_2가 되어야 한다고 설명한다. Pingora 팀은 수년 동안 디스크 공간을 가중치로 사용해 왔으며, 계산 집약적 작업에서는 CPU나 GPU 개수를 가중치로 삼는다.

그러나 문제는 가중치뿐만이 아니었다. 원문이 밝힌 메모리 폭발의 진정한 주범 3가지는 다음과 같다.

  • 모든 서버가 모든 요청을 처리할 수 있다는 전제가 실무에서는 성립하지 않으며, 규정 준수 요건이나 활성화된 캐싱 기능에 따라 특정 서버 서브셋만 요청을 처리할 수 있다.
  • 동일한 링에 해시를 추가하는 방식으로는 기능 조합을 분기할 수 없어, 기능의 조합마다 완전히 새로운 독립된 해시 링을 메모리에 생성해야 했다.
  • 소수의 기능 조합이 지수적으로 증가하여 원문 표현대로 2^(handful) = dozens 개의 개별 일관 해시 링이 PBR 메모리에 중복 상주하면서 최대 6GB의 RAM을 점유했다는 사실.

이 글의 해석으로는, 링의 개수가 수십 개로 곱해지는 환경에서 단일 링의 엔트리 크기와 점 개수를 줄이지 않으면 기능 추가에 따라 메모리 고갈이 가속화될 수밖에 없다.

표 2: 주요 파라미터별 이론상 변동계수(CV)와 원문 수치 비교

8. 캐시 무효화 없는 2차원 점진적 롤아웃 기법

원문은 해시 링의 파라미터를 변경할 때 맞닥뜨리는 가장 위험한 장애 시나리오로 '오리진 서버의 폭발(melting origins)'을 꼽는다. 해시 링을 변경하면 캐시 가능한 요청이 전달되는 백엔드 서버의 위치가 전면 재배치된다. 네트워크 전체에서 해시 링을 한순간에 전면 교체하면 전 세계 캐시가 일시에 무효화되어 오리진 트래픽이 폭증하는 치명적인 장애로 번지게 된다.

원문이 기술한 안전한 마이그레이션 아키텍처는 아래 4가지 제어 요소로 구성되었다.

  • PBR 프로세스 메모리에 기존의 대형 Ketama 링과 새롭게 축소된 소형 링 두 버전을 동시에 적재하여 운용했다는 점.
  • 기존 마이그레이션 프레임워크를 통해 각 요청의 해시를 기반으로 백엔드를 선택하여 롤아웃 결정이 요청 단위로 결정론적이고 안정적으로 유지되도록 했다는 점.
  • 이상이 감지될 경우 PBR 바이너리를 재배포할 필요 없이 새로운 요청을 즉시 구형 링으로 되돌리는 깨끗한 롤백 경로를 확보했다는 점.
  • 단순한 글로벌 백분율 방식 대신 트래픽의 비율과 이동 허용 데이터센터라는 두 가지 차원(two dimensions)을 독립적으로 통제하여 폭발 반경(Blast radius)을 엄격히 제한했다는 점.

마이그레이션 과정에서 Cloudflare 엔지니어들은 백엔드 선택 추적, 링 버전 카운터, PBR 연결 오류율, 프로세스 메모리, 프로세스 시작 시간, 캐시 적중 동작, 오리진 트래픽 추이를 면밀히 모니터링했다. 롤아웃이 소규모 검증 지역에서 대규모 데이터센터 그룹을 거쳐 100%에 도달한 후 임시 구형 링 경로를 영구 폐기했다. 그 결과 PBR의 메모리 사용량이 급격히 하강하며 글로벌 100TB 이상의 RAM이 온전히 회수되었다.

9. pingora-ketama 크레이트 v2의 변경점과 시사점

원문은 블로그에 기술된 모든 개선 사항이 오픈소스 `pingora-ketama` 크레이트에 현재 화물 기능(Cargo feature) 형태로 공개되어 사용 가능하다고 안내한다. 다만 현재 시점에서는 공식적으로 대대적인 광고를 하지 않은(unadvertised) 상태의 플래그로 제공된다고 적는다.

원문에서 공개한 pingora-ketama 라이브러리의 두 가지 링 버전 특성은 다음과 같다.

  • `v2` 링: 6바이트 바이트 배열을 사용한 압축 저장 포맷, 더 빠른 정렬 메서드, 그리고 노드당 기본 해시 수를 조절할 수 있는 확장 기능을 제공한다.
  • `v1` 링: pingora-ketama가 전통적으로 사용해 온 레거시 동작과 완전히 동일한 구현을 유지한다.
  • 두 링을 단일 라이브러리 내에서 동시에 실행할 수 있으며, 요청별 조건에 따라 링을 동적으로 선택할 수 있는 유연성을 제공한다.

원문 작성자는 글의 결론에서 독자들에게 단순히 일관 해싱 알고리즘을 복사해 적용하는 것을 넘어, 기존 시스템에서 '단순'하거나 '당연'하다고 여겨졌던 설계 결정들을 숫자를 통해 직접 재검토하라는 교훈을 전한다. 모든 시스템 문제를 Rust 언어만으로 해결할 수는 없지만, 통계 수학은 어떤 시스템에서도 보편적으로 적용 가능한 최적화의 강력한 도구라는 점을 강조한다.

10. 확인하지 못한 것

원문에 나오지 않은 항목은 다음과 같다.

  • pingora-ketama 크레이트에 v2 기능이 통합된 정확한 크레이트 버전 번호는 원문 텍스트에 기재되어 있지 않아 확인하지 못했다.
  • v2 링에서 언급된 '더 빠른 정렬 메서드(a faster sorting method)'의 구체적인 내부 알고리즘 명칭이나 코드 구현체는 원문에서 설명하지 않아 파악하지 못했다.
  • 100TB RAM 회수를 통해 Cloudflare가 절감한 구체적인 연간 하드웨어 구매 비용이나 전력 비용의 금전적 액수는 원문에 명시되지 않았다.
