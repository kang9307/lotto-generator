Git History Commands That Deserve More Love - A Practical Guide to Pickaxe, log -L, Bisect, and Reflog

Digging into individual commits with log -S/-G, log -L, blame --ignore-rev, bisect, and reflog - when and how to actually use them

Jul 16, 2026 Dev & Infra

Intro: Why We Only Ever Use log and blame

For most developers, "looking at git history" begins and ends with skimming commit messages via git log, or checking who wrote a line with git blame. But git hides a far more precise toolbox behind those two commands. There is pickaxe (-S/-G) for finding exactly when a string disappeared from the codebase, -L for pulling out the evolution of a single function, bisect for binary-searching the exact commit that introduced a bug, and reflog for resurrecting commits you thought you had lost for good.

This is not a dictionary that lists these commands one by one - it is a practical guide organized around "use this when..." scenarios. The syntax here has been cross-checked against official docs and real-world usage (current as of git in July 2026), and I have tried to flag the gotchas of each command along the way.

1. Sharper git log Options - Narrowing the Timeline with Graphs and Filters

Before reaching for the heavier tools, plain git log already gets much more powerful once you combine a few options. To see a history with multiple branches tangled together at a glance, a graph option is essential.

git log --oneline --graph --all --decorate

This combination shows every branch (--all) as a graph (--graph), labeled with branch and tag names (--decorate), one line per commit (--oneline). Stack search filters on top and you can narrow the range dramatically.

git log --author="Kim" --since="2026-06-01" --until="2026-07-01" --grep="fix"

Filtering by author, date range, and a keyword in the commit message all at once answers a specific question like "the bug-fix commits Kim made last month" directly. Just this much already breaks the habit of scrolling a raw log with your eyes.

2. git log -S / -G (Pickaxe) - "When Did This String Disappear?"

pickaxe searches the actual code changes (the diff), not the commit message. It directly answers questions like "who removed this API key string, and when" or "when was this function call added".

2.1 -S: Tracking a Change in Occurrence Count

-S targets a literal string and only surfaces commits where the number of times that string appears in the diff (adds minus deletes) changed. It is case-sensitive and not a regex by default.

git log -S'API_SECRET_KEY' --oneline -- src/

Add --pickaxe-regex if you want regex matching with -S, and --pickaxe-all if you want to see every file changed in a matching commit, not just the files where the match occurred.

2.2 -G: Tracking Every Line That Was Touched, via Regex

-G'regex', available since git 1.7.4, catches any commit where a line matching the pattern shows up anywhere in the diff. Unlike -S, even if the total occurrence count stays the same, -G will still catch it if that line was moved or lightly edited.

git log -G'function\s+parseConfig' --oneline

2.3 The Practical Difference - When Code Just Moves

Say a config value only changes position within a file and the total occurrence count stays identical - -S will not find that commit, since there was no count change. -G, on the other hand, catches it as long as a diff hunk containing that line exists. In short, -S tracks "did it appear or vanish", while -G tracks "was this line touched at all". When you're hunting for a removed feature, start with -S, and widen to -G if -S comes up empty.

3. git log -L - The Evolution of a Specific Function or Line Range

If blame answers "who last changed this line right now", -L answers "how has this line (or function) changed over time" - shown as a sequence of diffs in chronological order.

3.1 Specifying a Line Range

git log -L 120,150:src/parser.c

This prints how lines 120 through 150 of the file changed in each commit, in order. Git automatically tracks that block of lines as it walks backward and adjusts the range as needed.

3.2 Specifying a Function

git log -L :parseConfig:src/parser.c

The :funcname:file syntax treats the function name as a regex to locate its start, then uses a language-specific userdiff driver (built-in support for C, Python, Java, and more) to determine where the function ends. If git cannot detect the function boundaries automatically, you can specify the start and end lines with regexes directly.

git log -L '/^int parseConfig/',/^}/:src/parser.c

There is no more direct tool for tracing why a function ended up looking the way it does today. Watching small changes accumulate across many commits, in diff order, surfaces design intent or workarounds that a code review alone would never reveal.

4. Using git blame Properly - Ignoring Formatting Commits

Plain git blame <file> is powerful, but has a major trap: if a mass reformatting or find-and-replace commit sits in the history, blame will keep pointing to that noisy commit instead of the line's real author.

4.1 Skipping a Specific Commit with --ignore-rev

git blame --ignore-rev a1b2c3d4 src/app.js

Available since git 2.23, lines touched only by the ignored commit get attributed to the last revision before it that actually changed them. To ignore multiple commits, repeat the flag or manage them via a file.

4.2 Managing Them with a .git-blame-ignore-revs File

# .git-blame-ignore-revs
# Full repo reformat in May 2026 (prettier applied)
a1b2c3d4e5f6...

git blame --ignore-revs-file .git-blame-ignore-revs src/app.js

Name the file .git-blame-ignore-revs by convention and GitHub will automatically pick it up and apply it in the web blame view too. If passing the flag every time is annoying, register it once in your repo config.

git config blame.ignoreRevsFile .git-blame-ignore-revs

5. git bisect - Binary-Searching for the Commit That Introduced a Bug

When something worked fine a while ago and does not work now, checking out commits one by one and eyeballing them is a waste of time. bisect narrows the range between a known-good and known-bad commit through binary search, pinning down the exact culprit.

5.1 Manual Bisecting

git bisect start
git bisect bad                 # the current HEAD has the bug
git bisect good v1.2.0         # this tag was known to work

Git then automatically checks out the midpoint commit. Test at that point yourself, and answer with git bisect good or git bisect bad as needed - after log(N) rounds, git zeroes in on the exact culprit commit.

5.2 Fully Automating It with git bisect run

If the test itself can be scripted, you can automate the whole process. The script must report the result through its exit code: 0 = good, any value from 1 to 127 except 125 = bad, 125 = this commit cannot be tested at all (skip).

git bisect start HEAD v1.2.0
git bisect run npm test

Or wire up a custom script.

#!/bin/bash
# check.sh - build, then verify a specific response
npm run build || exit 125   # if the build itself fails, skip
curl -sf http://localhost:3000/health | grep -q '"ok":true' && exit 0 || exit 1

Running git bisect run ./check.sh lets git bisect the range and rerun the script automatically, no human intervention required, until it finds the culprit commit. Finish with git bisect reset to return to your original branch.

6. git reflog - Recovering a Commit You Thought Was Gone

When you accidentally run git reset --hard with the wrong target, or a commit seems to vanish mid-rebase, reflog is the rescue tool. Reflog is not the commit graph itself - it is a local record of every position HEAD and your branches pointed to over time.

git reflog
# or
git reflog show HEAD

Each entry is numbered like HEAD@{0}, HEAD@{1}, and records what action happened at that point (commit, checkout, reset, rebase, and so on). Once you find the entry you want, inspect it first with git show <hash> or git checkout <hash>, and only then reset once you are confident.

git reset --hard HEAD@{2}

But reflog is not forever. Entries still reachable from a branch expire after 90 days by default (gc.reflogExpire), and entries unreachable from anywhere expire after 30 days (gc.reflogExpireUnreachable) - once git gc runs past those windows, they are pruned. Checking as soon as possible after an accident is the safer habit.

7. git log --follow - Stitching Together a Renamed File's History

Move or rename a file, and git log <path> only shows commits after the rename. Add --follow and it stitches the history together through the rename, back to the original file (it only works on a single file at a time).

git log --follow -p -- src/utils/format.js

Add -p and you also see the actual diff of what changed in each commit. If you want to tune how aggressively renames are detected, pair it with -M (or --find-renames).

A similar idea applies when you need to recover a deleted file or a chunk of deleted code. First find the commit that deleted it,

git log --diff-filter=D --oneline -- src/legacy/old_parser.js

then restore the file from the parent revision of that deletion commit.

git checkout <deleting-commit>^ -- src/legacy/old_parser.js

8. git rev-list / git shortlog - Scripting and Statistics

Unlike the human-readable log, rev-list is a low-level plumbing command that just lists commit hashes, which makes it ideal for scripts. shortlog aggregates commits per author for quick statistics.

git rev-list --count HEAD                 # total commit count
git rev-list --count v1.0.0..v2.0.0        # commits between two tags
git rev-list --count --since=yesterday HEAD

git shortlog -sn --no-merges              # commits per author, merges excluded
git shortlog -sn --all                    # across all branches

When a CI script needs "how many commits went into this release" or "who committed the most during this period", these two commands are far lighter to run and easier to parse than scraping log output.

9. Choosing a Command by Scenario

In practice, it is faster to start from "what do I actually want to know right now" rather than the command name. Here is a quick lookup table.

What you want to knowCommand to use
Exactly when this bug was introducedgit bisect (automate with run)
Why this code ended up looking the way it doesgit log -L :func:file
Who last changed this line (ignoring formatting commits)git blame --ignore-revs-file
Where a deleted string or config value wentgit log -S (widen to -G if needed)
Recovering a commit you accidentally deletedgit reflog + reset --hard
The past history of a renamed filegit log --follow
Commit counts for release notes or CI scriptsgit rev-list --count, git shortlog -sn

10. A Related Note - Rewriting History Is Evolving Too

This piece has focused on commands for exploring history, but recent git releases (2.54-2.55) also added new experimental commands for rewriting it. git history reword, git history split, and git history fixup let you edit an old commit's message, split one commit into two, or fold staged changes into an old commit - automatically rebasing every branch descended from it. It is essentially a safer wrapper around the most common rebase -i patterns, though it still cannot handle merge commits and other edge cases, so treat production adoption cautiously for now. Worth remembering as the counterpart to the "reading" commands covered in this guide.

Conclusion: The Tools Already Exist, Only the Habit Is Missing

None of the commands covered here are new. -S has existed since git's early days, --ignore-rev is the relatively recent one (2.23), and everything else has been around for a long time. The problem was never a lack of tooling - it was never stepping outside log and blame in the first place. The next time you wonder "when did this bug get introduced", reach for bisect instead of checking out commits one by one; when you wonder "where did this string go", reach for log -S instead of grepping every file by hand. Build the habit of checking reflog before panicking over a commit you think you lost, and the time you spend digging through history will drop noticeably.
