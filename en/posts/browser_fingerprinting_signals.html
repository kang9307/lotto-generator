Why You Are Still the Same Person After Clearing Cookies

Not storage but recognition — how screen, fonts, canvas and audio drift between devices, and why none of it can be fully blocked

Aug 21, 2026 IT/Tech

Introduction: tracking with nothing to delete

You cleared everything. Cookies, site data, cache. You reopened the site in a private window and did not sign in. And there it is again on the front page: the product you glanced at three days ago. On another site, creating a fresh account triggers a message about an existing device and a request for extra verification.

The usual reaction is that something must still be left over, so you clear more. The result does not change. Nothing is left over, and that is exactly the point. No planted marker was found. The browser simply answered a set of questions the same way it did last time, and that was enough.

This piece takes that judgement apart signal by signal: why screen, fonts, drawing results and audio computations drift slightly between devices, how that drift becomes identifying information, and what browsers and standards do and do not manage to prevent. How to build any of it is out of scope.

1. Storing and recognizing are two different operations

A cookie has a simple shape. The server hands over a value, the browser keeps it, and the browser attaches it to the next request. Because the value exists, it can be inspected, and because it can be inspected, it can be deleted. There is a delete button in every browser and regulation arrived comparatively early for exactly one reason: the target is a visible object. If the mechanics of cookies themselves are what you are after, there is a separate piece on which requests drop your cookie under each SameSite value.

Fingerprinting creates no object. It collects values that already surface during ordinary page rendering and compresses them into a single string. That string lives on the server, not on your device. There is nothing on your side to erase.

The W3C guidance written for specification authors defines the capability as identifying or re-identifying a visiting user, user agent or device via configuration settings or other observable characteristics. The word re-identifying matters. Recognizing someone for the first time is less commercially interesting than restitching a connection that was deliberately cut.

The same document splits the capability four ways, and that split is where defensive design actually diverges.

  • Passive — observable from the request alone. Header composition and ordering, and lower level network characteristics, belong here. It works without any code running on the page, and there is no way to observe from outside that it is happening.
  • Active — requires script or styling to ask the browser something: window size, available fonts, sensor values. Because code runs, detection is at least conceivable.
  • Transient event correlation — no stored value at all. Near-simultaneous hardware or environmental events seen from different origins are matched up to infer that they belong to one device.
  • Cookie-like — state is written somewhere and read back later. Only the name differs from a cookie; the nature is storage, which means deletion still severs it.

For a user, the passive category is the awkward one. There is no switch inside the browser and no reliable way to tell which sites rely on it. Defenses work best against the active category, precisely because a question has to be asked before an answer exists — which leaves room to reshape the answer or refuse the question.

2. Which signals get used

Grouped by character, the commonly discussed material looks like this, with the reason each one varies between machines.

SignalWhat becomes visibleWhy it differs between devices
Screen and windowResolution, color depth, scaling factor, usable area once a taskbar or dock is subtractedMonitor combinations and OS scaling settings vary widely, and once taskbar position and size feed in, the number of distinct values grows sharply
Font inventoryWhich typefaces are installed and therefore available for renderingOn top of the OS base set, office suites, design tools, games and language packs each add a different bundle. Installation history becomes the combination
Canvas drawing resultThe pixels produced when the same string and shapes are drawnDifferent graphics devices, drivers, antialiasing methods and font rasterizers shift edge pixels by a step or two

Common values, rare combinations

A frequent objection lands here: my resolution is the most common one there is, so how does it single me out? The premise is right and the conclusion is wrong. Identification does not come from one field, it comes from multiplying fields together.

Suppose a quarter of all users share the most common resolution. Layer time zone and language ordering on top, then the font combination, then the graphics device string, and the surviving population collapses fast. Information theory calls the per-field splitting power entropy; in practice the surviving crowd is called your anonymity set. The goal of defense is not to erase your values but to keep the set you belong to large.

This framing matters because it decides a conclusion later in the piece. Tools that randomize values do not enlarge an anonymity set. They can manufacture a combination that exists nowhere else on earth.

3. Why devices drift at all

Go one layer beneath the table and the drift originates in three distinct places.

  • Hardware — different execution unit layouts and orderings change the last digits of floating point results. The same expression yielding different values depending on summation order is normal floating point behavior, not a defect.
  • System software — graphics drivers, font rasterizers and audio stacks each carry versions and each optimize on their own terms. Identical browsers on top of different stacks produce different output.
  • Configuration — display scaling, language ordering, accessibility options, color scheme preference. This layer is where people have often made themselves unusual on purpose.

So why do standards leave this in place? Most web specifications require results to look the same, not to be bit-for-bit identical. Requiring the latter would mean abandoning hardware acceleration or forcing every implementation onto a single rendering and arithmetic path, which trades away performance and portability wholesale. The permitted tolerance is what becomes identifying information — that is the structural nature of the problem.

Which is why this is less a story about someone shipping a bad API and more the bill for allowing fast, diverse implementations. Fixing it means giving up either performance or capability. Every browser defense examined below ends in a compromise for that reason.

4. What an audio signal actually measures

Audio-based signals invite a misreading because of the name. Nothing is being listened to. No permission prompt appears.

The structure matches the canvas case. Feed a known input, run a known process, read the numbers that come out. Push a harmonically rich waveform such as a sawtooth through a processing path and an array falls out the other end. In theory that array should be identical everywhere. In practice it splits somewhere below the decimal point, for the three-layer reasons above: rounding points, vectorization, resampler implementation, and the sample rate the system settled on.

One fact deserves emphasis. The Web Audio specification defines a rendering mode that computes without routing to a real output device. It describes the ordinary context as an audio graph whose destination node is routed to a real-time output device, while offline rendering processes without that device output. So a value appears with no speakers attached, with the system muted, with the earbuds pulled out.

The specification is not blind to this. The option controlling render quantum size carries a note to the effect that it exposes information about the host and can be used for fingerprinting, and there are dedicated privacy and security consideration sections. This is not a hidden vulnerability; it is a documented tradeoff left standing in the open.

5. How a silent computation can hold a device open

The distinction between those two modes is where a real side effect enters.

If the intent is only to compute, offline rendering is available. But it is equally possible to create a real-time context, connect it all the way to the destination, and simply set the final gain to zero. To a human ear nothing plays. To the browser, the output path is alive. The specification states that once created, a context will continue to play sound until it has no more sound to play or the page goes away, and explains that releasing some of its resources requires explicit suspension.

Bluetooth is where the difference shows. A multipoint headset connected to two devices decides handover based on which side is actually delivering audio. If the host keeps a stream alive it looks in use, and the natural switch to a phone does not happen. A tab mute button may not help either, because it generally operates on media elements within the page. With no media element and only a live graph, there is nothing for it to catch.

In August 2026 a personal blog reported that with one large shopping site left open, a Bluetooth headset would not hand over to a phone. The author attributed this to scripts on the page maintaining a silent audio graph, and further reported that the same scripts were collecting drawing results, graphics device information, screen dimensions and device class values.

How far this case should be taken as fact. The above is an observation and analysis published by a third party. No explanation from the site in question has been confirmed, and why the arrangement exists — design or side effect — is not knowable from outside. What this article treats as established goes only as far as the Web Audio specification making such a structure possible in principle.

Generalized, it comes to this. A feature with nothing on screen can still hold a system resource. That is a property of real-time media APIs broadly rather than of fingerprinting specifically, and unlike camera or microphone, audio output has no permission prompt and no indicator light. The real weight of the issue is that a user has almost no channel through which to notice.

6. The other side of the same technique — fraud and bot defense

Read only this far and the technology looks like it exists solely for tracking. It does not. Its widest deployment sits around payments and logins.

UseWhat it judgesWhat the user gainsWhere it becomes a problem
Payment fraud detectionWhether a stolen card is being used from an unfamiliar device configurationFewer charges that go through without the owner knowingA legitimate user who changed devices gets blocked as a false positive
Account takeover defenseWhether a login comes from a device never seen beforeNew device alerts and step-up verification slow down a takeoverThe genuine owner who reset a browser is also treated as new
Automation and scraping controlWhether traces differ from a browser a human drivesLess inventory hoarding and fewer ticket macrosSomeone with hardened privacy settings gets mistaken for a bot
Abuse suppressionWhether one device cycles accounts to claim a benefit repeatedlyOne-per-person offers actually stay one per personA shared family device gets collapsed into a single identity
Cross-site ad profilesWhether people seen on different sites are the same personNo clear gain on the user sideThe classic place where purpose creeps and retention lengthens

Read the table across and something surfaces. The technique is identical throughout; what differs is purpose, retention and sharing. One value feeds a risk decision and a profile alike. Which is why a rule shaped as ban fingerprinting does not survive contact with practice. Ban the technique and payment security goes with it; ban the purpose and there is no reliable way to verify from outside.

Users meet a paradox here too. The harder you defend, the more you look like a bot. Hiding values or assembling an uncommon configuration pushes the risk score up, and the result is more captchas and one more blocked payment. That is not unfairness so much as risk models doing what risk models do. What breaks as you turn blocking up is covered separately in the piece on the price of each strictness step.

7. What browsers actually do about it

Browsers reach for roughly four instruments, each with a different character.

  • Standardization — make everyone answer identically in the same situation. This is the first direction W3C guidance recommends to specification authors, because a uniform answer drives that field's entropy toward zero.
  • Entropy reduction — clamp precision, collapse a continuous value into a handful of buckets, or reduce it to a yes or no. Function survives, discriminating power drops.
  • List-based blocking — block known fingerprinting scripts by name. Reliable, and blind to anything not on the list.
  • Value normalization — answer certain fields with an unremarkable value. Which fields get touched is exactly where the compatibility bill lands.
  • Storage partitioning — separate storage per site. It works well against the cookie-like category and has no direct effect on active signals that never touch storage.

A shipped example shows the shape of the compromise. Mozilla describes Firefox fingerprinting protections as limiting graphics hardware details, font information on the device, processor core count, touchscreen finger support, dock and taskbar dimensions and mathematical performance differences, and states that the share of users appearing unique is cut by almost half. In the same breath it records the limit: more aggressive blocking is guaranteed to break legitimate website features. Values needed by real functionality, such as time zone for calendars, are deliberately preserved.

One direction is worth stating flatly. Standardization beats randomization. W3C guidance recommends standardizing specifications so that conformant browsers form larger anonymity sets. Answering differently every time is itself unusual behavior, so it draws attention while also destabilizing site functionality.

And W3C does not soften the conclusion. It states that complete elimination of browser fingerprinting by a determined adversary through solely technical means that are widely deployed is implausible. In its place it lists four achievable goals: a decreased surface, increased anonymity sets, detectability, and clearable state.

8. What a user can do, and where it stops

Starting from the premise that complete blocking is off the table, this is what remains.

MeasureWhat it actually doesCost and limit
Built-in protection modeBlocks known scripts and normalizes selected fieldsSome fields are left intact by design, and strict modes break some sites
Private windowDiscards stored state when the session endsThe signals are unchanged. It only addresses the cookie-like category
Tracking blocker extensionCuts requests to known collection endpointsAn unusual extension combination can become a signal in its own right
Value spoofing toolsAnswers certain fields with fabricated valuesDoes not enlarge an anonymity set, and inconsistent combinations are easier to single out
VPN or proxyChanges the network addressCovers part of the passive category only. No effect on active signals
Keeping browser and OS currentPicks up newly shipped mitigations automaticallyLowest cost measure available, with gradual effect
Keeping the setup unremarkableStays inside a configuration with a large anonymity setSometimes means giving up preferences and accessibility settings

The first move is to change the objective. Becoming invisible is not an available goal. Blending in is, and the road there generally runs through touching less. Turning on built-in protection and not deferring updates tends to serve an anonymity set better than stacking tools on top of each other.

How much your own browser stands out can be checked directly with a public diagnostic. The Electronic Frontier Foundation runs Cover Your Tracks, which MDN also points to as a reference. That said, no tool guarantees an outcome, and nothing here should be read as saying that a particular extension or browser makes you safe.

9. How the rules treat this

Disclaimer — this section is a general explanation drawn from public documents and is not legal advice. Outcomes in a specific matter depend on jurisdiction and facts, so professional review is worth seeking where it matters.

The European discussion started comparatively early. An opinion issued by the Article 29 Working Party in November 2014 argued that reading a value without storing it can still amount to accessing information on terminal equipment, so the consent requirement that applies to cookies may apply as well. Its core move was to reject explicitly the claim that nothing was stored and therefore nothing applies. The European Data Protection Board later reorganized the technical scope of Article 5(3) of the ePrivacy Directive in Guidelines 2/2023, with the final version adopted in October 2024.

Other jurisdictions start elsewhere. Korea, for instance, defines personal information in Article 2(1) of its Personal Information Protection Act as information about a living individual that identifies them, and also information that cannot identify anyone on its own but can identify a person when easily combined with other information, with ease of combination judged by reasonably considering the availability of that other information and the time, cost and technology required.

Under that structure, whether a browser fingerprint counts as personal information is not a question with one uniform answer. The value alone tells you nothing about who someone is, but the character of combinability changes when the same operator also holds account, payment and order history. The judgement comes from where the value sits, not from the value itself. That is why this article stops short of a verdict. Readers wanting more on the user-side privacy debate may find the piece on the European message scanning legislation useful.

10. Where web standards are heading

The standards-side response is not remove the bad APIs so much as calculate how much a new API leaks before shipping it. Distilling what W3C guidance asks of specification authors:

  • Do not increase the passive surface — it cannot be detected or avoided, which makes it the most expensive kind
  • Narrow exposure to what the feature functionally requires
  • Grow anonymity sets through standardization rather than randomization
  • Reduce entropy by clamping precision, enumerating options or reducing to booleans
  • Require an explicit server opt-in before values are sent, so the behavior is detectable
  • Align the clearing points of storage mechanisms so that state can genuinely be deleted
  • Avoid permanent identifiers that survive cookie clearing
  • Write the added surface into the design document when proposing a feature — it is treated as a concern for every stage of specification development

The tension is not going anywhere. APIs that report hardware details for performance, user settings for accessibility and codec support for media quality will keep arriving, and each time the same scale is set up again. This is not the kind of problem that gets solved; it is the kind that gets managed.

A usable standard for practitioners falls out of that. When adding a feature, write one line about what else it now leaks, and hold real-time resources only while they are needed, releasing them explicitly when done. The lesson from the audio case above is not a spectacular vulnerability but this ordinary piece of hygiene.

What could not be confirmed

Everything this article deliberately stops short of asserting, collected in one place.

  • Whether the behavior in the shopping site case was intentional or a side effect — no explanation from the operator has been confirmed
  • How long collected values are retained server-side and whether they are joined to other services — not observable from outside the client
  • The range of browser, OS and headset combinations in which the phenomenon reproduces — no independent write-up establishing reproduction conditions was located
  • Independent third party measurements of each browser defense — the near-half reduction cited above is the browser vendor's own description
  • Any settled determination treating a browser fingerprint as personal information in a specific jurisdiction — not confirmed

Conclusion: the axes worth keeping

Three of them survive the walkthrough.

First, is there a marker that can be deleted or not. That single distinction separates cookies from fingerprinting and defines the range of measures available to a user. It is also why a private window helps less than people expect.

Second, judge purpose, retention and sharing rather than the technique. Blocking a stolen card and accumulating an ad profile draw on the same material. Collapsing both into one word makes it impossible to handle either well.

Third, the goal is blending in, not disappearing. Standardization beats randomization, and built-in protection kept current usually beats a stack of tools. Anything promising complete blocking is worth pausing over at exactly that sentence.

For developers there is one more line. A feature invisible on screen is not therefore free. Real-time resources that were taken have to be given back.
