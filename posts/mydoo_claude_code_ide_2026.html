myDoo — Claude Code를 기본 LLM으로 삼는 AI 네이티브 IDE

터미널 기반 에이전트와 GUI IDE의 결합이 개발 경험을 어떻게 바꾸는가 — Cursor·Windsurf·Kiro와의 차별점과 AI 네이티브 IDE 흐름 분석

2026-06-23 IT/기술

서론: 에이전트를 편집기 안으로 끌어들이는 시도

2026년 6월 기준, AI 코딩 도구 시장은 크게 두 축으로 나뉜다. 하나는 Cursor·Windsurf처럼 VS Code 포크 위에 자체 AI 레이어를 얹은 AI 보강 편집기이고, 다른 하나는 Claude Code·OpenCode처럼 터미널에서 코드베이스를 자율적으로 다루는 CLI 에이전트다. 이 둘은 각자의 방식으로 개발 경험을 바꿔 왔지만, 본질적으로 별개의 세계였다. 에이전트를 쓰려면 터미널을 열어야 했고, 편집기를 쓰려면 에이전트의 컨텍스트 밖으로 나가야 했다.

개발자 이근영이 GeekNews(hada.io)에 공개한 myDoo는 이 간극을 메우려는 시도다. "Claude Code의 영민함과 IDE의 편리함을 VS Code 기반으로 새로운 환경으로 구현했다"는 한 문장이 핵심을 요약한다. Claude Code를 외부 터미널 도구가 아니라 편집기의 1급 시민으로 올려놓겠다는 선언이다.

이 글은 myDoo를 단순 소개하지 않는다. myDoo가 시도하는 통합이 왜 의미 있는지, 기존 도구들과 무엇이 다른지, 그리고 이 방향이 AI 네이티브 IDE라는 더 큰 흐름에서 어떤 위치인지를 본인의 관점으로 분석한다. 공개된 정보가 제한적이므로 확인된 사실과 추론을 명확히 구분해 서술한다.

1. myDoo란 — Claude Code를 IDE의 핵심으로

myDoo는 VS Code 기반 편집기에 Claude Code를 기본 LLM으로 통합한 AI 네이티브 IDE다. 개인 개발자 이근영이 만들어 GeekNews에 공개했으며, 2026년 6월 현재 커뮤니티에서 주목받고 있다.

1.1 핵심 개념: 1급 시민으로서의 에이전트

이 도구의 핵심 아이디어는 "플러그인"이 아니라 "엔진"이다. 기존 Claude Code VS Code 확장은 편집기 옆에 Claude Code를 붙이는 방식이다. 에이전트가 터미널에서 독립적으로 동작하고, 편집기는 그 결과를 보여주는 뷰어에 가깝다. 반면 myDoo가 지향하는 것은 Claude Code가 편집기 자체의 인지 레이어가 되는 구조다. 파일 열기, 탐색, 수정, 실행, 리뷰가 모두 에이전트와 공유된 단일 컨텍스트 위에서 이뤄지는 것이다.

이는 작은 차이처럼 보이지만 개발 흐름에서는 결정적이다. 에이전트가 "지금 편집기에서 열린 파일"을 자동으로 안다면, 개발자가 매번 컨텍스트를 복사해 붙여넣을 필요가 없다. 에이전트가 diff를 만들면 편집기가 곧장 그것을 인라인으로 보여주고, 개발자는 컨텍스트 전환 없이 검토하고 수락한다.

1.2 LLM 선택의 의미

myDoo가 Claude Code를 기본 LLM으로 선택한 것은 전략적 판단이다. 2026년 6월 기준, Claude Code는 전문 개발자 설문에서 주 도구 선택 비율 28%로 1위를 차지한다(Cursor 24%). Anthropic이 지속적으로 에이전트 능력을 개선하고 있고, MCP(Model Context Protocol) 생태계가 활성화되면서 Claude Code의 도구 통합 폭도 빠르게 넓어졌다. 이 성숙한 에이전트를 자체 LLM 개발 없이 활용하는 것은 소규모 프로젝트로서 합리적인 선택이다.

단, 이 선택은 의존성을 낳는다. Claude API 비용 구조, Anthropic의 정책 변화, 그리고 오프라인 환경에서의 제약이 그것이다. LLM 레이어를 위탁함으로써 얻는 속도와 잃는 자율성의 맞교환을 직시해야 한다.

2. 터미널 에이전트와 GUI IDE의 결합 — 무엇이 달라지나

이 통합이 개발 경험에서 구체적으로 무엇을 바꾸는지 짚어 보자.

2.1 컨텍스트 전환 비용의 제거

현재 Claude Code를 VS Code와 함께 쓰는 가장 일반적인 방식은 분리된 두 창이다. 한쪽엔 코드, 다른 쪽엔 터미널에서 돌아가는 에이전트. 개발자는 에이전트에게 파일 경로를 알려주거나, 에러를 복사하거나, diff를 확인하기 위해 끊임없이 두 세계를 오간다. 이 컨텍스트 전환 비용은 단순한 불편 이상이다. 흐름 상태(flow state)를 끊고, 에이전트에게 넘겨야 할 컨텍스트를 수동으로 구성하는 인지 부하를 만들며, 에러의 여지를 늘린다.

myDoo가 제대로 구현된다면, 에이전트는 이미 편집기가 보고 있는 것을 안다. 열린 파일, 커서 위치, 최근 수정 내역, 진단 오류가 에이전트의 컨텍스트에 자동으로 반영된다. 개발자는 묻고 싶은 것을 그 자리에서 물으면 된다.

2.2 diff 검토와 승인 흐름의 통합

에이전트가 코드를 수정할 때 가장 중요한 순간은 개발자가 그 변경을 검토하는 순간이다. 터미널 기반 에이전트는 diff를 텍스트로 출력하거나 별도 도구로 넘긴다. GUI IDE에 통합된 에이전트는 인라인 diff를 편집기 안에 직접 보여주고, 파일별·라인별로 수락·거절·수정하는 UI를 제공할 수 있다. 이것이 "에이전트를 편집기에 통합하는 것"의 가장 구체적인 가치다. 코드 소유권이 에이전트에서 개발자에게 넘어오는 순간을 최대한 마찰 없이 만들어야 에이전트 기반 워크플로가 실무에 정착한다.

2.3 세션 관리와 멀티 에이전트 가능성

Claude Code Desktop 앱이 보여주듯, 에이전트를 GUI로 감쌀 때 얻는 또 다른 이점은 세션 관리다. 여러 작업을 병렬로 에이전트에 위임하고, 각 세션의 상태를 시각적으로 추적하며, 완료된 작업을 검토 큐에 넣는 워크플로는 터미널만으로는 다루기 어렵다. myDoo가 이 방향으로 나아간다면, 단일 에이전트 세션을 넘어 개발자가 여러 에이전트를 동시에 감독하는 "에이전트 오케스트레이터"로 발전할 수 있다.

3. Cursor·Windsurf·Kiro와의 차별점

myDoo의 포지셔닝을 이해하려면 경쟁 도구들과 정직하게 비교해야 한다.

3.1 Cursor — VS Code 포크의 최강자

Cursor는 2026년 기준 AI IDE 시장의 가장 완성된 제품이다. VS Code를 포크해 자체 AI 레이어를 얹었고, 탭 예측 완성(Tab Predictive Completion)은 단순 자동완성을 넘어 다음 코드 블록 전체를 예측한다. 컨텍스트 인식도 높고, 에디터 통합도 깊다. 그러나 Cursor는 자체 AI 레이어를 유지한다. Claude를 쓸 수 있지만 Claude Code의 에이전트 구조를 그대로 가져오지는 않는다. myDoo와의 차이는 "Claude Code의 에이전트 루프 자체를 IDE에 통합하느냐"의 여부다.

3.2 Windsurf — 자율성을 강조한 Cascade 에이전트

Windsurf의 핵심은 Cascade 에이전트다. 멀티 파일 자율 수정에서 강점을 보이며, "에이전트에게 통째로 위임"하는 워크플로를 선호하는 개발자에게 어필한다. Codeium이 Windsurf를 Devin Desktop으로 전환한 2026년의 변화는 이 자율성 방향의 연장선이다. myDoo와의 차이는 에이전트 엔진이다. Windsurf는 자체 Cascade를 쓰고, myDoo는 Claude Code를 쓴다. 에이전트 품질 면에서 어느 쪽이 우위인지는 워크로드에 따라 다르다.

3.3 Amazon Kiro — 스펙 주도 개발과 클라우드 통합

2026년 등장한 Kiro는 가장 독특한 포지셔닝이다. VS Code 기반이지만 AWS 서비스와 깊이 통합되고, "스펙 주도 개발"을 전면에 내세운다. 코드를 바로 쓰기 전에 에이전트가 요구사항·아키텍처 계획·테스트 스펙을 먼저 생성하고, 이 구조화된 계획 위에서 구현이 이뤄진다. Claude(Sonnet, Opus, Haiku)를 포함한 다중 LLM을 지원하지만 AWS 생태계 종속성이 명확하다. myDoo가 클라우드 중립으로 Claude Code를 쓰는 것과 대비된다.

3.4 myDoo의 차별점 — 경량 통합과 Claude Code 생태계 활용

myDoo가 Cursor·Windsurf·Kiro와 다른 것은 자체 AI 레이어를 개발하지 않는다는 점이다. 이것은 약점이면서 동시에 강점이다. 약점은 Claude Code의 한계가 곧 myDoo의 한계가 된다는 것이다. Anthropic이 Claude Code를 업데이트하지 않으면 myDoo도 정체된다. 강점은 역으로, Anthropic이 Claude Code를 개선할 때마다 myDoo도 함께 개선된다는 것이다. 개발자 한 명이 AI IDE 경쟁에서 수백 명 팀과 붙을 수 있는 방정식이 바로 이것이다. Claude Code 생태계의 MCP 통합, 에이전트 루프 개선, 새 모델 업그레이드가 myDoo에 자동으로 흐른다.

4. AI 네이티브 IDE 흐름 — 2026년의 지형도

myDoo는 고립된 프로젝트가 아니다. 2026년 AI 네이티브 IDE 시장의 더 큰 흐름 속에서 봐야 한다.

4.1 에이전트가 편집기를 흡수하는 방향

2025-2026년 AI 개발 도구 시장의 핵심 이동은 "AI를 IDE에 붙이는 것"에서 "에이전트를 중심에 놓고 IDE가 그 주변을 구성하는 것"으로의 전환이다. Claude Code Desktop, Google Antigravity, Kiro가 이 방향을 제각기 실험하고 있다. Claude Code Desktop은 에이전트를 스탠드얼론 앱으로 싸고, Antigravity는 에이전트 오케스트레이터를 중심에 두며, Kiro는 스펙을 에이전트의 출발점으로 삼는다. myDoo는 이 흐름에서 "에이전트를 편집기 안에 통합"하는 또 다른 경로를 택한다.

4.2 터미널 에이전트의 GUI화가 가져오는 것

터미널 기반 에이전트는 강력하지만 진입 장벽이 있다. 명령줄에 익숙하지 않은 개발자, 특히 시니어보다 주니어 개발자나 비개발 직군이 AI 코딩 에이전트를 쓰기 어려운 이유 중 하나가 터미널 환경이다. GUI IDE에 에이전트를 통합하면 이 장벽이 낮아진다. 에이전트의 동작이 시각화되고, 결과 검토가 편집기 내에서 이뤄지며, 에러 메시지를 복사할 필요 없이 편집기의 진단이 에이전트에게 바로 전달된다. 이것은 에이전트 코딩의 대중화를 의미한다.

4.3 오픈소스와 개인 개발자의 역할

myDoo가 개인 개발자의 프로젝트라는 사실은 이 시장의 또 다른 특징을 보여준다. Cursor는 수억 달러 투자를 받은 스타트업이고, Kiro는 AWS의 프로젝트다. 그러나 AI 네이티브 IDE 공간에서는 개인 개발자도 성숙한 기반 모델(Claude Code)과 오픈소스 에디터 프레임워크(VS Code)를 조합해 경쟁력 있는 도구를 빠르게 만들 수 있다. 이것은 AI 시대가 개발 도구 생태계의 진입 장벽을 낮추고 있다는 증거다.

4.4 단편화와 통합 사이

2026년 현재 AI 개발 도구 시장은 놀라울 정도로 단편화되어 있다. Cursor·Windsurf·Zed·Kiro·OpenCode·Aider·Continue.dev·myDoo가 각자의 방식을 실험한다. 이 단편화는 단기적으로 혼란이지만 장기적으로는 다양한 사용자 요구를 발굴하는 탐색 과정이다. 표준화는 승자가 가려진 뒤에 온다. 지금은 각 도구가 "어떤 개발자에게, 어떤 워크플로에서" 가장 잘 맞는지를 찾아가는 시간이다.

5. 이 통합이 가져오는 개발 경험의 변화

추상적 분석을 넘어, 구체적으로 개발 흐름이 어떻게 바뀌는지 본인의 관점에서 짚는다.

5.1 질의의 맥락이 자동으로 구성된다

현재 터미널 Claude Code에서 가장 많이 하는 작업 중 하나가 "지금 보고 있는 파일의 이 에러를 고쳐달라"는 요청이다. 이 한 줄을 터미널로 전달하기 위해 파일 경로를 복사하고, 에러 메시지를 복사하고, 필요한 경우 관련 파일을 함께 언급해야 한다. 에이전트가 편집기와 통합되면 이 모든 컨텍스트가 자동으로 구성된다. 개발자가 "이거 고쳐줘"라고 입력하면 에이전트는 편집기가 보고 있는 파일, 커서 위치, 진단 오류를 이미 알고 있다. 질의의 질이 높아지고, 응답의 정확도도 함께 높아진다.

5.2 검토 흐름이 코딩 흐름과 분리되지 않는다

에이전트 코딩에서 가장 위험한 순간은 개발자가 에이전트의 출력을 충분히 검토하지 않고 수락하는 때다. 터미널에서 에이전트가 파일을 수정하면, 개발자는 에디터로 전환해 변경사항을 확인하고, 다시 터미널로 돌아와야 한다. 이 마찰 때문에 많은 개발자가 리뷰를 대충 하거나 생략한다. 편집기 안에서 에이전트의 diff가 인라인으로 보이면, 검토가 코딩 흐름의 자연스러운 일부가 된다. "에이전트에 책임을 위임"하는 것이 아니라 "에이전트와 함께 개발"하는 패러다임이 구체화된다.

5.3 에이전트의 실수가 즉시 보인다

에이전트는 실수한다. 특히 컨텍스트가 불충분하거나 요청이 모호할 때. 터미널 기반 에이전트는 실수를 저질러도 개발자가 편집기로 전환해 확인하기 전까지 모른다. 편집기 통합 에이전트는 실수가 편집기의 진단 레이어에 즉시 반영된다. 컴파일 오류, 타입 오류, 린트 경고가 에이전트의 수정 직후 보이고, 에이전트는 이것을 컨텍스트로 받아 스스로 수정을 시도할 수 있다. 이 피드백 루프의 단축이 에이전트 코딩의 신뢰성을 높이는 핵심이다.

6. 주의할 점과 한계

myDoo를 둘러싼 현실적 한계도 직시해야 한다.

6.1 정보의 제한

myDoo는 GeekNews에 공개된 개인 프로젝트로, 2026년 6월 현재 공개된 기술 문서나 상세 기능 목록이 충분하지 않다. 이 글에서 서술한 "통합의 방향"과 "가져오는 경험 변화"는 공개된 컨셉과 AI IDE 시장의 일반적 흐름을 바탕으로 한 분석이며, 실제 구현 세부사항은 다를 수 있다. 직접 써보지 않은 도구에 대한 확정적 판단은 경계해야 한다.

6.2 Claude API 의존성

Claude Code를 기본 엔진으로 쓴다는 것은 Anthropic의 API 비용과 정책을 그대로 안는다는 뜻이다. Claude Code는 Pro 플랜 기준 월 $20이지만, 고강도 사용 시 추가 비용이 발생한다. 로컬 LLM을 쓰고 싶거나 오프라인 환경을 요구하는 팀에는 제약이 된다. 2026년 들어 Claude Code를 로컬 LLM으로 대체하는 프록시 솔루션이 등장했지만, 공식 지원은 아니다.

6.3 성숙도와 생태계

Cursor는 수백만 사용자를 보유하고, 빠른 릴리즈 사이클로 버그를 수정하며, 넓은 커뮤니티와 문서를 갖췄다. myDoo는 그 출발점에 있다. 개인 프로젝트가 성숙한 제품이 되기까지의 여정에는 엄청난 지속성이 필요하다. 지금 단계에서 myDoo를 주 개발 도구로 쓰기보다, 이 방향의 가능성을 탐색하는 참조 프로젝트로 보는 것이 현실적이다.

7. 결론 — AI 네이티브 IDE의 다음 수는 무엇인가

myDoo가 제시하는 방향은 분명하다. 터미널 에이전트와 GUI IDE 사이의 벽을 허물고, Claude Code를 편집기의 1급 구성 요소로 올려놓는다. 이것이 성공한다면, 개발자는 컨텍스트 전환 없이 에이전트와 협업하고, 에이전트의 출력을 편집기 흐름 안에서 검토하며, AI와 함께 코딩하는 경험을 완결된 루프로 만들 수 있다.

2026년 6월 기준, AI 네이티브 IDE 시장의 승자는 아직 결정되지 않았다. Cursor가 현재 가장 완성도 높지만, Kiro·Windsurf·OpenCode·myDoo가 각자의 각도에서 판을 흔들고 있다. 이 단편화는 시장이 아직 "어떤 방식이 옳은가"를 찾고 있다는 신호다. myDoo는 그 탐색에서 "Claude Code 생태계를 최대한 활용한 경량 통합"이라는 답을 시도한다.

터미널에서 태어난 에이전트가 편집기 안으로 들어오는 것. 그리고 편집기가 에이전트를 중심으로 재편되는 것. 이 두 움직임이 교차하는 지점에 myDoo가 있다. 결과가 어떻든, 이 실험은 AI 네이티브 IDE가 무엇을 의미해야 하는지를 더 선명하게 만드는 데 기여한다.
