どこまでがサイトで、どこからがブラウザ機能なのか。この線がどこに引かれているかによって、同じ操作が消すものが変わる。そしてこの主題には構造的な部分がある。その線を引く側と、その線の位置によって利を得る側が、同じ組織でありうるということだ。

きっかけ - 何に対する例外なのか

2026年9月初めに広まった文章は個人ブログの記事だ。Mac 向けソフトウェアを作るジェフ・ジョンソンが自分のサイトに書いたもので、見出しは Chrome が利用者のサイトデータ設定において Google を再び例外扱いしている、という趣旨になっている。特定ベンダーに照準を合わせた論調の記事であり、それを先に書いておいたほうが以後の記述は読みやすくなる。

記事や要約を経るあいだに最初に落ちる情報は、何に対する例外なのかという部分だ。ここで問題にされている設定は一つに特定できる。chrome://settings/content/siteData にある三つの選択肢のうち二番目、ウィンドウをすべて閉じたらサイトが端末に保存したデータを削除する項目だ。サードパーティ Cookie のブロック一般でもなければ、広告トラッキング一般でもない。

書き手が示す手順はこうだ。その選択肢を有効にし、Chrome にログインしていない状態で Google 検索を一度行い、ウィンドウをすべて閉じる。その後デバイス上のサイトデータ一覧を見ると、www.google.com の項目がおよそ 1,216 KB 残っていたと記す。ブラウザを起動し直しても残り、残っていた種類は Cookie とローカルストレージとセッションストレージだと書かれている。版は 152.0.7977.83 だ。彼は自分のスクリーンショットが証明ではなく説明のためのものだと添え、意図については断定しないと明示している。

同じ書き手は2020年にも似た趣旨の記事を書いており、そのときの件はのちに修正されたと今回の記事に述べている。見出しの「再び」はその経緯を指す語だ。ここまでが観察である。観察と規則は重みが違うので、先に表で分けてから進む。

項目ブログが記すこと一次資料で突き合わせられること

残ったとされる種類Cookie・ローカルストレージ・セッションストレージ三つともこの設定の適用対象である

設定が約束する一文をまず固定する

Chrome でのこの設定の名称は「デバイス上のサイトデータ」であり、経路は設定、プライバシーとセキュリティ、サイトの設定、その他のコンテンツの設定、デバイス上のサイトデータの順になる。画面上部の説明文は、訪れたサイトが期待どおり動くように情報を保存できると述べたうえで、ログイン維持と買い物かごを例に挙げる。その下に既定の動作が三つ、ラジオボタンで並ぶ。

選択肢画面に書かれた文併記される結果の文言
許可サイトがデバイスにデータを保存することを許可するサイトが期待どおりに動作する可能性が高い
終了時に削除ウィンドウをすべて閉じたらサイトがデバイスに保存したデータを削除するヘルプ文書は、サイトが訪問と訪問のあいだの記憶を保つ可能性が下がると記す
ブロックサイトがデバイスにデータを保存できないようにする（推奨されない）サイトが期待どおりに動作しない場合がある
カスタマイズされた動作下に並ぶサイトは既定値ではなく個別の設定に従う一覧は「デバイスへの保存を許可」と「許可しない」の二つ

隙間はここから始まる。ヘルプ文書は三つの選択肢の名前とおおよその効果までを書く。しかし、カスタマイズ一覧が既定値と衝突したときにどちらが勝つのか、その一覧にどんな経路で項目が載りうるのかは、その文書にない。利用者が画面で目にする語は「既定の動作」だが、実際の判定は既定値ひとつで終わらない。二段目があり、興味深い事例はすべてその二段目に住んでいる。

サイトデータは一枚岩ではない

「サイトデータ」という一語の下に、寿命もスコープ規則も API も異なる保存領域がいくつも並ぶ。ウィンドウを閉じたときに走るルーチンもこの区分をそのままなぞるので、コードを読む前に並べておく価値がある。

  • Cookie — サーバーがヘッダーで埋め込み、以後のリクエストに再び載る値。範囲はオリジンではなくドメイン単位で決まる
  • ローカルストレージ・セッションストレージ — スクリプトが書くキーと値の保存領域。セッションストレージはタブの寿命に縛られる
  • IndexedDB — 構造化されたデータベース。容量が大きく、オフラインアプリの状態が主にここに置かれる
  • キャッシュストレージと Service Worker — オフライン応答を抱える保存領域と、それを制御する登録情報
  • Origin Private File System・Storage Buckets — オリジン専用のファイル階層と、保存単位を分ける比較的新しい API
  • ブラウザキャッシュ — サイトが制御する保存領域ではなく、ブラウザが性能のために持つ複製。別の項目として扱われる

Chromium がウィンドウをすべて閉じたときに実行するコードは二手に分かれる。Cookie 以外のストレージは保存領域単位で一度に消し、Cookie は別に処理する。ソースのコメントはその理由を、Cookie がオリジン単位ではないからだと明記している。そして「このオリジンはセッション限りか」を判定する関数は、Cookie のコンテンツ設定をそのまま読む。

// chrome/browser/sessions/session_data_deleter.cc
bool OriginMatcher(const blink::StorageKey& storage_key,
                   storage::SpecialStoragePolicy* policy) {
  return policy->IsStorageSessionOnly(storage_key.origin().GetURL()) &&
         !policy->IsStorageProtected(storage_key.origin().GetURL());
}

// chrome/browser/extensions/extension_special_storage_policy.cc
bool ExtensionSpecialStoragePolicy::IsStorageSessionOnly(const GURL& origin) {
  return cookie_settings_->IsCookieSessionOnly(origin);
}

画面で選んだ「デバイス上のサイトデータ」の状態は内部的に Cookie のコンテンツ設定として保存され、その値ひとつが Cookie ではない保存領域の運命まで決める。利用者に二つに見える概念が、コードでは一つなのだ。この一点だけで、Cookie の例外がローカルストレージの残存につながる状況は不思議ではなくなる。

どこまでがサイトで、どこからがブラウザ機能か

この設定が扱う対象は「サイトが保存したもの」だ。ブラウザ自身が保存するものは別の区画にあり、その区画はこのスイッチの射程外にある。プロファイルディレクトリは二種類を一つのフォルダに収める。chrome://version の Profile Path がその位置であり、サイトのストレージもここにあるが、閲覧履歴・ブックマーク・設定・拡張機能のデータも同じ場所にある。

ブラウザ機能が使う保存領域は、ウェブページが呼べるストレージ API を通らない。だからサイトデータ削除のルーチンはそれを見にいかない。同期の状態、セーフブラウジングが先に取得しておくリスト、アドレスバーの候補が参照する記録、翻訳機能の設定。どれもサイトが作った保存領域ではない。閲覧データ削除画面の別項目か、端末ではなくサーバー側にあるアカウント設定がそれを担当する。

境界は一度ではなく二度引かれる。一つ目の線は、データがサイトのストレージにあるかブラウザ内部のストレージにあるかを問う。二つ目の線は、削除ルーチンがどこまでなぞるように書かれているかを問う。そして二つ目の線にも明示的な例外がある。Chromium ソースは拡張機能スキームのオリジンと、利用者が導入したホスト型アプリを保護されたストレージに分類し、終了時の掃除から外す。既定で導入されたアプリはこの保護を受けないと、同じ関数がわざわざ書き添えている。

この例外は特定の企業とは無関係なブラウザ側の設計だ。ウィンドウを閉じるたびに設定を失う拡張機能は使い物にならないからである。例外があること自体が問題なのではない。追うべきは常にどの例外がどこに書かれているかのほうだ。

文書に書かれている例外 - アカウントと行動記録

Chrome の閲覧データ削除に関するヘルプ文書には、多くの人が読み飛ばす三つの文がある。三つとも「消した」という語の範囲を狭める文であり、そのどれも隠されていない。文書に印刷されているという点が重要だ。

  • Chrome にログインした状態で Cookie を削除しても、Google アカウントからログアウトされることはない
  • Google アカウントに保存されたカードと住所は、この操作では削除されない
  • Google サービスでの検索やその他の行動はアカウントに保存され、アカウント側で別途削除する

企業向け管理者ポリシーの側にも同じ趣旨の一文がある。ウィンドウをすべて閉じたときに消す項目を管理者が指定するポリシーの説明に、Cookie を削除しても利用者は Google アカウントにログインした状態のままだという記述が入っている。同じ説明にはもう一つの条件も添えられている。ブラウザや OS が正常に終了しなかった場合、その回の削除は行われないというものだ。ウィンドウを閉じたことによる終了ではないから、という理由まで書かれている。

ここがこの記事の心臓部だ。「サイトデータを消す」という操作はアカウントの状態に触れないよう設計されており、その設計が文書にある。利用者が期待する削除の範囲と、文書が定める削除の範囲が分かれる地点がまさにこの線である。そしてこの線をどこに置くかは、技術的な判断であると同時に事業的な判断でもある。ログインが維持されるほうが使う人には便利であり、同時にそのアカウントを運営する側にも有利だ。

コードが定めた優先順位 - 許可一行が削除に勝つ

Cookie 側の判定は Chromium に関数一つとして入っており、検査の順序がはっきりしている。この順序こそが「例外が入り込みうる位置」の正確な座標なので、要約せずに一行ずつ読む価値がある。

  1. 当該オリジンの Cookie 設定が許可なら、その場で削除対象から外れて関数は戻る
  2. 次に例外項目をなぞり、ドメインが一致する項目のうち一つでも許可があれば、やはり削除対象にならない。セッション限りの項目はフラグを立てるだけだ
  3. 最後に、実効設定がセッション限りであるか、なぞる途中でセッション限りの規則に当たっていれば削除する
// components/content_settings/core/common/cookie_settings_base.cc
ContentSetting setting = GetContentSetting(
    origin, GURL(), ContentSettingsType::COOKIES, &setting_info);
if (setting == CONTENT_SETTING_ALLOW) {
  return false;              // 削除しない
}
for (const auto& entry : cookie_settings) {
  if (net::cookie_util::IsDomainMatch(domain, host)) {
    if (entry.GetContentSetting() == CONTENT_SETTING_ALLOW) {
      return false;          // 許可項目が一行あれば勝つ
    } else if (entry.GetContentSetting() == CONTENT_SETTING_SESSION_ONLY) {
      matches_session_only_rule = true;
    }
  }
}
return setting == CONTENT_SETTING_SESSION_ONLY || matches_session_only_rule;

既定値を「閉じたら削除」にしていても、ドメインが重なる許可項目が一行あればその一行が勝つ。ドメイン一致は上位ドメインの規則が下位まで覆う方式なので、ある登録ドメインに掛かった一行は、そのドメインと下位ドメインの Cookie 全体に届く。そして前節のとおり、同じ設定値が Cookie 以外の保存領域を掃除するかどうかも決めている。

同じ趣旨の注意が管理者ポリシー文書にもある。許可・ブロック・セッション限りの三つのポリシーに重なる URL パターンがある場合、どちらが優先するかは定めていないと書かれている。定められていない優先順位は、定義上、版によって挙動が変わりうる領域だ。挙動を語るときに版を記す理由がここにある。

つまり「例外がある」という観察だけでは原因を特定できない。例外が入る場所はすでに設計に含まれており、画面にも「カスタマイズされた動作」という名前で現れている。残る問いはその場所に何がどの経路で入ったのかであり、これは文書ではなく実行中のプロファイルが答える問題だ。

ウィンドウをすべて閉じるという条件の但し書き

条件節も約束と同じ丁寧さで読む必要がある。この設定の発動条件は「ウィンドウをすべて閉じる」であって「ブラウザを終了する」ではない。デスクトップ OS ではこの二つは同じ出来事ではない。

ウィンドウが一つでも残っていれば、ルーチンはそもそも走らない。バックグラウンドアプリの設定やトレイ常駐でプロセスが生きている場合も、キーボードの前にいる人からはすべて閉じたのと寸分違わず見える。異常終了も別経路で同じ結果を生む。ここではポリシー文書が、その回の削除は飛ばされると明示している。

起動時に前回のセッションを復元する設定にしている場合は、分岐がもう一つ増える。その構成では終了ルーチンが、有効期限を持たないセッション Cookie の一括削除の段階を飛ばす。セッション限りの規則に当たったものはそのまま消す。範囲の異なる二つの削除がここで絡んでおり、そのうち一方が別画面の選択によって無効化されていることは、設定画面のどこにも表示されない。同じルーチンでは、セッション限りのオリジンのメディアデバイス識別用の値と、トラストトークンのセッション限りデータも併せて片づけられる。

まとめると、削除が起きていない状態は不具合より条件が成立しなかった場合のほうが多い。残存を目にしたとき、最初に分けるべきはこの条件だ。

分割後のサイトという語 - パーティショニング

サイトという語はここ数年でもう一段細かく割られた。Chrome は 115 版からストレージのパーティショニングを全利用者に適用している。保存領域の鍵はオリジン単体ではなくオリジンと最上位サイトの組み合わせになり、途中に別サイトのフレームが挟まっていたかを示すビットが一つ加わる。

  • ストレージ API — クォータ、ローカルおよびセッションストレージ、IndexedDB、Cache Storage、Origin Private File System、Storage Buckets、Clear-Site-Data ヘッダーの射程、そして 137 版以降の Blob URL ストア
  • 通信 API — Broadcast Channel、SharedWorker、Web Locks も同じ鍵で分けられる
  • Service Worker — サードパーティ文脈で登録されたものは、タイミングによる漏れを塞ぐために分離される

その結果、あるドメインのローカルストレージは一つではない。どの最上位サイトの下で作られたかによって複数の区画に分かれる。一覧画面でドメイン一つに畳まれて見える項目が、実際には複数区画の合計でありうる。残存容量だけを見て「どのサイトが残したのか」を断じにくい理由がここにある。

Cookie 側の範囲規則はこれとは別の軸だ。あるリクエストで Cookie が載るか載らないかは SameSite がリクエスト種別ごとに作る判定表が決める。保存せずに端末を見分ける系統の信号はさらに別の軸であり、消すものがない追跡で扱ったとおり、どんな削除設定も届かない領域にある。

他のブラウザにも同じ場所がある

終了時削除を用意するブラウザは、例外の仕組みも併せて出荷している。例外がなければログイン維持のような機能が成立しないからだ。ベンダーごとに違うのは名称と、より重要なこととして文書化の密度である。

Edge の行は特に出所を見えるようにしておく必要がある。公開の質疑応答で、マイクロソフトのサポート担当者が、自社ドメインの既定 Cookie が消えないのは設計どおりの挙動だと回答した記録がある。これは製品文書に載った規定ではなくサポート窓口の回答であり、両者は引用するときの重みが違う。ただし同じ配置が複数のベンダーに存在するという論点を立てるには十分な資料だ。

Firefox 側の例外は最近になって明文化された部類に入る。終了時の片づけポリシーに例外オリジンの一覧が付いたのは 154 版からで、それ以前は項目単位の入切だけだった。例外が必要だという認識も、それを書き残す必要があるという認識も、遅れて訪れることはあっても結局は訪れる。

線を引く側とその線の受益者が重なるとき

ブラウザを作る組織がその上で検索・広告・アカウント事業も併せて営むとき、「サイト」と「ブラウザ機能」の境界線を定める側と、その線の位置によって利を得る側が重なる。これはどの企業の品性の話でもなく配置の話だ。同じ配置は各所にある。OS ベンダーが既定のブラウザを作るとき、検索事業者がブラウザエンジンを作るとき、コンテンツ事業者が自社コンテンツの流通経路まで運営するとき、同じ重なりが生じる。

配置が生み出すのは結論ではなく立証責任の方向だ。境界が自社サービスに有利な側に置かれたとき、それが機能上の必要によるものか事業上の便宜によるものかは、外から見分けにくい。ログインを維持してくれる例外は利用者の便宜でもあり、アカウント事業の資産でもある。動機をめぐる議論をいくら重ねても両者は分離しない。

だからこそこうした配置では文書化が信頼の代替物になる。例外があるならその例外を書き残すこと、一覧を利用者が開ける画面に置くこと、優先順位が決まっているならその順序を書くこと。同じ製品の中でもこの密度は一様ではない。アカウントのログイン維持という例外は、ヘルプとポリシーの説明という二か所に書かれている。一方でデバイス上のサイトデータの文書には、許可項目が既定値に勝つという事実がない。その規則はソースとポリシー定義でしか読めない。

この差はそのまま実務に移る。設定一つが複数の保存領域を同時に支配し、例外一覧が既定値に勝ち、優先順位が意図的に定められていない区間があるなら、それは読み手の推測ではなく文書に書かれるべき事項だ。広告ブロックと拡張 API をめぐる力の配分も同じ構造の別の顔である。

利用者が自分で読む手順

設定画面は状態を見せ、保存領域の画面は結果を見せる。両者が食い違うとき、答えはいつも後者にある。必要になる前に住所を知っておくとよい。

chrome://settings/content/siteData      既定の動作3択とカスタマイズ一覧
chrome://settings/content/all           デバイス上のサイトデータ一覧（サイト別の容量）
chrome://settings/clearBrowserData      閲覧データの削除（項目別）
chrome://version                        Profile Path — このプロファイルの保存位置
chrome://extensions                     導入済み拡張機能の一覧
  1. 設定画面で既定の動作が三つの選択肢のどれになっているかを読む
  2. その下のカスタマイズ一覧を二つとも読む。ここに載っているサイトは既定値に従っていない
  3. デバイス上のサイトデータ一覧で残っているサイトと容量を読む。ドメイン一行が複数区画の合計でありうる点を忘れない
  4. ウィンドウをすべて閉じて開き直し、同じ一覧をもう一度読む。ウィンドウが生きていたなら条件が成立していなかっただけだ
  5. 開発者ツールの Application パネルで種別ごとに読む。Cookies・Local storage・Session storage・IndexedDB・Cache storage がそれぞれ別項目で、ストレージ概要に使用量の内訳が並ぶ

プロファイルとゲストウィンドウは範囲を分ける別の仕組みだ。プロファイルはユーザーデータディレクトリの下位ディレクトリであり、プロファイルを分ければ保存領域も分かれる。ゲストウィンドウは Chrome のヘルプ文書が記すとおり、セッションが終わると閲覧履歴・Cookie・サイトデータを端末から削除する。ただし同じ文書は限界も併記している。訪れたサイト、ログインしたサイト、ネットワークを運営する組織、通信事業者、検索エンジンからは行動がそのまま見えるというものだ。端末に残さないことと観測されないことは別の主張であり、なされているのは前者だけである。

この種の報道を次から読む方法

ブラウザの挙動をめぐる観察の報道はこれからも出る。六つだけ分けておけば、どちらが正しいかを決めなくてもたいていは所定の位置に収まる。

  • どの設定に対する例外か — 設定名と画面経路まで特定されているか。サードパーティ Cookie のブロックと終了時削除は、コードパスの違う別機能だ
  • 観察か規則か — 一人の再現は観察であり、公式文書とソースは規則だ。観察は規則を覆さず、規則は観察を説明する義務を負う
  • 対照群があるか — 同じ条件で他のサイトに同じ手順を踏んだ結果が併せて示されているか
  • 例外が入る場所がもともとあるか — あるなら、例外を目撃したという事実だけでは原因の特定にならない
  • 版が記されているか — ブラウザの挙動は版ごとに変わり、優先順位が定められていない区間はとりわけ変わりやすい
  • 意図についての文か挙動についての文か — 意図は文書で判別されない。挙動の主張だけを残せば、残るものはずっと堅い

この一覧はブラウザに限った話ではない。クライアントで見えたものからサーバー側の規則を推し量る状況はどこにでもあり、その推論がどこで切れるかは信頼境界を扱った記事で見たのと同じ問題である。

確認できなかったこと

以下の項目は一次資料で文面を突き合わせられなかったため、本文に事実として入れていない。理由を添えて記す。

  • 報告された挙動そのもの — 特定ドメインのデータが終了後も残るという観察は再現結果であり、公式文書と突き合わせられない。そのため本文では観察としてのみ帰属させた。記事にある 152.0.7977.83 は実際に配布された安定版のビルド番号であり、この記事を書いている時点の安定版は 153.0.8010.27 である。版が違えば結果も変わりうる
  • Chrome が特定ドメインへの許可項目を既定で載せているか — 設定の文字列リソースにもヘルプ文書にもそうした規定はない。実行中のプロファイルの例外一覧を読まないかぎり分かれない項目だ
  • 観察された残存の原因 — 許可項目、拡張機能、セッション復元設定、異常終了、居残ったバックグラウンドプロセスのいずれもが同じ症状を出す。元記事はこのうちいくつかを排除したと記すが、残る経路すべてが排除されたという記述はない
  • 2020年の件がいつどの変更で修正されたか — 今回の記事は修正されたと記すが、その変更の識別子も版も示されていない。Chromium の課題番号も提示されていない
  • 対照群の範囲 — 元記事は問題のドメインが唯一のようだと記しつつ、自分のスクリーンショットが証明ではなく説明だと添えている。いくつのサイトをどの条件で比べたのかは記事にない
  • Edge の挙動を定めた製品文書 — 自社ドメインの Cookie が残るのは設計どおりだという記述は、サポート窓口の回答にしか見当たらない。同趣旨の製品文書は見つからなかった
  • Chrome プライバシーホワイトペーパーの機能別保存位置の記述 — 当該文書は本文をスクリプトで描画する構成のため、静的な取得では本文が返らない。そこでブラウザ内部機能の保存位置は、ヘルプとソースで明示される範囲だけを書いた
