序論 - マルチラインフラグは複数行に対応させるスイッチではない

正規表現エンジンは、複数行を含む文字列も1つの文字列として受け取る。デフォルトでは ^ は文字列の先頭に、$ は文字列の末尾(Python・.NET・Perlでは末尾の改行の前も含む)に対応し、マルチラインフラグ(Python re.M、JavaScript m、.NET Multiline、Perl /m)がオンになると、行の境界にも対応する。したがって、名前とは違い、Pythonのドキュメントによれば、フラグが変えるのは「複数行を処理する能力」ではなく、2つのアンカーが行の境界を認めるかどうかの1点だけである。ドット(.)が改行をまたぐかどうかは別のスイッチ(s)が決める(8節)。

実務で引っかかる場所は2つある。1つは、末尾に改行が1つ付いた入力で $ がどこに対応するかで、もう1つは、改行が \n ではなく \r\n(CRLF)のとき $ が \r の前に対応しない場合である。どちらもツールごとに答えが違う。言語・ツール間の正規表現の方言全体はどこでも動く正規表現の記事が、CRバイトがシェルスクリプトやgitで起こす問題はCRLFとLFの記事が扱っているので、ここではアンカーの行境界の解釈とCRLF入力の結果だけを、同じ入力で比べる。

扱う問いは次のとおりである。

  • デフォルトで ^・$ はどこに対応し、マルチラインフラグはそれをどう変えるか。
  • 入力末尾の改行の前と後で、$・^ の結果はツールごとに同じか。
  • \A・\z・\Z はどのツールにあり、マルチラインフラグの影響を受けるか。
  • grep・sed・awkでは、アンカーはすでに行単位か。
  • CRLF入力で $ はどこに対応し、どう対処するか。

同じ入力2つ - LFとCRLF、そして位置を目で見る方法

すべてのデモは同じ2つの入力を使う。LF入力は a1\nb2\n(2行、末尾に改行が1つ)、CRLF入力は a1\r\nb2\r\n である。アンカーが対応した位置を見る方法はどれも同じで、^ が対応した場所に < を、$ が対応した場所に > を挟んだ文字列を、エスケープした形で出力する。たとえば 'a1\nb2>\n>' は、$ が b2 の後ろと文字列の一番最後の2か所に対応したという意味である。以下の出力の読み方は3つある。

  • $ の > が最後の \n の前にも付くか(末尾の改行の前での対応)。
  • ^ の < が最後の \n の後ろの空の位置にも付くか(末尾の改行の後ろでの対応)。
  • CRLFで > が \r の前に付くか、\r と \n の間に付くか。

Python re - デフォルトの $ は2か所に対応する

import re, sys
                    print('Python', sys.version.split()[0])
                    LF = 'a1\nb2\n'
                    CRLF = 'a1\r\nb2\r\n'
                    def mark(pat, s, fl, ch):
                        return repr(re.sub(pat, ch, s, flags=fl))
                    for name, s in (('LF  ', LF), ('CRLF', CRLF)):
                        for label, fl in (('default     ', 0), ('re.MULTILINE', re.M)):
                            print(name, label, '^ ->', mark(r'^', s, fl, '<'), ' $ ->', mark(r'$', s, fl, '>'))
                    print(r'--- \A and \Z (Python 3.13)')
                    for name, s in (('LF  ', LF), ('CRLF', CRLF)):
                        print(name, r'\A ->', mark(r'\A', s, 0, '<'), r' \Z ->', mark(r'\Z', s, 0, '>'), r' \Z with re.M ->', mark(r'\Z', s, re.M, '>'))
                    print(r'--- \z in 3.13')
                    try:
                        re.compile(r'\z')
                    except re.error as e:
                        print('re.error:', e)
                    print('--- whole-line match')
                    for name, s in (('LF  ', LF), ('CRLF', CRLF)):
                        print(name, r'^\w\d$ re.M ->', re.findall(r'^\w\d$', s, re.M))
                        print(name, r'^\w\d\r?$ re.M ->', re.findall(r'^\w\d\r?$', s, re.M))
                        print(name, 'splitlines() ->', s.splitlines())
                    print('--- re.S is a different switch')
                    for fl, label in ((0, 'none'), (re.S, 're.S'), (re.M, 're.M'), (re.M | re.S, 're.M|re.S')):
                        print(label.ljust(10), re.findall(r'^a1.*$', LF, fl))
                    print('--- inline flag')
                    print(re.findall(r'(?m)^\w\d$', LF))

                    print(re.findall(r'^.*$', CRLF, re.M))

Python 3.13の re.M のドキュメントは次のように書いている。「When specified, the pattern character '^' matches at the beginning of the string and at the beginning of each line (immediately following each newline); and the pattern character '$' matches at the end of the string and at the end of each line (immediately preceding each newline). By default, '^' matches only at the beginning of the string, and '$' only at the end of the string and immediately before the newline (if any) at the end of the string.」(出典: docs.python.org/3.13/library/re.html)出力はこの文と同じ形をしている。

  • LFのデフォルト: $ は 'a1\nb2>\n>' となり、b2 の後ろ(末尾の改行の前)と一番最後に対応した。^ は一番先頭の1か所だけである。
  • LFで re.MULTILINE: ^ は '<a1\n<b2\n<' と3か所で、最後の \n の後ろの空の位置にも対応した。$ は 'a1>\nb2>\n>' で、行ごとに1つずつと一番最後である。
  • CRLF: $ は 'a1\r>\nb2\r>\n>' となり、\r と \n の間に対応する。\r は行の内側の文字として扱われる。
  • そのため、CRLFで ^\w\d$(re.M)は []、つまり0件である。^\w\d\r?$ は2行に合致するが、値が 'a1\r' のように \r を含む。splitlines() は ['a1', 'b2'] で、\r\n を1つの行境界として扱った。
  • \A と \Z: \A は一番先頭の1か所、\Z は 'a1\nb2\n>' で一番最後の1か所で、re.M を付けても同じである。3.13では \Z は末尾の改行の前には対応しない。
  • \z は3.13では re.error: bad escape \z になる。3.14以降の版のドキュメントは、\z を「Added in version 3.14」、\Z を「The same as \z. For compatibility with old Python versions.」と記している(docs.python.org/3/library/re.html の3.14以降の版の表記)。

MDNの入力境界アサーションのドキュメントは次のように書いている。「If the m flag is set, ^ also matches if the character to the left is a line terminator character, and $ also matches if the character to the right is a line terminator.」(出典: developer.mozilla.orgのInput boundary assertionのページ)同じページのノートには「To match the start and end of the entire string in m mode, use the buffer boundary assertions \A, \z, and \Z.」ともある。出力は次のとおりである。

  • LFのデフォルト: $ は "a1\nb2\n>" で、一番最後の1か所だけである。Pythonと違い、末尾の改行の前には対応しなかった。
  • LFの m フラグ: Pythonと同じ形である。^ は最後の改行の後ろの空の位置にも対応する("<a1\n<b2\n<")。
  • CRLFの m フラグ: ^ は "<a1\r<\n<b2\r<\n<" で \r と \n の間にも対応し、$ は "a1>\r>\nb2>\r>\n>" で \r の前と \n の前の両方に対応した。\r が行末文字として扱われる。
  • その結果、CRLFでも /^\w\d$/gm は ["a1","b2"] と2行に合致した。一方 /^.*$/gm は ["a1","","b2","",""] で空文字列が混ざる。ドットは行末文字の \r を越えられず、\r と \n の間の位置で空の行が別に対応する結果になる。
  • m フラグの行末文字は \n だけではない。\u2028 と \r の後ろでは ^ が対応し("<a<LS><b"、"<a\r<b")、垂直タブの後ろでは対応しなかった("<a<VT>b")。
  • \A: このNodeでは u フラグなしだと文字 A として扱われて 'Aa1\n' に合致し(false true の出力の2つ目の値)、u フラグを付けると SyntaxError: Invalid regular expression: /\Aa1/u: Invalid escape だった。MDNのノートとは異なり、このNode v22.16.0では \A はバッファ境界アサーションとして動作しなかった。

Microsoft Learnのアンカーのドキュメントは、$ のCRLFの事情を直接書いている。「Note that $ is satisfied at \n but not at \r\n (the combination of carriage return and newline characters, or CR/LF). To handle the CR/LF character combination, include \r?$ in the regular expression pattern. Note that \r?$ will include any \r in the match.」また \Z を「The match must occur at the end of the string, or before \n at the end of the string」、\z を「The match must occur at the end of the string only」と定義し、\Z は「identical to the $ anchor, except that \Z ignores the RegexOptions.Multiline option」だと書いている。(出典: learn.microsoft.comのAnchors in regular expressionsのページ)

  • デフォルトはPythonと同じである。$ は末尾の改行の前と一番最後の2か所(a1\nb2>\n>)で、Multiline では ^ が最後の改行の後ろの空の位置を含めて3か所になる。
  • \Z は $ と同じ位置(a1\nb2>\n>)に対応し、Multiline を付けても同じ結果である。\z は一番最後の1か所である。ドキュメントの定義と出力が一致する。
  • CRLF: $ は a1\r>\nb2\r>\n> のように \r の後ろに対応する。^\w\d$(Multiline)は0件、^\w\d\r?$ は2件で、値は a1\r,b2\r と \r を含んでいた。ドキュメントの「\r?$ will include any \r in the match」と同じである。
  • インライン (?m) は、PowerShellの -replace・-match 演算子でも同じ効果を出した(-match '(?m)^b2$' はLFでTrue、CRLFでFalse)。
  • ドキュメントは、.NET 11から RegexOptions.AnyNewLine で $ が \r\n を1つの単位として認識するようにできると書いている。このPCの5.1では、RegexOptions 列挙型の名前の一覧にその項目はなかった(出力の最後の行)。

                      printf "/%-3s %s\n", $f, defined $v ? esc($v) : '(no match)';
                    }

perlreは /m を「change "^" and "$" from matching the start of the string's first line and the end of its last line to matching the start and end of each line within the string」、\Z を「Match only at end of string, or before newline at the end」、\z を「Match only at end of string」と記している。(出典: perldoc.perl.org/perlre)

  • デフォルトと $・\Z・\z は、Python・.NETと同じ位置に対応した(a1\nb2>\n>、\z は一番最後)。
  • 違いは /m での ^ である。LFでは <a1\n<b2\n と2か所だけで、Python・JavaScript・.NETが対応した最後の改行の後ろの空の位置には対応しなかった。
  • CRLFはPythonと同じ事情である。^(\w\d)$ は空のリスト、^(\w\d)\r?$ は [a1,b2] である(値はキャプチャグループなので \r を含まない)。

  • sed はデフォルトのモードで出力バイトにCRがなく(<a1>\n)、sed -b では <a1\r>\n とCRの後ろに > が付いた。つまりCRが残った状態では、$ は \r の後ろ、\n の前に対応する。
  • awk も同じである。デフォルトのモードはCRを取り除き、-v BINMODE=3 ではCRが残った。
  • sed 'N;s/^/</g' は、合わせた2行(a1\nb2)の一番先頭にだけ < を付け、M 修飾子を付けると <a1\n<b2\n と2行目の前にも付いた。合わせた塊の中で ^ に行境界を認めさせるスイッチが M である。
  • レコード区切りを \001 に変えてファイル全体を1レコードとして読んだawkでは、^ と $ はレコードの一番先頭と一番最後に1か所ずつ対応した(<a1\nb2\n>)。

ドット(.)とsフラグ - アンカーとは別のスイッチ

4つの言語の出力の最後には同じ実験が入っている。パターン ^a1.*$ をLF入力(a1\nb2\n)に適用し、スイッチの組み合わせだけを変えた。結果はどのツールでも同じである。

スイッチ結果意味
なしマッチなし(Python []、JavaScript null、Perl (no match)).* は1行目の末尾で止まり、$ は一番最後(または末尾の改行の前)にしか対応しないため、つながらない
s(ドットが改行を含む)a1\nb2\n 全体.* が改行を越えて最後まで進み、一番最後の $ に届く
m(アンカーが行境界を認める)a1 のみ$ は1行目の末尾に対応するが、ドットは依然として改行を越えられない
mとsの両方a1\nb2\n 全体ドットが改行を越え、$ は行末も一番最後も認めるので、最も長い側まで進む
  • m だけをオンにすると .* は1行目で終わり、s だけをオンにすると行境界ではなく文字列の一番最後まで進む。2つのスイッチは独立である。
  • PowerShellの Singleline、Pythonの re.S が同じ役割を果たし、出力結果も同じだった。
  • したがって、「行単位のマッチ」が目的なら m、「複数行にまたがる1つのマッチ」が目的なら s を使い、両方必要なら両方をオンにする。

CRLFで $ が外れるとき - 対処は入力・パターン・スイッチの3通り

ツール対処出力で確認した結果
Pythonパターンに \r?$ を入れるか、先に splitlines() で行を分ける\r?$ は2行に合致するが値に \r を含み、splitlines() は ['a1', 'b2']
JavaScriptm フラグが \r を行末と認めるので、$ をそのまま使う。ドットを使うパターンは空のマッチを除く/^\w\d$/gm は ["a1","b2"]、/^.*$/gm は空文字列が混ざる
.NET(PowerShell)ドキュメントが示す \r?$0件から2件へ、値に \r を含む
Perl\r?$空のリストから [a1,b2] へ(キャプチャグループなので値に \r はない)
grep・sed・awk(このPC)デフォルトのモードはCRを除去して読む。CRを残すには grep -U・sed -b・awk -v BINMODE=3 を使い、そのモードではパターンにCRを入れるgrep -U でCRを入れたパターンはCRLFで1件
  • 入力を正規化する方法(Pythonの splitlines() のように先に行を分ける方式)は、パターンが行末文字を知らなくてよいので、同じパターンをLFでもCRLFでもそのまま使える。
  • パターン側(\r?$)は値に \r がついてくるので、値をそのまま比較したり保存したりする前に取り除く必要がある。
  • スイッチ側はJavaScriptにだけ当てはまる。同じ m フラグが \r を行末と見なすので、CRLFを意識せずに書いたパターンが通ってしまい、別の言語に移したときに初めて壊れる。
  • CRがどこから入ってくるか(ファイルの保存方法、gitの設定、ダウンロード)は、CRLFとLFの記事がバイトのレベルで扱っている。
  • アンカー自体が幅ゼロのアサーションであること(MDN:「Both are assertions, so they don't consume any characters」)は、先読み・後読みと同じ部類であり、その使い方は先読みの記事にある。

確認できなかったこと

  • LinuxとmacOSでのgrep・sed・awk、および各言語の結果。このPCのgrep・sed・awkはGit Bashのビルドで、デフォルトのモードでCRを除去する動作が他の環境でも同じかどうかは実行できなかった。
  • Python 3.14以降、.NET 11の RegexOptions.AnyNewLine、MDNのノートが挙げる \A・\z・\Z のバッファ境界アサーションが動作するJavaScriptエンジン。このPCには該当するバージョンがない。
  • PowerShell 7(pwsh)と.NET Core系の結果。このPCで実行した.NETの正規表現はWindows PowerShell 5.1のものだけである。
  • PCRE・Go・Java・Ruby・POSIX正規表現のアンカーの動作と、Unicodeの行区切り文字(\u0085 など)全般。JavaScriptでは \u2028・\r・垂直タブだけを試した。
  • 性能とコンパイルオプション(例: .NETの RegexOptions.Compiled)がアンカーの動作に与える影響、および re.M と re.A など他のフラグの組み合わせ。
