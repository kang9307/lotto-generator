1. while (true); が未定義動作とされた背景

一般に、プログラミング言語における反復制御構造は、所定の終了条件が成立するまで処理を維持するか、あるいは特定のイベントを待つために実行コンテキストを待機させる基本骨格として用いられます。多くの開発者はソースコード内で本体が空の while (true); を記述する際、プログラムがその地点に達して永久に停止する明確な無限ループを意図します。しかし原文は、C++26以前においては副作用（side effect）を伴わない while (true); 形式のループが、言語規格上「未定義動作（undefined behaviour）」として扱われていたと記しています。多くのプログラマはこのコードが完全に定義された動作（well-defined）であると思い込んでいますが、原文によるとC++26以前の規格仕様に照らすとそれは誤った認識でした。

原文は、副作用のないループに対してコンパイラが「このループはいずれ必ず終了する」と仮定できる裁量を与えられていたと説明しています。そして一部のコンパイラ、とりわけClangなどの最適化器は、この仕様上の規定を根拠としてループ全体を最適化の過程で完全に除去（optimize away）してしまう挙動を示したと原文は指摘しています。原文は、こうしたループの除去が開発者の予期せぬ衝撃的な結果（spectacular consequences）をもたらしたと述べています。

本稿の解釈では、コンパイラの最適化規則と開発者の直感的なコード記述意図が衝突した問題を、構文上の例外規定として整理した形です。

原文は、今回の改定があらゆる無限ループを一様に安全にしたわけではない点を明白に強調しています。C++26が導入した変更は、あらゆる反復文を無条件に救済するものではなく、構文的に極めて限定された形式に対してのみ未定義動作の烙印を外す狭い修正です。原文は、自明な無限ループという厳格な定義を満たしたときに初めてコンパイラの除去対象から除外されると記しています。

2. 前方進行（Forward Progress）の仮定とコンパイラのループ最適化

原文は、コンパイラが無限ループを削除できた理論的根拠として、C++11規格で正式に導入された前方進行（forward progress）保証の規定を挙げています。原文が引用するC++規格の [intro.progress] 節によると、コンパイラ実装は実行中のすべてのスレッドがいずれ指定された動作のいずれかを実行すると前提してよいことになっています。原文に引用されたC++11規格の条文は次の通りです（「the implementation may assume any thread will eventually do one of the following: terminate, call a library I/O function, access a volatile glvalue, or perform a synchronization or atomic operation」）。すなわち、コンパイラは各スレッドが最終的に以下の4つの動作のいずれかに達すると仮定する権限を持っています。

  • スレッドの正常な実行終了（terminate）。
  • 標準ライブラリのI/O関数の呼び出し（call a library I/O function）。
  • volatile修飾されたglvalueメモリへのアクセス（access a volatile glvalue）。
  • 同期操作またはアトミック（atomic）操作の実行（perform a synchronization or atomic operation）。

原文は、セミコロン1文字で終わる while (true); 構文が上記の4つの動作のいずれも行わないという事実を指摘しています。ループ内にはI/O呼び出しも存在せず、volatileメモリアクセスもなく、アトミック同期も実行されず、正常終了に至る分岐もありません。原文の説明によると、コンパイラは前方進行規則に依拠し、このスレッドが無限に停止し続けることはなく最終的には終了すると前提を立てます。そしてループ実行に伴う観測可能な副作用が皆無であることから、ループを実行すること自体が無駄であると判断し、ループの条件判定とジャンプ命令をバイナリから完全に削除してしまうのです。

本稿の解釈では、進行保証規定が定めた4つの観測可能動作のいずれも行わないループについて、コンパイラが終了可能なものとみなして処理した結果です。

3. Clangにおけるループ除去事例とunreachableコードの実行

コンパイラがループを除去した結果、実際にどのような現象が発生するかを示すため、原文はClangコンパイラを用いた具体的なサンプルコードを提示しています。原文に掲載されたコードは以下の通りです。

// https://godbolt.org/z/WYMxxeW1T
#include <iostream>

int main() {
    while (true)
        ;
}

void unreachable() {
    std::cout << "Hello world!" << std::endl;
}

原文は、Clangコンパイラ環境でこのプログラムをコンパイルして実行すると、驚くべきことにコンソールに 「Hello world!」 という文字列が出力されると記しています。ソースコードのどこを見渡しても unreachable() 関数を呼び出す記述は存在せず、main() 関数の内部には単一の while (true); ループが置かれているだけです。それにもかかわらず、プログラムは呼び出されていないはずの関数へと侵入し、文字列を出力して終了します。

原文は、コンパイラが副作用を伴わないという理由で while (true); 無限ループを完全に削除し、その結果 main 関数の実行フローがループを素通りして関数の終端を突き抜けたと説明しています。そしてリンカがメモリ上で main 関数の直後に配置していた unreachable() 関数の先頭へと制御がそのまま落下（fall through）し、同関数の本体が実行されてしまったのだと原文は明かしています。

本稿の解釈では、ループが除去されたことで関数の制御フロー境界が失われ、メモリ上で直後に配置された関数が実行された形です。

4. C++26 P2809R3が定義する「自明な無限ループ」の要件

原文は、このような未定義動作の問題を解決するために規格へ正式に採用された提案がP2809R3提案であると明らかにしています。原文は、この提案の採択によってC++26から自明な無限ループが未定義動作ではなくなったと記しています。ただし原文は、この提案によって与えられる保護の範囲が極めて厳格かつ狭隘に定義されている事実を核心として強調しています。

原文が引用する提案書の定義条文は次の通りです（「The loop must be a trivially empty iteration statement — meaning its body is literally empty (`;` or `{}`). Any non-empty statement in the body, even a meaningless expression statement such as `"a string";`, disqualifies it. The controlling expression must be a constant expression that evaluates to `true`.」）。原文に明記された保護要件を整理すると、以下の厳格な条件に集約されます。

  • ループ本体は、文字通り完全に空の反復文（trivially empty iteration statement）でなければならない。
  • 許容されるループ本体の形式は、単独のセミコロン（;）または空の中括弧ブロック（{}）のみである。
  • 本体内に何ら効果のない無意味な式文（例："a string";）であっても存在すれば、直ちに保護資格を喪失する。
  • ループを制御する条件式（controlling expression）は、必ずコンパイル時定数式として true と評価されなければならない。

原文は、ループ本体が空でなければならないという規則がいかなる例外も認めない厳密な構文要件であると説明しています。たとえ実行時にレジスタを変更せず、メモリの読み書きも行わない無害な式であっても、構文的に本体が空でない限り、P2809R3が規定する自明な無限ループには該当しません。したがってそのようなループは、C++26においても従来と同様に未定義動作のまま据え置かれます。

本稿の解釈では、保護範囲が構文的に判別可能な空の本体形式に限定された点が本規則の核心です。

5. 構文形式別のC++26保護対象の対照

原文は、開発者が記述し得る多様な無限ループ構文を例に挙げ、C++26において公式に保護される形式と、依然として未定義動作として扱われ保護されない形式を明確な一覧表で対比しています。原文にまとめられた保護対象の比較結果は以下の通りです。

構文の形式 C++26における保護の有無 原文に基づく判定根拠および理由
while (true); 保護される 制御式が定数式trueであり本体が単独のセミコロンで完全に空である
for (;;); 保護される 制御式が省略されてtrueとみなされ、本体が完全に空である
do {} while (true); 保護される ループ本体ブロックが空の中括弧であり制御式が定数式trueである
constexpr bool go = true; while (go); 保護される constexpr変数はコンパイル時にtrueと評価され本体が空である
while (true) { "a string"; } 保護されない 副作用のない文字列リテラル文であっても本体が空でないため失格
while (true) if (done) break; 保護されない 条件分岐文が本体に含まれているため空の本体要件を満たさない
while (true) if constexpr (false) break; 保護されない 構文的にif constexpr文が本体に存在するため自明な空文ではない
bool done = false; while (!done); 保護されない 非constexpr変数のため制御式がコンパイル時定数式trueではない

上記の対照結果から明らかなように、C++26の保護対象となる構文は極めて限定的です。原文が強調する保護構文の特徴と実務上の留意点は次の通りです。

  • 標準的な3種類の空ループ記法である while (true);、for (;;);、do {} while (true); はいずれも完全に保護されます。
  • 条件変数を外部で宣言する場合でも、constexpr 修飾が付与されてコンパイル時に true と確定していれば対象に含まれます。
  • 本体内に "a string"; のような文を1行でも挿入した時点で自明なループの資格を失い、未定義動作となります。
  • 実行時変数の真偽値に依存するループ（while (!done);）は、本体が空であっても自明な無限ループとして保護されません。

本稿の解釈では、表で while (!done); が保護されないと分類されているように、本体が空であっても制御式が [intro.progress] に明記されたvolatileアクセスや同期操作、アトミック操作を伴わない通常変数である場合、コンパイラの最適化から保護されません。

6. 欠陥報告（Defect Report）採択と過去のC++標準への遡及適用

原文は、P2809R3提案の適用範囲に関して実務上きわめて重要な事実を伝えています。原文は、当該提案が標準化委員会によって欠陥報告（defect report）として公式に採択されたと記しています（「The mentioned proposal was also accepted as a defect report, so implementations may apply the fix to earlier C++ modes as well.」）。

原文によると、欠陥報告として承認されたことにより、コンパイラ実装者はこの修正をC++26モードだけでなく過去のC++モード（earlier C++ modes）に対しても同様に遡及適用することが認められます。したがって、最新世代のコンパイラを使用している環境であれば、ビルドフラグで古い言語規格を指定していても、自明な無限ループが最適化で消し飛ばされる過去の異常動作がもはや再現しなくなっている可能性があります。標準の変遷と欠陥報告の関係は以下の通りです。

標準規格区分 前方進行保証の規定状況 自明な無限ループ（while (true);）の扱い
C++11以降（前方進行保証の導入以降） [intro.progress] の進行保証仮定を適用 副作用のないループは未定義動作（UB）としてコンパイラ削除を容認
C11 (ISO C) 定数制御式ループの進行保証例外を明記 原文「C got this right」: 定数条件ループは規格上完全に保護
C++26 (P2809R3) 自明な無限ループに対する明示的免責を新設 空の本体と定数式trueの要件を満たす場合UBから除外、yield意味論を付与
過去のC++モード（遡及） 欠陥報告（Defect Report）の反映 コンパイラ実装の裁量により過去のC++モードでもループ削除を抑止

欠陥報告としての採択がソフトウェア開発エコシステムに与える実質的な影響は以下の通りです。

  • 過去のC++モードでコンパイルする場合でも、ツールチェーンが新しければ自明な無限ループが保護される道が開かれました。
  • 原文が明記している通り、過去のモードへ適用するかどうかは各実装の裁量に委ねられているため、ツールごとの挙動確認が必要です。
  • 既存のレガシーコードベースで while (true); を使用しているプロジェクトが、過去の言語モードのままでも恩恵を享受できます。
  • 本稿の解釈では、実装者が過去のC++モードにおいても自明な無限ループを保持できる公式な根拠が整ったことが欠陥報告採択の意義です。

原文は、実装によって過去の言語モードでも本修正を適用できる裁量があることを明記しており、開発者が使用するツールの実装状況を確認する必要性を示しています。

7. 組み込みのhalt-on-errorパターンと自立型実装におけるyieldの懸念

原文は、自明な無限ループが使用される代表的な事例として、組み込みシステムやOSカーネルにおける「halt-on-errorパターン」を挙げています。原文の説明によると、OSが存在せず終了先がない場合、プログラムは単に停止します（原文： 「there's no operating system to exit to, you simply stop」 ）。原文はこうした状況の例としてハードウェア初期化失敗（hardware_init_failed()）を挙げ、致命的エラーの後にシステムを停止させる目的で空ループが用いられると記しています。

原文は、もしコンパイラがこのループを除去してしまった場合、プログラムが意図された停止状態を維持できずにループを突き抜けてしまうと説明しています。原文は、P2809R3がこうしたシステムプログラミングの要請に応え、空ループの保持を保証するために導入されたと説明しています。

しかし原文は、自立型（freestanding）環境において標準が定めた代替機構に関して懸念を記しています。標準提案では、自明な無限ループが前方進行保証に違反しないようにするため、当該ループを意味論的に std::this_thread::yield() 呼び出しに置き換える方式を採用しました。原文は、自立型実装に関して以下のようなただし書きが存在すると記しています（「it is implementation-defined whether the replacement with `std::this_thread::yield()` occurs at all」）。すなわち、自立型環境においてこの置き換えが実際に行われるかどうかは実装定義（implementation-defined）事項です。

原文は、意図的な停止ループを協調的譲歩へと変えることが、プログラマが意図しなかった動作を招く恐れがあるという懸念を記しています（「turning a deliberate halt loop into a cooperative yield could introduce behaviour the programmer never intended」）。自立型環境に関して原文が挙げている事項は以下の通りです。

  • 自立型実装では、std::this_thread::yield() への置き換えが実際に行われるかどうかは実装定義（implementation-defined）事項である。
  • 意図的な停止（halt）ループを協調的譲歩（yield）に変えることは、プログラマが意図しなかった動作を招く恐れがある。
  • 原文は協調的譲歩が引き起こし得る具体的な誤動作シナリオについては言及していない。
  • 本稿の解釈では、自立型環境において実装定義とされたyield置換の有無を対象プラットフォームごとに検証することが実務上必要である。

原文はこうした懸念を理由として、自立型環境で自明な無限ループを扱う際にはコンパイラの実装定義の挙動に注意を払う必要があると説明しています。

8. C11との比較およびC++標準委員会の選択

原文は、無限ループの未定義動作問題を扱うにあたり、先行するC言語の歴史的な対応を比較対象として取り上げ、「C got this right」と評価しています。ISO C規格委員会は、C11の改定時に前方進行規則を導入した際、制御式が定数式である無限ループについては進行保証仮定の例外とすることを明記し、コンパイラが勝手に削除できないよう保護しました。

原文は、C++標準委員会の内部でもC11が採用した方針をそのままC++へ導入する案が検討されたものの、最終的に棄却されたと記しています（「considered and rejected」）。C11の方針をそのまま適用した場合、制御式さえ定数であれば本体にコードが含まれていても未定義動作として扱えなくなります。原文の説明によると、この広範な免責はC++コンパイラの高度な最適化器に対して過度な制約（optimizer constraints）を課すことになるため拒絶されました。

結果としてC++委員会は、C11よりもはるかに狭く限定的な妥協案を選択しました。ループ制御式が定数式の true でなければならないだけでなく、ループ本体がセミコロンまたは空ブロックで完全に空でなければならないという厳しい追加条件を課したのです。C言語との対比およびC++規格の設計判断は以下の通りです。

  • C11は定数制御式を持つ無限ループ全般を進行保証の例外として認め、比較的広い範囲を保護した。
  • C++委員会はC11の規則をそのまま持ち込むと最適化器の解析機能が過度に制約されると判断し、これを棄却した。
  • C++26はループ本体が完全に空でなければならないという強力な制限を設けることで、最適化の自由度を最大限に保つ狭い道を選んだ。
  • 本稿の解釈では、C++が最適化性能を維持するため、C11よりもはるかに狭い空本体ルールを採用した形である。

原文は、C言語とC++が無限ループを異なる方針で規定しており、C++26の改定もC11の全面保護とは一線を画す独自の妥協案であることを強調しています。
