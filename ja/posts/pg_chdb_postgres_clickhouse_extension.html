何のための拡張か — 外部データを PostgreSQL の中へ

運用データベースが PostgreSQL で、分析用の元データは S3 に Parquet として積み上がっている構成はよくある。二つの世界をつなぐ方法は昔からいくつもあった。外部データラッパー（FDW）を入れる、別の ETL ジョブで CSV を落として COPY で入れる、あるいは分析エンジンを別に立てる。それぞれ導入の難しさ、フォーマット対応、速度で違う代償を払う。

pg_chdb はこの場所に ClickHouse が出した答えだ。核心のアイデアは、組み込み ClickHouse エンジンである chDB を PostgreSQL のプロセスの中で実行することである。外部ファイルを読み、解析し、形式を変換する仕事は ClickHouse がもともと得意とするところで、その結果を PostgreSQL のテーブルへ流し込む接点だけを拡張が担う。リポジトリの一行説明は「chDB クエリを実行し、外部ソースのデータを PostgreSQL テーブルにコピーする PostgreSQL 拡張」である。

この記事は README が明かした範囲内でこの拡張の構造、対応範囲、導入、性能数値、制約を整理し、最後に既存の選択肢と比べてどの場所に合うかを判断する。ライセンスは Apache-2.0 で、2026年9月15日時点のリポジトリはスター16、コミット84、オープンな Issue 4である。成熟したプロジェクトではなく初期のプロジェクトだという点を先に記しておく。

二つの部品 — chdb_query() と chdb_hook

拡張は二つの部品からなる。役割が違うので別々に見る。

  • chdb_query() 関数。文字列で受け取った ClickHouse SQL を chDB エンジンで実行し、結果を PostgreSQL の行集合として返す。ClickHouse のテーブル関数（s3() など）をそのまま使えるので、外部ファイルがそのままテーブルになる。返す列の型は呼び出し側で AS (…) として宣言する。
  • chdb_hook モジュール。LOAD 'chdb_hook' で読み込むと COPY … FROM 命令を横取りする。FROM の後にローカルパスの代わりに S3 のような外部 URL を書くと、フックが chDB でファイルを読んでテーブルに取り込む。既存の COPY 構文をそのまま使い、ソースだけを外部に変えるわけだ。
  • 二つの分業。照会だけなら関数、テーブルへの永続的な取り込みが必要ならフックだ。拡張はファイル URL だけを渡せば列構造を推論してテーブル作成と取り込みを一度に処理する経路も提供する。

設計上注目すべき点は、拡張が新しい SQL 構文を作らなかったことだ。関数呼び出しと COPY という PostgreSQL の既存構文二つの上に乗せた。学習コストが低く、既存のツールチェーン（psql スクリプト、スケジューラ）にそのまま入る。

軸README が明かした対応範囲

フォーマット一覧が広いのは拡張の功績ではなく chDB の功績だ。ClickHouse が入力フォーマットとして対応するものをそのまま受け継いだ。裏返せば、この一覧にあるフォーマットでも PostgreSQL 側の型に写す過程でどんな損失があるかを README は扱っていない。日付・タイムゾーン・小数の精度のように二つのエンジンの型体系が食い違う場所は、実際に入れてみるまで分からない。

導入 — PostgreSQL 15、chDB 26.7、Linux・macOS

  • PostgreSQL 15 以上。14 以下は対応リストにない。
  • chDB v26.7.0 以上。拡張とは別に先に導入する。README が案内する方法は curl -sL https://lib.chdb.io | bash だ。リモートのスクリプトをパイプで実行する方式なので、本番サーバではスクリプトを落として内容を確認してから実行するのが筋である。
  • Linux と macOS のみ。ソースビルドで導入し、Windows はリストにない。
  • ビルド順序。make → make installcheck → make install。gmake を使うシステムや pg_config のパスが違う環境は env PG_CONFIG=/path/to/pg_config make の形で指定する。

導入要件で実務的に引っかかるのは chDB への依存だ。組み込みエンジンなので PostgreSQL のプロセスの中に ClickHouse のランタイムが入ってくる。メモリ使用量とライブラリの衝突は README にない項目で、本番インスタンスに入れる前に別のインスタンスで測るべき対象である。

使用例 — 直接照会と COPY 取り込み

README の最初の例は S3 の CSV を関数で直接読むものだ。ClickHouse SQL をドル引用（$$ … $$）で囲んで渡し、返す列を宣言する。

SELECT * FROM chdb_query($$
                      SELECT * FROM s3('s3://bucket/file.csv')
                    $$) AS (id int, months int, days int);

二つ目の例はフックを読み込んだ後、COPY で複数ファイルを一度に取り込むものだ。グロブパターンで接頭辞二つと番号1〜3の組み合わせ、つまり六つのファイルを一文で指定する。

LOAD 'chdb_hook';
                    COPY times FROM 's3://bucket/{prefix1,prefix2}/file_{1..3}.csv';

二つの例の違いがそのまま使い方の違いだ。最初のものは結果を PostgreSQL の中に残さない一回限りの照会で、二つ目はテーブルに取り込む。スキーマ推論の経路を使えばテーブルを事前に作る必要もないが、推論された型が意図と違うことがあるので、本番テーブルには明示的なスキーマを置いて取り込むほうが安全である。

性能 — 100万行の実測で pg_duckdb・pg_lake より2〜3倍速い

README は NYC タクシーデータ約100万行を基準に、競合する拡張と取り込み時間を比較した。原文が明かした結果は次のとおりである。

比較対象README の記述
chdb_hook（pg_chdb）最も一貫した性能
pg_duckdb・pg_lakeCSV・JSON・Parquet の取り込みで2〜3倍の時間
aws_s3chDB の性能に迫るが、対応フォーマットがはるかに限られる

この数値を読むときは二つを一緒に置かなければならない。第一に、測定主体がプロジェクト自身である。ベンダー自身のベンチマークは方向を教えてくれるが大きさは保証しない。第二に、ハードウェア・ネットワーク・ファイルサイズ・競合拡張のバージョンといった条件が README にない。100万行という規模は分析ワークロードとしては小さいほうで、数十 GB 単位で同じ倍率が保たれるかは別の問いだ。

ただし方向自体はもっともらしい。ClickHouse の入力パーサーは列指向フォーマットを大量に読むために長く最適化されてきたし、組み込み実行はネットワークの往復をなくす。「速い理由がある」と「この倍率が自分の環境でも出る」は別の文であり、後者は自分のデータで測らなければならない。

制約 — クエリごとに完全に隔離される

README が既知の制約として明記したのは一つだ。各クエリが他のすべてのクエリから完全に隔離されて実行される。原文の表現は「テーブルを作って次のクエリでそれを照会できると期待しないこと」である。

  • chDB 側の状態は保持されない。chdb_query() の中で作った一時テーブル、設定、ビューは呼び出しが終わると消える。複数段階に分けた変換は一回の呼び出しの SQL にまとめるか、中間結果を PostgreSQL のテーブルに落として次の段階に渡さなければならない。
  • PostgreSQL 側の状態は正常だ。隔離は chDB の実行に関するものである。COPY で取り込んだテーブルは当然残る。
  • 設計上の帰結である可能性が高い。呼び出しごとにきれいなエンジン状態から始めれば、同時呼び出し間の干渉がなく資源の回収が単純になる。状態保持が必要なワークロードには不便だが、取り込みツールとして使う限り大きな問題ではない。

どこに使い、どこに使わないか

  • 合う場所 — 複数フォーマットの外部ファイルを定期的に PostgreSQL に取り込むパイプライン。Parquet・ORC・Avro が混ざって入ってくるデータレイクから COPY 一文で取り込むのが、この拡張の本領である。
  • 合う場所 — 分析エンジンを別に運用する余力のないチーム。別の ClickHouse クラスタなしに、PostgreSQL の中で ClickHouse のパーサーを使う。
  • 合わない場所 — 多段階の変換を chDB の中でつなげようとするワークロード。クエリの隔離のため中間状態が残らない。
  • 合わない場所 — Windows サーバ、PostgreSQL 14 以下。対応リストの外だ。
  • 合わない場所 — 検証なしに本番インスタンスへ直接載せること。スター16・コミット84の初期プロジェクトで、組み込みエンジンのメモリ・安定性は README にない項目である。別インスタンスで自分のデータで測る段階が先だ。

確認できなかったこと

  • ベンチマークのハードウェア・ネットワーク・ファイルサイズ・競合拡張のバージョン。README にない。
  • chDB エンジンが PostgreSQL プロセスの中で使うメモリ上限と、同時呼び出し時の挙動。
  • ClickHouse の型から PostgreSQL の型への写像規則と損失の有無（タイムゾーン・小数・ネスト構造）。
  • S3 の認証情報をどう渡すか — README の例には認証部分がない。
  • pg_duckdb・pg_lake・aws_s3・FDW の現在の機能範囲。README の比較文脈の外である。
  • プロジェクトの保守計画とリリース周期。
