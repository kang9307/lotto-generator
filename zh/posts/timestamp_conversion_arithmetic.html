「把除法换成乘法」编译器早就在做 - 时间戳转换中人手真正能赢的三个位置，以及它的代价

新的不是乘法，而是定义域、重排与恒等式这三种信息

2026-09-09 开发/基础设施

讲算术优化，几乎总会出现同一句话。除法很贵，所以换成乘法。这句话没错。但只把这句话搬走，最要紧的东西就掉了。只要除数是编译期确定的常数，这个替换早就已经发生了。主流编译器在那个位置并不发出除法指令。

那么人手写的优化究竟赢在哪里。这才是一个窄得多、也有用得多的问题。答案不在乘法，而在信息。编译器缺的不是能力，而是关于输入实际会走到哪里的知识、把式子摆成什么形状的选择，以及只在这个位置成立的代数恒等式。

把时间戳拆成时、分、秒的代码，几乎是检验这条界线的理想对象。除数是 60 和 3600 这两个常数，输入的定义域有限，而给出正确答案的朴素实现三行就写完。也就是说，哪些是编译器的份、哪些是人的份，以及人这一份押了多少担保，全都数得出来。

本文没有周期数和延迟数值。那些值随微架构、操作数宽度和编译器版本而变，剥掉条件的数字每被转述一次就更假一分。这里写的是性质、条件与验证方法。属于你环境的数字，只能从你的环境里出来。

起因 - 把一天的秒拆成三份的代码

要处理的问题很窄。接收一个从午夜起流逝的秒数，给出时、分、秒三个值。不涉及日期。除去闰秒，输入是 0 到 86,399，输出不超过 23:59:59。

解这个问题的教科书写法有两种形状。两者给出同样的答案，但式子之间的依赖关系不同。

/* 顺序式 - 每一步都要等前一步的结果 */
unsigned hour   = t / 3600;
unsigned rem    = t % 3600;
unsigned minute = rem / 60;
unsigned second = rem % 60;

/* 独立式 - 三个值分开求。代价是除法变多 */
unsigned hour   = t / 3600;
unsigned minute = (t / 60) % 60;
unsigned second = t % 60;

顺序式的运算数少，但链条被串成长长的一条。rem 出来之前动不了 minute，minute 出来之前做不了最后那个减法。独立式切断了链条，代价是同一个除法要做好几遍。减少运算数和切断链条在往相反的方向拉，这一点决定了这个问题的性格。

到这里都是老话题。新提出来的是这样一个观察：存在既切断链条又不增加运算数的摆法，以及把取余运算本身换掉的两种手法。这些手法各自落在哪个格子里，才是本文的正题。

为什么只有整数除法不一样

加法、乘法和除法都被归进算术运算，但它们在硬件上的性格不同。除法贵，是因为它不是一次性给出结果的电路，而是逐位确定的迭代结构。要定下商的某一位，它上面那一位必须先定下来。

这个性质带来三个结果。

  • 难以完全流水化。加法器或乘法器可以在前一个运算结束之前就把下一个灌进去。带迭代内核的电路没法那么自由地叠，于是一串除法就会互相等待。
  • 代价不是固定值。同一条指令，有的实现会随操作数宽度、甚至随实际数值的大小而花更长时间。32位除法和64位除法的价签并不相同。
  • 各架构的情况不同。有的指令集根本没有整数除法指令。在那里除法变成库调用，代价就不再是一条指令的事。

第三点最常被忘掉。除法很贵这个命题，并不是在每块芯片上都同等为真。所以这个话题里的任何数值，都不该脱离条件被搬走。

最后一行是下一节的前提。除法贵这个事实本身构不成优化的依据。只有当那个除法真的还留在机器码里时，它才是依据。

常数除数早就被编译器换成了乘法

这里是本文的心脏。很多人相信写下 t / 3600 就会往机器码里塞一条除法指令，而大多数时候并不会。

原理很简单。除以某个常数 D 等同于乘以 1/D。整数运算里没有小数，于是改成乘一个把 1/D 放大若干个 2 的幂之后的近似常数，乘完再把放大的位数移回来。这就是定点倒数乘法，针对不变除数的这个变换在1990年代被整理出来，成了编译器优化的标准条目。

造常数的规则同样简单。宽度为 b 位时，乘数是 2b 除以 D 的商再加一。时分秒转换里出现的常数，正是从这条规则里出来的。

  • 71582789 — 232 除以 60 的商再加一
  • 1193047 — 232 除以 3600 的商再加一
  • 2443359173 — 243 除以 3600 的商再加一
  • 37283 与 2185 — 分别是 227 除以 3600、217 除以 60 的商再加一

要紧的是这些常数不是手工发明的值，而是规则的输出。编译器也用同一条规则造自己的常数。只是编译器要背着一个人没有的不利条件去算。它必须在整个类型范围内都正确。如果输入是32位无符号整数，它就得挑一个从 0 到 4,294,967,295 全都成立的乘数和移位宽度，于是用上了比人所需更宽的中间宽度。

这个约束为什么解不开，也很清楚。编译器看到的是那个变量的类型，而不是那个变量实际装过什么值的履历。单看一个函数，无从知道实参会是什么；即便能看到全部调用方，也得一路追到调用这些调用方的地方，范围才定得下来。所以编译器永远往安全的一侧留足余量。这不是它偷懒，而是它必须正确，而人能赢的位置之所以出现，理由恰好相同。

不过编译器做什么和不做什么，这条界线比想象中更尖。引出本文的那篇文章，作者的观察是这样的。两个被广泛使用的编译器会把 t / 60 / 60 合并成 t / 3600，但只有当代码用减法和乘法而不是取余算子写出来时才这么做。另一个编译器在所试的全部情形里都没有做这项优化，而某个运行期编译器根本认不出重排之后的式子形状。

也就是说，同一份源码换个工具就变成另一个程序。作者本人的结论也是如此：这个做法依赖编译器聪明，而那并非总能成立，所以把它写成人直白重排后的形式更为可取。

作者还写道，理想情况下编译器应该替我们把这一切办掉，并补充说只要有一个关于有效输入范围的提示，编译器就能把余下的事做完。可那个提示并不是标准化的契约。GCC 文档把表示不可达的内建函数仅仅规定为控制流一旦到达该点程序即为未定义的标记，并没有写它是传达取值范围的手段。存在一个被广泛使用的惯用写法，和文档给出保证，是两回事。

那么人能赢的位置在哪里

把上一节倒过来，答案就出来了。编译器缺的不是算术能力，而是信息。人能卖出的信息只有三样。

  • 定义域 — 输入实际上只会落在窄得多的范围里这个事实。一天的秒数只有 86,400 种。编译器无从得知，只好发出适配整个类型的代码。人则可以写出只在窄范围内正确、但更短的代码。
  • 重排 — 把式子摆成三个结果互不等待的样子。数学上是等价的，因此没有风险，但哪个编译器认得出这个等价则各不相同。也就是说，人在这个位置赢，靠的不是数学而是工具之间的偏差。
  • 恒等式 — 只在这个问题里成立的代数真相。把取余变成位掩码的变形就属于这一类。编译器没有理由知道这类真相，也没有理由必须知道。

三者性格互不相同，这一点很重要。重排是白得的。式子等价，所以任何输入下答案都不变。而定义域和恒等式则要押担保。它们只在今后进入那个函数的值遵守约定的条件下才正确。那个约定没有写在代码里，通常只存在于某个人的脑子里。

于是实务中的次序分开了。重排可以先做，定义域和恒等式等到有理由去测量之后再做。不是因为前者可逆而后者难逆，而是因为后者会给未来的调用方寄账单。

按这个标准给原文的手法分类

引出本文的那篇文章给了三种形状。把它们分别放进上面三个格子，就能分清什么是新的、什么是本来就有的。

第一种 - 纯粹的重排

/* 让两个除法互相独立，其余用乘法和减法补上 */
unsigned tmin   = t / 60;      /* 从午夜起的总分钟数 */
unsigned hour   = t / 3600;
unsigned second = t - tmin * 60;
unsigned minute = tmin - hour * 60;

没有常数，也没有魔法。两个除法互不等待，等它们出来，剩下两个值各用一次乘法和一次减法就完事。作者形容这个形状是不会立刻想到的摆法，因为分现在完全由两个中间结果算出，而不是直接从时刻算出，这个判断很准确。人通常都想把每个输出直接从输入推出来。

这个形状的价值在于它一个假设都不带。任何输入下都和朴素实现给出相同的答案。它是这里唯一不押担保就能拿到的改善。

第二种 - 靠收窄定义域换来的定点

/* 32位定点。高半部是商，低半部是到下一整数步的进度
     1193047  = (2^32) / 3600 + 1
     71582789 = (2^32) / 60   + 1                        */
uint64_t hprd = (uint64_t) t * 1193047u;
uint32_t hlow = (uint32_t) hprd;
uint32_t mlow = (uint32_t) ((uint64_t) t * 71582789u);

unsigned hour   = (unsigned) (hprd >> 32);
unsigned minute = (unsigned) (((uint64_t) hlow * 60) >> 32);
unsigned second = (unsigned) (((uint64_t) mlow * 60) >> 32);

思路是这样。乘上乘数得到的64位结果里，高半部就是商，低半部则是表示距离下一个整数步走了多远的小数部分。把那个小数部分乘 60 再取高位，剩下的分或秒就出来了。这等于不另外求余，而是把一次已经算过的乘法中被丢掉的那一半回收利用。

代价是定义域。在32位宽度下这套计算成立有个上限，越过之后答案就变了。作者给出的有效范围是 0 到 2,255,818。这比一天的秒数宽得多，对原本的用途绰绰有余，但那个上限在代码里哪儿都没写。

第三种 - 把取余变成位掩码的恒等式

/* 恒等式:  x mod D  ==  (x + c*(x/D)) mod (D + c),   这里 c = 4  */
/* 60 加 4 等于 64，于是取余运算变成了 & 63                       */
uint32_t tmin = (uint32_t) (((uint64_t) t * 71582789u) >> 32);
uint32_t hour = (uint32_t) (((uint64_t) t * 1193047u)  >> 32);

unsigned second = (t    + 4 * tmin) & 63;
unsigned minute = (tmin + 4 * hour) & 63;

求对 60 取余时，把商乘四加上去，再对 64 取余，得到的是同一个值。64 是 2 的幂，于是那个取余就是保留低六位的一次掩码。而 x + 4*y 这个形状在两大主流架构上都能用一条指令表达，一边是地址计算指令，一边是带移位的加法。

这个恒等式并非对任意值都成立。它只在商与余数保持特定关系的范围内为真，作者给出的那个范围是 0 到 2,257,198。它与前一种手法的上限不同，这一点在后面变得重要。

竖着读这张表，结论就出来了。「把除法换成乘法」不是人能赢的位置。那个座位早就被占了。人赢的是下面四行，而其中不带假设就赢的只有重排这一行。其余全都是押上定义域这份担保才拿到的。

最后一行值得单独看。用到向量指令时，把中间结果加宽到64位，一个向量里能装的值的个数就变少。所以在向量路径上，更窄的常数反而胜过更准确的常数。用窄乘数会让有效范围大幅缩水，换来的是通道保住了。反过来，在向量宽度更大的架构上，作者写道前面那些形状又赢了回来。同一份代码在哪个架构上最优，并不是一个固定的排名。

代价 - 押上去的是什么

把优化的代价只当成速度的反面，就丢掉了一半。这里付出去的东西，多半是将来才会被索账的条目。

代价具体是什么何时被索账怎样预先挡住
定义域假设窄宽度乘数在上限之上给出不同的值那个函数被挪去别的用途时把有效上限钉进函数名和注释，并加上范围断言
中间值的宽度乘上乘数之后的值需要有地方装移到32位目标时，移进向量代码时用类型写明中间宽度，并在那个宽度上做全量比对
可移植性宽乘法的高半部是否廉价，各架构不同移植到别的芯片时把朴素实现留作备用路径，构建时择一
读者的验证成本掩码为何等于取余，光看代码分辨不出来每次要改那段代码时把恒等式和有效范围留在注释里，测试放在旁边
对工具的依赖同一份源码在不同编译器下变成不同的机器码换工具链或优化级别时对每个目标工具链重新看机器码与测量

第四行最被低估。让读者无法验证，同样是一种成本。朴素的代码错了，眼睛看得见。由掩码和乘数拼出来的代码错了也看不见，于是想改它的人要么不敢碰，要么碰了之后自己也说不清。这份成本不是一次性的，而是在那段代码活着的整个期间反复被索取。

同样性格的账单在别处也有。把预算压到极限的实现里，删掉一个数据结构，那个结构悄悄在做的校验也会一起消失，这个结构在把解释器塞进 1,024 字节的尝试里显得更鲜明。删掉的是一样，失去的是两样，这一点是相同的。

越过范围的第一个值上会发生什么

定义域假设的危险，如果只留成一句抽象的话，是没有实感的。定义域有限，所以越过声明上限的下一个值上会发生什么，可以照样数出来。而且各手法的结果并不相同。

手法声明的上限上限的下一个值真值该手法给出的值失败的性格
窄宽度定点2,255,8182,255,819626:36:59626:37:59安静。三个字段都是合法值，断言抓不到
取余换成位掩码2,257,1982,257,199626:59:59627:63:59看得见。分位是 63，一条范围断言就能抓住
为保住通道的窄乘数比一天略宽一点115,20032:00:00另一个值上限低得多。挪去算经过时间会很早撞上

第二行和第一行的差别，就是实务中分道扬镳的地方。分位出现 63 的失败一定会在某处被拦下。显示代码想补齐两位时会出怪样，校验器会退回，至少人在屏幕上能看出来。反过来，分位差了一的时刻会原样写进日志、原样存下、原样被汇总。两者破坏的是同一类假设，被发现的时间却差了几个月。

由此得出一条实务规则。假设了范围的函数，就该把那个范围写成断言。知道优化成立上限的人如果不把那个上限留在代码里，这份知识会在他离开团队的那一刻消失。不把值和附在值上的条件一起写下来，日后掉下来的总是条件。

第三行展示的是复用的陷阱。拆时刻的函数会让人很想直接拿去拆经过时间，因为形状一模一样。可按一天的秒数为前提挑出来的常数，在跨越数天的经过时间上会垮掉。处理经过时间时时钟本身已经带着哪些陷阱，另外整理在分开单调时钟与墙上时钟的那篇里。

要让变快了这句话成立

速度主张只有附上条件才成为命题。不带条件被搬走的倍数，传到下一个人手上时多半已经是假的。至少要有四样东西同行。

必须具备的缺了会怎样具体形式
正确性比对又快又错的代码被叫作快把整个定义域与朴素实现比对。定义域有限，所以用全量而不是抽样
机器码比对分不清除法是只从源码里消失了，还是从机器码里也消失了用编译器浏览器或反汇编看有没有除法指令，且按优化级别分别看
写明环境复现不出来编译器与版本、优化开关、目标架构、操作系统
区分测量轴嘴上说测延迟，手上测的是吞吐测延迟时把前一个结果喂回下一次计算的输入，挡住并行执行

最后一项在这个话题上最常塌。在循环里反复跑互相独立的计算，执行单元会把它们叠起来处理。那种状态下出来的数值，不是一次运算做完要多久，而是单位时间里能做完几个。这两个值可以往相反的方向动。切断链条的优化在延迟上能大赚，在吞吐上却可能只赚一点，甚至反而亏。

引出本文那篇文章的测量方式明确处理了这个区分。测延迟时把前一个结果用异或喂进下一次计算以挡住并行执行，吞吐则另外测。随机值预先装进内存，跑若干次后取中位数。向量路径上尝试自动向量化，作者写道一个编译器生成了向量代码，另一个没有。说的是同一份源码。

测量用的机器有三种：较新的笔记本级处理器、桌面级高性能处理器，以及一块32位小板子。放进最后那一种，在方法论上分量很重，因为在无法廉价取得64位乘法高半部的环境里，排名会变。不摆开这三条轴去测，只适合自己环境的结论就会被当成一般命题搬走。

介绍原文的那个论坛上有一条简短的反馈，说在另一种语言里试过，编译器优化把差别抹平了。因为没有写条件，那条反馈本身不能当作事实来处理，但方向和上一节一致。哪个工具替你做了什么，这件事会把结果整个翻过来。

定义域有限意味着什么

这个话题有一个多数优化都没有的性质。输入是有限的，而且小到数得过来。一天的秒数是 86,400 种。前面出现的扩展范围也只是数百万种的量级。也就是说，可以做的不是抽样验证，而是全量比对。

/* 定义域有限，所以能比对全部而不是抽样 */
for (uint32_t t = 0; t <= LIMIT; t++) {
    hms fast = fast_hms(t);
    hms ref  = { t / 3600, (t / 60) % 60, t % 60 };   /* 朴素实现就是标准答案 */

    if (fast.h != ref.h || fast.m != ref.m || fast.s != ref.s) {
        printf("first mismatch at %u\n", t);
        return 1;
    }
}
/* 把 LIMIT 取得比声明范围宽裕不少，好连边界外一步是怎么错的
   也一并看到。只在通过的范围里绕圈的测试，说明不了这个函数
   能不能被复用。 */

这个性质把验证的标准整个抬高。在有限的定义域上，只跑抽样就说它对，是在自降依据。引出本文的那篇文章在这一点上很明确。仓库里写着测试会把每个算法的有效范围整个与朴素实现比对，而对处理闰秒的变体，作者自己写道并没有数学证明，只是在一天的范围内做了全量比对。

留下没有证明这句话，是这篇文章里最值得学的地方。全量比对不是证明。在有限的定义域上两者实质相同，可一旦定义域变了，比对就什么都不保证。给自己标出那条边界的代码，和没标的代码，复用时的安全性不一样。

验证的次序也有规则。先验证再改值，验证之后不再改。放进优化路径的同时又去动输入的归一化，就分不清原因在哪一边。这个次序被颠倒时什么会失效，整理在讲归一化与验证次序的那篇里。

划算的位置与不划算的位置

同一个优化在有的代码里有意义，在另一些代码里没有。分开它们的不是手法有多优秀，而是那段代码被调用多少次。

划算的位置是这些。

  • 日志格式化 — 每行都打时间。每秒写几万行的系统里，这个转换会成为日志路径上的常数开销。
  • 时间序列的批量转换 — 把数百万行时间戳变成人能读的形式的批处理。同一个函数按行数被调用。
  • 渲染与序列化 — 一张表里打几万个时刻的情形。被调用的次数远多于屏幕上看得见的，这很常见。

不划算的位置是这些。

  • 每个请求只调几次的路径 — 拿到的收益比测量误差还小。在这种地方把朴素代码换成掩码和乘数，剩下的只有成本。
  • 本来就堵在别处的路径 — 在等存储或等网络的代码里削减算术，只会让等待变长。
  • 转换之后那一段更重的路径 — 求出时分秒之后，还要把数字变成字符写进缓冲区。如果那一段更大，削减前面这一段，整体几乎不动。哪一边更大，不测就分不出来。

第三项在这个话题上尤其常被绊住。看把时刻变成字符串的整个函数，除法只是其中一部分。要说优化了一部分而整体变快了，就得测整体。

而且处理时刻的代码里，往往还有排在算术开销之前的问题。同一个秒值在哪个时区、按哪套规则被解释，会改变结果，而那套规则是以数据而不是代码的形式更新的。时区数据更新连过去时刻的解释都会改变的那件事就是这条轴。挪到星期或日期上，计算的性格本身就变了，那一侧另外放在把日历搬进代码这件事里。

先测量，再动手

把次序理一理，是五步。这不是手法清单，而是判断的次序。

  • 第一，测一下那条路径是不是排在前面。去修一个在剖析结果里都不显眼的函数，那不是优化而是爱好。跳过这一步，后面四步全是浪费。
  • 第二，看机器码里还有没有除法。如果没有，这个位置上要做的事早就做完了。除数是常数的话，多半到这里就结束。
  • 第三，先套用不带假设的改善。也就是切断依赖链的重排。它不押担保，所以就算要回退也不损失什么。
  • 第四，还不够就去挖定义域。从这里起要押担保，所以要把有效范围写进代码，并把全量比对一起放进仓库。没有测试就塞进去的窄常数，是一个定了期限的缺陷。
  • 第五，再测一次。在同样的条件下比较前后，并把延迟和吞吐分开看。没有这一步，前面四步只是把代码弄难了而已。

这个次序里最常被省掉的是第二步。除法很贵这个知识流传得很广，而去看一眼那个除法是不是已经消失了的习惯却没有那么普及。于是人们把编译器早就做完的事再做一遍，代价是新背上一份定义域假设。

归结起来是这样。引出本文的那篇文章真正展示的，不是乘法比除法便宜这件事。它展示的是人胜过编译器的唯一一点，在于握有没写进代码里的信息，以及用上那份信息的同时，也就一并生出了把它写进代码的义务。不写下来，那个优化对下一个人来说就是一枚定时装置。

没能确认的部分

  • 周期数、延迟与吞吐的数值 — 没有比对厂商的优化手册，所以一个数字都没有用。只留下了整数除法比加法或乘法贵、且这份开销随架构与操作数宽度而异这样的定性表述。
  • 生成的机器码 — 没能把各个形状真的编译一遍看看出来什么指令。关于编译器如何处理常数除数的表述，依据的是广为人知的变换规则和引出本文那篇文章里的观察。在自己的工具链上会怎样，只有在那里编译一次才分得出来。
  • 原文基准测试的复现 — 没能把仓库构建起来跑一遍看是否出同样的数值。文中关于测量条件的表述，是把原文给出的方法论搬过来的。
  • 给出范围提示的标准手段 — 把取值范围告诉编译器有一种被广泛使用的惯用写法，但 GCC 文档对那个内建函数的规定只到不可达标记为止。近年标准里加入的假设属性是否真的能引出这类优化，没能比对。
  • 闰秒变体成立的依据 — 引出本文那篇文章的作者本人写道，他并没有那个算式的形式化证明，只是在一天的范围内做了全量比对。本文也没有主张超出这个范围的东西。
  • 在别的语言与运行环境下的复现 — 论坛上有一条简短的反馈，但没有写编译器版本、开关和测量方式，所以没有当作依据使用。
  • 这个转换在真实系统里占多大比重 — 在日志格式化或时间序列转换的路径上，这个函数占整体的几成，因系统而异，没有依据给出一个通用值。所以文中只写了测量这个比重的次序。
