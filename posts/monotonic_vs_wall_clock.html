경과 시간을 벽시계로 재면 음수가 나온다 - 단조 시계를 써야 하는 자리

두 시계가 답하는 질문이 다르다 - 「지금 몇 시인가」와 「얼마나 지났는가」

2026-07-30 개발/인프라

서론: 처리 시간 로그에 음수가 찍혀 있었다

어느 아침 대시보드에 duration_ms: -2760 이 떠 있다고 해 보자. 요청 하나가 마이너스 2.7초 동안 처리됐다는 로그다. 코드를 열어 보면 아무 문제가 없어 보인다. 시작할 때 시각을 찍고, 끝날 때 또 찍고, 뺀다. 이보다 단순한 계산이 없다.

그런데 그 단순한 계산이 가정 하나에 기대고 있다. 두 번째로 읽은 시각이 첫 번째보다 반드시 크다는 가정이다. 벽시계는 그것을 보장하지 않는다. 그 사이에 누군가 시계를 고쳤을 수 있다.

이 글의 결론은 「단조 시계를 쓰세요」가 아니다. 그런 조언은 규칙으로만 남고, 규칙은 잊힌다. 대신 이렇게 정리하겠다. 두 시계는 서로 다른 질문에 답한다.

  • 벽시계(wall clock)는 「지금 몇 시인가」에 답한다. 사람이 읽는 시각이고, 다른 기계와 비교할 수 있는 시각이고, 달력에 표시할 수 있는 시각이다. 그 대가로 외부에서 고쳐질 수 있다
  • 단조 시계(monotonic clock)는 「얼마나 지났는가」에 답한다. 기준점이 임의라 그 값 자체는 아무 뜻도 없다. 두 번 읽어 뺀 차이만 뜻이 있다. 그 대가로 아무도 되돌릴 수 없다
  • 그래서 벽시계는 경과 시간의 근거가 될 수 없다. 근거로 삼는 순간 「외부에서 고쳐질 수 있다」는 성질이 그대로 측정값에 새어 들어온다
  • 반대로 단조 시계는 사람에게 보여줄 시각이 될 수 없다. 로그 타임스탬프에 단조 시계를 쓰면 1970년이 찍히고, 다른 서버의 로그와 맞춰 볼 수 없다

이 구분을 몸으로 익히는 가장 빠른 길은 음수가 나오는 순간을 직접 보는 것이다. 그래서 이 글은 실행으로 시작한다. 열두 가지 실험을 Node와 Python과 셸에서 돌렸고, 아래 모든 블록은 그 출력을 그대로 옮긴 것이다.

실행 환경. 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 런타임은 Node.js v22.16.0 (win32)과 Python 3.13.3, 셸은 GNU bash 5.2.37 (MSYS2/MinGW64)다. 스크립트는 모두 파일로 저장해 실행했다.

시스템 시각은 한 번도 바꾸지 않았다. 관리자 권한이 필요하고 환경을 망친다. 대신 시각 점프를 주입했다. 프로그램이 벽시계를 읽는 자리에 Date.now() + offset 형태의 함수를 두고, 측정 도중에 그 offset을 바꿨다. NTP가 시계를 계단식으로 옮길 때 프로그램이 보는 것과 형태가 같다. 단조 시계는 손대지 않은 실제 값을 그대로 읽었다.

이 글이 다루지 않는 것. 시계가 왜 틀어지는지, 동기 상태를 어떻게 진단하는지는 다루지 않는다. 여기서는 「시계는 뒤로 갈 수 있다」는 사실까지만 쓰고, 그 이후 「경과 시간 측정에 어느 시계를 쓰는가」 한 점에 집중한다. 타임존 규칙과 과거 해석 문제도 이 글의 범위 밖이다.

2. 「끝 − 시작」이 음수가 되는 순간

이제 이 글의 심장이다. 120밀리초 일을 하고, 시각 보정을 3초 뒤로 주입하고, 다시 120밀리초 일을 한 다음 끝 시각에서 시작 시각을 뺐다. 같은 구간을 단조 시계로도 쟀다.

elapsed WALL : 600050 ms   (10.00 min)

elapsed WALL : -2760 ms. 실제로 240밀리초 동안 일했는데 벽시계는 마이너스 2.76초라고 답했다. 같은 구간을 단조 시계로 재면 239.265 ms다. 서비스가 그대로 로그를 찍으면 duration_ms:-2760이라는 줄이 남는다. 서론의 그 줄이다.

  • 끝 시각이 시작 시각보다 작다. 1785385663055가 1785385665815보다 작다. 시계가 그 사이에 뒤로 갔기 때문이다
  • 코드에는 버그가 없다. 뺄셈은 정확하다. 틀린 것은 「두 번째 값이 첫 번째보다 크다」는 가정이다
  • 단조 시계는 같은 주입에 흔들리지 않았다. 주입은 벽시계를 읽는 자리에만 걸었고, 단조 시계는 실제 값을 그대로 읽었기 때문이다. 규격상 이 시계는 조정 대상이 아니다
  • 반대 방향도 같은 문제다. 아래 2-3에서 시계를 10분 앞으로 옮기니 50밀리초 작업이 600050 ms, 10분으로 기록됐다. 음수보다 이쪽이 더 위험하다. 음수는 눈에 띄지만 10분은 그럴듯해 보인다

end   (wall)  : 1785385832.953251
elapsed WALL  : -2759.984 ms
elapsed MONO  : 240.017 ms

{"msg": "job finished", "elapsed_ms": 240.0, "clock": "monotonic"}

Python에서 같은 실험을 하면 값까지 거의 같다. -2759.984 ms다. 이것은 언어의 문제가 아니라 시계의 성질 문제라는 뜻이다. Python 공식 문서는 time.time()에 대해 「두 호출 사이에 시스템 시계가 되돌려졌다면 이전 호출보다 작은 값을 돌려줄 수 있다」고 적어 두었다. 즉 이 동작은 버그가 아니라 명세된 동작이다.

주입 방식에 대해. 시스템 시각은 바꾸지 않았다. 프로그램이 벽시계를 읽는 함수에 오프셋을 더해, 「프로그램이 보는 벽시계가 갑자기 옮겨진 상태」를 만들었다. NTP 계단식 보정이나 사람이 시각을 고쳐 넣을 때 프로그램에 보이는 것과 형태가 같다. 단조 시계 쪽은 오프셋 없이 실제 값을 읽었으므로, 두 열의 대비는 실제 시계의 성질 차이를 그대로 보여준다.

다만 이렇게 하지 않아도 확인할 수 있다. Python time.get_clock_info()가 time에 대해 adjustable=True, monotonic=False를 그대로 보고한다. 이 두 값이 곧 「이 시계는 옮겨질 수 있고 뒤로 갈 수 있다」는 진술이다. 주입 실험은 그 진술이 코드에 어떤 모습으로 나타나는지를 보여주는 것일 뿐이다.

2.1 시계가 뒤로 가는 경우들

「시계가 뒤로 간다」가 이상한 일처럼 들리지만, 실제로는 평범한 운영 활동의 결과다. 어느 경우에 어떤 방향으로 얼마나 움직이는지 정리했다. 움직임의 크기가 중요하다. 밀리초 단위 보정은 로그에 남지 않고 넘어가지만, 초 단위 계단식 보정은 곧바로 음수를 만든다.

계기방향크기측정에 나타나는 모습
시각 동기 계단식 보정양쪽 다수백 밀리초 ~ 수십 초경과 시간이 음수거나 과장된다. 이 글의 재현이 이것
시각 동기 점진식 보정양쪽 다주파수를 조금 조절단조 시계도 영향을 받는다. clock_gettime(2)이 「주파수 조정에는 영향을 받는다」고 적고 있다. 다만 뒤로 가지는 않는다
사람이 손으로 고침양쪽 다분 ~ 시간 ~ 일가장 큰 점프. 개발 장비와 새 서버에서 흔하다
가상 머신 정지 후 재개보통 앞으로정지 시간만큼재개 직후 벽시계가 한꺼번에 뛴다
컨테이너·가상 환경의 시각 소스 변경양쪽 다환경에 따라호스트와 게스트가 서로 다른 값을 보고 있다가 맞춰지는 순간
부팅 직후 하드웨어 시계에서 읽어옴보통 앞으로초 ~ 시간기동 초기에 시작된 측정이 첫 동기 시점에 깨진다

3. 해상도는 다른 문제다 - 그리고 통념이 틀린다

「벽시계는 해상도가 낮으니 단조 시계를 쓰라」는 설명을 자주 본다. 이 말은 절반만 맞다. 실제로 재 봤다. 연속 호출에서 값이 바뀌지 않는 횟수를 세는 방식으로 최소 눈금을 구했다.

--- 3-1. resolution measured by counting repeats  (node) ---
clock                calls    value changed   max identical run   smallest step
-------------------------------------------------------------------------------
Date.now()           400000   38              14402               1 ms
performance.now()    400000   292699          1                   0.000100 ms
hrtime.bigint()      400000   400000          0                   100 ns

--- P-5. resolution measured by counting repeats  (python) ---
clock                calls    value changed   max identical run   smallest step
-------------------------------------------------------------------------------
time.time()            300000   199586          2                   0.000238 ms
time.monotonic()       300000   300000          0                   0.000100 ms
time.perf_counter()    300000   300000          0                   0.000100 ms
time.monotonic_ns()    300000   300000          0                   100 ns
time.perf_counter_ns() 300000   300000          0                   100 ns
  • Node의 Date.now()는 40만 번 호출에서 값이 38번만 바뀌었다. 같은 값이 최대 14,402번 연속으로 나왔고, 최소 변화폭은 1밀리초였다. 밀리초보다 짧은 것은 이 시계로 잴 수 없다
  • 같은 환경의 Python time.time()은 30만 번에서 199,586번 바뀌었다. 최소 변화폭이 0.000238밀리초, 즉 238나노초다. get_clock_info()가 알려준 구현은 GetSystemTimePreciseAsFileTime()이었다
  • 즉 「벽시계는 거칠다」는 통념은 언어와 플랫폼에 따라 틀린다. 같은 기계 같은 순간에 한쪽 벽시계는 1밀리초, 다른 쪽 벽시계는 238나노초였다
  • 그런데 해상도가 높아도 문제는 그대로다. Python의 time.time()은 해상도가 충분한데도 2절에서 음수를 냈다. 해상도와 조정 가능성은 독립된 성질이다
  • 단조 시계 쪽은 양쪽 언어 모두 100나노초였고 같은 값이 두 번 나오는 일이 아예 없었다. 이 환경의 Python은 monotonic과 perf_counter 모두 QueryPerformanceCounter()를 쓴다고 보고했다

정리하면 이렇다. 해상도가 낮으면 짧은 구간을 못 잰다. 조정 가능하면 어떤 구간도 믿을 수 없다. 앞의 것은 불편이고 뒤의 것은 결함이다. 그래서 단조 시계를 쓰는 첫 번째 이유는 해상도가 아니라 adjustable=False다. 해상도는 덤으로 따라온다.

4. 1밀리초보다 짧은 작업을 재면

해상도가 실무에서 어떤 모습으로 나타나는지는 짧은 작업을 재 보면 바로 드러난다. 0.1밀리초쯤 걸리는 계산을 여덟 번 재고, 벽시계와 단조 시계를 나란히 찍었다.

  6           0        0.0703
  7           0        0.0704

----------------------------------------------------------

  1          6.5217           6.5193              6.5173

  • 그러니까 이 시계로 재면 이 작업은 「0밀리초 또는 1밀리초」다. 실제로는 두 배 차이가 나는 회차들이 있는데 그 차이가 전부 사라졌다
  • Python 쪽은 0이 하나도 없었다. 같은 계산이 Python에서는 2~8밀리초 걸려 밀리초 눈금 위로 올라갔고, 벽시계 해상도도 훨씬 높았기 때문이다. 즉 이 증상은 언어와 작업 크기에 따라 보이거나 안 보인다
  • 실무적 함의가 하나 있다. 「우리 코드에서는 0이 안 나오니 괜찮다」는 판단이 위험하다. 작업이 빨라지거나 런타임이 바뀌면 그때부터 0이 나온다. 성능 개선이 측정을 망가뜨리는 셈이다

5. 같은 구간을 100번 재면 분포가 무너진다

한 번 재고 넘어가는 코드는 드물다. 보통은 여러 번 재서 평균과 백분위를 낸다. 같은 작업을 100회 재고 두 시계의 분포를 비교했다.

--- 5-1. same interval, 100 samples, two clocks  (node) ---
clock                 mean       min        max        median    distinct values
---------------------------------------------------------------------------------
Date.now()           0.0700     0.0000     1.0000     0.0000    2
performance.now()    0.0738     0.0702     0.1177     0.0703    24
wall samples that came out exactly 0 : 93 / 100

--- P-7. same interval, 100 samples, three clocks  (python) ---
clock                   mean      min       max       median    distinct   zeros
------------------------------------------------------------------------------
time.time()             3.1561    2.1367    9.7034    2.3899    98         0
time.monotonic()        5.3347    2.1219    47.3406   3.3695    100        0
time.perf_counter()     4.1934    2.1830    12.9886   3.2359    100        0

  • 그런데 벽시계 쪽은 서로 다른 값이 딱 2개뿐이었다. 0과 1이다. 100개 표본 중 93개가 정확히 0이었다. 고해상도 시계는 24개의 서로 다른 값을 냈다
  • 최소와 최대가 0과 1이라는 것은 분포가 없다는 뜻이다. 중앙값은 0, 즉 「이 작업은 시간이 안 걸린다」가 된다
  • Python 쪽은 세 시계가 모두 그럴듯한 분포를 냈다. 다만 time.monotonic()의 최대값이 47.34밀리초로 튀었다. 이것은 시계 결함이 아니라 측정 중 스케줄링 지연이 실제로 있었다는 뜻이다. 시계가 정직하게 그것을 기록한 것이다

6. 짧은 측정을 합산할 때 - 예상과 다른 결과

  • 대신 무너진 것은 분포다. 중앙값이 0.0000, p95와 p99가 나란히 1.0000이다. 서로 다른 값이 2개뿐이니 백분위라는 개념 자체가 성립하지 않는다
  • 이쪽이 실무에서 더 아프다. 총합과 평균은 대시보드에서 그럴듯해 보이는데, 「p99 지연이 1밀리초에 붙어 있다」는 그래프는 측정 눈금을 보고 있는 것이지 서비스를 보고 있는 것이 아니다

7. 타임아웃과 재시도 - 여기서 사고가 커진다

지금까지는 숫자가 이상해지는 이야기였다. 이제 동작이 이상해지는 쪽으로 간다. 재시도 예산 500밀리초를 벽시계 절대 시각으로 잡아 두고, 두 번째 시도 뒤에 시계를 1시간 앞으로 주입했다.

--- 7-1. a wall-clock deadline expires the instant the clock is corrected ---
budget 500 ms of retries, clock steps +3600 s (1 h forward) after attempt 2
 WALL deadline:
  attempt 1: ok, remaining=500 ms
  attempt 2: ok, remaining=470 ms
  << clock stepped 3600 s >>
  attempt 3: ABORT deadline exceeded, remaining=-3599560 ms
  -> attempts completed: 2 of 6, aborted=true
 MONOTONIC deadline:
  attempt 1: ok, remaining=500.0 ms
  attempt 2: ok, remaining=470.8 ms
  << clock stepped 3600 s >> (monotonic unaffected)
  attempt 3: ok, remaining=440.8 ms
  attempt 4: ok, remaining=410.9 ms
  attempt 5: ok, remaining=380.9 ms
  attempt 6: ok, remaining=350.8 ms
  -> attempts completed: 6 of 6, aborted=false

벽시계 쪽은 세 번째 시도에서 즉시 포기했다. 남은 예산이 -3599560 ms라고 계산됐기 때문이다. 실제로는 60밀리초밖에 쓰지 않았는데 500밀리초 예산이 소진된 것으로 처리됐다. 단조 시계 쪽은 여섯 번을 다 돌았다. 반대 방향은 더 나쁘다.

--- 7-2. and a backward step makes the same deadline unreachable ---
deadline was set 200 ms out, then the clock stepped -86400 s
remaining according to the wall clock : 86399880 ms  (24.00 h)
real time actually spent waiting      : 319.6 ms (loop cut off by a guard)
without the guard this loop waits a full day for a 200 ms deadline

--- 7-3. sleep-until-instant vs sleep-for-duration ---
sleep until wall instant 1785385765471 :
  if the clock is stepped +1000 s first -> wakes immediately, 0 ms of real waiting
  if the clock is stepped -1000 s first -> waits ~1001 s of real time
sleep for 1000 ms (setTimeout, libuv timer) :
  setTimeout(1000) fired after 1013.7 ms of monotonic time
  the -50000 ms wall step did not move it
  • 앞으로 점프 → 즉시 만료. 재시도가 한 번도 남지 않고 끝난다. 장애 대응 중에 시각을 맞추면 그 순간 모든 재시도 로직이 동시에 포기한다
  • 뒤로 점프 → 영원히 안 끝난다. 200밀리초 뒤로 잡은 마감을 24시간 뒤로 미룬 셈이 됐다. 벽시계가 계산한 남은 시간은 86399880 ms, 24시간이다. 실험에서는 안전장치로 끊었지만, 없으면 하루를 기다린다
  • 「절대 시각까지 잔다」와 「이만큼 잔다」는 다른 명령이다. 앞의 것은 시계 보정에 휩쓸리고 뒤의 것은 안 휩쓸린다
  • 7-3에서 setTimeout(1000)은 벽시계를 50초 뒤로 주입해도 단조 시간 1013.7밀리초 뒤에 정확히 발화했다. 런타임 타이머는 이미 단조 시계 위에 올라가 있다는 뜻이다
  • 즉 런타임이 주는 타이머는 안전하고, 직접 계산한 마감이 위험하다. 「몇 초 뒤에」를 프레임워크에 맡길 수 있으면 맡기는 편이 낫다

이 절이 가장 위험한 이유. 앞 절들의 증상은 숫자가 이상해지는 것이고, 로그를 보면 알 수 있다. 이 절의 증상은 동작이 이상해지는 것이고, 로그에는 「타임아웃」이라고만 남는다. 그러면 조사는 자연스럽게 네트워크와 상대 서버로 향한다. 원인이 자기 코드의 시계 선택이라는 데까지 가는 길이 아주 멀다.

8. 캐시 만료와 속도 제한 - 같은 결함의 다른 얼굴

타임아웃과 똑같은 계산이 캐시와 레이트리밋에도 들어 있다. 「지금 + TTL」을 저장해 두고 나중에 「지금」과 비교하는 형태다. TTL 60초짜리 항목 5개를 넣고, 실제 시간은 전혀 흐르지 않은 상태에서 시계만 옮겼다.

--- 8-1. a TTL cache keyed on wall instants ---
5 entries, ttl 60 s, nothing has actually elapsed
  before step   wall-cache live=5   mono-cache live=5
  clock +3600 s wall-cache live=0   mono-cache live=5   get(k0)=(expired)
  -> the whole cache evaporates in one tick. every caller goes to the origin at once
  clock -3600 s wall-cache live=5   mono-cache live=5   get(k0)=v0
  -> entries now outlive their ttl by an hour. stale data served as fresh

시계를 1시간 앞으로 옮기자 살아 있는 항목이 5개에서 0개가 됐다. 캐시가 한 틱에 전멸한 것이다. 뒤로 옮기면 반대로 만료되어야 할 항목이 계속 살아 있다. 레이트리밋도 같은 구조다.

--- 8-2. a fixed-window rate limiter on the same clock ---
 WALL limiter, 3 req / 1000 ms:
   r1 window_age=0ms count=1 -> ALLOW
   r2 window_age=0ms count=2 -> ALLOW
   r3 window_age=0ms count=3 -> ALLOW
   r4 window_age=0ms count=4 -> REJECT
   << clock stepped +5 s, no real time passed >>
   r5 window_age=0ms count=1 -> ALLOW   <- quota reset for free
   << clock stepped back to where it was >>
   r6 window_age=-5000ms count=2 -> ALLOW   <- window frozen, it will never roll again
 MONOTONIC limiter, same sequence:
   r1 window_age=1ms count=1 -> ALLOW
   r2 window_age=1ms count=2 -> ALLOW
   r3 window_age=1ms count=3 -> ALLOW
   r4 window_age=1ms count=4 -> REJECT
   << clock stepped +5 s >>
   r5 window_age=1ms count=5 -> REJECT   <- still rejected, correctly
  • 앞으로 점프 → 캐시 전멸. 문제는 「캐시가 비었다」가 아니라 모든 호출자가 동시에 원본으로 몰린다는 것이다. 시각 보정 직후에 원본 부하가 튀는 형태로 나타난다
  • 뒤로 점프 → 만료가 미뤄진다. get(k0)=v0이 그대로 돌아왔다. 만료됐어야 할 값이 신선한 것으로 제공된다. 이쪽은 아무 오류도 안 난다. 그냥 낡은 값이 나간다
  • 레이트리밋은 공짜 할당량을 준다. 시계를 5초 앞으로 옮기니 거절되던 요청이 ALLOW로 바뀌었다. 창이 새로 열린 것으로 계산됐기 때문이다
  • 되돌리면 창이 얼어붙는다. window_age=-5000ms다. 창 나이가 음수이므로 창이 다시 굴러가는 조건을 영원히 만족하지 못한다. 그 뒤로는 카운터가 계속 늘어나기만 한다
  • 단조 시계로 바꾼 쪽은 같은 순서에서 정상적으로 계속 거절했다. 시계 주입이 판단에 전혀 닿지 않았다

9. 로그 타임스탬프는 반드시 벽시계여야 한다

여기서 방향을 뒤집는다. 지금까지는 벽시계를 쓰면 안 되는 자리들이었다. 단조 시계를 쓰면 안 되는 자리도 있다. 단조 시계 값을 그대로 타임스탬프로 찍어 봤다.

--- 9-1. the reverse mistake: a monotonic value cannot be a timestamp ---
monotonic reading                  : 20810933.933
formatted as if it were epoch ms   : 1970-01-01T05:46:50.933Z
wall reading                       : 1785385762171
formatted                          : 2026-07-30T04:29:22.171Z
a log line stamped with the monotonic value says 1970 and cannot be compared to any other machine

--- 9-2. the line that carries both ---
{"ts":"2026-07-30T04:29:22.176Z","duration_ms":44.628,"route":"/v1/orders"}
ts is orderable across hosts and readable by a human; duration_ms cannot go negative
  • 단조 시계 값을 타임스탬프로 포맷하면 1970-01-01T05:46:50.933Z가 나온다. 기준점이 에폭이 아니므로 당연한 결과다
  • 다른 기계의 로그와 맞춰 볼 수 없다. 두 서버의 기준점이 서로 다르므로 두 숫자를 비교하는 것은 의미가 없다. 분산 추적이 여기서 무너진다
  • 사람이 읽을 수 없다. 「20810933.933에 장애가 시작됐다」는 진술로는 아무것도 할 수 없다
  • 보관 정책도 걸린다. 「30일 지난 로그 삭제」 같은 규칙은 절대 시각이 있어야 판단된다

그래서 정답은 「어느 하나를 고르는 것」이 아니라 둘을 각자의 자리에 쓰는 것이다. 9-2의 한 줄이 그 형태다. ts는 벽시계로 「언제」를 적고, duration_ms는 단조 시계로 「얼마나」를 적는다. 이러면 타임스탬프는 다른 호스트와 정렬되고 사람이 읽을 수 있으며, 소요 시간은 절대 음수가 되지 않는다. 한 줄에 두 시계가 들어가는 것이 이상한 일이 아니라 정상이다.

10. 프로세스가 재시작되면 기준점이 바뀐다

단조 시계의 기준점이 임의라는 사실에는 실무적 귀결이 하나 더 있다. 그 값을 저장하면 안 된다. 같은 스크립트를 두 프로세스로 연달아 돌려 값을 비교했다.

--- 10-1. the monotonic origin is per boot and per process ---
field                   previous process     this process         delta
---------------------------------------------------------------------------------
pid                     14920                17368                -
Date.now()              1785386114435        1785386117740        3305 ms
hrtime.bigint()/1e6     21163198.428         21166503.246         3304.818 ms
performance.now()       1869.676             1882.334             12.658 ms
performance.timeOrigin  1785386112566.207    1785386115858.01     3291.803 ms

--- 10-2. so a persisted monotonic deadline is meaningless after restart ---
saved by the previous process : performance.now() + 30000 = 31869.676
this process reads it back and compares to its own performance.now() = 1885.058
  remaining, as computed      : 29984.557 ms
  real time between the runs   : 3305 ms (from the wall clock)
  the two numbers are unrelated. performance.now() restarts near 0 in every process
  • Date.now()는 두 프로세스 사이에서 3305밀리초 늘었다. 실제로 흐른 시간이다. 프로세스가 달라도 같은 좌표계를 본다
  • hrtime.bigint()도 3304.818밀리초 늘었다. 이 시계의 기준점은 프로세스가 아니라 부팅이라서 재시작을 넘어 이어진다
  • performance.now()는 12.658밀리초만 늘었다. 3.3초가 흘렀는데 12밀리초다. 이 시계는 프로세스마다 0에서 다시 시작하기 때문이다. 공식 문서의 「0이 현재 프로세스의 시작을 나타낸다」가 이 숫자로 확인된다
  • 10-2가 그 결과다. 앞 프로세스가 저장한 마감을 뒤 프로세스가 읽어 계산하니 남은 시간이 29984밀리초로 나왔다. 실제로는 3.3초가 흘렀는데 「아직 30초 남았다」고 답한 것이다. 두 숫자는 아무 관계가 없다

11. 절전 구간은 누가 세는가

단조 시계에도 갈래가 있다. 기계가 절전에 들어간 동안 카운터가 멈추는가 계속 도는가다. 이 환경에서 확인할 수 있는 만큼만 재 봤다. 단조 시계 값과, 운영체제가 보고하는 부팅 시각으로부터 계산한 벽시계 경과를 나란히 놓았다.

--- P-9. does the monotonic clock count time spent suspended? ---
time.monotonic() here            : 20892.159 s  (5.80 h)
implementation                   : QueryPerformanceCounter()
OS-reported last boot time       : 2026-07-30T07:42:31.500000+09:00
wall seconds since that boot     : 20892.807 s  (5.80 h)
difference (wall-since-boot minus monotonic) : 0.648 s

POSIX names for the distinction (not reproducible on this host):
  CLOCK_MONOTONIC  - does not step; on Linux it does NOT include suspend
  CLOCK_BOOTTIME   - same, but DOES include suspend
  CLOCK_REALTIME   - the wall clock, may be stepped
  time.CLOCK_MONOTONIC      available in this build : False
  time.CLOCK_BOOTTIME       available in this build : False
  time.CLOCK_MONOTONIC_RAW  available in this build : False
  time.CLOCK_REALTIME       available in this build : False
  • 두 값의 차이는 0.648초였다. 단조 시계는 20892.159초, 부팅 시각 기준 벽시계 경과는 20892.807초다. 5.8시간에 0.6초 차이다
  • 이 기계는 측정 구간에 절전에 들어간 적이 없다. 그래서 이 방법으로는 절전 구간의 처리를 관찰할 수 없었다. 0.6초는 부팅 시각 보고의 정밀도와 부팅 이후 시각 보정으로 설명되는 범위다
  • 절전·최대절전 구간을 이 환경에서 직접 재현하지 못했다. 그래서 아래 구분은 문서 근거로만 적는다. 이 글에서 직접 재현하지 못한 유일한 항목이다
  • clock_gettime(2) 문서는 CLOCK_MONOTONIC에 대해 「이 시계는 시스템이 절전에 든 시간을 세지 않는다」, CLOCK_BOOTTIME에 대해 「CLOCK_MONOTONIC과 동일하나 시스템이 절전에 든 시간도 포함한다」고 적고 있다. Python 문서도 time.CLOCK_BOOTTIME을 같은 뜻으로 설명한다

실무적 판단. 서버 프로세스라면 이 구분이 거의 문제가 되지 않는다. 절전에 들지 않기 때문이다. 문제가 되는 것은 노트북과 휴대 기기에서 도는 코드다. 뚜껑을 닫았다 여는 사이에 CLOCK_MONOTONIC 기반 타임아웃은 그 시간을 세지 않는다. 「5분 뒤 세션 만료」가 하룻밤을 지나도 만료되지 않는 형태다. 절전 시간도 흐른 것으로 봐야 하는 만료라면 CLOCK_BOOTTIME 쪽이 맞고, 사람이 인식하는 절대 시각 기준의 만료라면 애초에 벽시계 절대 시각이 맞다. 이 경우는 14절 표의 「만료」 행을 보라.

12. 셸에는 단조 시계가 없다

셸 스크립트에는 이 문제를 피할 도구가 거의 없다. 셸이 읽을 수 있는 시계들을 전부 찍어 봤다.

bash 5.2.37(1)-release / msys

--- S-1. the clocks a shell can read ---
date +%s          : 1785385886
date +%s%N        : 1785385886351968200
EPOCHSECONDS      : 1785385886
EPOCHREALTIME     : 1785385886.364763
SECONDS           : 0
all of these trace the wall clock. bash exposes no monotonic clock.

--- S-3. SECONDS advances with the wall clock, not with work done ---
SECONDS after sleep 2        : 2
date delta                   : 2132 ms

timeout available here : /usr/bin/timeout
Usage: timeout [OPTION] DURATION COMMAND [ARG]...

date, EPOCHSECONDS, EPOCHREALTIME, SECONDS 모두 벽시계를 따라간다. 즉 순수한 셸 문법으로는 단조 시계에 접근할 방법이 없다. 그래서 셸에서 가장 흔한 다음 패턴은 구조적으로 위험하다.

# the deadline loop everyone writes - both date calls are on an adjustable clock
end=$(( $(date +%s) + 30 ))
while [ "$(date +%s)" -lt "$end" ]; do
    check_ready && break
    sleep 1
done

# the portable fix: stop computing the deadline yourself
timeout 30 sh -c 'until check_ready; do sleep 1; done'
  • 마감을 직접 계산하지 않는 것이 답이다. timeout에 「몇 초 동안」을 넘기면 마감 계산이 셸 밖으로 나간다. 이 환경에도 /usr/bin/timeout이 있었다
  • date 호출 자체도 비싸다. S-2에서 200번 호출의 최소 변화폭이 48밀리초였다. 시계 해상도가 아니라 프로세스 생성 비용이다. 루프 안에서 시각을 읽는 스크립트는 이 비용을 매 회차 낸다
  • 기다림을 절대 시각으로 표현하지 않는다. 「몇 시까지」가 아니라 「몇 초 동안」으로 적는다
  • 정말 정확한 측정이 필요하면 셸에서 하지 않는다. 한 줄짜리라도 단조 시계가 있는 런타임에 맡기는 편이 낫다

13. 기존 코드에서 잘못된 시계 사용을 찾는 절차

이제 진단이다. 다행히 이 결함은 검색으로 거의 다 찾을 수 있다. 잘못된 사용이 구문 모양으로 드러나기 때문이다. 네 가지 패턴을 쓴다.

# A. elapsed  -  the subtraction of two wall readings
grep -rnE 'Date\.now\(\) *- *|time\.time\(\) *- *' src/

# B. deadline / expiry  -  a wall reading with something added to it
grep -rnE '(Date\.now\(\)|time\.time\(\)) *\+' src/

# C. the reverse mistake  -  a monotonic reading assigned into stored state
grep -rnE '(\[[^]]+\]|\.[a-zA-Z_]+) *= *(time\.)?(monotonic|perf_counter|performance\.now|process\.hrtime)' src/

# D. everything already monotonic, to confirm it is used as a difference
grep -rnE 'monotonic\(\)|perf_counter\(\)|hrtime\.bigint\(\)|performance\.now\(\)' src/

실제로 돌려 봤다. 시계 사용이 섞여 있는 예제 파일 두 개를 만들어 위 패턴을 걸었다. 아래는 그 출력이다.

--- 12-1. pattern A: subtraction of two wall readings (the smoking gun) ---
./src/handler.js:7:  const ms = Date.now() - t0;                   // can go negative
./src/worker.py:10:    elapsed = time.time() - start             # can go negative

--- 12-2. pattern B: a deadline built by adding to a wall reading ---
./src/handler.js:13:  const deadline = Date.now() + budgetMs;       // wall-clock deadline

./src/worker.py:15:    deadline = time.time() + timeout_s        # wall-clock deadline

--- 12-4. pattern D: the reverse mistake, a monotonic reading assigned into state ---
./src/worker.py:51:    state["saved_at"] = time.monotonic()

./src/handler.js:32:  const t0 = process.hrtime.bigint();           // correct: monotonic

패턴 A가 가장 강한 신호다. 벽시계 값의 뺄셈은 거의 예외 없이 경과 시간 계산이고, 거의 예외 없이 틀린 것이다. 패턴 B는 판단이 필요하다. 마감과 TTL은 고쳐야 하지만, 토큰 만료나 예약 시각처럼 절대 시각이 맞는 경우도 여기 걸린다. 그래서 검색은 시작이고 리뷰가 필요하다. 리뷰할 때 물어볼 문장들은 이렇다.

  • 이 값을 사람이 볼 것인가, 아니면 두 값을 뺄 것인가. 뺄 것이면 단조 시계다. 이 한 문장으로 대부분 갈린다
  • 이 시각이 프로세스 밖으로 나가는가. 저장되거나 전송되거나 다른 기계와 비교되면 벽시계여야 한다
  • 이 마감이 「몇 시까지」인가 「이만큼 동안」인가. 뒤쪽이면 단조 시계다. 사용자가 지정한 「오후 6시까지」라면 앞쪽이 맞다
  • 이 값이 음수가 되면 무슨 일이 일어나는가. 답이 「모르겠다」거나 「그럴 리 없다」면 그 자리가 위험한 자리다
  • 이 만료가 프로세스 재시작을 넘어 유지되어야 하는가. 그렇다면 단조 시계로 만든 값을 저장해서는 안 된다
// before - the duration can come out negative
const t0 = Date.now();
const out = doWork(req);
log({ ts: new Date().toISOString(), duration_ms: Date.now() - t0 });

// after - wall clock names the instant, monotonic clock measures the span
const t0 = process.hrtime.bigint();
const startedAt = new Date().toISOString();
const out = doWork(req);
log({ ts: startedAt, duration_ms: Number(process.hrtime.bigint() - t0) / 1e6 });
# before
start = time.time()
run_batch(items)
emit_metric("batch_seconds", time.time() - start)

# after
started_at = datetime.datetime.now(datetime.timezone.utc)
start = time.monotonic()
run_batch(items)
emit_metric("batch_seconds", time.monotonic() - start, ts=started_at)

고치는 형태는 위 두 조각처럼 단순하다. 시작 시각을 벽시계로 한 번 찍어 「언제」를 남기고, 구간 측정은 단조 시계로 따로 한다. 줄이 하나 늘어나지만 그 대가로 음수가 사라진다. 되짚어 볼 만한 점이 하나 있다. 12-5에서 단조 시계 사용을 전부 뽑았을 때, 정상 사용 네 건과 함께 단조 시계 값을 저장하는 한 건이 같이 걸렸다. 「단조 시계를 쓰고 있음」은 무사함의 증거가 아니다. 어떻게 쓰는지를 봐야 한다.

15. 왜 이 결함은 늦게 터지는가

이 결함의 가장 나쁜 성질은 기술적인 것이 아니다. 발견되는 방식이다.

  • 평소에는 정확히 맞는다. 두 시계가 나란히 가기 때문이다. 1절의 증가폭이 그것을 보여준다. 그래서 테스트를 통과하고 리뷰를 통과하고 몇 년을 산다
  • 틀리는 순간이 짧다. 시각 보정은 순간이고, 그 순간에 측정 구간이 걸쳐 있어야 증상이 난다. 확률이 낮다
  • 재현이 안 된다. 조사하려면 시계를 옮겨야 하는데, 그것은 조사자가 일부러 하지 않으면 일어나지 않는 일이다
  • 증상이 원인을 가리지 않는다. 「타임아웃」, 「캐시 미스 폭증」, 「p99 이상」은 모두 다른 곳을 가리키는 증상이다. 시계를 의심하기까지 여러 번 헛짚는다
  • 그래서 「가끔 이상하다」로 남는다. 티켓이 닫히고 재현 불가로 정리되고, 다음에 또 난다

이 성질 때문에 대응 순서가 뒤집힌다. 보통은 증상이 나면 고친다. 이 결함은 증상을 기다려서는 안 된다. 증상이 났을 때 원인에 도달할 확률이 낮기 때문이다. 대신 13절의 검색을 한 번 돌려 예산 안에서 정리하는 것이 훨씬 싸다. 패턴이 단순해서 큰 저장소에서도 몇 분이면 끝난다.

마지막으로 판단 기준을 한 문장으로 다시 적는다. 이 숫자를 사람에게 보여줄 것인가, 아니면 다른 숫자에서 뺄 것인가. 보여줄 것이면 벽시계, 뺄 것이면 단조 시계다. 이 질문 하나가 이 글의 표 전체를 대신한다.

16. 체크리스트

아래 항목들은 모두 위 실행에서 근거가 나온 것이다. 순서대로 훑으면 된다.

  • 경과 시간을 재는 자리에서 벽시계 뺄셈을 전부 걷어냈다 (13절 패턴 A)
  • 타임아웃과 재시도 예산이 「이만큼 동안」으로 표현되어 있고, 절대 시각 마감이 아니다
  • 캐시 TTL과 레이트리밋 창이 단조 시계 기준이다
  • 로그 타임스탬프는 벽시계이고, 소요 시간은 단조 시계다. 한 줄에 둘이 같이 있다
  • 단조 시계 값을 저장하거나 전송하는 곳이 없다 (13절 패턴 D)
  • 소요 시간 지표에 음수 방어가 있고, 음수가 들어오면 감춘 게 아니라 경고를 남긴다
  • 짧은 구간을 재는 곳이 고해상도 시계를 쓰고 있다. 백분위가 눈금에 붙어 있지 않다
  • 노트북·휴대 기기에서 도는 만료 로직이라면 절전 구간을 어떻게 셀지 정해 두었다 (11절)

마지막 한 가지. 음수를 발견했을 때 절댓값을 씌우거나 0으로 눌러 놓지 말 것. 그것은 증거를 지우는 일이다. 음수는 이 결함이 실제로 발생했다는 유일하게 명확한 신호이고, 이 글에서 본 것처럼 앞으로 점프한 경우에는 그런 신호조차 남지 않는다. 음수가 보인다면 오히려 운이 좋은 쪽이다. 그 자리에서 시계를 바꾸면 된다.

# 벽시계 vs 단조 시계 — 용도별 선택표와 코드 점검 패턴

> 출처: braindetox.kr — 경과 시간을 벽시계로 재면 음수가 나온다
> 근거: Windows 10 / Node 22.16.0 / Python 3.13.3 / bash 5.2.37 (MSYS2) 실행 검증
> 이 파일을 그대로 AI에 붙여 「이 기준으로 우리 코드의 시계 사용을 점검해줘」라고 쓰면 됩니다.

## 0. 대전제 — 두 시계는 다른 질문에 답한다

| | 벽시계 (wall clock) | 단조 시계 (monotonic clock) |
|---|---|---|
| 답하는 질문 | **지금 몇 시인가** | **얼마나 지났는가** |
| 값의 뜻 | 에폭 기준 절대 시각 | 임의 기준점으로부터의 거리 |
| 외부 조정 | **받는다** | 받지 않는다 |
| 뒤로 갈 수 있나 | **갈 수 있다** | 갈 수 없다 |
| 다른 기계와 비교 | 가능 | **불가능** |
| 저장·전송 | 가능 | **불가** (차이값만 가능) |

**이 숫자를 사람에게 보여줄 것인가, 아니면 다른 숫자에서 뺄 것인가.**
보여줄 것이면 벽시계, 뺄 것이면 단조 시계다. 이 한 문장이 아래 표 전체를 대신한다.

## 1. 용도별 선택표

| 용도 | 시계 | 전형적 실수와 증상 |
|---|---|---|
| **경과 시간 측정** | 단조 | 벽시계 뺄셈 → **소요 시간이 음수** |
| **타임아웃·재시도 예산** | 단조 | 절대 시각 마감 → 즉시 만료 또는 무한 대기 |
| **속도 제한 창** | 단조 | 벽시계 창 → 공짜 할당량, 창 동결 |
| **캐시 TTL** (프로세스 내) | 단조 | 벽시계 만료 시각 → 캐시 전멸 또는 낡은 값 제공 |
| **재시도 백오프 간격** | 단조 | 벽시계 기준 대기 → 간격이 뒤죽박죽 |
| **로그·감사 타임스탬프** | 벽시계 | 단조 값 → **1970년이 찍힌다** |
| **스케줄** 「매일 09시」 | 벽시계 | 단조 시계로는 표현 자체가 안 된다 |
| **만료** (토큰·세션·인증서) | 벽시계 | 단조 값 저장 → 재시작 후 무의미 |
| **성능 프로파일링** | 단조 고해상도 | 거친 벽시계 → 백분위가 눈금에 붙는다 |

## 2. 언어별 API 대응표

| 용도 | Node.js | Python | POSIX / C | 셸 |
|---|---|---|---|---|
| 경과 측정 | `process.hrtime.bigint()` | `time.perf_counter()` | `CLOCK_MONOTONIC` | **없음** |
| 경과 측정 (대안) | `performance.now()` | `time.monotonic()` | `CLOCK_MONOTONIC_RAW` | **없음** |
| 현재 시각 | `Date.now()` | `time.time()` | `CLOCK_REALTIME` | `date`, `EPOCHREALTIME` |
| 절전 포함 경과 | 표준 API 없음 | `time.CLOCK_BOOTTIME` | `CLOCK_BOOTTIME` | **없음** |
| 프로세스 CPU 시간 | `process.cpuUsage()` | `time.process_time()` | `CLOCK_PROCESS_CPUTIME_ID` | `times` |
| 지속 시간 대기 | `setTimeout` | `time.sleep()` | `clock_nanosleep` | `sleep`, `timeout` |
| 시계 성질 확인 | 문서 확인 | **`time.get_clock_info()`** | `clock_getres` | 해당 없음 |

- Node의 `hrtime.bigint()` 기준점은 **부팅**, `performance.now()` 기준점은 **프로세스**다 (실측 확인)
- Python은 `time.get_clock_info('time')` 이 `adjustable=True`, `monotonic=False` 를 그대로 알려준다
- 표에 없는 언어라면 두 가지만 확인한다: **기준점이 무엇인가 / 외부 조정을 받는가**

## 3. 코드 검색 패턴

```bash
# A. 경과 시간 — 벽시계 값의 뺄셈 (가장 강한 신호, 거의 다 틀린 것)
grep -rnE 'Date\.now\(\) *- *|time\.time\(\) *- *' src/

# B. 마감·만료 — 벽시계 값에 무언가를 더하는 형태 (리뷰 필요)
grep -rnE '(Date\.now\(\)|time\.time\(\)) *\+' src/

# C. 반대 실수 — 단조 시계 값이 저장되는 구조에 대입됨
grep -rnE '(\[[^]]+\]|\.[a-zA-Z_]+) *= *(time\.)?(monotonic|perf_counter|performance\.now|process\.hrtime)' src/

# D. 모든 단조 시계 사용 — 차이로만 쓰이는지 확인
grep -rnE 'monotonic\(\)|perf_counter\(\)|hrtime\.bigint\(\)|performance\.now\(\)' src/
```

- **A는 거의 전부 고칠 대상이다.** 벽시계 뺄셈은 사실상 경과 시간 계산이다
- **B는 판단이 필요하다.** 마감·TTL은 고치고, 토큰 만료·예약 시각은 그대로 둔다
- **D에서 걸린 것도 안심하면 안 된다.** 단조 시계를 쓰는 것과 올바르게 쓰는 것은 다르다

## 4. 리뷰 점검 문장

- [ ] **이 값을 사람이 볼 것인가, 아니면 두 값을 뺄 것인가** — 뺄 것이면 단조 시계
- [ ] **이 시각이 프로세스 밖으로 나가는가** — 저장·전송·타 기계 비교면 벽시계
- [ ] **이 마감이 「몇 시까지」인가 「이만큼 동안」인가** — 뒤쪽이면 단조 시계
- [ ] **이 값이 음수가 되면 무슨 일이 일어나는가** — 답이 「그럴 리 없다」면 그 자리가 위험하다
- [ ] **이 만료가 프로세스 재시작을 넘어 유지되어야 하는가** — 그렇다면 단조 값을 저장하면 안 된다
- [ ] **짧은 구간인가** — 밀리초 눈금 벽시계로는 0이 나온다
- [ ] **절전에 드는 기기에서 도는가** — `CLOCK_MONOTONIC` 은 절전 구간을 세지 않는다

## 5. 고치는 형태

```javascript
// before — 소요 시간이 음수가 될 수 있다
const t0 = Date.now();
const out = doWork(req);
log({ ts: new Date().toISOString(), duration_ms: Date.now() - t0 });

// after — 벽시계가 「언제」를, 단조 시계가 「얼마나」를 담당한다
const t0 = process.hrtime.bigint();
const startedAt = new Date().toISOString();
const out = doWork(req);
log({ ts: startedAt, duration_ms: Number(process.hrtime.bigint() - t0) / 1e6 });
```

```python
# before
start = time.time()
run_batch(items)
emit_metric("batch_seconds", time.time() - start)

# after
started_at = datetime.datetime.now(datetime.timezone.utc)
start = time.monotonic()
run_batch(items)
emit_metric("batch_seconds", time.monotonic() - start, ts=started_at)
```

```bash
# before — 두 date 호출이 조정 가능한 시계 위에 있다
end=$(( $(date +%s) + 30 ))
while [ "$(date +%s)" -lt "$end" ]; do check_ready && break; sleep 1; done

# after — 마감 계산을 셸 밖으로 내보낸다
timeout 30 sh -c 'until check_ready; do sleep 1; done'
```

## 6. 실측 참고값 (Windows 10 / Node 22.16.0 / Python 3.13.3)

| 시계 | 최소 눈금 | 비고 |
|---|---|---|
| Node `Date.now()` | **1 ms** | 40만 호출에서 값이 38번만 바뀜, 같은 값 최대 14,402회 연속 |
| Node `performance.now()` | 0.0001 ms | — |
| Node `hrtime.bigint()` | 100 ns | 40만 호출 전부 서로 다른 값 |
| Python `time.time()` | **0.000238 ms** | 구현 `GetSystemTimePreciseAsFileTime()` — **벽시계도 고해상도일 수 있다** |
| Python `monotonic` / `perf_counter` | 100 ns | 둘 다 `QueryPerformanceCounter()` |
| 셸 `date +%s%N` 왕복 | 약 48 ms | 시계 해상도가 아니라 **프로세스 생성 비용** |

**해상도와 조정 가능성은 독립된 성질이다.** 해상도가 충분한 Python 벽시계도 시각 보정에는 똑같이 음수를 낸다.

## 7. 하지 말 것

- ❌ 소요 시간 음수를 **절댓값이나 0으로 눌러 놓는 것** — 증거를 지우는 일이다. 앞으로 점프한 경우엔 그런 신호조차 없다
- ❌ 단조 시계 값을 **파일·DB·응답 본문에 저장하는 것** — 프로세스가 바뀌면 무의미해진다
- ❌ 「몇 시까지」로 표현한 **재시도 마감** — 시각 보정에 즉시 만료되거나 영원히 안 끝난다
- ❌ 로그 타임스탬프에 **단조 값** — 1970년이 찍히고 타 호스트와 맞춰 볼 수 없다
- ❌ **평균만 보고 넘어가는 것** — 거친 시계에서 총합은 맞고 백분위만 무너진다
- ❌ 셸 루프 안에서 **직접 마감 계산** — 조정 가능한 시계 위에 있고 `date` 호출 비용도 크다
- ❌ 「우리는 시각을 안 바꾼다」는 전제 — 시각 동기·가상 머신 재개·수동 수정은 평범한 운영 활동이다
