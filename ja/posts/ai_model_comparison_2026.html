ベンチマークの読み方

スコア表を信頼しにくいのは、数字が間違っているからではなく比較可能でないからだ。ランキングをそのまま持ち込めない理由が五つある。

  • 測定主体が違う。ベンダー自社測定と第三者測定は別種の主張だ。一つの表に混ぜると、どの行がどちらなのか消えてしまう。
  • 設定が違う。いまのモデルは推論の深さを調節するつまみを持つ。Anthropic は effort の既定が high だとドキュメントに書き、Google は thinking_level を最小から高まで調節すると書いている。同じモデルでも、つまみの位置で別のスコアが出る。
  • 汚染を外部から確認できない。公開問題集が学習データに混じったかどうかは、ウェイトとデータを見ないと判定できない。クローズドなモデルでは原理的に不可能だ。
  • 平均だけが残り、ばらつきが消える。5回に1回崩れるモデルと毎回同じ品質を出すモデルが同じ平均を持ちうる。運用ではまったく別の話になる。
  • 測定時点が流れる。モデルIDが同じでも、裏側のサービング構成は変わりうる。Anthropic は4.6世代以降のIDが固定スナップショットだと明記しているが、すべてのベンダーがそう書いているわけではない。

そこでこの記事はスコア表を写さない。代わりに公式ドキュメントで裏が取れる軸（価格・上限・寿命・可用性）を表にし、裏の取れない軸（品質）は読者が自分の業務で測る手順に置き換えている。

  • コーディング、確認できなかったこと：これらのモデルが実際にコード作業をより上手くこなすという公式数値はなかった。名前と説明はベンダーの意図表明であって性能の証拠ではない。
  • コーディング、実務的な判断：コーディングのワークロードは出力トークンの比重が大きいので出力単価が総額を支配する。本記事の作業C（入力8千・出力4千）では出力単価の低いモデルが有利だった。コードツールの比較はコーディングツール比較で別に扱う。

  • 長文、実務的な判断：コンテキスト上限の半分、四分の三、100%の地点でそれぞれ同じ質問を投げて正答率を測るのが唯一の検証法だ。この手順は第39節の文書にある。

洞察1 — 価格を押し下げる圧力

確認できた単価の分布にははっきりした形がある。同じ世代の中で最上位と最下位が100倍以上開く。gpt-5.5-pro の入力 $30.00 と GLM-4.7-FlashX の $0.07 は428倍の差だ。

この分布を作る圧力は三つに分けられる。

  • 競争圧力としての段階分化。各社が一つの価格ではなく三段以上の価格表を出す。gpt-5.6 は三段（sol・terra・luna）、Claude は四段（Fable・Opus・Sonnet・Haiku）、Gemini は三段（Pro・Flash・Flash-Lite）。段階分化は上端の価格を守りながら下端で戦う方法だ。
  • 同じ仕様、違う価格。gpt-5.6-sol と terra はコンテキスト・出力上限・カットオフ・モダリティがすべて同一なのに価格は2.5倍違った。価格が仕様ではなく別の何かに付けられているというサインだ。
  • 旧世代の残存。OpenAI の価格表に gpt-3.5-turbo（$0.50 / $1.50）が、Google に Gemini 2.5 Flash-Lite（$0.10 / $0.40）が、智譜に GLM-4.5（$0.60 / $2.20）が残っている。旧世代は消えずに低価格帯へ降りる。新型が出るほど底が厚くなる。
  • 公開ウェイトによる底値効果。DeepSeek のウェイトが MIT で公開されているという事実は、その性能帯の API 価格に上限を作る。誰でも自己ホスティングできる性能に高い単価は付けにくい。
  • 導入価という期限付きの値下げ。Claude Sonnet 5 の $2 / $10 は2026年8月31日までの導入価として告知され、9月1日から $3 / $15 になる予定だったが、その値上げが撤回されて $2 / $10 が正規価格になった。期限付きの値下げがそのまま定着することもあることを示す文書化された例だ。ただし予定された値上げがドキュメントに載っていたという事実自体は残る。単価は契約ではなく告知だ。

同時に価格を押し上げる圧力もドキュメントにある。高速モードが $10 / $50、優先処理が標準の1.8倍、米国限定処理が1.1倍、20万トークン超の区間が2倍、ピーク時間が2倍。基本単価は下がるがオプションの係数は増える。表示価格が安く見えても請求書がそうでない理由はここにある。

洞察2 — コンテキスト長が性能でない理由

確認できた事実を並べるだけで結論が出る。

  • 入力100万トークン級のモデルが、今回の調査だけで五つのベンダーにまたがっている。100万はもう差別化要素ではない。
  • 一方で出力上限は6万4千から38万4千まで6倍開く。長い文書を読む能力と長い文書を書く能力は別々に動く。
  • Google は20万トークンを境に単価を上げる。ベンダー自身が「長いコンテキストは高い」と価格で語っていることになる。
  • Anthropic は逆に100万全体を標準単価で提供すると明記した。同じ機能に対する二社の価格方針が正反対だ。
  • Google のドキュメントには既定のメディア解像度の上昇でコンテキストを超えうるという案内がある。コンテキストが静かに消費される経路が存在する。
  • Anthropic のドキュメントの表は、ツール定義が毎回の要求で数百トークンを占めることを示す。コンテキストは利用者が入れたものだけで埋まるわけではない。

ここから出る判断はこうだ。コンテキスト上限は「受け入れる量」であり、性能は「その中から必要なものを見つけ出す能力」である。前者はドキュメントにあり、後者はない。そして後者を測るには、上限の複数の地点で同じ質問を投げてみるしかない。コンテキスト設計そのものはコンテキストエンジニアリングの記事で扱う。

洞察3 — ベンダーごとに力点が違う構造的理由

同じ市場でなぜドキュメントの構成がここまで違うのか。確認できた事実から逆算できる。

  • Anthropic は予測可能性を文書化する。引退予定日、60日通知の方針、ツール別のトークン消費、キャッシュ係数、地域一覧、さらには自社の廃止方針の欠点まで書いた。これは長期契約を検討する組織が必要とする情報だ。
  • OpenAI は選択肢を文書化する。三十種以上のモデルを一ページに並べ、すべてにキャッシュ単価を付ける。一方で寿命や法的条件は今回の方法では確認できなかった。これはいますぐ繋いで使う開発者が必要とする情報だ。
  • Google は等級を文書化する。標準・バッチ・フレックス・優先という四段のサービス等級、モダリティ別単価、キャッシュ保管料まで分ける。これはクラウド事業の課金文法で、他のクラウドサービスと同じやり方で AI を売っている。
  • xAI は構成を文書化する。テキスト・画像・動画・音声を一つの表に置き、それぞれ別の課金単位を使う。これは製品の束を売る方法だ。
  • DeepSeek は単価とその条件を文書化する。キャッシュのヒットとミス、ピーク時間、言語別のトークン換算比まで書く。文書量は少ないがコスト計算に必要な値はすべて揃っている。

洞察4 — オープンとクローズドの境目

「オープン」という語が少なくとも三つのものを指している。確認できた事例で区別する。

  • ウェイトが公開され、ライセンスにも実質的な制約がない場合。DeepSeek-V3.2 の MIT ライセンスがこれにあたる。使用・改変・再配布・販売が許可され、著作権表示の保持だけが求められる。これが最も広い意味での開放だ。
  • ウェイトは公開されるが独自ライセンスが付く場合。Llama 系がここに入るとされるが、今回はライセンス本文を確認できなかったので条件は引用しない。
  • ウェイトは非公開で API のみ提供される場合。Claude・GPT・Gemini・Grok がここに該当する。

境目が分かれるのは「誰が失敗のリスクを負うか」という点だ。

  • API を使えばベンダーが可用性・拡張・更新を負い、自分は引退日程と方針変更を負う。本記事で確認した2026年8月5日の引退がまさにそれだ。
  • ウェイトを持てば自分がサービング・拡張・セキュリティを負い、代わりに引退がない。誰も自分のモデルを止めない。
  • したがって判断基準は性能ではなく「自社のサービスがベンダーの引退日程より長く生きる必要があるか」だ。契約期間が3年で引退保証が1年なら、答えはすでに出ている。
  • コスト面には交差点がある。本記事の想定ワークロードで最も安い API は月 $12.67 だった。その程度の金額では自己ホスティングのハードウェアと人件費は賄えない。自己ホスティングははるかに大きい規模か、データ統制の要求がある場合にのみ成立する。
  • ローカル実行のハードウェア要件と量子化のトレードオフはローカル LLM 実行ガイドで扱う。開放と閉鎖をめぐる規制の議論はオープンウェイト規制の記事にある。

ベンダーが言わないこと

これまでの空欄を集めると模様が見える。ベンダーが公開するものと公開しないものの間には一貫した線がある。

公開されるもの公開されないものなぜそうなるか（観察に基づく推定）
トークンあたりの単価実際の契約割引率大口顧客との交渉余地を残す必要がある
コンテキストの上限その上限内で品質が保たれるか測定方法が標準化されておらず、結果が不利になりうる
システムがエラーを返す条件モデルが間違った答えを自信をもって出す条件前者はシステムの仕様、後者はモデルの弱点
相対表現の応答時間の等級毎秒トークンのような絶対値負荷と地域で変動し、書けば約束になってしまう
サポート地域の一覧地域別の応答時間と可用性の差運用指標はサービスレベル契約の領域
引退予定日（一部ベンダー）プレビューモデルの寿命プレビューは定義上、約束ではない
モダリティ別の入力単価モダリティ別の品質差課金は仕様、品質は主張
トークナイザーを変更したという事実変更前後のコスト影響の数値顧客に自分で測らせる
モデル名に込めた用途その用途における性能の根拠名前はマーケティング、根拠は検証の対象
価格ページ利用規約の出力物権利（一部ベンダーは自動取得を遮断）法務審査を人にやらせるよう誘導する

線ははっきりしている。契約できるものは公開され、約束になった瞬間に不利になるものは公開されない。単価は契約の対象だから公開される。品質は契約の対象ではないから公開されない。これは不誠実ではなく契約可能性の境界だ。

実務的な含意は一つ。公開された軸で候補を絞り、公開されていない軸で決めないこと。後者は自分で測るしかなく、その手順が次の節にある。

自分で測る方法

この記事の正直な結論は一つだ。公開ベンチマークは自分の業務に移らないのだから、自分で測れ。そう書いておいて測り方を渡さなければ口先だけになるので、手順の文書をそのまま載せる。コピーしてすぐ使える。

  • ゴールデンセットは30から50件。実務から取る。易しいものが4割、普通が4割、難しいものが2割。
  • 合格条件を先に書く。出力を見てから基準を決めると、基準が出力に引きずられる。
  • プロンプトの型を固定し、モデルだけを替える。一度に一変数。二つ同時に変えると原因を分離できない。
  • 同じ入力を5回ずつ回す。5回中4回成功と5回中5回成功は、運用ではまったく別の話だ。
  • 数え方のある項目だけを記録する。満たした形式条項の数、事実誤りの件数、応答時間の中央値と最大値、出力トークン数、人が手を入れた回数。
  • トークンと時間を品質と同じ表に書く。片方だけ測ると結論が半分になる。

# AIモデルを自分で測る — 同一条件比較ハーネス

> 出典: braindetox.kr — 2026年 AIモデル比較
> このファイルは点数表ではなく**手順**です。公開ベンチマークの点数はあなたの業務には移りません。
> そのままコピーして使ってください。単価は本文の価格表を見て埋めます。
> ⚠ この手順は「どのモデルが優秀か」を決めません。**あなたの業務でどちらが間違いにくいか**だけを示します。

## 0. 前提 — なぜ自分で測るのか

| 公開ベンチマークが教えること | 教えないこと |
|---|---|
| ある公開問題集での正答率 | 社内用語・書式・例外ケースへの対応 |
| ベンダーが公開すると決めた項目 | ベンダーが公開しないと決めた項目 |
| ある時点・ある設定での値 | あなたの設定(推論強度・温度・ツール)での値 |
| 平均値 | ばらつき。5回に1回崩れるかどうか |

- ベンチマーク問題が学習データに混入したかは**外部から確認できません**
- ベンダー自社測定と第三者測定は**種類の違う主張**です。混ぜて順位を作らないでください
- あなたの業務50件は、公開ベンチマーク5,000問より**あなたにとって**正確です

## 1. 同一条件比較ハーネス — 手順

1. **ゴールデンセットを作る。** 実際の業務30〜50件。易しい40パーセント、普通40パーセント、難しい20パーセント
2. **正解または合格条件を先に書く。** 出力を見てから基準を決めると、基準が出力に引きずられます
3. **プロンプトの型を固定する。** 第2節の型を使い、業務ごとに空欄だけ差し替えます
4. **設定を記録する。** モデル名、バージョン文字列、推論強度、出力上限、ツール使用の有無
5. **各モデルに同じ入力を5回ずつ入れる。** 回ごとに別々に記録します
6. **採点は出力だけを見て行う。** どのモデルの出力か分からない状態で採点できればなお良いです
7. **表に記録する。** 第6節の様式
8. **トークンと時間も一緒に記録する。** 品質だけ測って費用を測らなければ結論は半分です

## 2. プロンプトの型 — 空欄に自分の業務を入れてください

```
[役割]
あなたは(領域)の(職種)です。

[入力]
以下は(入力資料の種類)です。
---
(ここに実際の資料を貼ります)
---

[やること]
1. (作業1)
2. (作業2)
3. (作業3)

[出力形式]
- 最上部に(要約形式)を1行
- 続いて(項目数)個の項目、各項目は(フィールドA) / (フィールドB)の順
- 全体で(長さ上限)以内

[制約]
- (資料)にない内容は書かないこと
- 確実でない場合は「要確認」と表記すること
- (禁止表現の一覧)は使わないこと

[出力は上記の形式のみ。前置きも締めの言葉も不要。]
```

- **空欄だけ変え、型は固定します。** 型が変わると、モデルの差かプロンプトの差か判別できません
- 制約に**わざと破りやすい条件**を一つ入れてください。指示遵守を測る目盛りになります
- 「確実でなければ要確認と書く」条項は**回避のしかた**を観察する装置です

## 3. 一度に一変数だけ

| 今回変えたもの | 固定したもの | 分かること | 分からないこと |
|---|---|---|---|
| モデルのみ | プロンプト、入力、設定 | モデル間の差 | プロンプトを直せば逆転するか |
| プロンプトのみ | モデル、入力、設定 | プロンプト感度 | 他のモデルでも同じか |
| 推論強度のみ | モデル、プロンプト、入力 | 強度に対する品質・費用曲線 | 他の業務でも同じ曲線か |
| 入力長のみ | それ以外すべて | 崩れ始める地点 | 原因が長さか内容か |

- 二つ同時に変えると**原因を分離できません**。結果が良くなっても理由が分かりません
- 急ぐときほど一変数。二変数で得た結論は来月また測り直すことになります

## 4. なぜ複数回まわすのか

- 同じ入力に同じ出力が出る保証は**ありません**。1回の結果は標本1個です
- **最低5回。** 5回中4回成功と5回中5回成功は、運用ではまったく別の話です
- 失敗が1回でも出たら、**その失敗を保管**してください。失敗のしかたがモデル選定の実質的な根拠です
- 回ごとのばらつきが大きいモデルは、平均点が高くても**自動化パイプラインに入れにくい**です

## 5. 評価基準チェックリスト — 数え方まで

| 項目 | どう数えるか | 記録単位 |
|---|---|---|
| 指示遵守 | 要求した形式・長さ・禁止事項を条項ごとに合否採点 | 満たした条項数 / 全条項数 |
| 出力形式の安定性 | 同じプロンプト5回のうち構造が保たれた回数 | 5回中N回 |
| 長さのばらつき | 5回の出力の文字数。最大値割る最小値 | 倍率 (1.0に近いほど安定) |
| 事実誤り | 正解が分かる項目をあらかじめ仕込み、外れた個数を数える | 件 / 試行 |
| 根拠のない断定 | 資料にないのに断言した文の数 | 件 / 試行 |

- 応答時間は平均ではなく**中央値**と**最大値**を一緒に見てください。利用者が体感するのは最大値です

## 7. 自分の費用を実測する手順

単価は本文の価格表を見て埋めます。ここには**数える手順と計算式**だけを置きます。

1. 代表的な業務を3種類選びます。例: 短い問い合わせ / 長文要約 / コード生成
2. 各業務を**実際に一度実行**し、応答に報告された入力トークンと出力トークンを書き留めます
3. ベンダーがトークン計算ツールを提供していれば、それで突き合わせます
4. その業務を**月に何回**行うか数えます。推測ではなくログから数えます
5. 下の式に入れます

```
業務別の月間入力トークン = 1回の入力トークン かける 月間実行回数
業務別の月間出力トークン = 1回の出力トークン かける 月間実行回数

月額費用 = (月間入力トークン わる 1000000 かける 入力単価USD)
        + (月間出力トークン わる 1000000 かける 出力単価USD)

全体の月額費用 = 業務3種類の月額費用の合計
```

6. キャッシュが効く業務なら、**ヒット分とミス分を分けて**計算します

```
キャッシュ適用時の月間入力費用
 = (ミストークン わる 1000000 かける 基本入力単価)
 + (ヒットトークン わる 1000000 かける キャッシュ読取単価)
 + (キャッシュ書込トークン わる 1000000 かける キャッシュ書込単価)
```

7. 次の項目は**表示単価に含まれないので別途足します**

- ウェブ検索やコード実行などサーバー側ツールの利用料
- ツール定義とシステムプロンプトが毎回の入力トークンに占める分
- 再試行。失敗して投げ直した要求も課金されます
- バッチ・非同期割引が効かないリアルタイム経路の比率
- 時間帯や地域オプションによる倍率

8. **トークナイザーが違えば同じ文書でもトークン数が変わります。** ベンダーを比べるときは単価だけを比べず、**同じ文書を入れたときそれぞれ何トークンと数えるか**を先に確認してください

| 項目 | 再試験する内容 | 合格条件 |

| システムプロンプトの移植性 | 同じシステムプロンプトをそのまま入れたときの挙動 | 強調表現が過剰反応を起こさないか |
| 出力形式の強制方式 | スキーマ強制機能の有無と対応するスキーマ文法の範囲 | 既存スキーマがそのまま通るか |
| コンテキスト超過時の挙動 | 入力を上限まで埋めたときの応答 | 切られるか、エラーか、黙って要約されるか |
| 出力上限 | 最大出力トークンと上限到達時の表示 | 途中で切れたことをコードが検知できるか |
| 拒否ポリシーの差 | 従来通っていた要求100件を再実行 | 新たに拒否される件数はいくつか |
| ストリーミング挙動 | チャンク単位、ツール呼び出し中のストリーム維持、中断処理 | 既存クライアントがそのまま繋がるか |
| トークン会計 | 同じ入力のトークン数、キャッシュの計算方式 | 費用予測が何パーセントずれるか |
| 応答時間の分布 | 同じ業務50回の応答中央値と最大値 | タイムアウト設定を変える必要があるか |
| 再現性 | 同じ入力10回の出力ばらつき | 後処理コードがばらつきに耐えるか |
| 廃止予定 | 対象モデルの公表済み引退予定日 | 自社の契約期間より後か |
| 地域・規制 | 要求が処理される地域、データ保持期間 | 自社の規定に合うか |

## 9. やってはいけないこと

- **モデルに「どのモデルが一番いい?」と聞かないでください。** 循環論法であり、モデルは自分の順位を知る根拠を持ちません
- ベンダー発表の点数をそのまま写して自分の表を作らないでください。測定条件が互いに違います
- ある業務で勝ったモデルを全業務の勝者に一般化しないでください
- 1回の実行結果で結論を出さないでください
- プロンプトをモデルごとに別々に調整しておいてモデルを比較しないでください
- 価格だけで選ばないでください。再試行が増えれば安いモデルの方が高くつきます
- 品質だけで選ばないでください。応答の遅さが利用者の離脱を生みます

- ベンダーが新しいモデルを出したとき
- 使っているモデルの引退予定日が公表されたとき
- 価格表が変わったとき
- トークナイザーの変更が公表されたとき (同じ文書のトークン数が変わります)
- プロンプトを大きく直したとき
- 四半期に一度。何もなくても
