The Git Undo Decision Table - When to Use reset, revert, restore or checkout

Where does it live, and have you shared it? Those two questions almost pick the command

Sep 1, 2026 Dev & Infra

Undoing things in Git is hard not because there are many commands, but because the options look alike and behave nothing alike. reset removes commits while revert adds one. restore leaves your branch alone while checkout can move it. Nothing in the names tells you that.

So this is not a command list. It is a decision procedure: ask two questions, and the answers hand you the command. Every example below was run in a fresh throwaway repository created for the purpose, and the output pasted here is what actually came back.

Some of the commands in this article are destructive and cannot be undone. Each section states plainly whether recovery is possible. If a command is new to you, try it in an empty repository created with git init rather than in the repository you actually work in.

Two questions to ask before you undo anything

Before your hands move, there are only two things to establish. Once both are answered, the set of usable commands usually collapses to one.

  • First, where does the thing you want back live? Have you only saved it in the editor (working tree), run git add on it (index), or already run git commit (HEAD)? That answer decides between restore and reset
  • Second, has that commit been shared? If it has been pushed, or somebody has pulled it, the commit is no longer only yours. That answer decides between reset and revert
  • A third question is really a sanity check. Has this change ever been committed at all? If not, no command will bring it back once it is gone

Most accidents come from skipping the second question. Erasing a commit locally with reset --hard costs nothing. The identical command applied to a commit you have already pushed puts every other clone of that branch out of step. Same keystrokes, entirely different bill. The asymmetry is easy to miss because Git gives you no warning at the moment you type it; the consequence arrives later, on someone else's machine, when they run a routine git pull and it does something unexpected.

Three areas - working tree, index, HEAD

In Git a single file can exist in three places at once: the working tree you saved from the editor, the index (the stage) where git add put a copy, and HEAD, the last commit. What separates the undo commands is how many of those three they touch.

Getting comfortable with git status when the three disagree makes the rest easy. Below, one file has been modified, one was created and added, and one was just created and left alone.

$ cd /tmp/demo
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	new file:   b.txt

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   a.txt

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	c.txt

$ git status --short
 M a.txt
A  b.txt
?? c.txt

The two columns in the --short output are exactly those two areas. The left column is the index, the right is the working tree. A  b.txt means only the index changed;  M a.txt means only the working tree did. When both changed you get MM. Learn to read those two characters and the screen is already telling you which command you need.

Helpfully, git status prints the remedy under each group: git restore --staged to come off the stage, git restore to throw away a working tree change. The table below lines those up.

AreaWhat it holdsHow status --short shows itCommand that undoes it

The decision table - where it lives times whether you shared it

This table is the centre of the article. The rows are the first question, the columns are the second. Every later section is a record of running one of these cells and checking what came back.

The important thing about this table is that reset never appears in the already-pushed column. Exceptions exist, but they only work when the whole team agrees and coordinates the timing. That is not a call one person makes alone.

It is also worth noticing how much of the table is decided by the first column alone. Once you know the change is still private, almost anything is permissible, because the only person who can be inconvenienced is you and the reflog is standing behind you. The moment the answer to the second question flips to yes, the range of acceptable commands narrows to essentially one, and the reason is not technical purity. It is that every other command in the row makes work appear on somebody else's desk without warning them first.

git restore - undoing one file at a time

restore was split out of checkout in Git 2.23. Its job is narrow, which is exactly what makes it easy to use. The Reset, restore and revert section of the official Git documentation describes it as restoring files in the working tree from either the index or another commit, and then adds the crucial sentence: this command does not update your branch. It never touches history.

What matters is that a single --staged flag changes the command's character entirely. Below, the same file has beta staged and gamma added only in the working tree, and the two forms are run in turn.

$ git status --short
MM note.txt

# 1) index only - file contents untouched
$ git restore --staged note.txt
$ git status --short
 M note.txt
$ cat note.txt
alpha
beta
gamma

# 2) working tree - this is where content disappears
$ git restore note.txt
$ git status --short
$ cat note.txt
alpha

The moment the second command ran, beta and gamma were gone. Neither had ever been committed, so there is no path back. That is why restore, gentle as the name sounds, belongs on the destructive list. The first form, with --staged, did not touch the file at all.

  • git restore --staged <file> - unstage. Reversible. The file on disk is unchanged
  • git restore <file> - discard the working tree change. Not reversible. Uncommitted content is destroyed
  • git restore --staged --worktree <file> - both areas at once. An MM becomes a clean status in one step
  • git restore --source=<commit> <file> - pull that file as it was at that commit. History stays exactly where it was
  • A tracked file you deleted by accident with rm comes straight back with git restore <file>. That use is entirely safe

That last form gets more use than people expect: keep the history, roll back a single file. Pulling the previous version out of a three-commit repository looks like this.

$ git log --oneline
1beb864 add delta
4fb8d79 add beta
96d2ca7 add note

$ git restore --source=HEAD~1 note.txt
$ cat note.txt
alpha
beta
$ git status --short
 M note.txt

The branch is still sitting on add delta; only the file went back, and it now shows up as modified. Commit that and you have made yourself a commit that undoes something - revert, hand-rolled at file granularity.

git reset - how far each of the three modes goes

reset is the only one of these three that moves the tip of your branch. The documentation puts it as updating your branch by moving the tip in order to add or remove commits, which changes commit history. The three modes differ solely in how far the index and working tree follow HEAD.

Three copies of the same repository were built and each rolled back to HEAD~1. The commits are C1 base, C2 feature and C3 oops, and the file gains one line each time.

$ git log --oneline
2152c39 C3 oops
3e571a5 C2 feature
44cb882 C1 base

$ git reset --soft HEAD~1
$ git log --oneline
3e571a5 C2 feature
44cb882 C1 base
$ git status --short
M  app.txt
$ cat app.txt
v1
v2
v3

--soft removed only the commit. Everything C3 contained is still sitting on the stage, shown by the M in the left column. This is the mode for rewording a commit or squashing several into one.

$ git reset --mixed HEAD~1
Unstaged changes after reset:
M	app.txt
$ git log --oneline
17b85e8 C2 feature
d42f7bf C1 base
$ git status --short
 M app.txt
$ cat app.txt
v1
v2
v3

--mixed reset the index too, so the same change dropped to the right column. The file still contains everything up to v3. This is what plain git reset does, and running git reset with no arguments at all means --mixed HEAD, which unstages everything you had added.

$ git reset --hard HEAD~1
HEAD is now at add35e9 C2 feature
$ git log --oneline
add35e9 C2 feature
453f0e3 C1 base
$ git status --short
$ cat app.txt
v1
v2

Only --hard actually changed the file. Status is empty and v3 is gone. The documentation reserves the phrase about discarding changes to tracked files for this mode alone. Of the three, this is the only one that can cost you uncommitted work.

ModeHEADIndexWorking treestatus --short afterwardsWhat you can lose

git revert - making a new commit that undoes

revert works differently from the other two, and the first line of its documentation is the definition: given existing commits, revert the changes those patches introduced and record new commits that record them. The old commit stays where it is. History does not get shorter; it gets longer.

$ git log --oneline
e4285bf C3 enable debug
b1fe989 C2 add timeout
f001827 C1 add config

$ git revert --no-edit HEAD
[main 83f6fc6] Revert "C3 enable debug"
 1 file changed, 1 deletion(-)
 delete mode 100644 debug.txt

$ git log --oneline
83f6fc6 Revert "C3 enable debug"
e4285bf C3 enable debug
b1fe989 C2 add timeout
f001827 C1 add config
$ git status --short

C3 is untouched and Revert "C3 enable debug" sits on top of it. The resulting files match the state at C2, but the record keeps both the doing and the undoing. In a repository where anyone might have to audit what happened, that is a feature rather than clutter.

Reverting does not always finish quietly. If a later commit touched the same lines, it conflicts. Reverting the middle commit of a history that kept editing adjacent lines in one file gives this.

$ git revert --no-edit HEAD~1
Auto-merging config.txt
CONFLICT (content): Merge conflict in config.txt
error: could not revert 17a5abe... C2 enable debug
hint: After resolving the conflicts, mark them with
hint: "git add/rm <pathspec>", then run
hint: "git revert --continue".
hint: You can instead skip this commit with "git revert --skip".
hint: To abort and get back to the state before "git revert",
hint: run "git revert --abort".

$ git status --short
UU config.txt

$ git revert --abort
$ git log --oneline
08823c4 C3 enable cache
17a5abe C2 enable debug
9b96f25 C1 add config
$ git status --short

The line to notice is git revert --abort. From the middle of a conflict, that one command puts the repository back exactly where it started. revert has a safe exit even when it fails, which makes it the most forgiving command in this article.

  • git revert <commit> - creates a new commit. Reversible. Revert the revert and you are back
  • --no-edit commits with the default message instead of opening an editor
  • On conflict it stops. --abort cancels everything, --continue resumes after you fix it, --skip drops that one commit
  • For several commits, give a range as git revert <older>..<newer>. They are processed newest first
  • It requires a clean working tree to start. That precondition is stated in the documentation

What rewriting a shared commit does to everyone else

Everyone repeats the rule about using revert on pushed commits, but the reason only lands once you have watched it. A repository was created and cloned to stand in for a colleague, then the same mistake was undone two different ways. Only the repository path in the output below has been replaced, with /tmp/demo/upstream.

# the colleague's clone - it already has the bad commit
$ git log --oneline
97b65d9 C2 bad change
2135f94 C1 base

# revert on my side
$ git revert --no-edit HEAD
[main 7085b16] Revert "C2 bad change"
 1 file changed, 1 deletion(-)

# the colleague pulls
$ git pull
From /tmp/demo/upstream
   97b65d9..7085b16  main       -> origin/main
Updating 97b65d9..7085b16
Fast-forward
 app.txt | 1 -
 1 file changed, 1 deletion(-)

One Fast-forward line and it was over. The colleague did nothing and hit no conflict. Now the same starting point, but with the commit erased and rebuilt.

# the colleague's clone - same starting point
$ git log --oneline
689d5e6 C2 bad change
f43e101 C1 base

# on my side I erase C2 and redo it properly
$ git reset --hard HEAD~1
HEAD is now at f43e101 C1 base
$ printf 'v1\ngood change\n' > app.txt
$ git add app.txt && git commit -q -m "C2 good change"
$ git log --oneline
2727247 C2 good change
f43e101 C1 base

# the colleague pulls
$ git pull
From /tmp/demo/upstream
 + 689d5e6...2727247 main       -> origin/main  (forced update)
Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
Automatic merge failed; fix conflicts and then commit the result.

$ git status --short
UU app.txt
$ cat app.txt
v1
<<<<<<< HEAD
bad change
=======
good change
>>>>>>> 272724744769a515b2d1fc26330c4883201016a3

Same intention, same final content, completely different experience on the other end. A forced update appears and conflict markers land inside the file. One commit I saved myself turned into one conflict resolution per person on the team - performed by people who have no idea what happened.

Force pushing (git push --force) adds a further hazard: it also erases anything somebody else pushed since your last fetch. --force-with-lease guards against that by only updating when the remote still holds the value you last saw, but it is not permission to overwrite. On a shared branch, neither is the default answer.

Why git checkout was confusing

checkout is hard because it carried two jobs of very different weight under one name. Moving a branch and restoring a file carry different risk, yet they were spelled the same. The result depends on the argument, and when a name is ambiguous you cannot tell which meaning you are getting.

Make the collision on purpose and the answer is unambiguous. A repository containing a file called app.txt got a branch called app.txt, the file was edited, and then checkout was run.

$ git branch app.txt
$ printf 'v2\n' > app.txt
$ git checkout app.txt
M	app.txt
Switched to branch 'app.txt'
$ git branch --show-current
app.txt
$ cat app.txt
v2

# since 2.23: a collision no longer creates ambiguity
$ git switch app.txt
Switched to branch 'app.txt'
$ git restore app.txt
$ cat app.txt
v1

Somebody trying to undo a file edit ends up on a different branch and finds out later. The Git 2.23 release notes addressed this head on: switch and restore were introduced to split checking out a branch to advance its history from checking out paths out of the index or a tree-ish, both of which had lived inside the single git checkout command.

Checkout has another face when you hand it a commit rather than a branch. Going to a commit puts you in detached HEAD, where any commit you make belongs to no branch at all.

$ git checkout HEAD~1
Note: switching to 'HEAD~1'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.
...
HEAD is now at f91e4ef C1 base

$ git status | head -2
HEAD detached at f91e4ef
nothing to commit, working tree clean

$ git switch main
Previous HEAD position was f91e4ef C1 base
Switched to branch 'main'

The state itself is not dangerous. As the notice says, it is a good place to look around and experiment. The problem is leaving without moving the commits you made there onto a branch. The reflog still holds them, but naming them up front with git switch -c <name> is far less work.

git reflog - the way back from a deleted commit

If you remember one section, make it this one. A commit destroyed with reset --hard can usually be brought back, because Git writes every position HEAD has held into the reflog. Here is the whole cycle: three commits, two of them destroyed, then recovered.

$ git log --oneline
78b8ce0 C3 more work
f1acddb C2 two days of work
7810949 C1 base

# the accident
$ git reset --hard HEAD~2
HEAD is now at 7810949 C1 base
$ git log --oneline
7810949 C1 base
$ cat work.txt
v1

# the rescue: the deleted commits are right here
$ git reflog
7810949 HEAD@{0}: reset: moving to HEAD~2
78b8ce0 HEAD@{1}: commit: C3 more work
f1acddb HEAD@{2}: commit: C2 two days of work
7810949 HEAD@{3}: commit (initial): C1 base

$ git reset --hard HEAD@{1}
HEAD is now at 78b8ce0 C3 more work
$ git log --oneline
78b8ce0 C3 more work
f1acddb C2 two days of work
7810949 C1 base
$ cat work.txt
v1
v2
v3

HEAD@{1} means where HEAD was one move ago, which is exactly where it stood before the reset --hard. Knowing this takes about half the fear out of that command. The other half is the next section.

The previous position also has a name. ORIG_HEAD points at where HEAD was before a large move such as a reset or a merge. To see the moves of one branch rather than HEAD, use git reflog show <branch>.

$ git reset --hard HEAD~2
HEAD is now at f1c8944 C1
$ git rev-parse --short ORIG_HEAD
4d26ce7
$ git reset --hard ORIG_HEAD
HEAD is now at 4d26ce7 C3

$ git reflog show main
4d26ce7 main@{0}: reset: moving to ORIG_HEAD
f1c8944 main@{1}: reset: moving to HEAD~2
4d26ce7 main@{2}: commit: C3
b8efd2c main@{3}: commit: C2
f1c8944 main@{4}: commit (initial): C1
  • The reflog is local to each repository. It is not transferred by a clone, and you cannot rescue somebody else's accident from your own reflog
  • It is not permanent storage. Per the configuration documentation, gc.reflogExpire defaults to 90 days, and gc.reflogExpireUnreachable, which covers entries unreachable from the current tip, to 30 days
  • The documentation also explains the shorter figure: those entries are typically produced by commit --amend or rebase, so expiring them sooner is considered reasonable
  • Which means planning to find it in the reflog later is not a plan measured in months. Once you notice the mistake, deal with it that day

What cannot be recovered

The reflog is a record of commits, not of the working tree. A change that was never committed does not come back from anywhere. Run reset --hard over an hour of edits you never committed and this is what remains.

$ cat draft.txt
committed line
an hour of work that was never committed
$ git status --short
 M draft.txt

$ git reset --hard HEAD
HEAD is now at 371a5ec C1 base
$ cat draft.txt
committed line

$ git reflog
371a5ec HEAD@{0}: reset: moving to HEAD
371a5ec HEAD@{1}: commit (initial): C1 base

$ git fsck --lost-found
$

The reflog holds one commit and one reset, and git fsck --lost-found returns nothing at all, because Git had never seen that hour of work. There is one exception worth knowing: content you had run git add on was written as an object, so fsck has something to find. Staging often turns out to be a safety net rather than bureaucracy.

git clean -fdUntracked files and directoriesNonegit clean -nd to read the list

git revertNothing at allRevert it againClean the working tree

git stash - one line before a dangerous command

The cheapest way to avoid the accident above is stash. It parks changes that are not tidy enough to commit and leaves the working tree clean. Because the parked content is written as Git objects, it becomes as safe as a commit.

$ git status --short
 M tracked.txt
?? newfile.txt

$ git stash push -m wip
Saved working directory and index state On main: wip
$ git status --short
?? newfile.txt

# the new file was not included. -u is required
$ git stash push -u -m wip2
Saved working directory and index state On main: wip2
$ git status --short
$ git stash list
stash@{0}: On main: wip2

$ git stash pop
...
Dropped refs/stash@{0}

The key detail is that newfile.txt was still sitting there after the first stash push. Stash does not include untracked files by default. Believing you are safe and then running reset --hard or clean -fd destroys precisely the files you just created. Make -u part of the habit.

  • git stash push -u -m <note> - takes tracked and new files together. The note is what lets you recognise it later in the list
  • git stash list to inspect, git stash pop to restore and remove, git stash apply to restore and keep
  • Stashes have a reflog of their own. If you dropped one by mistake, git fsck or the earlier stash entries may still hold it
  • But it is not long-term storage. Anything you plan to keep for more than a few days belongs on a temporary branch as a commit

git clean - a deletion with no way back

clean is the simplest and the most dangerous command here. The documentation describes it as cleaning the working tree by recursively removing files that are not under version control. Because Git never tracked them, nothing about them survives inside Git once they are gone.

$ git status --short
?? build/
?? notes.md
?? out.log

# -n deletes nothing. it only prints the list
$ git clean -n
Would remove notes.md
Would remove out.log

# directories only appear with -d
$ git clean -nd
Would remove build/
Would remove notes.md
Would remove out.log

$ git clean -fd
Removing build/
Removing notes.md
Removing out.log
$ ls
keep.txt

Compare -n with -nd: without -d, directories do not appear in the list at all. Reassure yourself with -n, then run -fd, and more disappears than you expected. There is only one correct order here: -nd first, read the list, then -fd.

-x goes one step further and removes files ignored by .gitignore as well. That is handy for clearing build products, but ignore lists routinely contain local configuration such as an .env file. Those go too.

Wrong message, or a file left out

The mistakes you notice right after committing are nearly always one of two: a typo in the message, or a file that should have been included. git commit --amend handles both. It does not stack a new commit on top; it replaces the previous commit with a new one.

$ git log --oneline
d8ed825 fix bugg
689816b C1 base

# 1) fix the message only
$ git commit --amend -m "fix bug"
$ git log --oneline
ca1558d fix bug
689816b C1 base

# 2) add the file that was left out
$ git add c.txt
$ git commit --amend --no-edit
$ git show --name-only --oneline HEAD
5ef662d fix bug
b.txt
c.txt

$ git reflog
5ef662d HEAD@{0}: commit (amend): fix bug
ca1558d HEAD@{1}: commit (amend): fix bug
d8ed825 HEAD@{2}: commit: fix bugg
689816b HEAD@{3}: commit (initial): C1 base

Watch the hash: d8ed825 then ca1558d then 5ef662d, changing every time. Amend does not edit a commit; it builds a new one and swaps it in. Use it on something you have already pushed and you reproduce the forced update situation from earlier exactly. The rule is one line long: only before you push.

To undo an amend, go to the reflog. From the state above, git reset --hard HEAD@{1} puts you back on ca1558d, precisely as it was before the file was added.

Committed on the wrong branch

Working on main and committing there by mistake is common. The reflex is to destroy the commit with reset --hard and start over, which is unnecessary. Leave the commit where it is and move the label instead.

$ git log --oneline --decorate
501da69 (HEAD -> main) C2 feature work
032adf6 C1 base

# 1) create a branch right here - the commit comes along
$ git switch -c feature
Switched to a new branch 'feature'
$ git log --oneline --decorate
501da69 (HEAD -> feature, main) C2 feature work
032adf6 C1 base

# 2) go back to main and step it back one
$ git switch main
$ git reset --hard HEAD~1
HEAD is now at 032adf6 C1 base
$ git log --oneline --decorate
032adf6 (HEAD -> main) C1 base
$ git log --oneline --decorate feature
501da69 (feature) C2 feature work

Order matters. Create the branch first, then roll main back. Do it the other way round and the commit belongs to no branch, and getting it back means digging through the reflog. This procedure also assumes main has not been pushed yet. If it has, revert the change and redo the commit on the correct branch.

If you have not committed yet it is simpler still: uncommitted changes travel with you when you switch branches, and when they cannot travel, Git stops on its own.

# before committing you can simply move
$ git status --short
 M app.txt
$ git switch -c feature
Switched to a new branch 'feature'
$ git status --short
 M app.txt

# if the target branch touched the same file, Git blocks it
$ git switch other
error: Your local changes to the following files would be overwritten by checkout:
	app.txt
Please commit your changes or stash them before you switch branches.
Aborting

That refusal is a feature. switch and checkout stop themselves whenever proceeding would overwrite uncommitted work, and the message tells you the two ways out: commit or stash. For the record, --discard-changes turns the protection off and the changes are lost. At least the flag is honest about it.

Environment and how to reproduce this

Every piece of output above was produced by actually running the command in the environment below. Commit hashes and timestamps differ on every run, so those parts will not reproduce identically.

$ git --version
git version 2.48.1.windows.1

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

The operating system is Windows 10 (build 19045) and the shell is Git Bash (MSYS2), which ships with Git for Windows. The commands themselves are identical on Linux and macOS, but the hint text quoted here varies by Git version. In particular, what git status recommends used to be git reset HEAD <file> and is now git restore --staged. That is usually why an older tutorial does not match your screen.

  • Reproducing this is easy: git init in an empty directory, make three commits out of a couple of files, and nearly every example here runs as printed
  • Do not practise in a repository you actually work in. Half the commands in this article delete files
  • One thing did bite during the runs. In a very deeply nested directory, Git could not write its objects and stopped with unable to write file ...: Invalid argument. That is the Windows path length limit, and moving to a shorter path fixed it immediately
  • Turning on core.longpaths did not clear that particular error. It is not a problem you will meet on Linux or macOS

I destroyed commits with reset --hardgit reflog then git reset --hard HEAD@{n}Commits come back
I want to clear out build leftoversgit clean -nd to check, then -fdYes
I committed on the wrong branchgit switch -c <branch>, then reset --hard HEAD~1 on the originalNo

It comes back to the two questions. Where does it live, and did you share it? The first picks between restore, reset and clean; the second separates reset from revert. Above all of that sits the reflog as a safety net, and the one place the net does not reach is anything that was never committed. The rest is mostly application.

If the investigative side of history is what you are after, Git History Commands That Deserve More Love covers bisect, log -S and reflog from a working perspective, and Git Basics - Getting Started with Version Control is the place to start over from the beginning.

What I could not verify

  • Every example ran on Git 2.48.1 only. Hint text and defaults can differ on other major versions. In particular, how git pull handles divergent histories by default is an area that has changed over time
  • The same scripts were not run on Linux or macOS for comparison. The commands mean the same thing, but the path length limit is specific to Windows, and a different shell may need the printf lines written differently
  • The remote experiment used a local clone on the same disk. On a real server or hosting service, protected branch settings can refuse a force push outright, and that behaviour was not tested
  • The note that git restore and git switch are marked experimental comes from the documentation shipped with 2.48.1. I could not confirm the same wording in the current online documentation, so it may have changed between editions
  • The reflog retention figures are the defaults as documented in the configuration reference. I did not observe entries actually expiring after 90 or 30 days
  • The idea that git fsck can recover content that was only ever staged is stated on principle. It was not executed and confirmed for this article

References

  • Git 2.23.0 release notes - the original statement that switch and restore were introduced to split the two roles of checkout apart
  • git-restore documentation - the option definition: --staged restores the index only, --worktree the working tree, and specifying both restores both
  • git-reset documentation - the three mode definitions. --soft touches neither index nor working tree, --mixed is the default action, and --hard discards changes to tracked files
