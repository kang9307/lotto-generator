Introduction: The 22 Minutes That Shook npm

In the early hours of May 19, 2026 (UTC), a single npm maintainer account was taken over, and 637 malicious versions were published across roughly 300 of the packages it controlled inside a window of about 22 minutes. Reports differ slightly on the package count: 314 according to The Register, 317 according to SafeDep's analysis. That works out to roughly twenty-nine malicious releases per minute, a cadence no human maintainer can match by hand, which points to an automated publish script. The short window and the fact that one account controlled hundreds of packages are the lesson: the JavaScript ecosystem still hangs on maintainer credentials as a single point of failure.

The incident is not a one-off. As this article recaps, npm has been hit by structurally similar attacks almost every year - event-stream in 2018, ua-parser-js in 2021, colors and faker in 2022, lottiefiles in 2024, and the self-spreading Shai-Hulud worm in September 2025. According to SafeDep, the payload in this incident belongs to the same Mini Shai-Hulud toolkit used in a compromise of SAP-related npm packages about three weeks earlier. The affected set included packages that sit deep inside other libraries' dependency trees - size-sensor (about 4.2M monthly downloads), echarts-for-react (about 3.8M), @antv/scale (about 2.2M), and timeago.js (about 1.15M) - so projects that never installed them directly could still be exposed.

This piece checks the facts against the discovery reports and official GitHub and npm announcements, then focuses on what JavaScript teams should actually do: a concrete defense playbook with 4 emergency steps for today and 7 long-term strategies. The framing is practical: the goal is to leave you with a checklist you can apply before the next 22 minutes arrive. On 2026-09-29 the facts were re-checked against primary sources, corrected where they were wrong, and a section on later developments was added.

Incident Overview - What, When, and How

Based on the published analysis and reporting, the shape of the incident is the following. This article paraphrases rather than reprinting any advisory verbatim, and lists only what could be confirmed.

  • Timeframe: began around 01:39 UTC on May 19, 2026. SafeDep recorded two waves, 01:39-01:56 and 02:05-02:06; press reports summarize it as a burst of about 22 minutes.
  • Scope: 637 malicious versions across 314 (The Register) to 317 (SafeDep) packages, including many packages in the @antv scope plus size-sensor, echarts-for-react, and timeago.js.
  • Entry vector: not a bundle of many maintainers' tokens but one maintainer account that maintained more than 500 AntV-related packages (547 by SafeDep's count). How that account was compromised has not been disclosed in the public analysis.
  • Payload pattern: a preinstall hook (not postinstall) ran an obfuscated Bun script of about 498KB. It harvested cloud credentials (AWS, GCP, Azure), GitHub and npm tokens, SSH keys, Kubernetes and Vault tokens, and database connection strings, then exfiltrated them to attacker-created public GitHub repositories and an external server.
  • Discovery: a security researcher first reported the malware on GitHub, and SafeDep published a detailed analysis (as reported by The Register).
  • Containment: some versions were deprecated with a "published in error" message and others were removed. GitHub said it was monitoring the situation and disabling malicious npm packages under its Acceptable Use Policies.

The most important number in that list is twenty-two. Whether the window was deliberately designed is not known. What it shows is that even a short burst is enough for CI pipelines that resolve semver ranges (^, ~) to pull a fresh malicious version during that time. The gate at install time matters more than detection speed.

Attack Mechanism - Stolen Credentials Plus Automation

The technically interesting part of this story is how unexciting the mechanism is. There is no exotic zero-day, no novel sandbox escape, no clever cryptographic break. There is simply credential theft plus automation. That is exactly what makes it dangerous - when one account holds publish rights to hundreds of packages, npm's authentication and publishing model becomes a single point of failure.

1) Account Takeover Phase

The public analysis does not say how the account was taken over. The usual npm takeover vectors are unglamorous: phishing aimed at maintainers, malware on maintainer workstations, reuse of tokens leaked earlier, and .npmrc files accidentally pushed to public repositories. Because this payload itself harvests npm and GitHub tokens, it is clear that tokens leaked in one infection can become the key to the next compromise. And 2FA did not fully protect accounts whose 2FA-bypass tokens leaked - GitHub itself acknowledged that an attacker could use such a token to take over an account (see What Happened Next).

2) Mass Publish Phase (the 22-Minute Window)

With one account that holds publish rights, pushing prepared malicious variants to that account's packages one after another is not hard. Scripted calls to npm publish can reach dozens of publishes per minute, and 637 versions in about 22 minutes is consistent with that.

3) Payload Execution Phase (Victim Side)

The malicious versions ran their script through the Bun runtime from a preinstall hook. SafeDep also found a second path: an optional github: dependency that fetched commits from GitHub, which could work even if install hooks were blocked. On infected machines the payload planted auto-run entries in AI coding tool and editor settings (.claude/settings.json, .vscode/tasks.json) and installed a persistent service, so one install could spread to other workspaces on the same machine. The risk splits into two profiles depending on where npm install runs. Local developer machines leak tokens and keys and may keep a persistent backdoor. CI/CD environments leak deployment tokens and any secret that lives in the build environment. This article considers the CI case worse, because CI tokens often carry broad permissions.

Historical Context - The Same Pattern, Year After Year

npm supply chain attacks are not new. The recurring shape of these incidents is what should worry us more than any single payload.

  • 2018, event-stream: a maintainer handed the package to a stranger, who shipped a malicious version targeting a Bitcoin wallet project. The first widely understood "trust handoff" attack.
  • 2021, ua-parser-js: a maintainer account compromise pushed malicious versions of a very widely downloaded package.
  • 2022, colors and faker: a maintainer deliberately broke their own packages. Not a malicious third party - a reminder that trust is voluntary.
  • 2023, the typosquatting boom: many malicious packages registered with names one keystroke away from popular libraries.
  • 2024, lottiefiles: an SDK package compromised to go after users' wallet data.
  • September 2025, Shai-Hulud: a self-replicating worm that used compromised maintainer accounts to inject install scripts. GitHub said more than 500 packages were affected, and it led GitHub to announce a plan to harden npm authentication and tokens.
  • May 2026, this incident: smaller than the 2025 Shai-Hulud wave, but notable because the same family of tooling (Mini Shai-Hulud) is being reused weeks apart.

The pattern is brutally consistent: maintainer credentials break, the registry permits the publish, downstream consumers pull the new version. Each incident produces ad-hoc fixes, but structural change - provenance, sigstore, trusted publishing, hardware-key enforcement - takes time to reach every package.

Why npm Keeps Getting Hit - 5 Structural Weaknesses

1) Single-Maintainer Norm

Many npm packages are maintained by one or two people. When that single set of credentials breaks, a package with millions of downloads is fully exposed - and when one account holds rights to hundreds of packages, as here, the damage spreads all at once. Other registries share this property, but npm's culture of many small packages tends to amplify the consequences.

2) Deep Transitive Trees

A project that directly depends on ten packages installs many more once transitive dependencies are counted. Run npm ls --all to see the difference in your own project. That means code from packages you have never heard of, written by maintainers you cannot name, runs in your build environment.

3) Arbitrary Code Execution via Install Scripts

npm can run preinstall, install, and postinstall scripts during installation. Legitimate uses exist (native module builds, for example), but these hooks are also a frictionless channel for attacker payloads. Some package managers default them off. At publication npm ran them by default; since npm v12 in July 2026, dependency install scripts are blocked by default (see What Happened Next).

4) Weak Maintainer Trust Transfer

Handing a package to a new maintainer is a lightweight process. There is no strong identity verification of the recipient, no automatic notice to consumers, and no built-in cooling-off period during which downstream projects could re-evaluate.

5) Slow Provenance Adoption

npm provenance was introduced in 2023, but not every package uses it. Provenance proves which CI workflow built a package; it does not prove the code is safe, and if the CI workflow itself is compromised a malicious build can carry provenance too. Still, it helps distinguish a version published from a laptop with a stolen token from one published by a legitimate CI run, so wider adoption shrinks the surface for incidents like this one.

4 Emergency Steps to Take Today

This section is the highest-value part of the article. Every JavaScript team should run through these four steps within the current week.

1) Audit Every Active Project

Start with the obvious commands across every active project.

npm audit --audit-level=high
npm audit signatures   # verifies registry signatures and provenance
npm outdated

npm audit signatures is the underused command here. It verifies the registry signatures and provenance attestations of downloaded packages. If you pulled packages around the incident date (May 19), run it once more.

2) Diff Your Lockfile

Walk the recent history of package-lock.json and yarn.lock, and check whether affected packages are in your tree.

git log --since="2026-05-18" -- package-lock.json
grep -nE "size-sensor|echarts-for-react|timeago\.js|@antv/" package-lock.json

If a lockfile changed inside the incident window or an affected package is present, compare the resolved version against GitHub Security Advisories and the discoverers' list of affected versions. A version bump that landed without a paired PR description is a red flag, especially if it came in with an otherwise unrelated change.

3) Invalidate Every Cache

Anywhere a malicious tarball might be cached, blow it away.

npm cache clean --force
rm -rf node_modules
npm ci   # clean reinstall from the lockfile

Do not forget GitHub Actions actions/cache, GitLab CI cache, and any internal Nexus or Verdaccio mirror. A poisoned tarball persisting in your private mirror nullifies every other step in this list.

4) Rotate Exposed Tokens and Secrets

This payload targeted tokens and keys in environment variables and config files. Rotate, do not just inspect, any of the following that were present in an environment where an affected version was installed on or after May 19, 2026.

  • npm publish tokens (top priority if used in CI)
  • GitHub PATs and Actions tokens
  • AWS, GCP, and Azure access keys
  • SSH keys, Slack tokens, and webhook URLs
  • Database connection strings and internal API secrets

Along with rotation, check for the traces SafeDep flagged: unknown public repositories created under your GitHub account, unfamiliar auto-run entries in .claude/settings.json or .vscode/tasks.json, and unknown persistent services. Rotating tokens while leaving a persistent implant in place simply leaks the new tokens too.

7 Long-Term Defense Strategies

1) Move to Trusted Publishing and npm Provenance

If you publish to npm, replace long-lived tokens with trusted publishing (OIDC). According to the npm docs it requires npm CLI 11.5.1 or later and Node 22.14.0 or later, and in GitHub Actions the workflow needs permissions: id-token: write. When you publish through trusted publishing from GitHub Actions or GitLab CI/CD, provenance attestations are generated automatically by default. After setup, npm strongly recommends selecting "Require two-factor authentication and disallow tokens" in the package's publishing access settings. On the consumer side, npm audit signatures verifies signatures and provenance.

2) Enforce Frozen Lockfiles in CI

Use npm ci or yarn install --frozen-lockfile in every CI job. The contract is simple: if the lockfile does not match the manifest, the build fails. This single change closes off "an attacker quietly publishes a new version and your CI pulls it overnight."

3) Generate and Store SBOMs

Produce a Software Bill of Materials on every build, using CycloneDX or SPDX. Tools like @cyclonedx/cyclonedx-npm are easy to add. The payoff is that the next time an advisory drops, you can answer "do we use this package" quickly.

4) Use Dependabot or Renovate, Never with Auto-Merge

Automate the creation of update PRs but never the merging of them. The PR is the gate where a human checks npm view for the new version's maintainer, publish timestamp, and download trend. Auto-merge defeats the entire point.

5) Quarterly Dependency Audits

Put a one-hour meeting on the calendar every quarter with three items: remove dependencies you no longer use, replace deprecated packages, and review packages whose maintainers have gone inactive. That hour greatly shortens the time it takes to scope your exposure when the next incident hits.

6) Minimalist Dependency Policy

Add a mandatory PR review question: "is this dependency worth the risk?" Many small utilities - left-pad style helpers, simple date formatters, trivial validators - can be inlined in twenty lines of code. Fewer dependencies, smaller attack surface. The point is not to write everything from scratch; the point is to make the import decision conscious.

7) Layer Behavioral Scanners

Add a behavioral scanner such as Socket.dev on top of plain npm audit. These tools flag suspicious behavior - unexpected network calls, eval, install-script patterns, sudden maintainer changes - rather than only matching against known advisories. Phylum, which this article also named at publication, had its technology acquired by Veracode in January 2025 and is now part of Veracode's offering. Behavioral scanners are the best chance of catching the next 22-minute event before it lands in production.

Hardening Your CI/CD Pipeline - GitHub Actions Example

Putting the strategies above into a single workflow looks something like this. Only the security-critical gates are shown. Node 20 reached end of life in April 2026, so the example now uses the LTS line 24. Give id-token: write only to the publish job, not to ordinary builds.

name: secure-build
on: [push, pull_request]
permissions:
  contents: read
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '24'
          cache: 'npm'

      # 1) frozen lockfile - fail fast on drift
      - run: npm ci

      # 2) audit gates
      - run: npm audit --audit-level=high
      - run: npm audit signatures

      # 3) generate SBOM
      - run: npx @cyclonedx/cyclonedx-npm --output-file sbom.json
      - uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.json

      # 4) behavioral scan (Socket.dev example)
      # - uses: socket-security/socket-cli-action@v1

      - run: npm test
      - run: npm run build

The key property is that any failed step kills the build. This is the central message of the entire article: emergency response should not depend on human willpower. It should be encoded as CI gates that a tired developer cannot accidentally bypass at 2am.

Applying This in Real Organizations

Common friction points and how to navigate them.

  • Startups: rarely have a dedicated security engineer. Lean on free tools - npm audit, Dependabot, the Socket.dev free tier - to cover much of the risk before chasing perfection. The goal is to start, not to finish.
  • Mid-size and large companies: if you run an internal Nexus or Verdaccio mirror, push allowlists and blocklists at the mirror layer. One block in the mirror affects every developer instantly.
  • Regulated industries (finance, healthcare, government): SBOMs and signature verification should be codified as written standards, not informal habits.
  • Indie developers and freelancers: your laptop is your infrastructure. Stop storing tokens in .env as plaintext; adopt a secrets manager such as 1Password CLI or doppler.

Where Individual Responsibility Ends and Ecosystem Responsibility Begins

If a team executed every recommendation in this article, supply chain attacks would still not be eliminated. That is the honest position. Some risks cannot be fixed by any individual team because they live in the design of the registry itself. The remaining responsibility belongs to the ecosystem.

At publication, this article named three ecosystem changes: mandatory hardware-key authentication for maintainers of high-impact packages; incentives or requirements for provenance on the most-downloaded packages; and a default-off posture for install scripts. The third became the default in npm v12 in July 2026, and the direction of the first (restricting 2FA-bypass tokens, moving to trusted publishing) is being rolled out in phases. The dates are listed in What Happened Next.

Trends for the Second Half of 2026 - The Outlook at Publication

The following is the outlook as written at publication (2026-05-22). Changes that were later confirmed are listed separately in What Happened Next.

  • Provenance adoption acceleration: incidents typically trigger a wave of voluntary maintainer adoption.
  • Behavioral scanners going mainstream: behavioral scanners spreading through free tiers for open source maintainers.
  • SBOM mandates spreading: in the wake of US Executive Order 14028, more procurement contracts in the public sector and finance requiring SBOM delivery.
  • AI-assisted dependency review: AI code review tools posting natural-language risk summaries on PRs that add new dependencies.
  • Renewed interest in alternative registries: deno, jsr, and bun's registry options evaluated more seriously, though npm replacement is unrealistic in the short term.

Conclusion and a 15-Point Checklist

The one-line takeaway: supply chain security is not a tool, it is a system, and the system is built from small CI gates that a tired developer cannot accidentally bypass. The next window may be shorter than this one. The only durable defense is to encode the response into the build pipeline before it arrives.

This is the 15-point checklist this article compiles. Print it and pin it next to your desk. Knock items off one at a time.

  1. Run npm audit --audit-level=high across every active project.
  2. Run npm audit signatures to verify signatures and provenance.
  3. Check lockfile changes around May 19 and whether affected packages are in your tree.
  4. Invalidate every npm cache: local, CI, and internal mirror.
  5. Rotate every token or secret in environments where an affected version was installed, and check for persistence.
  6. Move publishing automation to trusted publishing and remove long-lived publish tokens.
  7. Enforce npm ci or --frozen-lockfile in CI.
  8. Gate CI on npm audit failing high-severity findings.
  9. Add SBOM generation (CycloneDX recommended) to every build.
  10. Enable Dependabot or Renovate without auto-merge.
  11. Put a quarterly dependency audit on the team calendar.
  12. Apply npm provenance to every package your team publishes (automatic with trusted publishing).
  13. Adopt Socket.dev or Snyk on a free or starter tier.
  14. Review your install-script allowlist (allowScripts in npm v12).
  15. If you run an internal npm mirror, codify an allowlist/blocklist policy.
