서론: SQL은 여전히 아프다 - 왜 다시 데이터 모델링 언어인가

데이터를 다뤄 본 개발자라면 예외 없이 겪어 본 장면이 있다. 대시보드마다 미묘하게 다른 "매출" 숫자, 조인 하나를 잘못 걸어 두 배로 부풀려진 집계, 200줄짜리 CTE 스택을 스크롤하며 도대체 무엇을 구하려던 쿼리였는지 되짚는 순간. SQL은 지금도 데이터 세계의 공용어이지만, "관계"와 "의미"를 한 곳에 선언해 두고 재사용하는 데는 여전히 서툴다.

최근 hada.io(GeekNews)에 소개된 Malloy는 이 오래된 통증에 대한 답을 자처하는 오픈소스 언어다. 이 글은 보도자료를 옮기는 대신, 공식 문서와 저장소를 직접 확인해 문법을 검증하고, "시맨틱 레이어"라는 더 큰 흐름 속에서 Malloy가 어디에 서 있는지, 그리고 AI 에이전트가 데이터를 다루는 지금 왜 이런 언어가 다시 주목받는지를 본인의 시각에서 분석한다.

1. Malloy란 무엇인가 - Looker 창시자의 두 번째 언어

1.1 Lloyd Tabb, LookML에서 Malloy로

Malloy를 이해하려면 만든 사람부터 봐야 한다. Lloyd Tabb는 2012년 Ben Porterfield와 함께 Looker를 공동 창업하고, Looker의 데이터 모델링 언어 LookML을 설계한 인물이다. LookML은 "지표 정의를 버전 관리 아래 두자"는 아이디어를 처음 상용화한 언어로, 이후 시맨틱 레이어 논의 전반의 원형이 됐다. Looker가 2019년 구글에 인수된 뒤 Tabb는 구글 팀과 함께 새 언어를 실험하기 시작했고, 이것이 2022년 공개된 Malloy다. 즉 Malloy는 아마추어의 사이드 프로젝트가 아니라, 시맨틱 모델링 언어를 상용화까지 밀어붙여 본 사람이 그 경험을 바탕으로 다시 설계한 두 번째 시도다.

1.2 핵심 아이디어를 한 줄로

Malloy는 공식적으로 "데이터 관계와 변환을 기술하는 오픈소스 언어"이며, 시맨틱 모델링과 쿼리 언어를 겸한다. 결정적 차이는 이것이 새로운 데이터베이스나 실행 엔진이 아니라는 점이다. Malloy로 쓴 모델과 쿼리는 컴파일되어 BigQuery·Snowflake·PostgreSQL·MySQL·Trino·Presto·Databricks·DuckDB·MotherDuck 등 이미 쓰고 있는 SQL 엔진 위에서 그대로 실행된다. 현재 malloydata 아래 MIT 라이선스 오픈소스로 개발되며, GitHub에서 2.5천 개 이상의 스타를 받았다.

2. SQL의 오래된 고통 - 무엇이 문제였나

2.1 반복되는 조인과 중복 로직

SQL은 관계를 표현하는 언어라기보다, 매 쿼리마다 관계를 새로 서술하는 언어에 가깝다. 같은 세 테이블을 조인하는 쿼리를 이번 주에도, 다음 주에도, 다른 팀원도 각자 다시 쓴다. 조인 조건을 한 곳에 정의해 두고 계속 재사용할 방법이 SQL 자체에는 없다. 그 결과 조인 로직은 수십 개 쿼리 파일에 복사되고, 스키마가 바뀌면 그 복사본을 일일이 찾아 고쳐야 한다.

2.2 시맨틱의 부재 - 같은 지표, 다른 숫자

더 근본적인 문제는 SQL에 "의미"를 담을 자리가 없다는 것이다. "활성 사용자"나 "정시 도착률"처럼 조직이 합의해야 할 지표도 SQL에서는 그때그때 SELECT 절에 다시 풀어 써야 한다. 분석가 A는 취소 건을 빼고 계산하고 분석가 B는 포함해서 계산하면, 같은 이름의 지표가 대시보드마다 다른 숫자를 낸다. 이는 실수가 아니라 SQL이 애초에 "지표의 정의"라는 개념 자체를 갖고 있지 않기 때문에 생기는 구조적 문제다.

2.3 길고 읽기 어려운 쿼리, 그리고 팬아웃 함정

조인이 여러 겹 쌓이면 집계 결과가 조용히 부풀려지는 팬아웃(fan-out)·캐즘(chasm) 함정도 SQL의 고질병이다. 예를 들어 주문 테이블과 배송 이벤트 테이블을 조인한 뒤 SUM을 걸면, 한 주문에 배송 이벤트가 여러 건 걸려 있을 경우 매출이 중복 합산된다. SQL 자체는 이 위험을 경고해 주지 않는다. 결과 숫자는 그럴듯해 보여서, 틀렸다는 사실을 알아채기까지 오래 걸린다.

3. Malloy의 접근 - 관계를 모델로 선언하고 재사용한다

3.1 source와 extend - 한 번 정의하고 계속 쓴다

Malloy의 출발점은 source다. 테이블 하나를 가리키는 source를 정의하고, extend 블록 안에 그 테이블에 딸린 측정값(measure)과 차원(dimension), 조인(join)을 함께 묶어 둔다. 공식 문서가 보여주는 예시는 다음과 같다.

source: airports is duckdb.table('airports.parquet') extend {
  measure:
    airport_count is count()
    avg_elevation is elevation.avg()
}

이렇게 정의된 source는 파일 하나에 살아 있는 재사용 가능한 모델이 된다. 이후 이 모델로 쿼리를 쓰는 사람은 airport_count가 정확히 무엇을 세는지 다시 고민할 필요가 없다.

3.2 measure - 지표를 이름 뒤에 봉인한다

SQL이라면 매번 CASE WHEN과 필터를 반복해야 했을 "정시 도착률" 같은 지표도, Malloy에서는 한 번만 정의하면 이름으로 부를 수 있다. 공식 저장소가 제시하는 예시가 정확히 이 지점을 짚는다.

measure: on_time_rate is
  count() { where: cancelled = 'N' and diverted = 'N' and arr_delay < 15 }
  /
  count() { where: cancelled = 'N' and diverted = 'N' }

취소·회항 여부와 지연 기준이라는 비즈니스 로직이 단 한 곳에 박제된다. 다음부터 누구든 on_time_rate만 부르면 되고, 정의를 바꾸고 싶으면 이 한 곳만 고치면 그 지표를 쓰는 모든 쿼리에 반영된다.

3.3 join_one·join_many - 조인을 모델에 새기고, 팬아웃을 언어 차원에서 막는다

join_one: carriers with carrier
join_many: flights2 on code = flights2.origin

조인을 소스 정의 안에 한 번 선언해 두면, 이후 쿼리는 조인 키를 다시 쓸 필요 없이 관계로 이어진 필드를 이름으로 참조한다. 더 중요한 것은 집계 방식이다. Malloy는 여러 테이블이 조인된 상태에서도 집계가 중복 계산되지 않도록 대칭 집계(symmetric aggregate) 방식으로 계산한다. 조인이 몇 겹으로 쌓여도 팬아웃으로 숫자가 부풀려지는 사고를 언어 차원에서 막아 준다는 뜻이다. SQL이라면 개발자가 DISTINCT나 서브쿼리로 직접 막아야 했던 문제다.

3.4 run과 nest - 쿼리 안에 쿼리를, 한 결과 안에 여러 그룹을

run: airports -> {
  group_by: state
  aggregate: airport_count
  nest: by_facility_type is {
    group_by: fac_type
    aggregate: airport_count
  }
}

run: 뒤에 오는 -> 파이프라인은 소스에서 쿼리로 데이터가 흘러가는 구조를 그대로 코드에 옮겨 놓은 모양이다. nest는 SQL이라면 별도 쿼리를 여러 번 날리거나 복잡한 GROUP BY ROLLUP을 써야 했던 "한 결과 안에 하위 그룹별 세부 내역을 함께 담기"를 한 블록으로 표현한다. 실행 결과도 평평한 표가 아니라 중첩된 구조로 돌아와, 상위 그룹과 하위 그룹의 관계가 결과 자체에 그대로 남는다. 이미 만든 쿼리는 view로 저장해 두고 + { }로 이어 붙여 다시 다듬을 수도 있다. 이 짧은 문법 조각들은 화려한 신기술이 아니다. 다만 SQL이 매번 처음부터 다시 쓰게 만들던 것들을 "한 번 정의하고 이름으로 재사용"하는 방향으로 옮겨 놓았을 뿐이다. 그 "뿐"이 누적되면 쿼리 파일 수십 개가 모델 하나와 짧은 호출들로 줄어든다.

4. SQL로 컴파일된다는 것의 의미 - 새 엔진이 아니라 레이어

Malloy 팀은 이 언어를 SQL의 대체재가 아니라 그 위에 얹는 레이어로 설명하며, 자바스크립트와 타입스크립트의 관계에 비유한다. 타입스크립트가 결국 자바스크립트로 컴파일되어 브라우저에서 실행되듯, Malloy도 결국 각 데이터베이스에 맞는 SQL로 컴파일되어 실행된다. 이 설계가 중요한 이유는 도입 비용에 있다. 새 데이터베이스나 새 실행 클러스터를 들일 필요가 없다. 이미 쓰고 있는 BigQuery·Snowflake·Postgres·MySQL 위에 Malloy 모델 파일만 얹으면 되고, 로컬에서는 별도 서버 없이 DuckDB로 Parquet·CSV 파일을 바로 쿼리할 수 있다. VS Code 확장을 설치하면 스키마 탐색기, 비주얼 쿼리 빌더, 결과 미리보기까지 에디터 안에서 바로 쓸 수 있다.

5. '시맨틱 레이어' 흐름 속의 Malloy - dbt·LookML·Cube와 비교

5.1 계보 - Looker의 유산이 갈라진 세 갈래

"지표를 한 곳에서 정의하고 여러 곳에서 재사용하자"는 아이디어 자체는 새롭지 않다. LookML이 그 상용화의 원형이었고, 이후 시맨틱 레이어라는 흐름이 여러 갈래로 갈라졌다. dbt는 변환 파이프라인 위에 Semantic Layer를 얹어 YAML로 지표를 정의하고 dbt Cloud API로 서빙한다. Cube는 정의와 서빙을 함께 제공하는 헤드리스 시맨틱 레이어로, API·임베디드 분석·AI 에이전트 연동을 겨냥한다. Malloy는 이 흐름과 계보를 공유하면서도, 특정 BI 제품이나 변환 프레임워크에 종속되지 않는 독립 오픈소스 언어라는 점에서 다른 길을 걷는다.

5.2 무엇이 다른가

5.3 냉정하게 볼 지점

hada 토론에서 나온 지적처럼, C# LINQ 같은 기존 언어도 비슷한 선언적 쿼리 경험을 준다는 반론은 타당하다. Malloy의 차별점은 "완전히 새로운 것을 발명했다"기보다 "시맨틱 모델링과 쿼리를 하나의 짧은 언어로 묶고, 그 결과를 SQL 생태계 위에 그대로 얹었다"는 통합에 가깝다. 조각 하나하나는 낯설지 않되, 묶는 방식이 다르다.

6. 무엇이 실제로 좋아지나

재사용: source 하나에 측정값·차원·조인을 정의해 두면, 이후 모든 쿼리가 그 정의를 그대로 상속한다. 새 쿼리를 쓰는 사람이 매번 조인 조건과 필터 로직을 다시 발명하지 않는다. 일관된 지표: on_time_rate 같은 지표가 한 곳에만 정의되므로, 대시보드마다 숫자가 다르게 나오는 사고가 구조적으로 줄어든다. 정의를 바꾸면 그 지표를 쓰는 모든 쿼리에 한 번에 반영된다. 중첩 결과: nest로 한 쿼리 결과 안에 하위 그룹별 세부 내역을 그대로 담을 수 있어, SQL이었다면 여러 번 쿼리를 날리고 애플리케이션 코드에서 다시 합쳐야 했던 작업이 줄어든다. 가독성: 대칭 집계 덕분에 여러 겹 조인 위에서도 SUM·COUNT를 손으로 방어할 필요가 없고, 쿼리 자체가 "무엇을 구하는가"를 있는 그대로 드러낸다. 리뷰어가 서브쿼리 뭉치를 해독하는 대신 쿼리 의도를 바로 읽을 수 있다.

7. 한계와 도입 장벽

생태계: SQL은 수십 년치 도구·튜토리얼·인력 풀을 갖고 있다. Malloy는 2022년에 나온 언어로, VS Code 확장과 malloy-composer 정도가 주요 도구이며 서드파티 BI 연동이나 커뮤니티 규모는 아직 SQL·dbt 생태계에 비할 바가 못 된다. 학습 곡선: source/extend, measure/dimension, join_one/join_many, run/nest 같은 새 개념과 키워드를 팀 전체가 다시 익혀야 한다. SQL을 이미 잘 아는 팀일수록 "왜 새 언어를 배워야 하는가"라는 저항이 생기기 쉽다. 팀 표준의 부재: 시맨틱 모델은 누군가 소유하고 유지보수해야 한다. 이를 세우고 지킬 담당자나 프로세스가 없으면, 모델 파일이 또 다른 스파게티가 될 위험이 있다. 기존 SQL 자산: 이미 수백 개의 뷰·저장 프로시저·BI 대시보드가 SQL로 짜여 있는 조직이라면, 이를 Malloy 모델로 옮기는 작업 자체가 비용이다. SQL을 대체하지 않고 그 위에 얹힌다는 설계 덕분에 점진적 도입은 가능하지만, 전면 전환은 별개의 프로젝트급 결정이다.

8. AI 시대, 시맨틱 모델이 다시 중요해지는 이유

최근 본지가 다룬 Wes McKinney 인터뷰 분석과 데이터가 유일한 해자다 분석에서 공통으로 짚었듯, AI가 코드 작성 자체를 값싸게 만들수록 "무엇을 만들지, 무엇이 옳은 정의인지" 판단하는 층위가 더 중요해진다. 시맨틱 모델은 바로 그 판단을 코드로 박제해 두는 층이다.

LLM에게 원시 데이터베이스 스키마를 그대로 열어 주면, 매번 새로 SQL을 추론해 조인을 다시 짜고 지표를 다시 정의한다. 이 과정에서 존재하지 않는 컬럼을 참조하거나, 조인이 잘못 걸려 팬아웃으로 숫자가 부풀려지거나, 지표 정의가 매번 미묘하게 달라지는 오류가 반복된다. 결과 SQL은 문법적으로 멀쩡해 보여서, 틀렸다는 사실을 알아채기가 더 어렵다.

Malloy 진영에서 나온 malloyyo 같은 프로젝트는 이 문제에 직접 답한다. Malloy로 정의해 둔 시맨틱 모델을 MCP(Model Context Protocol)로 AI 에이전트에 그대로 서빙해, 에이전트가 SQL을 처음부터 새로 짜는 대신 이미 검증된 측정값·차원·조인을 이름으로 요청하게 만든다. AI가 접근할 수 있는 범위 자체가 모델 안으로 한정되고, 계산 로직은 이미 한 번 검증된 채로 재사용되므로 결과가 "우연히 맞다"가 아니라 "구조적으로 맞다"에 가까워진다.

본인의 해석은 이렇다. 모델과 코드 생성이 값싸질수록 경쟁력은 그 위에 쌓은 정의와 판단으로 옮겨간다는 논지는 데이터 영역에서 특히 또렷하다. Malloy 같은 시맨틱 모델링 언어가 AI 시대에 재조명되는 이유는 기능이 늘어서가 아니라, AI가 참조할 "이미 옳다고 합의된 정의"를 만드는 도구이기 때문이다.

9. 어떤 팀에 맞나, 어떻게 시작하나

9.1 어떤 팀에 맞나

여러 분석가가 같은 지표를 반복해서 다르게 계산하거나, 대시보드마다 숫자가 미묘하게 다른 조직. 조인이 여러 겹인 스키마 위에서 팬아웃 사고를 자주 겪는 팀. AI 에이전트에게 데이터 접근을 열어 주면서도 결과의 정확성을 통제하고 싶은 팀에 특히 유효하다. 반대로 쿼리가 단발성이고 팀 표준화에 쓸 여력이 없다면, 지금 당장은 이점이 크지 않을 수 있다.

9.2 시작 방법 - DuckDB 로컬

시작 장벽은 낮다. VS Code에 Malloy 확장을 설치하고, 로컬 Parquet 또는 CSV 파일을 duckdb.table()로 가리키는 source 하나를 .malloy 파일에 적는 것으로 충분하다. 별도 서버나 클러스터, 계정 없이 노트북에서 곧바로 모델을 정의하고 run: 쿼리를 실행해 결과를 확인할 수 있다. 감이 잡히면 같은 모델 정의를 BigQuery나 Postgres 같은 실제 운영 엔진으로 그대로 옮겨 확장하면 된다.

결론

Malloy는 SQL을 밀어내려는 언어가 아니라, SQL이 애초에 잘하지 못했던 것 - 관계의 재사용, 지표의 일관성, 안전한 집계 - 을 짧은 문법으로 메우려는 시도다. Looker와 LookML을 상용화까지 밀어붙여 본 사람이 다시 설계한 언어라는 이력, SQL 엔진을 대체하지 않고 그 위에 얹는 설계, 그리고 AI 에이전트가 참조할 검증된 정의를 제공한다는 시대적 쓸모까지 겹쳐 보면, Malloy는 단발성 실험을 넘어서는 흐름의 한 지점으로 보인다. 다만 생태계와 팀 표준화라는 도입 장벽은 실재하며, 전면 도입보다는 팬아웃과 지표 불일치가 반복되는 팀부터 로컬 DuckDB로 가볍게 실험해 보는 편이 합리적이다. 2026년 7월 기준, 이 언어가 시맨틱 레이어 논쟁의 승자가 될지는 아직 이르다. 그러나 SQL의 오래된 통증을 정확히 짚었다는 점만은 분명하다.
