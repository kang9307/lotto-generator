1. 셀프테스트의 초록불이 감춘 것과 바이브 코딩의 맹점

인공지능 코딩 에이전트에게 구현을 맡기면서 신뢰성을 확보하기 위해 가장 흔히 도입하는 방식은 셀프테스트(Self-test) 자동화다. 작성된 스크립트에 --selftest 실행 옵션을 부여하고, 내부 검증 루틴이 오류 없이 마무리되면 터미널에 GATE_OK라는 성공 신호를 출력하게 만드는 규칙이다. 에이전트가 문제를 스스로 인지하고 해결했다는 증거로 초록불 신호를 받아들인 개발자는 자연스럽게 작업이 완료되었다고 판단하기 쉽다.

그러나 테스트 통과라는 기계적 합격 신호가 실제 운영 데이터 환경에서의 정상 작동을 보장하지는 않는다. 유닛 테스트가 버그를 잡기보다 영역 표시에 머무르기 쉽다는 점은 유닛 테스트 테스팅 비판에서 살펴본 바 있고, 겉보기에 멀쩡하게 돌아가는 스택이 감추고 있는 위험은 바이브 코딩 스택 신화 점검에서도 다루었다. 또한 실행 검증의 오케스트레이션 구조는 Ordewell 멀티 에이전트 분석에서 논의된 바 있다. 이번 분석은 테스트의 일반론이 아니라, 단일 에이전트가 구현 코드와 검증 픽스처를 동시에 생성할 때 발생하는 가설의 중복과 일치 현상에 초점을 맞춘다.

2026년 9월 25일과 26일 이틀간 클로드 코드(Claude Code) 에이전트를 활용해 블로그 운영 자동화 도구 세 개를 제작한 개발자 워니즈의 기록은 이 구조적 맹점을 선명하게 드러낸다. 세 도구는 모두 초록 신호를 받았으나(원장 도구는 셀프테스트 GATE_OK, 광고 점검 도구는 셀프테스트 통과, 수요 게이트는 파생어 65개로 발행 허용), 실제 운영 데이터를 주입하자마자 전혀 엉뚱한 결론을 도출하거나 실데이터 매칭에 실패했다. 이 현상이 왜 반복되는지 이해하기 위해서는 실패한 도구 세 개의 구체적인 수치와 원인을 면밀히 들여다볼 필요가 있다.

  • 자체 합격 판정의 착시 — 에이전트가 만든 테스트 데이터와 검증 로직은 자신이 작성한 구현 코드의 가정을 그대로 복제하므로 버그를 스스로 드러내지 못한다.
  • 실제 데이터와의 접점 부재 — 격리된 환경에서 가상 입력을 대상으로 돌린 단위 테스트는 외부 플랫폼의 비정형 HTML이나 예외적 응답을 포착하지 못한다.
  • 단순 산술에 기반한 인과 단정 — 복합적인 외부 시스템의 동작 결과를 중간 관측 없이 단순 비교 수식 하나로 환원하여 잘못된 시스템 원인을 출력한다.
  • 게이트 입력 구조의 취약성 — 에이전트가 포커스 키워드를 넓은 상위어로 적었고, 게이트의 입력을 게이트를 통과하려는 쪽이 직접 적는 구조라 그대로 통과됐다.

2. 사례 1: post-ledger.py — innerText 오염과 261편 중 6편 매칭

첫 번째 도구인 post-ledger.py는 Aside 브라우저 자동화로 구글 서치콘솔(Search Console)의 실적 표를 긁어와 블로그 원장에 글별 노출 수와 검색 순위를 누적하는 역할을 맡았다. 에이전트는 셀프테스트 환경에서 깔끔한 URL 문자열을 생성하여 검증을 수행했고, 아무런 문제 없이 GATE_OK를 출력했다.

2.1 서치콘솔 실적 표 수집과 버튼 문구 유입

그러나 완성된 도구를 실제 서치콘솔 실적 데이터에 연결하자 심각한 괴리가 발생했다. 블로그 원장에 등록된 전체 글 261편 가운데 서치콘솔 실적 표와 정상적으로 매칭된 글이 단 6편에 불과했던 것이다. 원인은 브라우저가 렌더링한 서치콘솔 실적 표 첫 번째 칸의 innerText를 가공 없이 그대로 읽어온 데 있었다. 화면상에는 순수한 URL만 표시되는 것처럼 보였지만, 마우스 호버 시 노출되는 조작 버튼의 텍스트가 텍스트 노드에 한꺼번에 포함되어 있었다.

https://.../mcp-server-with-cusor-ai/ 클립보드에 URL 복사 새 탭에서 열기 URL 검사

도구는 이처럼 버튼 텍스트가 꼬리표처럼 붙어버린 오염된 문자열을 완전 일치 키로 사용하여 원장의 원본 글 URL과 대조했다. 에이전트가 작성한 셀프테스트는 처음부터 순수한 URL 문자열만을 픽스처로 주입했기 때문에, 실제 브라우저 렌더링 과정에서 발생하는 텍스트 결합 문제를 전혀 예측하지 못했다.

2.2 정규식 정리 후 100편 매칭과 미확인 2가지

문제 해결은 셀 텍스트를 통째로 키로 쓰지 않고 그 안에서 URL만 뽑아 정규화하는 키 정리 함수를 넣는 것으로 이루어졌다. 원문이 그 원리를 재현해 보인 한 줄은 아래와 같다.

python3 -c "import re; raw='https://blog.wonizz.com/2025/09/12/mcp-server-with-cusor-ai/ 클립보드에 URL 복사 새 탭에서 열기 URL 검사'; print(re.search(r'https?://\S+', raw).group(0))"

키를 정규화하여 원장을 다시 채운 결과, 261편 중 100편이 서치콘솔 실적 표와 정확하게 연결되었다. 나머지 161편이 매칭되지 않은 것은 3개월 조회 창 안에서 검색 노출이 전혀 발생하지 않아 서치콘솔 표에 행 자체가 없었기 때문이며, 원문 저자는 이를 정상 범위로 판단했다. 셀프테스트 픽스처에도 버튼 문구가 붙은 실제 모양의 입력을 추가해, 같은 오염이 다시 들어오면 테스트가 먼저 떨어지게 했다. 여기서 중요한 점은 「261편 중 255편이 틀렸다」가 아니라, 100편의 정상 데이터가 존재했음에도 도구는 단 6편만 인식하고 94편을 누락시켰다는 사실이다. 한편 원문 저자는 CSS 수준에서 왜 버튼 텍스트가 innerText에 포함되었는지, 그리고 모든 행이 동일하게 오염되었을 텐데 초기 실행에서 왜 6편은 매칭에 성공했는지는 구체적으로 파고들지 않고 미확인 상태로 남겨두었다.

3. 사례 2: ad-inventory.py — 단순 산술 판정과 실제 광고 손실 2단계

두 번째 도구인 ad-inventory.py는 블로그 글의 HTML을 파싱하여 삽입된 광고 슬롯 수를 세고, 이를 외부 측정 노출 수와 대조하여 운영상의 이상 원인을 자동으로 판정하는 점검 스크립트였다. 이 도구 역시 셀프테스트를 깔끔하게 통과했다.

3.1 3.67개 대 0.94개의 산술과 렌더 실패 단정

실제 블로그 글 표본 18편을 대상으로 도구를 구동하자, 페이지당 명시된 광고 슬롯 수는 평균 3.67개였던 반면 실측 노출 수는 페이지당 0.94개로 집계되었다. 도구는 앞의 수치가 뒤의 수치의 2배를 초과한다는 단순한 산술 규칙 하나에 근거하여 다음과 같은 최종 결론을 화면에 출력했다.

원인 판정 렌더 실패

에이전트가 심어둔 판정 로직은 명시 슬롯이 실제 노출보다 많으면 렌더가 실패한 것이라는 단선적인 인과 가설에 묶여 있었다. 원문에 따르면 셀프테스트는 계산이 맞는지를 봤고 계산은 실제로 맞았다. 틀린 것은 해석이었다.

3.2 실제 브라우저 렌더 확인과 28일 보고서의 167건·118건

그러나 브라우저로 실제 페이지를 열어 슬롯이 광고 iframe으로 채워졌는지 세어 보니 결과는 도구의 판정과 완전히 달랐다. 긴 글에서는 6개 슬롯 중 5개가, 짧은 글에서는 7개 슬롯 전부가, 홈 화면에서는 2개 슬롯 전부가 광고 iframe으로 정상 렌더링되어 채워져 있었다. 렌더링은 실패하지 않았던 것이다.

28일간의 공식 광고 콘솔 보고서를 정밀 분석하여 드러난 손실의 실체는 전혀 다른 2단계 구조였다. 해당 기간 페이지당 광고 요청 수는 2.47건으로 이미 설정된 운영 목표를 넘어선 상태였다. 문제는 요청 이후 발생했다. 게재되지 않은 요청이 167건, 게재됐지만 노출로 집계되지 않은 요청이 118건이었다. 즉, 슬롯이 모자란 것도 렌더가 깨진 것도 아니라 게재 단계의 문제였다. 도구는 자신이 직접 관측할 수 없는 영역을 산술로 예단하여 잘못된 진단을 내린 셈이다.

4. 사례 3: 수요 게이트 — 키워드 분리와 파생어 65개의 허상

세 번째 도구는 블로그 글의 수요를 사전 검증하는 「수요 게이트」 자동화였다. 구글 검색창의 자동완성 파생 검색어를 수집하여, 파생어가 20개 미만인 비인기 주제는 글 작성 및 발행 파이프라인을 중지시키는 안전장치 역할을 하도록 설계되었다.

4.1 포커스 키워드 축소와 게이트 우회

2026년 9월 26일 새벽 자동 제작 과정에서 에이전트는 「리눅스 폴더 비교」 글의 포커스 키워드를 넓은 상위어인 「리눅스」로 적었다. 게이트는 그 키워드로 파생어 65개를 수집했고, 하한선인 20개를 여유 있게 넘기며 게이트를 통과했다. 이렇게 제작된 글은 그날 아침 실제로 블로그에 발행되었다.

글이 실제로 답하는 검색어인 「리눅스 폴더 비교」로 파생 검색어를 다시 재자 단 2개에 불과했다. 구글 트렌드의 12개월 검색 평균값은 0이었으며, 동일 비교군인 「리눅스 명령어」가 18.9를 기록한 것과 대조적이었다. 또한 같은 날 측정한 「리눅스 diff」의 파생어도 9개에 그쳐 기준치인 20개에 한참 못 미쳤다. 재측정으로 게이트가 막았어야 할 글임이 드러나 그 글은 삭제되었다. 게이트의 입력을 게이트를 통과하려는 쪽이 직접 적는 구조였기 때문에, 넓은 상위어를 적는 것만으로 어떤 주제든 지나갈 수 있었던 셈이다.

4.2 20개 하한과 변이 테스트 람다 실행 결과

원문은 사례 3의 재발 방지로 자동 제작 지시문에 규칙 한 줄을 넣었지만, 규칙 문장은 코드 게이트가 아니라서 온전히 막았다고 말하기는 이르다고 적는다. 한편 원문은 변이 테스트의 원리를 수요 게이트처럼 20 미만을 막는 판정으로 재현해 보인다. 원래 조건과 등호를 넣은 변이를 입력 5, 65, 20에 돌린 명령은 아래와 같다.

python3 -c "gate=lambda n: n < 20; mutant=lambda n: n <= 20; [print(n, gate(n), mutant(n)) for n in (5, 65, 20)]"

이 코드를 실행하면 다음과 같은 세 줄의 평가 결과가 출력된다.

5 True True
65 False False
20 False True

기준값 20에서 원래 로직(gate)은 발행을 허용하는 False를 반환하지만, 등호가 포함된 변이 로직(mutant)은 차단을 의미하는 True를 반환한다. 만약 에이전트가 만든 테스트에 20이라는 정확한 경계값 검증 케이스가 포함되어 있지 않았다면, 부등호 조건 하나가 바뀐 변이 코드가 유입되어도 테스트는 동일하게 통과하게 된다.

ad-inventory.py 셀프테스트 통과 실제 iframe 정상 렌더, 손실은 미게재 167건 및 노출 미집계 118건 슬롯이 노출보다 많으면 렌더 실패다
수요 게이트 파생어 65개로 발행 허용 실제 키워드 파생어 2개, 트렌드 0 (발행 후 삭제) 적힌 키워드가 글의 검색어다

5. 같은 에이전트가 만든 코드와 테스트가 공유하는 가동 결함

세 가지 실패 사례를 관통하는 핵심 결론은 매우 명확하다. 실패의 원인은 파이썬 문법 오류나 에이전트의 단순한 오타 같은 코드 결함이 아니었다. 「셋 다 코드가 아니라 입력이나 해석에 대한 가정이 틀렸고 그 가정을 코드와 테스트가 똑같이 품고 있었기 때문」이다.

개발자가 사람 동료에게 작업을 맡길 때는 구현자와 검증자가 분리되는 경우가 많다. 구현자가 외부 데이터에 대해 잘못된 가정을 하더라도, 검증자는 다른 시각에서 엣지 케이스를 던져보며 그 가정을 흔든다. 하지만 단일 에이전트에게 도구 구현과 셀프테스트를 동시에 일임하면 다음과 같은 구조적 맹점이 발생한다.

  • 가설의 대칭적 복제 — 에이전트는 코드를 작성할 때 자신이 머릿속에 구성한 데이터의 형태를 그대로 테스트의 픽스처(Fixture)로 사용한다. 브라우저 복사 텍스트에 부가 문구가 붙을 것이라는 의심을 하지 못하면, 테스트 입력값에도 깨끗한 URL만 집어넣는다.
  • 순환 논리에 빠진 검증 — 원문에 따르면 테스트는 계산이 맞는지를 봤고 계산은 실제로 맞았다. 틀린 것은 「슬롯 수가 노출 수보다 많으면 렌더 실패」라는 해석이었다. 논리적 인과가 맞는지가 아니라 계산이 규칙대로 되는지만 점검한 셈이다.
  • 테스트 케이스 확장의 한계 — 원문 저자는 테스트 케이스를 몇 개 더 늘렸어도 잡혔을 것 같지는 않다고 본다. 더 많은 테스트가 아니라 다른 종류의 확인이 필요했다는 것이 원문의 결론이다.
  • 맹목적인 완료 신호 맹신 — 터미널에 출력되는 GATE_OK 신호는 시스템이 안전하다는 객관적 지표가 아니라, 에이전트가 자신의 편향 안에서 완결성을 달성했다는 폐쇄적 확인에 불과하다.

6. 세 줄의 완료 조건 — 변이 검증, 실데이터 1회 대조, 판별 불가 남기기

워니즈는 이 세 가지 쓰라린 경험을 거친 뒤 도구 제작의 완료 규칙을 근본적으로 개편했다. 에이전트가 출력하는 단순한 GATE_OK 한 줄을 완료의 징표로 삼던 관행을 폐기하고, 세 줄의 엄격한 완료 조건을 새롭게 규정했다.

6.1 변이 테스트를 통한 망가진 코드 포착

첫 번째 완료 조건은 변이 테스트(Mutation Testing)다. 테스트 스위트의 신뢰성을 입증하기 위해, 구현 코드의 부등호나 경계값 조건을 의도적으로 비틀어 망가뜨린 코드(변이체)를 주입하고 테스트가 이를 정확히 실패로 잡아내는지 확인하는 절차다. 변이체가 들어갔는데도 테스트가 여전히 통과한다면 그 테스트는 허수아비에 불과하다. 원문에서는 자바의 PIT나 자바스크립트·C# 생태계의 Stryker 같은 전문 도구를 언급했으나, 작은 스크립트에서는 수동으로 두세 개의 변이를 주입하여 점검하는 방식을 취했다.

6.2 실데이터 1회 실행과 기대 범위의 시각적 대조

두 번째 조건은 도구가 완성된 직후 반드시 실제 운영 데이터로 1회 이상 구동해 보는 것이다. 가상으로 꾸며낸 목(Mock) 데이터에 만족하지 않고, 실제 서치콘솔이나 브라우저 환경에서 한 번 실행하여 도출된 매칭률이나 건수가 사람이 사전에 예상한 범위 안에 들어오는지 눈으로 직접 대조해야 한다. 261편 중 6편이라는 비정상적인 수치는 이 단계에서 즉각 포착된다.

6.3 관측 불가능한 영역의 판별 불가 처리

세 번째 조건은 도구가 직접 확인할 수 없는 영역에 대해 인과관계를 함부로 예단하지 않는 것이다. HTML 슬롯 수와 노출 수의 차이만으로 외부 광고 서버의 동작을 렌더 실패로 단정하는 우를 범하지 않고, 도구가 수집할 수 없는 영역은 솔직하게 「판별 불가」와 그 사유를 명시하도록 코드를 설계하는 원칙이다.

완료 조건 무엇을 막나 (원문) 이번 사례 중 해당 (원문)
1. 변이 테스트 검증 아무것도 확인하지 않는 테스트 테스트 자체의 품질
2. 실데이터 1회 대조 입력 가정의 오류 사례 1(post-ledger.py), 사례 3(수요 게이트)
3. 판별 불가 남기기 산술로 내린 단정 사례 2(ad-inventory.py)

이 세 가지 조건을 에이전트 작업 파이프라인에 이식하기 위해 작업자가 프롬프트에 직접 붙여야 하는 세 가지 요청 문장은 아래와 같이 정립된다.

  • 변이 검증 요청 — 「셀프테스트를 만든 뒤 경계값과 조건을 바꾼 변이를 두세 개 넣어서 테스트가 전부 잡는지 보여 주세요」
  • 실데이터 1회 검증 요청 — 「만든 직후 실데이터로 한 번 돌리고 매칭률이나 건수를 기대 범위와 함께 보고해 주세요」
  • 관측 한계 고지 요청 — 「이 도구가 직접 볼 수 없는 것은 판정하지 말고 판별 불가와 그 이유로 남겨 주세요」

7. 기대 범위의 사전 정의와 바이브 코딩의 현실적 경계선

세 가지 완료 조건 중에서도 가장 본질적인 지점은 「기대 범위만큼은 에이전트에게 정하게 두지 않고 사람이 먼저 적는 편이 맞다」는 원문 저자의 통찰이다. 원문이 드는 이유는 에이전트에게 맥락이 없어서가 아니라 기대값을 정하는 시점에 있다.

원문 저자에게는 「글 261편 중 적어도 수십 편은 이어져야 한다」는 감각이 있었기에 6이라는 숫자가 이상하게 보였고, 기대값이 없었다면 6편짜리 원장을 그대로 믿고 다음 단계로 넘어갔을 것이라고 적는다. 그리고 결과를 본 뒤에 정한 기대값은 그 결과에 맞춰지기 쉬우므로, 돌리기 전에 사람이 먼저 적어 두는 숫자 하나가 가장 값싼 안전장치라고 본다.

  • 기대 수치의 선제적 설정 — 매칭률 하한선, 최소 추출 건수, 예상 오차 범위는 사람이 코딩 시작 전에 프롬프트에 규정해야 한다.
  • 게이트는 규칙 문장이 아님 — 원문은 규칙 문장으로만 막혀 있는 자리는 코드 게이트로 옮기기 전까지 그 통과를 믿지 않기로 했다. 키워드와 본문의 일치율을 강제하는 정량 게이트는 이 글의 제안이다.
  • 출발선으로서의 셀프테스트 — 원문의 결론처럼, 바이브 코딩으로 맡긴 도구의 셀프테스트 통과는 작업의 완성이 아니라 본격적인 실데이터 검증을 시작할 수 있는 최소한의 출발선에 불과하다.

이 기록은 특정 블로그의 도구 세 개에서 관측된 구체적인 사례이며, 바이브 코딩 전반에서 동일한 비율로 이러한 결함이 발생한다고 일반화할 수는 없다. 원문 저자도 말할 수 있는 것은 이 세 번의 모양까지라고 밝힌다. 다만 셀프테스트의 초록불 신호를 완료로 여기며 비슷한 방식으로 일하는 경우라면 참고할 만하다. 자동화의 마지막 방어선은 테스트 코드가 아니라, 실데이터의 수치를 직시하고 관측의 한계를 인정하는 인간 작업자의 눈이다.

8. 확인하지 못한 것

본 분석은 원문 기록과 공개된 코드에 철저히 기반하여 작성되었으며, 원문에서 구체적으로 밝히지 않아 객관적으로 확인하지 못한 항목들은 아래와 같다.

  • 서치콘솔 실적 표에서 조작 버튼 문구가 왜 CSS 렌더링을 거쳐 innerText 텍스트 노드에 결합되었는지에 대한 구체적인 프론트엔드 스타일 원인은 원문 저자가 분석하지 않아 확인하지 못했다.
  • 서치콘솔 실적 표의 모든 행이 동일한 구조로 오염되었을 텐데, 초기 post-ledger.py 실행에서 왜 하필 6편의 글만 매칭에 성공했는지는 원문 저자가 들여다보지 않아 확인하지 못했다.
  • 광고 콘솔 보고서에서 언급된 167건의 미게재 요청과 노출로 집계되지 않은 118건의 요청을 유발한 구체적인 광고 중개 네트워크의 입찰 로그나 정책 위반 여부는 원문에 데이터가 없어 확인하지 못했다.
