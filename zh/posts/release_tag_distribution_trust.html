当构建停在一张申请表前

昨天还跑得好好的流水线、今天早上空手而归。脚本没动、仓库地址没动、可是 git fetch --tags 一个新标签都拉不到。远端只到上一次发布、这次版本对应的名字不见了。上游没有宕机、权限也没有被撤。只是那个名字不再出现在那个位置。

取而代之的是一条说明。填好表单提交申请、几天后、有时是几周后、会收到一个能取到单个文件的链接。文件是完整的、代码也都在。可流水线仍然停着。

这个错位就是本文的主题。改变分发路径、从外面看像是把一种下载方式换成另一种。实际上、原本挂在那条路径上的东西会跟着一起落下来。固定引用、依靠哈希才成立的校验、自动化去抓取的地址、第三方能拿到同一份东西的前提。这四样是标签与发布归档这种形式默认自带的、并不是另外搭建出来的。所以格式一变、它们就悄悄跟着消失。下面就是这份清单。

已确认的事实

2026 年 8 月 8 日、GrapheneOS 项目在自有长毛象账号上发了一条短帖。要点是谷歌把部分源码原本推送 Git 标签的做法、换成通过表单提交申请后从云端硬盘获取、申请处理正在逐渐变慢、并且他们认为这已构成 GPLv2 违规。核心句子是 Google replaced pushing Git tags for certain source code with obtaining source code via Google Drive after making a request through Google Forms.

两天后安卓专业媒体做了报道。对象被定位为 Pixel 设备的内核源码、流程是提交谷歌表单后收到云端硬盘链接、报道同时载有项目方关于原本几小时现在要几周的描述、以及更新历史被压缩成一个难以阅读的单一文件这一指摘。该报道注明已向谷歌询问、但截至发稿未获回复。

Hacker News 的讨论露出了更多技术层面。Pixel 内核与用户态驱动仓库被一并提及、有人指出安卓构建系统以每个组件一个 Git 仓库为前提并会执行 Git 命令、因此单一 tarball 形式无法直接对接。

以上就是公开材料能确认的全部范围。原帖的措辞本身就是「部分源码」、并没有确认到说明哪些仓库、从何时起被纳入的规范。因此没有依据把结论扩大到整个 AOSP。下文讨论的不是对某个组织决策的评价、而是当公开标签分发转为申请制时、下游普遍会断掉什么。

标签不是 URL、而是固定引用

如果把 Git 标签理解成「每次发布贴上去的一张标记」、这次变化的分量就不容易看清。标签实际做的事、是用一个名字把全部内容绑定到一个值上。

把结构拆开看。标签指向提交、提交由 SHA 哈希标识、这个提交指向树对象、树又用哈希指向子树与文件 blob。最顶层的一个哈希覆盖了下面的全部、这是默克尔结构。所以两个都知道 v1.2.3 这个名字的人、不用互相传文件就能确认手里的内容是否一致。差一个字节、值就不同。再加上附注标签与签名、就多出一层、也就是「是谁决定把这份快照叫这个名字」。内容对不对与来源对不对是两个问题、两者都需要。

归纳起来、公开标签同时提供四样东西。

  • 名称与内容的固定 — 所有工具都建立在同一个标签名任何时候查询都指向同一提交这一惯例之上
  • 内容的自我证明 — 哈希由内容算出、因此不需要另外的清单也能成立完整性
  • 来源的证明 — 签名标签让分发主体可以在密码学意义上被确认
  • 对称性 — 无论谁在何时索取、都能从同一地址得到同一份东西、这意味着校验可以被第三方复现

转为申请制之后、文件本身还在。剩下三样则从默认降为可选。如果分发方公布校验和、附上签名、并保证每个申请者拿到完全相同的产物、那么大部分可以被恢复、但那是需要额外设计的事情、而不是格式自带的事情。

完整性校验哈希由内容自动算出可以计算、但可能没有公开基准值可比对

归档哈希真正保证的东西

对做过打包的人来说、源码不是文件、而是「地址加校验和」这一对。形式各生态不同、结构是一样的。

  • Arch 系的 PKGBUILD — source=() 与 sha256sums=() 并排声明
  • Homebrew formula — sha256 紧跟在 url 下面
  • Nix — fetchurl 一族把哈希作为参数、写错则构建根本不会开始
  • RPM 与 Debian 打包 — 用 Source0 或 debian/watch 指定上游、并逐文件记录哈希
  • 语言生态 — 模块代理或锁文件为每个依赖固定哈希

这里有一个经常被混掉的区分。校验和同时承担两件事：一是看下载途中有没有损坏的传输完整性、二是看这是不是自己审阅并批准过的那串字节的同一性共识。前者在申请制下照样成立、后者只有当别人也能从同一地址算出同一个值时才有意义。

第二件才是关键。打包者把哈希写进配方、不是为了确认自己这次下载没坏、而是为了确认全世界的构建服务器拿到的是同一个值。上游文件一旦被悄悄替换、那一刻所有构建同时失败、而这个失败本身就是警报。

从这个角度看、自动生成的归档其实一直很脆弱。托管服务从标签现场生成的 tarball、只要压缩实现或生成逻辑变了、即便内容相同、字节也可能不同。所以谨慎的打包者一直更偏好由上传者制作并附上的发布资产、因为后者是一次固定下来的。

申请制把这个问题又往前推了一步。「同一地址」这个前提根本不成立。每个申请者的链接不同、重新申请时也可能拿到不同的产物。于是哈希仍然能算、却不再是可共享的基准。哈希校验的不是文件、而是共识。如果需要达成共识的对象并未公开、哈希就从校验装置滑向私人备忘。

可复现构建链条断在哪里

可复现构建不是浪漫的目标、而是一条链。任何一环断掉、结论就从「我们校验过了」变成「我们决定相信」。

  1. 源码固定 — 从哪串字节出发
  2. 工具链固定 — 用哪个编译器与库版本跑的
  3. 环境固定 — 路径、时间、区域设置等不确定因素是怎么压住的
  4. 输出比对 — 两个独立方是否得到同一个产物

现代供应链证明工具就架在这条链上。构建来源证明用带签名的文档记录「这个产物由哪份源码经哪个构建器产出」、SBOM 在部件清单之外记录每个部件的原始位置、签名工具再给这些文档附上身份。三层都建立在第一环是公开的这一前提上。

SBOM 这一侧最为清晰。如果在部件条目的下载位置字段里填申请表单的地址、那它就不是材料的地址、而是流程的地址。SBOM 存在的理由是回答「这个产物里有什么、又能从哪里再次取得」、而后半句变成了有条件的。格式校验能通过、目的只达成了一半。

输出比对被堵得更直接。复现校验的定义本身就是独立第三方用同样的输入得到同样的结果、而如果这个第三方要花几周才能拿到输入、校验就从常态活动变成了偶发事件。不是常态的校验抓不住回归。

历史本身就是依据的场合

把「只有快照」与「带完整提交历史」之间的差别归入便利性、就会低估它的分量。历史是被当作依据使用的、不是舒适度。实务中真正消耗历史的地方有五处。

  • 回归二分查找 — 要找的是哪一次变更弄坏的、不是哪个版本。如果两份快照之间是几万行一整块、二分查找根本不成立
  • 安全补丁识别与回移 — 必须知道哪个提交修的是哪个漏洞、才能把它移到旧分支。快照只告诉你「已经修了」、不告诉你「改在哪里、为什么」
  • 根因分析 — 有提交信息与变更范围放在一起、才能回答「这一行为什么会写成这样」。只剩代码、意图就没了
  • 作者与许可证追溯 — 确认某段代码从哪里来、附带什么条件、通常要顺着历史往回走
  • 回馈上游 — 要把本地修改送回上游、就得把上游状态与自己的改动分开。基线是一整块时、分离成本会陡增

许可证条文在这里自然登场。GPLv2 第三条这样定义源码。The source code for a work means the preferred form of the work for making modifications to it. 历史是否属于那个「进行修改时的首选形式」、这场争论的技术核心就压在这一句话上。

一方认为、如果上游内部按提交开发、并以那种形态进行修改、那么被压缩的单一快照按定义就不是首选形式。另一方认为、条文只要求可构建、可修改的完整源码、并未明示版本控制历史、而且不带历史只发布源码的先例由来已久。哪种解读正确属于条文解释与管辖的问题、本文不做裁定。但技术上消失了什么、上面五项已经足够清楚。

谁会受阻 - 四类角色、四种不同原因

笼统说一句「变得不方便」、是拿不出对策的。受阻的性质因角色而异、可替代的手段也就不同。

发行版打包者 - 先死掉的是探测

打包者最先失去的不是文件、而是信号。新版本出现这件事、由工具而不是人来察觉、是被广泛采用的结构。定期读取上游发布页或标签列表、探测到新版本后发出更新提醒、甚至生成草稿提交。公开列表消失、这一层就整层停摆、而察觉一旦变慢、安全修复到达发行版的时间也随之推迟。

第二个失去的、是能写进配方的永久地址。打包配方必须公开、其中的源码地址必须是任何人都能跟随的、而逐次申请的链接写不进去。于是发行版只能把源码镜像到自有基础设施上、这既是存储成本、也是再分发权限的问题。许可证允许再分发的组件还好办、混入不允许的组件、镜像本身就无法成立。

CI 与自动化 - 等待时长与周期对不上

流水线并不是为了忍受人工审批等待而设计的。夜间构建每天都跑、而其中一个输入要几周才能拿到、那么这个输入只能挪到流水线之外。实务中的落法通常是：人把收到的文件上传到公司内部制品库、流水线改去读那里。这样能跑。只不过从那一刻起、源码的出处就不再是上游、而是组织内部的缓存。

从审计角度看、这一步很重。「这次发布里的源码来自哪里」的答案、从上游坐标变成了内部路径、而从这个路径回溯到上游的连线、只剩一个文件和某位负责人的记录。不写进文档、几个季度之后谁也还原不出来。

隔离网与气隙环境 - 流程从脚本降到人身上

网络隔离的环境本来就有把外部材料搬进内部的流程。关键在于这个流程能不能被固定下来。基于标签时、搬入流程会凝固成脚本：从固定地址取、用固定哈希校验、把校验日志留作搬入审查记录。审查者可以复现、所以批得快。

变成申请制之后、每个版本都要贴一个人上去。更麻烦的是审查所要求的来源证明。有公开地址与公开哈希时、证明是自洽的、没有这两样、收件邮件与链接就成了证据。安全要求越强的组织、越难把这种形态当作批准依据。结果要么引入被拖慢、要么干脆决定不用这个组件。

归档与长期保存 - 从抓取范围里掉出去

软件的长期保存靠机器扫描公开仓库并留存副本来完成。访问一旦变成申请制、就从这个范围里掉出去。当下看不出来、问题在几年后才到。回溯分析旧版本是否存在某个缺陷的漏洞排查、需要第三方确认某一时点究竟分发了什么的法律纠纷、论文所引用代码的学术复现、社区接手已停止支持设备的维护。这四件事之所以可能、都是因为当时有人留了副本、而无法留存时就没有替代手段。

角色最先失去的替代手段替代的代价

另一面 - 改变分发方式的理由确实存在

真正运营过公开仓库的一方、都清楚其中的成本。哪个组织出于什么理由改了什么、不发表就无从得知、本文也不去推测。但促使分发方式改变的一般性压力是可以梳理的。

  • 带宽与自动化流量 — 公开 Git 仓库的流量中相当大一部分是机器而非人。不使用浅克隆的流水线反复拉取全部历史、成本呈线性增长、仓库越大感受越明显
  • 公开历史本身的清理负担 — 提交级历史里会混入内部路径、未公开的代号、可识别个人的作者信息、以及中间阶段的实验代码。公开前的清理很难自动化、出错的代价又大
  • 第三方许可证边界 — 树里混有再分发条件不同的代码时、公开范围必须按组件逐个调整、比整体公开费事得多
  • 再打包与来源混淆 — 公开归档被原样再分发、导致来源或完整性变模糊的案例、各生态都有。收窄分发点是针对它的应对方式之一、并且确实在被使用

这些压力是真实存在的。把它整理成「公开一定对、申请制一定错」并不准确。不过有一点可以明确地说。成本不会消失、只会转移。分发方原本承担的带宽与清理成本、转移成了下游的等待时间、镜像运维与重建校验的成本。总量是不是变小了是另一个问题、而这个答案通常没人去测、因为转移过去的成本散落在许多组织身上、没有谁会去汇总。

依赖方今天能做的事

上游的决定在控制之外。控制之内的、是「那个决定会在几天之内让我们的构建停下来」。按顺序排是这样。

  1. 先把外部依赖地址列成表 — 把构建会从网络取的东西全部汇总到一张表里。第一次做这张表、通常会比预想的多出一倍
  2. 给没有哈希的条目补上哈希 — 只写了地址、没有校验和的那一行就是脆弱的那一行。这是最便宜的措施、效果又立刻显现
  3. 把源码留存策略写成文档 — 把构建实际用到的归档连同保存期限一起留下、而且不要只留文件、要把获取日期、获取路径、哈希与负责人一并记下。日后需要的不是文件、而是关于这个文件是什么的陈述
  4. 做镜像之前先看许可证 — 只把允许再分发的组件放进内部镜像。不要以「反正是开源」一笔带过、要核对具体条件并走过组织的法务确认。内部专用缓存与对外公开镜像的要求并不相同
  5. vendoring 要按组件判断 — 把源码放进仓库会提升自立性、但仓库体积与更新摩擦都会增加、安全补丁的跟踪责任也转到自己这边。全部 vendoring 不是答案。先从「没有它就发不出版本」的组件里挑
  6. 监控上游标签的新鲜度、把不可替代的组件登记为风险 — 分发方式的变化往往先以「标签好一阵子没上来」的形式出现、比公告更早。把距最后一个标签的天数作为指标、能提前几周察觉。另外、如果对「这个组件下季度拿不到、产品会怎样」没有答案、那就不是技术债、而是供应链风险

也把不在这份清单里的东西说清楚。绕开分发方所定流程的做法不包含在内。那不是实务措施、而是另起一个新问题、在组织层面尤其如此。

可获取性与许可证是两个问题

这件事里能留得最久的、不是某个仓库的具体情形、而是这个区分本身。许可证规定「拿到的人可以做什么」、可获取性规定「一开始能不能拿到」。两者常被当成一回事、实际上是不同的层。

GPLv2 第三条的结构正好展示了这个差别。3a 是随二进制以 a medium customarily used for software interchange 附带完整源码、3b 是以至少三年有效的书面要约在被索取时提供。也就是说、条文本身就把响应索取认作分发方式之一。「必须为所有人运营长期公开的仓库」这一要求、条文里并不存在。

所以在原理上可以存在这样一种状态：许可证义务被满足、而实质可获取性大幅下降。反过来、在本次事件中项目方认为延迟与形态超出了条文的要求。哪种解读成立不是本文能裁定的、也没有确认到权威解释或判决。对实务者而言、真正重要的结论在别处。

  • 「既然是开源、随时都能拿到」这个前提、许可证并不为它背书。多数开源许可证并不要求分发方运营长期公开的基础设施
  • 建立在这个前提上的流水线、其实依赖的不是许可证、而是分发方的运营策略。运营策略的变动频率远高于许可证
  • 生态填补这道缝隙的方法只有一种：公开镜像、归档、包仓库里的源码缓存。它们全都是因为有人留了副本才能运转
  • 因此、在还能复制的时候先复制下来、是唯一能规模化的防线。访问关闭之后、不存在还能做出来的副本

把这个区分固化到团队里、方法出人意料地简单。在依赖评估表的许可证列旁边、再加一列获取路径。公开仓库、发布资产、申请制、还是内部镜像。有了这一列、下次遇到策略变更、一天之内就能圈出影响范围。

没能确认的部分

本文所依据的材料是公开帖子、媒体报道、公开讨论与许可证原文。除此之外的范围如下、仍然是敞开的。

  • 「部分源码」的确切范围 — 报道定位到的是 Pixel 内核、讨论中还一并提到用户态驱动仓库、但没有找到列明受影响仓库的公开规范。没有依据认为整个 AOSP 都变成了同样的方式
  • 变更的生效时点与实际耗时 — 帖子只描述处理逐渐变慢、没有点明策略转换的日期。几周这个数字也是特定项目自述的经历、没有相当于均值或中位数的公开材料
  • 分发主体的官方说明 — 报道记录截至发稿未获回复。此后是否出现官方说明、本文没能确认
  • 所提供产物的确切形态 — 有历史被压缩成单一文件的描述、但没能确认到说明压缩到何种程度的一手材料
  • 许可证判断与扩散 — 关于是否违反 GPLv2 的权威解释或司法判决、没有确认到其存在、公开的只有双方论据。其他厂商是否会跟进、本次变更是否会被撤回、同样没有判断依据

结论 - 要固定的是承诺、不是地址

用标签与发布归档越久的人、越容易把它们当成「下载链接」。实际上那种格式一直在悄悄替你做四件事：把名称与内容绑在一起、让完整性自我证明、为来源留出附加签名的位置、并让第三方能拿到同一份东西。正因为有这四件事、校验和才成为可共享的基准、SBOM 才有坐标可写、复现校验才可能是一项常态活动。分发路径一变、这四样会一起晃动。文件照样会到手。晃动的是你能就这个文件说出什么。

所以在把这次变更归为别人仓库的事情之前、只要向团队问三个问题就够了。第一、我们的构建从外部抓取的地址、完整清单现在三十分钟内能不能拉出来。第二、其中没有附带哈希的条目有几个。第三、如果这些地址里有一个明天改成申请制、我们的发布会在几天后停下来。

第三个问题的答案如果是「不知道」、那这件事就不是别人的事、只是还没轮到。而且为这些问题准备答案这件事、无论上游怎么做都不吃亏。清单、哈希与副本、即便分发策略从不改变、也照样有价值。这是一种不多见的投资。
