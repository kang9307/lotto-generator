Prefer Duplication Over the Wrong Abstraction — The Paradox of Code Design

The DRY Principle Trap: Why Premature Abstraction Costs More Than Duplication, Signs of Wrong Abstraction, and Design Judgment That Holds in the AI Coding Era

2026-06-23 Dev & Infra

Introduction: Why a 10-Year-Old Classic Is Trending Again

In June 2026, Sandi Metz's 2016 essay "The Wrong Abstraction" resurfaced on GeekNews with 43 points. A decade-old piece being rediscovered suggests the problem it describes remains unsolved — or has worsened.

Metz's core claim fits in a single sentence: "Duplication is far cheaper than the wrong abstraction." On the surface it sounds paradoxical. Isn't reducing duplication what good code is about? Isn't DRY (Don't Repeat Yourself) a foundational software engineering principle?

Yes. But DRY is a principle you apply in response to what you observe, not one you force in anticipation. This post analyzes that distinction from my perspective. As of June 2026 — with AI coding tools deeply embedded in development workflows — I'll also explain why this principle has become more important, not less.

1. How Wrong Abstractions Are Created

The pattern Metz describes is precise. Developer A spots duplication in the code. Being a conscientious programmer, they extract the common logic and give it a name — a new function or class. The duplication is replaced by this abstraction. So far, textbook correct.

The problem arrives next. Developer B receives a new requirement. The existing abstraction almost fits, but not quite. B feels it would be wasteful to discard the abstraction. So they add a parameter and insert a conditional branch. Developers C, D, and E repeat this cycle. The originally clean abstraction becomes a monster bristling with parameters and nested conditionals.

The critical psychology here: B, C, and D feel a sense of obligation to honor the abstraction. Dismantling someone's structure seems like dirtying the code. So wrong abstractions are maintained by social pressure. The harder the code becomes to understand, the more frightening it is to touch. A vicious cycle.

2. The DRY Trap: Syntactic Similarity vs. Semantic Identity

In my view, the most common misunderstanding of DRY is conflating syntactic similarity with semantic identity. Two code fragments looking structurally similar does not mean they represent the same concept.

Consider an example: user authentication logic and admin permission verification logic may follow similar patterns. Both check a condition and throw an exception on failure. On the surface, it looks like duplication. But authentication verifies identity, while permission checks validate a role. Merge them into one abstraction and the abstraction tears apart when their requirements diverge.

To apply DRY correctly, ask: "Do these two pieces of code change for the same reason at the same time?" If the reasons for change differ, they are independent concepts regardless of how similar they look. Eliminating the duplication artificially couples two distinct ideas.

3. Signs of a Wrong Abstraction — What to Watch for in Code Review

Wrong abstractions typically show these warning signs. Be alert when you see them in code review.

3.1 Multiplying Boolean Parameters

If you see a function like doSomething(data, isAdmin, skipValidation, useCache), be suspicious. Multiplying boolean parameters mean multiplying branches inside. This function is actually bundling several distinct functions under a single name.

3.2 Callers Taking Different Paths

Trace the abstraction up to all its callers and you find each one uses a different parameter combination to take a different path through the code. This isn't a shared abstraction — it's multiple different behaviors hiding under one identifier.

3.3 Unexpected Blast Radius on Modification

Modifying the abstraction to meet one caller's needs breaks other callers that appeared unrelated. This is evidence that the abstraction has physically coupled semantically unrelated code.

3.4 Mismatch Between Name and Behavior

The function is named calculateDiscount, but inside it also logs, updates user history, and handles discount policy exceptions. When the name no longer accurately describes the behavior, the abstraction has lost its boundary.

4. When to Allow Duplication and When to Abstract

Here are my decision criteria.

4.1 Rule of Three — Don't Abstract Before the Third Occurrence

When a pattern appears for the first time, just use it. When it appears a second time, take note but resist the urge. When it appears a third time, then consider abstracting. This rule, which Martin Fowler also recommended in Refactoring, works because by the third occurrence the direction of variation is partially visible. Abstracting at that point has a higher chance of capturing correct boundaries that reflect real requirements.

4.2 WET and AHA — The Philosophy of Intentional Duplication

WET (Write Everything Twice) is a practical counterpart to DRY: writing the same code twice is acceptable; only on the third occurrence do you consider extracting an abstraction. Kent C. Dodds' AHA (Avoid Hasty Abstractions) is more fundamental. It isn't about avoiding abstraction itself — it's about avoiding rushed abstraction. The question to ask first is: "Do I have sufficient reason to abstract right now?"

4.3 Use Reason for Change as the Criterion

In SRP (Single Responsibility Principle) terms: group code that changes for the same reason at the same time. Even if two pieces of code look different, they can be grouped if they change for the same reason. Conversely, even if two pieces look similar, they should remain separate if they change for different reasons. The criterion for abstraction is conceptual identity, not code shape.

4.4 When You Find a Wrong Abstraction — Go Back

I fully agree with Metz's prescription: don't try to fix the wrong abstraction; inline it back. Unfold the abstraction into each caller, adapt each independently to its actual needs, then wait for genuine duplication to emerge. Attempting to repair a wrong abstraction typically produces a more complex wrong abstraction. Quickly abandoning it and returning to inline is cheaper in the long run.

5. Why This Principle Matters More in the AI Coding Era

As of June 2026, AI code generation tools are deeply embedded in development workflows. In this context, the wrong abstraction problem can become more severe than before.

5.1 AI Reacts Immediately to Structural Similarity

AI coding tools tend to suggest commonalization as soon as they detect structurally similar code. They excel at detecting syntactic similarity, but determining whether two pieces of code are semantically identical — representing the same concept with the same reason to change — requires domain understanding. Accepting AI-proposed abstractions uncritically can produce wrong abstractions bundling semantically unrelated code.

5.2 Intent Lost Between Sessions

When working with AI, the background and intent behind an abstraction created yesterday disappears in a new conversation session. Continuing to pile features onto an existing abstraction without knowing its original intent precisely replicates Metz's pattern — adding parameters and branches. A human developer can reconstruct context from memory, but AI cannot without that context present.

5.3 Duplication Can Facilitate AI Collaboration

Paradoxically, appropriate duplication becomes an advantage in AI collaboration. When each feature is described independently, AI can work on a specific feature modification clearly, looking only at the relevant code. When multiple features are entangled through complex abstractions, AI also struggles to assess the blast radius of a change.

5.4 Design Judgment Remains Human Work

One observation that appears frequently in AI coding statistics as of 2026: AI-generated code increases code cloning (duplication). In the short term this looks like a problem, but from the perspective of choosing the right moment to abstract, it isn't necessarily bad. What matters is whether the duplication is intentional or neglected. Intentional duplication is preparation for a correct future abstraction. Neglected duplication is technical debt. Making that distinction is the developer's job, not AI's.

6. What Is a Correct Abstraction — Resolving the Paradox

The title "Prefer Duplication Over the Wrong Abstraction" doesn't mean avoid abstraction altogether. It means: tolerate duplication if that's what it takes to avoid a wrong abstraction. The crux of this paradox lies in the timing and criterion of abstraction.

6.1 Abstraction Is Discovered, Not Imposed

Good abstractions are born in the moment of realization: "Oh, these things actually represent the same concept." That moment is the AHA. Bad abstractions are born from the obligation: "There's duplication, so I must extract it." The former reflects domain understanding; the latter merely reacts to code surface form.

6.2 Abstraction Must Align with the Direction of Change

Correct abstractions narrow the blast radius when requirements change. Wrong abstractions propagate changes to unrelated places. Before creating an abstraction, ask: "What direction of change is this abstraction designed to absorb?" If the answer is unclear, it's not yet time to abstract.

6.3 Consider the Cognitive Cost of Code

Code is executed by machines but read by humans. Wrong abstractions raise cognitive cost. If reading code requires traversing multiple layers to understand an abstraction and mentally simulating parameter-branch combinations, the abstraction is obstructing understanding rather than enabling it. Code with some duplication but independently readable features sometimes demands lower cognitive cost.

7. Practical Checklist — Questions to Ask Before Abstracting

Verify these questions before creating an abstraction:

  • Are these two code pieces merely syntactically similar, or do they actually express the same concept?
  • When this code changes, does it change for the same reason at the same time?
  • Have I seen this pattern three or more times, or am I feeling the urge to abstract on the second occurrence?
  • Has there already been a desire to add parameters or branches to this abstraction?
  • When I modify this abstraction, can I intuitively predict the blast radius?
  • If AI proposed this abstraction, have I personally verified semantic identity?

If even one answer is "no," deferring abstraction is the safer choice. Allow the duplication and wait until more information accumulates.

8. Conclusion — Not a Paradox, But a Question of Priority

The reason Metz's principle sounds paradoxical is that we have long misunderstood DRY as a goal. DRY is not a goal — it's a result. Duplication naturally decreases as a byproduct of correct abstraction. You must not force abstraction in order to reduce duplication.

As of June 2026, with AI coding tools commonplace, this principle has grown more important. AI generates code quickly and reacts to structural similarity immediately, but judging the boundaries of domain concepts remains human work. Don't delegate to AI the decision of when and by what criterion to abstract.

Not fearing duplication, and waiting until you discover an abstraction rather than imposing one — this is design judgment that remains valid in 2026, perhaps more valid than ever.
