驻留着智能体的服务器 - 个人自己运行一台时新出现的问题

与跑一个网页应用有什么不同，触发、上限、恢复、边界与记录都会改变

2026年9月1日 开发/基础设施

往自己的服务器上放东西是个老爱好。相册、笔记、媒体服务器，最近还有模型推理。这份清单里最近多了一项，而它和前面那些性质不同，就是常驻的智能体。不开页面它也在转，没有请求它也会启动，下一步做什么由它自己定，而不是由代码定。

这篇只谈这一个差别。买什么硬件、怎么开端口，那些在家庭服务器基础里。这里要看的只有一件事，一个在没人盯着时仍会动的进程，对服务器提出了哪些新要求。 用运维请求响应式服务的直觉，大概只能覆盖一半。剩下那一半会在夜里变成账单和无声的失败回来。

本文不是任何产品的安装或运维指南。作为起因的项目只作为一个案例被引用，核对范围止于仓库以及仓库内的文档。凡涉及安全的部分都只写防御视角，不涉及绕过手法。

起因 - 把智能体当住户的设计

2026年8月底，韩国开发者社区里流传了一个叫 mu 的项目。它是一台个人服务器，用 Go 写成的单个二进制里装了邮件、聊天、文件、笔记、日程、联系人和 shell，上面再架智能体。许可证是 AGPL-3.0，仓库建于2025年11月，核对时显示星标420、分叉20、标签30（最新为 v1.6.2），最后一次推送是前一天。年轻、活跃，但不是经过验证的东西。本文用它的方式也就到这个份上，它是一个案例，不是推荐方案。

比功能清单更有意思的，是这个项目自我说明的方式。仓库里的文档把系统比作一栋住宅，而且先写这个比喻禁止什么。这里没有一个界面是无限滚动的。不会因为多了一件事就加出第九个房间。只有一个作者的界面本身就是缺陷。它还说明了为什么偏要选住宅：只有把智能体放在住户的位置上，「另一个存在住在这里，在你不在时做事」才会成为一句平常的话，而不是一条功能说明。

结构上的线条也清楚。服务是原子，彼此不互相调用，也不调用智能体。这条规则由测试强制，而不是靠文档约束，文档甚至把测试的名字原样写了出来。智能体既不是代码也不是部署，而是一个标识符加上服务的子集再加上一段提示词。计费按端点计，连加价倍数都公开在一个配置文件里。

但同一份文档自己列出了四个缺口，其中两个正是本文的起点。一个是「这栋房子从不先开口」，文档写明这里能自发产生的动作只有抓取新闻和一个被触发的事件两种。另一个是「组合只发生在模型调用内部」，意思是服务始终是叶子，能把两个服务合起来的只有一个决定这么做的模型。

这两句不是谦虚的自评，而是准确的问题陈述。「智能体住在这里」和「智能体常驻于此」之间的距离就在那儿。前者是部署问题，后者是运维问题。下面写的，就是真正填这段距离要用到的东西。

与请求响应式服务有什么不同

一台网页应用形状很简单。请求进来、事情发生、响应出去、进程重新闲着。运维的绝大部分都从这个形状派生。失败因为有人在等，所以很快露头。一次作业消耗的资源被一个请求圈住。并发跟着流量走。所以盯着 5xx 比例、响应延迟和每秒请求数，多半就能得出答案。

常驻的智能体把这四条全都破了。

  • 起点不是请求。 没有人在等这次失败。而且没人看屏幕的时段占了一天的大半
  • 一次启动会产生多少次调用，事先不知道。 调用几个工具由模型决定。费用和耗时的上限，代码里任何地方都没写
  • 结束条件在判断里，不在代码里。 所以无限循环在语法上完全正常。进程活着、CPU 忙着、日志一直在长
  • 作业活得比进程久。 重启不再等于「从头开始」。走到哪一步了，必须写在进程之外的某个地方

要观测的对象也跟着变。网页应用里，一行日志和一次响应是同一件事。智能体里真正想知道的那件事，也就是为什么用这些参数调了这个工具，在任何请求路径上都不会留下。不决定要记，它就是不存在。

当触发方不是人

造出常驻状态的，归根结底是触发器。触发器只有用户一种时，运维很轻松。变成三种的那一刻，每一种都带来不同类型的事故。

触发器什么时候跑新需要的东西没有时会发生什么
用户请求有人在等超时界面卡住。很快就会知道
时刻（定时执行）约定的时刻防重叠、固定时区、允许的延迟量上一次还没跑完下一次就开始。在夏令时切换处会跑两次或一次都不跑
外部事件（邮件到达、Webhook、文件变更）由别人决定入流限速、去重、发件方限制上游一次暴涨就直接变成调用暴涨
自我判断（上一步结果引出下一步动作）无法预测步数上限、费用上限、停止条件无限循环与正常运行无法区分

防重叠这件事，工具有时替你做，有时不做。cron 不管上一次还在不在跑，下一次照样拉起来。systemd 定时器则在同一个单元还在运行时不另起一份，而是把它排到后面。你用的是哪一种、后面积压的执行稍后集中跑是不是可以接受的行为，如果没定下来，那么平时都很安静，事故会挑特别慢的那一天发生。自己加一把文件锁，就能盖住这个问题的大半。

  • 定时执行的时刻固定用 UTC，只在展示时换成本地时间。服务器在有夏令时的地区，或者任务跑在会随身移动的设备上时，这条规则才显出价值
  • 避开整点。整点是全世界定时任务扎堆的时刻，外部 API 的限流也偏偏在那时候撞上
  • 事件触发器先写清楚谁能把它拉动。用收件箱当触发器，那么知道地址的所有人都是这个触发器的共同持有者
  • 判断驱动的触发器要同时加三道上限：步数、总费用、实际耗时。只加一道，另外两道就会漏

没人盯着的那段时间

先说费用。mu 给每个端点标价、并把这些价钱公开在一个文件里，这个形态是好的。只是这个形态能回答的止于「这次调用多少钱」。运维里真正扎人的问题在另一边，昨晚一共多少次。 所以上限要放在两层：一次执行可以消耗的最大值（工具调用次数、令牌数、实际耗时）是一层，一天或一个月的总额是另一层。而且触到上限时的默认动作必须是停下并通知，不能是告警后继续。在没人看的时段，告警和不存在是一回事。

无声的失败有三副面孔，共同点是在指标上都看着没事。

  • 重试把失败吸收掉了。 第三次成功，成功率就记成百分之百。变了的只有费用和延迟，而这两样没人在看
  • 失败被记成了成功。 模型回一句「没有找到那个文件」，然后正常退出。退出码是 0。这在定时任务里是最难抓的一种
  • 干脆什么都没发生。 定时器死了，或者单元被停用了。失败通知只在失败时才来，所以没在跑和很安静无法区分

第三种在个人服务器上最常见、也拖得最久。应对思路是反过来的，不是通报失败，而是通报成功。 每次正常结束就往外面某个东西发一个信号，如果那个信号在约定时间内没到，由对方来联系你。自己的服务器监视自己，断电的时候监视也一起断了。别的都可以商量，唯独这一件必须放在服务器之外。

死掉之后从哪里重来

进程会死。内核更新、内存不足、断电、手滑的一次重启。在请求响应式里这个问题很好答，客户端再发一次就是了。常驻智能体没有一个会再发一次的客户端。

所以设计一个作业时，要先答三件事。

  • 这个作业走到哪一步，有没有记在进程之外。只在内存里的话，恢复这个概念本身就不成立
  • 重新执行时，里面有没有混着做两次就出事的动作
  • 只完成一半的状态算不算有效状态。如果不算，有没有把那一半退回去的办法
动作能做两次吗需要的机制
读文件并做摘要可以不需要。只是费用翻一倍
把结果写进本地笔记或数据库有条件用同一个键覆盖。每次追加一行的方式不行
发送邮件或消息不行发之前先记下「将要发送」，发完再改成「已发送」
通过外部 API 下单、支付、发布绝对不行由调用方生成请求标识并带上，接收方负责拒绝重复
删除或移动文件不行不立即删除，先移入隔离目录，过了宽限期再清掉

第三行的做法是这张表的核心。副作用离开服务器之前，先把「将要离开」写下来，写完再发。这样重启之后就能区分「写了但没发」和「已发」。写完立刻死掉的那一小段仍然存在，但它的长度从整个作业缩到了一次调用。运维能换来的不是事故消失，而是模糊区间的收缩。

当无法保证只做一次

恰好一次的执行在一般情况下无法保证。实务里用的是至少执行一次，并让副作用做多少次结果都一样。到这里为止，处理过队列的人都很熟。只在智能体上新长出来的陷阱在后面。

  • 幂等键不能由模型输出生成。 同一件事再做一遍，句子每次都不一样。拿输出的哈希当键，键每次都是新的，幂等性就只剩个形状
  • 键要从意图生成，不是从结果。「9月1日的每日摘要邮件」哪怕正文不同也是同一件事。目标周期和作业类型才是键的原料
  • 不要把执行时刻放进键里。积压后晚跑的那次和准点跑的那次如果成了不同的键，那天就会发出两封
  • 能做两次的动作和不能做两次的动作，不要塞进同一个函数。 重试的单位会变成整个函数，安全的前半段也会跟着重跑一遍
  • 需要人工审批的动作不是恢复的对象，而是重新审批的对象。把崩溃前拿到的审批在崩溃后照旧使用，那份审批就变成了对另一种状况的审批

最后一条经常被漏掉。审批不是「这个动作可以做」，而是「在这个状况下这个动作可以做」，而重启恰恰就是状况可能已经改变这件事本身。三十分钟前批准的文件移动，如果这中间另一个作业动过同一个目录，还照旧执行下去，那份审批就只剩下不在场证明的功能。

边界 - 隔离挡得住什么、挡不住什么

要让智能体能碰到哪一层。这个问题大多止于「放进容器不就行了」，但每种隔离手段挡的轴不一样。轴对不上，剩下的就只有放进去过这个事实。

隔离手段挡得住的挡不住的
容器宿主文件系统的访问、软件包与依赖污染出方向的网络。从里面往外调用默认就是通的
专用系统账号读取其他用户的家目录、密钥与配置这个账号手里的全部令牌。账号分开了却把令牌一并给出去，等于没分
只读挂载篡改与删除外泄。能读到的东西就能发出去
出方向允许清单发往任意目的地的外泄在允许的目的地内部发生的事。放行的某一个 API 本身就成了通道
独立物理主机或虚拟机共享内核带来的问题维护量。多出来的台数就是一个人要管的台数

隔离缩小的是能做的事的清单，它并不改变对方想做什么。所以边界要按能力来画，能力清单里只该装「此刻这项作业需要的东西」。一旦混进一行「以后也许会用到的」，清单就变成了文档，边界也就没了。

用工具清单表达权限，还带着一个固有的陷阱，清单里的某一个工具可能包含其余全部。 mu 的两个内置智能体把这个对比摆得很清楚。一个能碰到所有服务，另一个只收窄到 shell 和 apps 两项。光看数量，后者窄得多。可这两项里有一项是 shell。只要 shell 在清单上，清单的长度就失去意义。判断是否收窄，标准是最宽的那一项，不是数量。

  • 权限与其按智能体收窄，不如按执行收窄。哪怕是同一个智能体，读外部输入的那次执行也没有理由和写结果的那次执行拥有相同权限
  • 文件访问用路径清单来定。把整个家目录开出去，再在提示词里写一句「小心点」，那是请求，不是边界
  • 出方向连接从默认拒绝开始，只开需要的。按相反顺序建起来的清单，永远不会缩短
  • 外部账户一律新建最小权限的独立账号。复用一直在用的个人账号，事故半径就变成那个账号的整个履历

凭据是另一个问题

一谈边界就会立刻滑向「那密钥怎么给」，而那不是本文的轴。方向只有一条：不把凭据本身交给智能体，只给它一条代为执行需要凭据的动作的窄通道。这条通道允许什么、拒绝什么，就是实际的权限集合。具体的分离手法另写在不把凭据交给智能体也能让它干活里，而委托的幅度该放到多宽，则在智能体自主性等级那一篇。

事后必须还原得出来

标准收成一条最省事，三周之后有人问「当时怎么会那样」，你答得上来吗。 从这条往回推，该记什么自然就出来了。

  • 是什么启动了这次执行。 触发器的类型，如果是事件还要有原文。只写了时刻的记录，等于提前扔掉了一半的还原能力
  • 什么输入进了模型。 即使留不下全文，至少留下是哪份文档、哪段对话、多少字节
  • 用哪些参数调了哪个工具，返回了什么。 事故的原因几乎总在这一行上
  • 模型的标识与版本。 同一段提示词下个月的行为会不一样。没有版本就无法复现
  • 这次执行花了多少。 费用没法事后摊派。不按执行挂上去，最后就只剩月底一张账单
  • 是怎么结束的。 完成、超上限、报错、被强杀要分开。这四种挤在一栏里，成功率这个数字就开始说谎

mu 文档把线程定义成「不论从哪扇门进来，所发生的一切的因果记录」，这句正好指着这个位置。在一个有五扇门（邮件、Web、MCP、SSH、XMPP）的系统里，记录如果按门各自留存，还原从一开始就不成立。记录的单位必须是事件，而不是门。

陷阱也一并写下。把提示词和工具响应整份留存，这份日志本身就成了新的机密仓库。要记什么之外，还得定不记什么，保留期限也在同一时刻一起定下来。在个人服务器上，通常是磁盘先满。

外来文字变成指令的位置

在请求响应式应用里，外部数据要么被存下来，要么被显示在页面上。在智能体里，外部数据进的是模型的上下文，而在上下文里指令和素材是同一种形态。邮件正文、打开过的网页、议题描述、日历邀请的标题，甚至文件名，全都落在那个位置上。

这不是新发现的问题，而是清单的第一行。在 OWASP 的大语言模型应用漏洞清单里，第一项就是提示注入，其中的间接注入指的是指令被埋在模型要处理的外部文档或网页里的情形。常驻智能体把这些条件全占齐了：它自己去取外部输入、手里握着工具、而且没人在看。

  • 把信任边界画在能力上，不要画在数据上。 读外来内容的那次执行不挂带副作用的工具。读的执行与写的执行分开之后，被埋进去的指令所能触及的上限就被圈在「读」这一层
  • 外部内容要以引用的标记形式放进去，而不是当作指令。同时也要清楚这一层本身并不够用，它是第一层，不是最后一道防线
  • 不可撤销的动作前面放人工审批。审批界面上要出现的不是「做什么」，而是「做什么、发到哪里」。看不见目的地的审批不算审批
  • 收窄出方向的目的地。 如果摘要结果能发往任意地址，读取权限本身就已经是外泄通道
  • 还有一处是个人服务器特有的。把收件箱当触发器的那一刻，知道地址的任何人都能把它拉动。像 mu 这样直接收 SMTP 的结构，这扇门默认就是开的，所以发件人允许清单是第一项设置

维护人手只有一个的条件

到这里为止都与规模无关。加上个人自己运行这个条件，还会再多出几条。这些原本是在公司里由组织替你吸收掉的，所以一开始不太看得见。

  • 值班的只有一个人时，通知里只能出现你能采取行动的东西。 一天来四十条的通知，信息量和零条完全相同。每加一条通知，先回答「收到这条，我此刻要做什么」
  • 自己做的东西由自己的服务器来监视，同一次事故会把两边一起干掉。 至少把存活信号放到外面去。另一台设备上的一个定时任务就够了
  • 休假、搬家、病假就是无人巡检的区间。 设计真正受考验的就是那两周。上限在那段时间里还守不守得住，几乎就是全部
  • 没有回退计划，就会渐渐不再升级。 不升级，半年后只会更怕。留一份快照和一套旧版二进制的习惯，是保持最新的前提条件
  • 文档是写给半年后的自己的。 没有「当时为什么这么做」，你就会亲手拆掉自己立的约束。实际最常被拆掉的就是费用上限
  • 关停流程也算设计的一部分。 没有一份「停掉什么会连带停掉什么」的清单，赶时间时除了拔电源没有别的选项

值得放在个人服务器上的活

不必什么都往上放。判断依据是活的性质，不是功能。同样是「每日摘要」，对象是自己的邮箱就很有价值，是别人在等的报告就压根不是它该待的地方。

活的性质放到个人服务器上判断
数据本来就在这里（个人邮件、文件、笔记）往外送的理由消失了价值最大
结果错了也很快有人看（摘要、分类、草稿）无声失败的代价很小合适
频率低且可预测（一天一次）上限设计变得简单合适
带有不可撤销的副作用（发送、支付、删除）无人值守执行的代价很大没有审批就不放
有别人在等（需要可用性）一个人守不住不合适
时效性是命门且外部依赖很重外部一变就会悄悄停掉监控成本容易超过收益
存在记录或审计义务要一个人维持追溯链大体上不合适

收成一条标准就是这样，夜里悄悄失败了，早上你察觉得到吗。察觉到了，退得回去吗。 两个都是「是」，就值得放在自己的机器上。有一个是「否」，就先把那一样做出来再放上去。顺序反过来，动手去做的契机就永远不会来。

自托管部署本身的得失，也就是什么消失、什么新长出来，写在把部署平台放到自己服务器上这个选择里，而把整个工作环境搬到自己这一侧的形态在自托管 AI 工作空间那边。

小结

把网页应用放上去和让智能体常驻，两者之间的距离不在安装难度，而在触发方。启动的那一方不再是人的那一刻，察觉失败的人没有了，定上限的人没有了，记得走到哪一步的也只剩一个进程。其余的问题全都由此派生。

所以新需要的东西一样都不华丽。防止重叠的一把锁、三层上限、副作用出门前先写下的那一行、按能力画的边界、按事件留的记录，以及放在服务器之外的存活信号。只有六样，不是因为容易，而是因为没有它们，其余的都会失去意义。

再借一次那个项目文档自己写下的话：如今大多数个人服务器都不会先开口。 让它开口是下一步，而这一步的大部分不在模型那一侧，在运维这一侧。剩下的活恰好是不好玩的那一半。

  • 星标420、分叉20、标签30（最新 v1.6.2）以及仓库创建时间，都是2026年9月1日核对时的数值。这些数字会一直变，而且活跃并不等于稳定

  • 常驻智能体在现实中究竟会出多少事故、出哪些事故，未能找到公开统计。 本文的失败分类来自定时任务与队列运维，并不对智能体特有事故的发生频率作任何主张
