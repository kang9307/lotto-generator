WARN がゴミ箱になる理由 - ログレベル規約を合意する方法

レベルは深刻度の格付けではなく、読む人へ送る信号である

2026-08-01 開発/インフラ

はじめに: 警告ログが一日 3 万行あって誰も見ない

どのサービスも時間が経つと同じ状態に行き着く。ダッシュボードで WARN のフィルタをかけると画面が延々と流れ、誰もそれを見ない。「警告なのだから見るべきではないか」と問えば皆そうだと答えるが、実際に開く人はいない。そうしているうちに、本当に見るべきだった一行がその中に紛れて過ぎていく。

ここでよく出てくる処方が「ログを減らそう」だ。これは目標が間違っている。問題は量ではなく、レベルが何の意味も持たなくなったことだ。WARN が「人が手を入れる必要がある」を意味しないなら、WARN フィルタは何も濾していない。すると通知を掛ける場所がなくなる。

この記事の主張は一文だ。レベルは「どれくらい悪いか」の格付けではなく、読む人へ送る信号である。ERROR が「誰かが今見るべきだ」を意味してはじめて、そこに呼び出しを掛けられる。WARN が何の意味も持たなければフィルタは無意味になる。だからログレベル規約はコーディングの好みではなく、通知に直結する設計である。

以下はすべて実際にロガーを動かして確かめたものだ。しきい値を変えながら同じコードを実行してどの行が消えるか、レベルの内部の数値が何か、切り捨てられたログの費用が本当に 0 なのかを出力で確認した。

実行環境。以下のすべての出力は Windows 10 Pro (10.0.19045) で実際に実行した結果である。道具は Python 3.13.3 の標準ライブラリ logging と Node.js v22.16.0 の標準ライブラリだ。この機械には専用のログライブラリが入っていない。Node で広く使われる二つのパッケージを読み込んでみたがどちらもモジュールが見つからず、そのため Node 側は console と util.debuglog だけで確認した。存在しない道具をあるかのように使ってはいない。

スクリプトはすべてファイルに保存して実行した。コードをシェル引数やヒアドキュメントで渡すと静かに変形するからだ。ロガー名とメッセージはすべて架空の注文・決済サービスを想定して作ったものである。

この記事が扱わないこと。ログレコードにどのフィールドを載せるか、個人情報をどこで隠すか、要求をまたいで識別子をつなぐかは、それぞれ別の主題だ。この記事はレベルという一点にとどまる。

1. レベルは「重要度」ではなく切り捨ての基準だ

まずレベルが実際に何をするかを見よう。同じ八行を、しきい値だけ変えて四回動かした。

python 3.13.3 / win32
--- 1-1. same eight calls, four thresholds ---

threshold = DEBUG     -> 8 of 8 lines survive
   DEBUG    cache miss key=order:8821
   DEBUG    sql took 12ms rows=3
   INFO     order 8821 accepted
   INFO     payment captured amount=19900
   WARNING  retry 1/3 upstream=billing
   WARNING  config key TIMEOUT missing, using default
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: (none)

threshold = INFO      -> 6 of 8 lines survive
   INFO     order 8821 accepted
   INFO     payment captured amount=19900
   WARNING  retry 1/3 upstream=billing
   WARNING  config key TIMEOUT missing, using default
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: DEBUG

threshold = WARNING   -> 4 of 8 lines survive
   WARNING  retry 1/3 upstream=billing
   WARNING  config key TIMEOUT missing, using default
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: DEBUG, INFO

threshold = ERROR     -> 2 of 8 lines survive
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: DEBUG, INFO, WARNING

コードは一文字も変わっていない。変わったのはしきい値一つだけだ。それなのにしきい値が一段上がるたびに、丸ごと消えるレベルが一つずつ増える。ここから最初の結論が出る。

  • レベルは「この行がどれくらい重要か」を書き留めるラベルではない
  • レベルはどのしきい値でこの行が消えるかを決める。それがすべてだ
  • したがってレベルを決めるとは「この行を誰に見せるか」を決めることである
  • 同じ事実を二人が違うレベルで書けば、二人は別々の読み手にその事実を送ったことになる

一行だけ取り出してしきい値ごとに見えるかどうかを示すと、もっとはっきりする。

--- 1-2. the same line, seen or not seen, by threshold ---
threshold  visible    note
--------------------------------------------------------------
DEBUG      True       written out
INFO       True       written out
WARNING    True       written out
ERROR      False      the call still ran
CRITICAL   False      the call still ran

右の列に注意してほしい。見えないことは実行されなかったという意味ではない。呼び出しはそのまま起き、結果だけが捨てられた。この事実が後の費用の話につながる。

2. レベルはただの整数だ - 独自レベルの代償

レベルの正体は単純である。内部の数値をそのまま出してみた。

python 3.13.3 / win32
--- 2-1. the levels are just integers ---
name       value
------------------------
NOTSET     0
DEBUG      10
INFO       20
WARNING    30
ERROR      40
CRITICAL   50

WARNING is WARN  : True
gap between them : 10

--- 2-2. wedging a custom level in between ---
   TRACE    5    entered handler
   DEBUG    10   cache miss
   INFO     20   order accepted
   NOTICE   25   deploy finished, build 4412
   WARNING  30   retry 1/3
   ERROR    40   capture failed

レベルの間隔が10 ずつ空いているのは偶然ではない。途中に自分のレベルを差し込めるように空けてある。実際に 5 番に TRACE、25 番に NOTICE を登録すると、ちょうどその位置に並んだ。

ところがここに代償がある。登録していない数値を名前に戻してみるとこうなる。

--- 2-3. what a custom level costs you ---
threshold=INFO(20), NOTICE(25) and INFO(20) both pass:
   NOTICE   deploy finished
   INFO     order accepted

an unknown name reads back as a placeholder, not an error:
   getLevelName(25)  -> NOTICE
   getLevelName(23)  -> Level 23
   getLevelName(999) -> Level 999

a receiver that only knows the five names has to guess what 23 means.
the number sorts fine. the meaning does not travel.

核心は最後の二行だ。数値は並ぶ。意味は伝わらない。23 という数値を受け取った収集側は、それが INFO より重いかどうかしか分からず、そのレベルが何を意味するかは分からない。しかもエラーにもならない。静かに Level 23 という置き換え表示として流れていく。

  • 独自レベルは自分のプロセスの中でだけ名前を持つ
  • 収集・検索・通知の側がその数値を知らなければ、その行はフィルタも通知も掛けられない灰色地帯になる
  • 広く使われる標準の深刻度定義そのものが「深刻度は非常に主観的なので、すべての発信者が同じ定義を持っていると仮定してはならない」と釘を刺している
  • だから実務的な推奨は単純だ。独自レベルを使わないか、使うなら収集側の設定にその数値を必ず登録しておく
  • レベルを増やしたいという衝動はたいていレベルではなくフィールドが必要だという合図である。「デプロイ事象」は新しいレベルではなく INFO に付けた分類フィールドで解くのが正しい

3. ゲートは二つある - ロガーが落としたものは戻らない

レベルを扱うときに最もよく出る誤解がここにある。しきい値は一つではない。ロガーに一つ、出力先ごとに一つずつある。二つを組み合わせて動かしてみた。

python 3.13.3 / win32
--- 9-1. there are two gates, not one ---
4 calls each time: DEBUG, INFO, WARNING, ERROR

logger=DEBUG    console_h=NOTSET   audit_h=NOTSET   -> console 4, audit 4
logger=DEBUG    console_h=INFO     audit_h=ERROR    -> console 3, audit 1
logger=WARNING  console_h=DEBUG    audit_h=DEBUG    -> console 2, audit 2
logger=ERROR    console_h=DEBUG    audit_h=DEBUG    -> console 1, audit 1

--- 9-2. the practical shape: one lenient logger, several picky sinks ---
logger=DEBUG    console_h=INFO     audit_h=ERROR    -> console 3, audit 1

--- 9-3. the blunt instrument, and why it surprises people ---
logging.disable(WARNING) is active, logger level is DEBUG:
   ERROR line at ERROR
   -> 1 of 4 survived. it is a process-wide floor that outranks every logger.
   after disable(NOTSET): 4 of 4 survive again

三行目と四行目を見てほしい。出力先は DEBUG をくれと言ったのに、ロガーがすでに落とした後なので何の役にも立たなかった。ロガーのゲートが先に効き、出力先はすでに通ったものをさらに狭めることしかできない。

  • 「出力先を DEBUG にしたのに何も出ない」という問い合わせの大半がこれである。ロガー側を見ていない
  • 実務の配置はロガーは緩く、出力先はそれぞれ狭くが基本形だ
  • 人がリアルタイムで見るコンソールを INFO、呼び出しやチケットキューが読む側を ERROR にすれば、一度出した行が二つの読み手に違う形で届く
  • プロセス全体に床を敷いてしまうスイッチもある。これはロガー設定より上位にあるので、ロガーを DEBUG にしていても 4 行中 1 行しか残らなかった。ライブラリがこのスイッチを触っているとどこを直してもログが出ない

4. WARN が膨らんでいく過程

ここで冒頭の症状に戻る。小さなサービスの一日分を呼び出し箇所の単位で模型化して集計した。

python 3.13.3 / win32
--- 3-1. one day of a small service, simulated ---
total lines/day : 61070
  ERROR          13    0.0%
  WARNING     30057   49.2%
  INFO        31000   50.8%

--- 3-2. inside WARNING, sorted by volume ---
call site                                         lines   share     cumul
--------------------------------------------------------------------------
deprecated field 'user_name' used by client        9800   32.6%     32.6%
cache miss, falling back to db key=%s              7400   24.6%     57.2%
optional header X-Trace absent                     5100   17.0%     74.2%
retry 1/3 upstream=billing                         4200   14.0%     88.2%
slow query 340ms                                   2600    8.7%     96.8%
config key TIMEOUT missing, using default 5s        880    2.9%     99.7%
token expires in 2 days                              60    0.2%     99.9%
disk usage 91 percent on queue volume                14    0.0%    100.0%
payment webhook signature mismatch                    3    0.0%    100.0%

lines a human should act on today : 77
lines emitted at WARNING           : 30057
signal ratio                       : 1 in 390

この表が「WARN がゴミ箱になる過程」のすべてだ。順に読んでみよう。

  • WARN が全体の 49.2 パーセントだ。半分が警告のログにおいて、警告には何の意味もない
  • 上位 3 箇所が WARN の 74.2 パーセントを作っている。3 万行は「多くの種類の警告」ではなく「同じ三行の繰り返し」である
  • その三行はそれぞれ非推奨フィールドの使用、キャッシュミス、任意ヘッダの不在だ。どれも人が行動する対象ではない
  • 本当に人が見るべき行は下の三つ、一日 77 件だけである。390 行に 1 行だ
  • 決定的なのは、この状態を作ったのが悪い開発者ではないことだ。それぞれの呼び出し箇所は書かれた時点では合理的だった。「これは正常ではないから WARN」という判断が九回積み上がっただけである

この状態で通知を掛けるとどうなるかを計算してみた。

--- 3-3. what an alert on WARNING would do ---
  a  1-minute window carries     20.9 WARNING lines
  a  5-minute window carries    104.4 WARNING lines
  a 60-minute window carries   1252.4 WARNING lines
  an alert that pages on 'any WARNING' pages every window, forever.
  an alert that pages above a threshold has to sit above 20/min noise,
  which is higher than the 3 lines/day that actually mattered.

--- 3-4. same stream after reclassifying by 'must a human act now' ---
level          before      after
--------------------------------
ERROR              13         16
WARNING         30057         74
INFO            31000      48480
DEBUG               0      12500

WARNING/day : 30057 -> 74
ERROR/day   : 13 -> 16
now 'any WARNING today' is a 74-line list a person can read.
and ERROR stays small enough to page on.

ここがこの記事の主張が現れる地点だ。通知を掛けられるかどうかが、レベル定義の品質で決まる。毎分 20.9 行が流れるチャンネルには、どんなしきい値を掛けても無駄である。本当に重要だったのは一日 3 行なのに、雑音の底がそれよりはるかに高いからだ。

再分類後の数値を見てほしい。ログの総量は 6 万 1,070 行でまったく同じだ。減ったのは WARN だけで、代わりに INFO と DEBUG が増えた。目標はログを減らすことではなく ERROR と WARN を読めるようにすることだという言葉が、この表にそのまま入っている。

5. 判断基準 - 今、人が行動しなければならないか

では何を基準に分けるのか。Node 側の標準ライブラリで規則を立て、実際の呼び出し箇所に当ててみた。

node v22.16.0 / win32
installed logging packages on this machine: none
  require("winston") -> MODULE_NOT_FOUND
  require("pino")    -> MODULE_NOT_FOUND

--- 4-1. console has level-looking names but no threshold ---
method      stream    dropped when quiet
----------------------------------------------
console.log     stdout    never
console.debug   stdout    never
console.info    stdout    never
console.warn    stderr    never
console.error   stderr    never

there is no setLevel and no threshold. nothing is ever dropped.
a debug line in a hot loop is written in production exactly as
often as on a laptop. the four names only pick a stream.

--- 4-2. the stdlib does ship one gated channel: util.debuglog ---
NODE_DEBUG              : ""
payment channel enabled : false
db channel enabled      : false
(no channel output above: both are off)

この出力が教える事実が重要だ。レベルらしい名前があるからといってレベル機能があるわけではない。この実行環境の既定のコンソール関数四つにはしきい値がなく、決めるのは出力ストリーム一つだけである。実際に標準出力を捨てて実行すると warn と error だけが残る。つまりこれらの関数だけを使うコードでは、DEBUG の行が本番環境でも一行残らずディスクに書かれる。

ただしこの実行環境の標準ライブラリにも付けたり消したりできるチャンネルが一つある。環境変数でチャンネル名を指定したときだけ出力され、有効かどうかをコードから問い合わせることもできる。実際に環境変数へ決済チャンネルだけ指定して動かすと、決済チャンネルは true、データベースのチャンネルは false となり、決済側の一行だけが出力された。これが後で述べる「モジュール別にレベルを下げる」の最も単純な形である。

5.1 問いを変えると答えが一つに絞られる

レベルの議論が終わらないのは問いが間違っているからだ。「これがどれくらい深刻か」で問えば答えは好みになる。問いを変えなければならない。

この行が出たとき、人は何を、いつ、するのか?

この問いへの答えは四つしかなく、その四つがそのまま四つのレベルになる。

レベル一文の定義読む人がすること時間軸通知
ERRORシステムがやるべきことをできずこちらが直す必要がある今すぐ確認する深夜でも呼び出し
WARN人が手を入れる必要はあるが今夜ではない業務時間に処理する今週中日次サマリ
INFO誰も行動しない。何が起きたかを記録する追跡するときだけ読む-なし
DEBUGバグを再現している間だけ役に立つ再現中だけ有効にする-なし

定義に形容詞が一つもない点に注目してほしい。「深刻な」「重大な」「重要な」といった言葉は人によって線が違い、規約を文書の中だけに留める原因になる。一方で「深夜に人を起こすか」は二人が同じ答えを出す。

最も高くつく習慣が一つ。「正常ではないからとりあえず WARN」が、4 節の 3 万行を作った原因だ。この習慣には確かな代替規則がある。確信がなければ INFO である。WARN は「人が今週手を入れるもの」だけを入れる狭い引き出しでなければならず、その引き出しが狭く保たれるときにだけ開ける価値が生まれる。

6. 例外を捕まえたとき、どこで出すか

レベル規約が最も頻繁に崩れるのが例外処理だ。層ごとに捕まえて出し、再送出するよくある形をそのまま実行してみた。

python 3.13.3 / win32
--- 5-1. log-and-rethrow at every layer ---
   ERROR    app.db         db call failed: connect timeout to billing-db after 3000ms
   ERROR    app.service    could not load order: connect timeout to billing-db after 3000ms
   ERROR    app.api        request failed: connect timeout to billing-db after 3000ms
   -> 3 ERROR lines, 1 actual failure, 1 user-visible 500

--- 5-2. raise once, log once at the boundary that decides ---
   ERROR    app.api        request failed order=8821
   + 8 traceback lines attached to that single record
   -> 1 ERROR line, and it carries the full stack

--- 5-3. exception that was recovered from ---
   INFO     app.service    retry 1/3 after connect timeout
   INFO     app.service    retry 2/3 after connect timeout
   result: {'order': 8821}
   nothing failed for the user, so nothing is ERROR

--- 5-4. exception deliberately ignored ---
   5 lines at DEBUG (traceback included)
   visible only when someone turns DEBUG on for this module

最初のブロックが問題だ。実際の障害は 1 件なのに ERROR が 3 行残った。利用者に見えたエラーも 1 件である。この状態で「一日の ERROR が何件」を数えれば障害件数の三倍が出て、そこに通知のしきい値を置けばその倍率がそのまま誤差になる。

二つ目のブロックが解決策だ。送出する側では何も出さない。送出する行為そのものが上位へ知らせる手段だからである。代わりにあきらめると決めた境界の一か所でスタックトレースを付けて一度だけ出す。結果は ERROR 1 行に呼び出しスタック 8 行だ。行数は三分の一になり、情報量は増えた。

状況レベル誰が出すか根拠
再試行で復旧したINFO復旧した層利用者には何も起きていない
握りつぶした、影響なしDEBUG握りつぶした層再現中にだけ必要だ
上位へ再送出した誰も出さない-送出そのものがメッセージだ
500 に変わったERRORあきらめた境界の一か所こちらが直す必要がある
400 に変わったINFOその同じ境界悪いのは呼び出し側だ
  • 「後で原因が分からなくなるといけないから」層ごとに出す習慣はスタックトレース一回で完全に置き換えられる
  • 再試行のログを WARN にしたことが 4 節の 4,200 行を作った。復旧に成功したなら失敗ではない
  • 三回出た例外は同じ事象か別の事象かを後から区別できない。要求単位の識別子がなければなおさらだ
  • クライアントが誤って送った要求を ERROR で出すと、他人が作った通信量がこちらの呼び出しを鳴らす。外部から呼び出しボタンを押せる構造になる

bytes written                     : 2960000
-> once the line is kept, formatting happens anyway. lazy only helps when filtered.

この数値はこの機械で一度測った値である。別の機械、別のビルド、別の負荷では絶対値が変わる。絶対時間ではなく比率だけを持ち帰ってほしい。測り直せば、みなさんの環境でもおおむね同じ順序になるはずだ。

読み方はこうだ。

  • 五つの方式とも出力は 0 行だった。しきい値が WARNING だったので DEBUG はすべて切り捨てられた
  • それなのに文字列を先に組み立てた方式は、しきい値を確認してから組み立てる方式より 39.9 倍遅かった。切り捨てられたのは出力であって組み立ての費用ではない
  • どこに費用がかかるかは 6-2 が答える。ロガー呼び出し自体は 1 回 0.187 マイクロ秒で安い。渡す文字列を作るのに 4.032 マイクロ秒かかる。高いのは呼び出しではなく引数だ
  • 書式文字列と値を別々に渡す遅延評価の方式は 0.208 マイクロ秒で、先に組み立てるより 20 倍以上安い。しきい値を通った行だけが組み立てられるからだ
  • 毎秒 2 万件の規模でこの差はCPU 89.9 ミリ秒対 2.3 ミリ秒になる。そしてそのすべてがファイルに一文字も残らない
  • 最後のブロックが釣り合いを取ってくれる。しきい値を通ればどのみち書式化は起きる。遅延評価が得なのは捨てられるときだけで、有効にすると 1 回 18.749 マイクロ秒に跳ね上がる

実務の規則としてまとめると三行だ。引数は遅延評価で渡す。直列化のような重い引数はしきい値を確認した後にだけ作る。そして DEBUG を有効にするのはただではないと知った上で有効にする。

8. 再デプロイなしでレベルを変える

規約が実際に守られるためにはレベルを下げる作業が簡単でなければならない。難しくしておくと、人は「後で見るかもしれないから」と先に WARN へ上げておき、それが 4 節の 3 万行になる。ロガー名を階層にして動かしてみた。

python 3.13.3 / win32
--- 7-1. baseline: root of the tree at WARNING ---
shop=WARNING  -> 1 lines
   WARNING  shop.payment.gateway retry 1/3

--- 7-2. same process, one line changes the threshold ---
shop=INFO  -> 4 lines
   INFO     shop.db            pool size 8/20
   INFO     shop.payment       capture ok order=8821
   WARNING  shop.payment.gateway retry 1/3
   INFO     shop.web           200 GET /orders/8821 12ms

--- 7-3. turn up ONE module only, leave the rest alone ---
shop=WARNING, shop.payment=DEBUG  -> 4 lines
   DEBUG    shop.payment       building capture request amount=19900
   INFO     shop.payment       capture ok order=8821
   DEBUG    shop.payment.gateway http POST /v1/charges
   WARNING  shop.payment.gateway retry 1/3
   note shop.payment.gateway inherited DEBUG from its parent

7-3 が核心だ。決済モジュールだけ DEBUG に下げ、他は触っていない。それなのにその配下のゲートウェイのロガーも一緒に下がった。なぜそうなるかは次の出力が説明する。

--- 7-4. effective level is resolved by walking up the name ---
logger                   own level    effective
--------------------------------------------------
shop                     WARNING      WARNING
shop.db                  DEBUG        DEBUG
shop.payment             NOTSET       WARNING
shop.payment.gateway     NOTSET       WARNING
shop.web                 NOTSET       WARNING
NOTSET means 'ask my parent'. that is why one name can steer a whole subtree.

--- 7-5. driving it from the environment, no redeploy ---
  LOG_LEVELS=shop=WARNING                       -> 1 lines
     WARNING  shop.payment.gateway retry 1/3

  LOG_LEVELS=shop=WARNING,shop.payment=DEBUG    -> 4 lines
     DEBUG    shop.payment       building capture request amount=19900
     INFO     shop.payment       capture ok order=8821
     DEBUG    shop.payment.gateway http POST /v1/charges
     WARNING  shop.payment.gateway retry 1/3

  LOG_LEVELS=shop=ERROR,shop.web=INFO           -> 1 lines
     INFO     shop.web           200 GET /orders/8821 12ms

--- 7-6. the safety rail: a raise-only window ---
  shop=DEBUG                         depth=0  allowed=False
  shop.payment=DEBUG                 depth=1  allowed=True
  shop.payment.gateway=DEBUG         depth=2  allowed=True
  • 子のロガーを未設定のままにすると親に委譲する。だから上位の名前一つで部分木全体を操れる
  • 逆に子に明示的な値を打ち込むと親を変えてもその枝は追随しない。起動時にすべてのロガーへレベルを設定するコードがあると、運用中の調整が丸ごと塞がれる
  • 環境変数に 名前=レベル の一覧を受け取って適用すればプロセスを立て直さずにフィルタが変わる。7-5 の三つのブロックは同じプロセスの中で順に実行された結果である
  • 7-5 の最後の例に注目してほしい。最上位を ERROR に上げたらゲートウェイの WARNING が消えた。子が未設定なので親の ERROR を受け継いだからだ。委譲は双方向に働く
  • 安全装置が要る。最上位の名前をまるごと DEBUG に下げる要求は拒否し、下位モジュールにだけ許可する。でないと打ち間違い一つでクラスタが自分のログに埋もれる
  • 一時的に下げたレベルには有効期限を持たせる。戻し忘れるのが既定の結末である

9. 規約を作る - チームが合意すること

ここまでが材料だ。次にチームが実際に文書へ書くべきことを整理する。そしてすでに 3 万行が積み上がったリポジトリをどう戻すかも。

合意項目具体的に何を書くか書かないと
レベル定義レベルごとに一文。行動で述べ、形容詞を使わない人によって線が変わる
通知対応表どのレベルがどこへ行くかを定義のすぐ隣に定義が通知と別に漂流する
レベルを上げる手続きERROR に上げると呼び出しが鳴る → レビュアー承認ERROR が静かに膨らむ
レベルを下げる手続き誰でも、騒音の指摘と同じ変更のまとまりで下げるのが面倒で誰もやらない
必須フィールドレベルに関係なく全レコードが同じ項目を持つレベルごとに検索方法が変わる
ERROR 予算一日 N 件。超えたらコードではなく規約が壊れている基準がなく戻す契機が生まれない
自動降格ルール30 日間誰も対処しなかった行は既定で降格一度上げたレベルが永遠に残る

9.2 チェックリスト

  • レベル定義を行動の文で書いた(形容詞がない)
  • ERROR の定義と通知ルールが同じ文書にある
  • 「再試行して成功」が WARN になっていない
  • 「クライアントの入力エラー」が ERROR になっていない
  • 同じ例外を一か所でだけ出している
  • スタックトレースはあきらめる境界で一度だけ付ける
  • DEBUG の引数を先に組み立てていない
  • 重い引数はしきい値の確認後に作っている
  • 再デプロイなしでモジュール単位にしきい値を下げられる
  • 一時的に下げたレベルに有効期限がある
  • 最上位の名前をまるごと DEBUG に下げるのを防ぐ仕組みがある
  • ERROR の日次予算を決め、超過時の対応が決まっている
  • 独自レベルを使わない、または使うなら収集側がその数値を知っている
  • 30 日間誰も対処しなかった ERROR・WARN 行を探す定期点検がある
  • 上位の呼び出し箇所が占める割合を定期的に見ている

結論: レベルは通知の設計である

最初の問いに戻る。なぜ WARN はゴミ箱になるのか。悪い開発者のせいではない。「正常ではないからとりあえず WARN」という判断が、それぞれは合理的なまま九回積み上がったからだ。その結果が 4 節の 390 対 1 である。

この記事から一つだけ持ち帰るならこれだ。レベルを決めるとは、この行を誰に宛てるかを決めることである。「どれくらい悪いか」で問えば答えは好みになり、好みは合意されない。「誰がいつ何をするか」で問えば答えは一つに絞られ、その答えはそのまま通知ルールになる。

だから規約を作る仕事は文書作業ではない。ERROR が「今見るべきだ」を意味するときにだけそこへ呼び出しを掛けられ、WARN が狭く保たれるときにだけその引き出しを開ける価値が生まれる。フィルタが意味を持つかどうかが、規約一枚に懸かっている。

最後に、広く引用される標準の深刻度定義そのものがこの点を認めている。深刻度は非常に主観的なので、すべての発信者が同じ定義を持っていると仮定してはならないと書かれている。標準ですら定義を代わりに書いてはくれないという意味だ。その定義はチームが自分で書かなければならない。

# ログレベル規約 — コピペ用の定義表・再分類手順・チェックリスト

> 出典: braindetox.kr — WARN がゴミ箱になる理由
> 検証環境: Windows 10 / Python 3.13.3 標準 logging / Node.js v22.16.0
> 原則: レベルは深刻度の格付けではない。**誰がいつ何をするか**の宣言である

## 1. レベル定義表 — 行動で書いたもの

| レベル | 一文の定義 | 読む人がすること | 時間軸 | 通知 |
|---|---|---|---|---|
| **ERROR** | システムがやるべきことをできず、こちらが直す必要がある | 今すぐ確認する | 深夜でも | 呼び出し |
| **WARN** | 人が手を入れる必要はあるが、今夜ではない | 業務時間に処理する | 今週中 | 日次サマリ |
| **INFO** | 誰も行動しない。何が起きたかを記録する | 追跡するときだけ読む | — | なし |
| **DEBUG** | バグを再現している間だけ役に立つ | 再現中だけ有効にする | — | なし |

判定はこの一問に還元できる。

> **この行が出たとき、人は何を、いつ、するのか?**

「どれくらい悪いか」で問うと答えは好みになる。「誰がいつ動くか」で問うと答えは一つに絞られる。

### 必ず間違えられる二行

| 状況 | よくある選択 | 正しい選択 | 理由 |
|---|---|---|---|
| 再試行して成功 | WARN | **INFO** | 利用者には何も起きていない |
| クライアントから壊れた JSON | ERROR | **INFO** | 400 を返したのはシステムが正しく動いた証拠 |
| キャッシュミス | WARN | **DEBUG** | キャッシュが設計どおり動いている |
| 設定のデフォルト値を使用 | WARN | **INFO** | デフォルトがあること自体が正常経路 |
| 証明書の期限まで 9 日 | INFO | **WARN** | 人が今週中に手を入れる必要がある |
| 決済キャプチャ失敗 | WARN | **ERROR** | 金が動かず、こちらが直す必要がある |

## 2. 例外を捕まえたとき、どこで出すか

| 状況 | レベル | 誰が出すか |
|---|---|---|
| 再試行で復旧した | INFO | 復旧した層 |
| 握りつぶした、影響なし | DEBUG | 握りつぶした層 |
| 上位へ再送出した | **誰も出さない** | 送出そのものがメッセージ |
| 500 に変わった | ERROR | あきらめた境界の一か所 |
| 400 に変わった | INFO | 境界の一か所。悪いのは呼び出し側 |

**同じ例外が三回出るパターン**は、層ごとに捕まえて出して再送出するために起きる。
実行すると、障害 1 件に対し ERROR 3 行、利用者に見えたエラーは 1 件になる。
境界の一か所でスタックトレースを付けて一度だけ出せば ERROR は 1 行になり、情報量はむしろ増える。

## 3. チームが文書に書くべき項目

| 項目 | なぜ必要か |
|---|---|
| レベル定義 4〜5 行 | 深刻度ではなく**行動**で記述する |
| レベルを上げる手続き | ERROR に上げると呼び出しが鳴る → レビュアーの承認が要る |
| レベルを下げる手続き | 誰でも、騒音の指摘と同じ PR で |
| 必須フィールド | レベルに関係なく全レコードが同じ項目を持つ |
| ERROR 予算 | 一日 N 件を超えたらコードではなく規約が壊れている |
| 自動降格ルール | 30 日間誰も対処しなかった行は既定で降格 |
| どのレベルがどこへ通知するか | 定義のすぐ隣に書かないと定義が漂流する |

## 4. 既存のログを再分類する手順

1. **行ではなく呼び出し箇所で数える。** テンプレート単位で集計する。上位 10 件が通常は全体の 9 割を占める。
2. **算数で一次選別する。** ERROR や WARN で一日 500 件を超える呼び出し箇所は、人が行動できる対象ではない。判断は要らない。
3. **ソースに正規表現をかけて候補を集める。**
   - `\.error\(.*(retry|fallback|cached)` — 復旧したのに ERROR
   - `\.error\(.*(client|invalid|parse|malformed)` — 悪いのは呼び出し側なのに ERROR
   - `\.(warn|warning)\(.*(cache miss|deprecated|retry)` — 誰も見ない WARN
   - 正規表現が見つけるのは**候補だけ**。判定は人が一件ずつ確認する。
4. **降格を先に、昇格を後に。** 降格は戻しやすく、通知に触らない。
5. **1 PR につき 1 モジュール。** レビュアーが各行の「誰がいつ」を実際に判断できる大きさに切る。
6. **前後を測る。** 目標はログを減らすことではない。目標は **ERROR と WARN が読める長さになること**だ。総行数は増えても構わない。
7. **通知ルールを同じ PR で直す。** レベルだけ変えて通知を放置すると、規約は文書の中だけに残る。

### 追う指標

| 指標 | 目標 | 意味 |
|---|---|---|
| ERROR / 日 | 人が読み切れる数 | 超えると呼び出しが無視される |
| WARN / 日 | 朝会で流し読みできる数 | 超えるとフィルタが無意味になる |
| ERROR のうち実際に対処した割合 | 高いほどよい | 低ければ ERROR の定義が誤っている |
| 上位 3 箇所が占める割合 | 低いほどよい | 高ければ一、二行がログを飲み込んでいる |

## 5. 運用中にレベルを変える

- しきい値は**ロガー名の単位**で設定する。名前をドットで階層化すれば、親の名前一つで配下全体を操れる。
- 子のロガーは既定で**未設定**のままにし、親に委譲させる。だから一行の変更が部分木全体に効く。
- 環境変数や設定エンドポイントから `名前=レベル` の一覧を受け取って適用する。**再デプロイは不要であるべきだ。**
- 安全装置。最上位の名前をまるごと DEBUG に下げる要求は拒否し、**下位モジュールに限って**許可する。でないと打ち間違い一つでクラスタが自分のログに埋もれる。
- 一時的に下げたレベルには**有効期限**を持たせる。戻し忘れるのが既定の結末である。

### 二つのゲートを混同しない

まずロガーのしきい値が効き、その後に各出力先(シンク)のしきい値が効く。
**ロガーが落としたものは、シンクをいくら下げても戻らない。**
「シンクを DEBUG にしたのに何も出ない」はほぼこれである。

実務的な配置はたいてい次の形になる。

- ロガー: 緩く。レコードの生成自体は許す
- コンソールのシンク: INFO。人がリアルタイムで眺めるもの
- 通知のシンク: ERROR。呼び出しやチケットキューが読むもの

## 6. コストの規則

- **フィルタで捨てられても、引数を先に組み立てたコストはすでに発生している。** 文字列を連結したり直列化してからロガーに渡せば、その行が捨てられても CPU は使われている。
- 引数は**遅延評価**で渡す。書式文字列と値を別々に渡せば、しきい値を通った行だけが組み立てられる。
- 重い引数(直列化、大きなコレクションの走査)は**しきい値を確認した後にだけ**作る。
- しきい値を通ればどのみち書式化は起きる。遅延評価が得なのは**捨てられるときだけ**である。

- [ ] ERROR の定義と**通知ルールが同じ文書に**ある
- [ ] 「再試行して成功」が WARN になっていない
- [ ] 「クライアントの入力エラー」が ERROR になっていない
- [ ] 同じ例外を**一か所でだけ**出している
- [ ] スタックトレースは**あきらめる境界**で一度だけ付ける
- [ ] DEBUG の引数を先に組み立てていない
- [ ] 重い引数はしきい値の確認後に作っている
- [ ] 再デプロイなしで**モジュール単位に**しきい値を下げられる
- [ ] 一時的に下げたレベルに**有効期限**がある

## 8. やってはいけないこと

- とりあえず WARN — 確信がなければ INFO である。WARN には人が今週手を入れるものだけを入れる
- 深刻度の形容詞で定義を書くこと — 「重大な」の線引きは人によって違う
- 層ごとに捕まえて出して再送出すること — 一つの障害が複数行になり、あらゆる集計が歪む
- 数値が並ぶからと独自レベルを差し込むこと — 並びはするが、**意味は収集側に届かない**
- 通知ルールを放置してレベルだけ変えること — 規約が紙の上だけに残る
- ログの総量を目標にすること — 目標は **ERROR と WARN が読まれること**である
- シンクのしきい値だけ下げてロガー側を見ないこと — ロガーが落としたものは戻らない
- 昔からそうだからと古いレベルを残すこと — 誰も対処しない行は降格の候補である

コピーしてメモアプリやAIツールにそのまま貼り付けてください。
