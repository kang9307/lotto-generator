Introduction: 12 to 52, and what happened in between

The Codex use cases page on OpenAI’s developer site listed 12 entries in the Internet Archive copy from March 27, 2026, and 52 entries in the copy from May 24, 2026. The Korean developer community GeekNews picked it up under the title “Codex greatly expands its collection of use cases,” and this article first went out right after that, on May 26, 2026.

At the time, this article sorted the 52 into six coding buckets - migrations, refactoring, tests, documentation, operations automation, and learning - and named seven new entries to watch, including a Rails 5 to 7 migration, automatic i18n extraction, and GraphQL schema evolution. Recounting the archived list entry by entry on 2026-09-29 showed that those seven were not on the official list, and that 17 of the 40 additions were not coding work at all. This update corrects those parts against the official list. It also removes every first-person usage account and productivity figure that could not be verified.

That changes the conclusion. The 12-to-52 expansion is less “the coding examples got deeper” and more “the range of work you hand to Codex spread beyond development.” This article covers how to read the list, where to start, and how to turn it into a list that fits your team.

1. The 12-entry list and the 52-entry list - what changed

The 12 entries in the March copy were mostly tasks a developer would think of right away: Understand large codebases, Review pull requests faster, Upgrade your API integration (an OpenAI API integration), Iterate on difficult problems, Kick off coding tasks from Slack, responsive front-end designs and Figma-to-code, browser games, ChatGPT apps, iOS and macOS apps, slide decks, and dataset analysis reports.

Eleven of those survived unchanged in the May copy’s 52, and the iOS and macOS entry was split into two. The newcomers include development work such as Run code migrations, Refactor your codebase, and Keep documentation up-to-date, but also everyday office work: Manage your inbox, meeting preparation and follow-ups, Forecast cash flow, Model a DCF valuation, and a budget-versus-actuals review. The page grouped entries into five collections: game development, native development, production systems, productivity and collaboration, and web development.

The link to Goals needs a correction too. This article originally said OpenAI repositioned Codex as a Goal-based agent in late 2025, but the /goal command first arrived as an experimental feature in Codex CLI 0.128.0 on April 30, 2026, and became on by default in 0.133.0 on May 21. At the 52-entry point, “Follow a goal” was simply one entry on the list. Goals is not a layer above the list; it is one way to carry the list’s long tasks through to the end. How to use it is covered in OpenAI Codex Goals - A Practical Guide, updated against the official docs on the same day.

3. Seven of the 40 additions worth a closer look

The descriptions below follow each card’s official summary; difficulty and time come from the cards as of 2026-09-29. The seven entries this section originally discussed - Rails 5 to 7 migration, microservice extraction, security patch automation, performance regression hunting, automatic i18n, SQL index recommendations, and GraphQL schema evolution - could not be found by title on either the 52-entry list or the current list, so they were removed.

3-1. Run code migrations

Map a legacy system to a new stack, land the move in milestones, and validate parity before each transition. The card marks it Advanced, 1 hour. What matters is that it names no particular framework version and stresses controlled checkpoints: do not move everything at once; set several points where you confirm behavior.

3-2. Refactor your codebase

Remove dead code, untangle large files, collapse duplicated logic, and modernize stale patterns without changing behavior. The official summary says to do it in small, reviewable passes. The card marks it Advanced, 1 hour.

3-3. Follow a goal

Set a durable objective when a task needs Codex to keep working across turns toward a verifiable stopping condition. The card marks it Advanced, long running. It is most useful paired with work whose end can be judged by tests, like the two entries above.

3-4. QA your app with Computer Use

Click through real product flows, log what breaks, and finish with a bug report. The card marks it Intermediate, 30 minutes. Because it tests by operating the screen rather than reading code, it is a type of entry that did not exist in the 12-entry days.

3-5. Audit dependency incidents

Turn a public package or supply-chain advisory into a read-only audit plan, then inspect manifests, lock files, CI workflows, and scripts without running untrusted code. The card marks it Advanced, 1 hour. Worth noting: the security entry is designed as a read-only audit, not automatic patching.

3-6. Save workflows as skills

Turn a working Codex chat, review rules, test commands, release checklists, design conventions, or repo-specific scripts into a skill Codex can reuse in future tasks. The card marks it Easy, 5 minutes. A related newcomer, “Create a CLI Codex can use,” builds a composable command Codex can run from any folder.

3-7. Work outside coding (Manage your inbox, Forecast cash flow)

The inbox entry clears a backlog, drafts replies in your voice, and checks for new email on a schedule (Easy, 10 minutes). The cash flow entry takes inputs and constraints, builds an editable forecast workbook, and flags where the balance drops below a safety level and which assumptions drive cash pressure (Intermediate, 30 minutes). As of 2026-09-29 both card summaries name ChatGPT as the one doing the work, which shows the list no longer stays inside a coding tool.

4. Codex use cases vs Claude Code vs Cursor - what to compare

This section originally offered a split drawn from usage experience: new features and architecture discussions to Claude Code, large batch conversions and ops automation to Codex, everyday edits to Cursor. No official source or published comparison supports it, so this update drops the verdict and keeps three things to record on the same basis when you compare.

  • External connections: many of the 52 assume a connection to tools such as Slack, GitHub, or email (“Kick off coding tasks from Slack,” “Review GitHub pull requests,” “Manage your inbox”). To do the same job in another tool, first check that the connection is officially supported.
  • When long work stops: Codex sets an objective with /goal and stops on conditions such as success, pause, a budget limit, or being blocked on user input. Check in the official docs when the other tool stops long-running work and what it reports, and put both in the same table.
  • How results are verified: the official entries keep asking for verification - parity checks before each migration step, a verification step before publishing doc updates, and log or artifact checks for operations. Whatever the tool, which of tests, logs, or checklists confirmed the result matters more than the tool’s name.

Give the same task to all three and fill in those three columns; after a while, your team’s split between tools comes out of those notes. Common measurement mistakes when comparing tools are covered in Twelve Ways We Measure AI Coding Wrong.

5. Eight patterns for Korean SI environments

The eight items below are not entries on OpenAI’s list. They map common technical debt in Korean SI, SM, and in-house teams - or any environment with a similar legacy stack - to the closest official entry. The original note that these had been “applied in practice” could not be verified and has been removed.

  1. Spring 3.x to Spring Boot 3.x migration: the step-by-step checkpoints of “Run code migrations” fit. It is among the largest debts in Korean enterprise codebases.
  2. JSP to Thymeleaf or React: look at “Run code migrations” together with “Build responsive front-end designs.”
  3. jQuery to vanilla JS or React: follow the small, reviewable passes of “Refactor your codebase.”
  4. Oracle PL/SQL to PostgreSQL functions: a case for “Run code migrations.” For database moves, make result-comparison queries the completion condition.
  5. JUnit 4 to JUnit 5 plus test backfill: migrate with “Run code migrations,” and use the added tests as a safety net for later refactoring.
  6. Log format standardization and ops automation: follow “Run verified operations” - run only approved scripts and confirm the result from logs and artifacts.
  7. Onboarding docs for a legacy codebase: “Understand large codebases” covers tracing request flows, mapping unfamiliar modules, and pointing to the next files to read.
  8. Keeping docs and changelogs current: “Keep documentation up-to-date” compares code changes and PR context, drafts doc updates, and adds a verification step before publishing.

None of the official entries found says it can run as is in an air-gapped network. In public-sector SI where outside AI services are blocked, it is more realistic to use this mapping only for designing the work.

6. The trap: why not to take the 52 at face value

The number 52 is also product marketing. The personal count this article originally gave (“fewer than 20 of the 52 were actually useful”) has been removed; instead, here are traps visible in the list itself.

  1. Do not assume they are all development entries: 19 of the 52 are office, data, or finance entries (including the slide deck and dataset report entries from the 12-entry days). Using the full count to estimate the value for a development team overstates it.
  2. “Possible” is not “production-ready”: even the official entries assume parity checks at each migration step and small review units for refactoring. Keep the order: proof of concept, small scope, then company-wide.
  3. Do not ignore the difficulty labels: within one list the cards range from Easy, 5 minutes to Advanced, long running. Make the first attempt an Easy one.
  4. Measure the cost: long work accumulates usage, which is why a budget limit is one of the conditions that stop a goal. Set the limit for this task before you start.
  5. Legal and licensing traps: check the licensing and copyright of generated or converted code, and whether internal code or customer data may be sent to an outside model at all. Korean SI contracts call for particular care.

7. Your own use case library - the catalog developers should build

A list tuned to how your team works is more useful than OpenAI’s list taken as is. The process:

  1. Write down 20 tasks you repeated in a week: coding, refactoring, documentation, meeting prep, report writing - everything.
  2. Rate how delegatable each one is: full, partial, or none. The test is “what can the result be verified with?”
  3. Write prompt templates for the fully delegatable ones first: state the input and output format and the verification steps. Saving templates as skills, as in the official “Save workflows as skills,” lets you reuse them in later tasks.
  4. Review once a month: refine the templates that worked; fix or drop the ones that did not.
  5. Share with the team: move the stable list to the team wiki as a shared asset.

The original estimate that “20 to 30 entries accumulate in six months” had no basis and has been removed. What decides the quality of the list is not how many entries it has but whether each one states how to verify it.

8. What Codex looks like in late 2026 (forecast at the time)

The three paragraphs below are the forecast as published in May 2026; each ends with what was confirmed on 2026-09-29.

First, it expected that the list would grow again to 80 to 100 entries, with the growth in domain-specific work. On September 29 there were 105 cards, and new collections had appeared for business operations, data science, education, finance, life sciences, sales, and security. The direction was right, and the count exceeded the forecast.

Second, it expected that multi-agent collaboration - one agent writing code while another reviews it - would become an official entry. No entry on the current list names multi-agent collaboration in its title. “Set up a project teammate” and “Scan multiple repositories” exist, but whether they cover division of work between agents was not checked this time.

Third, it expected expansion into non-coding work. That was in fact already happening when the article was published: the 52-entry list already had 19 office, data, and finance entries, and the current list adds entries such as Create a classroom materials pack, Prioritize accounts, and Plan a budget and schedule.

10. Conclusion plus three things to do this week

12 to 52 was more than a list getting longer. But its meaning was broader than this article first said (“from coding assistant to engineering work agent”): 17 of the 40 additions were outside development, and the list later grew to 105 and moved to a ChatGPT-branded site. What a developer needs is not the total but the few entries that fit the team’s work, and a way to verify each one.

Three things you can start today:

Action 1 - list 20 repeated tasks: this week, write down 20 tasks you repeat in a typical week and give each a delegation rating (full, partial, none) and a one-line verification method.

Action 2 - start with one Easy entry: apply an entry labeled Easy, such as “Understand large codebases” or “Keep documentation up-to-date,” to a real repository. Starting with work whose output a person can check quickly is the safer path.

Action 3 - a one-week comparison note: give the same task to Codex, Claude Code, and Cursor, and keep a note for a week that fills in the three columns from section 4 (external connections, stop conditions, verification).

Fifty-two, and now 105, is a starting line. Turning that list into your team’s list will outlast any choice of tool.
