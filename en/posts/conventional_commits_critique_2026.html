Are Conventional Commits Actually Worth It - A Critique of the Commit Convention 2026

Between Format and Value - A Critical Look at the Commit Message Convention

Jun 7, 2026 Tech

Introduction: The Pause Before feat:

You finish the code, and just as you go to write the commit, your hands stop. "Is this a feat or a fix? Or a refactor? And what is the scope?" It is a trivial one-line change, yet you spend a moment turning the type of the commit over in your head. Anyone on a team that uses Conventional Commits has lived this scene. For some, that pause is evidence of good discipline. For others, it is evidence of pointless formalism.

This article takes on a question that is still hotly debated in 2026 - "Are Conventional Commits actually worth it?" - without taking sides up front. We will lay out what the convention is and what benefits it promised, what criticisms are raised against it, and when it helps versus when it is overkill, all from a practitioner's view. The short version: Conventional Commits is neither good nor bad in itself. It is a tool whose cost is recovered only when an automation pipeline actually consumes the commits.

1. What Conventional Commits Are - The Basic Structure

Let us set the foundation. Conventional Commits is a convention for writing commit messages in a fixed format that is readable not just by humans but by machines. It grew out of Angular's commit guidelines, was formalized into a separate specification, and its v1.0.0 is now the de facto standard. The basic structure is:

<type>[optional scope]: <description>

[optional body]

[optional footer(s)]

A few real examples make it intuitive:

feat(auth): add social login support

fix(api): fix crash on null response

docs: expand installation steps in README

feat(parser)!: switch config file format to YAML

BREAKING CHANGE: existing JSON config files no longer work.

The key is the type at the start. It classifies what changed in a single word; the scope in parentheses narrows down which area; and the description after the colon states the content. A ! after the type, or a BREAKING CHANGE: footer, signals a change that breaks compatibility.

2. The Vocabulary of Types - feat, fix, and the Rest

Only two types have a meaning fixed firmly by the spec: feat (a new feature) and fix (a bug fix). These two are special because they map directly to semantic versioning, as we will see. The rest are widely used by convention, but the spec does not nail them down.

Type Meaning Version impact
featNew featureMINOR bump
fixBug fixPATCH bump
docsDocumentation onlyNone
refactorStructural change, no behavior changeNone
testAdd or fix testsNone
choreBuild, tooling, miscNone
BREAKING CHANGEBreaks compatibilityMAJOR bump

Here the first friction appears. The spec does not provide its own recommended list of types; it points you to Angular's definitions. So debates about the boundary between chore and refactor, or the difference between style and format, repeat themselves on every team. According to the discussion, this ambiguity is one source of the confusion that shows up frequently in GitHub issues and Stack Overflow questions.

3. The Motivation - Why Build Such a Convention

Before criticizing the convention, we should fairly see the problem it tried to solve. Conventional Commits arose out of the chaos of free-form commit messages. A history full of "fixed it", "asdf", and "final_really_final" forces a human to read each one to learn what changed, and leaves no room for tools to act automatically.

The real goal of the convention is to turn commit messages into structured data. Once a commit is in a machine-parseable format, everything downstream - changelog generation, version computation, release notes, CI decisions - becomes automatable. The convention is not an end in itself; it is designed as an input format for automation. Miss this and it is easy to misjudge its value.

The essence of Conventional Commits is not "pretty commit messages" but "machine-readable commit messages." Without that machine, only the format remains.

4. Promised Benefit 1 - Automatic Changelogs

The first concrete benefit the convention promises is automatic changelog generation. Because commit types are structured, a tool can walk the history and place feat commits in a "Features" section, fix commits in "Bug Fixes", and breaking changes in their own prominent section, automatically.

Eliminating the per-release chore of hand-curating a change list is no small benefit. For a library with external users especially, the changelog is part of the product. Written by hand it is easy to omit or get wrong; generated from commits, it reflects "what actually changed" without gaps.

5. Promised Benefit 2 - Automated Semantic Versioning

The second benefit is the most powerful: automated semantic versioning (SemVer). A semantic version encodes compatibility in three numbers, MAJOR.MINOR.PATCH, and Conventional Commits maps precisely onto them.

  • fix commit → PATCH bump (e.g., 1.2.3 → 1.2.4)
  • feat commit → MINOR bump (e.g., 1.2.3 → 1.3.0)
  • BREAKING CHANGE → MAJOR bump (e.g., 1.2.3 → 2.0.0)

Thanks to this mapping, a tool can analyze only the commits since the last release and compute the next version with no human input. The emotional, inconsistent argument over "is this release a minor or a patch?" is replaced by a rule. The version number reflects what changed, not how anyone felt about it.

6. Promised Benefit 3 - semantic-release and Fully Automated Releases

When changelogs and versioning combine, the entire release becomes automatable. The flagship tool is semantic-release, with release-please widely used in the same spirit. The flow looks like this:

merge to main
   │
   ▼
analyze commits (commit-analyzer)   → tally feat/fix/BREAKING
   │
   ▼
compute next version                → apply SemVer rules
   │
   ▼
generate changelog + git tag + publish package
   │
   ▼
publish release notes (whole flow unattended)

When it works ideally, a developer simply commits per the convention and merges to main; the manual steps of choosing a version or pressing "release" drop to zero. This is the peak of the pro-convention case. One review found that a large share of top NPM libraries had adopted the convention, evidence that the automation ecosystem runs on top of it.

7. Criticism 1 - Formalism and Redundant Information

Now to the other side. The most common criticism is formalism. Does a prefix like feat: or fix: really add information? Critics argue that in "fix: fix crash on login", the fix: is filler - the description alone tells anyone it is a bug fix. The type is redundant with the description.

The criticism of scope is similar. The auth scope in feat(auth): tells you which area was touched, but you can already get that with git log -- path/to/auth. The changed file path is the scope; why should a human re-type it by hand?

A good commit message should explain not "what I changed" but "why I changed it." Yet the energy spent picking a type prefix is energy stolen from that "why."

Even in 2026, communities like Hacker News and Lobsters repeatedly post the complaint that "Conventional Commits encourages focus on the wrong things." The core worry is that filling in the format crowds out the most valuable part of a commit message - the intent and context of the change.

There is a subtler version of this critique worth naming. Once a team enforces the format, the act of committing quietly shifts from "explaining a change" to "satisfying a linter." A junior engineer who would otherwise have written a thoughtful three-line rationale learns instead that the gate they must pass is the prefix, and so they write the minimum that clears it: fix: stuff. The format was supposed to raise the floor of commit quality, but in practice it can also lower the ceiling, because it reframes the whole task as compliance rather than communication. That reframing is invisible in any tooling metric, which is exactly why it is easy to overlook.

8. Criticism 2 - Pure Overhead Without Automation

The second criticism is the most damaging. Every benefit of Conventional Commits rests on the premise that automation exists to consume the commits. For a team that does not auto-generate a changelog and does not bump versions with semantic-release, the convention leaves only the cost of the format, with none of the promised benefits.

In practice such teams are surprisingly common. They enforce the commit format with commitlint, yet have no pipeline that reads that format to build a changelog or automate a release. Here the developer pays the cognitive cost of picking a type on every commit, and the automation payoff in return is zero. This is the most common anti-pattern of the convention.

The adherence data illustrates the tension. According to one study, in projects that had not formally adopted the convention, only about 10% of 2023 commits followed it. Without enforcement people naturally drift away from it, so keeping the format requires tooling, and tooling in turn creates friction - a loop.

9. Criticism 3 - The Cognitive Load and Ambiguity of Classification

The third is the burden of classification itself. Using the convention properly means sorting commits into roughly ten categories, yet real changes do not fall so cleanly. A commit that fixes a bug while also refactoring and adding a test - is it a fix, a refactor, or a test? These "tangled commits" collide head-on with the classification rules.

Academic research points at exactly this spot. Existing studies mostly focus on a three-way split of feat, fix, and other, leaving how to define and apply the finer-grained categories as an unsettled gap. Because the spec does not pin down the type list, different developers pick different types for the same change. A convention introduced for consistency paradoxically spawns a new argument over what consistency even means.

The tangled-commit problem also collides with another widely taught practice: committing little and often. Developers are encouraged to commit work-in-progress frequently so that history is granular and bisectable, yet a strict convention pushes in the opposite direction, rewarding large, neatly-typed commits that map cleanly onto a single category. You end up choosing between two virtues - frequent commits and clean types - and the convention quietly biases you toward the latter, sometimes at the cost of a useful history. None of this means classification is worthless; for a release pipeline it is essential. It means the cost is real, falls on every commit, and is paid by humans rather than the machine that benefits.

10. Finding Balance - When It Helps and When It Is Overkill

Having heard the criticism fully, let us find the balance point. The key question is not "is the convention good or bad?" but "in my project, does automation actually consume the commits?" That single criterion settles most of the decision.

Situation Conventional Commits Why
Public library / packageStrongly recommendedChangelog and version matter directly to users
Automated release with semantic-releaseStrongly recommendedCommits are release input; cost recovered at once
Large multi-contributor repoRecommendedConsistent, navigable history has high value
Internal service (no releases)OptionalWorth it with automation, ambiguous without
Personal / small projectUsually overkillOverhead exceeds the benefit

In short, the cost of the convention is recovered when there is a machine reading the commits. If you publish a library or automate releases, the convention is almost always a win. Conversely, for a solo repository or an internal tool with no concept of a release, the convention easily becomes a form to fill in. 11. The Alternative - Good Commit Messages Without the Convention

Deciding not to use the convention does not mean you may write commit messages carelessly. Instead of a strict format, following the principles of good commit messages earns much of the convention's core value at no cost. The long-proven principles are:

  • Short, imperative subject: start with an imperative verb like "Add" or "Fix" and keep it around 50 characters. Avoid mixing past and present tense ("Added", "Fixes").
  • Body explains "why", not "what": the diff already shows what changed. What the message must carry is why the change was needed and which alternatives were rejected.
  • One logical change per commit: avoiding tangled commits removes the classification dilemma entirely and makes reverts and reviews easier.
  • Link issues and context: attach the related issue number or a background link so a future reader can trace the context of the decision.

Interestingly, these principles do not conflict with Conventional Commits. Even with the convention, you still need them for a good history. The convention is neither necessary nor sufficient for a good commit. A bad commit that follows the format, and an excellent commit with no format at all, are both entirely possible.

12. A Practical Adoption Guide - Five Gradual Steps

So how should you actually decide and adopt? Enforcing commitlint on the whole team at once amplifies friction. Here is a gradual, five-step path.

  1. Decide on automation first. Before adopting the convention, answer "will we auto-generate a changelog or automate releases?" If the answer is no, you can hold off on the convention.
  2. Minimize the types. If you adopt it, do not use all ten - narrow to about feat, fix, chore, docs. Most of the classification ambiguity disappears.
  3. Enforce later. Do not block with a commitlint hook from day one; start with agreement and examples, then add tooling once the culture has settled.
  4. Actually wire up the tools. Attach semantic-release or release-please so commits truly flow into versions and changelogs. That is how the cost is recovered.
  5. Re-evaluate periodically. If the convention is not feeding automation and only the format remains, do not fear dropping it. Tooling is a means, not an end.

This gradual stance is a sound principle for development tooling in general. The habit of understanding a tool's hidden settings and trade-offs before adopting it echoes the approach in Claude Code Hidden Settings Explained.

13. Conclusion + Three Things You Can Apply Now

The honest answer to "Are Conventional Commits actually worth it?" is "it depends", and the thing that "it" depends on is clear: is there automation that consumes the commits? If a pipeline of automatic changelogs, semantic versioning, and semantic-release actually reads the commits, the convention returns big gains in consistency and automation. If no such consumer exists, the convention becomes the pure overhead that the formalism critique describes precisely.

Three things you can apply right away:

  1. Ask "do we consume commits automatically?" first. The answer to this one question decides 90% of whether to adopt the convention. Without automation, good commit-message principles come before the convention.
  2. If you adopt it, minimal types, enforcement later. Narrow to feat/fix/chore/docs and add tool enforcement only after the culture settles. This reduces ambiguity and friction at once.
  3. Write the "why" over the format. Convention or not, the greatest value of a commit message is the intent and context of the change. The five seconds spent picking a type prefix are better spent on a single line of "why I changed it this way" - a far bigger gift to a future colleague.
