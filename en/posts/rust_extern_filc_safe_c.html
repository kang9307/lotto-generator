One extern C Line and the Guarantees It Erases - Filling the Rust FFI Boundary and What It Costs

Neither wrappers nor binding generators can check a contract, so can the boundary itself be shrunk?

Aug 16, 2026 Dev & Infra

Introduction: it compiled, but what exactly got switched off

Whether it is an image decoder or a crypto library, when you pull a mature C implementation into a Rust project the code you actually touch is about ten lines. Declare the function signatures in an extern block, link it from the build script, put a thin wrapper on top. It compiles. The tests pass.

And at that moment the character of the project changes. Every guarantee the Rust compiler had been enforcing across your code — no reads of freed memory, never two mutable references to the same data, no data races — holds only for the code the compiler can see. The linked C object is outside that scope.

This article is about what precisely gets severed at that boundary, what the existing techniques for patching the gap do and do not catch, and how the extern "fil-c" proposal that appeared in August 2026 tries to cut the problem differently. To say it up front: that proposal is not an adopted feature — its exact stage is pinned down below.

What this article is not about is also worth stating. The question of whether to rewrite C in Rust or leave C in place and harden it was covered in Memory Safety Absolutists - The Rust vs Fil-C Debate and What Is Actually Practical. Here the subject is not who wins that argument but the meeting point between the two worlds itself.

1. What unsafe means at an FFI boundary - where the compiler stops checking

1.1 A declaration is not checked code, it is a human assertion

The reason Rust safety holds is simple. The compiler checks ownership, lifetimes and aliasing rules over the whole program. That check is only meaningful when the whole program is visible to it.

An extern block is where the premise breaks. The signature you write there is not a fact the compiler verified but an assertion you are making. Argument count, integer width, struct field order — none of it is validated. Get it wrong and it still compiles and still runs, and the failure surfaces much later somewhere unrelated.

The Rust 2024 edition changed the syntax so that extern blocks themselves must be marked unsafe, precisely to make this property visible. It was settled in RFC 3484, and on editions 2024 and later unsafe extern is mandatory. Individual items inside the block can carry a safe qualifier marking them callable without an unsafe block — though that marking too is a human assertion, not a machine result.

// Conceptual example. Not code whose behaviour has been verified.
unsafe extern "C" {
    // The compiler has no idea whether this matches the header
    fn img_open(path: *const c_char) -> *mut ImgCtx;

    // safe removes the need for an unsafe block at the call site.
    // No check appears; you are simply taking the responsibility here.
    safe fn img_version() -> u32;
}

1.2 The guarantees that actually break at the boundary

Saying that memory safety breaks is a lump statement. Splitting it into the specific things that fall out of the checked set also splits the mitigations.

  • Lifetime — how long a pointer returned from C stays valid. Until the next call, for as long as the context lives, or forever, is not in the signature.
  • Ownership and free responsibility — whether Rust should free the returned buffer, call a dedicated release function, or never touch it.
  • Mutable exclusivity — if the C library internally keeps an alias to the same buffer, forming a &mut on the Rust side already violates the language rules. The optimiser trusts those rules when it moves code around.
  • Nullability, alignment and initialisation state — whether the returned pointer can be null, whether the returned memory is initialised.
  • Thread safety — whether the library uses global state, whether it is reentrant, whether it must be called from one particular thread. The moment you hand-implement Send or Sync, that judgement is entirely yours.
  • Panics and unwinding — a Rust callback that panics through a C frame is undefined behaviour. The callback boundary needs a catch that swallows it.
  • ABI layout — pass a struct without #[repr(C)] and the field arrangement may differ. Enum value ranges, bitfields and padding belong in the same family.
  • Error convention — negative return, errno, or a last-error query function. Misread the convention and you treat failures as successes and keep going.

The compiler checks not one of those eight. So unsafe at an FFI boundary is less a warning about dangerous code than a marker that the checker jurisdiction ends here.

2. The existing answers - wrappers, binding generators and incremental rewrites

2.1 Safe wrappers: transcribing the contract into types

The standard practice in the Rust ecosystem is a two-layer structure. A -sys crate at the bottom holding only raw declarations, and a crate above it exposing a safe interface. The upper layer ties free responsibility to a type through RAII, expresses validity windows with lifetime parameters, and surfaces nullability as Option.

This works. A user of a well-built wrapper never writes unsafe once. The risk has not vanished, it has been gathered into one place, and that is a legitimate strategy for shrinking the audit surface.

The limits are in two spots. The guarantee that the wrapper is correct is still supplied by a human, so a misread contract gets packaged and propagated under the name of a safe interface. And contracts change — a C library can bump a minor version and switch to 「this pointer is now only valid until the next call」 while the wrapper still compiles exactly as before.

2.2 Binding generators: fewer transcription slips, but the contract is not in the header

Tools like bindgen parse C headers and generate declarations. Typos, integer-width mistakes and missing struct fields drop sharply, and because platform-dependent type sizes are re-derived at build time it is especially useful for cross compilation.

But a generator reads only the header, and almost none of the eight items above are written in a header. Whether a char* is a null-terminated string or a buffer with a separate length, and who frees a returned pointer, live in documentation rather than in any compilable form. A generator gives you correct declarations, not a safe interface.

2.3 Incremental rewrite: the boundary does not disappear, it moves

Porting leaf modules to Rust first is common and broadly sensible. The accounting is worth reading precisely, though. During the rewrite the boundary count goes up, not down. What was one contact point becomes as many as the number of modules moved, and each new contact point regenerates all eight items.

  • The modules that are easy to move are usually pure computation, which carried little risk to begin with. The safety gained per unit of effort is small.
  • The genuinely dangerous code — parsers, protocol handling, ancient state machines — has its contract outside the documentation, which is exactly what makes it hardest to move.
  • A rewrite either demands a feature freeze or forces two implementations to be maintained side by side for a while. Either way the organisation pays.
  • Until the rewrite finishes you cannot make a safety claim. Move ninety percent and the remaining ten percent in the same address space still sets the safety of the whole.

2.4 Dynamic checkers: they only see the paths you ran

AddressSanitizer and Valgrind genuinely catch a lot. Their character differs, though. They find violations only on executed paths, so coverage is the extent of the guarantee. They are too costly to leave on in release builds, and Miri, the Rust-side interpreter, fundamentally cannot see past FFI.

2.5 Comparing the approaches

ApproachWhat it really catchesWhat it missesNature of the cost
Safe wrapper (two layers)Caller misuse, missed frees, missed null handlingMisread contracts, upstream behaviour changes, bugs inside CUp-front design time plus upstream tracking
Binding generatorDeclaration typos, type-width mistakes, per-platform layout differencesEvery contract not in the header: lifetime, ownership, thread safetyExtra build dependency, review of generated output
Incremental rewriteMemory errors inside the ported modulesThe remaining C, and the added boundaries themselvesLong-run headcount, dual maintenance period

Read the table down a column and the common thread appears. No cell guarantees that the C side obeys the rules. Every one of them either defends at the boundary, moves the boundary, or discovers the damage afterwards.

3. What Fil-C is aiming at - shrink the boundary rather than move it

Here the framing flips once. Instead of defending at the boundary, make the far side safe and there is less to lose at the boundary. That is where Fil-C stands.

Fil-C is a C and C++ compiler built by Filip Pizlo as a fork of Clang and LLVM, which recompiles sources unchanged and gives them runtime memory safety. Three things carry it.

  • InvisiCaps — a pointer looks like a 64-bit value but is really a trusted capability separated from an untrusted address. Capability information lives in a side area, and every access is checked against bounds.
  • A concurrent garbage collector — lifetime management moves into the runtime so that use-after-free is eliminated at the root.
  • No escape hatch — per the repository, Fil-C has no unsafe keyword that could turn protections off. That is a design declaration, not a missing convenience.

When a violation occurs the program panics instead of drifting into an exploitable state. So what Fil-C changes is not that bugs disappear but that the consequence of a bug drops from arbitrary code execution to process termination. That distinction is decisive when you write a threat model — availability remains attackable while confidentiality and integrity hold.

And this yields the property that matters most for the subject at hand. Fil-C is source compatible but deliberately not ABI compatible, because the pointer representation differs. It cannot link against objects built by an ordinary compiler, so the program and its entire dependency tree must be recompiled with Fil-C. In Fil-C terminology the ordinary C ABI is called Yolo-C — and Yolo-C is exactly what Rust extern "C" speaks.

4. The current stage of the extern fil-c proposal - what exists and what does not

On 13 August 2026 Domen Kožar published I want extern fil-c on his blog. The thesis fits in one sentence: he would like a Rust FFI that speaks the Fil-C ABI.

The stage, stated precisely: as checked on 16 August 2026 this is a personal blog post, not an RFC submitted to the rust-lang repository. There is no numbered RFC, no tracking issue and no implementation branch. The piece reads as an invitation rather than a specification, and it closes by proposing that people from the Rust, Fil-C, Zig and Nix communities gather at next year OceanSprint and build it together. Mikael Brockman, who packages Fil-C as a Nix cross-compilation platform in filnix, has said he is in.

The scope the proposal sketches for a first version is deliberately narrow.

  • Scalar values, copied strings and slices, and opaque handles — those three to start. Passing complex pointer graphs across as-is is not attempted.
  • It generates safe Rust wrappers. Removing the step where a human transcribes the contract is the point.
  • The whole C dependency graph gets compiled with Fil-C. Partial application does not hold together.
  • No escape hatch back to ordinary unsafe C. In the author phrasing, the trick is not to quietly punch a Yolo-shaped hole in the guarantee.

Why a new ABI string is needed also becomes clear here. The string in extern "…" is a switch that selects a calling convention, and since Fil-C differs right down to the pointer representation, extern "C" cannot carry the conversation. It is not a matter of syntactic taste but the minimum apparatus for addressing a different world.

// Hypothetical syntax. Nothing is settled and nothing here has been run.
// This only renders the direction of the proposal as a concept.
extern "fil-c" {
    // Pointers on the Fil-C side carry capabilities, so an
    // out-of-bounds access ends as a panic on the callee side.
    fn parse_config(text: &str) -> Result<ConfigHandle, ParseError>;
}

The author is equally clear about the difficulty. That boundary is the hard part, and Fil-C treats interoperability with ordinary C as a non-goal by design. What the Rust-side bridge has to do is not merely call a function but preserve, while building the bridge, the whole-world guarantee Fil-C imposes on a program.

5. Cost one - performance, memory, and how to read the numbers

Runtime checks plus garbage collection cannot be free. The trouble is that each quoted figure comes with different conditions, so a single number misleads. Here is what is confirmed, with conditions attached.

Source and dateConditionsFigure
LWN article (2025-10-28)Per Fil-C documentation, typical programsAbout 4x slower, overhead rising with pointer-heavy code
LWN article (2025-10-28)Structures containing pointersRoughly 2x memory use
LWN article (2025-10-28)bash 5.2.32 built with Fil-C and usedNo perceptible performance difference
Zig proposal issue (2026-07-20)Range cited while discussing adoption of the approach1x to 6x
extern fil-c post (2026-08-13)No benchmark offeredNo figures — only the direction that the tax disappears once checks become static

Read plainly, the width of the spread is itself the information. Check cost scales with how often you chase a pointer. So it splits like this.

  • Numeric work, signal processing and the inner loops of compression — code that is mostly array indexing — loses relatively little.
  • Linked lists, trees and graph traversal — code that chases pointers continuously — loses a lot.
  • Short-lived, I/O-dominated tools such as shells, build scripts and CLI utilities may show almost no perceptible difference. The bash observation belongs to this family.
  • Memory growth hits container limits and packing density before it hits throughput. How many instances fit on a node changes.
  • With a garbage collector in the picture, the tail latency distribution shifts more than the mean does. If a path has real-time requirements, measure that separately.

So the axis of judgement is not 「can I absorb 4x」 but 「is C on my hot path」. A thumbnail generator whose decoder runs 4x slower is a non-event for most services. The same multiplier in the middle of the request path rewrites capacity planning entirely.

6. Cost two - build, ecosystem and tooling maturity

In practice this side trips people up more often than performance does.

6.1 The weight of requiring a whole-program recompile

Because the ABI differs, you cannot use the .so your distribution ships. The entire dependency tree including libc has to be built with Fil-C. That is not merely a build-time issue but a change to the supply chain itself. The security-update path your package manager used to provide must be replaced by your own build pipeline.

This is where filnix earns its place. It packages Fil-C as a Nix cross-compilation platform, providing a reproducible toolchain and package universe, and more than a hundred nixpkgs packages have been ported. In other words it is the project that built the infrastructure needed to absorb the whole-recompile requirement, and without something like it this approach struggles to leave the lab.

6.2 Platforms and maturity

  • Per the repository notes, Fil-C runs only on Linux/x86_64 and Linux/ARM64. Darwin/ARM64 and FreeBSD, supported previously, are not current targets.
  • There is no Windows support. For a desktop application or a cross-platform library, that single line removes it from the shortlist.
  • The version number has not reached 1.0, and per LWN it is a relatively new project started in 2023 and led effectively by one person.
  • Licensing is layered. Compiler side, runtime side, and musl- or glibc-based distributions each carry different terms. This is a legal-review item before any internal rollout.
  • How well debuggers, profilers, core-dump analysis and static analysers understand the new pointer representation needs separate verification. If you cannot read a stack during an incident, the safety gain is partly cancelled out.

In short, the entry cost of this approach sits in build infrastructure and operational tooling rather than in code. An organisation that already builds its own container images on a reproducible toolchain is close to it; one that depends on vendor-supplied binaries is far from it.

7. Zig is heading the same way - the idea is not a single voice

That the same framing surfaced in another language is information in itself. On 20 July 2026 Andrew Kelley of Zig proposed a fully memory-safe compilation mode inspired by Fil-C. The issue carries an accepted label and an upcoming milestone, but it is not implemented. Here too, stage and date have to be read together.

  • It keeps the existing optimisation modes and adds an optional ABI named fil.
  • It plans an independent implementation of the Invisicaps approach plus syscall wrapping inside the Zig compiler.
  • It starts on x86_64-linux with an eye on widening to other platforms.
  • It draws an explicit contrast with Rust — no unsafe escape hatch, and application across the whole C and C++ dependency tree.
  • The creator of Fil-C is taking part in the issue discussion, working through allocator interfaces and architecture compatibility.

Set the two proposals side by side and a shared structure appears. Both cut the problem as 「make the unsafe side safe and remove the boundary」 rather than 「rewrite it in a safe language」. And both are still proposals. Neither is a switch you can flip in production today.

8. What to choose - a verdict table by condition

The options are not mutually exclusive. Different answers for different code inside the same organisation is the normal case. The table below does not decide for you; it sets out which axis to look at first.

Two axes repeat through the table. How long will this code live, and what happens when a violation occurs. The remaining conditions are closer to execution problems once those two are settled.

9. What could not be confirmed

The following had no settled answer at the time of writing. No assertions are made about them.

  • Whether extern "fil-c" has since been submitted as a formal RFC, and how the relevant teams responded, is not confirmed. If it matters to a decision, check the rust-lang RFC repository and the Internals forum directly.
  • No public case of Rust and Fil-C actually wired together and running was found. The first-version scope in the proposal is design intent, not an artefact.
  • A reproducible public benchmark suite under identical conditions was not located. The figures in the table above come from different conditions and cannot be compared directly.
  • No published plan or date for Fil-C support on Windows or macOS was found.
  • How procurement or financial-sector security requirements phrase memory safety — naming a language or naming a property — is outside the scope of this article.
  • Which release the Zig fil ABI targets has not been fixed.

Frequently asked questions

Is extern fil-c already a Rust feature?

No. As of 16 August 2026 it is a proposal from a personal blog post, with no numbered RFC, no tracking issue and no implementation. That the piece ends by inviting people to build it at next year sprint tells you its character. Its real value today is not a feature but a way of cutting the problem.

If I use unsafe blocks carefully, is my FFI not safe already?

unsafe does not make a check pass; it declares that a human is doing the checking instead. Pointer lifetime, free responsibility and thread safety are not in the header, so the compiler cannot see them. Using it well means you read the contract correctly and moved it into a wrapper, and when upstream changes that contract in a release, the transcription becomes wrong while still compiling.

How much performance does Fil-C cost?

It depends on conditions. About 4x is quoted from the documentation, yet the same article observed no perceptible difference for bash, and Zig-side discussion cites a 1x to 6x range. Check cost scales with pointer-chasing frequency. No single number is honest until you measure your own workload.

Why not just use extern C instead of a new ABI string?

Fil-C is source compatible but deliberately not ABI compatible, because a pointer is a capability paired with an address. Rust extern "C" speaks the plain C ABI, which Fil-C calls Yolo-C. The two worlds cannot converse through the same string, so a separate one is required.

What can I actually do about this today?

Three things pay off regardless of adoption. Enumerate the FFI boundaries in your project; write each boundary function contract (lifetime, free responsibility, thread safety, nullability) explicitly in the wrapper comments; and attach fuzzing to boundaries that untrusted input reaches. Whichever transition you eventually pick, these three become its input.

Conclusion: what remains even if it is never adopted

Whether extern "fil-c" ever lands in Rust is unknowable. On base rates alone, ideas that start on a personal blog rarely become language features. It has value anyway, because it redefined the problem.

FFI safety discussion has mostly been about how well to defend at the boundary. Better wrappers, smarter generators, denser checkers — all necessary, and all sharing one premise. The premise is that the far side is untrustworthy by definition. This proposal pokes at that premise.

Reduced to what is usable today, there are three things.

  • Count the FFI boundaries in your project. Without knowing how many there are and what contract each assumes, no option can be compared against another.
  • Write down what a violation results in, per boundary. Arbitrary code execution versus process termination changes the priority of the response completely.
  • Keep reading proposal stage and adoption stage as separate things. This field produces interesting ideas often, and a good share of them stay ideas for a long time.

This is not a question of which language is better. C carries forty years of proven implementations; Rust carries rules verified at compile time. As long as both assets share an address space the boundary exists, and how to handle that boundary is the question practice has to answer. Adopted or not, that question remains.
