エージェントに任せる前にデータを整えよ - Martin Fowlerの段階的自律性原則

人間の暗黙の直感に依存していたデータ基盤を機械が信頼・実行できるアーキテクチャへと刷新する

2026-09-14 開発・インフラ

序論：モデル性能競争の陰に潜むボトルネック、データインフラ

近年の人工知能分野における議論は、フロンティアモデルのパラメータ規模やマルチモーダル機能、自律的にツールを選択してタスクを実行するエージェントフレームワークに集中しています。多くの企業が新しい推論モデルが登場するたびに社内システムへ組み込み、複雑なオーケストレーションを構築すれば、即座に現場業務を自律化できると期待しています。しかし、実際に社内の基幹データベースやERP、CRMシステムに自律型エージェントを接続した途端、多くのプロジェクトが深刻な停滞に直面します。問題の本質はモデルの知能の低さにあるのではなく、エージェントへ供給されるエンタープライズデータが、機械が直接消費できる状態に全く整っていない点にあります。

過去30年以上にわたり、私たちが構築してきた企業データアーキテクチャは、画面の前に人間が座っているという前提で設計されてきました。ダッシュボード画面、定期レポート、アドホックなSQLクエリは、すべて「人間のアナリスト」を最終消費者として想定しています。人間の担当者はこれまでの経験を通じて、どのテーブルに古いデータが混在しているか、どの数値が怪しいかを直感的に知っています。数字に違和感があれば同僚にチャットで確認し、祝日の影響や定義変更を頭の中で加味してクエリを調整します。不完全でノイズの多いデータが存在しても、人間の持つ暗黙知と健全な懐疑心が、システムの欠陥を人知れず補ってきたのです。

しかし、自律型AIエージェントは全く異なる特性で動作します。エージェントは渡されたすべてのデータを疑うことなく確定的な事実（Ground Truth）として受け止め、矛盾した数値や鮮度の落ちたデータに対しても一切躊躇することなく、確信に満ちた態度で判断を下し外部APIを呼び出します。人間が暗黙のうちに行っていたセーフティネットを取り除いたまま機械の実行力を解放すると、些細なデータ不整合が即座にビジネスの重大事故へと連鎖します。まさにこの課題を構造的に解き明かしたのが、Martin Fowlerの技術サイトに寄稿されたThoughtworksのエンジニア陣（Pramod Sadalage氏およびPremanand Chandrasekaran氏）による論考です。エージェント導入における真の投資先はフレームワークの選定ではなく、エージェントが信頼できるデータ基盤と厳格なガバナンス体制を足元から構築することにあります。

先行の議論との関係：データ契約（Data Contract）の基本的な必要性や、スキーマ定義だけでは防ぎきれない意味のずれ（セマンティックドリフト）の一般論については、当サイトの既存の記事データを運ぶことより意味を合意することが難しいで詳細に論じました。本稿では、分析用データウェアハウスの議論から一歩進み、データを自律的に読み解き外部システムへの書き込み（状態変更）まで実行するエージェント環境において、データ契約と品質検証が自律性拡大の絶対前提となる理由を掘り下げます。

本稿では、Thoughtworksの知見をベースに、エージェント型AIのためにデータ基盤を刷新する4つの柱を整理します。データ契約による不良データの隔離、意思決定の理由を復元するエージェント系統、名詞・数値・動詞をコードで宣言する文脈層、そして静的な検索から書き込みへと至る段階的自律性拡張のロードマップを、実務的な観点から紐解いていきます。

人間の消費者と機械の消費者の根本的な違い：データの「臭い」を嗅ぎ分けられないエージェント

人間のアナリストには、問題のあるデータを直感的に嗅ぎ分ける「嗅覚（Smell Test）」が備わっています。特定カラムの数値が異常にきれいな丸数字であったり、祝日に大量の売上が計上されていたり、先週値上げしたはずの単価が古いまま残っていれば、人間は必ず立ち止まります。「先週の会議でこの製品の価格を59.99ドルに改定したはずだが、なぜ49.99ドルのままなのか」と疑問を抱き、そのまま決済を通さず担当部署に事実関係を確認します。この組織内の記憶とパターン認識こそが、これまでのデータ処理において膨大な見えないコンテキスト補正を担っていました。

しかし言語モデルは、Simon Willison氏が指摘するように本質的に「騙されやすい（Gullible）」性質を持っています。プロンプトやコンテキストに注入された前提を純粋に信じ込み、誤った前提の上で最も論理的で流暢なテキストを生成します。例えば、ある製品の価格が前日に49.99ドルから59.99ドルに改定されたものの、レプリケーションの遅延によりエージェントが参照するデータソースが古い49.99ドルを示していたとします。価格決定エージェントは一切迷うことなく49.99ドルを顧客に提示し、注文を確定させて販売1件あたり10ドルの損失を会社にもたらします。エージェントが実行したワークフローは技術的に完璧でしたが、参照したデータが誤っていたためにビジネス損害が発生したのです。

経営層の自信と現場の実態の間には深刻な乖離が存在します。Precisely社とドレクセル大学LeBow経営大学院がデータ・分析リーダー505人を対象に実施した2026年の調査（State of Data Integrity and AI Readiness）によると、回答者の88%が自社のデータはAI導入に対応できていると答えた一方で、43%がデータ準備状況こそがAIの価値創出を阻む最大の障壁であると挙げました。また、KPMGが2,145人の経営層を対象に実施したグローバル調査でも、半数近くのエグゼクティブがAIへの投資コストがビジネス上の便益を上回っていると回答しています。大半の組織が、たった1つの古いフィールド値によって大事故を引き起こすリスクに晒されているのです。

人間が無償で提供していた暗黙の判断業務をデータ基盤自体に移行させるため、元記事では「AI対応データ（AI-Ready Data）」を構成する5つの必須属性を定義しています。

属性人間の従来の暗黙的な振る舞いエージェント環境で要求されるアーキテクチャ実装
信頼性（Trusted）不審なデータを見つけると立ち止まり関係者に再確認するエージェントが見る前に鮮度と品質基準を機械的に検証・保証する
文脈性（Contextual）売上から返品が引かれているか、会計年度が何月開始か記憶しているビジネス定義や計算規則をコードとして明示的に宣言し保持する
追跡性（Traceable）判断を下した後、なぜそう判断したのかを後から口頭で説明できる推論プロセスや参照元の全体をスパン単位で自動ログとして記録する
ガバナンス（Governed）自身の職位や一般的な常識に基づき、アクセス権限を自己抑制する委譲アクセスと短命な認証情報によりエージェントの権限範囲を設計で縛る
運用性（Operational）ダッシュボードを読んだ後、手作業で他システムを操作して処理する読み取りに留まらず、安全にシステム状態を変更できるツールを提供する

2.1 沈黙するデータエラーと、自信満々に誤動作するリスク

従来のソフトウェア障害は「騒がしい失敗」でした。データベースのカラムが消去されたり型が不一致を起こせば、パイプラインは即座にエラーを吐いて停止しアラートが鳴ります。一方で、形式は維持されたまま意味が変わったり、過去のデータが滞留する現象は「静かな失敗」です。パイプラインはすべて正常終了を示し、ダッシュボードも無事に描画されます。エージェントはこの静かに破損した数値を疑いなく消費し、誤った価格での発注や無効な払い戻し処理を大量に発生させていきます。

2.2 人間の暗黙知をデータインフラの明示的なルールへ変換する

エージェント型AIを実稼働させる鍵は、組織内の暗黙のルールを明示的なコードへと書き換えることに尽きます。「このテーブルはバッチが遅れやすいから確認が必要だ」という警戒感は鮮度SLAコードへ、「売上集計では検証用アカウントを除外しなければならない」という習慣はセマンティック層の必須フィルタへと昇華されなければなりません。この地道なコード化をスキップして高度なモデルだけを導入しても、確信に満ちた誤動作を防ぐことは不可能です。

  • 信頼性の機械的担保: エージェントが読み込む直前にデータの整合性と更新時刻を厳格にアサーション検証
  • 文脈のコード化: 総売上や純売上、アクティブユーザーなどの曖昧な定義を宣言的設定ファイルに固定
  • 事後検証の完全性: 規制当局や内部監査の要求に応じ、判断に至る根拠と推論経路を完全に再現可能にする
  • 最小権限のアーキテクチャ: 広範な共有サービスアカウントを排除し、呼び出し元ユーザーに基づく委譲アクセスを採用
  • 段階的な権限付与: 読み取り専用の検索から始め、実績とテスト評価を積み重ねて書き込み権限へと拡張

データ契約と隔離パターン：汚染された入力値を上流で遮断する

エージェントへの不正データの混入を防ぐ最も確実な手法は、スキーマ定義を単なる推奨事項ではなく「厳格な法律」として扱うことです。過去10年間は柔軟性を重視してスキーマレスや緩やかな検証が好まれましたが、自律エージェントにとって緩いスキーマは致命傷となります。Open Data Contract Standard（ODCS）などの標準形式を用いてデータ契約（Data Contract）をコードとして定義し、CI/CDパイプラインおよび取り込みゲートで機械的に強制する必要があります。

Thoughtworksの論考で紹介された価格データのデータ契約例では、厳密な論理型・物理型を指定するだけでなく、価格が0より大きいことを保証するSQLルール、通貨コードをUSD・EUR・GBPの3種類に限定するチェック、そして取り込み時刻（`ingested_at`）が過去24時間以内であることを求める鮮度SLAが明記されています。

apiVersion: v3.1.0
kind: DataContract
id: product-pricing
name: Product Pricing
version: 1.0.0
status: active
schema:
  - name: product_pricing
    physicalType: table
    properties:
      - name: product_id
        logicalType: string
        physicalType: varchar(64)
        required: true
        unique: true
        primaryKey: true
        primaryKeyPosition: 1
      - name: price
        logicalType: number
        physicalType: decimal
        required: true
        quality:
          - type: sql
            description: Every price must be greater than zero
            query: SELECT min({property}) FROM {object}
            mustBeGreaterThan: 0
      - name: currency
        logicalType: string
        physicalType: varchar(3)
        required: true
        quality:
          - type: sql
            description: Currency must be a supported ISO code
            query: SELECT count(*) FROM {object} WHERE {property} NOT IN ('USD', 'EUR', 'GBP')
            mustBe: 0
      - name: ingested_at
        logicalType: timestamp
        physicalType: timestamp
        required: true
        slaProperties:
          - property: latency
            value: 24
            unit: h
            element: product_pricing.ingested_at

この契約は3つの次元で執行されます。第1はスキーマ強制であり、宣言された型や制約に違反していないかを検証します。第2は鮮度SLAであり、許容される遅延時間内にデータが届いているかを判定します。ここで極めて重要なのは、鮮度の計測基準を「値自体が変更された時刻」ではなく「パイプラインによって正常にデータが取り込まれた時刻」に結びつけることです。これにより、値に変動のない正常なデータが古いと誤認されるのを防ぎ、同時にパイプラインの停止事故を隠蔽してしまうリスクを遮断できます。第3はCI/CDゲートであり、契約を破壊する変更がマージされるのを自動テストで未然に防ぎます。

3.1 スキーマ強制と鮮度SLAの組み合わせ

データ契約を実効性あるものにするには、静的な型検証と動的な鮮度検証の統合が欠かせません。データベースの列の型が合致していても、取り込みから48時間が経過していればリアルタイムな見積エージェントにとっては毒となります。定期バッチのレポートを見る人間なら許容できても、自律的に取引を実行するエージェントには分単位の鮮度が要求される場合があります。消費者のユースケースごとに差別化された鮮度SLAを契約に埋め込む必要があります。

3.2 隔離パターン（Quarantine Pattern）とデッドレターキューの役割

契約を定義した後に必要となるのが、違反データに対するブレーカー機構、すなわち「隔離パターン（The Quarantine Pattern）」です。外部APIやデータベースから届いた生データは、エージェントが参照するストレージへ直接流し込まれません。取り込みゲートにおいてスキーマ、鮮度、品質の3条件が検証され、1つでも違反したレコードは即座にデッドレターキュー（Dead Letter Queue）へと迂回隔離されます。

隔離されたデータは担当エンジニアにアラートを飛ばして調査を促し、エージェントの視界からは完全に隠蔽されます。先ほどの価格の例であれば、鮮度24時間を超過したレコードは隔離されるため、エージェントは古い49.99ドルを提示する代わりに「現在の正規な価格データが存在しません」と安全に失敗（Fail-safe）します。誤った数値で勝手に取引を成立させるより、データ不足を明かして人間にエスカレーションする失敗モードのほうがビジネス上の安全性を遥かに高く維持できます。

3.3 メダリオンアーキテクチャにおけるエージェントアクセス層（Gold以上）の分離

Databricksが提唱しレイクハウス環境で定着したメダリオンアーキテクチャ（Medallion Architecture）も、エージェント向けに見直す必要があります。変更不可能な生ログを蓄積するBronze層や、契約検証と重複排除が行われるSilver層は、系譜の確認や人間によるデバッグのための領域であり、エージェントには直接公開してはなりません。エージェントは品質が保証され、セマンティックモデルがコンパイルされたGold層以上にのみアクセスを制限すべきです。

さらに進んだ形態として、エージェントが自身の利用パターンを観察して頻出するクエリの組み合わせをビューとして実体化する「Adaptive Gold」層の構想も示されています。DataHubのCONTEXT 2025においてApple社がデータカタログのメタデータ欠落を点検・補正する「デジタルスチュワード」エージェントを紹介したように、エージェントがデータの単なる消費者からキュレーターへと進化するパターンも登場し始めています。この隔離と階層化の原則は、RAGに用いるテキストチャンクやベクトル埋め込みのパイプラインにもそのまま適用されるべきです。

  • ODCS規格の採用: 業界標準フォーマットでデータ型、値の範囲、許容コードをコード化
  • 取り込み基準のSLA: 値の更新日ではなくパイプラインの正常投入時刻を基準に鮮度を測定
  • デッドレターキュー隔離: 違反レコードを即座に隔離し、エージェントへの露出を完全に防止
  • 安全な縮退動作: 誤ったデータで自律判断させるのではなく、データ欠落を認めて人間に引き継ぐ
  • Gold層以上の隔離: 不完全なBronzeやSilverを隠蔽し、認証済みのGold層以上のみをエージェントに解放

監査証跡とエージェントの系譜：「何を」だけでなく「なぜ」を記録する

データがどれほど清潔であっても、エージェントが社内システムで自律的な判断を下すようになれば、まったく別のガバナンス上の問いが浮上します。例えば、貿易金融エージェントが信用状（Letter of Credit）の発行申請を受け、KYCの照合、制裁対象者リストの確認、与信条件の評価を行い、わずか30秒で240万ドルの取引を承認したと仮定します。半年後に金融規制当局や内部監査から「なぜこの融資が承認されたのか」と問われた際、企業はその根拠を明確に復元できなければなりません。

従来のシステムログはこの問いに答えられません。従来のログには「特定のサービスアカウントが何時何分にコンプライアンスDBのテーブルを照会した」という「何（What）」の事実しか残らないからです。なぜ制裁リストを信用条件の前に確認したのか、軽微な書類の不一致をなぜ許容できると判断したのか、どのような代替案を検討した上で却下したのかといった「理由（Why）」は一切記録されません。この溝こそが、企業が直面する致命的なガバナンスの盲点です。

この監査の空白を埋める技術が「エージェント系統（Agentic Lineage）」です。分散トレーシングの概念をエージェントの推論ループに適用し、信用状LC-4892の処理全体を1つのトレース（Trace）として捕捉します。その中で、KYC確認、OFAC APIによる制裁確認、与信審査の各工程が個別のスパン（Span）として紐づけられ、最終スパンにおいて94%の信頼度スコアと完全な思考連鎖を伴って「承認」の判断が下されたという全体像が詳細に保存されます。

この記録体制は単なるベストプラクティスにとどまらず、法的な義務へと急速に収束しています。欧州連合の人工知能法（EU AI Act）第12条は、高リスクAIシステムに対してライフサイクル全体を通じたイベントの自動ロギングを義務付けており、第19条はプロバイダーに対してそのログを最低6ヶ月間保持することを求めています。これに違反した場合、最大1,500万ユーロまたは全世界年間売上高の3%という巨額の過料が科されます。他地域の企業であっても、事後デバッグや顧客との紛争解決のために意思決定理由の復元力は避けて通れません。

4.1 従来のログとエージェント系譜（Agentic Lineage）の決定的な溝

従来のインフラ監視ツールは決定論的な実行結果のみを追跡します。しかしエージェントは非決定論的であり、プロンプトやコンテキストのわずかな差異によって異なるツール選択を行います。事後検証を可能にするためには、入出力のペイロードだけでなく、「データソースZから情報Yを得たため、次にアクションXを実行した」という因果関係そのものを構造化して保持しなければなりません。

4.2 分散トレーシング（Trace & Span）と規制コンプライアンス（EU AI Act）

JaegerやZipkinといった分散トレーシングの思考モデルは、エージェントの観測性確立にそのまま流用できます。近年急速に普及しているOpenTelemetryのAI向け規格や、Langfuse、Arize Phoenixといった専用プラットフォームは、複数ステップのエージェント挙動を可視化します。EU AI Actの第12条・第19条が要求する厳格な基準を満たすには、これらのトレースを検索可能な長期保管インフラに統合し、いつでも監査に対応できる状態を保つ必要があります。

4.3 委任アクセスとジャストインタイム認証情報による致命的な三重苦への防御

エージェントのセキュリティにおいて最も危険なのは、全社的な強大権限を持つ単一のサービスアカウントをエージェントに与えてしまうことです。アリスというユーザーがエージェントに口座照会を依頼したのなら、エージェントは全顧客のデータを見渡せる特権ではなく、アリス本人の権限を一時的に引き継ぐ「委譲アクセス（Delegated Access）」で動作すべきです。誰の代理として行動しているのかがログ上で明確にならなければ、説明責任は成立しません。

さらに、永続的なAPIキーを廃止し、タスクごとに5分間だけ有効な「ジャストインタイム（JIT）認証情報」を動的に発行します。これにより、Simon Willison氏が警鐘を鳴らす「致死的トリフェクタ（The Lethal Trifecta）」—機密データへのアクセス権、信頼できない外部コンテンツへの露出、外部通信手段の3つが揃うことで、プロンプトインジェクションにより機密が外部流出するリスク—を解体できます。万が一エージェントが乗っ取られても、奪える権限と時間を最小限に抑え込む設計が不可欠です。

  • 判断理由の因果関係記録: 単なるアクセス時刻だけでなく、取得データが次の推論に与えた影響を保存
  • トレース・スパン構造の徹底: OpenTelemetry等の分散トレーシング技術を用いて思考プロセスを可視化
  • 規制に準拠した長期保管: EU AI Act第12条・第19条に基づき最低6ヶ月間以上の完全なログを維持
  • 委譲アクセスによる個人の特定: 共有サービスアカウントを排し、依頼元のユーザー権限を厳密に継承
  • 短命なJITトークン発行: 常駐する長寿命APIキーをなくし、タスク実行時のみ有効な認証情報を使用
  • 致死的トリフェクタの遮断: 権限範囲と通信経路を極小化し、プロンプトインジェクション被害を局所化

コンテキスト層の3つの軸：名詞・数値・動詞の宣言的バージョン管理

データが清潔で監査ログが万全であっても、ビジネス用語の明確な定義が与えられていなければエージェントは正しく機能しません。「製品Xの第3四半期の売上はいくらか」と人間に尋ねれば、社内カレンダーが2月開始であること、売上とは値引きや返品を差し引いた純売上であること、どのテーブルを結合すべきかを即座に理解します。しかし、エージェントにこの文脈が与えられていなければ、適当なテーブルを結合して誤ったSQLを生成するか、ハルシネーションを起こしてしまいます。

このギャップを埋めるのが「文脈層（The Context Layer）」です。従来のBIツールのセマンティックレイヤー（指標の計算式定義）をさらに拡張し、企業内に存在する実体（名詞）、指標の計算式（数値）、そして実行可能な操作（動詞）をコードとして宣言し、一元的にバージョン管理する仕組みを指します。エージェントは生のデータベーススキーマを直接推測するのではなく、この文脈層を通じてデータを安全に解釈します。

構成モデル言語的役割定義内容と責務実行対象およびアクセス経路
ドメインモデル（Domain Model）名詞（Nouns）エンティティ、関係性、業務上の意味規則（例: 注文は顧客に属する）参照用の知識モデルであり、直接的なクエリ実行経路は持たない
セマンティックモデル（Semantic Model）数値（Numbers）指標とディメンションの計算式（例: 売上＝注文額−値引き額）分析用DWH（SQL）へと決定論的にコンパイルされ結果を返す
機能モデル（Capability Model）動詞（Verbs）許可された実行操作、前提条件、責任者、可逆性クラスの定義運用系システム（API、MCP）を通じて保護された状態変更を行う

指標をコードとして管理するアプローチは、dbt MetricFlowの記述例を見れば明確です。注文テーブルにおいて、売上（revenue）が `order_amount - discount_amount` の合計として計算されるべきであるという定義をYAMLに固定します。これにより、誰がどのような自然言語で問い合わせても、同じ計算式が一貫して適用されます。

semantic_models:
  - name: orders
    model: ref('orders')
    defaults:
      agg_time_dimension: order_date
    entities:
      - name: order_id
        type: primary
      - name: customer_id
        type: foreign
    dimensions:
      - name: order_date
        type: time
        type_params:
          time_granularity: day
    measures:
      - name: revenue
        agg: sum
        expr: order_amount - discount_amount
        create_metric: true

セマンティックモデルの有無によってエージェントが生成するSQLの精度は天と地ほど変わります。定義がない場合、エージェントはテーブル名やカラム名を勝手に推測し、必須の値引き控除を落とします。定義が存在する場合、エージェントはコンパイラによって制約され、正しい結合と日付範囲を持ったSQLを出力します。

-- 指標定義がない場合にエージェントが推測で生成した不正確なSQL例
SELECT SUM(amount) FROM sales_data WHERE product = 'Product X' AND quarter = 'Q3';

-- セマンティックモデルの制約によって厳格にコンパイルされた正確なSQL例
SELECT SUM(order_amount - discount_amount)
FROM orders o
JOIN products p ON o.product_id = p.id
WHERE p.name = 'Product X'
  AND o.order_date BETWEEN '2025-07-01' AND '2025-09-30';

5.1 ドメインモデル・セマンティックモデル・機能モデルの分離と共通語彙

文脈層を構築する際によくある失敗は、指標集計用の顧客定義と、返金処理を実行する機能モデル側の顧客定義がバラバラに管理されてしまうことです。両者が乖離すれば、売上集計でカウントされた顧客に対して正しい返金処理が行われないといった不整合が生じます。ベースとなるドメインモデルを共通の語彙基盤とし、その上で集計用のセマンティックモデルと行動用の機能モデルを整合させなければなりません。

また、これら3つのモデルはすべてGitなどのバージョン管理システムにコードとして保管される必要があります。売上の定義改定や返金ルールの変更は、プルリクエストとコードレビューを経てCIテストを通過した後に初めて本番環境へデプロイされるべきです。ツールの管理画面で属人的に設定を変更する運用は直ちに破綻します。

5.2 ナレッジグラフを活用した動的関係性と時間性の探索

単純な集計クエリであればリレーショナルデータベースへのSQLコンパイルで十分ですが、「ある顧客が製品Xを購入し、価格改定の後に解約するまでに至った一連のサポート履歴」のように、探索の深さが事前に特定できない関係性の追跡はフラットなテーブルでは困難です。これこそがドメインモデルを知識グラフ（Knowledge Graph）として管理する真価です。

Microsoft GraphRAGやGraphitiといった技術は、エンティティ間の複雑な関係性や時間経過に伴う変化をグラフ構造として保持します。セマンティックモデルが数値を司り、知識グラフが文脈と関係性を補完することで、エージェントは組織のベテラン社員に匹敵する深い業務文脈を獲得できるようになります。

  • メトリクス・アズ・コード: 指標の計算ロジックをアドホックなSQLではなくGit上のコードとして管理
  • 推測SQLの排除: LLMにスキーマを推測させず、統制されたコンパイラを経由させてSQLを固定
  • 共通語彙の確立: 指標集計とシステム実行機能が同一のドメインエンティティキーを参照するよう統一
  • 敵対的テストの実施: エージェントがハルシネーションを起こした際はプロンプトではなく未定義のモデル側を修正
  • 知識グラフによる関係性探索: テーブル結合では扱いきれない深い因果関係や時間的変遷をグラフで補完
  • 範囲の絞り込み: 全社のオントロジーを一気に作ろうとせず、部署間で定義が衝突している重要指標から着手

検索から書き込みへ：段階的な自律性拡張とその参入障壁

データが信頼でき、文脈層が整った後に直面するのが、エージェントの「データアクセス権限」をいかに安全に開放していくかという課題です。現在多くの組織が導入している静的なドキュメント検索（RAG: Retrieval-Augmented Generation）は、エージェントアクセスの最も初歩的な段階に過ぎません。RAGエージェントはマニュアルを検索して案内することはできても、稼働中のサービスの障害状況を調査したり、JiraやServiceNowにインシデントチケットを発行することはできません。

マイクロソフトのAI向けクラウド導入フレームワーク（Cloud Adoption Framework for AI）でも示されているように、エージェントのアクセスは検索（Retrieval）、リアルタイム照会（Real-Time Query）、そして状態を変更する書き込み（Write-Back）という3段階のスペクトラムに分かれます。段階が上がるほどビジネスの自動化価値は飛躍しますが、潜在的な運用リスクも跳ね上がります。そのため、エージェントの自律性は厳格な管理下で段階的に開放されなければなりません。

アクセス階層主な操作内容MCPプリミティブ内在するリスクと要求される統制機構
第1段階: 検索（Retrieval）ベクトル検索、文書参照、ガイド確認Resources（読み取り専用リソース）リスク最小。チャンク鮮度SLAとメタデータの出所保証が必要
第2段階: リアルタイム照会（Real-Time Query）DB直接照会、監視APIの稼働確認Tools（読み取り専用ツール）リスク中程度。クエリ負荷制限とセマンティックモデルによる制約が必須
第3段階: 書き込み（Write-Back）チケット起票、決済承認、DBレコード更新Tools（状態変更ツール）リスク最大。事前の実行条件検証と可逆性に基づく承認ゲートが不可欠

発注書（PO）の決済エラー対応シナリオを考えると、この3段階の統合が鮮明になります。ユーザーから障害報告を受けた際、理想的なエージェントはまずトラブルシューティング手順を検索し（第1段階: Resource）、決済サービスの稼働状況を監視APIでリアルタイム確認し（第2段階: Read Tool）、障害を確認した上でサポートチケットを自動起票します（第3段階: Write Tool）。この一連の流れが1つのパイプラインとして安全に実行されてこそ、真のエージェント業務自動化が実現します。

6.1 RAGの限界とリアルタイム照会・書き込み（Write-Back）作業のリスク

RAGにとどまっている限り、AIのミスは画面上の誤答で済みます。しかし書き込み操作を伴うエージェントが暴走すれば、データベースの破壊や意図しない金銭の送金といった取り返しのつかない実害を生みます。したがって、書き込み権限の付与はモデルの賢さに期待するのではなく、厳格な「段階的自律性（Staged Autonomy）」の階段を一段ずつ登る形で進めなければなりません。

自律性の運用は4つのモードに分類されます。第1はエージェントが助言のみを行い人間が実行する「シャドーモード」、第2はエージェントが作業を準備し人間の承認ボタンを待つ「監督モード」、第3は規定の範囲内のみで自律実行し例外を人間に通知する「ガードレール付き自律モード」、第4は事後のサンプリング検査のみを行う「完全自律モード」です。新入社員に初日から法人カードを持たせないのと同様、エージェントもシャドーモードで十分な精度実績を積んだ後にのみ上位モードへ昇格させるべきです。

6.2 MCPのアンチパターン：無分別な1対1 APIラップからの脱却と業務機能設計

ツールインターフェースを設計する際に最も陥りがちな過ちは、既存のREST APIエンドポイントをそのまま1対1でMCPツールに変換してしまうことです。その結果、`get_po_status`や`create_ticket_network`といった微細なツールが50個も乱立することになります。LLMは選択すべきツールの数が増えるほど選択精度が急激に低下するため、Thoughtworks技術レーダーはこの「安易なAPIからMCPへの変換（Naive API-to-MCP Conversion）」を明確なアンチパターン（HOLD）に指定しました。

推奨される設計は、50個の細切れAPIではなく、豊富な自然言語説明とパラメータ化された入力を持つ5〜10個の「業務機能（Capability）」へと集約することです。例えば、単一の`check_service_status`ツールにサービス名とリージョンを引数として渡す構成や、優先度と説明を受け取る汎用的な`create_support_ticket`ツールを用意します。LLMがツールを選ぶ最大の判断材料は説明文そのものであるため、説明の質こそが成功を左右します。

6.3 事前条件の検証と可逆性（Reversibility）に基づくアクセス制御

実行を伴う機能モデルには、2つの強固な防御壁が不可欠です。第1は「前提条件（Preconditions）」のリアルタイム検証です。返金を実行する前には、未返金の元決済が存在し、ユーザーの権限金額内であることを実行直前の本番データから検証しなければなりません。この際、規約PDFなどの非構造化文書から検索したテキストは判断の「参考材料（Informs）」に過ぎず、権限を付与する「ゲート（Gates）」にしてはなりません。文面による認証を排除することで、プロンプトインジェクションによる不正実行を防止できます。

第2は「可逆性（Reversibility）」に基づく承認設計です。多くの企業が取引金額の大小だけで承認基準を定めがちですが、自律運用の安全性を予測する真の指標は「その操作を取り消せるかどうか」です。5,000万円の社内振替仕訳の修正はミスが起きても帳簿上で戻せるためリスクは限定的ですが、外部口座への20万円の送金は一度実行すれば回収が困難です。不可逆な操作については、エージェントの自律レベルにかかわらず、必ず人間の明示的な承認を挟むルールを徹底すべきです。

  • アクセスの段階的開放: 読み取り専用リソースから開始し、検証されたツールへと慎重に拡大
  • 安易なAPIラッピングの禁止: エンドポイントを機械的に露出させず、5〜10個の充実した業務機能に集約
  • 文書検索と認可の分離: 検索されたテキストは参考情報にとどめ、実行可否は確定的な事前条件で判定
  • 実行直前の前提条件検査: アクションを起こす瞬間の本番システム状態を照合して実行妥当性を検証
  • 可逆性重視のガバナンス: 金額の多寡よりも「元の状態へ巻き戻せるか」を基準に人間承認を必須化
  • 段階的自律性（Staged Autonomy）: シャドーモードで運用実績とテスト結果を証明してから権限を拡大

韓国企業の実務のための導入戦略：プロダクトとしてのデータと優先順位

多くの企業においてエージェント導入が暗礁に乗り上げる根本原因は、技術的な仕組みの不足というよりも「データの所有権（Ownership）」が組織内で宙に浮いている点にあります。全社のデータ基盤は中央のデータエンジニアリング部門が管理していますが、そのデータが持つ業務上の真の意味は営業や財務、物流などの現場ドメイン部門にしか分かりません。中央部門はビジネスコードの変更に気づけず、現場部門は自らのテーブル変更がエージェントをクラッシュさせている事実に無自覚です。

この不全を打開するには、データを単なるシステムの副産物ではなく「製品（Data as a Product）」として扱うデータメッシュ（Data Mesh）の考え方が不可欠です。データ契約、セマンティックモデルの指標定義、エージェントが叩くツールの機能定義には、必ず明確なドメイン所有者（チームおよび担当者）が紐づけられていなければなりません。契約違反でデプロイが停止した際に対処する責任者や、指標の定義が対立した際に判断を下すオーナーが定まっていて初めて、アーキテクチャは形骸化せずに維持されます。

Thoughtworksの論考が示す依存関係は、完全に下からの積み上げ（ボトムアップ）です。信頼できないデータ基盤の上に文脈層を載せても崩壊し、文脈層のないままツール実行を解放すれば大事故につながります。一方で観測性（Observability）だけは後から追加することが極めて困難であるため、初日からすべてのワークフローの足元に埋め込まなければなりません。

企業のエンジニアリングチームが直ちに着手すべき優先順位は、以下の通り整理できます。

7.1 社内システム（ERP・CRM・DB）連携時に優先確認すべきチェックリスト

自律エージェントを基幹システムに接続する際は、まず価格や在庫、顧客請求といった最もビジネスリスクの高い少数のデータセットを特定し、厳格な鮮度SLAを定義することから始めます。バッチの遅延がエージェントの誤答に直結することを前提とし、基準外のデータをデッドレターキューへと自動隔離する回路を最優先で組み込みます。

7.2 ツール導入よりも重要な、データプロダクト（Data as a Product）としての所有権確立

新しいモデルやフレームワークの検証に時間を費やす前に、社内で最も解釈が分かれている重要指標を1つ選び、バージョン管理されたセマンティックモデルとしてコード化する合意形成を始めるべきです。業務定義の合意とコード化は技術というより組織の課題であり、この合意プロセスを通過した企業だけが、安全で実効性のあるAIエージェントの恩恵を享受できます。

  • 初日からの観測性組み込み: エージェントの本番稼働を待たず、プロトタイプ段階から思考スパンを計測
  • 最重要データの契約化: 全社への一括展開を避け、価格や在庫などリスクの高いドメインからデータ契約を適用
  • モデル選定より文脈定義: モデルを頻繁に入れ替えるよりも、指標をコード化するほうが精度向上に直結
  • 書き込み前の読み取り隔離: MCP Resourcesによる文書公開から始め、監査体制を検証した後にToolsを導入
  • データ製品の所有者特定: 各データ契約や指標定義を長期的に維持・改定する現場ドメイン責任者を任命
