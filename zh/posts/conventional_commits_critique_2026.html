约定式提交真的有用吗 - 提交信息规范批判 2026

Are Conventional Commits Actually Worth It - 在形式与价值之间

2026年6月7日 IT/技术

引言：在 feat: 前停顿的那一刻

代码写完，正要留下最后一条提交，手却停住了。「这算 feat 还是 fix？还是 refactor？scope 该写什么？」明明只是一行的改动，却要为提交信息的类型动一会儿脑筋。任何使用约定式提交（Conventional Commits）的团队，都至少经历过一次这样的场景。对某些人而言，这种「停顿」是良好纪律的证明；对另一些人而言，它是无谓形式主义的证明。

本文要正面回答一个在 2026 年仍争论不休的问题——「约定式提交，真的有用吗？」——但不预先站队。我们将从实务视角梳理：规范是什么、承诺了哪些好处、受到哪些批评、何时有用、何时过度。先用一句话给出结论：约定式提交本身既非好也非坏，它是只有当自动化流水线真正消费提交时，成本才会被回收的工具。

1. 什么是约定式提交 —— 规范的基本结构

先打好地基。约定式提交是一种把提交信息写成不仅人能读、机器也能读的固定格式的规范。它源自 Angular 项目的提交惯例，后被整理为独立规范，如今 v1.0.0 是事实上的标准。基本结构如下：

<type>[optional scope]: <description>

[optional body]

[optional footer(s)]

看几个真实例子就很直观：

feat(auth): 新增社交登录支持

fix(api): 修复 null 响应导致的崩溃

docs: 在 README 补充安装步骤

feat(parser)!: 将配置文件格式改为 YAML

BREAKING CHANGE: 现有的 JSON 配置文件将不再可用。

核心是开头的 type。它用一个词把「改了什么」分类，括号内的 scope 进一步缩小到哪个区域，冒号后的 description 说明内容。在 type 后加 ! 或在脚注写 BREAKING CHANGE:，就表示这是破坏兼容性的改动。

2. 提交类型的词汇 —— feat、fix 与其余

规范中含义被明确固定的 type 只有两个：feat（新增功能）与 fix（修复缺陷）。这两者之所以特殊，是因为它们与稍后要讲的语义化版本直接挂钩。其余 type 虽被广泛沿用，却并非规范明确定义的。

type 含义 版本影响
feat新功能MINOR 提升
fix缺陷修复PATCH 提升
docs仅文档变更无
refactor不改变行为的结构调整无
test新增或修改测试无
chore构建、工具等杂项无
BREAKING CHANGE破坏兼容性MAJOR 提升

这里出现了第一处摩擦。规范并不提供自己的 type「推荐清单」，而是让你参考 Angular 的定义。于是 chore 与 refactor 的边界、style 与 format 的区别等争论在每个团队不断重演。据相关讨论，这种模糊正是 GitHub issue 与 Stack Overflow 问题中频繁出现的困惑来源之一。

3. 设立初衷 —— 为何要造这样的规范

在批评规范之前，应当公平地看它想解决的问题。约定式提交出现的背景，是自由格式提交信息的混乱。一段被「改了」「asdf」「最终_真的最终」之类信息填满的历史，逼人逐条去读才知道改了什么，也让工具无从自动处理。

规范的真正目标，是把提交信息变成结构化数据。一旦提交成为机器可解析的格式，其下游的 changelog 生成、版本计算、发布说明、CI 判定就全部可自动化。也就是说，规范本身不是目的，而是被设计为面向自动化的输入格式。错过这一点，就容易误判规范的价值。

约定式提交的本质不是「漂亮的提交信息」，而是「机器可读的提交信息」。没有那台机器，便只剩下形式。

4. 承诺的好处 1 —— 自动 changelog

规范承诺的第一个具体好处是自动生成 changelog。由于提交 type 已结构化，工具可以遍历历史，把 feat 提交放进「新功能」段，把 fix 提交放进「缺陷修复」段，把破坏性变更放进独立而醒目的段落，全部自动完成。

每次发布都要手工整理变更清单的活儿就此消失，这绝非小好处。尤其对有外部用户的库而言，changelog 本身就是产品的一部分。手写容易遗漏或不准确，而从提交生成，则能无遗漏地反映「实际改了什么」。

5. 承诺的好处 2 —— 语义化版本的自动化

第二个好处最为强大，那就是语义化版本（SemVer）的自动化。语义化版本用 MAJOR.MINOR.PATCH 三位数字表达兼容性信息，而约定式提交恰好与这三位一一对应。

  • fix 提交 → PATCH 提升（例：1.2.3 → 1.2.4）
  • feat 提交 → MINOR 提升（例：1.2.3 → 1.3.0）
  • BREAKING CHANGE → MAJOR 提升（例：1.2.3 → 2.0.0）

得益于这种映射，工具只需分析上次发布以来的提交，就能在无人介入下计算出下一个版本。围绕「这次发布算次版本还是补丁」的情绪化、不一致的争论，被一条规则取代。版本号反映的是「改了什么」，而非任何人对它的感受。

6. 承诺的好处 3 —— semantic-release 与全自动发布

当 changelog 与版本号合流，整个发布就可自动化。代表性工具是 semantic-release，同类思路的 release-please 也广为使用。流程如下：

合并到 main
   │
   ▼
分析提交 (commit-analyzer)   → 统计 feat/fix/BREAKING
   │
   ▼
计算下一个版本               → 应用 SemVer 规则
   │
   ▼
生成 changelog + 打 git 标签 + 发布软件包
   │
   ▼
发布发行说明（全流程无人值守）

当一切理想运转，开发者只需按规范提交并合并到 main，选版本或按「发布」的手动步骤降为零。这是约定式提交拥护论的顶点。一项调查发现，相当一部分头部 NPM 库已采用该规范，表明自动化生态正运行在它之上。

7. 批判论点 1 —— 形式主义与重复信息

现在转到反面。最常见的批评是形式主义。像 feat: 或 fix: 这样的前缀真的增加了信息吗？批评者认为，在「fix: 修复登录时的崩溃」里，fix: 是赘语——只读后面的描述，谁都知道这是缺陷修复。也就是说，type 与描述重复了。

对 scope 的批评类似。feat(auth): 中的 auth scope 告诉你改了哪个区域，但这信息用 git log -- path/to/auth 早就能拿到。改动的文件路径即 scope，何必让人手工再写一遍呢？

好的提交信息应当解释「为什么改」，而非「改了什么」。然而，选 type 前缀所耗的精力，恰恰夺走了本应用在那个「为什么」上的精力。

进入 2026 年，Hacker News、Lobsters 等社区仍反复出现「约定式提交让人聚焦于错误的事情」的批评。核心担忧是：忙于填写格式，反而冷落了提交信息中最有价值的部分——变更的意图与上下文。

8. 批判论点 2 —— 不用自动化便是纯粹开销

第二个批评最为致命。约定式提交的全部好处，都建立在存在消费提交的自动化这一前提之上。若团队既不自动生成 changelog，也不用 semantic-release 提升版本，那么规范只留下格式成本，承诺的好处一个不剩。

现实中这类团队意外地多。他们用 commitlint 强制提交格式，却没有任何读取该格式去生成 changelog 或自动发布的流水线。此时开发者每次提交都付出选 type 的认知成本，换回的自动化收益却是零。这是该规范最常见的反模式。

遵守率数据也印证了这种张力。据一项研究，在未正式采用规范的项目里，2023 年仅约 10% 的提交遵循了规范。不强制，人们自然就会偏离；要保住格式，就只能用工具强制；而强制又制造摩擦——形成一个循环。

9. 批判论点 3 —— 分类的认知负担与模糊

第三是分类本身的负担。要用好规范，得把提交分进十来个类别，可现实中的改动并不会如此干净地切分。一个既修缺陷、又做了重构、还加了测试的提交，到底算 fix、refactor 还是 test？这种「缠绕提交（tangled commit）」与分类规则正面冲突。

学术研究也指向这一点。既有研究多集中在 feat、fix、其他的三分类上，而如何定义与应用更细粒度的类别，仍是尚未达成共识的空白。由于规范不固定 type 清单，同一改动在不同开发者那里常被选成不同的 type。为一致性而引入的规范，反而催生了关于「何谓一致性」的新争论，颇为吊诡。

10. 寻求平衡 —— 何时有用、何时过度

批评已听够，现在来找平衡点。核心问题不是「规范好不好」，而是「在我的项目里，自动化是否真的消费提交」。这一个标准就能决定大部分判断。

场景 约定式提交 原因
公开库 / 软件包强烈推荐changelog、版本号对用户直接重要
用 semantic-release 自动发布强烈推荐提交即发布输入，成本立刻回收
多人协作的大型仓库推荐一致历史与历史检索价值高
内部服务（与发布无关）可选有自动化则得益，无则模糊
个人 / 小型项目多半过度开销超过收益

简言之，规范的成本在「有机器读提交」时才被回收。若你发布库或自动化发布，规范几乎总是划算。反之，对于一个人用的仓库或没有发布概念的内部工具，规范容易沦为只增加待填空格的形式。这条技术采用判断的通用原则，与 选择无聊的技术 —— AI 时代的技术选型一文所讲的保守态度相通。

11. 替代方案 —— 没有规范也能写好提交

决定不用规范，并不意味着可以随便写提交信息。用良好提交信息的原则替代严格格式，能以零成本获得规范的大部分核心价值。久经验证的原则如下：

  • 标题简短、用祈使句：以「Add」「Fix」等祈使动词开头，控制在 50 字左右。避免过去式与现在式混用（「Added」「Fixes」）。
  • 正文写「为什么」而非「做了什么」：看代码 diff 就知道改了什么。提交信息真正要承载的，是这次改动为何必要、舍弃了哪些备选方案。
  • 一次提交一个逻辑变更：避免缠绕提交，分类的纠结便自然消失，回退与评审也更轻松。
  • 关联问题与上下文：附上相关问题编号或背景链接，让未来的读者能追溯决策的来龙去脉。

有趣的是，这些原则与约定式提交并不冲突。恰恰相反，即便使用规范，也要守住这些原则才能得到好历史。也就是说，规范对于好提交既非必要条件也非充分条件。守住格式的烂提交，与没有格式的优秀提交，都完全可能存在。

12. 实务采用指南 —— 五步渐进

那么实际该如何决策与采用？一上来就用 commitlint 强制整个团队，只会放大摩擦。建议走下面这条五步渐进之路。

  1. 先决定自动化：采用规范前，先回答「我们会自动生成 changelog 或自动发布吗」。若答案是否，规范可以暂缓。
  2. 把 type 最小化：若要采用，别把十种全用上，收窄到 feat、fix、chore、docs 即可，大部分分类模糊就此消失。
  3. 强制留到后面：不要一开始就用 commitlint 钩子拦截，先从共识与示例做起，待文化扎根后再加上工具。
  4. 真正接上工具：接入 semantic-release 或 release-please，让提交真正流向版本与 changelog，如此成本才被回收。
  5. 定期重新评估：若规范没接上自动化、只剩形式，别怕废弃它。工具是手段，不是目的。

这种渐进态度，是对开发工具普遍有效的原则。先理解工具隐藏设置与权衡再使用的姿态，与 Claude Code 隐藏设置完全解析所讲的思路相通。

13. 结论 + 三条可立即落地

对「约定式提交真的有用吗」的诚实回答是「视情况而定」，而区分这个「情况」的标准很清晰：是否存在消费提交的自动化。若自动 changelog、语义化版本、semantic-release 这样的流水线真的读取提交，规范会回报以一致性与自动化的巨大收益。反之，若没有这样的消费者，规范就成了形式主义批评精准命中的纯粹开销。

用三条可立即落地的建议收尾：

  1. 先问「我们会自动消费提交吗？」这一个问题的答案决定了是否采用规范的九成。没有自动化，「良好提交信息的原则」应优先于规范。
  2. 要采用，就把 type 最小化、强制留到后面。收窄到 feat、fix、chore、docs，工具强制等文化扎根后再加，能同时减少模糊与摩擦。
  3. 比起格式，写好「为什么」。无论用不用规范，提交信息最大的价值都是变更的意图与上下文。把挑 type 前缀的五秒，用在「为什么这么改」的一行上，是给未来同事更大的礼物。
