Weave Router 분석 - 프롬프트별 모델 자동 라우팅이 필요한 이유

Anthropic·OpenAI·Gemini를 하나의 엔드포인트로 묶는 드롭인 프록시가 멀티 LLM 시대에 던지는 질문

2026-07-10 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 왜 지금 '모델 라우터'가 화두인가

2026년 7월 현재, 실무에서 LLM을 하나만 쓰는 조직은 오히려 드물다. Claude로 코드를 짜다가 대량 요약은 더 싼 모델로 돌리고, 이미지 설명은 Gemini로, 반복적인 배치 작업은 오픈웨이트 모델로 보내는 식의 멀티 LLM 운용이 표준이 되어가고 있다. 문제는 이 배분이 대개 "이 기능은 이 모델"처럼 사람이 미리 정해둔 거친 규칙으로 이뤄진다는 점이다. 프롬프트 하나하나의 난이도나 성격에 맞춰 실시간으로 모델을 바꾸는 조직은 아직 소수다. GeekNews(hada)에 올라온 Weave Router는 바로 이 지점, 즉 프롬프트 단위 모델 배분을 자동화하겠다고 나선 프로젝트다. Anthropic·OpenAI·Gemini API를 하나의 엔드포인트로 묶고, 들어오는 프롬프트마다 어떤 모델로 보낼지 자동으로 고른다고 주장한다. 이 글은 Weave Router의 기능을 그대로 소개하는 대신, "왜 지금 모델 라우팅이 필요한가"라는 더 큰 질문을 필자 관점에서 풀어보고, 유사 도구들과 비교해 실무 도입 시 무엇을 따져야 하는지 정리한다.

1. Weave Router란 무엇인가

Weave Router는 workweave 팀이 공개한, 에이전트 시스템을 위한 모델 라우터다. 저장소 설명에 따르면 Claude Code·Codex·Cursor 같은 도구의 API Base URL만 라우터 주소로 바꾸면 적용되는 드롭인 프록시 형태로 동작한다.

1.1 드롭인 프록시로서의 동작 방식

라우팅은 무작위나 단순 규칙이 아니라, 작은 온박스 임베딩 모델로 프롬프트를 벡터화한 뒤 사전에 정의된 "의도 클러스터"와 매칭해, 그 클러스터에서 과거에 프론티어 모델과 동등한 성능을 낸 것으로 확인된 가장 저렴한 후보 모델로 보내는 방식이라고 설명한다. 이 스코어러는 "AvengersPro" 계열 연구를 기반으로 실제 트래픽에 재학습했다고 밝히고 있다. DeepSeek·Kimi·GLM·Qwen·Llama·Mistral 같은 모델도 OpenRouter 호환 엔드포인트를 통해 라우팅 대상에 넣을 수 있다.

1.2 배포 형태와 라이선스

배포는 두 갈래다. 자체 인프라(Docker+PostgreSQL)에 셀프호스팅하거나, 매니지드 서비스에 프로바이더 키를 등록해 짧은 시간 안에 라우팅을 시작할 수 있다. 프로바이더 키는 사용자 인프라를 벗어나지 않는 BYOK(Bring Your Own Key) 구조이고, OTLP 트레이스로 Honeycomb·Datadog·Grafana 같은 관측 도구에 바로 연동된다고 설명한다. 다만 한 가지는 분명히 짚어야 한다. 라이선스는 Elastic License v2(ELv2)로, 소스코드는 공개돼 있지만 OSI가 승인한 전통적 의미의 오픈소스는 아니다. 이 라우터를 그대로 상용 매니지드 서비스로 재판매하는 것을 제한하는 조항이 포함된 소스공개(source-available) 라이선스에 가깝다. "오픈소스"라는 표현을 액면 그대로 받아들이기보다, 이 구분을 인지하고 접근하는 편이 안전하다.

2. 왜 지금 '모델 라우팅'이 필요한가 - 멀티 LLM 시대의 세 가지 비대칭

멀티 LLM을 실무에 들이면 곧바로 세 가지 비대칭과 마주친다. 첫째는 강점의 비대칭이다. 같은 세대 모델이라도 코딩, 장문 요약, 비전, 다국어 처리에서 강한 영역이 서로 다르다. 둘째는 비용의 비대칭이다. 토큰당 단가는 모델 간 수 배에서 수십 배까지 벌어지고, 같은 질문이라도 어떤 모델로 보내느냐에 따라 품질 대비 비용이 크게 갈린다. 셋째는 속도의 비대칭이다. 실시간 에이전트 루프에서는 무거운 추론 모델의 지연이 사용자 경험을 그대로 갉아먹는다. 이 세 비대칭을 사람이 매번 판단해 수동으로 배분하는 방식은 애초에 확장 가능하지 않다. 게다가 하나의 벤더 API에 코드베이스를 깊이 결합하면, 그 벤더가 가격을 올리거나 장애를 겪을 때 대안이 없는 벤더 락인에 빠진다. 모델 라우터가 이 결합을 걷어내면, 벤더 간 가격 경쟁이나 신모델 출시의 이득을 코드 변경 없이 흡수할 수 있다는 것이 라우팅 옹호론의 핵심이다. 이는 Weave Router만의 독자적 주장이 아니라, 2024년 UC버클리 LMSYS가 발표한 RouteLLM 연구가 학술적으로 뒷받침해 온 방향이기도 하다. 해당 연구는 강한 모델과 약한 모델 중 하나로 프롬프트를 분류해 보내는 이진 라우터로, MT-Bench 기준 GPT-4 성능의 상당 부분을 훨씬 적은 고비용 모델 호출만으로 달성할 수 있음을 보고한 바 있다.

3. 프롬프트별 최적 모델 자동선택의 원리와 가치

Weave Router가 서 있는 자리는 이 라우팅 연구의 실무 적용 지점이다. 원리를 필자 나름으로 풀면 이렇다. 프롬프트를 그대로 여러 모델에 동시에 보내 비교하는 방식은 호출 수만큼 비용이 배가된다. 그래서 실용적인 라우터는 프롬프트를 저차원 임베딩으로 변환한 뒤, 이 임베딩이 어떤 의도 군집에 속하는지 분류기로 판별하고, 그 군집에서 사전에 벤치마킹해둔 "가장 저렴하면서 품질이 동등한" 모델로 보낸다. 이 접근의 가치는 명확하다. 매 프롬프트마다 사람이 모델을 고르지 않아도 되고, 인사말이나 단순 요약 같은 저난도 프롬프트는 저가 모델로, 복잡한 추론이 필요한 프롬프트는 고성능 모델로 자동 분산되면서 평균 비용이 떨어진다. Weave Router는 이 절감폭을 40~70%라고 홍보하는데, 이는 제작자 주장이며 독립 벤치마크가 공개되지 않은 만큼 각자의 워크로드에서 직접 검증이 필요하다. 마찬가지로 "50ms 이내 라우팅 판단"이라는 지연 수치도 제작자 측 주장으로 읽는 것이 안전하다. 이 원리 자체는 새롭지 않다. RouteLLM이 학술적으로, vLLM 진영의 시맨틱 라우터 프로젝트가 추론 여부를 나누는 방식으로 이미 검증해 온 아이디어를, Weave Router는 세 개 주요 프로바이더 API 호환과 에이전트 코딩 도구 통합이라는 실무 포장으로 제품화한 사례에 가깝다.

4. 드롭인 프록시 방식의 장점 - 코드 최소 변경

이 방식의 가장 큰 실무적 장점은 통합 비용이 거의 0에 가깝다는 점이다. Claude Code나 Cursor의 API Base URL 한 줄만 로컬 라우터 주소로 바꾸면, 애플리케이션 코드를 한 줄도 고치지 않고 라우팅 계층이 끼어든다. 자체적으로 LiteLLM 같은 게이트웨이를 구축하려면 라우팅 로직·프로바이더 어댑터·관측성을 직접 설계해야 하지만, 드롭인 프록시는 이미 통합된 바이너리로 이 전부를 제공한다. 여러 벤더의 SDK 차이(Anthropic Messages, OpenAI Chat Completions, Gemini native)를 흡수해 클라이언트는 하나의 스펙만 알면 된다는 점도 부수적 이득이다. 실험적으로 라우터를 붙였다 떼는 전환도 설정값 하나로 가능해, PoC 단계의 위험 부담이 낮다.

5. 드롭인 프록시 방식의 한계 - 정확도·지연·프라이버시·캐싱

그러나 장점만큼 한계도 뚜렷하다. 첫째는 라우팅 정확도다. 임베딩 기반 의도 분류는 학습 분포 밖의 프롬프트, 특히 도메인 특수 용어나 긴 대화 맥락이 섞인 프롬프트에서 오분류 위험이 있다. 오분류가 나면 저가 모델로 잘못 보내 품질이 떨어지거나, 반대로 고가 모델로 과도하게 보내 절감 효과가 사라진다. 둘째는 지연이다. 라우팅 판단 자체가 임베딩 계산과 프록시 홉을 하나 더 추가하므로, 라우팅 지연 수치를 그대로 믿더라도 그 위에 실제 모델 응답 지연이 얹힌다. 특히 스트리밍 응답의 첫 토큰 도달 시간에 민감한 애플리케이션이라면 이 오버헤드가 누적될 수 있다. 셋째는 프라이버시다. BYOK로 프로바이더 키가 외부로 나가지 않는다고 해도, 프록시 자체가 모든 프롬프트 내용을 관측하는 위치에 있다는 사실은 변하지 않는다. 관측성 스택으로 트레이스를 내보내면 프롬프트 원문이나 요약이 제3자 서비스에 적재될 수 있어, 규제 산업이라면 별도 검토가 필요하다. 넷째는 실제 커뮤니티 논의에서도 지적된 문제로, 프로바이더 네이티브 프롬프트 캐싱과의 충돌이다. Anthropic과 OpenAI 모두 반복되는 시스템 프롬프트나 컨텍스트를 캐싱해 캐시 적중 시 입력 토큰 단가를 큰 폭으로 낮추는 기능을 제공하는 것으로 알려져 있는데, 프록시가 요청을 여러 모델·여러 세션으로 분산하거나 캐시 프리픽스를 조금이라도 바꾸면 캐시 적중률이 떨어져, 라우팅으로 아낀 비용을 캐싱 이득 상실로 상쇄하거나 오히려 역전시킬 수 있다는 지적이다. 이 트레이드오프는 도입 전에 반드시 자신의 트래픽 패턴으로 계산해봐야 한다.

6. 유사 접근과의 비교 - OpenRouter·LiteLLM·RouteLLM

모델 라우팅 생태계는 이미 여러 층으로 나뉘어 있다. OpenRouter는 매니지드 애그리게이터다. 60여 개 프로바이더의 수백 개 모델을 단일 API로 노출하지만, 라우팅 결정은 기본적으로 사용자가 모델을 직접 지정하거나 단순 우선순위·폴백 규칙을 설정하는 방식이라 Weave Router식 프롬프트별 자동 분류와는 결이 다르다. LiteLLM은 셀프호스팅 오픈소스 프록시로, 가중치 기반·지연 기반·최저비용 기반 등 여러 라우팅 전략을 제공하고 커스텀 코드까지 꽂을 수 있어 유연하지만, "이 프롬프트에 가장 적합한 모델"을 자동 학습해 고르는 지능형 분류기는 기본 제공되지 않는다. RouteLLM은 반대로 학술 프레임워크에 가깝다. 강한 모델과 약한 모델 이진 분류라는 단순한 축으로 비용 절감을 증명했지만, 프로덕션 배포·관측성·다중 프로바이더 어댑터 같은 실무 편의는 갖추지 않은 연구 코드에 가깝다. Weave Router는 이 세 층의 중간 지점을 노린다. LiteLLM의 프록시 편의성과 RouteLLM류의 학습된 분류기 아이디어를 결합하되, OpenRouter처럼 여러 프로바이더를 한 엔드포인트로 노출한다. 다만 "지능형 자동 라우팅"을 내세우는 만큼 검증 부담도 가장 크다. 규칙 기반 라우팅(LiteLLM)은 예측 가능하지만 손이 많이 가고, 학습된 라우팅(Weave Router·RouteLLM류)은 편하지만 블랙박스라 오분류를 사람이 바로 알아채기 어렵다는 트레이드오프를 이해하고 골라야 한다.

7. 실무 도입 시 고려사항

도입을 검토한다면 다음 순서를 권한다. 먼저 저위험 워크로드(내부 도구, 배치 요약 등)에 셀프호스팅으로 먼저 붙여보고, 라우팅 결정만 미리 보여주는 엔드포인트로 실제 어떤 모델로 보내지는지 프롬프트 샘플을 돌려 확인한다. 다음으로 자신의 실제 프롬프트 50~100개로 골든셋을 만들어, 라우터를 거친 답변과 항상 최상위 모델로 보낸 답변을 나란히 비교해 품질 손실이 감내 가능한 수준인지 측정한다. 이때 캐싱을 많이 쓰는 워크로드라면 캐시 적중률 변화를 비용 계산에 반드시 포함해야 한다. 관측성 스택에 프롬프트 원문이 그대로 적재되지 않도록 트레이스 마스킹 옵션을 확인하는 것도 필수다. 마지막으로, 고객 응대나 보안 패치처럼 실패 비용이 큰 워크로드는 라우팅 대상에서 제외하고 검증된 단일 모델에 고정하는 이원화 전략이 안전하다. Elastic License v2라는 라이선스 특성상, 이 라우터 자체를 상용 매니지드 서비스로 재판매할 계획이 있다면 라이선스 조항을 법무 검토 없이 넘기지 않아야 한다.

결론: 라우팅은 설치가 아니라 계측이다

멀티 LLM 시대에 모델 라우팅은 사치가 아니라 비용·속도·벤더 리스크를 관리하는 실무 인프라로 자리 잡고 있다. Weave Router는 그 흐름을 드롭인 프록시라는 가장 마찰이 적은 형태로 제품화한 사례이고, 학습된 분류기 기반 자동 라우팅이라는 방향성 자체는 RouteLLM 같은 연구로 뒷받침된다. 그러나 비용 절감폭이나 라우팅 지연 같은 구체적 수치는 어디까지나 제작자 주장이며, 실제 이득은 프롬프트 분포·캐싱 패턴·워크로드 위험도에 따라 크게 갈린다. 2026년 7월 기준 필자의 결론은, 라우팅을 "설치하면 끝"이 아니라 "계측하고 검증해야 하는 새로운 인프라 계층"으로 다뤄야 한다는 것이다. 저위험 워크로드부터 골든셋으로 검증하며 서서히 범위를 넓히는 것이 정답에 가깝다.
