LLM에게 차트를 그리게 하면 어디가 어긋나는가 - 의미 기반 시각화 사양의 값과 대가

축 타입 오판, 정수 날짜, 색상 남용, 그리고 「이 부분만」이 안 먹히는 사양

2026-08-03 IT/기술

서론: 「이 막대 색만 바꿔줘」가 차트를 통째로 갈아엎는다

모델에게 한 줄을 던진다. 「막대 색만 파랑 계열로 바꿔줘.」 돌아온 차트는 색이 바뀌어 있다. 그런데 어제 손으로 맞춰 둔 캔버스 폭이 원래대로 돌아가 있고, 축 눈금 간격이 달라져 라벨 몇 개가 겹친다. 고친 것 하나를 얻고 알아채지 못한 회귀 세 개를 받은 셈이다.

이게 운이 나빠서 생긴 일이 아니라는 게 이 글의 출발점이다. 어긋나는 자리는 놀랄 만큼 정해져 있다. 축을 연속형으로 볼지 범주형으로 볼지에서 한 번, 날짜처럼 생긴 정수를 어떻게 읽을지에서 한 번, 색을 몇 개까지 쓸지에서 한 번, 그리고 「이 부분만」이라는 지시가 사양의 어느 줄에 걸리는지에서 다시 한 번.

이 넷은 모델의 지능이 부족해서 생기는 문제가 아니다. 모델이 채워야 하는 칸이 너무 많고, 그 칸들이 서로 얽혀 있기 때문에 생긴다. Vega-Lite로 잘 만든 차트 하나에는 스케일 정의역, 시간 단위, 마크 폭, 캔버스 폭, 라벨 각도, 색 배합, 범례 위치가 전부 손으로 정해져 들어간다. 그중 하나를 바꾸면 나머지 여섯이 어긋난다. 사람이 만들어도 어긋나는데, 매번 처음부터 다시 쓰는 모델에게는 더 심하게 어긋난다.

2026년 7월 마이크로소프트 리서치가 Flint라는 물건을 공개했다. 필드가 무엇을 뜻하는지만 선언하면 파싱·축·서식·색상·레이아웃을 컴파일러가 끌어내는 중간 언어다. 이 글은 Flint를 소개하는 데 목적이 있는 게 아니라, Flint가 풀려는 문제가 실제로 무엇이고 그 방식이 무엇을 포기하는지를 보는 데 있다. 도구는 바뀌어도 이 문제는 남는다.

결론부터 적는다. 의미 기반 사양이 확실하게 주는 것은 「예쁜 차트」가 아니라 「짧고 고칠 수 있는 차트 정의」다. 품질 개선은 측정됐지만 폭이 작고, 흥미롭게도 모델이 강해질수록 그 이득이 줄어든다. 그런데 사양 길이가 짧아지는 효과는 모델과 무관하게 남는다. 도입 판단은 여기서 갈린다.

1. 어긋나는 자리는 정해져 있다 - 다섯 가지 고장

LLM에 차트를 맡겨 본 사람이면 아래 목록이 낯설지 않을 것이다. 이 다섯은 문법이 Vega-Lite든 ECharts든 Matplotlib이든 거의 같은 모양으로 반복된다.

고장사양의 어디서 생기나화면에는 어떻게 나타나나사람이 알아채는가
축 타입 오판정량·서수·명목 중 잘못된 스케일 선택연속량이 막대 스무 개로 흩어지거나, 범주가 선으로 이어짐보통 알아챈다
시간 파싱 실패정수·문자열 날짜를 그대로 시간축에 태움1970년대 어딘가로 날아가거나 순서가 뒤섞임알아채기 어렵다
비가산 값 누적비율·평균·순위를 스택 막대로 쌓음합계가 100퍼센트를 넘거나 의미 없는 높이가 생김거의 못 알아챈다
색상 오용·남용발산형 필드에 순차형 색, 범주 20개에 무지개0이 중간이 아닌 색으로 찍히고, 범례가 화면을 먹음남용은 보이고 오용은 잘 안 보인다
수정 지시 오적중한 요구가 여러 속성에 흩어져 있음고쳐 달라던 것 말고 다른 값이 바뀜바로 보이지만 원인은 안 보인다

여기서 세 번째와 네 번째가 특히 나쁘다. 결과물이 멀쩡해 보이기 때문이다. 축이 깨진 차트는 다시 그리면 되지만, 비율을 쌓아 올린 막대는 회의 자료로 그대로 나간다. 시각화의 값은 예쁨이 아니라 이상을 알아채는 데 걸리는 시간에서 나오는데, 이 두 고장은 그 시간을 무한대로 만든다. 무엇을 봐야 이상이 보이는가라는 질문 자체는 데이터베이스 관측 도구를 두고 따로 다룬 적이 있다.

다섯 번째는 성격이 다르다. 앞의 넷이 한 번 만들 때의 문제라면, 이건 고칠 때의 문제다. 그리고 LLM 워크플로에서는 차트를 한 번에 완성하는 일이 거의 없다. 대화는 언제나 「좋은데 이것만」으로 이어진다.

2. 202001이라는 컬럼 하나가 만드는 세 갈래

추상적으로 말하면 감이 안 오니 구체적인 자리를 하나 잡자. Flint 논문이 예시로 쓴 것과 같은 상황인데, 한국 사내 데이터 웨어하우스에서는 거의 매일 마주치는 형태다. 월별 지표 테이블의 기간 컬럼이 202001, 202002처럼 여섯 자리 정수로 들어 있다.

사람은 이걸 보자마자 2020년 1월이라고 읽는다. 모델도 그렇게 읽는다. 문제는 모델이 읽은 것을 사양에 옮기는 순간 세 갈래로 갈린다는 데 있다.

모델의 선택사양에 쓰이는 것결과왜 이렇게 되나
그냥 시간축으로필드 타입을 시간형으로 지정연도가 붕괴하거나 축이 뒤엉킴202001을 유닉스 초나 연도 값으로 해석
범주형으로 회피필드 타입을 명목형으로 지정72개 칸이 생겨 라벨이 서로 겹침6년치면 72개월이고, 각 월이 독립 범주가 된다
손으로 파싱변환식 + 시간 단위 + 마크 폭 + 캔버스 폭 + 라벨 각도제대로 나온다다섯 값이 서로 맞아야 성립한다

세 번째가 정답인데, 정답의 모양이 문제다. Vega-Lite에서 이걸 제대로 쓰면 대략 이렇게 된다.

{
  "transform": [
    { "calculate": "datetime(floor(datum.Period/100), datum.Period%100-1)",
      "as": "PeriodDate" }
  ],
  "mark": { "type": "bar", "width": { "band": 0.9 } },
  "encoding": {
    "x": {
      "field": "PeriodDate", "type": "temporal", "timeUnit": "yearmonth",
      "axis": { "format": "%Y-%m", "labelAngle": -45, "labelOverlap": "greedy" }
    },
    "y": { "field": "Users", "type": "quantitative", "aggregate": "sum",
           "scale": { "zero": true } }
  },
  "width": 504
}

이 조각에서 모델이 틀릴 수 있는 자리를 세어 보자. 나눗셈과 나머지의 조합, 월 인덱스가 0부터인지 1부터인지, 시간 단위 문자열, 서식 문자열, 라벨 각도, 겹침 회피 전략, 밴드 폭 비율, 캔버스 폭. 여덟 개다. 그리고 이 중 상당수는 서로 의존한다. 캔버스 폭을 720으로 늘리면 라벨 각도를 0으로 되돌려도 되고, 밴드 폭도 다시 봐야 한다.

여기서 핵심은 이것이다. 모델은 「2020년 1월이다」라는 것을 이미 안다. 아는 것을 저수준 파라미터 여덟 개로 번역하는 과정에서 어긋난다. 그러면 번역을 시키지 말고 아는 것을 그대로 쓰게 하면 되지 않나 — 이게 의미 기반 사양의 발상이다.

3. 짧게 쓰면 못생기고, 길게 쓰면 부서진다

시각화 문법에는 오래된 딜레마가 하나 있다. Flint 논문과 공식 블로그가 문제 제기의 출발점으로 삼은 것도 정확히 이 지점이다.

  • 짧은 사양은 시스템 기본값에 기댄다. 세 줄이면 차트가 나오지만 축 서식은 밋밋하고, 라벨은 겹치고, 색은 라이브러리 기본 팔레트 그대로다.
  • 긴 사양은 원하는 결과를 준다. 대신 장황하고, 부서지기 쉽고, 사람이 열어서 무엇을 왜 그렇게 했는지 읽어내기 어렵다.
  • 사람은 이 둘 사이를 반복 수정으로 오간다. 그려 보고, 안 맞으면 한 줄 고치고, 다시 본다.
  • 모델은 그 반복이 어렵다. 매번 전체를 다시 생성하니까 수렴하지 않고 진동한다.

여기에 하나가 더 붙는다. 긴 사양은 토큰을 먹는다. 차트 하나에 60줄짜리 JSON을 매번 통째로 다시 쓰는 파이프라인은 대화가 길어질수록 비용이 선형으로 는다. 그리고 그렇게 다시 쓴 60줄 중 실제로 바뀌는 것은 한 줄이다.

구조를 압축해 모델에 넘기면 무엇이 달라지는지는 코드 쪽에서 먼저 검증된 논점이다. 코드베이스를 질의 가능한 그래프로 바꾸는 접근이 노린 것도 결국 같다. 모델에게 전부를 던지지 말고, 모델이 판단해야 할 것만 남긴 표현을 주는 것.

4. 의미 타입이 대신 정하는 것 - 3단 계층

Flint의 사양은 두 덩어리로 나뉜다. 필드가 무엇인지를 선언하는 부분과 어떤 차트를 어떤 채널에 그릴지를 선언하는 부분이다. 저장소 문서가 보여 주는 최소 형태는 이렇다.

import { assembleVegaLite } from 'flint-chart';

const spec = assembleVegaLite({
  data: { values: myData },
  semantic_types: { weight: 'Quantity', mpg: 'Quantity', origin: 'Country' },
  chart_spec: {
    chartType: 'Scatter Plot',
    encodings: { x: { field: 'weight' }, y: { field: 'mpg' },
                 color: { field: 'origin' } },
    baseSize: { width: 400, height: 300 },
  },
});

origin이 Country라는 한 마디로 여러 결정이 따라온다. 범주형이고, 순서가 없고, 개수가 제한적이며, 색으로 구분하는 편이 자연스럽고, 범례에 이름을 그대로 써야 하고, 순차형 색 램프를 쓰면 안 된다. 저수준 설정 여섯 개를 대신하는 단어 하나다.

이 타입 체계는 평평하지 않고 3단 계층이다. 논문이 밝힌 구조는 다음과 같다.

층위무엇을 결정하나개수예
1단계 · 영역파싱 전략. 값을 애초에 무엇으로 읽을 것인가6시간형, 범주형, 측정값, 이산값, 식별자, 지리
2단계 · 계열집계 가능 여부, 0의 의미, 정의역 구조15날짜시각, 기간, 개체, 구간, 총량, 비율, 등급, 순위, 좌표
3단계 · 타입표현. 서식, 정렬, 기본 색 계열44연월, 월, 백분율, 매출, 이익, 위도, 상태, 방향

계층이 중요한 이유는 상속 때문이다. 새 타입을 하나 추가할 때 파싱과 집계 규칙을 처음부터 정의하지 않고 부모의 행동을 물려받은 뒤 표현만 좁히면 된다. 사내 지표 사전이 있는 조직이라면 이 구조가 매핑하기 좋다는 뜻이기도 하다.

숫자가 두 개인 이유. 저장소 문서는 의미 타입이 70종 이상이라고 적고, 논문은 3단계 44종이라고 적는다. 세는 층위가 다르다. 계열과 별칭까지 합치면 앞의 숫자가 되고, 최말단 타입만 세면 뒤의 숫자가 된다. 인용할 때 어느 쪽 기준인지 붙이지 않으면 서로 어긋난 것처럼 보인다.

2단계가 실무에서 가장 값이 나가는 층이다. 총량과 비율을 구분한다는 것은 곧 스택 막대를 허용할지 말지가 타입 단계에서 결정된다는 뜻이다. 앞서 「거의 못 알아챈다」로 표시한 비가산 값 누적 고장이 여기서 구조적으로 막힌다. 사람 리뷰가 잡아야 했던 것을 타입이 잡는 것이다.

5. 컴파일러가 하는 일 - 세 단계

선언에서 실제 차트 사양까지는 세 단계를 거친다. 이 구조를 알아 두면 결과가 마음에 안 들 때 어느 단계를 의심할지가 정해진다.

  1. 의미 해석. 의미 타입과 원본 데이터를 함께 보고 필드의 성질을 확정한다. 파싱 방식, 스케일 종류, 서식, 집계 함수가 여기서 나온다.
  2. 최적화. 제약 기반으로 레이아웃을 푼다. 축 길이, 항목 간격, 여백, 패싯 배치가 데이터 카디널리티와 캔버스 한계를 함께 보고 결정된다.
  3. 코드 생성. 라이브러리에 독립적인 속성 집합을 백엔드별 템플릿으로 찍어낸다. Vega-Lite, ECharts, Chart.js, Plotly, 그리고 Office.js를 통한 Excel 네이티브 차트.

2단계가 이 설계에서 가장 덜 알려진 부분이다. 논문은 각 축과 그룹과 패싯 패널을 「압축 가능한 용기」로 놓고 선호 크기와 최소 가독 크기를 둔 뒤, 이산 축은 항목을 늘리거나 줄여 제약을 만족시키고 연속 축은 캔버스를 늘려 겹침을 줄이는 식으로 푼다고 적는다. 전역 단계에서는 종횡비를 기울기 45도 기준으로 맞추고 패싯 줄바꿈 균형을 조정한다.

여기가 중요하다. 72개월짜리 축이 겹치지 않는 이유는 모델이 캔버스 폭 504픽셀을 잘 골라서가 아니라, 옵티마이저가 최소 가독 폭에서 역산했기 때문이다. 모델은 그 숫자를 몰라도 된다. 반대로 말하면 그 숫자를 우리가 정하고 싶을 때 어떻게 개입하는가가 다음 절의 주제가 된다.

백엔드가 여럿이라는 점도 실무에서 생각보다 크다. 같은 사양이 웹에서는 ECharts로, 보고서 납품에서는 Excel 네이티브 차트로 나간다는 것은 「스크린샷을 붙여 드릴까요, 원본 파일로 드릴까요」라는 매번의 실랑이가 없어진다는 뜻이다. Excel 쪽은 이미지가 아니라 편집 가능한 네이티브 차트로 만들어진다.

6. 부분 수정이 되는 사양 - 여기가 진짜 갈림길이다

이 글의 핵심 주장이다. LLM 워크플로에서 사양 설계의 값은 「처음 생성 품질」이 아니라 「두 번째 지시가 어디에 떨어지는가」에서 나온다.

이유는 단순하다. 차트를 한 번에 완성하는 대화는 없다. 실제 대화는 이렇게 흐른다.

  • 「이거 월별로 바꿔줘」 — 시간 단위 변경
  • 「y축을 0부터 시작하게」 — 스케일 기준값
  • 「범례를 아래로」 — 배치
  • 「이 지역만 강조」 — 색 채널 조건
  • 「가로로 눕혀줘」 — 채널 교환

저수준 문법에서 이 다섯 개는 각각 사양의 서로 다른 두세 군데를 동시에 건드린다. 「y축을 0부터」 하나만 해도 스케일 정의역과 축 눈금 설정과 경우에 따라 캔버스 높이가 함께 움직인다. 모델은 이걸 부분 편집으로 처리하지 못하고 전체를 다시 쓴다. 다시 쓰면 이전 네 번의 수정이 확률적으로 유실된다.

구분사용자·모델이 직접 쓰는 것컴파일러가 정하는 것
필드의미 타입, 고정 값 범위, 기준값파싱 규칙, 스케일 종류, 서식, 정렬
차트차트 종류, 채널 바인딩, 집계 함수마크 속성, 축 눈금, 범례 구성
레이아웃기준 크기축 길이, 간격, 여백, 패싯 배치, 종횡비
색(의미 타입을 통해 간접적으로)색 계열, 정의역 대응, 중립값 위치

왼쪽 열이 곧 수정 표면적이다. 표면적이 작으면 「이것만 바꿔」가 한 줄에 떨어지고, 나머지는 그대로 남는다. 논문이 제시한 사양 길이가 백엔드 네이티브 코드 대비 평균 85퍼센트 짧다는 결과는 단순한 절약 이야기가 아니라 이 표면적의 크기를 재는 숫자다.

다만 덜어낸 만큼 잃는 것도 정확히 그 자리에서 생긴다. 오른쪽 열은 우리가 못 만지는 열이라는 뜻이기도 하다.

7. 제어권을 넘긴 대가

자동 결정은 공짜가 아니다. 실무에서 부딪히는 대가는 세 가지 모양으로 온다.

7.1 기본값이 의도와 다를 때

컴파일러가 「이 필드는 비율이니 0부터 100까지」라고 판단했는데, 실제로는 92에서 98 사이 미세한 차이를 보여야 하는 상황이 있다. 이런 요구는 잘못된 게 아니라 맥락에서 나온다. 사양 스키마에는 인코딩 수준의 재정의 항목이 있고 값 범위와 기준값을 직접 지정하는 선택 항목도 있지만, 재정의가 어디까지 열려 있는지는 문서가 얇다. 여기서 막히면 컴파일 결과를 뽑아 손으로 고치는 쪽으로 빠져야 하는데, 그 순간 부분 수정의 이점은 사라진다.

7.2 표현이 곧 요건일 때

디자인 시스템이 색 코드와 폰트 크기와 그리드 간격을 명세로 못 박은 조직에서는 자동 결정 자체가 위반이다. 「보기 좋게 알아서」가 값이 아니라 비용이 되는 자리다. 이런 팀은 저수준 문법을 계속 쓰는 게 맞다. 폰트 축을 데이터에 직접 물리는 가변 폰트 기반 시각화 실험처럼 표현 자체가 주제인 작업도 같은 쪽이다.

7.3 타입 추론이 틀릴 때

이 설계 전체가 「필드에 올바른 의미 타입이 붙는다」는 전제 위에 서 있다. 그런데 그 타입을 붙이는 것도 결국 모델이다. score라는 컬럼이 등급인지 점수인지 순위인지는 컬럼명만으로 안 갈린다. 잘못 붙으면 고장이 사라지는 게 아니라 한 단계 위로 이동할 뿐이다.

다만 이동 자체에 값이 있다. 저수준 파라미터 여덟 개가 어긋난 상태는 원인을 짚기 어렵지만, 「이 컬럼 타입이 틀렸다」는 한 줄로 특정되고 한 줄로 고쳐진다. 실패의 개수를 줄이는 게 아니라 실패를 진단 가능한 형태로 모으는 것 — 이게 중간 언어 설계가 실제로 파는 물건이다.

논문 스스로도 한 필드가 하나의 의미 타입에 대응한다고 가정하며, 모호한 필드에는 이 가정이 부족하다고 적는다.

8. 숫자를 어떻게 읽나 - 승률 41~45퍼센트의 의미

평가 결과가 공개돼 있다. 그대로 옮기면 이렇다. TidyTuesday 2025 데이터셋 63개 표(행 수 중앙값 952, 열 8개)에서 질의 생성 에이전트가 315개 질의를 만들고, Flint 경로와 백엔드 직접 생성 경로가 각각 차트를 만든 뒤, 시각 언어 모델이 렌더된 이미지를 채점했다. 채점 항목은 관련성·차트 오류·명료성·디자인 품질 네 가지에 각 5점, 합계 20점이다.

모델Flint 승무승부직접 생성 승유의확률평균 점수 (20점 만점)
GPT-5.1129 (41%)65 (21%)118 (38%)0.0516.27 대 15.91
GPT-5-mini140 (45%)65 (21%)106 (34%)0.00116.16 대 15.60
GPT-4.1135 (43%)70 (23%)106 (34%)0.00415.91 대 15.34

이 표를 어떻게 읽을지가 도입 판단을 가른다. 세 가지를 짚는다.

  • 차이는 있지만 작다. 평균 점수 차는 20점 만점에서 0.36에서 0.57점이다. 백분율로는 2에서 4퍼센트대다. 「차트 품질이 도약한다」는 표현은 이 숫자가 뒷받침하지 않는다.
  • 강한 모델일수록 격차가 줄어든다. GPT-5.1에서 유의확률이 0.05로 가장 약하고 승패 차이도 129 대 118로 가장 좁다. 반면 GPT-5-mini와 GPT-4.1에서는 0.001과 0.004로 뚜렷하다. 모델이 좋아질수록 중간 언어의 품질 이득은 줄어든다고 읽는 게 자연스럽다.
  • 가장 견고한 숫자는 품질이 아니라 길이다. 85퍼센트 짧다는 결과는 모델 성능과 무관하게 성립하고, 토큰 비용과 부분 수정 가능성으로 곧장 이어진다.

그래서 이 도구를 「더 예쁜 차트를 얻는 방법」으로 도입하면 기대가 어긋난다. 「같은 품질을 5분의 1 길이의 정의로 유지하고, 그 정의를 사람이 열어 고칠 수 있게 만드는 방법」으로 도입하면 숫자와 기대가 맞는다.

측정 방식에도 한계가 있다. 채점자가 시각 언어 모델이므로 모델이 좋아하는 차트와 사람이 유용해하는 차트가 갈리는 지점은 이 점수로 잡히지 않는다. 「보인다」와 「알 수 있다」가 다른 문제라는 것은 관측 도구 전반에서 반복되는 구도이기도 하다.

9. 확인하지 못한 것

공개 자료에서 답이 나오지 않은 항목들이다. 도입을 검토한다면 이 목록이 곧 사전 검증 항목이 된다.

  • 한글·일본어·중국어 라벨의 폭 계산. 레이아웃 최적화는 최소 가독 폭을 전제로 하는데, CJK 문자의 실제 폭을 어떻게 잡는지는 확인되지 않았다. 한글 축 라벨은 같은 글자 수라도 라틴 문자보다 넓다.
  • 한국식 수 단위 서식. 만·억 단위 축약이나 원화 기호를 표준 의미 타입이 커버하는지, 아니면 재정의로 넣어야 하는지.
  • 재정의의 허용 범위. 인코딩 수준 재정의 항목이 스키마에 존재한다는 것까지는 확인되나, 어떤 속성이 열려 있고 어떤 속성이 닫혀 있는지 목록은 확인되지 않았다.
  • 의미 타입 추론 정확도. 최종 차트 품질은 평가됐지만, 타입 추론 단계 자체의 정확도를 따로 잰 수치는 확인되지 않았다.
  • 접근성 기본값. 자동 선택되는 색 배합이 색각 이상 대비 기준을 만족하는지, 어떤 기준을 쓰는지.
  • 컴파일 비용. 제약 최적화가 대용량 카디널리티에서 얼마나 걸리는지, 서버 렌더 파이프라인에 넣을 만한 지연인지.
  • 사람 평가. 자동 채점 결과는 공개돼 있으나 사람 평가자를 쓴 별도 결과는 확인되지 않았다.
  • 프로덕션 사례. 첫 공개가 2026년 7월이라 운영 환경 적용 사례는 아직 공개된 것이 없다.

10. 도입 판단 - 언제 쓰고 언제 기존 문법으로 남나

버전이 0.4.0이고 첫 릴리스가 2026년 7월이다. 1.0 이전이라는 사실을 판단의 전제로 깔아야 한다. API가 바뀔 수 있고, 바뀌면 사양을 다시 써야 한다. 라이선스는 MIT이므로 그 부분의 제약은 없다.

상황판단이유
에이전트·챗봇이 차트를 만들고 사람이 뒤에서 고침쓴다부분 수정 표면적이 작은 것이 그대로 값이 된다
같은 지표를 웹과 Excel 양쪽으로 내보내야 함쓴다단일 사양에서 백엔드별 네이티브 출력
차트 정의를 코드 리뷰에 올리고 싶음쓴다60줄 JSON은 리뷰가 안 되고, 10줄은 된다
사내 지표 사전이 있고 필드 의미가 안정적쓴다의미 타입 매핑이 한 번으로 끝난다
브러싱·줌·크로스필터가 요건안 쓴다상호작용은 현재 일급 지원 대상이 아니라고 논문이 명시
다층 차트·주석이 핵심안 쓴다같은 이유로 범위 밖

파이썬 데이터 파이프라인이 주력보류파이썬 패키지가 아직 소스 미리보기 단계
차트 한두 개짜리 일회성 작업안 쓴다의존성 추가 비용이 이득보다 크다

시험해 볼 생각이라면 순서는 이렇게 잡는 게 낫다.

  1. 실제로 쓰는 표 하나를 고른다. 날짜 같은 정수 키가 있는 표가 차이를 가장 크게 드러낸다.
  2. 지금 쓰는 문법으로 만든 사양과 나란히 놓고 줄 수와 토큰 수를 센다.
  3. 「이것만 바꿔줘」를 다섯 번 연속으로 던지고 몇 번째에서 앞선 수정이 유실되는지 본다. 이게 실제 판단 근거다.
  4. 사내에서 자주 쓰는 서식이 표준 의미 타입에 있는지, 재정의로 되는지 확인한다.
  5. 패키지는 npm install flint-chart로 들어가고, 에이전트 환경에서는 npx -y flint-chart-mcp로 MCP 서버를 붙인다.

결론: 사양 설계가 모델 성능을 대신하는 구간

정리하면 이렇다. LLM에 차트를 맡길 때 어긋나는 자리는 정해져 있고, 그 어긋남의 상당 부분은 모델이 이미 아는 것을 저수준 파라미터로 번역하는 과정에서 발생한다. 의미 기반 사양은 그 번역을 컴파일러로 옮긴다. 얻는 것은 짧은 정의와 부분 수정이 가능한 표면적이고, 잃는 것은 자동 결정된 값들에 대한 직접 제어권이다.

숫자가 말해 주는 것도 분명하다. 품질 개선은 실재하지만 크지 않고 모델이 강해질수록 줄어든다. 반면 사양이 5분의 1로 줄어드는 효과는 모델과 무관하게 남는다. 그래서 이 접근의 수명은 「모델이 더 좋아지면 필요 없어질 것」과 「모델이 좋아져도 남을 것」으로 갈린다. 앞쪽이 품질 보정이고, 뒤쪽이 편집 가능한 표현이다.

오늘 당장 적용할 수 있는 것 세 가지로 닫는다.

  • 지금 쓰는 프롬프트에 필드 의미부터 적어라. 도구를 안 바꿔도 된다. 「Period는 YYYYMM 정수, Users는 합산 가능한 개수, Ratio는 비율이라 누적 금지」 한 줄이 축 타입 오판과 비가산 누적을 상당 부분 막는다.
  • 차트 수정 지시를 다섯 번 연속으로 던져 보라. 지금 파이프라인이 몇 번째에서 앞선 수정을 잃는지가 곧 개선 여지의 크기다.
  • 「보기 좋게」를 요구 사항에서 분리하라. 자동 결정을 쓸 수 있는 자리인지 아닌지가 여기서 갈린다. 표현이 계약이면 자동화는 비용이다.
