重写一个正在运行的运行时 - Bun 1.4 从Zig到Rust

重写别人已经在用的软件时到底押上了什么，以及兼容性这个词实际指的是什么

2026年8月21日 开发/基础设施

引言：一个跑得好好的运行时换了实现语言

给生产环境的服务升级运行时版本时，我们通常只看两件事：有没有破坏性API，延迟有没有变差。2026年8月20日发布的 Bun 1.4 在这里多加了一个陌生的项目：运行时本身的实现语言整个换掉了。对外可见的API表面没变，底下却从Zig搬到了Rust。

只看版本号这是一次小版本更新，实际规模并非如此。据开发方公开文章，1448个 .zig 文件被移植到Rust，合并时一次性进入了百万行量级的改动。而这项工作在 2026年5月3日到14日，十一天 内完成。

这篇文章不是发布说明的翻译。真正值得追问的在别处：重写别人已经在依赖的软件 这个决定为什么沉重；以及判定这类决定成败的唯一工程标准 兼容性，究竟指的是什么。顺带把发布公告里的倍数与百分比该在什么条件下阅读一并整理清楚。换语言重写这个主题在 TypeScript 7.0 RC 与Go原生编译器 和 Grit 用AI智能体把Git重写为Rust的尝试 中也谈过，但那两次分别是工具与实验。这一次是 生产环境里的运行时，性质不同。

公布了什么 — 截至2026年8月可确认的范围

先把事实简要摆清。以下内容全部来自开发方官方博客，确认时点为2026年8月。

  • 实现语言移植 — Bun 1.4 是Rust移植版的首个正式发布。移植工作于2026年5月3日启动，5月14日合并。
  • 不是重新设计 — 开发方把目标钉死在 机械式移植 上。架构、数据结构，以及与JavaScriptCore、OpenSSL、SQLite、uWebSockets等C与C++库的绑定全部保持原样。
  • Node.js 测试通过数 — 通过的Node测试文件从v1.2.0的1450个增加到v1.4.0的3743个，本次发布新增通过1517项。
  • 标准库吸收 — 图像处理、无头浏览、定时任务、Markdown、XML、归档等相当于十五个npm依赖的功能被搬进内置API。
  • 明确标注为实验 — Bun.serve() 的HTTP/3 是实验功能，开发方自己写明不要在生产环境打开。fetch() 的HTTP/2与HTTP/3 也放在功能开关之后。

公告部分到此为止。有意思的是接下来。这种规模十一天完成的说法，与同一篇文章里写明的 19个已知回归，是同一个事实的正反两面。只读一面，画面就只有一半。

换语言重写这个决定有多重

新项目用什么语言起步，是口味与团队情况的问题。但把 已经在生产环境运行的软件 用另一种语言重写，性质完全不同。押上的不是代码，而是 积累起来的信任。

正在运行的软件身上挂着文档里没有的资产：被数年缺陷报告磨出来的边界情况处理、用户为了绕开问题而形成并逐渐依赖的做法、规范里没有却事实上成为契约的行为。这些都没有明确写在源码里。换到新语言的那一刻，最先消失的就是没写下来的那部分。

所以这类重写永远跟着同一个问题：押上什么，换回什么。

  • 押上的第一样 — 功能停摆：重写进行期间新功能停下。用户立刻感受到停滞，收益却要很久之后才出现。
  • 押上的第二样 — 缺陷回流：旧实现花数年修好的缺陷在新实现里重新打开。这次开发方承认的19个回归正是这一项。
  • 押上的第三样 — 信任重置：从用户角度看，验证履历被清零。这个版本两年没出过问题这句话，要从头重新攒起。
  • 换回来的 — 结构性解决：不再逐个追缺陷，而是让那一整类缺陷 从一开始就编译不过。这是换语言给出的唯一且决定性的回报。

我的判断是这样：重写站得住脚的场景是「结构性消灭某一类缺陷」，而不是「让它更快」。 如果只图性能，改热点路径几乎总是便宜得多。这个区分与 从Go迁移到Rust的判断框架 中讲的信号与反信号完全是同一条轴。

为什么要重写 — 四种动机

工程上会考虑换语言的理由大致是四种之一。这次案例落在哪里也一并标出。

  • 内存安全 — 想让手动内存管理里反复出现的 use-after-free、double-free、错误路径上忘记释放，在编译阶段就被拦下。这 正是这次移植公开说明的主要理由。Zig没有析构函数，清理必须在每个调用点用 defer 写出来；团队试过自制智能指针，结果被形容为比Rust更差的使用体验且没有任何保证。Rust的 Drop 顶上了这个位置。
  • 生态 — 需要的库在那门语言里是否已经存在。加密、解析器、序列化这类自己写很危险的领域，权重更大。
  • 招聘与交接 — 能不能找到会写这门语言的人。越小众，公交因子越小。
  • 工具链 — 调试器、性能剖析、静态分析、依赖审计是否成熟。说到底是出事时有没有手段定位根因。

需要注意的是这四项 权重并不相同。内存安全只能靠重写获得，而生态、招聘、工具链大多通过 局部引入 就能拿到相当一部分。真正撑得起全面重写的，实际上只有第一项。

为什么危险 — 重写崩在哪里

这次移植走的流程相当细密。据开发方说明，团队先写好移植规则文档与生命周期对照表，用三个文件做试运行，再扩展到全量。实现方与评审方的上下文被分开，每个实现者配两名评审，验证跑在与语言无关的测试套件上，并且 没有跳过或删除任何一条测试。合并之后对全部解析器长期运行覆盖率引导的模糊测试。

即便如此，这类工作崩掉的位置是固定的。

  • 测试不检查的行为 — 这次报告的回归例子很能说明性质：在奇数字节位置截取UTF-16字符串的结果、解析器栈使用量的变化。两者都不是API规范而是实现副产物，测试很难覆盖。
  • 仍然留着的安全边界 — 开发方说明Rust代码中约4%、大约13000处位于 unsafe 块内，其中78%是单行指针转换。只要还在使用JavaScriptCore这类C与C++库，这块区域就不会消失。
  • 速度带来的评审负债 — 短时间内涌入大量代码，人真正读过的比例必然下降。围绕这一点出现了公开的反驳。 一篇外部分析文章指出未关闭的合并请求超过五千件、稳定版发布间隔异常拉长，同时质疑安全性改善的实质与代码质量。
  • 成果归属问题 — 另一篇外部分析认为这次变化对用户是净收益，但同时指出公告把 确实由Rust带来的改善 与 本来不需要重写就能做的工程优化 捆在一起，说得过头了。

搬出这些反驳不是为了下判决，而是因为 重写的成败不在发布当天决定。判定需要的不是倍数而是时间，而截至2026年8月，那段时间还没有过去。

Node.js 兼容实际指的是什么

这是本文最具工程性的一节。评估替代运行时时人们最先看的就是Node.js兼容性，而 这个词至少把四个不同层次 混作一谈。在哪一层坏掉，处理成本会差一个数量级。

层次指的是什么坏在哪里怎么确认
1. API存在像 node:fs 这样的模块与函数是否存在调用未实现的模块立刻抛异常官方兼容文档中按模块列出的状态表
2. 行为一致同样的输入是否给出同样的输出与同样的错误部分选项不支持、错误码与消息差异、编码边界行为Node测试套件通过率，再加上自己代码的测试
3. 原生扩展用C与C++构建的 .node 模块能否加载N-API版本差异、缺少预编译二进制、构建工具链把原生包从依赖树中挑出来单独运行
4. 时序与私有API事件循环顺序、依赖内部符号的代码能否运行APM与埋点库、猴子补丁、测试运行器钩子真实的集成测试。静态分析抓不到

第一层靠文档解决。第二层测试套件能覆盖相当一部分。麻烦的是第三层与第四层。工程上迁移失败几乎总是发生在这里，而兼容率这个数字对这两层几乎没有反映。

  • 官方文档把 node:node-api 标为已实现，但支持到哪个N-API版本、预编译发布的包能否直接跑起来，是另外的问题。
  • node:crypto 基于BoringSSL，文档明确写出部分密钥类型与加密算法缺失。处理证书与签名的代码会卡在这里。
  • node:cluster 文档写明跨进程分发HTTP请求仅在Linux上支持。如果开发机是macOS，可能只有本地看起来正常。
  • 工作线程会忽略部分选项并缺少特定API。单可执行文件打包（node:sea）标为未实现。

兼容率这个数字怎么读

公布的兼容率通常是 对Node.js官方发布测试套件的通过比例。这个数字有结构性的局限。

  • 分母不是你的代码。 Node测试套件是为了验证Node自身而写的，并不代表你的依赖树。
  • 文件单位与用例单位会混起来。 通过测试文件3743个与新增通过用例1517项，计数单位不同。引用时丢掉这个区分，数字就被夸大了。
  • 模块之间的差异被总数淹没。 有的模块100%，有的97%，而你的代码偏偏用到那3%，总数就毫无意义。
  • 开发方自己写了尚未达到百分之百。 这次发布文章里就有这句话。把发布方留下的限定语从引用中拿掉，不算准确引用。

所以我只把兼容率当作 准入条件。是否越过90%中段，只是「值不值得开始评估」的信号；是否采用的决定，只看自己的仓库里 install 与测试能否通过。 评估任何一个运行时，这条都一样。

性能数值要连同发布主体与条件一起读

运行时的发布总会带上倍数。这不是说倍数是假的，而是说 倍数与条件是一体的。以下是这次发布中开发方公开的数值，以及同一篇文章里附带的条件。全部是 开发方自行测量并公布的值，不是第三方验证。

项目公布的值文章中写明的条件怎么读
启动时间（Linux）5.1ms，上一版本10.9ms，Node.js 26为27.2ms写明了对比版本（Node.js 26.7.0）。测试机器仅在部分项目中标注只有在CLI、无服务器这类 频繁拉起进程 的负载中才有体感
HTTP服务器内存按框架不同下降40%到48%100万请求、64个连接（部分项目为10万请求）改变连接数结果就会变。必须按自己的流量形态重新测
流吞吐量下载1519MB/s，Node.js 26为204MB/s64MB载荷、4KB分块，AMD EPYC 9R14 Linux x64，三次取中位数条件披露得最完整的一项。分块大小对结果影响极大
正则表达式比上一版本快138倍针对一个固定的80KB输入做Markdown解析对比这是单一输入的对比。 不等于正则表达式整体快138倍
移植本身的性能效果整体提升2%到5%Linux x64，Xeon Platinum 8488C★换语言带来的纯效果就是这个量级。不要与上面的倍数混为一谈

最后一行才是这张表的要害。开发方自己把 移植本身的性能效果写成2%到5%。上面那些大倍数来自单项功能优化，原理上不做移植也能做。前面引用的外部分析所说的「说得过头」，指的正是这里。

  • 先确认发布主体。 是自测值、第三方基准，还是附带了可复现脚本。
  • 条件没写明的数值，就写成条件未标注。 不带条件搬运的倍数不是引用，是转发。
  • 看清对比版本。 是与对方运行时的最新稳定版比，还是与几个版本之前比，画面完全不同。

选运行时时真正分歧的维度

基准测试只是评估的起点。是否采用，取决于下面这些维度。每一项都附上 在自己项目里怎么测。

维度差别在哪里在自己项目里怎么测陷阱
启动时间冷启动是否直接进入用户可感知的延迟把真实入口拉起100次，同时记录中位数与p95拿空脚本测没有意义，依赖加载占了大头
包安装CI耗时与锁文件兼容性清空缓存做一次完整安装，再带缓存做一次锁文件格式不同，整个团队就必须统一到同一个工具
测试运行器现有测试资产能否原样搬过去先跑最复杂的测试文件，优先确认模拟、快照、定时器操控只让简单测试通过就往前走，会在迁移收尾时撞墙
是否内置打包器构建工具链与配置文件的数量与现有构建产物逐字节比对，确认源码映射与摇树结果内置打包器省事，代价是精细配置可能被堵死
部署环境支持★工程上最常卡住的一条直接查阅所用PaaS、无服务器平台、容器基础镜像的官方支持文档本地能跑与部署目标支持是两回事
原生扩展依赖C与C++的包能否加载从依赖树中只挑出原生包单独运行没有预编译，整条构建工具链就搬进CI
长期支持安全补丁还能收到几年在官方发布策略文档中确认支持终止日期服务寿命长于支持期，等于预约了下一次迁移

如果只能挑一行，挑 部署环境支持。其他维度都有替代方案，这一条没有。部署目标不支持，其余所有优点都失去意义。

不换也是合理的选择

每次出现新运行时，讨论都会滑向「那什么时候迁」。我的判断更靠近另一侧：对大多数服务来说，替换运行时优先级很低。 理由如实写下。

  • 成熟度只能用时间买。 与代码质量无关，「这套组合几年没出过问题」这段履历，用钱和重写都造不出来。首个正式版本按定义就没有这段履历。
  • 长期支持策略必须与服务寿命匹配。 如果安全补丁供到什么时候都不清楚，采用当天就等于预约了下一次迁移。
  • 公司内部标准是有原因的。 CI镜像、安全扫描器、APM代理、故障处理流程，全部按某个特定运行时搭起来。换掉一个运行时，挂在它后面的东西会一起晃。
  • 瓶颈通常不是运行时。 如果响应延迟大部分来自数据库往返与外部API等待，把启动时间减半，用户也感觉不到。

这并不是说新运行时没有价值。对于 冷启动直接等于成本的负载、CI耗时直接吃掉团队产能的仓库、以精简工具链为目标的新项目，算式完全不同。要点不是胜负而是 条件。问哪个运行时赢了，这个问题本身多半就问错了。

如果要迁 — 试验顺序与回退位置

决定评估之后，顺序很重要。原则是 先试最便宜、失败最快的那一步。下面这个顺序适用于任何运行时迁移。

  • 第一步 — 只装依赖。 不碰生产代码，用新运行时的包管理器只做安装。卡在这里，后面就不用看了。原生包清单在这一步先提取出来。
  • 第二步 — 只换测试运行器。 执行运行时保持不变，只用新的运行器跑测试。看的不是通过率而是 失败测试的性质。在模拟、定时器、快照上崩，说明是第四层问题，代价很大。
  • 第三步 — 一个非核心服务。 挑一个有真实流量但故障影响有限的服务，真正跑起来。批处理作业或内部工具比较合适。
  • 第四步 — 对照观测指标。 把常驻内存、p95与p99延迟、重启频率、日志中的异常类型，在迁移前后放到同一个时间窗里比。只看均值会漏掉尾部变差。
  • 回退位置一 — 把运行时做成配置而不是代码。 一个容器镜像标签或一个流水线变量就能退回旧运行时。一旦把新运行时专属API写进源码，这个位置就消失了。
  • 回退位置二 — 提前写下中止标准。 用 数字 写清楚：p99恶化X%就中止；原生依赖中只要有一个没有预编译就中止。迁移越往前走，沉没成本越会把标准掰弯。

再补一句：在迁移初期就用上新运行时的内置API（图像处理、定时任务、归档等），我不建议。方便，但同时是 亲手抹掉自己的回退位置。等迁移稳定之后一个个搬过去也不迟。

没能确认的部分

写这篇文章时未能取得依据的项目，集中列在这里。

  • unsafe 处数的对比基线。 大约13000这个值，与同等规模的手写Rust项目相比是多还是少，我没有找到可用于判断的公开基线。没有对比就不能说多或少。
  • 原生扩展的实际覆盖范围。 官方文档把N-API标为已实现，但支持到哪些N-API版本、常用预编译包是否真的能跑，文档中没有。
  • 各项测量环境的一致性。 流吞吐量标明了硬件，但HTTP服务器内存、Windows启动时间等部分项目未能确认是否标注了机器。
  • 第三方复现结果。 我没有找到独立复现本次发布数值的基准测试。上文引用的外部文章也是对公告的分析，而非自行测量。
  • 各云厂商的官方支持状况。 主要无服务器与PaaS平台何时正式支持这个版本，需要各自查阅厂商文档。本文没有确认。

结论：运行时竞争给使用者留下什么

这件事留下的不是哪个运行时更快，而是 重写正在运行的软件要押上什么，被公开记录了下来。十一天的周期、19个回归、4%的安全边界、2%到5%的纯性能效果，以及针对这一切的公开反驳。这个组合对今后考虑类似决定的团队来说，是相当具体的参照点。

回到使用者身上的实惠也很明确。运行时之间一竞争，启动时间会缩短，工具链会整合，默认值会改善。这份效果对不迁移的一方同样有效，因为一旦出现竞争者，既有运行时也会沿着同样的维度动起来。

归纳起来是这样：公布的倍数连同条件一起读，兼容率只当作准入条件，采用与否的决定来自 自己仓库里的安装与测试。而决定不换，同样是有依据的结论。如果今天的瓶颈不在运行时，这个判断不会因为下一个版本发布而改变。
