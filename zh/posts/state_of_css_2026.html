CSS 清除掉的那些绕行方案 - 当浏览器接手预处理器和 JS 的工作

按功能看什么消失了、什么还留着，以及支持状态该怎么读

2026年8月16日 开发/基础设施

引言：从样式表里悄悄消失的那些行

打开一个搁置了几年的项目，几乎一定会同时看到三样东西。插在构建流水线里的预处理器，往父元素上加加减减类名的那几行 JavaScript，还有散落在各个文件里的媒体查询断点。它们看上去是三种不同的工具，来历却是同一个。三者都是为了填补 CSS 当时做不到的事而存在的。

这些绕行方案里的相当一部分，在最近几年进入了浏览器。嵌套由解析器直接处理，出现了以内容为条件挑选父元素的选择器，可以询问容器宽度而不是视口宽度，优先级之争也有了带名字的规则。所以今天有用的问题不是「CSS 又多了什么」，而是「它究竟去掉了什么」。新语法需要时再学就好，而可以删掉的代码，只要不删就会永远留着。

这篇文章会逐一确认五个功能各自移除的绕行方案，标出还没能移除的位置，然后整理支持状态的读法和采用判断的标准。所有关于浏览器支持的表述都是2026年8月16日核查的内容。CSS 的支持状态比本博客涉及的任何主题变化都快，如果你在半年后阅读，请再打开各功能 MDN 页面顶部的徽章看一眼。

前端二十年的整体脉络在前端到底发生了什么 - 从2008年jQuery到2026年AI编程里讲过，不要重新发明浏览器原生功能这条原则在「Don't Roll Your Own」原则 2026里。这里只看CSS 这一层。

1. 预处理器承担的活儿 - 嵌套与变量

请人说出把预处理器放进项目的理由，答案通常是三个：嵌套、变量、混入。其中前两个已经被标准吸收了。

1.1 嵌套 - 解析器直接读

嵌套由浏览器自己解析，不需要事先编译。语法的核心是指代父级的一个字符 &。

/* 以前：经过预处理器转换才有意义 */
.card { .title { font-weight: 700; } }

/* 现在：浏览器按原样读取 */
.card {
  padding: 1rem;
  & .title { font-weight: 700; }
  &:hover { border-color: currentColor; }
}
  • 消失的东西 - 构建步骤。为了改一条声明而启动 watch 进程、把编译产物加进 gitignore、源码映射错位时手动去找原始行号，这些都没有了。
  • 仍然需要的理由 - 混入与循环。用循环生成色阶或间距刻度的代码、编译期的颜色计算、把多个文件汇总起来的导入整理，依然是预处理器的活儿。
  • 注意 - 特异度照样会涨。嵌套会在你看不见的地方把选择器变长。预处理器时代的陷阱不会因为它变成标准就消失。深度控制在两三层以内比较安全。

1.2 自定义属性 - 和预处理器变量不是一回事

两者都叫「变量」，所以经常被当成同一样东西，但性质不同。$gap 在编译结束后就消失了，产物里只剩下算好的值。--gap 则在运行时活着。其余的一切都由这一点差异派生出来。

:root { --gap: 1rem; --brand: #2c6fdb; }
@media (min-width: 48rem) { :root { --gap: 2rem; } }
.grid { gap: var(--gap); }
.btn  { background: var(--brand); }
/* 回退值放在第二个参数 */
.card { border-radius: var(--radius, 6px); }
  • 会继承，也能在条件里切换。在父级改一个值，下面全部跟着走；在媒体查询或容器查询里只替换一个值即可，不必为每个条件复制一整套规则。
  • 消失的东西 - 主题文件的复制。为暗色模式再造一整套 CSS，或者在 .theme-dark 之下把所有规则重写一遍的做法，缩成了根节点上几行变量重定义。
  • 消失的东西 - 内联样式注入。不再由 JavaScript 逐个元素塞 style 属性，而是用 element.style.setProperty('--x', v) 只递下去一个值。规则仍然留在样式表里。
  • 边界。声明值的类型使其可动画属于 @property 的范畴，本文没有核查它的支持状态。

2. :has() - 过去为了挑父元素而调用 JS 的地方

场景总是相似的。卡片里有缩略图就想改成两栏布局。输入框里有值就想把标签上移。列表为空就想显示空状态提示。在选择器只能向下流动的年代，答案只有一个：渲染时给父元素加个类名。

那一个类名带来的成本比看上去大。内容一变就得有代码去更新它，服务端渲染和客户端渲染两边都要放同一份判断逻辑，逻辑上还会挂上测试，时间一长它就变成谁也不敢删的类名——因为已经追不到是什么把它加上去的了。

/* 输入框有值就把标签上移 - 不用 JS */
.field:has(input:not(:placeholder-shown)) label {
  transform: translateY(-1.2em);
  font-size: 0.8rem;
}

/* 只有带缩略图的卡片变两栏 */
.card:has(> img) { grid-template-columns: 8rem 1fr; }

能核查到的支持情况相对清晰。MDN 把 :has() 标为 Baseline 广泛可用，并写明自2023年12月起可在各浏览器中使用（2026年8月16日核查）。不过文档同时列出了几条限制，其中一条的失败方式相当粗暴，务必先知道再用。

  • :has() 里不能再嵌套 :has()。
  • 伪元素不能作为 :has() 的参数，也不能充当 :has() 的锚点。
  • 在不支持的浏览器里，包含该选择器的整个规则块都会失效。意思是你写在旁边的其他声明也会一起死掉。把它放进 :is() 或 :where() 这类宽容选择器列表中，就只丢弃那一部分，其余得以存活。
  • 特异度取参数中最高的那个，和 :is()、:not() 是同一条规则。
  • 文档里也有性能指引：不要把 body、:root、通配选择器当锚点，要用子代（>）和相邻兄弟（+）组合器把遍历范围收窄。

3. 容器查询 - 问的是所在的槽位，不是视口

媒体查询的局限从来不在语法，而在提问的对象。媒体查询只知道屏幕有多宽。真正需要知道的是「装着这张卡片的槽位有多宽」，而当同一个卡片组件既进窄侧边栏又进正文三栏网格时，屏幕宽度什么也说明不了。

于是组件必须知道自己在哪儿。这份知识通常以 variant="compact" 之类的属性注入，或者由 ResizeObserver 测量宽度再切换类名来实现。两种做法都是把布局知识复制到组件外面。

.sidebar, .main-grid > * { container-type: inline-size; }

@container (width > 30rem) {
  .card { display: grid; grid-template-columns: 8rem 1fr; }
}

MDN 把 @container 标为 Baseline 广泛可用，时间写作2023年2月起。但旁边带着一个星号——表示该功能的部分内容支持水平可能不同。因为同一份文档里除了尺寸查询，还并列着样式查询、滚动状态查询和锚点相关查询，不能用「支持容器查询」一句话把这四样打包在一起。

  • 容器必须显式声明。没有指定 container-type 的元素不在查询范围内。取值为 inline-size（仅行内轴）、size（双轴）、normal（默认值，不作为尺寸查询容器）。
  • 实务中绝大多数用 inline-size。size 会在双轴上施加包含，内容无法撑出高度，不另外给高度元素就会塌掉。
  • 不能查询自身。查询只对祖先容器成立，所以在卡片外面再套一层包裹元素的结构非常常见。
  • 消失的东西。ResizeObserver 与类名切换、把布局信息传给组件的 props，以及在 CSS 和 JS 两边各存一份、只等着彼此错位的断点常量。

4. @layer - 把优先级之争变成规则

想把设计系统里的按钮只在某个页面上稍作改动，结果不生效。把选择器写长。还是不生效。加上 !important。半年后来修这个页面的人又把同样的顺序走一遍。这道台阶来自特异度这种隐式竞争。

@layer 把那种竞争换成了声明顺序这一条显式规则。MDN 标注为 Baseline 广泛可用，2022年3月起。

/* 在开头一次性声明顺序 */
@layer reset, vendor, base, components, utilities;

@layer vendor { /* 第三方 CSS 放这里 */ }
@layer components { .btn { padding: .5rem 1rem; } }
@layer utilities { .mt-0 { margin-top: 0; } }

需要记住的规则有三行，其中第二行决定架构。

  • 先声明的层弱，后声明的层强。赢的是顺序，不是特异度。
  • 没有放进任何层的样式，比任何层里的样式都强。把第三方 CSS 关进低层，自己的样式只要留在层外就赢了。
  • !important 会把这个顺序反转。重要声明彼此相争时，先声明的层最强。也就是说在重置层里用 !important，会把上面所有层压平。
  • 消失的东西。!important 的台阶、.app .page .card .btn.btn-primary 这种特异度膨胀，以及为了保住加载顺序而去改打包器配置的活儿。
  • 注意 - 失败是安静的。漏掉层声明或把名字拼错，规则就会落进匿名层或层外，没有任何报错，只有优先级被翻转。刚引入时最好准备一份需要肉眼确认的页面清单。

5.1 仍然属于 JS 的地方

边界线一句话就能划出来。CSS 会应用样式，但不会返回值。判断某个功能能否消掉 JavaScript 时，按这条轴分基本都能猜对。

  • 读取测量值的活儿。需要以数值形式知道元素实际有多少像素、文本流成了几行的逻辑，仍然是 JS。容器查询会按那个宽度改样式，却不会告诉你宽度是多少。比较 A 和 B 的宽度来决定 C 的计算也属于这一类。
  • 条件在 DOM 之外的数据里。像库存少于三件就标红这样的规则，条件在服务端响应那边，CSS 没有办法看到它。但把那个值通过 data- 属性或自定义属性递下来的那一刻起就归 CSS 管了。边界在于「谁来计算值」，而不在于「谁来应用样式」。
  • 无障碍状态的更新。改动 aria-expanded 这类属性的是 JS。CSS 只能读取该属性来设置样式，改不了它。焦点陷阱和键盘移动顺序的管理也一样。
  • 绑定在时间点上的逻辑与列表操作。动画结束后才跑的代码、元素进入视口时的延迟加载，以及排序、筛选、虚拟滚动。用 :has() 做到「没有子元素就显示空状态」是可以的，但改不了条目的顺序。
  • 表单校验的内容与时机。显示哪条消息、什么时候显示属于约束校验 API 的范畴。CSS 接手的只是有效·无效状态的呈现。

归纳起来，CSS 接手的区间是「条件 → 样式」。「数据 → 条件」和「样式 → 值」原封不动地留着。框架一侧如何处理同一条边界，在Foldkit — 追求正确性的新前端框架里另行讲过。

6. 「已支持」的层次 - 浏览器支持的读法

「那个功能支持吗」听上去是一个问题，里面至少混着四个。不把层次分开，就会在不需要的地方铺回退，或者反过来在该铺的地方省掉，然后一直维护这个错误。

层次含义实务判断本文核查到的例子（2026-08-16）
广泛可用在众多设备与浏览器版本上稳定落地。MDN 会一并标出从何时起可以不带回退直接用的层:has() 自2023年12月起 / @container 自2023年2月起（带星号） / @layer 自2022年3月起
仅最新浏览器主流引擎最新版有，旧版没有只做渐进增强。若目标包含被锁定版本的企业浏览器或旧款移动端，必须有回退本文未核查到例子
仅部分引擎按引擎分化不要用在核心布局路径上锚点定位 - MDN 概览文档上不显示 Baseline 徽章
标志位·实验阶段用户需自行开启设置才生效禁止用于生产。仅限演示与学习本文未核查到例子
  • 看「从何时起」，而不是看「已支持」。日期越久远，用户设备上的浏览器已经越过那个版本的概率就越高。信息的实体在日期这一侧。
  • 别漏掉星号。像 @container 那样带着「部分内容支持水平可能不同」的标注，就是在提示你要把归在这个名字底下的子功能逐个核查。
  • 区分模块名和属性名。一个规范模块里装着多个属性，各自到达的时间并不相同。核查的单位是你实际要写的属性和取值，而不是模块。
  • 与自己用户的版本分布对照。最新浏览器里有，和你的访客正在用那个版本，是两件事。如果服务跑在锁定旧版的企业内网后面，或者来自即时通讯内置浏览器的比例很高，全球平均统计作为依据就很弱，分析工具的浏览器版本报告才是唯一的实测。
  • 把核查日期写进文档。不在团队 Wiki 里留下「2026-08-16 核查」这一行，半年后就得把同一批功能从头再查一遍。

6.1 @supports - 回退的设计方法

@supports 在 CSS 内部询问浏览器是否理解某条声明或某个选择器。语法有三种形态。

/* 基础放外面，增强放里面 */
.card { display: block; }

@supports (container-type: inline-size) {
  .card-wrap { container-type: inline-size; }
  @container (width > 30rem) { .card { display: grid; } }
}

@supports selector(:has(*)) { /* 选择器是否受支持 */ }
@supports not (anchor-name: --a) { /* 否定条件 */ }
  • 问的是解析，不是行为。@supports 只确认浏览器是否理解那条声明。它筛不掉「理解但实现不完整」的情况，所以通过了也不能省掉看屏幕这一步。
  • 方向要守住。连 @supports 本身都不认识的很旧的浏览器会整块忽略。所以基础样式放在块外，增强放在块内。用 not 去包回退，就会有浏览器把那份回退整块丢掉。
  • :has() 要包起来。不支持的浏览器会丢弃整个规则块，所以写成 :where(.card:has(img)) 这样放进宽容列表，其余声明才能活下来。代价是 :where() 会把特异度归零，因而更容易输给别的规则。
  • 回退策略三选一，并同时写上有效期。①渐进增强——基础状态已经够用时只叠加增强。②等价替代——先用媒体查询近似，再用容器查询精化。③暂缓——如果是核心布局、必须维护两套回退，那份成本往往超过功能带来的收益。无论选哪种，如果不在回退旁边用注释写清「满足什么条件就删掉」，那段代码在条件达成之后还会再活好几年。

7. 调查数字的读法 - 回答者不是平均水平的开发者

每年发布的 CSS 调查，作为观察「大家在讨论什么」的材料是好用的。但抄写数字时必须把样本的性质一起抄过来。State of CSS 2026 是一份2026年5月15日至6月29日、由4,902人作答的公开网络调查。把这一行拿掉，剩下的就不是依据而是印象。

  • 属于自愿作答。这不是随机抽样的样本，而是知道有这份调查、并且愿意作答的人聚在了一起。愿意在 CSS 调查上花时间的人，按定义就处在对 CSS 更上心的一侧。
  • 招募渠道会塑造结果。经由哪些渠道扩散，会让回答者构成整体改变。本文没能从公开页面确认招募渠道，那么就该把「这一项是空白」这件事本身附在引用旁边。
  • 总体 N 和各题 N 是两回事。4,902 是总回答人数，并非每道题都有这个分母。自由作答题尤其少——「最喜欢的新功能」一题的靠前项目是锚点定位168、:has()158、尺寸容器查询126、CSS 嵌套116，这是提及次数而非百分比，分母也不是4,902。
  • 确认「使用率」数的是什么，并从增减中扣除样本变化。「试过」「正在生产环境里用」「听说过名字」是三道不同的题，只看摘要抄写，这个区分就消失了。说某功能同比上升的表述里，也同时混着功能真正扩散的部分和回答者构成变化的部分。

带着这些前提去读，2026年版里值得提取的趋势是这样的。浏览器兼容性被列为采用的最大障碍，锚点定位作为「想用却因为支持不足而用不了」的代表例子被提及。框架题中 Tailwind 保持第一，「不使用框架」超过 Bootstrap 升到第二。CSS 代码由 AI 生成的比例平均在28%左右，低于其他开发领域，被提得最多的担忧则是认知过载。

另外还有一句这些数字并不支持的话。「现在大家都在用 :has()」从这份数据里推不出来。能成立的只到这里——在这个样本中，:has() 是被回答为使用最广的新功能之一。如果觉得两句话的差别微不足道，那就想一想：以前一句为依据把回退删掉之后，会坏掉什么。

8. 现在该采用的和该暂缓的

判断轴有四条就够了。不支持时什么会怎样坏掉，维护两套回退的成本，核查到的支持日期与自己用户分布之间的距离，以及日后回滚的成本。其中第一条最重。只是稍微难看一点的失败，和布局整个塌掉的失败，不该放在同一个天平上。

功能不支持时的症状回退难度判断
嵌套规则被忽略，样式完全不生效低 - 用预处理器编译就是0核查后采用。若尚未确认支持日期，保留编译更安全
自定义属性值为空，落到回退值低 - var(--x, 默认值)现在就用
:has()整个规则块失效 - 旁边的声明也一起死掉中 - 用 :where() 包起来 + 回退规则现在就用。失败方式粗暴，把「包起来」变成习惯
容器查询（尺寸）容器内规则不生效，保持默认排布中 - 用媒体查询近似现在就用。样式查询与滚动状态查询另行核查
@layer被当作层外处理，优先级反转中 - 调整加载顺序现在就用。但失败很安静，刚引入时需要一份确认清单
锚点定位位置定不下来，提示框与浮层跑到别处高 - 得继续维护 JS 定位库暂缓。MDN 上没有 Baseline 徽章，调查中支持不足也被列为采用障碍

暂缓这一侧也有成本，这点值得点明。维护两套回退的团队，时间一长就只会去看回退那条路径了。如果没有确认增强路径确实被渲染出来的流程，那段代码就是死代码，而且在无人知晓它已死的情况下继续留在维护清单上。加新功能时，最好把「在哪个浏览器上确认增强路径」也一并定下来。

9. 没能核查到的内容

本文关于支持状态的表述来自各功能的 MDN 文档，以下内容在这个范围之外，因此不做断言。

  • CSS 嵌套的 Baseline 等级与引入时间 - 在概览文档上没能确认到徽章。请直接查看嵌套文档底部的浏览器兼容性表格。
  • 锚点定位按引擎划分的支持版本 - 概览文档上没有出现兼容性表格。只确认了「未显示徽章」这一事实。
  • @property、aspect-ratio、动态视口单位、滚动驱动动画 - 正文只在概念层面提及，未核查支持状态。
  • @container 星号所指的确切范围，以及 Baseline 等级的晋级标准 - 前者文档只标注为「部分内容支持水平可能不同」，因此样式查询与滚动状态查询需要在各自的文档里分别查看；后者未查阅定义文档。
  • 调查的招募渠道与各题回答人数 - 从公开的摘要页面无法确认。百分比形式的数字是经由汇总摘要获得的，因此没有核对原题的表述。

常见问题（FAQ）

现在可以把预处理器拿掉了吗？

如果你用到的只有嵌套和变量，那么去掉的依据是成立的。混入、用循环生成工具类的代码、编译期颜色计算、文件拆分与导入顺序整理，依然是预处理器的活儿。判断不要靠偏好，要靠清单——把预处理器文件里实际用到的语法抽出来，分成能被标准替代的和不能替代的，答案立刻就出来了。

使用 :has() 会拖慢性能吗？

慢的不是选择器，而是你让它遍历的范围。MDN 的指引很明确——不要把 body、:root、通配选择器当锚点，用子代和相邻兄弟组合器把范围收窄。在一张卡片内部问子元素有没有，这种量级不成问题。不放心的话，在真实页面上测样式重算耗时比猜快得多。

容器查询会取代媒体查询吗？

不是取代而是分工。页面整体的骨架——分几栏、侧边栏折不折叠——依然在媒体查询这一侧。容器查询用于骨架里的零件按自己所在槽位的宽度做调整。两者会叠着用，所以把断点值集中在一处的习惯反而更重要。

引入 @layer 会不会弄坏现有的 CSS？

会，而且是安静地坏。记住一条规则大半都能预测——没有放进任何层的样式，比任何层里的样式都强。所以把现有 CSS 整体塞进层里，原本一直赢的规则会突然开始输。安全的顺序是反过来的：先把重置样式、第三方 CSS 这类希望永远输的东西放进低层，自己的样式留在层外先观察。

可以拿调查数字当技术选型的依据吗？

调查告诉你的是关注度的方向，不是采用率。公开网络调查属于自愿作答，回答者会偏向对该话题上心的一侧。所以使用率高这件事并不能成为你的用户浏览器支持该功能的依据。它的用处到「挑选评估清单」为止，之后的判断交给浏览器兼容性文档和自己服务的版本分布。

结论：今天要做的三个判断

把最近几年 CSS 的变化压缩成一句话，就是「判断条件这件事从脚本下沉到了样式表」。父级的状态、所在槽位的宽度、规则之间的次序——这三样以前都在 CSS 之外计算，再以类名的形式注入。现在这些计算进到了选择器里面。所以收益不在新语法上，而在可以删掉的代码上。

  • 先数一数现有的类名切换。往父元素上加减类名的代码、用 ResizeObserver 测宽度的代码、主题用的整套类名。这份清单就是可回收代码的清单。
  • 按失败方式判断，而不是按功能判断。不支持时只是稍微难看的功能，和让整个规则块死掉的功能，采用门槛就该不同。把 :has() 包进宽容列表的习惯，正是从这个判断里来的。
  • 留下核查日期。支持状态半年就会变。不在团队文档里写下各功能的核查时点，要么把同一批调研重做一遍，要么继续沿用过时的判断。

最后关于调查再说一句。这类材料在挑选「什么该进评估清单」时有用，也就到此为止。是否采用由浏览器兼容性文档和自己服务的版本分布决定。脱离回答人数与调查时段被引用的数字，无论那个数字是什么，都不是依据而是气氛。
