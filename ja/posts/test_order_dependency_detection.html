テストの順序を混ぜると見えてくるもの - 隠れた依存を暴く方法

合格は「正しい」ではなく「この順序では正しい」だった

2026-07-31 開発・インフラ

症状から: CIでだけ赤、手元では緑

月曜の朝、CIが赤い。ログを開くと金曜まで無事だったテストが一つ落ちている。その名前をコピーして手元で回す。通る。もう一度回す。また通る。コードをいくら眺めても間違っている箇所がない。そこで再実行ボタンを押す。今度は緑が出る。そうして先へ進む。

この状況の多くは「たまに落ちるテスト」という札を貼られて通り過ぎる。だがその札は原因を何一つ説明しない。この記事はそのうちの一つの原因だけを扱う。実行順序だ。

順序依存は他の不安定要因とは質が違う。時間や同時実行のせいで揺れるものは同じ条件でも結果が変わりうるが、順序依存は完全に決定論的だ。同じ順序で回せばいつでも同じ結果が出る。ただ、その順序がいつ変わるのかを誰も気にしていなかっただけだ。

だからこの記事の論旨は「テストを分離しましょう」ではない。それは結論であって診断ではない。言いたいのはこうだ。

テストの間に残る状態があれば順序がそのまま入力になる。そのとき合格は「正しい」ではなく「この順序では正しい」になる。そしてその入力は誰も検証したことがない。

こう捉えると、順序を混ぜる行為の意味も変わる。それは潔癖や好みではなく入力の範囲を広げる作業だ。一つの順序だけを回すのは、関数に値を一つだけ入れて正しいと宣言するのと同じである。

実行環境。以下のすべての出力はWindows 10 Pro (10.0.19045)で実際に実行した結果だ。道具はPython 3.13.3 (win32, MSC v.1943 64bit)の標準ライブラリunittestとNode.js v22.16.0 (win32 x64)のnode:test、シェルはGNU bash 5.2.37 (MSYS2)だ。

なくて回せなかったもの。この環境にはpytestが入っていなかった(No module named pytest)。Python 3.11でも同じで、nose2もなかった。そのためpytest系の順序の挙動と関連プラグインは直接測定できなかった。この記事でpytestに触れる箇所は文書を根拠にしたもので、実測ではないと明示している。

スクリプトはすべてファイルに保存して実行した。以下の例と経路はすべて/tmp/order-demoのような仮の置き場所に書き換えた架空のコードだ。

1. 問題のテスト四つ

まず対象を見よう。ごくありふれた形だ。モジュール一つがグローバルな辞書を持ち、テストたちがそれを共に使う。

# /tmp/order-demo/store.py
CONNECTIONS = {}          # プロセスごとに一度だけ読み込まれるモジュール水準のグローバル

# /tmp/order-demo/tests_shared.py
import unittest
import store

class SessionTests(unittest.TestCase):
    # わざと d, b, a, c の順で定義した
    def test_d_close_all(self):
        store.CONNECTIONS.clear()
        self.assertEqual(store.CONNECTIONS, {})

    def test_b_query_uses_connection(self):
        self.assertEqual(store.CONNECTIONS["main"], "pg://demo")

    def test_a_open_connection(self):
        store.CONNECTIONS["main"] = "pg://demo"
        self.assertEqual(len(store.CONNECTIONS), 1)

    def test_c_registry_has_one_entry(self):
        self.assertEqual(len(store.CONNECTIONS), 1)

四つともそれ自体としては自然に読める。接続を開き、問い合わせ、個数を数え、閉じる。どこにも「前のテストが接続を開いておくはずだ」とは書かれていない。ところが実際にはそう仕込まれている。

2.1 順序が入力なら、入力空間はどれほどか

二つだけ見れば「運が悪かった」で済ませられる。そこで24通りの並びをすべて新しいプロセスで回してみた。

合格率が17パーセントだ。そして決定的な事実がもう一つある。この道具の既定の順序であるa b c dが、緑の四つのうちの最初だ。開発者は毎日緑を見ていて、順序が少し揺れれば即座に赤になる状態で何か月も過ごしていた可能性がある。

  • 緑の四つを見ると共通点が浮かぶ。aがbとcより前にあり、dはb・cより後ろにある
  • この制約はコードのどこにも書かれていない。名前のアルファベット順がたまたまその制約を満たしていただけだ
  • 誰かがtest_a_open_connectionをtest_setup_connectionに改名した瞬間に赤になる。リファクタリングがテストを壊したのではなく、隠れていた依存が表に出たのだ
  • テストを一つ追加するだけでも位置がずれる。新しいテストには何の落ち度もないのに別のテストが赤になる

3. 既定の実行順序は道具ごとに違う

ここで最もよくある誤解を正しておきたい。「テストは上から順に回る」という思い込みだ。それは道具によって正しくもあり間違いでもある。だから一般化せず使う道具で自分で測ること。以下はこの環境で測った値だ。

一般化しないこと。上の値はこの道具、この版、この環境で測ったものだ。同じ道具でも版が変われば違いうるし、順序関連のプラグインを一つ入れればその瞬間に変わる。pytestの行は導入されておらず実際に回していない。文書を根拠に書いただけなので鵜呑みにせず各自の環境で測ってほしい。測り方は簡単だ。定義順と名前順がずれるテストをいくつか作っておき、実際にどちらで回るかを見ればよい。

4. 状態が残る五つの場所

順序が入力になるにはテストの間に何かが生き残らねばならない。その場所を五つに分けてそれぞれ実行で確かめた。すべての実行は新しいプロセスで始まり、fwdは名前順、revはその逆順だ。

4.1 モジュール水準のグローバル変数

case 1  module-level global       order=fwd
  run : a_open_connection -> b_query_uses_connection -> c_close_all
  ==> ALL PASS   (3/3 passed)

case 1  module-level global       order=rev
  run : c_close_all -> b_query_uses_connection -> a_open_connection
  ==> 1 FAILED   (2/3 passed)
      red: b_query_uses_connection
      KeyError: 'main'

最もよくある場所だ。モジュールはプロセスごとに一度だけ読み込まれるので、その中の変数はテスト全体の寿命のあいだ生きている。ファイルを分けても無駄だ。同じモジュールを読み込んだ瞬間に同じ物体を共有する。

4.2 クラス属性

class FeatureFlags:
    enabled = set()          # クラス属性: すべてのインスタンスがこの一つを共有する

    def on(self, name):
        self.enabled.add(name)     # インスタンスではなくクラスの集合を変える

case 2  class attribute           order=fwd
  run : a_enable_beta -> b_fresh_object_has_no_flags
  ==> 1 FAILED   (1/2 passed)
      red: b_fresh_object_has_no_flags
      AssertionError: Items in the first set but not the second: 'beta'

case 2  class attribute           order=rev
  run : b_fresh_object_has_no_flags -> a_enable_beta
  ==> ALL PASS   (2/2 passed)

ここでは方向が逆だ。既定の順序で落ち、逆順で通る。self.enabled.add(...)はインスタンス属性を作るように見えるが、実際にはクラスにある集合を辿ってそこへ入れている。だからFeatureFlags()で新しく作った物体にも以前の値が入っている。

4.3 キャッシュとメモ化

USERS = {}

@functools.lru_cache(maxsize=None)
def find_user(uid):
    return USERS.get(uid)

case 3  cache / memoization       order=fwd
  run : a_created_user_is_found -> b_lookup_again -> c_unknown_user_is_none
  ==> ALL PASS   (3/3 passed)

case 3  cache / memoization       order=rev
  run : c_unknown_user_is_none -> b_lookup_again -> a_created_user_is_found
  ==> 2 FAILED   (1/3 passed)
      red: b_lookup_again              AssertionError: None != 'kim'
      red: a_created_user_is_found     AssertionError: None != 'kim'

この事例が五つの中で最も厄介だ。test_a_created_user_is_foundの中身をもう一度見てほしい。

def test_a_created_user_is_found(self):
    USERS[7] = "kim"                          # データを正しく入れて
    self.assertEqual(find_user(7), "kim")     # 正しく照会する  -> それでも失敗する

このテストには何一つ落ち度がない。それなのに逆順では赤になる。先に回ったtest_b_lookup_againがまだデータのない時点でfind_user(7)を呼び、その結果のNoneがキャッシュに焼き付いたからだ。キャッシュは「無い」という答えも同じように覚える。

  • キャッシュの付いた関数は事実上グローバル変数だ。ただし目に見えない場所にある
  • 設定値をフィクスチャで戻してもキャッシュを消さなければ古い答えがそのまま出る
  • 否定的な結果(見つからない、権限がない、空である)のキャッシュが特に危ない。後で状況を正しく整えたテストのほうが落ちる
  • 自前のキャッシュだけではない。読み込んだライブラリ内部のキャッシュ、コンパイル済み正規表現のキャッシュ、接続プールも同じ場所だ

4.4 一時ファイルとディレクトリ

case 4  temp file / directory residue  order=fwd
  run : a_export_writes_report -> b_export_dir_starts_empty
  ==> 1 FAILED   (1/2 passed)
      red: b_export_dir_starts_empty
      AssertionError: Lists differ: ['report.csv'] != []

case 4  temp file / directory residue  order=rev
  run : b_export_dir_starts_empty -> a_export_writes_report
  ==> ALL PASS   (2/2 passed)

ここまでは前の事例と同じだ。ところがこの場所には他の四つにない性質が一つある。後始末を抜いて二回続けて回すと表に出る。

$ python -c "残留物を除去"
residue cleared

--- run 1: 後始末を抜いて fwd の順序で実行 ---
  run : a_export_writes_report -> b_export_dir_starts_empty
  ==> 1 FAILED   (1/2 passed)
      red: b_export_dir_starts_empty

--- run 2: 完全に新しいプロセス、rev の順序(さきほどは ALL PASS だった) ---
  run : b_export_dir_starts_empty -> a_export_writes_report
  ==> 1 FAILED   (1/2 passed)
      red: b_export_dir_starts_empty

さきほどALL PASSだった逆順が今度は赤だ。プロセスを新しく立てたにもかかわらずである。ファイルシステムに残った状態はプロセスの境界を越える。つまりこの場合、「前のテスト」の座に前回の実行全体が座り込む。

  • だからこの型は「新しく取ってきた保管庫では動くのに自分の作業フォルダでは動かない」として現れる
  • CIが毎回きれいな容器を使うならCIでだけ通って手元で落ちるという逆の形になる
  • 固定した経路を使った瞬間並列実行でも互いを踏む
  • データベース、キャッシュサーバー、メッセージキューも同じ性質だ。プロセスを再起動しても状態が残る

4.5 戻していないモンキーパッチ

def test_a_invoice_with_frozen_clock(self):
    clock.now = lambda: 1700000000.0      # 差し替えて戻さない
    ...

case 5  monkeypatch that is never undone  order=fwd
  run : a_invoice_with_frozen_clock -> b_invoice_uses_real_clock
  ==> 1 FAILED   (1/2 passed)
      red: b_invoice_uses_real_clock
      AssertionError: 85445231.48900342 not less than 5.0 : clock is off by 85445231 seconds

case 5  monkeypatch that is never undone  order=rev
  run : b_invoice_uses_real_clock -> a_invoice_with_frozen_clock
  ==> ALL PASS   (2/2 passed)

誤差が8,544万秒、およそ2年8か月だ。時刻を固定すること自体は正当な技法である。問題は戻していないことだ。時刻だけでなく乱数の種、環境変数、通信呼び出しの差し替え、記録設定がすべて同じ場所にある。

右の五つを実務ですぐ使える形に整理した。この記事から一つだけ持ち帰るならこの表だ。

6. 誰が汚し、誰が落ちたのか

診断で最も頻繁に犯す間違いが赤くなったテストを犯人と見ることだ。目で確かめるために、すべてのテストの前後で共有状態を出力した。

order=fwd
  a_open_connection          state {}                     -> {'main': 'pg://demo'}  CHANGED
  b_query_uses_connection    state {'main': 'pg://demo'}  -> {'main': 'pg://demo'}    --
  c_registry_has_one_entry   state {'main': 'pg://demo'}  -> {'main': 'pg://demo'}    --
  d_close_all                state {'main': 'pg://demo'}  -> {}                     CHANGED
  red tests : (none)

order=rev
  d_close_all                state {}                     -> {}                       --
  c_registry_has_one_entry   state {}                     -> {}                       --
  b_query_uses_connection    state {}                     -> {}                       --
  a_open_connection          state {}                     -> {'main': 'pg://demo'}  CHANGED
  red tests : b_query_uses_connection, c_registry_has_one_entry
  who mutated shared state : a_open_connection, d_close_all

最後の二行を重ねて読む必要がある。赤くなったbとcは共有状態を一文字も変えていない(--の印)。状態を変えたaとdはどちらも緑だ。

  • 失敗した地点と原因の地点が完全に分かれる。だから失敗ログのスタックトレースは犯人を指さない
  • 逆順での本当の原因はd_close_allが先頭で辞書を空にしたことだ。ところがdは自分の表明を通ったので何の信号も残さなかった
  • この構造のせいで被害者に防御コードを入れる対応が生まれる。赤は消えるが汚染源はそのまま残る
  • 直すべき場所は状態を変えて戻さなかった側だ

7. 二分探索で犯人を絞る

テストが四つなら目で見える。数百なら見えない。だから手順が要る。被害者の前に置くテスト集合を半分ずつ減らすことだ。

実験用に17個の例を作った。大半は平凡な計算検査で、そのうち一つが共有設定を静かに変える。最後のテストは税込みの合計を検査する。

CONFIG = {"tax_rate": 0.10, "currency": "KRW"}

    def test_09_tax_exempt_customer(self):
        # 犯人: 免税の検査をしようと税率を変えて戻さない
        CONFIG["tax_rate"] = 0.0
        self.assertEqual(CONFIG["tax_rate"], 0.0)

    def test_zz_total_includes_tax(self):
        # 被害者: 一つで置けば完全に正しい
        self.assertAlmostEqual(10000 * (1 + CONFIG["tax_rate"]), 11000.0)

では犯人を知らないことにして手順どおり絞る。試行ごとに新しいプロセスだ。

subprocess runs used     : 7
brute force would need   : 16 (one run per candidate)

7回で絞れた。一つずつ入れてみる総当たりなら16回だ。候補が増えるほど差は開く。候補が1,000個なら総当たりは1,000回だが、この手順は二十回ほどで済む。

  • 0段階を飛ばさないこと。「前半全体 + 被害者 = 赤」と「被害者単独 = 緑」が両方成り立って初めて順序依存だ。被害者が単独でも赤ならただの壊れたテストである
  • 試行ごとに新しいプロセスで。同じプロセスで続けて回すと試行同士が汚し合い判定がひっくり返る
  • 前後どちらの半分も赤でなければ犯人が二つ以上だ。二つのテストが合わさって条件が作られる場合である。このときは半分ずつ取り除きながら絞る
  • 見つけた最小再現ペアはそのまま回帰テストとして残す。この二つをこの順序で回す専用テストを作っておけば同じ事故がもう入り込めない
  • 直す場所は犯人の側だ。被害者に防御コードを入れるのは応急処置である

8. 分離実行が作る錯覚

「自分の環境では通る」の構造をそのまま再現してみよう。さきほどの17個の例で被害者だけを回す。

zz_total_includes_tax  単独実行             GREEN
17個すべて(名前順)                        RED

これがすべてだ。開発者が失敗ログを見てそのテスト名をコピーし手元で回せば必ず緑が出る。だから「環境のせい」という結論へ漏れ、再実行ボタンで先へ進む。

ところが先の四つの例で同じことをすると結果が違う。

a_open_connection                PASS
b_query_uses_connection          FAIL
c_registry_has_one_entry         FAIL
d_close_all                      PASS

ここではbとcが単独でも失敗した。この差は診断で非常に重要だ。順序依存には二種類ある。

区分単独実行全体実行性格発見の難度
先行依存型失敗順序により合格そもそも自立したテストではない。前のテストを準備段階として使っている低い。単独で回せばすぐ表に出る
汚染被害型合格順序により失敗テスト自体は正しい。前のテストが残した状態を踏んだだけだ高い。「自分の環境では通る」はここから来る

実務で時間を食うのは下の行だ。単独実行が通ることは無事である証拠ではなく、むしろ汚染被害型だという症状である。だから分離実行は診断の出発点でしかなく、結論にはなりえない。

9. 無作為順序と種の固定

順序が入力なら答えは明らかだ。入力を複数入れてみることである。ただし無作為をそのまま点けてはいけない。再現できない赤は診断できないからだ。種を固定すれば無作為と再現を同時に得られる。

seeds tried : 1..40   (order = random.Random(seed).shuffle)
green seeds : 10  -> [1, 3, 9, 11, 12, 13, 17, 26, 27, 33]
red   seeds : 30  -> [2, 4, 5, 6, 7, 8, 10, 14, 15, 16, 18, 19] ...

40個の種のうち30個が赤だった。では一つ選んで固定する。この記事で使う固定種は20260731だ。同じ種を入れれば誰でも同じ順序を得る。

$ python ci_shuffle.py 20260731
==============================================================
TEST ORDER SEED : 20260731      replay with: ci_shuffle.py 20260731
==============================================================
order : c -> d -> b -> a
FAILED with seed 20260731 -- rerun that seed to get the same order
   red: test_c_registry_has_one_entry
   red: test_b_query_uses_connection

$ python ci_shuffle.py 20260731          # 同じ種でもう一度
order : c -> d -> b -> a
FAILED with seed 20260731 -- rerun that seed to get the same order
   red: test_c_registry_has_one_entry
   red: test_b_query_uses_connection

二度の実行が順序も結果も完全に同じだ。これが無作為順序を実務で使えるものにする唯一の条件である。

  • 失敗ログの一番上に種と再実行コマンドを並べて出す。ログを受け取った人がその一行をコピーしてそのまま再現できねばならない
  • 種は実行時刻ではなく乱数から取る。時刻由来だと同じ分に回した二つの実行が同じ順序になり探索範囲が狭まる
  • Pythonの標準ライブラリだけで足りる。名前の一覧を受け取り種を固定して混ぜ、その順序でスイートを組み立てればよい
  • pytestの生態系には順序を混ぜるプラグインがあり、登録を切る選択肢も併せて提供されている。ただしこの環境にpytestがなく直接確かめていない

10. 戻す規則 - フィクスチャの設計

次は直す側だ。先の四つのテストを表明はそのままにフィクスチャだけ変えた。

class SessionTestsFixed(unittest.TestCase):
    def setUp(self):
        # 1. 引き継いだ状態を使わず、分かっている状態に到着する
        store.CONNECTIONS.clear()
        # 2. 戻しを先に登録する。テストが途中で落ちても実行される
        self.addCleanup(store.CONNECTIONS.clear)

    def given_open_connection(self):
        store.CONNECTIONS["main"] = "pg://demo"      # 必要な前提は自分で作る

    def test_b_query_uses_connection(self):
        self.given_open_connection()
        self.assertEqual(store.CONNECTIONS["main"], "pg://demo")

    def test_c_registry_has_one_entry(self):
        self.given_open_connection()
        self.assertEqual(len(store.CONNECTIONS), 1)

変えたのは二つだけだ。到着時点で状態を初期化し、必要な前提を自分で作る。結果を見よう。

  green : 24
  red   : 0  []
  pass rate : 24/24 = 100%

also run each test alone:
  a                          PASS
  b                          PASS

4/24から24/24になった。単独実行もすべて通る。五つの原因の型にも同じやり方を適用して確かめた。

case 1 fixed  global: reset in setUp, undo with addCleanup          order=rev  ==> ALL PASS
case 2 fixed  class attr: move the mutable default into __init__    order=fwd  ==> ALL PASS
case 2 fixed  class attr: move the mutable default into __init__    order=rev  ==> ALL PASS

case 4 fixed  temp files: a per-test directory that cleans itself   order=fwd  ==> ALL PASS

case 5 fixed  monkeypatch: register the restore before you patch    order=fwd  ==> ALL PASS
case 5 fixed  monkeypatch: register the restore before you patch    order=rev  ==> ALL PASS

10.1 八つの規則

  • 準備を他人任せにしない。必要な前提はそのテストが自分で作る。これ一つで順序依存の大半が消える
  • setUpは「分かっている状態に到着する」ためのもので、引き継いだ状態を確認する場所ではない
  • 戻しはパッチより先に登録する。テスト本体が途中で例外に切られても復元が走らねばならない
  • 後始末は後から登録したものが先に実行される。資源は取得と逆の順で返されるので依存関係が自然に守られる
  • 後始末をテスト本体の末尾に置かない。表明が失敗するとその行まで届かない。これが「一つ壊れたら十個続けて壊れた」の正体だ
  • キャッシュも全域変数だ。設定を戻したならキャッシュも消す
  • 一時ファイルはテストごとに新しく作り自分で消える形にする。決め打ちの経路を共有しない
  • クラス単位のフィクスチャは既定ではない。速度上どうしても必要なときだけ、そして読み取り専用で使う

10.2 共有してよいものといけないもの

共有してよいもの共有してはいけないもの
不変の定数、凍結した設定値辞書・リスト・集合などの可変コンテナ
純粋関数キャッシュが付いた関数
読み取り専用のフィクスチャデータ書き込みが起きるデータベース・ファイル
テストごとに作る一時ディレクトリ固定経路の作業ディレクトリ
テストクラス内の補助メソッドクラス属性に置いた可変の既定値
事前計算した値の複製その値そのものへの参照

判定基準は一つに縮められる。テストがそれに書き込むか。書き込むなら共有しない。読むだけなら共有してよいが、その「読むだけ」が本当に読むだけかは確かめねばならない。リストを並べ替えるのも、辞書を照会しながら既定値を埋めるのも書き込みだ。

11. CIに何を仕込むか

ここまでの実行をパイプラインに移すとこうなる。

  • 本線は固定順序にする。コミットごとに順序が揺れると赤の原因がコードか順序かを区別できない
  • 無作為順序は別のジョブに分け種を出力する。このジョブが赤なら「順序依存がある」の意味で、本線が赤なら「コードが間違っている」の意味だ。信号が混ざらない
  • 夜間ジョブに逆順実行を一本入れる。無作為より安く、この記事で見たとおり検出力が相当ある。決定論的なので再現も自動だ
  • 新しく見つけた最小再現ペアは専用テストとして固定する。その二つをその順序で回すテストを残せば同じ事故が再び入れない
  • 実行後に一時ディレクトリの残留物を検査する段階を入れる。4.4の型はこれ一つで大半が捕まる
  • 並列実行を点ける前に順序依存から消す。並列は順序をさらに揺らすだけでなく同時接近まで加える。順序の問題を抱えて並列へ行くと原因が二重になる

導入順の提案。順序の無作為化を急に点けると赤が山ほど降り、チームがそのジョブを切ってしまう結末がよくある。逆順実行を一本から始めることを勧める。決定論的なので再現が容易で、出てきた赤を一つずつ最小再現ペアに絞って直せばよい。それが片付いてから無作為を点ける。

12. 点検リスト

  • 追加したテストを単独で回した
  • 順序を逆にして一度回した
  • 無作為順序を種を固定して最低一度は回した
  • 実行後、一時ディレクトリに残ったファイルがない
  • モンキーパッチごとに復元が登録されている
  • キャッシュを使うコードのフィクスチャにキャッシュ消去が入っている
  • クラス属性に可変の既定値がない
  • どのテストも他のテストの名前や順番を前提にしていない
  • 後始末が本体の末尾ではなくフィクスチャにある
  • CIログに順序の種が出力される

12.1 やってはいけないこと

  • 落ちたテストにまず防御コードを入れる - 被害者を直して犯人を逃がす
  • テスト名に番号を振って順序を固定する - 依存を消すのではなく隠すことだ。しかも道具が名前順で回らなければそれすら効かない
  • 赤を再実行でやり過ごす - 順序が変わってたまたま緑になっただけだ
  • 無作為順序を種なしで点ける - 再現できなければ診断もできない
  • 「自分の環境では通る」で止まる - 8節で見たとおり単独合格は証拠ではなく症状だ
  • 速度を理由に共有フィクスチャを既定にする - 遅いテストより信用できないテストのほうが高くつく
  • 順序依存を抱えたまま並列実行を点ける

13. まとめ

この記事で実行して確かめたことを再び集めるとこうなる。

  • 共有状態を使うテスト4つの24通りの並びのうち緑は4つだった。合格率17パーセントで、しかも道具の既定の順序がその4つのうちの一つだった
  • 既定の実行順序は道具ごとに違う。測定したunittestは名前順、node:testは定義順だった。同じ論理のテストが一方で全部通り、もう一方で落ちた
  • 状態が残る場所は五つで、一時ファイルだけはプロセスの境界を越える
  • 赤くなったテストは共有状態を一文字も変えていなかった。犯人は緑だった
  • 候補16個から7回で最小再現ペアに絞れた
  • 被害者を単独で回すと通った。それが「自分の環境では通る」の正体だ
  • 種20260731を固定すると順序も失敗も完全に再現された
  • 表明はそのままにフィクスチャだけ直したら24/24が通った

結論は最初に立てた論旨のままだ。順序依存は「分離を怠った」という道徳的な欠陥ではなく、検証されていない入力がもう一つあるという事実である。その入力の名が順序だ。

だから最後の問いが変わる。「このテストは通るか」ではなく「どの順序で通るか」だ。逆にして一度回すのに数秒あれば足り、その数秒が月曜の朝の赤を今ここへ引き寄せる。

# テスト順序依存チェックリスト

テストの間に残る状態があれば、**順序がそのまま入力になる**。
そのとき合格は「正しい」ではなく「この順序では正しい」になる。

---

## 0. 30秒の判定

| 問い | はい | いいえ |
|---|---|---|
| そのテストを単独で回すと通るか | **順序依存で確定**（1節へ） | 本体の欠陥、または先行テストへの依存 |
| 順序を逆にすると別のテストが落ちるか | **順序依存で確定** | 別の原因 |
| 落ちたテスト自身が共有状態を書き換えるか | そのテストも容疑者 | **犯人は前にいる** |
| プロセスを立て直しても再現するか | ファイルやDBなど**プロセス外**の状態 | プロセス内メモリの状態 |

要点は一つ。**落ちたテストはたいてい犯人ではなく被害者だ。**

---

## 1. 原因の型と見分け方

| 型 | どこに残るか | 典型的な症状 | 確認方法 | 戻し方 |
|---|---|---|---|---|
| モジュール水準のグローバル変数 | 読み込まれたモジュールオブジェクト | 前のテストが入れた値を後のテストが読んで通る | 各テストの前後でモジュール変数を出力して比べる | setUpで初期化し、addCleanupで復元を登録 |
| クラス属性 | クラスオブジェクトそのもの | 新しく作ったインスタンスに以前の値が入っている | インスタンス属性かクラス属性かを確認する | 可変の既定値をコンストラクタの中へ移す |
| キャッシュ・メモ化 | 関数に付いたキャッシュ | **先に回ったテストが答えを確定させ**、残りが食い違う | キャッシュ統計やヒット数を出力する | setUpでキャッシュを消す。キャッシュも全域変数として扱う |
| 一時ファイル・ディレクトリ | ファイルシステム | **プロセスを立て直しても再現する** | 実行前後でディレクトリ一覧を比べる | テストごとに一時ディレクトリを作り、自動で消す |
| 戻していないモンキーパッチ | パッチされたモジュール属性 | 時刻・乱数・通信が見当違いの値を返す | 現在の属性を元の値と比べる | **パッチの前に復元を先に登録する** |

### 型ごとの方向感覚

- グローバル・キャッシュ・モンキーパッチ: たいてい**前が後を汚す**
- クラス属性: 累積するため、**既定の順序で早めに落ちる**ことが多い
- 一時ファイル: **前回の実行が今回を汚す**。プロセスの境界を越える
- キャッシュに**「無い」という結果**が入ると、後で正しくデータを入れたテストのほうが落ちる

---

## 2. 最小再現ペアの見つけ方

目標は「Aの次にBを回すと壊れる」のAを特定すること。

### 手順

1. **まず両端を固定する**
   - 前半全体と被害者を合わせて赤になることを確認する
   - 被害者を単独で回すと緑になることを確認する
   - 両方が成り立って初めて順序依存だ
2. **前に置く集合を半分に切る**
   - 前半と被害者を回す
   - 赤なら前半を採用し、緑なら後半を採用する
3. **一つになるまで手順2を繰り返す**
4. 残った一つが**犯人**であり、それと被害者が**最小再現ペア**だ

### 規則

- **試行ごとに新しいプロセスで回す。** そうしないと試行同士が汚し合う
- 前半も後半も単独では赤にならないなら、**犯人は二つ以上**だ。その場合は半分ずつ取り除いて絞る
- 候補がN個なら、およそ**2かける log2(N) 回**で終わる。候補16個なら7回前後で、総当たりの16回より少ない

### 見つけた後

- 最小再現ペアを**そのまま回帰テストとして残す**
- 犯人の側を直す。被害者に防御コードを足すのは応急処置にすぎない

---

## 3. フィクスチャの規則

1. **準備を他人任せにしない。** 必要な前提はそのテスト自身が作る
2. **setUpは「分かっている状態に到着する」こと。** 引き継いだ状態をそのまま使わない
3. **復元はパッチより先に登録する。** テストが途中で落ちても復元が走るようにする
4. **後から登録した後始末が先に実行される。** 資源は取得と逆の順で返す
5. **クラス単位のフィクスチャは既定ではない。** 速度上どうしても必要なときだけ、読み取り専用で使う
6. **キャッシュも全域変数だ。** 設定を戻したならキャッシュも消す
7. **一時ファイルはテストごとに新しく、自分で消える形に。** 決め打ちのパスを共有しない
8. **後始末をテスト本体の末尾に置かない。** 失敗するとその行まで届かない

---

## 4. 共有してよいもの / いけないもの

| 共有してよいもの | 共有してはいけないもの |
|---|---|
| 不変の定数、凍結した設定値 | 辞書・リスト・集合などの**可変**コンテナ |
| 純粋関数 | キャッシュが付いた関数 |
| 読み取り専用のフィクスチャデータ | 書き込みが起きるデータベースやファイル |
| テストごとに作る一時ディレクトリ | 固定パスの作業ディレクトリ |
| テストクラス内の補助メソッド | クラス属性に置いた可変の既定値 |
| 事前計算した値の**複製** | その値**そのもの**への参照 |

判定基準は一つ。**テストがそれに書き込むか。** 書き込むなら共有しない。

---

## 5. CIに何を仕込むか

- 順序を**無作為に混ぜたうえで、種を出力する。** 種がなければ赤を再現できない
- 失敗ログの一番上に**種と再実行コマンド**を並べて出す
- 夜間ジョブに**逆順実行**を一本入れる。最も安く確実な検出法だ
- 本線のパイプラインは**固定順序**にし、無作為は別ジョブへ分ける。赤の原因がコードか順序かがすぐ分かる
- 新しく見つけた最小再現ペアは**専用テストとして固定する**
- 並列実行を有効にする前に順序依存を消す。並列は順序をさらに揺らす

---

## 6. 点検リスト

- [ ] 追加したテストを**単独で**回した
- [ ] 順序を**逆にして**一度回した
- [ ] 無作為順序を**種を固定して**最低一度は回した
- [ ] 実行後、一時ディレクトリに**残ったファイルがない**
- [ ] モンキーパッチごとに**復元が登録**されている
- [ ] キャッシュを使うコードのフィクスチャに**キャッシュ消去**が入っている
- [ ] クラス属性に**可変の既定値**がない
- [ ] どのテストも**他のテストの名前や順番**を前提にしていない
- [ ] 後始末が**本体の末尾ではなくフィクスチャ**にある
- [ ] CIログに**順序の種**が出力される

---

## 7. やってはいけないこと

- 落ちたテストに**まず防御コードを入れる** — 被害者を直して犯人を逃がす
- テスト名に**番号を振って順序を固定する** — 依存を消さずに隠すだけだ
- 赤を**再実行でやり過ごす** — 順序が変わってたまたま緑になっただけだ
- 無作為順序を**種なしで**有効にする — 再現できなければ診断もできない
- 「自分の環境では通る」で**止まる** — 単独実行で通るのは証拠ではなく症状だ
- 速度のために共有フィクスチャを**既定にする** — 遅いテストより信用できないテストのほうが高くつく
- 順序依存を直さないまま**並列実行を有効にする**

コピーしてメモアプリやAIツールにそのまま貼り付けてください。
