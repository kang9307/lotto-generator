先扔掉什么，决定了这门语言的本质 - 把 Python 解释器塞进 1,024 字节 C 源码所暴露的顺序

错误处理第一个消失，标准库第二，性能第三，而文法留到最后

2026-09-08 开发/基础设施

把预算压到极限，设计就会浮出水面。宽裕的时候，所有层次并排摆着，谁是核心谁是装饰根本分不出来。预算掉到几千字节以下，顺序就被强制出来了。有的东西先被砍，有的东西留到最后。那个顺序，就是这套系统对自身优先级的声明。

解释器特别适合做这个实验，因为它该有的层次几乎像教科书一样固定。词法分析、语法分析、求值、把名字和值连起来的环境，还有错误处理。一共五个。这五个不可能全部塞进 1,024 字节，于是哪个先被削、哪个后被削，就直接可观测了。

这里要谈的就是那个顺序。不是缩小体积的技巧清单，而是决定放弃什么的先后，以及什么条件会把这个顺序整个翻过来。

所有数字都带着条件。1,024 字节是一个 C 源文件的大小，构建是在 GCC 下指定 C89 标准并关闭警告的状态。MicroPython、Lua 和 QuickJS 的数字各自量的是不同的轴，彼此并不能直接比较。没有标明是哪根轴的体积数字，基本没有用处。

起因 - 1,024 字节到底是什么的大小

让我抓住这个角度的，是奥斯汀亨利在 2026 年 9 月 6 日发的一篇文章。标题是用 1024 字节做一个 Python 解释器，正文开头就把条件挂上了：不用宏、不用库的小花招，1,024 字节的 C 代码。这句话里已经装了三件事，只看介绍文的话三件都会漏掉。

第一，1,024 是 C 源文件的大小，不是编译产物。仓库里分别放着可读版和高尔夫版，高尔夫版正好 1,024 字节，可读版超过 4,800 字节。两个版本实现的是同一门语言，差别只在写法。

第二，这个数字并不自足。作者列出的省字节手法里，有一条是依赖编译器帮忙链接 libc。从源码里消失的字符输入输出代码并没有不见，只是搬到了另一份预算上。少了这个区分，1,024 字节就会被读成执行所需的全部。

第三，跑起来的并不是 Python。作者本人钉死了这一点：把整门语言塞进 1,024 字节不可能，于是把目标重新定为做出看起来像 Python 的东西。他举的依据是 def、冒号、缩进和不带括号的条件。也就是说，文法的外形从一开始就是靶子。

构建条件同样是体积的一部分。仓库给出的命令是这样的。

gcc-16 -std=gnu89 -w python1024.c   # 退回 C89 并关掉警告
./a.out < fizzbuzz.py               # 要执行的程序从标准输入进来
wc python1024.c                     # 仓库给出的体积确认方式

-std=gnu89 为什么必要，后面还会再出现。高尔夫手法里有几条依赖 C89 的隐式 int 声明和隐式返回类型。-w 就是用来关掉随之而来的一堆警告的开关。仓库注明用 GCC 而不是 Clang，意思是同一份源码在所有编译器上并不会给出同样的结果。

归拢起来是这样：1,024 字节，是在特定编译器和特定标准之下、在 libc 会被链接进来的前提之上，执行一个形似 Python 的文法子集的一个 C 源文件的大小。不带这些条件、只说 1,024 字节能跑 Python，会在四个地方出错。

解释器最少要有的五层

不管实现风格如何，解释器都要干五件事。先把每一件压到极限之后还剩什么点出来，后面那份清单读起来才是地图而不是罗列。

  • 词法分析 - 把字符流切成有意义的单位。压到极限，一个字符就是一个词法单元。把名字长度上限锁死为一，这一层就整个消失。
  • 语法分析 - 判断词法单元的排列是否合乎文法，并构造结构。压到极限就不造结构，边读边算。递归下降解析器只要返回值，就不需要树。
  • 求值 - 把结构变成实际行为。这一层能削的余地最少。没有它，那东西就不是解释器而是文法检查器。
  • 环境 - 把名字和值连起来。压到极限就是一个数组。名字只有一个字符时，这个字符的编码值就是数组下标。
  • 错误处理 - 抓住违反规则的输入并报告出来。压到极限就是 0 字节。五层里唯一能被完全抹掉的一层。

最后一条是关键。另外四层再怎么压都会剩下点什么。求值为 0 就跑不起来，环境为 0 就没有变量，语法分析为 0 就不知道要算什么。只有错误处理能一路走到 0。所以它第一个走。

算术加、减、乘、取余，有优先级，一元符号只在表达式开头包含除法和幂运算在内的完整运算符集合

从上往下读这张表，会看到砍的程度并不均匀。算术、循环和函数保住了形状。名字、真假和代码块形状还在，但保证没了。错误则整个不存在。

有意思的是循环的 else。原文的支持清单里有挂在 while 和 for 上的 else，而同一份清单里没有 break。在 Python 参考里，else 子句的全部含义就是只有没被 break 跳出时才执行。没有 break，else 就永远执行。文法留下来了，这条文法存在的理由没有留下来。

被先扔掉的东西的顺序

这里是全文的中心。预算收缩时各层消失的顺序是有规律的，而这个规律就是对正常路径的贡献。

次序被扔掉的对正确输入的影响换来的损失1,024 字节版的状态
1错误处理与诊断信息完全没有错误输入下的行为变成未定义完全缺席
2标准库本来不用就没有程序能做的事情的宽度只剩一个 print
3性能与中间表示结果相同，时间变长重复的代价和静态分析的可能没有词法单元也没有树
4名字长度与命名空间把名字缩短就没有规模、可读性与作用域单个小写字母，无隔离
5挂在文法上的数量限制把式子拆开就没有表达力比较每个表达式一次
6文法的形状它就不再是那门语言身份没有动

对正常路径没有贡献的那一层先走

错误处理在正确的程序里一次都不会执行。删掉它，正常程序照跑不误。这是它排第一的第一个理由。

第二个理由是物理性的。诊断的实体是字符串，而字符串会原样吃掉预算。逻辑可以压缩，消息不能。一句二十七个字符的提示就是 1,024 字节预算的百分之二点六。把整个预算全填成提示语，上限也就三十八行。代码高尔夫的任何手法都翻不过这堵墙。

代价必须说准确。删掉错误处理，不是错误输入什么都不发生，而是错误输入什么都可能发生。原文也写明，这个实现建立在代码是正确的这一强假设之上。关键字识别就是例子。

if (ch == 'w' || ch == 'i' || ch == 'f') {
    int keyword = ch;
    int loop_var = 0;

    if (keyword == 'f') {        /* "for K in range(N):" 这种形状 */
        pos += 2;                /* 跳过 "or"                    */
        loop_var = next();
        pos += 8;                /* 跳过 "inrange("              */
        vars[loop_var] = 0;
    } else if (keyword == 'w')
        pos += 4;                /* 跳过 "hile"                  */
    else
        pos += 1;                /* 跳过 "if" 里的 "f"           */

只看第一个字符，剩下的是数着跳过去的。那里到底写没写 for，根本不检查。写成 fog 也走同一条路。这就是错误处理 0 字节的实际样子。

处在语言之外的东西排第二

标准库可以在不动文法的前提下抽走，这就是它排第二的理由。MicroPython 把自身范围写成包含 Python 标准库的一个小子集，却依然能自称 Python 3 的实现，靠的就是这个性质。把库缩小，语言的身份不会动摇。

1,024 字节版只留了一个 print，而且是只接受一个字符串字面量或一个整数表达式的形式。这里有个容易漏掉的细节：在 Python 里 print 和 range 都不是关键字。参考列出的三十五个保留字里两个都没有，它们是可以被重新绑定的名字。可是在名字被锁成一个字符的世界里，这个性质根本立不住。像前面的代码那样，range 变成了向前跳八个字符的固定模式。库函数硬化成了文法。

把同样结果算得更慢的那一层排第三

性能不是正确性的观测对象。变慢的程序照样给出正确答案，所以排第三。这里被砍掉的是整个编译阶段。原文写道 CPython 依次做词法化、构造语法树、分析、优化、发出字节码、解释执行，并说自己的实现不走这条流水线。

不过第三并非永远成立。在实时控制里，性能被放在第一位保住，反而是功能先被砍。决定顺序的不是层的性质，而是约束的种类。本文的顺序，是体积成为上限时的顺序。

文法为什么留到最后

文法排最后有两个理由。

第一，文法一消失，就没有理由把它叫做那门语言了。作者在 512 字节处改变方向的那一段说明了这点。他从加法式开始，加上赋值式，再加上条件语句，而对成果的判断是那是一台计算器而不是 Python 解释器。层都齐了，缺的是把它叫做 Python 的依据。于是目标从 512 挪到了 1,024。

第二，文法是实现唯一不花自己预算就能拿到的资产。因为它早就装在读者的脑子里了。看到 def、冒号和缩进，人就会把它读成 Python，而实现这一侧为制造这种认知一个字节都没花。反过来，错误信息不在任何人的脑子里，只能全额用字节支付。

而真正被砍掉的不是文法的形状，是挂在文法上的数量。Python 参考明确写着比较可以任意串联：与 C 不同，所有比较运算的优先级相同且低于算术运算，三个值排在一起的式子按数学里的习惯解释。1,024 字节版的支持清单把比较钉死为一个表达式里最多一次。运算符活了下来，只有串联死了。

作者写道，他差一点把比较式整个去掉，理由是真假判定可以代劳。与其问余数是不是零，不如把余数本身放进条件里。这是一笔删掉文法、用语义来偿还的交易，而这笔交易之所以做得成，是因为 Python 把整数的零当作假。决定文法能被丢掉多少的，是语义。

Python 解释器这句话覆盖的范围

实现之间相同到哪一层，可以分成三层：文法、语义、标准库。把这三层揉成一团，任何说法看上去都是真的。

层相同意味着什么1,024 字节版怎么验
文法同一份源文本被判为合乎文法只有子集，而且带着名字长度限制同一个文件两边是否都读得进去
语义同一份源码给出同样的结果在整数范围和作用域上分道扬镳用大数和函数内的变量试一次
标准库有同样的模块与内置函数只有一种形状的 print是否存在导入语句

原文在这三层里只主张文法的外形，而且还自己说明那是子集。把看起来像 Python 定为目标的那句话，就是这份主张的边界。作者没有模糊这条线。

线通常是在转述这一侧模糊掉的。1,024 字节的 Python 解释器这句话不区分三层。同样的陷阱在别的实现上也有。有的工具只是文法相同，有的工具想把语义也对齐结果和宿主语言撞车，还有的工具真正的争点是标准库搬过来了多少。把一门语言架在另一门语言之上会在哪里卡住，在谈 glojure 的那篇里另说；给编译型语言接上交互式执行时解释执行与编译执行分岔的位置，在谈 Go 解释器的那篇里。

单字母变量名连带删掉了什么

把名字锁成一个字符，表面上是体积优化，实际上是语义的变更。

先看得到的东西。Python 参考的名字规则把起始字符和后续字符分开，并且不设长度上限。要守住这条规则，就需要一个读名字的循环、一个装名字的缓冲区、一个比较名字的函数，还有一个哈希表或与之等价的结构，因为名字会有多少个是不确定的。把名字锁成一个字符，这些全都消失。

char src[999];       /* 去掉大部分空白后的整个程序 */
int  vars[256];      /* 符号表                     */
int  pos;            /* src 里下一个要读的字符位置 */
int  ch;             /* 当前看着的字符             */
int  line_start;     /* 当前这一行开始的位置       */

符号表就是 int vars[256] 这一行。查找是用字符编码值当下标的一次数组访问。没有哈希计算，没有冲突处理，没有字符串比较，也没有内存分配。

可是有东西跟着一起消失了。原文的支持清单写基于缩进的代码块时，在括号里补了一句没有作用域隔离。Python 的执行模型规定，在一个块里被绑定的名字就是那个块的局部变量。在一个全局数组就是全部的世界里，这条规定立不住。函数里用的名字和函数外用的名字看的是同一个格子。

更进一步，同一个格子里会放进不同种类的值。函数定义会把函数体的源码位置存进符号表，也就是说 vars[k] 可能是整数，也可能是代码位置，而且没有任何标记区分二者。这不是没有类型，而是没有地方去检查类型。整数和同一性比较纠缠在一起的地方在 CPython 里同样能吓人一跳，那段故事整理在谈整数缓存的那篇里。

没有词法单元也没有语法树 - 靠回卷重读来执行

把语法分析这一层缩小的最强办法，是根本不构造结构。递归下降解析器本来返回树节点，让它返回值而不是节点，整棵树就不需要了。

int parse_sum(void) {
    int value = parse_term();
    while (ch == '+' || ch == '-') {
        if (ch == '+')
            value = value + parse_term();
        else
            value = value - parse_term();
    }
    return value;
}

返回类型是 int。这一个词决定了整个设计。边读边算，所以没有中间表示，构造它、遍历它、释放它的代码也统统不存在。作为交换，源文本本身成了执行状态。

于是控制流就靠移动源码里的位置来实现。没有编译阶段就没有可跳的地址，取而代之的是把 pos 回卷。循环记住条件表达式的位置，函数体执行完就回到那个地方重新解析一遍。函数调用则保存调用点、跳到函数体的位置，函数体结束后再回到保存的位置。一个 pos 充当了程序计数器。

代码块的边界由缩进决定。

void run_block(int min_indent) {
    for (;;) {
        int indent = read_indent();

        if (ch == '\n')
            continue;

        if (indent < min_indent || ch == 0) {
            pos = line_start;
            return;
        }

这里藏着整个实现里最有意思的一次置换。Python 参考把缩进处理规定成一个栈：读文件第一行之前先压入一个 0，栈里的值从底到顶总是递增，缩进变小时那个值必须是栈上已经存在的某个值。最后这一条，正是抓住缩进不齐的代码的规则。

1,024 字节版根本不建这个栈。因为 run_block 会递归调用自己，C 的调用栈替它承担了这个角色。代码块的嵌套深度和递归深度一一对应，另设一个数据结构就没有理由。语言要求的数据结构，被宿主语言的数据结构偿还掉了。

可是栈一被丢掉，那个栈原本在做的校验也一起消失。没有已出现缩进值的清单，就没法问变小后的缩进是不是一个有效的层级。不齐的缩进不再是错误，而是径直挂到某个块上。这是全文最能一般化的一条观察。数据结构通常同时兼着校验。决定扔什么的时候，真正该数的不是那个结构占了多少字节，而是它一直在悄悄执行的那些检查。

小不是一件事

小这个词至少指向四根互不相同的轴。不标明是哪根轴的体积数字，没法用来比较。

轴量的是什么受压的场合怎么缩
源码字节人要读、要审计的量代码高尔夫，启动早期代码削标识符、空白，乃至结构本身
二进制体积存储与闪存的占用嵌入式固件，容器镜像在构建时排除功能，用链接器剔除
常驻内存运行时的内存用量单片机改数据结构和回收策略
依赖数量可移植性、供应链与审计成本沙箱，隔离网络不用外部库，自己实现

1,024 字节只量了第一根轴。而且它依赖 libc 被链接进来，所以在第二根和第四根轴上反而更差。从源码里抽走的东西由链接器补上。

看看别的实现用哪根轴说自己的体积，对比就很鲜明了。

  • MicroPython - 说它紧凑到能在 256k 代码空间和 16k 内存里装下并运行。它把第二根轴和第三根轴分开说明，因为在单片机上这是两种资源。
  • Lua - 说在 64 位 Linux 上，带全部标准库构建出来的解释器占 293K，库占 484K。源码大约三万两千行 C，发行压缩包 390K。它用构建产物而不是行数来讲体积。
  • QuickJS - 说只有几个 C 文件、没有外部依赖，一个简单程序的 x86 代码是 367 KiB。它把体积和依赖数量写在同一句话里。

这三个数字彼此不可比。轴不同，测量条件也不同。Lua 的 293K 标了平台，QuickJS 的 367 KiB 带着架构和目标程序，MicroPython 的 256k 是产物体积而不是源码体积。转述体积数字时，把条件摘掉，那个值就变成假的了。

真正需要做小的那些场合

有些场合，做小是要求而不是爱好。可是不同场合要的小并不一样，于是扔东西的顺序也会翻过来。

单片机 - 上限是内存

这里由第三根轴支配，而前面立的顺序恰好在一处被掀翻。MicroPython 把交互式提示符、任意精度整数、闭包、列表推导、生成器，还有异常处理当作自己的特性。1,024 字节版最先扔掉的那一层，MicroPython 挂在门面上。

理由很清楚。单片机上的程序跑在没人守着的地方。错误输入进来之后什么都可能发生的状态，在这里不被允许。要削的是别的东西，也就是它自己写明的把标准库缩成一个小子集。在端上装东西时内存究竟在哪里划出上限，在 ESP32-S3 上跑小模型的实测那篇里用数字整理过。

启动早期固件 - 上限唯一被规范钉死的场合

启动的第一阶段，是体积上限被写进规范的少数情形。这里连顺序本身都谈不上，问题不是扔掉什么，而是只留下哪一件。第一阶段自己不干活，只做到足以加载下一阶段就退场。

从这个位置能学到的是：扔掉功能比扔掉层次更狠。削掉一层，同一件事仍然在做，只是做得差；把功能挪走，这件事就整个换到别处去做了。这和前面 libc 的那段是同一个结构。

沙箱 - 小指的是能审计的量

在跑不可信代码的场合，小指的不是字节，而是人能读完的代码量。QuickJS 之所以把几个 C 文件和没有外部依赖摆在最前，原因就在这里。攻击面是随依赖图的宽度增长的，不是随源码体积增长的。

可是同一个页面还说它几乎完整支持 ES2025，并且能通过标准测试套件的接近百分之百。也就是说这里文法和语义都不扔，扔的只有第四根轴，依赖。在接收不可信代码的位置上，把语言规范缩成子集，那个子集的边界本身就会变成新的漏洞。

教学 - 小指的是一个人跟得下来的量

为教学而写的实现里，小指的是一天能读完的分量。这里扔掉的是性能和优化，反过来留得最大的是各个阶段的名字。词法分析、语法分析和求值都必须看得见。

对比非常戏剧化。代码高尔夫最先删掉词法单元和语法树，教学实现恰恰把这两个留得最大。同样叫做把东西做小，方向却完全相反。目的决定轴，轴决定顺序。

代码高尔夫和最小实现是两件事

原文里出现的省字节手法是这些。

  • 把变量名和函数名缩成一个字母
  • 依赖编译器会链接 libc 这个事实
  • 用全局变量代替临时变量
  • 利用全局变量会被零初始化的性质
  • 使用 C89 的隐式 int 声明和隐式返回类型
  • 把函数形参当作会保存在栈上的临时变量用
  • 直接写 ASCII 值而不用字符字面量
  • 使用三目运算符和逗号运算符
  • 用位运算替换逻辑运算

这九条有个共同点：没有一条改变语言的行为。全部都是写法层面的变换。所以 4,800 字节版和 1,024 字节版实现的是同一门语言。

/* 跳到行尾的函数 - 可读版 */
void skip_to_eol(void) {
  if (ch != 0 && ch != '\n') {
    next();
    skip_to_eol();
  }
}

/* 同一个函数的高尔夫版 */
Y(){c&&c-10&&Y(G());}

/* 前面出现过的 parse_sum 的高尔夫版 */
e(){for(z=t();c-43u<3;)y=44-c,z+=y*t();return z;}

反过来，单字母变量名、没有错误处理、没有作用域隔离，都不是高尔夫，是设计决定。写法怎么变，这三样都缩不下去。

分辨的方法很简单：把它还原回去，行为会不会变。不变就是高尔夫，变了就是设计。从 4,800 走到 1,024 是高尔夫，从 Python 走到形似 Python 是设计。把两件事用一个名字叫，两边的教训都留不下来。

而且高尔夫还带着构建条件这笔隐形成本。要依赖 C89 的隐式 int 就得把标准退回去，退回去就会冒出一堆警告，于是得关掉警告，而这个组合能通过的编译器是有限的。仓库注明用 GCC 而不是 Clang，原因就在这。转述体积数字时把这些条件摘掉，就复现不出来。换掉编译器后端会新增哪些账单，在谈基于 LLVM 的 Go 编译器那篇里从另一个角度戳过。

在自己代码里找可以不要的东西的顺序

把前面的顺序搬到自己的代码上，就是下面这样。这不是手法清单，而是提问的顺序。

位次候选判别的问题回退成本
1诊断、日志与统计删掉之后正常路径的结果是否相同低，重新打开即可
2没有人调用的功能支持清单和调用记录是否一致低，重新放回即可
3把同样结果算得更快的路径慢下来之后答案是否相同中，时间是能拿回来的
4名字、结构与泛化规模变大之后还撑不撑得住高，用读代码的人的时间支付
5接口与契约没有它还是同一个东西吗非常高，这就是身份本身

在实务里照这个顺序走的时候，有三条附注。

  • 第一位是做成可以关掉，而不是删掉。1,024 字节版把错误处理整个抹掉了，但那成立的前提是输入只有作者自己的一个文件。在别人要用的代码里做同样的决定，那不是高尔夫，是事故。
  • 第二位的判别靠记录而不是靠文档。支持清单几乎总是比现实更宽。只有和调用记录对上，才分得出哪个是已经死掉的功能。
  • 从第四位开始，回退成本陡然上升。把名字缩短，眼下确实少了，代价却要用之后每一个再读这段代码的人的时间来付。而且这笔付款不是一次就完的，这正是高尔夫和产品代码的差别。

还有一件事要在定顺序之前先写下来：会跟着一起被扔掉的东西的清单。删掉缩进栈，缩进校验会一起消失；把符号表换成数组，作用域会一起消失；删掉中间表示，静态分析的可能性会一起消失。三种情况里被删掉的都是一个数据结构，失去的却是两样。数字节之前，先数一数那个数据结构一直在悄悄做的事。

最后是把顺序翻过来的条件：由上限是被什么划出来的来决定。是内存就从数据结构下手，是审计对象就从依赖下手，是规范就从功能下手。只有当体积成为上限时，本文的顺序才原样成立。

没能确认的部分

  • 编译出的可执行文件的体积 - 原文和仓库里都没有。1,024 是源码体积，可执行文件的体积会随编译器、平台和链接方式变化。这也是本文没有谈二进制体积的原因。
  • 体积确认命令的准确判定 - 仓库写的是用 wc 看体积。这个命令会一起给出行数、词数和字节数三个值，所以单凭命令本身无法断定 1,024 指的是其中哪一个。正文沿用的是原文写明的字节数。
  • gcc-16 指向哪一个安装物 - 是哪个发行版的哪个包，换一个版本会不会得到同样的结果，仓库里没有写。
  • 注释的文法 - 支持清单里有注释支持，但它是否与 Python 参考规定的井号规则同形，仅凭原文的叙述分不出来。
  • CPython 流水线的官方描述 - Python 开发者指南的编译器文档，两次请求都只返回了重定向提示。正文里 CPython 各阶段的表述沿用的是原文作者的写法，而所有关于语言规则的表述都取自官方语言参考和标准库文档。
  • 执行速度的数字 - 回卷重读这种方式实际慢多少，原文里没有测量值。这里只陈述了每次迭代都要重新解析这一结构性事实。
  • 启动第一阶段在规范上的体积上限 - 广为引用的数字是有的，但没有和规范原文对照，所以没有写出数字。
