서론 - 멀티라인 플래그는 여러 줄을 지원하는 스위치가 아니다

정규식 엔진은 여러 줄이 든 문자열도 하나의 문자열로 받는다. 기본값에서 ^ 는 문자열의 시작에, $ 는 문자열의 끝(Python·.NET·Perl 은 끝 개행 앞도 포함)에 대응하고, 멀티라인 플래그(Python re.M, JavaScript m, .NET Multiline, Perl /m)가 켜지면 줄 경계에서도 대응한다. 그래서 플래그의 이름과 달리, Python 문서에 따르면 바뀌는 것은 「여러 줄을 처리하는 능력」이 아니라 두 앵커가 줄 경계를 인정하느냐 하나뿐이다. 점(.)이 줄바꿈을 넘는지는 별개 스위치(s)가 정한다(8절).

실무에서 걸리는 자리는 두 군데이다. 하나는 줄 끝 개행이 하나 붙은 입력에서 $ 가 어디에 대응하느냐이고, 다른 하나는 줄바꿈이 \n 이 아니라 \r\n(CRLF)일 때 $ 가 \r 앞에 대응하지 않는 경우이다. 두 가지 모두 도구마다 답이 다르다. 언어·도구 간 정규식 방언 전체는 어디서나 동작하는 정규표현식 글이, CR 바이트가 셸 스크립트와 git 에서 일으키는 문제는 CRLF 와 LF 글이 다루므로, 여기서는 앵커의 줄 경계 해석과 CRLF 입력의 결과만 같은 입력으로 비교한다.

다루는 질문은 다음과 같다.

  • 기본값에서 ^·$ 는 어디에 대응하고, 멀티라인 플래그는 그것을 어떻게 바꾸는가.
  • 입력 끝의 개행 앞과 뒤에서 $·^ 의 결과는 도구마다 같은가.
  • \A·\z·\Z 는 어느 도구에 있고, 멀티라인 플래그의 영향을 받는가.
  • grep·sed·awk 에서는 앵커가 이미 줄 기준인가.
  • CRLF 입력에서 $ 는 어디에 대응하고, 어떻게 대처하는가.

같은 입력 두 개 - LF 와 CRLF, 그리고 위치를 눈으로 보는 방법

모든 시연은 같은 두 입력을 쓴다. LF 입력은 a1\nb2\n(두 줄, 끝에 개행 하나), CRLF 입력은 a1\r\nb2\r\n 이다. 앵커가 대응한 위치를 보는 방법은 같다. ^ 가 대응한 자리에 < 를, $ 가 대응한 자리에 > 를 끼워 넣은 문자열을 이스케이프된 모양으로 출력한다. 예를 들어 'a1\nb2>\n>' 는 $ 가 b2 뒤와 문자열 맨 끝, 두 곳에 대응했다는 뜻이다. 아래 출력의 읽는 법은 세 가지이다.

  • $ 의 > 가 마지막 \n 앞에도 찍히는지(끝 개행 앞 대응).
  • ^ 의 < 가 마지막 \n 뒤의 빈 위치에도 찍히는지(끝 개행 뒤 대응).
  • CRLF 에서 > 가 \r 앞에 찍히는지, \r 와 \n 사이에 찍히는지.

Python re - 기본값의 $ 는 두 곳에 대응한다

import re, sys
                    print('Python', sys.version.split()[0])
                    LF = 'a1\nb2\n'
                    CRLF = 'a1\r\nb2\r\n'
                    def mark(pat, s, fl, ch):
                        return repr(re.sub(pat, ch, s, flags=fl))
                    for name, s in (('LF  ', LF), ('CRLF', CRLF)):
                        for label, fl in (('default     ', 0), ('re.MULTILINE', re.M)):
                            print(name, label, '^ ->', mark(r'^', s, fl, '<'), ' $ ->', mark(r'$', s, fl, '>'))
                    print(r'--- \A and \Z (Python 3.13)')
                    for name, s in (('LF  ', LF), ('CRLF', CRLF)):
                        print(name, r'\A ->', mark(r'\A', s, 0, '<'), r' \Z ->', mark(r'\Z', s, 0, '>'), r' \Z with re.M ->', mark(r'\Z', s, re.M, '>'))
                    print(r'--- \z in 3.13')
                    try:
                        re.compile(r'\z')
                    except re.error as e:
                        print('re.error:', e)
                    print('--- whole-line match')
                    for name, s in (('LF  ', LF), ('CRLF', CRLF)):
                        print(name, r'^\w\d$ re.M ->', re.findall(r'^\w\d$', s, re.M))
                        print(name, r'^\w\d\r?$ re.M ->', re.findall(r'^\w\d\r?$', s, re.M))
                        print(name, 'splitlines() ->', s.splitlines())
                    print('--- re.S is a different switch')
                    for fl, label in ((0, 'none'), (re.S, 're.S'), (re.M, 're.M'), (re.M | re.S, 're.M|re.S')):
                        print(label.ljust(10), re.findall(r'^a1.*$', LF, fl))
                    print('--- inline flag')
                    print(re.findall(r'(?m)^\w\d$', LF))
                    print('--- dot and CR')
                    print(re.findall(r'^.*$', CRLF, re.M))

Python 3.13 의 re.M 문서는 이렇게 적는다. 「When specified, the pattern character '^' matches at the beginning of the string and at the beginning of each line (immediately following each newline); and the pattern character '$' matches at the end of the string and at the end of each line (immediately preceding each newline). By default, '^' matches only at the beginning of the string, and '$' only at the end of the string and immediately before the newline (if any) at the end of the string.」 (출처: docs.python.org/3.13/library/re.html) 출력은 이 문장과 같은 모양이다.

  • LF 기본값: $ 는 'a1\nb2>\n>' 로 b2 뒤(끝 개행 앞)와 맨 끝에 대응했다. ^ 는 맨 앞 한 곳뿐이다.
  • LF 에서 re.MULTILINE: ^ 는 '<a1\n<b2\n<' 로 세 곳, 마지막 \n 뒤의 빈 위치에도 대응했다. $ 는 'a1>\nb2>\n>' 로 줄마다 하나씩과 맨 끝이다.
  • CRLF: $ 는 'a1\r>\nb2\r>\n>' 로 \r 와 \n 사이에 대응한다. \r 는 줄 안쪽의 문자로 취급된다.
  • 그래서 CRLF 에서 ^\w\d$(re.M)는 [], 즉 0건이다. ^\w\d\r?$ 는 두 줄에 맞지만 값이 'a1\r' 처럼 \r 를 포함한다. splitlines() 는 ['a1', 'b2'] 로 \r\n 을 한 줄 경계로 처리했다.
  • \A 와 \Z: \A 는 맨 앞 한 곳, \Z 는 'a1\nb2\n>' 로 맨 끝 한 곳이며, re.M 을 줘도 같다. 3.13 에서 \Z 는 끝 개행 앞에는 대응하지 않는다.
  • \z 는 3.13 에서 re.error: bad escape \z 이다. 3.14 이후 판 문서는 \z 를 「Added in version 3.14」 로, \Z 를 「The same as \z. For compatibility with old Python versions.」 로 적는다(docs.python.org/3/library/re.html 의 3.14 이후 판 표기).

MDN 의 입력 경계 단언 문서는 이렇게 적는다. 「If the m flag is set, ^ also matches if the character to the left is a line terminator character, and $ also matches if the character to the right is a line terminator.」 (출처: developer.mozilla.org 의 Input boundary assertion 문서) 또한 같은 문서의 노트는 「To match the start and end of the entire string in m mode, use the buffer boundary assertions \A, \z, and \Z.」 라고 적는다. 출력은 다음과 같다.

  • LF 기본값: $ 는 "a1\nb2\n>" 로 맨 끝 한 곳뿐이다. Python 과 달리 끝 개행 앞에는 대응하지 않았다.
  • LF 의 m 플래그: Python 과 같은 모양이다. ^ 는 마지막 개행 뒤의 빈 위치에도 대응한다("<a1\n<b2\n<").
  • CRLF 의 m 플래그: ^ 는 "<a1\r<\n<b2\r<\n<" 로 \r 와 \n 사이에도 대응하고, $ 는 "a1>\r>\nb2>\r>\n>" 로 \r 앞과 \n 앞 양쪽에 대응했다. \r 가 줄 끝 문자로 취급된다.
  • 그 결과 CRLF 에서도 /^\w\d$/gm 은 ["a1","b2"] 로 두 줄에 맞았다. 반면 /^.*$/gm 은 ["a1","","b2","",""] 로 빈 문자열이 끼어든다. 점은 줄 끝 문자인 \r 를 넘지 못했고, \r 와 \n 사이의 위치에서 빈 줄 하나가 따로 대응하는 것으로 나온다.
  • m 플래그의 줄 끝 문자는 \n 만이 아니다. \u2028 과 \r 뒤에서는 ^ 가 대응했고("<a<LS><b", "<a\r<b") 세로 탭 뒤에서는 대응하지 않았다("<a<VT>b").
  • \A: 이 Node 에서 u 플래그 없이는 문자 A 로 취급되어 'Aa1\n' 에 맞았고(false true 출력의 둘째 값), u 플래그를 주면 SyntaxError: Invalid regular expression: /\Aa1/u: Invalid escape 였다. MDN 의 노트와 달리 이 Node v22.16.0 에서는 \A 가 버퍼 경계 단언으로 동작하지 않았다.

Microsoft Learn 의 앵커 문서는 $ 의 CRLF 사정을 직접 적는다. 「Note that $ is satisfied at \n but not at \r\n (the combination of carriage return and newline characters, or CR/LF). To handle the CR/LF character combination, include \r?$ in the regular expression pattern. Note that \r?$ will include any \r in the match.」 또한 \Z 를 「The match must occur at the end of the string, or before \n at the end of the string」, \z 를 「The match must occur at the end of the string only」 로 정의하고, \Z 는 「identical to the $ anchor, except that \Z ignores the RegexOptions.Multiline option」 이라고 적는다. (출처: learn.microsoft.com 의 Anchors in regular expressions 문서)

  • 기본값은 Python 과 같다. $ 는 끝 개행 앞과 맨 끝 두 곳(a1\nb2>\n>), Multiline 에서 ^ 는 마지막 개행 뒤의 빈 위치까지 세 곳이다.
  • \Z 는 $ 와 같은 위치(a1\nb2>\n>)에 대응하고 Multiline 을 주어도 같은 결과이다. \z 는 맨 끝 한 곳이다. 문서의 정의와 출력이 일치한다.
  • CRLF: $ 는 a1\r>\nb2\r>\n> 로 \r 뒤에 대응한다. ^\w\d$(Multiline)는 0건, ^\w\d\r?$ 는 2건이며 값은 a1\r,b2\r 로 \r 를 포함했다. 문서의 「\r?$ will include any \r in the match」 와 같다.
  • 인라인 (?m) 은 PowerShell 의 -replace·-match 연산자에서도 같은 효과를 냈다(-match '(?m)^b2$' 는 LF 에서 True, CRLF 에서 False).
  • 문서는 .NET 11 부터 RegexOptions.AnyNewLine 으로 $ 가 \r\n 을 한 단위로 인식하게 할 수 있다고 적는다. 이 PC 의 5.1 에서 RegexOptions 열거형 이름 목록에는 그 항목이 없었다(출력 마지막 줄).

Perl - 같은 계열이지만 마지막 개행 뒤의 ^ 는 다르다

perlre 는 /m 을 「change "^" and "$" from matching the start of the string's first line and the end of its last line to matching the start and end of each line within the string」 으로, \Z 를 「Match only at end of string, or before newline at the end」, \z 를 「Match only at end of string」 으로 적는다.   • 기본값과 $·\Z·\z 는 Python·.NET 과 같은 위치에 대응했다(a1\nb2>\n>, \z 는 맨 끝).
  • 다른 점은 /m 에서의 ^ 이다. LF 에서 <a1\n<b2\n 으로 두 곳뿐이며, Python·JavaScript·.NET 이 대응한 마지막 개행 뒤의 빈 위치에는 대응하지 않았다.
  • CRLF 는 Python 과 같은 사정이다. ^(\w\d)$ 는 빈 목록, ^(\w\d)\r?$ 는 [a1,b2] 이다(값은 캡처 그룹이라 \r 를 포함하지 않는다).

grep·sed·awk - 이 PC 에서는 기본 모드가 CR 을 제거한다

아래 출력에서 grep·sed·awk 는 플래그 없이 ^·$ 를 줄마다 적용했다. 여러 줄을 한 덩어리로 합친 경우(sed 의 N 으로 두 줄을 합쳤을 때)에는 M 수정자를 주자 앵커가 줄 경계에 대응했다. 아래 스크립트는 mktemp -d 로 만든 임시 폴더 안에서만 파일을 만들고 끝에 지운다. od -c 는 CR 이 바이트로 남았는지를 보여 준다.

  • grep -c '^b2$' 는 LF 와 CRLF 파일 모두 1 이었다. 그런데 grep -U(바이너리 모드)로 읽으면 CRLF 에서는 0 이었고, 패턴에 CR 을 넣은 ^b2\r$ 는 CRLF 에서만 1 이었다. 이 PC 의 Git Bash grep 은 기본 모드에서 줄 끝의 CR 을 제거한 채 대응시킨다.
  • sed 는 기본 모드에서 출력 바이트에 CR 이 없었고(<a1>\n), sed -b 에서는 <a1\r>\n 으로 CR 앞에 > 가 붙었다. 즉 CR 이 남은 상태에서 $ 는 \r 뒤, \n 앞에 대응한다.
  • awk 도 같다. 기본 모드는 CR 을 제거했고, -v BINMODE=3 에서는 CR 이 남았다.
  • sed 'N;s/^/</g' 는 합친 두 줄(a1\nb2)의 맨 앞에만 < 를 붙였고, M 수정자를 주면 <a1\n<b2\n 으로 두 번째 줄 앞에도 붙었다. 합친 덩어리 안에서 ^ 가 줄 경계를 인정하는 스위치가 M 이다.
  • 레코드 구분자를 \001 로 바꿔 파일 전체를 한 레코드로 읽은 awk 는 ^ 와 $ 가 레코드의 맨 앞과 맨 끝 한 곳씩이었다(<a1\nb2\n>).

점(.)과 s 플래그 - 앵커와는 다른 스위치

네 언어의 출력 끝에는 같은 실험이 들어 있다. 패턴 ^a1.*$ 를 LF 입력(a1\nb2\n)에 적용하되 스위치 조합만 바꿨다. 결과는 도구마다 똑같다.

스위치결과의미
없음매치 없음(Python [], JavaScript null, Perl (no match)).* 가 첫 줄의 끝에서 멈추고 $ 는 맨 끝(또는 끝 개행 앞)에만 대응하므로 이어지지 않는다
s (점이 줄바꿈을 포함)a1\nb2\n 전체.* 가 개행을 넘어 끝까지 가서 맨 끝의 $ 에 닿는다
m (앵커가 줄 경계 인정)a1 만$ 가 첫 줄 끝에 대응하지만 점은 여전히 개행을 넘지 못한다
m 과 s 둘 다a1\nb2\n 전체점이 개행을 넘고 $ 는 줄 끝도 맨 끝도 인정하므로 가장 긴 쪽까지 간다
  • m 만 켜면 .* 는 첫 줄에서 끝나고, s 만 켜면 줄 경계가 아니라 문자열 맨 끝까지 간다. 두 스위치는 독립이다.
  • PowerShell 에서는 Singleline, Python 에서는 re.S 가 같은 역할을 하며 출력 결과도 같았다.
  • 그래서 「줄 단위 매치」가 목적이면 m, 「여러 줄에 걸친 한 매치」가 목적이면 s 를 쓰고, 둘 다 필요하면 둘 다 켠다.

  • 패턴 쪽(\r?$)은 값에 \r 가 딸려 오므로, 값을 그대로 비교하거나 저장하기 전에 잘라 내야 한다.

  • CR 이 어디서 들어오는지(파일 저장 방식, git 설정, 다운로드)는 CRLF 와 LF 글이 바이트 수준에서 다룬다.
  • 앵커 자체가 너비 0 의 단언이라는 점(MDN: 「Both are assertions, so they don't consume any characters」)은 룩어라운드와 같은 부류이며, 그 쪽의 쓰임은 룩어헤드 글에 있다.

확인하지 못한 것

  • 리눅스·macOS 에서의 grep·sed·awk 와 각 언어의 결과. 이 PC 의 grep·sed·awk 는 Git Bash 빌드이며, 기본 모드에서 CR 을 제거하는 동작이 다른 환경에도 같은지는 실행하지 못했다.
  • Python 3.14 이상, .NET 11 의 RegexOptions.AnyNewLine, MDN 노트가 언급한 \A·\z·\Z 버퍼 경계 단언이 동작하는 JavaScript 엔진. 이 PC 에는 해당 버전이 없다.
  • PowerShell 7(pwsh)과 .NET Core 계열의 결과. 이 PC 에서 실행한 .NET 정규식은 Windows PowerShell 5.1 의 것뿐이다.
  • PCRE·Go·Java·Ruby·POSIX 정규식의 앵커 동작과 유니코드 줄 구분자(\u0085 등) 전반. JavaScript 는 \u2028·\r·세로 탭만 시험했다.
  • 성능과 컴파일 옵션(예: .NET RegexOptions.Compiled)이 앵커 동작에 주는 영향, 그리고 re.M 과 re.A 등 다른 플래그의 조합.
