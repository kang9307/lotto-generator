引言：12到52，这之间发生了什么

OpenAI开发者网站的Codex用例页面，在2026年3月27日的互联网档案馆存档中列有12个用例，在5月24日的存档中列有52个。韩国开发者社区GeekNews也以「Codex大幅扩充用例合集」为题做了介绍，本文在那之后不久的2026年5月26日首次发布。

本文最初把这52个分成迁移、重构、测试、文档、运维自动化、学习6个编程类别，并把Rails 5→7迁移、i18n自动添加、GraphQL schema演进等列为新增项中值得关注的7个。2026-09-29逐条重新清点存档清单后发现，那7个并不在官方清单中，而新增的40个里有17个根本不是编程工作。本次更新按官方清单更正了这些内容，也删除了所有无法核实的第一人称使用经历和效果数字。

结论因此也随之改变。12→52的扩展与其说是「编程工具的用例更深入了」，不如说更接近「交给Codex的工作范围扩展到了开发之外」。本文讨论如何解读这份清单、从哪里开始尝试，以及如何把它转成适合团队的清单。

1. 12个的时期与52个的时点 - 有什么变化

3月存档中的12个，大多是开发者一想就能想到的任务：理解大型代码库(Understand large codebases)、评审拉取请求(Review pull requests faster)、升级OpenAI API集成(Upgrade your API integration)、反复攻克难题(Iterate on difficult problems)、从Slack发起编程任务(Kick off coding tasks from Slack)、响应式前端与Figma设计转代码、浏览器游戏、ChatGPT应用、iOS与macOS应用、生成幻灯片、数据分析报告。

5月存档的52个中，其中11个原样保留，iOS与macOS应用拆成了两个用例。新增的既有代码迁移(Run code migrations)、重构(Refactor your codebase)、保持文档最新(Keep documentation up-to-date)等开发工作，也有邮件整理(Manage your inbox)、会议准备与跟进、现金流预测(Forecast cash flow)、DCF估值模型(Model a DCF valuation)、预算与实际对比审查等业务工作。用于归类用例的合集(collections)当时有5个：游戏开发、原生开发、生产系统、效率与协作、Web开发。

与Goals的关系也需要更正。本文最初写的是「2025年底OpenAI把Codex重新定义为以Goals为单位的代理」，但/goal命令是在2026年4月30日的Codex CLI 0.128.0中以实验功能首次加入，5月21日在0.133.0中默认开启。在52个的时点，「Follow a goal」只是清单中的一个用例。Goals不是清单的上层概念，而是把清单中长任务做到底的方法之一。用法已整理在同日按官方文档更新的OpenAI Codex Goals 实战指南中。

OpenAI页面提供类别、团队、任务类型筛选，但一个用例带有多个标签，不适合用来计数。下表是本文把存档中的用例标题分成的5组。跨越边界的用例，按标题所指的主要任务只归入一处。

从表中可以看出两点。第一，开发方面新增的23个中，苹果原生增长最多，从1个增至8个：重构SwiftUI界面、添加App Intents、在模拟器中调试等平台专属工作各自成了用例。第二，办公辅助与数据财务方面新增的17个，完全不需要写代码。GeekNews的介绍文章也把这次扩展概括为延伸到工程、设计、数据、财务、运营、QA、销售团队。

本文最初给出的「迁移约12个、重构约10个、测试约8个」等数量与官方清单不符，已删除。在52个的时点，直接涉及代码迁移的用例是「Run code migrations」和「Upgrade your API integration」两个，而后者并非一般的API版本切换，而是把现有的OpenAI API集成升级到最新推荐模型和功能。

3. 新增40个中值得关注的7个

以下说明依据各用例卡片的官方摘要，难度和预计时间为2026-09-29的卡片标注。本节最初讨论的Rails 5→7迁移、微服务拆分、安全补丁自动化、性能回退排查、i18n自动添加、SQL索引推荐、GraphQL schema演进，在52个时点的清单和当前清单中都找不到对应标题，已删除。

3-1. 代码迁移 (Run code migrations)

把遗留系统映射到新技术栈，按里程碑推进迁移，并在每次切换前验证行为是否一致。卡片标注为高级、1小时。要点在于它没有点名任何框架版本，而是强调「受控的检查点」：不要一次性迁完，而要设置多个确认点。

3-2. 重构 (Refactor your codebase)

在不改变行为的前提下删除无用代码、拆开大文件、合并重复逻辑、更新过时的模式。官方摘要写明要以小而可评审的步骤推进。卡片标注为高级、1小时。

3-3. 追踪目标 (Follow a goal)

当任务需要Codex跨多轮朝着可验证的停止条件持续工作时，先设定一个目标。卡片标注为高级、长时间运行。与上面两个用例一样，搭配能用测试判定终点的工作时最有用。

3-4. 用电脑操作做应用QA (QA your app with Computer Use)

点击走查真实的产品流程，记录哪里出问题，最后形成缺陷报告。卡片标注为中级、30分钟。它不读代码，而是通过操作界面来检查，这是12个时期所没有的类型。

3-5. 依赖事件审计 (Audit dependency incidents)

把公开的软件包或供应链安全通告转成只读的审计计划，然后在不运行不可信代码的前提下检查清单文件、锁文件、CI工作流和脚本。卡片标注为高级、1小时。值得注意的是，这个安全用例被设计成「只读审计」，而不是「自动打补丁」。

3-6. 把工作流程保存为技能 (Save workflows as skills)

把行之有效的Codex对话、评审规则、测试命令、发布检查表、设计规范、仓库专用脚本，转成以后任务中可复用的技能。卡片标注为简单、5分钟。同类的新用例还有「Create a CLI Codex can use」，用于制作Codex在任何文件夹都能运行的CLI。

3-7. 编程之外的工作 (Manage your inbox · Forecast cash flow)

邮件整理用例会清理积压邮件、用用户的语气起草回复，并按设定周期检查新邮件(简单、10分钟)。现金流预测用例接收输入值和约束，生成可编辑的预测工作簿，并标出余额跌破安全线的时点以及造成资金压力的假设(中级、30分钟)。截至2026-09-29，这两张卡片的摘要都把执行者写成ChatGPT，说明这份清单已不再局限于编程工具之内。

4. Codex Use Cases vs Claude Code vs Cursor - 比较时要看什么

本节最初以使用经验给出了「新功能与架构讨论用Claude Code、大规模批量转换与运维自动化用Codex、日常修改用Cursor」的划分。由于缺乏官方资料或公开的对比测量支撑，本次更新删去了这一判定，改为保留比较时应按同一标准记录的三项。

  • 外部连接：52个中有不少以连接Slack、GitHub、邮件等工具为前提(「Kick off coding tasks from Slack」「Review GitHub pull requests」「Manage your inbox」)。要在其他工具上做同样的事，先确认该连接是否获得官方支持。
  • 长任务的停止条件：Codex用/goal设定目标，并在成功、暂停、预算上限、需要用户输入的阻塞等条件下停止。请用官方文档确认所比较的工具在什么条件下停止长任务、会报告什么，并填在同一张表里。
  • 验证方法：官方用例说明反复要求验证：代码迁移要在切换前确认行为一致，文档更新要在发布前设验证步骤，运维工作要核对日志和产出物。无论用哪款工具，结果是用测试、日志还是检查表确认的，比工具名称更重要。

把同一任务交给三款工具，并把上述三栏填好的笔记积累起来，团队的工具分工标准就会从这些笔记中得出。比较工具时常见的测量错误，另见AI编程衡量常犯的12个错误。

5. 可套用到中国SI环境的8项

以下8项并非OpenAI官方清单中的用例，而是把中国SI、运维、自有服务环境中常见的技术债务，对应到最接近的官方用例。本文最初附带的「实际应用过」这一说明无法核实，已删除。

  1. Spring 3.x → Spring Boot 3.x迁移：适合「Run code migrations」分阶段设检查点的方式。这是中国SI项目中积累最多的债务之一。
  2. JSP → Thymeleaf或React转换：把「Run code migrations」与「Build responsive front-end designs」结合来看。
  3. jQuery → 原生JS或React转换：遵循「Refactor your codebase」小步可评审的原则。
  4. Oracle PL/SQL → PostgreSQL函数迁移：属于「Run code migrations」。数据库迁移请以结果比对查询作为完成条件。
  5. JUnit 4 → JUnit 5迁移与补充测试：迁移用「Run code migrations」完成，补充的测试作为之后重构的安全网。
  6. 日志格式标准化与运维流程自动化：适合「Run verified operations」的方式，只运行已批准的脚本，并以日志和产出物确认结果。
  7. 遗留代码库的入职文档：「Understand large codebases」涵盖追踪请求流程、绘制陌生模块地图、指出下一步该读的文件。
  8. 文档与变更记录保持最新：「Keep documentation up-to-date」对比代码变更与PR上下文，起草文档更新，并在发布前设置验证步骤。

在官方用例中，没有找到声明可在内网隔离环境中直接使用的条目。在禁止使用外部AI服务的政企SI项目中，把上面的对应表仅用于任务设计更为现实。

6. 陷阱：为什么不能照单全收这52个

52这个数字同时也是产品宣传。本文最初写的「52个中实际用于工作的不到20个」这一个人测量已删除，改为列出从清单本身就能确认的陷阱。

  1. 不要以为都是开发用例：52个中有19个属于办公辅助、数据与财务(包括12个时期就有的生成幻灯片和数据分析报告)。开发团队估算引入效果时直接用总数，会造成高估。
  2. 「能做到」不等于「能用于生产」：官方用例本身也以代码迁移分阶段确认行为、重构以小的评审单位推进为前提。请遵循PoC → 小范围 → 全公司推广的顺序。
  3. 不要忽视难度标注：同一份清单里，卡片标注从简单、5分钟到高级、长时间运行不等。第一次尝试请选简单用例。
  4. 实测成本：长任务会累积用量，这也是Goals的停止条件中包含预算上限的原因。开始前先定好本次任务的上限。
  5. 法律与许可陷阱：先确认生成或转换代码的许可与著作权，以及内部代码、客户数据是否允许发送给外部模型。在中国的SI合同中尤其需要注意。

7. 开发者要建立的、自己的Use Case Library

与其原样接受OpenAI的清单，不如建立一份贴合团队工作方式的清单，这样更有用。步骤如下。

  1. 写下一周内重复的20项任务：写代码、重构、写文档、准备会议、写报告，全部列出。
  2. 为每项标注可委托程度：分为完全、部分、不可。标准是「结果能用什么来验证」。
  3. 从可完全委托的项目开始编写提示词模板：写明输入输出格式和验证步骤。像官方清单中的「Save workflows as skills」那样把模板保存为技能，下次任务就能复用。
  4. 每月回顾一次：效果好的模板继续打磨，不好的修改或删除。
  5. 与团队共享：把稳定下来的清单迁入团队Wiki，成为团队资产。

本文最初「6个月能积累20~30个」的预估缺乏依据，已删除。决定清单质量的不是积累了多少条，而是每一条是否写明了验证方法。

8. 2026下半年Codex演进预测 (当时的展望)

以下三段是2026年5月发布时的展望，每段末尾附上2026-09-29确认的结果。

第一，当时认为用例清单会再次增至80~100个，而增加的部分将是领域专属的工作。9月29日确认时卡片为105个，合集中新出现了商业运营、数据科学、教育、财务、生命科学、销售、安全。方向判断正确，数量超出了展望。

第二，当时认为一个代理写代码、另一个代理评审的多代理协作会成为官方用例。当前清单中没有找到以多代理协作为标题的用例。虽有「Set up a project teammate」和「Scan multiple repositories」，但它们是否涉及代理之间的分工，本次未作确认。

第三，当时认为会扩展到非编程领域。这一展望其实在发布时就已在发生：52个的时点已有19个办公辅助、数据与财务用例，而当前清单又增加了准备课堂材料(Create a classroom materials pack)、销售客户优先级排序(Prioritize accounts)、预算与日程规划(Plan a budget and schedule)等用例。

9. 后续经过 (2026-09-29确认)

  • 用例数量：2026-05-29存档为55个，2026-07-04存档为60个，2026-09-29确认时为105个。
  • 地址迁移：developers.openai.com/codex/use-cases以永久重定向(308)指向learn.chatgpt.com/use-cases。存档显示7月4日前仍可在原地址打开，自7月25日的存档起记录为重定向。
  • 页面性质：迁移后的页面标题为「Use cases」，简介文字是邀请读者浏览可以用ChatGPT完成的工作流程、团队和任务。卡片说明中的执行者也是Codex与ChatGPT混用。
  • 用例合集：从5个增至12个：商业运营、数据科学、教育、财务、游戏开发、生命科学、原生开发、生产系统、效率与协作、销售、安全、Web开发。
  • 筛选：有类别(工程、评估、前端、质量、科学、安全、iOS、移动、macOS)、工作流(自动化、数据、集成、知识工作)、团队和任务类型筛选。

本文第3节讨论的用例目前全部仍在清单中。Codex应用与ChatGPT桌面应用的关系以及/goal的用法，已整理在同日更新的Goals指南中。

10. 结论 + 本周可执行的3件事

12→52不只是条目的增加。但它的意义比本文最初写的「从编程助手到工程任务代理」更宽：新增的40个中有17个是开发之外的工作，而清单此后增至105个，并迁到了ChatGPT一侧的网站。开发者需要的不是总数，而是契合自己团队工作的几个用例，以及验证它们的方法。

从今天就能开始的3件事：

行动1 - 写下20项重复任务：本周内写下一周中重复的20项任务，并为每项附上一行可委托程度(完全/部分/不可)和验证方法。

行动2 - 从一个简单用例开始：把「Understand large codebases」或「Keep documentation up-to-date」这类卡片标注为简单的用例用到真实仓库上。从结果便于人工核对的工作开始更稳妥。

行动3 - 三款工具对比笔记：把同一任务交给Codex、Claude Code、Cursor，用一周时间积累填好第4节三栏(外部连接、停止条件、验证方法)的笔记。

52个，如今的105个，都只是起跑线。把这份清单转成团队自己的清单，比选择哪款工具留下的价值更久。
