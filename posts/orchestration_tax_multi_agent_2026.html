1. 서론 - 에이전트를 늘릴수록 느려지는 역설

2026년 5월 29일 news.hada.io 인기 글 5위에 "The Orchestration Tax"라는 토픽이 올라왔다. 핵심 주장은 단순하면서도 뼈아프다. 멀티 AI 에이전트를 도입하면 생산성이 올라갈 것 같지만, 에이전트를 관리하고 조정하는 데 드는 비용이 처리량 이득을 상당 부분 먹어 치운다는 것이다. 본인은 이 주장을 읽으면서 지난 1년 동안 본인 팀과 주변 팀에서 반복적으로 목격한 풍경이 떠올랐다. 에이전트를 다섯 개로 늘렸는데 어쩐 일인지 한 개로 돌릴 때보다 일이 더 안 끝났다.

이 역설은 새로운 게 아니다. 소프트웨어 공학에는 이미 브룩스의 법칙이 있다. "늦은 프로젝트에 인력을 추가하면 더 늦어진다." 사람을 늘리면 소통 경로가 제곱으로 늘어 회의·인수인계·충돌 조정 비용이 폭발하기 때문이다. 본인이 보기에 멀티 에이전트는 이 오래된 법칙을 AI 시대에 그대로 복제하고 있다. 에이전트는 회의에 지치지 않고 잠을 자지 않지만, 그들의 출력을 조정·검증·통합하는 부담은 고스란히 사람과 오케스트레이터에게 돌아온다.

이 글은 hada.io 토픽을 출발점 삼아 오케스트레이션 택스를 12개 챕터로 깊게 분해한다. 단순 소개가 아니라 본인이 실제로 멀티 에이전트 파이프라인을 운영하면서 겪은 비용 구조, 폭발 시나리오, 그리고 세금을 줄이는 구체적 전략을 정리한다. 결론부터 말하면 멀티 에이전트는 강력한 도구지만, 비용 구조를 모르고 무작정 늘리면 거의 확실하게 손해를 본다.

2. "Orchestration Tax"란 - 정의와 발생 지점

본인이 정의하는 오케스트레이션 택스는 이렇다. 여러 AI 에이전트를 함께 운영할 때, 에이전트 수가 늘어나는 만큼 자동으로 따라붙는 조정·검증·통합·모니터링 비용의 총합. 이 비용은 에이전트가 일을 잘하든 못하든 발생하며, 에이전트 수에 선형이 아니라 거의 제곱에 가깝게 늘어난다는 점이 핵심이다.

왜 제곱인가. 에이전트가 서로의 출력을 참고하거나 충돌을 조정해야 하는 순간, 소통 경로의 수는 n개 에이전트에 대해 n(n-1)/2로 늘어난다. 2개일 때는 1개의 경로지만, 5개일 때는 10개, 10개일 때는 45개다. 에이전트 수를 두 배로 늘리면 조정해야 할 관계는 네 배 가까이로 뛴다. 처리량 이득은 기껏해야 선형으로 늘어나는데 조정 비용은 제곱으로 늘어나니, 어느 지점을 넘어서면 순이득이 마이너스로 돌아선다.

오케스트레이션 택스가 발생하는 지점은 명확하다. 첫째 작업 분배 시점이다. 무슨 일을 누구에게 줄지 결정하는 데 사람의 판단이나 추가 LLM 호출이 든다. 둘째 중간 통신 시점이다. 에이전트 A의 출력이 에이전트 B의 입력이 될 때 포맷을 맞추고 의미를 검증해야 한다. 셋째 결과 통합 시점이다. 흩어진 산출물을 하나로 합치는 데 또 한 번 비용이 든다. 넷째 실패 복구 시점이다. 어느 에이전트가 틀렸는지 추적하고 재시도하는 비용이다. 이 네 지점이 오케스트레이션 택스의 청구서가 날아오는 곳이다.

3. 멀티 에이전트가 만드는 5가지 숨은 비용

본인이 운영 경험을 토대로 정리한 멀티 에이전트의 숨은 비용은 다섯 가지다. 토큰 비용처럼 청구서에 찍히는 게 아니라 시간과 주의력으로 빠져나가기 때문에 "숨은" 비용이다.

3-1) 컨텍스트 전환 비용

여러 에이전트가 각자 다른 맥락을 들고 있을 때, 한 에이전트의 결과를 다른 에이전트에 전달하려면 맥락을 다시 채워 넣어야 한다. 사람이 멀티태스킹할 때 작업을 바꿀 때마다 머리를 다시 데우는 것과 똑같다. 에이전트 간 핸드오프마다 시스템 프롬프트·이전 결과·제약 조건을 다시 주입해야 하고, 이 과정에서 토큰도 늘고 정보 손실도 생긴다.

3-2) 검증 부담

에이전트가 많아지면 검증할 출력도 많아진다. 단일 에이전트라면 결과 한 덩어리만 확인하면 되지만, 다섯 에이전트는 다섯 덩어리를 각각 확인해야 한다. 게다가 에이전트끼리 서로의 결과를 신뢰하고 다음 단계로 넘기면, 앞 단계의 오류가 뒤로 전파되어 어디서 틀렸는지 역추적하는 비용까지 추가된다. 본인 경험상 멀티 에이전트 운영 시간의 절반 이상이 검증에 쓰인다.

3-3) 충돌 조정 비용

두 에이전트가 같은 파일을 동시에 고치거나, 서로 모순되는 결론을 내거나, 같은 자원을 두고 경합하면 누군가 조정해야 한다. 사람 개발자 둘이 같은 코드를 동시에 건드릴 때의 머지 컨플릭트와 본질이 같다. 다만 에이전트는 자기들끼리 양보의 판단을 잘 못하기 때문에 조정 로직이나 사람이 끼어들어야 한다.

3-4) 결과 통합 비용

각 에이전트가 만든 부분을 하나의 완성품으로 합치는 비용이다. 부분의 합이 자동으로 전체가 되지 않는다. 톤·포맷·중복·누락을 맞춰야 하고, 종종 통합 자체를 위해 또 하나의 에이전트나 사람의 손이 필요하다. 본인은 이 단계가 가장 과소평가된 비용이라고 본다.

3-5) 모니터링 비용

여러 에이전트가 동시에 돌면 전체 흐름을 지켜보는 것 자체가 일이 된다. 어느 에이전트가 멈췄는지, 무한 루프에 빠졌는지, 비용이 폭주하는지 실시간으로 봐야 한다. 단일 에이전트라면 로그 한 줄기만 보면 되지만, 멀티 에이전트는 여러 줄기를 동시에 추적해야 하고, 이를 위한 관찰성 인프라 자체가 비용이다.

4. 단일 에이전트 vs 멀티 에이전트 - 언제 늘려야 하나

그렇다면 언제 멀티 에이전트가 정당화될까. 본인이 정리한 판단표는 다음과 같다.

판단 기준단일 에이전트 유리멀티 에이전트 유리
작업 분할성순차 의존이 강함독립 병렬 가능
맥락 결합도맥락이 강하게 얽힘하위 작업이 독립적

표를 한 문장으로 요약하면, 작업이 명확히 독립적이고 병렬화되며 결과 검증이 자동화될 때만 멀티 에이전트가 이득이다. 본인의 실전 기준은 더 단순하다. 멀티 에이전트로 얻는 병렬 이득이 3장에서 본 다섯 가지 조정 비용을 넘어설 것이라는 구체적 근거가 있을 때만 늘린다. 근거가 "왠지 더 빠를 것 같아서"라면 그건 늘리지 말라는 신호다.

5. Orchestration Tax가 폭발하는 5가지 시나리오

오케스트레이션 택스가 특히 가파르게 치솟는 다섯 가지 시나리오를 본인이 본 사례로 정리한다.

  • 에이전트끼리 자유 대화시킬 때 - 에이전트 A와 B를 직접 토론시키면 합의에 이르기까지 호출 수가 폭발하고, 종종 서로의 환각을 강화하며 무한 루프에 빠진다. 가장 비싼 안티패턴이다.
  • 역할 경계가 모호할 때 - 두 에이전트의 책임이 겹치면 같은 일을 중복으로 하거나 서로 떠넘긴다. 충돌 조정 비용이 끝없이 발생한다.
  • 중간 산출물 포맷이 제각각일 때 - 에이전트마다 출력 형식이 다르면 핸드오프마다 변환 비용이 든다. 표준 스키마가 없으면 통합 단계가 지옥이 된다.
  • 검증 없이 결과를 신뢰할 때 - 앞 에이전트의 오류가 검증 게이트 없이 뒤로 전파되면 마지막에 가서야 발견되고, 그때는 어디서 틀렸는지 역추적이 불가능에 가깝다.
  • 사람 개입 지점이 너무 많을 때 - 단계마다 사람의 승인이 필요하면 에이전트의 비동기 이점이 사라지고 사람이 병목이 된다. 자동화했다는 착각만 남는다.

다섯 시나리오의 공통점은 경계의 불명확함이다. 누가 무엇을 어떤 포맷으로 책임지는지가 흐릿할 때 오케스트레이션 택스가 폭발한다. 거꾸로 말하면 경계를 명확히 하는 것이 세금을 줄이는 가장 강력한 지렛대다.

6. 세금을 줄이는 7가지 전략

본인이 멀티 에이전트를 운영하면서 효과를 본 7가지 전략을 정리한다. 순서는 도입 우선순위 순이다.

6-1) 명확한 역할 분담

각 에이전트의 책임을 겹치지 않게 한 문장으로 정의한다. "기획 에이전트는 요구사항만 정리하고 코드는 만들지 않는다"처럼 명시적으로 못 박는다. 역할이 겹치지 않으면 충돌 조정 비용이 거의 사라진다.

6-2) 비동기 처리

독립적인 하위 작업은 동기적으로 줄 세우지 말고 비동기로 병렬 실행한다. 단 결과가 모이는 합류 지점(join point)을 명확히 두어, 한 에이전트가 늦어도 전체가 멈추지 않게 한다.

6-3) 자동 검증 게이트

에이전트의 출력은 사람이 보기 전에 자동 게이트를 통과시킨다. 테스트·린트·스키마 검증·룰 체크 등을 게이트로 두고, 통과한 산출물만 다음 단계로 넘긴다. 사람의 검증 부담을 급격히 줄이는 핵심 전략이다.

6-4) 결과 표준화

모든 에이전트가 같은 출력 스키마(JSON 등)를 따르게 강제한다. 핸드오프마다 변환할 필요가 없어지고 통합 단계가 단순해진다. 표준 스키마 하나가 통합 비용 절반을 날린다.

6-5) 관찰성 도구

모든 LLM 호출·도구 호출·중간 상태를 trace로 남긴다. LangSmith·Langfuse·Helicone 같은 도구로 어느 에이전트가 어디서 막혔는지 한눈에 본다. 모니터링 비용을 사람의 눈에서 대시보드로 옮기는 작업이다.

6-6) 단계적 확장

처음부터 다섯 에이전트로 시작하지 않는다. 단일 에이전트로 시작해 병목이 측정될 때만 하나씩 늘린다. 각 추가가 정말 순이득인지 데이터로 확인하고 넘어간다.

6-7) 인간 개입 지점 최소화

사람의 승인이 필요한 지점을 의도적으로 줄인다. 정말 위험한 단계(배포·결제·데이터 삭제)에만 사람을 두고 나머지는 자동 게이트에 맡긴다. 사람이 병목이 되는 순간 비동기의 이점이 모두 사라진다.

일곱 전략을 관통하는 원칙은 하나다. 에이전트끼리 직접 대화시키지 말고 표준 인터페이스를 통해 산출물만 주고받게 하라. 사람 조직에서 잘 작동하는 협업 원칙이 에이전트에도 그대로 적용된다.

7. 도구·프레임워크 비교 - LangGraph·CrewAI·AutoGen·Claude Code

오케스트레이션 비용을 다루는 대표 프레임워크 네 가지를 비교한다.

프레임워크주 언어오케스트레이션 모델강점오케스트레이션 택스
LangGraphPython/JS상태 그래프(상태 머신)복잡한 분기·재시도·체크포인트명시적 제어로 낮음
CrewAIPython역할 기반 크루빠른 역할 협업 프로토타입역할 모호 시 높음
AutoGen (MS)Python대화형 에이전트연구·실험·멀티턴 토론자유 대화 시 매우 높음
Claude Code 서브에이전트-위임형 서브에이전트코딩 작업 안전 위임·격리위임 경계 명확해 낮음

본인의 정리는 이렇다. LangGraph는 상태와 분기가 복잡한 워크플로에 강하다. 흐름을 명시적 그래프로 그리기 때문에 어디서 무엇을 하는지가 코드에 박혀 오케스트레이션 택스가 낮다. CrewAI는 역할 기반 협업을 빠르게 프로토타이핑할 때 좋지만 역할 경계가 흐리면 비용이 치솟는다. AutoGen은 연구·대화형 실험에 훌륭하나, 에이전트를 자유롭게 대화시키는 기본 패턴이 오케스트레이션 택스를 가장 키운다. Claude Code 서브에이전트는 메인 에이전트가 하위 작업을 격리된 서브에이전트에 위임하는 방식으로, 위임 경계가 명확해 코딩 작업에서 비용이 낮은 편이다.

본인의 권고는 단순하다. 작은 작업이면 프레임워크 없이 단일 에이전트로 시작하라. 조정 비용이 측정 가능할 만큼 커진 다음에야 LangGraph 같은 상태 머신 기반 도구로 옮겨라. 프레임워크는 문제를 해결하지 않고 문제를 구조화할 뿐이다.

8. 실무 측정 - 오케스트레이션 비용 추적법

줄이려면 먼저 재야 한다. 본인이 쓰는 오케스트레이션 비용 추적 지표는 다음과 같다.

  • 조정 호출 비율 - 전체 LLM 호출 중 실제 작업이 아니라 분배·검증·통합에 쓰인 호출의 비율. 이 비율이 30%를 넘으면 경고 신호다.
  • 핸드오프 횟수 - 작업 하나가 완료되기까지 에이전트 간 전달이 몇 번 일어났는가. 핸드오프마다 컨텍스트 전환 비용이 든다.
  • 재시도율 - 검증 실패로 다시 돌린 비율. 높으면 역할·프롬프트 경계가 흐리다는 뜻이다.
  • 사람 개입 시간 - 자동화했다는 작업에서 사람이 실제로 손댄 시간. 이게 줄지 않으면 자동화가 아니다.
  • 단일 대비 처리 시간 - 같은 작업을 단일 에이전트로 했을 때와 비교한 실제 소요 시간. 멀티가 더 느리면 즉시 단일로 회귀한다.

다음은 간단한 추적 의사코드다. 모든 호출에 태그를 달아 작업 호출과 조정 호출을 구분하는 것이 핵심이다.

# orchestration_cost.py - 조정 비용 추적 의사코드
from dataclasses import dataclass, field

@dataclass
class OrchestrationMetrics:
    work_calls: int = 0          # 실제 작업 호출
    coord_calls: int = 0         # 분배/검증/통합 호출
    handoffs: int = 0            # 에이전트 간 전달
    retries: int = 0             # 검증 실패 재시도
    human_seconds: float = 0.0   # 사람 개입 시간

    @property
    def coordination_ratio(self) -> float:
        total = self.work_calls + self.coord_calls
        return self.coord_calls / total if total else 0.0

    def warn_if_taxed(self):
        if self.coordination_ratio > 0.30:
            print(f"[WARN] 오케스트레이션 택스 과다: "
                  f"{self.coordination_ratio:.0%} 조정 호출")
        if self.retries > self.work_calls * 0.2:
            print("[WARN] 재시도율 과다 - 역할 경계 점검 필요")

m = OrchestrationMetrics()
# 각 LLM 호출 시점에 work_calls / coord_calls 중 하나를 증가시킨다
m.warn_if_taxed()

핵심은 조정 호출을 별도 태그로 분리해 가시화하는 것이다. 가시화되지 않은 비용은 줄일 수 없다. 본인은 이 한 가지 지표(조정 호출 비율)만 대시보드에 띄워도 팀의 의사결정이 크게 달라지는 것을 여러 번 봤다.

9. AI 에이전트 인프라 트렌드 - Mirage·Flue·CodeGraph 연속선

오케스트레이션 택스 논의는 갑자기 나온 게 아니라 2026년 에이전트 인프라 진화의 한 매듭이다. 최근 hada.io를 달군 토픽들을 연속선으로 보면 흐름이 또렷하다.

Mirage는 에이전트를 위한 통합 가상 파일시스템을 제안했다. 여러 에이전트가 같은 자원을 다룰 때의 충돌과 일관성 문제를 인프라 레이어에서 푼다. 이는 3장의 충돌 조정 비용을 인프라로 흡수하려는 시도다. Flue는 헤드리스 코딩 에이전트를 위한 TypeScript 샌드박스 프레임워크로, 에이전트 실행을 격리하고 워크플로를 코드로 정의한다. 이는 6장의 결과 표준화·관찰성 전략을 프레임워크 차원에서 제공한다. CodeGraph류의 코드 구조 그래프 도구는 에이전트가 코드베이스 맥락을 공유하는 비용, 즉 컨텍스트 전환 비용을 낮춘다.

세 흐름의 공통 메시지는 분명하다. 2026년 에이전트 인프라의 핵심 경쟁은 오케스트레이션 택스를 누가 가장 잘 흡수하느냐다. 개별 모델의 성능 경쟁은 이미 평준화 단계에 들어섰고, 이제 차별화는 여러 에이전트를 싸게 조정하는 인프라에서 나온다. 오케스트레이션 택스라는 개념이 5월 말 hada.io 상위에 오른 것 자체가 이 전환의 신호다.

10. 한국 개발 환경 적용

한국 개발 조직에 오케스트레이션 택스 개념을 적용할 때 고려할 세 가지가 있다.

첫째 소규모 팀 비중이 높다는 점이다. 한국 스타트업과 SI 현장은 1~5인 개발팀이 많다. 이런 환경에서 멀티 에이전트를 무리하게 도입하면 조정 인프라를 구축할 인력이 없어 오케스트레이션 택스를 사람이 손으로 떠안게 된다. 본인은 소규모 팀일수록 단일 에이전트에 충실하고, 정말 병렬이 필요한 야간 배치 같은 영역만 멀티로 분리하라고 권한다.

둘째 폐쇄망과 온프레미스 LLM이다. 금융·공공·통신은 외부 LLM 호출이 막혀 있어 HyperCLOVA X·KT 믿:음 같은 온프레미스 모델을 쓴다. 온프레미스 환경은 호출 비용이 토큰이 아니라 GPU 점유로 잡히기 때문에, 멀티 에이전트의 조정 호출이 늘면 GPU 큐가 막히는 형태로 비용이 나타난다. 조정 호출 비율 관리가 토큰 환경보다 더 중요하다.

셋째 관찰성 문화의 부재다. 많은 한국 팀이 아직 LLM 호출 trace를 남기지 않는다. 오케스트레이션 택스는 측정 없이는 보이지 않으므로, 멀티 에이전트 도입 전에 Langfuse 같은 오픈소스 관찰성 도구부터 세우는 것이 순서다. 본인이 권하는 한국형 도입 경로는 1개월 단일 에이전트 + 관찰성 구축, 3개월 한두 개 병렬 분리, 6개월 측정 기반 확장이다.

11. 위험 - "에이전트 많을수록 좋다"는 착각

이 글에서 본인이 가장 강하게 경고하고 싶은 것은 "에이전트가 많을수록 좋다"는 착각이다. 이 착각은 세 가지 잘못된 가정 위에 서 있다.

  • 가정 1: 에이전트 추가는 공짜다. 틀렸다. 에이전트를 하나 추가하면 그것과 기존 모든 에이전트 사이에 새 조정 경로가 생긴다. 추가는 절대 공짜가 아니다.
  • 가정 2: 병렬이면 항상 빠르다. 틀렸다. 합류 지점에서 가장 느린 에이전트를 기다려야 하고, 통합 비용이 병렬 이득을 종종 상쇄한다.
  • 가정 3: 에이전트는 사람보다 협업을 잘한다. 틀렸다. 에이전트는 양보·우선순위 협상·맥락 공유를 사람보다 못한다. 자유롭게 협업시키면 환각을 서로 강화한다.

마케팅 데모에서는 "10개 에이전트가 협업해 앱을 만들었다"가 화려해 보인다. 그러나 본인이 실제로 그런 데모를 재현해 보면, 같은 작업을 잘 설계된 단일 에이전트가 더 빠르고 싸게 끝내는 경우가 대부분이었다. 멀티 에이전트는 수단이지 목표가 아니다. 에이전트 수는 자랑거리가 아니라 비용이다. 이 한 줄을 팀의 벽에 붙여 두기를 권한다.

12. 결론 + 즉시 적용 가능한 3가지

본문의 핵심을 한 문장으로 정리한다. 멀티 AI 에이전트는 조정·검증·통합·모니터링이라는 오케스트레이션 택스를 동반하며, 이 세금을 모르고 에이전트를 늘리면 생산성 이득은 거의 확실하게 잠식된다. 그동안 즉시 적용할 수 있는 행동 세 가지를 정리한다.

  1. 오늘 조정 호출 비율을 측정하라. 현재 파이프라인의 LLM 호출 중 분배·검증·통합에 쓰이는 비율을 태그로 분리해 대시보드에 띄운다. 30%를 넘으면 즉시 단일화를 검토한다.
  2. 에이전트를 단일로 줄여 기준선을 만들어라. 같은 작업을 단일 에이전트로 한 번 돌려 시간·비용·품질을 측정하고, 멀티가 이 기준선을 정말 넘는지 데이터로 확인한 뒤에만 늘린다.
  3. 에이전트끼리 직접 대화시키지 마라. 표준 출력 스키마와 자동 검증 게이트를 두고, 에이전트는 산출물만 주고받게 한다. 자유 대화는 오케스트레이션 택스의 가장 비싼 안티패턴이다.

관련 글로 Flue - 헤드리스 AI 코딩을 위한 TypeScript 샌드박스 에이전트 프레임워크 2026 분석, AI 에이전트를 위한 통합 가상 파일시스템 Mirage, AI 에이전트가 저지르는 가장 비싼 실수 2026을 함께 읽으면 에이전트 인프라·조정 비용·운영 함정을 입체적으로 볼 수 있다.
