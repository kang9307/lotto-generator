1. 서론: AI가 자신의 추론 인프라를 최적화할 때 생기는 일

인공지능 모델이 차세대 인공지능을 만드는 순환 고리를 둘러싼 논의는 오랫동안 이론적 가설이나 안전 거버넌스의 영역에 머물러 있었다. 지난 2026년 6월 발표된 Anthropic의 AI 재귀적 자기개선 연구 - AI가 AI를 만드는 시대의 안전과 위험 2026이 프런티어 모델의 코드 작성 비중 확대와 지능 폭발에 대비한 전 지구적 통제 메커니즘이라는 개념적 논의에 집중했다면, 2026년 9월 17일 Z.ai가 공식 리서치 블로그를 통해 공개한 사례는 정반대의 위치에 서 있다. 이 사례는 철학적 담론이 아니라, 10만 개 이상의 이종 가속기 클러스터 위에서 차세대 경량 모델의 서빙 스택을 완성해 낸 구체적인 시스템 엔지니어링 기록이다.

Z.ai가 공개한 기록의 중심에는 GLM-5.3 기반의 에이전트 시스템인 「Infra Agent」와 주력 추론 모델인 「GLM-5.3-Flash」가 자리한다. 엔지니어 팀과 Infra Agent가 협업한 결과, 신규 하드웨어 위에서 초기 모델 적응을 시작한 지 2주 미만(under two weeks)의 기간 만에 시스템 전반의 서빙 처리량을 초기 베이스라인 대비 약 3배(3×)로 끌어올렸다. 나아가 토큰당 서빙 단가와 하드웨어 연산 자원 활용 효율을 엔비디아의 주류 GPU 환경에 필적하는 수준으로 최적화했다.

하드웨어 선택의 구조적 병목과 메모리 대역폭의 한계는 이미 추론 하드웨어를 고를 때 실제로 갈리는 것 - 대역폭·지연·생태계라는 세 축 2026에서, 단일 칩 수준의 메모리 산수와 제약은 대형 MoE를 GPU 한 장에 - 메모리 산수부터 막히는 지점까지 2026에서 상세히 살펴본 바 있다. 따라서 이번 분석에서는 일반적인 하드웨어 선택론을 반복하는 대신, Z.ai가 발표한 자료의 핵심 문제의식을 집중적으로 파고든다. 즉, 「AI 에이전트가 인프라 코드를 작성했다」는 대중적 수사 이면에 존재하는 진짜 병목, 즉 에이전트에게 실패의 근본 원인을 전달하는 「피드백 시스템의 해상도 설계」를 기술적으로 규명한다.

2. 10만 개 가속기 클러스터와 당시의 시스템 제약

Z.ai가 구축한 인프라의 물리적 규모는 10만 개 이상(100,000+)의 중국산 AI 가속기로 이루어진 대규모 분산 클러스터다. 원문 발표에 따르면 이 규모로 중국산 가속기 단일 클러스터를 구성하여 실제 프로덕션 서비스를 전면 배포한 사례는 이전까지 보고된 바 없었다. GLM-5.3-Flash의 모든 실제 상용 추론 트래픽이 현재 이 시스템 위에서 무중단으로 동작하고 있다.

그러나 이 프로젝트가 출발한 시점의 엔지니어링 조건은 극도로 열악했다. 상용 클러스터가 직면한 기술적 제약 조건들은 다음과 같은 다층적 난관으로 요약된다.

  • 제한된 칩 메모리 용량 및 대역폭: 주류 GPU 대비 개별 가속기 칩의 고대역폭 메모리(HBM) 용량과 전송 대역폭이 상대적으로 제약되어 있어, 단순한 무차별 대입식 서빙 아키텍처로는 대규모 동시성을 수용할 수 없었다.
  • 새로운 모델 아키텍처 수용: 표준적인 트랜스포머 구조에서 벗어난 선형 어텐션(Linear Attention) 및 상태 공간 모델(SSM) 하이브리드 계열 아키텍처를 하드웨어 연산기에 맞춰 바닥부터 매핑해야 했다.
  • 100만(1M) 토큰 초장문 컨텍스트 윈도우: 요청당 최대 1M 토큰에 달하는 방대한 키-값(KV) 캐시를 처리하면서도 디코드 단계의 지연 시간 급증을 억제해야 했다.
  • 멀티모달 동시 요청 지원: 텍스트 토큰뿐만 아니라 고해상도 이미지와 시각 데이터를 포함하는 이종 모달리티 연산이 단일 서빙 인프라 파이프라인 안에서 충돌 없이 인터리빙되어야 했다.
  • 미성숙한 생태계와 불완전한 커널 지원: 소프트웨어 툴체인의 지원이 미흡했고, 고성능 커널의 구현체가 누락되어 있거나 공식 문서화가 부족하여 상당수 하드웨어 동작 특성을 직접 역추적해 파악해야 했다.

이러한 중첩된 제약 조건은 인간 엔지니어 몇 명이 수동으로 커널을 하나씩 튜닝하거나 설정을 조정하는 전통적 접근법으로는 단기간 내에 해결하기 어려운 복잡도를 만들어냈다. 시스템의 각 계층이 서로 강하게 결합되어 있어, 한 지점의 병목을 해소하면 곧바로 다른 계층에서 새로운 병목이 돌출되는 전형적인 분산 시스템의 다체 문제(many-body problem)가 발생했기 때문이다.

3. '2주 만에 3배'의 이면: 코드 생성이 아닌 피드백의 해상도

표면적으로 드러난 결과는 매력적이다. 모델 적응부터 프로덕션 배포까지 걸린 시간은 2주 미만이었고, 종단 간 서빙 성능은 3배 향상되었다. 흔히 이러한 성과를 접하면 거대 언어 모델이 고난도의 C++이나 CUDA/Triton 커널 코드를 자율적으로 뚝딱 작성해 낸 마법 같은 코딩 능력을 떠올리기 쉽다. 하지만 Z.ai 연구진이 밝힌 진짜 핵심은 전혀 다른 지점에 있었다.

Infra Agent의 실질적인 공학적 유효성을 결정지은 결정적 요인은 모델의 정적 코드 생성이나 순수 추론 역량이 아니었다. 시스템이 에이전트에게 지속적으로 제공하는 피드백이 「구체적으로 어느 계층의 어떤 원인 때문에 발생했는지 추적 가능한 형태(attributable feedback)」로 설계되어 있는지가 성공과 실패를 갈랐다. 정적 코드베이스 자체는 시스템의 정적 문맥만을 제공할 뿐이다. 대규모 분산 추론 환경에서 발생하는 수치적 오차, 성능 저하, 최적화 실패는 언제나 여러 계층의 동적 상호작용 속에서 나타난다.

  • 커널 구현 계층: 개별 텐서 연산기 내부의 스레드 블록 타일링, 메모리 접근 패턴, 레지스터 할당.
  • 병렬화 전략 계층: 텐서 병렬화(TP), 컨텍스트 병렬화(CP), 파이프라인 병렬화(PP) 간의 텐서 분할 및 재조합 로직.
  • 통신 인터커넥트 계층: 노드 내 및 노드 간 텐서 전송, 집합 통신(All-Reduce, All-to-All) 스케줄링.
  • 메모리 관리 계층: 호스트와 디바이스 간 KV 캐시 페이징, 가중치 양자화 압축, 캐시 할당자(Allocator) 파편화.
  • 서빙 오케스트레이션 계층: 프리필 노드와 디코드 노드 간의 동적 요청 라우팅과 분산 스케줄링.

이러한 복합 구조에서 에이전트가 전체 코드베이스를 완벽히 이해하고 있다 하더라도, 변경 작업을 수행한 뒤 주어지는 피드백이 희소(sparse)하다면 에이전트는 무력화된다. 예컨대 시스템이 에이전트에게 「수치 정확도 테스트 실패」, 「첫 토큰 도달 시간(TTFT) 30% 증가」, 「초당 출력 처리량 20% 감소」와 같은 거시적인 종단 간(end-to-end) 지표만을 전달한다면, 에이전트는 다섯 개 계층 중 어디가 범인인지, 자신이 세운 가설이 왜 틀렸는지, 다음에 무엇을 검증해야 하는지 알 길이 없다. 거시적 결과 지표는 나빠졌다는 사실만 알릴 뿐, 그 이유를 설명하지 못하기 때문이다.

4. 희소한 종단 지표에서 귀속 가능한 고밀도 피드백으로

전통적인 추론 시스템 최적화 현장에도 프로파일러, 런타임 로그, 단위 테스트, 마이크로벤치마크 도구는 존재한다. 그러나 이 도구들은 엔지니어링 단계마다 파편화되어 흩어져 있다. 숙련된 인간 엔지니어는 부하 테스트 결과를 보고 직관적으로 다음 관찰 대상을 정한다. 실행 타임라인을 확인하고, 통신 이벤트를 들여다보며, 커널 출력을 검사하는 방식으로 머릿속에서 도구들을 연결한다.

하지만 AI 에이전트에게는 이러한 관찰 및 검증 경로가 직접 호출 가능하고 즉각 반복할 수 있는 워크플로로 구조화되어 있지 않으면, 실제로 활용 가능한 피드백은 여전히 극도로 희소한 상태로 남는다. 이를 타개하기 위해 Z.ai는 정확도 검증, 런타임 로그, 실행 트레이스, 런타임 이벤트, 마이크로벤치마크, 종단 메트릭을 단일한 에이전트 반복 루프 안으로 유기적으로 편입시켰다. 이 체계를 원문에서는 「고밀도 피드백(dense feedback)」이라 정의한다. 여기서 고밀도란 단순히 대량의 로그를 무차별 주입하는 것이 아니며, 아래 세 가지 공학적 성질을 갖추는 것을 뜻한다.

4.1 국소성(Locality): 원인이 되는 계층과 코드 경로의 특정

피드백은 반드시 최대한 국소적이어야 한다. 이상 징후가 발생했을 때 문제의 범위가 특정 엔진 실행 파라미터, 코드 변경 지점, 개별 커널, 입력 텐서 형태, 스레드 구간, 혹은 세부 실행 경로 단위로 즉시 좁혀져야 한다. 예컨대 「연산자 융합(Fusion) 이후 전체 모델 정확도가 떨어졌다」는 막연한 보고 대신, 변경 전후 특정 단일 요청의 텐서 출력 차이를 격리하여 식별해 주어야만 에이전트가 최소 재현 케이스(minimal reproduction)를 구성해 원인 분석에 착수할 수 있다.

4.2 신속성(Timeliness): 전체 재배포 없는 마이크로 단위 검증

가설 검증에 드는 비용이 극히 저렴하고 지연 시간이 짧아야 한다. 에이전트가 새로운 가설을 세우고 코드를 고쳤을 때, 단일 커널 테스트나 로컬 마이크로벤치마크로 판별할 수 있는 문제를 검증하기 위해 매번 전체 클러스터 서비스 재배포와 분산 부하 테스트를 기다리게 해서는 안 된다. 검증 주기가 수 초에서 수 분 단위로 짧아져야만 에이전트가 비생산적인 가설에 낭비하는 연산 자원과 탐색 시간을 최소화하고 경로를 올바르게 수정할 수 있다.

4.3 객관성(Objectivity): 통제 실험과 참조 구현 기반의 대조

코드 변경이 정당한지, 실제 성능이 향상되었는지는 주관적 추정이 아니라 참조 구현체(reference implementation)와의 수치 대조 및 통제된 실험 지표로 확정되어야 한다. 런타임 신호는 잠재적 원인을 짚어내는 힌트일 뿐, 상관관계 자체가 인과관계를 입증하지는 않는다. 특정 코드 경로의 수정이 의도한 성능 향상을 온전히 유발했는지는 철저히 격리된 통제 환경의 벤치마크로 검증되어야 한다.

이 세 가지 원칙 아래 국소 검증(Local Validation)과 종단 테스트(End-to-End Testing)는 명확히 분업화되었다. 국소 검증은 잘못된 구현이나 비효율적인 최적화 시도를 조기에 탈락시키고 유망한 후보를 선별하는 역할을 맡았으며, 종단 테스트는 국소적 이득이 실제 프로덕션 워크로드에서 회귀(regression) 없이 전체 서빙 성능 향상으로 이어지는지 최종 인가하는 관문 역할을 담당했다.

5. 3가지 구체적 사례: 수치 정밀도, 동시성 병목, 커널 최적화

고밀도 피드백 루프가 실제 인프라 구축 과정에서 어떻게 작동했는지는 Z.ai가 공개한 3가지 구체적인 디버깅 및 최적화 사례를 통해 명확히 드러난다. 각 사례는 에이전트가 「올바르게 계산하는가」, 「왜 충분히 빠르지 못한가」, 「어떻게 더 빠르게 만들 것인가」를 규명해 나간 실전 공학의 축소판이다.

5.1 수치 정확성: KDA 커널 컨텍스트 병렬화와 TF32 정밀도 누적

추론 성능 최적화의 대전제는 수치적 정확성이다. 병렬화 전략이 고도화되면 커널에 주어지는 텐서 입력이 조각나고 조합되는 경로가 완전히 달라진다. 따라서 분할되지 않은 단일 환경에서 커널 출력을 검증하는 것만으로는 실제 분산 배포 환경의 동작을 보장할 수 없다.

Infra Agent는 엔진의 병렬화 전략과 실제 커널 구현체 사이의 매핑 테이블을 기반으로, 컨텍스트 병렬화(CP) 적용 경로와 비적용 경로 간의 수치 오차를 비교 검증했다. 이 과정에서 KDA 커널의 CP 실행 경로에서 심각한 수치적 괴리가 발생함을 포착했다. CP 분할 환경에서는 샤드(shard) 간 상태 전이 행렬을 병합하고 다음 샤드의 초기 상태를 갱신하는 연산이 필수적이다.

M = tl.dot(M_chunk, M)     # Merge state transformations across shards
S_next = tl.dot(M, S) + H  # Update the initial state for the next shard

문제의 원인은 Triton 텐서 연산기인 tl.dot의 기본 동작 방식에 있었다. 원본 구현에서 tl.dot은 입력값이 FP32임에도 불구하고 성능 최적화를 위해 내부적으로 TF32 연산 모드를 기본값으로 사용했다. 그 결과 샤드 간 변환이 누적되는 과정에서 정밀도 손실이 복리로 누적되었고, 컨텍스트 길이가 길어질수록 오차가 감당할 수 없을 만큼 증폭되었다.

피드백을 통해 이를 파악한 에이전트는 해당 두 연산에 명시적으로 input_precision="tf32x3" 옵션을 부여했다. 이 수정은 세 개의 TF32 텐서 코어 연산을 결합하여 더 높은 정밀도를 확보함으로써, 텐서 코어의 가속 이점을 누리면서도 누적 오차를 허용 오차 이내로 통제하는 결과를 낳았다. 이 수치 정밀도 패치는 오픈소스 생태계인 Flash Linear Attention의 풀 리퀘스트(PR #1180)로 정식 업스트림 병합되었다.

5.2 시스템 동작: DeepEP와 Mooncake Transfer 사이의 GIL 경합

두 번째 사례는 시스템 아키텍처 수준의 동시성 병목을 추적한 과정이다. 엔지니어링 팀은 에이전트에게 사전 정의된 테스트 시나리오(프리필 단독, 프리필 + KV 전송, 디코드 단독)를 부여하고 성능 기준선을 설정했다. 정상적인 파이프라인이라면 동일 부하에서 「프리필 단독」 대비 「프리필 + KV 전송」의 성능 격차가 5% 이내로 유지되어야 했다.

그러나 에이전트가 측정한 특정 시나리오에서는 두 조합 간의 성능 격차가 20%를 초과했다. 고밀도 피드백 환경은 즉각 문제 구간을 KV 전송 오버헤드로 좁혀 주었다. 에이전트가 KV Transfer 실행 타임라인을 고해상도로 추적하자, 파이썬 기반의 KV 전송 작업이 하부 DeepEP의 디스패치 및 컴바인 호출 구간과 전혀 오버랩(overlap)되지 않고 직렬화되어 실행되는 기현상이 발견되었다.

호출 체인을 추적한 결과, 사용 중이던 DeepEP v1.2.1의 intranode_dispatch와 intranode_combine C++ 구현체 내부에서 파이썬 GIL(Global Interpreter Lock)을 명시적으로 해제하지 않은 채 CPU가 GPU 응답을 동기 대기하고 있었다. C++ 영역으로 진입한다고 해서 GIL이 자동으로 풀리지 않으므로, DeepEP가 락을 쥔 채 대기하는 동안 동일 프로세스 내에서 Mooncake Transfer를 구동하던 파이썬 스레드가 실행 기회를 완전히 박탈당했던 것이다. 노드 간 전송(internode_dispatch) 코드에는 이미 GIL 해제 처리가 되어 있었으나 노드 내 경로에서 누락되어 있던 결함이었다. 에이전트는 C++ 실행 구간에서 GIL을 명시적으로 해제하도록 수정했고, 수정 후 성능 격차는 기준치인 5%를 넘어 1% 미만으로 좁혀졌다.

5.3 커널 성능: 중복 연산 제거와 레지스터 기반 리덕션

세 번째 사례는 성능 피드백을 통해 기존 프로젝트들의 구현 노하우를 흡수하고 시스템 차원의 커널 성능을 끌어올린 과정이다. SGLang, Flash Linear Attention, DeepGEMM 등 유수의 고성능 오픈소스 프로젝트에 축적된 수제(handwritten) 커널 최적화 기법을 Infra Agent가 분석하여 일종의 「최적화 골격(optimization skeletons)」 라이브러리를 구축했다.

KDA 디코드 커널의 성능 진화 과정에서, 메모리 점유를 줄이기 위해 ReplaySSM 기법을 선제 도입하자 연산량이 늘어나며 실행 시간이 v0에서 v1으로 일시 증가했다. 에이전트는 먼저 나눗셈 연산 최적화를 통해 v1 대비 실행 시간을 9.6% 단축했다. 이후 프로파일러 피드백을 통해 해당 커널의 지배적 병목이 메모리 대역폭이 아니라 연산 자체에 있음이 드러났다.

상세 분석 결과, 원본 커널은 V 차원을 따라 타일링(tiling)을 수행하고 있었고, 그로 인해 동일한 FP32 정규화 및 게이팅 연산이 4개의 타일에서 무의미하게 중복 반복 계산되고 있었다. 에이전트는 이 타일들을 단일 스레드 블록으로 통합하고, 공유되는 중간 연산 결과를 레지스터에 상주시킨 뒤, 타일별 중복 연산을 단일 워프 레벨 리덕션(warp-level reduction)으로 대체했다. 병렬성의 일부를 의도적으로 희생하는 대신 원천적인 중복 연산을 완전히 제거함으로써, v2 대비 1.71배의 실행 속도 향상을 달성했다.

Z.ai가 GLM-5.3-Flash 인프라에 적용한 최적화 기법들은 단편적인 트릭의 집합이 아니다. 그것은 연산과 대역폭, 통신과 디바이스 메모리 사이의 교환비를 면밀히 계산하여 배치한 종합 스택이다. 원문에서 명시된 6가지 핵심 기법을 아키텍처적 목적에 따라 분류하면 아래 표와 같다.

7. 프로덕션 검증: 6일간 62조 토큰 처리와 하드웨어 효율

실험실 벤치마크에서의 3배 향상이 실제 사용자 트래픽 환경에서도 유효한지는 별개의 문제다. 인프라의 완성도를 증명하기 위해 Z.ai는 외부 생태계에서 매우 공격적인 실전 검증 절차를 거쳤다.

GLM-5.3-Flash는 출시 전 오픈 모델 벤치마크 및 서비스 플랫폼인 OpenCode와 OpenRouter에 「Ox-Alpha」라는 익명 모델명으로 비공개 투입되었다. 어떠한 사전 마케팅이나 브랜드 후광 효과 없이 순수하게 API 서빙 품질과 응답 속도만으로 전 세계 개발자들의 트래픽을 정면으로 받아냈다. 그 결과 출시 불과 1주일 만에 OpenCode와 OpenRouter 두 플랫폼 모두에서 가장 많이 사용되는 모델 1위에 등극했다. 특히 초기 6일 동안 무려 62조(62 trillion) 토큰 이상을 단 한 차례의 대규모 인프라 장애 없이 안정적으로 처리했다.

이 독립적이고 정량적인 트래픽 수치는 10만 개 가속기 클러스터와 Infra Agent가 공동 구축한 서빙 스택이 데모 수준에 머문 것이 아니라, 전 세계 단위의 실제 부하를 완벽히 견뎌내는 상용 수준에 도달했음을 입증하는 확실한 방증이다.

8. 재귀적 자기 개선(RSI)의 현재와 경계: 가능한 자리와 불가능한 자리

Z.ai는 이번 성과를 두고 「재귀적 자기 개선(Recursive Self-Improvement, RSI)의 초기 형태가 이미 나타나고 있다」고 규정했다. 모델이 시스템을 최적화하고, 최적화된 시스템이 모델을 서빙하며, 축적된 최적화 노하우가 다음 세대 인프라 튜닝의 밑거름으로 환류되는 구조가 실제로 작동했기 때문이다. 그러나 이러한 성공 서사를 대할 때 엔지니어가 경계해야 할 기술적 한계 역시 뚜렷하다.

  • 단일 조직 및 자체 모델 계열의 특수성: 이번 사례는 모델 아키텍처를 설계한 주체와 인프라를 최적화한 에이전트, 하드웨어 클러스터 관리자가 동일한 조직 내에서 단일한 목표로 결합되어 있었기에 가능했다. 외부 블랙박스 모델이나 이종 조직 간 인프라 작업으로 일반화하기에는 아직 거리가 멀다.
  • 고밀도 피드백 구축이라는 선행 비용: 에이전트가 동작하기 위해서는 인간 엔지니어가 국소적이고 신속한 피드백 환경을 고도로 정밀하게 선제 구축해야 한다. 피드백 파이프라인을 설계하는 공학적 비용이 결코 가볍지 않다.
  • 인간 엔지니어의 통제선 유지: 최적화 목표 설정, 시스템 경계 획정, 비동기 동시성 및 프로덕션 롤아웃 리스크 검토는 여전히 전적으로 인간 엔지니어의 승인 하에 진행되었다.
  • 완전한 RSI와의 거리: 스스로 학습 목표를 수립하고, 하드웨어 구조를 독자 설계하며, 안전 경계를 자율적으로 재설정하는 자율적 지능 단계에 도달한 것은 결코 아니다.

원문 스스로도 "우리는 아직 거기에 도달하지 않았다(We are not there yet)"고 유보적 태도를 분명히 밝혔다. 목표를 정하고 시스템 경계를 긋는 책임은 여전히 인간의 몫으로 남아 있어야 한다는 점을 명시하고 있다. 다만 2주라는 시간, 3배라는 처리량, 10만 개의 가속기라는 숫자는, 적절한 피드백 구조가 갖추어졌을 때 시스템 엔지니어링의 생산성 경계선이 어디까지 가속될 수 있는지를 명백히 보여준다.

9. 확인하지 못한 것

본 기술 분석을 작성하는 과정에서 1차 출처인 Z.ai 공식 발표문 및 관련 기술 문서를 대조했으나, 명확한 수치나 세부 근거가 부족하여 단정하지 않고 유보한 항목들은 아래와 같다.

  • Z.ai가 사용한 10만 개 이상의 중국산 AI 가속기의 구체적인 제조사, 칩 모델명, 아키텍처 세부 사양(SM/코어 수, HBM 대역폭 수치 등)은 원문에서 일체 명시되지 않아 확인하지 못했다.
  • 엔비디아 주류 GPU 대비 토큰당 서빙 원가와 하드웨어 연산 효율이 대등한 수준에 도달했다고 밝혔으나, 절대적인 달러 기준 비용이나 비교 대상으로 삼은 특정 엔비디아 GPU 모델명(H100, A100 등)의 실측 데이터는 공개되지 않아 확인하지 못했다.
  • OpenCode와 OpenRouter에서 기록한 6일간 62조 토큰 외에, Z.ai의 자체 상용 서비스나 내부 API 엔드포인트에서 발생한 전체 누적 트래픽의 구체적 집계 수치는 원문에 언급되지 않아 확인하지 못했다.
