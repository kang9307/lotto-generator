Introduction - where does open() get its value when encoding is omitted

Code that reads a text file containing Korean with open('data.txt').read() runs fine on the developer's PC, then stops with UnicodeDecodeError on another PC, or finishes without an error and returns changed characters. Since the code is identical and the result differs, there is one more input outside the code. That input is the default value the interpreter fills in when the encoding argument is omitted. The outputs below show where that default comes from, how easily it changes, and what the output looks like when it does.

Several articles already cover encoding problems, each with a different axis. The BOM article covers three leading bytes that break parsers. The cp949 and UTF-8 mojibake article works backwards from a garbled shape to its cause. The PowerShell 5.1 redirect article covers the encoding that is chosen when PowerShell writes a file, and the zip filename article covers the name bytes inside an archive. This article is limited to the point where the value used by Python's open() is decided when the encoding is omitted, the UTF-8 mode that changes it, EncodingWarning as a way to find risky lines, the change planned for 3.15, and patterns that are safe in code. Section 8 of the cp949 article contains a short run showing that PYTHONUTF8=1 changes the open() default, and the runs below extend it with more variables.

The questions covered are these.

  • What is the default of open() with no encoding, and which function returns the same value?
  • Which exception is raised, and where, when UTF-8 Korean text is read with the default?
  • What is seen when a file written with the default is read as UTF-8?
  • Which cases change characters without an exception, and which fail at write time?
  • What does UTF-8 mode change, and what does it leave alone?
  • Which lines does EncodingWarning flag, and which does it skip?
  • What change does PEP 686 specify for 3.15?

The default is whatever locale.getencoding() returns

First the values of the running environment are read. The code below prints the two locale encoding functions, the UTF-8 mode flag, two related environment variables, and the standard output encoding in one go.

On this PC the locale encoding is cp949, UTF-8 mode is off (utf8_mode 0), and neither PYTHONUTF8 nor PYTHONIOENCODING is set (None). In this state the encoding that open() actually uses is read directly.

import locale, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    f = open('probe.txt', 'w')
                    print('open(w).encoding  ', f.encoding)
                    f.close()
                    print('open(r).encoding  ', open('probe.txt').encoding)

                    print('== getencoding()  ', open('probe.txt').encoding == locale.getencoding())

                    explicit utf-8     utf-8
                    == getencoding()   True

Both write mode and read mode gave cp949, and writing encoding='utf-8' gave utf-8. The last line compares the file object's default encoding with the return value of locale.getencoding() and prints True. The open() entry of the Python documentation describes this relationship as follows: "The default encoding is platform dependent (whatever locale.getencoding() returns), but any text encoding supported by Python can be used." The output and the documented sentence agree.

  • The default is not a constant chosen by Python. It is read from the locale of the running environment, and on this PC it is cp949.
  • Running the same code on a PC with a different locale can produce a different default. That is why the documentation says "platform dependent".
  • The encoding attribute of a file object shows the value actually applied. It is the first value to look at before guessing about the cause of an error.
  • The stdout.encoding line of the output is an attribute of standard output and is a different attribute from the default used to open files. Section 6 covers the settings that move both.

Reading UTF-8 Korean text with the default

The most common accident is opening a UTF-8 file without an encoding. Files made by editors, git, and other operating systems are usually UTF-8. The code below writes a Korean sentence as UTF-8, prints the bytes, and then reads it without an encoding.

import os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    with open('ko_utf8.txt', 'w', encoding='utf-8') as f:
                        f.write('한글 테스트')
                    print(open('ko_utf8.txt', 'rb').read().hex(' '))
                    try:
                        open('ko_utf8.txt').read()
                    except UnicodeDecodeError as e:
                        print(type(e).__name__, e)
ed 95 9c ea b8 80 20 ed 85 8c ec 8a a4 ed 8a b8
                    UnicodeDecodeError 'cp949' codec can't decode byte 0xed in position 0: illegal multibyte sequence

The first line shows the 16 bytes that actually went into the file. One Korean character takes 3 bytes (ed 95 9c is the first character) and the space takes 1 byte (20). On reading, the cp949 codec stopped at 0xed in position 0 with "illegal multibyte sequence". The reason is visible in the output itself. The writer stated encoding='utf-8', while the reader omitted it and got the cp949 seen in the previous section. The codec name 'cp949' inside the exception message tells which encoding was applied on the reading side without looking at anything else.

  • The exception type is UnicodeDecodeError, and the message carries the codec name, the offending byte (0xed) and the position (position 0).
  • When the codec name is cp949, the reading side applied cp949, so the first suspect is the encoding argument of the reading code and not the file.
  • This exception reproduces every time in the same environment. The round-trip output of section 6 shows why nothing is visible when the writer and the reader share the same PC and settings.

The opposite direction - reading a default-written file as UTF-8

A file written without an encoding and then read as UTF-8 elsewhere produces the same problem in the opposite direction. The code below writes Korean with the default, prints the bytes, then prints the result of reading as cp949, as UTF-8, and as UTF-8 with errors='replace'. Printing Korean directly would involve the console encoding, so ascii() is used to print code point escapes.

import os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    with open('ko_default.txt', 'w') as f:
                        f.write('한글 테스트')
                    print(open('ko_default.txt', 'rb').read().hex(' '))
                    print(ascii(open('ko_default.txt', encoding='cp949').read()))
                    try:
                        open('ko_default.txt', encoding='utf-8').read()
                    except UnicodeDecodeError as e:
                        print(type(e).__name__, e)
                    print(ascii(open('ko_default.txt', encoding='utf-8', errors='replace').read()))
c7 d1 b1 db 20 c5 d7 bd ba c6 ae
                    '\ud55c\uae00 \ud14c\uc2a4\ud2b8'
                    UnicodeDecodeError 'utf-8' codec can't decode byte 0xc7 in position 0: invalid continuation byte
                    '\ufffd\u0471\ufffd \ufffd\u05fd\ufffd\u01ae'

The same sentence written with the default is now stored as c7 d1 b1 db …, cp949 bytes with two bytes per character. Reading as cp949 restores the original characters (\ud55c\uae00 …), while reading as UTF-8 stops at the first byte 0xc7 with "invalid continuation byte". With errors='replace' the exception disappears, but the resulting string is filled with \ufffd (the replacement character) and unrelated characters (\u0471, \u05fd, \u01ae), and the original sentence is no longer in the string.

The errors entry of the official documentation states the default behavior this way: "'strict' to raise a ValueError exception if there is an encoding error. The default value of None has the same effect." A call that omits errors is therefore strict, and the exceptions above are the result of that default.

  • Korean written as cp949 takes two bytes per character and as UTF-8 takes three, as the byte lines of sections 3 and 4 show.
  • Because the bytes differ between the two encodings, reading a file written in one with the other is a misreading and not a conversion, in either direction.
  • errors='replace' hides the error and erases information. In this output the original byte c7 became \ufffd and could not be recovered from the string.
  • To keep damaged bytes visible there is errors='backslashreplace', and section 9 compares the outputs.

Silent misreads and write-time failures

Not every misreading ends with an exception. The code below puts side by side strings whose UTF-8 bytes raise an exception when interpreted as cp949 and strings that do not. The last lines write a character that cp949 cannot represent (U+2728) with the default.

import os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    print('café'.encode('utf-8').hex(' '))
                    for s in ['한글 테스트', '가나다라마바사', 'abc', 'caf\u00e9', '\u2014 dash']:
                        b = s.encode('utf-8')
                        try:
                            print('silent', ascii(s), '->', ascii(b.decode('cp949')))
                        except UnicodeDecodeError as e:
                            print('error ', ascii(s), '->', e.reason, 'at byte', e.start)
                    try:
                        open('emoji.txt', 'w').write('ok \u2728')
                    except UnicodeEncodeError as e:
                        print(type(e).__name__, e)
                    print(os.path.getsize('emoji.txt'))
63 61 66 c3 a9
                    error  '\ud55c\uae00 \ud14c\uc2a4\ud2b8' -> illegal multibyte sequence at byte 0
                    error  '\uac00\ub098\ub2e4\ub77c\ub9c8\ubc14\uc0ac' -> illegal multibyte sequence at byte 2
                    silent 'abc' -> 'abc'
                    silent 'caf\xe9' -> 'caf\ucc55'
                    error  '\u2014 dash' -> illegal multibyte sequence at byte 0
                    UnicodeEncodeError 'cp949' codec can't encode character '\u2728' in position 3: illegal multibyte sequence
                    0

The first line is the UTF-8 bytes of café, 63 61 66 c3 a9. The Korean sentence, the sentence of consecutive Korean syllables, and the string with an em dash (U+2014) ended with an exception, and abc, containing only ASCII letters, came out unchanged because both encodings agree on it. café, however, was read as caf\ucc55 without any exception. The last two bytes c3 a9 were interpreted by cp949 as one valid two-byte character (U+CC55). Since there is no exception, this misreading stays hidden until someone looks at the screen or the data.

On the write side, the exception comes in the opposite way. open('emoji.txt', 'w').write('ok \u2728') ended with UnicodeEncodeError: 'cp949' codec can't encode character '\u2728', and reading the file size gives 0. The file was created, but not one byte of the intended content went into it.

UTF-8 mode - what changes and what does not

The UTF-8 Mode entry of the official documentation describes activation like this. UTF-8 mode is turned on or off with the -X utf8 command line option and the PYTHONUTF8 environment variable. When it is on, the filesystem encoding becomes UTF-8, and open(), io.open() and codecs.open() use UTF-8 by default. The documentation adds that they still use the strict error handler, so that opening a binary file in text mode is likely to raise an exception and not to produce nonsense data. The code below prints the values that correspond to these sentences in one go. The outputs below come from the same script with only the option changed.

The table copies the outputs for five option settings. What can be read from it is as follows.

  • -X utf8 and PYTHONUTF8=1 gave the same result. In both, utf8_mode became 1, and the open() default and the standard output encoding became utf-8.
  • -X utf8=0 and PYTHONUTF8=0 matched the run without options. In this environment the values that turn UTF-8 mode off could not be told apart from the default state.
  • locale.getencoding() is cp949 in every case. PEP 686 describes this function as a new API that returns the locale encoding while ignoring UTF-8 mode, and the output agrees with that description.
  • locale.getpreferredencoding(False) changes to utf-8 in UTF-8 mode. Two functions that both ask for the locale encoding give different answers, so which function was used to check the value changes the conclusion.
  • Specifying encoding='locale' gave cp949 even in UTF-8 mode. This value is for files that must deliberately use the locale encoding, such as an existing settings file saved in it.
  • The filesystem encoding (fs encoding) was utf-8 whether or not UTF-8 mode was on.

Without options, c7 d1 … (cp949 bytes) are stored and read back as they are, so there is no error. Adding only -X utf8 to the same code changes the stored bytes to ed 95 9c … (UTF-8), and this time the line that reads as cp949 raises UnicodeDecodeError. Not one character of the code changed. The only thing that changed is one default. This is the smallest reproduction of the mismatch that appears when files are exchanged between PCs with different settings.

UTF-8 mode also affects old files. When the file saved as cp949 earlier was opened without an encoding in an interpreter run with -X utf8, the following exception appeared.

UnicodeDecodeError 'utf-8' codec can't decode byte 0xc7 in position 0: invalid continuation byte

Turning on UTF-8 mode does not remove the problem. It changes the direction of the default. In an environment that holds cp949 files, those files stop being readable the moment it is turned on.

Finding omissions with EncodingWarning

With the -X warn_default_encoding option, a call that omits the encoding argument emits an EncodingWarning. The code below places seven ways of using encodings in one file. Line 4 omits it, line 5 omits it in Path.read_text(), and line 9 passes encoding=None.

                    with open('a.txt', 'w', encoding='utf-8') as f:
                        f.write('x')
                    open('a.txt').read()
                    pathlib.Path('a.txt').read_text()
                    open('a.txt', encoding='utf-8').read()
                    open('a.txt', 'rb').read()
                    open('a.txt', encoding='locale').read()

The same warning could also be turned on with the environment variable PYTHONWARNDEFAULTENCODING=1, with the same output as the option. The environment variable is useful for turning it on in a test runner or CI without touching the code. Turning it on together with UTF-8 mode (-X utf8) produced warnings on the same three lines.

Warnings come only from lines that were executed. An open() in a branch that never ran gives no warning. A static scan is a useful companion. Below is a short checker that uses the standard library ast to find text-mode open() and read_text() calls without an encoding.

import ast, sys
                    hits = []
                    for path in sys.argv[1:]:
                        tree = ast.parse(open(path, encoding='utf-8').read())
                        for node in ast.walk(tree):
                            if not isinstance(node, ast.Call):
                                continue
                            name = ast.unparse(node.func)
                            has_enc = any(k.arg == 'encoding' for k in node.keywords)
                            if name == 'open':
                                mode = node.args[1].value if len(node.args) > 1 else 'r'
                                if 'b' not in mode and not has_enc and len(node.args) < 4:
                                    hits.append((path, node.lineno, 'open() without encoding'))
                            elif name.endswith('.read_text') and not has_enc and not node.args:
                                hits.append((path, node.lineno, name + '() without encoding'))
                    for path, line, msg in sorted(hits):
                        print(path + ':' + str(line), msg)

The target is an example file containing common forms written without an encoding.

import json, pathlib

                    with open('out.txt', 'w') as f:
                        f.write('x')
                    raw = open('in.bin', 'rb').read()
                    ok = open('in.txt', encoding='utf-8').read()
                    note = pathlib.Path('note.txt').read_text()

                    legacy.py:3 open() without encoding

An open() nested inside a call, as in json.load(open('config.json')), was caught as legacy.py:2, and lines in binary mode or with an encoding were not. This checker, however, misses line 9 with encoding=None (warn.py:9 is not in the list). EncodingWarning caught that line. Because the two methods miss different places, executed paths are covered by the warning and branches that do not run are covered by the static check.

  • EncodingWarning is emitted only for calls that were actually executed.
  • encoding=None emits the warning in the same way as omission.
  • Turning on UTF-8 mode did not remove the warnings. The purpose of the warning is to expose lines that rely on the default.
  • A static check sees branches that never run, but cases such as an argument passed through a variable or encoding=None need separate rules.

PEP 686 - the plan for 3.15

The abstract of PEP 686 begins like this: "This PEP proposes enabling UTF-8 mode by default. With this change, Python consistently uses UTF-8 for default encoding of files, stdio, and pipes." As of the documents on 2026-10-06, the status at the top is Final and the target version is Python 3.15. The specification states "Python will enable UTF-8 mode by default from Python 3.15." and names PYTHONUTF8=0 and -X utf8=0 as ways to turn it off. The UTF-8 Mode documentation carries one sentence about 3.15: "Python 3.15 will make Python UTF-8 Mode default."

Reading this plan together with the earlier runs gives three points.

  • The run on 3.13 with -X utf8 turned on (section 6) has the same shape as the behavior the document sets as the default state of 3.15. In 3.15 that behavior becomes the default without an option.
  • Even after 3.15, a file that must use the locale encoding takes encoding='locale', and in the run of section 6 this value returned cp949 regardless of UTF-8 mode.
  • Because the direction of the default changes, existing code that reads files saved as cp949 without an encoding can fail to read them in the same shape as the exception at the end of section 6.

On versions before 3.15, code that relies on the default behaves differently from environment to environment. The existence of the plan does not make code safe on the current version. A call that states the encoding uses the stated value as it is, as the outputs of sections 2 and 6 show.

                    '\\xc7\u0471\\xdb'

replace erases the original bytes (\ufffd), while backslashreplace leaves the byte values in the string as \xc7 and \xdb. When clues are needed for analysis, the latter is better. Neither fixes the misreading, and the remedy is to state the correct encoding.

In summary, the following items can be used to check code.

  • Does every text-mode open() carry encoding?
  • Do Path.read_text() and write_text() carry encoding?
  • Do the places that open CSV carry newline=''?
  • If the locale encoding is meant to be used, is that intent visible as encoding='locale'?
  • Does the test runner or CI check that there are 0 warnings with -X warn_default_encoding?
  • Is the encoding of the party exchanging files fixed in a document?

What Could Not Be Verified

  • Behavior on a Python 3.15 interpreter. This PC has only 3.13, and the 3.15 default UTF-8 mode and the actual default are quoted only from the wording of PEP 686 and the UTF-8 Mode documentation. The statement that reading cp949 files may fail on 3.15 is inferred from the UTF-8 mode output on 3.13.
  • The output of the same code on Linux or macOS. The default in an environment whose locale is UTF-8 was not run.
  • The default on Windows with other locales (English, Japanese and others). This PC has one Korean locale.
  • The default when the Windows system locale option for UTF-8 support is turned on.
  • The encoding of sys.stdout when it is connected to a pipe or a file. The standard output values of section 6 were obtained in a console environment.
  • The range of calls outside open(), such as subprocess and io.TextIOWrapper, in which EncodingWarning appears.
  • Why -X utf8=0 and PYTHONUTF8=0 gave the same result as the default state in this environment. Interactions with other settings beyond the cp949 locale were not run.
  • Behavior with encodings other than cp949 and UTF-8 (UTF-16, EUC-KR variants, characters outside the extended Wansung set).
