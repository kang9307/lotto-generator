Scaling Postgres Up and Down Without Dropping Connections - Neon Lakebase Autoscaling

Real-Time Vertical Resizing Governed by Three Signals, Working-Set Projections, and In-Guest Memory Monitoring

2026-09-14 Dev & Infra

Selecting a database instance size prior to deploying a production workload has long been one of the most frustrating compromises in cloud systems engineering. When software teams are forced to predict traffic volumes, concurrent connection spikes, and memory consumption before running real queries, they inevitably veer toward extreme inefficiencies. Engineers either vastly overprovision virtual machines to guarantee headroom during rare traffic bursts—wasting immense cloud capital on idle silicon—or underestimate requirements, triggering saturated memory, connection timeouts, and cascading downtime when unexpected loads hit. In an era where cloud computing resources are increasingly contested and expensive, guessing hardware capacity in advance represents a fragile and obsolete architectural paradigm.

Neon’s Lakebase Postgres eliminates the upfront sizing dilemma entirely by introducing continuous, zero-downtime vertical autoscaling directly to running PostgreSQL instances. Rather than relying on traditional replica failovers or scheduled maintenance windows that sever active database connections, Lakebase dynamically adjusts the vCPU cores and RAM allocated to a live virtual machine without terminating client TCP sockets. Production telemetry released by Neon reveals that an average production database cluster changes compute capacity 32,016 times per month, translating to an instance resize roughly once every 81 seconds. This demonstrates that continuous, sub-minute vertical scaling is not an abstract academic concept, but an actively proven production reality running at scale.

The Dilemma of Database Sizing and Real Production Scaling Frequency

Within legacy database deployments, altering instance dimensions has historically imposed severe operational friction. Conventional managed relational database services require physical machine restarts or DNS failovers across read replicas to swap instance classes. During those failovers, established client connection pools are forcibly dismantled, pending transactions are aborted, and applications suffer connection storms while attempting to reconnect. Consequently, infrastructure teams systematically configure oversized compute instances, paying for idle gigabytes of memory around the clock simply to survive peak moments that may occur only a few times each month.

Fundamental Differences Between Horizontal Sharding and Vertical Autoscaling

Architects possess two primary pathways to expand database throughput: splitting data across multiple independent nodes via horizontal sharding, or expanding and contracting the hardware limits of a single node through vertical scaling. As explored in our companion analysis, Choosing to Split Postgres Across Multiple Nodes - The Cost Horizontal Scaling Levies on Transactions, Joins, and Constraints, sharding PostgreSQL across multiple instances levies steep functional taxes. Distributed two-phase commit (2PC) protocols introduce pervasive network round-trip overhead, cross-shard joins cripple throughput, and relational sequence guarantees break down. Conversely, the vertical autoscaling implemented in Lakebase Postgres preserves full relational semantics, complete transactional ACID guarantees, and rich SQL queries on a single logical engine, dynamically modulating physical vCPUs and RAM to match incoming load.

Averaging 32,016 Monthly Scale Events: One Adjustment Every 81 Seconds

Neon’s empirical operational datasets highlight that active production databases undergo an average of 32,016 compute unit adjustments every month. This staggering figure equates to a sizing alteration approximately every 81 seconds across daily operations. Real-world database traffic rarely adheres to steady states; morning business hours, seasonal sales, marketing campaigns, and background analytics generate volatile workload curves. An 81-second control cadence ensures that capacity curves tightly hug real workload demands, provisioning compute instantly when required and returning unused allocations as soon as pressure subsides.

  • Elimination of capacity guesswork: Removing the necessity of sizing databases before real-world query behavior is understood.
  • Non-disruptive in-place resizing: Expanding and shrinking live guest virtual machine resources without closing client connection sockets.
  • Bidirectional efficiency: Equalizing the urgency of scaling up to protect performance and scaling down to curtail cloud costs.
  • Sub-minute production responsiveness: Proven stability across 32,016 monthly automated scaling adjustments in live enterprise clusters.

Decoupling Compute from Storage: Foundation for Zero-Downtime Resizing

The primary barrier that historically prevented PostgreSQL from resizing dynamically on the fly was the intimate coupling of execution state and durable storage on the same physical disks. In a monolithic database server, resizing or migrating a node is fundamentally a heavy storage operation because the host owns both query processing and data durability. Lakebase Postgres eliminates this constraint by enforcing a strict architectural separation of concerns between ephemeral compute and resilient distributed storage.

Stateless Compute Nodes and the Durable Distributed Storage Tier

Under the Lakebase architecture, the compute tier functions as an ephemeral, stateless execution engine dedicated exclusively to running PostgreSQL and processing client queries. Compute nodes utilize local RAM and high-speed local NVMe solid-state drives strictly as low-latency caching tiers, completely abdicating ownership of persistent storage. Long-term durability, WAL ingestion, and version history are offloaded to an independent, distributed storage subsystem composed of three distinct services.

  • Safekeepers: SSD-backed consensus nodes that ingest and replicate PostgreSQL write-ahead logs (WAL) to ensure instant write durability.
  • Pageservers: Highly scalable SSD storage nodes that continuously reconstruct and serve requested page versions across historical LSN timelines.
  • Object Storage: Cost-effective cloud storage (such as Amazon S3) maintaining immutable, long-term block archives and historical checkpoints.

Because the compute node holds no unique, uncommitted state on its local disks, the database engine can be started, stopped, resized, or transferred across physical hardware boundaries without relocating the underlying dataset. Decoupling storage transforms database scaling from a risky disk migration into a lightweight compute allocation workflow.

Preserving Client Sockets via Live Migration with Static Private IPs

While in-place adjustments to vCPU and RAM can occur instantaneously when a Kubernetes host node possesses surplus capacity, physical hosts eventually face resource saturation. When a Kubernetes worker node lacks the physical memory needed to accommodate an expanding Postgres instance, Lakebase invokes live virtual machine migration powered by NeonVM and QEMU/KVM hypervisors.

During a live migration, the running virtual machine is transferred to an uncongested Kubernetes node while retaining its designated private IP address and network interfaces. Client connection pools maintain their existing TCP handshakes completely unaware that the underlying hypervisor has shifted. Because the compute instance maintains negligible durable local state, the migration payload consists solely of guest RAM contents and active CPU execution registers, allowing zero-downtime transfers to finalize in fractions of a second.

Three Target Metrics: CPU, Memory, and Working Set Size

Establishing the low-level infrastructure to alter VM resources without terminating connections solves only half the scaling challenge; determining precisely when and how much to resize requires sophisticated telemetry. Naive threshold monitoring produces disruptive resource oscillations, where instances thrash between oversized and undersized allocations. Lakebase Postgres balances stability and responsiveness by synthesizing three independent metric signals into distinct compute targets.

  • CPU load target: Tracking processor demand via cpuGoalCU.
  • Memory consumption target: Protecting guest OS stability via memGoalCU.
  • Working-set cache target: Maintaining buffer hit rates via lfcGoalCU.

The autoscaling engine calculates each target independently and selects the maximum compute unit value among the three, clamping the result within user-configured minimum and maximum bounds (the autoscaling limits) to determine final capacity.

goalCU = max(cpuGoalCU, memGoalCU, lfcGoalCU)

One-Minute Load Average Regulation for CPU (cpuGoalCU)

Processor utilization is governed through the node-level autoscaler-agent, which samples the guest VM's one-minute CPU load average every five seconds. The target sizing, designated as cpuGoalCU, seeks to keep the one-minute load average at or below 90 percent of available CPU capacity. Utilizing a one-minute rolling average successfully damps micro-bursts and fleeting query spikes, while the rapid five-second polling frequency guarantees that legitimate workload surges trigger timely capacity expansions.

Sub-Second Polling and Out-of-Memory Defense (memGoalCU)

Memory operates under severe failure characteristics that demand vastly different handling from CPU contention. When CPU capacity is temporarily saturated, queries merely experience latency degradation; conversely, when PostgreSQL exhausts physical RAM, the Linux kernel invokes the Out-of-Memory (OOM) Killer, terminating database processes via SIGKILL and triggering abrupt service failure. Memory exhaustion therefore requires an exceptionally rapid defense mechanism.

The autoscaling architecture observes memory through a dual-cadence model: the host-level autoscaler-agent inspects overall virtual machine memory metrics every five seconds, while the internal vm-monitor daemon resident inside the guest VM tracks PostgreSQL memory allocation every 100 milliseconds (0.1 seconds). The memory algorithm establishes memGoalCU to ensure memory consumption remains strictly below 75 percent of total allocated RAM. The remaining 25 percent headroom provides an essential buffer against aggressive query allocations while reserving space for the guest Linux kernel.

In early engineering iterations, Neon attempted to utilize Linux cgroup memory.high notifications to drive memory expansion. However, crossing memory.high boundaries triggered aggressive kernel memory reclamation and throttled active processes inside the cgroup, inducing erratic query latency. Transitioning to 100-millisecond active polling delivered predictable, stable telemetry without kernel throttling artifacts.

Eliminating Network Wait Blind Spots via Cache Sizing (lfcGoalCU)

Conventional autoscalers possess a profound blind spot regarding database buffer caches. In transactional database operations, query throughput depends directly on having frequently accessed index and table blocks cached locally in memory. When the local cache is undersized, worker threads continuously stall waiting for pages to be pulled across the network from remote pageservers.

During these network I/O stalls, CPU cores remain largely idle waiting on data packets, resulting in deceptively low CPU utilization metrics. A simplistic CPU-driven autoscaler observes 15 percent processor usage and mistakenly downscales the instance, starving the engine of cache precisely when memory expansion is needed most. Lakebase Postgres resolves this paradox by introducing lfcGoalCU, which directly measures and projects the active working set of the database cache (historically known as the Local File Cache or LFC) as an autonomous third signal.

Augmenting HyperLogLog with Time for Real-Time Cache Projection

A database workload's working set represents the distinct collection of table blocks, metadata, and index pages accessed repeatedly over a given evaluation period. While maintaining an exhaustive in-memory hash set of every visited page identifier would yield exact counts, the memory overhead of storing millions of block addresses would defeat the purpose of optimization, introducing severe memory bloat.

Inherent Limitations of Standard Monotonic HyperLogLog

Probabilistic cardinality estimation via HyperLogLog (HLL) has long been the standard technique for estimating distinct elements within constrained memory. Standard HLL hashes item identifiers, routes them to register buckets via leading bits, and tallies maximum observed leading zeroes in the remaining hash bits. This statistical approach permits tracking millions of distinct items with just a few kilobytes of state and bounded error.

However, traditional HyperLogLog exhibits a fatal flaw when applied to dynamic autoscaling: standard registers are strictly monotonic. Once a register bucket records an observation, it retains that high-water mark indefinitely. It cannot record when that item was observed, or whether the query responsible for the page access terminated hours ago. If standard HLL were employed, a single early morning batch export or analytical table scan would permanently inflate the cardinality estimate, forcing the database to maintain an oversized cache long after the heavy query completed.

Storing Observation Timestamps in Place of Static Bitflags

The Lakebase engineering team resolved this accumulation dilemma by fundamentally transforming the internal storage format of HyperLogLog registers. Rather than setting static bit values upon observing a hash pattern, the Lakebase estimator stores the **current epoch timestamp** directly within the register array.

When the system seeks to estimate unique pages accessed since a historical threshold timestamp T, the algorithm treats register entries containing timestamps updated after T as active, while treating older entries as empty. This elegant modification allows a single compact register structure to yield accurate cardinality estimates for any arbitrary sliding time window ending at the present moment.

  • Unique database pages accessed within the trailing 1-minute window.
  • Unique database pages accessed within the trailing 5-minute window.
  • Unique database pages accessed within the trailing 60-minute window.

Every 20 seconds, the node-level autoscaler-agent queries this timestamped HyperLogLog array, capturing a granular spectrum of working set curves across historical windows spanning 1 to 60 minutes.

Searching for Working-Set Jumps and Forward Cache Allocation

Even with timestamp-aware working-set estimation, determining the optimal evaluation window poses a critical engineering trade-off. Selecting a window that is too short (such as 1 or 2 minutes) causes the autoscaler to aggressively evict cache allocations during brief query pauses, inducing thrashing when the next batch of requests arrives. Conversely, enforcing an indiscriminate 60-minute window retains memory allocations for terminated batch workloads far longer than necessary, inflating billing costs.

Detecting Cardinality Jump Points Beyond the Five-Minute Boundary

Lakebase Postgres resolves this dilemma through an automated jump detection algorithm that inspects the rate of cardinality expansion across expanding window durations. For a steady, healthy transactional workload, increasing the time window from 5 to 30 minutes adds elapsed time but relatively few new page addresses, because the engine repeatedly touches the same active dataset. Consequently, the estimated working set size plateaus into a stable curve.

When a heavy analytical workload has recently terminated, the estimated working set exhibits a distinct structural signature: short windows reflect only the modest working set of current light traffic, but as the window expands to encompass the recent historical batch query, the cardinality estimate jumps sharply. The algorithm systematically scans for this jump point, selecting the stable plateau preceding the jump as the genuine working set of the active workload.

start after the initial downscale delay

for each working-set window:
    measure growth before this point
    measure growth after this point

    if later growth is much larger than earlier growth:
        return the estimate before the jump

return the estimate from the 60-minute window

The jump search begins evaluating strictly after the 5-minute mark. This deliberate initial delay prevents compute resources from prematurely contracting during transient workload pauses. If no sharp cardinality surge is detected across the full span, the algorithm falls back to the 60-minute estimate, which represents the natural steady-state profile of an active, stable database.

Forward Cache Projection Over Twenty-Second Control Cycles

Merely measuring past and current working set sizes introduces latency when workloads abruptly begin scanning new tables. If cache allocation expands only after blocks have already been read, early pages are evicted to accommodate subsequent pages, forcing the engine to fetch those evicted blocks over the network a second time.

To preempt this thrashing, the algorithm calculates the rate of change across consecutive window estimates and projects working-set growth forward into the upcoming control cycle. Because cache metrics are evaluated every 20 seconds, this projection covers only a fraction of a minute into the future. Restricting projections to sub-minute horizons prevents the system from overreacting to short-lived data spikes, avoiding severe capacity oscillations. The resulting projected value sets lfcGoalCU, allocating local cache headroom up to 75 percent of VM RAM.

Four Coordinating Components and the Three-Tier Control Loop

Once goalCU is synthesized from CPU, memory, and working-set signals, the system must execute the resize operation on the live database virtual machine. Standard Linux container architectures face significant limitations when attempting to dynamically adjust physical memory limits on running processes without violating kernel security boundaries. Lakebase Postgres overcomes this by executing each PostgreSQL instance within a dedicated lightweight virtual machine orchestrated within Kubernetes, delivering hardware-level virtualization with dynamic resource hot-plugging.

Architectural Roles of Agent, Monitor, Scheduler, and NeonVM

Four specialized distributed components coordinate every capacity adjustment to guarantee seamless resource modifications.

  • autoscaler-agent: Runs as a daemon on every Kubernetes worker node, gathering telemetry from local Postgres VMs, computing goalCU targets, and driving scaling workflows.
  • vm-monitor: Resides inside each guest VM alongside PostgreSQL, continuously tracking process memory allocations, validating downscale commands, and dynamically resizing cache boundaries.
  • Modified Kubernetes Scheduler: Maintains the authoritative global inventory of cluster physical capacity, validating and approving all upscale requests before memory is committed.
  • NeonVM Controller: A custom Kubernetes operator built on QEMU and KVM that hot-plugs vCPU and RAM directly into active guest VMs and manages live migrations.

The scale-up workflow executes through an explicit five-step coordination sequence:

  1. The autoscaler-agent evaluates CPU, memory, and cache telemetry, establishing a higher goalCU target.
  2. The modified Kubernetes scheduler checks host node memory headroom and formally approves the allocation.
  3. The autoscaler-agent updates the corresponding NeonVM custom resource definition (CRD).
  4. The NeonVM controller commands the QEMU hypervisor to hot-plug vCPUs and memory into the live guest.
  5. The in-guest vm-monitor detects the expanded RAM and immediately expands the compute cache buffer.

Maintaining the modified Kubernetes scheduler as the single source of truth for resource commitments is critical. Without centralized scheduler approval, a standard Kubernetes scheduler might schedule a heavy unrelated container on a node at the exact moment the autoscaler committed remaining memory to an expanding Postgres VM, inducing severe host-level memory overcommit.

Scale-down operations employ the same architectural components but enforce rigorous validation within the guest. If a downward adjustment is requested, the vm-monitor verifies that current active queries and operating system routines can safely execute within the reduced footprint. If shrinking memory threatens to compress headroom below safe operational boundaries, the downscale is rejected, eliminating the risk of kernel-level crashes.

The Multi-Tiered Feedback Loop Across 100ms, 5s, and 20s Intervals

The operational resilience of the autoscaling architecture stems from three distinct control timescales operating concurrently:

  • 100-millisecond cycle: The in-guest vm-monitor checks PostgreSQL heap and query allocations to prevent sudden memory exhaustion and block unsafe shrink commands.
  • 5-second cycle: The host autoscaler-agent polls 1-minute CPU load averages and overall memory metrics to adjust to shifting compute demands.
  • 20-second cycle: The autoscaler-agent computes timestamped HyperLogLog working set windows and forward projections to tune cache capacity.

Treating capacity reductions with the same algorithmic rigor as capacity expansions ensures that workloads stop paying for cloud resources the precise instant those resources are no longer required.

Engineering Implications: Eliminating Overprovisioning and Cloud Waste

In modern cloud engineering environments, volatile database workloads have historically incurred severe cost penalties. Applications experiencing dramatic diurnal traffic swings, promotional flash sales, or scheduled batch pipelines have routinely maintained instances provisioned for tenfold their baseline load. Over an annual billing cycle, this defensive overprovisioning squanders millions of dollars in unutilized compute capacity.

As advanced artificial intelligence workloads drive global competition for data center compute capacity, overpaying for idle peak capacity is becoming an unsustainable engineering habit. The mechanisms demonstrated by Lakebase Postgres outline a clear path forward for cloud data architectures.

  • Rethinking sharding thresholds: Before undertaking the immense developmental burden of horizontal partitioning and distributed query gateways, teams should leverage zero-downtime vertical scaling to absorb traffic surges within a single relational instance.
  • Adopting cache-aware observability: Engineering teams must look past CPU-only dashboard alerts, establishing monitoring pipelines that distinguish network I/O stalls from genuine idle states via buffer cache working set tracking.
  • Reclaiming idle capital through symmetric scaling: Infrastructure designs must prioritize aggressive, safe scale-down capabilities that immediately relinquish surplus capacity once workloads stabilize.

Lakebase Postgres is deployed across both Neon's serverless platform and Databricks' Data Intelligence Platform. While Neon optimizes the engine as a flexible backend for developers, startups, and autonomous agent infrastructure, Databricks integrates the same core architecture directly into Unity Catalog governance, lakehouse analytics, and enterprise data workflows.
