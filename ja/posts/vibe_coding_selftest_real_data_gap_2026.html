1. 自己テストの緑信号が覆い隠すものとバイブコーディングの死角

AIコーディングエージェントに実装を委ねる際、信頼性を確保するために広く導入されている手法が自己テスト（Self-test）の自動化である。生成されたスクリプトに --selftest 実行オプションを設け、内部の検証ルーチンが例外なく完了した際にターミナルへ GATE_OK という成功シグナルを出力させるルールだ。エージェントが問題を自己解決した証拠として緑信号を受け取った開発者は、作業が問題なく完了したと判断しがちである。

しかし、テスト合格という機械的なシグナルは本番データ環境での正常動作を何ら保証しない。単体テストがバグ検出ではなく領域表示になりやすい問題は単体テスト批判の考察で整理し、急速に構築されたスタックが隠蔽するリスクはバイブコーディングスタックの技術的神話で論じた。また複数エージェントによる検証連携はOrdewellアーキテクチャ分析で扱った。本稿が扱うのはテスト一般論ではなく、単一のエージェントが実装コードと検証フィクスチャを同時に作成する際に生じる仮説の重複と一致現象である。

2026年9月25日と26日の2日間にわたり、Claude Codeエージェントを用いてブログ運営ツール3件を作成した開発者wonizz氏の記録は、この構造的盲点を鮮明に示している。3つのツールはいずれも緑信号を受けていた（台帳ツールは自己テストの GATE_OK、広告点検ツールは自己テスト通過、需要ゲートは派生語65件で公開許可）が、実際の本番データを注入した瞬間に誤診を下すか一致に失敗した。この現象を解明するには、失敗した3つのツールの具体的数値と要因を精査する必要がある。

  • 自己認証の錯覚 — エージェントが作成したテストデータと検証ロジックは自身の実装コードの前提をそのまま複製するため、バグを自己検出できない。
  • 本番データとの接点喪失 — 隔離された環境で架空入力を対象に実行されたテストは、外部システムの複雑なHTMLや例外的レスポンスを捉えられない。
  • 短絡的算術による因果断定 — 外部システムの複雑な挙動を中間観測なしに単純な不等式に還元し、誤ったシステム障害要因を出力する。
  • ゲート入力構造の脆弱性 — エージェントがフォーカスキーワードを広い上位語で書き、ゲートの入力をゲートを通過しようとする側が自ら書く構造だったため、そのまま通過した。

2. 事例1: post-ledger.py — innerText汚染と261件中6件一致

最初のツール post-ledger.py は、Asideブラウザを用いてGoogle Search Consoleの実績表をスクレイピングし、ブログ台帳に記事ごとの表示回数と検索順位を記録する役割を担っていた。エージェントは自己テスト環境で整ったURL文字列を生成して検証を実行し、問題なく GATE_OK を出力した。

2.1 Search Console実績表の取得とボタン文言の混入

だが完成したツールを実際のSearch Console実績データに接続したところ、深刻な乖離が生じた。ブログ台帳に登録された全261件の記事のうち、Search Consoleの実績表と正常に一致した記事はわずか6件にとどまった。原因は、ブラウザが描画したSearch Console実績表の最初のセルの innerText を未加工のまま読み取った点にあった。画面上には純粋なURLのみが表示されているように見えたが、マウスホバー時に表示される操作ボタンのテキストがテキストノードに一括で含まれていたのである。

https://.../mcp-server-with-cusor-ai/ 클립보드에 URL 복사 새 탭에서 열기 URL 검사

ツールはこのボタン文言が付加された汚染文字列を完全一致キーとして用い、台帳の元記事URLと突き合わせていた。エージェントの自己テストは最初から純粋なURL文字列のみをフィクスチャとして注入していたため、実際のブラウザ描画で生じる文字列結合を全く予測できなかった。

2.2 正規表現による100件一致と未確認の2要素

問題の解決は、セルのテキストを丸ごとキーにせず、その中からURLだけを抜き出して正規化するキー整理関数を入れることで達成された。原典がその原理を再現してみせた1行は以下の通りである。

python3 -c "import re; raw='https://blog.wonizz.com/2025/09/12/mcp-server-with-cusor-ai/ 클립보드에 URL 복사 새 탭에서 열기 URL 검사'; print(re.search(r'https?://\S+', raw).group(0))"

キーを正規化して台帳を再集計した結果、261件中100件がSearch Console表と正確に結合された。残る161件が一致しなかったのは、3か月の集計期間内に検索露出が全く発生せずSearch Console表に行自体が存在しなかったためであり、原著者はこれを正常な範囲と判断した。また自己テストのフィクスチャにも、ボタン文言が付いた実際の形の入力を追加し、同じ汚染が再び入ればテストが先に落ちるようにした。「261件中255件が壊れていた」のではなく、100件の有効データが存在したにもかかわらずツールが94件を脱落させていた点が本質である。なお原著者は、CSS描画においてなぜボタンテキストが innerText に含まれたのか、そして全行が一様に汚染されていた中で初期実行時に6件だけ一致した理由は深掘りせず未確認事項として残した。

3. 事例2: ad-inventory.py — 単純算術判定と実際の2段階広告損失

2つ目のツール ad-inventory.py は、ブログ記事のHTMLをパースして挿入広告スロット数を数え、外部計測のインプレッション数と突き合わせて運用の異常原因を自動判定するスクリプトであった。このツールも自己テストを軽快に通過した。

3.1 3.67個対0.94個の算術と描画失敗の断定

実際のブログ記事18件のサンプルを対象に実行したところ、1ページあたりの明示スロット数は平均3.67個であったのに対し、実測インプレッション数は1ページあたり平均0.94個にとどまった。ツールは、前者が後者の2倍を超えるという短絡的な算術ルールに基づき、以下の診断結果を出力した。

原因判定 描画失敗

エージェントが埋め込んだロジックは、明示スロットが実際の表示回数より多ければ描画が失敗しているという単線的な因果関係の仮説に縛られていた。原典によれば、自己テストは計算が合っているかを見ており、計算は実際に合っていた。誤っていたのは解釈であった。

3.2 実際のブラウザ描画確認と28日間レポートの167件・118件

しかしブラウザで実際のページを開き、スロットが広告iframeで埋まっているかを数えてみると、結果は診断と完全に異なっていた。長文記事では6スロット中5スロットが、短文記事では7スロットすべてが、トップページでは2スロットすべてが広告iframeで正常に埋められていた。描画自体は破綻していなかったのである。

公式の広告管理レポート（28日間）を精査して判明した損失の実態は、全く異なる2段階構造であった。対象期間中の1ページあたり広告リクエスト数は2.47件であり、目標値を既に上回っていた。問題はリクエスト後に生じていた。配信されなかったリクエストが167件、配信されたもののインプレッションとして集計されなかったリクエストが118件であった。すなわちスロットが足りなかったのでも描画が壊れていたのでもなく、配信段階の問題であった。ツールは直接観測できない領域を算術で断定し、誤った診断を下したのである。

4. 事例3: 需要ゲート — キーワード縮小と派生語65件の虚像

3つ目のツールは、ブログ記事の需要を事前判定する「需要ゲート」自動化であった。Google検索のオートコンプリート派生語を収集し、派生語が20件未満の不人気テーマは記事生成および公開パイプラインを停止させる安全装置として設計された。

4.1 フォーカスキーワードの縮小とゲート回避

2026年9月26日未明の自動生成において、エージェントは「Linuxフォルダ比較」の記事のフォーカスキーワードを、広い上位語である「Linux」と書いた。ゲートはそのキーワードで65件の派生語を収集し、基準値の20件を余裕で上回ってゲートを通過した。こうして生成された記事はその日の朝に実際に公開された。

記事が実際に答えている検索語「Linuxフォルダ比較」で派生語を測り直すと、わずか2件であった。Googleトレンドの12か月平均値は0であり（同日計測の「Linuxコマンド」は18.9）、同日に計測した「Linux diff」の派生語も9件にとどまり、下限値20件を大きく下回っていた。再計測でゲートが止めるべき記事だったことが判明し、その記事は削除された。ゲートの入力をゲートを通過しようとする側が自ら書く構造だったため、広い上位語を書くだけでどんなテーマでも通過できたわけである。

4.2 下限値20件とミューテーションテストのラムダ実行結果

原典は事例3の再発防止として自動制作の指示文に規則を一行加えたが、規則の文章はコードゲートではないため、完全に防げたと言うのはまだ早いと記している。一方、原典は変異テストの原理を、需要ゲートのように20未満を止める判定で再現してみせる。元の条件と等号を加えた変異を入力5、65、20で実行したコマンドは以下の通りである。

python3 -c "gate=lambda n: n < 20; mutant=lambda n: n <= 20; [print(n, gate(n), mutant(n)) for n in (5, 65, 20)]"

このコードを実行すると、以下の3行が出力される。

5 True True
65 False False
20 False True

基準値20において、元のロジック（gate）は公開を許可する False を返すが、等号を含む変異ロジック（mutant）は遮断を意味する True を返す。エージェントが作成したテストに境界値20のテストケースが含まれていなければ、不等号条件が書き換わった変異コードが混入してもテストは通過してしまう。

post-ledger.py 自己テスト GATE_OK 261件中6件のみ一致（修正後100件） 表の最初のセルにはURLだけがある
ad-inventory.py 自己テスト合格 iframeは正常描画、実態は未配信167件およびインプレッション未集計118件 スロットが表示より多ければ描画失敗だ
需要ゲート 派生語65件で公開許可 実際の検索派生語は2件、トレンド0（公開後削除） 書かれたキーワードが記事の検索語だ

5. 同一エージェントが作成したコードとテストが共有する稼働欠陥

3つの事例に通底する本質的な教訓は明白である。失敗の原因は構文エラーやエージェントの誤字といったコードレベルの不具合ではない。「3件ともコードではなく入力や解釈に対する前提が誤っており、その前提をコードとテストが同様に抱え込んでいたためである」。

人間同士で開発を進める場合、実装者と検証者は分離されることが多い。実装者が外部データに関して誤った思い込みを抱いていても、検証者は別の視点からエッジケースを突きつけ前提を崩す。しかし単一のエージェントに実装とテストの双方を一任すると、以下の構造的死角が生じる。

  • 前提の対称的複製 — エージェントはコードを書く際に頭の中に描いたデータ形式をそのままテストのフィクスチャとして流用する。表のセルにボタン文字が付加される事態を想定できなければ、テストデータにも純粋なURLのみを投入する。
  • 循環論法に陥った検証 — 原典によれば、テストは計算が合っているかを見ており、計算は実際に合っていた。誤っていたのは「スロット数が表示回数より多ければ描画失敗」という解釈であった。因果関係の正しさではなく、計算がルール通りかだけを確かめていたことになる。
  • テストケース拡充の限界 — 原著者は、テストケースを数個増やしても捕捉できたとは思えないと見る。必要だったのはより多くのテストではなく別の種類の確認だった、というのが原典の結論である。
  • 完了シグナルへの盲信 — ターミナルに表示される GATE_OK は安全性の客観的証明ではなく、エージェントが自己の偏見の枠組み内で整合性を満たしたという閉鎖的確認に過ぎない。

6. 3行の完了条件 — 変異検証、実データ1回突合、判定不可の明記

wonizz氏はこれら3つの失敗を経て、ツールの完了基準を刷新した。エージェントが出力する GATE_OK 1行を完了の証とする運用を撤廃し、3行の厳格な完了条件を新たに策定した。

6.1 変異テストによる破損コードの捕捉

第1の条件はミューテーションテスト（Mutation Testing）である。テストスイートの検出力を確認するため、実装コードの不等号や境界条件を意図的に変更した壊れたコード（変異体）を投入し、テストが確実に失敗するかを検証する。変異体を注入してもテストが合格するなら、そのテストは無力である。原典ではJavaのPITやJavaScript・C#のStrykerに言及しているが、小規模なスクリプトでは手動で2〜3個の変異を注入して検証する手法が取られた。

6.2 実データ1回実行と期待値範囲の目視照合

第2の条件は、ツール完成直後に必ず本番実データで最低1回実行することである。合成モックデータで満足せず、実際のSearch Consoleやブラウザ環境で1回動かし、得られた一致率や件数が事前に人間が想定した期待範囲に収まっているかを目視で突き合わせる。261件中6件という異常値はこの段階で即座に発見される。

6.3 観測不能領域の判定不可処理

第3の条件は、ツールが直接確認できない領域について因果関係を安易に予断しないことである。スロット数と表示数の比率のみから外部広告サーバーの動作を描画失敗と断定せず、取得不能な領域については「判定不可」とその理由を明確に出力するようコードを設計する。

完了条件 何を防ぐか（原典） 今回の事例で該当するもの（原典）
1. 変異テスト検証 何も確認しないテスト テスト自体の品質
2. 実データ1回突合 入力前提の誤り 事例1（post-ledger.py）、事例3（需要ゲート）
3. 判定不可の明記 算術による断定 事例2（ad-inventory.py）

これら3つの条件をエージェントへの作業指示に組み込むため、プロンプトに付加すべき3行の要求文は以下のように定式化される。

  • 変異検証の指示 — 「自己テスト作成後、境界値や条件を変更した変異を2〜3個投入し、テストがすべて失敗することを提示してください」
  • 実データ1回検証の指示 — 「作成直後に実データで1回実行し、一致率や件数を期待範囲とともに報告してください」
  • 観測限界明記の指示 — 「このツールが直接観測できない事項は勝手に判定せず、判定不可とその理由を明記してください」

7. 期待範囲の事前定義とバイブコーディングの現実的境界線

3つの完了条件の中で最も本質的な洞察は、「期待値の範囲だけはエージェントに決めさせず、人間が事前に明記すべきである」という原著者の結論である。原典が挙げる理由は、エージェントに文脈がないことではなく、期待値を決めるタイミングにある。

原著者には「261件中少なくとも数十件はつながるはずだ」という感覚があったため6という数字がおかしく見えたのであり、期待値がなければ6件の台帳をそのまま信じて次の段階へ進んでいただろうと書く。そして結果を見た後に決めた期待値はその結果に引きずられやすいため、実行前に人間が書き留めておく数字1つが最も安価な安全装置だと見ている。

  • 期待数値の先行設定 — 一致率の下限値、抽出件数の下限、許容誤差範囲はコーディング開始前にプロンプトへ規定する。
  • 指示文はコードゲートではない — 原典は、規則の文章だけで守られている箇所は、コードゲートに移すまでその通過を信じないことにした。キーワードと本文の一致率を強制する定量ゲートは本稿の提案である。
  • 出発線としての自己テスト — 原著者の結論通り、バイブコーディングにおける自己テスト合格は完了ではなく、実データ検証を開始するための最低限の出発点に過ぎない。

本稿で取り上げた記録は個人ブログの3つの自動化ツールから得られた実例であり、バイブコーディング全般において同一の割合で発生すると一般化することはできない。原著者も、言えるのはこの3回の形までだと明言している。ただし、自己テストの緑信号を完了とみなす似た働き方をしている場合には参考になるだろう。自動化における最後の防衛線はテストコードではなく、実データの数値を直視し観測の限界を見極める人間の目である。

8. 確認できなかった事項

本稿は原典の記録に基づき事実を忠実に整理したものであり、原典で言及がなく客観的に確認できなかった事項は以下の通りである。

  • Search Console実績表において、操作ボタン文言がなぜCSS描画を経てセルの innerText ノードに結合されたのかというフロントエンドの実装要因は原著者により分析されておらず確認できなかった。
  • Search Console実績表の全行が同様に汚染されていたはずであるにもかかわらず、初期実行時に特定6件の記事のみが一致に成功した具体的要因は原著者が追究しなかったため確認できなかった。
