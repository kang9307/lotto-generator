契機 — Git 3.0計画とSHA-256既定化を巡る議論

バージョン管理システムの核心は、変更履歴の不変性を維持し、過去の任意のソースコードを正確に再現することにある。Gitは2005年の初期設計以来、20年以上にわたってオブジェクトの一意識別子として160ビットの暗号学的ハッシュ関数SHA-1を採用してきた。しかし、暗号学界においてSHA-1の衝突脆弱性に関する研究が進展し、理論的および実践的な衝突生成が実証されたことを受け、Gitプロジェクト内部でも次世代ハッシュへの移行方針が長期にわたり協議されてきた。Git公式文書BreakingChanges.adocによれば、将来のメジャーリリースであるGit 3.0における主要な破壊的変更として、新規リポジトリの既定オブジェクト形式（Object Format）を従来のSHA-1からSHA-256へ移行する計画が明記されている。

この方針に対し、開発者コミュニティでは期待と懸念が交錯している。GitHubの共同創業者であり現在はGitButlerを率いるScott Chacon氏は論説を公開し、Git 3.0で新規リポジトリの初期値をSHA-256へ一律移行する計画は、得られるセキュリティ上の実利に比して開発生態系全体が支払うコストが過大であると警鐘を鳴らした。同氏の論点は単なる変更への抵抗ではなく、リポジトリ内のオブジェクトを特定する「コンテンツアドレス指定（Content Addressing）」と、コード作成者の素性を保証する「出所への信頼（Trust）」を混同している点にあるという指摘に基づいている。

本稿では、Git 3.0計画に含まれるハッシュ移行の経緯を整理し、暗号学の観点から指摘される攻撃ベクトルの実効性と限界を精査する。さらに、基本形式変更に伴うリポジトリ間の相互運用断絶、サブモジュールの互換性崩壊、40文字の16進数文字列を前提とした各種開発ツールの誤動作など、現実的な移行コストを一覧化する。併せて、同氏が提案したコミット署名に基づく独立ツリー検証という代替案の技術的構造を公式文書と対比しつつ客観的に検証する。

Gitの完全性モデル — コンテンツアドレス指定とSHA-1の役割

Gitの内部構造を正確に捉えるには、Gitが単なる差分追跡ツールではなく「コンテンツアドレス指定のキー・バリュー型データベース」であるという本質を理解する必要がある。Gitに保存されるすべてのデータ（ファイル内容を表すblob、ディレクトリ構造を表すtree、履歴を繋ぐcommit、注釈付きtag）は、リポジトリに書き込まれる際に暗号ハッシュが計算され、その値がオブジェクトのキーとして使用される。保存される内容そのものがキーを決定するため、内容が完全に同一であるファイルはリポジトリ内で重複して保持されることなく、単一のオブジェクトとして参照される。

このアーキテクチャにおけるデータの完全性は、マークルツリー（Merkle Tree）構造によって担保されている。コミットオブジェクトはルートツリーのハッシュと親コミットのハッシュを直接記録する。したがって、過去の履歴に含まれる1文字の修正であっても、該当オブジェクトのハッシュ変更を引き起こし、連鎖的に上位ツリーおよび後続の全コミットハッシュを一変させる。最新コミット（HEAD）のハッシュを1つ確定させるだけで、それ以前に積み上げられた数百万のファイルと履歴全体の完全性を数学的に検証することが可能となる。

Linus Torvalds氏が2005年にSHA-1を選択した理由は、当時の水準において極めて高速であり、かつ偶然のハッシュ衝突が実用上完全に排除できると考えられたためである。この設計においてSHA-1ハッシュが果たす具体的役割は以下の通りである。

  • オブジェクトの識別と重複排除： リポジトリ内のオブジェクトを40文字の16進数キーで迅速に索引付けし、同一内容の重複保存を防止する。
  • 偶発的なデータ破損の検知： ストレージ障害やメモリのビット反転、ネットワーク伝送時の欠損を確実に検出する。
  • 履歴の不変性チェーン維持： 親コミットハッシュの連鎖により、過去の履歴が後から密かに改変されることを構造的に封じる。
  • 作業ツリーとの高速比較： インデックスに保持されたハッシュと作業ファイルを突き合わせることで、内容全体を再走査することなく変更の有無を即座に判定する。

数学的に160ビットの出力空間を持つSHA-1において、異なる2つのファイルが偶然同一のハッシュを持つ確率は、誕生日のパラドックスを勘案しても天文学的に低い。単一プロジェクト内に約1.4 × 1024個（1.4セプティリオン）もの無作為ファイルが存在して初めて、偶然衝突の確率が50%に達する。これまでに世界中で作成された膨大なGitリポジトリにおいて、自然発生的な偶然衝突は1件も確認されていない。

暗号学的破綻の現実的範囲 — 衝突攻撃と第2原像攻撃の相違

SHA-1が暗号学的に安全でないと見なされる契機となったのは、2017年のSHAttered攻撃や2020年のSHA-1 is a Shambles攻撃など、意図的な衝突生成の実証研究である。暗号理論においてハッシュ関数が「破綻した（Broken）」と言われる場合、日常会話における完全な無力化とは意味合いが異なる。ここでの破綻とは、天文学的な全数探索を行わずとも、大規模なGPUファームと数万ドル規模の予算を投入することで、「作為的に同一ハッシュを出力する2つの異なる入力」を生成可能な短縮手順が存在することを指す。

ここで極めて重要な工学的区別が存在する。ハッシュ関数への攻撃は「衝突攻撃（Collision Attack）」と「第2原像攻撃（Second-Preimage Attack）」に大別される。

  • 衝突攻撃（Collision Attack）： 攻撃者が事前に無害なファイルAと悪意あるファイルBを同時に計算し、双方が同一のハッシュ値を持つように作為的なペアを作り出す手法である。攻撃者は両方の入力値を完全に制御できる。
  • 第2原像攻撃（Second-Preimage Attack）： すでに公開・配布されている既存のファイルXに対し、事後的にXと全く同一のハッシュ値を出力する別の悪意あるファイルYを生成する攻撃である。
  • 計算複雑性の圧倒的な格差： 衝突攻撃は双方の入力値に自由度があるため計算量が相対的に少なく、SHA-1において実証に至った。一方、第2原像攻撃は固定された目標値に一致させる必要があるため、計算量は桁違いに跳ね上がる。
  • 旧式ハッシュの頑健性： 衝突耐性が完全に破綻したMD5であっても、第2原像攻撃に対しては実質的に耐性を維持している。地球上の約30億台のGPUをすべてRTX 5090に置き換え、毎秒2.2 × 1011回のMD5計算のみを継続した場合でも、期待される計算時間は宇宙の年齢に匹敵する約160億年を要する。

したがって、Gitにおいて攻撃者が既存のLinuxカーネルや既存ライブラリの特定コミットをそのまま残し、同一ハッシュを持つ悪意あるソースコードを事後的に差し替える第2原像攻撃は成立しない。現実に成立し得るのは、攻撃者自身が最初から作為的な衝突ペアを用意して無害なコードとして承認させ、後に悪意あるコードへすり替える衝突攻撃のシナリオに限られる。

完全性ハッシュと出所信頼の分離 — サプライチェーン攻撃の侵入経路

Scott Chacon氏の論考において最も本質的な指摘は、「内容の完全性（Integrity）」と「コードの出所に対する信頼（Trust）」を分離して設計すべきだという点である。Linus Torvalds氏も2005年のカーネルメーリングリストにおいて、ハッシュそのものをセキュリティの本体と見なすべきではなく、真の安全性は配布経路と認証にあると強調していた。開発者がリモートからコードを取得する際、真に信頼しているのはコミットハッシュという文字列ではなく、ホスティングサービスの認証基盤とメンテナーの権限管理である。

実際のソフトウェアサプライチェーンにおける侵入事件を分析すると、攻撃者が数万ドルの費用をかけてGPUを借り受け、SHA-1衝突ペアを計算してバイナリ内にノイズを付加するような高度な攻撃例は事実上存在しない。現実の侵害は、遥かに単純で低コストなソーシャルエンジニアリングや権限奪取によって引き起こされている。

  • 認証情報やAPIトークンの漏洩： npmやPyPIなどのパッケージレジストリやリポジトリ管理者のアカウントが侵害され、正規のリリースとして悪意あるコードが配信される。
  • メンテナー権限の譲渡や乗っ取り： 活動が停滞したオープンソースプロジェクトの管理権限を引き継ぎ、正規コミットとしてバックドアを混入させる。
  • 依存関係の偽装（タイポスクワッティング）： 有名パッケージと類似した名称の悪意あるパッケージを公開し、設定ミスにより取り込ませる。
  • リポジトリ書き込み権限の悪用： 書き込み権限が奪取された場合、オブジェクトハッシュがSHA-1であるかSHA-256であるかにかかわらず、メインブランチへ直接悪意ある変更を投入できる。

信頼できるリモートリポジトリからコードを取得する大多数の開発環境において、オブジェクトハッシュの暗号強度が侵害の成否を分けるわけではない。リポジトリへのアクセス制御が破られればハッシュ形式に関係なく侵害が発生し、逆にアクセス制御と署名検証が機能していれば衝突攻撃の入り込む余地は極めて狭小となる。

生態系の移行コスト — 相互運用の分断とサブモジュール・ツールの破損

Git 3.0において初期オブジェクト形式をSHA-256へ切り替える方針は、長期的な暗号強度の向上を意図したものである。しかし、初期値が変更された瞬間、開発生態系全体が深刻な互換性の断絶と莫大な移行コストに直面する。ハッシュ形式の変更は、単なる設定項目の切り替えにとどまらず、Gitの基盤となるアドレス体系そのものを全面的に改変することを意味するためである。

指摘されている主な移行コストおよび生態系の破損要因は以下の通りである。

  • リポジトリ間における相互運用の完全断絶： SHA-1リポジトリとSHA-256リポジトリは直接通信できず、パッチの適用やfetch、pushの互換性が失われる。両者は互いに孤立した体系となる。
  • サブモジュールの多重管理負担： サブモジュールは親リポジトリと同一のハッシュ形式を持つ必要がある。ライブラリ開発者は、既存のSHA-1利用企業と新規のSHA-256利用企業の双方を支えるため、2系統のリポジトリを並行保守せざるを得なくなる可能性がある。
  • 40文字固定ハッシュを前提としたツールの機能停止： 過去20年間に構築された膨大なCI/CDスクリプト、静的解析ツール、リリース自動化システム、正規表現パーサーが40文字の16進数文字列を前提に作成されており、64文字のSHA-256ハッシュにより広範に破損する。
  • サードパーティ製Gitライブラリの対応遅延： GitコアはGPLライセンスのため直接リンクが難しく、各言語で独自に再実装されたライブラリ（libgit2、go-git、dulwich等）が普及している。これらのライブラリの多くはSHA-256への完全対応が未完了である。
  • 履歴変換に伴う署名の失効とリンク切れ： 既存リポジトリをSHA-256へ変換すると全オブジェクトのハッシュが再計算されるため、過去のGPG/SSHコミット署名がすべて無効化され、イシューやドキュメントに記載されたコミットURLが一斉にリンク切れとなる。
  • ホスティングインフラの運用負荷： GitHubやGitLab等のサービスは形式ごとの厳格な分離や変換層の維持を迫られ、莫大なインフラコストを背負うことになる。

公式サポート状況とローカル検証 — 読み取り専用によるオブジェクト形式確認

Gitプロジェクトはバージョン2.29以降、実験的機能としてSHA-256オブジェクト形式を実装してきた。現行のGit環境において既存の運用リポジトリを破壊することなく、SHA-256リポジトリの挙動を確認したり形式を判別したりすることは安全に実施できる。この際、運用中のリポジトリに対して履歴書き換えや強制プッシュを行ってはならず、独立した一時ディレクトリでの非破壊的コマンドのみを用いるべきである。

公式マニュアル（git-init、git-rev-parse）に記載された安全なコマンド例は以下の通りである。

# 一時ディレクトリにSHA-256形式の新規リポジトリを初期化（非破壊検証）
                    git init --object-format=sha256 /tmp/test-sha256-repo
                    
                    # 対象ディレクトリに移動して現在の形式を確認（読み取り専用）
                    cd /tmp/test-sha256-repo
                    git rev-parse --show-object-format
                    
                    # 既存の運用リポジトリで形式を確認（読み取り専用、通常はsha1を出力）
                    git rev-parse --show-object-format

上記コマンドの実行時における留意点は以下の通りである。

  • 形式の不変性： リポジトリ初期化時に決定されたオブジェクト形式は、設定ファイルの書き換えによって後から変更することはできない。
  • リモート受け入れの確認： ローカルでSHA-256リポジトリを作成しても、送信先リモートが当該形式をサポートしていなければプッシュ時にエラーとなる。
  • 社内ツールの事前検証： 社内のCI/CD環境やデプロイスクリプトが存在する場合、一時リポジトリで生成したコミットを用いて64文字ハッシュに対する挙動を安全に試験できる。
  • 全体ポリシーの策定： 将来Git 3.0が導入された際に備え、システム全体の設定（init.defaultObjectFormat = sha1）により従来の挙動を維持する方針の要否を検討できる。

代替案としての署名ベース独立ツリー検証 — 仕組みとトレードオフ

生態系の断絶を回避するためChacon氏が提起した代替案は、「コミットやタグへの署名時に作業ツリー全体のチェックサムを独立計算し、署名ヘッダーに格納する方式」である。この手法では、リポジトリ内部のオブジェクト識別子は従来の40文字SHA-1のまま維持されるため、既存のツール群やサブモジュールの互換性は100%保持される。その上で、厳密な検証が求められるリリース成果物や重要コミットに対してのみ、SHA-256やBLAKE3などの強固なハッシュを重畳適用する。

この発想には先例が存在する。2015年にColin Walters氏が公開したgit-evtagは、コミット、ツリー、全blobを再帰的に走査してGit-EVTag-v0-SHA512チェックサムを算出し、タグに埋め込んで署名を行う。Chacon氏はこの概念を拡張し、Rust製の概念実証ツール（tree-sha256）を開発して大規模リポジトリでの計算性能を計測した。

# Scott Chacon氏によるtree-sha256の計測結果（M5 Macマルチスレッド）
                    - Chromiumリポジトリ（全サブモジュール込み35GB、210万ファイル）：約5秒
                    - Linuxカーネルリポジトリ（作業ツリー1.5GB）：約257ms
                    - Gitコアプロジェクトリポジトリ：約17ms

この代替手法とリポジトリ全体のSHA-256移行を比較した場合の長所と短所は以下の通りである。

  • 生態系の完全な継続性： リポジトリ形式が変更されないため、既存のスクリプトやツール、コミットURLが一切破損しない。
  • 暗号学的アジリティの確保： 将来SHA-256が陳腐化した場合でも、リポジトリ全体を再移行することなく署名ヘッダーのアルゴリズムを更新できる。
  • 二重の完全性担保： 検証時にはSHA-1と独立ツリーハッシュの双方が合致する必要があるため、単一アルゴリズム移行よりも理論上高い衝突耐性を発揮する。
  • 構造的制約 — 全コミットへの波及欠如： マークルツリーによる自然な連鎖保護と異なり、独立ツリー署名は明示的に署名されたコミットやタグに限定され、中間の全履歴を自動で保護するわけではない。

移行摩擦世界中の数億のリポジトリとライブラリで移行作業が発生署名・検証ツールの追加のみで即座に段階導入が可能
保護の適用範囲リポジトリ内の全コミット・全オブジェクトへ暗号強度を適用署名ヘッダーが付与されたタグおよび特定コミットに限定

この議論は、内部構造の完全な刷新による理論的完全性の追求と、実用的な互換性維持による現実的セキュリティ確保の間のエンジニアリング上の選択を浮き彫りにしている。
