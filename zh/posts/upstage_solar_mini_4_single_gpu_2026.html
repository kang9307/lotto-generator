缘起 - 「一块GPU」所指的GPU

2026年10月1日，Upstage发布了Solar Mini 4，GeekNews在10月4日以「Upstage发布可在一块GPU上运行的Solar Mini 4」为题做了介绍。标题里的「一块GPU」容易让人联想到本地电脑的显卡，但发布文实际写的是「在本地部署时，以量化模型为基准，一块H100 80GB起即可部署」。

这一差别决定了判断。是能在消费级GPU上运行的模型，还是能用一块数据中心级GPU搭建服务的模型，使用者就不同。这个模型的发布文属于后者，并且没有提及权重公开或许可证。

要处理的问题有三个。

  • 「一块GPU」这一表述，按规格数字最多能说到哪里
  • 70%首发折扣究竟到什么时候，适用于哪里
  • 厂商自报的基准测试应放在什么位置来读

在价格这句话里，折扣期限与流传的概述一致。首发折扣截至UTC 10月10日的说法原样存在，但该句限定于Upstage Console这一点，是摘要里容易丢掉的部分。标题和概述用语缩减掉的条件，往往就是这类限定语。

发布文给出的规格 - 总计35B、激活3B、512K上下文

发布文把Solar Mini 4介绍为「Upstage自主预训练、针对智能体任务优化的模型」。把它作为规格写出的值汇总如下。

项目发布文中的值
结构MoE（混合专家），总计35B参数中处理token时激活3B
上下文输入最多512K token，输出128K token
功能JSON结构化输出、并行工具调用
模型名（API）solar-mini4
提供途径Upstage Console API、Solar Chat、OpenRouter、本地部署
本地部署的最低配置以量化模型为基准，一块H100 80GB起
权重公开与许可—

权重是否公开以及许可条款，发布文没有提及，所以表中记为「—」。提供途径里有本地部署，并不意味着可以拿到权重，这只是Upstage支持部署的叙述，其条件发布文中没有。

发布文把该模型的用途介绍为：以较少的计算和成本处理查询信息、按既定格式生成结果、调用工具这类重复性工作，页面开头的标题语句译为「让重复的智能体工作更轻」。后面的价格一节和用途一节应以这一介绍为基准来读。

「独立预训练」是发布文第一句中的表述。发布文正文中看不到对训练数据或训练方法的说明，因此判断依据应是实际测得的准确率和成本，而不是模型的来历。

总计35B与激活3B各自决定什么 - 内存与计算

发布文对结构的表述如下（译文）：「虽然是由总计35B参数构成的MoE模型，但处理每个token时只激活3B。」关于内存，它写道：「活跃参数少，并不意味着部署所需内存也按同样比例减少。每个token的计算只激活3B，但部署模型时需要把全部35B权重加载到内存中。」有了这两句话，就可以把Solar Mini 4的「一块GPU」与「重复工作的成本」分开来读。

  • 总计35B - 发布文：部署模型时需要把全部35B权重加载到内存中
  • 活跃3B - 发布文：处理每个token时被激活的部分，并称由此降低每个token的计算量，提供高吞吐和成本效率
  • 二者之比约为8.6%（3/35，计算）

仅权重的大小由精度相乘得出。下表是发布文中没有的值，是35B乘以各精度下每参数字节数的计算。实际部署中，权重之外还要加上KV缓存和运行开销，所以这些值是下限。

存储精度（假设）每参数字节数仅权重大小相对H100 80GB
16比特2约70GB只剩约10GB
8比特1约35GB剩约45GB
4比特0.5约17.5GB剩约62.5GB

该表并未说明实际采用哪种精度。发布文也只写了「以量化模型为基准」，没有写精度，所以这张表只作为与80GB对照的算术参考来读。

拆解「一块H100 80GB起」这句话

发布文的部署句子很短，却附有四个条件，每个都在缩小或限定「一块GPU」的含义。

  1. 「在本地部署时」 - 这一表述仅限于本地部署。
  2. 「以量化模型为基准」 - 没有写明精度（8位还是4位）。
  3. 「H100 80GB」 - 发布文作为最小部署配置写出的GPU型号与显存容量。
  4. 「一块起」 - 是最低配置。性能数值不是来自这一配置，而是来自另一种配置（两块）。

最后一个条件尤其重要。发布文的速度数值是在两块H100的配置上测得的，与「一块起」即可部署的说法并不是同一配置的测量。一块配置下的吞吐和延迟，发布文中没有。同样，不同上下文长度下的内存需求也没写，所以「一块」对长上下文服务是否足够，仅凭发布文无法得知。

总结来说，要把「一块GPU」这一表述套用到自己的情况，需要向供应方追问三件事：用哪种量化精度、在多长的上下文下该配置才有效、多少并发请求下延迟是多少。有了这三个值，才能分辨一块GPU是测试环境的配置还是服务配置。

速度70 tok/s以上 - 测量条件与读法

发布文这样描述速度：「在实际内部测量中，即使用两块H100同时处理32个并发请求，每个请求也保持了70 tokens/s以上的生成速度」。测量条件写明如下。

  • 硬件：两块H100
  • 并发请求：32个
  • 输入4K token、输出1K token
  • 前缀缓存（prefix caching）关闭
  • 600秒以上的连续负载
  • 测量主体：Upstage内部测量

换算这些数字如下，全部是计算，发布文中没有这些值。

  • 若每个请求70 tok/s在32个并发下得以保持，则总生成吞吐至少为2,240 tok/s（32×70）。
  • 以70 tok/s生成1K输出token（按1,000个token假设）约需14秒（仅生成时间，不含首token延迟）。
  • 发布文的脚注写明，该测量是在不启用prefix caching、持续负载600秒以上的条件下得出的，吞吐测量使用了两块H100，与最低部署规格是不同的配置。

这个数字能告诉我们的是有限条件下每请求生成速度的下限。它不能告诉我们的是首token时间（TTFT）、输入远长于4K时的速度、并发超过32时的下降，以及一块H100配置下的值。这些都是要结合自己服务的输入长度和并发数亲自测量的项目。

也可以把这些数字换算成服务容量。仅看生成时间，一个请求约14.3秒（1,000/70），32个并发得以保持，所以每秒约完成2.2个请求（32/14.3）。折算为每小时约8,000个请求（计算）。这是去掉输入处理时间和首token延迟的上限近似，实际吞吐应估得更低。

价格与首发折扣 - 期限与适用范围

发布文的价格语句译为：「API标价为每百万token输入$0.10、缓存输入$0.01、输出$0.40。Upstage Console截至UTC 10月10日适用70%折扣价，10月11日起转为正常价格。」把这句话确定的内容与不确定的内容分开，如下所示。

项目标价（发布文）适用70%折扣时（计算）
输入，每百万token$0.10$0.03
缓存输入，每百万token$0.01$0.003
输出，每百万token$0.40$0.12
  • 确定的：折扣率70%、期限「截至UTC 10月10日」、转为正常价格的时点10月11日、适用位置Upstage Console
  • 不确定的：折扣是否覆盖三项（输入、缓存输入、输出）。该句只写了「70%折扣价」，所以表中的折扣价是基于这一假设的计算
  • 不确定的：10月10日的几点（UTC）为止。「截至」与「10月11日起」相接，可理解为10日结束，但没有写明时刻
  • 韩国时间比UTC早9小时，所以UTC 10日一天结束的时点在韩国是11日上午9点前后（计算，时刻的定义发布文中没有）
  • 适用范围：该句限定于「Upstage Console」，因此OpenRouter、Solar Chat等其他渠道的价格与是否有折扣，仅凭发布文无法得知

折扣是首发时的促销，所以成本规划以标价为基准更稳妥，把折扣当作试用期的余量。若在恢复正常价格之后仍沿用以折扣价做的单价表，成本会膨胀约3.3倍（1/0.3，计算）。

把规模放大来看，若同样形状（输入4K、输出1K）的请求每月一百万次，按标价每月约$800，假设70%折扣则约$240（计算）。这些值仅为模型调用成本，不含重试、验证环节的额外调用和基础设施成本。

换算成单次请求的成本

把单价换成按请求计的数字，比较起来更容易。以与速度测量相同形状的请求为例：输入4,000个token、输出1,000个token（计算，输入token数为估数）。

场景单次请求（标价）1,000次（标价）1,000次（假设70%折扣）
输入4K全部未缓存 + 输出1K$0.0008$0.80$0.24
输入4K全部缓存 + 输出1K$0.00044$0.44$0.132
输入512K未缓存单个请求（仅输入）$0.0512——

从表中可读出两点。第一，这种形状的请求里输入与输出各为$0.0004，比重相同（4,000×$0.10/百万 = 1,000×$0.40/百万）。输入越长，输入单价越占主导，输出越长，输出单价越占主导。第二，缓存输入是输入单价的十分之一，所以反复使用同一个长系统提示的工作负载，输入成本会大幅下降。缓存在什么条件下命中，发布文中没有，所以实际命中率要自己测。

发布文的「初期内部测试」对比也属于同一脉络。3个韩语任务（包括代码分析与评审、联动多个工具的日程协调等）每个模型各运行3次，两个模型都通过了三项任务的质量检查点。按标价计算，3个任务1,000组的完成成本为Solar Mini 4 $1.25、MiMo-V2.5 $2.20，低约43%（1.25/2.20经计算约低43.2%）。据脚注，条件为temperature=0，成本按两个模型都不启用提示缓存折算，且因MiMo V2.5经过外部路由器，延迟不纳入对比。仅看日程协调（查询日历并向参会者发送消息）任务，1,000次运行的成本为$0.36对$0.61。发布文补充说，结果会因实际运行环境和任务难度而不同。

读基准测试 - 厂商自报数值的性质

把发布文提出的评测数值汇总到一张表里，并附上各自衡量什么。分数均为Upstage自报的数值。

评测发布的值发布文的说明
Artificial Analysis Intelligence Index v4.3.224.1分「本次评测中已确认分数的激活3B模型里结果最高」
AutomationBench-AA22.3%使用真实SaaS工具完成工作的评测
τ³-Banking47.2分与Artificial Analysis Intelligence Index v4.3.2分开的另一项评测结果
AA-LCR83.3评测长上下文推理能力
SciCode47.6基于代码的科学问题评测
Humanity's Last Exam25.8—

读的顺序整理如下。

  1. 综合指数24.1分要连同对比对象一起读。发布文称，它比激活参数为31B的Gemma 4 31B高9.1分（激活参数约为其十分之一），比激活参数为55B的Nemotron 3 Ultra高1.1分，比MiMo-V2.5低0.9分（Solar Mini 4的激活参数约为MiMo-V2.5的五分之一）。
  2. 「激活3B模型中最高」这一说法附有「本次评测中已确认分数的」这一限定。激活3B类别内与哪些模型做了比较，正文中没有列出。
  3. 该指数是外部机构的标尺，但这个分数是外部机构亲自评测并发布的，还是厂商按该指数的方式测的，仅凭发布文无法区分。
  4. 发布文把AutomationBench-AA的22.3%解释为评测信息查询、结构化、状态确认、后续执行跨多个步骤的工作的指标。发布文中没有并列给出其他模型在该项上的分数。
  5. 发布文称该模型默认不使用推理，可通过reasoning_effort调节推理程度，但没有写评测得分时采用的是哪种设置。

在实务中，这张表不是用作选择的依据，而是用作筛选候选的起点。用自己任务（信息抽取、文档验证等）的几十到几百个代表样本直接测准确率和成本，比再次确认同样的数字信息量更大。

设计自己的评估时，把准确率、每请求成本和失败类型放进同一张表，而不是只看准确率。把失败类型按格式违规（JSON损坏）、遗漏、错误值、工具调用错误来统计，就能区分出分数相同但后处理成本不同的候选。发布文把结构化输出和并行工具调用写为支持的功能，但没有写这些功能的失败率。

建议用途与发布文写出的局限

发布文列举的使用案例有三个。

  • 信息抽取与结构化
  • 连接内部系统的重复性工作
  • 文档流水线的验证环节

发布文列举的三类用例内容如下。信息提取与结构化，是从合同中提取主要条目、对客户咨询分类、把文本转换为JSON和表格。联动内部系统的重复性工作，是查询审批状态、依内部规定判断能否处理并整理结果。文档流水线的验证环节，是对照Document Parse和Information Extract得到的结果、检查缺失字段、按既定规则决定后续处理。

关于局限，发布文自己留下了一句话。译为：「对会影响实际决策的工作，建议不要把模型输出当作最终判断，而应设置单独的验证流程。」同一段中，发布文还请读者在应用到运行环境之前，用真实数据评估准确率和失败类型。

  • 即使用于验证环节，也不把模型的判定结果当作最终决定
  • 信息抽取的结果与抽样复核或基于规则的验证配对使用
  • 使用工具调用的重复性工作，先确定调用失败与重试的策略

最后再看发布文的AutomationBench-AA 22.3%，该指标被描述为评测跨多个步骤的工作，因此与单次调用的准确率是不同的标尺。上一节建议把准确率、单次请求成本和失败类型放在一张表里设计自评，原因也在这里，而发布文的安全提示正是要求做这种评估。

评估引入的顺序

  1. 先看任务是否属于发布文的用途（信息抽取与结构化、重复性工作、验证环节）。
  2. 选择获取途径。是API（Upstage Console、OpenRouter）还是本地部署，成本、安全和运维责任都不同。
  3. 若是本地部署，要知道一块H100 80GB是最低线，并按要使用的上下文长度和并发数直接测量内存和吞吐。发布文的速度数值是两块配置下的值。
  4. 若用API，查看价格页面的当前数值。以标价为基准做单价表，折扣只当作试用期的余量。
  5. 用代表样本测量准确率。发布文的基准测试是厂商自报的数值，所以只用于筛选候选。
  6. 检查提示结构（固定系统提示之后接可变输入）能否利用缓存输入的单价。
  7. 对输出会影响决策的路径，附加单独的验证流程。
  8. 用折扣结束后的正常价格，重新计算每月的预计成本。

这一顺序里重要的是顺序本身。成本计算（第4步）与准确率测量（第5步）互相独立，但只通过其中一个就决定引入，是常见的错误。便宜但会出错的模型与准确但昂贵的模型之间的取舍，只有把两个值放在同一张表里才看得见。
