How Linear Feels Instant - Local-First Sync and In-Browser Databases 2026

Why Some Web Apps Feel Native - The Secret of the Sync Engine

Jun 9, 2026 Tech

Introduction: The App That Finishes the Instant You Click

Developers trying the issue tracker Linear for the first time tend to say the same thing: "Why is this so fast?" Changing an issue's state, dragging its priority, applying a filter - every action finishes the moment you click. No loading spinner, no brief stall. It feels less like a web app and more like a well-built native desktop program. Reports suggest Linear handles most interactions in a few milliseconds, and many views render in under 50ms.

That speed is not luck; it is the result of a deliberate architecture. At its core sit the local-first design philosophy and the two things that support it: an in-browser database and a sync engine. Starting from the question "how does Linear hit millisecond responsiveness," this article unpacks what local-first is, how it differs from the classic server round-trip model, how optimistic updates, the sync engine, and CRDT conflict resolution interlock, and what the trade-offs are when you bring this approach to your own project. The short answer up front: Linear's speed comes not from making the server faster, but from taking the server out of the user's perceived path.

1. Why Classic Web Apps Feel Slow - The Round-Trip Trap

To understand the secret, you first have to understand the "slow." A typical web application runs on the request-response model. The user presses a button, the browser sends a request to the server, the server reads and updates the database, sends a response back, and only then does the screen update.

[Classic request-response flow]

User clicks
   |  (network round-trip: tens to hundreds of ms)
   v
Server processing -> DB read/write
   |  (network round-trip)
   v
Response arrives -> screen updates   <- the user "waits" the whole time

The problem is that network latency sits right in the middle of this whole process. Even within the same city a round-trip costs tens of milliseconds; across continents it balloons to hundreds. Add server processing and rendering, and a single click turns into perceptible "jank." Not because the CPU or database is slow, but because the physical limits of the speed of light and the size of the earth weigh down the user experience.

Traditional optimization tries to make that round-trip "faster": add caches, attach a CDN, tune the queries. All valid, but bounded. As long as the network stays on the path, the user always waits a little. Local-first flips the idea. Instead of making the round-trip faster, it removes the round-trip itself from the user's perceived path.

2. What Local-First Means - Keep Data Next to the User

Local-first is a software design principle articulated by the Ink & Switch research group in 2019. In one sentence: "keep the primary copy of data on the user's device, and treat the cloud as a backup and sync helper." Where classic cloud apps assume "the data lives on the server and the user peers through a window at it," local-first assumes "the data lives on my device and the server assists with a copy of it."

Ink & Switch laid out seven ideals for local-first, but they reduce to two axes. The first is speed and availability: because data is local, reads and writes are instant, and the app keeps working when the network drops. The second is ownership and control: the user holds the primary rights to their data, and the data survives even if the service disappears.

The core shift of local-first is simple: from an app that "asks the server and waits" to one that "answers instantly from data it already has and reconciles later."

Linear is the flagship example of implementing this principle pragmatically for collaboration tools. It is less a purist academic local-first and more an "engineered local-first" that combines an in-browser DB with a sophisticated sync engine to land both fast responsiveness and multi-device sync at once.

3. The In-Browser Database - A Real DB Inside the Browser

For local-first to work, you need a "local store" to keep data in. What Linear and other modern web apps use is the browser's built-in IndexedDB. IndexedDB is not a simple key-value cache; it is a browser-native database with indexes, transactions, and large storage.

Per reports and reverse-engineering analyses, Linear's data flow looks roughly like this:

  • Bootstrap: on a user's first visit, the server's /sync/bootstrap endpoint sends down, in one shot, the data needed to render the screen. That data is stored in IndexedDB.
  • In-memory object pool: afterward the app reads data from IndexedDB rather than the server, hydrating it into a huge in-memory object map (an object pool keyed by UUID). The UI looks at these in-memory objects.
  • Lazy hydration: the heaviest tables (issues, comments) are not loaded in full upfront; only the properties actually accessed are filled in. It resembles code-splitting at the data level.

The key is that the UI looks at "in-memory objects inside my browser," not "the server." Because the data is already in hand, reads finish at memory-access speed, not network speed. That is the first secret behind sub-50ms rendering.

4. Optimistic Updates - Show First, Reconcile Later

Fast reads make sense. But how can "writes" be instant? Saving to the server still has to cross the network, doesn't it? This is where optimistic updates come in.

The idea behind optimistic updates is exactly what the name says: optimism. When a user flips an issue's state to "In Progress," the app applies that change to the local object and refreshes the screen without waiting for the server response. At the same time, it queues a request to send that change to the server in the background. The user already sees the result and moves on to the next action.

[Optimistic update flow]

User clicks
   |
   +--> mutate local object -> refresh screen (a few ms; user is done here)
   |
   +--> append change to a transaction queue -> send to server in background
                                                 |
                                     success -> commit
                                     failure -> roll back or retry

Because most requests succeed, this optimism is almost always right. In the rare case the server rejects it (permissions, conflict), the app rolls the change back or retries. A crucial design point is that the change is written first to a durable transaction queue in IndexedDB. So even if the browser closes or the network drops mid-send, the change is not lost; when the connection recovers, the queue finishes sending.

5. The Sync Engine - Making Many Devices Act as One

A change applied instantly on the local side must ultimately propagate, via the server, to other users and devices in the same workspace. The component that does this is the sync engine. It is considered the hardest and most valuable part of a local-first app.

Pulling together the analyses of Linear's sync engine, here is how it works:

  • Changes as transactions: every change - create, update, delete, archive - is encapsulated as a "transaction." That transaction is sent to the server and executed there.
  • Delta broadcast: the server takes the result and broadcasts only the delta (not the whole dataset) over WebSocket to other connected clients in real time. Because so little flows over the network, propagation is fast.
  • Incremental sync: other devices receive only the deltas since the point they last saw, updating their local DB. They never re-download everything, which is efficient.

In other words, the heavy data stays in each client's IndexedDB, while only small deltas - "what changed" - cross the network. The server is the source of truth and the relay of changes, but it steps back from being the gate that blocks each individual user action. This structure connects to something we covered earlier in UUID primary keys and identifier design for distributed systems, since clients must be able to mint IDs first for optimistic creation to feel seamless.

6. How Conflicts Are Resolved - CRDTs and Merge Strategies

What happens when several people change the same data at once? If A edits an issue's title offline while B changes the same issue's priority online, how do you merge the two? That is the problem of conflict resolution.

The most powerful tool is the CRDT (Conflict-free Replicated Data Type). A CRDT is a data structure designed mathematically so that concurrent changes across replicas merge automatically into the same result without central coordination. Because each change carries a unique identifier and ordering information, one user inserting characters at the start of a document and another at the end merge without conflict. Automerge, built by Ink & Switch, is a representative implementation.

That said, not every conflict needs a CRDT. In practice teams mix in simpler strategies that fit the workload:

Strategy How it works Best for
Last-write-wins (LWW) the change with the later timestamp wins single fields like status and flags
Custom merge per-field rules defined by hand data with clear domain meaning
CRDT auto-merge concurrent edits collaborative text and list editing

For an app like an issue tracker, most fields are single values - "status," "assignee," "priority" - so last-write-wins or per-field merge is often enough. Paying the cost of a CRDT only where genuine concurrent editing is frequent (like collaborative text) is the pragmatic choice.

7. Why It "Feels Fast" - The Psychology of Perceived Performance

Here we should step back and draw an important distinction. Actual performance and perceived performance are different. What local-first truly changes is the latter.

Human cognition perceives anything around 100ms as "instant." When the screen responds within that boundary, the user gets a sense of direct manipulation - "I am operating the system myself." Conversely, past 0.1 seconds people start to notice a faint stutter, and past 1 second attention breaks. Local-first uses optimistic updates to pull every user action inside that 100ms boundary.

The interesting part: server sync still takes hundreds of milliseconds in the background. Yet the user "does not feel" that latency, because during that time they are already doing the next thing. The latency was not eliminated; it was moved into a window the user does not look at. That is the paradox behind Linear feeling faster than the network even though nothing can be faster than the network.

This reframing has a practical consequence for how you measure success. Backend dashboards proudly report p50 and p99 server latency, but those numbers are invisible to the user once optimistic updates are in place. The metric that actually correlates with the feeling of speed is the gap between the input event and the first visual change on screen - often called input latency or interaction-to-paint. A team can shave 50ms off server response time and the user notices nothing; the same team can move a single hot interaction inside the 100ms boundary and the whole product suddenly "feels" rewritten. Optimizing the number users feel, rather than the number servers report, is the quiet lesson local-first teaches.

8. Trade-offs - There Is No Free Lunch

By now it sounds like every app should be local-first. But for balance we must spell out the cost. Local-first speed is bought with significant complexity.

  • Implementation difficulty: you build a database, a sync protocol, conflict resolution, and a transaction queue on the client. Even Linear called its sync engine one of the hardest technical investments in its history.
  • Schema changes and migration: because data is scattered across countless clients' IndexedDB, changing the data model means caring about compatibility with older clients.
  • Security and permissions: the more data flows down to the client, the more precisely you must control "who can see what" along the bootstrap and sync paths.
  • Initial size and memory: the bootstrap pulls a lot of data and holds it in memory, so as a workspace grows, initial loading and memory management become real challenges.

So for a simple CRUD app with rare offline concurrent editing and screens whose data differs widely, local-first's benefit may not justify its cost. The return on investment is highest where the frequently used core screens are narrow and repetitive, like operational tools and back offices. The way "fast tools" pay off in productivity follows the same logic we covered in terminal performance and developer productivity.

9. Tools in the Same Current - The Local-First Ecosystem

The direction Linear sparked has grown into an ecosystem as of 2026. There are now more frameworks and sync engines that help you get a similar experience without building it all yourself.

  • Sync-engine frameworks: they package the client DB and server sync so you do not have to implement optimistic updates and delta sync by hand.
  • CRDT libraries: libraries like Automerge and Yjs let you bolt on automatic merge for collaborative editing easily.
  • In-browser DB tools: wrappers that add query and reactive subscriptions on top of IndexedDB simplify the client data layer.

The shared message is clear: "take the server out of the user's perceived path" is no longer Linear's secret sauce alone - it is descending into tools that ordinary developers can pick up. The broader design question of where to keep data and how to sync it connects to the perspective in file SDKs and unified blob storage.

10. Applying It to Your Project - An Incremental Path

Rewriting everything as local-first at once is risky. Here is an incremental path:

  1. Identify the bottleneck: find the interaction users do most often and feel is "slowest." The starting point is one or two core actions, not every screen.
  2. Start with optimistic updates: before a full local-first rewrite, just adding optimistic updates and a local cache to frequent mutations changes the feel dramatically.
  3. Durable queue: to handle send failures and offline, write changes locally first and keep a queue that retries.
  4. Pick a conflict strategy: start most fields with last-write-wins, and introduce CRDTs only where genuine concurrent editing is required.
  5. Observe and fall back: measure the rate of sync failures and rollbacks, and provide a clear fallback UI that tells the user when the optimism was wrong.

The core principle is that local-first is not all-or-nothing. It is safer to adopt the smallest piece - optimistic updates - confirm the felt improvement, and add depth step by step while weighing need against cost.

11. Conclusion + 3 Things You Can Apply Today

The answer to "how does Linear hit millisecond responsiveness" is clear. It did not make the server faster; it kept the data next to the user (in the browser), processed every action locally and instantly, and pushed server sync into a background window the user does not watch. The in-browser DB puts data in hand, optimistic updates make writes instant, and the sync engine and conflict resolution quietly reconcile many devices into one. The secret of the speed is not technical magic but a design decision: take the network out of the perceived path.

Let us close with three things you can apply today.

  1. Measure perceived performance. Measure "click to visible change," not server response time. The speed a user feels is that number, not your backend latency.
  2. Add optimistic updates to your most frequent action. Without a full redesign, converting just one or two core interactions to instant local reflection changes the feel.
  3. Start conflict handling simple. Don't lay down a CRDT from day one; start with last-write-wins and spend the cost only where real concurrent editing becomes a problem.
