Every AWS Check Passed and a Path Still Remains - Putting the Relationships Between Resources on the List

What role passing, trust policies, resource policies and cross-service calls each join together, and what you have to look at before the seam becomes visible

2026-09-05 Dev & Infra

There is a particular moment when a cloud security dashboard is full of green and the feeling still does not arrive. Every item passed. The bucket is not public, encryption at rest is on, no security group has an open port that should not be open. And yet none of that adds up to the sentence this account is safe. That discomfort is not a mood. It comes out of the structure.

The unit a check inspects and the unit in which risk is produced are different things. A check looks at one resource. Risk is manufactured between one resource and another. As long as those two units are misaligned, you can keep adding items forever and the path that formed in the gap between them will never enter the list.

What follows is the anatomy of that misalignment. There is a small, finite set of channels through which permission can travel, and each channel becomes visible only from a different vantage point. Below, those channels are split into four, and for each one the question is paired: what manufactures the risk, and what reveals it. This is a matter of visibility, not of attack procedure. No offensive step appears anywhere in this article.

The IAM definitions and recommendations quoted below are taken from the official AWS User Guide text. Cloud permission models are revised often, and condition keys and policy types keep being added. Every quoted statement here reflects the documentation as of early September 2026.

The trigger - where passing and being safe stop meaning the same thing

In early September 2026 an open-source repository was introduced on a developer community under the headline a security verification tool that finds attack paths hiding between AWS settings. The word that catches the eye in that headline is between. It is not saying inside a setting. It is saying between one setting and another.

That phrasing is too accurate to dismiss as marketing copy, because the structural limit of cloud configuration checking sits exactly there. A check assigns true or false per resource. Permission, though, is not confined inside a resource. It flows to whatever it is connected to. Flow is a property of a graph, not of an item.

The tool itself is handled later in this article, and only on the level of verifiable fact. The first part deals with a question that holds with or without any tool. What has to go on the list in your own account before that in-between becomes visible, and why that list is never completed by a collection of individual items.

Why security is a problem of structure rather than of knowledge was covered in Why Security Is Unusually Hard to Learn, and the question of getting work done without ever placing a credential in someone hands is in Getting Work Done Without Handing an Agent Your Credentials. This article deliberately avoids both axes and looks only at the structure by which permission moves between resources.

A check inspects one resource at a time

Bring any cloud configuration rule to mind and its shape shows up immediately. A rule is almost always the question does this property of this resource hold this value. Is public access blocking enabled on the bucket. Is the database snapshot marked public. Does the log group have a retention period set. The answer is true or false, and everything needed to reach that answer is contained in the properties of that one resource.

This shape has real virtues. The verdict is deterministic, rules are independent of one another, and adding a new rule does not disturb the existing ones. Whoever authors one rule does not need to know about any other rule. That independence is precisely why such catalogs can be grown to thousands of entries without collapsing under their own weight.

The same shape has an equally clear ceiling. The premise is that everything needed for the verdict fits inside a single resource. If a fact only holds when you look at the properties of two resources together, that fact cannot be expressed as a rule of this shape. And what cannot be expressed neither passes nor fails. It is simply not an object of observation.

This is where a common misreading takes root. Because the item did not fail, the reader concludes that this area is fine. In reality, did not fail and was never examined are rendered in the same shade of green on the same screen. The dashboard does not distinguish between the two states.

The unit in which risk is produced - the relation

Permission is not a property of a resource. It is a relation between a principal and a resource. The very organization of the AWS documentation reflects this. An identity-based policy attaches on the principal side. A resource-based policy attaches on the resource side. A role trust policy decides who is allowed to become this role. Not one of these yields a conclusion when read alone.

The AWS User Guide defines a role as an IAM identity that you can create in your account that has specific permissions, and immediately distinguishes it from a user: instead of being uniquely associated with one person, a role is intended to be assumable by anyone who needs it. A role has no standard long-term credentials such as a password or access keys. Instead, when you assume a role, it provides you with temporary security credentials for your role session. A role, in other words, is a bundle of permissions that travels.

The same page defines delegation as the granting of permissions to someone to allow access to resources that you control, and notes that delegation involves setting up a trust between two accounts. The first is the account that owns the resource, the trusting account. The second is the account that contains the users who need to access the resource, the trusted account. Two policies attach to the role created in the trusting account: the permissions policy, which grants the user of the role the permissions needed to carry out the intended tasks, and the trust policy, which specifies which trusted account members are allowed to assume the role.

Add role chaining and the relation becomes a chain. The definition is terse: role chaining is when you use a role to assume a second role. If one role has permission to assume another, the short-term credentials of the first can be used to assume the second. The documentation adds an operational detail worth carrying: role chaining limits a console, CLI or API role session to a maximum of one hour, and it does so regardless of the maximum session duration configured for the individual roles. An assume call that supplies a duration greater than one hour while chaining fails outright.

Every link in such a chain can look entirely correct when inspected on its own. That role A may assume role B is not a defect in itself. What matters is the start and the end of the chain. If the start is open wider than intended and the end holds permissions stronger than intended, then every intermediate link can be flawless and the outcome still diverges from the intent.

Channel one - passing a role to a service

The first channel is the act of handing a role to a service. The AWS explanation opens like this: to configure many AWS services, you must pass an IAM role to the service. This allows the service to assume the role later and perform actions on your behalf. For most services you only have to pass the role once during setup, and not every time the service assumes it.

Passing requires permission. The same page states that to pass a role and its permissions to an AWS service, a user must have permissions to pass the role to the service, and explains the intent as helping administrators ensure that only approved users can configure a service with a role that grants permissions.

The nature of this channel is captured in a warning that appears in the documentation verbatim. When setting the PassRole permission, you should make sure that a user does not pass a role where the role has more permissions than you want the user to have. The example given is unambiguous: a user might not be allowed to perform any storage actions at all, yet if that user can pass a role to a service that allows storage actions, the service could perform those actions on the user behalf when executing the job.

The relational character is now plain. Reading the user permissions policy alone does not produce this fact. Reading the role permissions policy alone does not produce it either. It appears only when the two are joined, because the effective permission of the user is determined not by the user own policy but by the policies of every role that user is able to pass.

The documentation also supplies the mechanisms for narrowing the set. One is the Resource element of the policy statement, which filters which roles may be passed. The other is the Condition element. The iam:PassedToService condition key in particular is used to specify the service principal of the service to which a role can be passed. The same page flags a trap explicitly: do not try to control who can pass a role by tagging the role and then using the ResourceTag condition key in a policy with the iam:PassRole action. This approach does not have reliable results.

From the standpoint of visibility, the most consequential fact lives on the logging side. The wording is direct: PassRole is not an API call. PassRole is a permission, meaning no CloudTrail logs are generated for IAM PassRole. To review which roles are passed to which services, you must review the CloudTrail log that created or modified the AWS resource receiving the role. In the example the documentation gives, a role is passed to a function when the function is created, so the log for the create action shows a record of the role that was passed.

Why does one sentence matter so much? Because if an audit pipeline is built around IAM events, this channel is structurally invisible to it. The place to look is not IAM but the service that received the role.

Channel two - the principals a trust policy accepts

The second channel is the entrance to a role. AWS defines a trust policy as a JSON policy document in which you define the principals that you trust to assume the role, and adds that a role trust policy is a required resource-based policy that is attached to a role in IAM. The principals you can specify in a trust policy include users, roles, accounts and services.

The same page enumerates who can assume a role: an IAM user in the same account or another account, IAM roles in the same account, service principals for use with AWS services and features, and an external user authenticated by an external identity provider compatible with SAML 2.0 or OpenID Connect. That last entry is what turns a trust policy into a document that crosses the account boundary.

One grammatical constraint is stated outright: when you create a trust policy, you cannot specify a wildcard as part of an ARN in the principal element. That constraint does not narrow the trust scope by itself. An account-level principal, or a federated principal with no conditions attached, is entirely valid grammar. In those cases the effective reach of the trust is decided not by the policy grammar but by the Condition element.

So what deserves attention in a trust policy is not the principal element alone but the pairing of principal and condition. When the principal points at an account or an external provider, whether a narrowing condition sits beside it is what determines the real scope of the trust. A trust policy with an empty condition passes grammar validation and per-item checking alike, and remains an entrance wider than anyone intended.

Channel three - when a resource policy points outside the account

The third channel is the policy that attaches on the resource side. AWS defines it plainly: resource-based policies control how the specified principal can access the resource to which the policy is attached. The documentation notes that some services allow you to attach a policy directly to a resource instead of using a role as a proxy, and that such policies can grant principals in another AWS account access to the resource.

The reason this channel routinely slips past item-level checking is that what manufactures the risk is not the existence of a policy but the direction the policy points. The mere presence of a policy is neither true nor false. To render a verdict you must decide whether the principal inside it falls within your zone of trust or outside it, and that decision requires information external to the resource: the boundaries of your accounts and your organization.

AWS offers that decision as a service in the form of IAM Access Analyzer. The documentation says it helps you identify the resources in your organization and accounts shared with an external entity, and describes the method as identifying resources shared with external principals by using logic-based reasoning to analyze the resource-based policies in your AWS environment. The organization or account you choose when creating an analyzer is known as its zone of trust, and any access to resources by principals within that zone is considered trusted.

The operational caveats are in the same document. If you add a new policy or change an existing one, it is analyzed within about 30 minutes. On rare occasions the analyzer does not receive notification of a change, in which case the policy is analyzed during the next periodic scan, which is within 24 hours. And one constraint is set in bold: for external access, IAM Access Analyzer analyzes only policies applied to resources in the same AWS Region where it is enabled. To monitor all resources you must create an external access analyzer in each Region where you use supported resources. The contrast is stated too: for unused access, findings do not change based on Region and creating an analyzer per Region is not required.

Which means the visibility of this channel is not completed by switching it on. Which Regions have an analyzer is exactly which Regions you can see, and an unattended Region looks identical to a clean result.

Channel four - when a service acts on a user behalf

The fourth channel is the one where the principal is not a person but a service. AWS calls the failure mode here the confused deputy problem and defines it as a security issue where an entity that does not have permission to perform an action can coerce a more-privileged entity to perform the action.

The cross-service description is especially precise. The documentation states that when an AWS service principal from a calling service is accessing a resource from a called service, the resource policy from the called service is only authorizing the AWS service principal, and not the actor who configured the calling service. In the example given, a bucket that trusts a particular service principal with no conditions could receive logs from the accounts a trusted administrator configures, but also logs from an unauthorized actor in their own account, if they know the name of the bucket.

In the cross-account case, the external ID is the instrument. The documentation introduces it as an optional identifier that you can use in an IAM role trust policy to designate who can assume the role, and states that the primary function of the external ID is to address and prevent the confused deputy problem. Control of the value is spelled out as well. The external ID value must be unique among the provider customers and controlled by the provider, not its customers. That is why you receive the value from the provider rather than inventing one yourself.

{
  "Version": "2012-10-17",
  "Statement": {
    "Effect": "Allow",
    "Principal": { "AWS": "EXAMPLE-PROVIDER-ACCOUNT-ID" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": { "sts:ExternalId": "EXAMPLE-EXTERNAL-ID" }
    }
  }
}

The shape above is the skeleton of the cross-account trust policy the documentation presents, with placeholders standing in for the account identifier and the external ID. What matters here is not the values but whether the Condition element is present at all.

For the cross-service case the instrument is a set of condition keys. AWS states that it recommends using aws:SourceArn, aws:SourceAccount, aws:SourceOrgID or aws:SourceOrgPaths in your resource policies wherever an AWS service principal is granted permission to access one of your resources. The uses divide cleanly. SourceArn allows a service principal to act on behalf of a specific resource. SourceAccount restricts it to a specific account. SourceOrgID restricts it to specific organizations, and SourceOrgPaths to a specific organizational path.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "EXAMPLE-SERVICE.amazonaws.com" },
      "Action": "EXAMPLE-SERVICE:ExampleAction",
      "Resource": "EXAMPLE-RESOURCE-ARN",
      "Condition": {
        "StringEquals": { "aws:SourceAccount": "EXAMPLE-ACCOUNT-ID" }
      }
    }
  ]
}

When the same control needs to apply organization-wide at once, the documentation points to resource control policies, which allow cross-service confused deputy controls to be applied centrally to an organization, organizational units or accounts without adding statements to specific resource-based policies. One caution accompanies them. AWS states flatly that service control policies and resource control policies alone are insufficient to grant permissions to principals and resources in your organization. No permissions are granted by SCPs and RCPs. They are ceilings, not grants.

Relation types mapped to visibility

Collecting the four channels into a single table makes one thing immediately legible: each type becomes visible only from a different vantage point. The right-hand column is the heart of this article. What manufactures the risk and what reveals it do not live inside the same resource.

That mismatch in timing is the practical reason this problem stays hard. The relation created during design persists on its own, while the instrument that would show it has to be switched on separately, later, by someone who already suspects it is there.

Effective permissions are an intersection - where policy types overlap

To follow a relation you first need to know how the permission that actually gets through is decided. AWS defines effective permissions as the permissions that are granted by all the policies that affect the user or role, and lists what can affect an entity within an account: identity-based policies, resource-based policies, permissions boundaries, organization service control policies and session policies.

The skeleton of the rule fits in two sentences. First: if any one of these policy types explicitly denies access for an operation, then the request is denied. Second, the allow side depends on the combination. For identity-based policies and permissions boundaries, the effective permissions are the intersection of both policy types. Add an organization service control policy and the request is allowed only if all three policy types allow it, and the effective permissions are the intersection of all three. The session policy case works the same way, as an intersection of three types.

The definition of the boundary itself is as quoted earlier. It is an advanced feature for using a managed policy to set the maximum permissions that an identity-based policy can grant to an IAM entity, and an entity permissions boundary allows it to perform only the actions that are allowed by both its identity-based policies and its permissions boundaries. Decisively, it limits the user permissions but does not provide permissions on its own.

Up to here the whole thing compresses into a single word, intersection. And then the documentation immediately proceeds to list the exceptions that break that compression. These exceptions are the part that makes relational analysis genuinely difficult.

  • Within the same account, resource-based policies that grant permissions to an IAM user ARN, where that is not a federated user principal session, are not limited by an implicit deny in an identity-based policy or permissions boundary
  • Resource-based policies that grant permissions to an IAM role ARN are limited by an implicit deny in a permissions boundary or session policy
  • Resource-based policies that grant permissions to an IAM role session ARN grant permissions directly to the assumed role session, and permissions granted directly to a session are not limited by an implicit deny in an identity-based policy, a permissions boundary or a session policy. When you assume a role and make a request, the principal making the request is the role session ARN and not the ARN of the role itself
  • Federated user principal sessions behave the same way, except that if a resource-based policy grants permission to the ARN of the IAM user who federated, requests made during the session are limited by an implicit deny in a permissions boundary or session policy
  • In the worked example the documentation supplies, a target explicitly denied by the permissions boundary stays inaccessible even if a resource policy allows it, while a service the boundary does not explicitly deny becomes accessible on the strength of the resource policy allow alone, because implicit denies in permissions boundaries do not limit resource-based policies

Reading that list makes it obvious why effective permission is hard to total up by eye. The same allow statement yields different outcomes depending on whether the principal is a user ARN, a role ARN or a session ARN. It also makes obvious that per-item checking does not perform this computation on your behalf, and never claimed to.

Seeing it as a graph - asking about reachability

If the relation is the unit of risk, the natural next move is to move relations into nodes and edges. Put principals, roles and resources down as nodes. Put assuming, passing and granting access down as directed edges. The shape of the question then changes. It stops being is this setting correct and becomes can you get from here to there.

The benefits of that shift are concrete. First, the existence of a path can be asked about independently of whether individual items passed. Second, since a path exists regardless of which link along it is defective, the model can express a state in which nothing is defective and a path exists anyway. Third, remediation priority changes character. The minimum change required to sever a path becomes a computable question on the graph rather than a matter of taste.

The design documentation of the repository behind the trigger takes this direction explicitly. It separates individual misconfiguration from compound risk this way: individual misconfigurations create conditions for compromise, they are not compromises themselves. And it defines the difference between a control and a chain as follows. A control is a predicate about a single asset property, answering whether this one thing is configured correctly. A chain is a relationship between multiple controls, answering whether these failures together create a risk greater than the sum of the parts.

The same document records a design choice that is practically interesting. Chains carry an escalation threshold, so that a chain with three member controls and a threshold of two activates when any two of the three fail simultaneously. Two reasons are given. Real attack paths tend to require most of the conditions rather than all of them, and the threshold also prevents a single transient failure in one control from triggering a critical compound finding out of noise.

How edges are formed is written down too. Each chain carries preconditions and postconditions drawn from a closed capability vocabulary, and if the postcondition of one chain matches the precondition of another, a directed edge exists between them in the attack path graph. The document is careful about what this is: it is not a graph algorithm, it is a double loop over active chains performing set intersection, and the graph structure is data, not computation. Path finding, centrality analysis and visualization are left to external tools.

What static analysis cannot settle

The graph approach has clear limits, and those limits mostly arrive from what is not written in the policy documents. The AWS documentation itself exposes that boundary in several places.

The first is condition keys. AWS advises that you can specify conditions under which a policy statement is in effect, so that you can grant access to actions and resources but only if the access request meets specific conditions. The examples given are a condition requiring all requests to be sent using TLS, and a condition granting access to service actions only when they are used through a specific service. The difficulty is that the truth of a condition is determined by the context of the request at the moment it is made. From the policy document alone you cannot decide when that condition will actually be true.

The second is time. Some values are pinned in documentation, like the one-hour ceiling on chained role sessions, but the real lifetime of a session and whether a credential is actually held by anyone right now are not captured in a configuration snapshot. That a path is structurally possible and that it works at this moment are different statements.

The third is state outside the account. The effective reach of a trust policy that accepts federated principals depends on configuration held by the external identity provider. That provider state is not in the snapshot, and no amount of analysis over the snapshot will recover it.

The fourth is the observational range of the analysis tooling itself. As quoted above, external access analysis looks only at policies applied to resources in the same Region where it is enabled. The documentation further notes that under certain conditions notification of a policy change can be missed and finding generation delayed, and that changes involving multi-Region access points can take up to six hours. Snapshot-based analysis adds one more of its own: changes made after the snapshot was captured are not in the snapshot.

The fifth is the hole in the logs. That PassRole leaves no CloudTrail record is a limit of retrospective tracing rather than of static analysis, but the two limits compound where they meet. Static analysis may tell you a path exists, and IAM logs alone offer no way to establish whether that path was ever used.

What the repository behind the trigger actually claims

It is worth placing the community headline and the repository self-description side by side. The headline read a security verification tool that finds attack paths hiding between AWS settings. The opening paragraph of the repository README says something different. Open-source cloud configuration verifier. Proves your AWS configuration is correct instead of searching for what is wrong. It works offline without any credentials. The repository description field, separately, reads Stave finds compound attack paths that single-resource scanners miss.

The two sentences put their weight in different places. The headline puts it on finding. The README puts it on proving. The README goes out of its way to insist on the distinction: the word is verifier, not scanner: proof, not heuristics. Compound path discovery is one branch resting on top of that, not the entirety of what the project says about itself.

There is a second place where the headline and the artifact diverge. The headline specifies AWS, but the generated control reference in the repository lists non-AWS entries alongside the AWS ones in its per-service table, including 141 Azure controls, 29 Cloudflare controls and 30 Cisco controls. AWS is clearly the center of gravity, but the catalog is not AWS-only.

One point about the operating model also needs correcting. The phrase without any credentials applies to the evaluation stage. The README explains that evaluation never calls AWS APIs and works on local JSON snapshots, while describing the capture stage as running read-only AWS CLI calls and requiring SecurityAudit credentials. What needs no credentials is evaluation. Capture costs a read-only credential.

The three-way split in capture method is laid out as a table in the README as well. A risk-averse or regulated profile uses a bundled collector or pre-built filters with no language model involved. A pragmatic profile lets a local model map raw JSON to the contract before deterministic evaluation. A contributor profile has the model write filters that the team reviews before they ship in the repository. The document maintains that the contract and the evaluation are deterministic in every case, and that the collection method is a choice made according to risk posture.

The four minimum principles the official docs set out

Tool or no tool, the ground on which relations get onto the list is a set of principles AWS has already written down. Four of them, rendered close to the original wording.

First, least privilege. The sentence reads when you set permissions with IAM policies, grant only the permissions required to perform a task, and the method is defining the actions that can be taken on specific resources under specific conditions. A realistic caveat travels with it: you might start with broad permissions while you explore the permissions that are required for your workload or use case, and as your use case matures, you can work to reduce the permissions that you grant to work toward least privilege. On managed policies, the guidance notes that they might not grant least-privilege permissions for your specific use cases because they are available for use by all AWS customers.

Second, permissions boundaries. The documentation recommends that when you delegate permissions management within an account, you use permissions boundaries to set the maximum permissions that you delegate. The situation it describes is allowing developers to create and manage roles for their own workloads. As established earlier, the boundary is a ceiling and grants nothing by itself.

Third, condition keys. A dedicated best-practice item says to use conditions in IAM policies to further restrict access. Conditions matter disproportionately in relational analysis because, as the table above showed, in several of the channels what separates risk from safety is not the presence of a statement but the presence of a condition.

Fourth, access analysis. Three strands are recommended. Before granting public or cross-account access, verify whether such access is required and review the findings. Generate least-privilege policies from access activity logged in CloudTrail. And validate policies for grammar and best practices, where the documentation states that policy validation provides more than 100 policy checks and actionable recommendations. A separate item covers unused access: regularly review and remove unused users, roles, permissions, policies and credentials.

Rewriting those four in the language of relations turns them into a checklist. Is the scope of passable roles never broader than the permissions of the principal that can pass them. Is there a ceiling on delegation. Does every statement that accepts a broad principal carry a condition. Is every Region observed for policies pointing outside the account. All four questions share one property: none of them can be answered by looking at a single object.

What could not be established

  • The repository records its control count as 3,395 in the generated metrics file and 3,554 in the generated control reference. Which value is current, and how the generation times of the two documents differ, could not be established
  • The latest tag is v0.0.3 dated 2026-03-10 while commits continue through 2026-09-04. The reason no release was cut in between is not stated in the public release information and could not be established
  • The repository contains a substantial volume of SMT-format files and its documentation index lists Z3, Soufflé, Clingo and Prolog specifications, but which controls those reasoning engines are actually applied to could not be established, as those specification documents were not opened
  • No result of running the tool against a real account snapshot appears in this article. No execution verification was performed, so no statement is made about detection rate or false positive rate
  • The OWASP non-human identity top ten mapping document and the per-framework compliance mapping documents referenced by the README were not opened. The figure of ten frameworks comes from the generated metrics file
  • The full IAM policy evaluation logic reference is not cited here. The intersection description in the body rests on the effective permissions section of the permissions boundary page, while the complete specification of evaluation order lives in a separate document
  • Future expansion plans for the resource types supported by the IAM Access Analyzer internal access analyzer, and the precise adjudication range of custom policy checks, were treated only at the level of the overview page
  • The documentation mentions that some service interactions have additional controls against cross-service confused deputy issues, but an exhaustive list of which service carries which additional mechanism is scattered across individual service documents and was not compiled
