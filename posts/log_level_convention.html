WARN이 쓰레기통이 되는 이유 - 로그 레벨 규약을 합의하는 법

레벨은 심각도 등급이 아니라 읽는 사람에게 보내는 신호다

2026-08-01 개발/인프라

서론: 경고 로그가 하루 3만 줄이라 아무도 안 본다

어느 서비스든 시간이 지나면 같은 상태에 도달한다. 대시보드에서 WARN 필터를 걸면 화면이 끝없이 흐르고, 아무도 그걸 보지 않는다. 「경고니까 일단 봐야 하는 거 아니냐」고 물으면 다들 그렇다고 답하지만, 실제로 여는 사람은 없다. 그러다 정말 봐야 했던 한 줄이 그 안에 섞여 지나간다.

이때 흔히 나오는 처방이 「로그를 줄이자」다. 이것은 틀린 목표다. 문제는 양이 아니라 레벨이 아무 뜻도 갖지 않게 된 것이다. WARN이 「사람이 손대야 한다」를 뜻하지 않으면, WARN 필터는 아무것도 걸러 주지 않는다. 그러면 알림을 걸 자리가 사라진다.

이 글의 주장은 한 문장이다. 레벨은 「얼마나 나쁜가」의 등급이 아니라, 읽는 사람에게 보내는 신호다. ERROR가 「누군가 지금 봐야 한다」를 뜻해야 거기에 호출기를 걸 수 있다. WARN이 아무 뜻도 없으면 필터가 무의미해진다. 그래서 로그 레벨 규약은 코딩 스타일 취향이 아니라 알림과 직결된 설계다.

아래는 전부 실제로 로거를 돌려 확인한 것이다. 임계값을 바꿔 가며 같은 코드를 실행해 어느 줄이 사라지는지, 레벨의 내부 숫자가 무엇인지, 잘린 로그의 비용이 정말 0인지를 출력으로 확인했다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 도구는 Python 3.13.3의 표준 라이브러리 logging과 Node.js v22.16.0의 표준 라이브러리다. 이 기기에는 별도의 로깅 라이브러리가 설치돼 있지 않다. Node에서 널리 쓰이는 두 패키지를 불러 봤으나 둘 다 모듈을 찾을 수 없었고, 그래서 Node 쪽은 console과 util.debuglog만으로 확인했다. 없는 도구를 있는 것처럼 쓰지 않았다.

스크립트는 모두 파일로 저장해 실행했다. 한글이 섞인 코드를 셸 인자나 히어독으로 넘기면 조용히 변형되기 때문이다. 로거 이름과 메시지는 전부 가상의 주문·결제 서비스를 가정해 지어낸 것이다.

이 글이 다루지 않는 것. 로그 레코드에 어떤 필드를 담을지, 개인정보를 어디서 가릴지, 요청을 가로질러 식별자를 이어 붙일지는 각각 다른 주제다. 이 글은 레벨 한 점에만 머문다.

1. 레벨은 「중요도」가 아니라 자르는 기준이다

먼저 레벨이 실제로 하는 일을 보자. 같은 여덟 줄을 임계값만 바꿔 가며 네 번 돌렸다.

python 3.13.3 / win32
--- 1-1. same eight calls, four thresholds ---

threshold = DEBUG     -> 8 of 8 lines survive
   DEBUG    cache miss key=order:8821
   DEBUG    sql took 12ms rows=3
   INFO     order 8821 accepted
   INFO     payment captured amount=19900
   WARNING  retry 1/3 upstream=billing
   WARNING  config key TIMEOUT missing, using default
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: (none)

threshold = INFO      -> 6 of 8 lines survive
   INFO     order 8821 accepted
   INFO     payment captured amount=19900
   WARNING  retry 1/3 upstream=billing
   WARNING  config key TIMEOUT missing, using default
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: DEBUG

threshold = WARNING   -> 4 of 8 lines survive
   WARNING  retry 1/3 upstream=billing
   WARNING  config key TIMEOUT missing, using default
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: DEBUG, INFO

threshold = ERROR     -> 2 of 8 lines survive
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: DEBUG, INFO, WARNING

코드는 한 글자도 바뀌지 않았다. 바뀐 것은 임계값 하나다. 그런데 임계값이 한 칸 올라갈 때마다 통째로 사라지는 레벨이 하나씩 늘어난다. 여기서 첫 번째 결론이 나온다.

  • 레벨은 「이 줄이 얼마나 중요한가」를 적어 두는 라벨이 아니다
  • 레벨은 어느 임계값에서 이 줄이 사라지는가를 결정한다. 그게 전부다
  • 따라서 레벨을 정하는 것은 「이 줄을 누가 보게 할 것인가」를 정하는 일이다
  • 같은 사실을 두 사람이 다른 레벨로 적으면, 두 사람은 서로 다른 독자에게 그 사실을 보낸 것이다

한 줄만 떼어 임계값별로 보이는지 표시하면 더 분명해진다.

--- 1-2. the same line, seen or not seen, by threshold ---
threshold  visible    note
--------------------------------------------------------------
DEBUG      True       written out
INFO       True       written out
WARNING    True       written out
ERROR      False      the call still ran
CRITICAL   False      the call still ran

오른쪽 열에 주의하라. 보이지 않는다는 것은 실행되지 않았다는 뜻이 아니다. 호출은 그대로 일어났고 결과만 버려졌다. 이 사실이 7절의 비용 이야기로 이어진다.

2. 레벨은 그냥 정수다 - 사용자 정의 레벨의 대가

레벨의 정체는 단순하다. 내부 숫자를 그대로 찍어 봤다.

python 3.13.3 / win32
--- 2-1. the levels are just integers ---
name       value
------------------------
NOTSET     0
DEBUG      10
INFO       20
WARNING    30
ERROR      40
CRITICAL   50

WARNING is WARN  : True
gap between them : 10

--- 2-2. wedging a custom level in between ---
   TRACE    5    entered handler
   DEBUG    10   cache miss
   INFO     20   order accepted
   NOTICE   25   deploy finished, build 4412
   WARNING  30   retry 1/3
   ERROR    40   capture failed

레벨 사이 간격이 10씩 비어 있는 것은 우연이 아니다. 중간에 자기 레벨을 끼워 넣으라고 비워 둔 것이다. 실제로 5번에 TRACE, 25번에 NOTICE를 등록하니 정확히 그 자리에 정렬됐다.

그런데 여기에 대가가 있다. 등록하지 않은 숫자를 이름으로 되돌려 보면 이렇게 나온다.

--- 2-3. what a custom level costs you ---
threshold=INFO(20), NOTICE(25) and INFO(20) both pass:
   NOTICE   deploy finished
   INFO     order accepted

an unknown name reads back as a placeholder, not an error:
   getLevelName(25)  -> NOTICE
   getLevelName(23)  -> Level 23
   getLevelName(999) -> Level 999

a receiver that only knows the five names has to guess what 23 means.
the number sorts fine. the meaning does not travel.

핵심은 마지막 두 줄이다. 숫자는 정렬된다. 의미는 전달되지 않는다. 23이라는 숫자를 받은 수집기는 그것이 INFO보다 중한지 아닌지만 알 수 있고, 그 레벨이 무엇을 뜻하는지는 알 수 없다. 게다가 오류도 나지 않는다. 조용히 Level 23이라는 자리표시자로 흘러간다.

  • 사용자 정의 레벨은 내 프로세스 안에서만 이름을 갖는다
  • 수집·검색·알림 쪽이 그 숫자를 모르면, 그 줄은 필터링도 알림도 걸 수 없는 회색 지대가 된다
  • 널리 쓰이는 표준 심각도 정의 자체가 「심각도는 매우 주관적이므로 모든 발신자가 같은 정의를 갖고 있다고 가정하지 말라」고 못 박고 있다
  • 그래서 실무 권고는 단순하다. 사용자 정의 레벨을 쓰지 않거나, 쓴다면 수집 쪽 설정에 그 숫자를 반드시 등록해 둔다
  • 레벨을 늘리고 싶다는 충동은 대부분 레벨이 아니라 필드가 필요하다는 신호다. 「배포 이벤트」는 새 레벨이 아니라 INFO에 붙은 분류 필드로 푸는 게 맞다

3. 게이트는 둘이다 - 로거가 자른 것은 돌아오지 않는다

레벨을 다룰 때 가장 자주 나오는 오해가 여기 있다. 임계값이 하나가 아니다. 로거에 하나, 출력 대상마다 하나씩 있다. 두 개를 조합해 돌려 봤다.

python 3.13.3 / win32
--- 9-1. there are two gates, not one ---
4 calls each time: DEBUG, INFO, WARNING, ERROR

logger=DEBUG    console_h=NOTSET   audit_h=NOTSET   -> console 4, audit 4
logger=DEBUG    console_h=INFO     audit_h=ERROR    -> console 3, audit 1
logger=WARNING  console_h=DEBUG    audit_h=DEBUG    -> console 2, audit 2
logger=ERROR    console_h=DEBUG    audit_h=DEBUG    -> console 1, audit 1

--- 9-2. the practical shape: one lenient logger, several picky sinks ---
logger=DEBUG    console_h=INFO     audit_h=ERROR    -> console 3, audit 1

--- 9-3. the blunt instrument, and why it surprises people ---
logging.disable(WARNING) is active, logger level is DEBUG:
   ERROR line at ERROR
   -> 1 of 4 survived. it is a process-wide floor that outranks every logger.
   after disable(NOTSET): 4 of 4 survive again

셋째와 넷째 줄을 보라. 출력 대상은 DEBUG를 달라고 했는데 로거가 이미 자른 뒤라 아무 소용이 없었다. 로거 게이트가 먼저 걸리고, 출력 대상은 이미 통과한 것을 더 좁힐 수만 있다.

  • 「출력 대상을 DEBUG로 바꿨는데 아무것도 안 나온다」는 문의의 대부분이 이것이다. 로거 쪽을 안 본 것이다
  • 실무 배치는 로거는 넉넉하게, 출력 대상은 각자 좁게가 기본형이다
  • 사람이 실시간으로 보는 콘솔은 INFO, 호출기나 티켓 큐가 읽는 쪽은 ERROR로 두면 한 번 찍은 줄이 두 독자에게 다르게 도달한다
  • 프로세스 전역으로 바닥을 깔아 버리는 스위치도 있다. 이것은 로거 설정보다 위에 있어서, 로거를 DEBUG로 해 놔도 4줄 중 1줄만 남았다. 라이브러리가 이 스위치를 건드려 놓으면 어디를 고쳐도 로그가 안 나온다

4. WARN이 부풀어 오르는 과정

이제 서론의 증상으로 돌아간다. 작은 서비스 하루치를 호출 지점 단위로 모형화해 집계했다.

python 3.13.3 / win32
--- 3-1. one day of a small service, simulated ---
total lines/day : 61070
  ERROR          13    0.0%
  WARNING     30057   49.2%
  INFO        31000   50.8%

--- 3-2. inside WARNING, sorted by volume ---
call site                                         lines   share     cumul
--------------------------------------------------------------------------
deprecated field 'user_name' used by client        9800   32.6%     32.6%
cache miss, falling back to db key=%s              7400   24.6%     57.2%
optional header X-Trace absent                     5100   17.0%     74.2%
retry 1/3 upstream=billing                         4200   14.0%     88.2%
slow query 340ms                                   2600    8.7%     96.8%
config key TIMEOUT missing, using default 5s        880    2.9%     99.7%
token expires in 2 days                              60    0.2%     99.9%
disk usage 91 percent on queue volume                14    0.0%    100.0%
payment webhook signature mismatch                    3    0.0%    100.0%

lines a human should act on today : 77
lines emitted at WARNING           : 30057
signal ratio                       : 1 in 390

이 표가 「WARN이 쓰레기통이 되는 과정」 전부다. 순서대로 읽어 보자.

  • WARN이 전체의 49.2퍼센트다. 절반이 경고인 로그에서 경고는 아무 의미가 없다
  • 상위 3개 호출 지점이 WARN의 74.2퍼센트를 만든다. 3만 줄이 「많은 종류의 경고」가 아니라 「같은 세 줄의 반복」이다
  • 그 세 줄은 각각 사용 중단 예정 필드 사용, 캐시 미스, 선택적 헤더 없음이다. 어느 것도 사람이 행동할 대상이 아니다
  • 정말 사람이 봐야 하는 줄은 아래 세 개, 하루 77건뿐이다. 390줄 중 1줄이다
  • 결정적으로, 이 상태를 만든 것은 나쁜 개발자가 아니다. 각각의 호출 지점은 작성될 때는 합리적이었다. 「이건 정상은 아니니까 WARN」이라는 판단이 아홉 번 쌓였을 뿐이다

이 상태에서 알림을 걸면 어떻게 되는지 계산해 봤다.

--- 3-3. what an alert on WARNING would do ---
  a  1-minute window carries     20.9 WARNING lines
  a  5-minute window carries    104.4 WARNING lines
  a 60-minute window carries   1252.4 WARNING lines
  an alert that pages on 'any WARNING' pages every window, forever.
  an alert that pages above a threshold has to sit above 20/min noise,
  which is higher than the 3 lines/day that actually mattered.

--- 3-4. same stream after reclassifying by 'must a human act now' ---
level          before      after
--------------------------------
ERROR              13         16
WARNING         30057         74
INFO            31000      48480
DEBUG               0      12500

WARNING/day : 30057 -> 74
ERROR/day   : 13 -> 16
now 'any WARNING today' is a 74-line list a person can read.
and ERROR stays small enough to page on.

여기가 이 글의 논지가 드러나는 지점이다. 알림을 걸 수 있느냐가 레벨 정의의 품질로 결정된다. 분당 20.9줄이 흐르는 채널에는 어떤 임계값을 걸어도 소용이 없다. 정말 중요했던 것은 하루 3줄인데, 소음 바닥이 그것보다 훨씬 높기 때문이다.

재분류 후 숫자를 보라. 총 로그량은 6만 1,070줄로 똑같다. 줄어든 것은 WARN뿐이고, 대신 INFO와 DEBUG가 늘었다. 목표는 로그를 줄이는 게 아니라 ERROR와 WARN을 읽을 수 있게 만드는 것이라는 말이 이 표에 그대로 있다.

5. 판단 기준 - 「지금 사람이 행동해야 하는가」

그러면 무엇을 기준으로 가르나. Node 쪽 표준 라이브러리로 규칙을 세우고 실제 호출 지점에 적용해 봤다.

node v22.16.0 / win32
installed logging packages on this machine: none
  require("winston") -> MODULE_NOT_FOUND
  require("pino")    -> MODULE_NOT_FOUND

--- 4-1. console has level-looking names but no threshold ---
method      stream    dropped when quiet
----------------------------------------------
console.log     stdout    never
console.debug   stdout    never
console.info    stdout    never
console.warn    stderr    never
console.error   stderr    never

there is no setLevel and no threshold. nothing is ever dropped.
a debug line in a hot loop is written in production exactly as
often as on a laptop. the four names only pick a stream.

--- 4-2. the stdlib does ship one gated channel: util.debuglog ---
NODE_DEBUG              : ""
payment channel enabled : false
db channel enabled      : false
(no channel output above: both are off)

이 출력이 알려 주는 사실이 중요하다. 레벨처럼 생긴 이름이 있다고 레벨 기능이 있는 것은 아니다. 이 런타임의 기본 콘솔 함수 네 개는 임계값이 없고, 결정하는 것은 출력 스트림 하나뿐이다. 실제로 표준 출력을 버리고 실행하면 warn과 error만 남는다. 즉 이 함수들만 쓰는 코드에서는 DEBUG 줄이 운영 환경에서도 한 줄도 빠짐없이 디스크에 쓰인다.

다만 이 런타임의 표준 라이브러리에도 켜고 끌 수 있는 채널이 하나 있다. 환경변수로 채널 이름을 지정해야만 출력되고, 켜져 있는지 코드에서 물어볼 수도 있다. 실제로 환경변수에 결제 채널만 지정하고 돌리면 결제 채널은 true, 데이터베이스 채널은 false가 되고 결제 쪽 한 줄만 출력됐다. 이것이 8절에서 말할 「모듈별로 레벨 내리기」의 가장 단순한 형태다.

5.1 질문을 바꾸면 답이 하나로 좁혀진다

레벨 논쟁이 끝나지 않는 이유는 질문이 틀렸기 때문이다. 「이게 얼마나 심각한가」로 물으면 답은 취향이 된다. 질문을 바꿔야 한다.

이 줄이 떴을 때, 사람이 무엇을, 언제 해야 하는가?

이 질문에 대한 답이 네 가지뿐이고, 그 네 가지가 그대로 네 레벨이 된다.

레벨한 문장 정의읽는 사람이 할 일시간알림
ERROR시스템이 해야 할 일을 못 했고 우리가 고쳐야 한다지금 확인한다새벽이라도호출
WARN사람이 손대야 하지만 오늘 밤은 아니다업무 시간에 처리한다이번 주일간 요약
INFO아무도 행동하지 않는다. 무슨 일이 있었는지 기록한다사후 추적할 때만 읽는다-없음
DEBUG버그를 재현하는 동안에만 쓸모 있다재현 중에만 켠다-없음

정의에 형용사가 하나도 없다는 점에 주목하라. 「심각한」, 「중대한」, 「중요한」 같은 말은 사람마다 선이 다르고, 규약을 문서로만 남게 만든다. 반면 「새벽에 사람을 깨우는가」는 두 사람이 같은 답을 낸다.

이 아홉 줄 가운데 팀에서 반드시 논쟁이 붙는 두 줄이 있다. 그 두 줄이 WARN이 쓰레기통이 되는 경로 전부다.

상황흔한 선택옳은 선택이유
재시도 후 성공WARNINFO사용자에게 아무 일도 안 일어났다
클라이언트가 보낸 JSON이 깨짐ERRORINFO400을 돌려준 것은 시스템이 제대로 동작한 것
캐시 미스WARNDEBUG캐시가 설계대로 동작 중이다

인증서 만료 9일 전INFOWARN사람이 이번 주에 손대야 한다
결제 캡처 실패WARNERROR돈이 안 움직였고 우리가 고쳐야 한다

가장 비싼 습관 하나. 「정상은 아니니까 일단 WARN」이 4절의 3만 줄을 만든 원인이다. 이 습관에는 확실한 대체 규칙이 있다. 확신이 없으면 INFO다. WARN은 「사람이 이번 주에 손댈 것」만 담는 좁은 서랍이어야 하고, 그 서랍이 좁게 유지될 때만 열어 볼 가치가 생긴다.

6. 예외를 잡았을 때 어디서 찍나

레벨 규약이 가장 자주 무너지는 곳이 예외 처리다. 계층마다 잡아서 찍고 다시 던지는 흔한 패턴을 그대로 실행해 봤다.

python 3.13.3 / win32
--- 5-1. log-and-rethrow at every layer ---
   ERROR    app.db         db call failed: connect timeout to billing-db after 3000ms
   ERROR    app.service    could not load order: connect timeout to billing-db after 3000ms
   ERROR    app.api        request failed: connect timeout to billing-db after 3000ms
   -> 3 ERROR lines, 1 actual failure, 1 user-visible 500

--- 5-2. raise once, log once at the boundary that decides ---
   ERROR    app.api        request failed order=8821
   + 8 traceback lines attached to that single record
   -> 1 ERROR line, and it carries the full stack

--- 5-3. exception that was recovered from ---
   INFO     app.service    retry 1/3 after connect timeout
   INFO     app.service    retry 2/3 after connect timeout
   result: {'order': 8821}
   nothing failed for the user, so nothing is ERROR

--- 5-4. exception deliberately ignored ---
   5 lines at DEBUG (traceback included)
   visible only when someone turns DEBUG on for this module

첫 블록이 문제다. 실제 실패는 1건인데 ERROR가 3줄 남았다. 사용자에게 보인 오류도 1건이다. 이 상태에서 「하루 ERROR 몇 건」을 세면 실패 건수의 세 배가 나오고, 여기에 알림 임계값을 잡으면 그 배수가 그대로 오차가 된다.

두 번째 블록이 해법이다. 던지는 쪽에서는 아무것도 찍지 않는다. 던지는 행위 자체가 상위에 알리는 수단이기 때문이다. 대신 포기하기로 결정한 경계 한 곳에서 스택트레이스를 붙여 한 번 찍는다. 결과는 ERROR 1줄에 호출 스택 8줄이다. 줄 수는 3분의 1이 됐고 정보량은 늘었다.

상황레벨누가 찍나근거
재시도로 복구됨INFO복구한 계층사용자에게 아무 일도 안 일어났다
삼키고 넘어감, 영향 없음DEBUG삼킨 계층재현 중에만 필요하다
상위로 다시 던짐아무도 안 찍음-던지는 것 자체가 메시지다
500으로 바뀜ERROR포기한 경계 한 곳우리가 고쳐야 한다
400으로 바뀜INFO경계 한 곳호출자가 틀린 것이다
  • 「나중에 원인을 못 찾을까 봐」 계층마다 찍는 습관은 스택트레이스 한 번으로 완전히 대체된다
  • 재시도 로그를 WARN으로 두는 것이 4절의 4,200줄을 만들었다. 복구에 성공했으면 실패가 아니다
  • 세 번 찍힌 예외는 같은 사건인지 다른 사건인지 사후에 구분할 수 없다. 요청 단위 식별자가 없으면 더 그렇다
  • 클라이언트가 잘못 보낸 요청을 ERROR로 찍으면 남이 만든 트래픽이 우리 호출기를 울린다. 외부에서 호출기를 누를 수 있는 구조가 된다

7. 잘려도 비용은 이미 냈다

1절 마지막에 나온 「보이지 않는다는 것이 실행되지 않았다는 뜻은 아니다」를 수치로 확인한다. 임계값을 WARNING으로 두고 DEBUG 호출 20만 번을 다섯 가지 방식으로 측정했다.

python 3.13.3 / win32
one run on one machine. treat the ratios, not the absolute numbers.

--- 6-1. cost of a DEBUG line that is thrown away (threshold=WARNING) ---
form                                  total sec    per call us   vs guard
--------------------------------------------------------------------------
f-string built up front                  0.8994          4.497
json.dumps built up front                0.8100          4.050
%-style args, lazy                       0.0416          0.208
isEnabledFor guard                       0.0226          0.113       1.0x
no logging call at all                   0.0081          0.040       0.4x

f-string form is 39.9x the guarded form
json form is     35.9x the guarded form
lazy %-args is   1.8x the guarded form

all five produced ZERO output lines. the threshold was WARNING throughout.

--- 6-2. where the money actually goes ---
building the string only        : 0.8064 sec  (4.032 us/call)
calling lg.debug('x') only      : 0.0373 sec  (0.187 us/call)
-> the call itself is cheap. the argument you built is not.

--- 6-3. at production volume ---
    1000 debug calls/sec -> eager    4.5 ms/sec of cpu, guarded   0.1 ms/sec
   20000 debug calls/sec -> eager   89.9 ms/sec of cpu, guarded   2.3 ms/sec
  and none of it reaches a file, because DEBUG is off.

--- 6-4. the same guard, when DEBUG is ON ---
threshold=DEBUG, 20000 lazy calls : 0.3750 sec (18.749 us/call)
bytes written                     : 2960000
-> once the line is kept, formatting happens anyway. lazy only helps when filtered.

이 숫자는 이 기기에서 한 번 측정한 값이다. 다른 기기, 다른 파이썬 빌드, 다른 부하에서 절대값은 달라진다. 절대 시간이 아니라 비율만 가져가라. 재보면 여러분 환경에서도 대략 같은 순서가 나올 것이다.

읽는 법은 이렇다.

  • 다섯 방식 모두 출력은 0줄이었다. 임계값이 WARNING이었으므로 DEBUG는 전부 잘렸다
  • 그런데 문자열을 미리 조합한 방식이 임계값 확인 후 조합하는 방식보다 39.9배 느렸다. 잘린 것은 출력이지 조합 비용이 아니다
  • 어디에 돈이 드는지는 6-2가 답한다. 로거 호출 자체는 호출당 0.187마이크로초로 싸다. 넘길 문자열을 만드는 데 4.032마이크로초가 든다. 비싼 것은 호출이 아니라 인자다
  • 포맷 문자열과 값을 따로 넘기는 지연 평가 방식은 0.208마이크로초로, 미리 조합하는 것보다 20배 이상 싸다. 임계값을 통과한 줄만 조립되기 때문이다
  • 초당 2만 건 규모에서 이 차이는 CPU 89.9밀리초 대 2.3밀리초가 된다. 그리고 그 전부가 파일에 한 글자도 안 남는다
  • 마지막 블록이 균형을 잡아 준다. 임계값을 통과하면 어차피 포맷은 일어난다. 지연 평가는 잘릴 때만 이득이고, 켜면 호출당 18.749마이크로초로 뛴다

실무 규칙으로 정리하면 세 줄이다. 인자는 지연 평가로 넘긴다. 직렬화처럼 무거운 인자는 임계값을 확인한 뒤에만 만든다. 그리고 DEBUG를 켜는 것은 공짜가 아니라는 것을 알고 켠다.

8. 재배포 없이 레벨 바꾸기

규약이 실제로 지켜지려면 레벨을 내리는 일이 쉬워야 한다. 어렵게 만들어 두면 사람들은 「나중에 볼지 모르니까」 미리 WARN으로 올려 두고, 그게 4절의 3만 줄이 된다. 로거 이름을 계층으로 두고 돌려 봤다.

python 3.13.3 / win32
--- 7-1. baseline: root of the tree at WARNING ---
shop=WARNING  -> 1 lines
   WARNING  shop.payment.gateway retry 1/3

--- 7-2. same process, one line changes the threshold ---
shop=INFO  -> 4 lines
   INFO     shop.db            pool size 8/20
   INFO     shop.payment       capture ok order=8821
   WARNING  shop.payment.gateway retry 1/3
   INFO     shop.web           200 GET /orders/8821 12ms

--- 7-3. turn up ONE module only, leave the rest alone ---
shop=WARNING, shop.payment=DEBUG  -> 4 lines
   DEBUG    shop.payment       building capture request amount=19900
   INFO     shop.payment       capture ok order=8821
   DEBUG    shop.payment.gateway http POST /v1/charges
   WARNING  shop.payment.gateway retry 1/3
   note shop.payment.gateway inherited DEBUG from its parent

7-3이 핵심이다. 결제 모듈만 DEBUG로 내렸고 나머지는 건드리지 않았다. 그런데 그 하위인 게이트웨이 로거도 함께 따라 내려갔다. 왜 그런지는 다음 출력이 설명한다.

--- 7-4. effective level is resolved by walking up the name ---
logger                   own level    effective
--------------------------------------------------
shop                     WARNING      WARNING
shop.db                  DEBUG        DEBUG
shop.payment             NOTSET       WARNING
shop.payment.gateway     NOTSET       WARNING
shop.web                 NOTSET       WARNING
NOTSET means 'ask my parent'. that is why one name can steer a whole subtree.

--- 7-5. driving it from the environment, no redeploy ---
  LOG_LEVELS=shop=WARNING                       -> 1 lines
     WARNING  shop.payment.gateway retry 1/3

  LOG_LEVELS=shop=WARNING,shop.payment=DEBUG    -> 4 lines
     DEBUG    shop.payment       building capture request amount=19900
     INFO     shop.payment       capture ok order=8821
     DEBUG    shop.payment.gateway http POST /v1/charges
     WARNING  shop.payment.gateway retry 1/3

  LOG_LEVELS=shop=ERROR,shop.web=INFO           -> 1 lines
     INFO     shop.web           200 GET /orders/8821 12ms

--- 7-6. the safety rail: a raise-only window ---
  shop=DEBUG                         depth=0  allowed=False
  shop.payment=DEBUG                 depth=1  allowed=True
  shop.payment.gateway=DEBUG         depth=2  allowed=True
  • 하위 로거를 미설정 상태로 두면 부모에게 위임한다. 그래서 상위 이름 하나로 서브트리 전체를 조종할 수 있다
  • 반대로 하위에 명시적으로 값을 박아 두면 부모를 바꿔도 그 가지는 안 따라온다. 배포 시점에 모든 로거에 레벨을 설정하는 코드가 있으면 운영 중 조정이 통째로 막힌다
  • 환경변수에 이름=레벨 목록을 받아 적용하면 프로세스를 다시 띄우지 않고 필터가 바뀐다. 7-5의 세 줄이 같은 프로세스에서 순서대로 실행된 결과다
  • 7-5 마지막 사례를 눈여겨보라. 최상위를 ERROR로 올렸더니 게이트웨이의 WARNING이 사라졌다. 하위가 미설정이라 부모의 ERROR를 물려받았기 때문이다. 위임은 양방향으로 작동한다
  • 안전장치가 필요하다. 최상위 이름 전체를 DEBUG로 내리는 요청은 거부하고 하위 모듈에만 허용한다. 그러지 않으면 오타 하나로 클러스터가 자기 로그에 묻힌다
  • 임시로 내린 레벨에는 만료 시간을 둔다. 되돌리는 것을 잊는 것이 기본값이다

9. 규약 만들기 - 팀이 합의할 것들

여기까지가 재료다. 이제 팀이 실제로 문서에 적어야 할 것을 정리한다. 그리고 이미 3만 줄이 쌓인 저장소를 어떻게 되돌리는지도.

합의 항목구체적으로 무엇을 적나안 적으면
레벨 정의레벨당 한 문장. 행동으로 서술하고 형용사를 쓰지 않는다사람마다 선이 달라진다
알림 대응표어느 레벨이 어디로 가는지 정의 바로 옆에정의가 알림과 따로 표류한다
레벨을 올리는 절차ERROR로 올리면 호출기가 울린다 → 리뷰어 승인ERROR가 조용히 불어난다
레벨을 내리는 절차누구나, 소음 신고와 같은 변경 묶음에서내리는 게 번거로워 아무도 안 한다
필수 필드레벨과 무관하게 모든 레코드가 같은 항목을 갖는다레벨별로 검색 방법이 달라진다
ERROR 예산하루 N건. 넘으면 코드가 아니라 규약이 깨진 것기준이 없어 되돌리는 계기가 안 생긴다
자동 강등 규칙30일간 아무도 조치 안 한 줄은 기본 강등한 번 올라간 레벨이 영원히 남는다

9.1 이미 쌓인 로그를 재분류하는 절차

기존 저장소를 손보는 순서를 실행으로 확인했다.

python 3.13.3 / win32
--- 8-1. inventory a day of logs by call site, not by line ---
template                                 level     lines/day   verdict
------------------------------------------------------------------------

--- 8-2. a grep-shaped rule you can run against source ---
  log.warn("retry %s/3", attempt)                       WARN nobody acts on -> INFO or DEBUG
  log.warning("cache miss for key %s", key)             WARN nobody acts on -> INFO or DEBUG
  log.error("could not parse client json: %s", err)     ERROR caused by the caller -> probably INFO
  log.warning("deprecated endpoint hit by %s", ua)      WARN nobody acts on -> INFO or DEBUG
  log.error("could not load user, returning cached cop  ERROR that recovered -> probably INFO
  5 of 7 call sites flagged by three regexes
  this finds candidates, not answers. a human confirms each one.

--- 8-3. did the change actually work? measure before and after ---
level          before      after    readable?
----------------------------------------------
ERROR              13         16          yes
WARNING         30057         74          yes
INFO            31000      48480          yes
DEBUG               0      12500          yes

the target is not 'fewer logs'. total lines went UP: 61070 -> 61070
the target is that ERROR and WARNING became short enough to read.
  1. 줄이 아니라 호출 지점으로 센다. 같은 템플릿이 몇 번 찍혔는지 집계한다. 상위 10개가 보통 전체의 90퍼센트다
  2. 산수로 1차 선별한다. ERROR나 WARN인데 하루 500건을 넘는 호출 지점은 사람이 행동할 대상이 될 수 없다. 12개 중 6개가 걸렸고 그 6개가 2만 9,980줄을 만들고 있었다. 여기까지는 판단이 필요 없다
  3. 소스에 정규식을 돌려 후보를 모은다. 복구했는데 ERROR, 호출자 잘못인데 ERROR, 아무도 안 보는 WARN 세 가지 패턴으로 7개 중 5개가 걸렸다. 정규식은 후보만 찾는다. 판정은 사람이 한 건씩 한다
  4. 강등을 먼저, 승격을 나중에 한다. 강등은 되돌리기 쉽고 알림을 건드리지 않는다
  5. 한 변경 묶음에 한 모듈만 담는다. 리뷰어가 각 줄의 「누가 언제」를 실제로 판단할 수 있는 크기여야 한다
  6. 전후를 측정한다. 8-3을 보라. 총 줄 수는 6만 1,070줄로 똑같은데 WARN이 3만 57줄에서 74줄이 됐다. 목표는 총량이 아니라 가독성이다
  7. 알림 규칙을 같은 변경 묶음에서 고친다. 레벨만 바꾸고 알림을 안 고치면 규약이 문서로만 남는다

9.2 점검 목록

  • 레벨 정의를 행동 문장으로 적었다 (형용사가 없다)
  • ERROR의 정의와 알림 규칙이 한 문서에 있다
  • 「재시도 성공」이 WARN이 아니다
  • 「클라이언트 입력 오류」가 ERROR가 아니다
  • 같은 예외를 한 곳에서만 찍는다
  • 스택트레이스는 포기하는 경계에서 한 번만 붙인다
  • DEBUG 인자를 미리 조립하지 않는다
  • 무거운 인자는 임계값 확인 뒤에 만든다
  • 재배포 없이 모듈 단위로 임계값을 내릴 수 있다
  • 임시로 내린 레벨에 만료 시간이 있다
  • 최상위 이름을 통째로 DEBUG로 내리는 것을 막는 장치가 있다
  • ERROR 일일 예산을 정했고 초과 시 대응이 정해져 있다
  • 사용자 정의 레벨을 쓰지 않거나, 썼다면 수집 쪽이 그 숫자를 안다
  • 30일간 아무도 조치하지 않은 ERROR·WARN 줄을 찾는 정기 점검이 있다
  • 상위 호출 지점 비중을 주기적으로 본다

결론: 레벨은 알림 설계다

처음 질문으로 돌아간다. 왜 WARN이 쓰레기통이 되나. 나쁜 개발자 때문이 아니다. 「정상은 아니니까 일단 WARN」이라는 판단이 각각은 합리적인 채로 아홉 번 쌓였기 때문이다. 그 결과가 4절의 390 대 1이다.

이 글에서 하나만 가져간다면 이것이다. 레벨을 정하는 것은 이 줄을 누구에게 보낼지 정하는 일이다. 「얼마나 나쁜가」로 물으면 답이 취향이 되고, 취향은 합의되지 않는다. 「누가 언제 무엇을 하는가」로 물으면 답이 하나로 좁혀지고, 그 답은 그대로 알림 규칙이 된다.

그래서 규약을 만드는 일은 문서 작업이 아니다. ERROR가 「지금 봐야 한다」를 뜻할 때만 거기에 호출기를 걸 수 있고, WARN이 좁게 유지될 때만 그 서랍을 열어 볼 가치가 생긴다. 필터가 의미를 갖느냐 마느냐가 규약 한 장에 달려 있다.

마지막으로, 널리 인용되는 표준 심각도 정의 자체가 이 점을 인정한다. 심각도는 매우 주관적이므로 모든 발신자가 같은 정의를 갖고 있다고 가정해서는 안 된다고 적혀 있다. 표준조차 정의를 대신해 주지 않는다는 뜻이다. 그 정의는 팀이 직접 써야 한다.

# 로그 레벨 규약 — 복붙용 정의표·재분류 절차·점검 목록

> 출처: braindetox.kr — WARN이 쓰레기통이 되는 이유
> 근거: Windows 10 / Python 3.13.3 표준 logging / Node.js v22.16.0 실행 검증
> 원칙: 레벨은 심각도가 아니라 **누가 언제 무엇을 하는가**의 선언이다

## 1. 레벨 정의표 — 행동 기준으로 쓴 것

| 레벨 | 한 문장 정의 | 읽는 사람이 할 일 | 시간 | 알림 |
|---|---|---|---|---|
| **ERROR** | 시스템이 해야 할 일을 못 했고 우리가 고쳐야 한다 | 지금 확인한다 | 새벽이라도 | 호출(page) |
| **WARN** | 사람이 손대야 하지만 오늘 밤은 아니다 | 업무 시간에 처리한다 | 이번 주 | 일간 요약 |
| **INFO** | 아무도 행동하지 않는다. 무슨 일이 있었는지 기록한다 | 사후 추적할 때만 읽는다 | — | 없음 |
| **DEBUG** | 버그를 재현하는 동안에만 쓸모 있다 | 재현 중에만 켠다 | — | 없음 |

핵심 판정 질문은 하나다.

> **이 줄이 떴을 때 사람이 무엇을, 언제 해야 하는가?**

「얼마나 나쁜가」로 물으면 답이 취향이 되고, 「누가 언제 행동하는가」로 물으면 답이 하나로 좁혀진다.

### 자주 틀리는 두 줄

| 상황 | 흔한 선택 | 옳은 선택 | 이유 |
|---|---|---|---|
| 재시도 후 성공 | WARN | **INFO** | 사용자에게 아무 일도 안 일어났다 |
| 클라이언트가 보낸 JSON이 깨짐 | ERROR | **INFO** | 400을 돌려준 것은 시스템이 제대로 동작한 것 |
| 캐시 미스 | WARN | **DEBUG** | 캐시가 설계대로 동작 중이다 |
| 설정 기본값 사용 | WARN | **INFO** | 기본값이 있다는 것은 정상 경로다 |
| 인증서 만료 9일 전 | INFO | **WARN** | 사람이 이번 주에 손대야 한다 |
| 결제 캡처 실패 | WARN | **ERROR** | 돈이 안 움직였고 우리가 고쳐야 한다 |

## 2. 예외를 잡았을 때 어디서 찍나

| 상황 | 레벨 | 누가 찍나 |
|---|---|---|
| 재시도로 복구됨 | INFO | 복구한 계층 |
| 삼키고 넘어감, 영향 없음 | DEBUG | 삼킨 계층 |
| 상위로 다시 던짐 | **아무도 안 찍음** | 던지는 것 자체가 메시지다 |
| 500으로 바뀜 | ERROR | 포기한 경계 한 곳 |
| 400으로 바뀜 | INFO | 경계 한 곳 (호출자가 틀린 것) |

**같은 예외가 세 번 찍히는 패턴**은 계층마다 잡아서 찍고 다시 던지기 때문에 생긴다.
실행으로 확인하면 실패 1건에 ERROR 3줄, 사용자에게 보인 오류는 1건이다.
경계 한 곳에서만 스택트레이스를 붙여 찍으면 ERROR 1줄로 줄고, 정보량은 오히려 늘어난다.

## 3. 팀이 문서에 적어야 할 항목

| 항목 | 왜 필요한가 |
|---|---|
| 레벨 정의 4~5줄 | 심각도가 아니라 **행동**으로 서술한다 |
| 레벨을 올리는 절차 | ERROR로 올리면 호출기가 울린다 → 리뷰어 승인 필요 |
| 레벨을 내리는 절차 | 누구나, 소음 신고와 같은 PR에서 |
| 필수 필드 | 레벨과 무관하게 모든 레코드가 같은 필드를 갖는다 |
| ERROR 예산 | 하루 N건을 넘으면 코드가 아니라 규약이 깨진 것 |
| 자동 강등 규칙 | 30일간 아무도 조치하지 않은 줄은 기본 강등 |
| 어느 레벨이 어디로 알림 가는가 | 정의 바로 옆에 적지 않으면 정의가 표류한다 |

## 4. 기존 로그 재분류 절차

1. **줄이 아니라 호출 지점으로 센다.** 같은 템플릿이 몇 번 찍혔는지 집계한다. 상위 10개가 보통 전체의 90퍼센트를 차지한다.
2. **산수로 1차 선별한다.** ERROR/WARN인데 하루 500건을 넘는 호출 지점은 사람이 행동할 수 있는 대상이 아니다. 판단이 필요 없다.
3. **소스에 정규식을 돌려 후보를 모은다.**
   - `\.error\(.*(retry|fallback|cached)` → 복구했는데 ERROR
   - `\.error\(.*(client|invalid|parse|malformed)` → 호출자 잘못인데 ERROR
   - `\.(warn|warning)\(.*(cache miss|deprecated|retry)` → 아무도 안 보는 WARN
   - 정규식은 **후보만** 찾는다. 판정은 사람이 한 건씩 확인한다.
4. **강등을 먼저, 승격을 나중에 한다.** 강등은 되돌리기 쉽고 알림을 건드리지 않는다.
5. **한 PR에 한 모듈만 담는다.** 리뷰어가 각 줄의 「누가 언제」를 실제로 판단할 수 있는 크기로 자른다.
6. **전후를 측정한다.** 목표는 총량 감소가 아니다. **ERROR와 WARN이 사람이 읽을 만한 길이가 되는 것**이다. 총 줄 수는 늘어도 상관없다.
7. **알림 규칙을 같은 PR에서 고친다.** 레벨만 바꾸고 알림을 안 고치면 규약이 문서로만 남는다.

### 측정 지표

| 지표 | 목표 | 의미 |
|---|---|---|
| ERROR / 일 | 사람이 다 읽을 수 있는 수 | 넘으면 호출기가 무시된다 |
| WARN / 일 | 아침 회의에서 훑을 수 있는 수 | 넘으면 필터가 무의미해진다 |
| ERROR 중 실제 조치 비율 | 높을수록 좋다 | 낮으면 ERROR 정의가 틀린 것 |
| 상위 3개 호출 지점 비중 | 낮을수록 좋다 | 높으면 한두 줄이 로그를 삼키고 있다 |

## 5. 운영 중 레벨 바꾸기

- 임계값은 **로거 이름 단위**로 잡는다. 이름을 점으로 계층화하면 상위 이름 하나로 하위 전체를 조종할 수 있다.
- 하위 로거는 기본적으로 **미설정** 상태로 두고 부모에게 위임한다. 그래야 한 줄로 서브트리 전체가 바뀐다.
- 환경변수나 설정 엔드포인트로 `이름=레벨` 목록을 받아 적용한다. **재배포가 필요 없어야 한다.**
- 안전장치: 최상위 이름 전체를 DEBUG로 내리는 요청은 거부하고, **하위 모듈에 한해** 허용한다. 안 그러면 오타 하나로 클러스터가 로그에 묻힌다.
- 임시로 내린 레벨은 **만료 시간**을 둔다. 되돌리는 것을 잊는 것이 기본값이다.

### 두 개의 게이트를 혼동하지 말 것

로거 임계값이 먼저 걸리고, 그다음 각 출력 대상(싱크)의 임계값이 걸린다.
**로거가 자른 것은 싱크를 아무리 낮춰도 돌아오지 않는다.**
「싱크를 DEBUG로 했는데 아무것도 안 나온다」는 대부분 이것이다.

실전 배치는 보통 이 모양이다.

- 로거: 넉넉하게 (레코드 생성 자체는 허용)
- 콘솔 싱크: INFO (사람이 실시간으로 보는 것)
- 알림 싱크: ERROR (호출기·티켓 큐가 읽는 것)

## 6. 비용 규칙

- **필터에 잘려도 인자를 미리 만든 비용은 이미 발생한다.** 문자열을 붙이거나 직렬화한 뒤에 로거에 넘기면, 그 줄이 버려져도 CPU는 썼다.
- 인자를 **지연 평가**로 넘긴다. 포맷 문자열과 값을 따로 넘기면 임계값을 통과한 줄만 조립된다.
- 무거운 인자(직렬화, 큰 컬렉션 순회)는 **임계값 확인 후에만** 만든다.
- 임계값을 통과하면 어차피 포맷은 일어난다. 지연 평가는 **잘릴 때만** 이득이다.

## 7. 발행 전 점검 목록

- [ ] 레벨 정의를 **행동 문장**으로 적었다 (「심각한」, 「중요한」 같은 형용사가 없다)
- [ ] ERROR의 정의와 **알림 규칙이 한 문서에** 있다
- [ ] 「재시도 성공」이 WARN이 아니다
- [ ] 「클라이언트 입력 오류」가 ERROR가 아니다
- [ ] 같은 예외를 **한 곳에서만** 찍는다
- [ ] 스택트레이스는 **포기하는 경계**에서 한 번만 붙인다
- [ ] DEBUG 인자를 미리 조립하지 않는다
- [ ] 무거운 인자는 임계값 확인 뒤에 만든다
- [ ] 재배포 없이 **모듈 단위로** 임계값을 내릴 수 있다
- [ ] 임시로 내린 레벨에 **만료 시간**이 있다
- [ ] 최상위 이름을 통째로 DEBUG로 내리는 것을 막는 장치가 있다
- [ ] ERROR **일일 예산**을 정했고 초과 시 대응이 정해져 있다
- [ ] 사용자 정의 레벨을 **쓰지 않거나**, 썼다면 수집 쪽이 그 숫자를 안다
- [ ] 30일간 아무도 조치하지 않은 ERROR/WARN 줄을 찾는 정기 점검이 있다
- [ ] 상위 호출 지점 비중을 주기적으로 본다

## 8. 하지 말 것

- 「일단 WARN」 — 확신이 없으면 INFO다. WARN은 사람이 이번 주에 손댈 것만 담는다
- 심각도 형용사로 정의를 쓰는 것 — 「중대한」의 기준은 사람마다 다르다
- 계층마다 잡아서 찍고 다시 던지는 것 — 한 실패가 여러 줄이 되어 집계를 왜곡한다
- 사용자 정의 레벨을 정렬만 보고 끼워 넣는 것 — 숫자는 정렬되지만 **의미는 수집 쪽에 전달되지 않는다**
- 알림 규칙을 그대로 두고 레벨만 바꾸는 것 — 규약이 문서로만 남는다
- 로그 총량을 목표로 삼는 것 — 목표는 **ERROR와 WARN이 읽히는 것**이다
- 싱크 임계값만 낮추고 로거 임계값을 안 보는 것 — 로거가 자른 것은 돌아오지 않는다
- 오래된 레벨을 「원래 그랬으니」 두는 것 — 아무도 조치 안 한 줄은 강등 대상이다
