求星期几为什么需要公式

在7和365对不齐的地方，Zeller与Sakamoto替我们算的是什么

2026年8月28日 开发/基础设施

引言：计算机怎么知道今天是星期五

2026年8月28日是星期五。要让计算机造出这句话，需要做些什么？不是去翻日历，也不是某处存着一张写好星期的表格供人查阅。它在计算。可是这个计算比想象中脏得多。

脏的原因在于日历既是规则又是不规则。星期每7天准确轮回一次。而一年是365天或366天，究竟是哪一种由4年、100年、400年这三级条件决定。月份长度混杂着28、29、30、31，这个次序背后没有任何算术上的理由。一个完美规则的周期，必须叠在人类花了一千年反复修补出来的不规则体系之上。

2026年8月，GeekNews上出现了「让星期计算更快的方法」。这是Ben Joffe在同月17日公开的文章，提出把从基准日算起的天数转成星期的最后一步，压缩为一次乘法加一次移位。着眼点在于7是梅森数，也就是2的幂减1的数，因而可以把除以7的余数搬到除以8的余数上去。

这里要看的不是那个技巧本身，而是它所站的位置。为什么需要公式，公式又预先算好了什么，以及为什么会有人连最后剩下的一次除法都想消掉。文章最后附上一个诚实的问题：这真的能让谁的程序变快吗。

1. 7除不尽365

所有问题的起点是一次除法。365除以7，商是52，余数是1。所以平年过去之后，同一个日期的星期就往后挪一天。闰年是366，余数变成2，挪两天。

如果这个挪动每年都是同一个值，那就不成问题，一次乘法即可了结。问题在于挪1和挪2有规律地混在一起，而决定这种混合的正是闰年规则。

1.1 闰年的三级规则 — 4、100、400

格里高利历的闰年判定由三个条件层叠而成。

  • 年份能被4整除就是闰年
  • 但能被100整除则是平年
  • 但能被400整除又重新是闰年

1900年是平年而2000年是闰年，原因就在这里。写成代码需要三次除法，或者三次取余运算。后面会看到，这三次除法占了星期计算成本中很大的一块。

1.2 格里高利历为什么变成这个样子

这套规则并非随意定下的。季节转完一圈的实际长度比365天略长一点。四年加一天的儒略历把那一点估成了一天的四分之一，比实际略微慷慨了些。那点微小的超出累积数百年之后，春分在日历上被提前，复活节的基准也随之动摇。

1582年的改历做了两件事。为清除累积的误差，从日历上剜掉了十天；为防止再度累积，加入了100和400的规则。结果是400年当中的闰年不是100次而是97次，400年的总天数为146,097天。

这里发生了一件优雅的事。146,097除以7恰好等于20,871，整除。也就是说格里高利历的星期排布每400年完整重复一次。2026年的星期排布与2426年相同，与1626年也相同。这个性质是后面所有公式所倚靠的地基。

2. 最简单的办法 — 从基准日开始数

在造公式之前，有一个人们最先想到的办法。定下一个基准日，数出从那天起过了多少天，再看除以7的余数。

基准日按惯例是1970年1月1日，那天是星期四。把从基准日算起的天数记作rd，星期就是(rd + 4) % 7。把0设为星期日时星期四是4，所以加上4。

我们真的来数一遍到2026年8月28日的天数。1970年到2025年共56年，其间的闰年从1972年到2024年共14次。2000年落在400规则上是闰年，所以不被扣除。因此到2026年1月1日为止是56×365+14，即20,454天。8月28日是那一年的第240天，所以加上239得到rd = 20,693。再加4是20,697，除以7的余数是5。0是星期日，所以5是星期五。对了。

这个办法有三个问题。

  • 求天数这件事本身已经需要公式 — 要把上一段用手做的事搬进代码，闰年的三个条件和逐月累计天数原封不动地还是需要。除法并没有消失，只是挪到了前一个阶段
  • 用循环去数，就会随输入变慢 — 逐年判断闰年再累加的实现，离1970年越远耗时越久。你会得到一个求公元3000年的星期比求2026年更慢的程序
  • 基准日之前会塌掉 — C系语言的%让余数的符号跟随被除数

第三点尤其安静而危险。1900年3月1日是星期四，而这一天的rd是−25,508。(rd + 4) % 7变成−25,504除以7的余数，在C里那个值是−3。把它当作星期名称数组的下标，就会读到数组之外。要得到正确答案4，必须像((rd % 7) + 7 + 4) % 7这样再折一次。−25,508能被7整除，余数为0，于是(0 + 7 + 4) % 7 = 4，得出星期四。等于用了两次除法。

3. 换成公式 — Zeller同余式与Sakamoto方法

要去掉循环，就需要一个从年月日直接走到星期的闭式。这样的式子有两个，两者以彼此不同的方式吸收了同一份不规则。

3.1 Zeller同余式 — 把月份长度拉成一条直线

格里高利历用的Zeller同余式长成这样。q是日，m是月，K是年份的后两位，J是前两位。

h = (q + ⌊13(m+1)/5⌋ + K + ⌊K/4⌋ + ⌊J/4⌋ + 5J) mod 7
    (m: 3=3月 … 12=12月, 13=1月, 14=2月。1月和2月把年份减1)
    (h: 0=星期六, 1=星期日, 2=星期一, 3=星期二, 4=星期三, 5=星期四, 6=星期五)

这个式子里看起来最古怪的部分是把3月放在第一个月和13(m+1)/5。这两样其实是一体的。

把3月当作起点，长度会变的2月就去了一年的最末尾。闰日不再推动它后面的任何月份，于是从3月开始的各月长度除以7的余数变成3、2、3、2、3、3、2、3、2、3、3这样一个固定图案。而⌊13(m+1)/5⌋在m从3走到14时给出10、13、15、18、20、23、26、28、31、33、36、39。这个数列的差分正好是同一个图案。月份长度造出的台阶被一次除法画了出来，而剩下的K与J各项则是把闰年的三级规则搬了过来。

用真实日期来检验一下。

  • 2026-08-28 — q=28, m=8, K=26, J=20。⌊13×9/5⌋=23，⌊26/4⌋=6，⌊20/4⌋=5，5×20=100。和是28+23+26+6+5+100=188，而188 mod 7 = 6。h=6是星期五。对了
  • 2000-02-29 — 因为是2月，所以m=14，年份降到1999。q=29, K=99, J=19。⌊13×15/5⌋=39，⌊99/4⌋=24，⌊19/4⌋=4，5×19=95。和是29+39+99+24+4+95=290，而290 mod 7 = 3。h=3是星期二。2000年2月29日确实是星期二
  • 2026-01-01 — 因为是1月，所以m=13，年份是2025。q=1, K=25, J=20。⌊13×14/5⌋=36，⌊25/4⌋=6，⌊20/4⌋=5，5×20=100。和是1+36+25+6+5+100=173，而173 mod 7 = 5。h=5是星期四。对了

3.2 Sakamoto方法 — 换成十二格的同一个想法

如果说Zeller是用除法画出了月份的台阶，那么Sakamoto方法就是干脆把那道台阶写进一张十二格的表里。

t = [0, 3, 2, 5, 0, 3, 5, 1, 4, 6, 2, 4]
if m < 3: y = y − 1
w = (y + ⌊y/4⌋ − ⌊y/100⌋ + ⌊y/400⌋ + t[m−1] + d) mod 7
   (w: 0=星期日, 1=星期一, … 6=星期六)

用同样的日期确认一遍。2026年8月28日时m不小于3，所以y仍是2026，t[7]是1。⌊2026/4⌋=506，⌊2026/100⌋=20，⌊2026/400⌋=5。和是2026+506−20+5+1+28 = 2,546，而2,546 mod 7 = 5。w=5是星期五。2000年2月29日则把y降到1999并使用t[1]=3。1999+499−19+4+3+29 = 2,515，而2,515 mod 7 = 2，也就是星期二。1900年3月1日是1900+475−19+4+2+1 = 2,363，余数为4，星期四。三个日期全都与Zeller以及从基准日数出来的结果一致。

表里那十二个数字从哪儿来，是这个方法的核心。3月以后的值，是该月之前累计的天数除以7的余数再准确地减去1。8月之前累计的天数是212天，212 mod 7 = 2，而表里的值是1。10月之前是273天，余数为0，而表里是6，也就是−1。这个−1只做一件事。m不小于3时不把y降下来，于是⌊y/4⌋这一项会把那一年还没到来的2月29日先数进去，而表里的−1把那一格退回来。1月和2月因为降了y所以没有这个问题，于是t[0]=0与t[1]=3和累计天数原样吻合。

把两种方法与从基准日数天数并排放在一起，差别就清楚了。

维度从基准日数起Zeller同余式Sakamoto方法
处理月份不规则的位置造出天数的前一阶段⌊13(m+1)/5⌋这一项十二格常数表
需要的除法前一阶段的闰年判定 + 最后的mod 7向下取整除法3次 + mod 7向下取整除法3次 + mod 7
返回值的0指向哪一天随基准日的修正而不同星期六星期日
1月和2月的处理不适用挪到13月和14月把年份减1
是否需要天数的值必需不需要不需要
负数年份余数符号的问题中间项可能变成负数向下取整除法的前提被打破

由此得出一条判断标准。如果手里已经握着天数，那么Zeller或Sakamoto就是亏本买卖。这两个公式不从天数出发，而是付出三四次除法。反过来，如果只有年月日，那么它们比先造出天数再取余要短。哪一边划算，不由算法决定，而由自己的代码把日期握成什么形式来决定。

4. 十二格的表为什么能替代除法

Sakamoto的表看着小，里面却有想法。月份长度不是能靠计算推导出来的值，因为30天和31天的排布没有算术上的依据。想用计算去造出无法计算的东西，就得走⌊13(m+1)/5⌋这样的迂回路，而那条迂回路就是除法。

表把那次除法换成一次内存读取。十二个小整数，用字节数组是12字节，就算用32位整数也只有48字节。一条缓存行通常是64字节，所以整张表都装得进一条缓存行。

  • 只要表常驻在缓存里，查表就比除法便宜得多
  • 表一旦变大被挤出缓存，一次查表就成了主存访问，那笔开销会超过好几次除法
  • 表要求下标落在有效范围内 — 计算错了得到的不是错误答案而是内存错误
  • 表里的值必须可被检验 — 说不清数字从哪儿来的常数表既改不动也移植不了

4.1 分支与查表 — 表并非总是赢

用表还有另一个理由。那就是消掉分支。按月份摆一串if或者写个switch，CPU每次都得预测往哪边走。猜对了几乎没有代价，猜错了就要丢掉已经在执行的指令，重新填满流水线。那笔罚款远远超过好几次乘法。

所以输入越接近随机，查表就越有利。随机日期的月份无法预测，而无法预测的分支会一直猜错。反过来，如果代码里连续进来的都是同一个月的日期，预测几乎全中，分支那一边反而可能更快。

还有一件容易被忽略的事。表大了，局面就翻转。把400年的星期全部做成表，除法固然消失，但表会变成14万6千个条目。装不进缓存的表，每次查询都是一次内存等待，而在那段等待里CPU什么也做不了。这正是被称作优化的东西给出完全相反结果的地方。

5. 除法为什么昂贵

到目前为止所有办法最后都留下一个mod 7。在它之前还有三四个来自闰年规则的除法。之所以不断有人试图削减它们，是因为整数除法在日常算术运算里属于最昂贵的一类。

原因在于电路的性质。乘法可以一次生成全部部分积，再以树的形状层层相加。各个阶段互不等待，因而能深度流水线化，乘法器每个周期都能接收新的乘法，并在若干周期后按顺序把结果送出。除法正相反。它是从高位起逐位确定商的逐次过程，前一步的结果不出来就无法开始下一步。

  • 延迟很长 — 结果出来所需的时间是乘法的好几倍
  • 吞吐量也差 — 在许多实现里除法器并未完全流水线化，接连抛出除法时，后面的要等前面的做完
  • 时间随操作数而变 — 部分实现会因数值不同而周期数不同，于是混有除法的代码执行时间依赖于输入
  • 具体数值因微架构而异 — 延迟与吞吐量在不同CPU世代之间差别很大，无法用一个数字概括。需要某颗芯片的数值，就得去看那颗芯片的指令表

5.1 编译器对常数除法做了什么

所幸星期计算里的除法除数全是常数。7、4、100、400在编译时就已经知道。这种情况下编译器不会发出除法指令，而是改写成乘以一个倒数再移位的形式。

原理很简单。想把x除以7，乘上一个接近1/7的值即可，而整数世界里没有小数，于是先乘上2的幂，之后再用移位退回来。把232除以7并向上取整得到613,566,757，十六进制是0x24924925。把x乘上这个数再只取高32位，多数情况下就得到⌊x/7⌋。

用一个小例子确认。216=65,536除以7并向上取整是9,363。x=100时，100×9,363=936,300，除以65,536的商是14，而⌊100/7⌋=14，对得上。x=21时，21×9,363=196,623，商是3，而⌊21/7⌋=3，同样对得上。一次乘法加一次移位顶替了一次除法。只不过这个变换不是白来的。它有有效范围，超出范围就会安静地出错。

6. 7是梅森数 — 起因文章抓住的那一点

以上都是背景。作为起因的那篇文章所触碰的，是最后剩下的mod 7。

6.1 把七天一周搬到八天一周

7是23−1。这种形态的数被称作梅森数，由此引出一条性质。x除以7的余数，等于x加上⌊x/7⌋之后除以8的余数。

x mod 7  =  (x + ⌊x/7⌋) mod 8

证明只有一行。把x写成7q+r，则x+q = 8q+r，除以8之后8q消失，只剩下r。r小于7，所以能原样落进除以8的余数位上。

实际代入看看。用前面求出的20,697来验证，⌊20697/7⌋=2,956，20,697+2,956=23,653。23,653除以8的余数是5。而20,697 mod 7 同样是5。小数字也一样。x=13时⌊13/7⌋=1，13+1=14，14 mod 8 = 6，而13 mod 7 = 6。

这为什么划算？因为除以8的余数根本不是除法。只要一次保留低3位的掩码就够了。而剩下的⌊x/7⌋，正如上一节所见，可以换成乘法与移位。一次除法就变成了乘法、移位、加法、掩码这样一条短链。作为起因的那篇文章把这个变换称作Mul-Add-Shift，并给把7天周期搬进8天空间的映射取名为Nundinal Map。

6.2 魔数的有效范围 — 从哪里开始出错

先前搁下的问题在这里回来了。用向上取整造出的倒数比真实的1/7大上极小的一点。那点微小的超出会随着乘以x而放大，从某一点开始把商膨胀1。

用16位的例子可以直接验证。常数9,363在x不超过13,109时都准确。13,109×9,363=122,739,567，除以65,536的商是1,872，实际的⌊13109/7⌋也是1,872。可是到13,110第一次崩掉。13,110×9,363=122,748,930，商是1,873，而7×1,873=13,111，所以实际的商是1,872。答案大了1。既不抛异常也不报错，只是给出一个错误的星期。

在32位下结构相同，只是边界离得更远。作为起因的那篇文章写道，自己所用的向上取整常数只在32位输入的约80%上准确，并附上把输入推进有效区间的Range Compression。做法是给负侧的输入加上一个固定偏移，把分布挪进有效区间。这套技巧有一半不是用在速度上，而是用在确保正确性上。

  • 魔数不是算法，而是一份附带范围的契约 — 不把范围写下来，往后谁也修不动
  • 越界之后的失败是安静的 — 它不表现为崩溃，而表现为差了一天的星期
  • 有符号输入尤其危险 — 在负数区间里，向下取整与截断的差别会直接变成错误答案
  • 换位宽移植时，常数和范围都得重新算 — 在32位上正确的常数，在64位上未必最优

7. 可是这真的会成为瓶颈吗

诚实地回答：在大多数程序里并不会。

在屏幕上打印一个日期的代码里，星期计算是整体时间中看不见的碎片。它的前后有字符串解析，有时区规则查询，还有按照区域设置挑选星期名称的活儿。如果一次网页请求是数毫秒，那么省下一百次星期计算，连响应时间小数点后几位都推不动。

有意义的场合，条件很清楚。同一个计算重复非常多次，而周边成本已经被清理干净。

  • 海量日志解析 — 从数亿行时间戳里抽出日期字段，分进星期或日期分桶的流水线。每行几纳秒的差别会变成整体处理时间里的真实比例
  • 时序索引与分区 — 每次写入都把日期转成分区键的那条路径。它落在写入路径的热循环里
  • 日历规则的大批量重算 — 把重复日程展开数千次，或者按工作日基准大批重算到期日的批处理
  • 日期库自身的实现 — 它一旦慢下来，架在它上面的所有代码都会跟着慢
  • 又小又慢的硬件 — 在除法器很弱或根本没有的环境里，一次除法的相对比重与桌面机完全不同

共同点看得出来。它们全都是除了星期计算之外没什么别的事可做的循环。如果自己的代码里没有这样的循环，那么这套技巧属于该知道的东西，而不是该套用的东西。

8. 正确性先于性能

如果决定撇开标准库自己实现，那就得把得到的和失去的放在同一杆秤上。得到的是几次除法。可能失去的，清单却很长。

  • 越界输入 — 13月、2月30日、0日这样的值进来时，公式不会报错，而会给出一个看着像样的星期。校验成了调用方的活儿
  • 负数年份与公元前 — 公式里的⌊⌋是数学意义上的向下取整，而语言的整数除法大多是朝0截断。年份一变成负数，两者就分家
  • 儒略历的切换 — 把格里高利历的公式往1582年之前推，就会与真实历史记录里的日期对不上。切换的时点各国不同，于是「这个日期是按哪一种历写的」成了数据本身的属性
  • 溢出 — 中间项之和超出整数范围，结果就没有意义了。有符号整数的溢出在有些语言里是未定义行为
  • 星期编号约定不一致 — Zeller的0是星期六，Sakamoto的0是星期日，而ISO 8601的1是星期一。把不同约定的值混着用，就会差上好几天

顺序是这样的。先做对，再做到能证明它对，然后才做快。星期计算有一个便于守住这个顺序的性质。它每400年重复一次，所以可以把146,097天全部穷举检验。十几万条作为测试完全算不上大。把既有实现与新实现在整个400年区间里逐格比对，就能把「优化是否破坏了正确性」当作事实而不是猜测来知晓。

9. 不测就不知道

作为起因的那篇文章附了基准测试。怎么读那些数字，是本文最后的主题。先把条件说明白。下面是原文作者在自己环境里测得的相对时间，以Neri在2024年发表的方法为1.00倍。数字越小越快。

测量方法原文也交代了。把大量随机日期放进内存后跑，在延迟测量模式下用按位异或把结果喂给下一次计算，以阻止并行执行。每项试验重复5次取中位数，并减去循环本身的基线。输入范围是有符号32位的全部。

抽掉这些条件，只把「快四倍」搬走，那句话就成了错的。在同一张表里，同一个方法在0.25倍与0.55倍之间来回。这意味着CPU不同、编译器不同，结果就会变，而这不是某个实现的缺陷，只是这类测量本来就是如此。

微基准测试骗人的地方，大体是固定的那几处。

  • 输入分布 — 随机日期与已排序日期的分支预测结果完全不同。如果真实数据是排好序的，而你在用随机去测，那些数字就不是你的
  • 死代码消除 — 结果哪儿都不用，编译器就会把计算本身删掉。若跑出接近0的时间，那测到的不是优化而是删除
  • 内联 — 在微基准里被内联的函数，在真实代码里可能跨不过调用边界。反过来的情形也有
  • 把延迟和吞吐量混为一谈 — 下一次计算要等前一次结果的代码，和独立地一股脑灌进去的代码，性能特性并不相同。原文之所以分成两种模式来测，原因就在这里
  • 预热与频率 — 首次执行里混着缓存填充，而持续负载下时钟会降下来。这就是需要重复和中位数的理由
  • 周边被清空的环境 — 从数组里取出整数只求星期的循环，和解析字符串再造出对象的真实代码，瓶颈所在的位置并不相同

所以结论很简单。别人的基准测试是这项技巧存在的证据，而不是你的代码会变快的证据。如果这项计算真的是你的瓶颈，这个事实会由性能分析器先告诉你。分析器什么都没说，那就没有理由去改。

未能确认的内容

  • 原文的基准测试表把吞吐量与延迟分开列出。上表中的数值属于哪一边，未能确定
  • 原文表里还有上面搬过来之外的平台行，以及以纳秒为单位的绝对值，但只收录了能够一致读取的行
  • Neri在2024年发表的方法的原论文未能查证。本文对Neri方法只处理一件事实：它是起因文章所选定的比较基准
  • 主流编译器针对常数除法实际发出什么样的指令序列，会随版本与目标架构而不同，某个特定组合的输出未能确认
  • 当下广泛使用的各款CPU的整数除法延迟与吞吐量实测值，本文没有收录

总结

星期计算之所以难，原因不在算法而在日历。一个完美规则的7天周期，必须叠在365与366按4、100、400规则混合而成的体系之上。这份错位在代码里表现为除法。

那些公式是削减这份除法的不同办法。Zeller用一个⌊13(m+1)/5⌋画出了月份长度的台阶，Sakamoto把同一道台阶写进十二格的表里，并以「从表值减1」的方式把闰日的那一格退了回来。作为起因的那篇文章站得更靠后，用7是梅森数这一性质，把最后剩下的mod 7换成了对8的掩码。这三个阶段做的是同一件事。把能提前知道的提前算好，运行时只做剩下的那部分。

而最后留下的是判断。如果这项计算不是你的瓶颈，标准库就是正解。如果确实是瓶颈，那么在改动之前，先用400年的全量比对把正确性钉死，把常数的有效范围留成测试而不是注释，再用自己的输入分布亲手去测。把顺序颠倒过来，得到的是几个周期，失去的是差了一天的日期。这笔买卖大多不划算。
