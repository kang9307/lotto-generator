缘起 - 「Go编译器」这个说法遮住了什么

介绍文字通常都很短。写着「基于LLVM的Go编译器」，多数人就把它读成一件原样接收标准Go、只是吐出不同机器码的东西。这个读法只对了一半。

仓库给自己划定的范围是这样的：兼容Go 1.20及以后的源码，支持完整的Go 1.27语言语法，也接受cgo。在受支持的原生平台上完整支持标准库。只读到这里，子集这个词是错的。

可同一份文档在下一节又说了别的话。它的运行时与标准工具链不同。原生协程与操作系统线程一对一绑定，栈是固定大小的原生栈，默认回收器是保守式的Boehm系回收器。裸机目标则改用另一套保守式的标记清除回收器。语法全都接受，可是这些语法跑在上面的地板换了一块。

所以要用一句话概括这件东西，「标准Go的子集」不准确，「兼容标准Go」也不准确。准确的概括是语法与标准库全都要，运行时保证不一样。有些介绍只把支持平台写成Linux与macOS，而仓库文档同时列出了Windows的amd64与arm64，并分成MSVC与MinGW两条线，还罗列了多种WebAssembly目标和嵌入式开发板。摘要总是更新得更慢。

Go原本为什么这么做 - 自建后端的代价

Go团队在项目早期考察过LLVM，最后没有采用。官方常见问题里留下了一句话作为理由：他们判断它太大也太慢，达不到性能目标。这里说的性能不是生成代码的执行速度，而是编译器自身的速度。同一份文档在另一处把目标写得很明白：在一台机器上构建一个大型可执行文件，最多只应花几秒钟。

这一个选择连锁式地决定了这门语言的性格。用自建后端和自建链接器，工具链就小；默认静态链接，部署就简单；用两个环境变量切换目标操作系统与架构，交叉编译就便宜。代价则是：优化的深度赶不上积累了数十年的通用后端，支持的架构广度也没有那么宽。

同样这个选择，还决定了cgo的性格。在一个用自己的调用约定、自己的栈管理、自己的调度器的运行时里调用C函数，这件事就成了暂时走进别人的约定再走回来。走过去再走回来的这套手续，本身就是成本。

标准工具链选了什么换来了什么因此放弃了什么
自建的编译器后端大型可执行文件也在秒级完成构建通用后端积攒下来的优化深度
自建链接器与默认静态链接一个文件就结束的部署小体积二进制。运行时与类型信息总是被带上
用环境变量指定目标平台不需要C工具链的交叉编译一旦用上C库，这份简单立刻消失
可增长的协程栈开到几十万个也扛得住的并发无法把C代码直接跑在那种栈上
依赖精确指针图的回收器精确的存活判定与可预期的终结时机要碰回收器不认识的内存，就得靠约定

cgo为什么不是普通的函数调用

Go运行时源码里那个叫cgocall的文件，开头有一段很长的注释，把整条调用路径讲了一遍。这段注释就是「贵」这个字的实际内容。

Go代码调用C函数时，生成的代码会去调运行时的cgocall。cgocall首先调entersyscall，为的是不挡住其他协程和回收器。注释把这次调用的目的写明了：告诉调度器，在本线程跑进外部代码的这段时间里，需要再造一个线程来跑其他协程。

接着汇编层的asmcgocall离开当前协程栈，切到g0栈上。注释连理由都写了：g0栈被假定为操作系统分配的栈，所以把C编译器生成的代码放上去是安全的。反过来说就是，C代码不能就这么跑在协程栈上。一个会按需增长的栈，不是执行C函数的地方。

C函数结束后回到原来的协程栈，cgocall调用exitsyscall。注释用一句话交代了这个函数的性质：它会一直阻塞，直到本线程可以在不违反并行上限的前提下跑Go代码。也就是说，返回不是立刻发生的，而是一道等待调度器许可的手续。

如果C那边反过来调Go函数，这道楼梯还要反方向再走一遍。适配器把C的调用约定换成Go的调用约定，再从g0栈切回原来的协程栈，然后在那里再一次等待上限。一次回调，往返切换就叠成了两层。

阶段运行时做的事为什么必须做
进入声明标记为进入系统调用好在本线程被占住期间安排另一个线程去跑协程
栈切换从协程栈切到操作系统栈因为C代码不能跑在可增长的栈上
真正的调用从帧里取出参数并调用C函数两边调用约定不同，需要有人居中转接
返回切换切回原来的协程栈Go代码只能在自己的栈上继续
退出等待阻塞到并行上限允许为止为了维持并发执行数量的账目
如果有回调同一道楼梯反方向再走一遍从C进入Go走的是同一条边界

把这张表摆开就能看清，「调用很贵」讲的不是一个微秒级的固定延迟。调度器的账目和栈的所有权，每次调用都要易手一回。所以把一大块计算一次性交出去几乎不受影响，而密集地调用小函数，那就不是调参问题，而是结构问题。

指针传递规则 - 守住它的不是编译器而是约定

比成本更危险的是规则。cgo文档把传指针的条件钉死了。要把Go指针传给C，该指针所指向的内存里不能含有指向未固定内存的Go指针。而且C代码不得在调用返回之后仍保留Go指针的副本，唯一的例外是那块内存被固定装置按住的情形。

作为参数传过去的Go指针，只在调用持续期间被隐式固定。调用一结束，这份保证也就结束了。字符串更简单：C.CString会在C堆上做一份副本，文档写明安排释放是调用方的责任。

// 标准Go的cgo - 跨越边界的值会被复制，释放的责任留在调用方
cs := C.CString(s)                  // 在C堆上做一份副本
defer C.free(unsafe.Pointer(cs))    // 少了这一行就会一直漏
n := C.strlen(cs)                   // 从这里开始就是C的内存了

如果C在调用结束之后还得握着Go内存，那就要用固定装置。标准库里的Pinner会把对象按住，让回收器既不能移动它也不能回收它。如果被固定的对象又指向别的Go对象，而C还要顺着追下去，那些对象也必须单独固定。

// 当C必须在调用结束后继续持有Go指针时
var pinner runtime.Pinner
pinner.Pin(p)            // 按住它，让回收器既不能移动也不能回收
defer pinner.Unpin()     // 只有在解开之前，C那边的引用才是有效的

这里值得盯住的是规则的执行者。这些规则类型检查器不会替你抓。编译照样通过，违反之后的后果也不会立刻显现。只有当回收器真的去移动或回收那块内存时，症状才出现。这是一类要等到负载升高、或者堆长大之后才第一次爆出来的缺陷。

  • 能传什么的条件 — 所指向的内存里不能有未固定的Go指针。结构体里装着切片或字符串，就会撞上这个条件
  • 禁止保留 — C要在调用之后继续持有Go指针就必须固定，而固定一解开，那个引用立刻失去依据
  • 释放的归属 — 在C堆上造出来的，就按C的约定释放。Go的回收器不统计那块内存，所以泄漏是悄悄堆起来的

同一个问题能不能在语言层面收窄，是Rust FFI 边界上中断的安全保证那篇处理的轴。那边走的是把边界本身缩小的路子，而这里要看的是为了消掉边界干脆换掉地板的路子。

把运行时整个换掉这个选择

第三节那道楼梯，全都建立在一个前提上：协程栈和调度器不属于C。把这个前提抹掉，楼梯也就没了。基于LLVM的实现选的正是这条路。

仓库文档的措辞很简洁：原生协程与操作系统线程一对一绑定，栈是固定大小的原生栈，因此直接调用C时既不需要Go到C的栈切换，也不需要调度器切换。绑定方式也不经过包装层，一条Go声明直接绑到C ABI的符号上。

import _ "unsafe" // 要使用 go:linkname 指令就需要它

//go:linkname Sqrt C.sqrt
func Sqrt(x float64) float64

这条指令本身在标准编译器里也有。官方文档这样描述它的性质：它指定Go变量或函数声明所使用的目标文件符号，让两个Go符号指向同一个符号，并且只在导入了unsafe的文件里才启用。同一页还明确写着，这条指令可以绕开对未导出声明的常规封装，甚至绕开类型安全。这份便利究竟是什么做成的，文档自己就说了。

改掉的不只是调用路径。默认回收器换成了保守式：不依赖精确的指针图，而是扫描栈与寄存器，把所有长得像指针的值都当作存活。正因为这个选择，C代码造出来的内存和Go代码造出来的内存才好放进同一个堆里处理。而它的代价，就是下一节那份清单。

在「完整支持」与「不在兼容目标内」之间

有意思的是，这个项目把兼容性当成清单而不是散文来管理。它原样跑标准发行版的编译器测试集，把没通过的条目分进两个文件。一个装还没对齐的，另一个装本来就不打算对齐的。

还没对齐的那一侧有十一条。其中六条是解析器发出的错误信息措辞与标准不同：包声明写坏、名字写坏、字节序标记之类的情形下，诊断文本长得不一样。剩下五条与堆采样剖析有关，其中两条把一个尚未合并的提案编号写成了理由。

不打算对齐的那一侧有一百三十六条。这一侧才是真正的边界线。其中一百一十条的理由以同一句话收尾：支持那种工具链特有的行为不属于兼容目标。其余的理由更具体：因为用保守式回收器，所以不去对齐精确存活判定与终结时机的，大约十八条；因为不使用写屏障，所以不复现与之相关诊断的，有若干条；还有一些写着因为用固定大小的原生栈，所以不复现可增长栈的行为。

轴声明的范围实际分岔的地方
语言语法完整的Go 1.27语法解析器诊断措辞有六条不同。不是语法本身，是错误信息
标准库在受支持的原生平台上完整支持项目自己写明，其他目标上可能缺少部分系统服务或实现特有行为
协程能用与操作系统线程一对一。数量往上堆时的成本与标准不同
栈能用固定大小。以可增长栈为前提的行为被归入不兼容目标
垃圾回收默认提供保守式。精确存活判定与终结时机与标准不同
构建工具用法与标准命令相仿整套LLVM 22系列加上多个系统库都是前置条件
  • 语法兼容与运行时兼容是两个轴。同一份源码能编译，与同一份源码在同一时刻给出同样的观测，是两回事
  • 依赖终结器与弱引用的代码是第一类风险。在保守式回收器下，回收时机可能与标准错开
  • 会开出极大量协程的设计是第二类风险。一对一映射之下，那个数量就是线程数量

改用LLVM之后会变什么

得到的一侧

换上通用后端，那个后端积累下来的东西就整套跟过来：优化通道集合、链接期优化、各架构的代码生成器，以及架在它上面的调试器与分析工具。目标的扩张也是同样的来路。这个实现之所以能吐出好几种WebAssembly，还能把嵌入式开发板纳入目标，是因为那个后端本来就认识这些架构。

直接按C ABI对接这个性质也出自同一处。同一个后端也编译C，于是调用约定与类型表示从一开始就用同一种语言表达出来。不需要包装层的原因就在这里。

付出的一侧

后端大，意味着工具链大。LLVM官方文档把所需磁盘写得很直白：只构建LLVM大约要1到3GB，把LLVM与Clang一起完整构建大约要15到20GB。这个实现把LLVM 22系列的编译器、链接器、调试器全部列为前置条件，再往上加保守式回收器库、外部函数接口库、加密库与压缩库。

这份清单本身就是构建可复现性的账单。标准Go的交叉编译之所以便宜，是因为不需要目标平台的C工具链。边界一开，这个前提就塌了。开发机、持续集成机、部署目标三处的系统库版本号，全都会进入结果。

把LLVM换作Go后端的尝试，也不是这个项目才有的。Go官方常见问题里同时提到了接在GCC后端上的前端，以及使用同一前端的实验性LLVM后端。用同样方式把TypeScript往下降的尝试，在Perry - 将TypeScript直接编译为LLVM机器码的原生编译器里讲过，而那篇文章里的一个陷阱在这里同样重演：更好的后端并不自动意味着更快的结果。语言的语义能不能顺利降到那个后端上，才是先决问题。

一个自测数字 - WebAssembly的文件体积

这个项目在一个专门的仓库里持续跑体积对比，并把结果公开。条件是随数字一起给出的，所以值得引用。只是做度量的主体就是项目自己，这一点必须原样带进阅读里。

条件是这样的：执行编号403，生成时刻为2026-09-07的07:11 UTC，持续集成执行机是Linux x64的Ubuntu 24镜像，目标是WebAssembly系统接口。使用Go 1.26.2、LLVM 22、TinyGo 0.41.1，样本是十个应用程序，指标是产物文件的总字节数。构建选项也一并公开：Go一侧加了路径裁剪与符号和调试信息剥离，TinyGo一侧加了体积优先优化与去调试信息，这个实现一侧则把体积优先优化与链接期优化、全局死代码消除组合起来。

配置对标准Go对TinyGo该怎么读
不做链接期优化0.66倍11.2倍默认设置就已经小于标准，可与小型编译器还差着一个数量级
死代码剔除0.47倍8.0倍一个选项又削掉了三成体积
链接期优化，全局消除关0.44倍7.5倍只开链接期优化，与上一行差别不大
链接期优化，全局消除开0.34倍5.8倍最小的配置。即便如此仍是小型编译器的五倍以上

这张表里该读出来的不是倍数本身，而是倍数的方向有两个这个事实。同一件产物，按一把尺子量是三分之一，按另一把量就接近六倍。看单个案例更清楚：样本里的Base64转换器，标准Go的产物约228万字节，小型编译器的产物约9万7千字节，最小配置的产物约60万字节。取决于跟哪一边比，同一个数字既能是胜利也能是失败。只把倍数摘出来的句子之所以危险，原因就在这里。

还有，这张表量的是文件体积而不是执行速度。体积与速度是两个轴，一个按体积优先调过的构建，在速度轴上未必占优。

跨越边界时真正会坏掉的东西

这里是本文的中心。无论从哪门语言跨到哪门语言，边界上会坏掉的东西，清单大体一致。要紧的是每一项会以什么症状出现。知道症状，才有可能把原因往那个方向去怀疑。

会坏的东西为什么会坏出现的症状先看哪里
内存所有权分配的一方与释放的一方遵循不同约定长时间运行后常驻内存单调上涨。重启就消失每一个跨边界的字符串或缓冲区是否都有配对的释放
回收器看不见的指针唯一存活的引用落在回收器不扫描的地方只在高负载时崩。栈回溯指向已被回收的对象线程局部存储、C堆、交给回调的上下文指针
对象被搬动回收器把对象挪走了，而C还握着旧地址断续出现错值，堆长大之后才复现调用结束后仍存活的指针有没有被固定住
异常与panic一边的栈展开约定在另一边并不存在不是返回错误而是进程整个终止，日志也留不下跨边界的回调里panic会不会漏出去
线程模型一边给线程附加了条件同一段代码在这个协程上能跑，在另一个协程上就死加锁与解锁是不是在同一个线程上配对
错误约定用返回值、全局变量还是异常来报告，两边不一致失败被读成成功。缺陷要很久之后才显形C函数报告错误的方式，以及读取那个值的时机
类型表示同名的类型在宽度与布局上不一样结构体字段错位。32位与64位结果分岔整数宽度、数组作参数与作字段的差别、函数指针
构建可复现性系统库与工具的版本号进入了结果本机能过，持续集成上过不去前置条件清单里有没有把版本号钉死

第二行不是抽象的警告，它在这个实现自己的文档里就是一次真实事故。延迟调用链的表头只以裸指针放在线程局部存储里，保守式回收器看不见它。在压入一百万次延迟调用的压力测试中，回收器把那些节点回收掉了，结果代码就死在延迟调用里面。诊断写得很干脆：那是根注册的遗漏，而不是逻辑上的损坏。修法也跟着诊断走，改成从回收器认得的根上去分配那份状态。

第七行同样有具体的文档依据。这个实现的类型对应表把C函数指针作为参数出现和作为结构体字段出现分开处理：在参数位置上按Go函数类型接收，在结构体字段里则按普通指针接收。因为C的函数指针只是一个函数的地址，而Go的函数值可能是闭包。数组也一样，在参数位置降级为指针，只有在结构体内部才保持数组形态。对于Windows回调，文档出于同样理由明确写道：要传直接的函数引用而不是会捕获状态的闭包，状态请用单独的上下文指针传递。

调用Python意味着 - 一把锁跟着过来

调用C库和调用Python库难度不一样。后者等于把一整台叫作解释器的状态机搬进进程里。那台状态机有自己的约定。

Python官方C接口文档里的句子简短而断然：除非是自由线程构建，否则解释器一般不是线程安全的，因此存在全局解释器锁，而且只有持有这把锁的线程才能操作Python对象或调用Python的C接口。从外部线程进来时必须成对地获取和释放状态，文档明确写着每一次获取调用都必须由同一线程上的一次释放调用来配对。

// 直接从Go代码里调用Python库
x := math.Sqrt(py.Float(2))       // 交给Python的math.sqrt
std.Print(py.Str("sqrt(2) ="), x) // 用Python的print打印

表面上看是两行函数调用。可这两行要成立，进程里的解释器必须已经初始化，执行这段代码的线程必须持有那把锁，传过去的值必须已经被造成遵循引用计数约定的Python对象。看不见的前提叠了三层。

看这个条件与Go的执行模型如何相遇，就能猜到一对一线程映射这个选择是怎么来的。标准Go里协程并不钉在某个线程上，调度器会把它挪走。协程握着锁却被挪到另一个线程，约定就破了。一个协程固定在一个线程上，这个问题就从结构上消失了。

自由线程构建也不是万能药。官方文档写明，即便在那种构建下把线程状态解绑的手续依然是必要的，因为解释器需要周期性地暂停所有线程，才能拿到对Python对象的一致视图。文档举的例子就是跑回收器的那段时间。

  • 并行度的上限由别人决定。Go这边协程开得再多，触碰Python对象的那段区间都要围着一把锁排队
  • 加锁约定编译器不检查。获取与释放配对错位，编译照样通过
  • 第三方库要另行安装。发布物里必须带上解释器和它的那些包，它们的版本号也会进入结果

这个选择在什么时候是对的

当既有的库事实上是唯一实现时

判断多半能压缩成一个问题：有没有一个能替代那个库的纯语言实现。没有的话，边界成本就不是选项而是前提。数值计算里的某个核心算子、打磨了很多年的编解码器、特定硬件的官方驱动、因监管要求而必须使用的密码模块，都属于这一类。此时争论的重点就不再是「用不用」，而是「把边界放在几个地方」。

缩小边界的办法大体一致：把调用点收拢到一处，在那里粗粒度地跨一次。与其密集调用小函数，不如成批交出去。第三节那道楼梯是每次调用都要附上的结构，所以减少调用次数本身就是在减少成本。

当存在纯语言实现时

有纯语言实现的话，账就换了一种算法。要比的不是性能，而是运维总成本。边界一开，系统库会跟进发布物，交叉编译会变难，故障排查会需要两门语言的知识，标准工具链的性能剖析器与竞态检测器只能看见一半。

情形开边界的一侧纯语言实现的一侧决定胜负的因素
根本没有替代实现事实上唯一的选择不适用边界能收拢到几处
有纯语言实现但慢只有单次工作量大时才划算通常选这一侧一次交出去的工作量。太小的话切换成本会吃掉收益
纯语言实现功能不足缺的功能正是核心时缺的部分可以不用的话那个功能位于需求的中心还是边缘
部署目标很多样不利有利能不能为每个目标备齐C工具链
会开出极大量协程换运行时的路子不利有利并发规模换算成线程数之后还扛不扛得住
运维团队只懂一门语言故障排查成本会变高有利凌晨挂掉时有没有人能追出原因

最后一行在实务中最常把决定翻过来。开了边界的系统出故障，只靠一门语言的知识很难追到底。Go与另一门语言之间这个判断该怎么立，在Go迁移到Rust完全指南2026里从另一个角度讲过；把语言选择本身换算成验证成本的那条轴，则在降低 AI 生成代码验证成本的语言特性里。

怎么读成熟度 - 别看星标数

星标数不会告诉你的事

公开仓库的星标数是关注度的指标，不是可信度的指标。这个仓库在查询时点显示星标749、分叉50、未解决议题151。它建于2023年12月，查询当天仍在收到提交。光靠这些数字，引入决策所需要的东西一个也得不到。

该看的是另外四样：发布标签的轨迹、未解决议题的种类、兼容性声明的形态、项目对标准符合范围的自我陈述。

真正该看的四样

先看发布轨迹。第一个标签是2024年4月，正式版本号1.0.0落在2026年8月24日。在正式版之前的一周多时间里集中放出了五个预发布版，之后又在8月29日和9月6日出了两个维护版。发布总数是四十九个。走到正式版本号花了两年四个月，而且紧接着就有两次维护，这个事实比星标数说明得多。

指标查询值该从中读出什么
抵达正式版本号1.0.0在2026-08-24，最新为2026-09-06的1.0.2正式版之后两周内出了两个维护版。仍处在早期稳定化区间
距第一个发布的时间自2024-04-21起共49个发布有稳定的发布节奏。是项目仍在被维护的信号
未解决议题151条种类比绝对数量重要。这是引入前该拿自己的使用场景去检索的地方
兼容性声明未达标11条、不在目标内136条，均附理由并落成文件声明不是一句话而是可核对的清单。这是很强的成熟度信号
标准符合范围语法与标准库全都要，运行时语义不同同一份源码能编译，并不意味着能给出同样的观测
前置条件整套LLVM 22系列加上多个系统库引入成本里相当一部分花在装工具和钉版本号上
许可证Apache-2.0带专利条款的宽松型。企业引入时法务审查负担相对轻

第四行是这张表里最值钱的一行。多数项目把兼容性写成散文。「基本兼容」这句话没法验证，而带理由的例外清单可以读、可以追问。意思是你能直接去核对：自己代码所依赖的行为，有没有落在那份清单里。语言项目被打开究竟改变了什么、又没改变什么，在Mojo 编译器开源里是从治理的轴讲的。这里要看的轴是兼容性声明的可验证性。

引入之前必须答的五个问题

挑工具这件事，多半就是挑问题。下面五个有了答案，决定自然就跟着出来。

  1. 要跨几次边界。调用次数少、单次交出去的工作量大，那标准cgo就够用。只有当密集调用在结构上无法避免时，换运行时才成为议题
  2. 要开多少协程。一对一映射之下，并发规模就是线程数。以几万个为前提的设计，不适合走这条路
  3. 有没有依赖终结器与回收时机的代码。保守式回收器会让那个时机与标准不同。把资源释放交给终结器的代码，是第一批要检查的对象
  4. 部署目标有几种。能不能为每个目标备齐LLVM系列工具与系统库并把版本号钉死，才是实际引入成本的大头
  5. 凌晨挂掉时谁来看。开了边界的系统出故障，要求两门语言的知识。组织里有没有这个人，比技术判断更靠前

值得注意的是，这五个问题没有一个在问性能。在开边界这个决定里，性能通常是答案早就定下的那条轴，真正把项目拖垮的是其余四个。给编译型语言加上交互式执行时也会出现同一类取舍，那条轴整理在给编译型语言加上交互式执行意味着什么里。

未能确认的部分

  • 速度对比未能确认。公开的持续集成度量是WebAssembly产物文件的字节数，没有找到以同样形式公开的执行时间对比。第八节的倍数不能挪去当速度读
  • 原生目标的体积表没能打开。结果文件用单独的摘要与表格形式指向原生条目，但那部分内容没有放进本文的依据里
  • C调用路径实际节省了多少，未能用数字确认。没有栈与调度器切换是设计层面的陈述，没有拿到在同等条件下与标准cgo比较单次调用延迟的公开数值
  • 第三方复现未能确认。第八节的数值全部出自项目自己跑的度量，没有找到独立的度量报告
  • 151条未解决议题的构成未能确认。没有把缺陷、功能请求与文档条目的比例分开，所以这个数字不能当质量指标来读
  • 贡献者数量的准确总计未能确认。清单第一页显示19人，但没有把其余页面加总
  • 在Python自由线程构建下这个实现如何表现，未能确认。仓库文档要求的只是3.12以上这个条件，关于无锁构建的单独说明不在查阅范围之内
