스크립트가 어제까지 돌았는데 오늘 No such file or directory 를 뱉는다. 파일은 그대로 있고, 첫 줄도 #!/bin/bash 그대로다. 편집기로 열어 봐도 이상한 데가 없다. 이럴 때 의심할 자리가 하나 있다. 파일 맨 앞의 세 바이트다.

UTF-8 BOM 은 EF BB BF 다. 화면에는 아무것도 그려지지 않고, 편집기 대부분은 커서를 그 앞에 놓지도 못하며, diff 는 두 줄이 다르다고 말하면서 화면에는 똑같은 글자를 보여 준다. 이 글은 그 세 바이트가 어디서 무엇을 깨뜨리는지를 실제로 만들어 돌려 본 기록이다. 개념 설명보다 출력이 많다.

BOM 은 원래 바이트 순서 표시였다

이름이 답이다. Byte Order Mark, 바이트 순서 표시. 이것은 UTF-16 이나 UTF-32 처럼 여러 바이트를 묶어 한 단위로 읽는 인코딩을 위해 만들어졌다. 그런 인코딩에서는 같은 값이라도 큰 자리부터 저장하느냐 작은 자리부터 저장하느냐에 따라 바이트가 뒤집힌다. 그래서 파일 맨 앞에 U+FEFF 를 하나 놓고, 읽는 쪽이 그 두 바이트가 FE FF 로 오는지 FF FE 로 오는지 보고 순서를 판단하게 했다.

유니코드 컨소시엄의 FAQ 는 이 자리를 분명히 적어 둔다. BOM 은 데이터 스트림 맨 앞의 U+FEFF 로, 바이트 순서와 인코딩 형태를 정의하는 서명으로 쓰인다는 것이다. 그리고 바로 이어서 UTF-8 을 따로 떼어 설명한다. UTF-8 은 바이트 지향이라 그 문제 자체가 없다. 항상 같은 바이트 순서를 갖기 때문이다. 그래서 UTF-8 에서 맨 앞 BOM 은 순서를 알리는 것이 아니라, 표시가 없는 텍스트 파일이 UTF-8 이라는 것을 알리는 서명 용도로만 쓰인다고 적혀 있다. 같은 문서가 곧바로 주의를 하나 붙인다. UTF-8 데이터를 받는 쪽 중에는 BOM 을 예상하지 않는 곳이 있다는 것이다.

그러면 왜 이렇게 자주 보이는가. 윈도우 계열 도구의 오래된 관행 때문이다. 코드 페이지가 지역마다 다르던 시절, 확장자만으로는 이 텍스트가 UTF-8 인지 지역 코드 페이지인지 알 방법이 없었다. 세 바이트를 앞에 붙이면 적어도 자기네 도구끼리는 구분이 됐다. 메모장이 그렇게 저장했고, PowerShell 의 -Encoding utf8 도 오랫동안 그 뜻이었다. 리눅스 쪽은 처음부터 UTF-8 을 기본으로 잡고 갔으므로 이 서명이 필요 없었다. 두 관행이 한 저장소에서 만나면 그때부터 사고가 난다.

  • UTF-16 / UTF-32 — 바이트 순서 문제가 실재한다. BOM 이 원래 하려던 일이 여기 있다
  • UTF-8 — 순서 문제가 없다. 붙은 BOM 은 순서 표시가 아니라 그냥 서명이다
  • 서명이 필요한 상황 — 인코딩을 알려 줄 다른 경로가 없을 때. 파일 확장자와 로컬 코드 페이지만으로 판단해야 하는 도구들
  • 서명이 방해가 되는 상황 — 첫 바이트가 곧 문법인 형식. 셰뱅, JSON, XML 선언, CSV 헤더가 전부 여기 해당한다

보이지 않는다는 말의 실제 의미

같은 내용의 파일을 둘 만들고 한쪽에만 BOM 을 붙여서 나란히 놓아 보면, 이 문제가 왜 오래 안 잡히는지가 바로 보인다. cat 은 두 파일을 똑같이 보여 준다. 크기만 3바이트 차이가 난다.

$ printf 'hello\n'              > plain.txt
$ printf '\xef\xbb\xbfhello\n'  > bom.txt

$ cat plain.txt; cat bom.txt
hello
hello                      # 두 줄이 똑같아 보인다

$ ls -l plain.txt bom.txt
-rw-r--r-- 1 user user 6 Sep  1 10:25 plain.txt
-rw-r--r-- 1 user user 9 Sep  1 10:25 bom.txt

$ xxd plain.txt
00000000: 6865 6c6c 6f0a                           hello.
$ xxd bom.txt
00000000: efbb bf68 656c 6c6f 0a                   ...hello.

$ od -c bom.txt
0000000 357 273 277   h   e   l   l   o  \n
0000011

$ file plain.txt bom.txt
plain.txt: ASCII text
bom.txt:   Unicode text, UTF-8 (with BOM) text

xxd 의 오른쪽 칸에 찍힌 점 세 개가 ef bb bf 다. file 은 아예 「with BOM」 이라고 적어 준다. 여기까지는 도구가 친절하다. 문제는 비교 도구다.

$ diff plain.txt bom.txt
1c1
< hello
---
> hello                    # 화면상 같은 글자인데 다르다고 나온다
$ echo $?
1

$ cmp plain.txt bom.txt
plain.txt bom.txt differ: char 1, line 1

$ wc -c < bom.txt
9
$ LC_ALL=en_US.UTF-8 wc -m < bom.txt
7                          # 바이트 9, 문자 7 (BOM 1 + hello 5 + 개행 1)

diff 는 정확히 일하고 있다. 두 줄이 다르다고 말했고 실제로 다르다. 다만 사람에게 보여 준 화면에는 그 차이가 없다. 코드 리뷰에서 「왜 이 줄이 바뀐 걸로 나오지」 하고 넘어가는 변경이 이렇게 생긴다.

셰뱅이 셰뱅이 아니게 된다

실행 파일의 첫 두 바이트가 #! 이면 커널이 그 뒤를 인터프리터 경로로 읽는다. 그 두 바이트가 파일의 첫 바이트여야 한다는 것이 조건이다. 앞에 세 바이트가 끼면 그 줄은 더 이상 셰뱅이 아니라 그냥 첫 번째 명령줄이 된다.

$ printf '#!/bin/bash\necho ok\n'              > ok.sh
$ printf '\xef\xbb\xbf#!/bin/bash\necho ok\n'  > bomshebang.sh
$ chmod +x ok.sh bomshebang.sh

$ ./ok.sh
ok

$ ./bomshebang.sh
./bomshebang.sh: line 1: #!/bin/bash: No such file or directory
ok
                           # 위 메시지의 #! 앞에 보이지 않는 BOM 이 그대로 찍혀 있다

$ head -c 16 bomshebang.sh | xxd
00000000: efbb bf23 212f 6269 6e2f 6261 7368 0a65  ...#!/bin/bash.e

이 출력에는 읽어야 할 대목이 두 개 있다. 하나는 에러 메시지가 파일 이름이 아니라 셰뱅 줄 자체를 가리킨다는 것이다. bash 가 지워졌나 싶어 which bash 를 쳐 보게 되는데, bash 는 멀쩡히 있다. 실행되지 않은 것은 <BOM>#!/bin/bash 라는 이름의 명령이다.

다른 하나는 그 다음 줄에 ok 가 찍혔다는 것이다. 이 환경(MSYS2 의 bash 5.2.37)에서는 셰뱅 해석에 실패한 뒤 셸이 스스로 나머지를 읽어 실행했다. 즉 스크립트가 죽지 않고 첫 줄만 실패한 채 계속 간다. 이쪽이 더 나쁘다. 종료 코드가 0 이라 CI 도 통과한다.

$ printf '\xef\xbb\xbf#!/bin/bash\nset -e\necho reached\n' > strict.sh
$ bash strict.sh
strict.sh: line 1: #!/bin/bash: No such file or directory
reached
$ echo $?
0                          # set -e 를 걸어 두어도 첫 줄 실패는 잡히지 않는다

set -e 는 그 줄 이후부터 적용되므로 1번 줄의 실패에는 손이 닿지 않는다. 이 조합 때문에 「빌드는 성공했는데 결과물이 이상하다」는 형태로 며칠 뒤에 발견되는 경우가 생긴다.

설정 파일에서는 첫 줄 하나만 사라진다

셸이 읽어들이는 것은 스크립트만이 아니다. .env 처럼 KEY=value 를 나열하고 source 로 불러오는 파일도 같은 규칙을 탄다. 그리고 여기서 나타나는 증상은 훨씬 조용하다. 딱 첫 줄 하나만 안 들어온다.

$ printf 'API_HOST=example.internal\nAPI_PORT=8080\n'             > plain.env
$ printf '\xef\xbb\xbfAPI_HOST=example.internal\nAPI_PORT=8080\n' > bom.env

$ bash -c '. ./plain.env; echo "HOST=[$API_HOST] PORT=[$API_PORT]"'
HOST=[example.internal] PORT=[8080]

$ bash -c '. ./bom.env; echo "HOST=[$API_HOST] PORT=[$API_PORT]"'
./bom.env: line 1: API_HOST=example.internal: command not found
HOST=[] PORT=[8080]
$ echo $?
0                          # 두 번째 줄부터는 정상이다. 첫 줄만 비어 있다

API_PORT 는 제대로 들어왔고 API_HOST 만 빈 문자열이다. 파일에는 분명히 값이 적혀 있는데 변수만 비어 있으니, 보통은 오타를 찾거나 로딩 순서를 의심하며 시간을 쓴다. command not found 한 줄이 로그 어딘가에 흘러갔더라도, 그 줄의 왼쪽 끝에 보이지 않는 문자가 있다는 사실은 화면으로 알 수 없다.

같은 일이 YAML 에서도 일어난다. 직접 파싱하는 코드라면 첫 키의 이름이 바뀐다.

$ printf '\xef\xbb\xbfname: demo\nport: 8080\n' > app.yaml
$ node -e "
const s = require('fs').readFileSync('app.yaml', 'utf8');
const m = {};
for (const line of s.split(/\r?\n/)) {
  if (!line) continue;
  const i = line.indexOf(':');
  m[line.slice(0, i)] = line.slice(i + 1).trim();
}
console.log('keys :', JSON.stringify(Object.keys(m)));
console.log('name :', m.name);
console.log('port :', m.port);
"
keys : ["name","port"]     # 첫 키 앞에 U+FEFF 가 붙어 있다
name : undefined
port : 8080

키 목록을 찍어 봐도 ["name","port"] 로 보인다. 그런데 m.name 은 undefined 다. 눈으로 보는 것과 프로그램이 비교하는 것이 갈리는 전형적인 자리다.

JSON - 표준은 붙이지 말라고 한다

JSON 은 이 문제에 대해 표준 문서에 답이 적혀 있는 드문 경우다. RFC 8259 의 8.1 절, 문자 인코딩 항목은 두 문장을 나란히 둔다. 하나는 강제다. 네트워크로 전송하는 JSON 텍스트 앞에 BOM 을 붙여서는 안 된다(MUST NOT). 다른 하나는 허용이다. 상호운용을 위해 JSON 텍스트를 파싱하는 구현은 BOM 이 있을 때 그것을 오류로 취급하는 대신 무시해도 된다(MAY).

이 비대칭이 현장의 혼란을 그대로 설명한다. 붙이는 쪽은 하면 안 되고, 걷어내는 쪽은 해도 되고 안 해도 된다. 즉 어떤 파서는 통과시키고 어떤 파서는 던진다. 같은 파일이 도구를 바꾸면 다르게 동작하는 이유가 여기 있다. Node.js v22.16.0 에서는 한 런타임 안에서도 갈린다.

// jsontest.js
const fs = require('fs');
for (const f of ['plain.json', 'bom.json']) {
  const raw = fs.readFileSync(f, 'utf8');
  console.log(f, 'first char U+' +
    raw.codePointAt(0).toString(16).toUpperCase().padStart(4, '0'));
  try   { console.log('  OK', JSON.stringify(JSON.parse(raw))); }
  catch (e) { console.log('  ' + e.name + ': ' + e.message); }
}

$ node jsontest.js
plain.json first char U+007B
  OK {"name":"demo","port":8080}
bom.json first char U+FEFF
  SyntaxError: Unexpected token '', "{"name":""... is not valid JSON

$ node -e "console.log(JSON.stringify(require('./bom.json')))"
{"name":"demo","port":8080}
                           # 같은 파일인데 require 로는 통과한다

JSON.parse 는 던지고 require 는 통과한다. 모듈 로더 쪽이 BOM 을 걷어내고 넘기기 때문이다. 그래서 「로컬에서는 되는데 배포하면 안 된다」 같은 형태로 나타나는데, 실제로 갈린 것은 환경이 아니라 그 파일을 읽는 코드 한 줄이다. require('./config.json') 로 읽던 것을 JSON.parse(fs.readFileSync(...)) 로 바꾸는 순간 터진다.

덧붙일 것이 하나 있다. SyntaxError 메시지에 찍힌 Unexpected token 뒤의 따옴표 안이 비어 보인다. 거기 U+FEFF 가 들어 있다. 에러 메시지조차 원인을 보여 주지 못한다.

CSV 의 역설 - 여기서는 BOM 이 해법이다

여기까지 읽으면 BOM 을 무조건 없애는 것이 답처럼 보인다. 그런데 정확히 반대인 자리가 하나 있다. 엑셀로 여는 CSV 다. UTF-8 로 저장한 CSV 를 엑셀에서 그냥 더블클릭해 열면 한글이 깨져 보이는 일이 흔하고, 파일 앞에 BOM 을 붙이면 UTF-8 로 인식해 제대로 여는 경우가 많다. CSV 내보내기 기능을 만들 때 BOM 을 일부러 붙이는 코드가 널려 있는 이유다.

즉 이 세 바이트는 사람이 여는 파일에서는 힌트이고 프로그램이 읽는 파일에서는 쓰레기다. 문제는 같은 CSV 가 두 용도로 다 쓰인다는 점이다. 엑셀용으로 BOM 을 붙여 내보낸 파일이 나중에 다른 시스템의 입력으로 들어가면, 첫 열 이름이 바뀐다.

// csv.js — trim() 을 쓰지 않는 파서
const fs = require('fs');
const text  = fs.readFileSync(process.argv[2], 'utf8');
const lines = text.split(/\r?\n/).filter(l => l.length > 0);
const cols  = lines[0].split(',');
const rows  = lines.slice(1).map(r =>
  Object.fromEntries(r.split(',').map((v, i) => [cols[i], v])));

console.log('cols[0]         :', JSON.stringify(cols[0]));
console.log('cols[0].length  :', cols[0].length);
console.log('cols[0] === "id":', cols[0] === 'id');
console.log('row0.id         :', rows[0].id);

$ node csv.js plain.csv
cols[0]         : "id"
cols[0].length  : 2
cols[0] === "id": true
row0.id         : 1

$ node csv.js bom.csv
cols[0]         : "id"     # 화면에는 똑같이 보인다
cols[0].length  : 3        # 그런데 길이가 3 이다
cols[0] === "id": false
row0.id         : undefined

cols[0].length 가 2 와 3 이다. 이 한 줄이 없으면 아무것도 안 보인다. 실패 방식도 나쁘다. 예외가 나지 않고 undefined 가 조용히 흘러 들어간다. 십만 행짜리 적재 작업이 「전부 성공, 첫 열은 전부 빈 값」 으로 끝난다.

어느 쪽을 고쳐야 하는가는 파일의 최종 소비자가 정한다. 사람이 엑셀로 여는 것이 목적이면 붙이고, 프로그램이 다시 먹을 예정이면 붙이지 않는다. 두 용도가 겹치면 파일을 두 벌 만드는 편이 낫다.

왜 어떤 코드는 멀쩡한가 - trim() 의 정체

위 예제를 만들면서 처음에는 헤더 줄을 text.trim().split('\n') 으로 잘랐다. 그러자 BOM 파일이 정상 통과했다. 파서를 잘못 짠 것이 아니라, 자바스크립트의 trim() 이 U+FEFF 를 공백으로 취급해 걷어냈기 때문이다.

// t7.js — '\ufeff' 는 BOM 문자 자체를 뜻하는 이스케이프다
const s = '\ufeffid';
console.log('length          :', s.length);
console.log('trim().length   :', s.trim().length);
console.log('trim() === id   :', s.trim() === 'id');
console.log('/\\s/ matches?   :', /\s/.test('\ufeff'));
console.log('Number()        :', Number('\ufeff42'));
console.log('parseInt()      :', parseInt('\ufeff42'));

$ node t7.js
length          : 3
trim().length   : 2
trim() === id   : true
/\s/ matches?   : true
Number()        : 42
parseInt()      : 42

/\s/ 가 U+FEFF 에 매치하고, Number() 와 parseInt() 는 앞에 붙은 BOM 을 무시하고 42 를 돌려준다. 이 관용이 문제를 간헐적으로 만든다. 어떤 필드는 trim() 을 거쳐서 멀쩡하고 어떤 필드는 안 거쳐서 깨진다. 같은 파일, 같은 코드베이스, 다른 결과다.

  • 객체 키로 쓰는 경로는 대개 trim() 을 안 거친다. 그래서 헤더 이름에서 터진다
  • 숫자로 바꾸는 경로는 거의 항상 통과한다. 그래서 수치 검증으로는 이 버그를 못 잡는다
  • 정규식 검증도 \s 를 쓰고 있으면 통과한다. 「값에 공백이 없어야 한다」 류의 검사는 BOM 을 잡지 못한다
  • 즉 일반 검증기로는 안 걸린다. 첫 3바이트를 직접 보는 검사를 따로 두어야 한다

비교와 검색과 해시가 조용히 어긋난다

BOM 이 붙은 줄은 줄 시작에 앵커를 건 검색에서 빠진다. ^ 다음에 오는 것이 i 가 아니라 U+FEFF 이기 때문이다. 로그 필터, 배치 스크립트, 마이그레이션 검증 쿼리가 여기서 조용히 0 건을 돌려준다.

$ grep -c '^id' plain.csv
1
$ grep -c '^id' bom.csv
0                          # 앵커를 건 순간 안 잡힌다
$ grep -c 'id' bom.csv
1                          # 앵커를 빼면 잡힌다

$ grep -Fxc 'id' list_a.txt
1
$ grep -Fxc 'id' list_b.txt
0                          # 줄 전체 일치도 마찬가지

$ cat v1.txt v2.txt | sort -u | xxd
00000000: 616c 7068 610a efbb bf61 6c70 6861 0a    alpha....alpha.
                           # sort -u 가 같은 단어를 둘로 남긴다

$ sha256sum plain.html bom.html
904ee45b2e532f436f4c05f8d809365538b9bf9843030bc01d0f9079deb0cbe7 *plain.html
a3369d9b5f62004281debdaccdc69395cc94af732b19023258576308ce7cbc35 *bom.html

해시가 다르다는 것은 배포 검증에서 바로 문제가 된다. 「산출물이 이전과 동일한지」를 체크섬으로 확인하는 파이프라인이라면, 누군가 편집기 설정을 바꾼 것만으로 전부 변경됨이 뜬다.

한 가지 더. BOM 은 파일 맨 앞에만 있는 것이 아니다. BOM 이 붙은 파일 여럿을 그냥 이어 붙이면 중간에 박힌다.

$ cat part1.csv part2.csv > merged.csv
$ grep -c $'\xef\xbb\xbf' merged.csv
2
$ xxd merged.csv
00000000: efbb bf69 642c 760a 312c 610a efbb bf69  ...id,v.1,a....i
00000010: 642c 760a 322c 620a                      d,v.2,b.
                           # 두 번째 BOM 이 데이터 한가운데 들어가 있다

중간의 U+FEFF 는 옛 유니코드에서 zero-width no-break space 로도 쓰이던 문자라 렌더링해도 아무것도 안 보인다. 로그 수집기나 분할 다운로드를 합치는 배치에서 이런 파일이 나오면 추적이 오래 걸린다.

웹에서 나타나는 증상

HTML 파일 맨 앞에 BOM 이 있으면 문서 첫 문자가 < 가 아니게 된다. 바이트로 보면 이렇다.

$ head -c 24 bom.html | xxd
00000000: efbb bf3c 2144 4f43 5459 5045 2068 746d  ...<!DOCTYPE htm
00000010: 6c3e 0a3c 6874 6d6c                      l>.<html

$ node -e "
const s = require('fs').readFileSync('bom.html', 'utf8');
console.log('indexOf   :', s.indexOf('<!DOCTYPE'));
console.log('startsWith:', s.startsWith('<!DOCTYPE'));
"
indexOf   : 1
startsWith: false

여기서부터는 실행으로 확인하지 않았고, 구조만 적는다. 서버 사이드 템플릿을 쓰는 환경에서 자주 보고되는 형태는 두 가지다. 하나는 본문 맨 위에 정체불명의 빈 줄이나 여백이 생기는 것이다. 문서 시작 전에 문자 하나가 출력됐으니 파서가 그것을 본문 내용으로 처리한다. 다른 하나는 헤더 전송 실패다. PHP 처럼 파일 내용을 그대로 출력 스트림에 흘리는 구조에서는, <?php 태그 앞의 세 바이트가 이미 출력이므로 그 뒤의 헤더 설정이나 리다이렉트가 「이미 헤더가 전송됨」 류의 경고와 함께 실패한다.

이런 경우에 쓸 만한 접근은 증상 쪽이 아니라 파일 쪽에서 좁히는 것이다. 포함되는 파일이 수십 개라도, 첫 3바이트가 EF BB BF 인 것만 뽑으면 대개 한두 개로 끝난다.

있는지 확인하는 법

도구는 여러 개지만 하는 일은 같다. 파일의 첫 3바이트를 본다. 상황에 따라 편한 것을 쓰면 된다.

$ file config.json run.sh clean.txt
config.json: Unicode text, UTF-8 (with BOM) text
run.sh:      POSIX shell script, Unicode text, UTF-8 (with BOM) text executable
clean.txt:   ASCII text

$ xxd config.json | head -1
00000000: efbb bf7b 2261 223a 317d 0a              ...{"a":1}.

$ grep -rlI $'\xef\xbb\xbf' .
./config.json
./sub/run.sh

$ grep -rlI $'^\xef\xbb\xbf' .    # 줄 맨 앞에 있는 것만
./config.json
./sub/run.sh

$ cat -A bom.txt
M-oM-;M-?hello$

$ sed -n l bom.txt
\357\273\277hello$

cat -A 의 M-oM-;M-? 와 sed -n l 의 \357\273\277 는 같은 세 바이트를 각각 8진수와 메타 표기로 보여 준 것이다. 터미널에서 눈으로 확인할 때 이 둘이 제일 빠르다. 다만 grep -rlI 는 파일 중간의 BOM 도 같이 잡는다는 점을 알고 써야 한다. 맨 앞만 보고 싶으면 앵커를 붙이되, 그것도 「어떤 줄의 시작」 이지 「파일의 시작」 은 아니다. 정확히 파일 첫 3바이트만 보려면 프로그램으로 여는 편이 낫다.

// bomcheck.js — 첫 3바이트만 읽어 확인한다. CI 에 걸기 좋다
const fs = require('fs'), path = require('path');
const BOM = Buffer.from([0xEF, 0xBB, 0xBF]);

function walk(dir, out = []) {
  for (const e of fs.readdirSync(dir, { withFileTypes: true })) {
    const p = path.join(dir, e.name);
    if (e.isDirectory()) walk(p, out); else out.push(p);
  }
  return out;
}

let bad = 0;
for (const f of walk(process.argv[2] || '.')) {
  const fd = fs.openSync(f, 'r');
  const head = Buffer.alloc(3);
  fs.readSync(fd, head, 0, 3, 0);
  fs.closeSync(fd);
  if (head.equals(BOM)) { console.log('BOM: ' + f); bad++; }
}
console.log(bad ? bad + ' file(s) with a UTF-8 BOM' : 'no BOM found');
process.exit(bad ? 1 : 0);

$ node bomcheck.js ./tree
BOM: tree\config.json
BOM: tree\sub\run.sh
2 file(s) with a UTF-8 BOM
$ echo $?
1

$ node bomcheck.js ./cleantree
no BOM found
$ echo $?
0

PowerShell 쪽에서는 ReadAllBytes 로 앞부분만 찍어 보면 된다. 주의할 것이 하나 있는데, Get-Content 로 읽으면 BOM 이 이미 걷힌 문자열이 온다. Windows PowerShell 5.1.19041.6456 에서 BOM 이 붙은 파일을 Get-Content -Raw 로 읽어 첫 글자를 찍어 보면 U+006C, 즉 본문 첫 글자가 나온다. 문자열 수준에서는 아무 문제가 없어 보이므로, 확인은 반드시 바이트 수준에서 해야 한다.

PS> $b = [System.IO.File]::ReadAllBytes('config.json')
PS> ($b[0..2] | ForEach-Object { $_.ToString('X2') }) -join ' '
EF BB BF

PS> (Get-Content -Path config.json -Raw)[0]
{                          # 문자열로 읽으면 BOM 이 이미 없다

지우는 법, 그리고 지우다 망가뜨리는 법

지우는 것 자체는 어렵지 않다. 어려운 것은 지우면 안 되는 파일까지 건드리지 않는 것이다. 일괄 처리는 되돌리기가 없으므로 백업부터 잡고 시작한다.

$ sed '1s/^\xEF\xBB\xBF//' in.csv > out.csv     # 새 파일로 (가장 안전)
$ sed -i.bak '1s/^\xEF\xBB\xBF//' in.csv        # 제자리 편집 + 원본 백업

$ xxd in.csv | head -1
00000000: 6964 2c6e 616d 650a 782c 790a            id,name.x,y.
$ xxd in.csv.bak | head -1
00000000: efbb bf69 642c 6e61 6d65 0a78 2c79 0a    ...id,name.x,y.

$ awk 'NR==1{sub(/^\xef\xbb\xbf/,"")}1' in.txt > out.txt
$ perl -pi -e 's/^\x{ef}\x{bb}\x{bf}// if $.==1' in.txt

1s/ 로 첫 줄만 대상을 좁힌 것이 중요하다. 범위를 안 주면 본문 중간에 정당하게 들어 있을 수도 있는 U+FEFF 까지 지운다. 그리고 -i 에 접미사를 붙이면 GNU sed 4.9 는 원본을 .bak 로 남긴다. 수백 개 파일을 한 번에 도는 작업이면 이쪽을 기본으로 쓰는 편이 낫다.

다음은 전용 도구다. 여기에 함정이 하나 있다.

$ xxd before.csv
00000000: efbb bf61 0d0a 620d 0a                   ...a..b..     # BOM + CRLF

$ dos2unix --remove-bom before.csv
dos2unix: converting file before.csv to Unix format...

$ xxd before.csv
00000000: 610a 620a                                a.b.          # BOM 도 CR 도 사라졌다

$ dos2unix -m -n a.csv a.bom.csv          # -m 은 반대로 BOM 을 붙인다
$ xxd a.bom.csv
00000000: efbb bf61 0a62 0a                        ...a.b.

dos2unix --remove-bom 은 BOM 만 지우지 않는다. 이름 그대로 줄바꿈까지 LF 로 바꾼다. 위 출력에서 0d0a 두 쌍이 전부 0a 가 됐다. 윈도우 전용으로 유지해야 하는 파일에 이걸 돌리면 BOM 문제 하나 고치려다 줄바꿈 문제를 새로 만든다. 반대로 붙이는 쪽은 -m 이고, -n 을 주면 원본을 두고 새 파일로 쓴다.

iconv 는 이 용도로는 기대만큼 동작하지 않는다.

$ iconv -f UTF-8 -t UTF-8 in.csv > out.csv
$ xxd out.csv | head -1
00000000: efbb bf69 642c 6e61 6d65 0a78 2c79 0a    ...id,name.x,y.
                           # UTF-8 에서 UTF-8 로는 BOM 이 그대로 남는다

$ iconv -f UTF-8-BOM -t UTF-8 in.csv
iconv: conversion from UTF-8-BOM unsupported

$ iconv -f UTF-8 -t UTF-16 ab.txt | xxd
00000000: feff 0041 0042 000a                      ...A.B..      # BOM 이 붙는다
$ iconv -f UTF-8 -t UTF-16LE ab.txt | xxd
00000000: 4100 4200 0a00                           A.B...        # 붙지 않는다

GNU libiconv 1.18 에서 UTF-8-BOM 이라는 이름은 인식되지 않는다. 다만 마지막 두 줄은 기억해 둘 만하다. UTF-16 으로 변환하면 BOM 이 붙고 UTF-16LE 로 변환하면 안 붙는다. 엔디언을 이름에 명시하면 순서를 알릴 필요가 없어지기 때문이다.

마지막으로, 가장 흔하게 제안되지만 가장 위험한 방법이다.

$ printf '\xef\xbb\xbfhi\n' > a.txt
$ tail -c +4 a.txt | xxd
00000000: 6869 0a                                  hi.           # 잘 지워졌다

$ printf 'hi there\n' > b.txt                                    # BOM 이 없는 파일
$ tail -c +4 b.txt | xxd
00000000: 7468 6572 650a                           there.        # 'hi ' 를 먹었다

tail -c +4 는 앞 3바이트를 무조건 버린다. BOM 이 있는 파일에만 돌리면 맞지만, 폴더 전체에 반복문으로 돌리는 순간 BOM 없는 파일들의 첫 세 글자가 사라진다. 위 예에서 hi  가 없어졌다. 이 방식을 쓰려면 반드시 앞에서 BOM 여부를 확인하는 조건을 붙여야 한다.

읽는 쪽에서 해결하는 길도 있다. 파일을 못 고치는 상황이면 이쪽이 낫다. 파이썬 3.11.9 는 이 용도의 코덱을 표준으로 갖고 있다.

>>> open('bom.json', encoding='utf-8').read()[0]
'\ufeff'
>>> json.load(open('bom.json', encoding='utf-8'))
json.decoder.JSONDecodeError: Unexpected UTF-8 BOM (decode using utf-8-sig): line 1 column 1 (char 0)

# csv.DictReader — 인코딩 이름 하나로 첫 열 이름이 달라진다
utf-8      fieldnames: ['\ufeffid', 'name', 'qty']   row.get('id') -> None
utf-8-sig  fieldnames: ['id', 'name', 'qty']         row.get('id') -> 1

파이썬의 오류 메시지는 이 글에서 본 것 중 가장 친절하다. 원인과 해법을 한 줄에 같이 적어 준다. utf-8-sig 는 BOM 이 있으면 걷어내고 없으면 그냥 통과하므로, 입력 파일을 통제할 수 없는 코드에서는 기본으로 써도 되는 값이다.

붙여야 하는 자리와 붙이면 안 되는 자리

규칙은 하나로 정리된다. 첫 바이트가 곧 문법인 형식에는 붙이지 않는다. 셰뱅, JSON 의 여는 중괄호, XML 선언, CSV 의 첫 열 이름은 전부 그 첫 바이트 자리가 의미를 갖는다. 반대로 인코딩을 알려 줄 다른 경로가 없고 사람이 여는 것이 목적인 파일이라면 붙이는 쪽이 낫다.

파일 종류BOM이유
셸 스크립트 (.sh, .bash)붙이지 않는다셰뱅이 셰뱅이 아니게 된다. 첫 줄만 실패하고 계속 도는 형태라 더 나쁘다
JSON (.json)붙이지 않는다RFC 8259 가 전송 시 추가를 금지한다. 파서가 무시해 줄 의무는 없다
YAML·설정 파일 (.env 포함)붙이지 않는다첫 키 이름이 달라진다. 예외 없이 조용히 실패한다
소스 코드 전반붙이지 않는다해시가 달라지고 diff 가 보이지 않는 변경을 만든다
엑셀로 여는 CSV붙인다BOM 이 없으면 한글이 깨져 열리는 경우가 많다. 사람이 여는 파일이다
프로그램이 읽을 CSV붙이지 않는다첫 열 이름이 id 가 아니게 된다. 예외 없이 undefined 가 흐른다
윈도우 전용 텍스트 (메모장 등)붙여도 된다인코딩을 알릴 다른 수단이 없다. 다른 시스템으로 넘길 계획이 없을 때만
UTF-16 / UTF-32 파일붙인다바이트 순서 문제가 실재한다. BOM 의 원래 용도가 여기다
HTML붙이지 않는다<meta charset> 이나 HTTP 헤더가 이미 인코딩을 알린다

애매한 경우의 판단 기준도 하나로 줄일 수 있다. 이 파일을 마지막에 여는 것이 사람인가 프로그램인가. 사람이면 붙이는 쪽에 이득이 있고, 프로그램이면 거의 항상 손해다. 둘 다면 파일을 나눈다.

팀에서 재발을 막는 법

한 번 지우는 것보다 다시 안 생기게 하는 것이 어렵다. 대부분은 사람이 아니라 도구 설정이 만들어 내기 때문이다. 가장 흔한 발생원은 PowerShell 이다.

PS> "line one" | Set-Content a_default.txt
PS> "line one" | Set-Content b_utf8.txt   -Encoding utf8
PS> "line one" | Out-File   c_outfile.txt -Encoding utf8
PS> [System.IO.File]::WriteAllText("$pwd\d_nobom.txt", "line one`n",
      (New-Object System.Text.UTF8Encoding($false)))

a_default.txt   len=10   first bytes: 6C 69 6E 65 20 6F 6E 65
b_utf8.txt      len=13   first bytes: EF BB BF 6C 69 6E 65 20
c_outfile.txt   len=13   first bytes: EF BB BF 6C 69 6E 65 20
d_nobom.txt     len= 9   first bytes: 6C 69 6E 65 20 6F 6E 65

PS> "x" | Set-Content f.txt -Encoding utf8NoBOM
Cannot bind parameter 'Encoding'. Cannot convert value "utf8NoBOM" to type
"Microsoft.PowerShell.Commands.FileSystemCmdletProviderEncoding".

Windows PowerShell 5.1.19041.6456 에서 -Encoding utf8 은 BOM 을 붙인다. 그리고 utf8NoBOM 이라는 값은 이 판본에 존재하지 않아 파라미터 바인딩 단계에서 거부된다. 이 판본에서 BOM 없는 UTF-8 을 쓰려면 UTF8Encoding($false) 를 직접 넘기는 것이 확실한 방법이다. 배포 스크립트가 설정 파일을 생성하는 구조라면 여기가 첫 번째 점검 대상이다.

편집기 쪽은 .editorconfig 로 어느 정도 통제된다. 명세에 charset 속성이 있고 값으로 latin1, utf-8, utf-8-bom, utf-16be, utf-16le 를 쓸 수 있다. 명세 자체가 utf-8-bom 사용을 권하지 않는다고 적어 두었다. 다만 이것은 편집기가 읽고 따라 줄 때만 성립하는 규약이다. 지원하지 않는 도구가 파일을 쓰면 그대로 뚫린다.

# .editorconfig
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true

[*.csv]
charset = utf-8-bom          # 엑셀로 여는 내보내기 파일만 예외로 둔다

여기서 분명히 해 둘 것이 있다. git 은 BOM 을 정규화해 주지 않는다. gitattributes 문서가 다루는 text 와 eol 은 줄바꿈 변환이고, working-tree-encoding 은 UTF-16 계열처럼 저장소와 작업 트리의 인코딩이 다를 때 쓰는 것이다. UTF-8 BOM 을 붙이거나 떼는 속성은 없다. 줄바꿈은 .gitattributes 한 줄로 팀 전체가 통일되지만, BOM 에는 그런 장치가 없다는 뜻이다.

그러니 마지막 방어선은 검사다. 앞 절의 bomcheck.js 는 BOM 을 찾으면 종료 코드 1 을 돌려주므로 CI 단계에 그대로 걸 수 있다. 셸만 있는 환경이면 한 줄로도 된다.

# BOM 이 하나라도 있으면 실패시킨다 (GNU grep 3.0)
! grep -rlI $'^\xef\xbb\xbf' --include='*.sh' --include='*.json' \
                            --include='*.yaml' --include='*.yml' . \
  || { echo "BOM found in the files above"; exit 1; }
  • 발생원부터 막는다 — PowerShell 의 -Encoding utf8, 메모장, 일부 윈도우 편집기가 대부분을 만든다
  • .editorconfig 로 합의를 적어 둔다 — 강제력은 없지만 도구가 지원하면 자동으로 맞는다
  • git 에는 기대하지 않는다 — 줄바꿈과 달리 저장소가 통일해 주지 않는다
  • CI 에서 막는다 — 첫 3바이트를 보는 검사 한 개면 된다. 확장자로 대상을 좁혀 CSV 예외를 남긴다
  • 일괄 제거는 한 번에 하나의 커밋으로 — 다른 변경과 섞으면 나중에 무엇이 바뀐 것인지 구분할 수 없다

BOM 과 줄바꿈은 다른 문제다

이 둘은 늘 같이 언급되지만 원인도 해법도 다르다. 같은 자리에서 나타나고 같은 도구로 고치는 경우가 많아서 하나로 묶여 버린 것뿐이다. 실제로는 다음 표만큼 다르다.

항목UTF-8 BOMCRLF / LF
위치파일 맨 앞 3바이트, 한 번모든 줄 끝, 파일 전체
바이트EF BB BF0D 0A 또는 0A
git 이 정규화하는가안 한다. 관련 속성이 없다한다. text·eol 속성으로 통일된다
대표 증상첫 줄만 실패. 셰뱅·첫 키·첫 열 이름bad interpreter: /bin/bash^M 류의 즉시 실패
발견 난이도높다. 화면에 아무것도 안 보인다낮다. 에러 메시지에 ^M 이 찍힌다
고치는 도구sed 1s, utf-8-sig, 첫 3바이트 검사dos2unix, .gitattributes

실무에서 중요한 차이는 세 번째 줄이다. 줄바꿈은 저장소 설정으로 팀 전체를 한 번에 맞출 수 있지만, BOM 은 각자의 편집기와 각자의 스크립트에서 계속 새로 생긴다. 그래서 줄바꿈은 정책으로 풀고 BOM 은 검사로 푸는 것이 맞다. dos2unix 가 두 가지를 한꺼번에 해 준다는 사실이 이 구분을 흐리는데, 앞에서 본 것처럼 그 편의는 원하지 않는 변환을 같이 데려온다.

인코딩 자체가 어긋나서 글자가 깨지는 문제 — 이를테면 cp949 로 저장된 파일을 UTF-8 로 읽어 ????? 나 ìëíì 가 되는 쪽 — 는 또 다른 층위의 이야기이고 이 글의 주제가 아니다. 그쪽은 한글이 깨지는 지점을 특정하는 법 에 정리해 두었다. 압축 파일 안의 한글 파일명이 깨지는 경우는 zip 안의 한글 파일명이 깨지는 지점 쪽이 맞고, 한글 문자열을 정규식으로 다루다 헛짚는 문제는 한글 정규식 함정 에 있다.

확인하지 못한 것

  • 엑셀의 실제 동작 — BOM 이 있으면 UTF-8 CSV 를 제대로 연다는 것은 널리 쓰이는 대응책이지만, 이 글에서는 엑셀로 열어 보지 않았다. 버전과 지역 설정에 따라 결과가 다르다는 보고도 있으므로, 도입 전에 실제 사용 환경의 엑셀에서 직접 확인하는 편이 낫다. 확인한 것은 프로그램이 그 파일을 읽을 때 첫 열 이름이 달라진다는 쪽뿐이다
  • PowerShell 7 계열 — 이 환경에 pwsh 가 설치돼 있지 않아 확인하지 못했다. 본문의 -Encoding utf8 이 BOM 을 붙인다는 결과와 utf8NoBOM 이 없다는 결과는 Windows PowerShell 5.1.19041.6456 한정이다. 판본이 다르면 기본값이 다를 수 있으므로 쓰는 판본에서 바이트를 직접 찍어 볼 것을 권한다
  • PHP 의 헤더 전송 실패 — 이 환경에 PHP 가 없어 재현하지 못했다. 9절의 해당 대목은 구조 설명이며 실행 결과가 아니다. HTML 파일에서 문서 첫 문자가 < 가 아니게 된다는 것까지만 실제로 확인했다
  • BSD 계열 도구 — 여기서 쓴 sed 는 GNU sed 4.9 다. \xEF 같은 16진 이스케이프와 -i 의 접미사 처리 방식은 GNU 구현에 의존하고, macOS 기본 sed 에서는 다르게 동작한다고 알려져 있으나 확인할 환경이 없었다
  • git 의 실제 동작 — BOM 을 정규화하는 속성이 없다는 것은 gitattributes 문서에서 확인한 내용이고, 저장소에서 명령을 실행해 본 것은 아니다
  • 셰뱅 실패 후의 동작 — 첫 줄 실패 후 나머지가 그대로 실행된 것은 MSYS2 의 bash 5.2.37 에서 관찰한 결과다. 리눅스 배포판의 셸이나 다른 커널에서 같은 폴백이 일어나는지는 확인하지 못했다
