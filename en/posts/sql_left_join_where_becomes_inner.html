A WHERE Clause Turns Your LEFT JOIN Into an INNER JOIN - Where ON Ends and WHERE Begins

Reproducing the ten-rows-become-four bug on SQLite, and deciding which clause is right for which intent

2026-07-30 Dev & Infra

The symptom: every month the report count was slightly low

There was a monthly report broken down by region. The revenue totals matched accounting. But the customer count was always a little low. The error log was empty, and nobody had touched that query in months. In some months an entire region was missing from the table, but that region had zero revenue, so nobody found it strange.

The cause was one line. A LEFT JOIN pulled in every customer, and then WHERE o.status = 'paid' was appended below it. That single line turns a LEFT JOIN into an INNER JOIN. It is not a syntax error. There is no warning. Execution actually gets faster. The only thing that shrinks is the row count.

There are reasons a bug like this survives for months.

  • It raises no error. Syntax and types are both fine, so no tool warns about it
  • It does not reproduce on a development database. Seed data is densely related and has almost no gaps. With no gaps, LEFT and INNER return the same thing
  • What shrinks is the absent data. The rows that left the screen were zero-valued or empty, so nothing looks visually different
  • The totals stay correct. Sum metrics are untouched and only count metrics are wrong, so an accounting reconciliation does not catch it

This article does not re-explain join types. I built three tables in SQLite and ran the same query with small variations, counting rows one case at a time. Every number and every block of output below is exactly what appeared on screen.

Environment. Every output below was really executed on Windows 10 Pro (10.0.19045). The engine is SQLite 3.49.1, reached through two paths: the sqlite3 module of CPython 3.13.3, and node:sqlite bundled with Node.js v22.16.0. Section 14 compares the two.

Every script was saved to a file before running. Passing queries and output through shell arguments quietly mangles quoting. All tables and data are fictional: customers, orders, shipments.

What this article does not cover. An overview of join types and basic syntax lives in the SQL primer. Performance topics such as indexes, locking and N+1 are handled in the operational database survival guide. Here I dig into one single point: the boundary between ON and WHERE.

1. The reproduction - the moment 10 rows become 4

Three tables. Ten customers, six orders, four shipments. And four customers with no order at all. Those four are the protagonists of this article.

-- customers 10 rows | orders 6 rows | 4 customers have no order at all

First, a plain LEFT JOIN with no filter.

SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ---------
  1            Ada   101       paid
  2            Ben   102       paid
  3            Cara  103       paid
  4            Dan   104       paid
  5            Eve   105       pending
  6            Finn  106       cancelled
  7            Gus   NULL      NULL
  8            Hana  NULL      NULL
  9            Ivan  NULL      NULL
  10           Joy   NULL      NULL
  rows: 10

Ten rows. Customers 7 through 10 have no order to pair with, so every right-hand column is filled with NULL. So far this is exactly the intended picture: the customer list stays whole, and an order attaches when one exists.

Now a requirement arrives: show only paid orders. The most natural hand movement is to append one line at the bottom of the query.

-- exactly the same query, one line added at the bottom
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = 'paid'
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ------
  1            Ada   101       paid
  2            Ben   102       paid
  3            Cara  103       paid
  4            Dan   104       paid
  rows: 4

-- and now the same thing written as an INNER JOIN
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = 'paid'
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ------
  1            Ada   101       paid
  2            Ben   102       paid
  3            Cara  103       paid
  4            Dan   104       paid
  rows: 4

Ten rows became four. And the INNER JOIN rewrite directly below returns exactly the same four rows. The two queries are equivalent. Which means the word LEFT in the first one is doing nothing at all.

Split the six missing rows and they turn out to be two different things.

  • Two rows are intentional removals. Customer 5 with pending, customer 6 with cancelled. We asked for paid only, so this part is right
  • Four rows are unintentional. Customers 7 through 10. It is not that they have no paid order; they have no order at all
  • The requirement was paid orders only, not remove customers. The query removed customers as well
  • The word LEFT is still sitting in the query. In review it reads as it is a LEFT JOIN, so all customers come through and gets waved past
  • If the development database had no order-less customers, the two queries return the same result forever. No test can catch it

2. Move the same condition into ON

Now attach the same condition to ON with AND instead of putting it in WHERE. The character count is similar and the predicate is identical.

SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o
       ON c.customer_id = o.customer_id
      AND o.status = 'paid'
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ------
  1            Ada   101       paid
  2            Ben   102       paid
  3            Cara  103       paid
  4            Dan   104       paid
  5            Eve   NULL      NULL
  6            Finn  NULL      NULL
  7            Gus   NULL      NULL
  8            Hana  NULL      NULL
  9            Ivan  NULL      NULL
  10           Joy   NULL      NULL
  rows: 10

Ten rows again. But the content differs from the first output in section 1. Customer 5 with a pending order and customer 6 with a cancelled order did not disappear; they turned into NULL. The customers stayed and only the non-qualifying orders fell away.

Counting rows and NULLs side by side makes the difference between the three queries obvious.

--- row counts, five spellings of nearly the same query ---
  LEFT JOIN, no filter           : 10 rows
  LEFT JOIN + WHERE status=paid  :  4 rows
  LEFT JOIN + ON   status=paid   : 10 rows
  INNER JOIN + WHERE status=paid :  4 rows
  INNER JOIN + ON   status=paid  :  4 rows

--- how many NULL order_id survive in each ---
  LEFT JOIN, no filter          : 10 rows, 4 NULL order_id
  LEFT JOIN + WHERE status=paid :  4 rows, 0 NULL order_id
  LEFT JOIN + ON   status=paid  : 10 rows, 6 NULL order_id
  • The WHERE version: 4 rows, 0 NULL right-hand rows. Only customers with a paid order remain
  • The ON version: 10 rows, 6 NULL right-hand rows. Every customer remains and only matching orders attach
  • The point is that NULL rows went up from four to six. Two non-qualifying orders were not removed but nulled out
  • Which one is correct is not something the query can answer. What the report was trying to count decides it

As a table. Where the same predicate sits changes what the result means.

Query shapeRowsNULL right rowsQuestion actually asked
LEFT JOIN, no filter104All customers, plus their order if any
LEFT JOIN + WHERE40Only customers who have a paid order
LEFT JOIN + ON106All customers, plus their paid order if any
INNER JOIN + WHERE40The same question as the second row
INNER JOIN + ON40Same. In an inner join there is no difference

The last two rows matter. In an INNER JOIN, ON and WHERE produce the same result. So anyone who learned the advice about putting conditions in ON while working with inner joins never had a chance to feel the difference. The difference only appears in outer joins.

3. Why: the join runs first, the WHERE runs after

One fact explains all of it. The join runs first and produces an intermediate result; the WHERE is applied to that intermediate result. So I printed the intermediate result as it stands and noted, next to each row, whether it survives the WHERE.

--- the intermediate result, right after the join, before WHERE ---
  cid  name  order_id  status     -> does WHERE o.status=paid keep it?
  ---  ----  --------  ---------  --------------------------------------
  1    Ada   101       paid       KEEP
  2    Ben   102       paid       KEEP
  3    Cara  103       paid       KEEP
  4    Dan   104       paid       KEEP
  5    Eve   105       pending    DROP (not paid)
  6    Finn  106       cancelled  DROP (not paid)
  7    Gus   NULL      NULL       DROP (NULL = paid is NULL, not true)
  8    Hana  NULL      NULL       DROP (NULL = paid is NULL, not true)
  9    Ivan  NULL      NULL       DROP (NULL = paid is NULL, not true)
  10   Joy   NULL      NULL       DROP (NULL = paid is NULL, not true)
  join produced 10 rows, WHERE kept 4

The last column shows how the four NULL-filled rows die. A NULL manufactured by the join is caught by the very next WHERE and erases the row. The WHERE throws away exactly the rows the LEFT JOIN worked to keep.

Three-valued logic is what makes that call. Printing the comparison itself:

SELECT NULL = 'paid'            AS null_eq_paid,
       NULL <> 'paid'           AS null_ne_paid,
       NULL IS NULL             AS null_is_null,
       (NULL = 'paid') IS NULL  AS comparison_is_null;

  null_eq_paid  null_ne_paid  null_is_null  comparison_is_null
  ------------  ------------  ------------  ------------------
  NULL          NULL          1             1
  rows: 1

-- a row survives WHERE only when the predicate evaluates to TRUE (1).
-- NULL = 'paid' is neither TRUE nor FALSE. It is NULL. So the row goes away.
-- NULL <> 'paid' does not rescue it either: that is NULL too.

NULL = 'paid' is not false; it is NULL. WHERE keeps only rows whose predicate is true, so a row that is neither true nor false does not survive. A common misconception splits off right here: rewriting it as NULL <> 'paid' does not rescue anything. That is NULL too.

Separating what each clause does, item by item. This table is the skeleton of the article.

AspectONWHERE
When it is evaluatedWhile the join is being builtAfter the join is finished
What it decidesWhat gets pairedWhat survives after pairing
Left row with no partnerKept, right side filled with NULLDiscarded unless the predicate holds
Rows in this example104
Difference in an inner joinNoneNone
Query planLEFT-JOIN marker staysThe marker disappears
  • ON is the pairing rule. It decides which left row merges with which right row into a single row
  • LEFT is the rescue rule. It keeps a left row that found no partner by filling the right side with NULL
  • WHERE is the selection rule. After both of the above, it passes only the rows whose predicate holds
  • So a right-table predicate in WHERE erases the row LEFT just rescued. Two rules collide head-on
  • A left-table predicate does not collide. WHERE c.region = 'north' narrows the left side while leaving the LEFT JOIN behaviour intact

The PostgreSQL documentation states the ordering explicitly. Section 7.2.1.1, Joined Tables, says that a restriction placed in the ON clause is processed before the join while a restriction placed in the WHERE clause is processed after it, and that this does not matter for inner joins but matters a great deal for outer joins. In other words, this is not a quirk of one product; it is the definition of the join.

4. The IS NULL exception - same clause, opposite outcome

A natural objection follows. If NULLs are dropped, should not WHERE o.order_id IS NULL drop everything too? In practice it does the opposite: it keeps only the customers with no orders. Three variants, run side by side.

-- 1. customers with no order at all
SELECT c.customer_id, c.name, o.order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL
ORDER BY c.customer_id;

  customer_id  name  order_id
  -----------  ----  --------
  7            Gus   NULL
  8            Hana  NULL
  9            Ivan  NULL
  10           Joy   NULL
  rows: 4

-- 2. ON filter + IS NULL = customers with no PAID order
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.status = 'paid'
WHERE o.order_id IS NULL
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ------
  5            Eve   NULL      NULL
  6            Finn  NULL      NULL
  7            Gus   NULL      NULL
  8            Hana  NULL      NULL
  9            Ivan  NULL      NULL
  10           Joy   NULL      NULL
  rows: 6

-- 3. orders.status is declared NOT NULL, yet IS NULL matches 4 rows
SELECT c.customer_id, c.name, o.status
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status IS NULL
ORDER BY c.customer_id;

  customer_id  name  status
  -----------  ----  ------
  7            Gus   NULL
  8            Hana  NULL
  9            Ivan  NULL
  10           Joy   NULL
  rows: 4

The first gives four rows. The mechanism is identical to before. IS NULL is the one kind of predicate that returns true for NULL. So the rows the join filled with NULL pass the WHERE, and the matched rows are the ones that fall away. This idiom is called an anti-join.

The second is far more useful. Put the condition in ON and the IS NULL in WHERE, and you get the six customers with no paid order. That is a different set from the first four. Customers 5 and 6 have orders but none paid, so they belong here.

The third output is worth filing away separately.

  • IS NULL is the predicate that returns true for NULL. Every other comparison operator returns NULL
  • So it is the tool for picking out the rows the join created. It is an idiom, not an exception
  • Condition in ON plus WHERE ... IS NULL yields left rows with no partner matching that condition. Six rows here
  • With no condition in ON you get left rows with no partner at all. Four rows. Two different questions
  • IS NULL matches even on a column declared NOT NULL. That NULL is not a stored value; the join manufactured it

5. Meeting an aggregate - COUNT(o.order_id) versus COUNT(*)

Add an aggregate and the same trap wears a different face. I applied GROUP BY to the join result and pulled two kinds of COUNT side by side.

SELECT c.customer_id, c.name,
       COUNT(*)          AS count_star,
       COUNT(o.order_id) AS count_order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
ORDER BY c.customer_id;

  customer_id  name  count_star  count_order_id
  -----------  ----  ----------  --------------
  1            Ada   1           1
  2            Ben   1           1
  3            Cara  1           1
  4            Dan   1           1
  5            Eve   1           1
  6            Finn  1           1
  7            Gus   1           0
  8            Hana  1           0
  9            Ivan  1           0
  10           Joy   1           0
  rows: 10

-- grand totals over exactly the same join
  count_star  count_order_id  count_status
  ----------  --------------  ------------
  10          6               6
  rows: 1

The two values diverge for customers 7 through 10. COUNT(*) gives 1, COUNT(o.order_id) gives 0. The failure here is that a customer with no orders at all gets reported as having one. The reason is plain: a NULL-filled row is still a row, and COUNT(*) counts rows.

The grand totals show the same split. Overall COUNT(*) is 10 and COUNT(o.order_id) is 6. Ten is the customer count and six is the order count. Both are correct numbers, but if the report column is labelled order count, 10 is wrong.

What each aggregate returns for a group with no match:

ExpressionValue for a group with no matchWhyConsequence in practice
COUNT(*)1A NULL-filled row is still a rowZero orders is reported as one
COUNT(o.order_id)0NULL arguments are not countedUsually the number you want
SUM(o.amount)NULLThere is nothing to addNot zero. It spreads into outer math
COALESCE(SUM(...), 0)0Substitutes the aggregate resultThe recommended position
AVG(o.amount)NULLThe divisor is zeroOuter averages lose divisor and inflate
  • COUNT(*) counts rows. A NULL-filled row is a row, so a group with no match comes out as 1
  • COUNT(o.order_id) counts non-NULL values. With no match it is 0, and that is usually the number you want
  • Which column you count matters. COUNT(o.status) also gave 6. Any NOT NULL column of the right-hand table works
  • COUNT(DISTINCT c.customer_id) is a third value again. In the section 12 report that function gave different answers per region

6. SUM goes NULL, not zero

On the money side the symptom is quieter. I summed the same column four ways.

SELECT c.customer_id, c.name,
       SUM(o.amount)              AS sum_raw,
       COALESCE(SUM(o.amount), 0) AS coalesce_outside,
       SUM(COALESCE(o.amount, 0)) AS coalesce_inside,
       TOTAL(o.amount)            AS sqlite_total
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
ORDER BY c.customer_id;

  customer_id  name  sum_raw  coalesce_outside  coalesce_inside  sqlite_total
  -----------  ----  -------  ----------------  ---------------  ------------
  1            Ada   120      120               120              120
  2            Ben   80       80                80               80
  3            Cara  45       45                45               45
  4            Dan   300      300               300              300
  5            Eve   60       60                60               60
  6            Finn  210      210               210              210
  7            Gus   NULL     0                 0                0
  8            Hana  NULL     0                 0                0
  9            Ivan  NULL     0                 0                0
  10           Joy   NULL     0                 0                0
  rows: 10

-- what those NULLs do one layer further out
  from SUM(o.amount)             : sum=815  avg=135.83  count=6
  from COALESCE(SUM(o.amount),0) : sum=815  avg= 81.50  count=10
-- the totals agree, the averages do not: AVG skipped the four NULL groups.

With no match, SUM is NULL, not zero. There is nothing to add. Right there the NULL looks harmless. The problem appears one layer out.

Same data, and the average split into 135.83 and 81.50. Both totals are 815. AVG does not count the NULL groups, so the divisor became 6 in one case and 10 in the other. A metric like average spend per customer quietly inflates at exactly this point.

Where you wrap COALESCE also got checked for real.

  • COALESCE(SUM(o.amount), 0) - wrapped around the aggregate. Produces 0 when the whole group is empty. This is usually the right spot
  • SUM(COALESCE(o.amount, 0)) - wrapped before aggregation. Same answer in this dataset, different meaning. They diverge when NULL amounts are actually stored
  • SQLite has TOTAL(), which returns 0 even for an empty group. Other engines do not have it, so keep it out of portable queries
  • Letting a NULL escape upward makes the outer aggregate quietly wrong. The combination where totals are right and only averages are wrong is especially dangerous
  • Asking can this value be NULL once per report column stops most of it

7. Chain three joins and a filter in the middle kills the tail

With three tables the trap propagates. Two LEFT JOINs: customers to orders, orders to shipments.

SELECT c.customer_id, c.name, o.order_id, o.status, s.carrier
FROM customers c
LEFT JOIN orders    o ON c.customer_id = o.customer_id
LEFT JOIN shipments s ON o.order_id    = s.order_id
ORDER BY c.customer_id;

  customer_id  name  order_id  status     carrier
  -----------  ----  --------  ---------  -------
  1            Ada   101       paid       ACME
  2            Ben   102       paid       ACME
  3            Cara  103       paid       NULL
  4            Dan   104       paid       BOLT
  5            Eve   105       pending    NULL
  6            Finn  106       cancelled  ACME
  7            Gus   NULL      NULL       NULL
  8            Hana  NULL      NULL       NULL
  9            Ivan  NULL      NULL       NULL
  10           Joy   NULL      NULL       NULL
  rows: 10

Ten rows. Customer 3 has an order but no shipment, so only carrier is NULL; customers 7 through 10 have no order, so everything downstream is NULL. Missing data appears at a different position in each layer - that is the character of this shape.

Now put a condition in two different places. One on the last table, one on the middle table.

-- filter on the LAST table
... LEFT JOIN shipments s ON o.order_id = s.order_id
WHERE s.carrier = 'ACME';

  customer_id  name  order_id  status     carrier
  -----------  ----  --------  ---------  -------
  1            Ada   101       paid       ACME
  2            Ben   102       paid       ACME
  6            Finn  106       cancelled  ACME
  rows: 3

-- filter on the MIDDLE table
... LEFT JOIN shipments s ON o.order_id = s.order_id
WHERE o.status = 'paid';

  customer_id  name  order_id  status  carrier
  -----------  ----  --------  ------  -------
  1            Ada   101       paid    ACME
  2            Ben   102       paid    ACME
  3            Cara  103       paid    NULL
  4            Dan   104       paid    BOLT
  rows: 4

A condition on the last table takes ten rows down to three. Customer 3, who had no shipment, and the four with no order all vanish together. In other words, a filter at the tail disables both LEFT JOINs upstream of it.

A condition on the middle table gives four rows. But this one carries an extra loss. Customer 6 had a shipment attached to a cancelled order, and when the order was filtered out that shipment record disappeared from the result too. Data from a table you never filtered went missing.

Now move both conditions into ON.

SELECT c.customer_id, c.name, o.order_id, o.status, s.carrier
FROM customers c
LEFT JOIN orders    o ON c.customer_id = o.customer_id AND o.status  = 'paid'
LEFT JOIN shipments s ON o.order_id    = s.order_id    AND s.carrier = 'ACME'
ORDER BY c.customer_id;

  customer_id  name  order_id  status  carrier
  -----------  ----  --------  ------  -------
  1            Ada   101       paid    ACME
  2            Ben   102       paid    ACME
  3            Cara  103       paid    NULL
  4            Dan   104       paid    NULL
  5            Eve   NULL      NULL    NULL
  6            Finn  NULL      NULL    NULL
  7            Gus   NULL      NULL    NULL
  8            Hana  NULL      NULL    NULL
  9            Ivan  NULL      NULL    NULL
  10           Joy   NULL      NULL    NULL
  rows: 10

Ten rows are preserved. Customer 4 kept a paid order but the carrier does not match, so only carrier went NULL. Each layer of condition acts on its own layer. This is how you hold on to the intent of seeing the absent rows across three tables.

  • A condition belongs to its own layer. A downstream predicate in WHERE disables the upstream LEFT JOINs along with it
  • The longer the chain, the larger the damage. In a three-table join, one condition on the last table took 10 rows to 3
  • Data from a table you never filtered disappears too. Filtering the middle table also removes the downstream rows hanging off it
  • Move them into ON and the layers become independent. You get rows like customer 4 that pass the first layer and go NULL only at the second
  • For a chain, run the probe per layer. Narrowing down with a per-layer COUNT finds the guilty join fastest

8. RIGHT JOIN and FULL OUTER JOIN - the same trap, reversed

I checked whether reversing the direction reverses the problem. SQLite added RIGHT JOIN and FULL OUTER JOIN in 3.39.0, released 25 June 2022, and this environment is 3.49.1, so both run.

I inserted one order whose customer id does not exist in the customer table, to make the directional differences visible.

--- SQLite 3.49.1, same data ---
  RIGHT JOIN, no filter        : 10 rows
  RIGHT JOIN + WHERE           :  4 rows
  FULL OUTER JOIN, no filter   : 10 rows
  FULL OUTER JOIN + WHERE      :  4 rows

--- now insert one orphan order (customer_id 99 does not exist) ---
INSERT INTO orders VALUES (107, 99, 'paid', 500.0, '2026-07-25');

  LEFT JOIN             : 10 rows   <- orphan invisible
  RIGHT JOIN            :  7 rows   <- 6 orders + orphan, customers 7-10 gone
  FULL OUTER JOIN       : 11 rows   <- 10 customers + orphan
  FULL OUTER + WHERE o  :  5 rows   <- WHERE on the right table
  FULL OUTER + WHERE c  :  3 rows   <- WHERE on the LEFT table also collapses it

With FULL OUTER JOIN, a condition on either side causes the collapse. A right-table condition in WHERE took 11 rows to 5; a left-table condition took 11 rows to 3. It preserves both sides, so both sides are vulnerable.

By direction:

JoinSide preservedWith a right-table predicate in WHERESupport here
LEFT [OUTER] JOINLeftBecomes an inner join (10 → 4)All versions
RIGHT [OUTER] JOINRightBecomes an inner join (10 → 4)From 3.39.0 (2022-06-25)
FULL OUTER JOINBothEither side collapses it (11 → 5, 11 → 3)From 3.39.0
INNER JOINNoneNothing happensAll versions
  • RIGHT JOIN is only reversed. It preserves the right table, and a left-table predicate in WHERE causes the identical collapse
  • FULL OUTER JOIN is vulnerable on both sides. A predicate on either table in WHERE breaks that side of the preservation
  • Insert one orphan row and the directions separate clearly. LEFT gives 10 rows and cannot see the orphan; RIGHT gives 7 and cannot see four customers
  • In SQLite these two joins are available only from 3.39.0 onward. If old builds are in the mix, check the version first

9. What the query plan tells you

Does the optimizer actually perform this transformation? EXPLAIN QUERY PLAN answers it.

EXPLAIN QUERY PLAN <query>;

-- 1. LEFT JOIN, no filter
   SCAN c
   BLOOM FILTER ON o (customer_id=?)
   SEARCH o USING AUTOMATIC COVERING INDEX (customer_id=?) LEFT-JOIN

-- 2. LEFT JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

-- 3. LEFT JOIN + ON ... AND o.status = 'paid'
   SCAN c
   BLOOM FILTER ON o (status=? AND customer_id=?)
   SEARCH o USING AUTOMATIC PARTIAL COVERING INDEX (status=? AND customer_id=?) LEFT-JOIN

-- 4. INNER JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

Plans 2 and 4 are identical. A LEFT JOIN with a WHERE and a query written as an INNER JOIN from the start produced character-for-character the same plan. And crucially, the LEFT-JOIN marker present in plans 1 and 3 is gone from plan 2.

The drive order flipped as well. Plans 1 and 3 start with SCAN c and walk the customers; plans 2 and 4 start with SCAN o and walk the orders. Once the constraint to preserve every customer is gone, starting from the smaller table is the better plan. Adding an index did not change the conclusion.

CREATE INDEX idx_orders_customer ON orders(customer_id);

-- LEFT JOIN, no filter
   SCAN c
   SEARCH o USING COVERING INDEX idx_orders_customer (customer_id=?) LEFT-JOIN

-- LEFT JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

-- INNER JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

How to use this output in practice:

  • Look for the LEFT-JOIN marker in the plan. If it is gone, the optimizer is already treating the join as inner
  • Look at whether the driving table changed. A plan that used to walk the left table first and now walks the right one is signalling that the preservation constraint disappeared
  • Compare against the plan of the INNER JOIN rewrite. If the two plans match, the two queries are the same query
  • This check touches no data, so it is safe to run against a production database

10. The OUTER keyword, USING, and constant predicates

I checked the surrounding syntax too. First, what does the OUTER keyword change?

--- does the OUTER keyword change anything ---
  LEFT JOIN       rows: 10
  LEFT OUTER JOIN rows: 10
  result sets identical : True
  query plans identical : True

--- the inner-join spellings, same data ---
  JOIN        :  6 rows
  INNER JOIN  :  6 rows
  CROSS JOIN  :  6 rows   (SQLite accepts ON after CROSS JOIN)
  comma join  :  6 rows   (FROM customers c, orders o WHERE c.customer_id=o.customer_id)

Nothing. The result sets match and even the plan strings match. OUTER is optional, and LEFT JOIN is already an outer join. In the other direction, JOIN, INNER JOIN and the comma join all gave the same six rows.

The USING clause carries the same trap unchanged.

SELECT customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o USING (customer_id)
ORDER BY customer_id;
  rows: 10

-- append the filter to WHERE and the same collapse happens
LEFT JOIN orders o USING (customer_id) WHERE o.status = 'paid'
  rows: 4

-- there is no place to put an extra predicate inside USING
LEFT JOIN orders o USING (customer_id) AND o.status = 'paid'
  ERROR: near "AND": syntax error

-- which side does the merged column come from on an unmatched row?
SELECT customer_id, c.customer_id AS from_left, o.customer_id AS from_right
FROM customers c LEFT JOIN orders o USING (customer_id)
WHERE o.order_id IS NULL;

  customer_id  from_left  from_right
  -----------  ---------  ----------
  7            7          NULL
  8            8          NULL
  9            9          NULL
  10           10         NULL
  rows: 4

Two things stand out. One, appending the WHERE collapsed it to four rows just the same. Two, USING has no place to accept an extra predicate. Adding AND is a syntax error. So the moment you write USING, the option of moving the condition into ON is gone. To keep the condition you must switch to ON or pull it into a subquery.

Constant predicates show the difference between the two clauses most sharply.

--- constant predicates, to isolate what each clause does ---
  ON c.customer_id=o.customer_id AND 1=1  : 10 rows
  ON c.customer_id=o.customer_id AND 1=0  : 10 rows   <- still 10
  ON 1=1 (no join key at all)             : 60 rows   <- 10 x 6 cartesian
  WHERE 1=1                               : 10 rows
  WHERE 1=0                               :  0 rows   <- everything gone
  WHERE c.region='north' (LEFT table!)    :  3 rows

--- ON ... AND 1=0 keeps every left row and nulls the right side ---
  customer_id  name  order_id
  -----------  ----  --------
  1            Ada   NULL
  2            Ben   NULL
  3            Cara  NULL
  ...
  10           Joy   NULL
  rows: 10

ON ... AND 1=0 keeps all ten rows. Nothing pairs at all, yet every left row survives and only the right side goes NULL. WHERE 1=0, by contrast, gives zero rows. The same false predicate reads as do not pair in one clause and as discard everything in the other.

  • OUTER changes nothing. Result sets matched and plan strings matched
  • JOIN, INNER JOIN and the comma join all gave the same six rows. SQLite even accepted ON after CROSS JOIN with the same result
  • USING has no syntactic slot for an extra predicate. The escape hatch of moving the condition into ON is closed, so prefer ON from the start on any join that will carry a filter
  • On an unmatched row the merged USING column returned the left-hand value. So that column cannot be used to detect a miss. Use a different column of the right-hand table
  • The gap between ON ... AND 1=0 and WHERE 1=0 shows the division of labour directly. Ten rows against zero

11. Filtering in a subquery or CTE instead

As conditions grow, the ON clause gets hard to read. The alternative is to push the condition inside a subquery or CTE and join the result.

SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN (SELECT * FROM orders WHERE status = 'paid') o
       ON c.customer_id = o.customer_id
ORDER BY c.customer_id;
  rows: 10

--- three spellings that must agree, and do ---
  ON       : 10 rows
  subquery : 10 rows
  CTE      : 10 rows
  all three identical : True

--- and four that are not the same thing ---
  WHERE o.status='paid'                        :  4 rows
  WHERE o.status='paid' OR o.order_id IS NULL  :  8 rows
  EXISTS (paid order)                          :  4 rows
  NOT EXISTS (paid order)                      :  6 rows

All three spellings gave ten rows with identical values. The script compared the result sets directly and they came back equal. When there are several conditions, or when the subquery needs its own aggregate, this shape reads better.

These four lines are four different questions, and it is worth being explicit about that.

  • ON, subquery and CTE gave the same result. Pick whichever reads better
  • With three or more conditions, or when the subquery needs its own aggregate, the CTE is far easier to read
  • WHERE ... OR ... IS NULL is not the same as moving the condition into ON. It gave eight rows: rows with a non-qualifying partner come back to life
  • If all you need is existence, EXISTS is more precise. A join can multiply rows; EXISTS cannot

12. Why date ranges trigger this more than anything else

One place produces this bug more than any other: the date range. Monthly and weekly reports almost always carry a period condition, and the table that condition sits on is almost always the right-hand table.

--- a date range is the most common way to trip this ---
  no filter                                     : 10 rows
  WHERE o.ordered_at >= '2026-07-01'            :  5 rows
  ON ... AND o.ordered_at >= '2026-07-01'       : 10 rows
  WHERE o.ordered_at BETWEEN Jul01 AND Jul31    :  5 rows
  WHERE (o.ordered_at >= Jul01 OR o.id IS NULL) :  9 rows

-- the WHERE version drops two different populations at once:
--   the 4 customers with no order, and the 1 customer whose only order is from June.
-- the OR ... IS NULL version brings back the 4 but still hides the June customer.

The WHERE version discards two kinds of row at once. The four customers with no order, and the one customer whose only order fell in June and thus outside the range. The first four leave some chance of being noticed; the last one is a customer with no activity this month and is far harder to find.

The common workaround, OR ... IS NULL, only half works. It gave nine rows. The four with no orders came back, but the June customer is still hidden. It is not the same as moving the condition into ON.

I built it as an actual report and ran both versions side by side. The symptom from the introduction reproduces here exactly.

-- the report, WHERE version
SELECT c.region,
       COUNT(DISTINCT c.customer_id) AS customers_in_report,
       COALESCE(SUM(o.amount), 0)    AS revenue
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = 'paid'
GROUP BY c.region ORDER BY c.region;

  region  customers_in_report  revenue
  ------  -------------------  -------
  east    1                    300
  north   2                    165
  south   1                    80
  rows: 3

-- the report, ON version
LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.status = 'paid'

  region  customers_in_report  revenue
  ------  -------------------  -------
  east    2                    300
  north   3                    165
  south   3                    80
  west    2                    0
  rows: 4

-- revenue per region is identical. the customer counts are not,
-- and the whole 'west' region is missing from the first report.

Revenue per region is identical in both versions. That is why it passes an accounting check. What differs is the customer count: north reads 2 against 3, south reads 1 against 3. And the west region is simply absent from the WHERE version. Nobody reading a report easily notices that a zero-revenue region stopped appearing.

  • A period condition almost always lives on the right-hand table. Customers have no period; orders do. Report queries are structurally exposed to this
  • Two kinds of row go missing. Rows with no partner, and rows whose partner falls outside the period. The second kind is much harder to find
  • OR ... IS NULL is a partial workaround. It revives the partnerless rows and still hides the out-of-period ones
  • The money totals agree between versions. That is why accounting reconciliation passes. Only the count metrics diverge
  • A whole zero-revenue category drops out of the table. Here the west region vanished. Few people notice a row that is not there

13. Diagnosis - finding it in a query that already shipped

Now the reverse direction: find this bug in a query that is already running. Three steps.

--- probe 1. how many rows does the WHERE remove? ---
  driving table rows       : 10
  after LEFT JOIN          : 10
  after WHERE              : 4
  lost by the WHERE clause : 6  (60%)

--- probe 2. unmatched ratio, straight from the join ---
SELECT COUNT(*)                                           AS joined_rows,
       SUM(CASE WHEN o.order_id IS NULL THEN 1 ELSE 0 END) AS unmatched_rows,
       ROUND(100.0 * SUM(CASE WHEN o.order_id IS NULL THEN 1 ELSE 0 END)
             / COUNT(*), 1)                               AS unmatched_pct
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;

  joined_rows  unmatched_rows  unmatched_pct
  -----------  --------------  -------------
  10           4               40
  rows: 1

--- probe 3. the one that settles it ---
SELECT (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
          ON c.customer_id=o.customer_id)                        AS rows_join_only,
       (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
          ON c.customer_id=o.customer_id WHERE o.status='paid')  AS rows_with_where,
       (SELECT COUNT(*) FROM customers c JOIN      orders o
          ON c.customer_id=o.customer_id WHERE o.status='paid')  AS rows_if_inner;

  rows_join_only  rows_with_where  rows_if_inner
  --------------  ---------------  -------------
  10              4                4
  rows: 1

-- rows_with_where equals rows_if_inner -> the word LEFT is doing nothing.

The third probe settles it. If rows_with_where equals rows_if_inner, the LEFT in that query is decoration. Equal numbers mean the intent to preserve the left table is not being executed.

Read the second probe alongside it. Here unmatched_pct was 40 percent. If that value is 0 on your development database, the bug will never reproduce there. A query validated against data with few gaps returns wrong numbers only against production data, where the gaps live.

The same probe works on a chain. And when sweeping a whole codebase, narrow it in two steps.

--- same probe on the three-table chain ---
  rows_join_only  rows_with_where  rows_if_inner
  --------------  ---------------  -------------
  10              3                3
  rows: 1

--- grep patterns for a code review sweep ---
# every LEFT JOIN in the repository, with the ten lines that follow it
grep -rn -A 10 -i 'left join' --include='*.sql' --include='*.py' .

# LEFT JOIN and WHERE in the same statement, single-line queries
grep -rn -iE 'left[[:space:]]+(outer[[:space:]]+)?join.*where' .

--- what to look at once you have the hits ---
# 1. does the WHERE mention an alias that is introduced by a LEFT JOIN?
# 2. if yes, is the predicate an IS NULL check? then it is intentional.
# 3. anything else -> run probe 3 above and compare the two numbers.

As a procedure:

What to checkHowVerdict
Does WHERE mention a right-hand aliasRead the query textIf yes, it is a candidate
Is that predicate IS NULLLook at the predicate shapeIf yes, a deliberate anti-join
Row count right after the joinDelete the WHERE and COUNT(*)The baseline
Row count after the WHERECOUNT(*) as writtenThe drop is the size of the gap
Row count rewritten as INNERDelete LEFT and COUNT(*)Equal to the WHERE result means confirmed
  • Step 1. Check whether the WHERE clause mentions an alias introduced by a LEFT JOIN. If it does not, this is not the bug
  • Step 2. If it does, check whether that predicate is IS NULL. If so, it is probably a deliberate anti-join
  • Step 3. Otherwise run probe 3 and compare rows_with_where against rows_if_inner. Equal means confirmed
  • Record the unmatched ratio alongside. At 0 percent the bug cannot reproduce, so validation has to happen on data resembling production
  • Fixing means choosing one of two things: move the condition into ON, or drop the LEFT and state INNER. Leaving it ambiguous is the worst option

15. The decision table - start from the intent

The conclusion is not put your conditions in ON. The two clauses do different jobs, and each has a place where it is right. What decides is not syntax but intent. Write the sentence you mean first, then pick the clause that says it.

What you mean to sayWhich clauseRows in this exampleHow to verify
Only the rows that matchWHERE, stated as INNER JOIN4No NULL right-hand rows in the result
Show the absent ones as zeroON10Result row count equals left table row count
Only the ones with no matching partnerON + WHERE ... IS NULL6Right-hand columns are all NULL
Only the ones with no partner at allWHERE ... IS NULL4Row count equals NOT EXISTS
Narrow the left tableWHERE on a left-table column3NULL right-hand rows are still present
The condition is too long to readSplit into a subquery or CTE10Rows and values match the ON version

The rules behind the table, compressed:

  • If you want the absent rows reported as zero, use ON. The result row count should equal the left table row count
  • If you want only the rows that exist, use WHERE. But then drop LEFT and write INNER JOIN. The intent stays in the code
  • If you want the rows with no qualifying partner, use ON plus WHERE ... IS NULL. This is the one common case for using both clauses together
  • A condition that narrows the left table stays in WHERE. It does not conflict with the LEFT JOIN behaviour
  • If you are unsure, run both versions and compare row counts. The numbers tell you which question you asked

16. Checklist, and what not to do

A list for review and self-checking.

  • For each report query, I checked which join introduced the alias the WHERE clause mentions
  • For queries using LEFT JOIN, I counted once whether the result row count equals the left table row count
  • I validated against data whose unmatched ratio is not zero. Seed data alone was not enough to pass
  • I did not use COUNT(*) directly for a count metric. I counted a right-hand table column
  • I decided once whether the SUM needed COALESCE. No NULL escaped into an outer aggregate
  • Where the condition belonged in WHERE, I dropped the LEFT and wrote INNER so the next reader is not misled

And the inverse.

  • Appending a right-table predicate as a WHERE under a LEFT JOIN - if it is intentional, write INNER
  • Reading it as a LEFT JOIN, so the left side all comes through - read the WHERE below it first
  • Validating report queries against gapless seed data - the bug cannot reproduce in that environment
  • Reporting it seems to have shrunk without counting rows - write the two numbers side by side
  • Treating OR ... IS NULL as equivalent to ON - eight rows and ten rows are different results
  • Trying to attach a predicate to a join written with USING - there is no slot for it. Rewrite with ON

# The LEFT JOIN + WHERE trap — decision table, diagnostic SQL, reproduction data

> Source: braindetox.kr — A WHERE clause turns your LEFT JOIN into an INNER JOIN
> Verified on: Windows 10 / SQLite 3.49.1 (CPython 3.13.3 sqlite3, Node.js v22.16.0 node:sqlite)
> Paste this file into an AI and say 「review our report queries against these rules」.
> ⚠ This bug raises no error. Only the row count shrinks, and it does not reproduce on a development database with few gaps.

## 0. One sentence

**ON decides what gets paired. WHERE decides what survives after pairing.**
The join runs first and manufactures NULL rows; the WHERE then tests those NULLs and erases the rows. So a predicate on a right-hand column, placed in WHERE, turns a LEFT JOIN into an INNER JOIN.

## 1. Decision table — start from the intent

| What you mean to say | Which clause | Rows in the example | How to verify |
|---|---|---|---|
| Only the rows that match | `WHERE` + state `INNER JOIN` | 4 | No NULL right-hand rows in the result |
| Show the absent ones as zero | `ON ... AND` | 10 | Result rows = left table rows |
| Only those with no matching partner | `ON` + `WHERE ... IS NULL` | 6 | Right-hand columns are all NULL |
| Only those with no partner at all | `WHERE ... IS NULL` | 4 | Row count equals `NOT EXISTS` |
| Narrow the left table | `WHERE` on a left-table column | 3 | NULL right-hand rows still present |
| The condition is too long to read | Split into a subquery or CTE | 10 | Rows and values match the ON version |

## 2. What each clause does

| Aspect | `ON` | `WHERE` |
|---|---|---|
| When it is evaluated | While the join is being built | After the join is finished |
| What it decides | What gets paired | What survives after pairing |
| Left row with no partner | Kept, right side filled with NULL | Discarded unless the predicate holds |
| Difference in an inner join | None | None |
| Query plan | `LEFT-JOIN` marker stays | The marker disappears |

## 4. Four ways to write it, and the real row counts (verified)


## 6. Aggregate cheat sheet — value for a group with no match

| Expression | Value | Consequence in practice |
|---|---|---|
| `COUNT(*)` | **1** | Zero orders is reported as one |
| `COUNT(o.order_id)` | **0** | Usually the number you want |
| `SUM(o.amount)` | **NULL** | Not zero. It spreads into outer math |
| `COALESCE(SUM(o.amount), 0)` | **0** | The recommended position |
| `AVG(o.amount)` | **NULL** | Outer averages lose divisor and inflate |

Verified case: on the same data both totals came out at 815 while the averages split into 135.83 and 81.50. **Reconciling totals alone does not catch this.**

## 7. Sentences to paste straight into a code review

- 「Which join introduced the alias this WHERE mentions? If it is a LEFT JOIN, please count whether the result rows equal the left table rows.」
- 「If the condition belongs in WHERE, drop the LEFT and write INNER JOIN. The next reader will misread the intent otherwise.」
- 「What is the unmatched ratio in the data you validated this report against? At 0 percent the query is effectively unvalidated.」
- 「Should this be counting a right-hand table column rather than COUNT(\*)? Groups with no match are being reported as one.」
- 「This SUM can leave as NULL. Please decide whether COALESCE belongs around the aggregate.」
- 「The period condition sits on the right-hand table. Anything with no activity this month drops out of the report entirely.」
