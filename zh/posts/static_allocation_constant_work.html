让最坏情况保持恒定，和让平均值变快，是两个不同的目标 - 静态分配与恒定工作量

如何分辨有截止时间的工作、每种手法各自换来什么又付出什么、以及真正用来确认的那个指标

2026-09-05 开发/基础设施

说性能改善了，通常就是说变快了。可是在某些场合，变快根本不是目标。每一次都花同样的时间才是目标。平均值哪怕降了一半，只要一百次里有一次跳到十倍，在那种场合这不是改善而是恶化。

这篇文章要看的，是这两个目标有什么不同，以及为什么它们通常互相削弱。这不是一篇内存分配技巧的合集。它讲的是去掉运行期分配这个决定究竟买了什么、又卖了什么，以及这笔交易的结果该用哪个指标去确认。

缘起 - 原文说了什么，又没说什么

2026年9月2日，matklad 发表了 Static Allocation, Constant Work。篇幅不长，示例代码是 Zig，用订单撮合引擎来打比方。不过作者本人写明自己对订单撮合引擎只有模糊的理解，只是猜测这些手法在那里可能有用。所以这篇文章更适合当成两种设计习惯来读，而不是某个领域的处方。

第一种习惯是静态分配。启动时按上限一次取够，之后不再取。原文的例子把上限交给命令行参数，用 const orders: []Order = try gpa.alloc(Order, cli_args.orders_max); 一次预留完。而且运行期如果来的请求超过上限，多出来的请求就被拒绝。理由说得很直白。按原文的说法，为了多分配一条订单，内核的 OOM 杀手可能把整个订单撮合引擎杀掉，让另外一百万条订单一起丢失，更糟的是连监管进程也一起死掉，连重启都做不到。

第二种习惯是恒定工作量。不要用索引或位集单独追踪存活的对象，而是始终完整遍历一个定长数组。空着的位置上放一个什么都不做的中性状态。在原文的例子里，订单的标签取 bid、ask、reserved 三个值，最后那个就是中性状态。

启动时按上限预留，运行期拒绝超出的请求这个上限究竟该依据什么算出来
完整遍历对向量化和缓存预取都要有利得多支撑这个说法的测量值或基准数据
P100 延迟不随负载变化，始终平坦关于 P99 或中位数等其他分位的任何提法
对象池是一个标签联合，标签表示当前住在这个槽位里的是第几代对象竞技场分配器，环形缓冲区

这是值得放进武器库的一个手法，而不是所有编程问题的万能解功耗或电池成本

这里有一点需要说清楚。原文说保持平坦的是P100 而不是 P99。P99 是丢掉最慢的百分之一之后的最大值，P100 什么都不丢，是真正的最大值。经过转述之后这个区分很容易糊掉，而下一节会看到，在有截止时间的工作里，被丢掉的那百分之一恰恰就是出问题的那百分之一。

有截止时间的工作和没有的工作

为什么恒定会成为目标，得先把工作分类才看得出来。判据只有一条。如果结果没能在某个固定时刻之前出来，这个结果是不是就没用了。是的话，这份工作有截止时间；不是的话，就没有。

有截止时间那一侧的典型是音频回调、游戏的每一帧，以及驱动机器的控制回路。音频设备在固定时刻索要下一段缓冲，那时候数据不在，就会填入静音，声音随之断掉。已经过去的那一刻的声音，事后补出来也没有意义。迟到结果的价值是零，甚至是负的。这条轴线原文里没有。原文既没提截止时间，也没提音频或游戏。

不过操作系统那边的文档很早就把这个性质记了下来。Linux 的 mlockall(2) 说明写道，实时应用要求确定性的时序，而和调度一样，分页是造成程序执行出现意外延迟的主要原因之一。同一份文档还更进一步：使用 mlockall() 来避免缺页延迟的实时进程，应当在进入时间关键区之前预留足够多的已锁定栈页，这样函数调用也不会引发缺页。为什么把内存提前全部取好是可预测性的问题而不是速度的问题，答案就在这两句话里。

/* 进入实时区之前，锁住当前和将来的所有映射 */
mlockall(MCL_CURRENT | MCL_FUTURE);
该问的问题有截止时间没有截止时间
迟到结果的价值是零，甚至有害迟到也不影响价值
延迟如何堆积推迟下一个周期，逐次累积由队列吸收
重试不可能，或者没有意义可行而且常见
该看的统计量最大值和超时次数平均值、中位数、吞吐量
改善的定义超时次数收敛到零单位时间内处理得更多
失败的样子声音断掉，画面卡顿感觉有点慢
空余资源的用途空着不用，只为压低最坏情况填满，用来提高处理量

最后一行是实务中最容易谈不拢的地方。面对同样空闲的 CPU，有截止时间的系统会把它空着，用来防备最坏情况，没有截止时间的系统会把它填满，用来提高吞吐。两个团队看着同一块面板得出相反结论，原因就在这里。

平均值和最坏情况为什么互相削弱

能降低平均值的手法，多数都是同一个形状。现在不付出代价，攒到以后一次性付。缓存是这样，延迟初始化是这样，数组按倍数扩容是这样，分代垃圾回收也是这样。绝大多数调用变得很便宜，偶尔有一次变得非常贵。总量下降，最大值上升。

这笔交易在只看平均值的面板上结构性地看不见。收益落在图里，代价落在图外。所以有截止时间的系统的风格指南，往往会把这一点明确钉死。TigerBeetle 的风格指南写着给一切都加上限，并举例说所有循环和所有队列都必须有固定的上界，以防止无限循环或尾部延迟尖刺。它把没有上界的循环和没有上界的队列，并排放在尾部延迟的成因位置上。

反方向同样成立。恒定工作量是故意把平均值做差的。活跃条目只有十个，却把一百个槽位全部走一遍，那就有九十次是白扔的工。总工作量上升，平均值跟着上升。换来的是十个的情形和一百个的情形变成同一种情形。原文关于 P100 的那句话说的正是这笔交易。它不是把最坏情况压低了，而是把最坏情况变成常态，因而变平了。

还有一样东西是白送的，原文把它和性能收益并列写出来。性能不够这件事，会在系统上线时暴露，而不是在旺季凌晨的值班电话里。因为没有负载时它做的活和满负载时一样多。从这个意义上说，恒定工作量与其说是性能手法，不如说更接近可观测性手法。

去掉运行期分配之后，什么消失了

把「运行期不分配」这条规则守住之后会消失哪些东西，最好一项一项数出来。数完了才能反过来数清楚，自己的系统里究竟有过其中几项。

  • 分配调用本身的可变开销 — 要同样多的字节，两次花的时间未必一样。刚好有合适大小的空闲块就便宜，需要切分或合并就贵，得向内核新要一块就贵得多。没有运行期分配，这整个分布都不见了
  • 在分配器前面排队 — 多个线程同时敲同一个分配器时，总得在某处决定先后。没人去调用，也就没人去排队
  • 缺页 — 新拿到的内存第一次触碰时内核要介入。前面引的 mlockall(2) 说明把分页点名为意外延迟的主要成因，说的就是这一处。启动时取好并挨个碰一遍，这份开销就挪到了启动阶段
  • 垃圾回收器的介入 — 不分配就没有触发回收的压力。不过在有垃圾回收的语言里这层关系没那么简单，所以放到第十节单独看
  • 碎片带来的尾部延迟 — 进程跑得越久，越难拿到大块连续内存。这份开销一开始没有，几天之后才出现，所以短时间的测试几乎抓不住
  • 释放后使用的一个分支 — TigerBeetle 的风格指南把避免释放后使用和性能不可预测并列，作为静态分配的理由。既没有释放也没有重新分配，指向已释放内存的指针这个概念本身就萎缩了

还有一样不在清单上的东西也消失了，那就是失败的时刻。启动时就按上限取够，机器上没有那么多余量的话，进程一启动就死。在部署之后立刻死掉，几乎总是比四天后凌晨三点死掉更好。TigerBeetle 的风格指南之所以钉死所有内存都必须在启动时静态分配，初始化之后不得动态分配任何内存，也不得释放后重新分配，一半的理由就在这里。

恒定工作量把什么反转了过来

按通常的直觉，「只做该做的活」才是美德。单独维护一份存活条目的清单，只遍历那份清单。原文把这个直觉反转过来。走完整个数组，空位上放一个不会改变结果的中性值。

// 原文不推荐的一侧 - 沿着活跃索引走
for (orders_active) |order_index| {
    const order = orders[order_index];
    process(order);
}

// 原文推荐的一侧 - 无条件走完每一个槽位
for (orders) |order| {
    process(order);
}

原文给出的理由有两个。上面那种写法先读一个索引，再拿这个值回到数组里去找，每个条目要两次有依赖的访问。下面那种则是把内存从前往后顺着扫一遍。按原文的说法，下面这种对编译器做向量化、对 CPU 缓存做预取都要容易得多。而且它做的活和存活条目的数量无关，所以P100 延迟不随负载变化，始终平坦。

设计中性状态比看上去麻烦。正确性排在速度前面。

  • 中性值不能改变结果。求和取零，求积取一，求最小值就取可表示的最大值
  • 中性槽位一旦混进聚合，程序不会崩，而是安静地给出一个错的数。这类缺陷比性能问题活得久得多
  • 要复用槽位就必须区分代次。这正是原文把对象池看成以槽位中对象的代次为标签的标签联合的原因。漏掉代次，旧引用就会指向新对象
  • 只有当处理中性槽位的开销和处理真实条目差不多时，这笔交易才成立。中性便宜太多，全遍历就是纯浪费；中性反而更贵，那就完全说不通
  • 数组大到装不进缓存时，全遍历反而是亏的。预取的好处出现在你确实会用到所走过的那段连续内存的时候
  • 原文没有讨论分支预测。分支并没有消失，只是处理中性状态的那个分支挪进了循环内部

原文把同样的思路也用在带提前返回的查找循环上。像 const item = for (items) |item| { if (predicate(item)) break item; } else null; 这样找到就跳出的写法，对平均值有好处，但耗时取决于数据。全部扫一遍则永远花同样的时间。这同样是卖掉平均值去买恒定。

逐项手法的交易 - 换来什么、失去什么、看哪个指标

静态分配这个词底下，捆着几种性格相当不同的手法。把每一种各自给什么、拿走什么，尤其是用什么去确认它真的在起作用都写出来，选的时候就不会乱。竞技场和环形缓冲区在原文里没有出现，因为属于同一族手法，所以并排放在这里。

环形缓冲区这一行的细节，Linux 内核文档里写得清清楚楚。头是生产者往缓冲区里插入条目的位置，尾是消费者找到下一个条目的位置。缓冲区取二的幂大小时，回绕可以改用快得多的按位与指令。而且头指针比尾指针小一的时候就是满，也就是说永远要空出一个位置来区分满和空。要做到无锁，必须只有一个生产者和一个消费者，并且不是用一把锁去管住两端，而是生产者侧用 smp_store_release()、消费者侧用 smp_load_acquire() 来保证次序。

代价一 - 上限该怎么定

静态分配的第一个代价是必须事先知道上限。原文把这个问题推到了代码之外，因为上限是从命令行参数进来的。这在某种意义上是对的，上限取决于部署环境而不是代码，本来就不该写死成常量。但这个值该依据什么定出来，原文里没有。

  • 先找物理上限：机器的内存容量、文件描述符上限、网络队列深度。比它更大的业务上限没有意义
  • 再找业务上限：并发连接数、未结订单数、打开的会话数的实测值。要看观测到的最大值，不是平均值
  • 观测窗口一短，最大值永远是低估的。窗口里至少要包含一次旺季
  • 不要把上限写进代码，放进配置。同一个二进制要能跑在大机器上，也能跑在小机器上
  • 把触达上限的次数作为指标暴露出来。不去数触达次数，就分不清这个值究竟是上限还是随手写的一个大数
  • 在上限的某个比例处另设告警线。触达之后才知道就晚了
  • 把上限定得很大也不是免费的。始终占着最大量，就意味着同一台机器上放不下别的东西

如果还要把内存锁住，就又多一层约束。mlockall(2) 文档写道，自 Linux 2.6.9 起对特权进程能锁多少内存不再设限，而RLIMIT_MEMLOCK 这个软资源上限转而定义非特权进程可以锁定多少内存。文档还明确写着，若指定了 MCL_FUTURE，那么之后的 mmap、sbrk、malloc 一旦会让已锁定字节数超过允许的最大值，就可能失败。也就是说上限的设计不会在应用内部收尾，它和部署环境的资源上限是咬合在一起的。

代价二 - 溢出的时候做什么

第二个代价更重。越过上限之后，没有优雅失败的办法。准确地说，上限之内一切优雅，上限之外只有五个选项，而且没有一个是「无论如何都全部处理掉」。

  • 立即拒绝 — 原文的选择。只有调用方有重试策略时才有意义，没有的话就只是丢失。拒绝并没有消除问题，只是把问题交给了调用方
  • 让它等 — 前面放一个队列让人等。可是那个队列也需要上限。没有上界的等待队列，等于把刚刚加上的上限又拆掉了
  • 丢掉最旧的 — 环形缓冲区里常见的选择。适合只有最新状态才有意义的数据，比如传感器读数或者画面刷新
  • 丢掉最新的 — 适合次序本身带有含义的数据。保住先进来的，把后面截掉
  • 降级运行 — 降低精度或者关掉部分功能，继续接收。这是有截止时间的系统里最常见的答案，在那种场合，准时的近似值胜过迟到的准确值

动态分配一个都不选，而是去模仿那个「无论如何」。模仿走到尽头的地方站着 OOM 杀手。正如原文所指出的，那时候丢掉的不是溢出的那一条，而是正在处理的全部，最坏的情况连重启的路径也一并丢掉。设上限这个选择的本质，不是消除失败，而是挑选失败的形状。

所以真正要回答的问题不是「拒不拒绝」，而是丢什么、什么时候丢，并且把这个答案写在代码里显眼的地方。这是静态分配的实质好处之一。在动态取内存的代码里，这个决定哪里都没写，所以从来没人评审它。

代价三 - 没活干也照样满负荷干

第三个代价已经写在名字里了。恒定工作量就是说没有负载的时候也干着满负载的活。这看上去纯是好处，只有在专用机器上、守住截止时间是唯一目标的时候才成立。

  • 靠电池运行的设备 — 空闲不再是空闲。屏幕关着，同一个循环照样在转
  • 按用量计费的环境 — CPU 时间就是钱。为了买一条平坦的最大值曲线，得一直付满额的费用
  • 共享机器 — 自己的空闲开销变成邻居进程的延迟。没有隔离的话，账是邻居替你付
  • 有散热约束的设备 — 长期满负荷会招来降频，于是本来想守住的那个截止时间反而开始晃动
  • 专用机器上截止时间是唯一目标时 — 这份开销根本看不见。反正也没打算拿那颗 CPU 干别的

原文里没有功耗或电池的内容。上面这份清单是从结构里推出来的代价，支撑它的公开测量值没能得到确认（见第十三节）。所以在自己的环境里，把应用前后的空闲 CPU 使用率各测一次，才是靠得住的做法。

也有缓和的变体。不走整个数组，而是每个周期只扫固定数量的槽位，下个周期接着往下走。最大值仍然是常数，空闲开销降下来了。代价是单个条目被处理之前的延迟上界，会随数组大小成比例地变长。截止时间是按条目算还是按周期算，决定了这个变体是不是答案。

在有垃圾回收的运行时里会怎样

运行期不分配这条规则，前提是手动管理内存的语言。在有垃圾回收器的运行时里，光是少分配并不会让回收器消失。方向仍然一致，理由写在 Go 官方的 GC 指南里：GC 的 CPU 开销主要由分配速率和扫描内存的每字节成本决定。

看看指南列出的五项延迟来源，就明白分配速率为什么这么关键。第一，GC 在标记与清扫阶段之间切换时的短暂全停顿；第二，标记阶段 GC 占用百分之二十五的 CPU 资源所带来的调度延迟；第三，为应对高分配速率，用户协程要替 GC 分担工作；第四，标记阶段中指针写入需要额外的工作；第五，正在运行的协程必须被挂起以便扫描其根。第三项是关键：大量分配的代码是在自己制造自己的延迟。

# 用肉眼看见 GC 在干活的最省事的办法
GODEBUG=gctrace=1 ./myserver

在设上限这一侧也有同样的张力。Go 的内存上限是软上限。按指南的说法，Go 运行时不保证在所有情况下都维持这个内存上限，它只承诺付出某种程度的合理努力。放松的理由写得很明白：正是这种放松对避免抖动至关重要，因为它给了 GC 一条退路。具体机制是给 GC 能用的 CPU 时间设一个上限，目前大约是百分之五十，窗口是 2 * GOMAXPROCS 个 CPU 秒。

没有这条退路会怎样，同一份文档也写了。把 GOGC 关掉再不断压低上限，应用的总耗时会开始无限制地增长，因为 GC 在不停地运行，试图维持一个不可能的内存上限。还有一句像结论的话，和第八节的论点严丝合缝：在很多情况下，无限期的停顿比内存不足更糟，因为后者往往以快得多的失败收场。

归拢起来是这样。原文为了避开 OOM 杀手把上限设得很硬，Go 运行时为了避开无限期停顿把上限设得很软，这是同一个问题的两端。无论选哪一端，都还得回答「触到上限之后做什么」。旋钮本身倒是简单，按指南的说法，把 GOGC 翻倍会让堆内存开销翻倍，而 GC 的 CPU 成本大致减半。内存和 CPU 之间的交易被暴露在一个旋钮上。实测工具本身占多少内存和连接上限设错时会发生什么都另有整理。

搬到服务器上，哪些成立哪些不成立

这些原则是在截止时间很紧的地方长出来的。搬到服务器和 Web 后端之后，有些早就换了个名字在用，有些则根本不成立。

原则在截止时间很紧的地方在服务器与 Web 后端
启动时预留最大量物理内存是固定的，因此很自然在实例弹性伸缩的环境里，单台的最大量就是成本。但换成并发处理条数的上限，就完全成立
拒绝超出的请求没有别的选项直接成立。它以负载卸除之名，早就是标准做法
全部遍历数据结构小，装得进缓存基本不成立。遍历全体用户这种事装不进缓存
以 P100 为目标有截止时间，理所当然按请求计的截止时间很少见，实际目标通常是 P99 或 P99.9
去掉运行期分配语言允许这么做运行时替你做了。它换成降低分配速率的形式出现
给一切都加上限照原样适用照原样适用。队列深度、连接池、超时、重试次数说的都是同一件事
用中性状态填满槽位数组小，所以便宜基本不用。取而代之的是预先建好的连接和工作者池

搬得最顺的两条是给一切都加上限和超出的就拒绝。这两条与语言无关，而且在服务器这边早就换了名字在用。连接池大小、队列深度、超时、并发请求上限，全都是「给一切都加上限」的实例。TigerBeetle 的风格指南说，凡是程序与外部实体交互的地方，不要直接对外部事件作出反应去做事，而应让程序按自己的节奏运行，讲的也是同一件事，它给出的理由是这样更容易维持单位时间内工作量的上界。

搬得最不顺的是全部遍历。它的好处只在你确实会用到所走过的那段连续内存时才出现，而服务器的数据结构通常装不进缓存。夹在中间的是启动时预留最大量：把单个进程的内存钉死，在弹性环境里可能是亏的，但换成并发处理条数的上限就是净赚。

也有既不是嵌入式也不是游戏、却明确采用这条规则的例子。ggml 仓库把无第三方依赖、运行期零内存分配、支持整数量化写成了设计目标。一个推理库把运行期零分配挂成目标，理由不是炫耀速度，而更接近放到哪里都以同样的形态运行。硬件那边的约束会先替你决定什么，写在推理硬件的岔路口里；塞进极小设备时会遇到的问题，写在在八美元单片机上跑模型的案例里。内存安全该在多大程度上交给语言的那场争论，整理在围绕内存安全绝对主义的讨论里。

应该先测什么

以上是判断标准，实际动手的顺序很短。改代码之前，有些东西得先测。

第一步 - 先确定有没有截止时间

把这个系统里迟到的结果会失去价值的地方在哪里用一句话写下来。写不出来就说明没有截止时间，那本文的多数手法都不需要。如果有，就把那个时刻和可以容忍的超时次数写成数字。「应该要快」不是截止时间。

第二步 - 记录最大值

在平均值和中位数旁边，并排放上最大值和超时次数。缺了这两列的面板，看不见第三节讲的那笔交易。同时把在处理的条数、队列深度、池占用率的峰值也一并留下。定上限时要用的正是这些数。

第三步 - 加上限并统计触达次数

只给最大的那一个数据结构加上限，然后把触达上限的次数作为指标暴露出来。把代码改成静态分配是之后的事。触达次数为零说明上限定得宽，持续触达则说明上限偏小，或者上游放进来的量太多。这一个数字，就能替你做掉第七节和第八节的大部分决定。
