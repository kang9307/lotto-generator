起因 - 一年前的建议与 Pi 1.0 的 Codemode

这篇文章标注为「written on October 06, 2026」，作者是 Armin Ronacher。他回顾说，一年多以前写过几篇文章，建议不要把自定义工具或 MCP 服务器装进上下文，而是多用脚本。其中最重要的一篇是《Code Is All You Need》，另外还写过《MCP needs code》。然而 Pi 1.0 通过 Codemode 加入了对 MCP 的支持。作者写道，这在某种意义上早该发生，但对一些人来说也许有些意外，所以他想在这篇文章里分享更新后的想法。

  • 作者与日期：Armin Ronacher，2026 年 10 月 6 日。
  • 涉及的工具：Pi。作者写道 Pi 1.0 通过 Codemode 加入了 MCP 支持。
  • 本站的 Pi 1.0 文章讲 1.0 的整体功能，本文则沿着作者关于 Codemode 的论点展开。

工具是什么，bash 做不到什么

作者先厘清工具是什么。harness 给 LLM 提供可调用的工具时，会提供工具定义，这些定义在服务器端被转换成某种 token 结构。模型是否被鼓励去调用某个工具，是强化学习过程的结果，他说这个话题自己以前写过。

作者强烈倾向于 CLI 和 bash，理由有两个：调用容易组合，而且模型在训练时也学到了文件系统是怎么运作的。当模型调用 echo foo > /tmp/test.txt 这样的工具时，它同时也学到调用之后 /tmp 里有了一个叫 test.txt 的文件。

不过 bash 有一个根本的局限：它只能组合会运行的程序。作者写道，有些东西不是程序，对 LLM 来说却是原生工具，也只能是原生工具。

  • read 或 view_image：多模态模型需要读取图片时不能用 cat，因为 harness 需要把真正的图片载荷注入 LLM 的协议。
  • 子智能体：要创建并协调它们，很难避开 harness 提供的工具。理论上可以提供一个通过环境变量和 Unix 套接字与外层 harness 通信的 CLI 工具，但作者称之为相当粗糙的做法。
  • 代码在哪里运行：这种做法还有另一个问题，作者在下一节展开。

大脑与手 - harness 与执行环境

作者请读者想一想各个部分分别在哪里运行。通常有两个系统。第一个是大脑，也就是 harness：它运行在一台机器上，受到信任。第二个是手，往往是同一台机器，但那是工具真正执行的地方。Pi 现在把它称为执行环境，可以把它理解为所有操作的目标（target）。

重要的是，harness 这个大脑与运行 bash、执行工具的目标环境之间有一条分界线。作者写道，把它一分为二会带来重要的后果：二者运行在不同的文件系统上，信任级别也不同。比如使用 Gondolin 这类沙箱方案，bash 一侧会被很好地沙箱化，但 harness 本身不会。

部分作者的说明信任与隔离
大脑（harness）运行在一台机器上受信任
手（执行环境，target）往往是同一台机器，但是 bash 与工具真正运行的地方文件系统与 harness 不同，信任级别也不同
使用 Gondolin 这类沙箱时bash 一侧被沙箱化harness 本身没有被沙箱化

Codemode 做什么 - harness 一侧的沙箱

作者这样概括 Codemode 的作用：它是让 LLM 在 harness 一侧而不是执行环境一侧表达并协调复杂操作的方式。Codemode 在 harness 内部、自己的沙箱中运行。在 Pi 中，它是 WASM 运行时里的 QuickJS，并带有刻意设置的限制。

  • 没有网络。
  • 没有文件系统。
  • 没有计时器。
  • RAM 有限。

在这里面，代码唯一能做的就是调用更多工具。作者补充说，也可以想象让 Codemode 运行 Scheme 或别的语言。为了照顾不熟悉它的读者，作者这样说明：它基本上就是在某种语言内部发出工具调用的方法，这里的语言是 JavaScript。这样就可以不必经过 LLM 的上下文来组合这些调用。名字是 Cloudflare 起的，作者把这个功劳归给他们那边的朋友。

上下文里发生的变化

作者以一次 bash 调用为例。如果把 bash 作为普通工具调用发出，Pi 只会把末尾 2000 行放进上下文，智能体想看更多就得自己去看溢出文件。如果智能体通过 Codemode 发出同样的调用，Codemode 一侧会以结构化的方式收到更大的输出。

因为 Codemode 是 JavaScript，智能体可以表达并发操作和基本的工作流。作者现在常见智能体这样用：先从某个工具响应里探查 5 到 10 项，看看长什么样，然后写一个 Codemode 脚本去处理接下来的 n 项。

Codemode 还可以把状态放进会话记录。一次 Codemode 调用可以把数据藏起来，会话中的下一次调用再把它读回来。作者强调，这发生在 harness 主机上，而不是沙箱里。在 Pi 中，一些放在传统界面里没有意义的调用，比如用图像模型生成图片，或用单次分类器模型对文本分类，会通过 Codemode 暴露出来，而不会通过普通工具暴露，因为那样只会浪费上下文。

项目普通工具调用Codemode（作者的说明）
bash 的大输出只有末尾 2000 行进入上下文，其余进入溢出文件Codemode 一侧以结构化方式收到更大的输出
并发与工作流—因为是 JavaScript，可以表达并发操作和基本工作流
了解响应的形状—先探查 5 到 10 项，再写脚本处理其余部分
保存状态—把数据放进会话记录，下一次调用再读回（在 harness 主机一侧）
图像生成与分类器模型 API作为普通工具暴露只会浪费上下文只通过 Codemode 暴露

三个真实会话 - 图片、Issue 分类、游戏循环

作者展示了自己最近 Pi 会话中的 Codemode 调用。他说明这些代码都不是人写的，而是来自真实的 Pi 会话，只是重新缩进了一下。智能体开始自动使用 Codemode，要么是因为这类任务模型本来就会自然选择该工具，要么是因为用户要求。在 Pi 中，Codemode 默认只在启用 MCP 时开启，也可以在设置里的 defaultTools 中加入 "+codemode" 来开启。作者写道，直接让 Pi 帮你开启也行。下面的代码是作者的代码，只整理了空白，第二段有所省略。

生成图片

图像生成是 Pi 在 AI SDK 核心里支持的功能，但不是智能体可以使用的工具。过去使用图像模型的唯一办法，是自己写一个定制扩展，或者让智能体自己运行 node 并调用内部的图像 API。由于 Pi 在 Codemode 里暴露了不少内部模型 API，现在智能体就能使用了。

const [painter] = await models.getAvailableOfType("image");
                    const result = await models.generateImages(painter, {
                      input: [{ type: "text", text: "A cute little puppy sitting on a grassy " +
                        "lawn, soft natural light, photorealistic" }],
                    });
                    if (result.stopReason !== "stop") return result.errorMessage;
                    for (const block of result.output) {
                      if (block.type === "image") image(block);
                      else text(block.text);
                    }

调用 image() 会把图片作为图像内容送回给 LLM。在 harness 一侧，它把图片直接送进智能体，同时作为临时产物写到磁盘上，以便智能体想把这张图片再交给 bash 时使用。

用分类器分析 GitHub Issue

像 Jev 这样的分类器模型，同样很难通过典型工具融入智能体的工作流。与其提供一个定制工具，Codemode 让智能体直接伸手进 AI SDK 去调用它们。作者展示的代码，是用 Jev 批量处理 GitHub 的 Issue，做一次快速的情感分析。

const jev = await models.getModelOfType("classifier", "typesafe", "jev-latest");
                    const r = await tools.bash({
                      command: "gh issue list --state open --limit 100 " +
                        "--json number,title,body,comments",
                    });
                    const issues = JSON.parse(r.output);
                    const results = await Promise.all(issues.map(async (issue) => {
                      const res = await models.classify(jev, {
                        state: {
                          title: issue.title,
                          body: (issue.body || "").slice(0, 4000),
                          comments: issue.comments.slice(-5).map(c => c.body.slice(0, 800)),
                        },
                        questions: {
                          sentiment: {
                            type: "choice",
                            instructions: "What is the overall sentiment of the author towards pi?",
                            criteria: {
                              positive: "Appreciative, happy, constructive praise",
                              neutral: "Matter-of-fact report or request without emotion",
                              negative: "Frustrated, annoyed, upset, or angry",
                            },
                          },
                          // ... frustration (score), kind (choice)
                        },
                      });
                      // ...
                    }));
                    store("sentiment_results", results);
  • 最多取回 100 个未关闭的 Issue（gh issue list 加 --limit 100）。
  • 对每个 Issue，正文截取到 4000 个字符，最后 5 条评论各截取到 800 个字符，再送给分类器。
  • 提出三个问题：作者整体的情感倾向（从 positive、neutral、negative 中选择）、提报者的沮丧程度（打分）、Issue 的类型（从 bug、feature、question、other 中选择）。
  • 用 store() 把全部结果存进会话记录，只返回沮丧分数最高的 12 个。作者写道，之后的 Codemode 调用可以把这个结果读回来。
  • 作者解释说，这里 Promise.all 没问题，因为 Pi 把同时执行的工具总数限制为四个，其余的放进队列。

游戏调试循环

作为更大胆的例子，作者用 Jev 驱动游戏引擎来辅助调试。智能体知道他的 tankctl 命令，很快围绕它搭了一个最小的 harness 来驱动游戏循环。它运行一个 30 步的循环，每一步都先回到游戏引擎取一份当前情况的文本转储，再交给 Jev 判断下一步做什么。

示例用 Codemode 做的事作者指出的要点
生成图片通过 models 找到图像模型并生成，再用 image() 返回结果Pi 支持这个功能，但它不是给智能体用的工具。内部模型 API 现在暴露在 Codemode 里
GitHub Issue 分类用 Jev 对 100 个未关闭的 Issue 分类，并用 store() 保存分类器不适合放进普通工具的工作流。不需要定制工具，直接调用 AI SDK
游戏调试循环在 30 步循环中把引擎的文本转储交给 Jev，决定下一步行动智能体自己围绕 tankctl 搭了一个最小的 harness

调用 MCP 服务器与「Codemode 套 Codemode」

作者写道，Codemode 显然很适合调用 MCP 服务器。Pi 不会把任何 MCP 工具暴露给 LLM。智能体会先用 Codemode 里提供的 API 做一次工具搜索，找出能用已连接的服务器做什么。他认为这种渐进式发现，让整个 MCP 在今天的许多用例里足够好用。

在示例中，智能体没有先发现工具，就直接伸手去用 Sentry MCP。作者推测，这大概是因为它在强化学习过程中已经学过 Sentry MCP 长什么样。不过从 Pi 注入系统提示的内容里，它本来就知道 Sentry 服务器可用，所以他补充说它并不是完全在瞎猜。

const orgs = await tools.mcp__sentry__find_organizations({});
                    const { organizations } = orgs.structuredContent;
                    const results = await Promise.allSettled(
                      organizations.map(org => tools.mcp__sentry__find_projects({
                        organizationSlug: org.slug,
                        regionUrl: org.regionUrl,
                      }))
                    );

作者说自己真不想在这里多谈 MCP，却写道 MCP 是一个能从 Codemode 中大大受益的协议。问题的一部分在于，MCP 在实践中常常面向还不使用 Codemode 的 harness。他认为风向正在转变。在此期间，一种权宜之计是照 Cloudflare 的做法，在 MCP 服务器内部做 Codemode。但现在变成了 Codemode 套 Codemode，他评价说这相当糟糕。

  • 意味着 JSON 要双重转义。
  • 较小的模型很容易被搞糊涂。
  • 内层代码无法调用外层的工具。

所以如果在 Pi 里使用 Cloudflare 的 MCP 服务器，智能体就得先写 JavaScript，再把它灌进另一层 JavaScript。作者写道，这确实不理想，但也能理解为什么会这样。

对 MCP 的期望与遗留课题

被问到 Codemode 今天与 MCP 配合得怎么样，作者回答说，并不算好。因为 MCP 服务器还没有真正面向使用 Codemode 的 harness，不过他认为到现在大多数 harness 已经支持它了。要让它运转得好，他提出了四条建议。

项目问题作者的说明
结构化内容Codemode 希望调用返回整齐的 JSON，但许多服务器还没有这样做MCP 的 outputSchema 机制很适合这一点
一致的结果服务器如果按结果集的条目数来优化 token，返回的数据可能不一致用 5 项做的第一次探查可能成功，但服务器返回最大批量时又失败
大体积二进制数据MCP 目前还不支持大体积二进制数据，不少有意思的用例根本跑不好会出现各种奇怪的变通办法，比如用预签名 URL 让文件上传走 MCP 之外的通道
可组合的工具搜索哪个工具适合某项任务，MCP 服务器可能比客户端更清楚目前没有好的机制让 harness 把工具搜索分发到多个 MCP 服务器，只是涌现出来的行为，活跃服务器一多就无法扩展

被问到这是否推翻了他一年前鼓励使用 CLI 的说法，作者说他不这么认为。在他看来，MCP 生态正好跟上了他一年前指出的行得通的东西，也就是代码。Codemode 的意义超出了 MCP，它可以作为 harness 内部一种强大的机制，让智能体表达更多自由。不过他写道，仍有一些事情需要想清楚。

  • 持久性：在 Codemode 里更棘手，可能需要借用持久化工作流引擎的一些思路，对调用做快照。
  • 组合语言：就确定性而言，Starlark 这类语言或许比 JavaScript 更适合。
  • 图片和二进制数据还有待理清。
  • 这种模式在较小的模型上行不通。

他最后写道，它当然还不是完美的解决方案，但是一个相当有用的模式，他预计会更多地用到它。
