에이전트에게 맡기기 전에 데이터부터 정리하라 - Martin Fowler의 단계적 자율성 원칙

인간의 직관에 기대던 데이터 시스템을 기계가 신뢰하고 실행할 수 있는 아키텍처로 바꾸는 법

2026-09-14 개발/인프라

서론: 모델 성능 경쟁의 그늘, 데이터 인프라라는 병목

인공지능 생태계의 관심은 새로운 파운데이션 모델의 매개변수 규모, 다중 모달 성능, 그리고 자율적으로 계획을 수립하고 도구를 호출하는 최신 에이전트 프레임워크에 집중되어 있다. 많은 기업들이 새로운 모델이 출시될 때마다 신속하게 사내 환경에 통합하고, 복잡한 오케스트레이션 파이프라인을 구축하면 즉시 현업 업무를 자율적으로 대체할 수 있을 것이라 기대한다. 그러나 실제 사내 데이터베이스, 전사적 자원 관리(ERP), 고객 관계 관리(CRM) 시스템을 자율 에이전트에 연결하는 순간 대부분의 도입 프로젝트는 예상치 못한 암초에 부딪힌다. 모델이 똑똑하지 않아서가 아니라, 에이전트에게 공급되는 엔터프라이즈 데이터가 전혀 기계 친화적으로 준비되어 있지 않기 때문이다.

지난 30여 년간 우리가 구축해 온 기업용 데이터 아키텍처는 철저하게 「인간 분석가」를 최종 소비자로 상정하고 설계되었다. 대시보드 화면, 정기 리포트, 임의의 SQL 질의문은 모두 화면 앞에 앉아 있는 사람의 눈을 거친다는 전제하에 운영되어 왔다. 인간 작업자는 업무 경험을 통해 특정 테이블에 오래된 레코드가 섞여 있다는 사실을 알고, 숫자가 평소보다 지나치게 높거나 낮으면 동료에게 슬랙으로 확인하거나 질의문을 스스로 수정한다. 즉, 불완전하고 오염된 데이터가 시스템에 존재하더라도 인간의 암묵적 지식과 상황 판단이라는 강력한 완충 장치가 그 오류를 조용히 상쇄해 온 것이다.

그러나 자율 에이전트는 인간과 완전히 다른 방식으로 작동한다. 에이전트는 전달받은 모든 데이터를 의심 없이 사실(Ground Truth)로 받아들이며, 결함이 있거나 최신성이 떨어지는 수치 앞에서도 결코 망설이지 않고 확신에 찬 어조로 결정을 내리고 외부 시스템의 API를 호출한다. 사람이 하던 암묵적 검증이 사라진 자리에 기계의 거침없는 실행력이 결합되면, 사소한 데이터 결함 하나가 연쇄적인 업무 사고로 이어진다. 바로 이 문제를 근본적으로 짚은 글이 마틴 파울러(Martin Fowler)의 기술 사이트에 실린 Thoughtworks 엔지니어들의 분석이다. 원문은 에이전트 도입에서 가장 중요한 투자는 화려한 프레임워크 선택이 아니라, 에이전트가 믿고 소비할 수 있는 데이터 파운데이션과 엄격한 거버넌스 체계를 밑바닥부터 구축하는 일이라고 강조한다.

선행 논의와의 관계: 데이터 계약(Data Contract) 자체의 필요성과 스키마가 잡지 못하는 시맨틱 드리프트(의미 어긋남)의 일반론은 본 사이트의 기존 분석인 데이터를 옮기는 일보다 뜻을 합의하는 일이 어렵다에서 상세히 다루었다. 본 글에서는 일반 데이터 웨어하우스 수준을 넘어, 데이터를 능동적으로 읽고 판단하여 상태 변경(쓰기)까지 수행하는 '에이전트형 AI' 환경에서 데이터 계약과 품질 검증이 왜 에이전트 자율성 확장의 절대적 전제 조건이 되는지에 집중한다.

본 글에서는 Thoughtworks의 프라모드 사달라게(Pramod Sadalage)와 프레마난드 찬드라세카란(Premanand Chandrasekaran)이 정리한 아키텍처 원칙을 바탕으로, 에이전트형 AI를 위해 기업 데이터 환경을 전환하는 핵심 축을 분석한다. 데이터 계약을 통한 불량 데이터 격리, 의사결정의 이유를 복원하는 감사 추적, 명사와 숫자와 동사를 버전 관리하는 맥락 계층, 그리고 검색에서 실시간 조회와 쓰기 작업으로 이어지는 단계적 자율성 확장 전략을 국내 실무 관점에서 살펴본다.

인간 소비자와 기계 소비자의 근본적 차이: 데이터 악취를 맡지 못하는 에이전트

인간 분석가에게는 데이터의 이상 징후를 감지하는 일종의 '후각(Smell Test)'이 존재한다. 특정 컬럼의 값이 비정상적으로 둥근 숫자이거나, 주말이나 공휴일에 대량의 결제가 기록되어 있거나, 지난주에 인상하기로 협의했던 단가가 예전 수치 그대로 남아 있으면 사람은 본능적으로 멈칫한다. "잠깐, 지난주 회의에서 이 제품 가격을 59.99달러로 올리기로 결정하지 않았나?"라는 의문이 드는 순간, 사람은 즉각 결제를 승인하지 않고 담당 부서에 확인을 요청한다. 이러한 현업의 감각과 오랜 경험에서 축적된 맥락은 데이터 파이프라인의 설계 결함을 보이지 않게 메워 주었다.

하지만 언어 모델은 사이먼 윌리슨(Simon Willison)이 지적했듯 천성적으로 쉽게 믿는(Gullible) 성향을 지닌다. 모델은 자신에게 주입된 컨텍스트를 의심하지 않으며, 틀린 전제 위에서도 가장 유려하고 논리적인 문장을 만들어 낸다. 제품 X의 가격이 어제 49.99달러에서 59.99달러로 변경되었지만 캐시나 파이프라인의 지연으로 데이터 소스가 갱신되지 않은 채 49.99달러를 가리키고 있다면, 가격 책정 에이전트는 한 치의 망설임도 없이 고객에게 49.99달러를 제시하고 결제를 확정한다. 에이전트가 수행한 워크플로는 기술적으로 완벽했고 모든 단계가 정상 처리되었지만, 기업은 판매 건당 10달러씩의 금전적 손실을 입게 된다. 모델의 성능이 아무리 뛰어나도 입력된 데이터가 틀리면 결과는 치명적이다.

이러한 현실과 기업 리더들의 인식 사이에는 심각한 간극이 존재한다. 원문이 인용한 2026년 Drexel University LeBow 경영대학원과 Precisely의 조사 보고서(505명의 데이터·분석 리더 대상)에 따르면, 응답자의 88%가 자사의 데이터가 AI 도입에 준비되어 있다고 답했으나, 동시에 43%는 데이터 준비 상태를 AI 가치 창출의 가장 큰 장애물로 꼽았다. 자신이 준비되었다고 믿는 자신감과 실제 운영 환경에서의 준비 부족 사이의 괴리가 고스란히 드러난 것이다. 또한 2,145명의 경영진을 조사한 KPMG Global AI Pulse 보고서에서도 응답자의 절반 가까이가 AI 도입 비용이 비즈니스 편익을 초과하고 있다고 평가했다. 이는 대부분의 엔터프라이즈가 단 하나의 오래된 필드 값 때문에 에이전트의 오작동 위험에 상시 노출되어 있음을 방증한다.

따라서 인간이 무료로 제공하던 암묵적 맥락과 상식적 검증 작업을 데이터 시스템 자체에 엔지니어링으로 구현해야만 한다. 이를 원문에서는 에이전트 준비도(AI-Ready)를 구성하는 다섯 가지 핵심 속성으로 정의한다.

속성인간 소비자의 기존 행동에이전트 환경에서 요구되는 아키텍처 구현
신뢰성(Trusted)이상한 수치를 보면 스스로 멈추고 담당자에게 재확인에이전트가 데이터를 보기 전에 최신성과 품질 기준을 엄격히 검증하여 보장
맥락성(Contextual)매출에서 반품이 제외되었는지, 회계연도 기준이 언제인지 기억숫자와 개체의 비즈니스 정의와 계산 규칙을 시스템에 선언적으로 명시
추적성(Traceable)결정을 내린 후 사람이 사후에 이유와 근거를 구두로 설명에이전트의 30초 판단 과정을 전체 추론 체인과 함께 스팬 단위로 자동 기록
거버넌스(Governed)자신의 직책과 상식에 따라 시스템 접근 범위를 스스로 조절역할 기반이 아닌 위임 접근과 적시 자격 증명으로 에이전트 권한을 설계로 통제
실행성(Operational)대시보드를 읽고 수작업으로 타 시스템에 접속해 업무 처리읽기 전용 문서 조회를 넘어 상태를 안전하게 변경할 수 있는 도구 인터페이스 제공

2.1 침묵하는 데이터 오류와 확신에 찬 오작동의 위험

전통적인 시스템에서는 데이터 스키마가 깨지거나 필드가 누락되면 데이터베이스나 배치 잡이 에러를 뿜으며 중단된다. 이는 불편하지만 시스템이 즉시 문제를 인지할 수 있는 '시끄러운 실패'다. 반면, 데이터의 형식이 유지된 채 의미가 달라지거나 과거의 낡은 값이 유지되는 현상은 어떤 에러 로그도 남기지 않는다. 에이전트는 아무런 경고 없이 정상 응답 코드를 반환하며, 다운스트림 업무 프로세스를 왜곡시킨다. 잘못된 단가로 수천 건의 발주서가 처리되거나, 폐기된 환불 규정을 바탕으로 부적절한 보상금이 지급되는 사고는 모두 이러한 침묵의 결함에서 비롯된다.

2.2 인간의 암묵지를 데이터 인프라의 명시적 규칙으로 전환하기

결국 에이전트형 AI를 조직에 안착시키기 위한 본질적인 작업은, 회의실 대화나 담당자의 기억 속에 파편화되어 있던 비즈니스 규칙을 명시적인 코드로 전환하는 것이다. 인간 작업자가 "이 데이터는 어제 배치 작업이 실패했을 수도 있으니 한 번 더 확인해야지"라고 생각하던 주의사항은 이제 데이터 파이프라인의 최신성 SLA(Service Level Agreement) 검증 코드로 변환되어야 하며, "매출 집계 시 테스트 계정은 제외해야 한다"는 관례는 시맨틱 모델의 필수 필터링 조건으로 고정되어야 한다. 이 전환 없이는 어떤 고성능 모델을 도입해도 사내 핵심 업무를 안심하고 위임할 수 없다.

  • 신뢰성 확보: 에이전트가 조회하기 직전에 데이터의 정확성과 적재 주기를 기계적으로 단언 검증
  • 명시적 맥락 부여: 총매출과 순매출, 활성 고객 등 복잡한 비즈니스 개념을 코드로 선언
  • 의사결정 복원력: 규제 당국이나 내부 감사가 판단 근거를 요구할 때 완벽히 재현 가능한 로그 축적
  • 경계 기반 권한 통제: 광범위한 서비스 계정 대신 특정 사용자의 권한을 일시 위임받는 최소 권한 체계 구축
  • 실행 가능성의 단계적 개방: 읽기 전용 검색에서 안전한 쓰기 작업까지 검증된 순서로 권한 확장

데이터 계약과 격리 패턴: 오염된 입력값의 사전 봉쇄

나쁜 데이터의 유입을 원천적으로 막기 위한 최선의 방법은 스키마를 단순한 권장 사항이 아니라 엄격한 법률처럼 강제하는 것이다. 지난 수년간 빅데이터 분야에서는 유연성을 이유로 스키마리스(Schemaless)나 느슨한 스키마 검증이 유행했으나, 자율 에이전트 환경에서 느슨한 스키마는 곧바로 시스템 장애로 이어진다. Open Data Contract Standard(ODCS)와 같은 표준 규격을 활용하여 데이터 계약(Data Contract)을 작성하고, 이를 배포 파이프라인 및 실시간 수집 게이트에서 코드로서 집행해야 한다.

원문에서 제시한 가격 책정 데이터셋의 데이터 계약 예시는 아래와 같다. 필드의 논리적 타입과 물리적 타입을 엄격히 지정할 뿐 아니라, 가격이 0보다 커야 한다는 SQL 품질 규칙, 통화 코드가 허용된 세 가지 ISO 코드(USD, EUR, GBP) 중 하나여야 한다는 제약, 그리고 수집 시각(`ingested_at`)이 24시간 이내여야 한다는 최신성 SLA를 명시하고 있다.

apiVersion: v3.1.0
kind: DataContract
id: product-pricing
name: Product Pricing
version: 1.0.0
status: active
schema:
  - name: product_pricing
    physicalType: table
    properties:
      - name: product_id
        logicalType: string
        physicalType: varchar(64)
        required: true
        unique: true
        primaryKey: true
        primaryKeyPosition: 1
      - name: price
        logicalType: number
        physicalType: decimal
        required: true
        quality:
          - type: sql
            description: Every price must be greater than zero
            query: SELECT min({property}) FROM {object}
            mustBeGreaterThan: 0
      - name: currency
        logicalType: string
        physicalType: varchar(3)
        required: true
        quality:
          - type: sql
            description: Currency must be a supported ISO code
            query: SELECT count(*) FROM {object} WHERE {property} NOT IN ('USD', 'EUR', 'GBP')
            mustBe: 0
      - name: ingested_at
        logicalType: timestamp
        physicalType: timestamp
        required: true
        slaProperties:
          - property: latency
            value: 24
            unit: h
            element: product_pricing.ingested_at

이 계약은 세 가지 차원에서 집행된다. 첫째는 스키마 강제로, 데이터의 타입과 제약 조건이 선언된 스펙과 일치하는지 검사한다. 둘째는 최신성 SLA로, 데이터가 허용된 지연 시간 내에 적재되었는지를 검증한다. 여기서 중요한 점은 최신성의 기준을 '값 자체가 변경된 시각'이 아니라 '데이터가 성공적으로 수집되어 적재된 시각'에 연결해야 한다는 것이다. 그래야 가격 변동이 없는 안정적인 데이터가 오래된 데이터로 오판되지 않으며, 반대로 파이프라인이 멈춘 사고를 정상 데이터로 오인하는 사태를 방지할 수 있다. 셋째는 CI/CD 배포 게이트로, 계약을 위반하는 변경 사항이 코드 저장소에 병합되는 것을 사전에 차단한다.

3.1 스키마 강제와 최신성 SLA의 결합

데이터 계약이 실제 효과를 발휘하려면 정적 스키마 검증과 동적 품질 검사가 결합되어야 한다. 데이터베이스 컬럼의 데이터형이 맞더라도, 수집된 지 48시간이 지난 데이터라면 실시간 고객 상담 에이전트에게는 치명적인 독이 된다. 대시보드를 보는 인간 임원에게는 하루 전의 통계가 충분할 수 있지만, 고객에게 실시간 견적을 발송하는 에이전트에게는 분 단위의 신선도가 요구된다. 따라서 데이터 소비자의 성격에 따라 차등화된 최신성 SLA를 계약에 명시하고, 이를 기계적으로 감시해야 한다.

3.2 격리 패턴(Quarantine Pattern)과 데드 레터 큐의 역할

계약을 선언하는 것만으로는 충분하지 않다. 계약을 위반한 불량 데이터가 도착했을 때 시스템이 어떻게 대처할 것인가가 핵심이다. 여기서 요구되는 설계 패턴이 바로 '격리 패턴(The Quarantine Pattern)'이다. 원천 API나 데이터베이스에서 흘러들어온 원시 데이터는 에이전트가 접근 가능한 저장소로 바로 전달되지 않는다. 수집 게이트웨이에서 스키마, 최신성, 품질 규칙을 검증받고, 단 하나라도 위반한 레코드는 즉시 데드 레터 큐(Dead Letter Queue)로 우회 격리된다.

격리된 데이터는 사람 담당자에게 알림을 발송하여 검토를 유도하며, 에이전트의 시야에서는 철저히 은폐된다. 앞서 언급한 가격 책정 시나리오에서 수집 시각이 24시간을 초과한 레코드는 격리 큐로 이동하므로, 에이전트는 오래된 49.99달러를 조회하는 대신 "현재 제품 X의 유효한 가격 데이터를 조회할 수 없습니다"라고 안전하게 실패(Fail-safe)하게 된다. 부정확한 수치로 즉각 거래를 체결하는 것보다, 데이터 부재를 인지하고 인간에게 확인을 요청하는 실패 모드가 비즈니스적으로 훨씬 안전하다.

3.3 메달리온 아키텍처에서 에이전트 접근 계층(Gold 이상) 분리

레이크하우스 환경에서 널리 사용되는 메달리온 아키텍처(Medallion Architecture) 역시 에이전트 관점에서 재정립되어야 한다. 원시 불변 로그가 저장되는 Bronze 계층과, 중복이 제거되고 데이터 계약 검증 및 격리 패턴이 동작하는 Silver 계층은 디버깅과 계보 추적을 위한 공간으로 인간 엔지니어에게만 개방되어야 한다. 자율 에이전트는 품질 검증이 완전히 끝난 공인된 Gold 계층 이상에만 접근하도록 물리적·논리적 접근 제어를 분리해야 한다.

나아가 원문은 에이전트가 자신의 빈번한 질의 패턴을 스스로 관찰하여 뷰를 최적화하는 'Adaptive Gold' 계층을 제안한다. DataHub의 CONTEXT 2025 행사에서 Apple이 데이터 카탈로그의 메타데이터 누락을 점검하고 업데이트를 제안하는 '디지털 스튜어드' 에이전트를 소개했듯이, 에이전트가 데이터의 단순 소비자에 머무르지 않고 데이터 관리자로서 신뢰 계층을 큐레이션하는 패턴이 발전하고 있다. 이러한 계층 분리는 정형 데이터뿐만 아니라 RAG(검색 증강 생성)에 사용되는 벡터 스토어와 텍스트 청크에도 동일하게 적용되어야 한다.

  • 선언적 계약 명세: ODCS 표준을 통해 테이블 타입, 값 범위, 허용 열거형을 코드로 고정
  • 적재 시점 기반 SLA: 데이터 수정 시각이 아닌 파이프라인 수집 시각을 기준으로 최신성을 평가
  • 데드 레터 큐 라우팅: 품질 기준 미달 레코드를 즉시 격리하여 에이전트 노출을 원천 차단
  • 안전한 실패 모드: 오염된 값으로 자의적 판단을 내리는 대신 데이터 부재를 알리고 이관
  • Gold 계층 격리: 불완전한 Bronze/Silver 데이터를 차단하고 검증 완료된 Gold 이상만 인가

감사 추적과 에이전트 계보: 무엇을 넘어 왜 행동했는가를 기록하기

데이터가 완벽하게 정제되었다고 하더라도, 에이전트가 사내 시스템에서 자율적으로 결정을 내리기 시작하면 전혀 다른 차원의 질문이 대두된다. 만약 무역금융 에이전트가 신용장(Letter of Credit) 발행 요청을 검토하여, 고객 신원 확인(KYC)을 수행하고, 해외 제재 대상 목록을 조회하고, 여신 한도를 심사한 끝에 240만 달러 규모의 거래를 단 30초 만에 승인했다고 가정해 보자. 6개월 후 금융 감독 기관이나 감사 부서에서 "이 대규모 여신 거래를 도대체 왜 그 시점에 승인했는가?"라고 질문했을 때, 기업은 명확한 근거를 제시할 수 있어야 한다.

전통적인 시스템 로그는 이 질문에 답하지 못한다. 기존 로그에는 "서비스 계정이 몇 시 몇 분 몇 초에 컴플라이언스 DB의 특정 테이블을 SELECT 했다"는 사실, 즉 '무엇(What)'이 일어났는지만 적혀 있을 뿐이다. 에이전트가 왜 제재 목록 조회를 신용 한도 심사보다 먼저 수행했는지, 서류상의 경미한 불일치를 왜 위험하지 않다고 판단했는지, 어떤 대안적인 조치들을 검토하다가 최종적으로 기각했는지와 같은 '이유(Why)'는 전통적 로그에서 완전히 증발한다. 이 간극이 바로 에이전트 도입 시 기업이 직면하는 거대한 거버넌스 공백이다.

이 문제를 해결하기 위해 도입되는 개념이 바로 '에이전트 계보(Agentic Lineage)'다. 분산 시스템 관측성(Observability)에서 검증된 트레이스(Trace)와 스팬(Span) 모델을 에이전트의 의사결정 과정에 그대로 투영하는 것이다. 예컨대 신용장 LC-4892 처리 전체가 하나의 트레이스가 되고, 그 내부의 개별 행동들이 스팬으로 기록된다. 스팬 1에서는 규정 준수 DB에서 고객 KYC를 확인하여 검증을 통과했고, 스팬 2에서는 OFAC API를 통해 제재 명단을 조회하여 이상 없음을 확인했으며, 스팬 3에서는 여신 정책 엔진을 호출하여 한도 내임을 확인한 후, 최종 스팬에서 94%의 신뢰도 점수와 상세한 추론 체인을 첨부하여 승인을 내렸다는 전체 맥락이 완벽하게 보존된다.

이러한 감사 추적 체계는 단순한 기술적 권장 사항이 아니라 법적 의무로 구체화되고 있다. 유럽연합의 인공지능법(EU AI Act) 제12조는 고위험 AI 시스템이 운영 수명주기 전반에 걸쳐 이벤트를 자동으로 로깅하도록 의무화하고 있으며, 제19조는 시스템 제공자가 해당 로그를 최소 6개월 이상 보존하도록 규정하고 있다. 이러한 의무를 위반할 경우 최대 1,500만 유로 또는 전 세계 연간 매출액의 3% 중 높은 금액에 달하는 막대한 과징금이 부과된다. 다른 관할권에서도 유사한 규제가 도입될 가능성이 높으며, 규제가 아니더라도 사후 디버깅과 고객 분쟁 해결을 위해서는 의사결정 이유의 복원력이 필수적이다.

4.1 전통적 로그와 에이전트 계보(Agentic Lineage)의 결정적 간극

기존 인프라 엔지니어링의 로그는 호출된 API 엔드포인트와 반환 코드만을 건조하게 남긴다. 그러나 에이전트는 비결정적(Non-deterministic) 특성을 지니고 있으므로, 동일한 시스템 상태에서도 프롬프트와 컨텍스트에 따라 다른 경로를 선택할 수 있다. 단순히 테이블 접근 이력만으로는 사후 역추적이 불가능하며, 에이전트가 어떤 문서를 근거로 채택했고 어떤 추론 논리를 전개하여 다음 도구를 선택했는지를 인과 관계 중심으로 연결해 기록해야 한다.

4.2 분산 추적 모델(Trace & Span)과 규제 컴플라이언스(EU AI Act)

Jaeger나 Zipkin 같은 마이크로서비스 관측 도구의 멘탈 모델은 에이전트 시스템에 완벽하게 부합한다. 에이전트 전용 관측성 도구로 자리 잡고 있는 Langfuse, Arize Phoenix, 그리고 OpenTelemetry의 AI 확장 규격은 Thoughtworks 기술 레이더에서도 채택 및 평가 단계로 비중 있게 다루어지고 있다. 특히 EU AI Act와 같은 글로벌 규제 요건을 충족하기 위해서는 로그를 단순히 저장하는 데 그치지 않고, 시스템이 작동한 전체 추론 과정을 사후에 인간 감사인이 이해할 수 있는 형태로 재구성할 수 있어야 한다.

4.3 위임 접근과 적시 자격 증명: 치명적 삼중 조합의 방어

에이전트 거버넌스의 또 다른 핵심은 자격 증명 관리다. 전통적인 시스템처럼 전사 권한을 가진 강력한 단일 서비스 계정(Service Account)을 에이전트에 부여하면, 감사 로그에서 책임 소재가 완전히 흐려진다. 앨리스가 에이전트에게 계좌 조회를 요청했다면, 에이전트는 전지전능한 계정이 아니라 '앨리스의 권한을 일시 위임받은 대리인'으로서 작동해야 한다. 이를 '위임 접근(Delegated Access)'이라 한다.

또한 영구적인 API 토큰 대신, 특정 작업을 수행하는 동안에만 5분간 유효한 '적시 자격 증명(Just-In-Time Credentials)'을 발급하고 작업 종료 즉시 만료시켜야 한다. 이는 사이먼 윌리슨이 경고한 '치명적 삼중 조합(The Lethal Trifecta)'—즉 비공개 데이터에 대한 접근권, 신뢰할 수 없는 외부 콘텐츠에 대한 노출, 외부로 통신할 수 있는 채널이 한 에이전트에 결합되는 위험—을 무력화하는 핵심 방어선이 된다. 프롬프트 인젝션 공격으로 에이전트가 탈취되더라도, 탈취된 에이전트가 접근할 수 있는 권한과 수명을 극소화하여 데이터 유출을 방어할 수 있다.

  • 의사결정 인과성 기록: 데이터 조회 시점뿐 아니라 이전 단계의 결과가 다음 판단에 미친 영향을 추적
  • 트레이스-스팬 계측: OpenTelemetry 및 AI 전용 추적 플랫폼을 활용해 전체 워크플로를 구조화
  • 법적 로그 보존: EU AI Act 제12조 및 제19조 규정을 준수하여 최소 6개월 이상 의사결정 체인 보존
  • 위임 기반 신원 증명: 공용 서비스 계정을 배제하고 요청자 신원에 기반한 대리 권한을 부여
  • 단기 수명 토큰(JIT): 작업 단위로 유효 기간이 극도로 짧은 자격 증명을 동적 발급하여 탈취 위험 최소화
  • 치명적 삼중 조합 해체: 비공개 데이터와 외부 통신 경로 사이에 권한 및 유효성 격벽을 설치

맥락 계층의 세 축: 명사, 숫자, 동사의 선언적 버전 관리

에이전트가 신뢰할 수 있는 데이터를 공급받고 감사 체계가 마련되었더라도, 비즈니스 개념에 대한 구체적인 정의가 누락되어 있다면 에이전트는 정상적으로 작동할 수 없다. 사용자가 "3분기 제품 X의 매출이 얼마인가?"라고 질문했을 때, 인간 분석가는 사내 회계 달력이 2월에 시작한다는 점, 매출(Revenue)이 총매출인지 반품과 할인을 차감한 순매출인지, 주문 테이블과 제품 테이블을 어떤 외래 키로 조인해야 하는지를 직관적으로 알고 있다. 하지만 에이전트에게 이 맥락이 전달되지 않으면 모델은 임의의 테이블을 조인하거나 환각에 빠지게 된다.

이 간극을 메우는 장치가 바로 '맥락 계층(The Context Layer)'이다. 맥락 계층은 단순히 숫자의 계산식만을 모아두는 기존 BI 도구의 시맨틱 레이어를 넘어, 기업의 엔터티(명사), 지표 계산식(숫자), 그리고 실행 가능한 작업(동사)을 코드로 선언하고 단일하게 버전 관리하는 아키텍처다. 에이전트는 원천 데이터베이스 스키마에 직접 접근하지 않고, 반드시 이 맥락 계층을 통과하여 데이터를 질의하고 명령을 실행해야 한다.

하위 모델언어적 비유주요 정의 내용 및 특성데이터 저장소 및 실행 경로
도메인 모델(Domain Model)명사 (Nouns)기업 내 개체와 상호 관계, 비즈니스 의미 규칙 정의 (예: 주문은 고객에 속함)참조용 지식 체계로 사용되며, 직접적인 데이터 질의 실행 경로는 갖지 않음
시맨틱 모델(Semantic Model)숫자 (Numbers)지표와 차원의 공식 계산식 정의 (예: 매출 = 주문액 - 할인액)분석용 웨어하우스(SQL)로 컴파일되어 단일한 계산 결과를 보장
기능 모델(Capability Model)동사 (Verbs)시스템에 허용된 읽기·쓰기 동작, 권한, 사전 조건, 가역성 등급 정의실시간 운영 시스템(API, MCP)을 통해 통제된 상태 변경을 수행

아래는 dbt MetricFlow 명세를 활용하여 비즈니스 지표를 코드로 선언한 전형적인 시맨틱 모델 예시다. 주문 테이블에서 매출(revenue)이 `order_amount - discount_amount`의 합계로 계산된다는 점을 명시적으로 선언함으로써, 어떤 클라이언트가 질의하더라도 동일한 수식이 산출되도록 강제한다.

semantic_models:
  - name: orders
    model: ref('orders')
    defaults:
      agg_time_dimension: order_date
    entities:
      - name: order_id
        type: primary
      - name: customer_id
        type: foreign
    dimensions:
      - name: order_date
        type: time
        type_params:
          time_granularity: day
    measures:
      - name: revenue
        agg: sum
        expr: order_amount - discount_amount
        create_metric: true

이러한 선언적 제약이 있을 때와 없을 때 에이전트가 생성하는 SQL 질의문의 차이는 극명하다. 시맨틱 정의가 없을 때 에이전트는 테이블명과 컬럼을 마음대로 추측하여 부정확한 쿼리를 만들지만, 시맨틱 모델이 주어지면 선언된 수식과 올바른 조인 경로, 정확한 회계 일자를 엄격하게 반영한 SQL을 생성한다.

-- 지표 정의가 없을 때 에이전트가 추측하여 생성한 부정확한 SQL 예시
SELECT SUM(amount) FROM sales_data WHERE product = 'Product X' AND quarter = 'Q3';

-- 시맨틱 모델 정의에 의해 엄격하게 제약되어 컴파일된 SQL 예시
SELECT SUM(order_amount - discount_amount)
FROM orders o
JOIN products p ON o.product_id = p.id
WHERE p.name = 'Product X'
  AND o.order_date BETWEEN '2025-07-01' AND '2025-09-30';

5.1 도메인 모델, 시맨틱 모델, 기능 모델의 분리와 공통 어휘

맥락 계층을 설계할 때 가장 흔히 저지르는 실수는 지표 계산용 엔터티 정의와 실행 기능 정의를 제각각 분리하여 관리하는 것이다. 만약 시맨틱 모델에서 정의한 '고객'과 기능 모델에서 환불을 처리할 때 참조하는 '고객'의 식별자 체계가 다르다면, 환불 금액 집계와 실제 환불 처리 사이에서 심각한 불일치가 발생한다. 따라서 기본 도메인 모델을 공유 어휘집으로 삼고, 그 어휘 체계 위에 계산을 위한 시맨틱 모델과 행동을 위한 기능 모델을 정렬시켜야 한다.

또한 이 세 가지 모델은 모두 Git과 같은 버전 관리 시스템에 코드로 보관되어야 한다. 매출의 정의나 환불 승인 기준이 변경될 경우, 담당 팀의 풀 리퀘스트(PR)와 코드 리뷰, CI 환경의 회귀 테스트를 거쳐 배포되어야 한다. 변경 이력이 남지 않는 GUI 도구의 설정값으로 관리되면 비즈니스 규칙의 진화 과정을 추적할 수 없게 된다.

5.2 지식 그래프를 활용한 동적 관계와 시간성 탐색

단순한 수치 집계는 시맨틱 모델의 SQL 컴파일로 충분하지만, "특정 고객이 제품 X를 구매한 후 요금제 개편을 거쳐 이탈하기까지 거친 지원 티켓 이력"과 같이 탐색 깊이를 사전에 예측할 수 없는 복합 질의는 관계형 테이블 조인만으로 해결하기 어렵다. 이 영역은 도메인 모델의 연결 관계를 표현하는 지식 그래프(Knowledge Graph)의 영역이다.

Microsoft의 GraphRAG나 시간 인식 그래프를 다루는 Graphiti와 같은 기술은 Thoughtworks 레이더에서도 검증 단계(Trial)로 평가되고 있다. 시맨틱 모델이 지표의 정확한 수식을 책임지고 지식 그래프가 엔터티 간의 시간적·인과적 맥락을 연결해 주면, 에이전트는 신규 입사자가 수개월에 걸쳐 습득해야 하는 사내 조직 지식과 흡사한 깊은 이해도를 갖추게 된다.

  • 단일 진실 공급원: 지표 수식을 ad-hoc 질의문이나 BI 설정이 아닌 Git 저장소의 코드로 관리
  • SQL 추측 제거: LLM의 자의적 쿼리 생성을 차단하고 사전 검증된 컴파일러 규칙으로 SQL 생성 강제
  • 공통 도메인 어휘: 지표 집계와 시스템 쓰기 작업이 동일한 고객 및 주문 식별 체계를 참조하도록 통일
  • 적대적 테스트 검증: 에이전트 환각 발생 시 프롬프트 수정이 아닌 누락된 시맨틱 정의를 보완
  • 그래프 기반 관계 추적: 깊이가 불확실한 엔터티 간의 복합 인과 관계를 지식 그래프로 보완
  • 선별적 범위 설정: 전사 모든 지표를 한 번에 모델링하려 하지 말고 충돌이 잦은 핵심 지표부터 착수

검색에서 쓰기까지: 단계적 자율성 확장과 진입 장벽

데이터의 신뢰성이 확보되고 맥락 계층이 정립되었다면, 마지막으로 해결해야 할 과제는 에이전트의 '데이터 접근 수준'을 어떻게 통제할 것인가이다. 현재 많은 기업이 채택하고 있는 단순한 문서 검색 중심의 RAG(Retrieval-Augmented Generation)는 데이터 접근의 가장 낮은 단계에 불과하다. RAG 기반 에이전트는 사내 규정 문서를 찾아 읽어줄 수는 있지만, 실시간 서비스 장애 여부를 모니터링 시스템에서 확인하거나 Jira 또는 ServiceNow에 티켓을 등록하는 능동적 행위는 수행하지 못한다.

마이크로소프트의 AI 클라우드 도입 프레임워크(Cloud Adoption Framework for AI)에서도 지적하듯, 에이전트의 데이터 접근은 검색(Retrieval), 실시간 조회(Real-Time Query), 그리고 상태를 변경하는 쓰기 작업(Write-Back)의 세 단계 스펙트럼으로 나뉜다. 단계가 올라갈수록 비즈니스 자동화의 가치는 비약적으로 커지지만, 그에 수반되는 운영 리스크 역시 급격히 증가한다. 따라서 에이전트의 자율성은 엄격한 통제하에 점진적으로 개방되어야 한다.

접근 계층주요 작업 형태MCP 프리미티브 매핑수반되는 리스크 및 요구 통제 장치
1단계: 검색(Retrieval)벡터 검색, 문서 조회, 위키·가이드 지식 참조Resources (읽기 전용 자원)리스크 최하. 청크 최신성 SLA 및 메타데이터 무결성 검증 필요
2단계: 실시간 조회(Real-Time Query)라이브 DB 조회, 모니터링 API 호출, 상태 확인Tools (읽기 전용 도구)리스크 중간. 질의 성능 부하 관리 및 시맨틱 모델 제약 필요
3단계: 쓰기 작업(Write-Back)티켓 생성, 결제 승인, DB 레코드 변경, 환불 처리Tools (상태 변경 도구)리스크 최고. 사전 조건 엄격 검사 및 가역성 기반 승인 게이트 필수

구매 주문서(PO) 결제 장애 시나리오를 예로 들면 이 세 단계의 융합이 명확해진다. 직원이 "발주서 결제가 진행되지 않는다"고 문제를 접수했을 때, 이상적인 에이전트는 먼저 지식 저장소에서 장애 조치 가이드를 검색하고(1단계: Resource 참조), 결제 서비스의 현재 라이브 헬스체크 상태를 실시간 조회하며(2단계: Tool 읽기), 시스템 장애가 확인되면 지원 티켓을 자동으로 발행한다(3단계: Tool 쓰기). 이 모든 과정이 하나의 워크플로 안에서 안전하게 연결되어야 진정한 에이전틱 자동화가 완성된다.

6.1 RAG의 한계와 실시간 조회·쓰기 작업(Write-Back)의 위험

대부분의 엔터프라이즈 프로젝트가 RAG 단계에 머무르는 이유는 쓰기 작업이 내포한 위험성 때문이다. 검색 단계의 오류는 잘못된 답변을 화면에 보여주는 수준에 그치지만, 실시간 쓰기 작업의 오류는 실제 사내 데이터베이스를 훼손하거나 회수할 수 없는 금전적 송금을 유발한다. 따라서 쓰기 권한은 모델 성능에 대한 막연한 신뢰가 아니라, 에이전트가 통과해야 하는 엄격한 승격 단계(Staged Autonomy)와 운영 실적 데이터를 바탕으로 부여되어야 한다.

자율성 단계는 다음과 같이 4단계로 운영하는 것이 안전하다. 첫째는 에이전트가 조언만 제시하고 실행은 사람이 전담하는 '섀도 모드(Shadow Mode)', 둘째는 에이전트가 실행 직전까지 작업을 구성하고 사람의 승인 버튼을 기다리는 '감독 모드(Supervised Mode)', 셋째는 사전에 합의된 명확한 경계 내에서만 자율 실행하고 예외 시 인간에게 이관하는 '가드레일 모드(Autonomous with Guardrails)', 넷째는 사후 표본 점검만을 수행하는 '완전 자율 모드(Fully Autonomous)'다. 신규 입사자에게 첫날부터 법인카드를 쥐어주지 않듯, 에이전트 역시 섀도 모드에서 충분한 의사결정 정확도 데이터가 입증된 후에만 다음 단계로 승격시켜야 한다.

6.2 MCP 안티패턴: 무분별한 1:1 API 래핑 탈피와 업무 기능 설계

도구 인터페이스를 구축할 때 가장 자주 범하는 실수는 기존 REST API 엔드포인트를 기계적으로 1:1 변환하여 MCP 도구로 노출하는 것이다. 이로 인해 `get_po_payment_status`, `create_ticket_po_payment`, `create_ticket_network` 등 미세하게 갈라진 50여 개의 도구가 난립하게 된다. LLM은 선택해야 할 도구의 개수가 늘어날수록 정확도가 급격히 떨어지며, Thoughtworks 기술 레이더는 이러한 '단순한 API-to-MCP 변환(Naive API-to-MCP Conversion)'을 명백한 안티패턴(HOLD)으로 규정했다.

올바른 접근법은 50개의 조각난 엔드포인트 대신, 풍부한 자연어 설명과 구조화된 매개변수를 갖춘 5~10개의 핵심 '업무 기능(Capability)'으로 도구를 재설계하는 것이다. 예컨대 모든 서비스 상태를 조회할 수 있는 단일한 `check_service_status` 도구와, 카테고리와 우선순위를 인자로 받는 `create_support_ticket` 도구를 제공하는 식이다. 도구 설명문 자체가 LLM이 올바른 도구를 선택하는 판단 근거가 되므로, 설명의 완성도가 성공을 좌우한다.

6.3 사전 조건 검증과 가역성(Reversibility) 기반의 권한 통제

행동을 유발하는 기능 모델에는 반드시 두 가지 통제 메커니즘이 선언되어야 한다. 첫째는 '사전 조건(Preconditions)'이다. 환불을 실행하기 전에는 원본 결제 내역이 존재하고 아직 환불되지 않았는지를 실행 직전의 실시간 상태에서 기계적으로 검증해야 한다. 이때 비정형 규정 문서(예: 환불 정책 PDF)에서 검색한 텍스트는 판단의 참고 자료(Informs)일 뿐이며, 권한을 최종 부여하는 게이트(Gates)가 되어서는 안 된다. 규정에서 추출된 규칙은 시스템에 사전 조건 코드로 고정되어 있어야만 악의적인 문서 주입 공격(Prompt Injection)으로 인한 오작동을 차단할 수 있다.

둘째는 '가역성(Reversibility)'에 따른 권한 분기다. 많은 조직이 거래 금액의 크기만을 기준으로 승인 권한을 나누지만, 자율성 통제에서 더 결정적인 지표는 그 작업을 원래대로 되돌릴 수 있는가이다. 5,000만 원 규모의 사내 장부 수정 작업은 오류가 발견되어도 회계적으로 역분개하여 원상복구할 수 있으므로 자율 실행의 위험이 상대적으로 낮다. 반면 외부 계좌로 20만 원을 송금하는 작업은 일단 실행되면 강제로 회수하기 어렵다. 비가역적(Irreversible) 작업은 에이전트의 자율성 단계가 아무리 높아도 반드시 사람의 명시적 승인을 거치도록 강제해야 한다.

  • 단계적 스펙트럼 적용: 읽기 전용 자원(Resources)에서 시작하여 상태 변경 도구(Tools)로 점진적 확장
  • 단순 API 래핑 금지: 엔드포인트 나열을 지양하고 5~10개의 풍부하게 설명된 업무 단위 도구로 집약
  • 문서 검색과 승인 분리: 검색된 텍스트는 참고 증거로만 활용하고 실행 권한은 선언된 규칙으로 통제
  • 실시간 사전 조건 검증: 실행 직전 원천 데이터베이스의 실시간 상태를 대조하여 필수 조건 충족 확인
  • 가역성 기반 통제: 거래 금액보다 복구 가능 여부(가역성 등급)를 기준으로 인간 승인 필요성 결정
  • 단계적 자율성(Staged Autonomy): 섀도 모드에서 실적 데이터를 충분히 축적한 후 상위 모드로 승격

한국 기업 실무를 위한 도입 전략: 제품으로서의 데이터와 우선순위

국내 대기업 및 중견 엔터프라이즈 환경에서 에이전트형 AI 프로젝트를 추진할 때 흔히 겪는 문제는, 데이터의 기술적 관리 체계는 마련했으나 데이터 자체의 '소유권(Ownership)'이 비어 있다는 점이다. 전사 데이터 웨어하우스는 중앙 데이터 팀이 관리하지만, 그 데이터가 담고 있는 비즈니스의 참뜻은 영업, 재무, 물류 등 현업 도메인 부서에 흩어져 있다. 중앙 팀은 결제 상태 코드의 변경 사항을 알지 못하고, 현업 팀은 자신들의 테이블 스키마 변경이 에이전트의 다운스트림 업무를 파괴한다는 사실을 인지하지 못한다.

이 문제를 해결하는 유일한 길은 데이터를 단순한 시스템 부산물이 아닌 '제품(Data as a Product)'으로 대우하는 데이터 메시(Data Mesh)의 거버넌스 철학을 도입하는 것이다. 모든 데이터 계약, 시맨틱 모델의 지표 공식, 그리고 에이전트가 호출하는 도구 기능마다 반드시 실명을 가진 담당 부서와 소유자가 지정되어야 한다. 데이터 계약 위반으로 CI 빌드가 멈추었을 때 책임을 지고 수정할 주체, 영업과 재무가 매출 지표 정의를 두고 갈등할 때 중재할 책임자가 명확해야만 아키텍처가 부패하지 않고 유지된다.

원문이 강조하는 핵심 메시지는 명료하다. 의존성 순서는 철저히 상향식(Bottom-up)으로 흘러간다. 신뢰할 수 없는 원천 데이터 위에 구축된 맥락 계층은 모래 위의 누각이며, 맥락 계층이 결여된 에이전트 도구 호출은 언제 폭발할지 모르는 시한폭탄이다. 반면 관측 가능성(Observability)은 나중에 덧붙이는 것이 불가능에 가까우므로 프로젝트 첫날부터 모든 워크플로의 바닥에 깔아 두어야 한다.

한국 엔지니어링 조직이 지금 즉시 실행에 옮겨야 할 우선순위는 다음과 같이 정리할 수 있다.

7.1 사내 시스템(ERP·CRM·DB) 연계 시 우선 점검 체크리스트

사내 시스템에 에이전트를 연결하려는 팀은 먼저 가장 위험도가 높은 소수의 데이터셋(가격, 재고, 고객 원장)을 선별하고, 해당 데이터에 대한 최신성 SLA를 정의하는 것부터 착수해야 한다. 배치 주기가 달라지는 순간 에이전트가 잘못된 답변을 내놓을 수밖에 없음을 인정하고, 계약 위반 데이터를 데드 레터 큐로 격리하는 서킷 브레이커를 소프트웨어 레벨에서 먼저 구축해야 한다.

7.2 도구 도입보다 중요한 데이터 제품(Data as a Product) 소유권 확립

에이전트가 어떤 모델을 사용할지, 어떤 에이전트 라이브러리를 쓸지 논쟁하는 데 시간을 쓰기 전에, 사내에서 가장 논쟁적인 핵심 지표 하나를 골라 버전 관리되는 시맨틱 모델 코드로 고정하는 협의를 시작해야 한다. 비즈니스 정의를 명시적으로 코딩하는 작업은 기술적 난이도보다 조직 간의 합의가 핵심이며, 이 합의 과정을 거친 기업만이 안전하고 지속 가능한 자율 에이전트 시대를 맞이할 수 있다.

  • 첫날부터 관측성 계측: 에이전트가 배포되기 전부터 모든 도구 호출과 추론 체인을 추적하도록 계측 구성
  • 핵심 데이터 계약화: 전사 확장이 아닌 가격, 재고 등 비즈니스 위험이 가장 큰 도메인부터 계약 적용
  • 맥락의 코드화 우선: 모델 교체보다 시맨틱 모델을 통한 지표 정의 강제가 정확도 향상에 훨씬 큰 영향 제공
  • 쓰기 작업 전 읽기 격리: MCP Resources를 통해 문서를 먼저 노출하고, 감사 체계 검증 후 Tools를 도입
  • 명확한 제품 소유권 지정: 데이터 계약과 지표 정의를 유지 관리할 현업 도메인 팀과 책임자 명시

확인하지 못한 것

본 글은 마틴 파울러 공식 웹사이트에 게재된 원저자(Pramod Sadalage, Prem Chandrasekaran)의 아티클 및 관련 기술 표준 문서를 대조하여 작성되었다. 다만 원문 및 공개 자료의 범위 한계로 인해 다음 항목들은 본 분석에서 확정적으로 기술하지 못하였으며, 추가적인 검증이 필요하다.

  • 에이전트 품질 점수 산출 알고리즘: 원문은 모델 자체의 신뢰도와 데이터 최신성·완전성 신호를 단일 점수로 결합하는 가중 점수제 방식이 현재 미해결된 설계 과제(Open design problem)라고 명시하고 있으며, 상용 환경에서 검증된 구체적인 합성 알고리즘 수식은 제시하지 않았다.
  • Adaptive Gold 뷰 생성 엔진의 내부 스펙: Apple의 데이터 카탈로그 디지털 스튜어드 사례 외에, 에이전트가 자신의 질의 패턴을 분석해 웨어하우스 뷰를 자율적으로 생성하는 구체적인 오픈소스 구현체나 상세 메커니즘은 원문에 서술되어 있지 않다.
  • 국내 주요 ERP/CRM 벤더의 네이티브 MCP 지원 여부: SAP, 영림원, 더존비즈온 등 국내 기업들이 주로 사용하는 엔터프라이즈 시스템의 네이티브 데이터 계약 및 MCP 서버 공식 지원 로드맵은 원문의 분석 범위에 포함되지 않았으므로 서술에서 제외하였다.
