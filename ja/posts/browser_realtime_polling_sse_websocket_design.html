契機 — 「リアルタイム」という言葉が覆い隠す3つの要件

仕様書や要件定義書に「この画面はリアルタイムで反映されなければならない」と記載されている場合、開発者は即座にWebSocketの導入を考えがちである。しかし現実の画面要件は一様ではない。共同編集ドキュメントにおけるカーソル位置の追従、大容量ファイルの変換完了通知、チャットメッセージの受信では、許容される遅延時間も、一時的な通信切断時に復旧すべきデータの性質も全く異なる。

計算機工学においてリアルタイム(real-time)とは、出力の論理的正しさだけでなく、結果が出力される時刻(デッドライン)を守ることまでを含めて正しさと定義する概念である。カーネギーメロン大学SEIの分類によれば、デッドライン超過の影響度によってシステムは3つに大別される。一度でもデッドラインを越えるとシステム全体の破綻を招くハードリアルタイム、遅れた結果の価値は完全に消失するが破綻には至らないファームリアルタイム、遅延に伴って結果の有用性が徐々に低下するソフトリアルタイムである。一般的なWebブラウザは非決定論的な実行環境であり、厳密なハードリアルタイムを保証することは困難であって、大半はソフトリアルタイムまたはファームリアルタイムの領域に属する。

したがって曖昧な「リアルタイム」という言葉を設計可能な具体的要件へ落とし込むには、まず以下の3つの問いに答えなければならない。

  • どれほど遅れても許容されるか (許容遅延と達成率): 処理発生から画面描画までに許容される最大遅延時間と、それを達成すべき目標パーセンタイル(例: 99%の要求が2秒以内)を定義する。
  • 誰がいつ通信を主導するか (方向と頻度): サーバーが一方的に変更を通知する形態か、クライアントが頻繁にコマンドを送出するか、通信頻度が毎秒数十回か数分に1回かを区別する。
  • 欠落したデータをどう取り戻すか (状態復旧戦略): 一時切断後の再接続時に最新の現在状態のみを取得すればよいか、欠落したすべてのイベントを順序正しく再生(replay)する必要があるかを決定する。

これら3つの評価軸により、選択すべきトランスポートとプロトコル契約が明確になる。下表はWebで用いられる主要なリアルタイム通信手法の伝送特性と責任分界を整理したものである。

遅延と鮮度は異なる要件である — レンダリングパイプラインのボトルネック

リアルタイム設計において最も混同しやすいのが遅延(latency)と鮮度(freshness)の違いである。遅延時間はイベントがサーバーで確定してからクライアントがそれを観測するまでの経過時間を指す。これに対して鮮度は、クライアント画面に描画されている状態が現在のサーバーの正規状態とどれほど一致しているかを表す整合性の指標である。

例えば1分間の通信断絶を経験したブラウザが、再接続直後に20ミリ秒という極めて低い往復遅延でパケットを受信したとする。しかし切断中の1分間に発生した状態変更が補填されていなければ、表示されている画面は最新パケットを受け取っていても全体として著しく古い状態のままである。逆に丸一日何の変更も発生していない静的データであれば、前回の同期が数時間前であっても画面の鮮度は100%保たれている。

サーバーでデータが確定してから画面上にピクセルとしてレンダリングされるまでには、以下のパイプラインを通過する。

  • サーバー内部処理と送信キュー: DBトランザクション確定からブローカー配信、ソケット送信バッファへの蓄積遅延。
  • ネットワーク伝送とプロキシバッファ: パケット伝送時間、ルーターホップ、CDNやリバースプロキシのバッファリング。
  • ブラウザネットワーク層のパース: TCPセグメントの再構築、TLS復号、プロトコルフレームのデコード処理。
  • JavaScriptタスクキューの待機: メインスレッドのイベントループが現在実行中のタスクを完了するまでの遅延。
  • DOM操作と描画パイプライン: スタイル再計算、レイアウト(Reflow)、ペイント、コンポジット処理。

どれほど低遅延なWebSocketプロトコルを採用しても、ブラウザのメインスレッドが巨大なJSON解析や重いDOM操作で占有されていればイベント処理は著しく遅れる。ブラウザ標準のsetTimeout(fn, 100)でさえ100msを厳密に保証するものではなく、先行タスクによって容易に遅延する。メインスレッド負荷の分離についてはブラウザメインスレッドのコスト解説で詳細を扱っている。ネットワーク速度だけでエンドツーエンドのリアルタイム性を担保することはできない。

ポーリングとロングポーリング — 周期問い合わせのコストと応答待機の隙間

最も直感的なリアルタイム化の手法は、一定間隔でHTTPリクエストを送信するポーリングである。既存のWebキャッシュ、認可ゲートウェイ、CDNインフラをそのまま再利用できるため導入が容易である。しかし固定周期Δでポーリングを実施する場合、遅延時間とサーバー負荷のトレードオフは数式通りに制約される。

サーバー側のデータ変更が時間軸上に均等に分布し、問い合わせ処理時間が十分に短いと仮定すれば、クライアントが変更を検知するまでの平均待機時間は約Δ / 2となる。遅延を半減させるには周期を半分にする必要があり、クライアント数Nに比例して総リクエスト量(N / Δ)は正確に2倍に跳ね上がる。例えば1万クライアントが5秒間隔でポーリングを行えば毎秒2,000リクエストがサーバーに到達し、データの変更が全くない状況でも膨大な帯域とDBリソースを消費し続ける。

さらにsetIntervalで安易にリクエストを繰り返すと深刻な障害を招く。ネットワークの乱れで応答が遅延した際、先行リクエストが完了しないまま次のリクエストが発行される。応答の到着順序が逆転すれば、過去のレスポンスが最新データを上書きする不整合が生じる。これを回避するには、完了を待って次回タイマーをセットする直列化と、指数バックオフ(exponential backoff)およびランダムなジッター(jitter)の実装が不可欠である。

function startPolling({ read, apply, onError }, intervalMs = 5000) {
                      let stopped = false;
                      let timer;
                      let inFlightController;
                      let failures = 0;
                    
                      async function tick() {
                        if (stopped) return;
                        const controller = new AbortController();
                        inFlightController = controller;
                        const timeout = setTimeout(() => controller.abort(), 10000);
                    
                        try {
                          const data = await read(controller.signal);
                          if (stopped) return;
                          apply(data);
                          failures = 0;
                        } catch (err) {
                          if (stopped) return;
                          failures += 1;
                          onError(err);
                        } finally {
                          clearTimeout(timeout);
                          inFlightController = null;
                          if (!stopped) {
                            const backoffCap = Math.min(60000, intervalMs * (2 ** Math.min(failures, 4)));
                            const delay = failures ? backoffCap * (0.5 + Math.random() * 0.5) : intervalMs;
                            timer = setTimeout(tick, delay);
                          }
                        }
                      }
                    
                      void tick();
                      return () => {
                        stopped = true;
                        clearTimeout(timer);
                        inFlightController?.abort();
                      };
                    }

ロングポーリングは変更が生じるまでサーバーがHTTPレスポンスを返さずに接続を保留(hold)する方式である。イベント発生時またはタイムアウト(例: 30秒)時に即座に応答し、クライアントはレスポンス受領後ただちに次の接続を開く。これにより平均待機遅延(Δ / 2)を排除できる。

しかしロングポーリングには構造的な「応答と次リクエストの隙間」が存在する。レスポンスを受信して次のリクエストがサーバーへ届くまでの短い空白期間にサーバー側で新たなイベントが発生した場合、その変更は消失する。これを防ぐには、サーバー側でカーソルに基づきイベントを保持し、クライアントが次回リクエストに最終カーソルを付与して問い合わせる契約が必須となる(RFC 6202参照)。

SSE(Server-Sent Events) — HTTP単方向ストリームと自動再接続の限界

Server-Sent Events(SSE)はWHATWG HTML仕様で定義された標準技術であり、単一のHTTPリクエストに対してサーバーがtext/event-stream形式のテキストデータを接続を切断せずにストリーミング配信する。ブラウザ側では標準のEventSource APIを用いて容易に購読できる。

SSEのデータ形式はシンプルであり、連続する改行コード( )によって各イベントの境界を区切る。

Content-Type: text/event-stream
                    Cache-Control: no-cache
                    Connection: keep-alive
                    
                    id: evt-1001
                    event: order-status
                    retry: 3000
                    data: {"orderId": "ord-881", "status": "completed", "version": 4}
                    
                    : keep-alive heartbeat

SSEの最大の利点は、ブラウザ仕様のレベルで自動再接続が組み込まれている点である。回線切断等でストリームが中断した場合、ブラウザはretryフィールドで指定された時間待機した後に自動で再接続を試行する。この際、前回最後に受信したidの値をLast-Event-IDリクエストヘッダーへ自動的に付与する。サーバーはこのヘッダーを読み取り、保持しているログから未達イベントのみを再生配信できる。

しかし実務においては以下の運用制約に留意しなければならない。

  • リクエストヘッダーのカスタマイズ不可: ブラウザ標準のEventSourceコンストラクタは任意のHTTPヘッダー(例: Authorization)を送信できない。クエリ文字列にトークンを渡すとアクセスログ等に資格情報が漏洩するリスクがある。
  • リバースプロキシのバッファリング: NginxやCDNがレスポンスバッファリングを行っていると、バッファが満杯になるまでイベントが滞留してリアルタイム性が損なわれる。Nginx環境ではX-Accel-Buffering: noヘッダー等でバッファを停止する必要がある。
  • HTTP/1.1の接続数制限: HTTP/1.1環境では同一ドメインに対する同時接続数が6本に制限されており、複数タブを開くと容易にソケットが枯渇する。この問題はHTTP/2のマルチプレキシング環境を適用することで解消される。
  • 完全な単方向性: クライアントからサーバー方向へのメッセージ送信はできないため、ユーザー操作による状態更新は別途通常のHTTP POSTリクエスト等で送る必要がある。

WebSocket — 全二重メッセージングとアプリケーション層の責務

WebSocket(RFC 6455)は、単一の持続的TCP接続上でブラウザとサーバー間の全二重(full-duplex)かつ双方向のメッセージ通信を実現するプロトコルである。HTTP Upgradeハンドシェイクを経て接続を確立した後は、軽量なフレーム単位でテキストやバイナリを送受信できる。

クライアントとサーバー双方がいつでも自律的にデータを送信できるため、共同編集キャンバス、オンライン対戦ゲーム、超高速な金融取引画面などに最適である。標準クライアントAPIはイベントリスナーの登録を通じて利用される。

const socket = new WebSocket('wss://example.com/stream');
                    
                    socket.addEventListener('open', () => {
                      socket.send(JSON.stringify({ type: 'subscribe', channel: 'orders' }));
                    });
                    
                    socket.addEventListener('message', (event) => {
                      try {
                        const payload = JSON.parse(event.data);
                        handleMessage(payload);
                      } catch (err) {
                        reportError('Payload parse failure', err);
                      }
                    });
                    
                    socket.addEventListener('close', (event) => {
                      scheduleReconnect(event.code, event.reason);
                    });

しかし看過されがちな事実として、標準のWebSocket APIには自動再接続の仕組みが一切存在しない。SSEであればブラウザが自動的に処理してくれたバックオフ制御やセッション復旧を、すべてアプリケーションエンジニアが自前で記述しなければならない。さらに以下の重大な責務が課される。

  • 接続完了と購読完了の厳密な分離: ソケットのopenイベントはトランスポート層の確立を意味するだけであり、サーバー側で認可やトピック購読が完了したことではない。サーバーからの明示的な購読承認ACKメッセージを受信するまで、データ送受信の準備完了と見なしてはならない。
  • アプリケーション層のハートビート実装: RFC 6455にはPing/Pongフレームの規定があるが、ブラウザJavaScriptにはPingを直接送出するAPIが露出していない。そのためアプリケーションレベルで定期的なping/pongメッセージをやり取りしてハングした接続を検知する必要がある。
  • 受信バックプレッシャーの欠落: サーバーがクライアントの処理能力を超える大量メッセージを連続送信した場合、ブラウザ側から送信速度を抑制させる標準APIが存在しない。未処理キューが肥大化してタブがクラッシュすることを防ぐため、キューの上限設定や最新値の上書き合算処理が必要となる。
  • CORS非適用に伴うセキュリティ対策: WebSocketはブラウザの同一生成元ポリシー(SOP)やCORSプリフライトの制約を受けない。悪意ある外部サイトから社内WebSocketへ不正接続されるCSWSHを防ぐため、サーバー側でOriginヘッダーを厳格に照合しなければならない。

再接続後の状態復旧 — スナップショットとカーソルの分離

リアルタイムシステムの真価は平常時ではなく、ネットワーク断絶から復帰した際に生じる状態の不整合をいかに矛盾なく修復できるかで決まる。単にソケットを再接続してトピックを再購読するだけでは、切断中にサーバー側で起きたイベントは決して取り戻せない。

「再接続時にRESTで現在一覧を全件取得し、その直後にWebSocketを購読する」という設計には致命的な競合状態(race condition)が潜んでいる。スナップショットを取得してからリアルタイム購読が有効化されるまでのわずかな隙間に発生した更新は、取得したスナップショットにも含まれず、以降のストリームにも流れてこないため完全に消失する。

この問題を防ぐ確実な設計は、スナップショットとその時点におけるイベントログのカーソル(cursor)を不可分に返却する契約である。クライアントが全件取得を要求すると、サーバーは現在のデータと同時にその時点のカーソルCを返す。クライアントは再接続時にこのカーソルCを添えて購読を開始し、サーバーはC以降の未達イベントを再生配信した上でライブ配信へと接続をシームレスに切り替える。

この整合性を保つため、システムは以下の表に示す5つの異なる識別子(ID)を設計上明確に分離しなければならない。

識別子担当する責務保証される不変条件単独使用時の限界
イベントID (Event ID)個別メッセージの一意性識別同一イベントの重複受信検知と除外イベント間の順序や欠落の有無は証明できない
カーソル (Cursor)ストリームログ上の単調増加位置切断後にどの地点から再開すべきかの位置情報エンティティの最新状態そのものは表現できない
エンティティバージョン (Version)特定レコードの更新世代管理古い遅延レスポンスによる最新画面の上書き防止ストリーム全体の順序関係は関知しない
リクエストID (Request ID)非同期通信と元操作の紐付け非同期メッセージ応答がどの操作の結果かを識別通信切断時の安全な再試行(再実行)は保証できない
冪等キー (Idempotency Key)コマンドの重複実行防止応答欠落に伴う再試行時における二重処理の防止データ更新後の画面反映順序とは無関係

また画面のUI状態を単一の真偽値isConnectedだけで管理してはならない。接続が確立していても同期処理が完了していない間にユーザーが操作を行えば不整合が拡大する。状態機械は切断中、接続試行中、接続済み(同期中)、最新同期完了、同期失敗の各フェーズを厳格に区別して画面に提示すべきである。

順序保証と再送制御を切り離すトランスポート層の代替選択肢

TCPを基盤とするWebSocketやHTTP/2 SSEは、完全なパケット順序保証と信頼性のある再送を提供する。しかしこの信頼性にはトランスポート層におけるHead-of-Line Blocking(HOLB)という代償が伴う。インターネット上で1つのパケットが欠落した場合、OSのTCPスタックは欠落パケットが再送され到着するまで、後続の正常パケットをアプリケーション層へ渡さずに内部バッファへ留め置く。

協調作業画面におけるマウスポインターの座標データやビデオ通話中のジェスチャーデータなどは、過去のパケットをわざわざ再送して取り戻す価値が薄い。2番の座標パケットが落ちたなら、その再送を待って3番や4番の座標まで遅延させるより、2番を潔く破棄して最新の4番を即座に描画する方が滑らかな体験を提供できる。

このような要件に対応するブラウザ標準としてWebRTC DataChannelとWebTransportが存在する。WebRTC DataChannelはSCTPおよびDTLS上で動作し、チャンネル単位で順序保証と再送回数の挙動を変更できる。

const positionChannel = peerConnection.createDataChannel('cursor-positions', {
                      ordered: false,
                      maxRetransmits: 0,
                    });
                    
                    positionChannel.addEventListener('message', (event) => {
                      const { userId, x, y, seq } = JSON.parse(event.data);
                      applyCursorPosition(userId, x, y, seq);
                    });

ordered: falseおよびmaxRetransmits: 0を指定すると、パケット欠落時に再送を行わず後続パケットを直ちにアプリケーションへ引き渡すため、Head-of-Line Blockingが完全に解消される。ただしWebRTCはシグナリングサーバーやSTUN/TURNインフラを運用する必要がある。一方、HTTP/3およびQUICを基盤とするWebTransportはUDP上でストリームと非信頼性データグラムを直接扱えるため、インフラの普及に伴い今後の有力な選択肢となっている。

バックグラウンドタブとService Workerのライフサイクル制約

ブラウザ上で動作するリアルタイムアプリケーションは、ネイティブアプリとは異なりPage Lifecycle仕様に基づく厳しいリソース制御を受ける。ユーザーがタブを非アクティブ化したり最小化したりした場合、ブラウザエンジンは省電力とメモリ確保のために実行抑制を開始する。

バックグラウンドに回ったタブはJavaScriptタイマーが毎秒1回以下に厳しくスロットリングされ、場合によってはスレッドの実行自体が凍結(Freeze)される。モバイル環境ではメモリ圧迫時に非アクティブなタブのプロセス自体が強制破棄(Discard)されることもある。タブが開かれているからといって常時接続が維持されていると過信してはならない。

  • 画面可視性の復帰検知: document.visibilityState === 'visible'イベントを検知し、ユーザーがタブへ戻った瞬間にソケットの生存確認とスナップショット同期を直ちに発動させる。
  • Web Workerの限界: 接続処理をWeb Workerに移譲すればメインスレッドのUIブロックは回避できるが、OSやブラウザがタブ全体を凍結・破棄するポリシー自体を回避することはできない。
  • Service Workerは常時ソケットサーバーではない: Service Workerはプッシュ通知などの特定イベント駆動でのみ起動する仕組みであり、アイドル時にはブラウザによって強制停止されるため、持続的なWebSocket接続を維持する用途には使えない。
  • Push APIとの復旧連携: タブが完全に閉じている状態での緊急通知にはPush APIが適しているが、プッシュ通知には到達時刻の保証がない。通知をクリックして画面が開かれた際にサーバーから正規状態を再取得する連携設計が不可欠である。
  • 複数タブ間での接続共有: 同一ドメインでタブごとにソケットを開く無駄を省くため、BroadcastChannelやSharedWorkerを用いてリーダータブを1つ選出し接続を集約する設計がある。しかしタブ終了時のリーダー選出やログアウト時の後処理など状態機械が高度化するため慎重な判断が必要である。

実務検証 — ネットワーク切断と欠落を再現する9つの試験シナリオ

ローカル開発環境のローカルホスト上で通信がスムーズに動いたとしても、本番投入の準備が整ったことにはならない。実際のネットワーク環境ではパケット損失、モバイル回線のハンドオーバー、プロキシのタイムアウトなど様々な障害が発生する。システムの耐障害性を事前に評価するための9大検証シナリオは以下の通りである。

  • 30秒間の切断とサーバー側の状態変更: クライアントの通信を30秒遮断した間にサーバー側でデータを更新し、復旧後に欠落した変更が漏れなく順序通りに反映されるか、あるいは最新スナップショットで正常置換されるかを検証する。
  • コマンド処理後のレスポンス欠落: 登録や更新コマンドはサーバーで処理されたが応答パケットが途中で消失した状況を模擬し、クライアントが冪等キーを用いて安全に再試行し二重実行が防止されるかを確認する。
  • 古いHTTPレスポンスの遅延到着: 一覧取得リクエストが遅延し、最新のリアルタイムストリームを受信した後に古いレスポンスが遅れて届いた際、バージョン判定によって古いデータが画面を上書きしないことを検証する。
  • メインスレッドの占有とイベント大量流入: 重い同期処理でメインスレッドが3秒間停止した間に大量のイベントが到着した場合、メモリリークを起こさずキュー上限内で最新値へ正常に縮約されるかを確認する。
  • サーバーインスタンスの再起動と別ノード再接続: ロードバランサー配下の特定ソケットサーバーを停止させ、クライアントが別ノードへフェイルオーバーした際に、分散ストアを通じてカーソルや購読状態が正常復元されるかを検証する。
  • イベント保持期限を超過した長期切断: クライアントが保持するカーソルがサーバー側のログ保持期限(TTL)を超過していた場合、サーバーがエラーを明示的に返し、クライアントが安全にスナップショット初期化へフォールバックできるかを確認する。
  • タブ切り替えと端末スリープ復帰: タブをバックグラウンドに下げて10分放置した後に復帰させた際、未確認の古い状態を「最新」と誤表示せず、同期中インジケーターを経て整合性を回復できるかを検証する。
  • ログアウトおよび別アカウントへの切り替え: ユーザーがログアウトした瞬間に既存のソケット接続と購読が即時破棄され、別アカウントでログインした際に前ユーザーの機密イベントが画面へ漏洩しないことを確認する。
  • 本番CDNおよびロードバランサー経由の検証: 本番環境のCDNやL7ロードバランサーを通過させ、バッファリングによる遅延やアイドルタイムアウトによる周期的切断が発生しないかを検証する。

確認できなかった事項

  • クラウドベンダー別マネージドWebSocketの内部キュー仕様: AWS API Gateway WebSocketやCloudflare Workers Durable Objects等のマネージド基盤における詳細な内部バッファ上限値はベンダー固有であり本稿では数値化していない。
  • OS別バックグラウンドネットワーク切断の厳密なしきい値: iOS WebKitおよびAndroid Chromeが画面ロック時にソケットを切断するまでの正確な時間しきい値はOSの省電力ヒューリスティクスに依存するため一概に特定できなかった。
  • グローバルネットワークにおけるWebTransport到達率: 2026年時点における企業ファイアウォール環境でのWebTransport(UDP)通過率の実測値はプロバイダ構成により多岐にわたるため直接検証できていない。
  • 大規模分散ブローカーにおけるカーソルシャーディング遅延: KafkaやRedis Streamsをバックエンドに採用した超大規模構成において、数百万接続規模でのパーティション間カーソル整合性維持に関するベンチマーク数値は本稿の範囲に含まれていない。
