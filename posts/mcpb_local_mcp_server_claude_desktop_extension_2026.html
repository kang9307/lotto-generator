계기 — 복잡한 설정 파일 편집을 원클릭 확장 설치로 전환하는 MCPB

엔지니어링 블로그 「Desktop Extensions」는 로컬 MCP 서버가 Claude에 파일 시스템부터 데이터베이스까지 접근을 열어 주었지만 설치가 너무 복잡하다는 의견이 계속 들어왔다고 적는다. 사용자는 개발 도구를 갖춰야 했고, 설정 파일을 직접 편집해야 했으며, 의존성 문제에서 막히는 일이 많았다는 것이다. 블로그는 그 장벽을 다섯 가지로 꼽는다. 개발 도구 필요(Node.js, Python 등의 런타임 설치), 수동 설정(서버마다 JSON 설정 파일 편집), 의존성 관리(패키지 충돌과 버전 불일치 해결), 발견 수단 없음(유용한 서버를 찾으려면 GitHub 검색), 업데이트 복잡(최신 상태 유지가 수동 재설치)이다.

MCPB(.mcpb)는 이 문제에 대한 답으로 소개된다. 공식 문서는 MCP 번들을 로컬 MCP 서버와 manifest.json을 담은 zip 아카이브라고 정의하고, Claude Desktop이 브라우저가 확장을 설치하듯 한 번의 클릭으로 설치한다고 설명한다. 이 형식은 원래 DXT(Desktop Extensions, .dxt)라는 이름이었다. README는 프로젝트가 DXT에서 MCPB로 이름이 바뀌는 중이라고 공지하며 dxt CLI가 mcpb가 되고, .dxt 파일이 .mcpb 파일이 되고, @anthropic-ai/dxt 패키지는 @anthropic-ai/mcpb로 옮겨질 예정(will be moved)이라고 적는다. 이름을 바꾼 이유는 README에 적혀 있지 않다. 블로그는 2025년 9월 11일 자 안내에서 기존 .dxt 확장은 계속 동작하고 새 확장에는 .mcpb를 권하며 기능은 그대로라고 밝혔다. README는 이 형식이 Chrome 확장(.crx)이나 VS Code 확장(.vsix)과 정신적으로 비슷하다고 설명한다.

사용자 쪽 절차는 블로그가 세 단계로 요약한다. .mcpb 파일을 내려받고, 더블클릭해 Claude Desktop으로 열고, 설치(Install)를 누른다. 터미널도 설정 파일도 의존성 충돌도 없다는 설명이다.

  • 첫째, 설치 과정에서 설정 파일을 직접 편집하지 않는다. 블로그가 대비해 보여 주는 이전 방식과 새 방식의 차이가 이 점이다.
  • 둘째, 서버의 실행 방법과 필요한 설정은 manifest.json에 선언한다. MANIFEST.md는 manifest_version, name, version, description, author, server를 필수 필드로 둔다.
  • 셋째, 민감한 설정은 별도로 다룬다. 블로그는 API 키 같은 민감 값이 OS 키체인에 저장된다고 적고, MANIFEST.md는 sensitive 값을 가리고 안전하게 저장한다(store securely)고 적는다.
  • 넷째, 서버는 사용자 PC에서 stdio로 실행되며 클라우드 인프라가 필요 없고, 오프라인으로 동작하며, OAuth가 필요 없다. 공식 문서가 MCPB의 특성으로 꼽는 항목이다.

README는 이 저장소가 세 가지를 제공한다고 소개한다. MANIFEST.md의 번들 명세, 번들을 만드는 CLI, 그리고 Claude for macOS와 Windows가 MCPB 번들을 불러오고 검증하는 데 쓰는 코드다.

아키텍처 — 사용자 PC에서 stdio로 도는 로컬 서버

공식 문서의 첫 문단이 아키텍처의 핵심을 말한다. 서버는 사용자의 머신에서 stdio로 실행되므로 클라우드 인프라 없이도 로컬 파일, 로컬에 설치된 도구, 사용자 방화벽 뒤의 시스템에 닿을 수 있다. 같은 문서는 두 방식의 실행 위치를 이렇게 대비한다. MCPB는 사용자 머신에서 stdio로 로컬과 내부 자원에 접근하며 동작하고, 원격 커넥터는 개발자의 서버에서 HTTPS로 실행되어 Anthropic의 인프라를 거쳐 접근된다. 조직들이 MCPB를 내부 MCP 서버로 가는 보안 프록시, 내부 문서 접근, 개발 도구 연결에 보안 구조를 유지한 채 쓰는 경우가 흔하다고도 적는다.

문서가 MCPB의 특성으로 꼽는 것은 다섯 가지다. 사용자 머신에서 로컬로 실행되고, stdio 전송으로 통신하고, 모든 의존성을 번들에 담고, 오프라인에서 동작하고, OAuth가 필요 없다는 점이다.

공식 문서(Build a desktop extension with MCPB)는 로컬 MCPB와 원격 커넥터(Remote Connector)를 고르는 기준을 표로 제시한다. 아래 표는 그 표의 항목을 네 가지 관점으로 묶어 다시 정리한 것이다.

선택 기준 로컬 MCPB (.mcpb) 원격 커넥터 (Remote Connector)
네트워크 및 방화벽 사내 방화벽 뒤의 시스템(이슈 트래커, 사내 위키, 내부 DB) 접근 중앙 클라우드 인프라 기반의 퍼블릭 API 및 클라우드 서비스
인증 및 자격증명 기존 SSO 및 로컬 브라우저 세션 활용, 토큰 관리 불필요 OAuth 흐름과 서버 측 토큰 관리
데이터 보존 및 보안 기기 외부로 유출되면 안 되는 민감 작업 및 로컬 파일시스템 직접 제어 웹, 모바일, 데스크톱 전역에 걸친 다중 클라이언트 중앙 배포
런타임 및 의존성 Claude Desktop에 내장된 Node.js 런타임 활용, 별도 인프라 불필요 중앙 서버에서 코드 및 서비스를 일괄 배포하고 즉각 업데이트

원문 표에는 위 항목 외에도 MCPB 쪽 선택 이유가 더 있다. 코드 편집과 Git 작업을 위한 직접 파일 시스템 접근, Docker·IDE·데이터베이스 같은 로컬 설치 도구와의 연동, 하드웨어 연동과 데스크톱 애플리케이션 제어, 번들된 Node.js 런타임으로 의존성을 관리할 필요 없는 원클릭 설치, 클라우드 인프라·VPN 설정·방화벽 규칙이 필요 없다는 점, 커스텀 업로드와 허용 목록 같은 조직 수준의 관리자 통제, 인증·인가·감사 로그에 대한 완전한 통제다.

로컬 stdio 실행 모델에서 문서가 직접 적은 내용은 다음 네 가지다.

  • 로컬 실행: 서버는 사용자의 머신에서 돌며 로컬 파일과 로컬에 설치된 도구에 접근한다.
  • stdio 전송: Claude Desktop과 서버는 stdio 전송으로 통신한다.
  • 오프라인 동작: 문서는 MCPB가 오프라인에서 동작한다고 적는다.
  • 인증과 인프라: OAuth가 필요 없고, 기존 SSO와 브라우저 세션으로 인증하면 토큰을 관리하지 않아도 되며, 클라우드 인프라가 필요 없다.

이 네 가지를 넘어선 해석, 예를 들어 포트 개방 여부나 프로세스 권한 경계에 대한 서술은 이 문서들에 없다. 이 글도 그 부분은 문서가 말한 범위까지만 옮긴다.

런타임 선택 — Node.js 번들 내장과 Python 의존성 처리

MCPB 확장을 개발할 때 가장 먼저 정할 것은 구현 언어다. 공식 문서는 Node.js를 강력히 권장(strongly recommended)하며 이유 세 가지를 든다. Claude Desktop에 macOS와 Windows용으로 포함되어 있어 사용자가 별도 런타임이 필요 없고, Claude Desktop과의 호환성과 안정성이 가장 좋고, MCP SDK 지원이 폭넓다는 것이다. 블로그도 Claude Desktop과 함께 Node.js를 제공해 외부 의존성을 없앴다고 적는다.

README는 같은 권고를 설치 마찰의 관점에서 쓴다. Node.js는 macOS와 Windows용 Claude에 함께 오므로 번들이 사용자에게 추가 Python 런타임 설치를 요구하지 않고(혹은 개발자가 그 런타임을 직접 패키징하지 않아도) 바로 동작한다는 설명이다. 플랫폼은 macOS(darwin)와 Windows(win32)이며, 지원 플랫폼은 manifest.json의 compatibility 섹션에 적는다. 한 플랫폼에서 주로 개발하더라도 양쪽에서 테스트하라고 문서가 권한다.

README의 「Bundling Dependencies」는 서버 유형별로 의존성을 다루는 방식이 다르다고 정리한다.

  • Node.js 번들: npm install --production으로 node_modules를 만들고 그 디렉터리 전체를 번들에 포함하라고 한다. 재현 가능한 빌드에는 npm ci나 yarn install --frozen-lockfile을 쓰고, 서버 진입점은 server.entry_point로 지정한다. MANIFEST.md도 Node.js 확장은 모든 의존성을 node_modules에 번들해야 한다고 적는다.
  • Python 번들(전통 방식): server.type = "python"을 쓰고, 필요한 패키지를 server/lib/에 번들하거나 완전한 가상환경을 server/venv/에 번들한다. mcp_config.env로 PYTHONPATH를 지정해 번들 패키지를 가리킨다. README는 한계도 명시한다. 컴파일된 의존성(MCP Python SDK가 요구하는 pydantic 같은 것)은 이식 가능하게 번들할 수 없다는 점이다.
  • uv 유형(v0.4+): server.type = "uv"로 두고 의존성을 적은 pyproject.toml을 포함한다. 번들된 패키지가 필요 없고 호스트 애플리케이션이 Python과 의존성을 자동으로 관리하며, 사용자의 Python 설치 없이 여러 플랫폼에서 동작한다고 README가 적는다. MANIFEST.md의 uv 예시는 manifest_version이 0.4다.
  • 바이너리 번들: 최대 호환성을 위해 정적 링크를 선호하고, 동적 링크를 쓰면 필요한 공유 라이브러리를 모두 포함하며, 개발 도구가 없는 깨끗한 시스템에서 테스트하라고 한다. MANIFEST.md는 바이너리 유형을 모든 의존성이 포함된 사전 컴파일 실행 파일이라고 설명하고 플랫폼별 바이너리도 지원한다고 적는다.

정리하면 README는 Node.js가 Claude에 포함되어 있어 Python 런타임을 따로 설치하거나 직접 패키징할 필요가 없다는 점을 Node.js를 권하는 이유로 든다. 그렇다고 Python 서버가 모두 의존성을 통째로 번들해야 하는 것은 아니다. 전통적인 python 유형은 패키지를 번들에 담아야 하고 컴파일 의존성에 한계가 있지만, uv 유형은 이 부담을 호스트로 넘긴다.

매니페스트 규격(v0.3) — 필수 필드와 설정 UI 자동 생성

manifest.json은 번들에 꼭 있어야 하는 유일한 파일이다. 공식 문서는 이 파일이 MCPB가 하는 일, 실행 방법, 제공하는 도구, 필요한 설정을 설명하는 필수 메타데이터라고 적는다. MANIFEST.md는 현재 버전이 0.3이고 최종 갱신일이 2025년 12월 2일이며 대부분의 필드가 선택이라고 밝힌다. 필수 필드만 갖춘 기본 매니페스트는 다음과 같다.

{
                      "manifest_version": "0.3",
                      "name": "my-extension",
                      "version": "1.0.0",
                      "description": "A simple MCP extension",
                      "author": {
                        "name": "Extension Author"
                      },
                      "server": {
                        "type": "node",
                        "entry_point": "server/index.js",
                        "mcp_config": {
                          "command": "node",
                          "args": [
                            "${__dirname}/server/index.js"
                          ]
                        }
                      }
                    }

MANIFEST.md의 설명에 따르면 ${__dirname}은 확장 디렉터리로 치환된다. 블로그는 이 값이 확장이 풀린 디렉터리의 전체 경로로 바뀐다고 적는다. 사용자에게서 값을 받아야 하는 서버라면 user_config 블록을 둔다. 공식 문서는 user_config를 정의하면 Claude Desktop이 확장용 설정 UI를 자동으로 만든다고 설명한다. 블로그의 예시 해설은 더 구체적이다. 개발자가 사용자가 api_key를 줘야 한다고 선언하면 Claude는 그 값이 입력될 때까지 확장을 켜지 않고, 값을 운영체제의 비밀 저장소에 자동으로 보관하며, 서버를 실행할 때 ${user_config.api_key}를 사용자가 준 값으로 투명하게 바꿔 넣는다.

{
                      "manifest_version": "0.3",
                      "name": "my-extension",
                      "version": "1.0.0",
                      "description": "A simple MCP extension",
                      "author": {
                        "name": "Extension Author"
                      },
                      "server": {
                        "type": "node",
                        "entry_point": "server/index.js",
                        "mcp_config": {
                          "command": "node",
                          "args": ["${__dirname}/server/index.js"],
                          "env": {
                            "API_KEY": "${user_config.api_key}"
                          }
                        }
                      },
                      "user_config": {
                        "api_key": {
                          "type": "string",
                          "title": "API Key",
                          "description": "Your API key for authentication",
                          "sensitive": true,
                          "required": true
                        }
                      }
                    }

MANIFEST.md가 정리한 주요 필드는 다음과 같다.

  • manifest_version (필수, 문자열): 이 매니페스트가 따르는 명세 버전으로 현재 예시는 0.3이다. 나머지 필수 필드는 name, version(semver), description, author(이름은 필수이고 이메일과 URL은 선택)다.
  • server (필수, 객체): type은 node, python, binary 중 하나이며 entry_point로 주 서버 파일을 가리킨다. mcp_config에는 command, args, env를 둔다. 같은 문서가 설명하는 uv 유형은 호스트가 실행을 관리하므로 mcp_config가 선택이다.
  • user_config (선택, 객체): 입력 유형으로 string, number, boolean, directory, file을 둔다. title, description, required, default, multiple, min, max도 정의할 수 있고, 문자열 유형에서 sensitive를 켜면 입력을 가리고 안전하게 저장한다.
  • compatibility (선택, 객체): platforms에 darwin, win32, linux를 지정하고, runtimes에 런타임 버전 요구를 적는다. 문서의 예시는 node: ">=16.0.0"이며 생략하면 모든 플랫폼을 지원하는 것으로 본다.
  • icon (선택, 문자열): 패키지 안의 상대 경로 또는 https:// URL이다. 공식 문서는 512×512 픽셀의 투명 PNG를 권장하고 최소 크기를 256×256으로 둔다. 밝은 테마와 어두운 테마, 여러 크기가 필요하면 icons 배열을 쓴다.

치환 변수는 ${user_config.KEY}처럼 쓰며, 여러 개를 고르는 항목은 배열로 받아 별도 인자로 펼쳐진다. MANIFEST.md는 환경 변수가 민감한 데이터에 알맞고 명령 인자는 경로나 민감하지 않은 옵션에 알맞다고 덧붙인다.

빌드 도구체인 — @anthropic-ai/mcpb CLI의 명령과 패키징 흐름

공식 문서가 안내하는 흐름은 다섯 단계다. MCPB CLI를 설치하고, MCP SDK로 stdio MCP 서버를 만들고, mcpb init으로 매니페스트를 만들고, mcpb pack으로 번들을 만든 뒤, 생성된 .mcpb 파일을 더블클릭해 Claude Desktop에서 설치하고 시험한다. README도 폴더에 서버 파일을 모으고 manifest.json을 만든 다음 아카이브를 만드는 것이 번들 제작의 전부라고 설명한다. 이전 @anthropic-ai/dxt 패키지는 README의 표현대로 @anthropic-ai/mcpb로 옮겨질 예정이다.

npm install -g @anthropic-ai/mcpb
                    
                    # 매니페스트 대화형 생성
                    mcpb init
                    
                    # 매니페스트 유효성 검증
                    mcpb validate manifest.json
                    
                    # 디렉터리를 .mcpb 번들 파일로 패키징
                    mcpb pack .

CLI.md는 명령 일곱 가지를 나열한다. 그중 핵심은 다음과 같다.

  • mcpb init [directory]: 새 매니페스트를 대화형으로 만든다. 확장 이름, 작성자, 확장 ID, 표시 이름, 버전, 설명, 작성자의 이메일과 URL, 서버 유형(Node.js, Python, Binary), 진입점, 도구 구성, 키워드·라이선스·저장소 정보를 묻는다. 블로그는 --yes 옵션으로 가장 기본적인 매니페스트를 빠르게 만들 수 있다고 적는다.
  • mcpb validate <path>: 매니페스트를 스키마에 맞게 검증한다. manifest.json 경로나 그 파일이 든 디렉터리를 줄 수 있다.
  • mcpb pack <directory> [output]: 디렉터리를 .mcpb 파일로 묶는다. manifest.json을 자동 검증하고, .git, node_modules/.cache, .DS_Store 같은 흔한 개발용 파일을 제외하며, 최대 압축의 ZIP을 만든다.
  • mcpb sign과 mcpb verify: sign은 인증서로 .mcpb 파일에 서명하며 인증서와 키 경로, 중간 인증서를 옵션으로 줄 수 있다. 자체 서명 인증서를 만들어 쓰는 --self-signed도 있다. verify는 서명 유효성, 인증서의 주체와 발급자, 유효 기간, 지문을 보여 주고 자체 서명이면 경고한다.

나머지 두 명령은 info(파일 크기, 서명 상태, 인증서 정보를 표시)와 unsign(서명 제거, 개발과 시험용)이다. README가 보여 주는 Node.js 번들의 디렉터리 구조는 manifest.json(필수), server/index.js, 번들된 node_modules/, 선택 사항인 package.json과 icon.png, assets/이다.

설치 경험과 배포 정책 — 디렉터리 등록 중단과 플러그인 연계

공식 문서는 사용자가 .mcpb 파일을 Claude Desktop에 직접 설치한다고 설명한다. 설치 방법은 다음과 같다.

  • 파일 탐색기에서 .mcpb 파일을 더블클릭한다.
  • 실행 중인 Claude Desktop 창에 .mcpb 파일을 드래그 앤 드롭한다.
  • Claude Desktop에서 Settings > Extensions > Advanced settings > Install Extension…으로 가서 .mcpb 파일을 선택한다.
  • 사용자별 설치: 설치는 사용자 단위이므로 각 사용자가 자기 시스템에 따로 설치한다.

이 세 방법은 모두 설치 UI를 연다. 문서에 따르면 사용자는 이 화면에서 확장의 세부 정보와 권한을 검토하고, 필요한 설정을 입력하고, 권한을 허용한 뒤 설치를 마친다. 블로그는 같은 화면을 사람이 읽을 수 있는 확장 정보, 필요한 권한과 설정, 설치 버튼으로 설명한다.

배포에는 정책 변화가 있다. 공식 문서의 같은 페이지에 있는 「Distribute your MCPB」 절은 사용자가 .mcpb 파일을 직접 설치한다고 쓴 뒤, 디렉터리의 데스크톱 확장 목록은 폐기(deprecated)됐고 디렉터리는 더 이상 MCPB 제출을 받지 않는다고 밝힌다. 로컬 MCP 서버를 디렉터리로 배포하려면 그 서버를 플러그인에 포함하라는 안내가 이어진다. 문서 첫머리도 디렉터리에 올리려면 모든 표면에 닿는 원격 MCP 서버를 만들거나 로컬 서버를 플러그인에 포함하라고 적는다.

따라서 .mcpb 형식은 내부용이나 비공개 배포를 위해 파일을 직접 전달하는 용도로 쓰이고, 디렉터리 등록은 플러그인 경로를 따라야 한다. 엔지니어링 블로그는 출시 당시 디렉터리에 확장을 제출하는 절차를 안내했지만, 현행 문서는 그 경로가 폐기됐다고 적으므로 서술이 시점에 따라 다르다. 이 글은 현행 문서를 기준으로 삼는다. Team이나 Enterprise 조직에서 확장을 배포할 때의 관리자 통제(허용 목록, 정책 설정)와 최종 사용자의 설치 경험은 Anthropic의 지원 문서에 따로 안내되어 있다.

MCPB 구성요소별 공식 문서 서술과 확인되지 않은 사항

로컬 확장을 실제 업무에 도입하려면 공식 문서가 말하는 영역과 문서에 없는 영역을 구별해야 한다. 아래 표는 MCPB 구성요소별로 그 둘을 대조한 것이다.

구성 요소 공식 문서의 서술 확인되지 않았거나 주의할 사항
프로세스 실행 모델 stdio 기반 로컬 프로세스 실행, ${__dirname} 치환 지원 서브 런처 프로세스 사용 시 stdin/stdout 파이프 전달 특성은 공식 문서 미기재
설정 UI 및 비밀값 user_config 선언 시 UI 자동 생성, sensitive 값은 입력을 가리고 안전하게 저장(블로그: OS 키체인) OS별 저장소 종류와 암호화 방식, 파일(file) 타입의 임의 절대경로 지정 가능 여부는 문서에 구체적 명시 없음
런타임 종속성 macOS·Windows용 Claude Desktop에 Node.js 포함, python 유형은 패키지를 번들, uv 유형은 호스트가 Python과 의존성 관리 내장 Node.js의 정확한 SemVer 버전 및 v8 플래그 설정은 문서에 미기재
확장 배포 방식 .mcpb 파일 직접 공유 또는 플러그인 포함 배포, 디렉터리 제출 중단 서명(sign) 검증 시 신뢰할 인증기관(CA) 요구사항 및 엔터프라이즈 화이트리스트 규격 미기재

이 대조를 바탕으로 설계할 때 살필 점은 문서에서 곧바로 나오는 것으로 한정한다.

  • 플랫폼 점검: 문서는 주로 한 플랫폼에서 개발하더라도 macOS와 Windows 양쪽에서 시험하라고 권한다.
  • 경로 입력: user_config는 directory와 file 유형을 지원하고 multiple로 여러 개를 고를 수 있다. 파일 선택기가 임의 경로를 어디까지 허용하는지는 문서에 없으므로 직접 확인해야 한다.
  • 배포 경로: 디렉터리 제출이 중단됐으므로 .mcpb 파일을 직접 전달하거나 플러그인에 포함한다. 조직 수준의 커스텀 업로드와 허용 목록 같은 관리자 통제는 Team과 Enterprise 문서가 다룬다.
  • 서명: mcpb sign은 인증서로 서명하고 자체 서명 인증서도 만들 수 있으며, verify는 자체 서명이면 경고를 낸다. 서명을 도입하려면 이 경고의 의미를 먼저 정해 두어야 한다.

확인하지 못한 것

  • Claude Desktop에 번들로 내장된 Node.js 런타임의 정확한 버전 번호(예: Node v20 또는 v22) 및 지원되는 ECMAScript 기능 범위.
  • manifest.json의 user_config에서 file 타입 설정 시 로컬 시스템의 임의 절대경로 파일 탐색기를 공식 지원하는지 여부.
  • 중간 런처 프로세스(wrapper)를 통해 서버를 스폰할 때 Claude Desktop의 유틸리티 프로세스 구조가 stdin EOF 처리에 미치는 내부 구현 동작.
  • Claude 브라우저 확장(Claude in Chrome)이 데스크톱의 로컬 MCPB 확장을 감지하고 도구를 공유할 수 있는지에 관한 공식 통합 사양.
  • 엔터프라이즈 관리자 정책에서 서명되지 않은 .mcpb 파일의 설치를 강제로 차단하는 세부 GPO 또는 MDM 정책 키 목록.
