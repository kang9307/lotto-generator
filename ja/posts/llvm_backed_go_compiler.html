Goで書いたプログラムからNumPyを呼び、PyTorchを走らせ、raylibで画面を描く。この一文は魅力的に響く。一つの言語で書いてきたコードに、他人の生態系がまるごと付いてくる絵だからだ。しかしこの一文が実際に指示している作業は一つしかない。互いに異なる実行モデルを二つ、一つのプロセスの中に重ねて置くことである。

重ねれば必ず境界が生じる。境界には値段が付く。メモリを誰が解放するのか、コレクタがそのポインタを見ているのか、片方の例外がもう片方のパニックへ翻訳されるのか、スレッド規約は誰のものか。そのすべてが、その境界の上で改めて決め直されねばならない。言語一つだけを使っているあいだは、コンパイラとランタイムが代わりに守ってくれていたものだ。

LLVMをバックエンドに据えてGoをコンパイルし、CとPythonのライブラリを直接呼べるようにした実装が、正式な版番号を付けて出た。ここで見るべきはその道具の使い方ではない。他言語のライブラリを使うという決定が何を背負うのかである。その実装は、その請求書をひときわ鮮明に見せてくれる標本だ。問題を回避せず正面から受け止め、受け止めた代償を文書として残しているからである。

きっかけ - 「Goコンパイラ」という言葉が隠すもの

紹介文はたいてい短い。「LLVM基盤のGoコンパイラ」と書かれていれば、多くの読者はそれを、標準Goをそのまま受け取って機械語だけ別に吐く代物と読む。そしてその読みは半分だけ当たっている。

リポジトリが自ら定めている範囲はこうだ。Go 1.20以降のソースと互換であり、Go 1.27の言語文法をすべて支え、cgoも受け取る。対応するネイティブ環境では標準ライブラリを全面的に支えると記す。ここまで読めば部分集合という言い方は誤りである。

ところが同じ文書がすぐ次の節で別のことを言う。ランタイムが標準ツールチェーンと異なる。ネイティブのゴルーチンがOSスレッドへ一対一で結び付き、スタックは固定長のネイティブスタックであり、既定のコレクタは保守的方式のBoehm系である。ベアメタル向けの対象はさらに別の保守的なマーク・スイープ方式を使う。文法はすべて受け取るのに、その文法が動く床が別物になっている。

だからこの代物を一行で要約するとき、「標準Goの部分集合」は不正確であり、「標準Go互換」もまた不正確だ。正確な要約は文法と標準ライブラリはすべて、ランタイム保証は別物である。対応環境をLinuxとmacOSだけと書く紹介もあるが、リポジトリの文書はWindowsのamd64とarm64をMSVC向けとMinGW向けの二系統で併記し、WebAssemblyの各対象と組み込みボードまで並べている。要約はいつも遅れて更新される。

Goはなぜそう作られたのか - 自前バックエンドの代償

Goのチームはプロジェクト初期にLLVMを検討し、採用しなかった。公式のFAQにその理由が一文で残っている。性能目標を満たすには大きすぎ、遅すぎると判断したというものだ。ここでいう性能は生成コードの実行速度ではなく、コンパイラ自身の速度である。同じ文書は別の箇所で目標を明示する。大きな実行ファイル一つを一台の計算機で数秒以内にビルドすることだ。

この選択は連鎖的に言語の性格を決めた。自前のバックエンドと自前のリンカを使うためツールチェーンが小さく、静的リンクが既定なので配布が単純で、対象のOSとアーキテクチャを環境変数二つで切り替えてクロスコンパイルできる。その代わり最適化の深さは数十年積み上げてきた汎用バックエンドに及ばず、対応アーキテクチャの幅もそのバックエンドほど広くはない。

そして同じ選択がcgoの性格まで決めた。自前の呼び出し規約と自前のスタック管理、自前のスケジューラを使うランタイムでC関数を呼ぶということは、他人の規約へ一時的に渡って戻ってくる作業になる。渡って戻ってくる手続きそのものが費用だ。

自前のコンパイラバックエンド大きな実行ファイルでも数秒規模のビルド汎用バックエンドが積み上げてきた最適化の深さ

環境変数で指定する対象環境C用の道具なしで済むクロスコンパイルCライブラリを使った瞬間にその単純さが消える
伸長するゴルーチンスタック数十万個を立てても耐える並行性Cのコードをそのスタック上でそのまま走らせること
精密なポインタ地図を使うコレクタ正確な生存判定と予測できる終了処理の時点コレクタが知らないメモリを扱うには規約が要る

cgoはなぜ単なる関数呼び出しではないのか

Goのランタイムのソースにあるcgocallというファイルの冒頭には、呼び出し経路の全体を説明する長い注釈が付いている。この注釈こそが「高価だ」という言葉の中身である。

GoのコードがC関数を呼ぶと、生成されたコードがランタイムのcgocallを呼ぶ。cgocallはまずentersyscallを呼ぶ。他のゴルーチンとコレクタを止めないためだ。注釈はこの呼び出しの目的を明示する。外部コードに入っているあいだ、他のゴルーチンを走らせるスレッドをもう一つ用意すべきだとスケジューラへ知らせることである。

次にアセンブリ層のasmcgocallが、現在のゴルーチンスタックを離れてg0スタックへ移す。注釈はその理由まで書いている。g0スタックはOSが確保したスタックなので、Cコンパイラが生成したコードを載せても安全だからだ。裏返せばゴルーチンスタックの上ではCのコードをそのまま走らせられない。必要に応じて伸びるスタックの上でC関数を実行してはならないからである。

C関数が終わると元のゴルーチンスタックへ戻り、cgocallがexitsyscallを呼ぶ。注釈はこの関数の性質を一文で記す。並列実行の上限を破らずにこのスレッドがGoコードを走らせられるようになるまで待たされるというものだ。つまり復帰は即時ではなく、スケジューラの許可を待つ手続きである。

C側からGoの関数を呼び戻すと、この階段を逆向きにもう一度下りる。アダプタがCの呼び出し規約をGoの呼び出し規約へ変換し、再びg0スタックから元のゴルーチンスタックへ移し、そこでまた上限を待つ。コールバック一回で往復の切り替えが二重に積み上がるということだ。

段階ランタイムがすることなぜ必要か
進入の宣言システムコールへの進入として印を付けるこのスレッドが塞がるあいだ、他のゴルーチンを走らせるスレッドを用意するため
スタック切り替えゴルーチンスタックからOSのスタックへ移す伸長するスタックの上でCのコードを走らせられないから
実際の呼び出し引数をフレームから取り出してC関数を呼ぶ呼び出し規約が互いに違うので仲介が要る
復帰の切り替え元のゴルーチンスタックへ戻すGoのコードは自分のスタックの上でしか続けられない
離脱の待機並列上限が許すまで待たされる同時実行の数の会計を保つため
コールバックがあれば同じ階段を逆方向へもう一度CからGoへ入るのも同じ境界だから

この表を見れば、「呼び出しが高価だ」がマイクロ秒単位の定数遅延の話ではないと分かる。スケジューラの会計とスタックの所有権が、呼び出しのたびに行き来する。だから大きな計算を一度渡す場合はほとんど問題にならず、小さな関数を細かく呼ぶ場合は調整ではなく構造そのものが問題になる。

ポインタ受け渡しの規則 - 守るのはコンパイラではなく規約だ

費用より危ういのは規則のほうだ。cgoの文書はポインタを渡すときの条件を明確に定めている。GoのポインタをCへ渡すには、そのポインタが指すメモリが、固定されていない他のGoポインタを含んでいてはならない。そしてCのコードは呼び出しが終わった後にGoポインタの写しを保持できない。例外は固定機構でそのメモリを押さえている場合だけである。

引数として渡したGoポインタは、呼び出しが続いているあいだだけ暗黙に固定される。呼び出しが終わる瞬間、その保証も終わる。文字列はもっと単純だ。C.CStringはCのヒープへ写しを作り、文書は解放の手配は呼び出し側の責任であると記す。

// 標準Goのcgo - 境界をまたぐ値は複製され、解放の責任は呼び出し側に残る
cs := C.CString(s)                  // Cのヒープへ写しを作る
defer C.free(unsafe.Pointer(cs))    // この一行がなければそのまま漏れる
n := C.strlen(cs)                   // ここから先はCのメモリだ

呼び出しが終わった後もCがGoのメモリを保持せねばならない場合は固定機構を使う。標準ライブラリのPinnerは対象をコレクタが動かすことも回収することもできないように押さえておく。固定した対象がさらに別のGoオブジェクトを指し、Cがそこまでたどるのなら、その対象も別途固定せねばならない。

// Cが呼び出し終了後もGoポインタを保持せねばならないとき
var pinner runtime.Pinner
pinner.Pin(p)            // コレクタが動かすことも回収することもできないよう押さえる
defer pinner.Unpin()     // 解くまでのあいだだけC側の参照が有効だ

ここで注目すべきは規則の執行主体である。これらの規則は型検査器が捕まえてくれない。コンパイルはそのまま通り、破ったときの結果もすぐには現れない。コレクタがそのメモリを実際に動かすか回収する時点になって初めて症状が生じる。負荷が高くなってから、あるいはヒープが育ってから初めて出る種類の欠陥だ。

  • 渡せるものの条件 — 指すメモリの中に固定されていないGoポインタがあってはならない。構造体の中にスライスや文字列が入っていればこの条件に引っかかる
  • 保持の禁止 — Cが呼び出し後までGoポインタを持つには固定が要り、固定を解いた瞬間その参照は根拠を失う
  • 解放の帰属 — Cのヒープに作ったものはCの規約で解放する。Goのコレクタはそのメモリを数えないので、漏れは静かに積み上がる

同じ問題を言語の側でどう減らせるかはRust FFI 境界で途切れる安全保証で扱った軸である。そちらは境界そのものを減らす接近であり、ここで見るのは境界をなくすために床を替える接近だ。

ランタイムを差し替えるという選択

三節の階段はすべて一つの前提から出ている。ゴルーチンスタックとスケジューラがCのものではないという前提だ。その前提を消せば階段も消える。LLVM基盤の実装が選んだ道がまさにそれである。

リポジトリの文書の言い回しは簡潔だ。ネイティブのゴルーチンがOSスレッドへ一対一で結び付き、スタックは固定長のネイティブスタックなので、Cを直接呼ぶときGoからCへのスタック切り替えもスケジューラの切り替えも要らないという。束縛の仕方もラッパを経ない。Goの宣言一つをC ABIのシンボルへ直に結び付ける。

import _ "unsafe" // go:linkname 指示子を使うために必要だ

//go:linkname Sqrt C.sqrt
func Sqrt(x float64) float64

この指示子そのものは標準のコンパイラにもある。公式文書はその性質をこう記す。Goの変数や関数の宣言が使うオブジェクトファイルのシンボルを指定し、二つのGoシンボルが同じものを指すようにするもので、unsafeを取り込んだファイルでのみ有効になる。そして同じ頁が、この指示子は非公開宣言のカプセル化や、さらには型安全性まで迂回しうると明示する。便利さの正体が何なのかを文書自身が語っているわけだ。

変わったのは呼び出し経路だけではない。既定のコレクタが保守的方式へ替わった。精密なポインタ地図を持たずにスタックとレジスタを走査し、ポインタらしく見える値をすべて生存しているものとして扱う方式だ。この選択のおかげで、Cのコードが作ったメモリとGoのコードが作ったメモリを一つのヒープで扱うのが容易になる。そしてその代償が次の節の一覧である。

「全面対応」と「互換対象外」のあいだ

興味深いのは、このプロジェクトが互換性を文章ではなく一覧として管理している点だ。標準配布物のコンパイラ試験一式をそのまま回し、通らなかった項目を二つのファイルに分けている。一つはまだ合わせられていないもの、もう一つはそもそも合わせるつもりのないものである。

まだ合わせられていない側は十一件だ。そのうち六件は、パーサが出すエラーメッセージの文言が標準と違うというもの。壊れたパッケージ宣言、壊れた名前、バイト順序表示といった状況で診断文が別の形で出る。残り五件はヒープ標本プロファイルに関するもので、そのうち二件には未併合の提案番号が理由として記されている。

合わせるつもりのない側は百三十六件である。こちらが本当の境界線だ。百十件は理由が同じ文で終わる。そのツールチェーンに固有の挙動を支えることは互換の目標ではないというものだ。残りは理由がより具体的である。保守的コレクタを使うので正確な生存判定と終了処理の時点は合わせないという項目が十八件ほど、書き込み障壁を使わないのでそれに関わる診断は再現しないという項目が複数、そして固定長のネイティブスタックを使うので伸長するスタックの挙動は再現しないという項目もある。

軸宣言された範囲実際に分かれる地点
言語文法Go 1.27の文法すべてパーサの診断文言が六件違う。文法そのものではなくエラーメッセージだ
標準ライブラリ対応するネイティブ環境では全面的に他の対象では一部のOSサービスや実装固有の挙動がないことがあると自ら記す
ゴルーチン動作するOSスレッドへ一対一。数を増やすときの費用が標準と異なる
スタック動作する固定長。伸長するスタックを前提とした挙動は互換対象外に分類される
ガベージコレクション既定で提供保守的方式。正確な生存判定と終了処理の時点が標準と異なる
ビルドの道具立て使い方は標準コマンドに似ているLLVM 22系統一式と複数のシステムライブラリが前提条件だ
  • 文法互換とランタイム互換は別の軸だ。同じソースがコンパイルされるという事実と、同じソースが同じ時点で同じ観測を出すという事実は別物である
  • 終了処理や弱参照に頼るコードが第一の危険群だ。保守的コレクタでは回収の時点が標準からずれうる
  • ゴルーチンを極端に多く立てる設計が第二の危険群だ。一対一の対応ではその数がそのままスレッド数になる

LLVMに載せると何が変わるのか

得る側

汎用バックエンドを使えば、そのバックエンドが積み上げてきたものが全部付いてくる。最適化のパス群、リンク時最適化、アーキテクチャごとのコード生成器、そしてその上に載っているデバッガと解析の道具立てだ。対象の拡大も同じ形でやってくる。この実装がWebAssemblyを複数系統で吐き、組み込みボードまで対象に入れられるのは、そのバックエンドがすでにそれらのアーキテクチャを知っているからである。

C ABIで直に結び付くという性質もここから出る。同じバックエンドがCもコンパイルするので、呼び出し規約と型の表現が最初から同じ言語で表される。ラッパ層が要らない理由がこれだ。

払う側

バックエンドが大きいということはツールチェーンが大きいということだ。LLVMの公式文書は所要ディスクをこう記す。LLVMだけをビルドすればおよそ1から3ギガバイト、LLVMとClangを併せてビルドすればおよそ15から20ギガバイトである。この実装はLLVM 22系統のコンパイラ・リンカ・デバッガをすべて前提条件として要求し、そこへ保守的コレクタのライブラリ、外部関数インターフェースのライブラリ、暗号のライブラリと圧縮のライブラリを足して要求する。

この一覧がそのままビルド再現性の請求書だ。標準Goのクロスコンパイルが安いのは、対象環境向けのC用の道具が要らないからである。境界を開いた瞬間その前提が崩れる。開発者の機械と継続的インテグレーションの機械と配布対象の、システムライブラリの版番号がすべて結果に入り込む。

LLVMをバックエンドへ差し替える試みそのものは、このプロジェクトが初めてではない。Goの公式FAQもGCCバックエンドを使うフロントエンドと、同じフロントエンドを使う実験的なLLVMバックエンドの存在を記している。TypeScriptを同じやり方で下ろす試みはPerry - TypeScriptをLLVM機械語へ直接コンパイルするネイティブコンパイラで扱ったが、その記事で扱った落とし穴の一つがここでも繰り返される。より良いバックエンドが自動的により速い結果を意味するわけではない。言語の意味論がそのバックエンドへうまく下りるかどうかが先だ。

自己計測の数値を一つ - WebAssemblyのファイル容量

このプロジェクトは専用のリポジトリで容量比較を継続的に回し、結果を公開している。条件も併記されているので引用に足る。ただし計測している主体がプロジェクト自身である点は、そのまま抱えて読まねばならない。

条件はこうだ。実行番号403、生成時刻は2026-09-07の07:11 UTC、継続的インテグレーションの実行機はLinux x64のUbuntu 24イメージ、対象はWebAssemblyのシステムインターフェース。Go 1.26.2、LLVM 22、TinyGo 0.41.1を使い、標本はアプリケーション十本、指標は出力ファイルの総バイト数である。ビルドの選択肢も併せて公開されている。Go側は経路の除去とシンボル・デバッグ情報の除去を掛け、TinyGo側は容量優先の最適化とデバッグ情報の除去を掛け、この実装側は容量優先の最適化にリンク時最適化と全域の不要コード除去を組み合わせた。

構成標準Go比TinyGo比読み方

この表から読むべきは倍率そのものではなく、倍率の向きが両方にあるという事実だ。同じ生成物が、片方の物差しでは三分の一であり、もう片方では六倍近い。個別の事例で見ればもっと明白である。標本に入っているBase64変換器の場合、標準Goの生成物がおよそ228万バイト、小型向けコンパイラの生成物がおよそ9万7千バイト、最小構成の生成物がおよそ60万バイトだ。どちら側と比べるかによって、同じ数字が勝利にも敗北にもなる。倍率だけを切り取ってきた文が危ういのはこのためである。

そしてこの表は実行速度ではなくファイル容量だ。容量と速度は別の軸であり、容量優先の最適化を掛けたビルドが速度の軸で有利とは限らない。

境界をまたぐとき実際に壊れるもの

ここがこの記事の中心である。どの言語からどの言語へ渡るのであれ、境界で壊れるものの一覧はおおむね同じだ。重要なのは各項目がどんな症状として現れるかである。症状を知って初めて、原因をそちらへ疑えるからだ。

壊れるものなぜ壊れるのか現れる症状まず見る場所
メモリの所有権確保する側と解放する側が別の規約を使う長時間の稼働で常駐メモリが単調に増える。再起動すれば消える境界をまたぐ文字列やバッファごとに解放の相方があるか
コレクタが見られないポインタコレクタが走査しない場所にだけ参照が残る負荷が高いときだけ落ちる。スタックの追跡がすでに回収された対象を指すスレッド局所記憶、Cのヒープ、コールバックへ渡した文脈ポインタ
対象の移動コレクタが対象を動かすのにCは古い番地を持っている断続的に誤った値。ヒープが育ってから再現する呼び出し終了後も残るポインタに固定が掛かっているか
例外とパニック片方の巻き戻し規約がもう片方に存在しないエラーの代わりにプロセスが丸ごと終了する。記録が残らない境界をまたぐコールバックの中からパニックが漏れ出ないか
スレッドモデル片方がスレッドに条件を付ける同じコードがあるゴルーチンでは通り、別のゴルーチンでは落ちる鍵の取得と解放が同じスレッドで対になっているか
エラーの規約戻り値・大域変数・例外のどれで知らせるかが違う失敗が成功として読まれる。欠陥がずっと後で表に出るC関数のエラー表明の方式と、その値を読む時点
型の表現同じ名前の型が幅と配置で異なる構造体の欄がずれる。32ビットと64ビットで結果が分かれる整数の幅、配列が引数のときと欄のときの違い、関数ポインタ
ビルドの再現性システムライブラリと道具の版番号が結果に入り込む自分の機械では通るのに継続的インテグレーションで通らない前提条件の一覧に版番号の固定があるか

二行目は抽象的な警告ではない。この実装の文書に実際の事故の記録として残っている。遅延実行の連鎖の先頭をスレッド局所記憶にだけ生ポインタとして置いたところ、保守的コレクタがそれを見られなかったというものだ。百万件の遅延実行を積む負荷試験でコレクタがそのノードを回収し、その結果、遅延実行の中で落ちた。診断は明快である。論理的な破損ではなく根の登録漏れだった。直し方も診断に合わせて、その状態をコレクタが知っている根から確保するよう変えている。

七行目にも具体的な文書の根拠がある。この実装の型対応表はCの関数ポインタが引数として来るときと構造体の欄として来るときを別に扱う。引数の位置ではGoの関数型として受け取るが、構造体の欄では素のポインタとして受け取る。Cの関数ポインタは関数一つの番地でしかなく、Goの関数値はクロージャでありうるからだ。配列も同じく、引数の位置ではポインタへ落ち、構造体の中でだけ配列として残る。Windowsのコールバックについても同じ理由で、状態を捕捉するクロージャの代わりに直接の関数参照を渡し、文脈は別のポインタで伝えよと文書が明示している。

Pythonを呼ぶということ - 鍵が付いてくる

Cのライブラリを呼ぶことと、Pythonのライブラリを呼ぶことは難度が違う。後者はインタープリタという状態機械を一つ丸ごとプロセスの中へ持ち込む作業だからだ。その状態機械には自分の規約がある。

Python公式のC API文書の一文は短く断定的である。自由スレッドのビルドでない限りインタープリタは一般にスレッド安全ではなく、だから大域インタープリタ鍵があり、その鍵を握っているスレッドだけがPythonのオブジェクトを扱ったりPythonのC APIを呼んだりできる。外部のスレッドから入るときは状態の確保と解放を対で合わせねばならず、文書はすべての確保の呼び出しが同じスレッドでの解放の呼び出しと対にならねばならないと明示する。

// Pythonのライブラリをそのままコードから呼ぶ
x := math.Sqrt(py.Float(2))       // Pythonのmath.sqrtへ渡す
std.Print(py.Str("sqrt(2) ="), x) // Pythonのprintで表示する

見た目には関数呼び出しが二行である。ところがこの二行が成り立つには、プロセスの中でインタープリタがすでに初期化されていなければならず、このコードを実行するスレッドが鍵を握っていなければならず、渡した値がPythonのオブジェクトとして作られ参照計数の規約に従わねばならない。見えない前提が三重だ。

この条件がGoの実行モデルとどう出会うのかを見れば、なぜ一対一のスレッド対応という選択が出てきたのか見当がつく。標準のGoではゴルーチンはスレッドに固定されていない。スケジューラが移す。鍵を握ったままゴルーチンが別のスレッドへ移れば規約が壊れる。ゴルーチン一つがスレッド一つに固定されていれば、この問題は構造的に消える。

自由スレッドのビルドも万能ではない。公式文書はそのビルドでもスレッド状態を切り離す手続きは依然として必要だと記す。インタープリタが一貫した視界を得るために、周期的にすべてのスレッドをしばらく止めるからである。例としてコレクタを走らせているあいだが挙げられている。

  • 並列性の上限が他人のもので決まる。Go側でゴルーチンをいくら増やしても、Pythonのオブジェクトへ触れる区間は鍵一つを巡って列を作る
  • 鍵の規約はコンパイラが検査しない。確保と解放の対がずれてもコンパイルは通ってしまう
  • 第三者のライブラリは別途の導入だ。配布物の中にインタープリタとその一群が必要で、その版番号が結果に入り込む

いつこの選択が正しいのか

既存のライブラリが事実上唯一の実装であるとき

判断はたいてい一つの問いへ圧縮される。そのライブラリを代替できる純粋な実装があるか。なければ境界の費用は選択肢ではなく前提だ。数値計算の特定の中核処理、長年磨かれてきた符号化器、特定のハードウェアの公式ドライバ、規制対応のために特定の実装を使わねばならない暗号モジュールなどがここに当たる。この場合、論点は「使うのか」ではなく「境界を何箇所に置くのか」へ移る。

境界を減らす方法はおおむね同じだ。呼び出し地点を一箇所へ集め、その中で太く一度だけ渡す。小さな関数を細かく呼ぶ代わりに、まとめて渡すのである。三節で見た階段は呼び出しのたびに付く構造なので、呼び出し回数を減らすことがそのまま費用を減らすことになる。

純粋な実装があるとき

純粋な実装があるなら計算は変わる。比べる対象は性能ではなく運用の総費用だ。境界を開けば配布物にシステムライブラリが付いてきて、クロスコンパイルが難しくなり、障害の調査に二つの言語の知識が要るようになり、標準の道具立てのプロファイラと競合検出器が半分しか見られなくなる。

状況境界を開く側純粋な実装の側決定を分けるもの
代替の実装自体がない事実上唯一の選択該当なし境界を何箇所まで減らせるか
純粋な実装はあるが遅い一度に渡す仕事量が大きいときだけ普通はこちら一回に渡す作業量。小さければ切り替えの費用が利益を食う
純粋な実装の機能が足りない足りない機能が中核のとき足りない部分を使わずに済むならその機能が要件の中心か周辺か
配布対象が多様だ不利だ有利だ対象ごとにC用の道具を揃えられるか
ゴルーチンを極端に多く立てるランタイム差し替え型は不利だ有利だ並行性の規模がスレッド数へ換算されても耐えるか
運用する組織が一つの言語しか知らない障害調査の費用が大きくなる有利だ未明に落ちたとき原因を追える人がいるか

最後の行が実務で最もよく決定を覆す。境界を開いた系の障害は、片方の言語の知識だけでは最後まで追いにくい。Goと別の言語のあいだでこの判断をどう立てるかはGoからRustへの移行完全ガイド2026で別の角度から扱い、言語選択そのものを検証費用へ換算する軸はAI生成コードの検証コストを下げる言語特性にある。

成熟度の読み方 - 星の数ではなく

星の数が語らないこと

公開リポジトリの星の数は関心の指標であって信頼の指標ではない。このリポジトリは照会時点で星749、フォーク50、未解決の課題151である。2023年12月に作られ、照会当日もコミットが入っていた。これらの数字だけでは、導入の判断に要るものが一つも出てこない。

代わりに見るべきは四つだ。リリースタグの軌跡、未解決課題の種類、互換性宣言の形、標準準拠の範囲についての自己記述である。

リリースの軌跡から見ると、最初のタグが2024年4月、正式な版番号である1.0.0が2026年8月24日だ。事前配布版を五つ、一週間あまりに集中して出した後に正式版を出し、その後8月29日と9月6日に保守版が二度出ている。総リリース数は四十九だ。正式な版番号まで2年4か月かかり、その直後に二度の保守があったという事実が、星の数よりはるかに多くを語る。

四行目がこの表で最も値打ちがある。ほとんどの企画は互換性を散文で書く。「ほぼ互換だ」という文は検証できないが、理由の付いた例外の一覧は読んで問い詰められる。その一覧に自分のコードが頼っている挙動が入っているかを、直に突き合わせられるということだ。言語の企画が開かれることが実際に何を変え何を変えないのかはMojoコンパイラのオープンソース公開で統治の軸として扱った。ここで見る軸は互換性宣言の検証可能性である。

導入前に答えるべき五つ

道具を選ぶ作業は、たいてい問いを選ぶ作業だ。下の五つに答えが出れば決定は付いてくる。

  1. 境界を何回またぐのか。呼び出し回数が少なく一度に渡す仕事量が大きいなら標準のcgoで十分だ。細かい呼び出しが構造的に避けられないときだけ、ランタイムの差し替えが論点になる
  2. ゴルーチンを何個立てるのか。一対一の対応では並行性の規模がそのままスレッド数だ。数万個を前提とした設計ならこの経路は合わない
  3. 終了処理や回収の時点に頼るコードがあるか。保守的コレクタではその時点が標準と変わる。資源の解放を終了処理に任せたコードが最初の点検対象だ
  4. 配布対象は何種類か。対象ごとにLLVM系統の道具とシステムライブラリを揃え、版番号を固定できるかが実際の導入費用の大半である
  5. 未明に落ちたとき誰が見るのか。境界を開いた系の障害は二つの言語の知識を要求する。その人が組織にいるかが技術的な判断より先だ

五つの問いのどれも性能を訊いていない点が重要である。境界を開く決定において性能はたいてい既に答えの決まった軸であり、実際に企画を沈めるのは残りの四つだ。コンパイル言語に対話的実行を付けるときにも同じ種類の交換が現れるが、その軸はコンパイル言語に対話的実行を付けるということに整理してある。

確認できなかったこと

  • 速度の比較を確認できなかった。公開されている継続的インテグレーションの計測はWebAssembly出力ファイルのバイト数であり、実行時間の比較を同じ形式で公開したものは見つからなかった。八節の倍率を速度へ移して読んではならない
  • ネイティブ対象の容量表は開けなかった。結果ファイルはネイティブの項目を別途の要約と表形式で指しているが、その中身はこの記事の根拠に入れていない
  • C呼び出し経路の実際の削減幅を数値で確認できなかった。スタックとスケジューラの切り替えがないことは設計上の記述であり、標準のcgoに対する呼び出しあたりの遅延を同じ条件で比べた公開値は得られなかった
  • 第三者による再現を確認できなかった。八節の数値はすべてプロジェクト自身が回したものであり、独立した計測報告は見つからなかった
  • 未解決の課題151件の構成を確認できなかった。欠陥と機能要望と文書の項目の比率を分けていないので、この数字を品質の指標として読んではならない
  • 貢献者数の正確な総計を確認できなかった。一覧の最初の頁に19名が出るが、全頁を合算していない
  • Pythonの自由スレッドのビルドでこの実装がどう動くかを確認できなかった。リポジトリの文書が要求しているのは3.12以上という条件だけで、鍵のないビルドについての別途の記述は確認の範囲になかった
