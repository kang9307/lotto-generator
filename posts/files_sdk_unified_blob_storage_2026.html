Files SDK - S3·R2·GCS를 하나의 API로 통합하는 blob 스토리지 추상화 2026

Stop Rewriting Storage Code - 스토리지마다 다른 API를 하나로 묶는 통합 추상화의 모든 것

2026-06-02 IT/기술

서론: 클라우드 스토리지마다 다른 API의 고통

2026년 6월 1일 news.hada.io 1번 토픽으로 "Files SDK - Unified API for blob storage"가 20점으로 올라왔다. 제목만 봐도 가슴이 답답해지는 개발자가 많을 것이다. 본인도 그랬다. 클라우드 스토리지를 한 번이라도 진지하게 다뤄 본 사람이라면, S3에 맞춰 짠 업로드 코드를 GCS로 옮기려다 절반을 다시 쓴 경험이 분명히 있을 것이다. 이 글은 그 고통의 정체가 무엇이고, Files SDK 같은 통합 추상화가 그것을 어떻게 풀어내는지를 한국 개발 현장의 맥락으로 풀어 보려 한다.

문제의 본질은 단순하다. AWS S3, Cloudflare R2, Google Cloud Storage(GCS), Azure Blob, 그리고 셀프호스팅 MinIO는 개념적으로는 거의 같은 일을 한다. 키를 주면 객체(파일)를 저장하고, 키를 주면 꺼내 주고, 목록을 보여 주고, 지운다. 그런데 막상 코드를 짜 보면 SDK 이름이 다르고, 클라이언트 초기화 방식이 다르고, 인증 자격증명 형식이 다르고, 메서드 시그니처가 다르고, 오류 코드와 페이지네이션 규칙까지 제각각이다. 같은 일을 하는데 다섯 가지 방언을 익혀야 하는 셈이다.

이 글은 세 가지를 한다. 첫째, Files SDK가 표방하는 '통합 blob 스토리지 API'가 정확히 무엇을 추상화하는지 본인의 언어로 정리한다. 둘째, 이 추상화가 해결하는 실제 문제와 작동 원리를 의사코드로 보여 준다. 셋째, R2 egress 무료 같은 비용 최적화, 한국 멀티클라우드 환경 적용, 그리고 추상화의 한계까지 균형 있게 다룬다. 결론부터 말하면, 통합 스토리지 SDK는 만능이 아니지만 'put/get/list가 주력인 대다수 서비스'에게는 벤더 락인을 푸는 가장 실용적인 무기다.

1. Files SDK란 - blob 스토리지 통합 추상화 개요

먼저 용어부터 정리하자. 'blob 스토리지'는 Binary Large Object, 즉 이미지·동영상·백업·로그 같은 비정형 대용량 객체를 키-값 형태로 저장하는 객체 스토리지를 말한다. S3가 사실상 표준을 만들었고, 이후 거의 모든 클라우드가 유사한 모델을 따라왔다. Files SDK는 이런 객체 스토리지들을 하나의 통일된 인터페이스로 다루게 해 주는 추상화 라이브러리다.

핵심 아이디어를 본인 말로 다시 정리하면 이렇다. 애플리케이션은 "S3에 올려라"가 아니라 "스토리지에 올려라"라고만 말한다. '어느 스토리지인지'는 코드가 아니라 설정이 결정한다. 개발 환경에서는 로컬 MinIO에, 운영에서는 R2에, 백업은 S3에 — 똑같은 호출 코드로 목적지만 바꾼다. 이것이 통합 SDK가 약속하는 그림이다.

여기서 중요한 구분이 있다. 통합 SDK는 '스토리지를 대체하는 것'이 아니라 '스토리지 접근 방식을 표준화하는 것'이다. 데이터는 여전히 S3나 R2에 그대로 저장된다. 다만 그것을 부르는 방법을 하나로 통일할 뿐이다. 이 차이를 헷갈리면 추상화의 가치와 한계를 둘 다 오해하게 된다.

2. 통합 API가 해결하는 5가지 문제

왜 굳이 추상화 레이어를 한 겹 더 얹는가. 본인이 보기에 통합 SDK가 푸는 핵심 문제는 다섯 가지다.

  1. 벤더 락인(vendor lock-in): S3 SDK에 코드를 깊게 묶으면, 나중에 더 싸거나 빠른 대안이 나와도 옮기는 비용이 막대해진다. 추상화는 이 묶임을 느슨하게 만든다.
  2. 마이그레이션 비용: 스토리지 이전은 보통 데이터 이전과 코드 수정이 동시에 일어난다. 통합 SDK는 최소한 코드 수정 부분을 거의 0으로 줄여 준다.
  3. 멀티클라우드 운영: 한 서비스가 동시에 여러 클라우드 스토리지를 써야 할 때(규제, 이중화, 비용 분산), 백엔드마다 다른 코드를 유지하는 것은 악몽이다. 하나의 인터페이스가 이를 정리한다.
  4. 코드 중복 제거: 백엔드별로 업로드 유틸을 따로 짜면 같은 로직이 여러 벌 생긴다. 추상화는 공통 로직을 한곳으로 모은다.
  5. 테스트 용이성: 통합 인터페이스가 있으면 테스트에서 실제 클라우드 대신 인메모리/로컬 백엔드로 손쉽게 갈아끼울 수 있다. CI에서 외부 의존성을 줄이는 효과가 크다.
핵심 메시지: 통합 SDK의 진짜 가치는 '한 번에 여러 클라우드를 쓰는 화려함'이 아니라, 스토리지 선택을 '코드 결정'에서 '설정 결정'으로 끌어내려 미래의 선택지를 열어 두는 것이다.

3. 지원 백엔드 - S3, R2, GCS, Azure Blob, MinIO

통합 SDK가 다루는 주요 blob 스토리지 백엔드를 본인 기준으로 비교 정리하면 다음과 같다. 각 백엔드는 같은 객체 저장이라는 목표를 공유하지만 비용 구조와 강점이 뚜렷이 다르다.

백엔드제공사egress 요금강점
S3AWS유료사실상 표준, 가장 넓은 생태계와 도구

GCSGoogle유료GCP/BigQuery 데이터 분석 통합

여기서 눈여겨볼 점은 R2와 MinIO가 'S3 호환 API'를 제공한다는 사실이다. 이 호환성 덕분에 통합 SDK는 S3용 어댑터 하나를 엔드포인트만 바꿔 R2·MinIO에도 상당 부분 재사용할 수 있다. 반면 GCS와 Azure는 호출 규칙이 달라 전용 어댑터가 그 차이를 흡수해야 한다. 즉 '얼마나 쉽게 통합되는가'도 백엔드마다 차이가 있다.

4. 어떻게 작동하는가 - 통합 인터페이스에서 어댑터까지

통합 SDK의 내부 구조는 사실 고전적인 소프트웨어 설계 패턴의 깔끔한 적용이다. 세 개의 층으로 보면 명확하다.

4.1 통합 인터페이스(Interface) 층

맨 위에는 모든 백엔드가 따라야 할 공통 계약이 있다. put(key, data), get(key), delete(key), list(prefix), exists(key) 같은 최소한의 표준 메서드 집합이다. 애플리케이션은 오직 이 인터페이스에만 의존한다. S3라는 단어도, R2라는 단어도 애플리케이션 코드에는 등장하지 않는다.

4.2 어댑터(Adapter) 층

중간에는 백엔드별 어댑터가 있다. S3 어댑터, R2 어댑터, GCS 어댑터, Azure 어댑터, MinIO 어댑터가 각각 위 인터페이스를 구현하면서, 그 안에서 해당 클라우드의 진짜 SDK를 호출한다. 예를 들어 통합 인터페이스의 put은 S3 어댑터 안에서 PutObjectCommand로, GCS 어댑터 안에서는 bucket.file().save()로 번역된다. 차이를 흡수하는 책임이 전부 어댑터에 모인다.

4.3 백엔드(Backend) 층

맨 아래는 실제 클라우드 스토리지 그 자체다. 어댑터가 보낸 호출을 받아 데이터를 저장하고 반환한다. 이 구조의 묘미는, 새 클라우드를 지원하고 싶을 때 새 어댑터 하나만 추가하면 애플리케이션 코드는 한 줄도 안 바뀐다는 점이다. 확장이 가산적(additive)이라 안정적이다.

5. 코드 예시 - 같은 코드로 S3와 R2 전환

말보다 코드가 분명하다. 아래는 통합 SDK의 전형적인 사용 패턴을 보여 주는 의사코드다(특정 라이브러리의 실제 API가 아니라 개념을 드러내기 위한 예시).

// 1) 설정으로 백엔드를 결정 — 코드가 아니라 환경변수/설정
const storage = createStorage({
  backend: process.env.STORAGE_BACKEND, // "s3" | "r2" | "gcs"
  bucket: process.env.STORAGE_BUCKET,
  // R2/MinIO는 endpoint만 추가로 지정
  endpoint: process.env.STORAGE_ENDPOINT,
});

// 2) 애플리케이션 코드는 백엔드를 전혀 모른다
await storage.put("avatars/user-42.png", imageBuffer);
const file = await storage.get("avatars/user-42.png");
const keys = await storage.list("avatars/");
await storage.delete("avatars/user-42.png");

여기서 핵심은 업로드·다운로드·삭제 코드가 백엔드와 완전히 분리되어 있다는 점이다. S3에서 R2로 옮기고 싶으면 애플리케이션 코드는 한 줄도 건드리지 않고 STORAGE_BACKEND=s3를 STORAGE_BACKEND=r2로 바꾸고 엔드포인트만 R2 주소로 지정하면 된다.

# 운영 환경 — egress 많은 미디어는 R2로
STORAGE_BACKEND=r2
STORAGE_BUCKET=media-prod
STORAGE_ENDPOINT=https://<account>.r2.cloudflarestorage.com

# 백업 환경 — 생태계가 넓은 S3로
STORAGE_BACKEND=s3
STORAGE_BUCKET=backup-archive

코드를 다시 짜는 대신 설정 한 줄을 바꾼다. 이것이 통합 추상화가 약속하는 핵심 경험이다. 다만 뒤에서 다룰 '고유 기능' 영역은 이 깔끔함에서 예외라는 점을 미리 기억해 두자.

6. 유사 접근 비교 - Files SDK, Libcloud, fog, flysystem

'스토리지 통합 추상화'라는 아이디어 자체는 새롭지 않다. 언어 생태계마다 비슷한 시도가 있었다. 본인이 정리한 비교는 다음과 같다.

도구생태계특징비고

이 비교에서 본인이 강조하고 싶은 점은, 통합 추상화는 검증된 패턴이라는 것이다. Flysystem이 PHP/Laravel에서, fog가 Ruby/Rails에서 오래 자리 잡았다는 사실은 이 접근이 실무에서 작동한다는 증거다. Files SDK류의 새 도구는 여기에 R2처럼 egress가 0인 신흥 백엔드와 현대적 비동기 패턴을 더한 진화형으로 볼 수 있다.

7. 실무 활용 시나리오 5가지

추상론을 구체적 상황으로 내리자. 통합 스토리지 SDK가 진짜 빛나는 다섯 가지 시나리오다.

  1. 멀티클라우드 이중화: 핵심 자산을 S3와 GCS 양쪽에 동시 저장해 한 클라우드 장애에 대비. 통합 인터페이스 덕에 이중 쓰기 로직이 단순해진다.
  2. 비용 최적화 분산: egress가 많은 미디어는 R2로, 분석 파이프라인과 붙는 데이터는 GCS로 — 버킷별로 최적 백엔드를 고른다.
  3. 점진적 마이그레이션: 전체를 한 번에 옮기지 않고, 새 데이터부터 새 백엔드로 보내고 기존 데이터는 천천히 이전. 추상화가 두 백엔드를 동시에 다루게 해 준다.
  4. 로컬 개발 환경: 개발자 PC와 CI에서는 로컬 MinIO/파일시스템 백엔드를 쓰고, 운영에서만 클라우드를 쓴다. 클라우드 자격증명 없이도 개발이 돈다.
  5. 테스트 격리: 단위 테스트에서 인메모리 백엔드로 갈아끼워 외부 네트워크 의존성을 제거. 테스트가 빠르고 결정론적이 된다.

이 다섯 가지의 공통점은 모두 '스토리지 백엔드를 상황에 따라 자유롭게 바꾸는 능력'에서 가치가 나온다는 점이다. 그 능력은 코드를 인터페이스 뒤로 숨겼기 때문에 생긴다.

8. 비용 최적화 - R2 egress 무료의 위력

통합 SDK의 가장 현실적인 동기는 사실 돈이다. 그리고 그 중심에 Cloudflare R2의 egress 무료가 있다.

객체 스토리지 비용은 크게 세 가지로 나뉜다. 저장 용량(GB·월), 요청 수(API 호출), 그리고 egress(데이터를 인터넷으로 내보낼 때의 전송 요금)다. 많은 사람이 저장 용량만 생각하지만, 이미지·동영상·다운로드 트래픽이 많은 서비스에서는 egress가 전체 스토리지 청구서의 대부분을 차지하는 경우가 흔하다. 사용자가 파일을 받을 때마다 GB당 요금이 붙기 때문이다.

R2는 이 egress를 0으로 만든다. 저장과 요청 요금은 받되, 내보내기는 공짜다. 그래서 본인이 권하는 전략은 명확하다. egress가 큰 워크로드(공개 미디어, CDN 원본, 대용량 다운로드)는 R2로, egress가 작고 생태계 연계가 중요한 워크로드(분석용 데이터, AWS 서비스와 붙는 데이터)는 S3/GCS로 나누는 것이다. 통합 SDK가 있으면 이 분리를 버킷별 설정만으로 깔끔하게 구현할 수 있다.

주의: egress 무료라고 모든 것을 R2로 몰면 안 된다. AWS 생태계 깊숙이 들어간 워크로드(Athena, Lambda 트리거, 특정 IAM 연계 등)는 S3에 있어야 자연스럽다. 비용만 보고 옮기다 운영 복잡성이 커지면 절감액을 까먹는다. 최적화는 전체가 아니라 트래픽 패턴별 선택이어야 한다.

9. 한국 개발 환경 적용 - 네이버 클라우드, KT, 멀티클라우드 전략

이 주제는 한국 환경에서 특히 흥미로운 함의가 있다. 국내에는 글로벌 3사(AWS·GCP·Azure) 외에도 네이버 클라우드(NCP) Object Storage, KT Cloud, 카카오 클라우드 등 국산 클라우드가 있고, 이들 상당수가 S3 호환 API를 제공한다.

여기서 통합 SDK의 가치가 커진다. S3 호환 백엔드라면 통합 SDK의 S3 어댑터를 엔드포인트만 바꿔 국산 클라우드에도 그대로 쓸 수 있다. 즉 "글로벌 S3로 개발하고, 데이터 주권·비용·규제 때문에 국산 클라우드로 옮겨야 할 때 코드를 안 바꾼다"는 시나리오가 현실적으로 가능해진다. 공공·금융처럼 망 분리와 국내 리전이 요구되는 영역에서 이 이식성은 큰 무기다.

본인이 권하는 한국형 멀티클라우드 전략은 이렇다. 첫째, 처음부터 통합 인터페이스 뒤에 스토리지를 숨겨 특정 벤더에 코드를 묶지 않는다. 둘째, 규제·데이터 주권이 걸린 데이터는 국산 클라우드 어댑터로, egress가 큰 글로벌 트래픽은 R2로, 분석 데이터는 글로벌 클라우드로 분산한다. 셋째, 국산 클라우드의 S3 호환성이 완벽하지 않을 수 있으므로 도입 전 멀티파트 업로드·서명 URL 등 핵심 기능을 반드시 검증한다. 호환 API라도 미묘한 차이가 있을 수 있기 때문이다.

10. 위험과 한계 - 추상화 누수와 고유 기능

이 글이 '통합 SDK는 무조건 좋다'로 읽히면 곤란하다. 모든 추상화에는 대가가 있다. 본인이 보는 핵심 한계 세 가지다.

  • 추상화 누수(leaky abstraction): 모든 백엔드를 하나로 묶으려면 공통분모만 노출하게 된다. 그 결과 S3의 Intelligent-Tiering, GCS의 세밀한 IAM, R2의 Cloudflare 연계 같은 강력한 고유 기능을 충분히 못 쓰게 된다. 추상화는 이식성을 주는 대신 특수 능력을 깎는다.
  • 백엔드별 미묘한 차이: 일관성 모델(즉시 vs 최종 일관성), 오류 코드, 페이지네이션, 성능 특성이 백엔드마다 다르다. 추상화가 이를 완벽히 감추지 못하면 운영 중에 '같은 코드인데 다르게 동작'하는 함정이 드러난다.
  • 또 하나의 의존성: 통합 SDK 자체가 새 의존성이자 새 단일 장애 지점이다. 이 라이브러리에 버그가 있거나 유지보수가 끊기면, 추상화가 풀어 준 락인 대신 추상화 레이어에 대한 락인이 생긴다. 앞선 글에서 다룬 '혁신 토큰'을 여기에도 적용해야 한다.

그래서 본인의 권고는 균형적이다. put/get/list가 주력인 단순 사용 패턴이면 통합 SDK의 이득이 크고, 특정 클라우드의 고급 기능을 깊게 쓰는 워크로드라면 그 부분은 추상화를 우회해 직접 SDK를 쓰는 하이브리드가 현실적이다. 추상화는 신앙이 아니라 트레이드오프다.

11. 결론 - 통합 추상화는 미래 선택지를 사는 보험이다

Files SDK 같은 통합 blob 스토리지 추상화의 본질은 화려함이 아니다. 그것은 '미래에 스토리지를 바꿀 수 있는 권리'를 미리 사 두는 보험에 가깝다. 지금 당장은 S3 하나만 써도 충분할 수 있다. 그러나 1년 뒤 egress 청구서가 부담스러워 R2를 검토할 때, 혹은 규제 때문에 국산 클라우드로 옮겨야 할 때, 코드를 인터페이스 뒤에 숨겨 둔 팀과 S3 SDK에 코드를 깊게 묶은 팀의 마이그레이션 비용은 하늘과 땅 차이가 난다.

물론 이 보험에는 보험료가 있다. 추상화 누수, 고유 기능 제약, 추가 의존성이라는 비용이다. 그래서 핵심은 '추상화하느냐 마느냐'의 이분법이 아니라, '어디까지 추상화하고 어디부터 직접 쓸 것인가'의 경계 설계다.

즉시 적용할 수 있는 세 가지로 글을 닫는다. 첫째, 지금 새 프로젝트라면 스토리지 접근을 처음부터 얇은 자체 인터페이스나 통합 SDK 뒤에 숨겨라. 나중에 추가하는 비용이 처음부터 넣는 비용의 몇 배다. 둘째, egress 청구서를 한 번 들여다보고, 큰 트래픽 버킷만 R2로 옮기는 선택적 최적화를 검토하라. 전체 이전이 아니라 부분 최적화가 안전하다. 셋째, 국산 클라우드를 고려한다면 S3 호환 핵심 기능(멀티파트·서명 URL)을 도입 전에 직접 검증하라. 호환은 동일이 아니다. 이 세 가지만 지켜도 스토리지 코드를 다시 짜는 고통의 대부분을 미리 피할 수 있다.
