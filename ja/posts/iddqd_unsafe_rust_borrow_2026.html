序論: なぜ「値からキーを借りる」マップが難しいのか

Rustをある程度使った人なら誰もが一度はボローチェッカー（borrow checker）と戦った経験があるはずです。多くの戦いはコードを少し変えれば解けます。ところが、いくらコードをひねっても安全なRustの文法だけでは決して表現できない問題があります。iddqdという小さなマップライブラリが扱うのは、まさにその種類の問題です。iddqdは「値の中にあるフィールドをキーとして借りてインメモリ索引を作る」という、一見ありふれた要求を解きます。しかしその平凡さの裏には、Rustで最も厄介なunsafeのテーマ — 自己参照構造、ムーブとダングリング、Pin、そして安全なカプセル化 — がすべて凝縮されています。

本稿は2026年6月初旬にnews.hada.ioで話題になった「iddqd: 最も難しい種類のunsafe Rust」というトピックを出発点としつつ、原文を直訳せず独自の視点でこの問題を一つずつ解剖します。ちなみにライブラリ名iddqdは、古典ゲームDOOMの無敵チートコードから取られたものと見られ、「バグに無敵な索引」という冗談混じりの自負が感じられます。本当に無敵なのか、そしてその無敵がどんな代償の上に得られるのかを覗いてみます。

1. borrow-from-value - 問題を正確に定義する

まず問題を曖昧にせず定義します。あるオブジェクトのリストをメモリに保持し、それを高速に参照したいとします。よくある方法はキー・バリューのマップです。ところが多くの実務状況ではキーは既に値の中にあります。例えばユーザー構造体はidフィールドを持ち、私たちはそのidでユーザーを探したい。

struct User {
    id: u64,        // このフィールドがキーだ
    name: String,
    addr: String,
}

一般的なHashMap<u64, User>を使うと、キーidはマップのキー枠に一度、値User.idにもう一度 — 同じ値を二箇所に保存することになります。些細に見えますが二つが気になります。一つは重複保存。もう一つ、より本質的に、キーと値が別々だと両者がずれる余地が生まれます。誰かが値のidを変えると、マップのキーと不一致になります。

borrow-from-valueはこの重複をなくす発想です。キーを別に複製して保存するのではなく、値の中のフィールドを直接キーとして借りて（borrow）索引を作ろうというものです。概念的にはマップがUserを所有し、同時にそのUser.idを指す参照でハッシュテーブルを構成します。この「所有しつつ同時に内部を参照する」が、Rustで最も扱いにくい構造の種です。

2. 一般的なHashMapとの違い

標準ライブラリのHashMapはキーと値を別個の所有データとみなします。キーを入れるとき通常はキーを複製するか所有権を渡します。このモデルは単純で安全ですが、先に見た「キーが値の中にある」状況には合いません。

項目一般的なHashMapborrow-from-valueマップ（iddqd系）
キー保存値と別に複製・所有値の内部フィールドを借りて使用
重複キーが値内にもあれば重複なし（単一所有）
一貫性キーと値がずれる余地キーが値なのでずれない
多重キー索引ごとに別マップが必要一つの値に複数のキー索引
実装難度安全Rustで簡単内部unsafeが必要

核心的な違いは最後の二行です。borrow-from-valueマップは一つの値に複数のキー索引を同時に付けられ（idでもnameでも参照）、その代わり内部でunsafeを受け入れます。iddqdが提供する価値は「このunsafeを利用者が直接書かなくて済むよう、ライブラリが代わりに責任を持ってカプセル化する」点にあります。

3. 自己参照構造が危険な理由

なぜunsafeが不可避かをもう一段掘り下げます。マップがUserを所有しつつ、そのUser.idを指すポインタでハッシュバケットを構成するということは、データ構造の中に自分自身を指す参照が生じることを意味します。これが自己参照構造（self-referential struct）です。

// 概念的な形（そのままではコンパイルされない）
struct Index {
    storage: Vec<User>,        // 値を所有
    by_id: HashMap<&u64, usize>, // storage内部のidを借りる
}

このコードがコンパイルされない理由は、ボローチェッカーから見てby_idの参照の生存期間を表現する方法がないからです。by_idはstorageが生きている間だけ有効ですが、両者が同じ構造体の中にあると「この参照は兄弟フィールドと同じだけ生きる」という生存期間をRustの型システムで書けません。Rustの生存期間表記は構造体の外のデータを指す前提で設計されており、自分の内部を指す循環は静的に証明できません。

安全なRustが自己参照を拒むのは欠陥ではなく誠実さだ。コンパイラは「私はこの参照が安全だと証明できない」と正直に言っているだけだ。

そこで選択肢は二つです。参照の代わりに索引（usize）をキーに使う回避策（安全だが一段の間接コスト）、または生ポインタとunsafeで自己参照を直接表現しつつその安全を人が責任を持つ道。iddqdのようなライブラリは性能と使い勝手のため後者を選び、その危険を狭いunsafe中核の中に閉じ込めます。

4. ムーブとダングリング - 最も微妙な罠

自己参照の本当に恐ろしい点は、コンパイル時ではなく実行時にあります。核心の言葉はムーブ（move）です。Rustでは値は既定で移動可能で、移動はたいていメモリ上のバイトコピーで行われます。値が新しいアドレスへ移されると、その値の内部を指していた生ポインタは古いアドレスをそのまま指したまま残ります。その瞬間ポインタはダングリング（dangling）になり、参照外しすると未定義動作（UB）です。

// なぜ危険か - 疑似コード
let mut v = vec![user];          // userがヒープバッファAにある
let p: *const u64 = &v[0].id;    // A内部を指す
v.push(other);                   // 容量超過 → ヒープバッファBへ再割り当て（移動！）
// 今やv[0]はBにあるが、pは依然としてAを指す → ダングリング
unsafe { let _ = *p; }           // UB: 解放済みメモリの参照外し

この例が示すように、Vecの再割り当て一回だけで内部ポインタがまるごと無効化されます。自己参照データ構造を作るとき最も多く、最も捕まえにくいバグがこれです。コンパイルは問題なく通り、小さな入力では偶然動き、特定のサイズで再割り当てが起きた瞬間にメモリ破壊が起きます。

注意 - この種のバグはデバッグビルドで運良く生き残りリリースビルドで爆発したり、その逆だったりします。「私の環境では動くのですが」が最も危険な一文になる領域です。

5. Pinの役割と限界

移動が問題なら、解の一軸は明確です。値が移動できないよう固定すること。このためRust標準ライブラリはPinという型を提供します。Pin<P>は、指す対象がメモリ上でもう移動しないことを型レベルで約束します。自己参照構造がいったん正しい場所に落ち着けば、Pinがその場所を守り内部ポインタが有効であり続けるよう助けます。

ただし強調したいのは、Pinが万能の安全装置ではない点です。Pinが保証するのは「安全なコードからは対象を移動できない」という制約だけで、自己参照ポインタを正しく設定し維持する責任は依然としてunsafeを書く人にあります。Unpinでない型を扱い、get_unchecked_mutのようなunsafeの通路を正確な不変条件の下でのみ使う、厄介な規則の集合です。

use std::pin::Pin;
use std::marker::PhantomPinned;

struct SelfRef {
    data: String,
    // dataを指すポインタ（概念）
    slice: *const u8,
    _pin: PhantomPinned, // Unpinでなくして移動を防ぐ印
}

実務でPinを手で扱うコードは悪名高く難しいです。だから多くのライブラリはPinを直接公開せず、自己参照の危険をライブラリ内部に隠して利用者には普通のマップAPIだけを見せます。iddqdの価値もまさにこの「隠蔽」にあります。利用者はinsert・getだけを呼び、Pinと生ポインタの地獄はライブラリが背負います。

6. iddqdの設計アイデア

では、iddqdはこの問題をどう解くのか。公開情報と一般的なborrow-from-valueマップの設計原理を基に、私が理解した核心のアイデアを整理します。（細部の実装はバージョンにより異なるので原理レベルで見ます。）

6-1) 値は一度だけ所有する

マップは各値を一箇所に安定して保管します。値が一度落ち着けばそのアドレスが揺れないよう保存戦略を設計します（例えば安定したアドレスを保証する割り当て方式）。このアドレス安定性が、自己参照ポインタを有効に保つ土台です。

6-2) キーは値から借りて索引を作る

利用者は「この値からキーをどう取り出すか」をトレイトで知らせます。マップは挿入時にその規則で値からキーを借りてハッシュし、内部索引に登録します。キーを別に複製・所有しないので重複が消え、キーと値がずれることがありません。

6-3) unsafeは狭い中核に閉じ込める

生ポインタと自己参照の危険はライブラリの小さな中核にのみ存在し、その上に100%安全な公開APIを乗せます。利用者コードにはunsafeが一文字も現れません。

// 概念的な使用例（APIはバージョンにより異なる）
let mut map = IdHashMap::new();
map.insert(User { id: 1, name: "kim".into(), addr: "10.0.0.1".into() });
map.insert(User { id: 2, name: "lee".into(), addr: "10.0.0.2".into() });

// 値の中のidをキーとして借りて参照 - 利用者には普通のマップ
if let Some(u) = map.get(&1) {
    println!("{} @ {}", u.name, u.addr);
}
核心 - 良いunsafeライブラリの美徳は「危険をなくす」ことではなく「危険を狭い場所に閉じ込め、その境界の外では安全を保証する」ことです。iddqdが狙う地点がまさにこの境界設計です。

7. 多重キー索引とコントロールプレーン

borrow-from-valueの真価は多重キー索引で現れます。同じ値を複数のキーで参照したいとき、普通は索引ごとに別のマップを手で維持します。問題は、挿入・削除・変更のたびに全てのマップを漏れなく更新せねばならず、一つでも漏れると索引が壊れる点です。

// 手で多重索引を維持すると同期地獄
by_id.insert(u.id, u_ref);
by_name.insert(u.name.clone(), u_ref);
by_addr.insert(u.addr.clone(), u_ref);
// 削除時に三つのうち一つでも漏らすと → 幽霊エントリ、リーク、誤った参照

borrow-from-valueマップは値を一度だけ保存し複数のキー索引をその上に付けるので、挿入・削除が自動で全索引に一貫して反映されます。この特性が輝く代表的な舞台がコントロールプレーンです。コントロールプレーンはクラスタノード、サービス、エンドポイントといったメタデータをメモリに保持し、同じオブジェクトをIDでも・名前でも・ネットワークアドレスでも即座に探す必要があります。

  • サービスディスカバリ: サービス名とインスタンスIDの両方で同一オブジェクトを参照
  • ノードレジストリ: ノードUUID、ホスト名、IPをすべてキーとして使用
  • スケジューラ状態: ジョブIDと割当ノードを相互参照

こうしたシステムは参照が非常に頻繁で、索引の不一致がそのまま障害につながります。だから「一度保存、複数キー、自動一貫性」というiddqd系の保証は単なる便利さではなく正確性の安全装置になります。Rustでコントロールプレーンを書くチームがこうしたライブラリに魅力を感じる理由です。Rustシステムツールの広い文脈はsshc - Rust SSHマネージャ 2026でも扱います。

8. unsafeカプセル化 - 良いunsafeと悪いunsafe

unsafeという言葉に過剰反応する必要はありません。Rustの標準ライブラリ自体が内部に膨大なunsafeを抱え、Vec・Stringも生ポインタの上に安全APIを乗せた構造です。重要なのはunsafeの有無ではなく設計の質です。

私が見る「良いunsafe」の条件は次の通りです。

  • 狭い面積: unsafeブロックがライブラリの中核数箇所にのみ隔離されていること
  • 明文化された不変条件: 各unsafeが依存する安全条件がコメント・文書に明確に書かれていること
  • 安全な境界: 公開APIはどんな入力でもUBを起こさないこと（健全性 soundness）
  • 検証の痕跡: Miri・ファジング・テストでその不変条件を実際に叩いたこと

逆に「悪いunsafe」は面積が広く、不変条件が頭の中だけにあり、公開APIが特定の使い方でUBに漏れる場合です。iddqdのようなライブラリを評価するとき、私がまず見るのは機能一覧ではなくunsafe面積と検証の痕跡です。この視点はメモリ安全のためCをRustで書き直す大きな流れとも通じており、詳しい文脈はRustによるZstandard実装 2026で整理しました。

9. 検証ツール - Miri、ファジング、RustSec

unsafeコードはコンパイラが安全を保証しないので、作者がツールで安全を立証せねばなりません。自己参照・生ポインタを扱うライブラリならなおさらです。私が信頼の根拠とする三つのツールを整理します。

9-1) Miri - 未定義動作の検出器

MiriはRustコードを中間表現（MIR）レベルで解釈実行し、ダングリング参照・アライメント違反・解放後使用といったUBを捕まえます。cargo +nightly miri testの一行でテストをMiri上で回せます。自己参照データ構造のポインタ規則違反はMiriが最も得意とする部類です。

# Miriでテスト実行（nightly必要）
rustup +nightly component add miri
cargo +nightly miri test

9-2) ファジングとプロパティテスト

cargo-fuzzで無作為な入力を大量生成して境界条件を叩き、proptest・quickcheckで「どんな挿入・削除の順序でも索引が一貫する」といった不変条件を自動検査します。自己参照マップでは特に再割り当てを誘発する大量挿入のシナリオを重点的に叩くべきです。

9-3) RustSecとcargo-audit

依存に既知の脆弱性があるかはcargo auditでRustSecの勧告DBと照合します。unsafeを抱えるライブラリを採用するとき、過去に報告された健全性の問題があったか、どう修正されたかを確認するのは基本的な衛生です。

10. 自作する際の落とし穴

「大したことなさそうだから自分で書けないか」という誘惑が湧くかもしれません。私の経験では、自己参照マップを自作しようとして陥る代表的な落とし穴は次の通りです。

  1. Vec再割り当ての見落とし: 4章で見た通りです。要素を増やして容量を超えるとバッファがまるごと移動し、全ての内部ポインタが無効化されます。Vecではなくアドレスが安定したコンテナが必要です。
  2. drop順序の誤り: 自己参照構造はフィールドの解放順序が誤ると、既に解放されたメモリを指すポインタが一瞬生き残ります。Drop実装に微妙なUBが潜みます。
  3. 可変エイリアシング違反: 同じデータに可変参照と別の参照が同時に存在すると、Rustのエイリアシング規則（特にstacked/tree borrowsモデル）に違反し、最適化がコードを壊し得ます。
  4. 変更時の索引更新漏れ: キーとなるフィールドが変わると索引も更新せねばなりませんが、安全APIでこれを防がないと静かに壊れます。だから良い設計はキーフィールドを不変として扱います。

このリストだけでも、既に検証されたライブラリを使う方がほぼ常に合理的だと分かります。私の推奨は「本当にホットパスで、自分で測定してボトルネックが確認されたときだけ」自作を検討し、その場合も必ずMiriとファジングを付けることです。

11. 開発現場への示唆

このトピックはニッチですが、開発現場に照らしてもいくつか明確な示唆があります。

11-1) Rustインフラ導入が増えている

ネットワークプロキシ、ストレージエンジン、Kubernetes周辺のコントロールプレーンをRustで書く事例が増えています。こうしたシステムほどインメモリ索引の正確性と性能が直接安定性につながるため、borrow-from-valueマップの価値を体感しやすいです。

11-2) unsafeレビュー力が資産になる

Rustを使うチームが増えるにつれ「unsafeを読み評価する」力の希少価値が高まります。ライブラリのunsafe面積を見積もり、Miri・ファジングの痕跡を点検し、健全性の境界を吟味するシニアの眼力は、そのまま採用・コードレビューの武器になります。

11-3) 採用基準は「機能」でなく「検証」だ

私の推奨は、unsafeを抱えるライブラリを選ぶとき星の数や機能表ではなく検証の成熟度を第一に置くことです。CIにMiriが回り、ファジングのターゲットがあり、RustSec履歴が綺麗で、unsafeごとに安全コメントが付いていれば — そのライブラリは信頼できます。GoからRustへ移る大きな移行の文脈はGoからRustへの移行ガイド 2026でも触れました。

12. 結論 + 得るべき教訓3つ

iddqdを一文で要約するとこうです。「値からキーを借りてインメモリ索引を作る、平凡に見えてRustで最も難しいunsafe領域を正面からカプセル化した小さなマップ」です。自己参照・ムーブ・Pin・エイリアシングという難題を狭い中核に閉じ込め、利用者には普通のマップAPIだけを渡します。このトピックから得た三つの教訓で締めます。

12-1) 教訓1: 「平凡な要求」がunsafeの入口になり得る

「値の中のidで参照したい」という極めて平凡な要求が、深く入るとRustで最も難しい自己参照問題につながります。あるデータ構造を設計するとき「これは自分自身を参照することになるか？」を早く問う習慣が、大きな事故を防ぎます。

12-2) 教訓2: unsafeはなくすものではなく閉じ込めるものだ

良いライブラリはunsafeをゼロにしません。危険を狭い中核に隔離し、その境界の外を安全に保証します。利用者として私たちが見るべきは、unsafeの存在ではなくその面積と検証です。

12-3) 教訓3: 自己参照を扱うならMiriは選択でなく必須だ

生ポインタと自己参照に触れた瞬間、普通のテストはダングリング・エイリアシング違反を見逃し得ます。Miri・ファジング・プロパティテストで不変条件を実際に叩くまでは「動く」と言わないでください。私にとってiddqdの本当の教訓は派手なトリックではなく、最も難しいunsafeほど最も謙虚に検証すべきだという態度です。
