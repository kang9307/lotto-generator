계기 — 구조 설명이 아니라 설계 판단을 묻는 글

2026년 7월 28일 stock-engineer.com에 「Claude Code 스킬 패턴」이라는 글이 게시되어 9월 29일 수정되었고, GeekNews에는 2026년 10월 4일 등록 항목으로 소개되었다. 원문은 일곱 개 장으로 나뉜다. 같은 작업을 왜 매번 처음부터 설명해야 하는지에서 출발해 스킬을 명령어 모음이 아니라 작업 판단 기준으로 보는 관점을 세우고, Anthropic의 스킬 설계에서 읽은 네 가지 원칙, 규모별 구성 방식, 공개 컬렉션 세 가지의 설계 철학, 저자가 실무에서 얻은 다섯 가지 경험, 마지막으로 별도 스킬로 분리할 가치가 있는지 가르는 질문 여섯 가지를 차례로 다룬다. 저자 소개에 따르면 임베디드 소프트웨어 개발 경력이 있는 엔지니어이고, 실무 경험은 그 개발 업무와 블로그 운영에서 나온 것으로 서술된다.

이 주제의 기본 구조와 작성법은 이미 Claude Code Skills A-Z 가이드에 정리되어 있고, 특정 스킬이 실제로 어떻게 만들어졌는지는 Archify 분석에 있다. 규칙을 컨텍스트에 두는 방식과 훅으로 바꾸는 방식의 구조적 비교는 CLAUDE.md 규칙을 훅으로 컴파일하는 접근 분석이 다룬다. 여기서는 그 글들이 직접 답하지 않는 질문, 즉 설계 판단에 한정한다. 언제 스킬로 나누는가, description에 무엇을 써서 호출 시점을 맞추는가, 어떤 규칙을 스킬에 두고 어떤 규칙을 훅에 넘기는가.

설계 판단은 근거의 종류가 섞이기 쉬운 영역이다. 공식 문서가 확정한 사실, 공식 문서가 권고하는 것, 한 사람이 실무에서 얻었다고 말하는 경험이 한 문단에 뒤섞이면 독자는 어디까지가 규칙인지 알 수 없다. 그래서 아래에서는 원문의 각 주장을 공식 문서와 대조해, 확인되는 것, 부분적으로만 확인되는 것, 저자의 경험으로만 남는 것으로 나눈다. 원문의 훅 절에는 종료 코드 2의 설명이 없고, 「구체적인 설정과 종료 코드 함정은 규제산업 이중 게이트 글에 정리했습니다」라며 다른 글로 넘긴다는 언급만 있다는 점도 먼저 밝혀 둔다. PreToolUse 이벤트와 종료 코드 2는 공식 훅 문서에서 가져와 별도 항목으로 표시했다.

원문의 주장과 공식 문서로 확인되는 범위

아래 표는 원문의 핵심 주장 일곱 가지를 공식 문서와 대조한 결과다. 「확인」은 같은 취지의 문장이 공식 문서에 있다는 뜻이고, 「부분 확인」은 일부만 있다는 뜻이며, 「저자 경험」은 대조할 공식 문장이 없다는 뜻이다. 저자 경험이 틀렸다는 표시가 아니다. 공식 문서가 다루지 않는 영역일 뿐이다.

description은 설명문이 아니라 트리거다

원문이 네 번째 원칙으로 꼽는 것이 이 항목이다. 원문은 description이 사용자를 위한 설명문이 아니라 에이전트가 스킬을 켤지 정하는 신호라고 말하고, 무엇을 하고 언제 쓰는지를 함께 적으라고 한다. 예시는 「API 변경 후 호환성 테스트와 마이그레이션 검증이 필요한 작업에 사용」이다. 공식 자료는 같은 방향이다. 모범 사례는 description이 스킬 발견의 기준이며, Claude가 100개 이상일 수 있는 스킬 중에서 알맞은 것을 고를 때 이 필드를 쓴다고 설명한다. Claude Code 문서도 Claude가 이 필드로 스킬을 적용할 시점을 정하며, 생략하면 본문의 첫 비지 않은 줄을 대신 쓴다고 적는다.

아래 코드는 Claude Code 문서가 보여 주는 SKILL.md 머리말의 형식이다. 현재 문서의 예시를 그대로 옮긴 것이며, 문서는 이 예가 필드 네 개를 지정한다고 적는다.

---
                    name: my-skill
                    description: What this skill does
                    disable-model-invocation: true
                    allowed-tools: Read Grep
                    ---
                    Your skill instructions here...

이 예에서 트리거와 관련된 필드는 둘 이상이다. description이 호출 시점의 판단 재료이고, disable-model-invocation을 true로 두면 Claude가 그 스킬을 자동으로 로드하지 않는다. 같은 문서의 표에는 description 뒤에 덧붙는 when_to_use, Claude만 호출하도록 하는 user-invocable, 활성 범위를 글롭으로 제한하는 paths도 있다. 호출 시점을 맞추는 일이 문구 하나에만 달린 것이 아니라는 뜻이다.

  • 무엇과 언제를 함께 — 모범 사례의 좋은 예는 PDF 텍스트·표 추출과 양식 채우기 같은 기능 뒤에 「PDF 파일을 다루거나 사용자가 PDF, 양식, 문서 추출을 언급할 때 사용」을 붙인다.
  • 모호한 설명은 실패한다 — 모범 사례가 나쁜 예로 드는 것은 「Helps with documents」「Processes data」 같은 문장이다. 무엇도 가리지 않아 다른 스킬과 구별되지 않는다.
  • 3인칭으로 — 모범 사례는 description이 시스템 프롬프트에 주입되므로 시점이 섞이면 발견에 문제가 생길 수 있다고 하며 3인칭을 권한다.
  • 한도는 문서마다 다르다 — 스킬 작성 모범 사례는 description을 최대 1,024자로 적고, Claude Code 문서는 description과 when_to_use를 합친 글이 스킬 목록에서 1,536자에서 잘린다고 적는다. 두 수치는 서로 다른 문서의 서술이며 하나로 합칠 수 없다.
  • 핵심 용도를 앞에 — Claude Code 문서는 목록에서 잘릴 수 있으므로 핵심 사용 사례를 앞에 두라고 한다.
  • 절차는 본문으로 — 한도가 있는 필드에 절차까지 넣으면 정작 호출 시점 신호가 밀린다. 이는 두 한도에서 이어지는 해석이며 원문이 이렇게 말한 것은 아니다.
  • 제외 조건 — 「쓰지 않을 때」를 적는 방식에 대한 지침은 조회한 공식 문서 범위에 없었다. 겹치는 스킬이 있을 때 설계자가 정할 부분이다.

SKILL.md는 목차이고 세부는 밖으로 뺀다

원문의 두 번째와 세 번째 원칙은 같은 방향을 가리킨다. 점진적 공개를 위해 SKILL.md를 목차로 쓰고, 세부 내용은 references, 실행 코드는 scripts, 템플릿은 assets에 둔다. 그리고 지시는 반드시 지킬 순서·완료 조건·금지사항만 남기고 배경 설명은 별도 문서로 옮긴다. 공식 문서에서 이에 해당하는 것이 500줄 권고다. Claude Code 문서는 SKILL.md를 500줄 아래로 유지하고 상세한 참고 내용은 별도 파일로 옮기라고 적는다. 스킬 작성 모범 사례도 최적의 성능을 위해 같은 기준을 제시한다.

이 원칙에서 설계 판단이 필요한 곳은 두 군데다. 하나는 무엇을 밖으로 내보내는가이고, 다른 하나는 얼마나 깊이 내보내는가다. 공식 모범 사례는 후자에 구체적이다. 참조 파일은 SKILL.md에서 한 단계 깊이로 연결하라는 것이다. 참조가 다른 참조를 가리키면 Claude가 파일 앞부분만 미리 보고 끝낼 수 있어 정보가 불완전해진다고 설명한다. 100줄이 넘는 참조 파일은 맨 위에 목차를 두라는 권고도 같은 이유에서 나온다.

  • 500줄은 권고다 — 두 공식 문서 모두 「유지하라」「최적의 성능을 위해」로 적고 있고, 초과 시 자동으로 거부된다는 서술은 없다.
  • 한 단계 깊이 — SKILL.md에서 참조 파일로 직접 연결하고, 참조 파일에서 다시 다른 파일을 가리키는 구조는 피한다.
  • 긴 참조 파일에는 목차 — 100줄을 넘으면 맨 위에 목차를 두어 부분 읽기에서도 전체 범위가 보이게 한다.
  • 실행인지 참고인지 명시 — 스크립트는 읽는 것인지 실행하는 것인지를 지침에 밝힌다. 실행하면 스크립트의 출력만 토큰을 쓰고 내용은 컨텍스트에 들어가지 않는다.
  • 자유도를 작업에 맞춘다 — 접근법이 여럿 유효하면 텍스트 지시, 선호 패턴이 있으면 파라미터가 있는 스크립트, 작업이 취약하고 순서가 고정이면 「이 스크립트를 그대로 실행」처럼 좁게 지시한다.
  • 기본값 하나와 예외 — 여러 도구를 나열하지 말고 기본 도구 하나를 정하고 예외 상황만 덧붙인다.

파이프라인 스킬과 도구 스킬을 나누는 기준

원문이 실무 경험의 첫째로 드는 것이 이 분리다. 저자는 파이프라인 스킬이 티켓을 읽는 것부터 분석, 테스트 작성, 구현, 검증, PR 생성까지 여러 단계를 잇고, 그 안의 개별 동작인 빌드·테스트·포맷·린트는 도구 스킬이 맡는다고 서술한다. 공식 문서에는 이 두 용어가 없다. 따라서 이 분리는 저자의 설계 경험으로 다루어야 한다. 다만 근거가 되는 인접한 권고는 있다. 스킬 모범 사례는 결정론적 동작에는 스크립트를 쓰라고 하며, 그 이유로 생성된 코드보다 믿을 수 있고 토큰과 시간을 아끼며 사용 간 일관성을 보장한다는 점을 든다.

분리가 의미를 갖는 조건은 두 가지로 정리할 수 있다. 첫째는 같은 동작이 여러 절차에서 반복될 때다. 빌드와 테스트처럼 어느 파이프라인이든 거치는 동작을 도구 스킬로 떼어 두면 절차가 바뀌어도 동작의 정의는 한 곳에 남는다. 둘째는 절차는 자주 바뀌는데 동작은 고정일 때다. 이 두 조건은 원문이 직접 적은 것이 아니라 저자의 서술에서 읽을 수 있는 설계 해석이며, 원문이 제시한 근거는 분리했다는 경험 자체다.

  • 파이프라인 스킬 — 단계의 순서, 단계 사이의 완료 조건, 금지사항을 가진다. 원문의 예는 티켓 읽기에서 PR 생성까지다.
  • 도구 스킬 — 빌드·테스트·포맷·린트처럼 입력과 출력이 비교적 고정된 동작을 맡는다.
  • 연결 방식 — 파이프라인이 도구 스킬을 호출하는 구조다. 호출 방식의 세부는 원문에 없다.
  • 적용 한계 — 이 구분이 모든 팀에 맞는다는 근거는 없다. 원문은 저자 자신의 개발 파이프라인과 블로그 운영에서 얻은 경험이라고 밝힌다.

공개 컬렉션 세 가지가 갈라 놓은 축

원문은 공개 컬렉션 세 가지를 서로 다른 설계 철학의 예로 든다. 원문이 공개 컬렉션으로 든 것은 Superpowers, GSD, caveman 세 가지이며, 더 늘리지 않는다. 규모를 다루는 절에서는 Karpathy의 관찰을 바탕으로 한 CLAUDE.md 프로젝트와 42개 스킬 카탈로그 사례도 들지만 그것은 구성 방식의 예이다. 아래 표의 두 번째 열은 원문의 요약이고, 세 번째 열은 스킬 설계의 관점에서 어느 축을 대표하는지에 대한 해석이다.

컬렉션원문의 요약대표하는 설계 축(해석)
Superpowers개발 절차를 강제하는 스킬. 브레인스토밍, 계획, RED-GREEN-REFACTOR 구현, 명세 검토, 코드 품질 검토절차의 강제. 순서와 검토 단계가 스킬의 중심
GSDdiscuss에서 execute까지 컨텍스트를 나눈다. discuss, plan, execute, verify, ship. 작은 계획으로 나눠 메인 세션 컨텍스트 비대화를 줄인다컨텍스트의 분리. 단계마다 쓰는 컨텍스트를 갈라 놓음

원문은 이 세 가지를 규모별 구성 방식과 함께 놓는다. 단일 규칙 파일은 설치와 유지가 단순하지만 작업별 세부 절차를 담기 어렵다. 소규모 스킬 세트는 반복되는 개발 흐름을 분리하기 쉬우나 역할 경계가 겹칠 수 있다. 대형 스킬 카탈로그는 여러 직무와 업무를 폭넓게 지원하지만 탐색·권한·버전 관리가 복잡해진다. 이 세 가지의 장단점은 원문의 표를 옮긴 것이며, 공식 문서가 같은 분류를 두고 있지는 않다.

  • 단일 규칙 파일 — 장점은 설치와 유지의 단순함, 주의점은 작업별 세부 절차를 담기 어렵다는 것.
  • 소규모 스킬 세트 — 장점은 반복 개발 흐름을 분리하기 쉬운 것, 주의점은 역할 경계의 중복.
  • 대형 스킬 카탈로그 — 장점은 폭넓은 지원, 주의점은 탐색·권한·버전 관리의 복잡도.

함정 목록은 어디에 두는가

원문의 첫 번째 원칙은 좋은 스킬이 정상 절차뿐 아니라 흔한 실수와 실패 패턴을 명시한다는 것이다. 예로 드는 문장이 「테스트 통과만으로 요구사항 충족을 단정하지 않는다」이다. 이 원칙은 실무 경험의 둘째 항목에서 문제를 만난다. 저자는 함정 목록이 스킬 본문이 감당하는 속도보다 빨리 늘어난다고 서술하고, 해법으로 함정을 스킬 밖의 지식 파일로 분리하는 방식을 택했다고 한다. 스킬 본문은 절차만 담고, 지식 파일은 세션마다 얻은 교훈을 리뷰·포맷·빌드·테스트·CI·설계 같은 접두어로 분류해 쌓는다.

공식 문서에서 이에 가까운 것은 참조 파일 분리와 시간에 민감한 정보를 다루는 방식이다. 모범 사례는 곧 낡을 정보를 본문에 두지 말고 「old patterns」 절에 접어 두라고 한다. 함정 목록은 낡는 속도가 서로 다르다는 점에서 이 권고와 맞닿는다. 다만 접두어 분류와 세션마다 쌓는 운영 방식은 공식 문서에 없는 저자의 방식이다.

  • 본문에 둘 함정 — 절차를 건너뛰면 곧바로 실패하는 금지사항. 원문의 세 번째 원칙인 「필수 순서·완료 조건·금지사항」에 해당한다.
  • 지식 파일에 둘 함정 — 세션을 거치며 계속 늘어나는 개별 사례. 접두어로 분류해 필요한 분류만 읽게 한다.
  • 낡는 함정 — 특정 버전이나 시점에 묶인 함정은 「old patterns」 같은 구역에 모아 본문과 분리한다.
  • 어디까지가 경험인가 — 본문과 지식 파일을 가르는 기준은 위처럼 해석한 것이며, 원문이 기준을 수치로 제시하지는 않았다.

스킬은 지시하고 훅은 막는다 — 역할 분담

원문의 네 번째 경험이 이 분담이다. 저자는 「리뷰 문서를 만든 뒤에 push한다」는 지시를 스킬에 적는 것보다, 리뷰 문서가 없으면 push 명령 자체를 막는 Claude Code 훅으로 강제하는 편이 낫다고 서술한다. 요약하면 스킬은 하라고 말하고 훅은 못 하게 막는다. 원문은 훅의 이벤트나 종료 코드를 설명하지 않고, 「구체적인 설정과 종료 코드 함정은 규제산업 이중 게이트 글에 정리했습니다」라고 다른 글로 넘긴다. 아래는 공식 훅 문서가 확인해 주는 부분이다.

공식 훅 문서에서 종료 코드 2는 차단 오류다. 차단할 수 있는 이벤트에서는 JSON을 출력했는지와 관계없이 종료 코드 2가 차단하며, JSON의 permissionDecision이 allow여도 이를 덮어쓰지 못한다. PreToolUse에서 종료 코드 2는 도구 호출을 막는다. 차단 메시지는 JSON이 있으면 그 사유, 없으면 표준 오류 텍스트가 쓰인다. 종료 코드 0은 성공이고, 그 밖의 종료 코드는 대부분의 이벤트에서 그것만으로는 차단하지 않는다.

{
                      "hookSpecificOutput": {
                        "hookEventName": "PreToolUse",
                        "permissionDecision": "deny",
                        "permissionDecisionReason": "Destructive command blocked by hook"
                      }
                    }

위 JSON은 공식 문서가 종료 코드 2의 대안으로 보여 주는 PreToolUse의 구조적 출력이다. permissionDecision에 쓸 수 있는 값은 allow, deny, ask, defer이다. 훅은 settings.json 같은 JSON 설정 파일이나 플러그인에서 정의하고, matcher 필드로 어떤 도구에 반응할지 거른다. 공식 훅 레퍼런스는 훅을 셸 명령, HTTP 엔드포인트, MCP 도구 호출, LLM 프롬프트 또는 서브에이전트로 설명한다. 「결정론적(deterministic)」이라는 표현은 훅 가이드에 있고, 훅이 LLM의 선택에 기대지 않고 정해진 시점에 항상 실행되는 사용자 정의 셸 명령이라는 뜻이다. 이 성질이 원문의 분담, 곧 어겨서는 안 되는 규칙은 훅이 맡는다는 판단을 뒷받침한다.

  • 스킬에 둘 규칙(해석) — 판단과 순서가 필요하고 어겨도 되돌릴 수 있는 것. 에이전트가 읽고 따르는 절차다.
  • 훅에 둘 규칙 — 어기면 안 되는 것(원문의 분담). 도구 호출 직전에 조건을 검사해 막는다. 원문의 예는 리뷰 문서가 없을 때의 push 차단이다.
  • 종료 코드의 함정 — 차단하려면 종료 코드 2이거나 구조적 출력으로 deny여야 한다. 다른 비정상 종료 코드는 대부분의 이벤트에서 그것만으로 차단하지 않으므로, 스크립트가 오류로 종료했다고 해서 막힌다고 가정하면 안 된다.
  • 차단 사유의 전달 — 차단 메시지는 에이전트가 읽는 정보이므로 무엇이 없어서 막혔는지 구체적으로 적는 편이 다음 행동에 도움이 된다. 이는 문서의 서술에서 이어지는 해석이다.
  • 스킬과 훅의 접점 — 공식 문서의 훅 정의 위치 목록에는 스킬과 서브에이전트의 머리말도 있으며 그 경우 스킬이 실행되는 동안에 적용된다.
  • 더 깊은 비교 — 규칙을 컨텍스트에 주입하는 방식의 한계와 훅으로 바꾸는 접근은 앞선 분석 글이 다룬다.

스킬이 늘어날수록 커지는 비용

원문의 다섯 번째 경험은 스킬이 많아지면 매 세션 비용도 늘어난다는 것이다. 저자는 스킬 설명 전문과 스킬 약 50개, 에이전트 약 20개, 도구 약 60개의 목록이 컨텍스트에 들어왔다고 서술하고, 에이전트 오케스트레이션 플러그인 두 개를 끄고 기본 설정으로 돌아왔다고 적는다. 플러그인 이름은 원문에 적혀 있지 않다. 쓰지 않는 스킬이 많은 카탈로그는 그 자체로 비용이라는 것이 저자의 결론이다.

공식 문서를 대조하면 비용의 정체가 더 정확해진다. 스킬 작성 모범 사례는 시작할 때 모든 스킬의 이름과 설명만 미리 로드되고, SKILL.md는 스킬이 관련될 때 읽힌다고 한다. Claude Code 문서도 설명은 항상 컨텍스트에 있고 전체 스킬은 호출될 때 로드되며, 스킬 본문은 쓸 때만 로드되므로 긴 참고 자료가 필요해지기 전까지 비용이 거의 없다고 적는다. 즉 쓰지 않는 스킬이 차지하는 것은 본문이 아니라 설명이다. 그리고 설명 부분도 목록에서 1,536자에서 잘린다.

  • 상시 비용 — 이름과 설명(메타데이터). 스킬 수에 비례해 늘어난다.
  • 호출 시 비용 — SKILL.md 본문. 호출될 때만 로드되며, 500줄 권고는 이 비용을 겨냥한다.
  • 저자 수치의 해석 — 원문은 스킬 약 50개, 에이전트 약 20개, 도구 약 60개를 따로 센다. 50이 스킬의 수이므로 스킬 목록만 보아도 약 50개가 매 세션 컨텍스트에 들어왔다는 서술이다. 에이전트와 도구 목록, 도구마다 붙는 안내문이 더해진 것은 별개의 비용이다.
  • 줄이는 방법 — 설명을 짧고 겹치지 않게 쓰고, 자동 호출이 필요 없는 스킬에는 disable-model-invocation: true를 두는 선택이 있다. 공식 스킬 문서의 표는 이 경우를 「Description not in context, full skill loads when invoked」, 곧 설명이 컨텍스트에 없다고 적고, 문서는 이 설정을 스킬을 Claude의 컨텍스트에서 완전히 제거하는 방법(removes the skill from Claude's context entirely)이라고 설명한다. 대신 Claude가 스스로 호출하지 못하고 사용자가 직접 호출해야 한다.

이 표에서 공식 문서가 직접 말하는 것은 분리의 시점이 아니라 분리한 뒤의 품질이다. 모범 사례는 광범위한 문서를 쓰기 전에 평가를 먼저 만들라고 하며, 스킬 없이 대표 작업을 돌려 실패를 기록하고 그 공백을 메울 최소한의 지시를 쓰라는 순서를 제시한다. 평가는 최소 세 개, 사용할 모든 모델로 시험하라는 점검 항목도 있다. 원문의 맺음도 방향이 같다. 성공 지표는 스킬의 개수가 아니라 같은 실수가 줄었는지, 필요한 때 정확히 호출되는지에 있다는 취지다.

  • 표의 신호는 모두 현재 상태를 묻는 질문이다. 반복하고 있는가, 고정 순서가 있는가, 완료를 판정할 수 있는가 하는 식이다.
  • 분리한 뒤에는 같은 실수가 줄었는지와 호출이 정확한지를 지표로 삼는다는 것이 원문의 기준이다.
  • 평가를 먼저 만드는 순서는 모범 사례의 권고이며, 원문의 여섯 질문은 이 평가 이전의 분리 판단에 해당한다.

확인하지 못한 것

  • 원문의 모든 문장. 조회는 장별 질의 추출이어서 원문 전체를 단어 단위로 대조하지 않았고, 맺음 문장은 요약 수준으로만 확인했다.
  • 원문 작성자의 사용자명. 원문 페이지에서는 「Stock Engineer」 표기만 확인했다.
  • assets 폴더에 대한 공식 문서의 서술. 조회한 발췌에는 reference.md·examples.md·scripts/만 있었다.
  • disable-model-invocation: true로 저자의 약 50개 스킬 목록을 실제로 얼마나 줄일 수 있는지. 원문에는 그 시도가 없다.
  • 저자가 측정한 50·20·60이라는 목록 수와 어떤 플러그인을 껐는지. 플러그인 이름은 원문에도 없다.
  • 파이프라인 스킬이 도구 스킬을 어떻게 호출하는지의 구현. 원문에 서술이 없다.
  • 원문이 말한 「실무에서 쌓은 경험」의 재현 가능성. 직접 실행한 결과는 싣지 않았다.
