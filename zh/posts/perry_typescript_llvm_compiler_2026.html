Perry - 将TypeScript直接编译为LLVM机器码的原生编译器

无需转译、无需JIT，把TypeScript直接编译成原生二进制

2026年6月9日 IT/技术

引言: TypeScript真的是一门「慢语言」吗

如果你曾发布过用TypeScript写的CLI工具，一定记得某种不便。哪怕只是打印一行问候的程序，也得拖着几十MB的Node.js运行时；进程一启动，V8引擎便苏醒过来，开始解释并逐步优化你的代码。当我们说「TypeScript慢」时，真正慢的并非类型系统，而是它的执行模型。类型在编译结束后被抹去，剩下的JavaScript要在庞大的虚拟机上被再解释一遍。

2026年6月，在GeekNews(news.hada.io)引发热议的Perry正面颠覆了这一前提。Perry既不把TypeScript转译为JavaScript，也不让它跑在V8这类重型JIT运行时上，而是经由LLVM直接编译为原生机器码。据项目介绍，Perry用Rust编写，解析用SWC、代码生成用LLVM，产出无需Node.js、Electron或浏览器引擎即可运行的单一可执行文件。本文将逐步拆解它的工作原理，以及为何它在技术上引人入胜。

1. 传统TypeScript执行的三段结构

要理解Perry解决了什么，先要准确描绘「过去是怎么执行的」。传统的TypeScript执行大致经过三个阶段。

TypeScript源码 (.ts)
   │   (1) 类型检查 + 转译 (tsc / swc / esbuild)
   ▼
JavaScript源码 (.js)   ← 类型信息在此被全部抹去
   │   (2) 解析 + 生成字节码 (V8 / JavaScriptCore)
   ▼
字节码解释器执行
   │   (3) 检测热点代码 → JIT编译 → 机器码
   ▼
原生机器码 (运行时才生成)

这里产生两种成本。第一是类型信息的丢失。在第(1)步，TypeScript的静态类型只用于校验，随后从产出的JavaScript中被完全抹去。结果是第(2)(3)步的引擎不得不把每个值都假设为「类型未知的动态值」再出发。第二是JIT的预热。V8起初用解释器缓慢运行，观察到经常执行的代码后才将其编译为机器码。启动慢，达到峰值速度需要时间，而这一过程本身就消耗内存和CPU。

对浏览器这种「无法预先得知代码」的环境而言，这套模型是合理的。但我们自己编写并发布的CLI或服务器，在运行前代码就已全部确定。那么，何必把优化推迟到运行时呢?正是这一问题，构成了AOT编译的出发点。

2. AOT 对 JIT - 移动优化的时点

JIT(即时编译)与AOT(提前编译)的差别可凝练成一句话:何时生成机器码。

维度 JIT (V8/Node.js) AOT (Perry)
生成机器码的时点 运行中(运行时) 运行前(构建时)
启动速度 需预热，较慢 即时(接近0ms)
运行时依赖 需引擎+运行时 单一二进制，无依赖
优化信息来源 运行中观测到的类型 编译期的静态类型
动态代码(eval) 天然支持 结构上困难

JIT的强项在于「看着实际流动的类型」来优化。而AOT虽看不到执行，却也无需顾虑编译速度。构建只发生一次，运行却重复无数次，因此可以像C++和Rust那样尽情施加重型静态分析与激进优化。这正是Perry的着力点:既然TypeScript本就携带丰富的静态类型，那就别丢掉它，把它当作编译期优化的燃料。

JIT说:「我会在运行中弄清类型。」AOT说:「我已经知道类型，所以提前优化。」对TypeScript这类显式标注类型的语言而言，后者是自然的选择。

3. 什么是LLVM，为何要用它

Perry的代码生成后端是LLVM。一句话概括，LLVM是一座夹在众多语言前端与众多CPU后端之间、负责强力优化的业界标准编译器基座。Clang(C/C++)、Rust、Swift都运行在它之上。

LLVM的核心是名为LLVM IR的中间表示。语言前端(在Perry这里就是TypeScript)只需把源码降低(lower)为LLVM IR，之后的内联、常量传播、循环向量化、死代码消除等数十种优化通道，以及面向x86、ARM、WebAssembly等多种目标的机器码生成，都由LLVM接手。打造新语言时无需从零编写优化器和代码生成器，而是站在一个久经检验的后端之上。

有意思的是，Perry并非一开始就用LLVM。据项目博客，它最初以Cranelift(WebAssembly阵营常用的快速单层编译器)为后端，后迁移到LLVM。原因有二:其一，Cranelift刻意是一个「编译得快」的单层优化器，对于以运行性能为首要目标的AOT编译器而言，这是错误的取舍;其二，LLVM的目标支持面更广，例如面向Apple Watch的arm64_32，而Cranelift缺乏支持。

要点
选择LLVM，意味着选了「哪怕更慢，也要优化得更深」的一边。以构建略慢为代价，可执行文件获得了C、Rust所享有的优化水准。

4. Perry的编译管线

把Perry将.ts文件变成可执行文件的过程按项目说明整理如下。

TypeScript源码
   │   用SWC解析 → AST
   ▼
AST → 降低为HIR(高层IR) + 类型推断
   │   IR变换 / 优化通道
   ▼
生成LLVM IR (codegen)
   │   LLVM优化 + 目标机器码生成
   ▼
与运行时库链接 → 单一原生可执行文件

逐段来看。SWC是一款用Rust编写的超高速TypeScript/JavaScript解析器，Perry以它为前端，把源码变成抽象语法树(AST)。随后把AST降低为高层中间表示(HIR)并推断类型，经过若干变换通道后生成LLVM IR。最后与Perry以原生方式实现的运行时库链接，产出一个免依赖的二进制文件。据项目介绍，「hello world」级别的产物约为数百KB，而大量使用标准库的应用可膨胀到数十MB。

5. 借助类型信息的优化

Perry真正的妙处源于「不丢弃类型」。一般JavaScript引擎需在运行时费力推断的信息，TypeScript在编译期就已告知。据介绍，Perry用这些信息做如下优化。

  • NaN-boxing: 一种无需指针或装箱即可表示数值的技巧，降低数值运算的开销。
  • 内联对象分配: 通过bump分配器对对象做内联分配，降低内存访问成本。
  • i32循环计数器: 在以整数取值的循环中，使用32位整数计数器而非通用浮点，让循环更快。
  • 形状缓存(shape cache)对象: 缓存对象的形状，免去动态查找而直接访问字段。
  • fast-math标志: 允许浮点运算使用fast-math，拓宽循环向量化的空间。

这些优化的共同点是:它们都只在「知道值的类型」这一前提下才成立。JavaScript引擎在运行之前无法确定x + y是整数相加还是字符串拼接，但在TypeScript中若声明了x: number，编译器便可直接降低为整数/浮点指令。静态类型本身就成了优化信息。

这种「借助类型的编译优化」思路，与系统语言中的无损压缩和内存分配设计一脉相通。正如压缩越了解数据结构就越能缩小，编译器越了解值的结构也越能精简。相关脉络可参阅另文用Rust重写的Zstandard与mimalloc高性能分配器。

6.「迁到LLVM反而慢了70倍」的悖论

Perry的后端迁移期有一段发人深省的轶事。据项目博客，从Cranelift首次切换到LLVM时，部分基准测试反而慢了70倍。迁到更强的后端，怎么反倒慢了?

原因在于「边界」。早期的LLVM版本把大多数运算都走不透明的运行时辅助函数调用，在LLVM看来，那些调用内部是无法窥探的黑盒。跨越函数边界的优化(内联、常量传播)被堵住，优化器再强也无事可做。Perry团队解释道，只有在刻意内联热点路径、拆除这些边界之后，才真正释放出LLVM的威力。

仅仅接上一个强力优化器并不会变快。必须把代码展开到优化器「看得见」，它的力量才会生效。这是一切编译器设计的通则。

7. 那到底快了多少 - 基准测试的语境

完成优化后，Perry报告了有意义的性能提升。在项目公布的某个版本的基准里，相对Node.js引用了如下结果。

  • 递归阶乘:约快24.6倍
  • 方法调用:约快11倍
  • 循环开销:约快4.4倍
  • 数值密集型运算:约快3.5倍

不过这些数字要谨慎解读。上述项目大多是类型明确、循环密集的微基准，恰是AOT与静态类型最占优的领域。真实应用混杂着I/O等待、内存分配与库调用，实际感受到的差距可能更小。此外V8是历经多年打磨的世界顶级JIT，在充满动态模式的代码上依旧强劲。把它理解为「在静态类型与AOT占优的工作负载上差距显著」，比「Perry总是快N倍」更准确。

8. 既有的尝试 - Perry并非第一个

把TypeScript/JavaScript编译到原生或WebAssembly的尝试，并非始于Perry。理清谱系，Perry的位置便一目了然。

8.1 AssemblyScript

AssemblyScript把TypeScript的子集(subset)编译为WebAssembly。语法与TypeScript相似，实则更接近一门独立语言:它不接受任意TypeScript，需遵循显式整数类型等自有规则。其后端不是LLVM，而是Binaryen(WebAssembly工具链)。这是一条「严格约束类型以逼近原生」的路线。

8.2 Static Hermes

Meta(Facebook)的Static Hermes是面向React Native的Hermes引擎的下一代版本，目标是把带有TypeScript/Flow类型注解、「类型健全」的JavaScript在构建时AOT编译为原生代码，借静态类型减少JIT的猜测，从而更快更小。但据公开资料，其TypeScript支持仍是实验性且不完整。它与Perry的理念(以类型驱动AOT)最为接近，不过Static Hermes有一个明确的舞台:React Native生态。

8.3 Porffor

由Oliver Medhurst打造的Porffor，是一款把JavaScript/TypeScript以AOT方式编译为WebAssembly和原生二进制的实验性引擎。由于它编译代码本身而非打包解释器，据介绍其产物相比既有「JS→Wasm」方案小得多(引用了二进制最多小1000倍的案例)且更快。Porffor的目标更宽广，追求的是JavaScript整体的标准符合性(Test262)，而不仅限于TypeScript。

项目 输入 后端 主要目标
Perry TypeScript LLVM 原生二进制
AssemblyScript TS子集 Binaryen WebAssembly
Static Hermes 带类型的JS/TS 自研+LLVM系 原生(RN)
Porffor JS/TS 自研→Wasm/原生 Wasm·原生

Perry的区别在于「接收平常写法的TypeScript，经LLVM直接产出原生可执行文件」的直接性，以及同时提供用Rust重新实现的标准库与包。

9. 标准库与npm兼容的现实

对原生编译器而言，最棘手的不是语言，而是生态。TypeScript的力量源自数十万个npm包，而它们大多以Node.js运行时API(fs、http、net等)为前提。由于Perry不携带V8/Node，就必须自行重新实现这些API。

据项目介绍，Perry配备了用Rust编写的高性能标准库，原生提供console、fs、path、process、JSON、Math、Date、crypto、Buffer、Map/Set、worker_threads等。此外还包含fastify、axios、PostgreSQL、MySQL、Redis、bcrypt、JWT等热门包的可直接替换的原生实现。也就是说，并非「任意npm包都能原样运行」，而是在Perry已原生重新实现的范围内运行的模型。

// 据介绍的概念示例:无需独立运行时、即可构建为单一二进制的HTTP服务器
import { createServer } from "http";

const server = createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain" });
  res.end("Hello from a native TypeScript binary");
});

server.listen(8080, () => {
  console.log("listening on :8080"); // 无需Node.js即可运行的二进制
});

10. 局限 - 动态特性与生态之墙

为求平衡，必须明确指出局限。AOT原生编译并非免费，它与JavaScript最动态的部分存在本质冲突。

  • 动态求值: 在运行时把字符串当作代码执行的eval与new Function，与AOT「运行前编译全部代码」的前提正面相撞，这是静态编译器最难处理的领域。
  • 未支持特性: 据项目文档，装饰器目前被标注为不支持。标准的广阔角落正在被逐步补齐。
  • 生态兼容: 只有不依赖原生运行时API、或Perry已重新实现的包才能运行。要把拥有深层npm依赖树的既有大型应用原样迁移，相当困难。
  • 成熟度: 据介绍，版本处于0.5.x区间，是仍在积极开发的早期阶段。比起全面投产，更应先在合适的工作负载上做验证。

简言之，把Perry看作「在特定工作负载下让你像系统语言一样使用TypeScript的工具」，比看作「所有TypeScript应用的Node.js替代品」更准确。

11. 适合用在哪里 - 应用场景

那么Perry的长处在何处最为闪光?顺着AOT、单一二进制、即时启动这些特性，答案自然浮现。

  • CLI工具: 免依赖的单一二进制易于分发、启动即时，用户无需安装Node。
  • Serverless与边缘: 在冷启动即成本与延迟的环境里，免预热的即时启动是明确优势。
  • 嵌入式与受限环境: 小体积二进制与低内存占用，利好资源紧张的设备。
  • 性能敏感的工作负载: 在类型明确、数值运算密集的任务上，可瞄准接近原生的性能。

这也与「从Go到Rust」之类的系统语言选型讨论相通。因为当你追求更快的执行、更小的二进制与可预测的性能时，本质上就是在选择哪种语言/工具链。相关脉络在从Go到Rust的迁移指南中继续展开。

12. 结语 - TypeScript的「第二人生」

Perry抛出的讯息很清晰:TypeScript的类型并非仅是开发便利的工具，而是编译器可以利用的优化信息。与其通过转译抹去类型、再在重型JIT之上重新推断，不如把这些类型原封不动地交给LLVM、降低为原生机器码——如此一来，TypeScript便能获得接近系统语言的性能与部署便利。

当然，Perry仍处早期，动态特性与庞大npm生态这两道硬墙犹在。并非所有应用明天就能编译为原生。但与Static Hermes、Porffor、AssemblyScript一道，Perry所勾勒的大图景十分清晰:JavaScript/TypeScript那「诞生于浏览器的动态语言」身份，正通过AOT编译这条新路，扩展为「也能踏入系统领域的语言」。若你乐于使用TypeScript，这股潮流值得持续关注。
