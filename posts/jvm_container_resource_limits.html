JVM은 컨테이너 한도를 어떻게 보는가 - 쿠버네티스 Request와 Limit이 힙·GC·지연을 정하는 자리 2026

-Xmx를 limit과 같게 주면 왜 죽는지, availableProcessors 하나가 GC 스레드와 병렬도까지 정하는 경로

2026-09-02 개발/인프라

파드 스펙에 limits.memory: 1Gi 를 적으면 그 컨테이너는 실제로 그 선을 넘지 못한다. 문제는 안에서 도는 JVM 이 그 숫자를 어떻게 읽느냐다. JVM 은 한도를 준수하는 프로그램이 아니라 한도를 보고 자기 계획을 세우는 프로그램이고, 계획이 어긋나면 한도를 지키는 쪽은 커널이다. 커널이 지키는 방식은 프로세스를 죽이는 것이다.

CPU 쪽은 더 조용히 어긋난다. 평균 사용률은 낮은데 p99 만 튄다. 그 사이 JVM 안에서는 컬렉터 선택과 스레드 풀 크기가 파드 스펙의 숫자 하나를 따라 바뀌어 있다.

기준은 Java 21 의 java man page, Java 25 GC 튜닝 가이드, OpenJDK 소스와 버그 데이터베이스, 2026년 9월 기준 쿠버네티스 공식 문서다. 리눅스 컨테이너에서 직접 실행해 확인하지 못했으므로 명령 출력은 붙이지 않았다. 본문의 기본값과 동작은 전부 위 문서에서 확인한 것이다.

계기 - 한도를 걸었는데도 어긋나는 자리

2026년 9월 초 국내 개발자 커뮤니티에 쿠버네티스에서 자바 JVM 의 CPU·메모리 Request 와 Limit 을 다룬 글이 소개됐다. 요지는 하나였다. 컨테이너 안의 자바 프로세스에는 메모리 경계가 둘 있다. 힙 경계와 컨테이너 경계인데, 둘을 같은 것으로 취급하는 순간 사고가 난다.

같은 구조가 CPU 쪽에도 있다. 파드 스펙의 CPU 숫자는 스케줄러에게 하는 말이면서 동시에 JVM 이 자기 병렬도를 계산하는 입력인데, 대시보드에는 한쪽만 나온다. 컨테이너가 왜 OOMKilled 로 끝났는지의 일반적인 진단은 따로 쓴 글에, 장애 중에 관제 화면이 답을 주지 못하는 이유는 그 글에 있다. 여기서는 JVM 고유의 문제만 다룬다.

JVM 은 원래 호스트를 봤다

뿌리는 JVM 이 자기 힙 크기를 스스로 정한다는 데 있다. Oracle 의 GC 튜닝 가이드가 적어 둔 기본 선택은 이렇다. 초기 힙은 물리 메모리의 64분의 1, 최대 힙은 4분의 1, 컬렉터는 서버급 머신에서 G1 이고 그 밖에는 Serial 이다. 서버급의 정의도 각주로 붙어 있다. 프로세서 2개 이상이면서 물리 메모리 1792MB 이상일 때다.

여기서 「물리 메모리」가 문제다. 컨테이너 인식이 없던 시절의 JVM 에게 그것은 호스트 전체였다. 64GB 노드에 limit 512Mi 짜리 파드를 띄우면 그 안의 JVM 은 최대 힙을 16GB 로 계획했다. 계획이 틀렸으니 GC 는 여유가 많다고 보고 수거를 미루고, 그 사이 컨테이너는 512Mi 를 넘어 커널에게 죽는다.

고쳐진 시점은 명확하다. JDK 10 릴리스 노트의 JDK-8146115 항목이다. JVM 이 컨테이너 안에서 돌고 있음을 인지하도록 수정됐고, 운영체제에 묻는 대신 컨테이너별 설정 정보를 추출한다. 추출하는 것은 할당된 CPU 수와 총 메모리다. 리눅스에서만 동작하며 기본으로 켜져 있고 -XX:-UseContainerSupport 로 끌 수 있다.

  • 같은 변경에서 -XX:ActiveProcessorCount 가 추가됐다. 릴리스 노트는 이 값이 JVM 의 다른 모든 CPU 자동 탐지 로직을 덮어쓴다고 적는다
  • 같은 자리의 JDK-8186248 로 InitialRAMPercentage·MaxRAMPercentage·MinRAMPercentage 가 추가됐다. 이전의 Fraction 형태를 대체한 것이다
  • 이 항목은 Oracle JDK 8u191 릴리스 노트에도 같은 내용으로 실려 있다. JDK 8 계열도 8u191 이상이면 컨테이너 인식이 들어 있다
  • 바꿔 말하면 8u190 이하와 JDK 9 에는 없다. 그런 이미지를 쓰고 있다면 옛날 방식대로 -Xmx 를 손으로 못 박아야 한다

컨테이너 인식이 실제로 읽는 값

메모리 쪽 경로는 -XX:MaxRAM 문서에 그대로 있다. 기본값은 「JVM 프로세스가 쓸 수 있는 최대 메모리 또는 128GB 중 작은 쪽」이고, 다음 문장이 핵심이다. 그 최대 메모리란 머신의 물리 메모리와 환경(예: 컨테이너)이 건 제약 중 작은 쪽이다. 컨테이너 memory limit 이 여기로 들어오고, 그 위에 비율 플래그가 얹힌다.

CPU 쪽 알고리즘은 man page 가 아니라 OpenJDK 소스 주석에 있다. cgroupSubsystem_linux.cpp 의 active_processor_count 설명은 세 줄이다. sched_getaffinity 로 쓸 수 있는 CPU 수를 구한다. quota 가 지정돼 있으면 quota 를 period 로 나눈다. 그리고 나눗셈 결과는 모두 다음 정수로 올림한다. 결과는 활성 프로세서 수를 넘지 않는다.

올림이 실제로는 크다. CPU limit 이 500m 이면 0.5 가 올라가 1 이고, 1500m 이면 2 다. 1 CPU 미만을 줘도 JVM 은 최소 1개로 본다. 반대로 2100m 같은 값은 3이 되어, 실제로 쓸 수 있는 것보다 많은 스레드를 만들게 한다.

놓치기 쉬운 것은 limit 이 없을 때다. quota 가 없으면 위 알고리즘은 시스템의 활성 프로세서 수를 그대로 쓴다. 96코어 노드에 requests.cpu: 500m 짜리 파드만 올리면 그 JVM 은 96코어짜리 계획을 세운다.

-Xmx 대신 비율로 주는 이유

절대값과 비율의 차이는 취향이 아니라 관리 지점의 개수다. -Xmx2g 는 파드 스펙과 따로 사는 숫자다. limit 을 3Gi 로 올리면서 JVM 인자를 안 고치면 늘린 메모리가 놀고, 1Gi 로 줄이면서 안 고치면 그 파드는 배포 직후부터 죽는다. 비율로 주면 고칠 곳이 한 군데다.

플래그무엇을 정하는가Java 21 man page 기준 기본값주의
-XX:InitialRAMPercentage초기 힙1.5625 퍼센트기동 직후 힙이 아주 작다. 늘어나는 동안 GC 가 자주 돈다
-XX:MaxRAMPercentage최대 힙25 퍼센트지정하지 않으면 1Gi 컨테이너의 최대 힙이 약 256Mi 다
-XX:MinRAMPercentage작은 힙에서의 최대 힙50 퍼센트최솟값이 아니다. 문서는 「약 125MB 이하의 작은 힙」에 적용된다고 적는다
-XX:MaxRAM위 비율들의 분모사용 가능 메모리와 128GB 중 작은 쪽여기서 사용 가능 메모리가 컨테이너 limit 이다

기본값 25퍼센트가 실무에서 가장 자주 사고를 낸다. 컨테이너에 4Gi 를 줬는데 힙은 1Gi 만 잡히고 나머지 3Gi 는 아무도 쓰지 않는다. 「메모리를 늘렸는데 왜 여전히 GC 가 심한가」의 절반은 여기서 나온다. MaxRAMPercentage 는 컨테이너에서 사실상 필수 지정 항목이다.

이름 함정도 하나 있다. MinRAMPercentage 는 「최소 몇 퍼센트는 힙에 준다」가 아니라 작은 힙 구간에서의 최대 비율이다. 250Mi 짜리 사이드카 자바 프로세스에서 MaxRAMPercentage 만 만지고 왜 안 먹느냐고 하는 경우가 여기 걸린다.

resources:
  requests:
    cpu: 500m
    memory: 1Gi
  limits:
    memory: 1Gi          # 비율의 분모가 되는 값
env:
  - name: JAVA_TOOL_OPTIONS
    value: >-
      -XX:MaxRAMPercentage=70.0
      -XX:InitialRAMPercentage=70.0
      -XX:+ExitOnOutOfMemoryError

70이라는 숫자에 근거는 없다. 공식 문서 어디에도 「힙은 limit 의 몇 퍼센트」라는 권고는 없다. 계기가 된 글은 50에서 75 사이에서 시작해 검증하라고 적었고, 그 정도가 정직한 표현이다. 남은 몫이 무엇에 쓰이는지는 다음 절이 설명한다.

힙만 메모리가 아니다

이 절 하나만 가져가도 된다. -Xmx 를 컨테이너 limit 과 같게 주면 그 파드는 반드시 죽는다. 힙 밖에도 JVM 이 쓰는 메모리가 여럿 있고, 그것들은 -Xmx 에 안 들어가면서 컨테이너 사용량에는 그대로 들어가기 때문이다.

메타스페이스-XX:MaxMetaspaceSize크기가 제한되지 않음포함

표에서 눈에 띄는 것은 메타스페이스가 기본적으로 무제한이라는 점이다. 클래스를 많이 찍어 내는 프레임워크에서 이 값이 늘어나면 힙은 멀쩡한데 컨테이너만 한도에 닿는다. 다만 예약과 실제 커밋은 다르다. 표의 숫자는 상한이지 상시 점유량이 아니다.

죽는 방식이 다르다는 점이 더 중요하다. 힙이 부족하면 JVM 이 OutOfMemoryError 를 던지고 스택 트레이스와 힙 덤프가 남는다. 반면 컨테이너 한도를 넘기면 쿠버네티스 문서의 표현대로 memory limit 은 커널의 OOM kill 로 강제된다. 예외도 덤프도 없다. 같은 문서는 이 종료가 커널이 메모리 압박을 감지할 때만 일어나므로 한도를 넘긴 컨테이너가 즉시 죽지 않을 수도 있다고 덧붙인다. 같은 코드, 같은 부하인데 죽는 시점이 다른 이유다.

힙 밖이 어디로 갔는지 알아내는 JVM 내장 수단은 네이티브 메모리 추적이다. -XX:NativeMemoryTracking 의 기본값은 off 이고 summary 로 켜면 하위 시스템별 사용량을 추적한다.

# 힙 밖 메모리 내역 (추적을 켜고 뜬 프로세스에서만 유효)
jcmd 1 VM.native_memory summary

# JVM 이 컨테이너를 어떻게 인식했는지 최대치 로깅
java -Xlog:os+container=trace -XX:MaxRAMPercentage=70 -version

# 최종적으로 확정된 플래그 값 확인
java -XX:+PrintFlagsFinal -version | grep -E 'MaxHeapSize|ActiveProcessorCount'

availableProcessors 하나가 정하는 것들

Runtime.availableProcessors() 의 javadoc 은 짧다. JVM 이 사용할 수 있는 프로세서 수를 반환하고, 이 값은 실행 중에 바뀔 수 있으며, 1보다 작지 않다. 컨테이너에서 이 값은 앞 절의 올림 계산 결과다. 이 숫자 하나가 아래 것들을 연쇄로 정한다.

컬렉터 선택과 GC 스레드 수

서버급 판정 조건이 여기 걸린다. 프로세서 2개 미만이거나 메모리 1792MB 미만이면 서버급이 아니고, 기본 컬렉터는 G1 이 아니라 Serial 이 된다. CPU limit 이 500m 인 컨테이너는 프로세서 1개로 계산되므로 이 조건에 걸린다. 그 상태에서 G1 전용 튜닝 플래그를 붙여 봐야 아무 일도 일어나지 않는다.

서버급을 통과하더라도 GC 워커 수가 프로세서 수를 따라간다. 가이드는 「최대 GC 스레드 수는 힙 크기와 가용 CPU 자원에 의해 제한된다」고만 적고 산식은 밝히지 않는다. 그래도 방향은 분명하다. 프로세서를 적게 보면 GC 도 느리게 돈다.

ActiveProcessorCount 로 덮어쓰기

man page 가 이 플래그의 범위를 알려 준다. 「VM 이 가비지 컬렉션이나 ForkJoinPool 같은 작업에 쓸 스레드 풀 크기를 계산할 때 사용하는 CPU 수를 덮어쓴다」. 「UseContainerSupport 가 켜져 있지 않아도 존중된다」는 단서와, 여러 자바 프로세스를 컨테이너에서 돌릴 때 CPU 자원을 나누는 데 유용하다는 용도까지 적혀 있다.

  • 이 플래그는 JVM 이 보는 값만 바꾼다. cgroup 의 quota 는 그대로다. 1로 낮춰도 컨테이너는 여전히 limit 만큼 쓸 수 있다
  • 그래서 낮게 잡으면 GC 워커와 병렬 처리가 줄어드는데 정작 스로틀링은 줄지 않는다. 스로틀링 해결책이 아니다
  • 반대로 높게 잡으면 스레드만 늘고 quota 는 그대로라 스로틀링이 심해진다. 「코어를 더 준 셈 치자」는 성립하지 않는다
  • 제대로 쓰이는 자리는 한 파드에 자바 프로세스가 둘 이상일 때다. 각자가 파드 전체를 자기 것으로 계산하는 것을 막는다

병렬 스트림도 같은 값에 묶인다. ForkJoinPool 의 javadoc 은 인자 없는 생성자가 Runtime.availableProcessors() 와 같은 병렬도로 풀을 만든다고 적고, 공용 풀의 병렬도는 java.util.concurrent.ForkJoinPool.common.parallelism 속성으로 지정할 수 있다고 안내한다. CPU limit 을 바꾸는 일은 애플리케이션 코드의 병렬도를 바꾸는 일이기도 하다.

CPU Limit 은 왜 지연을 만드는가

쿠버네티스 문서의 문장이 명확하다. cpu limit 은 CPU 스로틀링으로 강제되며, 컨테이너가 limit 에 가까워지면 커널이 그만큼으로 CPU 접근을 제한한다. 커널이 강제하는 하드 리밋이다. 메모리처럼 「넘으면 죽는다」가 아니라 「넘으려 하면 멈춘다」다.

멈추는 단위가 핵심이다. kubelet 은 기본적으로 CFS quota 로 파드 CPU limit 을 강제하고, 주기값을 정하는 옵션 --cpu-cfs-quota-period 의 기본값은 100ms 다. 스로틀링은 초 단위로 매끄럽게 일어나지 않고 100ms 짜리 창 안에서 할당량을 다 쓰면 그 창이 끝날 때까지 멈추는 방식으로 일어난다.

여기서 평균의 함정이 나온다. CPU limit 이 1이고 스레드가 4개면 100ms 분량이 25ms 만에 소진되고, 남은 75ms 동안 그 컨테이너의 모든 스레드가 멈춘다. 1초로 평균 내면 사용률은 100퍼센트 미만이라 그래프는 평온하다. 그 1초 안에 최대 75ms 짜리 정지가 여러 번 들어 있는데도 그렇다. 평균 사용률이 낮은데 p99 만 튀는 현상의 정체가 대개 이것이다.

GC 와 겹치면 더 나빠진다. stop-the-world 구간에서 할당량이 소진되면 GC 스레드도 같이 멈추고, 다음 주기가 열려야 재개된다. 짧았을 정지가 주기 경계까지 늘어난다. GC 로그의 정지 시간과 스로틀 지표를 같이 놓고 봐야 하는 이유다.

CPU limit 을 걸 것인가 말 것인가

이 주제는 결론이 갈린다. 양쪽이 다른 것을 최적화하고 있고, 양쪽 다 문서로 뒷받침되는 근거가 있다. 나란히 두는 편이 정확하다.

걸지 말자는 쪽근거걸자는 쪽근거
스로틀링이 실제 지연을 만든다커널이 강제하는 하드 리밋이고 주기 기본값이 100ms 다Guaranteed QoS 의 조건이다모든 컨테이너의 CPU limit 이 request 와 같아야 Guaranteed 가 된다
CPU 가 모자라도 파드는 죽지 않는다축출 신호는 memory·파일시스템·pid 뿐이고 CPU 가 없다축출 순서에서 뒤로 밀린다축출은 BestEffort, Burstable, Guaranteed 순서다
노드가 한가하면 남는 CPU 를 쓸 수 있다자원이 남으면 request 이상을 쓰는 것이 허용된다CPU 고정을 쓰려면 필수다static 정책의 전용 CPU 는 Guaranteed 파드 + 정수 request 에만 배정된다

정리하면 지연이 중요한 소수 서비스와 밀도가 중요한 다수 배치 작업이 다른 답을 낸다. 앞쪽은 스로틀링을 피하려 limit 을 빼거나 크게 잡고, 뒤쪽은 예측 가능성과 축출 순위를 위해 건다. 판단 기준은 취향이 아니라 지표다. 스로틀 지표가 실제로 올라가고 있는가를 먼저 본다.

한 가지는 분명히 구분해야 한다. 메모리 limit 을 빼는 것은 CPU limit 을 빼는 것과 같은 성질의 결정이 아니다. CPU 는 모자라면 느려질 뿐이지만 메모리는 압축되지 않는다. 메모리 limit 이 없으면 그 파드는 노드 전체를 위험에 빠뜨리고, JVM 은 노드 메모리를 기준으로 힙을 계획한다.

Request 와 Limit 은 다른 일을 한다

쿠버네티스 문서의 정의는 짧다. request 를 지정하면 kube-scheduler 가 그 정보로 파드를 어느 노드에 놓을지 정한다. limit 을 지정하면 kubelet 이 그것을 강제해서 실행 중인 컨테이너가 그 이상 쓰지 못하게 한다. 하나는 배치 단계의 숫자, 다른 하나는 실행 단계의 숫자다.

JVM 관점에서 결정적인 것은 JVM 이 request 를 보지 않는다는 점이다. MaxRAM 이 참조하는 것은 「환경이 건 제약」, 즉 cgroup 의 limit 이다. request 만 크게 잡고 limit 을 비워 둔 파드는 스케줄러 눈에 여유 있게 배치된 파드인데, 그 안의 JVM 은 있지도 않은 메모리를 전제로 움직인다.

QoS 클래스조건축출 순서JVM 관점에서의 뜻
Guaranteed모든 컨테이너가 CPU·메모리의 limit 과 request 를 갖고 두 값이 같다가장 늦게 축출된다힙 비율의 분모가 확정적이다. 어긋날 여지가 가장 적다
BurstableGuaranteed 조건을 못 채우면서 컨테이너 중 하나라도 request 나 limit 이 있다BestEffort 다음limit 이 있으면 그것이 분모다. 없으면 노드 메모리가 분모다
BestEffort어떤 컨테이너에도 CPU·메모리의 request 와 limit 이 없다가장 먼저 축출된다JVM 이 노드 전체를 자기 것으로 계산한다. 자바에는 사실상 금지

문서가 덧붙이는 조건도 알아 둘 만하다. 자원 압박으로 인한 축출일 때 후보가 되는 것은 request 를 초과해 쓰고 있는 파드다. request 를 현실적으로 잡아 두는 일이 단순한 서류 작업이 아닌 이유다.

JIT 워밍업이 readiness 를 무너뜨리는 자리

HotSpot 은 기본으로 C1 과 C2 를 함께 쓰는 계층 컴파일러로 뜬다. 컴파일 자체가 CPU 를 쓴다. 그래서 자바 애플리케이션의 CPU 사용량은 기동 직후가 가장 높고 정상 상태에서 내려간다. 그런데 CPU limit 은 대개 정상 상태를 기준으로 잡힌다. 가장 CPU 가 필요한 구간이 가장 심하게 스로틀링된다.

다음은 정해진 수순이다. 기동이 늦어지면 readiness probe 가 실패하고, 문서의 표현대로 kubelet 이 컨테이너를 준비되지 않음으로 표시하면 엔드포인트 컨트롤러가 그 파드의 IP 를 매칭되는 서비스 엔드포인트에서 제거한다. 여기까지는 정상 동작이다. 문제는 liveness probe 까지 같은 임계값으로 걸어 둔 경우다. liveness 가 실패하면 재시작 정책에 따라 컨테이너가 죽고, 다시 기동하며 같은 구간을 또 지나간다. 재시작 루프가 만들어진다.

공식 처방은 startup probe 다. 문서는 이 프로브가 느리게 시작하는 컨테이너를 보호하며 liveness·readiness 를 건드리지 않고 기동 전용 성공 기준을 정의하게 해 준다고 적는다. 권장 형태까지 안내한다. liveness 와 같은 검사를 쓰되 실패 임계값만 높게 잡는 것이다. liveness 자체를 헐겁게 풀면 진짜 고장을 못 잡는다.

  • 기동 구간에만 CPU 를 더 주는 것은 표준 request·limit 만으로는 되지 않는다. startup probe 로 시간을 벌거나 limit 을 올리는 쪽으로 간다
  • limit 을 올리기 싫다면 클래스 데이터 공유나 사전 컴파일 같은 기동 최적화가 다음 선택지다. 그 효과는 이 글에서 확인하지 않았다
  • 기동이 느려 첫 요청이 느린 것과 스로틀링 때문에 상시 p99 가 높은 것은 다른 문제다. 기동 구간과 정상 구간을 나눠 보지 않으면 섞인다

무엇을 보고 정하는가

가장 흔한 실수는 숫자 하나로 결정하는 것이다. 힙 사용량 그래프 하나로 limit 을 정하거나 CPU 사용률 하나로 스로틀링 여부를 판단한다. 아래 다섯 개는 서로 다른 것을 말한다.

  • GC 직후의 힙 사용량 — 힙 크기 산정의 근거다. 톱니 그래프의 꼭대기는 「필요한 크기」가 아니라 「수거 직전의 쓰레기 포함 크기」다
  • 커밋된 힙 — JVM 이 실제로 확보해 둔 크기. 컬렉터에 따라 쓰지 않는 부분을 운영체제에 돌려주기도 한다
  • 프로세스 RSS — 물리 메모리에 올라와 있는 양. 여기서 힙을 빼면 힙 밖이 얼마인지 대략 보인다
  • 컨테이너 메모리 사용량 — cgroup 이 보는 값이고 OOM 판단의 기준이다. 페이지 캐시가 섞인다
  • CPU 스로틀 지표 — 사용률이 아니라 스로틀된 주기 수와 시간을 본다. 사용률은 스로틀링을 숨긴다

순서는 단순하다. limit 을 정하고, 비율로 힙을 주고, 실제 트래픽에서 위 다섯을 같이 보고, 되돌아가 고친다. 특히 합성 부하만으로는 힙 밖 메모리가 잘 드러나지 않는다. 클래스 로딩과 코드 캐시는 실제 코드 경로가 다양하게 밟혀야 늘어난다.

흔한 실패 다섯 가지

같은 실패가 반복되는 이유는 증상이 원인과 멀리 떨어져 나타나기 때문이다.

실패실제로 일어나는 일증상무엇을 보나

네 번째에는 반대 방향의 함정도 있다. -XX:ActiveProcessorCount 로 프로세서 수만 올려 잡으면 컬렉터 선택은 바뀌지만 quota 는 그대로다. 스레드가 늘어난 만큼 스로틀링만 심해진다. 컬렉터를 바꾸고 싶으면 프로세서 수를 속이는 대신 -XX:+UseG1GC 처럼 직접 지정하는 편이 정직하다.

어느 버전을 기준으로 한 이야기인가

이 영역은 버전에 따라 동작이 실제로 다르다. 오래된 글을 그대로 옮겨 적용했다가 어긋나는 대표적인 자리라서 기준을 밝혀 둔다.

  • JDK 8u190 이하와 JDK 9 — 컨테이너 인식이 없다. 호스트 기준으로 힙과 프로세서 수를 정하므로 -Xmx 를 손으로 못 박는 것 외에 방법이 없다
  • JDK 8u191 이상과 JDK 10 이상 — UseContainerSupport 가 기본으로 켜져 있고 RAMPercentage 세 플래그와 ActiveProcessorCount 를 쓸 수 있다
  • JDK 19 — OpenJDK 버그 JDK-8281181 「Do not use CPU Shares to compute active processor count」 가 이 버전에 반영됐다. 그 전에는 quota 가 없을 때 cpu shares 로 프로세서 수를 계산했고, 쿠버네티스에서 cpu shares 는 CPU request 에서 나온다. 옛 JDK 에서는 request 가 JVM 병렬도에 영향을 줬다는 뜻이다
  • 본문의 플래그 기본값 — Java 21 의 java man page 기준이다. 컬렉터 선택과 서버급 판정은 Java 25 GC 튜닝 가이드 기준이다
  • 쿠버네티스 쪽 — 2026년 9월 기준 공식 문서다. cgroup v1 과 v2 의 차이는 다루지 않았다

세 번째가 특히 성가시다. 런타임을 올리면서 CPU 설정을 그대로 뒀는데 병렬도가 달라지는 일이 생길 수 있다. 플래그를 그대로 두는 것 자체가 변경일 수 있다는 뜻이다.

정리

뼈대는 한 문장이다. 파드 스펙의 숫자는 컨테이너를 제약하는 값이면서 동시에 JVM 이 자기 계획을 세우는 입력이다. 메모리 limit 은 힙 비율의 분모가 되고, CPU limit 은 프로세서 수가 되어 컬렉터 선택과 스레드 풀 크기를 정한다.

실무적으로 남는 것은 셋이다. -Xmx 를 limit 과 같게 두지 않는다. 힙 밖 몫을 남기지 않으면 커널이 조용히 죽인다. 비율로 준다. 관리할 숫자가 하나로 줄고 기본값 25퍼센트는 대개 너무 작다. CPU limit 은 지연 예산과 함께 정한다. 100ms 주기 안의 정지는 초 단위 평균에 나타나지 않는다. 그리고 어떤 비율도 남이 정해 줄 수 없다. 힙 밖 메모리는 프레임워크와 스레드 수에 따라 서비스마다 다르다. 측정해서 정하고, 런타임을 올릴 때마다 다시 본다.

확인하지 못한 것

  • 리눅스 컨테이너에서 직접 실행해 검증하지 못했다. 본문의 명령은 문서에 근거해 적은 것이고, 실행 출력은 하나도 붙이지 않았다
  • ForkJoinPool 공용 풀의 기본 병렬도 산식은 javadoc 에 없다. 인자 없는 생성자가 availableProcessors() 와 같다는 것만 확인했다
  • -XX:ParallelGCThreads 와 -XX:ConcGCThreads 의 기본 산식도 man page 에 없다. 가이드는 「힙 크기와 가용 CPU 자원에 의해 제한된다」고만 적는다
  • JDK-8281181 의 백포트 여부는 확인하지 못했다. 버그 데이터베이스에 기록된 수정 버전은 19 하나였다
  • cgroup v1 과 v2 의 차이가 위 계산에 미치는 영향은 다루지 않았다. 파일 이름과 단위가 다르다
  • 파드 자원을 재시작 없이 바꾸는 기능과, 그때 JVM 이 값을 다시 읽는지는 확인 범위 밖이다
  • 기동 최적화 기법이 스로틀링 구간에서 얼마나 도움이 되는지는 측정하지 않았다
