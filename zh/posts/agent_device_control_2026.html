引言：最后一格一直是人的活

智能体读完工单、改完代码、连构建都跑完了。可是到底是不是长成那样，最后还是人拿起手机去看。打开应用、翻三屏、点按钮、发现这里文字被截断了、退回来。自动化的最后一格总是断在这里。

声称要补上这一格的工具出现了。callstack公开的agent-device是一个CLI，让编码智能体直接打开运行中的应用、读取界面结构、点击、输入，并把结果留成证据。除了iOS和安卓，它还把tvOS、Android TV、macOS、Linux和网页收进同一套接口。

先把判断写在前面。看屏幕再点击的方式，用于「核对」已经够用，用于「执行」还早。而分开这两者的标准不是模型有多聪明，是出错之后能不能撤回。看错截图点到别的标签页，退回去就行；同样的错误落在支付确认按钮上，就没有可退的地方。

本文要画的就是这条线：循环实际怎么转、在哪里崩、什么必须从工具表面拿掉，以及核验密集的应用环境又额外加了什么。方向相反的那件事，在手机上写代码，在用Codex手机版完整开发并发布应用里单独讲过。

1. 设备操控循环的五个步骤

操控设备的智能体最终都在转同一个轮子。工具之间叫法不同，但步骤是五个。

  1. 获取状态。此刻屏幕上有什么，截图或结构转储皆可
  2. 指定目标。要动其中哪个元素
  3. 发送操作。点击、输入、滚动、手势送到设备
  4. 等待稳定。等到画面停止移动
  5. 校验结果。预期的变化是否真的发生

agent-device的命令与这些步骤一一对应。open AppName --platform ios开会话，snapshot抓无障碍树，press @ref点元素，fill @ref输入文本，screenshot ./path.png留证据，close结束。值得盯住的是--settle选项。把「操作之后等界面沉下来」这一步做成显式命令表面，说明跳过它在实际使用中崩得足够频繁。

1.1 每个平台的通道不同

这类工具不会发明新通道，走的是各操作系统早已开好的门。

  • iOS与tvOS — XCTest，架在苹果的UI测试基础之上
  • 安卓与Android TV — ADB，直接使用开发者通道
  • Linux桌面 — AT-SPI，无障碍服务接口
  • 网页 — 在同一会话中并行跑浏览器自动化

这份清单里有一点要读出来：全都是「开发者或无障碍」的通道。它们不是随意操控处于普通使用状态的手机的路径，而是开发者朝自己的设备、自己的应用打开的门。本文的范围也就到这里为止。

1.2 为什么做成CLI

把能力交给智能体的方式有好几种，可以挂成MCP服务器，也可以定义成函数调用工具。agent-device选择把CLI放在中心，同时提供MCP工具和带类型的Node客户端。

CLI占优的理由很直白：编码智能体本来就在用shell。不必把二十个工具定义摊进上下文，教一条命令就够，子命令需要时用--help取出来。工具越挂越多导致选择摇摆的问题在智能体最多能挂多少工具里详细讲过，而用一个CLI包起来正是在token和选择难度两条轴上同时绕开那个问题的做法。

2. 看坐标还是看树

这是把设备操控智能体一分为二的最大轴线：把屏幕当成图片看，还是当成结构看。

坐标方式截图给模型看，拿回一个「点这个像素」的答案。树方式读取操作系统本来就在构建的无障碍结构，也就是安卓无障碍服务文档所描述的那套结构。每个节点带着文本和标签、是否可勾选、是否可点击，并且可以对节点本身施加ACTION_CLICK、ACTION_SET_TEXT、ACTION_SCROLL_FORWARD这类动作，不需要算坐标。

对比维度坐标（截图）方式无障碍树方式
指定单位像素坐标节点引用
分辨率与字号变化会错位不受影响
布局重排全线崩溃标签不变则存活
没有标签的图标可以按形状猜树里看不到
画布、游戏、自绘唯一手段树是空的
token成本图片，贵文本，便宜
追查失败难，不知道看错了什么易，选了哪个节点有记录
附带效果没有顺带产出无障碍质量体检

看表基本已经有答案了：把树放首位，坐标留作兜底。只用坐标的方案演示很漂亮，应用一更新就得全部重写。如果不是自家应用，这份维护费根本没法扛。

不过树也有坑：树的质量由应用决定。开发者没加标签，节点在但没名字。只有图标的工具栏、图片按钮、自绘区域这个问题最严重。于是提升自动化成功率最便宜的办法，反过来成了把无障碍标签补齐。为自动化做的事，顺带把真实读屏用户的体验也改善了。利益能对得这么齐的活并不多见。

3. 循环崩掉的六个地点

「偶尔会失败」是修不了的。失败分种类，每种对策不同。常见的有六个。

崩掉的地点表面症状常见误诊真正的对策
动画中途抓取读到过渡帧，指错元素「模型读不懂屏幕」每个操作后强制等待稳定
加载延迟把空列表判成「无结果」「服务端故障」把骨架屏与转圈明确为未完成
A/B实验与功能开关同一版本，画面和昨天不同「非确定性缺陷」为测试账号固定开关
布局变更发版后场景全挂「工具坏了」把依赖坐标的步骤单列清单
状态残留只有第一次成功，之后失败「不稳定」每次运行重置起始状态
系统弹窗插队权限、更新、通知盖住应用「应用的缺陷」把弹窗处理常驻在循环里

3.1 用屏幕判定成功，就会跟着屏幕一起被骗

六个之中最贵的错误出在最后一步：只用屏幕来校验结果。屏幕上出现「发送完成」不等于真的发出去了，反过来屏幕还没变也不等于失败了。

谷歌研究院的移动智能体评测环境AndroidWorld正面处理了这个问题。它在20个真实安卓应用上放了116个任务，奖励信号取自系统状态而不是画面。所以任务描述怎么改写，判定都不会飘。在企业内部跑自动化也适用同一条原则：成功判定尽量放到屏幕之外。数据库的一行、文件是否存在、API响应、日志里的一行。屏幕留作证据，判定交给状态。

3.2 这个领域的绝对水平

同一份资料里，AndroidWorld论文的基线智能体M3A完成全部任务的30.6%。怎么读这个数字很关键。之后发表的多种方法都报告了高得多的成功率，所以不要把30.6%误当成当前最高水平。但基线是从这个位置出发的这一事实，说明这个问题有多容易打滑。

换成实务感觉就是：成功过一次的场景什么都证明不了。把同一个场景跑二十遍，数通过了几次。通过十九次的自动化和通过十四次的自动化是完全不同的东西，后者因为每次都要人重新核对结果，根本算不上自动化。

4. 在哪里切断不可撤销的操作

这是本文的核心。设备操控的事故半径比浏览器自动化和文件操作更大，因为已登录的真实账号、已绑定的支付方式、通讯录、照片、消息，都只隔着一屏。

等级对应操作默认值安全装置
读取快照、截图、日志与网络采集自动允许敏感界面打码
可撤销的写入滚动、点击、表单输入、页面跳转自动允许记录全部操作
不可撤销的写入支付确认、转账、发送消息、发布评价、删除数据阻断从工具表面移除
凭据与核验登录、身份核验、生物识别、支付密码不作为自动化对象由人亲自完成
设备设置增删账号、恢复出厂、修改权限阻断用专用设备隔离

4.1 确认弹窗不是安全装置

最常见的设计是「危险操作前先问人」，而它几乎总是失败。原因不在技术而在人。二十次里有十九次都是直接同意，第二十次手比眼快。审批疲劳不是异常状况，是常态。

所以顺序要倒过来。

  1. 让它物理上不可能。没绑支付方式的账号、没有余额的环境、与生产分离的数据。先造出「错了也什么都不会发生」的状态
  2. 从工具表面拿掉。模型能看到的命令清单里没有那条路径，判断再飘也不会出这个事故
  3. 剩下的才去问人。一天问两三次，人会真的读；一天问二十次，就不读了

权限该按什么粒度切、什么该默认阻断，这套通论在该允许AI智能体做什么里讲过。设备操控里变化的只有一点：API大多有撤销路径，真机上的UI操作没有。按下去的按钮就是按下去了。

4.2 留证据的设计为什么算功能

agent-device把截图、录像、日志、追踪、网络、性能采样、崩溃信息一起收集，不是便利功能。智能体看了什么、按了什么如果没留下记录，事后核查就无从谈起。把人做的事交出去时，最先消失的就是「当时画面长什么样」的记忆，没有它，失败既无法复现也无法修复。

必须留存的最小集合 — 操作前快照、所选节点的引用与标签、发出的操作、等待稳定的时长、操作后快照，以及用于判定的系统状态。有这六项，大多数失败都能复现。

5. 与Appium、XCUITest的差别

「已经有Appium了，为什么还要这个」是个自然的疑问。答案是两者在做不同的事。

Appium是一个面向多平台、多语言的UI自动化框架，被拆成核心、驱动、客户端、插件四块的模块结构。这套设计出自一个判断：用一个庞大的单体覆盖所有平台，即便不是不可能也极其艰巨。iOS由XCUITest驱动承担，安卓由UiAutomator2驱动承担。

维度既有测试自动化（Appium、XCUITest）智能体设备操控
谁决定下一步人预先写好的脚本模型当场决定
画面与预期不符时停下来绕过去
该性质的评价回归测试里是优点回归测试里是致命伤
选择器人指定并维护每次运行重新发现
运行成本低，无推理高，每步推理
可复现性确定性每次运行可能不同
擅长确认已知的东西没变扫未知界面并起草
不擅长探索新界面、挖掘场景夜间无人值守回归

表的第二行是关键。回归测试如果自己绕过去，那就不是测试。按钮位置变了就停下来报告，这才是回归测试存在的理由；而智能体会自行找到新位置、点下去、给出通过。测试因为「太聪明」而被架空。

所以成立的组合是探索交给智能体，重复交给脚本。智能体扫过界面起草场景，人来确认，确认过的落到确定性脚本。agent-device把执行记录成可回放的脚本并支持导出Maestro YAML，就是把这个格局直接写进了设计。把智能体当测试编写者而不是测试执行器，是当下最现实的用法。

6. 现在能做的和还不能做的

判断标准压成一句：如果出错后撤回的代价高于人自己动手的代价，那就还不到时候。

6.1 现在可以交出去的活

  • 刚改完的界面的目视核对 — 一边留截图一边翻三屏。人最烦的区间，而且没有什么要撤回的
  • 照着复现步骤走一遍 — 按报告的顺序点，同时收集日志、网络与崩溃信息
  • 无障碍标签缺失体检 — 读树的工具会把没标签的元素直接暴露出来，不需要另配审计工具
  • 多分辨率、多语言界面扫查 — 找文字被截断或按钮重叠的组合。组合太多，人做不过来
  • 测试场景起草 — 是起草不是执行，由人复核确定
  • 新手引导流程体检 — 从全新安装到首屏，中间卡几次

6.2 还不能交出去的活

  • 整套夜间无人值守回归 — 理由如前，测试会自己绕开
  • 真实账号支付流程走到底 — 只到确认之前，确认按钮由人来按
  • 触及生产数据的操作 — 删除、发送、发布
  • 通过认证与身份核验 — 下一节单独讲
  • 在个人主力设备上运行 — 消息、照片、通讯录都进了事故半径
  • 他人的设备或账号 — 属于范围之外。前提是自己的设备、自己的账号、自家的应用

7. 核验密集环境带来的约束

这里各地情况开始分化。在金融与实名核验被层层叠进普通消费应用的市场里，自动化成立的区间是身份核验结束之后，到支付确认之前。两头封住不是工具不够，而是本来就被设计成这样。

7.1 安全界面会让智能体失明

安卓有一个把窗口标记为安全表面的标志。加了WindowManager.LayoutParams.FLAG_SECURE的窗口无法被截图，也不会显示在投屏、电视、投影仪这类非安全的显示设备上。安卓官方文档把处理登录与支付信息的银行应用和密码管理器列为典型用途。同一页还附了一条值得记住的但书：在安卓11（API 30）及更低版本上，这个标志只在大约70%的设备上稳定生效，因为部分设备上的键盘输入仍可能被录下。

银行、支付、认证类应用用到这个标志并不罕见。以截图为眼睛的智能体走到那一屏，只看到一个黑框，然后停住。这不是缺陷，而是那个应用刻意为之的行为，是该停下的边界线而不是要越过的东西。自动化设计在这里该做的不是绕行，而是把这一段交回人手，从之后的界面重新接上。

7.2 身份核验不是自动化的对象

身份核验、生物识别、支付密码，是为了证明「此时此地是本人」而造出来的流程。一旦让它自动通过，这道流程就失去了存在的意义。在讨论技术上难不难之前，它先违背了目的。

实务设计要从接受这一点开始：把自动化场景写成从已核验状态出发，会话过期就交回给人。如果是测试环境，另外准备一个不需要核验的预发账号要干净得多。

7.3 想用无障碍服务做内部分发的计划

「做个无障碍服务的应用发到公司内部不就行了」这个想法经常出现。有两堵墙。

  • 必须由用户自己开启。无障碍服务无法自动激活，用户必须在设置里显式启用，而且只有系统才能绑定它
  • 政策限定了用途。安卓文档把无障碍服务定位为构建通用辅助工具的专门手段，并明确它不是让自家应用变得可访问的标准做法。官方指引是自家应用的可访问性应当用标准无障碍API解决

因此企业内部自动化的现实路径是开发设备上的ADB与XCTest通道，而不是分发一个应用。把设备集中到实验室、只在那里跑，在政策与安全两方面的摩擦都最小。

7.4 公司设备的管理策略

办公用手机往往被管理策略锁掉了开发者选项和调试通道。自动化用设备应当作为脱离受管资产的独立资产来立项，也就意味着在资产登记阶段就把用途分开。一开始就放进另一个箱子，永远比事后去争取例外便宜。

8. 要落地就按这个顺序

顺序换了就要付代价。跳过第3步直接从第5步开始的团队特别多。

  1. 把范围限定在自家应用。不要开启以他人应用为自动化对象的方案
  2. 把设备分离出来。禁用个人主力手机。不绑支付方式、只用测试账号、数据与生产分离
  3. 先只开读取。快照、截图、日志采集。至少在这里跑满两周
  4. 补齐无障碍标签。成功率变动最大的地方，副作用是真实可访问性变好
  5. 再开可撤销的写入。滚动、点击、表单输入，全部操作留痕
  6. 把判定挪到屏幕之外。成功与否用系统状态确认，屏幕只当证据
  7. 把定型的场景落到脚本。一直让智能体跑重复执行，成本和抖动会一起累积
  8. 不可撤销的操作始终不开。如果觉得非开不可，那就不是自动化需求，而是另一个设计课题

度量做得简单些：同一场景跑20遍、通过次数、平均耗时、人工介入次数。这四个值按周记录，三周之内就能看出落地到底有没有推进。

最常见的失败套路 — 先做一个华丽的演示场景（从登录一路到支付），看它五次只成一次，得出「还太早」的结论然后收摊。该起步的地方在反方向：失败了也什么都不会发生的读取类工作。

9. 未能确认的部分

以下内容因为没能锁定一手依据，正文中没有作为数字或断言使用。

  • AndroidWorld的最新最好成绩。正文里的30.6%是论文基线智能体的值。之后的多项研究报告了高得多的成功率，但无法在论文正文中比对条件，因此没有搬成数字
  • agent-device在真机与模拟器上的成功率差异。没有公开的对比数值
  • iOS真机上的限制范围。XCTest路径开放的操作范围与模拟器一致到什么程度，未能确定
  • 哪些应用的哪些界面使用了安全标志。各应用不同且没有公开清单，这是要在实际目标应用上直接确认的问题
  • 成本。读一屏并作出判断的token随场景长度如何增长，各方案差异太大，没有一般化

结论：先把可撤销的活交出去

操控设备的智能体常被介绍成「替你用手机的助理」，但当下真正能产出价值的位置不在那边，而在核对性劳动。改的东西是不是真长那样，报上来的缺陷是不是真按那个顺序复现，有没有文字被截断的组合。这是人最嫌烦、最常跳过的活，同时也是错了也没什么可撤回的活。

另一端是支付确认、发送和删除。这里需要的不是更好的模型，而是更窄的工具表面。做成办不到，判断再飘也出不了事故。确认弹窗排在其后，写成文字的禁止排在更后。

只留两件今天就值得试的事。一是把自家应用的无障碍树抓一次，回来多少个没名字的节点，几乎就直接说明了这个应用的可自动化程度。二是把现在由人手工完成的核对工作列成清单，其中没有什么要撤回的条目就是今天能交出去的部分，通常比想象的多。
