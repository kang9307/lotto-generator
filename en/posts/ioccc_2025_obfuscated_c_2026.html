IOCCC 2025 - The International Obfuscated C Code Contest, Code as Art

There Is Even an Aesthetic to Writing Code That Is Hard to Read

Jun 9, 2026 Tech & IT

Introduction: A Contest That Judges Deliberately Unreadable Code

Most programming contests reward speed, correctness, and clarity. But since 1984 one contest has chased the exact opposite. It is the International Obfuscated C Code Contest, or IOCCC. Its aim is simple: to crown "the most creatively hard-to-read C code that nevertheless actually runs." In August 2025, the winners of the 29th contest were announced, and the developer community took notice once again.

The word "obfuscation" usually carries a negative charge. It is the language of code that hides malware, evades licensing, or sabotages collaboration. Yet the IOCCC's obfuscation has an entirely different texture. Here, obfuscation is an intellectual game that explores the limits of C, and a form of art. Source code can take the shape of a picture; a few lines can hold an operating-system emulator. In this article we will calmly cover what the IOCCC is, why obfuscation is called "art," the trends among the 2025 winners, and what this strange contest teaches us.

1. The Birth of the IOCCC: An Idea Born from Terrible Code

The story begins in 1984 at the American chipmaker National Semiconductor. Two employees, then-24-year-old Landon Curt Noll and Larry Bassel, were tasked with fixing "some very broken code." Wrestling with horribly unreadable software, they had a flash of inspiration: "If the code has to be bad, why not hold a contest for the worst possible code?"

So they posted contest rules to the Usenet discussion groups where C was debated (net.lang.c and net.unix-wizards). The first contest carried the modest name "First Annual Obfuscated C Code Contest," and the source-file size limit was a mere 512 bytes. Curiously, that first year there was not even a rule against machine-dependent code. This small, playful experiment became the starting point of a legendary contest that has now run for over forty years.

The IOCCC is meant to be annual, though some years were skipped (1997, 1999, 2002, 2003, 2006, and others). After a long hiatus from 2020 to 2024, the contest resumed in earnest. The 2025 contest was the second held since that revival.

2. The Goal: Showing the Value of Clear Code by Paradox

The IOCCC is not a mere joke contest, because a serious purpose sits inside it. Its stated goals can be summarized as follows:

  • Write the most obscure C program. That is, compete to make code that is deliberately hard to read.
  • Show the value of clear programming style by paradox. By pushing "bad examples" to the extreme, it makes you realize, in reverse, why good code is good.
  • Stress-test C compilers with unusual constructs. Code at the edge of the standard exposes a compiler's weak spots.
  • Expose the subtleties of the language. It shines a light on C's dark corners and rarely used grammar.
  • Provide a safe outlet for experimental code. It is a stage to unfurl outlandish ideas you could never use in production.

The crucial goal is the second. The IOCCC is, in fact, the most dazzling cautionary tale of "how not to write code." By marshalling variable names, indentation, and macros to extremes that no normal program would ever use, it freshly reminds us of the value of the "readable code" we take for granted.

There is a quiet wisdom in teaching this way. Lectures about clean code tend to slide off; everyone nods, and then writes the same tangled function the next day. But spend an hour wrestling with a single IOCCC entry, watching a perfectly reasonable-looking line turn out to hide three levels of macro trickery, and the lesson lands in your bones. You come away with a visceral appreciation for descriptive names, generous whitespace, and the small acts of consideration that make code legible to the next human. The contest does not preach; it lets you feel the cost of obscurity firsthand, which is a far more durable teacher.

3. What Counts as Obfuscation: The Signature Techniques

The obfuscation techniques in IOCCC winners are endless, but the recurring types include the following.

Abusing the Preprocessor

One of the most famous categories is the "Worst Abuse of the C Preprocessor." C's preprocessor is meant to be a simple text-substitution tool, but IOCCC entrants use it for purposes utterly unlike its intent. Some entries finish almost all of their computation in the preprocessing stage, stringing together endless #define macros so that the code expands into something entirely different before compilation.

Code as Image

Here the source code itself becomes a picture. The code is laid out in a particular shape - a figure, a letter, a drawing - while still compiling and running correctly. Because it must satisfy both the "shape" and the "function" of the code, it demands sophisticated design.

Quines and Self-Reference

A quine is a program that prints its own source code. The idea of replicating oneself with no input is an elegant puzzle in itself and a perennial IOCCC subject. In 2025, too, a patch/diff variant of the quine won.

Detours into Obscure Expressions

This is the technique of producing the same result through far more opaque means than the usual grammar: nested ternary operators, the comma operator, abuse of bitwise operations, and seemingly meaningless whitespace and line breaks to hide intent.

The joy of the IOCCC is not "you cannot read it" but "once you do read it, it is astonishing." The gasp at the moment of cracking an entry is the contest's real reward.

4. The Precision of the Rules: Guards Against Infinite Macros

You might wonder, "Couldn't you just string out infinite macros?" The IOCCC has precise rules to block exactly this trick. The key is that the size limit is measured after preprocessor expansion. To do this, the contest measures source size with a dedicated tool called iocccsize. So strategies that bloat the code with excessive macros simply do not work.

There is another important constraint. Submissions must compile without undefined behavior (UB) under common compilers like GCC or Clang with standard flags. In other words, IOCCC code is not "randomly broken code"; it is code precisely engineered to run correctly within the demanding boundaries of the C standard. It looks like chaos on the surface, but underneath it is meticulous order. This very paradox is what lifts the IOCCC into the realm of art.

5. The Legendary Types of Winners Over the Years

Across forty years there are masterpieces recounted again and again. Without naming individual entries, the legendary recurring types can be summarized as follows.

Type Description
Tiny interpreter / compiler An interpreter or compiler for a small language packed into a few hundred bytes of code
Ray tracer / graphics Visual entries that perform 3D rendering or ray tracing in very short code
Quine variants Programs that print themselves, with twists like rotation, multilingualism, or multiple stages
Emulators / virtual machines Entries that mimic CPUs, game consoles, or classic computers in small code
Code that forms a picture Entries whose source layout itself forms a drawing or letters

Winners receive a distinctive category name each year. Titles like "Most Erratic Behavior" or "Worst Abuse of the Preprocessor" are funny in themselves while pinning down each entry's character precisely.

6. IOCCC 2025: Trends of the 29th Contest

In early August 2025, according to the announcement, around 23 winners of the 29th IOCCC were revealed in a four-and-a-half-hour livestreamed ceremony. The organizers noted that the volume and quality of submissions were near historic highs. Even though this was only the second contest since the hiatus, both the number of submissions and the overall polish stayed high. Notably, a first-time winner from Taiwan (jingp49) appeared, widening the contest's geographic reach.

The standout keyword among the 2025 winners was unmistakably emulators and virtual machines. Among the announced winners, the much-discussed examples include:

  • A VM that runs Doom: a virtual machine implemented in small C code, running the legendary game Doom on top of it.
  • An OpenRISC 32-bit CPU emulator: an emulator mimicking a real CPU architecture.
  • A Game Boy emulator: an entry reproducing the classic handheld console (ncw1).
  • A Subleq single-instruction computer: an abstract computer that operates with just one instruction (cable).
  • A patch/diff quine: a resilient quine that twists the self-reference idea (endoh3).
  • Use of the U"string" prefix: a "salmon recipe" entry that cleverly exploits C's Unicode string-literal prefix.

The trend here is clear. Beyond merely tangling code, the IOCCC's aesthetic is evolving toward "packing a vast system into tiny code." The sight of a few hundred bytes to a few kilobytes of code mimicking a CPU, a game console, or an OS-grade program is astonishing in its own right.

This shift says something about how the craft has matured. The earliest contests prized clever one-liners and visual gimmicks, code shaped like a fish or a circle that nonetheless ran. Those still appear, but the heavyweight entries increasingly demonstrate real systems engineering compressed into an absurdly small footprint. Writing an emulator that boots a game is hard even with all the room in the world; doing it within IOCCC's size budget, without undefined behavior, while keeping the source dense enough to qualify as obfuscated, is a feat that combines deep architectural knowledge with a poet's discipline about every byte. The fact that a first-time author from Taiwan joined the winners this year also hints at how the contest's reach keeps widening, drawing fresh talent and fresh ideas from new corners of the world.

7. Why This Is "Art"

Let us lay out why obfuscated code is called art. If the heart of art is "creativity within constraint," the IOCCC fits that definition exactly.

First, extreme constraint. The strict size limit and the rule of compiling without UB bind the author the way a sonnet's meter or a haiku's syllable count binds the poet. Aesthetics are born precisely when something is achieved within those bounds.

Second, the fusion of form and content. When code forms a picture while simultaneously performing a function related to that picture, form (the visual) and content (the behavior) are bound into one. This is no different from what painting or concrete poetry pursues.

Third, conceptual elegance. A program that prints itself, like a quine, carries a mathematical beauty in its very idea. Producing the most astonishing result with the fewest means is the essence of elegance.

8. What the IOCCC Teaches: The Depth of C

Paradoxically, a contest for badly written code teaches C most deeply. As you decode an IOCCC entry, you confront subjects like these:

  • The nature of the preprocessor: you learn through extreme examples how macro expansion, token pasting (##), and stringization (#) actually work.
  • Operator precedence and associativity: unraveling dense, parenthesis-free expressions demands an exact grasp of precedence rules.
  • Undefined behavior (UB): you develop a feel for what is guaranteed by the standard versus left to the compiler.
  • Portability: you viscerally grasp why the same code behaves differently across platforms.

This depth also matters when moving from C to safer, more modern languages. 9. Educational and Cultural Significance

The IOCCC is more than a game for eccentrics; it holds a unique place in programming culture. Educationally, as noted, it teaches the value of good code through "bad examples." Having students decode IOCCC entries is excellent training in C debugging and in understanding the standard.

Culturally, the IOCCC represents a view of programming as a medium of expression. Code is not merely a means to drive a machine; it can be a canvas onto which humans pour ingenuity, humor, and aesthetic feeling. Over four decades, countless developers have come to see C and the nature of computing anew through this contest.

10. Never Imitate This: The Opposite of Production Code

Here is the most important warning, stated plainly. You must never imitate the IOCCC style in production code. This contest is a game that deliberately violates every principle of good software engineering.

Principle of production code The opposite the IOCCC pursues
Clear variable and function names Meaningless single letters, confusing names
Consistent indentation and structure Deliberately broken formatting
Flow that is easy to read and maintain Flow tangled to make decoding take time
Standard, predictable idioms The most obscure, surprising detours

In real work, code is not written once and forgotten; it is an asset that colleagues read and revise and live with for years. Readability and clarity are the basic courtesy of collaboration and the foundation of productivity. The IOCCC is something to admire, decode, and learn from, not a style to copy. Keep that distinction clear, and the IOCCC becomes an unmatched intellectual pleasure for anyone who loves C.

11. How to Enjoy It Yourself: Where to Look and How to Decode

If the IOCCC has caught your interest, here is how to approach it.

  1. Browse the official repository. Past winners and their source are public on the official IOCCC site (ioccc.org) and the GitHub repository (ioccc-src/winner). Each entry ships with a hint file written by the author.
  2. Read the hint first. Diving straight into the code without the author's notes is daunting. Grasp the entry's intent and tricks from the hint file, and you will find the thread to start unraveling.
  3. Run the preprocessor alone. A command like gcc -E expands just the preprocessing stage, showing at a glance how macros transform the code. Half the obfuscation unravels here.
  4. Restore the indentation. Tidy the formatting with a code formatter, rename variables to something meaningful as you read, and order slowly emerges from the chaos.

For reference, the next contest, the 30th IOCCC, is reportedly planned to open toward the end of 2026 and run until the end of Q1 2027. If you are interested, taking a shot at it yourself is one way to engage.

12. Conclusion + Three Things You Can Apply Now

The IOCCC fits in one sentence: a forty-year art contest that competes to write the most unreadable code and, by paradox, teaches the depth of C and the value of good code. From two engineers' playful idea in 1984 to a VM running Doom and a Game Boy emulator in 2025, the IOCCC has steadily proven that code can be expression as well as function.

Let us close with three things you can do right away.

  1. Decode one winner. Pick one of the IOCCC 2025 entries and work through it alongside its hint. You will learn the subtleties of C more vividly than from any textbook.
  2. See the preprocessor expansion yourself. Run gcc -E on your own code to watch how macros unfold, and a vague fear of the preprocessor falls away.
  3. Re-confirm the value of readability. Recalling the IOCCC's opposite, polish the variable names and structure of the code you write today one more time. Your colleagues, and your future self, will thank you.
