プロセスが黙って死んだ - OOM キラーの読み方

アプリケーションログが空のとき、カーネルが残した記録から犯人を絞る順番

2026-09-02 開発・インフラ

プロセスが消えた。アプリケーションログの最後の行はありふれたリクエスト処理の記録で、その後には何もない。例外スタックもなく、終了フックが残す挨拶もない。監視ツールはプロセスがもう存在しないという事実だけを伝えてくる。

ここで最も多く浪費される時間は、アプリケーションログをさらに詳しく漁ることに使われる。そこにはない。あるはずがない。SIGKILL はプロセスが受け取って処理するシグナルではなく、プロセスをその場で終わらせる動作なので、その時点でアプリケーションは一文字も書く機会を持たない。だから最初の一手はログを掘ることではなく、仮説を変えることだ。死んだのではなく殺されたのである。

この記事を書いた環境は Windows 10 に Git Bash(MSYS2、GNU bash 5.2.37(1)-release)である。Linux カーネルも cgroup も dmesg もない環境なので、以下に出てくるカーネルの挙動・フィールド定義・ファイルパスはすべて kernel.org の公式ドキュメントとカーネルソースで確認したものであり、実際の OOM ログを再現して貼ったものではない。この環境で実際に実行して確認したのは終了コードの規則だけで、その出力は本文にそのまま載せてある。確認できたことと確認できなかったことの境界は、最後から二番目の節にまとめてある。

アプリケーションログが何も語らない理由

カーネルのメモリ管理ドキュメントは OOM キラーをこう説明する。負荷のかかったマシンでメモリが枯渇し、カーネルが動作を続けられるだけのメモリを回収できない状況が起こりうるので、残りのシステムを救うためにカーネルが OOM キラーを呼び出す、というものだ。そしてシステム全体の健全性のために犠牲にするタスクを一つ選ぶと書かれている。重要なのは「選ぶ」だ。選択はカーネル側で起こり、選ばれた側は通知を受けない。

そのためアプリケーションが普段残していたものが丸ごと抜け落ちる。例外スタックは例外が起きなければ生まれないが、例外は起きていない。終了フックはシグナルを捕捉できて初めて回るが、SIGKILL は捕捉できない。バッファに残っていたログはフラッシュされずに消える。「最後のログ行がありふれている」ということ自体が信号であって、情報がないという意味ではない。

  • 残らないもの — 例外スタック、終了フックが走った痕跡、フラッシュされていないログバッファ、アプリケーション自身が記録する終了コード
  • 残るもの — カーネルリングバッファの OOM 記録、親プロセスが受け取った終了ステータス、コンテナランタイムが付けた終了理由、メトリクス収集器が最後に取得した値
  • 順番が逆になっている — 普段はアプリケーションログが一次資料でカーネルログが補助だ。この事件では逆になる
  • メトリクスが途切れた地点がヒントだ — 収集周期が 15 秒なら死ぬ直前 15 秒の値はない。最後の点が穏やかに見えても、その間に急騰があった可能性がある

死んだのではなく殺された - 137 と OOMKilled

仮説を切り替える根拠は終了コードだ。シェルはコマンドが致命的シグナルで終わったとき、128 にシグナル番号を足した値を終了ステータスとして報告する。この規則は Linux でない環境でも同じシェルなら同様に動くので、この記事を書いた Git Bash でそのまま確認できた。

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

$ bash -c 'kill -9 $$'; echo "exit=$?"
/usr/bin/bash: line 1:  1419 Killed                  bash -c 'kill -9 $$'
exit=137

$ bash -c 'kill -15 $$'; echo "term_exit=$?"
Terminated
term_exit=143

9 番が SIGKILL なので 128 足す 9 は 137、15 番が SIGTERM なので 143 になる。押さえておくべきは137 が伝える範囲が思ったより狭いという点だ。137 は「強制終了された」までしか語らない。誰が SIGKILL を送ったのかはここに含まれていない。カーネルの OOM キラーかもしれないし、終了猶予を超えてオーケストレータが仕上げに送ったものかもしれないし、バッチスクリプトかもしれない。

シグナル番号シェルが報告する終了コードこのコードが伝えること
SIGTERM15143片付ける機会があった。何をしたかはアプリケーションログに残る
SIGKILL9137即座に終了した。送った主体はカーネルログと突き合わせないと分からない
SIGSEGV11139不正なメモリアクセス。メモリ不足とは別の事件だ
SIGABRT6134ランタイム自身が諦めた。確保失敗を abort で処理する実装で出る
正常終了-0 ~ 125アプリケーションが決めた値。強制終了ではない

シグナル番号はプラットフォームのシグナル表に従う。上の 6、9、11、15 は Linux では安定して同じだが、すべての番号がそうではない。この記事を書いた MSYS 環境で kill -l を出すと 7 番が SIGEMT と出るが、Linux x86 で 7 番は SIGBUS だ。番号を暗記して使うより、そのシステムの表を一度出してみるほうが安全である。

コンテナではラベルがもう一つ付く。ランタイムが終了理由を OOMKilled として記録し、オーケストレータがそれを Pod のステータスに露出する。終了コードより明示的だが、「どの OOM なのか」は依然として伝えてくれない。ノード全体が不足していた場合とコンテナの上限に達した場合が、同じラベルを付けて出てくる。

付け加えると、Kubernetes のドキュメントはメモリ上限が反応的に強制されると記す。上限を超えて使うとカーネルが終了させうるが、終了はカーネルがメモリ圧迫を検知したときにのみ起こるので、過剰に確保したコンテナが即座に殺されない場合があるという説明だ。「昨日も上限を超えていたのになぜ今日死んだのか」の答えがここにある。

どこを見るか

カーネルが残す場所は一つだが、読む窓口は複数あり、窓口ごとに保存期間が違う。この差のせいで「記録がない」という結論がよく間違う。

# 1) カーネルリングバッファ - 最も速いが長くは残らない
dmesg -T | grep -i -E 'out of memory|oom-killer|killed process'

# 2) ジャーナル - カーネルメッセージのみ、時刻範囲を絞って
journalctl -k --since '2 hours ago' | grep -i -E 'oom|killed process'

# 3) 再起動を挟んでいるならブート単位でさかのぼる
journalctl --list-boots
journalctl -k -b -1 | grep -i 'killed process'

# 4) リングバッファがすでに流れたとき - パスはディストリビューションによって違う
grep -i -E 'oom-killer|killed process' /var/log/messages
grep -i -E 'oom-killer|killed process' /var/log/syslog

dmesg が見るリングバッファは固定サイズなので、新しいメッセージが入ると古いものから押し出される。ストレージやネットワークのメッセージが毎秒数行出るノードなら、数時間前の OOM 記録はすでにない。「dmesg にないから OOM ではない」という結論は、リングバッファが流れていないことを確認した後にのみ成り立つ。ジャーナルも保存方式が揮発性なら再起動とともに消える。ログがどこまで残っているかはそれ自体が別の主題であり、ローテーション設定が作る罠はログローテーションが静かにずれる場所で別に扱った。

コンテナ側の窓口はランタイムとオーケストレータが持っている。カーネルログにアクセスする権限がない場合が多く、こちらのほうが先に手に届く。

# Kubernetes - 前回の終了の理由とコード
kubectl describe pod <pod> | sed -n '/Last State/,/Restart Count/p'
kubectl get pod <pod> -o jsonpath='{range .status.containerStatuses[*]}{.name}{"\t"}{.lastState.terminated.reason}{"\t"}{.lastState.terminated.exitCode}{"\n"}{end}'

# Docker - OOMKilled フラグと終了コードを一行で
docker inspect --format '{{.Name}} oom={{.State.OOMKilled}} exit={{.State.ExitCode}}' <container>

# ノードに入れるなら、カーネル側と時刻を合わせる
journalctl -k --since '2026-09-02 09:00' --until '2026-09-02 10:00'

ここで最初の分かれ道が出る。コンテナのステータスは OOMKilled なのにノードのカーネルログにシステム OOM の記録がなければノードは無事だったということで、事件は cgroup の上限側だ。逆に同じ時刻に複数の Pod が一緒に死に、カーネルログにノード全体のメモリダンプが残っていればノード側である。この分かれ道を通る前に上限を上げたりノードを増設したりするのはコイン投げだ。

カーネルが出力する表の読み方

カーネルは OOM キリングを実行するときタスク一覧を表としてダンプし、この動作は sysctl でオンオフする。カーネルの sysctl ドキュメントは oom_dump_tasks が、カーネルスレッドを除いたシステム全域のタスクダンプを生成し、pid、uid、tgid、vm size、rss、pgtables_bytes、swapents、oom_score_adj スコア、name といった情報を含めると記す。カーネルソースのヘッダ出力関数でも、このダンプが sysctl 値に掛かっているのがそのまま見える。

ログに出る文字列は三つの塊だ。以下はカーネルソースのフォーマット文字列をそのまま写したもので、%s や %d の位置に実際の値が埋められて出力される。

# (1) 誰が OOM キラーを呼んだか - dump_header()
%s invoked oom-killer: gfp_mask=%#x(%pGg), order=%d, oom_score_adj=%d

# (2) 候補一覧の列名 - dump_tasks()
[  pid  ]   uid  tgid total_vm      rss rss_anon rss_file rss_shmem pgtables_bytes swapents oom_score_adj name

# (3) 結論 - __oom_kill_process()
%s: Killed process %d (%s) total-vm:%lukB, anon-rss:%lukB, file-rss:%lukB, shmem-rss:%lukB, UID:%u pgtables:%lukB oom_score_adj:%d

ほとんどの人は (3) だけ読んで終わる。ところが (3) は結論であり、原因候補の一覧は (2) の下に続く表にある。表を見なければ「なぜあのプロセスだったのか」に答えられず、答えられなければ次も同じことが起こる。

列単位何か犯人を選ぶときの使いどころ
total_vmページ仮想アドレス空間の大きさ低い。予約しただけで使っていない領域が含まれる
rssページ実際に物理メモリに載っている総量ここから始める。大きい順に並べると候補が絞られる
rss_anonページファイル背景のない部分。ヒープとスタックリーク疑いの筆頭。回収手段がスワップしかない
rss_fileページマップされたファイルページおおむね回収可能。この列だけ大きいプロセスは犯人でない確率が高い
rss_shmemページtmpfs と共有メモリ/dev/shm の使用量。ファイルのように見えるが回収されない
pgtables_bytesバイトページテーブル自体が使うメモリスレッドが多いときやマッピングが細かく割れているときに大きくなる
swapentsページスワップに出ているページ数スワップがあると rss が実際より小さく見える。一緒に見る必要がある
oom_score_adjなし選択に掛かる重みrss で一位でないプロセスが死んだなら答えはこの列にある
nameなし実行ファイル名長いと切れる。同じ名前が複数あれば pid で突き合わせる

読むときに間違えやすい箇所が二つある。一つは単位がページだということだ。名前に _bytes が付いた pgtables_bytes だけがバイトで、残りのメモリ列はページ数である。ページサイズはアーキテクチャと設定によって違うので、そのシステムの値を確認して掛ける必要がある。もう一つは列構成がカーネルバージョンによって違うことだ。上の sysctl ドキュメントの一覧と現在のソースのヘッダ文字列はすでに食い違っている(ソース側に rss_anon、rss_file、rss_shmem が加わっている)。自分のログのヘッダ行を先に読んで列位置を合わせなければならない。

# 保存しておいたログから表の部分だけ抜き出す
# 列番号はカーネルバージョンごとに違うので、ヘッダ行も必ず一緒に出力する
awk '/\[ *pid *\]/{print; f=1; next} f && /^\[/{print} f && !/^\[/{f=0}' oom.log | head -40

# rss 列が何番目かをヘッダで数えてから並べ替える(以下は 4 番目の場合)
awk '/^\[/{print $4, $NF, $0}' oom.log | sort -nr | head -20

なぜよりによってそのプロセスが死んだのか

カーネルは候補ごとに badness スコアを付けて最も高いものを選ぶ。現在のソースではその計算が、RSS とスワップエントリ数、そしてページテーブルの大きさをページ単位に換算した値を足すことから出発する。「このプロセスを今終わらせたら何ページ戻ってくるか」に対する推定値だ。その次に oom_score_adj が加えられるが、そのまま加えられるのではなく全体のページ数を 1000 で割った値を掛けてから加えられる。

この掛け算が実務的に重要だ。oom_score_adj 1 点が全体メモリの 0.1 パーセントに当たるページ数に換算されるので、この値を 100 に上げてあるプロセスは全体メモリの 10 パーセントを余分に使っているかのように扱われる。128GiB のノードなら 13GiB 余分に使っている計算になる。「最も使っているプロセスが死ぬ」が常に正しいとは限らない算数的な理由がここにある。

カーネルドキュメントによればこの値の範囲は -1000 から +1000 だ。ドキュメントは最も低い -1000 についてそのタスクの OOM キリングを事実上無効にする値だと記す。常に badness スコア 0 を報告するようになるから、という説明である。/proc/<pid>/oom_score で露出される値にはこの重みがすでに含まれ、実質範囲が 0 から 2000 になるという点もドキュメントにある。

# 特定プロセスの現在のスコアと重み
cat /proc/<pid>/oom_score
cat /proc/<pid>/oom_score_adj

# 重みが 0 でないプロセスだけを洗い出す(誰が手を入れたかの確認)
for p in /proc/[0-9]*; do
  a=$(cat "$p/oom_score_adj" 2>/dev/null) || continue
  [ "$a" = "0" ] && continue
  printf '%s\t%s\t%s\n' "${p#/proc/}" "$a" "$(tr -d '\0' < "$p/comm")"
done
  • カーネルはスレッド一つではなくスレッドグループを単位として見る。表に tgid 列がある理由だ
  • 監視エージェントやサイドカーはたいていスコアが低い。メモリを少ししか使わないからだ。だから死ぬのは本体で、死んだ後もエージェントは生きて「プロセスなし」を報告する
  • 逆にサイドカーに重みを上げたまま忘れている場合がある。はるかに少ないのに先に死ぬなら、この列を疑う
  • オーケストレータがワークロードの等級に応じてこの値を設定することもある。触った覚えがなくても 0 でない場合がある
危険表示。oom_score_adj を -1000 に下げるのはそのプロセスを候補から外す措置であって、メモリを増やしてやる措置ではない。不足はそのまま残り、代わりに別の何かが死ぬ。データベースを免除しておけばその隣の監視エージェントが死に、そうなると障害を誰も知らせてくれない。免除は対応ではなく死ぬ順番を変えることなので、何が代わりに死んでよいのかを先に決めてから触る値だ。

システム OOM と cgroup OOM は別の事件だ

カーネルソースにはこの二つが分かれる地点が一行で入っている。OOM 処理関数を呼ぶときメッセージ文字列を三項演算子で選ぶのだが、メモリ cgroup の OOM でなければ "Out of memory"、そうなら "Memory cgroup out of memory" を渡す。この文字列が前節 (3) 番フォーマットの先頭の %s の位置に入る。ログの最初の単語が事件の種類を教えてくれる。

区分システム(ノード)OOMcgroup OOM
引き金ノード全体で回収が失敗したその cgroup が自分の上限に達した
ログの先頭Out of memory: Killed process ...Memory cgroup out of memory: Killed process ...
候補範囲ノードのすべてのプロセスその cgroup とその配下
ノードの余裕ない。だからこの事件が起きた余っている場合がある。ダッシュボードは穏やかに見える
一緒に死ぬもの無関係なワークロードまで揺れるそのコンテナだけが死ぬ
よくある誤診アプリケーションのリークだと決めつけるノードを増設する
先に見る場所/proc/meminfo、カーネルログのメモリダンプmemory.events、memory.max、memory.current

カーネルの cgroup v2 ドキュメントは memory.max をメモリ使用量のハード上限と定義しつつ、cgroup の使用量がこの上限に達して減らせない場合、その cgroup 内で OOM キラーが呼び出されると記す。memory.high は違う。使用量が high 境界を越えるとその cgroup のプロセスがスロットリングされ強い回収圧力を受けるが、high 上限を越えることは決して OOM キラーを呼び出さないと同じドキュメントが記している。high はブレーキで、max は壁だ。

# コンテナの中から - cgroup v2
cat /sys/fs/cgroup/memory.max        # 壁。max なら上限なし
cat /sys/fs/cgroup/memory.high       # ブレーキ
cat /sys/fs/cgroup/memory.current    # 今どれだけ使っているか
cat /sys/fs/cgroup/memory.events     # ここで low/high/max/oom/oom_kill を見る
cat /sys/fs/cgroup/memory.stat | head -20

# ノードから特定の cgroup パスを指定するとき
cat /sys/fs/cgroup/kubepods.slice/.../memory.events

memory.events の二つの値は意味が違い、この差が予報の役割を果たす。ドキュメントは oom をcgroup の使用量が上限に達して確保が失敗しかけた回数、oom_kill をこの cgroup に属するプロセスが何らかの OOM キラーによって殺された回数と定義する。つまり oom は上がっているのに oom_kill が 0 ならまだ誰も死んでいないということで、それは次のデプロイか次のピークで死ぬという予告だ。この値をアラートに掛けておけば事後ではなく事前に手を入れられる。

同じドキュメントに memory.oom.group もある。この cgroup を OOM キラーが分割できない一つのワークロードとして扱うかを決める値で、設定するとその cgroup と配下のすべてのタスクが一緒に死ぬか誰も死なないかになる。プロセス一つだけが死んで残りが半分の状態で回り続ける事態を防ぐスイッチだ。

ランタイムがメモリ上限をどう認識するかはまた別の層だ。JVM のようにヒープサイズをコンテナの上限から推測するランタイムには固有の罠があり、その話はコンテナの中の JVM が上限を読み違えるときで別に扱った。ここではカーネルと cgroup 側の一般論だけを見る。

cgroup v1 と v2 で変わるもの

同じ「メモリ上限 512Mi」が二つのバージョンで違うものを意味しうる。ファイル名からして違い、スワップの数え方が違う。

# どのバージョンで動いているか - v2 単独なら cgroup2fs と出る
stat -fc %T /sys/fs/cgroup
mount | grep -E 'cgroup|cgroup2'

# v1 系で見るファイル
cat /sys/fs/cgroup/memory/memory.limit_in_bytes
cat /sys/fs/cgroup/memory/memory.usage_in_bytes
cat /sys/fs/cgroup/memory/memory.failcnt
cat /sys/fs/cgroup/memory/memory.memsw.limit_in_bytes
cat /sys/fs/cgroup/memory/memory.oom_control
grep -E '^(cache|rss|mapped_file) ' /sys/fs/cgroup/memory/memory.stat
  • スワップの数え方。v1 は memory.memsw.limit_in_bytes でメモリとスワップを合わせて掛ける。v2 は memory.swap.max で別に掛ける。同じ数字を入れても意味が変わる代表的な場所だ
  • 使用量の値の正確さ。v1 のドキュメントは memory.usage_in_bytes が正確な値を示さないと自ら明かしつつ、より精密に見るには memory.stat の RSS と CACHE(そして SWAP)を使えと案内する
  • 失敗回数のカウンタ。v1 の memory.failcnt は上限にぶつかった回数を数える。v2 でこの位置を代わりに担うのが memory.events だ
  • 上限に達したときの手順は同じ骨格だ。v1 のドキュメントは、cgroup が上限を超えるとまずその cgroup からメモリを回収しようと試み、成功しなければ OOM ルーチンが呼び出され最も大きいタスクを選んで殺すと記す
  • OOM キリングを切るスイッチ。v1 の memory.oom_control には oom_kill_disable と under_oom がある。ドキュメントは under_oom が 1 のときその cgroup が OOM 状態でありタスクが停止している場合があると記す
危険表示。v1 の oom_kill_disable を有効にすると、死なない代わりに止まる。プロセスは一覧に生きていてヘルスチェックの種類によっては通過することもあるのに、リクエストを一つも処理できない。死んで再起動されるほうがよい場合が多いので、この値はその状態を検知する別の手段があるときにだけ検討する。

オーバーコミット - malloc が成功しても死ぬ仕組み

Linux は既定で実際に持っているより多くのメモリを約束する。そうするほうが大半の場合に得だからだ。fork の直後に exec を呼ぶプロセスはコピーされたアドレス空間をほとんど使わないし、大きな配列を先に確保して前のほうだけ使うコードもよくある。物理ページはそのアドレスへ最初に書き込むときに割り当てられる。

だから失敗が遅れて来る。確保関数はアドレス空間を得ることに成功し、死ぬのはそのアドレスへ最初に書き込む瞬間だ。コードで見れば成功した確保の次の行で死ぬ。確保失敗の処理をどれだけ緻密に書いても、その経路に来ない理由がここにある。

vm.overcommit_memoryカーネルドキュメントの説明実際に起こること副作用
0 (既定)カーネルがユーザ空間の要求サイズを全体メモリとスワップの合計と比較し、明白な過剰要求を拒否するたいていの要求は通る失敗が確保時点ではなく使用時点に OOM として現れる
1実際に尽きるまでカーネルがメモリは常に十分だというふりをするほぼすべての要求が成功する確保失敗という信号が消え、すべての問題が OOM に収束する
2いかなるオーバーコミットも防ごうとする方針を使うCommitLimit を超えるコミット自体が拒否される今まで成功していた確保が失敗し始める

オーバーコミット会計のドキュメントは 2 番モードの上限をスワップに物理 RAM の設定可能な割合(既定 50 パーセント)を足した値と説明する。この割合は vm.overcommit_ratio、絶対値は vm.overcommit_kbytes で決め、どちらも 2 番モードでのみ効力がある。現在の上限とコミット量は /proc/meminfo の CommitLimit と Committed_AS で見られると記されている。

sysctl vm.overcommit_memory vm.overcommit_ratio vm.overcommit_kbytes

# 今どれだけ約束しているか - Committed_AS が CommitLimit にどこまで近いかを見る
grep -E '^(MemTotal|SwapTotal|CommitLimit|Committed_AS):' /proc/meminfo

Committed_AS はドキュメント上システムに現在割り当てられているメモリの量であり、プロセスが確保したすべてのメモリの合計で、まだ実際に使っていなくても含まれるという但し書きが付いている。したがってこの値が MemTotal を大きく超えるのは正常であり、オーバーコミットが働いている証拠だ。問題として見る値ではない。

危険表示。vm.overcommit_memory を 2 に変えると OOM の代わりに確保失敗が始まる。大きく予約して少しだけ使うプロセスは起動すらできない場合がある。稼働中のノードで sysctl によって即座に変えるのは全サービスを同時に揺らす措置なので、まず Committed_AS と CommitLimit の平常の推移を数日測り、ステージングで起動を確認してから行う。

スワップが変えるもの

スワップがあればカーネルに回収する場所がもう一つできる。匿名ページをストレージへ追い出してその場所を再利用できるので OOM が遅れて来る。代わりにその区間が遅くなる。この「遅さ」が死ぬことよりましかはサービスの性質次第だ。

カーネルの PSI ドキュメントはこの状態を二行に分けて見せる。some は一部のタスクがその資源を待って停滞していた時間の割合で、full はアイドルでないすべてのタスクが同時に停滞していた時間の割合だ。ドキュメントは full の状態を浪費された CPU サイクルとして説明し、スラッシングを指すと記す。full が上がっているなら、そのノードはまだ死んでいないだけで、すでに仕事をしていない。

swapon --show
free -h
grep -E '^(SwapTotal|SwapFree|SwapCached):' /proc/meminfo

# 今止まっている割合 - some と full を分けて見る
cat /proc/pressure/memory
cat /sys/fs/cgroup/memory.pressure

# どのプロセスがスワップに出ているか
grep -H VmSwap /proc/[0-9]*/status | sort -t: -k3 -n -r | head -10

コンテナ環境でスワップを切る慣行にはこういう背景がある。応答遅延が死ぬことより悪いサービスがあるからだ。30 秒かかる応答はすでに失敗なのにプロセスは生きているのでヘルスチェックを通過し、そうするとトラフィックが入り続けて状態はさらに悪くなる。この場合は早く死んで早く再起動されるほうが全体の可用性に勝る。

  • Kubernetes のドキュメントは、既定で kubelet がスワップの有効なリナックスノードでは起動しないと記す。起動させるには failSwapOn: false を明示しなければならない
  • スワップの挙動は memorySwap.swapBehavior で決める。既定の NoSwap ではそのノードの Pod として回るワークロードはスワップを使わないし使えず、LimitedSwap では使える
  • 同じドキュメントに注目すべき手がかりがある。NoSwap にしてスワップを許可しても、Kubernetes が管理しないプロセス、つまり systemd のサービスや kubelet 自身はスワップを使えるということだ。ノードのスワップ使用量が 0 でないからといって Pod が使っているとは限らない
  • kubelet はコンテナランタイム API で設定を指示し、cgroup v2 の場合の例としてドキュメントが挙げるのが memory.swap.max だ。前節のファイルとそのままつながる
  • スワップを有効にすると決めたなら遅延がどこまで許容されるかを先に決める。決めないと「死なないがずっと遅い」状態が常態化し、その状態はアラートに掛かりにくい
危険表示。稼働中のノードでの swapoff -a は、スワップに出ていたページをすべて物理メモリへ読み戻す動作だ。その瞬間の物理的な余裕がスワップ使用量より小さければ、その場で OOM を呼ぶ。切る前に SwapTotal から SwapFree を引いた値が MemAvailable に収まるかを確認し、トラフィックの少ない時間帯に一枚ずつ切る。

RSS がすべてではない

メモリを見るとき最もよく読み違える値が free の free 列だ。free のマニュアルは free を使われていないメモリとしてのみ定義し、used をtotal から available を引いた値として計算すると記す。カーネル側でその available に当たるのが /proc/meminfo の MemAvailable であり、カーネルドキュメントはこの値をスワップせずに新しいアプリケーションを開始するためにどれだけのメモリが利用可能かの推定値と定義し、MemFree と SReclaimable、ファイル LRU リストの大きさ、各ゾーンの low watermark から計算されると記す。見るべき値は free ではなく available だ。

free -h
grep -E '^(MemTotal|MemFree|MemAvailable|Buffers|Cached|Shmem|Slab|SReclaimable|SUnreclaim):' /proc/meminfo

# プロセス一つの内訳 - VmRSS は下の三つの合計だ
grep -E '^(VmRSS|RssAnon|RssFile|RssShmem|VmSwap):' /proc/<pid>/status

# ファイルのように見えてメモリである場所
df -h /dev/shm
  • ページキャッシュはロックされたメモリではない。必要なら回収される。キャッシュが大きくて free が小さく見えるのは正常であり、その状態をメモリ不足として報告すると見当違いの場所を直すことになる
  • 共有メモリと tmpfs は違う。/dev/shm に積まれたものはファイルのように見えるがメモリであり、キャッシュのようには回収されない。カーネルドキュメントは Shmem を共有メモリと tmpfs が使う総量と定義する
  • カーネルスラブもメモリを使う。SReclaimable は回収されうる部分、SUnreclaim はメモリ圧迫でも回収されない部分だ。後者が大きく増えていれば、ユーザ空間をいくら漁っても答えは出ない
  • RSS は合算してはいけない。カーネルドキュメントによれば VmRSS は RssAnon、RssFile、RssShmem の合計だが、共有ライブラリのように複数のプロセスが一緒に使うページがプロセスごとに数えられる。プロセス別 RSS を足してノードの使用量を推定すると実際より大きくなる
  • ファイルを掴んでいるプロセスもメモリとして計上される。削除されたのに開かれたままのファイルや大きなマッピングを抱えているプロセスを探す方法はどのプロセスがこのファイルを掴んでいるのかにまとめてある

OOM は症状であって原因ではない

OOM キリングはメモリが不足したという事実を伝えるだけで、なぜ不足したのかは伝えない。そしてなぜ不足したのかは、死んだ瞬間のスナップショットではなくその手前の区間の形に入っている。死んだ時点の値はすでに全部大きくなった後なので、原因と結果が区別できない。症状は一つなのに原因は複数あり、順番を決めて切り分ける必要があるという点で、ディスクは空いているのに No space left on device と同じ種類の問題だ。

  • リーク — 時間に比例して上がる。再起動した後も同じ傾きでまた上がる。トラフィックのない深夜にも上がるならほぼ確定だ
  • リクエストの急増 — 階段状に上がり、トラフィックのグラフと時刻が重なる。ピークが過ぎれば下がる。下がらなければ急増とリークが重なっている
  • 上限設定のミス — デプロイ直後から始まる。前回のデプロイとマニフェストを並べれば数分で終わるので、順番として前に置く
  • 上限のないキャッシュ — ヒット率は良くなり続けメモリは際限なく上がる。低負荷では見えず、負荷が増えたときに一気に破裂する。最大項目数や最大バイト数が掛かっているかをまず見る
  • 結果セットが大きくなる — ページネーションのない照会、関連データを一件ごとに読み直して膨らんだ一覧。コードは変わっていないのにある日破裂する類はたいていこれで、傾きが緩やかなので見落としやすい
  • 並行度の数値 — リクエストあたりのバッファサイズ掛ける同時リクエスト数だ。ワーカ数やコネクションプールを上げた翌日に破裂する。デプロイ履歴ではなく設定変更の履歴から探さなければならない
  • 隣人 — システム OOM なのに自分のプロセスが選ばれた場合。原因は同じノードの別のワークロードで、こちらは単に図体が大きかっただけなので、自分のコードをいくら見ても何も出てこない
  • ノードの他の消費者 — ログ収集デーモン、バックアップエージェント、カーネルスラブのようなコンテナでないもの。Pod 使用量の合計とノード使用量が大きく開いていればこちらだ

切り分けに最も役立つ一つを選ぶなら傾きの形だ。直線か階段かのこぎりかを見るだけで候補の半分が落ちる。だから事後調査で真っ先に確保すべきはログではなく死ぬ前の数時間のメモリ時系列である。これがなければ調査は推測になる。

防ぎ方 - 上限とリクエスト、そして再起動ループ

上限を掛けることは必要だが、それだけでは足りない。スケジューラはリクエスト値を見て配置を決めるので、リクエスト値がないか実際よりはるかに小さいと一つのノードに過密配置が起こる。するとコンテナごとの上限は守られるのにノード全体が先に崩れる。Kubernetes のドキュメントは、ノードが資源を使い切ると BestEffort の Pod をまず、次に Burstable、最後に Guaranteed を追い出すと記す。リクエストと上限をどう書いたかが追い出しの順番を決める。

  • 上限とリクエストを一緒に掛ける。上限だけならスケジューラが実消費を知らず、リクエストだけなら暴走を止められない
  • リクエスト値は平常の使用量、上限はピークに余裕を足した値から出発する。二つを同じにすると等級は上がるがノードの利用率が下がる
  • 上限の引き上げは時間を買う措置だ。リークなら周期が延びるだけ。買うと決めたならいつまで買うのかをチケットに書く。書かなければその上限は恒久になる
  • readiness がなければ再起動直後が危ない。ウォームアップ中のインスタンスにトラフィックが入り、その負荷がまたメモリを押し上げる
  • liveness が過度に攻撃的だと OOM でない死が混ざる。少し止まったのを死んだと見て再起動させる場合だが、こちらは SIGTERM なので 143 だ。137 と 143 が混ざっているなら二つの事件を一つとして見ている
  • 終了猶予を超えると 143 ではなく 137 になる。同じ 137 でもカーネルログにその時刻の OOM 記録がなければこちらだ
  • レプリカを増やす対応は原因によって分かれる。リクエストが分散する種類なら効くが、インスタンスごとに同じキャッシュを一つずつ増やす構造ならノードの総量はむしろ増える
  • 多プロセスのコンテナは memory.oom.group を検討する。一つだけ死んで残りが残れば、コンテナは生きているのに機能は半分になり、この状態は再起動でも整理されない

再起動ループへ広がる順番はたいていこうだ。死ぬ。再起動する。ウォームアップ中に溜まったリクエストを一度に受ける。また死ぬ。オーケストレータが再起動間隔を徐々に広げるので、最初の数分は連続して死に、その後は断続的に死ぬ。この後半を「断続的な障害」と呼んだ瞬間、原因から遠ざかる。再起動間隔が指数的に広がる形かどうかを確認すれば、同じ事件かどうかがすぐ分かれる。

危険表示。メモリ上限をそもそも無くすのは問題を無くすことではなく、cgroup OOM をシステム OOM へ格上げすることだ。上限があれば死ぬ対象はそのコンテナに限られるが、上限を無くせばカーネルがノード全体から候補を選ぶ。そのとき選ばれるものはこちらで決められず、無関係なワークロードまで一緒に揺れる。

点検の順番

順番を決めておく理由は、段階ごとに次の段階が絞られるからだ。前のものを飛ばすと後のものを見ても解釈できない。

  1. 本当に死んだのかを確認する。終了コードが 137 か 143 か、0 から 125 の間か。コンテナなら前回の終了の理由とコードを一緒に見る。143 や正常終了が出れば OOM の調査は畳む
  2. カーネルが殺したのかを確認する。同じ時刻にカーネルログへ OOM の記録があるか。なければリングバッファが流れたのかをまず確認し、流れていなければカーネルではなくオーケストレータか監視者か人だ
  3. システムか cgroup かを切り分ける。ログの先頭が Out of memory か Memory cgroup out of memory か。コンテナ側では memory.events の oom_kill が増えたかを見る。ここで対応の方向が完全に分かれる
  4. 誰が増えたのかを見る。カーネルが残した表を rss で並べ替える。死んだプロセスが一位でなければ oom_score_adj 列を、一位なら rss_anon と rss_shmem の比重を見る
  5. いつから増えたのかを見る。死ぬ前の数時間の時系列を確保する。直線か階段かのこぎりかがここで決まる
  6. なぜ増えたのかを突き合わせる。デプロイ時刻、設定変更の履歴、トラフィックのグラフ、データ増加量を時系列の上に重ねる。重なるものが一つならほぼ答えで、なければ一層下(キャッシュ上限、結果セットの大きさ、並行度)を見る
  7. 何を変えるかを決める。上限の引き上げは最後の選択肢だ。その手前にキャッシュ上限、ページサイズ、ワーカ数、コネクションプールがある。上げると決めたならどれだけ長くその状態に置くのかも併せて書く

まとめ

アプリケーションログが空なのは情報がないという意味ではなく、記録の主体が変わったという意味だ。SIGKILL は捕捉できないのでアプリケーションは何も書けず、その事件はカーネル側に残る。調査の出発点がアプリケーションログを掘ることではなく、終了コードを確認してカーネルログへ移ることである理由だ。

移った後の分かれ道は一つだ。ノードが不足したのか、上限に達したのか。ログの最初の単語がこれを教えてくれ、ここで対応が完全に変わる。ノードの問題に上限をいじったり、上限の問題にノードを増設したりするのは、どちらも何も変えない。そしてどちらであれOOM 自体は原因ではない。原因は死ぬ前の数時間の傾きの中にあり、その傾きは事件が終わった後には確保できない。だから残すべきはコマンドの一覧ではなく順番だ。死んだのが本当か、カーネルが殺したのか、システムか cgroup か、誰が増えたのか、いつから、なぜ。この六つを順に通れば、最後の問いにはたいてい答えが一つしか残らない。

  • ログファイルのパスはディストリビューションとログデーモンの設定によって違う。/var/log/messages と /var/log/syslog のどちらが使われるかは確認できなかった
  • コンテナランタイムが終了コード 137 を付ける正確な規則は公式ドキュメントで確認できなかった。128 足すシグナル番号はシェルの規則としてこの環境で確認したものであり、ランタイムが同じ規則に従うという文書上の根拠は見つからなかった。Bash マニュアルの当該条項も gnu.org がレート制限で応答せず原文を開けなかった
  • Kubernetes の QoS ドキュメントは追い出しの順番だけを説明し、oom_score_adj を等級別にどう設定するかには触れていない。本文で「オーケストレータが設定することもある」以上に書かなかった理由だ。systemd-oomd のようなユーザ空間で動く OOM 管理者も扱っていない
