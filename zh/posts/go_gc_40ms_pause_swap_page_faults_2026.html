本文将Fernando Simões的《A 40ms Go GC pause caused by swap》（2026年9月13日，含9月14日更新）与仓库go-gc-swap-cost中的bpf/stw.bt、Go 1.26发布说明以及Go博客的Green Tea文章对照整理而成。

问题提出——启用交换空间的环境中观测到的40ms停顿

原文源于作者的一次经历：为了吸收内存突增而决定在生产环境使用交换空间，差点拍额头后悔。作者说写这篇文章是为了让读者不必重蹈覆辙。实验结构很简单：一个cgroup里放两个进程。一个是调用io.ReadAll后再调用proto.Unmarshal、生成blob和图结构体的Go进程，图结构体是Go分配器标记为scan的对象。另一个是大部分时间保持安静的HTTP服务器。

作者最初的预期是这样的。收集器每次运行都会逐个指针地读取这些scan span，并决定如何处理。内存压力出现时，内核会把页面换出到交换设备，但换出是按cgroup而不是按进程进行的，所以两个进程的页面会一起被换出。因此内核与垃圾回收器之间陷入换入换出的悲伤循环的可能性很小。作者随后写道，这个预期是错的。

实验中发现的问题是：Go的垃圾回收器会在世界停止（stop-the-world）的区间读取位于堆外、且不会被释放的区域中的元数据，而这些元数据可能在交换空间里。作者在启用MGLRU、内核6.8的Hetzner服务器上做了模拟运行，停顿时间中位数约为51µs，当元数据位于NVMe上时，最坏的停顿为40ms。

  • 中位数与最坏值：中位数约51µs，最坏值40ms（详细测量值39,902µs）。原文写40ms是中位数的800倍。直接用39,902除以51约得782倍（计算）。
  • 测量条件：最坏值按原文的说法是「元数据位于NVMe上时」的数值。测量51µs中位数时是否正在使用交换空间，原文没有明确说明。
  • 全局停顿：由于所有P都停止，例如原本在等待I/O的goroutine，其I/O在停顿期间完成返回时，也没有主体来处理。

原文还提到，在测试中每次内存突增时这样的停顿会重复两三次。

STW的两个时间点与发生缺页的GC内部调用位置

根据原文，Go GC要在两个时间点停止世界：执行清扫终止（sweep termination）时和执行标记终止（mark termination）时。在作者的实验中，30分钟内出现了312次这样的停顿。

作者写了一个小型bpf脚本，统计世界停止期间的缺页次数。最坏的一次输出如下：停顿39,902µs，期间缺页228次，缺页内花费39,013µs。作者将其概括为「40ms中有39ms花在了228次缺页上」。这些缺页发生在GC的账目处理（bookkeeping）内部，原文用addr2line输出给出了十行调用位置。

  • runtime.(*spanSet).reset — internal/runtime/atomic/types.go:194
  • runtime.finishsweep_m — mcentral.go:71，另一条栈中为mgcsweep.go:268
  • runtime.gcStart.func2 — mgc.go:724
  • runtime.systemstack — asm_amd64.s:518
  • runtime.gcStart — mgc.go:722
  • runtime.nextMarkBitArenaEpoch — mheap.go:2481

这十行可以读成两条各五帧的栈。一条从spanSet.reset开始，另一条从nextMarkBitArenaEpoch开始，两条都经过finishsweep_m、gcStart.func2、systemstack、gcStart。这与仓库脚本用ustack(5)捕获五帧相吻合。原文没有说明各函数的作用，也没有说明这些调用位置对应哪个STW时间点，因此本文也只写到名称和位置为止。

原文说明的内核路径——从换出到主缺页

原文给出的理由是这样的。运行时分配了这些页面。它们不会被释放，而是被重复使用。并且它们在GC周期中被读取。内核按年龄换出页面，所以会把最久没有被访问的页面送入交换空间。GC停止世界并试图读取这些页面时，它们已经在交换空间里，于是发生主缺页。

作者以「长话短说」的方式列出了一次缺页的处理过程：内核读取PTE，调用do_swap_page，找一个新的页框，把它计入cgroup，提交bio来读取页面，等待磁盘，再把它们放回内存。原文在这些步骤旁边附上了指向Linux 6.8源码（mm/memory.c、mm/swap_state.c、mm/page_io.c）相应行的链接。

  • 换出标准：访问时间。最久没有被访问的页面先被送入交换空间。
  • 换出单位：在作者的前提中是cgroup而不是进程，所以连安静的HTTP服务器的页面也处在同样的压力之下。
  • 元数据的访问模式：按原文的说法，这些页面在GC周期中被读取，也就是说在两个周期之间可能没有被触碰过。
  • 一次缺页的成本：由于上面的列表以等待磁盘结尾，在原文的最坏情况中，228次缺页发生在一次停顿之内。

同样是缺页，发生的位置不同，影响范围也不同。作者在谈到构建511 KiB消息的goroutine的延迟时写道，这个成本只由执行分配的goroutine承担，所以是局部的，不像元数据停顿那样是全局的。相反，元数据缺页发生在世界停止期间，所有P一起等待。

实验环境与bpftrace脚本——stw.bt全文

原文的模拟运行是在启用MGLRU、内核6.8的Hetzner服务器上进行的。图表、模拟分配器、bpf脚本、Python脚本等实验的全部内容都在仓库go-gc-swap-cost中。观测持续30分钟，其间STW出现了312次。下面是该仓库bpf/stw.bt的全文，连同注释原样抄录。

// BIN: path of the Go binary as seen by bpftrace, e.g. /proc/<pid>/root/tmp/pagefault
                    // both processes run the same binary, so everything is keyed by pid: a fault counts only
                    // against a pause of its own process
                    uprobe:BIN:runtime.stopTheWorldWithSema /comm == "pagefault"/ {
                      @stw_start[pid] = nsecs; @stw_faults[pid] = 0; @stw_fault_ns[pid] = 0;
                    }
                    uprobe:BIN:runtime.startTheWorldWithSema /@stw_start[pid]/ {
                      $d = (uint64)(nsecs - @stw_start[pid]);
                      @stw_us = hist($d / 1000); @stw_n[pid] = count(); @stw_ns[pid] = sum($d);
                      printf("stw t=%d pid=%d %d us, faults during it %d, %d us in faults\n",
                             elapsed / 1000000, pid, $d / 1000, @stw_faults[pid], @stw_fault_ns[pid] / 1000);
                      delete(@stw_start[pid]);
                    }
                    // swap-in and file-backed faults both: the binary's own code pages can be evicted too
                    kprobe:do_swap_page, kprobe:filemap_fault /comm == "pagefault" && @stw_start[pid]/ {
                      @f_start[tid] = nsecs; @stw_faults[pid]++; @stw_stack[ustack(5)] = count(); // five frames reach gcStart
                    }
                    kretprobe:do_swap_page, kretprobe:filemap_fault /@f_start[tid]/ {
                      @stw_fault_ns[pid] += (uint64)(nsecs - @f_start[tid]); delete(@f_start[tid]);
                    }
                    END { clear(@stw_start); clear(@f_start); clear(@stw_faults); clear(@stw_fault_ns); }

脚本的结构分四部分。第一，挂在stopTheWorldWithSema上的uprobe按pid记录起始时间，并把缺页次数和缺页耗时清零。第二，挂在startTheWorldWithSema上的uprobe计算停顿时间$d并放入微秒直方图，把停顿时间、缺页次数、缺页耗时输出为一行，然后删除该pid的起始时间。第三，kprobe在进入do_swap_page和filemap_fault时记录时间戳，增加缺页次数，并用ustack(5)汇总调用栈。第四，kretprobe在这两个函数返回时把经过的时间累加到缺页耗时上。

脚本的注释说明了两件事。一是两个进程运行同一个二进制文件，所以所有值都按pid区分，使缺页只计入自己进程的停顿；二是换入缺页和文件映射缺页都会被统计，因为二进制文件自身的代码页也可能被换出。读过脚本就能知道，原文的228次是do_swap_page与filemap_fault调用次数之和。

  • 观测：30分钟内STW共312次。
  • 最坏情况：停顿39,902µs，缺页228次，缺页处理合计39,013µs。
  • 缺页的占比：39,013 ÷ 39,902 ≈ 97.8%（计算）。原文自己的表述是「40ms中的39ms」。
  • 缺页之外的时间：39,902 − 39,013 = 889µs（计算）。原文没有给出这段时间的明细。
  • 重复：在测试中，每次内存突增会出现两三次这样的停顿。

消息构建延迟——由分配goroutine独自承担的成本

作者还注意到另一件事。构建一条511 KiB的消息通常需要3到5ms，当交换空间在NVMe上时升到了105ms，在Hetzner的网络卷上时升到了903ms。作者写道，按每条消息计算，这个成本比元数据停顿还大。不过只有执行分配的goroutine要付出这个代价，所以至少是局部的，不像元数据那样是全局的。

  • 范围：延迟只限于执行分配的goroutine。与全局STW不同，它不会让其他P停下来。
  • 介质差异：903ms相对于105ms约为8.6倍（903÷105，计算）。
  • 时间明细：作者亲自说明，尚未确认这段时间花在了哪里。

作者把这一项写进文章的理由是，这是「你可能还要付出的另一项成本」。因此本文也不把消息构建延迟当作与STW缺页相同机制的结果。

Green Tea GC的复测与Go官方说明

原文9月14日的更新很短。有人问Go 1.26的Green Tea垃圾回收器是否改变了GC读取元数据的方式，作者测量后发现影响可以忽略（negligible）。测量环境和数字没有公布。

Go官方资料这样描述Green Tea。据Go博客（2025年10月29日），核心思想是「以页面而不是对象为单位工作」。它不再扫描对象而是扫描整个页面，工作列表里跟踪的也不是对象而是整个页面，已标记的对象则在每个页面内部局部跟踪，而不是在整个堆范围内跟踪。在Go中，页面大小为8 KiB，与硬件虚拟内存页大小无关。

  • Go 1.25：通过GOEXPERIMENT=greenteagc启用的实验功能。博客写道，许多工作负载花在垃圾回收上的时间减少约10%，有些最多减少40%。
  • Go 1.26：据发布说明，原为实验功能的Green Tea已默认启用，通过更好的局部性和CPU可扩展性改进小对象的标记与扫描。对大量使用垃圾回收的真实程序，预计GC开销减少10%到40%（Go官方数字）。
  • 进一步改进：在较新的amd64 CPU（Intel Ice Lake、AMD Zen 4及更新）上，扫描小对象时使用向量指令，预计GC开销还能再减少约10%。
  • 关闭方式：可在构建时用GOEXPERIMENT=nogreenteagc关闭，预计该设置将在Go 1.27中移除。

10%到40%是针对GC的CPU开销的基准测试预期，而原文的问题是STW期间读取元数据时发生的缺页。两者测量的对象不同，不能用一方的数字推断另一方。本文确认到的只有一句话：作者测得Green Tea对元数据读取的影响可以忽略。

原文的结论与阅读时的注意事项

原文的结论是一句半话。作者同意Chris Down的观点，认为交换空间并不是坏东西。但是交换空间与垃圾回收配合得不好，作者还补充说自己的生产环境会进行大量回收。原文中没有关闭交换空间的建议，也没有修改任何设置的建议。

  • 作者直接确认的：世界停止期间发生了元数据缺页，并且存在该缺页占停顿大部分的案例。
  • 作者写明未确认的：511 KiB消息构建延迟中的时间明细。
  • 作者只简短提及的：Green Tea的复测只给出了结果，没有数字。
  • 原文中没有的：运维建议、设置值，以及在其他环境中的复现。

从这个案例只能谨慎地得出一般性的教训：即使在停顿很短的区间，如果该区间读取的内存在交换空间里，磁盘延迟就会直接叠加到停顿上。这在哪些生产环境中、以多高的频率发生，原文没有回答。

未能确认的内容

  • 测量51µs中位数时的条件。是否为使用交换空间时的数值，原文没有明确说明。
  • 构建511 KiB消息所花的105ms和903ms的时间明细。原文作者也写明没有确认时间花在哪里。
  • 元数据位于网络卷时的STW最坏值。原文只给出了NVMe情形的40ms。
  • Green Tea GC复测的数字和运行条件。原文只写了影响可以忽略。
  • 在Hetzner服务器以外的环境以及内核6.8以外的内核上的复现结果。
  • 228次缺页中，换入缺页（do_swap_page）与文件映射缺页（filemap_fault）的比例。脚本把两者合并统计。
