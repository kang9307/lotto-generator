Postgresを複数台に分割するという選択 - 水平スケーリングがトランザクション・結合・制約に請求する対価

単一ノードで自明だった関係モデルの機能が複数サーバーに分散する際に払うコストと、シャーディング前の点検順序

2026-09-12 開発・インフラ

リレーショナルデータベースを運用する組織において、トラフィックとデータ量が膨張した際、エンジニアが最初に思い浮かべる言葉は水平スケーリングである。Webサーバーやアプリケーションコンテナを増設するように、データベースも複数台のノードに分割すれば書き込み処理量とストレージ容量が線形に伸びると期待しがちだ。実際、NoSQLや分散キーバリューストアはそのような設計思想でスケールする。しかし、PostgreSQLは本質的に単一ノードの強固な関係モデルとして磨き上げられてきたエンジンである。

単一インスタンスで完璧に動作していたデータベースを複数の物理マシンに切り分けた瞬間、これまで当たり前に享受してきた数々の機能が静かに損なわれ、あるいは巨額のアーキテクチャ的請求書となって跳ね返ってくる。単一メモリ空間で即座に検証されていた不可分なトランザクションはネットワーク通信を経由する分散合意へと変貌し、超高速なハッシュ結合は帯域を食いつぶすデータ転送処理へと成り下がる。テーブル単位で一意性を保っていたインデックスや自動採番シーケンスは、大域的な衝突の火種へと変わる。

この記事は特定の分散ツールや製品を賞賛あるいは非難するために書かれたものではない。1台のマシンで完結していた処理がネットワーク境界を跨ぐ瞬間、構造的に何が壊れ、何を諦める必要があり、どのような代替手段を組まねばならないのかを冷静に解剖する。その上で、シャーディングという極めて危険で後戻りのできない河を渡る前に、単一インスタンス内で必ず試し切るべき最適化手順を整理する。

本稿で扱う分散トランザクションの限界、2相コミット（2PC）の制約、テーブルパーティショニングの仕様はPostgreSQL 17の公式マニュアルの記述に基づく。また契機として触れるMultigresのアーキテクチャや制約事項は、同プロジェクトの公式リポジトリREADMEおよび技術文書が自ら明かしている内容に限定し、原文にない性能数値やスループットは一切記載しない。

発端 - Postgresの水平スケーリングを掲げたオープンソースの登場

2026年9月初旬、技術コミュニティにおいてMultigresというプロジェクトが発表された。MySQLエコシステムにおいて大規模水平分割のデファクトスタンダードとして知られるVitessのアーキテクチャを、PostgreSQLへと持ち込もうとするオープンソースの試みである。このプロジェクトの骨子は、PostgreSQL本体のコードを改変して独自の派生データベースを作るのではなく、標準のPostgreSQLインスタンス群の前段にプロキシ、コネクションプーラー、オーケストレーターを階層配置して水平拡張を実現しようとする点にある。

公開リポジトリおよび公式ドキュメントから確認できる客観的事実は次の4点に要約される。

  • 何を行う構造か — アプリケーションとデータベースの間に多層プロキシを配置する。上位層のMultigatewayはPostgreSQLサーバーとして振る舞い、クエリを適切なノードへルーティングし分散結合を調停する計算層である。下位層のMultipoolerは各PostgreSQLインスタンスに1対1で常駐し、セッション状態の保持と接続プーリングを担う。Multiorchはレプリケーション監視、自動フェイルオーバー、WALのクォーラム同期を統括する。
  • 何を要求するのか — 関連するテーブルと行を同一シャード内に物理的に集約する関係モデル型のシャーディング設計を前提とする。これにより分散結合や分散トランザクションを最小化するためである。複数シャードに跨がるトランザクションが避けられない場合は、PostgreSQL標準の2相コミット（2PC）プロトコルを利用する設計となっている。
  • 文書自らが明かす現在の限界 — 2026年6月に最初のアルファ版が公開された初期段階にある。現在の公開リリースには接続プーリング、自動フェイルオーバー、バックアップ、Kubernetes Operatorのみが含まれており、核心であるシャーディング機能そのものは未だ公式リリースに含まれておらず開発計画の段階である。またプーラー層を経由する際、CREATE DATABASEや外部データラッパ（FDW）、一部の動的SQLが制限されると明記されている。
  • 本番稼働に対する原文の見解 — プロジェクトの公式文書は現在のフェーズをテストおよび実験目的のアルファ版と位置づけており、本番環境での利用を推奨しないと明確に述べている。

この取り組みは、技術者に根本的な問いを投げかける。大掛かりな調停レイヤーを設けてまでPostgreSQLを複数台に分割すべきタイミングとはいつであり、その選択によってシステムが支払う真の代償とは何か、という点である。

垂直スケーリングが最初に突き当たる物理的限界

データベースの負荷が増大した際、最も安全で確実な選択肢は垂直スケーリング（スケールアップ）である。単一のマシンに対してより多くのCPUコア、数百ギガバイトのメモリ、そして数万IOPSを誇るエンタープライズNVMeストレージを投入する手法である。垂直スケーリングであればアプリケーションのコードやSQLを変更する必要は一切なく、リレーショナルエンジンが提供する完全なACID保証、インデックス、制約を保ち続けることができる。

実のところ、現代における大半のサービスは垂直スケーリングだけで十分に運用を維持できる。最新のクラウドインスタンスは単一ノードで数百規模のvCPUとテラバイト単位のメモリを提供する。適切なインデックス設計と参照用レプリカ（Read Replica）の活用を組み合わせれば、毎秒数万件のトランザクションを安定して処理可能である。しかし、それでも垂直スケーリングが物理的に壁に突き当たる瞬間が存在する。

  • 単一プライマリの書き込み限界 — 参照トラフィックはレプリカを増設して分散できるが、データの挿入・更新・削除は必ず単一のプライマリノードを通過しなければならない。書き込みはWAL（先行書き込みログ）の同期書き込み、共有バッファのダーティページ排出、行ロックの競合を伴うため、単一マシンのストレージ帯域と同期処理の限界に達した時点でスケールアップは停止する。
  • メンテナンス窓とVACUUM負荷の爆発 — 単一ノード内のデータが数十テラバイトに達すると、内部メンテナンスが深刻なリスクへと転じる。PostgreSQLの追記型MVCCは不要行を回収するためにVACUUMを必要とするが、テーブルが巨大化するとautovacuumがディスクI/Oを占有し、サービスの応答速度を著しく低下させる。巨大なB-treeインデックスの再構築（REINDEX）も極めて長時間を要する。
  • 単一障害点（SPOF）と復旧時間（RTO）の増大 — 単一ノードの規模が大きくなるほど、ハードウェア障害発生時のクラッシュリカバリとWAL再生にかかる時間は跳ね上がる。フェイルオーバーを実施しても、膨大なバッファプールが冷え切った状態（コールドキャッシュ）から直ちにピークトラフィックを捌き切ることは極めて難しい。
  • ハードウェア費用の指数関数的急騰 — サーバーのスペックは一定の閾値を超えた途端、価格曲線が跳ね上がる。上位スペックほどコストは仕様に比例せず、より急峻に上がる。具体的な倍率はベンダーと時期によって異なるため、実際の見積もりで確認する必要がある。

このように、書き込み飽和、メンテナンス限界、リカバリ遅延が同時に臨界点へ達した時、アーキテクトは初めてデータベースを複数台に分割する水平スケーリングの検討へ追い込まれる。

垂直スケーリングと水平スケーリングの構造的比較

垂直スケーリングと水平スケーリングの違いは単なるサーバー台数の増減ではない。システムの動作原理と前提条件を根本から交換する選択である。両者の構造的な相違点は次の通りである。

比較項目 垂直スケーリング（Scale-up） 水平スケーリング（Sharding / Scale-out） 実務的な意味合い
拡張の軸とリソース 単一ノードのCPU・RAM・NVMeスペック増設 独立した複数ノードへのデータ分散配置 水平スケーリングは内部通信媒体として物理ネットワークを導入する。
SQL互換性と機能 100%完全なPostgreSQL機能をそのまま利用 結合・トランザクション・DDLに部分的な制約が発生 水平スケーリングはアプリケーション側のクエリ書き換えを強制する。
トランザクション保証 エンジン内部のローカルACID（WALおよびMVCC） シャードを跨ぐ2相コミット（2PC）または結果整合性 分散トランザクションは通信遅延とロック保持時間を劇的に増大させる。
運用の複雑性 単一インスタンスの監視とシンプルなバックアップ ゲートウェイ、プーラー、ノード別オーケストレーション 管理すべきプロセスと潜在的な障害点が倍数で増殖する。
書き込み限界の突破 単一マシンのハードウェア上限に縛られる シャーディングキーに基づいて書き込みを複数台へ分散 超巨大な書き込みトランザクションを捌くための唯一の突破口となる。
障害の影響範囲 プライマリ障害がドメイン全体へ波及 理論上は特定シャードの障害を局所化可能 部分障害がクラスタ全体の連鎖停止を引き起こさない設計が求められる。

上記が示すように、水平スケーリングは書き込みの限界を打破できる強力な選択肢である一方、単一ノードが提供してきた関係モデルの統一された抽象化を解体する。

分割した瞬間に変わるもの - 単一ノードで自明だった仕組みの崩壊

エンジニアがPostgreSQLを選ぶ最大の理由は、その信頼性と表現力豊かな関係モデルにある。外部キーによって親子レコードの整合性が保証され、複雑な変更処理は単一トランザクション内で例外時に巻き戻される。数行のJOIN句を書くだけで複数テーブルがミリ秒で結合され、SERIAL型が重複のない一連番号を滞りなく払い出す。

しかし、データベースを複数台に分断した瞬間、これらの前提は一斉に崩壊する。分散された環境では、異なる物理マシンに存在するテーブル間のメモリポインタを直結することはできず、異なるディスクのWALへ単一のアトミック操作で書き込むこともできない。1台のコンピュータ内部でCPUキャッシュとメモリバスを通じて行われていた通信が、スイッチとネットワークケーブルを通過するTCPパケットへと置き換わるからである。

マイクロ秒単位で完了していたロック獲得やインデックス探索は、ネットワークの往復遅延（RTT）が介入することでミリ秒単位へと千倍近く遅延する。速度が千倍遅い環境において、単一マシン前提の直列化やロック機構をそのまま維持することは不可能だ。水平スケーリングとは、関係モデルの基盤的機能を一つずつ手放すか、分散システム用の代替部品と交換する厳しい取引に他ならない。

トランザクション境界 - シャードを跨ぐ2相コミットと原子性の代償

水平分割によって最も深刻な打撃を受けるのがトランザクションの原子性（Atomicity）である。処理対象のデータが同一シャード内に完結している限り、そのノードのローカルエンジンが以前と変わらずACIDを担保する。問題は、1つの論理的ビジネス処理が異なるシャードに点在する複数のデータを同時に更新しなければならない場合に生じる。

この課題に対する古典的な解法が2相コミット（2PC, Two-Phase Commit）である。外部コーディネーターが関与する全シャードに対してコミットの準備が整ったかを問い合わせる準備（Prepare）フェーズを経て、全ノードから承認を得た後に確定（Commit）フェーズを実行する。PostgreSQLはエンジン標準の構文としてPREPARE TRANSACTIONおよびCOMMIT PREPAREDを提供している。

-- 分散トランザクション環境におけるPostgreSQLの2相コミット（2PC）実行フロー
-- [フェーズ1: ローカルでトランザクションを開始し変更を実行]
BEGIN;
UPDATE user_balance SET balance = balance - 10000 WHERE user_id = 42;

-- [フェーズ2: コミット準備 - セッションから切り離し状態をディスクへ永続化]
PREPARE TRANSACTION 'tx_shard1_user42_20260912';

-- 外部コーディネーターが他シャードの準備完了を確認した後にコミットを指示
-- [フェーズ3: 大域的コミットの確定実行]
COMMIT PREPARED 'tx_shard1_user42_20260912';

-- いずれかのシャードで障害が発生した場合は大域的にロールバック
-- ROLLBACK PREPARED 'tx_shard1_user42_20260912';

この2PCプロトコルは論理的には整合性を保てるが、運用環境においては極めて重大な性能低下と可用性の危機を招く。PostgreSQL 17の公式マニュアルは、PREPARE TRANSACTIONに関して以下の痛烈な警告を記している。

  • max_prepared_transactionsの有効化義務 — デフォルト設定値は0（無効）である。外部トランザクションマネージャーが厳密に管理しない限り、誤って残存したトランザクションがシステムを破壊するのを防ぐため、0のままにしておくことが強く推奨されている。
  • ロック（Lock）の無期限保持 — トランザクションがPREPARE状態に入ると、クライアント接続が切断されても、そのトランザクションが取得した行ロックやテーブルロックは解除されずディスクに残り続ける。コーディネーターの障害やネットワーク分断で確定指示が届かなければ、他のすべてのセッションがそのデータへアクセスできず永久にブロックされる。
  • VACUUMによる不要行回収の完全停止 — 準備されたトランザクションは、それが生成された時点のトランザクションID（XID）を固定してしまう。結果としてVACUUMプロセスが古い不要タプルを掃除できなくなり、テーブルが異常に肥大化（Bloat）する。
  • XID周回（Wraparound）に伴う強制シャットダウン — 準備状態のトランザクションが放置されたまま通常のトランザクションが進むと、XIDの枯渇が進み、データベースはデータ消失を防ぐために最終的に強制停止（緊急シャットダウン）に至る。

この物理的オーバーヘッドゆえに、Multigresのような最新の水平分割ツールであっても「最適なシャーディング設計によって2PCを極力回避せよ」と繰り返し説いている。実務においては、複数シャードに跨がる分散ACIDトランザクションは事実上のアンチパターンであり、非同期なSagaパターンによる結果整合性を受け入れるか、単一シャード内へ更新を閉じ込める設計が求められる。

結合演算 - データ配置とネットワーク往復のボトルネック

単一のPostgreSQL環境におけるテーブル結合は、オプティマイザがネステッドループ結合、ハッシュ結合、マージ結合から最適な実行計画を選定し、ローカルメモリ内で極めて高速に完結する。

しかし、データが10台のシャードに分散された環境でordersテーブルとusersテーブルを結合する場合、その挙動はデータの配置構造によって決定づけられる。

  • コロケーション結合（Collocation Join） — ordersとusersが同一のキー（例: user_id）でシャーディングされ、同一ユーザーのレコードが同一のPostgreSQLノードに同居している場合である。ゲートウェイは結合クエリ全体を個別のシャードへそのままプッシュダウンし、各シャードがローカルのデータだけで結合を終えて結果を返すため、ネットワーク転送コストは発生しない。
  • ブロードキャスト結合（Broadcast Join） — 都道府県マスターや商品分類コードのように、容量が小さく更新頻度が極めて低いテーブルを結合する際に用いられる。参照テーブルの完全なコピーを全シャードに事前に複製配置しておくことでローカル結合を可能にするが、マスターデータの更新時に全ノードへ書き込み負荷が波及する。
  • スキャッター・ギャザー結合（Scatter-Gather Cross-shard Join） — 最も避けるべきケースである。結合対象のテーブル同士が異なるキーで分割されている場合、プッシュダウンは不可能となる。ゲートウェイは関係する全シャードへクエリをばら撒き（Scatter）、膨大な中間データをネットワーク越しに回収（Gather）して、ゲートウェイ自身のメモリ上でハッシュテーブルを構築して結合しなければならない。

スキャッター・ギャザー結合が発生した瞬間、ネットワーク帯域は逼迫し、プロキシノードのメモリ消費は跳ね上がり、OOM（メモリ不足）による障害リスクが跳ね上がる。水平分割環境では、これまで自由自在に駆使していた複雑なSQL結合を封印し、データを非正規化して冗長保持するか、アプリケーション層で個別取得して組み立て直す苦肉の策が必要となる。

一意制約とシーケンス - グローバル一意性が消失する場所

単一インスタンスにおいてid SERIAL PRIMARY KEYやemail VARCHAR(255) UNIQUEを宣言することは日常的な開発手法である。ローカルのB-treeインデックスが重複データを瞬時に検知し、データの一貫性を保ってくれるからである。

しかし、複数の独立したノードに分かれた環境では、この大域的な一意性が根底から崩れ去る。

  • 単一シーケンスの衝突 — PostgreSQLのシーケンスは単一インスタンス内のメモリ管理下にある。シャード1とシャード2がそれぞれ独立して1から番号を採番すれば、生成された主キーは必然的に重複する。分散環境ではSERIALを廃止し、128ビットのUUIDv7（時間順ソート可能）やSnowflake型（タイムスタンプ＋マシンID＋連番）の分散ID生成機構を導入せざるを得ず、インデックスサイズとストレージを余計に浪費する。
  • シャーディングキーを含まない一意制約の不可能性 — これは単一ノード内の宣言的パーティショニングでも水平シャーディングでも共通する根本的な制約である。PostgreSQL 17の公式文書はこう明記している。「パーティションテーブルに一意制約または主キー制約を作成するには、制約のカラムにすべてのパーティションキーを含めなければならない。なぜなら、個別のインデックスは自分自身のパーティション内の一意性しか直接強制できないからである」。
  • 大域的一意性の検証コスト — ユーザーをuser_idで分割した状態でemailカラムに一意制約をかけたい場合、データベースエンジン単体ではこれを防ぐ手段が存在しない。シャード2で新しいメールアドレスをINSERTする際、シャード2はシャード1のローカルインデックスを覗き見ることができないためである。これを防ぐには専用のグローバル参照インデックスを設けて事前検証するか、Redis等の外部分散ロックに依存しなければならない。
  • 書き込みスループットの相殺 — すべてのINSERT操作のたびに大域的一意性を確認するための追加通信が発生するならば、水平スケーリングによって獲得しようとした書き込み性能向上は完全に帳消しになる。

外部キーと分散集約 - 放棄するか代替すべきもの

リレーショナルエンジンのもう一つの象徴である外部キー（Foreign Key）や集約処理（Aggregation）も、水平スケーリングによって過酷な制約を受ける。以下の比較表は、1台で自明だった主要機能がシャーディング時にどのように崩壊し、現場でどのように代替・妥協されているかを整理したものである。

関係モデルの標準機能 単一ノード（Single Node）の動作 水平分割（Sharding）時の現実 現場における代替策・妥協点
原子的なトランザクション（ACID） 単一エンジンのローカルWALとMVCCにより即座に保証 複数シャードに跨がる更新で2PCが必須となり、遅延とロックが激化 同一シャード内の更新に限定するか、Saga等の結果整合性を受け入れる
テーブル間結合（JOIN） ローカルメモリ内のハッシュ／マージ結合によりミリ秒で完了 シャードを跨ぐデータ転送によりネットワーク帯域とプロキシメモリを圧迫 同一キーでのコロケーション配置を徹底するか、非正規化して保持する
大域的一意制約（UNIQUE） ローカルB-treeインデックスで重複行の挿入を瞬時に遮断 シャーディングキーを含まないカラムは別ノードの重複を検知不能 シャーディングキーを一意キーへ合成するか、外部ロックで事前確認する
自動採番主キー（SERIAL） 単一の内部カウンタにより重複のない単調増加連番を自動発行 各ノードが独自に採番するため、同一のID番号が必然的に衝突する UUIDv7やSnowflake等の分散ID生成器、ノード別採番範囲の割り当て
外部キー制約（FOREIGN KEY） 参照整合性およびCASCADE削除をデータベースエンジンが強制 親レコードと子レコードが異なるノードにある場合、参照検証が物理的に不可能 DB層の外部キーを全廃し、アプリケーションロジック側で整合性を管理する
集約とページネーション（GROUP BY / LIMIT） インデックス走査とインラインソートにより即座に結果を抽出 全シャードから大量データを集約してプロキシで再ソート、深層OFFSETで爆発 カーソルベースのページネーション（Keyset Pagination）や事前集約テーブルの活用

特にORDER BY created_at LIMIT 20 OFFSET 10000のような深層ページネーションは分散環境において致命的である。ゲートウェイは10台のシャードすべてに対して先頭10,020件の取得を要求し、合計10万件以上の行をネットワーク経由で吸い上げてメモリ上でソートし直す羽目になる。データベースが提供していた利便性は消滅し、すべてのツケがアプリケーションコードへと回される。

シャーディングキーの変更は極めて困難 - ホットスポットと再シャーディングの重み

水平スケーリングを決断した際、最初に立ちはだかる最大の設計判断がシャーディングキー（パーティションキー）の決定である。シャーディングキーは、各レコードがどの物理シャードへ格納されるかを決定づける番地情報である。選定基準とそれぞれの危険性は以下の通りである。

選定における観点 考慮すべき技術的背景 推奨されるパターン 不適切なパターン（アンチパターン）
カーディナリティ（値の多様さ） 値の種類が十分に多くなければ均等にノードへ分散されない 数百万以上の重複しない識別子（user_id, account_id） ステータス値、性別、国コード等の限定されたカテゴリ値（特定の偏り）
書き込みトラフィックの均等性 特定時点において特定の単一ノードへ書き込みが偏らないこと ハッシュ分割、ランダム性の高い業務エンティティ識別子 日付タイムスタンプ、単調増加ID（最新日付のシャード1台だけが高負荷）
クエリのアクセスパターン 大半の検索WHERE条件にシャーディングキーが含まれていること 業務の起点となる主キー（テナントID、顧客番号） 検索条件にほとんど指定されない内部UUID（毎回全シャード走査）
データ容量の増加傾向 特定キーに紐づくデータボリュームが極端に巨大化しないこと 均一な規模の一般ユーザー、中小型のテナント識別子 超巨大企業が含まれるB2BのテナントID（特定シャードのディスクが枯渇）
キーの不変性（Immutability） キーの値が変更されると、行を別の物理サーバーへ移管しなければならない レコード生成後に二度と変更されない不変のサロゲートキー メールアドレス、所属部署コード、変更可能なユーザー名

シャーディングキーの選定が恐ろしい理由は、一度決定して本番稼働を始めたら、後から変更することが極めて困難だからである。日付単位で分割した結果として最新ノードだけにアクセスが集中するホットスポットが発生したり、テナントIDで分割した結果として1社の大企業顧客がシャードのディスクを埋め尽くす偏りが生じた場合、どう対処すべきか。

取り得る手段は、クラスタ全体のデータを新たなルールに基づいて再配置する再シャーディング（Resharding）のみである。再シャーディングは単なる設定変更ではない。稼働中のテーブルからターゲットシャードへ数十テラバイトのデータをリアルタイムでレプリケーションし、同期差分を追いつかせた上でトラフィックを切り替え（カットオーバー）、万一に備えて逆方向のレプリケーションを敷くという極めて高度なインフラ手術である。Multigresのドキュメントが再シャーディングのワークフローと障害復旧に多くの記述を割いているのもそのためだ。誤った選定は数ヶ月にわたる開発チームの疲弊とサービス障害に直結する。

運用で爆発する作業 - リカバリ・DDL伝播・可観測性

データベースノードが1台から10台へ増えたとき、運用の手間は単に10倍になるのではなく、乗数的に跳ね上がる。単一ノード運用では想定もしなかった新たな課題が次々と噴出する。

運用管理の項目 単一インスタンス（または基本レプリカ構成） 分散シャーディングクラスタ（水平分割） 運用の複雑化を招く主な要因
バックアップと時点復元（PITR） 単一のWALアーカイブを順次再生して指定時刻へ復元完了 各シャードで独立したWALのタイムスタンプが微妙に乖離 分散トランザクション整合性を保ちながらクラスタ全体を同一瞬間に巻き戻すのが極難
スキーマ変更（DDLマイグレーション） 単一トランザクション内でDDLを実行、失敗時は即座にロールバック 多数のシャードへDDLを順次または並列適用、バージョン混在期が発生 一部ノードだけマイグレーションが完了した移行期間を許容するアプリケーションコードが必須
コネクションプーリング管理 pgBouncerを1〜2台置くだけで数千のクライアント接続を保護 ゲートウェイプロキシ＋ノード別Multipoolerによる多層構造 プロキシとプーラーの間でセッション状態の追従オーバーヘッドとメモリ消費が増大
障害検出とフェイルオーバー Patroni等により単一マスターを自動選出しスタンバイを昇格 全シャードが各自のプライマリ・レプリカ構成を持ち、個別合意を形成 ネットワーク分断時に特定シャードがスプリットブレインを起こさないようクォーラム管理が必要
可観測性と性能分析 単一ホストのpg_stat_statementsと基本メトリクスで原因特定 分散トレーシング（Distributed Tracing）と全ノードのログ統合 クエリ遅延がゲートウェイの負荷か、特定シャードの行ロックか、ネットワーク遅延かの判別が困難

とりわけ過酷なのが災害復旧（DR）である。単一のPostgreSQLであれば「昨日の14時15分00秒時点に戻してほしい」という要求は容易に実現できる。単一のWALストリームに確実なタイムスタンプが刻まれているからだ。しかし10台のシャードに分かれた環境では、サーバー間の微小なクロックスキュー（時刻ズレ）や通信ラグが存在するため、完全な一貫性を保った同一スナップショットに全台を巻き戻すことは極めて難易度が高い。分散トランザクションの処理途中の瞬間に復元してしまえば、シャード間のデータ不整合は永久に残る。

水平分割に踏み切る前に必ず経るべき5つの段階

水平スケーリングがもたらす巨大な複雑性と運用上の負債を直視すれば、熟練したエンジニアリング組織がとるべき姿勢は明白である。「シャーディングは誇るべき成果ではなく、あらゆる手段を尽くした後の最終防衛線である。」可能な限り単一ノード内の最適化を極限まで押し進め、シャーディングという選択を遠ざけなければならない。

データベースを複数台に切り分ける前に、以下の5段階を順番にやり切ったかを自問すべきである。

段階 重点的に取り組むべき最適化作業 期待される改善効果 この段階を飛ばした際のリスク
第1段階: クエリとインデックスの徹底整備 pg_stat_statementsによる遅延分析、不要インデックス削除、欠落インデックス追加、N+1撲滅 不要なディスクI/Oの完全排除、CPU使用率の大幅低減 フルスキャンを伴う非効率なクエリをクラスタ全体にばら撒き、問題を何倍にも悪化させる
第2段階: 読み取り専用レプリカの分離 参照用トラフィック、分析バッチ、管理画面クエリをリードレプリカへオフロード プライマリノードの計算資源とI/Oを純粋な書き込み処理専用として確保 単なる参照トラフィックの競合を書き込みの限界と錯覚し、不要な分割に走ってしまう
第3段階: 単一ノード内での宣言的パーティショニング PostgreSQL標準の宣言的パーティショニング（Range/List）で肥大テーブルを物理ファイル分割 パーティションプルーニングによる高速化、VACUUM範囲の局所化、瞬時のDETACH/DROP 分散ネットワークの複雑さを背負うことなく手に入るエンジン内部の分割効果を見落とす
第4段階: コールドデータの外部アーカイブ 1年以上経過した古い履歴データを別ストレージ（S3等）や分析用DWHへ退避 アクティブなワーキングセットをRAM内に常駐させ、キャッシュヒット率を極大化 ほとんど読まれない過去の巨大データを抱えたままシャーディングし、インフラ費を爆発させる
第5段階: ハードウェアの垂直増設（スケールアップ） 最新世代の高性能CPU、512GB〜数TBのRAM、超高速ローカルNVMeストレージの導入 完全なACIDと関係モデルの機能を維持したまま、単一ノードの処理限界を数倍に引き延ばす コード変更なしにインフラ投資だけで安全に解決できる最も安価な機会を放棄してしまう

特に第3段階のPostgreSQL宣言的パーティショニング（Declarative Partitioning）は、シャーディングが持つ利点の多くをネットワーク通信の介在なしに享受できる。以下に示すのは、日付範囲をキーとした標準的なパーティション定義である。

-- 単一インスタンス内での宣言的範囲パーティショニング構成例
CREATE TABLE measurement (
    city_id         int not null,
    logdate         date not null,
    peaktemp        int,
    unitsales       int
) PARTITION BY RANGE (logdate);

-- 各月ごとのパーティションテーブルを定義（物理的にストレージが分離される）
CREATE TABLE measurement_y2026m08 PARTITION OF measurement
    FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

CREATE TABLE measurement_y2026m09 PARTITION OF measurement
    FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

-- パーティションキーを含むインデックスを作成
CREATE INDEX ON measurement (logdate);

-- クエリ実行時、enable_partition_pruningにより該当月のテーブルのみが走査される

この仕組みを用いれば、数億件のデータが蓄積されても不要になった過去の月をALTER TABLE measurement DETACH PARTITION ...というコマンド1つで瞬時に切り離すことができ、autovacuumの負荷もパーティションごとに分散される。この手順を飛ばしてシャーディングに手を出すのは、階段を使わずにいきなり窓から飛び降りるようなものである。

まとめ - 4つの文

本稿で展開してきた議論を、現場のエンジニアが心に留めるべき4つの文で総括する。

  • PostgreSQLを複数台に分断する選択は魔法の銀の弾丸ではなく、関係モデルの堅牢な保証をネットワーク遅延と運用負債に引き換える高額な取引である。
  • シャードの境界を跨いだ瞬間、ACIDトランザクション、結合演算、一意制約、自動採番は機能しなくなり、整合性を担保する重責はすべてアプリケーションコードへと押し付けられる。
  • シャーディングキーはデータの物理的配置を決定する後戻り不能な選択であり、判断を誤った際に生じるホットスポットと再シャーディングはシステムを揺るがす災難となる。
  • クエリ最適化、リードレプリカ、宣言的パーティショニング、データアーカイブ、垂直増設のすべてを試し切るまでは、決してデータベースの水平分割を始めてはならない。

確認できなかったこと

今回の調査および公式資料の精査において、確認が取れず判断を保留した項目は以下の通りである。

  • Multigresにおける分散結合の内部メモリ制御の詳細 — 公式ドキュメントは将来的にプッシュダウン結合やスキャッター結合をサポートすると述べているが、大規模なデータ転送時にゲートウェイノードで発生するメモリ枯渇を防ぐためのディスク退避（Disk Spill）の具体的実装については未公開である。
  • PostgreSQL 2PCにおける遅延増大の定量的基準値 — 公式マニュアルはPREPARE TRANSACTIONの動作原理、ロック保持、XID周回リスクを詳細に解説しているものの、ネットワーク構成や参加ノード数によって変動が激しいため、性能劣化の具体的なパーセンテージ等は記述されていない。
  • アルファ版以降における拡張機能（Extension）の網羅的動作性 — Multigresは標準テストスイートによる高互換性を掲げているが、PostGISやpgvectorといった特殊なデータ型やインデックス構造を伴う拡張が分散層でどこまで十全に動作するかは現行の資料から検証できなかった。
