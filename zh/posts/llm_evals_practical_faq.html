引言：仪表盘上显示0.82。所以产品变好了吗

评估脚本接好了，流水线在跑，仪表盘上出现了数字。本周0.82，上周0.79。会上有人问，这三个点意味着什么。

答不上来的原因不是工具不够，而是顺序反了。分数是把什么算失败这句话搬成数字的结果。没有那句话，0.82就不表示某类失败从多少条降到了多少条，它就只是0.82。涨了说不出哪里变好，跌了也不知道该修什么。

这里要讲的，是衡量自家产品、自家提示词在自家用户输入上如何出错的一台仪器。排行榜分数和公开基准的可信度是另一个问题，那部分在知识基准不会告诉你的事和企业为何自建基准的案例里讲过。组织把这件事交给谁、以什么会议节奏运转，评估驱动开发的运作方式那边更详细。本文处在两者之间，看的是工程部分，即数据、评分、验证、闸门。

1. 什么算失败 - 分数之前必须先有的那句话

1.1 失败的定义出自观测而非想象

设计评估时最常见的第一步是列指标清单。准确性、相关性、有害性、简洁性。这份清单能挂到任何产品上，也就不适合任何产品，因为里面缺了自家用户到底以什么方式受损。

把顺序倒过来。先读输出，再从里面提取指标。这项工作有从质性研究借来的名字：读追踪记录并自由记下哪里不对，叫开放式编码；把这些笔记归拢成失败类型，叫轴心编码。不是先建类目再把笔记塞进去，而是让笔记生成类目。自动化能帮的是后面的归拢，前面的阅读必须由人做，否则信息进不来。

这里说的追踪记录，指系统为一次用户提问所做的全部事情。不只是最终回答，还包括实际拼装出来的提示词、工具调用及其返回值、检索到的文档。这个区分后面会见效。只存最终回答，就没法回溯它为什么错，失败类型会塌成一行：偶尔会答些奇怪的东西。

停止的时点也要定好。这个标准叫理论饱和，实务里好用的形式是：连续读二十条没有出现任何新的失败类目，这一轮就可以收尾。起步量常被提到的是一百条。一上来就打算读一千条的计划，通常在三百条左右停下，而那三百条就那么摊着没整理。

1.2 把判定落到通过或不通过

一到五分的量表看着诱人，因为像是携带了更多信息。问题在于你能不能把三分和四分的差别写成一句话。写不出来，这把量表就在每个标注者手里变成不同的轴，一取平均就是不同轴的平均。

一手资料在这里出现分歧。实务派的FAQ主张二元判定，而Anthropic的评估编写文档原样放着李克特量表的评分示例。不是谁错了，是前提不同。如果这个属性确实连续到需要分级，量表合适；如果评分标准写不成一句话，量表制造的就是噪声。

确实需要分级时，与其用量表，不如拆成多个二元项更好处理。求和就是等级，而且还能顺带告诉你是在哪一项掉的。

{
  "trace_id": "t-10482",
  "checks": {
    "grounded":      0,   // 提到了检索文档里没有的条款
    "no_jargon":     1,
    "format_valid":  1,
    "answered":      1    // 没有拒答一个可以回答的问题
  },
  "label_source": "human",
  "notes": "把退款期限写成14天。依据文档写的是7天"
}

1.3 怎么检验一条失败定义

判断失败定义好不好用，只有一条标准：两个不同的人看同一条输出，会不会得出同样的结论。

  • 坏例子 - 回答是否足够有帮助。人跟人不一样
  • 坏例子 - 回答是否符合我们的品牌语气。那个语气压根没写在任何地方
  • 好例子 - 提到检索文档里没有的数值或条款，算失败
  • 好例子 - 用户问的项目里只要有一项没答，算失败
  • 好例子 - 向用户暴露内部系统名称，算失败

在两个人还没统一的时候接上模型评分者，那个评分者会随便站一边，记录下大约一半的一致度。此时该修的不是评分提示词，而是那句定义。把人的分歧留着就去自动化，自动化的不是判定而是混乱。

2. 评估数据从哪里来

2.1 第一来源是真实使用日志

关于评估集的讨论里最常被略过的就是这一段。指标名字开一次会就定了，但拿它对着什么测，永远是数据问题。而日志没留下来的话，这里就直接卡住。至少要留下这些。

  • 用户输入原文和时间
  • 实际拼装并送进模型的完整提示词
  • 模型标识、版本、温度等采样参数
  • 工具调用的名称、参数和返回值
  • 如果有检索环节，检索到的文档标识与分数
  • 最终输出和响应延迟
  • 用户行为信号 - 立刻重问、中途离开、复制、明确反馈

最后一行后面最值钱。用户又把同一个问题问了一遍，这个事实比任何自动评分器都更准确地指向失败。

2.2 只靠随机抽样抓不到失败

失败率5%的系统里随机取一百条，失败是五条。其中属于某一特定类型的只有一两条，而一两条称不上类型。所以要把抽样混着来。

  • 随机 - 看分布的基线。必须有一部分出自这里
  • 分层 - 按用户类型、请求类别、输入长度、语言建格子，每格分配名额
  • 离群 - 响应长度最高和最低的、延迟最高的、工具调用次数最多的
  • 信号驱动 - 带着负面反馈、立刻重问、中途离开的追踪记录
  • 聚类 - 把输入做嵌入后聚类，从每个簇里取。得到的是一百种问题而不是同一个问题一百遍
  • 已有评分器 - 已经在跑的规则检查标出来的条目
务必记录每条样本的来源。 随机样本告诉你分布，有偏样本告诉你失败。混在一起算一个总通过率，那个数字不代表任何总体。给每条加上 sample_source 这样的字段，之后就能把随机部分单独拎出来算通过率。

2.3 先收失败样例，但不能只收失败

在只有好输出的集合上，无条件判通过的评分者也会记录下很高的一致率。那是错觉不是性能。反过来只收失败，通过率就失去意义，也量不出评分者的误报倾向。

这里要分开的不是比例而是集合本身。做两个，分开管。

  • 校准集 - 目的是检验评分者有没有分辨力。通过与不通过大致对半，而且边界样例比明显样例更值钱
  • 追踪集 - 目的是看通过率走势。原样保留真实使用的分布

合成一个就两件事都干不成。校准部分塞了很多失败，通过率会低于实际；保留了追踪分布，评分者的检验就发生在有偏的数据上。

2.4 日志变成评估集时的个人信息

日志是用户写下的句子。一旦进入评估集，团队里好几个人会读它，它会发到外部评分API，会被提交进代码仓库，还会留上几个月。这需要一套独立于留存策略的管控。

  • 脱敏要作用在评估集副本上，不是原始日志。原件被抹掉，事故调查就无从谈起
  • 脱敏会改变分布。所有名字都换成同一个占位符，模型行为本身就变了。确认脱敏后同一个失败仍能复现，再纳入
  • 评估集的访问权限与生产日志的访问权限分开管理
  • 定下保留期限，并且让过期条目也从通过率的计算里退出

3. 合成数据 - 有价值的地方和塌掉的地方

3.1 用开放式提示词生成，出来的都是同一个东西

让它生成一百条客户咨询，得到的是措辞不同的同一个问题一百条。指令一开放，生成模型就往它认为最像样的那个方向收。这样做出来的评估集，通过率是针对那一类问题的通过率。

处方是先用手把维度定下来。立起用户类型、请求类别、难度、输入形态这些轴，生成组合，再按组合逐个生成。把叉乘全部展开再筛掉不成立的，也是可用的顺序。无论哪种，要点相同：维度设计就是你声称覆盖了什么的那份声明，没有它，覆盖率这个词也不成立。

3.2 合成失效的四个条件

  • 复杂的专业领域 - 生成模型不知道该领域真实的提问分布
  • 低资源语言 - 表达的多样性和错误类型跟真实的不一样
  • 高风险应用 - 一条错误的合成样例会把错误的标准固定下来
  • 代表性不足的群体 - 原始数据里本就少的群体，在生成里会更少

四个条件结构相同。生成模型不知道那个分布，合成数据就是模型想象出来的分布，而不是用户的分布。再用同系列的模型去评分，评分就完全发生在那份想象之内。中文算不上低资源语言，但在内部术语、语体层次和机构名写法混杂的业务文档里，同样的陷阱照样出现。

3.3 合成确实有价值的地方

  • 还没有用户的早期原型 - 这个阶段要的是失败的形状，不是通过率
  • 罕见但必须处理的输入 - 注入尝试、空输入、超长文本、语言混杂、编码损坏
  • 校准评分者用的边界样例 - 明显通过和明显失败，任何评分者都判得对
  • 回归用的固定用例 - 真实数据一直在动，但回归测试必须站住不动
不要把合成数据算出的通过率当成产品质量指标。 合成用例是用来发现什么会坏的工具，不是用来说明有多好的工具。把这两样放进同一个仪表盘，一定会混。

4. 三类评分方式 - 成本与可信条件

评分器只有规则、模型、人三种，而这三种不是备选项，是性质不同的工具。只挑一种解决问题，多半以昂贵或不准确收场。

5. 送到哪个评分器，由输出的性质决定

把逐项的分流规则事先定好，争论就没了。

  • 正确答案是否唯一 → 规则。精确匹配或数值容差
  • 是不是结构或格式要求 → 规则。模式校验和解析就足够
  • 是不是绝对不能出现的东西 → 规则优先，模型做辅助。拦截必须快且确定
  • 是不是对照参考文档的事实一致 → 模型评分，但参考文档必须一起放进评分提示词
  • 是不是语气、完整性、有用性 → 模型评分加人工抽样
  • 是不是安全、监管、法律责任 → 人工。在这里省下的钱会加倍还回去

规则能抓的事情不要去问模型。拿JSON解析失败去问模型，是花钱买延迟再把准确率往下拉。如果连哪些项目能用规则判定本身都模糊，划这条线的方法在验证工具链划出的边界里单独整理过。

顺序也是成本设计的一部分。便宜那层已经滤掉的东西，在贵那层再测一遍，只花钱不增信息。把格式坏掉的输出送给模型评分者，评分者会对格式问题起反应，连内容分也一并压低。

6. 模型评分的陷阱 - 评分者被什么吸引

模型评分者不是人的代理，而是另一个模型，它对不同的东西起反应。下面三项已有论文测量，所以可以在设计阶段提前防住。

偏差被什么吸引测到了什么缓解
位置偏差提示词里放在前面的那个在15种裁判、22项任务、15万余条实例上测量。候选之间质量差距越小偏差越大，与提示词长度只有弱关联调换顺序评两次，结论翻转就判该条无效
长度偏差更长的回答在成对比较的自动评估中确认了对长度的偏好。做长度受控的回归校正后，与人类偏好排名的秩相关从0.94升到0.98在评分标准里单列长度项，或对长度做受控校正
熟悉度偏差读起来对它不陌生的文本模型给低困惑度文本的分数比人类更宽松。给出的解释是熟悉度而非署名评分模型与生成模型分开，连系列也分开

第三行在实务里最常被无视。同一个模型生成、同一个模型评分，流水线是简单了，但评分者开始奖励自己的文风。Anthropic的评估文档也把评分使用与生成不同的模型列为一般性建议。若预算所限只能用同一个模型，至少先量一下与人工标注的一致度，确认差距在可接受范围内再用。

位置偏差的那个条件也值得多看一眼。质量差距越小偏差越大，意思是拿提示词A和只改了一行的A′去比时最严重。而我们用评估要做的，恰恰就是这件事。

7. 验证评分者的方法 - 与人工标注的一致度

7.1 正确率量不出评分者

评分者验证里最常见的错误是看正确率。在失败率低的数据上，正确率反映的是数据的倾斜而不是评分者的分辨力。下面是让四个评分者跑一百条人工标注样例后，由混淆矩阵算出的数值。

function stats(tp, fn, fp, tn) {          // tp = 人判通过 且 评分者判通过
  const n = tp + fn + fp + tn;
  const po = (tp + tn) / n;                // 简单一致率
  const pe = ((tp+fn)/n)*((tp+fp)/n) + ((fp+tn)/n)*((fn+tn)/n);
  return {
    acc:   po,
    kappa: (po - pe) / (1 - pe),           // 科恩kappa
    tpr:   tp / (tp + fn),                 // 通过被判为通过
    tnr:   tn / (tn + fp)                  // 失败被判为失败
  };
}

四个里有三个正确率同为0.880。kappa却从0.189拉开到0.760。而什么都不做的A正确率最高，kappa恰好为零。只看正确率就把A挂上仪表盘，那它每天显示通过率90%，而这个数字对任何提示词改动都不起反应。

kappa扣掉了靠偶然对上的那部分，只数剩下的真实一致。标注者有三人以上，或标签是有序等级时，克里彭多夫alpha更好用。

7.2 单独看真阴性率

表里的TNR列是关键。B在十条失败里只抓住两条。挂上这种评分者，通过率变得好看，失败照样发出去。反方向的风险也有：为了抬高TNR把评分标准收紧，正常输出会被判成失败，这样的告警积上几周，团队就不再看仪表盘了。

  • 不能漏掉失败的项目 - 优先TNR，误报交给人来滤
  • 用作拦截闸门的项目 - 优先TPR，一次误报就挡住一次发布
  • 两种要求同时存在，就把项目拆开。想用一个评分者同时满足两者，通常两边都落空

7.3 评分者同样是版本管理的对象

如果你改过评分标准来提高一致度，那套标准已经贴合了那份集合。一开始就把人工标注集分成两半，调标准时只看其中一半，最终数值在未动过的留出集上产出。跳过这一步，一致度会往上走，而在新数据上纹丝不动。

  • 把评分提示词、模型、温度作为版本记录下来。评分者一变，过去的分数就无法比较
  • 换评分者那天，用旧评分者再跑一遍，把两条序列叠上
  • 人工标注集在失败类型发生变化时更新。这是事件驱动而不是按日历

提示词本身的版本管理与回滚判断，在生产提示词的变更、验证与回滚设计里单独讲过。评分者需要多加一层这种纪律：量东西的尺子在晃，就看不见被量对象的变化。

8. 把评估挂到CI上 - 非确定性、阈值、回归判定

8.1 不要用跑一次的结果来判定

相同输入不返回相同输出，这是这个问题的起点。把温度降到零也不会完全消失，批次构成、硬件、服务方的更新都还在。

所以先要做的不是定阈值，而是量出抖动的幅度。把同一批用例在不改代码的情况下跑上几轮，看各轮通过率的分布。不知道这个幅度，任何下降要么都被读成回归，要么都被读成噪声。幅度大就加用例，或者把摇摆最厉害的用例隔离出来。

8.2 阈值要相对基线而不是绝对值

通过率0.85这种绝对线是没有依据定下来的，而且每挡住一次就有人把线往下挪。几个月后那条线已经挪到了保证通过的位置。

  • 把上一个发布版用同样的数据跑同样的轮次
  • 比较两个分布，看下降幅度是否超过轮次之间的抖动
  • 逐项看。总分那一行没动，而某一类失败翻倍，这很常见
  • 把新变成失败的个别用例列成清单。清单比数字更快指向原因

8.3 CI用和监控用是两样东西

维度CI闸门生产监控
数据精选的固定用例真实流量的抽样
评分以规则为主，确定性以模型为主，异步
时间预算几分钟无约束
失败时拦截合并告警并抽样复核
变更节奏少改，有意识地改每出现新失败类型就改

想把两者并进一条流水线的尝试常常失败。往CI里塞两百条模型评分，流水线就变慢变贵，还时不时无缘无故地飘红。几周后总会有人把那一步改成有条件跳过，闸门也就没了。实务里跑得住的组合是两层：规则可判定的项目只要坏一条就拦截，模型评分的指标不做拦截而是告警，由人来看。

9. 分数在涨而产品变差的时候

9.1 古德哈特定律 - 测量变成目标的那一刻

测量一旦变成目标，它就不再是好的测量。在LLM评估里这条定律生效得特别快。一旦知道评分者偏爱长回答，提示词就悄悄变长，分数上去，用户不再读。前面那条长度偏差在这里直接变成了成本。

基于规则的项目也不安全。挂上包含依据文档引用即通过这条规则，模型会连不相干的文档也引。规则看的是形式，不是意图。

9.2 评估集老化 - 团队学会了怎么通过

同样一百条看半年，团队就学会了怎么通过这一百条。提示词里一条条加上例外处理，而每条例外都瞄着评估集里的某个具体用例。到那个时候，评估集已经不是考卷而是训练数据。它和公开基准的污染结构相同，而且因为是自家的，更难察觉。

同一个问题的另一副面孔，是评估形式本身的寿命。任务变长、步骤变多之后，给单次输出打分的做法会失去分辨率。那次转变在评估转向长时程任务里单独整理过。

9.3 分布偏移 - 原本要量的那个总体消失了

  • 用户群变了 - 从内部试运行走到对外开放，输入的文体就先变了
  • 流量来源变了 - 从搜索来的用户和从应用内来的用户，问的东西不一样
  • 上了新功能 - 评估集里关于这个功能的输入一条也没有
  • 季节与事件 - 报税季、开学、故障公告，这些时段的提问分布整个换掉
  • 上游系统变了 - 更新检索索引后，同一个问题带回来的是另一批文档

9.4 防线 - 三条就够

  • 轮换 - 每一轮把评估集的固定比例换成新日志，换入部分和固定部分的分数分开出
  • 留出集 - 留一份团队看不到的集合。只有这里分数不动，说明优化是冲着评估集去的
  • 产品指标并行 - 把重复提问率、会话流失率、转人工率这些与评估独立的信号并排看。它们和评估分数反向移动时，先怀疑评估

10. 搭建阶段表 - 什么时候做什么

阶段做什么产出进入下一步的条件常见失败
0. 观测打开追踪记录留存输入、提示词、工具、输出、用户信号能回溯过去几天只存最终回答
1. 错误分析读样本、做笔记、归成类型失败类型清单及条数连续20条不出现新类型先列指标清单
2. 定义为每种类型写判定句二元项清单两个人得出同样结论写成是否有帮助之类
3. 标注由人打标签校准集与留出集两份标注者之间的分歧已消解只收好例子
4. 自动化逐项分配评分器规则检查与评分提示词规则能办的都在规则里全部丢给模型
5. 验证在留出集上量一致度kappa、TPR、TNR的记录达到目标一致度只看正确率
6. 闸门CI与监控分开挂拦截规则与告警指标抖动幅度已经量过钉死一个绝对阈值
7. 维护轮换、留出集、产品指标逐轮记录持续运转做一次就撂下

有报告说第1阶段要吃掉整体工期的一半以上，这个分配不值得惊讶，是正常的。后面每个阶段都是把第1阶段的结果搬进机器，所以第1阶段单薄，剩下的就会把错误的东西量得很精确。

11. 没能确认的部分

  • 模型评分者与人的一致率有多少，不存在通用数值。 公开的只是特定任务、特定评分标准、特定数据下的个案值。把别的组织的一致度数字搬来当自己的目标线，没有找到依据
  • 位置偏差是在两个公开基准上测的。在中文业务数据或企业内部领域是否以同样量级出现，没能确认
  • 长度校正方法是为成对比较的排名设计的。把它直接搬到单条评分上的步骤，那篇论文里没有
  • 错误分析要占开发时间60~80%，以及自建复核工具的团队快约十倍，这些是实践者的经验报告。没能确认有公开样本与测量方法的调查
  • 二元判定和李克特量表孰优孰劣尚无定论。两份一手资料给出不同建议，也没能确认区分条件的对比研究
  • 评估集每轮要轮换多少比例才能防住老化，没有找到数值依据。需要轮换和需要多少轮换是两个问题

结论：评估不是挑工具的活儿

评估落地失败的地方几乎每次都相同。先挑工具，先定指标名字，数据后面再往上凑。这样仪表盘是有了，但那些数字代表什么，没人说得出来。

守住顺序，工具就成了后面的问题。读输出，把失败写成句子，检验这句话在两个人那里读法是否一致，逐项分配最便宜够用的评分器，用人工标注验证评分者，量出抖动幅度，然后才挂闸门。从这个顺序里出来的0.82，能翻译成这类失败从多少条降到了多少条。

今天要开始的话，就三件事。打开追踪记录留存，读一百条抽样，把人工标注集分成两半留一半不动。其余的都要靠这三件才能起步，而有了这三件，没有工具也能起步。
