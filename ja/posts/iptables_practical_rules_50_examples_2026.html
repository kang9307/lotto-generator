iptables実戦ルールセット50選 - シナリオ別ファイアウォール例

10シナリオカテゴリ × 5ルール = すぐ使える50例

2026年5月18日 IT・技術

はじめに:なぜiptables 50選なのか

iptablesはLinuxサーバセキュリティで最も歴史が長く堅牢なツールです。2026年現在、多くのディストリビューションでnftablesが標準となりましたが、RHEL 7/8系、組み込み機器、多数のコンテナホストではiptables(またはiptables-translate)が依然として現役です。問題は構文が直感的でないこと。一度ミスするだけでSSHセッションが切れて、コンソール往復という事故が後を絶ちません。

本記事はそうした試行錯誤を減らすため10シナリオカテゴリ × 5ルール = 合計50の実戦ルールを整理します。各ルールはコマンド・意味・適用シナリオの3点セットで、コピーしてすぐ適用可能な形にしました。単なる文法の羅列ではなく「いつ何を入力すべきか」に焦点を絞っています。

当サイトのiptablesジェネレータと併用するとさらに効果的です。記事で概念を掴み、ツールでルールを視覚的に組み合わせ、そのままサーバに適用する流れが最速です。

1. 基本ポリシー設定 (5選)

すべてのファイアウォールの出発点。ポリシー(POLICY)を明示的に定義することで、意図せぬトラフィック許可・遮断を防げます。

[#1] デフォルトDROP + 明示的許可方式
sudo iptables -P INPUT DROP
sudo iptables -P FORWARD DROP
sudo iptables -P OUTPUT ACCEPT
意味:INPUT/FORWARDはデフォルト遮断、明示ACCEPTのみ通過。OUTPUTは自由。
適用:一般サーバセキュリティの標準。最も安全な出発点。
[#2] ESTABLISHED・RELATED接続の許可
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
意味:既に確立した接続とその関連(FTP-data等)を自動許可。
適用:ほぼ全てのINPUTチェーンの最初のルール。
[#3] ループバックインタフェース許可
sudo iptables -A INPUT -i lo -j ACCEPT
sudo iptables -A OUTPUT -o lo -j ACCEPT
意味:127.0.0.1通信を許可。多くのデーモンがIPCに使用するため必須。
適用:ポリシーDROP直後に真っ先に登録。
[#4] INVALIDパケット遮断
sudo iptables -A INPUT -m conntrack --ctstate INVALID -j DROP
意味:不正なシーケンス番号やフラグ組合せ等の異常パケットを遮断。
適用:基本衛生ルール。ポートスキャナ回避にも有効。
[#5] ICMPエコー許可(レートリミット付き)
sudo iptables -A INPUT -p icmp --icmp-type echo-request -m limit --limit 10/sec -j ACCEPT
意味:毎秒10回までpingに応答。pingフラッド防止。
適用:NMSやヘルスチェックがICMPを使う場合に必須。
即座に生成:iptablesジェネレータでINPUTチェーン + ESTABLISHED + loopbackチェックして出力。

2. SSHセキュリティ強化 (5選)

サーバ侵害の半数は22番ポート経由。SSHは最優先で保護すべきサービスです。

[#6] SSHポート変更後の許可
sudo iptables -A INPUT -p tcp --dport 2222 -j ACCEPT
意味:22の代わりに2222でSSHを受ける。自動ボットスキャンを約95%回避。
適用:sshd_configのPort 2222設定と併用。
[#7] SSHホワイトリスト(特定IPのみ)
sudo iptables -A INPUT -p tcp -s 203.0.113.0/24 --dport 22 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 22 -j DROP
意味:オフィス帯域からのみSSH許可、他は遮断。
適用:固定IP環境(VPN・オフィス)で最強のSSH防御。
[#8] SSHブルートフォースのレートリミット
sudo iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW \
    -m recent --set --name SSH
sudo iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW \
    -m recent --update --seconds 60 --hitcount 4 --name SSH -j DROP
意味:60秒以内に4回以上の新規接続を自動遮断。
適用:fail2ban代替としてカーネルレベルで処理。
[#9] 国単位SSH遮断 (xtables-addons geoip)
sudo iptables -A INPUT -p tcp --dport 22 -m geoip --src-cc CN,RU,KP -j DROP
意味:特定国IPからのSSHを全遮断。
適用:グローバルトラフィック不要な内部サーバ。xtables-addonsが必要。
[#10] ポートノッキング(knockシーケンス)
sudo iptables -N SSH_PHASE2
sudo iptables -A INPUT -p tcp --dport 7000 -m recent --name PH1 --set -j DROP
sudo iptables -A INPUT -p tcp --dport 8000 -m recent --name PH1 --rcheck \
    -m recent --name PH2 --set -j DROP
sudo iptables -A INPUT -p tcp --dport 22 -m recent --name PH2 --rcheck -j ACCEPT
意味:7000 → 8000の順にノックして初めてSSHが開く。
適用:固定IPがなく、露出を最小化したい場合。

3. Webサーバセキュリティ (HTTP/HTTPS) (5選)

80/443は外部に開く必要があるため攻撃が最も集中する表面。レートリミットとSYN flood防御が核心。

[#11] 80/443の一般許可
sudo iptables -A INPUT -p tcp -m multiport --dports 80,443 -j ACCEPT
意味:HTTPとHTTPSを同時許可。
適用:全ての公開Webサーバの基本。
[#12] Cloudflare IPのみ80/443許可
for ip in $(curl -s https://www.cloudflare.com/ips-v4); do
    sudo iptables -A INPUT -p tcp -s $ip -m multiport --dports 80,443 -j ACCEPT
done
sudo iptables -A INPUT -p tcp -m multiport --dports 80,443 -j DROP
意味:CDN迂回の直接攻撃を遮断。CFを経由しないなら一律DROP。
適用:Cloudflareプロキシ使用時のorigin保護に必須。
[#13] 同時接続数制限(基本DDoS対策)
sudo iptables -A INPUT -p tcp --dport 80 -m connlimit --connlimit-above 50 -j REJECT
意味:同一IPから80番への同時接続が50以上で拒否。
適用:ボット・HTTP floodの一次緩和。
[#14] Slowloris防御(遅いHTTP接続)
sudo iptables -A INPUT -p tcp --dport 80 -m hashlimit \
    --hashlimit-name http_slow --hashlimit-mode srcip \
    --hashlimit-above 30/min --hashlimit-burst 20 -j DROP
意味:IPあたり毎分30接続超過を遮断。遅延多接続によるリソース枯渇を防止。
適用:Apache・Nginxの前段に無料のSlowloris保護。
[#15] SYN flood防御
sudo iptables -A INPUT -p tcp --syn -m limit --limit 1/sec --limit-burst 3 -j ACCEPT
sudo iptables -A INPUT -p tcp --syn -j DROP
意味:SYNパケットを毎秒1個に制限、バースト3。
適用:カーネルtcp_syncookiesと併用推奨。
Webルール自動生成:iptablesジェネレータで「Webサーバ」プリセットを選択。

4. データベースセキュリティ (5選)

DBは絶対に外部公開不可。多層防御が原則で、iptablesはその最外殻として最強です。

[#16] MySQL外部遮断 + アプリサーバ許可
sudo iptables -A INPUT -p tcp -s 10.0.1.10 --dport 3306 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 3306 -j DROP
意味:特定のアプリサーバ(10.0.1.10)からのみMySQL接続可。
適用:全ての本番DBの基本形。
[#17] PostgreSQL 5432を内部網限定
sudo iptables -A INPUT -p tcp -s 10.0.0.0/16 --dport 5432 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 5432 -j DROP
意味:プライベート帯域のみPG接続許可。
適用:VPC・VPNで隔離された環境。
[#18] Redis 6379(bind 127.0.0.1 + ファイアウォール二重防御)
sudo iptables -A INPUT -p tcp ! -s 127.0.0.1 --dport 6379 -j DROP
意味:redis.confのbindとは別にiptables側でも外部遮断。
適用:Redis認証未設定環境で必須。
[#19] MongoDB 27017の外部全面遮断
sudo iptables -A INPUT -p tcp --dport 27017 -i ! lo -j DROP
意味:ループバック以外の全インタフェースで27017遮断。
適用:単一サーバMongoDB事故防止の最終防衛線。
[#20] Memcached 11211のホワイトリスト
sudo iptables -A INPUT -p tcp -s 10.0.1.0/24 --dport 11211 -j ACCEPT
sudo iptables -A INPUT -p udp -s 10.0.1.0/24 --dport 11211 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 11211 -j DROP
sudo iptables -A INPUT -p udp --dport 11211 -j DROP
意味:Memcached UDP増幅攻撃を防止。TCP・UDP両方ホワイトリスト。
適用:認証なしMemcached公開時のDDoS反射対策。

5. Dockerコンテナ環境 (5選)

Dockerは自前で多数のiptablesルールを生成するため衝突が頻発。DOCKER-USERチェーンの活用が必須。

[#21] Dockerデーモンポート(2375/2376)の遮断
sudo iptables -A INPUT -p tcp -m multiport --dports 2375,2376 -j DROP
意味:Docker APIのリモート露出を全面遮断。露出すると即コンテナ乗っ取り。
適用:全Dockerホスト必須。
[#22] DOCKER-USERチェーンでコンテナ外部接続制御
sudo iptables -I DOCKER-USER -s 203.0.113.0/24 -j ACCEPT
sudo iptables -I DOCKER-USER -j DROP
意味:特定帯域のみコンテナ公開ポートに接続可能。
適用:Dockerが自動生成するルールの上に安全にポリシー追加。
[#23] コンテナ間通信の隔離
sudo iptables -I DOCKER-USER -i docker0 -o docker0 -j DROP
意味:同一bridge内のコンテナ間直接通信を遮断。
適用:マルチテナントコンテナホスト。--icc=falseの代替。
[#24] Swarmノード間通信 (2377/7946/4789)
sudo iptables -A INPUT -p tcp -s 10.0.0.0/24 --dport 2377 -j ACCEPT
sudo iptables -A INPUT -p tcp -s 10.0.0.0/24 --dport 7946 -j ACCEPT
sudo iptables -A INPUT -p udp -s 10.0.0.0/24 --dport 7946 -j ACCEPT
sudo iptables -A INPUT -p udp -s 10.0.0.0/24 --dport 4789 -j ACCEPT
意味:Swarmクラスタの管理・gossip・overlay通信。
適用:Swarmクラスタ内では開放、外部には閉鎖。
[#25] コンテナegress制限(SSRF対策)
sudo iptables -I DOCKER-USER -s 172.17.0.0/16 -d 169.254.169.254 -j DROP
意味:コンテナからEC2メタデータエンドポイントへのアクセスを遮断。
適用:AWS・GCPクラウドホストでコンテナ乗っ取り被害最小化。

6. Kubernetesノード (5選)

K8sコントロールプレーンとワーカーノードはそれぞれ開放すべきポートが決まっている。内部通信用ポートは絶対に外部公開不可。

[#26] APIサーバ6443のホワイトリスト
sudo iptables -A INPUT -p tcp -s 10.0.0.0/16 --dport 6443 -j ACCEPT
sudo iptables -A INPUT -p tcp -s 203.0.113.5 --dport 6443 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 6443 -j DROP
意味:クラスタ内部網と管理者IPのみkube-apiserverに接続可。
適用:マスターノード標準ポリシー。
[#27] Kubelet 10250を内部ノードからのみ
sudo iptables -A INPUT -p tcp -s 10.0.0.0/16 --dport 10250 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 10250 -j DROP
意味:kubelet APIはコントロールプレーンからのみ呼び出し。外部公開すると権限昇格リスク。
適用:全ワーカーノード。
[#28] NodePort範囲 (30000-32767) の制限
sudo iptables -A INPUT -p tcp -s 10.0.0.0/16 --dport 30000:32767 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 30000:32767 -j DROP
意味:NodePortはLB/Ingressの内部網からのみアクセス可。インターネット直接公開禁止。
適用:LoadBalancerが前段にある標準構成。
[#29] etcd 2379-2380をクラスタ内部限定
sudo iptables -A INPUT -p tcp -s 10.0.1.0/24 --dport 2379:2380 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 2379:2380 -j DROP
意味:etcdはコントロールプレーンノード間のみ通信。公開するとクラスタ鍵漏洩。
適用:マスターノード(HA etcd構成含む)。
[#30] CNIプラグイン通信 (VXLAN 4789, Wireguard 51820)
sudo iptables -A INPUT -p udp -s 10.0.0.0/16 --dport 4789 -j ACCEPT
sudo iptables -A INPUT -p udp -s 10.0.0.0/16 --dport 51820 -j ACCEPT
意味:Flannel・Calico VXLANまたはCilium Wireguardのノード間トンネル。
適用:使用中のCNIに合わせて該当ポートのみ開放。

7. メールサーバ (5選)

メールポートはスパムボットが絶えず叩く。適切なレートリミットとTLS強制が核心。

[#31] SMTP 25/587/465の許可
sudo iptables -A INPUT -p tcp -m multiport --dports 25,465,587 -j ACCEPT
意味:標準メール送受信ポートを全て許可。
適用:Postfix・Exim等のメールサーバ基本。
[#32] IMAPS・POP3Sのみ許可(平文遮断)
sudo iptables -A INPUT -p tcp -m multiport --dports 993,995 -j ACCEPT
sudo iptables -A INPUT -p tcp -m multiport --dports 143,110 -j DROP
意味:TLSポートのみ開放、平文IMAP/POP3を全面遮断。
適用:モダンメールサーバは平文無効化必須。
[#33] SMTPレートリミット(スパムボット対策)
sudo iptables -A INPUT -p tcp --dport 25 -m connlimit --connlimit-above 10 -j REJECT
sudo iptables -A INPUT -p tcp --dport 25 -m hashlimit \
    --hashlimit-name smtp --hashlimit-mode srcip \
    --hashlimit-above 5/min --hashlimit-burst 3 -j DROP
意味:IPあたり同時10件、毎分5件超過のSMTP接続を遮断。
適用:正常なメール流は影響なくボットのみ遮断。
[#34] 疑わしいIP遮断 (ipset連携)
sudo ipset create spamips hash:ip
sudo iptables -A INPUT -p tcp --dport 25 -m set --match-set spamips src -j DROP
意味:ipsetに追加するだけで即座に遮断。動的遮断に有効。
適用:rspamd・SpamAssassinがipsetへ追加するよう連携。
[#35] メールサーバoutbound 25制限(オープンリレー防止)
sudo iptables -A OUTPUT -p tcp -m owner --uid-owner postfix --dport 25 -j ACCEPT
sudo iptables -A OUTPUT -p tcp --dport 25 -j DROP
意味:postfixユーザのみ外部25番接続可。一般ユーザ・Webシェルのスパム送信を遮断。
適用:共有ホスティング・多ユーザサーバで必須。

8. NATとポートフォワーディング (5選)

iptables natテーブルはルーター・ゲートウェイ役割で必須。PREROUTING・POSTROUTINGの違いを正確に理解する必要があります。

[#36] 外部80 → 内部8080フォワーディング
sudo iptables -t nat -A PREROUTING -p tcp --dport 80 -j REDIRECT --to-port 8080
意味:外部からの80番パケットをローカル8080へリダイレクト。
適用:root権限なしで80番にバインドする標準的トリック。
[#37] 別ホストへのDNAT
sudo iptables -t nat -A PREROUTING -p tcp --dport 80 -j DNAT --to-destination 10.0.1.50:80
sudo iptables -t nat -A POSTROUTING -p tcp -d 10.0.1.50 --dport 80 -j MASQUERADE
意味:ゲートウェイ受信80番トラフィックをバックエンド10.0.1.50:80へ転送。
適用:簡易L4ロードバランサ、リバースプロキシ代替。
[#38] MASQUERADE(ホームルーター標準NAT)
sudo iptables -t nat -A POSTROUTING -o eth0 -s 192.168.0.0/24 -j MASQUERADE
意味:内部網パケットがeth0(WAN)を出る際にゲートウェイIPへ変換。
適用:Linuxルーター・ホームサーバゲートウェイ。
[#39] SNAT(固定IP変換)
sudo iptables -t nat -A POSTROUTING -o eth0 -s 10.0.0.0/8 -j SNAT --to-source 203.0.113.10
意味:MASQUERADEと違い明示的な送信元IPを指定。性能で若干優位。
適用:WAN IPが固定の環境で推奨。
[#40] 1:1 NAT(外部IP ↔ 内部IPマッピング)
sudo iptables -t nat -A PREROUTING -d 203.0.113.20 -j DNAT --to-destination 10.0.1.20
sudo iptables -t nat -A POSTROUTING -s 10.0.1.20 -j SNAT --to-source 203.0.113.20
意味:外部IP1つを内部サーバ1台に完全マッピング。双方向NAT。
適用:DMZサーバに公開IPを直接付与する効果。
NATルール生成:iptablesジェネレータでPREROUTING/POSTROUTINGチェーン + DNAT/SNATオプションを選択。

9. ロギングとモニタリング (5選)

遮断と同じくらい重要なのが可視性。LOGターゲットを適切に活用すれば侵入痕跡を事後追跡できます。

[#41] DROP直前のLOGロギング
sudo iptables -A INPUT -m limit --limit 5/min -j LOG --log-prefix "iptables-drop: " --log-level 7
sudo iptables -A INPUT -j DROP
意味:DROP前に毎分5回までログ。/var/log/kern.logまたは/var/log/messagesに記録。
適用:事後分析用。ログ爆発防止のためlimitが必須。
[#42] 新規SSH接続を全てログ
sudo iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW \
    -j LOG --log-prefix "ssh-new: "
意味:新規SSH試行を全て記録。ブルートフォース・正常接続両方を確認。
適用:セキュリティ監査が必要な環境。
[#43] レートリミット発火をログ
sudo iptables -A INPUT -p tcp --dport 80 -m connlimit --connlimit-above 50 \
    -j LOG --log-prefix "http-flood: "
sudo iptables -A INPUT -p tcp --dport 80 -m connlimit --connlimit-above 50 -j REJECT
意味:フラッド閾値到達時にログ+拒否。事故時点の確認が容易。
適用:モニタリングシステムとgrokパターン連携。
[#44] 疑わしいパターンのアラート用prefix
sudo iptables -A INPUT -p tcp --dport 22 -m recent --rcheck --seconds 60 --hitcount 4 \
    --name SSH -j LOG --log-prefix "SSHBRUTE-ALERT: "
意味:特定prefixでログ → rsyslog・Lokiでアラート発火。
適用:SIEM・中央集中ログ環境。
[#45] ULOG/NFLOG(カーネル→ユーザ空間ロギング)
sudo iptables -A INPUT -p tcp --dport 80 -j NFLOG --nflog-group 1 --nflog-prefix "http-in: "
意味:ulogd2がグループ1を受け取りPostgreSQL・MySQL・JSON等に格納。
適用:大容量パケットログ。dmesg爆発を回避。

10. 緊急・一時的遮断 (5選)

攻撃進行中や事故疑い時に即適用すべきルール。一時的なので時間ベース自動解除と併用すると安全。

[#46] 特定IPの即時遮断
sudo iptables -I INPUT 1 -s 198.51.100.45 -j DROP
意味:最先頭(-I 1)に挿入。他のACCEPTルールより先に評価。
適用:攻撃IP確認後1秒以内に遮断可能。
[#47] CIDR単位遮断(小規模ボットネット)
sudo iptables -I INPUT 1 -s 192.0.2.0/24 -j DROP
意味:同一帯域から多数IPが攻撃する際に一括遮断。
適用:ホスティング・VPSから発生したボットネット対応。
[#48] 国単位の遮断(全INPUT)
sudo iptables -I INPUT 1 -m geoip --src-cc CN,RU,KP -j DROP
意味:特定国IPを全面遮断。SSHだけでなく全ポートに適用。
適用:グローバルトラフィック不要な内部サービス。xtables-addonsが必要。
[#49] 時間制限遮断(1時間後自動解除)
sudo iptables -I INPUT 1 -s 198.51.100.45 -j DROP
echo "sudo iptables -D INPUT -s 198.51.100.45 -j DROP" | at now + 1 hour
意味:atコマンドで1時間後自動解除。永久遮断ルール蓄積を防止。
適用:一時的に疑わしいIPに適合。atデーモンが必要。
[#50] DOS疑い時の自動ipset追加
sudo ipset create blacklist hash:ip timeout 3600
sudo iptables -I INPUT -m set --match-set blacklist src -j DROP
# 攻撃IP発見時
sudo ipset add blacklist 198.51.100.99 timeout 3600
意味:ipsetに追加するだけで即遮断、3600秒後自動解除。
適用:スクリプト・CrowdSec・fail2banと統合。

適用時の注意事項

50ルールを一度に適用するのは危険です。以下の順序を守るのが最も安全。

  • SSH接続切断防止:ポリシーをDROPに変える前に必ずiptables -I INPUT 1 -p tcp --dport 22 -s 自分のIP -j ACCEPTを先に登録。事故時も自分の接続は維持。
  • 永続化:ルールはメモリ上のみなので再起動で消える。iptables-save > /etc/iptables/rules.v4で保存し、iptables-persistentパッケージで起動時に復元。
  • ufw・firewalldとの衝突:同一サーバで2種類のツールを併用するとルールが上書きされる。1つだけ選ぶか、ufw/firewalldが内部でiptablesをどう扱うか理解した上で使用。
  • ロールバック計画:作業前にiptables-save > /root/iptables.backup.$(date +%F)でバックアップ。事故時iptables-restore < /root/iptables.backup.YYYY-MM-DDで即復旧。
  • 視覚的検証:当サイトiptablesジェネレータでルールをGUIで組み合わせ、プレビュー後に適用するとミスが激減します。

結論:50個は出発点

本記事の50ルールは一般環境の標準的な出発点です。実際の運用環境はワークロード・トラフィックパターン・規制要件によってルールが変わります。例えばPCI-DSS環境は全ての遮断・許可にログが義務付けられ、医療データサーバはePHIアクセスIPの厳格なホワイトリストが必要です。

iptablesを習得する最速の方法は1カテゴリずつ、実験サーバで直接適用し壊してみることです。システムを壊さず学習できる環境(例:Vagrant・LXC・Docker)を用意し、本記事の50選をカテゴリ別に手に馴染ませてください。
