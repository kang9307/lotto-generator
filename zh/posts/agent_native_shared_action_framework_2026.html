1. 超越传统输入框的交互环境 — 为何需要Agent-Native

将AI智能体接入应用程序最常见的方式是在屏幕一侧放置一个聊天窗口。从本文的视角来看，这种方式中智能体处理的上下文与用户所看到的界面往往容易脱节。

Builder.io开源项目BuilderIO/agent-native的README开篇写道：「Coding agents work with more than a text box. Their environment provides context, tools, files, tests, and previews that make their capabilities and results visible.」README将这一观点延伸至智能体与人类共同使用的定制UI。

根据本文的梳理，此前的文章（MCP无状态架构演进、Claude Code MCP服务器选型基准以及OmniRoute AI网关整合）主要探讨智能体客户端与工具服务器之间的协议与路由，而本文则探讨在应用程序内部由UI与智能体共享单一动作的框架。

README将该项目介绍为一套用于构建将自主任务与定制UI相结合的智能体的开源TypeScript框架。本文在README披露的范围内梳理三大原则与六大表面，并以本文的解读补充在引入时需要权衡的技术代价。

2. 界面与工具的分歧 — 双重维护引发的逻辑不一致

本节代表本文梳理的常规架构背景，而非README中的表述。在全栈Web应用架构中，用户交互的核心传统上是界面事件处理器。当按钮被点击时，组件点击处理器被触发，前端初步校验表单数据后通过HTTP客户端向后端发送请求。后端执行业务逻辑，更新数据库，返回成功响应，并更新状态以完成页面渲染。

当尝试向该结构追加大模型智能体功能时，工程团队有时会构建并行的辅助路径。这种方式采用独立的模式格式编写智能体可调用的工具清单，并开设专用端点来处理模型的函数调用请求。但在这种二元结构中，可能会产生以下维护负担。

  • 规格定义与验证规则的重复：界面按钮处理函数中的输入验证规则与智能体工具的模式定义位于不同位置，当业务规则调整时，可能出现某一方漏改的情况。
  • 执行路径与鉴权控制的分离：界面操作所经历的会话认证检查与智能体工具调用链路的权限验证逻辑分离，可能产生安全死角。
  • 界面视图状态与模型认知的滞后：智能体通过工具调用修改了数据，若前端内存中的状态未能即时捕获，屏幕上可能会残留旧数据导致不一致。
  • 测试与回归验证负担加重：团队可能需要针对UI交互与智能体工具调用分别编写测试用例，可能会增加测试套件的维护负担。

针对本节梳理的问题背景，README以单个动作驱动所有表面这一形式来应对该问题。

3. 三大核心原则 — Shared Actions、Data与State

官方代码仓库README对支撑智能体原生应用的三大核心原则作出了如下定义：

共享原则 共享对象 README描述
Shared actions 智能体工具与UI代码中的功能 智能体将各项能力作为工具调用，UI从代码中调用。两条路径使用相同的验证、权限和实现。
Shared data 智能体与UI中执行的工作结果 智能体完成的工作呈现在UI中，UI中完成的工作可供智能体使用。
Shared application state 当前页面、选中的记录、活动视图 智能体接收相关的UI状态，例如当前页面、选中的记录或活动视图。

关于这三大原则在README中的陈述内容可归纳如下：

  • 其一，Shared actions：根据README说明，智能体将各项能力作为工具调用，UI从代码中调用，且两条路径使用相同的验证、权限和实现。由于业务逻辑与验证共用同一路径，有助于减少行为不一致。
  • 其二，Shared data：README指出，智能体完成的工作呈现在UI中，UI中完成的工作可供智能体使用。这是一种在双方表面之间传递数据操作结果的结构。
  • 其三，Shared application state：README说明，智能体接收相关的UI状态，例如当前页面、选中的记录或活动视图。作为本文举出的示例，如果选中的记录信息传递给智能体，用户的指令可能会简化。README本身并未给出这一具体示例。

4. 单个动作暴露的6个表面 — 从UI到CLI

README指出，单个动作可驱动应用的各个交互表面：UI、智能体、HTTP、MCP、A2A和CLI。

暴露表面 调用主体 运行机制与作用
UI UI界面代码（React） 在React中使用useActionQuery调用
Agent tools AI智能体 智能体接收动作作为工具
HTTP API HTTP客户端 通过动作中的http属性指定方法（示例为GET）
MCP MCP客户端 作为Model Context Protocol表面暴露
A2A 外部智能体 作为agent-to-agent表面暴露
CLI 命令行环境 作为命令行表面暴露

以下是基于README由本文梳理的解读。

  • 实现位置的统一（本文的解读）：根据README，由于单个动作驱动六大表面，因此无需针对各个表面分别编写相同功能。
  • 验证与权限的共享：README指出，智能体路径与UI路径使用完全相同的验证、权限和实现。
  • 外部协议表面：MCP与A2A包含在表面列表中。README并未说明支持哪些具体的客户端。
  • CLI与HTTP调用（本文的解读）：由于同一动作也可以通过命令行或HTTP调用，因此看来可用于问题复现与自动化流程。
  • 模式共享（本文的解读）：由于动作包含description与schema，各表面之间可能更容易统一输入规则。README并未提及文档自动生成。

5. defineAction代码结构 — 单一定义与运行时绑定

README中的示例代码如下（省略了import语句）：

export default defineAction({
  description: "Return a friendly greeting.",
  schema: z.object({
    name: z.string().default("world").describe("Name to greet"),
  }),
  http: { method: "GET" },
  run: async ({ name }) => {
    return { message: `Hello, ${name}!` };
  },
});

README对该示例进行了如下说明：「The agent receives hello as a tool. React calls the same function with useActionQuery("hello", { name: "Alex" }). Agent-Native also exposes it through HTTP, MCP, A2A, and the CLI.」代码构成包括description（描述字符串）、schema（Zod对象，name的默认值“world”与说明）、http（指定请求方法，示例为GET）以及run（执行函数）。各个字段在运行时具体如何使用超出了README示例范围，本文未能确认。

根据本文的观察，单一定义中同时包含了描述、输入模式、HTTP方法以及执行逻辑。

8. 适用场景与局限性 — 何时有效何时无效

没有任何框架是适用于所有问题的万能方案。本节不是README的建议，而是本文整理的解读。以下从本文的视角划分智能体原生设计能够产生价值与可能不适用的场景。

  • 适用场景 ① — 人机协同的交互式工具：在图形设计或数据分析界面等场景中，用户在操作界面元素的同时向智能体委派相关任务，单一定义动作与状态共享可能减少开发工作量。
  • 适用场景 ② — 需要多种交互接口的系统：如果系统不仅需要Web界面，还需兼顾命令行（CLI）或外部智能体（MCP/A2A）集成，支持六大交互表面可能会有所助益。
  • 不适用场景 ① — 无界面交互的纯后端处理：对于离线批处理作业或网络爬虫等完全不存在UI界面的系统，该框架的界面相关功能可能并不需要。
  • 不适用场景 ② — 静态网站及绑定其他框架的项目：常规博客或文档站点，亦或是深度依赖其他智能体框架的既有项目，可能不适合引入该架构。
