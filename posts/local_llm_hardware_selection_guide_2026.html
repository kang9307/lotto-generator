서론: 왜 2026년에 다시 로컬 LLM인가

2024년까지만 해도 "AI는 클라우드"라는 인식이 지배적이었습니다. ChatGPT·Claude·Gemini로 충분했고, 굳이 무거운 모델을 내 PC에서 굴릴 이유가 없었습니다. 그런데 2025년을 거치며 분위기가 달라졌습니다. 사용량에 비례해 쌓이는 API 비용, 그리고 개인 코드와 업무 문서를 외부 API에 통째로 보내는 데 따르는 보안·법무 부담이 본격적으로 표면화됐습니다. 동시에 Meta의 Llama 3.x, Alibaba의 Qwen 2.5, Microsoft의 Phi-3.5처럼 7B~70B 파라미터 오픈 가중치 모델이 빠르게 발전했고, 2026년에는 Qwen3.6·Gemma 4·gpt-oss 같은 다음 세대가 이어졌습니다. 적당한 하드웨어로도 실용적인 출력을 얻을 수 있는 시대가 된 것입니다.

GeekNews에 올라온 whichllm이라는 CLI 도구가 작은 화제가 됐습니다. 자기 PC 스펙을 분석해 "이 모델은 돌아갑니다, 저 모델은 무리입니다"를 알려주는 단순한 도구인데, 적지 않은 토론이 이어졌습니다. 그만큼 "내 PC에서 어떤 모델이 실제로 돌아가는지"가 모두의 공통 고민이라는 뜻입니다. 본 글은 도구 소개가 아니라, 공개된 모델 파일 크기와 제조사 공식 사양을 기준으로 맞춘 하드웨어-모델 매트릭스 + 양자화 가이드 + 런타임 비교로 실전 결정 기준을 제시합니다.

1. 로컬 LLM이 다시 뜨는 4가지 이유

1-1. 사용량에 비례하는 클라우드 API 비용

프런티어 모델 API는 토큰 단위로 과금되므로, 하루 수십만 토큰을 처리하는 개발 워크플로(코드 리뷰·문서 생성·번역)에서는 청구액이 사용량에 비례해 커집니다. 단가의 방향은 한쪽으로 단정하기 어렵습니다. Anthropic 공식 가격표 기준으로 Opus 4.5 이후 모델의 토큰 단가는 Opus 4·4.1보다 낮게 책정돼 있고, 반대로 Claude 4.7 이후 모델은 같은 텍스트에서 토큰이 약 30% 더 나오는 새 토크나이저를 쓴다고 명시돼 있습니다(2026-09-29 확인). 그래서 요점은 단가가 아니라 총량입니다. 반복 작업의 일부만 7B~14B 모델로 로컬에서 처리해도 사용량에 비례하던 비용 곡선이 달라집니다.

1-2. 프라이버시·기밀 유출 우려

"이 코드를 외부 API에 보내도 됩니까?"라는 질문이 기업 법무팀의 일상이 됐습니다. EU AI Act, 한국 개인정보보호법 강화 흐름과 맞물려, 고객 데이터·내부 코드를 포함한 프롬프트를 외부로 전송하는 것 자체가 컴플라이언스 리스크가 됐습니다. 로컬 추론은 외부 전송이라는 경로 자체를 없앱니다. 다만 모델을 올린 서버의 접근 통제·로그 관리는 여전히 따로 챙겨야 합니다.

1-3. 오프라인·고립망 작동 필요성

금융권, 의료, 군·정부, 공장 OT 네트워크처럼 외부 인터넷이 차단된 환경에서는 클라우드 LLM 자체가 선택지가 아닙니다. 이런 환경에서는 사내 GPU 서버에 오픈 가중치 모델을 직접 올리는 자체 호스팅이 현실적인 경로이고, 로컬 모델은 사실상 "유일한 옵션"입니다.

1-4. 7B~70B 오픈 모델의 빠른 발전

2024년 초만 해도 "7B 모델은 장난감"이라는 평이 많았습니다. 발행 당시(2026년 5월)에는 Llama 3.2 3B가 GPT-3.5급, Qwen 2.5 14B가 일부 벤치마크에서 GPT-4급이라는 평가가 흔했습니다. 이런 비교는 벤치마크와 과제에 따라 크게 달라지므로 단정하지 않습니다. 분명한 것은 세대 교체 속도입니다. Hugging Face 공식 저장소 기준으로 Qwen3.6(27B, 35B-A3B)이 2026년 4월, Gemma 4(E2B·E4B·12B·26B-A4B·31B)가 2026년 3월부터 올라왔고, OpenAI의 오픈 가중치 모델 gpt-oss(20b·120b)는 2025년 8월에 공개됐습니다. 하드웨어가 받쳐주면 고를 수 있는 모델이 계속 늘어납니다.

2. 하드웨어별 권장 모델 매트릭스

본 절은 본 글의 핵심입니다. 모델별 메모리 요구량은 Hugging Face에 공개된 GGUF 파일 크기(2026-09-29 확인)를 기준으로 맞췄습니다. 실제로는 파일 크기보다 여유가 더 필요합니다. 컨텍스트 길이에 비례해 커지는 KV 캐시와 런타임 자체가 메모리를 쓰기 때문입니다. VRAM이 부족하면 RAM으로 오프로드되며, 그 순간 속도가 크게 떨어집니다. 따라서 "파일 크기에 여유분을 더해 VRAM 안에 들어가는 모델"이 실용성의 기준선입니다.

3. 런타임 비교: 무엇으로 돌릴 것인가

같은 모델 파일이라도 어떤 런타임으로 실행하느냐에 따라 성능·편의성이 크게 달라집니다. 개인과 소규모 팀이 고르는 대표적인 선택지는 다음 네 가지입니다.

런타임 UI 주력 포맷 강점 추천 사용자
Ollama CLI + REST API GGUF 설치 1줄, 모델 풀이 큐레이션됨, Docker 친화 입문자~중급 개발자, RAG 백엔드

실전 결정 기준

  • 개인 PC에서 처음 시작: Ollama 또는 LM Studio. 둘 다 설치 후 곧바로 첫 응답을 받을 수 있습니다.
  • RAG·앱에 통합: Ollama. 공식 문서 기준으로 http://localhost:11434/v1/ 아래에 /v1/chat/completions·/v1/embeddings·/v1/responses 등 OpenAI 호환 엔드포인트를 제공하므로(2026-09-29 확인) 기존 코드를 거의 그대로 쓸 수 있습니다.
  • 맥북에서 최대 성능: llama.cpp(Metal 빌드) 또는 Ollama. 둘 다 Metal 가속을 활용합니다.
  • 다수 사용자 동시 서비스: vLLM. PagedAttention 기반이라 대량 동시 요청 처리에 강합니다.

Ollama 5분 시작

# 1) 설치 (Linux/macOS)
curl -fsSL https://ollama.com/install.sh | sh

# 2) 모델 다운로드 및 실행
ollama run qwen2.5:7b

# 3) OpenAI 호환 API로 호출
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen2.5:7b",
    "messages": [{"role":"user","content":"안녕하세요"}]
  }'

4. 양자화 가이드: Q4·Q5·Q8을 언제 쓸 것인가

양자화(Quantization)는 모델 가중치를 16-bit 부동소수점에서 4-bit, 5-bit, 8-bit 수준으로 압축하는 기술입니다. 메모리·속도를 절약하는 대신 약간의 품질 손실을 감수합니다. 가장 널리 쓰이는 형식은 GGUF 포맷의 K-quants 계열이며, 자주 보이는 변종은 다음과 같습니다. 메모리 절감률은 Qwen 공식 저장소의 Qwen2.5-7B-Instruct GGUF 파일 크기(FP16 15.24GB 기준)로 계산했습니다.

양자화 메모리 절약 (FP16 대비, 7B 파일 크기) 품질 손실 (상대 순서) 속도 권장 작업
Q4_K_M 약 69% 절감 (4.68GB) 넷 중 가장 큼 가장 빠름 일반 대화, 단순 요약, 챗봇
Q5_K_M 약 64% 절감 (5.44GB) 작음 빠름 번역, 코드 자동완성, RAG
Q6_K 약 59% 절감 (6.25GB) 더 작음 중간 장문 코드 생성, 추론 체인
Q8_0 약 47% 절감 (8.10GB) 거의 없음 느림 품질 우선 작업, 벤치마크

작업별 양자화 매칭

  • 일상 대화·요약: Q4_K_M으로 충분. 같은 VRAM에 더 큰 모델(예: 14B Q4)을 넣는 게 7B Q8보다 일반적으로 낫다는 평가가 많습니다.
  • 코딩 어시스턴트: Q5_K_M 이상 권장. 코드 토큰은 한 글자 오차가 컴파일 실패로 이어지므로 손실에 민감합니다.
  • 번역: Q5_K_M이 균형점. Q4는 미묘한 뉘앙스에서 손실이 누적되고, Q8은 속도 손해가 큽니다.
  • 법률·의료 문서: Q6_K 이상. 단어 하나의 의미가 결정적이므로 품질 우선.
"같은 VRAM이면 큰 모델 + 강한 양자화가 낫다"

예를 들어 12GB VRAM에는 Qwen 2.5 7B Q8_0(8.10GB)을 넣을 수도 있고 Qwen 2.5 14B Q4_K_M(8.99GB)을 넣을 수도 있습니다. 파일 크기는 거의 같지만, 파라미터 수가 양자화 손실보다 출력 품질에 더 크게 기여한다는 이유로 후자가 낫다는 평가가 많습니다(과제에 따라 다릅니다). 그래서 "내 VRAM에 여유를 두고 들어가는 최대 크기 모델을 Q4로 돌린다"가 일반 사용자에게 합리적인 출발점입니다.

5. 자동 추천 도구의 의의와 한계

whichllm 같은 도구는 "내 PC 스펙을 입력하면 추천 모델을 알려준다"는 단순한 컨셉입니다. 본격적인 도구라기보다 "오픈 LLM 생태계가 너무 복잡해져서 진입 장벽이 생겼다"는 신호로 읽는 것이 정확합니다. 모델은 계속 새로 나오고, 양자화 변종도 많습니다. Qwen 공식 GGUF 저장소에는 Qwen2.5-7B 하나에 FP16을 포함해 9가지 변종이, 한 커뮤니티 저장소에는 Llama 3.3 70B 하나에 약 30가지 GGUF 변종이 올라와 있습니다. 동일한 모델도 런타임마다 메모리 사용량이 다릅니다. 이 미궁에서 길을 잃는 사용자가 많다는 뜻입니다.

이런 도구의 한계도 분명합니다. 첫째, 실제 추론 속도는 모델 크기와 양자화만으로 결정되지 않습니다. 토크나이저 효율, KV 캐시 크기, 컨텍스트 길이, 동시 요청 수, 메모리 대역폭 등 변수가 많습니다. 둘째, 품질 만족도는 사용자 작업 종류에 따라 천차만별이며 자동 도구가 평가할 수 없습니다. 셋째, 한국어 성능은 영어 벤치마크 점수와 별개로 봐야 하는데, 자동 도구 대부분은 영어 기준으로만 추천합니다.

결국 자동 도구는 "1차 거름망"으로 쓰고, 최종 선택은 두세 개 후보를 자신의 작업으로 직접 돌려보고 정하는 것이 정확합니다. 본 글의 매트릭스가 그 1차 거름망의 역할을 합니다.

6. 한국 사용자 특별 고려사항

6-1. 한국어 지원은 모델 카드부터 확인

모든 오픈 LLM이 한국어를 같은 수준으로 다루지는 않습니다. 먼저 각 모델 카드가 밝힌 지원 언어를 확인하십시오(2026-09-29 확인).

  1. Qwen 2.5 (7B/14B/32B/72B): 모델 카드에 "29개 이상 언어 지원"이 명시돼 있고, 나열된 언어에 한국어가 들어 있습니다.
  2. Llama 3.1/3.3: 공식 지원 언어는 영어·독일어·프랑스어·이탈리아어·포르투갈어·힌디어·스페인어·태국어 8개로, 한국어는 들어 있지 않습니다. 모델 카드는 라이선스를 지키는 조건으로 다른 언어 파인튜닝을 허용하며, Hugging Face에서 한국어 파인튜닝 변종을 찾을 수 있습니다.
  3. Phi-3.5 mini·gpt-oss 등 그 밖의 모델: 지원 언어와 한국어 품질은 모델 카드에서 먼저 확인하고, 자신의 과제로 두세 개를 비교해 보는 것이 안전합니다.

6-2. Apple Silicon Mac: 담을 수 있는 크기와 속도는 다르다

Apple Silicon은 통합 메모리(Unified Memory) 구조라 RAM 대부분을 GPU가 함께 씁니다. 그래서 같은 VRAM의 외장 GPU보다 큰 모델을 담을 수 있습니다. 다만 발행 당시 적은 "24GB 맥북에서 70B Q3, 64GB 맥북에서 70B Q8"은 파일 크기와 맞지 않아 정정합니다. Llama 3.3 70B Q3_K_M은 34.27GB, Q8_0은 74.98GB라 각각 24GB·64GB에 들어가지 않습니다. OS와 다른 앱이 쓰는 몫까지 빼면 70B Q4_K_M(42.52GB)은 64GB, Q8_0은 128GB 구성이 현실적인 출발점입니다. 속도는 메모리 대역폭에 크게 좌우됩니다. 공식 사양 기준 대역폭은 M5 153GB/s, M5 Pro 307GB/s, M5 Max 460~614GB/s, RTX 5090 1,792GB/s입니다(2026-09-29 확인). 큰 모델을 담는 것과 빠르게 돌리는 것은 다른 문제입니다.

6-3. Hugging Face 다운로드

다운로드 속도는 회선·시간대·모델 크기에 따라 크게 달라집니다(Llama 3.3 70B Q8_0 파일 하나가 74.98GB입니다). 발행 당시 소개한 hf_transfer(HF_HUB_ENABLE_HF_TRANSFER)는 Hugging Face 공식 문서에서 폐기(deprecated)로 표시됐습니다. 허브의 파일 전송이 Xet 백엔드(hf-xet)로 바뀌면서 hf_transfer는 더 이상 쓰이지 않으며, 고성능 모드는 HF_XET_HIGH_PERFORMANCE로 켭니다. CLI 명령도 hf입니다(2026-09-29 확인). Ollama는 자체 레지스트리에서 모델을 받습니다.

# Hugging Face CLI 다운로드 (공식 문서 기준, 2026-09-29)
pip install -U huggingface_hub
export HF_XET_HIGH_PERFORMANCE=1
hf download Qwen/Qwen2.5-14B-Instruct-GGUF --include "*q4_k_m*.gguf" --local-dir ./models
# 파일이 여러 조각(-00001-of-0000N)으로 나뉘어 있으면 조각을 모두 받는다

6-4. 24시간 추론 서버의 전기료

RTX 4090을 종일 추론 부하 50%로 가동해 평균 200W를 쓴다고 가정하면, 200W × 24시간 × 30일 = 월 144kWh입니다. 한국 가정용 누진제 최고 구간 단가를 발행 당시 적은 약 285원/kWh(2026년 5월 기준, 갱신 확인 못 함)로 잡으면 144kWh × 285원 ≈ 월 41,000원이 추가됩니다. 발행 당시 적은 "월 약 30,000원"은 계산 오류라 정정합니다. 실제 요금은 기존 사용량과 계절별 구간에 따라 달라집니다. 사용량이 많으면 클라우드 API보다 싸질 수 있지만 "공짜"가 아니라는 점은 인지하고 시작해야 합니다.

7. 결론: 2026년 누구에게 무엇을 권하는가

사용자 유형 1순위 추천 이유

로컬 LLM은 더 이상 "취미"가 아닙니다. 발행 당시에는 7B 클래스를 GPT-3.5 대체재, 14B~32B를 GPT-4 상당 부분의 대체재로 보는 평가가 많았지만, 이 비교는 과제별로 크게 다르니 자신의 작업으로 확인하십시오. "파일 크기에 여유분을 더해 내 VRAM에 들어가는 최대 크기 모델을 Q4_K_M으로 돌린다"는 단순 원칙을 기억하면 시행착오를 크게 줄일 수 있습니다.

본 사이트의 Claude Code 가이드나 AI 기술 전망 2026과 함께 읽으면 클라우드 LLM과 로컬 LLM을 어떻게 조합할지 그림이 더 명확해질 것입니다.

# 로컬 LLM 하드웨어 점검표 - 내 메모리에 들어가는 모델 고르기

기준일: 2026-09-29. 파일 크기는 Hugging Face에 공개된 GGUF 파일 기준이고, 하드웨어 수치는 NVIDIA·Apple 공식 사양 기준이다.
가격은 다루지 않는다(지역·시기별 변동이 크다).

---

## 1. 먼저 할 일 3단계

- [ ] 내 GPU의 **VRAM 용량**을 확인한다 (Mac이면 통합 메모리 용량). 같은 이름에 용량이 다른 판이 있다: RTX 3060은 12GB·8GB, RTX 5060 Ti는 16GB·8GB
- [ ] 쓰려는 모델의 **GGUF 파일 크기**를 확인한다 (아래 표)
- [ ] **파일 크기 + 여유분**(컨텍스트 길이에 비례하는 KV 캐시, 런타임 사용량)이 VRAM 안에 들어가는지 본다. 넘치면 RAM으로 오프로드되어 속도가 크게 떨어진다

Mac은 OS와 다른 앱이 쓰는 몫을 통합 메모리에서 빼고 계산한다.

---

## 2. GGUF 파일 크기 참조표

| 모델 | Q4_K_M | Q5_K_M | Q6_K | Q8_0 | FP16 |
|---|---|---|---|---|---|
| Qwen 2.5 7B | 4.68GB | 5.44GB | 6.25GB | 8.10GB | 15.24GB |
| Qwen 2.5 14B | 8.99GB | 10.51GB | 12.12GB | 15.70GB | 29.55GB |
| Qwen 2.5 32B | 19.85GB | 23.26GB | 26.89GB | 34.82GB | 65.54GB |
| Qwen 2.5 72B | 44.01GB | 51.67GB | 59.86GB | 77.53GB | 145.93GB |
| Llama 3.3 70B (커뮤니티 양자화) | 42.52GB | 49.95GB | 57.89GB | 74.98GB | 141.12GB |

- gpt-oss-20b: 모델 카드에 "16GB 메모리 안에서 실행"으로 명시
- Llama 3.3 70B Q3_K_M은 34.27GB — 24GB·36GB 메모리에 들어가지 않는다

---

## 3. 메모리 구간별 결정표

| 내 메모리 | 현실적인 상한 | 넣으면 안 되는 것 |
|---|---|---|
| VRAM 8GB | 7B~8B Q4~Q5 (Qwen 2.5 7B Q4_K_M 4.68GB) | 14B Q4_K_M (8.99GB) 이상 |
| VRAM 12GB | Qwen 2.5 14B Q4_K_M (8.99GB) | 14B Q8_0 (15.70GB) |
| VRAM 16GB | Qwen 2.5 14B Q5_K_M (10.51GB), gpt-oss-20b | 32B Q4_K_M (19.85GB) |
| VRAM 24GB | Qwen 2.5 32B Q4_K_M (19.85GB) | 32B Q8_0 (34.82GB), 70B Q4_K_M (42.52GB) |
| VRAM 32GB | Qwen 2.5 32B Q6_K (26.89GB) | 70B Q4_K_M (42.52GB) |
| 통합 메모리 36GB | Qwen 2.5 32B Q4_K_M (19.85GB) | 70B Q3_K_M (34.27GB) |
| 통합 메모리 64GB | Llama 3.3 70B Q4_K_M (42.52GB) | 70B Q8_0 (74.98GB) |
| 통합 메모리 128GB | Llama 3.3 70B Q8_0 (74.98GB) | 405B Q4 (약 240GB 이상, 계산값) |

VRAM을 넘는 모델은 RAM 오프로드로 "돌아는 가지만" 느리다. 실용 기준은 VRAM 안이다.

---

## 4. 양자화 선택

| 양자화 | FP16 대비 절감 (Qwen 2.5 7B 파일 기준) | 품질 손실 (상대 순서) | 쓰는 곳 |
|---|---|---|---|
| Q4_K_M | 약 69% | 넷 중 가장 큼 | 일반 대화·요약 |
| Q5_K_M | 약 64% | 작음 | 번역·코드 자동완성·RAG |
| Q6_K | 약 59% | 더 작음 | 장문 코드·추론 체인, 법률·의료 문서 |
| Q8_0 | 약 47% | 거의 없음 | 품질 우선·벤치마크 |

- [ ] 같은 VRAM이면 "큰 모델 + Q4"를 먼저 시도한다 (예: 12GB에서 7B Q8_0 8.10GB 대신 14B Q4_K_M 8.99GB)
- [ ] 코딩은 Q5_K_M 이상에서 시작한다

## 5. 속도는 메모리 대역폭을 본다

| 하드웨어 | 메모리 | 대역폭 (공식 사양) |
|---|---|---|
| RTX 5090 | 32GB | 1,792GB/s |
| RTX 5080 | 16GB | 960GB/s |
| RTX 5070 | 12GB | 672GB/s |
| M5 Max | 최대 128GB | 460~614GB/s |
| M5 Pro | - | 307GB/s |
| M5 | 최대 32GB | 153GB/s |

담을 수 있는 크기와 빠르게 도는 속도는 다른 문제다.

---

## 6. 런타임 선택

- [ ] 처음 시작 → Ollama 또는 LM Studio
- [ ] 앱·RAG 연동 → Ollama (`http://localhost:11434/v1/` 아래 `/v1/chat/completions`·`/v1/embeddings`·`/v1/responses`)
- [ ] 맥 최대 성능 → llama.cpp(Metal 빌드) 또는 Ollama
- [ ] 다수 사용자 동시 서비스 → vLLM (70B FP16 가중치만 약 141GB, 멀티 GPU)

---

## 7. 다운로드 명령 (2026-09-29 공식 문서 기준)

```
pip install -U huggingface_hub
export HF_XET_HIGH_PERFORMANCE=1
hf download Qwen/Qwen2.5-14B-Instruct-GGUF --include "*q4_k_m*.gguf" --local-dir ./models
```

- `hf_transfer`·`HF_HUB_ENABLE_HF_TRANSFER` 는 폐기됐다. 고성능 모드는 `HF_XET_HIGH_PERFORMANCE`
- `huggingface-cli` 대신 `hf`
- llama.cpp 저장소는 `github.com/ggml-org/llama.cpp`

---

## 8. 한국어 지원 (모델 카드 기준)

- Qwen 2.5: 29개 이상 언어, 목록에 한국어 명시
- Llama 3.1/3.3: 공식 지원 8개 언어에 한국어 없음. 파인튜닝 변종을 찾는다
- 그 밖의 모델: 모델 카드 확인 후 자신의 과제로 두세 개 비교

---

## 9. 전기료 계산식

월 사용량(kWh) = 평균 소비전력(W) × 24 × 30 ÷ 1000
예: 200W 가정 → 144kWh. 144kWh × 단가 = 월 추가 요금.
단가는 본인 요금제·계절 구간으로 넣는다.
