πFS - データをハードディスクではなく円周率πに保存するというファイルシステム

データのないファイルシステムの発想、なぜ無意味なのか、そしてその冗談が教える真剣な情報理論

2026-06-12 IT・技術

はじめに：データを保存しないファイルシステムという冗談

2026年6月にnews.hada.ioで再び話題になったトピックの一つがπFS（パイ・ファイルシステム）でした。提案はこうです。あなたのファイルをハードディスクに書かないでください。代わりに、そのファイルが円周率πの数字のどこかにすでに含まれている位置（オフセット）だけを記録してください。πは無限なので、データそのものはどこにも保存する必要がありません。

最初に聞くと天才的な無限圧縮のように聞こえます。あらゆるデータをたった一つの数、位置の値で置き換えるのですから。しかし少し考えればこれは動作しません。そしてなぜ動作しないのかこそ、この冗談の本当の価値です。πFSはPhilip Langdaleが作った、わざと役に立たないようにしたファイルシステムであり、同時に情報理論・数論・圧縮の限界を一度に教える教育的な寓話です。

本記事は単なる紹介ではありません。12個のH2を通じて、(1) πFSの発想、(2) 動作メカニズム、(3) 正規数とは何か、(4) πの正規性がなぜ未証明なのか、(5) 無限の猿定理とのつながり、(6) オフセットがデータより大きい理由、(7) 検索コストの天文学的な規模、(8) コルモゴロフ複雑性、(9) 圧縮の情報理論的限界と鳩の巣原理、(10) 似た冗談（魔法の圧縮など）、(11) 開発者が得る洞察、(12) 結論まで扱います。ユーモアは保ちつつ、数学の事実は正確にが原則です。

一行要約 - πFSはデータをπの中の位置に変えますが、その位置の値はデータと同じくらい大きいため節約になりません。情報は表現を変えても消えません。

1. πFSの発想 - すべてのデータはすでにπの中にある

発想の出発点は一文です。「πが正規数なら、πの無限の数字の中にはあらゆる有限の数字列が必ず現れる」。あなたの写真、映画、小説、どんなファイルも結局は0と1（あるいは0〜9）の有限の並びです。であれば、その並びはπのどこかの位置にそっくり同じに現れるはずです。

この観察自体は新しくありません。「πは無限だから自分の誕生日もシェイクスピア全集もその中にある」という話は昔から語られてきました。πFSの巧妙さは、この観察をファイルシステム設計として真剣に（冗談めかして）実装した点にあります。データを保存する代わりにデータの「住所」を保存する — まるで本そのものをコピーする代わりに図書館の請求記号だけを書き留めるようなものです。

問題はこの比喩にすでに表れています。図書館にすべての本が実際に並んでいれば請求記号は短いです。しかしπという「図書館」は無限で、その中から特定のデータを探すには請求記号（オフセット）がデータと同じか、それより長くなります。πFSのすべての冗談はこの一点に収束します。

2. 動作メカニズム - オフセットとメタデータ

実際のπFS実装はどう動くのでしょうか。Philip Langdaleの原本を基準に整理するとこうです。

  • 分解：ファイルをバイト（あるいはより小さい単位）に分けます。
  • 検索：各単位がπの数字表現（BBP公式などで桁を直接計算）で最初に現れる位置を探します。
  • 記録：その位置（オフセット）とファイル構造を実際のディスクのメタデータディレクトリに保存します。
  • 復元：読み出すときは保存したオフセットでπの該当する桁を計算し直し、元のバイトを復元します。

核心的な矛盾がまさにここにあります。データそのものはディスクに書かないが、位置を指すメタデータはディスクに書くのです。そしてそのメタデータのサイズが元のデータより大きい。つまり「データを保存しない」という主張は形式的にしか正しくなく、実際のディスク使用量はむしろ増えます。原本のREADMEさえ容量の節約を主張せず、この矛盾を冗談の核にしています。

# 概念的な擬似コード（実際には節約がないことを示す例）
file = [0x48, 0x49]              # "HI"、2バイト = 16ビット
offset_H = πで0x48が最初に現れる位置   # 天文学的に大きい整数
offset_I = πで0x49が最初に現れる位置   # やはり巨大な整数
metadata = [offset_H, offset_I] # 二つの巨大整数 → 元より大きい
# 結果：2バイトをなくすために数十〜数百バイトのオフセットを保存

3. 正規数（normal number）とは何か

πFSの前提を理解するには正規数の概念が必要です。ある実数がある基数（base）で正規（normal）であるとは、その基数表現において各数字とあらゆる長さの数字の並びが均等な頻度で現れることを意味します。たとえば10進法で0〜9がそれぞれ1/10の頻度で、00〜99がそれぞれ1/100の頻度で現れるといった具合です。

正規数の重要な性質の一つが離接性（disjunctive）です。すべての基数で正規な数（絶対正規数）はあらゆる有限の数字列を部分列として含みます。つまり正規数なら「自分が欲しいどんなデータもその中のどこかにある」が数学的に真になります。πFSの前提はまさに「πが正規数だ」ということです。

注意 - 「無限で繰り返さない（無理数）」というだけではあらゆる数列を含むとは保証されません。たとえば0.1010010001000010...は無理数ですが数字の2が一切ありません。「あらゆる数列を含む」は無理数ではなく正規性（少なくとも離接性）から来ます。

4. πの正規性はまだ証明されていない

ここで最も重要な事実をはっきりさせます。πが正規数であることは2026年時点でも証明されていません。推測（conjecture）にすぎません。

数学者はπ、e、√2のような大半の「自然な」無理数が正規数だろうと信じていますが、特定の数の正規性を証明することは驚くほど難しいです。πについては数兆桁まで計算した統計が正規性とよく一致しますが、有限の桁数をいくら検査しても正規性の証明にはなりません。さらに衝撃的なのは、0から9までの各数字がπに無限回現れるかどうかすらまだ証明されていないことです。

したがって正確な表現はこうです。「πは正規数だと推測され、そうであればあらゆる有限データがその中に現れる — しかしその前提自体が未証明である」。πFSは動作しないだけでなく、それが動作するための数学的前提さえまだ仮説という二重の限界の上に立っています。本記事で最も強調したい訂正ポイントです。

5. 無限の猿定理とのつながり

正規数の直観は有名な無限の猿定理と同じ根から来ています。猿がタイプライターの前で無限にランダムにキーを打てば、シェイクスピア全集をほぼ確実に（almost surely）いつか打つという命題です。

数学的にはこう表されます。有限のアルファベットから各文字を独立・均等にランダムに選んで無限数列を作ると、与えられたどんな有限文字列もほぼ確実にその数列の部分列として現れる。これはあらゆる有限文字列の集合が可算（countable）であることに依拠します。正規数があらゆる数列を含むという性質と本質的に同じ直観です。

ただし落とし穴があります。「ほぼ確実に」は確率1を意味するのであって、速い・実用的という意味ではありません。猿が「Hamlet」という6文字を打つまでの期待時間ですら宇宙の年齢を圧倒します。πFSも同じです。あなたのデータがπの中に「ある」ことと、それを「探して使う」ことはまったく別の問題です。存在性と実用性の混同 — これがπFSという冗談の正確な急所です。

6. オフセットがデータより大きい理由 - 節約はない

ではπFSが無意味な核心的理由を定量的に見ましょう。結論から言えばπでデータが現れる位置（オフセット）はほぼ常にデータ自体より大きいのです。

直観は単純です。πをランダム数列として扱うと、長さNビットの特定パターンが最初に現れる位置はおよそ2のN乗桁あたりです。ところが2のN乗桁の位置の値を表すには再び約Nビットが必要です。つまりデータNビットをなくす代償に位置の値Nビットを新たに保存することになります。節約は0か、むしろ損です。

保存方式データビットインデックス/オフセットビット実質効果
そのままディスクに保存N0基準線
πFS（オフセット保存）0約N（またはそれ以上）節約なし
オフセットをまたπに保存0インデックスのインデックスが必要無限再帰

最後の行が決め手です。「オフセットが大きいなら、そのオフセットもπFSで保存すればいいのでは」と思うかもしれませんが、そうするとインデックスのインデックス、そのインデックスのインデックス…が果てしなく必要になります。どの段階でも情報量は減りません。これが情報理論の言う「ただの圧縮はない」の具体的な形です。

7. 検索コストの天文学的な規模

仮に保存スペースの問題を無視しても、πから欲しいデータを「探す」コストがもう一つの壁です。

πの任意の桁を直接計算するBBP（Bailey–Borwein–Plouffe）公式のような方法はあります。しかしπFSがやろうとするのは逆方向です。与えられたバイトパターンがπで最初に現れる位置を探す — これは無限数列での検索であり、パターンが長くなるほど候補位置が指数的に遠ざかります。数バイトを超えた瞬間、検索は現実的に不可能になります。

そのため実際のπFS実装は通常、一度に1バイト（あるいはそれ以下）ずつ探してオフセットを積みます。これは検索コストを下げますが、6章のオフセット爆発問題を正面から蘇らせます。検索コストを下げれば保存コストが爆発し、保存を減らそうとパターンを長くすれば検索が不可能になるというトレードオフ — どちらに進んでも袋小路です。この両面挟撃がπFSを「完璧に無用な」設計にしています。

8. コルモゴロフ複雑性 - データの本質的な情報量

なぜどんな表現に変えても情報が減らないのでしょうか。その答えがコルモゴロフ複雑性（Kolmogorov complexity）です。

コルモゴロフ複雑性C(x)は、ある文字列xを出力する最短プログラムの長さで定義されます。これがデータの「本質的な情報量」です。規則的なデータ（例：「010101…」1万回）は短いプログラムで生成されるので複雑性が低く、ランダムに近いデータは自分自身を丸ごと書くより短いプログラムがないので複雑性が高くなります。

πFSの観点から見ると興味深いです。「データをπのオフセットで表す」とは、そのデータを生成する一つのプログラム（「πのi番目の桁からk個を出力せよ」）を書くことと同じです。ところがそのプログラムの長さはオフセットiのサイズに支配され、iは前に見たようにデータと同じくらい大きい。つまりπFS表現はデータのコルモゴロフ複雑性を減らせません。ランダムに近いデータはどんな巧妙な表現でも圧縮されないという事実を、πFSは迂回路で再確認してくれます。

9. 圧縮の限界 - 鳩の巣原理

「あらゆるデータを縮める完璧な圧縮器は作れない」という命題は鳩の巣原理（pigeonhole principle）できれいに証明されます。

長さNビットの文字列は全部で2^N個です。もしある可逆圧縮器がこれらをすべてNビット未満に縮めると仮定しましょう。Nビット未満の異なる文字列は2^N − 1個しかありません。2^N個を2^N−1個の巣に入れれば必ず二つ以上が同じ巣に入ります。すると一つの圧縮結果が異なる二つの元に対応し、復元が不可能になります — 可逆圧縮の定義に矛盾します。

したがってあらゆる入力を縮める完璧な可逆圧縮器は数学的に不可能です。実際、長さNの文字列のうちcビット以上縮められる割合はせいぜい2^(−c)であり、大半の文字列はほとんど圧縮されません（こうした文字列を「圧縮不可能」またはコルモゴロフ・ランダムと呼びます）。πFSはこの限界を破るように見えますが、実際にはオフセットという形で情報をそっくり移すだけで破ってはいません。πFSの失敗は圧縮限界定理のもう一つの証明なのです。

誤解注意 - 実用圧縮器（zip、zstdなど）が効果を出すのは「あらゆるデータ」ではなく「現実の構造あるデータ」を扱うからです。テキスト・画像・ログには繰り返しとパターンが多く、コルモゴロフ複雑性が低いです。圧縮は魔法ではなく構造の発見です。

10. 似た冗談 - 魔法の圧縮とその仲間

πFSは「不可能な圧縮」ユーモアの系譜の一枝です。似た思考実験があります。

10-1) 魔法/自己参照の圧縮

「私の圧縮器はどんなファイルでも1バイトに縮める」という類の主張です。鳩の巣原理で即座に反論されます。1バイト（256通り）では257個以上の異なるファイルを区別できません。繰り返し適用で無限圧縮するという変種も、結局情報がどこか（例：圧縮回数や復元器自体）に隠れるという点で同じ誤りです。

10-2) すべての本の図書館（ボルヘスのバベルの図書館）

あらゆる可能な本を収めた図書館では、「自分が欲しい本」を探すコストが本を書くコストを圧倒します。πFSのオフセット問題とまったく同じ構造です。存在するからといってアクセス可能とは限りません。

10-3) ハッシュをデータと取り違える

「ファイルのハッシュ値だけ保存すればいいのでは」という誤解もよくあります。ハッシュは一方向なので元の復元が不可能で（衝突も存在）、逆算するには事実上元の情報がまた必要です。やはり「ただの情報はない」の変奏です。

11. 開発者が得る洞察

この冗談から実務開発者が持ち帰るべき教訓を整理します。

11-1) 情報は表現を変えても消えない

データをインデックス・ハッシュ・オフセット・別の座標系に移しても、本質的な情報量（コルモゴロフ複雑性）は減りません。「どこかにすでにあるから位置だけ保存しよう」という類の設計に出会ったら、まずその位置の値のサイズを検討してください。

11-2) 存在性と実用性を混同するな

「理論上可能」と「現実で使える」は違います。無限・正規性・確率1のような数学的性質は強力ですが、検索コスト・時間計算量を無視すると実用性と正反対の結論になります。

11-3) 圧縮は構造の発見である

現実データが圧縮されるのは繰り返しとパターン、つまり低いコルモゴロフ複雑性のためです。圧縮率を上げたいならデータの構造を理解すべきで、表現を変えるトリックでは限界を超えられません。

11-4) 冗談の中の数学を真剣に検証する

πFSのような「明らかに冗談」の設計も、正規数・鳩の巣・コルモゴロフのような本物の数学を正確に押さえてこそ正しく理解できます。お勧めの習慣は、もっともらしい主張に出会ったら情報理論の保存則で一度検算してみることです。

12. 結論 - 動作しないが完璧な思考実験

πFSを一文で要約するとこうです。「データをπの中の位置に変えることには成功するが、その位置がデータと同じくらい大きく、何も節約できない、意図的に無用なファイルシステム」。

しかし無用さこそこのプロジェクトの価値です。πFSは、(1) πの正規性がまだ未証明の仮説であること、(2) 「ほぼ確実に存在する」と「実用的に使える」は違うこと、(3) オフセット・検索の両面挟撃で節約が不可能なこと、(4) コルモゴロフ複雑性と鳩の巣原理が完璧な圧縮を禁じることを一度に教えます。動作しないコード一つが情報理論の一学期を圧縮したわけです — これは本物の圧縮です。

残したいメッセージはこれです。奇抜な無限保存のアイデアに出会ったら笑い、しかし情報保存則で検算せよ。圧縮と保存は魔法ではなく構造と限界の科学です。πFSはその真実を、最も楽しい方法で教えてくれます。
