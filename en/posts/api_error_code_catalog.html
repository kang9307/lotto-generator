What It Means to Design an Error Code Catalogue - Numbers or Strings, and Who Gets to Add One

A code is worth something only when the client can do something different because of it

2026-08-01 Dev & Infra

Opening: the client was comparing error message strings

Chasing a bug report on a checkout screen, I ran into this.

if (res.body.message.includes('already paid')) {
  goToReceipt();
}

My first reaction was to ask who wrote it. Then I opened the server response and could not blame that developer at all. Everything the server sent back was a status code of 400 and one sentence written for a human. With that alone, there is no way to tell an order that is already paid from an order with insufficient funds except by comparing the sentence.

So this is not the client being sloppy. It is the server never having handed over a contract. The name of that contract is the error code.

From here the usual reactions split two ways. One camp says let us add error codes and starts a list. The other says a growing list becomes unmanageable and puts it off. Both miss the same thing. An error code is not documentation, it is a contract. You fix documentation when it is wrong. You cannot unilaterally change a contract once the other party is holding it.

This article is about designing that contract. Not how many codes to create, but what should decide where the lines fall, why a code cannot change while a message can, and what has to be automated so the list does not rot.

Environment. Every output below was produced on Windows 10 Pro (10.0.19045) with Node.js v22.16.0 (win32). Every API, error code and team name that appears is entirely fictional, borrowing the familiar order-and-payment domain to reproduce the situation. Scripts were saved to files and run from there.

What this article does not cover. Pointing at which field failed validation lives inside the details part of the schema and belongs to its own article. Finding who is still receiving a code you want to retire is another topic on its own. Here I look only at the design and lifetime of the code itself. Other contract surfaces of a response are in turning API docs into a machine-readable contract and what offset pagination cannot do.

1. The question a status code cannot answer

First I reproduced the problem precisely. A fictional payment API, six different failures.

node v22.16.0 / win32
--- 1-1. six different failures, one status ---
case            status  message
------------------------------------------------------------------------------
missing id      400     orderId is required
bad id format   400     orderId format is invalid
already paid    400     this order is already paid
window closed   400     the payment window has closed
no money        400     insufficient balance
gateway down    400     gateway temporarily unavailable
distinct statuses observed : [400]

--- 1-2. client branching on status only ---
case            decided action        action it actually needed
------------------------------------------------------------------------------
missing id      ???                   highlight the form field
bad id format   ???                   highlight the form field
already paid    ???                   send user to the receipt
window closed   ???                   reopen the payment sheet
no money        ???                   offer another card
gateway down    ???                   retry in 30 seconds
cases the client could not decide : 6 / 6

Six failures collapsed into a single status code. The only distinct status observed was 400. Yet the right-hand column shows six different things the client needs to do. Writing the status-only branch and actually running it left all six cases undecidable.

There is an easy misreading here. This does not mean status codes are bad. A status code is the axis that proxies, caches and retry layers read, and it fits that purpose well. The problem is trying to decide what to show a user at that resolution. Wrong axis.

1.1 So people start comparing sentences

--- 1-3. the workaround: matching the message string ---
missing id      show the raw message
bad id format   show the raw message
already paid    send user to the receipt
window closed   show the raw message
no money        offer another card
gateway down    retry in 30 seconds

--- 1-4. server rewords one message, nothing else changes ---
before : this order is already paid          -> send user to the receipt
after  : This order has already been paid.   -> show the raw message
same failure, different client action : true
nobody deployed the client. nobody changed the status. a copy edit did this.

Comparing sentences resolved three cases exactly right. That is why the approach survives. It works at first and nobody feels a problem.

Then someone polishes the copy. The last block is that moment. Capitalising the first letter, adding a full stop and reordering a clause was all it took, and the client now behaves differently for the same failure. Nobody deployed the client. Nobody touched the status. A copy edit did it.

  • This failure leaves no trace in the deploy history, because only one server line changed, and only a string literal at that
  • Tests rarely catch it either. Server tests assert the status, and client tests use fixtures they wrote themselves
  • The moment you add translations it becomes a branch that works in one language. A comparison tuned to English fails everywhere else
  • The root cause is the server having offered only a human field. The client can only branch on what it has

The standards say so explicitly. RFC 9457, which defines the error body format for HTTP APIs, states that consumers should not parse the human-readable detail and that extension members are the appropriate place instead. In other words, give machines their own axis.

2. Numbers or strings

Once you decide to build a machine axis, the next question is its shape. E1043 or ORDER_ALREADY_PAID. I wrote the branch both ways.

  if (err.code === "E1051") return offerAnotherCard();

The typo result is decisive. Once a numeric range has filled in, getting one digit wrong lands you on another real code. Three of four typos did exactly that, and all three took a different branch with no exception and no warning. Mistyping a word leaves you outside the list and drops you into the default. All five string typos were caught that way.

Search behaves the same. Grepping a log for the bare number also matched latency and byte counts that happened to share the value, so finding two real hits cost five lines. Being precise means searching the field name too. The string had zero false positives.

  • On embedded devices or over text messaging, where bandwidth genuinely costs money, numbers are the right call
  • Everywhere else sixteen bytes is smaller than one header. You are buying readability six months out at that price
  • A middle path exists: make the string the contract and ship the number alongside as a secondary field. The cost is maintaining two axes
  • Either way, you cannot change it later. Changing the shape is changing every code at once

3. Names collide as domains multiply

Choosing strings does not finish the job. Names invented when there was one team collide the moment there are three. I reproduced three teams each shipping a flat list.

--- 3-1. three flat lists, merged into one gateway ---

collisions                           : 5

code         kept (first writer wins)        from       lost                            from
------------------------------------------------------------------------------------------------
NOT_FOUND    order does not exist            orders     invoice does not exist          billing
EXPIRED      the payment window has closed   orders     the card has expired            billing

--- 3-2. what the client sees for a shipping lookup miss ---
server sends : NOT_FOUND
client asks  : not found... of what?
client branch on NOT_FOUND from shipping -> send the user back to the order list
correct action for a missing tracking id -> show the carrier retry hint
the branch is not wrong. the code is ambiguous.

Eleven codes passed through the gateway and came out as six. Five collided, and where they did, whoever registered first won and the rest vanished. The teams that lost do not know. Testing their own service in isolation works fine.

3-2 is the consequence. A shipping lookup miss arrives as NOT_FOUND, and the branch in the client was written by the orders team. The branch is not wrong, the code is ambiguous. It says not found, and never says of what.

With prefixes, eleven codes survived as eleven. Zero collisions. The price is 7.4 characters per code on average.

The usual objection is that the service name is already in the URL, so why repeat it. The answer is that codes live outside the response. In log aggregation, in metric labels, in support tickets and inside a client enum, a code appears alone with no URL attached. In those places NOT_FOUND tells you nothing.

  • One layer of prefix is enough. The 42-character version that stacks company, product and domain destroys the log column, and only one of those parts is ever used
  • A repeated word like ORDER_ORDER_NOT_FOUND appears automatically when the domain and the subject share a name. A checker catches it
  • The suffixes _ERROR, _EXCEPTION and _FAILURE carry zero information. Everything in an error code list is an error
  • Any separator survives log parsing, but the moment a code becomes an enum member or a metric label only the underscore does. Dots and hyphens cannot be generated constant names
  • Set a length limit. Thirty-two characters keeps log alignment and readability at once

4. Stability is the contract - the code cannot move, the message can

This is the section that matters most. Assume a client shipped in January and now sitting on user phones. You cannot recall it. With that fixed, I changed the server two ways.

node v22.16.0 / win32
--- 4-1. baseline: the shipped client against server v1 ---
case      code                          client action
------------------------------------------------------------------------
paid      ORDER_ALREADY_PAID            showReceipt
funds     PAYMENT_INSUFFICIENT_FUNDS    offerAnotherCard
window    ORDER_WINDOW_CLOSED           reopenPaymentSheet

--- 4-2. v2: every message rewritten, codes untouched ---
paid      showReceipt           same as before: true
funds     offerAnotherCard      same as before: true
window    reopenPaymentSheet    same as before: true
branches broken by the rewrite : 0 / 3

--- 4-3. v3: one code renamed for readability, messages same as v2 ---
paid      ORDER_PAYMENT_ALREADY_COMPLETED   showGenericError      BROKEN
funds     PAYMENT_INSUFFICIENT_FUNDS        offerAnotherCard      ok
window    ORDER_WINDOW_CLOSED               reopenPaymentSheet    ok
branches broken by one rename  : 1 / 3
the user now lands on a generic error screen instead of the receipt.

The contrast is sharp. Rewriting all three messages broke zero branches. No amount of rewording matters because the client reads the code. Renaming a single code for readability killed that branch instantly. The user sees a generic error screen instead of a receipt.

That is the basis for the rule that messages may change but codes may not. And the rule only holds when you gave machines an identifier to read. Without a code it inverts. The client comes to depend on the sentence, so the message is what freezes. Large-scale API guidance says the same thing in the same order: an API that always shipped a machine-readable identifier may change its message text, while an API that started without one has to keep the text stable.

4.1 So when you do want a better name

--- 4-4. a release gate that compares the published code set ---
v2 (messages only)
  added   : (none)
  removed : (none)
  verdict : allow
v3 (one rename)
  added   : ORDER_PAYMENT_ALREADY_COMPLETED
  removed : ORDER_ALREADY_PAID
  verdict : REJECT - a published code disappeared

--- 4-5. the same rename, done without breaking anyone ---
paid      ORDER_ALREADY_PAID            showReceipt           ok
funds     PAYMENT_INSUFFICIENT_FUNDS    offerAnotherCard      ok
window    ORDER_WINDOW_CLOSED           reopenPaymentSheet    ok
v4 (rename announced, old code still emitted)
  added   : (none)
  removed : (none)
  verdict : allow

The gate is simple. Compare the code set against the previous version and stop the build if anything disappeared. Additions pass, because an unknown code merely falls through to the client default and breaks nothing.

If you really want the new name, do it like v4. Announce it in a supersededBy field and leave the value on the wire alone. Swap it only after confirming the old code emits zero traffic. And that is something only traffic can tell you, never a document.

  • A code name is a value, not a label. The urge to attach a better name later is the most dangerous one
  • For the same reason you cannot change the HTTP status of a code. Proxies and retry layers are already deciding on it
  • Retryability is likewise fixed per code. Change it and client auto-retry behaviour shifts silently
  • Conversely, adding a field to details is always allowed. It is an additive change, and old clients simply ignore it
  • Deleting a code is exactly as dangerous as renaming one. That is why deprecation needs a procedure of its own

5. The code is fixed, the human sentence is per language

If the code is the contract, what is the sentence a person reads? I ran both approaches: the server providing it, and the client composing it.

client-rendered : (nothing) - no template shipped for this code

a client that renders locally goes blank on any code newer than its last release.
a client that prints the server sentence always has something to show.

When the server picks the sentence, the fallback chain is the whole design. Serve the requested locale, fall back to the default language, and if even that is missing, send the code string itself. The last step looks odd but it beats a blank screen.

5-3 exposes the weakness of client-side translation. As soon as the server starts emitting a new code, a build that has never heard of it has no sentence to show. Clients release slowly and users postpone updates, so that state lasts months.

5.1 So send both

--- 5-2. server sends only the machine parts ---
{"code":"PAYMENT_INSUFFICIENT_FUNDS","params":{"required":42900,"available":12300,"currency":"KRW"}}
en    rendered locally              You need ₩42,900 but only have ₩12,300.
ko    rendered locally              PAYMENT_INSUFFICIENT_FUNDS ko template ₩42,900 ₩12,300

--- 5-4. so ship both, and say which one is which ---
en    client bundle                 You need ₩42,900 but only have ₩12,300.
ko    client bundle                 PAYMENT_INSUFFICIENT_FUNDS ko template ₩42,900 ₩12,300
ja    server message (fallback)     Your balance is not enough to complete this payment.

--- 5-5. what breaks if you translate the code itself ---
en    ORDER_ALREADY_PAID            showReceipt
ko    ORDER_ALREADY_PAID_KO         showGenericError
ja    ORDER_ALREADY_PAID_JA         showGenericError
locales where the branch still fires : 1 / 3

--- 5-6. coverage report you can run in CI ---

----------------------------------------------------------------------
ORDER_ALREADY_PAID            y     y     y     -     zh
PAYMENT_INSUFFICIENT_FUNDS    y     y     -     -     ja,zh

5-2 is the advantage of client composition. Instead of baking an amount into the server sentence, send the number and the currency and the client assembles it in its own locale format. The server never has to know every language grouping rule.

So the answer is not one or the other, it is both. As in 5-4, the client prefers its own template and prints the server sentence when it has none. New codes never leave a blank screen, and existing codes keep their locale formatting.

  • 5-5 shows what not to do. Making a code per language leaves the branch alive in exactly one of them. It fired in one locale out of three
  • A code is an identifier, not prose. Having no language is a property of a code, not an omission
  • Translation coverage is easy to table in CI. Six cells were empty in 5-6
  • What matters is that a translation hole and a missing code weigh differently. Without a translation you survive on the default language. Without a code the client cannot decide anything
  • There is a support angle too. What users screenshot is the sentence. Surfacing the code inside the sentence cuts ticket handling time sharply

6. Machine fields and human fields

Now design the whole response body. One principle: decide who each field is for, and write that down as the contract.

This is where teams split most often. I ran both designs side by side.

Counting codes, four versus three is not much of a gap. The difference appears in 6-4. When a provider outage persists and the circuit opens, the same failure crosses from retryable to permanent. In design A the code string itself moves.

The last two lines are the result. On a dashboard grouped by code, one incident split into two series. Design B stayed one. Why splitting a metric hurts becomes obvious during an incident: a graph halves and a new one appears under a new name, and in that moment nobody can say whether it is a new problem or the same one.

  • The third row of 6-5 is the important one. An absent field was read as not retryable. That is the safe default. Reading a missing field as retryable creates an infinite retry every time a new code appears
  • 6-6 re-confirms section 1 from another angle. Two heuristics against three wordings produced no stable answer at all. Over the same period the code and the retry field never moved
  • traceId plays a different role from the code. The code names the class of failure, the trace id names the one occurrence. Support uses the latter
  • Without a trace id you sweep by code and time window, which means thousands of rows. Requiring it on every error response is cheap and pays well
  • details is where specifics that do not warrant a code belong. Not turning them into new codes is how the list stays small

401   true       refresh the token and retry once  AUTH_TOKEN_EXPIRED (platform), AUTH_SESSION_EXPIRED (checkout)
500   true       retry with backoff                INTERNAL (platform), UNKNOWN_ERROR (checkout)
flagged groups : 5

7-3 puts a number on the thesis of this article. Twenty-three codes converge on twelve behaviours. Ten of them are beyond the first for their action. That does not make all ten wrong. Insufficient funds and a declined card both end in offer another card, but they are failures an operator must count separately, so they earn a code.

The genuinely suspicious ones are in 7-4: same action, same status, same retryability, different names. The owner column shows why. Of the three codes that lead to a receipt, two came from the orders team and one from checkout. Token expiry was built separately by platform and by checkout. Duplicate codes are usually not a technical problem but the record of two teams not talking.

7.1 Near-identical names, and what can actually be retired

--- 7-6. the deprecated one, and whether it can go ---

code                    emissions / 30d   verdict
------------------------------------------------------------------------------
ORDER_EXPIRED           0                 safe to delete from the catalogue
ORDER_WINDOW_CLOSED     4127              load bearing, leave it alone
ORDER_PAYMENT_DONE      3                 still emitted, find the caller first
UNKNOWN_ERROR           918               load bearing, leave it alone

The first row of 7-5 is a false positive. Strip the prefixes and the tokens match perfectly, but these are different failures in different domains. A checker like this proposes candidates, it does not rule. Pairs like ORDER_ALREADY_PAID and ORDER_ALREADY_SETTLED, which 7-4 also flagged, are the ones worth looking at.

7-6 is the reality of retirement. A code carries a deprecation mark, and that mark does not remove it. Thirty days at zero emissions is what earns a delete, and even three occurrences mean you go find the caller first.

  • Step one of adding a code is writing what the client does differently, in one sentence. If you cannot write it, you do not need the code
  • Step two is searching the existing list for that behaviour. Same action, same status, same retryability means it is details, not a new code
  • Record an owner for every code. A code with no owner is one nobody dares delete six months later
  • The last row matters most. UNKNOWN_ERROR at 918 in thirty days is not a code, it is 918 unclassified failures. First candidate to split
  • The signal that a list has rotted is read not from its size but from the share of catch-all codes

8-4 is the conclusion of this section. Of the codes the client branches on, two did not exist on the server. One was a misremembered name, the other a guess made without reading the docs. Both are dead branches that can never fire, and review never catches them, because the syntax is fine and the names look plausible.

Having the checker propose the nearest registered code turns out to be genuinely useful in practice. Token overlap alone was enough to point out that PAYMENT_DECLINED is a misremembering of PAYMENT_CARD_DECLINED.

  • The other direction, twelve unhandled codes, is a different animal. They land on the generic error screen but nothing breaks, so report them as a number rather than stopping the build
  • Coverage at 45.5 percent is not a bad figure by itself. The trend is what counts. If codes keep growing while branches do not, the list stops meaning anything
  • Only two things should fail a build: a code that broke its own rules and a branch that can never fire. A machine can be certain of both
  • Everything else stays a warning. Vague names and duplicate candidates are judgement calls, and blocking on them breeds a culture of bypassing the check
  • Measure the checker false positive rate first. A noisy checker gets ignored by everyone, and real errors get buried with it

10. Checklist and things not to do

Finally, a list to hold against the API you have right now.

  • Zero branches in the client compare a message string
  • Failures that share an HTTP status are separated by code
  • Every error response carries code and a trace id, always
  • When the retry field is missing, the retry layer reads it as not retryable
  • Retryability is not baked into any code string
  • Every code has a domain prefix and there are zero bare NOT_FOUND style codes
  • The code list lives in one file, and docs and client constants are generated from it
  • The release gate catches a disappeared code
  • Codes marked for retirement have their emission count instrumented
  • Every code records an owner
  • You know what percentage of errors are catch-all codes

And the things not to do.

  • Branch on HTTP status alone — the same 400 comes back for six different reasons
  • Branch on a substring of the message — one copy edit kills it
  • Rename a published code because it reads better — shipped clients cannot be recalled
  • Ship a bare NOT_FOUND — it will collide as soon as a second domain exists
  • Bake retryability into the code string — your metric splits in two during an incident
  • Append _ERROR or _EXCEPTION — zero information, extra length
  • Translate the code per language — a code is an identifier, not prose
  • Maintain docs and client constants by hand — they will drift
  • Record a deprecation date and never look at traffic — you delete something people still receive
  • Create a code because it might be useful later — unused codes erode trust in the list

To put it together: an error code is not documentation, it is a contract with the client. A contract is worth something only when the other party can act differently because of it. So split by units of behaviour rather than by count, and remember that a code you have published, unlike a message, cannot change. Those two sentences generate every other rule.

# Designing an Error Code Catalogue — Schema, Decision Table, Procedures

> Source: braindetox.kr — What It Means to Design an Error Code Catalogue
> Basis: Windows 10 / Node.js v22.16.0, verified by running the cases (fictional order and payment API)
> Paste this into an AI assistant and say: check our error responses against this.
> Premise: an error code is a contract with the client. Once published, unlike a message, it cannot change.

## 0. Where the decision starts — is this code worth anything

Answer this before adding a code. If all three are no, do not create it.

| Question | What a yes means |
|---|---|
| Does the client show a **different screen or take a different action** on it | worth branching on |
| Does an operator need to **count or alert on this failure alone** | worth a metric axis |
| Is the **retry decision different** | worth a retry contract |

- Split by **units of behaviour**, not by how many failures you can name
- Two failures that end in the same screen and the same action need one code plus `details`
- The reason it might be useful later is not a reason. Codes are easy to add and nearly impossible to remove

## 1. Response body schema — separate the machine fields from the human field

```json
{
  "error": {
    "code": "PAYMENT_GATEWAY_UNAVAILABLE",
    "message": "The payment provider is not responding. Please try again shortly.",
    "retryable": true,
    "retryAfterMs": 30000,
    "traceId": "01J8ZQ9K3M7T4V2N6P0R5S8W1X",
    "details": [
      { "subcode": "GATEWAY_TIMEOUT", "attempt": 2 }
    ]
  }
}
```

| Field | Audience | May it change | Rule |
|---|---|---|---|
| `code` | machine | **never**, once published | the only field a branch may read |
| `message` | human | **any time** | never parsed, localized per language |
| `retryable` | machine | fixed per code | absent means `false` |
| `retryAfterMs` | machine | value differs per call | absent means the caller decides |
| `traceId` | both | differs per call | humans quote it, machines join logs on it |
| `details` | machine | **additive only** | never remove a field or change its meaning |
| HTTP status | machine | fixed per code | proxies and retry layers key off it |

- Do **not** encode retryability in the code string (`..._RETRYABLE` / `..._PERMANENT`)
- Why: when the same failure flips between retryable and permanent, **the code itself moves and your metric splits into two series**
- Retryability is a **field**, the class of failure is a **code**. Different axes

## 2. Code shape decision table

| Decision | Option | When | Cost |
|---|---|---|---|
| number vs string | **string, preferred** | humans read the logs and stack traces | 15 to 20 extra bytes per response |
| | number | bandwidth is genuinely expensive (embedded, SMS) | unreadable to everyone six months later |
| namespace | **domain prefix** | two or more domains | roughly seven more characters per code |
| separator | **underscore** | the code becomes an enum member or metric label | none |
| | dot or hyphen | you want the hierarchy to be visible | illegal as a generated enum member |
| case | **all caps** | signals a constant | none |
| suffix | **none** | `_ERROR` and `_EXCEPTION` carry zero information | none |
| length | **32 chars or fewer** | log column alignment and readability | longer names need abbreviation |

### What choosing numbers costs you (verified by running it)

- A one-character typo lands on **another valid code** and takes the wrong branch silently. A mistyped word almost always falls through to the default
- Grepping a log for `1043` also matches `latency_ms=1043` and `bytes=1043`. You have to search the field name too
- What you gain: fixed-width alignment, and domains separated by numeric range

## 3. Namespace rules

```
{domain}_{subject}_{state}    e.g. ORDER_WINDOW_CLOSED
{domain}_{state}              e.g. SHIPPING_NOT_FOUND
```

- Unprefixed `NOT_FOUND`, `EXPIRED`, `INVALID`, `RATE_LIMIT` **will collide the moment a second domain appears**
- On collision the gateway keeps **whichever list was registered first** and the rest disappear. The client cannot tell what is missing
- Do not repeat a word: `ORDER_ORDER_NOT_FOUND` is wrong
- Do not append empty suffixes: `..._ERROR`, `..._EXCEPTION`, `..._FAILURE` are wrong
- **One layer** of prefix is enough. `COMMERCE_ORDER_PAYMENT_WINDOW_CLOSED_ERROR` is 42 characters and destroys your log column

## 4. Stability rules — what you may change and what you may not

| Change | Allowed | Why |
|---|---|---|
| Rewrite the message entirely | **yes** | the contract says nobody parses it |
| Add or fix a translation | **yes** | a code has no language |
| Add a field to `details` | **yes** | additive change |
| Add a new code | **yes** (procedure below) | unknown codes fall through to the default |
| Rename a code | **no** | every shipped client branch dies instantly |
| Delete a code | **no** (only via deprecation) | same as above |
| Change a code HTTP status | **no** | proxies and retry layers key off it |
| Change a code `retryable` | **no** | automatic retry behaviour changes |

- **If you want a new name**: announce it in a `supersededBy` field and leave the wire value alone
- Swap the wire value only after the old code emits **zero traffic**
- Release gate: compare the code set against the previous version and **fail the build if any published code disappeared**

## 5. Translation and messages

- The server picks the sentence from `Accept-Language`. Missing locale falls back to the default language, then to the code string
- A client that renders locally **goes blank on any code newer than its last release**
- So send both: the client prefers its own bundle and prints the server `message` when it has no template
- Do not bake numbers, amounts or dates into the server sentence. Send them in `details` or `params` so **the client formats them for its locale**
- **Never translate the code itself.** Something like `ORDER_ALREADY_PAID_KO` makes the branch fire in one language only
- Put a locale coverage report in CI. Translation holes survive on fallback. A missing **code** does not

## 6. Procedure for adding a code

1. **Write the behaviour first.** One sentence: the client does X. If you cannot write it, you do not need a code
2. **Search the existing list for that behaviour.** Same action plus same HTTP status plus same retryability means it is `details`, not a new code
3. Name it: `{domain}_{subject}_{state}`, all caps, underscores, 32 characters or fewer
4. Add it to the registry, one file: `code` / `http` / `retryable` / `action` / `since` / `owner`
5. Run the linter (section 8). Zero errors to merge
6. **Never hand-write** the docs table or the client constants. Generate both from the registry
7. Record an owner. A code with no owner is a code nobody can delete six months later

## 7. Procedure for retiring a code

1. Record a `deprecated` date and `supersededBy` in the registry — **nothing disappears at this point**
2. The server keeps emitting the old code. The new one is added alongside
3. **Instrument the emission count** of the old code
4. Zero for thirty consecutive days makes it a deletion candidate. Anything above zero means **find the caller first**
5. Delete from the registry only. Client constants and docs follow by regeneration

- A deprecation date does not remove a code. **Traffic does**
- A high emission count on `UNKNOWN_ERROR` or `INTERNAL` is not a code, it is **a pile of unclassified failures**. First candidate to split

## 8. Automated checks — one registry, everything else generated or compared

Lint rules for the registry itself:

- [ ] `duplicate-code` — the same name registered twice
- [ ] `bad-shape` — violates `^[A-Z][A-Z0-9]*(_[A-Z0-9]+)*`
- [ ] `too-long` — over 32 characters
- [ ] `repeated-word` — the prefix repeats a word in the body
- [ ] `useless-suffix` — ends in `_ERROR`, `_EXCEPTION`, `_FAILURE`
- [ ] `vague-name` — catch-alls like `INTERNAL`, `UNKNOWN_ERROR`, `INVALID`, `FAILED`
- [ ] `no-namespace` — no underscore, therefore no domain prefix
- [ ] `unstable-http` — the same code registered under two HTTP statuses
- [ ] `retryable-4xx` — marked retryable on a 4xx that is not 401, 408 or 429
- [ ] `non-retryable-5xx` — a 5xx marked non-retryable
- [ ] `deprecated-orphan` — deprecated with no replacement

Cross-check against the client source:

- [ ] **Dead branches** — the client branches on a code the registry does not define, so it can never fire. **Fail the build**
- [ ] **Unhandled codes** — the server can emit it but no branch exists. Report as a coverage number
- [ ] For each dead branch, **suggest the nearest registered code** by token overlap

Generated artefacts:

- [ ] Client constants (a frozen object or enum)
- [ ] Docs table (code / HTTP / retryable / what the client should do)
- [ ] A code list snapshot the release gate compares against the previous version

## 9. Checklist

- [ ] **Zero** branches in the client compare a message string
- [ ] Failures that share an HTTP status are **separated by code**
- [ ] Every error response carries `code` and `traceId`, **always**
- [ ] The retry layer reads a missing `retryable` as **`false`**
- [ ] Retryability is **not baked into any code string**
- [ ] Every code has a domain prefix, and there are **zero** bare `NOT_FOUND` style codes
- [ ] The code list lives in **one file**, and docs and client constants are **generated** from it
- [ ] The release gate catches a **disappeared code**
- [ ] Deprecated codes have their **emission count instrumented**
- [ ] Every code records an **owner**
- [ ] Groups sharing action plus status plus retryability are **reviewed on a schedule**
- [ ] You **know** what percentage of errors are the `UNKNOWN_ERROR` kind
- [ ] A translation coverage report runs in CI

## 10. Do not

- Branch on HTTP status alone — the same 400 comes back for six different reasons
- Branch on a substring of the message — one copy edit kills it
- Rename a published code because it reads better — shipped clients cannot be recalled
- Ship a bare `NOT_FOUND` — it will collide as soon as a second domain exists
- Bake retryability into the code string — your metric splits into two series
- Append `_ERROR` or `_EXCEPTION` — zero information, extra length
- Translate the code — a code is an identifier, not prose
- Maintain docs and client constants by hand — they will drift
- Record a deprecation date and never look at traffic — you delete something people still receive
- Create a code because it might be useful later — unused codes erode trust in the list
