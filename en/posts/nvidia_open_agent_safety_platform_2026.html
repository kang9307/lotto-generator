What was announced — what became public on September 28, 2026

On September 28, 2026, NVIDIA released the Open Agent Safety Platform. As the name suggests, this is not a new model. It is software and a system design for a different question: how an autonomous AI agent that operates tools should be confined and observed. The announcement has two parts. One is OpenShell, which sets the execution boundary of an agent on the host CPU side. The other is Sentry, which watches agent behavior from a BlueField-4 DPU, a processor in the networking family.

The most quoted line in coverage is CEO Jensen Huang's analogy. He compared the platform to a browser for agents, describing a containment system that lets an agent reach only what it needs for its job. A remark reported from the same interview is blunter: when an agent is deployed, however smart it is, the first thing done is to take away all of its rights.

How model alignment differs from execution control

The phrase AI safety covers two different jobs. The first is training a model so that it does less harmful things. The second is limiting, from the outside, the range of resources the model can reach whatever it decides to do. This announcement clearly belongs to the second. NVIDIA's developer blog states the position this way: drift cannot be trained away while the capability is retained, and an agent in that situation cannot be expected to fully govern its own behavior.

This distinction matters because of what an agent is. A model that only converses can produce a wrong answer, but a person can read that answer and filter it. An agent that writes files, runs commands and sends network requests turns output directly into action, so a wrong judgment reaches the system without a human review in between. The focus of safety moves from what is said to what can be executed.

In coverage of the announcement, NVIDIA's Justin Boitano is reported to have said that model-level safeguards alone cannot govern what agents can access or do. That sentence is the logical starting point of the announcement. Training changes probabilistic tendencies but cannot guarantee that a particular action never happens, so the parts that need a guarantee are handed to a device outside the probabilities.

AxisModel alignment (training stage)Execution control (run stage)
What it changesThe tendency of behavior a model producesThe files, networks, tools and credentials an agent can reach
Where it worksInside the model, at training and evaluation timeAt a boundary outside the agent, at run time
How it failsBehavior that departs from intent in a situation training never sawPasses through whenever the policy is too broad or a path is left open
How it is checkedBenchmarks and red-team evaluationPolicy definitions and allow or deny records

This table is commentary in this article and not a table from NVIDIA material. Still, the point that the two layers do not replace each other shows in the announcement's own vocabulary. NVIDIA frames the platform as a full-stack engineering problem and says safety and security require full-stack engineering. It is not a proposal to give up on training, but to put one more layer of access control on top of it.

  • Alignment deals with what a model tends to want to do, and execution control deals with what it is able to do.
  • Alignment failures are often observed only afterward, while execution control blocks in advance within the range written in the policy.
  • The strength of execution control depends on how narrowly the policy is written, so the mere presence of a tool does not establish safety.
  • Using both layers together is the premise of the announcement, and it is not a claim that execution control replaces alignment.

OpenShell — fixing the resources an agent can reach in advance

The role of OpenShell is summarized in one sentence of NVIDIA's developer blog. Operators define which files, networks, tools, processes and credentials an agent can access, and OpenShell checks those limits before the agent runs and enforces them as it works. That five categories of resources are listed is important, because the channels through which an agent affects the world mostly fall within those five.

The source wording for the implementation layer is an open source secure runtime for executing autonomous AI agents in sandboxed environments with kernel-level isolation. The license is Apache 2.0. The release says OpenShell was designed with NVIDIA Vera CPUs in mind and, being open source, can be extended to third-party compute platforms including those from Arm and Intel. When coverage summarized the announcement as limiting agent capability at the CPU, it was pointing to this location.

The easiest way to understand OpenShell is to compare it with the permission model of an operating system. Ordinary programs are bound by user accounts, file permissions and firewall rules, so they cannot touch the system at will. An agent is a program that judges situations like a person and chooses its actions, which makes those traditional permissions hard to apply as they are. The premise of the announcement is that a boundary designed specifically for agents is therefore needed.

  • Files: fixes the range of paths the agent can read and write.
  • Network: limits the destinations the agent can connect to.
  • Tools: fixes the set of tools the agent can call.
  • Processes: controls the execution units the agent can start.
  • Credentials: fixes the range of keys and tokens the agent can use.

This list comes from the developer blog, and the exact configuration syntax for each item has to be read in that documentation. This article does not cover setup. The two-moment distinction of checking before the run and enforcing during the run is still practically meaningful. The pre-run check prevents an agent with a disallowed policy from starting at all, and the in-run enforcement prevents attempts to widen its range after it has started.

Sentry — watching from outside the agent

Sentry is the second layer of the announcement and sits in a different place. NVIDIA describes it as an out-of-band watchdog running on a BlueField-4 DPU. A DPU is a separate processor placed on the network path of a server, so it can observe traffic and behavior from a position isolated from what happens inside the CPU and GPU where the agent runs. When coverage said it monitors the agent from a network chip, it referred to this placement.

The developer blog adds one more premise about the placement. In an NVIDIA Vera Rubin POD, each compute tray includes a BlueField-4 DPU, and that DPU is on the node's only path to the model. The logic is that the watchdog must be on the only path so that an agent cannot bypass monitoring to reach the model. Sentry is described as using NVIDIA DOCA to correlate agent interactions, policy decisions, and tool and data access.

The phrase from outside is the core of this layer. A monitoring device inside the same software stack as the agent can be disabled together with the agent if the agent is taken over. A watchdog on another processor structurally reduces that weakness, and that is NVIDIA's reasoning. How far the reasoning holds depends on how wide a range of signals the watchdog can see.

NVIDIA's claims about behavior come in two kinds. The first is that it enforces security policy in real time at line speed, and the second is that it can quarantine an agent that tries to move outside its boundaries in milliseconds. Both are NVIDIA's descriptions, and the material cited here contains no independent measurement of either.

  • Location: on a processor (DPU) separate from the CPU and GPU where the agent runs.
  • Vantage: the description is that it observes behavior from a trust domain that the agent and an attacker have difficulty reaching.
  • Means: built on NVIDIA DOCA, it correlates interactions, policy decisions and access records.
  • Action: NVIDIA claims it can quarantine an agent leaving its boundaries within milliseconds.
  • Premise: it holds only when that hardware actually sits on the node's path to the model.

The two preceding sections collapse into one table below. The last column records which material each row's sentence came from. Cells whose only basis is a summary in coverage are marked as such.

The two layers are split because their failure modes differ. A runtime on the host runs on the same machine as the agent, so it can express policy finely, but it may be shaken together with that machine if the machine is compromised. A watchdog on a separate processor is less fine-grained but is separated from compromise on the agent side. The announcement presents the pair as a combination that complements each other.

What the scope of the announcement does not tell

Every safety device has a boundary between what it blocks and what it does not. It is natural for a promotional document to stress the first side, and the reader has to ask about the second. Below are questions the announcement materials do not answer.

The limits named here are things not written in NVIDIA's announcement documents, and they are not judgments that something is technically impossible. An announcement is product introduction in character, so failure cases and environments where it does not apply are usually not covered. The list marks where a team considering adoption has to ask for itself.

  • Policy quality is the operator's job. OpenShell enforces the limits the operator sets. If the limits are written broadly they are enforced broadly. What default policy is supplied, and how narrow that default is, cannot be learned from the announcement sentences alone.
  • Misuse inside the permitted range is separate. A wrong action taken within the tools and credentials granted to an agent is not an action that leaves the boundary. Access control narrows the range but does not verify judgment inside it.
  • Sentry presumes specific hardware. The explanation that the watchdog must sit on the node's path to the model reads as meaning the same assurance does not hold in an environment without that hardware. Which environments are targeted has to be learned from the reference design documents.
  • There is no independent verification. Quarantine in milliseconds and enforcement at line speed are NVIDIA performance claims. No third-party test of them appears in the material cited.
  • The effect on real incidents is at the claim stage. Coverage says NVIDIA stated its platform would have prevented recently reported sandbox-escape incidents. That is the claim of the announcing party, and no after-the-fact reproduction test is presented.
  • There is no comparison outside the NVIDIA stack. Results compared against other isolation approaches such as containers, virtual machines or software firewalls are outside the scope of the announcement.

These six items are not meant to diminish the announcement. The approach of separating layers in the design points in the same direction as long-standing security engineering principles. But the information the announcement gives and the range within which a reader may conclude are different, so it is accurate to keep the attribution NVIDIA said in any sentence that draws a conclusion.

What developers and operators can check now

A team that actually runs agents can answer the same questions in its own environment regardless of the details of the announcement. Below is a checklist arranged along the logic of the announcement. These questions are valid whether or not OpenShell is adopted.

The order of checking goes from cheap to costly. Listing credentials and file and network ranges can be finished quickly without tools, whereas hardware-based monitoring needs infrastructure planning. The list therefore gets more expensive from top to bottom.

  • List the credentials the agent uses. Write out which keys, tokens and environment variables the agent can read. The longer the list, the wider the boundary.
  • Narrow the file access range. See whether it can be limited to one working directory, and whether the entire home directory is open.
  • Turn outbound network access into an allow list. If the default is allow-all, reducing it to a few permitted destinations is the first step.
  • Keep the tool set minimal. Do not register tools the agent does not use.
  • Tell whether control lives inside or outside the agent. An agent limiting itself through its own prompt and an outside boundary enforcing limits are different assurances.
  • See whether denials are recorded. A record of what was refused is needed to tune the policy.
  • Look at OpenShell in a test environment first. Since it is presented as open source, reading the policy definitions in an isolated test environment is the sensible order. Putting it directly into production is not advised.
  • Read Sentry together with the hardware plan. Unless the infrastructure uses the BlueField-4 family it is not an immediate target, and using it to understand the structure as a reference design is the realistic use.

The first six items on this list can be done today without any tool. The announcement can be read less as asking for something new than as packaging an old principle into a product bundle: move an agent's access range from allow-by-default to allow-by-explicit-grant.

What could not be verified

  • The CNBC article page. Access was refused and the page did not open, so CNBC details were seen through the GeekNews summary and other coverage. Jensen Huang's browser for agents analogy, Boitano's remark and the partner roster fall in that category.
  • The figure of 17,000 agents in the July Hugging Face breach, carried in the GeekNews summary. It was not confirmed in any material opened, and one report said the number of agents was not specified, so it is not used in the text.
  • Sentry's availability date, pricing and range of supported hardware.
  • The default policy contents of OpenShell and the details of its configuration syntax. These can only be learned by opening the developer blog and repository documentation directly.
  • Independent measurement of quarantine in milliseconds and enforcement at line speed.
  • The concrete scope of the Anthropic integration. The newsroom has only a quotation, and no sentence in the material describes the method of integration.
