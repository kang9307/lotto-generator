缘起 - 智能体多到成千上万时，仓库的基础是什么

2026 年 10 月 1 日，Cloudflare 官方博客发布了一篇由 Dina Kozlov、Dillon Mulroy 和 Zebulon Piasecki 三人撰写的文章，内容是大赛公告。Cloudflare 提议开发者用 Workers 和 Artifacts 构建「下一代 Git 平台」。GeekNews 将其作为 2026 年 10 月 4 日登记的条目介绍，摘要集中在大赛截止日、奖励，以及 Artifacts 处于公开测试这几点。

公告开头先讲前提，再讲规则。博客写道，GitHub 是为这样一个世界而建的：人类写代码，把代码整理成仓库，并通过分支、提交、议题和拉取请求协作。接着说，下一代软件将由另一类开发者来构建，也就是智能体。博客列出的智能体工作包括修复缺陷、开发功能、测试、代码评审、依赖更新和维护任务。公告的核心问题由此而来：在成百上千个智能体同时处理同一代码库的世界里，基础应当是什么样子？

博客把这个问题展开为四个未解决的问题。智能体能否知道其他智能体正在同时进行的工作？彼此冲突的变更如何处理？智能体产出的结果如何评审？为什么这样修改的理由如何保存？大赛被表述为收集回答这四个问题的实现的一种方式。要求不止于在现有 GitHub 上附加智能体，而是重新思考仓库、分支、拉取请求、工作树、代码评审和合并冲突本身。

这里的范围是把公告中写明的条件整理成表格和清单，并把指向同一对象却因来源而异的值分开。截止日临近、计费即将开始，日期只有准确才有用。大赛的价值判断和参赛建议不在范围内。同一主题的背景见分析 AI 原生 Git 托管的Cursor Git 服务 Origin 分析，以及分析智能体运行时的Cloudflare OS 分析。下面只限于那些文章没有涉及的本次大赛条件和 Artifacts 文档中的数字。

三项提交物与许可证条件

博客要求的提交物有三项。第一是展示所做作品的 5 至 10 分钟视频。视频要涵盖三点：做了什么、它让智能体和开发者能做什么、以及如何工作。第二是源码链接，必须以宽松的开源许可证提供，括号中举例的许可证是 MIT、Apache 和 BSD。第三是运行或试用该项目的方法。

在这些条件里，许可证一项在实务上最先遇到。公告把范围限定为「宽松」许可证，举例的三个都属于使用、修改、再分发条件较轻的一类。至于其他许可证是否允许，例如互惠条件较强或限制源码公开的许可证会怎样处理，公告没有写。如果项目依赖外部代码，那些代码的许可证与提交许可证是否冲突，也是提交前要查的项目。这一判断属于一般的开源使用惯例，而非大赛规则，公告没有涉及这一点。

  • 视频 - 5 分钟以上 10 分钟以下，用于说明做了什么、它让智能体和开发者能做什么、以及如何工作。
  • 源码链接 - 以 MIT、Apache、BSD 一类宽松许可证公开。
  • 运行方法 - 运行或试用项目的说明。
  • 提交格式 - 公告没有写。是否另有页面，未能确认。

奖励结构 - 一等奖额度与前三名差旅

奖励分为两层。前三名项目每队最多两名成员前往旧金山参加 Cloudflare Connect 并展示作品。博客原文是「fly up to two members from each team to San Francisco」，即每队最多两人乘机前往，没有提住宿。一等奖在此之外还有 25,000 美元的 Cloudflare 额度，以及 Connect 周一晚上的 VIP 演讲者晚宴邀请。博客的措辞把额度和晚宴邀请并在一起，作为一等奖的部分。

从这个结构中，能读出的和读不出的可以分开。能读出的是：一等奖是额度而非现金，额度的单位是美元，机票支持适用于前三名团队。读不出的是：二等奖和三等奖有没有额度，额度可用于多大范围的 Cloudflare 产品、有效期多长，机票支持有没有上限，住宿等机票以外的费用是否支持，两名成员的限制是否意味着团队规模限制。最后一项尤其要小心。「每队最多两人的机票」只是说明支持的规模，公告里没有依据把它当作团队人数限制。

奖励实际价值多少，由各人自行判断。额度是用途限于 Cloudflare 服务的价值，这里不做其他换算。Artifacts 的价格表是公开的，第 7 节列出了费率。但按这些费率，25,000 美元额度能用多久取决于操作次数和存储量等使用方式，这里不做计算。

  • 前三名项目：每队最多两名成员，飞往 Cloudflare Connect（旧金山）；住宿公告中未提。
  • 一等奖：25,000 美元 Cloudflare 额度，加上 Connect 周一晚 VIP 演讲者晚宴邀请。
  • 公告中没有的：二等奖、三等奖的额度，额度有效期，机票支持上限以及是否包含住宿。

Artifacts 是什么 - 文档所界定的范围

大赛所依托的 Artifacts，博客定义为「能说 Git 的版本化文件系统，可扩展到数百万个仓库」。Cloudflare 开发者文档的概览称其为「能说 Git 的版本化存储」，并说明它存储的是带版本的文件树，而不是原始 blob。按变更记录，它在 2026 年 4 月 16 日以私有测试开始，2026 年 10 月 1 日进入公开测试。公开测试面向 Workers Paid 套餐客户，Workers Free 上不能使用。

下表整理博客和概览文档共同提到的功能。两个来源都只写到这个程度，所以各功能内部如何实现不作描述。

功能文档与博客的记述与大赛任务的联系（解读）
访问途径Workers 绑定、REST API、标准 Git 客户端说明智能体用 Git 客户端连接的配置是可行的
仓库创建、导入、fork以编程方式创建仓库、导入已有仓库并 fork可读作给每个任务一份隔离副本的用法
事件订阅仓库创建、导入、fork、删除、push、clone、fetch 事件在出现变更时启动评审流程的用法（博客示例）

第三列是读者的解读，不是公告中的句子。博客没有指定这些功能应如何用于大赛任务。能确认的只有一点：文档概览中「把智能体会话记录在单独的仓库或分支」「通过 fork、比较、合并进行并行探索」的说法，与大赛提出的问题方向一致。

  • 定义：博客称「能说 Git 的版本化文件系统，可扩展到数百万仓库」，文档称「能说 Git 的版本化存储」。
  • 时间：2026-04-16 私有测试，2026-05-18 Wrangler 命令，2026-06-17 仪表板，2026-10-01 公开测试（文档变更记录）。
  • 对象：Workers Paid 套餐。Workers Free 不可用。
  • 规模表述的差异：博客写数百万，变更记录写数千万。措辞不同，限额文档中的仓库数量是无限制。

读两段官方代码示例 - fork 与 push 事件

博客里有两段代码示例。下面照原文抄录。模板字符串中的反引号和美元符号只是改用 HTML 字符引用书写，代码本身相同。这里没有运行代码，对行为的说明只限于博客示例给出的范围。

using project = await env.ARTIFACTS.get("my-project");
                    const { defaultBranch } = await project.info();
                    const workspace = await project.fork(`task-${crypto.randomUUID()}`);
                    
                    using repo = await env.ARTIFACTS.get(workspace.name);
                    const instructions = await repo.readFile({
                      ref: defaultBranch,
                      path: "AGENTS.md",
                    });
                    
                    const agentTask = {
                      remote: workspace.remote,
                      token: workspace.token,
                      instructions: instructions ? await instructions.text() : null,
                    };

第一段示例展示的流程有四步：按名称获取项目，查询默认分支，为每个任务用随机名称做 fork，再从 fork 出来的仓库读取默认分支上的 AGENTS.md。然后把远程地址、令牌和指令文本放进要交给智能体的任务对象。值得注意的是，智能体用的访问信息是绑定在一个 fork 出来的工作空间上给出的。给的是每个任务副本的远程和令牌，而不是直接打开原仓库。至于这是多个智能体同时工作时减少冲突的设计方向，这一说明是从示例代码读出的解读，博客并未这样说。

export default {
                      async queue(batch, env) {
                        for (const message of batch.messages) {
                          const event = message.body;
                          if (event.type !== "cf.artifacts.repo.pushed") continue;
                    
                          await env.REVIEW_WORKFLOW.create({
                            params: {
                              namespace: event.source.namespace,
                              repo: event.source.repoName,
                              ref: event.payload.ref,
                              commit: event.payload.after,
                            },
                          });
                        }
                      },
                    };

第二段示例是队列消费者。它遍历消息，事件类型不是 push 就跳过，是 push 就把命名空间、仓库名、ref 和提交作为参数，在名为 REVIEW_WORKFLOW 的绑定上创建一个工作流实例。按博客的说明，这段示例的结构是对 push 做出反应，启动代码评审流程。事件名称的格式（cf.artifacts.repo.pushed）和负载的字段（source.namespace、source.repoName、payload.ref、payload.after）都直接出现在示例里。

  • 两段示例都使用 Workers 运行时的绑定（env.ARTIFACTS、env.REVIEW_WORKFLOW）。
  • 第一段示例中的 using 声明被用作资源离开作用域时自动清理的语法。示例没有说明清理具体做什么。
  • 示例只是节选，不包含 REVIEW_WORKFLOW 的定义和队列配置。
  • 示例中的指令文件是 AGENTS.md，看起来沿用了从仓库内文件读取智能体指令的惯例。

价格与限额 - 计费开始日为何有两种写法

定价有两个维度。博客写的是按仓库操作次数和存储的数据量计费。开发者文档的定价页面给出了具体数值：操作为每月前 10,000 次之后每 1,000 次 0.15 美元，存储为每月前 1 GB 之后每 GB 月 0.50 美元。GB 月按 30 天计费周期内每日存储峰值的平均值确定。

问题在于计费开始日。博客写的是 2026 年 10 月 15 日开始对 Artifacts 的使用计费。开发者文档的定价页面写的是 10 月 14 日开始对操作和存储计费，变更记录 10 月 1 日的条目也写 10 月 14 日。相差一天，这个幅度也可能由时区解释造成，但两个来源都没有写时区。原因在这里无法确定。可以确定的是，两者都在 10 月中旬，与大赛截止日（10 月 14 日）在同一周。因此，打算在截止后继续运行参赛作品的人，应按截止后几天内开始收费来计算。

项目值来源
操作（operations）每月前 10,000 次，之后每 1,000 次 0.15 美元开发者文档定价页面
存储（storage）每月前 1 GB，之后每 GB 月 0.50 美元开发者文档定价页面
计费开始日2026-10-15大赛博客

限额中直接影响设计的是每个仓库 1 GB 和每个 blob 32 MB。在智能体为每个任务 fork 仓库的配置里，仓库数量无限制，存储合计上限为 1 TB，所以清理工作空间的频率可能比单个仓库的大小更直接地影响账单。这是从价格表推出的推论，实际计费方式需要以账单确认。

  • 定价页面把 create、push、pull、clone 这类仓库动作列为操作的示例。这些示例之外的请求如何计数，未能确认。
  • 命名空间名称为 2 至 63 个字符，以字母或数字开头，其后可用字母、数字、句点、下划线和连字符。
  • 免费额度（10,000 次操作、1 GB 存储）是 Workers Paid 账户内的数值，不适用于 Workers Free。

把大赛的问题转成设计项

博客的问题转成实现项后会更具体。下面的清单把博客列举的问题与可读作与之对应的 Artifacts 工具连接起来。这种对应是解读，并不意味着大赛要求这个方向。博客设定的最低要求是展示多个智能体同时处理变更。

  • 对同时工作的感知 - 一个智能体是否知道另一个智能体正在进行的变更。事件订阅中的 push、fork 事件可以作为素材。
  • 冲突的变更 - 向不同方向修改同一文件的变更。按任务 fork 隔离、在合并时处理，是从示例 1 的结构中可以读出的一种方向。
  • 成果评审 - 示例 2 中由 push 事件启动工作流的结构，是评审自动化的一种形式。
  • 保存修改理由 - 博客提到保存智能体上下文的新方法。存储方式没有指定。
  • 同时比较并选择 - 同时比较多个变更并决定发布哪一个的步骤。博客把它作为示例列出。

其中哪一项是必须的，公告没有写。由于没有评审标准，无从得知强调哪一点的作品更有利。可以确定的是，公告要求参赛者重新思考的是基础，而不是某个单项功能。

读完条件后要先定下的事

这不是鼓励参赛的清单，而是从公告条件直接得出的准备事项汇总。是否参加由各人自行判断。

  • 套餐 - Artifacts 仅限 Workers Paid，使用需要该套餐的账户。套餐价格不在这里确认的范围内。
  • 截止前的余量 - 公告没有写截止时刻和时区，所以在截止日前一天完成提交是最简单的预防。
  • 许可证一致性 - 源码需以 MIT、Apache、BSD 之一公开。先检查依赖库的许可证是否相容。
  • 视频长度 - 必须在 5 至 10 分钟之内。不足 5 分钟或超过 10 分钟如何处理，公告没有写。
  • 可复现性 - 运行方法说明本身是提交物，所以环境变量、令牌等机密值不要放进源码，而是分离到配置说明里。
  • 计费开始后的费用 - 如果打算在截止后继续运行作品，应按在 10 月 14 日或 15 日起收取操作和存储费用的账户中运行来计算。
  • 数据管辖 - Artifacts 可以在美国或欧盟中选择数据存储和处理的区域。如果演示使用真实代码，要先决定放在哪个区域。
