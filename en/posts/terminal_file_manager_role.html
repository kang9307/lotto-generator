What a Screen Actually Does for File Work - The Gap a Terminal File Manager Fills

Finding, moving and inspecting make different demands - where the shell stalls, where the window stalls, and how to handle the operations you cannot take back

Aug 29, 2026 Dev & Infra

Introduction: why moving a handful of files is still tedious

Picture opening a log directory on a remote server, picking out a few files and sending them somewhere else. You list the directory and read the names, you squint to work out which ones are the targets, you check the destination path again, and after the move you check once more that everything landed. The operation that actually touches a file happens once; four checks bracket it. Where those four come from is the subject of this article.

The occasion is a terminal file manager that has been circulating again in developer communities. It is called superfile, and here is the scope its introduction states.

  • Multiple panels let you look at different directories at the same time.
  • The screen carries a sidebar for bookmarked folders alongside the file list, progress, file information, a clipboard and a command execution window.
  • Sorting by name, size or modification date, searching inside a directory, showing hidden files, and previewing a file.
  • Shortcuts for creating, renaming, copying, cutting, pasting, compressing and extracting, plus a selection mode for acting on several files at once.
  • Written in Go with the Bubble Tea terminal UI framework, under the MIT license. Linux and macOS are supported; Windows is described as not yet fully supported.
  • Themes, plugins and hotkeys are configurable, and it can return you to the directory you were last in when you quit.

That is the documented scope, and this article is not an assessment of that tool. It is about what a screen actually does for you when you handle files. Arguments about which tool is better have to start over every time a new one appears; an answer about what a screen replaces survives the turnover.

1. File work is not one job - finding, moving, inspecting

Lumping everything under file work derails the discussion from the start. What we actually do splits into three activities with different natures, and each asks for something different.

Finding splits again. Pointing at a name you already know is not the same activity as scanning to remember what was around here. The first ends with a single string; the second requires walking a list with your eyes. For the first, a screen gets in the way. For the second, without a list you can do nothing at all.

Moving and deleting need two places at once. Naming the source does not complete the operation. And this family alone is irreversible. A bad search can simply be repeated; a bad deletion cannot be undeleted.

Inspecting only reads. Being wrong costs nothing, which makes it completely unlike the other two. That is why you can repeat it freely, and why most devices that prevent accidents take the shape of inserting one more inspection.

ActivityWhat it needsWhat fitsWhat happens when it does not
Finding (name known) One exact string Naming it in a single line. No screen required You lose time raising a list and scrolling it
Finding (name unknown) A list to scan, sorting, preview A screen where the list stays up You repeat the same query with the conditions tweaked
Moving and deleting Source and destination, plus a check A layout showing both places at once You act on a destination you misread. There is nowhere to go back to
Inspecting Attributes and the head of the content, read access only Either works. Whichever repeats more cheaply wins You skip the check and move on to the next step
The point of the table is not a ranking. It is that the same person does all four on the same day, so any attempt to serve all four with one shape pays for it somewhere.

2. Where a shell alone falls short - state is invisible

Saying the command line is inconvenient is usually imprecise. The commands themselves are exact, short and reproducible. What is missing is not the command but state. A command runs and disappears, and it stores the context between runs nowhere.

Three things must stay known while you work with files: where you are, what is selected, and what the last operation produced. On the command line all three live in your head or must be asked again whenever needed.

  • Where am I — the prompt does tell you. But abbreviating deep paths is a common setting, and an abbreviated path cannot distinguish sibling directories with similar names. Accidents usually start here.
  • What is selected — a shell has no concept of selection. What a pattern will match is not settled until it runs, and the directory can change between the check and the operation. Check and act being separate is structural, not sloppy.
  • What was the result — a successful command usually says nothing. Reading silence as success is a well-built convention, but silence is not a confirmation. Learning the result means asking once more.
  • How far along is it — while a large file copies, a quiet screen gives you no basis for telling running apart from stuck.
  • What did I just do — history is a list of commands, not a list of states. Where you were three steps ago has to be reconstructed by reading backwards.

What a screen does is display that list on your behalf, continuously. There is no further magic. With the file list up, where you are stops being a question and becomes a visible fact; with marks on the items you picked, selection stops being memory and becomes screen.

So the value of a screen scales with how often you have to ask again. If the target is already exact, there is nothing to re-ask and one line wins. If it is not decided yet, the count climbs sharply. That is a property of the work, not of taste.

3. What a window cannot do - remote, repetition, composition, records

This is where the discussion usually tips into terminals being better than windows, and that direction is shallow. More precisely, there are four places a graphical window structurally cannot reach, and only there is the terminal irreplaceable.

  • Remote — there is no window on the far side of a remote shell. Mounting a share or opening a remote desktop can bring one over, but that layer brings latency, permissions and a failure point with it. The terminal is already there.
  • Repetition — to redo today what you did yesterday, you have to remember what you clicked. Clicks do not replay. Commands run again as they are.
  • Composition — the output of a command can be the input of another. The output of a window cannot be the input of another window. Handing a result straight to the next step is native on one side and absent on the other.
  • Records — what you did remains as text. For handover and incident review that text is effectively everything. Picking an item on a screen and pressing a key leaves nothing behind.

Conversely, what a graphical window does well is also a requirement rather than a preference: scanning the contents of many files at a glance, large previews, deletion designed around undo, and the accessibility layer the operating system provides. Those four are hard to imitate from the terminal side, and where they can be imitated the imitation is thinner.

So the axis is not terminal versus window. It is whether there is a window where I am standing, whether I will do this again later, and whether it has to be recorded. Answer those three and the choice usually settles itself.

4. Multiple panels are a very old idea

Showing two places side by side is not new. It traces back to PathMinder in 1984 and Norton Commander in 1986, and the family that followed became known as orthodox file managers. Midnight Commander on Unix-like systems, Total Commander and Far Manager on Windows, Krusader on the Linux desktop: the same layout repeated across environments that had little else in common. By 1997 someone had written down a set of criteria the family was expected to meet.

More striking is that the function-key layout hardened into convention. In this family F5 copies from the active panel to the inactive one and F6 moves. Different programs from different companies, and the same key means the same thing.

Why did the shape survive? Because moving is inherently an operation that takes two arguments. On a screen showing one place, the destination remains an action you re-specify every time; with both places visible, the destination becomes a state pinned to the screen. The operation count does not drop by one so much as an operation turns into a state, and this is exactly the point where the re-asking from the previous section shrinks the most.

There is a price, of course.

  • The width is split, so long file names and deep paths get truncated. A truncated name is the most dangerous label to have among similar ones.
  • Work that spans three or more places outgrows two panels. Add tabs or panels and which one is active becomes a new thing to verify.
  • The active panel is itself a piece of state. Misread it and the operation runs in the opposite direction.
  • On a narrow screen two panels do not hold, and the layout collapses back to showing one place at a time.

5. The biggest risk is the operation you cannot take back

Fast operations invite fast accidents. This has nothing to do with tool quality. If anything, the better the tool and the more a single keystroke accomplishes, the more one wrong keystroke puts beyond recovery. In file work the risk shows up in roughly three forms.

First, there is nowhere to go back to. A desktop trash can is not a filesystem feature but a convention the participating programs agree to honor: move the file to an agreed location instead of removing it, and record where it came from. Deletions outside that convention skip the step entirely, and remote servers usually have no desktop environment to honor it in the first place.

Second, overwriting is quiet. What happens when the destination already holds the same name depends on the tool and the settings. The overwritten side is awkward because it is not even recognized as something to recover. A deleted file is visibly absent; an overwritten file sits in place under the same name.

Third, selection leaves the screen. The moment you scroll, the items you picked earlier stop being visible, and from then on selection is something you remember rather than something you check. Human memory is not accurate past about twenty items.

OperationWhat disappearsWhen you noticeThe order that reduces accidents
Bulk deletion Every selected item. A place to go back to is not guaranteed Usually at once, though what was included comes later Settle the list first, look at it with your own eyes, then act
Same-name overwrite The original file at the destination. The name stays Much later, when someone opens that file Fix the destination first and proceed only with overwrite confirmation on
Move in the wrong direction The file at its original place. It is somewhere, at least When the next person looks for the original place Verify which panel is active with your eyes before acting
Interrupted copy The tail of the content. Name and existence remain When the file is actually used Clean up the source only after the copy is confirmed complete
The last two rows are worse than the first two. What is gone announces that it is gone; what is wrongly left behind says nothing at all. A file with the right name and the wrong contents is the hardest artifact to deal with.

What reduces accidents is not the choice of tool but the order. Settle the destination first, split bulk operations rather than doing them in one shot, and clean up the source only after seeing that the copy is intact. That order holds regardless of tool.

6. What changes over a remote link - latency, big listings, disconnects

What is comfortable locally hurts remotely because the unit of cost changes. Asking the local filesystem something is close to free. Over a remote link the same question spends a round trip, and the richer the screen, the more questions it asks.

  • Latency — when every keypress costs a round trip, scanning a list becomes choppy. Cursor movement that felt natural locally lands a beat late.
  • Big listings — showing a directory of tens of thousands of entries in name order means reading all of them. Adding size and modification time means asking once more per entry. More information on the screen means more questions.
  • Preview — showing the head of a file is a transfer remotely. Moving the cursor through a list can trigger a transfer for every file you pass.
  • Disconnects — a copy that dies with the session leaves a half-written file. This is where the right name and wrong contents from the previous section comes from.
  • Network filesystems — mounting and treating it as local leaves the latency untouched while making it look local, so the cost stops being visible.

One judgment follows. Remotely, configure the screen to ask less. Turn automatic preview off, and in large directories narrow with search instead of sorting. Carry over the settings that felt good locally and the same tool feels like a different one.

7. The learning curve of keyboard control - what gets faster and what gets riskier

Keyboard-driven control is genuinely fast once learned. Your hands stay on the list, and for someone doing the same operation dozens of times a day the difference is large.

It is worth being precise about what the speed is made of. What shrinks is not the operation but the confirmation. Opening a menu, finding an item and clicking it contains a checking step you never notice, and compressing that into one key removes the check along with it.

  • Operations with completely different outcomes routinely sit on adjacent keys. Copy next to move, rename next to delete. One finger separates what can be undone from what cannot.
  • Muscle memory crosses tool boundaries. A key learned in one tool does something else in another, and the body does not know the difference.
  • Freely remappable shortcuts are freedom and hazard at once. Changing a settled convention removes predictability with it, and on a shared server that cost lands on the team rather than the individual.
  • Typing ahead is especially risky. A key pressed in anticipation of a confirmation dialog runs the next operation when the dialog does not appear.
  • The safest order while learning is read-only operations first. Navigating, sorting and searching cost nothing when you get them wrong.

This is why the function-key convention of the orthodox family lasted. When many tools put the same meaning on the same key, hands do not slip when a person switches tools. A convention can look inconvenient and still be the thing preventing accidents.

8. So when do you reach for it - conditions, not tools

Instead of deciding which tool to use, it works far better to check which conditions the work in front of you sits under. The table below is that list.

Condition to checkIf yesIf no
Is there a window where I will work Using the layer the OS already gives you pays well It has to be solved inside the terminal. That is a condition, not a choice
Is the target already settled Naming it in one line is fastest and reproducible A screen with the list up cuts how often you re-ask
Does the same work repeat Write it down rather than driving a screen. Repetition should replay The work is exploratory, so a screen helps
Can it be undone You can afford to go faster Slow down and add a check. Here every tool is dangerous
Is a record required It must be the form that leaves text. Screen actions leave no evidence Use whichever is comfortable
Is the listing large You need a way to narrow. Drawing everything gets slow Either approach is fine

The judgment running through the table is this. Exploratory work wants a screen, settled repetition wants to be written down, and an irreversible bulk operation wants neither — it wants a human review step. That last item matters most. Changing tools does not reduce risk in irreversible work. The only thing that does is inserting one more check.

People who log into servers daily and people who never do read this table completely differently. For the first group the top row is already decided and only the rest remains; for the second the discussion ends on that row.

9. Accessibility as a separate axis

One more axis is easy to leave out. A terminal screen is a grid of stamped characters, so it has no counterpart to the semantic structure a graphical application hands the operating system. Things that read as a list or a table to a human arrive as coordinates and glyphs on the machine side. The gap widens as the screen gets richer, and on this site Looking Like Text Is Not Being Readable - Why Terminal UIs Have No Structure covers that down to the rendering model. A file manager, whose list and selection state redraw continuously, is where the problem that article identifies shows up most strongly.

What I could not verify

Gathered in one place, the parts of this article without established grounding.

  • Whether the tool behind this article routes deletions through a trash convention is not stated in its repository documentation. The trash discussion here is about desktop conventions in general, not any specific tool.
  • Remote access support for the same tool is likewise not mentioned. The remote sections describe handling files inside a terminal in general, not a product feature.
  • I found no published measurements for behavior or performance on very large directories. The latency material is a structural account of round-trip cost, not a number.
  • How far Windows support goes is not documented beyond the note that it is not fully supported.
  • The panel and sidebar description reflects the scope of the introductory write-up; the repository readme does not spell out that level of detail.

Conclusion: a screen does one thing, and that is show state

File work mixes activities of different natures, and what a screen genuinely provides among them is one thing: it keeps displaying where you are, what is selected and what the result was. The old layout that puts two places side by side has repeated for four decades for the same reason. It moves the destination out of the action and into the state.

The risk that convenience creates is concentrated in one place too. Deletions have no guaranteed way back, overwrites do not even announce that something is gone, and a selection that has scrolled off screen is memory rather than confirmation. In that interval safety comes from an order of operations rather than a tool.

So the remaining question is not what to use. It is whether this work is exploratory or settled, whether it can be undone, and whether there is a window where I am standing. Answer those three and the rest tends to follow.
