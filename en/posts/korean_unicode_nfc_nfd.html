When Hangul Falls Apart Into Jamo - NFC, NFD, and What Breaks at the Boundaries

Where filenames, grep, sorting, length checks and archives each fall over, shown with output I actually ran

2026-07-30 Tech & IT

Introduction: two files with the same name were in one folder

I printed a directory listing and the same name appeared twice. 사진.png and 사진.png. Not one letter different, no stray whitespace, same extension. Zooming in does not help. Yet the operating system treated them as two separate files, and their contents really were different.

Dumping the filenames as bytes gives the answer. One is 19 bytes, the other is 10. The same three character name, stored with twice the bytes in one case. One stored each Hangul syllable as a single precomposed character, the other stored the leading, vowel and trailing parts separately. Unicode permits both. They only become the same shape when they are drawn on screen.

This is the Unicode normalization problem. And the real substance of it is not that someone forgot to normalize. It is that nobody decided where and by whom normalization would happen. Web form to server, server to database, database to filesystem, filesystem to archive, archive to another operating system. Strings cross these boundaries many times. If it is not settled whether a form is preserved or changed at each crossing, and who unifies it, something will break.

This article crosses those boundaries one at a time and shows what breaks, using output I ran and observed. The conclusion up front: storage is mostly safe. Boundaries are what is dangerous. And the most frequent accident in Korean language services is not filenames at all, it is the [가-힣] regex.

Test environment. Every output below was actually executed on Windows 10 Pro (10.0.19045) with NTFS. The tools are Node.js v22.16.0 (win32), Python 3.13.3, GNU bash 5.2.37 (MSYS2/MinGW64), GNU tar 1.35 and Windows PowerShell 5.1. Example paths have been rewritten as placeholders such as /tmp/demo.

Every script was saved to a file before running. Code mixing Hangul and backslashes gets silently mangled when passed as a shell argument. That trap is covered in The Korean Regex Trap.

What this article does not cover. The syllable composition arithmetic and per ending safe patterns behind the fact that a suffix changes the preceding character are in the article above. The problem of spaces and newlines in filenames breaking pipelines is in The Whitespace Trap in find and xargs. This article digs only into the same name becoming two different byte sequences. Regex dialects and portability live in Regular Expressions That Work Everywhere.

1. Two strings that look identical are not - there are three answers to length

Fact check first. I built 한 in composed and decomposed form and measured three lengths side by side.

node v22.16.0 / win32
대상            .length  [...s].length  utf8 byte
-------------------------------------------------
NFC 한                1              1          3
NFD 한                3              3          9
NFC 한글              2              2          6
NFD 한글              6              6         18
NFC 대한민국          4              4         12
NFD 대한민국         11             11         33
NFC 가                1              1          3
NFD 가                2              2          6
-------------------------------------------------
NFC 한 : U+D55C
NFD 한 : U+1112 U+1161 U+11AB
NFC 가 : U+AC00   (종성 없음)
NFD 가 : U+1100 U+1161   (2 코드포인트)

How to read it. The composed 한 is the single U+D55C. The decomposed 한 is three: leading hieuh (U+1112), vowel a (U+1161), trailing nieun (U+11AB). That is why byte length splits into 3 and 9.

  • The syllable 가, which has no trailing consonant, decomposes into only 2 code points. In other words the inflation ratio differs per character. Sometimes it is twofold, sometimes threefold
  • 대한민국 went from 4 to 11. Three of its four syllables have a trailing consonant, so it is not four times three
  • Therefore rough estimates like character count times three do not work. You have to actually measure
  • In UTF-8 both a composed syllable and a decomposed jamo are three bytes each. The inflation comes from the number of code points

1.1 Every comparison operator says they differ

--- 1-4. 비교 ---
nfc === nfd                : false
nfc == nfd                 : false
Object.is(nfc, nfd)        : false
nfc.localeCompare(nfd)     : 0
JSON.stringify 동일        : false
Set([nfc,nfd]).size        : 2
Map 키 충돌하는가          : false

The line to stare at is the fourth. === says false while localeCompare returns 0, meaning equal. The two functions give different answers.

What matters is how that inconsistency plays out in production. Sorting looks fine while deduplication fails. Sort a list with localeCompare and the two 한 entries end up adjacent. A human looking at the list sees the duplicate immediately. But Set and a database unique index look at bytes, so they let both through as distinct. That is where you get the report that says sorting shows them next to each other but deduplication does not remove them.

1.2 How the Unicode standard defines this

Unicode Standard Annex 15 defines four normalization forms. Transcribed directly, they are these.

FormStandard definitionResult for HangulTypical use
NFCCanonical decomposition, then canonical compositionOne code point per syllableDefault for storage, comparison, transport
NFDCanonical decompositionSplit into jamoJamo level work such as initial consonant search
NFKCCompatibility decomposition, then canonical compositionCompatibility jamo become combining jamo, fullwidth becomes halfwidthSearch index normalization
NFKDCompatibility decompositionAs above but left decomposedRarely, for special indexes

One sentence in the standard bears directly on Hangul. Decomposition and composition of Hangul syllables are algorithmic, not table driven. It is a design that lets an implementation compute in code instead of storing lookup data. The practical implication is blunt. There are no exceptions. It is not that certain characters are affected, it is that every Hangul syllable can be decomposed. This differs in kind from the situation in English, where normalization is a matter of a handful of accented letters. In Korean the entire text is in scope.

2. Normalization fixes it - but the question of where remains

The prescription is short. Put both sides in the same form. I confirmed it in both JavaScript and Python.

정규화 없이 비교                              : false

normalize('NFC') 후 비교      : True

--- 2-6. 코드포인트 이름 ---
U+1112  HANGUL CHOSEONG HIEUH

U+11AB  HANGUL JONGSEONG NIEUN

--- 2-7. in 연산자도 실패한다 ---

The code point names lay the structure bare. A single HANGUL SYLLABLE HAN splits into CHOSEONG HIEUH plus JUNGSEONG A plus JONGSEONG NIEUN. Python's unicodedata.is_normalized reports the form without normalizing, which makes it useful for logging the state of incoming strings.

So far this is easy. The hard part is which line to put normalize on. That is the real subject of this article. The common failures appear in two directions.

  • It happens nowhere - the most common case. No decomposed string ever arrives in the development environment, so the problem never surfaces. It reproduces only for certain users, certain devices, certain upload paths
  • It happens everywhere - this is what a rushed response after an incident looks like. A normalize gets bolted on before every comparison. It works, but one place is left out, and finding that one place takes weeks
  • Different layers disagree about whether it happened - worse still. Storage is composed, the cache key is raw, the search index is a third form. Three places out of step
  • Believing it happened when it did not - normalize() returns a new string. Calling it without using the return value does nothing at all. This mistake is hard to see in code review

The strategy in Annex 15 points the same way. It suggests that components preserve a normalization form by guaranteeing normalized input and output at system boundaries. In other words normalization should be a boundary contract, not scattered defence. The sections below are a record of actually crossing those boundaries one by one.

The first boundary to cross. I created a file with a decomposed name and then looked for it with the composed name.

That asymmetry is what betrays intuition.

3.1 A shell literal cannot express a decomposed name

In a directory holding only the decomposed file, I typed the name straight into the shell.

--- 3-11. 이 디렉터리에는 NFD 이름 파일 하나만 있다 ---
보고서.txt
--- 3-12. 셸 리터럴(NFC)로 접근 시도 ---
[ -e "보고서.txt" ]  : 없음 (NFC 리터럴로는 못 찾음)

--- 3-13. 글로브로는 잡힌다 ---

The three lines each say something different.

  1. A typed name comes out composed. Input methods and editors produce composed text. So it becomes a different string from the actual file
  2. The error message renders the name unreadably. The shell escapes the bytes it failed to match, so a human cannot guess the cause. You assume you mistyped and retype it several times
  3. The glob succeeds. A glob uses the name the filesystem handed over, not a string a human composed. If globbing works while an explicit name does not, that is grounds to suspect this problem

There is also a half failure that happens purely in memory. I ran a prefix filter over a list mixing both forms.

--- 3-5. 목록 필터가 절반만 걸리는 경우 ---
목록 길이                             : 3

Two entries in the list start with 보고서 and only one matched. If a batch job that moves or deletes files picks its targets with this filter, half are silently skipped. No exception, no error log. Unless you count the processed items you will not notice for days.

3.2 So what about macOS

There is a piece of common wisdom here. That the macOS filesystem stores names in a decomposed style, and that archives created on macOS therefore produce broken names when extracted on another operating system.

This article could not verify that. The test environment is only Windows and NTFS, so there was no way to check macOS behaviour by execution. So I will not assert it. Behaviour may differ by filesystem type and operating system version, so you have to check in the environment you use. The method is the one above. Create a file with a decomposed name, read the listing, and print the code points of the name that comes back. Three lines and you are done.

Writing down what you did not verify makes it the next person's basis for judgment. What is actually risky here is not knowledge about which OS does what, it is whether your own code survives either way. There is one way to make it survive, and that is to normalize on the line that reads the listing.

// 파일 목록을 읽는 경계에서 한 번
const names = fs.readdirSync(dir).map(n => n.normalize('NFC'));
// 이 아래로는 전부 NFC라고 가정하고 쓴다

4. The search boundary - [가-힣] matches zero decomposed Hangul

This is the most practical part of the article. Filename problems hit a limited set of people, but this one is in almost every piece of code that handles Korean.

node v22.16.0 / win32
--- 5-1. [가-힣]가 NFD를 못 잡는다 ---
대상            [가-힣] test    개수   Script=Hangul
----------------------------------------------------
NFC 한글              O 잡힘       2               2
NFD 한글              X 놓침       0               6
NFC 서울시            O 잡힘       3               3
NFD 서울시            X 놓침       0               7
--- 5-5. 정규식 문자 클래스 전수 비교 ---
패턴                       NFC 개수   NFD 개수
----------------------------------------------
[가-힣]                           3          0
[ㄱ-ㅎㅏ-ㅣ가-힣]                 3          0
\p{Script=Hangul}/u               3          9
[ᄀ-ᇿ]                   0          9

The [가-힣] count goes from 2 to 0 and from 3 to 0. It is not that fewer match, it is exactly zero. The reason is the range itself. [가-힣] covers only the precomposed syllable block from U+AC00 to U+D7A3, and decomposed jamo sit in the U+1100 area, outside it.

The third line shows one more trap. Widening the range with jamo, as in [ㄱ-ㅎㅏ-ㅣ가-힣], is also 0. The expectation that opening up jamo will catch decomposed text is wrong. Why it is wrong comes in section 9. The conclusion you need now is one line. Adding jamo does not solve it.

4.1 Validators fail silently in both directions

--- 5-2. 검증기가 조용히 통과한다 ---
NFC 사용자이름  ^[가-힣]+$ 통과 : true    | 한글 섞임 탐지 : true
NFD 사용자이름  ^[가-힣]+$ 통과 : false   | 한글 섞임 탐지 : false

The two lines are opposite accidents. Same name, only the form differs.

  • A Hangul only validator - rejects the decomposed name. The user typed a perfectly normal Korean name and receives an error telling them to enter Hangul only. What is on screen is plainly Hangul, so the user cannot tell what is wrong. Even when they report it, it does not reproduce
  • A mixed Hangul detector - fails to catch decomposed Hangul. Tools that check whether Korean leaked into a multilingual page, banned word filters, and language detectors all land here. The checker returns all clear and nobody doubts it
  • The second is far more dangerous. Users complain about the first so it surfaces eventually, but nobody complains about the second. The result wears the shape of success rather than failure
  • From the same root comes banned word filter evasion. Enter the word you want to block in decomposed form and it sails past a composed form filter. On screen the word appears exactly as it is

4.2 When query and document forms disagree

--- 5-3. NFD 텍스트에서 NFC 패턴으로 검색 ---
본문 형식        : NFD (코드포인트 26개)
검색어 형식      : NFC (코드포인트 3개)
doc.includes(pat)                        : false
new RegExp(pat).test(doc)                : false
doc.indexOf(pat)                         : -1
양쪽 NFC 정규화 후 includes              : true
양쪽 NFD 정규화 후 includes              : true

Note the last two lines. Aligning both sides to composed or to decomposed both make the search succeed. Which form you pick is therefore not the essence of the problem. Whether both sides are in the same form is the whole of it. So rather than memorizing that NFC is correct, the habit of asking whether the two values being compared came through the same boundary is substantially stronger.

I confirmed it on the command line too, running grep against the same content stored in both forms.

The same single line is 37 bytes and 79 bytes. And a composed query finds nothing in the decomposed file. Log search, source code search and batch filters all pass through this point. The conclusion that a string is not in that log may actually mean the forms differed.

4.3 The grep character class has one more trap

An unexpected number turned up mid run. I record it honestly.

--- 5-13. C 로케일 grep -o [가-힣] (바이트로 해석된다) ---
LC_ALL=C  nfc.txt : 30
LC_ALL=C  nfd.txt : 72

The text holds 10 Hangul characters, yet grep -o "[가-힣]" counted 30. Thirty is the UTF-8 byte count of those ten characters. In other words this grep was interpreting the bracket range as a byte range rather than a character range. The 72 is the decomposed side's byte count arrived at the same way.

  • So these numbers must not be read as Hangul character counts. Depending on locale settings a tool may treat multibyte characters as characters, or as bytes
  • If your goal is counting characters, do not lean on shell tools; count in a runtime that understands Unicode. In the output above the Node figures are unambiguous at 10 and 0
  • Fixed string search (-F) is a byte comparison regardless of locale. So a form mismatch means it never matches. That behaviour is at least predictable
  • The lesson is confirm that a tool counts a Hangul syllable as one character before relying on it. The way to confirm is to feed in a sample of known size and check the result

5. The sorting and dedup boundary - decomposed always sorts first

I mixed two decomposed entries into a composed list and sorted it. Only 나 and 마 are decomposed.

node v22.16.0 / win32
--- 4-2. 기본 sort() (코드포인트 순) ---
결과 : 나 마 가 다 라 바
기대 : 가 나 다 라 마 바
--- 4-3. localeCompare 정렬 ---

--- 4-6. 왜 기본 sort가 어긋나나 ---

The default sort() produced 나 마 가 다 라 바. The two decomposed entries were dragged to the front. The cause is right there in the code point table. Composed syllables are at U+AC00 and above while decomposed leading jamo are in the U+1100 area, so in code point order decomposed always precedes composed.

  • The symptom does not reproduce. If most of the list is composed, sorting looks correct. Only on days when a decomposed entry is mixed in does that entry jump to the top
  • Pagination goes wrong. When the sort key wobbles, cursor based paging duplicates or skips entries
  • Sorting with localeCompare gets the order right. Which makes it easy to look at the sort and conclude nothing is wrong
  • But getting the order right is a different problem from treating them as the same item. The Set.size = 2 from section 1 is still sitting there
--- 4-7. 비교 결과 ---

--- 4-8. Intl.Collator 로 중복 판정 ---

The third line is this section's conclusion. localeCompare and Intl.Collator return 0, meaning equal. Those two account for normalization. But Set, Map, object keys, database unique indexes and cache keys do not.

Put plainly, the comparison layer has split in two. The sorting and searching shown to humans accounts for normalization, while the identity checks that protect data integrity look at bytes. In a system where the two layers give different answers, the state where the list appears to hold one item while the store holds two persists as normal. Duplicate accounts, duplicate tags and duplicate categories are born this way.

6.1 It leaks in the opposite direction too

--- 6-3. 「3자 이상」 검증이 NFD를 뚫는다 ---
NFC 「가」 .length     : 1  → 3자 이상 통과? false
NFD 「한」 .length     : 3  → 3자 이상 통과? true

A minimum length check let a single character through. The decomposed 한 has a code unit length of 3. A maximum length check rejects valid input so users complain, but a minimum length check admits invalid input, so nobody complains. Same structure as section 4. The quiet direction is the dangerous one.

6.2 Truncation causes damage you cannot undo

--- 6-4. 자르기가 글자를 반토막 낸다 ---
NFD 한국어 slice(0,2)  : "하"  ← 종성이 떨어져 나갔다
NFD 자른 뒤 NFC 정규화 : "하"  ← 정규화해도 복구되지 않는다
--- 6-5. Segmenter 단위로 안전하게 자르기 ---
권장 순서 : NFC 정규화 → Segmenter 로 자르기
정규화 먼저 한 결과 : "한" (코드포인트 1)

한 became 하. The trailing nieun was cut off. And the second line matters. Normalizing after truncating does not restore it. Normalization cannot resurrect a consonant that is gone. This is what makes it different in kind from the other traps here.

  • Comparison, search and sort failures are fixed by normalizing later. The data is still there
  • Truncation throws data away. It cannot be fixed later. Preview text, summaries, notification messages and log trimming all qualify
  • So the order is fixed. Normalize first, truncate second. This order is not negotiable
  • To handle emoji, flags and combining characters safely you must cut on grapheme cluster boundaries. That is what Intl.Segmenter is for

6.3 Database column arithmetic

--- 6-6. DB 컬럼 바이트 계산 ---
NFD 홍길동전이야기 utf8 바이트 : 54
NFC 홍길동전이야기 utf8 바이트 : 21

Seven characters are 21 bytes and 54 bytes. Where columns are sized in bytes, a VARCHAR(30) is comfortable for composed text and overflows for decomposed. The error the database raises just says the data is too long; it does not point at normalization. Getting a too long error for a seven character name is grounds to suspect normalization.

7. The serialization boundary - nothing gets fixed here

What we have seen so far are boundaries that break. Now it is time to check a boundary that does not break. And the point of this section is that not breaking is not good news.

node v22.16.0 / win32
--- 7-1. JSON.stringify / parse 왕복 ---
원본 nfd 코드포인트 수     : 8
왕복 후 nfd 코드포인트 수  : 8
nfd 보존됨                 : true
--- 7-3. 파일 저장·읽기 왕복 (utf8) ---
파일 크기 (byte)           : 52
읽은 뒤 nfd 보존됨         : true
--- 7-4. 바이트로 확인 ---
파일 안에 NFD 초성 U+1112(e1 84 92) 바이트가 있는가 : true
파일 안에 NFC 한(U+D55C, ed 95 9c) 바이트가 있는가   : true

JSON serialization and file I/O pass the form straight through. Put it in decomposed and it comes out decomposed. Check the bytes and both forms are sitting side by side in one file.

Why is this bad news? Because it means no normalization happens anywhere in the round trip. The vague hope that saving and reloading will tidy things up is confirmed to have no basis. Once a decomposed string enters, it stays that way until it leaves the system. It never unifies itself by passing through storage.

7.1 When object keys split, values get buried

--- 7-2. JSON 객체 키가 NFC/NFD로 갈리면 ---
키 개수                    : 2 ← 같은 이름인데 2개
키 목록 코드포인트 수      : 3, 8
parse 후에도 키 2개인가    : true
obj['한국어'] 로 읽으면    : NFC 값 ← NFD 값은 조용히 묻힌다

Two keys with the same name were created, and reading with the composed key returns only the composed value. The decomposed value exists in the object but is unreachable. Config files, translation dictionaries, mapping tables and caches all have this shape. The cause of a setting not taking effect despite being entered may be right here. Open the file and the key is plainly present, which makes it hard to trace.

7.2 URLs and hashes expose the form directly

--- 7-6. URL 인코딩 ---
NFC URL : %ED%95%9C%EA%B5%AD%EC%96%B4
NFD URL : %E1%84%92%E1%85%A1%E1%86%AB%E1%84%80%E1%85%AE%E1%86%A8%E1%84%8B%E1%85%A5
--- 7-7. 해시가 갈린다 ---
sha256(NFC 한국어) : ea3252281bc3bcec
sha256(NFD 한국어) : 4cbdf1837a1d7592
해시가 같은가      : false
정규화 후 해시 같은가 : true

The same query becomes a completely different URL. The consequences follow.

  • Caches split - a CDN and an application cache see the two URLs as separate resources. Hit rate drops and the cause is invisible
  • Analytics split - traffic for one query is tallied on two rows. It ranks lower in top query lists and its real popularity is understated
  • Canonical URLs wobble - once one document has two addresses, search visibility is divided
  • Hashes split - integrity checks, signatures and duplicate file detection fail. You get the same file with different hashes
  • Wherever hashes are used you must fix the form by convention. Unless normalize to NFC before signing is written down, the signing side and the verifying side will produce different answers

8. The archive boundary - what do tar and zip actually do

Archives are the corridor along which files travel between operating systems. I packed a decomposed name and a composed name together and checked.

The conclusion is clear. In the environment tested neither tar nor zip normalized the names. The decomposed nine code points were identical going in and coming out, matching byte for byte.

And this is the result that best illustrates this article's argument. An archive tool is a faithful courier. It fixes nothing and ruins nothing. Which means the decomposed name arrives at its destination undamaged. The accident does not happen in compression. It happens at the next consumer that tries to find that name with a composed string.

  • If you have automation that receives and extracts archives, the line that reads the listing right after extraction is the normalization point
  • If you are the side creating archives, unifying names before packing is better. When there are many consumers, fixing it in one place is cheaper
  • A listing may display names escaped. In practice the tar -tf output rendered the decomposed name in a hard to read form. An odd looking listing does not mean the file is broken. Byte equality was confirmed in 8-4 above
  • Behaviour may differ by tool and version. Some archive formats have options related to name encoding, so verify with the tool you use. Verification is done by printing code points, as above

9. Kinds of jamo and NFKC - widening the net loses more

Time to answer the question left in section 4. Why did widening the range with jamo, [ㄱ-ㅎㅏ-ㅣ가-힣], fail to catch decomposed text?

node v22.16.0 / win32
--- 9-1. 세 종류의 「ㄱ」 ---
구분                    출력    [가-힣]   Hangul   utf8
-------------------------------------------------------
호환 자모 (U+3131)      ㄱ            X        O      3
조합용 초성 (U+1100)    ᄀ            X        O      3
조합용 종성 (U+11A8)    ᆨ              X        O      3
--- 9-2. NFD는 호환 자모를 쓰지 않는다 ---
NFD('가') 첫 글자 : U+1100  ← 조합용 초성
호환 자모 ㄱ      : U+3131
둘이 같은가       : false
NFD('가나다') 에서 [ㄱ-ㅎㅏ-ㅣ] 매칭 수 : 0
NFD('가나다') 에서 [ᄀ-ᇿ] 매칭 수 : 6

There is the answer. There are three kinds of ㄱ. What you get from pressing a consonant key alone is the compatibility jamo U+3131, what decomposition uses is the combining leading jamo U+1100, and the trailing position is yet another, U+11A8. The three look similar on screen and are different characters.

  • Writing [ㄱ-ㅎ] in a regex opens the compatibility jamo range. It has nothing to do with decomposition
  • To catch decomposed text you must open the [ᄀ-ᇿ] area. In the output above it caught 6
  • That leading and trailing forms are different code points is another trap. Searching for a trailing ㄱ with a leading ㄱ will not match
  • The widest option is \p{Script=Hangul}. In the section 4 table it was the only pattern that caught both sides
  • But widest is not always right. For username validation you may need to reject jamo that are mid composition. Deciding what to admit comes first

9.1 What NFKC additionally changes

This is the point where you think, then why not unify everything with NFKC. You have to actually see what changes.

--- 9-3. NFC/NFD는 호환 자모를 건드리지 않는다 ---
입력        NFC       NFD       NFKC      NFKD
U+3131 ㄱ   U+3131    U+3131    U+1100    U+1100
U+3158 ㅘ   U+3158    U+3158    U+116A    U+116A
--- 9-4. NFKC가 추가로 바꾸는 것들 ---
구분                원본    NFC     NFKC      변경됨
----------------------------------------------------
전각 영문 ＡＢＣ    ＡＢＣ  ＡＢＣ  ABC       O
전각 숫자 １２３    １２３  １２３  123       O
로마숫자 Ⅷ          Ⅷ       Ⅷ       VIII      O
원문자 ㈜           ㈜      ㈜      (주)      O
단위 ㎉             ㎉      ㎉      kcal      O
합자 ﬁ              ﬁ       ﬁ       fi        O
--- 9-5. NFKC는 되돌릴 수 없다 ---
'㈜'.normalize('NFKC') = (주)  (코드포인트 3개)
원본으로 되돌릴 방법이 있는가 : 없다 (정보가 손실된다)

The first table states an important fact. NFC and NFD do not touch compatibility jamo. U+3131 survives canonical decomposition unchanged. Only NFKC and NFKD change it.

And the second table shows how much NFKC changes along the way. The enclosed 「㈜」 becomes the three characters (주), and the unit 「㎉」 becomes kcal. There is no way back. Annex 15 says as much explicitly. Compatibility normalization forms must not be blindly applied to arbitrary text, because they erase many formatting distinctions.

  • NFKC is useful for search indexes. It lets a fullwidth query match halfwidth body text
  • But do not use it for the stored, displayed original. If a company name with 「㈜」 is stored as (주), it cannot be recovered
  • The practical arrangement is store the original as NFC and build a separate NFKC index. You keep both values
  • In other words the normalization form may differ per layer. What matters is that each layer states which form it holds

9.2 This is not a Hangul only problem

--- 9-6. 이모지·결합 문자도 같은 문제 ---
구분                      .length  코드포인트   자소
é 합성형 (U+00E9)               1           1      1
é 분해형 (e + U+0301)           2           2      1
가족 이모지                     8           5      1
국기 KR                         4           2      1
정규화 후 같은가                        : true

The letter é has the same structure. There is a single precomposed code point, and there is e with a combining acute accent as two. They look the same on screen and === is false. Every prescription in this article applies unchanged.

Emoji are slightly different. The family emoji is 8 code units, 5 code points and 1 grapheme cluster. That is not a problem normalization unifies; it is one character made of several code points from the start. So there is a second, independent reason to need Intl.Segmenter. The conclusion that grapheme clusters are the only safe way to count what a user sees holds from both directions.

10. The boundary decision table - where to normalize exactly once

I collected every boundary crossed so far into one table. If you take one thing from this article, take this.

BoundaryWhat breaksWhere to normalize

10.1 Why exactly once

What is wrong with normalizing in many places? There are reasons not to recommend it even though it works.

  1. A gap will always appear. Attaching normalization at every comparison site means reattaching it whenever new code arrives. Miss one and that one place is quietly wrong
  2. You lose the ability to state an invariant. Normalize once at the boundary and you can write the sentence every string inside here is composed. Scatter it and you cannot, and every reader has to trace it themselves
  3. Whether it was normalized becomes a branch. Once code starts asking whether this spot is normalized, the design has already collapsed
  4. It conflicts with places needing the original. Signature verification or faithful reproduction requires keeping the pre normalization value. With a single normalization point you can say everything before it is the original
  5. Cost is genuinely not the issue. Normalization is idempotent, and applying it again to an already normalized string yields the same result. So the reason is ownership, not performance

10.2 Diagnostic order

When a suspicious situation arises, the order is this. Three steps from top to bottom usually settles it.

  1. Dump the bytes. View the string or filename with od, or print code points. A run of three byte groups starting with e1 84 means decomposed. Starting with ec or ed means composed
  2. Count length three ways. See whether code units, code points and grapheme clusters disagree. If the first two exceed the grapheme count, it is decomposed
  3. Normalize both sides and compare. If they become equal, the cause is confirmed. That one line is the end of the diagnosis
  4. Once confirmed, pick the fix location from the table above. Fix the boundary the value entered through, not the site where the symptom appeared

11. What this article could not verify

For balance, the limits. Writing down unverified things as verified would mislead the next reader.

  • Behaviour on macOS and other filesystems. The test environment was only Windows and NTFS. The common claim that macOS stores in a decomposed style could not be verified, so I do not assert it. Checking it yourself with the method in 3.2 is the right move
  • Various Linux filesystems. Not tested. They are generally said to treat filenames as byte sequences, but I confirmed nothing by execution
  • Behaviour of the zip command. This environment has no zip, so PowerShell stood in. Name encoding handling may differ across zip and unzip implementations
  • Per database behaviour. Whether a particular database normalizes at write time was not tested. It may vary with collation settings, so check with the product you use
  • Per browser input method behaviour. Which input paths produce decomposed text was not tested by execution. Since the prescription is to survive either way, though, it matters little in practice
  • Normalization performance. Whether the cost is meaningful on large texts was not measured. Skipping normalization for performance reasons without measuring is not recommended

The unverified items do share one trait. They are all questions about what the other side does. And this article's prescription does not depend on knowing that. Normalize at the boundary and it stops mattering which form the other side sends. That is the reason to write a boundary contract.

Conclusion: the problem is not storage, it is the boundary

This article started with two files of the same name in one folder. The cause was not an encoding setting, not a filesystem bug, not a defect in some tool. It was that Unicode permits one character to be represented two ways, and nobody decided where to unify it.

Summarizing what execution confirmed: the storage layer is largely faithful. JSON, file I/O, tar and zip all carry the form across unchanged. They ruin nothing. Which is exactly why a decomposed string, once admitted, survives until it leaves the system. The accident happens where it meets code that expects composed text. The line that finds a file, the line that runs a regex, the line that counts length, the line that builds a hash.

Among those, the one that fires overwhelmingly most often in Korean services is [가-힣] matching zero decomposed characters. Two to zero, three to zero. Widening the range with jamo still gives zero. And this failure throws nothing. The validator admits, the filter misses, the checker returns all clear. The result wears the shape of success, not failure.

So the conclusion is not normalize your strings. It is closer to pick one normalization point and write it down. Defending right before each comparison will always miss a spot. Unify once at the boundary and you can write one sentence about everything inside: all strings in here are composed. The difference between code that has that sentence and code that does not is the whole of this problem.

There is one thing you can do right now. Find the code in your repository that checks Korean strings with [가-힣], and feed one decomposed sample into that spot. If something that should pass is rejected, or something that should be caught passes, that validator has been doing half a job all along. And the place to fix is not that regex, it is the boundary that string came in through.

# Unicode Normalization Boundary Checklist (NFC / NFD)

> Source: braindetox.kr — When Hangul Falls Apart Into Jamo, NFC and NFD
> Standards basis: Unicode UAX #15 (normalization forms), UAX #29 (grapheme clusters)
> How to use: walk the path Hangul travels from top to bottom. Any boundary with no answer to who normalizes here is your accident site.
> You can paste this file straight into an AI assistant and say review our code against this.

## 0. Thirty second triage — if any of these apply, read the whole thing

- [ ] You compare, search or sort Hangul strings
- [ ] Hangul arrives from user input, filenames or an external API
- [ ] You count characters or truncate strings
- [ ] You look up files by name
- [ ] Hangul goes into hashes, signatures or cache keys
- [ ] You exchange archive files

## 1. Three core facts

1. The same 한 may be one code point (U+D55C) or three (U+1112 U+1161 U+11AB)
2. The rendered output is identical. No human can tell them apart visually
3. Hangul decomposition and composition are algorithmic, so there are **no exceptions**. Every syllable is in scope

## 2. Boundary decision table — what breaks where

| Boundary | What breaks | Where to normalize |
|---|---|---|
| Web form to server | Length checks triple, regex validation flips | NFC right after the server receives it |
| External API receive | Sender's form is out of your control | NFC right after parsing |
| Directory listing read | Entries arrive decomposed, prefix filters catch half | NFC immediately on the readdir result |
| File write | Two identical looking names get created | NFC before assembling the path |
| Archive to extract | Names are preserved, breaks at the next consumer | NFC before packing, or right after extracting |
| Database write | A unique index sees one name as two | Assume normalized, else just before write |
| Search index build | Decomposed documents go missing from the index | NFC before indexing |
| URL and query build | One query becomes two URLs, splitting caches and metrics | NFC before building the link |
| Hash and signature | Same characters, different hash | Fix by convention, then NFC before signing |
| Truncation and summaries | Trailing consonants cut, **unrecoverable** | Normalize first, truncate second |
| Rendering to screen | Nothing breaks | Do not. It is already too late |

## 3. Diagnostic commands — inspect bytes and code points

### 3.1 Viewing filename bytes in a shell

```
# Inspect filename bytes

# How to read it

### 3.2 Determining a string's state (Node)

```
const cps = s => [...s].map(c => 'U+' + c.codePointAt(0).toString(16).toUpperCase()).join(' ');
console.log(cps(s));
console.log('code units', s.length);
console.log('code points', [...s].length);
console.log('bytes', Buffer.byteLength(s, 'utf8'));
console.log('graphemes', [...new Intl.Segmenter('en', {granularity:'grapheme'}).segment(s)].length);
console.log('already NFC', s === s.normalize('NFC'));
```

### 3.3 Determining a string's state (Python)

```
import unicodedata
print(len(s), len(s.encode('utf-8')))
print(unicodedata.is_normalized('NFC', s))

```

```
const fs = require('fs');

## 4. Rules for deciding where to normalize

- [ ] Have you settled on **exactly one form** (generally NFC)
- [ ] Have you **written that form down** (verbal agreements get forgotten)
- [ ] Is the normalization point **at a boundary** (not right before each comparison)
- [ ] Can you **write the sentence** every string inside here is NFC
- [ ] Is there anywhere that must keep the pre normalization original (signing, faithful reproduction)
- [ ] Are you **using the return value** of `normalize()` (calling it alone does nothing)
- [ ] If a search index needs NFKC, is **the original kept separately as NFC**

### Why exactly once

1. Attaching it at every comparison site risks **a miss every time new code lands**
2. Doing it at the boundary lets you **state an invariant as a sentence**
3. Once code appears asking whether this spot is normalized, the design has already collapsed
4. With a single normalization point you can say everything before it is the original
5. Normalization is idempotent so cost is not the issue. The reason is **ownership**

## 5. Frequently broken patterns and their fixes

| Symptom | Cause | Fix |
|---|---|---|
| Two files with the same name appear | Created once in each form | Unify to NFC before assembling the path |
| A file that exists is reported missing (ENOENT) | Stored decomposed, looked up composed | Use the readdir result as given |
| `[가-힣]` validation rejects a normal name | Input is decomposed | NFC before validating |
| A Hangul mixing filter catches nothing | Target is decomposed, `[가-힣]` is powerless | Check after normalizing, or use the Script property |
| A banned word filter is bypassed | Evading input is decomposed | NFC at the input boundary |
| grep does not find it in the log | Document and pattern forms disagree | Put both sides in the same form |
| Deduplication does not work | Set and unique indexes compare bytes | Normalize the key to NFC |
| A few entries jump to the top when sorting | Decomposed leading jamo sit in the U+1100 area | NFC before sorting |
| A ten character limit rejects a normal name | Counting code units triples it | Count grapheme clusters |
| A three character minimum admits one character | Decomposed single character has length 3 | Count grapheme clusters |
| Preview text shows a broken character | The trailing consonant was cut | Normalize first, truncate second |
| A setting was entered but has no effect | Object keys split into two forms | Normalize keys to NFC |
| Same file, different hash | The forms differ | NFC before signing, state the convention |
| One query shows as two rows in analytics | There are two URLs | NFC before building the link |
| A seven character name overflows the column | Decomposed bytes are triple | NFC before write, size columns in bytes |

## 6. Choosing a normalization form

| Form | What it does | Where to use | Caution |
|---|---|---|---|
| NFC | Canonical decomposition then canonical composition | Default for storage, comparison, transport | Unify on this in most cases |
| NFD | Canonical decomposition | Jamo level work such as initial consonant search | Use only within that stretch |
| NFKC | Compatibility decomposition then canonical composition | Search indexes | **Irreversible**, never on the original |
| NFKD | Compatibility decomposition | Rare | Same caution as above |

- `[가-힣]` catches **only precomposed syllables**. Matches against decomposed text are 0
- `[ㄱ-ㅎㅏ-ㅣ]` is the **compatibility jamo** range. It is unrelated to decomposition and also gives 0
- Decomposed jamo live in the `U+1100`~`U+11FF` area
- To open widest use the Script property escape, and always attach the `u` flag
- Widest is not always right. **Decide what to admit first**

## 7. Final three lines before shipping

- [ ] Does this code actually handle **one decomposed input**
- [ ] Is there **exactly one** normalization point, at a boundary
- [ ] Does truncation come **after** normalization
