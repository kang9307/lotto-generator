Here Document 实战 - 变量展开的开与关，以及缩进陷阱

加在定界词上的那一个引号改变整段正文的解读方式。下面的输出全部是跑出来原样贴的

2026-09-01 开发/基础设施

脚本要生成十行配置文件时，用十次 echo 的人和用 here document 的人，差别不是口味问题。十行里只要有一行带上双引号，前一种写法就塌了。here document 这个语法存在的意义就是接手这块活，所以shell 到底把正文动到什么程度，就是这套语法的全部。

这条边界只在一个地方定下来：定界词有没有加引号。这一个字符同时改变 $、反引号和反斜杠的命运。剩下的坑要么由此派生，要么收敛成同一个问题——找不到结束定界词。

下面的输出全部是在 Windows 的 Git Bash 环境、GNU bash 5.2.37(1)-release (x86_64-pc-msys) 上实际跑出来后原样搬过来的。需要对照的地方也用同一台机器里的 dash 跑了一遍，结果分岔的位置都随手记下了。

shell 的行为随实现和版本而变。本文的输出来自上面写明的那一个组合，尤其是 here document 的内部存放方式和换行处理，是 MSYS 系与 glibc Linux 可能不同的地方。没能确认的部分都收在后面。

here document 顶替的是哪块活

拼多行字符串的办法有好几种：重复 echo、把换行塞进 printf、或者往一个变量里接 \n。这三种只在内容里没有引号时才舒服。一旦进来的是配置文件、SQL 或 JSON 这类引号本身就是内容一部分的文本，外层引用和内层引用就会叠在一起，变成没法读的行。

# 引号进入内容的那一刻
echo "{"                     # 这行还行
echo "  \"name\": \"$app\","  # 从这里开始眼睛就疼了
echo "  \"debug\": false"
echo "}"

# 同一件事用 here document
cat <<EOF
{
  "name": "$app",
  "debug": false
}
EOF

here document 解决的正是这个位置。正文里的引号没有任何含义，因为 shell 根本不会把那些行拆成词。换行原样保留，缩进也原样过去。如果连引号的一般规则本身都还发虚，那应该先看 Shell 引号规则。这里只讲加在定界词上的引号，那是性质完全不同的东西。

  • 正文里的 " 和 ' 不用转义、也不会被当成引号
  • 换行按字面保留，完全没有写 \n 的场合
  • 正文进的是命令的标准输入，不是参数，所以和参数长度限制无关
  • 代价是它占用标准输入，会和本来就在用标准输入的地方相撞。第 7 节讲这个
  • 定界词按惯例多用 EOF，但任何词都行。挑一个正文里不可能出现的词最好

定界词上的那一个引号

本文只带走一条的话，就是这条。<<EOF 和 <<'EOF' 会把同一段正文读成完全不同的东西。我把八种输入放进同一个文件，用两种形式各跑了一遍。

name=world

# A: 不加引号的定界词
cat <<EOF
plain: $name
cmdsub: $(echo hi)
backtick: `echo hi`
backslash-dollar: \$name
backslash-n: \n
backslash-backslash: \\
tilde: ~
star: *
EOF

# B: 正文一个字符都没改，只给定界词加了引号
cat <<'EOF'
plain: $name
cmdsub: $(echo hi)
backtick: `echo hi`
backslash-dollar: \$name
backslash-n: \n
backslash-backslash: \\
tilde: ~
star: *
EOF

跑出来的输出如下。

plain: world
cmdsub: hi
backtick: hi
backslash-dollar: $name
backslash-n: \n
backslash-backslash: \
tilde: ~
star: *

=== B: <<'EOF' (quoted) ===
plain: $name
cmdsub: $(echo hi)
backtick: `echo hi`
backslash-dollar: \$name
backslash-n: \n
backslash-backslash: \\

star: *
正文里写的<<EOF 的输出<<'EOF' 的输出发生了什么

$(echo hi)hi$(echo hi)命令替换
反引号里的 echo hihi反引号原样旧写法的命令替换
\$name$name\$name反斜杠挡住美元符号、自己消失
\n\n\n两边都原样。n 不是特殊字符
\\\\\只有前者剥掉一层反斜杠
~~~两边都原样。不做波浪号展开
***两边都原样。不做路径名展开

关掉的写法有三种

能用的不只是单引号。POSIX 规范写明，只要定界词中有任何一部分被引用，正文就不展开。所以下面三种效果完全一样。这三种形式在 bash 5.2.37 和 dash 上都验证过确实把展开关掉了。

  • <<'EOF' — 最常见、也最显眼。用这个就行
  • <<"EOF" — 双引号一样关得干净。看着像是会半开着，其实不是
  • <<\EOF — 一个反斜杠也能关掉。正因为短，反而最容易看漏

here document 不做的展开

表里最后两行最常被误解。哪怕是不加引号的 here document，分词、路径名展开和波浪号展开都不会发生。因为正文从一开始就不是词，而是被当作一整块文本。真正会发生的只有参数展开、命令替换和算术展开三样，反斜杠遵循和双引号内部一样的规则。

  • 所以正文里写 *.log 也不会展开成文件清单。想让对面去展开时这一点很省事
  • ~/bin 同样不会变成家目录路径。想把本地的家目录写死进去就用 $HOME
  • 正文里的空格原样保留，靠多个空格对齐的排版不会散掉
  • 算术展开 $(( )) 是开着的。想让对面算就用 \$(( )) 挡住

只想展开一半的时候

实务里最常出现的需求是大部分原样保留、只把几个位置填成当前的值。用不加引号的 here document，把其余全部用 \$ 挡住即可。能做是能做，但下面这段也顺便说明了它为什么很快就会变脏。

LOCAL_DIR=/tmp/demo

cat <<EOF
cd $LOCAL_DIR
for f in *.log; do
  echo "\$f"
done
total=\$(( 1 + 2 ))
echo "\$total \$HOME"
EOF
cd /tmp/demo
for f in *.log; do
  echo "$f"
done
total=$(( 1 + 2 ))
echo "$total $HOME"

如愿只有 $LOCAL_DIR 一处变成了值。问题在比例：六行里有五个转义。二十行这么送过去，反斜杠就超过二十个，只漏掉一个，就会悄悄填进一个错的值。

  • 转义数量超过三四个就掉头。给定界词加上引号，需要的值改用参数传
  • 用参数传的做法在第 9 节。思路是把本地展开的位置全部收拢到 "$1" 一处
  • 还有一种折中：正文开头先用不加引号的 here document 输出几行 VAR=值，正文本身再用加引号的 here document 接上
  • 无论哪种，原则只有一条。让会展开的位置少到能数得过来

带连字符的形式只删制表符

<<-EOF 一般被说成是会去掉缩进的那个。准确地说，它只去掉行首的制表符。POSIX 规范的原句就是这么写的，结束定界词那一行也适用同一条规则。空格不在范围内。

制表符可以

# 用 cat -A 看到的原文。^I 是制表符
if true; then$
^Icat <<-EOF$
^I^Iline one$
^I^Iline two$
^IEOF$
fi$
echo "after: $?"$

# 运行结果
line one
line two
after: 0

空格不行

编辑器的一个设置就能把它掀翻。下面是把同一个文件改用四个空格保存后跑出来的结果。

# 用 cat -A 看到的原文。一个制表符都没有
if true; then$
    cat <<-EOF$
        line one$
        line two$
    EOF$
fi$
echo "after"$

# 运行结果
e2b.sh: line 7: warning: here-document at line 2 delimited by end-of-file (wanted `EOF')
e2b.sh: line 8: syntax error: unexpected end of file
exit=2

这里因为有个 fi 兜着，才以语法错误炸了出来。这算走运。要是外面没有块包着，它就连错误都不报，安静地过去了。第 5 节看那一边。

当制表符就是内容时

规范的原句是「剥掉行首的全部制表符」，不是只剥你缩进的那些。所以把制表符本身带有含义的内容用带连字符的形式输出，那些制表符也会一起没。Makefile 的配方行就是典型。

# 原文 (^I 是制表符)
cat <<-EOF$
^Iall:$
^I^Igcc -o app main.c$
^IEOF$

# 输出 — 配方行的制表符没了。这份 Makefile 跑不起来
all:$
gcc -o app main.c$

# 同样的内容不加连字符
cat <<EOF$
all:$
^Igcc -o app main.c$
EOF$

# 输出 — 制表符还在
all:$
^Igcc -o app main.c$
  • 带连字符的形式只有内容里没有制表符时才安全。有的话就放弃缩进，把正文顶到最左边
  • 输出 Makefile、TSV、用制表符对齐的表格时不要用带连字符的形式
  • 它和编辑器「制表符转空格」的设置正面相撞。要么给这一个文件单独开例外，要么干脆不用带连字符的形式
  • 替代做法是顶格写。看着乱，但不依赖编辑器设置
  • 另一种替代是用可展开的形式输出后再用 sed 's/^ *//' 去掉空格。只在内容本身没有行首空白时用

找不到结束定界词时

结束定界词那一行有三个条件：只能有定界词和换行、两者之间不能有空白、不是带连字符的形式就必须从行首开始。任何一条不满足，shell 就会把文件末尾之前的全部内容当成正文。

失败来得很安静

外面没有块包着的话，连语法错误都不会有。下面是把用空格缩进的带连字符形式，后面再接上几条命令。

# 原文
cat <<-EOF$
    body line$
    EOF$
echo "THIS SHOULD PRINT"$
touch /tmp/demo/marker$

# 运行结果
e2c.sh: line 5: warning: here-document at line 1 delimited by end-of-file (wanted `EOF')
    body line
    EOF
echo "THIS SHOULD PRINT"
touch /tmp/demo/marker
exit=0

# marker 没有被创建
ls: cannot access '/tmp/demo/marker': No such file or directory

这是整套语法里最危险的样子。退出码是 0，警告只走标准错误，后面跟着的命令没有被执行、而是被当成字符串打印了出来。如果日志只收标准输出，这和一次成功的运行看不出区别。在 CI 里这个脚本会亮绿灯。

退出码会漏掉什么，写在 Shell 退出码与 set -e 那边。这类事故只能靠不丢掉标准错误抓住。

违反的条件bash 5.2.37 的反应退出码抓得住吗
定界词后面多一个空格警告之后吞到文件末尾0要盯着标准错误才行
空格缩进 + 带连字符同上0要盯着标准错误才行
同上，但在 if 块内警告加上 syntax error: unexpected end of file2抓得住
拼写或大小写不一致同一条警告。eof 不是 EOF0 或 2同上
前面多了别的字符 (xEOF)当成正文的一行0靠输出变长察觉

同一个空格缩进的文件在 dash 上跑，消息不一样。只有 Syntax error: end of file unexpected (expecting "fi")，没有 bash 那句「哪一行的 here document 在等哪个定界词」的贴心提示。需要诊断的时候，bash 这边的警告文有用得多。

  • 原因往往是定界词后面那个看不见的空白。用 cat -A 看清楚是 EOF$ 还是 EOF $
  • 正文里有可能出现定界词那个单词的话，就别用 EOF，改用 __CONFIG_END__ 之类
  • 定界词的匹配区分大小写。正文里的 eof、Eof、MARKERX 以及缩进过的 MARKER，验证下来都没有被当成结束
  • 如果用了把脚本拼接起来的生成器，这里最先坏。拼完之后用 bash -n 只检查语法

重定向与管道的先后

here document 是重定向的一种，所以它和别的重定向放在同一行时，先后顺序就让人在意。答案是顺序无所谓。两者都在命令执行之前处理，而且动的是不同的文件描述符。

# 重定向在前
cat > out1.txt <<'EOF'
one
two
EOF

# 重定向在后
cat <<'EOF' > out2.txt
one
two
EOF

# 接上管道 — 正文是管道左边那条命令的输入
cat <<'EOF' | tr 'a-z' 'A-Z'
alpha
beta
EOF
out1.txt:
one
two

out2.txt:
one
two

ALPHA
BETA

三种写法都按预期工作。不过哪种更好读是有定论的。把重定向放在前面，只读命令行那一行就知道输出去了哪里。放在后面，要越过十行正文才看得见 > out.txt。

  • 同一行放两个 here document 也行。正文按书写顺序，从下一行起依次读取
  • 和管道混用时容易糊涂的只有一点：here document 喂的是左边那条命令，不是整条管道
  • 对于要求文件名的命令，用 - 或 /dev/stdin，或者用进程替换 <(...) 包起来
  • 进程替换会开子 shell。里面改的变量为什么留不到外面，写在 管道里的 while 为什么变量会消失 那边

它会吃掉标准输入

here document 是用来填标准输入的语法，所以它和本来就在用标准输入的地方相撞，是排好日程的事。最有名的事故就是循环里的 ssh。我拿一个会把标准输入读到底的程序当替身，用三行列表复现了一遍。

printf 'host-a\nhost-b\nhost-c\n' > hosts.txt

# 像 ssh 那样把标准输入整个读掉的替身
drain() { echo "  [$1] draining stdin..."; cat > /dev/null; }

# 1. 直接这么写
while read -r h; do
  echo "visiting $h"
  drain "$h"
done < hosts.txt

# 2. 挡住内层命令的标准输入
while read -r h; do
  echo "visiting $h"
  drain "$h" < /dev/null
done < hosts.txt

# 3. 用另一个文件描述符传列表
while read -r h <&3; do
  echo "visiting $h"
  drain "$h"
done 3< hosts.txt
=== 1. loop body drains stdin (the ssh problem) ===
visiting host-a
  [host-a] draining stdin...

=== 2. same loop, stdin closed for the inner command ===
visiting host-a
  [host-a] draining stdin...
visiting host-b
  [host-b] draining stdin...
visiting host-c
  [host-c] draining stdin...

=== 3. same loop, list fed on fd 3 instead ===
visiting host-a
  [host-a] draining stdin...
visiting host-b
  [host-b] draining stdin...
visiting host-c
  [host-c] draining stdin...

第 1 种只处理了第一行就结束了。没有报错，退出码也正常。往三台服务器发布的脚本只碰了一台却报告成功，就是这个样子。真正的 ssh 用 -n 选项做的就是同一件事，ffmpeg 和一部分包管理器也有同样的习性。

有意思的是挂上 here document 之后这个问题会自己消失。here document 把那条命令的标准输入替换掉了，内层命令就够不着外面的列表。同一个循环改成 drain "$h" <<EOF ... EOF 的形式，三行全部处理完，这一点验证过。

  • 原因永远一样：循环的输入和命令的输入是同一个描述符
  • 办法 1：给内层命令加 < /dev/null。最短，确定内层不用输入时就这么写
  • 办法 2：列表用 3< 传，读的时候写 read -r h <&3。这样把标准输入留给内层命令正常使用
  • 办法 3：给内层命令挂一个 here document。反正本来就要往远端送脚本的话，这样最自然
  • 办法 4：干脆不用 while read，先把数组填好再用 for 循环。列表不大时这最稳

here string 用在只有一行时

<<< 是 here document 的单行亲戚。它是 bash 扩展，POSIX 规范里没有。在 dash 上跑会直接以 Syntax error: redirection unexpected 猝死。需要可移植性的脚本，路就在这里分岔。

# here string 会在末尾补一个换行
printf 'abc' | wc -c     # => 3
wc -c <<< 'abc'          # => 4

# 不加引号也不会被拆成词
v='a b'
cat <<< $v      # => a b
cat <<< "$v"    # => a b
cat <<< '$v'    # => $v

# 和 read 搭配时不会产生子 shell
read -r first rest <<< "alpha beta gamma"
echo "first=$first rest=$rest"      # => first=alpha rest=beta gamma

# 用管道的话变量留不下来
echo "alpha beta gamma" | read -r f2 r2
echo "f2=[$f2] r2=[$r2]"            # => f2=[] r2=[]

第三段才是用 here string 的真正理由。echo ... | read 里 read 跑在子 shell 中，变量会蒸发；而 here string 是重定向，所以不产生子 shell。同理 while ... done <<< "$var" 这种写法也安全。

  • 末尾会多一个换行。凡是要数字节的地方，这一个字符就会改变结果
  • 变量为空时也仍然进去一个换行。wc -l <<< "$empty" 是 1，不是 0
  • 不加引号也不会分词。不过还是写成 "$v" 更好，否则读的人会犯嘀咕
  • 放多行的值也可以。放 $'one\ntwo\nthree' 进去，wc -l 会返回 3
  • 想关掉展开就在值那一侧加单引号。这和定界词的引号规则是两码事

往远端送时在哪一侧展开

ssh host bash -s <<EOF 这种写法会出事，原因只有一个：正文被解释了两次。一次是本地 shell 构造 here document 的时候，另一次是远端 shell 把那段文本当脚本读的时候。决定由哪一侧来展开，就是这一节的全部。没有远程连接也行，用 bash -c 立起第二个 shell，同样的结构就出来了。

export TAG=local-tag

# A: 不加引号的定界词 — 全部在这一侧展开
bash -c 'export TAG=remote-tag; exec bash -s' <<EOF
echo "TAG seen = \$TAG"
echo "TAG baked = $TAG"
echo "PID of the second shell = \$\$"
EOF

# B: 加引号的定界词 — 全部在那一侧展开
bash -c 'export TAG=remote-tag; exec bash -s' <<'EOF'
echo "TAG seen = $TAG"
echo "PID of the second shell = $$"
EOF

# C: 只把需要的值用参数传过去
bash -c 'export TAG=remote-tag; exec bash -s -- "$1"' _ "$TAG" <<'EOF'
echo "argument from the local side = $1"
echo "value from the remote side  = $TAG"
EOF
=== A ===
TAG seen = remote-tag
TAG baked = local-tag
PID of the second shell = 1780

=== B ===
TAG seen = remote-tag
PID of the second shell = 1781

=== C ===
argument from the local side = local-tag
value from the remote side  = remote-tag

(参考: 跑这个实验的外层 shell 的 PID 是 1777)

A 里那两行就是本节的摘要。\$TAG 给出的是远端的值 remote-tag，而 $TAG 是把本地的值 local-tag 写死进文本后送过去的。C 是不把两者搅在一起的做法。正文整体关掉展开，本地的值只从参数位置进来。会展开的位置就减少到看得见的个数。

sudo 的纹理稍有不同。这里常见的错误是 sudo cat > /etc/some.conf <<'EOF'。重定向不是 sudo 处理的，而是调用它的那个 shell 处理的，也就是没有权限的那一侧在开文件。同样的结构，我用不存在的目录代替权限验证了一下。

cat > /nonexistent_dir/x.conf <<'EOF'
payload
EOF
# => e12.sh: line 3: /nonexistent_dir/x.conf: No such file or directory

tee /nonexistent_dir/x.conf <<'EOF'
payload
EOF
# => tee: /nonexistent_dir/x.conf: No such file or directory

报错的主体不同。前者是带着脚本名和行号的 shell 的消息，后者是 tee 自己的消息。所以要以管理员权限写文件时用 sudo tee，开文件的主体就落到 sudo 底下了。

  • 给 ssh 挂 here document 时，把加引号的定界词当成默认。默认应该是挡住的那一侧，不是漏出去的那一侧
  • 需要本地的值就用 bash -s -- "$v1" "$v2" 传，在远端用 $1、$2 接
  • 远端要跑的脚本变长之后，比起 here document 不如用 scp 把文件送过去再执行。第 15 节还会回到这里
  • 管理员权限的写入用 sudo tee file > /dev/null 或 sudo sh -c 'cat > file'，前者更好读
  • 无论哪种，都别忘了它被解释两次这件事。在远端日志里留下实际执行的那些行，诊断会快很多

写文件的三种惯用写法

here document 一多半的用处是写文件。我把结果应当相同的三种写法用同一段正文跑了一遍，对了对哈希。

# 1. 最常见的写法
cat > a.conf <<'EOF'
key = $VALUE
EOF

# 2. 需要权限、或者也想在屏幕上看到时
tee b.conf > /dev/null <<'EOF'
key = $VALUE
EOF

# 3. 不用外部命令，只靠 shell
while IFS= read -r line; do printf '%s\n' "$line"; done <<'EOF' > c.conf
key = $VALUE
EOF
254b9d772669ad5fc3e7724fe7fe623e *a.conf
254b9d772669ad5fc3e7724fe7fe623e *b.conf
254b9d772669ad5fc3e7724fe7fe623e *c.conf

三个文件逐字节相同。那该选哪个。cat 那种写法读起来好太多，为省一个进程去用第 3 种基本是亏的。不过 cat 和 tee 都是外部命令，所以在最小环境的早期启动脚本这类 /bin 还不存在的场合，第 3 种就成了唯一选择。

  • 默认用 cat > file <<'EOF'。引号习惯性地加上，只在需要展开时才摘掉
  • 需要权限就用 sudo tee。标准输出会漏到屏幕上，所以接一个 > /dev/null
  • 追加写用 cat >> file 或 tee -a。跑两次是否安全是另一个问题，写在 跑两次也安全的脚本 那边
  • 想在写文件前先备份原文件，就在 here document 前面加条件。它是重定向，所以放在 if 里也照样能用
  • 生成文件的权限要紧的话，install -m 0644 /dev/stdin file <<'EOF' 这种写法也值得知道，创建的同时就把权限定下来

装进变量末尾会被剪掉

把 here document 装进变量的惯用写法是 var=$(cat <<'EOF' ... EOF )。这里有一处安静的损失：命令替换会把结果末尾的换行全部去掉。我用一段 19 字节的正文量了四种做法。

# 原文是 19 字节: "line one\nline two\n\n"

v=$(cat <<'EOF'
line one
line two

EOF
)

read -r -d '' v2 <<'EOF'
line one
line two

EOF

IFS= read -r -d '' v3 <<'EOF'
line one
line two

EOF

mapfile -t arr <<'EOF'
line one
line two

EOF
=== the source text is 19 bytes ===
19

$(cat <<EOF)        exit=0 bytes=17
read -r -d ''       exit=1 bytes=17
IFS= read -r -d ''  exit=1 bytes=19
mapfile -t          elements=3

这四行要读出什么

第一行如预期：两个换行没了，17 字节。第二行才是陷阱。read -r -d '' 本来是为了保住换行才用的写法，可不把 IFS 置空的话，最后还是 17 字节。因为 read 会剪掉最后一个字段两端的 IFS 空白，而默认的 IFS 里就含着换行。只有第三行守住了 19 字节。

而且第二行和第三行的退出码都是 1。分隔符设成了空字符，输入里却没有空字符，于是 read 报告「没遇到分隔符，输入就结束了」。哪怕值已经正常装进去了也照样如此。开着立即退出的设置，脚本就死在这里。

( set -e; read -r -d '' z <<'EOF'
payload
EOF
echo "NEVER REACHED" )
# => subshell exit code = 1   (echo 没有被执行)

( set -e; read -r -d '' z <<'EOF' || true
payload
EOF
echo "reached, z=[$z]" )
# => reached, z=[payload]
# => subshell exit code = 0
装载方式末尾换行退出码子 shell什么时候用
$(cat <<'EOF')被剪 (19→17)0会产生末尾换行无所谓的大多数场合
read -r -d ''被剪 (19→17)1不产生最好别用，是个半吊子写法
IFS= read -r -d ''保留 (19)1不产生需要精确到字节时
mapfile -t数组 3 个元素0不产生按行处理时。需要 bash 4 以上
  • read 连开头的空白也剪。read -r a b <<< " x y " 给出的是 a=[x] b=[y]
  • 同样的输入用 IFS= read -r c，得到的是 c=[ x y ]，空白还活着。这就是习惯性加 IFS= 的理由
  • 去掉 -r，反斜杠就会被当成转义吃掉。在 here document 里好不容易保住的反斜杠，可能在 read 这一步丢掉
  • 退出码 1 用 || true 挡住。写成 read ... ; : 也行，但意图不够明显
  • mapfile 要 bash 4 以上，dash 里没有。需要可移植性就把它从候选里去掉

在函数里、一行放两个

here document 正文开始的位置是写着运算符那一行的下一行，不是运算符的紧后面。正因为有这条规则，一行里才能放两个 here document，here document 后面也才能接别的命令。

# 在函数里 — 局部变量也正常展开
emit() {
  local target=$1
  cat <<EOF
[unit]
target=$target
EOF
}
emit alpha

# 在 if 里、在 case 里也一样
if [ -n "$HOME" ]; then
  cat <<'EOF'
inside an if
EOF
fi

# 一行放两个 — 正文按书写顺序从下一行起读取
diff <(cat <<'A'
same
left
A
) <(cat <<'B'
same
right
B
)

# 在 here document 后面接别的命令
cat <<'EOF' ; echo "<- this ran after the heredoc"
body of the heredoc
EOF
[unit]
target=alpha
---
inside an if
---
2c2
< left
---
> right
diff exit=1
---
body of the heredoc
<- this ran after the heredoc

最后一段把规则显示得最清楚。; echo ... 和 here document 运算符在同一行，却没有被正文吞掉，而是在正文结束之后才执行。shell 会把那一行读到底、解析成命令，然后从下一行开始收集正文。

  • 在函数里缩进的问题一模一样。想让结束定界词跟着函数体缩进，就必须用带连字符的形式加制表符
  • 在 case 里用的时候，;; 必须落在结束定界词的下一行。贴在同一行上，它就不再是定界词了
  • 管道的每一段都可以各自挂一个 here document。只不过读的人在那个地方就迷路了
  • 正文里出现和定界词相同的词，只要不在行首就没问题。xEOF 或者缩进过的 EOF 就只是正文

正文是管道还是临时文件

here document 的正文实际装在哪里再送到命令手上，规范并没有规定，交给实现自己去办。在 bash 5.2.37 上查看正在运行的命令的标准输入，能看到它按大小分岔。

# 小正文
ls -l /proc/self/fd/0 <<'EOF'
payload
EOF
# => /proc/self/fd/0 -> pipe:[8589943248]

# 大正文 (约 350KB)
# => /proc/self/fd/0 -> /tmp/sh-thd.6MTpiD (deleted)

# 把边界缩小之后的结果
body=65000    pipe:[4294982180]
body=66000    /tmp/sh-thd.ib1lXH (deleted)
body=70000    /tmp/sh-thd.NCKE8B (deleted)

小正文通过管道递过去，超过管道容量就变成名字已经删掉的临时文件。边界落在六万五千字节和六万六千字节之间，Linux 默认的管道缓冲区是 64KiB，数字对得上。老版本的 bash 无论大小都用临时文件，用管道这个行为是比较近期才进来的。

实务上会绊到的地方有两处。会把标准输入倒回去读第二遍的程序在管道上会失败。临时目录写满或者只读时，大的 here document 同样会失败。

在边界附近看到一件怪事。正文正好是 65,536 字节和 65,537 字节时，这个构建的 bash 会永远卡住。加了 8 秒限制复现了两次。再大一点就落到临时文件上，一切正常。这是个很窄的区间，看起来和 MSYS 那边对管道容量的判定有关，但别的环境是不是也一样，我没能确认。
  • 要送大数据的时候，比起 here document，写成文件再把路径传过去更可预测
  • 如果工具需要重新读标准输入，就别给 /dev/stdin，给它一个真实文件
  • 临时文件名后面带着 (deleted) 是正常的。创建之后立刻删掉，别的进程就看不到了
  • 同理，here document 的正文不会通过 ps 或命令行参数暴露出来。这就是传密文值时它比参数好的原因
  • 不过临时文件的路径哪怕只存在一瞬也是存在的，所以真正的密文值最好保持在能装进管道的大小

和严格模式相撞的地方

如果习惯在脚本开头挂上 set -euo pipefail，那有必要知道它和 here document 碰头的地方。有两处。

# 1. set -u 撞上不加引号的 here document
( set -u; cat <<EOF
value = $DEFINITELY_NOT_SET
EOF
)
# => e12.sh: line 14: DEFINITELY_NOT_SET: unbound variable
# => unquoted exit=1

( set -u; cat <<'EOF'
value = $DEFINITELY_NOT_SET
EOF
)
# => value = $DEFINITELY_NOT_SET
# => quoted exit=0

# 2. 不成对的反引号
cat <<EOF
a `oops
EOF
# => bash: line 1: bad substitution: no closing "`" in `oops
# => exit=1

cat <<'EOF'
a `oops
EOF
# => a `oops
# => exit=0

第一处其实是件好事。要送到对面去的变量名打错时，它不会悄悄填进一个空字符串，而是在这里停下来。第二处就烦人了。正文里放上命令示例或 Markdown，一个不成对的反引号就能把脚本弄死。这两处，只要给定界词加上引号就都没了。

  • 正文里有代码示例、正则表达式、Markdown、Windows 路径时，几乎永远是加引号的定界词为正解
  • 和 set -e 相撞的是第 11 节的 read -r -d ''。别忘了 || true
  • 要在 set -u 下用不加引号的 here document，就用 ${VAR:-默认值} 的形式防一手
  • 诊断时用 bash -n script.sh 只检查语法，结束定界词的问题相当一部分能在执行前被抓住
  • bash -x 不会把 here document 的正文打进 trace。要确认正文，用 cat 先输出一遍更快

什么时候不该用 here document

here document 用顺手了，就什么都想拿它来做。可下面这些情况用别的工具更好。判断标准很简单：正文会不会活得比脚本久。

  • 正文超过 30 行就放到单独的文件里。读脚本时逻辑会被正文埋掉，语法高亮也没有，那份内容也没法单独检查
  • 要替换的位置超过五处就用模板工具。envsubst 在默认环境里往往就有，还能显式限定要替换哪些名字
  • 同一段正文被多个脚本用就抽成文件。把 here document 复制一份放着，两份会慢慢分岔
  • 要生成 JSON 或 YAML 就先看值里会不会进特殊字符。一旦掺进用户输入，here document 是不负责转义的。jq -n 或 yq 才对
  • 远端要跑的脚本很长就把文件送过去再执行。被解释两次的那一段没有了，失败时文件还留在远端可以复现
  • 只有一行就别用 here document。printf '%s\n' '...' 或者 here string 更短
  • 反过来，十行上下的配置文件、送往远端的短脚本、引号很多的文本正是 here document 该待的位置

未能确认的部分

  • 本文的输出全部来自 基于 MSYS 的 bash 5.2.37。glibc Linux 上同一版本是否完全一致，我没能确认。尤其是管道与临时文件分岔的边界值、以及 65,536 字节附近卡住的现象，在别的环境能不能复现我说不好
  • 用 CRLF 保存的脚本在这个构建上跑，here document 工作正常，输出里也没有留下回车符。这很可能是 MSYS 读文件的方式，我并不认为 glibc Linux 上会是同样的结果
  • 对照用的只有同一台机器里的 dash。zsh、ksh、BusyBox ash 没有装，跑不了
  • dash 查不到软件包信息，没能写出准确的版本号
  • 关于 sudo 的那段，是用不存在的目录而不是无权限的目录验证的。重定向由谁处理这个结构是一样的，但真实的权限拒绝情形下的消息我没能确认
  • 远程执行不是用真的 ssh，而是用 bash -c 立起的第二个 shell 复现的。被解释两次这个结构是一样的，但 ssh 把参数拼起来交给远端 shell 的方式所带来的额外引号问题，本文没有涉及
