What Happens When You Carry Over Opus 5 Settings — Prompting Migration to Claude Opus 5.5

Lower default effort, increased thinking per turn, mandatory thinking, and progress updates moved to thinking blocks

September 29, 2026 Tech & IT

When flagship large language models receive an upgrade, the most frequent path taken in software engineering pipelines is simply swapping the model identifier string in the API request configuration while leaving all remaining parameters untouched. If legacy prompts return valid completions without throwing immediate runtime exceptions, teams often assume the migration process is complete. However, according to Anthropic's official technical guide, "Prompting Claude Opus 5.5", the fact that existing prompts function without breaking is entirely distinct from whether carrying over previous settings yields optimal or cost-effective behavior.

The baseline token pricing structure and standard evaluation metrics for Claude Opus 5.5 were covered comprehensively in our earlier release analysis, Claude Opus 5.5 Released — Performance Analysis via Token Price Cuts and Benchmark Metrics. This guide deliberately avoids duplicating release pricing and benchmark scores. Instead, it focuses squarely on the runtime behavioral shifts and prompting adaptations encountered when migrating production workloads from Claude Opus 5 to 5.5. From strict model ID syntax to lower default effort, increased internal reasoning volume, non-disableable thinking returning 400 errors, and intermediate status messages shifting into thinking blocks, we examine the official technical specifications provided by Anthropic.

All configuration parameters, breaking API requirements, and verbatim quotations in this article are derived directly from Anthropic's official documentation, specifically "Prompting Claude Opus 5.5", the "Migration Guide", and "What's New in Claude Opus 5.5". Unsubstantiated claims and speculative performance comparisons are omitted. Items lacking direct confirmation are cataloged explicitly under the "Unconfirmed Items" section at the end of the post.

1. Background and Context — Why Carrying Over Legacy Settings Fails

The official prompting guide opens by acknowledging that existing Claude Opus 5 prompts will generally perform well without modifications. However, this compatibility does not imply that existing configuration parameters should remain frozen. In fact, Anthropic issues an explicit and prominent warning regarding legacy parameter retention:

"If you keep the `effort` value you set for Claude Opus 5, expect longer turns and more output tokens."

The implications of this statement are critical for infrastructure engineering. Retaining previous effort settings without checking them should be expected to lengthen turns and increase output token consumption. Even if a system previously operated with predictable latency and token budgets, the increased thinking per turn within Claude Opus 5.5 can change both execution timing and downstream processing overhead.

1.1. Subtle Runtime Behavioral Shifts and Cost Dynamics

Beyond the four breaking API changes documented in the official migration guide, the prompting layer introduces quiet behavioral changes that produce no explicit runtime errors yet undermine system efficiency. For model identification, Anthropic requires the exact identifier claude-opus-5-5, a fixed model ID with no date suffix. In AWS Amazon Bedrock environments, the identifier is formatted as anthropic.claude-opus-5-5. The migration guide notes that this is the same scheme as claude-opus-5.

How the effort parameter is handled leads to two different outcomes. Omitting the parameter causes requests to execute at a default level one tier lower than on Opus 5. Conversely, keeping the value you used on Opus 5 means that, because Opus 5.5 tends to think more per turn at a given level, the documentation says to expect longer turns and more output tokens. The documentation therefore recommends setting effort explicitly and testing several levels against your own evals rather than carrying over the setting you used on Claude Opus 5.

3. Calibrating Effort — The Lower Default and Three Recommended Adjustments

Claude Opus 5.5 supports all five standard effort tiers: low, medium, high, xhigh, and max. The most significant departure from earlier models is that omitting the parameter defaults execution to medium. On Claude Opus 5 and earlier Opus releases, requests omitting effort defaulted to high. Consequently, migrating an integration without explicitly declaring effort drops execution by one full level compared to historical baselines.

3.1. Divergence Between Level Names and Thinking Volume

A lower default level does not translate to compromised output quality. The documentation highlights that effort tier names do not signify equivalent amounts of deliberation across different model families. In Anthropic's internal evaluations covering software engineering and complex knowledge work, Claude Opus 5.5 operating at medium matched or exceeded Claude Opus 5 operating at high. Furthermore, across several programming benchmarks, low effort approached previous high-tier performance at significantly reduced operational cost.

Conversely, carrying over the effort value you already use changes the picture. According to the documentation, at a given level Claude Opus 5.5 tends to think more per turn than Claude Opus 5, especially at xhigh and max. If you keep the value you set for Opus 5, the documentation says to expect longer turns and more output tokens.

3.2. Three Key Adjustments Recommended by Anthropic

To balance deliberation depth, latency, and cost, the documentation lists three adjustments that help:

  • Allocate Sufficient Headroom for max_tokens: Internal thinking tokens consume budget allocations from max_tokens even when reasoning content is omitted from client delivery. A token limit calibrated tightly for Claude Opus 5 with thinking disabled will truncate responses prematurely. For the long turns that agentic coding can produce, a max_tokens of 128,000, the model's maximum, has worked well in Anthropic's testing.
  • Reserve xhigh and max for Empirically Proven Workloads: The documentation says to reserve xhigh and max for work where you have measured a quality gain.
  • Reduce Effort Levels Rather Than Adding Prompt Instructions: When attempting to curb deliberation, lowering the effort parameter works more reliably than inserting natural language instructions such as "do not think at length." Lowering effort reduces thinking, and with it cost and latency, more reliably than prompt instructions do.

4. Four Migration Steps for Prompts Written for Thinking Disabled

Under Claude Opus 5, developers could disable internal reasoning by passing thinking: {"type": "disabled"} at high effort or below. In Claude Opus 5.5, this capability is entirely removed, and any API request specifying disabled thinking triggers an immediate 400 Bad Request error. Thinking is mandatory across all effort levels. Consequently, existing pipelines optimized around disabled thinking must execute the four migration steps summarized in the table below.

Step Migration Milestone Implementation Details and Documentation Guidance Operational Expected Outcome and Caveats
Step 1 Start at low effort and measure Start at low, measure latency and quality on your own traffic, and move to medium if quality drops. If time to first token still matters after that, a system prompt line such as "Answer directly without deliberating." can reduce thinking further. Less thinking can lower quality, so measure quality when you add that line.
Step 2 Remove instructions that stood in for thinking Remove instructions that asked the model to write out its reasoning in the response as a substitute for thinking. Read the reasoning from summarized thinking blocks instead (display: "summarized"). A prompt that pushes the model to reproduce its reasoning in the response text can be declined with the reasoning_extraction refusal category.
Step 3 Re-test thinking-disabled mitigations Re-test whether you still need the combined instruction that the Opus 5 thinking-disabled guidance recommended (permission to speak before a tool call, what to do when no tool fits, no internal tags). That instruction and the no-thinking rule address artifacts that appear on Opus 5 only when thinking is disabled. Check whether you still need the instruction, and remove the no-thinking rule either way.
Step 4 Read the response by block type Update API parsing logic to check each block's type, since a response may or may not begin with a thinking block, rather than assuming the first block is text. Under the default display: "omitted", the thinking field of that block is empty, so parse by block type.

4.1. Starting at Low Effort and Stripping Surrogate Reasoning

For API endpoints that previously ran with thinking disabled, starting at low effort and measuring is the first step. At low the model keeps its thinking short, but how often it skips thinking altogether depends on your prompts, so measure latency and quality on your own traffic and move to medium if quality drops. If time to first token still matters after that, a system prompt line telling the model to answer directly without deliberating can reduce thinking further. Because less thinking can lower quality, measure quality when you add it.

Moreover, instructions that asked the model to write out its reasoning in the response as a substitute for thinking should be removed, and the reasoning read from summarized thinking blocks (display: "summarized") instead. The reason is that a prompt pushing the model to reproduce its reasoning in the response text can be declined with the reasoning_extraction refusal category.

4.2. Refactoring Parsers for Block-Type Inspection

From an application integration perspective, client-side response parsers must be refactored to inspect block types dynamically. The documentation advises checking each block's type instead of assuming the first content block is text. On Opus 5.5, a response may or may not begin with a thinking block. Under default configuration settings (display: "omitted"), the thinking field within this block is returned empty. Index-based array parsers assuming text at index zero will misinterpret the payload, resulting in blank outputs.

5. User-Facing Progress Updates — Shifting to Thinking Blocks and Four Levers

In autonomous agent architectures executing sequential tool invocations, the mechanism for conveying interim progress notes has shifted fundamentally. On Claude Opus 5, short conversational updates between tool executions arrived as regular text blocks, readily exposed to user-facing consoles. On Claude Opus 5.5, these intermediate notes return as progress-update thinking blocks.

5.1. Preventing Blank Updates via Four Architectural Levers

Because the text of these blocks is empty at the default thinking.display, a client that renders only text blocks can look silent during a long agentic turn. The official documentation identifies four specific levers to restore informative user progress:

  • First Lever (Configuring Display Updates): Include the beta header thinking-display-updates-2026-08-18 and configure display: "updates" to receive summarized intermediate notes.
  • Second Lever (Explicit Tool Declaration): If the model may need to hand the user something verbatim partway through a long turn, such as a code snippet, give it a simple tool for sending the user a message and tell it to reserve the tool for that content. Declare the tool in tools from the first request of the session; adding it later edits the conversation's prefix and invalidates earlier thinking blocks.
  • Third Lever (Specifying Update Triggers): Define explicit conditions and milestones within the system prompt dictating when the agent must report current progress.
  • Fourth Lever (Harness-Level Reminders): With display: "updates" set (the first lever), count consecutive tool-calling steps that give the user nothing to read (no text block and no progress-update text). After several in a row (five, for example), the harness appends a reminder after the latest tool results. If the turn stays quiet, stop after two or three reminders.

5.2. Mitigating Silent Stretches with Turn-Scoped System Reminders

The fourth lever's reminder is appended as a turn-scoped system message. Utilizing the beta header mid-conversation-system-clear-at-2026-08-21 combined with the attribute clear_at: "next_user_message", developers can insert mid-conversation system instructions that expire upon the subsequent user message. In Anthropic's testing on agentic coding tasks, this roughly halved the share of tasks with a long silent stretch, with no measurable change in cost.

The exact verbatim phrasing recommended for this silence-breaking reminder prompt is provided below:

The user hasn't heard from you in a while — say in a few words what you're doing, then continue.

Because each reminder is appended and left in place, rather than inserted for one request and deleted on the next, the documentation explains that the prompt cache keeps matching and the thinking blocks that follow it stay valid.

6. Autonomous Agents and Long-Running Loop Stability Rules

In unattended environments where software agents execute multistep workflows without real-time human intervention, controlling premature turn termination and preventing infinite loops is paramount. The official documentation outlines specific guidelines to maintain operational stability.

6.1. Capping Automatic Continuations and Tracking Time Budgets

When an agent completes a turn without calling a tool despite pending items remaining on its task list, orchestrators frequently inject automated continuation prompts. The documentation advises stopping after two or three automatic continuations on the same task rather than repeating them indefinitely, so that a run that is genuinely stuck ends and can be reviewed.

Time budgets come up in a different context: multiagent harnesses, for example a lead agent that delegates to subagents. If you can estimate how long the task should take, the harness can add a short line at the end of each message it sends back to the model giving the elapsed time against that budget, in seconds, such as elapsed 340s / 1200s. The documentation stresses that these budgets are advisory. The model does not halt autonomously upon reaching time boundaries. Where hard execution boundaries are mandatory, orchestrator harnesses must maintain independent wall-clock timeouts.

The following system prompt addition is one example the documentation gives, written for agents that run fully unattended. It is meant as a starting point that you might need to adapt for your own application. Add it at the end of your system prompt from the first request of the session, and leave it out of human-in-the-loop applications, where someone is there to answer. Expect somewhat more tool calls and output tokens per task:

A standing instruction from the user, the person you are working for. It is about how your turns end. A message with no tool call in it ends your turn, and the work stops there until you are asked to continue. The user has seen you end turns in four ways while work they asked for was still owed, and does not want any of them. One: a long summary of what was done that closes by announcing the next step and has no tool call, so the next thing never starts. Two: an offer to carry on with something unless the user would prefer otherwise, which stops to wait for an answer the user was not going to give. Three: a list of decisions for the user when, by your own account, none of them blocks the rest of the work. Four: deciding that this is a good place to report, because the turn has been long or a milestone is done. Status notes are welcome, and so are your recommendations on open decisions, but put them in the same message as your next tool call and carry on with whatever does not depend on the user's answer. If you notice yourself inviting the user to redirect you or offering to wait, delete it and do the next thing. The stops the user does want are the ones where nothing can move without them, or where the thing blocking you is deliberately protected from you. This does not override the need for confirmation on risky or destructive actions.

6.2. Preserving Prompt Caches and Handling Classifier Refusals

Two runtime engineering nuances require careful handling. First, altering top-level effort parameters between sequential API requests invalidates existing prompt caches. To vary effort dynamically across individual interaction turns while retaining cached prefix tokens, integrations must utilize the beta per-message effort change feature.

Second, Claude Opus 5.5 integrates automated safety classifiers covering domains such as biology, cybersecurity, and reasoning extraction. When a request is declined by these classifiers, the platform does not throw an HTTP error. Instead, it arrives as a normal API response marked with stop_reason: "refusal" and accompanied by a stop_details object specifying the category. You can have such a request retried automatically on a fallback model, except for reasoning_extraction declines, which server-side fallback returns to you instead of retrying.

7. Frontend Code Styling and Vision Prompting Guidance

In web application engineering and multimodal analysis, Claude Opus 5.5 exhibits distinct prompt response characteristics. The official documentation supplies concrete recommendations for guiding visual layout generation and processing high-density graphical assets.

7.1. Specifying Explicit Anti-Patterns Over Vague Directives

When generating HTML and CSS interface code, generic constraints such as "avoid a generic AI look" do not get you far. The guide observes that such a general instruction mostly swaps one default for another. Achieving distinctive styling requires articulating precise anti-patterns and explicitly banned visual elements:

Output a vanilla HTML/CSS personal website with placeholder data. Do not use a cream or off-white background, italic accent words in headlines, numbered "01/02/03" section labels, monospace labels, or pill-shaped buttons.

Explicitly enumerating prohibited colors, typography accents, button shapes, and section labeling conventions allows the model to constrain its styling choices effectively.

7.2. High-Resolution Visuals and Tool Integration

When analyzing visual inputs, Claude Opus 5.5 demonstrates improved baseline accuracy even without external vision utilities. However, for dense information assets such as technical blueprints and engineering schematics, supplying higher-resolution imagery and integrating dedicated image-processing tools still add accuracy. The guide notes that while raising effort improves the interpretation of technical drawings without tools, it provides negligible benefit for standard chart comprehension.

Finally, in conversational chat implementations, the documentation suggests considering removing prompt directives that tell the model to think carefully before answering. In Anthropic's testing in a chat product, removing such a line made replies start sooner, with no clear decline in the quality of the reply.

  • Publication and Modification Timestamps for the Prompting Guide: The official web page and its raw markdown companion lack explicit publication or revision timestamps, leaving the precise release schedule unverified.
  • Detailed Request Schema for Per-Message Effort Configuration: While the prompting guide confirms that per-message effort changes preserve prompt caching, the complete JSON request schema is deferred to external documentation and could not be verified within this document alone.
  • Private Domain Latency and Cost Differentials: The documentation states that output generation is more than 30 percent faster as a flat statement without describing measurement conditions, and presents the finding that medium effort matches or exceeds Opus 5 high as a result of Anthropic's own testing. Actual latency and token cost deltas on proprietary corporate prompt distributions remain subject to local empirical verification.
