ハングルの並び順が期待と違う理由 - ロケールと照合順序

同じリストがツールごとに違う並びになる地点と、一箇所に固定する方法

2026年8月4日 IT/技術

はじめに: データは一つなのに順序が三つある

会員名のリストを管理画面で見る。同じリストをCSVでダウンロードして開く。サーバーに上がった添付ファイルをlsで確認する。三箇所の順序がすべて違う。元のデータは一つなのに。

こうなると、たいてい二つを疑う。エンコーディングが壊れたか、ソートのコードにバグがあるか。実際にはどちらでもない場合の方がはるかに多い。三つのツールがそれぞれ違うソートルールを正常に適用しているのであって、どれも故障していない。故障しているのは「ソートはどこでやっても同じ結果になる」という前提のほうだ。

結論を先に書く。並び順が製品の要件なら、それをシェルの環境変数やDBサーバーの設定に委ねず、アプリケーションコードにコレータとして明示して固定せよ。なぜそうなのか、そしてそうしなかったときにどこでどう食い違うのかを以下で一つずつ見ていく。

文字が字母に分解される現象そのものと、それがファイルシステム・検索・長さ検証で何を壊すのかはハングルが字母に分解される瞬間 - NFCとNFDで扱った。この記事は順序だけを見る。文字が実際に壊れて見える問題はハングルが壊れる地点を特定する方法、圧縮ファイル内の名前が壊れる問題はzipの中のファイル名が壊れる地点のほうだ。正規表現でハングルを捉えるときの罠はハングル正規表現の罠にある。

ここから読み取るべきものが三つある。

  • 最大の違いはハングルとラテン文字の前後だ。ICUの韓国語照合順序はハングルを先に置き、残りはすべてラテン文字を先に置く。二文字だけ比べれば明白で、韓国語コレータではcompare('가', 'a')が負、英語・日本語・中国語のコレータではいずれも正になる。
  • アンダースコアで始まる_tempの位置が跳ねる。コードポイント順では_はU+005Fなので大文字と小文字の間に挟まり、照合順序では記号として扱われて先頭に来る。一時ファイルやシステム項目にアンダースコア接頭辞を使う慣習があるなら、この差はそのまま画面に出る。
  • 六行のうち五行で10번째が1번째より前だ。ロケールをいくら変えてもこれは直らない。数値比較はロケールとは別の軸だからである。

2. コードポイント順 - ハングルはなぜ「おおむね」合うのか

コードポイント順は文字を数値と見なして大小を比べる。人が使う並べ方とは何の関係もない。Unicode照合アルゴリズムの標準文書であるUTS #10が冒頭でこう釘を刺している。

Unicodeコード表における文字の位置は、その並び順を規定しない。

ところがハングルではこの二つが驚くほどよく合う。どのくらいかというと、完成形ハングル音節領域U+AC00からU+D7A3までの11,172文字をすべて並べ、コードポイント順と韓国語照合順序を位置ごとに比較すると、食い違う箇所が一つもない。二文字の組み合わせ3,000件の標本でも結果は同じだ。

偶然ではない。ハングル音節のコードポイントは0xAC00 + (初声 × 588) + (中声 × 28) + 終声という計算式で配置されており、初声・中声・終声の並び順が辞書順と一致する。終声（パッチム）の有無もこの構造に従う。韓国語コレータで確かめると가 < 각、간 < 갈、강 < 개と、いずれもコードポイント順と同じ答えになる。

そこでこういう判断が可能になる。入力が完成形音節だけで、すべて結合形に統一されているなら、コードポイント順は辞書順への正確な近道だ。速度も最も速い。問題はその前提を誰が保証するのかである。

3. 壊れる地点 - 他のものが混ざるとき

前提が崩れる経路は三つある。

3.1 分解形ハングルが混ざるとき

結合形の가はU+AC00の一文字。分解形の가はU+1100とU+1161の二文字だ。コードポイントで見ると0x1100は0xAC00よりはるかに小さいので、分解形は必ず結合形より前になる。リストに分解形が混ざると、その項目がすべて前に押し寄せる。

入力: 가방(結合形) 나무(結合形) 다리(結合形)
      각목(分解形) 남산(分解形) 대구(分解形)

コードポイント順 → 각목 | 남산 | 대구 | 가방 | 나무 | 다리
韓国語コレータ   → 가방 | 각목 | 나무 | 남산 | 다리 | 대구

コードポイント順のほうは辞書順とは何の関係もない結果だ。同じ入力をSQLiteの既定のORDER BYで取り出しても、LC_ALL=C sortで回しても、同じように分解形が前に行く。どの言語の問題でもなく、コードポイント比較というルールそのものの性質である。

分解形がなぜリストに入ってくるのか、どの境界で形が変わるのかはNFC・NFDの記事にまとめてある。ここで付け加えるのは並び順側の事実が一つだ。ICUコレータは二つの形を等しいと見なす。結合形の가방と分解形の가방を比較すると0が返る。ソートは問題なくできるということだ。ところが同じ二つの値をSetに入れるとサイズは2になる。

ソートはできるのに重複除去はできない区間
コレータは二つの形を同等に扱うが、===やハッシュベースのデータ構造は違うものと見る。「ソートしたら隣り合っていたから重複除去もできているだろう」という推論がここで静かに外れる。重複除去はコレータではなく正規化が行う。

3.2 字母と記号が混ざるとき

互換用字母のㅏはU+314Fで完成形音節領域より前にある。コードポイントで並べると가の前に置かれる。ところが韓国語コレータはこの文字をリストの最後尾に送る。ハングルの字母一文字をタグや索引キーに使う画面なら、二つの方式の結果が正反対になる。

絵文字も同様だ。コードポイントでは値が大きいので最後尾に行くが、韓国語コレータでは数字よりも前に置かれる。ユーザーのニックネームのように何でも入りうるフィールドでは、この差が目に見えて現れる。

3.3 大文字小文字が混ざるとき

コードポイント順は大文字をすべて前に集める。Apple、Bananaの次にapple、zebraが来る形なのでアルファベット順には読めない。照合順序は同じ綴りをまとめて置き、大文字小文字は最終段階でのみ考慮する。JavaScriptではこの段階をsensitivityで選べる。

設定区別するものapple vs Apple
base基本文字のみ0（同じ）
accent基本文字 + ダイアクリティカルマーク0（同じ）
case基本文字 + 大文字小文字異なる
variant（既定）すべて-1（appleが前）
caseFirst: 'upper'大文字を前へ+1（Appleが前）

SQLiteのNOCASEはこれにはるかに及ばない。公式文書がASCII 26文字だけを畳むと明記している。実際に'A' = 'a' COLLATE NOCASEは真だが'Ä' = 'ä' COLLATE NOCASEは偽だ。名前検索をNOCASEで作っておいて多言語データを入れると、ここに静かな漏れが生まれる。

4. ロケールが変えるものと変えないもの

「ロケールを韓国語に合わせれば韓国語の順序が出る」という期待は半分しか当たらない。ロケール名はルールを指すラベルにすぎず、実際のルールはその名前を解釈するライブラリが持っている。だから同じ名前が環境によって違う順序を出す。

計測環境（後述の「計測環境と再現」節を参照）で確認されたことだ。

  • LC_ALL=ko_KR.UTF-8 sortとLC_ALL=en_US.UTF-8 sortの出力が一文字も違わない。韓国語ロケールを指定したからといって韓国語のソートルールが付くわけではない。
  • Pythonのlocale.strxfrmもko_KR.UTF-8・en_US.UTF-8・Korean_Korea.949の三つのロケールすべてで同じ結果を出す。
  • 同じ機器のIntl.Collator('ko')だけがハングルをラテン文字より前に置く。ICUは別のルール表を使う。
  • locale.setlocale(locale.LC_COLLATE, '')は機器のシステム設定に従う。計測機器ではKorean_Korea.949として解釈された。開発ノートPCと本番サーバーのシステムロケールが違えば、同じコードが違う順序を出す。

UTS #10の説明がこの状況を正確に突いている。既定の照合表であるDUCETだけではすべての言語を満足させられないため、仕様は「ほとんどの言語で、ユーザーの期待に合わせるにはある程度の調整（tailoring）が必要だ」と述べている。ICUはその調整表を持っており、Cライブラリの実装は持っている場合も持っていない場合もある。

ここにPythonの公式文書が付け加える警告がもう一つある。ロケールはプログラム全体の属性であり、setlocale()はほとんどのシステムでスレッドセーフではない。ウェブサーバーの中でリクエストごとにロケールを切り替えながらソートする設計は、それゆえ採用できない。

5. 数値の並び - ファイル2とファイル10

文字列比較は파일2と파일10の三文字目で2と1を見比べ、1のほうが小さいので파일10を前に置く。ルールどおりに動いた結果であり、ロケールを変えてもそのままだ。

入力: 파일1.txt 파일2.txt 파일10.txt 파일20.txt 파일3.txt 파일100.txt

既定のソート   → 파일1 · 파일10 · 파일100 · 파일2 · 파일20 · 파일3
数値比較を有効 → 파일1 · 파일2 · 파일3 · 파일10 · 파일20 · 파일100

直す方法はツールごとにある。

  • JavaScript: new Intl.Collator('ko', { numeric: true })
  • GNU sort: sort -V（バージョンソート）。上のリストで期待どおりの順序がそのまま出る
  • Python: 数字の塊だけをintに変えたリストをソートキーにする
import re, unicodedata

def natural_key(s):
    s = unicodedata.normalize('NFC', s)
    return [int(t) if t.isdigit() else t
            for t in re.split(r'(\d+)', s)]

sorted(names, key=natural_key)
数値比較を有効にすると生じる罠 - ゼロ埋めが同点になる
numeric: trueでA-007とA-7を比較すると結果は0、つまり同点だ。数として解釈すればどちらも7だからである。桁数を揃えて保存していた時代のデータとそうでないデータが一つのテーブルに混在していると、ここで順序が毎回揺れる。桁数を統一するか、後ろに一意な補助ソートキーをもう一つ付ける必要がある。

6. ツールごとに固定する方法

6.1 シェル - ロケールを信じず釘を打て

スクリプトが作る順序が成果物に残るなら（チェックサム一覧、マニフェスト、比較用ダンプなど）ロケールを明示的に固定しなければならない。方向は二つに一つだ。

# 1) 再現可能なバイト順が目的のとき - どの機器でも同じ結果
LC_ALL=C sort names.txt

# 2) 人が読む順序が目的のとき - シェルでやらずに委ねる
#    （ロケール名が同じでも機器ごとにルールが違いうる）

判断はこうだ。機械が比較するリストならLC_ALL=Cで固定し、人が読むリストならシェルでソートするな。曖昧にシステム既定値に委ねた状態が最も悪い。開発機器とCIコンテナのLANGが違えば、同じスクリプトが違うファイルを作り出す。

6.2 JavaScript - コレータを作って再利用せよ

// 一度作って再利用する
const collator = new Intl.Collator('ko', {
  numeric: true,          // 파일2 < 파일10
  sensitivity: 'variant', // 大文字小文字・発音区別記号まで区別
  caseFirst: 'false'      // ロケール既定値
});

names.sort(collator.compare);

覚えておくべきことが三つある。

  • コレータのインスタンスを再利用せよ。比較のたびにa.localeCompare(b, 'ko')を呼ぶと毎回コレータを組み立て直す。2万件のソートでlocaleCompare方式はコレータ再利用より2倍以上遅い。
  • usage: 'search'でソートするな。MDNが釘を刺している。「ソート・順序付けにsearchを使うのは不適切だ」。実際に가と까を比較するとsortとsearchで符号が逆の値が返る。searchの戻り値は0かどうかだけを見るべきだ。
  • ソートキーをあらかじめ取り出す最適化は使えない。JavaScriptにはICUのソートキー抽出に相当する公開APIがない。Pythonのstrxfrmのような方式が不可能なので、性能が問題ならコレータの再利用が事実上唯一の手段になる。

6.3 Python - 標準ライブラリとICUのあいだ

標準ライブラリだけではlocaleモジュールがすべてだ。strxfrmは文字列を比較用の形に変換し、同じ文字列を繰り返し比較するときに使えと文書が案内している。

import locale
locale.setlocale(locale.LC_COLLATE, 'ko_KR.UTF-8')
result = sorted(names, key=locale.strxfrm)

ただし先に見たとおり、この方式は機器のCライブラリに結果を委ねることであり、スレッドセーフでもない。ICUのルールが必要ならPyICUを入れるのが定石だ。それも難しければ、実務で通用する折衷案は正規化 + 自然順ソートキーを自分で作ることである。ロケールに依存しないので、どの機器でも同じ結果になる。

import re, unicodedata

def sort_key(s):
    s = unicodedata.normalize('NFC', s)          # 分解形を結合形へ
    parts = re.split(r'(\d+)', s)
    return [(1, int(t), '') if t.isdigit() else (0, 0, t) for t in parts]

完成形ハングルだけを扱うリストなら、このキーだけで辞書順が正確に出る。2節で見た全数比較の結果がその根拠だ。

7. データベース - COLLATEをどこに書くかがインデックスを分ける

DBで並び順を直す方法は二つに見える。クエリにCOLLATEを付けるか、列定義に入れるか。結果は同じだがコストがまったく違う。

SQLiteに名前列を作りインデックスを張って実行計画を取ると、差がそのまま現れる。

クエリ実行計画
ORDER BY nameSCAN t USING COVERING INDEX idx_name
ORDER BY name COLLATE NFCSCAN t
USE TEMP B-TREE FOR ORDER BY
WHERE name = ?SEARCH t USING COVERING INDEX idx_name (name=?)
WHERE name = ? COLLATE NFCSCAN t
列定義にCOLLATE NFC + インデックスSCAN t USING COVERING INDEX idx（順序も正常）

クエリにCOLLATEを付けた瞬間、ソート用インデックスも検索用インデックスも一緒に死ぬ。インデックスが既定の照合順序を基準に作られているので、別のルールを要求すると使えない。一時B木を作って毎回ソートすることになり、等値比較は全スキャンに落ちる。

直す場所はクエリではなくスキーマだ。

-- SQLite: 列に照合順序を打ち込み、その上にインデックスを作る
CREATE TABLE members (name TEXT COLLATE NOCASE);
CREATE INDEX idx_members_name ON members(name);

-- PostgreSQL: ICUプロバイダで照合順序を作って列に付ける
CREATE COLLATION ko_icu (provider = icu, locale = 'ko-KR');
CREATE TABLE members (name text COLLATE ko_icu);

-- MySQL 8.x: utf8mb4系の照合順序を列に指定する
CREATE TABLE members (
  name VARCHAR(100) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_as_cs
);

製品ごとに知っておくべきことだ。

  • SQLite: 組み込みの照合順序はBINARY・NOCASE・RTRIMの三つだけ。既定値のBINARYはmemcmp()比較、つまりコードポイント順だ。韓国語のルールが必要ならアプリケーション側で照合順序を登録する必要がある。
  • PostgreSQL: libcとICUの二つのプロバイダがあり、ICU照合順序はエンコーディングと無関係に名前一つで存在する。順序を安定して固定するならICU側がよい。
  • MySQL 8.x: Unicode照合順序の一覧に韓国語専用の照合順序がない。日本語・中国語・ロシア語・ドイツ語などはあるのに、韓国語は一覧に載っていない。既定値のutf8mb4_0900_ai_ciはUCA 9.0.0 / CLDR v30ベースで、発音区別記号と大文字小文字を区別しない。名前の順序を厳密に扱う必要があれば_as_cs系を使う。
照合順序が変わるとインデックスが壊れうる
PostgreSQLの文書はこう書いている。「照合順序の定義が変わるとインデックスが壊れたり他の問題が生じたりしうる。データベースシステムが、格納されたオブジェクトが特定の並び順を持つことに依存しているためだ。」そして、こうしたことがOSを新しいメジャーバージョンに上げるときや、新しいICUにリンクされたバイナリに移すときに実際に起きると付け加える。対応は影響を受けたオブジェクトをREINDEXで作り直し、ALTER COLLATION ... REFRESH VERSIONを実行することだが、文書自身がこのコマンドは実際に作り直されたかを検査しないと明かしている。

8. 同点 - ソートが終わっても順序が決まらない場合

照合順序は二つの値を「同じ」と判定できる。その瞬間、その項目群の最終順序はソートアルゴリズムに渡る。JavaScriptのArray.prototype.sortは安定ソートなので入力順がそのまま保たれる。よい性質に聞こえるが、裏返すとこういう意味だ。

句読点無視オプションを有効にした状態 (compare('한-국', '한국') === 0)

入力 [한-국, 한국, 한.국]  →  出力 한-국 | 한국 | 한.국
入力 [한.국, 한국, 한-국]  →  出力 한.국 | 한국 | 한-국

同じデータなのに入ってきた順序が違えば画面の順序が違う。この問題は照合順序一つでは終わらない。同点が生じる経路が複数ある。

  • sensitivity: 'base'や'accent'にすると大文字小文字だけ違う値が同点になる
  • ignorePunctuation: trueにするとハイフン・ピリオドだけ違う値が同点になる
  • numeric: trueにするとゼロ埋めだけ違う値が同点になる
  • DBでORDER BY nameだけを掛けると同姓同名が同点になる

解法は一つだ。ソートキーに一意な値を一つ付け足せ。DBならORDER BY name, id、アプリケーションなら比較関数が0を返したときにIDでもう一度比べることである。

この同点問題がリストをページに分けるときに何を壊すのかはオフセットページングが構造的にできないことで別途扱った。ソートキーが一意でないと、ページ境界で項目が消えたり二度出たりする。

9. 性能 - 何がどれだけ遅いのか

ハングル文字列2万件をソートした時間だ。五回回した中央値。

方式時間既定比
既定のsort()（コードポイント）10.1 ms1.0倍
Intl.Collatorインスタンス再利用27.0 ms2.7倍
a.localeCompare(b, 'ko')を毎回呼ぶ59.5 ms5.9倍

読み方はこうだ。

  • 照合順序の代価は2.7倍だ。2万件で27ミリ秒なら、ほとんどの画面で論争の種にならない。「遅くなりそうだからコードポイントのままにする」という判断は、この規模では根拠が弱い。
  • 実質的な損はlocaleCompareを比較関数の中で直接呼ぶことだ。コレータを外で一度作る一行で半分に減る。結果はまったく同じである。
  • 数十万件以上をリクエストのたびにソートしているなら、それはソート方式ではなくソートする場所の問題だ。DBのインデックスに下ろすのが正しい。

10. 判断 - 照合順序はアプリケーション層に置く

ここまでの事実を一つの基準にまとめるとこうなる。

状況どこに固定するか理由
ユーザーに見えるリストアプリケーション層の明示的なコレータ
（Intl.Collator・ICU）		環境に関わらず同じ順序。オプションがコードに残りレビューできる
大量リストのページ照会DBの列照合順序 + インデックスクエリのCOLLATEはインデックスを殺す。一意なタイブレーカーを併用
スクリプト・CI成果物LC_ALL=Cを明示再現可能性が目的。人が読む順序ではない
重複除去・キー比較NFC正規化コレータは同等判定をするだけで値を統合しない
ファイル名・パス正規化してから比較分解形が混ざるとコードポイント順が崩れる

「アプリケーション層に置け」という推奨の根拠は好みではなく、以下の四つだ。

  1. 同じロケール名が同じ順序を保証しない。一台の機器でko_KR.UTF-8とen_US.UTF-8のシェルソート結果が同じであり、同じ機器のICU韓国語コレータはまったく違う順序を出した。環境変数は順序を固定する手段になりえない。
  2. ロケールはプロセス全体のものでスレッドセーフではない。リクエストごとに違うルールが必要なサーバーでは構造的に使えない。
  3. DBの照合順序はインフラ変更に引きずられる。OSやICUのバージョンが上がるとインデックスを作り直す必要がありうるとPostgreSQLの文書が警告している。順序ルールがインフラの日程に縛られることになる。
  4. オプションがコードに残る。numeric・sensitivity・caseFirstをどう設定したかがソースに見える。サーバーの環境変数に散らばっていると、画面の順序がなぜそうなのか誰も説明できない。

DBのソートを使うなという話ではない。数万件をページに切って見せる画面なら、ソートはインデックスがやるべきだ。そのときも列定義に照合順序を打ち込み、インデックスをその上に作れ。クエリにCOLLATEを付ける方式は結果だけ合っていてコストは全部払う選択である。

12. 確認できなかったこと

以下の項目はこの記事では計測していない。公式文書を根拠にした部分はそのように表示した。

  • Linux glibc環境でのsortのロケール挙動。上のシェル計測はWindowsのMSYS2ランタイムで出た値だ。glibcは違う照合表を使いうるので、同じ結果を期待してはならない。サーバーでシェルのソート結果が成果物に入るなら、そのサーバーで直接確認する必要がある。
  • PyICUの実際の出力。計測環境にインストールされていない。Python標準ライブラリのlocaleモジュールの挙動だけを計測した。
  • PostgreSQL・MySQLサーバーの実際のソート結果。この記事のDB実測はSQLiteで行ったもので、PostgreSQLとMySQLに関する記述は各公式文書を根拠にしている。インデックスと照合順序の関係は製品ごとに細部が違うので、導入前に対象バージョンで実行計画を直接確認してほしい。
  • macOSのファイルシステムが名前を保存する形の細部。この記事は分解形がリストに混ざったときにソートがどうなるかだけを扱っており、どのファイルシステムがいつどの形で保存するかはNFC・NFDの記事の範囲だ。
  • ICUのバージョンが上がるときに順序がどれだけ変わるか。一つのバージョン（ICU 77.1）でのみ計測した。照合順序のデータはバージョンごとに改訂されるので、順序が契約の一部ならICUのバージョンを固定して回帰テストを置くほうが安全だ。

13. よくある質問

完成形ハングルしか使わないなら既定のソートでよいか

よい。11,172文字の全数比較でコードポイント順と韓国語照合順序が完全に一致する。ただし「完成形ハングルだけ」という前提を守ってくれるコードがどこかになければならない。ユーザー入力・アップロードされたファイル名・外部APIのレスポンスが混ざるリストなら、その前提はすぐに崩れる。

ブラウザごとにIntl.Collatorの結果が違わないか

内蔵されたICU・CLDRのバージョンが違えば細部が違いうる。だから順序がサーバーとクライアントの両方で同じでなければならない画面なら、ソートを片方でだけ行うべきだ。サーバーがソートして返し、クライアントはそのまま描くほうが揺れが少ない。

韓国語なのになぜハングルが後ろに行くのか

コレータのロケールがkoでない可能性が高い。ICUの韓国語照合順序だけがハングルをラテン文字の前に置く。英語・日本語・中国語のロケールではすべてラテン文字が先だ。ブラウザの言語設定をそのまま使っているなら、ユーザーごとに順序が変わる。

ORDER BYの結果と画面の順序が違うが、どちらを直すべきか

二つを合わせようとせず、ソートする場所を一つに減らせ。DBがソートして返した配列をフロントエンドがもう一度ソートしている構造なら、二つのルールが違う以上、結果はずれ続ける。ページ照会が必要ならDB側に統一し、列の照合順序を合わせるほうがよい。

正規化はいつやるべきか

保存の直前に一度が最も安い。読むたびに正規化するとインデックスが使えず、比較のときだけ正規化すると保存された値に二つの形が積み上がり続ける。すでに混ざって保存されたデータがあるならマイグレーションで一度整理し、その後は入力経路で塞ぐ。
