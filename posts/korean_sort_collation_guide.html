한글 정렬이 기대와 다른 이유 - 로케일과 콜레이션

같은 목록이 도구마다 다르게 줄 서는 지점과, 한 곳에 고정하는 법

2026-08-04 IT/기술

서론: 데이터는 하나인데 순서가 세 개다

회원 이름 목록을 관리자 화면에서 본다. 같은 목록을 CSV 로 내려받아 연다. 서버에 올라간 첨부 파일을 ls 로 확인한다. 세 곳의 순서가 전부 다르다. 원본 데이터는 하나인데.

이런 일이 생기면 대개 두 가지를 의심한다. 인코딩이 깨졌거나, 정렬 코드에 버그가 있거나. 실제로는 둘 다 아닌 경우가 훨씬 많다. 세 도구가 각자 다른 정렬 규칙을 정상적으로 적용하고 있는 것이고, 어느 쪽도 고장 나지 않았다. 고장 난 것은 「정렬은 어디서 하든 같은 결과가 나온다」는 가정이다.

결론을 먼저 적는다. 정렬 순서가 제품의 요구사항이라면 그것을 셸 환경 변수나 DB 서버 설정에 맡기지 말고, 애플리케이션 코드에 콜레이터로 명시해 고정하라. 왜 그런지, 그리고 그렇게 하지 않았을 때 어디서 어떻게 어긋나는지를 아래에서 하나씩 본다.

글자가 자모로 분해되는 현상 자체와 그것이 파일 시스템·검색·길이 검증에서 무엇을 깨뜨리는지는 한글이 자모로 분리되는 순간 - NFC와 NFD에서 이미 다뤘다. 이 글은 순서만 본다. 글자가 실제로 깨져 보이는 문제는 한글이 깨지는 지점을 특정하는 법, 압축 파일 안의 이름이 망가지는 문제는 zip 안의 한글 파일명이 깨지는 지점 쪽이다. 정규식으로 한글을 잡을 때의 함정은 한글 정규식 함정에 있다.

여기서 읽어야 할 것 세 가지.

  • 가장 큰 차이는 한글과 라틴 문자의 앞뒤다. ICU 한국어 콜레이션은 한글을 먼저 놓고, 나머지는 전부 라틴 문자를 먼저 놓는다. 두 글자만 비교해 보면 분명해진다. 한국어 콜레이터에서 compare('가', 'a') 는 음수, 영어·일본어·중국어 콜레이터에서는 양수다.
  • 밑줄로 시작하는 _temp 의 자리가 튄다. 코드포인트 순서에서 _ 는 U+005F 라 대문자와 소문자 사이에 끼고, 콜레이션에서는 기호로 취급돼 맨 앞으로 간다. 임시 파일이나 시스템 항목에 밑줄 접두사를 쓰는 관례가 있다면 이 차이가 그대로 화면에 나온다.
  • 여섯 줄 중 다섯 줄에서 10번째 가 1번째 보다 앞이다. 로케일을 아무리 바꿔도 이건 안 고쳐진다. 숫자 비교는 로케일과 별개의 축이기 때문이다.

2. 코드포인트 순서 - 한글은 왜 「대체로」 맞나

코드포인트 정렬은 문자를 숫자로 보고 크기를 견준다. 사람이 쓰는 정렬 규칙과는 아무 상관이 없다. 유니코드 정렬 알고리즘 표준 문서인 UTS #10이 첫머리에 이렇게 못 박는다.

유니코드 코드 차트에서 문자가 놓인 위치는 그 정렬 순서를 규정하지 않는다.

그런데 한글에서는 이 둘이 놀랍도록 잘 맞는다. 얼마나 맞느냐면, 완성형 한글 음절 영역 U+AC00부터 U+D7A3까지 11,172자를 전부 늘어놓고 코드포인트 순서와 한국어 콜레이션 순서를 자리마다 비교하면 어긋나는 곳이 하나도 없다. 두 글자 조합 3,000건 표본에서도 결과가 같다.

우연이 아니다. 한글 음절 코드포인트는 0xAC00 + (초성 × 588) + (중성 × 28) + 종성 이라는 계산식으로 배치돼 있고, 초성·중성·종성의 나열 순서가 사전 순서와 일치한다. 받침 유무도 이 구조를 따른다. 한국어 콜레이터로 확인해 보면 가 < 각, 간 < 갈, 강 < 개 로, 전부 코드포인트 순서와 같은 답이 나온다.

그래서 이런 판단이 가능하다. 입력이 완성형 음절뿐이고 전부 결합형으로 통일돼 있다면, 코드포인트 정렬은 가나다순의 정확한 지름길이다. 속도도 가장 빠르다. 문제는 그 전제를 누가 보장하느냐다.

3. 무너지는 지점 - 다른 것이 섞일 때

전제가 깨지는 경로는 셋이다.

3.1 분해형 한글이 섞일 때

결합형 가 는 U+AC00 한 글자다. 분해형 가 는 U+1100 과 U+1161 두 글자다. 코드포인트로 보면 0x1100 이 0xAC00 보다 한참 작으므로 분해형은 무조건 결합형보다 앞이다. 목록에 분해형이 섞이면 그 항목들이 전부 앞으로 몰려 버린다.

입력: 가방(결합형) 나무(결합형) 다리(결합형)
      각목(분해형) 남산(분해형) 대구(분해형)

코드포인트 정렬  → 각목 | 남산 | 대구 | 가방 | 나무 | 다리
한국어 콜레이터  → 가방 | 각목 | 나무 | 남산 | 다리 | 대구

코드포인트 정렬 쪽은 가나다순과 아무 관계가 없는 결과다. 같은 입력을 SQLite 의 기본 ORDER BY 로 뽑아도, LC_ALL=C sort 로 돌려도 똑같이 분해형이 앞으로 간다. 어느 언어의 문제가 아니라 코드포인트 비교라는 규칙 자체의 성질이다.

분해형이 왜 목록에 들어오는지, 어느 경계에서 형태가 바뀌는지는 NFC·NFD 글에 정리돼 있다. 여기서 붙일 것은 정렬 쪽의 사실 하나다. ICU 콜레이터는 두 형태를 같다고 본다. 결합형 가방 과 분해형 가방 을 비교하면 0 이 나온다. 정렬은 문제없이 된다는 뜻이다. 그런데 같은 두 값을 Set 에 넣으면 크기가 2 다.

정렬은 되는데 중복 제거는 안 되는 구간
콜레이터는 두 형태를 동등하게 취급하지만 === 와 해시 기반 자료구조는 다르게 본다. 「정렬해 보니 나란히 붙어 있으니 중복 제거도 됐겠지」라는 추론이 여기서 조용히 틀린다. 중복 제거는 콜레이터가 아니라 정규화가 한다.

3.2 자모와 기호가 섞일 때

호환용 자모 ㅏ 는 U+314F 로 완성형 음절 영역보다 앞이다. 코드포인트로 정렬하면 가 앞에 놓인다. 그런데 한국어 콜레이터는 이 글자를 목록 맨 뒤로 보낸다. 한글 자모 낱글자를 태그나 색인 키로 쓰는 화면이라면 두 방식의 결과가 정반대가 된다.

이모지도 마찬가지다. 코드포인트로는 값이 커서 맨 뒤로 가지만, 한국어 콜레이터에서는 숫자보다도 앞에 놓인다. 사용자 닉네임처럼 무엇이든 들어올 수 있는 필드에서는 이 차이가 눈에 띄게 나타난다.

3.3 대소문자가 섞일 때

코드포인트 정렬은 대문자를 전부 앞에 모은다. Apple, Banana 다음에 apple, zebra 가 오는 식이라 알파벳순으로 읽히지 않는다. 콜레이션은 같은 철자를 붙여 놓고 대소문자를 마지막 단계에서만 따진다. 자바스크립트에서는 이 단계를 sensitivity 로 고를 수 있다.

설정구분하는 것apple vs Apple
base기본 글자만0 (같음)
accent기본 글자 + 발음 구별 기호0 (같음)
case기본 글자 + 대소문자다름
variant (기본값)전부-1 (apple 이 앞)
caseFirst: 'upper'대문자를 앞으로+1 (Apple 이 앞)

SQLite 의 NOCASE 는 여기에 훨씬 못 미친다. 공식 문서가 ASCII 26글자만 접는다고 명시한다. 실제로 'A' = 'a' COLLATE NOCASE 는 참이지만 'Ä' = 'ä' COLLATE NOCASE 는 거짓이다. 이름 검색을 NOCASE 로 만들어 두고 다국어 데이터를 넣으면 여기서 조용히 새는 곳이 생긴다.

4. 로케일이 바꾸는 것과 못 바꾸는 것

「로케일을 한국어로 맞추면 한국어 순서가 나온다」는 기대는 절반만 맞다. 로케일 이름은 규칙을 가리키는 라벨일 뿐이고, 실제 규칙은 그 이름을 해석하는 라이브러리가 들고 있다. 그래서 같은 이름이 환경에 따라 다른 순서를 낸다.

측정 환경(뒤의 「측정 환경과 재현」 절 참조)에서 확인된 것들이다.

  • LC_ALL=ko_KR.UTF-8 sort 와 LC_ALL=en_US.UTF-8 sort 의 출력이 한 글자도 다르지 않다. 한국어 로케일을 지정했다고 한국어 정렬 규칙이 붙는 것은 아니다.
  • 파이썬 locale.strxfrm 도 ko_KR.UTF-8·en_US.UTF-8·Korean_Korea.949 세 로케일에서 모두 같은 결과를 낸다.
  • 같은 장비의 Intl.Collator('ko') 만 한글을 라틴 문자보다 앞에 놓는다. ICU 는 다른 규칙표를 쓴다.
  • locale.setlocale(locale.LC_COLLATE, '') 는 장비의 시스템 설정을 따라간다. 측정 장비에서는 Korean_Korea.949 로 해석됐다. 개발 노트북과 운영 서버의 시스템 로케일이 다르면 같은 코드가 다른 순서를 낸다.

UTS #10 의 설명이 이 상황을 정확히 짚는다. 기본 정렬표인 DUCET 만으로는 모든 언어를 만족시킬 수 없어 「대부분의 언어에서 사용자 기대에 맞추려면 어느 정도의 조정(tailoring)이 필요하다」고 적는다. ICU 는 그 조정표를 갖고 있고, C 라이브러리 구현은 갖고 있을 수도 없을 수도 있다.

여기에 파이썬 공식 문서가 덧붙이는 경고가 하나 더 있다. 로케일은 프로그램 전역 속성이고 setlocale() 은 대부분의 시스템에서 스레드 안전하지 않다. 웹 서버 안에서 요청마다 로케일을 바꿔 가며 정렬하는 설계는 그래서 쓸 수 없다.

5. 숫자 정렬 - 파일2와 파일10

문자열 비교는 파일2 와 파일10 의 세 번째 글자에서 2 와 1 을 견주고, 1 이 작으므로 파일10 을 앞에 놓는다. 규칙대로 동작한 결과이고, 로케일을 바꿔도 그대로다.

입력: 파일1.txt 파일2.txt 파일10.txt 파일20.txt 파일3.txt 파일100.txt

기본 정렬     → 파일1 · 파일10 · 파일100 · 파일2 · 파일20 · 파일3
숫자 비교 켬  → 파일1 · 파일2 · 파일3 · 파일10 · 파일20 · 파일100

고치는 방법은 도구마다 있다.

  • 자바스크립트: new Intl.Collator('ko', { numeric: true })
  • GNU sort: sort -V (버전 정렬). 위 목록에서 기대한 순서가 그대로 나온다
  • 파이썬: 숫자 덩어리만 int 로 바꾼 리스트를 정렬 키로 쓴다
import re, unicodedata

def natural_key(s):
    s = unicodedata.normalize('NFC', s)
    return [int(t) if t.isdigit() else t
            for t in re.split(r'(\d+)', s)]

sorted(names, key=natural_key)
숫자 비교를 켜면 생기는 함정 - 0 패딩이 동점이 된다
numeric: true 로 A-007 과 A-7 을 비교하면 결과가 0, 즉 동점이다. 숫자로 해석하면 둘 다 7 이기 때문이다. 자리수를 맞춰 저장하던 시절의 데이터와 그렇지 않은 데이터가 한 테이블에 섞여 있으면 여기서 순서가 매번 흔들린다. 자리수를 통일하거나, 뒤에 유일한 보조 정렬 키를 하나 더 붙여야 한다.

6. 도구별로 고정하는 법

6.1 셸 - 로케일을 믿지 말고 못 박아라

스크립트가 만드는 순서가 결과물에 남는다면(체크섬 목록, 매니페스트, 비교용 덤프 등) 로케일을 명시적으로 고정해야 한다. 방향은 둘 중 하나다.

# 1) 재현 가능한 바이트 순서가 목적일 때 - 어느 장비에서도 같은 결과
LC_ALL=C sort names.txt

# 2) 사람이 읽을 순서가 목적일 때 - 셸에서 하지 말고 넘겨라
#    (로케일 이름이 같아도 장비마다 규칙이 다를 수 있다)

판단은 이렇다. 기계가 비교할 목록이면 LC_ALL=C 로 고정하고, 사람이 읽을 목록이면 셸에서 정렬하지 마라. 애매하게 시스템 기본값에 맡긴 상태가 가장 나쁘다. 개발 장비와 CI 컨테이너의 LANG 이 다르면 같은 스크립트가 다른 파일을 만들어 낸다.

6.2 자바스크립트 - 콜레이터를 만들어 재사용하라

// 한 번 만들어 두고 재사용한다
const collator = new Intl.Collator('ko', {
  numeric: true,          // 파일2 < 파일10
  sensitivity: 'variant', // 대소문자·발음 구별 기호까지 구분
  caseFirst: 'false'      // 로케일 기본값
});

names.sort(collator.compare);

기억할 것 세 가지.

  • 콜레이터 인스턴스를 재사용하라. 비교할 때마다 a.localeCompare(b, 'ko') 를 부르면 매번 콜레이터를 새로 조립한다. 2만 건 정렬에서 localeCompare 방식이 콜레이터 재사용보다 두 배 넘게 느리다.
  • usage: 'search' 로 정렬하지 마라. MDN 이 못 박는다. 「정렬·순서 지정에 search 를 쓰는 것은 부적절하다.」 실제로 가 와 까 를 비교하면 sort 와 search 가 부호가 반대인 값을 낸다. search 의 반환값은 0 인지 아닌지만 봐야 한다.
  • 정렬 키를 미리 뽑아 두는 최적화는 쓸 수 없다. 자바스크립트에는 ICU 의 정렬 키 추출에 해당하는 공개 API 가 없다. 파이썬의 strxfrm 같은 방식이 불가능하므로, 성능이 문제라면 콜레이터 재사용이 사실상 유일한 수단이다.

6.3 파이썬 - 표준 라이브러리와 ICU 사이

표준 라이브러리만으로는 locale 모듈이 전부다. strxfrm 은 문자열을 비교용 형태로 바꿔 주고, 같은 문자열을 반복 비교할 때 쓰라고 문서가 안내한다.

import locale
locale.setlocale(locale.LC_COLLATE, 'ko_KR.UTF-8')
result = sorted(names, key=locale.strxfrm)

다만 앞에서 본 대로 이 방식은 장비의 C 라이브러리에 결과를 맡기는 것이고 스레드 안전하지도 않다. ICU 규칙이 필요하면 PyICU 를 붙이는 쪽이 정석이다. 그것도 어렵다면, 실무에서 통하는 절충안은 정규화 + 자연 정렬 키를 직접 만드는 것이다. 로케일에 의존하지 않으므로 어느 장비에서든 같은 결과가 나온다.

import re, unicodedata

def sort_key(s):
    s = unicodedata.normalize('NFC', s)          # 분해형을 결합형으로
    parts = re.split(r'(\d+)', s)
    return [(1, int(t), '') if t.isdigit() else (0, 0, t) for t in parts]

완성형 한글만 다루는 목록이라면 이 키만으로도 가나다순이 정확히 나온다. 2절에서 본 전수 비교 결과가 그 근거다.

7. 데이터베이스 - COLLATE 를 어디에 쓰느냐가 인덱스를 가른다

DB 에서 정렬 순서를 고치는 방법은 두 가지로 보인다. 질의에 COLLATE 를 붙이거나, 열 정의에 넣거나. 결과는 같지만 비용이 전혀 다르다.

SQLite 에 이름 열을 만들고 인덱스를 건 뒤 실행 계획을 뽑아 보면 차이가 그대로 드러난다.

질의실행 계획
ORDER BY nameSCAN t USING COVERING INDEX idx_name
ORDER BY name COLLATE NFCSCAN t
USE TEMP B-TREE FOR ORDER BY
WHERE name = ?SEARCH t USING COVERING INDEX idx_name (name=?)
WHERE name = ? COLLATE NFCSCAN t
열 정의에 COLLATE NFC + 인덱스SCAN t USING COVERING INDEX idx (순서도 정상)

질의에 COLLATE 를 붙이는 순간 정렬용 인덱스도, 검색용 인덱스도 함께 죽는다. 인덱스가 기본 콜레이션 기준으로 만들어져 있으니 다른 규칙을 요구하면 쓸 수가 없다. 임시 B-트리를 만들어 매번 정렬하게 되고, 등호 비교는 전체 스캔으로 떨어진다.

고치는 자리는 질의가 아니라 스키마다.

-- SQLite: 열에 콜레이션을 박고 그 위에 인덱스를 만든다
CREATE TABLE members (name TEXT COLLATE NOCASE);
CREATE INDEX idx_members_name ON members(name);

-- PostgreSQL: ICU 프로바이더로 콜레이션을 만들어 열에 붙인다
CREATE COLLATION ko_icu (provider = icu, locale = 'ko-KR');
CREATE TABLE members (name text COLLATE ko_icu);

-- MySQL 8.x: utf8mb4 계열 콜레이션을 열에 지정한다
CREATE TABLE members (
  name VARCHAR(100) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_as_cs
);

제품별로 알아 둬야 할 것들이다.

  • SQLite: 내장 콜레이션은 BINARY·NOCASE·RTRIM 셋뿐이다. 기본값 BINARY 는 memcmp() 비교, 즉 코드포인트 순서다. 한국어 규칙이 필요하면 애플리케이션에서 콜레이션을 등록해야 한다.
  • PostgreSQL: libc 와 ICU 두 프로바이더가 있고, ICU 콜레이션은 인코딩과 무관하게 이름 하나로 존재한다. 순서를 안정적으로 고정하려면 ICU 쪽이 낫다.
  • MySQL 8.x: 유니코드 콜레이션 목록에 한국어 전용 콜레이션이 없다. 일본어·중국어·러시아어·독일어 등은 있는데 한국어는 목록에 올라 있지 않다. 기본값인 utf8mb4_0900_ai_ci 는 UCA 9.0.0 / CLDR v30 기반이며 발음 구별 기호와 대소문자를 구분하지 않는다. 이름 순서를 엄격히 다뤄야 하면 _as_cs 계열을 쓴다.
콜레이션이 바뀌면 인덱스가 깨질 수 있다
PostgreSQL 문서는 이렇게 적는다. 「콜레이션 정의가 바뀌면 인덱스가 손상되거나 다른 문제가 생길 수 있다. 데이터베이스 시스템이 저장된 객체가 특정 정렬 순서를 갖는다는 것에 의존하기 때문이다.」 그리고 이런 일이 운영체제를 새 주요 버전으로 올릴 때나 새 ICU 에 링크된 바이너리로 옮길 때 실제로 생긴다고 덧붙인다. 대응은 영향받은 객체를 REINDEX 로 다시 만들고 ALTER COLLATION ... REFRESH VERSION 을 실행하는 것인데, 문서 스스로 이 명령이 실제로 다시 만들어졌는지 검사하지는 않는다고 밝힌다.

8. 동점 - 정렬이 끝나도 순서가 안 정해지는 경우

콜레이션은 두 값을 「같다」고 판정할 수 있다. 그 순간 그 항목들의 최종 순서는 정렬 알고리즘에 넘어간다. 자바스크립트의 Array.prototype.sort 는 안정 정렬이므로 입력 순서가 그대로 보존된다. 좋은 성질처럼 들리지만, 뒤집으면 이런 뜻이다.

구두점 무시 옵션을 켠 상태 (compare('한-국', '한국') === 0)

입력 [한-국, 한국, 한.국]  →  출력 한-국 | 한국 | 한.국
입력 [한.국, 한국, 한-국]  →  출력 한.국 | 한국 | 한-국

같은 데이터인데 들어온 순서가 다르면 화면 순서가 다르다. 이 문제는 콜레이션 하나로 끝나지 않는다. 동점이 생기는 경로가 여럿이다.

  • sensitivity: 'base' 나 'accent' 로 두면 대소문자만 다른 값들이 동점이 된다
  • ignorePunctuation: true 로 두면 하이픈·마침표만 다른 값들이 동점이 된다
  • numeric: true 로 두면 0 패딩만 다른 값들이 동점이 된다
  • DB 에서 ORDER BY name 만 걸면 동명이인이 동점이 된다

해법은 하나다. 정렬 키에 유일한 값을 하나 덧붙여라. DB 라면 ORDER BY name, id, 애플리케이션이라면 비교 함수가 0 을 반환할 때 ID 로 한 번 더 견주는 것이다.

이 동점 문제가 목록을 페이지로 나눌 때 무엇을 망가뜨리는지는 오프셋 페이징이 구조적으로 못 하는 것에서 따로 다뤘다. 정렬 키가 유일하지 않으면 페이지 경계에서 항목이 사라지거나 두 번 나온다.

9. 성능 - 무엇이 얼마나 느린가

한글 문자열 2만 건을 정렬한 시간이다. 다섯 번 돌린 중앙값.

방식시간기본 대비
기본 sort() (코드포인트)10.1 ms1.0배
Intl.Collator 인스턴스 재사용27.0 ms2.7배
a.localeCompare(b, 'ko') 매번 호출59.5 ms5.9배

읽는 법은 이렇다.

  • 콜레이션의 값은 2.7배다. 2만 건에 27밀리초면 대부분의 화면에서 논쟁거리가 아니다. 「느려질까 봐 코드포인트로 둔다」는 판단은 이 규모에서는 근거가 약하다.
  • localeCompare 를 비교 함수 안에서 직접 부르는 것이 실질적인 손해다. 콜레이터를 밖에서 한 번 만드는 한 줄로 절반이 줄어든다. 결과는 완전히 같다.
  • 수십만 건 이상을 매 요청마다 정렬하고 있다면 그건 정렬 방식이 아니라 정렬 위치의 문제다. DB 인덱스로 내리는 것이 맞다.

10. 판단 - 콜레이션은 애플리케이션 계층에 둔다

여기까지의 사실들을 하나의 기준으로 모으면 이렇게 된다.

상황어디에 고정하나이유
사용자에게 보이는 목록애플리케이션 계층의 명시적 콜레이터
(Intl.Collator·ICU)		환경에 무관하게 같은 순서. 옵션이 코드에 남아 리뷰가 된다
대량 목록의 페이지 조회DB 열 콜레이션 + 인덱스질의 COLLATE 는 인덱스를 죽인다. 정렬 키에 유일 값 병행
스크립트·CI 산출물LC_ALL=C 명시재현 가능성이 목적. 사람이 읽는 순서가 아니다

파일명·경로정규화 후 비교분해형이 섞이면 코드포인트 정렬이 무너진다

「애플리케이션 계층에 두라」는 권고의 근거는 취향이 아니라 아래 네 가지다.

  1. 같은 로케일 이름이 같은 순서를 보장하지 않는다. 한 장비에서 ko_KR.UTF-8 과 en_US.UTF-8 의 셸 정렬 결과가 같았고, 같은 장비의 ICU 한국어 콜레이터는 전혀 다른 순서를 냈다. 환경 변수는 순서를 고정하는 수단이 못 된다.
  2. 로케일은 프로세스 전역이고 스레드 안전하지 않다. 요청마다 다른 규칙이 필요한 서버에서 구조적으로 쓸 수 없다.
  3. DB 콜레이션은 인프라 변경에 끌려간다. 운영체제나 ICU 버전이 올라가면 인덱스를 다시 만들어야 할 수 있다고 PostgreSQL 문서가 경고한다. 순서 규칙이 인프라 일정에 묶이는 셈이다.
  4. 옵션이 코드에 남는다. numeric·sensitivity·caseFirst 를 어떻게 두었는지가 소스에 보인다. 서버 환경 변수에 흩어져 있으면 화면 순서가 왜 그런지 아무도 설명하지 못한다.

DB 정렬을 쓰지 말라는 말은 아니다. 수만 건을 페이지로 끊어 보여 주는 화면이라면 정렬은 인덱스가 해야 한다. 그때도 열 정의에 콜레이션을 박고 인덱스를 그 위에 만들라. 질의에 COLLATE 를 붙이는 방식은 결과만 맞고 비용은 전부 치르는 선택이다.

11. 측정 환경과 재현

이 글의 출력은 아래 환경에서 나온 값이다. 콜레이션 데이터는 ICU·CLDR 버전에 따라 달라질 수 있으므로 버전을 함께 적는다.

  • Node.js v22.16.0 (ICU 77.1 · Unicode 16.0 · CLDR 47.0)
  • GNU coreutils sort 8.32 — Windows 의 Git Bash(MSYS2) 환경
  • CPython 3.13.3 (win32) · SQLite 3.49.1

직접 확인하려면 아래 세 줄이면 충분하다. 첫 줄이 코드포인트 순서, 둘째 줄이 한국어 콜레이션 순서, 셋째 줄이 두 순서가 완성형 음절 전체에서 일치하는지다.

node -e "const a=['홍길동','apple','가나다','Banana','2번째','10번째','zebra','나무','_temp','Apple','하늘','1번째']; console.log([...a].sort().join(' '))"

node -e "const a=['홍길동','apple','가나다','Banana','2번째','10번째','zebra','나무','_temp','Apple','하늘','1번째']; console.log([...a].sort(new Intl.Collator('ko').compare).join(' '))"

셸에서 한글이 깨진다면 .js 파일로 저장해 node 파일명.js 로 실행하는 편이 확실하다. 명령줄에 한글을 직접 넣으면 셸의 인코딩 처리에 좌우된다.

12. 확인하지 못한 것

아래 항목은 이 글에서 측정하지 않았다. 공식 문서를 근거로 쓴 부분은 그렇게 표시했다.

  • 리눅스 glibc 환경의 sort 로케일 동작. 위 셸 측정은 Windows 의 MSYS2 런타임에서 나온 값이다. glibc 는 다른 콜레이션 테이블을 쓸 수 있으므로 같은 결과를 기대해서는 안 된다. 서버에서 셸 정렬 결과가 산출물에 들어간다면 그 서버에서 직접 확인해야 한다.
  • PyICU 의 실제 출력. 측정 환경에 설치돼 있지 않다. 파이썬 표준 라이브러리의 locale 모듈 동작만 측정했다.
  • PostgreSQL·MySQL 서버의 실제 정렬 결과. 이 글의 DB 실측은 SQLite 로 한 것이고, PostgreSQL 과 MySQL 관련 서술은 각 공식 문서를 근거로 했다. 인덱스와 콜레이션의 관계는 제품마다 세부가 다르므로 도입 전에 대상 버전에서 실행 계획을 직접 확인하라.
  • macOS 파일 시스템이 이름을 저장하는 형태의 세부. 이 글은 분해형이 목록에 섞였을 때 정렬이 어떻게 되는지만 다뤘고, 어떤 파일 시스템이 언제 어떤 형태로 저장하는지는 NFC·NFD 글의 범위다.
  • ICU 버전이 올라갈 때 순서가 얼마나 바뀌는지. 한 버전(ICU 77.1)에서만 측정했다. 콜레이션 데이터가 버전마다 개정되므로 순서가 계약의 일부라면 ICU 버전을 고정하고 회귀 시험을 두는 편이 안전하다.

13. 자주 묻는 질문

완성형 한글만 쓴다면 그냥 기본 정렬을 써도 되나?

된다. 11,172자 전수 비교에서 코드포인트 순서와 한국어 콜레이션 순서가 완전히 일치한다. 다만 「완성형 한글만」이라는 전제를 지켜 주는 코드가 어딘가 있어야 한다. 사용자 입력·업로드 파일명·외부 API 응답이 섞이는 목록이라면 그 전제는 곧 깨진다.

브라우저마다 Intl.Collator 결과가 다르지 않나?

내장된 ICU·CLDR 버전이 다르면 세부가 다를 수 있다. 그래서 순서가 서버와 클라이언트 양쪽에서 같아야 하는 화면이라면 정렬을 한쪽에서만 해야 한다. 서버가 정렬해 내려주고 클라이언트는 그대로 그리는 쪽이 흔들림이 적다.

한국어인데 왜 한글이 뒤로 가나?

콜레이터의 로케일이 ko 가 아니기 때문일 가능성이 크다. ICU 한국어 콜레이션만 한글을 라틴 문자 앞에 놓는다. 영어·일본어·중국어 로케일에서는 전부 라틴 문자가 먼저다. 브라우저 언어 설정을 그대로 쓰고 있다면 사용자마다 순서가 달라진다.

ORDER BY 결과와 화면 순서가 다른데 어느 쪽을 고쳐야 하나?

둘을 맞추려 하지 말고 정렬하는 곳을 하나로 줄여라. DB 가 정렬해 내려준 배열을 프런트엔드가 한 번 더 정렬하고 있는 구조라면, 두 규칙이 다른 이상 결과는 계속 어긋난다. 페이지 조회가 필요하면 DB 쪽으로 통일하고 열 콜레이션을 맞추는 편이 낫다.

정규화는 언제 해야 하나?

저장 직전에 한 번이 가장 싸다. 읽을 때마다 정규화하면 인덱스를 못 쓰고, 비교할 때만 정규화하면 저장된 값에 두 형태가 계속 쌓인다. 이미 섞여 저장된 데이터가 있다면 마이그레이션으로 한 번 정리하고, 그 뒤로는 입력 경로에서 막는다.
