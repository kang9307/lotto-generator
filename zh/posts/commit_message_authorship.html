提交信息仍然由人来写

提交信息在什么时候、被谁读到，差异里留不下的信息是什么，以及自动生成可以走到哪一步

2026年8月20日 开发/基础设施

引言：编辑器打开后的三秒

改动已经完成。敲下 git commit，编辑器打开，光标在第一行闪烁。如今这三秒可以由工具替你填满。它读取暂存的改动，给出一行建议，而这行建议通常并没有错。文件名对得上，动词也说得通。可还是有人会把这行建议删掉，从头开始写。

这看上去像固执，或者只是个人偏好。其实都不是。提交信息不是改动内容的摘要，而是把改动内容里留不下的信息抓住的地方，这两件事性质完全不同。摘要这件事机器做得更快也更一致。而没有被记录下来的信息，任何模型都造不出来，因为那等于要还原一个并不存在的东西。

这篇文章并不反对自动生成。它更像是在划一条线：哪些提交可以交给机器，哪些提交需要人介入。下面依次看提交信息在什么时候被谁读到，公开的惯例在哪些地方已经达成一致，以及把它变成团队规则时通常会在哪里失败。

1. 原文的主张 - 亲手写的六个理由

这个话题重新被讨论，起因是 2026 年 8 月 17 日发布的一篇个人博客文章，标题是「Why I still hand-write my commit messages」。它被 GeekNews 转载，引来了一场不短的讨论。作者给出的理由大致可以归为六条。

  • 为了留下为什么 - 改了什么在改动内容里已经完整存在，重要的是做出这个选择的理由和背景
  • 为了自我检验 - 写这段文字的过程会暴露你是否真的理解了这次改动
  • 为了保持归属 - 即使代码是借助工具产生的，成果的责任仍然属于提交它的人
  • 为了标出工具用在哪里 - 把提交拆小之后，工具介入的范围会直接体现在历史里
  • 为了保住自己的文字质感 - 作者明确表示不希望工具模仿自己的写法。原文的说法是 I do not actually want an AI to be able to write like I do
  • 作为记录习惯的延伸 - 就像写博客一样，提交也被当作个人记录的一部分

讨论中的反对意见同样清晰。第一，需要的时候让模型从改动内容重新推断理由即可，没必要提前写。第二，要求整个团队都这样写在现实中做不到。第三，设计上的取舍应该写在代码注释里而不是提交里。这三点都有依据，后面会逐条处理。

2. 提交信息在什么时候、被谁读到

提交信息的价值不在写下来的那一刻确定，而在几个月后有人走到那一行时确定。而那个人通常不是作者，通常还很着急。Linux 内核文档精确地点出了这个处境：说明正文会进入永久变更记录，因此必须让一个早已忘记当时细节的合格读者也能看懂。读者是未来的陌生人，而这个陌生人里也包括半年后的你自己。

具体来说，提交信息会在这些场合被打开。

场合读的人要找的东西怎么到达
代码评审评审者这次改动的意图和范围合并请求里的提交列表
凌晨排查故障值班工程师这一行为什么是这样git blame
追查消失的代码缺陷负责人这段处理是什么时候没的git log -S
缩小回归区间缺陷负责人从哪个提交开始坏的git bisect
着手重构下一任维护者这块能不能动先 blame 再看正文
写发布说明产品或发布负责人这次要发出去什么标签区间的 git log
加入团队第一周新成员这个结构为什么长这样git log -L

值得注意的不是工具，而是工具停下来的那个位置。二分查找会精确指出引入问题的那一个提交，工具的职责到此为止。如果那个提交的标题只有 fix: 修正逻辑 一行，负责人就得从头再读一遍代码。相反，如果正文里写着当天的判断和约束，这一来一回就消失了。这些历史命令本身怎么用，我们在Git 历史命令实用指南里单独讲过。这里想说的是这些命令抵达的终点是什么质量。

还有一点容易被忽略。上面这些场合，只要仓库在，任何地方都成立。就算问题跟踪系统没有响应，就算内部维基迁移之后链接失效，只要有一台克隆过仓库的笔记本，提交信息照样读得到。这就是把背景放在和代码同一个地方的实际好处。

3. 差异说了什么、又永远不会说什么

这篇文章的核心在这里。改动内容对于改了什么是一份完整而精确的记录。人把它改写成散文，反而会有损失：明明动了五个文件，正文里只写了三个。所以「把改了什么再说一遍」本来就不是提交信息的任务。

能从改动内容读出来的只会留在提交信息里的
哪个文件的哪一行变了为什么现在做这次改动
新增和删除的函数与签名考虑过哪个方案又放弃了
依赖版本怎么变的为什么停在那个版本
测试有没有一起进来在什么条件下复现的
配置值改成了什么定这个值的依据数字是什么
代码最终是什么样子哪些相邻代码是故意不动的

右边这一列有一个共同点：它们都来自仓库之外。故障报告里的复现条件、从客户咨询中确认的使用方式、供应商回复的限制、跑基准测试得到的数字、会议上定下的优先级。代码里哪里都没有这些。提交信息几乎是仓库内部唯一能把外部背景固定下来的位置。

第三个反对意见在这里出现：这类取舍难道不该写在代码注释里吗。有一半是对的，分界线也很简单。如果这是别人每次读这段代码都需要知道的约束，那就是注释。某个常量必须固定为这个值的理由、这个顺序不能调换的理由，都应该贴在代码旁边。如果这条信息只有在回溯这次改动时才需要，那就是提交。这次放弃了什么、为什么缩小范围，放在代码旁边就会在下一次重构时一起被删掉。而提交不会被删掉。

4. 没做的和放弃的 - 不记录就会被重新尝试

还有一类东西是改动内容在结构上装不下的：你没有做的事。不存在的代码，任何工具都读不出来。而在实际工作中，最值钱的信息常常正在这里。

  • 被放弃的方案 - 先试了库 A，为什么换成了 B
  • 故意没动的相邻代码 - 本来想一起改，但超出了这次发布的范围
  • 这是临时处理这件事 - 以及要等什么解决之后才能把它拿掉
  • 数字的测量条件 - 在多大的数据量、什么硬件上跑出来的
  • 外部依据在哪里 - 参考的缺陷编号、供应商回复、规范文档的章节号

缺了这些会发生什么，是可以预测的。半年后另一个人站在同样的位置，试同样的方案，踩同样的坑，得到同样的结论。那段时间整个是浪费，而浪费的起因只是当初少写了两句话。临时处理如果没写解除条件，临时处理就会变成永久代码。这里也正是自动生成的上限。模型看着最终状态做摘要，而被放弃的东西不在最终状态里。

5. 自动生成真正擅长的部分

话虽如此，这并不意味着每个提交都要有人守着。打开任何一个仓库，相当一部分提交的理由都是显而易见的：错别字修正、格式化、依赖的例行更新、生成代码的重新生成、文件批量移动。对这类提交要求写「为什么」，只会量产出 fix: 修正错别字 - 因为有错别字 这样的句子。这是规则制造噪音的典型形态。

  • 机械式摘要 - 把几十个文件以同样方式改动的提交准确压缩成一行
  • 统一格式 - 每次都把标题长度、语气、前缀对齐到团队约定
  • 降低语言门槛 - 让母语不是英语的团队也能轻松写出读得通的标题
  • 兜住遗漏 - 不会漏掉人经常忘记提的第五个文件
  • 提供草稿 - 把空白的屏幕换成一份可以修改的文字

实际用起来，最后一条最有价值。人之所以把提交信息写得敷衍，多数时候不是因为懒，而是因为空白的屏幕让人下不去手。如果先有一份摘要草稿，人只在下面补上理由，手写的部分就缩到两三句。所以落到实处的规则不该是全部手写，而应该是只在理由不显而易见的提交上由人介入。

6. 自动生成填不上的位置

正面看第一个反对意见，也就是需要的时候让模型从改动内容重新推断理由。这个立场的问题在于它把推断和还原当成了同一件事。模型看着代码给出一个说得通的理由，而那并不是当天真实存在的理由。多数情况下两者接近，所以问题一直藏着。麻烦出在两者分叉的少数情况上。

而那少数情况，恰恰就是人去翻提交信息的时刻。光看代码就能明白的改动，本来就没人会去翻历史。凌晨打开 blame，说明代码已经没能解释自己了。在那个时刻，一个说得通的错误答案比什么都没有更糟，因为它会带着确定的语气把排查推向错误的方向。

  • 被放弃的方案 - 最终代码里没有痕迹，连推断的材料都不存在
  • 外部事实 - 供应商的回复、故障工单的内容，仓库里哪儿都没有
  • 优先级判断 - 为什么是现在、为什么只做到这一步，这是组织层面的事情
  • 测量条件 - 数字留在了代码里，测它的环境没有留下
  • 确信的程度 - 这是一次确定的修复还是一次有依据的猜测，只有作者知道

最后一条在实际工作中特别值钱。一句「根因未能确认，只挡住了症状」，能把下一个人的排查时间按天缩短。而这句话工具做不出来，因为它无从知道作者当时有多确定。

还有一个附带效果。如果一句话怎么都写不明白，那这个提交通常太大了，或者混了好几个目的。这时需要的不是更长的句子，而是把提交拆开。Git 官方文档也建议不要把多个问题的改动塞进一个提交，而是用部分暂存（git add --patch）分开。写信息这件事，实际上成了检查提交形状的一道关口。

7. 好提交信息的结构 - 标题、正文、尾注与回退

在形式方面，公开的惯例其实早已在很大程度上达成一致，只是具体数字各项目不同。这个不同意味着什么，比数字本身更重要。

要素惯例依据文档
标题长度建议一行摘要不超过 50 个字符Git git-commit 文档
标题长度（内核）70 到 75 个字符，同时说明改了什么和为什么Linux 内核提交补丁文档
标题与正文第一个空行之前的文字被当作标题Git git-commit 文档
正文宽度大约 72 个字符换行Pro Git 贡献指南
语气祈使句现在时（Fix bug 而不是 Fixed bug）Pro Git 与内核文档一致
缺陷引用Fixes: 后面接 SHA 前 12 位以上和一行摘要Linux 内核提交补丁文档
签署与共同作者正文后空一行，再写 Signed-off-by 或 Co-authored-by内核文档与 GitHub 文档
回退在自动生成的那句之后自己补上回退的理由Git git-revert 文档

标题长度上 50 和 70 到 75 的分歧，不值得争论谁对谁错。两份文档真正要求的是同一件事：这一行单独出现在列表里时要能传达要点。内核允许更长也有明确的原因，因为它要求摘要一行里同时装下改了什么和为什么改。

祈使句看起来像口味问题，其实有功能上的理由。Git 自动生成的信息，比如合并和回退提交，全都是祈使句，语气统一之后整段历史读起来像同一份文档。Pro Git 把这一点说得很直白：写 Fix bug，不要写 Fixed bug。

回退提交是最容易马虎的地方。git revert 会自动在正文里记下回退了哪个提交，从终端执行时默认还会打开编辑器。但那句自动生成的文字只说了什么。Git 文档明确写着，强烈建议说明为什么要回退原来的提交。同一页甚至警告说，反复回退回退会让标题越来越臃肿，出现 Reapply "Reapply "..."" 这种形态。少了这一行理由，几个月后想把这个功能重新加回来的人根本不知道它当初为什么被拿掉。

顺带说一下规范。Conventional Commits 规定用 type[scope]: description 的形式书写，破坏性变更用 ! 或专门的脚注标出，其目的是自动生成变更日志和自动判定语义化版本。也就是说，规范的成本要靠自动化流水线真正去读这些提交才能收回。这是另一条线上的讨论，我们在对 Conventional Commits 的批判里单独写过。这里只强调一点重叠之处：前缀写得再准确，也完全不代表正文里有理由。

8. 提交 AI 写的代码时 - 标注与责任

这是原文作者着力最重的部分。借助工具产生的代码，归属和责任仍然在提交它的人身上；而把提交拆小，工具介入的边界就会直接体现在历史里。

标注的手段其实早就有了，就是提交信息的尾注。GitHub 文档说明，在描述之后空一行，然后按共同作者的数量各加一行 Co-authored-by: name <name@example.com>。在 Git 这边，git commit --trailer 可以附加同样形式的字段。因为格式固定，日后也可以机械地统计。

  • 把提交拆小 - 不要把工具生成的范围和自己写的范围混在同一个提交里
  • 写上工具名称 - 几个月后需要回溯某个工具特有的习惯时，这是唯一的线索
  • 写下验证方式 - 用什么确认过，比标注本身更重要
  • 不要把标注当免责 - 加了尾注，评审和责任仍然留在人身上
  • 先把格式定下来 - 每个人标注得不一样，就既统计不了也搜索不到

这个标注在两种场合真正产生价值。一是质量复盘：如果某段时期用某个工具产出的代码反复出现同一类缺陷，只有存在标注时这个规律才看得见。二是评审分配，越来越多的团队会根据生成比例调整评审强度。把评审本身变成流程的做法，我们在代码评审不会自己变好里讲过。

9. 变成团队规则时 - 钩子、模板与评审要点

第二个反对意见，也就是没法强推给团队，大体上是对的。但很多团队失败是因为强推错了对象。一上来就检查格式，结果格式合规而内容空洞的信息越来越多。fix: 修复缺陷 能通过任何一个规范检查器，信息量却是零。

把顺序反过来更好。先让它容易写，机器只拦能确定判断的东西。

  • 提交模板 - 用 commit.template 设置或 -t 指定编辑器的初始内容。里面放问题比放字段名更有效，比如「为什么现在需要」「考虑过什么又放弃了」
  • 在编辑器里显示差异 - git commit -v 会把改动内容附在信息下方，指定两次连未暂存的改动也一并显示。按文档的说法，它是通过提醒你这次提交包含什么来帮助你描述它
  • prepare-commit-msg 钩子 - 在默认信息准备好之后、编辑器打开之前执行。它的目的是就地修改信息文件，因此 --no-verify 也不会跳过它。适合从分支名自动填入问题编号
  • commit-msg 钩子 - 以写好的信息文件作为唯一参数，可以检查它，也可以把它规整成统一格式。返回非零退出码会中止提交，并且可以用 --no-verify 绕过
  • 评审要点 - 看内容而不是看形式，下面五条就够了

评审时看提交信息，真正该问的是这些。

  • 只读标题能不能猜到这次改了什么
  • 正文说的是为什么，还是把改了什么又说了一遍
  • 如果放弃过方案或者留下了范围，有没有写出来
  • 如果是临时处理，有没有写解除条件
  • 有没有关联到问题或工单

只有最后一条适合交给钩子，因为机器能确定地判断它。让钩子去判断正文里有没有真正的理由，误报就会堆积；误报一堆积，团队就会习惯性地加上 --no-verify。到那一刻，钩子等于不存在了。

10. 语言的选择 - 母语还是英语

非英语地区的团队总会碰到这个问题，中文和韩语团队都是典型。判断标准不是口味，而是会读这个仓库的人的范围。

  • 纯内部、成员母语一致 - 正文用母语写，每句话承载的信息更多。与其在翻译中丢掉分寸，不如把话说准
  • 有开源的可能 - 一开始就用英语，因为事后翻译整段历史实际上做不到
  • 预计有外籍成员或外包交接 - 用英语。历史比人留得久
  • 折中做法 - 标题用英语祈使句，正文用母语。既保住发布说明的自动化和工具兼容，又拿到表达的精度
  • 无论选哪种，一致性优先 - 一旦混用，git log --grep 只能捞到一半，因为它是字符串搜索，你得两种语言都试一遍

用折中做法时有一点要注意。问题跟踪系统识别的关键词以及尾注的名称，无论正文用什么语言，都必须保持规定的英文形式。把 Co-authored-by 翻译成母语，工具就不认了。人读的句子用什么语言都行，机器读的那几行按规范原样写着才安全。

顺便一提，最近也出现了把自然语言写的规格说明直接提交进仓库的做法。在那种结构里提交信息的角色反而更重，因为需要一个地方记录规格为什么变了。这条线我们在提交韩语规格说明书而非代码里另外整理过。

没能确认的部分

  • 把自动生成的提交信息与人写的做过质量对比的公开基准或学术研究，这次没有找到。本文的比较依据的是信息本身的性质，也就是最终状态里不存在的信息无法从中还原
  • 关于开发组织用哪种语言写提交信息的统计数据没有找到。上面的语言选择标准是判断框架，不是统计结论
  • 提交正文的有无对故障恢复时间有多大影响，没有找到测量数据
  • 原文作者的团队规模和所用工具组合，原文里没有写

结语：信息比代码活得更久

代码会消失。今天写的函数会在下一次重构里改名，再下一次改版里整段不见。可是记录了它为什么被写成那样的提交会留下来。换仓库它还在，维基被废弃它还在，换掉问题跟踪系统它也还在。这就是提交信息是一个项目里活得最久的文档的原因。

所以结论不是用不用自动生成，而是草稿交给工具，人只补上工具不可能知道的部分。落到动作上是三件事。第一，标题写成能在列表里一行读懂的样子，直接沿用工具给的摘要也没关系。第二，凡是理由不显而易见的提交，都要补两三句正文，把放弃的方案和留下的范围写进去。第三，回退的提交要写清楚为什么回退。仅这三条，就会改变半年后凌晨打开 blame 的那个人所看到的画面。

编辑器打开后的那三秒，说到底是在问自己一个问题：我能解释这次改动吗。如果答不上来，问题不在句子，而在这个提交本身。

常见问题

Q1: 可以让 AI 生成提交信息吗

A: 理由显而易见的提交，自动生成完全够用。依赖升级、自动格式化、错别字修正就属于改动本身即说明的类型。相反，放弃过方案、加了临时处理、依据性能实测做判断的提交需要人来写正文。这些信息不在代码的最终状态里，仅凭改动内容无法还原。

Q2: 提交信息的标题应该写多少个字符

A: Git 官方文档建议一行摘要不超过 50 个字符，随后空一行再写详细说明。Linux 内核文档要求 70 到 75 个字符，并且同时写清改了什么和为什么。数字不一致这件事本身就是要点。并不存在绝对标准，真正的要求是这一行单独出现在列表里时能传达要点。

Q3: 设计上的理由该写在提交信息里还是代码注释里

A: 别人每次读这段代码都需要知道的约束就写成注释，某个常量必须固定为这个值的理由就是这一类。只有回溯这次改动时才需要的信息就写进提交，被放弃的方案、缩小范围的理由、临时处理的解除条件都属于后者。注释可能在下一次重构中被删掉，提交不会。

Q4: 提交 AI 写的代码时需要标注吗

A: 标注用尾注就能解决。在正文后空一行加上 Co-authored-by 那一行，或者用 git commit --trailer 附加。但标注不是转移责任的机制，它只是让人日后能回溯工具用在哪里的记录，验证和责任仍然在提交者身上。要标注就把提交拆小，让范围本身说明问题。

Q5: 怎样把提交信息规则引入团队

A: 从格式检查开始通常会失败，因为格式合规而内容空洞的信息会变多。更有效的是在提交模板里放入问题，并把在提交编辑器中一并显示改动内容的选项设为默认。钩子只拦机器能确定判断的项目，比如缺少问题编号，正文的质量交给代码评审。
