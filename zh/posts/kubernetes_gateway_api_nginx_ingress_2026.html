迁移到 Kubernetes Gateway API - NGINX Ingress Controller 退役之后 2026

告别注解的时代，用标准资源治理流量

2026-06-09 IT/技术

引言：撼动半数集群的事件

2025 年 11 月，Kubernetes 项目发布了一则沉重的公告。约半数云原生环境所依赖的核心基础设施——ingress-nginx(NGINX Ingress Controller)将于 2026 年 3 月退役(retirement)。SIG Network 与安全响应委员会曾努力寻找额外的人力与支持以使该项目可持续，但最终未果，为优先保障用户安全而决定关停项目。根据官方公告，2026 年 3 月之后不再有新版本、缺陷修复，也不再修补安全漏洞。

这不是又一个库的普通 EOL(End-of-Life)。ingress-nginx 在太多地方充当着互联网与集群内部之间的关口，它的退役向无数运维团队同时抛出一个问题：该迁移到什么？ 而 Kubernetes 项目给出的推荐路径中心，正是 Gateway API。本文以 ingress-nginx 退役为起点，梳理 Ingress 为何走到极限、Gateway API 如何以标准方式解决，以及在实践中如何迁移。

注意：退役的是开源社区项目 kubernetes/ingress-nginx。F5(原 NGINX Inc.)的商用 NGINX Ingress Controller 是完全独立的代码库，按自己的生命周期持续维护。混淆二者容易做出错误决策。

1. Ingress 曾是什么——以及为何撞墙

先打牢基础。Ingress 是 Kubernetes 中把集群外部 HTTP/HTTPS 流量路由到内部服务的标准资源。它基于主机名和路径定义流量去往哪个服务，是一种 L7 路由规则。概念本身很简单。

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop-ingress
spec:
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 80

问题在于，这个简单的规范跟不上现实需求。实践中需要超时、重写(rewrite)、头部操作、金丝雀分流、mTLS、限流等功能，而 Ingress 标准规范里没有表达它们的位置。于是各控制器用 注解(annotation) 来弥补缺失的表达力。

metadata:
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$1
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "20"

Ingress 的三大顽疾就此显现。

  • 注解泛滥：核心路由行为藏在控制器专属的注解字符串里，而非标准规范。难以校验，一个拼写错误就能悄悄破坏行为。
  • 厂商锁定：nginx.ingress.kubernetes.io/... 注解只属于 ingress-nginx。换成 Traefik 或 HAProxy 就得重写所有注解，「标准」之名形同虚设。
  • 缺乏角色分离：主机、路径、TLS、重写挤在同一资源里，平台团队和应用团队不得不操作同一个对象。在多租户环境中难以划定权限边界。

ingress-nginx 安全负担加重的背后也是这套结构。把注解传入的配置字符串在内部转换为 NGINX 配置，本质上攻击面很广、维护难度也高。用迂回弥补标准无法表达之处，复杂度便不断累积。

2. Gateway API 是什么——作为标准重新设计的流量关口

为正面解决这些局限，SIG Network 设计了 Gateway API。它是 Ingress 的继任者，但不是简单的版本升级，而是从零重新建模流量路由的标准。核心思想有二：其一，把实践中需要的功能(头部、重写、流量分流、跨命名空间路由)用 标准字段而非注解 表达；其二，把一个庞大的资源 按角色拆分成多个资源。

最重要的事实是，Gateway API 的核心资源已在 v1.0 达到 GA(正式可用，Generally Available)。据官方文档，GatewayClass、Gateway、HTTPRoute 已晋级 v1，是保证向后兼容的稳定 API。这不是实验特性，而是可用于生产的标准。

2.1 三个核心资源

资源 定义什么 类比
GatewayClass 由哪个控制器(实现)处理流量。集群范围的模板。 类似 StorageClass
Gateway 实际的流量入口实例。定义监听器、端口、协议、TLS。 负载均衡器本身
HTTPRoute 从 Gateway 监听器到后端的 HTTP 路由规则。 基于路径与头部的路由表

关系很直观。每个 Gateway 绑定一个 GatewayClass，确定「谁来处理这股流量」；而 HTTPRoute 之类的路由资源附着到 Gateway 上，确定「如何路由」。除 HTTP 外还有 TCPRoute、TLSRoute、GRPCRoute 等兄弟资源，可以用同一套写法表达各协议的标准路由。

2.2 用 Gateway API 表达同一件事

# 1) 集群运维者：定义流量入口
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shop-gateway
spec:
  gatewayClassName: envoy        # 由哪个实现处理
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    tls:
      mode: Terminate
      certificateRefs:
      - name: shop-tls
---
# 2) 应用开发者：定义路由规则(无需注解，用标准字段)
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: api-route
spec:
  parentRefs:
  - name: shop-gateway
  hostnames:
  - "shop.example.com"
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /api
    filters:
    - type: URLRewrite        # 标准过滤器：无需注解
      urlRewrite:
        path:
          type: ReplacePrefixMatch
          replacePrefixMatch: /
    backendRefs:
    - name: api-svc
      port: 80

看到差别了吗？重写不再是 nginx.ingress.kubernetes.io/rewrite-target 这种厂商专属字符串，而是 filters 中的 标准 URLRewrite 过滤器。这份清单在 Envoy Gateway、Istio、NGINX Gateway Fabric 上都能同样工作。换实现，路由定义照旧。

3. 角色分离(Role-Oriented)——Gateway API 真正的革新

Gateway API 最深的变化不是增加功能，而是 角色分离。官方设计按参与 Kubernetes 网络的组织的真实角色来拆分资源。

  • 基础设施提供方(Infrastructure Provider)：云厂商或平台提供方部署 GatewayClass。它是集群范围资源，是定义由其派生的 Gateway 行为的模板。
  • 集群运维者(Cluster Operator)：用 GatewayClass 部署 Gateway，定义「流量从何处、以何种方式进入集群」。端口、TLS、监听器是他们的职责。
  • 应用开发者(Application Developer)：用 HTTPRoute 只定义「如何把流量路由到我的服务」，无需了解基础设施细节。

为何重要？在 Ingress 中，TLS 证书配置与应用路由规则混在一个对象里，应用开发者要碰基础设施，或者反过来平台团队要包揽全部路由。在 Gateway API 中，平台团队管理 Gateway(入口与 TLS)，各团队只管理自己的 HTTPRoute。多租户环境下安全的权限边界被刻进了资源模型本身。这一结构与平台工程「自助服务加安全护栏」的理念精确契合。更广的脉络见 平台工程完全指南 2026。

4. 为什么「标准化」很重要

把 Gateway API 的价值压成一个词，就是 可移植性(portability)。当标准本身具备表达力，路由意图就不再被绑定到某一厂商的注解字典。这带来三项实质收益。

  1. 切换成本骤降：只改 GatewayClass 的 controllerName，同一份 HTTPRoute 就能跑在另一个实现上。即便 ingress-nginx 退役这类事件再次发生，站在标准之上，冲击也很小。
  2. 可校验性：路由用强类型(typed)字段表达，因此能在 kubectl 与 CI 中做模式校验，注解拼写错误引发的静默故障随之减少。
  3. 生态聚焦：所有实现都竞相通过同一标准的一致性(conformance)测试，因此功能创新不再分散，而是叠加在标准之上。

简言之，标准化不是「强推某一种实现」，而是 打造一门多种实现可兼容沟通的共同语言。这正是它与 Ingress 注解巴别塔的根本区别。

5. 主要 Gateway API 实现——如何选择

标准只有一个，实现却有多种。以下整理 2026 年的主要实现及其特性。重要前提是：无论选哪个，清单(HTTPRoute 等)大多可复用。

实现 数据面 优势 适合场景
Envoy Gateway Envoy 一致性高、功能迭代快，Envoy 原生 广泛使用 L7 功能的通用之选
Istio Envoy(Ambient) 服务网格集成，毫秒级配置传播 已用网格或以 mTLS、流量策略为核心
Cilium eBPF L4 吞吐最强，规避内核开销 用 Cilium 作 CNI 且看重 L4 性能
NGINX Gateway Fabric NGINX 对 ingress-nginx 用户亲切，Go 控制面 从 NGINX 出发最近的迁移路径
Kong Kong/NGINX API 网关能力，配置传播快 需要 API 管理与插件生态

近期业界分析认为，「Envoy 原生」生态(Envoy Gateway、Istio Ambient)展现出最高的一致性与功能速度，已成为事实上的主导架构模式。若 L4 吞吐绝对关键，拥有 eBPF 数据面的 Cilium 更为突出。而对从 ingress-nginx 出发的团队而言，把 NGINX 控制面用 Go 重写、原生支持 Gateway API 的 NGINX Gateway Fabric，在心理与技术上都最为接近。

6. 迁移——ingress2gateway 与分阶段切换

进入最现实的问题：「已经有几十个 Ingress 在跑，怎么迁？」所幸，SIG 提供了官方转换工具。

6.1 ingress2gateway

ingress2gateway 是把现有 Ingress 资源自动转换为 Gateway 与 HTTPRoute 的 Kubernetes SIG 项目，支持 NGINX、Istio、Kong、Apisix、GCE 等多家提供方的专属注解处理。手工翻译复杂的 Ingress 规则与注解极易出错，而该工具将这一过程自动化。

# 读取集群中所有 Ingress 并输出 Gateway API 资源
ingress2gateway print --input-file=ingress.yaml --providers=ingress-nginx

# 结果(概念上)：生成 Gateway + HTTPRoute YAML
# → 切勿直接应用，务必审查(自动转换只是「草稿」)

关键提醒：自动转换的结果是 草稿。有些规则能干净地映射到标准字段，但部分厂商专属注解在标准里没有一一对应。转换后要审查差异，必要时用实现专属扩展(例如 Envoy Gateway 的策略资源)来补足。

6.2 分阶段迁移路线图

  1. 盘点清单：列出集群中所有 Ingress 及其注解，先确认哪些注解能映射到标准。
  2. 选型与安装：依据上面的对比选定 Gateway API 实现，并与既有 ingress-nginx 并行 安装，不要一次性全部替换。
  3. 生成转换草稿：用 ingress2gateway 生成 Gateway 与 HTTPRoute 草稿，再审查与修正。
  4. 从非核心开始迁移：先把流量小、风险低的服务迁到新 Gateway 验证行为。
  5. 逐步迁移流量：用 DNS 权重、金丝雀、蓝绿把流量分阶段切到新路径，出问题立即回滚。
  6. 下线 ingress-nginx：所有路由验证通过后，停用旧控制器。

这种分阶段姿态与可靠性运维的基本原则一致。「一次性全面切换」看似最快，实则最危险。给自动化与迁移始终留一条回滚路径的思路，与 SRE 中的 AI——可靠运维的未来 所述原则精确呼应。

7. 迁移时的考量——陷阱清单

要让切换顺畅，需提前了解几个陷阱。

  • 没有一一对应的注解：精细的 NGINX 调优(特殊超时、自定义配置片段)未必能全用标准字段表达。可用实现专属策略补足，但要意识到那部分会重新产生厂商依赖。
  • TLS 与证书管理模型变化：Ingress 的 TLS 块移到 Gateway 的按监听器 certificateRefs，cert-manager 的对接方式也要检查。
  • 跨命名空间路由：Gateway API 用 ReferenceGrant 显式允许跨命名空间引用。安全上更强，但初期常成为「为何连不上？」的根源。
  • 各实现一致性差异：并非每个实现都 100% 支持标准的全部功能。请确认要用的功能在所选实现的一致性(conformance)范围内。在 Gateway API v1.5 评审过程中，更新停滞的实现将从列表中移除。
  • 可观测性与指标重建：针对 ingress-nginx 指标调好的仪表盘与告警，需按新数据面(如 Envoy)重新搭建。

8. 对国内基础设施环境的启示

把这股趋势放进国内运维现实，可见几个实质要点。

  • 托管 Kubernetes 用户：使用各类托管 K8s 的团队，应先确认平台默认提供哪个 GatewayClass。基础设施提供方铺好 GatewayClass，运维团队的负担就会减轻。
  • 金融与电信的安全要求：在面向互联网的集群里，2026 年 3 月后继续运行无安全补丁的控制器，从合规与审计角度都是风险，应提高迁移优先级。
  • 小型运维人手：在基础设施工程师身兼数职的众多组织中，角色分离即意味着「运维负担的下放」。应用团队自助管理 HTTPRoute，平台团队的瓶颈就会缓解。
  • 分阶段迁移文化：对以不停机为生命线的大型服务而言，以金丝雀与并行运行为前提的分阶段切换，几乎是唯一安全之路。

9. 纠正常见误解

9.1 「Ingress 立刻就死」

不对。死的是开源 ingress-nginx 控制器。Ingress 资源(networking.k8s.io/v1)本身仍留在 Kubernetes，其他 Ingress 控制器也存在。但未来指向 Gateway API。

9.2 「Gateway API 还在实验阶段」

不对。核心资源(GatewayClass、Gateway、HTTPRoute)已在 v1.0 达到 GA，是稳定 API，可用于生产。

9.3 「F5 NGINX 商用产品也要终止」

不对。退役的只是社区项目。F5 的商用 NGINX Ingress Controller 另行维护。

9.4 「选错实现就得从头来」

大体不对。只要使用标准资源，HTTPRoute 等路由定义大多可复用。更换实现的成本远低于 Ingress 时代。

10. 结论 + 可立即落地的三件事

ingress-nginx 的退役看似危机，更准确地说是 一个迫使我们完成被一再拖延的标准化的转折点。Ingress 靠注解这条迂回路撑了十年，而这条迂回路在厂商锁定、不可校验、安全负担上走到了极限。Gateway API 用标准字段与角色分离而非注解来解决同样的问题，是从零重新设计的答案。核心资源已是 GA，实现有多种，站在标准之上无论选哪个，清单都可复用。

以可立即落地的三件事收尾。

  1. 先盘点清单。列出集群中所有 Ingress 与注解，从面向互联网的开始排优先级。不知道要迁什么，就无法制定迁移计划。
  2. 用 ingress2gateway 生成草稿。别手工翻译，用官方 SIG 工具产出转换草稿再审查。一旦看清哪些注解无法映射到标准，就成功了一半。
  3. 以并行运行做分阶段迁移。让新实现与 ingress-nginx 并排运行，先把非核心服务用金丝雀迁过去验证。始终留好回滚路径，是不停机切换的核心。

用一句话概括：「退役的只是一个控制器，要迁向的不是某个厂商，而是标准。」 对所有思考 ingress-nginx 之后该何去何从的团队，Gateway API 不只是替代品，更是面对「下一次退役」也不会动摇的根基。
