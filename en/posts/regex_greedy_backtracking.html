When a Regex Never Finishes - Greedy Matching and Backtracking Blowup

Measuring the structure that doubles the time for every extra character, then cutting it four different ways

2026-09-01 Dev & Infra

When a regex returns the wrong answer, you find out quickly. A test goes red, or a badly truncated value shows up in the logs. The awkward case is the one where the regex returns no answer at all. There is no exception and no error message. The process is simply standing still on that line. One core sits pinned at 100 percent, and if you grab a stack trace it points somewhere inside String.prototype.match.

The most common misreading of this situation is that the input must be large. The input in the example measured below is 31 bytes, and processing it took 7.8 seconds. The cause is not the size of the data but the shape of the pattern. This article works out what that shape is, why it grows exponentially, and how to cut it, with a stopwatch on every claim.

Every number in this article came from actually running the code on the single machine described under Measurement environment below. Absolute values will differ with CPU, runtime version and whatever else is competing for the machine. The thing to read is not the millisecond figure but the ratio by which time grows when the input grows a little. That ratio holds its shape across machines.

Backtracking as a structure

Most programming languages ship a backtracking regex engine. It behaves exactly as the name suggests. It reads the pattern left to right, matching it against the string, and when it gets stuck it returns to the most recent point where a choice was available and takes a different one. It is the maze strategy of marking every fork and walking back to the last mark on hitting a dead end.

There is a reason this approach stays popular despite being slow in the worst case. Several features can only exist if the engine is able to walk back.

  • Backreferences — syntax like (\w+)\s+\1, which demands the same text that an earlier group captured. It only works if the engine can remember what was captured and try again
  • Lookaround — positional checks such as (?=...) and (?<=...). The engine matches a trial pattern at one point and then returns to where it started
  • Give-back in greedy quantifiers — .* consuming everything and then handing characters back one at a time when what follows fails to match is itself backtracking
  • Ordered alternation — the rule that (a|ab) tries the left branch first and falls through to the right on failure also sits on top of the ability to walk back

These features reach past what formal language theory calls the regular languages. That means a single pass through a state machine cannot handle them, and a search is required. Searches have worst cases. That worst case is usually much closer than people expect.

Reproducing the disaster - one character, twice the time

The textbook example is ^(a+)+$. Feed it a string of n copies of a with a single b at the end. The b can never match, so the engine can only declare failure after it has tried every possible branch. The measuring code is this.

const CAP_MS = 4000;   // stop as soon as one run exceeds 4 s

for (let n = 10; n <= 34; n++) {
  const s = 'a'.repeat(n) + 'b';
  const re = new RegExp('^(a+)+$');
  const t0 = process.hrtime.bigint();
  re.test(s);
  const ms = Number(process.hrtime.bigint() - t0) / 1e6;
  console.log(n, ms.toFixed(3));
  if (ms > CAP_MS) break;
}

Every entry in the ratio column clusters around 2. That is the fingerprint of exponential growth. One character doubles the time, which means ten characters multiply it by a thousand. Extending the table gives hours at 40 characters and months at 50. That is why it feels like the process has stopped. Nothing has actually stopped; the finish time has simply moved outside human time.

The striking part is how narrow the band is. Up to 20 characters it is 6 milliseconds, which passes any test suite you care to write. At 25 characters it is a tenth of a second, at 29 characters two seconds, at 31 characters 7.8 seconds. Short development samples will never trip it, and the first slightly longer production value crosses the whole range at once.

Why it explodes - counting the ways to split

The disease has a name: ambiguity. In (a+)+ the inner a+ takes one or more a characters and the outer + repeats that one or more times. So there is not one way to match the four characters aaaa. There are 4, 3+1, 1+3, 2+2, 2+1+1, 1+2+1, 1+1+2 and 1+1+1+1 — eight of them. In general the number of ways to cut n characters like this is 2n-1.

When the match succeeds, the engine stops at the first arrangement it finds. But when a trailing b makes $ fail, the engine reasons that a different split might have worked and tries them all. There are 2n-1 splits, so there are that many attempts. The blowup sits exactly where two conditions overlap: the same substring can be divided in several ways, and all of those divisions fail.

The way to confirm the diagnosis is to measure other shapes that carry the same property. They look nothing alike, but each one admits several ways to split.

Patternn=20n=24n=28n=29
^(a+)+$6.480 ms109.264 ms2233.649 ms3995.791 ms
^(a|a)*$13.354 ms191.011 ms3368.902 ms6640.935 ms
^(a*)*$12.359 ms242.906 ms3675.270 ms7156.893 ms

All three trace the same curve. In (a|a)* the two branches match exactly the same thing. Either choice gives the same result, so n repetitions produce 2n paths that all fail identically. In (a*)* the inner part can match the empty string as well, which raises the count of splits further. The syntax differs; the disease is one thing.

  • A quantifier inside a quantifier, where the inner one is variable length — (a+)+, (\w+\s?)*, ([a-z]*)+
  • Alternatives that can match the same character — (a|a)*, (\d|\w)*, (x|xy)*
  • A repetition containing something that can match the empty string — (a*)*, (\s?)*
  • All three reduce to one condition. If the same input maps onto the pattern in two or more ways, failure means checking every one of them

It only blows up on failure

This property is decisive when diagnosing. With the same pattern and the same size of input, nothing happens at all if the match succeeds, because the engine stops at the first success. Three cases at the same n=26, measured side by side.

input "a"x26 + "b"   pattern ^(a+)+$    447.897 ms   (fails)
input "a"x26 + "b"   pattern ^(a+)+     0.0005 ms    (succeeds at once)
input "a"x26        pattern ^(a+)+$    0.0002 ms    (succeeds at once)

The third line matters most. The pattern is the notorious one, unchanged, but with the single b removed it takes 0.0002 ms. A factor of more than a million rides on the last character of the input. The second line drops the $. Once there is no requirement to reach the end, the match succeeds early and stops.

That yields a practical conclusion. Tests that only feed valid values will never catch this class of defect. Filling a regex test with success cases is a common habit, and this failure mode hides precisely in that blind spot. Meanwhile the values arriving in production are far more varied on the invalid side.

For the same reason, anchoring changes the timing. Without a leading ^, the engine fails at the first character, then restarts from the second, then from the third. At n=24, ^(a+)+$ took 116.532 ms while (a+)+$ took 295.768 ms, a factor of 2.5. An anchor does not remove the exponent, but it does remove the constant factor in front of it.

Greedy, lazy and possessive

Quantifiers come in three temperaments. The difference is not how much they consume but whether they will give any of it back.

NotationNameBehaviourJS (V8)Python 3.13Perl 5.38
* +GreedyTakes as much as possible, hands back one character at a time when blockedYesYesYes
*? +?LazyTakes as little as possible, takes one more at a time when blockedYesYesYes
*+ ++PossessiveTakes as much as possible and never gives any backNoYesYes
(?>...)Atomic groupOnce the group is left, its choices are never revisitedNoYesYes

Start with the common misconception. Switching to a lazy quantifier makes it faster is only half true. Laziness does not abandon backtracking; it reverses the direction of the backtracking. In a 200,000-character haystack the result flips entirely depending on where the target sits.

PatternTarget near the frontTarget at the end
<h2>(.*)</h2>0.2658 ms0.0350 ms
<h2>(.*?)</h2>0.0003 ms0.0357 ms
<h2>([^<]*)</h2>0.0003 ms0.0356 ms

With the target at the front, lazy is nearly 900 times faster, because greedy first swallows all 200,000 characters and walks back from there. With the target at the end, the three patterns are effectively identical, because laziness now extends one character at a time across 200,000 attempts. Laziness is not a performance measure but a choice of meaning. Use it when you want the shortest match; the speed follows the shape of the data.

The real countermeasures are possessive quantifiers and atomic groups. Both tell the engine explicitly to give up backtracking here. a++ takes as many a characters as it can and refuses to regurgitate them even when what follows fails. With nothing to hand back there are no branches, and with no branches there is no exponent. These are the values measured on Python 3.13.3 and Perl 5.38.2.

Python 3.13.3
  ^(a+)+$    n=26        3323.962 ms
  ^(a++)+$   n=100000    0.0398 ms
  ^(?>a+)+$  n=100000    0.0395 ms

Perl 5.38.2
  ^(a++)+$   n=100000    0.0091 ms
  ^(?>a+)+$  n=100000    0.0091 ms

The input grew by a factor of about 3800 and the time is still four hundredths of a millisecond. One caution though: possessive quantifiers change meaning. Applied where no give-back is needed, as in "[^"]*+", they are safe, but bolted onto a pattern that relies on give-back further along they will make things that used to match stop matching. Treat them as a declaration of intent, not a performance flag.

Cutting the retries in JavaScript

JavaScript does not have those tools. On Node.js v22.16.0 (V8 12.4.254.21-node.26) all three are rejected at compile time.

> new RegExp('^(?>a+)+$')
SyntaxError: Invalid regular expression: /^(?>a+)+$/: Invalid group

> new RegExp('^a*+$')
SyntaxError: Invalid regular expression: /^a*+$/: Nothing to repeat

> new RegExp('^a++$')
SyntaxError: Invalid regular expression: /^a++$/: Nothing to repeat

The message Nothing to repeat tells the whole story. V8 does not read a++ as a possessive quantifier; it reads it as a syntax error meaning repeat the + with another +. The concept simply is not there.

There is an idiom that produces the same effect: put the group inside a lookahead and then consume it with a backreference. Rewrite (?>X) as (?=(X))\1. A lookahead fixes its result once and does not hand it back from the outside, so consuming that result through a backreference behaves like an atomic group.

// making ^(a+)+$ atomic
const naive  = /^(a+)+$/;
const atomic = /^(?=(a+))\1+$/;

// "a"x26 + "b"
naive.test(s)    →  528.117 ms
atomic.test(s)   →  0.0005 ms

// the same atomic pattern on far larger inputs
n=1000     0.0009 ms
n=10000    0.0077 ms
n=100000   0.0771 ms

Each hundredfold increase in input costs roughly ten times the time, which is close to linear. The idiom is undeniably hard to read, so if you use it, leave a comment explaining why. Otherwise someone will later mistake it for a pointless lookahead, tidy it away, and bring the defect straight back.

Slow without being exponential

Exponential blowup is dramatic but not common. What turns up far more often in practice is polynomial backtracking, and the classic form is several .* groups separated by delimiters. It appears in almost every log parser and CSV handler ever written.

I fed a pattern of the form ^"(.*)" "(.*)" "(.*)"$ a line holding many quoted fields, with one extra character on the end to force the match to fail. The three .* groups do work proportional to the number of ways the delimiter positions can be chosen.

FieldsLine length"(.*)""([^"]*)"
1050 chars0.003 ms0.0001 ms
20110 chars0.024 ms0.0001 ms
40230 chars0.208 ms0.0001 ms
80470 chars1.774 ms0.0001 ms
1601010 chars15.522 ms0.0001 ms

A 20-fold increase in length produced a 5000-fold increase in time. That is roughly 8 times per doubling, so about cubic. It does not kill instantly the way an exponent does, but as an explanation for a parser slowing down when log lines get longer, this is much the more frequent culprit. And the right-hand column already contains the answer: replacing .* with [^"]* flattens every size.

The reason is simple. [^"]* is forced to stop at a quote. With the stopping point fixed there is no combinatorial choice to explore. .* can swallow quotes too, so the engine has to try each possible stopping point. Taking the delimiter out of the character class is the cheapest fix available in this family.

The shapes that actually show up at work

Dangerous patterns rarely look dangerous. Nobody writes (a+)+ on purpose; what is actually sitting in the codebase looks like the rows below.

ShapeHow it really appearsWhat is hiding in it
Nested quantifier^(\w+\s?)*$ — checking a line of words joined by spaces\s? is optional, so \w+ runs can abut and the split becomes ambiguous
Overlapping alternatives(\d|\w)+ — a run of digits or letters\d is contained in \w, so every digit creates two paths
Chained dot-star^(.*) (.*) \[(.*)\] "(.*)"$ — one access log lineCombinations of delimiter positions, growing polynomially as fields get longer
Loose email validation^([\w.-]+)+@([\w-]+\.)+[a-z]{2,}$The local part is shaped like (X+)+, and the domain side is another repetition inside a repetition
Whitespace cleanup^(\s*)+$ or (\s|\t)*$Repetition of something that can match empty; it splits on mixed tabs and spaces

I measured the first row. Against ^(\w+\s?)*$ I fed n letters followed by a !. Even with no spaces in the string, \s? can match empty, which is enough to make the split ambiguous.

This pattern is a standard fixture in input validation that checks whether a user name consists only of words and spaces. And such validation sits, by definition, exactly where user input arrives.

ReDoS - where termination becomes an availability problem

Everything so far has been a performance story. The character of it changes the moment user input reaches one of these patterns. Regular expression denial of service (ReDoS) describes a short input pinning a worker long enough to stall the whole service. What defines the problem is that it needs no special privilege and no volume of traffic.

On a runtime with a single-threaded event loop the blast radius is worse. If one request spends 7 seconds matching, every other request in that process waits for those 7 seconds. The health check stops responding, the instance gets replaced, and if the same request lands on the replacement the cycle simply repeats.

This article does not cover how to construct a harmful input. What is needed is the ability to find and close these shapes yourself.

  • Cap the input length first. Putting if (s.length > 200) return false; in front of the regex bounds the worst case to a constant. On an exponential curve, a few characters of cap make an enormous difference
  • Remove the shape from the pattern. This is the real fix: un-nest the quantifiers, stop the branches from overlapping, take the delimiter out of the character class
  • Put a time bound at the boundary. Move matching on user input into a separate worker or a path with a deadline. The standard JavaScript regex has no timeout of its own
  • Never accept a pattern as data. Building new RegExp() from a user-supplied string puts the pattern itself outside your control, and none of the review above applies any more
  • Patterns in your dependencies count too. If it is absent from your code but present inside a parser or validation library, the outcome is identical

I measured the effect of the first item. These are worst-case values for the same vulnerable pattern under different caps.

maxLength=16   worst 0.195 ms
maxLength=20   worst 3.131 ms
maxLength=24   worst 51.605 ms
maxLength=28   worst 849.141 ms

Moving the cap from 28 down to 16 removes a factor of about 4000. Still, this is mitigation rather than repair. A length cap quietly creeps upward the next time requirements change, and the defect comes back with it. Fixing the pattern itself always comes first.

Engines differ

Here an unexpected result turned up. Running the same ^(a+)+$ under Perl 5.38.2, it did not explode. It stayed flat at 0.017 ms for n=20 and 0.018 ms for n=34. ^(a*)*$ and ^(\w+\s?)*$ behaved the same way. Perl's engine appears to remember which (position, pattern point) combinations have already failed and to decline to repeat that work.

That does not make Perl safe. In the same Perl, the polynomial pattern from the previous section, ^"(.*)" "(.*)" "(.*)"$, slowed down exactly as before: 0.011 ms at 10 fields, 6.199 ms at 80, and 323.276 ms at 320. Some shapes are caught by the optimisation and others are not.

At the opposite end sit automaton-based engines. Instead of walking back they carry all the possible states at once and read the input a single time. I measured the same pattern with GNU grep 3.0.

grep process startup alone (1-byte file)   0.046 ~ 0.052 s

grep -E '^(a+)+$'
  n=20         0.049 s
  n=100        0.053 s
  n=10000      0.050 s
  n=100000     0.059 s
  n=1000000    0.058 s
  n=5000000    0.104 s

Startup costs 0.05 s, so nothing below that is measurable. The meaningful line is the last one. Five million characters were matched in roughly 0.05 s of actual work. That is the pattern on which Node spent 7.8 seconds for 31 characters. The curve itself is a different curve.

There is a trade. The documentation for Go's regexp package states that «the regexp implementation provided by this package is guaranteed to run in time linear in the size of the input (this is a property not guaranteed by most open source implementations of regular expressions)». The price is that the RE2 syntax reference marks backreferences \1 and the lookaround forms (?=re), (?!re), (?<=re) and (?<!re) all as NOT SUPPORTED.

Engine and versionApproach^(a+)+$ observedPossessive / atomicNote
Node.js v22.16.0 (V8 12.4)Backtracking7798 ms at 31 charsNot supportedEmulated with lookahead plus backreference
Python 3.13.3 reBacktracking6961 ms at 28 charsSupportedBoth (?>...) and a++ compile
Perl 5.38.2Backtracking plus optimisation0.018 ms up to 35 charsSupportedStill slows down on polynomial patterns
GNU grep 3.0 -EAutomatonAbout 0.05 s at 5M charsNot applicableMeasured on ERE without backreferences
Go regexp (RE2)AutomatonCould not run itNot applicableLinear guarantee per docs; no backreferences or lookaround

There is a quiet symmetry here. The idiom that rescued JavaScript in the earlier section, (?=(a+))\1, uses both a lookahead and a backreference. The very tool that saves a backtracking engine cannot exist in an automaton engine, which is the one that never explodes in the first place. A linear-time guarantee and expressive power are two ends of the same axis.

Fixing it - before and after, side by side

There are four fixes, and each has already appeared above. Here they are with before and after in one table. The order matters: the higher ones are more fundamental.

Un-nest the quantifiers

This is the surest repair. When a repetition contains an optional element, as in (\w+\s?)*, pull that optional element out of the repetition so the split becomes determined. Rewritten as ^\w+(\s\w+)*$, a space must be present before the next repetition can start, so there is exactly one way to divide the string.

Narrow the character class

Remove the delimiter character from the class. "(.*)" becomes "([^"]*)"; (.*) becomes (\S+) . Once the stopping point is fixed, the combinatorics disappear. The meaning usually gets more precise as well.

Make it give up backtracking

On Python, Perl or a PCRE-family engine, use a possessive quantifier or an atomic group. On JavaScript, use the lookahead idiom. This treats the symptom while leaving the shape in place, so it is the option for when the two fixes above are unavailable.

Do not use a regex

If the job is splitting on a delimiter, string functions are both faster and easier to read. Here is the result of decomposing a 602-character three-field line 200,000 times.

FixBeforeAfter
^(\w+\s?)*$ → ^\w+(\s\w+)*$2268.459 ms at n=280.0003 ms at n=30 / 0.2574 ms at n=100000
"(.*)" → "([^"]*)"15.522 ms at 160 fields0.0001 ms at 160 fields
Python ^(a+)+$ → ^(a++)+$3323.962 ms at n=260.0398 ms at n=100000
JS ^(a+)+$ → ^(?=(a+))\1+$528.117 ms at n=260.0771 ms at n=100000
Regex exec → indexOf + slice83.5 ms for 200k runs5.9 ms for 200k runs

Under the same conditions String.split(',') took 56.1 ms. But that difference only becomes visible across 200,000 runs. There is no reason to write unreadable code over the gap between 0.4 microseconds and 0.03 microseconds per call. The exponential and polynomial problems live at a completely different order of magnitude from this one.

A minimal script for measuring your own pattern

Judging a pattern by eye is harder than it sounds. Growing the input length and timing it removes the need to judge at all. Linear keeps the ratio near 1; exponential keeps it near 2.

// redos-probe.js
// usage: node redos-probe.js "<pattern>" [repeated unit] [suffix]
const [, , src, unit = 'a', tail = 'b'] = process.argv;
const BUDGET_MS = 2000;
const re = new RegExp(src);
let prev = 0;

console.log('n\tms\tratio');
for (let n = 2; n <= 200000; n = n < 40 ? n + 2 : Math.ceil(n * 1.6)) {
  const s = unit.repeat(n) + tail;
  const t0 = process.hrtime.bigint();
  re.test(s);
  const ms = Number(process.hrtime.bigint() - t0) / 1e6;
  const ratio = prev > 0.05 ? (ms / prev).toFixed(2) : '-';
  console.log(n + '\t' + ms.toFixed(3) + '\t' + ratio);
  if (ms > BUDGET_MS) {
    console.log('\nVERDICT: super-linear. ' + ms.toFixed(0) + ' ms at n=' + n);
    process.exit(2);
  }
  prev = ms;
}
console.log('\nVERDICT: stayed under ' + BUDGET_MS + ' ms up to n=200000');

BUDGET_MS is the important part. The loop stops the moment one run exceeds it. On an exponential curve the next step is double, so running without a cap means stalling your own machine. The tail value must be a character that makes the match fail. Inputs that succeed reveal nothing, as the earlier measurement showed.

The difference between the two outputs is the diagnosis. In the first, n grows by 2 and time grows fourfold. In the second, n grows by a factor of 1.6 and so does the time. Read the third column, not the second. Absolute times vary by machine; the ratio is a property of the pattern.

When not to use a regex at all

That covers the repairs. The last question is where not to reach for a regex in the first place. What a regex can express is everything except structures nested to an unbounded depth. Cross that boundary and the pattern grows long, and long patterns drag in the shapes described above.

  • HTML and XML — tags can wrap each other to any depth. A regex cannot pair an opening tag with its closing tag. Use a parser
  • JSON and YAML — the same reason. Objects inside objects are a recursive structure, and a parser already ships with the standard library
  • Balancing brackets — the canonical example formally proven to sit outside the regular languages. Code that walks and counts is the right answer
  • Email address validation — a regex that follows the specification exactly is long and usually contains a dangerous shape. Check the form only, roughly one @ with something on each side, and do the real validation with a confirmation email
  • URL parsing — every language has a URL class or an equivalent. A hand-written pattern will be wrong on some edge case, guaranteed
  • Splitting on a fixed delimiter — using a regex where split or indexOf would do is slower and harder to read
  • Searching for a literal string — use includes or grep -F. There is no reason to feed something that is not a pattern to a pattern engine

The territory where a regex belongs is still large. For flat, length-bounded, non-recursive text nothing states intent as compactly. The problem is continuing to use it after leaving that territory.

The separate problem of the same regex meaning different things in different tools is covered in regex dialect portability; practical uses of lookahead are in lookahead in practice; and the syllable trap when handling Korean text is in the Korean regex syllable trap. Confusing shell globs with regexes is covered in shell globs versus regular expressions.

What I could not verify

  • The exact mechanism by which Perl 5.38.2 avoided exploding on ^(a+)+$ is unconfirmed. It looks like an optimisation that remembers failed combinations, but perldoc was not functional on this machine, so I could not confirm its name or conditions in the official documentation. Only the measurements are reported
  • Go and RE2 are not installed on this machine and could not be run. Those rows in the table are documentation, not measurement. The linear-time guarantee and the absence of backreferences and lookaround were confirmed in the docs, but no timing was taken
  • I did not read GNU grep 3.0's source to confirm its internals. The automaton description is widely reported and the measurements are consistent with it, but what this article verified is only that no blowup was observed
  • The grep measurements are buried under roughly 0.05 s of process startup, so the actual matching cost below that could not be separated out. The five-million-character figure is an estimate obtained by subtracting startup from 0.104 s
  • Python's third-party regex module and the re2 bindings were absent from this environment and are missing from the comparison. Only the standard re was measured
  • Other JavaScript engines (SpiderMonkey, JavaScriptCore) were not measured. There is no basis for assuming the V8 figures carry over to them
