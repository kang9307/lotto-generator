TypeScript 7 正式发布 - Go 原生编译器改变了什么，又没能改变什么

RC之后三周迎来GA，从实务角度审视迁移、兼容性与esbuild的关系

2026年7月9日 开发/基础设施

引言:编译器替换成为「正式」的那一刻

2026年7月8日，微软宣布TypeScript 7正式发布(GA)，距离6月18日RC发布约三周。本人在RC阶段就已经分析过这次重写的技术背景。这篇文章的重点不同。RC是「预告片」，GA则是「定稿」——它揭示了那份预告到底有多少原样落地，以及真正把它用到项目里时应该注意什么。

本文以2026年7月的官方公告与发布后的报道为依据，回答三个问题:为什么必须把整个编译器搬到Go上、开发者到底能从中获得什么、以及最重要的——现在是否应该立刻迁移。最后一个问题最贴近实务，也最常被人略过。

1. tsc为何必然遇到瓶颈

如果把整个编译器换语言这件事理解成「团队只是喜欢快的语言」，就会错过重点。问题从来不是算法，而是执行模型。

1.1 两道结构性瓶颈

旧版tsc用TypeScript自身(本质上是JavaScript)写成，运行在JavaScript引擎之上。这带来两道天花板。其一，只要不是原生代码，即便经过JIT也无法完全抹去执行开销。其二，其模型基本是单线程的，即便多核已是常态，也没有干净的办法把大型代码库的类型检查并行拆分。代码库一旦膨胀到数十万行，类型检查动辄耗时数十秒，编辑器的自动补全、错误提示跟不上输入速度，正是这道天花板的症状，而非算法缺陷。

1.2 为何是Go而非Rust

更值得玩味的是选择Go的原因。单看性能，Rust本该是有力候选。但根据公开的说明，既有编译器代码库大量依赖共享可变状态与指针密集的图遍历结构。要把这种结构搬进所有权模型严格的Rust，几乎必须大幅重新设计;而基于GC的Go则能让团队几乎原样保留既有逻辑与数据结构，实现方法论式移植(methodical port)而非从零重写。选择移植而非重写的理由很清楚:只有移植才能借助数十年积累的测试套件，验证「新实现是否给出与旧实现相同的答案」——这对一个价值核心就是「可信赖」的工具而言至关重要。

2. 开发者实际获得什么 - 构建与编辑器

官方给出的两个案例很有代表性。VS Code代码库(约150万行)的构建时间据报从约78秒降到约7.5秒，Sentry从约133秒降到约16秒，大致落在8~10倍区间。这一提速是两个因素叠加的结果:原生编译贡献约3~4倍，此前无法实现的并行能力再贡献约3~4倍。作为附带效果，Go的内联结构体比JavaScript版本那种以分配为主的对象更省内存，据称大型项目的内存占用降到约一半。

本人更看重的体感点不是构建时间，而是编辑器的响应速度。语言服务器一旦变慢，影响的不只是「红色波浪线出现得晚」，而是自动补全本身出现延迟，让开发者不再信任工具、转而绕过它。如果原生语言服务器能从根本上压缩这种延迟，体感生产力的提升会比CI时间的缩短来得更直接。不过这些数字都是基准项目上的表现，自己代码库的实际收益仍取决于结构与硬件配置，这一点需要说清楚。

3. 迁移的真正陷阱 - Compiler API的空白

本人认为这是这次GA中实务上最重要的一点。tsc自身的类型检查结果力求与6.0保持一致，但编程式Compiler API在7.0的原生编译器中尚不存在。GA再次确认它被推迟到7.1。

3.1 到底会破坏什么

受影响的不是「编译代码、检查类型」这类普通用法，而是集中在直接调用ts.createProgram或ts.transpileModule等API来操作AST的工具上。据报道，受影响的例子包括基于AST的代码生成与重构工具、以编程方式生成声明文件(.d.ts)的打包器插件，以及把tsc直接别名指向原生二进制的测试运行器配置。相比之下，编辑器扩展所依赖的Language Service Plugin API据称在7.0中依然保留，因此大多数IDE自动补全、Lint插件应该不受此空白影响，能继续正常工作。

3.2 安全网 - 新旧版本并行

为填补这一空白，官方同时提供了重新暴露旧API的兼容包。新版tsc指向快速的原生编译器，另一个独立的可执行文件则让依赖旧版JavaScript编译器及其API的工具继续可用。换言之，官方推荐的过渡策略是两者并行:把构建与类型检查迁到新编译器，同时让依赖API的工具留在旧版可执行文件上。

3.3 早已预告的破坏性变更

除API空白外，TypeScript 7还确定了一批清理性变更:strict默认开启、移除target: es5(最低支持ES2015)、移除module的AMD/UMD/SystemJS格式、移除moduleResolution: node10。这些从RC阶段就已预告，且被设计为先在TypeScript 6.0中以警告形式出现，因此只要提前认真升级到6.0，这部分大多是可预见的。

4. 与esbuild、swc的关系 - 不是竞争，而是边界重新划清

一个自然的问题随之而来:「都已经用esbuild或swc让构建变快了，TypeScript 7还有什么意义?」这个问题背后藏着一个假设。esbuild和swc从一开始就不做类型检查——它们只是剥离类型标注、原样放行，这正是其速度的来源。也正因如此，业界长期采用二分式流水线:用这两者快速完成转换，把较慢的类型检查单独放到别处(编辑器里、只在CI中、有时干脆跳过)。

TypeScript 7让tsc本身变快，从而降低了这种拆分的必要性。但这并不会把esbuild、swc挤出局。它们承担打包、压缩、JSX转换等职责，而这些从来都不是tsc的工作。本人的解读是:TypeScript 7会促使团队重新审视那些「仅仅因为类型检查太慢而不得不绕开」的工作流，而esbuild、swc作为打包工具的角色不会改变。与其说是竞争，不如说是各自的边界重新变得清晰。

5. 实务采用时机的判断

最终还是回到最重要的问题:现在迁移，还是再等等。本人建议按工作负载来区分判断。

5.1 可以立刻迁移的情况

如果团队主要只用tsc和编辑器功能，没有ts-morph一类AST操作工具或tsup --dts这类依赖API的构建环节，现在迁移风险较低。尤其是那些CI耗时、大型monorepo类型检查曾是瓶颈的团队，很可能立刻感受到收益。

5.2 更适合再等等的情况

如果团队在运行内部代码生成器、自定义转换器，或基于schema/类型的代码生成工具，不必急于求成更为稳妥。等7.1的Compiler API形态明朗后再迁移也不迟。在此期间，只把构建与类型检查迁到新编译器、让依赖API的工具留在官方并行提供的旧版可执行文件上，是现实可行的折中方案。

5.3 通用检查清单

无论哪种情况，第一步都一样:先升级到TypeScript 6.0，处理完全部弃用警告，再让新旧编译器在CI中并行运行、确认输出没有差异后再切换。相比厂商强调的速度数字，自己代码库的实际差异与工具链兼容性验证才是更可信的依据。

结语:原生化是起点，不是终点

TypeScript 7的GA只是「JavaScript生态工具跳出自身语言、走向原生化」这一更大趋势中的一幕。Vite、esbuild、SWC、Rspack早已走在这条路上，TypeScript更像是其中坚持最久之后终于加入队列的一员。但这次GA展现的不只是速度。速度的获得也伴随着一个事实——编程式API这部分扩展性被暂时让渡了出去。理解这层权衡、先盘点自己工具链再迁移的团队，与只看速度数字就贸然升级的团队，最终结果恐怕会不一样。
