"Don't Roll Your Own" 원칙 2026 - 브라우저의 기본 기능을 재발명하지 말아야 하는 7가지 이유

왜 2026년의 웹 UI는 다시 native로 돌아가고 있는가

2026-05-25 IT/기술

서론: 모든 웹사이트가 같은 컴포넌트를 다시 만드는 이상한 풍경

웹사이트 100개를 무작위로 펼쳐 본인이 직접 검사기를 열어 보면 발견하는 사실이 하나 있다. 거의 모든 사이트가 같은 컴포넌트를 직접 만들고 있다. 드롭다운 메뉴, 모달 창, 아코디언, 날짜 선택기, 파일 업로더, 진행 바, 폼 유효성 검사. 이 컴포넌트들은 모두 브라우저가 이미 기본으로 제공하지만, 90% 이상의 사이트는 div와 JavaScript로 처음부터 다시 만든다. 이상하지 않은가. 운영체제가 이미 제공하는 파일 다이얼로그를 모든 데스크톱 앱이 직접 다시 만든다면 우리는 그것을 비효율이라 부를 것이다. 그런데 웹에서는 그게 표준 관행이다.

news.hada.io 2026년 5월 24일자 토픽 6번 "Don't Roll Your Own" Principle은 이 현상에 적절한 이름을 다시 붙였다. 이 원칙은 원래 1990년대 후반 암호학 영역에서 시작되었다. "Don't roll your own crypto" — 직접 암호 알고리즘을 만들지 마라. 잘못 만들면 안전하다는 환상만 주고 실제로는 더 위험해진다는 경고였다. 이후 같은 원칙이 인증·세션 관리·HTML 파서·날짜 라이브러리로 확장되었다. 그리고 2026년에 다시, 웹 UI 영역으로 돌아왔다. 본 글은 hada.io의 짧은 토론을 단순 번역하지 않고, 본인 관찰과 한국 개발자 환경에서의 함의를 12개 챕터로 풀어 본다.

핵심 질문은 셋이다. 첫째 브라우저 native 기능을 직접 재구현하지 말아야 할 구체적 이유는 무엇인가. 둘째 어떤 기능들이 2026년 기준 이미 충분히 성숙했는가. 셋째 그럼에도 직접 만들어야 할 정당한 예외는 무엇인가. 이 세 질문에 답하면서 GitHub·Stripe·Linear 같은 사용자 경험 1위 사업자들이 native를 택하는 이유, React·Vue 생태계가 만들어 놓은 잘못된 관행, 그리고 한국 디자이너·기획자와 협상하는 실무 방법까지 함께 다룬다.

"Don't Roll Your Own"의 짧은 역사 - 암호학에서 UI로

원칙 자체의 출처를 정확히 짚어 두는 게 좋다. "Don't roll your own crypto"는 Bruce Schneier 같은 보안 연구자들이 1990년대 후반부터 반복해 온 경고다. 직접 만든 암호 알고리즘은 검증되지 않은 채 배포되어 사용자에게 안전하다는 잘못된 확신을 준다. 표준 라이브러리(OpenSSL·libsodium 등)는 수십 년간 수백 명의 전문가가 검증한 결과물이다. 둘 사이의 신뢰도 격차는 비교 자체가 무의미하다.

두 번째 확장은 인증과 세션 관리다. PHP에서 직접 세션을 관리하던 시절의 무수한 취약점이 OAuth·OpenID Connect·표준 세션 라이브러리로 정리되면서 같은 원칙이 자리 잡았다. CSRF·세션 고정·세션 재생성 같은 미묘한 이슈는 직접 만든 시스템에서 거의 100% 실수가 발생한다. 인증 라이브러리는 직접 만들지 말고 검증된 것을 가져다 쓰라는 합의가 백엔드 진영에서 정착했다.

세 번째 확장이 바로 2026년의 웹 UI 영역이다. 이 영역에서 "직접 만들지 말라"는 대상이 바로 브라우저가 이미 제공하는 native HTML 요소들이다. select·dialog·details·input의 다양한 type·progress·video·audio. 이 요소들은 W3C·WHATWG 표준에 기반해 모든 주요 브라우저에서 수십 년간 다듬어진 결과물이다. 그리고 그 결과물 위에 우리는 div를 깔고 JavaScript를 얹어 처음부터 다시 만든다. 같은 원칙을 다시 적용해야 할 시점이라는 게 hada.io 토론의 핵심이다.

재발명하지 말아야 할 10가지 브라우저 native 기능

본인이 정리한, 2026년 기준 이미 충분히 성숙해 굳이 직접 만들 이유가 없는 native 기능 10가지다. 각각에 대해 "왜 자주 재발명되는지"와 "왜 native가 더 나은지"를 짧게 본다.

1) <select> 드롭다운

가장 자주 재발명되는 요소다. 디자이너가 "스타일링이 어렵다"고 말해서 div로 대체된 경우가 많다. 그러나 2024년부터 appearance: base-select 제안이 브라우저에 들어오기 시작했고, 2026년에는 customizable select가 Chromium·Firefox에서 정식 지원되는 단계다. 기본 select 한 줄로 키보드 내비게이션·모바일 휠 피커·검색·접근성 트리 등록까지 무료로 얻는다.

2) <details> / <summary> 아코디언

아코디언과 토글은 details/summary 한 쌍으로 JS 0줄에 구현된다. open 속성 토글, 키보드 Enter/Space 동작, 검색 가능(브라우저 내장 검색에 포함됨)까지 자동이다. React 컴포넌트로 같은 동작을 재현하는 데 평균 100~300줄의 코드가 들어간다.

3) <dialog> 모달

2022년 모든 메이저 브라우저에서 안정화된 이후 dialog는 모달의 정답이 되었다. showModal() 호출 한 번으로 포커스 트랩·ESC 닫기·backdrop 자동 생성·접근성 처리까지 끝난다. ::backdrop 가상 요소로 배경 스타일링도 자유롭다. 직접 만든 모달이 흔히 놓치는 "모달 안에서 Tab 순환" 같은 미묘한 동작이 native에서는 무료다.

4) <input type="date|time|datetime-local"> 날짜·시간

React 생태계의 react-datepicker·MUI DatePicker가 사실상 표준처럼 사용되지만, 모바일 OS의 휠 피커를 native로 노출하는 input type=date의 사용성이 더 높은 경우가 많다. 특히 한국 모바일 사용자의 70% 이상이 iOS·Android의 익숙한 OS 피커를 더 빠르게 조작한다는 자체 측정 결과가 있다. CSS로 ::-webkit-datetime-edit 등 세밀한 스타일링도 가능해졌다.

5) <input type="file"> 파일 업로드

드래그 앤 드롭 영역까지 만들고 싶은 경우에도 native input type=file 위에 dropzone CSS만 얹으면 된다. multiple·accept·capture 같은 속성은 모바일에서 카메라·갤러리를 직접 띄워 주는 핵심이다. 직접 만든 파일 업로더가 모바일에서 동작하지 않는 흔한 실수를 native가 자동으로 피해 준다.

6) <progress> / <meter> 진행 바

div+width 애니메이션으로 만든 진행 바는 접근성 트리에 등록되지 않는다. 스크린리더는 그냥 "1번 영역"이라고만 읽는다. progress 요소는 value·max 두 속성만으로 접근성 트리에 자동 등록되고, 발화 시 정확한 퍼센트가 나온다. 같은 기능을 위해 ARIA를 수동으로 다는 것보다 훨씬 안전하다.

7) <video> / <audio> 미디어

video.js 같은 라이브러리는 분명 강력하지만, 단순 재생용이라면 native video가 PIP·자막·재생 속도·음량까지 모두 제공한다. controls 속성 한 줄로 OS별로 최적화된 컨트롤이 나타난다. 미디어 라이브러리가 진정으로 필요한 케이스는 HLS·DRM·스트리밍 같은 특수 영역이다.

8) input type="color | range | search | tel | email | url"

type을 정확히 지정하기만 해도 모바일 키보드가 자동 변환되고, 유효성 검사가 무료로 동작하며, 모바일에서 음성 입력·자동 완성·OS 비밀번호 매니저 연동까지 자동으로 활성화된다. 단순히 placeholder만 바꾸고 type을 text로 두는 흔한 실수가 한국 사이트에서 너무 자주 보인다.

9) 폼 validation (required·pattern·minlength·maxlength)

HTML5의 form validation은 직접 만든 JS validation보다 빠르고 접근성도 좋다. :valid·:invalid CSS 의사 클래스로 스타일링이 가능하고, novalidate 속성으로 부분적으로만 비활성화할 수도 있다. JS validation은 native validation을 보완하는 용도로만 쓰는 것이 2026 모범 사례다.

10) 스크롤 동작 (scroll-snap·scroll-behavior·overscroll-behavior)

캐러셀과 슬라이더를 직접 만드는 대신 CSS scroll-snap을 쓰면 JS 0줄에 부드러운 스냅 스크롤이 동작한다. smooth scrolling은 scroll-behavior 한 줄로, 오버스크롤 처리는 overscroll-behavior로 끝난다. 모바일 관성 스크롤까지 native가 자동 처리하므로 손이 가지 않는다.

재발명의 5가지 비용 - 코드만 늘어나는 게 아니다

"왜 native를 안 쓰고 직접 만드는가"라는 질문 다음은 "직접 만들면 정확히 무엇을 잃는가"이다. 본인이 정리한 5가지 비용은 다음과 같다.

  • 접근성(a11y) 손실: native 요소는 ARIA 역할·키보드 단축키·스크린리더 발화 패턴이 모두 무료다. div로 재구현하면 평균 200~500줄의 JS와 수십 시간의 a11y QA가 추가로 필요하고, 그래도 native보다 못한 경우가 대부분이다.
  • 키보드 단축키 부재: select에 진입한 뒤 첫 글자를 누르면 그 글자로 시작하는 옵션으로 점프하는 동작, dialog에서 Tab이 순환되는 동작, details에서 Enter로 열고 닫는 동작 — 이런 미묘한 키보드 패턴이 직접 만든 컴포넌트에서는 거의 100% 누락된다.
  • 모바일 호환성 문제: native input type=date는 iOS에서 휠 피커를, Android에서 머티리얼 캘린더를 자동으로 띄운다. 직접 만든 datepicker는 두 플랫폼 모두에서 어색하다. 같은 일이 file·color·range에서도 발생한다.
  • 번들 크기 증가: react-select 50KB, react-datepicker 40KB, react-modal 15KB, react-dropzone 30KB. 흔한 SPA 한 화면에 평균 150~300KB의 컴포넌트 라이브러리가 들어 있다. native로 대체하면 그 무게가 0KB가 된다.
  • 유지보수 부담: 라이브러리는 메이저 버전 업그레이드마다 깨진다. React 18→19 전환에서 react-select API가 변경되어 수천 개 SaaS가 마이그레이션 비용을 지불했다. native는 표준이 깨지지 않으므로 영원히 작동한다.

이 5가지 비용을 모두 정량화하면, 평균 중급 SaaS 기준 매년 200~500인시(person-hour)의 추가 비용이 컴포넌트 재발명에서 발생한다. 디자인 시스템 컨설팅에서 가장 자주 듣는 한국 기업 회신은 "그 정도면 디자이너 한 명 인건비"라는 표현이다. native 전환은 그 비용을 거의 0으로 만든다.

그럼 언제 재발명이 정당화되는가 - 3가지 예외 시나리오

본 글의 결론이 "모든 컴포넌트를 native로 쓰라"라면 절반은 틀린 결론이 된다. 직접 만드는 게 정당한 세 가지 시나리오를 정확히 짚어 둔다.

  • Native가 아예 지원하지 않는 인터랙션: 드래그 앤 드롭 정렬, 무한 스크롤 가상화, 멀티 컬럼 그리드, 코드 에디터, 캔버스 기반 화이트보드. 이런 영역은 native가 제공하지 못하므로 직접 만들거나 검증된 라이브러리를 가져다 쓰는 게 맞다.
  • 브랜드 정체성이 결정적 가치인 영역: 결제 페이지의 핵심 카드 영역, 메인 히어로 영역, 랜딩 페이지의 시그니처 컴포넌트. 디자인이 곧 사용자 신뢰의 근거가 되는 영역에서는 native의 제약을 풀고 커스텀으로 가는 게 정당하다.
  • Native의 구조가 요구사항과 맞지 않는 경우: 중첩 메뉴(메가 메뉴), 가상 키보드, 가상 드롭다운(수만 개 옵션). select가 1만 개 옵션을 화면에 그리면 브라우저가 멈춘다. 이런 케이스는 가상화가 필수이므로 커스텀이 맞다.

핵심 의사 결정 룰은 단순하다. "native가 70%만 충족해도 native로 가라"이다. 나머지 30%를 메우려고 100% 커스텀으로 가면 결과적으로 접근성·번들·유지보수 비용 모두에서 손해다. 30%의 갭은 CSS나 약간의 JS로 보완하는 게 거의 항상 더 싸다.

2026년의 native 기능 진화 - View Transitions·Anchor Positioning

2026년이 native를 다시 매력적으로 만든 이유 중 하나는 브라우저가 그동안 결정적으로 부족했던 기능들을 빠르게 채우고 있다는 점이다. 본인이 가장 영향력 있다고 보는 3가지 신기능을 본다.

View Transitions API

SPA의 매끄러운 전환 애니메이션을 위해 framer-motion이나 react-spring을 도입하던 시대가 끝났다. View Transitions API는 DOM 변경 전후를 자동으로 캡처해 사이를 부드럽게 보간한다. document.startViewTransition() 한 줄로 페이지 전환·요소 이동·리스트 정렬 애니메이션이 모두 동작한다. Chrome·Safari가 지원하고 Firefox도 2026 상반기 정식 지원에 들어갔다.

CSS Anchor Positioning

툴팁·드롭다운·팝오버 위치 잡기를 위해 Popper.js·floating-ui를 쓰던 시대도 끝났다. CSS anchor-name·position-anchor 속성으로 "이 요소 옆에 자동 배치, 화면 밖이면 반대편으로 뒤집기" 동작이 CSS만으로 동작한다. 2025년 Chrome 정식 지원, 2026년 Firefox·Safari도 안정화 단계다.

Popover API

popover 속성과 popovertarget으로 툴팁·드롭다운·메뉴를 JS 없이 만들 수 있다. dialog와 비슷하지만 모달이 아닌 비차단형이라 더 가볍다. Anchor Positioning과 결합하면 거의 모든 부유 UI가 native로 가능하다.

이 세 API의 등장으로 2024년까지 "native로는 불가능하다"고 여겨졌던 영역의 70~80%가 native로 가능해졌다. 그리고 이 흐름은 가속될 가능성이 높다. Interop 프로젝트(2022년 시작)가 4년째 운영되면서 주요 브라우저 4사가 같은 기능을 같은 일정으로 출시하는 협력 모델이 정착했기 때문이다.

CSS 변수와 ::backdrop으로 스타일링 - native를 유지하면서 디자인

"native를 쓰면 디자인이 못생겨진다"는 반박은 2026년 기준 더 이상 유효하지 않다. CSS의 진화로 native 요소를 거의 모든 부분에서 스타일링할 수 있게 되었기 때문이다. 본인이 자주 쓰는 패턴 3가지를 본다.

첫째 ::backdrop 가상 요소다. dialog와 popover의 배경을 ::backdrop으로 잡으면 backdrop-filter: blur(10px)·background: rgba(0,0,0,0.5) 같은 효과가 자유롭다. iOS Safari도 2024년부터 지원한다.

둘째 customizable select의 appearance: base-select다. Chromium 130+ Firefox 135+에서 native select의 옵션 영역을 거의 모든 측면에서 CSS로 스타일링할 수 있다. ::picker(select)·option::checkmark 같은 가상 요소로 디자인 시스템의 룩 앤 필을 완벽히 재현할 수 있다.

셋째 color-scheme·accent-color다. accent-color 한 줄로 input type=checkbox·radio·range·progress의 브랜드 색상이 모두 통일된다. 직접 만든 체크박스를 만드는 수백 줄의 노력이 CSS 한 줄로 끝난다.

이 세 기법만 알아도 디자인 시스템 90% 이상의 시각적 요구사항을 native 위에서 충족시킬 수 있다. "디자인 vs 접근성"의 이분법이 2026년에는 사라진 것이 가장 큰 변화다.

사례 분석 - GitHub·Stripe·Linear가 native를 쓰는 이유

이론은 충분하다. 실제로 사용자 경험 1위 사업자들이 어떻게 native를 쓰는지 본다.

GitHub

GitHub은 2020년경부터 디자인 시스템 Primer를 정비하면서 native HTML을 1순위로 두는 정책을 명문화했다. details/summary로 만든 사이드바 토글, dialog로 만든 PR 모달, native select 위에 얹은 검색 가능 드롭다운이 대표적이다. 그 결과 GitHub의 페이지 무게는 같은 규모 SaaS 평균보다 30~40% 가볍고, 키보드 단축키는 모든 페이지에서 자연스럽게 동작한다.

Stripe

Stripe Dashboard는 native form validation·input type=number·input type=email을 적극 사용한다. 결제 페이지의 카드 입력 영역만 PCI-DSS 요구사항으로 iframe 격리되어 있고, 그 외 영역은 거의 모두 native다. 그 결과 Stripe Dashboard는 로딩 속도와 접근성 점수 모두에서 SaaS 평균을 압도한다.

Linear

Linear는 그 자체로 디자인 시스템 영감을 주는 사이트지만, 내부적으로는 details·dialog·native form을 많이 쓴다. 키보드 단축키가 어디서나 자연스럽게 동작하는 이유 중 하나가 native 위에 얹힌 구조이기 때문이다. 디자인이 멋있다고 native를 포기할 필요가 없다는 가장 좋은 증거다.

세 회사의 공통점은 "디자인 vs native"의 이분법을 거부한다는 점이다. native 위에 디자인을 얹는 게 디자인을 처음부터 다시 만드는 것보다 더 빠르고 더 안정적이라는 합의가 사내에 정착되어 있다. 이 합의는 시니어 엔지니어와 시니어 디자이너의 신뢰 관계에서만 가능하다.

React·Vue 생태계의 잘못된 관행 - shadcn·MUI도 무조건 신뢰하지 마라

React·Vue 생태계의 컴포넌트 라이브러리는 두 종류다. 하나는 native 위에 얹는 형태(Radix UI·Headless UI 일부, Ariakit), 다른 하나는 div로 처음부터 만든 형태(많은 디자인 시스템). 사용 전에 어느 쪽인지 반드시 확인해야 한다.

shadcn/ui는 Radix UI를 기반으로 하므로 대체로 좋은 접근성 출발점을 제공한다. 그러나 그 안의 일부 컴포넌트(특히 Select·Dropdown Menu)는 div로 재구현되어 있어 native select가 아니다. 모바일에서 OS 휠 피커가 안 뜨고, 키보드 동작도 약간 다르다. 사용 전에 어떤 컴포넌트가 어떤 요소를 기반으로 하는지 확인하는 습관이 필요하다.

MUI도 마찬가지다. MUI의 Select는 div 기반이고, 모바일에서 native와 다르게 동작한다. MUI의 DatePicker는 50KB+의 추가 번들이다. 단순 케이스라면 native select·input type=date를 쓰는 게 더 가볍고 빠르다.

본인이 자주 쓰는 룰은 단순하다. "Radix·Ariakit·Headless UI 같은 unstyled 라이브러리가 필요한 경우에만 라이브러리, 그 외에는 native"이다. 디자인 시스템 컴포넌트 라이브러리가 처음부터 div로 만들어진 경우, 사용 비용이 native보다 항상 비싸다.

개발자가 즉시 적용할 5가지 체크리스트

다음 5가지를 다음 PR부터 적용해 보자. 한 가지씩만 해도 즉시 효과가 있다.

  1. 모달은 dialog로 바꿔라. react-modal을 쓰던 곳을 native dialog + showModal()로 교체한다. 평균 15KB 번들 절약 + 키보드 동작 자동화.
  2. 아코디언은 details/summary로 바꿔라. 자체 구현 토글 컴포넌트를 모두 제거한다. 평균 200~300줄 JS 제거.
  3. 날짜 입력은 input type=date로 바꿔라. 모바일이 70% 이상이면 거의 항상 더 나은 사용성. react-datepicker 40KB 제거.
  4. 폼 validation은 native required·pattern을 1순위로 두라. JS validation은 보완용으로만 둔다.
  5. 새 기능 PR에서 div+role보다 먼저 native 요소가 있는지 검색하라. "dropdown" 키워드로 MDN을 먼저 검색하는 습관이 1년 후 큰 차이를 만든다.

이 5가지는 모두 PR 단위로 즉시 적용 가능하고, 즉시 가시적 효과(번들 사이즈·Lighthouse 점수·접근성 점수)를 낸다. 디자이너와의 합의가 필요한 영역이 아니라 개발자가 단독으로 결정할 수 있는 영역이다.

한국 디자이너·기획자와의 협상 방법

한국 IT 조직에서 가장 자주 발생하는 갈등은 "디자인 시스템이 정한 룩을 native가 못 따라간다"는 디자이너 측 의견이다. 이때 본인이 실무에서 쓰는 협상 패턴 3가지를 공유한다.

첫째 "기능별 분리 협상"이다. 모든 컴포넌트를 한꺼번에 native로 전환하지 말고, 영향이 큰 5개(모달·드롭다운·아코디언·날짜·파일)부터 native로 전환하고 나머지는 디자인 시스템 유지를 약속한다. 단계적 협상이 정면 충돌보다 항상 더 빠르다.

둘째 "숫자로 말하기"다. 디자인 변경의 비용을 KB·ms·접근성 점수로 환산한다. "react-datepicker를 native input type=date로 바꾸면 모바일에서 700ms 빨라지고 번들이 40KB 줄어듭니다"는 문장은 디자이너가 거부하기 어렵다. "그냥 native가 나아요"보다 100배 효과가 크다.

셋째 "디자이너에게 통제권 주기"다. CSS 변수로 디자인 토큰을 노출하고, 디자이너가 색상·간격·폰트를 직접 조정할 수 있게 만든다. 디자이너가 결과물을 통제할 수 있으면 native에 대한 거부감이 크게 줄어든다. 이게 본인이 본 가장 효과적인 협상 방법이다.

한국 기획자에게는 "사용자 70%가 모바일이고, 그 사용자들은 OS 피커를 더 잘 쓴다"는 사용성 데이터를 가장 먼저 제시한다. UX 데이터가 디자인 의사 결정을 이긴다는 사실은 한국 기획 조직에서도 점점 명확해지고 있다.

결론과 즉시 실행 가능한 3가지

본문 핵심을 한 문장으로 정리한다. 2026년의 웹 UI는 "직접 만들기"의 시대를 끝내고 "native 위에 얹기"의 시대로 이동한다. 브라우저는 그동안 부족했던 기능들을 빠르게 채우고 있고, CSS는 native를 디자인하는 모든 도구를 제공한다. 직접 만드는 비용은 시간·번들·접근성·유지보수 네 측면 모두에서 점점 더 비싸진다. 반면 native의 표준은 깨지지 않고 영원히 작동한다.

즉시 실행 가능한 행동 세 가지를 정리한다.

  1. 다음 PR에서 modal 1개를 dialog로 교체하라. 한 시간 안에 완료되고, 즉시 번들 15KB 절감 + 접근성 점수 상승의 결과를 본다.
  2. 자사 SPA의 컴포넌트 라이브러리 사용 내역을 감사하라. 어떤 컴포넌트가 native로 대체 가능한지 1주일 안에 목록을 만든다. 이 목록 자체가 향후 1년의 개선 로드맵이 된다.
  3. 디자인 시스템 회의에서 "native 1순위" 정책을 제안하라. 디자이너에게 통제권(CSS 변수)을 주는 조건으로 협상하면 통과 확률이 높다. 정책이 정착되면 매년 200~500인시의 절감이 자동으로 발생한다.

관련 글로 소프트웨어는 헤드리스가 되는가 - AI 에이전트 시대 UI의 종말과 API 우선 설계 2026, 제품의 시대에서 두뇌의 시대로 - 2026 새 비즈니스 패러다임을 함께 읽으면 UI 영역과 SaaS 산업 전반의 변화를 함께 볼 수 있다.
