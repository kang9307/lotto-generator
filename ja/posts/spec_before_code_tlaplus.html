仕様を先に書くと何が捕まるのか - モデル検査器がなめる範囲、状態爆発という請求書、コードまで残る距離

テストが捕まえられないのではなく、その順序を作り出す確率が低いのである

2026-09-10 開発・インフラ

証明支援系の隣にモデル検査器を並べる比喩がある。数学者に証明を機械で検査する道具があるように、開発者にも設計を機械で検査する道具があるという言い方だ。この比喩は役に立つ。ただし半分しか当たっていない。二つの道具が検査する対象が互いに違うからである。

比喩がよく合う側はこうだ。型検査器も単体テストも通ったプログラムが、並行に走った途端に壊れることはよくある。それぞれ自分の中では順序を守る二つの仕事があっても、その二つが混ざる方法の数は人が手で数えられる規模ではない。開発者が選んだいくつかの筋書きは、その数の前では標本にすぎない。標本を増やす代わりに全部をなめる道具があるなら、その場所で使う値打ちがある。

比喩がずれる側は二つある。第一に、全部をなめることには請求書が付く。検査費用がモデルの大きさに対して指数的にかかる。だから実務で回すのは常に極めて小さな模型であり、小さな模型に欠陥が無いことは大きなシステムに欠陥が無いという意味ではない。第二に、モデル検査器が見たのは設計の模型であってコードではない。仕様が通っても、実装がその仕様に従うという保証は別に作らねばならない。

この記事には状態数や検査所要時間といった数値がない。その値はモデルの変数の個数と定数の大きさと検査器の設定によって桁ごと変わり、条件を外した数字は引用されるたびに偽になる。代わりに性質と条件と限界を書く。自分のモデルの数字は自分のモデルから出る。

きっかけ - 証明検査器の隣にモデル検査器を置く発想

数学側の道具は命題を型に置き、証明をその型の値に置く。ある値の型がある命題だという言い方が、そのままその値がその命題の証明だという言い方になるように言語を組んである。任意の対象に対して証拠を作り出す関数が正しく構成されているかを検査する方式で動き、だから証明がコンパイルされるという表現が成り立つ。

開発側でその位置を占めるのが形式仕様言語とモデル検査器だ。ここでの検査対象は証明ではなく状態機械である。システムが取りうる状態を変数として書き、どの状態からどの状態へ移れるかを関係として書く。すると検査器が初期状態から出発してその関係で到達できる状態をすべて作りながら、書いておいた条件が破れる地点があるかを探す。

この対比が有用なのはどちらも人の目ではなく機械が判定するという共通点があるからだ。そしてこの対比が危ういのは、見た目の似かよりが二つの道具の保証範囲まで同じだという印象を与えるからである。数学的証明の形式化が何を保証し何を保証しないかは形式化は証明ではないに別途まとめてある。ここで扱うのはその反対側、すなわち並行性と分散設計の状態探索である。

何を検査するのか - 実行された経路と到達可能な状態

二つの方式の違いは欠陥の難しさではない。観察の対象にある。

  • 単体テストが見るもの — テストを書いた人が選んだ入力で実際に実行された経路が一つ。スレッドが複数なら、その日その機械でたまたま取られた順序が一つ一緒に決まる。同じテストを千回回してもその千回が同じ順序で行きうる。
  • モデル検査器が見るもの — モデルが許す次の状態をすべて作りながら到達可能な状態空間をなめる。どの動作が先に起きるかを決めておかなければ両方とも起きてみる。だから人が想像しなかった割り込みが自動的に試される。
  • 両者に共通する限界 — どちらも書かれていないものは検査しない。テストは書いていない場合を知らず、モデル検査器は仕様に入れなかった遷移を知らない。後者がより危ういことは後で別に扱う。

ここでよく滑る表現がある。テストでは捕まえられない欠陥という言い方だ。正確ではない。競合から生じる欠陥もタイミングが合えばテストで表に出る。実際、断続的に赤が点く試験項目のかなりの部分がそういう欠陥である。正確な文はこちらだ。テストがその順序を作り出す確率が低い。確率が低いことと不可能なことは別の言葉であり、この差が道具を選ぶ基準を変える。

確率が低いという言い方は二つの実務的な帰結を生む。一つは再現が難しいことだ。表に出た後で同じものをもう一度作れなければ、直ったかどうかも確かめられない。もう一つは断続的な失敗が無視されることだ。回し直せば通るので、試験が不安定だという結論に流れやすい。モデル検査器が与えるのは確率を上げることではなく確率を無くすことである。モデルの中で可能な順序なら必ず出会う。

順序の場合の数を数えると - 184,756 という数字が語ること

それぞれ十段階からなる仕事が二つあるとする。仕事の中での順序は守られる。つまり A の三番目の段階は A の二番目の段階の後に来る。ところが A の段階と B の段階が互いにどう割り込むかは決まっていない。

このとき可能な実行順序の数は、二十の枠のうちどの十枠を A に与えるかという問題になる。答えは184,756 通りだ。二十の階乗を十の階乗の二乗で割った値である。状態そのものは有限で仕事も二つだけなのに、順序だけでこれだけ出る。

この数字から読むべきなのは大きさではなく増え方の形だ。仕事を三つに増やすか段階を二十に増やせば、この値は緩やかには伸びない。そして実際のシステムにはここに加えて部分的な失敗が入ってくる。各段階が成功したり失敗したりでき、失敗の後に再試行が付き、再試行が重複を作りうる。順序の場合の数に失敗地点の場合の数が掛かる。

人が筋書きを選ぶというのは、この掛け算の結果から五つ六つをつまむ作業だ。選ぶ目が良ければよく当て悪ければ当てられないのだが、よく当てたかどうかを判定する方法がないことが問題である。網羅率の数値はコードの行が実行されたかを語るだけで、順序がなめられたかは語らない。

だから捕まる欠陥の種類が分かれる

二つの方式がよく捕まえる欠陥を分けて書けば線がはっきりする。下の表でどちらの側にも不可能と書いていない点に注意する値打ちがある。分かれるのは確率と費用だ。

欠陥の種類 テストで捕まるか モデル検査で捕まるか なぜそうなるか
計算式の誤り(境界値、丸め、符号) よく捕まる おおむね捕まらない モデルは計算を抽象化してしまうのが普通だ。値ではなく順序を見るために作った模型だからである。
ヌル参照、型の不一致 よく捕まる 対象ではない 言語水準の問題であり仕様にはそんな概念がない。型検査器とテストの持ち場だ。
二つの仕事が資源一つを共有するときの競合 確率が低い 確実に捕まる 特定の割り込みでのみ現れる。モデル検査器はその割り込みを偶然ではなく規則にする。
再試行が重複反映を作る欠陥 確率が低い 確実に捕まる 失敗と再送の組み合わせからのみ出る。実環境でその組み合わせを作るには障害を注入するしかない。
リーダー交代の途中の書き込み消失 非常に低い モデルに遷移を入れたなら捕まる 交代と書き込みが重なる短い区間でのみ成り立つ。その遷移を仕様に書かなければ検査器も見られない。

デッドロックと停止(誰も進めない) 再現されれば捕まる 捕まる 次の状態がない状態に至ったかを検査器が直接見る。実行中は止まったのと遅いのが区別できない。
飢餓(一部だけがずっと後回し) ほぼ捕まらない 公平性を書いたなら捕まる 活性の領域だ。公平性の仮定を使わなければ判定そのものが成り立たない。
性能低下、遅延の増加 測定で捕まる 対象ではない モデルには時間がない。順序はあっても掛かる時間はない。
要求そのものが間違っている 捕まらない 捕まらない どちらも書いておいたものを検査する。書いたものが間違っていれば通過は何も意味しない。

表の最後の行が最も大事だ。二つの道具はどちらも人が書いたものを検査する。違うのは書く言語が違い、だから書くときに人がすることになる思考の種類が違うという点である。仕様を書いている途中で答えが出てしまい、検査器を回す必要が無くなることも少なくない。

例を一つ - 接続一つを二つの仕事が分け合うとき

具体的な形が必要だ。非同期の仕事が二つあって接続一つを一緒に使い、各仕事が終わるときに後始末としてその接続を閉じる構成を考える。ストリーム系のライブラリで書けば次のような形になる。

// 欠陥のある配置 - 後始末が各仕事に付いている
merge(
  jobA$.pipe(finalize(() => resource.close())),
  jobB$.pipe(finalize(() => resource.close())),
).subscribe();

// 直した配置 - 接続の寿命を外側の購読に合わせる
merge(jobA$, jobB$).pipe(
  finalize(() => resource.close()),
).subscribe();

前の配置で何が起きるかは順序を一つ指せば出る。A が先に終われば A の後始末が走って接続を閉じ、まだ動いている B が閉じた接続を使う。逆に B が先に終わっても対称に同じことが起きる。二つがほぼ同時に終われば何も起きない。

この欠陥が試験でうまく引っ掛からない理由がここにある。開発環境では二つの仕事の長さが似ているか、一方があまりに短くて残りが終わった後に後始末が走る側へ偶然に配置されやすい。二つの仕事の長さの差が開く条件が実トラフィックで初めて作られる。そしてそのときの症状は後始末のコードではなく接続を使う側に現れる。

直した配置がしていることは単純だ。資源の寿命を所有者へ移す。二つの仕事のどちらも接続の主ではなく、二つを束ねた外側の購読が主である。後始末をその位置へ上げれば、最後の仕事が終わった後にだけ接続が閉じる。この訂正はコードを減らしながら欠陥を無くすという点で珍しい部類に入る。

仕様を書く順序 - 変数、初期状態、次状態関係

同じ状況をモデルへ移すと書く順序が決まっている。状態変数を選び、初期状態を書き、次の状態へ移る関係を書き、守られるべき条件を書く。この四段階のほかに何かを書く場所はない。

---- MODULE SharedConnection ----
VARIABLES connection, aRunning, bRunning
vars == <<connection, aRunning, bRunning>>

Init == /\ connection = "open"
        /\ aRunning   = TRUE
        /\ bRunning   = TRUE

\* A が終わりながら自分で接続を閉じる - 欠陥のある設計
FinishA == /\ aRunning
           /\ aRunning'   = FALSE
           /\ connection' = "closed"
           /\ UNCHANGED bRunning

FinishB == /\ bRunning
           /\ bRunning'   = FALSE
           /\ connection' = "closed"
           /\ UNCHANGED aRunning

Next == FinishA \/ FinishB
Spec == Init /\ [][Next]_vars

\* 不変式 - まだ動いている仕事があれば接続は開いていなければならない
Safe == (aRunning \/ bRunning) => connection = "open"
====

読み方はこうだ。プライムの付いた名前は次の状態での値である。aRunning' = FALSE は代入ではなく、次の状態が満たすべき条件を書いたものだ。UNCHANGED はその変数がそのままだという意味で、これを抜かすと検査器がその変数を任意の値に変えてみる。

Next が二つの動作の選択として書かれている点が核心だ。どちらが先かを書いていないので検査器が二つの枝を両方とも踏む。プログラムなら実行系が一つを選んでくれるが、仕様では選ばなかったものがそのまま残って探索の枝になる。

回すのに必要なのは、検査する対象と検査する条件を書いた設定ファイル一つだ。

SPECIFICATION Spec
INVARIANT Safe
CHECK_DEADLOCK FALSE

この模型で検査器は Safe が破れる状態を見つける。A が終わって接続が閉じたのに B はまだ動いている状態だ。そしてその状態に至る経路を反例として吐く。反例が出ることがこの方式の実質的な値打ちである。条件が破れたという通知だけでは直せず、どの順序で行ったら破れたのかがあって初めて直せる。

不変式と活性 - 常に真といつか真

書ける条件は二種類ある。この区別がぼやけると、仕様を書いていて検査器がなぜ通すのか分からなくなる。

区分 不変式(安全性) 活性
言葉にすると 悪いことが起きない 良いことがいつか起きる
判定の単位 状態一つ見ればよい 状態の列全体を見る必要がある
例文 リーダーが同時に二つ存在しない 要求はいつか応答を受け取る
反例の形 条件が破れた状態とそこまでの経路 良いことが永遠に後回しになる無限の繰り返し
設定ファイルでの置き場所 不変式の項目 性質の項目
追加で必要なもの ない 公平性の仮定が事実上必須である
検査の費用 相対的に安い はるかに高い
縮約手法との相性 対称性の縮約を併用できる 対称性の縮約を併用しにくい

不変式は状態一つを置いて真か偽かを答えられる文だ。先の例で Safe がそれである。動いている仕事があるかと接続が開いているか、二つの値だけ見れば判定が終わる。だから検査器は状態を一つ作るたびにその場で検査する。

活性はそうはならない。要求がいつか応答を受け取るという文は、ある一時点の状態を見ても真偽が分かれない。まだ応答が無いことが違反なのか、少し後に来るのかを区別する方法がその状態の中に無いからだ。判定するには状態の列を最後まで見る必要があり、無限に続く列まで扱わねばならない。

実務でこの区別を落とすと起きることがある。不変式だけ書いておいてシステムが進むことまで検査したと思い込むことだ。何もしないシステムはたいていの不変式を簡単に満たす。何もしなければ悪いことも起きない。だから安全性だけ通った設計は止まっていても合格である。

公平性を書かなければ活性はほぼ必ず破れる

仕様言語は基本的に最悪を仮定する。ある動作が今可能であっても永遠に起きないことがありうると見る。この仮定の下ではいつか何かになるという文がほぼ全部偽になる。誰も何もしない実行が常に許されるからだ。

だから活性を検査するには公平性の仮定を仕様に付けねばならない。付け方は二段階だ。

\* 公平性を付けた仕様 - 回れる動作はいつか回る
FairSpec == Spec /\ WF_vars(Next)

Done     == /\ ~aRunning
            /\ ~bRunning

\* 活性 - 二つの仕事が終われば接続はいつか閉じる
Liveness == <>(Done /\ connection = "closed")

ここで WF は弱い公平性だ。ある動作が可能な状態として居続けるならいつかは起きるという仮定である。強い公平性は条件がもっときつい。ずっとではなくても無限にしばしば可能になりさえすればいつか起きると見る。資源を巡って争う模型では二つの差が結果を分ける。弱い公平性だけでは飢餓が許され、強い公平性では許されない実行がある。

公平性の仮定は無料ではない。仮定を入れた瞬間、その仮定が実際に成り立つかをシステム側で負うことになる。スケジューラがあるスレッドを永遠に後回しにしないこと、再試行が無限に失敗し続けないことは、コードではなく運用環境が担保する性質だ。仕様で気楽に書いた仮定が現場で成り立たなければ、通った活性は仮定が真である世界でのみ真である。

代償は状態爆発である

ここがこの方式の中心的な制約だ。到達可能な状態を漏れなくなめるということはその状態を全部作ってどこかに保管するという意味である。すでに見た状態を再び広げないためには見たものを覚えねばならず、覚えるべきものの個数が費用を決める。

そしてその個数はモデルの大きさに対して指数的に増える。変数が一つ増えればその変数が取りうる値の数だけ掛かり、参加者が一つ増えれば参加者ごとの状態が掛かる。ノードを三つから四つへ上げるような小さな変更が状態数を桁ごと変える。これが状態爆発であり、緩和手法はあっても原理的に無くすことはできない。

緩和手法の側に何があるかを書けばこうだ。

  • モデルを小さく作る — 最もよく使う方法だ。ノード三つ、値二つ、メッセージ列の長さ二つのように、欠陥が現れる最小の規模へ縮める。欠陥の構造が参加者数に依存しない場合が多いという経験に寄りかかった選択である。
  • 対称性を宣言する — 互いに区別する必要のない参加者たちを一まとまりにして、名前だけ変わった状態を同じものとして扱わせる。状態数を大きく減らすが活性の検査とは併用しにくい。
  • 抽象度を上げる — 値そのものではなく値の区別の有無だけ残す。整数の代わりに互いに異なる二つの元を使い、本体の代わりに標識だけ残す式だ。検査したい性質に値の大きさが関与しないときにのみ成り立つ。
  • 範囲を切っておく — 再試行の回数や列の長さに上限を掛けて無限の拡大を防ぐ。この上限が結論の有効範囲をそのまま決めるという点を一緒に書いておかねばならない。

これらの手法の共通点は費用を減らす方法が全部モデルを減らす方法だということである。検査器を速くするのではなく検査するものを小さくする。だから節約した費用の分だけ結論の適用範囲も一緒に縮む。この交換が次節の内容だ。

小さなモデルに無いことは大きなシステムに無いという意味ではない

検査器が違反を見つけたなら、その反例は確実だ。モデルが許した順序の中に実際にそういうものがある。反例には条件が付かない。だからこの方式は欠陥を見つける道具としては非常に強い。

逆に検査器が何も見つけられなかったときの文には条件が三つ付く。

  • その大きさの中で — ノードを三つに置いて回したなら結論はノード三つの模型に関するものだ。四つで初めて現れる欠陥は検査対象ではなかった。参加者の数が増えて初めて成り立つ欠陥が実際にあるので、この条件は形式的な但し書きではない。
  • その仮定の中で — メッセージが失われないと書いたなら失われる世界は検査されていない。公平性を入れたならその公平性が成り立つ実行だけが検査された。仮定はモデルを小さくする最も強力な手段であり、だから最もよく忘れられる。
  • 書いておいた遷移の中で — これが最も危うい。重要な遷移を仕様で落とすと、検査器はその遷移が無いシステムを検査したことになる。通過が出て、その通過が何も意味しない。ところが結果の画面だけ見ると正常な通過と区別できない。

三番目の項目は、バックアップが成功したというログと復元ができるという事実が別の命題であるのと同じ構造だ。成功したバックアップが嘘をつく場所で扱ったものと形が重なる。緑の意味は、その緑が何を検査したかに全面的に懸かっている。

だから仕様を書く側が持つべき習慣が一つ生まれる。わざと欠陥を入れてみて検査器が捕まえるか見る。後始末を移す前の配置で回したとき反例が出ねばならず、出ないならモデルがその欠陥を表現できない状態だという意味だ。通過だけ確かめた模型は、検査されたことのない検査器である。

仕様が通っても実装が正しい保証は別に作る

ここが証明支援系との対比が分かれる場所だ。数学側では形式化された証明そのものが検査対象である。対象と検査物が同じ物だ。残る隔たりは定理の陳述が元々言おうとした命題を正しく写したかの一つだけである。

モデル検査はそうではない。検査対象は人が手で書いた設計の模型であり、実行されるのはそれとは別のコードだ。だから隔たりが二つに増える。

  • 上側の隔たり — 仕様が実際のシステムを正しく写したか。落とした遷移、強すぎる仮定、実際には原子的でないのに一段階として書いた動作がここに入る。
  • 下側の隔たり — コードがその仕様に従うか。仕様に無い近道、仕様で一つだった動作がコードで二つに分かれた場所、ライブラリが裏でしていることがここに入る。

きっかけとなった記事もこの点は明確に書いてある。検査器の結果は設定した有限モデルと仮定の中でのみ有効であり、重要な遷移を落としたモデルは通過した後でも実際の欠陥を見逃し、モデルの設計が実際のコードとしてきちんと実装されたかは別途見ねばならないという記述がある。無限の範囲に対する一般的な証明が必要ならモデル検査器ではなく証明の道具へ移らねばならないことも一緒に書かれている。

ただし原文はその別途の検証が何で成り立つのかまでは広げていない。だからその場所を要件として整理すると次節になる。

隔たりを狭める三つの要件

仕様とコードを結ぶ方法は三筋ある。三つとも完全な保証ではなく、三つを重ねるほど隔たりが狭まる構造だ。

第一に、詳細化の関係を書く

抽象的な仕様と具体的な仕様の両方を書き、具体側のすべての振る舞いが抽象側の振る舞いへ写ることを検査する方式である。抽象仕様で一歩だったものが具体仕様で数歩になっても、外から見える結果が同じなら成り立つ。この方式の値打ちは中間段階を一つ置けるところにある。設計とコードの間が遠すぎるなら、その間に実装に近い仕様を一つ挟んで二度検査する。

限界ははっきりしている。具体仕様も依然として仕様だ。コードではない。詳細化をいくら緻密にしても最後の一枠、すなわち具体仕様と実際のコードの間はこの方法では閉じない。

第二に、実行を計測してモデルと突き合わせる

動いているコードから状態の変化を痕跡として残し、その痕跡が仕様の許す実行かを検査する方式だ。方向が逆である点が重要である。前のものは仕様から降り、これはコードから上がる。実際に起きたことだけを扱うので到達可能な全部をなめることはできないが、代わりに本物のコードを対象にする。

ここで要求されるのは計測の品質だ。仕様の状態変数に対応する値を同じ時点で原子的に取らねば突き合わせが成り立たない。互いに異なる時点で取った値を一つの状態として束ねると、実際には無かった状態が作られ、その状態が違反として出る。ログを増やすことと計測を整えることは別の仕事である。

第三に、仕様から試験を取り出す

モデル検査器が作った反例や探索経路を試験の筋書きへ移してコードに与える方式だ。仕様が見つけた順序をコードで強制的に再現するので、先に述べた確率が低いという問題を正面から解く。偶然その順序が出るのを待つ代わりにその順序を作る。

引っ掛かる地点は再現の仕掛けだ。特定の割り込みをコードで強制するには実行地点を押さえられねばならず、これが可能な構造と不可能な構造が分かれる。スレッド間の順序を試験で統制できるように設計を変えねばならない場合も生じる。つまりこの方法はコード側に要求を作る。

効く場所と効かない場所

分ける基準はシステムの難しさではない。良い状態と悪い状態を一文で書けるかである。書けるなら検査対象になり、書けないなら模型をどれだけうまく作っても判定が出ない。

対象 不変式が言葉で書けるか 値打ち 理由
合意とリーダー選出 書ける(リーダーは同時に二つ存在しない) 高い 欠陥が交代の区間でのみ現れ、その区間を試験で作るのが非常に難しい。
複製と確定の規則 書ける(確定した項目は失われない) 高い 部分的な失敗と再試行の組み合わせが多く、消失が静かに起きる。
リースと排他アクセス 書ける(リースを持つ側だけが書く) 高い 失効と更新が重なる短い区間が問題であり、時計まで絡む。
トランザクションと分離 書ける(許されない読み取り結果がない) 高い 許容の可否が定義で決まっており模型へ移しやすい。
キャッシュ無効化 書ける(書き込み後の読み取りは古い値を見ない) 高い 書き込みと無効化の相対順序だけが問題なので模型が小さく済む。
重複要求の抑止 書ける(同じ要求は二度反映されない) 高い 再試行が作る欠陥なので実行試験で再現しにくい。
取り消しと完了の競合 書ける(取り消された仕事の結果は反映されない) 高い 二つが重なる瞬間が狭く、コードを見ただけでは重なることが見えない。
画面の流れと使いやすさ 書けない 低い 良い状態の定義が人の判断だ。形式化する対象がない。
性能と容量 書けない 低い モデルに時間がない。順序はあっても掛かる時間はない。
人が挟まる運用手順 部分的にのみ 低い 人の行動を遷移として書くことはできるが、書いた通りにするという保証が模型の外にある。

表の前の七行に共通する性質がある。欠陥が現れる条件が狭く、現れたときに静かだということである。大きな音を立てて死ぬ欠陥はどのみち見つかる。値が少し狂ったまま回り続ける欠陥が長く残り、そういう欠陥が主に順序から出る。資源一つを複数で分け合うときに生じる停止の構造はパイプバッファが満杯になって起きるデッドロックの側に実物が一つある。

もう一つ付け足すことがある。外からは分散システムに見えないのに実際はそういう場所が多い。設定一つが複数の端末でそれぞれ変わり後で合わさる構造がそれだ。トグル一つが分散システムになる話がその例である。同時に書かれて後で合わさる値があるなら、その場所はすでに順序の問題を抱えている。

始める順序 - 全体を模型化しない

失敗する導入の形はほぼ一つだ。システム全体を仕様へ移そうとすることである。その試みは状態爆発の前に人の時間で先に終わる。きっかけとなった記事の勧めも同じ方向で、全体を模型化せず特定の問題一つに集中せよというものだ。共有資源の解放、重複要求の抑止、取り消しと完了の競合といったものがその例として書かれている。

順序を整理すると五段階だ。道具の使い方ではなく判断の順序である。

  • 第一に、一文を選ぶ。このシステムで絶対に起きてはならないこと一つを文として書く。書けないならモデル検査の対象ではなく、別の方法を探すほうが速い。
  • 第二に、その文に関与する変数だけ残す。文に出てこないものは模型に入れない。本体データ、待ち時間の値、記録はたいていここで抜ける。残すか迷うなら抜いたまま先に回す。
  • 第三に、欠陥のある設計で先に回す。反例が出るのを見てから直した設計へ移る。最初から直した設計を入れると、その通過が何を意味するのか分からない。
  • 第四に、大きさを一つずつ上げてみる。参加者を二つから三つへ、三つから四つへ上げながら、どこで検査が終わらなくなるかを見る。その地点がこのモデルで語れる範囲の上限だ。
  • 第五に、結論に条件を付けて書く。どの大きさで、どんな仮定の下で、どの遷移の集合で検査したかを仕様と同じ場所に残す。この三行が無ければ次の人がその通過を無制限に読む。

第四段階が実際には最も多くを教えてくれる。大きさを上げていくとどの変数が状態数を支配するかが見え、その変数を抽象化できるかが次の判断になる。検査が終わらないのは失敗ではなく、モデルがその場所で何を要求しているかについての情報だ。

最後に整理するとこうなる。形式仕様が与えるのは確実な欠陥の発見と条件付きの無欠陥である。前者には但し書きが付かず後者には三つ付く。そしてどちらであれコードがその仕様に従うことは依然として別の命題だ。この三つを一緒に書いておけば、仕様は設計文書の中では珍しく長く使い道が残る物になる。行動を文として書くという発想そのものがどこまで押し進められるかは行動を仕様として書くという発想の実体に別の角度でまとめてある。

確かめられなかったこと

  • きっかけとなった記事の検査器の実行結果 — 原文には仕様ファイルと設定ファイルと実行命令が載っているが、検査器が吐いた反例の出力や探索した状態数は載っていない。本文もそれ以上を主張していない。
  • 状態数と検査時間の具体的な数値 — モデルの大きさごとの状態数と所要時間は変数の構成と実行環境によって桁ごと変わる。一般値として示す根拠が無く、増え方の性質までにとどめた。
  • 証明の道具側の実際の要件 — 有限モデルを越えて一般的な証明が必要なときに使う証明系があるというところまでが原文の記述範囲だ。その道具がどんな後段の証明器を使い人の手がどれだけ掛かるかはこの記事の範囲外に置いた。
  • 記号実行方式の代替検査器 — 状態を一つずつ広げる代わりに制約として扱う系統の検査器があり状態爆発に対する性質が異なると知られているが、成立条件を突き合わせていないので本文に入れていない。
  • 産業適用事例の個別文書 — 公式サイトに産業適用をまとめたページがあり、プロセッサのキャッシュ一貫性プロトコル、クラウドのサービス、調整サービスなどの項目が並んでいる。ただし大半が学会のアーカイブや発表資料であり個別の主張までは突き合わせていない。そのため本文に組織名や成果の数値を書いていない。
  • 痕跡検証の道具の成熟度 — 実行の痕跡を仕様と突き合わせる方式は要件としては明確だが、実際に使える道具がどの言語とランタイムで整っているかは突き合わせていない。本文はその方式が要求する条件までにとどめた。
  • 模型の下書き自動生成の実効 — 原文は試験の下書き作成の費用が下がるように仕様作成もそうなりうるという見通しを添える。その見通しを裏づける実測は原文に無く、本文も見通しとして扱っていない。
