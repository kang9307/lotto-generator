GitHub Stacked Pull Requests in Public Preview - What Changes When You Split a Large Change Into Layers

Building the layers is easy. Re-aligning the ones above when the bottom moves is the hard part

2026-08-01 Development/Infrastructure

Opening scene: review stalls in front of a forty-file pull request

One pull request, forty files. A schema change, the query layer that uses that schema, the API endpoint that calls that layer, and the config cleanup someone did while they were in there. All one block. A reviewer opened it and closed it again. Three days, no approval. Nudged, they reply that they will look at it tomorrow. Meanwhile the author starts stacking the next task on top of the same branch. At this point the problem is not the reviewer's diligence, it is that the work arrived in a shape that cannot be reviewed.

On 30 July 2026 GitHub opened stacked pull requests in public preview: a way to pile a large change into layers and have each layer reviewed on its own. But this article is not interested in the fact that a feature shipped. Chaining branches has always been possible with plain local git, and I build one below to show it. What was announced is not the concept but the fact that the platform now carries the repetitive work of keeping that concept intact.

So the question here is a single one. How much of the cost of splitting a large change does tooling actually remove? The real difficulty of stacking is not creating the layers. It is re-aligning everything above every time the bottom moves. I ran exactly that work in local git so you can see, in output, where it hurts and what gets automated.

Environment. Every git output below was actually executed on Windows 10 Pro (10.0.19045) with git 2.48.1.windows.1 and GNU bash 5.2.37 (MSYS2/MinGW64). Commands were saved to files and run, not passed through heredocs, and the example repository was created fresh in a temporary directory. All branch and file names are invented for the example.

What this article does not cover. How to open a pull request and the basics of reviewing are in Pull Requests and Code Review. Whether capping the number of open pull requests shortens the queue is treated as a queueing problem, with a simulation, in Caps and Queue Dynamics. This article only looks at how to split one item. Branching strategy itself lives in Branch Strategy.

1. What was announced - only the facts I verified

Below is only what I confirmed by opening the official changelog and documentation directly. I did not settle any question about the feature on the basis of summary articles or community posts.

  • Date and status. The GitHub changelog entry dated 30 July 2026 announced the public preview of stacked pull requests. The rollout to all repositories is described as happening over the coming days
  • Definition. The changelog says stacked pull requests break large changes into small, reviewable pull requests, and describes them as an ordered series in which each pull request represents a focused layer of the change
  • Structural rule. The documentation says the bottom pull request targets the default branch and each one above it targets the branch below. It states the principle that if code in one layer depends on code in another, the dependency must be in the same branch or a lower one
  • Where you can work with them. github.com, the GitHub CLI and the mobile app. The CLI extension installs with gh extension install github/gh-stack, and the subcommands that appear in the documentation are gh stack init, gh stack add, gh stack submit, gh stack rebase and gh stack push
  • Creating them on the web. The documentation also describes setting each pull request's base branch to the branch of the one below, then choosing the create-stack option
  • Constraints. All branches must live in the same repository and cross-fork stacks are not supported. They are not supported in GitHub Desktop. Auto-merge is not supported. A fully linear history is required between the stack branches
  • Merge queue. The documentation says stacks fully support merge queues and enter the queue in the correct order, and that to keep a stack together the merge group is allowed to exceed its configured maximum size by up to 50 percent. If the stack is too large even for that buffer it is split across consecutive merge groups. The changelog notes that merge queue support rolls out over the coming weeks, so this part may arrive at different times per repository

Preview status, stated plainly. The documentation carries the line that the feature is in public preview and subject to change. Everything here was verified as of 1 August 2026. The interface, the subcommand names and the list of constraints can all move before general availability, so re-read the primary sources before deciding to adopt.

What I did not open. The community discussion thread, the roadmap issue, the gh-stack repository page, the quickstart guide and the organisation rollout tutorial appeared in search results but I did not open them. Anything found only in those documents is therefore absent here. The reference list at the end contains only the five pages I actually opened and read.

2. Why large pull requests fail - structurally, not statistically

Everyone says large pull requests do not get reviewed, but explaining why with statistics usually means repeating somebody else's numbers. Here I use no numbers at all and look only at structure. A review is three activities: reading, holding context in your head, and judging. As a pull request grows, those three do not grow at the same rate.

  • Reading grows linearly. Twice the files, roughly twice the reading time. That part is survivable
  • The context you must hold grows faster. By the fortieth file the reviewer needs to remember what the previous thirty-nine changed. Checking whether a function signature really did change means scrolling back to find it, and those round trips multiply with file count
  • The unit of judgement grows in the opposite direction. Approval is only possible per pull request. If thirty-nine of the forty are perfect and one is dubious, all of it waits. The good parts are held hostage by the bad one
  • Every revision means re-reading everything. When the author pushes a fix, the reviewer has to work out what changed. The larger the pull request the more that re-verification costs, which is why the second review is always looser
  • The undo unit equals the review unit. If something breaks after release, the smallest thing you can revert is that whole pull request. The API endpoint disappears along with the schema change
  • CI behaves as all-or-nothing. One lint error in one of forty files turns the whole pipeline red. The fact that the other thirty-nine passed carries no weight

Put plainly, the problem with a large pull request is that the minimum unit of review and the minimum unit of change are forced to be the same. Stacking is an attempt to pull those apart: keep the change large, but do review, approval and reverting per layer.

One thing should be stated flatly. Splitting does not increase review capacity. The total volume of change a team can absorb in a week is set by reviewer time, not by how you cut the pull requests. I covered why cap rules fail to shorten the queue in the previous article, and the same line holds here. What stacking changes is not the total, but the time per item and the possibility of partial landing.

3. What stacking is - built directly in local git

The definition is one line. Base each branch on the branch below it instead of on the trunk. Then each branch's diff excludes what the layers below already did and shows only what that layer newly does. No special tooling is involved.

$ git switch -c stack/1-db   main          # layer 1: DB connection pool config
$ git switch -c stack/2-repo stack/1-db    # layer 2: query layer (on top of layer 1)
$ git switch -c stack/3-api  stack/2-repo  # layer 3: API endpoint (on top of layer 2)

Look inside the repository built that way and this is what you get.

git version 2.48.1.windows.1 / MINGW64_NT-10.0-19045

=== 1-2. the stack as one line of history ===
* 3f0f26a (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* 50bdde2 (stack/2-repo)          feat(repo): order lookup, raise pool size
* cb5f977 (stack/1-db)            feat(db): add connection pool config

=== 1-3. what each branch points at ===
main          78b0629  chore: bootstrap trunk
stack/1-db    cb5f977  feat(db): add connection pool config
stack/2-repo  50bdde2  feat(repo): order lookup, raise pool size
stack/3-api   3f0f26a  feat(api): GET /orders/:id

Three branches pointing at three different points on one line. That is the whole of a stack. Not a fan of diverging branches but tick marks on a single line. Now look at the review unit of each layer.

=== 1-4. the REVIEW UNIT of each layer (diff vs the layer below) ===
--- base=main          head=stack/1-db
 db.yml | 3 +++
 1 file changed, 3 insertions(+)
--- base=stack/1-db    head=stack/2-repo
 db.yml  | 2 +-
 repo.py | 2 ++
 2 files changed, 3 insertions(+), 1 deletion(-)
--- base=stack/2-repo  head=stack/3-api
 api.py | 2 ++
 1 file changed, 2 insertions(+)

=== 1-5. what ONE big PR would have looked like (main..top) ===
 api.py  | 2 ++
 db.yml  | 3 +++
 repo.py | 2 ++
 3 files changed, 7 insertions(+)

Same work. Combined it is three files and seven added lines; layered it splits into one file, two files, one file. The example is tiny but the ratio scales. Split a forty-file change into twelve, twenty and eight and three people can look in parallel, and layer one can be approved today.

3.1 Where to cut the layers - the one thing tooling cannot do

Read the documentation's dependency principle again and the cutting rule falls out. What a layer depends on must be in the same layer or a lower one. Cutting so that this holds is the only creative part of stacking, and no tool does it for you.

  • Cut along the technical direction. Repository, then service, then controller, so that calls point upward from below. The upper knows the lower; the lower knows nothing of the upper
  • Separate preparation from the actual work. Renames, file moves, formatting passes and anything else that does not change behaviour goes into the bottom layer. That layer reads easily and gets approved fast
  • Put the feature flag at the top. If the commit that flips the switch is the last layer, everything below it can ship harmlessly first
  • Do not cut two blocks that reference each other. If A calls B and B calls A there is no order to choose. Keep them in one layer
  • Attach tests to their layer. Piling all tests into the last layer makes the CI of every layer below meaningless
  • Keep the layer count low. Every extra layer is one more thing to re-align when the bottom moves. The next section shows that cost

4. Move the bottom and everything above wobbles - rebase, conflict, undo

Here is the real cost of stacking. Say a reviewer leaves one comment on layer one: the connection pool is too small. The author adds one more commit to layer one. Watch what happens at that moment.

=== 2-1. reviewer asks the bottom layer to change: pool size 5 -> 10 ===
stack/1-db moved: cb5f977 -> 63509a2

=== 2-2. the layers above are now stale ===
* 63509a2 (HEAD -> stack/1-db)  fix(db): pool size 5 -> 10 per review
| * 3f0f26a (stack/3-api)        feat(api): GET /orders/:id
| * 50bdde2 (stack/2-repo)       feat(repo): order lookup, raise pool size
|/
* cb5f977                        feat(db): add connection pool config

The single line of history has forked. Layers two and three are still hanging off the old layer one. Leave it there and the layer-two pull request will not show the fix just made below it, and CI will run against a stale base. The upper layers have to be moved onto the new layer one.

4.1 Where moving the next layer up runs into a conflict

$ git switch stack/2-repo
$ git rebase stack/1-db
Auto-merging db.yml
CONFLICT (content): Merge conflict in db.yml
error: could not apply 50bdde2... feat(repo): order lookup, raise pool size
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
rebase exit code: 1

--- status while stopped ---
UU db.yml
A  repo.py

--- the conflicted file ---
pool:
<<<<<<< HEAD
  size: 10
=======
  size: 20
>>>>>>> 50bdde2 (feat(repo): order lookup, raise pool size)
  timeout: 30

A conflict. Why it happened is the point. Layer one changed that line from 5 to 10, and layer two was originally a commit changing the same line from 5 to 20. The rebase is trying to re-apply layer two's commit on top of the new layer one, and the line it anchors to has already moved, so it cannot decide automatically.

  • Conflicts only occur when layers touch the same line of the same file. Cut the layers cleanly along technical direction and most rebases finish silently
  • In the conflict marker the HEAD side is the new base, the layer below, and the other side is the commit being replayed, the upper layer. It feels inverted compared with an ordinary merge, which is exactly where people get it wrong
  • While stopped the repository is in an intermediate state. You can confirm it by the existence of the .git/rebase-merge directory
  • With three layers this happens at most twice. The layer count is the repeat count

4.2 How to undo - three escape hatches

There is no reason to panic at a conflict, because undoing is fully guaranteed. I actually undid it.

=== 2-4. escape hatch: abort puts everything back ===
$ git rebase --abort
after abort, stack/2-repo = 50bdde2
db.yml on stack/2-repo:
pool:
  size: 20
  timeout: 30

=== 2-9. undoing a FINISHED rebase (reflog) ===
a4f0a88 stack/3-api@{0}: rebase (finish): refs/heads/stack/3-api onto 8e137ce
3f0f26a stack/3-api@{1}: commit: feat(api): GET /orders/:id
50bdde2 stack/3-api@{2}: branch: Created from stack/2-repo

$ git reset --hard stack/3-api@{1}    # exactly back to the pre-rebase state

Keep three cases apart.

  • Still in progress: git rebase --abort. The branch returns exactly to where it started. In the output above it went back to 50bdde2 and the file content was as it had been
  • Already finished: git reflog. The pre-rebase position is sitting at @{1}. Use git reset --hard to return there
  • ORIG_HEAD serves the same purpose. It points at the position just before the rebase, so git reset --hard ORIG_HEAD is the short form. Other commands overwrite it, though, so the reflog is safer
  • An important precondition. This undo is harmless locally only. If you already force-pushed, the history someone else pulled no longer lines up. Stack branches need an agreement that only the author pushes to them

4.3 The layer above that needs its start point spelled out

Once layer two has moved, layer three is the problem. It points at the old layer two, so a plain rebase would drag the wrong commits along.

=== 2-6. layer 3 still points at the OLD layer 2 ===
layer3 does NOT contain the new layer2 -> must rebase too

=== 2-7. rebase layer 3 with --onto (old base -> new base) ===
$ git rebase --onto stack/2-repo 50bdde2 stack/3-api
Successfully rebased and updated refs/heads/stack/3-api.

=== 2-8. the stack is one line again ===
* a4f0a88 (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* 8e137ce (stack/2-repo)          feat(repo): order lookup, raise pool size
* 63509a2 (stack/1-db)            fix(db): pool size 5 -> 10 per review
* cb5f977                         feat(db): add connection pool config

The three arguments of git rebase --onto NEWBASE OLDBASE TARGET are where to, from where, and what. Note that you have to type the old layer-two hash in by hand. Five layers means four rounds of this by hand, and one wrong hash makes commits vanish or duplicate. This is where people make mistakes, and it is exactly what the tooling is aiming at.

5. Moving the whole stack at once - update-refs

Git itself has something that removes this repetition. git rebase -h describes --update-refs as updating branches that point to commits that are being rebased. I ran the same situation with and without it. The situation is the trunk moving forward, that is, somebody else's pull request landing first, which happens constantly.

=== 3-1. WITHOUT --update-refs ===
before:  main 5ea68a0   1-db 9b331dc   2-repo a08d522   3-api 6d241f4
$ git switch stack/3-api
$ git rebase main
after:   main 5ea68a0   1-db 9b331dc   2-repo a08d522   3-api 6204587

* 6204587 (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* 483c62e                        feat(repo): order lookup
* b422809                        feat(db): add connection pool config
* 5ea68a0 (main)                 chore: bump trunk
| * a08d522 (stack/2-repo)       feat(repo): order lookup
| * 9b331dc (stack/1-db)         feat(db): add connection pool config
|/
* c2562b8                        chore: bootstrap trunk

This is a stack quietly breaking. Layer three moved cleanly onto the new trunk while the layer-one and layer-two branches stayed on the old one. Push in that state and the layer-one and layer-two pull requests are reviewing old code, while the layer-three diff shows again everything the layers below already did. The point of splitting has evaporated.

=== 3-2. WITH --update-refs, same situation ===
before:  main ebfef49   1-db 7862785   2-repo d8b3ddc   3-api 79b45bc
$ git rebase --update-refs main
Rebasing (1/5)(2/5)(3/5)(4/5)(5/5)
Successfully rebased and updated refs/heads/stack/3-api.
Updated the following refs with --update-refs:
    refs/heads/stack/1-db
    refs/heads/stack/2-repo
after:   main ebfef49   1-db 469e32a   2-repo cd35dca   3-api a807932

* a807932 (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* cd35dca (stack/2-repo)          feat(repo): order lookup
* 469e32a (stack/1-db)            feat(db): add connection pool config
* ebfef49 (main)                  chore: bump trunk
* 153d615                         chore: bootstrap trunk

=== 3-3. make it the default for this repo ===
$ git config rebase.updateRefs true
plain 'git rebase main' now moves every layer   exit code: 0

The single line held and the intermediate branches moved with it. Git tells you outright which refs it updated. Set rebase.updateRefs to true and an ordinary git rebase main behaves the same way.

This section is the heart of the article. The concept of stacking was already finished in section 3; three commands build it. What remains is the manual work from section 4 - finding an old hash and feeding it to --onto - repeated once per layer. The value of tooling is not in providing the concept, it is in removing that repetition. --update-refs does that job locally, and the platform feature adds the review interface, the approval rules and the merge ordering on top. Which is why, even with tooling, deciding where to cut is still a human job.

6. Merge order - why it has to start at the bottom

The documentation states that stacked pull requests merge from the bottom, closest to the trunk, upward, and that a mid-stack pull request cannot be merged in isolation because the ones below it always merge with it. Read as a rule it looks like policy; run it locally and it turns out to be a physical constraint that falls out of how history is shaped.

=== 4-2. merge the MIDDLE first: what actually lands ===
commits layer2 would bring in:
  fc9279e feat(repo): order lookup
  6c5b822 feat(db): add connection pool config     <-- layer 1 commit rides along

$ git switch main
$ git merge --no-ff stack/2-repo

files now on main:
  README.md  app.yml  db.yml  repo.py            <-- db.yml came in too

what is LEFT in the bottom PR (main..stack/1-db):
  commits: 0
   repo.py | 2 --
  -> the bottom PR is now EMPTY

Merging only layer two carried layer one's commit into the trunk with it. Naturally: layer one's commit is already inside layer two's history. The result is that last line. The layer-one pull request has zero remaining commits.

  • Layer one landed without ever being reviewed under its own name. If you have per-pull-request approval rules, they were quietly bypassed
  • The layer-one pull request now shows no changes. The reviewer has no way of knowing what happened
  • Notice the diff came out negative. The trunk is ahead of layer one, so measured from layer one it looks as though repo.py was deleted
  • Which is why the platform blocking a solo mid-stack merge is protection, not a restriction. It merges the lower ones together to make this situation impossible

6.1 The squash-merge trap

A great many teams use squash merge by default, flattening everything into one commit to keep the trunk history tidy. But squashing produces a new commit with the same content and a different hash. I ran two cases to see how that meets a stack.

=== 4-3. bottom squash-merged, then the stack rebased (nobody edited it) ===
$ git merge --squash stack/1-db
$ git commit -m "feat(db): add connection pool config (#1)"
same content, different commit id:
  main:db.yml        c7c0b78
  stack/1-db:db.yml  c7c0b78      <-- the blob is identical

$ git switch stack/2-repo
$ git rebase main
warning: skipped previously applied commit 8fd3e84
hint: use --reapply-cherry-picks to include skipped commits
Successfully rebased and updated refs/heads/stack/2-repo.
layer 2 review unit:
 repo.py | 2 ++                                   <-- cleanly tidied up

=== 4-4. same, but the maintainer edited one line while squashing ===
$ git rebase main
Auto-merging db.yml
CONFLICT (add/add): Merge conflict in db.yml
error: could not apply 1cb43a1... feat(db): add connection pool config
  AA db.yml
pool:
<<<<<<< HEAD
  size: 8
=======
  size: 5
>>>>>>> 1cb43a1 (feat(db): add connection pool config)
  timeout: 30
rebase exit code: 1

The two results diverged. When the squash left the content untouched, git announced that it was skipping a previously applied commit and tidied up by itself, leaving layer two's review unit as a clean single repo.py. But when the maintainer changed even one line during the merge, the same file counted as newly created on both sides and produced an add/add conflict.

  • The claim that squash merge breaks stacks is only half true. If the content is identical git skips it on its own
  • What breaks it is content changing at merge time. Fixing a typo in the web editor, an auto-formatter in the pipeline, or the habit of folding release notes into the commit all land in this category
  • The fully linear history requirement in the documentation is the same story. It states directly that the condition is disturbed when changes are pushed to a lower branch or the trunk moves ahead
  • There is no way to check this other than running a stack through your team's default merge method once before adopting

7. Three approaches compared - one big PR, independent PRs, stacked PRs

The same work can be delivered three ways. None is superior; they differ in where the cost is placed.

CriterionOne big pull requestSeveral independent PRsStacked PRs
Review unitthe whole thing as one blockindependent per pull requestindependent per layer, lower content excluded
Dependency expressednone needed, it is one blockcannot be. Only prose in the descriptionwritten into the history via the base branch
Duplicate changesnoneoverlapping files appear in bothnone. Lower content is invisible above
Revertingall or nothingper pull request, order still mattersper layer, from the top down
Partial landingimpossiblepossiblepossible bottom-up only
CI costone run, full re-run on failureone per pull request, mutually independentone per layer + all above re-run when the bottom moves
Merge orderunconstrainedunconstrained, conflicts handled individuallybottom first, enforced
Author burdenlowmedium, manual conflict resolutionhigh. A rebase every time the bottom moves
Reviewer burdenvery highlow, but the whole picture is invisiblelow, plus a stack map for the whole picture
Tooling requirednonenonepossible in local git, easier with platform support

What to read out of the table is that the cost of stacked pull requests lands on the author. The reviewer's relief is paid for by the author's rebasing. Which is why a team where one person reviews their own work gains nothing, and stacking only pays where review genuinely is the bottleneck.

8. What it looks like in a real team - headcount, approval rules, release branches

No specific organisation is discussed here. I only look at three structural conditions that are common in engineering teams and how stacking meshes with each.

8.1 When there are few reviewers

  • Stacking increases the number of review items. Three layers means three notifications. With one reviewer, the same person opens it three times
  • Whether the total time drops depends on how well the layers were cut. Cut well, each layer is short and the sum falls; cut badly, re-establishing context three times makes it worse
  • One gain is certain. The lower half can be landed first. The author can continue on top of an approved lower layer, and the risk of having to revert shrinks
  • Conversely, if the single reviewer is away the entire stack stops at once. Nothing above can merge while the bottom is blocked, so the single point of failure gets stronger

8.2 When approval rules are in force

  • With required approvers or code owner rules, every layer must satisfy the rule. The documentation states that all pull requests below one must meet the requirements before it merges
  • That means as many approval events as there are layers. Two required approvers and four layers gives eight approval actions
  • So the stricter the approval policy, the more realistic it is to keep stacks to three or four layers
  • Different code owners per layer actually helps. The database owner takes layer one and the API owner layer three in parallel, and total waiting time genuinely falls. In a big pull request those two people each had to scan the same forty files
  • The documented constraint that auto-merge is not supported also bites here. Even with every approval in place, a human has to press merge

8.3 When it meets a release branch strategy

  • If the bottom of the stack targets a release branch rather than the trunk, every hotfix into that branch shakes the whole stack. --update-refs from section 5 becomes effectively mandatory
  • If a stack straddles a release freeze you end up with the lower layers in this release and the upper ones in the next. The upper layers then have to be re-based onto the next release branch, which is another rebase
  • If cherry-picking into releases is the habit, the same content, different hash problem from 6.1 reproduces exactly
  • A repository that takes fork-based contributions cannot use this at all. The documentation states plainly that cross-fork stacks are not supported
  • In practice the only workable answer is to keep a stack's lifetime shorter than the release cycle. Once layers start crossing release boundaries the management cost climbs sharply

9. The adoption call - when it pays and when it is overkill

The conclusion first. Stacking is not a tool for increasing review capacity. The total volume of change per week is still set by reviewer time. What stacking changes is review time per item and the possibility of landing the lower half first, and nothing else. Which narrows the criteria.

SituationIs stacking rightWhy
The change splits naturally along layersYesDependencies point one way, so an order exists
There is a large harmless prep step such as a rename or moveYesPulled into the bottom layer it gets approved quickly
Shipping only the lower layers still means somethingYesThe partial-landing benefit is actually realised
Code owners differ per layerYesParallel review reduces total waiting
Two blocks reference each otherNoNo order can be chosen. Keep them in one layer
There are more than five layersNoThe update cost eats the gain
The bottom layer changes dailyNoYou will be rebasing the upper layers daily
Pull requests are already about five filesNoThere is nothing to split. Only overhead is added
Contributions arrive from forksNot possibleThe documentation says it is unsupported

9.1 What plain local git can and cannot do

  • Can. Create the layers. Three lines of git switch -c UPPER LOWER and it is done
  • Can. Check each layer's review unit. git diff --stat LOWER..UPPER shows only what that layer newly did
  • Can. Move the upper layers when the bottom changes. --onto and --update-refs do this job
  • Can. Undo. --abort, the reflog, ORIG_HEAD
  • Can. Even open the pull requests. Set each one's base branch to the layer below by hand and the review interface shows exactly that layer
  • Cannot. Retarget the upper pull requests automatically once the bottom merges. Done by hand it is forgotten every time
  • Cannot. Show the reviewer where this layer sits in the whole. You are left writing a list in the description, and it goes stale immediately
  • Cannot. Enforce bottom-up merging. You end up relying on discipline, and the accident from section 6 happens
  • Cannot. Merge several layers in one action
  • In other words, those four things are precisely the gap the platform feature fills. Everything else is already in git

9.2 A checklist before adopting

  • Are your pull requests actually large? Measure file counts and days waiting first. Adopting this on small ones is a net loss
  • Is review the bottleneck, or is it deployment or QA? If it is not review, stacking fixes nothing
  • What is the team's default merge method? If it is squash, run the 6.1 test first
  • Is there an agreement that only the author pushes to stack branches? Force pushes flying about will derail the history
  • Is git 2.38 or newer? Without --update-refs the manual work remains, once per layer
  • Is there a rule keeping stacks to three or four layers?
  • Will a release branch ever sit at the bottom of a stack? If so, keep the lifetime shorter than the release cycle
  • Are there fork-based contributions? If so, that path cannot use stacks
  • Can you afford the CI cost? Every layer above re-runs when the bottom changes
  • Does the team know this is a preview? The interface and the commands can change

To close, the line this whole article holds. Stacked pull requests are a tool that lowers the cost of the repetitive work involved in splitting a large change. Nothing more and nothing less. Where to cut, what belongs at the bottom, whether this change is worth splitting at all - the tool does not make those calls for you. And once split, throughput is still set by review capacity. Adding layers does not lengthen a reviewer's day.

# Stacked PRs — Commands to Reproduce a Stack, and an Adoption Checklist

> Source: braindetox.kr — GitHub stacked pull requests in public preview
> Basis: verified on git 2.48.1.windows.1 / GNU bash 5.2.37 (MSYS2) / Windows 10 Pro
> As of 2026-08-01. Stacked PRs are in public preview; the UI and commands may change.
> Paste this file into an AI assistant and ask it to audit your repository against these criteria.

## 1. Building a stack (plain local git)

```
git switch -c stack/1-db   main          # layer 1
git switch -c stack/2-repo stack/1-db    # layer 2 sits on layer 1
git switch -c stack/3-api  stack/2-repo  # layer 3 sits on layer 2
```

Inspection commands:

```
git log --graph --oneline --decorate main..stack/3-api
git for-each-ref --format='%(refname:short) %(objectname:short)' refs/heads/
git diff --stat stack/1-db..stack/2-repo    # the review unit of that layer only
git diff --stat main..stack/3-api           # what one big PR would have shown
```

## 2. Updating the layers above after the bottom changes

```
# one layer straight above
git switch stack/2-repo
git rebase stack/1-db

# two or more layers up (name the old base explicitly)
git rebase --onto stack/2-repo OLD_HASH stack/3-api

# the whole stack in one command (git 2.38+)
git switch stack/3-api
git rebase --update-refs main

# make it the default
git config rebase.updateRefs true
```

## 3. Conflicts and undoing

```
# give up mid-rebase
git rebase --abort

# resolve and carry on
git add db.yml
git rebase --continue

# undo a rebase that already finished
git reflog stack/3-api
git reset --hard stack/3-api@{1}
git reset --hard ORIG_HEAD          # shorter form
```

- In a conflict marker the HEAD side is the new base (the layer below), the other side is the upper-layer commit being replayed
- If `.git/rebase-merge` exists you are mid-rebase
- Undoing is harmless locally only. After a force push, history someone else already pulled no longer lines up

## 4. Merge procedure

- Merge from the bottom up (the rule stated in the platform docs)
- A middle PR cannot be merged alone — everything below it always merges with it
- Force a middle merge and the bottom PR drops to zero remaining commits, meaning it landed without being reviewed as itself
- Once the bottom merges, the layer above is re-based onto the trunk
- Auto-merge is not supported (as of the preview)
- Squash-merge test: if the content is untouched git skips the commit. Change even one line while squashing and you get an add/add conflict

## 5. Three approaches compared

| Criterion | One big PR | Several independent PRs | Stacked PRs |
|---|---|---|---|
| Review unit | one whole block | independent per PR | independent per layer |
| Dependency expressed | not needed | cannot be | written into the base branch |
| Undo | all or nothing | per PR | per layer, from the top |
| Partial landing | impossible | possible | bottom-up only |
| CI cost | one run | one per PR | one per layer + all above on a bottom change |
| Merge order | unconstrained | unconstrained | bottom first, enforced |
| Author burden | low | medium | high (rebasing) |

## 6. Adoption checklist

- [ ] Is the current PR actually large (measure file count and days waiting first)
- [ ] Is review the bottleneck (if it is deploy or QA, stacking changes nothing)
- [ ] Does the change split along layer boundaries (put mutually referencing parts in one layer)
- [ ] Is there a rule keeping stacks to three or four layers
- [ ] Is squash the team default merge method (if so, test it first)
- [ ] Is there an agreement that only the author pushes to stack branches
- [ ] Is git 2.38 or newer available (for --update-refs)
- [ ] Will a release branch ever sit at the bottom of a stack
- [ ] Do contributions arrive from forks (if so, stacks cannot be used)
- [ ] Can you afford every upper CI run repeating when the bottom changes

## 7. What not to do

- Cutting layers that reference each other — no order can be chosen
- Growing past five layers — the update cost eats the benefit
- Letting several people push to stack branches — it fights with rebasing
- Merging a middle layer first — the bottom rides along unreviewed
- Expecting stacks to raise review capacity — throughput is set by reviewer time
- Documenting a preview feature's UI and commands as if they were fixed
