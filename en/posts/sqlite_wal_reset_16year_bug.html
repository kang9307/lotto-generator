The Conditions Under Which a 16-Year-Old Bug Finally Shows Itself

Tracking rare defects through the SQLite WAL reset corruption - from checkpoint mechanics to upstream reporting

Aug 16, 2026 Dev & Infra

Introduction: the kind of failure where data goes quietly wrong

The backup job finished successfully every night, the disks report no errors, and the application log is clean. Yet a row that was definitely saved yesterday is missing from today's query. A query that uses an index and a full scan return different answers.

This class of failure is among the worst to deal with in practice, because there is no moment when it breaks. No process dies, no 500 goes out. The mismatched data rides straight into the next backup, and weeks later it finally surfaces when the books do not balance or one user asks about a setting that vanished. By then the logs from the hour that mattered have already been rotated away.

A Tailscale engineering report, featured on GeekNews on 2026-08-13, describes exactly that shape of incident. Nineteen database corruption events over six months, a cause that stubbornly refused to reproduce in a controlled environment, and a conclusion that eventually narrowed to a rare race condition in SQLite's WAL rewind path. The fix landed on trunk as a check-in dated 2026-03-03. WAL first appeared in SQLite 3.7.0 (2010-07-21), so roughly sixteen years sit between the two.

Read only the number and it becomes 'neglected for sixteen years', which teaches nothing. Three things are worth taking from it instead: what WAL and checkpointing actually do, why a defect with narrow reproduction conditions stays statistically invisible until a particular moment, and what to secure in what order when you meet one. This is not an argument about whose fault it was.

1. What WAL mode does - why it is fast, and what a checkpoint is

1.1 How it differs from the rollback journal

SQLite's default journalling mode works like this. Before a page is modified, its original content is copied into a separate journal file, and only then is the main database file changed in place. If the process dies midway, the journal restores the originals. It is safe, but the same data is effectively written twice.

WAL runs in the opposite direction. The main database file is not touched; changed pages are appended sequentially to the end of the WAL file. The official documentation summarises the benefit directly: write transactions are very fast because they only involve writing the content once, versus twice for rollback-journal transactions, and because the writes are all sequential.

In practice the bigger win is on the read side. With a rollback journal the writer edits the main file, so readers and writers block each other. Under WAL the main file stays put, so readers keep reading their own snapshot while the writer appends. How a reader finds the newest version of a page is the job of the wal-index, kept in shared memory in the file whose name ends in -shm; the documentation describes it as helping readers locate pages in the WAL quickly and with a minimum of I/O.

The price WAL pays is that one database becomes three files: app.db, app.db-wal, app.db-shm. That fact matters again in the evidence-preservation section below.

1.2 The checkpoint - moving the WAL back into the main file

A WAL cannot grow forever. The operation that copies accumulated frames back into the main database file is the checkpoint. In the documentation's own words, moving the WAL file transactions back into the database is called a checkpoint.

The default is automatic: once the WAL passes a size threshold, a checkpoint runs right after a commit. You can also drive it yourself with PRAGMA wal_checkpoint, which has four modes.

ModeBehaviourWhy you would pick it
PASSIVECheckpoints as many frames as possible without waiting for readers or writersThe default. Smallest impact on live traffic
FULLBlocks until there is no writer and every reader is on the most recent snapshot, then transfersWhen you want the WAL genuinely drained
RESTARTLike FULL, plus it waits until all readers are finished with the log fileTo let the next write start at the front of the WAL
TRUNCATELike RESTART, plus the WAL file is truncated to zero bytesWhen disk space must be reclaimed immediately
NOOPTransfers no frames at all and only returns the status valuesAdded in 3.51.0 (2025-11-04). Purely for observation

1.3 The rewind - the second mechanism that keeps the WAL from growing

Moving content out with a checkpoint does not by itself shrink the WAL file. That is where the rewind comes in. The documentation explains it this way: whenever a write occurs, the writer checks how far the checkpointer has progressed, and if the entire WAL has been transferred into the database and synced and no readers are making use of the WAL, the writer rewinds the WAL back to the beginning and starts putting new transactions at the front.

That sentence deserves a slow read. The party that decides to rewind is the writer, and the basis of that decision is the progress state left by the checkpointer. Two different actors read and update the same state independently. Concurrency defects live in exactly this shape of structure.

One thing is worth flagging early. RESTART and TRUNCATE effectively induce rewinds. A deployment that drives checkpoints itself, and does so often, walks this path far more than one that leaves checkpointing on automatic. Half of the answer to 'why now' is in that single line.

2. Where this particular defect was sitting

The fix went in as check-in 7168988acbec2d8d in the SQLite repository: 2026-03-03, trunk branch, authored by dan. The changed file is src/wal.c, and test/walrestart.test was added as a new file. The check-in comment is a single sentence.

Avoid an obscure race condition between a checkpointer and a writer wrapping around to the start of the wal file.

That is the structure from the previous section restated as prose: a race between the checkpointer and a writer that is wrapping back to the start of the WAL file.

The symptom side is described in the original report. If a write occurs at a particular moment during a checkpoint, the checkpointing process gets confused and believes that some pages have been copied from the WAL into the main database file when they have not.

What follows is the path to silent corruption. The region marked as transferred becomes reusable space, and a rewind lays new transactions over it. Pages then exist neither in the main file nor in the WAL. Rows disappear, or a table and the index that should point at the same data end up holding different content.

SQLite raises no error in that state, because as far as it is concerned the work was done. The damage only becomes visible when you run a separate comparison. The items PRAGMA integrity_check inspects are listed in the documentation.

  • Table or index entries that are out of sequence
  • Misformatted records
  • Missing pages
  • Missing or surplus index entries
  • UNIQUE, CHECK and NOT NULL constraint errors
  • Integrity of the freelist
  • Sections of the database used more than once, or not at all

When nothing is wrong, a single row with the value ok comes back. Put the other way round: in a system that never runs this pragma, every failure on that list produces no signal at all when it happens.

That is as far as the published material goes. Which internal state diverges in which order is not described beyond the check-in comment and the list of changed files. Filling in the rest plausibly would not be explanation, it would be guesswork.

3. Why it stayed hidden for 16 years - the statistics of rare defects

3.1 Exposure multiplies, it does not add

For a defect to reach anyone's bug report, three quantities must all be non-zero at the same time.

  • Trigger probability - the chance that traversing the code path actually goes wrong
  • Traversal count - how many times a day the system walks that path
  • Observability - whether anything exists that recognises a wrong result as wrong

The three multiply rather than add, so one factor near zero drags the product to zero. Which is why 'nobody reported it' and 'nothing was wrong' are entirely different claims.

Applied to this case: the trigger probability holds only inside a millisecond-scale window where a checkpoint, a rewind and a write overlap in a specific order. The traversal count varies by orders of magnitude depending on how checkpoints are driven, and the report states that the checkpoint process was taken under manual control and run very aggressively. Observability existed because an integrity check ran over backups continuously and something watched the result.

The third factor is the decisive one. Without a standing integrity check, the nineteen events would not have been one incident but nineteen separate tickets scattered across six months. A ticket that reads 'data is sometimes odd' never produces a signal that can travel upstream.

3.2 Defects tests can catch, and defects they cannot

SQLite is well known for the density of its test suite. But the question coverage answers is 'was this line executed', not 'did these two lines overlap in this order'. As line count grows, the coverage target grows linearly; the set of interleavings two threads can produce does not.

So the defects that survive longest in mature software tend to have a fixed shape. The easy ones are already gone, and what remains are ordering problems that hold only inside a narrow window. Reading more code does not reduce them. They surface probabilistically as execution volume and environmental diversity grow. The report notes the defect was so rare that SQLite's developers had to add code that deliberately triggers the condition in their test environments.

Sixteen years is less a measure of neglect than of how long it took for the necessary execution volume to accumulate. The longer software survives and the more varied the places it runs, the more of its remaining narrow conditions get actually stepped on. That is a normal property of the maturity curve, not a black mark against a project.

3.3 What attitude this implies at the start

In practice this recognition changes the order of suspicion. Take an old, well-proven component off the suspect list at the outset and you can spend months wandering through application code. Suspect the library from the first day and you will be wrong nine times out of ten.

The workable order is fixed: my code, then my configuration, then the environment (filesystem, kernel, hardware), then upstream. What matters is not the order itself but writing down the grounds on which each stage was ruled out. A stage skipped without evidence always comes back. Accumulated exclusion evidence is what earns you the right to tell upstream that it was not any of those.

4. Tracking stages - what to secure, in what order

Here is a usable order for tracking a defect that will not reproduce. Each row records what has to remain before you can move on, and where that stage typically collapses.

StageWhat you doWhat must remainWhere it usually collapses
1. Build a counterAttach an automatic check that judges corruption as corruptionCount, timestamp, affected instanceHandled only as tickets, so the count is never aggregated
2. Normalise casesRecord every case in the same formatVerbatim integrity check outputSummarised on the way in, so later comparison is impossible
3. Narrow common conditionsIntersect version, configuration, hardware, load patternLists of what overlaps and what does notCorrelation read as causation on a small sample
4. Align clocksPut application, DB, backup and infrastructure logs on one axisUpper and lower bound of the damage windowClocks differ per host and the ordering inverts
5. Attempt minimal reproductionNarrow conditions in a controlled environmentA procedure if it works, the boundary of attempts if notFailure to reproduce concluded as no cause
6. Move observation to productionInsert tracing one layer below the suspected oneLow-level records that show orderingOnly application logging gets louder
7. Confirm with upstreamReport with version, configuration, symptom and frequency attachedA bundle upstream can judge without reproducingReporting delayed because there is no repro procedure
8. Verify after the fixCount whether the condition itself still occursSeparate counters for condition and for corruptionSymptoms stopping mistaken for the cause being gone

Stages one and two get skipped most often and the skip costs most. If a human judges corruption by eye, the cases never standardise, and non-standardised cases cannot produce an intersection at stage three. Tracking then stalls at stage three.

Stage four is broken out for the same reason. What connects cause to effect is ordering, and ordering is invisible if logs from different machines cannot be placed on one axis. Why the clock you use to measure elapsed time must differ from the one that names an instant is covered separately in measuring elapsed time with a wall clock can return a negative number.

5. Observing an unreproducible bug in production

Reproducing in a controlled environment is a good goal but not the ultimate one. The goal is identifying the cause. When reproduction keeps failing, the direction has to change: drop the observation point one layer down.

5.1 Wedging tracing into the file layer

SQLite abstracts filesystem access behind an interface called the VFS. Slip a thin shim into that layer and you can see, in order, what was written at which offset and when, without touching application code. In this investigation the SQLite developers built tmstmpvfs, a wrapper around the virtual filesystem that writes additional tracing information. It lives on in the public repository as ext/misc/tmstmpvfs.c.

For an ordering defect that record of ordering is effectively the only evidence there is. Application logs preserve what the program intended to do; they do not preserve the order in which those intentions actually reached the disk.

5.2 Streaming modifying SQL outside the database

The second instrument was a transaction logging pipeline that captured every modifying statement. It plays two roles at once. It is a recovery mechanism, since the log can be replayed on top of the last known-good backup, and it is the reference for comparison, since it defines the state that ought to exist. Establishing the scope of damage requires a reference, and a backup alone only serves as a reference up to the moment it was taken.

5.3 An alert that keeps counting the condition after the fix

What happens after the fix ships matters more than it sounds. The report describes leaving an alert in place that detects the collision between a write and a checkpoint on its own, and confirming in production that the condition still occurred even though corruption no longer did.

Why bother. Because symptoms disappearing is not proof that the cause is gone. Two possibilities exist.

  • The condition still occurs but no bad result follows, which means the fix is genuinely working
  • The condition no longer occurs at all, which may just mean the load pattern or deployment shape changed

If you cannot tell the two apart, you will redo the entire investigation from scratch when traffic grows a few months later. That is the reason to keep the condition counter and the corruption counter separate.

5.4 Three lines worth generalising

  • Put the observation point one layer below the layer you suspect. More logging at the same layer adds volume, not ordering
  • Observation costs from the instant it is switched on. Decide the sampling ratio and the scope-reduction plan before enabling it
  • Do not switch the alert off after the fix. The moment it goes, the next recurrence starts from a blank page

6. Principles for handling data corruption

6.1 Preservation comes before repair

A corrupted database file is not a broken file, it is evidence. Yet the first thing done in the field is usually repair: run VACUUM, run REINDEX, dump and reload into a fresh file. All three erase the traces of the cause. Dump-and-reload is the worst offender because it launders corruption into a clean state, after which there is no way left to reconstruct what happened.

The scope of the copy matters too. Under WAL, the main file is not the whole story.

# Rule: stop first, copy first, look afterwards
cp app.db      evidence/app.db
cp app.db-wal  evidence/app.db-wal   # always include it if present
cp app.db-shm  evidence/app.db-shm   # include it too

# Diagnose on a second copy, never on the evidence itself
cp evidence/app.db     work/app.db
cp evidence/app.db-wal work/app.db-wal
sqlite3 work/app.db 'PRAGMA integrity_check;' > evidence/integrity.txt

There is a reason for that second copy. Opening a WAL database read-write can trigger recovery or a checkpoint that rewrites the file at the moment you connect. Attaching sqlite3 directly to the copy you intend to keep as evidence means altering the evidence. Stopping the process before copying is the principle, but note that stopping it also makes the -shm file disappear. Whichever you choose, record that you chose it.

6.2 Put every clock on one axis

The time of corruption is not the time of discovery. Strictly it is the interval between the last confirmed-good moment and the moment of discovery. The narrower that interval, the better the observation system, and the only way to narrow it is to confirm good state more often. This is exactly where the habit of checking integrity on every backup turns into incident response capability.

Placing several logs on one axis also means dealing with clocks first. Drift between hosts, mixed timezone notation across logs and wall-clock jumps from resynchronisation all invert ordering.

6.3 Keep the verdict verbatim

  • Do not summarise integrity check output. Which sentences appeared and how many times is the raw material for comparison, not a count
  • Attach version and configuration to the incident record: sqlite_version(), journal_mode, and who drives checkpoints
  • Stop accepting writes on an instance where corruption was detected. The report states that control plane shards were hard-stopped on detection
  • A hard-stop policy chooses consistency over availability. For ledger-like data that is usually right; for cache-like data a different call is defensible

7. What happened after the fix - a fix is still a change

The most practically useful part of this case is what came after the fix. In chronological order:

Version or check-inDateContent
SQLite 3.7.02010-07-21WAL mode introduced
SQLite 3.51.02025-11-04PRAGMA wal_checkpoint=NOOP added
Check-in 7168988acbec2d8d2026-03-03Avoids the race between checkpointer and wrapping writer. src/wal.c modified, test/walrestart.test added
SQLite 3.52.02026-03-06Released then withdrawn. Its planned features moved forward into 3.53.0
SQLite 3.51.32026-03-13Shipped carrying only the WAL reset corruption fix
SQLite 3.53.02026-04-09WAL reset fix plus the self-healing index feature (REINDEX EXPRESSIONS)

Right after 3.52.0 went out, backup monitoring reported corruption in thirteen databases. The cause was not the WAL fix. An optimisation had subtly changed the rounding behaviour of text-to-floating-point conversion.

Why did that become a corruption alert. High-precision timestamps were stored as text and converted to a floating point number in a VIRTUAL generated column, and that column was indexed. The values frozen into the index and the values the new build computed no longer agreed, so the integrity check reported the mismatch between index and table as corruption. That state is called a stale expression index. The stored data itself was fine.

SQLite withdrew 3.52.0 and published 3.51.3 carrying only the WAL fix, then added a feature in 3.53.0 that repairs stale expression indexes automatically. On the application side the timestamp precision was reduced to integer seconds, removing the ambiguous conversion entirely.

Two things are worth taking from that.

  • Expression indexes and generated columns store the result of a function. When the function changes, the stored result spoils. A change that improves accuracy is no exception
  • The first question on an integrity alert is not whether data is damaged but what disagrees with what. Those thirteen cases were an index disagreeing with a table, not data disappearing. The two situations call for completely different responses

This episode also feeds the version-pinning debate with real material. Pin only, and you never receive this WAL fix. Chase the latest unconditionally, and production meets changes like 3.52.0 first. Neither is the answer; the answer lives in the promotion procedure. The tension between backward compatibility and safer defaults in a SQLite context is covered separately in SQLite needs Rust-style editions.

8. Defences to adopt in your own system - a checklist

These are not countermeasures for this one defect but for silent data corruption in general. Use it to count how many of the items you already have.

ItemCadencePass criterionWhat happens if you skip it
Integrity check on a backup copyEvery backup generationAnything other than a single ok is a failureCorruption propagates through backup generations
Restore rehearsalAt least monthlySample queries on the restored copy match expectationsThe backup file exists but nothing can be revived from it
Choosing the right pragmaOnce, at design timeUse integrity_check when index comparison mattersquick_check does not verify that index content matches table content and misses this class
Halting writes on detectionImmediate and automaticStop and alert fire without human involvementWrites pile on top of damage and the recovery point disappears
Change log kept outside the DBContinuousLast good backup plus replay can restore the stateYou can only rewind as far as the backup
Version promotion procedureEvery releasePromote only after staging passes backup verificationProduction meets the other changes that shipped alongside the fix
Documented checkpoint policyOn configuration changeWho runs checkpoints, and when, is written downNobody knows which code paths their system walks often
Version string collectionEvery deploysqlite_version() and build method recordedAfter an incident the build cannot be reconstructed

Start by confirming what you are actually running. The snippet below is a shape, not a script; adapt paths and table names to your environment.

-- Start with what you are actually running
SELECT sqlite_version();      -- 3.51.3 or later, or 3.53.0 or later
PRAGMA journal_mode;          -- is it wal
PRAGMA wal_autocheckpoint;    -- automatic checkpoint threshold

-- The corruption verdict. A healthy database returns one row: ok
PRAGMA integrity_check;

Backup verification that is not automated eventually stops happening. The minimal form that runs per generation looks roughly like this.

#!/bin/sh
# A backup is only a backup once restored (illustrative shape)
set -e
backup="$1"
work=$(mktemp -d)
cp "$backup" "$work/verify.db"

result=$(sqlite3 "$work/verify.db" 'PRAGMA integrity_check;')
if [ "$result" != "ok" ]; then
  echo "INTEGRITY FAIL: $result"
  exit 1
fi

# Passing a structural check says nothing about content being right
sqlite3 "$work/verify.db" 'SELECT count(*) FROM users;'
rm -rf "$work"

Whether backups are wrapped in a web UI or driven by a shell script, leaving out restore verification breaks in the same place. Tooling choices and the 3-2-1 rule are discussed in tying scattered DB backups together behind one web UI.

9. What to bring when reporting upstream

Reports often get postponed because there is no reproduction procedure. But ordering defects are precisely the ones whose repro arrives last. What lets upstream judge without a repro is the density of conditions you supply.

  • The exact version - the output of SELECT sqlite_version(), the build method (distribution package, bundled, self-built) and compile options
  • Driver and bindings - name and version. Drivers frequently manage connection lifetime or checkpointing on their own
  • The full configuration - journal_mode, synchronous, who runs checkpoints and when, concurrent connection and process counts, filesystem and mount options
  • Verbatim symptoms - the integrity check output as it came out. Summarised, upstream cannot read the pattern
  • Frequency and duration - how many events over how many days. Almost the only material upstream has for judging probability
  • The boundary of your repro attempts - what was tried under which conditions and how far it failed. A bare 'cannot reproduce' carries zero information
  • Hypotheses you ruled out and why - how hardware, filesystem and application code were excluded
  • Willingness to produce observation data - whether a tracing hook built upstream could be deployed in your production, and within what scope

Tone matters as well. Upstream time is finite and usually not free; the report notes that a professional support arrangement with the SQLite developers was in place during the investigation. Open source does not mean upstream labour costs nothing.

Reporting also does not end when the cause is identified. The VFS tracing shim built during this investigation remaining in SQLite's public repository is a good way to finish, because the next person to hit something similar starts from a different place. Leaving behind a tracing tool outlasts fixing any single defect.

10. What could not be confirmed

The following are not settled by publicly available material, which is why this article does not assert them.

  • The internal mechanics of the race - only the check-in comment and the list of changed files (src/wal.c, test/walrestart.test) are public. Which internal state diverges in which order appears neither in the report nor in the release notes
  • The incidence rate under default settings - the report states that checkpointing was driven manually and aggressively. No published figure expresses the relative risk against a standard automatic configuration
  • Whether all nineteen events share one cause - the report describes them that way, but no per-event comparison table has been published
  • A reproduction procedure - the report states the team could not reproduce it in a controlled environment. The commands in this article are general diagnostic and defensive procedures, not steps that reproduce this defect
  • The official wording for the 3.52.0 withdrawal - the release notes say only that its planned features moved forward into 3.53.0. The causal link to the false alerts comes from the report
  • Similar reports elsewhere - no public account of the same symptom from other operators was found

Conclusion

What the number sixteen should convey is structure, not neglect. Defects that hold only on narrow conditions do not shrink under code review or coverage; they emerge probabilistically as execution volume and environmental diversity accumulate. And emerging requires a third condition without exception: something that recognises a wrong result as wrong. Without it, incidents happen and go unreported.

What this case leaves behind in practice is a list of exactly that machinery. An integrity check on every backup, an automatic halt on detection, a restore rehearsal that actually restores, and an alert that keeps counting the condition after the fix. None of the four is glamorous and none of them does anything on an ordinary day.

Three things worth doing today:

  1. Write down, on one page, your SQLite version, your journal_mode, and who drives checkpoints
  2. Make an integrity check run against every backup generation and have the result recorded
  3. Actually restore one backup this month and confirm sample queries against it

The third gets postponed most and bills the most when it comes due. A backup that has never been restored is not yet a backup.
