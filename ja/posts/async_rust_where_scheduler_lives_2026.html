きっかけ - 二十五マスの不満から始まり、自らそれを覆す記事

MOND←TECH MAGAZINEに2026年10月3日、「Async Rust: Where does the scheduler live?」という記事が掲載され、GeekNewsでは10月6日に紹介された。著者表記はMondである。記事はasync Rustについて繰り返される不満を5×5のビンゴカードに集めるところから始まる。関数の色、asyncクロージャ、Tokioデフォルト主義、「スレッドを使えばいい」、Async Drop、キャンセル安全性、Send + Sync + 'static制約の蔓延、io_uring、Pinまで二十五のマスが埋まり、マスごとに読み物を添えたチートシートが続く。

その後に著者自身の不満が出てくる。async Rustがランタイムを要求する点が引っかかるという。Rustの看板はガベージコレクタのようなランタイムなしにメモリ安全性を与えることなのに、ランタイム前提のモデルに戻るのは後退のように感じられると書く。ランタイムができた瞬間、関数を自分で実行するのではなくエンジンに渡すことになり、エンジンは自らの規則に従ってそれを実行する。スケジューリングのアルゴリズムは最適化問題であり、トレードオフの境界上の一点を選ばなければならず、あらゆる場合に合う答えはない。性能をもう少し絞り出すためにTokioランタイムをJavaのガベージコレクタのようにいじることになる、と続く。

そして著者はこの愚痴を自ら取り下げる。原文の文は「In short, that whole gripe was nonsense.」である。ランタイムらしさ、スケジューラ最適化のトレードオフ、複雑さはasync Rustだけの問題ではなく、並行に動くコード一般の問題だというのがその理由だ。記事の残りはこの転換を解きほぐすことに費やされる。スケジューラはどこかになければならず、残る問いはその置き場所がどこかである。

以下でたどるのもその置き場所である。カーネル、言語に組み込まれたランタイム、クレート、そして著者が望む四つ目の置き場所である引数を順に置き、それぞれについて原文が挙げたコストと制約を、RustとTokioの公式ドキュメントの文言と並べる。印が呼び出し階層へ広がっていく関数の色の問題とキャンセルの意味論は別の軸であり、同じasyncコードがランタイムごとに違う終わり方をする理由にまとめてある。

スケジューラは消えない - 著者の五段階

著者の出発点となる命題は短い。コードを並行に実行したいならスケジューリングを担うランタイムが必要であり、それは並行性の定義に事実上組み込まれているというものだ。async Rustを避けてスレッドを使っても、変わるのはスケジューラがTokioからカーネルに替わる点だけで、スケジューラは依然として存在し、同じ問題のすべて、少なくとも一部が付いてくると著者は書く。続いて、何が問題なのかを五段階に整理する。

  1. 並行性は何らかの形で必要である。
  2. 並行性には常にランタイムが必要である。すると問いは、ランタイムがどこにあり、スタックを誰が管理するのかになる。
  3. ランタイムを避けようとするときにできる最善は二つである。イベントループを自分で書けば自前のランタイムを保守することになり、「スレッドを使えばいい」を選べばカーネルをランタイムとして使うことになって、特化したTokioタスクよりはるかに重いカーネルスレッドを扱うことになる。原文はこの重さの差を誇張を交えて書いている。
  4. Goがしているようにランタイムを言語に載せて出荷すれば、Rustをほかの場所に埋め込むことが難しくなり、FFI境界でコストを払うことになる。
  5. 選択肢を使い果たして残ったものが現在の姿である。ランタイムはクレートである。取り込んで初期化し、場合によっては渡して回り、futureをスケジューリングするのに使う。

著者は設計上の決定を一つずつ振り返りながら不満を言おうとしたが、段階ごとにもっともだという結論に行き着いたと書く。まとめの文は「The scheduler has to live somewhere, and Rust doesn't get to trade performance for convenience.」である。ここにも留保が付いている。async Rustの問題の半分を消し去る未発見の抽象があるのかどうかは分からないとまず述べ、そのうえで、ないという側に傾いていると書く。根拠は、それらの問題の多くが並行性一般の問題だという点である。

この整理から持ち帰る区別は一つである。著者はasync Rustの問題を、並行性に内在する問題と、スケジューラをクレートに置くと決めたことの下流にある問題とに分けて見ることを提案する。この区別に従えば、前者はスケジューラをどこに置いても付いてきて、後者は置き場所を移せば形が変わると読むことができる。何が後者に属するのかは、著者が直接名指しした三つを通して後で扱う。

標準ライブラリが規定するもの - Future・poll・Wakerまで、スケジューラはない

五つ目の段階である「ランタイムはクレートである」がどういう姿なのかは、標準ライブラリのドキュメントに表れている。std::future::FutureはRust 1.36.0から安定化されているトレイトであり、定義は次がすべてである。

pub trait Future {
                        type Output;
                    
                        // Required method
                        fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
                    }

ドキュメントはfutureを、まだ計算が終わっていないかもしれない値だと説明する。pollはfutureを最終的な値へ解決しようと試みるメソッドであり、値が準備できていなければブロックせずに戻る。その代わり、もう一度ポーリングすれば進める状態になったときに現在のタスクが起こされるよう予定される。誰がpollを呼ぶのかを決める型は、このドキュメントにはない。ドキュメントが記しているのは、futureはそれだけでは不活性(inert)であり、基礎となる計算が進むには能動的にポーリングされる必要があるという点だ。futureを使う側は通常pollを直接呼ばず.awaitを使うとも記す。

ポーリングを担う側がエグゼキュータである。WakerのドキュメントはWakerを、タスクが実行できる状態になったことをエグゼキュータに知らせてそのタスクを起こすためのハンドルと定義する。典型的な一生は、エグゼキュータが作ってContextに包み、Future::poll()に渡すというものだ。次にどのタスクを実行するかもエグゼキュータに委ねられている。同じドキュメントは、競合するタスクへ譲ることは保証されず、どのタスクを実行するかはエグゼキュータの選択であり、エグゼキュータが現在のタスクをもう一度実行することもありうると記す。標準ライブラリは起こすための経路までを定め、起こされたタスクをいつ、どのスレッドで動かすかは空けてある。

Async Bookはこの配置の理由を直接書いている。多くの言語はランタイムを提供し、そのランタイムはメモリ管理や例外処理、さらには仮想マシンの役割まで担うことが多い。Rustは低水準の言語としてランタイムのオーバーヘッドを最小にしようとするので、asyncランタイムの範囲はほかの言語のランタイムよりずっと狭い。そしてasyncランタイムを設計し実装する方法が多数あるため、Rustは一つを提供するのではなく要件に応じて選ばせる。本はその代償も一文で書いている。asyncプログラミングを始めるには手順が一つ余分に要る。ランタイムの構造にも強い規則はなく、表の用語と役割分担が一般的であるにすぎないと述べる。spawnが標準ライブラリではなくTokioの関数である理由は、タスクが純粋にランタイムの概念だからだと説明している。

第一の置き場所、カーネル - 「スレッドを使えばいい」が移すもの

ビンゴカードの一マスは「just use threads」である。チートシートはこの主張の最もよくある変種を、asyncは同時に1万を超える接続を受けなければならないサーバを書くときにだけ必要になり、それ以外はスレッドプールで足りるという考えとして要約している。著者の答えは、この選択がスケジューラをなくすわけではないというものだ。スレッドを使えばカーネルがスケジューラになる。

この置き場所の性質は、Rustがグリーンスレッドを取り除いたときに書かれたRFC 230に整理されている。RFCは、タスクが常にOSスレッド一つに対応するモデルを1:1、ユーザ空間のスケジューラがタスクをワーカースレッドに載せるモデルをM:Nと呼ぶ。1:1モデルではタスクはすなわちスレッドなのでそれぞれが自分のスタックを備えなければならず、各タスクがOSスレッドであるため、ほかのタスクに危険を及ぼすことなく自由にブロックできる。M:Nモデルでは、OSの意味でのブロッキングはワーカースレッドをブロックすることになる。長く回るループやページフォールトも同じだとRFCは付け加える。

著者がこの置き場所のコストとして挙げるのは重さである。カーネルスレッドは特化したTokioタスクよりはるかに重いという。比較される側には、Tokioのチュートリアルが数値を一つ書いている。Tokioのタスクは内部的に一回のアロケーションと64バイトのメモリしか必要とせず、数千はもちろん数百万を生成しても構わないという。チュートリアルはTokioのタスクを非同期のグリーンスレッドと呼んでいる。カーネルスレッド側の大きさの数値は、原文にも上記のドキュメントにもない。

著者はこの置き場所について、自ら辛口の意見と呼ぶ考えをもう一つ持ち出す。言語ごとにランタイムを作り直して論争する代わりに、カーネルのスレッディングとスケジューリングを直すか新しい種類のカーネルスレッドを導入して、「スレッドを使えばいい」が効率的になるようにはできないのか、というものだ。goroutineはカーネルの上で動く抽象であり、それを安価で高速にできるのなら、カーネルもそうしたスレッディングを支えられるはずだという推論だ。この考えには著者自身の留保が三つ付いている。

  • 同様の試みが「M:N user-level threading」のような名前で何度かあったと書きつつ、それについての調査はしていないと明かしている。
  • 実際には、カーネルは言語専用のランタイムほどコードについて知ることができないのでスケジューリングの能力が限られ、カーネルに追加の情報を渡す方法を見つけない限り、言語専用のランタイムがおそらく優位に立ち続けるだろうと見る。原文は「always」の後に疑問符を付けている。
  • 理想的な場合でも、結果は誰もがあらゆることにスレッドを使う世界へ戻ることであり、性能が高くなるだけである。それがより良いのかという問いに、著者は分からないと答える。

第二の置き場所、言語ランタイム - Goの選択とRustが取り除いたもの

原文が組み込みランタイムの例として挙げる言語はGoである。著者の記述はこうだ。Goにベアメタルの性能を期待する人はおらず、トレードオフがあることを誰もが理解している。利便性と引き換えに性能をいくらか手放しているのであり、だからGoにはgoroutine、すなわちグリーンスレッドがある。チートシートはグリーンスレッディングを、言語が自前のランタイムを持ち込むモデルと説明する。Rustについて著者は、完璧なスケジューラは存在せず、スケジューラごとに用途が異なるので、Rustが利用者に代わってスケジューラを選ぶことはできないと書く。GoとRustの間で何を基準に移るかを扱った記事はGoからRustへの移行ガイドである。

Rustもかつてはこの置き場所にいた。RFC 230は開始日が2014年9月16日と記された文書で、当時標準ライブラリに含まれていたランタイムシステムを取り除く提案である。RFCの記述によれば、Rustは最初グリーンスレッディングのモデルだけをサポートし、後からネイティブスレッディングが加わって最終的に既定になった。RustのグリーンスレッドはM:Nでスケジューリングされ自前のスタックを持っていたが、当初使っていたセグメントスタックが取り除かれ、あらかじめ確保したスタックに替わったことで軽量ではなくなったとRFCは書く。RFCが挙げた問題は五つである。

  • 強制された共進化。グリーンとネイティブの二つのモデルが常に同じI/O APIを提供しなければならなかった。片方にしか合わない、あるいは片方でしか効率的でない機能があるにもかかわらずである。
  • オーバーヘッド。二つのモデルの混在をトレイトオブジェクトで実装したため、バイナリサイズ、タスクローカルストレージ、アロケーションと動的ディスパッチにコストが生じた。RFCは最後の項目について、I/Oそのもののコストに比べればほとんどの場合ささいであり、強い反対論拠ではないと自ら断っている。
  • 問題のあるI/Oの相互作用。ネイティブコードがブロッキングI/Oを呼ぶと、グリーンスケジューラを動かしているワーカースレッドがブロックされるおそれがあった。統一されたAPIではあったが、完全に相互運用できたわけではない。
  • Rustの埋め込み。Cのコードから呼ぶ場合や高水準言語に埋め込む場合、標準ライブラリが頼るランタイムの基盤を用意するための準備作業がかなり必要だった。
  • 保守の負担。柔軟なスレッディングモデルを提供するために、標準ライブラリがより複雑になっていた。

FFIのコストという論拠を、原文は自分では展開せず、Without Boatsの2023年10月15日付の記事「Why async Rust?」に委ねている。その記事は、グリーンスレッド上の実行をOSスレッドのスタック上の実行へ切り替えることがFFIにとって法外に高くつくことがあり、Goはこのコストを受け入れていると書く。Rustは別の言語で書かれたバイナリにライブラリとして埋め込まれる用途と、仮想スレッディングのランタイムを動かすだけのクロックサイクルやメモリを持たない組み込みシステムを支えるように設計されているので、この点がとりわけ問題だったという説明が続く。著者は組み込みの論点が妥当だと認めつつ、async Rustの議論で組み込みを持ち出すこと自体がほとんどミームになっているという観察も添えている。

著者がここから読み取るのは設計原則である。グリーンスレッドを捨てた決定は、当時まだ流動的だった原則、すなわちRustが組み込みのno_std環境でも使え、ゼロコスト抽象を備えたC++の代替という道を進むという原則を固めたと見る。振り返ってみればこの方向は正しい判断だったように見える、というのが著者の評価だ。Rustがグリーンスレッディングを推し進めた反実仮想の世界がどのような姿かは分からないと前置きしたうえで、その世界でRustがLinuxカーネルに入ったとは思えないという推測を加える。原文もこのくだりを「assume」という動詞で書いている。FFI境界でRustの安全性の保証がどう途切れるかは、Rust FFI境界で途切れる安全保証で別に扱った。

第三の置き場所、クレート - Tokioがドキュメントに書いているスケジューラ

ランタイムがクレートになると、スケジューラの動作は言語仕様ではなくそのクレートのドキュメントに書かれる。Tokio 1.53.2のドキュメントは、非同期アプリケーションはほかのRustプログラムと違ってランタイムの支援を必要とすると記し、必要なサービスを三つ挙げる。I/Oリソースを駆動してイベントをタスクに配るI/Oイベントループ(driver)、タスクを実行するスケジューラ、一定時間の後に作業を動かすためのタイマーである。TokioのRuntimeはこの三つを一つの型にまとめている。

ドキュメントは用途に合ったスケジューリング戦略を複数提供していると述べ、選ぶ目安を決定木として描いている。work-stealingやマルチスレッドのスケジューラが必要ならMulti-threaded Runtime、そうではなく!Sendのfutureを実行するならLocal Runtime、それでもなければCurrent-thread Runtimeである。ドキュメントはこの木が網羅的ではなく、ほかの要因が判断に影響しうると断っている。マルチスレッドのスケジューラはスレッドプールの上でwork-stealing戦略によってfutureを実行し、既定ではシステムのCPUコアごとにワーカースレッドを一つ起動し、既定で選択される。

ドキュメントの「Detailed runtime behavior」の節は内部の動作を数値とともに書いている。二つのランタイムの小見出しには「behavior at the time of writing」と付いており、この動作は今後のTokioのバージョンで変わりうると明記されている。下の表の値はその条件のもとで読む。

公平性についての保証も条件付きで書かれている。タスクの総数が際限なく増えず、どのタスクもスレッドをブロックしていないなら、タスクが公平にスケジュールされることが保証される。それ以外には、スケジュールされる順序についての保証はなく、すべてのタスクに等しく公平だという保証もない。ドキュメントの例では、どちらも準備ができているタスクAとBがあるとき、ランタイムはBをスケジュールする前にAを5回スケジュールすることがありえ、保証されるのはBがいずれスケジュールされるということだけである。

原文とこのドキュメントを並べると二つのことが読み取れる。第一に、著者がスケジューラについて「トレードオフの境界上の一点を選ばなければならない最適化問題」と述べたものが、Tokioでは31、61、256、10msといった値と設定項目として表に出ている。第二に、それらの値は一つのクレートの一つのバージョンが選んだ点である。標準ライブラリのドキュメントにはこれに対応する値がなく、どのタスクを実行するかはエグゼキュータの選択だというWakerのドキュメントの一文があるだけだ。

クレートに置いた代償 - 著者が名指しする三つ

著者は、スケジューラがクレートにあるために生じる問題を直接名指ししている。Tokioデフォルト主義、ランタイム中立性の不足、そしてSend + 'static制約である。

  • Tokioデフォルト主義(Tokio Defaultism)。チートシートの説明によれば、Tokioだけが意味のあるランタイムだという観念である。自分が話している内容がasync Rust一般ではなくTokioにしか当てはまらないと気づいていない場合がこれに含まれる。Async BookはTokioをエコシステムで最も広く使われている汎用ランタイムと紹介しつつ、状況によっては別のランタイムのほうがより良い性能やより単純なコードを与えうるとも併せて書いている。
  • futureはランタイム中立ではない。チートシートは、タスクの生成がランタイムに依存し、さまざまな前提がそこに焼き込まれており、一部の事柄はトレイトに焼き込まれていると書く。人々が「ecosystem split」と言うときに指している問題の一つがこれであり、もう一つは、asyncがRustのエコシステム全体をasyncのライブラリと非asyncのライブラリに分けてしまう点だと付け加える。
  • Send + 'static制約の伝播。著者の説明は、ランタイムがタスクをスレッド間で移動するかどうかを言語自体が知りえないため、Send制約がジェネリックなコード全体に広がるというものである。

三つ目の項目はTokioのドキュメントの文言と照らし合わせられる。tokio::spawnのシグネチャは次のとおりである。

pub fn spawn<F>(future: F) -> JoinHandle<F::Output>
                    where
                        F: Future + Send + 'static,
                        F::Output: Send + 'static,

Tokioのチュートリアルは二つの制約の理由を別々に書いている。'staticは、生成されるタスクがタスクの外で所有されているデータへの参照を含んではならないという意味である。Sendは、タスクが.awaitで中断している間にTokioランタイムがタスクをスレッド間で移動できるようにするためのものであり、.awaitをまたいで保持されるデータがすべてSendであるときにタスクはSendになる。spawnのドキュメントは、!Sendの値を.awaitの呼び出しをまたいで持ち続けると、親切とは言えないコンパイルエラーのメッセージが出るとも書いている。

この制約がwork-stealingというスケジューリングの選択から出てくることは、チートシートの別のマスに書かれている。work-stealingはタスクをあるCPUコアから別のコアへ移せるので各スレッドに常に仕事があるようにできるが、すべてのタスクにSend制約を要求し、thread per coreのランタイムにはこの制限が当てはまらない。標準ライブラリがタスク生成のAPIを標準化するという考えが難しい理由も、著者はここに見いだす。ランタイムごとに期待するものが異なるからだ。Tokioのドキュメントの決定木にLocal Runtimeの枝が別にあるのも同じ事情を示す。

ブロッキングもこの置き場所で形が変わる問題である。標準ライブラリのドキュメントは、pollの実装は素早く戻るよう努めるべきでありブロックすべきではなく、時間がかかると前もって分かっているなら作業をスレッドプールなどへ逃がすようにと書いている。チートシートのspawn_blockingのマスは、これが守られなかったときの様子を書く。Tokioのワーカースレッドを誤ってブロックすると、残った仕事はほかのスレッドがスティールするのでプログラムはよろよろと動き続けるかもしれないが、その呼び出しがブロックしている間ワーカープールはスレッド一つ分減った状態になり、トラフィックが少ないうちは気づきにくい。Tokioの公平性の保証が、どのタスクもスレッドをブロックしないという仮定の上に立っている点とかみ合う。

I/Oインターフェースの側にも同じ種類の摩擦が書かれている。チートシートによれば、io_uringのAPIでは操作が終わるまでカーネルがバッファを所有し、これがdropでキャンセルできるfutureと衝突するため、Tokioでこれを直すにはAPIを作り直す必要がある。io_uringそのものの動作はio_uring SQPOLLとシステムコール不要のI/Oにある。

暗黙のエグゼキュータ文脈 - 同じ関数が呼び出しスレッドによってパニックする

著者がTokioについて個別に持ち出す不満は、暗黙のアンビエントなエグゼキュータ(ambient executor)のモデルである。少しもどかしいという程度の口調だ。生成されたTokioタスクはスレッドローカルな文脈に漂うエグゼキュータにひとりでに結び付き、そのようなエグゼキュータがなければランタイムパニックで壊れるという。原文の例は次のとおりである。

fn record_metric(_value: u64) {
                        tokio::spawn(async move {
                            // do stuff
                        });
                    }
                    
                    fn checksum(data: &[u8]) -> u64 {
                        let sum = data.iter().map(|&b| b as u64).sum();
                        record_metric(sum);
                        sum
                    }
                    
                    #[tokio::main]
                    async fn main() {
                        let data = vec![1u8; 1024];
                        checksum(&data); // fine
                    
                        let (tx, rx) = tokio::sync::oneshot::channel();
                        rayon::spawn(move || {
                            let _ = tx.send(checksum(&data)); // panics, process abort
                        });
                        println!("{:?}", rx.await);
                    }

checksumはシグネチャだけを見れば、バイトスライスを受け取って合計を返す同期関数である。その中で呼ばれるrecord_metricがtokio::spawnを使っているという事実は、シグネチャには現れない。原文では、#[tokio::main]の下で直接呼んだ行に「fine」、同じ関数をrayon::spawnに渡したクロージャの中で呼んだ行に「panics, process abort」というコメントが付いている。

Tokioのドキュメントの文言も同じ契約を記している。tokio::spawnはTokioランタイムの文脈の中から呼ばなければならず、Panics項はランタイムの外から呼ぶとパニックすると記す。ランタイム上で動いているタスクは常にその文脈の中にあり、Runtime::enterメソッドで文脈に入ることもできるという説明が併せてある。Async Bookは入門段階の読者に、当面はランタイムをasync関数の中でだけアクセスできるグローバル変数のように想像してよいと説明している。

著者はこれを、すべてのTokioの関数が受け渡している「secret argument」にたとえる。呪文を忘れると、つまりTokioランタイムの文脈の外でTokioを使おうとすると、実行時エラーを受け取る。著者が問題にしている性質は次のとおりである。

  • 副作用がある。
  • グローバル変数に近い隠れた変数がある。
  • 動的スコープが隠れている。

上の例に照らすと、この副作用はchecksumのシグネチャに現れず、同じ関数の成否が呼び出したスレッドの文脈に左右され、エラーはコンパイル時ではなく実行時に出る。

著者は脚注で、要求が過大であることを自ら認めている。Rustにはエフェクトシステムがなく、コードがパニックしうるかどうかすら追跡できないのだから、副作用の追跡は言うまでもないという。それでも、コンパイル時に追跡されない点が気に入らないと書く。TokioにHandle::spawnがあることも脚注にあり、アンビエントな形のほうが既定であることを問題として挙げている。

著者が描く理想の世界では、タスクを生成する場所までエグゼキュータをコード全体を通して渡さなければ、タスクを生成できない。多くの人がこの世界を嫌うだろうと著者自身が書いている。渡さずにTokioのエグゼキュータに手を伸ばしたいのなら、それはグローバル変数に置かれていて、呼び出し箇所でそこから取り出すべきだというのが次善の形である。基準は検索で見つけられるかどうかであり、この性質は隠されているのではなくgrepで探せるべきだと著者は書く。

「これ以上は望めない」という通念 - futureのサイズの例

原文には性能についての脇道が一つある。async Rustは漠然と「as good as it gets」だという信念があるが、実際にはそうではないというものだ。著者が取り上げる通念は、Rustのfutureはすべてのデータを保持するのに必要なだけの大きさしかない、最適なサイズの状態機械にコンパイルされるという信念である。著者は、それは設計の意図ではあるが長年の問題がいくつも存在すると書き、yield点をまたいで保持される引数が二倍のコストを払うという事例を挙げる。

async fn test(arg: [u8; 8192]) {
                        wait().await;
                        drop(arg);
                    }
                    
                    async fn wait() {}
                    
                    fn main() {
                        // Expected: 8194 == 2 + 8192
                        // Actual: 16386 == 2 + 2 * 8192
                        println!("{}", std::mem::size_of_val(&test([0; 8192])));
                    }

コメントに書かれた値が、原文が示す数値のすべてである。8192バイトの配列を引数として受け取るasync関数のfutureのサイズをstd::mem::size_of_valで出力すると、期待される値は8194(2 + 8192)なのに、実際の値は16386(2 + 2 × 8192)だという。原文はdrop(arg);の呼び出しを消して何が起きるか見てみよと付け加えるが、その結果は書いていない。futureを引数として渡す場合にはサイズの増加が指数的になるとも書き、この問題を解決しようとする作業としてrust-lang/rustリポジトリのプルリクエスト135527を挙げている。

この例を読むときに見るべきなのは数値の種類である。8194と16386はコンパイラが作った状態機械のバイトサイズであり、どのランタイムのスループットでもレイテンシでもない。原文にはランタイム同士、あるいはスレッドとasyncを比べたベンチマークはない。チートシートは、深くネストしたasync関数のfutureがスタックをあふれさせうるというマスを別に設けている。原文はこの通念を、あらゆる用途に合うスケジューラがあるという考えとは別の誤解として扱う。スケジューラについての誤解はどのスケジューラを選ぶかの問題であり、futureのサイズについての誤解はコンパイラがfutureをどの大きさで作るかの問題である。

第四の置き場所、引数 - ZigのI/Oインターフェースと著者の留保

著者が原則にかなった形の例として挙げるのはZigである。ZigではI/Oインターフェースを、それを必要とするすべての関数に渡す。非同期であるかどうかとI/Oは、渡された実装に焼き込まれた性質になる。原文がLoris Croの記事から取ったと明記している例は次のとおりである。

const std = @import("std");
                    const Io = std.Io;
                    
                    fn saveData(io: Io, data: []const u8) !void {
                        const file = try Io.Dir.cwd().createFile(io, "save.txt", .{});
                        defer file.close(io);
                    
                        try file.writeAll(io, data);
                    
                        const out: Io.File = .stdout();
                        try out.writeAll(io, "save complete");
                    }

saveDataの最初の引数io: Ioがそのインターフェースである。ファイルを作り、閉じ、書き込む呼び出しのたびにioが渡される。著者はI/Oインターフェースがランタイムに対する契約を定義すると書き、全員がインターフェースを渡すという規律を厳格に守るという仮定のもとで、原理上三つのものが得られると整理する。

  1. ブロッキングする操作が起こりうる場所を正確に追跡できる。
  2. 関数の色を避けられる。色が関数の引数になるからである。脚注はここに留保を付けている。色が特別な言語機能ではなく関数に渡す引数として符号化されるのであり、これを関数の色と見るかどうかについて人々が合意することは決してないだろうと書く。
  3. すべてのライブラリのコードがエグゼキュータやスケジューラに対して中立になる。I/Oインターフェースの別の実装を渡せばよいので、エコシステムが分かれない。

題名の問いに対する著者の答えがここで出てくる。スケジューラを、渡して回る引数の中に置くのが正しく感じられるという。冗長ではあるが多くの問題を解決し、ビンゴカードの三分の一ほどを解決すると著者は書く。カーネルでもなく、周囲に漂う実行文脈でもなく、引数として渡し、必要に応じて差し替えられるもの。それが著者の望む置き場所である。

この答えには留保が立て続けに付いている。原文の順に移すと次のとおりである。

  • Zigはまだ安定版ではなく、asyncを正しく作るのは非常に難しい。著者の言葉では、このアプローチは実戦ではまだ証明されていない。
  • Zigのチームがこれを成功させられるなら、Rustをその方向へ進化させる実験にはやる価値があるだろうと著者は確信している。条件が先に付いた文である。
  • 全面的に採用するにはstd::fsのようなRust標準ライブラリのAPIの書き直しが必要になるため、ほぼ確実に論外だと見る。
  • クレートのエコシステムはそのような制約の下にないので、もしかすると可能かもしれないと書く。原文の表現は「Maybe it's possible.」である。

著者の結論は、RustはZigに倣うべきだという勧告ではない。クレートに置いた現在の選択がRustにとって正しかったという評価を保ったまま、Zigのチームがこれを成功させるならRustをその方向へ進化させる実験にはやる価値があるということ、クレートのエコシステムではもしかすると可能かもしれないということまでである。

  • futureのサイズの例の実際の出力。8194と16386は原文のコメントの値であり、コンパイラのバージョンごとに動かして得た結果ではない。drop(arg);を消したときの値は原文にも書かれていない。
  • ランタイムの外でspawnする例の実際の実行。「panics, process abort」は原文のコメントであり、Tokioのドキュメントと照らし合わせたのは、ランタイムの外からの呼び出しがパニックするというPanics項までである。
  • カーネルスレッドとTokioタスクの重さを同じ条件で測った数値。Tokioチュートリアルの64バイトはタスク側の値だけである。
  • Goランタイムのスケジューラの動作とFFIのコストについてのGo側の公式ドキュメント。Goに関する記述は、原文とWithout Boatsの記事の文に限った。
  • カーネルの水準でM:N user-level threadingを試みた事例の内容と結果。原文の著者も調査していないと明かしている。
  • Tokioのio_uring対応の程度。原文は「Afaik」という断り付きで、まだ完全には対応していないと書いており、Tokio側のドキュメントとは照らし合わせていない。
  • Tokioのスケジューラの細かい数値が1.53.2より後のバージョンでも維持されるかどうか。ドキュメント自身が変更の可能性を明記している。
