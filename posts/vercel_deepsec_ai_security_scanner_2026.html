본문의 사실적 근거는 Vercel의 오픈소스 프로젝트인 DeepSec(Apache 2.0 라이선스)의 공개 아키텍처와, 2026년 8월 30일 개발자 Flavio Copes가 자신의 웹사이트 저장소(flaviocopes.com)를 대상으로 직접 스캔을 수행하고 공개한 2차 리뷰 기록을 바탕으로 한다. 본문에 인용된 특정 스캔 통계 수치(729개 파일 대상 504건 잠재 위험 등)는 DeepSec의 전역 공식 벤치마크가 아니라 Flavio Copes 개인 환경에서의 1회성 스캔 결과다.

1. 패턴 검색과 AI 에이전트의 융합 — 2단계 파이프라인 개요

일반적으로 소프트웨어 보안 취약점을 탐지하는 정적 분석 도구(SAST)는 사전에 정의된 규칙 집합과 정규식을 기반으로 소스코드를 고속 탐색한다. 문자열 결합으로 작성된 SQL 질의문이나 인증 미들웨어가 누락된 라우트 핸들러를 식별하는 작업에서 이러한 패턴 매칭은 매우 빠른 속도를 발휘한다. 그러나 패턴 매칭만으로는 해당 경로로 유입되는 사용자 입력이 선행 함수에서 이미 무해화되었는지, 또는 실제 운영망에서 외부 트래픽이 닿지 않는 내부 전용 모듈인지와 같은 문맥적 연관성을 온전히 판별하기 어렵다.

반면 대규모 언어 모델(LLM) 기반의 코딩 에이전트는 다중 파일에 걸친 데이터 흐름을 추적하고 방어 로직의 존재 여부를 추론하는 데 강점을 지닌다. 하지만 저장소 전체의 모든 소스파일을 무차별적으로 모델의 입력 컨텍스트에 밀어 넣는 방식은 막대한 토큰 비용과 긴 지연 시간을 유발한다. Flavio Copes의 리뷰에 따르면, Vercel의 오픈소스 보안 스캐너 DeepSec은 이 두 가지 접근 방식을 결합한 2단계 파이프라인 구조를 채택한다.

원문은 DeepSec의 작동 방식을 설명하며 빠른 패턴 스캐너가 먼저 검토 대상이 되는 코드를 골라내고, 이어지는 단계에서 코딩 에이전트가 해당 코드를 정밀하게 읽으며 파일 간 데이터 흐름을 추적하고 기존 방어 체계를 확인한다고 명시한다. 이러한 구조를 통해 계산 비용이 저렴한 로컬 패턴 스캐너가 조사 범위를 대폭 좁혀주고, 높은 추론 역량을 요구하는 심층 조사는 선별된 후보군 파일에만 집중시키는 분업 체계가 완성된다.

이 글의 해석으로는, 단일 프롬프트에 저장소 점검을 통째로 맡기는 기존 AI 코드 분석과 달리, 상태 저장소 디렉터리를 기반으로 검토 후보군을 체계적으로 유지하는 하네스(Harness) 구조를 설계한 점이 DeepSec 아키텍처의 핵심 차별점이다. 파일 단위의 검토 이력과 상태가 관리되므로 대규모 코드베이스에서도 반복 가능하고 재개 가능한 보안 감사가 가능해진다.

2. DeepSec 전체 워크플로우 6단계와 아키텍처

Flavio Copes의 기술 리뷰에 기술된 DeepSec의 전체 실행 파이프라인은 단일 명령어로 끝나는 블랙박스가 아니라, 순차적으로 상태를 축적해 나가는 6단계 워크플로우로 구성되어 있다. 저장소 분석부터 최종 보고서 작성에 이르는 전 과정은 다음과 같은 흐름을 거친다.

표 1: DeepSec 보안 스캔 파이프라인 6단계 구조 (Flavio Copes 리뷰 기반 정리)
단계 번호 파이프라인 단계 주요 수행 작업 및 시스템 역할 비용 및 실행 특성
1단계 저장소 (Repository) 분석 대상이 되는 프로젝트 코드베이스 인식 및 기본 환경 감지 로컬 파일시스템 읽기 작업 (비용 발생 없음)
2단계 인벤토리 (Inventory) HTTP 라우트, RPC 핸들러, 웹훅 등 외부 입력 유입 지점의 목록 작성 프로젝트 구조 분석 및 매처 커버리지 검증
3단계 패턴 스캔 (Pattern scan) 사전 정의된 매처 규칙을 적용하여 정밀 조사가 필요한 후보 파일 선별 고속 로컬 정적 검사 (외부 AI 호출 없음)
4단계 AI 수사 (AI investigation) 코딩 에이전트가 후보 코드를 정독하며 호출 경로, 데이터 흐름, 방어 로직 추적 모델 API 토큰 소모 발생 (주요 비용 구간)
5단계 재검증 (Revalidation) 도출된 잠재 위험에 대해 2차 에이전트 패스를 수행하여 오탐 배제 및 심각도 재조정 선별된 후보군 대상 추가 모델 추론 수행
6단계 보고서 (Report) 검증된 최종 보안 위험 항목을 구조화된 마크다운 또는 데이터 형식으로 출력 로컬 디스크 내 파일 생성 및 요약 집계

원문에 따르면 DeepSec은 이 모든 파이프라인 단계를 프로젝트 루트의 전용 디렉터리 내부에 격리된 상태로 보관한다. 이 공간에는 설정 파일과 함께 자동 생성된 위협 모델 문서, 감지된 진입점 목록, 중간 검사 결과가 체계적으로 저장된다. 따라서 장시간이 소요되는 전체 저장소 점검 과정에서 작업이 끊기더라도 처음부터 다시 시작할 필요 없이 완료된 단계를 건너뛰고 이어서 진행할 수 있다.

이러한 모듈형 파이프라인이 제공하는 이점은 명확하다:

  • 정적 패턴 검사 단계가 로컬에서 무상으로 실행되므로 불필요한 파일에 대한 AI 토큰 지출을 사전에 차단한다.
  • 공개된 진입점 인벤토리를 먼저 수집함으로써 정적 검사 규칙이 실제 공격 표면을 놓치는 사각지대를 방지한다.
  • 조사 단계에서 기록된 모델의 판단 근거와 코드 분석 히스토리가 누적 보관되어 사후 감사가 용이하다.
  • 1차 수사 결과에 대해 독립적인 재검증 패스를 둠으로써 단일 모델 추론 시 발생할 수 있는 환각과 과잉 경보를 줄인다.
  • 모든 설정과 결과 산출물이 프로젝트 코드와 격리된 작업 영역에 배치되어 빌드 아티팩트 오염을 방지한다.

3. 초기 설치 및 스캐폴딩과 비용 제어 옵션

Flavio Copes의 설명에 따르면, DeepSec을 코드베이스에 처음 도입할 때 전체 점검을 즉시 시작하지 않고 작업 환경 뼈대만 안전하게 구축하는 방식을 권장한다. 특히 비용이 발생하는 외부 모델 호출 전에 프로젝트 설정을 육안으로 검토할 수 있도록 전용 플래그가 지원된다.

작업 공간 디렉터리와 기본 설정 파일 골격만을 생성하고 AI 처리를 시작하지 않는 스캐폴딩 명령어는 다음과 같다:

# 작업 공간 스켈레톤만 생성하고 패키지 설치나 모델 호출 없이 종료
npx deepsec init --scaffold-only

이 명령을 실행하면 프로젝트 루트에 격리된 작업 영역이 생성되고, 저장소의 성격을 요약한 프로젝트 설명 파일과 자동 생성된 매처 규칙이 자리 잡는다. 개발자는 실제 스캔을 수행하기 전에 이 파일들을 열어 외부 입력이 유입되는 경로가 올바르게 정의되어 있는지, 민감하지 않은 정적 자산이나 튜토리얼 예제 코드가 제외 경로로 설정되어 있는지 점검할 수 있다.

또한 대규모 저장소에서 처음으로 전체 점검을 돌릴 때 예기치 않은 요금 폭탄을 방지하기 위해 엄격한 상한선을 거는 플래그가 제공된다. Flavio Copes 리뷰에 인용된 예시 명령어는 다음과 같다:

# 최대 지출 비용 25달러 및 최대 실행 시간 30분으로 엄격한 제한 설정
npx deepsec init --max-cost-usd 25 --max-duration 30m

원문은 이 명령어가 지정된 금전적 한도나 시간 한계에 먼저 도달할 경우 안전한 체크포인트에서 처리를 스스로 멈춘다고 기술한다. 작업이 멈춘 상태에서 동일한 명령어를 다시 실행하면 이미 조사가 완료된 파일은 건너뛰고 남은 후보군에 대해서만 처리를 이어가므로, 예산을 통제하면서 점진적으로 검사를 확장할 수 있다.

초기 설정 단계에서 관리해야 하는 핵심 설정 요소는 다음과 같다:

  • 스캐폴딩 전용 명령어를 통해 실제 토큰 호출 전에 생성된 위협 모델의 사실 관계를 대조한다.
  • 비용 상한 옵션을 지정하여 허용 가능한 예산 범위 내에서 점진적 검증 사이클을 유지한다.
  • 실행 시간 제한 옵션을 함께 병행하여 특정 복잡한 파일에서 모델이 장시간 지연되는 현상을 방지한다.
  • 환경 변수에 설정된 API 자격증명이 버전 관리 시스템(Git)에 커밋되지 않도록 제외 규칙을 확인한다.
  • 자동 생성된 매처 규칙이 지나치게 광범위한 파일군을 포섭하지 않도록 정규식 범위를 교정한다.

4. 일상적 검사 워크플로우를 위한 4종 기본 명령어

초기화와 환경 구성이 완료된 이후, 실무 개발 환경에서 일상적으로 반복 실행하는 작업 흐름은 패키지 매니저 기반의 4가지 기본 명령어로 나누어진다. Flavio Copes의 리뷰에서 인용된 핵심 명령어 4종은 다음과 같다:

# 1. 로컬 매처 기반 고속 패턴 스캔 (후보 파일 목록 선별)
pnpm deepsec scan

# 2. 선별된 후보 파일을 대상으로 코딩 에이전트 심층 수사 수행
pnpm deepsec process

# 3. 발견된 잠재적 위험 항목에 대한 2차 에이전트 재검증 수행
pnpm deepsec revalidate

# 4. 검증 결과 요약 집계 및 최종 보안 보고서 생성
pnpm deepsec report

각 명령어는 2단계 파이프라인의 특정 책임을 격리하여 담당한다. 첫 번째 스캔 명령은 로컬 CPU 자원만을 사용하여 파일들을 탐색하므로 실행 속도가 빠르고 네트워크 비용이 발생하지 않는다. 이 과정에서 위험 가능성이 있는 패턴을 가진 후보 코드 목록이 작성된다.

두 번째 처리 명령은 작성된 후보 파일들을 배치 단위로 묶어 설정된 코딩 에이전트에게 전달한다. 에이전트는 프로젝트 컨텍스트와 소스코드를 전달받아 함수 호출자, 인증 미들웨어, 유효성 검사 로직을 추적하며 구체적인 위험 징후를 기록한다.

세 번째 재검증 명령은 1차 처리에서 생성된 발견 사항들을 다시 검토한다. 모델의 오판이나 환각 가능성을 걸러내기 위해 의심스러운 경로를 재조사하며, 확인된 결과에 따라 참양성, 위양성, 중복, 불확실 등으로 상태를 재분류한다.

네 번째 보고서 생성 명령은 축적된 상태 데이터를 기반으로 전체적인 통계를 산출하고 마크다운 형태의 개별 이슈 문서를 내보낸다. Flavio Copes의 설명에 따르면 개발자가 매 코드 수정마다 이 네 가지 명령어를 전부 연쇄 실행할 필요는 없으며, 대규모 감사가 아닌 일상 개발 작업에서는 변경된 브랜치만을 대상으로 증분 검사를 수행할 수도 있다.

일상 워크플로우 운영 시 고려해야 할 실무 지침은 다음과 같다:

  • 스캔 명령은 비용이 들지 않으므로 로컬 커밋 전이나 스테이징 단계에서 수시로 실행하여 후보군을 갱신한다.
  • 처리 명령은 실제 API 토큰이 지출되므로 파일 제한 옵션을 적절히 활용하여 단계적으로 적용한다.
  • 재검증 단계는 높은 심각도로 보고된 항목부터 우선 선별하여 실행함으로써 검증 비용을 효율화한다.
  • 보고서 명령으로 생성된 산출물은 민감한 소스코드 경로와 취약점 정보를 담고 있으므로 공개 저장소 노출을 방지한다.

5. Flavio Copes 개인 프로젝트 스캔 사례 — 729개 파일과 504건의 발견

Flavio Copes는 자신이 직접 운영하는 웹사이트인 flaviocopes.com 저장소를 대상으로 DeepSec을 전체 실행한 실제 점검 경험을 공개했다. 그의 설명에 따르면 해당 사이트는 Astro 기반의 정적 페이지 생성이 중심을 이루고 있으나, Cloudflare Pages Functions 기반의 뉴스레터, 후원 결제 웹훅, 강좌 복구 흐름, 브라우저 유틸리티 도구, 운영 스크립트 등 복합적인 서버리스 로직을 포함하고 있었다.

이 스캔에서 나타난 구체적인 수치와 세부 통계는 아래 표와 같다. 거듭 강조하지만, 이 결과는 특정 개발자의 개인 저장소를 대상으로 실행된 단일 사례 연구이며 DeepSec 도구 자체의 전역 표준치나 평균적인 성능 통계가 아니다.

표 2: Flavio Copes 개인 웹사이트(flaviocopes.com) DeepSec 1회성 스캔 결과 상세 (Flavio Copes 리뷰 인용)
분류 항목 세부 통계 수치 비고 및 특이사항

심각도: 일반 버그 (Bug) 378건 단순 계산 오류, UI 결함, 예외 처리 미비 등 일반 결함
입력 토큰 소모량 약 1,440만 (14.4M) 토큰 729개 파일 및 관련 문맥 분석에 소모된 입력량
출력 토큰 소모량 약 170만 (1.7M) 토큰 에이전트 추론 및 상세 보고서 생성에 쓰인 출력량

스캔 결과 화면에 504건이라는 거대한 숫자가 표시되었을 때 저자는 초기 인상으로 상당한 경각심을 느꼈다고 기술한다. 그러나 이 결과는 해결해야 할 즉각적인 보안 사고 목록이 아니라, 도구가 감지해 낸 잠재적 조사 대상의 총합이었다. 또한 이 실행에서는 저자의 로컬 Codex 세션을 활용하여 별도의 추가 API 요금 결제 없이 구독 용량 내에서 처리가 완료되었다고 저자는 덧붙였다.

이 실제 사례에서 확인된 핵심 관전 포인트는 다음과 같다:

  • 정적 사이트 기반이라도 729개 파일 규모의 저장소에서는 수백 건 단위의 잠재적 패턴이 탐지될 수 있다.
  • 보고된 504건 중 절반 이상인 378건은 보안 침해가 아닌 일반적인 소프트웨어 버그로 분류되었다.
  • 전체 점검 과정에서 약 1,440만 개의 입력 토큰과 170만 개의 출력 토큰이 소모되어 대규모 언어 모델 자원이 투입되었다.
  • 초기 실행 결과에 명시된 잠재적 발견이라는 단어는 반드시 후속 재검증을 거쳐야 함을 시사한다.
  • 로컬 계정 세션을 통한 무료 실행이라 하더라도 모델 제공자의 사용량 한도가 소진될 수 있다.

6. 504건이 504개의 수정 작업을 의미하지 않는 이유 — 심각도 분류와 트리아지

Flavio Copes의 리뷰에서 도출된 가장 실무적인 핵심 통찰은 "504건의 발견이 504개의 변경 필요를 의미하지 않습니다"라는 명제에 집약되어 있다. 숫자의 표면적 크기에 압도되어 즉각적인 코드 패치 작업에 돌입하는 것은 잘못된 접근이며, 선별과 트리아지(Triage) 과정이 필수적이라는 의미다.

저자가 분석한 결과, 504건 중 462건은 웹사이트에서 제공하는 소형 브라우저 유틸리티 도구 디렉터리(src/tools 및 src/pages/tools)에 집중되어 있었다. 이 도구들은 서버 환경과 분리된 클라이언트 브라우저에서 격리 실행되는 스크립트들이었으며, 보고된 문제의 대부분인 378건은 계산 로직의 엣지 케이스 처리 누락이나 레이아웃 결함 같은 일반 버그였다. 이들은 코드 품질 측면에서 수정 가치가 있을 수 있으나, 서버를 위협하는 긴급 보안 패치 대상은 아니었다.

또한 도구 컴포넌트와 이를 렌더링하는 Astro 페이지 양쪽에서 동일한 원인의 경보가 중복 집계된 사례들이 존재했다. 이 글의 해석으로는, 단 하나의 공통 유효성 검사 모듈이나 공통 입력 처리 루틴을 개선함으로써 수십 건의 보고 항목이 한꺼번에 해소되는 구조였다.

저자는 에이전트와의 추가 질의를 통해 보고서를 근본 원인과 네트워크 도달 가능성을 기준으로 재그룹화했다. 그 결과 504개의 과업 목록은 다음과 같은 소수의 핵심 집중 영역으로 압축되었다:

  • 서버 측에서 실행되는 결제 처리, 강좌 계정 복구, 공개 양식 제출과 관련된 진입점 경로
  • 사용자 입력을 바탕으로 활성 스크립트나 명령어를 생성하여 렌더링하는 브라우저 도구 계층
  • 신뢰할 수 없는 외부 데이터가 셸 명령어 실행이나 파일시스템 접근으로 이어질 가능성이 있는 로컬 운영 스크립트
  • 단순 제품 백로그로 이관하여 추후 점진적으로 개선할 수 있는 일반 소프트웨어 품질 결함
  • 학생들에게 취약점 원리를 설명하기 위해 의도적으로 작성된 교육용 예제 코드 등 명백한 안전 영역

결국 개발자가 실제로 코드를 수정하고 방어벽을 보강해야 했던 작업은 수백 건이 아니라 한 손에 꼽히는 명확한 핵심 엔드포인트들로 수렴되었다. 원문의 서술대로, 보안 점검 결과의 우선순위는 단순히 도구가 매긴 심각도 라벨이 아니라 외부 공격자가 실제로 해당 입력에 접근할 수 있는가에 의해 결정되어야 한다.

7. 실무 도입 시의 적합성과 경계 조건

DeepSec은 패턴 매칭의 신속성과 AI 에이전트의 문맥 이해력을 결합하여 강력한 감사 기능을 제공하지만, 모든 소프트웨어 프로젝트에 무조건적으로 추천되는 만능 도구는 아니다. Flavio Copes의 리뷰는 도구가 제 몫을 다하는 최적의 대상과 오히려 적합성이 떨어지는 경계 조건을 명확히 짚고 있다.

원문에 따르면 DeepSec이 가장 강력한 효과를 발휘하는 자리는 복잡한 비즈니스 로직, 데이터베이스 연결, 외부 결제 웹훅, 인증 흐름이 얽혀 있는 다계층 웹 애플리케이션 및 백엔드 서비스다. 반면 서버 측 코드가 전혀 없는 순수 정적 웹사이트나, 외부 입력을 받지 않는 독립형 단일 스크립트의 경우에는 불필요한 토큰 지출과 과도한 작업 복잡성을 초래할 수 있다.

실무 환경에서 고려해야 할 도입 가이드라인은 다음과 같다:

  • 사용자 인증, 금융 거래, 민감 개인정보, 권한 인가 로직을 보유한 서비스 저장소에 우선 적용한다.
  • 외부 공격 표면이 존재하지 않는 로컬 유틸리티 라이브러리의 경우 전용 위협 모델 작성이 선행되어야 한다.
  • 단순한 코드 한 줄 수정마다 전체 AI 점검을 돌리는 것은 비효율적이므로 일반 린터와 단위 테스트를 1차 방어선으로 둔다.
  • 신뢰할 수 없는 외부 기여자의 풀 리퀘스트를 로컬 환경에서 직접 스캔할 때는 잠재적 스크립트 실행 위험을 경계한다.
  • 모델이 제시한 수정 권고안을 맹목적으로 병합하지 않고 사람이 직접 방어 경로를 확인한 후 적용한다.
  • 지속적 통합(CI) 환경에 연동할 경우 읽기 전용 권한과 보안 보고서의 비공개 보관 정책을 엄격히 준수한다.

8. 확인하지 못한 것

본 문서의 작성 과정에서 원문 자료의 한계로 인해 확인하지 못한 사항들과 그 사유는 다음과 같다:

  • DeepSec 프로젝트가 2026년 현재 기준으로 공식 제공하는 지원 프레임워크 목록(Next.js, Express 등)의 전체 최신 버전 명세는 2차 리뷰 본문에 전체 항목이 망라되지 않아 확인하지 못했다.
  • Flavio Copes가 729개 파일 점검에 소모한 1,440만 입력 토큰 및 170만 출력 토큰의 수치 외에, 다른 상용 프로덕션 저장소에서 측정한 평균 토큰 단가 및 공식 벤치마크 통계는 원문에 수치가 없어 확인하지 못했다.
  • Vercel Sandbox 마이크로VM을 활용한 원격 분산 스캔 시의 실제 인스턴스 과금 정책과 초당 처리량 데이터는 리뷰에서 세부 비용표가 생략되어 확인하지 못했다.
  • 스캔 당시 적용된 Codex 모델(gpt-5.6-sol) 외에 Claude Code 백엔드를 선택했을 때의 탐지 정확도 및 위양성 비율 차이는 원저자가 비교 실험을 수행하지 않아 확인하지 못했다.
