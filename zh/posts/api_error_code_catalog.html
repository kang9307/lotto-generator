设计一套错误码 - 用数字还是字符串，以及谁来新增

码的价值，只有在客户端能看着它采取不同行动时才产生

2026-08-01 开发/基础设施

引子：客户端在比较错误消息字符串

顺着结算页的一份缺陷报告往下查，遇到了这样一段代码。

if (res.body.message.includes('already paid')) {
  goToReceipt();
}

第一反应是想问这是谁写的。可打开服务端响应之后，就没法责怪那位开发者了。服务端返回的全部内容，就是一个 400 状态码和一句写给人看的话。在这种情况下要区分「订单已支付」和「余额不足」，除了比较句子没有别的办法。

也就是说，这不是客户端的过错，而是服务端从来没有交出一份契约。这份契约的名字就是错误码。

从这里开始，常见的反应分成两派。一派说那就加错误码吧，然后开始列清单。另一派说码一多就管不住了，于是往后拖。两派漏掉的是同一件事。错误码不是文档，是契约。文档错了改掉就好，契约一旦交到对方手里，就不能由你单方面更改。

这篇文章讲的就是设计这份契约。不是要造多少个码，而是该按什么标准去切，为什么码不能改而消息可以改，以及要自动化什么才能让清单不烂掉。

运行环境。下面所有输出都是在 Windows 10 Pro (10.0.19045) 上用 Node.js v22.16.0 (win32) 实际运行的结果。文中出现的 API、错误码与团队名全部是虚构的，只是借订单与支付这个常见领域来复现。脚本都保存成文件后运行。

本文不涉及的内容。输入校验失败时如何指出是哪个字段出错，属于响应模式里 details 内部的问题，会另文讨论。清单被放着不管时如何找出谁还在接收某个码，也是另一个主题。这里只看码本身的设计与寿命。响应的其他契约面在 把 API 文档换成机器可读的契约 与 偏移量分页做不到的事 里。

1. 状态码回答不了的问题

先把问题精确复现一遍。造一个虚构的支付 API，制造六种不同的失败。

node v22.16.0 / win32
--- 1-1. six different failures, one status ---
case            status  message
------------------------------------------------------------------------------
missing id      400     orderId is required
bad id format   400     orderId format is invalid
already paid    400     this order is already paid
window closed   400     the payment window has closed
no money        400     insufficient balance
gateway down    400     gateway temporarily unavailable
distinct statuses observed : [400]

--- 1-2. client branching on status only ---
case            decided action        action it actually needed
------------------------------------------------------------------------------
missing id      ???                   highlight the form field
bad id format   ???                   highlight the form field
already paid    ???                   send user to the receipt
window closed   ???                   reopen the payment sheet
no money        ???                   offer another card
gateway down    ???                   retry in 30 seconds
cases the client could not decide : 6 / 6

六种失败被压成了一个状态码。观测到的不同状态值只有 400。可是看右边那一列，客户端要做的事六种全不一样。写一个只看状态码来分支的函数并实际运行，六个用例全部落到无法判断。

这里有个容易误读的地方。这不是说状态码不好。状态码是代理、缓存与重试层读的维度，在那个用途上它相当称职。问题在于想用那个分辨率去决定给用户看什么。维度不对。

1.1 于是人们开始比较句子

--- 1-3. the workaround: matching the message string ---
missing id      show the raw message
bad id format   show the raw message
already paid    send user to the receipt
window closed   show the raw message
no money        offer another card
gateway down    retry in 30 seconds

--- 1-4. server rewords one message, nothing else changes ---
before : this order is already paid          -> send user to the receipt
after  : This order has already been paid.   -> show the raw message
same failure, different client action : true
nobody deployed the client. nobody changed the status. a copy edit did this.

比较句子之后，有三种情况分得很准。所以这个办法才活得下来。一开始它工作良好，谁也感觉不到问题。

后来有人润色文案。最后那一段就是那个瞬间。只是把首字母改成大写、加了句号、调整了语序，同一种失败下客户端的行为就变了。没有人发布客户端，也没有人改状态码。一次文案修改就做到了。

  • 这类事故在发布记录里留不下痕迹，因为只改了服务端一行，而且还只是一个字符串字面量
  • 测试也很难抓到。服务端测试断言状态码，客户端测试用的是自己准备的假响应
  • 一加上翻译，它就变成只在一种语言下有效的分支。照着英文句子写的比较，在其他语言下全部失败
  • 根本原因是服务端只给出了写给人看的字段。客户端只能拿现有的东西去分支

标准也明确写了这一点。规定 HTTP API 错误响应体格式的 RFC 9457 写道，消费方不应解析给人看的详细文本，那个用途应当使用扩展字段。意思就是，另外给机器一个维度。

2. 用数字还是字符串

决定要做机器维度之后，下一个问题是形态。是 E1043 还是 ORDER_ALREADY_PAID。两种都写了一遍分支代码。

打字错误的结果很关键。当数字清单填得很密时，错一位就会正好落到另一个真实的码上。四个误输中有三个如此，而且这三个既没有异常也没有警告，直接走了另一条分支。而单词打错就不在清单里，会落到默认分支，五个误输全部被这样挡住。

检索也一样。在日志里只搜数字，会因为延迟和字节数恰好取同一个值，导致为了找到真实的两条要看五行。想搜得准就得连字段名一起搜。字符串是零误报。

当然数字也有它的好处。下面这张表就是运行确认过的两边的性质。

性质数字 (E1043)字符串 (ORDER_ALREADY_PAID)判断
按数值段区分域可以 (1000 段, 2000 段)不行数字唯一的实质优势
在堆栈里读得懂不行可以人要读就选字符串

  • 在嵌入式设备或短信这类带宽真的很贵的地方，数字是对的
  • 其余场合十六字节比一个头部还小。你是用这个代价买半年后的可读性
  • 也有折中：把字符串定为契约，数字作为辅助字段一起下发。代价是要维护两个维度
  • 无论选哪种，定了就改不了。改形态等于一次性改掉所有的码

3. 域一多，名字就会撞

选定字符串还不算完。团队只有一个时起的名字，到了三个团队的那一刻就会撞上。我复现了三个团队各自做一份扁平清单的情形。

十一个码穿过网关之后只剩六个。五处相撞，撞上的地方先注册的一方获胜，其余消失。消失的那些团队并不知情，因为单独测试自己的服务时一切正常。

3-2 就是后果。物流查询失败返回 NOT_FOUND，而客户端里那条分支是订单团队先写下的。不是分支错了，是码太含混。只说了「找不到」，没说「找不到什么」。

加上前缀之后，十一个码原封不动地活了下来。零冲突。代价是每个码平均多 7.4 个字符。

这里常见的反问是：服务名不是已经在 URL 里了吗，为什么还要再写一遍。原因在于码会在响应之外继续活着。在日志聚合、指标标签、支持工单、客户端枚举里，码是脱离 URL 单独出现的。在那些地方，NOT_FOUND 什么也没说。

  • 前缀一层就够。把公司、产品、域全堆上去的四十二字符会把日志列撑坏，而且堆上去的信息里真正被用到的只有一层
  • ORDER_ORDER_NOT_FOUND 这种重复词，在域名和对象名相同时会自动产生。用检查器可以抓到
  • _ERROR、_EXCEPTION、_FAILURE 后缀的信息量为零。错误码清单里的每一条本来就都是错误
  • 分隔符只看日志解析的话怎么写都能过，但一旦码成为枚举成员名或指标标签，就只有下划线活得下来。点和连字符不能当生成的常量名
  • 最好定一个长度上限。三十二个字符能同时兼顾日志列对齐与可读性

4. 稳定性就是契约 - 码改不了，消息可以改

这是全文最重要的一节。假设有个一月发布、已经装进用户手机的客户端，收不回来了。在这个前提下，我把服务端改了两次。

node v22.16.0 / win32
--- 4-1. baseline: the shipped client against server v1 ---
case      code                          client action
------------------------------------------------------------------------
paid      ORDER_ALREADY_PAID            showReceipt
funds     PAYMENT_INSUFFICIENT_FUNDS    offerAnotherCard
window    ORDER_WINDOW_CLOSED           reopenPaymentSheet

--- 4-2. v2: every message rewritten, codes untouched ---
paid      showReceipt           same as before: true
funds     offerAnotherCard      same as before: true
window    reopenPaymentSheet    same as before: true
branches broken by the rewrite : 0 / 3

--- 4-3. v3: one code renamed for readability, messages same as v2 ---
paid      ORDER_PAYMENT_ALREADY_COMPLETED   showGenericError      BROKEN
funds     PAYMENT_INSUFFICIENT_FUNDS        offerAnotherCard      ok
window    ORDER_WINDOW_CLOSED               reopenPaymentSheet    ok
branches broken by one rename  : 1 / 3
the user now lands on a generic error screen instead of the receipt.

对比非常鲜明。三条消息全部重写，损坏的分支是零。文案怎么改都无所谓，因为客户端看的是码。而仅仅因为读起来更顺就改掉一个码名，那条分支立刻死了。用户看到的是通用错误页，不是收据。

这就是「消息可以改但码不能改」这条规则的依据。而且这条规则只有在你给了机器一个可读的标识符时才成立。没有码的话就反过来了。客户端会依赖句子，于是被冻住的是消息。大型 API 的设计指南也是按同样的顺序写的：一直提供机器可读标识符的 API 可以改错误文案，而没有标识符就上路的 API 必须把文案固定住。

4.1 那么真想换名字的时候

--- 4-4. a release gate that compares the published code set ---
v2 (messages only)
  added   : (none)
  removed : (none)
  verdict : allow
v3 (one rename)
  added   : ORDER_PAYMENT_ALREADY_COMPLETED
  removed : ORDER_ALREADY_PAID
  verdict : REJECT - a published code disappeared

--- 4-5. the same rename, done without breaking anyone ---
paid      ORDER_ALREADY_PAID            showReceipt           ok
funds     PAYMENT_INSUFFICIENT_FUNDS    offerAnotherCard      ok
window    ORDER_WINDOW_CLOSED           reopenPaymentSheet    ok
v4 (rename announced, old code still emitted)
  added   : (none)
  removed : (none)
  verdict : allow

闸门很简单。与上一版的码集合对比，只要有码消失就让构建停下。新增放行，因为未知的码在客户端只会落到默认分支，不会坏。

真想换名字就照 v4 来。把新名字放进替代码字段做告知，线上传输的值原样不动。真正的替换只在旧码的发出次数归零之后才做。而那件事只有流量能告诉你，文档不行。

  • 码名是值，不是标签。想着以后再起个好名字，这份诱惑最危险
  • 同样的道理，码的 HTTP 状态也改不了。代理与重试层正在拿它做判断
  • 可重试性同样按码固定。它一变，客户端的自动重试行为会无声地改变
  • 反过来，给 details 加字段随时可以。这是加法式变更，老客户端忽略就行
  • 删掉一个码和改名一样危险。所以废弃需要有自己的一套流程

5. 码是固定的，给人读的句子按语言分

如果码是契约，那给人读的句子是什么。我把服务端给句子和客户端造句子两种方式都跑了一遍。

服务端挑句子的方式，关键在回退链。请求语言有就用它，没有就用默认语言，再没有就把码字符串本身发下去。最后这一步看着别扭，但总比空白页强。

5-3 展示了客户端自带翻译的弱点。服务端一开始发出新码，不认识这个码的发布版就没有句子可显示。客户端的发版周期长，用户又会推迟更新，这种状态能持续好几个月。

5-2 是客户端拼装的好处。不把金额写死进服务端句子，只下发数值与币种，客户端就会按自己的本地格式拼出来。服务端不必知道每种语言的分位规则。

所以答案不是二选一，而是两样都要。像 5-4 那样，客户端有自己的模板就用自己的，没有就原样打印服务端的句子。新码出来不会让页面空白，老码也保住了本地格式。

  • 5-5 展示了不该做的事。把码按语言拆开，分支就只在一种语言下活着。三种语言里只触发了一种
  • 码是标识符，不是句子。没有语言是码的性质，不是遗漏
  • 翻译覆盖率在 CI 里就能出表。5-6 里有六个格子是空的
  • 要紧的是翻译缺口和码缺失分量不同。没有翻译还能靠默认语言撑住，没有码客户端就什么都决定不了
  • 还有支持团队的视角。用户截图发过来的是句子。把码一起显示在句子里，工单处理时间会大幅下降

6. 机器读的字段与人读的字段

现在来设计整个响应体。原则只有一条。定下每个字段是给谁看的，并把它写进契约。

node v22.16.0 / win32
--- 6-1. the response body, split by audience ---
{
  "error": {
    "code": "PAYMENT_GATEWAY_UNAVAILABLE",
    "message": "The payment provider is not responding. Please try again shortly.",
    "retryable": true,
    "retryAfterMs": 30000,
    "traceId": "01J8ZQ9K3M7T4V2N6P0R5S8W1X",
    "details": [
      {
        "subcode": "GATEWAY_TIMEOUT",
        "attempt": 2
      }
    ]
  }
}

field         for       contract
------------------------------------------------------------------------------
code          machine   the only field a branch may read
message       human     never parsed, freely reworded, localized
retryable     machine   decides whether the transport retries at all
retryAfterMs  machine   how long to wait, absent means caller decides
traceId       both      machine copies it, human quotes it to support
details       machine   structured extras, additive only

这张表就是契约书，而这份契约生成了第 4 节的规则。下面整理各个字段能改什么。

字段面向能改吗原因
code机器发布后绝对不能分支唯一可以读的字段
message人随时可以契约上就是没人会解析它
HTTP 状态机器按码固定代理与重试层据此判断
retryable机器按码固定自动重试行为会改变
retryAfterMs机器每次调用不同缺失时由调用方决定
traceId两者每次调用不同设计上就是不透明的值
details机器只能新增字段只有加法式变更是安全的

6.1 可重试性放进码里，还是抽成字段

这是现场分歧最多的地方。两种设计并排跑了一遍。

--- 6-2. design A: retryability baked into the code ---
PAYMENT_GATEWAY_UNAVAILABLE_RETRYABLE     retry=true
PAYMENT_GATEWAY_UNAVAILABLE_PERMANENT     retry=false
ORDER_ALREADY_PAID_PERMANENT              retry=false
ORDER_WINDOW_CLOSED_PERMANENT             retry=false

--- 6-3. design B: retryability as a field ---
PAYMENT_GATEWAY_UNAVAILABLE               retry=true
PAYMENT_GATEWAY_UNAVAILABLE               retry=false
ORDER_ALREADY_PAID                        retry=false
ORDER_WINDOW_CLOSED                       retry=false
distinct codes needed : 3

--- 6-4. now the operational question: can it flip at runtime? ---
failures  design A code                             design B
----------------------------------------------------------------------------------------------------
1         PAYMENT_GATEWAY_UNAVAILABLE_RETRYABLE     code=PAYMENT_GATEWAY_UNAVAILABLE retryable=true

9         PAYMENT_GATEWAY_UNAVAILABLE_PERMANENT     code=PAYMENT_GATEWAY_UNAVAILABLE retryable=false

  design A series : {"PAYMENT_GATEWAY_UNAVAILABLE_RETRYABLE":2,"PAYMENT_GATEWAY_UNAVAILABLE_PERMANENT":2}
  design B series : {"PAYMENT_GATEWAY_UNAVAILABLE":4}

只看码的数量，四比三差得不多。差别出在 6-4。支付服务商故障持续、熔断器打开时，同一种失败会从可重试跨到不可重试。在 A 设计里，那时候码字符串本身会移动。

结果就是最后那两行。按码分组的看板上，一次事故被拆成了两条线。B 设计仍然是一条。为什么拆分指标是坏事，在故障处理过程中就能体会到：图突然掉了一半，同时冒出一条新名字的图，而那一刻你说不清它是新故障还是同一个。

--- 6-5. a transport layer that only reads the machine fields ---
PAYMENT_GATEWAY_UNAVAILABLE     retryable=true      sleep 30000ms then retry
ORDER_ALREADY_PAID              retryable=false     surface to caller
SOMETHING_WE_ADDED_LAST_WEEK    retryable=undefined surface to caller

--- 6-6. what happens when a client parses the human field ---
version contains "try again"      contains "unavailable"    text
--------------------------------------------------------------------------------------------------------------
v1      true                      true                      The payment provider is unavailable. Please try again shortly.
v2      false                     false                     We could not reach the payment provider. Retry in a moment.
v3      false                     true                      Payment temporarily unavailable.
two heuristics, three wordings, no stable answer. meanwhile:
v1      code=PAYMENT_GATEWAY_UNAVAILABLE retryable=true  -> unchanged
v2      code=PAYMENT_GATEWAY_UNAVAILABLE retryable=true  -> unchanged
v3      code=PAYMENT_GATEWAY_UNAVAILABLE retryable=true  -> unchanged

--- 6-7. the trace id is the field support actually uses ---
has traceId   what support can do
----------------------------------------------------------------------
true          exact match, 1 request
false         scan by code + time window, thousands of rows
  • 6-5 的第三行很重要。字段根本不存在时被读作不可重试。这是安全的默认值。把缺失字段解释成「可重试」，每出一个新码就会多一条无限重试
  • 6-6 从另一个角度再次印证了第 1 节。两种启发式对上三种文案，没有一个稳定的答案。同一时期码和重试字段一动没动
  • traceId 与码的职责不同。码指出失败的种类，追踪 id 指出具体这一次。支持团队真正用的是后者
  • 没有追踪 id 就只能按码加时间窗扫，范围会是几千条。要求每个错误响应都带上它，成本低而收益大
  • details 是放那些不值得单开一个码的细节的地方。不要把能放进这里的东西变成新码，这是让清单保持精简的诀窍

  • 每个码都写上所有者。没有所有者的码，半年后谁都不敢删
  • 最后一行最重要。UNKNOWN_ERROR 三十天内九百一十八次，那不是一个码，而是九百一十八次没被分类的失败。拆分的第一候选
  • 清单烂掉的信号，看数量不准，看笼统码的占比才准

10. 检查清单与不要做的事

最后，这是一份可以立刻拿去对照现有 API 的清单。

  • 客户端代码里比较消息字符串的分支为 0 个
  • 共用同一个 HTTP 状态的失败能用码区分开
  • 每个错误响应必定带 code 与追踪 id
  • 重试字段缺失时，重试层读作不可重试
  • 可重试性没有被写进任何码字符串
  • 每个码都有域前缀，裸的 NOT_FOUND 这类为 0 个
  • 码清单在一个文件里，文档与客户端常量都从它生成
  • 发布闸门能抓到消失的码
  • 待废弃的码装了发出次数计数
  • 每个码都写了所有者
  • 清楚知道笼统码占全部错误的百分之多少

以及不要做的事。

  • ❌ 只按 HTTP 状态分支 — 同一个 400 有六种理由
  • ❌ 用消息字符串的子串来分支 — 一次文案微调就死
  • ❌ 因为读起来更顺就改已发布的码名 — 已发出去的客户端收不回来
  • ❌ 发布裸的 NOT_FOUND — 只要出现第二个域就必然冲突
  • ❌ 把可重试性写进码字符串 — 故障期间指标会裂成两条线
  • ❌ 加 _ERROR、_EXCEPTION 后缀 — 信息量为零，只增加长度
  • ❌ 按语言翻译码 — 码是标识符，不是句子
  • ❌ 用手维护文档与客户端常量 — 一定会漂移
  • ❌ 只写废弃日期却不看流量 — 删掉的东西还有人在收
  • ❌ 因为「以后也许用得上」而造码 — 未使用的码会侵蚀清单的可信度

总结起来是这样。错误码不是文档，而是与客户端签订的契约。契约的价值，只有在对方能看着它采取不同行动时才产生。所以要按行为分叉的单位去切，而不是按数量；并且已经发出去的码，和消息不同，改不了。这两句话生成了其余所有规则。

# 错误码体系设计 — 可直接复制的模式、判断表与流程

> 来源: braindetox.kr — 设计一套错误码意味着什么
> 依据: Windows 10 / Node.js v22.16.0 实际运行验证（用虚构的订单与支付 API 复现）
> 把这份文件原样贴给 AI，写「按这个标准检查我们的错误响应」即可。
> 前提: 错误码是与客户端签订的契约。一旦发布，它和消息不同，改不了。

## 0. 判断的起点 — 这个码有价值吗

新增一个码之前先回答这三个问题。三个都是「否」，就不要造它。

| 问题 | 回答「是」意味着 |
|---|---|
| 客户端看到这个码会**走不同界面、做不同动作**吗 | 值得用码来分支 |
| 运维需要**单独统计或单独告警**这类失败吗 | 值得作为指标维度 |
| 自动重试的判断**不一样**吗 | 值得作为重试契约 |

- 按**行为分叉的单位**切，而不是按能想出多少种失败切
- 落到同一个界面、同一个动作的两种失败，一个码加 `details` 就够了
- 「以后也许用得上」不是理由。码增加容易，删除几乎不可能

## 1. 响应体模式 — 把机器读的字段和人读的字段分开

```json
{
  "error": {
    "code": "PAYMENT_GATEWAY_UNAVAILABLE",
    "message": "支付服务商没有响应，请稍后再试。",
    "retryable": true,
    "retryAfterMs": 30000,
    "traceId": "01J8ZQ9K3M7T4V2N6P0R5S8W1X",
    "details": [
      { "subcode": "GATEWAY_TIMEOUT", "attempt": 2 }
    ]
  }
}
```

| 字段 | 面向 | 能改吗 | 规则 |
|---|---|---|---|
| `code` | 机器 | **发布后绝对不能** | 分支唯一可以读的字段 |
| `message` | 人 | **随时可以** | 绝不解析，按语言不同 |
| `retryable` | 机器 | 按码固定 | 缺失时读作 `false` |
| `retryAfterMs` | 机器 | 每次调用不同 | 缺失时由调用方决定 |
| `traceId` | 两者 | 每次调用不同 | 人拿去报工单，机器拿去串日志 |
| `details` | 机器 | **只能新增字段** | 不得删除字段或改变含义 |
| HTTP 状态 | 机器 | 按码固定 | 代理与重试层据此判断 |

- **不要**把可重试性写进码字符串（`..._RETRYABLE` / `..._PERMANENT`）
- 原因: 同一种失败在可重试与不可重试之间摆动时，**码本身会移动，指标会裂成两条线**
- 可重试性是**字段**，失败的种类是**码**。这是两个维度

## 2. 码形态判断表

| 判断项 | 选项 | 何时选它 | 代价 |
|---|---|---|---|
| 数字还是字符串 | **推荐字符串** | 日志与堆栈由人来读 | 每次响应多 15 到 20 字节 |
| | 数字 | 带宽真的很贵（嵌入式、短信） | 半年后没人读得懂 |
| 命名空间 | **域前缀** | 域有两个以上 | 每个码长度增加约七个字符 |
| 分隔符 | **下划线** | 码会变成枚举成员或指标标签 | 无 |
| | 点或连字符 | 想让层级在视觉上可见 | 不能作为生成的枚举成员名 |
| 大小写 | **全大写** | 表明这是常量 | 无 |
| 后缀 | **不加** | `_ERROR` `_EXCEPTION` 信息量为零 | 无 |
| 长度 | **32 字符以内** | 日志列对齐与可读性 | 超出就需要缩写 |

### 选数字会失去什么（运行验证过）

- 打错一个字符会落到**另一个有效的码**上，静悄悄地走错分支。打错的单词多半不在名单里，会落到默认分支
- 在日志里搜 `1043`，会连 `latency_ms=1043`、`bytes=1043` 一起搜出来。必须连字段名一起搜才准
- 得到的是: 固定宽度对齐，以及按数值段区分域

## 3. 命名空间规则

```
{域}_{对象}_{状态}     例) ORDER_WINDOW_CLOSED
{域}_{状态}            例) SHIPPING_NOT_FOUND
```

- 没有前缀的 `NOT_FOUND`、`EXPIRED`、`INVALID`、`RATE_LIMIT`，**只要出现第二个域就必然冲突**
- 冲突时网关会保留**先注册的那一份**，其余消失。客户端看不出少了什么
- 不要重复词: `ORDER_ORDER_NOT_FOUND` 不行
- 不要加没有信息的后缀: `..._ERROR`、`..._EXCEPTION`、`..._FAILURE` 不行
- 前缀**一层**就够。`COMMERCE_ORDER_PAYMENT_WINDOW_CLOSED_ERROR` 有 42 个字符，会把日志列撑坏

## 4. 稳定性规则 — 什么能改，什么不能改

| 变更 | 允许 | 原因 |
|---|---|---|
| 全面改写消息文案 | **可以** | 契约上没人会解析它 |
| 增加或修正翻译 | **可以** | 码没有语言 |
| 给 `details` 加字段 | **可以** | 加法式变更 |
| 新增一个码 | **可以**（见下面流程） | 未知的码会落到默认分支 |
| 重命名一个码 | **不可以** | 已发布客户端的分支立刻失效 |
| 删除一个码 | **不可以**（只能走废弃流程） | 同上 |
| 改一个码的 HTTP 状态 | **不可以** | 代理与重试层据此判断 |
| 改一个码的 `retryable` | **不可以** | 自动重试行为会变 |

- **想换名字时**: 把新名字放进 `supersededBy` 字段**只做告知**，线上传输的值原样不动
- 真正替换只能在旧码流量**归零之后**
- 发布闸门: 与上一版的码集合对比，**只要有已发布的码消失就让构建失败**

## 5. 翻译与消息

- 服务端按 `Accept-Language` 挑句子。缺少的语言**回退到默认语言**，再没有就回退到码字符串
- 客户端只用自己的翻译时，**遇到比自己上次发版更新的码，界面就会一片空白**
- 所以两样都发。客户端优先用自己的文案，没有模板时就原样打印服务端的 `message`
- 数字、金额、日期不要写死在服务端句子里，用 `details` 或 `params` 下发，**让客户端按本地格式拼装**
- **绝不要翻译码本身。** 造出 `ORDER_ALREADY_PAID_KO` 这种东西，分支就只在一种语言下有效
- 在 CI 里放一份语言覆盖率报告。翻译的缺口靠回退撑得住，**码缺失撑不住**

## 6. 新增一个码的流程

1. **先写行为。** 一句话：客户端会做 X。写不出来就说明不需要新码
2. **在现有名单里找同样的行为。** 同样的动作加同样的 HTTP 状态加同样的重试判断，那就是 `details`，不是新码
3. 起名: `{域}_{对象}_{状态}`，全大写，下划线，32 字符以内
4. 加进注册表（单一文件）: `code` / `http` / `retryable` / `action` / `since` / `owner`
5. 跑检查器（第 8 节）。零错误才能合并
6. 文档和客户端常量**不要手写**，从注册表生成
7. 写上所有者。没有所有者的码，半年后谁都不敢删

## 7. 废弃一个码的流程

1. 在注册表写上 `deprecated` 日期和 `supersededBy` — **这一刻什么都不会消失**
2. 服务端继续发出旧码，新码并列添加
3. **给旧码的发出次数装上计数**
4. 连续 30 天为零才是删除候选。不为零就**先去找调用方**
5. 只从注册表删除。客户端常量与文档靠重新生成跟上

- 废弃日期不会让一个码消失。**流量才会**
- 如果 `UNKNOWN_ERROR` 或 `INTERNAL` 的发出次数很高，那不是一个码，而是**一堆没被分类的失败**。拆分的第一候选

## 8. 自动校验 — 注册表只有一处，其余靠生成与比对

针对注册表本身的检查规则:

- [ ] `duplicate-code` — 同一个名字登记了两次
- [ ] `bad-shape` — 违反 `^[A-Z][A-Z0-9]*(_[A-Z0-9]+)*`
- [ ] `too-long` — 超过 32 字符
- [ ] `repeated-word` — 前缀与主体重复同一个词
- [ ] `useless-suffix` — 以 `_ERROR`、`_EXCEPTION`、`_FAILURE` 结尾
- [ ] `vague-name` — `INTERNAL`、`UNKNOWN_ERROR`、`INVALID`、`FAILED` 这类笼统词
- [ ] `no-namespace` — 没有下划线，也就没有域前缀
- [ ] `unstable-http` — 同一个码登记在两个状态码下
- [ ] `retryable-4xx` — 标了可重试，却是 401/408/429 之外的 4xx
- [ ] `non-retryable-5xx` — 5xx 却标为不可重试
- [ ] `deprecated-orphan` — 只标了废弃却没有替代码

与客户端源码比对:

- [ ] **死分支** — 客户端在分支的码注册表里没有，永远不会触发 → **让构建失败**
- [ ] **未处理的码** — 服务端能发出但客户端没有分支 → 以覆盖率数值报告
- [ ] 对每个死分支，**按词元重合度推荐最接近的已注册码**

生成物:

- [ ] 客户端常量（冻结对象或枚举）
- [ ] 文档表格（码 / HTTP / 可重试 / 客户端该做什么）
- [ ] 码清单快照 — 发布闸门用它与上一版比对

## 9. 检查清单

- [ ] 客户端代码里**比较消息字符串的分支为 0 个**
- [ ] 共用同一个 HTTP 状态的失败**能用码区分开**
- [ ] 每个错误响应**必定**带 `code` 与 `traceId`
- [ ] `retryable` 缺失时，重试层**读作 `false`**
- [ ] 可重试性**没有被写进任何码字符串**
- [ ] 每个码都有域前缀，裸的 `NOT_FOUND` 这类**为 0 个**
- [ ] 码清单在**一个文件**里，文档与客户端常量都从它**生成**
- [ ] 发布闸门能抓到**消失的码**
- [ ] 待废弃的码**装了发出次数计数**
- [ ] 每个码都写了**所有者**
- [ ] 动作加状态加重试判断都相同的那几组码，**按周期复审**
- [ ] **清楚知道** `UNKNOWN_ERROR` 这类占全部错误的百分之多少
- [ ] CI 里有翻译覆盖率报告

## 10. 不要做的事

- ❌ 只按 HTTP 状态分支 — 同一个 400 有六种理由
- ❌ 用消息字符串的子串来分支 — 一次文案微调就死
- ❌ 因为读起来更顺就改已发布的码名 — 已发出去的客户端收不回来
- ❌ 发布裸的 `NOT_FOUND` — 只要出现第二个域就必然冲突
- ❌ 把可重试性写进码字符串 — 指标会裂成两条线
- ❌ 加 `_ERROR`、`_EXCEPTION` 后缀 — 信息量为零，只增加长度
- ❌ 按语言翻译码 — 码是标识符，不是句子
- ❌ 用手维护文档与客户端常量 — 一定会漂移
- ❌ 只写废弃日期却不看流量 — 删掉的东西还有人在收
- ❌ 因为「以后也许用得上」而造码 — 未使用的码会侵蚀清单的可信度
