Write Code Like a Human Will Maintain It

In the age of AI-generated code, your codebase doubles as the AI's training context — merge a bad pattern and the next generation learns it as house style

2026-07-12 Dev & Infra

Introduction: Why Care More About Code Quality When AI Writes the Code

Now that coding agents can churn out hundreds of lines a day, discipline around "how to write it" paradoxically tends to loosen. On the assumption that AI will clean it up later anyway, it has become common to bolt on one more conditional as a stopgap, copy-paste similar logic, leave a TODO comment, and move on. As of July 2026, an article from unstack.io, surfaced on GeekNews (news.hada.io), pushed back directly on that assumption: because AI writes code by referencing your existing codebase, a sloppy pattern you casually merged becomes the baseline the next AI-generated code learns from.

I think this argument is not just another clean-code lecture — it is a structural issue every engineering team needs to reckon with now that AI coding tools are deeply embedded in daily work in 2026. This piece walks through my own analysis of why a codebase effectively functions as an AI prompt, how severe the code-quality erosion looks in real data, and what teams concretely need to change to break the cycle. This article follows up on my earlier piece, The Real Purpose of Code Review — Finding Code That Will Be Hard to Maintain, but from a different angle. That piece asked, at the level of a single PR, "is this code maintainable?" This one asks a codebase-wide, time-axis question: "what precedent does merging this code set for the next AI-generated code?"

1. The Core Insight — Your Codebase Is Now the AI's Prompt

When only humans wrote code, the cost of a bad habit was mostly paid by the person who wrote it. A messy function you wrote yourself came back to bite you, or at most inconvenienced a few teammates. With a coding agent generating code every day, the math changes.

1.1 LLMs Are Sponges — They Absorb Whatever Pattern Is Already There

unstack.io put this concisely. In the source's own phrasing, 'LLMs are sponges' (source: unstack.io). Asked for a new feature, a coding agent does not imagine an ideal design from a blank page. It looks first at the files currently open, recent commits, and similar code already sitting in the repository, and follows that style. In effect, what is in your codebase functions as the real prompt behind every request. Every shortcut merged into the repo gets etched into the model as a signal that says "this is how it's done here."

1.2 The Fifth Copy — The Moment Duplication Becomes "Our Style"

The place this mechanism actually bites is repetition. Say you add API endpoints one at a time, each carrying the same permission-check logic, and each time you copy-paste the same conditional block instead of extracting it into a shared helper. The third or fourth copy still looks like a minor shortcut. But ask the AI for a fifth endpoint, and instead of an ideal solution, the model treats the four existing copies in the repo as its reference point and produces a fifth. Worse, when you later ask for a refactor, the model tends to preserve all five rather than consolidate them, precisely because that is what the codebase already looks like. A single shortcut quietly gets promoted to "our project's style."

2. What the Data Shows — Less Refactoring, More Copy-Paste

This is not just an anecdotal worry — it shows up in recent large-scale code-change data. Here are the key figures I cross-checked.

2.1 Refactoring Share Cut in Half, Copy-Paste Rising

GitClear's 2025 report, based on an analysis of over 211 million lines of code changes, found that the share of changed lines classified as refactoring fell from about 25% in 2021 to under 10% in 2024, while lines classified as copy-pasted rose from 8.3% to 12.3% over the same period. The report also found that the frequency of duplicated code blocks rose eightfold during 2024 alone. Structured work to reuse code is shrinking, while copying existing code to fit a new requirement is rising fast.

2.2 AI-Generated PRs Carry More Defects, and Debt Survives

A 2026 study analyzing over 8.1 million pull requests across more than 4,800 engineering teams gives more direct numbers. PRs containing AI-generated code carried roughly 1.7 times more defects per PR than human-written PRs (10.83 vs 6.45), and technical debt rose 30-41% in the year following AI tool adoption. More concerning, 22.7% of defects traced back to AI introduction were still alive at HEAD — meaning a substantial share of shortcuts that got merged do not fade away on their own; they accumulate in the codebase.

2.3 Maintenance Costs Compound

Industry analysis warns that unmanaged AI-driven technical debt left unaddressed can push maintenance costs to roughly 4x the initial baseline by year two. When you layer declining refactoring and rising copy-paste on top of higher per-PR defect rates and defects that persist, this looks less like a one-off bad habit and more like a self-reinforcing debt structure.

3. Why This Is a New Problem — The Codebase Version of "Garbage In, Garbage Out"

"Garbage in, garbage out" (GIGO) originally described the quality of the large training datasets used to train a model — contaminated training data produces contaminated output. But now that coding agents read repository context in real time to generate answers, I think this principle resurfaces in a far more immediate and personal form.

The old GIGO problem was one step removed — only the organization training the model needed to worry about it. Now, a single PR you merge today is immediately folded into the context an AI will reference in this same repository tomorrow. There is no separate data-curation stage the way there is for training a model; the moment you hit merge is the moment you register a training signal for the next generation. This immediacy, and the personalized feedback loop it creates, turns the problem from "something that will resolve itself as AI improves" into "something that compounds daily, one habit at a time." The loop spins faster in repositories with weak team conventions, and faster still where code review is a rubber stamp.

4. The Discipline of Writing Code a Human Can Read and Fix

Breaking this cycle starts, in the end, by going back to basics. In the AI era, though, those basics gain one more reason beyond "so future-me has an easier time" — "so the next generation of AI-generated code doesn't learn this as the standard."

4.1 Clear Names and Small Functions

When a name reveals intent and a function does exactly one thing, both humans and AI learn the right pattern when they use that code as a reference point. A name like data or temp2 paired with a 200-line function, on the other hand, sends a false signal to human and AI alike: "this is just how things are lumped together here."

4.2 Consistency — One Solution per Problem

If the same problem is solved three different ways scattered across a repository, the AI has no clear signal for which to follow and often invents a fourth. If the solution instead converges on one pattern, the next generated code is far more likely to follow that single pattern strongly. Consistency is not aesthetics — it is a practical device that narrows the signal AI references and raises its accuracy.

4.3 Clean Up Shortcuts on the Spot — TODO Debt Accrues Interest

"I'll refactor this later" TODO comments were rarely honored even back when only humans wrote code, but the AI era adds one more risk. Even if you later ask an AI to "clean up these TODOs," there's no guarantee the model will sweep the entire repository and catch every last copy. There are reported cases where a model asked to refactor, out of caution to preserve existing patterns, missed some copies entirely. Cleaning up duplication or a shortcut inside the very PR where it appears is far safer than trying a batch cleanup later.

5. Why Code Review, Linting, and Conventions Matter More in the AI Era

There is an interesting twist here. The more AI writes, the more the "slow" human mechanisms — code review, linting — grow in importance rather than shrink.

5.1 AI Ignores Docs, Not CI Lint Failures

Coding agents often skip the recommendations written in a convention doc. But when a linter fails a build in the CI pipeline, that failure cannot be ignored. In other words, an automated rule that actually fails when violated controls an AI agent's behavior far more reliably than a "please write it this way" document. Teams equipped with static-analysis rules that catch architectural violations — dependencies crossing forbidden layers, disallowed patterns — hold AI-generated code far more consistent than teams without them.

5.2 The Rise of Repository-Level Standards — AGENTS.md

The AGENTS.md specification, formalized in August 2025 through a collaboration led by OpenAI across several AI coding tools, established the convention of placing standardized instructions for AI agents at the root of a repository. As of December 2025, more than 60,000 open-source projects had adopted the format, and more than twenty AI coding tools support it. This reflects a shift from treating team conventions as a wiki page only humans read, to promoting them into a repository-level standard AI actually references.

5.3 Code Review Is Now the Gatekeeper of Next-Generation Training Data

The piece I referenced earlier, The Real Purpose of Code Review, looked at whether an individual PR is maintainable. In the AI era, one more lens needs adding. A shortcut a reviewer approves today does not stay contained to that one PR — it gets registered as a reference point for the next generation of AI-written code. Code review is no longer just "is this code right now" but also "what pattern does merging this establish as standard in this repository going forward." As AI review tools increasingly handle the first pass on mechanical issues like security vulnerabilities and style violations, what's left for the human reviewer narrows toward precisely this long-horizon precedent judgment.

6. A Practical Checklist — What to Apply Today

Five concrete practices I recommend to teams.

  • Extract duplication the moment you spot it. The instant you're about to copy similar logic a third time is the signal to pull it into a shared helper. "Later" usually never comes.
  • Enforce what you can through linting, not documentation. Put architectural boundaries, forbidden patterns, and naming rules into CI so neither AI nor humans can violate them.
  • Keep an AGENTS.md or equivalent repository-level standards file. Put team conventions where AI actually reads them.
  • Add "will this become a precedent for the next AI-generated code?" to your review comments. Correct functionality with a bad pattern is still grounds for a flag.
  • Track AI-generated PRs separately. Apply stricter review and quality gates to AI-generated code early on, and watch quality metrics — defect rate, revert frequency — separately from human-written code.

Conclusion

The more AI writes code on your behalf, the more reason there is — not less — to care about how humans write code. A codebase is no longer just an artifact humans read; it is a living prompt that shapes the next generation of AI-generated code. The data already shows the process by which one merged shortcut becomes a fifth copy, and those copies harden into project style. Declining refactoring, rising copy-paste, and defects in AI-generated PRs that persist for a long time do not stop on their own. Clear names, small functions, a single converged solution, cleaning up on the spot, and lint and review that are enforced rather than merely documented — these five things remain the oldest, and still the most reliable, way to keep a codebase healthy, even in the AI era.
