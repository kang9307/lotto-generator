LLM 평가의 사각지대 2026 - 지식 벤치마크로는 알 수 없는 AI 행동 품질의 진실

MMLU Won't Tell You If Your LLM Hallucinates in Production - The 2026 Evaluation Gap

2026-05-28 IT/기술

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 벤치마크 1위 모델이 프로덕션에서 실패하는 이유

2026년 5월 현재, LLM 벤치마크 순위표는 과거 어느 때보다 치열하다. MMLU 90점 이상은 기본이고, GPQA-Diamond에서 70%를 넘기는 모델이 분기마다 쏟아진다. 그런데 본인이 주변 팀에서 반복적으로 듣는 불만은 정확히 이것이다. '벤치마크 1등이라 골랐는데, 프로덕션에서 왜 이 모양이냐.' 고객 문의에 없는 정보를 지어내고, 20턴 넘어가면 앞 대화를 잊고, API 도구를 엉뚱한 파라미터로 호출한다. 벤치마크 점수와 체감 품질 사이의 간극이 2026년 AI 도입 팀이 직면한 가장 실질적인 문제다.

이 글의 직접 계기는 2026년 5월 27일 news.hada.io에 2번 토픽(12점)으로 올라온 'LLM Evaluation Blindspots'다. 영문 원문은 벤치마크의 구조적 한계를 지적하며 '지식(Knowledge)과 행동(Behavior)의 측정이 분리되어야 한다'는 논점을 전개한다. 본인이 이 주제를 기다렸던 이유는, 한국 IT 현장에서 LLM 선택 기준이 여전히 '리더보드 순위 → 가격 → 레이턴시' 순서에 머물러 있기 때문이다. 행동 품질을 측정하지 않으면 모델을 바꿔도 같은 실패가 반복된다.

이 글은 세 가지를 한다. 첫째, 지식 벤치마크와 행동 벤치마크의 차이를 5가지 축으로 정리한다. 둘째, 프로덕션에서 나타나는 3가지 사각지대(환각, 컨텍스트 일관성, 도구 호출 안정성)를 분석한다. 셋째, 실무에서 LLM을 평가하는 7가지 방법과 도구를 제시한다. 본인의 핵심 주장은 하나다. 공개 벤치마크는 후보 좁히기에만 쓰고, 최종 결정은 반드시 본인 서비스 데이터로 해야 한다.

1. '지식 벤치마크'란 - MMLU, GPQA, ARC 등의 한계

지식 벤치마크는 모델이 '무엇을 아는가'를 측정한다. 대표적 예시는 다음과 같다.

  • MMLU (Massive Multitask Language Understanding): 57개 학문 분야의 객관식 15,908문항. 대학 수준 지식을 묻는다.
  • GPQA (Graduate-Level Google-Proof Q&A): 대학원 수준의 물리·화학·생물 448문항. PhD 학생도 검색 없이 틀리도록 설계되었다.
  • ARC (AI2 Reasoning Challenge): 초등학교 과학 7,787문항 중 어려운 세트(ARC-Challenge)로 추론 능력을 측정한다.
  • HellaSwag: 상식 추론 10,042문항. 문장 완성 형태로 일상 상식을 평가한다.

이 벤치마크들의 공통점은 정답이 하나이고, 선택지 중 고르는 방식이라는 것이다. 이 구조가 만드는 한계는 크게 세 가지다.

한계 1: 실제 사용 패턴과 다르다. 프로덕션에서 사용자는 객관식을 내지 않는다. '이 에러 로그 보고 원인 분석해줘', '계약서 3조 해석해줘'처럼 열린 질문을 던진다. 객관식 정답률과 열린 질문 응답 품질 사이의 상관관계는 생각보다 낮다.

한계 2: 벤치마크 오염(Contamination)에 취약하다. MMLU 문항이 학습 데이터에 포함되면 점수가 올라가지만 실력이 올라간 것은 아니다. 2025년 여러 연구가 주요 모델의 MMLU 오염률이 10~30%에 달한다고 보고했다.

한계 3: 포화 상태에 도달했다. 2026년 기준 상위 모델의 MMLU 점수는 90~93점대에 몰려 있다. 차이가 1~2점이면 통계적으로 유의미하지 않고, 순위 변동은 프롬프트 형식이나 few-shot 수에 따라 뒤집힌다. 사실상 '누가 1등인가'를 MMLU로 가리는 것은 의미가 없다.

2. '행동 벤치마크'란 - SWE-bench, HumanEval, AgentBench의 의미

행동 벤치마크는 모델이 '무엇을 할 수 있는가'를 측정한다. 지식이 아니라 실행 능력이 평가 대상이다.

  • SWE-bench: 실제 GitHub 이슈 2,294개를 주고 코드 패치를 생성하게 한다. 패치가 기존 테스트를 통과해야 정답이다. 2026년 5월 기준 최고 성적은 약 55% (SWE-bench Verified)로, 아직 절반 수준이다.
  • HumanEval / HumanEval+: 164개 Python 함수 구현 문제. 생성한 코드가 테스트 케이스를 통과해야 정답. 단순 코드 생성 능력을 측정하지만 실제 소프트웨어 엔지니어링(파일 수정, 의존성 처리 등)은 포함하지 않는다.
  • AgentBench: 웹 브라우징, 코드 실행, 데이터베이스 조작, 게임 등 8가지 환경에서 에이전트로서의 행동을 종합 평가한다.
  • GAIA: 실세계 질문 466개로, 웹 검색·파일 분석·계산 등 다단계 추론과 도구 사용을 복합 평가한다.

행동 벤치마크의 장점은 프로덕션 시나리오에 가깝다는 것이다. 코드를 생성하고, 테스트를 통과시키고, 도구를 호출하는 행위는 실제 사용에서 일어나는 일이다. 그러나 행동 벤치마크도 완벽하지 않다. SWE-bench가 측정하는 것은 '주어진 이슈를 패치로 해결하는 능력'이지, '어떤 이슈를 먼저 해결해야 하는지 판단하는 능력'이 아니다. 행동 벤치마크는 지식 벤치마크보다 예측력이 높지만, 여전히 프로덕션의 전체 그림을 담지는 못한다.

3. 지식 vs 행동 - 5가지 핵심 차이

본인이 정리한 지식 벤치마크와 행동 벤치마크의 핵심 차이는 다음 5가지 축으로 나뉜다.

비교 축 지식 벤치마크 (MMLU, GPQA 등) 행동 벤치마크 (SWE-bench, AgentBench 등)
측정 대상 정적 지식 보유량 동적 작업 수행 능력
평가 방식 정답 선택 (객관식) 실행 결과 검증 (테스트 통과, 환경 변화)
난이도 조절 문항 교체 (오염 가능성 높음) 실제 이슈 기반 (오염 저항성 높음)
벤치마크 gaming 저항성 낮음 (학습 데이터 포함 시 점수 급등) 중간 (실행 환경 재현 필요)
프로덕션 예측력 낮음 (지식 ≠ 행동) 중간 (행동 ≈ 프로덕션 일부)
본인 해석: 지식 벤치마크는 '이 사람이 교과서를 읽었는가', 행동 벤치마크는 '이 사람이 일을 할 수 있는가'에 해당한다. 채용 면접에서 필기시험 만점자가 실무에서 실패하는 것과 같은 구조적 문제다.

4. 프로덕션에서 나타나는 3가지 사각지대

지식 벤치마크도, 행동 벤치마크도 잡아내지 못하는 프로덕션 사각지대가 있다. 본인이 한국 팀들과 일하며 가장 자주 마주하는 세 가지를 정리한다.

4-1. 환각(Hallucination) 빈도

환각은 모델이 사실이 아닌 정보를 그럴듯하게 생성하는 현상이다. MMLU 점수가 높다고 환각이 적은 것이 아니다. 환각은 모델이 '모른다'고 말하지 않고 '아는 척하는' 행동이며, 이것은 지식 보유와 별개의 축이다.

현재 환각을 직접 측정하는 공개 벤치마크는 TruthfulQA, HaluEval 정도인데, 이것들도 프로덕션 환각의 일부만 포착한다. 가장 위험한 환각은 '도메인 특화 지식에서 미세하게 틀리는 것'이다. 법률 문서에서 조문 번호를 한 자리 바꾸거나, 의료 정보에서 용량을 잘못 말하는 종류의 환각은 범용 벤치마크로 측정할 수 없다.

실무 대응: 본인 서비스 도메인의 핵심 사실 100~500개를 골든 데이터셋으로 만들고, 모델이 이 사실을 정확하게 인용하는지 주기적으로 측정해야 한다. 환각률이 5% 이상이면 프로덕션 투입은 신중해야 한다.

4-2. 긴 대화 컨텍스트 일관성

컨텍스트 윈도우가 128K, 200K로 늘어나면서 '긴 컨텍스트를 처리할 수 있다'는 주장이 마케팅 포인트가 되었다. 그러나 Needle-in-a-Haystack 테스트를 통과하는 것과, 20턴 대화에서 5턴 전 사용자 발화와 모순되지 않는 것은 전혀 다른 능력이다.

본인이 관찰한 패턴에서, 대부분의 모델은 10~15턴 이후부터 초기 대화 맥락을 '희석'시킨다. 사용자가 처음에 '비용 절감이 최우선'이라고 말했는데, 15턴 뒤에는 성능 최적화 관점의 답변을 한다. 이것은 벤치마크에서 측정되지 않지만, 고객 만족도에 직결된다.

실무 대응: 실제 고객 대화에서 10턴 이상 이어진 세션을 50개 이상 추출하고, 첫 턴의 사용자 의도와 마지막 턴의 모델 응답이 일관되는지 수동 또는 자동(LLM-as-Judge)으로 평가해야 한다.

4-3. 도구 호출(Tool Use) 안정성

2026년 LLM 활용의 핵심은 RAG와 도구 호출이다. 모델이 검색 API를 호출하고, 결과를 해석하고, 다음 도구를 선택하는 파이프라인에서 문제가 가장 자주 발생한다. 도구 호출 안정성 문제는 세 단계로 나뉜다.

  • 호출 판단 오류: 도구를 호출해야 할 때 호출하지 않거나, 호출할 필요 없을 때 호출한다.
  • 파라미터 오류: 올바른 도구를 선택하지만, 잘못된 인자를 전달한다 (날짜 형식 틀림, 필수 필드 누락 등).
  • 결과 해석 오류: 도구 응답을 받았지만, 에러 메시지를 정상 결과로 해석하거나 부분 결과만 사용한다.

AgentBench가 일부 도구 사용 시나리오를 측정하지만, 프로덕션 도구 호출의 복잡성(인증, 속도 제한, 비결정적 응답 등)은 포함하지 않는다.

실무 대응: 본인 서비스의 도구 호출 로그를 1주일 수집하고, 호출 성공률·파라미터 정확도·결과 해석 정확도를 3단계로 나눠 측정해야 한다. 도구 호출 성공률이 90% 미만이면 워크플로 안정성이 확보되지 않은 것이다.

5. 벤치마크 Gaming - 왜 점수는 올라가는데 체감은 안 변하나

벤치마크 gaming은 실제 능력 향상 없이 벤치마크 점수만 올리는 행위를 말한다. 2024~2026년 사이에 드러난 주요 gaming 패턴은 다음과 같다.

  • 학습 데이터 오염: 벤치마크 문항을 학습 데이터에 포함시킨다. 의도적이지 않더라도, 대규모 웹 크롤링 시 벤치마크 문항이 자연스럽게 포함된다.
  • 프롬프트 최적화: 특정 벤치마크의 프롬프트 형식에 맞춰 RLHF를 튜닝한다. 실제 사용에서 이 프롬프트 형식이 아닌 경우 성능이 떨어진다.
  • 선택적 보고: 좋은 점수만 발표하고, 나쁜 점수는 공개하지 않는다. 10개 벤치마크 중 3개에서 1등이면 '리더보드 3관왕'이라고 마케팅한다.
  • 버전 체리피킹: 동일 벤치마크의 여러 버전(Lite, Verified, Full) 중 가장 유리한 버전을 선택한다.

결과적으로, 모든 주요 모델의 벤치마크 점수는 2024년 대비 5~15% 올랐지만, 프로덕션 환각률이 같은 비율로 줄었다는 증거는 없다. 이것이 '점수는 올라가는데 체감은 안 변하는' 현상의 본질이다.

경고: 벤치마크 점수를 모델 선택의 유일한 기준으로 삼으면, gaming에 능숙한 모델을 고르게 된다. 이것은 면접 기술만 좋은 지원자를 뽑는 것과 같다.

6. 실무에서 LLM을 평가하는 7가지 방법

본인이 정리한 실무 LLM 평가 방법은 다음 7가지다. 규모와 여건에 따라 순서대로 도입하면 된다.

방법 1: 골든 데이터셋 정답률

본인 서비스의 핵심 시나리오 100~500개를 수집하고, 기대 응답(정답 또는 정답 범위)을 정의한다. 모델이 이 데이터셋에서 몇 %를 맞추는지 측정한다. 가장 기본이지만 가장 강력한 방법이다. 골든 데이터셋이 없으면 다른 모든 평가는 의미가 반감된다.

방법 2: 환각 탐지 전용 테스트

모델이 확실히 모르는 질문(존재하지 않는 법률, 가상의 인물)을 의도적으로 던지고, '모르겠다'고 대답하는 비율을 측정한다. 이 비율이 낮을수록 환각 위험이 높다. 별도로, 골든 데이터셋의 정답과 모델 응답을 대조하여 사실 오류율을 계산한다.

방법 3: 긴 컨텍스트 일관성 측정

실제 고객 대화에서 15턴 이상 세션을 추출하고, 첫 턴의 사용자 의도와 마지막 턴의 모델 응답의 정합성을 1~5점으로 채점한다. 자동화하려면 LLM-as-Judge를 쓸 수 있다.

방법 4: 도구 호출 성공률 추적

모든 도구 호출을 로깅하고, 호출 판단 정확도·파라미터 정확도·결과 해석 정확도를 분리해서 추적한다. 전체 성공률(세 단계 모두 성공)이 모델 비교의 핵심 지표다.

방법 5: A/B 테스트로 사용자 체감 비교

트래픽의 일부를 새 모델로 라우팅하고, 사용자 만족도(좋아요/싫어요, 재시도율, 세션 길이)를 비교한다. 벤치마크 점수와 사용자 체감이 불일치하는 경우가 적지 않다.

방법 6: LLM-as-Judge 자동 채점

강력한 모델(Claude 4.7 Opus, GPT-5 등)을 심판으로 세우고, 다른 모델의 응답을 채점하게 한다. 비용이 낮고 확장 가능하지만, 심판 모델 자체의 편향(자사 모델에 관대)을 교정해야 한다. 교차 심판(A가 B를 채점, B가 A를 채점)이 권장된다.

방법 7: 비용 대비 품질 효율 지표

같은 점수를 달성하는 데 드는 비용(토큰당 가격 x 평균 토큰 수)을 모델별로 비교한다. 품질이 5% 높지만 비용이 3배인 모델은, 한국 스타트업 환경에서 합리적 선택이 아닐 수 있다.

7. Eval Harness 도구 비교

위 7가지 방법을 실행할 때 쓸 수 있는 도구를 4가지로 나눈다.

도구 강점 약점 적합한 팀
LangSmith LangChain 생태계 통합, 트레이싱+평가 일체, 시각화 우수 LangChain 종속, 비LangChain 파이프라인 통합 불편 LangChain 기반 팀

8. 한국 IT 환경 적용 - 한국어 LLM 평가 방법

한국어 LLM 평가에는 영어권과 다른 세 가지 고려사항이 있다.

8-1. 한국어 벤치마크의 부재

MMLU 한국어 번역본(KMMLU)이 존재하지만, 번역 품질이 고르지 않고 한국 특화 지식(한국 법률, 한국사, 한국 의료 제도)을 충분히 담지 못한다. KoBEST, KorQuAD 같은 한국어 벤치마크는 규모가 작고 갱신이 느리다. 결과적으로, 한국어 성능을 공개 벤치마크로 판단하기 어렵다.

8-2. 한국어 환각의 특수성

한국어 모델은 영어 모델과 다른 패턴의 환각을 보인다. 한자어 혼동(권리/권리금), 조사 오류로 의미가 바뀌는 경우, 한국 법률 조문 번호 오류 등이 한국어 특유의 환각 패턴이다. 영어 기준 환각 테스트를 한국어에 그대로 적용하면 이런 패턴을 놓친다.

8-3. 실무 권장

  • 한국어 골든 데이터셋을 자체 구축한다. 영어 데이터셋 번역이 아니라, 실제 한국어 고객 질문에서 추출한다.
  • 한국어 환각 테스트를 별도로 설계한다. 존재하지 않는 한국 법률, 가상의 한국 지명, 잘못된 한국사 사실을 포함한다.
  • 한국어 LLM-as-Judge를 구성할 때, 심판 모델이 한국어 뉘앙스를 이해하는지 검증한다. 영어로 채점 기준을 주면 한국어 미세 차이를 놓칠 수 있다.

9. 시니어가 알아야 할 5가지 - 모델 선택 기준 재정립

LLM을 도입하거나 교체할 때, 시니어 엔지니어와 테크 리드가 알아야 할 기준을 5가지로 정리한다.

  1. 벤치마크는 후보 좁히기에만 쓴다. 상위 3~5개 모델을 선별하는 1차 필터 역할이다. 최종 선택은 반드시 본인 데이터로 한다.
  2. 행동 벤치마크를 지식 벤치마크보다 우선한다. SWE-bench 성적이 MMLU 성적보다 프로덕션 예측력이 높다. 코딩 용도가 아니더라도, 행동 벤치마크 성적이 높은 모델이 도구 호출·멀티턴 대화에서도 더 안정적인 경향이 있다.
  3. 환각률을 공식 평가 지표에 포함시킨다. 레이턴시, 비용, 정확도 옆에 환각률 열을 추가하고, 분기별 추적한다.
  4. 모델 교체 비용을 과소평가하지 않는다. 프롬프트 재작성, 가드레일 재설정, 테스트 재실행, 사용자 재교육까지 모델 교체의 전체 비용을 산정해야 한다. 벤치마크 2점 차이로 모델을 바꾸는 것은 비합리적이다.
  5. 내부 eval 파이프라인을 자산으로 관리한다. 모델은 바뀌지만, eval 파이프라인은 남는다. 잘 만든 골든 데이터셋과 자동 평가 파이프라인은 팀의 장기 경쟁력이다.

10. 2026 하반기 평가 트렌드

2026년 하반기에 주목할 평가 트렌드 두 가지를 정리한다.

10-1. Agentic Eval - 에이전트 전체 워크플로 평가

단일 응답이 아니라, 에이전트가 여러 단계를 거쳐 과제를 완수하는 전체 과정을 평가한다. 계획 수립 → 도구 선택 → 실행 → 오류 복구 → 최종 결과까지의 워크플로 전체가 평가 대상이다. SWE-bench가 이 방향의 초기 형태이고, 2026년 하반기에는 더 복잡한 멀티스텝 에이전트 벤치마크가 등장할 전망이다.

10-2. Sandbox Eval - 격리 환경 실행 평가

모델을 Docker 컨테이너나 VM 안에서 실행하고, 실제 코드를 작성·실행·디버깅하게 하는 방식이다. OpenAI Codex의 sandbox 접근법이 대표적이다. 벤치마크가 '문항풀이'에서 '실제 환경 실행'으로 전환되는 것이 핵심 흐름이다. 이 방향은 벤치마크 gaming을 크게 줄일 수 있지만, 평가 비용과 시간이 늘어나는 트레이드오프가 있다.

11. 위험 - '벤치마크 무시'도 함정

여기까지 읽으면 '그러면 벤치마크는 다 무시하고 자체 평가만 하면 되는 것 아니냐'는 생각이 들 수 있다. 이것도 함정이다.

벤치마크가 여전히 유용한 세 가지 이유:

  • 후보 선별 효율: 100개 모델을 모두 자체 평가할 수 없다. 벤치마크로 상위 5개를 추린 뒤 자체 평가하는 것이 합리적이다.
  • 기본 역량 보장: 벤치마크 점수가 매우 낮은 모델은 기본적인 언어 이해·추론 능력이 부족할 가능성이 높다. 하한선 필터로 쓸 수 있다.
  • 시간 흐름 추적: 같은 모델의 버전별 벤치마크 추이를 보면, 전반적 능력 향상/퇴행을 빠르게 감지할 수 있다.

올바른 자세는 '벤치마크를 참고하되 맹신하지 않는다'이다. 벤치마크는 지도이고, 프로덕션은 영토다. 지도와 영토가 다를 때 신뢰해야 하는 것은 영토다. 그러나 지도 없이 영토를 탐험하는 것은 비효율적이다.

12. 결론 + 즉시 적용 3가지

2026년 LLM 평가의 핵심 문제는 '벤치마크가 나빠서'가 아니라, '벤치마크를 잘못 쓰고 있어서'다. 지식 벤치마크는 지식을, 행동 벤치마크는 행동의 일부를 측정할 뿐이고, 프로덕션의 전체 그림은 어느 쪽도 담지 못한다. 이 격차를 인정하고, 자체 평가 체계를 세우는 팀만이 모델 교체 때마다 반복되는 시행착오에서 벗어날 수 있다.

내일부터 즉시 적용할 수 있는 3가지:

  1. 골든 데이터셋 30개를 오늘 만든다. 완벽하지 않아도 된다. 본인 서비스에서 가장 중요한 질문 30개와 기대 응답을 정리한다. 이것이 자체 평가의 시작이다.
  2. 환각 테스트 10개를 추가한다. 모델이 확실히 모르는 질문(가상의 법률, 존재하지 않는 API) 10개를 던지고, '모르겠다'고 대답하는 비율을 기록한다.
  3. Promptfoo를 설치하고 모델 2개를 비교한다. npx promptfoo@latest init 한 줄이면 된다. 골든 데이터셋 30개 + 환각 테스트 10개를 YAML에 넣고 두 모델을 돌리면, 벤치마크 순위와 다른 결과를 보게 될 것이다.
