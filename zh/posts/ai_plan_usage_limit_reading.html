同样的20倍量的却不是同一个东西 - 如何读懂AI套餐的用量上限

倍数写法从来不写分母。判断被乘的到底是5小时窗口还是一周总量的顺序

2026年9月2日 IT/技术

定价表上写着20倍。旁边那家服务的定价表上也写着20倍。可是一边的20倍，乘的是五个小时里能用的量，另一边的20倍，乘的是一周里能用的总量。两个数字摆在同一个位置上，量的却不是同一个东西。

升级套餐之后有人说比想象中更快就卡住，问题多半就出在这里。价钱涨了五倍，能用的量自然也该涨五倍，可实际涨了五倍的往往只有一类上限，另一类上限要么没动，要么涨得少得多。而且两个上限同时生效时，实际生效的是先碰到的那一个。

这篇文章不去论证哪家更划算。百万Token单价的对比在2026 AI API价格对比，单价一直在降账单却不变的原因在推理单价与账单分道扬镳的地方，组织层面的费用管控在在组织层面控制AI编程费用。这里只处理一件事，怎么读用量上限的写法。

正文中的全部数值，都是2026年9月2日在各家官方定价页面和帮助文档上直接确认到的时点值。没能确认的数值一律没有写。套餐和上限会在不预告的情况下变动，真正落到账号上的数值以产品内的用量界面为准。本文不推荐任何一家服务，也不主张谁优谁劣。

起因 - 同样的20倍在说不同的事

2026年8月底，一位AI公司内部人士的公开发言被韩国开发者社区转载。大意是自家高档套餐的20倍写法，连每周用量也确实是二十倍，而竞品的20倍只挂在5小时限制上，每周上限并没有涨那么多。接着的说法是，只看价格表就升级，很容易误以为每周用量也会按同样的比例增加。

判定这段话对不对不是本文的任务。公司内部人士谈竞品，本质上是来自一边的说法，更重要的是这类数值在发言之后还会继续变动。所以这里不去转述那段话，只写2026年9月2日今天各家官方文档上实际写着的内容。

不过这段话戳中的那个点本身是准确的。倍数写法从来不写分母。20倍这三个字符不会告诉你被乘以二十的是什么，而这条信息通常不在定价表里，在帮助文档的深处。

20倍的分母是什么

把官方文档打开，同样的20倍指向不同东西这件事就直接摆在那里。以下都是2026年9月2日确认的。

Anthropic 的 Max 套餐帮助页把 Max 5x 写成相对 Pro 套餐每个会话五倍的用量，把 Max 20x 写成相对 Pro 套餐每个会话二十倍的用量。同一份文档明确写着，基于会话的用量上限每5小时重置一次。20倍能管到的范围就到这里。下面另有一句独立的话，Max 套餐还有一个适用于全部模型的每周用量上限，该每周上限在为账户指定的固定时刻重置。也就是说被乘以二十的对象是会话，每周上限不是这次乘法的对象，而是作为单独一项写在那里的。

OpenAI 的 Codex 定价文档结构不同。套餐列的名字本身就是 Plus、Pro 5x、Pro 20x、Business，表里放的数值是每5小时窗口的消息数估算区间。三行模型档位里，Plus 列分别是 10~100、25~200、250~2,000，Pro 20x 列分别是 200~2,000、500~4,000、5,000~40,000。算一下就知道，Pro 20x 行正好是 Plus 行的二十倍，Pro 5x 行是五倍。也就是说这张表里的20倍，乘的是每5小时窗口的消息数。表下面还挂着一句话，本地消息和云端对话共用一个5小时窗口，并且可能另外适用每周上限。Business 列的数值和 Plus 列相同。

Cursor 的定价页在个人最高档的说明行上写着相对 Pro 的智能体额度二十倍。这里的分母是 Pro 档的智能体额度，而 Pro 档的额度是多少，同一张卡片上并没有写。紧邻的下一档写的是相对 Pro 三倍，团队高档席位写的是相对标准席位五倍。倍数链条是有的，链条的末端却没有绝对值。

GitHub Copilot 干脆不用倍数写法。它把每月可用的额度直接写成金额。这是第三种类型，既不是倍数也不是时间窗口，而是一个月里能烧掉多少钱。

写法出现的位置倍数乘的是什么同时生效的另一类上限是否公开了绝对值
Anthropic Max 5x / 20x相对 Pro 的每会话用量，会话每5小时重置另有适用于全部模型的每周上限，按账户固定时刻重置否。只有倍数，没有每会话的绝对值
OpenAI Codex Pro 5x / 20x每5小时窗口的消息数，正好是 Plus 列的5倍和20倍明确写明可能另外适用每周上限部分公开。窗口数值以区间给出，每周数值没有
Cursor 个人最高档相对 Pro 的智能体额度仅凭页面文字无法确认否。作为分母的 Pro 额度没有绝对值
GitHub Copilot不使用倍数写法每月额度耗尽之后的处理规则是。每月额度数量和折算金额都写在文档里

这里得出的结论不是谁更好，而是同样的字符串在量不同的东西，所以把两个倍数并排比较这个动作本身就不成立。要拿20倍去比20倍，得先把两个20倍的分母换成同一个东西，而做这个换算所需的数值通常没有公开。

实务上更要紧的，是前面已经写过一次的那句话。两类上限同时生效时，实际生效的是先碰到的那一个。如果只有窗口上限变成二十倍而每周上限没动，那么升级之后能感觉到的不是涨上去的那一边，而是没涨的那一边。把一整周摊开来看，瓶颈只是从窗口挪到了每周而已。

用来计量上限的单位

要确认分母，先得知道单位。实际在用的单位大致有五种，每一种给使用者的感受都不一样。

消息条数

最老也最直观的单位。问题在于一条消息的体量差别极大。一行字的提问和附了十个文件的请求没法算作同样的一条，所以真正的文档大多写成区间。前面看到的 10~100 就是这种写法。拿一个最小值和最大值差十倍的数字去做计划很难，所以这个单位好懂，但对预测几乎没有用。

Token和积分

Token是最贴近真实成本的单位，可惜使用者没法提前去数。于是各家在Token外面包一层，叫作积分。OpenAI 的定价文档写道，积分是把Token用量折算成更简单的单位，而且积分的消耗会随模型、上下文、推理、工具而变化。GitHub 更进一步，把积分钉死在金额上。文档里写着1个积分等于0.01美元，并说明输入Token、输出Token和被缓存的Token会按模型单价计算后折算成积分。

时间窗口、并发与模型系数

时间窗口定的不是量，而是区间。5小时窗口只看这五个小时之内的消耗。模型系数则是让同一次请求因为经过的模型不同而被扣掉不同数量的系数。GitHub 关于旧的按请求计费的文档写道，每个模型都有倍数，高级请求额度会按这个倍数扣减，并写明代码审查功能从2026年6月1日起挂上13这个倍数。一次请求被算作十三次。

单位数的是什么使用者的体感能否提前规划
消息条数来回的次数直观，但一条的体量参差不齐，和实际情况对不上难。文档只给区间
Token输入、输出、被缓存文本的量看不见。长对话和大附件在悄悄地扣只能事后统计
积分折算过的Token，有时被钉在金额上像余额。不同类型的活儿消耗速度差很多相对可以。看余额曲线就行
时间窗口固定区间之内的消耗只在集中干活的那天突然冒出来可以。知道自己的模式就能预测
模型系数用的是哪个模型同样的活儿，有些天掉得特别快可以。固定模型就能控住

时间窗口的脾气 - 集中用会撞，摊开用不会

窗口上限是体感和总量上限完全相反的地方。不理解这个脾气，就选不出适合自己的套餐。

5小时窗口只看你往这五个小时里塞了多少。一天守着十个小时以上，只要摊开来用，也可能碰不到窗口上限。反过来把大活儿压进下午三个小时，一天的总量并不多也会撞上。同样的总量，摆放的时间不同，结果就不同。

一周总量上限恰好相反，它不看你什么时候用。凌晨集中用也好，一周里均匀铺开也好，合计相同扣掉的就相同。所以两类上限瞄准的使用者类型是不同的。

  • 短时间猛干的人 — 一天一两次，把大活儿一次性跑完。这一类先撞窗口上限，一周总量还剩着，下午就被拦住了
  • 每天长时间稳定使用的人 — 整天频繁提问。这一类先撞每周上限，到周四前后一周突然就结束了
  • 长时间跑智能体的人 — 一旦启动就自动读文件改文件几十分钟。窗口上限和每周上限会同时压上来，这一类最难预测
  • 偶尔用的人 — 两个上限都碰不到。这种情况下，高档套餐的倍数就是一个用不上的数字

这里有一处经常被误读。撞上窗口上限，并不等于把这个套餐的总量用完了，而是把那五个小时用完了。反过来撞上每周上限，那才是真的把这一周的总量用完了。屏幕上弹出来的提示看着差不多，但这两件事性质不同，应对方式也不同。前者把活儿摊开就解决了，后者摊开也解决不了。

实际文档也是分开写的。Anthropic 的用量说明文档把用量界面上可以查看的项目分开列出，一个是当前会话，即5小时会话上限已经用掉多少、这个会话还剩多少时间，另一个是每周上限，即每周用量上限什么时候重置。而每周这一项又进一步分成某个高档模型专用和其余模型共用两条。也就是说一个账号上至少挂着三个上限。

为什么各家计量方式不同

不只是书写习惯不同，而是因为瞬时负载和总消耗是两笔不同的成本。

同一时刻涌进来的请求，考验的是要备多少机器。如果所有人都在下午两点涌上来，就得备够扛住那一刻的机器，而这些机器在其余时间闲着也要付钱。至于一个月里流过的Token总和，考验的是实际支出的电力和时间。前者靠削峰解决，后者靠封顶解决。时间窗口上限管前面，总量上限管后面。所以一家公司同时上两种是常见的做法，前面看到的两家也确实都同时上了两种。

计量单位的选择也是同一个道理。消息条数对使用者直观，却和成本对不上。Token和积分贴近成本，使用者却难以提前估算。选哪一边都要放弃另一边，所以同一家公司有时会把两种写法混着用。

钉在金额上的积分还有一层理由。GitHub 的个人套餐文档在基础积分之上加了一份弹性额度，并写明它被设计成会随着AI经济性的变化而调整，包括模型价格、新模型以及效率改进。也就是说，这是一个让底层成本变动时不必重写定价页数字的装置。从使用者一侧看，这也意味着写法没变，实际能买到的量却可能悄悄变了。

公开的数值和不公开的数值

把几份上限文档打开，很快会注意到一件事，写着绝对值的格子比想象中少。

Anthropic 的 Max 套餐文档写了五倍和二十倍这样的相对倍数，写了会话每5小时重置，也写了存在每周上限。但每个会话是多少条消息、每周上限是多少，没有写。文档里放的是这样一句话，为了管理容量并保障所有用户的公平访问，可以通过每周和每月上限，或者模型与功能的使用等其他方式，自行裁量地限制用量。这是一条裁量条款。

这类措辞的读法是固定的。用量大可能被限制这句话，并不是说没有上限，而是说上限存在，只是不公开数值，同时也意味着那个数值不是一个固定的数字，而是会随当时的容量情况调整的量。事实上 Anthropic 在2026年5月6日宣布，把编程工具的5小时上限提高到两倍，并取消了高峰时段的额度缩减。这是公司自己给出的、数值会动的证据。

反过来也有绝对值公开得比较充分的一边。GitHub 的个人套餐文档把每档的每月积分拆成基础额度和弹性额度，用数字写清楚。积分钉在金额上，乘一下就是每月上限。只是这一边不会告诉你能撑多久。同样的积分，用来做轻量提问能撑很久，用来跑大型智能体会话很快就没了，文档自己就是这么写的。

  • 只公开倍数的情况 — 不知道分母，所以没法和别家比。只能用于同一家服务内部的档位比较
  • 以区间公开的情况 — 按最小值来做计划更稳妥。最大值是最轻量任务时的数字
  • 以金额公开的情况 — 上限很清楚，但换算不成时间。换一类活儿，消耗速度整个就变了
  • 不公开的情况 — 先看有没有裁量条款，如果有，就应当把那个套餐的上限当作浮动的

撞上上限之后会发生什么

撞上上限这句话指的并不是一件事。实际上至少分成四种，这四种对使用者来说是完全不同的经历。选套餐之前，先看这一栏比先看倍数更有用。

撞上上限时会发生什么使用者需要什么已确认的实例
等待到重置时刻之前用不了这个功能知道重置时刻，以及在那之前能做的别的事Anthropic 帮助文档给出等待重置、升级套餐、购买用量额度三个选项
放行进行中的任务正在跑的这一轮让它走完相信活儿不会被从中间掐断OpenAI 定价文档写道，即使触顶，智能体也能继续完成这一轮，并适用公平使用限制
降级高档模型停掉，换更轻的模型继续用能察觉质量下滑的基准GitHub 关于旧的按请求计费的文档写道，额度用完后当月剩余时间仍可用其中包含的模型
超额计费不拦截，按用量计费设置上限。不设就等于无限Anthropic 写明开启用量额度后，后续使用按标准API费率计费

超额计费这一侧尤其要当心。用订阅制的理由有一半是账单可预测，而一旦打开超额计费，这个性质就没了。所以文档也会把刹车一并放上。Anthropic 写明是预付方式，并且一天能用掉的金额有上限；GitHub 写明提供预算设置以及75%、90%、100%三档提醒。这些装置不打开，选套餐这件事就失去意义了。

降级则是安静的陷阱。阻断会立刻被察觉，降级不会。产出质量从某个时点开始下滑，而不知道为什么下滑的状态可能持续好几天。自己用的工具在触顶时切到哪个模型、会不会把这件事显示在界面上，是需要提前确认的项目。

怎么量自己的用量

盯着定价表看多久，也得不出适合自己的档位，因为表上没有的另一半在自己这边。是集中用还是摊开用，是长会话还是短提问。不知道这两点，就分不清窗口上限和总量上限哪一个是自己的瓶颈。

量的方法很简单，记一周就够，也不需要精确。真正需要的只是两个比例。

  • 峰值占比 — 一天里最集中的那五个小时占当天全部消耗的比例。这个值高，说明窗口上限是瓶颈
  • 最大单日占比 — 一周里用得最多的那一天占整周的比例。这个值低而且均匀，说明每周上限是瓶颈
  • 会话时长分布 — 一次开始要用多少分钟。大多在十分钟以内，还是掺着一小时以上的
  • 任务类型占比 — 短提问、长文档工作、自动执行的智能体各占多少。这三者的消耗速度差着数量级
  • 模型占比 — 高档模型用了多少。在挂了模型系数的服务上，光这一个值就能把其余全部推翻

手写记录也行，把工具提供的用量界面一天截两次图也行。格式做到这个程度就够了。

日期        时段         任务类型      模型     会话时长    备注
2026-09-01  09-14        短提问        轻量      ~5分钟x12  会议准备
2026-09-01  14-19        智能体运行    高档      ~90分钟x2  重构，触顶告警1次
2026-09-02  09-14        长文档工作    高档      ~40分钟x3  -
2026-09-02  19-24        短提问        轻量      ~5分钟x6   -

需要统计的
  峰值占比       = (最集中的5小时消耗) / (当天全部消耗)
  最大单日占比   = (用得最多的一天)     / (整周)
  高档模型占比   = (高档模型消耗)       / (全部消耗)

攒够一周，判断几乎是自动出来的。峰值占比高，加大窗口上限的档位就有意义；低而均匀，窗口倍数提得再高也没有体感。而如果两个值都高，那意味着选哪个套餐都会触顶，这时候动的不该是档位，而是任务编排和模型路由那一侧，那样更快。

用量界面大多数服务都提供。Anthropic 写明界面上会显示当前会话的消耗与剩余时间、每周上限的重置时刻，并把影响用量的因素列为消息长度、附件大小、当前对话长度、工具使用、模型选择、努力等级、产出物生成。对话长度出现在这份清单里，尤其值得留意。同样一个问题，放在长对话的末尾去问，前面的内容每次都会被一起带上去。

做比较表时必须对齐的东西

需要对齐的五条轴

坐下来想比较套餐，表往往从第一行就对不上，因为一格里是每5小时窗口的消息数，旁边一格是每月积分，再旁边一格只写着倍数。五条轴不对齐到同一个基准，这张表就只有数字，没有比较。

  • 周期 — 5小时、一天、一周、一月，是哪一个。会很想把窗口数值换算成周，而这个换算多半是错的，因为另有每周上限时，窗口数值乘出来的量并不是实际能用的量
  • 单位 — 消息、Token、积分、金额，是哪一个。它们之间不会自动换算。换算系数没有公开时，把那一格空着才是准确的
  • 模型 — 同一个套餐内部也会按模型档位分出不同上限。高档对高档，轻量对轻量，行要对齐
  • 覆盖范围 — 智能体自动运行、代码审查、网页搜索、附件是不是在扣同一份额度。有时多个产品共用一份额度，Anthropic 写明 Pro 和 Max 的上限在对话型产品和编程工具之间共享，两个工具里的全部活动都算进同一份上限
  • 超出后的行为 — 等待、降级还是计费。这一格不同，前面四格一样也仍然是不同的商品

对齐周期这条轴时有个好用的验算，把只按窗口上限算出来的每周理论值，和公开的每周上限并排写下来。两者中小的那个才是实际生效的上限，如果理论值大得多，就说明那个套餐的窗口倍数被用到的程度不如宣传。

只看窗口上限得到的每周理论值
  = (每窗口上限) x (每天开启的窗口数) x 7
  每周7天 x 每天24小时 / 5小时 = 33.6 个窗口   (假设连续使用，并不现实)

实际生效的每周上限
  = min( 窗口理论值 , 公开的每周上限 )

怎么读
  窗口理论值 >> 每周上限   -> 每周上限是瓶颈，提高窗口倍数体感很小
  窗口理论值 <= 每周上限   -> 窗口是瓶颈，把任务摊开就能改善
  每周上限未公开            -> 算不出来，只能靠实测确认

连单位本身都会被换掉

这篇文章里能留存最久的一段就在这里。会变的不只是上限的数值，单位本身也会变。

GitHub Copilot 就是实例。以前用的单位叫高级请求，各档套餐里每月包含多少件是定好的，每个模型挂着倍数，用完之后可以按每件多少钱加购。而在2026年6月1日，按请求计费改成了按用量计费。现在的文档写道，一次交互的费用由两件事决定，模型和消耗的Token数。文档另附了一条，原本在年度套餐上的用户，可以在那个套餐结束之前继续沿用旧方式。

这个变化的含义很简单，在此之前做的所有比较表，从那天起全部失效了。每月多少件这条轴消失了，就没法和旁边那一格并排放。现在文档上写着的数值是这样的。

档位月费基础积分弹性额度每月合计折算金额
Pro10美元1,0005001,50015美元
Pro+39美元3,9003,1007,00070美元
Max100美元10,00010,00020,000200美元

文档上写明1个积分等于0.01美元。重置在每月1日的协调世界时零点，与订阅扣款日无关，是固定的。剩下的积分不会结转到下个月，会清零。这里值得注意的一点是月费和积分金额的比例在各档之间并不一致，10美元给15美元的量，39美元给70美元的量，100美元给200美元的量。这其实也是一种倍数，只是没人把它叫作20倍。

同一时期另一边的数值也动了。Anthropic 在2026年5月6日的公告里说明，针对 Pro、Max、Team 以及按席位计费的 Enterprise，把编程工具的5小时上限提高到两倍，并取消了高峰时段的额度缩减。也就是说，本文引用的倍数和窗口长度本身，几个月前也是另外的数值。

最新的数值该去哪里看

既然数值这样动，这篇文章能留下的就不是数值，而是找数值的位置。按优先级排是这样的。

  1. 产品内的用量界面 — 最准确，因为那不是文档上的数值，而是实际挂在自己账号上的数值。会话余量、每周重置时刻、积分余额都在这里
  2. 帮助中心或文档里讲用量的页面 — 不是定价页，是帮助那一侧。定价页是拿来卖的文档，只写倍数，分母在帮助里
  3. 公告与发布说明 — 上限有变动时通常先出现在这里，定价页跟上来可能要过几天
  4. 服务条款与公平使用政策 — 裁量条款所在的地方。如果那里有一句可以自行裁量设定上限，那么前面所有数字都是暂定值
  5. 员工与相关人士的公开发言 — 最快，也最不准。那是某个时点的快照，掺进对竞品的评价时就是一边的视角。和文档有出入时，以文档为准
  6. 社区反馈 — 了解真实体感的唯一通道，但那是使用模式不同的另一个人的数值。要读的不是绝对值，而是哪一类人在哪里被拦住

另外需要养成把确认日期一起写下来的习惯。这篇文章在正文各处反复写2026年9月2日，原因就在这里。没有日期的上限数值，比错误的数值更危险。错的数值会被验证，没有日期的数值则因为没人知道它什么时候失效，而被一直引用下去。

小结

同样是20倍，一边乘的是5小时窗口，一边乘的是一周总量，还有一边乘的是没有名字的智能体额度。而乘法没有碰到的那些上限依旧留在原地，所以在两个上限同时生效的地方，没涨的那一个才是实际生效的上限。升级之后体感不成比例，机制大多出在这里。

所以从表里该读出来的不是倍数，而是四件事，分母是什么、用哪种单位计量、有没有另一类上限同时压着、碰到时会发生什么。这四格填上了，倍数就成了附带信息；填不上，倍数再大也支撑不了任何判断。

另外，选套餐之前先量自己的模式，顺序上才对，因为同一个套餐对集中用的人和摊开用的人作用是相反的。一周的记录就够了，而且这份记录在套餐改版之后还能继续用。会变的是厂商那一侧的数字，自己的使用模式变得慢得多。如果还想对实际支出规模有个概念，用LLM API 价格计算器把同样的工作量按量计费折算一遍，也是一个办法。
