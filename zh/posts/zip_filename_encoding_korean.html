zip 里的文件名在哪一步坏掉 - 谁用什么编码写的

文件名是一串字节。怎么读取这串字节，取决于一个标志位和工具的猜测

2026-07-30 开发/基础设施

引子: 收到的压缩包一解开，名字全乱了

从合作方收到一个 zip，下载解压，文件都在，名字却变成了 ║╕░φ╝¡.txt、1║╨▒Γ ╕┼├Γ.xlsx 这样的东西。问对方，对方说 「我们这边看着是好的」。反过来的情况同样常见: 自己压缩后发出去，对方回话说名字乱了，而自己机器上一切正常。

这段对话之所以无休止地重复，是因为双方都没有做错任何事。这时最常见的建议是 「用 UTF-8 压缩」，这话只对了一半。zip 压缩包里的文件名就是一串字节。能够说明这串字节属于哪种编码的手段只有一个标志位，而这个位为 0 时该按什么读，规范并没有规定。

所以这篇文章讲的不是改设置，而是把压缩包拆成字节，直接读文件名字段和标志位。这两个值一看，坏掉的原因当场确定，能不能救回来也当场分明。下面所有输出都来自真实运行。

运行环境。压缩包是用 struct 逐字节拼出来的，读取时也没有交给标准库，而是手工解析中央目录。所有脚本都先存成文件再执行，因为把混有非 ASCII 字符和反斜杠的代码作为 shell 参数传递会被悄悄改形。工作路径统一写成 \work\demo 这样的占位形式。

本文不涉及的部分。文件内容的编码误转换及其诊断方法，已在 cp949 与 UTF-8，两类编码错误 中讲过。Unicode 规范化的原理在 NFC 与 NFD 里。这里只盯住一点: zip 压缩包里的文件名字段。

1. 规范没有规定的东西

zip 格式的规范是 PKWARE 的 APPNOTE 文档。它关于文件名编码的内容短得惊人。通用位标志第 11 位的那一句话，实际上就是全部。

Bit 11: Language encoding flag (EFS). If this bit is set, the filename and comment fields for this file MUST be encoded using UTF-8.

这句话只谈该位置位时的情形。为 0 时呢？附录 D 给出答案: zip 格式历来只支持最初的 IBM PC 字符编码集。第 11 位尚未存在的年代，默认值是 DOS 时代的代码页，而使用其他编码时没有办法声明。

  • 文件名字段只有长度和字节串，没有放编码名称的位置
  • 第 11 位只有置位才有意义。为 0 不等于 「不是 UTF-8」，而是 「没有声明」
  • 因此未声明的 UTF-8 压缩包是可以存在的，也不算违规，因为规范并没有强制置位
  • 同一份文档的 4.4.17 规定路径分隔符必须使用正斜杠。这一条是强制的。后面我们会遇到一个破坏这条规则的工具
  • 结论: 文件名乱码不是谁的过错，而是规范的空白。各家工具用各自的猜测去填这块空白

理解了这个结构，下一个问题就变了。不再是 「这是什么编码」，而是 「第 11 位置位了吗，那串字节又是什么」。两个问题打开压缩包就能立刻回答。

2. 把文件名字段拆成字节

先准备材料。同一个名字用两种编码写出来，字节差别是这样的。

--- 2-1. one name, two encodings ---
name : 보고서.txt
  utf-8 bytes : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74   (13 B)
  cp949 bytes : BA B8 B0 ED BC AD 2E 74 78 74            (10 B)

name : 1분기 매출.xlsx
  utf-8 bytes : 31 EB B6 84 EA B8 B0 20 EB A7 A4 EC B6 9C 2E 78 6C 73 78   (19 B)
  cp949 bytes : 31 BA D0 B1 E2 20 B8 C5 C3 E2 2E 78 6C 73 78               (15 B)

一个韩文字符在 UTF-8 里是 3 字节，在 cp949 里是 2 字节。所以同一个名字存在 13 字节和 10 字节两种形态。把这两串字节分别放进压缩包，手工解析中央目录。先看旧工具做出来的形态。

=== A_legacy_cp949.zip  (258 B) ===
EOCD  entries=2  cd_offset=119  cd_size=117
--- entry 1 ---
  gp flag raw      : 0x0000   bin 0000000000000000
  bit 11 (UTF-8)   : not set
  name field len   : 10 bytes
  name field hex   : BA B8 B0 ED BC AD 2E 74 78 74
  as utf-8         : <UnicodeDecodeError>
  as cp949         : [보고서.txt]
  as cp437         : [║╕░φ╝¡.txt]
  extra len        : 0 bytes  (no extra field)
--- entry 2 ---
  gp flag raw      : 0x0000   bin 0000000000000000
  bit 11 (UTF-8)   : not set
  name field len   : 15 bytes
  name field hex   : 31 BA D0 B1 E2 20 B8 C5 C3 E2 2E 78 6C 73 78
  as utf-8         : <UnicodeDecodeError>
  as cp949         : [1분기 매출.xlsx]
  as cp437         : [1║╨▒Γ ╕┼├Γ.xlsx]
  extra len        : 0 bytes  (no extra field)

这段输出就是诊断的全部，看三行足矣。

  • 标志位是 0x0000。第 11 位为 0，所以这个压缩包没有声明编码
  • 名字字节是 BA B8 B0 ED BC AD。按 UTF-8 解码会抛异常，按 cp949 则干净读出。字节自己说明了编码
  • 没有扩展字段，也没有把名字再存一份的地方
  • 判定是确定的: 未声明的 cp949 压缩包。在韩文 Windows 上看着正常，在别处就乱

这里要留意 as cp437 那一行。把文件名字节用 DOS 时代的默认代码页读出来就是 ║╕░φ╝¡.txt。正是引子里的那串字符。也就是说本文开头的症状，不过是 「按规范默认值读取一个未声明的 cp949 压缩包」 的结果。

3. 第 11 位，唯一的声明

作为对照，把同一个名字以 UTF-8 字节存入并置位第 11 位。

=== B_utf8_flagged.zip  (272 B) ===
EOCD  entries=2  cd_offset=126  cd_size=124
--- entry 1 ---
  gp flag raw      : 0x0800   bin 0000100000000000
  bit 11 (UTF-8)   : SET
  name field len   : 13 bytes
  name field hex   : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74
  as utf-8         : [보고서.txt]
  as cp949         : <UnicodeDecodeError>
  as cp437         : [δ│┤Ω│á∞ä£.txt]
  extra len        : 0 bytes  (no extra field)
--- entry 2 ---
  gp flag raw      : 0x0800   bin 0000100000000000
  bit 11 (UTF-8)   : SET
  name field len   : 19 bytes
  name field hex   : 31 EB B6 84 EA B8 B0 20 EB A7 A4 EC B6 9C 2E 78 6C 73 78
  as utf-8         : [1분기 매출.xlsx]
  as cp949         : [1遺꾧린 留ㅼ텧.xlsx]
  as cp437         : [1δ╢äΩ╕░ δºñ∞╢£.xlsx]
  extra len        : 0 bytes  (no extra field)

标志位是 0x0800。写成二进制是 0000100000000000，只有从右数第 12 位被置起来，如此而已。这一个位就是 「这个名字是 UTF-8」 的声明，也是 zip 格式里唯一能传达编码的手段。

3.1 没有声明的 UTF-8 这个陷阱

还有第三种情况: 字节是 UTF-8，但第 11 位没有置起来。这同样不算违规。

=== C_utf8_noflag.zip  (141 B) ===
EOCD  entries=1  cd_offset=60  cd_size=59
--- entry 1 ---
  gp flag raw      : 0x0000   bin 0000000000000000
  bit 11 (UTF-8)   : not set
  name field len   : 13 bytes
  name field hex   : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74
  as utf-8         : [보고서.txt]
  as cp949         : <UnicodeDecodeError>
  as cp437         : [δ│┤Ω│á∞ä£.txt]
  extra len        : 0 bytes  (no extra field)
  • A 和 C 的标志位数值完全相同，都是 0x0000
  • 但名字字节不同。A 只能按 cp949 读，C 只能按 UTF-8 读
  • 可见只看标志位不够。标志位为 0 时必须同时看字节的有效性，才能把两者分开
  • C 反而在韩文 Windows 上会乱。系统代码页是 949，就会把 UTF-8 字节按 949 去读
  • A 和 C 造成方向相反的事故，这正是问题棘手之处: 修好一边的措施会制造另一边

4. 复现乱码 - 同一个名字的六副面孔

下面把乱掉的样本做出来并列。本文中乱掉的字符串本身就是资料，所以原样呈现。

  as utf-8 with replace : [������.txt]

--- 4-2. name 1분기 매출.xlsx, same treatment ---

  as cp437              : [1║╨▒Γ ╕┼├Γ.xlsx]

  as cp437              : [1δ╢äΩ╕░ δºñ∞╢£.xlsx]

样本是有读法的。乱掉的字符属于哪一类，就说明了原因。

  • 像 ║╕░φ╝¡ 这样制表符与希腊字母混杂，就是按 cp437 读的。DOS 代码页正好在那个区间放着制表符和希腊字母
  • 像 1遺꾧린 留ㅼ텧 这样汉字与谚文混在一起，就是把 UTF-8 字节按 cp949 读了。三字节写下的东西被两字节两字节地取走，偶然落在了合法字符上
  • 像 ������ 这样替换字符连成一串，就是把 cp949 字节按 UTF-8 读了。cp949 的字节组合大多不符合 UTF-8 的规则
  • º¸°í¼­.txt 看得见的字符有五个，而原名只有三个字。最后那个字节 AD 在 latin-1 里是看不见的软连字符。想靠数字符个数来判断，就会在这里出错
  • 乱掉的样本里混进希腊字母和阿拉伯字母是正常的。它们与原文毫无关系，只是被错误套用的代码页在那个位置正好放着那个字符

4.1 扩展名消失的原因

上面的样本里 蹂닿퀬�꽌.txt 的点还在。可实际解压后落到磁盘上的名字却是 蹂닿퀬__txt，扩展名没了。把字节两个两个地捆起来看就明白了。

--- 4-3. why the extension disappears ---
utf-8 bytes of the name : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74  (13 B)
cp949 reads two at a time:
  EB B3 -> [蹂] U+8E42
  B4 EA -> [닿] U+B2FF
  B3 A0 -> [퀬] U+D02C
  EC 84 -> <UnicodeDecodeError>
  9C 2E -> <UnicodeDecodeError>
  74 -> [t] single byte
  78 -> [x] single byte
  74 -> [t] single byte

the pair that eats the dot:
  9C 2E   the byte 2E is the '.' of .txt
          a cp949 lead byte 9C swallowed it

what the platform decoder returned for the same bytes:
  [蹂닿퀬??txt]
  U+8E42 U+B2FF U+D02C U+003F U+003F U+0074 U+0078 U+0074   (8 chars)
  chars illegal in a Windows file name : U+003F U+003F
  the extractor replaced them with underscores -> [蹂닿퀬__txt]

这条链条正是如此。把 UTF-8 名字按 2 字节为单位读取，导致首字节 9C 把那个点当成搭档拉了进去。这一对不是合法字符，于是变成问号；问号又是 Windows 文件名里不能用的字符，解压工具就换成了下划线。结果扩展名消失。

  • 这不只是 「名字乱了」。扩展名没了，关联程序也就没了，双击打不开
  • 点被吃掉的条件是名字里最后一个非 ASCII 字符的第三个字节落在 cp949 首字节区间。因名字而异，有时会有时不会
  • 所以 「有的文件扩展名还在，有的没了」 这种现象会在同一个压缩包里同时出现
  • 靠扩展名有无来判断是否乱码的脚本，在这里会悄悄误判

5. 能不能还原 - 关键只在字节是否还在

看到乱掉的名字就想修。能修和不能修的情况，用运行结果分开。先看能修的一边。

--- 5-1. bytes preserved in the archive -> reversible ---
  as reported by reader : [║╕░φ╝¡.txt]
  codepoints            : U+2551 U+2555 U+2591 U+03C6 U+255D U+00A1 U+002E U+0074 U+0078 U+0074
  re-encode cp437       : BA B8 B0 ED BC AD 2E 74 78 74
  decode cp949          : [보고서.txt]
  round trip ok         : True

  as reported by reader : [1║╨▒Γ ╕┼├Γ.xlsx]
  codepoints            : U+0031 U+2551 U+2568 U+2592 U+0393 U+0020 U+2555 U+253C U+251C U+0393 U+002E U+0078 U+006C U+0073 U+0078
  re-encode cp437       : 31 BA D0 B1 E2 20 B8 C5 C3 E2 2E 78 6C 73 78
  decode cp949          : [1분기 매출.xlsx]
  round trip ok         : True

步骤是两步。用读取工具当初套用的编码重新编码，把原始字节找回来，再用正确的编码解码。这里工具套用了 cp437，所以按 cp437 还原、按 cp949 读取。字节与原始完全一致就是成功的证据。

  decoded utf-8/repl : [������.txt]

两种失败的性质不同。

  • 5-2 是工具把字节碾碎了。某些解压工具会把名字转写成自己那套字符集再写到磁盘。BA B8 变成了 A6 A9，不存在任何编码能把原始字节找回来
  • 5-3 是替换字符吃掉了它们。替换字符不带任何关于它替代了哪个字节的信息。10 字节变成 22 字节不是信息变多，而是同一个值重复了六次
  • 所以判断顺序很重要。不要看已经解压到磁盘上的名字，先看压缩包里的字节。压缩包完好就换个工具重新解压；已经用怪名字解出来的那批文件，删掉重来更快
  • 不要删掉原始压缩包文件，这是第一道防线。只要压缩包在，随时可以回头

6. 制作方 - 哪些工具会置第 11 位

准备一个含非 ASCII 名字的文件夹，用本环境里可用的工具分别压缩，然后读中央目录。

  readme.txt                flag_bits=0x0000  bit11=not set
  name field hex (first)   : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74
  separator                : 2F  '/'

  separator      : 5C  '\'   <-- APPNOTE 4.4.17 requires 2F

第三行是本文最实用的发现。今天 Windows 10 自带的 tar 命令，把文件名写成 cp949 字节且不置第 11 位。这不是特意翻出来的老工具，而是随操作系统附带的标准工具就这样。在没有 zip 命令的环境里，tar -a -c -f out.zip 是很自然的选择，而这样做出来的压缩包在同一代码页环境之外必定会乱。

第一行也藏着一个陷阱。Python 的 zipfile 只有在名字含非 ASCII 字符时才置第 11 位，readme.txt 的标志位是 0x0000。也就是说同一个压缩包里各条目的标志位可能不同，只检查第一条的判别脚本在这里就会出错。

这张表就是 「我们这边看着是好的」 的真相。同一个压缩包在某个工具里正常，在另一个工具里就乱。其中特别值得注意的有三点。

  • Windows 的工具能正确读出 A。没有第 11 位时它套用系统 ANSI 代码页，而那正是 949。在韩国做、在韩国解，什么问题都没有。只有接收方是别的环境时问题才会暴露
  • C 在 Windows 上最糟。tar 连扩展名都弄没了，Expand-Archive 直接抛异常一个文件都没解出来。不是得到一堆难看的名字，而是整个作业失败
  • UnZip 6.00 无视了第 11 位。B 已经明确声明是 UTF-8，它仍套用自家的字符转换把名字字节碾了。因为这是 2009 年的版本。老工具并不知道自己有义务遵守声明
  • 这里出现的阿拉伯字母 ٦ 和 ۦ 与原文毫无关系。工具生成的字节 D9 A6、DB A6 后来被当作 UTF-8 解释，落进了阿拉伯字母区。乱掉的样本里混进毫不相干的字符，就是这种双重解释造成的
  • 实务教训只有一句。收到 「乱了」 的反馈，先问对方用的是什么工具。原因可能不在压缩包而在工具

  • 目录会作为单独条目存入，名字以斜杠结尾。整条路径都装在一个名字字段里，所以文件夹名一乱，它下面所有条目的路径都会跟着乱
  • 分隔符字节 2F 是安全的。它不落在 cp949 的首字节区间，所以不会像 4.1 节的点那样被吃掉。前面那个写 5C 的工具，等于自己扔掉了这道保险
  • 名字字段的长度限制按字节计。56 个字符的名字在 cp949 下是 96 字节，同样的名字用 UTF-8 写会更长。也就是说改用 UTF-8 会让名字变长，撞上路径长度上限的时点会提前
  • 也可以做出目录条目用 UTF-8 而下级条目用 cp949 的压缩包。规范允许逐条目的标志位，所以一个压缩包里混两种编码是可能的

9. 分解形式的名字进入压缩包之后

同一个 보고서 在 Unicode 内部也存在两种码位序列: 合成形式和分解成字母的形式。把分解形式的名字放进压缩包确认。规范化的原理本身在 NFC 与 NFD，这里只看它在压缩包名字字段里呈现出的样子。

  • 名字字段是 22 字节，比合成形式的 13 字节多 9 字节。把字母一个个分开写，每个字要花三次三字节
  • 第 11 位是置起来的，声明完美无缺。确实是 UTF-8，解码也成功。这不是编码问题，而是规范化形式的问题
  • 分解形式的名字根本无法编码成 cp949。cp949 里只有完整音节，没有组合用字母区的映射。所以这个名字在用旧工具重新压缩的路径上必定崩
  • 解压工具会把收到的形式原样写到磁盘，不会替你规范化。实测环境里那个十个字符的分解形式名字就那样留着
  • 脚本里写死名字去找文件的地方会悄悄返回 0 条。不是报错，而是按 「没有该文件」 处理，很难察觉
  • 对策是比较之前把两边规范化成同一形式。最后一行显示规范化之后就相等了

10. Unicode 路径扩展字段 0x7075

规范里还有一条迂回路: 不置第 11 位，而把名字用 UTF-8 再存一份的扩展字段。APPNOTE 4.6.9 定义的 Unicode 路径扩展字段，头部标识是 0x7075。做了一个含该字段的压缩包来读。

结果很有意思。确认的四个工具全都尊重了这个字段。连无视第 11 位的 UnZip 6.00 也读了它并给出正确名字。明确给出忽略该字段的选项后又乱了，说明默认行为就是 「尊重」。

  • 字段结构是版本 1 字节 + 头部名字的 CRC 4 字节 + UTF-8 名字。有 CRC，所以当别的工具改写过头部名字时，可以察觉这个字段已经过时
  • Python 的 zipfile 读到这个字段就覆盖头部的名字，于是第 5 节的 cp437 还原步骤就不需要了
  • 不过确认的三个工具里没有一个会写这个字段。读取被广泛支持，写入却很少见
  • APPNOTE 自己也写明，用了第 11 位就不需要这个扩展字段。新做的压缩包走第 11 位这条路才对
  • 这个字段的实用价值在于诊断。收到的压缩包里有它，就能不靠猜测知道原始名字

12. 名字和内容是两回事

在一个压缩包里故意做了一个名字是 UTF-8、内容是 cp949 的条目。本节确认这个组合在规范上完全没有问题。内容编码的诊断方法已在 cp949 与 UTF-8，两类编码错误 中讲过，这里只强调两层互不相干这一事实。

--- 12-1. name layer and content layer disagree, on purpose ---
  entry name         : [보고서.txt]  bit11=SET
  name bytes (utf-8) : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74
  content bytes      : C7 D1 B1 DB 20 B5 A5 C0 CC C5 CD 0A
  content as utf-8   : '�ѱ� ������\n'
  content as cp949   : [한글 데이터]

--- 12-2. is the content encoding recorded anywhere? ---
  internal_attr = 0x0000     (bit 0 is a text/binary hint only)
  per-entry fields available :
    CRC, comment, compress_size, compress_type, create_system, create_version,
    date_time, external_attr, extra, extract_version, file_size, flag_bits,
    header_offset, internal_attr, orig_filename, volume
  none of them names the content encoding
  • 第 11 位只作用于文件名和注释，规范写得很死，文件内容不在其列
  • 把条目拥有的字段全部列出来，也找不到写内容编码的位置。只有一个暗示文本还是二进制的位
  • 所以 「名字显示正常，内容应该也没问题」 没有依据。两层之间不共享任何信息
  • 反过来也成立。名字乱掉的压缩包，内容可能完好无损。解压与名字无关，会原样还原字节
  • 实务中必须把两层分开确认: 名字看中央目录，内容看解出来的字节

13. 诊断顺序 - 收到的压缩包属于哪一种

把前面所有判别一次跑完的检查器写好了。中央目录里的标志位、名字字节的有效性、扩展字段的有无这三样就能完成分类。

archive                    bit11    ascii  utf8ok 949ok  0x7075 verdict
--------------------------------------------------------------------------------------
A_legacy_cp949.zip         clear    no     no     yes    no    undeclared cp949, breaks off Korean Windows
B_utf8_flagged.zip         SET      no     yes    no     no    declared UTF-8, safe everywhere

按顺序整理如下。

  1. 先不要解压，只看列表。一旦用错误的名字写到磁盘，就可能滑向第 5 节那些无法恢复的情形
  2. 从中央目录读第 11 位。置位了，名字就是 UTF-8；若仍然显示为乱码，原因不在压缩包而在读取工具
  3. 为 0 就看名字字节的有效性。只能按 UTF-8 读、只能按 cp949 读，还是两者皆可
  4. 找扩展字段 0x7075。有它就不必猜，UTF-8 名字就在里面
  5. 不要只看一个条目。ASCII 名字的标志位是 0，一个压缩包里可能混着两种编码
  6. 判定完再解压，并且不要删掉原始压缩包。只要压缩包在就能重来

确实存在两种编码都有效的情况。某些字节串按 UTF-8 和按 cp949 都能无异常读出。只含 ASCII 的名字是最常见的例子，此外也有重叠区间。这时光看字节无法确定。有效性检查是缩小候选的工具，不会给出结论。所以最后的判断，往往还是人去读一遍名字，看它是否说得通。

15. 分发时要定下的事

换个立场。如果是自己做压缩包对外分发，要先定下什么？依据上面的实测有四项。

决定项选项已确认的依据建议
制作工具置第 11 位 / 不置Python 的 zipfile 和 Compress-Archive 会置，Windows 的 tar.exe 不置固定为会置第 11 位的工具并写进文档

  • 第二是分发前的检查。读第 13 节那三个值，只要有一个条目第 11 位为 0 就判定失败，这类事故就从源头上被堵住
  • 如果确定接收方使用旧工具，把名字改成 ASCII 并在清单里记下原名更好，比依赖扩展字段可靠
  • 已经分发出去的压缩包如果还能修，重做一份才是正解。只改名字字段的编辑要同时对齐本地头部和中央目录，偏移量很容易错位
  • 写进内部规范文档的句子很短。「压缩包的文件名使用 UTF-8 并置通用标志位第 11 位。路径分隔符使用正斜杠。名字规范化为合成形式。」 三句话就能挡住本文所有事故

结语: 用规则去覆盖规范的空白

「用 UTF-8 压缩」 作为建议只对了一半。对的一半是因为使用会置第 11 位的工具确实能解决大部分问题，错的一半是因为它掩盖了 zip 并不强制文件名编码这个事实。一旦掩盖，下一次事故就无从诊断。

把运行确认过的内容再整理一遍: 压缩包里的文件名只有长度和字节串。传达编码的手段是一个位，而这个位为 0 时该按什么读，规范没有规定。于是各家工具各自去猜，Windows 的工具套用系统代码页，Python 套用 DOS 默认值，老 unzip 套用自家转换表。三种猜测都不违反规范。

这也正是它在韩国特别频繁的原因。cp949 时代的文件和习惯还在流通，而在系统代码页为 949 的环境之间互相传递时什么都不会暴露。因为只有接收方是别的环境时故障才出现，制作方根本没有途径知道自己的压缩包会乱。确认了今天 Windows 自带的 tar 就在生产这种压缩包，是本文最实用的结论。

现在马上能做的事有一件。打开一个最近对外发出去的压缩包，读一下第 11 位。置位了就可以放心。为 0 而且名字里有非 ASCII 字符的话，收到它的人此刻很可能正对着一堆乱码，只是没有告诉你而已。

# zip 文件名编码 判别表

## 0. 一句话

zip 不用规范强制文件名编码。名字是一串字节，声明手段只有通用位标志的 **第 11 位**。该位为 0 时按什么读，各家工具各不相同。

## 1. 先看的三样 (解压之前)

| 看什么 | 位置 | 含义 |
|---|---|---|
| 通用位标志第 11 位 | 中央目录头部 +8，2 字节小端 | `0x0800` 即声明为 UTF-8 |
| 文件名字段原始字节 | 头部 +46 起，按名字长度 | 判定 UTF-8 / cp949 有效性 |
| 扩展字段 `0x7075` | 名字字段之后 | 有它就说明 UTF-8 名字又存了一份 |

## 2. 乱码形态判别表

| 看到的名字 | 样本 | 原因 | 能否恢复 |
|---|---|---|---|
| 制表符与希腊字母 | `║╕░φ╝¡.txt` | cp949 名字按 cp437 读 | 可以 (cp437 重编码后 cp949) |
| 小写希腊字母与符号 | `δ│┤Ω│á∞ä£.txt` | UTF-8 名字按 cp437 读 | 可以 (cp437 重编码后 UTF-8) |
| 汉字与谚文混杂 | `1遺꾧린 留ㅼ텧.xlsx` | UTF-8 名字按 cp949 读 | 可以 (cp949 重编码后 UTF-8) |
| 汉字混杂 + 扩展名丢失 | `蹂닿퀬__txt` | 同上，点被首字节吃掉 | 从压缩包重新解压 |
| 替换字符连成串 | `������.txt` | cp949 名字按 UTF-8 读 | 保存之前可以 |
| 拉丁 + 阿拉伯字母 | `٦¦ۦáýä£.txt` | 旧工具套用自家转换表 | 不行。换工具解压 |
| 字符数变多 | `º¸°í¼­.txt` | 单字节代码页，含不可见字符 | 可以 (latin-1 重编码后 cp949) |
| 看着正常却找不到 | `보고서.txt` | 以分解形式保存的名字 | 可以。比较前先规范化 |
| 解压抛异常中断 | (没有文件) | 未声明的 UTF-8 + 代码页解释 | 换工具解压 |

# 还原 (工具套用了 cp437 的情况)

python -c "b=bytes.fromhex('BAB8B0EDBCAD'); [print(e, (lambda: b.decode(e))() if True else '') for e in ('utf-8','cp949')]"

## 4. 工具行为对照 (Windows 10 / ANSI 949 实测)

### 制作方

| 工具 | 名字字节 | 第 11 位 | 分隔符 | 判定 |
|---|---|---|---|---|
| Python 3.13.3 `zipfile` | UTF-8 | 置位 (ASCII 不置) | `2F` | 安全 |
| PowerShell 5.1 `Compress-Archive` | UTF-8 | 置位 | `5C` 违反规范 | 名字安全 |
| Windows `tar.exe` (bsdtar 3.5.2) | cp949 | **不置位** | `2F` | 出了这个环境就乱 |
| Node.js v22 | 核心无 zip 压缩包 API | 不适用 | 不适用 | 不适用 |
| Info-ZIP `zip` / 7-Zip | 本环境没有，未确认 | 未确认 | 未确认 | 未确认 |

### 读取方

| 工具 | cp949 + 无标志位 | UTF-8 + 置位 | UTF-8 + 无标志位 | `0x7075` |
|---|---|---|---|---|
| Python `zipfile` | 套用 cp437 → 乱 | 正常 | 乱 | 尊重 |
| Windows `tar.exe` | 正常 | 正常 | 扩展名丢失 | 尊重 |
| `Expand-Archive` | 正常 | 正常 | 抛异常，未解压 | 尊重 |
| UnZip 6.00 | 乱 | **乱 (无视标志位)** | 乱 | 尊重 |

## 5. 分发时的决定项

- [ ] 制作工具已 **固定为会置第 11 位的那种**
- [ ] 压缩包生成收拢进一个脚本，不让人自己挑工具
- [ ] 对外分发的名字 **限制为 ASCII**，或允许非 ASCII 时把规则写进文档
- [ ] 名字已 **规范化为合成形式** 再打包
- [ ] 已确认路径分隔符是 `2F`
- [ ] 已检查 **每一个条目** 的标志位 (不是只看第一个)
- [ ] 随包附上清单文件，减少对名字的依赖
- [ ] 保留原始压缩包 (唯一能重来的路径)

## 6. 不要做的事

- 判定之前就 **解压** — 用错误的名字写到磁盘会收窄恢复路径
- **只检查第一个条目** — ASCII 名字标志位为 0，且允许逐条目混用
- **靠扩展名有无判断乱码** — 点可能被首字节吃掉而消失
- 只对名字字段做 **字节编辑** — 本地头部、中央目录与偏移量会错位
- 「没抛异常所以是这种编码」 — 存在两种编码下都有效的字节串
- 对使用旧工具的一方 **指望扩展字段** — 一个选项就能让它被忽略
- 因为名字显示正常就 **推断内容也没问题** — 两层互不相干
