AI 在写代码，为什么还选 C

生成量不再是瓶颈之后，决定语言选择的轴换成了什么

2026年8月16日 开发/基础设施

引言：看上去自相矛盾的组合

自从代码生成速度上来之后，团队里反复出现同一个问题：事到如今，选什么语言还有意义吗。既然不再由人一行一行敲，那么选顺手的语言、选语法舒服的语言，理由都在变淡。那么还剩下什么标准。

对这个问题，有一个值得推敲的案例。Redis 的作者 antirez 在 2026 年往公开仓库里放的东西，绝大部分是用纯 C 写的推理引擎：Flux 2 的图像生成推理、Voxtral 的语音识别、Qwen 系的转写模型、MiniMax H3、DeepSeek 4 系的本地推理引擎，全部是 C 仓库。可同一个人在自己的博客上写的却是「控制想法，而不是控制代码」那一类文章，主张在 AI 一天产出数千行的情况下，逐行去看基本没有意义。

表面上这两件事是拧着的：挑了最费手工的语言，却要减少用手去读代码。本文不是人物介绍。要回答的问题只有一个：生成量暴涨之后，决定语言选型的轴换成了什么。

先把方向钉住。这不是哪门语言更好的问题，而是阅读与验证的成本压在人身上还是压在编译器身上，以及这一选择在什么约束下才成立的问题。约束不同，答案就不同。条件不同的团队照抄同一个决定，只会得到成本而得不到收益。

1. 哪些是真正可以确认的

在处理主张之前，先立住可以确认的部分。从他本人的博客和公开仓库里能看到三件事。

  • 产出是 C。最近的仓库清单全是 C，覆盖图像生成、语音识别、转写和大模型推理，领域很宽。这不是把一个方向挖深的结果，而是把同一套做法在多个领域反复套用的结果。
  • 本地执行是前提。Metal、CUDA、ROCm 这些不同的加速后端在同一个代码库里处理。目标不是藏在服务背后的推理，而是在手边机器上跑起来的推理。
  • 他本人说明自己下调了代码审查的位置。他写道，如果你控制着软件的想法，去看代码本身是次优的，而且往往没有意义。他补充说 Redis 那边的生成代码仍会看，出于对用户的尊重，但也说在当前模型水平下这项工作大体是无意义的。

关键在于，第三点被拆成了三条理由。这三条性质不同，性质不同则可反驳的程度也不同。

理由内容性质模型变强之后
体量一天几千行，全量审查根本不成立算术 — 人的时间不会变多更成立，因为生成量还会涨
偏向模型擅长局部优化，对整体结构较弱观察 — 针对当下模型的陈述可能减弱
机会成本一天八小时，只能在审查与设计、QA 之间取舍选择 — 优先级问题保持不变

这样拆开，讨论就清楚了。偏向这条理由是有时效的，模型更会处理结构之后它会变弱。而体量这条没有时效，反而会加强：生成越快，无人阅读的比例越大。所以评估这个主张的办法是问一句：只留下体量这一条，它还成立吗。成立。而语言选型介入的位置，恰恰就在这里。

2. 控制单元转移，实际意味着什么

「控制想法而不是代码」这句话原样放着更像口号。要让它在工程上可用，就得说清控制单元换成了什么。

他给出的答案是设计文档：把数据结构是什么、实现策略是什么、为什么选这个结构，作为文档维护下来。智能体在这个模型内部接受指令，人维护的是模型而不是代码。据 GeekNews 的中文语境解读文章，这一习惯最初是某个项目的实现笔记文件，后来固定成了 DESIGN.md 的形态。

这里有一点需要工程师自己过滤：有设计文档不等于控制单元真的转移了。大多数组织本来就有设计文档，其中相当一部分是读了代码才看得懂的摘要。那种文档替代不了阅读。判定标准很简单。

如果代码整个消失，仅凭这份文档能不能重造出同一个东西？能，控制单元就是真的转移了；不能，那只是名字转移了。

能通过这一测试的文档不是摘要，而是可重建规格：写明不支持什么、状态归谁所有、哪些不变式一破就是缺陷、正确与否如何判定。于是文档那一侧的劳动自然增加。减少的是审查劳动，增加的是规格劳动。总量下降的魔法并不存在。差别在于规格劳动不会随生成量成比例增长，这正是后文所谈可扩展性的核心。

3. 生成量上去之后，成本跑到哪里

这一节是全文的主干。AI 生成与语言选型的交汇点正在此处。

先把不对称摆明：写代码的成本暴跌，读代码的成本几乎原地不动。生成器几分钟产出几百行，但人理解它、判断它是否正确的速度和从前一样。一天没有变长，能集中阅读的分量也没有增加。

结果是瓶颈从编写转移到验证。瓶颈一旦转移，应对方式只有三种。

  1. 减少需要读的东西。把代码库保持得小，把支持范围收窄。
  2. 把阅读交给机器。编译器、静态分析、消毒器、模糊测试、回归闸门替人去读。
  3. 降低出错时的代价。隔离故障、保证可回滚、限制爆炸半径。

第三种基本属于发布与运维范畴，与语言关系不大。语言选型直接介入的是前两种，而两个阵营正是在这里分开的。

  • 「减少要读的东西」这一侧在执行模型薄的语言上占优。层次少，同样的功能就能用更少的概念表达，什么时候发生什么可以预测，人能装进脑子里的范围因此变宽。
  • 「把阅读交给机器」这一侧在检查器强的语言上占优。类型与所有权规则足够密时，即便是没人读过的代码，某一类缺陷根本通不过。

antirez 的选择更靠近前者，而这个选择是有代价的：编译器不替你抓的部分，必须由别的装置补上。我认为这正是他另外写了一篇关于软件测试的文章的原因。那篇文章里他说，自动生成的代码达不到最好的手写软件那种结构质量，但往往优于开发得还算像样的手写代码，并指出大模型真正压倒性强的领域是 QA：看最近的提交推断哪些部分可能受影响，据此跑针对性的测试，甚至在没有预设基线的情况下检查性能是否退化。

这里就是可扩展性的钥匙。生成量上去，测试的生成量也跟着上去，而人的审查不会。把验证挪向机器一侧，是体量问题唯一的扩展路径。从这个角度看，选一门把验证压在编译器上的语言，和把验证交给 QA 智能体，并不是两种不同的答案，而是同一条轴上的不同位置。

# 人不读的部分，让机器去读 - 开发与 CI 构建
cc -std=c11 -O1 -g \
   -Wall -Wextra -Wconversion -Wshadow -Werror \
   -fsanitize=address,undefined \
   -fno-omit-frame-pointer \
   -c engine.c

# 发布构建必须分开。不要把消毒器带进发布产物
cc -std=c11 -O2 -DNDEBUG -c engine.c

上面这套配置里最关键的是 -Werror。把警告继续当警告，生成量涨多少警告就涨多少，而堆积起来的警告没人会读。要让机器替你读，机器就必须有能力把你拦下。

4. C 给出的东西 — 控制与可预测性

把情绪剔掉，选 C 的理由是四条。

  • 执行模型很薄。源码与机器码之间夹的东西少：没有隐藏的分配，没有隐藏的析构调用，没有隐藏的异常路径。性能为什么是这个数容易解释，不对劲的时候也知道该看哪里。
  • 没有运行时。启动快，产物小，执行过程中不会结构性地插入不可预测的停顿。在音频与实时处理这类看尾部延迟而不是均值的场景里，这个性质很难被替代。
  • 哪里都能接上。加速后端的 SDK 大多以 C 头文件形式发布。要支持新硬件时，能不经中间层直接接上的语言就是 C。对一个要在同一代码库里同时应付 Metal、CUDA、ROCm 的项目而言，这不是便利而是要求。
  • 语言几乎不变。十年前的代码今天照样能构建。在自动生成让代码快速堆积的情况下，语言本身不动这一性质会把维护成本压住。语言若每年都变，多出来的代码量会原样变成迁移债务。

这里有个想加第五条的诱惑：训练数据里 C 多，所以模型写 C 更好。这条不用。主流模型按语言划分的训练数据构成并未公开，公开的编码基准通常也没有控制各语言的难度差异就直接汇总。两个方向都没有证据，所以不能作为论据。

能确定说的是：C 的好处不是因为语言替你做了什么，而是因为它不做什么。不介入所以可预测，不介入所以好接，不介入所以不变。也正因为同样的原因，它也不保护你。

5. C 拿走的东西 — 安全网由人来顶

代价很清楚，而且一旦遇上 AI 生成，性质会变坏。

  • 内存安全在语言层面得不到保证。释放后使用、越界访问、读取未初始化值，在语法上都是可行的。
  • 故障不在发生点显现。这才是真问题。越界写一格的代码不会当场死掉，而是过很久之后以某个无关数据结构被破坏的样子冒出来。
  • 未定义行为会与优化相互作用。改一下优化等级，症状可能消失，也可能新生。光是复现就成了一项工程。
  • 标准库很薄。字符串、容器、错误处理每次都要手工搭。生成器代劳之后，编写成本下降了，但要读要验证的对象同样增加了。
  • 复用生态很浅。比起引入现成库，更常见的是自己造，而自己造多少，就自己拥有多少缺陷。

最糟的组合就在这里形成：第二条与「少读代码」重叠的时候。当无人阅读的代码增多，而症状点与原因点相距很远，调试就从阅读变成了搜索。而搜索的成本不是与代码量成正比，而是比代码量涨得更快。

因此，在选了 C 的前提下削减审查，逻辑上必然要求同时引入运行期验证。没有消毒器、没有模糊测试、没有确定性回归基线，却只把审查砍掉，那不是新方法论，而是省略了验证。上一节那份好处清单，只有在付出这份代价时才成立。

而且最后一条里藏着内部张力：「保持小代码库」和「自己造缺失的库」方向相反。化解这个张力的办法不是省着写代码，而是把领域收窄。这正是下一节的主题。

6. 相反的视角 — Rust 与 Zig 对同一问题的答案

对于同一个问题，也就是人读不完的代码要如何信任，另有阵营给出了不同的答案。如果把这些答案轻描淡写地带过，这篇文章就成了偏袒一方的文字。

Rust — 把验证压在编译器上

Rust 的所有权与借用检查在编译阶段拒绝了内存错误与数据竞争中很大的一类。放在 AI 生成的语境里，这个性质的价值非常直接：存在一类即使无人阅读也通不过的缺陷，在审查带宽是瓶颈时就是净收益。生成量上涨时，检查成本因为在机器一侧，会跟着一起上涨。

代价同样明确：为通过检查器而产生的设计压力，不安全块的边界仍需人来把守，以及构建时间与学习曲线。至于究竟应当要求全面重写，还是把既有 C 资产原样保留再做安全化，本身就是一场大论争。本站已有一篇按威胁模型与代码寿命梳理该论争的文章，这里不再重复，可参见内存安全绝对主义者 - Rust 与 Fil-C 之争，什么才现实。

Zig — 保留控制，只清掉陷阱

Zig 保留了手动内存管理与显式分配器，也就是没有放弃 C 给的控制。作为交换，它去掉了隐藏的控制流，把编译期执行纳入语言，并允许直接取用 C 头文件。它把位置放在了「减少要读的东西」和「交给机器」之间。

代价是成熟度。按官方下载页，最新正式版是 0.16.0（2026 年 4 月 13 日），仍处于 1.0 之前。这意味着语言与标准库还在持续移动，而这一点与 C 那条「语言不变」的好处正面冲突。反过来说，如果是今天启动、今后几年还会持续投入的项目，那种移动更像是在领取改进而不是在付成本。

竖着读这张表看不出优劣，必须横着读才能得出判断：先确定在自己的项目里哪一行才是真正的约束，再在那一行里挑有利的列。顺序一旦颠倒，就变成先选语言再去凑约束，从那一刻起任何选择都能被自圆其说。

7. 「小代码库」不是审美，是约束设计

在他的叙述里反复出现的表达是能够拥有的规模：与其骑在成熟但难啃的大型代码库上，不如直接掌控一个小而聚焦的代码库。

这话乍听像审美。换成工程语言就是：不是要减少代码，而是要减少承诺。代码变大的原因通常不是功能多，而是需要预备的情况多。承诺接受任意模型、承诺支持任意精度、承诺在任何机器上都能跑，每一条都会生出分支与抽象层。

收回的承诺随之消失的代码换来的损失
我们会加载任意模型图图解析、算子分派、形状推断模型一变就得改代码
我们会支持多种精度转换路径与按精度分叉的内核精度实验无法在代码之外进行
我们在任何硬件上都能跑回退路径与运行期能力探测清单之外的设备干脆跑不起来
我们会使用外部库构建配置、版本对齐、初始化代码自己写的部分，缺陷也归自己
我们会留出以后扩展的余地插件点、配置表面、抽象接口需求一变就是重做而非扩展

表格右列就是这套策略诚实的价目表。只有当领域窄且长期固定时，这笔交易才划算。像推理引擎这样，输入格式与运算结构在模型发布时就已确定的领域很契合；反过来，在需求每季度都变的业务系统里做同样的交易，收回的承诺每季度都得再买回来。

没有依赖同样不是审美而是价值：构建可复现，供应链审计项减少，几年之后仍能产出同一个物件。对于引入审查本身就是瓶颈的组织，仅凭这一项就足以为底层选择正名的情况是存在的。不过要真正拿到这份价值，可复现构建必须被文档化。哪儿都没写的话，「没有依赖」这个事实在审计中是证明不了的。

8. 少读了之后，那个位置放什么

此前谈的是判断，这一节谈执行。削减人工审查不是决定而是结果，决定是往腾出的位置里放什么。

甲、先把机器阅读层立起来

  • 把警告提升为错误。没人读的警告等于没有警告。
  • 把地址与未定义行为消毒器常驻挂在开发与 CI 构建上，并与发布构建分开。
  • 对输入解析与边界处理做模糊测试。生成代码越多，用手点不出来的边界就越多。
  • 把静态分析放进 CI，但只对新增问题设卡并取基线。全量设卡在上线第一天就会被绕过。

乙、造出可判定的基线

  • 把参考实现的输出与容差事先定成数字。事后再定，就会定成刚好能通过的样子。
  • 先故意破坏、确认能被检出之后，才承认它是回归闸门。未经验证的闸门只是一枚通过章。
  • 性能不记绝对值，只记同条件下的相对比较，并把设备、线程数、输入长度一并留存。

丙、把设计文档做成可重建规格

把第 2 节说的判定标准挪进文档骨架，大致是这个样子。

# DESIGN.md - 仅凭这份文档必须能重造出同一个东西

## 1. 我们决定不做的事
- 支持模型：固定 1 种。不加载任意计算图
- 支持精度：固定 1 种。运行期不做转换
- 支持硬件：低于基准指令集则在初始化阶段直接失败

## 2. 数据结构与所有权
- 状态集中在单个结构体。初始化之后不再分配
- 缓冲区归调用方所有。库不负责释放

## 3. 不变式 - 一旦破坏就是缺陷
- 帧边界处始终满足 write_pos < capacity
- 公开函数即使失败也不修改输入缓冲区

## 4. 正确性如何判定
- 基线：与参考实现输出的容差为 1e-4
- 回归闸门：故意注入缺陷确认可检出之后才登记进 CI
- 性能：只承认标注了设备、线程数、输入长度的相对比较

这份文档的价值在第 1 节。大多数设计文档只写做什么，从不写决定不做什么。可指挥生成器时真正需要的恰恰是后者。不做的事没有写下来，生成器就会很贴心地补上兜底代码，那一刻，本想保持得小的代码库就悄悄变大了。

9. 工程视角 — 这一判断在什么条件下可复现

同样的决定，团队能不能照搬？有条件。而且这些条件不在语言功力上，在组织结构上。

目标硬件确定的端侧与边缘场景高基准指令集与失败策略
引入审查、供应链审计是瓶颈中到高可复现构建有没有文档化
人员流动频繁的外包与派驻结构低交接对象是代码还是设计文档
受监管行业的采购与安全检查对象低到中检查项是否约束语言与工具
需求每季度变动的业务系统低收回的承诺要多久买回一次
初级工程师占比高的团队低不读代码能否建立心智模型

表里最沉的一行是人员流动。控制单元从代码转向设计之后，交接对象也跟着转移；可很多现场的交接仍以源码和界面为主。在没有维护文档习惯的组织里只砍审查，转移过去的控制哪儿也留不下。这种情况下，比语言选型更该先动的是文档习惯。

最后一行也不能一带而过。antirez 本人在这一点上留了保留意见，大意是他不确定经验不足的程序员能否在不直接看代码的情况下建立起软件的心智模型。这与招聘结构直接咬合：新人靠读代码积累手感的通道正在变短，而替代通道尚未成形。这个问题目前没有确立的答案。

现实的折中不是全面迁移，而是只把一条瓶颈路径窄窄地固定下来下沉到底层，其余留在既有技术栈上。这样即便失败，需要回滚的范围也被限制在一个模块之内，也不必一次凑齐上表的全部条件。先在那个模块里练习设计文档与回归闸门，要不要扩大，之后再拿证据来定。

10. 没有确认到的部分

把本文没有当作依据使用的东西集中放在一处。

  • 具体的产出轶事。五分钟做出 700 行嵌入库、仅凭设计文档二十分钟复现某项改造之类的说法，出自韩文的解读文章，承载这些数字的原始博文未能逐条比对。文中仅作为方向性的注脚提及，没有当作论据。
  • 跨语言性能对比数字。没有找到这些仓库与既有推理框架之间标注了条件的公开对比表，因此本文不放任何倍数或吞吐数字。
  • 模型在各语言上的强弱。主流模型训练数据的语言构成并未公开。「AI 写 C 更好」与「写得更差」都没有依据。
  • 设计文档习惯的外部复现。没有找到其他团队以同样方式转移控制单元并公开成果的案例。本文第 8 节不是对观察案例的报告，而是从原则推导出来的构造。
  • 仓库热度指标。星标数之类的数字随时点变动，未予引用。

结论：选的不是语言，是约束

这个案例真正能确认的不是「C 更好」这个命题，而是在某组条件下这个组合成立：领域窄且固定、目标硬件确定、拥有者人数少、代码需要活得久、并且已经准备好把验证挪向机器一侧。条件一变，同样的选择会给出不同的结果。

另一侧也一样。检查器强的语言在结构上适配无人阅读的代码不断增加的局面，团队越大、安全要求越强，这份收益越大。本文并不认为那个答案是错的。两个答案是同一问题上的不同位置，站在哪里由约束决定。

工程师可以带走的有三点。

  1. 不要先选语言。先确定在自己的项目里，真正的约束是哪一行 — 是贴近硬件，是安全要求，还是代码寿命 — 再在那一行里挑有利的列。顺序颠倒，任何选择都能事后自圆其说。
  2. 要削减审查，先定好拿什么来替。警告升级、消毒器、模糊测试、经故意注入缺陷验证过的回归闸门，以及一份能据以重建的设计文档。没有这些就只砍审查，那不是方法论。
  3. 把「保持小」翻译成「少许承诺」。不支持什么如果没写进文档，生成器永远会替你补上兜底代码。

压成一句话：写代码的成本下降了多少，涨价的就是阅读与验证，而语言是决定这笔账单开给谁的装置。这张账单由人来收、由编译器来收，还是由工具来收，取决于自己项目的约束，而不是潮流。
