引言：清理代码在最后一行，而脚本没走到那里

设想一个脚本：创建临时目录，把中间产物堆进去，用完了在最后一行删掉。平时一切正常，问题出在不平常的时候。输入文件缺失于是中途exit 1退出，发布过程中CI取消了任务，或者有人在终端按了Ctrl+C。每一种情况清理代码都不会执行，因为脚本压根没走到那一行。

这类残骸会悄悄堆积。一个200MB的工作目录每天留下几个，几周后就变成磁盘告警。等到那时打开残留目录，也很难判断它出自哪一次运行、什么时候产生的。

trap正面处理这个问题。它把清理代码从「最后要执行的一行」改成「shell退出时必须执行的代码」。不过这句话后面挂着一串例外：有的结束方式能被捕获，有的不能；不同shell结果不一样；写得不当还会删掉不该删的东西。

本文的命令和输出都是在GNU bash, version 5.2.37(1)-release和dash上原样跑出来的。所有删除动作只针对/tmp下由mktemp创建的路径。如果shell基本功还不牢，先看Shell脚本基础和Shell脚本高级。

1. 无论怎么结束都会清理的一行

基本写法很短。创建临时文件，然后把删除它的命令注册到EXIT上。

#!/usr/bin/env bash
tmp=$(mktemp /tmp/work.XXXXXX)
trap 'rm -f "$tmp"' EXIT

EXIT不是信号，而是指代shell终止那一刻的一个假名字。所以正常结束、显式exit 1、以及被set -e捕获的失败，全都会经过这个点。三条路径分别跑过一遍，结果如下。

$ bash t1.sh ok
created: /tmp/work.Z8kaai
doing work
[trap] cleaning /tmp/work.Z8kaai
exit=0

$ bash t1.sh fail            # 脚本中途的 exit 1
created: /tmp/work.af0aeI
about to exit 1
[trap] cleaning /tmp/work.af0aeI
exit=1

$ bash t1.sh err             # set -e 状态下某条命令失败
created: /tmp/work.cLzp5n
about to run a failing command
[trap] cleaning /tmp/work.cLzp5n
exit=1

三种情况处理函数都执行了，退出码也保持了原值。这就是trap能确定给你的部分。

1.1 单引号和双引号会给出不同结果

陷阱主体有两次被解释的机会：注册时一次，触发时一次。变量在哪一次展开，由引号决定。

$ tmp=/tmp/first
$ trap "echo [double] would remove $tmp" EXIT   # 双引号：此刻就展开
$ tmp=/tmp/second
$ echo "tmp is now $tmp"
tmp is now /tmp/second
[double] would remove /tmp/first

$ tmp=/tmp/first
$ trap 'echo "[single] would remove $tmp"' EXIT # 单引号：触发时才展开
$ tmp=/tmp/second
$ echo "tmp is now $tmp"
tmp is now /tmp/second
[single] would remove /tmp/second

双引号那一侧要删的是注册时刻的值/tmp/first。只要临时路径是后面才确定的，或者会在循环里变化，这个差别就直接变成事故。

  • 陷阱主体默认用单引号包起来
  • 主体超过一行就抽成函数，用trap cleanup EXIT只注册名字，引号的烦恼就消失了
  • 抽成函数后用trap -p检查时注册内容也短，读起来更轻松
  • 只有在调试、确实想把值冻结在注册时刻的时候，才刻意使用双引号

2. 按了Ctrl+C临时文件却还在的原因

从这里开始才是真正会分岔的部分。只挂了EXIT的脚本被信号杀掉会怎样？让脚本给自己发信号来确认。

$ cat t4.sh
tmp=$(mktemp /tmp/work.XXXXXX)
trap 'echo "[EXIT trap] rm $tmp"; rm -f "$tmp"' EXIT
kill -"$1" $$
sleep 5
echo "SURVIVED the signal"

$ bash t4.sh INT
pid=1349 tmp=/tmp/work.ZaHJMi  sending SIGINT to self
[EXIT trap] rm /tmp/work.ZaHJMi
exit=130 tmpfile=cleaned

$ bash t4.sh TERM
[EXIT trap] rm /tmp/work.By1Y9n
Terminated
exit=143 tmpfile=cleaned

在bash上只挂EXIT，SIGINT、SIGTERM、SIGHUP都会触发处理函数。退出码也准确，130和143，就是128加上信号编号。

2.1 可是在dash上不执行

同一个脚本换成dash跑，结果就翻过来了。

$ bash /tmp/d2.sh          # 只注册 EXIT 陷阱，给自己发 SIGTERM
[EXIT] rm /tmp/work.LJpwWB
Terminated
  rc=143
  cleaned

$ dash /tmp/d2.sh
Terminated
  rc=143
  LEFTOVER /tmp/work.skxk0l

dash根本没执行处理函数，文件原样留下。shebang写成#!/bin/sh的脚本在部署环境里经常由dash执行。如果开发机上/bin/sh链接到bash，这个差别根本看不见，等上了线残骸才开始堆积。

2.2 把信号写明，dash也会清理

修法就是在EXIT旁边把信号列出来。

cleanup() { rm -f "$tmp"; }
trap cleanup EXIT
trap 'cleanup; trap - INT;  kill -INT  $$' INT
trap 'cleanup; trap - TERM; kill -TERM $$' TERM
trap 'cleanup; trap - HUP;  kill -HUP  $$' HUP
$ dash /tmp/d3.sh
[cleanup] rm /tmp/work.Gjy9y6
Terminated
  rc=143
  cleaned

关键在于处理函数用trap - INT解除自己的陷阱之后，再用同一个信号把自己打死。直接用exit 0结束的话，调用方看到的是运行成功。

$ cat /tmp/reraise2.sh
trap 'echo "[INT] cleaning"; exit 0' INT
kill -INT $$

$ bash /tmp/reraise2.sh
[INT] cleaning
rc=0        # 明明被中断，却报告成功

$ bash /tmp/reraise.sh      # 清理后用同一个信号重新触发
pid=587 tmp=/tmp/work.QAJTr9
rc=130      # 128+2，调用方期待的值

CI运行器和上层脚本靠这个退出码区分「已取消」「失败」和「成功」。清理做得再干净，把退出码搞坏了，上层判断照样会乱。

3. 哪些信号会触发处理函数，哪些不会

把同一个脚本用两种方式武装起来，逐个发送信号，整理成表。A只注册trap ... EXIT，B在EXIT之外再加INT TERM HUP QUIT。

信号编号A：仅EXITB：EXIT+信号退出码备注
SIGINT2已清理已清理130Ctrl+C发出的
SIGTERM15已清理已清理143kill的默认值
SIGHUP1已清理已清理129终端断开
SIGQUIT3脚本活了下来处理函数执行但继续跑0非交互bash默认忽略
SIGKILL9留下残骸留下残骸137无法捕获

表里A和B看着一样，但这说的是bash。正如第2节所示，dash上A会垮掉。一旦考虑可移植性，B才是基本形。

3.1 SIGQUIT默认被忽略

这是表里唯一一个另类的行。非交互的bash脚本在没挂陷阱时会直接忽略SIGQUIT。

$ cat /tmp/q2.sh
echo "no trap armed; sending QUIT to self"
kill -QUIT $$
echo "survived"

$ bash /tmp/q2.sh
no trap armed; sending QUIT to self
survived
rc=0

挂上陷阱之后处理函数本身是会执行的，只是处理函数不调用exit的话脚本会照常往下走。

$ bash /tmp/q1.sh
armed; sending QUIT to self
[QUIT handler] ran
survived (handler did not abort the script)
rc=0

dash上结果相同。实际工作中直接处理SIGQUIT的场合不多，但它很好地说明了「既然挂了陷阱脚本就会停」这个前提可能落空。处理函数执行和脚本结束是两回事。

4. kill -9之后到底留下了什么

SIGKILL不会投递给进程。内核直接抹掉进程，shell根本没有执行代码的机会。把装有五个64KB文件的工作目录用kill -9打断，数一下剩下什么。

$ bash /tmp/leftover.sh &
$ sleep 1; kill -9 $!
$ du -sh /tmp/work.yURWz1; ls -1 /tmp/work.yURWz1
320K    /tmp/work.yURWz1
    chunk.1
    chunk.2
    chunk.3
    chunk.4
    chunk.5

陷阱在EXIT INT TERM HUP上全都挂着，一个都没执行。

4.1 bash并不阻止你给KILL挂陷阱

这才是真正的坑。如果能当语法错误拒掉就好了，可惜并没有。

$ bash -c 'trap "echo caught" KILL; trap -p'
trap -- 'echo caught' SIGKILL
rc=0

trap -p的清单里堂而皇之地列着SIGKILL条目。代码评审时看到trap cleanup EXIT INT TERM KILL这样一行，读起来像是连KILL都堵上了，可那个位置什么也不做。它制造的是一种并不存在的安全感。

4.2 所以对策要放在进程外面

  • 给临时路径加固定前缀。用mktemp -d /tmp/myjob.XXXXXX这样创建，事后一眼就能看出留了什么
  • 让一个独立的清扫任务定期回收该前缀下的陈旧条目。按最后修改时间过滤就不会碰到正在运行的
  • 产物确实很大就别用/tmp，改用容量有余的独立卷，免得残骸把别的服务拖垮
  • 先减少SIGKILL到来的途径。容器编排器和服务管理器通常在停止宽限期到点后升级为KILL，只要清理能在这个窗口内完成，就很少会见到KILL
  • 如果清理要花几十秒，正确做法是缩短清理，延长宽限期是第二步

5. 挂了两个清理却只跑一个的原因

对同一个信号挂两次陷阱，后挂的会覆盖先挂的，不会累加。

$ bash -c 'trap "echo first" EXIT; trap "echo second" EXIT; echo body'
body
second

既没有报错也没有警告。两个函数各自把自己的临时文件注册到EXIT上，只有后调用的那个活下来，前一个清理悄无声息地消失。用source引入库性质脚本的结构里，这种情况尤其常见。

5.1 把清理项堆起来一次性执行

_cleanups=()
add_cleanup() { _cleanups+=("$1"); }
_run_cleanups() {
    for ((i=${#_cleanups[@]}-1; i>=0; i--)); do eval "${_cleanups[i]}"; done
}
trap _run_cleanups EXIT

add_cleanup "echo remove file A"
add_cleanup "echo remove dir B"
add_cleanup "echo release lock C"
$ bash /tmp/stack.sh
body
release lock C
remove dir B
remove file A

按注册的逆序执行是关键。如果先拿锁后建目录，释放时就应该先删目录、最后解锁。

5.2 往已有处理函数后面拼接的办法

如果别处已经挂了陷阱，可以用trap -p读出来再拼接。

add_exit() {
    local prev new
    prev=$(trap -p EXIT)
    prev=${prev#trap -- \'}
    prev=${prev%\' EXIT}
    if [ -z "$prev" ]; then new="$1"; else new="$prev; $1"; fi
    trap "$new" EXIT
}
$ bash /tmp/a1.sh
captured: trap -- 'echo first-handler' EXIT
now armed as: trap -- 'echo first-handler; echo second-handler; echo third-handler' EXIT
body
first-handler
second-handler
third-handler

能跑，但要接受两点代价。第一，处理函数字符串里若含有单引号，上面的字符串截取就会错位。第二，trap -p是bash扩展，dash里用不了。

$ dash -c 'trap "echo x" EXIT; trap -p'
dash: 1: trap: Illegal option -p

在dash里不带参数敲trap是能列出清单的，但把那份输出解析回去，引号处理更加棘手。需要可移植性的话，5.1的数组方式更合适。

$ bash -c 'trap "echo a" EXIT INT; trap'
trap -- 'echo a' EXIT
trap -- 'echo a' SIGINT

$ dash -c 'trap "echo a" EXIT INT; trap'
trap -- 'echo a' EXIT
trap -- 'echo a' INT

bash写作SIGINT，dash写作INT。要是做一个机械比对这份输出的检查器，就会栽在这个差别上。

5.3 怎样撤掉陷阱

trap - EXIT       # 恢复默认行为
trap '' INT       # 改为忽略（与解除不同）

第二种写法有副作用。被设为忽略的信号会被子进程继承，而且子进程无法改回来。

$ cat /tmp/ig.sh
trap '' INT
bash -c 'trap "echo child handler" INT; trap -p INT'

$ bash /tmp/ig.sh
trap -- '' SIGINT

子进程明明执行了trap "echo child handler" INT，清单里依然是空字符串，也就是忽略状态。父进程以忽略状态传下去的信号，子进程再也抓不回来。如果你的脚本是包着另一条命令运行的封装器，这份继承会把那条命令的Ctrl+C响应给抹掉。

6. 子shell、后台任务和函数里陷阱能跟到哪

管道和括号会多创建一个进程这件事，在管道里的while为什么变量会消失里讲过。陷阱在同一条边界上的表现和变量并不一样。

6.1 子shell会继承陷阱，但不会因自身退出而触发

$ cat /tmp/sub_t.sh
trap 'echo "[EXIT] fired in BASHPID=$BASHPID"' EXIT
echo "parent BASHPID=$BASHPID"
( echo "  inside subshell BASHPID=$BASHPID"; exit 3 )
echo "subshell rc=$?"

$ bash /tmp/sub_t.sh
parent BASHPID=340
  inside subshell BASHPID=341
subshell rc=3
[EXIT] fired in BASHPID=340

子shell是独立进程（341）并且以exit 3结束，可处理函数只在父进程（340）里执行了一次。不必担心同一份清理被执行两遍。反过来说，只在子shell内部使用的临时文件，就得在里面单独挂一个。

$ cat /tmp/sub_t2.sh
trap 'echo "[parent EXIT] BASHPID=$BASHPID"' EXIT
( trap 'echo "  [subshell EXIT] BASHPID=$BASHPID"' EXIT
  echo "  inside subshell BASHPID=$BASHPID"; exit 3 )
echo "subshell rc=$?"

$ bash /tmp/sub_t2.sh
  inside subshell BASHPID=344
  [subshell EXIT] BASHPID=344
subshell rc=3
[parent EXIT] BASHPID=343

在子shell内部注册的陷阱，会在子shell结束时于其中执行；父进程的陷阱在父进程结束时另行执行。两者互不干扰。

6.2 后台任务同理，管道内部的也出不来

$ bash /tmp/sub_t3.sh
parent BASHPID=346
  bg BASHPID=347
parent done
[EXIT] fired in BASHPID=346
$ bash /tmp/a2.sh
echo x | { trap 'echo "[inner EXIT]"' EXIT; cat > /dev/null; }
[inner EXIT]
parent continues
parent trap -p EXIT output:
(nothing between the two lines = the parent has no EXIT trap)

在管道组成部分内部挂的陷阱，会在该组成部分结束时执行，不会留在父进程里。要是脚本正文里挂了陷阱却好像不触发，先看那一行是不是在管道右侧或者括号里面。

6.3 函数里挂的陷阱出了函数还活着

$ bash -c 'f() { trap "echo [EXIT] set inside f" EXIT; echo "in f"; }; f; echo "after f"'
in f
after f
[EXIT] set inside f

EXIT陷阱是整个shell的状态，不是函数局部的。函数为了清理自己的临时文件而注册到EXIT，这份注册会一直留到脚本结束，并且覆盖其他函数的注册。和第5节是同一个根源。

6.4 ERR和RETURN需要开选项才能进到里层

ERR陷阱在命令失败时触发，但默认配置下不会进入函数、子shell和命令替换的内部。

$ bash -c 'set -e; trap "echo [ERR] caught" ERR; h() { false; }; h; echo "NOT REACHED"'
rc=1                       # 处理函数没有执行

$ bash -c 'set -eE; trap "echo [ERR] caught" ERR; h() { false; }; h; echo "NOT REACHED"'
[ERR] caught
rc=1

要开set -E，ERR才会继承到函数内部。RETURN和DEBUG陷阱由set -T扮演同样的角色。

$ bash -c 'trap "echo [RETURN]" RETURN; g() { echo "in g"; }; g'
in g

$ bash -c 'set -T; trap "echo [RETURN]" RETURN; g() { echo "in g"; }; g'
in g
[RETURN]

触发顺序也确认过了。发生失败时ERR在前，EXIT在后。

$ bash -c 'trap "echo [ERR]  seen" ERR; trap "echo [EXIT] seen" EXIT; set -e; false'
[ERR]  seen
[EXIT] seen
rc=1

用ERR记录在哪里失败，把真正的清理留在EXIT上，这样的分工比较自然。另外ERR、RETURN、DEBUG全都是bash扩展。

$ dash -c 'trap "echo err" ERR; false; echo done'
trap: ERR: bad trap
done

$ dash -c 'trap "echo ret" RETURN; f(){ :; }; f'
trap: RETURN: bad trap

7. 不让清理代码删掉不该删的东西

请先读这一节。本节内容必须先于后面的示例落实。清理脚本写得不当就会删掉不该碰的东西。删除不可撤销，而且脚本删掉的文件不会进回收站。在下面三道护栏装好之前，别把含有rm -rf的陷阱放到有真实数据的机器上。

7.1 变量为空就地停下

陷阱可以在脚本的任何位置触发。临时路径变量还没赋值就收到信号的情况是真实存在的。在那种状态下删除命令照跑，目标会变成什么完全无法预测。

cleanup() {
    : "${workdir:?cleanup called with no workdir}"
    ...
}

:是什么都不做的内建命令，${var:?消息}是变量为空就打印消息并当场停下shell的展开。两者合起来就是一行只做取值检查的断言。

$ bash -c 'cleanup() { : "${workdir:?cleanup called with no workdir}"; echo "would remove $workdir"; }
trap cleanup EXIT
echo body'
body
environment: line 2: workdir: cleanup called with no workdir

还没走到删除那一行就停住了。没有这一行会发生什么，这里只做说明，不做演示。rm -rf -- "$workdir"在变量为空时参数变成空字符串，通常会以报错收场，但下面这些常见写法就完全不同了。

  • rm -rf "$workdir"/* — 变量为空就变成/*，根目录下的所有内容都成了目标
  • rm -rf "$base/$sub" — 两者之一为空，残留的斜杠会让删除落到比预期高一层的位置
  • cd "$workdir" && rm -rf . — cd失败就会在当前目录里执行。即使有&&，只要cd成功进了错的地方，照样往下走
  • rm -rf $workdir — 不加引号时，含空格的路径会被拆成多个参数，前面那一截碰巧存在就会被删掉

这四种都不是拿来试跑看看的东西。先装护栏，再写删除那一行。

7.2 把路径钉死

只是非空还不够，还要看值是不是预期的形状。

cleanup() {
    : "${workdir:?}"
    case "$workdir" in
        /tmp/myjob.*) rm -rf -- "$workdir" && echo "[cleanup] removed $workdir" ;;
        *)            echo "[cleanup] refusing to remove unexpected path: $workdir" >&2 ;;
    esac
}
$ bash /tmp/guarded.sh
workdir=/tmp/work.nGJBt5
removed /tmp/work.nGJBt5
rc=0

前缀不匹配就不删，只留告警。改脚本时不小心让workdir装进别的值，删除也不会发生，而且日志里会留下痕迹。

7.3 先挂陷阱，再创建

顺序颠倒的代码很常见。

# 脆弱的顺序：在这两行之间死掉，文件就留下了
tmp=$(mktemp /tmp/work.XXXXXX)
... 准备工作 40 行 ...
trap 'rm -f -- "$tmp"' EXIT

中间看着再短，只要信号落在那个区间，残骸照样留下。反过来写就行了。

tmp=
cleanup() { [ -n "$tmp" ] && rm -f -- "$tmp"; echo "[cleanup] handled tmp=[$tmp]"; }
trap cleanup EXIT
tmp=$(mktemp /tmp/work.XXXXXX)
$ bash /tmp/race2.sh
trap armed before anything exists
created /tmp/work.35mmxL
[cleanup] handled tmp=[/tmp/work.35mmxL]

$ bash /tmp/race3.sh        # 在 mktemp 之前退出
[cleanup] handled tmp=[]
rc=1

还什么都没创建就死掉的话，处理函数会安静地什么也不做然后结束。用tmp=预先声明，在set -u环境下尤其重要。

$ bash -c 'set -u; cleanup() { echo "rm -rf -- \"$workdir\""; }; trap cleanup EXIT; echo body'
body
environment: line 3: workdir: unbound variable

7.4 不可撤销的那个点

  • 删除一旦开始，中断也没用。rm -rf跑到一半按Ctrl+C，已经没了的东西不会回来
  • 把原件挪进临时目录的设计很危险。如果是用移动而不是复制放进去的，清理陷阱就成了删除原件的陷阱
  • 清理目标有可能是符号链接的结构，要确认删除会不会跟着链接走。本想删链接本身，结果删掉了链接指向的真实数据，这种事是有的
  • 把网络文件系统或共享卷当临时空间用，意味着别的进程可能在用同一个路径。在前缀里放上进程标识，避免撞车
  • 改了清理逻辑之后，把删除换成echo先跑一遍。用眼睛确认目标路径，再换回真正的删除
  • 第一次上生产机时，用mv挪到隔离目录而不是rm，这样跑几天。意料之外的路径会在这段时间里暴露出来

8. 整个目录进，整个目录出

如果任务要创建的不止一个文件，用mktemp -d拿一个目录、所有处理都在里面进行会更好，清理目标就收敛成一个。

#!/usr/bin/env bash
set -euo pipefail

workdir=
_cleaned=0

cleanup() {
    [ "$_cleaned" -eq 1 ] && return
    _cleaned=1
    trap '' INT TERM HUP
    if [ -n "$workdir" ] && [ -d "$workdir" ]; then
        case "$workdir" in
            /tmp/job.*) rm -rf -- "$workdir" && echo "[cleanup] removed $workdir" ;;
            *)          echo "[cleanup] refusing to remove unexpected path: $workdir" >&2 ;;
        esac
    else
        echo "[cleanup] nothing to remove"
    fi
}

on_signal() {
    local sig=$1
    echo "[signal] SIG$sig received" >&2
    cleanup
    trap - "$sig" EXIT
    kill -"$sig" "$$"
}

trap cleanup EXIT
for s in INT TERM HUP; do trap "on_signal $s" "$s"; done

workdir=$(mktemp -d /tmp/job.XXXXXX)
echo "workdir=$workdir"

printf 'row1\nrow2\nrow3\n' > "$workdir/input.txt"
wc -l < "$workdir/input.txt"

三条路径全部跑过并确认。

$ bash job.sh ok
workdir=/tmp/job.QoSGZJ
rows: 3
work finished
[cleanup] removed /tmp/job.QoSGZJ
rc=0
verified: /tmp/job.QoSGZJ gone

$ bash job.sh fail
workdir=/tmp/job.aHj3Nw
rows: 3
failing on purpose
[cleanup] removed /tmp/job.aHj3Nw
rc=1
verified: /tmp/job.aHj3Nw gone

$ bash job.sh signal
workdir=/tmp/job.ipwR33
rows: 3
signalling myself
[signal] SIGINT received
[cleanup] removed /tmp/job.ipwR33
rc=130
verified: /tmp/job.ipwR33 gone

把这份模板里的要素逐条点出来是这样的。

  • 先声明workdir=，挂好陷阱之后再调用mktemp -d（7.3）
  • 用_cleaned标志避免清理跑两遍（第10节）
  • 清理一开始就用trap '' INT TERM HUP挡住后续信号
  • 用case确认路径前缀（7.2）
  • 信号处理函数清理完之后用同一个信号把自己再打一枪，保住退出码（2.2）
  • local sig=$1让处理函数接收自己的参数，就不用为每个信号名各写一个函数

8.1 子进程也要一起清

如果起了后台任务，只删目录是不够的。会留下继续想用已消失路径的孤儿进程。

cleanup() {
    echo "[cleanup] killing $(jobs -p | wc -l) background job(s)"
    jobs -p | while read -r p; do kill "$p" 2>/dev/null; done
    : "${workdir:?}"
    rm -rf -- "$workdir"
}
$ bash /tmp/kids.sh
running with 2 children
[cleanup] killing 2 background job(s)
[cleanup] workdir removed
workdir gone: /tmp/work.47Wiqu

顺序很重要。先杀子进程，再删目录。反过来的话，子进程会往消失的路径里写，把日志刷满错误。

9. 和set -e一起用时会错位的地方

在开了set -e的脚本里，陷阱处理函数会怎样？处理函数内部出错的话，剩下的清理又会怎样？就从这里开始确认。

$ bash -c 'trap "echo [EXIT] start; false; echo [EXIT] still running; echo [EXIT] done" EXIT; echo body'
body
[EXIT] start
[EXIT] still running
[EXIT] done
outer rc=0

处理函数中途的失败没有挡住后面的部分，退出码也没变。可是在处理函数内部开set -e，情况就不一样了。

$ bash -c 'cleanup() { set -e; echo "[cleanup] step 1"; false; echo "[cleanup] step 2 - NOT REACHED"; }
trap cleanup EXIT
echo body'
body
[cleanup] step 1
outer rc=1

第二步没有执行。清理函数里第一个删除失败，第二个删除和解锁就被整体跳过。退出码也变成了1，把原来的结果覆盖掉。

  • 清理函数内部不要开set -e。清理是即使失败也要一路试到底的那类代码
  • 脚本开头的set -e在函数内部同样有效，所以在清理函数第一行写set +e有时是稳妥的做法
  • 要吸收单条命令的失败，就用rm -f这类目标不存在也算成功的选项，或者加上|| true
  • 想忽略失败但保留记录，就换成|| echo "..." >&2的写法

9.1 处理函数里的exit会覆盖退出码

$ bash -c 'trap "echo [EXIT] handler; exit 99" EXIT; exit 3'
[EXIT] handler
rc=99

$ bash -c 'trap "echo [EXIT] handler" EXIT; exit 3'
[EXIT] handler
rc=3

处理函数不调用exit的话，原来的退出码原样保留。习惯性地在清理处理函数里加exit 0，会让失败的运行被报告成成功。在自动化流水线里，比这更糟的缺陷不多。

9.2 exec不会把陷阱带走

$ bash -c 'trap "echo [EXIT] should not print" EXIT; echo before-exec; exec echo after-exec'
before-exec
after-exec

exec会用另一个程序替换掉shell进程。替换之后那个shell已经不存在，EXIT陷阱也随之消失。如果容器入口脚本最后是用exec拉起主程序，那么在它前面挂的清理陷阱永远不会执行。

10. 清理途中又来一次Ctrl+C

在清理需要2秒的情况下，以1秒间隔发了三次SIGINT。这是一个没有护栏的处理函数。

$ bash /tmp/reenter.sh
start (05)
  [cleanup] enter  (06)
  [cleanup] enter  (08)      <-- 前一次清理还没结束又进来了
  [cleanup] leave  (10)
  [cleanup] leave  (10)
end (16)

enter连着出现了两次。清理代码在自身内部被嵌套执行了。这种状态下实际会发生什么？

  • 会尝试删同一个目录两次。第二次因为目标不在而报错
  • 解锁跑两遍的话，第二次解锁可能把下一次运行刚拿到的锁给放掉
  • 回滚计数器或整理日志之类的代码会被应用两次，数值出现偏差
  • 嵌套的内层先结束并调用exit，外层清理就会在只做了一半的状态下随进程一起消失

10.1 标志位和信号屏蔽一起用

_cleaned=0
cleanup() {
    [ "$_cleaned" -eq 1 ] && { echo "  [cleanup] already done, ignoring"; return; }
    _cleaned=1
    trap '' INT TERM HUP      # 清理期间忽略信号
    ...
}
$ bash /tmp/reenter2.sh
start (17)
  [cleanup] enter  (18)
  [cleanup] leave  (20)
end (26)

同样收到三次SIGINT，清理只跑了一次。用两层来挡是有理由的。

  • _cleaned标志防止EXIT和信号处理函数都调用同一个清理函数时的重复
  • trap '' INT TERM HUP阻止清理进行中新信号再次调用处理函数
  • 只有标志位的话，第二次进入确实会return退出，但期间第一次清理已经挨了一次中断
  • 只有屏蔽的话，挡不住从EXIT路径来的重复。EXIT不是信号，不在屏蔽范围内

清理太长的话，屏蔽本身也有风险。忽略信号的区间一长，用户按Ctrl+C就毫无反应，最后只会走向kill -9，那就又回到第4节的局面了。把清理保持得足够短，才是最好的防御。

11. 处理函数看上去反应很慢的时候

你大概经历过按了Ctrl+C好几秒都没动静的情况。shell在等待前台子命令期间会推迟陷阱的执行。信号是立刻接收的，但处理函数要等那个子进程结束之后才动。实测是这样。

$ bash /tmp/measure.sh 5        # sleep 5 放前台，t+1 秒发 SIGINT
  signal will arrive at t+1s
  [handler] ran at t+5s
  foreground sleep 5 returned at t+5s

$ bash /tmp/measure2.sh         # sleep 5 & 起到后台再 wait
  signal will arrive at t+1s
  [handler] ran at t+1s
  wait returned at t+1s

同样是5秒等待，一个处理函数晚了4秒，另一个立刻执行。差别在于wait会被信号中断，而前台的sleep不会。

11.1 让反应变快的办法

  • 长等待改写成sleep 300 & wait $!的形式。信号一来wait立刻返回
  • 能拆就拆。用多次sleep 0.5的循环来验证时，处理函数在t+1秒就执行了
  • 把耗时的外部命令起到后台再用wait等待，效果相同。只是要从wait "$job"的返回值里取退出码
  • 这种延迟不是清理做不了，而是晚一点做。着急连按Ctrl+C，就转移到第10节的重入问题了
$ bash /tmp/defer5.sh
[04:37] waiting on background sleep 4
  >>> [04:38] TERM handler
rc=143

12. 挡住重复运行的锁，以及孤儿锁

清理陷阱第二常见的用途是释放锁。mkdir在目标已存在时会失败，而且检查与创建是一步完成的，所以能当作加锁的原语来用。

lockdir=/tmp/myjob.lock
if ! mkdir "$lockdir" 2>/dev/null; then
    echo "another run holds $lockdir - exiting"
    exit 1
fi
trap 'rmdir "$lockdir" 2>/dev/null' EXIT INT TERM HUP
$ bash /tmp/lock.sh &          # 第一次运行
1854 holds the lock
$ bash /tmp/lock.sh            # 紧接着第二次运行
another run holds /tmp/myjob.lock - exiting
second run rc=1
[cleanup] released /tmp/myjob.lock
lock released

12.1 SIGKILL留下的锁会永远留着

第4节的结论在这里再次出现。被kill -9打死之后锁目录原样留下，之后任何一次运行都启动不了。这比磁盘写满还要紧急。在锁里留下持有者信息，下一次运行就能做判断。

if mkdir "$lockdir" 2>/dev/null; then
    echo "$$" > "$lockdir/pid"
    trap 'rm -f "$lockdir/pid"; rmdir "$lockdir" 2>/dev/null' EXIT INT TERM HUP
else
    owner=$(cat "$lockdir/pid" 2>/dev/null)
    if [ -n "$owner" ] && kill -0 "$owner" 2>/dev/null; then
        echo "lock held by live pid $owner"
    else
        echo "STALE lock (owner $owner is gone) - safe to break"
    fi
fi
$ bash /tmp/lock2.sh &
acquired by 1862
$ bash /tmp/lock2.sh           # 持有者还活着的时候
lock held by live pid 1862

$ kill -9 1862
$ bash /tmp/lock2.sh           # 持有者消失之后
STALE lock (owner 1862 is gone) - safe to break

kill -0不发送信号，只确认那个进程是否存在。不过这个判断有漏洞。

  • PID会被复用。死掉的持有者编号被另一个完全无关的进程接手，就会误判成还活着
  • 多台服务器共用共享卷上的同一把锁时，PID检查毫无意义，必须连主机名一起记录
  • 自动打破孤儿锁的逻辑本身会制造竞态。两次运行可能同时判定为「已陈旧」
  • 安全的折中是不自动打破，只告警然后退出，让人确认后再删
  • 持有者信息里连启动时刻一起留下，陈旧判定会安全得多

13. 那到底该用哪一种

把各种清理方式能抓住什么、会漏掉什么整理一下。

模式正常结束exit 1 · 报错INT · TERMKILL可移植性
最后一行rm已清理留残骸留残骸留残骸所有shell
trap ... EXIT已清理已清理只有bash会清理留残骸dash上对信号很脆弱
trap ... EXIT INT TERM HUP已清理已清理已清理留残骸bash与dash均已验证
上面 + 重发信号与重入护栏已清理已清理已清理 · 保住退出码留残骸bash为准，第8节模板
固定前缀 + 外部清扫任务———事后清理唯一能覆盖KILL的办法

最后一行很重要。光靠trap覆盖不了所有情况。第三行是脚本内部能做到的上限，再往上就得靠脚本外面的机制。两者一起放，才是真正的答案。

13.1 最小检查清单

  • 清理代码抽成函数，用trap cleanup EXIT注册。引号问题随之消失
  • 在EXIT旁边列出INT TERM HUP。bash上看着多余，dash上却是必需
  • 信号处理函数清理完用trap - SIG解除，再用同一个信号把自己打死
  • 清理函数第一行是: "${var:?}"，第二行是case路径检查
  • 变量先声明成空值，挂好陷阱之后再调用mktemp
  • 加上重入标志和trap '' INT TERM HUP
  • 处理函数里不要调用exit 0。保住原来的退出码
  • 临时路径加固定前缀，另设一个回收陈旧残骸的任务
  • 有后台子进程的话，删目录之前先把它们杀掉
  • 长等待改成& wait，确保响应速度
  • 入口脚本以exec结尾的话，记住它前面的陷阱不会执行
  • 用部署目标的shell实际跑一次。做出本文这些表格只花了几分钟

14. 没能验证的部分

本文中没能通过实际执行验证的项目集中列在这里。

  • 在真实终端按下的Ctrl+C。所有验证都是非交互脚本给自己或子进程发信号的方式做的。终端把SIGINT撒向整个进程组、也就是shell和子进程同时收到信号的情形没有复现。那种条件下处理函数的执行顺序有可能不同
  • Linux glibc环境。本文的运行环境是面向x86_64-pc-msys的bash 5.2.37以及同环境的dash。信号投递层未必和Linux完全一致。尤其第3节的SIGQUIT忽略行为和退出码，最好在部署目标上复现一次
  • zsh、ksh和busybox ash。没有可运行的环境，未能确认。这在最小容器镜像里是常见组合，对实际工作而言是个重要的空白
  • 基于flock的加锁。此环境没有安装flock，所以第12节只用mkdir方式验证。文件描述符关闭时锁自动释放这一性质没能验证
  • 服务管理器和容器编排器的停止流程。宽限期过后升级为SIGKILL这一行为在第4节被当作对策的依据提到，但没有做出实际的服务定义来复现
  • 网络文件系统上的删除延迟。7.4提到把共享卷当临时空间的风险，但没有测量实际的延迟或部分删除
  • 大批量删除的耗时。第10节说要把清理保持得短，但没有按文件数量测量rm -rf的耗时
  • 旧版本的bash。trap -p和set -E在很老的版本上行为是否一致，没有确认

FAQ

Q1. 一行trap cleanup EXIT不够吗

只在bash上跑的话大体够了。实际执行确认，bash 5.2.37只挂EXIT也会在SIGINT、SIGTERM、SIGHUP上执行处理函数。问题出在同一个脚本用dash跑的时候：SIGTERM下处理函数没执行，临时文件原样留下。shebang是#!/bin/sh就可能在部署环境里由dash执行，而开发机上/bin/sh指向bash的话这个差别根本看不见。把信号明确列出来的成本只有一行，那就老老实实列出来。

Q2. 清理处理函数用exit 0结尾不行吗

不行。确认过的结果是，处理函数里的exit 99把原来的退出码3覆盖成了99。处理函数不调用exit的话原值会原样保留。给清理处理函数加上exit 0，会让失败的运行和被中断的运行统统报告成成功。CI运行器靠这个码决定要不要重试，上层脚本靠这个码决定要不要进入下一步。清理做得再好却把退出码搞坏，前面的收益就全没了。

Q3. 陷阱处理函数里出错的话，剩下的清理会怎样

默认状态下会继续往下走。在处理函数中间塞一个false，后面的行照样全部执行，退出码也没变。不过在清理函数内部开set -e，就会在第一次失败处停住。实际确认时只打印了第一步，第二步没有执行，退出码变成了1。清理是即使失败也要试到底的代码，所以里面不要开set -e。删除命令用目标不存在也算成功的选项，需要吸收失败的位置加上|| true。

Q4. 每个函数各自把清理挂到EXIT上为什么会有问题

因为对同一个信号的陷阱不累加而是覆盖。函数A挂了，函数B再挂，就只剩B。而且EXIT陷阱是整个shell的状态，出了函数还会一直留着，不是函数局部的。绕开的办法是把清理项压进数组，EXIT上只挂一个按逆序遍历该数组的函数。逆注册顺序在资源释放顺序上也是对的：先拿锁后建目录的话，就先删目录、最后解锁。

Q5. 在子shell里创建的临时文件该怎么清

需要在那个子shell内部单独挂陷阱。实际执行确认的结果是，子shell会以清单形式继承父进程的EXIT陷阱，但自己终止时并不执行它，只在父进程里跑一次。反过来，在子shell内部注册的陷阱会在子shell结束时于其中执行，不会留在父进程里。在管道组成部分内部挂的陷阱也一样。所以挂了陷阱却好像不触发时，先确认那一行是不是在管道右侧或者括号里面就行了。

结语：今天就改的三件事

第一，把清理代码从最后一行搬到陷阱里。然后在EXIT旁边列出INT TERM HUP。在bash上看着可有可无，在dash上就会垮掉。信号处理函数清理完之后解除自己的陷阱，再用同一个信号把自己打死，以保住退出码。

第二，在清理函数第一行放上: "${var:?}"和路径检查。陷阱可以在脚本任何位置触发，变量还没赋值就收到信号的情况是真实存在的。在那种状态下执行删除，谁也不知道会删掉什么，而删掉的东西不会回来。所以这两行要写在删除那一行前面。改了逻辑之后，把删除换成echo跑一遍，用眼睛确认目标路径。

第三，不要相信trap能覆盖所有情况。kill -9抓不住，实测下320KB的工作目录整个留了下来。因为bash不会把trap ... KILL当语法错误拒掉，甚至还列在清单里，只看代码就会以为已经堵上了。给临时路径加固定前缀，再设一个回收陈旧残骸的独立任务，是填上这个脚本内部永远解决不了的窟窿的唯一办法。

最后一点。本文的表格和输出全都是用十行上下的脚本得到的。想知道清理会不会执行，别猜，用mktemp建一个文件然后把进程杀掉试试就行。三十秒就完事了。
