이 글의 코드와 출력은 Windows 10의 Git Bash(bash 5.2.37)·Windows PowerShell 5.1(5.1.19041.6456, CLR 4.0.30319)·Node.js v22.16.0·Python 3.13.3에서 얻은 값이고 출력은 그대로 옮겼다. 난수 표본은 모두 고정 시드라 같은 코드를 다시 실행하면 같은 출력이 나온다. 로캘에 따라 달라지는 값은 이 PC 설정(ko-KR)의 것이다. 항목마다 「코드 → 실제 출력 → 이유」 순서이며, 이유에서 공식 문서를 옮긴 곳은 문서의 문장임을 밝힌다. 64비트 정수 ID의 끝자리가 바뀌는 문제는 JSON 숫자 정밀도 글이 다루므로 여기서는 소수 쪽 자릿수만 본다.

서론 - 같은 수가 아니게 되는 두 방향

double은 메모리에서 64비트이지만 파일·로그·JSON·CSV 안에서는 글자이다. 값을 글자로 쓰는 순간과 글자를 다시 읽는 순간 사이에서 몇 자리를 쓰느냐가 값의 동일성을 정한다. 이때 「왕복」은 방향이 둘이고 보장하는 자릿수가 다르다.

  • 글자 → double → 글자: 사람이 쓴 십진 문자열이 그대로 복원되는가. 보장 자릿수는 15이다.
  • double → 글자 → double: 계산으로 얻은 값이 같은 비트로 복원되는가. 필요한 자릿수는 17이다.
  • 두 방향을 섞어 「15자리까지 안전하다」라고 말하면, 계산 결과를 15자리로 저장하는 코드가 조용히 값을 바꾼다.

다루는 질문은 다음과 같다.

  • 6·9·15·16·17자리로 쓴 글자를 다시 읽으면 몇 개가 다른 비트가 되는가.
  • Python의 repr와 JavaScript의 toString이 고르는 「최단 왕복 표기」는 무엇을 보장하는가.
  • 17자리가 필요한 값은 어떤 모습인가.
  • Python·Node·PowerShell 5.1·awk·SQLite가 설정 없이 출력하는 자릿수는 몇 자리인가.
  • 도구 사이에서 값이 달라지는 사례는 쓰는 쪽과 읽는 쪽 중 어디서 생기는가.

JSON 숫자 정밀도 글의 8절은 15·16·17자리 실패 개수를 20만 개 표본으로 센다. 여기서는 그 표를 반복하지 않고 비트 패턴·산술 결과·15자리 이하 입력이라는 표본 세 종류의 대비, float32의 6·9자리, 도구의 기본 출력 자릿수, 도구 사이 교환의 변인 분리를 다룬다.

비트로 본 0.1과 0.1+0.2

Python 공식 튜토리얼의 부동소수점 문서는 IEEE 754 binary64 값이 53비트의 정밀도를 가지며 0.1은 3602879701896397 / 2 ** 55로 근사된다고 적는다. 같은 문서는 0.1, 0.10000000000000001, 0.1000000000000000055511151231257827021181583404541015625가 모두 같은 근사값을 가리키므로 어느 것을 표시해도 eval(repr(x)) == x가 유지된다고 설명한다. 이 설명을 비트와 16진 표기로 확인한 코드이다.

import struct, math
                    from decimal import Decimal
                    def bits(x): return '%016X' % struct.unpack('<Q', struct.pack('<d', x))[0]
                    for label, x in (('0.1', 0.1), ('0.3', 0.3), ('0.1+0.2', 0.1 + 0.2)):
                        print('%-8s bits=%s  hex=%s  repr=%s' % (label, bits(x), x.hex(), repr(x)))
                    print('Decimal(0.1)   =', Decimal(0.1))
                    print('Decimal(0.1+0.2) =', Decimal(0.1 + 0.2))

                    print('%.15g text     =', t, '-> back bits', bits(float(t)), '| same value?', float(t) == s)

출력에서 읽을 수 있는 것은 다음과 같다.

  • 0.1+0.2의 비트는 3FD3333333333334이고 0.3의 비트는 3FD3333333333333이다. 마지막 비트 하나가 다르며 두 값은 서로 다른 double이다.
  • 0.1+0.2를 %.15g로 쓰면 글자는 0.3이고, 이 글자를 다시 읽으면 0.3의 비트(...333)로 돌아가 원래 값과 같지 않다.
  • %.17g로 쓰면 0.30000000000000004이고 다시 읽으면 원래 비트(...334)로 돌아간다.
  • 0.3 주변의 이웃 double은 0.29999999999999993, 0.3, 0.30000000000000004이다. 17자리는 이웃과 구분하는 데 필요한 자릿수이다.
  • 0.1을 17자리로 쓰면 0.10000000000000001이고 repr는 0.1이다. 두 글자는 같은 double로 돌아간다.

6·9·15·16·17자리 왕복표 - 표본 세 종류

아래 코드는 표본 세 종류를 만들어 %.N g로 쓴 글자를 다시 float로 읽고 64비트를 전부 비교한다. A는 무작위 64비트 패턴 중 유한한 값(지수 범위 전체), B는 일반 범위의 산술 결과(곱셈과 나눗셈), C는 유효숫자 1~15자리로 입력한 십진 글자에서 만든 값이다. 같은 방식으로 float32도 센다.

import random, struct, math, sys
                    def bits(x): return struct.unpack('<Q', struct.pack('<d', x))[0]
                    def f32(x): return struct.unpack('<f', struct.pack('<f', x))[0]
                    def f32bits(x): return struct.unpack('<I', struct.pack('<f', x))[0]
                    print(sys.version.split()[0], 'float_info.dig =', sys.float_info.dig, ' mant_dig =', sys.float_info.mant_dig)
                    rnd = random.Random(20261006)
                    N = 100000
                    A = []
                    while len(A) < N:
                        x = struct.unpack('<d', struct.pack('<Q', rnd.getrandbits(64)))[0]
                        if math.isfinite(x): A.append(x)
                    B = [rnd.uniform(-1000, 1000) * rnd.uniform(0.001, 1000) / rnd.uniform(1, 97) for _ in range(N)]
                    C = [float('%.*g' % (rnd.randint(1, 15), rnd.uniform(-1e6, 1e6))) for _ in range(N)]
                    def fails(S, n):
                        return sum(1 for x in S if bits(float('%.*g' % (n, x))) != bits(x))
                    print('double, %d values per set; text = %%.Ng, then float(text), compare all 64 bits' % N)
                    print('%-4s %10s %10s %10s' % ('N', 'A:bitpat', 'B:arith', 'C:<=15dig'))
                    for n in (6, 9, 15, 16, 17):
                        print('%-4d %10d %10d %10d' % (n, fails(A, n), fails(B, n), fails(C, n)))
                    F = [f32(rnd.uniform(-1000, 1000) * rnd.uniform(0.001, 1000)) for _ in range(N)]
                    def f32fails(n):
                        return sum(1 for x in F if f32bits(f32(float('%.*g' % (n, x)))) != f32bits(x))
                    print('float32, %d values; text = %%.Ng, then back to float32' % N)
                    for n in (6, 7, 8, 9):
                        print('N=%d  failures=%d' % (n, f32fails(n)))

표를 읽는 규칙은 다음과 같다.

  • A와 B에서 17자리는 실패가 0건이다. 15자리는 약 94%, 16자리는 약 42~45%가 다른 비트로 돌아왔다. double을 글자로 쓰는 쪽에서는 15자리가 안전선이 아니다.
  • C에서는 15·16·17자리 모두 0건이다. Python 문서의 sys.float_info.dig 설명, 곧 유효숫자 15자리 이하의 십진 문자열은 float로 바꿨다가 다시 쓰면 같은 십진값이 복원된다는 문장과 일치한다. 같은 문서는 16자리 문자열 9876543211234567이 .16g로 되돌리면 9876543211234568로 바뀌는 예를 든다.
  • C의 6자리와 9자리 실패(59411, 39308)는 입력 글자가 최대 15자리였기 때문에 6·9자리로 줄이는 순간 값이 바뀐 것이다. 줄이는 쪽의 자릿수가 원래 글자보다 짧으면 어느 방향에서도 복원되지 않는다.
  • float32는 9자리에서 0건이고 8자리에서 1568건이 실패한다. Microsoft Learn은 표준 숫자 서식 문서에서 Double은 G17, Single은 G9을 쓰라고 적으며 이 표와 일치한다.
  • 표본 실패 0건은 모든 double에 대한 증명이 아니다. 17자리가 필요하다는 근거는 이 표본과 Microsoft Learn의 권고가 같은 방향을 가리킨다는 점이다.

최단 왕복 표기 - repr와 toString이 하는 일

매번 17자리를 쓰면 0.1이 0.10000000000000001이 되어 읽기 불편하다. Python 문서는 3.1부터 repr가 후보 중 가장 짧은 문자열을 고른다고 적고, sys.float_repr_style 값이 short이면 float(repr(x)) == x가 성립한다고 설명한다. ECMAScript 사양의 Number::toString은 s와 n과 k를 정할 때 k를 가능한 한 작게 잡는다고 규정하고, MDN은 toString이 이웃 값과 구별하는 데 필요한 가장 적은 유효숫자를 쓴다고 적는다. 이 「최단」이 값마다 몇 자리가 되는지 센 코드이다.

import random, collections
                    rnd = random.Random(20261006)
                    def need(x):
                        for n in range(1, 18):
                            if float('%.*g' % (n, x)) == x: return n
                    B = [rnd.uniform(-1000, 1000) * rnd.uniform(0.001, 1000) / rnd.uniform(1, 97) for _ in range(100000)]
                    h = collections.Counter(need(x) for x in B)
                    print('smallest N with float(%.Ng) == x, 100000 arithmetic values:')
                    for n in sorted(h): print('  N=%2d  %6d' % (n, h[n]))
                    print('examples (digits needed, repr):')
                    for x in (0.1, 0.1 + 0.2, 0.1 * 3, 1.1 * 1.1, 0.1 + 0.7, 1 / 3, 2 / 3, 100 * 1.1, 1e23, 5e-324):
                        print('  %2d  %s' % (need(x), repr(x)))

  • 17자리가 필요한 예는 0.30000000000000004, 1.2100000000000002, 110.00000000000001이다. 16자리가 필요한 예는 0.7999999999999999와 0.3333333333333333이다.
  • 0.1, 1e+23, 5e-324는 1자리만으로 같은 값이 돌아온다. 최단 표기는 자릿수가 값마다 달라지는 가변 길이이다.

  • Microsoft Learn의 표준 숫자 서식 문서는 G 서식의 기본 자릿수를 Double에 대해 「가장 짧은 왕복 가능 자릿수(.NET Framework에서는 G15가 기본)」라고 적는다. PowerShell 5.1의 15자리 출력은 이 문장과 같은 값이다. 이 PC의 5.1은 .NET Framework 위에서 돈다.
  • 같은 문서의 「R」 항목은 Double에는 G17을 쓰라고 권고한다. ToString("R")이 쓴 17자리 출력은 이 권고와 같은 자릿수이다.
  • Python %g, awk print, SQLite CAST AS TEXT는 모두 사람이 읽는 값을 위한 짧은 출력이며 복원용이 아니다. awk의 printf %.17g는 같은 값을 17자리로 쓴다.
  • Node toLocaleString은 이 PC의 로캘에서 소수 3자리까지만 썼다. 숫자 서식 함수는 값을 보존하는 직렬화 경로가 아니다.

실행에서 얻은 결과를 쓰는 목적별로 정리하면 다음과 같다.

목적쓰는 방식앞 절에서 본 근거
사람이 읽는 표시, 복원 불필요%g·G15·toLocaleString 같은 짧은 서식5절의 출력. 값을 일부 버린다
복원해야 하는 double(JSON·로그·CSV)최단 왕복(repr·JSON.stringify) 또는 유효숫자 17자리(%.17g·G17)3절 17자리 0건, 6절 표
float32유효숫자 9자리(G9)3절 9자리 0건, Microsoft Learn 권고
PowerShell 5.1에서 CSV로 내보낼 doubleToString("G17", InvariantCulture)6절 G17 0건, ToString() 기본값 1870건
PowerShell 5.1에서 JSON 숫자를 double로 받기값을 문자열로 바꿔 [double]::Parse(InvariantCulture)7절 형 변환 222건, Parse 0건
도구 사이 값이 달라졌는지 확인같은 파일을 두 도구로 읽어 비트(16진)를 비교6절 구성
  • 복원이 목적이면 「몇 자리로 쓸까」보다 「최단 왕복이거나 17자리인가」를 먼저 확인한다.
  • 15자리는 글자 → double → 글자 방향의 보장이므로, 사람이 입력한 값의 표시에는 맞고 계산 결과의 저장에는 맞지 않는다.
  • 쓰는 도구의 기본 자릿수는 도구와 출력 경로마다 다르다. 같은 PowerShell 5.1 안에서도 보간과 ConvertTo-Json이 다르다.
  • 값의 비교에는 글자가 아니라 비트를 쓴다. Python은 struct, Node는 DataView, PowerShell은 BitConverter로 64비트를 꺼낼 수 있다.
  • 정수에 가까운 큰 값과 64비트 ID의 문제는 여기서 다루는 소수 자릿수와 별개이며, JSON 숫자 정밀도 글에서 다룬다.

확인하지 못한 것

  • PowerShell 7과 최신 .NET. 이 PC에는 pwsh가 없다. Microsoft Learn은 Double의 G 기본 자릿수를 「가장 짧은 왕복 가능 자릿수」로 적고 .NET Framework만 G15라고 구분하지만 실행으로 비교하지 못했다.
  • Java·Go·Rust·C 등 다른 언어와 Node 이외의 JavaScript 엔진의 기본 출력 자릿수.
  • 17자리가 모든 double에서 복원된다는 전수 증명. 표본은 세 종류 각 10만 개이다.
  • ConvertTo-Json이 어떤 값에 15자리를, 어떤 값에 17자리를 쓰는지의 규칙. 반례 하나와 2000개 표본의 결과만 있다.
  • PowerShell 5.1의 Decimal 형 변환이 한 비트 어긋나는 원인과 double.Parse가 -6667.211341195974를 다르게 읽는 원인.
  • 무한대·NaN·음의 0·비정규 수(subnormal)의 왕복. 표본 A에 비정규 수가 포함되었는지는 세지 않았다.
  • ConvertTo-Json에 객체나 배열을 넘길 때의 자릿수. 스칼라 double만 넘겼다.
  • Linux·macOS에서의 동작과 쉼표를 소수점으로 쓰는 로캘. PowerShell 코드는 InvariantCulture로 고정했다.
  • SQLite printf에서 %.17g가 17자리로 나오지 않은 현상. 실행에서 0.3으로 나왔으나 원인은 조사하지 않았다.
