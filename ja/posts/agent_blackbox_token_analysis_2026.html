Agent-Blackbox — Claude CodeとOpenCodeをセッションマップとトークン無駄遣いで分析する

AIコーディングエージェントのブラックボックスを開く — セッションフロー・トークン消費・浪費ポイントを可視化し、なぜエージェントオブザーバビリティが重要なのかを分析する

2026-06-23 開発・インフラ

序論：エージェントは何をしているのか

Claude CodeやOpenCodeに複雑なタスクを任せて10分後、画面にはツール呼び出しのログがスクロールし、API使用量ダッシュボードの数値は急上昇している。問題はなぜそこまで多く消費されているのかがわからないことだ。どのステップで不要なファイル読み込みが繰り返されたのか、サブエージェントが上位エージェントがすでに処理した情報を再計算していないか——セッションが終わると何の痕跡も残らない。エージェントは依然としてブラックボックスだ。

Agent-Blackboxはこの問題に正面から向き合うツールだ。2026年6月にGeekNewsで38ポイントを獲得して紹介されたこのツールは、Claude CodeとOpenCodeの実行セッションをセッションマップとして可視化し、各ステップのトークン消費量と浪費ポイントを分析する。単なる使用量追跡ではなく、エージェントオブザーバビリティ（観測性）の概念をAIコーディングエージェント領域に持ち込むことが核心だ。

本稿はAgent-Blackboxの発想を起点に、AIコーディングエージェントでトークン浪費がどのように構造的に発生するか、セッションマップがデバッグにどのような価値をもたらすか、そしてエージェントオブザーバビリティという概念が2026年のインフラ実務においてなぜ無視できない課題になったかを独自の視点から分析する。2026年6月基準でこのツールはまだ初期段階だ。方向性は正しいが、ツール自体よりもそれが提起する問いのほうが重要だ。

1. エージェントブラックボックス問題 — なぜ今なのか

従来のソフトウェアデバッグは決定論的だ。同じ入力には同じ出力が返り、ログを逆追跡すれば問題箇所を見つけられる。AIエージェントはこの前提を崩す。温度（temperature）ゼロでさえ非決定論が残り、一つのエージェント実行が数十のツール呼び出しとサブエージェント生成につながり、各ステップで消費されたトークンのコンテキストと理由は出力ファイルのどこにも記録されない。

2026年にこの問題がより深刻になった理由がある。AIコーディングエージェントが開発ワークフローの中心に入り込み、エージェント1セッションのコストがドル単位を超えることが日常化した。Claude Opus 4.x系は同じエージェント構成で以前のバージョン比1.5倍近くトークンを消費するというコミュニティレポートがすでに出ている。あるCIパイプラインでは4時間のエージェントセッションで180以上のツール呼び出しが発生し、数十ドルのトークンコストが生じた事例も報告されている。このコストがどこから来たのかわからなければ、削減する方法もない。

Agent-Blackboxの問題定義はここにある。「エージェントが何をしたかわからなければ、なぜそこまで消費したかもわからない。」セッション終了後に残るのは合計トークン数とコスト数字だけだ。どのツール呼び出しが全コストの40%を占めたか、どのファイル読み込みが不要に繰り返されたか、サブエージェントが重複したコンテキストはどこかは、すべてブラックボックスの中にある。

2. セッションマップとは何か — エージェント実行の解剖

Agent-Blackboxが提示する核心概念はセッションマップ（session map）だ。これはエージェント実行をタイムラインまたはツリー構造で表現したものだ。各ノードは一つのツール呼び出し（ファイル読み込み、Bash実行、検索、サブエージェント生成など）を表し、ノード間のエッジは呼び出し順序と因果関係を示す。各ノードには消費された入力トークン・出力トークン・キャッシュヒット状況・遅延時間が付与される。

この構造があれば、いくつかの即座の診断が可能になる。

  • 繰り返し読み込み検出：同じファイルパスがセッションマップに3回以上現れるなら、エージェントがすでに読んだ内容をコンテキストから失って再要求しているということだ。コンテキスト圧縮戦略やキャッシュ設定の見直しが必要なシグナルだ。
  • トークン集中区間の把握：全トークンの60%がわずか2つのノードから生じているなら、そのツール呼び出しが過大な出力を生成しているということだ。ファイル読み込み出力制限（CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS）やBash出力制限（BASH_MAX_OUTPUT_LENGTH）の調整根拠になる。
  • サブエージェント重複の検出：2つのサブエージェントが同様のファイルセットをそれぞれ読み込んでいるなら、オーケストレーション設計に問題がある。一方のエージェントの結果を他方に渡すコンテキスト共有構造に変えれば重複コストを削除できる。
  • 不要なMCP呼び出しの特定：MCPサーバーに登録されたツール定義だけでシステムプロンプトに数千トークンが付く。セッションマップで実際に呼び出されたMCPツールと一度も呼び出されなかったツールを区別すれば、使用していないMCPを削除して固定コストを削減するデータが得られる。

Claude Codeの場合、PreToolUseとPostToolUseフックがあり、外部ツールがこのイベントをインターセプトしてログを積み上げることができる。Agent-Blackboxはこのフックイベントストリームを読み込んでセッションマップを構築する。OpenCodeはオープンソース構造なのでセッションファイル自体を直接パースして分析が可能だ。2つのエージェントを統合されたビューで比較できる点がこのツールの差別化ポイントだ。

3. トークン浪費の構造 — どこから漏れるか

セッションマップを見る前に、エージェントトークン浪費の構造的原因を理解しておく必要がある。2026年6月現在、実務で観察される浪費パターンは大きく4つに分類される。

3.1 固定オーバーヘッド：システムプロンプトとツール定義

エージェントは毎ターン、システムプロンプトと登録されたツール定義全体をコンテキストとして含める。Claude Codeのビルトインツールだけで約20個あり、MCPサーバーを10個接続するとツール定義トークンだけで数千が追加される。このコストはタスクに関係なく毎ターン支払われる。使用していないMCPサーバーを接続したままエージェントを動かすと、ツール定義の固定オーバーヘッドが全コストの20〜30%を占めることがある。

3.2 会話履歴の蓄積

エージェントは長いタスクになるほど、過去の会話履歴をコンテキストにどんどん多く持ち込む。ファイル読み込み結果・Bash出力・過去のアシスタント応答がすべて履歴に積み上がる。短いエージェントループを100回回すと、100回目のターンの入力トークンは1回目より指数関数的に多くなる。コンテキスト圧縮が機能しなかったりキャッシュ読み込みが失敗したりすると、コストが爆発的に増加する。あるコミュニティ事例では、キャッシュ書き込みは成功したが読み込みに失敗し、毎会話で67,374トークンを最初から再処理した件が報告されている。

3.3 不要な外部接続

IDE自動接続（autoConnectIde）、Web検索、グローバルドキュメントの自動ロードが有効な状態でエージェントを動かすと、実際の作業とは無関係な接続コストが毎セッション追加される。OpenCodeでWeb検索を無効化（web_search = disabled）しMCPアプリを無効化（features.apps = false）するだけで、単純なコーディングタスクではセッションごとのトークンが明らかに減少するという実測結果がコミュニティで共有されている。

3.4 サブエージェントの重複コンテキスト

マルチエージェント構成で、オーケストレーターが同じファイルや情報を複数のサブエージェントにそれぞれ渡す場合、重複コンテキストコストが発生する。これはエージェント自体の問題ではなく設計の問題だが、セッションマップなしにはこの重複が発生しているかどうかさえわからない。Agent-Blackboxが狙う核心的な価値がまさにこの点にある。

4. エージェントオブザーバビリティという概念 — なぜ2026年に本格化するのか

エージェントオブザーバビリティ（agent observability）とは、AIエージェントの実行を構造化されたトレースとして捉え、各ステップをモニタリング・評価・デバッグできるようにする実践だ。従来のAPM（アプリケーション性能監視）がAIエージェント領域に拡張された概念で、2026年に入り独自のカテゴリとして確立し始めた。

なぜ今なのか。2つの構造的変化が重なった。第一に、エージェントが単発呼び出しから数十ステップの自律実行として使われ始めた。シンプルなチャットボットはログ1行で十分だが、4時間のエージェントセッションは180個のツール呼び出しがどうつながったかを追跡する手段がなければ失敗原因を見つけられない。第二に、コストが無視できない水準になった。エージェントコーディングが実際の開発ワークフローに入り込み、月数百ドルのエージェントAPIコストが日常化し、そのコストのどの部分が無駄なのかを知りたいという需要が生まれた。

エージェントオブザーバビリティの4つの軸は以下の通りだ。

  • 実行トレース：ツール呼び出し・サブエージェント生成・モデル応答を時系列と因果関係で記録
  • トークン・コスト帰属：どのステップでどれだけ使ったかのステップ別内訳
  • 出力評価：各ステップの成果物が期待に沿っているかの定量評価
  • エージェント身元追跡：マルチエージェント環境でどのエージェントがどの作業を担当したかの帰属

Agent-Blackboxはこのうち実行トレースとトークン・コスト帰属に集中するツールだ。Claude Code・OpenCode特化のアプローチがLangfuseやArize Phoenixのような汎用観測プラットフォームと異なる点がここにある。コーディングエージェントのセッションファイル形式とフックイベントを直接処理する軽量ローカルファーストツールという位置づけがより実用的に感じられる理由もここにある。

5. Claude Code vs OpenCode — オブザーバビリティの視点

Agent-Blackboxが2つのエージェントを同時にサポートするのは、両エージェントの観測性アプローチが構造的に異なるため興味深い。

5.1 Claude Codeの観測性構造

Claude Codeには公式フックシステムが内蔵されている。PreToolUse・PostToolUse・Stopなどのフックポイントがあり、外部ツールが設定ファイル（~/.claude/settings.json）にフックコマンドを登録すれば、すべてのツール呼び出しイベントをインターセプトして処理できる。この構造は観測ツール側にとって便利だ。エージェントコードを修正したりプロキシを挟む必要なく、公式拡張ポイントだけを使えばよい。欠点はフックイベントがツール呼び出しレベルの情報を提供するだけで、内部推論プロセス（extended thinking）のトークン使用量や中間の意思決定コンテキストは露出しないことだ。

5.2 OpenCodeの観測性構造

OpenCodeはオープンソースなのでセッションファイル形式自体をパースして分析できる。ソースを開けばエージェントの内部構造をより深く理解でき、カスタム計測を直接挿入することも可能だ。一方で公式フックAPIがないため、OpenCodeのバージョンアップに伴いパーサーが壊れるリスクがある。ツールが特定の形式に依存するという脆弱性だ。

5.3 両エージェントの共通ブラックボックス領域

両エージェントとも内部推論トークン（thinking tokens）は完全には公開していない。Claude Codeのextended thinkingモードでモデルが内部的にどれだけ長く推論したか、その推論トークンが全コストの何%を占めたかは、現在の観測ツールでは把握が難しい。これはAgent-Blackboxを含む現世代の観測ツール全体の共通の限界だ。エージェント実行をブラックボックスから取り出す作業はまだ半分しか完了していない。

6. 実務への応用 — どう使うか

2026年6月基準で、エージェントオブザーバビリティツールを実務に導入する際の優先順位を以下に示す。

6.1 ローカルファーストツールから始める

セッションログにはプロンプト原文とコード内容が含まれる。これを外部サーバーに送信するSaaS観測プラットフォームを使うと、データセキュリティポリシーと衝突する可能性がある。Agent-Blackbox・AgentProf・CodeBurn・ccusageのようなローカルファーストツールは分析が自分のマシン内で完結する。導入の第一歩はローカルファーストツールでセッションデータを収集し、どのパターンが頻繁に現れるかをまず把握することだ。

6.2 固定オーバーヘッドを先に削減する

セッションマップ分析の前にも今すぐできる最適化がある。Claude Code基準ではincludeGitInstructions: false（Git指示文の削除）、autoConnectIde: false（IDE自動接続の無効化）、使用していないMCPサーバーの無効化だけで、ターンごとの固定オーバーヘッドをすぐに削減できる。OpenCodeではfeatures.apps = falseとWeb検索無効化が同様の効果をもたらす。これらの設定はセッションマップ分析なしでも確認された削減方法だ。

6.3 セッションマップでパターンを見つける

Agent-Blackboxのようなセッションマップツールは、単発コスト追跡よりパターン発見に価値がある。同様の作業を10回実行してセッションマップを並べると、毎セッション繰り返される高コストパターンが見える。「このエージェントは常にXファイルを3回読み込む」「Yツール呼び出しの直後に同一検索が繰り返される」といったパターンが発見されれば、それがプロンプト修正やツール設定調整の具体的な根拠になる。

6.4 マルチエージェント構成では特に注意する

単一エージェントよりマルチエージェントオーケストレーションでオブザーバビリティの価値がはるかに大きい。2つのサブエージェントが独立して動いているとき、どちらのサブエージェントがコストの何%を占めているか、両エージェント間にコンテキストの重複があるかは、セッションマップなしには見えない。Claude Codeのサブエージェント機能やOpenCodeの並列エージェント構成を使っているなら、セッションマップはほぼ必須だ。

7. オブザーバビリティツールエコシステム — 2026年6月の状況

Agent-Blackboxだけがこの空間の唯一のツールではない。2026年6月現在、同様の目的を持つツールが同時多発的に登場した。このエコシステムを整理するとエージェントオブザーバビリティの地形が見えてくる。

8. 限界と冷静な評価

メリットだけを列挙するのは分析ではない。Agent-Blackboxと現世代エージェントオブザーバビリティツール全般の限界を指摘しなければならない。

内部推論領域の不透明性：前述の通り、Claude CodeのExtended thinkingトークンはフックイベントでは捉えられない。エージェントコストの相当部分を占めうる推論トークンがセッションマップから抜け落ちるなら、分析の完全性に穴がある。

観測オーバーヘッド：フックを追加したりイベントをログに記録すること自体が微小な遅延を生む。ほとんどの場合は無視できるレベルだが、遅延に敏感なワークフローでは観測ツールを常時オンにすることが負担になる可能性がある。

ログのセキュリティ：セッションログを保存するとプロンプト内容とコードスニペットがディスクに蓄積される。ローカルファーストツールでも、ログファイル自体のアクセス制御と保持ポリシーを明示的に設定する必要がある。

バージョン依存性：セッションファイル形式はエージェントのバージョンアップで変わることがある。ツールが特定の形式に依存していると、エージェント更新後にパーサーが壊れる。Agent-Blackboxの長期的な信頼性はこのメンテナンス問題をどれだけうまく対処するかにかかっている。

9. 結論 — ブラックボックスから取り出した問いのほうが重要だ

Agent-Blackboxが提起する問いはツール自体よりも重要だ。「エージェントが何をしたか把握しているか？」2026年6月現在、ほとんどのチームがこの質問に「よくわからない」と答えるだろう。コスト数字は見えているが、その数字がどこから来たかは見えていない。

エージェントオブザーバビリティは選択肢ではなく、エージェントをプロダクションで使うチームが必ず備えるべきインフラレイヤーになりつつある。セッションマップで無駄を見つけ、固定オーバーヘッドを削減し、マルチエージェントの重複を除去するプロセスは、エージェント実行をより予測可能に、より低コストに、よりデバッグしやすいシステムにする作業だ。

Agent-Blackboxはこの方向に向かう初期ツールだ。今すぐ完成したソリューションではないが、アプローチは正しい。エージェント実行をブラックボックスのままにしておくコストは、観測ツールを導入するコストより速く増大している。
