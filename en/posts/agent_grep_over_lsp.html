When the Accurate Tool Goes Unused, the Problem Is Not the Tool - Measuring Why Coding Agents Reach for grep Instead of LSP

A tool with 1.00 precision called 0 percent of the time, and a return format change that moved success from 0.67 to 0.83

2026-09-07 Dev & Infra

Hand an agent a codebase and it almost always types grep first. It does this even when a language server is sitting right next to it, ready to return definitions and references with full type information behind them. Anyone watching this for the first time tends to blame the model. There is a better tool available, the reasoning goes, and the model fails to recognise it.

That accusation rests on a premise: that an accurate tool will naturally get used. There is now measured evidence of that premise failing. The path that reached 1.00 precision on reference finding was called 0 percent of the time on simple code-location work. Accuracy and adoption do not sit on the same axis.

The subject here is not whether grep or LSP is better. It is this: when the more accurate tool loses out, is the thing that needs fixing the tool or the interface? The measurements point at the interface, and more precisely at what the tool hands back. The same tool moved success from 0.67 to 0.83 on the strength of its response format alone.

Every figure below is taken from the source. But each one has its own denominator, and those denominators are small. The source calls the work a preliminary pilot and states that it ran two to three rollouts per cell. So this article names the task and the arm every time it quotes a number. Strip the denominator away and the same figure turns into an entirely different claim.

The trigger - an accurate tool that cannot get a foothold

Language servers are old technology. Jump to definition and find all references have been refined in editors for more than two decades, and their accuracy is not in the same conversation as text search. They distinguish a local variable from a global function that happens to share its name, follow import aliases, and treat a differently typed symbol as a stranger. grep does none of this.

Wiring a language server into a coding agent is therefore a natural move. Rather than having the model read whole files and burn tokens, let it query the symbol graph. That idea and its payoff were covered in a code graph MCP built on the TypeScript compiler. The question here comes after that one: once it is wired in, does the agent actually call it?

The measured answer is that call frequency splits sharply by task. And the thing producing that split turns out not to be a shortfall in the model's judgement but the shape of what the tool returns, a conclusion that several independent arms of the study converge on. Accuracy is a property of the tool. Adoption is a property of the interface. Conflate the two and you can polish a tool indefinitely without it ever being used.

What was measured - two to three rollouts per cell

The design is simple. Give the agent both a grep-style text search and a language-server-backed semantic search at the same time, then set it code navigation and editing tasks on real repositories. Count which of the two it calls on every invocation. Score success separately, per task.

Three repositories were used: remeda and hono on the TypeScript side, requests on the Python side. Three models were tested: Opus 4.8, Sonnet 4.6 and Haiku 4.5. On the semantic side the capabilities actually exercised were reference finding, definition finding and document symbol listing.

The scale is the part that matters most. The source calls this a preliminary pilot in its own words. Task sets are small, only a few repositories were involved, and two to three rollouts were run per cell, where a cell means one combination of repository, model and task type. Many of the percentages and decimals that follow are therefore sitting on single-digit trial counts.

What two to three rollouts per cell actually means

Percentages produced under these conditions cannot carry a confidence interval. Two successes out of three gives 67 percent, three out of three gives 100 percent, and there is nothing in between. What is worth extracting from a study like this is therefore not a precise figure but a direction and a structure: under which conditions adoption shifts wholesale, and which changes visibly move the outcome. That is the durable information.

0 percent and 45 percent - the model does not blindly prefer grep

The most widely quoted figure is 0 to 6 percent: with both tools in hand, the three models picked the semantic one only that often. But there is a condition attached to that figure, and quoting it without the condition inverts the fact.

The 0 to 6 percent belongs to a single row covering simple code-location tasks. Look at another row of the same table and the picture changes. On reference-completeness tasks the same three models chose the semantic tool 45 percent, 50 percent and 57 percent of the time. The heading over that table in the source says precisely this: that the model is not blindly preferring text search but routing by task.

Task typeOpus 4.8Sonnet 4.6Haiku 4.5What this row says
Localization0%4%6%When the job is only to learn where something is, text search takes almost the whole share
Reference-completeness45%50%57%When nothing may be missed, roughly half the calls move to the semantic path
Multi-file rename3%not reportednot reportedOnce editing enters the picture, the balance tips back toward text search

The column header is the share of semantic tool calls when both grep and LSP are available and the agent chooses freely. The denominator is every search-tool call made on that task, not the number of sessions and not the number of successes.

The differences between models must not be turned into a ranking. The gap between 0 and 6 on the localization row cannot be separated at two to three rollouts per cell, and the same holds for 45 against 57 on the reference row. The information is that all three values point the same way. Which one is a few points higher is not information.

This is where the angle shifts. The problem is not that the model fails to recognise the tool. The model is already routing by task. The problem is that the criterion behind that routing is not the accuracy of the tool. If accuracy were the criterion, semantic search would have been chosen for localization too, since filtering out same-named strangers is plainly more accurate there as well.

Forcing the good tool made things worse - 100 percent to 89 percent

Observing choices alone cannot establish cause. So a separate arm forced a semantic-first path. If the problem is that a good tool goes unused, then making it get used should improve the outcome.

It went the other way. Success in that arm fell from 100 percent to 89 percent. The agent was pushed toward the more accurate tool and completed fewer tasks.

Two readings follow. The first is the cost of compulsion itself: take away an agent's ability to switch paths according to circumstance and it will take a detour even where the direct route was working. The second, and the more important one, is that a tool being good does not by itself make the workflow around that tool good. Tool quality is one component of the result. What has to happen after the tool returns decides the rest.

The 89 percent figure itself needs careful handling, though. The source does not state how many trials that arm contained. Given the overall condition of two to three rollouts per cell, an eleven-point drop could be the work of one or two failures. The direction is worth trusting. The magnitude is not.

  • Forced routing is not an improvement to the tool. It is a withdrawal of the right to choose. Withdrawing that right removes the risk of choosing badly and the room to choose well at the same time
  • If you want a particular tool to be used without fail, look first at why it is not being used. The other half of this study points straight at the reason
  • Where selection accuracy breaks down as tool counts rise is a separate matter, covered in how many tools an agent can handle. This article looks at the shape of the response rather than the count

Precision 1.00 and recall 0.66 - what was actually accurate

On reference-completeness tasks the semantic path reached 1.00 precision. grep reached 0.76. On the numbers alone that is a rout. Yet in the same experiment recall stayed near 0.66 in both arms.

Precision and recall answer different questions

Precision is the share of what you returned that was genuine. Recall is the share of what should have been found that you actually found. Precision of 1.00 means the semantic search produced no false candidates. It does not mean it missed nothing.

That both arms sat near 0.66 recall is the heart of this section. Roughly a third of the references were caught by neither tool. Semantic search could not see what lay outside its jurisdiction, and text search either drowned the hits in noise or never matched the pattern. Before any argument about which is more accurate, the first fact is that neither tool solved the task completely.

  • A high-precision tool gives you the property that you can trust what it returns, which cuts the cost of downstream verification
  • Low recall means you cannot trust what it did not return. On this task, neither set of results can be treated as final
  • From an agent's point of view recall is the more painful of the two. A false candidate can be opened and discarded, but a reference that never appeared is not known to exist
  • In practice the union of both result sets beats either one alone: pin down the certain hits with the high-precision path, then sweep the remainder with text search

The repository changes the answer - no noise, no gain

The same tool produces completely different figures depending on the repository. This is the most directly actionable part of the study.

RepositoryLanguagegrep precisionF1 difference (semantic minus grep)Token cost change
remedaTypeScript1.00+0.000+16%
honoTypeScript0.51+0.246−12%
requestsPython0.76+0.072+19%

In remeda, text search alone already reaches 1.00 precision, because names in that codebase do not collide. Add semantic search there and F1 does not move while tokens rise 16 percent. That is pure loss.

hono is the opposite. Text search precision is 0.51, meaning half of what matches is spurious. Semantic search lifts F1 by 0.246 there and actually cuts tokens by 12 percent, because the waste of opening files to inspect false candidates disappears.

requests sits between the two: precision 0.76, an F1 gain of 0.072, tokens up 19 percent. There is a gain, but it is paid for in tokens.

The decision rule that falls out of this is compact. The value of semantic search is proportional to the name noise in that particular repository. Codebases that use common words as symbol names, that scatter the same identifier across modules, or that favour short function names stand to gain the most. A repository where names are unique and one search returns exactly the right answer only pays the cost.

  • This means the decision belongs at the repository level. It is not something to roll out uniformly across an organisation
  • The evidence needed is easy to gather. Run text search over a handful of frequently used symbol names and count the share of false hits. That share is the grep precision column of this table
  • Token cost does not always rise either. Where noise is severe, as in hono, the accurate tool saves tokens as well. There is a regime where accuracy and cost move in the same direction
  • The memory to keep a language server resident is a separate budget line, and its mechanics and trade-offs are laid out in why developer tools eat memory

Same tool, different response - format moved 0.67 to 0.83

This is the experiment the article turns on. The tool was not replaced. Only the response format of the tool changed: semantic navigation, which had been returning coordinates alone, was altered to carry the source text at those coordinates alongside them.

The three arms side by side

Armpass@1Site recallTokensFollow-up file reads per episode
grep1.001.0002,4514.3
Semantic search — locations only0.670.9304,13115.2
Semantic search plus inline context0.830.9583,3363.2

Same language server, same queries, same tasks. The only difference is whether source text rode along in the response. That single change lifted pass@1 from 0.67 to 0.83, dropped follow-up file reads from 15.2 to 3.2 per episode, and brought tokens down from 4,131 to 3,336. More was returned, and the total token count fell.

Something has to be stated honestly alongside that. In this table pass@1 of 1.00 belongs to the grep arm. The format improvement narrowed the gap without reversing the ranking. That 3.2 follow-up reads beats grep's 4.3 is meaningful, but on this task the final success rate still favours text search.

So what the experiment demonstrates is not that semantic search wins. It is that the performance of one and the same tool swings substantially on its return format alone. Evaluate a tool by looking only at the tool and this variable never enters the frame.

Why format weighs so heavily - the price of a round trip

The figure of 15.2 follow-up file reads explains the cause. An agent handed coordinates alone does not know what is at those coordinates. It has a file path, a line number and a column, and nothing to reason from. So it opens the file. Fifteen candidate sites means fifteen openings.

Every one of those round trips adds probability of failure. Context is pushed out while the file is being read, the earlier coordinate list gets truncated away, the ordering slips and it becomes unclear which candidates have already been inspected. One misstep among fifteen round trips and the episode is recorded as a failure. The failure did not come from the tool being inaccurate. It came from the number of round trips.

Ship the source alongside and those round trips vanish. The agent can read the response, judge which candidate is the site that actually needs changing, and move straight to editing. That is why the total token count fell even though the response itself grew: the tokens dragged in by fifteen file reads far exceeded the snippets appended to the response.

A design rule falls out of this. A tool response written for an agent must be able to produce the next action on its own. Tools written for people are exempt from this rule. When a person receives a reference list in an editor, one click puts the site in front of their eyes. Because that looking costs nothing, coordinates alone are sufficient. For an agent that click is a tool call, a token count and a failure point.

  • Porting a human interface unchanged walks straight into this trap. LSP is a specification designed for editors, and behind every editor there is a screen and a pair of eyes
  • The test is simple. Print the tool response as text and ask whether the next action can be decided from that alone. If a file has to be opened to know, the tool manufactures round trips
  • How much snippet to attach is a budget question. Attaching context to a query with hundreds of hits will blow out the window. A ceiling and a truncation flag have to be designed together
  • The model emits nothing but text, and the thing that actually runs tools and returns results is the harness. Where that boundary sits is set out in the model only emits text

Open the specification - coordinates yes, source no

Why did the coordinates-only implementation become the default shape? Because the specification is written that way.

The result type of a reference-finding request is an array of locations. That location type has exactly two fields: a document identifier and a range. The range is a start point and an end point, and each point is a line number and a character offset. Nowhere in that data structure is there room for what is actually written on that line.

What the specification definesWhat it carriesWhat it does not carry
Result of reference findingAn array of locationsThe source text at each location
LocationDocument identifier, rangeFile contents, surrounding context
RangeStart point, end pointThe string spanning that interval
PositionLine number, character offsetThe content of that line
Result of definition findingA location or an array of locationsThe body of the definition
Document symbol listingSymbol names and rangesThe source of the symbol bodies
Result of a rename requestA workspace edit bundleThe full file contents after editing

What the specification leaves open

The specification fixes the shape of the coordinates, but leaves what counts as a reference to the server implementation. The same request can therefore return different result sets depending on which language server is behind it. The recall figure of 0.66 from the previous section is not a theoretical ceiling of the technique but one value obtained within that implementation spread.

None of this is a fault in the specification. An editor client already holds the file open in memory, so given coordinates it pulls the text out of its own buffer and renders it. Shipping the source through the protocol would be duplication and wasted bandwidth. For a structure in which a human looks at a screen, this design is correct.

The trouble begins when the client is not an editor. An agent has no buffer. Reading a file again is a tool call and a token cost. A lookup that would have been free for an editor becomes an expensive round trip for an agent. The client the specification assumed and the client that actually turned up are different things. The specification is not wrong.

The right way to attach a language server to an agent, then, is not to forward the protocol response verbatim but to place a thin layer that fills that response out with file content in between. That layer is exactly what moved 0.67 to 0.83 in the measurements.

Different jurisdictions - when a rename is really a string edit

There is one place where text search wins structurally. In the source's own framing, it is when a rename also needs to update comments, docstrings, configuration and string literals. Semantic reference finding by design does not return those.

That is a definition, not a defect. Semantic search finds what the parser recognised as a symbol. A word inside a comment is not a symbol to the parser, nor is a word inside a string literal, and a key in a YAML configuration file was never within that language server's jurisdiction in the first place. Saying semantic search cannot find those things is the same statement as saying semantic search is accurate.

Site that needs changingSemantic searchText searchWhat happens in practice
Symbol references in codeCatches them, distinguishing same-named strangersCatches them with false hits mixed inCompare only here and semantic search comes out ahead
Mentions inside commentsCannot catch them, by designCatches themDocumentation is left pointing at the old name
DocstringsCannot catch them, by designCatches themGenerated API documentation keeps showing the old name
Log message stringsCannot catch them, by designCatches themProduction log search rules break silently
Keys in configuration filesOut of jurisdictionCatches themMismatches surface only after deployment
References from other languagesOut of jurisdictionCatches themFront end and back end drift apart

This table explains the 0.66 recall from earlier. Most of what semantic search misses comes from the lower four rows. And the fact that the real scope of a rename is usually wider than the top row is why text search held its ground on the editing tasks.

In practice this distinction is settled at the point the work is described. If the job is to change symbol references precisely, the semantic path is right. If the job is to change the name of a concept across an entire organisation, text search is indispensable. Handle the second with the tool for the first and you are left with code that compiles while documentation and logs no longer agree with it. That state passes the tests, which is why it surfaces much later.

The decimals leak the denominators

There is one more thing to notice when quoting figures from this study. The values that appear line up exactly with particular fractions.

  • 0.67 matches two thirds, or four sixths
  • 0.83 matches five sixths
  • 0.89 matches eight ninths
  • 1.00 is everything succeeding, so it holds for any denominator

This is inference, not something the source states. Other denominators can produce the same decimals. But laid alongside the source's own declaration of two to three rollouts per cell, the natural reading is that these values most likely rest on single-digit trial counts.

On that reading, the move from 0.67 to 0.83 could be four successes out of six becoming five out of six. A difference of one trial. The drop from 100 percent to 89 percent is likewise explained by one failure in nine.

None of which makes the study worthless, because other indicators that moved with it back the direction up. The fall in follow-up file reads from 15.2 to 3.2 is a continuous quantity, unlike a success rate, and a magnitude of that size is not manufactured by a single trial. The same goes for the token drop from 4,131 to 3,336. Pass@1 alone wobbles, but three indicators pointing the same way is hard to write off as coincidence.

The rule for quoting, then, is this. Carry conditions with every ratio, trust continuous quantities somewhat more, and build no rankings. That is why this article never arranges the percentages beside the model names into an order.

Where to start fixing the tools in your own agent

Carrying this study into your own environment means touching three places. The order matters.

Return format first

This is the cheapest place with the largest effect. If a tool returns only coordinates or identifiers, ship the content those coordinates point at in the response. For a search that means the matched line plus a line or two on either side; for a lookup, the key fields of the record retrieved; for a listing, enough of a summary to tell the entries apart.

// A response that manufactures round trips - no next action can be chosen
{
  "matches": [
    { "file": "src/cache/store.ts", "line": 142, "col": 8 },
    { "file": "src/cache/store.ts", "line": 207, "col": 15 },
    { "file": "test/store.spec.ts",  "line": 33,  "col": 4 }
  ]
}

// A response that produces the next action directly - the evidence is inside
{
  "matches": [
    {
      "file": "src/cache/store.ts", "line": 142, "col": 8,
      "kind": "definition",
      "text": "export function evictStale(now: number): number {",
      "context_before": "// drop entries past their expiry",
      "context_after": "  const cutoff = now - this.ttlMs;"
    }
  ],
  "truncated": false,
  "total": 3,
  "returned": 3
}

Not omitting truncated and total matters here. If a ceiling clipped the results and the response does not say so, the agent believes it received everything. That is the recall problem from the earlier section, manufactured artificially.

Descriptions second

The tool description is the only material a model has for deciding whether to call a tool at all. Yet most descriptions say only what the tool does and leave when it should be chosen blank. Since selection splits by task type, as this study's table showed, writing that split into the description is the direct move.

Tool description review - is each of these written as one line

1. Tasks this tool suits
   e.g. gathering every reference to a symbol with no same-named strangers
2. Tasks this tool does not suit
   e.g. when comments, strings and config must change too, use text search
3. What the response contains
   e.g. locations plus the source line and one line either side
4. What the response does not contain
   e.g. matches inside comments and string literals are not included
5. How truncation can be detected
   e.g. when truncated is true, compare total against returned

Item four especially. Write down what the tool cannot do and the model will decide for itself to move to a different tool for work outside that jurisdiction. That decision is exactly the task-based routing this study observed, and it worked better than compulsion did.

Forced routing comes last. It is last because the measurements do not support it. If adoption still refuses to move after the return format and the descriptions have been fixed, it becomes worth considering. It is not a lever to reach for at the outset.

What to log if you want to measure adoption

Knowing whether those changes helped requires measuring adoption. Yet most agent logs record only whether a tool succeeded and never whether it was chosen. Answering in your own environment the question this study answered takes a few more fields in the log.

  • Task type - localization, reference gathering, editing. Without this, 0 percent and 45 percent are mashed into one number. The biggest misreading of this study came from exactly that mashing
  • The tools that were available - what was in reach at that moment. A tool that was never attached must not be counted as a tool that went unused
  • File reads after the tool call - the round-trip indicator. It moves earlier than the success rate and gives a clear signal at low trial counts
  • Response tokens and session tokens - the cost of a larger response and the saving from fewer round trips have to be netted against each other. Look at response tokens alone and a format improvement looks like a loss
  • Whether truncation occurred - how often responses hit the ceiling. This is the artificial cause of recall decline
Fields to record on one line - adoption and round trips together

task_kind        localization | reference_gathering | editing | other
tools_available  [text_search, semantic_refs, read_file]
tool_called      semantic_refs
result_count     3
truncated        false
followup_reads   1        # how many files were opened after this call
tokens_response  412
tokens_session   3336
outcome          success | fail | abandoned

With these five lines you can draw the tables above for your own repository. followup_reads in particular is the first indicator to respond when the return format changes. Success rates need accumulated samples before they move, but round-trip counts show a difference across a handful of sessions.

Where these results do not reach

The source draws its own boundaries, and the right thing is to carry them over unaltered.

  • What was exercised on the semantic side was references, definitions and document symbols. Dedicated rename functionality was never tested. The source states directly that a configuration equipped with it might perform differently on precisely the refactoring tasks where text search did best. That is why the editing conclusions must not be widened into a verdict on LSP as a whole
  • Diagnostics and code actions are also outside the test. A path that locates edit sites from compiler errors does not appear in this study at all
  • The edit tasks were local, and the source states explicitly that these are not standard benchmark scores. The pass@1 values here cannot be laid alongside public leaderboard figures
  • There were three repositories and two of them are TypeScript. As the table in section six shows, repository character can invert the conclusion, so three of them cannot support a generalisation about languages
  • All three models come from one family. Whether models from other families route the same way lies outside what this study reaches

The recommendation the source closes on sits on the same boundary: evaluate the model and the harness together, preserve the interfaces that already support reliable behaviour, and test changes against real tasks before assuming that a more sophisticated abstraction will help. The crucial part is what is not to be assumed, namely sophistication itself. That a more sophisticated abstraction yields a better result is a proposition to be tested, not a premise.

The recommendation carries over to tool selection generally. Whether the apparently better option is actually adopted, and whether outcomes improve once it is, are two separate questions. How the same structure shows up in third-party service selection was covered in when an agent picks a vendor, which agent was it. That piece asks what gets chosen. This one asks why the accurate thing does not.

What could not be confirmed

  • The trial count of the forced arm could not be confirmed. The source does not say how many runs produced the drop from 100 percent to 89 percent. The eight-ninths inference in section eleven rests on decimal coincidence, not on a denominator the source published
  • The number of tasks per task type could not be confirmed. How many tasks sat inside localization, reference-completeness and multi-file rename respectively is not recorded
  • The values for Sonnet 4.6 and Haiku 4.5 on the multi-file rename row could not be confirmed. Those two cells are empty in the table, so it is impossible to tell whether the 3 percent is common to all three models or belongs to one
  • How the ground truth set for the reference-completeness task was built, and by whom, could not be confirmed. The denominator behind the 0.66 recall, meaning the full list of references that should have been found, governs how that value is to be read
  • The language server implementations and versions used could not be confirmed. What counts as a reference is up to the server implementation, so there is no guarantee another server produces the same figures
  • The detailed parameter specification of the reference-finding request could not be verified directly against the official specification, since the specification document truncated before that section in the responses retrieved. This article states only what was verified, namely that the result type carries coordinates alone
  • The snippet length and ceiling rules in the inline-context arm could not be confirmed. How many lines were attached governs how reproducible the token saving is
  • Whether this study has been replicated on other model families or other language ecosystems could not be confirmed. No follow-up replication report was found as of publication
