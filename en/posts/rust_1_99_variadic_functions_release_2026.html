Overview of Rust 1.99.0 and Core Changes

Released on October 1, 2026, Rust 1.99.0 officially resolves several longstanding challenges at the boundary between low-level systems programming and the Foreign Function Interface (FFI). The headline addition is the ability to directly author C-ABI-compatible variadic functions inside native Rust codebases. Previously, software engineers building systems libraries, operating system hooks, or logging frameworks that interface with C runtimes had to rely on out-of-tree C glue shims or platform-dependent inline assembly shims to export variadic entry points. With Rust 1.99.0, this structural gap is permanently closed by first-class compiler support.

Simultaneously, the release stabilizes three foundational APIs for inspecting the memory layout of raw pointers. By formalizing the safety contracts for unsized types (!Sized) whose layout cannot be determined at compile time, Rust provides memory allocators, runtime collectors, and serialization frameworks with safer, dereference-free primitives. Furthermore, comprehensive updates to the official guidance around Box::leak and the introduction of new collection utilities provide production teams with clear architectural guidance for modern memory management.

Broader architectural reflections regarding systems safety and language boundaries can also be explored in related analyses such as Memory Safety Absolutists and Rust Position and multi-language system interop patterns in Rust Migration Architecture Guide. This article focuses strictly on the verified specifications and technical implications delivered in Rust 1.99.0.

  • Direct Definition of C-ABI Variadic Functions: Full support for defining functions accepting variable arguments under "C" and "C-unwind" ABIs.
  • ABI-Compatible VaList and VaArgSafe Trait: Seamless interop with C va_list guarded by compiler-checked argument promotion rules.
  • Three Raw Pointer Layout Inspection APIs: Stabilization of Layout::for_value_raw, size_of_val_raw, and align_of_val_raw.
  • Revised Box::leak Deallocation Guidance: Deprecation of round-trip unleaking patterns in favor of explicit pointer conversion methods.
  • Standard Collection and Iteration Additions: IntoIterator for Box<[T; N]>, VecDeque::retain_back, and key buffer utilities.

Stabilization of C-ABI Variadic Function Definitions — From Calling to Defining

Variadic functions represent an established C paradigm where the number and types of arguments passed to a routine are determined dynamically at runtime. Rust has historically supported declaring and calling external C variadic functions through extern "C" { fn printf(format: *const c_char, ...) -> c_int; }. However, the inverse capability—allowing C code or foreign environments to invoke a variadic function implemented natively in Rust—was previously unsupported. Rust 1.99.0 closes this gap by allowing functions with the ... parameter syntax to be defined directly under the "C" and "C-unwind" calling conventions.

Because variadic parameter passing bypasses static compiler verification of argument types and counts, all variadic function implementations must reside within an unsafe context. The calling environment assumes full responsibility for passing arguments that match the callee's expectations, and the receiving routine must determine argument boundaries via delimiters or format strings. Additionally, the release stabilizes naked variadic functions with non-"C" ABIs under the #[unsafe(naked)] attribute, with the mandatory constraint that their implementation must consist entirely of inline assembly.

/// SAFETY: must be called with (at least) 2 i32 arguments.
                    unsafe extern "C" fn sum(mut args: ...) -> i32 {
                        // SAFETY: guaranteed by the caller.
                        let a = unsafe { args.next_arg::<i32>() };
                        let b = unsafe { args.next_arg::<i32>() };
                        a + b
                    }
                    
                    fn foo() -> i32 {
                        unsafe { sum(0i32, 2i32) }
                    }

In this official example, the identifier mut args: ... binds the incoming variable argument sequence to a core::ffi::VaList structure within the function body. Callers invoke the function using standard call syntax, such as sum(0i32, 2i32), while the compiler handles parameter passing according to target-specific register and stack conventions. For FFI engineers writing native libraries intended for consumption by C, Python, or Go runtimes, this feature eliminates the need for intermediate C wrapper layers entirely.

  • Calling Convention Scope: Permitted strictly on functions declared with extern "C" or unwinding-aware extern "C-unwind".
  • Caller-Guaranteed Safety Contract: Mismatches between supplied arguments and extracted types trigger undefined behavior, requiring unsafe markers.
  • Syntactic Binding: The ... token in the parameter list manifests inside the routine body as an operable VaList instance.
  • Naked Function Implementation: Routines annotated with #[unsafe(naked)] require manual stack and register management via inline assembly.
  • Shim Elimination: Removes the necessity of shipping auxiliary C wrapper files solely to construct variadic callbacks.

VaList and VaArgSafe — Argument Extraction and Type Safety

To unpack individual arguments from the incoming argument stream, Rust introduces the core::ffi::VaList type alongside the core::ffi::VaArgSafe marker trait. VaList guarantees 100% binary ABI compatibility with the native C va_list definition across every supported target architecture. Whether running on x86_64 System V, Windows x64, or AArch64, target-specific variations in register save areas and overflow arguments are transparently managed by the underlying type implementation.

The primary safety barrier during argument extraction is the VaArgSafe trait. Under the C specification, values passed through variadic ellipses undergo default argument promotions, where float values are promoted to double, and types smaller than int (such as char or short) are widened to int. If an author were permitted to call args.next_arg::<u8>() on raw stack frames, memory alignment would misalign immediately, causing subsequent reads to decode corrupted bytes. By constraining the generic parameter of next_arg::<T>() to types implementing VaArgSafe, the Rust compiler mathematically prevents extraction of types that violate the target calling convention.

Nevertheless, calling args.next_arg::<T>() remains inherently unsafe. While the compiler verifies that T is a promotion-safe type, it cannot inspect whether the foreign caller actually placed a value of type T at that exact position in memory. Consequently, systems developers must continue to design robust protocols, such as format strings or length prefixes, to validate input integrity before decoding arguments.

  • Target Architecture Parity: VaList accurately models platform-specific calling conventions including register spill areas and stack offsets.
  • Compile-Time Promotion Enforcement: VaArgSafe trait boundaries restrict extraction to types compatible with C default argument promotions.
  • Lack of In-Band Length Metadata: C-ABI argument streams do not carry length information, requiring callee-managed boundary termination.
  • Explicit Extraction Method: Arguments are decoded one by one via args.next_arg::<T>() within an explicit unsafe block.
  • State Cloning Parity: Provides standard facilities equivalent to C va_copy for multi-pass argument parsing workflows.

Three Raw Pointer Layout APIs — Safety Requirements for Sized and !Sized Types

Rust 1.99.0 stabilizes three vital functions for computing the size and alignment requirements of values directly from raw pointers: core::alloc::Layout::for_value_raw, core::mem::size_of_val_raw, and core::mem::align_of_val_raw. While Layout::for_value and mem::size_of_val have existed in Rust for years, they strictly demand a shared reference (&T). In memory allocators, garbage collectors, and low-level deallocation paths, creating a temporary reference to a dangling, unaligned, or partially uninitialized memory address is an immediate violation of Rust's aliasing rules.

The newly stabilized _raw family addresses this issue by taking a raw pointer (*const T) directly. For Sized types, the safety requirements are trivial: because size and alignment are entirely static, the functions can be evaluated without dereferencing the pointer, making them safe even on dangling or unaligned addresses. In contrast, for dynamically sized types (!Sized), such as dynamically sized slices ([T]) or trait objects (dyn Trait), the layout depends on metadata stored inside the fat pointer. For these types, the functions require that the pointer's metadata (the slice length or trait vtable pointer) be fully valid.

use std::alloc::Layout;
                    
                    // For Sized types, layout computation is completely safe even on dangling pointers
                    let dangling_ptr = std::ptr::NonNull::<u64>::dangling().as_ptr();
                    let layout_sized = unsafe { Layout::for_value_raw(dangling_ptr) };
                    assert_eq!(layout_sized.size(), 8);
                    
                    // For !Sized slices, valid fat pointer metadata (length) is strictly required
                    let slice_ptr: *const [u8] = std::ptr::slice_from_raw_parts(dangling_ptr as *const u8, 42);
                    let layout_unsized = unsafe { Layout::for_value_raw(slice_ptr) };
                    assert_eq!(layout_unsized.size(), 42);

As demonstrated in this sample, Layout::for_value_raw enables systems engineers to reconstruct exact deallocation layouts without invoking &*ptr. This clean decoupling between pointer inspection and reference creation prevents subtle compiler undefined behavior in custom memory managers and embedded allocators.

  • core::alloc::Layout::for_value_raw: Returns the full Layout instance (size and alignment) directly from a raw pointer.
  • core::mem::size_of_val_raw: Returns the exact memory footprint in bytes without constructing intermediate references.
  • core::mem::align_of_val_raw: Returns the required byte alignment constraint directly from raw pointer metadata.
  • Elimination of Dangling References: Prevents undefined behavior caused by creating transient references to unallocated or dangling memory.
  • Formally Defined Unsized Contracts: Establishes clear preconditions requiring valid fat pointer metadata for slices and trait objects.

Box::leak Documentation Update and Alternatives to Memory Unleaking Patterns

A notable policy and architectural shift in Rust 1.99.0 centers on the documentation for Box::leak. The Box::leak function has long served as a straightforward mechanism to surrender ownership of heap-allocated memory and acquire a mutable reference with a static lifetime (&'static mut T). Over time, numerous production libraries adopted a pattern of temporarily leaking a Box to obtain a static reference and later reconstructing the box using Box::from_raw to deallocate it—a practice known as the round-trip or unleaking pattern.

The updated documentation in 1.99.0 explicitly advises developers to avoid this round-trip unleaking pattern. While this change does not break backward compatibility or cause existing code to fail compilation, it addresses severe optimizations assumptions made by the compiler. A 'static reference implies to LLVM and the compiler backend that the underlying memory will remain valid and immutable across the entire lifetime of the process. Artificially reclaiming and deallocating that memory invalidates compiler assumptions and threatens future language enhancements, particularly the upcoming stabilization of custom allocators.

Instead of relying on Box::leak for temporary ownership transfers, the documentation recommends transitioning to explicit raw pointer methods, specifically Box::into_non_null or Box::into_raw. These functions explicitly convey to the compiler that ownership has exited the safe lifetime system into raw memory. When deallocation is eventually required, the pointer can be safely reconstructed via Box::from_non_null or Box::from_raw without violating reference semantics. This updated guidance applies uniformly to all similar leakage APIs across the standard library, including Vec::leak.

  • Guidance Revision Without Semantic Breakage: Existing code continues to compile, but adopting recommended patterns prevents future optimization hazards.
  • Protection of Optimization Guarantees: Preserves the compiler assumption that 'static references remain valid throughout application execution.
  • Preparation for Custom Allocators: Ensures allocator metadata is correctly tracked rather than lost in untracked static references.
  • Recommended Alternatives: Explicit adoption of Box::into_non_null and Box::into_raw for reversible ownership transfers.
  • Ecosystem-Wide Consistency: Extends the same architectural guideline across all standard library leak utilities, including Vec::leak.

Additional Stabilized APIs for Collections, Strings, and Filesystems

Beyond low-level FFI and pointer mechanics, Rust 1.99.0 delivers a rich array of standard library improvements aimed at boosting everyday application ergonomics. In the collections module, boxed fixed-size arrays now fully support standard iteration traits: IntoIterator for Box<[T; N]>, &Box<[T; N]>, and &mut Box<[T; N]>. Developers can now consume or inspect boxed arrays directly without first converting them into dynamically sized vectors or copying data onto the stack.

Furthermore, VecDeque::retain_back was introduced to allow selective pruning of ring buffers starting from the back, avoiding unnecessary element shifting in FIFO queues. The StepBy iterator adapter now implements FusedIterator for StepBy<I>, guaranteeing that once an iterator returns None, subsequent calls will continuously yield None. Low-level vector decomposition is now standardized through Vec::into_parts (returning pointer, length, and capacity) and its counterpart Vec::from_parts, providing a clean abstraction for zero-copy FFI buffer transfers.

In text and filesystem handling, String::from_utf8_lossy_owned avoids heap allocations when an owned Vec<u8> contains invalid UTF-8 by replacing invalid bytes in place where possible, paired with string::FromUtf8Error::into_utf8_lossy. For filesystem manipulation, std::fs::set_times and std::fs::set_times_nofollow were stabilized, enabling tools like archivers and build engines to update file timestamps without inadvertently following symlinks, mitigating common symlink-based security vulnerabilities.

  • Iteration over Boxed Arrays: Complete IntoIterator implementations for Box<[T; N]> across values, shared references, and mutable references.
  • Back-to-Front Queue Pruning: VecDeque::retain_back enables efficient queue maintenance without full buffer shifting.
  • Fused Iterator Guarantees: FusedIterator for StepBy<I> ensures predictable pipeline behavior following stream termination.
  • Vector Buffer Decomposition: Vec::into_parts and Vec::from_parts offer direct control over underlying allocation primitives.
  • Efficient Lossy String Decoding: String::from_utf8_lossy_owned reuses existing vector allocations during lossy UTF-8 conversion.
  • Symlink-Safe Filesystem Timestamps: set_times_nofollow allows precise metadata modification while preventing symlink traversal attacks.

Projects configured with any modern edition in Cargo.toml can immediately consume these stabilized APIs without altering package edition settings.

  • Toolchain Upgrade Procedure: Execute rustup update stable to fetch the official 1.99.0 release.
