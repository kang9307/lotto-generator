C++ 40년사 - 벨 연구소에서 현재까지, 다큐멘터리가 짚은 여정

한 언어가 어떻게 죽지 않고 다시 성장했는가

2026-06-07 IT/기술

서론: 40년을 견딘 언어, 그리고 한 편의 다큐멘터리

2026년 6월, 한 편의 다큐멘터리가 공개되며 개발자 커뮤니티가 술렁였습니다. 제목은 단순합니다. 「C++: The Documentary」. 1979년 벨 연구소의 작은 실험에서 시작해, 게임 엔진과 금융 거래 시스템, CERN의 입자 물리 실험, 그리고 전 세계 수백만 개발자의 손끝까지 퍼진 한 언어의 40년을 담은 작품입니다. 이 다큐멘터리에는 언어를 만든 Bjarne Stroustrup(비야네 스트롭스트룹), 표준화를 이끈 Herb Sutter, STL을 설계한 Alexander Stepanov, 그리고 Doom과 Quake를 만든 John Romero까지 등장합니다.

흥미로운 점은 이 다큐멘터리가 '추억 회고'가 아니라는 것입니다. 공개 시점에 인용된 통계에 따르면, C++는 2025년 3분기 기준 상위 4개 프로그래밍 언어 중 가장 빠르게 성장하고 있으며, 최근 3.5년간 사용자가 90% 이상 늘었다고 합니다. 한때 '레거시'로 취급받던 언어가 다시 성장 곡선을 그리고 있는 것입니다. 이 글에서는 다큐멘터리가 짚은 흐름을 따라, C++가 어디서 태어나 어떻게 표준이 되었고, 왜 아직도 쓰이며, 현대 C++는 무엇이 달라졌는지, 그리고 Rust 시대에 어떤 의미를 갖는지를 차분히 정리하겠습니다.

1. 탄생: 벨 연구소와 'C with Classes' (1979)

이야기는 1979년, 덴마크 출신의 젊은 컴퓨터 과학자 Bjarne Stroustrup이 AT&T 벨 연구소에 합류하면서 시작됩니다. 그는 박사 과정에서 분산 시스템을 연구하며 한 가지 딜레마에 부딪혔습니다. 시뮬레이션에 좋은 Simula(시뮬라) 언어는 클래스와 같은 강력한 추상화를 제공했지만 실무에 쓰기엔 너무 느렸고, 반대로 BCPL은 빠르지만 대규모 소프트웨어를 다루기엔 너무 저수준이었습니다.

Stroustrup의 결론은 명쾌했습니다. "C의 속도에 Simula의 추상화를 얹자." 1979년 10월, 그는 C 코드에 Simula식 클래스를 더하는 전처리기 Cpre를 만들었고, 이것이 'C with Classes'의 시작이었습니다. 이 시기에 더해진 기능들 - 클래스, 파생 클래스, 강한 타입 검사, 인라인 함수, 기본 인자 - 은 오늘날 C++의 골격을 그대로 결정했습니다. 중요한 철학은 이때 이미 자리 잡았습니다. "추상화의 대가를 런타임에 치르지 않는다(zero-overhead abstraction)." 즉, 쓰지 않는 기능에는 비용이 들지 않고, 쓰는 기능도 손으로 짠 코드만큼만 비싸야 한다는 원칙입니다.

2. 이름이 바뀌다: C++의 탄생 (1982~1985)

1982년, Stroustrup은 'C with Classes'의 후계자를 개발하기 시작하며 새 이름을 고민했습니다. 여러 후보 끝에 선택된 이름이 C++였습니다. C 언어의 증가 연산자 ++에서 따온 것으로, "C를 한 단계 끌어올린다"는 의미를 담았습니다. 작명 자체에 프로그래머의 위트가 배어 있는 셈입니다.

1983년에는 Cfront라는 컴파일러가 등장했습니다. Cfront의 핵심은 C++ 코드를 일단 C 코드로 변환한 뒤 기존 C 컴파일러로 컴파일하는 방식이었습니다. 이 영리한 전략 덕분에 C++는 당시 거의 모든 플랫폼에 존재하던 C 도구 생태계 위에 올라탈 수 있었습니다. 그리고 1985년, C++는 첫 상용 배포와 함께 세상에 정식으로 나왔고, 같은 해 Stroustrup의 저서 The C++ Programming Language 초판이 출간되었습니다. 아직 공식 표준이 없던 시절, 이 책 자체가 사실상의 표준 역할을 했습니다.

C++의 설계 철학은 한 문장으로 요약됩니다. "프로그래머를 믿되, 추상화의 대가는 런타임이 아니라 컴파일 타임에 치르게 하라."

3. 표준화의 시대: C++98의 길

1980년대 후반, C++는 빠르게 퍼졌지만 동시에 위험도 커졌습니다. 컴파일러마다 동작이 조금씩 달랐고, 책 한 권에 의존하는 비공식 표준으로는 대규모 산업 채택을 감당하기 어려웠습니다. 그래서 1990년대 초, ISO와 ANSI 위원회가 구성되어 본격적인 표준화 작업이 시작되었습니다.

그 결실이 1998년의 C++98(ISO/IEC 14882:1998)입니다. C++의 첫 공식 국제 표준이며, 이 과정에서 가장 중요한 사건은 Alexander Stepanov가 설계한 STL(Standard Template Library)의 통합이었습니다. vector, map, set, list 같은 컨테이너와 알고리즘이 템플릿 기반의 일반화 프로그래밍으로 표준 라이브러리에 들어왔습니다. STL은 단순한 자료구조 모음이 아니라, '컨테이너-반복자-알고리즘'을 분리해 조합하는 사고방식 자체를 C++에 새긴 사건이었습니다. 2003년에는 C++98의 버그와 모호함을 바로잡은 소규모 수정판 C++03이 나왔습니다.

4. 정체와 'C++의 겨울'

C++98 이후 C++는 한동안 정체기에 들어섭니다. 다큐멘터리에서도 '2000년대 초반 C++의 겨울'이라는 표현으로 이 시기를 다룹니다. Java와 C#처럼 가비지 컬렉션을 갖춘 언어들이 떠올랐고, "C++는 너무 복잡하고 위험하다"는 비판이 쏟아졌습니다. 포인터를 잘못 다뤄 생기는 메모리 누수와 충돌은 C++의 대표적 약점으로 지목되었습니다.

2003년 이후 무려 8년간 새 표준이 나오지 않았다는 사실은 이 정체를 상징적으로 보여줍니다. 많은 사람이 C++의 전성기가 끝났다고 생각했습니다. 그러나 이 침묵의 시기는 사실 다음 도약을 위한 준비 기간이었습니다. 위원회는 언어를 근본적으로 현대화할 큰 그림을 그리고 있었습니다.

5. 부활: C++11과 '현대 C++'의 시작

2011년, 8년의 침묵을 깨고 발표된 C++11은 게임 체인저였습니다. 너무 많은 것이 바뀌어, 사람들은 이때부터를 '현대 C++(Modern C++)'라고 부르기 시작했습니다. Stroustrup 본인도 "C++11은 마치 새 언어처럼 느껴진다"고 표현했습니다. 핵심 추가 기능을 정리하면 다음과 같습니다.

  • 스마트 포인터(unique_ptr, shared_ptr): 수동 new/delete 없이 자원 수명을 자동 관리합니다. 메모리 누수의 핵심 원인을 구조적으로 제거합니다.
  • 이동 의미론(Move Semantics): 불필요한 복사 대신 자원의 소유권을 '이동'시켜 성능을 끌어올립니다. 큰 객체를 반환·전달할 때의 비용을 극적으로 줄였습니다.
  • auto 타입 추론: 장황한 타입 선언을 컴파일러가 추론하게 해 코드를 간결하게 만듭니다.
  • 람다 표현식: 익명 함수를 코드 흐름 속에 직접 작성할 수 있게 되었습니다.
  • constexpr: 컴파일 타임 계산을 명시적으로 지원합니다.

이 변화들의 공통된 방향은 분명합니다. "위험한 수동 작업을 줄이고, 컴파일러가 더 많은 일을 하게 한다." 특히 스마트 포인터와 이동 의미론은 C++의 고질병이던 메모리 문제를 크게 완화하면서도, 가비지 컬렉터의 런타임 비용은 피했습니다.

6. 3년 주기의 진화: C++14 / 17 / 20

C++11 이후 위원회는 3년 주기로 표준을 내놓는 규칙적인 리듬을 정착시켰습니다. 이 예측 가능성 자체가 산업의 신뢰를 회복하는 데 크게 기여했습니다.

  • C++14 (2014): C++11의 빈틈을 메우는 소규모 확장입니다. 제네릭 람다, 변수 템플릿 등 사용성을 다듬었습니다.
  • C++17 (2017): 표준 파일시스템 라이브러리(<filesystem>)와 병렬 STL이 대표 기능입니다. 구조적 바인딩, std::optional, std::string_view, if constexpr 등 실용적 도구가 대거 추가되었습니다.
  • C++20 (2020): C++11에 버금가는 대변혁입니다. 흔히 '빅 4'로 불리는 네 기능 - 개념(Concepts), 범위(Ranges), 코루틴(Coroutines), 모듈(Modules) - 이 핵심입니다.

특히 C++20의 빅 4는 언어의 표현 방식 자체를 바꿨습니다. 개념(Concepts)은 템플릿에 제약을 명시해 난해하던 오류 메시지를 읽을 만하게 만들었고, 범위(Ranges)는 컬렉션 처리를 선언적으로 연결할 수 있게 했습니다. 코루틴(Coroutines)은 비동기·지연 평가 코드를 자연스럽게 쓰게 했고, 모듈(Modules)은 수십 년 묵은 헤더 파일 방식의 느린 컴파일과 매크로 오염을 근본적으로 개선할 길을 열었습니다.

7. 코드로 보는 변화: 옛 C++ vs 현대 C++

말로만 설명하면 추상적이니, 같은 작업을 두 시대의 스타일로 비교해 보겠습니다. 메모리를 직접 다루던 옛 방식과, 스마트 포인터·범위를 쓰는 현대 방식의 차이입니다.

// 옛 스타일 (C++98) - 수동 메모리 관리, 누수 위험
#include <vector>
#include <iostream>

void old_style() {
    int* arr = new int[3];          // 수동 할당
    arr[0] = 1; arr[1] = 2; arr[2] = 3;

    int sum = 0;
    for (int i = 0; i < 3; ++i) {    // 인덱스 기반 루프
        sum += arr[i];
    }
    std::cout << sum << std::endl;

    delete[] arr;                    // 잊으면 곧 메모리 누수
}
// 현대 스타일 (C++20) - RAII, 범위, 안전한 추론
#include <vector>
#include <numeric>
#include <iostream>

void modern_style() {
    // 스택에 자동 관리되는 컨테이너 - delete 불필요
    std::vector<int> nums{1, 2, 3};

    // 표준 알고리즘으로 의도를 선언적으로 표현
    auto sum = std::accumulate(nums.begin(), nums.end(), 0);

    std::cout << sum << std::endl;
}   // nums는 스코프를 벗어나며 자동 해제 (RAII)

핵심 차이는 delete가 사라졌다는 점입니다. 현대 C++의 RAII(Resource Acquisition Is Initialization, 자원 획득은 초기화) 원칙은 자원의 수명을 객체의 수명에 묶습니다. 객체가 스코프를 벗어나면 자원이 자동으로 반환되므로, "delete를 깜빡해서 생긴 누수"라는 고전적 버그가 구조적으로 사라집니다. 스마트 포인터가 바로 이 RAII를 포인터에 적용한 사례입니다.

8. 왜 아직도 C++인가: 성능이 곧 정체성

2026년에도 C++가 건재한 이유는 한 단어로 요약됩니다. 성능입니다. 더 정확히는 '가비지 컬렉터 없이 하드웨어에 가까운 제어를 제공하면서도 고수준 추상화를 쓸 수 있다'는 독특한 위치입니다. 이 특성이 빛을 발하는 분야는 분명합니다.

분야 왜 C++인가 대표 사례
게임 엔진 프레임당 밀리초 단위 제어, 예측 가능한 지연 Unreal Engine, 주요 AAA 게임
운영체제·브라우저 저수준 하드웨어 접근, 극한의 최적화 Windows 핵심부, Chrome/V8
금융 거래 나노초 단위 지연이 곧 수익 고빈도 트레이딩(HFT) 시스템
임베디드·자동차 제한된 자원, 실시간 제어 차량 제어, 항공·우주 시스템
과학 계산 대규모 수치 연산의 처리량 CERN 입자 물리 분석(ROOT)

한 벤치마크 보고서에 따르면, 지연이 핵심인 일부 애플리케이션에서 C++는 Rust보다 15~20% 빠르게 동작하기도 합니다. 이는 Rust가 안전을 위해 추가하는 일부 런타임 검사가 없기 때문입니다. 매 사이클이 중요한 게임 엔진과 임베디드에서, 이런 미세한 차이가 채택의 근거가 됩니다. 한 연구에서는 임베디드 개발자의 73%가 실시간 시스템에 C++를 쓴다고 답하기도 했습니다.

9. 도전자 Rust: 경쟁이 아니라 공존

현대 C++ 이야기에서 Rust를 빼놓을 수 없습니다. Rust는 소유권(ownership)과 빌림 검사(borrow checker)를 통해 댕글링 포인터, use-after-free, 데이터 레이스를 컴파일 타임에 차단합니다. 메모리 안전이 생명인 자동차·임베디드 분야에서 강력한 매력입니다. 한때 "Rust가 C++를 대체할 것"이라는 전망이 유행했습니다.

그러나 2026년의 현실은 '대체'보다 '공존'에 가깝습니다. 그 이유는 다음과 같습니다.

  • 방대한 기존 코드베이스: 게임 엔진, 운영체제, 금융 시스템에 쌓인 수십 년치 C++ 코드를 하룻밤에 다시 쓸 수는 없습니다.
  • 생태계와 도구의 성숙도: 라이브러리, 디버거, 프로파일러 등 C++ 생태계의 깊이는 압도적입니다.
  • C++ 자신의 진화: C++26은 std::vector·std::string의 경계 검사를 강화한 '하드닝된 표준 라이브러리'로 안전성 격차를 좁히고 있습니다.

실제 산업의 선택은 명확합니다. 기존 자산과 극한 성능이 필요한 영역은 C++가 지키고, 새로 시작하는 안전 중심 프로젝트는 Rust가 가져가는 식의 분업입니다. 두 언어를 한 시스템 안에서 섞어 쓰는 사례도 늘고 있습니다. Rust로의 점진적 이주에 관심이 있다면 Go에서 Rust로 이주 가이드를, 메모리 안전과 성능의 균형에 대해서는 Rust로 구현한 Zstandard 분석을 함께 보면 이 흐름이 더 또렷해집니다.

10. 다큐멘터리가 던지는 메시지

「C++: The Documentary」는 CultRepo가 제작했고, 금융 분야의 후원을 받아 만들어졌습니다. 단순한 기술 소개를 넘어, 한 언어가 40년간 어떻게 살아남고 다시 성장했는가라는 더 큰 질문을 다룹니다. 다큐멘터리가 짚는 메시지를 정리하면 세 가지입니다.

첫째, 지속성의 힘입니다. C++는 한 번도 '가장 트렌디한 언어'였던 적이 없지만, 묵묵히 진화하며 사라지지 않았습니다. 둘째, 하위 호환성의 무게입니다. 수십 년 전 코드가 오늘도 컴파일되어야 한다는 제약은 언어를 복잡하게 만들지만, 동시에 거대한 산업이 안심하고 기댈 수 있는 토대가 됩니다. 셋째, 커뮤니티와 위원회의 헌신입니다. 표준을 둘러싼 끝없는 논쟁과 타협이야말로 C++를 살아 있게 한 동력이었습니다.

11. C++를 배우려는 사람에게

이 모든 역사가 흥미롭더라도, 결국 실용적인 질문이 남습니다. "지금 C++를 배워야 할까, 배운다면 어떻게?" 다큐멘터리의 흐름과 현대 C++의 방향을 토대로 정리하면 다음과 같습니다.

  1. 현대 C++부터 시작하라. 옛 교재의 new/delete 중심 스타일이 아니라, C++17/20 이후의 스마트 포인터와 RAII를 처음부터 익히세요. 같은 언어라도 안전성과 생산성이 전혀 다릅니다.
  2. STL과 알고리즘에 익숙해져라. vector, map, 그리고 표준 알고리즘은 현대 C++의 일상 언어입니다. 직접 구현하기 전에 표준을 먼저 찾는 습관이 중요합니다.
  3. 왜 C++인지 분명한 목표를 가져라. 게임, 임베디드, 고성능 시스템처럼 C++가 빛나는 분야를 목표로 삼으면 학습 동기가 분명해집니다. 단순 웹 백엔드라면 다른 선택이 나을 수 있습니다.
  4. 도구를 함께 익혀라. 컴파일러 경고를 최대로 켜고, 정적 분석기와 sanitizer(주소·메모리 검사 도구)를 습관화하면 C++의 위험을 크게 줄일 수 있습니다.

12. 결론 + 즉시 적용 가능한 3가지

C++의 40년은 한 문장으로 요약됩니다. "성능을 포기하지 않으면서, 끊임없이 더 안전하고 표현력 있게 진화한 언어." 벨 연구소의 작은 전처리기에서 시작해, 표준화의 길과 '겨울'을 지나, C++11의 부활과 C++20의 대변혁을 거쳐, 이제 C++26을 앞두고 다시 가장 빠르게 성장하는 언어가 되었습니다. Rust의 도전조차 C++를 끝내기보다 더 안전하게 진화하도록 자극했습니다.

당장 실천할 수 있는 세 가지로 마무리합니다.

  1. 현대 C++로 다시 보라. C++를 예전에 접하고 멀어졌다면, C++17/20의 스마트 포인터·범위·개념을 30분만 살펴보세요. "이게 그 C++ 맞아?" 싶을 만큼 달라졌습니다.
  2. 수동 메모리 관리를 RAII로 바꿔라. 기존 코드에 남은 new/delete를 unique_ptr·vector 같은 RAII 도구로 점진적으로 교체하면, 가장 흔한 메모리 버그가 사라집니다.
  3. 다큐멘터리를 직접 보라. 「C++: The Documentary」는 기술을 넘어 '한 기술이 어떻게 오래 살아남는가'에 대한 통찰을 줍니다. 언어를 떠나, 만드는 사람이라면 한 번쯤 볼 가치가 있습니다.
