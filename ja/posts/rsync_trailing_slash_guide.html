はじめに: 昨日と同じコマンドを打ったのに結果が違うなら

rsync でこの言葉が出たら、十中八九スラッシュ一つだ。二行を並べてみる。

rsync -a /tmp/src  /tmp/dst/
rsync -a /tmp/src/ /tmp/dst/

違いはソースパス末尾の / 一つだけ。結果はこう分かれる。一行目は /tmp/dst/src/ を作ってその中に内容を入れる。二行目は /tmp/dst/ の直下に内容を展開する。

ここまでは不便な程度の話だ。問題はこのコマンドに --delete が付いたときである。その瞬間、スラッシュ一つの差は「一階層深くなった」ではなく「宛先ディレクトリの既存の中身がすべて消えた」になる。rsync に取り消しはなく、消えたファイルはゴミ箱を経由しない。

この記事はその規則を正確に立て、--delete が付いたときどこが戻れない地点なのかを明示し、Enter を押す前に一秒で確かめる手順を残す。rsync のオプション全般 — 圧縮、SSH 連携、帯域制限、部分転送の再開 — は Linux Rsync コマンド完全マスターの方にまとめてある。ここでは事故が起きる一点だけを掘る。

1. スラッシュが変えるのはパスではなく「何を運ぶか」だ

規則そのものは一行だ。ソース末尾の / は「このディレクトリの中身をコピーせよ」という意味で、無ければ「このディレクトリを名前ごとコピーせよ」という意味になる。

マニュアルはこの規則を等式としても記している。下の二行は宛先ディレクトリの属性設定まで含めて完全に同じ結果になる。

rsync -av /src/foo  /dest
rsync -av /src/foo/ /dest/foo

この等式が規則を覚える一番の近道だ。スラッシュを外した形は、宛先パスに名前を一つ足した形と同じである。ソースにスラッシュを付けるか迷ったら、宛先パスがどう伸びるかを思い浮かべれば答えが出る。

付け加えると、スラッシュの数は関係ない。/tmp/src// のように二つ続いても一つと同じに動く。この性質は雑学ではなく、後の 9 節でスクリプトの防波堤を立てるときにそのまま使う。

2. 四つの組み合わせの結果を一つの表で

前提を先に固定する。/tmp/src の中に a.txt と sub/b.txt があり、/tmp/dst は既にディレクトリとして存在する。

コマンド宛先にできるもの意味
rsync -a /tmp/src /tmp/dst/tmp/dst/src/a.txt
/tmp/dst/src/sub/b.txt		ディレクトリごと
rsync -a /tmp/src /tmp/dst/上と同じ宛先スラッシュは影響なし
rsync -a /tmp/src/ /tmp/dst/tmp/dst/a.txt
/tmp/dst/sub/b.txt		中身だけ
rsync -a /tmp/src/ /tmp/dst/上と同じ宛先スラッシュは影響なし

読み方は二方向ある。縦に見れば宛先側のスラッシュは何も変えず、横に見ればソース側のスラッシュがすべてを変える。この表を一度こう読んでおけば、コマンドを打つとき目が先にソースの末尾へ行くようになる。

宛先ディレクトリがまだ無いときは rsync が作ってくれる。ただし一階層までだ。宛先パスの親ごと無ければディレクトリを作れずに止まる。中間パスまで作る必要があるなら --mkpath を付ける。

3. 宛先側のスラッシュが意味を持つ唯一の場所

前の表で宛先スラッシュは何もしなかった。例外が一つある。項目を一つだけ別の名前でコピーするときだ。

rsync が運ぶ項目の名前を宛先パスの最後の要素に変えてくれるのは、下の三条件がすべて揃ったときだけである。

  • 転送リストが単一項目であること — ファイル一つ、または空のディレクトリ一つ
  • 宛先パスの最後の要素がディレクトリとして既に存在しないこと
  • 宛先パスを末尾スラッシュ付きで指定していないこと

三つ目がこの節の要点だ。実際に分かれる様子はこうなる。

rsync -a a.txt /tmp/dst/b.txt
# -> /tmp/dst/b.txt          名前が変わる

rsync -a a.txt /tmp/dst/b.txt/
# -> /tmp/dst/b.txt/a.txt    b.txt をディレクトリとみなす

スラッシュ一つが「この名前で保存」と「このディレクトリの中に保存」を分ける。スクリプトで宛先パスを変数から組み立てるとき、末尾に習慣で / を付けておくと、改名が黙って効かなくなり見慣れないディレクトリが一つできる。しかもこの失敗はエラーを出さない。だから数日後になってようやく見つかる。

まとめると宛先側のスラッシュ規則は二行だ。

  • ディレクトリを同期するとき — 付けても付けなくても同じ。読み手に宛先がディレクトリだと伝えるため付けておく方がよい
  • 単一項目の名前を変えるとき — 付けてはいけない

4. -a が実際に有効にするものと、しないもの

-a はオプション一つではなく束だ。正確には -rlptgoD である。中身を知っていることが、どこから漏れるかを見抜く条件になる。

オプション有効になる動作無いときに起きること
-r下位ディレクトリまで再帰ディレクトリを丸ごと飛ばす
-lシンボリックリンクをリンクのままリンクが一覧から抜ける
-pパーミッション保存宛先の umask で新しく決まる
-t更新時刻の保存実行のたびに全量再転送
-gグループ保存宛先の既定グループになる
-o所有者保存 (スーパーユーザ時のみ)実行アカウントの所有になる
-Dデバイスファイル・特殊ファイル保存該当項目が抜ける

実務で一番よく噛まれるのが -t の行だ。rsync の既定判定は「サイズまたは更新時刻が違えば転送」である。時刻を保存しなければ次の実行ですべて新しいファイルに見え、そこから「なぜ毎回全量転送なのか」が始まる。

ここからが本題、含まれないものである。

  • -H — ハードリンクを探して保存する動作。有効にならない
  • -A — ACL。有効にならない
  • -X — 拡張属性 (xattr)。有効にならない
  • -U アクセス時刻、-N 作成時刻。どちらも有効にならない
  • --delete — 決して含まれない。ここが核心だ
  • 例外が一行 — --files-from を併用すると -a の中の -r は含意されなくなる

-a が削除までしてくれるという誤解は、二方向に事故を生む。含まれると信じれば宛先に古いファイルが残ったままデプロイが混ざり、含まれないと知りながら習慣で --delete を一緒に打てば、消してはいけないものを消す。七文字 rlptgoD を覚えておけば、この二つの事故が同時に塞がる。

5. --delete を有効にする前に知っておくこと

--delete はデータを消すオプションだ。これが入ったコマンド行を、他の行と同じ重さで扱ってはいけない。マニュアルもこの項目で「誤用すると危険だ」と述べ、何が削除されるかを見るためにまず --dry-run(-n)を試すのが非常に良い考えだと明記している。この節を読んですぐ実行せず、7 節まで読んでからにする方がよい。

このオプションがすることを正確に書くとこうなる。受信側にあって送信側に無いファイルを消す。同期対象になったディレクトリに限ってのことだ。

ここで読むべきは「送信側に無い」という判定基準である。rsync はそのファイルがなぜ無いのかを問わない。ソースで意図的に消したファイルも、パスを打ち間違えて見えていないファイルも、マウントが外れていて見えていないファイルも、判定はまったく同じだ。この無差別さが 6 節の事故シナリオをすべて作る。

頭に入れておくべき条件をいくつか。

  • 再帰(-r)か -d が有効でなければ削除は起きない。-a の中に -r があるので大抵は有効になっている
  • 送信側で I/O エラーが検出されると削除は自動的に無効化される。安全装置ではあるが「ソースが空だ」はエラーではない。これを防波堤と信じてはいけない
  • --exclude で除外したファイルは宛先にあっても消えない。消させたければ --delete-excluded を別途有効にする必要がある
  • rsync 3 以降は、別途指定が無ければ転送しながら順次消していく方が既定になっている
オプション削除の時点・動作いつ使うか
--delete既定動作 (現在は転送中に削除)一般的なミラーリング
--delete-before転送開始前に一括削除宛先の空き容量が厳しいとき
--delete-during (--del)転送しながら順次ファイル数が多くメモリを節約したいとき
--delete-delay転送中に算出、終わってから削除中間状態を減らしたいとき
--delete-after転送がすべて終わった後宛先が稼働中でファイルが急に消えると困るとき
--delete-excluded除外項目まで削除宛先をソースと完全に同一にするとき
--max-delete=NN 個を超えようとすると中断すべての自動化に既定で掛けるシートベルト
--backup --backup-dir=DIR消す・上書きする代わりに移す戻る余地を残すとき

この表で価値が最も大きいのは最後の二行だ。上の六行は状況次第の好みだが、下の二行は保険である。特に --backup-dir はrsync コマンドを取り消し可能にする唯一の装置だ。

6. スラッシュ一つでデータが消える経路

意図したコマンドはこうだ。

rsync -a --delete /tmp/src/ /tmp/dst/
# /tmp/dst を /tmp/src の中身と同じにする

ここでスラッシュが一つ抜ける。

rsync -a --delete /tmp/src /tmp/dst/
#                          ↑ スラッシュ無し

何が起きるかを順に書く。

  1. ソースが「src というディレクトリ一つ」として解釈される
  2. 送信側の全体一覧が src/ とその下位項目だけになる
  3. /tmp/dst の直下にあった既存項目はすべて「送信側に無いファイル」になる
  4. --delete がそれらを消す
  5. 残るのは /tmp/dst/src/ 一つ

宛先ディレクトリの既存の中身がすべて消え、その場所に一階層深くなった複製が一つだけ残る。これが rsync 事故の標準形だ。スラッシュを付け忘れること自体はよくあるタイプミスであり、それが --delete と出会ったときだけこの結末になる。

6.1 同じ結末へ向かう別の道が三つ

ソースがマウントされていないとき。バックアップ元が外付けディスクやネットワークボリュームで、マウントが外れていると、マウントポイントのディレクトリは存在するが空だ。rsync は「送信側にファイルが一つも無い」と読み、宛先を全部消す。パスの打ち間違いと違い、この場合はエラーすら出ない。正常終了する。終了コードだけを見て成功と記録する自動化なら、事故を成功として残すことになる。

変数が空のとき。下の一行が宛先変数の空いた状態で回ると、宛先は / になる。

rsync -a --delete "$SRC/" "$DST/"
# DST が空 -> 宛先が / になる

何が消えるかはこれ以上説明する必要がないだろう。逆に SRC が空ならソースが / になり、ルート全体を宛先へ押し込む。こちらはディスクが先に埋まって止まる程度だが、前者は機材を失う。AI エージェントや自動化がシェル変数を組み立ててコマンドを作る構成なら、危険がもう一枚増える — 似た性質の事故を PowerShell 変数衝突事故で扱った。

フィルタを後から足したとき。問題なく回っていたミラーリングに --exclude を一つ入れる。数日後「除外したものが宛先にまだ残っているな」と気づいて --delete-excluded を有効にする。その瞬間、それまで守られていたファイルが一度に消える。オプションが一つ増えただけなのに、削除の範囲が変わったのだ。

6.2 戻れない地点は Enter だ

はっきり書いておく。rsync に取り消しはない。--delete で消えたファイルはゴミ箱を経由せず、宛先がリモートならそのサーバのファイルシステムから即座に消える。消えた後にできることは別のバックアップから復旧することだけであり、そのバックアップがたった今のその rsync だったなら、残るものは無い。

バックアップを世代で分ける理由がこれだ。ミラーリング一つはバックアップではない。ソースで消えたものが宛先でも消える構成は、定義上、事故をそのまま複製する。世代と保管期間をどう分けるかは クラウドバックアップ完全ガイドと databasement 徹底分析で扱い、自宅に置く機材の話は NAS(ホームサーバー)の選び方にある。

7. 消す前に一秒で確かめる方法

-n を一つ付けるだけでよい。手順は三段階だ。

# 1) 確認 - -n を付けて何も変えずに回す
rsync -avn --delete /tmp/src/ /tmp/dst/

# 2) 出力を読む  (読み方は 8 節)

# 3) シェル履歴からその行を呼び出し、n の一文字だけを消す
rsync -av --delete /tmp/src/ /tmp/dst/

三段階目が重要だ。パスを打ち直さない。確認したコマンドと実行するコマンドが一文字しか違わないので、確認と実行の間にタイプミスが入り込む余地がない。コマンドを二度打つ習慣は、この確認手順そのものを無力化する。

-n は何も変えずに、実際の実行とほぼ同じ出力を出す。ここで「ほぼ」の範囲を正確に知っておく必要がある。

  • 信じてよいもの — --itemize-changes(-i)の出力は dry run と後続の実際の実行で同じになるよう設計されている。つまり -ni で見た項目一覧と各項目の変更理由はそのまま起きる
  • 信じてはいけないもの — dry run は実際のデータを送らない。そのため「送信バイト」「受信バイト」といった統計が実際より小さく出て、--progress は効果を持たない。転送量や所要時間の見積もりを dry run で出すと外れる

要約すると「何が変わるか」は信じ、「どれくらいかかるか」は信じない、が正しい。

cron や CI に入れる前にもう一度押さえておく。自動化に入る --delete コマンドは、人間が手で -n を回したことがあるものでなければならない。スケジューラの中で初めて回る削除コマンドほど危険なものはない。誰も見ておらず、失敗しても次の周期でまた回る。

8. dry run の出力を読む方法

-v だけ付けるとファイル名の一覧しか出ない。「なぜこのファイルがまた転送されるのか」には答えられない。-i を付ければ答えが出る。

rsync -ain --delete /tmp/src/ /tmp/dst/

-i は各項目の前に 11 桁の要約を付ける。形は YXcstpoguax だ。桁ごとに意味が決まっている。

桁記号意味
1Y更新の種類
2X項目の種類
3c内容 (チェックサム) が違う
4sサイズが違う
5t更新時刻が違う
6pパーミッションが違う
7o所有者が違う
8gグループが違う
9u予約 (アクセス時刻系)
10aACL が違う
11x拡張属性が違う

先頭二桁に入る文字は別途覚えておく価値がある。

桁文字意味
1 桁目<リモートへ送る
1 桁目>こちらで受け取る
1 桁目cローカルで作成・変更する (ディレクトリやリンクの作成など)
1 桁目h他の項目へのハードリンクだ
1 桁目.更新しない (属性だけ触ることはある)
1 桁目*後ろがメッセージだ — 削除はここに出る
2 桁目fファイル
2 桁目dディレクトリ
2 桁目Lシンボリックリンク
2 桁目Dデバイス
2 桁目S特殊ファイル (ソケット・FIFO など)

属性桁が埋まる規則は三つだ。

  • 新しく作られる項目は文字の位置がすべて + で埋まる
  • 完全に同じ項目はドットが空白に変わる
  • 分からない属性は ? になる

8.1 読む練習

>f+++++++++   新しいファイルを受け取る
>f..t......   内容は同じで更新時刻だけ合わせる
>f.st......   サイズと時刻が違う = 内容が変わった
.d..t......   ディレクトリはそのまま、時刻だけ合わせる
cd+++++++++   ディレクトリを新しく作る
*deleting     消す

一番重要なのは最後の行だ。*deleting が一行でも見えたら、そこで止めて一覧全体を読むべきである。消える予定の数が想定と違えば、そのコマンドは間違っている。

数えるのも手だ。目で追うには一覧が長すぎることが多い。

rsync -ain --delete /tmp/src/ /tmp/dst/ | grep -c '^\*deleting'

0 であるべき作業で三桁の数字が出たなら、それは今まさにタイプミスを捕まえたということだ。この一行をデプロイスクリプトの事前点検として組み込んでいるチームもある。

9. よくある失敗七つとそれぞれの防波堤

  1. ソースのスラッシュ抜け — 結果が一階層深くなり、--delete と出会えば宛先が空になる。防波堤: スクリプトではソース変数にスラッシュを入れず、使用箇所で必ず "$SRC/" と付ける。変数値に既にスラッシュがあっても // は一つと同じに動くので、どちらでも安全になる
  2. タブ補完が付けたスラッシュ — 手で打つときと補完するときでコマンドが変わる。防波堤: 補完した後にソースの末尾を目で一度見る。--delete がある行なら特に
  3. -a が --delete を含むという誤解 — 宛先に古いファイルが残りデプロイが混ざる。防波堤: -a は rlptgoD の七文字だけだと覚える
  4. 宛先変数が空 — 宛先が / になる。防波堤: スクリプト冒頭に set -euo pipefail と : "${DST:?}" を置く。set -u だけでは「定義済みだが空文字列」を捕まえられない
  5. ソースのマウント外れ — 宛先が全滅し、しかもエラーが出ない。防波堤: mountpoint -q を rsync の前に立て、--max-delete を併せて掛ける
  6. 時刻を保存できないファイルシステム — exFAT や一部のネットワーク共有は更新時刻の解像度が違い、毎回全量再転送になる。防波堤: --modify-window=1 で許容誤差を与える。パーミッション保存まで失敗する宛先なら -a ではなく -rlt に落とすか --no-p --no-g --no-o を付ける
  7. 除外規則と削除の衝突 — --exclude したファイルは宛先にあっても消えない。知らなければ「なぜ消えないのか」になり、知らずに --delete-excluded を有効にすれば「なぜ消えたのか」になる。防波堤: どちらを望むのかを先に文章で書いてからオプションを選ぶ

リモートパスも規則は同じだ。user@backup.example.com:/srv/data と user@backup.example.com:/srv/data/ の違いはローカルとまったく同じで、コロンの後ろがパスだという点だけが増える。リモートだからといって規則が緩むことはなく、むしろ事故に気づくまでの時間が長くなる。

10. 戻れない地点を明示するスクリプト骨格

--delete が入った行は他の行と別扱いにするべきだ。下をそのまま骨格として使ってよい。

#!/usr/bin/env bash
set -euo pipefail

# 変数の末尾にスラッシュを入れない。使用箇所で付ける。
SRC=/srv/app/current
DST=/mnt/backup/app

: "${SRC:?ソースパスが空だ}"
: "${DST:?宛先パスが空だ}"

mountpoint -q /mnt/backup || { echo "バックアップボリュームがマウントされていない"; exit 1; }

rsync -a --delete \
  --max-delete=100 \
  --backup --backup-dir="/mnt/backup/_trash/$(date +%F)" \
  --log-file=/var/log/app-sync.log \
  "$SRC/" "$DST/"

各行が何を止めているかを一つずつ挙げる。

  • set -u — 未定義の変数を使えばその場で死ぬ
  • : "${DST:?}" — 変数が空文字列のときにも死ぬ。set -u が塞げない穴をここで塞ぐ
  • mountpoint -q — マウント外れという最も静かな事故経路を止める
  • --max-delete=100 — 想定より多く消そうとすれば rsync が自ら止まる。数字はその作業の平常時の削除量を見て決める
  • --backup-dir — 消される・上書きされるファイルが消滅する代わりにそのディレクトリへ移る。戻る余地が残る唯一の装置だ
  • --log-file — 何が消えたかを後から確認できる。事故が起きた後には作れない資料だ
  • "$SRC/" — 変数にスラッシュを入れず使用箇所で付ける。9 節 1 番の防波堤がここに入っている

これに人がやる手順を二つ足す。

  • 新しく書いた rsync の行は必ず -n を付けて一度回す。例外なし
  • --backup-dir を使うなら、そのディレクトリを空ける周期も一緒に決める。そうしないとバックアップボリュームが先に埋まる

11. 直接実行して確かめられなかったこと

この記事で実行によって確認できなかった項目を一箇所にまとめる。

  • コードブロックの出力。ここに書いた出力の形は rsync の文書が規定する形式に従ったものであり、この記事を書いた環境で実行してキャプチャしたものではない。その環境に rsync が入っていなかったためだ
  • したがってオプションの組み合わせごとの結果は、各自が自分の環境で -n を使って一度確認することを前提に読むべきである。表に書いたのはマニュアルが規定する動作であり、ディストリビューション・バージョン・ファイルシステムによって細部は変わりうる
  • バージョン差。--mkpath は比較的最近入ったオプションで、-d だけでも削除が動くようになったのは rsync 2.6.7 以降だ。古い機材では同じコマンドが違う動きをしうる
  • 宛先パスが無いときに作ってくれる階層数と、そのときの正確なエラー文言は確認できなかった。一階層までというのは文書上の根拠であり、文言はバージョンごとに違う
  • exFAT やネットワーク共有の時刻解像度。毎回全量再転送が起きる現象は広く知られたパターンだが、どのマウントオプションで何秒の誤差が出るかは確認範囲の外だ
  • --max-delete が上限に掛かったときの終了コード。自動化でこの値を分岐条件に使うつもりなら、自分のバージョンで直接測る方がよい

よくある質問

Q. src と src/ は正確に何が違うのか?

ソース末尾のスラッシュは「このディレクトリの中身を」という意味で、無ければ「このディレクトリを名前ごと」という意味だ。だから rsync -a /tmp/src /tmp/dst は /tmp/dst/src/ を作り、rsync -a /tmp/src/ /tmp/dst は /tmp/dst の直下に展開する。スラッシュを外した形は宛先パスに名前を一つ足した形と同じと覚えれば迷わない。

Q. 宛先パスにも末尾スラッシュを付けるべきか?

ディレクトリを同期する通常のケースでは結果は同じだ。例外は項目を一つだけ別の名前でコピーするときである。このときは転送リストが単一項目で、宛先パスの最後の要素がディレクトリとして存在せず、宛先パスに末尾スラッシュが無いことが必要だ。一つでも崩れると改名は黙って効かない。

Q. -a を使えば宛先にしか無い古いファイルも消えるのか?

消えない。-a は -rlptgoD の七文字の束であり、削除は含まれていない。ハードリンク・ACL・拡張属性・アクセス時刻・作成時刻も有効にしない。宛先をソースと同じにしたければ --delete を明示的に有効にする必要があり、有効にした瞬間そのコマンドは性格が変わる。

Q. --delete を安全に試すには?

先に -n を付けて回す。手順は三段階だ。rsync -avn --delete で実行して出力を読み、消すと表示された行の数と中身が想定と合うか確認し、シェル履歴からその行を呼び出して n の一文字だけを消す。そこに --max-delete で上限を掛け、--backup-dir で戻る余地を残せば防波堤は三重になる。

Q. dry run の出力は実際の実行と完全に同じか?

同じ部分と違う部分がある。--itemize-changes の出力は dry run と実際の実行で同じになるようになっており、「何が変わるか」は信じてよい。一方 dry run はデータを実際には送らないので転送量の統計は実際より小さく出て、--progress は効果を持たない。「どれくらいかかるか」は信じてはいけない。

結論: 今日から変える三つ

第一に、ソースの末尾を先に見る。rsync のコマンドを読むとき、目が最初に行くべきなのはオプションではなくソースパスの最後の一文字だ。スラッシュがあれば中身、無ければディレクトリごと。この一度の視線が事故の大多数を止める。

第二に、変数にはスラッシュを入れず使用箇所で付ける。SRC=/srv/app と置き、使うときは "$SRC/" と書く。値に既にスラッシュがあっても結果が同じになるので、チームで誰がどう値を入れてもコマンドの意味が揺れない。

第三に、--delete が入った行を -n 無しで初めて実行しない。確認し、履歴から呼び出し、n の一文字だけを消す。そこに --max-delete と --backup-dir を重ねれば、人が間違えても道具がもう一度捕まえてくれる。

最後に一つ。この記事の主題はスラッシュに見えるが、実際の主題は取り消せないコマンドをどう扱うかだ。rsync はそういうコマンドを、非常に短く、非常に打ちやすい形で提供する。短いというのは楽だという意味であって、安全だという意味ではない。楽な道具ほど、防波堤を道具の外側に — スクリプトの骨格と指の習慣に — 立てておかなければならない。
