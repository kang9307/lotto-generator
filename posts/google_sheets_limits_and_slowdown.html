스프레드시트는 어디서 막히고 어디서 느려지는가 - 한도와 재계산 비용, 그리고 떠날 시점

하드 한도와 소프트 한도를 가르고, 무엇이 재계산을 비싸게 만드는지부터 옮길 곳까지

2026-09-08 IT/기술

파일이 안 열린다는 말과 파일이 굼뜨다는 말은 같은 원인을 가리키지 않는다. 앞의 것은 한도의 문제이고, 뒤의 것은 비용의 문제다. 한도는 숫자가 정해져 있어서 넘으면 동작이 거부된다. 비용에는 정해진 숫자가 없다. 대신 무엇이 비싼가에 대한 규칙이 있고, 그 규칙은 공개되어 있다.

이 둘을 갈라 두지 않으면 진단이 엉킨다. 셀을 지워서 풀리는 문제와, 셀을 지워도 그대로인 문제가 따로 있기 때문이다. 대부분의 「시트가 느려요」는 뒤쪽이다.

아래 수치는 2026년 9월 기준 구글 공식 도움말과 개발자 문서에 적혀 있는 값이다. 구글은 이 한도를 과거에 올린 적이 있으므로, 시점을 떼고 옮겨 적으면 언젠가 틀린 값이 된다. 각 수치의 출처는 마지막 절에 링크로 있다. 계정 선택과 공유 권한처럼 시트를 만들기 전에 정할 것은 구글 스프레드시트 처음 시작하기가, 수식과 Apps Script 로 일을 시키는 방법은 구글 시트 자동화 완전 가이드가 따로 다룬다.

  10. 언제 스프레드시트를 떠나야 하나

  12. 옮길 곳과 각각이 요구하는 것

느려지는 것과 막히는 것은 서로 다른 문제다

막히는 쪽은 판정이 쉽다. 값이 있고, 넘으면 화면이 거부한다. 행을 더 못 넣거나, 가져오기가 실패하거나, 스크립트가 중간에 끊긴다. 원인을 찾는 일이 아니라 숫자를 확인하는 일이다.

느려지는 쪽은 값이 없다. 같은 크기의 두 파일이 전혀 다르게 움직이고, 셀을 반쯤 지워도 체감이 그대로인 일이 흔하다. 이유는 하나다. 비용을 만드는 것은 셀의 개수가 아니라 다시 계산해야 하는 대상의 수이기 때문이다.

그래서 이 글은 두 축을 따로 세운다. 앞쪽 절들은 넘으면 안 되는 숫자를, 가운데 절들은 넘어도 되지만 값을 치르는 구조를 다룬다. 마지막은 도구를 바꿀 시점이다.

하드 한도 - 넘으면 거부당하는 값

스프레드시트 하나가 담을 수 있는 양은 셀의 개수로 정해진다. 행 수의 상한은 따로 있지 않고, 열 수에는 별도의 상한이 있다.

항목값 (2026년 9월 기준)넘으면
스프레드시트 하나의 셀 수1,000만 개행과 열, 셀 추가가 거부된다
열 수18,278개 (ZZZ 열)열 추가가 거부된다
Excel 파일 가져오기1,000만 셀 또는 18,278열 (CSV 도 같다)가져오기가 되지 않는다
Excel 변환 시 한 셀의 문자 수50,000자그 셀이 변환 과정에서 제거된다
Connected Sheets 피벗 테이블20만 행그 위의 행은 결과에 나오지 않는다
Connected Sheets 추출50만 행 또는 500만 셀초과분이 잘린다
Apps Script 실행 시간6분 / 실행실행이 중단된다
Apps Script 맞춤 함수30초 / 실행오류가 반환된다
Sheets API 읽기와 쓰기사용자당 분당 60회, 프로젝트당 분당 300회429 오류가 돌아온다

행 수는 나눗셈으로 나온다. 열이 26개면 약 38만 행, 100개면 10만 행, 1,000개면 1만 행에서 셀 한도에 닿는다. 쓰지 않는 열을 남겨 두는 것이 곧 담을 수 있는 행 수를 깎는 일이라는 뜻이다. 새 시트가 기본으로 주는 빈 행과 빈 열도 셀 수에 들어간다.

Excel 변환의 5만 자 규칙은 조용히 동작한다는 점에서 다르다. 오류로 멈추는 것이 아니라 그 셀의 내용이 사라진 채로 변환이 끝난다. 긴 메모나 붙여 넣은 문서가 한 칸에 들어 있는 파일이라면 변환 전후를 대조해 볼 값이다.

소프트 한도 - 넘어도 되지만 대가를 치르는 값

공개 도움말은 「몇 셀부터 느려진다」는 임계를 적지 않는다. 대신 성능 문서 두 편이 무엇이 비싼가를 항목으로 적어 둔다. 임계 대신 규칙을 준 셈이고, 실제로 임계는 기기와 브라우저에 따라 갈리므로 그 편이 정확하다.

다만 다른 각도의 숫자가 하나 있다. 구글의 노코드 앱 도구 문서는 스프레드시트를 앱의 데이터 원본으로 쓸 때 10만 행 또는 1,000열을 넘기지 말라고 적고, 한 앱의 전체 데이터가 압축된 크기의 상한을 기기에 따라 5MB 또는 10MB 로 밝힌다. 같은 문서는 한도에 닿기 훨씬 전부터 성능이 나빠진다는 문장을 붙인다.

이 값은 스프레드시트 자체의 한도가 아니라 그 위에 앱을 얹었을 때의 한도다. 그래도 「1,000만 셀까지 된다」와 「10만 행을 넘기지 말라」 사이의 거리가 소프트 한도의 크기를 짐작하게 해 준다. 하드 한도의 1퍼센트 지점에서 이미 다른 문서가 경고를 적고 있는 것이다.

재계산은 셀 개수가 아니라 의존 관계를 따라 돈다

성능 문서의 첫 문장이 기준이 된다. 셀을 수정할 때마다 그 셀의 수식과 모든 종속 셀의 수식이 평가된다. 값 하나를 바꾸는 일이 여러 갈래의 변경을 부르고, 그것이 다 끝나야 화면이 돌아온다는 서술이 같은 문서에 있다.

여기서 두 가지가 곧바로 따라 나온다.

  • 비어 있는 셀은 거의 비용이 아니다. 빈칸 100만 개보다 서로 물린 수식 1,000개가 비싸다. 셀 수를 줄여도 체감이 그대로인 경우가 여기서 나온다.
  • 한 칸을 고치는 비용은 그 칸에 매달린 것의 수로 정해진다. 그래서 같은 수식이라도 어디에 놓느냐에 따라 값이 달라진다.

이 문장 하나만 쥐고 있으면 아래의 항목들이 전부 같은 이야기의 변주로 읽힌다. 재계산 대상을 줄이는 방법의 목록이다.

무엇이 재계산을 비싸게 만드는가

휘발성 함수 - 편집할 때마다 처음부터 다시

공식 문서가 휘발성으로 이름을 든 함수는 TODAY, RAND, RANDBETWEEN, NOW 넷이다. 값이 스스로 바뀌기 때문에 무엇을 고치든 다시 평가되고, 그 셀에 매달린 것도 함께 돈다. 성능 문서는 이런 함수를 아껴 쓰고 가능하면 자체 셀로 옮기라고 권한다.

행마다  =TODAY()-A2        <- 휘발성 셀이 행 수만큼

H1 에   =TODAY()
행마다  =$H$1-A2           <- 휘발성 셀 1개

재계산 주기 자체도 설정으로 바뀐다. 파일 > 설정 > 계산의 「다시 계산」 항목이 그것이고, API 문서가 열거하는 값은 세 가지다. 변경할 때마다, 변경할 때마다와 매분, 변경할 때마다와 매시간. 매분이나 매시간을 고르면 아무도 손대지 않아도 휘발성 함수가 돈다. 같은 화면의 「반복 계산」은 순환 참조가 있는 수식을 몇 번까지 돌릴지를 정한다.

열린 범위 참조 - A:A 가 실제로 읽는 것

문서의 설명은 짧고 분명하다. 범위의 시작과 끝을 특정 행이나 열로 지정하지 않은 참조가 열린 범위이고, 지정한 것이 닫힌 범위다. SUM(A:A) 는 빈칸이 대부분이어도 그 열 전체를 읽고, SUM(A1:A10) 은 열 칸만 읽는다.

=SUM(A:A)
=COUNTIF(B:B, "완료")

=SUM(A2:A5000)
=COUNTIF(B2:B5000, "완료")

열린 범위가 편한 이유는 행이 늘어도 수식을 안 고쳐도 되기 때문이다. 그 편의의 값이 매 편집마다의 전체 열 읽기다. 행이 계속 붙는 표라면 여유를 넉넉히 잡은 닫힌 범위가 대개 낫다.

연쇄 참조 - 한 칸이 바뀌면 줄줄이

A2 가 A1 을 읽고 A3 가 A2 를 읽는 사슬은 계산을 직렬로 묶는다. 앞 칸이 끝나야 뒤 칸이 시작되므로, 사슬이 길수록 대기가 쌓인다. 문서는 이 형태를 피하고 절대 참조로 원본을 직접 가리키라고 적는다.

A2 =A1*1.1
A3 =A2*1.1          <- 앞 칸을 기다린다
A4 =A3*1.1

A2 =$A$1*1.1
A3 =$A$1*1.1^2      <- 원본을 직접 읽는다
A4 =$A$1*1.1^3

조회 함수의 범위 인수에 함수를 중첩하는 것

성능 문서는 VLOOKUP 과 MATCH 가 단순한 범위 인수에 맞게 최적화되어 있다고 적는다. 범위 자리에 함수를 넣으면 그 최적화가 통하지 않으므로, 미리 계산해 둔 도우미 열을 쓰라는 것이 권고다.

=VLOOKUP(A2, ARRAYFORMULA(TRIM(D2:E999)), 2, FALSE)

F 열에  =ARRAYFORMULA(TRIM(D2:D999))
=VLOOKUP(A2, F2:G999, 2, FALSE)

조회 함수 자체의 문법과 오류 유형은 VLOOKUP·XLOOKUP 완전 가이드에 정리되어 있다.

조건부 서식 - 수식이 아닌데 계산된다

문서의 문장이 그대로 답이다. 조건부 서식은 계산에 시간이 오래 걸릴 수 있고, 모든 규칙이 데이터 범위 전체에 적용된다. 데이터가 늘면 해야 할 계산도 함께 는다. 규칙이 서로 겹치거나 덮어쓰는 상태로 쌓여 있는 파일이 흔한데, 그런 규칙도 계산은 다 한다.

여기가 특히 눈에 안 띄는 자리다. 수식 목록을 아무리 봐도 보이지 않는 비용이라서, 수식만 손보다 원인을 놓치는 일이 잦다.

외부 참조 - 가져오기 함수는 자기 시계로 돈다

같은 스프레드시트 안의 데이터를 참조하는 편이 가져오기 함수보다 빠르다는 것이 문서의 권고다. 각 함수의 갱신 주기도 표로 명시되어 있다.

  • IMPORTRANGE - 30분
  • IMPORTHTML, IMPORTFEED, IMPORTDATA, IMPORTXML - 1시간. 문서가 열려 있는 동안 매시간 업데이트를 확인한다
  • GOOGLEFINANCE - 최대 20분 지연

제약도 하나 있다. 가져오기 함수는 NOW, RAND, RANDARRAY, RANDBETWEEN 이 들어 있는 셀을 참조할 수 없다. 스프레드시트에 과부하가 걸리는 것을 막기 위한 설계이며, TODAY 만 예외다. 하루 한 번을 넘겨 갱신되지 않기 때문이라는 이유가 문서에 적혀 있다. 셀을 지웠다 다시 넣거나 같은 수식으로 덮어쓰면 새로고침이 걸린다는 것도 같은 문서에 있다.

가져오기 함수의 사용량에는 한도가 있다고만 적혀 있고 구체적인 값은 공개되어 있지 않다. 넘으면 요청이 많아 시간이 걸린다는 안내가 뜬다.

비싼 쓰기왜 비싼가대체
행마다 TODAY 나 NOW휘발성이라 모든 편집에서 다시 평가된다한 칸에 두고 절대 참조로 가리킨다
SUM(A:A) 같은 열 전체 참조빈칸까지 열 전체를 읽는다여유를 준 닫힌 범위로 바꾼다
A3 이 A2 를, A4 가 A3 를 읽는 사슬계산이 직렬로 묶여 대기가 쌓인다절대 참조로 원본을 직접 읽는다

어디가 느린지 좁히는 순서

추측으로 고치면 무엇이 들었는지 남지 않는다. 사본을 하나 만들어 두고, 한 번에 하나씩만 바꾸는 편이 빠르다.

  1. 사본에서 한다. 원본은 건드리지 않는다. 아래 단계는 전부 되돌릴 필요가 없는 파괴적 시험이다.
  2. 시트를 하나씩 지우고 반응을 본다. 감추는 것으로는 계산이 줄지 않는다. 어느 시트를 지웠을 때 체감이 달라지는지가 첫 좌표다.
  3. 수식 열을 값으로 덮어 비교한다. 그 열을 복사한 뒤 수정 > 선택하여 붙여넣기 > 값만 붙여넣기로 덮는다. 계산이 사라진 상태와의 차이가 그 열이 차지하던 몫이다.
  4. 조건부 서식 규칙을 센다. 서식 메뉴의 조건부 서식 패널에 규칙이 나열된다. 범위가 열 전체인 규칙부터 본다.
  5. 가져오기 함수의 개수를 센다. IMPORTRANGE 는 30분마다, 나머지는 한 시간마다 각자 자기 일을 한다.
  6. 휘발성 함수가 흩어진 자리를 찾는다. TODAY, NOW, RAND, RANDBETWEEN 이 몇 개의 셀에 들어 있는지가 그대로 비용이다.
  7. 계산 설정을 본다. 파일 > 설정 > 계산에서 다시 계산이 매분이나 매시간으로 되어 있으면, 아무도 손대지 않는 동안에도 계산이 돈다.

기기 쪽도 변수다. 같은 파일이 컴퓨터에 따라 다르게 움직인다면 원인은 파일 바깥에 있다. 두 상태를 비교할 때는 같은 브라우저, 같은 기기, 같은 확장 프로그램 상태에서 재야 비교가 성립한다. 이 조건을 맞추지 않은 체감 차이는 근거로 쓰기 어렵다.

자동화 쪽 한도는 종류가 다르다

수식이 아니라 스크립트나 외부 프로그램이 시트를 건드리기 시작하면, 앞의 것과 전혀 다른 한도에 걸린다. 이쪽은 계정 등급에 따라 값이 갈린다.

맞춤 함수의 30초는 특히 자주 걸린다. 공식 문서는 맞춤 함수가 한 스프레드시트 안에서 되풀이 호출될 때 오류가 흔하다고 적고, 데이터 범위마다 한 번만 실행되도록 코드를 짜라고 권한다. 행마다 호출되는 맞춤 함수는 그 자체로 앞 절의 「행마다 같은 수식」과 같은 형태다.

Sheets API 는 또 다른 축이다. 읽기와 쓰기 각각 프로젝트당 분당 300회, 사용자당 분당 60회이며 넘으면 429 가 돌아온다. 한 행씩 쓰는 코드가 한 번에 묶어 쓰는 코드보다 이 벽에 훨씬 빨리 닿는다.

떠나지 않고 버티는 법

도구를 바꾸는 것은 마지막 선택지다. 그 앞에 값싼 수가 몇 개 있다.

  • 아카이브를 분리한다. 지난 연도 자료를 다른 파일로 옮긴다. 셀 수와 재계산 대상이 함께 줄어드는 유일한 수다.
  • 입력 시트와 계산 시트를 나눈다. 사람이 값을 넣는 자리와 수식이 도는 자리를 분리하면, 어느 쪽이 비용인지 다음에 볼 때 바로 보인다.
  • 행 단위 수식을 배열 수식 한 줄로 바꾼다. ARRAYFORMULA 는 배열 수식이 반환한 값을 여러 행과 열에 펼치고, 배열이 아닌 함수를 배열과 함께 쓸 수 있게 한다. 1만 개의 수식 셀이 한 개가 된다.
  • 굳은 자료는 값으로 만든다. 다시 계산될 이유가 없는 지난 기록은 값만 붙여넣기로 덮는다. 수식이 사라지면 그 부분은 평가 대상에서 빠진다.
  • 쓰지 않는 서식과 규칙을 지운다. 조건부 서식 규칙, 남은 데이터 확인 규칙, 표 아래로 한참 이어지는 빈 행과 빈 열이 대상이다.
행마다  =IF(A2="", "", A2*B2)                        <- 수식 셀 10,000개

한 줄만 =ARRAYFORMULA(IF(A2:A="", "", A2:A*B2:B))    <- 수식 셀 1개

배열 수식은 만능이 아니다. 한 칸이 전체를 책임지므로 오류가 나면 범위 전체가 함께 비고, 중간에 예외를 끼워 넣기가 어렵다. 그래도 수식 개수를 줄이는 수단으로는 가장 직접적이다.

언제 스프레드시트를 떠나야 하나

한도에 닿아서가 아니다. 아래 셋 중 하나라도 해당하면, 셀이 얼마 안 차 있어도 이미 도구가 맞지 않는다.

  • 여러 명이 같은 행을 동시에 쓴다. 스프레드시트에는 행 단위 잠금이 없다. 같은 칸을 동시에 고치면 나중에 쓴 쪽이 남는다. 사람이 서로 말로 조율해서 겨우 굴러가는 상태라면, 그 조율 비용이 이미 도구가 못 하는 일을 대신하고 있는 것이다.
  • 누가 언제 무엇을 바꿨는지가 자료의 일부다. 버전 기록이 있지만 그것으로 감사 기록을 대신할 수 없다. 구글 문서 자신이 편집 기록에 나타나지 않는 항목을 적어 둔다. 행과 열의 추가와 삭제, 셀 서식 변경, 그리고 수식에 의한 변경이다. 마지막 항목이 결정적이다. 이름을 지정한 버전은 스프레드시트당 15개까지다.
  • 참조 무결성이 필요하다. 고객 표의 한 행을 지웠을 때 그 고객을 가리키던 주문 표의 행이 어떻게 되어야 하는가. 스프레드시트에는 이 질문에 답하는 장치가 없다. 데이터 확인 규칙은 입력을 막을 뿐 이미 들어간 관계를 지키지 못한다.

엑셀로 옮기면 된다가 대개 답이 아닌 이유

느린 원인이 재계산이라면 엑셀에서도 재계산은 한다. 앞 절에 적은 비싼 쓰기들은 파일 형식을 바꾼다고 사라지지 않는다. 열 전체 참조는 어디서든 열 전체를 읽고, 서로 물린 수식은 어디서든 서로를 기다린다.

하드 한도의 모양이 다르다는 것은 사실이다. 엑셀 워크시트는 1,048,576행 곱하기 16,384열이고 한 셀에 32,767자까지 담긴다. 행이 많고 열이 적은 자료라면 엑셀 쪽 여유가 크고, 열이 아주 많은 자료라면 오히려 스프레드시트 쪽 상한이 높다. 다만 이건 막히는 지점의 이야기이지 느려지는 지점의 이야기가 아니다.

옮겨서 실제로 달라지는 것은 다른 데 있다. 여러 사람의 동시 편집이 파일 잠금 방식으로 바뀌고, 링크 한 줄로 끝나던 공유가 파일 전달이 되며, 대신 계산이 그 컴퓨터의 자원을 쓴다. 셋 다 상황에 따라 이득도 손해도 된다. 엑셀 쪽 도구의 사용법은 엑셀 피벗테이블 실무 가이드가 따로 다룬다.

자주 묻는 질문

구글 스프레드시트 한 파일에 몇 행까지 들어가나?

행 자체의 상한은 공개 도움말에 값이 없다. 대신 셀 1,000만 개와 열 18,278개라는 한도가 있고, 담을 수 있는 행 수는 그 나눗셈으로 정해진다. 열이 26개면 약 38만 행, 100개면 10만 행, 1,000개면 1만 행에서 셀 한도에 닿는다. 2026년 9월 기준 값이며, 구글은 과거에 이 한도를 올린 적이 있으므로 오래된 글의 숫자와 어긋날 수 있다.

셀 수가 한도의 절반도 안 되는데 왜 느린가?

셀의 개수와 계산 비용은 다른 축이기 때문이다. 성능 문서는 셀을 수정할 때마다 그 셀과 모든 종속 셀의 수식이 평가된다고 적는다. 비용은 셀이 몇 개인가가 아니라 서로 매달린 관계가 몇 개인가로 정해진다. 빈칸 100만 개는 거의 비용이 아니고, 열 전체를 읽는 수식 1,000개는 비싸다.

TODAY 나 NOW 를 아예 쓰지 말아야 하나?

쓰되 개수를 줄이면 된다. 문서의 권고는 휘발성 함수를 자체 셀로 옮기고 나머지는 그 셀을 절대 참조로 가리키라는 것이다. 행마다 TODAY 를 쓰면 휘발성 셀이 행 수만큼 생기지만, 한 칸에 두면 하나로 줄어든다. 가져오기 함수가 NOW 나 RAND 계열이 든 셀을 참조하지 못하는 것도 같은 이유에서 나온 설계다.

IMPORTRANGE 결과가 왜 바로 안 바뀌나?

갱신 주기가 정해져 있기 때문이다. 도움말의 표는 IMPORTRANGE 를 30분, IMPORTHTML 과 IMPORTFEED 와 IMPORTDATA 와 IMPORTXML 을 1시간, GOOGLEFINANCE 를 최대 20분 지연으로 적는다. 급하면 셀을 지웠다 다시 넣거나 같은 수식으로 덮어쓰면 새로고침이 걸린다.

언제 데이터베이스로 옮겨야 하나?

한도에 닿았을 때가 아니라 도구의 성질이 안 맞을 때다. 여러 사람이 같은 행을 동시에 쓰거나, 변경 이력 자체가 자료이거나, 참조 무결성이 필요한 관계가 있으면 이미 맞지 않는다. 셋 다 아니라면 아카이브 분리와 배열 수식만으로도 한참 더 간다.

마무리

정리하면 축은 둘이다. 하드 한도는 1,000만 셀과 18,278열, 그리고 자동화 쪽의 6분과 30초와 분당 60회다. 이 숫자들은 넘으면 거부당하고, 넘기 전에는 아무 영향이 없다.

소프트 한도에는 숫자가 없고 규칙만 있다. 무엇을 고치든 다시 도는 것을 줄이고, 읽지 않아도 될 범위를 읽지 않게 하고, 계산을 직렬로 묶지 않고, 눈에 안 보이는 서식 계산을 걷어 내는 일이다. 이 넷이 성능 문서가 적어 둔 항목의 전부이기도 하다.

그리고 셋 중 하나에 걸리면 숫자와 무관하게 옮길 때다. 동시 쓰기, 변경 이력, 참조 무결성. 이 셋은 스프레드시트가 잘하는 일의 목록에 처음부터 없었다.

확인하지 못한 것

아래는 공개된 공식 문서만으로 값이 갈리지 않는 항목이다. 널리 도는 숫자가 있어도 근거가 공개되지 않은 것은 옮겨 적지 않았다.

  • 시트(탭)의 최대 개수 - 공개 도움말에 값이 없다. 셀 한도가 실질적 상한 역할을 하므로 숫자를 적지 않았다.
  • 조건부 서식 규칙의 최대 개수 - 상한이 문서화되어 있지 않다. 성능 문서는 규칙을 줄이라고만 적는다.
  • 일반 입력에서 한 셀의 문자 수 상한 - 문서에 있는 것은 Excel 변환 시 5만 자를 넘는 셀이 제거된다는 서술뿐이다. 그것을 일반 입력의 상한으로 옮겨 적지 않았다.
  • 다시 계산 설정의 화면 문구 - 도움말은 항목 이름까지만 적는다. 세 가지 값은 API 문서의 열거값에서 온 것이며, 화면에 뜨는 문구와 한 글자까지 같은지는 갈리지 않는다.
  • 반복 계산의 최대 반복 횟수 상한 - API 문서에 필드는 있으나 상한값이 명시되어 있지 않다.
  • QUERY 나 FILTER 같은 집계 함수의 상대 비용 - 공식 문서에 성능 서술이 없다. 함수별 속도 순위표가 여럿 돌지만 측정 조건이 공개되지 않아 옮기지 않았다.
  • 몇 셀 또는 몇 수식부터 체감이 나빠지는가의 임계 - 공식 문서에 없고 기기와 브라우저에 따라 갈린다. 이 글에 속도 배수를 하나도 적지 않은 이유다.
  • 가져오기 함수 사용량 한도의 구체적 수치 - 문서는 엄격한 한도가 있다고만 적고 값을 밝히지 않는다.

  • Google 스프레드시트 - 성능 개선 방법 - 셀을 수정할 때마다 그 셀과 모든 종속 셀이 평가된다는 문장, 휘발성 함수를 아껴 쓰라는 권고, 반복 하위 표현식과 도우미 열, 조건부 서식 규칙 삭제 권고의 출처
  • Google 스프레드시트 - 데이터 참조 최적화 - 열린 범위와 닫힌 범위의 정의, 휘발성 함수 네 가지 목록, 연쇄 참조를 절대 참조로 바꾸라는 권고, 가져오기 함수보다 같은 시트 참조가 빠르다는 서술
  • Google 스프레드시트 - 위치 및 계산 설정 - 파일 > 설정 > 계산 경로, 다시 계산과 반복 계산 항목의 정의, ImportRange 30분과 ImportHtml 계열 1시간, GoogleFinance 최대 20분 지연의 출처
  • Google 스프레드시트 - 가져오기 함수 알아보기 - 문서가 열려 있는 동안 매시간 업데이트를 확인한다는 서술, 셀 재입력이 새로고침을 부른다는 서술, NOW 와 RAND 계열 셀을 참조할 수 없고 TODAY 만 예외라는 설계, 사용량 한도가 엄격하다는 문장
  • Google Sheets API v4 - Spreadsheets 참조 - 재계산 주기 열거값 세 가지와 각각의 정의, 반복 계산의 최대 반복 횟수와 수렴 임계값 필드
  • Apps Script - 할당량과 제한 - 실행 6분, 맞춤 함수 30초, 트리거 총 실행 시간 90분과 6시간, 동시 실행 30, 스프레드시트 생성 250과 3,200, 속성 읽기와 쓰기 5만과 50만의 출처
  • Google Sheets API - 사용량 한도 - 읽기와 쓰기 각각 프로젝트당 분당 300회, 사용자당 분당 60회, 초과 시 429 응답
  • Google 문서 도구 - 버전 기록 - 행과 열의 추가와 삭제, 셀 서식 변경, 수식에 의한 변경이 편집 기록에 나타나지 않을 수 있다는 서술과, 이름이 지정된 버전의 개수 상한
  • AppSheet - 데이터 크기 제한 - 스프레드시트를 데이터 원본으로 쓸 때 10만 행 또는 1,000열을 넘기지 말라는 권고, 압축 데이터 5MB 또는 10MB, 한도 훨씬 전부터 성능이 나빠진다는 서술
