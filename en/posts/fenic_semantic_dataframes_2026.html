fenic and Semantic Operators: Weaving LLMs Into DataFrames Declaratively

Why typedef's open-source, PySpark-style engine turns LLM calls into first-class dataframe operations - and where it falls short

Jul 11, 2026 Dev & Infra

Introduction: Why Unstructured Text Still Lives Inside a for Loop

There's a question that keeps resurfacing in data engineering circles in 2026. Structured tables are handled cleanly with SQL and dataframes, so why do unstructured artifacts - emails, call transcripts, reviews - still get processed through hand-rolled scripts calling an LLM API one row at a time? fenic is an open-source project that answers this head-on. Built by the US startup typedef, this dataframe library layers LLM calls on top of a PySpark/SQL-familiar operation model, exposing them as first-class semantic operators.

This piece first verifies what fenic actually does, then analyzes the larger question it raises - how should LLMs be integrated into data pipelines - from my own vantage point. Rather than restating a press release, I compare it against related projects LOTUS, LangChain, and DSPy to work out what this direction actually means in practice.

1. What Is fenic - typedef's PySpark-Style DataFrame

1.1 Who Built It and Why

fenic comes from typedef, a startup founded by data-infrastructure engineers Yoni Michael and Kostas Pardalis. The company emerged from stealth with a $5.5 million seed round led by Pear VC, joined by Verissimo Ventures, Monochrome Ventures, Tokyo Black, and a number of angels - and open-sourced fenic under Apache 2.0 the same day. The GitHub repository (typedef-ai/fenic) went public in July 2025, with a documentation site (docs.fenic.ai) walking through the API and architecture in detail. Open-sourcing the core engine from day one suggests typedef's business model sits in managed services or infrastructure built on top, not in gatekeeping the engine itself.

1.2 What It Claims to Be

fenic's own framing is direct: a dataframe "built from the ground up with inference in mind." The claim is that unstructured data - text, markdown, call transcripts - and LLM inference were treated as first-class citizens from the start, rather than bolted onto pandas or Spark after the fact. A model is configured once at the Session level and reused across the pipeline, executed through lazy evaluation and query optimization. That design philosophy is what separates fenic from a thin LLM wrapper library.

2. What Semantic Operators Are - Turning LLM Calls Into DataFrame Operations

2.1 Eight Operators

Per fenic's documentation, eight operators live under the semantic namespace as first-class dataframe operations. semantic.map applies a natural-language instruction to each row to produce a new column, and semantic.predicate filters rows on a natural-language condition. semantic.join joins two dataframes on meaning rather than exact value equality, while semantic.extract pulls structured fields out of unstructured text against a declared schema. semantic.classify assigns categories from a handful of examples, semantic.analyze_sentiment labels sentiment, semantic.group_by clusters rows by semantic similarity, and semantic.reduce aggregates clustered data using an LLM operation.

2.2 What It Means to Frame This as an Operator

The key point is that these eight sit at the same syntactic layer as select, filter, join, group_by, and agg, rather than being bolted-on API calls. A developer chains filtering, structured extraction, and classification within a single pipeline, exactly as they would chain ordinary dataframe operations. That turns LLM calls from "an occasional exception step" into a regular node in the dataframe's execution graph - meaning the query optimizer can plan around it. That's precisely why fenic reaches for the term "semantic operator."

3. Advantages of Declarative Integration Over Manual LLM Calls

3.1 Reproducibility

The typical pattern I've seen in LLM data pipelines is this: loop over rows, assemble a prompt per row, call the API, parse the response by hand, and bolt on retry logic when things fail. Because prompt strings, parsing logic, and retry rules end up scattered across scripts, reproducing the exact same run twice becomes surprisingly hard. Declaring a schema and calling an operator instead separates "what to extract" from "how to execute it." The schema and the operation are version-controlled as code, while execution mechanics - batching, retries, model selection - are handled consistently by the engine.

3.2 Batching and Cost Management

With manual calls, developers must implement batch sizing, concurrency limits, and rate-limit handling themselves, every time. fenic states it provides these as engine-level features - automatic batch optimization, built-in retry and rate limiting, and token/cost accounting. When a single dataframe operation can expand into thousands of LLM calls under the hood, having the engine own this instead of application code is a meaningful practical difference.

3.3 Observability

Another benefit of a declarative pipeline is that it becomes easier to trace what actually ran. Because a lazy-evaluation query engine builds a plan before execution, you can inspect the execution plan - rather than re-reading the whole codebase - to see how many LLM calls a given step triggers and what schema it extracted against. That's genuinely useful when auditing a production pipeline or tracking down a cost spike.

4. What a PySpark/SQL-Friendly Interface Means

Layering semantic operators on top of familiar operations is both a technical choice and an adoption strategy. Most data engineering organizations already run Spark- or SQL-based pipelines. Rather than asking teams to learn an entirely new paradigm, attaching one LLM operation to syntax they already know sharply lowers the learning curve. Offering a SQL interface also means analysts and BI staff who aren't comfortable in Python scripts can invoke semantic operators directly inside a SQL statement. This is also a constraint, though - inheriting Spark's distributed-processing syntax and optimization model means the design was never intended for streaming or very-low-latency real-time inference scenarios.

5. Comparing Related Approaches - LOTUS, LangChain, DSPy

5.1 LOTUS - Where the Concept Originated

The concept of semantic operators wasn't invented by fenic. LOTUS (LLMs Over Tables of Unstructured and Structured data), a Stanford/Berkeley research project, formalized the term academically first. Advised by Spark creator Matei Zaharia and Carlos Guestrin, LOTUS offers a pandas-style API (sem_filter, sem_join) and published optimization theory in a paper appearing in the VLDB journal, quantitatively showing that operator optimization can substantially cut cost and latency. fenic reads as a production-oriented, commercial implementation of that academic concept, weighted more heavily toward PySpark compatibility and engineering infrastructure - retries, batching, cost tracking.

5.2 LangChain - Orchestration vs. Query Engine

LangChain is an imperative orchestration framework that chains LLM calls, tool use, and memory together. Its strengths are a massive integration ecosystem and fast prototyping, but as data volume grows, batching, retries, and cost management fall on application code to handle. fenic was never designed as "a tool for building chains" - it's a query engine for processing tables. A batch pipeline crunching millions of rows of text fits fenic's model; a conversational agent centered on tool use fits LangChain's model better.

5.3 DSPy - Prompt Optimization vs. Data Processing

DSPy treats the prompt itself as a learnable parameter, automatically optimizing prompts or fine-tuning adapters against a labeled dataset. Unlike fenic and LangChain, which handle "what to execute," DSPy addresses a different axis entirely - "how do I make this prompt work better." The two aren't mutually exclusive in practice: in principle, a prompt called by fenic's semantic.map could itself be optimized DSPy-style before being dropped into a fenic pipeline. In one line: fenic answers how to process data, LangChain answers what an agent should do, and DSPy answers how to optimize a prompt.

6. Practical Applications - Where This Fits

In my view, the fenic-style approach shines brightest on repetitive, high-volume unstructured text processing. Classifying complaint types across tens of thousands of customer reviews, extracting structured fields - customer name, inquiry type, resolution status - from call transcripts, and joining product descriptions from multiple sources by meaning to unify a catalog are all textbook fits. These jobs are inherently batch, run the same pipeline daily or weekly, and put a premium on reproducibility and cost predictability. Conversely, a real-time customer-facing chatbot or an autonomous agent that must pick a different tool on every request gets little benefit from fenic's batch/query-optimization model. That territory belongs to LangChain or dedicated agent frameworks.

7. Limits and Caveats - Cost, Non-Determinism, Accuracy

Three things need to be said plainly. First, cost. A single semantic operator may look like one dataframe column, but under the hood it fires an LLM call per row. Running semantic.extract over millions of rows translates directly into millions of inference calls' worth of API spend. The engine can optimize batching, but it cannot reduce the underlying number of inference calls.

Second, non-determinism. A SQL WHERE clause always returns the same result for the same input, but semantic.predicate can shift its output for the same condition depending on model version or temperature settings. Mixing deterministic and probabilistic operations under the same pipeline syntax is convenient, but the whole team needs to be aware of where that boundary sits.

Third, accuracy validation. Trusting the output of classify or extract directly as input to the next step lets early-stage errors compound and amplify downstream. Before putting this into production, each semantic operator's accuracy needs to be measured separately against a golden set.

Conclusion: From a Pile of Scripts to a Declarative Pipeline

The real question fenic raises isn't "should I use this library" - it's "should unstructured-text pipelines keep living as piles of scripts, or should they be managed as declarative operations the way structured data already is." The academic legitimacy of semantic operators was already established by LOTUS's research; fenic productizes that concept into something a PySpark-literate data engineer can pick up immediately.

As of July 2026, this project is still early in its open-source lifecycle, but any data engineering organization processing large volumes of unstructured data repeatedly should find it worth a golden-set-based pilot. That said, teams building real-time conversational agents will likely find LangChain or a dedicated agent framework a better fit than fenic.
