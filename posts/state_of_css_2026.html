CSS가 걷어낸 우회책들 - 전처리기와 JS가 하던 일을 브라우저가 가져갈 때

기능별로 무엇이 없어졌고, 무엇이 아직 남아 있으며, 지원 현황을 어떻게 읽을 것인가

2026-08-16 개발/인프라

서론: 스타일시트에서 조용히 사라진 줄들

몇 년 묵은 프로젝트를 열면 거의 항상 세 가지가 같이 나온다. 빌드 파이프라인에 걸려 있는 전처리기, 부모 요소에 클래스를 붙였다 떼는 자바스크립트 몇 줄, 그리고 파일 여기저기에 흩어진 미디어 쿼리 중단점. 이 셋은 서로 다른 물건처럼 보이지만 사연이 같다. CSS가 못 하던 일을 메우려고 있던 것들이다.

그 우회책 상당수가 지난 몇 년 사이 브라우저 안으로 들어왔다. 중첩은 파서가 직접 처리하고, 부모를 조건으로 고르는 선택자가 생겼고, 뷰포트 대신 컨테이너 폭을 물을 수 있게 됐고, 우선순위 싸움에는 이름 붙은 규칙이 생겼다. 그래서 지금 유용한 질문은 「CSS에 뭐가 새로 생겼나」가 아니라 「그게 정확히 무엇을 없앴나」다. 새로 생긴 문법은 외우면 되지만, 지워도 되는 코드는 지우지 않으면 영원히 남는다.

이 글은 다섯 가지 기능이 각각 걷어낸 우회책을 짚고, 아직 걷어내지 못한 자리를 표시한 다음, 지원 현황을 읽는 법과 채택 판단 기준을 정리한다. 브라우저 지원 서술은 모두 2026년 8월 16일 확인 기준이다. CSS 지원 상태는 이 블로그가 다루는 어떤 주제보다 빨리 바뀌므로, 반년 뒤에 읽는다면 각 기능의 MDN 문서 상단 배지를 다시 볼 것.

프런트엔드 20년의 흐름 자체는 프론트엔드에 무슨 일이 있었나 - 2008년 jQuery에서 2026년 AI 코딩까지에서 다뤘고, 브라우저 기본 기능을 재발명하지 말자는 원칙은 Don't Roll Your Own 원칙 2026에 있다. 여기서는 CSS 한 겹만 본다.

1. 전처리기가 하던 일 - 중첩과 변수

전처리기를 프로젝트에 넣은 이유를 지금 대보라고 하면 대개 셋이 나온다. 중첩, 변수, 믹스인. 이 중 앞의 둘이 표준으로 흡수됐다.

1.1 중첩 - 파서가 직접 읽는다

중첩은 브라우저가 직접 파싱하므로 사전 컴파일이 필요 없다. 문법의 핵심은 부모를 가리키는 & 하나다.

/* 예전: 전처리기가 컴파일해야 의미가 생겼다 */
.card { .title { font-weight: 700; } }

/* 지금: 브라우저가 그대로 읽는다 */
.card {
  padding: 1rem;
  & .title { font-weight: 700; }
  &:hover { border-color: currentColor; }
}
  • 없어진 것 - 빌드 단계. 스타일 하나 고치려고 watch 프로세스를 띄우고, 컴파일 산출물을 gitignore에 넣고, 소스맵이 어긋나면 원본 줄 번호를 손으로 찾던 일이 사라진다.
  • 남는 이유 - 믹스인과 루프. 색 단계나 간격 스케일을 반복문으로 찍어내는 코드, 컴파일 타임 색 계산, 여러 파일을 하나로 묶는 임포트 정리는 여전히 전처리기 쪽 일이다.
  • 주의 - 특이성은 여전히 오른다. 중첩은 선택자를 눈에 안 보이게 길게 만든다. 전처리기 시절의 함정이 표준이 됐다고 사라지지는 않는다. 깊이는 두세 단계까지로 잡는 편이 안전하다.

1.2 커스텀 프로퍼티 - 전처리기 변수와 다른 물건

이름이 둘 다 「변수」라서 같은 것으로 취급되는 일이 잦은데, 성질이 다르다. $gap은 컴파일이 끝나면 사라지고 결과물에는 계산된 값만 남는다. --gap은 런타임에 살아 있다. 이 차이 하나에서 나머지가 전부 따라 나온다.

:root { --gap: 1rem; --brand: #2c6fdb; }
@media (min-width: 48rem) { :root { --gap: 2rem; } }
.grid { gap: var(--gap); }
.btn  { background: var(--brand); }
/* 폴백 값은 두 번째 인자에 둔다 */
.card { border-radius: var(--radius, 6px); }
  • 상속되고, 조건 안에서 바뀐다. 부모에서 값을 바꾸면 그 아래가 전부 따라오고, 미디어 쿼리나 컨테이너 쿼리 안에서 값 하나만 갈아 끼울 수 있다. 조건마다 규칙 세트를 복제할 이유가 사라진다.
  • 없어진 것 - 테마용 파일 복제. 다크 모드용 CSS를 통째로 한 벌 더 만들거나, .theme-dark 아래에 모든 규칙을 다시 적던 방식이 루트 변수 재정의 몇 줄로 줄어든다.
  • 없어진 것 - 인라인 스타일 주입. 자바스크립트가 요소마다 스타일 속성을 심는 대신 element.style.setProperty('--x', v)로 값 하나만 내려 준다. 스타일 규칙은 CSS 파일에 남는다.
  • 경계. 값의 형을 선언하고 애니메이션 가능하게 만드는 것은 @property 영역인데, 이 글에서는 그 지원 상태를 확인하지 않았다.

2. :has() - 부모를 고르려고 JS를 부르던 자리

상황은 늘 비슷하다. 카드 안에 썸네일이 있으면 레이아웃을 2단으로 바꾸고 싶다. 입력란에 값이 들어오면 라벨을 위로 올리고 싶다. 목록이 비어 있으면 빈 상태 안내를 보이고 싶다. 선택자가 아래로만 흐르던 시절 답은 하나였다 — 렌더링할 때 부모에 클래스를 붙인다.

그 클래스 한 줄이 끌고 오던 비용은 생각보다 컸다. 내용이 바뀔 때마다 클래스를 갱신하는 코드가 필요하고, 서버 렌더링과 클라이언트 렌더링 양쪽에 같은 판단 로직을 두어야 하고, 그 로직에 테스트가 붙고, 시간이 지나면 아무도 지우지 못하는 클래스가 된다. 무엇이 그 클래스를 붙였는지 추적이 안 되기 때문이다.

/* 입력란에 값이 있으면 라벨을 올린다 - JS 없이 */
.field:has(input:not(:placeholder-shown)) label {
  transform: translateY(-1.2em);
  font-size: 0.8rem;
}

/* 썸네일이 있는 카드만 2단으로 */
.card:has(> img) { grid-template-columns: 8rem 1fr; }

확인된 지원 상태는 명확한 편이다. MDN은 :has()를 Baseline 널리 사용 가능으로 표시하고 2023년 12월부터 브라우저 전반에서 쓸 수 있다고 적고 있다(2026년 8월 16일 확인). 다만 문서가 함께 명시하는 제약이 몇 가지 있고, 그중 하나는 실패 모드가 거칠어서 반드시 알고 써야 한다.

  • :has() 안에 다시 :has()를 넣을 수 없다.
  • 의사요소는 :has()의 인자가 될 수 없고, :has()의 앵커도 될 수 없다.
  • 지원하지 않는 브라우저에서는 그 선택자가 든 규칙 블록 전체가 무효가 된다. 옆에 같이 적어 둔 다른 선언까지 함께 죽는다는 뜻이다. :is()나 :where() 같은 관대한 선택자 목록 안에 넣으면 그 부분만 버려지고 나머지는 살아남는다.
  • 특이성은 인자 중 가장 높은 것을 따른다. :is()·:not()과 같은 규칙이다.
  • 성능 지침도 문서에 있다 — body·:root·전체 선택자에 앵커하지 말 것, 자식(>)과 인접 형제(+) 결합자로 훑을 범위를 좁힐 것.

3. 컨테이너 쿼리 - 뷰포트가 아니라 자리를 묻는다

미디어 쿼리의 한계는 문법이 아니라 질문의 대상에 있었다. 미디어 쿼리는 화면이 얼마나 넓은지만 안다. 정작 필요한 것은 「이 카드가 놓인 자리가 얼마나 넓은가」인데, 같은 카드 컴포넌트가 좁은 사이드바에도 들어가고 본문 3단 그리드에도 들어가면 화면 폭은 아무것도 말해 주지 못한다.

그래서 컴포넌트가 자기 위치를 알아야 했다. 그 앎은 대개 variant="compact" 같은 속성으로 주입되거나, ResizeObserver가 폭을 재서 클래스를 토글하는 방식으로 구현됐다. 둘 다 레이아웃 지식을 컴포넌트 바깥에 복제하는 일이다.

.sidebar, .main-grid > * { container-type: inline-size; }

@container (width > 30rem) {
  .card { display: grid; grid-template-columns: 8rem 1fr; }
}

MDN은 @container를 Baseline 널리 사용 가능으로 표시하고 2023년 2월부터라고 적는다. 다만 별표가 붙어 있다 — 일부 부분은 지원 수준이 다를 수 있다는 표시다. 같은 문서 아래에 크기 쿼리 말고도 스타일 쿼리, 스크롤 상태 쿼리, 앵커 관련 쿼리가 함께 들어 있기 때문이고, 「컨테이너 쿼리를 지원한다」는 한 문장으로 이 넷을 묶으면 안 된다.

  • 컨테이너는 명시적으로 선언해야 한다. container-type을 지정하지 않은 요소는 조회 대상이 아니다. 값은 inline-size(인라인 축만), size(양축), normal(기본값, 크기 쿼리 대상 아님)이다.
  • 실무 대부분은 inline-size다. size는 양축에 억제가 걸려 콘텐츠가 높이를 만들어 내지 못하므로, 높이를 따로 주지 않으면 요소가 무너진다.
  • 자기 자신을 물을 수 없다. 쿼리는 조상 컨테이너에 대해서만 성립한다. 그래서 카드 바깥에 래퍼를 하나 더 두는 구조가 자주 나온다.
  • 없어진 것. ResizeObserver와 클래스 토글, 컴포넌트에 레이아웃 정보를 넘기는 props, 그리고 중단점 상수를 CSS와 JS 양쪽에 복제해 두고 어긋나기를 기다리던 구조.

4. @layer - 우선순위 싸움을 규칙으로 바꾼다

디자인 시스템 버튼을 특정 페이지에서만 살짝 바꾸려는데 안 먹는다. 선택자를 길게 늘인다. 그래도 안 먹는다. !important를 붙인다. 반년 뒤 그 페이지를 고치러 온 사람이 같은 순서를 반복한다. 이 계단은 특이성이라는 암묵적 경쟁에서 나온다.

@layer는 그 경쟁을 선언 순서라는 명시적 규칙으로 바꾼다. MDN은 Baseline 널리 사용 가능, 2022년 3월부터로 표시한다.

/* 순서를 맨 위에서 한 번에 선언한다 */
@layer reset, vendor, base, components, utilities;

@layer vendor { /* 서드파티 CSS를 여기로 */ }
@layer components { .btn { padding: .5rem 1rem; } }
@layer utilities { .mt-0 { margin-top: 0; } }

기억할 규칙은 세 줄이고, 두 번째 줄이 설계를 결정한다.

  • 먼저 선언한 레이어가 약하고, 나중에 선언한 레이어가 강하다. 특이성이 아니라 순서가 이긴다.
  • 레이어에 들어가지 않은 스타일은 어떤 레이어 스타일보다도 강하다. 서드파티 CSS를 낮은 레이어에 가둬 두면, 내 스타일은 레이어 밖에 그냥 두는 것만으로 이긴다.
  • !important는 이 순서를 뒤집는다. 중요 선언끼리 겨루면 먼저 선언한 레이어가 가장 강해진다. 리셋 레이어에 !important를 쓰면 위 레이어를 전부 눌러 버린다는 뜻이다.
  • 없어진 것. !important 계단, .app .page .card .btn.btn-primary 같은 특이성 인플레, 그리고 로드 순서를 지키려고 번들러 설정을 만지던 일.
  • 주의 - 실패가 조용하다. 레이어 선언을 빠뜨리거나 이름을 잘못 적으면 그 규칙은 익명 레이어나 레이어 밖으로 떨어지고, 오류 없이 우선순위만 뒤집힌다. 도입 직후에는 눈으로 확인할 화면 목록을 만들어 두는 편이 낫다.

5. 대체된 것과 대체되지 않은 것

지금까지의 이야기를 한 표로 접으면 이렇게 된다. 오른쪽 끝 열이 이 글의 요지다 — 새 문법을 배우는 것보다 지워도 되는 코드를 찾는 쪽이 이득이 크다.

5.1 아직 JS가 남는 자리

경계선은 한 줄로 그을 수 있다. CSS는 스타일을 적용하지만 값을 돌려주지 않는다. 어떤 기능이 자바스크립트를 없앨 수 있는지 판단할 때 이 축으로 나누면 대체로 맞는다.

  • 측정값을 읽는 일. 요소가 실제로 몇 픽셀인지, 텍스트가 몇 줄로 흘렀는지를 숫자로 알아야 하는 로직은 그대로 JS다. 컨테이너 쿼리는 그 폭에 맞춰 스타일을 바꿔 주지, 폭이 얼마인지 알려 주지 않는다. A와 B의 폭을 비교해 C를 정하는 계산도 여기 속한다.
  • DOM 밖 데이터가 조건인 경우. 재고가 3개 이하면 빨갛게 같은 규칙에서 조건은 서버 응답에 있고, CSS가 그것을 볼 방법은 없다. 다만 그 값을 data- 속성이나 커스텀 프로퍼티로 내려 주는 순간부터는 CSS 몫이 된다. 경계는 「누가 값을 계산하느냐」에 있지 「누가 스타일을 적용하느냐」에 있지 않다.
  • 접근성 상태 갱신. aria-expanded 같은 속성을 바꾸는 것은 JS다. CSS는 그 속성을 읽어서 스타일링할 수 있을 뿐 바꾸지 못한다. 포커스 트랩과 키보드 이동 순서 관리도 같다.
  • 시점에 걸린 로직과 목록 조작. 애니메이션이 끝난 뒤 실행되는 코드, 요소가 화면에 들어올 때의 지연 로딩, 그리고 정렬·필터·가상 스크롤. :has()로 「자식이 없으면 빈 상태를 보인다」 정도는 되지만 항목의 순서를 바꾸지는 못한다.
  • 폼 검증의 내용과 시점. 어떤 메시지를 언제 보일지는 제약 검증 API의 영역이다. CSS가 가져간 것은 유효·무효 상태의 표시뿐이다.

정리하면 CSS가 가져간 구간은 「조건 → 스타일」이다. 「데이터 → 조건」과 「스타일 → 값」은 그대로 남아 있다. 프레임워크 쪽에서 이 경계를 어떻게 다루는지는 Foldkit - 정확성을 추구하는 새로운 프론트엔드 프레임워크에서 따로 다뤘다.

6. 지원됨의 층위 - 브라우저 지원을 읽는 법

「그 기능 지원돼요?」는 질문 하나처럼 들리지만 최소 네 가지가 섞여 있다. 층을 구분하지 않으면 폴백을 과하게 깔거나, 반대로 안 깔아도 될 자리에 깔아 두고 영원히 유지하게 된다.

층위뜻실무 판단이 글에서 확인한 예 (2026-08-16)
널리 사용 가능여러 기기·브라우저 버전에 안정적으로 자리 잡음. MDN이 언제부터인지를 함께 표시한다폴백 없이 써도 되는 층:has() 2023년 12월부터 / @container 2023년 2월부터(별표) / @layer 2022년 3월부터
최신 브라우저에만주요 엔진의 최신 버전에는 있으나 오래된 버전에는 없다진행적 향상으로만. 기업 고정 브라우저·구형 모바일이 대상이면 폴백 필수이 글에서 확인한 예 없음
일부 엔진만엔진에 따라 갈린다핵심 레이아웃 경로에 쓰지 말 것앵커 포지셔닝 - MDN 개요 문서에 Baseline 배지가 표시되지 않는다
플래그·시험 단계사용자가 설정을 켜야 동작한다프로덕션 금지. 데모와 학습용이 글에서 확인한 예 없음
  • 「지원됨」이 아니라 「언제부터」를 본다. 날짜가 오래됐을수록 사용자 기기의 브라우저가 이미 그 버전을 지나쳤을 확률이 높다. 정보의 실체는 날짜 쪽에 있다.
  • 별표를 놓치지 않는다. @container처럼 「일부 부분은 지원 수준이 다를 수 있다」가 붙어 있으면, 그 이름 아래 묶인 하위 기능을 하나씩 확인해야 한다는 신호다.
  • 모듈 이름과 속성 이름을 구분한다. 명세 모듈 하나에 여러 속성이 들어 있고 각각 도착 시점이 다르다. 확인 단위는 모듈이 아니라 실제로 쓸 속성과 값이다.
  • 내 사용자의 버전 분포와 대조한다. 최신 브라우저에 있다는 사실과 내 방문자가 그 버전을 쓴다는 사실은 별개다. 기업 내부망에 구버전이 고정돼 있거나 메신저 인앱 브라우저 비중이 높은 서비스라면 전 세계 평균 통계는 근거로 약하고, 분석 도구의 브라우저 버전 보고서가 유일한 실측이다.
  • 확인 날짜를 문서에 적는다. 팀 위키에 「2026-08-16 확인」 한 줄을 남기지 않으면, 반년 뒤에 같은 기능들을 처음부터 다시 조사하게 된다.

6.1 @supports - 폴백을 설계하는 법

@supports는 브라우저가 특정 선언이나 선택자를 이해하는지를 CSS 안에서 묻는다. 문법은 세 갈래다.

/* 기본은 밖에, 향상은 안에 */
.card { display: block; }

@supports (container-type: inline-size) {
  .card-wrap { container-type: inline-size; }
  @container (width > 30rem) { .card { display: grid; } }
}

@supports selector(:has(*)) { /* 선택자 지원 여부 */ }
@supports not (anchor-name: --a) { /* 부정 조건 */ }
  • 파싱을 묻지 동작을 묻지 않는다. @supports는 브라우저가 그 선언을 이해하는지만 확인한다. 이해는 하는데 구현이 부분적인 경우를 걸러내지 못하므로, 통과했다고 화면 확인을 건너뛰면 안 된다.
  • 방향을 지킨다. @supports 자체를 모르는 아주 오래된 브라우저는 그 블록을 통째로 무시한다. 그러므로 기본 스타일은 블록 밖, 향상은 블록 안이다. not으로 폴백을 감싸면 그 폴백이 통째로 사라지는 브라우저가 생긴다.
  • :has()는 감싼다. 미지원 브라우저가 규칙 블록 전체를 버리므로, :where(.card:has(img))처럼 관대한 목록에 넣으면 나머지 선언이 살아남는다. 대신 :where()는 특이성을 0으로 만들어 버리므로 그만큼 다른 규칙에 지기 쉬워진다.
  • 폴백 전략은 셋 중 하나로 고르고 만료를 함께 적는다. ① 진행적 향상 — 기본 상태가 이미 쓸 만하면 향상만 얹는다. ② 동등 대체 — 미디어 쿼리로 근사한 뒤 컨테이너 쿼리로 정밀화한다. ③ 미룬다 — 핵심 레이아웃이라 폴백을 두 벌 유지해야 한다면 그 비용이 기능 이득보다 클 때가 많다. 어느 쪽이든 폴백 옆에 「어느 조건이 되면 지운다」를 주석으로 남기지 않으면 그 코드는 조건이 충족된 뒤에도 몇 년을 더 산다.

7. 설문 수치를 읽는 법 - 응답자는 평균적 개발자가 아니다

매년 나오는 CSS 설문은 무엇이 논의되고 있는지를 보기에 좋은 자료다. 다만 수치를 옮겨 적을 때는 표본의 성격을 함께 옮겨야 한다. State of CSS 2026은 2026년 5월 15일부터 6월 29일까지 4,902명이 응답한 공개 웹 설문이다. 이 한 줄을 떼면 남는 것은 근거가 아니라 인상이다.

  • 자발 응답이다. 무작위 추출 표본이 아니라, 설문의 존재를 알게 되고 답할 의욕이 있는 사람이 모인다. CSS 설문에 시간을 쓰는 사람은 정의상 CSS에 관심이 큰 쪽이다.
  • 모집 경로가 결과를 만든다. 어떤 채널로 퍼졌는지에 따라 응답자 구성이 통째로 달라진다. 이 글은 공개 페이지에서 모집 채널을 확인하지 못했고, 그렇다면 그 항목이 비어 있다는 사실 자체를 인용에 붙여야 한다.
  • 전체 N과 문항별 N은 다르다. 4,902는 전체 응답자 수이고 모든 문항이 그 모수를 갖지 않는다. 자유 응답 문항은 특히 적다 — 「가장 좋아하는 새 기능」 문항의 상위 항목은 앵커 포지셔닝 168, :has() 158, 크기 컨테이너 쿼리 126, CSS 중첩 116으로, 백분율이 아니라 언급 횟수이며 모수도 4,902가 아니다.
  • 「사용률」이 무엇을 센 것인지 확인하고, 증감에 섞인 표본 변화를 뺀다. 「써 봤다」와 「프로덕션에서 쓰고 있다」와 「이름은 안다」는 서로 다른 질문인데 요약본만 보고 옮기면 이 구분이 사라진다. 전년 대비 올랐다는 서술에도 기능이 실제로 퍼진 몫과 응답자 구성이 달라진 몫이 함께 들어 있다.

이 전제를 붙이고 읽으면 2026년 판에서 읽어낼 만한 경향은 이렇다. 브라우저 호환성이 채택의 최대 장벽으로 꼽혔고, 앵커 포지셔닝이 「쓰고 싶은데 지원 때문에 못 쓴다」의 대표 사례로 언급됐다. 프레임워크 문항에서는 Tailwind가 1위를 유지했고, 「프레임워크를 쓰지 않는다」가 Bootstrap을 제치고 2위가 됐다. CSS 코드의 AI 생성 비중은 평균 28% 수준으로 다른 개발 영역보다 낮게 나왔으며, 가장 많이 언급된 우려는 인지 과부하였다.

그리고 이 수치들이 지지하지 않는 문장이 있다. 「이제 모두가 :has()를 쓴다」는 이 데이터로 성립하지 않는다. 성립하는 문장은 여기까지다 — 이 표본에서 :has()는 가장 널리 쓰인다고 응답된 신기능 중 하나였다. 두 문장의 차이가 사소해 보인다면, 앞 문장을 근거로 폴백을 걷어냈을 때 무엇이 깨지는지 생각해 보면 된다.

8. 지금 채택할 것과 미룰 것

판단 축은 넷이면 충분하다. 실패했을 때 무엇이 어떻게 깨지는가, 폴백을 두 벌 유지하는 비용, 확인된 지원 날짜와 내 사용자 분포 사이의 거리, 그리고 나중에 되돌리는 비용이다. 이 중 첫째가 가장 무겁다. 조금 덜 예뻐지는 실패와 레이아웃이 무너지는 실패는 같은 저울에 올리면 안 된다.

기능미지원일 때 증상폴백 난이도판단
중첩규칙이 무시되어 스타일이 아예 안 걸림낮음 - 전처리기로 컴파일하면 0확인 후 채택. 지원 날짜를 확인하지 못했다면 컴파일을 유지하는 쪽이 안전하다
커스텀 프로퍼티값이 비어 폴백 값으로 떨어짐낮음 - var(--x, 기본값)지금 쓴다

미루는 쪽에도 값이 있다는 점은 짚어 둘 만하다. 폴백을 두 벌 유지하는 팀은 시간이 지나면 폴백 경로만 보게 된다. 향상 경로가 실제로 렌더링되는지 확인하는 절차가 없으면 그 코드는 죽은 코드이고, 죽은 줄도 모른 채 유지 대상 목록에 남는다. 새 기능을 넣을 때는 「어느 브라우저에서 향상 경로를 확인할 것인가」를 함께 정해 두는 편이 낫다.

9. 확인하지 못한 것

이 글의 지원 상태 서술은 각 기능의 MDN 문서에서 나왔고, 아래는 그 범위 밖이라 단정하지 않는다.

  • CSS 중첩의 Baseline 등급과 도입 시점 - 개요 문서에서 배지를 확인하지 못했다. 중첩 문서 하단의 브라우저 호환성 표를 직접 볼 것.
  • 앵커 포지셔닝의 엔진별 지원 버전 - 개요 문서에 호환성 표가 나타나지 않았다. 배지가 표시되지 않는다는 사실만 확인했다.
  • @property·aspect-ratio·동적 뷰포트 단위·스크롤 연동 애니메이션 - 본문에서 개념만 언급했고 지원 상태는 확인하지 않았다.
  • @container 별표의 정확한 범위와 Baseline 등급의 승격 기준 - 앞은 문서가 「일부 부분은 지원 수준이 다를 수 있다」고만 표시하므로 스타일 쿼리와 스크롤 상태 쿼리를 각각의 문서에서 따로 봐야 하고, 뒤는 정의 문서를 확인하지 않았다.
  • 설문의 모집 경로와 문항별 응답 수 - 공개 요약 페이지에서 확인하지 못했다. 백분율 형태의 수치는 집계 요약을 거쳐 얻은 것이라 원 문항의 표현을 확인하지 않았다.

자주 묻는 질문(FAQ)

전처리기를 이제 걷어내도 되나?

중첩과 변수만 쓰고 있었다면 걷어낼 근거가 생긴 것이 맞다. 다만 믹스인, 반복문으로 유틸리티를 찍어내는 코드, 컴파일 타임 색 계산, 파일 분할과 임포트 정리는 여전히 전처리기 쪽 일이다. 판단은 취향이 아니라 목록으로 한다 — 전처리기 파일에서 실제로 쓰고 있는 문법을 뽑아 표준으로 대체 가능한 것과 아닌 것을 나눠 보면 답이 바로 나온다.

:has()를 쓰면 성능이 나빠지나?

선택자가 느린 것이 아니라 훑는 범위가 비용을 만든다. MDN이 권하는 방향은 분명하다 — body·:root·전체 선택자에 앵커하지 말고 자식·인접 형제 결합자로 범위를 좁히라는 것이다. 카드 한 장 안에서 자식 유무를 묻는 정도는 문제가 되지 않는다. 걱정되면 실제 페이지에서 스타일 재계산 시간을 재 보는 편이 추측보다 빠르다.

컨테이너 쿼리가 미디어 쿼리를 대체하나?

대체가 아니라 분업이다. 페이지 전체의 골격 — 몇 단으로 나눌지, 사이드바를 접을지 — 은 여전히 미디어 쿼리 쪽이다. 컨테이너 쿼리는 그 골격 안에 놓인 부품이 자기 자리 폭에 맞추는 데 쓴다. 둘을 겹쳐 쓰게 되므로 중단점 값을 한 곳에 모아 두는 습관이 오히려 더 중요해진다.

@layer를 도입하면 기존 CSS가 깨지지 않나?

깨질 수 있고 조용히 깨진다. 규칙 하나만 기억하면 대부분 예측된다 — 레이어에 들어가지 않은 스타일이 어떤 레이어 스타일보다 강하다. 그래서 기존 CSS를 통째로 레이어에 밀어 넣으면 이기고 있던 규칙들이 갑자기 지기 시작한다. 안전한 순서는 반대다. 리셋이나 서드파티처럼 항상 지기를 바라는 것부터 낮은 레이어에 넣고, 내 스타일은 레이어 밖에 둔 채 관찰한다.

설문 수치를 근거로 기술 선택을 해도 되나?

설문이 알려 주는 것은 채택률이 아니라 관심의 방향이다. 공개 웹 설문은 자발 응답이라 응답자가 그 주제에 관심 있는 쪽으로 쏠린다. 그래서 사용률이 높게 나왔다는 사실은 내 사용자의 브라우저가 그 기능을 지원한다는 근거가 되지 못한다. 쓸모 있는 사용법은 검토 목록을 고르는 데까지이고, 그 다음 판단은 브라우저 호환성 문서와 내 서비스의 버전 분포에서 한다.

결론: 오늘 판단할 세 가지

지난 몇 년의 CSS 변화를 한 문장으로 줄이면 「조건을 판단하는 일이 스크립트에서 스타일시트로 내려왔다」가 된다. 부모의 상태, 놓인 자리의 폭, 규칙 사이의 서열 — 이 셋은 예전에 전부 CSS 바깥에서 계산되어 클래스라는 형태로 주입됐다. 지금은 그 계산이 선택자 안에 들어간다. 그래서 이득은 새 문법에 있는 게 아니라 지워도 되는 코드에 있다.

  • 지금 있는 클래스 토글부터 세어 본다. 부모에 클래스를 붙였다 떼는 코드, ResizeObserver로 폭을 재는 코드, 테마용 클래스 세트. 이 목록이 곧 회수 가능한 코드의 목록이다.
  • 기능이 아니라 실패 모드로 판단한다. 미지원일 때 조금 덜 예뻐지는 기능과 규칙 블록 전체가 죽는 기능은 채택 기준이 달라야 한다. :has()를 관대한 목록으로 감싸는 습관은 이 판단에서 나온다.
  • 확인 날짜를 남긴다. 지원 상태는 반년이면 달라진다. 팀 문서에 기능별 확인 시점을 적어 두지 않으면 같은 조사를 반복하게 되고, 반복하지 않으면 낡은 판단을 계속 쓰게 된다.

마지막으로 설문 이야기 한 줄. 이런 자료는 무엇을 검토 목록에 올릴지를 고를 때 유용하고, 거기까지다. 채택 여부는 브라우저 호환성 문서와 내 서비스의 버전 분포가 결정한다. 응답자 수와 조사 시점을 떼고 인용된 수치는, 그 수치가 무엇이든 근거가 아니라 분위기다.
