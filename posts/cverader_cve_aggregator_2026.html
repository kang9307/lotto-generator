CVERader — CVE와 보안 뉴스를 한곳에 모아 보는 취약점 레이더

정보의 홍수 속에서 보안 담당자가 빠르게 트리아지하려면 — NVD·CISA KEV·EPSS 지표 활용과 집계 도구의 실무 가치

2026-06-23 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 하루 130개씩 쌓이는 취약점, 어떻게 살아남나

2025년 한 해 동안 공개된 CVE는 48,185개였다. 하루 평균 132개다. 2020~2025년 사이 CVE 제출량은 263% 급증했고, 2026년 1분기는 전년 동기 대비 또 약 33% 높게 진행 중이다. 보안 담당자가 NVD를 매일 열고 전체 목록을 훑는 건 더 이상 현실적이지 않다.

이런 배경에서 CVERader라는 도구가 주목을 받았다. CVE와 보안 뉴스를 여러 소스에서 끌어와 한 화면에 집계하고, 브랜드나 제품 키워드로 필터링해 알림을 보내는 취약점 레이더다. GitHub에 오픈소스로 공개된 파이썬 도구로, 이메일·Discord 같은 채널로 매칭된 취약점을 바로 통보할 수 있다.

그러나 이 글은 CVERader 단 하나의 도구 소개서가 아니다. 이 도구가 등장한 맥락 — 왜 CVE 정보 집계와 우선순위화가 2026년 보안 운영의 핵심 숙제가 됐는지, NVD·KEV·EPSS 세 지표를 어떻게 조합해야 하는지 — 를 본인 관점에서 풀어 본다. 수치는 2026 취약점 통계와 NIST·CISA 공식 발표를 기반으로 한다.

1. CVERader란 — 취약점을 원하는 채널로 받아 보는 레이더

CVERader(github.com/Mehdi0x90/CVE-Radar)는 "최신 취약점을 모니터링하고, 원하는 브랜드·제품과 매칭해 이메일·Discord 등으로 알림을 보내는 작은 프로그램"으로 정의된다. 설계 철학은 단순하다. 보안 담당자가 매일 여러 피드를 직접 순회하는 대신, 도구가 대신 순회하고 나와 관련 있는 것만 골라 가져다준다.

유사한 오픈소스 도구로 OpenCVE(MITRE·NVD·Red Hat·CISA 등 다중 소스 집계, 커뮤니티·클라우드 두 버전)와 Security Feed Aggregator(CVE·KEV·GitHub Advisories·Hacker News를 JSON 설정으로 통합하는 C++17 기반 도구) 등이 있다. 상용 SaaS로는 CVEFeed, SecAlerts, CVEPulse가 비슷한 역할을 한다.

1.1 이 종류의 도구가 해결하는 문제

보안팀이 실제로 겪는 일상을 생각해 보자. 매일 아침 NVD RSS를 열고, CISA 알림 메일을 확인하고, 벤더별 어드바이저리 페이지를 차례로 방문한다. 이 과정에서 자사 스택과 무관한 수십 개의 항목을 걸러 내고, 정말 중요한 것 몇 개를 남긴다. CVERader 류의 집계 도구는 이 "관련 없는 것 걸러내기"를 자동화한다. 브랜드(예: "nginx", "apache", "citrix")나 제품 키워드를 미리 등록해 두면, 해당 제품이 포함된 CVE가 나왔을 때만 알림이 온다.

1.2 단순 집계와 인텔리전스의 차이

집계는 필요조건이지 충분조건이 아니다. 키워드 매칭으로 관련 CVE를 걸러낸 다음에는 "이 CVE를 얼마나 빨리 패치해야 하는가"를 결정해야 한다. 여기서 NVD·KEV·EPSS 세 지표가 함께 작동해야 한다. 집계 도구는 이 판단을 위한 원재료를 모아 주는 것이지, 판단 자체를 대신해 주지 않는다.

2. 2026년 CVE 풍경 — 왜 지금 집계 도구가 필수인가

숫자로 먼저 현실을 직시하자. 2025년 48,185개의 CVE 중 실제로 악용 가능성이 높은 것은 극히 일부다. CISA KEV 카탈로그에 등록된 것은 1,484개로, 전체의 약 0.5%에 불과하다. 나머지 99.5%는 이론상 취약점이거나 특정 조건에서만 발동되는 저위험 항목이다.

그러나 문제는 그 0.5%를 1초라도 빨리 잡아내는 것이다. Mandiant의 M-Trends 2026 보고서에 따르면 평균 익스플로잇 시간은 마이너스 7일로 측정됐다. 패치가 나오기 전에 이미 공격이 이루어진다는 뜻이다. CrowdStrike 데이터에서는 악용된 취약점의 42%가 공개 전에 공격을 받았고, 최단 익스플로잇 시간은 27초에 불과했다.

이 숫자들이 의미하는 바는 명확하다. 주간 취약점 검토 회의를 기다리는 시간이 없다. 수작업으로 피드를 돌아다닐 여유가 없다. 자사 제품과 관련된 KEV 등재 CVE가 공개되는 즉시 알림을 받고, 그날 내로 대응 여부를 결정하는 체계가 필요하다.

3. NVD — 기준점이자 이제는 부분적 기준점

National Vulnerability Database(NVD)는 미국 NIST가 운영하는 CVE 보강 데이터베이스로, CVSS 점수·CPE 식별자·참조 링크를 각 CVE에 붙여 왔다. 2026년 4월 15일까지는 사실상 취약점 관리의 기준점이었다.

그런데 2026년 4월 15일, NIST는 NVD를 트리아지 모델로 전환한다고 발표했다. 이유는 명확했다. CVE 제출 폭증(2020~2025년 +263%)으로 처리 능력이 한계에 달했다. 약 29,000개의 미처리 CVE가 'Not Scheduled'로 재분류됐고, 앞으로 들어오는 CVE의 15~20%만 완전한 CVSS·CPE 보강을 받는다. 우선 보강 대상은 CISA KEV 등재 CVE, 연방정부 사용 소프트웨어 CVE, EO 14028 핵심 소프트웨어 CVE다.

이 변화의 실무 의미는 크다. 지금까지 많은 보안팀이 "NVD에 CVSS High 이상인 것을 패치한다"는 단순 정책을 썼다면, 이제 그 정책은 작동하지 않는다. NVD가 보강하지 않은 CVE는 CVSS 점수도 없고, 관련 소프트웨어 정보도 없는 채로 남는다. 여러 소스를 조합하는 집계 체계가 선택이 아닌 필수가 된 것이다.

4. CISA KEV — "이미 터졌다"는 가장 강력한 신호

CISA의 Known Exploited Vulnerabilities(KEV) 카탈로그는 실제 공격에서 악용이 확인된 CVE의 공식 목록이다. 2025년 말 기준 1,484개가 등록되어 있으며, 2025년 한 해만 245개가 추가됐다(+20%).

KEV가 강력한 이유는 예측이 아니라 확인이기 때문이다. EPSS가 "앞으로 악용될 것 같다"는 확률이라면, KEV는 "실제로 악용됐다"는 사실이다. 그래서 취약점 트리아지의 1단계는 언제나 "이 CVE가 KEV에 있는가?"여야 한다. KEV 등재 CVE는 연방정부 기관에 14일 이내 패치가 의무화되어 있으며, 민간에서도 즉각 대응의 기준점으로 삼는 것이 합리적이다.

2025년 KEV 추가 현황을 보면 패턴이 보인다. Microsoft가 전체의 약 24%(350개)를 차지하며 최다이고, 2025년 신규 추가 59개 중 19개가 Citrix·Ivanti·Fortinet 같은 네트워크 보안 어플라이언스를 대상으로 했다. 엣지 디바이스·VPN 장비의 익스플로잇이 전년 대비 8배 급증(3%→22%)했다는 데이터와 일치한다. 즉, 경계 장비 관리자라면 KEV를 눈에 불을 켜고 봐야 하는 상황이다.

5. EPSS — "앞으로 터질 것"을 예측하는 머신러닝 점수

EPSS(Exploit Prediction Scoring System)는 FIRST(Forum of Incident Response and Security Teams)가 관리하는 머신러닝 기반 CVE 악용 가능성 예측 모델이다. 각 CVE에 0~1 사이의 점수를 부여하며, 이는 해당 CVE가 향후 30일 내에 실제 공격에 사용될 확률을 뜻한다.

2025년 3월에 출시된 EPSS v4는 ROC AUC 0.838을 달성했다. 쉽게 말하면 "악용된 CVE vs. 악용되지 않은 CVE"를 약 84% 정확도로 구분한다. 이 수치는 CVSS 점수만으로 악용 여부를 예측하는 것보다 훨씬 정교하다.

실무에서 EPSS의 핵심 통찰은 이렇다. CVSS 점수가 높다고 해서 EPSS 점수도 높은 것이 아니다. CVSS 9.0 이상의 Critical 취약점 수만 명이지만, 그 중 실제로 공격 코드가 공개되고 악용이 이루어지는 것은 소수다. 반대로 CVSS 7.0의 High 취약점이 EPSS 0.5를 기록한다면(30일 내 악용 확률 50%), 이 CVE를 먼저 처리해야 한다. 심각도 기반 우선순위화의 한계를 EPSS가 채운다.

5.1 EPSS를 어떻게 쓸 것인가

일반적으로 EPSS 0.1(10%) 이상을 실질 위험 임계치로 본다. 전체 CVE의 약 2~3%만 이 범위에 든다. 여기서 더 좁히면 EPSS 0.5 이상은 즉각 대응 후보, 0.1~0.5는 단기 패치 대상으로 분류할 수 있다. 단, EPSS도 가정이 있다. 인터넷 노출 서버와 내부 전용 시스템은 EPSS 점수가 같더라도 실제 위험이 다르다. 자산 노출 맥락을 반드시 결합해야 한다.

6. 세 지표의 결합 — 실무 트리아지 4계층

NVD·KEV·EPSS를 각각 이해했다면, 이제 이것을 어떻게 조합하는지가 핵심이다. 2026년 기준 권장 트리아지 계층 구조는 다음과 같다.

계층기준대응 타임라인근거
1계층 (즉시)CISA KEV 등재14일 이내 (연방 기준)실제 악용 확인, 가장 강력한 신호
2계층 (긴급)EPSS ≥ 0.57일 이내30일 내 악용 확률 50%+, 고위험
3계층 (높음)EPSS 0.1~0.5 또는 CVSS 9.0+30일 이내통계적 위험 또는 높은 잠재 피해
4계층 (일반)나머지분기별 패치 사이클낮은 실질 위험, 모니터링 유지

이 계층 구조에서 CVERader 같은 집계 도구의 역할이 명확해진다. 도구는 여러 피드에서 자사 관련 CVE를 걸러 내고, 각 CVE의 KEV 상태와 EPSS 점수를 함께 표시해야 한다. 그래야 보안팀이 알림 하나를 받았을 때 즉시 "이게 1계층인가 4계층인가"를 판단할 수 있다.

7. NVD 트리아지 전환 이후 — 대안 피드의 필요성

NVD가 15~20%만 완전 보강한다는 사실은, 나머지 80~85%의 CVE에 대해 다른 출처를 봐야 한다는 뜻이다. 2026년 기준 주요 대안 피드는 다음과 같다.

  • CNA(CVE Numbering Authority) 직접 데이터: CVE.org에서 CNA가 직접 제출한 정보. Microsoft·Google·Apple 등 대형 벤더는 자체 CNA로서 상세 정보를 빠르게 올린다.
  • VulnCheck: NVD가 보강하지 않은 CVE에 CPE와 CVSS를 채워 넣는 상용 피드. NVD 공백을 직접 메우는 용도.
  • GitHub Advisory Database: 오픈소스 패키지 취약점에 특화. 개발팀이 많이 쓰는 npm·pip·Maven 라이브러리 취약점을 빠르게 업데이트한다.
  • 벤더 어드바이저리: Cisco·Microsoft·Red Hat 등 직접 공지. 자사 스택의 주요 벤더를 구독하는 것은 기본이다.

CVERader와 같은 도구가 이 여러 피드를 하나의 설정 파일로 통합하고, 키워드 필터로 관련 항목만 추출해 단일 알림 채널로 보내 주는 역할을 한다면, 보안팀의 일일 업무 부담이 의미 있게 줄어든다.

8. 도구 선택의 실제 기준 — 오픈소스 vs. SaaS

CVERader처럼 자체 운영하는 오픈소스 집계 도구와, CVEFeed·SecAlerts·CVEPulse 같은 SaaS 중 무엇을 선택해야 하는가? 본인 기준을 정리하면 다음과 같다.

8.1 오픈소스가 유리한 경우

CVE 정보와 자사 자산 DB를 직접 연동해야 할 때, 내부 Slack·Teams·PagerDuty에 알림을 연결해야 할 때, 규제 상 CVE 데이터가 외부 SaaS 서버를 경유할 수 없을 때다. CVERader의 경우 Python 기반으로 사내 환경에 배포하면 데이터가 사내 인프라 안에만 머문다. 필터 규칙과 알림 채널을 코드로 완전히 통제할 수 있다는 것도 장점이다.

8.2 SaaS가 유리한 경우

운영 인력이 부족하거나, 빠르게 시작해야 할 때다. CVEPulse는 설치 없이 11개 인텔리전스 소스를 기반으로 실시간 CVE 관심도 점수를 보여 준다. SecAlerts는 수백 개의 데이터 포인트를 지속적으로 수집하며, 구독 제품에 대한 맞춤 알림을 제공한다. 운영 부담 없이 즉시 가시성을 얻는 것이 목표라면 SaaS가 더 빠른 출발점이다.

8.3 하이브리드 접근

실무에서 좋은 타협점은 하이브리드다. SaaS로 빠르게 가시성을 확보하고, 자산 연동·자동화 대응이 필요해지면 오픈소스 도구로 확장한다. 핵심은 어느 도구를 쓰든 KEV+EPSS+자산 맥락의 3요소를 결합해야 한다는 것이지, 도구 자체가 정답이 아니라는 점이다.

9. 보안 운영팀이 지금 당장 할 수 있는 것

이 글의 결론을 실행 가능한 수준으로 좁힌다. 2026년 6월 기준, 취약점 관리 체계를 개선하려는 보안팀이 오늘 시작할 수 있는 것들이다.

9.1 CISA KEV 알림 구독을 지금 설정하라

CISA는 KEV 업데이트를 RSS·이메일로 무료 제공한다. 비용이 없고 설정이 5분이다. KEV 등재 CVE가 자사 스택과 겹치는지 즉시 확인하는 워크플로만 만들어도 최우선 위험의 절반을 해결한다.

9.2 EPSS API를 정기 스크리닝에 넣어라

FIRST는 EPSS API를 무료로 제공한다. 현재 열린 취약점 목록에 있는 CVE-ID를 배치로 넣으면 각 CVE의 EPSS 점수를 받을 수 있다. 주 1회 이 스크리닝을 돌려 EPSS 점수가 급상승한 CVE가 있으면 즉시 검토 대상으로 올린다.

9.3 자사 제품 키워드 필터를 구축하라

CVERader처럼 키워드 기반 필터를 쓰거나, CISA KEV CSV에서 자사 벤더 이름으로 grep하는 스크립트를 짜라. "nginx", "apache httpd", "openssl" 같은 구체적 제품명으로 시작하면 충분하다. 자사 스택 목록이 없다면 자산 인벤토리를 먼저 만드는 것이 선행 과제다.

9.4 NVD 의존도를 분산하라

NVD 트리아지 전환 이후, NVD만으로 CVSS 점수를 얻을 수 없는 CVE가 늘어난다. GitHub Advisory Database, 주요 벤더 어드바이저리, CISA KEV를 추가 소스로 편입하라. 완전 자동화가 부담이라면 주간 리뷰에 이 세 소스를 병행 확인하는 체크리스트를 만드는 것만으로도 시작이다.

마치며 — 집계는 수단이고 판단이 본체다

CVERader는 좋은 아이디어를 담은 도구다. 분산된 CVE 피드를 한곳에 모으고, 자사와 관련된 것만 걸러 알람으로 보내는 발상은 실제로 보안팀의 일일 시간을 아껴 준다. 하지만 도구가 모든 것을 해결하지 않는다.

2026년 기준으로 취약점 관리의 진짜 숙제는 우선순위화다. 하루 130개씩 쌓이는 CVE 중 오늘 내가 반드시 대응해야 하는 것이 무엇인지를 판단하는 능력이다. 그 판단은 KEV로 확인된 사실, EPSS로 예측한 가능성, 자사 자산의 노출 현황, 비즈니스 영향도를 4계층으로 결합할 때 비로소 의미가 생긴다. 집계 도구는 그 판단의 재료를 빠르게 모아 주는 역할이다. 재료를 넘겨받았으면 판단은 사람이 해야 한다.
