Kimi K3 の重み公開 - 2.8兆パラメータのオープンウェイトは導入できるか

ライセンス条件・VRAM 計算・総コスト - 発表資料ではなく、導入判断に必要なもの

2026年7月28日 IT・技術

序論 - 「公開された」と「使える」の距離

2026年7月末、Moonshot AI が Kimi K3 の重みをダウンロード可能な形で公開した。見出しの数字は 2.8兆パラメータである。誰でも入手できる重みとしては異例の規模であり、それゆえ報道の見出しはほぼその数字で埋まった。

ところが導入を検討する立場から見ると、パラメータ数はもっとも重要度の低い情報に近い。実務者が実際に答えねばならない問いは四つある。第一に、ライセンス上わが社はこれを使ってよいのか。第二に、手に入る機材で動くのか。第三に、どの業務に使えば得で、どの業務では損か。第四に、商用 API を使うより本当に安いのか。この四つに答えが出なければ、2.8兆だろうと28兆だろうと検討は進まない。

本稿はこの四つだけを扱う。リリース事実を並べる代わりに、モデルカードとライセンス原文に書かれていることを確認し、確認できなかったものは確認できなかったと明記した。とくに数値を引くたびに 誰が測定したか を併記している。メーカーの自社測定値と第三者評価機関の測定値では重みが違うからである。

なお前世代の紹介は Kimi K2.7-Code の分析 で扱ったため繰り返さない。オープンウェイトモデルをめぐる規制論やエコシステムの議論は オープンウェイト AI 規制の論点 と オープンウェイトのクーバネティス的転回 で別途整理した。ここでは ひとつの組織がこのモデルを導入するか否かを決めるための情報 に集中する。世代ごとの座標は AI モデル比較ハブ を併せて見るとよい。

1. K3 の実スペック - 何が公開されたのか

以下の数値はすべて Hugging Face に掲載された Moonshot AI 公式モデルカード に記載された値である。報道や二次要約ではなく、配布ページの原文に基づく。

1.1 モデル構成

K3 は Mixture-of-Experts(MoE) 構成である。総パラメータは2.8兆だが、ひとつのトークンを処理する際に実際に計算へ参加するのは 1,040億(104B) にとどまる。エキスパートは全体で 896個 あり、トークンごとに 16個 が選択され、そこに常時稼働する共有エキスパート2個が加わる。

  • 総パラメータ: 2.8兆(2.8T)
  • トークンあたり活性: 1,040億(104B)
  • エキスパート構成: 全896個のうちトークンごとに16個を選択、加えて共有エキスパート2個
  • レイヤー: 計93層(Kimi Delta Attention 69層 + Gated MLA 24層)
  • コンテキスト: 1,048,576トークン(100万トークン級)
  • ビジョンエンコーダ: MoonViT-V2、約4億100万パラメータ
  • 語彙サイズ: 16万
  • 活性化関数: SiTU-GLU

ここで実務的に意味を持つ数字は2.8兆ではなく 104B である。計算量と応答速度を左右するのは活性パラメータだからだ。逆にメモリ要求量を左右するのは総パラメータである。つまり K3 は メモリは2.8兆級に食いながら、計算は1,040億級で行う モデルである。この非対称性が以降のハードウェア議論のすべてを支配する。

1.2 注意機構 - KDA と Gated MLA

モデルカードは注意機構を Kimi Delta Attention(KDA) と Gated MLA の混成として説明する。93層のうち69層が KDA、24層が Gated MLA である。線形注意系を多く配置し全体注意を少数だけ混ぜるハイブリッド構成は、100万トークンのコンテキストで KV キャッシュが膨張する問題を緩和する設計として読める。

ただしこの構成の実効果がどの程度かについて、独立検証の結果は確認できなかった。アーキテクチャ名とレイヤー配分はモデルカードに書かれた事実だが、それが長文処理の品質にどれだけ寄与するかは別問題である。長いコンテキストを実際に使う計画なら、自前のデータで再現率を測るほうが安全だ。

1.3 MXFP4 ネイティブという選択

もっとも実務的に重要な項目がこれである。K3 は MXFP4 の重み / MXFP8 の活性値 という形式で配布され、モデルカードはこれを 量子化認識学習(quantization-aware training) の結果と説明している。

この違いは押さえておく必要がある。通常オープンウェイトモデルは BF16 のような高精度形式で配布され、利用者が後から4ビットに圧縮して動かす。この事後量子化はたいてい品質劣化をともなう。対して K3 は 最初から4ビットを前提に学習された状態で配布される。利用者が別途量子化の工程を踏む必要がなく、事後圧縮でよく起きる劣化リスクもその分下がる。

副次効果は容量である。パラメータあたり4ビットはパラメータあたり0.5バイトなので、2.8兆パラメータの重み容量は 約1.4TB になる。同じモデルを FP16 で配布していたら5.6TB だったはずだ。(この二つの値は筆者がパラメータ数にビット幅を掛けて計算したものであり、モデルカードに明記された数値ではない。)4分の1に減ったのはありがたいが、次節で見るとおり1.4TB も決して小さな数字ではない。

1.4 K2 世代から何が変わったか

Moonshot は新しいアーキテクチャ要素によって K2 比で全体のスケーリング効率が2.5倍改善した と述べている。これは メーカーの自社主張 であり第三者が再現した値ではない。利用者が体感しやすい変化はむしろ次のほうだ。

項目Kimi K2.7-Code(前世代系)Kimi K3
総パラメータ1兆2.8兆
トークンあたり活性320億1,040億
コンテキスト256K トークン1,048,576トークン
配布形式高精度形式で配布し利用者が量子化MXFP4 ネイティブ(量子化認識学習)
位置づけエージェント型コーディング特化汎用 + ネイティブ視覚 + エージェント
思考モード既定で有効常時有効、強度3段階(low/high/max)
ライセンス修正 MIT 系Kimi K3 ライセンス(条件付き)

実務上もっとも大きな変化は 活性パラメータが320億から1,040億へ3倍以上に増えた ことである。品質は上がるが、トークンあたりの計算量もそのぶん増える。つまり K3 は前世代より 軽くない。コーディングエージェントを安く回すために K2 系を使っていた組織が K3 にそのまま乗り換えると、コストがむしろ上がりうる。世代が上がれば自動的に上位互換、とはならないということだ。

もうひとつ、K3 は 思考モードを切れない。モデルカードは K3 が常に推論を行い reasoning_content を返すと明記している。強度は low / high / max で調整できる。短く単純な分類や抽出の処理に付けると不要な思考トークンが発生し続けるということなので、ワークロード配置では必ず考慮すべき点である。

2. ライセンス精読 - オープンウェイトはオープンソースではない

本稿でもっとも重要なのがこの節である。社内の導入検討が実際に止まる地点は性能ではなく、たいていライセンスだからだ。

2.1 Kimi K3 ライセンスの条件

K3 のコードと重みは 「Kimi K3 ライセンス」 という独自ライセンスで配布される。MIT のような標準ライセンスではなく、寛容な許諾文にいくつか条件を足した形である。ライセンス原文で確認した内容は以下のとおりだ。

  • 基本許諾: 使用・複製・改変・結合・公開・配布・サブライセンス・販売を許可する。実行・展開・ファインチューニング・派生物の作成が明示的に許可されている。
  • 著作権表示の保持: 著作権表示をソフトウェアのすべての複製または重要な部分に含めなければならない。これが基本義務である。
  • 大規模サービス提供時の個別契約: モデルをサービス(Model as a Service)として提供し、連続12か月の合計売上が2,000万米ドルを超える場合、その商用利用の前に Moonshot AI と個別契約を締結する必要がある。
  • UI 表示義務: 派生物を含め、月間アクティブユーザー1億人超 または 月間売上2,000万米ドル超 の商用製品・サービスに用いる場合、ユーザーインターフェースに Kimi K3 を目立つ形で表示しなければならない。
  • 例外: 内部利用、および Moonshot AI 公式製品や認定パートナー経由でのアクセスは、上記二つの条件の適用から除外される。

整理するとこうなる。大半の組織にとってこれらの条件は事実上無害である。月間売上2,000万米ドルや MAU 1億人は多くの企業が到達しない水準であり、社内利用はそもそも例外として外れている。しかし条件がないことと、条件はあるが自社には掛からないことは、法務レビューではまったく別の扱いになる。後者は文書化が要る。

2.2 社内導入時に確認すべき四点

実際に検討を進めるなら、以下は記録に残しておくとよい。

  1. 自社の利用形態は「内部利用」か「対外サービス」か。社内の従業員だけが使うツールなら例外条項に該当する可能性が高い。一方、顧客が使う製品に組み込んだ瞬間から、売上・MAU の基準線を追い続ける必要が生じる。
  2. 基準線を超える計画があるか。いまは掛からなくても3年後の成長計画で超えるなら、その時点で UI 表示を入れるか個別契約を結ぶことになる。製品設計の段階で知っておくほうがよい。
  3. ファインチューニング成果物の扱い。ライセンスは派生物の作成を許可するが、派生物にも同じ条件が付いて回ることを前提に検討すべきである。社内データで調整したモデルを外部に販売する計画があるならなおさらだ。
  4. データの経路。これはライセンスではなくセキュリティ検討の項目である。重みを入手して自社インフラで動かせばプロンプトは外に出ない。逆に便宜上 Moonshot のホスティング API を使えばデータは外に出る。オープンウェイトモデルを使うという事実そのものがデータ主権を保証するわけではない。保証するのはセルフホストという配置方式である。

もうひとつ実務的な助言を添えると、上記の要約はあくまで 筆者がライセンス原文を読んで整理したもの である。契約判断は要約ではなく原文で行うべきであり、金額基準に掛かる可能性がある組織なら法務レビューを通すのが正しい。ライセンス条項は改定されうるため、検討時点の原文を確認されたい。本文の数値は 2026年7月時点 のものである。

2.3 なぜ「オープンソース」と呼んではいけないのか

報道やコミュニティでは二つの用語が混ざって使われるが、導入検討では区別が要る。

  • オープンソース は通常 OSI 定義に従う。核心は 利用分野・利用者・規模による差別がないこと である。
  • オープンウェイト は学習済みパラメータをダウンロードできるという配布方式だけを指す。条件はライセンスごとに異なる。
  • K3 ライセンスは売上・MAU の規模によって義務が変わる。この時点で OSI の意味でのオープンソース定義とは分かれる。
  • さらに 学習データと学習コードは公開対象ではない。再現や偏りの監査を目的とした透明性は確保されない。

この区別は揚げ足取りではない。公共機関や金融の調達文書に オープンソース と記して提出し、あとからライセンス条件が見つかると困ることになる。文書には オープンウェイトモデル、独自ライセンス と正確に書くほうが安全である。

3.2 第三者による測定

独立評価機関である Artificial Analysis の測定結果は次のとおりだ。こちらはメーカーではない外部機関が同一条件で複数モデルを走らせた値なので性格が異なる。

  • 知能指数57点、発表時点で 3位。上位は Claude Fable 5 と GPT-5.6 Sol であった。
  • Artificial Analysis は K3 を 公開重みモデルのなかで最上位圏 と評価した。
  • 9つの評価全体で出力トークン 1億3,200万個 を使用し、これは前世代比 21パーセント減 である。
  • 課題あたりの平均コストは 0.94米ドル と算定された。

ただし注意点がある。この種の指数は バージョンが更新され新しいモデルが加わるたびに順位が変わる。実際、その後の集計では点数や順位が異なって表記された資料も確認できる。したがって 3位 という数字を固定された事実のように引くより、公開重みモデルのなかでフロンティア近接圏 程度に理解するほうが寿命が長い。

3.3 よい数字だけを見ないこと - ハルシネーション率の悪化

同じ機関が指摘した否定的項目がひとつあり、導入判断ではむしろこちらが重要である。ハルシネーション率が前世代の39パーセントから51パーセントへ上がった というものだ。正確性の指標が改善する一方で、ハルシネーションの指標は逆行した。

この組み合わせは実務で特定の失敗類型を生む。難しい問題をより解ける一方、知らないことを知らないと言う能力は落ちた状態 である。コードを書いたり検索エージェントを走らせたりする場面では結果を実行してみれば誤りが露見するので、リスクは吸収される。逆に事実の要約、資料調査、顧客対応のように 出力をそのまま人が信じてしまう用途 では、リスクがそのまま露出する。後述する適合・不適合判断の中心的な根拠がこれである。

付け加えると、ベンチマークの優位が自社業務での品質を 保証するわけではない。どのモデルであれ、自前のデータで作った小規模な評価セットを走らせるまでは確信の根拠がない。

4. 実際に動かすには - まず VRAM の計算から

ここで多くの検討が終わる。モデルカードには 最小ハードウェア要件が明記されていない。そこで筆者が直接計算した値を計算根拠とともに示す。引用ではなく算術なので、読者が自分で検算できる。

4.1 重み容量の計算

計算は単純である。パラメータひとつが占めるバイト数にパラメータ数を掛ければよい。

  • MXFP4(4ビット)基準: 2.8兆 × 0.5バイト = 約1.4TB
  • 参考までに FP8 なら 2.8兆 × 1バイト = 2.8TB
  • 参考までに FP16 なら 2.8兆 × 2バイト = 5.6TB
  • つまり MXFP4 ネイティブ配布は高精度配布に比べ メモリ要求を4分の1に 下げたことになる

さてこの1.4TB をアクセラレータに分けて載せねばならない。80GB 級のアクセラレータを基準にすると 1.4TB ÷ 80GB ≒ 18枚 である。重みを載せるだけで18枚、そこに KV キャッシュ・活性値・フレームワークのオーバーヘッドが加わる。8枚構成のノードに換算すれば 最低3ノード以上 が出発点になる。

注意すべきは、この計算が 理論上の下限 だという点だ。実際の配置ではテンソル並列の通信バッファ、CUDA コンテキスト、スケジューラのメモリ、断片化のせいで、デバイスごとに数 GB がパラメータと無関係に消える。余裕なくぴったり設計すると起動すらしないことが珍しくない。

ちなみにウェブには 単一サーバーや GPU 5〜6枚で動かせる という趣旨の記事が多数あるが、上の算術と合わない。2.8兆パラメータを4ビットで格納しても1.4TB なので、80GB カード6枚(480GB)には物理的に入らない。この種の資料を根拠に予算案を組まないほうがよい。

4.2 KV キャッシュとコンテキスト - 100万トークンの代価

重みを載せて終わりではない。KV キャッシュ が残る。これは同時処理セッション数と各セッションのコンテキスト長に比例して増える。

  • 100万トークンのコンテキストは 使える という意味であって ただ という意味ではない。
  • 長いコンテキストのセッションが数本同時に開くだけで、KV キャッシュは数百 GB 単位に膨らみうる。
  • したがって実際の容量設計は 重み + (同時セッション数 × セッションあたりコンテキスト長) で計算すべきである。
  • KV キャッシュを FP8 などに圧縮するオプションが推論スタックにあるか確認すると余裕が生まれる。
  • K3 の KDA 中心のハイブリッド構成はこの負担を減らす設計だが、具体的な削減率は確認できなかった。

実務的にはこう進めるほうがよい。最大コンテキストを基準に設計せず、実際のリクエスト長の分布を測って95パーセンタイルで設計する。100万トークンを使うリクエストが全体の1パーセントなのに、その1パーセントのためにクラスタ全体を大きくするのは不合理である。そうしたリクエストだけ別キューに回すほうが安い。

4.3 推論スタック

モデルカードは推論エンジンとして vLLM、SGLang、TokenSpeed を挙げ、OpenAI/Anthropic 互換 API 形式を提供すると明記している。

  • MoE ルーティング対応が必須 である。896個のエキスパートを扱うにはエンジンがエキスパート並列に対応している必要がある。
  • MXFP4 形式の対応可否 をエンジンのバージョン単位で確認すべきだ。新しい形式はたいてい特定バージョン以上でのみ動く。
  • API 互換形式を提供する点は実用的な利点である。既存の OpenAI SDK ベースのコードを エンドポイント差し替え程度 で繋いで試せる。
  • 複数ノード構成なので ノード間インターコネクトの帯域 が性能を左右する。一般的なイーサネットで束ねるとトークン生成速度が大きく落ちうる。
  • 思考モードが常時有効なので応答に reasoning_content が含まれる。既存のパーサーがこれを処理できないと統合の段階で手間がかかる。

まとめると K3 のセルフホストは モデルを入手する作業ではなく、小規模 GPU クラスタを運用する作業 である。この一文が導入検討における現実的な分岐点になる。

5. 総コスト判断 - セルフホスト対商用 API

重みが公開されたという事実は、ただちに 安い という意味ではない。この節では判断基準を立てる。

5.1 API 価格の座標

Artificial Analysis がまとめた Kimi API 基準の価格は次のとおりである。(2026年7月時点であり、価格は提供者と時期によって変わる。)

  • 入力: 100万トークンあたり3米ドル
  • 出力: 100万トークンあたり15米ドル
  • キャッシュヒット入力: 100万トークンあたり0.30米ドル(90パーセント割引)
  • 混合単価: 100万トークンあたり2.31米ドル(キャッシュ・入力・出力を7:2:1と仮定した場合)

ここで押さえるべき点がある。同じ機関は K3 を 他のオープンウェイトモデルと比べるととくに高いほう と評価した。すなわち オープンウェイト = 低価格 という通念は K3 にはそのまま当てはまらない。活性パラメータが1,040億なら提供原価そのものが高いので、自然な結果である。低価格を求めるなら K3 より活性パラメータの小さいオープンウェイトモデルのほうが適した選択になりうる。

速度特性も記録されている。同じ機関の測定で出力速度は 毎秒33.3トークン、最初のトークンまでの遅延は 約148秒 であった。後ろの数字は大きく見えるが、これは思考モードが常時有効で応答前に推論を行うためと解釈するのが自然である。対話型 UI にそのまま繋ぐには負担の大きい遅延 という実務的な含意がある。

5.2 損益分岐の考え方

セルフホストと API のどちらが安いかは 稼働率 が決める。枠組みは次のとおりだ。

  • セルフホストのコストは 固定費 である。リクエストが0件でも GPU 賃料・電力・設置費用はそのまま出ていく。
  • API のコストは 変動費 である。使わなければ0円だ。
  • したがって損益分岐は クラスタを遊ばせずに埋められる月間トークン量 で決まる。
  • トラフィックが日中に集中し夜間に空く対話型サービスは稼働率が低く、セルフホストに不利である。
  • 逆に夜間バッチでキューを埋められる大量文書処理は稼働率を100パーセント近くに保てるので有利になる。
判断軸商用 API が有利セルフホストが有利
月間処理量少ないか変動が大きい大きく予測可能
稼働率ピークと閑散の差が大きいバッチで24時間埋められる
データ機微性外部送信が許容される網分離・持ち出し禁止の要件がある
運用人員GPU クラスタの運用人員がいない推論インフラ運用の経験がある
モデルのバージョン方針最新モデルへ乗り換え続けたいバージョンを長期間固定する必要がある
初期投資先行投資ができない複数ノードを確保できる
遅延要求即時応答が必要バッチ・非同期が許容される

5.3 計算から抜けやすいコスト

セルフホストの見積もりが実際より安く出るのは、たいてい以下の項目が抜けているからである。

  • 人件費: 複数ノードの推論クラスタには担当者が要る。この人件費が GPU 賃料を上回る場合もある。
  • 障害対応: ノードがひとつ抜けるとモデルが丸ごと落ちる。二重化するにはクラスタが二式必要になる。
  • アップグレード費用: 半年後により良いモデルが出ればクラスタ設計をやり直すことになる。API なら文字列をひとつ変えるだけだ。
  • 稼働初期の低効率: 推論パラメータを調整するまでは、スループットが期待の半分にも届かないことが珍しくない。
  • 電力・冷却: オンプレミスなら設置場所と電力が別途コストになる。

現実的な折衷案は ハイブリッド である。機微データが絡むワークロードだけ自社ホストし、残りは API で処理する。K3 が OpenAI 互換形式を提供するので、二つの経路を同じコードで扱うのが比較的容易だ。LLM API 価格計算機 で処理量ごとの API コストをまず計算してみると、損益分岐の感覚をつかむのに役立つ。

6. どの業務に適し、どの業務に適さないか

これまでの根拠を総合すると配置判断が出る。根拠は三つだ。思考モードが常時有効であること、ハルシネーション率が逆行したという第三者の指摘、そして活性パラメータが大きく単価が低くないことである。

6.1 適した業務

  • 多段階のエージェント作業: ツール利用・ウェブ探索系のベンチマークで強いと発表され、思考モードが常時動く設計とも合う。
  • 長期のコーディング課題: 複数ファイルを行き来しながら計画・修正・検証を繰り返す作業。結果を実行して検証できるためハルシネーションのリスクが吸収される。
  • 大容量の文書・コードベース分析: 100万トークンのコンテキストを実際に使う数少ない用途である。
  • 文書画像の処理: ネイティブ視覚を備え、文書視覚のベンチマークで上位と発表された。
  • 持ち出し禁止データの処理: 重みを入手して内部で動かせること自体が、代替のない状況では決定的である。
  • 夜間バッチのパイプライン: 遅延が問題にならず稼働率を埋められる。

6.2 適さない、あるいは慎重を要する業務

  • 単純な分類・抽出・ラベリング: 思考モードを切れないため不要な推論トークンが発生し続ける。小さいモデルのほうがはるかに安い。
  • 即時応答が必要な対話型 UI: 最初のトークンまでの遅延が長く測定された。利用者が待つ画面では負担になる。
  • 検証なしにそのまま提示される事実記述: ハルシネーション率悪化の指摘があるため、根拠提示と検証の手順を併せて設計すべきである。
  • コスト最小化が最優先の大量単純作業: オープンウェイトのなかでも単価が低いほうではない。
  • 小規模チームの初めてのセルフホスト: 複数ノードの MoE 推論は難度が高い。より小さいモデルで運用経験を積むほうがよい。
  • 規制文書にオープンソースと記載する必要がある調達: 前述のライセンス条件のため表現を正確にすべきである。

7. 導入判断チェックリスト

実際に検討を進めるなら以下の順序を勧める。上から下へ降りていき、詰まった地点で止まればよい。

  1. 用途は API で足りるか をまず問う。足りるなら重みを入手する理由はない。セルフホストは目的ではなく手段である。
  2. 持ち出し禁止データがあるか。あればセルフホストの検討が正当化される。なければコストだけで判断する。
  3. ライセンスの基準線に掛かるか。内部利用か対外サービスか、売上・MAU の基準を超える計画があるかを文書化する。
  4. 1.4TB を載せられるハードウェアを確保できるか。不可能ならここで検討は終わる。より小さいオープンウェイトモデルへ候補を替える。
  5. 推論スタックが MXFP4 と MoE ルーティングに対応しているか。エンジンのバージョンまで確認する。
  6. 自前の評価セットで品質を測ったか。自社業務のデータ30〜100件あれば方向は見える。ベンチマーク順位で代用しない。
  7. 稼働率を埋める処理量があるか。なければ API のほうが安い。
  8. 運用・障害対応の主体が決まっているか。担当者なしに始めたクラスタは結局放置される。

この八つを通さないまま 2.8兆パラメータが公開されたそうだからうちも入手してみよう で始めると、たいていハードウェアの見積もり段階で引き返すことになる。

8. 限界と未解決の問い

本稿を書くにあたり 確認できなかったこと を明記しておく。推定で埋めるより空けておくほうがよいと考えるからである。

  • 公式の最小ハードウェア要件: モデルカードに記載がない。本文の1.4TB は筆者がパラメータ数とビット幅から計算した値である。
  • 実測スループット: 特定のハードウェア構成における毎秒トークン数や同時処理セッション数について、信頼できる一次資料を見つけられなかった。
  • KDA 構成による KV 削減率の定量: アーキテクチャの構成は公開されているが、削減幅を数値で確認できなかった。
  • ファインチューニングの実務難度: 派生物の作成が許可されることと、この規模を実際に調整できることは別問題である。必要な資源についての公式案内を確認できなかった。
  • 日本語性能: 公開されたベンチマークはほとんどが英語圏の評価である。日本語業務での品質は自前の検証が必要だ。
  • 指数順位の現在値: 評価指数はバージョン更新とともに順位が変わる。本文の数値は発表時点のものである。

もうひとつ。規模競争が続くなかで 公開重みの実効的なアクセス性はむしろ下がっている という逆説も挙げておく価値がある。数百億パラメータのモデルが公開されていた時期は、よく整えた個人のワークステーションでも実行が可能だった。2.8兆パラメータは違う。誰でも ダウンロード はできるが、実行 できる主体は複数ノードのクラスタを回せる組織に狭まる。この流れが開放性の意味をどう変えるかは オープンウェイト規制の論点 と オープンウェイト生態系の分析 でより詳しく扱った。

結論 - 三つの文にまとめると

第一に、Kimi K3 はオープンウェイトであってオープンソースではない。独自ライセンスに売上・利用者規模を基準とした条件が付いている。大半の組織には無害な水準だが、調達文書と法務レビューでは オープンウェイト、独自ライセンス と正確に書くべきである。

第二に、公開されたことと動かせることは別である。MXFP4 ネイティブ配布で容量を4分の1に減らしてなお、重みだけで約1.4TB。80GB 級アクセラレータ18枚分であり、複数ノードのクラスタ運用が前提となる。ここで詰まれば残りの議論は意味を持たない。

第三に、世代が上がれば自動的に上位互換、とはならない。活性パラメータが3倍以上に増え、思考モードを切れず、第三者測定ではハルシネーション率がむしろ上がった。多段階エージェント・長期コーディング・大容量文書分析には強力な候補だが、単純な分類や即時応答の対話型サービスには過剰で遅い。モデルを選ぶ作業ではなくワークロードごとに配置する作業 という原則は今回もそのまま当てはまる。

最後に方法論をひとつ。どのモデルであれ導入判断はベンチマーク順位ではなく 自社業務のデータで作った小規模な評価セット から出るべきである。30〜100件あれば十分に方向が見える。発表資料の数字は候補を絞るところまでに使い、最後の決定は自分で測った値で行うのが安全だ。
