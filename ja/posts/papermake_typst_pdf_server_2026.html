PapermakeとTypst - セルフホスティングPDFサーバーはLaTeX・ヘッドレスブラウザの代替になるか

請求書・レポート・証明書をサーバーでPDF化しなければならない実務者のために、Typstベースのオープンソース文書生成サーバーPapermakeを掘り下げる

2026年7月15日 開発・インフラ

序論: サーバーがPDFを吐き出さねばならない瞬間は常にある

注文が完了すれば請求書を出さねばならず、バッチが終わればレポートが積み上がらねばならず、申請が承認されれば証明書が発行されねばならず、出荷が終われば送り状ラベルが印刷されねばならない。こうした瞬間のたびに、サーバーのどこかでPDFを動的に打ち出すパイプラインが静かに動いている。派手ではないが欠かせないインフラだ。2026年7月時点、この古い問題を新しい角度で解こうとする試みが目を引く。TypstテンプレートをREST APIでレンダリングするセルフホスティングのオープンソースサーバーPapermakeだ。本稿はPapermakeを紹介するだけにとどまらず、なぜサーバーPDF生成が今なお痛みを伴う問題なのか、Typstがその痛みをどう和らげるのか、そしてセルフホスティングと商用APIのどちらを選ぶべきかを実務基準で分析する。

実務で繰り返される4つのPDFニーズ

  • 請求書/インボイス - 注文・決済直後に即座に生成される必要があり、国別の電子インボイス規格のような形式順守が求められる。
  • レポート - 定期バッチで数百~数千件を一度にレンダリングする必要があり、レイアウトの一貫性が鍵となる。
  • 証明書 - 在職証明書・修了証のように頻度は低いが、署名・透かしといった信頼性要素が重要だ。
  • ラベル - 物流ラベルのように超低遅延・高頻度で打ち出す必要があり、小さく反復的なレイアウトが特徴だ。

1. 既存方式の痛み - なぜみんなこの問題で苦労するのか

1.1 LaTeX - 品質は高いが重く遅い

LaTeXは数十年にわたり高品質組版の標準だった。しかし自動化パイプラインに乗せるには摩擦が大きい。フルディストリビューションは数GBに達し、モノリシックな.texファイルに画像・複雑な図が混じるとコンパイルが目に見えて遅くなる。リクエストごとに重い組版プロセスを新たに立ち上げねばならず、失敗時に出るログはLaTeX開発者でない運用担当者には解釈のハードルが高い。インボイスの明細のように自動化コードがテンプレート内部の値を注入する構造は組めるが、その構造自体を保守するコストは軽くない。

1.2 HTML→PDFヘッドレスブラウザ - 柔軟だが資源を食う

PuppeteerやwkhtmltopdfというHTML→PDF方式は、Web開発者に馴染みのあるCSS・テンプレートエンジンをそのまま使えるという魅力がある。しかし代償ははっきりしている。ヘッドレスChromeは起動だけで200~300MBのメモリを使い、画像・フォントが多いページでは500MBを超えやすい。同時レンダリングをかけるとプロセスが片付かず残り、CPUを圧迫する事例も報告されている。逆に古いWebKitエンジンベースのwkhtmltopdfは軽いが、最新のCSS Grid・Flexboxをうまく描画できない。結局、実務者は「軽さ」と「最新のWeb標準レンダリング」のどちらかを選ばされてきた。

2. Typstとは何か - 組版言語の第三の道

Typstは2023年に公開されたマークアップベースの組版言語だ。LaTeXの膨大なバックスラッシュ・波括弧の文法の代わりにMarkdownに近い簡潔な文法を使い、計算と組版の境界を無くして変数・ループ・条件分岐といったプログラミングロジックを滑らかに織り込めるよう設計されている。性能差は特に印象的で、大きな論文基準でLaTeXがフルコンパイルに90秒かかる文書をTypstは約15秒で処理し、内容を少し直した後の差分コンパイルは1秒未満で終わるというベンチマークが報告されている。コンパイラ並みの明確なエラーメッセージ、化学式・楽譜・回路図パッケージを集めた「Typst Universe」というエコシステムも備えている。

2.1 なぜバックエンドPDFエンジンとして魅力的か

Typstは Rustで実装されており、ブラウザなしで純粋なライブラリとしてサーバープロセスに直接組み込める。つまりヘッドレスブラウザのように重いサブプロセスを複数立ち上げる必要なく、サーバー内で直接文書をレンダリングできるということだ。これはまさに「サーバーサイドPDF生成」という用途にぴったり合う特性であり、Papermakeのようなプロジェクトが Typstをレンダリングエンジンに選んだ理由でもある。

3. Papermake - テンプレートをAPIにするアプローチ

Papermakeはドイツの開発者Erik Steiger(rkstgr)が作ったオープンソースプロジェクトで、自らを「文書テンプレートのためのDockerレジストリ」に例える。Typstテンプレートを SHA-256ハッシュでコンテンツアドレス化して保存し、invoice:latestのようなタグで特定のバージョンを指し示す方式だ。テンプレートは一度発行(publish)すれば不変(immutable)であり、レンダリング要求ごとに入力・出力ハッシュが記録され、全履歴を再現・監査できる。

3.1 アーキテクチャ

構造は4つのパーツからなる。コアのpapermakeは仮想ファイルシステムを備えたTypstレンダリングエンジンで、papermake-registryはS3互換ストレージ(テンプレート保存)とClickHouse(レンダー履歴)を束ねる。papermake-serverはAxumベースのHTTP APIレイヤーでテンプレート発行・レンダリング・PDF取得のエンドポイントを提供し、papermake-workerはキューベースのレンダリングを担う(まだ初期段階)。PDF 1.7はもちろん、電子インボイスに使われるPDF/A-2b・PDF/A-3bまで対応している点は、実務のインボイス自動化を念頭に置いた設計と読める。Apache 2.0ライセンスで公開されている。

3.2 テンプレート一元管理+REST APIが与える価値

この構造が実務に持つ意味は明確だ。第一に、マイクロサービス環境で注文・精算・CSなど複数のサービスが一つのインボイステンプレートをAPI呼び出しだけで共有でき、テンプレートロジックが各サービスに重複しない。第二に、多言語・多フォーマット対応が容易になる。テンプレートバージョンを言語・国別にタグ付けして管理すれば、アプリケーションコードを変更せずに新バージョンをデプロイできる。第三に、不変バージョンとレンダー監査ログは「なぜこの請求書がこの形で出たのか」を後から正確に再現できるようにする。規制産業や会計監査が絡む文書では、これは些細な付加機能ではなく核心的な要件だ。

4. セルフホスティング vs 商用PDF API

Papermakeのようなセルフホスティングのオープンソースと、CraftMyPDFやAPITemplate.io系のマネージド商用APIはトレードオフがはっきりしている。セルフホスティングの利点はデータが外部に出ないこと、そして高ボリュームでは単位コストが下がりうることだ。実際にある商用ベンダーは、ブラウザベースのセルフホスティングコストを年間2万7千ドル水準とし、自社のマネージドAPIをそれよりはるかに安く提示する比較資料を公開したことがある(ベンダー自身の比較なので額面通り受け取るより、自分のワークロードで直接検証することを勧める)。逆に商用APIの利点は運用負担がないことにある。Dockerイメージの肥大化、サーバーレスのサイズ制限、ブラウザプロセスのクラッシュといった問題を気にする必要がない。結論ははっきりしている。発送量が少なく専任の運用人員がいないならマネージドAPIが合理的で、データ主権が重要であったり高頻度・定型文書(請求書・ラベル)を大量に処理する必要があるなら、Papermakeのようなセルフホスティングの選択肢を検討する価値がある。

5. 実務導入時に考慮すべきこと - フォント・CJK・性能・セキュリティ

5.1 CJK(日中韓)フォントサポートはまだ未成熟

最も慎重であるべき点だ。Typstプロジェクト自体にCJK組版サポートが不足しているという課題が公に提起されている。フォントスタイル(明朝体対ゴシック体)の切り替え、CJK-ラテン文字間の字間調整、縦書き、ルビ(発音)表記といった機能がまだ整っていないと報告されている。日本語の請求書・証明書のようにCJKテキストが中心の文書をPapermake/Typstへ移そうとするなら、実際の日本語フォントレンダリングと改行品質をパイロット段階でまず検証すべきだ。

5.2 性能とセキュリティ

性能面ではRust実装とブラウザ非起動の構造のおかげで高頻度レンダリングに有利と期待されるが、公開された独立ベンチマークはまだ乏しい。セキュリティ面ではセルフホスティングであるため、テンプレート自体(ユーザー入力がレンダリングに流れ込むインジェクション経路)、S3ストレージのアクセス権限、レンダー履歴DBの個人情報保存ポリシーを自ら設計・点検せねばならない負担が伴う。

結論: どこで使うべきか

Papermakeは2026年7月時点で初期段階(バージョン0.3.0、GitHubスター166個)のプロジェクトだ。すぐに本番全面移行するより、まずは低リスクのワークロード - 社内レポート、内部証明書のように失敗しても大きな打撃がない文書 - でパイロットを回してみるのが合理的だ。逆に高頻度・定型化された文書(請求書・ラベル)を大量に打ち出す必要があり、LaTeXやヘッドレスブラウザの重さが実際に負担だったなら、TypstとPapermakeの組み合わせは真剣に検討する価値のある選択肢だ。ただしCJKフォントの品質とプロジェクトの成熟度は、導入前に自分のデータで直接検証することが必須だ。
