背景 — 複雑な設定ファイル編集をワンクリック拡張導入へ変えるMCPB

エンジニアリングブログ「Desktop Extensions」は、ローカルMCPサーバーがClaudeにファイルシステムからデータベースまでのアクセスを開いた一方で、インストールが複雑すぎるという声が続いたと書いている。利用者は開発ツールを用意し、設定ファイルを手で編集しなければならず、依存関係の問題で行き詰まることも多かったという。ブログはその障壁を5つに整理している。開発ツールの必要性（Node.jsやPythonなどのランタイムの導入）、手動設定（サーバーごとにJSON設定ファイルを編集）、依存関係の管理（パッケージの衝突とバージョン不一致の解消）、発見手段の欠如（役に立つサーバーを探すにはGitHub検索）、更新の複雑さ（最新に保つには手動での再インストール）である。

MCPB（.mcpb）はこの問題への答えとして紹介される。公式ドキュメントはMCPバンドルを、ローカルMCPサーバーとmanifest.jsonを含むzipアーカイブと定義し、ブラウザが拡張機能を導入するようにClaude Desktopがワンクリックで導入すると説明する。この形式はもともとDXT（Desktop Extensions、.dxt）という名称だった。READMEはプロジェクトがDXTからMCPBへ名称変更中であると告知し、dxt CLIはmcpbになり、.dxtファイルは.mcpbファイルになり、@anthropic-ai/dxtパッケージは@anthropic-ai/mcpbへ移される予定（will be moved）だと書く。名称を変えた理由はREADMEには書かれていない。ブログは2025年9月11日付の告知で、既存の.dxt拡張は引き続き動作し、新しい拡張には.mcpbを推奨し、機能は変わらないと述べた。READMEはこの形式がChrome拡張（.crx）やVS Code拡張（.vsix）と精神的に似ていると説明する。

利用者側の手順をブログは3段階にまとめている。.mcpbファイルをダウンロードし、ダブルクリックしてClaude Desktopで開き、Installを押す。ターミナルも設定ファイルも依存関係の衝突もないという説明である。

  • 第一に、導入の過程で設定ファイルを手で編集しない。ブログが対比して示す従来の手順と新しい手順の違いがこの点である。
  • 第二に、サーバーの起動方法と必要な設定はmanifest.jsonに宣言する。MANIFEST.mdはmanifest_version、name、version、description、author、serverを必須項目とする。
  • 第三に、機密設定は別に扱われる。ブログはAPIキーのような機密値がOSのキーチェーンに保存されると書き、MANIFEST.mdはsensitiveの値を隠して安全に保存する（store securely）と書く。
  • 第四に、サーバーは利用者のPC上でstdioにより動作し、クラウドインフラを必要とせず、オフラインで動き、OAuthは不要である。公式ドキュメントがMCPBの特性として挙げる項目である。

READMEはこのリポジトリが3つを提供すると紹介している。MANIFEST.mdのバンドル仕様、バンドルを作るCLI、そしてClaude for macOSとWindowsがMCPBバンドルを読み込み検証するために使うコードである。

基本構造 — 利用者のPC上でstdioにより動くローカルサーバー

公式ドキュメントの最初の段落が、構造の核心を述べている。サーバーは利用者のマシン上でstdioにより動くため、クラウドインフラなしにローカルファイル、ローカルにインストールされたツール、利用者のファイアウォールの内側のシステムへ届く。同じページは2つの方式の実行場所をこう対比する。MCPBは利用者のマシン上でstdioにより動き、ローカルと内部の資源に接続できる。リモートコネクタは開発者のサーバー上でHTTPSにより動き、Anthropicのインフラを通じてアクセスされる。組織がセキュリティ構造を保ったまま、MCPBを内部MCPサーバーへのセキュアなプロキシ、内部ドキュメントへのアクセス、開発ツールの接続に使う例が多いとも書いている。

ドキュメントがMCPBの特性として挙げるのは5つである。利用者のマシン上でローカルに動き、stdio転送で通信し、すべての依存関係をバンドルし、オフラインで動作し、OAuthを必要としない。

公式ドキュメント（Build a desktop extension with MCPB）は、ローカルMCPBとリモートコネクタ（Remote Connector）を選ぶ基準を表で示している。以下の表はその項目を4つの観点にまとめ直したものである。

選定基準 ローカルMCPB（.mcpb） リモートコネクタ（Remote Connector）
ネットワークとファイアウォール 社内ファイアウォール内のシステム（課題管理、社内Wiki、内部DB）にアクセス 集中型クラウド基盤を前提としたパブリックAPIおよび外部サービス
認証と資格情報管理 端末内の既存SSOやブラウザセッションを活用、トークン管理不要 OAuthフローとサーバー側でのトークン管理
データ保護と処理境界 端末外へ出してはならない機密処理、ローカルファイルシステムの直接操作 Web、モバイル、デスクトップを含む全端末への一括配信・集中管理
ランタイムとインフラ基盤 Claude Desktop内蔵のNode.js環境を利用、外部クラウド不要 中央サーバーでコードやサービスを一括管理し、即座に更新を反映

原文の表には、上記のほかにもMCPBを選ぶ理由が載っている。コード編集とGit操作のための直接的なファイルシステムアクセス、Docker・IDE・データベースのようなローカルツールとの連携、ハードウェア連携とデスクトップアプリの制御、同梱のNode.jsランタイムで依存関係を管理しなくてよいワンクリック導入、クラウドインフラ・VPN設定・ファイアウォール規則が不要なこと、カスタムアップロードや許可リストのような組織レベルの管理者制御、認証・認可・監査ログの完全な制御である。

ローカルstdio実行モデルについて、ドキュメントが直接書いている内容は次の4点である。

  • ローカル実行：サーバーは利用者のマシン上で動き、ローカルファイルとローカルにインストールされたツールに接続する。
  • stdio転送：Claude Desktopとサーバーはstdio転送で通信する。
  • オフライン動作：ドキュメントはMCPBがオフラインで動作すると書いている。
  • 認証とインフラ：OAuthは不要で、既存のSSOとブラウザセッションで認証すればトークンを管理しなくてよく、クラウドインフラも不要である。

この4点を超える解釈、たとえばポートを開くかどうかやプロセス権限の境界に関する記述は、これらのドキュメントにはない。この記事もその部分は、ドキュメントが述べた範囲までしか伝えない。

ランタイム選定 — 内蔵Node.js環境とPython依存性の扱い

MCPB拡張を開発するときに最初に決めるのは実装言語である。公式ドキュメントはNode.jsを強く推奨（strongly recommended）し、3つの理由を挙げる。macOSとWindows向けのClaude Desktopに含まれているため利用者が別のランタイムを必要としないこと、Claude Desktopとの互換性と信頼性が最も高いこと、MCP SDKの対応が幅広いことである。ブログもClaude DesktopとともにNode.jsを提供して外部依存をなくしたと書いている。

READMEは同じ推奨をインストールの摩擦という観点から述べる。Node.jsはmacOSとWindows向けのClaudeに同梱されているので、バンドルは利用者に追加のPythonランタイムを入れさせることなく（あるいは開発者がそれを手でパッケージ化することなく）そのまま動く。対象プラットフォームはmacOS（darwin）とWindows（win32）で、対応プラットフォームはmanifest.jsonのcompatibilityセクションに記す。主に1つのプラットフォームで開発する場合でも、両方でテストするようドキュメントは勧めている。

READMEの「Bundling Dependencies」は、サーバー種別ごとに依存関係の扱いが違うと整理している。

  • Node.jsバンドル：npm install --productionでnode_modulesを作り、そのディレクトリ全体をバンドルに含めるよう求める。再現可能なビルドにはnpm ciまたはyarn install --frozen-lockfileを使い、サーバーのエントリーポイントはserver.entry_pointで指定する。MANIFEST.mdもNode.js拡張はすべての依存関係をnode_modulesにバンドルしなければならないと書く。
  • Pythonバンドル（従来方式）：server.type = "python"を使い、必要なパッケージをserver/lib/にバンドルするか、完全な仮想環境をserver/venv/にバンドルする。mcp_config.envでPYTHONPATHを指定してバンドルしたパッケージを指す。READMEは制限も明記している。コンパイル済みの依存関係（MCP Python SDKが必要とするpydanticなど）は、移植可能な形でバンドルできないという点である。
  • uv種別（v0.4+）：server.type = "uv"とし、依存関係を記したpyproject.tomlを含める。バンドルされたパッケージは不要で、ホストアプリがPythonと依存関係を自動で管理し、利用者のPythonインストールなしに複数のプラットフォームで動作するとREADMEは書く。MANIFEST.mdのuvの例はmanifest_versionが0.4である。
  • バイナリバンドル：最大の互換性のために静的リンクを優先し、動的リンクを使う場合は必要な共有ライブラリをすべて含め、開発ツールのないクリーンな環境でテストするよう求める。MANIFEST.mdはバイナリ種別を、すべての依存関係を含むコンパイル済み実行ファイルと説明し、プラットフォーム別のバイナリにも対応する。

まとめると、READMEはNode.jsがClaudeに含まれているのでPythonランタイムを別に導入したり自分でパッケージ化したりしなくてよい点を、Node.jsを勧める理由に挙げている。だからといってPythonサーバーがすべて依存関係を丸ごとバンドルしなければならないわけではない。従来のpython種別はパッケージをバンドルに入れる必要があり、コンパイル済みの依存関係に制限があるが、uv種別はその負担をホストに渡す。

マニフェスト仕様（v0.3） — 必須項目と設定UIの自動生成

manifest.jsonはバンドルに必ず含めるべき唯一のファイルである。公式ドキュメントはこのファイルを、MCPBが何をするか、どう実行するか、どのツールを提供するか、どんな設定が必要かを記述する必須のメタデータと説明する。MANIFEST.mdは現在のバージョンが0.3で、最終更新日が2025年12月2日であり、ほとんどの項目は任意であると述べる。必須項目だけの基本的なマニフェストは次のとおりである。

{
                      "manifest_version": "0.3",
                      "name": "my-extension",
                      "version": "1.0.0",
                      "description": "A simple MCP extension",
                      "author": {
                        "name": "Extension Author"
                      },
                      "server": {
                        "type": "node",
                        "entry_point": "server/index.js",
                        "mcp_config": {
                          "command": "node",
                          "args": [
                            "${__dirname}/server/index.js"
                          ]
                        }
                      }
                    }

MANIFEST.mdの説明によれば${__dirname}は拡張のディレクトリに置換される。ブログはこの値が拡張を展開したディレクトリのフルパスになると書く。利用者から値を受け取る必要があるサーバーは、user_configブロックを置く。公式ドキュメントは、user_configを定義するとClaude Desktopが拡張用の設定UIを自動生成すると説明している。ブログの例の解説はさらに具体的である。開発者が利用者にapi_keyを求めると宣言すると、Claudeはその値が入力されるまで拡張を有効にせず、値をOSの秘密情報の保管庫に自動で保管し、サーバーを起動するときに${user_config.api_key}を利用者が入力した値へ透過的に置き換える。

{
                      "manifest_version": "0.3",
                      "name": "my-extension",
                      "version": "1.0.0",
                      "description": "A simple MCP extension",
                      "author": {
                        "name": "Extension Author"
                      },
                      "server": {
                        "type": "node",
                        "entry_point": "server/index.js",
                        "mcp_config": {
                          "command": "node",
                          "args": ["${__dirname}/server/index.js"],
                          "env": {
                            "API_KEY": "${user_config.api_key}"
                          }
                        }
                      },
                      "user_config": {
                        "api_key": {
                          "type": "string",
                          "title": "API Key",
                          "description": "Your API key for authentication",
                          "sensitive": true,
                          "required": true
                        }
                      }
                    }

MANIFEST.mdがまとめている主なフィールドは次のとおりである。

  • manifest_version（必須、文字列）：このマニフェストが準拠する仕様のバージョンで、現在の例は0.3である。そのほかの必須項目はname、version（semver）、description、author（名前は必須で、メールアドレスとURLは任意）である。
  • server（必須、オブジェクト）：typeはnode、python、binaryのいずれかで、entry_pointで主となるサーバーファイルを指す。mcp_configにはcommand、args、envを置く。同じ文書が説明するuv種別ではホストが実行を管理するため、mcp_configは任意である。
  • user_config（任意、オブジェクト）：入力の型としてstring、number、boolean、directory、fileがある。title、description、required、default、multiple、min、maxも定義でき、文字列型でsensitiveを有効にすると入力が隠され安全に保存される。
  • compatibility（任意、オブジェクト）：platformsにdarwin、win32、linuxを指定し、runtimesにランタイムのバージョン要件を書く。ドキュメントの例はnode: ">=16.0.0"で、省略するとすべてのプラットフォームに対応するものとして扱われる。
  • icon（任意、文字列）：パッケージ内の相対パスまたはhttps://のURLである。公式ドキュメントは512×512ピクセルの透過PNGを推奨し、最小サイズを256×256とする。明暗のテーマや複数サイズが必要ならicons配列を使う。

置換変数は${user_config.KEY}のように書き、複数選択された項目は配列として別々の引数に展開される。MANIFEST.mdは、環境変数は機密データに向き、コマンド引数はパスや機密でないオプションに向くと付け加えている。

ビルドツール群 — @anthropic-ai/mcpb CLIのコマンドとパッケージング手順

公式ドキュメントが案内する流れは5段階である。MCPB CLIをインストールし、MCP SDKでstdioのMCPサーバーを作り、mcpb initでマニフェストを生成し、mcpb packでバンドルし、生成された.mcpbファイルをダブルクリックしてClaude Desktopに導入して試す。READMEも、フォルダに必要なファイルを集め、manifest.jsonを作り、アーカイブを作ることがバンドル化のすべてだと説明する。以前の@anthropic-ai/dxtパッケージは、READMEの表現では@anthropic-ai/mcpbへ移される予定である。

npm install -g @anthropic-ai/mcpb
                    
                    # 対話型でマニフェストを生成
                    mcpb init
                    
                    # マニフェストの構文検証
                    mcpb validate manifest.json
                    
                    # ディレクトリを.mcpbファイルへパッケージング
                    mcpb pack .

CLI.mdはコマンドを7つ挙げている。主なものは次のとおりである。

  • mcpb init [directory]：新しいマニフェストを対話形式で作る。拡張名、作者、拡張ID、表示名、バージョン、説明、作者のメールとURL、サーバー種別（Node.js、Python、Binary）、エントリーポイント、ツール構成、キーワード・ライセンス・リポジトリの情報を尋ねる。ブログは--yesオプションで最も基本的なマニフェストを素早く作れると書いている。
  • mcpb validate <path>：マニフェストをスキーマに照らして検証する。manifest.jsonのパスか、そのファイルを含むディレクトリを渡せる。
  • mcpb pack <directory> [output]：ディレクトリを.mcpbファイルにまとめる。manifest.jsonを自動で検証し、.git、node_modules/.cache、.DS_Storeのような一般的な開発用ファイルを除外し、最大圧縮のZIPを作る。
  • mcpb signとmcpb verify：signは証明書で.mcpbファイルに署名し、証明書と鍵のパス、中間証明書をオプションで渡せる。自己署名証明書を作って使う--self-signedもある。verifyは署名の有効性、証明書の主体と発行者、有効期間、フィンガープリントを表示し、自己署名なら警告する。

残る2つのコマンドはinfo（ファイルサイズ、署名状態、証明書情報を表示）とunsign（署名の削除で、開発とテスト用）である。READMEが示すNode.jsバンドルのディレクトリ構成は、manifest.json（必須）、server/index.js、バンドルされたnode_modules/、任意のpackage.jsonとicon.png、assets/である。

導入手順と配布方針 — ディレクトリ登録廃止とプラグイン連携

公式ドキュメントは、利用者が.mcpbファイルをClaude Desktopに自分で導入すると説明する。導入方法は次のとおりである。

  • ファイルエクスプローラーで.mcpbファイルをダブルクリックする。
  • 起動中のClaude Desktopのウィンドウに.mcpbファイルをドラッグ＆ドロップする。
  • Claude DesktopでSettings > Extensions > Advanced settings > Install Extension…を開き、.mcpbファイルを選択する。
  • ユーザー単位の導入：導入はユーザー単位なので、各利用者が自分のシステムに別々に導入する。

この3つの方法はいずれも導入UIを開く。ドキュメントによれば、利用者はこの画面で拡張の詳細と権限を確認し、必要な設定を入力し、権限を許可して導入を完了する。ブログは同じ画面を、人が読める拡張情報、必要な権限と設定、簡単なInstallボタンとして説明している。

配布には方針の変更がある。公式ドキュメントの同じページにある「Distribute your MCPB」の節は、利用者が.mcpbファイルを自分で導入すると書いたうえで、ディレクトリのデスクトップ拡張リストは非推奨（deprecated）となり、ディレクトリはもうMCPBの提出を受け付けないと述べている。ローカルMCPサーバーをディレクトリ経由で配布するには、そのサーバーをプラグインに含めるようにという案内が続く。ページの冒頭も、ディレクトリに載せるにはあらゆる画面に届くリモートMCPサーバーを作るか、ローカルサーバーをプラグインに含めるよう書いている。

したがって.mcpb形式は、内部向けや非公開の配布のためにファイルを直接渡す用途で使われ、ディレクトリへの掲載はプラグインの経路をたどる必要がある。エンジニアリングブログは公開当時、ディレクトリに拡張を提出する手順を案内していたが、現行のドキュメントはその経路が非推奨だと書いているため、記述は時点によって異なる。この記事は現行のドキュメントを基準にしている。TeamやEnterpriseの組織で拡張を配備するときの管理者制御（許可リスト、ポリシー設定）や最終利用者の導入体験は、Anthropicのサポート文書に別途案内されている。

MCPB構成要素別の公式記述と未確認事項の対照

ローカル拡張を実際の業務に導入するには、公式ドキュメントが述べている領域と、記載のない領域を区別する必要がある。以下の表はMCPBの構成要素ごとにその2つを対照したものである。

この対照をもとに設計するときに押さえる点は、ドキュメントから直接導けるものに限る。

  • プラットフォームの確認：ドキュメントは、主に1つのプラットフォームで開発する場合でもmacOSとWindowsの両方で試すよう勧めている。
  • パス入力：user_configはdirectory型とfile型に対応し、multipleで複数選択もできる。ファイル選択UIが任意のパスをどこまで許すかはドキュメントに記載がないので、自分で確認する必要がある。
  • 配布経路：ディレクトリへの提出が中止されたため、.mcpbファイルを直接渡すか、プラグインに含める。カスタムアップロードや許可リストのような組織レベルの管理者制御は、TeamとEnterpriseの文書が扱う。
  • 署名：mcpb signは証明書で署名し、自己署名証明書も作れる。verifyは自己署名なら警告を出す。署名を導入するなら、この警告の意味を先に決めておく必要がある。

  • 自作ランチャースクリプト経由でサーバーを多段起動した際におけるClaude Desktop内部の標準入力EOF処理の詳細仕様。

  • エンタープライズ管理者が未署名の.mcpbファイルの導入を一括禁止するためのグループポリシー（GPO）またはMDM設定キーの一覧。
