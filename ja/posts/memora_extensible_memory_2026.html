Memora — 長期タスク向け拡張型AIメモリシステム

コンテキスト忘却の壁を越え、AIエージェントが数日にわたる作業を記憶する方法

2026-07-01 IT・技術

はじめに：AIが記憶できないという問題

AIエージェントと複数日にわたるプロジェクトを進めた経験がある人なら、共通の不満を知っているはずだ。新しいセッションは毎回ゼロからスタートする。昨日の決定を今日また説明しなければならない。先週合意した制約が消えてしまう。128Kや200Kのコンテキストウィンドウがあっても、セッションが終わればすべてが消える。これはトークン数の問題ではなく、メモリアーキテクチャの問題だ。

Microsoft Researchはこの問題に正面から取り組むMemoraを公開した（MITライセンス、ICML 2026投稿）。2026年6月時点でGeekNewsで11ポイントを獲得したこのフレームワークは、AIエージェントが会話や文書から必要な情報を自動的に抽出し、長期にわたって保存・検索・更新できるよう設計されている。単純なRAGパイプラインや会話要約を付け加える方式と何が異なるのか、そしてこの設計がエージェントエコシステムにどんな意味をもたらすかを分析する。

本稿はMemora公式GitHubリポジトリと関連報道を基にしている。ベンチマーク数値は公開された実験結果を引用するが、ICML 2026投稿段階であり、まだ査読を経ていないことを前提に読むべきだ。

1. コンテキストウィンドウを拡大するだけでは不十分な理由

1.1 コンテキストウィンドウの物理的限界

コンテキストウィンドウはRAMに相当する。今実行中のものは保持できるが、プログラムが終了すれば消える。128Kトークンウィンドウでも約80K以降から想起率が低下するという研究がある。長い会話では前半の文脈をモデルが軽視し、直近の入力に偏る。また、コンテキストを満杯にすることは推論コストの面でも非効率だ。2026年6月時点で、フルコンテキスト方式はクエリあたり平均26,000トークン以上を消費するのに対し、うまく設計されたメモリシステムは7,000トークン未満で同等以上の精度を達成できるというデータが出ている。

1.2 エージェントの長期タスクとは

コーディングエージェントがリポジトリのリファクタリングを一週間かけて行う作業、調査エージェントが複数日にわたってレポートを完成させる作業、個人アシスタントがユーザーの好みと決定を蓄積してパーソナライズする作業。これらはすべて単一セッションでは終わらない。エージェントが昨日どのようにファイル構造を変更したか、ユーザーが一週間前にどんな制約を定めたかを覚えていなければ、次のステップは意味をなさない。コンテキストウィンドウはこの問題を技術的に解決しない。セッション境界がある以上、外部の長期メモリレイヤーは不可欠だ。

2. Memoraの3層メモリ構造

Memoraが既存のアプローチと最も明確に区別されるのは、メモリ項目の表現方式だ。各メモリは3つの構成要素に分離される。

2.1 Memory Value — 原文をそのまま保存

Memory Valueはインデックス化されない。元の情報を圧縮せずに保存する役割で、最終的にエージェントに渡されるコンテンツだ。インデックス対象から外すという設計決定が核心である。埋め込みモデルは長いテキストをベクトルに圧縮する過程で細部の情報を失い、意味を平坦化する。元の値をインデックス対象から除外することで、検索は抽象化レイヤーが担当し、配信は原文が担当するという役割分離が生まれる。

2.2 Primary Abstraction — メモリの正規単位

Primary Abstractionはインデックス化される。メモリ値のエッセンスを要約した一対一の表現であり、検索・更新・重複排除の基準点だ。新しい情報が入ってきたとき、既存のメモリと重複するかを判断する軸がこの抽象化だ。「Aliceがシアトルに引っ越す」というMemory Valueから、抽象化は「Aliceの引越し計画」のような、検索クエリと対照できる形になる。正規単位という表現が重要で、同じ事実が複数の表現で入ってきても、一つの抽象化の下にマージ・更新できる。

2.3 Cue Anchors — 複数の意味的入口

Cue Anchorsは一つのメモリに複数の角度からアクセスできるようにする多重インデックスだ。「エンティティ+核心側面」の組み合わせで構成され、多対多構造により複数のクエリが同じメモリ項目を見つけることができる。例えば「Aliceの転職」「シアトルへの引越し」「新しい職場」という異なる表現のクエリが同一のメモリ項目を取得できる。これは従来のベクトル検索のクエリ-文書類似度という単一軸への依存からの脱却だ。

2.4 この設計が意味すること

3層の分離は「何を保存するか」と「どのように見つけるか」を完全に分離する。埋め込みモデルの意味圧縮損失が元の情報に影響を与えず、検索精度は抽象化とCue Anchorsが担当する。この設計の実質的な効果はベンチマークで確認されている。LoCoMoでマルチホップ質問タイプ+23.1点、時間的推論+29.6点の向上が既存のメモリ方式比で報告された。

3. メモリライフサイクル — 収集から検索まで

3.1 収集（Ingestion）：会話と文書からの自動抽出

Memoraは会話や文書をトピック別エピソードに分割し、各エピソードから事実的・エピソード的・手続き的知識を構造化されたメモリ項目として自動抽出する。このプロセスはエージェントが明示的に「保存して」と指示しなくても自動で進む。収集段階で既存メモリとの重複を確認し、重なる情報はマージまたは更新される。別途重複項目を積み上げるのではなく、生きた知識ベースとして管理するという意味だ。

3.2 保存：ChromaDBとRedis

デフォルトのストレージはChromaDBで、Primary AbstractionとCue Anchorsをベクトル埋め込みとしてインデックス化する。Redisは高速な構造化照会のためのCueインデックスとして活用される。ローカルまたはリモートバックエンドの両方をサポートし、複数のエージェントが一つのメモリレイヤーを共有する構成も可能だ。エージェント別・役割別にメモリスコープを指定してアクセスを制御することも設計に含まれている。

3.3 検索：4つの戦略

戦略方式特徴
Semanticベクトル類似度検索高速で汎用的な意味マッチング
PromptedLLMによる多段階精製複雑なクエリに高い精度
Hybridベクトル+BM25キーワード意味とキーワードのバランス
GRPO強化学習ベース（実験的）ローカル軽量モデルでLLM呼び出し代替

GRPO（Group Relative Policy Optimization）戦略は特に注目に値する。Qwen 3B/7BなどをLoRAでファインチューニングした軽量モデルを検索ポリシー決定に使用することで、LLM API呼び出しコストを削減する実験的アプローチだ。まだ実験段階だが、コスト敏感な環境での重要な方向性を示している。

4. RAG・メモリフレームワーク対比でのMemoraの差別化

4.1 従来型RAGとの違い

RAGは事前構築された外部知識文書（Wiki、マニュアル、コードベースなど）をクエリに応じて検索し、LLMに注入する構造だ。ここで保存されるのは「世界知識」であり、更新サイクルが遅い。Memoraはこれとは異なり、エージェントが直接経験したこと — 特定ユーザーとの会話履歴、当該プロジェクトで下した決定、個人化された好み — を保存・更新することに焦点を当てる。両者は解決する問題が異なる。RAGとMemoraは競合関係ではなく補完関係だ。しかし多くのシステムがこの二つを混同し、文書RAGで会話メモリを代替しようとする誤った設計をしている。

4.2 フラットメモリストアとの違い

最も単純なメモリ実装は会話をテキストファイルやDBに蓄積し、ベクトル検索で類似した過去の会話を引き出す方式だ。この方法の限界は2つある。第一に、重複なく管理するのが難しい。同じ事実が複数の表現で繰り返し保存されると検索ノイズが生じる。第二に、更新が難しい。「Aliceの仕事が変わった」という情報が入ってきたとき、既存の項目を見つけて修正するのではなく新しい項目が追加される。MemoraのPrimary Abstraction基盤の正規単位管理はこの問題を直接解決する。

4.3 グラフベース知識ベースとの違い

MemGPT系やグラフメモリアプローチはエンティティと関係をグラフとして構造化する。表現力は高いが構築・保守コストが大きく、非構造化エピソード情報をグラフにマッピングするのが難しい。Memoraは外部グラフストアの代わりに内蔵された構造化表現（3層）で同様の目標を達成しようとする設計だ。2026年のトレンドが外部グラフストアから内蔵エンティティリンキングへと移行していることと一致する。

5. エージェントが数日にわたる作業を引き継ぐことの意味

5.1 プロジェクトの継続性

現在、AIエージェントと一週間のプロジェクトを進めると、毎セッションの最初の数分を「前回どこまでやったか」の再説明に費やす。長期メモリがうまく機能すれば、このオーバーヘッドがなくなる。エージェントが自ら昨日の決定を読み込み、今日の作業を引き継ぐ。コーディングエージェントなら、ファイル構造変更の履歴、決定の理由、保留中のタスクリストを記憶する。

5.2 パーソナライズの実質的な実現

パーソナライズは長らくAIの目標だったが、実質的な実装は限定的だった。セッションが終わるとユーザーの好みが消えるからだ。長期メモリがユーザーの作業スタイル、繰り返されるパターン、フィードバック履歴を蓄積すれば、エージェントの応答は時間とともにその人に最適化されていく。Memoraのマルチエージェントメモリ共有設計は複数のエージェントが同じユーザーコンテキストを共有できるようにもする。

5.3 音声エージェントと非視覚的インターフェース

音声インターフェースではユーザーが以前の会話履歴をスクロールしたりコピーしたりできない。長期メモリはこのような環境で特に不可欠だ。2026年にエージェントメモリ市場が年35%成長を記録している背景には、音声・車載・IoTデバイスへのAI普及という流れがある。

6. 実用的評価

6.1 強みが実際に機能する場所

Memoraが最も直接的な価値を発揮するシナリオは明確だ。数日〜数週間にわたるコーディングプロジェクト、ユーザーの好みと履歴を蓄積する必要がある個人アシスタント、複数のエージェントが共有コンテキストで分業するマルチエージェントシステム、文書が蓄積される知識管理パイプラインが代表的な事例だ。

6.2 注意すべき点

正直に書かなければならない注意点もある。第一に、ICML 2026投稿段階であり、ベンチマーク数値は著者側の結果で独立検証が必要だ。第二に、10倍スケールで時間的抽象化性能が25%低下するという報告がある。第三に、GRPO戦略は実験的段階であり、本番環境では慎重な検証が必要だ。第四に、ChromaDBのデフォルト設定以外の大規模分散ストレージとの統合には別途作業が必要だ。

6.3 現実的な導入アプローチ

まず自分のエージェント作業で「昨日の決定を今日覚えていなくて問題が生じたことがあるか」を確認しよう。そのようなケースがあれば、長期メモリレイヤーの価値が実証される。MemoraはPython 3.10以上でpip install -e .でインストールできるよう設計されており、既存のエージェントシステムへのプラグインとして追加できる。小さな作業から実験し、LoCoMoベンチマークスクリプトで直接性能を検証してみることが現実的な出発点だ。

7. 結論 — 長期記憶がエージェントの次のレイヤーを開く

Memoraが投げかける核心的な問いは単純だ。AIエージェントが真の長期的な協力者になるためには、記憶が必要だ。コンテキストウィンドウを無限に拡大する方向ではなく、何を記憶するかを選択し構造化する方向が現実的でコスト効率が高い。

Memoraの3層構造（Memory Value / Primary Abstraction / Cue Anchors）はこの問題への一つの明確な答えだ。元の情報と検索インデックスを分離し、更新可能な正規単位を置き、複数の意味的入口で取得精度を高める設計は、既存のRAGとフラットメモリの限界をうまく捉えている。

まだ初期公開段階であり、大規模環境での検証が残っている。しかし、この方向性そのもの — エージェントが数日にわたる作業を引き継ぐこと — は、2026年にAIエージェントが生産性ツールとして実用化される核心条件だ。Memoraはその方向の具体的な最初の実装の一つとして注目に値する。
