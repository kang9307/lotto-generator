서론: 틀린 가정 두 개

웹 애플리케이션의 결함 목록은 길다. 그런데 그 목록을 한 칸씩 뒤로 물러나서 보면 대부분이 같은 자리에서 출발한다. 서로 다른 이름이 붙어 있고 서로 다른 점검 항목에 흩어져 있을 뿐, 뿌리는 두 개의 문장이다.

가정 ① 「클라이언트는 못 바꾼다」 — 폼에 넣어 둔 값, HTML의 data- 속성, 쿠키, 요청 본문, 요청 헤더. 이 가운데 사용자가 바꿀 수 없는 것은 하나도 없다.
가정 ② 「공격자는 못 맞힌다」 — 재설정 토큰, 세션 값, 내부 식별자. 예측 가능한 값은 비밀이 아니다.

이 두 문장이 왜 중요한가 하면, 결함을 하나씩 외우는 대신 코드를 읽으며 판별할 수 있게 되기 때문이다. 어떤 값이 서버에 도착했을 때 「이 값이 우리가 보낸 그 값일 것」이라고 전제하는 코드가 보이면 그건 ①이다. 어떤 값을 비밀로 취급하는데 그 값을 만든 함수가 시각이나 순번을 재료로 쓰고 있으면 그건 ②다.

이 글은 열네 개의 구체적인 지점을 다룬다. 쿠키가 언제 실려 나가는지부터, 각각 중간 위험인 두 결함이 겹쳤을 때 무엇이 가능해지는지, 클라이언트가 계산한 금액을 서버가 받는 설계가 왜 성립하지 않는지, 그리고 식별 통제가 무너진 시스템의 로그가 무엇을 증명할 수 있고 무엇을 증명할 수 없는지까지. 모든 절은 취약한 코드와 안전한 코드를 나란히 놓고, 절 끝에서 그 결함이 ① 또는 ② 가운데 어느 가정에서 나왔는지 되짚는다.

쿠키 전송 규칙 자체를 요청 유형별로 더 세밀하게 보고 싶다면 SameSite Lax·Strict·None - 어느 요청에서 쿠키가 사라지는가가 따로 다룬다. 헤더가 중복으로 도착했을 때의 해석 문제는 같은 헤더가 두 번 오면에서 정리했다.

이 글의 범위. 여기서는 왜 위험한가와 어떻게 막는가만 다룬다. 동작하는 공격 코드, 우회 기법, 자동화 도구 사용법은 싣지 않는다. 마지막 절의 점검 방법도 본인이 운영하거나 명시적 권한이 있는 사이트에 한정된다. 코드 예시에 나오는 경로와 파일명은 전부 설명을 위한 가상의 값이다.

1. 브라우저는 언제 쿠키를 보내는가 - SameSite 세 값의 실제 동작

서버 코드를 읽다 보면 암묵적으로 깔려 있는 전제가 하나 있다. 「세션 쿠키가 붙어 있으니 우리 화면에서 온 요청이다.」 이 전제가 성립하는지는 서버가 정하지 않는다. 브라우저가 쿠키를 언제 붙이는지가 정한다. 그 규칙을 조정하는 것이 SameSite 속성이다.

정의는 MDN의 Set-Cookie 문서에 있다. SameSite=Strict는 쿠키를 설정한 사이트와 같은 사이트에서 시작된 요청에만 쿠키를 보낸다. SameSite=Lax는 같은 사이트 요청에 더해, 크로스사이트 요청 가운데 최상위 탐색이면서 동시에 안전한 메서드인 경우에만 쿠키를 보낸다. 같은 문서는 최상위 탐색을 「주소 표시줄의 URL이 바뀌는 요청」으로 정의하고, 안전한 메서드에서 제외되는 것으로 POST·PUT·DELETE를 명시한다. SameSite=None은 크로스사이트와 같은 사이트 요청 모두에 쿠키를 보내며, 이 값을 쓸 때는 Secure 속성도 함께 설정해야 한다.

# 취약: 속성이 하나도 없다. 스크립트가 읽을 수 있고, 평문으로도 나가고,
#      크로스사이트 요청에 붙을지 여부가 브라우저 기본값에 맡겨진다.
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/

# 취약: 크로스사이트 전송을 명시적으로 열어 두었다.
#      임베드가 필요해서 켜 두고 그대로 남은 형태가 흔하다.
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/; SameSite=None; Secure

# 안전: 세션 쿠키의 기본형.
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/; HttpOnly; Secure; SameSite=Strict

# 안전: 외부에서 들어오는 링크로 로그인 상태가 유지되어야 하는 화면이 있다면 Lax.
#      Strict는 외부 링크를 타고 들어온 첫 요청에서 로그아웃처럼 보인다.
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/; HttpOnly; Secure; SameSite=Lax

1.1 세 값이 실제로 무엇을 막는가

표 1. SameSite 값별 쿠키 전송 여부. 기준은 MDN Set-Cookie 문서(2026-08 확인)의 정의이며, 「미지정」 행은 명시적 값이 없을 때 브라우저 기본값에 위임되는 상태를 뜻한다.
SameSite 값같은 사이트 요청크로스사이트 최상위 탐색(GET)크로스사이트 POST·서브리소스권고되는 사용처
Strict보냄안 보냄안 보냄세션 쿠키의 기본 선택
Lax보냄보냄안 보냄외부 링크로 로그인 유지가 필요할 때
None + Secure보냄보냄보냄크로스사이트 임베드가 실제로 필요한 쿠키만
미지정보냄브라우저에 따라 다름동작을 가정할 수 없음없음. 값을 항상 명시한다

1.2 기본값에 기대면 안 되는 이유

MDN의 Set-Cookie 문서는 「일부 브라우저는 SameSite가 지정되지 않으면 Lax를 기본값으로 쓴다」고 적는다. 문장에 「일부」가 들어 있다는 점이 핵심이다. 그리고 기본값으로 적용되는 Lax는 명시적으로 지정한 Lax와 같지 않다. 같은 문서의 설명은 이렇다. 기본값으로 적용될 때는 더 관대한 형태가 쓰이며, 이 형태에서는 쿠키가 설정된 지 2분이 지나지 않았다면 POST 요청에도 쿠키가 포함된다.

쿠키 전송 조건을 명시하지 않으면 그 판단은 브라우저 기본값에 위임되고, 기본값은 브라우저와 버전에 따라 달라질 수 있는 값이다.

  • 기본값은 코드 리뷰에서 「기본이 Lax니까 괜찮다」는 근거로 쓰기 어렵다. 근거가 자기 코드 밖에 있기 때문이다
  • 더 관대한 기본 Lax의 2분 창은, 로그인 직후에 이어지는 흐름과 시간대가 겹친다
  • None을 쓰면서 Secure를 빠뜨린 쿠키는 브라우저가 거부한다. 결과는 「보안이 약해진 상태」가 아니라 「쿠키가 아예 안 붙는 상태」라서, 기능 장애로 먼저 드러나는 편이다
  • SameSite의 판단 단위는 오리진이 아니라 등록 가능 도메인이다. 같은 도메인 아래의 다른 호스트는 같은 사이트로 취급된다
  • OWASP Session Management Cheat Sheet는 세션 쿠키가 SameSite=Strict를 우선으로, 또는 Lax를 명시적으로 설정해야 한다고 적는다

가정 되짚기 — ①. 「우리 화면에서 보낸 요청만 도착한다」는 전제는 요청의 출처를 클라이언트 쪽 사정에 맡긴 것이다.

2. CSRF 토큰이 막는 것과 못 막는 것

CSRF는, OWASP Cross-Site Request Forgery Prevention Cheat Sheet의 정의에 따르면, 악성 웹사이트·메일·블로그·메신저·프로그램이 인증된 사용자의 브라우저를 속여 신뢰된 사이트에서 원치 않는 동작을 수행하게 만드는 공격이다. 같은 문서는 성립 조건을 한 문장으로 요약한다. 브라우저 요청은 세션 쿠키를 포함한 모든 쿠키를 자동으로 싣기 때문에, 적절한 인가가 쓰이지 않는 한 이 공격은 통한다.

여기서 「적절한 인가」가 뜻하는 것은 로그인 여부 확인이 아니다. 로그인은 이미 되어 있다. 필요한 것은 이 요청이 우리 화면에서 시작됐다는 증거이고, 그 증거는 브라우저가 자동으로 붙이지 않는 값이어야 한다.

CSRF 토큰이 하는 일은 요청의 출처를 증명하는 것이다. 그래서 그 값은 브라우저가 자동으로 붙이지 않는 값이어야 하고, 자동으로 붙는 쿠키만으로는 그 역할을 대신할 수 없다.

2.1 Synchronizer Token - 서버가 기억하는 값

OWASP Cross-Site Request Forgery Prevention Cheat Sheet가 설명하는 동기화 토큰 패턴에서 토큰은 서버 측에서 생성되고, 세션당 한 번 또는 요청마다 생성된다. 서버는 요청에 실려 온 토큰이 자기가 세션에 저장해 둔 값과 일치하는지 검증한다. 자동으로 붙지 않는 값이므로, 다른 사이트에서 만든 요청에는 그 값이 들어 있을 수 없다.

<!-- 취약: 상태를 바꾸는 폼인데 자동으로 붙는 값(쿠키)만으로 인증된다 -->
<form method="POST" action="/api/items/delete">
  <input type="hidden" name="item_id" value="PLACEHOLDER_ID">
  <button type="submit">삭제</button>
</form>

<!-- 안전: 서버가 세션에 저장해 둔 값을 폼에 실어 보낸다 -->
<form method="POST" action="/api/items/delete">
  <input type="hidden" name="csrf_token" value="PLACEHOLDER_TOKEN_FROM_SESSION">
  <input type="hidden" name="item_id" value="PLACEHOLDER_ID">
  <button type="submit">삭제</button>
</form>
// 취약: 로그인 여부만 본다. 요청이 어디서 시작됐는지는 보지 않는다.
function handleDelete(req, res) {
  if (!req.session.userId) return res.status(401).end();
  deleteItem(req.body.item_id);
  res.status(200).end();
}

// 안전: 세션에 저장된 토큰과 요청의 토큰을 상수 시간 비교로 대조한다.
function handleDelete(req, res) {
  if (!req.session.userId) return res.status(401).end();

  const expected = req.session.csrfToken;         // 서버가 기억하는 값
  const provided = req.body.csrf_token;           // 요청이 가져온 값
  if (!expected || !provided || !timingSafeEqual(expected, provided)) {
    return res.status(403).end();                 // 검증 실패는 거부, 통과가 아니다
  }
  deleteItem(req.body.item_id);
  res.status(200).end();
}

2.2 Double Submit Cookie와 그 한계

서버가 상태를 저장하기 어려운 구조에서는 이중 제출 패턴을 쓴다. 같은 값을 쿠키와 요청 본문에 각각 넣고 서버는 둘이 같은지만 본다. 문제는 서버가 그 값을 기억하지 않는다는 데 있다. OWASP Cross-Site Request Forgery Prevention Cheat Sheet는 단순한 이중 제출이 대상 도메인에 쿠키를 쓸 수 있는 공격자에게 우회 가능하다고 명시하며, 그 경로로 취약한 형제 서브도메인, DNS 탈취, 평문 HTTP를 통한 쿠키 주입을 든다. 같은 문서의 권고는 서명된 이중 제출이다. 서버 측 비밀 키로 세션 데이터에 토큰을 묶어 HMAC 처리한다.

// 취약: 두 값이 같은지만 본다. 그 값이 어디서 왔는지는 확인하지 않는다.
function verifyCsrf(req) {
  return req.cookies.csrf === req.body.csrf_token;
}

// 안전: 세션에 묶인 값을 서버 비밀 키로 서명한다.
//       쿠키를 쓸 수 있다는 것만으로는 유효한 토큰을 만들 수 없다.
function issueCsrf(session) {
  const nonce = randomTokenHex(32);                       // 암호학적 난수
  const mac   = hmacSha256(SERVER_SECRET, session.id + '.' + nonce);
  return nonce + '.' + mac;
}
function verifyCsrf(req) {
  const [nonce, mac] = String(req.body.csrf_token || '').split('.');
  if (!nonce || !mac) return false;
  const expected = hmacSha256(SERVER_SECRET, req.session.id + '.' + nonce);
  return timingSafeEqual(expected, mac);                  // 세션과 묶여 있는지까지 검증
}

토큰이 막지 못하는 것도 분명히 해 두는 편이 낫다. OWASP Cross-Site Request Forgery Prevention Cheat Sheet는 대문자로 강조해 적어 두었다. XSS는 모든 CSRF 완화 기법을 무력화한다. 페이지 안에서 공격자 코드가 실행되고 있으면 그 코드는 DOM에서 토큰을 읽어 요청에 붙일 수 있다. 토큰은 「외부 사이트가 만든 요청」을 걸러 낼 뿐, 「우리 페이지 안에서 만들어진 요청」은 걸러 내지 못한다.

  • 토큰 검증에 실패했을 때의 기본 동작은 거부여야 한다. 로그만 남기고 통과시키는 구현은 통제가 없는 것과 같다
  • 커스텀 헤더 방식도 유효하다. 같은 OWASP 문서는 모든 최신 브라우저가 커스텀 헤더가 붙은 요청을 프리플라이트 대상으로 지정하므로, 서버가 그 헤더의 존재를 확인하면 브라우저에서 온 요청이라면 프리플라이트를 거쳤음을 알 수 있다고 설명한다
  • 다만 커스텀 헤더 방식은 Access-Control-Allow-Origin이 느슨하면 무너진다. 와일드카드 오리진은 이 방어를 무효로 만든다
  • 토큰을 GET 요청의 쿼리 문자열에 실으면 로그·리퍼러·브라우저 기록에 남는다. 상태 변경은 GET으로 노출하지 않는다
  • 세션당 하나의 토큰과 요청마다 새 토큰 중 어느 쪽이든 유효하다. 요청마다 새로 발급하는 쪽은 병렬 탭에서 앞선 토큰이 무효가 되는 문제를 함께 설계해야 한다

가정 되짚기 — ①. 「이 요청은 우리 폼이 만든 것이다」가 이 절의 가정이다. 출처를 증명하는 값이 없으면 그 문장은 검증되지 않은 추정으로 남는다.

3. 두 결함이 겹칠 때 - 각각 중간, 합치면 치명적

점검 항목을 하나씩 보면 이 두 가지는 각각 그리 심각해 보이지 않는다.

  • 결함 A — 상태 변경 엔드포인트에 CSRF 토큰 검증이 없다. 단독으로는 중간 수준이다. 브라우저 기본값이 크로스사이트 POST에 쿠키를 안 붙이는 방향으로 움직여 왔고, 그 기본값이 사실상의 완화 장치 노릇을 한다
  • 결함 B — 세션 쿠키에 SameSite=None; Secure가 설정돼 있다. 단독으로는 설정 항목으로 분류된다. 값 자체는 유효하고, 임베드가 필요한 서비스라면 정당한 선택일 수도 있다

그런데 이 둘이 같은 시스템에 함께 있으면 성격이 달라진다. B가 브라우저 쪽 완화 장치를 명시적으로 꺼 버린다. 그러면 크로스사이트 요청에도 세션 쿠키가 실려 나간다. 이때 A 때문에 서버에는 요청의 출처를 판별할 수단이 아무것도 남아 있지 않다. 서버가 보는 것은 유효한 세션 쿠키가 붙은 상태 변경 요청 하나뿐이고, 그 요청이 자기 화면에서 시작됐는지 다른 곳에서 시작됐는지 구분할 근거가 없다.

개별 점검표는 항목에 등급을 매기지만, 실제 위험은 항목이 아니라 항목 사이의 관계에서 생긴다. 항목별 채점표에는 관계를 적는 칸이 없다.

3.1 위험도는 더하기가 아니라 곱하기다

표 2. CSRF 토큰 부재(결함 A)와 SameSite=None 설정(결함 B)의 단독 상태와 조합 상태 비교. 등급 열은 항목 단위로 채점하는 일반적 점검표에서 각 항목이 받는 상대적 취급을 나타낸 것이며, 특정 표준의 공식 등급 체계가 아니다.
상태브라우저의 쿠키 전송서버의 출처 검증결과항목 단위 점검표에서의 취급
결함 A만 있음 (CSRF 토큰 없음)기본값이 크로스사이트 POST를 대체로 차단없음브라우저 기본값에 의존하는 상태중간
결함 B만 있음 (SameSite=None)크로스사이트에도 전송CSRF 토큰으로 차단토큰이 막아 냄정보 또는 낮음
결함 A + 결함 B크로스사이트에도 전송없음외부 출처의 상태 변경 요청이 사용자 세션으로 처리됨어느 항목에도 잡히지 않음

마지막 행의 오른쪽 칸이 이 절의 요점이다. 항목별 점검표는 A는 A의 등급을, B는 B의 등급을 준다. 두 항목 모두 「즉시 조치」 기준을 넘지 않으면 둘 다 대기열 아래로 내려간다. 그런데 실제 위험은 경로에 있고, 경로는 항목 사이의 관계에서 생긴다.

  • 같은 구조가 반복되는 조합은 더 있다. 예측 가능한 식별자 + 소유권 검증 누락, 로그인 후에도 유지되는 세션 + 세션 값을 외부에서 심을 수 있는 경로, 관대한 Access-Control-Allow-Origin + 자격 증명 허용
  • 조합을 보려면 항목을 세는 대신 요청 하나가 처리되는 경로를 끝까지 따라가야 한다. 브라우저가 무엇을 붙이는가, 서버가 무엇을 확인하는가, 확인하지 않는 것은 무엇인가
  • 등급을 낮게 준 항목이라도 「이 항목이 지금 무엇에 의존해 완화되고 있는가」를 함께 적어 두면 조합이 드러난다. A의 완화 근거가 브라우저 기본값이었다면, 그 기본값을 끄는 설정이 어딘가에 있는지 곧바로 확인할 대상이 된다
  • 수정 우선순위도 달라진다. A와 B 중 어느 하나만 없애도 경로는 끊긴다. 임베드가 실제로 필요 없다면 B를 되돌리는 쪽이 대개 더 싸다

가정 되짚기 — ①. A와 B는 모두 「요청이 어디서 왔는지 클라이언트 쪽 사정이 알려 줄 것」이라는 같은 가정 위에 서 있다. 그래서 겹쳤을 때 서로를 상쇄하지 않고 증폭한다.

4. 쿠키에 사용자 식별자를 넣으면 생기는 일

구현하다 보면 편해서 손이 가는 형태가 있다. 로그인할 때 쿠키에 사용자 번호를 넣어 두고, 이후 요청에서 그 값을 읽어 「누구의 요청인지」 판단하는 것이다. 조회 한 번을 줄여 준다.

# 취약: 사용자 번호가 쿠키에 그대로 들어 있다.
Set-Cookie: uid=1042; Path=/
Set-Cookie: role=member; Path=/

# 취약: 사람이 읽을 수 있는 형태로 신원이 담긴 세션 값.
Set-Cookie: session=user-1042-member; Path=/; HttpOnly

# 안전: 값 자체는 아무 의미가 없고, 신원은 서버가 그 값으로 조회한다.
Set-Cookie: session=PLACEHOLDER_OPAQUE_128BIT_VALUE; Path=/; HttpOnly; Secure; SameSite=Strict

OWASP Session Management Cheat Sheet의 요구는 명확하다. 세션 ID의 내용은 정보 노출을 막기 위해 아무 의미가 없어야 하며, 세션 ID는 클라이언트 쪽에서 단순한 식별자여야 하고 그 값에 민감 정보나 개인식별정보가 절대 포함되어서는 안 된다. 같은 문서는 엔트로피도 함께 명시한다. 무차별 대입 추측을 막기 위해 최소 64비트의 엔트로피가 필요하고, 16진수 인코딩이라면 그 엔트로피를 얻기 위해 최소 16자가 필요하다.

IDOR는, OWASP Insecure Direct Object Reference Prevention Cheat Sheet의 정의에 따르면, 웹 애플리케이션의 URL이나 파라미터에 쓰인 식별자를 조작해 객체에 접근하거나 객체를 수정할 수 있게 되는 취약점이다. 같은 문서는 이 결함이 객체, 그 객체를 가리키는 참조, 그리고 빠져 있는 객체 수준 인가 검사라는 세 요소로 성립한다고 정리한다.

// 취약: 요청이 알려 준 사용자 번호로 조회한다.
//       조회 대상의 소유자와 요청자가 같은지 아무도 확인하지 않는다.
function getOrder(req, res) {
  const uid = req.cookies.uid;                    // 클라이언트가 정한 값
  const order = db.findOrder(req.params.orderId);
  res.json(order);                                // 소유권 검증 없음
}

// 안전: 신원은 서버 세션에서만 얻고, 소유권을 조회 조건에 넣는다.
function getOrder(req, res) {
  const uid = req.session.userId;                 // 서버가 기억하는 값
  if (!uid) return res.status(401).end();

  // 찾은 다음 비교하는 대신, 애초에 내 것만 찾는다.
  const order = db.findOrderOwnedBy(req.params.orderId, uid);
  if (!order) return res.status(404).end();       // 존재 여부도 흘리지 않는다
  res.json(order);
}

추측 난이도는 접근 통제가 아니다. OWASP Insecure Direct Object Reference Prevention Cheat Sheet는 복잡한 식별자를 쓰더라도 접근 통제 검사는 필수이며, 공격자가 인가되지 않은 객체의 URL을 얻더라도 애플리케이션이 여전히 그 접근을 차단해야 한다고 적는다.

4.1 쿠키 속성별로 정확히 무엇을 막는가

표 3. 쿠키 속성별로 차단되는 위협과 차단되지 않는 위협. 「막는 것」·「막지 못하는 것」 열은 MDN Set-Cookie 문서의 속성 정의에서, 「세션 쿠키 권고」 열은 OWASP Session Management Cheat Sheet에서 온 것이다.
속성막는 것막지 못하는 것세션 쿠키 권고
HttpOnly스크립트가 document.cookie로 값을 읽는 것스크립트가 만든 요청에 그 쿠키가 실려 나가는 것필수
Secure평문 http: 요청에 쿠키가 실리는 것HTTPS 위에서 일어나는 모든 문제필수
SameSite값에 따라 크로스사이트 요청에 쿠키가 붙는 것같은 사이트 안에서 만들어진 요청Strict 우선, 필요 시 Lax
Max-Age / Expires브라우저에 쿠키가 남는 기간서버 측 세션의 수명. 서버에서 별도로 만료시켜야 한다세션은 비영속 쿠키
Path / Domain쿠키가 붙는 범위같은 범위 안의 취약한 경로가능한 한 좁게
  • MDN의 Set-Cookie 문서는 HttpOnly로 만들어진 쿠키라도 자바스크립트가 시작한 요청에는 여전히 실려 나간다고 명시한다. 값을 못 읽는 것과 값이 안 쓰이는 것은 다르다
  • 같은 문서에 따르면 Expires와 Max-Age가 모두 설정되면 Max-Age가 우선하고, 값이 0이거나 음수면 즉시 만료된다
  • 쿠키 만료는 클라이언트 쪽 정리일 뿐이다. OWASP Session Management Cheat Sheet는 세션이 만료되면 클라이언트와 서버 양쪽에서 무효화해야 하며, 보안 관점에서 후자가 가장 중요하고 필수라고 적는다
  • 같은 문서는 인증 토큰·세션 ID·JWT·리프레시 토큰 등 자격 증명을 localStorage나 sessionStorage에 저장하지 말라고 명시한다
  • 권한을 쿠키에 담는 것도 같은 문제다. role=member가 클라이언트에 있으면 그것은 표시용 힌트이지 인가 근거가 될 수 없다

가정 되짚기 — ①. 「쿠키는 우리가 심었으니 우리가 쓴 값 그대로다」가 이 절의 가정이다. 쿠키는 서버가 발급하지만 보관하는 쪽은 클라이언트다.

5. 예측 가능한 재설정 토큰 - 예측 가능한 값은 비밀이 아니다

비밀번호 재설정 링크에 실리는 토큰은 그 순간 인증 수단을 대신하는 값이다. 유효한 토큰을 가진 쪽이 계정의 비밀번호를 바꾼다. 그래서 이 값의 품질은 로그인 비밀번호의 품질과 같은 층위에서 다뤄야 한다.

CWE는 이 결함에 별도의 번호를 부여해 두었다. CWE-640은 「원래 비밀번호를 몰라도 비밀번호를 복구하거나 변경할 수 있는 메커니즘이 있는데, 그 메커니즘이 약한」 상태를 Weak Password Recovery Mechanism for Forgotten Password로 명명한다. 상위 항목은 CWE-1390 Weak Authentication과 CWE-287 Improper Authentication이다. 즉 이 결함은 인증 결함으로 분류된다. 부가 기능의 문제가 아니라 인증 경로가 하나 더 있는데 그쪽이 약한 상태다.

5.1 난수의 출처가 전부다

MDN은 Math.random() 문서 상단에 경고를 달아 두었다. 「Math.random()은 암호학적으로 안전한 난수를 제공하지 않는다. 보안과 관련된 어떤 용도로도 사용하지 말 것. 대신 Web Crypto API를, 더 정확히는 Crypto.getRandomValues() 메서드를 사용할 것.」 같은 문서는 「구현이 난수 생성 알고리즘의 초기 시드를 선택하며, 사용자가 그것을 고르거나 재설정할 수 없다」고도 적는다. 시드를 통제할 수 없다는 것은 안전하다는 뜻이 아니다. 그 값이 무엇을 재료로 만들어지는지에 대한 보장이 없다는 뜻이다.

예측 가능한 값은 비밀이 아니다. 값을 비밀로 취급하는 코드와 그 값을 만드는 코드가 서로 다른 전제 위에 있으면, 비밀로 다뤄지는 것은 값이 아니라 그 값을 만든 함수에 대한 믿음이다.

// 취약: 시각과 사용자 번호를 재료로 쓴다. 두 재료 모두 외부에서 좁혀진다.
function makeResetToken(userId) {
  return md5(Date.now() + '-' + userId);
}

// 취약: 난수 함수를 쓰긴 했으나 암호학적 난수원이 아니다.
function makeResetToken() {
  return Math.random().toString(36).slice(2, 12);
}

// 취약: 순번. 발급받은 값 하나로 이웃 값의 형태가 드러난다.
function makeResetToken(seq) {
  return 'reset' + String(seq).padStart(8, '0');
}

// 안전: 암호학적 난수원에서 충분한 길이로 뽑는다.
function makeResetToken() {
  const buf = new Uint8Array(32);                 // 256비트
  crypto.getRandomValues(buf);
  return [...buf].map(b => b.toString(16).padStart(2, '0')).join('');
}

5.2 토큰 하나로는 부족하다

OWASP Forgot Password Cheat Sheet가 요구하는 것은 난수 품질만이 아니다. 토큰은 암호학적으로 안전한 난수 생성기로 생성되고 무차별 대입을 막을 만큼 충분히 길어야 하며, 사용된 뒤에는 무효화되어야 한다. 같은 문서는 사용자 열거 방지도 함께 요구한다. 존재하는 계정과 존재하지 않는 계정에 대해 일관된 메시지를 반환하고, 공격자가 어떤 계정이 존재하는지 알아내지 못하도록 응답이 일관된 시간 안에 돌아오게 해야 한다. 링크가 열리는 페이지에는 리퍼러 유출을 피하기 위해 noreferrer 값의 Referrer Policy를 지정하라고 적혀 있고, 재설정 URL을 만들 때 Host 헤더에 의존하지 말고 하드코딩하거나 신뢰 도메인 목록으로 검증하라고 명시한다. 기존 세션에 대해서는 사용자에게 모든 기존 세션을 무효화할지 묻거나, 자동으로 무효화하라고 권고한다.

// 취약: 토큰을 평문으로 저장하고, 만료도 1회용 처리도 없다.
//       재설정 뒤에도 예전 로그인 세션이 그대로 살아 있다.
async function requestReset(email) {
  const user = await db.findUserByEmail(email);
  if (!user) return { ok: false, message: '가입되지 않은 이메일입니다' };  // 계정 존재 여부 노출
  const token = makeResetToken(user.id);
  await db.saveResetToken(user.id, token);
  await sendMail(email, 'https://example.com/reset?token=' + token);
  return { ok: true };
}

// 안전: 해시로 저장, 만료 설정, 1회용, 응답은 항상 동일.
async function requestReset(email) {
  const user = await db.findUserByEmail(email);
  if (user) {
    const token = makeResetToken();                       // 암호학적 난수
    await db.saveResetToken({
      userId:    user.id,
      tokenHash: sha256(token),                           // 원문은 저장하지 않는다
      expiresAt: Date.now() + RESET_TTL_MS,               // 짧은 만료
      usedAt:    null                                     // 1회용 표시
    });
    await sendMail(email, RESET_BASE_URL + '?token=' + token);  // Host 헤더 아님
  }
  await constantDelay();                                  // 응답 시간을 맞춘다
  return { ok: true, message: '해당 주소로 안내를 보냈습니다' };  // 항상 같은 문구
}
// 안전: 재설정을 완료하는 쪽의 처리.
async function completeReset(token, newPassword) {
  const row = await db.findResetByHash(sha256(token));
  if (!row) return fail();
  if (row.usedAt) return fail();                    // 이미 쓴 토큰
  if (row.expiresAt < Date.now()) return fail();    // 만료된 토큰

  await db.markResetUsed(row.id);                   // 먼저 소진 처리
  await db.updatePassword(row.userId, hashPassword(newPassword));
  await db.invalidateAllSessions(row.userId);       // 기존 세션 전부 무효화
  await db.invalidateOtherResetTokens(row.userId);  // 남아 있는 다른 토큰도 정리
  await notifyPasswordChanged(row.userId);          // 본인에게 사실 통지
  return ok();
}
  • 토큰을 데이터베이스에 평문으로 저장하면, 저장소를 읽을 수 있게 된 쪽이 곧바로 계정 인수 수단을 얻는다. 비밀번호와 같은 이유로 해시해 저장한다
  • 토큰을 URL 쿼리에 싣는 방식은 널리 쓰이지만, 그만큼 서버 접근 로그·프록시 로그·브라우저 기록·리퍼러라는 네 개의 부수 경로를 만든다
  • 재설정 요청 자체에 속도 제한이 없으면 열거와 대량 시도의 통로가 된다. CWE-640은 재설정 시도에 대한 속도 제한 부재를 결함 유형의 하나로 든다
  • 「가입되지 않은 이메일입니다」는 친절한 문구지만, 그 자체로 계정 존재 여부를 알려 주는 응답이다. 존재 여부를 알려 주지 않으면서 안내를 제공하는 문구가 필요하다
  • 재설정 완료 후 기존 세션을 남겨 두면, 재설정의 목적 자체가 절반만 달성된다. 비밀번호를 바꾼 이유가 「누군가 들어와 있는 것 같아서」라면 특히 그렇다

가정 되짚기 — ②. 「공격자는 못 맞힌다」가 이 절의 가정이다. 시각·순번·일반 난수 함수는 모두 이 가정에 기대는 재료다.

6. eval()이 금지된 진짜 이유 - 숫자 변환이 코드 실행이 되는 순간

eval()이 나쁘다는 말은 널리 퍼져 있지만, 그 이유가 「느려서」로 기억되는 경우가 많다. 실제 이유는 다르다. MDN의 eval() 문서는 이 함수를 인젝션 싱크로 규정한다. 전달된 인자가 동적으로 파싱되어 자바스크립트로 실행되며, 이런 API는 크로스사이트 스크립팅 공격의 매개가 될 수 있다는 것이다. 같은 문서는 「직접 eval()을 절대 쓰지 말 것」이라는 항목에서 첫 번째 이유를 이렇게 적는다. 「eval()은 전달된 코드를 호출자의 권한으로 실행한다.」

문자열 하나를 숫자로 바꾸려던 코드가, 문자열의 내용에 따라 임의 코드 실행 지점이 된다. 그 코드는 로그인된 사용자의 화면이 할 수 있는 모든 일을 할 수 있다.

// 취약: 입력을 숫자로 바꾸려고 eval을 쓴다.
//       입력이 숫자가 아니면 그 내용이 코드로 실행된다.
const qty = eval(document.getElementById('qty').value);

// 취약: 서버가 준 문자열을 데이터로 신뢰하고 코드로 평가한다.
const data = eval('(' + responseText + ')');

// 취약: setTimeout에 문자열을 넘기면 내부적으로 같은 평가가 일어난다.
setTimeout('refreshPanel(' + panelId + ')', 1000);

// 안전: 숫자는 숫자로 바꾼다.
const raw = document.getElementById('qty').value;
const qty = Number.parseInt(raw, 10);
if (!Number.isInteger(qty) || qty < 1 || qty > MAX_QTY) {
  return showError('수량이 올바르지 않습니다');
}

// 안전: JSON은 JSON 파서로 읽는다.
const data = JSON.parse(responseText);

// 안전: 콜백은 함수로 넘긴다.
setTimeout(() => refreshPanel(panelId), 1000);

같은 이유로 이름으로 속성에 접근하려고 문자열을 조립해 평가하는 패턴도 피한다. MDN의 eval() 문서가 드는 대안은 대괄호 표기다. eval('obj.' + name) 대신 obj[name]을 쓴다. 값이 사용자로부터 온다면 허용 목록으로 이름을 검증하는 단계를 함께 둔다.

6.1 CSP가 이 문제를 다루는 방식

MDN의 Content-Security-Policy 문서는 unsafe-eval을 이렇게 설명한다. 「기본적으로 CSP에 default-src 또는 script-src 지시자가 있으면, 인자를 자바스크립트로 평가하는 함수들이 비활성화된다. 여기에는 eval(), setTimeout()의 code 인자, Function() 생성자가 포함된다.」 그리고 unsafe-eval 키워드가 그 보호를 되돌린다고 적으며 경고한다. 「개발자는 'unsafe-eval'을 피해야 한다. CSP를 두는 목적의 상당 부분을 무력화하기 때문이다.」

  • eval()을 코드에서 지우는 일과 CSP에서 unsafe-eval을 지우는 일은 순서가 있다. 코드가 남아 있는 상태에서 정책만 조이면 기능이 깨진다
  • 직접 쓰지 않아도 외부 라이브러리가 내부적으로 문자열 평가를 쓰는 경우가 있다. 정책을 조이면 그 지점이 콘솔 오류로 드러난다
  • MDN의 eval() 문서는 위험을 줄이는 수단으로 문자열 대신 신뢰 타입 객체를 넘기고 CSP의 require-trusted-types-for 지시자로 이를 강제하는 방식을 안내한다
  • 서버 쪽에도 같은 종류의 싱크가 있다. 문자열을 코드나 질의로 조립해 평가하는 지점은 언어를 가리지 않고 같은 성질을 가진다

가정 되짚기 — ①. 「이 문자열은 우리가 만든 숫자다」가 이 절의 가정이다. 그 문자열이 입력란·URL·응답 본문 중 어디서든 왔다면 내용은 클라이언트 쪽에서 정해진다.

7. 문자열로 HTML을 조립하면 - 컨텍스트별 이스케이프

출력 이스케이프에서 가장 흔한 오해는 「특수문자를 치환하는 함수 하나를 만들어 두고 전부 그걸로 통과시키면 된다」는 것이다. OWASP Cross Site Scripting Prevention Cheat Sheet의 답은 다르다. 「잘못된 인코딩 방식을 쓰면 취약점이 생기거나 애플리케이션 기능이 망가질 수 있다.」 값이 놓이는 자리가 달라지면 필요한 인코딩도 달라진다.

출력 이스케이프의 단위는 값이 아니라 값이 놓이는 자리다. 같은 값이라도 HTML 본문, 속성, 자바스크립트, URL, CSS에서 각각 다른 인코딩을 요구한다.

// 취약: 사용자 입력을 문자열로 이어 붙여 HTML로 해석시킨다.
el.innerHTML = '<span class="name">' + user.name + '</span>';

// 취약: 속성 자리에 따옴표 없이 값을 넣는다.
//       값에 공백만 들어가도 새 속성이 생기는 자리가 된다.
el.innerHTML = '<img src=' + imgPath + ' alt=프로필>';

// 안전: 값을 텍스트로 다루는 싱크를 쓴다.
const span = document.createElement('span');
span.className = 'name';
span.textContent = user.name;        // 절대 코드로 해석되지 않는다
el.replaceChildren(span);

// 안전: 속성은 setAttribute로 넣는다. 속성 이름은 코드가 정한다.
const img = document.createElement('img');
img.setAttribute('src', imgPath);
img.setAttribute('alt', '프로필');

OWASP Cross Site Scripting Prevention Cheat Sheet는 안전한 싱크를 따로 열거한다. elem.textContent, elem.insertAdjacentText(), elem.setAttribute(safeName, value), formfield.value, document.createTextNode()가 그것이다. 그리고 이렇게 권고한다. 「innerHTML 같은 안전하지 않은 싱크에 대한 참조를 제거하도록 코드를 리팩터링하고, 대신 textContent나 value를 쓸 것.」 HTML 구조 자체를 사용자 값에서 만들어야 하는 경우에만 검증된 HTML 새니타이저를 거친다.

// 취약: URL을 검증 없이 링크 속성에 넣는다.
//       스킴을 통제하지 않으면 값이 클릭 시 실행되는 형태가 될 수 있다.
a.href = profile.website;

// 안전: 스킴 허용 목록으로 먼저 거른다.
function safeHttpUrl(raw) {
  let u;
  try { u = new URL(raw, location.origin); } catch { return null; }
  return (u.protocol === 'https:' || u.protocol === 'http:') ? u.href : null;
}
const href = safeHttpUrl(profile.website);
if (href) { a.href = href; } else { a.removeAttribute('href'); }
  • 서버에서 이스케이프해 내려보낸 값이라도 클라이언트가 그 값을 innerHTML로 다시 넣으면 인코딩이 어긋난다. OWASP Cross Site Scripting Prevention Cheat Sheet는 서버 측 인코딩이 DOM 기반 결함에는 효과가 없다고 지적한다
  • 템플릿 엔진의 자동 이스케이프는 대체로 HTML 본문 컨텍스트를 기준으로 동작한다. 같은 값을 스크립트 블록 안이나 href에 넣을 때는 별도 처리가 필요하다
  • 속성에 값을 넣을 때 따옴표로 감싸는 것만으로도 인코딩해야 할 문자 집합이 줄어든다. 같은 문서가 이 점을 명시적으로 강조한다
  • 「이 값은 우리 데이터베이스에서 나왔으니 안전하다」는 판단은 성립하지 않는다. 그 값을 데이터베이스에 넣은 것도 대개 클라이언트다
  • 값을 저장할 때 이스케이프하면 표시 컨텍스트를 알 수 없는 상태에서 인코딩하는 셈이 된다. 이스케이프는 출력 시점에, 그 자리에 맞는 방식으로 한다

가정 되짚기 — ①. 「이 값은 우리가 통제한 값이다」가 이 절의 가정이다. 값의 내용이 클라이언트에서 정해질 수 있다면 통제되는 것은 값이 아니라 그 값을 놓는 자리다.

8. 가격을 클라이언트가 계산하면 안 되는 이유 - 신뢰 경계의 정의

주문 화면을 만들 때 자연스럽게 나오는 구조가 있다. 옵션을 고르면 화면에서 금액이 갱신되고, 결제 버튼을 누르면 화면에 표시된 총액이 요청에 담겨 서버로 간다. 사용자 입장에서 보이는 값과 처리되는 값이 일치하니 직관적이다.

// 취약: 금액 산출의 입력이 전부 DOM에서 읽은 값이다.
function buildOrder() {
  const unit  = Number(document.querySelector('#unit-price').dataset.price);
  const qty   = Number(document.querySelector('#qty').value);
  const disc  = Number(document.querySelector('#discount').dataset.rate);
  const total = Math.round(unit * qty * (1 - disc));

  return { itemId: currentItemId, qty, unitPrice: unit, discount: disc, total };
}

// 서버: 받은 값을 그대로 저장한다.
function createOrder(req, res) {
  const o = req.body;
  db.insertOrder({ itemId: o.itemId, qty: o.qty, total: o.total });  // 재계산 없음
  res.json({ ok: true });
}

이 구조에서 서버가 저장하는 금액은 서버가 계산한 값이 아니라 요청이 알려 준 값이다. unitPrice, discount, total 세 필드가 모두 클라이언트에서 왔고, 서버에는 이 값들이 자기 가격 정책과 일치하는지 확인하는 코드가 없다. 화면이 계산했으므로 맞을 것이라는 전제가 유일한 근거다.

// 안전: 클라이언트는 무엇을 사는지만 보낸다. 금액은 서버가 만든다.
function buildOrder() {
  return {
    itemId:    currentItemId,
    optionIds: selectedOptionIds,        // 선택 항목의 ID 목록
    qty:       Number(document.querySelector('#qty').value),
    displayedTotal: shownTotal           // 표시가. 대조용이지 근거가 아니다
  };
}

// 서버: 자기 가격표에서 다시 계산한다.
function createOrder(req, res) {
  const uid = req.session.userId;
  if (!uid) return res.status(401).end();

  const qty = Number.parseInt(req.body.qty, 10);
  if (!Number.isInteger(qty) || qty < 1 || qty > MAX_QTY) {
    return res.status(400).json({ error: 'INVALID_QTY' });
  }

  const item    = db.findSellableItem(req.body.itemId);          // 판매 가능 여부까지
  if (!item) return res.status(400).json({ error: 'INVALID_ITEM' });

  const options = db.findOptionsOf(item.id, req.body.optionIds); // 이 상품의 옵션인지
  if (options.length !== req.body.optionIds.length) {
    return res.status(400).json({ error: 'INVALID_OPTION' });
  }

  const rate  = pricing.discountRateFor(uid, item);              // 서버가 판단
  const total = pricing.total(item, options, qty, rate);         // 서버가 계산

  if (req.body.displayedTotal !== total) {                       // 표시가와 다르면
    return res.status(409).json({ error: 'PRICE_CHANGED', total });  // 재확인 요구
  }

  db.insertOrder({ itemId: item.id, qty, total, userId: uid });
  res.json({ ok: true, total });
}

8.1 신뢰 경계란 무엇인가

표준 정의는 CWE에 있다. CWE-501 Trust Boundary Violation의 설명에 따르면, 신뢰 경계는 프로그램을 가로질러 그은 선이며, 선의 한쪽에서 데이터는 신뢰되지 않고 다른 쪽에서는 신뢰할 수 있는 것으로 간주된다. 같은 문서는 검증 로직의 목적을 「데이터가 신뢰 경계를 안전하게 넘어 신뢰되지 않는 상태에서 신뢰되는 상태로 이동하게 하는 것」으로 규정한다.

이 글에서는 그 정의를 웹 애플리케이션으로 좁혀 쓴다. 웹에서 신뢰 경계는 브라우저와 서버 사이에 있다. 브라우저 쪽에서 만들어진 값은 전부 신뢰되지 않는 쪽에 있고, 그 값이 네트워크를 건너 서버에 도착하는 순간이 경계를 넘는 순간이며, 경계를 넘어온 데이터는 예외 없이 검증 대상이다. 화면에 그려지는 값도, 스크립트가 계산한 결과도, 요청에 담기는 필드도 모두 경계의 바깥쪽에 있다.

클라이언트는 의도를 보내고, 서버는 결과를 만든다. 「이 상품의 이 옵션을 이만큼」은 의도이고, 「그러니까 얼마」는 결과이며, 결과는 경계의 안쪽에서만 만들어질 수 있다.

이 정의에서 따라 나오는 실무 규칙은 세 가지다.

  1. 클라이언트는 의도를 보내고, 서버는 결과를 만든다. 금액·권한·상태 전이는 전부 결과에 속한다
  2. 화면에서 지운 것은 지운 것이 아니다. 버튼을 숨기고 입력란을 읽기 전용으로 만드는 것은 사용성 개선이지 통제가 아니다. 통제는 요청을 처리하는 쪽에 있어야 한다
  3. 클라이언트 검증은 안내이고, 서버 검증은 통제다. 둘 다 필요하지만 역할이 다르다. 클라이언트 검증만 있는 필드는 검증되지 않은 필드다

경계에 놓인 값을 판별하는 질문도 세 개면 충분하다.

  • 이 값은 서버가 만들어 낸 값인가, 요청이 가져온 값인가
  • 이 값이 요청이 가져온 값이라면, 서버가 그 값의 유효 범위를 자기 데이터로 확인하는가
  • 확인한다면, 그 확인을 모든 진입 경로에서 하는가
  • 금액만의 문제가 아니다. 권한 등급, 판매자 식별자, 배송비, 포인트 사용액, 쿠폰 적용 여부처럼 서버 정책이 결정해야 할 값이 요청 본문에 들어 있으면 같은 구조다
  • 상태 전이도 마찬가지다. 「배송 완료로 바꿔 달라」는 요청에서 전이 가능 여부를 판단하는 것은 서버의 상태 기계이지 화면이 아니다
  • 서버 재계산이 있어도 표시가와의 대조가 없으면 사용자 혼란이 생긴다. 앞의 예시가 409로 되돌리는 이유는 보안이 아니라 표시가와 청구가가 다른 상황을 막기 위한 것이다
  • 모바일 앱이나 외부 연동처럼 진입 경로가 여러 개면 재계산 로직은 공통 계층에 두어야 한다. 경로마다 따로 두면 다음 절의 문제가 된다

가정 되짚기 — ①. 가장 순수한 형태다. 「화면이 계산했으니 맞다」는 문장에서 계산 주체는 클라이언트다.

9. 같은 코드베이스 안의 비대칭 - 일관성 없는 통제는 없는 통제다

실제 코드베이스를 열어 보면 통제가 있느냐 없느냐로 딱 갈리는 경우는 드물다. 훨씬 흔한 것은 어떤 엔드포인트에는 있고 어떤 엔드포인트에는 없는 상태다. 최근에 만든 화면에는 토큰 검증이 들어 있고, 오래전에 만든 관리 화면에는 없다. 목록 조회는 소유권을 확인하는데 내려받기는 확인하지 않는다.

// 취약: 라우트마다 개별적으로 붙인다. 붙이는 것을 잊으면 그냥 열린다.
app.post('/api/items/create', requireCsrf, requireAuth, createItem);
app.post('/api/items/update', requireCsrf, requireAuth, updateItem);
app.post('/api/items/delete',              requireAuth, deleteItem);  // 빠졌다
app.post('/api/admin/purge',                            purgeItems);  // 둘 다 빠졌다

// 안전: 기본을 차단으로 두고, 예외만 명시한다.
//       새 라우트를 추가할 때 아무것도 안 하면 보호되는 쪽이 기본이 된다.
const CSRF_EXEMPT = new Set([
  'POST /api/webhooks/inbound'   // 세션 쿠키를 쓰지 않는 경로만. 근거를 주석으로 남긴다
]);

app.use((req, res, next) => {
  if (SAFE_METHODS.has(req.method)) return next();
  if (CSRF_EXEMPT.has(req.method + ' ' + req.path)) return next();
  return requireCsrf(req, res, next);
});
app.use(requireAuth);   // 인증도 같은 방식으로 기본 적용 + 공개 경로만 예외

통제의 실효는 평균이 아니라 최솟값으로 결정된다. 방어하는 쪽은 모든 경로를 지켜야 하고 통과하려는 쪽은 한 경로만 찾으면 되기 때문이다.

  • 비대칭은 대개 시간에서 생긴다. 통제를 도입한 시점 이전에 만들어진 코드에는 그 통제가 없고, 이후 코드에는 있다. 도입 시점이 코드베이스를 두 층으로 나눈다
  • 사람에서도 생긴다. 같은 규칙을 알고 있어도 적용하는 습관은 사람마다 다르다. 규칙이 문서에만 있고 코드로 강제되지 않으면 편차가 남는다
  • 「내부용이라 괜찮다」는 예외가 가장 오래 남는다. 관리 화면, 배치 처리용 엔드포인트, 임시로 만든 점검 경로가 여기에 해당한다
  • 해결의 방향은 opt-in을 opt-out으로 뒤집는 것이다. 통제를 라우트마다 붙이는 대신 전역에 걸고 예외를 명시한다. 빠뜨림이 곧 보호로 이어진다
  • 예외 목록은 코드 안에 있어야 리뷰 대상이 된다. 설정 파일이나 문서에 있으면 변경이 리뷰를 우회한다
  • 같은 원리가 출력 이스케이프에도 적용된다. 기본 이스케이프를 켜고 예외만 명시적으로 표시하는 템플릿 구조가, 자리마다 함수를 부르는 구조보다 편차가 적다

가정 되짚기 — ①과 ② 모두. 통제의 존재 여부 자체가 클라이언트가 어느 경로로 들어오느냐에 달리게 된다. 그 순간 「어느 경로로 들어올지는 우리가 정한다」는 또 하나의 ①이 만들어진다.

10. 이 로그는 무엇을 증명하는가 - 부인방지

여기까지의 논의는 대체로 「무엇을 막는가」였다. 이 절은 조금 다른 질문을 다룬다. 막지 못했을 때, 남은 기록으로 무엇을 말할 수 있는가.

부인방지란, NIST 용어집이 SP 800-53 Rev. 5에서 인용하는 정의에 따르면, 특정 행위를 수행하고도 그것을 거짓으로 부인하는 개인에 대한 보호이며, 정보를 생성하거나 메시지를 보내거나 정보를 승인하거나 메시지를 수신하는 것과 같은 특정 행위를 어떤 개인이 했는지 판별할 수 있는 능력을 제공하는 것을 말한다. 같은 용어집이 인용하는 CNSSI 4009-2015도 같은 취지로 적고, NISTIR 4734는 더 짧게 「특정 행위를 수행한 데 대한 책임을 부인할 수 없음」이라고 적는다.

정의의 두 부분을 나눠 보면 실무적 의미가 드러난다. 앞부분은 「부인에 대한 보호」이고, 뒷부분은 「어떤 개인이 그 행위를 했는지 판별할 수 있는 능력」이다. 뒷부분이 성립하지 않으면 앞부분도 성립하지 않는다.

로그의 증명력은 식별 통제가 건전한 만큼만 성립한다. 「사용자 X가 삭제했다」는 기록은 그 X가 어디서 온 값인지에 따라 전혀 다른 문장이 된다.

10.1 로그의 「누가」는 어디서 오는가

로그 한 줄에 사용자 식별자가 적혀 있다고 해서 그 사용자가 그 행위를 했다는 뜻이 되지는 않는다. 그 식별자가 어디서 온 값인지에 따라 문장의 의미가 달라진다.

표 5. 로그에 기록된 행위자 식별자의 출처별 증명 범위. 「전제되는 통제」 열의 항목은 OWASP Session Management Cheat Sheet(세션 엔트로피·세션 고정 방지)와 OWASP Cross-Site Request Forgery Prevention Cheat Sheet(출처 검증)에서 온 것이다.
행위자 식별자의 출처그 값을 정한 주체전제되는 통제그 통제가 없을 때 기록이 뜻하는 범위
요청 본문의 필드클라이언트없음요청이 자신을 X라고 주장했다
클라이언트가 수정 가능한 쿠키클라이언트없음쿠키에 X라고 적혀 있었다
서버 세션 조회 결과서버세션 ID 엔트로피, 세션 고정 방지세션이 X의 것이었다
서버 세션 조회 + CSRF 검증서버세션 ID 엔트로피, 세션 고정 방지, 요청 출처 검증X의 화면에서 시작된 요청이었다

표의 각 행은 앞 절들과 그대로 대응한다. 4절에서 본 것처럼 사용자 식별자가 클라이언트가 고칠 수 있는 쿠키에 있거나 요청 본문에서 온다면, 그 기록은 X를 특정하지 못한다. 로그가 부정확한 것이 아니라, 로그가 기록한 대상이 「행위자」가 아니라 「요청이 주장한 값」인 것이다. 기록 자체는 정확하다. 기록이 가리키는 대상이 다를 뿐이다.

세 번째 행에서 한 걸음 더 들어가야 하는 이유가 세션 고정이다. 세션 고정은, OWASP Session Management Cheat Sheet의 정의에 따르면, 공격자가 피해자의 세션 ID를 알아내는 대신 피해자 브라우저에 세션 ID를 설정하는 공격이다. 같은 문서는 대책을 필수로 적는다. 「세션 ID는 해당 사용자 세션에서 권한 수준이 변경된 후에 반드시 갱신되거나 재생성되어야 한다」, 「세션 ID 재생성은 세션 고정 공격을 막기 위해 필수다」. 권한 수준 변경에는 미인증 상태에서 인증 상태로 바뀌는 로그인 시점이 포함된다.

// 취약: 로그인해도 세션 식별자가 그대로다.
//       로그인 전에 만들어진 세션 값이 로그인 후에도 유효하다.
function login(req, res) {
  const user = authenticate(req.body.id, req.body.pw);
  if (!user) return res.status(401).end();
  req.session.userId = user.id;                // 값만 채운다
  res.json({ ok: true });
}

// 안전: 인증에 성공한 시점에 세션 식별자를 새로 만든다.
function login(req, res) {
  const user = authenticate(req.body.id, req.body.pw);
  if (!user) return res.status(401).end();

  regenerateSessionId(req, () => {             // 이전 식별자는 폐기
    req.session.userId = user.id;
    req.session.authAt = Date.now();
    res.json({ ok: true });
  });
}

네 번째 행이 이 절에서 가장 자주 간과되는 지점이다. CSRF 방어가 없으면 「X의 세션으로 요청이 나갔다」는 사실조차 X의 의사를 뜻하지 않는다. CSRF는 정의상 사용자의 의도 없이 요청이 발생하는 공격이기 때문이다. OWASP Cross-Site Request Forgery Prevention Cheat Sheet의 정의가 그대로 이 결론을 담고 있다. 인증된 사용자의 브라우저가 속아서 원치 않는 동작을 수행하는 것. 세션은 진짜였고 요청도 진짜 그 브라우저에서 나갔지만, 그 행위를 하기로 결정한 주체는 사용자가 아니다.

10.2 무엇을 남기고 무엇을 남기지 않는가

OWASP Logging Cheat Sheet는 남길 항목을 언제·어디서·누가·무엇의 네 축으로 정리한다. 누가에 해당하는 항목은 「출처 주소, 예를 들어 사용자의 기기·머신 식별자, 사용자의 IP 주소」와 「사용자 신원(인증되었거나 달리 알려진 경우)」이다. 괄호 안의 조건절이 이 절 전체의 요약이다. 알려진 경우에만이다.

같은 문서는 로그와 부인방지의 관계에 대해 조심스러운 문장을 남긴다. 로그가 「부인방지 통제를 뒷받침한다(다만 부인방지라는 성질은 로그로 달성하기 어렵다. 로그의 신뢰성은 대개 기록하는 쪽이 적절히 감사받고 있다는 사실에만 근거하기 때문이다)」. 로그를 증거로 다루려면 로그 자체의 무결성이 먼저 필요하다는 뜻이다. 그래서 같은 문서가 「기록이 수정되거나 삭제되었는지 알 수 있도록 변조 탐지를 내장할 것」과 「가능한 한 빨리 로그 데이터를 읽기 전용 매체에 저장하거나 복사할 것」을 함께 요구한다.

// 취약: 행위자를 요청 본문에서 가져온다. 로그는 요청의 주장을 그대로 옮긴다.
function deleteRecord(req, res) {
  removeRecord(req.body.recordId);
  logger.info('record deleted', {
    actor:    req.body.userId,        // 클라이언트가 정한 값
    recordId: req.body.recordId
  });
  res.status(200).end();
}

// 안전: 행위자는 서버 세션에서만 가져오고, 판단 근거를 함께 남긴다.
function deleteRecord(req, res) {
  const actor = req.session.userId;                   // 서버가 아는 값
  if (!actor) return res.status(401).end();

  const rec = db.findRecordOwnedBy(req.body.recordId, actor);
  if (!rec) return res.status(404).end();             // 소유권 검증

  removeRecord(rec.id);
  logger.info('record deleted', {
    at:          new Date().toISOString(),            // 언제
    service:     SERVICE_ID,                          // 어디서
    actor:       actor,                               // 누가 (세션 기준)
    sessionRef:  hash(req.sessionID),                 // 세션 원값은 남기지 않는다
    sourceIp:    req.ip,
    userAgent:   req.get('user-agent'),
    action:      'record.delete',                     // 무엇을
    target:      rec.id,
    outcome:     'success',
    csrfChecked: true,                                // 어떤 검증을 통과했는지
    authMethod:  req.session.authMethod
  });
  res.status(200).end();
}

남기지 말아야 할 것도 명시돼 있다. OWASP Logging Cheat Sheet는 인증 비밀번호, 세션 식별 값(해시로 대체 가능), 접근 토큰, 암호화 키와 그 밖의 주요 비밀, 계좌·결제카드 정보, 민감한 개인정보를 기록하지 말라고 적는다. 위 예시가 세션 ID 대신 해시를 남기는 이유가 이것이다. 같은 세션에서 일어난 일을 묶어 볼 수는 있으면서, 로그를 읽을 수 있는 쪽이 세션을 재사용할 수는 없게 된다.

10.3 이것이 누구를 위한 통제인가

정리하면 이렇게 된다. 부인방지가 무너진 시스템의 로그로는 행위자를 특정할 수 없다. 이것은 누구의 잘못을 가리키는 문장이 아니라 그 상태에서 무엇이 가능하고 무엇이 불가능한지에 대한 기술적 서술이다. 식별 수단이 클라이언트에서 오면 로그의 「누가」는 주장이고, 출처 검증이 없으면 세션 기준의 「누가」도 의사를 뜻하지 않으며, 세션 재생성이 없으면 세션 자체의 귀속이 흔들린다.

  • 이것은 이용자 보호다. 자기가 하지 않은 행위가 자기 계정의 기록으로 남는 상황에서, 그 기록의 한계를 기술적으로 설명할 수 있어야 한다
  • 동시에 운영자 보호다. 책임 소재를 정확히 가릴 수 있어야 운영자도 근거 없는 분쟁에 휘말리지 않는다. 로그가 무엇을 증명하고 무엇을 증명하지 못하는지 스스로 알고 있는 쪽이 유리하다
  • 그래서 이 절의 통제는 「사고를 막는 통제」와 성격이 다르다. 사고가 났을 때 무엇을 말할 수 있는지를 미리 정하는 통제다
  • 기록의 증명력을 높이는 순서는 앞선 절들과 같다. 서버 세션 기반 식별 → 세션 재생성 → 출처 검증 → 로그 무결성. 뒤의 것부터 하면 앞의 것이 뚫린 상태로 남는다
  • 시각도 증명력의 일부다. OWASP Logging Cheat Sheet는 로그 날짜와 시각을 국제 표준 형식으로 기록하라고 적는다. 서버 간 시각이 어긋나면 사건 순서를 재구성할 수 없다

가정 되짚기 — ①과 ② 모두. 식별이 ①에 기대면 「누가」가 주장으로 내려앉고, 세션 값이 ②에 기대면 그 「누가」가 다른 사람일 수 있다.

11. CSP와 SRI - 마지막 방어선

앞의 절들이 「경계를 어디에 긋는가」였다면 이 절은 「경계가 뚫렸을 때 피해를 어디까지로 묶는가」다. 순서가 중요하다. 이 층은 앞의 통제를 대신하지 않는다.

CSP는, MDN의 Content-Security-Policy 문서의 정의에 따르면, 웹사이트 관리자가 특정 페이지에서 사용자 에이전트가 로드할 수 있는 리소스를 통제할 수 있게 하는 HTTP 응답 헤더이며, 크로스사이트 스크립팅 공격을 방어하는 데 도움을 준다. 같은 문서는 인라인 스크립트에 대해 「기본적으로 CSP에 default-src 또는 script-src 지시자가 있으면 인라인 자바스크립트는 실행이 허용되지 않는다. 여기에는 인라인 <script> 태그, 인라인 이벤트 핸들러 속성, javascript: URL이 포함된다」고 적는다. unsafe-inline 키워드가 이 보호를 되돌리며, 같은 문서는 「개발자는 'unsafe-inline'을 피해야 한다. CSP를 두는 목적의 상당 부분을 무력화하기 때문이다」라고 경고한다.

정책이 존재한다는 사실과 그 정책이 무엇을 막는가는 별개다. unsafe-inline과 unsafe-eval이 들어 있는 정책은 헤더는 있는데 보호는 크게 줄어든 상태다.

# 취약: 정책은 있지만 두 키워드가 보호를 되돌린다.
Content-Security-Policy: default-src *; script-src * 'unsafe-inline' 'unsafe-eval'

# 안전: 요청마다 새 nonce를 발급하고, 그 nonce가 붙은 스크립트만 실행한다.
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-PLACEHOLDER_RANDOM_PER_REQUEST' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none';

# 도입 단계: 먼저 위반만 보고받아 무엇이 걸리는지 확인한다.
Content-Security-Policy-Report-Only:
  default-src 'self';
  script-src 'self' 'nonce-PLACEHOLDER_RANDOM_PER_REQUEST';
  report-to csp-endpoint
  • nonce 값은 요청마다 새로 발급되어야 한다. 고정 nonce는 정책이 없는 것과 크게 다르지 않다
  • MDN의 Content-Security-Policy 문서는 지시자에 nonce나 해시가 들어 있으면 브라우저가 unsafe-inline을 무시한다고 적는다. 구형 브라우저 호환을 위해 둘을 함께 두는 구성이 가능한 이유다
  • 같은 문서에 따르면 해시 소스의 알고리즘 식별자는 sha256·sha384·sha512 중 하나여야 한다
  • strict-dynamic은 nonce나 해시로 신뢰된 스크립트가 동적으로 로드하는 스크립트까지 그 신뢰를 확장한다. 이 키워드가 있으면 호스트 목록·스킴·'self'·'unsafe-inline'은 모두 무시된다
  • frame-ancestors는 이 페이지를 <iframe> 등으로 embed할 수 있는 부모를 제한한다. 클릭재킹 대응의 현대적 형태다
  • 도입은 Content-Security-Policy-Report-Only로 시작한다. 같은 문서는 이 헤더가 코드 실행을 막지 않고 위반만 보고하므로 시험 단계에 쓰인다고 설명한다

11.1 SRI가 막는 것과 못 막는 것

서브리소스 무결성은, MDN의 Subresource Integrity 문서의 정의에 따르면, 브라우저가 가져온 리소스가 예상치 못하게 조작되지 않았는지 검증할 수 있게 하는 보안 기능이며, 가져온 리소스가 반드시 일치해야 하는 암호학적 해시를 지정하는 방식으로 동작한다. 같은 문서는 이 기능이 방어하는 위협을 공급망 공격으로, 구체적으로는 공격자가 서드파티 호스트를 장악해 파일에 악성 내용을 주입하거나 파일을 통째로 바꿔치기하는 경우로 든다. 동작은 단순하다. 브라우저가 받은 내용의 해시를 계산해 지정된 값들과 비교하고, 일치하면 로드하고 그렇지 않으면 로드를 거부하며 네트워크 오류를 반환한다.

<!-- 취약: 외부 호스트의 스크립트를 검증 없이 실행한다.
     그 파일이 바뀌면 우리 페이지에서 바뀐 코드가 그대로 돈다. -->
<script src="https://cdn.example.com/widget.js"></script>

<!-- 안전: 해시가 맞을 때만 실행한다.
     크로스오리진 요청은 CORS 모드여야 하므로 crossorigin 속성이 필수다. -->
<script src="https://cdn.example.com/widget.js"
        integrity="sha384-PLACEHOLDER_BASE64_HASH_VALUE"
        crossorigin="anonymous"></script>

crossorigin="anonymous"가 필요한 이유도 같은 문서가 설명한다. 리소스는 기본적으로 no-cors 모드로 로드되는데, 무결성 검증이 no-cors에서 허용되면 공격자가 해시 값을 바꿔 가며 시험해 리소스 내용에 대한 정보를 추론할 수 있다. 그 정보 유출을 막기 위해 브라우저는 no-cors 요청에 서브리소스 무결성을 허용하지 않으며, crossorigin이 없는 요청은 항상 실패한다.

  • SRI가 검증하는 것은 내용이 지정한 해시와 같은가뿐이다. 원 저작자가 처음부터 넣어 둔 로직은 해시가 맞으므로 그대로 통과한다
  • 버전이 바뀔 때마다 해시를 갱신해야 한다. 갱신 절차가 자동화되어 아무 검토 없이 새 해시를 받아 넣는다면 검증의 실효가 줄어든다
  • 내용이 수시로 바뀌는 스크립트에는 적용하기 어렵다. 그런 리소스는 자체 호스팅으로 옮기는 편이 대안이 된다
  • CSP는 브라우저 안에서만 작동한다. 인가 검사 누락, 클라이언트가 보낸 금액을 그대로 저장하는 처리, 예측 가능한 재설정 토큰에는 아무 영향이 없다
  • 두 기능 모두 나머지 방어가 뚫린 뒤에 작동하는 층이다. 이 층이 있다는 이유로 앞의 통제를 미루면 순서가 뒤집힌다

가정 되짚기 — 이 절은 가정을 고치지 않는다. CSP와 SRI는 ①과 ②가 이미 깨졌을 때 피해 범위를 좁히는 층이다.

12. 알면서도 안 고쳐지는 이유

여기까지의 내용에 새로운 것은 별로 없다. 인용한 문서들은 대부분 오래전부터 공개돼 있고 널리 참조된다. 그렇다면 남는 질문은 하나다. 왜 알려진 결함이 계속 남아 있는가. 「몰라서」가 아니라 「알아도 안 고쳐지는」 구조가 따로 있다.

  • 켜는 순간 깨진다. 오래된 코드베이스에 CSRF 보호를 전역으로 적용하면, 토큰을 넣지 않은 기존 폼과 비동기 요청이 전부 거부된다. 사용자에게 즉시 보이는 장애이고, 통제를 켜는 작업이 곧 회귀 위험을 안는 작업이 된다
  • 동작하는 코드를 건드리는 부담. 자동화된 시험이 얇을수록 이 부담은 커진다. 손댈 범위를 정확히 알 수 없으면, 고치는 쪽이 두는 쪽보다 위험해 보인다
  • 보안 부채는 사고 전에는 비용이 보이지 않는다. 성능 문제나 기능 결함과 달리, 남아 있는 동안에는 지표에 잡히지 않는다. 비용이 0으로 보이는 항목은 우선순위 회의에서 밀린다
  • 처리 주체가 없으면 접수는 처리로 이어지지 않는다. 통보를 받을 창구가 있어도 그 통보를 코드 변경으로 옮길 담당이 지정돼 있지 않으면 접수 기록만 쌓인다. 이는 역할 정의의 공백에서 생긴다
  • 기능 개발과의 우선순위 경쟁. 같은 인력이 두 가지를 하고, 한쪽만 일정에 이름이 있다
  • 범위를 모른다. 하나를 고치려고 열어 보니 같은 패턴이 얼마나 더 있는지 셀 수 없어서 착수 자체가 미뤄진다. 이 항목은 다음 절과 직접 이어진다

이 구조가 실제로 결과에 나타난다는 것은 공개 자료로 확인할 수 있다. Project Zero는 2022년 6월 30일 공개한 중간 집계에서 이렇게 적었다. 「2022년 6월 15일 기준으로, 2022년에 야생에서 악용된 것으로 탐지·공개된 0-day는 18건이다.」 그리고 「그중 최소 9건은 이전에 패치된 취약점의 변종이다.」 같은 글의 결론 문장은 이렇다. 「2022년 상반기에 관측된 0-day의 최소 절반은 더 포괄적인 패치와 회귀 시험으로 예방할 수 있었다.」 재악용까지 걸린 시간에 대한 서술도 있다. 「2022년 0-day 중 4건은 2021년 야생 0-day의 변종이다. 원래의 야생 0-day가 패치된 지 불과 12개월 만에, 공격자들은 원래 버그의 변종을 들고 돌아왔다.」

기한이라는 장치가 왜 존재하는지도 같은 맥락에서 읽을 수 있다. Project Zero의 Vulnerability Disclosure Policy는 벤더가 통보 후 90일 안에 패치를 제공하도록 하고, 패치 제공 후 30일이 지나면 상세 내용을 공개한다. 90일 안에 어렵지만 추가 14일 안에 가능하다면 유예를 부여할 수 있고, 실제 악용 증거가 있으면 90일 정책 대신 7일 정책이 적용되며 이 경우 유예는 3일이다.

기한을 문서로 정해 두었다는 사실 자체가, 기한이 없으면 수정이 지연된다는 경험적 판단을 담고 있다.

12.1 대응 수단별 비용과 효과

표 6. 통제 수단별 도입 비용·회귀 위험·차단 범위 비교. 비용과 위험은 절대 수치가 아니라 표 안의 일곱 항목을 서로 비교한 상대 등급이며, 기존 코드베이스에 사후 도입하는 상황을 기준으로 한다.
수단도입 비용회귀 위험막는 범위착수 순서 판단
쿠키 속성 정리 (HttpOnly·Secure·SameSite)낮음낮음 (임베드 사용처만 확인)좁음 — 전송 조건과 스크립트 읽기가장 먼저
CSP Report-Only 도입낮음없음 (차단하지 않음)없음 — 현황 파악용병행 가능
외부 스크립트에 SRI 추가낮음낮음 (해시 갱신 절차 필요)좁음 — 외부 파일 변조병행 가능
서버 측 소유권·인가 검사 보강중간중간넓음 — 데이터 접근 전반높은 우선순위
재설정 토큰 재설계중간낮음 (경로가 국지적)계정 인수 경로높은 우선순위

CSP 강제 전환높음높음중간 — 브라우저 안에 한정Report-Only 결과 확인 후

표의 마지막 열이 실무적으로 쓸모 있는 부분이다. 비용이 낮고 회귀 위험이 낮은 것부터 하면 착수가 막히지 않는다. 쿠키 속성 세 개를 붙이는 일은 대개 한 곳의 설정 변경이고 되돌리기도 쉽다. 반대로 CSRF 전역 적용을 첫 항목에 올리면 그 항목이 대기하는 동안 나머지도 함께 멈춘다.

가정 되짚기 — 이 절은 가정의 층위가 다르다. ①과 ②는 코드의 가정이고, 이 절이 다루는 것은 조직의 제약이다. 다만 결과는 같다. 경계가 그어지지 않은 채로 남는다.

13. 고쳤다는데 그대로인 경우 - 불완전 패치

수정이 이루어졌는데 같은 경로가 남아 있는 경우가 있다. 수정의 범위를 정하는 방식에서 생기는 문제이고, 유형은 대체로 네 가지다.

  1. 증상만 고치고 근본 원인은 그대로. 특정 화면에서 값이 그대로 그려지는 것이 확인되면 그 화면에만 이스케이프를 넣는다. 같은 값을 그리는 다른 화면, 같은 필드를 내려보내는 다른 응답은 손대지 않는다
  2. 변종 분석 부재. 같은 패턴이 코드베이스에 몇 개 더 있는지 세지 않는다. 보고된 한 곳만 고치면 나머지는 그대로 남고, 그 나머지가 다음 보고가 된다
  3. 클라이언트만 고치고 서버는 그대로. 버튼을 숨기고, 입력란을 읽기 전용으로 바꾸고, 화면 쪽 검증을 추가한다. 요청을 처리하는 코드는 그대로다
  4. 한 경로만 닫고 다른 경로는 남김. 특정 응답에서 필드를 제거했지만 같은 정보를 나르는 다른 엔드포인트, 오류 메시지, 캐시된 응답, 내려받기 파일이 남는다

신뢰 경계의 관점에서 클라이언트 수정은 방어가 아니다. 화면에서 버튼을 지우는 것은 그 요청을 보내기 어렵게 만드는 일이지, 그 요청이 도착했을 때 거부하는 일이 아니다.

// 수정 전: 권한 없는 사용자에게도 삭제 요청이 처리된다.
function deleteRecord(req, res) {
  removeRecord(req.body.recordId);
  res.status(200).end();
}

// 불완전한 수정: 화면에서 버튼을 감췄다.
// 서버 코드는 위와 동일하다. 경계는 그대로다.
if (!currentUser.isOwner) {
  document.querySelector('#delete-btn').style.display = 'none';
  document.querySelector('#delete-btn').disabled = true;
}

// 완전한 수정: 요청을 처리하는 쪽에서 판단한다.
function deleteRecord(req, res) {
  const actor = req.session.userId;
  if (!actor) return res.status(401).end();

  const rec = db.findRecordOwnedBy(req.body.recordId, actor);   // 소유권 검증
  if (!rec) return res.status(404).end();

  removeRecord(rec.id);
  res.status(200).end();
}
// 화면 쪽 버튼 숨김은 그대로 두어도 좋다. 다만 그것은 사용성이지 통제가 아니다.

두 번째 유형에 대해서는 앞 절에서 인용한 수치가 그대로 근거가 된다. Project Zero가 2022년 상반기 18건 중 최소 9건이 이전에 패치된 취약점의 변종이라고 적고, 최소 절반은 더 포괄적인 패치와 회귀 시험으로 예방 가능했다고 결론지은 것은 이 유형이 예외적 사례가 아니라 반복되는 패턴임을 보여 준다. 하나를 고칠 때 같은 패턴을 코드베이스 전체에서 검색해 세는 단계가 수정 작업의 일부여야 하는 이유다.

13.1 절차에 생기는 검증 공백

기술적 유형과 별개로, 수정 여부를 확인하는 절차에서도 같은 종류의 공백이 생긴다. 구조는 단순하다. 결함이 접수되고, 개발 주체에게 전달되고, 개발 주체가 「수정했다」고 회신하고, 그 회신으로 건이 종결된다. 이 흐름에는 「수정했다」는 진술을 확인하는 단계가 없다.

  • 회신이 사실인지 아닌지의 문제가 아니다. 회신이 성실하더라도 위의 네 가지 유형 중 하나에 해당할 수 있다. 고쳤다고 판단하고 회신했는데 변종이 남아 있는 경우가 가장 흔하다
  • 재검증이 없으면 종결은 상태가 아니라 절차의 끝이다. 그런데 종결이라는 표시는 「안전해졌다」는 오인을 만든다. 목록에서 사라진 항목은 더 이상 누구의 대기열에도 없다
  • 재검증에 드는 비용은 대개 최초 확인보다 낮다. 어디를 봐야 하는지 이미 알고 있기 때문이다. 그럼에도 절차에 단계가 없으면 수행되지 않는다
  • 수정 확인은 보고된 지점과 같은 패턴의 다른 지점 두 곳을 봐야 한다. 앞의 것만 보면 두 번째 유형을 그대로 통과시킨다

또 하나 구분해 둘 것이 있다. 감사 표시는 수정의 증거가 아니다. 보안 감사 페이지나 기여자 목록에 등재되는 것은 접수와 인지의 증거다. 그 결함을 알게 되었다는 사실을 기록한 것이지, 그 결함이 제거되었다는 사실을 기록한 것이 아니다. 여기에 비대칭이 있다. 인지에는 비용이 거의 들지 않고, 수정에는 비용이 든다. 그래서 인지는 빠르게 표시되고 수정은 천천히 진행된다. 두 지표를 같은 것으로 읽으면 실제 상태를 실제보다 좋게 추정하게 된다.

가정 되짚기 — ①. 세 번째 유형이 정확히 ①이다. 화면을 바꾸는 수정은 「클라이언트는 못 바꾼다」는 가정을 그대로 둔 채, 그 가정 위에 한 겹을 더 올린 것이다.

14. 내 사이트를 30분 안에 점검하는 법

이 절의 내용은 본인이 운영하거나 명시적 권한이 있는 사이트에 한정한다. 타인의 서비스를 무단으로 점검하는 행위는 법적 문제가 될 수 있다. 아래 방법은 전부 브라우저 개발자 도구로 자기 사이트의 응답을 읽는 수준이며, 요청을 조작하거나 반복 시도를 하는 내용은 포함하지 않는다.

이 30분이 답하는 질문은 결함 목록이 아니라 「우리 시스템은 지금 어느 가정 위에 서 있는가」이다.

14.1 5분 - 쿠키 속성

개발자 도구의 Application(또는 저장소) 탭에서 Cookies를 연다. 세션 쿠키 한 줄에서 볼 것은 네 개다.

  • HttpOnly 열에 표시가 있는가. 없으면 스크립트가 그 값을 읽을 수 있다
  • Secure 열에 표시가 있는가
  • SameSite 열의 값이 무엇인가. 비어 있으면 브라우저 기본값에 맡겨진 상태다. None이면 그 쿠키가 왜 크로스사이트로 나가야 하는지 설명할 수 있어야 한다
  • 세션 쿠키의 값이 사람이 읽을 수 있는 형태인가. 사용자 번호·이메일·권한 이름이 보이면 4절의 상태다

14.2 10분 - 응답 헤더

Network 탭에서 문서 요청(맨 위의 HTML 응답)을 골라 Response Headers를 본다.

  • Content-Security-Policy가 있는가. 없다면 11절의 층이 아예 없는 상태다
  • 있다면 'unsafe-inline'과 'unsafe-eval'이 들어 있는가. 들어 있으면 MDN이 경고한 그 상태다
  • Set-Cookie 줄의 속성이 14.1에서 본 것과 일치하는가. 여러 쿠키가 서로 다른 속성으로 설정되는 경우가 흔하다
  • 로그인 전후로 세션 쿠키 값이 바뀌는가. 10절의 세션 재생성이 이루어지고 있는지를 눈으로 확인할 수 있는 지점이다

14.3 10분 - 외부 스크립트

페이지가 어디서 코드를 가져오는지 세어 본다. 아래는 자기 사이트의 콘솔에서 돌리는 읽기 전용 확인 스니펫이다. 아무것도 바꾸지 않고 목록만 출력한다.

// 읽기 전용: 외부 호스트에서 오는 스크립트 중 integrity가 없는 것을 나열한다.
[...document.querySelectorAll('script[src]')]
  .filter(s => new URL(s.src, location.href).origin !== location.origin)
  .map(s => ({
    src:       s.src,
    integrity: s.integrity || '(없음)',
    crossorigin: s.crossOrigin || '(없음)'
  }))
  .forEach(row => console.log(row));

// 읽기 전용: meta 태그로 걸린 CSP가 있는지 확인한다.
console.log(
  document.querySelector('meta[http-equiv="Content-Security-Policy"]')?.content
  ?? '(meta CSP 없음 - 응답 헤더 쪽을 확인할 것)'
);
  • 외부 호스트 목록이 예상보다 길면, 그 각각이 페이지 안에서 코드를 실행할 수 있는 주체다
  • integrity가 없는 항목은 그 파일이 바뀌면 바뀐 대로 실행된다
  • 내용이 자주 바뀌어 SRI를 걸 수 없는 리소스라면, 자체 호스팅으로 옮길 수 있는지 검토 대상에 올린다

14.4 5분 - 재설정 토큰의 형태

자기 계정으로 비밀번호 재설정을 요청해 링크를 받는다. 확인할 것은 토큰의 형태와 수명이다.

  • 길이가 충분한가. 문자 집합이 무엇인가. 16진수 문자열이라면 5절의 기준으로 최소 자릿수를 넘는가
  • 연속해서 두 번 요청했을 때 두 값 사이에 눈에 보이는 규칙성이 있는가. 앞부분이 같거나 뒷자리만 조금씩 달라지면 시각이나 순번이 재료로 쓰였을 가능성이 있다
  • 한 번 사용한 링크를 다시 열면 어떻게 되는가. 그대로 재설정 화면이 뜨면 1회용 처리가 없는 상태다
  • 재설정을 마친 뒤, 다른 브라우저에서 열어 두었던 기존 로그인이 그대로 유지되는가
  • 존재하지 않는 주소로 재설정을 요청했을 때의 응답 문구가 존재하는 주소일 때와 같은가

가정 되짚기 — ①과 ②. 네 항목 중 하나라도 클라이언트 쪽 사정에 기대고 있으면 그 지점이 ①이고, 재설정 토큰의 형태에 규칙성이 보이면 그 지점이 ②다.

확인하지 못한 것

본문에 쓰지 않은 것들을 여기 모아 둔다. 근거를 확인하지 못한 내용은 싣지 않았다.

  • 재설정 토큰의 구체적 만료 시간. OWASP Forgot Password Cheat Sheet는 토큰을 사용 후 무효화하라고 명시하지만, 몇 분 또는 몇 시간이라는 구체적 수치는 제시하지 않는다. 본문에서 「짧은 만료」라고만 쓴 이유다
  • 불완전 패치에 대한 단축 기한. Project Zero의 Vulnerability Disclosure Policy와 Vulnerability Disclosure FAQ에는 불완전 패치를 위한 별도의 단축 기한 조항이 명시돼 있지 않다. 확인 가능한 것은 90일 기한, 패치 후 30일 공개, 14일 유예, 실제 악용 시 7일 기한과 3일 유예다. 불완전 패치와 관련해 인용할 수 있는 것은 정책이 아니라 변종 재악용에 대한 집계 수치다
  • 브라우저별 SameSite 기본값 현황. MDN의 Set-Cookie 문서는 「일부 브라우저가 Lax를 기본값으로 쓴다」고만 적는다. 어느 브라우저가 어느 버전부터 어떻게 적용하는지는 각자의 대상 환경에서 확인해야 한다
  • 산업 전반의 패치 지연 중앙값과 미패치 비율. 공개 자료마다 표본과 집계 정의가 달라 하나의 수치로 인용하지 않았다. 12절과 13절이 인용한 수치는 Project Zero가 자체 추적 대상에 대해 발표한 값이며, 그 범위 밖으로 일반화되지 않는다
  • SRI가 막지 못하는 것의 공식 목록. MDN의 Subresource Integrity 문서는 SRI가 방어하지 못하는 항목을 명시적으로 열거하지 않는다. 본문의 한계 서술은 SRI의 동작 정의에서 따라 나오는 범위까지만 적은 것이다
  • NIST 용어집의 신뢰 경계 표제어. NIST 용어집에서 해당 표제어를 확인하지 못했다. 그래서 8절의 표준 정의는 CWE-501의 설명을 인용했고, 웹으로 좁힌 정의는 이 글의 작업 정의임을 밝혀 두었다
  • 이 글의 코드 예시. 설명을 위한 형태이며 특정 실행 환경에서 검증한 코드가 아니다. 함수 이름과 경로는 전부 가상의 값이고, 실제 적용은 각자의 프레임워크가 제공하는 기능을 쓰는 편이 낫다

자주 묻는 질문

Q1. 쿠키에 사용자 번호가 그대로 보이는데 문제가 되나?

쿠키는 서버가 발급하지만 보관하는 쪽은 클라이언트다. 개발자 도구에서 값을 바꿔 다시 보낼 수 있으므로, 그 번호로 데이터를 조회하는 서버 코드가 있다면 조회 대상의 소유자와 요청자의 관계는 검증되지 않은 상태로 남는다. OWASP Insecure Direct Object Reference Prevention Cheat Sheet는 이 결함이 객체, 그 객체를 가리키는 참조, 그리고 빠져 있는 객체 수준 인가 검사라는 세 요소로 성립한다고 정리한다. OWASP Session Management Cheat Sheet는 세션 ID의 값이 정보 노출을 막기 위해 아무 의미가 없어야 하며 민감 정보나 개인식별정보를 포함해서는 안 된다고 요구하고, 무차별 대입 추측을 막기 위해 최소 64비트의 엔트로피가 필요하다고 적는다. 조치는 두 가지다. 첫째, 쿠키에는 의미 없는 세션 식별자만 두고 사용자 신원은 서버가 그 값으로 조회한다. 둘째, 조회할 때 소유자 조건을 질의 자체에 넣어 자기 것만 찾도록 한다. 식별자를 추측하기 어려운 값으로 바꾸는 것은 대책이 아니다. 같은 문서가 복잡한 식별자를 쓰더라도 접근 통제 검사는 필수라고 명시한다.

Q2. SameSite를 Strict로 바꾸면 CSRF 토큰은 없어도 되나?

OWASP Cross-Site Request Forgery Prevention Cheat Sheet는 SameSite를 단독 방어로 쓰지 말고 깊이 방어의 한 층으로 다루라고 명시한다. 이유는 세 가지다. 첫째, Lax는 안전하지 않은 메서드만 막으므로 상태를 바꾸는 동작이 GET으로 노출돼 있으면 그대로 통과한다. 둘째, SameSite의 판단 단위는 오리진이 아니라 등록 가능 도메인이어서 같은 도메인 아래의 다른 호스트는 같은 사이트로 취급된다. 셋째, 브라우저마다 기본값이 다르다. MDN의 Set-Cookie 문서는 일부 브라우저가 SameSite를 지정하지 않으면 Lax를 기본값으로 쓴다고만 적고, 기본값으로 적용되는 Lax는 더 관대한 형태여서 쿠키가 설정된 지 2분이 지나지 않았다면 POST 요청에도 쿠키가 실린다고 설명한다. Strict는 이 가운데 첫째와 셋째를 상당 부분 해소하지만 둘째는 남는다. 그래서 세션 쿠키에 Strict를 걸더라도, 상태를 바꾸는 요청에는 동기화 토큰이나 서명된 이중 제출 토큰을 함께 두는 구성이 권고된다.

Q3. HttpOnly를 걸었는데 왜 아직 XSS가 문제라고 하나?

HttpOnly가 막는 것은 단 하나, 스크립트가 document.cookie로 그 쿠키 값을 읽는 것이다. MDN의 Set-Cookie 문서는 HttpOnly로 만들어진 쿠키라도 자바스크립트가 시작한 요청에는 여전히 실려 나간다고 명시한다. 즉 페이지 안에서 코드가 실행되고 있다면 쿠키 값을 읽지 못해도 그 쿠키가 붙는 요청을 만들 수 있다. 값을 빼내는 대신 값을 쓰는 것이다. 같은 이유로 OWASP Cross-Site Request Forgery Prevention Cheat Sheet는 XSS가 모든 CSRF 완화 기법을 무력화한다고 강조해 적는다. 페이지 안에서 도는 코드는 정상 화면과 같은 권한을 가지므로 토큰을 DOM에서 읽어 요청에 붙일 수 있다. 정리하면 HttpOnly는 유출 경로 하나를 좁히는 유용한 통제이고, XSS 자체의 대책은 출력 이스케이프다. OWASP Cross Site Scripting Prevention Cheat Sheet는 innerHTML 같은 안전하지 않은 싱크에 대한 참조를 제거하도록 코드를 리팩터링하고 textContent나 value를 쓰라고 권고한다.

Q4. 비밀번호 재설정 링크가 한 번 쓴 뒤에도 열리는데 괜찮은가?

OWASP Forgot Password Cheat Sheet는 재설정 토큰을 사용된 뒤에 무효화하라고 명시한다. 한 번 쓴 링크가 다시 열려 재설정 화면이 뜬다면 그 요구가 구현돼 있지 않은 상태다. 문제가 되는 이유는 이 토큰의 성격에 있다. 재설정 토큰은 유효한 동안 인증 수단을 대신하는 값이고, CWE-640은 이 결함을 Weak Password Recovery Mechanism for Forgotten Password로 명명하며 상위 항목을 CWE-1390 Weak Authentication과 CWE-287 Improper Authentication으로 둔다. 즉 인증 결함으로 분류된다. 링크는 메일함, 브라우저 기록, 서버 접근 로그, 프록시 로그, 리퍼러에 남을 수 있어 재사용이 가능하면 그 잔여물 하나하나가 계정 인수 경로가 된다. 함께 확인할 것이 세 가지 더 있다. 토큰에 만료가 걸려 있는지, 저장소에는 원문 대신 해시가 저장되는지, 그리고 재설정을 마친 뒤 기존 로그인 세션이 어떻게 되는지다. 같은 문서는 사용자에게 모든 기존 세션을 무효화할지 묻거나 자동으로 무효화하라고 권고한다.

Q5. 로그에 사용자 아이디가 남아 있으면 그 사람이 한 것으로 볼 수 있나?

그 아이디가 어디서 온 값인지에 따라 다르다. 값이 요청 본문이나 클라이언트가 수정할 수 있는 쿠키에서 왔다면, 그 기록이 뜻하는 것은 요청이 자신을 그 사용자라고 주장했다는 사실까지다. 값이 서버 세션 조회에서 왔다면 세션이 그 사용자의 것이었다는 데까지 간다. 여기서 두 가지가 더 필요하다. OWASP Session Management Cheat Sheet는 세션 고정을 공격자가 피해자의 세션 ID를 알아내는 대신 피해자 브라우저에 세션 ID를 설정하는 것으로 정의하고, 세션 ID 재생성이 세션 고정을 막기 위해 필수라고 적는다. 이것이 없으면 세션 자체의 귀속이 흔들린다. 그리고 CSRF 방어가 없으면 세션이 진짜여도 그 요청이 사용자의 의사를 뜻하지 않는다. CSRF는 정의상 사용자의 의도 없이 요청이 발생하는 공격이기 때문이다. NIST 용어집이 SP 800-53 Rev. 5에서 인용하는 부인방지의 정의는 어떤 개인이 특정 행위를 했는지 판별할 수 있는 능력을 포함한다. 그 능력은 식별 통제가 건전한 만큼만 성립한다.

결론: 이 글이 주장하는 네 가지

요약 대신 명제로 닫는다. 이 글이 주장하는 것은 네 가지이고, 각각을 뒷받침하는 절을 함께 적는다.

  1. 클라이언트에서 온 값을 근거로 쓰는 코드는, 그 값이 무엇이든 검증되지 않은 상태다. 폼 값·data- 속성·쿠키·요청 본문·요청 헤더가 모두 여기에 해당한다. 근거: 4절(쿠키의 사용자 식별자), 8절(신뢰 경계의 정의와 서버 재계산), 13절(클라이언트만 고친 수정).
  2. 예측 가능한 값은 비밀이 아니다. 비밀로 다루는 값은 그 값을 만든 난수원까지 확인해야 성립한다. 근거: 5절(재설정 토큰과 CWE-640, Math.random()에 대한 MDN의 명시), 10절(세션 값의 귀속).
  3. 개별 등급이 낮은 결함도 조합되면 새로운 경로를 만들며, 항목 단위 점검표는 그 경로를 잡지 못한다. 근거: 3절(CSRF 토큰 부재와 SameSite=None의 조합), 9절(같은 코드베이스 안의 비대칭).
  4. 식별 통제가 무너진 시스템의 로그로는 행위자를 특정할 수 없다. 이는 이용자 보호이자 운영자 보호다. 근거: 10절(부인방지의 정의, 로그 항목의 출처별 증명 범위, 세션 고정과 CSRF가 각각 증명력에 미치는 영향).
