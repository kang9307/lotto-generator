往页面里放一个会动的图形，是一次决策

以 ThorVG 1.1 为基准线，重新审视网页动画的格式选型问题

2026年7月28日 开发/基础设施

引言：一个加载动画成了页面上最重的东西

做过几次性能审计的人都会反复遇到同一幕。既不是图片也不是字体，而是加载状态里转个不停的那个小动画，成了这个页面上最大的资源。原因往往很平淡：设计师交付了素材，工程师原样放进去，素材恰好是 GIF，颜色多，帧数长。没有人做错决定，结果却是坏的。

2026 年 7 月 22 日，ThorVG 1.1.0 发布。它是一款渲染 SVG 与 Lottie 的 C++ 矢量图形引擎，编译成 WebAssembly 之后也能在浏览器里运行，GeekNews 上还出现了浏览器演示。看到这类消息，很自然会跳到那我们是不是该换成 Lottie这个问题，但我认为这个问题的顺序错了。

往网页里加动效不是选库的问题，而是约束条件的问题。要表达什么，用户是否需要能够控制它，会重复多少次，移动网络上还能多花几 KB，以及对不想看到动效的用户呈现什么。这五项一旦确定，格式几乎就自动定下来了。不是因为引擎好才选它，而是只有当约束要求它时才选它。

所以这不是一篇 ThorVG 介绍。ThorVG 1.1 在这里只作为基准线，是用来确认浏览器矢量动画走到哪一步的坐标。其余篇幅留给如何切分六种选择、引入之后要付出什么，以及什么时候不该用。最后一个问题是本文最重要的部分。

1. 矢量与位图：分水岭不在分辨率

1.1 差别在于存了什么

常见解释停在矢量放大不会糊。这话没错，但不足以支撑决策。真正的差别在于文件里存了什么。

  • 位图存的是结果像素。体积大致跟随分辨率 × 帧数 × 颜色复杂度。无论画面简单还是复杂，铺满屏幕就要付出代价
  • 矢量存的是绘制方法。体积跟随图形数量与关键帧数量。分辨率翻倍，文件不变
  • 因此在把简单形状放大显示时矢量优势压倒性，图标、标志、线稿、进度指示都属于这一类
  • 反过来，把复杂形状缩小显示时矢量就吃亏了。每帧重算几千条路径，不如提前把像素烤好来得便宜
  • 矢量把开销推迟到绘制时刻。下载变轻了，但整个播放过程都在持续消耗 CPU 或 GPU
  • 位图把开销压在传输时刻。下载完成之后只剩解码，播放本身是可预测的

理解这个取舍关系，就能看出矢量永远更好为什么危险。矢量是用把计算搬到用户设备上来换取体积。如果主要用户群是低端安卓机，这次搬迁可能是净亏。

1.2 位图这一侧也有选择

提到动图人们条件反射想到 GIF，但翻开 MDN 的图像格式指南，情况并非如此。GIF 是8 位索引色，每帧最多 256 色，使用无损 LZW 压缩。因此一有渐变就出色带，为掩盖色带加入抖动又会拉低压缩率，体积反而增大。

MDN 建议无损静态图使用 PNG，而动画序列则考虑 WebP、AVIF 或 APNG。实际特性也支持这一点。

  • APNG 是把 PNG 扩展成无损动画的格式，按 MDN 的数据自 Chrome 59、Edge 12、Firefox 3、Opera 46、Safari 8 起获得支持。颜色自由度和透明通道都比 GIF 完整
  • WebP 同时支持有损与无损，也能承载动画。MDN 记载有损 WebP 在视觉质量相近时平均比 JPEG 小 25% 到 35%
  • AVIF 支持 8、10、12 位深度以及广色域与 HDR，也能做动画。但 MDN 明确指出一个限制：它不支持渐进式渲染，必须完整下载后才能显示
  • 动画 AVIF 在各浏览器之间支持度不一，MDN 建议配合 <picture> 提供备选格式

所以要脱离 GIF 就只能上 Lottie是一个错误的二分法。相当一部分问题，只要把 GIF 换成 APNG 或动画 WebP 就解决了。不增加任何运行时，不改动设计流程，无障碍处理也和普通图片保持一致。

2. 把选择放进一张表

实务中真正会纳入考虑的有六种。这张表不是排名，它存在的意义是让人看清加上某个约束之后，哪一行会被淘汰。

做法 体积特性 画质与缩放 运行时控制 无障碍处理 适合的场景
GIF 随帧数急剧增长，颜色多时最糟 256 色上限，放大后劣化 几乎没有，无法暂停或回退 只有替代文本，难以响应减弱动态 颜色简单的短循环，且以兼容性为先
APNG 与动画 WebP 优于 GIF，但仍与帧数成正比 全彩且透明通道完整 几乎没有 与图片相同，容易提供静态替代 直接替换 GIF，代价最小的路线
视频（MP4、WebM） 与时长成正比，长内容效率压倒性 分辨率固定，放大后劣化 播放、暂停、跳转均可 可配字幕与描述轨，受自动播放策略约束 实拍影像，持续数秒以上的场面
CSS 与 Web Animations 没有额外文件，只有几行代码 完全矢量或基于 DOM 完全可控，与状态联动自由 用媒体查询处理最干净 界面转场、强调与微交互

表里最常被忽略的是运行时控制那一列。GIF 和 APNG 一旦开始，用户就碰不到了。要为设置了减弱动态的用户停下 GIF，只能换成静态图，于是需要维护两套素材。而 CSS 一条媒体查询就结束了。这正是无障碍要求越强，基于代码的动画价值越高的原因。

3. Lottie 究竟是什么：选择 JSON 的代价

3.1 里面存了什么

Lottie 官方文档把这个格式定义为使用 JSON 表示数据的矢量动画格式。要点在于它装的不是像素，而是结构化的图层、图形、关键帧与插值方式。这个设计带来两个性质。

  • 人类可读，工具可处理。改颜色、换文本这类操作可以在运行时完成
  • 各平台共用同一个文件，只替换播放器。对于要把同一套动效发到网页、安卓与 iOS 的团队，这是实打实的优势
  • 代价是没有播放器它什么都不是。它不像图片格式那样被浏览器原生支持
  • JSON 重复多、文本长，尤其在用 base64 内嵌图片之后会急剧膨胀

为了解决最后这个问题才有了 dotLottie。按规范，.lottie 文件是用 Deflate 压缩的 ZIP 归档，MIME 类型为 application/zip+dotlottie。内部有必需的 manifest.json 和 animations/ 目录，可选的 images/ 目录可放 PNG、JPG、SVG、WebP 或 GIF。由于图片以压缩文件而非 base64 字符串的形式存在，含图片的动画节省最明显。LottieFiles 表示视复杂度可小 2 到 10 倍，但这出自格式提出方的说明，所以拿自己的素材实测更可靠。

3.2 格式支持与播放器支持是两回事

Lottie 落地翻车多半发生在这里。设计工具导出的文件，在每个播放器里并不会长得一样。有些功能只有特定播放器才有，有些功能哪里都没有。

ThorVG 在这方面算比较坦诚的。官方维基的 Lottie 支持文档把图形、描边、填充、变换、插值器、蒙版、遮罩、图层效果与文本列为支持项，同时直接给出数字：Expressions 的整体支持率为 75%（完全支持 72%，部分支持 3%）。随后它列出了具体限制。

  • 循环模式只有 cycle 和 pingpong 可用
  • propertyGroup(level) 只支持第 1 层
  • 图层名称访问因脚本引擎冲突而被停用
  • footage()、坐标转换、路径生成、posterize time、速度类属性、smooth()、offset 与 continue 循环模式、标记访问、摄像机属性、lookAt()、音频电平采样、路径切线数组均不支持
  • SVG 一侧，仓库也写明不支持 SVG Tiny 的动画、交互性与多媒体

读这份清单的正确方式不是ThorVG 不够用，而是确认一个事实：Lottie 看着像单一规范，实际上是一个各播放器支持范围各不相同的生态。所以选型时该问的不是要不要用 Lottie，而是我们要用的那个播放器，其支持表里有没有设计师实际会用的功能。

4. ThorVG 1.1 改了什么：只写发布说明能确认的部分

这一节只写官方仓库与发布说明中可核实的事实，不照搬宣传语。

ThorVG 是以 MIT 许可证分发的 C++ 矢量图形引擎。官方介绍称核心库的二进制体积维持在约 170KB 的水平，相对以桌面为主要目标设计的引擎属于较小的一档。可接受的输入包括 SVG 与 Lottie（JSON）、PNG、JPEG、WebP 与原始位图，以及 TTF 与 OTF 字体。渲染后端有四种：CPU 软件（SIMD）、OpenGL/ES、WebGL、WebGPU。

1.0.0 于 2026 年 1 月 31 日发布，1.1.0 于 2026 年 7 月 22 日发布。1.1.0 发布说明描述的变更如下。

  • 通过渲染管线优化与批处理改进实现的 GPU 渲染性能提升
  • 在 CPU 与 GPU 引擎之间更准确、更一致的描边渲染
  • 面向 WebCanvas 的字体加载架构改进，以及实验性的 OpenType（OTF）字体支持
  • 扩展的 Lottie 能力，包含实验性的 Dynamic Tweening 与更快的 Expressions 处理
  • Lottie 与 SVG 规范符合度的改进，提升与真实内容的兼容性
  • 平台层面新增 Android 的 OpenGL 支持、WebCanvas 多线程与可插拔字体提供者

请认真对待实验性标注。发布说明把 OpenType 字体支持与 Dynamic Tweening 明确标为实验性。这个标注不代表它不能用，而是代表它的行为可能改变。把产品的核心画面压在这类功能上，等到某个小版本渲染结果变了，也没有立场抱怨。

在浏览器里使用有两条路径。一条是 ThorVG 自己提供的 WebCanvas，把 C++ 引擎编译成 WebAssembly 并包上 JavaScript 接口。另一条是通过把 ThorVG 当作内部渲染器的播放器，例如 LottieFiles 的 dotlottie-web。后者门槛更低且备有框架封装，实务中通常先评估这一条。

采用方面，官方仓库列出了 Canva、Godot、LVGL、Tizen、Espressif 一类嵌入式目标以及 dotLottie 等。采用清单应当读作部署场景多样性的证据，而非质量担保。能同时出现在游戏引擎和嵌入式界面里，说明它依赖少、可移植性高。

5. 怎么读性能数字：在什么环境测的

这个领域的宣传材料很爱用倍数。可是抹掉条件的倍数没有任何意义。把最常被引用的四个数字连同条件整理如下。

被引用的数字 测量方 测量条件 这个数字说明不了什么
渲染约提升 80%，峰值内存约下降 70% Canva（采用方自测），经 LottieFiles 博客发布 在 iOS 上与此前使用的 rLottie 对比，工作负载为视频导出与播放管线 浏览器性能。对比基准是另一款原生库，不是浏览器播放器
CPU 光栅化性能对比（对比 Skia） ThorVG 项目自测 Apple M1（macOS 15），渲染分辨率 2560×1440，每次测试 5000 个半透明图元，ThorVG 1.0.0 对比 Skia v144 一般网页内容的性能。5000 个半透明图元是合成压力场景，并非平均界面
GPU 渲染提升超过 150% ThorVG 项目自测 只公开了相对 v0.15 这一对比基准，硬件、分辨率与测试内容在公开资料中无法确认 绝对性能。这是相对自家旧版本的改进幅度，不是跨引擎对比
WebGPU 相对 OpenGL 平均约 1.8 倍 ThorVG 项目自述 官方介绍页面的表述，具体测量方法无法确认 特定内容上的预期值。浏览器、驱动与 GPU 之间差异很大

该从表里读到的不是数字被夸大了，而是四个数字全部来自厂商或采用方自测，其中条件完整公开的只有第二个。这未必意味着不诚实。图形性能对内容的依赖太强，做出通用基准本身就很难。

实务者需要的态度很简单。不要用别人的数字做决定，挑自家最重的一个素材亲自测。半小时足够。而且对比基准不该是别的引擎，应该是你现在正在用的做法。新引擎比旧引擎快，不构成引入理由；新引擎在总成本上优于你当前的做法，才是引入理由。

5.1 有 WebGPU 就一定更快吗

不是。按 MDN 的说明，WebGPU 的设计对应 Direct3D 12、Metal、Vulkan 这类现代原生 API，单个对象渲染的 CPU 侧开销显著更低，并把 GPGPU 计算作为一等能力支持。到这里都是明确的优点。

但 MDN 同时写明该特性不属于 Baseline，因为它在一部分使用最广泛的浏览器中无法工作，并且只能在 HTTPS 安全上下文中使用。落到实务上意味着以下几点。

  • 即便走 WebGPU 路径，也必须保留回退到 WebGL 或 CPU 的路径
  • 准备好回退路径之后，要么要下载的二进制变多，要么条件加载的代码变多
  • GPU 路径有初始化开销，因此在只播放一次的短动画上反而可能是亏的
  • GPU 加速的收益在同时长时间播放多个或动画占屏比例大时才会放大

6. 运行时的真实成本：打包与 WASM

我经常看到团队在纠结动画文件是 40KB 还是 60KB，却把几百 KB 的播放器整个漏掉。把真实数字摆出来。以下是截至 2026 年 7 月从公开包信息中确认的值。

对象 版本 体积 备注
lottie-web（JavaScript 渲染器） 5.13.0 未压缩约 305KB / gzip 约 76.8KB 零依赖。纯 JavaScript，没有额外二进制
dotlottie-web（JavaScript 部分） 0.78.2 未压缩约 152KB / gzip 约 29.1KB 零依赖。WASM 不计入这个数字
dotlottie WASM（CPU 渲染器） 0.78.2 未压缩约 1.81MB 包内文件体积，传输时会应用服务器压缩
dotlottie WASM（WebGL 渲染器） 0.78.2 未压缩约 1.94MB 每个渲染器一份独立二进制
dotlottie WASM（WebGPU 渲染器） 0.78.2 未压缩约 1.97MB 若要准备回退路径，需要按两份来预算
ThorVG 核心库（原生） 依官方介绍 约 170KB 这是原生二进制口径，与浏览器 WASM 体积不同

表里最重要的是最后一行。不要把核心约 170KB 这个数字误当成浏览器成本。那是原生核心二进制的口径，在浏览器里还要叠加 WASM 编译产物、胶水代码与播放器层。ThorVG 项目并没有公开 WebCanvas 的 WASM 体积官方数字，因此浏览器侧的成本只能拿你实际要发布的产物去实测。

6.1 如果还是要引入，至少做到这些

成本高不等于引入是错的，只是需要建立能把付出收回来的结构。最低限度的措施如下。

  • 延迟加载。首屏看不见的动画，其播放器推迟到进入视口时再取
  • 自建托管。不要每次从第三方 CDN 拉取，放在自己域名下以掌控缓存策略
  • 确认服务器压缩。通过响应头确认 WASM 确实应用了 brotli 或 gzip
  • 只用一套。一个项目里混进两种 Lottie 播放器的事故意外地常见
  • 固定渲染器。先判断是否真的需要 GPU 回退路径，不需要就只发一份二进制
  • 写清回收条件。把动画数量达到多少才值得付这笔固定成本，写进团队文档
// 只在进入视口时才加载播放器的最小写法
const target = document.querySelector('#hero-anim');

const io = new IntersectionObserver(async (entries, obs) => {
  for (const entry of entries) {
    if (!entry.isIntersecting) continue;
    obs.unobserve(entry.target);

    // 对希望减弱动态的用户，根本不去加载播放器
    if (window.matchMedia('(prefers-reduced-motion: reduce)').matches) {
      entry.target.innerHTML = '<img src="/img/hero-still.webp" alt="产品介绍静帧">';
      continue;
    }

    const { DotLottie } = await import('@lottiefiles/dotlottie-web');
    new DotLottie({ canvas: entry.target.querySelector('canvas'), src: '/anim/hero.lottie', autoplay: true, loop: true });
  }
}, { rootMargin: '200px' });

io.observe(target);

这个写法的关键不是性能而是顺序。希望减弱动态的用户根本不会下载播放器。把无障碍处理放在加载之前而不是播放之后，无障碍与性能就朝同一个方向走。

7. 动工之前要和设计师谈妥的事

Lottie 落地失败大多不在工程，而在交接这一环。设计师做出在工具里看着没问题的成果，工程师之后才发现它在播放器里长得不一样。到那时回头的代价已经很高。所以在动工之前把下面这些谈妥更划算。

要谈妥的事项 为什么会出问题 约定的形式
确定播放器 同一个文件在不同播放器里支持范围不同 把播放器名称与版本写进文档，并共享该播放器的官方支持表
特效的使用范围 设计工具的许多特效在导出时会丢失或被近似 采用允许清单。不在清单上的，改用图形与关键帧表达
是否允许表达式 表达式支持率因播放器而异，部分函数根本不存在 原则上禁用；确有必要时，先确认该函数在支持清单里
蒙版与遮罩数量上限 合成层级越多，每帧开销上升越陡 为每个文件设定数量上限，超出的列入评审
是否内嵌位图 一旦内嵌位图，矢量的体积优势就消失了 不得已时用 dotLottie 打包，并设定分辨率上限
静态替代画面 减弱动态设置的用户与播放失败时都需要有东西可看 要求连同静帧图片一起交付，事后再要通常会拖
时长与循环 无限循环同时消耗电量与注意力 把循环次数上限或停止条件写进规格

对这张表有抵触是可以理解的，因为在设计师看来它像是提前收窄表达空间的文件。所以谈的时候最好换个框架。这不是一份限制表达的清单，而是一份保证做出来的东西能原样上线的清单。用不受支持的功能做出来的动效，最终还是会在开发阶段被砍掉，那时吃亏的是设计师。

8. 性能崩塌的条件

矢量动画的负载与文件体积相关性很弱。几十 KB 的文件在低端设备上掉帧是家常便饭。抬高每帧开销的因素大致如下。

  • 图层数量。每个图层都带来变换计算与合成，看不见的辅助图层同样要付费
  • 蒙版与遮罩。Alpha 与亮度遮罩是先画到独立缓冲再合并的结构，占屏面积越大代价上升越陡
  • 表达式。脚本每帧都要求值。ThorVG 的文档允许在构建选项里把表达式整个关掉，这件事本身就说明该开销不可忽视
  • 路径顶点数。自动描摹生成的曲线往往顶点过多，这会以每帧光栅化开销的形式还回来
  • 修剪路径与重复器。写起来省事，但它们是在执行时重新生成几何体的运算
  • 占屏面积。同一个文件放大到全屏，要填的像素成倍增加，在 CPU 光栅化上尤其吃力
  • 同时播放数量。列表页每张卡片放一个动画，开销会随卡片数线性累积
  • 高刷新率屏幕。在 120Hz 设备上，每帧预算被砍掉一半以上

诊断顺序也值得固定下来。通常下面这个顺序最快。

  1. 在真实的低端设备上复现，开发用笔记本上看不到问题
  2. 把动画换成静态图，看帧率是否恢复，以此缩小原因范围
  3. 若恢复，问题在文件侧。数一数图层、遮罩与表达式，找出超过上限的项
  4. 若不恢复，问题在动画之外。查看布局重算与主线程争用
  5. 若缩小显示尺寸就有改善，说明是填充率瓶颈。缩小显示面积可能比换渲染器更快

9. 无障碍：prefers-reduced-motion 不是可选项

按 MDN 的说明，prefers-reduced-motion 自 2020 年 1 月起在主流浏览器中已广泛可用。取值有默认的 no-preference 与 reduce 两种，@media (prefers-reduced-motion) 等同于 reduce。

重要的不是语法，而是这个开关为什么会被打开。MDN 解释动画可能给有前庭功能障碍的用户带来不适，并指出放大大型对象或让画面平移的动作特别容易成为诱因。也就是说，这不是偏好设置而是症状规避设置。用户已经向操作系统声明了自己的状况，网页只需要读取它。

MDN 列出的各系统设置位置在测试时也很有用。Windows 11 在辅助功能的视觉效果里的动画效果，macOS 在辅助功能的显示中的减弱动态，iOS 在辅助功能的动态效果，Android 9 及以上在无障碍的移除动画。

/* 1) 基于代码的动画，一条媒体查询就结束 */
@media (prefers-reduced-motion: reduce) {
  .hero-anim { animation: none; transition: none; }
  .hero-anim__still { display: block; }
}

/* 2) 基于播放器的动画，必须用 JavaScript 读取同一个值 */
const mq = window.matchMedia('(prefers-reduced-motion: reduce)');

function applyMotionPreference(player) {
  if (mq.matches) {
    player.pause();
    player.setFrame(0);          // 固定在代表性的一帧
  } else {
    player.play();
  }
}

// 该设置在页面运行期间也可能改变
mq.addEventListener('change', () => applyMotionPreference(player));

还需要补上的项目如下。

  • 提供停止手段。MDN 关于 SVG 动画元素的文档建议提供暂停或停用动画的方式，自动播放超过五秒的元素更应如此
  • 替代文本。纯装饰就用 aria-hidden 隐藏；承载信息就用文本提供同样的信息
  • 挑好静帧。暂停时呈现的那一帧不该是第 0 帧，而应是最能表达内容的一帧
  • 服务端提示。MDN 还提到 Sec-CH-Prefers-Reduced-Motion 客户端提示，可以在服务端直接下发完全不同的素材
  • 自动播放策略。若改用视频，按 Chrome 的文档，静音自动播放始终允许，而带声音的自动播放需要用户交互或参与度等条件。务必处理 play() 返回的 Promise 被拒绝的情况

10. 许可证与法务核查

有时技术评估通过了，却在发布前一步被卡住。动画是代码与创作内容混在同一个文件里的领域，所以要核查的对象不止引擎一个。

核查对象 看什么 漏掉会怎样
渲染引擎 ThorVG 在仓库中标注为 MIT，分发时有保留版权声明的义务 声明缺失。从开源声明页面里掉出去是常见疏漏
播放器封装 引擎与播放器的许可证可能不同，框架封装又是另一回事 只查了引擎，漏掉实际发布产物的条款
随包字体 不把文本图层转成轮廓而是随包发字体，就会触发字体许可 分发了不允许网页嵌入的字体
动画素材本身 公开市场上取得的文件即使免费，也可能附带使用范围或署名条件 超出允许的商业使用范围
内嵌图片 放进 dotLottie 里的位图各自也是权利客体 打包过程中来源追溯链断掉
商标与品牌资产 标志动效同时牵涉著作权与商标 合作结束后素材仍留在产品里被使用

实务上的答案是把动画素材当作依赖来管理。逐个文件记录来源与许可，并确认开源声明的生成流程里包含了引擎与播放器。这项工作在引入时只要十分钟，发布之后再回溯则要花上好几天。

11. 什么时候不该用

这是本文最想写的一段。在下列情况下，我认为不该引入矢量动画运行时。

  • 只有一两个动画的时候。播放器的成本压倒内容的成本。为了让一个图标动起来而下载兆字节级的二进制，怎么算都收不回来。用 CSS 或 SVG 结束它
  • 内容是实拍影像或照片的时候。矢量的前提不成立。无法归约成图形的画面，视频编解码效率高得多
  • 主要用户群是低端设备与慢网络的时候。矢量是把计算搬到用户设备上的选择，只有设备扛得住时这笔交易才划算
  • 动作本身承载信息的时候。如果用户必须理解的内容只以运动的方式存在，那么对开启减弱动态的人来说这条信息就消失了。信息必须在文本或静帧里也是完整的
  • 维护责任不明确的时候。没有设计工具的原始工程文件，动画几乎无法修改。如果原件的归属与存放位置没定下来，半年后它就会变成没人能改的资产
  • 不得不依赖标注为实验性的功能时。把核心画面压在发布说明称为实验性的功能上，每次版本升级都会变成一次回归测试事件
  • 不是品牌要求而是惯性使然时。大家最近都在加无法为预算辩护。若在转化率或理解度上都没有测量计划，不加反而更好

反过来，引入被正当化的条件相当清晰。同一套动效需要同时发到网页、安卓与 iOS；动画会持续增加；设计师需要不经工程师之手就能更新；并且确实需要运行时控制（片段跳转、换色、与状态联动）。这四点凑齐时，播放器成本就变成固定成本，数量越多单位成本越低。在此之前它是纯粹的亏损。

12. 判断顺序：一棵可用的决策树

归纳起来，按下面的顺序往下走大多能得到答案。从上往下读，在第一个符合的条目处停下即可。

  1. 是实拍影像吗？那就用视频。同时准备静音自动播放、playsinline 以及 play() 的拒绝处理
  2. 是界面状态变化（悬停、转场、强调）吗？那就用 CSS 或 Web Animations。零额外文件，无障碍处理也最干净
  3. 是几个简单图形的循环吗？那就用内联 SVG。可通过 DOM 访问，按元素控制与主题适配都很容易
  4. 只是想改进现有的 GIF 吗？那就用 APNG 或动画 WebP。不增加运行时就同时改善画质与体积
  5. 是设计师制作的复杂动效要复用到多个平台吗？到这里 Lottie 才第一次成为候选。先确定播放器并共享其支持表
  6. 选定 Lottie 之后，看是否内嵌图片以决定要不要用 dotLottie 打包，播放器采用延迟加载，对减弱动态的用户则根本不加载播放器
  7. 若帧率仍然不够，先给内容减重再考虑换渲染器。削减图层、遮罩与顶点数通常效果更大

ThorVG 这类引擎的意义出现在这棵树的第 5 步和第 6 步。把第 4 步之前就能解决的问题硬拖到第 5 步，是最常见的错误。

结论：格式是约束的函数，不是口味

ThorVG 1.1 是观察这个领域走到哪一步的好坐标。MIT 许可证、小巧的核心、同时覆盖 CPU 与 GPU 的后端组合，以及把不支持的功能整理成清单公开的态度。最后这一点尤其少见。大多数项目只宣传能做的，做不到的就埋在问题追踪里。有一份连数字一起公开支持范围的文档，意味着引入评估真的可以做。

然而存在一个好引擎，并不构成使用它的理由。把本文确认的内容重新汇总：被广泛引用的四个性能数字中，条件完整公开的只有一个，其余要么是自测，要么只公开了对比基准。在浏览器里引入播放器，仅 WASM 二进制未压缩就是兆字节量级。Lottie 的功能支持由播放器而非格式决定，因此与设计师的约定要排在技术选型之前。而且无论选什么，对减弱动态设置的处理都不是可谈判的事项。

所以结论很朴素。大多数画面的答案是 CSS 与 SVG；如果现在还在用 GIF，仅仅换成 APNG 或 WebP 就能解决相当一部分问题。Lottie 以及驱动它的引擎，只有在需要把同一套动效反复供给多个平台、且动画数量持续增长的组织里才真正回本。不在这些条件里的话，一个优秀新引擎的登场是值得庆贺的消息，而不是引入的理由。

最后还有一点。这个领域最贵的错误不是选错引擎，而是让本来不需要动的东西动了起来。那个加载动画成为页面最重资源的案例，并不是技术选型的失败。失败在于没有人问过那个位置是否真的需要一个动画。
