Time Zones Are Data, Not Code - Updating tzdata Changes How Past Timestamps Read

Why a stored value never changes yet the displayed time does, and what you must store to be able to recompute it later

2026-07-30 Dev & Infra

Introduction: the stored value never changed, yet the time on screen did

There is one class of bug that is genuinely hard to reason about. Nobody touched the database, and yet the time shown on screen is different from yesterday. A timestamp in the audit log has slid by an hour. The time on a record from years ago has changed. The only thing you shipped was a library version bump.

The first suspect is always the code. People read the conversion function, check the server clock, and dig through change history looking for whoever edited the row. They find nothing. The value really is unchanged. What changed is not the value but the rule used to read it.

The heart of this article is a single sentence.

A timestamp is a value; a time zone is a rule. The rule ships not as code but as a data file that gets revised on a schedule. So when it is updated, the same value reads differently — and not only in the future.

That sounds abstract, so this article starts by asserting nothing. Instead it proves the sentence with output run on this machine right now. This machine happens to have two runtimes that each carry their own copy of the time zone data, and their data versions differ. Feed the same stored value to both and, for certain past instants, you get two different answers. I counted how many, and for which regions and years.

Environment. Every output below was actually run on Windows 10 Pro (10.0.19045). The runtimes are Node.js v22.16.0 (win32 x64) and Python 3.13.3 (win32 AMD64). Their time zone data sources and versions were as follows.

  • Node.js — the bundled ICU 77.1 carries the time zone data. process.versions.tz reported 2025b
  • Python — zoneinfo.TZPATH was an empty tuple. That is, this platform has no system time zone database, and the tzdata package from PyPI supplies the data instead. That package was version 2025.3 and tzdata.IANA_VERSION read 2025c
  • On the same day, the IANA distribution page announced the current release as 2026c (2026-07-08). Neither runtime is current, and they do not agree with each other

This article did not update or modify any system time zone data. Proving that an update changes interpretation did not require performing an update. Running two runtimes with different data versions side by side on one machine was enough. Every script was saved to a file and executed.

What this article does not cover. Which clock to use for measuring elapsed time is a separate topic and is left alone. The two holes at a DST boundary get exactly one section and no more; they deserve an article of their own. Characters breaking at an encoding boundary is covered in cp949 and UTF-8.

1. A timestamp is a value; a time zone is a rule

The vocabulary has to be split precisely first. If this distinction blurs, none of what follows holds together.

  • Instant — a point that happened exactly once in the universe. Usually expressed as seconds since an epoch. This is a value. No government can change this number
  • Local time — the name people in a particular region give to that instant, such as 13:00 on 30 July 2026. This is a computed result
  • Offset — how far that region sat from the reference at that instant, written like +09:00. Also a computed result
  • Time zone — the entire history of rules that turn instants into local times. A region identifier such as Asia/Seoul points at that bundle of rules. This is the data

The last item is the point. Asia/Seoul does not mean plus nine hours. It means the record of which rules this region's clocks followed from 1890 until now. That bundle lives in the IANA time zone database, and when a government changes a rule or an error in the historical record is found, it ships as a new release.

The IANA distribution page states that the data is updated periodically to reflect changes made by political bodies to time zone boundaries, UTC offsets and daylight-saving rules. It also says that end users typically receive updates to this data through their software and operating system vendors. Those two sentences create every problem in this article. The rules change outside your system, and you generally do not know when you received the change.

  • A daily-rollup report that never decided whose midnight it uses has this one instant belonging to two dates at once

4. One machine, two data versions, 33 disagreements

This is the centre of the article. To prove that a different data version means a different interpretation without touching system data, you just need two copies of the data at different versions side by side. This machine already had them.

  > python -c "import tzdata;print(tzdata.IANA_VERSION)"

  > python -c "import importlib.metadata as m;print(m.version('tzdata'))"

The last two rows cause incidents of their own.

  • In 1980 the two runtimes agree. This kind of disagreement does not appear across the whole range. It surfaces only in specific regions and specific year bands. A test suite that only uses recent dates will never catch it
  • Python knows 180 more identifiers. Older names and compatibility links such as ROK, Japan, Asia/Calcutta, US/Pacific and Israel live there. Conversely, Node knew zero identifiers that Python did not
  • So a region string a user stored can be valid in one runtime and a failure in the other. In a service that runs both, that lands as a 500
  • It also matters that the disagreement showed up only in the offset value. Neither runtime raised an exception. They quietly gave different answers

The conclusion to draw. The stored value never changed but the screen did — that is not misbehaviour. It is the design working. A value stored with a region identifier is a request to recompute it under that region's rules, and when the rules are corrected the computation is corrected too. That is a feature. The problem is that we do not know when a correction will land, and we get no notification that one did.

5. What you lose by storing only an offset

The obvious objection arrives here. Why not store the offset alongside it? Something like 2026-01-15T10:00:00+09:00 looks unambiguous. I counted what disappears.

--- B-1. an offset does NOT identify a region ---
  offset +09:00 at that instant :  12 zone ids  e.g. Asia/Chita, Asia/Dili, Asia/Jayapura, Asia/Khandyga
  offset +05:30 at that instant :   3 zone ids  e.g. Asia/Calcutta, Asia/Colombo, Asia/Kolkata
  offset -05:00 at that instant :  47 zone ids  e.g. America/Atikokan, America/Bogota, America/Cancun, America/Cayman
  offset +01:00 at that instant :  53 zone ids  e.g. Africa/Algiers, Africa/Bangui, Africa/Brazzaville, Africa/Casablanca
  total distinct offsets in use at that instant : 38

At one instant, 12 regions use +09:00, 47 use -05:00 and 53 use +01:00. And the whole world uses only 38 distinct offsets at that moment. An offset is far too narrow to point at a region.

But the point is not ambiguity. It is that recomputation becomes impossible. An offset is the result of a computation, and storing only the result means you threw away the input. When the rule changes there is nothing left to compute from.

  • Storing an offset does preserve the instant. You can recover which epoch it was. For uses that need only that, it is sufficient
  • But you cannot answer what the same clock time in that region will be six months later. You do not know the region, nor what rule it will be under
  • Without a region identifier the value also never benefits from a correction. Updating the data will not change its interpretation. Turn section 4 around and consider that this can be the bad outcome
  • A front end that lets the user pick a region and then sends only the offset to the server discards information at that exact point. It must send the region identifier too

6. The same commitment stored three ways

Now put the three storage forms head to head. That needs a region whose rules actually changed. Probing Europe/Istanbul year by year in this runtime's data shows a discontinuity between 2015 and 2017.

--- B-2. a rule change that is IN the data: Europe/Istanbul ---
  2014-01-15 10:00 local -> offset +02:00  abbr EET   dst 0:00:00 -> UTC 08:00Z
  2015-01-15 10:00 local -> offset +02:00  abbr EET   dst 0:00:00 -> UTC 08:00Z
  2015-07-15 10:00 local -> offset +03:00  abbr EEST  dst 1:00:00 -> UTC 07:00Z
  2016-07-15 10:00 local -> offset +03:00  abbr EEST  dst 1:00:00 -> UTC 07:00Z
  2017-01-15 10:00 local -> offset +03:00  abbr +03   dst 0:00:00 -> UTC 07:00Z
  2018-01-15 10:00 local -> offset +03:00  abbr +03   dst 0:00:00 -> UTC 07:00Z
  2026-01-15 10:00 local -> offset +03:00  abbr +03   dst 0:00:00 -> UTC 07:00Z

In January 2015 the winter offset is +02:00, rising to +03:00 in summer. From January 2017 it is +03:00 even in January, with dst at zero. The transition is gone and the value is fixed year round. The abbreviation also moved from EET to +03.

Now build the scenario. Suppose that in 2014 you agreed to a call at 10:00 local time on 15 January 2017 and stored it. The rule known at that time put winter at +02:00. Stored three ways, here is how it splits.

This is where the advice to just store UTC runs out. Storing UTC preserves the instant but discards the intent. What people agreed on was not an instant; it was 10:00 in the morning in that region. When the rule changes, the instant has to move for that intent to hold. Freezing the instant is freezing it in the position where the intent breaks.

  • An event that already happened is the opposite. Its instant is settled, so storing the instant is correct
  • A commitment in the future is fundamentally a wall-clock intent, so the region identifier and the wall clock must be stored
  • The safest option is the last row of the table. Store both and raise an alert when they disagree. That disagreement becomes the only notification you will get that a rule changed
  • Automate that check and you can detect a tz data update after the fact: a batch that compares the stored UTC against a UTC recomputed from the region identifier and reports the rows that differ

7. The future is not settled, and the past is not safe either

Most people have this backwards. They assume the past is fixed and only the future is uncertain. That is half right. I checked both directions.

7.1 The future — the data does not distinguish fact from projection

First, what does this runtime claim to already know about the future?

--- B-4. past is settled, future is projected ---
  America/New_York transitions the data already asserts for 2027-2030:
      2027-03-14 -> -04:00
      2027-11-07 -> -05:00
      2028-03-12 -> -04:00
      2028-11-05 -> -05:00
      2029-03-11 -> -04:00
      2029-11-04 -> -05:00
      2030-03-10 -> -04:00
      2030-11-03 -> -05:00
  ...and for the year 2100:
      2100-03-14 -> -04:00
      2100-11-07 -> -05:00
  Asia/Seoul transitions 2027-2031 : none

It answers with transition dates in the year 2100. Obviously nobody has decided those dates. They are a projection of the current rule extended indefinitely. Here is the problem: nothing in the output marks it as a projection. The 2027 answer and the 2100 answer are formally identical. The calling code has no way to tell them apart.

7.2 The future — this machine's answers were already stale

There was something more concrete to check. This machine carries 2025c while IANA's current release is 2026c. If any release in between changed a future rule, this machine should still be scheduling a clock change that no longer exists. The 2026b and 2026c entries in the tz project's NEWS record several regions ceasing seasonal transitions and moving to a year-round offset. So I asked this machine.

--- F-3. does this runtime still schedule clock changes that were cancelled? ---
  America/Edmonton     2026-2027 : 2026-03-08 -> -06:00, 2026-11-01 -> -07:00, 2027-03-14 -> -06:00, 2027-11-07 -> -07:00
  America/Vancouver    2026-2027 : 2026-03-08 -> -07:00, 2026-11-01 -> -08:00, 2027-03-14 -> -07:00, 2027-11-07 -> -08:00
  Africa/Casablanca    2026-2027 : 2026-02-15 -> +00:00, 2026-03-22 -> +01:00, 2027-02-07 -> +00:00, 2027-03-14 -> +01:00
  Europe/Chisinau      2026-2027 : 2026-03-29 -> +03:00, 2026-10-25 -> +02:00, 2027-03-28 -> +03:00, 2027-10-31 -> +02:00

--- F-2. and the resulting local time this runtime reports ---
  zone                   date (12:00Z) offset     abbr
  --------------------------------------------------------
  Africa/Casablanca      2026-10-15   +01:00     +01
  America/Edmonton       2026-12-15   -07:00     MST
  America/Vancouver      2026-12-15   -08:00     PST

It does. This machine answers as though the clocks will go back on 1 November 2026. The official release notes record that those regions are not making that transition. In other words, the local time this machine computes today for December of this year is already a wrong answer. No exception, no warning, just a value that is an hour off.

  • This is the practical reason to put tz data updates in the deployment pipeline. Skip them and future calculations run wrong, silently
  • The trap is that the failure lands on the date being computed, not the date the rule changed. Everything can look fine today and bookings still slip by an hour in November
  • Checking that it works right now is therefore meaningless. It only shows up when you test with future dates

7.3 The past — settled, but subject to correction

Section 4 already proved this side. To restate it: a past instant is settled; the name a region gives that instant is not. That name is a record written in the data, records can contain errors, and errors get corrected.

The very fact that the tz project's release notes carry a dedicated section headed Changes to past timestamps makes the point. The releases I read contained entries correcting the hour of transitions decades old and changing which rules a region observed during a particular period.

8. Abbreviations are not identifiers

Printing KST or CST on screen is kind to humans. Storing or parsing one is a different story. I gathered every region's abbreviation at one instant and counted.

--- B-5. abbreviations are not identifiers ---
  KST  :  3 zone ids, offsets ['+09:00']
           Asia/Pyongyang           +09:00
           Asia/Seoul               +09:00
           ROK                      +09:00
  CST  : 44 zone ids, offsets ['+08:00', '-05:00', '-06:00']
           America/Bahia_Banderas   -06:00
           America/Belize           -06:00
           America/Chicago          -06:00
           America/Chihuahua        -06:00
  IST  :  5 zone ids, offsets ['+02:00', '+05:30']
           Asia/Calcutta            +05:30
           Asia/Jerusalem           +02:00
           Asia/Kolkata             +05:30
           Asia/Tel_Aviv            +02:00
  EST  : 35 zone ids, offsets ['-05:00']

CST is used by 44 regions, and those regions sit at three different offsets: +08:00, -05:00 and -06:00. IST means +02:00 and +05:30 simultaneously. The worst case is 14 hours. Now feed those strings to a parser.

--- C-1. parsing a string that carries an abbreviation (Python) ---
  2026-01-15 10:00 KST       -> ValueError: time data '2026-01-15 10:00 KST' does not match format '%Y-%m-%d %H:%M %Z'
  2026-01-15 10:00 CST       -> ValueError: time data '2026-01-15 10:00 CST' does not match format '%Y-%m-%d %H:%M %Z'
  2026-01-15 10:00 UTC       -> 2026-01-15T10:00:00        tzinfo=None
  2026-01-15 10:00 GMT       -> 2026-01-15T10:00:00        tzinfo=None
  2026-01-15 10:00 +0900     -> 2026-01-15T10:00:00+09:00  tzinfo=UTC+09:00

Three different failure modes on one screen.

  • KST and CST fail to parse at all. This parser accepts a very narrow set of abbreviations, so round-tripping a string a user sent you does not work
  • UTC and GMT parse, but tzinfo comes back None. The abbreviation was read and discarded. The result is naive, and using it as-is means it gets read as the process's local time. No exception, which makes this the dangerous one
  • Only the numeric offset survives. And as section 5 showed, what survived is not a region identifier

On another runtime the failures have different shapes.

--- G-3. what Date parsing does with each written form (Node) ---

  "2026-07-30T00:00:00"            -> 2026-07-29T15:00:00.000Z  epoch 1785337200
  "2026-07-30T00:00:00Z"           -> 2026-07-30T00:00:00.000Z  epoch 1785369600
  "2026-07-30T00:00:00+09:00"      -> 2026-07-29T15:00:00.000Z  epoch 1785337200
  "2026/07/30 00:00:00"            -> 2026-07-29T15:00:00.000Z  epoch 1785337200
  "July 30 2026 00:00:00"          -> 2026-07-29T15:00:00.000Z  epoch 1785337200
  "2026-07-30 00:00:00 KST"        -> Invalid Date
  "2026-07-30 00:00:00 CST"        -> 2026-07-30T06:00:00.000Z  epoch 1785391200

The last two lines are the highlight. KST becomes Invalid Date while CST parses successfully. And the result is 06:00Z, meaning this parser read CST as -06:00. If someone sent the CST that means +08:00, a value 14 hours wrong is stored silently.

  • The first two lines are a trap as well. 2026-07-30 was read as reference-time midnight, while 2026-07-30T00:00:00 was read as local midnight. Adding the time part shifted it by nine hours
  • So a date-only string and a string that spells out midnight are different instants. Depending on which form a date picker submits, your rollups slide by a day
  • The slash form and the English month-name form were both read as local. Log-parsing code that meets those forms gives different answers on different servers
  • The conclusion is simple. Pin machine-readable values to one format with an explicit offset, and move the region identifier into its own field

9. The two holes at a DST boundary

This topic deserves its own article, so here is only the part that bears directly on storage form. A region with transitions has a wall-clock time that does not exist and a wall-clock time that happens twice.

--- C-2. the two holes at a DST boundary (America/New_York, 2026) ---
  nonexistent local time 2026-03-08 02:30
    fold=0 -> offset -05:00 abbr EST  -> UTC 07:30Z -> back to zone 2026-03-08 03:30 EDT
    fold=1 -> offset -04:00 abbr EDT  -> UTC 06:30Z -> back to zone 2026-03-08 01:30 EST
    round trip preserved the wall clock : False

  ambiguous local time 2026-11-01 01:30
    fold=0 -> offset -04:00 abbr EDT  -> UTC 05:30Z -> epoch 1793511000
    fold=1 -> offset -05:00 abbr EST  -> UTC 06:30Z -> epoch 1793514600
    the two are equal by ==            : True
    seconds apart in real time         : 3600

The two holes behave in opposite ways.

  • The nonexistent time raises nothing. It accepts the value, and a round trip yields a different wall clock (False). You put in 02:30 and get back 03:30 or 01:30. Storing and re-reading changes the value
  • The doubled time is subtler. The two values compare equal under == while sitting 3,600 seconds apart. Two values judged identical are different instants
  • Distinguishing them needs an extra bit such as fold. And that bit goes into neither the ISO string nor most database columns
  • So storing an ambiguous time as wall clock plus region identifier alone is not enough information. Values landing in this band need the instant stored as well

That is the second reason the last row of the table in section 6 exists. Future commitments need a region identifier, and ambiguous boundaries need a settled instant.

10. Twenty-four hours later is not the same time tomorrow

I confirmed by execution that a day later means two things. The starting point is noon the day before a transition.

--- C-3. 24 hours later vs the same clock time tomorrow ---
  start                          : 2026-03-07 12:00 -0500
  start + timedelta(hours=24)    : 2026-03-08 12:00 -0400
    real seconds elapsed         : 82800
  UTC + 24h, then converted back : 2026-03-08 13:00 -0400
    real seconds elapsed         : 86400
  the two answers differ by      : 12:00 vs 13:00

  the same pair over the autumn boundary
  start                          : 2026-10-31 12:00 -0400
  wall +24h                      : 2026-11-01 12:00 -0500  real seconds 90000
  instant +24h                   : 2026-11-01 11:00 -0500  real seconds 86400

  and where a zone with a 30 minute shift lands (Australia/Lord_Howe)
    start        : 2026-10-03 12:00 +1030
    wall +24h    : 2026-10-04 12:00 +1100  real seconds 84600

  • A daily 09:00 reminder wants the wall-clock version, accepting that the elapsed interval varies from day to day
  • Cancel within 24 hours of payment wants the instant version. A regional rule must not extend or shorten a user's rights
  • The danger is that this choice is made implicitly. In the output above, the wall-clock computation is just a timedelta added to an aware value. There is no warning of any kind
  • In a half-hour region the error is 30 minutes, so it slips past any test that only checks for an hour of drift
  • Anything like three business days rests on where the date boundary itself falls, so it must take a region identifier as input

11. Sorting and comparison only work in UTC

Gathering records from several regions onto one screen creates a sorting problem. I produced the ordering by local-time text next to the ordering by instant.

--- C-4. sorting local-time text vs sorting instants ---
  as written
  id        local text            zone                  fold  offset UTC
  order-A   2026-11-01 01:30:00   America/New_York      0     -04:00 2026-11-01 05:30:00Z
  order-B   2026-11-01 01:30:00   America/New_York      1     -05:00 2026-11-01 06:30:00Z
  order-C   2026-11-01 09:00:00   Asia/Seoul            0     +09:00 2026-11-01 00:00:00Z
  order-D   2026-10-31 22:00:00   Europe/London         0     +00:00 2026-10-31 22:00:00Z
  order-E   2026-11-01 14:30:00   Australia/Lord_Howe   0     +11:00 2026-11-01 03:30:00Z

  sorted by the local text  : ['order-D', 'order-A', 'order-B', 'order-C', 'order-E']
  sorted by the real instant: ['order-D', 'order-C', 'order-E', 'order-A', 'order-B']
  the two orders agree      : False

The two orderings are completely different. order-A is second by local-time text but fourth in reality.

  • Local-time strings are not values on a common axis. Comparing them is comparing numbers taken from different rulers
  • order-A and order-B have byte-identical strings. With only local-time text, no sort can ever decide their order
  • Even within a single region, local-text sorting breaks across a transition. We only use one region is not a safe defence
  • So sorting, comparison and range queries all belong on the instant column. Local time is computed only when drawing the screen
  • If you stored a display-local column and indexed it, that index cannot be used for ordering

12. The rule evaporates at serialization and database boundaries

Even when you hold the region identifier correctly, it often vanishes the moment the value leaves the process. I traced the round trips.

--- F-5. serialization round trips ---
  original object      : datetime.datetime(2027, 6, 15, 14, 30, tzinfo=zoneinfo.ZoneInfo(key='Asia/Seoul'))
  original tzinfo type : ZoneInfo -> Asia/Seoul
  isoformat()          : 2027-06-15T14:30:00+09:00
  fromisoformat()      : datetime.datetime(2027, 6, 15, 14, 30, tzinfo=datetime.timezone(datetime.timedelta(seconds=32400)))
  tzinfo type after    : timezone -> UTC+09:00
  same instant         : True
  region id survived   : False

  the same pair for a zone that does have transitions:
    stored           : 2027-01-15T14:30:00-05:00
    region form + 6 months : 2027-07-15 14:30 -0400
    offset form + 6 months : 2027-07-15 14:30 -0500
    those are different instants, one hour apart

Export to an ISO string and read it back and the instant survives (True) while the region identifier does not (False). The type changed from ZoneInfo to a fixed offset. On the surface it is the same value, so the loss is invisible.

It becomes visible the moment you compute from that value. Move six months forward in a region with transitions and the region-identifier form gives -04:00 while the offset form gives -05:00 — instants an hour apart. Merely storing and retrieving froze the rule.

--- G-4. JSON round trip (Node) ---
  JSON.stringify        : {"label":"meeting","when":"2027-06-15T05:30:00.000Z"}
  the zone the user chose is nowhere in that payload
  same instant revived  : true
  toString() (local)    : Tue Jun 15 2027 14:30:00 GMT+0900
  toISOString()         : 2027-06-15T05:30:00.000Z
  in Asia/Seoul         : 2027-06-15, 14:30:00 GMT+09:00
  in America/New_York   : 2027-06-15, 01:30:00 GMT-04:00

--- F-6. an SQL boundary: with and without zone information ---
  meeting  text=2027-06-15T14:30:00+09:00        epoch=1813037400 zone='Asia/Seoul'
           read back -> 2027-06-15T14:30:00+09:00        tzinfo=UTC+09:00
           with the zone column, recomputable -> 2027-06-15 14:30 +0900
  naive    text=2027-06-15T14:30:00              epoch=1813037400 zone=''
           read back -> 2027-06-15T14:30:00              tzinfo=None
           without a zone column, the reader must guess
  • JSON serialization does not even keep the offset. It always emits reference-time form, so the region the user chose appears nowhere in the payload
  • Printing the same object with toString() shows it in the process's local region. This is a common reason logs and API responses report different times
  • In a database, the fork is whether a separate column holds the region identifier. A type that carries an offset still cannot carry the rule; it carries a result
  • A naive value with no region reads back as tzinfo=None. Which region it was survives only as a convention outside the schema — that is, nowhere
  • So a table of future commitments should carry both an instant column and a region identifier column. One is not enough

13. Leaning on an environment variable fails quietly

Leaving the region to the process environment instead of naming it in code is widespread. I set TZ for both runtimes on this platform and looked at the results.

--- H-1. TZ env var, seen by Node ---
  America/New_York     -> resolved America/New_York   | new Date(2026,6,30,12,0) = 2026-07-30T16:00:00.000Z
  Asia/Seoul           -> resolved Asia/Seoul         | new Date(2026,6,30,12,0) = 2026-07-30T03:00:00.000Z
  Europe/London        -> resolved Europe/London      | new Date(2026,6,30,12,0) = 2026-07-30T11:00:00.000Z
  UTC                  -> resolved UTC                | new Date(2026,6,30,12,0) = 2026-07-30T12:00:00.000Z
  EST5EDT              -> resolved America/New_York   | new Date(2026,6,30,12,0) = 2026-07-30T16:00:00.000Z

--- H-3. does TZ reach Python zoneinfo on this platform? ---
  TZ=<unset>            local astimezone() -> +0900  | ZoneInfo('America/New_York') -> -0400  | tzset available: False
  TZ=America/New_York   local astimezone() -> +0100  | ZoneInfo('America/New_York') -> -0400  | tzset available: False
  TZ=Europe/London      local astimezone() -> +0100  | ZoneInfo('America/New_York') -> -0400  | tzset available: False
  TZ=UTC                local astimezone() -> +0000  | ZoneInfo('America/New_York') -> -0400  | tzset available: False

The two runtimes react completely differently.

  • In Node, TZ worked properly. Give it a region identifier and the same wall-clock arguments become different instants. The legacy name EST5EDT was resolved to a canonical identifier and produced an answer
  • Python is another matter. time.tzset does not exist on this platform (False). Yet TZ did influence how the local region was determined, and the result was wrong. Setting America/New_York produced +0100. That region is at -0400 in July
  • Worse, setting Europe/London produced the identical +0100. It looks right by coincidence, but being the same value proves it was not resolved as a region identifier at all
  • By contrast, ZoneInfo('America/New_York') returned -0400 in every case. An explicitly named region was unmoved by the environment

There is one conclusion. Make the region part of the value. Reading it from the process environment produces silently wrong answers on some platforms. In a world where containers and development machines are expected to differ, an environment variable is not a reproducible input.

14. The procedure — deciding what to store as what

Here are the execution results turned into decision rules. The starting question is not store UTC but what kind of value is this.

14.2 Why tz data updates belong in the deployment pipeline

Section 7.2 is the whole reason. Without updates, future calculations run wrong and stay wrong, silently. Today's results can be correct and still fail when the computed date arrives. And because the error raises no exception, monitoring never sees it.

  • Manage tz data as an application dependency. Write down which runtime gets its data from where — on this machine one used bundled ICU and the other a package
  • With multiple runtimes, align the versions. As section 4 showed, differing versions quietly give different answers
  • Log the version at startup. After an incident that is the only way to know which version was in play
  • Schedule updates, but treat an update as a deployment. It is a change capable of altering how past data reads
  • An OS package update may not change the data your application uses. A runtime with bundled data is unaffected by updating the OS

14.3 How to check for regressions after an update

Once you update, you have to count what changed. The method used in section 4 becomes the procedure itself.

  • Snapshot before updating. Save a table of offsets for every region identifier your service uses across the period you care about. The experiment above built 230,000 rows from 418 regions and 564 instants in a few seconds
  • Take the same table afterwards and look only at the diff. A small number like 33 rows is normal. Zero rows means the update did not take effect, which is itself a signal
  • Reconcile the diff against the release notes. A change not covered by the notes points at code or configuration, not data
  • Recompute every stored future commitment and compare. Diff the stored instant against one recomputed from the region identifier. If you follow the last row of the table in section 6, this is your alert
  • Validate region identifiers. Check that every region string in user data still resolves after the update. Section 4 found a gap of 180 identifiers between runtimes
  • Put past and future dates into tests. A test that only uses the current time cannot catch this class of regression, even in principle
  • Test transition boundaries with fixed values. Pin a nonexistent time and a doubled time as explicit cases

14.4 Questions to ask in review

  • Is this value an event that happened or a commitment ahead? — different answers mean different storage forms
  • Where is the region identifier stored? — it is in the offset is a wrong answer
  • Will anything recompute from this value later? — if so, a rule reference has to survive
  • Which column do sorting and comparison run on? — if it is a local-time column, fix it
  • Is a day later wall clock or elapsed time? — is that written down in the requirements
  • With multiple runtimes, are the tz data versions equal? — can you confirm it from startup logs
  • Do you show users an abbreviation and accept it back? — if so, fix it
  • Is this a screen where a past record's display must not change? — if so, keep the rendered string alongside

In one line. A timestamp is a value and a time zone is a rule. Store only the value and you cannot recompute when the rule changes; store only the rule reference and the answer changes when the rule changes. Which is correct depends on whether the value is something that happened or something that was agreed. And a system that never made that decision is the one that, one day after a single library bump, watches the times on old records move.

# Time Zones Are Revised Data — Storage Decision Table and Post-Update Checklist

> Source: braindetox.kr — Time Zones Are Data, Not Code
> Evidence: Windows 10 / Node v22.16.0 (ICU 77.1, tz 2025b) / Python 3.13.3 (tzdata 2025.3 = IANA 2025c), all run
> Paste this into an AI tool and say 「review our schema and deployment pipeline against these rules」.
> ⚠ Observed: two runtimes on the same machine gave different past offsets for 33 of 235,752 pairs. Not one stored value changed.

## 0. The premise — a timestamp is a value, a time zone is a rule

| Concept | What it is | Who changes it |
|---|---|---|
| **Instant** | An epoch value. A point that happened once | **Nobody can** |
| **Local time** | The name a region gives that instant | A computed result |
| **Offset** | How far the region sat from the reference then | A computed result |
| **Time zone** | **The entire history of rules** mapping instants to local times | Governments change it, IANA ships it |

**A storage form that loses the rule (offset only) cannot answer questions about the future.**

## 1. Storage form by the nature of the value — this table is the point

| Nature of the value | What it really is | Storage form | When a rule changes | Recomputable |
|---|---|---|---|---|
| **Event that happened** (logs, payments, audit) | Instant | **One instant (UTC)** | Instant holds, display may change | Display recomputable |
| **Future commitment** (meetings, bookings) | Wall-clock intent | **Wall clock + region id**, instant cached | Instant must move to honour intent | **Yes** |
| **Recurring schedule** (daily 09:00) | Rule + wall clock | **Wall clock + region id + recurrence rule** | Next occurrence moves | **Yes** (no, if instants stored) |
| **Business days, deadlines** | A region's date boundary | **Region id + date** (+ holiday calendar) | Date boundary can shift | Yes |
| **Birthdays, anniversaries** | A calendar date | **Date only** (no time, no region) | Unaffected | Not applicable |
| **Values on a boundary** (ambiguous, nonexistent) | One of two instants | **Instant + wall clock + region id, all three** | Safe, instant is settled | Yes |
| Offset only (`+09:00`) | A computed result | **Avoid** — supplementary only | Nothing happens | **No** |
| Abbreviation (`KST`, `CST`) | A human-readable label | **Do not store** | Not applicable | **No** |

### The rule in three lines

- Did it **already happen**? → store the instant
- Is it something **agreed for later**? → store wall clock + region id
- Need both? → **store both, and alert when the recomputed value disagrees**

## 2. Checking your tz data version

```bash
# Node — the bundled ICU carries the data
node -p "process.versions.tz + ' / icu ' + process.versions.icu"
# measured: 2025b / icu 77.1

# Python — with no system database, the PyPI tzdata package supplies it
python -c "import tzdata;print(tzdata.IANA_VERSION)"
python -c "import importlib.metadata as m;print(m.version('tzdata'))"
python -c "import zoneinfo;print('TZPATH:', zoneinfo.TZPATH)"
# measured: 2025c / 2025.3 / TZPATH: ()   (empty tuple = no system database)

# How many region identifiers each runtime knows — look for the gap
node -p "Intl.supportedValuesOf('timeZone').length"
python -c "import zoneinfo;print(len(zoneinfo.available_timezones()))"
# measured: 418 vs 598  (180 compatibility links only Python knows)
```

- **With multiple runtimes, align the versions.** Differing versions quietly give different answers
- **Log the version at startup.** After an incident it is the only way to know which version was in play
- An OS package update **may not touch a runtime that uses bundled data**

## 3. Post-update regression checklist

- [ ] Took a **snapshot before updating** — offsets for every region id the service uses across the period that matters
- [ ] Took the **same table afterwards** and looked **only at the diff** (measured: 418 regions x 564 instants = 230k rows, seconds)
- [ ] The diff was **not zero rows** — zero means the update did not take effect
- [ ] Reconciled the diff **against the release notes** — changes not in the notes point at code or config
- [ ] **Recomputed every stored future commitment** and compared it with the stored instant
- [ ] Verified that **every region identifier in user data still resolves** after the update
- [ ] Put **past and future dates** into tests (a test using only the current time cannot catch this)
- [ ] Tested **transition boundaries with fixed values** — a nonexistent time and a doubled time
- [ ] Confirmed the schema survives a **sub-minute offset** such as `+08:27:52`
- [ ] Confirmed nothing breaks on **30 and 45 minute offsets** (`+05:30`, `+05:45`, `+08:45`, `+10:30`)
- [ ] Defined what happens when `+14:00` makes a **daily rollup span two dates**
- [ ] Treated the update **as a deployment** — it can change how past data reads

## 4. Questions to ask in review

- Is this value **an event that happened or a commitment ahead**? — different answers, different storage
- **Where is the region identifier stored?** — 「it is in the offset」 is a wrong answer
- Will anything **recompute from this value later**? — if so, a rule reference must survive
- **Which column** do sorting, comparison and range queries run on? — a local-time column needs fixing
- Is 「a day later」 **wall clock or elapsed time**? — is that written in the requirements
- With multiple runtimes, **are the tz data versions equal**? — confirmable from startup logs?
- Do you **show users an abbreviation and accept it back**? — if so, fix it
- Is this a screen where a past record's display **must not change**? — then keep the rendered string too

## 6. Do not

- ❌ **Store only an offset** — the instant survives but the material for recomputation is gone
- ❌ **Store or parse abbreviations** — one `CST` covers three offsets
- ❌ **Resolve future commitments to UTC once** — a rule change freezes them where the intent breaks
- ❌ **Sort or compare on a local-time column** — that is comparing numbers from different rulers
- ❌ **Leave the region to a process environment variable (`TZ`)** — silently wrong on some platforms (measured: `America/New_York` came back as `+0100` on one runtime)
- ❌ **Test with the current time only** — this class of regression cannot be caught that way
- ❌ **Deploy without tz data updates** — future calculations run wrong, silently
- ❌ **Model offsets as whole hours in a schema** — 45-minute and sub-minute offsets exist
