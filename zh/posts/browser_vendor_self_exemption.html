删除网站数据到底留下了什么 - 当造浏览器的一方也在上面做服务

设置承诺的范围、例外落脚的位置，以及用户自己就能读的那块屏幕

2026-09-07 IT/技术

几乎每个现代浏览器的设置里都有一项，写着删除网站保存在本机上的数据。用户按下这个开关时脑中浮现的画面，和实现它的代码实际走过的范围，并不是同一件事。缝隙几乎总是从同一个词裂开，那个词是网站。

网站到哪里结束，浏览器功能从哪里开始。这条线的位置决定同一次点击清掉什么、留下什么。而结构性的一面在于，画线的一方与从落点获益的一方，可能是同一个组织。

起因 - 到底是对什么的例外

2026年9月初被转开的那篇文章是个人博客。写 Mac 软件的 Jeff Johnson 发在自己站点上，标题的意思是 Chrome 又一次把谷歌排除在用户的网站数据设置之外。这是明确针对某一家厂商的文章，先说清这点，后面读起来更省力。

在转述和摘要中最先掉下去的信息是这个例外到底是对哪一个设置的例外。被点名的设置可以精确定位：chrome://settings/content/siteData 三个选项中的第二个，即关闭所有窗口后删除网站保存到本机的数据。既不是笼统的第三方 Cookie 拦截，也不是广告追踪。

作者描述的步骤是这样的。打开那个选项，在未登录 Chrome 的状态下做一次谷歌搜索，关掉所有窗口。之后去看设备上的网站数据列表，据文中所述 www.google.com 这一项还留着，约 1,216 KB，重启后依然在。留下的种类写的是 Cookie、本地存储和会话存储，版本写的是 152.0.7977.83。他还补了一句，自己的截图是用来解释而非当证据的，并明确表示不对动机下定论。

同一位作者在2020年写过意思相近的文章，这次说当时那件事后来被修好了，标题里的「又」指的就是这段经历。以上都属于观察。观察和规则分量不同，先用一张表把它们分开。

项目博客的说法一手资料能对上的部分
涉及的设置关闭所有窗口后删除网站数据设置字符串资源和帮助文档里有同一句话
据称留下的种类Cookie、本地存储、会话存储三者都在这个设置的适用范围内
只有某个域名留下www.google.com没有任何官方文档规定这样的域名例外
例外可能怎么产生未涉及源码中存在允许记录优先于删除的规则
动机明确表示不下定论不是文档能判定的项目

先把设置承诺的那句话钉住

在 Chrome 里这个设置叫做设备上的网站数据，路径是设置、隐私和安全、网站设置、其他内容设置。页面顶部的说明写着，你访问的网站可以保存关于你在做什么的信息，好让它按预期工作，并举了保持登录和购物车两个例子。下方是三个默认行为的单选项。

选项界面上的原句并列显示的结果说明
允许允许网站在你的设备上保存数据网站更有可能按你预期的方式工作
退出时删除关闭所有窗口后删除网站保存到你设备上的数据帮助文档写的是网站更不容易记住上一次访问
拦截不允许网站在你的设备上保存数据，并标注为不推荐网站可能不会按你预期的方式工作
自定义行为下方列出的网站按单独设置而不是默认值走两份列表：允许在设备上保存数据，以及不允许

缝隙就是从这里开始的。帮助文档写了三个选项的名字和大致效果，却没写自定义列表与默认值冲突时谁赢，也没写哪些途径能让记录出现在那份列表里。界面上的词是默认行为，可判定并不止于默认值。

网站数据不是一整块

网站数据这一个词底下，站着若干套生命周期、作用域规则和 API 都不同的存储，窗口全部关闭时跑的流程正是照这些区分走的。

  • Cookie — 服务器用响应头种下、每次请求又被带回的值。范围按域名划定，而不是按源
  • 本地存储与会话存储 — 脚本写入的键值存储。会话存储绑定标签页生命周期，本地存储不是
  • IndexedDB — 结构化数据库，体积通常最大，离线应用的状态多在这里
  • 缓存存储与 Service Worker — 装离线响应的存储，以及控制它的注册记录
  • Origin Private File System 与 Storage Buckets — 源专属的文件层级，以及把存储切成可单独回收单元的新 API
  • 浏览器缓存 — 不是网站控制的存储，而是浏览器为性能留的副本，属于另一类

Chromium 在所有窗口关闭时执行的代码分成两条路。非 Cookie 的存储按存储区域一次性清掉，Cookie 单独处理。源码注释把理由写得很直白：Cookie 不按源划定范围，搭不上按源匹配的那套。而回答「这个源是不是仅限会话」的函数值得停一下，它读的是 Cookie 的内容设置，没有别的。

// chrome/browser/sessions/session_data_deleter.cc
bool OriginMatcher(const blink::StorageKey& storage_key,
                   storage::SpecialStoragePolicy* policy) {
  return policy->IsStorageSessionOnly(storage_key.origin().GetURL()) &&
         !policy->IsStorageProtected(storage_key.origin().GetURL());
}

// chrome/browser/extensions/extension_special_storage_policy.cc
bool ExtensionSpecialStoragePolicy::IsStorageSessionOnly(const GURL& origin) {
  return cookie_settings_->IsCookieSessionOnly(origin);
}

于是，界面上选的设备上的网站数据状态，内部是作为 Cookie 内容设置存下来的，而这一个值决定了跟 Cookie 毫无关系的存储的命运。界面上是两个概念，代码里是一个。

网站到哪里结束，浏览器功能从哪里开始

这个设置管的是网站保存的东西。浏览器自己保存的东西在另一个格子里，而那个格子在开关的射程之外。配置文件目录把两类装在同一个文件夹，chrome://version 里的 Profile Path 就是那个位置。

浏览器功能使用的存储不经过网页能调用的那套存储 API，所以网站数据删除流程根本不会去看它。同步状态、安全浏览预下载的名单、地址栏给建议时参考的记录、翻译功能的偏好，都不是网站建的存储，归清除浏览数据界面的其他条目或账号设置管。

所以边界画了两次。第一条线问数据在网站存储里还是浏览器内部存储里，第二条线问删除流程被写成扫到哪里为止。第二条线自己也有明写的例外：Chromium 源码把扩展程序协议的源，连同用户自己安装的托管应用，归为受保护存储，在关闭时的清扫中跳过。同一个函数还写明，默认预装的应用不享有这份保护。

这个例外跟任何一家公司无关，是浏览器层面的设计：每关一次窗口就丢掉配置的扩展程序根本没法用。例外存在本身不是结论，值得追的永远是哪些例外存在、又写在哪里。

写在文档里的例外 - 账号与活动记录

Chrome 关于清除浏览数据的帮助页里有三句话，大多数人会一眼扫过。它们都在收窄「删掉了」的范围，没有一句是藏起来的。

  • 在已登录 Chrome 的状态下删除 Cookie，不会让你退出谷歌账号
  • 保存在谷歌账号里的银行卡和地址，不会被这个操作删除
  • 在谷歌服务上的搜索和其他活动保存在账号里，需要从账号一侧另行清除

面向企业的管理员策略文档在同一位置也有一句对应的话。那条让管理员指定所有窗口关闭时清掉哪些类别的策略，说明里就写着删除 Cookie 时用户仍保持在谷歌账号的登录状态。同一段还带了第二个条件：若浏览器或操作系统不是正常退出，那一次的删除完全不会发生，因为关闭并非由用户关掉所有窗口造成。

这里是全篇的心脏。名为删除网站数据的操作，被设计成不去碰账号状态，而这个设计是写下来的。用户预期的删除范围和文档规定的删除范围分岔的地方，正是这条线。这条线放在哪里既是技术判断也是商业判断：保持登录对使用的人确实方便，对运营账号体系的一方同样有利。

代码定下的优先级 - 一条允许压过删除

Cookie 那一侧的判定在 Chromium 里就是一个函数，检查顺序写得很清楚。这个顺序正是「例外能落脚的位置」的精确坐标。

  1. 如果该源的 Cookie 设置是允许，当场就不是删除对象，函数直接返回
  2. 接着遍历例外记录，只要有一条域名匹配且设为允许，同样不是删除对象。仅限会话的记录只是立个标记
  3. 最后，若生效设置为仅限会话，或者遍历途中命中了仅限会话的规则，才执行删除
// components/content_settings/core/common/cookie_settings_base.cc
ContentSetting setting = GetContentSetting(
    origin, GURL(), ContentSettingsType::COOKIES, &setting_info);
if (setting == CONTENT_SETTING_ALLOW) {
  return false;              // 不删除
}
for (const auto& entry : cookie_settings) {
  if (net::cookie_util::IsDomainMatch(domain, host)) {
    if (entry.GetContentSetting() == CONTENT_SETTING_ALLOW) {
      return false;          // 一条允许记录就赢了
    } else if (entry.GetContentSetting() == CONTENT_SETTING_SESSION_ONLY) {
      matches_session_only_rule = true;
    }
  }
}
return setting == CONTENT_SETTING_SESSION_ONLY || matches_session_only_rule;

就算把默认值设成关闭后删除，只要有一条域名重叠的允许记录，那一条就赢。域名匹配是上级规则覆盖下级，所以挂在某个可注册域名上的一条，能够到它及其子域名的全部 Cookie。按上一节所说，同一个设置值也决定该源的非 Cookie 存储要不要被清扫。

管理员策略文档里有一条同样意思的提醒。当允许、拦截、仅限会话这三种 URL 策略存在重叠模式时，文档写的是谁优先并未作出规定。未作规定的优先级，按定义就是行为可能随版本变化的区域。

因此，仅凭「存在例外」并不能锁定原因。放例外的位置本来就是设计的一部分，界面上也以自定义行为的名义露了出来。剩下的问题是那里进了什么、走哪条路进去，而这只有正在运行的配置文件能回答。

关闭所有窗口这个条件后面的附注

条件从句值得和承诺读得一样细。这个设置的触发条件是关闭所有窗口，不是退出浏览器，在桌面系统上这两件事并不相同。

只要还有一个窗口开着，流程根本不会跑。后台应用设置或托盘常驻让进程活着时，在键盘前的人看来跟全部关掉一模一样。非正常退出以另一条路径得到同样结果，策略文档写得很明确：那一轮删除会被跳过。

如果把浏览器设成启动时恢复上次会话，还会多出一个分支。在这种配置下，退出流程会跳过对没有过期时间的会话 Cookie 的整体清除那一步，被仅限会话规则命中的仍然照清。两种范围不同的删除在这里纠缠，而其中一种被另一块界面上的选择关掉这件事，设置界面没有任何提示。同一段流程里，仅限会话的源的媒体设备标识值和信任令牌的仅限会话数据也会一并清理。

分区之后的网站这个词

网站这个词在最近几年又被切细了一层。Chrome 从 115 版起对全部用户启用存储分区。存储的键不再只是一个源，而是源与顶级站点的组合，另外还多一个比特，记录祖先链上是否出现过跨站点的框架。

  • 存储类 API — 配额系统、本地与会话存储、IndexedDB、Cache Storage、Origin Private File System、Storage Buckets、Clear-Site-Data 响应头的作用范围，以及 137 版起的 Blob URL 存储
  • 通信类 API — Broadcast Channel、SharedWorker 和 Web Locks 按同样的键划分
  • Service Worker — 在第三方上下文中注册的会被分区，以堵住基于时序的侧信道

结果是，某个域名的本地存储并不是一份，它按当初在哪个顶级站点下创建而分成若干格子。列表里折叠成一行域名的条目，实际可能是多个分区的和。仅凭残留体积断定是哪个网站留下的，理由就不牢。

Cookie 那一侧的范围规则是另一根轴。某次请求会不会带上 Cookie，由 SameSite 按请求类型给出的判定表决定。完全不需要存储就能认出设备的那一类信号又是另一根轴，正如没有东西可删的追踪那篇所写，它完全在任何删除设置的射程之外。

把前面的规则按类型折起来就是下表。会留下的那一栏只写文档和源码能确认的路径。

别的浏览器也有同一个位置

凡是提供退出时删除的浏览器，都会连例外机制一起出货，因为没有例外，保持登录之类的功能无法成立。厂商之间不同的是名称和文档化密度。

浏览器退出或过期时的删除机制已文档化的例外依据的性质
Chrome 与 Chromium设备上的网站数据的退出时删除，以及列出退出时清理类别的管理员策略自定义允许列表、策略中的允许 URL 列表、受保护存储、账号保持登录设置字符串、源码、策略定义、帮助页
Firefox管理员策略的关机时清理，按缓存、Cookie、历史、会话、站点设置等类别分别指定关机时也不清除其 Cookie 和网站数据的源列表（154 版起），以及 Cookie 策略里的允许与会话允许列表官方管理员文档
Safari 与 WebKit对长期没有用户交互的网站，在固定期限后删除脚本可写的存储添加到主屏幕的网页应用另行计数、不在范围内，以及通过 Storage Access API 取得的授权引擎团队的官方博客
Edge关闭时清除浏览数据不清除的站点列表不是产品文档，而是支持人员的论坛回复

Edge 这一行尤其需要把出处摆在明面上。在一个公开的问答帖里，一位微软支持工程师写道，自家域名的默认 Cookie 不被清除属于设计如此的行为。这是支持渠道的回复而非产品文档里的规定，两者分量不同。不过要立起同一种安排在不止一家厂商存在这个论点，这已经够用。

Firefox 那侧的例外属于最近才明文化的一类：关机时清理策略上挂例外源列表是从 154 版开始，在那之前只有按类别的开关。

画线的一方和受益的一方重合时

当造浏览器的组织同时在这个浏览器上经营搜索、广告和账号业务时，决定这条边界落在哪里的一方，和落点的受益方，就是同一方。这是关于安排的陈述，不是关于品行的陈述。同样的安排到处都有：操作系统厂商做默认浏览器，搜索公司做浏览器引擎，内容公司同时运营自家内容的分发通道。

这种安排产出的不是结论，而是举证责任的方向。当边界恰好落在对自家服务有利的一侧，外人很难分清那是功能上的必要还是商业上的便利。一个让人保持登录的例外，既是真实的便利，也是账号业务的资产，围绕动机争论多久都分不开。

所以在这种安排里，文档化就成了信任的替代品。有例外就写下来，把列表放在用户打得开的界面上，若代码里存在优先次序就写明。在同一个产品内部这个密度也不均匀：账号保持登录这个例外出现在帮助页和策略说明两处，而设备上的网站数据那一页完全没提允许记录压过默认值。那条规则只在源码和策略定义里读得到。

这个差别会原样搬进日常工程。一个设置悄悄支配好几套存储、例外列表压过默认值、有一段被有意留作未规定的优先级，这些都该写进文档而不是留给读者推断。围绕广告拦截与扩展 API 的权力分配，是同一结构的另一副面孔。

用户可以自己走的步骤

设置界面给的是状态，存储界面给的是结果。两者对不上时，答案永远在后者。

chrome://settings/content/siteData      三个默认选项加自定义列表
chrome://settings/content/all           设备上的网站数据列表（按站点的体积）
chrome://settings/clearBrowserData      清除浏览数据（按类别）
chrome://version                        Profile Path — 这个配置文件的存放位置
chrome://extensions                     已安装的扩展程序
  1. 在设置界面读一下当前选中的是三个默认行为中的哪一个
  2. 把下面两份自定义列表都读一遍。出现在那里的站点根本就没在跟默认值走
  3. 在设备上的网站数据列表里读还留着的站点和体积，记住一行域名可能是多个分区的和
  4. 关掉所有窗口再打开，把同一份列表再读一遍。若当时还有窗口活着，那只是条件没成立
  5. 在开发者工具的 Application 面板按类型读。Cookies、Local storage、Session storage、IndexedDB、Cache storage 是彼此独立的条目，存储概览还会列出用量分布

配置文件和访客窗口是另一套划分范围的机制。配置文件是用户数据目录下的子目录，分开配置文件就分开了存储。访客窗口按 Chrome 帮助页的说法，会在会话结束时把浏览历史、Cookie 和网站数据从本机删除。但同一页也把限度写在旁边：访问过的网站、登录过的网站、运营网络的组织、网络服务商和搜索引擎照样看得见这些活动。不在本机留下和不被观测到是两个不同的主张，被主张的只有前一个。

下次该怎么读这类报道

关于浏览器行为的观察类报道还会出现。只要分开六件事，多数报道就各归其位。

  • 是对哪个设置的例外 — 有没有点明设置名称和界面路径。拦截第三方 Cookie 和退出时删除是不同的功能
  • 是观察还是规则 — 一个人的复现是观察，文档和源码是规则。观察推不翻规则，规则有义务解释观察
  • 有没有对照组 — 有没有给出相同条件下对其他站点走同一步骤的结果
  • 放例外的位置本来就有吗 — 如果有，目击到一个例外并不构成对原因的锁定
  • 有没有记版本 — 浏览器行为随版本变化，未作规定的优先级区间尤其快
  • 是关于动机的句子还是关于行为的句子 — 动机不是文档能判定的。只留下行为主张，剩下的会硬实得多

这份清单并不专属于浏览器。从客户端现象反推服务端规则的场面到处都是，而这种推断在哪里断掉，跟谈信任边界的那篇里看到的是同一个问题。

没能确认的部分

下面这些项目因为无法与一手资料对上文面，没有作为事实写进正文，理由一并记下。

  • 被报告的行为本身 — 某个域名的数据在退出后仍然留存是复现结果，没有官方文档可佐证，所以正文只把它归属为观察。文中引用的 152.0.7977.83 是确实发布过的稳定版版本号，写作时的稳定版是 153.0.8010.27，版本不同结果也可能不同
  • Chrome 是否为某个域名预置了允许记录 — 设置字符串资源和帮助文档里都没有这样的规定。不读运行中配置文件的例外列表，这一项分不出来
  • 观察到的残留的成因 — 允许记录、扩展程序、恢复会话设置、非正常退出、遗留的后台进程都会给出同样症状。原文说排除了其中几种，但没说剩下的全部排除
  • 2020年那件事在何时因何改动被修好 — 这次的文章说被修好了，却没给出该改动的标识、版本或 Chromium 的问题编号
  • 对照组的范围 — 原文说问题域名似乎是唯一的一个，又补充说截图是解释而非证据。到底比较了几个站点、在什么条件下比较，文中没写
  • 规定 Edge 行为的产品文档 — 自家域名 Cookie 留存属于设计如此的说法只在支持渠道的回复里出现，没有找到同样意思的产品文档
  • Chrome 隐私白皮书里按功能列出的存储位置 — 该文档正文由脚本绘制，静态请求取回的只是外壳。浏览器内部功能的存储位置只按帮助页和源码写出的范围描述
