测量方法 - 由接收程序自己打印命令行和argv

PowerShell如何拆分并传递参数，从PowerShell自己的输出中无从得知。必须由接收方打印出进程实际收到的字符串。下面这个小程序会同时打印Windows API返回的原始命令行（raw），以及C运行时把它拆分后的argv。在之后所有代码块中，raw行是PowerShell组装的命令行，argv行是接收程序看到的参数。参数个数行（n）就是argv的长度，所以省略了；行首的>>>是被测试的输入。

import sys, json, ctypes
                    ctypes.windll.kernel32.GetCommandLineW.restype = ctypes.c_wchar_p
                    raw = ctypes.windll.kernel32.GetCommandLineW()
                    i = raw.find('argv.py')
                    print('  raw : ' + raw[i + 7:].lstrip().encode('ascii','backslashreplace').decode())
                    print('  argv: ' + json.dumps(sys.argv[1:], ensure_ascii=True))
                    print('  n   : %d' % (len(sys.argv) - 1))

官方文档这样描述这一过程：调用原生命令时，PowerShell先解析参数，再把解析后的参数用空格连成一个字符串，这个字符串被赋给ProcessStartInfo的Arguments属性。字符串里的引号必须用额外的引号或反斜杠来转义，文档写明，反斜杠不是PowerShell的转义字符，而是底层API的转义字符。这一段就是全文的框架：PowerShell拼出一行，接收程序再把这一行拆开。结果取决于PowerShell的规则与接收程序的拆分规则相遇的地方。

基本规则 - 有空格就包起来，空字符串会被丢弃

先看最简单的输入。$v里是a b（含空格）。

>>> python argv.py a b
                      raw : a b
                      argv: ["a", "b"]
                    
                    >>> python argv.py ''
                      raw : 
                      argv: []
                    
                    >>> python argv.py '' x
                      raw : x
                      argv: ["x"]
                    
                    >>> python argv.py 'a b'
                      raw : "a b"
                      argv: ["a b"]
                    
                    >>> python argv.py "$v"   ($v = 'a b')
                      raw : "a b"
                      argv: ["a b"]
                    
                    >>> python argv.py '$v'
                      raw : $v
                      argv: ["$v"]
                    
                    >>> python argv.py a$v
                      raw : "aa b"
                      argv: ["aa b"]
输入raw（组装出的命令行）收到的argv
a ba b2个参数
''（什么都没有）0个参数
'' xx1个参数，只剩x
'a b'"a b"1个参数
"$v""a b"1个参数
'$v'$v1个参数，字面文本
a$v"aa b"1个参数
  • 只有含空格的参数才会被双引号包起来。没有空格就不包。
  • 单引号由PowerShell剥掉，内容原样传递。'$v'不会展开，"$v"会展开。展开后的值即使含空格也不会被分词，仍是一个参数。
  • a$v这种变量后面跟着字符的形式，也连成一个参数。官方文档同样写道，简单变量引用之后的字符属于同一个参数。
  • 空字符串在raw中不留痕迹。它后面的参数位置依次前移一位。

最后一项是无声事故的起点。在--name '' --flag这样的调用中，即使想传一个空值，接收方看到的也是--name --flag。

双引号会消失 - 最先坏掉的是JSON

参数中的双引号在5.1中不会被转义。文档也写道，PowerShell的命令行解析会去掉你输入的引号字符。

>>> python argv.py 'say "hi"'   (single-quoted, contains double quotes)
                      raw : "say "hi""
                      argv: ["say hi"]
                    
                    >>> python argv.py 'say"hi'   (no space in value)
                      raw : say"hi
                      argv: ["sayhi"]
                    
                    >>> python argv.py '{"a":1}'
                      raw : {"a":1}
                      argv: ["{a:1}"]
                    
                    >>> python argv.py '{"a": 1}'   (JSON with a space)
                      raw : "{"a": 1}"
                      argv: ["{a: 1}"]
  • 'say "hi"'含空格所以被双引号包起来，但内部的引号原样进入，raw成为"say "hi""。接收方把引号当分隔符消耗掉，得到say hi。
  • 像'say"hi'这样没有空格时，参数不被包起来，引号原样进入raw，结果却是sayhi。不论是否被包起来，引号都会被消耗。
  • '{"a":1}'到达时是{a:1}。没了引号的JSON是无效的。含空格的'{"a": 1}'也是{a: 1}。

这种症状会以同样的形态出现在所有传递含引号的值的调用中，如curl -d、git commit -m、python -c和node -e。危险之处在于不报错，值却被悄悄改变。

保留双引号的方法 - 反斜杠转义、重复引号与已包好的值

测试了文档提到的两种方法（重复引号、反斜杠）以及已经用引号包好的值。

>>> python argv.py 'say \"hi\"'   (backslash-escaped quotes)
                      raw : "say \"hi\""
                      argv: ["say \"hi\""]
                    
                    >>> python argv.py '{\"a\":1}'
                      raw : {\"a\":1}
                      argv: ["{\"a\":1}"]
                    
                    >>> python argv.py '{\"a\": 1}'
                      raw : "{\"a\": 1}"
                      argv: ["{\"a\": 1}"]
                    
                    >>> python argv.py 'say ""hi""'   (doubled quotes inside single quotes)
                      raw : "say ""hi"""
                      argv: ["say \"hi\""]
                    
                    >>> python argv.py 'a""b'
                      raw : a""b
                      argv: ["ab"]
                    
                    >>> python argv.py '{""a"":1}'
                      raw : {""a"":1}
                      argv: ["{a:1}"]
                    
                    >>> python argv.py '"a b"'
                      raw : "a b"
                      argv: ["a b"]
                    
                    >>> python argv.py 'x "a b"'
                      raw : "x "a b""
                      argv: ["x a", "b"]
                    
                    >>> python argv.py '""'
                      raw : ""
                      argv: [""]
方法输入收到的值判定

反斜杠转义'{\"a\":1}'{"a":1}成功（无空格）
反斜杠转义'{\"a\": 1}'{"a": 1}成功

  • 把值中的双引号替换成反斜杠加双引号，无论有没有空格，都完整到达。
  • 重复引号只有在PowerShell用双引号包住参数时（含空格时）才对Python有效。在不被包裹的参数里引号被消耗，而在git中同样的形式则是错误。同一条命令行，不同的接收程序可能有不同的拆分规则。
  • 已经用双引号包好的"a b"，5.1没有再包一次（已包好的值并非总是如此，条件在第10节中做了实验），但那些引号会被当作分隔符消耗。如果引号必须是值的一部分，这种方法就用不了。
  • 把两个双引号字符作为值传入，会到达一个空字符串。这是找回第3节中消失的空参数的办法。

末尾的反斜杠会吞掉下一个参数

含空格的路径会被双引号包起来。如果这个路径以反斜杠结尾，就会出问题。下面的argv行是JSON格式，所以一个反斜杠写成两个。

>>> python argv.py 'C:\Program Files\x'
                      raw : "C:\Program Files\x"
                      argv: ["C:\\Program Files\\x"]
                    
                    >>> python argv.py 'C:\Program Files\x\'   (path ends with backslash)
                      raw : "C:\Program Files\x\" next
                      argv: ["C:\\Program Files\\x\" next"]
                    
                    >>> python argv.py 'C:\Program Files\x\\'   (two backslashes)
                      raw : "C:\Program Files\x\\" next
                      argv: ["C:\\Program Files\\x\\", "next"]
                    
                    >>> python argv.py 'C:\x\' next   (no space in path)
                      raw : C:\x\ next
                      argv: ["C:\\x\\", "next"]
  • 含空格的路径C:\Program Files\x是正常的。
  • 同一路径以一个\结尾时，raw变成"C:\Program Files\x\" next，结束的引号被读成被转义的引号，后面的next被并入同一个参数。收到的参数只有一个，值是C:\Program Files\x" next。不是少了一个参数，而是两个参数结成了一团。
  • 末尾放两个\\，会被读成一个反斜杠加结束引号，next单独到达。到达的路径末尾留有一个反斜杠。
  • 不含空格的路径C:\x\不会被包起来，所以没有这个问题。

条件是两个同时成立：参数含空格因而被包起来，并且以反斜杠结尾。把文件夹路径连末尾分隔符一起拼出来的代码，例如指向用户文件夹下含空格的文件夹的变量，就会撞上这个问题。用TrimEnd('\')去掉末尾的反斜杠，或者把它加倍再传，就正常了。

变量、逗号与元字符 - 哪些是PowerShell的工作

参数里混有PowerShell先解释的内容，也有原样传递的内容。

>>> python argv.py 1,2
                      raw : 1,2
                      argv: ["1,2"]
                    
                    >>> python argv.py $env:OS
                      raw : Windows_NT
                      argv: ["Windows_NT"]
                    
                    >>> python argv.py (1+2)
                      raw : 3
                      argv: ["3"]
                    
                    >>> python argv.py '%OS%'
                      raw : %OS%
                      argv: ["%OS%"]
                    
                    >>> python argv.py *.nothing  (no match, wildcard)
                      raw : *.nothing
                      argv: ["*.nothing"]
                    
                    >>> python argv.py 'a & b' 'a | b'
                      raw : "a & b" "a | b"
                      argv: ["a & b", "a | b"]
                    
                    >>> python argv.py a;echo b   (semicolon ends the statement)
                      raw : a
                      argv: ["a"]
                    b
                    
                    >>> python argv.py ('caf' + [char]0xE9) ('x' + [char]0xD55C)
                      raw : caf\xe9 x\ud55c
                      argv: ["caf\u00e9", "x\ud55c"]
  • 1,2以单个参数1,2到达。官方文档写道，逗号在PowerShell命令中会创建数组，但在原生应用程序中被解释为可扩展字符串的一部分。
  • $env:OS、(1+2)这样的变量和括号表达式，由PowerShell先求值再传递值。'%OS%'不被PowerShell触碰，保持字面。
  • 通配符*.nothing不会展开，原样传递。PowerShell不做文件名展开。
  • 像'a & b'这样引号内的元字符作为一个参数被保留。引号外的分号会结束命令。在a;echo b中，Python只收到参数a，echo b作为单独的命令运行并输出了b。
  • 非ASCII字符因输出时使用了ASCII转义，显示成\xe9、\ud55c，但参数是正常到达的。这是因为命令行以Unicode传递。

文档列出的参数模式元字符有：空格、单引号、双引号、反引号、逗号、分号、圆括号、花括号、管道符、与号、尖括号、@符号和井号。其中尖括号、@符号和井号只在记号开头才有特殊含义。如果不加引号传递的参数里含有这些字符，PowerShell会先接管它们。

数组与展开传参 - 一个字符串就是一个参数

参数列表可变时，会把它放进变量再传，而放进去的形式决定结果。

>>> $arr = 'x','y z'; python argv.py $arr
                      raw : x "y z"
                      argv: ["x", "y z"]
                    
                    >>> $s = '--flag "a b"'; python argv.py $s
                      raw : "--flag "a b""
                      argv: ["--flag a", "b"]
                    
                    >>> $sp = @('--flag','a b'); python argv.py @sp
                      raw : --flag "a b"
                      argv: ["--flag", "a b"]
                    
                    >>> $h = @{k=1}; python argv.py @h  (hashtable splat)
                      raw : -k:1
                      argv: ["-k:1"]
  • 数组变量$arr每个元素成为一个参数，只有含空格的元素被包起来。
  • 把参数列表放成一个字符串的$s，整体成为一个参数。它因含空格被包起来，内部的引号被消耗，拆成了--flag a和b。这是把列表拼成字符串再传这种做法出错的典型。
  • 对数组做展开传参（@sp），变量里的每个元素各成为一个参数。对于可变参数，这种方式是安全的。
  • 哈希表展开@h把键和值变成了-k:1形式的一个参数。它是否符合原生程序的选项格式，取决于程序本身。

--%与-- - 关闭解析的标记

stop-parsing标记--%会让后面的文字不经PowerShell解释直接传递。文档说明，同一行的其余部分被当作字面量，只有%USERPROFILE%这类Windows写法的环境变量会被替换。

>>> python argv.py --% a "b c" %OS%
                      raw : a "b c" Windows_NT
                      argv: ["a", "b c", "Windows_NT"]
                    
                    >>> python argv.py --% --opt="a b" 'q'
                      raw : --opt="a b" 'q'
                      argv: ["--opt=a b", "'q'"]
                    
                    >>> python argv.py --% "a b" "c
                      raw : "a b" "c
                      argv: ["a b", "c"]
                    
                    >>> python argv.py -x -- y
                      raw : -x -- y
                      argv: ["-x", "--", "y"]
                    
                    >>> python argv.py --opt="a b"
                      raw : "--opt=a b"
                      argv: ["--opt=a b"]
                    
                    >>> python argv.py --opt=$v
                      raw : "--opt=a b"
                      argv: ["--opt=a b"]
                    
                    >>> python argv.py -p:val
                      raw : -p:val
                      argv: ["-p:val"]
  • 在--% a "b c" %OS%中，双引号起到了分隔符作用，b c成为一个参数，%OS%被替换为Windows_NT。正如文档所说，%名称%形式总会被展开，名称未定义时保持原样。
  • --%之后的单引号不会被PowerShell剥掉。'q'带着引号以'q'到达。
  • 引号不成对也会原样传递。未闭合的"c以单个参数c到达。
  • 按文档，--%只在下一个换行或管道符之前有效，重定向也会作为参数传递，除环境变量外不能嵌入任何动态元素。
  • 作为PowerShell命令用标记的--，对原生程序来说只是被当作--参数原样传递。-x -- y成了三个参数。
  • --opt="a b"和--opt=$v都被组装成"--opt=a b"这一个参数，因为选项名与值连成了一个记号。

反引号与here-string - 多行参数

反引号只在双引号字符串里才是转义。在单引号里它就是字面字符。含换行的值可以用here-string构造。

>>> python argv.py 'a`tb' "a`tb"
                      raw : a`tb "a	b"
                      argv: ["a`tb", "a\tb"]
                    
                    >>> python argv.py "line1`nline2"
                      raw : "line1
                    line2"
                      argv: ["line1\nline2"]
                    
                    >>> here-string: python argv.py (@'...'@)  with a double quote inside
                      raw : "first line
                    second "quoted" line"
                      argv: ["first line\nsecond quoted line"]
  • 单引号里的反引号t按字面到达，双引号里的反引号t变成了制表符。
  • 含换行的参数，换行原样进入raw，并作为一个参数到达。与含空格的参数一样，会被双引号包起来。
  • here-string里的双引号像第3节一样被消耗，成了second quoted line。正如文档所说，here-string按字面解释其中的引号，但在传给原生程序的环节又被剥掉了。

如何安全传递带引号的多行值，将在第11节curl.exe的实例中比较。

精确控制命令行的方法 - Start-Process与ProcessStartInfo

要避开PowerShell的组装规则，可以自己构造命令行再传入。先确认了Start-Process的-ArgumentList为字符串时和为数组时会发生什么。

>>> Start-Process python -ArgumentList 'argv.py "a b" {\"k\":1}' -NoNewWindow -Wait
                      raw : "a b" {\"k\":1} 
                      argv: ["a b", "{\"k\":1}"]
                    
                    >>> Start-Process python -ArgumentList @('argv.py','a b','c') -NoNewWindow -Wait
                      raw : a b c 
                      argv: ["a", "b", "c"]

给一个字符串时，raw与输入字符串相同，所以由调用者直接控制双引号和反斜杠。给数组时，只是用空格连接各元素而不加包裹，所以'a b'拆成了a和b两个参数。不能认为数组是安全的。

要精确传递任意值，可以准备一个按C运行时规则转义的辅助函数，把它的结果放进ProcessStartInfo.Arguments。下面的辅助函数会把值中双引号前的反斜杠加倍，用反斜杠转义双引号，把末尾的反斜杠加倍，然后把整体用双引号包起来。

function ConvertTo-NativeArg([string]$a) {
                      if ($a -eq '') { return '""' }
                      $r = $a -replace '(\\*)"', '$1$1\"'
                      $r = $r -replace '(\\+)$', '$1$1'
                      '"' + $r + '"'
                    }
                    function Invoke-NativeExact([string]$File, [string[]]$ArgList) {
                      $psi = New-Object Diagnostics.ProcessStartInfo
                      $psi.FileName = $File
                      $psi.Arguments = ($ArgList | % { ConvertTo-NativeArg $_ }) -join ' '
                      $psi.UseShellExecute = $false
                      $psi.RedirectStandardOutput = $true
                      $psi.StandardOutputEncoding = [Text.Encoding]::UTF8
                      $p = [Diagnostics.Process]::Start($psi)
                      $out = $p.StandardOutput.ReadToEnd()
                      $p.WaitForExit()
                      $out
                    }
$cases = @('plain', 'a b', 'say "hi"', '{"a": 1}', 'C:\Program Files\x\', 'tail\\', 'q"', '', 'a\"b c')
                    foreach ($c in $cases) {
                      $json = Invoke-NativeExact 'python' @('-c', 'import sys,json;print(json.dumps(sys.argv[1]))', $c)
                      $back = $json | ConvertFrom-Json
                      '{0,-22} -> received equal: {1}' -f ("'" + $c + "'"), ($back -ceq $c)
                    }

让Python以argv接收九个值，用JSON返回，再与原值比较的结果如下。其中包含空格、双引号、末尾反斜杠、空字符串，以及反斜杠与双引号的组合。

'plain'                -> received equal: True
                    'a b'                  -> received equal: True

                    '{"a": 1}'             -> received equal: True

                    'tail\\'               -> received equal: True
                    'q"'                   -> received equal: True

                    '{"a": 1}'             -> arg "{\"a\": 1}"                   -> received equal: True
                    'C:\Program Files\x\'  -> arg "C:\Program Files\x\\"         -> received equal: True
                    'tail\\'               -> arg "tail\\\\"                     -> received equal: True
                    'q"'                   -> arg "q\""                          -> received equal: True
                    ''                     -> arg ""                             -> received equal: True
                    'a\"b c'               -> arg "a\\\"b c"                     -> received equal: False

九项中有八项一致，值里同时含反斜杠和双引号的a\"b c不一致。这个值的辅助函数结果本来就以双引号开头并结尾，5.1仍再包了一层，使raw以两个双引号开头，收到的参数被拆成了两个。但其余八项的辅助函数结果（如"say \"hi\""）以同样方式传递，却没有被再次包裹。为查明只有这个值被包裹的原因，对变量做了分离。不使用辅助函数，把只在引号、反斜杠和空格位置上不同的十四个字符串放进变量，用同样方式传递，记录收到的raw是否是输入再被双引号包了一层（rewrapped）。rule列是依据观察提出的假设（只要存在一个空白字符，其前面的双引号个数为偶数（0也算偶数），就会包裹）计算出的值。

function Test-Rule([string]$s) {
                      $n = 0
                      foreach ($ch in $s.ToCharArray()) {
                        if ($ch -eq '"') { $n++ }
                        elseif ([char]::IsWhiteSpace($ch) -and $n % 2 -eq 0) { return $true }
                      }
                      $false
                    }
                    $cases = @(
                      '"a b"',
                      '"a\"b c"',
                      '"a\\"b c"',
                      '"a\\\"b c"',
                      '"a\\\\"b c"',
                      '"a\\\"bc"',
                      '"a\\\b c"',
                      '"say \"hi\""',
                      'a\\\"b c',
                      '"a" b',
                      '"a b" c',
                      'a "b c"',
                      'x y',
                      '"x""y z"'
                    )
                    foreach ($v in $cases) {
                      $raw = (python argv.py $v)[0] -replace '^\s*raw : ', ''
                      '{0,-14} raw={1,-16} rewrapped={2,-5} rule={3}' -f $v, $raw, ($raw -ceq ('"' + $v + '"')), (Test-Rule $v)
                    }
"a b"          raw="a b"            rewrapped=False rule=False
                    "a\"b c"       raw=""a\"b c""       rewrapped=True  rule=True
                    "a\\"b c"      raw=""a\\"b c""      rewrapped=True  rule=True
                    "a\\\"b c"     raw=""a\\\"b c""     rewrapped=True  rule=True
                    "a\\\\"b c"    raw=""a\\\\"b c""    rewrapped=True  rule=True
                    "a\\\"bc"      raw="a\\\"bc"        rewrapped=False rule=False
                    "a\\\b c"      raw="a\\\b c"        rewrapped=False rule=False
                    "say \"hi\""   raw="say \"hi\""     rewrapped=False rule=False
                    a\\\"b c       raw=a\\\"b c         rewrapped=False rule=False
                    "a" b          raw=""a" b"          rewrapped=True  rule=True
                    "a b" c        raw=""a b" c"        rewrapped=True  rule=True
                    a "b c"        raw="a "b c""        rewrapped=True  rule=True
                    x y            raw="x y"            rewrapped=True  rule=True
                    "x""y z"       raw="x""y z"         rewrapped=False rule=False
  • 再次包裹的有十四项中的八项，假设的预测与十四项观察全部一致。只要某个空白前的双引号个数为偶数，就被包裹（x y、"a" b、a "b c"，以及"a b" c的第二个空格）。
  • 反斜杠的个数（1、2、3、4个）不改变结果。第2至5行全部被包裹，结果就像前面带反斜杠的引号也按一个引号计数一样。
  • 未被包裹的六行（第1、6、7、8、9、14行）要么没有空格（第6行），要么空格前的双引号个数为奇数（其余）。
  • 在九个辅助函数结果中，只有a\"b c的结果在空格前有两个双引号（起始引号和被转义的引号），其余八项要么没有空格，要么空格前为奇数个（一个或三个）。

这条规则是为了贴合这十四项观察而提出的假设，并未在5.1的实现或文档中得到确认，本文引用的官方文档摘录里也没有这样的判定。已确认的只有这一观察：5.1是否再次包裹，取决于空格前双引号的个数。因此辅助函数的结果不应交给5.1的普通调用，而应交给原样使用命令行的途径。

方法构造命令行的一方实测结果
普通调用python argv.py ...PowerShell（有空格就包裹）遵循第2至9节的规则
Start-Process -ArgumentList '字符串'调用者raw与字符串相同，2个参数正确

实例 - git commit与curl.exe

在临时仓库中传递了含双引号的提交信息。下面五次调用之后的输出，其编号与调用顺序相同。

git commit -q --allow-empty -m 'fix "x" bug'
                    git commit -q --allow-empty -m 'fix \"x\" bug'
                    git commit -q --allow-empty -m "fix ""x"" bug"
                    git commit -q --allow-empty -m 'fix ""x"" bug'
                    git commit -q --allow-empty -m 'fix "x"'
1) -m 'fix "x" bug'          -> fix x bug
                    2) -m 'fix \"x\" bug'        -> fix "x" bug
                    3) -m "fix ""x"" bug"          -> fix x bug
                    error: pathspec 'bug' did not match any file(s) known to git
                    4) -m 'fix ""x"" bug'        -> fix x bug
                    5) -m 'fix "x"'              -> fix x
  • 第1项是fix x bug，双引号没了，第5项也是fix x。
  • 第2项使用反斜杠转义，fix "x" bug被准确记录。
  • 第3项在PowerShell的双引号字符串里重复了引号，但这个字符串产生的值与第1项一样都是fix "x" bug，所以结果也与第1项相同。PowerShell层面的转义并不会为原生程序转义引号。
  • 第4项把重复引号放进命令行后，git报出pathspec 'bug' did not match错误。第4项那一行显示的信息是上一次提交的。同样的输入在Python中可行，所以重复引号的结果因程序而异。

发送JSON正文的curl.exe -d是更常见的例子。在本地启动了一个把POST正文存入文件的小服务器，并读取收到的正文。

import http.server, sys
                    class H(http.server.BaseHTTPRequestHandler):
                        def do_POST(self):
                            n = int(self.headers.get('Content-Length', 0))
                            body = self.rfile.read(n)
                            open('last_body.txt', 'wb').write(body)
                            self.send_response(200); self.end_headers(); self.wfile.write(b'ok')
                        def log_message(self, *a): pass
                    http.server.HTTPServer(('127.0.0.1', 18080), H).serve_forever()

服务器就是上面的代码，所用curl.exe的路径和版本见下面Get-Command curl.exe的输出。这台电脑的PATH中先找到的是Git自带的curl，所以实际运行哪个curl.exe取决于环境。用C:\Windows\System32\curl.exe（8.13.0）运行同样的调用，收到的正文也相同。下面的调用是在先创建$body和body.json之后运行的。

  • 用单引号写的JSON，到达时成了引号全部消失的{a: 1}。
  • 用反斜杠转义双引号后，以{"a": 1}准确到达。

PowerShell 7.3之后不同 - 只写文档中有的内容

按官方文档（7.4版），PowerShell 7.3改变了解析原生命令的命令行的方式，新变量$PSNativeCommandArgumentPassing对其进行控制。文档警告说，这一变更是破坏性变更，可能会破坏那些为绕开调用原生应用程序时各种问题而写的脚本和自动化。

  • 取值有Legacy、Standard、Windows，Legacy是历史行为。
  • 在Windows上默认值是Windows，在其他平台上是Standard。
  • Windows模式与Standard相同，但对于cmd.exe、cscript.exe、find.exe、sqlcmd.exe、wscript.exe以及以.bat、.cmd、.js、.vbs、.wsf结尾的文件，使用Legacy方式。

此环境中没有pwsh，7的行为没有运行。以上是文档的原话，本文的5.1规避办法（反斜杠转义、辅助函数）在7中如何表现没有确认。把5.1的规避办法搬到7之前，用同样的方法打印raw和argv，是最可靠的确认方式。

按场景选择表

根据5.1中的实测结果，整理按场景可用的方法。接收程序只测试了Python、git和curl.exe三种。

场景方法依据
没有空格和引号的简单参数直接使用实测，raw与argv和输入相同
含空格的变量值直接用"$v"或$v实测，被包成一个参数
值里有双引号把双引号替换成反斜杠加双引号再传实测，在python、git、curl.exe中都完整到达
空字符串参数把两个双引号字符作为值传入实测，以一个空字符串到达
以反斜杠结尾的路径去掉末尾的反斜杠，或写成两个实测，避免下一个参数被合并
可变的参数列表构造数组再展开传参实测，一个字符串作为一个参数到达
引号很多或多行的正文写入文件，使用程序的文件参数选项实测，curl.exe的文件输入准确到达
需要逐字符控制命令行ProcessStartInfo.Arguments加自制的转义辅助函数，或给Start-Process一个字符串实测，辅助函数九项一致
不可信的输入，或经过批处理文件不要直接作为参数传递文档的警告，对批处理文件，参数以原始命令行传给cmd.exe

所有行有一个共同的原则：接收程序看到了什么参数，不让接收程序打印出来就无从得知。调用新工具时，先把同样的形式传给一个数参数的程序，确认raw和argv，比这张表里的任何一行都更可靠。

未能确认的内容

  • PowerShell 7（pwsh）：环境中没有，无法直接运行。7.3之后的参数传递以及$PSNativeCommandArgumentPassing三个取值的行为，是官方文档的原话。
  • 5.1的规避办法（反斜杠转义、重复引号、辅助函数）在7.3之后如何表现：没有运行。
  • Python、git、curl.exe以外的程序：Node、Go、Java、.NET以及其他MinGW系工具的命令行拆分规则。重复引号在git中失败的原因没有确认，只记录了结果。
  • 经由cmd.exe、.bat、.cmd的调用（npm.cmd等）：没有运行。文档警告，对批处理文件，参数以原始命令行传递。
  • here-string正文在curl.exe中中途被截断的原因：是参数被拆成两个的推测，没有直接确认curl一侧的参数。
  • 其他Windows版本、区域设置、控制台代码页下的差异：只在韩文版Windows 10的5.1.19041上确认。非ASCII参数只测试了Python一种情形。
  • 5.1再次包裹参数的内部条件：只确认了与十四个字符串的观察相符的规则，未能在5.1的实现或文档中确认。这条规则在更多样的输入下是否成立，也没有测试。
  • Start-Process的-Verb等ShellExecute路径，以及用调用运算符&运行的情形：未涉及。
