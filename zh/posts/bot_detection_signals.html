引言:从日志里一个空栏开始的判断

注册用户列表里,每天差不多同一时段都会多出几个账号。既不发帖也不再登录。打开访问日志会看到,创建这些账号的请求里 User-Agent 那一栏是空的。接下来浮现的念头通常只有一个:User-Agent 为空就拒绝。

这一行确实能减少幽灵账号。同时它也会毫无声息地把一部分真实用户推到服务之外。被拦下的人不会去客服留言,只会直接关掉页面,于是指标里只留下「拦截成功」,而「失去的人」不会留下任何痕迹。

本文要讲的是加上这一行之前应当知道的事:为什么靠客户端发来的值无法区分人与自动化,那么该看什么,以及按判断出错时的代价而不是按识别精度来决定响应强度的设计为什么在实务中才站得住脚。攻击方的手法不在讨论范围内。

1. 空的 User-Agent 不是机器人的证据

定义 HTTP 语义的 RFC 9110 在 10.1.5 节写道:A user agent SHOULD generate a User-Agent header field。是 SHOULD 而不是 MUST。不发送并不构成违反规范。

同一节还补充道:a user agent MAY allow its User-Agent value to be configured by the user。让用户自行修改该值,同样是规范预设的正常行为。这一栏从一开始就被设计成客户端可以填也可以留空的位置,所以在真实流量里会因为各种原因变空或变得奇怪。

日志中观察到的现象常见原因是否自动化
没有值并非浏览器的原生应用与移动端 SDK 建立的连接不是。是我们自己的应用用户
没有值企业代理或安全网关对请求头做了归一化不是。是企业客户的流量
值很简单或为空通过隐私扩展或设置抹去该值的用户不是。这是有意的选择
陌生且陈旧的字符串嵌入式设备、智能电视、自助终端大多不是
直接写着工具名的值命令行工具、API 客户端、集成脚本是自动化,但通常是正当的
完整的浏览器字符串真实浏览器,或是驱动真实浏览器的自动化仅凭这个值无法区分

表格最后一行就是本节的结论。空值不是自动化的证据,完整的值也不是人的证据。两个方向都已经塌掉,所以仅凭这一栏无法做出任何一侧的判定。

  • 发送是建议而不是义务 - 没有它也是正常请求
  • 值的内容由客户端决定 - 通过用户设置修改同样是预设行为
  • 协议里没有让服务端验证该值的手段 - 不存在可供比对的原本

2. 伪造是自由的 - 是主张而非证据

第三项是核心。User-Agent 是客户端自己写好发过来的自我介绍,服务端没有可以比对的原本。不能把客户端发来的值放进信任边界内侧的理由在这里同样适用。正如不能相信请求体里的价格字段,请求头里的身份主张也不能相信。

编写浏览器文档的一方也劝阻按这个值做分支。MDN 在 User-Agent 文档顶部放了一条警告,提醒读者另行阅读为什么给不同浏览器返回不同内容通常是个坏主意,并写明这个头字段可以用来识别特定的用户代理,因而可能被用于指纹采集。

其结果就是取值的收缩。各家浏览器在有意减少这个头字段所承载的信息,并建议服务端如需更多信息就通过单独的提示机制去请求。任何靠这个字符串来区分事物的规则,都会随着时间推移而分辨率下降。

2.1 依然保留的用处

这并不是说它没用。只是说不能作为放行与拒绝的唯一依据,值本身在三处仍然在发挥作用。

  • 统计与审计 - 用于掌握哪些客户端构成在访问服务。因为不用于判定,可伪造性就不成问题
  • 识别主动表明身份的爬虫 - 搜索爬虫通常会在值里写上名称和说明网址。不过确认必须交给别的维度。谷歌在验证文档中给出了先反向解析再正向回溯的方法,以及与公开地址段比对的方法
  • 缩小候选 - 决定接下来该细看哪里的线索。判定由随后的维度完成

归纳一下 - 主动表明身份的机器人可以靠名字辨认,而决定不表明身份的自动化则无法如此。基于 User-Agent 的规则会造成只筛掉诚实一方的不对称。面向诚实爬虫的策略,用 robots.txt 来声明要比手工维护规则清单更好。

3. 误拦截的代价 - 悄无声息离开的人

评估拦截规则时常看的数字是「拦截了多少条」。这个数字并不能告诉你规则是否在正确地工作。真正该知道的是被拦下的那些里混进了多少人,而标准日志里没有这项。误拦截之所以危险,是因为它很安静。

  • 机器人失败了还会再来。重试是默认行为,所以拦截在压缩自动化总量上并不像感觉的那么有效
  • 人失败一次就不会再来。在注册页面被拒绝一次之后还会再试的用户比例并不高
  • 不满传不到我们这里。提交咨询通常需要登录,而在注册环节被拦下的人根本没有账号
  • 共享地址背后人很多。运营商级地址共享和企业代理会让同一个来源背后站着数百甚至数千人

无障碍问题也叠加在这里。使用辅助技术的人、低配设备、窄带线路,以及使用自动填充和密码管理器的用户,都会自然产生「不像人」的模式。判别器做得越精细,这个群体反而越容易先被抓住。验证方式越来越重的趋势中被反复指出的问题也是同一个。

所以在上线规则之前必须经过一个环节:观测模式。不真正应用规则,只记录如果应用了会命中哪些请求。把一两天的记录用肉眼扫一遍,通常立刻就能看出里面是否混着我们自己的应用用户或企业客户。跳过这一步就打开的规则,永远不会告诉你它切掉了什么。

4. 组合信号 - 行为、网络、时间

那么该看什么。维度大体上有三个,而前提是这三个单独看都很弱。

4.1 行为 - 输入的速度与顺序

  • 人不会从上到下一次性填完表单。会退回去改,字段之间的间隔参差不齐
  • 打字和粘贴混在一起,焦点经常离开页面又回来
  • 自动化通常很均匀。不过均匀同样会来自密码管理器和自动填充

4.2 网络与连接特征

  • 同一来源在短时间内反复发出的创建请求。要成批地看而不是看单条请求
  • 声明与实际行为之间的错位。如果发来完整的浏览器字符串,却没有任何浏览器必然会一并去取的附属资源请求,这个不一致本身就是观察对象
  • 这里同样禁止单独判定。一个来源地址并不等于一个人

4.3 时间分布 - 只在集合中才可见的信号

  • 人的注册会画出一条日曲线。早上增多、凌晨减少,按星期也有形状
  • 在完全相同的时分反复出现的创建,不是人的节律而是调度器的节律。把几天的数据叠起来才会浮现
维度看什么单独为何弱叠加后意味着什么
声明的值User-Agent 等请求头的构成由客户端自由决定只有与别的维度冲突时才有意义
行为输入顺序与间隔的分布辅助技术和自动填充会造出同样的形状与时间分布叠加时可能性上升
网络按来源成批的请求、声明与行为不一致一个地址背后有很多人同一来源加同样的时钟模式就会变强
时间分布创建时刻的日内与周内分布人也可能集中在特定时段精确到分钟的重复很难用人来解释

每个信号单独都构不成依据,只有多个维度指向同一方向时才会变强。而变强这句话并不等于「可以拦截了」,这是下一节的主题。

5. 误判昂贵的一侧与便宜的一侧

机器人治理失败的地方,多半不在识别精度,而在于响应是二值的。只有放行和拦截两种,每一次判断都变成死刑判决。于是只能把规则放松,而放松的规则什么也拦不住。首先要做的不是阈值而是分级。

信号强度响应判断错时用户会遇到什么回滚的代价
弱只做记录没有没有
弱到中延后在列表中的展示,并排除出索引自己的帖子会晚一点被看到把展示状态改回来即可
中暂缓新账号的部分功能发外链或邀请要晚些才能用解除暂缓就结束了
中到强送入人工复核队列需要等待审核通过审核处理时间
强拒绝注册或封停账号无法使用,多数就此离开即使撤销,人也不会回来

最后一列就是设计的全部。上面三行判断错了还能回滚,最下面一行即使撤销也无法修复。先把可回滚的响应用尽,再动最后一行。

这并不是拍脑袋想出来的做法。在 OWASP 整理的自动化威胁清单中,批量创建账号被登记为 OAT-019,而推荐的应对措施之一是limiting the functionality and/or capacity available to all newly created accounts。这不是说挑出坏的那一部分去限制,而是把所有新建账号的初始权限都调低。

5.1 把打分与决策分开

如果信号评估和决策揉成一团,每改一次标准就得发布一次,也无法拿新标准去回放过去的请求。

// 概念示例 - 仅用于展示结构,未实际运行验证。
// 权重与阈值因服务而异,不要照搬。

score = 0
if (ua_absent)            score += 1   // 弱信号,单独不做任何决定
if (source_burst)         score += 2   // 同一来源短时间内反复
if (schedule_like_timing) score += 2   // 叠加多天才能看见的信号
if (declared_vs_observed) score += 3   // 声称是浏览器却没有附属请求

decision =
    score >= 6 ? "queue_for_human_review"   // 交给人看
  : score >= 3 ? "limit_new_account"        // 可回滚的限制
  :              "log_only"                 // 只做记录

// 拦截不在这张表里。自动做出的最高级别,到交给人为止。

最后一条注释就是要点。把自动能下的最强决定设为「交给人」,判别器的误判就不会直接落到用户身上。

6. 为了以后能判别,现在该留下什么

机器人判别多半发生在事后。先是某个奇怪的账号引起注意,然后才去翻日志。那一刻能不能给出答案,取决于今天留下了什么。这是结构问题而不是数量问题。

  • 时间精确到毫秒。要看时间分布,秒级不够用。同时确认各服务器的时钟是否对齐
  • 连接请求与事件的关联键。如果无法知道账号创建来自哪次请求,就无法还原前后脉络。仅这一个键就能把调查时间从几天缩到几分钟
  • 规则标识、分数与决策放在一起。只留结果就无法再回头改规则。哪条规则给了多少分、做了什么决定,必须在同一行里
  • 观测模式下的虚拟判定。不真拦截,只标注「本来会拦截」的记录
  • 请求头记形态而不是记值。有哪些头字段、集合是什么形状,才是判别要用的信息。把整个值都留下只会平白增加个人信息

不该留的东西同样明确。输入内容本身不要留。需要的是间隔的分布,而不是敲了什么。决定日志级别时使用的标准在这里同样适用。先确定要回答的问题,再只留下回答它所需的东西。

7. 个人信息视角 - 判别用的值也是个人信息

不能因为是为了识别机器人而收集的,就跳出个人信息的规制。恰恰相反,这一侧更敏感,因为提高判别力的方向和提高识别力的方向事实上是同一个。

欧盟通用数据保护条例在鉴于条款第 30 项直接谈到这一点:自然人可能与其设备、工具和协议所提供的在线标识符相关联,其中包括internet protocol addresses, cookie identifiers之类,而这些痕迹与其他信息结合起来可能被用于构建画像并识别个人。

韩国个人信息保护法的方向也一致。第 3 条要求明确处理目的,并在该目的所需范围内只收集最少的个人信息,禁止超出目的的使用。第 21 条要求在达成目的、信息已不再需要时不得延迟地予以销毁,并采取无法复原或再生的措施。

7.1 落到设计上是四件事

  • 写清目的。写得窄一些,比如「防止自动注册」,并且不要把这些值挪去做个性化或营销
  • 缩短保存期限。要看时间分布,几周通常就够了。把原始值留上一年,多半没有理由
  • 降低精度。用区间代替精确毫秒、用网段代替精确地址,「是否在重复」依然看得出来
  • 写进隐私政策。如果写不出收集什么、为什么、留多久,那就是该重新审视这项收集的信号

不断提高指纹精度的方向会与这套规制正面相撞。观察整个会话行为的做法之所以引发争议,症结也在这里。

一条实务判据 - 每次新增一个信号,先回答「如果这个值泄露,用户会遭受什么损害」。如果答案是「设备和习惯会被暴露」,那么这个信号相对于换来的判别力就太贵了。

8. 比修信号更该先修的是流程

到此为止讲的是判别,这一节讲的是如何减少判别的必要。而后者通常便宜得多。

打开那些大量出现自动注册的服务会发现,账号创建常常被放在用户明确操作之前。应用启动时、首屏打开时先创建匿名账号,之后再补填信息。方便,但有代价。凡是打开链接的东西都会成为注册用户,生成预览的一方和建立索引的一方都算在内。这不是攻击,只是网络世界的日常。

修复的方向不是挂上判别器,而是调换顺序。把账号创建移到同意并开始这一明确操作之后,自动访问就不会创建账号。需要判别的对象消失了,信号也就不必那么准确。这在成为安全措施之前,首先是个度量问题。注册数虚高的话,转化率和活跃用户数都会是错的。改完之后注册数下降不是损失,而是数字变诚实了。

一般化来说就是:不要把改变状态的操作,放在自动请求可能顺手穿过的位置上。只要浏览计数器就上涨的页面、只要预览请求就发出通知的流程、只要打开链接就消耗邀请名额的设计,都带着同一个毛病。

2026 年 8 月,韩国开发者社区上出现过一篇追踪这个问题三周的记录。一位匿名社区的运营者先后加了拦截爬虫名称的规则和拒绝空 User-Agent 的规则,却遇到真实应用用户一并被拦的副作用,最后靠把流程改成在按下同意按钮之前不建立连接、不创建账号解决了问题。这篇记录的价值在于,结论是流程变更而不是一份更长的信号清单。

10. 常见问题

空的 User-Agent 可以直接当作机器人吗

不可以。HTTP 规范只是把这个头字段列为建议,并且把用户修改取值也写成了预设行为。空值不是「这是机器人」,而是「这里没有浏览器式的自我介绍」的观察,只有与其他维度重叠时才有意义。

那么 User-Agent 是不是完全没用

只是说不能作为放行或拒绝访问的唯一依据。用于统计和审计足够,识别主动表明身份的爬虫也用得上。不过确认要由反向解析或与公开地址段比对来完成。

几个信号叠加之后就可以拦截了吗

这不是数个数的问题。只做记录、暂缓新账号功能这类可回滚的响应,信号弱也可以施加。像拒绝注册这种会让用户当场离开的响应,只在多个维度指向同一方向时才使用。

为识别机器人而收集的地址和请求头也算个人信息吗

按个人信息处理才稳妥。欧盟规则明确指出协议地址与 Cookie 标识符可能被用于识别个人,韩国法律也要求只收集最少信息、不再需要时不得延迟销毁。把目的写窄、缩短保存期限、降低精度。

减少自动注册最便宜的办法是什么

在挂上判别器之前先移动账号被创建的位置。把创建推到用户明确操作之后,自动访问就不会创建账号,需要判别的对象本身也随之减少。

11. 结论 - 今天要定的三件事

第一,把现有的拦截规则用观测模式只跑一天。不要真拦,只收集本来会命中的清单并逐条看。如果那份清单里出现我们自己的应用用户或企业客户,说明这条规则早就在切人了。

第二,在放行与拦截之间造出一个中间级。把新账号的初始权限调低最省事。有了这一级,判别器再粗糙也伤不到用户。

第三,在代码里确认账号是在哪个位置被创建的。如果它排在用户明确操作之前,就先把它挪走。这比加一个判别器通常用更少的代码消掉更多问题。

最常见的错觉是:只要找到准确的信号,问题就结束了。客户端发来的值无法验证,行为和时间在人这一侧也有大量例外。完美的信号不会到来。但允许出错的结构今天就能造出来。这才是能长久撑住的顺序。
