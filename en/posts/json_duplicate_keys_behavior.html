Introduction - a document the grammar allows but whose value is not settled

A document such as {"a":1,"a":2} does not violate the JSON grammar. The object grammar in RFC 8259 only says that members are joined by commas and sets no condition that forbids repeated names. Uniqueness survives only as the recommendation sentence "SHOULD be unique", not as a grammar rule. Two programs that receive the same bytes can therefore read different values.

The difference stays invisible in a program that uses one parser: if it parses once and keeps using that result, the answer is consistent whether it is the last value or the first. The trouble starts in designs that read the same document twice. A front layer that inspects a request body while a back layer parses the same body again is the typical case. Section 13 of the article on 64-bit ID precision covered duplicate keys as a single item inside the number-precision topic; the sections below widen that one item into a per-parser comparison, a detector and a reproduction.

The questions covered are the following.

  • What do the specification documents say about duplicate keys?
  • What value do node, Python and PowerShell 5.1 each produce from the same document?
  • Are key order, keys that differ only in case, and escaped keys treated as duplicates?
  • Does a server-side parser give the same value as a local call?
  • How is a duplicate-key detector written?
  • When the layer that validates and the layer that consumes see different values, what actually gets through, and how is it stopped?

What the specifications and official documents say

The sentences on duplicate keys in RFC 8259 section 4, in the ECMAScript specification of JSON.parse, in the Python json module documentation, and in the Microsoft Learn page for ConvertFrom-Json (5.1) follow. The original English is kept as is.

SourceOriginal wordingMeaning
RFC 8259 4The names within an object SHOULD be unique.Uniqueness of names is a recommendation
RFC 8259 4When the names within an object are not unique, the behavior of software that receives such an object is unpredictable. Many implementations report the last name/value pair only. Other implementations report an error or fail to parse the object, and some implementations report all of the name/value pairs, including duplicates.Behavior is unpredictable; implementations report only the last pair, raise an error, or report all pairs
ECMAScript JSON.parseIn the case where there are duplicate name Strings within an object, lexically preceding values for the same key shall be overwritten.The specification itself says earlier values are overwritten
Python json docsBy default, this module does not raise an exception; instead, it ignores all but the last name-value pair for a given nameBy default only the last pair is used with no exception; object_pairs_hook can change this
Microsoft Learn ConvertFrom-Json (5.1)if the JSON string contains duplicate keys, only the last key is used by this cmdletOnly the last key is used when duplicates exist

Four points follow from the table.

  • The RFC only recommends uniqueness and, after listing the three behaviors (last value, error, report all), calls the outcome unpredictable.
  • The ECMAScript specification directly states that earlier values are overwritten in JSON.parse. For JavaScript, last-value-wins is a specification sentence, not a custom.
  • The Python and PowerShell documents also state that the last value is used. For these it is the documented behavior of that implementation.
  • The error and report-all behaviors that the RFC leaves open can be implemented through extension points such as the object_pairs_hook of Python.

  • For a document with the same name twice, all three runtimes kept only the last value, which matches the direction of the quoted specification and documents.
  • When the value is an object, it is replaced as a whole rather than merged; the x of the first object is gone from the result.
  • Objects inside an array were judged one by one: only the first object ended with k equal to 2, and the second kept k equal to 3.
  • object_pairs_hook=list in Python returned [('a', 1), ('a', 2)]. The parser did read both pairs; keeping only one happens in the later step that builds a dict.

The value comes from the last, the position from the first

For the second row of the table, {"a":1,"b":2,"a":3}, all three runtimes produced {"a":3,"b":2}. The value of a came from the last occurrence (3), yet the key stayed ahead of b, that is, in the position of its first occurrence. Code that reads key order to judge the first field, or processes keys in order, meets this combination when it receives a duplicate-key document: the value of the later one with the order of the earlier one.

In JavaScript a reviver function lets code look into the parsing. In the last line of the node output above, the reviver received only two calls: a=2 and the root object. The value 1 was never passed to the reviver.

  • The object returned by JSON.parse has a single key (keys=1), so nothing in it shows that a duplicate existed.
  • The reviver did not receive the overwritten value either; in this run the reviver gave no way to learn that a duplicate existed.
  • Python has object_pairs_hook, which hands over the list of pairs the parser read. The detection script in section 7 builds on that difference.

Keys that are the same without looking the same

The fourth row of the table is a and A. node and Python treated them as separate keys and kept 2 keys. PowerShell 5.1 failed the conversion itself with an InvalidOperationException. The same document is accepted by one layer and rejected by another. On this PC's Korean locale the exception message contained a phrase meaning 「duplicated keys 'a' and 'A'」 (translated here; the original is Korean). The message itself names duplicate keys as the reason for the rejection, so PowerShell 5.1 appears to have judged keys that differ only in case to be duplicates (the wording is locale-dependent).

The fifth row writes a key with an escape. Inside the document, "\u0061" decodes to the same name as a. All three runtimes treated it as a duplicate and kept only the last value, 2. The following script shows what this means for validation built on text search: a document whose second key is written with escapes so that the key role is visible only once.

import json
                    text = '{"role":"user","\\u0072ole":"admin"}'
                    print("raw text    : " + text)
                    print("text search : " + str(text.count('"role"')) + ' occurrence of "role"')
                    pairs = json.loads(text, object_pairs_hook=list)
                    print("parsed pairs: " + str(pairs))
                    print("parsed dict : " + str(json.loads(text)))
raw text    : {"role":"user","\u0072ole":"admin"}
                    text search : 1 occurrence of "role"
                    parsed pairs: [('role', 'user'), ('role', 'admin')]
                    parsed dict : {'role': 'admin'}
  • The raw text contained only one match for "role", yet the parser read two role pairs and the dict kept the last value, admin.
  • A check that counts keys by text search or regular expression misses a duplicate written with an escape. Validation has to work on the keys after the parser has decoded them.
  • Keys that differ only in case were handled differently by each runtime. In a structure with more than one parser, that difference is another path by which the same document is read differently per layer.

Does a server-side parser behave the same

A duplicate-key detector

Since the Python documentation describes object_pairs_hook as an extension point that receives the list of pairs and uses the return value instead of a dict, checking whether a key already exists while pairs are put into a dict makes a detector. The script below reads a file with one JSON document per line and judges each line.

import json, sys
                    
                    def reject_duplicates(pairs):
                        obj = {}
                        for key, value in pairs:
                            if key in obj:
                                raise ValueError("duplicate key " + repr(key) + ": " + repr(obj[key]) + " then " + repr(value))
                            obj[key] = value
                        return obj
                    
                    for lineno, line in enumerate(open(sys.argv[1], encoding="utf-8"), 1):
                        text = line.rstrip("\n")
                        try:
                            json.loads(text, object_pairs_hook=reject_duplicates)
                            print(str(lineno) + ": OK    " + text)
                        except ValueError as err:
                            print(str(lineno) + ": FAIL  " + text)
                            print("    " + str(err))

The input file has seven lines, and the last line is a deliberately broken document. The result of running it is below.

1: OK    {"a":1,"b":2}
                    2: FAIL  {"a":1,"a":2}
                        duplicate key 'a': 1 then 2
                    3: OK    {"a":1,"A":2}
                    4: FAIL  {"a":1,"\u0061":2}
                        duplicate key 'a': 1 then 2
                    5: FAIL  {"l":[{"k":1,"k":2},{"k":3}]}
                        duplicate key 'k': 1 then 2
                    6: OK    {"a":1,"b":{"a":2}}
                    7: FAIL  {"a":1,

  • Line 2 (a twice) and line 5 (k twice inside an object in an array) were caught. Because the hook is called for every object, a duplicate inside a nested object is caught too.
  • The escaped a on line 4 was caught as well, because the detector looks at keys after decoding, unlike the text search of the previous section.
  • Line 3 (a and A) and line 6 (an outer a and an inner a) passed. This detector counts only exactly equal names inside the same object as duplicates.
  • Line 7 failed as a syntax error rather than a duplicate, under the same except ValueError with a different message. To tell syntax errors from duplicates, the exception types have to be caught separately.

Reproducing two layers that see different values

There are two components. The front gateway (Python) parses the request body and rejects it with 403 if role is admin, and forwards the original bytes of a passing request unchanged to the back end (node, the echo server from before). The back end returns what JSON.parse read, so the response is exactly the value the back end saw. The gateway parser implements a first-value-wins policy ("do not overwrite a key that already exists") with object_pairs_hook. All three stock parsers on this PC are last-value-wins, so two layers with different policies had to be built this way. This policy difference is an assumption chosen for the demonstration; it does not show which real product uses first-value-wins.

import json, os, sys, urllib.request
                    from http.server import BaseHTTPRequestHandler, HTTPServer
                    
                    MODE = sys.argv[1]
                    PORT = int(sys.argv[2])
                    BACKEND = "http://127.0.0.1:18082/"
                    
                    def first_wins(pairs):
                        obj = {}
                        for key, value in pairs:
                            obj.setdefault(key, value)
                        return obj
                    
                    def reject_duplicates(pairs):
                        obj = {}
                        for key, value in pairs:
                            if key in obj:
                                raise ValueError("duplicate key " + repr(key))
                            obj[key] = value
                        return obj
                    
                    class H(BaseHTTPRequestHandler):
                        def reply(self, code, text):
                            data = text.encode()
                            self.send_response(code)
                            self.send_header("Content-Length", str(len(data)))
                            self.end_headers()
                            self.wfile.write(data)
                    
                        def do_POST(self):
                            body = self.rfile.read(int(self.headers["Content-Length"]))
                            hook = reject_duplicates if MODE == "reject" else first_wins
                            try:
                                doc = json.loads(body, object_pairs_hook=hook)
                            except ValueError as err:
                                return self.reply(400, "gateway: 400 " + str(err))
                            if doc.get("role") == "admin":
                                return self.reply(403, "gateway: 403 role admin is not allowed")
                            forward = json.dumps(doc).encode() if MODE == "canonical" else body
                            req = urllib.request.Request(BACKEND, data=forward, method="POST")
                            with urllib.request.urlopen(req) as r:
                                self.reply(200, "gateway: passed; backend saw " + r.read().decode())
                    
                        def log_message(self, *a):
                            pass
                    
                    HTTPServer(("127.0.0.1", PORT), H).serve_forever()

Two ways to stop it - reject, or pass on what was validated

The same gateway code was run in two modes. In reject mode a key that already exists makes parsing fail and the request is returned with 400. In canonical mode the gateway serializes the object it parsed once more and sends that to the back end. The request has the same body as request 5 of the previous section, and the results are outputs 6 and 7 of run.sh.

MethodGateway behaviorResult for the body of request 5
Reject duplicates (reject)Parsing fails on a duplicate key; the back end is not calledgateway: 400 duplicate key 'role'
Serialize the validated object and forward it (canonical)Forward JSON rebuilt from the object the gateway parsed, instead of the original bytesgateway: passed; backend saw {"user":"alice","role":"user"}
No change (raw)Forward the original bytes unchangedgateway: passed; backend saw {"user":"alice","role":"admin"}
  • reject stopped the request with 400 before it reached the back end. If a legitimate client sends duplicate keys on purpose, its request gets the 400 as well.
  • With canonical the back end received user, the value the gateway had validated. This enforces the gateway policy of choosing the first value on the back end, so if the value the client meant was the last one, a different value gets used.
  • What the two methods share is that the validated object and the used object are made to carry the same value: one refuses the document, the other interprets it once and passes on the result.
  • The example of the previous section shows a structure in which the validating layer and the consuming layer each parse the original bytes again. Interpreting input that crosses a trust boundary only once connects to the principle in the article on the client trust boundary.

The items to check in practice are the following.

  • Is there a layer that parses the same request body more than once? If so, are the kind and the settings of the parser the same?
  • Does validation rely on keys decoded by the parser, or on a search of the raw text?
  • Has it been decided whether a duplicate key is rejected, or normalized to one policy and passed on?
  • Is it checked that the value validated and the bytes the back end receives agree? In the output above, the body the back end received in canonical mode was not the original bytes but JSON the gateway had rebuilt.

What Could Not Be Verified

  • The behavior of runtimes other than node, Python and PowerShell 5.1 (Go, Java, Ruby, PHP, jq and others). Real examples of the "implementations that report an error" and "implementations that report all pairs" of the RFC could not be run, apart from object_pairs_hook=list in Python.
  • PowerShell 7 and System.Text.Json of .NET. This PC has no pwsh, and that class was not used in 5.1.
  • Why keys that differ only in case become an error in PowerShell 5.1. The document says duplicate keys are prohibited in PSObject and Hashtable types, and the exception message on this PC's Korean locale contains a phrase meaning 「duplicated keys 'a' and 'A'」, which names the duplicate-key rule directly. What was not checked is the message wording in other locales and the .NET code path that applies the rule.
  • How to detect duplicate keys in node. In this run neither the JSON.parse result nor the reviver revealed the duplicate, and other methods were not tried.
  • The first-value-wins policy of the gateway was implemented by hand for the demonstration. Whether any real product, library or proxy chooses the first value was not verified.
  • Request-body parsers of web frameworks other than the standard http.server of Python and the http module of node, and the effect of Content-Type and character-encoding headers on the result.
  • How stores such as PostgreSQL jsonb or MongoDB handle duplicate keys at input time. Not run on this PC.
  • Behavior and performance with very large documents or streaming parsers, and duplicate-key handling in extended syntaxes such as JSON5.
