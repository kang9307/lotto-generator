跑两次也安全的脚本 - 幂等性设计与真正会出问题的六种模式

不是概念而是复现 - 用执行输出和三次哈希比对验证的安全写法

2026年7月29日 开发/基础设施

引言: 回答不了「能再跑一次吗」的脚本

部署脚本跑到一半死了。翻日志发现八步走到了第五步。原因很快就查清楚了，剩下的问题只有一个。「这个直接再跑一次行吗？」

答不上这句话的那一刻，当晚就会变长。因为你得从头把脚本读一遍，一行一行地在脑子里推演这行跑第二次会怎样。而结局往往是没推完就变成「先手工从第五步开始吧」。手工做的那部分不会留在记录里，下一个人便不知道服务器状态为什么和脚本对不上。

幂等性就是让你能在半秒内回答「可以」的那种性质。它不是背定义的问题，而是弄清自己脚本的每一行在第二次执行时到底做了什么的问题。所以本文不从定义开始，而从真的跑两次把它弄坏之后的输出开始。

顺序是这样：先逐个复现真正会出问题的六种模式，并给每个配上安全写法；接着展示标记块这一通用解法，以及用哈希证明重跑结果相同的流程；最后整理部分失败后的续跑设计与需要加锁的条件。

先统一一个术语。实务中被笼统称作「幂等」的东西其实分三个层级。先把这个区分做好，后面的讨论会简单得多。

层级保证什么不保证什么代表手段
① 重跑安全跑两次也不会崩（不会因报错中断）结果变得相同mkdir -p、rm -f
② 结果收敛不论跑几次都到达相同的最终状态清除人为造成的漂移先确认存在再变更、标记块
③ 自我修复状态跑偏时拉回目标状态没有声明过的项目整块替换、整文件生成

大多数事故发生在只做到①却以为做到了②的时候，也就是改成 mkdir -p 之后就说「已经改成幂等的了」。下面的复现会让你看清这道缝隙具体在哪里。

执行前的安全提示。 本文的所有复现都只在新建的临时目录内进行。正文中出现 rm -rf 的地方，用途仅限于删除那个临时目录或其中的子路径。请不要在真实服务器上照着做。 尤其是 rm -rf "$DIR" 这种形式，一旦 $DIR 为空就会变成 rm -rf ""，可能扫到意料之外的地方，所以在用变量做删除时，务必先加上 [ -n "$DIR" ] && [ "$DIR" != "/" ] 这类防护。放进 cron 或 CI 之前，先用 --check 之类的试运行把目标路径用眼睛确认一遍会更安全。

1. 复现环境与验证方式

下面的输出全部是实际跑出来的结果原样贴上。复现环境如下。

===== T0 ENVIRONMENT =====
MINGW64_NT-10.0-19045 3.5.7-882031da.x86_64
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)
sed (GNU sed) 4.9
grep (GNU grep) 3.0
sha256sum (GNU coreutils) 8.32

这是 Windows 10 上的 MSYS2/Git Bash 环境。因为是 GNU 工具系列，行为与 Linux 一致，但有三点是这个环境特有的限制，先说明清楚。这是读者判断结果时需要的信息。

  • 符号链接在默认设置下会被当成文件复制处理。为了创建真正的链接，是在设置了 MSYS=winsymlinks:sys 的状态下执行的。
  • POSIX 权限位在 NTFS 上无法原样反映。实测执行 chmod 600 之后模式仍显示为 644。因此与权限相关的幂等性，本文不以执行结果来主张，相关条目只作为规则留在清单里。
  • 没有 crontab 和 flock 这两个二进制。 cron 部分是把 crontab -l 会输出的文本用文件模拟出来，只验证行操作逻辑；锁则用 mkdir 的原子性代替 flock 做了实证。

验证方式混用了三种：退出码（命令是否成功）、文件内容（留下了什么）、SHA-256 哈希（重复执行结果是否相同）。其中哈希是区分「看着一样」和「就是一样」的唯一工具，所以会反复用到。

2. 模式① append 在悄悄累积

最常见，也最晚被发现，因为它不报错。把往 .bashrc 里加一行 PATH 的脚本跑两次看看。

-- run 1 --
export PATH=/opt/tool/bin:$PATH
-- run 2 (same command again) --
export PATH=/opt/tool/bin:$PATH
export PATH=/opt/tool/bin:$PATH
lines: 2

两次的退出码都是 0，没有任何人告诉你失败了。如果这行是 PATH，顶多是路径重复；可一旦挂上每次都往同一个文件里加一点的 cron，几个月后配置文件就变成几千行。真实事故大多是这种形态。

2.1 安全写法 - 先确认存在再写入

LINE='export PATH=/opt/tool/bin:$PATH'
grep -qxF -- "$LINE" safe.conf || printf '%s\n' "$LINE" >> safe.conf

下面是跑三次的结果，行数与哈希都固定不变。

run1 -> 1 line(s) | sha=0a0746b7d8c9bd1f
run2 -> 1 line(s) | sha=0a0746b7d8c9bd1f
run3 -> 1 line(s) | sha=0a0746b7d8c9bd1f

2.2 陷阱 - 一个 grep 选项就能让结果反转

这里 -qxF 中的 x 和 F 不是装饰。把它们去掉，会分别引发方向完全相反的两种事故。

陷阱 A - 把注释误判成「已配置」。 目标文件里那一行是被注释掉的状态，这很常见，往往是有人临时关掉后忘了。

file: #export PATH=/opt/tool/bin:$PATH
grep -qF  -> found (skips append) ... setting is never applied
grep -qxF -> not found (correct: a comment is not an active setting)

只用部分匹配的 -F，注释行也会被匹上。脚本每次都说「已经设好了」然后安静跳过，配置永远得不到应用。因为没有报错，能拖上好几个月。-x（整行匹配）挡住的正是这个。

陷阱 B - 正则元字符导致重复堆积。 这是相反的方向。要写入的行里如果含有 [、]、.、* 这类字符，grep -q 会把它们当作正则来读。

file: PATH=/opt/tool[1]/bin
grep -q   -> NOT found ([1] read as a character class) -> duplicate append
grep -qxF -> found (correct)
after 3 runs: grep -q => 4 lines | grep -qxF => 1 lines

[1] 是表示「字符 1 之一」的字符类，与字面量 [1] 匹配不上。于是每次都判为「没有」，跑三次变成四行。-F（固定字符串）挡住的正是这个。

2.3 更安静的陷阱 - grep 的退出码 2

这一条得翻文档才知道。grep 会返回三种退出码，下面是实测值。

match      -> 0
no match   -> 1
read error -> 2  (|| append treats this like 'no match')

grep -qxF ... || append 这种形式无法区分 1（不匹配）与 2（出错）。当文件没有读权限或路径写错时，脚本会判断为「没有」然后继续追加。要做准确，就得把退出码分开接住。

grep -qxF -- "$LINE" "$F"; rc=$?
case $rc in
  0) : ;;                                   # 已存在
  1) printf '%s\n' "$LINE" >> "$F" ;;       # 不存在 -> 追加
  *) echo "grep failed(rc=$rc): $F" >&2; exit 1 ;;   # 出错 -> 中止
esac

3. 模式② mkdir 与 rm 的退出码把脚本拦腰截断

这是流传最广的一条，所以简单带过，把篇幅留给较少被提到的副作用。

-- mkdir d1 (run 1) --
exit=0
-- mkdir d1 (run 2) --
mkdir: cannot create directory 'd1': File exists
exit=1
-- mkdir -p d1 (run 3) --
exit=0

-- rm f1 (run 1) --
exit=0
-- rm f1 (run 2) --
rm: cannot remove 'f1': No such file or directory
exit=1
-- rm -f f1 (run 3) --
exit=0

这个行为由 POSIX 规范规定。对 mkdir -p 写的是「以已存在目录为名的每个 dir 操作数都会被无错误地忽略」，对 rm -f 写的是「对于不存在的操作数，不写诊断信息，也不改变退出状态」。选项做的事情精确地就只有这些。

3.1 真正的伤害出现在遇上 set -e 时

退出码是 1 本身不算大事。问题在于，在挂了 set -e 的脚本里，后面的步骤会整段消失。下面是把一个三步脚本跑两次的结果。

-- seq.sh run 1 --
  [step 2] place config files
  [step 3] restart service
exit=0
-- seq.sh run 2 --
mkdir: cannot create directory '.../s/stage': File exists
exit=1  <- steps 2 and 3 never ran

重跑时卡在创建目录的第一步，配置投放和服务重启都没有发生。而脚本只会说「失败」，不会告诉你走到了哪里。运维只看日志最后一行就判断成「目录问题」，至于服务还在用旧配置跑这件事，往往是后来才发现的。

3.2 选项替不了的事

  • mkdir -p 只忽略存在与否。对已存在目录的属主与权限，它不会调整为目标值。-m 只在新建时生效，所以要保证权限就得用单独的 chmod、chown 行钉死。（如前所述，本环境无法验证权限位，因此不以执行输出呈现。）
  • rm -f 只对不存在的文件睁一只眼。要删的对象若是目录，照样失败。
  • 两者都不管内容。目录存在，和目录里面处于目标状态，是两回事。

4. 模式③ ln -s 第二次会钻进链接内部

这一条在本文里最值得复现，因为它不失败却留下荒唐的结果。就是无停机部署里把 current 符号链接切到新发布版的那段代码。

-- ln -s rel_a current (run 1) --
exit=0 | readlink=rel_a
-- ln -s rel_b current (run 2) --
exit=0

第二次是退出码 0，看起来像成功。那就确认一下实际生成了什么。

## ln -sf on a symlink that points to a directory
ln -sf exit=0
readlink current = rel_a   <- still points at rel_a
ls current/:
FROM_A
rel_b
what was actually created: lrwxrwxrwx 1 user  users 5 Jul 29 05:13 rel_a/rel_b -> rel_b
  -> it did not repoint the link; it created a new link INSIDE the target directory

关键是最后一行。当 current 是指向目录的符号链接时，ln -sf rel_b current 会把 current 当目录跟进去，在里面建一个叫 rel_b 的新链接。readlink current 依旧是 rel_a。

想想这在运维里意味着什么。部署脚本返回成功，监控也是绿灯，而服务仍然跑在旧版本上。而且旧发布目录里还会一个个堆起来路不明的链接，每部署一次堆一个。

4.1 安全写法 - ln -sfn

GNU coreutils 的 ln 对 -n 的说明是「当链接名是指向目录的符号链接时，把它当作普通文件处理」，意思就是别跟进去。下面是跑三次的结果。

run1 -> readlink=rel_b | rel_a contains: FROM_A
run2 -> readlink=rel_b | rel_a contains: FROM_A
run3 -> readlink=rel_b | rel_a contains: FROM_A

三次都固定为 rel_b，rel_a 里除了 FROM_A 之外没有多出任何东西。实务规则可以概括成一句：切换指向目录的符号链接时，永远带上 -n。 用 -T（--no-target-directory）还能强制得更严格。

更安全的做法。 要让符号链接的切换真正原子化，需要先用临时名字建好链接，再用 mv -T 换上去的两步。ln -sfn 内部存在先删再建的瞬间，那一刹那可能出现 current 不存在的时点。对流量大的路径来说，这个差别是有意义的。

5. 模式④ sed -i 会一边返回成功一边撒谎

sed -i 的重跑安全性按模式分成三种情形，逐个复现如下。

5.1 情形 A - 结果与模式不再重叠就是安全的

sed -i 's/^timeout = 30$/timeout = 60/' a.conf

run1 sha=ca1a53713b3fbd1d | timeout = 60 retries = 3
run2 sha=ca1a53713b3fbd1d | timeout = 60 retries = 3
run3 sha=ca1a53713b3fbd1d | timeout = 60 retries = 3

替换结果 timeout = 60 与模式 ^timeout = 30$ 不重叠，所以从第二次起没有匹配，文件不再变化，三次哈希相同。这属于运气好才幂等的情况。

5.2 情形 B - 结果再次满足模式就会无限累积

sed -i 's#PATH=#PATH=/opt/bin:#' b.conf

run1: PATH=/opt/bin:/usr/bin
run2: PATH=/opt/bin:/opt/bin:/usr/bin
run3: PATH=/opt/bin:/opt/bin:/opt/bin:/usr/bin

替换结果里仍然留着 PATH=，下一次执行又会命中，每跑一次路径就多一段。这比前面的 append 累积更难察觉，因为行数不增加，得把文件打开、把那一行读到底才会发现。

5.3 情形 C - 什么都没做却返回成功

sed -i 's/^debug = true$/debug = false/' c.conf
exit=0 | content=debug = false  <- exit code is not evidence that it applied

文件里本来就是 debug = false，模式一处都没匹配上，可 sed 还是返回退出码 0。这不是缺陷而是设计：sed 不会用退出码告诉你「替换了几处」。

由此得出的实务规则很重要：sed -i 的退出码不是「已应用」的证据。 要确认配置真的生效，必须在替换之后重新读回结果再检查。安静的失败之所以最可怕，是因为文件路径写错、锚点对不上，返回的同样是 0。

5.4 安全写法 - 先检查目标状态并做事后验证

TARGET='PATH=/opt/bin:/usr/bin'
grep -qxF "$TARGET" d.conf || sed -i 's#^PATH=/usr/bin$#PATH=/opt/bin:/usr/bin#' d.conf
grep -qxF "$TARGET" d.conf || { echo "apply failed"; exit 1; }

run1: PATH=/opt/bin:/usr/bin
run2: PATH=/opt/bin:/usr/bin
run3: PATH=/opt/bin:/usr/bin
post-check: target state reached (0)

这里同时做了三件事：①先检查目标状态，已到达就不碰；②用 ^...$ 把锚点夹住，让结果无法再次满足模式；③替换后重新读回，确认真的到达。这三样齐备，sed -i 也能安全地用。

6. 模式⑤ crontab 登记每执行一次就翻一番

有个流传很广的惯用写法：(crontab -l; echo "$JOB") | crontab -。下面是跑三次的结果。

run1 -> sync.sh lines: 1
run2 -> sync.sh lines: 2
run3 -> sync.sh lines: 3
*/5 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1
*/5 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1
*/5 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1
  -> a job meant to run every 5 minutes now starts 3 times per tick

这个结果的危险等级和其他模式不是一个量级。前面那些是文件变脏的问题，而这个是同一个作业同时起来好几个的问题。如果是同步脚本，它们会互相碰同一批文件；如果是备份，会分掉带宽让两边都变慢；如果是数据库清理，会出现锁竞争。更麻烦的是，环境准备脚本跑了三次，负载正好变成三倍，原因还不容易定位。

6.1 安全写法 - 先删掉再写入

正确答案不是「已存在就跳过」，而是「把引用该脚本的行全部删掉，再重新写入」。原因马上说明。

{ crontab -l 2>/dev/null | grep -vF '/opt/app/bin/sync.sh'
  printf '%s\n' "$JOB"; } | crontab -

run1 -> lines: 1 | sha=7352c0d47610f2d1
run2 -> lines: 1 | sha=7352c0d47610f2d1
run3 -> lines: 1 | sha=7352c0d47610f2d1

三次都是一行，哈希相同。这比「已存在就跳过」更好的理由在于调度变更。 只检查存在性的做法，即使把 */5 改成 */10，也会以「已经有了」为由把旧行原封不动留着；删掉再写入的方式则不会。另外也一并确认了它不会碰到别的作业。

-- schedule change is absorbed too (*/5 -> */10), and other jobs survive --
0 3 * * * /opt/other/backup.sh
*/10 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1

backup.sh 那行原样保留，只有 sync.sh 那行更新成了新调度。这里的关键在于过滤字符串收得有多窄。用 sync.sh 这种常见名字去过滤，可能连别的团队的 /opt/legacy/sync.sh 一起删掉。写完整的绝对路径，或者改用下面的标记块方式，会更安全。

能不直接写 crontab 就不写，也是一个选项。 往 /etc/cron.d/ 里整个投放一个文件，这件事本身就是「整体替换」，重复从根源上不可能发生。写到临时文件再用 mv 换上去，还能顺带拿到原子性。不过各发行版对文件名规则（例如带点的名字会被忽略）和是否有用户字段的规定不同，请查阅对应发行版文档后再采用。

7. 模式⑥ 看着幂等其实不是的那些

如果说到这里都算「已知的陷阱」，那么这一节是大多数人误以为幂等的命令。

7.1 cp -r - 首次执行与重跑的结果结构不同

cp -r src dst   # 连续三次

run1: dst dst/a.txt
run2: dst dst/a.txt dst/src dst/src/a.txt
run3: dst dst/a.txt dst/src dst/src/a.txt
  -> run 1 produced dst/a.txt; from run 2 on, dst/src/a.txt appeared as well

原因是cp -r 的含义会随目标是否存在而改变。dst 不存在时，它把 dst 做成 src 的副本（dst/a.txt）；dst 存在时，它把 src 放进 dst 里面（dst/src/a.txt）。同一条命令，新机器和重新部署的机器结果不一样。「全新安装没问题，一更新就变怪」这种症状的常见元凶就是它。

安全写法是指定内容物而不是目录。

cp -r src/. dst2/   # 连续三次

run1: dst2 dst2/a.txt
run2: dst2 dst2/a.txt
run3: dst2 dst2/a.txt

7.2 mv - 第二次直接失败

run1 exit=0
mv: cannot stat 'mvsrc/data.bin': No such file or directory
run2 exit=1

mv 是本质上无法重跑的命令，因为源没了。要让它可重跑，就得像 [ -e "$SRC" ] && mv ... 那样把源的存在作为条件，或者干脆不用 mv，改成描述目标状态的方式（复制后验证，或以目的地为准做判断）。

7.3 sed 的「插入一行」 - a 命令等同于 append

sed -i '/^\[core\]$/a\    autocrlf = input' gitcfg.ini   # 连续三次

run1: [core]|    autocrlf = input|
run2: [core]|    autocrlf = input|    autocrlf = input|
run3: [core]|    autocrlf = input|    autocrlf = input|    autocrlf = input|

用了 sed 并不等于就是替换。a（append）命令如其名就是追加，性质与 >> 相同。安全写法是「有则替换，无则插入」的两路分支。

if grep -q '^[[:space:]]*autocrlf[[:space:]]*=' f.ini; then
  sed -i 's/^[[:space:]]*autocrlf[[:space:]]*=.*/    autocrlf = input/' f.ini
else
  sed -i '/^\[core\]$/a\    autocrlf = input' f.ini
fi

run1 sha=94ff19468316c369 | [core]|    autocrlf = input|
run2 sha=94ff19468316c369 | [core]|    autocrlf = input|
run3 sha=94ff19468316c369 | [core]|    autocrlf = input|

7.4 时间戳与随机数 - 让幂等验证本身变得不可能

文件里一旦混进 date 的输出或 $RANDOM，那个文件每跑一次哈希都不一样。这与逻辑是否幂等无关，是验证手段本身丢失了。规则很简单：把状态文件和审计日志分开。 何时做了什么另外记日志，脚本管理的配置文件里只写确定性的内容。

7.5 小结 - 用重跑安全的三个层级重新看

  • mkdir -p、rm -f 只给到①重跑安全。
  • grep -qxF 之后 append、ln -sfn 能到达②结果收敛。
  • 标记块替换与整文件生成能走到③自我修复，人把块内改了也会被拉回来。
  • cp -r、mv、sed ... a\ 哪一层都不属于，不包一层就是事故本身。

8. 标记块 - 跑三次哈希也相同的原因

到目前为止的防御手段都是按行的。要管理的行超过五条，这种方式会迅速变脏。这时候用的就是标记块。Ansible 的 blockinfile 模块默认使用 # BEGIN ANSIBLE MANAGED BLOCK 与 # END ANSIBLE MANAGED BLOCK，正是这套做法。

思路很简单：用标记圈出「我管理的区间」，然后把中间整段换掉。 这样就不需要逐行确认存在与否了。

apply_block(){
  local file="$1" tag="$2" body="$3"
  local begin="# BEGIN ${tag}" end="# END ${tag}"
  [ -e "$file" ] || : > "$file"
  if grep -qxF "$begin" "$file"; then
    awk -v b="$begin" -v e="$end" -v body="$body" '
      $0==b { print b; printf "%s", body; skip=1; next }
      $0==e { print e; skip=0; next }
      skip==1 { next }
      { print }' "$file" > "$file.new" && mv "$file.new" "$file"
  else
    { printf '%s\n' "$begin"; printf '%s' "$body"; printf '%s\n' "$end"; } >> "$file"
  fi
}

把这个函数对一个已经含有三行人工维护内容的文件应用了三次。

run1 sha256=5d22eee7c5ef0991451ca494fdff31a15f39c10ab6a1626136c7d990f0beb8b6
run2 sha256=5d22eee7c5ef0991451ca494fdff31a15f39c10ab6a1626136c7d990f0beb8b6
run3 sha256=5d22eee7c5ef0991451ca494fdff31a15f39c10ab6a1626136c7d990f0beb8b6
-- resulting file --
# hand-maintained section
Port 22
PermitRootLogin no
# BEGIN braindetox-keepalive
ClientAliveInterval 60
ClientAliveCountMax 3
# END braindetox-keepalive
OK: the hand-maintained 3 lines are untouched

三次执行的哈希完全相同，标记之外的既有配置也没有受损。这就是②结果收敛。

8.1 值变了只会更新块内

## ClientAliveInterval 60 -> 30, three more runs
run4 sha256=1a402ffc0e2c088220b5e90471c69c330f6e4925ab579c3f0db1dc17271f3b18
run5 sha256=1a402ffc0e2c088220b5e90471c69c330f6e4925ab579c3f0db1dc17271f3b18
run6 sha256=1a402ffc0e2c088220b5e90471c69c330f6e4925ab579c3f0db1dc17271f3b18
total lines: 7 (no accumulation)

它会以新值重新固定到一个新哈希上，行数保持 7，块不会堆积。

8.2 append 方式永远做不到的事 - 删除条目

这里才是标记块真正的价值。把管理条目从两行减到一行看看。

# BEGIN braindetox-keepalive
ClientAliveInterval 30
# END braindetox-keepalive
  -> append-based approaches cannot do this: a removed entry would linger

ClientAliveCountMax 消失了。用「存在就跳过」的方式，这件事根本做不到。 你在脚本里删掉那一行，已部署服务器上的文件里它会永远留着。几年下来，谁也说不清为什么存在的配置就会在各台服务器上以不同形态堆积。标记块因为整个块本身就是声明，结构上不会产生这个问题。

8.3 使用标记块时的注意点

  • 标签要取得唯一。 同一个文件里可能有多个脚本各自放块。像 # BEGIN myapp-nginx-upstream 这样把归属和用途一起写上。
  • 注释符号因文件格式而异。 如果用的不是 # 而是 ; 或 //，标记也必须跟随那套语法，否则解析器会挂。
  • 标记被人删掉的话，下次执行会新加一个块，从而产生重复。把「请勿改动」的提示一并写在块的第一行会有帮助。
  • 不要用在有结构的格式（JSON、YAML）上。 基于行的插入会破坏这类格式，必须用专用解析器读写。
  • 只在块内做管理。 一旦脚本开始碰标记之外的地方，这个模式的优点就消失了。

9. 如何证明重跑没问题 - 状态哈希与 dry-run

「我写成幂等的了」这种主张必须是可验证的。最便宜的办法是把整棵目标树折叠成一个哈希。

state_hash(){
  ( cd "$1" && {
      find . -type f | LC_ALL=C sort | xargs sha256sum
      find . -type l | LC_ALL=C sort | while read -r l; do echo "$(readlink "$l")  $l"; done
    } | sha256sum | awk '{print $1}' )
}

普通文件用内容哈希折叠，符号链接用 readlink 的结果折叠。用 LC_ALL=C sort 固定排序顺序很重要，顺序随区域设置变化的话哈希也会跟着变。下面是把环境准备函数跑三次的结果。

provision run1  state_hash=219dd1b402f930f92ce94faa467761005c47cb12d740c452e7609d3d6d0d4526
provision run2  state_hash=219dd1b402f930f92ce94faa467761005c47cb12d740c452e7609d3d6d0d4526
provision run3  state_hash=219dd1b402f930f92ce94faa467761005c47cb12d740c452e7609d3d6d0d4526

9.1 注入漂移再跑一次 - 诚实的结果

这里出现了一个不太好看的结果，原样放上来。先故意把状态弄偏，然后重跑。

after drift   state_hash=74c1a29f825801f98c4d235c47df56ad943e386df4697f5ffd3b1709e7d3785b
after re-run  state_hash=3e25756382253f698945962c75d2fd19bc1455d5dc20b79aa672057b3220cb81
MODE=production
TZ=Asia/Seoul
MODE=debug

重跑之后哈希并没有回到原来的值（219dd1...）。看看什么被修复了、什么留下了。

  • 已修复 - 人为造出的 obsolete.conf 被 rm -f 删掉了。
  • 已修复 - current 符号链接被 ln -sfn 重新指回了 releases/v2。
  • 残留 - 人手工加进去的 MODE=debug 那一行原样留着。

原因很清楚。grep -qxF ... || append 这套只问「我要的行在不在」，从不问「有没有我不要的行」。也就是说它到达了②结果收敛，但不是③自我修复。如果应用读文件时以最后一行为准，这台机器就会一边宣称自己是 production，一边跑在 debug 上。

要挡住这个，就得丢掉 append，改成声明整个文件或整个标记块。重跑验证如果停在「哈希三次相同」，就看不见这个洞。这正是需要故意注入漂移再跑一遍的理由。

9.2 dry-run - 改之前先看会改什么

运维中实际用得更多的其实不是哈希，而是试运行。--check 模式给你两样东西：预先看到会改什么，以及判定是否已收敛。

-- --check (nothing exists yet) --
  would add to app.env: MODE=production
  would add to app.env: TZ=Asia/Seoul
  changed=1
-- apply --
  changed=1
-- --check again --
  changed=0 (already at target state)

第二次 --check 返回了 changed=0。这就是幂等性的运维定义：「它能不能自己说出第二次执行没有东西要改」。 放进 CI 也很容易：应用之后再跑一次 --check，如果出现 changed=1，说明那个脚本没有收敛，直接让构建失败即可。

实现上的关键是把所有变更收拢到一个函数里。上面的例子只让 want_line 一个函数去看 CHECK 标志。变更点一旦散落在代码各处，dry-run 就维持不住。

10. 部分失败后的续跑 - 步骤标记及其陷阱

回到引言的问题：八步走到第五步死掉时该怎么办。

10.1 坏设计 - 前面的步骤不幂等就永远过不去

-- bad.sh run 1 (forced failure) --
  step 3 failed
exit=3
-- remove the cause, run 2 --
mkdir: cannot create directory 'rbad/data': File exists
exit=1  <- blocked at step 1 forever

失败原因已经修好了，却卡在第一步。这种状态下运维能做的只剩打开脚本把前面注释掉再跑。那一刻，「用脚本部署」这个前提就崩了。

10.2 好设计 - 每一步幂等 + 完成标记

run_step(){
  local name="$1"; shift
  if [ -f "$S/$name.done" ]; then echo "  [skip] $name"; return 0; fi
  "$@" && : > "$S/$name.done" && echo "  [done] $name"
}
run_step schema s1 && run_step seed s2 && run_step release s3
-- good.sh run 1 (step 3 fails) --
  [done] schema
  [done] seed
   markers: schema.done seed.done
-- remove the cause, run 2 --
  [skip] schema
  [skip] seed
  [done] release
  completed
-- run 3 (should do nothing) --
  [skip] schema
  [skip] seed
  [skip] release
  completed
seed.csv lines: 1 | version: v1

第二次从失败的位置接着跑完，第三次什么都没做就跑完了。seed.csv 是一行这一点也很重要：因为每一步本身就是幂等的，即使没有标记也安全。

10.3 步骤标记的陷阱 - 标记不保证收敛

这个模式有个陷阱。试着让人把产物删掉后再重跑。

a human deleted 'version'; re-run:
  [skip] schema
  [skip] seed
  [skip] release
  completed
version present? no - the marker made it skip

脚本报告了「完成」，产物却不存在，因为它只看标记不看真实状态。由此得出的原则很明确。

  • 步骤标记是续跑速度的优化，不是收敛的保证。 只用来跳过重量级步骤（大文件下载、数据迁移）。
  • 轻量步骤不要打标记。 每次都确认既安全又没有成本。
  • 输入变了标记就要失效。 把输入哈希放进文件名（release.$(sha256 of config).done），配置一变就会自动重新执行。
  • 最后要直接验证状态。 与标记无关，补上 [ -f "$R/version" ] 这类最终确认。
  • 慎重决定标记的存放位置。 放在目标机器上，换机器就没了；放在中心，又反映不出各机器各自的状态。

11. 需要锁的条件，不需要锁的条件

到此为止的所有防御手段都有一个共同前提：同一时刻只跑一个。这个前提一旦破掉，「先确认再变更」本身就垮了，这就是所谓的 check-then-act 问题。

11.1 复现 - 8 个进程同时执行「没有就创建」

round1: no lock SEED=5 | mkdir lock SEED=1 (expected 1)
round2: no lock SEED=4 | mkdir lock SEED=1 (expected 1)
round3: no lock SEED=4 | mkdir lock SEED=1 (expected 1)
round4: no lock SEED=5 | mkdir lock SEED=1 (expected 1)
round5: no lock SEED=4 | mkdir lock SEED=1 (expected 1)

五轮全都生成了4 到 5 行，而期望值是 1。因为在用 grep 确认的瞬间和用 >> 追加的瞬间之间，别的进程插了进来。上一节里那么费劲做出来的 grep -qxF || append，在并发面前无能为力。

更重要的是这种情况实际何时发生：cron 周期是 5 分钟而执行要花 6 分钟时，部署流水线因重试把同一个作业起了两次时，多个节点去碰共享存储上的同一个文件时。三种都很常见。

11.2 不需要锁的情况 - 整体替换

并非所有情况都需要锁。把整个文件写到临时文件再用 mv 换上去的方式，8 个进程一起冲上来也毫发无伤。

printf 'value=42\n' > ".atomic.$i.tmp" && mv ".atomic.$i.tmp" atomic.txt

lines=1 | content=value=42 | sha=72cc615c7f451bd5

依据是 rename(2) 的保证。手册写着「若 newpath 已存在，它会被原子地替换，因此不存在其他进程试图访问 newpath 时它不存在的时刻」。只需守住一个条件：临时文件和目的地必须在同一个文件系统上（跨文件系统会退化为复制，原子性随之失效）。

11.3 必须要锁的情况 - 读改写

## 8 processes increment count by 1 concurrently
final count=2  (expected count=8)

8 次自增丢失到只剩 2 次，这是读到的值在写回之前就过期的典型更新丢失。整理成判断表如下。

作业形态需要锁理由替代方案
整个文件重写后替换不需要rename 是原子的临时文件 + mv（同一文件系统）
创建目录 mkdir -p不需要内核以原子方式处理直接使用
确认行存在后 append需要检查与变更之间有间隙加锁，或改为整体替换
读改写（计数器、列表）需要更新丢失加锁，或 append-only 后再聚合
防止长任务重复启动需要执行时间可能超过周期在作业入口处获取锁
标记块替换需要属于读-改-写结构锁 + 临时文件 mv 并用

11.4 用什么来加锁

在 Linux 上，util-linux 的 flock 是标准选择。手册给出了让脚本锁住自身的惯用写法。

[ "${FLOCKER}" != "$0" ] && exec env FLOCKER="$0" flock -en "$0" "$0" "$@" || :

用 -n（非阻塞）时，拿不到锁会返回默认退出码 1（可用 -E 修改）。放进 cron 时要先决定把这个值当成「正常的重复防护」还是「失败」，否则告警会很吵。

如果环境里没有 flock，可以用 mkdir 的原子性。这次复现中五轮都精确保持一行的就是这个方式。

if mkdir "$LOCKDIR" 2>/dev/null; then
  trap 'rmdir "$LOCKDIR"' EXIT INT TERM
  ... 临界区 ...
else
  echo "another instance is running"; exit 0
fi
  • 一定要用 trap 释放。不加的话，异常退出时锁会留下，下一次执行将被永远挡住。
  • 在锁目录里留下 PID 与时间。 这是判断残留的锁是否属于活着的进程的依据。
  • 定好孤儿锁的回收策略。 按时间自动回收很省事，但有杀掉正常慢执行的风险。
  • 在 NFS 等网络文件系统上，锁的语义会不同。 如果有多个节点参与，请考虑用专门的协调手段代替文件锁。
  • 锁不是幂等性的替代品。 锁只挡并发，顺序重跑就会坏掉的代码，加了锁照样坏。

12. 各命令的安全写法对照表

把到此为止复现的内容折成一页。写脚本写到手停下来时，看这张表就够了。

结论: 幂等性不是性格，而是设计

本文复现的这些事故有个共同点：大多数都不会报错。ln -sf 返回 0 却让旧版本继续对外服务，sed -i 返回 0 却什么都没做，被注释匹上的 grep -qF 让配置几个月没有生效。退出码是 0 和已经到达目标状态，是两回事。 哪怕只留下这一句，本文也值回票价。

所以实务规则可以缩成三行。第一，逐行去问「这条命令在已经做过的状态下执行会做什么」，大部分事故都源于一次都没问过这个问题。第二，检查的是「是不是目标状态」，而不是「做没做过」，基准是当前状态而非操作历史。第三，别主张，去证明，跑三次比一比哈希只要一分钟，而这一分钟能省下凌晨三点的两个小时。

规模一大，最终还是会走向 Ansible 这类工具。而那些工具所说的「幂等」，其真身正是本文里手工做出来的这些东西：lineinfile 是先确认存在再变更，blockinfile 是标记块，--check 是 dry-run，changed 的值就是是否收敛。就算用了工具，不懂这些原理，用 shell 模块一行照样能捅出同样的事故。 实际上引入工具之后事故仍不断的组织，大多卡在这个点上。

最后是今天就能做的一件事：把跑得最频繁的那个脚本放进临时目录跑三次，打出状态哈希。 三个值如果不同，那个脚本已经每天都在悄悄改动着什么，只是还没有人察觉而已。

# 幂等脚本检查清单 — 动手写之前先过一遍

> 来源: braindetox.kr — 跑两次也安全的脚本
> 依据: POSIX Issue 8 (mkdir/rm)、GNU coreutils (ln -n)、rename(2)、flock(1)
> 可以把这个文件直接贴给 AI，写「按这份标准帮我改我们的脚本」。

## 1. 各命令的安全写法 — 直接照抄

| 想做的事 | 就这么写 |
|---|---|
| 创建目录 | `mkdir -p "$D"`，权限用单独一行 `chmod 0750 "$D"` |
| 删除文件 | `rm -f "$F"`（目录用 `rm -rf` — 必须先做变量防护） |
| 追加一行 | `grep -qxF -- "$L" "$F" \|\| printf '%s\n' "$L" >> "$F"` |
| 删除一行 | `grep -vxF -- "$L" "$F" > "$F.t" && mv "$F.t" "$F"` |
| 符号链接 | `ln -sfn "$TARGET" "$LINK"` |
| 替换取值 | `grep -qxF "$WANT" "$F" \|\| sed -i "s#^$OLD\$#$WANT#" "$F"` |
| 插入一行 | 有则 `sed -i 's/^key=.*/key=v/'`，无则走 `a\` 分支 |
| 注册 cron | `{ crontab -l 2>/dev/null \| grep -vF "$ABS_PATH"; echo "$JOB"; } \| crontab -` |
| 复制目录 | `cp -r "$SRC/." "$DST/"`（不是 `cp -r src dst`） |
| 移动文件 | `[ -e "$S" ] && mv "$S" "$D"` |
| 整体写文件 | `... > "$F.tmp" && mv "$F.tmp" "$F"`（同一文件系统） |

## 2. 逐行自问
- [ ] 这一行在**已经做完的状态**下执行会做什么
- [ ] 检查的是**「是否为目标状态」**，而不是「是否做过」
- [ ] `grep` 判断同时带了 `-x`（整行）和 `-F`（固定字符串）吗
- [ ] 有没有把 `grep` 的退出码 **2（出错）** 和 1（不匹配）区分开
- [ ] `sed` 替换后的结果会不会**再次匹配同一个模式**
- [ ] 是不是把 `sed -i` 的退出码当作「已生效」的证据了
- [ ] 每次替换符号链接都带了 **`-n`** 吗
- [ ] 在 `set -e` 下，前面一步失败会**整段吞掉后续步骤**吗
- [ ] 文件里混入**时间戳、随机数**，导致无法做哈希比对了吗
- [ ] 当管理项**减少**时，已经下发的文件里会跟着消失吗

## 3. 标记块模板 — 管理行超过五条就用它

```bash
apply_block(){                     # apply_block <文件> <标签> <正文>
  local file="$1" tag="$2" body="$3"
  local begin="# BEGIN ${tag}" end="# END ${tag}"
  [ -e "$file" ] || : > "$file"
  if grep -qxF "$begin" "$file"; then
    awk -v b="$begin" -v e="$end" -v body="$body" '
      $0==b { print b; printf "%s", body; skip=1; next }
      $0==e { print e; skip=0; next }
      skip==1 { next }
      { print }' "$file" > "$file.new" && mv "$file.new" "$file"
  else
    { printf '%s\n' "$begin"; printf '%s' "$body"; printf '%s\n' "$end"; } >> "$file"
  fi
}
apply_block /etc/ssh/sshd_config "myapp-keepalive" \
  $'ClientAliveInterval 30\nClientAliveCountMax 3\n'
```

- [ ] 标签里写清了**归属方和用途**（`myapp-nginx-upstream`）
- [ ] 标记符合该文件的**注释符号**（`#` / `;` / `//`）
- [ ] **不用在** JSON、YAML 这类结构化格式上
- [ ] 脚本**不碰标记之外**的内容

## 4. 重跑验证流程 — 提交前花一分钟

```bash
state_hash(){
  ( cd "$1" && {
      find . -type f | LC_ALL=C sort | xargs sha256sum
      find . -type l | LC_ALL=C sort | while read -r l; do echo "$(readlink "$l")  $l"; done
    } | sha256sum | awk '{print $1}' )
}
for i in 1 2 3; do ./provision.sh "$ROOT"; echo "run$i $(state_hash "$ROOT")"; done
```

- [ ] 三次哈希**完全一致**（不一致说明某处在累积）
- [ ] 用 `LC_ALL=C sort` 固定了排序
- [ ] **故意制造漂移**后再跑一次（多加一行配置、改掉链接指向、放个多余文件）
- [ ] 第二次 `--check` 返回 **changed=0**
- [ ] 所有试验只在**临时目录**里进行

## 5. 什么时候需要加锁

| 场景 | 锁 | 替代做法 |
|---|---|---|
| 整体替换文件 | 不需要 | 临时文件 + `mv` |
| `mkdir -p` | 不需要 | 照常使用 |
| 先检查再追加 | **需要** | 改成整体替换 |
| 读—改—写 | **需要** | 只追加，事后汇总 |
| 执行时间超过周期的 cron | **需要** | 在入口处加锁 |
| 替换标记块 | **需要** | 加锁 + 临时文件 `mv` |

```bash
# 有 flock 时
[ "${FLOCKER}" != "$0" ] && exec env FLOCKER="$0" flock -en "$0" "$0" "$@" || :

# 没有就利用 mkdir 的原子性
if mkdir "$LOCKDIR" 2>/dev/null; then
  trap 'rmdir "$LOCKDIR"' EXIT INT TERM
else
  echo "已有另一个实例在运行"; exit 0
fi
```

- [ ] 一定要用 `trap` 释放锁
- [ ] 锁目录里留下 **PID 和时间**
- [ ] 定好了**残留锁的回收策略**
- [ ] 记住锁只挡**并发** — 顺序重跑的缺陷依然存在

## 6. 部分失败后的续跑
- [ ] 每一步**本身就是幂等的**（没有标记也安全）
- [ ] 标记只加在**耗时重的步骤**上
- [ ] 标记文件名里嵌入**输入哈希**，配置一变就自动失效
- [ ] 最后校验的是**真实状态**，而不是标记
