JSON に載せた 64 ビット ID の末尾が変わる - 数値精度が消える地点

エラーは出ない。末尾の二桁か三桁だけが静かに変わる

2026-07-30 開発/インフラ

はじめに: 照会できないのに ID は確かに合っていた

サポートからチケットが上がってくる。注文番号を入れたのに照会できないという。担当者が書き取った番号を確認すると、その注文はデータベースに確かに存在する。ところが管理画面で同じ番号を検索すると結果が出ない。画面に出ている番号と DB の番号を並べて見ると、先頭の 16 桁は同じで末尾の 3 桁だけが違う。

この時点でよく出る推測は三つある。コピーのときに切れた、画面が丸めて表示している、データが二重になっている。三つとも違う。値が変わったのはサーバでも DB でも画面でもなく、その間にある JSON の一行である。

この記事の要点は「識別子は文字列で送りましょう」という結論ではない。その助言は誰もが知っているし、それだけでは既に動いているシステムから何も見つけられない。この記事が扱うのは、どこで精度が消え、代わりに何を諦めるのか、そしてなぜこの事故はいつも遅れて発見されるのかである。

まずこの問題の性質を一文にまとめる。この一文が残りのすべてを説明する。

JSON 標準は数値の精度を規定していない。壊れるのは標準ではなくパーサ、つまり言語の選択である。だから送る側と受ける側の言語が違えば、両方とも正常に動作しながら値がずれる。

実行環境。以下のすべての出力は Windows 10 Pro (10.0.19045) で実際に実行した結果をそのまま写したものである。ランタイムは Node.js v22.16.0 (win32)、Python 3.13.3 (win32)、Perl v5.38.2(JSON::PP 4.16)、SQLite 3.49.1 である。スクリプトはすべてファイルに保存して実行し、例に使った ID と金額はすべて架空の値である。

この記事が扱わないこと。お金の計算そのものの原則、つまりなぜ金額に浮動小数を使ってはいけないのかはフィンテックエンジニアリングハンドブックで既に扱った。ここでは JSON の境界での直列化だけを見る。スキーマと契約文書をどう運用するかはAPI 文書ガバナンスの側である。同じ「境界で静かに壊れる」構造の別の事例としてはエンコーディングが壊れる地点がある。

1. 再現: 19 桁の ID を JSON に一度載せると

まずやることは目で見ることである。ツイッターやスノーフレーク系の ID がそうであるように、19 桁の整数を JSON に載せて往復させた。元と結果を並べて出力した。

読み方はこうである。送ったテキストには 1234567890123456789 が確かに入っていた。解析した値は 1234567890123456800 である。長さは 19 桁のままで、先頭の 16 桁もそのままである。17 桁目から 789 が 800 に変わった。

  • 再直列化された JSON がまた有効である。だから次のシステムへそのまま流れていく。誰も止められない

さらに直感を壊すのがその下である。x と x + 1 が同じになる地点がある。9007199254740992 に 1 を足しても値がそのままである。19 桁の ID では言うまでもない。整数論的にはありえないことだが、ここで扱っているのは整数ではなく整数の近似値なので成立する。

5. 標準は何を規定し何を規定しないのか

ここで規格を確認して進まなければならない。この問題を「実装のバグ」と誤解すると対応の方向が丸ごとずれるからである。

RFC 8259 の数値の節は表記文法を定義したあと、精度については規定ではなく推奨を書いている。開いて確認した文はこうである。

「good interoperability can be achieved by implementations that expect no more precision or range than these provide」 — これ以上の精度や範囲を期待しない実装どうしなら、良い相互運用性を得られる。

「numbers that are integers and are in the range [-(2**53)+1, (2**53)-1] are interoperable in the sense that implementations will agree exactly on their numeric values」 — 整数でありこの範囲にある数は、実装がその数値に正確に同意するという意味で相互運用可能である。

文を正確に読まなければならない。「この範囲を越えてはならない」ではない。越えても文法的には完全に有効な JSON である。標準が言っているのはその範囲の中でだけ実装が同じ値に同意する保証があるということである。外では保証がないだけであり、保証がないということは壊れても規格違反ではないという意味である。

結論がここから出る。

  • これはバグ報告を出す相手がいない問題である。パーサも正しく直列化器も正しい
  • 直せる場所は契約だけである。どの値をどの形でやり取りするかを決める地点ひとつだけである
  • だからこの問題の解決策はライブラリの交換ではなく仕様書に一行書くことである
  • RFC が 2**53 を明示的に書いている理由もここにある。この数は JavaScript の事情ではなく相互運用の共通分母として文書に刻まれている

同じ文書は Infinity と NaN についても釘を刺している。「Numeric values that cannot be represented in the grammar below (such as Infinity and NaN) are not permitted.」 この文は 10 節でまた使う。

6. 文字列に入れると - そして何を諦めるのか

最もよく知られた解法を実際に確認する。同じ値を引用符の中に入れて送った。

  9  > 100   (numeric)       : False

保存される。当然である。文字列はパーサが数値として解釈しないので手を出す理由がない。ところがそんなに簡単なら、なぜ最初からみんなそうしなかったのか。二つ目のブロックが答えである。

  • 並び順が変わる。数値で並べると 9, 10, 99, 100 だが文字列で並べると 10, 100, ... が前に来る。桁数の違う値が混ざると順序が完全にずれる
  • 比較演算が逆転する。文字列の比較では 9 が 100 より大きいと出る。辞書順だからである
  • 0 で埋めれば順序は復元される。20 桁に揃えると並べた結果が数値の順序と同じになった。代わりに保存領域と索引の大きさが増え、後で桁数が増えると全体をやり直すことになる
  • 算術が塞がれる。文字列に 1 を足そうとすると型エラーになる。これは欠点ではなくむしろ安全装置に近い
  • 範囲検索が難しくなる。「昨日以降に発行された ID」のような条件を ID 自体で掛けていた設計は組み直さなければならない

だから判断基準は型ではなく用途である。その値で算術や範囲比較をするのか。しないなら文字列で失うものは事実上ない。するなら文字列は答えではなく、値の大きさを契約で制限する方が正しい。

7. BigInt で受ければよいのか

JavaScript には任意精度の整数型がある。ならそれで受ければよいのではないか、というのが自然な次の問いである。結論から言うとそのままでは駄目である。

node v22.16.0 / win32

--- 6-1. can JSON.parse produce a BigInt by itself ---

BigInt("1234567890123456789")            : 1234567890123456789

  -> converting AFTER parsing is too late, the digits are already gone

二つのことが確認される。第一に、標準のパーサは BigInt を作ってくれない。逆方向に BigInt を直列化しようとすると最初から例外になる。第二に、解析したあとに変換するのは遅すぎる。既に壊れた数値を BigInt に変えても壊れた値が正確に保存されるだけである。

二つ目のブロックのリバイバがその罠をそのまま示している。リバイバはコールバックなので介入地点が早いように見えるが、コールバックが受け取る値は既に数値に変換されたあとである。だから結果が相変わらず 1234567890123456768 である。

では方法がないのか。ある。元のテキストにアクセスできなければならない。

  result : 1234567890123456789

  exact  : true

--- 6-5. writing BigInt back out ---

unquoted number form              : {"order_id":1234567890123456789,"amount":1000}
  the second form is valid JSON, and it breaks again at the next JS reader
  • この環境の Node 22 ではリバイバの三つ目の引数として元のテキストの断片を受け取れた。それを使えば 1234567890123456789 が正確に復元される
  • この機能を使えない環境なら、解析前にテキストを直して引用符を被せる方式がある。広く使われる回避法である
  • ただしその回避法には代償がある。上の出力の最後の事例がそれである。文字列の中に入った長い数字は触らないべきなのに、正規表現でテキストを直すと境界を取り違えることがある

8. 浮動小数の往復 - 何桁書けば保証されるのか

整数の話を終えたので小数に行く。よく知られた例から確認した。

--- 7-1. the classic float sum, in python ---

0.1 + 0.2 == 0.3           : False
Decimal of 0.1             = 0.1000000000000000055511151231257827021181583404541015625
json.dumps(0.1 + 0.2)      = 0.30000000000000004
json.loads of that == sum  : True

--- 7-2. how many decimal digits guarantee a float round trip ---
sys.float_info.dig     : 15  (digits guaranteed to survive text -> float -> text)
mant_dig               : 53 bits
  %.15g : 183351 failures out of 200000
      first failure  original 399955.7584213044 -> text 399955.758421304 -> back 399955.758421304
  %.16g :  51352 failures out of 200000
      first failure  original -377762.57764660777 -> text -377762.5776466078 -> back -377762.5776466078
  %.17g :      0 failures out of 200000

--- 7-3. repr already picks the shortest text that round trips ---
  0.1                    len= 3  round trip: True
  0.30000000000000004    len=19  round trip: True
  0.3333333333333333     len=18  round trip: True
  1.4142135623730951     len=18  round trip: True
  1e-07                  len= 5  round trip: True

0.1 + 0.2 が 0.3 ではないことは有名である。ここで見るべきはその次である。その値を JSON で出してまた読むと、正確に同じ値が戻ってくる。つまり浮動小数の往復は安全である。整数とは正反対である。

安全な理由が二つ目のブロックにある。桁数を変えて 20 万回ずつ往復させてみた。

  • 15 桁で書くと 18 万件を超えて失敗した。つまり 15 桁は往復を保証できない
  • 16 桁も 5 万件を超えて失敗した
  • 17 桁で失敗が 0 になった。20 万件すべてが正確に戻った

これが倍精度実数で 17 桁という数が出てくる根拠である。仮数 53 ビットが表現する値どうしを十進数で区別するにはそれだけ必要である。Python が報告する「保証桁数」が 15 であることと混同しやすいが、二つは方向の違う値である。15 は十進数から出発して往復するときの保証で、17 は二進数から出発して往復するときに必要な桁数である。

JavaScript でも同じ実験をした。

実務の規則。小数を JSON で出すとき桁数を自分で指定してはいけない。丸めてきれいにしようという介入が往復の保証を壊す。表示の書式は画面で決め、送信には既定の直列化を使うのが正しい。

9. 金額 - JSON の境界での直列化

金額に浮動小数を使ってはいけないという原則自体はフィンテックエンジニアリングハンドブックで扱った。ここでは JSON の境界でだけ起きることを見る。

--- 8-1. money at the JSON boundary (serialization only) ---
float sum of [19.99,19.99,19.99,0.1,0.2] = 60.27
JSON.stringify(sum)                     = 60.27
rounded to 2dp                          = 60.27
integer minor units sum                 = 6027  (60.27)
difference                              = 0 minor units

  the JSON boundary problem is not the arithmetic, it is the text:
    text 0.10      -> number 0.1       -> re-stringified 0.1       text preserved: false
    text 19.99     -> number 19.99     -> re-stringified 19.99     text preserved: true
    text 1234.50   -> number 1234.5    -> re-stringified 1234.5    text preserved: false
    text 100.00    -> number 100       -> re-stringified 100       text preserved: false
  trailing zeros and the scale of the amount are not part of a JSON number

まず上から。この標本では実数の合計と整数の合計の差が 0 だった。丸めたあとの結果が同じだったという意味であり、「小数で足すと必ず一円が消える」という通念が常に成立するわけではないことを示している。消える場合とそうでない場合があり、この標本は後者だった。だからこそ危険である。テストが通ってしまう。

本当の問題は下である。JSON の境界で消えるのは値ではなく表記である。

  • 0.10 を送ると 0.1 になって戻る。末尾の 0 が消える
  • 1234.50 は 1234.5 になる。金額の表記としては不自然で、文字列の比較や署名の検証では不一致になる
  • 100.00 は 100 になる。小数点そのものが消える。通貨の小数桁数の情報がなくなる
  • 19.99 だけがそのままだった。偶然短い表記が元と同じだっただけである

つまり JSON 数値には小数桁数という概念がない。100.00 と 100 は同じ数であり、直列化器は短い方を選ぶ。小数桁数の違う通貨を一緒に扱うシステムでこれが問題になる。

代案は二つだけである。最小単位の整数で送って通貨コードを一緒に入れるか、文字列で送って表記をそのまま保存するか。前者が一般的で、後者は小数桁数を契約で固定しにくい場合に使う。どちらにしても JSON 数値で金額を送る選択肢だけが抜ける。

10. NaN と無限大 - 標準にない値

5 節で引用した RFC の文のとおり、この二つの値は JSON の文法に存在しない。ところがプログラムでは作られる。0 で割ったり範囲を越えたりすると生じる。では直列化器は何をするのか。

--- 9-2. NaN and Infinity at the JSON boundary in JS ---
JSON.stringify(NaN)                  : null
JSON.stringify(Infinity)             : null
JSON.stringify(-Infinity)            : null
JSON.stringify({a:NaN,b:Infinity})   : {"a":null,"b":null}
JSON.stringify([NaN, Infinity])      : [null,null]
JSON.stringify(-0)                   : 0
JSON.parse(JSON.stringify(-0))       : 0  Object.is(-0) : false
  JSON.parse("NaN"        ) -> SyntaxError
  JSON.parse("Infinity"   ) -> SyntaxError
  JSON.parse("-Infinity"  ) -> SyntaxError
  JSON.parse("nan"        ) -> SyntaxError
  JSON.parse("1e400"      ) -> Infinity
  JSON.parse("-1e400"     ) -> -Infinity
  JSON.parse("1e-400"     ) -> 0

JavaScript の選択は null に変えることである。例外も警告もない。これが実務で何を意味するか見よう。測定に失敗して NaN になった値と、もともと測定していないので null の値が受信側で完全に区別不可能になる。「データなし」と「計算失敗」が一つの値に合わさる。

追加で確認されたことがある。

  • 負のゼロが消える。-0 を出すと 0 になり、戻ってきた値はもはや負のゼロではない
  • 範囲を越えるリテラルは無限大になる。1e400 は解析エラーではなく Infinity である。つまり読むときは静かに受け入れ、書くときは null に変える
  • 小さすぎる値は 0 になる。1e-400 は 0 として解析された。0 でない値が 0 になるのは除算があるコードで危険である
  • 逆に読む側は厳格である。NaN や Infinity という文字を入れると構文エラーになる

他の言語はこの地点でまた違う振る舞いをする。

--- 9-1. NaN and Infinity: python writes them, the standard has them not ---
json.dumps default      : {"nan": NaN, "inf": Infinity, "ninf": -Infinity}
json.loads of that back : {"nan": NaN, "inf": Infinity, "ninf": -Infinity}

json.loads('Infinity')  : inf
with parse_constant     -> ValueError: rejected NaN

--- 11-5. NaN and Infinity in a third parser ---
  decode(NaN) -> error: malformed JSON string, neither array, object, number, string or atom,
  decode(Infinity) -> error: malformed JSON string, neither array, object, number, string or atom,
  decode(-Infinity) -> error: malformed number (no digits after initial minus),
  decode(1e400) -> Inf
  encode([inf, nan]) -> [Inf,NaN]

この出力が示す非対称は大きい。

  • Python は既定値で NaN と Infinity をそのまま書き出す。これは標準 JSON ではない。そして自分が書いたものを自分でまた読めるので、同じ言語どうしでだけテストすると決して現れない
  • Python にはこれを禁じるオプションがあり、入れると例外になる。既定値が寛容な方だというのが核心である
  • Perl は読むのを拒否する。NaN と Infinity の両方が解析エラーである
  • ところが Perl は書くときは書き出す。無限大と NaN が入った配列をエンコードすると [Inf,NaN] が出た。このテキストは Perl 自身もまた読めない

11. 大きな数の指数表記 - 桁数の検査をすり抜ける

整数の防御を「16 桁以上なら危険」という規則で組むと見落とす穴がある。どの大きさから表記が変わるのか確認した。

--- 10-2. where JS flips to exponent notation ---
n                        String(n)                          JSON.stringify(n)
----------------------------------------------------------------------------------
10^18                    1000000000000000000                1000000000000000000
10^19                    10000000000000000000               10000000000000000000
10^20                    100000000000000000000              100000000000000000000
10^21                    1e+21                              1e+21
10^22                    1e+22                              1e+22
10^100                   1e+100                             1e+100

  and back again:
    JSON.parse(1e21                    ) -> 1e+21   re-stringified -> 1e+21
    JSON.parse(1e+21                   ) -> 1e+21   re-stringified -> 1e+21
    JSON.parse(1E21                    ) -> 1e+21   re-stringified -> 1e+21
    JSON.parse(1000000000000000000000  ) -> 1e+21   re-stringified -> 1e+21
  a naive digit-count guard misses this shape entirely:
    text          : 1e+21
    /^\d{16,}$/   : false   <- the guard does not fire

正確に 10 の 21 乗から指数表記になる。その下の 10 の 20 乗までは数字をそのまま並べる。この境界は言語仕様が定めたもので勝手に変わらない。

実務でこれがなぜ問題なのか。最後の二行が答えである。16 桁以上を探す正規表現が 1e+21 には反応しない。テキストが五文字だからである。桁数の検査を通りながら実際には 21 桁も失った値がそのまま通る。

  • また解析しても元の桁数は戻らない。1000000000000000000000 と 1e21 は同じ値として扱われる
  • 大文字の 1E21 も同じ値として読まれる。検査の正規表現で大文字小文字を落とす間違いがよくある
  • この区間の値が識別子に使われることは稀だが、累積合計やバイト数では到達する
  • だから診断手順には指数表記の探索が別項目として入らなければならない

13. 重複キー・キーの順序・正規化ハッシュ

数値と同じくらいよく絡む周辺の問題を同じ実行で確認した。

--- 13-1. duplicate keys: last one wins, silently ---

  a raw sha256      : 342ae634b438dfbe6c65969e

  and here is the catch:

    which is NOT the id that was sent. canonicalization does not undo the loss.

三つのことが出てくる。

  • 重複キーは最後の値が勝つ。RFC 8259 は名前が一意であるべきだと推奨しつつ、一意でないときの動作は予測不可能だと書いている。実際に確認した三つのパーサはすべて最後の値を採ったが、これは保証ではなく慣行である
  • キーの順序が再配置される。整数のように見えるキーが前に引き出された。順序に意味を与えた設計はここで壊れる
  • 正規化するとハッシュが一致する。空白とキーの順序だけが違う三つのテキストが正規化後に同じハッシュになった

ところが最後のブロックにこの節の要点がある。正規化された結果の中に入っている ID は既に損傷した値である。正規化は表記の違いをなくすだけで、消えた桁を戻せない。署名が一致しても値が元であるという保証はないという意味である。正規化ハッシュで完全性を確認するシステムはこの点を別に防御しなければならない。

--- 13-4. escapes and lone surrogates in the same payload ---
  JSON.parse of \u escaped digits stays a string:
    value : 1234567890123456789   length : 19
  numbers cannot be escaped that way:
    JSON.parse of an escaped bare digit -> SyntaxError
  JSON.stringify of a lone surrogate : "\ud800"  (well-formed output, ES2019)
    code unit : U+D800
    round trip identical : true
  and a number-shaped string is not a number:
    JSON.parse('"1e21"') typeof : string

--- 11-6. key order and duplicate keys, third parser ---
  decode of three identical keys -> id = 3
  canonical encode of {b,a,c}    -> {"a":2,"b":1,"c":3}
  default encode of the same     -> {"c":3,"b":1,"a":2}
  • 文字列の中の数字はユニコードのエスケープで書いても文字列である。損傷しない
  • 逆に数値リテラルはエスケープできない。エスケープした瞬間に構文エラーである
  • 対のないサロゲートは直列化のときエスケープの形で安全に出力され、往復も同一だった
  • 数値のように見える文字列は相変わらず文字列である。1e21 を引用符に入れても数値にならない
  • Perl でも重複キーは最後の値であり、キーの順序を固定するオプションが別にあった

14. なぜいつも遅れて発見されるのか

この事故の最も厄介な性質は技術ではなく時間にある。発見が遅れる理由が構造的である。

  • 開発データの ID が小さい。1、2、3 で開発すればこの問題は存在しない。2 節の出力のとおり 16 桁までは全部正常である
  • ステージングもたいてい小さい。本番データをそのまま使わないのが普通なのでここでも引っかからない
  • 初期の本番でも引っかからない。連番方式なら ID が 16 桁に到達するまで長くかかる
  • 破裂する時点は ID の体系を変えるときである。連番から分散 ID に移るか、タイムスタンプ基盤の ID を導入するか、他のシステムの ID を受け取り始めるときに急に 19 桁が入ってくる
  • その時点ではコードが既に複数の場所にある。最初の設計時には一箇所直せばよかったものが今は全区間である
  • テストが全部通る。既存のテスト用データの ID が小さいからである。新しいコードを書いても古いデータで検証すれば相変わらず通る

対応は単純である。開発データに 19 桁の ID を混ぜておくことである。データを一つ変えるだけでこの問題は開発段階で現れる。費用がほとんどかからないのに効果は最も大きい。

付け加えると、この問題が既に起きたかを確認する方法もある。ログや監査記録から同じフィールドの値が末尾一二桁だけ違う組を探すことである。先頭の桁が完全に同じで後ろだけ違う値が繰り返し現れるなら、それは偶然ではなく既に発生した事故の痕跡である。

17. 断定しなかったこと

この記事で確認した範囲と確認できなかった範囲を区分しておく。

  • すべての言語を確認したわけではない。確認したのは JavaScript、Python、Perl、そして SQLite だけである。他の言語と他のパーサ実装はまた違う振る舞いをしうる
  • 同じ言語の中にもパーサが複数ある。ここで見たのは各言語の既定の実装であり、代替のパーサはオプションと動作が違う
  • バージョン依存がある。リバイバで元のテキストを受け取る機能は比較的最近の仕様であり、以前のランタイムにはない。「この環境でできた」は「どこでもできる」ではない
  • 金額の実験の結論を一般化していない。この標本では実数の合計と整数の合計が一致した。別の標本ではずれる。この記事はその違いが標本に依存するということだけを言う
  • 表計算ソフト自体は実行していない。CSV のテキスト層と数値変換の層だけを確認した。特定の製品の動作は別に確認しなければならない
  • 性能は測っていない。文字列の識別子が索引と照会にどれほど負担になるかはデータの規模によって変わるので各自測定しなければならない

おわりに: 標準が規定しなかった場所

この問題を一文でもう一度書くとこうである。JSON 標準は数値の精度を規定せず、その空白を各言語が自分の方式で埋めた。その選択が互いに違うので、両方が各々正常に動作しながら値がずれる。

だからこの問題はコードで直せない。パーサを変えても、ライブラリを変えても、言語を変えても、次の消費者が別の言語ならまた起きる。直せる場所は契約ひとつだけである。どの値をどの形でやり取りするかを書いておくこと、そしてそれを境界テストとして常駐させること。

今すぐできる最も安い措置を一つだけ選ぶなら開発データに 19 桁の ID を一つ混ぜておくことである。データ一行でよい。その一行がないために、この事故はいつも本番で、ID が大きくなったあとに、顧客の問い合わせで発見される。

# JSON の数値精度 — 型の判断表と境界テスト値

> 出典: braindetox.kr — JSON に載せた 64 ビット ID の末尾が変わる
> 根拠: Windows 10 / Node 22.16.0 / Python 3.13.3 / Perl 5.38.2 (JSON::PP 4.16) / SQLite 3.49.1 での実行検証
> 規格: RFC 8259 Section 6 — 相互運用可能な整数区間は -(2^53)+1 から (2^53)-1

## 1. 一行でいうと

JSON 標準は数値の精度を規定していない。壊れるのはパーサ、つまり言語の選択である。
送る側と受ける側の言語が違えば、値は**例外を出さずに**変わる。

## 5. API 契約に書く文 (仕様書やレビューにそのまま貼る)

- このフィールドは**識別子**であり算術の対象ではない。JSON 文字列で送信し、最大長は 20 文字とする。
- このフィールドは JSON 数値で送信し、値は常に -(2^53)+1 以上 (2^53)-1 以下であることを保証する。
- 金額フィールドは通貨の**最小単位の整数**で送信する。単位と通貨コードを同じオブジェクトに同梱する。
- 応答に NaN、Infinity、-Infinity は現れない。測定不能は `null` で表す。
- 利用側は数値フィールドを倍精度浮動小数として解析しても損失がないと仮定してよい。
- スキーマに `type: integer` と `format: int64` を併記し、`format` は文書上の表記であって言語のパーサを強制しないことを明記する。
- クライアントが識別子を送り返すときは、**受け取ったテキストをそのまま**返すことを要求する。

## 6. すでに稼働中の API を診断する手順

1. 応答の**生テキスト**を確保する。解析済みのオブジェクトを見た時点で遅い。
2. その生テキストから 16 桁以上の整数リテラルを探す。文字列の中の数字は除く。
3. 見つけたリテラルを `2^53-1` と比べる。一つでも超えていれば危険が確定する。
4. 指数表記 (`e`、`E`) を含むリテラルは別に探す。桁数の検査では引っかからない。
5. 小数リテラルは再直列化した結果と**文字列で**比べる。末尾の 0 と桁数が消えるのを見る。
6. ログと監査記録から、同じフィールドの値が**末尾 1〜2 桁だけ**違う組を探す。すでに起きた事故の痕跡である。
7. 3 節の境界値を契約テストに入れ、値ではなく文字列で断定する。

| スキーマ・仕様 | 識別子を文字列と定め上限を書く | 「普通は大きくならない」という推測 |
| サーバの直列化 | 識別子を文字列で出す | 数値で出してクライアントに任せる |
| クライアントの解析 | 生テキストから大きな整数を見つけ文字列や多倍長で受ける | 解析後に多倍長へ変換する (すでに遅い) |
| 保存 | 整数の列に入れる | 浮動小数の列、表計算の自動変換 |
| テスト | 開発データに 19 桁の ID を混ぜる | 1、2、3 だけで開発する |
| 監査 | 契約テストに境界値を常駐させる | 事故の後にだけ確認する |

## 8. してはいけないこと

- 解析した後に大きな整数を文字列や多倍長へ変えること — その時点で桁はすでに失われている
- 桁数だけを数える検査 — 指数表記がその検査をすり抜ける
- 値が等しいかで往復を検証すること — 損失した値どうしは互いに等しい
- 小さい ID だけで開発しテストすること — 本番で ID が大きくなった後に破裂する
- 正規化後のハッシュ比較で完全性を確認すること — 正規化はすでに失われた桁を戻せない
- 「文字列で送れば終わり」と考えること — 並べ替え、範囲検索、比較の費用をどこで払うか決める必要がある

コピーしてメモアプリやAIツールにそのまま貼り付けてください。
