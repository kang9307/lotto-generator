はじめに - 同じ名前が指す場所

クラス本体にitems = []と書くと、すべてのインスタンスが同じリストを見る。Pythonチュートリアルの「Class and Instance Variables」の節は、この形を「mistaken use of a class variable」（クラス変数の誤用）の例（Dog.tricks）として載せ、インスタンス変数はインスタンスごとに固有のデータのため、クラス変数は全インスタンスが共有する属性とメソッドのためと区別している。症状そのものの再現は、既定引数に空リストを置くと呼び出しごとに値が溜まるの第7節と、テストの順序を入れ替えると見えるものの4.2節にすでにある。

混乱の根は、同じ名前がインスタンスにもクラスにも存在しうることにある。クラス属性はクラス本体で代入された名前でクラスの__dict__にあり、インスタンス属性はインスタンスの__dict__にある名前である。同じ名前がどちらにあるかで、読み取り・書き込み・削除の結果が分かれる。以下では、その位置を直接のぞき、一つずつ操作がどこに触れるかを切り分ける。

扱う問いは次のとおりである。

  • 値はインスタンスとクラスのどちらにあり、それをどう調べるか。
  • 読み取りと書き込みと削除は同じ場所を見るか。
  • クラス側の値を変えると、すでに作られたインスタンスはどうなるか。
  • +=は整数とリストでそれぞれ何を残すか。
  • サブクラスは親の可変属性を共有するか、type(self)で書くと値はどこに入るか。
  • dataclass・ClassVar・__slots__はこの区別をどう扱うか。
  • 意図して共有するとき、どの形が読む人に分かりやすいか。

値の置き場所 - __dict__とvarsで見る

この節の出力は既存の記事の第7節で扱った実験で、ここではvars()とtype(obj).__dict__で値の位置を見るために使う。データモデル文書は、クラス属性の参照がクラス辞書の検索に翻訳されると記し（C.xはC.__dict__["x"]）、クラスのインスタンスについては、インスタンスの辞書が属性参照を最初に検索する場所であり、そこになくてクラスに同名の属性があれば検索がクラス属性へ続くと記している。この二つの辞書の出力は次のとおりである。

class Cart:
                        items = []
                        label = 'cart'
                    
                    a = Cart()
                    b = Cart()
                    print('a.__dict__            :', a.__dict__)
                    print('vars(a)               :', vars(a))
                    print('Cart.__dict__ keys    :', [k for k in vars(Cart) if not k.startswith('__')])
                    print('type(a) is Cart       :', type(a) is Cart)
                    print('type(Cart.__dict__)   :', type(vars(Cart)).__name__)
                    print('a.items is Cart.items :', a.items is Cart.items)
                    a.items.append('x')
                    print('b.items               :', b.items)
a.__dict__            : {}
                    vars(a)               : {}
                    Cart.__dict__ keys    : ['items', 'label']
                    type(a) is Cart       : True
                    type(Cart.__dict__)   : mappingproxy
                    a.items is Cart.items : True
                    b.items               : ['x']

インスタンスaの辞書は空である。itemsとlabelはCartの辞書にしかない。a.items is Cart.itemsはTrueで、a経由でリストに値を足すとb.itemsにも見えた。どちらのインスタンスにもリストがないまま、二つのインスタンスがクラスのリスト一つを読んでいた。クラスの辞書はmappingproxyとして出力され、値の位置を見るにはvars(obj)とvars(type(obj))の二つの呼び出しで足りる。

  • vars(obj)はインスタンスの辞書を返す。空ならインスタンス属性はない。
  • vars(type(obj))はクラスの辞書を返す。名前がここにだけあればクラス属性である。
  • obj.name is type(obj).nameがTrueで、かつインスタンス辞書に名前がないとき、共有が確定する。
  • ここでisはリストのような可変オブジェクトにだけ使う。小さな整数や文字列でisの結果が実行方法によって分かれる件は、テストは通るのに本番だけ条件が合わない理由が扱っている。

読み取りは上へ上がり、書き込みはインスタンスで止まる

同じ名前の読み取りと書き込みは別の場所を見る。データモデル文書の文は「Attribute assignments and deletions update the instance's dictionary, never a class's dictionary」である。読み取りはインスタンスからクラスへ上がるが、インスタンスに対する代入と削除はインスタンスの辞書だけを書き換える。文字列の属性での出力は次のとおりで、この非対称が見える。

class Cart:
                        label = 'cart'
                    
                    a = Cart()
                    b = Cart()
                    a.label = 'mine'
                    print('a.__dict__ after set  :', a.__dict__)
                    print('a.label, b.label, Cart.label:', a.label, b.label, Cart.label)
                    del a.label
                    print('after del a.label     :', a.label, a.__dict__)
                    Cart.label = 'changed'
                    print('after Cart.label=...  :', a.label, b.label)
                    b.label = 'shadow'
                    Cart.label = 'again'
                    print('b shadowed, a not     :', b.label, a.label)
a.__dict__ after set  : {'label': 'mine'}
                    a.label, b.label, Cart.label: mine cart cart
                    after del a.label     : cart {}
                    after Cart.label=...  : changed changed
                    b shadowed, a not     : shadow again

a.label = 'mine'の後、aの辞書に項目ができ、Cart.labelは変わらなかった。del a.labelの後は辞書がふたたび空になり、a.labelはクラスの値に戻った。クラス側でCart.labelを変えると、自分の値を持たないaは追従し、最後の2行では自分の値を持つbはクラスの新しい値の影響を受けなかった。操作ごとに変わる場所を表にまとめる。

クラス側を変えたとき、追従するインスタンスとしないインスタンス

クラス属性に新しいオブジェクトを代入することと、既存のオブジェクトを書き換えることは、インスタンスへの及び方が違う。クラス側で名前を結び直し、一部のインスタンスに自分の値を持たせてからもう一度結び直した。

class Box:
                        items = []
                        n = 0
                    
                    a = Box()
                    b = Box()
                    Box.items = ['new']
                    print('class rebinding        :', a.items, b.items)
                    a.items = ['mine']
                    Box.items = ['newer']
                    print('after a has its own    :', a.items, b.items)
                    Box.n = 5
                    a.n += 1
                    Box.n = 9
                    print('a.n, b.n, Box.n        :', a.n, b.n, Box.n)
class rebinding        : ['new'] ['new']
                    after a has its own    : ['mine'] ['newer']
                    a.n, b.n, Box.n        : 6 9 9

Box.items = ['new']の直後は、両方のインスタンスが新しいリストを読んだ。クラス辞書の名前が指すオブジェクトが変わり、インスタンスには自分の値がなかったからである。次にa.items = ['mine']でaに自分の値を置いてクラスをもう一度変えると、aだけが追従しなかった。数値も同じである。Box.n = 5の後のa.n += 1は、読んだ5に1を足した6をaの辞書に入れ、その後のBox.n = 9ではb.nは9に追従したがa.nは6のままだった。

  • クラス属性の結び直しは、自分の値を持たないインスタンスにだけ広がる。
  • インスタンスが一度自分の値を持つと、その名前についてはクラス側の変更が届かない。
  • そのため、同じクラスの一部のインスタンスだけが新しい設定を読む現象は、どのインスタンスが自分の値を持つに至ったかに左右される。

+=が残すもの - 整数とリストの違い

整数の部分は既存の記事の第7節で扱った実験で、ここではvars()でインスタンス辞書に名前ができるかを見るために使う。self.count += 1は、読み取りと書き込みが一行に重なっている。右辺の読み取りはクラスまで上がり、左辺の書き込みはインスタンスで止まる。整数とリストに同じ演算を適用した。

class Counter:
                        hits = 0
                        log = []
                    
                    p = Counter()
                    q = Counter()
                    p.hits += 1
                    p.hits += 1
                    q.hits += 1
                    print('p.hits q.hits Counter.hits:', p.hits, q.hits, Counter.hits)
                    print('p.__dict__ :', p.__dict__)
                    p.log += ['p']
                    q.log += ['q']
                    print('p.log      :', p.log, ' Counter.log:', Counter.log)
                    print('p.log is Counter.log:', p.log is Counter.log)
                    print('p.__dict__ :', p.__dict__)
                    p.log = p.log + ['new']
                    print('after p.log = p.log + [...]:', p.log, Counter.log, p.log is Counter.log)
p.hits q.hits Counter.hits: 2 1 0
                    p.__dict__ : {'hits': 2}
                    p.log      : ['p', 'q']  Counter.log: ['p', 'q']
                    p.log is Counter.log: True
                    p.__dict__ : {'hits': 2, 'log': ['p', 'q']}
                    after p.log = p.log + [...]: ['p', 'q', 'new'] ['p', 'q'] False

整数側は期待どおり分かれた。p.hitsは2、q.hitsは1で、クラスの値は0である。名前hitsがpの辞書にできたからである。リスト側は違う。p.log += ['p']とq.log += ['q']の後、クラスのリストに両方の値が入っており、p.log is Counter.logはTrueである。それでもpの辞書にはlogができた。リストの+=は、クラスに付いたリストをその場で伸ばし、その結果として同じリストをインスタンスの名前に代入したものとして出力と合う。インスタンス辞書に名前が見えても、そのインスタンスがオブジェクトを所有したことにはならない。

最後の行のp.log = p.log + ['new']は新しいリストを作って代入するので、p.logはクラスのリストから離れた。クラス側のリストに'new'はなく、isはFalseである。

  • 整数の+=は新しいオブジェクトを作ってインスタンスに結ぶので、共有が解ける。
  • リストの+=は同じオブジェクトを伸ばして結び直すので、共有が残る。
  • x = x + [...]は新しいリストを作って結ぶので、共有が解ける。同じに見える二つの式が違う動きをする。
  • インスタンス辞書に名前があるかだけで判断せず、obj.name is type(obj).nameまで確かめる。

サブクラスは親のリストをそのまま使う

サブクラスでも同じ規則が続く。データモデル文書は、名前がクラス辞書になければ検索が基底クラスへ続くと記している。親一つと子二つについて、リストの位置の出力は次のとおりである。

class Base:
                        tags = []
                    
                    class Child(Base):
                        pass
                    
                    class Other(Base):
                        tags = ['own']
                    
                    c = Child()
                    o = Other()
                    bs = Base()
                    print('Child.tags is Base.tags :', Child.tags is Base.tags)
                    print('Other.tags is Base.tags :', Other.tags is Base.tags)
                    c.tags.append('from child instance')
                    print('Base.tags               :', Base.tags)
                    print('bs.tags                 :', bs.tags)
                    print('o.tags                  :', o.tags)
                    print("'tags' in vars(Child)   :", 'tags' in vars(Child))
                    print('MRO of Child            :', [k.__name__ for k in Child.__mro__])
Child.tags is Base.tags : True
                    Other.tags is Base.tags : False
                    Base.tags               : ['from child instance']
                    bs.tags                 : ['from child instance']
                    o.tags                  : ['own']
                    'tags' in vars(Child)   : False
                    MRO of Child            : ['Child', 'Base', 'object']

Childは自分の辞書にtagsを持たず、Child.tagsはBase.tagsと同じオブジェクトだった。子のインスタンス経由で値を足すと、親クラスと親のインスタンスにもその値が見えた。クラスを作るときにtagsを宣言し直したOtherは自分のリストを持ち、親の値と混ざらなかった。検索の順序は、MROの出力（Child, Base, object）のとおり子から親へ上がる。

  • サブクラスを作るだけでは、クラス属性のリストは複製されない。
  • サブクラス本体で同じ名前を宣言し直すと、そのサブクラスは自分のオブジェクトを持つ。
  • 親の属性をサブクラスごとに別々に持たせるには、サブクラスが作られる時点で新しく代入する必要がある。方法は第10節にある。

カウンターの二つの数え方 - type(self)とクラス名

クラス側のカウンターを増やすコードは、二通りに書かれる。インスタンスのクラスを指すtype(self)を使う方法と、クラス名を直接書く方法である。サブクラスが加わると結果が分かれる。

class Reg:
                        count = 0
                        def __init__(self):
                            type(self).count += 1
                    
                    class RegChild(Reg):
                        pass
                    
                    Reg(); Reg(); RegChild()
                    print('Reg.count, RegChild.count   :', Reg.count, RegChild.count)
                    print("'count' in vars(RegChild)   :", 'count' in vars(RegChild))
                    
                    class Reg2:
                        count = 0
                        def __init__(self):
                            Reg2.count += 1
                    
                    class Reg2Child(Reg2):
                        pass
                    
                    Reg2(); Reg2Child(); Reg2Child()
                    print('Reg2.count, Reg2Child.count :', Reg2.count, Reg2Child.count)
                    print("'count' in vars(Reg2Child)  :", 'count' in vars(Reg2Child))
Reg.count, RegChild.count   : 2 3
                    'count' in vars(RegChild)   : True
                    Reg2.count, Reg2Child.count : 3 3
                    'count' in vars(Reg2Child)  : False

type(self).count += 1は、読み取りで親の値2を取り、書き込みをRegChild自身の辞書に行った。その結果、RegChild.countは3になり、Reg.countは2のままだった。クラス名を直接書いたReg2.count += 1は、子のインスタンスを作っても親の辞書だけを書き換えて3の一つにまとまり、Reg2Childの辞書には名前ができなかった。

  • 全インスタンスの数を一つの値で数えるなら、クラス名を直接書く方が一つにまとまる。
  • サブクラスごとに別々に数えるならtype(self)を使うが、最初の書き込みは親の現在の値から始まることを踏まえる。
  • 二つの方式が一つのクラス階層に混ざると、同じ名前の値が親と子でずれる。

dataclassが見るもの - フィールド、ClassVar、可変の既定値

listのValueErrorは既存の記事の第7節で扱った実験で、ここではフィールドとClassVarの判定と並べて見る。dataclassはこの問題を宣言の段階で扱う。公式文書は、既定値がクラス属性として保存されることを指摘し、ハッシュできない既定値ならValueErrorを出すと記している。ハッシュできなければ可変だという仮定で、部分的な解決策だとみずから述べている。また、フィールドの型がtyping.ClassVarならフィールドから除外され、fields()が返さないとも記している。フィールド・ClassVar・注釈なしの属性を一つのクラスに置いた場合と、四種類の既定値を与えた場合の出力は次のとおりである。

from typing import ClassVar

                    class Plain:
                        name: str
                        tags: list = field(default_factory=list)
                        registry: ClassVar[dict] = {}
                        note = 'no annotation'
                    
                    p1 = Plain('a'); p2 = Plain('b')
                    print('fields          :', [f.name for f in fields(Plain)])
                    print('annotations     :', list(Plain.__annotations__))
                    print('registry shared :', p1.registry is p2.registry is Plain.registry)
                    print('tags shared     :', p1.tags is p2.tags)
                    print('p1.__dict__     :', p1.__dict__)
                    print('note is a field :', 'note' in [f.name for f in fields(Plain)], '/ Plain.note =', Plain.note)
                    try:
                        Plain('x', ['q'], {}, 'extra')
                    except TypeError as e:
                        print('TypeError       :', e)
                    
                    for kind, default in [('list', []), ('dict', {}), ('set', set()), ('tuple', ())]:
                        try:
                            @dataclass
                            class Probe:
                                x: object = default
                            print(kind, '-> accepted')
                        except ValueError as e:
                            print(kind, '-> ValueError:', e)

                    tags shared     : False

                    list -> ValueError: mutable default <class 'list'> for field x is not allowed: use default_factory

                    set -> ValueError: mutable default <class 'set'> for field x is not allowed: use default_factory

fields()にはnameとtagsだけが出た。registryは注釈にあるがClassVarなので外れ、注釈のないnoteは最初からフィールドではなく通常のクラス属性として残った。コンストラクタは引数を2つまでしか受けず、4つ渡すとTypeErrorになった。このメッセージはPython 3.13.3での出力で、メッセージの表記はバージョンによって異なる場合がある。tagsはインスタンスごとに別のリストで、registryはインスタンスとクラスが同じ辞書を指した。既定値の判定は表のとおりである。

  • ClassVarの注釈は共有を示すだけで防がない。registryが共有されたままなのが出力で見える。

__slots__とクラス属性の衝突

__slots__を使うクラスでは、同じ名前のクラス属性は許されない。データモデル文書の__slots__の節（3.3.2.4）は「class attributes cannot be used to set default values for slot variables; otherwise, the class attribute would overwrite the descriptor」と記している。

try:
                        class WithSlots:
                            __slots__ = ('x',)
                            x = 1
                    except ValueError as e:
                        print('ValueError:', e)
                    
                    class Ok:
                        __slots__ = ('x',)
                    o = Ok()
                    o.x = 1
                    print('slots instance has __dict__:', hasattr(o, '__dict__'))
ValueError: 'x' in __slots__ conflicts with class variable
                    slots instance has __dict__: False

クラスを作った瞬間にValueErrorになった。メッセージは、スロット名とクラス変数が衝突すると知らせる。スロットだけを宣言したクラスのインスタンスには__dict__がなかった。文書の文が言う範囲は、スロット変数の既定値をクラス属性で与えられないということで、この出力が示すのもその衝突と__dict__がないことまでである。スロット変数の既定値は__init__で代入する。

意図して共有する - サブクラスごとのレジストリと既定値のコピー

共有が意図であることもある。レジストリや既定の設定がそうである。このとき問題は共有そのものではなく、サブクラスまで同じオブジェクトを使うことになるかと、読む人が意図に気づけるかである。三つの形の出力は次のとおりである。前の二つはサブクラスが定義されるときに呼ばれる__init_subclass__を使い、一つはサブクラスごとに新しいリストを代入し、もう一つは親のリストに名前を集める。三つめは、クラス辞書の既定値をインスタンスがコピーして使う形である。

class Plugin:
                        registry = []
                        def __init_subclass__(cls, **kw):
                            super().__init_subclass__(**kw)
                            cls.registry = []          # each subclass gets its own list
                            Plugin.registry.append(cls.__name__)
                    
                    class A(Plugin): pass
                    class B(Plugin): pass
                    print('Plugin.registry :', Plugin.registry)
                    print('A.registry      :', A.registry, ' B.registry:', B.registry)
                    
                    class Shared:
                        registry = []
                        def __init_subclass__(cls, **kw):
                            super().__init_subclass__(**kw)
                            cls.registry.append(cls.__name__)
                    class C(Shared): pass
                    class D(Shared): pass
                    print('Shared.registry :', Shared.registry, C.registry is D.registry)
                    
                    # per-instance copy of a class-level default
                    class Config:
                        defaults = {'retries': 3}
                        def __init__(self, **over):
                            self.opts = {**type(self).defaults, **over}
                    c1 = Config(retries=5); c2 = Config()
                    print('c1.opts, c2.opts, defaults:', c1.opts, c2.opts, Config.defaults)
Plugin.registry : ['A', 'B']
                    A.registry      : []  B.registry: []
                    Shared.registry : ['C', 'D'] True
                    c1.opts, c2.opts, defaults: {'retries': 5} {'retries': 3} {'retries': 3}

Pluginは、サブクラスが定義されるたびにそのサブクラスへ空のリストを新しく代入した。A.registryとB.registryはそれぞれ別のリストで、親のリストにはサブクラス名が二つ集まった。Sharedはcls.registryに名前を足し、CとDは同じリストを指した。どちらも意図しだいで正しい設計だが、どちらなのかがコードから分かる必要がある。最後のConfigは、クラス辞書の既定値を読み取り専用の原本として置き、インスタンスごとに新しい辞書を作って上書きする値だけを載せた。c1で変えた値はc2とConfig.defaultsに広がらなかった。

  • 親に一つへ集めるなら親のリストに足し、サブクラスごとに別々に持つなら新しく代入する。
  • クラス属性を既定値の原本としてだけ読み、インスタンスがコピーを作れば、共有の事故は構造的に減る。
  • 意図した共有にはtyping.ClassVarの注釈を付け、インスタンス属性でないことを示す。typing文書は、これが実行時の動作を変えず、静的型チェッカーが利用できる印だと記している。

確認できていないこと

  • Python 3.13.3以外のバージョンでの動作。dataclassの可変既定値の判定がバージョンで違ったかは、実行で比較できていない。
  • プロパティやディスクリプタ（__get__・__set__）をクラス属性として置いたときの検索順序。上の実行は通常の値だけを扱った。
  • メタクラスやクラスデコレータが属性を書き換える場合。
  • mypyやpyrightのような静的型チェッカーがClassVarと通常のクラス属性を実際にどう報告するか。文書は利用できるとだけ記している部分である。
  • ハッシュ可能な可変オブジェクトをdataclassの既定値にしたときの動作。
  • 複数のスレッドがクラス属性のリストを同時に書き換えるときの安全性。
  • __init_subclass__の呼び出し規則は公式文書で確認しておらず、出力で示された動作だけを記した。
