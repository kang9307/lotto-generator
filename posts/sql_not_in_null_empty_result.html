NOT IN에 NULL 하나가 섞이면 결과가 통째로 빈다 - 에러 없이 0행이 되는 SQL 3값 논리

0행과 8행을 가른 것은 목록 안의 NULL 하나였다. SQLite와 DuckDB에서 직접 실행한 출력으로

2026-07-30 개발/인프라

서론: 조회 결과가 비었는데, 데이터는 분명히 있었다

운영 중인 서비스에서 「한 번도 환불을 요청하지 않은 고객」 목록을 뽑는 쿼리가 있었다. 어제까지 잘 나왔다. 오늘 돌리니 0행이다. 고객 테이블에는 여전히 수만 건이 들어 있고, 환불 요청 테이블도 멀쩡하다. 쿼리는 성공했다. 에러 메시지가 단 한 줄도 없다.

이 상황에서 사람이 가장 먼저 떠올리는 결론은 대개 이렇다. 「조건에 맞는 데이터가 없나 보다.」 그리고 그 결론은 화면에 아무것도 안 뜨는 대시보드, 아무에게도 안 나가는 발송 배치, 0으로 채워진 리포트가 되어 며칠씩 방치된다. 실패한 것이 아니라 성공한 채로 비어 있기 때문에 알림도 울리지 않는다.

범인은 대개 이 한 줄이다.

SELECT id, name FROM customers
WHERE id NOT IN (SELECT customer_id FROM refund_requests);

그리고 refund_requests.customer_id에 NULL이 딱 한 행 들어 있다. 그것으로 끝이다. 나머지 만 건이 아무리 정상이어도 결과는 0행이 된다.

이 글은 「NOT IN 쓰지 마세요」를 말하려는 것이 아니다. 왜 그렇게 설계됐고, 언제 무엇을 써야 하는가를 다룬다. 결론부터 말하면 이 동작은 버그가 아니라 논리적으로 옳은 결과다. 그 옳음이 하필 에러 없이 조용하게 나타나기 때문에 사고가 된다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 엔진은 SQLite 3.49.1(Python 3.13.3의 sqlite3 드라이버)과 DuckDB 1.5.5(PostgreSQL 계열 SQL 방언) 두 가지다. 두 엔진에서 같은 스크립트를 돌려 일치하는 지점과 갈라지는 지점을 구분했다. 규격에 대한 서술은 SQLite와 PostgreSQL 공식 문서로만 대조했고, 열어 확인하지 못한 엔진(MySQL, Oracle, SQL Server 등)에 대해서는 단정하지 않는다.

예제 스키마. customers 10행(id 1부터 10까지), refund_requests 4행이다. 요청 4건 중 1건만 customer_id가 NULL이다. 전부 가상의 테이블이며, 그대로 복사해 자기 DB에서 재현할 수 있다.

이 글이 다루지 않는 것. SQL 자체가 처음이라면 SQL 입문 가이드를 먼저 보라. 여기서는 NULL의 3값 논리 한 점만 파고든다. 조인의 ON과 WHERE 경계 문제는 이 글의 주제가 아니며, 5절과 6절의 NOT EXISTS·LEFT JOIN은 반조인 대안으로서만 다룬다.

1. 3분 재현 - 목록에 NULL 하나를 넣어 본다

말로 설명하기 전에 먼저 실행한다. 준비물은 10행짜리 테이블 하나다.

CREATE TABLE customers (
  id      INTEGER PRIMARY KEY,
  name    TEXT,
  region  TEXT,
  credit  INTEGER
);
INSERT INTO customers VALUES
 (1,'aria','seoul',300),(2,'brio','seoul',NULL),(3,'cedar','busan',150),
 (4,'delta','busan',NULL),(5,'echo','jeju',420),(6,'flux','seoul',90),
 (7,'gale','busan',NULL),(8,'hive',NULL,210),(9,'iris','jeju',60),
 (10,'juno',NULL,NULL);

이제 목록에 NULL을 하나 섞은 것과 뺀 것을 나란히 돌린다.

engine  : SQLite 3.49.1 (python sqlite3 driver, Windows)
python  : 3.13.3

--- 1-1. NOT IN with a literal NULL in the list ---
  SQL: SELECT id, name FROM customers WHERE id NOT IN (1, 2, NULL)
  rows returned: 0
  id | name

--- 1-2. exactly the same query, NULL removed from the list ---
  SQL: SELECT id, name FROM customers WHERE id NOT IN (1, 2)
  rows returned: 8
  id | name
  3 | cedar
  4 | delta
  5 | echo
  6 | flux
  7 | gale
  8 | hive
  9 | iris
  10 | juno

--- 1-3. no error was raised - both queries succeeded ---
  q1 status: OK (0 rows)
  q2 status: OK (8 rows)

0행과 8행. 두 쿼리의 차이는 목록 안의 NULL 하나뿐이다. 그리고 둘 다 정상 종료했다. 예외도, 경고도, 로그 한 줄도 없다.

같은 스크립트를 DuckDB 1.5.5에서도 돌렸다.

engine  : DuckDB 1.5.5 (PostgreSQL-family SQL dialect, Windows)

--- 1. basic reproduction ---
  NOT IN (1, 2, NULL) -> 0 rows
  NOT IN (1, 2)       -> 8 rows
  IN (1, 2, NULL)     -> 2 rows
  IN (1, 2)           -> 2 rows

숫자가 완전히 같다. 이것은 특정 엔진의 결함이 아니다. SQL 표준의 정의를 따른 결과이고, 그래서 어디서든 똑같이 재현된다.

2. IN은 왜 멀쩡한가

흥미로운 것은 IN이다. 완전히 같은 목록을 줬는데 IN은 정상 동작한다.

--- 2-1. IN with the same list ---
  SQL: SELECT id, name FROM customers WHERE id IN (1, 2, NULL)
  rows returned: 2
  id | name
  1 | aria
  2 | brio

--- 2-2. IN without the NULL ---
  SQL: SELECT id, name FROM customers WHERE id IN (1, 2)
  rows returned: 2
  id | name
  1 | aria
  2 | brio

NULL이 있든 없든 2행이다. 그러면 NOT IN은 왜 다른가. 답을 보려면 행마다 조건식이 실제로 어떤 값이 되는지 찍어 보면 된다. SQLite는 참을 1, 거짓을 0으로 표시하고, 세 번째 값은 NULL로 표시한다.

--- 2-3. the expression value per row (1 = true, 0 = false, NULL = unknown) ---
  id | in_expr | not_in_expr | in_clean | not_in_clean
  1 | 1 | 0 | 1 | 0
  2 | 1 | 0 | 1 | 0
  3 | NULL | NULL | 0 | 1
  4 | NULL | NULL | 0 | 1
  5 | NULL | NULL | 0 | 1
  6 | NULL | NULL | 0 | 1
  7 | NULL | NULL | 0 | 1
  8 | NULL | NULL | 0 | 1
  9 | NULL | NULL | 0 | 1
  10 | NULL | NULL | 0 | 1

이 표가 이 글의 핵심이다. not_in_expr 열을 세로로 읽어 보라. 값이 1인 칸이 단 하나도 없다. id 1과 2는 0(거짓), 나머지 8개 행은 전부 NULL이다. 반면 not_in_clean(NULL을 뺀 목록) 열에는 1이 8개 있다.

DuckDB는 같은 것을 진짜 불리언 타입으로 보여준다. 표기만 다를 뿐 구조는 동일하다.

--- 1-1. the expression value per row - booleans, not 1/0 ---
  id | in_expr | not_in_expr | not_in_clean
  1 | true | false | false
  2 | true | false | false
  3 | NULL | NULL | true
  4 | NULL | NULL | true
  5 | NULL | NULL | true
  ... (rows 6-10 identical in shape)

왜 이렇게 되는지는 다음 절에서 원리로 푼다.

3. NULL은 「없음」이 아니라 「모름」이다

대부분의 사람은 NULL을 「값이 비어 있음」으로 이해한다. 그래서 NULL = NULL이 참일 것 같고, 1 <> NULL이 참일 것 같다. 실제로 실행해 보면 그렇지 않다.

--- 3-1. comparisons against NULL ---
  eq | neq | null_eq_null | null_neq_null | gt | is_null | one_is_null
  NULL | NULL | NULL | NULL | NULL | 1 | 0

읽는 법: 1 = NULL은 NULL, 1 <> NULL도 NULL, NULL = NULL도 NULL, 1 > NULL도 NULL이다. 확정값을 준 것은 IS NULL뿐이다(NULL IS NULL은 1, 1 IS NULL은 0).

여기서 NULL은 「결과가 비었다」는 뜻이 아니라 세 번째 논리값 UNKNOWN이다. 타입을 찍어 보면 확실해진다.

--- 3-2. typeof() of each result - NULL is a value, not an error ---
  t_eq | t_true | t_false | t_nn
  null | integer | integer | null

참·거짓은 integer이고, NULL과의 비교 결과는 null 타입이다. 에러가 아니라 값이다. 그래서 아무 소리 없이 계산에 섞여 든다.

3.1 왜 이렇게 정의했나

NULL을 「모르는 값」으로 읽으면 전부 자연스러워진다.

  • 어떤 사람의 나이가 모른다. 그 나이가 30인가? 모른다. 거짓이 아니라 모른다. → age = 30은 UNKNOWN
  • 그 나이가 30이 아닌가? 이것도 모른다. → age <> 30도 UNKNOWN
  • 두 사람의 나이를 둘 다 모른다. 두 사람은 동갑인가? 모른다. → NULL = NULL도 UNKNOWN

「값이 없음」으로 읽으면 세 번째가 이상해 보이지만, 「모름」으로 읽으면 당연한 결론이다. 모르는 값 두 개가 같은지를 어떻게 단정하겠는가.

3.2 UNKNOWN이 AND와 OR를 통과하는 방식

--- 3-3. NOT of unknown is still unknown ---
  not_unknown | unknown_or_true | unknown_or_false | unknown_and_true | unknown_and_false
  NULL | 1 | NULL | NULL | 0

이 한 줄을 표로 펼치면 이렇다.

식결과왜
UNKNOWN OR TRUETRUEOR는 참이 하나면 확정된다
UNKNOWN OR FALSEUNKNOWN모름이 참일 수도 있으니 확정 불가
UNKNOWN AND TRUEUNKNOWN모름이 거짓일 수도 있으니 확정 불가
UNKNOWN AND FALSEFALSEAND는 거짓이 하나면 확정된다
NOT UNKNOWNUNKNOWN모르는 것의 반대도 모른다

규칙은 하나다. 결론을 확정할 수 있을 때만 확정되고, 나머지에서는 모름이 전염된다. 그리고 NOT UNKNOWN이 여전히 UNKNOWN이라는 점이 NOT IN을 죽인 결정타다.

3.3 WHERE는 TRUE만 통과시킨다

마지막 조각이다. 세 논리값이 필터에서 어떻게 취급되는지를 직접 세어 봤다.

--- 3-4. what WHERE does with each of the three values ---
  WHERE TRUE     -> 1 row(s)
  WHERE FALSE    -> 0 row(s)
  WHERE UNKNOWN  -> 0 row(s)
WHERE 절의 값그 행실행 확인
TRUE통과1행
FALSE탈락0행
UNKNOWN탈락0행

여기서 함정이 완성된다. UNKNOWN은 필터 단계에서 FALSE와 구분되지 않는다. 「모르겠다」와 「아니다」가 같은 대우를 받는다. 논리식 안에서는 셋을 구분하다가, 결과를 내보낼 때는 둘로 접는 것이다.

3.4 이제 NOT IN을 다시 읽는다

x NOT IN (1, 2, NULL)은 이렇게 풀린다.

x NOT IN (1, 2, NULL)
  = NOT (x IN (1, 2, NULL))
  = NOT (x = 1 OR x = 2 OR x = NULL)

x = 1  -->  NOT (TRUE  OR FALSE OR UNKNOWN) = NOT TRUE    = FALSE    -- 탈락
x = 7  -->  NOT (FALSE OR FALSE OR UNKNOWN) = NOT UNKNOWN = UNKNOWN  -- 탈락

어느 경로로 가도 TRUE가 나오지 않는다. 목록에 있으면 FALSE, 목록에 없으면 UNKNOWN. WHERE는 TRUE만 통과시키니 결과는 0행이다. 앞의 2-3 출력에서 1이 한 칸도 없었던 이유가 이것이다.

반대로 IN은 살아남는다. x = 1인 행에서 TRUE OR FALSE OR UNKNOWN = TRUE가 되기 때문이다. OR는 참 하나면 확정되므로, NULL이 끼어도 참을 만드는 경로가 막히지 않는다.

PostgreSQL 공식 문서도 이 동작을 명시적으로 규정한다. 좌변이 NULL이거나, 일치하는 우변 값이 없으면서 우변 행 중 하나라도 NULL을 내면 NOT IN의 결과는 참이 아니라 널이며, 이것은 널에 대한 SQL의 통상적인 불리언 결합 규칙에 부합한다고 적혀 있다. 즉 규격이 그렇게 정한 것이다.

4. 실무의 진짜 사고 지점 - NOT IN (SELECT ...)

리터럴 목록에 NULL을 직접 써 넣는 사람은 거의 없다. 사고는 서브쿼리에서 난다. 목록이 코드에 안 보이기 때문이다.

--- 0-1. refund_requests contents ---
  req_id | customer_id | amount
  101 | 1 | 5000
  102 | 2 | 3000
  103 | NULL | 7000
  104 | 1 | 1200

4행 중 단 한 행의 customer_id가 NULL이다. 이 상태에서 「환불을 요청한 적 없는 고객」을 뽑는다.

--- 4-1. customers who never requested a refund - the naive query ---
  SQL: SELECT id, name FROM customers WHERE id NOT IN (SELECT customer_id FROM refund_requests)
  rows returned: 0
  id | name

--- 4-2. how many NULLs are in that subquery column ---
  total | non_null | nulls
  4 | 3 | 1

--- 4-3. same query after deleting the single NULL row ---
  rows returned: 8
  id | name
  3 | cedar
  4 | delta
  ...
  10 | juno

--- 4-4. one NULL row is enough - inserting it back ---
  rows in rr_clean before insert : 3
  rows in rr_clean after insert  : 4
  NOT IN result now              : 0 rows
  after removing it again        : 8 rows

NULL 행을 지우면 8행, 다시 넣으면 0행, 또 지우면 다시 8행이다. 스위치처럼 동작한다.

4.1 규모는 아무 상관이 없다

「우리 테이블은 1만 건인데 NULL 하나쯤이야」라는 직관이 통하지 않는다는 것을 숫자로 확인했다.

=== B. one NULL among ten thousand rows ===
  blocklist rows                  : 10000   (values 1001..11000, none overlap customers)
  NULLs in blocklist.v            : 0
  SELECT id FROM customers WHERE id NOT IN (SELECT v FROM blocklist)
  rows returned                   : 10

  -- one single NULL row inserted --
  blocklist rows                  : 10001
  NULLs in blocklist.v            : 1
  NULL share of the table         : 1 / 10001 = 0.00999 percent
  rows returned                   : 0

  NOT EXISTS on the same table    : 10 rows
  LEFT JOIN / IS NULL             : 10 rows

1만 행 중 NULL 1행, 비율로 0.01퍼센트. 결과는 10행에서 0행이 됐다. 비율이 아니라 존재 여부가 전부다. 하나면 충분하고, 만 개여도 결과는 같다.

4.2 서브쿼리의 WHERE가 우연히 NULL을 가려 줄 때

더 고약한 경우가 있다. 서브쿼리에 붙은 다른 목적의 필터가 NULL을 우연히 걸러 내면, 쿼리는 멀쩡하게 동작한다. 그러다 그 필터를 손대는 순간 터진다.

=== B-2. a WHERE clause in the subquery can hide the NULL by accident ===
  NOT IN (SELECT v FROM blocklist)                             -> 0 rows
  NOT IN (SELECT v FROM blocklist WHERE v > 5000)              -> 10 rows
  NOT IN (SELECT v FROM blocklist WHERE v > 5000 OR v IS NULL) -> 0 rows

  the middle query works only because v > 5000 is UNKNOWN for the NULL row
  and therefore drops it. Change the filter and the query breaks again:
  NOT IN (SELECT v FROM blocklist WHERE v > 5000 OR v <= 5000)  -> 10 rows

가운데 쿼리가 10행을 낸 것은 v > 5000이 NULL 행에서 UNKNOWN이 되어 그 행이 서브쿼리 결과에서 이미 탈락했기 때문이다. 즉 NULL이 두 번 작용해서 우연히 상쇄됐다. 이런 쿼리는 조건 하나만 바꿔도 원인 모르게 0행이 된다.

4.3 바깥 컬럼이 NULL인 경우도 있다

지금까지는 목록 쪽 NULL만 봤다. 비교당하는 쪽 컬럼이 NULL이어도 그 행은 사라진다. 목록에는 NULL이 하나도 없는데도 그렇다.

=== D. SQLite: when the OUTER value is NULL ===
  rows: 3, one of them region = NULL
  WHERE region NOT IN ('seoul')  -> 1 rows
  id | region
  2 | busan
  the NULL-region row disappeared even though the list has no NULL
  WHERE region NOT IN ('seoul') OR region IS NULL -> 2 rows

3행 중 region이 NULL인 행이 하나 있었는데, 「서울이 아닌 지역」을 뽑았더니 1행만 나왔다. 지역을 모르는 고객은 「서울이 아니다」라고 단정할 수 없으므로 UNKNOWN이 되어 탈락한 것이다. 포함하려면 OR region IS NULL을 명시해야 하고, 그러면 2행이 된다. DuckDB에서도 숫자가 같았다.

5. 왜 아무도 눈치채지 못하나

이 버그의 진짜 무서움은 논리가 아니라 발견 실패에 있다. 세 겹으로 숨는다.

  • 에러가 없다. 예외도, 경고도, 느린 쿼리 로그도 없다. 모니터링이 잡을 신호 자체가 존재하지 않는다
  • 0행은 정상적인 결과처럼 보인다. 「조건에 맞는 데이터가 없다」와 구분되지 않는다
  • 개발 DB에서는 통과한다. 손으로 만든 픽스처에는 NULL이 없다
  • 코드는 아무 문제가 없어 보인다. 쿼리 문장만 읽으면 논리가 정확하다. 결과를 바꾸는 것은 코드가 아니라 그 순간 테이블에 들어 있는 값이다
  • 재현이 간헐적이다. NULL을 만든 행이 지워지면 쿼리가 다시 정상 동작하므로, 보고를 받고 확인할 때는 이미 멀쩡한 경우가 있다

세 번째를 숫자로 만들어 봤다.

=== B-3. the dev-versus-prod illusion ===
  dev fixture  (3 rows, hand-written, no NULL)       -> 10 rows   test PASSES
  prod data    (4 rows, one NULL from an old import) -> 0 rows    silently empty

테스트는 통과한다. 개발자가 손으로 적은 픽스처에는 NULL을 넣을 이유가 없기 때문이다. 반면 운영 DB의 NULL은 대개 예전 마이그레이션, 중단된 배치, 외부 연동 실패가 남긴 흔적이다. 코드 리뷰에서도 안 보인다. 서브쿼리가 무슨 값을 돌려주는지는 코드가 아니라 데이터가 결정하기 때문이다.

단위 테스트에 NULL이 든 픽스처를 한 줄 추가하는 것이, 이 버그에 대해서는 코드 리뷰 열 번보다 낫다.

6. 대안 하나 - NOT EXISTS는 죽지 않는다

같은 의도를 NOT EXISTS로 쓰면 어떻게 되는지 같은 데이터에서 돌렸다.

--- 5-1. the same intent written with NOT EXISTS ---
  SELECT c.id, c.name FROM customers c
  WHERE NOT EXISTS (SELECT 1 FROM refund_requests r WHERE r.customer_id = c.id)

  rows returned: 8
  id | name
  3 | cedar
  4 | delta
  5 | echo
  6 | flux
  7 | gale
  8 | hive
  9 | iris
  10 | juno

8행이다. 데이터는 그대로고 NULL도 그대로인데 결과가 나온다. 이유는 판정 기준이 다르기 때문이다.

  • NOT IN은 값들을 비교해 논리값을 만든다. 그래서 3값 논리의 지배를 받는다
  • NOT EXISTS는 안쪽 질의가 행을 하나라도 냈는지만 본다. 「있다/없다」는 두 값뿐이고 UNKNOWN이 낄 자리가 없다

NULL 행이 어떻게 되는지 직접 세어 봤다.

--- 5-3. why - the NULL row never matches r.customer_id = c.id ---
  id | matching_rows
  1 | 2
  2 | 1
  3 | 0
  4 | 0
  5 | 0
  6 | 0
  7 | 0
  8 | 0
  9 | 0
  10 | 0

customer_id가 NULL인 103번 요청은 어느 고객에도 붙지 않았다. NULL = 3이 UNKNOWN이라 매치가 안 되고, 매치가 안 되면 그냥 그 서브쿼리가 0행을 낼 뿐이다. NULL이 결론을 오염시키지 못하고 그 자리에서 멈춘다.

DuckDB에서도 같았다. 두 엔진 모두 NOT EXISTS 8행이다.

7. 대안 둘 - LEFT JOIN 뒤에 IS NULL

세 번째 표기법이다. 조인해서 매치 실패한 행만 남긴다.

--- 6-1. anti-join written as LEFT JOIN + IS NULL ---
  SELECT c.id, c.name FROM customers c
  LEFT JOIN refund_requests r ON r.customer_id = c.id
  WHERE r.req_id IS NULL

  rows returned: 8

--- 6-2. the three forms side by side, same table, same intent ---
  NOT IN (subquery)     -> 0 rows
  NOT EXISTS            -> 8 rows
  LEFT JOIN / IS NULL   -> 8 rows

세 줄이 이 글의 요약이다. 같은 데이터, 같은 의도, 같은 정답. 그런데 첫 번째만 0행이다.

7.1 이 표기법에도 함정이 있다

IS NULL을 어느 컬럼에 거는지가 정답과 오답을 가른다. 값이 NULL일 수 있는 일반 컬럼에 걸면 조용히 틀린다. 요청 104번의 amount를 NULL로 바꾸고 다시 돌려 봤다.

=== A. SQLite: the LEFT JOIN trap, done properly ===
  req_id | customer_id | amount
  101 | 1 | 5000
  102 | 2 | 3000
  103 | NULL | 7000
  104 | 1 | NULL

  WHERE r.req_id IS NULL  (primary key, never NULL in a matched row) -> 8 rows
  WHERE r.amount IS NULL  (nullable column - WRONG choice)           -> 9 rows

  the wrong version leaked customer 1, who DID request a refund:
  id | name | req_id | amount
  1 | aria | 104 | NULL
  3 | cedar | NULL | NULL
  4 | delta | NULL | NULL
  ...
  10 | juno | NULL | NULL

8행이어야 할 것이 9행이 됐고, 환불을 실제로 요청한 고객 1번이 「요청한 적 없는 고객」 목록에 섞여 들어갔다. 매치는 성공했는데 그 행의 amount가 마침 NULL이었기 때문이다.

규칙은 명확하다. IS NULL 검사는 조인 키나 기본키처럼 NULL이 절대 들어갈 수 없는 컬럼에만 건다. 매치된 행에서도 NULL일 수 있는 컬럼을 쓰면 「매치 실패」와 「매치했는데 값이 비었다」를 구분하지 못한다.

8. 방어법 - IS NOT NULL을 넣으면 되지 않나

가장 손쉬운 대응은 서브쿼리에 가드를 넣는 것이다. 실제로 동작한다.

--- 7-1. the defensive rewrite ---
  SELECT id, name FROM customers
  WHERE id NOT IN (SELECT customer_id FROM refund_requests WHERE customer_id IS NOT NULL)

  rows returned: 8

8행이 나온다. 그런데 이것을 근본 해결로 부르면 안 되는 이유가 셋 있다.

  • 반복해야 한다. NOT IN이 쓰인 모든 자리에 빠짐없이 붙여야 하고, 한 곳만 빠지면 그 쿼리는 조용히 0행이 된다. 사람이 매번 기억해야 하는 방어는 언젠가 실패한다
  • 보이지 않는다. 바깥 쿼리만 읽는 사람에게 이 가드는 안 보인다. 왜 붙었는지 모르니 리팩터링에서 지워지기 쉽다
  • 의미를 바꾼다. 그 NULL이 정보였다면 지우는 순간 사실이 사라진다

세 번째가 특히 중요하다. 예제에서 그 NULL이 무엇이었는지 보자.

--- 7-3. what the NULL actually meant here ---
  req_id | customer_id | amount
  103 | NULL | 7000
  a 7000 refund with no customer attached - dropping it hides a data bug

고객이 연결되지 않은 금액 7000짜리 환불 요청. 이것은 무시해도 되는 잡음이 아니라 어딘가에서 참조 무결성이 깨졌다는 증거다. IS NOT NULL로 걸러 내는 순간 그 사실은 영원히 리포트에서 사라진다.

그래서 순서는 이렇다.

  1. 그 NULL이 왜 거기 있는지 먼저 본다. SELECT * FROM t WHERE col IS NULL
  2. 들어오면 안 되는 값이면 컬럼에 NOT NULL과 외래키 제약을 걸어 원천 차단한다
  3. 들어올 수 있는 값이면 표기를 NOT EXISTS로 바꿔 NULL의 영향권 밖으로 나간다
  4. IS NOT NULL 가드는 급한 불을 끌 때만 쓰고, 왜 버려도 되는지 주석을 남긴다

9. NULL이 숨는 다른 자리 하나 - 집계 함수

NOT IN만 문제가 아니다. 같은 3값 논리가 집계에서는 다른 방식으로 나타난다. customers.credit 10행 중 4행이 NULL인 상태다.

--- 8-1. COUNT(*) vs COUNT(col) on customers.credit ---
  count_star | count_credit | count_distinct_credit | sum_credit | avg_credit | min_credit | max_credit
  10 | 6 | 6 | 1230 | 205.0 | 60 | 420

COUNT(*)는 10, COUNT(credit)은 6이다. 전자는 행을 세고 후자는 값이 있는 것만 센다. 그리고 평균의 분모가 어느 쪽인지가 실무에서 계속 문제가 된다.

--- 8-2. AVG denominator - it divides by the non-null count, not the row count ---
  s | n_nonnull | n_all | avg_builtin | s_div_nonnull | s_div_all
  1230 | 6 | 10 | 205.0 | 205.0 | 123.0

--- 8-3. COALESCE changes the answer, and that is the point ---
  avg_ignoring_nulls | avg_nulls_as_zero
  205.0 | 123.0

205.0과 123.0. 같은 데이터에서 나온 두 개의 「평균」이다. AVG(credit)은 1230을 6으로 나누고, AVG(COALESCE(credit, 0))은 1230을 10으로 나눈다.

어느 쪽이 맞는지는 NULL의 의미에 달렸다. 「한도를 아직 심사하지 않았다」면 분모에서 빼는 것이 맞고, 「한도가 0이다」면 넣는 것이 맞다. 둘 다 SQL이 대신 결정해 주지 않는다. 이것이 COALESCE 남용이 위험한 이유다. 눈앞의 NULL을 없애는 대신 측정 대상 자체를 바꿔 버린다.

빈 집합에서는 또 다르다.

--- 8-4. aggregates over an empty set ---
  c | s | a | m
  0 | NULL | NULL | NULL
  COUNT returns 0, SUM/AVG/MAX return NULL - a SUM of nothing is not 0

COUNT는 0을 주지만 SUM은 NULL을 준다. 「아무것도 없는 것의 합계는 0」이 상식 같지만 SQL은 그렇게 하지 않는다. 그래서 집계 결과를 그대로 애플리케이션 정수형에 넣으면 그 지점에서 널 참조가 난다. 방어하려면 COALESCE(SUM(x), 0)을 의식적으로 써야 한다. DuckDB에서도 동일했다.

식NULL 취급실행 확인값

COUNT(col)NULL을 뺀다6
SUM / MIN / MAXNULL을 무시1230 / 60 / 420
AVG(col)분모가 비NULL 개수205.0
AVG(COALESCE(col,0))분모가 전체 행 수123.0

10. NULL이 숨는 다른 자리 둘 - UNIQUE 제약

「이 컬럼은 UNIQUE니까 중복이 없다」는 문장이 NULL 앞에서 성립하지 않는다.

--- 9-1. inserting several NULLs into a UNIQUE column ---
  insert 'A' -> OK
  insert NULL -> OK
  insert NULL -> OK
  insert NULL -> OK
  insert 'A' again -> IntegrityError: UNIQUE constraint failed: u_test.code
  rows now: 4
  id | code
  1 | A
  2 | NULL
  3 | NULL
  4 | NULL

NULL 세 개가 전부 들어갔다. 반면 같은 문자열 'A'를 두 번째로 넣을 때는 정확히 거부됐다. 유일 제약이 NULL을 서로 다른 값으로 보기 때문이다. NULL = NULL이 UNKNOWN이니 「중복이다」라고 판정할 근거가 없는 것이다.

복합 UNIQUE에서도 마찬가지다.

--- 9-2. same thing on a multi-column UNIQUE ---
  insert ('x', 'y') -> OK
  insert ('x', NULL) -> OK
  insert ('x', NULL) -> OK
  insert (NULL, NULL) -> OK
  insert (NULL, NULL) -> OK
  rows now: 5

('x', NULL)이 두 번, (NULL, NULL)이 두 번 들어갔다. 총 5행 전부 삽입 성공이다. DuckDB 1.5.5에서도 NULL 세 개가 들어가고 'A' 중복만 거부됐다. 즉 두 엔진 모두 같다.

SQLite 공식 문서는 이 비일관성을 스스로 인정한다. UNIQUE 컬럼에서는 NULL이 서로 구별되지만 SELECT DISTINCT와 UNION에서는 구별되지 않는다고 명시하고, 이것이 다소 자의적이지만 Oracle·PostgreSQL·DB2와 동일하게 맞추기 위한 결정이었다고 적고 있다. 같은 엔진 안에서 규칙이 반대인 것이 의도된 상태다.

실무 함의. 「사업자번호는 UNIQUE니까 안심」이라고 썼는데 그 컬럼이 NULL을 허용한다면, 사업자번호가 비어 있는 행은 무제한으로 들어간다. 중복을 정말 막으려면 UNIQUE와 NOT NULL을 함께 걸어야 한다. 참고로 PostgreSQL 15부터는 UNIQUE에 NULL을 같은 값으로 취급하게 하는 선택지가 생겼다고 알려져 있으나, 이 글에서는 직접 실행해 확인하지 못했으므로 단정하지 않는다.

11. NULL이 숨는 다른 자리 셋 - GROUP BY와 DISTINCT

여기서 규칙이 뒤집힌다. =로는 같지 않은 NULL들이 그룹으로 묶을 때는 하나가 된다.

--- 10-1. GROUP BY region ---
  region | n
  busan | 3
  seoul | 3
  NULL | 2

  the two NULL-region rows landed in ONE group

--- 10-2. but = says they are not equal ---
  eq_test | is_test

--- 10-3. DISTINCT collapses NULLs the same way ---
  all_rows | distinct_region
  10 | 3
  region
  NULL
  busan
  jeju
  seoul

--- 10-4. UNION also dedupes NULLs ---
  n

12. NULL이 숨는 다른 자리 넷 - ORDER BY, 그리고 엔진마다 다른 지점

지금까지는 두 엔진의 숫자가 전부 일치했다. 여기서 갈린다. 같은 데이터를 같은 문장으로 정렬했는데 결과가 다르다.

SQLite 3.49.1
--- 11-1. default placement, ascending ---

  2 | NULL
  4 | NULL
  7 | NULL
  10 | NULL
  9 | 60
  6 | 90

SQLite는 오름차순에서 NULL을 맨 앞에, 내림차순에서 맨 뒤에 둔다. NULL을 모든 값보다 작은 것처럼 취급하는 것이다. DuckDB는 다르다.

  default_null_order | default_order
  NULLS_LAST | ASCENDING

DuckDB는 오름차순에서도 내림차순에서도 NULL을 맨 뒤에 둔다. 그리고 이것은 설정값이다. 바꿔 봤다.

  as shipped                         ORDER BY v ASC -> 1 5 9 NULL
  default_null_order = NULLS_FIRST

PostgreSQL 공식 문서는 또 다른 규칙을 규정한다. 널 값은 널이 아닌 어떤 값보다도 큰 것처럼 정렬되며, 따라서 NULLS FIRST가 DESC의 기본값이고 그 외에는 NULLS LAST가 기본값이라고 적혀 있다. 셋을 표로 모으면 이렇다.

세 엔진이 서로 다르다. 그리고 이 차이는 LIMIT과 만나는 순간 실제 사고가 된다. 「최신 1건」, 「상위 10건」, 페이지네이션의 첫 페이지 — 정렬 결과의 앞이나 뒤를 잘라 쓰는 코드는 엔진을 옮기거나 설정이 바뀌는 순간 조용히 다른 답을 낸다.

해법은 명시다. 두 엔진 모두 NULLS FIRST/NULLS LAST를 지원했다.

--- 11-3. explicit NULLS FIRST / NULLS LAST (SQLite 3.49.1) ---
  ORDER BY credit ASC NULLS FIRST     -> NULL NULL NULL NULL 60 90 150 210 300 420
  ORDER BY credit ASC NULLS LAST      -> 60 90 150 210 300 420 NULL NULL NULL NULL
  ORDER BY credit DESC NULLS FIRST    -> NULL NULL NULL NULL 420 300 210 150 90 60
  ORDER BY credit DESC NULLS LAST     -> 420 300 210 150 90 60 NULL NULL NULL NULL

이 구문을 지원하지 않는 엔진에서는 불리언 식을 정렬 키로 하나 더 얹는 우회가 통한다.

--- 11-4. the portable workaround when NULLS FIRST/LAST is unavailable ---
  SELECT id, credit FROM customers ORDER BY (credit IS NULL) ASC, credit ASC

  id | credit
  9 | 60
  6 | 90
  3 | 150
  8 | 210

참고로 정렬과 MIN/MAX는 서로 다르게 행동한다. 이것도 확인했다.

=== C. SQLite: where NULL sorts, and what MIN/MAX think ===
  ORDER BY v ASC  -> NULL 1 5 9
  ORDER BY v DESC -> 9 5 1 NULL
  min_v | max_v | n | n_nonnull
  1 | 9 | 4 | 3
  so NULL sorts as if smaller than every value, yet MIN() skips it entirely

정렬에서는 NULL이 가장 작은 값처럼 맨 앞에 오는데, MIN()은 그것을 아예 무시하고 1을 돌려준다. 「정렬해서 첫 행을 꺼내는 것」과 MIN()은 같지 않다.

13. 진단법 - 이미 있는 쿼리에서 이 위험을 찾아내기

원리를 알았으니 이제 이미 운영 중인 쿼리를 점검할 차례다. 순서가 있다.

13.1 1단계 - 30초 판정 SQL

의심되는 서브쿼리 컬럼에 대해 이것 하나만 돌리면 된다.

SELECT COUNT(*)                       AS total_rows,
       COUNT(the_column)              AS non_null,
       COUNT(*) - COUNT(the_column)   AS null_rows,
       CASE WHEN COUNT(*) = COUNT(the_column)
            THEN 'SAFE for NOT IN'
            ELSE 'DANGEROUS - NOT IN returns 0 rows' END AS verdict
FROM the_table;

예제 테이블에 돌린 결과다.

--- 12-1. does this subquery column contain NULL at all ---
  total_rows | non_null | null_rows | verdict
  4 | 3 | 1 | DANGEROUS - NOT IN will return 0 rows

--- 12-2. the same check on a NULL-free column ---
  total_rows | non_null | verdict
  4 | 4 | SAFE for NOT IN

판정 기준은 단순하다. COUNT(*)와 COUNT(컬럼)의 숫자가 다르면, 그 컬럼에 대한 모든 NOT IN은 이미 고장 나 있다. 이 판정은 DuckDB에서도 같은 결과를 냈다.

13.2 2단계 - 스키마가 보장하는지 확인

지금 NULL이 0건인 것과 스키마가 NULL을 금지하는 것은 완전히 다른 이야기다. 전자는 내일 깨진다.

--- 12-3. is the column even declared NOT NULL - read the schema ---
  name | type | notnull | pk
  req_id | INTEGER | 0 | 1
  customer_id | INTEGER | 0 | 0
  amount | INTEGER | 0 | 0

customer_id의 notnull이 0이다. 즉 스키마상 NULL이 허용된다. 오늘 NULL이 없어도 안전하다고 말할 수 없다. PostgreSQL 계열에서는 다음으로 같은 것을 본다.

SELECT column_name, is_nullable, data_type
FROM information_schema.columns
WHERE table_name = 'the_table';

13.3 3단계 - 그 NULL이 무엇이었는지 본다

지우기 전에 반드시 이것을 먼저 한다.

SELECT * FROM the_table WHERE the_column IS NULL LIMIT 20;

8절에서 봤듯이 그 NULL이 데이터 결함의 증거인 경우가 많다. 증상을 지우기 전에 원인을 본다.

13.4 4단계 - 세 표기를 나란히 돌려 숫자를 비교한다

가장 확실한 확인법이다. 같은 의도를 세 가지로 써서 숫자가 갈리는지 본다. 갈리면 NOT IN이 범인이다.

  step 1  SELECT COUNT(*) FROM t;                 -- 4
  step 2  SELECT COUNT(col) FROM t;               -- 3
  if the two numbers differ, every NOT IN against that column is already broken

13.5 5단계 - 실행 계획도 힌트를 준다

세 표기의 계획이 어떻게 다른지 찍어 봤다.

--- 13-7. query plan of the three anti-join forms (SQLite) ---
  NOT IN     : SCAN customers / USING INDEX ix_rr_cust FOR IN-OPERATOR
  NOT EXISTS : SCAN c / CORRELATED SCALAR SUBQUERY 1
               SEARCH r USING COVERING INDEX ix_rr_cust (customer_id=?)
  LEFT JOIN  : SCAN c
               SEARCH r USING COVERING INDEX ix_rr_cust (customer_id=?) LEFT-JOIN

셋 모두 인덱스를 쓴다. NOT EXISTS로 바꾸는 것이 성능을 희생하는 선택이 아니라는 뜻이다. 이 예제 규모에서는 계획의 형태만 다를 뿐 인덱스 활용은 동등했다. 참고로 IS NULL 조건도 인덱스로 처리됐다.

--- 13-6. index scan still finds NULLs - IS NULL is indexable here ---
  WHERE customer_id IS NULL : SEARCH refund_requests USING INDEX ix_rr_cust (customer_id=?)
  WHERE customer_id = 1     : SEARCH refund_requests USING INDEX ix_rr_cust (customer_id=?)

14. 그 밖의 함정 - CHECK, CASE, 문자열, 빈 집합

같은 원리가 나타나는 자리를 몇 개 더 확인했다.

14.1 CHECK 제약은 UNKNOWN을 통과시킨다

--- 13-2. CHECK constraint passes when the result is UNKNOWN ---
  insert qty=5 -> OK
  insert qty=NULL -> OK
  insert qty=-1 -> IntegrityError: CHECK constraint failed: qty > 0
  rows now: 2

CHECK (qty > 0)을 걸었는데 NULL이 통과했다. -1은 정확히 거부됐다. NULL > 0이 UNKNOWN이고, 제약 조건은 거짓일 때만 거부하기 때문이다. DuckDB에서도 같았다. 수량이 반드시 양수여야 한다면 CHECK만으로는 부족하고 NOT NULL을 따로 걸어야 한다.

14.2 CASE WHEN col = NULL은 절대 발화하지 않는다

--- 13-1. CASE WHEN col = NULL never fires ---
  id | credit | branch
  1 | 300 | has-value
  2 | NULL | matched-is
  10 | NULL | matched-is

WHEN credit = NULL THEN 'matched-eq' 가지는 한 번도 선택되지 않았다. NULL인 행조차 그 다음 가지인 WHEN credit IS NULL로 갔다. = NULL은 문법 오류가 아니라서 조용히 죽은 코드가 된다. 코드 리뷰에서 이 패턴을 보면 무조건 지적해야 하는 이유다.

14.3 문자열 결합 하나가 전체를 지운다

--- 13-3. string concatenation with NULL ---
  concat_result | with_coalesce
  NULL | fallback

'total: ' || NULL의 결과는 'total: '이 아니라 NULL 전체다. 리포트 문자열을 조립하다가 컬럼 하나가 비면 문장 전체가 사라진다. 이 자리가 COALESCE를 정당하게 쓰는 대표적인 경우다.

14.4 빈 목록에서는 NOT IN이 전부를 돌려준다

--- 13-5. an empty subquery makes NOT IN return everything ---
  NOT IN (SELECT customer_id FROM refund_requests WHERE 1=0) -> 10 rows
  NOT EXISTS on the same empty set                           -> 10 rows

서브쿼리가 0행이면 NOT IN은 전체 10행을 돌려준다. 논리적으로 맞다(아무것도 없는 목록에 속하지 않는 것은 전부다). 그런데 0행과 전체 행이라는 양극단 사이에 NULL 하나가 스위치로 놓여 있다는 점은 기억해 둘 만하다. 삭제 배치나 권한 필터에서 이 두 극단은 성격이 완전히 다른 사고를 만든다.

14.5 좌변이 NULL이면 IN도 NOT IN도 UNKNOWN

--- 13-4. NOT IN with NULL on the LEFT side ---
  left_null_notin | left_null_in
  NULL | NULL

4.3절에서 본 것의 축약이다. NULL NOT IN (1,2)도 NULL IN (1,2)도 둘 다 UNKNOWN이다. 목록에 NULL이 없어도 좌변이 NULL이면 그 행은 어느 쪽으로도 통과하지 못한다.

14.6 널 안전 비교 연산자

NULL끼리 같다고 판정하고 싶을 때 쓸 수 있는 연산자가 있다. SQLite 3.49.1에서 확인했다.

--- 3-5. null-safe comparison operators available here ---
  is_ | is_not | isnd | isnd2 | isd
  1 | 0 | 0 | 1 | 1
  • NULL IS NULL → 1(참). SQLite에서 IS는 널 안전 등호 역할을 한다
  • NULL IS NOT DISTINCT FROM NULL → 1(참). NULL끼리 같다고 본다
  • 1 IS NOT DISTINCT FROM NULL → 0(거짓). UNKNOWN이 아니라 확정된 거짓이다
  • 1 IS DISTINCT FROM NULL → 1(참)

DuckDB에서도 같은 결과였다(false, true, true). IS DISTINCT FROM 계열은 결과가 절대 UNKNOWN이 되지 않는다. 두 값이 「모름」을 포함하더라도 참이나 거짓 중 하나로 확정된다. 두 컬럼을 비교하면서 양쪽 NULL을 「같음」으로 처리해야 하는 변경 감지 로직에서 유용하다.

15. 판단 표 - 언제 무엇을 쓸 것인가

지금까지의 실행 결과를 하나의 표로 접는다. 이 표가 실무에서 쓰는 최종 산출물이다.

의도쓸 것이유와 주의점
서브쿼리 결과에 없는 행 찾기(가장 흔한 경우) NOT EXISTS NULL과 무관하게 동작한다. 의도가 문장으로 읽히고, 확인한 실행 계획상 인덱스도 그대로 쓴다. 기본값으로 삼을 것
반조인 + 상대 테이블 컬럼도 함께 SELECT LEFT JOIN ... IS NULL 조인 결과를 그대로 쓸 수 있다. IS NULL은 반드시 기본키나 조인 키에 — 일반 컬럼에 걸면 8행이 9행이 된다
하드코딩된 소수의 리터럴 제외 NOT IN ('a','b') 목록에 NULL이 없음이 눈으로 확인된다. 이 경우에 한해 안전하다
서브쿼리 컬럼이 NOT NULL로 선언됨 NOT IN도 가능 스키마가 보장한다. 단 스키마 변경 한 번에 깨진다. 주석으로 의존을 남길 것
NULL인 행도 결과에 포함하고 싶다 ... OR col IS NULL 명시 바깥 컬럼이 NULL이면 그 행도 탈락한다. 1행이 2행이 되는 차이
두 값을 NULL 포함해 같다/다르다로 판정 IS NOT DISTINCT FROM 결과가 UNKNOWN이 되지 않는다. 변경 감지·비교 로직에 적합
급한 불 끄기 WHERE col IS NOT NULL 가드 안전망이지 해결이 아니다. 모든 자리에 반복해야 하고, NULL이 정보였다면 사실이 사라진다

한 줄로 줄이면 이렇다. 집합에 없는 것을 찾을 때는 NOT EXISTS를 기본값으로 두고, NOT IN은 목록이 리터럴이거나 컬럼이 NOT NULL로 선언되었을 때만 쓴다.

16. 정리 - 이것은 버그가 아니다

이 글에서 확인한 것을 다시 세어 본다.

  • 목록에 NULL 하나 → 0행. 빼면 8행. 두 쿼리 모두 에러 없이 성공
  • 같은 목록에서 IN은 2행으로 정상 동작
  • 행별 조건식 값에 1이 단 하나도 없음. 거짓 2개, 나머지 8개는 전부 UNKNOWN
  • 1만 행 중 NULL 1행(0.01퍼센트)만으로 10행이 0행이 됨
  • NOT EXISTS 8행, LEFT JOIN IS NULL 8행, NOT IN만 0행
  • LEFT JOIN에서 검사 컬럼을 잘못 고르면 9행이 되어 오답이 섞임
  • 개발 픽스처 10행 통과, 운영 데이터 0행 — 테스트로 못 잡음
  • 평균이 205.0과 123.0 두 개, 빈 집합의 SUM은 NULL
  • UNIQUE 컬럼에 NULL 3개 삽입 성공, CHECK (qty > 0)에 NULL 삽입 성공
  • ORDER BY의 NULL 위치가 세 엔진에서 서로 다름

이 모든 것이 하나의 정의에서 나온다. NULL은 「값이 없음」이 아니라 「모름」이다. 모르는 값이 목록 안에 있는지 없는지 단정할 수 없으니 UNKNOWN이고, WHERE는 TRUE만 통과시키니 0행이다. SQL은 틀린 답을 내느니 아무 답도 내지 않기를 선택한 것이다. 그것이 이 설계의 일관성이다.

문제는 그 일관성이 에러 없이 나타난다는 데 있다. 타입 오류라면 컴파일에서 잡히고, 구문 오류라면 실행에서 잡힌다. 그런데 이것은 성공한 채로 비어 있다. 그래서 사람이 「데이터가 없나 보다」로 넘긴다.

대응은 두 줄로 끝난다. 첫째, 집합에 없는 것을 찾을 때는 NOT EXISTS를 기본값으로 둔다. 둘째, 테스트 픽스처에 NULL을 한 줄 넣는다. 두 번째가 특히 값싸고 강력하다. 이 글의 모든 실패 사례는 NULL이 든 픽스처 한 줄이면 배포 전에 잡혔을 것이다.

자주 묻는 질문

Q. NOT IN 결과가 0행인데 에러가 없다. 왜 그런가?

목록이나 서브쿼리 결과 안에 NULL이 하나라도 있으면 그렇게 된다. 확인한 결과, 10행 테이블에서 id NOT IN (1, 2, NULL)은 0행, NULL만 뺀 id NOT IN (1, 2)는 8행이었고 둘 다 정상 종료했다. SQL의 논리값이 참·거짓 둘이 아니라 참·거짓·모름 셋이기 때문이다. NULL과의 비교는 전부 모름이 되고, NOT 모름도 여전히 모름이며, WHERE는 참만 통과시킨다. 문법 오류가 아니라 정의대로 계산한 결과라 에러가 나지 않는다.

Q. IN은 잘 되는데 NOT IN만 안 되는 이유는?

일치하는 행에서 참이 나오는지가 갈린다. IN (1, 2, NULL)은 2행, NULL을 뺀 것도 2행으로 같았다. IN은 등호 비교를 OR로 이은 것이고, OR는 참이 하나면 나머지가 모름이어도 참으로 확정된다. 반대로 NOT IN에서는 어떤 행도 참이 되지 못한다. 행별 값을 찍어 보니 id 1과 2에서 0, 나머지 8개 행은 전부 NULL이었다. 참이 단 한 칸도 없었다.

Q. NOT EXISTS로 바꾸면 정말 해결되나?

해결된다. 같은 데이터에서 NOT IN 0행, NOT EXISTS 8행, LEFT JOIN IS NULL 8행이었다. NOT EXISTS는 값 비교가 아니라 행의 존재 여부만 보므로 UNKNOWN이 낄 자리가 없다. 참조 컬럼이 NULL인 행은 등호를 만족하지 못해 그냥 매치되지 않을 뿐이고, 실제로 고객별 매칭 행 수를 세어 보니 그 행은 어느 고객에도 붙지 않았다. 다만 LEFT JOIN 형태에는 별도 함정이 있어서, IS NULL을 기본키가 아닌 일반 컬럼에 걸었더니 9행이 나오며 오답이 섞였다.

Q. 서브쿼리에 IS NOT NULL을 넣으면 되는 것 아닌가?

동작은 한다(8행). 그러나 안전망이지 해결이 아니다. 첫째, NOT IN이 쓰인 모든 자리에 반복해야 하고 한 곳만 빠지면 그 쿼리는 조용히 0행이 된다. 둘째, 바깥 쿼리만 읽는 사람에게 보이지 않아 리팩터링에서 지워지기 쉽다. 셋째, 그 NULL이 정보였다면 의미가 바뀐다. 예제에서 그 행은 고객이 연결되지 않은 금액 7000짜리 요청, 즉 참조 무결성이 깨진 증거였다. 근본 대책은 NOT NULL 제약을 걸거나 표기를 NOT EXISTS로 바꾸는 것이다.

Q. NULL 때문에 조용히 틀리는 다른 자리는 어디인가?

적어도 다섯 군데를 실행으로 확인했다. 집계에서 COUNT(*)는 10인데 COUNT(credit)은 6이었고 평균이 205.0과 123.0으로 갈렸다. 빈 집합에서 COUNT는 0이지만 SUM·AVG·MAX는 NULL이었다. UNIQUE 제약에는 NULL이 3개나 들어갔다. GROUP BY에서는 =로 같지 않은 NULL들이 한 그룹이 됐다. ORDER BY에서는 SQLite가 NULL을 오름차순 맨 앞에, DuckDB가 맨 뒤에 놓아 엔진마다 답이 달랐다.

## 0. 증상 카드 — 이 글이 필요한 상황

- 쿼리는 성공했다. **에러가 없다.**
- 그런데 결과가 **0행**이다.
- 어제까지는 나왔다. 또는 개발 DB에서는 나온다.
- 쿼리 안에 `NOT IN (SELECT ...)` 가 있다.

## 1. 3값 논리 진리표

SQL 의 논리값은 TRUE / FALSE 두 개가 아니라 **TRUE / FALSE / UNKNOWN 세 개**다.

### 1-1. 비교 연산자가 NULL 을 만나면

| 식 | 결과 | 비고 |
|---|---|---|
| `1 = 1` | TRUE | |
| `1 = 2` | FALSE | |
| `1 = NULL` | **UNKNOWN** | FALSE 가 아니다 |
| `1 <> NULL` | **UNKNOWN** | TRUE 가 아니다 |
| `NULL = NULL` | **UNKNOWN** | 같지 않다고도 못 한다 |
| `1 > NULL` | **UNKNOWN** | 모든 비교 연산자가 동일 |
| `NULL IS NULL` | TRUE | `IS` 만이 확정값을 준다 |
| `1 IS NULL` | FALSE | |

### 1-2. AND / OR / NOT

| 식 | 결과 |
|---|---|
| `UNKNOWN OR TRUE` | **TRUE** |
| `UNKNOWN OR FALSE` | UNKNOWN |
| `UNKNOWN AND TRUE` | UNKNOWN |
| `UNKNOWN AND FALSE` | **FALSE** |
| `NOT UNKNOWN` | **UNKNOWN** |

읽는 법: OR 는 TRUE 하나면 확정된다. AND 는 FALSE 하나면 확정된다. **그 외에는 모름이 전염된다.**

### 1-3. WHERE 는 TRUE 만 통과시킨다

| WHERE 절의 값 | 그 행 |
|---|---|
| TRUE | 통과 |
| FALSE | 탈락 |
| **UNKNOWN** | **탈락** |

UNKNOWN 이 FALSE 처럼 취급되는 이 규칙 하나가 모든 사고의 출구다.

### 1-4. 그래서 IN 은 살고 NOT IN 은 죽는다

`x IN (a, b, c)` 는 `x = a OR x = b OR x = c` 로 풀린다.

| 상황 | `IN (1, 2, NULL)` | `NOT IN (1, 2, NULL)` |
|---|---|---|
| x = 1 (목록에 있음) | `TRUE OR ... OR UNKNOWN` = **TRUE** → 통과 | `NOT TRUE` = **FALSE** → 탈락 |
| x = 7 (목록에 없음) | `FALSE OR FALSE OR UNKNOWN` = **UNKNOWN** → 탈락 | `NOT UNKNOWN` = **UNKNOWN** → 탈락 |

- `IN` 은 일치하는 행에서 TRUE 가 나오므로 **정상 동작한다.**
- `NOT IN` 은 어떤 행에서도 TRUE 가 나오지 않는다. 일치하면 FALSE, 불일치하면 UNKNOWN. **그래서 항상 0행이다.**

## 2. 세 가지 반조인 비교표

「A 에는 있고 B 에는 없는 것」을 구하는 세 가지 표기. 같은 데이터(고객 10행, 요청 4행 중 참조컬럼 NULL 1행)에서 실행한 결과다.

| 표기 | 결과 | NULL 안전 | 판정 기준 | 주의점 |
|---|---|---|---|---|
| `NOT IN (SELECT col FROM t)` | **0행** | ❌ | 3값 논리 | col 에 NULL 이 하나라도 있으면 전멸. 에러 없음 |
| `NOT EXISTS (SELECT 1 FROM t WHERE t.col = a.id)` | **8행** | ✅ | 행의 존재 여부 | NULL 행은 `=` 를 만족하지 못해 그냥 매치 안 됨 |
| `LEFT JOIN t ON t.col = a.id WHERE t.pk IS NULL` | **8행** | ✅ | 매치 실패한 행 | **`IS NULL` 검사는 반드시 NOT NULL 컬럼(PK)에** |

`NOT IN` 만 다른 답을 냈다. 나머지 둘은 같다.

### 2-1. LEFT JOIN 형태의 함정

`WHERE` 에서 검사할 컬럼을 잘못 고르면 조용히 틀린다.

| 검사 컬럼 | 결과 | 판정 |
|---|---|---|
| `r.req_id IS NULL` (PK, 매치된 행이면 절대 NULL 아님) | 8행 | 정답 |
| `r.amount IS NULL` (값이 NULL 일 수 있는 일반 컬럼) | **9행** | 오답 — 실제로 요청한 고객이 섞여 나옴 |

**규칙: LEFT JOIN 반조인의 `IS NULL` 은 조인 키 또는 기본키에만 건다.**

### 2-2. 의도별 판단표

| 하려는 것 | 쓸 것 | 이유 |
|---|---|---|
| 서브쿼리 결과에 없는 행 찾기 | **`NOT EXISTS`** | NULL 무관, 의도가 문장으로 읽힘 |
| 반조인 + 상대 테이블 컬럼도 SELECT 해야 함 | **`LEFT JOIN ... IS NULL`** | 조인 결과를 그대로 쓸 수 있음 |
| 하드코딩된 소수의 리터럴 목록 제외 | `NOT IN ('a','b')` | 리터럴에 NULL 이 없음이 눈으로 확인됨 |
| 서브쿼리 컬럼이 **`NOT NULL` 로 선언**되어 있음 | `NOT IN` 도 가능 | 단 스키마 변경으로 언제든 깨질 수 있음 |
| 「값이 NULL 인 행도 결과에 포함」이 의도 | `... OR col IS NULL` 을 **명시** | 바깥 컬럼이 NULL 이면 그 행도 탈락한다 |

## 3. 진단 SQL — 그대로 붙여 쓰기

### 3-1. 이 컬럼이 NOT IN 에 안전한가 (30초)

```sql
SELECT COUNT(*)                       AS total_rows,
       COUNT(the_column)              AS non_null,
       COUNT(*) - COUNT(the_column)   AS null_rows,
       CASE WHEN COUNT(*) = COUNT(the_column)
            THEN 'SAFE for NOT IN'
            ELSE 'DANGEROUS - NOT IN returns 0 rows' END AS verdict
FROM the_table;
```

`COUNT(*)` 와 `COUNT(컬럼)` 의 숫자가 **다르면 그 컬럼에 대한 모든 `NOT IN` 은 이미 고장 나 있다.**

### 3-2. 스키마가 NOT NULL 을 보장하는가

```sql
-- SQLite
SELECT name, type, "notnull", pk FROM pragma_table_info('the_table');

-- PostgreSQL 계열
SELECT column_name, is_nullable, data_type
FROM information_schema.columns
WHERE table_name = 'the_table';
```

`is_nullable = 'NO'` (또는 SQLite `notnull = 1`) 가 아니면 **지금 NULL 이 0건이어도 안전하지 않다.** 내일 들어온다.

### 3-3. NULL 이 실제로 무엇을 의미했는지 보기

```sql
SELECT * FROM the_table WHERE the_column IS NULL LIMIT 20;
```

지우기 전에 이걸 먼저 본다. NULL 이 **데이터 버그의 증거**인 경우가 많다. 예제에서는 고객이 연결되지 않은 환불 요청이었다.

### 3-4. 셋 다 돌려서 숫자를 비교한다

```sql
SELECT 'not_in'     AS form, COUNT(*) AS n FROM (
  SELECT id FROM customers WHERE id NOT IN (SELECT customer_id FROM refund_requests)
)
UNION ALL
SELECT 'not_exists', COUNT(*) FROM (
  SELECT c.id FROM customers c
  WHERE NOT EXISTS (SELECT 1 FROM refund_requests r WHERE r.customer_id = c.id)
)
UNION ALL
SELECT 'left_join', COUNT(*) FROM (
  SELECT c.id FROM customers c
  LEFT JOIN refund_requests r ON r.customer_id = c.id
  WHERE r.req_id IS NULL
);
```

세 숫자가 다르면 첫 번째가 범인이다.

### 3-5. 바깥 컬럼이 NULL 인 경우도 잊지 말 것

목록에 NULL 이 없어도, **비교당하는 쪽 컬럼**이 NULL 이면 그 행은 탈락한다.

```sql
-- region 이 NULL 인 행은 이 조건에서 사라진다
SELECT * FROM t WHERE region NOT IN ('seoul');

-- 포함하려면 명시해야 한다
SELECT * FROM t WHERE region NOT IN ('seoul') OR region IS NULL;
```

## 4. NULL 이 숨는 다른 자리 — 요약표

| 자리 | 동작 | 실행 확인값(예제 10행, NULL 4개) |
|---|---|---|
| `COUNT(*)` | 행을 센다 | 10 |
| `COUNT(col)` | **NULL 을 뺀다** | 6 |
| `SUM` / `AVG` / `MIN` / `MAX` | **NULL 을 무시한다** | AVG = 205.0 |
| `AVG(COALESCE(col, 0))` | NULL 을 0 으로 센다 | **123.0** — 답이 달라진다 |
| 빈 집합의 `SUM` / `AVG` / `MAX` | **NULL 반환** (0 아님) | NULL |
| `UNIQUE` 제약 | **NULL 은 여러 개 허용** | NULL 3개 삽입 성공 |
| `GROUP BY` | **NULL 끼리 한 그룹** | NULL 그룹 1개(2행) |
| `SELECT DISTINCT` / `UNION` | **NULL 을 중복 제거** | distinct 3개 |
| `CHECK` 제약 | 결과가 UNKNOWN 이면 **통과** | `CHECK (qty > 0)` 에 NULL 삽입 성공 |
| `CASE WHEN col = NULL` | **절대 발화하지 않음** | 반드시 `IS NULL` |
| 문자열 결합 `'a' \|\| NULL` | **NULL** | 전체가 사라진다 |

`UNIQUE` 는 NULL 을 서로 다르다고 보고, `DISTINCT` 는 같다고 본다. **같은 엔진 안에서 규칙이 반대다.**

## 5. ORDER BY 의 NULL 위치 — 엔진마다 다르다

| 엔진 | `ORDER BY col ASC` | `ORDER BY col DESC` | 근거 |
|---|---|---|---|
| SQLite 3.49.1 | **NULL 먼저** | NULL 나중 | 실행 확인 |
| DuckDB 1.5.5 (기본 설정) | NULL 나중 | **NULL 나중** | 실행 확인 |
| PostgreSQL | NULL 나중 | **NULL 먼저** | 공식 문서 |

세 엔진이 서로 다르다. **`ORDER BY` 결과의 앞뒤를 잘라 쓰는 코드(LIMIT, 페이지네이션, 최신값 1건)는 엔진을 옮기는 순간 조용히 답이 바뀐다.**

이식 가능한 해법:

```sql
-- NULLS FIRST / NULLS LAST 를 명시 (SQLite 3.30+, PostgreSQL, DuckDB 지원)
SELECT * FROM t ORDER BY col ASC NULLS LAST;

-- 지원하지 않는 엔진에서의 우회
SELECT * FROM t ORDER BY (col IS NULL) ASC, col ASC;
```

## 6. 코드리뷰 점검 문장 — 그대로 복사해 쓰기

리뷰 코멘트에 붙일 수 있게 문장 형태로 정리했다.

- [ ] **이 `NOT IN` 의 서브쿼리 컬럼이 `NOT NULL` 로 선언되어 있는지 스키마에서 확인했나요?** 값이 지금 없는 것과 스키마가 금지하는 것은 다릅니다.
- [ ] **`NOT IN (SELECT ...)` 을 `NOT EXISTS` 로 바꿀 수 있나요?** 바꿀 수 있다면 바꾸는 편이 안전합니다. 성능도 대개 같거나 낫습니다.
- [ ] **`WHERE col IS NOT NULL` 가드를 서브쿼리에 넣었다면, 그 NULL 을 버려도 되는 이유가 주석에 있나요?** 가드는 증상을 가리는 것이지 원인을 고치는 것이 아닙니다.
- [ ] **LEFT JOIN 반조인의 `IS NULL` 이 기본키나 조인 키에 걸려 있나요?** NULL 이 들어갈 수 있는 일반 컬럼에 걸면 매치된 행이 결과에 섞입니다.
- [ ] **비교당하는 바깥 컬럼이 NULL 일 수 있나요?** 그렇다면 그 행이 결과에서 빠지는 것이 의도인지 확인하고, 아니라면 `OR col IS NULL` 을 명시하세요.
- [ ] **`= NULL` 또는 `<> NULL` 로 쓴 조건이 있나요?** 항상 UNKNOWN 입니다. `IS NULL` / `IS NOT NULL` 로 바꾸세요.
- [ ] **`COUNT(col)` 과 `COUNT(*)` 중 의도한 쪽을 썼나요?** 전자는 NULL 을 빼고 셉니다.
- [ ] **`AVG` 의 분모가 전체 행 수여야 하나요, NULL 을 뺀 수여야 하나요?** 기본은 후자입니다. 전자를 원하면 `COALESCE` 로 명시하세요.
- [ ] **`ORDER BY` 결과를 `LIMIT` 으로 자르고 있다면 `NULLS FIRST/LAST` 를 명시했나요?** 엔진 기본값이 서로 다릅니다.
- [ ] **테스트 픽스처에 NULL 이 들어 있나요?** 손으로 만든 픽스처에는 대개 NULL 이 없어서, 이 버그는 테스트를 통과하고 운영에서만 터집니다.
- [ ] **`UNIQUE` 로 중복을 막았다고 썼다면, 그 컬럼이 NULL 일 때도 막히나요?** 대부분의 엔진에서 NULL 은 여러 개 들어갑니다.
- [ ] **`CHECK` 제약이 NULL 도 막아준다고 가정하고 있나요?** 조건이 UNKNOWN 이면 통과합니다. `NOT NULL` 을 따로 거세요.

## 7. 한 문단 요약

`NOT IN` 은 고장 난 기능이 아니다. NULL 이 「모름」이라는 정의를 끝까지 지킨 결과다. **모르는 값이 목록 안에 있는지 없는지 단정할 수 없으므로 UNKNOWN 이고, WHERE 는 TRUE 만 통과시키므로 0행이다.** 논리적으로 옳다. 문제는 이 옳음이 **에러 없이** 나타나서 「데이터가 없나 보다」로 넘어가게 만든다는 것이다. 그래서 규칙은 하나다 — **집합에 없는 것을 찾을 때는 `NOT EXISTS` 를 기본값으로 두고, `NOT IN` 은 목록이 리터럴이거나 컬럼이 `NOT NULL` 로 선언되었을 때만 쓴다.**
