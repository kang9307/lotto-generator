The Real Purpose of Code Review — Finding Code That Will Be Hard to Maintain

Why bug hunting is the wrong yardstick, and how review protects your future self and teammates

2026-07-04 Dev & Infra

Introduction: Code Review Is Not a Bug Hunt

Ask most developers to review a pull request, and their reflex is to hunt for bugs: is a condition flipped, is there an off-by-one error, is a null check missing. If nothing jumps out, they click approve and move to the next PR. This piece questions that reflex itself. As of July 2026, a topic discussed on GeekNews (news.hada.io) argues that the primary purpose of code review is not catching bugs but finding code that will become hard to maintain. What makes this framing worth taking seriously is that it isn't just an opinion — it lines up with empirical research on what review actually accomplishes.

Over several years of reviewing and being reviewed across different teams, I've repeatedly seen a paradox: the pressure to "catch the bug" actually degrades review quality. Since catching 100% of bugs is an unachievable bar to begin with, reviewers either skim and rubber-stamp out of resignation, or fixate on trivial nits and burn time on the wrong things. This piece is my own analysis of why maintainability is a far clearer, more achievable lens for a reviewer, and how that lens should actually play out in practice.

1. The Real Purpose of Code Review — Maintainability, Not Bug Hunting

Start with the data. The 2013 Microsoft Research study "Code Reviews Do Not Find Bugs" (Bacchelli & Bird) analyzed a large volume of internal Microsoft review comments. The result was counterintuitive: the vast majority of comments were about code improvement, alternative solutions, documentation, and readability — not functional defects. There was a clear mismatch between what developers and managers expected review to deliver (critical bug detection) and what it actually delivered (low-level defects and maintainability gains).

1.1 Google Arrived at the Same Conclusion

Google's internal engineering guidance, eng-practices, states this explicitly. The primary standard isn't "is this code perfect" but "does this change improve the overall health of the codebase". Instead of stalling approval while demanding perfection, reviewers should accept a change as progress if it leaves the codebase better than it was yesterday. This standard is quietly radical — it redefines the reviewer's role from "defect detector" to "codebase curator."

1.2 The Question GeekNews Raised

The topic that surfaced on GeekNews in early July 2026 pushes this a step further: when a reviewer struggles to understand a piece of code, that struggle is itself the signal. If the reviewer is spending time trying to follow the logic right now, whoever has to fix it months later — possibly the original author — will hit the same wall. Bugs get filtered somewhat by tests and production monitoring; code that's hard to understand is caught only by a human reading it. Interestingly, pushback on that same discussion argued that narrowing review down to maintainability alone misses other functions review serves — knowledge sharing, security checks, design validation, team mentoring. I think both sides have a point. It's more accurate to call maintainability the primary purpose, not the only one.

1.3 Why This Framing Is Practical for Reviewers

"Find the bugs" hands the reviewer an effectively unbounded responsibility — how can anyone guarantee this code will never break in production? "Flag whatever you don't understand" is something a reviewer can actually execute. Getting stuck while reading the code is, by itself, grounds for a comment. Because it requires no extra domain knowledge or environment reproduction, this framing makes review meaningfully more actionable.

2. What "Hard-to-Maintain Code" Actually Looks Like

To apply this in practice, "hard to maintain" needs to be broken into concrete signals. Here are four I actually check for during review.

2.1 Readability — Time to Comprehension

Readability isn't taste, it's a measurable cost. Whether a function takes 30 seconds or 5 minutes to understand directly compounds into the cumulative time every future maintainer who reads it twenty more times will spend. Conditionals nested five levels deep, functions that don't fit on one screen, and calculations riddled with magic numbers are classic low-readability signals.

2.2 Naming — Do Names Explain the Code For You?

Variable and function names are the one piece of documentation in a codebase that is always forced to stay current. Names like data, temp, or flag2 offload the entire burden of interpretation onto the reader. A name like isEligibleForDiscount, by contrast, carries intent on its own, letting a caller understand the code without reading the implementation. Naming comments in review may look trivial, but they're often the highest-leverage improvement available.

2.3 Cohesion and Coupling — Does It Do One Thing?

A highly cohesive function or module carries a single responsibility. Low cohesion — a function that validates, writes to the database, and sends a notification all at once — forces you to re-read the same code for three unrelated reasons every time it changes. High coupling, where dependencies between modules are tangled, means fixing one spot breaks something unpredictable elsewhere. The moment a reviewer asks "isn't this function doing too much?" is the central scene of a maintainability-focused review.

2.4 Over-Engineered Abstraction — When Preparing for the Future Becomes a Burden

Just as common as too little abstraction is too much. Three layers of interfaces, factory patterns, and configurable strategy objects, all pre-built "in case we need to extend this later." When that extension never comes, the next maintainer has to jump across several files just to follow one simple piece of logic. That's why the YAGNI (You Aren't Gonna Need It) principle keeps getting invoked in review. The reviewer's job is to ask: is there evidence this abstraction is needed now, or is it just a guess?

3. Review as a Gift to Your Future Self and Your Teammates

3.1 You in Six Months Is a Stranger

It's a common joke, but it's close to the truth. Reopen code you wrote in a rush six months ago and you often can't recall why you wrote it that way. At review time, the author's context is still fresh in everyone's mind. Asking, at that moment, for a comment explaining a decision or for a section to be extracted into a function costs far less than reverse-engineering that same code after the context has evaporated. Review is the last chance to pin context into the code before it's gone.

3.2 Review as an Investment That Lowers Onboarding Cost

Whether an engineer who joined the team a month ago can understand the code the moment they open it determines the codebase's real-world value. Teams that consistently emphasize maintainability in review see a noticeably shorter onboarding period for new hires. That's not an abstract virtue — it's a practical metric directly tied to hiring and how fast a team can scale.

4. What Automation — Linters, Tests, CI — Cannot Catch

"Isn't that what linters and tests are for?" is a question I hear often. The answer is: only partly.

4.1 What Linters and Formatters Catch

Tools like ESLint, Prettier, Black, and golangci-lint mechanically catch style inconsistency, unused variables, and obvious anti-patterns. This layer should always be automated out of human review entirely. A human flagging a missing semicolon or wrong indentation wastes both the reviewer's time and their emotional capital.

4.2 What Tests Guarantee — and What They Don't

Tests guarantee only that "given this input, this output results, right now." They say nothing about whether the code will be understandable to someone else in six months, whether names reflect intent, or how flexible the design is to the next requirement change. Code that passes every test can still be a maintenance nightmare.

4.3 The Territory Automation Fundamentally Cannot Judge

No matter how advanced static analysis and AI linters become, they cannot answer questions like: does this name match how this term is actually used in this domain; is this abstraction too much or too little given our team's roadmap for the next six months; is this code understandable within this company's conventions and context. These questions require domain knowledge and organizational context — and that's the fundamental reason human review survives no matter how good automation gets.

5. Why Human Review Survives the Age of AI Code Review

As of 2026, AI code review tools — GitHub Copilot review, CodeRabbit, Graphite — are already used routinely. It's worth examining what this shift changes for maintainability-focused review.

5.1 What AI Review Tools Are Genuinely Good At

AI review tools scan for mechanically verifiable patterns — security vulnerabilities, consistency violations, missing error handling — faster and more tirelessly than a human reviewer. Teams that adopted AI-assisted review have reported faster merge times and fewer post-merge defects. Handing this layer of first-pass screening to AI is a reasonable division of labor.

5.2 What AI Still Can't Do — the Territory of Judgment

AI is markedly less reliable on questions like: does this change actually belong in the product; does the test strategy match this change's risk level; will whoever maintains this code a year from now understand this decision. Reports also indicate a meaningful share of unadopted AI-suggested code would break the build or contradict project context. AI is strong at scanning facts and history, but the judgment to interpret what those facts mean for this specific team and product still isn't something AI replaces.

5.3 Why Hybrid Review Is Becoming the Standard

Practice in 2026 is converging not on replacement but on division of labor. AI takes the mechanical first pass, saving human time, and humans then focus on higher-order judgment — design, context, future maintainability. Paradoxically, the better AI review tools get, the more the human reviewer's remaining share narrows and concentrates precisely on the topic of this piece: maintainability review.

6. Good Review Culture — Improvement, Not Blame

6.1 Comment on the Code, Never Attack the Person

"Why did you write it like this?" and "I'm curious why this approach was chosen here — this might read more clearly if ~" deliver the exact same critique in completely different ways. For maintainability review to work, comments have to target the state of the code, not the author's competence. Once that line blurs, review produces only defensiveness, and the actual maintainability issue gets approved without ever being discussed.

6.2 Progress, Not Perfection

As Google's guidance emphasizes, a reviewer who demands perfection before approving slows the whole team down and turns review into a nitpicking session. Anchoring on "does this PR leave the codebase better than yesterday" prevents a beneficial change from being blocked for days over a trivial flaw.

6.3 Structures That Reduce Ambiguity

Good review culture doesn't rely on goodwill alone. Team convention docs, review checklists, PR size limits (400 lines is a common recommendation), and review turnaround targets (under an hour, for example) are structural devices that reduce ambiguity. When the rules for what's fair game to flag are clear, both reviewer and author can focus on the maintainability discussion without burning emotional energy.

7. Applying This on Real Teams — Practical Suggestions

7.1 Bake a Comment Template Into Team Convention

I recommend writing into the team wiki an explicit distinction between "I don't understand this" and "consider fixing it this way." Tagging comments as blocking versus nit clarifies which the author needs to address first, and cuts down on trivial style debates holding up a merge.

7.2 Set PR Size Limits and a Review SLA

A common failure mode at fast-growing teams is PRs so large — thousands of lines — that the reviewer effectively skims and rubber-stamps. Disciplining PRs into small units is a prerequisite for maintainability review; a PR too large to review makes the principle of "flag what you don't understand" impossible to execute at all.

7.3 Design an AI-First-Pass-Plus-Human-Second-Pass Pipeline

I recommend wiring an AI code review tool into CI to filter out style, security, and obvious bugs first, letting the human reviewer use that output as a baseline while focusing on naming, cohesion, abstraction level, and design judgment. Splitting the work this way reduces reviewer fatigue and concentrates review time on the maintainability judgment only a human can make.

Conclusion: Code Review Is an Investment in Tomorrow's Understandability, Not Today's Correctness

Measuring the value of code review by "how many bugs did it catch" was the wrong yardstick from the start. The research, Google's internal guidance, and this GeekNews discussion all point the same direction. Review's greatest value lies in catching the moment a reader finds this code "hard to understand" — before that code sits in production long enough to cost many people. As automation and AI absorb more mechanical verification, what's left for the human reviewer only becomes clearer: does this name lie, does this function do one thing, is this abstraction actually needed now, and will you — or a teammate — six months from now open this code without getting lost. In your next review, I'd suggest leading with "will whoever has to fix this in six months understand it?" instead of "are there bugs?"
