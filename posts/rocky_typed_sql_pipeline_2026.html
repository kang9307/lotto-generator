Rocky — 파이프라인 전체를 타입 검사해 스키마 드리프트를 배포 전에 잡는 SQL 엔진

스키마 드리프트는 왜 개발은 통과하고 운영에서 터지는가 - 컴파일 타임 타입 검사의 가치와 한계를 분석한다

2026-07-08 개발/인프라

서론: 데이터팀에서 가장 무서운 장애는 요란하지 않다

데이터팀에서 가장 무서운 장애는 대시보드에 빨간불이 들어오는 장애가 아니다. 진짜 무서운 건 아무 경고도 없이 숫자가 조용히 틀려지는 장애다. GeekNews에 올라온 짧은 소개 하나가 이 문제를 정면으로 겨눈 도구를 소개했다. Rocky라는 이름의 오픈소스 SQL 변환 엔진으로, 파이프라인 전체를 컴파일 타임에 타입 검사해 상류 스키마가 바뀌었을 때 배포 전에 걸러내는 것을 핵심 기능으로 내세운다. 상류 컬럼의 타입이나 이름이 바뀌면 자동으로 감지해 타겟을 재생성하고, PR 단계에서 컬럼 단위로 어디까지 영향이 가는지 보여준다는 것이 원문 소개의 골자다.

본인은 이 글을 소개 글 요약이 아니라, 스키마 드리프트라는 문제의 구조, dbt·SQLMesh 같은 기존 데이터 변환 도구가 이 문제를 어떻게 다뤄왔는지, 그리고 "타입 안전한 SQL"이라는 개념이 정확히 무엇을 보장하고 무엇을 보장하지 못하는지를 독립적으로 조사하고 교차 확인한 뒤 쓰는 자체 분석으로 정리한다. 2026년 7월 기준으로 Rocky는 아직 Apache 2.0 라이선스의 젊은 오픈소스 프로젝트이고, Databricks를 제외한 웨어하우스 지원은 베타 단계다. 이 점을 감안하며 이 도구가 짚은 문제의식과 접근 방식이 실무에 어떤 의미를 갖는지를 중심으로 풀어본다.

1. Rocky란 무엇인가 - 컴파일러가 파이프라인을 지키는 방식

1.1 한 줄 요약

Rocky는 Rust로 작성된 단일 정적 바이너리로 동작하는 SQL 변환 엔진이자 웨어하우스 제어 플레인이다. SQL 모델과 TOML 설정으로 파이프라인을 정의하면, 이를 웨어하우스에 실행하기 전에 전체 DAG에 걸쳐 컬럼 단위로 타입을 추론하고 검증한다. 공식 홈페이지가 내세우는 표현을 빌리면 Rocky는 "코드와 웨어하우스 사이의 타입이 있는 그래프"를 자처한다. SQL 코드베이스 자체를 하나의 타입 시스템을 가진 프로그램처럼 다루겠다는 것이다.

1.2 핵심 기능

공개된 기능 목록은 크게 다섯 갈래다. 첫째, 컬럼 단위 타입 추론으로 DAG 전체를 훑어 35개 이상의 진단 코드로 실패를 표준화한다. 필수 컬럼 누락, 보호된 컬럼 삭제, 안전하지 않은 타입 변경 같은 상황은 각각 E010·E011·E013 같은 코드로 PR을 막는다. 둘째, rocky lineage-diff 명령으로 변경된 컬럼이 어떤 하류 테이블·컬럼까지 영향을 주는지 병합 전에 보여준다. 셋째, 상류 컬럼 타입이 바뀌면 다음 실행에서 소스와 타겟을 비교해 타겟을 드롭하고 재생성한다. 조용히 오염되는 대신 명시적으로 다시 짓는 쪽을 택한 것이다. 넷째, 네임드 브랜치로 격리된 스키마 사본에서 실행해 보고 승격하거나 버릴 수 있고, 콘텐츠 주소 방식의 실행 기록을 남겨 rocky replay로 검증할 수 있다(다만 replay는 현재 검증 전용이고 완전한 재실행은 추후 지원 예정이라고 명시돼 있다). 다섯째, 모델별 비용 귀속을 1급 기능으로 제공해 BigQuery 기준 스캔 바이트가 실제 청구와 일치한다고 주장한다.

1.3 기술적 선택

Rocky가 Rust 단일 바이너리를 택한 것은 단순한 구현 디테일이 아니다. 웨어하우스에 연결하지 않고도 오프라인에서 컴파일(타입 검사)이 가능하다는 뜻이고, 이는 CI 파이프라인에서 실제 쿼리를 실행하지 않고도 빠르게 검사를 돌릴 수 있다는 의미로 이어진다. rocky import-dbt 명령으로 기존 dbt Core 프로젝트를 변환 없이 한 번에 들여올 수 있다고 홍보하는데, 이는 신규 채택보다 마이그레이션 장벽을 낮추는 데 초점을 둔 설계로 읽힌다. Rocky 측은 스스로를 향해 "dbt Core has hit a ceiling"이라는 표현을 내세우는데, 이는 검증된 사실이 아니라 자사 포지셔닝이라는 점을 분명히 해 둔다.

2. 스키마 드리프트가 왜 무서운가 - "개발 통과, 운영 폭발"의 구조

2.1 스키마 드리프트란 무엇인가

스키마 드리프트는 파이프라인이 기대하던 입력 구조가 예고 없이 바뀌는 현상이다. 컬럼이 추가되거나 삭제되거나, 이름이 바뀌거나, 무엇보다 타입이 바뀐다. 정수였던 컬럼이 문자열이 되고, 날짜였던 컬럼이 타임스탬프가 되는 식이다. 문제는 이런 변화 대부분이 파이프라인을 소유한 팀이 아니라 상류의 다른 팀 - 프로덕션 애플리케이션 DB, 서드파티 SaaS 커넥터, 다른 조직의 마이크로서비스 - 에서 일어난다는 점이다. 데이터팀 입장에서는 통보 없이 바닥이 바뀌는 셈이다.

2.2 왜 조용히 지나가는가 - 관용적 타입 캐스팅의 함정

SQL 엔진 대부분은 타입 불일치에 관대하다. 정수 컬럼이 문자열로 바뀌어도 대부분의 웨어하우스는 즉시 에러를 내지 않고 암묵적 캐스팅이나 널 처리로 넘어간다. 파이프라인은 실패하는 대신 다른 값을 낸다. 값이 잘리거나, 반올림되거나, 조용히 널이 된다. 로그에는 에러가 없고 잡(job)은 초록불로 끝난다. 바로 이 지점이 스키마 드리프트를 다른 장애 유형과 구별짓는 특징이다 - 시스템은 "고장났다"고 말하지 않는다.

2.3 왜 개발 환경은 이를 못 잡는가

이것이 본인이 이 글에서 가장 강조하고 싶은 지점이다. 개발·스테이징 환경은 보통 특정 시점에 뜬 스냅샷이나 샘플 데이터를 쓴다. 코드 리뷰와 테스트는 그 고정된 데이터 위에서 통과한다. 그런데 실제 운영 소스는 그 스냅샷을 뜬 순간 이후로도 계속 진화한다. 상류 팀이 컬럼 타입을 바꾸거나 필드를 리네이밍하는 순간, 그 변화는 코드 리뷰나 CI 어디에도 걸리지 않은 채 프로덕션 실행에서만 드러난다. 즉 "개발에서 통과했다"는 사실 자체가 안전을 보장하지 않는다 - 개발이 테스트한 것은 코드 로직이지, 미래에 상류가 어떻게 바뀔지가 아니기 때문이다. 이 간극이야말로 정적 스키마 검증 도구가 정확히 겨냥하는 지점이다: 코드가 아니라 코드와 실제 소스 스키마 사이의 계약을 검증 대상으로 삼는 것이다.

2.4 폭발 시점의 비용은 기하급수적이다

드리프트가 조용히 흘러 들어가면, 그 시점부터 발견 시점까지 만들어진 모든 산출물 - 대시보드, 리포트, 그 데이터로 학습한 모델, 그 리포트를 근거로 내려진 의사결정 - 이 잠재적으로 오염된다. 발견이 늦어질수록 되돌려야 할 반경이 넓어진다. 단순히 파이프라인 하나를 고치는 비용이 아니라, 그 파이프라인 산출물을 소비한 모든 다운스트림을 감사하고 정정하는 비용이 붙는다. 이것이 스키마 드리프트가 조용한 장애로 불리는 이유이고, 왜 사후 감지가 아니라 사전 차단이 가치를 갖는지의 근거다.

3. 파이프라인 전체를 정적 타입 검사한다는 것의 실질적 가치

3.1 소프트웨어 엔지니어링의 교훈을 데이터에 옮기다

타입 시스템이 애플리케이션 코드에서 해온 역할을 떠올려 보면 이 접근의 논리를 이해하기 쉽다. 정적 타입 언어는 함수 시그니처가 안 맞으면 실행 전에 컴파일이 실패한다. 실행 후 런타임에 터지는 대신, 코드를 짠 사람의 화면에서 즉시 드러난다. Rocky가 시도하는 것은 이 원칙을 SQL 파이프라인에 그대로 옮기는 일이다. 모델 간의 컬럼 타입·존재 여부를 함수 시그니처처럼 취급하고, DAG 전체를 하나의 타입 있는 프로그램처럼 컴파일한다.

3.2 PR 단계에서 영향 범위를 보여준다는 것

rocky lineage-diff가 흥미로운 이유는 검사를 "실행 후 실패"가 아니라 "병합 전 가시화"로 옮긴다는 데 있다. 어떤 컬럼을 바꾸는 PR이 올라오면, 그 변경이 몇 개의 하류 테이블과 컬럼에 닿는지를 사람이 리뷰하는 시점에 보여준다. 이는 코드 리뷰어가 "이 변경이 안전한가"를 추측이 아니라 명시적 근거로 판단할 수 있게 한다는 점에서, 단순 타입 체크를 넘어 조직의 리뷰 프로세스에 개입하는 설계다.

3.3 드리프트에 대한 자동 대응 - 침묵 대신 재생성

상류 타입이 실제로 바뀐 순간에 대한 Rocky의 대응도 짚을 만하다. 다음 실행에서 소스와 타겟 스키마를 비교해 타겟을 드롭하고 재생성한다. 이는 "계속 돌아가되 값이 틀려지는" 상태보다 "명시적으로 멈추고 다시 짓는" 상태를 택한 것이다. 후자가 항상 더 안전하다고 단정할 수는 없다 - 재생성 도중 다운타임이나 백필 비용이 발생할 수 있다 - 하지만 최소한 실패가 눈에 보이는 형태로 일어난다는 점에서 조용한 오염보다는 낫다는 게 본인의 판단이다.

4. dbt·SQLMesh와 비교 - 같은 문제, 다른 개입 시점

4.1 dbt Core의 접근 - 실행 후 테스트, 옵트인 계약

dbt Core는 스키마 계약을 지원하지만 기본적으로 수동 설정이다. YAML에 계약을 선언하면 모델의 스키마를 런타임에 대조하고, 모델 버저닝으로 하류 팀에 이전 기간을 준다. 문제는 두 가지다. 첫째, 계약이 옵트인이라 선언하지 않은 모델은 보호받지 못한다. 둘째, dbt의 테스트는 "만들고 나서 검증"하는 구조다. 테이블이 이미 써진 다음에 테스트가 돌기 때문에, 문제가 있는 데이터가 이미 한 번은 착지한 뒤에야 발견된다.

4.2 SQLMesh의 접근 - 계획 단계의 자동 계약

SQLMesh는 한 단계 더 나아간다. sqlmesh plan을 실행하면 모델의 스키마뿐 아니라 쿼리 로직까지 분석해 어떤 변경이 하류에 어떤 영향을 주는지 자동으로 보여준다. SQL의 의미를 이해하기 때문에, 변경이 실제로 출력을 바꾸지 않는다고 판단되면 하류 재구체화를 건너뛸 수도 있다. 감사(audit)도 테이블이 노출되기 전에 돈다. dbt의 실행 후 테스트 구조와 대비되는 지점이다.

4.3 Rocky가 더 파고드는 지점

이 계보 위에서 Rocky의 위치는 명확하다. dbt는 런타임 검증, SQLMesh는 계획 시점 검증이라면, Rocky는 이를 컴파일 타임으로 한 단계 더 당긴다. 웨어하우스에 붙지 않고도 정적 검사가 가능하다는 점, 필수 컬럼 보호가 옵트인이 아니라 기본값으로 강제된다고 주장하는 점(Rocky 측 자체 비교표에 근거한 주장이므로 실제 프로젝트에서 직접 검증이 필요하다), 그리고 컬럼 단위 diff를 PR 리뷰 화면까지 끌고 온다는 점이 차별점이다. 다만 이 "더 이른 개입"이 공짜는 아니다 - Databricks 밖에서는 아직 베타 단계이고, dbt·SQLMesh가 갖춘 생태계·문서·커뮤니티 자산은 훨씬 얇다.

5. "타입 안전한 SQL/데이터"의 의미와 한계

5.1 의미 - 모양의 정확성을 배포 전으로 당기다

타입 안전한 SQL이 보장하는 것은 명확히 한정적이다. 컬럼이 존재하는지, 타입이 선언과 맞는지, 필수 필드가 빠지지 않았는지 - 이런 구조적 정확성을 실행 전에 확인해 준다. 이는 소프트웨어에서 타입 체커가 "이 변수에 문자열이 아니라 정수가 들어올 수 있는가"를 보장하는 것과 정확히 같은 층위의 안전이다. 값이 아니라 모양을 보증한다.

5.2 한계1 - 타입이 맞아도 값은 틀릴 수 있다

타입 검사를 통과했다는 것이 데이터 품질을 보증하지는 않는다. 나이 컬럼이 INTEGER 타입을 정확히 유지해도 값이 음수이거나 200처럼 비상식적일 수 있다. 이메일 컬럼이 STRING 타입이어도 형식이 틀렸을 수 있다. 이런 값 수준의 검증은 타입 시스템의 영역이 아니라 별도의 데이터 품질 도구 - dbt의 데이터 테스트, Great Expectations, Soda 같은 - 가 맡아야 하는 영역이다. 타입 검사와 값 검증은 서로 대체재가 아니라 보완재다.

5.3 한계2 - 선언되지 않은 것은 잡을 수 없다

정적 검사는 선언된 계약 위에서만 작동한다. 어떤 컬럼이 필수인지, 어떤 컬럼이 보호돼야 하는지를 아무도 선언하지 않았다면 도구는 그것을 지킬 근거가 없다. 또한 소스 자체가 느슨하게 타입화돼 있다면 - JSON 블롭이나 Snowflake의 Variant 컬럼처럼 - 컴파일러가 추론할 근거 자체가 빈약해진다. 정적 타입 검사의 가치는 상류 소스가 얼마나 명시적으로 타입 정보를 노출하느냐에 비례한다.

5.4 한계3 - 동적 SQL과 NULL 의미론의 사각지대

쿼리가 런타임에 문자열로 조립되는 동적 SQL은 정적 분석기가 구조를 미리 알 수 없는 경우가 많아 검사망을 피해 갈 수 있다. 또한 SQL의 NULL 의미론은 프로그래밍 언어의 null과 정확히 대응하지 않는다 - 세 값 논리(참·거짓·알 수 없음) 위에서 동작하는 SQL의 NULL을 정적으로 완벽히 추적하는 것은 알려진 난제다. 정적 타입 체커는 본질적으로 보수적이다. 실제로는 안전한 실행도 확신이 없으면 막아 버리는 쪽을 택하는 경우가 많고, 반대로 모든 실행 경로를 다 알 수 없어 놓치는 경우도 있다.

5.5 한계4 - "통과"가 주는 과신의 위험

가장 경계해야 할 것은 타입 검사 통과를 논리적 정확성의 증명으로 착각하는 일이다. 컬럼 타입과 존재 여부가 맞다고 해서 비즈니스 로직이 옳다는 뜻은 아니다. 매출 계산식이 틀렸어도, 조인 조건이 의도와 다르게 걸려도, 타입 체커는 아무 말을 하지 않는다. 타입 안전은 특정 종류의 장애 - 구조적 불일치로 인한 조용한 오염 - 를 없애 주는 도구이지, 파이프라인이 옳다는 보증서가 아니다.

6. 실무 도입 고려 - 러닝커브·생태계·기존 파이프라인 통합

6.1 러닝커브

SQL과 YAML(혹은 Jinja)에 익숙한 dbt 팀 입장에서 Rocky는 TOML 설정, 자체 DSL, Rust 단일 바이너리라는 새로운 층을 얹는다. 순수 SQL로도 작성할 수 있다고 홍보하지만, 진단 코드 체계·브랜치/replay 개념·컬럼 보호 문법을 익히는 데는 초기 투자가 필요하다. 팀 규모가 작고 파이프라인이 단순하다면 이 학습비용이 얻는 이득보다 클 수 있다.

6.2 생태계 성숙도

공개된 지원 등급을 보면 Databricks만 프로덕션 준비 상태이고, Snowflake·BigQuery·Trino는 베타, DuckDB는 테스트 단계다. Databricks 밖에서 도입한다면 사실상 베타 소프트웨어를 프로덕션에 들이는 결정이 된다. 메트릭 레이어는 자체 제공하지 않고 Cube나 dbt Semantic Layer 같은 외부 도구를 권장하며, 내장 스케줄러 연동은 Dagster(dagster-rocky)가 유일하고 다른 스케줄러는 Python SDK나 rocky serve를 직접 붙여야 한다. dbt가 수년간 쌓아온 패키지 생태계·커뮤니티 자산과 비교하면 아직 얇다는 점을 감안해야 한다.

6.3 기존 파이프라인 통합

rocky import-dbt로 기존 dbt Core 프로젝트를 재작성 없이 들여올 수 있다는 것은 마이그레이션 장벽을 크게 낮추는 설계다. 다만 "한 번에 들여온다"는 주장과 "들여온 뒤 Rocky의 타입 검사·계약 기능을 온전히 활용하려면 얼마나 재구성이 필요한가"는 다른 질문이다. 실제 도입을 검토한다면, 본인 프로젝트의 대표 모델 몇 개를 골라 임포트 후 lineage-diff와 진단 코드가 기대한 대로 동작하는지 직접 확인하는 파일럿이 필요하다.

7. 어디에 맞고 어디서 신중해야 하는가

7.1 잘 맞는 곳

여러 상류 소스 - 특히 통제 밖의 서드파티 SaaS나 다른 팀 마이크로서비스 - 에서 스키마가 자주, 예고 없이 바뀌는 파이프라인이 1순위다. 모델 수가 많아 사람이 영향 범위를 손으로 추적하기 어려운 대규모 DAG, 그리고 모델별 비용 어트리뷰션이 실제로 조직 운영에 필요한 팀에도 유효하다. 무엇보다 Databricks가 주 웨어하우스인 조직이라면 지원 성숙도 리스크가 가장 낮다.

7.2 신중해야 할 곳

이미 dbt Cloud나 SQLMesh에 깊이 투자해 계약·테스트 체계를 갖춘 팀이라면, 전환 비용 대비 이득을 냉정히 따져야 한다. Databricks 이외 웨어하우스가 주력이라면 베타 리스크를 프로덕션에 들이는 셈이므로 비프로덕션 환경에서 충분히 검증한 뒤 판단하는 편이 안전하다. 그리고 문제의 핵심이 스키마 구조가 아니라 값 품질(이상치·중복·참조 무결성)이라면, 타입 검사 도구 하나로 해결되지 않는다는 점도 분명히 해야 한다.

결론: 오늘 적용 가능한 것

Rocky가 제기하는 문제의식 자체는 정확하다. 스키마 드리프트는 개발 환경의 고정된 스냅샷과 운영 환경의 살아있는 소스 사이의 간극에서 태어나고, 그 간극은 코드 리뷰만으로는 메워지지 않는다. 이 문제를 컴파일 타임으로 끌어올려 잡겠다는 접근은 소프트웨어 엔지니어링이 이미 검증한 원칙을 데이터 파이프라인에 적용하는 자연스러운 다음 단계로 보인다. 다만 Rocky라는 특정 도구는 2026년 7월 기준으로 아직 젊고, Databricks 밖에서는 베타이며, 타입 검사가 값 품질까지 보장하지는 않는다는 한계도 명확하다.

이번 주 시도해 볼 만한 것 세 가지다. 첫째, 최근 겪은 파이프라인 장애 중 "개발은 통과했는데 운영에서 터진" 사례를 되짚어, 그것이 스키마 드리프트 패턴이었는지 확인해 본다. 둘째, 본인이 다루는 상류 소스 중 명시적 계약 없이 암묵적으로 신뢰하고 있는 것이 무엇인지 목록으로 정리해 본다. 이 목록 자체가 다음 장애가 어디서 터질지 보여주는 지도다. 셋째, Databricks를 쓰는 팀이라면 비프로덕션 브랜치에서 rocky import-dbt로 대표 모델 몇 개를 시험 삼아 들여오고 lineage-diff 결과가 실제 하류 의존 관계와 맞는지 확인해 본다.
