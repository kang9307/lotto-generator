One NULL in a NOT IN List Empties the Whole Result - SQL Three-Valued Logic

What separated 0 rows from 8 rows was a single NULL in the list. Measured on SQLite and DuckDB

2026-07-30 Development/Infrastructure

The symptom: the result was empty, and the data was definitely there

A production service had a query that pulled the list of customers who had never requested a refund. It worked until yesterday. Today it returns 0 rows. The customer table still holds tens of thousands of records, and the refund table is intact. The query succeeded. Not one line of error output.

Faced with this, the first conclusion a person reaches is usually the same one: there must not be any data matching the condition. That conclusion then becomes a dashboard showing nothing, a notification batch that mails nobody, and a report full of zeros, left in place for days. Because nothing failed — it succeeded while empty — no alert ever fires.

The culprit is usually this one line.

SELECT id, name FROM customers
WHERE id NOT IN (SELECT customer_id FROM refund_requests);

And refund_requests.customer_id has exactly one row holding NULL. That is all it takes. However healthy the other ten thousand rows are, the result is 0 rows.

This article is not an argument for never using NOT IN. It is about why it was designed this way, and when to use what. To state the conclusion first: this behaviour is not a bug, it is the logically correct result. It becomes an incident only because that correctness arrives quietly, without an error.

Execution environment. Every output below was produced by actually running the statements on Windows 10 Pro (10.0.19045). Two engines were used: SQLite 3.49.1 (through the sqlite3 driver of Python 3.13.3) and DuckDB 1.5.5 (a PostgreSQL-family SQL dialect). The same script was run on both so that the points where they agree and the points where they diverge could be separated. Statements about the specification were cross-checked only against the official SQLite and PostgreSQL documentation, and nothing is asserted about engines that were not opened and verified, such as MySQL, Oracle, or SQL Server.

Example schema. customers holds 10 rows (id from 1 to 10) and refund_requests holds 4 rows. Of those 4 requests, exactly 1 has a NULL customer_id. All tables are fictional and can be copied verbatim to reproduce the results on your own database.

What this article does not cover. If SQL itself is new to you, start with the SQL beginner guide. Here we dig into a single point: the three-valued logic of NULL. The boundary between ON and WHERE in joins is not the subject of this article, and the NOT EXISTS and LEFT JOIN material in sections 6 and 7 is treated purely as an anti-join alternative.

1. A three-minute reproduction: put one NULL in the list

Before any explanation, run it. All you need is one table with 10 rows.

The numbers match exactly. This is not a defect of one particular engine. It follows from the definition in the SQL standard, which is why it reproduces identically everywhere.

2. Why is IN unharmed?

The interesting part is IN. Given exactly the same list, IN behaves correctly.

--- 2-1. IN with the same list ---
  SQL: SELECT id, name FROM customers WHERE id IN (1, 2, NULL)
  rows returned: 2
  id | name
  1 | aria
  2 | brio

--- 2-2. IN without the NULL ---
  SQL: SELECT id, name FROM customers WHERE id IN (1, 2)
  rows returned: 2
  id | name
  1 | aria
  2 | brio

Two rows with or without the NULL. So why is NOT IN different? To see the answer, print what the condition actually evaluates to for each row. SQLite shows true as 1, false as 0, and the third value as NULL.

--- 2-3. the expression value per row (1 = true, 0 = false, NULL = unknown) ---
  id | in_expr | not_in_expr | in_clean | not_in_clean
  1 | 1 | 0 | 1 | 0
  2 | 1 | 0 | 1 | 0
  3 | NULL | NULL | 0 | 1
  4 | NULL | NULL | 0 | 1
  5 | NULL | NULL | 0 | 1
  6 | NULL | NULL | 0 | 1
  7 | NULL | NULL | 0 | 1
  8 | NULL | NULL | 0 | 1
  9 | NULL | NULL | 0 | 1
  10 | NULL | NULL | 0 | 1

This table is the heart of the article. Read the not_in_expr column downward. There is not a single cell holding 1. Rows 1 and 2 hold 0 (false), and the remaining 8 rows all hold NULL. The not_in_clean column, built from the NULL-free list, holds eight 1 values.

DuckDB shows the same thing with a real boolean type. Only the rendering differs; the structure is identical.

--- 1-1. the expression value per row - booleans, not 1/0 ---
  id | in_expr | not_in_expr | not_in_clean
  1 | true | false | false
  2 | true | false | false
  3 | NULL | NULL | true
  4 | NULL | NULL | true
  5 | NULL | NULL | true
  ... (rows 6-10 identical in shape)

The next section explains the mechanism.

3. NULL does not mean absent, it means unknown

Most people read NULL as an empty value. That reading makes NULL = NULL feel like it should be true, and 1 <> NULL feel like it should be true too. Running it shows otherwise.

--- 3-1. comparisons against NULL ---
  eq | neq | null_eq_null | null_neq_null | gt | is_null | one_is_null
  NULL | NULL | NULL | NULL | NULL | 1 | 0

How to read it: 1 = NULL is NULL, 1 <> NULL is NULL, NULL = NULL is NULL, and 1 > NULL is NULL. The only construct that returned a definite value was IS NULL (NULL IS NULL gave 1, 1 IS NULL gave 0).

Here NULL does not mean the result was empty. It is the third logical value, UNKNOWN. Printing the type makes that unambiguous.

--- 3-2. typeof() of each result - NULL is a value, not an error ---
  t_eq | t_true | t_false | t_nn
  null | integer | integer | null

True and false are integer, and the result of a comparison against NULL has type null. It is a value, not an error. Which is exactly why it slips into calculations without a sound.

3.1 Why was it defined this way?

Read NULL as a value we do not know and everything becomes natural.

  • We do not know someone's age. Is that age 30? We do not know. Not false — unknown. So age = 30 is UNKNOWN
  • Is that age something other than 30? Also unknown. So age <> 30 is UNKNOWN too
  • We do not know either of two people's ages. Are they the same age? We do not know. So NULL = NULL is UNKNOWN as well

Under the empty-value reading the third case looks strange, but under the unknown reading it is the obvious conclusion. How could you assert that two values you do not know are equal?

3.2 How UNKNOWN passes through AND and OR

--- 3-3. NOT of unknown is still unknown ---
  not_unknown | unknown_or_true | unknown_or_false | unknown_and_true | unknown_and_false
  NULL | 1 | NULL | NULL | 0

Unfolding that single line into a table gives this.

ExpressionResultWhy
UNKNOWN OR TRUETRUEOR is settled by a single true
UNKNOWN OR FALSEUNKNOWNthe unknown might be true, so nothing is settled
UNKNOWN AND TRUEUNKNOWNthe unknown might be false, so nothing is settled
UNKNOWN AND FALSEFALSEAND is settled by a single false
NOT UNKNOWNUNKNOWNthe opposite of what we do not know is also unknown

There is one rule. Things settle only when the conclusion can be settled; everywhere else, unknown is contagious. And the fact that NOT UNKNOWN remains UNKNOWN is the blow that kills NOT IN.

3.3 WHERE admits only TRUE

The last piece. Counting directly how the filter treats each of the three logical values.

--- 3-4. what WHERE does with each of the three values ---
  WHERE TRUE     -> 1 row(s)
  WHERE FALSE    -> 0 row(s)
  WHERE UNKNOWN  -> 0 row(s)
Value of the WHERE clauseThat rowMeasured
TRUEkept1 row
FALSEdropped0 rows
UNKNOWNdropped0 rows

Here the trap completes itself. At the filtering step UNKNOWN is indistinguishable from FALSE. I do not know and it is not so receive identical treatment. Inside a logical expression three values are kept apart; on the way out they are folded into two.

3.4 Now read NOT IN again

x NOT IN (1, 2, NULL) unfolds like this.

x NOT IN (1, 2, NULL)
  = NOT (x IN (1, 2, NULL))
  = NOT (x = 1 OR x = 2 OR x = NULL)

x = 1  -->  NOT (TRUE  OR FALSE OR UNKNOWN) = NOT TRUE    = FALSE    -- dropped
x = 7  -->  NOT (FALSE OR FALSE OR UNKNOWN) = NOT UNKNOWN = UNKNOWN  -- dropped

No path leads to TRUE. Present in the list gives FALSE; absent from the list gives UNKNOWN. WHERE admits only TRUE, so the result is 0 rows. That is why the 2-3 output above contained no 1 anywhere.

IN, conversely, survives, because for the row where x = 1 the expression becomes TRUE OR FALSE OR UNKNOWN = TRUE. OR is settled by a single true, so adding a NULL does not block the path to a true result.

The official PostgreSQL documentation states this behaviour explicitly. It notes that if the left-hand expression yields null, or if there are no equal right-hand values and at least one right-hand row yields null, the result of the NOT IN construct will be null rather than true, and that this is in accordance with the normal rules for boolean combinations of null values. In other words, the specification decided it.

4. Where it really bites: NOT IN (SELECT ...)

Almost nobody writes a literal NULL into a list by hand. Incidents happen in the subquery form, because there the list is not visible in the code.

--- 0-1. refund_requests contents ---
  req_id | customer_id | amount
  101 | 1 | 5000
  102 | 2 | 3000
  103 | NULL | 7000
  104 | 1 | 1200

Exactly one of the 4 rows has a NULL customer_id. In this state, pull the customers who never requested a refund.

--- 4-1. customers who never requested a refund - the naive query ---
  SQL: SELECT id, name FROM customers WHERE id NOT IN (SELECT customer_id FROM refund_requests)
  rows returned: 0
  id | name

--- 4-2. how many NULLs are in that subquery column ---
  total | non_null | nulls
  4 | 3 | 1

--- 4-3. same query after deleting the single NULL row ---
  rows returned: 8
  id | name
  3 | cedar
  4 | delta
  ...
  10 | juno

--- 4-4. one NULL row is enough - inserting it back ---
  rows in rr_clean before insert : 3
  rows in rr_clean after insert  : 4
  NOT IN result now              : 0 rows
  after removing it again        : 8 rows

Delete the NULL row and you get 8 rows; put it back and you get 0 rows; delete it again and you get 8 rows. It behaves like a switch.

4.1 Scale is completely irrelevant

The intuition that one NULL cannot matter in a table of ten thousand rows does not hold, and here is the number that shows it.

=== B. one NULL among ten thousand rows ===
  blocklist rows                  : 10000   (values 1001..11000, none overlap customers)
  NULLs in blocklist.v            : 0
  SELECT id FROM customers WHERE id NOT IN (SELECT v FROM blocklist)
  rows returned                   : 10

  -- one single NULL row inserted --
  blocklist rows                  : 10001
  NULLs in blocklist.v            : 1
  NULL share of the table         : 1 / 10001 = 0.00999 percent
  rows returned                   : 0

  NOT EXISTS on the same table    : 10 rows
  LEFT JOIN / IS NULL             : 10 rows

One NULL row out of ten thousand, 0.01 percent by share. The result went from 10 rows to 0 rows. What matters is not the proportion but the existence. One is enough, and ten thousand gives the same result.

4.2 When a WHERE clause in the subquery hides the NULL by accident

There is a nastier variant. When a filter added to the subquery for some unrelated purpose happens to remove the NULL, the query works fine — until someone touches that filter.

=== B-2. a WHERE clause in the subquery can hide the NULL by accident ===
  NOT IN (SELECT v FROM blocklist)                             -> 0 rows
  NOT IN (SELECT v FROM blocklist WHERE v > 5000)              -> 10 rows
  NOT IN (SELECT v FROM blocklist WHERE v > 5000 OR v IS NULL) -> 0 rows

  the middle query works only because v > 5000 is UNKNOWN for the NULL row
  and therefore drops it. Change the filter and the query breaks again:
  NOT IN (SELECT v FROM blocklist WHERE v > 5000 OR v <= 5000)  -> 10 rows

The middle query produced 10 rows only because v > 5000 is UNKNOWN for the NULL row, so that row had already been dropped from the subquery result. NULL acted twice and happened to cancel itself out. Such a query turns into 0 rows for no visible reason as soon as one condition changes.

4.3 The outer column can be NULL too

So far we have looked only at NULLs on the list side. A NULL in the column being compared also makes that row vanish — even when the list contains no NULL at all.

=== D. SQLite: when the OUTER value is NULL ===
  rows: 3, one of them region = NULL
  WHERE region NOT IN ('seoul')  -> 1 rows
  id | region
  2 | busan
  the NULL-region row disappeared even though the list has no NULL
  WHERE region NOT IN ('seoul') OR region IS NULL -> 2 rows

Of 3 rows, one had a NULL region. Selecting the regions that are not Seoul returned only 1 row. For a customer whose region is unknown you cannot assert that the region is not Seoul, so the expression became UNKNOWN and the row was dropped. To include it you must state OR region IS NULL explicitly, which gives 2 rows. DuckDB produced the same numbers.

5. Why does nobody notice?

The genuinely dangerous part of this bug is not the logic but the failure to discover it. It hides behind three layers.

  • There is no error. No exception, no warning, no slow-query log. The signal that monitoring would catch does not exist
  • Zero rows looks like a legitimate result. It is indistinguishable from there being no matching data
  • It passes on the development database. Hand-written fixtures contain no NULLs
  • The code looks perfectly fine. Read the query text alone and the logic is exact. What changes the result is not the code but the values sitting in the table at that moment
  • Reproduction is intermittent. Delete the row that carried the NULL and the query works again, so by the time you investigate a report the system may already look healthy

The third layer, expressed as numbers.

=== B-3. the dev-versus-prod illusion ===
  dev fixture  (3 rows, hand-written, no NULL)       -> 10 rows   test PASSES
  prod data    (4 rows, one NULL from an old import) -> 0 rows    silently empty

The test passes. A developer writing fixtures by hand has no reason to include a NULL. NULLs in a production database, by contrast, are usually the residue of an old migration, an aborted batch, or a failed external integration. Code review does not catch it either, because what the subquery returns is decided by the data, not by the code.

For this particular bug, adding one fixture row containing a NULL to your unit tests is worth more than ten code reviews.

6. Alternative one: NOT EXISTS does not die

Here is what happens when the same intent is written with NOT EXISTS, on the same data.

--- 5-1. the same intent written with NOT EXISTS ---
  SELECT c.id, c.name FROM customers c
  WHERE NOT EXISTS (SELECT 1 FROM refund_requests r WHERE r.customer_id = c.id)

  rows returned: 8
  id | name
  3 | cedar
  4 | delta
  5 | echo
  6 | flux
  7 | gale
  8 | hive
  9 | iris
  10 | juno

Eight rows. The data is unchanged and the NULL is still there, yet results come back. The reason is that the decision criterion is different.

  • NOT IN compares values to produce a logical value, so it falls under the rule of three-valued logic
  • NOT EXISTS only asks whether the inner query produced any row. Present or absent is two values, and UNKNOWN has nowhere to fit

Counting directly what becomes of the NULL row.

--- 5-3. why - the NULL row never matches r.customer_id = c.id ---
  id | matching_rows
  1 | 2
  2 | 1
  3 | 0
  4 | 0
  5 | 0
  6 | 0
  7 | 0
  8 | 0
  9 | 0
  10 | 0

Request 103, whose customer_id is NULL, attached to no customer at all. NULL = 3 is UNKNOWN so it never matches, and a failure to match simply means that subquery yields 0 rows. NULL cannot contaminate the conclusion; it stops right there.

DuckDB agreed. Both engines gave 8 rows for NOT EXISTS.

7. Alternative two: LEFT JOIN followed by IS NULL

A third spelling. Join, then keep only the rows that failed to match.

--- 6-1. anti-join written as LEFT JOIN + IS NULL ---
  SELECT c.id, c.name FROM customers c
  LEFT JOIN refund_requests r ON r.customer_id = c.id
  WHERE r.req_id IS NULL

  rows returned: 8

--- 6-2. the three forms side by side, same table, same intent ---
  NOT IN (subquery)     -> 0 rows
  NOT EXISTS            -> 8 rows
  LEFT JOIN / IS NULL   -> 8 rows

Those three lines are the summary of this article. Same data, same intent, same correct answer — and only the first one gives 0 rows.

7.1 This spelling has its own trap

Which column you apply IS NULL to separates a correct answer from a wrong one. Apply it to an ordinary column that can hold NULL and it fails quietly. Setting amount of request 104 to NULL and re-running shows this.

=== A. SQLite: the LEFT JOIN trap, done properly ===
  req_id | customer_id | amount
  101 | 1 | 5000
  102 | 2 | 3000
  103 | NULL | 7000
  104 | 1 | NULL

  WHERE r.req_id IS NULL  (primary key, never NULL in a matched row) -> 8 rows
  WHERE r.amount IS NULL  (nullable column - WRONG choice)           -> 9 rows

  the wrong version leaked customer 1, who DID request a refund:
  id | name | req_id | amount
  1 | aria | 104 | NULL
  3 | cedar | NULL | NULL
  4 | delta | NULL | NULL
  ...
  10 | juno | NULL | NULL

What should have been 8 rows became 9, and customer 1, who genuinely did request a refund, leaked into the list of customers who never did. The match had succeeded, but the amount on that row happened to be NULL.

The rule is clear. Apply the IS NULL test only to a column where NULL can never appear, such as the join key or the primary key. Use a column that can be NULL even in a matched row and you can no longer distinguish failed to match from matched but the value was empty.

8. The guard: cannot I just add IS NOT NULL?

The easiest response is to put a guard in the subquery. It does work.

--- 7-1. the defensive rewrite ---
  SELECT id, name FROM customers
  WHERE id NOT IN (SELECT customer_id FROM refund_requests WHERE customer_id IS NOT NULL)

  rows returned: 8

Eight rows. But there are three reasons not to call this a real fix.

  • It must be repeated. Every site using NOT IN needs it, and missing one leaves that query silently at 0 rows. A defence a human has to remember every time will eventually fail
  • It is invisible. Anyone reading only the outer query cannot see the guard. Not knowing why it is there, they delete it during refactoring
  • It changes the meaning. If that NULL was information, discarding it erases a fact

The third point matters most. Look at what that NULL actually was in the example.

--- 7-3. what the NULL actually meant here ---
  req_id | customer_id | amount
  103 | NULL | 7000
  a 7000 refund with no customer attached - dropping it hides a data bug

A refund request for an amount of 7000 with no customer attached. That is not noise you may ignore, it is evidence that referential integrity broke somewhere. The moment you filter it out with IS NOT NULL, that fact disappears from your reports forever.

So the order of operations is this.

  1. First look at why that NULL is there. SELECT * FROM t WHERE col IS NULL
  2. If the value should never arrive, block it at the source with NOT NULL and a foreign key constraint
  3. If the value legitimately can arrive, change the spelling to NOT EXISTS and step outside the reach of NULL
  4. Use an IS NOT NULL guard only to put out an immediate fire, and leave a comment explaining why discarding it is correct

9. Where else NULL hides, part one: aggregate functions

NOT IN is not the only problem. The same three-valued logic appears differently in aggregates. Of the 10 rows in customers.credit, 4 are NULL.

--- 8-1. COUNT(*) vs COUNT(col) on customers.credit ---
  count_star | count_credit | count_distinct_credit | sum_credit | avg_credit | min_credit | max_credit
  10 | 6 | 6 | 1230 | 205.0 | 60 | 420

COUNT(*) is 10 and COUNT(credit) is 6. The former counts rows, the latter counts only the ones that have a value. And which of those is the denominator of the average keeps causing trouble in practice.

--- 8-2. AVG denominator - it divides by the non-null count, not the row count ---
  s | n_nonnull | n_all | avg_builtin | s_div_nonnull | s_div_all
  1230 | 6 | 10 | 205.0 | 205.0 | 123.0

--- 8-3. COALESCE changes the answer, and that is the point ---
  avg_ignoring_nulls | avg_nulls_as_zero
  205.0 | 123.0

205.0 and 123.0. Two different averages out of the same data. AVG(credit) divides 1230 by 6, while AVG(COALESCE(credit, 0)) divides 1230 by 10.

Which is right depends on what the NULL means. If it means the limit has not been assessed yet, excluding it from the denominator is correct; if it means the limit is zero, including it is correct. SQL will not make that decision for you. This is why overusing COALESCE is dangerous: instead of removing the NULL in front of you, it changes what you are measuring.

Empty sets behave differently again.

--- 8-4. aggregates over an empty set ---
  c | s | a | m
  0 | NULL | NULL | NULL
  COUNT returns 0, SUM/AVG/MAX return NULL - a SUM of nothing is not 0

COUNT gives 0 but SUM gives NULL. The sum of nothing being zero feels like common sense, but SQL does not do that. So feeding an aggregate result straight into an application integer type produces a null reference at that exact point. To defend against it you must write COALESCE(SUM(x), 0) deliberately. DuckDB behaved identically.

10. Where else NULL hides, part two: the UNIQUE constraint

The sentence this column is UNIQUE so there are no duplicates does not hold in the presence of NULL.

--- 9-1. inserting several NULLs into a UNIQUE column ---
  insert 'A' -> OK
  insert NULL -> OK
  insert NULL -> OK
  insert NULL -> OK
  insert 'A' again -> IntegrityError: UNIQUE constraint failed: u_test.code
  rows now: 4
  id | code
  1 | A
  2 | NULL
  3 | NULL
  4 | NULL

All three NULLs went in. A second insert of the same string 'A', by contrast, was rejected precisely. The unique constraint treats NULLs as different values from one another. Since NULL = NULL is UNKNOWN, there is no basis on which to rule that a duplicate exists.

The same applies to a composite UNIQUE.

--- 9-2. same thing on a multi-column UNIQUE ---
  insert ('x', 'y') -> OK
  insert ('x', NULL) -> OK
  insert ('x', NULL) -> OK
  insert (NULL, NULL) -> OK
  insert (NULL, NULL) -> OK
  rows now: 5

('x', NULL) went in twice and (NULL, NULL) went in twice. All 5 rows inserted successfully. On DuckDB 1.5.5 the three NULLs also went in and only the duplicate 'A' was rejected. Both engines agree.

The official SQLite documentation acknowledges this inconsistency itself. It states that NULLs are distinct in a UNIQUE column but are not distinct for the purposes of SELECT DISTINCT and UNION, and records that this is somewhat arbitrary but was chosen to match the behaviour of Oracle, PostgreSQL, and DB2. Having the rule reversed inside the same engine is a deliberate state of affairs.

Practical implication. If you wrote that the registration number is UNIQUE so we are safe, but that column permits NULL, then rows with an empty registration number go in without limit. To genuinely prevent duplicates you must apply UNIQUE together with NOT NULL. For reference, PostgreSQL 15 is reported to have added an option that makes UNIQUE treat NULLs as equal, but this was not verified by execution here, so nothing is asserted about it.

11. Where else NULL hides, part three: GROUP BY and DISTINCT

Here the rule flips. NULLs that = refuses to call equal become one when grouped.

--- 10-1. GROUP BY region ---

12. Where else NULL hides, part four: ORDER BY, and where engines diverge

Up to this point the numbers from both engines matched exactly. Here they part. The same data sorted by the same statement gives different results.

SQLite 3.49.1
--- 11-1. default placement, ascending ---

  2 | NULL
  4 | NULL
  7 | NULL
  10 | NULL
  9 | 60
  6 | 90
  3 | 150
  8 | 210
  1 | 300
  5 | 420

--- 11-2. default placement, descending ---
  id | credit
  5 | 420
  1 | 300
  8 | 210
  3 | 150
  6 | 90

SQLite puts NULL at the very front in ascending order and at the very back in descending order, treating NULL as though it were smaller than every value. DuckDB differs.

DuckDB 1.5.5
=== 8. ORDER BY NULL placement ===
  ORDER BY credit ASC               -> 60 90 150 210 300 420 NULL NULL NULL NULL
  ORDER BY credit DESC              -> 420 300 210 150 90 60 NULL NULL NULL NULL

--- 8-1. the configured default ---
  default_null_order | default_order
  NULLS_LAST | ASCENDING

DuckDB puts NULL at the back in both ascending and descending order. And this is a setting. Changing it shows as much.

=== E. DuckDB: the default NULL order is a setting ===
  default_null_order = NULLS_LAST
  as shipped                         ORDER BY v ASC -> 1 5 9 NULL
  default_null_order = NULLS_FIRST
  after SET NULLS FIRST              ORDER BY v ASC -> NULL 1 5 9
  the same query text produced two different orders on one engine

The official PostgreSQL documentation prescribes yet another rule. It states that by default null values sort as if larger than any non-null value, so that NULLS FIRST is the default for DESC order and NULLS LAST otherwise. Gathering all three into a table gives this.

All three engines differ. And this difference becomes a real incident the moment it meets LIMIT. The latest one row, the top ten, the first page of a paginated list — any code that slices the head or the tail of a sorted result silently produces a different answer when you move engines or when a setting changes.

The fix is to be explicit. Both engines supported NULLS FIRST and NULLS LAST.

--- 11-3. explicit NULLS FIRST / NULLS LAST (SQLite 3.49.1) ---
  ORDER BY credit ASC NULLS FIRST     -> NULL NULL NULL NULL 60 90 150 210 300 420
  ORDER BY credit ASC NULLS LAST      -> 60 90 150 210 300 420 NULL NULL NULL NULL
  ORDER BY credit DESC NULLS FIRST    -> NULL NULL NULL NULL 420 300 210 150 90 60
  ORDER BY credit DESC NULLS LAST     -> 420 300 210 150 90 60 NULL NULL NULL NULL

On engines that do not support the clause, the workaround of adding one more sort key built from a boolean expression works.

--- 11-4. the portable workaround when NULLS FIRST/LAST is unavailable ---
  SELECT id, credit FROM customers ORDER BY (credit IS NULL) ASC, credit ASC

  id | credit
  9 | 60
  6 | 90
  3 | 150
  8 | 210

Incidentally, sorting and MIN/MAX behave differently from each other. That was checked too.

=== C. SQLite: where NULL sorts, and what MIN/MAX think ===
  ORDER BY v ASC  -> NULL 1 5 9
  ORDER BY v DESC -> 9 5 1 NULL
  min_v | max_v | n | n_nonnull
  1 | 9 | 4 | 3
  so NULL sorts as if smaller than every value, yet MIN() skips it entirely

In sorting, NULL comes to the front as if it were the smallest value, yet MIN() ignores it entirely and returns 1. Sorting and taking the first row is not the same thing as MIN().

13. Diagnosis: finding this risk in queries you already have

Now that the mechanism is clear, it is time to audit the queries already running in production. There is an order to it.

13.1 Step 1: the thirty-second verdict query

For the suspect subquery column, this one statement is all you need.

SELECT COUNT(*)                       AS total_rows,
       COUNT(the_column)              AS non_null,
       COUNT(*) - COUNT(the_column)   AS null_rows,
       CASE WHEN COUNT(*) = COUNT(the_column)
            THEN 'SAFE for NOT IN'
            ELSE 'DANGEROUS - NOT IN returns 0 rows' END AS verdict
FROM the_table;

Here is the result on the example table.

--- 12-1. does this subquery column contain NULL at all ---
  total_rows | non_null | null_rows | verdict
  4 | 3 | 1 | DANGEROUS - NOT IN will return 0 rows

--- 12-2. the same check on a NULL-free column ---
  total_rows | non_null | verdict
  4 | 4 | SAFE for NOT IN

The criterion is simple. If COUNT(*) and COUNT(column) differ, every NOT IN against that column is already broken. The same verdict query produced the same result on DuckDB.

13.2 Step 2: check whether the schema guarantees it

Having zero NULLs today and having a schema that forbids NULL are completely different stories. The former breaks tomorrow.

--- 12-3. is the column even declared NOT NULL - read the schema ---
  name | type | notnull | pk
  req_id | INTEGER | 0 | 1
  customer_id | INTEGER | 0 | 0
  amount | INTEGER | 0 | 0

notnull for customer_id is 0, meaning the schema permits NULL. Even with no NULLs today you cannot call it safe. On PostgreSQL-family engines you look at the same thing this way.

SELECT column_name, is_nullable, data_type
FROM information_schema.columns
WHERE table_name = 'the_table';

13.3 Step 3: look at what that NULL was

Always do this before deleting anything.

SELECT * FROM the_table WHERE the_column IS NULL LIMIT 20;

As section 8 showed, that NULL is often evidence of a data defect. Look at the cause before erasing the symptom.

13.4 Step 4: run all three spellings and compare the numbers

This is the most conclusive check. Write the same intent three ways and see whether the numbers diverge. If they do, NOT IN is the culprit.

  step 1  SELECT COUNT(*) FROM t;                 -- 4
  step 2  SELECT COUNT(col) FROM t;               -- 3
  if the two numbers differ, every NOT IN against that column is already broken

13.5 Step 5: the query plan offers a hint too

Printing how the plans of the three spellings differ.

--- 13-7. query plan of the three anti-join forms (SQLite) ---
  NOT IN     : SCAN customers / USING INDEX ix_rr_cust FOR IN-OPERATOR
  NOT EXISTS : SCAN c / CORRELATED SCALAR SUBQUERY 1
               SEARCH r USING COVERING INDEX ix_rr_cust (customer_id=?)
  LEFT JOIN  : SCAN c
               SEARCH r USING COVERING INDEX ix_rr_cust (customer_id=?) LEFT-JOIN

All three use the index. That means switching to NOT EXISTS is not a choice that sacrifices performance. At this example's scale only the shape of the plan differed while index usage was equivalent. For reference, the IS NULL condition was served by the index as well.

--- 13-6. index scan still finds NULLs - IS NULL is indexable here ---
  WHERE customer_id IS NULL : SEARCH refund_requests USING INDEX ix_rr_cust (customer_id=?)
  WHERE customer_id = 1     : SEARCH refund_requests USING INDEX ix_rr_cust (customer_id=?)

14. Other traps: CHECK, CASE, strings, empty sets

A few more places where the same principle surfaces were verified.

14.1 A CHECK constraint lets UNKNOWN through

--- 13-2. CHECK constraint passes when the result is UNKNOWN ---
  insert qty=5 -> OK
  insert qty=NULL -> OK
  insert qty=-1 -> IntegrityError: CHECK constraint failed: qty > 0
  rows now: 2

CHECK (qty > 0) was in place, yet NULL passed. -1 was rejected precisely. NULL > 0 is UNKNOWN, and a constraint rejects only when the condition is false. DuckDB behaved the same. If a quantity must be positive, CHECK alone is not enough and you must add NOT NULL separately.

14.2 CASE WHEN col = NULL never fires

--- 13-1. CASE WHEN col = NULL never fires ---
  id | credit | branch
  1 | 300 | has-value
  2 | NULL | matched-is
  10 | NULL | matched-is

The WHEN credit = NULL THEN 'matched-eq' branch was never selected once. Even the NULL rows fell through to the next branch, WHEN credit IS NULL. Because = NULL is not a syntax error, it becomes quietly dead code. That is why this pattern must always be flagged in code review.

14.3 One concatenation erases the whole string

--- 13-3. string concatenation with NULL ---
  concat_result | with_coalesce
  NULL | fallback

The result of 'total: ' || NULL is not 'total: ' but NULL for the entire expression. Assemble a report string and let one column be empty, and the whole sentence disappears. This is the textbook case for using COALESCE legitimately.

14.4 With an empty list, NOT IN returns everything

--- 13-5. an empty subquery makes NOT IN return everything ---
  NOT IN (SELECT customer_id FROM refund_requests WHERE 1=0) -> 10 rows
  NOT EXISTS on the same empty set                           -> 10 rows

When the subquery yields 0 rows, NOT IN returns all 10 rows. That is logically right: everything fails to belong to an empty list. Still it is worth remembering that a single NULL sits as a switch between the two extremes of zero rows and every row. In a deletion batch or a permission filter, those two extremes produce incidents of entirely different character.

14.5 A NULL on the left makes both IN and NOT IN unknown

--- 13-4. NOT IN with NULL on the LEFT side ---
  left_null_notin | left_null_in
  NULL | NULL

This is the condensed form of what section 4.3 showed. Both NULL NOT IN (1,2) and NULL IN (1,2) are UNKNOWN. Even with no NULL in the list, a NULL on the left means that row passes neither way.

14.6 Null-safe comparison operators

There are operators available when you do want NULLs judged equal. Verified on SQLite 3.49.1.

--- 3-5. null-safe comparison operators available here ---
  is_ | is_not | isnd | isnd2 | isd
  1 | 0 | 0 | 1 | 1
  • NULL IS NULL gives 1 (true). In SQLite, IS serves as a null-safe equality
  • NULL IS NOT DISTINCT FROM NULL gives 1 (true). NULLs are judged equal
  • 1 IS NOT DISTINCT FROM NULL gives 0 (false). Definitely false, not UNKNOWN
  • 1 IS DISTINCT FROM NULL gives 1 (true)

DuckDB produced the same results (false, true, true). The IS DISTINCT FROM family never yields UNKNOWN. Even when one of the values carries unknown, the answer settles into true or false. That is useful in change-detection logic where two columns must be compared with NULL on both sides treated as equal.

15. Decision table: when to use what

Folding all the measurements into one table. This is the artefact you actually use at work.

IntentUseReason and caveat
Find rows absent from a subquery result (the most common case) NOT EXISTS Works regardless of NULL. The intent reads as a sentence, and in the measured plan it still uses the index. Make this the default
Anti-join where you also SELECT columns from the other table LEFT JOIN ... IS NULL The join result is right there to use. Apply IS NULL only to the primary key or join key — on an ordinary column 8 rows became 9
Exclude a short hard-coded list of literals NOT IN ('a','b') You can see with your own eyes that no NULL is in the list. Safe in this case only
The subquery column is declared NOT NULL NOT IN is acceptable The schema guarantees it. But one schema change breaks it. Record the dependency in a comment
You want rows with NULL included in the result state ... OR col IS NULL If the outer column is NULL that row is dropped too. The difference between 1 row and 2 rows
Judge two values equal or different with NULL included IS NOT DISTINCT FROM The result never becomes UNKNOWN. Suited to change-detection and comparison logic
Putting out an immediate fire WHERE col IS NOT NULL guard A guard, not a fix. It must be repeated everywhere, and if the NULL was information a fact disappears

Compressed into one line: make NOT EXISTS the default when searching for what is absent from a set, and use NOT IN only when the list is literal or the column is declared NOT NULL.

16. Summary: this is not a bug

Counting again what this article established.

  • One NULL in the list gave 0 rows; removing it gave 8 rows. Both queries succeeded without error
  • With the same list, IN worked correctly at 2 rows
  • The per-row condition value contained not a single 1: two falses, and the remaining eight all UNKNOWN
  • One NULL row among ten thousand (0.01 percent) turned 10 rows into 0 rows
  • NOT EXISTS gave 8 rows, LEFT JOIN IS NULL gave 8 rows, and only NOT IN gave 0 rows
  • Choosing the wrong column to test in the LEFT JOIN produced 9 rows with a wrong answer mixed in
  • The dev fixture passed at 10 rows while production data gave 0 rows — the test could not catch it
  • Two averages, 205.0 and 123.0, and a SUM of NULL over an empty set
  • Three NULLs inserted successfully into a UNIQUE column, and NULL inserted successfully past CHECK (qty > 0)
  • NULL placement in ORDER BY differed across all three engines

All of it flows from one definition. NULL does not mean absent, it means unknown. You cannot assert whether an unknown value is inside a list, so the answer is UNKNOWN, and WHERE admits only TRUE, so you get 0 rows. SQL chose to give no answer rather than a wrong one. That is the consistency of this design.

The trouble is that this consistency arrives without an error. A type error would be caught at compile time; a syntax error would be caught at execution. But this one succeeds while empty. So a person waves it away as there being no data.

The response fits in two lines. First, make NOT EXISTS the default when looking for what is absent from a set. Second, put one NULL into your test fixtures. The second is remarkably cheap and powerful. Every failure case in this article would have been caught before deployment by a single fixture row containing a NULL.

Frequently asked questions

Q. My NOT IN query returns 0 rows and there is no error. Why?

It happens whenever the list or subquery result contains even one NULL. Measured: on a 10-row table id NOT IN (1, 2, NULL) gave 0 rows and id NOT IN (1, 2) gave 8 rows, and both terminated normally. SQL logic has three values rather than two. Every comparison against NULL becomes unknown, NOT unknown is still unknown, and WHERE admits only true. No error is raised because this is not a syntax mistake but the definition applied faithfully.

Q. Why does IN work fine while only NOT IN breaks?

The difference is whether any row can reach true. IN (1, 2, NULL) gave 2 rows, the same as without the NULL. IN is equality tests joined by OR, and OR is settled by a single true even when the rest is unknown. With NOT IN, no row can reach true. Printing the per-row values showed 0 for rows 1 and 2 and NULL for the remaining 8 rows. There was not one true anywhere.

Q. Does rewriting to NOT EXISTS really fix it?

It does. On the same data NOT IN gave 0 rows, NOT EXISTS gave 8 rows, and LEFT JOIN IS NULL gave 8 rows. NOT EXISTS decides on the existence of a row rather than on a value comparison, so UNKNOWN has nowhere to fit. A row whose referencing column is NULL fails the equality and simply never matches; counting matches per customer showed that row attached to no customer at all. The LEFT JOIN form has its own trap, though: applying IS NULL to an ordinary column rather than the primary key gave 9 rows with a wrong answer mixed in.

Q. Cannot I just add IS NOT NULL inside the subquery?

It works (8 rows). But it is a guard, not a fix. First, it must be repeated at every site using NOT IN, and missing one leaves that query silently at 0 rows. Second, it is invisible to anyone reading only the outer query, so it gets deleted during refactoring. Third, if the NULL was information, the meaning changes. In the example that row was a request for an amount of 7000 with no customer attached — evidence that referential integrity broke. The real remedies are a NOT NULL constraint or changing the spelling to NOT EXISTS.

Q. Where else does NULL silently produce wrong answers?

At least five places were verified. In aggregates, COUNT(*) was 10 while COUNT(credit) was 6, and the average split into 205.0 and 123.0. Over an empty set, COUNT gave 0 but SUM, AVG, and MAX gave NULL. A UNIQUE constraint accepted three NULLs. In GROUP BY, NULLs that = refuses to call equal formed one group. In ORDER BY, SQLite put NULL at the front of an ascending sort while DuckDB put it at the back, so the answer differed by engine.

## 0. Symptom card — when you need this file

- The query succeeded. **There was no error.**
- The result is **0 rows**.
- It worked yesterday. Or it works on the development database.
- The query contains `NOT IN (SELECT ...)`.

→ Run the diagnostic SQL in §3. It takes thirty seconds.

## 1. Three-valued logic truth tables

SQL logic has three values, not two: **TRUE / FALSE / UNKNOWN**.

### 1-1. Comparison operators meeting NULL

| Expression | Result | Note |
|---|---|---|
| `1 = 1` | TRUE | |
| `1 = 2` | FALSE | |
| `1 = NULL` | **UNKNOWN** | not FALSE |
| `1 <> NULL` | **UNKNOWN** | not TRUE |
| `NULL = NULL` | **UNKNOWN** | you cannot even claim they differ |
| `1 > NULL` | **UNKNOWN** | every comparison operator behaves this way |
| `NULL IS NULL` | TRUE | only `IS` yields a definite answer |
| `1 IS NULL` | FALSE | |

### 1-2. AND / OR / NOT

| Expression | Result |
|---|---|
| `UNKNOWN OR TRUE` | **TRUE** |
| `UNKNOWN OR FALSE` | UNKNOWN |
| `UNKNOWN AND TRUE` | UNKNOWN |
| `UNKNOWN AND FALSE` | **FALSE** |
| `NOT UNKNOWN` | **UNKNOWN** |

How to read it: OR is settled by a single TRUE. AND is settled by a single FALSE. **Everywhere else, unknown is contagious.**

### 1-3. WHERE admits only TRUE

| Value of the WHERE clause | That row |
|---|---|
| TRUE | kept |
| FALSE | dropped |
| **UNKNOWN** | **dropped** |

This single rule — UNKNOWN is treated like FALSE at the filter — is the exit through which every one of these bugs escapes.

### 1-4. Which is why IN survives and NOT IN dies

`x IN (a, b, c)` expands to `x = a OR x = b OR x = c`.

| Case | `IN (1, 2, NULL)` | `NOT IN (1, 2, NULL)` |
|---|---|---|
| x = 1 (present in list) | `TRUE OR ... OR UNKNOWN` = **TRUE** → kept | `NOT TRUE` = **FALSE** → dropped |
| x = 7 (absent from list) | `FALSE OR FALSE OR UNKNOWN` = **UNKNOWN** → dropped | `NOT UNKNOWN` = **UNKNOWN** → dropped |

- `IN` still yields TRUE for matching rows, so it **works correctly**.
- `NOT IN` yields TRUE for no row at all. Matching rows give FALSE, non-matching rows give UNKNOWN. **So it always returns zero rows.**

## 2. Anti-join comparison table

Three ways to express *in A but not in B*. These are measured results on identical data: 10 customer rows, 4 request rows of which 1 has a NULL in the referencing column.

| Form | Result | NULL-safe | Decides on | Caveat |
|---|---|---|---|---|
| `NOT IN (SELECT col FROM t)` | **0 rows** | no | three-valued logic | a single NULL in col wipes everything. No error raised |
| `NOT EXISTS (SELECT 1 FROM t WHERE t.col = a.id)` | **8 rows** | yes | existence of a row | the NULL row simply fails `=` and never matches |
| `LEFT JOIN t ON t.col = a.id WHERE t.pk IS NULL` | **8 rows** | yes | rows that failed to match | **test `IS NULL` on a NOT NULL column, i.e. the key** |

Only `NOT IN` gave a different answer. The other two agree.

### 2-1. The trap inside the LEFT JOIN form

Pick the wrong column to test and it fails quietly.

| Column tested | Result | Verdict |
|---|---|---|
| `r.req_id IS NULL` (primary key, never NULL in a matched row) | 8 rows | correct |
| `r.amount IS NULL` (an ordinary nullable column) | **9 rows** | wrong — a customer who did request a refund leaked in |

**Rule: in a LEFT JOIN anti-join, apply `IS NULL` only to the join key or the primary key.**

### 2-2. Decision table by intent

| What you want | Use | Why |
|---|---|---|
| Rows absent from a subquery result | **`NOT EXISTS`** | NULL-immune, and the intent reads as a sentence |
| Anti-join where you must also SELECT columns from the other table | **`LEFT JOIN ... IS NULL`** | the join result is right there to use |
| Exclude a short hard-coded list of literals | `NOT IN ('a','b')` | you can see with your eyes that no NULL is in the list |
| The subquery column is **declared `NOT NULL`** | `NOT IN` is acceptable | but a schema change can break it at any time |
| You intend rows with a NULL value to be included | state `... OR col IS NULL` **explicitly** | if the outer column is NULL, that row is dropped too |

## 3. Diagnostic SQL — copy and paste

### 3-1. Is this column safe for NOT IN (thirty seconds)

```sql
SELECT COUNT(*)                       AS total_rows,
       COUNT(the_column)              AS non_null,
       COUNT(*) - COUNT(the_column)   AS null_rows,
       CASE WHEN COUNT(*) = COUNT(the_column)
            THEN 'SAFE for NOT IN'
            ELSE 'DANGEROUS - NOT IN returns 0 rows' END AS verdict
FROM the_table;
```

If `COUNT(*)` and `COUNT(column)` differ, **every `NOT IN` against that column is already broken.**

### 3-2. Does the schema guarantee NOT NULL

```sql
-- SQLite
SELECT name, type, "notnull", pk FROM pragma_table_info('the_table');

-- PostgreSQL family
SELECT column_name, is_nullable, data_type
FROM information_schema.columns
WHERE table_name = 'the_table';
```

Unless you see `is_nullable = 'NO'` (or SQLite `notnull = 1`), **zero NULLs today is not safety.** They arrive tomorrow.

### 3-3. Look at what the NULL actually meant

```sql
SELECT * FROM the_table WHERE the_column IS NULL LIMIT 20;
```

Run this before deleting anything. Very often the NULL is **evidence of a data bug**. In the worked example it was a refund request with no customer attached.

### 3-4. Run all three and compare the numbers

```sql
SELECT 'not_in'     AS form, COUNT(*) AS n FROM (
  SELECT id FROM customers WHERE id NOT IN (SELECT customer_id FROM refund_requests)
)
UNION ALL
SELECT 'not_exists', COUNT(*) FROM (
  SELECT c.id FROM customers c
  WHERE NOT EXISTS (SELECT 1 FROM refund_requests r WHERE r.customer_id = c.id)
)
UNION ALL
SELECT 'left_join', COUNT(*) FROM (
  SELECT c.id FROM customers c
  LEFT JOIN refund_requests r ON r.customer_id = c.id
  WHERE r.req_id IS NULL
);
```

If the three numbers disagree, the first one is the culprit.

### 3-5. Do not forget the outer column

Even with no NULL in the list, a NULL in **the column being compared** drops that row.

```sql
-- rows whose region is NULL vanish from this condition
SELECT * FROM t WHERE region NOT IN ('seoul');

-- to include them you must say so
SELECT * FROM t WHERE region NOT IN ('seoul') OR region IS NULL;
```

## 4. Other places NULL hides — summary

| Place | Behaviour | Measured value (10 rows, 4 NULLs) |
|---|---|---|
| `COUNT(*)` | counts rows | 10 |
| `COUNT(col)` | **excludes NULL** | 6 |
| `SUM` / `AVG` / `MIN` / `MAX` | **ignore NULL** | AVG = 205.0 |
| `AVG(COALESCE(col, 0))` | counts NULL as zero | **123.0** — a different answer |
| `SUM` / `AVG` / `MAX` over an empty set | **returns NULL**, not 0 | NULL |
| `UNIQUE` constraint | **allows many NULLs** | 3 NULLs inserted successfully |
| `GROUP BY` | **all NULLs form one group** | one NULL group of 2 rows |
| `SELECT DISTINCT` / `UNION` | **dedupe NULLs** | 3 distinct values |
| `CHECK` constraint | passes when the result is UNKNOWN | NULL accepted by `CHECK (qty > 0)` |
| `CASE WHEN col = NULL` | **never fires** | always use `IS NULL` |
| Concatenation `'a' \|\| NULL` | **NULL** | the whole string disappears |

`UNIQUE` treats NULLs as distinct while `DISTINCT` treats them as equal. **The rules are opposite inside the same engine.**

## 5. NULL placement in ORDER BY — engines disagree

| Engine | `ORDER BY col ASC` | `ORDER BY col DESC` | Evidence |
|---|---|---|---|
| SQLite 3.49.1 | **NULLs first** | NULLs last | measured |
| DuckDB 1.5.5 (default settings) | NULLs last | **NULLs last** | measured |
| PostgreSQL | NULLs last | **NULLs first** | official manual |

All three differ. **Any code that slices the head or tail of an ORDER BY result — LIMIT, pagination, latest-one-row — silently changes answers the moment you move engines.**

The portable fix:

```sql
-- state it explicitly (SQLite 3.30+, PostgreSQL, DuckDB all support this)
SELECT * FROM t ORDER BY col ASC NULLS LAST;

-- workaround on engines without the clause
SELECT * FROM t ORDER BY (col IS NULL) ASC, col ASC;
```

## 6. Code review checklist — copy into your review comments

- [ ] **Did you check in the schema that this `NOT IN` subquery column is declared `NOT NULL`?** Having no NULLs right now is not the same as the schema forbidding them.
- [ ] **Can this `NOT IN (SELECT ...)` be rewritten as `NOT EXISTS`?** If it can, it should be. Performance is usually equal or better.
- [ ] **If you added a `WHERE col IS NOT NULL` guard to the subquery, is there a comment explaining why discarding that NULL is correct?** A guard hides the symptom; it does not fix the cause.
- [ ] **In the LEFT JOIN anti-join, is `IS NULL` applied to the primary key or the join key?** Applied to an ordinary nullable column, matched rows leak into the result.
- [ ] **Can the outer column being compared be NULL?** If so, confirm that dropping those rows is intended; otherwise state `OR col IS NULL`.
- [ ] **Are there any conditions written as `= NULL` or `<> NULL`?** They are always UNKNOWN. Change them to `IS NULL` / `IS NOT NULL`.
- [ ] **Between `COUNT(col)` and `COUNT(*)`, did you use the one you meant?** The former excludes NULLs.
- [ ] **Should the denominator of `AVG` be the row count or the non-NULL count?** The default is the latter. If you want the former, say it with `COALESCE`.
- [ ] **If you are slicing an `ORDER BY` result with `LIMIT`, did you state `NULLS FIRST/LAST`?** Engine defaults differ from each other.
- [ ] **Do the test fixtures contain NULLs?** Hand-written fixtures usually do not, which is why this bug passes tests and only fires in production.
- [ ] **If you claim `UNIQUE` prevents duplicates, does it also prevent them when the column is NULL?** On most engines several NULLs go in.
- [ ] **Are you assuming a `CHECK` constraint also blocks NULL?** It passes when the condition is UNKNOWN. Add `NOT NULL` separately.

## 7. One-paragraph summary

`NOT IN` is not a broken feature. It is the consequence of taking the definition of NULL — unknown — all the way to its conclusion. **You cannot assert whether an unknown value is inside a list, so the answer is UNKNOWN, and WHERE admits only TRUE, so you get zero rows.** That is logically correct. The problem is that this correctness arrives **without an error**, which lets everyone conclude that there must not be any data. So the rule is single: **make `NOT EXISTS` the default when searching for what is absent from a set, and reserve `NOT IN` for literal lists or for columns declared `NOT NULL`.**
