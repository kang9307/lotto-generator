はじめに - 文法に反しないのに値が決まらない文書

{"a":1,"a":2} のような文書は JSON の文法に違反しない。RFC 8259 のオブジェクト文法は member をカンマでつなぐ規則だけを定め、名前の重複を禁じる条件を置いていない。一意性は文法ではなく「SHOULD be unique」という推奨の一文として残っているだけである。そのため、同じバイト列を受け取った二つのプログラムが異なる値を読むことが起こりうる。

この差は、パーサーを一つしか使わないプログラムでは表に出ない。一度パースしてその結果を最後まで使えば、最後の値でも最初の値でも一貫するからである。問題は同じ文書を二度読む構造で生じる。前段がリクエスト本文を検査し、後段が同じ本文を再びパースして使う場合が典型である。64 ビット ID の精度の記事の 13 節は重複キーを数値精度の話の中の一項目として扱った。この記事はその一項目を、パーサー別の比較・検出・再現へ広げたものである。

扱う問いは次のとおりである。

  • 仕様書は重複キーについて何と書いているか。
  • node・Python・PowerShell 5.1 は同じ文書からそれぞれどんな値を出すか。
  • キーの順序、大文字小文字だけが異なるキー、エスケープで書いたキーは重複として扱われるか。
  • サーバー側のパーサーもローカル呼び出しと同じ値を出すか。
  • 重複キーを検出するスクリプトはどう書くか。
  • 検証する層と使う層が異なる値を見たとき、実際に何が通り、どう防ぐか。

仕様と公式文書の記述

RFC 8259 の 4 節、ECMAScript 仕様の JSON.parse、Python の json モジュール文書、Microsoft Learn の ConvertFrom-Json 文書(5.1)で、重複キーを扱っている文を示す。原文は英語のまま載せる。

出典原文意味
RFC 8259 4The names within an object SHOULD be unique.名前の一意性は推奨
RFC 8259 4When the names within an object are not unique, the behavior of software that receives such an object is unpredictable. Many implementations report the last name/value pair only. Other implementations report an error or fail to parse the object, and some implementations report all of the name/value pairs, including duplicates.重複時の動作は予測不能。最後の組のみ報告、エラー、全組報告の実装がいずれも存在する
ECMAScript JSON.parseIn the case where there are duplicate name Strings within an object, lexically preceding values for the same key shall be overwritten.仕様が先の値は上書きされると規定
Python json docsBy default, this module does not raise an exception; instead, it ignores all but the last name-value pair for a given name既定では例外なしで最後の組のみ使用。object_pairs_hook で変更可能と記載
Microsoft Learn ConvertFrom-Json (5.1)if the JSON string contains duplicate keys, only the last key is used by this cmdlet重複キーがあれば最後のキーのみ使用

表から整理できるのは四点である。

  • RFC は一意性を推奨するだけで、重複時の動作を最後の値・エラー・全件報告の三通り挙げたうえで予測不能と書く。
  • ECMAScript 仕様は JSON.parse で先の値が上書きされると直接規定している。JavaScript における「最後の値が勝つ」は慣行ではなく仕様の文である。
  • Python と PowerShell の文書も最後の値を使うと記している。こちらは当該実装の文書化された動作である。
  • RFC が開いたままにしている「エラー」と「全件報告」の動作は、Python の object_pairs_hook のような拡張点で実装できる。

  • 配列内のオブジェクトはオブジェクトごとに判定された。最初のオブジェクトだけ k が 2 になり、二つ目の k は 3 のまま残った。
  • Python の object_pairs_hook=list は [('a', 1), ('a', 2)] を返した。パーサーは両方の組を読んでおり、一つだけを残すのはその後の dict を作る段階の仕事である。

値は最後のもの、位置は最初のもの

表の二行目 {"a":1,"b":2,"a":3} の結果は、三つのランタイムともに {"a":3,"b":2} だった。a の値は最後の出現(3)から来たが、キーの位置は b より前、つまり最初の出現の位置に残った。キーの順序を読んで先頭フィールドを判断したり順に処理したりするコードが重複キーの文書を受け取ると、値は後ろのもの、順序は前のものという組み合わせに出会う。

JavaScript では reviver 関数でパースの途中を覗ける。前の node 出力の最終行で、reviver が受けた呼び出しは a=2 とルートオブジェクトの二件だけだった。値 1 は reviver に渡されなかった。

  • JSON.parse が返したオブジェクトにはキーが一つだけ(keys=1)で、重複があった痕跡はない。
  • reviver も上書きされた値を受け取らなかった。この実行では reviver で重複の事実を知ることはできなかった。
  • Python には object_pairs_hook があり、パーサーが読んだ組のリスト自体を受け取れた。検出スクリプトはこの差の上に置かれる(7 節)。

同じに見えない同じキー

表の四行目は a と A である。node と Python は両者を別のキーとして扱い、キー 2 個を残した。PowerShell 5.1 は変換自体が失敗し、InvalidOperationException が出た。同じ文書をある層は受け入れ、ある層は拒否する。この PC の韓国語ロケールでは、例外メッセージに「重複したキー 'a' と 'A'」を意味する句(原文は韓国語で、ここでは訳した)が含まれた。メッセージ自体が重複キーを拒否の理由として書いているため、PowerShell 5.1 は大文字小文字だけが異なるキーも重複と判定したと読める(文言はロケールによって異なる)。

五行目はキーをエスケープで書いた場合である。文書内の "\u0061" はデコードすると a と同じ名前になる。三つのランタイムともこれを重複とみなし、最後の値 2 だけを残した。この事実が文字列検索方式の検証にとって何を意味するかを次のスクリプトが示す。キー role が一度しか見えないように、二つ目のキーをエスケープで書いた文書である。

import json

                    print("text search : " + str(text.count('"role"')) + ' occurrence of "role"')

                    print("parsed pairs: " + str(pairs))
                    print("parsed dict : " + str(json.loads(text)))

                    text search : 1 occurrence of "role"
                    parsed pairs: [('role', 'user'), ('role', 'admin')]

  • 元のテキストでは "role" は 1 件しか検索されなかったが、パーサーは role の組を二つ読み、dict には最後の値 admin が残った。
  • 文字列検索や正規表現でキーを数える検証は、エスケープで書かれた重複を見逃す。検証はパーサーがデコードした後のキーを基準にする必要がある。
  • 大文字小文字だけが異なるキーはランタイムごとに異なる扱いを受けた。パーサーを複数使う構造では、この差も同じ文書が層ごとに異なって読まれる経路になる。

サーバー側のパーサーも同じか

同じ本文を curl で送った二つのローカル HTTP サーバーの応答である。一つは Python 標準ライブラリの http.server と json.loads、もう一つは node の http モジュールと JSON.parse である。どちらもパース結果をシリアライズして応答本文として返す。

import json
                    from http.server import BaseHTTPRequestHandler, HTTPServer
                    
                    class H(BaseHTTPRequestHandler):
                        def do_POST(self):
                            body = self.rfile.read(int(self.headers["Content-Length"]))
                            out = json.dumps(json.loads(body), separators=(",", ":")).encode()
                            self.send_response(200)
                            self.send_header("Content-Type", "application/json")
                            self.send_header("Content-Length", str(len(out)))
                            self.end_headers()
                            self.wfile.write(out)
                        def log_message(self, *a):
                            pass
                    
                    HTTPServer(("127.0.0.1", 18081), H).serve_forever()

  • Python サーバーも node サーバーも {"a":2} を返した。サーバー側パーサーの結果はローカル呼び出しの結果と同じだった。

重複キーを検出するスクリプト

Python の文書が object_pairs_hook を「組のリストを受け取り dict の代わりに戻り値を使う拡張点」と記しているので、組を dict に入れる途中で既存のキーかどうかを検査すれば検出器になる。下のスクリプトは一行に JSON 文書一つが入ったファイルを読み、行ごとに判定する。

import json, sys
                    
                    def reject_duplicates(pairs):
                        obj = {}
                        for key, value in pairs:
                            if key in obj:
                                raise ValueError("duplicate key " + repr(key) + ": " + repr(obj[key]) + " then " + repr(value))
                            obj[key] = value
                        return obj
                    
                    for lineno, line in enumerate(open(sys.argv[1], encoding="utf-8"), 1):
                        text = line.rstrip("\n")
                        try:
                            json.loads(text, object_pairs_hook=reject_duplicates)
                            print(str(lineno) + ": OK    " + text)
                        except ValueError as err:
                            print(str(lineno) + ": FAIL  " + text)
                            print("    " + str(err))

入力ファイルは七行で、最後の行はわざと壊した文書である。実行結果は次のとおりである。

1: OK    {"a":1,"b":2}
                    2: FAIL  {"a":1,"a":2}
                        duplicate key 'a': 1 then 2
                    3: OK    {"a":1,"A":2}
                    4: FAIL  {"a":1,"\u0061":2}
                        duplicate key 'a': 1 then 2
                    5: FAIL  {"l":[{"k":1,"k":2},{"k":3}]}
                        duplicate key 'k': 1 then 2
                    6: OK    {"a":1,"b":{"a":2}}
                    7: FAIL  {"a":1,
                        Expecting property name enclosed in double quotes: line 1 column 8 (char 7)
  • 2 行目(a が二度)と 5 行目(配列内オブジェクトの k が二度)が検出された。hook はオブジェクトごとに呼ばれるため、入れ子のオブジェクト内の重複も捕まった。
  • 4 行目のエスケープで書いた a も検出された。前節の文字列検索と違い、デコード後のキーを見ているからである。
  • 3 行目(a と A)と 6 行目(外側の a と内側の a)は通過した。この検出器は同じオブジェクト内の完全に同じ名前だけを重複とみなす。
  • 7 行目は重複ではなく構文エラーとして検出され、同じ except ValueError の下でメッセージだけが異なった。構文エラーと重複を区別するには、例外の型を分けて受ける必要がある。

二つの層が異なる値を見る再現

構成は二つである。前段のゲートウェイ(Python)はリクエスト本文をパースして role が admin なら 403 で拒否し、通したリクエストの元のバイト列をそのまま後段(node、先の echo サーバー)へ渡す。後段は JSON.parse で読んだ結果を返すので、応答がそのまま後段の見た値である。ゲートウェイのパーサーは object_pairs_hook で「既にあるキーは上書きしない」最初の値優先の方針を自前で実装した。この PC の標準パーサー三つはいずれも最後の値優先なので、方針の異なる二つの層はこのように作る必要があった。この方針の違いはデモ用に決めた仮定であり、実際の製品のどれが最初の値優先かを示すものではない。

import json, os, sys, urllib.request

                        return obj
                    
                    class H(BaseHTTPRequestHandler):
                        def reply(self, code, text):
                            data = text.encode()
                            self.send_response(code)
                            self.send_header("Content-Length", str(len(data)))
                            self.end_headers()
                            self.wfile.write(data)
                    
                        def do_POST(self):
                            body = self.rfile.read(int(self.headers["Content-Length"]))
                            hook = reject_duplicates if MODE == "reject" else first_wins
                            try:
                                doc = json.loads(body, object_pairs_hook=hook)
                            except ValueError as err:
                                return self.reply(400, "gateway: 400 " + str(err))
                            if doc.get("role") == "admin":
                                return self.reply(403, "gateway: 403 role admin is not allowed")
                            forward = json.dumps(doc).encode() if MODE == "canonical" else body
                            req = urllib.request.Request(BACKEND, data=forward, method="POST")
                            with urllib.request.urlopen(req) as r:
                                self.reply(200, "gateway: passed; backend saw " + r.read().decode())
                    
                        def log_message(self, *a):
                            pass
                    
                    HTTPServer(("127.0.0.1", PORT), H).serve_forever()

  • リクエスト 5 は role が user、admin の順に二度現れる本文である。ゲートウェイは最初の値 user を見て通し、後段は最後の値 admin を読んだ。拒否すべき値が検証を通り抜けて後段に届いた。
  • リクエスト 8 は二つの値の順序だけを入れ替えた本文である。今度はゲートウェイが最初の値 admin を見て 403 で拒否した。変数を順序一つに絞ることで、ゲートウェイが最初の値を読むことが出力で切り分けられる。
  • リクエスト 3 と 4 は対照群である。重複のない本文では、ゲートウェイの判定と後段の値は一致した。
  • どちらかのパーサーが間違っているわけではない。RFC が予測不能と書く領域で、二つの層がそれぞれ異なる選択をしただけである。問題は、検証した文書と使った文書が同じバイト列でありながら同じ値ではない点にある。

防ぐ方法は二つ - 拒否するか、検証したものを渡すか

同じゲートウェイのコードでモードだけを変えて二つの方法を実行した。reject モードは既存のキーに出会うとパースを失敗させ 400 で返す。canonical モードはゲートウェイがパースしたオブジェクトを再度シリアライズして後段へ送る。リクエストは前節のリクエスト 5 と同じ本文で、結果は run.sh の 6 番と 7 番の出力である。

方法ゲートウェイの動作リクエスト 5 と同じ本文の結果
重複を拒否 (reject)重複キーでパース失敗、後段は呼ばないgateway: 400 duplicate key 'role'
検証したオブジェクトをシリアライズして転送 (canonical)元のバイト列の代わりに、ゲートウェイがパースしたオブジェクトから作り直した JSON を転送gateway: passed; backend saw {"user":"alice","role":"user"}
修正なし (raw)元のバイト列をそのまま転送gateway: passed; backend saw {"user":"alice","role":"admin"}
  • reject はリクエストが後段に届く前に 400 で止めた。重複キーを意図して送る正当なクライアントがあれば、そのリクエストも 400 を受ける。
  • canonical では後段がゲートウェイの検証した値 user を受け取った。この方式はゲートウェイが最初の値を選ぶという方針を後段に強制した結果なので、クライアントの意図した値が最後のものだった場合は別の値が使われる。
  • 二つの方法の共通点は、検証したオブジェクトと使うオブジェクトが同じ値を持つようにすることである。一方は文書を受け入れず、他方は文書を一度だけ解釈してその結果を渡す。
  • 前節の例が示したのは、検証層と消費層が元のバイト列をそれぞれ再度パースする構造である。信頼境界を越える入力を一度だけ解釈する構造は、クライアント信頼境界の記事が扱った原則につながる。

実務で点検する項目は次のとおりである。

  • 同じリクエスト本文を二度以上パースする層があるか。あるなら、パーサーの種類と設定は同じか。
  • 検証はパーサーがデコードしたキーを基準にしているか、元のテキストの検索を基準にしているか。
  • 重複キーを受けたら拒否するのか、一つの方針に正規化して渡すのか決めてあるか。
  • 検証した値と後段が受け取るバイト列が一致するかを確認しているか。前の出力では、canonical モードの後段が受け取った本文は元のバイト列ではなく、ゲートウェイが作り直した JSON だった。

確認できなかったこと

  • node・Python・PowerShell 5.1 以外のランタイム(Go・Java・Ruby・PHP・jq など)の動作。RFC が書く「エラーを出す実装」と「全件を報告する実装」の実例は、Python の object_pairs_hook=list を除いて実行できなかった。
  • PowerShell 7 と .NET の System.Text.Json。この PC には pwsh がなく、5.1 では当該クラスを使っていない。
  • PowerShell 5.1 で大文字小文字だけが異なるキーがエラーになる理由。文書は重複キーが PSObject と Hashtable で禁止されると書き、この PC の韓国語ロケールの例外メッセージにも「重複したキー 'a' と 'A'」を意味する句が含まれていて、重複キーの規則が原因であることを直接示している。確認できていないのは、他のロケールでのメッセージの文言と、この規則を適用する .NET 内部の経路である。
  • node で重複キーを検出する方法。この実行では JSON.parse の結果と reviver では重複の事実を得られず、他の方法は試していない。
  • ゲートウェイの最初の値優先の方針はデモ用に自前で実装したものである。実際の製品・ライブラリ・プロキシに最初の値を選ぶものがあるかは確認できなかった。
  • Python 標準の http.server と node の http モジュール以外の Web フレームワークの本文パーサー、および Content-Type・文字エンコーディングのヘッダーが結果に与える影響。
  • PostgreSQL jsonb や MongoDB などのストアが入力時に重複キーを処理する方式。この PC では実行していない。
  • 非常に大きな文書やストリーミングパーサーでの動作と性能、JSON5 のような拡張構文での重複キーの扱い。
