序論：圧縮ライブラリをRustで書き直す理由

2026年6月のnews.hada.ioで話題になったトピックの一つが、Rustで実装したZstandardの発表でした。すでに数年Cで問題なく動いている圧縮ライブラリをわざわざRustで書き直すという知らせに、「なぜ？」という反応と「ついに」という反応が同時に出ました。私の見方では、これは単なる言語の好みの論争ではなく、信頼できない外部入力を解析するシステムソフトウェアがメモリ安全言語へ移行する大きな流れの一場面です。

圧縮ライブラリは目立ちませんが、ほぼすべてのシステムの裏側で動いています。Webサーバーが応答を圧縮するとき、データベースがディスクへデータを書くとき、コンテナレジストリがイメージを転送するとき、バックアップツールがファイルをアーカイブするとき、いずれも圧縮コーデックが呼ばれます。そしてこれらは多くの場合、ネットワークやファイルから受け取った制御不能なデータを展開します。展開過程にメモリバグが1つでもあれば、攻撃者は悪意を持って細工した圧縮ファイル1つでサーバーを掌握できます。

1. Zstandardとは - zstd圧縮アルゴリズム概要

Zstandard（略してzstd）は、Facebook、現在のMetaが開発し2016年に公開した汎用可逆圧縮アルゴリズムです。公式リポジトリはgithub.com/facebook/zstdでライセンスはBSDです。設計目標は明確でした。gzipレベルの圧縮率を保ちつつ、圧縮・展開速度を大幅に引き上げることです。

zstdが他のアルゴリズムと区別される特徴は3つです。第一に、圧縮レベルが1から22まで幅広く調整できます。レベル1はlz4に近い速度で軽く圧縮し、レベル19〜22はbrotliに近い高圧縮率を出します。1つのアルゴリズムでリアルタイムからアーカイブまでカバーします。第二に、辞書学習機能です。JSONメッセージのように構造が似た小さなデータを繰り返し圧縮するとき、事前学習した辞書を使うと圧縮率が劇的に良くなります。第三に、ストリーミングAPIがきれいで、大容量ファイルをメモリに全て載せずに処理できます。

内部的にはzstdは、FSE（Finite State Entropy）とHuffman符号を組み合わせたエントロピーエンコーダの上にLZ77系の辞書マッチングを載せた構造です。理論に深入りしなくても、本人が強調したいのはzstdが2020年代の事実上の圧縮標準になったという事実です。Linuxカーネル、RocksDB、Parquet、ZFS、btrfs、そして多数のパッケージマネージャがzstdを採用しています。

2. なぜRustで再実装するのか - メモリ安全性の価値

うまく動くCライブラリをわざわざRustで書き直す理由は、たった一語に集約されます。メモリ安全性です。なぜこの価値を強調するのか説明します。

CとC++は強力で速いですが、メモリを手動で管理します。ポインタ演算、手動の確保・解放、境界検査の不在は、すぐにバッファオーバーフロー、use-after-free、double free、整数オーバーフローにつながります。これらは単なるバグではなくセキュリティ脆弱性です。MicrosoftとGoogleが公開した統計によれば、自社のセキュリティ脆弱性の約70%がメモリ安全の問題に由来します。

Rustは所有権（ownership）と借用チェッカー（borrow checker）でこの問題をコンパイル時に遮断します。ガベージコレクタなしで、ランタイムオーバーヘッドなしで、メモリ安全を静的に保証します。つまりzstdのような圧縮コーデックをRustで書き直せば、「信頼できない入力を解析してメモリ破壊が起きる」種類のCVEを構造的に除去できます。本人の視点では、これがRust再実装の本質であり、わずかな初期性能の損失を受け入れる十分な理由です。

核心 - 圧縮ライブラリはほぼ常に「外部から受け取った制御不能なデータ」を展開します。この地点こそ、メモリ安全言語が最大の価値を発揮する領域です。

3. C実装の危険 - 圧縮ライブラリのセキュリティ脆弱性の歴史

抽象的な危険ではありません。圧縮ライブラリは実際に深刻なCVEを繰り返してきました。本人が記憶する代表例を整理します。

3-1) zlibと展開爆弾

最も広く使われるzlibは数十年磨かれましたが、その上で動く多数のラッパーやパーサーで展開関連の脆弱性が絶えず見つかってきました。「圧縮爆弾（zip bomb）」のように、小さな圧縮ファイルが展開時に巨大なメモリを占有させる攻撃は今も有効です。

3-2) 整数オーバーフローとヒープ破壊

圧縮フォーマットは長さ・オフセットフィールドを扱います。Cでこの値を検証なしに掛けたり足したりすると整数オーバーフローが発生し、その結果ヒープバッファが誤ったサイズで確保され、ヒープ破壊につながります。圧縮コーデックで繰り返し報告される典型パターンです。

3-3) XZ Utilsバックドア事件（2024年）

2024年に発見されたXZ Utils（liblzma）バックドア事件は、圧縮ライブラリがサプライチェーン攻撃の標的になりうることを衝撃的に示しました。これはメモリ安全とは別次元の問題（サプライチェーン・信頼）ですが、圧縮ライブラリがシステム深くに埋め込まれており、一度突破されると被害が広範囲に及ぶことを皆に刻みつけました。

本人が強調したい結論はこれです。圧縮コーデックは「うまく動くから触らない」領域ではなく、最優先でメモリ安全性を確保すべきセキュリティ中核コンポーネントです。Rust再実装はこの認識の自然な帰結です。

4. Rust再実装の5つの利点

本人が整理した、圧縮ライブラリをRustで再実装したときの5つの実質的利点です。

4-1) メモリ安全

最大の利点です。バッファオーバーフロー・use-after-free・double freeをコンパイラが遮断します。unsafeブロックを最小化すれば、信頼できない入力を解析してもメモリ破壊系の脆弱性が根本から封じられます。

4-2) 安全な並行性

Rustの所有権モデルはデータ競合をコンパイル時に防ぎます。圧縮はブロック単位の並列化が自然な作業で、Rustではrayonのようなライブラリで安全なマルチスレッド圧縮を実装しやすいです。

4-3) 統合の容易さ

Rustクレートはcargo一行で依存を追加します。Cライブラリ特有のビルドシステム地獄（autotools、CMake、ヘッダパス）なしに、純Rust実装ならクロスコンパイルやWASMビルドも滑らかです。

4-4) 保守性

Rustの強い型システムとパターンマッチは、圧縮フォーマットパーサーのように状態が複雑なコードをより安全で読みやすくします。コンパイラが捕まえる領域が広く、リファクタリングの負担が減ります。

4-5) 信頼

上の4つが合わさり、結局信頼になります。「このライブラリは悪意ある入力を受けてもメモリ破壊がない」という保証は、セキュリティが重要なインフラでの採用判断を大きく早めます。本人の視点では、この信頼こそRust再実装の真の資産です。

5. 圧縮アルゴリズム比較 - gzip / lz4 / zstd / brotli

本格的にzstdを評価する前に、主要圧縮アルゴリズム4つを一つの表に整理します。本人の実践経験と公開ベンチマークを総合した比較マトリクスです。

アルゴリズム圧縮率速度適した用途
gzip普通普通汎用、レガシー互換
lz4低い非常に速いリアルタイム処理
zstd高い速いバランス（主流）
brotli非常に高い遅いWeb静的資源

本人が整理した選択基準は単純です。特別な理由がなければzstdを既定にし、極端な速度が必要ならlz4、一度圧縮して何度も配信するWeb静的資源はbrotli、古いシステムとの互換が必要ならgzipです。4つのうちどれも全状況で最良ではなく、zstdの強みは「最も広い領域で無難に1位」というバランス感です。

6. Zstandardが人気の理由 - 速度と圧縮率のバランス

zstdが短期間で事実上の標準になった理由を本人視点で整理します。

6-1) バランス感

5章の表のとおり、zstdは圧縮率は高く、速度は速いです。多くのワークロードは「圧縮率も速度もそこそこ良い」必要があり、zstdが正確にその位置を占めます。gzipより速く、より良く圧縮し、lz4よりはるかに良く圧縮します。

6-2) レベルチューニングの自由

圧縮レベル1〜22一つで、リアルタイム（レベル1〜3）からアーカイブ（レベル19〜22）まで一つのツールでカバーします。運用中にレベルだけ変えて速度・容量のトレードオフを調整できる柔軟性は、本人が見た最も実用的な強みです。

6-3) 辞書学習

小さなメッセージを大量に圧縮する環境（例：マイクロサービス間のJSONメッセージ、IoTセンサーデータ）で、辞書学習は圧縮率を2〜5倍引き上げます。gzipにはないzstdだけの決定的武器です。

6-4) エコシステムの採用

Linuxカーネル（initramfs・モジュール圧縮）、ZFS・btrfsファイルシステム、RocksDB・Parquet、Arch・Fedoraパッケージマネージャ、多数のコンテナレジストリがzstdを既定で採用しています。採用が採用を呼ぶ好循環が定着しました。

7. Rustエコシステムでの活用

Rust陣営で圧縮はすでによく統合されています。本人の使い方を基準に整理します。

7-1) cargo依存の追加

最も広く使われるzstdクレートはCリファレンス実装へのバインディングで、純Rust実装（ruzstdなどのデコーダ）も成長中です。使い方は依存一行で終わります。

[dependencies]
# Cバインディング（最も成熟した選択）
zstd = "0.13"

# または純Rustデコーダ（メモリ安全優先）
# ruzstd = "0.7"

7-2) 基本の圧縮・展開コード

use std::io::Read;

fn main() -> std::io::Result<()> {
    let data = b"Hello, Zstandard in Rust! ".repeat(1000);

    // 圧縮（レベル3 = バランス、19+ = アーカイブ）
    let compressed = zstd::encode_all(&data[..], 3)?;
    println!("{} bytes -> {} bytes", data.len(), compressed.len());

    // 展開
    let mut decompressed = Vec::new();
    zstd::Decoder::new(&compressed[..])?.read_to_end(&mut decompressed)?;
    assert_eq!(data, decompressed);
    Ok(())
}

7-3) システムプログラミングでの位置

Rustで書かれたストレージエンジン、ログ収集器、ネットワークプロキシはzstdをほぼ既定圧縮として採用します。純Rustデコーダが成熟すれば、FFI境界（Cバインディング）なしに圧縮経路全体をメモリ安全に保てる点が、本人が見る最大の魅力です。

8. 性能 - Rust対C実装のトレードオフ

最もよく出る質問は「Rust再実装はCより遅くないか」です。本人が整理した率直な答えは次のとおりです。

8-1) 理論上の上限は同じ

RustはLLVMバックエンドでC/C++と同等のネイティブコードを生成します。ガベージコレクタがなくランタイムオーバーヘッドもないため、理論的性能上限はCと同一です。

8-2) 初期の差は存在する

現実ではCリファレンス実装が数年間SIMD手動チューニングとアセンブリホットパスで極限まで最適化されています。最初から書いたRust実装は特定ベンチマークで5〜20%ほど遅いことがあります。これは言語の限界ではなく、最適化への投資時間の差です。

8-3) 差は縮まる

Rustでもstd::simdやcore::arch intrinsicsでSIMDを使え、安全な並列化でマルチコアの恩恵をより容易に得られます。時間とともに差は縮まり、一部のワークロードでは同等または上回る結果も出ます。

注意 - 「5〜20%遅い」という数字はワークロード・レベル・データで大きく変わります。単一ベンチマークの数字を絶対化せず、自分のデータで直接測定するのが本人の推奨です。

本人の視点では結論は明確です。わずかな性能トレードオフは「悪意ある入力でもメモリ破壊がない」というセキュリティ価値で十分に相殺されます。セキュリティが重要なインフラほど、この交換は合理的です。

9. 実務活用シナリオ5つ

本人が整理した、zstd適用が正当化される5つのシナリオです。

9-1) ログ収集・保存

ログは量が多く反復パターンが強いため圧縮率がよく出ます。zstdは圧縮率が良くストレージコストを下げ、展開が速くログ検索・分析時の遅延が小さくなります。Elasticsearch・Lokiなどがzstdをサポートします。

9-2) バックアップ・アーカイブ

長期保管バックアップは圧縮率がそのままコストです。zstdレベル19〜22を使えばbrotliに近い圧縮率を得ながら、展開は依然として速いです。復元時間が短い点がアーカイブでは特に重要です。

9-3) ネットワーク転送

API応答・メッセージキュー・ストリーミングで、低レベル（1〜3）のzstdはリアルタイム性を保ちつつ帯域を節約します。辞書学習を組み合わせると、小さなJSONメッセージの圧縮率が劇的に良くなります。

9-4) ストレージ・データベース

RocksDB、Parquet、ClickHouse、ZFS、btrfsがzstdを既定または推奨圧縮として採用します。ディスクI/Oがボトルネックの環境で、圧縮は事実上の性能向上手段です - 読み書きするバイトが減るからです。

9-5) コンテナイメージ・パッケージ

コンテナレジストリとパッケージマネージャ（Arch・Fedoraなど）はzstdで転送時間と保存容量を同時に削減します。イメージのプルが速くなり、デプロイパイプライン全体が軽くなります。

10. 実際の開発現場への適用

開発現場の視点から、zstdとRust再実装の意味を整理します。

10-1) コスト削減効果

各主要クラウドのストレージ・転送コストは無視できません。ログ・バックアップ・DB圧縮をgzipからzstdへ変えるだけで、ストレージ使用量と転送量が減り、直接的なコスト削減につながります。

10-2) セキュリティ要件への対応

金融・公共部門はセキュリティ要求が強いです。「信頼できない入力を解析してもメモリ破壊がない」というRust再実装の保証は、セキュリティ審査・脆弱性点検の負担が大きい現場で説得力ある採用根拠になります。

10-3) 段階的導入戦略

本人の推奨は、一度に全て変えず、新規ログパイプラインや新規バックアップ作業からzstdで始める段階的導入です。既存gzip資産は互換性のため維持しつつ、新しく作る部分にzstdを既定にすれば、リスクなく利益を積み上げられます。

11. 結論 + 即適用できる3つ

RustによるZstandardを一文で要約すると、「バランスの良い標準圧縮zstdに、メモリ安全というセキュリティ価値を加えた合理的進化」です。本人が即適用する3つのパターンを共有します。

11-1) 即適用1：新規圧縮はzstdを既定に

新しく作るログ・バックアップ・転送経路は、特別な理由がなければzstdレベル3（バランス）を既定にしてください。gzipより速く、より良く圧縮します。5分で変えられ、損をすることはほぼありません。

11-2) 即適用2：データ別の最適レベルを測定で決める

リアルタイム経路はレベル1〜3、アーカイブはレベル19〜22で始めつつ、自分の実データで圧縮率・速度を測定し最適点を取ってください。反復する小さなメッセージなら辞書学習を必ず試してください。

11-3) 即適用3：Rustプロジェクトはメモリ安全デコーダを優先検討

Rustで信頼できない入力を展開するなら、純Rustデコーダ（ruzstdなど）を優先検討してFFI境界を減らしてください。成熟度が不足ならCバインディング（zstdクレート）を使いつつ、将来純Rustへ移行できるようインターフェースを抽象化しておくのが本人の推奨です。

最後に本人が強調するメッセージはこれです。圧縮は「見えないコスト削減のてこ」であり「見えないセキュリティ表面」です。zstdはコスト削減のてこを最もバランスよく提供し、Rust再実装はそのセキュリティ表面を構造的に閉じます。2026年に新規システムを設計するなら、この組み合わせは一度真剣に評価する価値があります。
