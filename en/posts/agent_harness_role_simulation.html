How Far Does Simulating an Organization With Agents Actually Go

What context isolation and parallelism buy, and what handoff loss, coordination cost and verification independence charge back

Aug 23, 2026 Tech & IT

Introduction: Booting Up an Entire Office

Once you can drive a single agent reasonably well, the next thought tends to land in the same place. If one works, would five? And if five work, why not seat a developer, a designer and a product manager side by side and let them pass work between themselves? The harnesses shipping this year turn exactly that daydream into a product. One released recently describes running agents on your own machine that take the roles of developer, designer, product manager and sales, message each other, and hand work off.

The official copy calls these autonomous clones of team members. That phrasing belongs to the project, and this article will not reuse it, because what actually happens is not the duplication of a person. It is several execution units, each assigned a role, wired together through a defined interface. The accurate name is role-split simulation. Naming it accurately sharpens the question too. It stops being did this succeed at imitating a person and becomes is splitting the work into pieces a net gain.

The question is interesting because the answer defies intuition. Drawing an org chart is easy. What is hard is not the chart but everything the organization was actually doing. Human teams transmit far more outside documents than inside them: a half-heard remark from the next desk, disagreement carried by a facial expression, the memory of getting burned last month, and an unspoken agreement about who decides when opinions split. Agents have none of that. The text you hand over is all there is.

So this is not a review of one tool. It examines how far the idea of imitating an organization with several agents holds, and where it breaks. What splitting buys, what it charges back, what shape the cost curve takes, where verification belongs, and what you should even count as success. To state the conclusion early: it is neither more is better nor do not bother. It is that the tasks where splitting pays and the tasks where it costs separate quite cleanly.

1. What the Thing Actually Does - Confirmed Scope Only

Here is what the project that prompted this article states publicly. Everything past this section is discussion of the idea rather than description of the product.

  • It is a harness wrapping existing agent CLIs. It does not sell a model; it sits on top of the CLIs and subscriptions you already have. The site lists twelve supported providers including Claude Code, Codex, Grok, Kimi Code, Antigravity, Qwen, Gemini CLI, OpenCode, Crush, Pi, Copilot and Cursor
  • It leads with local-first operation. In the default configuration, code and keys are described as never leaving your machine
  • Agents message each other. Those messages are documented as using X25519 / AES-256-GCM encryption
  • Shared knowledge is separated from personal context. An organization-level knowledge base is inherited by every agent, while your own repositories, notes and style stay on your machine
  • Roles map to command-line-shaped work. The examples given include PR review, bug fixes, screen audits, spec writing and CRM management
  • Licensing and price. The local open-source build is MIT and free, with a 39 dollar per month Pro tier and a 149 dollar per seat per month Teams tier alongside it

The structurally interesting part is that this is a layer selling execution and coordination rather than a model. That layer has thickened noticeably over the past year. Tools that solve parallel execution through isolation, daemons that manage work queues, harnesses that pin roles onto agents are all pushing at the same problem from different angles. The problem has one name: how do you divide work that exceeds what a single agent can hold?

2. Why Split at All Instead of Running One

The claim that more agents are better usually arrives as a single lump. In practice splitting buys four distinct things, and failing to separate them produces the wrong prescription: adding parallelism when the window is the constraint, or polishing role prompts when the shortage is time.

2.1 Context isolation - each gets its own window

This is the most substantive gain. Run a long task in one agent and irrelevant material keeps accumulating in the window. Step three needs only the conclusion of step two, yet the file listings and failed attempts from step two are all still sitting there. Describing its research system, Anthropic wrote that subagents facilitate compression by operating in parallel with their own context windows, and elsewhere in the same write-up called them intelligent filters. The reason for splitting was never only speed.

2.2 Per-role prompts - instructions get shorter

Put every instruction in one window and conflicting rules stack up. When be concise and cite every claim live in the same prompt, the model leans a different way each run. Splitting roles shortens each instruction set and stops them colliding. This is less a performance problem than a problem of instruction design. There is also a ceiling on how large a rule bundle a person can maintain.

2.3 Parallelism - buying wall-clock time

Five genuinely independent tasks running at once cut waiting. But this differs in kind from CPU parallelism. It is closer to overlapping idle time than to dividing compute. If one human receives and judges the results, the pipeline narrows back to serial at the end no matter how wide the fan-out. That specific limit is covered in Where Parallel Coding Agents Actually Pay Off.

2.4 Verification separation - the maker does not inspect

This is the most valuable reason and the one most often reduced to ceremony. An agent reviewing its own output usually passes it. Having a different agent look is the right direction. The question is how different that other agent really is, which section six takes up separately.

Axis of the splitWhat it buysWhat it charges
Context isolationNo window pollution, escapes window limitsHandoffs must be summarized, so information leaks
Per-role promptsNo instruction conflict, rules stay manageableWork falling between roles gets done by nobody
ParallelismShorter wall-clock timeMore calls, and the judging bottleneck moves later

3. The Problems Splitting Creates

This is the core of the article. The cost of splitting is usually waved off as management overhead, when in reality four different failures appear, each with a distinct character.

3.1 Handoff loss - summarizing shrinks the information

The arrows on an org chart are not free. What agent A passes to B is not everything A saw, it is A's summarized conclusion. The same things always fall out of that summary: why the conclusion was reached, what was ruled out, which premises were assumed. B receives only the conclusion and builds on top of it. If A's assumption was wrong, B has no way of knowing.

Cognition nailed this down as two principles. The first is share context, and share full agent traces, not just individual messages. Pass the process, not merely the conclusion. That is harder than it sounds, because passing the full trace dissolves the very reason you isolated context in the first place. What section 2.1 gains and what section 3.1 loses compete for exactly the same resource.

3.2 Conflicting implicit decisions

Cognition's second principle is actions carry implicit decisions, and conflicting decisions carry bad results. Every small choice an agent makes while working, which naming convention to follow, which style to adopt, which reading of an ambiguous requirement to accept, is a decision. These decisions are never written down; they dissolve into the artifact. Two agents that cannot see each other's work each make locally reasonable choices, and the result is output that looks fine piece by piece and does not line up when combined. This is not a symptom of a weak model. It follows from the information structure.

3.3 Compounding error

Chain steps in series and their success probabilities multiply. A step that is right 95 percent of the time comes out around 77 percent after five hops. Real agent pipelines are not independent between steps, so the arithmetic does not transfer literally, but the direction holds. And there is a nastier property attached. An error from an earlier stage is not recognized downstream as an error; it is recognized as a premise. The later agent diligently processes bad input and finishes a bad result smoothly. That is why these failures are unusually hard for a human to localize.

3.4 Who makes the final call

Human organizations have a decider. When opinions split, someone is designated to cut, and if nobody is, the meeting never ends. In agent setups that seat is frequently empty. Even with an orchestrator, what it typically does is distribute work rather than adjudicate. With no adjudication rule, in practice whichever agent wrote last wins. That is an accident, not a design.

4. Where the Organizational Metaphor Breaks

The AI office metaphor speeds up understanding. The trouble is that it stays around after it has done that job, making things look transferable that are not.

In a human team, documents are a secondary channel. Whatever the spec left out you ask about, and often you have already read it off someone's face before asking. When a new hire heads the wrong way, somebody stops them without being told to. Between agents, documents are the only channel. If it is not in the spec it does not exist, and when the work heads the wrong way nobody stops it. That is the first break.

The second is asking back. A person pushes back on a strange instruction. One sentence, are you sure this is really how we want it?, saves a day of wasted work. An agent will generally execute a strange instruction plausibly. You can make it ask back, but raising the frequency erodes the value of automating at all, and lowering it increases silent failure. That dial does not set itself.

The third is accountability. In a human team a role is both a division of labor and a division of responsibility. An agent role is only the former; responsibility attaches to nothing. Which means that in practice adding roles does not reduce what one human is accountable for, it increases it, because that person still has to check what all five produced.

Parts of the metaphor do hold up, though. Sorted out:

  • Holds - as a frame for making role boundaries explicit. Writing down who owns what reduces instruction conflict
  • Holds - as a device that exposes handoff points. Once you fix where work crosses over, you can put verification there
  • Holds - as standardization of output shape. Fixed artifact formats per role stabilize the next stage
  • Breaks - shared tacit knowledge. What was not handed over does not exist
  • Breaks - unprompted objection. Nobody says I do not think that is right
  • Breaks - attribution. No name attaches to the result
  • Breaks - work between the seams. In a human team someone picks it up; here nobody does

5. Calls Multiply - The Cost Structure

How cost grows with agent count is worth reading structurally rather than guessing. There are three places it grows.

  • Agent count. Launch five and at least five runs begin
  • Round trips. Each agent calls tools, receives results and thinks again, several times over, individually
  • Reloaded context. Every handoff requires loading enough background for the receiver to follow. This is the part that grows quietly

There are published figures worth citing. Describing its research system, Anthropic reported that agents use roughly 4 times the tokens of a chat interaction, and multi-agent systems roughly 15 times. The same write-up states that a configuration with a Claude Opus 4 lead agent and Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2 percent on their internal research evaluation. Both numbers come from Anthropic's own system and their own evaluation, and do not transfer unchanged to other tasks or models.

The third sentence is the one that matters. The same write-up notes that token usage alone explained about 80 percent of the variance in the performance metric. That sends you back to reread the 90.2 percent, because it implies a large share of the multi-agent win may be the product of computing more rather than of the architecture. In practice, then, if you compare configurations without matching token budgets, you compared budgets rather than architectures.

So when does it pay? Three conditions have to stand at once.

  • When the result is worth far more than the tokens. Broad investigative work, where the answer only appears after wide search, is the canonical case
  • When the time parallelism bought is actually used. If results pile in a queue reviewed tomorrow, you did not buy time
  • When failures can be discarded cheaply. Fan-out only works if throwing away four of five is acceptable

How coordination overhead eats into the gain is treated separately in The Orchestration Tax 2026 - The Hidden Cost of Managing Multiple AI Agents.

6. Where Verification Belongs

We added a verification agent is reassuring to say, but what that verification actually filters has to be examined on its own. It reduces to one question: does the verifier hold information the generator did not?

A verifier that is the same model with a swapped role prompt answers no. Same training distribution, same priors, same blind spots. What the generator judged plausible, the verifier generally judges plausible too. The limit is sharpest for the class of errors that are correctly formatted and substantively wrong. Where the line between machine-checkable and non-checkable claims falls is covered in What a Machine Can and Cannot Verify in an LLM Answer.

Where verification sitsIndependenceCatchesMisses
Machine checks (tests, compiler, schema, lint)HighSpec violations, broken references, regressionsRequirements that were wrong to begin with
External lookup (docs, APIs, real data)HighFactual errors, stale informationJudgments with nothing to look up
A different modelMediumQuirks specific to one modelShared blind spots, ambiguous requirements
Same model, different role onlyLowObvious omissions, format errorsMost plausible-sounding wrong answers
A humanHighContext violations, wrong direction entirelyBecomes the bottleneck as volume rises

The working rule that falls out is simple. Wire at least one signal from outside the model into verification. Test output, schema checks, a real data lookup, any of them. A verification stage containing no such signal is not verification, it is a second generation pass, and a second generation pass merely doubles the cost.

7. Tasks That Work and Tasks That Do Not

Fold everything so far into task properties and three conditions remain. Can it be decomposed, can it be verified, can failure be discarded cheaply? With all three standing, splitting pays. Knock one out and it generally costs.

There is already a published account of what failure looks like here. Anthropic wrote that early on the system was spawning 50 subagents for simple queries, and also reported subagents duplicating each other's work when task instructions were vague. Both are textbook symptoms of applying a decomposition tool where decomposition does not hold.

8. What Counts as Success

Configurations with many agents are unusually awkward to evaluate. With a single agent you can walk the steps and see where it went wrong; once several agents take different routes, that method stops working. Anthropic named the same point: agents might take completely different valid paths to reach their goal, so step-by-step validation fails because you do not always know what the right steps are. They listed hallucinated answers, system failures and subtle source selection biases among what automated evaluation missed, and reported that human testing proved essential.

Four design principles follow for evaluation.

  • Score the final artifact, not the process. Route diversity is not the defect. A rubric bound to a route is
  • Freeze a regression set. Testing on new tasks each time makes it impossible to tell improvement from an easier sample
  • Put cost in the same table as performance. Skip this and whichever configuration spent more tokens always wins. That is the exact point where a performance comparison silently becomes a budget comparison
  • Read a sample by hand. Pull cases that automated scoring passed and look at them. What automated scoring misses is usually the category its designer never imagined

One more thing. Do not define success as whether it finished without a human. That criterion selects for tasks easy enough to need no intervention, and files the valuable ones as automation failures. A setup where a person spends five minutes at the end is usually better than one where nobody looks at all.

9. The Other Side - When One Is Enough

Since the current is running toward more, the counterweight deserves equal space. Cognition recommended a single-threaded linear agent with unbroken context for most tasks. For long ones approaching the window limit, it suggested a separate compression model that condenses history into key details, decisions and events, while admitting compression is hard to get right and requires real investment. Its conclusion was that current model capability does not support reliable cross-agent communication and shared decision-making at scale.

The places a single configuration genuinely wins:

  • Handoff loss is zero. Nothing is handed over, so nothing leaks in summarization
  • There is one trace. When it goes wrong you can read the divergence in order, and reading sequentially is something people are natively good at
  • Implicit decisions do not conflict. The naming convention set early is still in force later
  • Cost is predictable. There is no place where it multiplies

So it is better to ask three things before adding agents. What exactly is blocked right now? The prescription differs depending on whether the window is short, the instructions conflict, or you are purely out of time. If the window is short, fixing retrieval, compression and tool design first is cheaper. If instructions conflict, tidying the prompt often ends it. When it is none of those and genuinely independent work has piled up, that is when you split.

10. On Modeling a System After a Person

The moment products in this category adopt the language of cloning a teammate, questions arrive from outside engineering. Briefly, then. This is not about any particular product or person; it is the list any organization adopting this shape should settle first.

  • Consent. Did the person agree to having their working style, voice and judgment habits learned and run continuously, and can they withdraw that later
  • Attribution. Whose work is the output recorded as? Both performance review and accountability tracing hang on this
  • Mistaken identity. When used in outward communication, could the other party believe they are dealing with a person? The risk is highest in outward-facing roles like sales and customer contact
  • Afterwards. When the person leaves the team, what happens to the learned profile and the personal context

Local execution and encryption reduce part of the problem of data leaving the building. But consent and attribution are not solved by cryptography. They are agreements rather than technical decisions, and the kind that cannot be settled later if they were not written down before adoption.

Conclusion: The Interface, Not the Org Chart

Imitating an organization with several agents is closer to inevitable than fashionable. There is a ceiling on what one agent can hold, and getting past it requires dividing the work somehow. But the moment you divide, every problem organizations always had comes along with it. Information leaks in transit, assumptions drift apart, and it becomes unclear who decides at the end. Human teams patch that with intuition, conversation and accountability, and agents have none of the three.

What decides the outcome, then, is the interface rather than the org chart. Settling what gets handed over and what does not, what verifies whatever crossed, and what wins when two answers conflict matters far more than settling how many roles to create. If you are starting, this order works.

  • Step 1 - run one agent end to end. Without a baseline there is no way to measure whether adding helped
  • Step 2 - name what is blocked. Window, instruction conflict, or time. Each takes a different fix
  • Step 3 - try the cheap remedies before splitting. Retrieval, compression and tool design solve this more often than expected
  • Step 4 - if you split, write the interface first. The list of what gets handed over comes before the role names
  • Step 5 - put verification outside the generator. Wire in at least one signal originating outside the model
  • Step 6 - write cost next to performance. Omit it and what you keep is an impression rather than a judgment

Finally, to be clear about what this article did not do: there is no verdict here on which harness or framework is better. Tool choice is the last variable to arrive in this problem. Point any tool at work that does not decompose and the result is the same.
