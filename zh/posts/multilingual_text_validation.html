引言：翻译说是完成了，可里面还留着东西

假设产品文档要发五种语言。文件四千个，一半人工翻译，一半机器翻译。审校人员打开二十来个，判断没问题就签字。两个月后，有人在英文页面正中间发现了一句韩文。到那时已经没人说得清它是从哪一批进来的。

这个缺陷麻烦的地方不在于难，而在于不对称：机器几秒钟就能找到，人基本上永远找不到。人不会去读四千个文档。读二十个，改掉最扎眼的那一处，剩下三千九百八十个照原样发出去。

所以这不是审校问题，是检查器问题。而且做检查器时真正难的部分不是找出混入，是从找出来的东西里挑出本来就该留着的那些。产品名保留原文才对，代码示例里的字符串不能翻，术语夹注是故意把两种语言并排放的。分不出这些的检查器会吐几百条告警，人三天就开始不看了。

先把结论写在前面。字符编码能抓到的比想象中多，而手写 Unicode 区块范围这种常见做法会漏掉其中一半，同时又误抓正常的句子。换成脚本属性，这两个问题一起消失。剩下的就是例外设计，从这里开始不是选正确答案，而是选付哪一种代价。

1. 为什么人眼抓不到

语种混入不会出现在显眼的位置。整个标题是另一种语言，谁都会看见。问题不在那里。

  • 段落中间的一句话。前后衔接自然，滚动着读就过去了
  • 表格的第三行。十行里只有一行还是原文，扫一遍表格的视线不会停
  • 屏幕上看不到的位置。图片替代文本、表单输入提示、错误消息、无障碍标签，在正常浏览流程里根本不渲染
  • 只换了一部分的词。用术语词典做替换的翻译有时只改词的内部，形成一个词内部书写系统发生切换的形态，快速阅读会滑过去
  • 看起来像符号的字符。长音符或间隔号这类别的语言不太用的标点残留下来，会被当成排版而不是文字，没人起疑

还有一条。审校人员只审自己看得懂的语言。泰文页面混进俄文，韩文审校和英文审校都抓不到。机器翻译流水线吐出不相干的语种并不罕见，而组织里如果没人读得懂那种语言，它就那样上线了。书写系统检查在这一段压倒性地强于人，因为它不需要读懂就能抓。

2. 字符里没有写着语言

先要把术语理清。这项检查处理的不是语言，而是书写系统。两者不同。英语和法语语言不同，书写系统同为拉丁。只看字符编码分不开这两个。

反过来，韩语、日语、俄语这种书写系统不同的组合，只看编码就分得开。于是这项检查实际做的事收窄成一句话：文档里是否含有目标语种不可能出现的书写系统。对这个很窄的问题，机器回答得接近完美。

2.1 Unicode 早已给出答案

每个码位都带有 Script 属性。这是 UAX #24 定义的值，名称包括 Hangul、Hiragana、Katakana、Han、Cyrillic、Latin 等。JavaScript 正则可以直接写成 \p{Script=Hangul}。正如 MDN 文档所说，必须带 u 或 v 标志，没有标志时 \p 只会被当作字面字符 p。这是静默失败，值得留意。

有两个特殊值要知道。Common 给多种书写系统共用的字符（数字、标点等），Inherited 给从基字符继承性质的组合记号。UAX #24 指出，被赋予 Common 或 Inherited 的字符里有很多其实并非与所有书写系统一起使用，而只与有限的一部分一起使用，并为此定义了 Script_Extensions 属性来记录这种较窄的关系。

由此得出一条实务判断：混入检查用 Script，不要用 Script_Extensions。Script_Extensions 表达的是「这个字符也可以用在这套书写系统里」这种宽泛关系，用于污染检查会把多语言共用的标点全部抓进来。下面第 3 节的实测表格直接展示了这个差别。

2.2 汉字不会告诉你语种

这一节是全文最重要的。有汉字这件事，不能作为该文档是中文的依据。

Unicode 把中文、日文、韩文使用的汉字编码为一个统一集合。Unicode 标准第 18 章在说明这个统一集合的同时写明，标准不试图对汉字的语言进行编码，而把语言标注和分词留给上层软件。也就是说码位里并不包含这个字是中文还是日文。这是一开始就决定不放进去的。

具体验证是这样：日文新字体的国和中文简体的国是同一个码位 U+56FD。会同样是 U+4F1A，两边一致。把两种语言的文档并排放，只抽出汉字比对码位，找不到任何可区分的点。

// 确认新字体与简体是否共享码位
for (const ch of ['国', '会', '發', '发']) {
  console.log(ch, 'U+' + ch.codePointAt(0).toString(16).toUpperCase(),
              /\p{Script=Han}/u.test(ch));
}
// 国 U+56FD true   ← 日文新字体 = 中文简体
// 会 U+4F1A true   ← 两边相同
// 發 U+767C true   ← 仅繁体
// 发 U+53D1 true   ← 仅简体

于是规则这样划分。

  • 英文文档里的汉字 — 可以视为混入。拉丁文字圈的文档几乎没有出现汉字的理由
  • 日文文档里的汉字 — 当然正常。这条规则根本就不该写
  • 中文文档里的汉字 — 正常。要另外看的是属于哪一系的汉字（第 6 节）
  • 韩文文档里的汉字 — 正常。韩文会用汉字做夹注。在这里加禁止汉字的规则，法律和学术文档会被误报淹没

同样的道理，日文文档中全部由汉字构成的片段属于不可判定区间。像公司名或标题这种一个假名都没有的短字符串，没有办法与中文区分。这是编码设计的性质而非检查器的缺陷，所以不要用规则去解，而应标记为「此区间不在检查范围内」。

3. 区块范围与脚本属性的实测差异

现场最常见的代码是手写 Unicode 区块范围。谚文写成 AC00–D7A3 加 1100–11FF，假名写成 3040–30FF，西里尔写成 0400–04FF，汉字写成 4E00–9FFF。这些范围本身没错。问题在于只有这些范围既不够，同时又过头了。

下面是在 Node 22 上对同一批字符跑两种方式的结果。要自己验证，把这段代码存成文件运行即可。

const BLOCK  = { hangul: /[가-힣ᄀ-ᇿ]/u, kana: /[぀-ヿ]/u };
const SCRIPT = { hangul: /\p{Script=Hangul}/u,
                 kana:   /[\p{Script=Hiragana}\p{Script=Katakana}]/u };

for (const ch of ['한', 'ㄱ', '㉮', 'ｻ', '・', 'ー', 'の']) {
  console.log(ch,
    'U+' + ch.codePointAt(0).toString(16).toUpperCase().padStart(4, '0'),
    'block:',  BLOCK.hangul.test(ch)  || BLOCK.kana.test(ch),
    'script:', SCRIPT.hangul.test(ch) || SCRIPT.kana.test(ch));
}

한U+D55C命中命中两者都正常
ㄱ（兼容字母）U+3131落空命中兼容字母在 3130–318F，不在那两个范围里
㉮（圈形）U+326E落空命中括号形和圈形同样属于 Hangul 脚本
谚文 NFD 分解形U+1112 U+1161 …视情况命中只写 [가-힣] 会落空，必须加上字母范围

表里要读出两件事。区块范围会漏掉散落的字符。半角假名是代表案例。经过自动转换器的文档里常留有半角假名，而只看 3040–30FF 的检查器会放行。以及区块范围会误抓共用字符。间隔号 U+30FB 位于假名区块内，但韩文和中文文档也把它当作并列符号使用。就因为这一个字符，可能有几百份韩文文档被报成「日文混入」。

3.1 同一批样本跑两种方式的结果

污染六件、正常八件，共十四个样本上跑两种方式，结果这样分开。污染样本是在正常文本之后埋入谚文、假名和西里尔残留；正常样本则放入间隔号、波浪线这类容易招致误报的字符。

区块范围6314

区块范围漏掉的三个是兼容字母、圈形和半角假名，误抓的一个是使用了间隔号的韩文句子。十四个样本太小，不能把比率当作准确率来读，但失败的类型可以直接照搬。区块范围方式会在「散落在边界之外的字符」和「区块内的共用字符」两侧同时崩掉，而且样本再多也是在同样的地方崩。

UTS #18 指向同一方向。该文档明确指出，用 Unicode 区块来识别字符附带非常重大的注意事项，并引导实现者不要把区块当作书写系统识别的替代品。手写范围哪怕是能跑的代码，标准另外定义 Script 属性也是有理由的。

不过也有必须用区块范围的场合。正则引擎不支持脚本属性的环境（旧运行时、某些数据库的正则、shell 工具）没有别的选择。这时至少要把半角假名 FF65–FF9F 和 谚文兼容字母 3130–318F 加进范围，并显式排除 U+30FB 和 U+30FC。仅这三处改动就能消除上表中区块方式出错的五处里的四处。剩下那一处是圈形，正文里很少出现，可以接受。

4. 杀死检查器的是误报，不是漏报

真正难的部分从这里开始。前面讲的都是只要懂字符编码就能做的机械工作。接下来要挑出该保留的原文，这里就掺进判断了。

原文保留下来属于正当的场合，比想象中多。

  • 专有名词和品牌。公司名、产品名、人名、地名，很多情况下不译才符合原则
  • 引用。原文照引时如果翻译了，就不再是引用
  • 代码示例。变量名、字符串字面量、命令不是翻译对象，译了代码就跑不起来
  • 术语夹注。像「假名（かな）」这样用括号并列原文，是翻译质量好的标志而不是缺陷
  • 像本文这样以字符本身为主题的文档。示例里出现多种书写系统正是内容本身
  • 有意保留原文的界面字符串。法律告示和商标标注有时要求保持原文

分不出这些会怎样，才是核心。检查器吐出 300 条告警，人打开一看，280 条是品牌名和代码示例。第三天没人再打开。第一周结束就把这项检查从 CI 里拿掉了。然后那 20 条真污染照样上线。

所以这两种失败的分量不一样。漏报一次只毁一处文档，误报累积却会让检查器整个失效。新做检查器时，应该把这个不对称当作默认前提。方向不是拓宽抓取范围，而是收紧到每一条上报的都是真的。漏掉的类型以后加一条规则就行，但已经被关掉的检查器不会再打开。

5. 处理例外的四种手段与各自代价

手段有四种。没有白拿的，用哪个、用多少，就是设计。

手段做什么代价什么时候用
缩小检查范围 扫描前剥掉代码块、URL、属性值和元数据 剥掉的区间变成永久盲区 最先做。便宜且见效大
白名单 把特定字符串排除在扫描之外 需要人不断维护，变长后会遮住真污染 专有名词和品牌这类列表有限时
比例阈值 占总字数达到一定比例才上报 长文档里只漏译一句会被埋掉 检出机器翻译批次的大面积未翻译
按文件排除 整个文件退出扫描 最危险。那个文件再也不会被看 最后手段，且必须带过期时间

5.1 缩小检查范围是第一件事

只是剥掉代码块和 URL，误报就会消掉相当一部分。顺序很重要：先剥离，后检查。

function stripUncheckable(text) {
  return text
    .replace(/```[\s\S]*?```/g, ' ')            // 围栏代码块
    .replace(/`[^`\n]*`/g, ' ')                 // 行内代码
    .replace(/<code[\s\S]*?<\/code>/gi, ' ')   // HTML 的 code
    .replace(/<pre[\s\S]*?<\/pre>/gi, ' ')
    .replace(/https?:\/\/\S+/g, ' ');           // URL
}

有一点要注意：剥掉的区间从此再也看不到。代码块内注释里留着未翻译的说明也抓不到。所以剥离对象要取最小，并且把「代码块内的注释不做检查」这个决定写成文档留下来。日后那个区间真出了缺陷，必须能确认那是约定好的边界而不是检查器的 bug。

5.2 白名单只在有限时使用

白名单准确，但会持续消耗人力。两条原则能压低维护成本。

  1. 列表按规则分，不要做成全局的。「en 文档中允许的汉字」和「ko 文档中允许的假名」是两份不同的列表。合成一份，en 里批准的条目在 zh 里也会悄悄放行
  2. 每条都写上理由。没有理由的条目，半年后既不能删也不敢留，列表就这样永久膨胀
const ALLOW = {
  en: [
    { term: '任天堂',  why: 'brand name, kept in original' },
    { term: '한글',    why: 'subject of the article itself' },
  ],
  ko: [
    { term: 'かな',    why: 'term gloss in parentheses' },
  ],
};

实际判定这样分开：含品牌名的英文句子在没有白名单时会被报成 Han 3 字，加入列表后归零。含术语夹注的韩文句子同样从 Hiragana 2 字降到零。代码示例里的正则，仅靠范围缩小就已经是零。

5.3 比例阈值比绝对个数稳定

同样两个字符，随文档长度不同意义完全不同。假设英文文档里残留两个谚文字符。

  • 在全文 815 字的文档里 → 0.25%。大概率是品牌或引用
  • 在全文 6 字的文档里 → 33.33%。根本没翻译

所以阈值按比例取，不按个数取。但只有比例还不够，长文档里只漏译一句会被比例埋掉。两条规则一起挂才是实务上正确的构成。比例超过某个水平就当作大面积未翻译并阻断；即便比例很低，只要连续污染片段的长度超过阈值，就单独上报。整句残留会形成较长的连续片段，因而落入第二条规则。

// 按连续片段上报，位置也一并给出
const doc = 'The runner reads the tree. 접근성 트리를 읽고 반환한다. Then it exits.';
const re = /\p{Script=Hangul}+/gu;
let m;
while ((m = re.exec(doc)) !== null) {
  console.log(`offset ${m.index}: ${JSON.stringify(m[0])}`);
}
// offset 27: "접근성"
// offset 31: "트리를"
// offset 35: "읽고"
// offset 38: "반환한다"

关于上报格式再补一句。不要报字符数，要报位置和原文片段。上例中「检出谚文 12 字」是无法据以修改的信息，「offset 27 处有 접근성」则可以立刻修。人打开去看的成本越低，检查器活得越久。

5.4 没有过期时间就不要用文件级排除

把整个文件移出扫描是最后手段。一旦加入，那个文件再也不会被检查，而加入的理由半年就忘了。真要用，就把过期时间设为必填字段，并让检查器把「存在已过期条目」这件事本身作为一项发现上报。不去管理例外列表，例外列表就直接变成盲区列表。

5.5 词内部书写系统发生切换的情况

有一类需要单独处理：用术语词典替换的翻译只改写了词的内部。这类问题用扫描全文的规则抓不到，因为正常韩文文档里也会出现汉字，出现谚文更是理所当然。异常之处在于两者贴在一起。

这里有个陷阱。按词切分、再看单个词里是否含两种书写系统，看上去是自然的做法，但实际上行不通。分词器会把书写系统发生变化的位置当作词边界。

const seg = new Intl.Segmenter('ko', { granularity: 'word' });
console.log([...seg.segment('会원 가입')].map(p => p.segment));
// [ '会', '원', ' ', '가입' ]   ← 会 和 원 落到了不同的 token

所以看的不是词，而是相邻。直接找汉字紧跟谚文、或者反过来的位置。

const adj = /(\p{Script=Han}\p{Script=Hangul}|\p{Script=Hangul}\p{Script=Han})/gu;

[...'会원 가입 절차'.matchAll(adj)];    // [ '会원' ]   ← 抓到
[...'新규 등록'.matchAll(adj)];         // [ '新규' ]   ← 抓到
[...'민법(民法) 제839조'.matchAll(adj)]; // []          ← 夹注不会被抓
[...'한자 漢字 병기'.matchAll(adj)];     // []          ← 带空格的夹注也不会

这条规则好在会自动绕开正当的夹注。括号夹注和空格夹注都在两种书写系统之间隔了别的字符，相邻条件不成立。它是少见的、一条白名单都不用就能把误报降到零的规则，值得做。

5.6 肉眼无法区分的字符

西里尔字母和拉丁字母有好几对形状相同的字。大写 А（U+0410，西里尔）和 A（U+0041，拉丁）在屏幕上无法区分。这类字符经由机器翻译流水线或复制粘贴混进来，审校再怎么看也抓不到。

这反倒是机器很容易抓的。在韩文文档里禁止西里尔字母，一条规则就能拦下。再加上同一个 token 内同时含拉丁和西里尔的判断，精度会更高，因为正常文档里没有理由让一个词由两套字母体系构成。

function scriptsOf(token) {
  const s = new Set();
  for (const ch of token) {
    if (/\p{Script=Latin}/u.test(ch))    s.add('Latin');
    if (/\p{Script=Cyrillic}/u.test(ch)) s.add('Cyrillic');
  }
  return [...s];
}
scriptsOf('Аpple');  // [ 'Cyrillic', 'Latin' ]  ← 首字母是 U+0410
scriptsOf('Apple');  // [ 'Latin' ]

6. 同一书写系统内部的污染

前面所有规则只在书写系统不同时才起作用。可实际本地化中经常出现的缺陷，恰恰发生在同一套书写系统内部：简体文档里混进繁体，中文文档里残留日式字形，翻译记忆把两系混着返回。

如第 2 节所述，仅凭码位判断不出系别。于是换个办法：把只存在于一系的字收成样本，数个数。挑出简繁写法不同的字，比如发与發、国与國、会与會、门与門、时与時，建两个集合，数文档里各出现几个。

const HANS = new Set([...'这么无发国际会议们个东车马门问题时间实现体系统计龙凤业务产资总']);
const HANT = new Set([...'這麼無發國際會議們個東車馬門問題時間實現體系統計龍鳳業務產資總']);

function variant(t) {
  let s = 0, r = 0;
  for (const c of t) { if (HANS.has(c)) s++; if (HANT.has(c)) r++; }
  return { simplified: s, traditional: r };
}
variant('这是国际会议的问题');  // { simplified: 7, traditional: 0 }
variant('這是國際會議的問題');  // { simplified: 0, traditional: 7 }
variant('这是國際会议的问题');  // { simplified: 5, traditional: 2 }  ← 混用
variant('中文');                // { simplified: 0, traditional: 0 }  ← 无法判定

把这个方法的性质弄准确，就不会误解。

  • 混用抓得很好。只期待一系的文档里出现了对面的标记字，那个位置就是缺陷位置
  • 不可判定区间必然残留。只由两系共有字构成的短字符串无法归类，上例的中文就是
  • 样本规模就是灵敏度。标记字只放二十来个，短文档大多会落到不可判定。要在生产里用，最好准备数百字规模的表
  • 日文新字体是另一个问题。新字体里有些与简体相同，有些不同。要抓中文文档里残留的日式字形，需要另建第三份样本：只在新字体里有、简体里没有的字

记一条判断：这条规则留在警告级，不要升到阻断。引文中带入原系写法、专有名词沿用繁体、标记字恰好以别的义项出现，都是正当例外。与跨书写系统的混入不同，这里真正需要人来判定的比例明显更高。

7. 乱码和语种混入是两回事

这两种缺陷常被塞进同一个检查器。必须分开，因为成因不同、修法也不同。

  • 语种混入 — 字符完全正常，只是位置不对。根源在翻译流程
  • 乱码 — 字符本身被造错了。根源在编码处理

区分不难，因为乱码留有指纹。

// 把 UTF-8 字节当作西欧编码来读
Buffer.from('한글', 'utf8').toString('latin1');
// 'íê¸'  →  U+ED U+95 U+9C U+EA U+B8 U+80
//   Hangul 脚本字符为零，取而代之的是一串拉丁补充区符号

// 把 cp949 字节当作 UTF-8 来读
Buffer.from([0xC7, 0xD1, 0xB1, 0xDB]).toString('utf8');
// '�ѱ�'  →  插入了替换字符 U+FFFD
症状乱码语种混入
U+FFFD 替换字符经常出现不会出现
拉丁补充区符号连续出现典型特征不会出现
人能否读懂不能能读，只是另一种语言
脚本属性判定原本的书写系统消失被判定为正常的书写系统
该在哪里修文件读写处的编码翻译流程与源文件

关于 U+FFFD，Unicode 标准第 5 章规定了遇到非法字节序列时的处理原则。文档里出现替换字符，是某处解码失败的确定信号，因此这是为数不多的、可以脱离语言检查而始终阻断的规则之一。

编码错误发生在哪一环，在定位韩文乱码发生的那一点里另作讨论。本文只讲到一点：把规则和上报消息分开，别让编码缺陷混进语种检查。两种缺陷若以同一个名字上报，修的人每次都会先看错地方。

8. 规范化放在检查之前还是之后

规范化形式不同，同一个检查器会给出不同答案。这真的会把判定翻过来。

const doc = 'The word 한글 appears here.'.normalize('NFD');

/[가-힣]/.test(doc);              // false  ← 漏掉
/\p{Script=Hangul}/u.test(doc);   // true   ← 抓到
/[가-힣]/.test(doc.normalize('NFC'));  // true  ← 转成 NFC 就抓到

原因很简单。分解成 NFD 的谚文不是预组合音节，而是一串单独的字母。[가-힣] 只看预组合音节区，所以一个都不匹配。脚本属性在字母上同样带 Hangul，所以照样抓到。文本以 UAX #15 定义的四种规范化形式中的哪一种进来，结果就此分岔。

兼容规范化那边方向正好相反。

const s = 'ko 文档里的 ｻｰﾊﾞｰ';
/[぀-ヿ]/.test(s);                   // false  ← 半角，漏掉
/[぀-ヿ]/.test(s.normalize('NFKC')); // true   ← NFKC 折叠成全角

'ｻｰﾊﾞｰ'.normalize('NFKC');  // 'サーバー'
'ＡＢＣ'.normalize('NFKC');   // 'ABC'
'㈱'.normalize('NFKC');      // '(株)'

由此得出实务规则。

  1. 被检查的文本在检查前立刻统一为 NFC。防止以分解形进来的文本溜过规则
  2. 如果不得不用区块范围方式，就连 NFKC 一起做。半角假名会折叠成全角进入范围
  3. 如果用脚本属性方式，NFKC 就没必要。半角假名同样带 Katakana 脚本，不做规范化也抓得到
  4. 不要把规范化后的文本写回去。只对检查用的副本做。NFKC 是会抹掉信息的变换，对原文做了就回不来

最后一条是一般原则的特例。改值的时刻和检查的时刻顺序错位，检查结果本身就失去意义，这个轴在校验之后再改值，校验就作废了里有详细讨论。谚文在 NFC 与 NFD 之间如何变化、在哪些边界上形态会变，则是韩文被拆成字母的瞬间讲得更细。

9. 要信任检查器，先往里埋污染

检查器什么都没上报时，需要有办法区分这究竟意味着确实干净，还是检查器坏了。这类失败经常发生：正则漏了标志、文件扩展名过滤错位、范围缩小得太宽把正文整个剥掉，结果都同样是「没有异常」。

解法只有一个：故意埋进污染，确认检查器抓不抓得到。这不是检查器的单元测试，是灵敏度测试，埋进去的样本必须是实际会出现的类型。

  1. 与目标语种不同书写系统的一句话 — 最常见的类型
  2. 半角假名 — 区块范围方式漏掉的代表案例
  3. 谚文兼容字母 — 只看字母范围的检查器会漏
  4. 分解成 NFD 的字符串 — 暴露规范化顺序的缺陷
  5. 一个西里尔词 — 流水线事故类型
  6. 汉字与谚文贴在一起的词 — 确认相邻规则还活着
  7. 简繁混用的句子 — 确认标记样本是否够用

另一侧也要一起埋。放进正当例外，确认它是否保持沉默。含品牌名的句子、括号夹注、代码块里的正则、用间隔号做的并列。只要出现一条误报，那条规则就还不能发布。

要点是把这项测试固定成回归测试。把样本文件放进仓库，每次都验证检查器抓住全部污染样本、放行全部正常样本。改一条规则却把以前抓得到的东西弄丢，这种事真的会发生，而且没有这项测试就浮不出水面。

做样本时还有一点。污染样本文件如果就放在被扫描的目录里，检查器会把这些文件报成缺陷。样本要放在扫描范围之外，或者用明确的文件名约定排除掉。然后再确认一次，那条排除规则有没有把真文档一起吞掉。

10. 哪些阻断，哪些只警告

不要把所有规则按同样的分量对待。升到阻断级有三个条件，而且必须同时成立。

  1. 误报实际为零。你必须说不出一个会触发它的正常文档
  2. 判定依据能立刻查证。上报里必须带位置和原文片段
  3. 修复方式明确。动作要收敛为唯一一件事，比如「把这句翻掉」
规则判定理由
存在 U+FFFD 替换字符阻断解码失败的确定信号，不存在正当情形
en 文档里的谚文、假名、西里尔阻断经过范围缩小和白名单后，误报接近零
zh 文档里的假名阻断同上
ja 文档里的谚文阻断同上
任何语种里意料之外的西里尔阻断流水线事故类型，没有进入正常文档的路径
汉字与谚文贴在一起的词阻断结构上绕开夹注形态，误报低
比例阈值超标警告阈值本身就是判断，文档类型之间存在正当差异
简繁混用警告引用和专有名词是实际存在的正当例外
ko 文档里的汉字不设规则夹注是正常的，设了规则只会产生误报
纯汉字短字符串的语种不设规则不可判定区间，移出检查范围

表里最后两行最重要。决定不写某条规则，同样是设计决策。想去抓抓不到的东西，那条规则一定会以误报的形式回来，而误报正如第 4 节所示会把整个检查器拖下水。

警告级最好也附上一个条件：把告警条数本身当作指标看。上周 12 条、这周 80 条，不用逐条打开就知道某个批次里有东西变了。把告警当成读趋势的仪表盘而不是「回头再看的列表」，被忽视的速度就会慢下来。

10.1 推行顺序

一次全部打开，第一天就是几百条告警，然后就被关掉。要分阶段。

  1. 先只上报。不阻断地跑一两周，看清现状的实际规模
  2. 给误报分类。分成品牌、代码、夹注和其他，并且务必弄清「其他」是什么
  3. 用范围缩小和白名单把误报压到接近零。这一步吃掉大部分时间
  4. 把存量缺陷一次清完。留着它们就打开阻断，会把所有无关的改动一起卡住
  5. 只把误报为零的规则升到阻断。其余留在警告级
  6. 接上回归样本。在这个时点接上，之后改规则灵敏度才守得住

第 4 步常被跳过，而这正是推行失败最常见的原因。存量缺陷还在就打开阻断，会把跟这些缺陷毫无关系的改动全部卡住。于是人不去修检查器，而是开始写抑制注释，这类注释一多，规则其实已经死了。

11. 没能确认的事项

以下条目因无法锁定依据，未在正文中作为数值或断言使用。

  • 其他运行时上脚本属性的行为。本文的执行结果基于 Node 22。正则的 \p{Script=…} 会随运行时内置的 Unicode 数据版本而变，尤其是裁剪了国际化数据构建的环境下会怎样，未能确认
  • Python、Java、Go 等的等价写法。各语言正则引擎以何种语法支持脚本属性、支持范围是否一致，未做比对
  • 与统计式语种识别库的比较。基于 n-gram 的识别器在短字符串上准确度如何、与书写系统检查组合能带来多少增益，未做测量
  • 简繁标记字的合适规模。正文示例是二十来字的样本。生产中要放多少字才能让短文档也可判定，取决于文档性质，故未给出数字
  • 日文新字体专有字集。只在新字体里存在、简体中没有的字的完整清单，未能确认
  • 东南亚与阿拉伯文字圈的例外类型。泰文、高棉文这类不分词的文字圈，以及阿拉伯文这类含双向文本的情形，还需要哪些额外的正当例外，未能覆盖
  • 误报率的绝对值。正文 3.1 的十四个样本是为展示失败类型，不是准确度测量。真实文档集上的误报率高度依赖语料性质

结论：不要拓宽抓取范围，要收紧上报

多语言文档的语种混入检查分成两半。前一半是机械的。Unicode 已经在每个字符上记下了书写系统，读出脚本属性、找出目标语种不可能出现的值就行。这明显优于手写区块范围的常见做法，切换成本也不大。

后一半是设计。分不出专有名词、代码和夹注，检查器就会变成误报堆；变成误报堆的检查器会被关掉。所以写规则时的基本方向不是「多抓一些」，而是「收紧到每一条上报的都是真的」。漏掉的类型以后加一条规则就行，失去信任的检查器却很难救回来。

只留两件现在就值得做的事。一是把半角假名和谚文兼容字母加进你现在跑的检查规则里。要是真抓出东西来，说明这整类问题一直被漏掉。二是拿十份已知正常的文档跑一遍检查器。这里吐出的告警就是这个检查器的寿命，只要吐出一条，就该收紧了。
