前言：超越防火墙的安全之眼

如果说上一篇第3部分介绍的防火墙扮演的是网络"守门员"的角色，那么IDS（入侵检测系统）和IPS（入侵防御系统）就是网络的"监控摄像头"和"安保人员"。IDS/IPS的核心功能是在防火墙允许通过的流量中检测和应对恶意活动。

当今的网络攻击越来越精细化。仅靠端口封锁已无法阻止Web应用攻击、零日漏洞利用、APT（高级持续性威胁）等。本篇第4部分将以实践为中心，介绍IDS/IPS的概念、检测方式，以及代表性开源解决方案Snort和Suricata的安装与配置。

1. IDS vs IPS：理解区别

1.1 IDS（入侵检测系统）

IDS是监控网络流量或系统活动，检测可疑活动或策略违规并生成告警（Alert）的系统。IDS以被动（Passive）方式运行，不阻断流量，而是分析流量副本。

IDS工作方式：
┌─────────┐     ┌─────────┐     ┌─────────┐
│  互联网  │────▶│  交换机  │────▶│  服务器  │
└─────────┘     └────┬────┘     └─────────┘
                     │ (镜像/SPAN)
                     ▼
               ┌─────────┐
               │   IDS   │ → 检测 → 生成告警
               └─────────┘

IDS的特点：

  • 分析流量副本（带外/Out-of-Band）
  • 检测后只发出告警，不直接阻断
  • 不影响网络性能
  • 误报时不影响服务

1.2 IPS（入侵防御系统）

IPS是在IDS的检测功能基础上增加实时阻断（Block）功能的系统。它以内联（Inline）方式部署在流量路径上，可以即时阻断恶意流量。

IPS工作方式：
┌─────────┐     ┌─────────┐     ┌─────────┐
│  互联网  │────▶│   IPS   │────▶│  服务器  │
└─────────┘     └─────────┘     └─────────┘
                     │
                检测 → 阻断 或 放行

IPS的特点：

  • 直接部署在流量路径上（内联/Inline）
  • 检测到恶意流量后可立即阻断
  • 可能产生延迟（Latency）
  • 误报时可能阻断正常服务

1.3 IDS与IPS比较

区分 IDS IPS
部署方式 带外（镜像） 内联（串联连接）
响应方式 检测和告警 检测和阻断
网络影响 无 可能产生延迟
误报影响 仅生成告警 可能阻断正常流量
故障时 监控中断 网络中断（无旁路时）
应用场景 监控、分析 实时威胁阻断

实用技巧：许多组织采用先以IDS模式运行进行检测规则调优，稳定后再转换为IPS模式的方式。

2. 检测方式

2.1 基于签名的检测（Signature-based Detection）

将流量与已知的攻击模式（签名）进行比较的检测方式。类似于杀毒软件的模式匹配。

工作原理：

数据包 → 与签名库比较 → 匹配时告警/阻断

签名示例：
- SQL注入："' OR '1'='1"
- XSS攻击："<script>alert("
- 缓冲区溢出：特定字节序列

优点：

  • 对已知攻击检测率高
  • 误报率低
  • 处理速度快

缺点：

  • 无法检测零日攻击
  • 对签名规避技术脆弱
  • 需要持续更新签名

2.2 基于异常的检测（Anomaly-based Detection）

学习正常的网络/系统行为基线（Baseline），检测偏离基线的异常活动。

工作原理：

学习阶段：收集正常流量模式 → 生成基线(Baseline)

检测阶段：当前流量 ↔ 基线比较 → 超出偏差时告警

监控指标示例：
- 各时段流量
- 协议分布
- 连接频率
- 数据包大小分布
- 用户行为模式

优点：

  • 可检测未知攻击（零日攻击）
  • 对内部威胁检测有效
  • 无需更新签名

缺点：

  • 误报率高
  • 需要学习期
  • 环境变化时需要重新学习
  • 对低速攻击（Low and Slow）脆弱

2.3 混合检测

现代IDS/IPS解决方案采用同时使用签名检测和异常检测的混合方式。

混合检测架构：

          ┌──────────────────────┐
          │      流量收集        │
          └──────────┬───────────┘
                     │
          ┌──────────▼───────────┐
          │      预处理引擎      │
          └──────────┬───────────┘
                     │
       ┌─────────────┴─────────────┐
       ▼                           ▼
┌─────────────┐           ┌─────────────┐
│  签名匹配   │           │  异常检测   │
│    引擎     │           │    引擎     │
└──────┬──────┘           └──────┬──────┘
       │                         │
       └─────────────┬───────────┘
                     ▼
          ┌──────────────────────┐
          │     关联分析引擎     │
          └──────────┬───────────┘
                     ▼
          ┌──────────────────────┐
          │    告警/响应模块     │
          └──────────────────────┘

3. 网络型 vs 主机型

3.1 NIDS（基于网络的IDS）

监控整个网络段流量的方式。

特点：

  • 部署在网络边界或核心区段
  • 在一处检测针对多个主机的攻击
  • 难以分析加密流量
  • 高带宽环境下可能丢包

主要解决方案：Snort、Suricata、Zeek（原Bro）

3.2 HIDS（基于主机的IDS）

在单个主机（服务器、工作站）上运行，监控该系统的活动。

特点：

  • 监控系统调用、文件系统、日志文件
  • 可在解密后分析加密流量
  • 对内部威胁和权限提升攻击检测有效
  • 使用主机资源

主要解决方案：OSSEC、Wazuh、Tripwire、AIDE

3.3 NIDS与HIDS比较

区分 NIDS HIDS
监控范围 网络段 单个主机
安装位置 网络设备 各服务器/PC
加密流量 难以分析 可分析
资源影响 与主机无关 使用主机资源
部署复杂度 低（集中式） 高（各主机）
检测对象 网络攻击 本地攻击、文件篡改

推荐配置：为实现最佳安全性，建议同时运营NIDS和HIDS以构建互补的检测体系。

4. Snort安装与配置

Snort是使用最广泛的开源NIDS/NIPS。由Martin Roesch于1998年开发，目前由Cisco管理。

4.1 Snort 3安装（Ubuntu/Debian）

# 安装必需包
sudo apt update
sudo apt install -y build-essential libpcap-dev libpcre3-dev \
    libnet1-dev zlib1g-dev luajit hwloc libdumbnet-dev \
    bison flex liblzma-dev openssl libssl-dev pkg-config \
    libhwloc-dev cmake cpputest libsqlite3-dev uuid-dev \
    libcmocka-dev libnetfilter-queue-dev libmnl-dev autotools-dev \
    libluajit-5.1-dev libunwind-dev libfl-dev

# 安装DAQ（数据采集）库
cd /tmp
git clone https://github.com/snort3/libdaq.git
cd libdaq
./bootstrap
./configure
make
sudo make install

# 下载并安装Snort 3
cd /tmp
wget https://github.com/snort3/snort3/archive/refs/heads/master.zip
unzip master.zip
cd snort3-master
./configure_cmake.sh --prefix=/usr/local --enable-tcmalloc
cd build
make -j$(nproc)
sudo make install
sudo ldconfig

# 验证安装
snort -V

4.2 Snort基本配置

# 创建配置目录
sudo mkdir -p /etc/snort/rules
sudo mkdir -p /var/log/snort

# 复制默认配置文件
sudo cp /usr/local/etc/snort/snort.lua /etc/snort/
sudo cp /usr/local/etc/snort/snort_defaults.lua /etc/snort/

# 编辑配置文件
sudo nano /etc/snort/snort.lua

snort.lua主要配置：

-- 网络变量设置
HOME_NET = '192.168.1.0/24'
EXTERNAL_NET = '!$HOME_NET'

-- 服务器定义
DNS_SERVERS = '$HOME_NET'
SMTP_SERVERS = '$HOME_NET'
HTTP_SERVERS = '$HOME_NET'
SQL_SERVERS = '$HOME_NET'

-- 端口定义
HTTP_PORTS = '80 8080 8443'
SSH_PORTS = '22'

-- 规则文件路径
ips = {
    enable_builtin_rules = true,
    rules = [[
        include /etc/snort/rules/local.rules
        include /etc/snort/rules/snort3-community.rules
    ]]
}

-- 输出设置
alert_json = {
    file = true,
    limit = 100,
    fields = 'timestamp iface src_addr src_port dst_addr dst_port proto action msg'
}

-- 日志设置
output = {
    logdir = '/var/log/snort',
    show_year = true
}

4.3 运行Snort

# 验证配置文件
sudo snort -c /etc/snort/snort.lua -T

# 以IDS模式运行（数据包捕获）
sudo snort -c /etc/snort/snort.lua -i eth0 -A alert_fast -l /var/log/snort

# 以IPS模式运行（内联，使用NFQ）
sudo snort -c /etc/snort/snort.lua -Q --daq nfq --daq-var queue=0

# 以守护进程模式运行
sudo snort -c /etc/snort/snort.lua -i eth0 -D -l /var/log/snort

# 分析PCAP文件
sudo snort -c /etc/snort/snort.lua -r capture.pcap -A alert_full

6. 规则编写方法

Snort和Suricata使用相似的规则语法。理解规则编写方法对于有效检测至关重要。

6.1 规则基本结构

规则结构：
[action] [protocol] [source] [src_port] -> [dest] [dst_port] ([options])

示例：
alert tcp $EXTERNAL_NET any -> $HOME_NET 80 (msg:"HTTP GET Request"; content:"GET"; sid:1000001; rev:1;)

Action（动作）：

  • alert：生成告警并记录
  • log：仅记录
  • pass：允许数据包（不检查后续规则）
  • drop：阻断数据包并记录（IPS）
  • reject：阻断数据包并发送RST/ICMP响应

6.2 规则选项

# 消息（必需）
msg:"检测消息";

# 内容匹配
content:"搜索字符串";
content:"|00 01 02|";  # 十六进制值
content:"GET"; nocase;  # 忽略大小写

# 内容位置指定
content:"login"; offset:0; depth:10;  # 在前10字节内
content:"password"; distance:5; within:20;  # 在上一匹配后5~25字节之间

# 正则表达式
pcre:"/^GET.*\.php/i";

# 流条件
flow:to_server,established;
flow:from_server,established;

# 元数据
sid:1000001;  # 规则唯一ID
rev:1;        # 规则版本
classtype:web-application-attack;
priority:1;   # 优先级（1=高）
reference:cve,2024-1234;  # 参考信息

# 阈值（防止过多告警）
threshold:type limit, track by_src, count 5, seconds 60;

# HTTP专用选项
http_uri;       # 仅检查URI
http_header;    # 仅检查头部
http_client_body;  # 请求主体
http_method;    # HTTP方法

6.3 实战规则示例

# SQL注入检测
alert http $EXTERNAL_NET any -> $HTTP_SERVERS $HTTP_PORTS (
    msg:"SQL Injection Attempt - UNION SELECT";
    flow:to_server,established;
    http_uri;
    content:"union"; nocase;
    content:"select"; nocase; distance:0;
    classtype:web-application-attack;
    sid:1000010;
    rev:1;
)

# XSS攻击检测
alert http $EXTERNAL_NET any -> $HTTP_SERVERS $HTTP_PORTS (
    msg:"XSS Attack - Script Tag Detected";
    flow:to_server,established;
    content:" $HOME_NET 22 (
    msg:"SSH Brute Force Attempt";
    flow:to_server;
    threshold:type threshold, track by_src, count 5, seconds 60;
    classtype:attempted-admin;
    sid:1000020;
    rev:1;
)

# 端口扫描检测
alert tcp $EXTERNAL_NET any -> $HOME_NET any (
    msg:"TCP Port Scan Detected";
    flags:S;
    threshold:type both, track by_src, count 20, seconds 10;
    classtype:attempted-recon;
    sid:1000030;
    rev:1;
)

# 恶意User-Agent检测
alert http $EXTERNAL_NET any -> $HTTP_SERVERS $HTTP_PORTS (
    msg:"Suspicious User-Agent - Nikto Scanner";
    flow:to_server,established;
    content:"Nikto"; http_header;
    classtype:web-application-attack;
    sid:1000040;
    rev:1;
)

# DNS隧道疑似
alert dns any any -> any any (
    msg:"Possible DNS Tunneling - Long Query";
    dns_query;
    pcre:"/^[a-z0-9]{50,}\./i";
    classtype:policy-violation;
    sid:1000050;
    rev:1;
)

7. 误报/漏报管理

7.1 误报（False Positive）管理

误报是将正常流量错误判断为恶意的情况。过多的误报会增加安全团队的疲劳度，可能导致忽略真正的威胁。

减少误报的方法：

  • 应用白名单：排除可信的IP/域名
  • 规则调优：修改过于宽泛的规则
  • 设置阈值：利用threshold选项
  • suppress规则：在特定条件下抑制告警
# suppress设置示例（threshold.config）

# 抑制特定IP的特定规则
suppress gen_id 1, sig_id 1000001, track by_src, ip 192.168.1.100

# 抑制特定网络的规则
suppress gen_id 1, sig_id 1000010, track by_dst, ip 10.0.0.0/8

# 完全禁用特定规则
suppress gen_id 1, sig_id 2100366

7.2 漏报（False Negative）管理

漏报是未能检测到实际攻击的情况。这是一个严重问题，会降低系统的安全效果。

减少漏报的方法：

  • 更新规则：定期更新签名
  • 多重检测：签名+异常检测并行
  • 检查加密流量：SSL/TLS解密
  • 多种规则源：利用多种威胁情报
  • 定期渗透测试：验证检测能力

7.3 规则性能监控

8.2 Slack/Discord Webhook告警

#!/usr/bin/env python3
# ids_alert_webhook.py

import json
import requests
import sys
from datetime import datetime

WEBHOOK_URL = "https://hooks.slack.com/services/YOUR/WEBHOOK/URL"

def send_alert(alert_data):
    message = {
        "blocks": [
            {
                "type": "header",
                "text": {
                    "type": "plain_text",
                    "text": "IDS/IPS Alert"
                }
            },
            {
                "type": "section",
                "fields": [
                    {"type": "mrkdwn", "text": f"*Signature:*\n{alert_data.get('signature', 'N/A')}"},
                    {"type": "mrkdwn", "text": f"*Severity:*\n{alert_data.get('severity', 'N/A')}"},
                    {"type": "mrkdwn", "text": f"*Source:*\n{alert_data.get('src_ip', 'N/A')}:{alert_data.get('src_port', '')}"},
                    {"type": "mrkdwn", "text": f"*Destination:*\n{alert_data.get('dest_ip', 'N/A')}:{alert_data.get('dest_port', '')}"},
                    {"type": "mrkdwn", "text": f"*Protocol:*\n{alert_data.get('proto', 'N/A')}"},
                    {"type": "mrkdwn", "text": f"*Time:*\n{alert_data.get('timestamp', 'N/A')}"}
                ]
            }
        ]
    }

    response = requests.post(WEBHOOK_URL, json=message)
    return response.status_code == 200

9.4 SIEM关联分析示例

关联规则示例：

规则1：端口扫描后漏洞攻击
  条件：
    - 5分钟内从同一源地址检测到端口扫描（10个以上端口）
    - 之后从该源检测到Web攻击
  响应：生成紧急告警，考虑自动IP封锁

规则2：登录尝试后疑似数据泄露
  条件：
    - 检测到SSH/RDP暴力破解
    - 之后检测到大量数据传输（超过特定阈值）
  响应：账户锁定，网络段隔离

规则3：疑似内部横向移动
  条件：
    - 从内部IP向其他内部IP端口扫描
    - 之后检测到SMB/RDP异常连接尝试
  响应：隔离相关主机，详细分析
