This article relies on the sentences in the Polars 2.0 release post published on October 6, 2026, the pre-release post dated September 2, the 2.0 migration guide and the README of the benchmark repository. The benchmark was measured and published by Polars itself, and its figures are carried over only together with their measurement conditions.

The Trigger - A Major Version That Changes Defaults Rather Than Features

Polars published Release of Polars 2.0 on October 6, 2026, with Ritchie Vink named as the author in the byline, and GeekNews carried it the same day. The release post hands the rationale for the version bump to the earlier post of September 2, Pre-release of Polars 2.0, and says it will itself discuss what features 2.0 brings. The reasons the pre-release post gives are these. The team does not aim to make 2.0 a big feature release, it hopes the release will be a boring experience for users, and it bumps the major version in order to get rid of design decisions made in the past and to change defaults to more sensible settings that will benefit a greater audience.

The biggest default change is that LazyFrame queries now run on the streaming engine. The release post says the switch leads to massive memory and performance improvements on most queries. It calls this one of the biggest impact changes of 2.0 and gives the reason a major version was required in a single sentence. The streaming engine doesn’t guarantee row-order by default for certain operations. That means the same code can return its result in a different order without raising any error, and the migration guide attaches to this item a warning that the change may silently impact the results of pipelines.

The release post lists five highlights for 2.0.

  • Out-of-core. The initial version of out-of-core (spill-to-disk) support is enabled.
  • Performance. A lot of very core performance improvements have landed. On the optimizer and engine side, the highlights the post names are join reordering, much better common-subplan-elimination and dynamic predicates/bloom filters.
  • SQL. SQL gets first class support. The post says that, together with the performance improvements, this has Polars leading DataFusion and DuckDB in benchmarks derived from TPC-H and TPC-DS.
  • Map. There is a new Map dtype.
  • Strictness. Polars is stricter on dtypes and explicitness. The post describes the outcome as faster feedback and faster AI iteration.

The pre-release post said that, in aggregate, the team expects the streaming engine to be easily 5x faster. That sentence states an expectation, not a measurement. The multiple does not appear again in the release post, which instead carries a benchmark with its conditions spelled out.

The Default Engine of collect() - What engine="auto" Now Resolves To

This change is the first item in the migration guide. The engine argument of LazyFrame.collect and collect_async still defaults to "auto", exactly as before. What has changed is where "auto" points. For lazy queries, "auto" used to resolve to the in-memory engine and now resolves to the streaming engine. No call site has to change for the engine underneath it to change, which is why code that never mentions an engine is affected as well.

The guide also says where nothing changes. Eager DataFrame operations are unaffected and continue to resolve to the in-memory engine internally. Writing to a file through sink_* was already dispatched to the streaming engine regardless of the engine value, so it is not affected either. explain() still prints the optimized IR plan as before. For show_graph(), the default of plan_stage changes from "ir" to "physical", so a bare call now renders the streaming physical graph.

SQL moves along with it. SQLContext.execute(eager=True) and pl.sql(..., eager=True) used to collect through the in-memory engine, and they now go through LazyFrame.collect() like any other lazy query. To keep using the in-memory engine for a SQL query, the guide says to leave the result lazy with eager=False and pick the engine at the point of collecting it. It adds that the engine affinity settings apply to SQL as well.

The eager readers have moved onto the lazy path as well. pl.read_csv is now dispatched to pl.scan_csv(...).collect(), and pl.read_ipc is dispatched to pl.scan_ipc(...).collect() for all inputs that do not use use_pyarrow. As a consequence read_csv loses the n_threads, batch_size, sample_size and rechunk parameters, and read_ipc loses memory_map and rechunk. The guide adds that the behavior of read_csv now matches scan_csv exactly. A column selection returns the columns in the requested order rather than sorted.

  • The argument is the same. The default of engine is still "auto". What differs between the versions is how that value is interpreted for lazy queries.
  • The old argument. collect(streaming=...) was deprecated in 1.25 and is removed in 2.0, and the replacement listed in the removal table of the guide is engine="streaming".
  • Profiling. LazyFrame.profile() was designed for the in-memory engine and has been removed on the grounds that the concurrent nature of the streaming engine would make its per-node timings misleading. The guide says the team is working on a way to provide query profiling for open source Polars.
  • Environment variable. Setting the environment variable POLARS_ENGINE_AFFINITY=in-memory is another way the guide gives to restore the previous default engine.

Row Order - Operations Without a Guarantee and How to Get It Back

The sentence in the release post runs as follows. The streaming engine doesn’t guarantee row-order by default for certain operations (join, group_by, unpivot, etc.), and if observable row-order is required in those operations, it can be opted into by setting maintain_order=True. The migration guide draws the scope slightly differently. It says the streaming engine does not guarantee row order for operations that don't require it (unpivot, group_by, joins, ...). Both sentences leave the end of the list open, so these three operations cannot be read as the complete set.

The two documents diverge in how they describe the remedy. The release post says only maintain_order=True. The guide says that if code relies on incidental ordering, it should sort explicitly, or pass maintain_order where the operation supports it, and it gives join(..., maintain_order="left") as the example. In the join example the value is the string "left", not True. The join example in the pre-release post also uses maintain_order="left". For the unpivot example, the alternative the guide offers is not maintain_order but a sort after collecting.

The unpivot example in the guide shows what the change looks like. When columns b and c are unpivoted, the pre-2.0 output listed the three rows for b first and the three rows for c after them. In the example output for 2.0, the rows come as b and c for x, then b and c for y, then b and c for z. The guide adds a caveat here. The exact row order shown is not guaranteed, and the only thing guaranteed is that it is no longer the pre-2.0 order. Of joins, the guide says they are easy to miss since nothing about the query looks order-sensitive. The join example in the guide is a left join of two frames whose key k runs in opposite orders, and it carries a comment saying that the row order no longer matches the left frame.

>>> lf.unpivot(pl.selectors.numeric(), index="a").collect().sort(pl.all())
                    >>> left.join(right, on="k", how="left", maintain_order="left").collect()
                    >>> pl.Config.set_engine_affinity("in-memory")  # process-wide
                    >>> lf.collect(engine="in-memory")  # per query

The four lines above are taken one at a time from the examples in the migration guide. They belong to separate examples there and are grouped here only for reference, so the names lf, left and right refer to the frames defined in those examples. The first is the alternative for an unpivot that relies on order, the second is the alternative for a join that relies on the row order of the left-hand frame, and the remaining two restore the previous default engine either process-wide or per query. The engine name is spelled with a hyphen, "in-memory".

  • Operations the sources name. The release post and the migration guide both name join, group_by and unpivot, and both documents leave the end of the list open rather than presenting it as complete.
  • No error is raised. The wording of the warning in the guide is This change may silently impact the results of your pipelines. Nothing fails when the code runs, so the difference shows up only in the output.
  • The value for joins. In the join examples of both the migration guide and the pre-release post, the argument is written as maintain_order="left", a string rather than a boolean.
  • Sorting as an option. For code that relies on incidental ordering, the first thing the guide says is to sort explicitly, and passing maintain_order comes second, for the operations that support it.
  • Reverting. There are three ways to go back to the previous engine, namely a process-wide setting, a per-query argument and an environment variable.

Out-of-Core - On by Default, About 80% of RAM, 64GB of Disk

The release post says out-of-core (spill to disk) is now enabled by default. It starts spilling at about 80% of RAM, and next to that value the post adds in parentheses the caveat that this may need tuning. The default disk budget is 64GB.

The scope of support is stated narrowly. The operations that support out-of-core at this moment are sort, window functions and many expressions, and these can now start spilling to disk to finish a query. Joins and group-by are not yet covered. The post says that in the coming time the team will enable out-of-core for joins and group-by’s as well, and its closing words again list better out-of-core as work for the coming months. No date is given.

The highlights list in the release post calls this the initial version of out-of-core support. A month earlier, the pre-release post had counted proper out-of-core support for the streaming engine among the work in flight that the team had not talked about publicly enough. The assessment in the release post is that the two changes, the streaming default and out-of-core, will make Polars much more resilient in high-memory workloads, and it names casual data practitioners as the group that benefits.

So the release post gives no basis for assuming that a join or a group-by larger than memory will finish in 2.0 by moving to disk. What is on the supported list is sorting, window functions, and many expressions whose range is not enumerated. The wider question of how large a workload a single-node engine can take on was covered in The 2026 Data Tooling Landscape.

  • Names. The source uses the terms out-of-core, spill-to-disk and the abbreviation OOC with the same meaning throughout the post.

The Map dtype - Direct Support for the Arrow MapType

Polars now supports the Arrow MapType directly as a Polars Map dtype. The release post explains that a Map can be thought of as a Python dictionary, mapping keys to values. Before 2.0 the Arrow MapType was read in Polars as List(Struct({"key": ..., "value": ...})). The post says that, as a supported dtype, the map type will now have dedicated expressions, like key lookups, iteration over values and other dictionary like methods.

# Key lookups and dictionary-like methods:
                    df.select(
                        "user",
                        pl.col("scores").map.get("math").alias("math"),                # fixed key
                        pl.col("scores").map.get(pl.col("subject")).alias("by_subject"),  # key from another column
                        pl.col("scores").map.contains_key("art").alias("has_art"),
                        pl.col("scores").map.len().alias("n"),
                        pl.col("scores").map.keys().alias("keys"),
                        pl.col("scores").map.values().alias("values"),
                    )

Only the lookup part of the example in the release post is reproduced here. The frame in that example has three columns named user, scores and subject, and the scores column is declared as pl.Map(pl.String, pl.Int64), that is, a map with string keys and integer values. In the output the dtype of that column is shown as map[str, i64]. map.get accepts both a fixed key and a key taken from another column. In the example output, bob has no art key, so the by_subject value for that row is null and has_art is false.

The migration guide attaches the silent-impact warning to this change too. Map columns coming from Arrow (pl.from_arrow and others), Parquet and Iceberg used to be flattened to List(Struct) and now load as Map, and their Python values are dicts rather than lists of key/value structs. No error is raised, and what changes is the schema and the shape of the values returned by to_list(), to_dicts() and rows(). Code that used the list or struct namespaces on these columns now fails.

The guide says that when the previous shape is needed it can be recovered with map.entries(), and that when scanning, the column can be loaded as entries in the first place by giving a List(Struct) type in schema.

  • Inference is unchanged. pl.Series([{"a": 1}]) is still a Struct. Map only arises from an explicit dtype, from list.to_map(), or from Arrow, Parquet, Iceberg or IPC input.
  • Constraints on keys. Keys are unique within a row and never null. Duplicate keys in a Parquet map are repaired on read, with the first position and the last value winning.
  • Export. to_arrow(), write_parquet() and write_ipc() export a Map column as a real Arrow map and round-trip it as Map.
  • Namespace. Expr.map and Series.map provide entries(), keys(), values(), len(), contains_key() and get().
  • Casting during key lookup. get() and contains_key() cast the key they look up to the key type of the Map, and a key that the cast cannot represent exactly is treated as absent.

Stricter Behavior - Results That Change Silently and Calls That Now Raise

The release post says Polars aims to be strict and fail fast. Errors should ideally raise up-front, not 20 minutes into a pipeline, and implicit behavior on data-mismatches should be opt-in, not a default. The reason it gives is that those mismatches can hide bugs.

The post says this strictness has become even more valuable with the rise of AI-driven development. Agents can validate the structure of a query early by calling collect_schema(), which resolves types and catches schema-level mismatches without materializing any data. Not all errors can be caught during compilation of the query plan, and some depend on data. In those cases, the post says, Polars defaults to stricter behavior to ensure inconsistencies are caught instead of silently producing different results. How AI coding tools relate to the design of data systems was covered in Wes McKinney on the Future of Data Systems in the AI Era.

The pre-release post gives three examples. is_in used to cast operands of different dtypes to their common supertype before comparing, and it now coerces only when doing so is lossless and raises otherwise. The example is an Int64 value of 9007199254740993 that was coerced to Float64 and silently rounded down to 9007199254740992.0, giving a false positive. Horizontal concat now raises a ShapeError when the heights differ instead of filling with null. Casts between integers and Enum or Categorical types, and casts from strings to temporal types, are removed in favor of dedicated methods (.cat.to(dtype), .cat.physical(), .str.to_date() and .str.to_datetime()).

Calling removed functionality now raises new exceptions that point to the replacement. Removed attributes and methods raise AttributeRemovedError, and removed or renamed parameters raise ArgumentRemovedError. The guide states that coverage is not complete. Some entries, which the guide marks in its removal table, still raise a plain built-in AttributeError or TypeError rather than one of the new typed exceptions.

Changes that turn into errors show themselves when the code runs. The ones that take more work are the changes where the result differs with no error. In the body of the guide, the warning sentence This change may silently impact the results of your pipelines appears 12 times. Six of those items are listed below.

  • The streaming default. Row order is no longer the same for operations that do not require an order, because the streaming engine does not guarantee it there.
  • explode(). An empty list now explodes into zero rows rather than one null row. Row counts change wherever a list column contains empty lists. The previous behavior is obtained with empty_as_null=True.
  • Integer supertype. Adding a signed integer column to a UInt64 column now produces Int128 rather than Float64. Both the output dtype and the computed values change.
  • Selectors combined with pl.col. Combining a selector with pl.col(...) through &, | or ^ is now read as an element-wise operation rather than a set operation on columns. For compatible dtypes the switch happens without an error.
  • Map columns. Map columns that come from Arrow, Parquet and Iceberg now load as Map instead of being flattened.
  • Horizontal concat. Frames of different heights are no longer padded and raise an error instead. When padding is wanted, how="horizontal_extend" is used.

Benchmark Conditions - What Was Measured and How

The benchmark in the release post was run by Polars and published by Polars. The post says Polars SQL was run on data derived from TPC-H and TPC-DS, and a footnote states that these benchmarks are derived from the TPC-H and TPC-DS Benchmarks and that, as such, any results obtained are not comparable to published TPC-H and TPC-DS Benchmark results, since the results obtained do not comply with those Benchmarks. The README of the benchmark repository carries the same notice.

Three of these conditions bear directly on how the results are read. First, each value is the best of 5 runs in a hot setting. Averages and first-run times are not in the tables. Second, some queries are excluded. Polars and both DuckDB versions completed all queries, while DataFusion timed out on TPC-DS q72 (and once on q67) and ran out of memory on TPC-H q18 on the c7a.4xlarge. Those queries are excluded from the results for all engines. Third, the query text was generated by DuckDB, and the row-group sizes of the data are the defaults of tpcgen-cli. The post says the team confirmed that those defaults are roughly similar to what Polars scan_csv piped through sink_parquet and DuckDB COPY produce.

The post encourages readers to replicate the results and shares the repository pola-rs/polars-2.0-benchmark. The README gives, per engine, the commands that set up the environment with uv, generate the data with setup.py and run bench.py with --iters 5 --timeout 60. It says that on the 192 core machine an additional Polars run was made with --threads 32, and that the file cache was dropped before each command. The raw data that was observed is in results/ in the repository.

  • Self-measured. The party that ran the measurement, aggregated the numbers and published the results is Polars in each case.
  • Not TPC-compliant. The footnote in the source says the benchmarks are derived from TPC-H and TPC-DS and that the results are not comparable to published TPC-H and TPC-DS Benchmark results.
  • Exclusion rule. The queries that DataFusion did not complete, whether through a timeout or by running out of memory, were removed from the results for all engines.
  • Repository. The commands needed for reproduction and the raw results that were observed are public in the benchmark repository.

Benchmark Results - The Sum Table in the Appendix and 192 Threads

The concluding sentence in the release post comes with conditions. It says default Polars is fastest on all but one benchmarks, and goes straight on to say that Polars has a constant overhead when scaling to 192 threads, which hurts small data queries. It adds that Polars limited to 32 cores is competitive or winning in all benchmarks, that the cause has been diagnosed, and that the team will hopefully fix this problem in the next release.

The appendix has two tables of figures in seconds, one for the sum of query times and one for the geometric mean. The values below are those of the sum table, which adds up, per configuration, the best times of the queries that every engine completed. In each row the smallest value is the fastest engine, and Polars with 32 threads was only run on the c7a.metal.

In the four rows for the 16 vCPU machine, the sum for default Polars is the smallest. The same holds in the two SF100 rows for the 192 vCPU machine. In the two SF10 rows for the 192 vCPU machine, default Polars is not the smallest value. On TPC-H it is 3.10 seconds, larger than the 2.46 seconds of DuckDB 1.5.6, and on TPC-DS it is 23.16 seconds, larger than the 12.25 and 12.92 seconds of the two DuckDB versions. In those same two rows, Polars fixed to 32 threads is the smallest at 1.97 and 9.63 seconds. This is where the constant overhead that the source describes for 192 threads and small data queries becomes visible in the numbers.

The appendix also describes scaling with core count. Moving from 16 to 192 vCPUs at SF100 makes Polars 3.8x faster on TPC-H and 2.2x faster on TPC-DS by sum. Under the same conditions the figures are 3.2x and 1.9x for DuckDB 1.5.6, 2.2x and 1.5x for the DuckDB 2.0 alpha, and 1.7x and 1.0x for DataFusion. At SF10 the extra cores do not help Polars with its default settings. The appendix says it is equally fast on TPC-H and 1.8x slower on TPC-DS, while DuckDB 1.5.6 still gets 1.8x and 1.3x faster.

The sentence that can be carried away from this benchmark is therefore a conditional one. In a measurement published by Polars, on these machines and at these scales, by the sum over the queries left after removing those DataFusion did not complete, default Polars was the fastest in six of the eight configurations. The case of small data on a machine with many cores is one the source itself records as an exception.

  • 16 vCPUs. On the c7a.4xlarge, default Polars has the smallest sum in all four rows of the sum table.
  • 192 vCPUs, SF100. On the c7a.metal at SF100, default Polars has the smallest sum in both rows, at 9.85 seconds on TPC-H and 42.33 seconds on TPC-DS.
  • 192 vCPUs, SF10. On the c7a.metal at SF10, default Polars does not have the smallest sum in either row, and the run fixed to 32 threads does.
  • Scaling factors. Going from 16 to 192 vCPUs at SF100, the speedup of Polars is the largest among the four engines listed in the appendix. At SF10 the extra cores do not help Polars with its default settings.
  • The announced fix. The wording is will hopefully fix this problem in the next release, which is not a committed date.

Order of Migration - What the Migration Guide Says

The migration guide groups the changes into six blocks. These are Breaking changes, casts and operations no longer supported, API reshapes, CSV reading changes, removal of deprecated functionality, and new Deprecations.

The pre-release post says most of the removed functionality has been deprecated for a long time and hopefully should not have affected pipelines that stayed up to date. The removal table in the guide lists the version in which each item was deprecated. For example, melt() was deprecated in 1.0, group_by(...).count() in 0.20, and collect(streaming=...) in 1.25.

There are also three new deprecations. read_avro() and write_avro() are marked as unstable. strict=True on horizontal concat is deprecated because it no longer does anything now that equal heights are always required. cut() and qcut() are deprecated in favour of bin_intervals(), bin_quantiles() and bin_ranks().

The warning marks in the guide supply a criterion for the order of checking (interpretation). A change that surfaces as an error is seen as soon as the code runs, while an item carrying the silent-impact warning is seen only when results are compared. The list below places the remedies written in the guide with the warned items first.

  • Lazy queries that rely on order. Sort explicitly, or pass maintain_order to operations that support it. While migrating, the previous engine can be kept through the engine affinity.
  • Places that use explode. If a column contains empty lists the row count changes, so decide whether to pass empty_as_null=True.
  • Operations that mix signed integers and UInt64. The output of such an operation becomes Int128 where it used to be Float64.
  • Places that read map columns. Either keep the previous shape, with map.entries() or by giving a schema when scanning, or move the code over to the Map namespace.
  • Horizontal concat. The heights of the frames must now be equal. When padding is what was intended, it is requested with how="horizontal_extend".
  • Parameters of the readers. Remove from the call sites the parameters that read_csv and read_ipc no longer accept. The guide says that if rechunking is needed, .rechunk() should be called on the returned frame instead.

What Could Not Be Confirmed

  • The unit behind all but one. The release post does not say what it counts as one benchmark. In the sum table of the appendix, the rows where default Polars is not the smallest are the two SF10 rows on the c7a.metal.
  • The range of many expressions. The release post does not list which expressions support out-of-core.
  • How to configure out-of-core. The names of the settings that change the 80% threshold and the 64GB budget, and where the temporary files are placed, were not found in the release post or the migration guide.
  • When joins and group-by get out-of-core. No schedule is written beyond the phrase in the coming time, either in the out-of-core section or in the closing words of the post.
  • The cause of the 192-thread overhead. The release post says only that the cause has been diagnosed on the Polars side and does not describe what it is.
  • The full list of operations without an order guarantee. Both the release post and the guide leave the end of the list open.
  • Memory usage. The release post speaks of massive memory and performance improvements on most queries but carries no memory usage figures, either for the benchmark or for any other workload.
  • Independent reproduction. The benchmark repository is public, but no result reproduced by a party outside Polars could be confirmed.
