re_gent - Version Control and Auditability for AI Coding Agents

Git tracks files. re_gent tracks agents - the tool that tells you which prompt wrote which line

2026-06-16 Dev & Infra

Introduction: Agents Have No Version Control of Their Own

Anyone who has used an AI coding agent seriously knows the same frustration. You tell Claude Code or Codex to "fix this bug," and the agent reads several files, runs tools, and edits code. Then thirty minutes later something breaks, and there is no way to retrace exactly which prompt damaged which line. Ask the agent to "revert it" and it half-reverts into a Frankenstein state. So we fall back on primitive backups: screenshotting the "version that worked" or copy-pasting code into a fresh chat.

In June 2026, re_gent (regent-vcs), which surfaced on GeekNews, takes direct aim at this gap. As its creator Shay Livni frames the core problem in a single line: "Git tracks what developers do. Nothing tracks what agents do." Rather than reproducing the original, this post analyzes what re_gent actually does and, more importantly, why version control and auditability suddenly become critical infrastructure in the AI agent era, from my own point of view.

Let me set a clear caveat first. The features and specs here are based on re_gent's public repository, official site, and the creator's writing. And one asterisk up front: re_gent is in public alpha. The direction is clear, but production maturity is still being proven, so read it with that in mind.

1. What re_gent Is - Git for Agent Activity

In one line, re_gent is version control for AI coding agents. The official site puts it plainly: "Git tracks files. Regent tracks agents." Where git handles human-authored, commit-level changes, re_gent automatically captures a much lower layer - the change an agent makes on every single tool call.

1.1 Three Core Operations

The basic operations deliberately echo git's. The command prefix is rgt.

  • Log (rgt log): Shows what each agent session did - which tools it called in which order and which files it touched - in causal order. It is the agent version of git log.
  • Blame (rgt blame): Answers "which prompt wrote this line?" It annotates each line with the Step hash that introduced it, so you can trace provenance line by line.
  • Show (rgt show): Reconstructs the "full context" of a given change, restoring the exact prompt and conversation flow that produced that Step.

Add to these rgt sessions (managing concurrent sessions) and rgt diff (comparing file and conversation changes between two Steps). The key point is that you never create a commit manually. Every agent turn is captured automatically.

1.2 How It Works - Steps and Content-Addressed Storage

re_gent deliberately mirrors git's architecture but reimplements it from scratch. It keeps a .regent/ folder in your working directory and records state with four object types: Blobs (file bytes content-addressed by BLAKE3 hashes), Trees (workspace snapshots with per-line provenance), Steps (immutable records of each tool call - parent pointers, transcript hash, tool arguments and results), and Refs (mutable pointers to current session state).

Each tool call becomes one Step, and Steps form a directed acyclic graph (DAG). Each session keeps its own Ref, so multiple concurrent sessions get separate branches without workspace conflicts. Content-addressed storage deduplicates common ancestors automatically, and a SQLite index answers queries fast. The stack is nearly single-language Go (about 98.6% Go), using Cobra (CLI), BLAKE3 (content addressing), SQLite (indexing), and the Myers diff algorithm.

1.3 The Record Survives /compact

To me, re_gent's smartest design is this. Agent conversations are highly volatile. Tools like Claude Code compact or delete messages via /compact to shrink context, and in that instant the answer to "what was that prompt again?" evaporates. re_gent preserves the complete record in separate content-addressed storage regardless of how the tool cleans up its history. In the creator's words, you never lose the audit trail no matter what the agent does to its own history. This persistence is not just backup - it is the foundation of auditability.

2. Why Now - The Era of Agents Writing Code Directly

What makes re_gent interesting is less the tool itself than the trend it points to. Let me unpack why such a tool became necessary in 2026.

2.1 The Author of Code Has Changed

Just two or three years ago, AI was an assistant suggesting snippets for developers to paste. Humans committed every line, so git blame was, in effect, accountability tracking. The 2026 coding agent is different. Without a human at every step, it loops through plan, execute, check, and fix to produce pull-request-scale changes. Behind a single commit sits not a person but dozens of prompt-and-tool-call iterations. A wide gap has opened between git's unit of tracking (the commit) and the agent's unit of work (the tool call).

2.2 Auditability Became a Procurement Requirement

This gap is not mere inconvenience - it is a governance problem. From my research, as of 2026 enterprise procurement of AI coding tools treats "how AI-generated code changes are attributed, logged, and governed" as a standard security and legal review item. Frameworks such as NIST AI RMF and NIST SSDF, the EU AI Act's provenance requirements, SOC 2, and ISO 27001 apply when agents contribute to production code. An audit trail for AI-generated code is described as requiring "a chronological, tamper-evident, context-rich ledger linking technical provenance with governance records."

The industry sometimes calls this an "Action Provenance Graph" - a structure linking prompts, plans, tool invocations, intermediate reasoning, and outcomes so auditors can reconstruct causal pathways. re_gent's Step DAG is, in effect, a local, open-source implementation of that graph. What the grand governance discourse demands abstractly, re_gent makes concrete with a single .regent/ folder.

2.3 The Nature of Debugging Changes

What hits home practically is debugging. When chasing a bug an agent introduced, what we really want to know is not "which line is wrong" but "which instruction produced this wrong line." Was the prompt ambiguous? Did the agent lose context? Did it make a bad assumption? Without provenance, we reason backwards from code alone. re_gent's blame lets you jump straight from a faulty line to the prompt that produced it, turning debugging from "code archaeology" into "record lookup." You can even bisect agent sessions to locate when a bug was introduced.

3. The Practical Workflows re_gent Unlocks

A tool's value lies not in its command list but in the work it enables. Here is what re_gent actually changes.

3.1 Provenance-Based Debugging

Identify a problematic change and the prompt that caused it instantly. Use rgt blame to find the Step hash of a suspect line, then rgt show <hash> to restore the prompt and conversation at that moment. "Why did the agent do this?" becomes a lookup rather than a guess.

3.2 Non-Destructive Rewind

re_gent's rewind restores both workspace and conversation to a prior Step, but without destroying history - it creates a new branch point. That is the decisive difference from an agent's clumsy half-revert, what I call the "Frankenstein merge." When you wander down a wrong path, you can return to a clean point and try again.

3.3 Parallel Exploration and Agent-to-Agent Sharing

Because each session has its own Ref, multiple agents or sessions can work on separate branches and merge at a convergence point. More intriguing is agent-to-agent sharing: one agent passes a working branch as a single Step hash, and the recipient's re_gent reconstructs the full conversation and workspace from content-addressed objects. Just as humans collaborate via PRs, agents collaborate via Step hashes.

3.4 Querying the Agent Archive

You can query sessions by author, tool, and time. As the creator's example shows, a query like rgt log --author=claude --tool=Bash --since=yesterday isolates "what claude did with Bash since yesterday." For audits, retrospectives, and onboarding, "what have the agents been doing" becomes data you can work with.

4. Relationship to Git - Complement, Not Competitor

Let me clear up a common misconception in advance. re_gent does not replace git. They look at different layers.

In practice you use both. While the agent works, re_gent accumulates provenance for each tool call; when the result is mature enough for human review, you commit to git as usual. The git history stays a clean "history of outcomes," while re_gent keeps the "history of process" - how those outcomes came to be. In code review, when someone asks "why did this change happen this way?", if the PR author can answer from re_gent records instead of guessing, the review quality of agent-written code changes entirely.

5. A Practical Perspective - Where to Use It First

From my point of view, here is where agent version control like re_gent earns its keep first.

5.1 Organizations With Heavy Regulatory and Audit Burden

In finance, healthcare, and the public sector - where change history and accountability are audited - the biggest barrier to adopting agents is "how do you explain and trace AI-written code?" The more an organization is bound by privacy and security rules, the heavier this question. Per-agent, per-prompt provenance technically supports the compromise of "use AI, but keep it traceable." That said, an alpha tool will not fully meet audit requirements like tamper resistance, access control, and retention, so for now the realistic start is as a supplementary record for internal debugging and retrospectives.

5.2 Teams Running Agents at Scale

When several developers each run coding agents, "whose agent changed this" becomes a collaboration problem. re_gent's session queries and agent-to-agent sharing turn that confusion into data. Especially where humans review agent-authored PRs, showing prompt provenance alongside blame lets reviewers grasp intent fast.

5.3 Even for Solo Developers

The value is clear even for a solo developer with no governance concerns. Safely returning to "the point where it worked" in a long agent session, and tracing what went wrong where, is enough to free you from screenshot-and-paste backups. Running locally with no data leaving your machine also makes it pleasant for light use.

6. Considerations and Limitations

Showing only the upside would be dishonest. Here is what to weigh before adopting.

6.1 Alpha Maturity

re_gent is in public alpha. The direction and design are convincing, but long-term stability, large-repository performance, and edge-case handling are still being proven. Relying on a single alpha tool for a core codebase or regulated audit records is risky. Run it on non-critical workflows first, confirm in your own environment that records are captured accurately, then widen the scope.

6.2 Supported Tool Range

As of June 2026, official support covers Claude Code, the Codex CLI, and OpenCode. Cursor, Cline, Continue, and Aider are planned. If your agent is not yet supported, the value is limited. Because integration is hook-based, record completeness hinges on whether the tool exposes hooks and whether those hooks capture every tool call without gaps.

6.3 Storage Burden and Operations

Snapshotting every tool call can grow records fast. Content-addressed deduplication eases this, but with long sessions run over time you should monitor the size of .regent/ and index performance. And if you use it for audit purposes, you need a separate policy on who is responsible for the integrity and access control of the records themselves. Producing a record and keeping that record trustworthy are different problems.

7. Outlook - The Missing Piece of Agent Infrastructure

There is a reason I see re_gent as more than a convenience tool. Every new computing paradigm earned large-scale trust only once the basic infrastructure for tracking, undoing, and collaborating was in place. For developers, git played that role. In an era where agents write code directly, a layer that tracks, rewinds, and audits agent work must play the same role. re_gent aims precisely at that missing piece.

Whether a single open-source alpha will own this spot is uncertain. Cloud agent platforms could build in similar features, or a standard format could emerge. But the direction is clear. If the question of 2026 was "can we write code faster with AI," the next question is "can we trace, explain, and trust the code AI wrote." Auditability is becoming a precondition for agent coding to move from experiment into production.

8. Conclusion - Three Things You Can Apply Today

re_gent is in alpha, but the questions it raises are valid right now. Three concrete moves I would make this week.

8.1 Run It on Non-Critical Workflows First

If you use a supported agent (Claude Code, Codex, OpenCode), run rgt init on a side project rather than a core repo and walk through one session. Confirming with your own eyes that blame and show really reconstruct the prompt, and that no records are missing, is the only evidence that matters.

8.2 Fold Provenance Into Agent Code Review

If your organization has humans review agent-authored PRs, pilot the habit of viewing "the prompt provenance of this change" during review. When provenance is visible, "why was it done this way?" shifts from guess to confirmation. Even with an alpha tool, the habit itself is an asset.

8.3 Sketch Your Audit Policy in Advance

If your organization carries heavy regulatory and audit burden, design a policy before bringing agents into production: "how will we record, preserve, and verify the provenance of agent-written code?" Whether or not you use re_gent, the organizations that prepare an answer to this question will pass through the agent era safely.
