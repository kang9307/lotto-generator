シェルの終了コードと set -e - 何を捕まえ何を見逃すか

errexit・pipefail・nounset の死角を実行出力で全て開いてみる

2026-07-29 開発・インフラ

序論: CI は緑で、配備された値は空だった

先頭に set -euo pipefail が付いたスクリプトがある。設定ファイルから値を二つ読んで整理コマンドを組み立てる。設定ファイルにそのキーが無い状態で走らせてみた。結果はこうだ。

  target      = []
  retain_days = []
  would run: find /srv/backup/ -mtime + -delete
  DEPLOY OK
  script rc=0  <- CI sees GREEN

読めなかった値二つが空文字列になってそのまま流れた。組み立てられたコマンド行では経路が /srv/backup/ で終わってしまい、保管日数は消えて -mtime + だけが残った。それでもスクリプトの終了コードは0だ。CI は緑を点け、誰もこのビルドを見返さなかった。

このスクリプトには set -e も set -u も set -o pipefail も全て有効だった。俗に「シェルスクリプト安全三点セット」と呼ばれるあの行だ。その行はこの事故を防げない。なぜ防げないのか、どこまでなら防げるのかを知ることがこの記事の目的だ。

静かな失敗が恐ろしい理由は単純だ。失敗が終了コード 0 で報告されれば、それは失敗ではなく成功だからだ。人がログを読み飛ばして見逃すのではなく、パイプラインが「通過」と判定して見逃す。派手に死ぬスクリプトは直せばよいが、緑を点けながら誤ったことをするスクリプトは直す必要があるという事実そのものが発見されない。

この記事は set -euo pipefail を付けろとは勧めない。それがどこまで守ってくれるのかを先に見せ、その後で付けろと言う。規定は GNU Bash Reference Manual と POSIX 仕様で確認し、動作は全て一時ディレクトリで直接走らせた。本文の出力は全て実際に画面に出たものだ。15節の死角表がこの記事の結論だ。

軸を先に分けておく。同じスクリプトを二度走らせてよいかは二度走らせても安全なスクリプト、走らせる前に結果を知れるかは--dry-run を正しく作る方法にある。あちらが「計画と適用の結果をどう伝えるか」を扱うなら、こちらはその前段の「失敗をそもそもどう検知するか」を扱う。変数に引用符を付ける文法はシェルの引用符規則にある。

1. 実行環境とこの記事の根拠

本文の出力は全て実際に走らせた結果だ。再現環境は次のとおり。

  • OS: Windows 10 Pro 10.0.19045 上の MSYS2 系 Unix 環境
  • bash: GNU bash 5.2.37(1)-release (x86_64-pc-msys)
  • POSIX sh: dash — bash と分かれる箇所を確認するための対照群
  • ユーティリティ: GNU coreutils 8.32
  • 作業場所: 新規作成した一時ディレクトリ。実験ごとに下位フォルダを作って隔離

本文に出る経路は全て /tmp/demo のようなプレースホルダだ。実際の実行は隔離された一時フォルダで行った。終了コードと set 選択肢の動作はシェル自体の規定から来るものなので、Linux や macOS に移しても同じだ。ただしこの環境で再現しなかった項目が一つあるので先に記しておく。

環境で分かれた箇所 — 実行権限ビット
POSIX は「見つかったが実行できなければ 126」を規定する。Linux では実行ビットを外したファイルを実行すると 126 が出る。ところがこの環境は NTFS 上なので chmod 644 が実際には強制されず、実行ビットを外してもスクリプトがそのまま実行されて 0 が出た。そこで 126 はディレクトリを実行しようとする場合で確認し、こちらは正常に 126 が出た。本文の 126 の例が権限ではなくディレクトリである理由だ。

規定の確認には一次資料のみを使った。「たいていこうだ」という記述はこの記事に無い。

  • GNU Bash Reference Manual — The Set Builtin(-e・-u・pipefail)、The Shopt Builtin(inherit_errexit)
  • The Open Group Base Specifications Issue 8 — Shell Command Language 2.8.2 Exit Status and Errors
  • 実行中の bash 自身 — help set でこのバイナリの選択肢説明を直接確認

2. 終了コードの基礎 - 0・1・126・127・128+N

全てのコマンドは終わるときに 0 から 255 の間の整数を残す。シェルはそれを $? に入れる。規則は一つだ。0 は成功、残り全部が失敗。「1 が失敗」ではなく「0 でなければ失敗」という点が重要だ。

$ true;  echo $?
0
$ false; echo $?
1
$ no_such_command_xyz 2>/dev/null; echo $?
127
$ ./sandbox 2>/dev/null; echo $?        # ディレクトリを実行しようとすると
126
$ bash -c 'exit 3'; echo $?
3

127 と 126 は POSIX が直接規定した値だ。仕様の 2.8.2 節はこう記す。

If the command is not found, the exit status shall be 127. (…) if the command name is found, but it is not an executable utility, the exit status shall be 126.

つまり127 はほぼ常に打ち間違いか PATH の問題だ。コマンドが失敗したのではなく、コマンドが見つからなかった。この二つを区別すると CI ログを読む時間が大きく減る。

シグナルで死んだ場合は 128 を足した値になる。実際に作って確認した。

$ sleep 30 & pid=$!; kill -9 "$pid"; wait "$pid" 2>/dev/null; echo $?
137
$ sleep 30 & pid=$!; kill -TERM "$pid"; wait "$pid" 2>/dev/null; echo $?
143

137 は 128+9(SIGKILL)、143 は 128+15(SIGTERM)だ。コンテナがメモリ超過で死ぬと 137 が出るのはこの計算のためだ。ただし POSIX の表現は少し緩い。

If the command terminated due to the receipt of a signal, the shell shall assign it an exit status greater than 128. The exit status shall identify, in an implementation-defined manner, which signal terminated the command.

すなわち「128 より大きい」までが規定であり、正確に 128+N であることは実装が決める慣例だ。実務の主要なシェルは全て 128+N を使うので信じて使ってよいが、規定と誤解しないようにしたい。

コードは 8 ビットで切られる。これも実測した。

$ bash -c 'exit 256'; echo $?
0
$ bash -c 'exit -1' 2>/dev/null; echo $?
255
$ sh -c 'exit 300'; echo $?
44

exit 256 が 0 になる。失敗を知らせようと大きな数字を選んだのに成功として報告される事故がここで起きる。エラー件数をそのまま終了コードに使うスクリプトが特に危ない。エラーがちょうど 256 件なら緑だ。

最後に、0 と 1 が常に成功と失敗であるわけでもない。道具ごとに独自の規約がある。

$ printf 'alpha\nbeta\n' > /tmp/demo/data.txt
$ grep -q alpha /tmp/demo/data.txt; echo $?
0
$ grep -q zzzzz /tmp/demo/data.txt; echo $?
1
$ grep -q alpha /tmp/demo/nope.txt 2>/dev/null; echo $?
2

grep は0 を発見、1 を未発見、2 をエラーとして使う。「見つからない」は正常な結果でありエラーではない。ところが set -e は 1 も 2 も同じく失敗と見なす。grep を set -e の下で素のまま呼ぶと「無い」という正常な結果がスクリプトを殺す。13節で改めて扱う。

3. set -e の規定 - マニュアルが例外を自ら列挙する

set -e(errexit)の説明は help set の一行ではこうだ。

-e Exit immediately if a command exits with a non-zero status.

この一行だけ読むと「失敗すれば無条件に止まる」と理解してしまう。そしてその理解がこの記事に出る全ての事故の出発点だ。Bash Reference Manual の完全な記述ははるかに長く、例外を自ら列挙する。

The shell does not exit if the command that fails is part of the command list immediately following a while or until reserved word, part of the test in an if statement, part of any command executed in a && or || list except the command following the final && or ||, any command in a pipeline but the last (subject to the state of the pipefail shell option), or if the command's return status is being inverted with !.

五つだ。while・until 直後のコマンドリスト、if の条件、&& と || リストの最後以外のコマンド、パイプラインの最後以外のコマンド、! で反転されたコマンド。ここまでは比較的知られている。本当の罠はその次の段落だ。

If a compound command or shell function executes in a context where -e is being ignored, none of the commands executed within the compound command or function body will be affected by the -e setting, even if -e is set and a command returns a failure status.

噛み砕くとこうなる。関数を if の条件に入れた瞬間、その関数本体の全体が set -e の保護の外に出る。条件の位置にあるのは関数呼び出しの一行だけなのに、効力は関数内の全ての行に及ぶ。次の節で実行して見せる。

4. set -e が捕まえられない箇所 - 全て実行で

規定だけ読むと抽象的だ。死角を一つのスクリプトに全て詰め込み、先頭に set -e を付けて走らせた。一つでも引っかかればそこで死ぬはずだ。

まず基準線だ。set -e が正しく動作する場合を確認しておく。

== A. baseline: set -e DOES stop here ==
  inner script died, rc=1  (NOT REACHED never printed)

素の false は確実に捕まえる。ここからが死角だ。以下は一回の実行で連続して出た出力である。

== B. condition of if ==
  survived: if-condition

== C. while condition ==
  survived: while-condition

== D. left side of && / || ==
  survived: false &&
  ran RHS of ||
  survived: false ||

== E. negated with ! ==
  survived: ! true

== F. non-final command of a pipeline ==
  survived: false | cat   rc=0

== G. function failing inside a condition ==
  ...function continued past its own false
  survived: function under if

== H. local x=$(failing) hides the status ==
  local v=$(false) -> rc=0  (local's own status wins)
  split declaration caught it -> rc=1

== J. arithmetic that evaluates to zero ==
  (( c++ )) returned nonzero because the OLD value was 0; c is now 1

== ALL BLIND SPOTS PASSED THROUGH; script still alive ==

一つも引っかからなかった。最下行まで到達したということは、set -e が有効なままこれら全ての失敗を通したという意味だ。項目ごとに見ていく。

  • B・C — if false; then …; fi と while false; do …; done。条件は失敗してよい場所だ。当然である。失敗こそが「偽」という意味を担うからだ
  • D — false && echo x も false || echo … も生き残った。|| true を付ける慣用句はここから来る。便利だが代償が大きい。13節で改めて見る
  • E — ! true は最終結果が失敗(1)なのに通過する。反転されたコマンドは例外一覧に明記されている
  • F — false | cat の終了コードが0だ。パイプラインのコードは末尾のものであり、cat は成功した。7節の主題である
  • G — 最も危険だ。関数内の false の次の行がそのまま実行された。3節のマニュアル最終段落そのものだ。関数を if に入れた瞬間、本体全体が無防備になる
  • H — local が終了コードを飲み込んだ。5節で別途扱う
  • J — (( c++ )) は演算結果が 0 なら終了コード 1 だ。カウンタが 0 から始まると最初の増加でスクリプトが死ぬ。(( ++c )) や c=$((c+1)) を使えば避けられる
⚠ G が実務で現れる形
「関数で包んで if で検査する」はごく自然な構造だ。if deploy_app; then … の一行を書いた瞬間、deploy_app 内の全ての失敗が無視される。途中の段階が全て失敗しても最後の行が成功すれば関数は 0 を返し、if は真と判定する。関数内で set -e を信じていたなら、その信頼が呼び出し方一つで消える。

5. local が終了コードを飲み込む

4節の H が set -e の罠の中で最も頻繁に実務を崩す。原理は単純だ。local は代入の文法ではなくビルトインコマンドであり、コマンドの終了コードは local 自身のものだ。内側のコマンド置換が何で終わろうと、local は「変数をうまく作った」という意味で 0 を返す。

まず素の代入がどう動作するか見よう。こちらは正常だ。

== plain assignment: status comes FROM the substitution ==
  v=$(false)      -> rc=1
  v=$(exit 7)     -> rc=7
  v="pre-$(exit 7)-post" -> rc=7  v=[pre--post]

代入式の終了コードはコマンド置換のコードがそのまま上がってくる。文字列の途中に挟んでも 7 が生き残る。だから set -e はこの形を正常に捕まえる。ここで前に宣言キーワードを一つ付けてみよう。

== declaration builtins SWALLOW it ==
  local    v=$(exit 7) -> rc=0
  declare  v=$(exit 7) -> rc=0
  typeset  v=$(exit 7) -> rc=0
  export   v=$(exit 7) -> rc=0
  readonly r=$(exit 7) -> rc=0

五つとも 0 だ。local だけの問題ではなく宣言ビルトイン全体の性質である。export PATH_X=$(some_command) も同じように失敗を飲み込む。

set -e と組み合わせたときどの形が実際にスクリプトを殺すか確認した。

== under set -e: which one actually kills the script? ==
  rc=7   out=[]
     form: v=$(exit 7); echo ALIVE
  rc=0   out=[ALIVE-in-func
ALIVE]
     form: f(){ local v=$(exit 7); echo "ALIVE-in-func"; }; f; echo ALIVE
  rc=7   out=[]
     form: f(){ local v; v=$(exit 7); echo "ALIVE-in-func"; }; f; echo ALIVE

真ん中の形だけが生き残り ALIVE を二度出力した。一つ目と三つ目はコード 7 で正しく死んだ。違いは宣言と代入を一行に書いたか二行に分けたかだけだ。

複数を一行で宣言するともっと静かになる。

== the multi-declaration variant is worse ==
  three locals, rc=0  b=[]

真ん中のものだけが失敗したのにどれが失敗したのか知る方法が全く無い。終了コードは 0 で、失敗した変数だけが静かに空の値になる。

規則を一つだけ覚えるなら
local x=$(cmd) は常に二行に割る。local x で名前だけ作り、次の行で x=$(cmd) と代入する。declare・export・readonly も同じだ。この規則一つが set -e 事故のかなりの部分を無くす。

6. コマンド置換は errexit を継承しない

もう一つの死角がある。$( ) の内側は既定では set -e が切られた別世界だ。実行して確認した。

$ shopt inherit_errexit
inherit_errexit	off

== A. WITHOUT inherit_errexit ==
  out=[LEAKED]  rc=0
  script continued
  rc=0

set -e が有効なスクリプトで out=$( false; echo "LEAKED" ) を実行した。内側の false がサブシェルを止められず、後ろの echo が実行されて LEAKED が変数に入った。複数のコマンドを $( ) の中に並べる習慣があるなら、前方が全て失敗しても最後のものさえ成功すれば値が作られる。

bash 4.4 からこれを直す選択肢ができた。マニュアルの記述はこうだ。

If set, command substitution inherits the value of the errexit option, instead of unsetting it in the subshell environment. This option is enabled when POSIX mode is enabled.

有効にして同じコードを走らせると結果が分かれる。

== B. WITH inherit_errexit ==
  rc=1

== C. POSIX mode also turns it on ==
  rc=1

どちらも内側の false で死んだ。マニュアルどおり --posix で起動しても同じ効果が出た。そこで実務の推奨はこうなる。

set -euo pipefail
shopt -s inherit_errexit    # bash 4.4 以上

ただしこれも万能ではない。12節で inherit_errexit を有効にしても通過する事例を示す。local が先にコードを飲み込むと inherit_errexit が介入する機会そのものが無いからだ。

7. set -o pipefail - パイプラインの本当の状態を取り戻す

パイプラインの終了コードは既定では末尾のコマンドのものだ。前方が何で死のうと無視される。

== 1. pipeline status = LAST command, by default ==
  false | true   -> rc=0
  true  | false  -> rc=1
  false | cat    -> rc=0

false | true が成功だ。前が失敗したのに結果は 0 である。pipefail を有効にすると変わる。

== 2. same pipelines with pipefail on ==
  false | true   -> rc=1
  true  | false  -> rc=1
  false | cat    -> rc=1

三つとも失敗に変わった。実行中の bash 自身の説明はこうだ。

pipefail — the return value of a pipeline is the status of the last command to exit with a non-zero status, or zero if no command exited with a non-zero status

「0 でないコードのうち最も右のもの」という意味だ。確認した。

== 3. pipefail returns the RIGHTMOST nonzero ==
  (exit 3)|(exit 4)|true -> rc=4
  (exit 3)|true|true     -> rc=3

実務でこれが最も大きく引っかかる場所が tee だ。ログを残そうとパイプにつないだ瞬間、失敗が消える。

== 5. the classic: cmd | tee log ==
  no pipefail: rc=0  PIPESTATUS=(1 0)   <- failure vanished
  pipefail   : rc=1  PIPESTATUS=(1 0)

同じパイプラインなのに上は成功、下は失敗だ。ビルドコマンドを | tee build.log で包むのは非常によくあるパターンであり、pipefail が無ければビルドが壊れても CI が通過する。

ところが pipefail には逆方向の代償がある。正常な早期終了を失敗に変えてしまう。

== 8. pipefail cannot see a head that quits early (SIGPIPE) ==
  yes | head -1 -> rc=141  PIPESTATUS=(141 0)

head -1 が一行だけ読んで閉じると yes が SIGPIPE で死んで141(128+13)になる。何の問題も無い正常な動作なのに pipefail がこれを失敗として上げる。grep -q や head で前方を断つパイプラインを使うなら、その箇所は別途処理が要る。

8. PIPESTATUS - 段階ごとに読み、直ちに保存する

pipefail は一つのコードにまとめてしまう。どの段階が失敗したかを知るには bash の PIPESTATUS 配列を使う。

== 4. PIPESTATUS keeps every stage ==
  rc=0  PIPESTATUS=(3 0 4 0)

四段階のコードが全て残った。終了コードは末尾に従って 0 だが、配列を見れば1 番目と 3 番目の段階が失敗したことがそのまま見える。

ただしこの配列には致命的な性質がある。次のコマンド一つで直ちに上書きされる。

== 6. PIPESTATUS is clobbered by the very next command ==
  first read : PIPESTATUS=(3 4)
  second read: PIPESTATUS=(0)   <- the echo above overwrote it

最初の echo が成功した瞬間、配列が (0) に変わった。二度読むことはできない。だから必ずパイプラインの直後の行で複製しておく。

== 7. save it immediately ==
  saved copy : (3 4)  stage0=3 stage1=4

実務の形はこうだ。パイプラインの直後に配列を丸ごと複製し、その後は複製だけを見る。

curl -fsS "$url" | gzip -d | psql "$dsn"
st=("${PIPESTATUS[@]}")          # 必ず直後の行で
if [ "${st[0]}" -ne 0 ]; then echo "ダウンロード失敗 (${st[0]})" >&2; exit 1; fi
if [ "${st[1]}" -ne 0 ]; then echo "展開失敗 (${st[1]})" >&2; exit 1; fi
if [ "${st[2]}" -ne 0 ]; then echo "投入失敗 (${st[2]})"     >&2; exit 1; fi

pipefail だけなら「どこかで失敗した」までしか分からないが、こうすれば「ダウンロードが失敗した」までログに残る。三段以上のパイプラインではこの差が大きい。

9. set -u - 未定義変数と空の配列

set -u(nounset)は定義されていない変数を参照すると直ちに終了する。打ち間違いで作られた空の値がコマンド行に流れ込むのを防ぐ仕掛けだ。

== 1. plain unset reference ==
  echo "[$nope]"     rc=127 bash: line 1: nope: unbound variable
  echo "[${nope}]"   rc=127 bash: line 1: nope: unbound variable

ここで終了コードが興味深い。同じエラーなのに呼び出し方によって値が異なる。四つの組み合わせを全て確認した。

$ bash -u -c 'echo "[$nope]"'   ; echo $?
127
$ bash -u script.sh             ; echo $?
1
$ dash -u -c 'echo "[$nope]"'   ; echo $?
2
$ dash script.sh                ; echo $?
2

bash は -c で呼ぶと 127、スクリプトファイルで呼ぶと 1 だ。dash はどちらも 2 でメッセージも parameter not set と異なる。set -u が出した失敗を特定の終了コードで区別しようとするのはやめよう。移植性が無い。

回避は既定値の文法で行う。コロンの有無で違う。

== 2. defaults let you opt out ==
  ${nope:-fallback}        rc=0   [fallback]
  ${nope-fallback}         rc=0   [fallback]
  ${nope:?must be set}     rc=127 bash: line 1: nope: must be set

== 3. set vs empty are different ==
  empty="" then ${empty:-d}   rc=0   [d]
  empty="" then ${empty-d}    rc=0   []

コロンがあれば「無いか空なら」、無ければ「無ければ」だ。空文字列を有効な値として扱う必要があるならコロンを外す。${var:?メッセージ} は必須引数を強制するときに便利だ。自分で if を書かずに一行で済む。

次によく混乱する空の $@ と空の配列だ。bash のバージョンによって分かれてきた部分なので、この環境のバージョンとともに記す。確認したバージョンは GNU bash 5.2.37 である。

== 4. empty $@ and $1 ==
  no args, "$@"        rc=0   argc=0 / REACHED
  no args, "$1"        rc=127 bash: line 1: $1: unbound variable
  no args, "${1:-def}" rc=0   [def] / REACHED

== 5. empty arrays ==
  declare -a arr=(); "${arr[@]}"   rc=0   n=0 / REACHED
  unset arr; "${arr[@]}"           rc=0   REACHED
  declare -a arr=(); "${arr[0]}"   rc=127 bash: line 1: arr[0]: unbound variable
  empty array + ${arr[@]:-}        rc=0   x=[] / REACHED

整理するとこうだ。bash 5.2.37 では引数が無いときの "$@" と空の配列の "${arr[@]}" は安全だ。一方"$1" や "${arr[0]}" のように個別の要素を掴むと弾ける。境界線は「全体を展開するか、特定の要素を掴むか」である。

古い bash についての注意
空の "$@" と空の配列が set -u でエラーになった時代があった(bash 4.4 以前)。上の結果は5.2.37 で直接確認したものであり、この環境に古い bash が無いため過去の動作は再現していない。macOS 既定の bash 3.2 のような古いシェルを対象にするなら "${arr[@]:-}" の形で守るほうが安全だ。

最後に、set -u は失敗したコマンドとは何の関係も無いことを確認しておく。

== 6. -u alone does not stop a FAILING command ==
  -u only, false   rc=0   REACHED
  -eu, false       rc=1   (no output)

-u だけを有効にすると false がスクリプトを殺せない。三つの選択肢はそれぞれ別の仕事をし、互いの代わりにはならない。

10. trap - ERR で見つけ EXIT で片付ける

trap は失敗地点を記録し後片付けを保証する仕掛けだ。ERR トラップから見よう。

== 1. ERR trap reports line and command ==
  step one
  ERR: line 5 rc=2 cmd=[grep -q nothing /nonexistent/path]
  outer saw rc=2

LINENO・$?・BASH_COMMAND の三つの変数で何行目でどのコマンドがどのコードで死んだかが一行に残った。set -x で全部出すよりログがはるかに綺麗だ。

関数の中まで及ばせるには -E(errtrace)が要る。

== 5. functions need -E (errtrace) to inherit the ERR trap ==
  without -E: trap did not fire inside f
  with -E: trap fired inside f

set -e ではなく set -eE と書く理由がこれだ。-E が無いと関数・サブシェル・コマンド置換の中で ERR トラップが動作しない。

ところが決定的な限界がある。ERR トラップは set -e と全く同じ死角を持つ。4節の死角をそのまま ERR トラップの下で走らせた。

== 4. ERR trap has the SAME blind spots as set -e ==
  reached the end with no ERR trap firing
  outer saw rc=0

if false、false || true、! true、false | cat、local v=$(exit 7) を全て実行したのにトラップが一度も発火しなかった。「ERR トラップを付けたから失敗は全部捕まる」という期待は成り立たない。

EXIT トラップは性格が違う。成功でも失敗でも必ず実行されるので一時ファイルの整理に向く。

== 2. EXIT trap always runs; use it for cleanup ==
  workdir created: yes
  cleanup: removing workdir
  outer saw rc=5  (EXIT trap did not change it)

コード 5 で死んだのに整理が実行され、終了コードは 5 のまま維持された。ここでよくある誤解を実測で切り分けた。

== 3. an EXIT trap CAN silently rewrite the exit code ==
  cleanup running
  outer saw rc=9
  cleanup running
  outer saw rc=9
  ...now a cleanup with an explicit exit in the trap:
  cleanup running
  outer saw rc=0   <- the real failure was erased

重要な区別だ。トラップ内の最後のコマンドが失敗したり成功したりするだけでは終了コードは変わらない。前の二つの場合は 9 がそのまま維持された。トラップ内で exit を明示的に呼んだときだけコードが上書きされる。三つ目で本当の失敗 9 が 0 に消された。

⚠ 整理関数の中で exit を呼ばないこと
trap cleanup EXIT の cleanup の中に exit 0 があると全ての失敗が成功として報告される。実測ではコード 9 で死んだスクリプトが 0 で終わった。整理関数は整理だけをして静かに戻るべきだ。どうしてもコードを扱う必要があるなら、入り口で rc=$? で受けておき最後に exit "$rc" で返す。

11. サブシェルと関数の境界

set -e が境界を越えるときどうなるかを整理する。マニュアルは「シェル環境と各サブシェル環境に別々に適用される」と記す。実行で確認した。

== 1. set -e is inherited by subshells ==
  rc=1

== 2. ...but not if the subshell sits in a condition ==
  subshell CONTINUED past false
  subshell failure absorbed by ||
  script alive, rc=0

サブシェルは set -e を継承するが、そのサブシェルが条件の位置に置かれると内側まで丸ごと無防備になる。4節の G と同じ原理だ。

コマンド置換は6節で見たとおり既定では継承しない。inherit_errexit 無しで走らせた結果だ。

== 3. command substitution: -e does NOT apply inside by default ==
  out=[SHOULD-NOT-APPEAR]
  rc=0

== 5. the killer: substitution inside a declaration ==
  local out=[SHOULD-NOT-APPEAR] rc=0
  script survived
  rc=0

関数の戻り値は最後に実行されたコマンドのコードだ。return を書かなければそれがそのまま返る。

== 6. a function without an explicit return ==
  f -> 1       # f(){ true; false; }   最後が false
  g -> 0       # g(){ false; true; }   最後が true
  h -> 0       # h(){ echo "..."; }    echo が成功

g が危ない。中で失敗したが最後の行が成功したので 0 を返す。検証関数の末尾に echo や log の一行を習慣的に付けるとその関数は永遠に成功する。こういう関数は return を明示しなければならない。

== 7. exit inside a subshell only leaves the subshell ==
  after subshell, rc=4  (parent still running)
  parent rc=0

丸括弧の中の exit 4 はサブシェルだけを終わらせた。親は走り続け最終コードは 0 だ。「検証に失敗したら exit」をサブシェルやパイプラインの中に書くとスクリプトが止まらない。

パイプラインの各段階もサブシェルなので変数の代入が消える。

== 8. a pipeline runs its stages in subshells ==
  after while-in-pipeline: count=0  (child's copy was discarded)
  with process substitution: count=3

printf … | while read … で数えた値が0だ。子プロセスの変数なので親には戻らない。プロセス置換に変えれば 3 が出る。エラー件数を数えて最後に判定するスクリプトがこの罠によく引っかかる。常に「エラー 0 件」で終わる。

12. set -euo pipefail を付けても誤った値が通り抜ける

序論のスクリプトに戻る。ここまでの断片を合わせればなぜ通過したかを説明できる。スクリプトはこうだった。

#!/usr/bin/env bash
set -euo pipefail

read_key() {
  local value=$(grep -m1 "^$1=" "$2" | cut -d= -f2)
  echo "$value"
}

target=$(read_key target /tmp/demo/app.conf)
retain=$(read_key retain_days /tmp/demo/app.conf)

echo "  target      = [$target]"
echo "  retain_days = [$retain]"
echo "  would run: find /srv/backup/$target -mtime +$retain -delete"
echo "  DEPLOY OK"

設定ファイルには name と owner しかなく target・retain_days は無い。実行結果だ。

=== run 1: the 'safe' version ===
  target      = []
  retain_days = []
  would run: find /srv/backup/ -mtime + -delete
  DEPLOY OK
  script rc=0  <- CI sees GREEN

失敗が三重に消された。一つずつ挙げるとこうなる。

  • grep がキーを見つけられず 1 で終わったが、後ろに | cut があるのでパイプラインのコードは cut の 0 になる。pipefail が有効なのでここまでは 1 として生き残る
  • ところがそのパイプラインが local value=$(…) の中にある。local がコードを飲み込んで 0 にする(5節)
  • 関数は echo "$value" で終わる。echo は成功するので関数の戻り値も 0 だ(11節)
  • 結局 target=$(read_key …) は 0 を受け取る。set -e が介入する理由が無い。set -u も役に立たない。変数は「定義されていない」のではなく「空文字列として定義された」からだ

6節で学んだ inherit_errexit を追加したらどうか。同じスクリプトに shopt -s inherit_errexit の一行だけ入れて走らせた。

=== run 2: same script, inherit_errexit added ===
  target      = []
  retain_days = []
  would run: find /srv/backup/ -mtime + -delete
  DEPLOY OK

結果が全く同じだ。inherit_errexit はコマンド置換の内側で errexit を生かす選択肢だが、ここではlocal がそれより先にコードを飲み込むので介入する機会が無い。選択肢を増やす方式ではこの事故を防げないということだ。

解決策は選択肢ではなく検証だ。値を読んだ後に「読めたか」と「空でないか」を直接確認する。

read_key() {
  local value
  if ! value=$(grep -m1 "^$1=" "$2"); then
    printf 'config key missing: %s\n' "$1" >&2
    return 3
  fi
  value=${value#*=}
  if [ -z "$value" ]; then
    printf 'config key empty: %s\n' "$1" >&2
    return 3
  fi
  printf '%s\n' "$value"
}
=== run 3: validated version ===
config key missing: target
  run3 rc=3

コード 3 で正しく失敗し、どのキーが無いかがメッセージに残った。変わったのは四つだ。local の宣言と代入を分け、grep の失敗を if ! で直接受け、cut の代わりにパラメータ展開で切ってパイプラインを無くし、空の値を明示的に検査した。

⚠ この節の結論
set -euo pipefail は「コマンドが失敗した」を捕まえる仕掛けだ。「コマンドは成功したが値が誤っている」は捕まえられない。そして実務事故のかなりの部分が後者である。空文字列、想定と違う形式、0 件のリストは全て成功したコマンドの正常な出力だ。値の妥当性は人が直接検査するしかない。

13. 終了コードの設計 - 呼び出し側に何を伝えるか

ここまでが失敗を検知する問題だったなら、次は検知したものを伝える問題だ。状態が三つ以上なら 0 と 1 では足りない。広く使われる形は三分岐である。

コード意味呼び出し側がすること
0正常 — 問題なし通過
2差分あり — 検査は成功し結果が異なる内容を見て判断・承認
1エラー — 検査そのものを実行できなかった直ちに失敗 + 通知
64 以上使用法エラーなど細分化した状態呼び出し方を直す

三つの状態を出す検査器と、それを受ける側を作って走らせた。

  PASS  : no differences
    -> caller exits 0
  DRIFT : 3 files differ  (gate: fail the build, keep the log)
    -> caller exits 2
  ERROR : checker itself failed
    -> caller exits 1
  USAGE : bad invocation
    -> caller exits 64

受ける側の骨格はこうだ。set -e の下でそのまま呼ぶと 0 でない値が全てスクリプトを殺すので、コードを変数で受けてから case で分ける。

rc=0
out=$(./check.sh "$1") || rc=$?     # 死なずにコードだけ受ける
case "$rc" in
  0)  echo "  PASS  : $out" ;;
  2)  echo "  DRIFT : $out" ;;
  1)  echo "  ERROR : checker itself failed" ;;
  64) echo "  USAGE : bad invocation" ;;
  *)  echo "  UNKNOWN rc=$rc" ;;
esac
exit "$rc"

ここで || rc=$? が核心だ。4節の D で見たとおり || の左側は set -e の死角なのでスクリプトは死なず、コードは変数にそのまま残る。死角を問題ではなく道具として使う場面である。

逆に|| true は同じ場所で情報を破壊する。

== 3. the anti-pattern: '|| true' erases the state ==
  after || true, rc=0  <- error is gone

== 4. '|| true' vs capturing the code ==
  captured rc=1  <- still known, still recoverable

|| true は「このコマンドは失敗してもよい」という意味で付けるが、実際には「このコマンドがどう終わったのか永遠に分からない」という宣言だ。失敗してよいことと失敗を知る必要が無いことは違う。|| rc=$? で受けておけば両方を満たせる。

grep のように「無い」が 1 の道具はこう包む。

if grep -q "$pattern" "$file"; then
    echo "発見"
elif [ $? -eq 1 ]; then
    echo "未発見 — 正常"
else
    echo "grep 実行エラー" >&2; exit 1
fi

失敗地点を素早く見つけたいときは set -x が役に立つ。実行されるコマンドをそのまま出す。

== 5. set -x shows the failing command ==
  + grep -q token /nonexistent/file.txt
  grep: /nonexistent/file.txt: No such file or directory

展開が終わった最終形が見えるのが利点だ。変数が空だったのか、経路がどう組み立てられたのかが直ちに現れる。ただし出力が多いので問題の区間だけを set -x … set +x で包むほうがよい。

最後に、受け取ったコードをそのまま返すことを忘れないでほしい。整理トラップがあってもコードは維持される。

== 6. exit with the code you were given ==
  propagating rc=2
  cleaning up
  outer sees 2

計画と適用を分ける構造でこの規約をどう配線するかは--dry-run を正しく作る方法の終了コードの節でより詳しく扱った。

14. POSIX sh と分かれる箇所

スクリプトの一行目が #!/bin/sh なら、ここまでの半分は存在しない。同じコードを bash と dash にそれぞれ食わせて対照した。

機能bash 5.2.37dash実測メッセージ
set -o pipefail動作無しIllegal option -o pipefail
PIPESTATUS(3 4)無しBad substitution
配列n=3無しSyntax error: "(" unexpected
trap … ERR発火無しtrap: ERR: bad trap
trap … EXIT発火、rc=5発火、rc=5両方同一
プロセス置換hello無しSyntax error: redirection unexpected
local動作動作両方 v=1
local のコード飲み込みrc=0rc=0両方同じく飲み込む
set -e + 関数 + if通過通過両方 CONTINUED ALIVE
exit 300rc=44rc=44両方 8 ビット切断

読み方はこうだ。

  • pipefail が無い。POSIX sh で書くスクリプトでパイプラインの失敗を捕まえるにはパイプ自体を避けるしかない。一時ファイルに受けてコードを確認してから次の段階に渡す形になる
  • PIPESTATUS も配列も無い。段階ごとの状態を見る方法が事実上無い
  • ERR トラップが無い。EXIT トラップは両方で動作し終了コードも 5 で同じだった。整理のロジックは移植可能だが失敗のログ記録はそうではない
  • local は dash にもある。そして終了コードを飲み込む性質まで同じだ。5節の罠は #!/bin/sh でもそのまま成立する
  • set -e の死角は同一だ。関数を if に入れると両方とも通過した。これは bash の特異な動作ではなくシェル言語の規定である

要約すると安全装置は bash 専用で、罠は両方に共通だ。移植性が必要なら道具を失って罠だけが残る形になるので、#!/bin/sh を選ぶときはそれなりの理由が要る。

15. 死角表 - 状況から代替へ

この記事の結論だ。左の状況に出会ったら set -e は何もしない。右を代わりに使う必要がある。

状況set -e は捕まえるか代わりに何を使うか
素の失敗したコマンド捕まえるそのままでよい
if cmd; then の条件いいえ意図された動作。条件内でエラーと「偽」を区別するには $? を直接見る
while cmd; do の条件いいえループ本体で別途検査
cmd && … / cmd || … の左側いいえ|| rc=$? でコードを受けて case で分岐

パイプラインの最後以外のコマンドいいえset -o pipefail + PIPESTATUS の即時複製

local x=$(cmd)いいえlocal x と x=$(cmd) に二行で分離

16. テンプレート - 保証するものと保証しないもの

ここまでの内容を反映した出発点の雛形だ。このテンプレートが何を保証しないかを併記することがこの節の要点である。

#!/usr/bin/env bash
set -Eeuo pipefail
shopt -s inherit_errexit 2>/dev/null || true   # bash 4.4+ のみ

readonly WORKDIR=$(mktemp -d)
cleanup() {
    rm -rf "$WORKDIR"        # ここで exit を呼ばない(10節)
}
trap cleanup EXIT
trap 'echo "失敗: line $LINENO rc=$? cmd=[$BASH_COMMAND]" >&2' ERR

need() {                     # 必須の値を検証(12節)
    local name="$1" value="$2"
    if [ -z "$value" ]; then
        echo "必須の値が無い: $name" >&2
        return 3
    fi
}

run_stage() {
    local rc                 # 宣言と代入を分離(5節)
    local out
    out=$(some_command "$1") || rc=$?
    : "${rc:=0}"
    case "$rc" in
        0) printf '%s\n' "$out" ;;
        *) echo "段階の失敗: $1 (rc=$rc)" >&2; return "$rc" ;;
    esac
}

main() {
    local value
    value=$(run_stage fetch)
    need "value" "$value"    # 成功しても値を検証する
    echo "正常に完了"
}

main "$@"

このテンプレートが保証するものは次のとおり。

  • 素のまま失敗したコマンドで直ちに止まる(-e)
  • パイプライン途中の失敗が消えない(pipefail)
  • 打ち間違いで作られた未定義変数の参照で止まる(-u)
  • コマンド置換内側の失敗も捕まえる(inherit_errexit)
  • 関数内でも ERR トラップが発火し失敗地点がログに残る(-E)
  • どの経路で終わっても一時ディレクトリが整理される(EXIT トラップ)
  • 整理トラップが終了コードを上書きしない(トラップ内に exit 無し)

保証しないもののほうが重要だ。

  • 関数を if や || に入れるとその関数本体の全体が保護の外に出る。テンプレートの run_stage も例外ではない
  • コマンドは成功したのに値が誤っている場合は捕まえられない。だから need を別に置いた。検証は人が書くものであって選択肢がやってくれるものではない
  • 0 件・空のリスト・想定と違う形式は全て正常な成功だ。「結果があるはずだ」という条件は自分で書く必要がある
  • pipefail のせいで head で前方を断つパイプラインが 141 で失敗しうる(7節)。そういう箇所は個別に処理する
  • set -u は空文字列を防がない。定義された空の変数は未定義ではない
  • 外部コマンドが失敗したのに 0 を返せばシェルには知る術が無い。終了コードが不正確な道具は出力で検証しなければならない

最後に自己点検用のコマンドをいくつか。既存のスクリプトからこの記事の罠を探すときに使う。

### 宣言と代入がくっついている箇所
$ grep -rnE '(local|declare|typeset|export|readonly)[[:space:]]+[A-Za-z_]+=\$\(' .

### パイプにつないで失敗が消えうる箇所
$ grep -rn '| *tee' .

### 整理トラップ内の exit
$ grep -rnE 'trap .*(exit|EXIT)' .

### 安全選択肢が全く無いスクリプト
$ grep -rLE 'set -[a-zA-Z]*e' --include='*.sh' .

結論: 検知されなかった失敗は失敗ではなく偽の成功だ

規則に圧縮すると四つの文になる。

  • set -e は「素のまま失敗したコマンド」だけを捕まえる。条件・否定・論理演算・パイプライン途中は全て例外であり、これはバグではなくマニュアルが自ら列挙した規定だ
  • 関数を条件の位置に入れると本体全体が保護を失う。実測では関数内の失敗したコマンドの次の行がそのまま実行された。死角の中で最も広い
  • local・declare・export は終了コードを飲み込む。五つの宣言ビルトイン全てが 0 を返した。宣言と代入を二行に分けるだけで解決する
  • 最も危険なのはコマンドが成功したのに値が誤っている場合だ。どの set 選択肢でも捕まえられず、検証は手で書くしかない

実行で確認したことを改めて整理するとこうだ。死角九つを一つのスクリプトに詰め込み set -e を有効にしたまま走らせたら一つも引っかからず最後まで到達した。local を前に付けるとコード 7 が 0 になり、五つの宣言ビルトイン全てが同じだった。false | tee は pipefail 無しで成功として報告された。PIPESTATUS は次の echo 一つで消えた。整理トラップ内の exit 0 が本当の失敗 9 を 0 で上書きした。そして set -euo pipefail に inherit_errexit まで有効にしたスクリプトが空の値二つを通してコード 0 で終わった。

最後の事例がこの記事の要点だ。安全選択肢は「コマンドが失敗した」を捕まえる仕掛けであって「結果が正しい」を保証する仕掛けではない。この二つを同じものと見なした瞬間、選択肢を有効にしたという事実そのものが検証を飛ばす言い訳になる。実際、序論のスクリプトを書いた人は set -euo pipefail を付けたからこそ値の検証を省いた可能性が高い。

だから順序を逆にしよう。まず何が誤りうるかを書き出し、それを検査するコードを書き、その後で安全選択肢を付ける。set -euo pipefail は床であって天井ではない。15節の表で右の列が空でない行が一つでも自分のスクリプトにあるなら、その行こそが次の事故が起きる場所だ。

# シェルの終了コードと set -e - 実務参照表

検証環境: GNU bash 5.2.37(1)-release, dash, GNU coreutils 8.32。
以下の値は全て実際に実行して確認したものである。

---

## 1. 終了コード表

| コード | 意味 | 出典 | 実測での確認 |
|---|---|---|---|
| 0 | 成功 | POSIX | `true` |
| 1 | 一般的な失敗(慣例) | 慣例 | `false` |
| 2 | 使用法エラーまたは「差分あり」 | 慣例 | `grep` のエラー |
| 126 | 見つかったが実行できない | POSIX 2.8.2 | ディレクトリの実行 |
| 127 | コマンドが見つからない | POSIX 2.8.2 | 存在しないコマンド |
| 137 | 128+9、SIGKILL で終了 | 実装慣例 | `kill -9` |
| 143 | 128+15、SIGTERM で終了 | 実装慣例 | `kill -TERM` |
| 141 | 128+13、SIGPIPE | 実装慣例 | `yes | head -1` |
| 256 以上 | 8 ビットで切られる(256 は 0 になる) | 実測 | `exit 256` |

道具ごとの慣例もある。`grep` は 0=発見、1=未発見、2=エラーだ。
「見つからない」は正常な結果だが `set -e` は失敗と見なす。

---

## 2. set -e の死角チェックリスト

以下は全て `set -e` が有効な状態で**通過する**。実行で確認した。

- [ ] `if cmd; then` の条件 → 通過
- [ ] `while cmd; do` の条件 → 通過
- [ ] `cmd && ...` の左側 → 通過
- [ ] `cmd || ...` の左側 → 通過
- [ ] `! cmd`(否定)→ 通過
- [ ] パイプラインの最後以外のコマンド → 通過(`false | cat` は rc=0)
- [ ] **関数を `if` や `||` に入れると関数本体の全体が無防備** ← 最も広い死角
- [ ] `local x=(コマンド置換)` → `local` のコードが勝って rc=0
- [ ] `declare` / `typeset` / `export` / `readonly` の代入 → 全て rc=0
- [ ] コマンド置換 `( )` の内側 → 既定では errexit を継承しない
- [ ] 条件の位置に置かれたサブシェル → 内側まで無防備
- [ ] 関数の最後の行が `echo` → 常に 0 を返す
- [ ] サブシェル内の `exit` → サブシェルだけが終わる
- [ ] 整理トラップ内の `exit 0` → 全ての失敗を 0 で上書き
- [ ] **コマンドは成功したが値が空文字列** ← どの選択肢でも捕まえられない

`(( c++ ))` は逆方向の罠だ。演算結果が 0 なら終了コード 1 になるので、
カウンタが 0 から始まると最初の増加でスクリプトが死ぬ。`(( ++c ))` を使う。

---

## 3. 三つの選択肢がそれぞれ何をするか

| 選択肢 | 捕まえるもの | 捕まえられないもの |
|---|---|---|
| `set -e` | 素のまま失敗したコマンド | 上のチェックリスト全て |
| `set -u` | 未定義変数の参照 | 空文字列、失敗したコマンド |
| `set -o pipefail` | パイプライン途中の失敗 | SIGPIPE の早期終了を失敗と誤認 |
| `shopt -s inherit_errexit` | コマンド置換内側の失敗 | `local` が先に飲み込むと無効 |
| `set -E` | 関数内で ERR トラップを発火 | `set -e` と同じ死角 |

`set -u` の実測(bash 5.2.37):
- 引数が無いときの引数リスト全体の展開と、空配列の全体展開は安全
- 位置パラメータの一つ目や `arr[0]` のように個別要素を掴むと弾ける
- 回避は `${var:-既定値}`。コロンがあれば「無いか空なら」、無ければ「無ければ」
- 終了コードに移植性は無い: bash スクリプト 1、bash -c 127、dash 2

---

## 4. PIPESTATUS は直ちに保存する

パイプラインの直後に一度しか読めない。次のコマンド一つで上書きされる。

```
curl -fsS "url" | gzip -d | psql "dsn"
st=("${PIPESTATUS[@]}")          # 必ず直後の行で
[ "${st[0]}" -ne 0 ] && echo "ダウンロード失敗"
[ "${st[1]}" -ne 0 ] && echo "展開失敗"
[ "${st[2]}" -ne 0 ] && echo "投入失敗"
```

---

## 5. 安全なテンプレート

```
#!/usr/bin/env bash
set -Eeuo pipefail
shopt -s inherit_errexit 2>/dev/null || true

readonly WORKDIR=(mktemp の結果を代入)
cleanup() {
    rm -rf "WORKDIR"          # ここで exit を呼ばない
}
trap cleanup EXIT
trap 'echo "失敗: line LINENO cmd=[BASH_COMMAND]" >&2' ERR

need() {                      # 成功しても値を検証する
    local name="1" value="2"
    if [ -z "value" ]; then
        echo "必須の値が無い: name" >&2
        return 3
    fi
}

run_stage() {
    local rc                  # 宣言と代入を分離
    local out
    out=(コマンドの実行結果を代入) || rc=?
    case "rc" in
        0) printf '%s\n' "out" ;;
        *) echo "段階の失敗 (rc)" >&2; return "rc" ;;
    esac
}
```

**保証するもの**: 素の失敗で停止、パイプラインの失敗を維持、未定義変数の遮断、
コマンド置換内側の失敗検知、関数内の ERR トラップ、一時ディレクトリの整理、終了コードの保存。

**保証しないもの**: 関数を条件に入れると本体全体が保護の外に出る。
値が空だったり形式が違う場合は捕まえられない。0 件の結果は正常な成功だ。
`set -u` は空文字列を防がない。終了コードが不正確な外部の道具は出力で検証する必要がある。

---

## 6. 終了コードの設計規約

| コード | 意味 | 呼び出し側がすること |
|---|---|---|
| 0 | 正常 | 通過 |
| 2 | 差分あり(検査は成功) | 内容を確認して判断 |
| 1 | エラー(検査そのものが失敗) | 直ちに失敗 + 通知 |
| 64+ | 使用法エラーなど | 呼び出し方を修正 |

受ける側はこう書く。`|| rc=?` で受ければ `set -e` が殺さない。

```
rc=0
out=(検査コマンドを実行) || rc=?
case "rc" in
  0)  echo "PASS" ;;
  2)  echo "DRIFT" ;;
  1)  echo "ERROR" ;;
  *)  echo "UNKNOWN" ;;
esac
exit "rc"
```

`|| true` は使わない。「失敗してもよい」ではなく
「どう終わったのか永遠に分からない」という宣言になる。

## 7. POSIX sh との違い

| 機能 | bash 5.2.37 | dash |
|---|---|---|
| `set -o pipefail` | 動作 | **無し** |
| `PIPESTATUS` | 動作 | **無し** |
| 配列 | 動作 | **無し** |
| `trap ... ERR` | 動作 | **無し** |
| `trap ... EXIT` | 動作 | 動作 |
| プロセス置換 | 動作 | **無し** |
| `local` | 動作 | 動作 |
| `local` のコード飲み込み | rc=0 | **rc=0(同一)** |
| `set -e` + 関数 + `if` | 通過 | 通過(同一) |

要約: **安全装置は bash 専用、罠は両方に共通。**

## 8. 自己点検コマンド

```
### 宣言と代入がくっついている箇所
grep -rnE '(local|declare|typeset|export|readonly)[[:space:]]+[A-Za-z_]+=' .

### パイプにつないで失敗が消えうる箇所
grep -rn '| *tee' .

### 整理トラップ内の exit
grep -rnE 'trap .*(exit|EXIT)' .

### 安全選択肢が全く無いスクリプト
grep -rLE 'set -[a-zA-Z]*e' --include='*.sh' .
```
