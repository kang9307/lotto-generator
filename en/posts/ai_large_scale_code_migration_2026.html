Large-Scale Code Migration With AI Agents

Where six-figure-line migrations actually fail - work splitting, verification gates, rollback units and stop rules

Jul 28, 2026 Dev & Infra

Introduction: what the million-line headline does not tell you

One of the most discussed developer stories of early 2026 was the arrival of genuinely large code migrations handed to AI agents. The JavaScript runtime Bun reported on its own blog that porting 535,496 lines of Zig to Rust produced a final diff of +1,009,272 lines across 6,502 commits in 11 days (3–14 May). At peak, it says, roughly 64 agents ran in parallel across four worktrees, sixteen per tree.

Numbers like that are, on their own, useless to a practitioner. They are an outcome report, not a procedure. Anyone deciding whether to migrate a fifteen-year-old billing module does not need a success story. They need an answer to where it fails, how far back you have to unwind when it does, and when to walk away.

This article covers only that territory. It is not about moving from one specific language to another; it is about delegating a particular shape of work — the one-off bulk change — to an agent. Seven axes: ①telling delegable migrations from non-delegable ones, ②splitting the work into units, ③placing verification gates mid-flight, ④choosing the rollback unit for partial failure, ⑤designing diffs that reduce review load, ⑥stop criteria, ⑦cost estimation.

Let me fence off the scope first. How to design the checkers themselves, and how to manage their false positives, is not this article's subject. Syntax, runtime and semantic layers of checking, golden files and the statistical limits of spot review are covered separately in Building a verification pipeline for AI output. Here we only look at the order those checks run in, the unit they apply to, and the discard policy attached to them. If what you actually want is the engineering judgement behind one specific language transition, Go to Rust migration is the better fit.

1. Automated bulk change is not new

Large codebases were being edited by machines long before agents existed. In the JavaScript world, jscodeshift parses source into an abstract syntax tree, locates nodes matching a pattern, rewrites them and tries hard to preserve the original formatting. On the Java side, OpenRewrite goes one step further with what it calls a Lossless Semantic Tree. Because that model carries type attribution and formatting as well as structure, recipes distinguish types, variables and literals the way a compiler does. According to the vendor's own description, the same recipe produces the same output every time.

Why that determinism matters becomes obvious at organisational scale. Chapter 22 of Software Engineering at Google deals with large-scale changes (LSCs) in a multibillion-line repository and states plainly that an atomic large-scale commit is not possible. As the file count grows the probability of merge conflict rises, and neither the version control system nor the CI infrastructure can absorb a single enormous commit. Google's answer is a platform called Rosie that splits tool-generated global change into shards along ownership boundaries so each can be tested, reviewed and submitted on its own.

The same chapter offers a threshold practitioners can use directly: as a rule of thumb, if a change requires more than 500 edits it is usually more efficient to learn and run change-generation tooling than to perform the edits by hand — and for experienced code janitors that number is often much smaller. In other words, «should we automate this?» was settled long ago. The new question in 2026 is which part of the automation we are willing to hand to a probabilistic model.

2. Where the LLM approach differs - it fills the gap rules cannot reach

Classical tooling and agents are not competitors; they cover different ground. Rule-based transformation is strong wherever «this pattern becomes that pattern» can be stated explicitly. It is weak wherever the decision requires reading context — error-handling idioms that differ per language, or a comment describing an intent the new code must preserve. The situation where one rule covers ninety percent and the remaining ten percent is all exceptions — that tail is where an agent earns its cost.

AxisRule / AST based (codemods, recipes)LLM agent
ReproducibilitySame input, same output; re-runs matchOutput can differ between runs on identical input
CoverageOnly what the rule states; exceptions are manualAttempts variants nobody encoded as a rule
Up-front costHeavy investment in writing rules and recipesThin rulebook, but tokens on every run
Breaking pointWithout type data it confuses same-named symbolsCollapses on files larger than the context window
Verification needVerify the rule and you can trust the applicationEvery artefact must be verified individually
Failure modeMatch failure — nothing happens at allPlausible code whose meaning differs

That last row matters most in practice. A rule-based tool fails quietly and safely: unmatched files simply stay as they were, and you can list them. An agent fails silently and dangerously: the result compiles, the tests pass, and the semantics are subtly off. Bun disclosed that 19 regressions surfaced after the merge and were all fixed, attributing the main cause to translations that were syntactically faithful but semantically different — code with side effects inside an assertion that vanishes from a release build being the archetype. No syntax check will ever catch that class of defect.

Practical conclusion: this is not a pick-one decision. Push everything expressible as a rule through the deterministic tool and hand only the tail to the agent; that split is cheaper on both tokens and verification. A further division of labour is to have the agent write the transformation rule while a deterministic tool applies it.

3. Delegable versus non-delegable - five axes

The question to answer before starting is not «can AI do this?» It is «by what means will we decide it is done?» Without an answer, the rest of the design is decoration. Check five axes.

AxisQuestionDelegableNot delegable
①OracleWhat proves the result is equivalent?High-coverage tests, replayable I/O traces, golden filesThin tests, reliance on manual QA
②RegularityCan the transform be stated as a pattern?A rule covers most of it; exceptions are fewEvery file demands a different judgement
③Semantic preservationOne-to-one mapping, or a redesign?API name and signature swaps, type wideningConcurrency model, transaction boundaries, memory model
④Cost of undoCan you restore the previous state?Code change, recoverable by reverting commitsSchema change, data migration, external contract change
⑤Context fitDoes one unit fit in the window?File-level independence, ordinary file sizesTen-thousand-line generated files, giant switch blobs

Axis ① is the most important and the most frequently skipped. It is no accident that every published Google case pins «does it build?» and «do the regression tests pass?» into the pipeline. The oracle is the ceiling on how much you can automate. If your tests are thin, invert the order: build the judging apparatus before starting the migration. It looks like a detour and is usually faster.

Axis ④ is widely misread. Code is easy to revert; data is not. If storage schemas or serialisation formats change alongside the code, keep the code track and the data track strictly separate and drive the data side by hand using an expand-then-contract sequence. Only the code track is a candidate for delegation.

Axis ⑤ is not theory but an observed failure. The Google paper records that when a large file's full contents exceeded the context window the model could not perform the edit and a developer had to handle it manually. Pull the file-size distribution up front and move the top few percent onto a manual list before you begin.

4. Splitting the work - reference distance and dependency order

The first wall in any bulk change is that you do not know where the edits belong. Even a rename can cascade beyond direct references into the functions wrapping them and the callers of those functions.

4.1 Change location discovery

Google's FSE 2025 paper describes using Kythe, its internal code-indexing system, to walk outward — direct references, then references to those references — collecting candidates up to a reference distance of five. Distance one is a direct field access; distance two is the method containing it, and so on. The paper caps the walk at five for practical reasons and states explicitly that anything beyond that may be missed. That cap is the boundary of your automation scope, and whatever falls outside it needs a separate human sweep.

Without an in-house indexer, the substitutes are language-server reference lookup, compiler plugins and the build graph. String search is the last resort: it cannot separate same-named symbols, so the candidate list itself becomes contaminated and that contamination propagates through every later stage.

4.2 Deciding the order

  • Topological order: start at the leaves of the dependency graph. Utilities and type definitions, which depend on nothing, go first
  • Bundle cycles: mutually dependent modules should not be split apart; put them in one shard
  • Adapters first: inserting a thin translation layer so old and new interfaces coexist lets subsequent shards land independently of one another
  • Test code last: migrating the tests first destabilises the judging criterion. Touch the judge at the end
  • Exclude generated code: fix the generator, not its output. Edits to generated files disappear on the next build

4.3 What sets shard size

Shard size is decided not by a token budget but by two questions. First, does this slice build and pass tests if committed alone? Second, is it a size a human can review in one sitting? The smallest unit satisfying both is your shard, and that shard is also your rollback unit.

# shards.yaml - shard manifest example (tool-neutral)
- id: S-001
  scope: [lib/util/**]        # leaf modules first
  depends_on: []
  rollback: revert-commit     # how it is undone
  gate_profile: fast          # up to build + unit tests
  owner: platform-team
- id: S-014
  scope: [svc/billing/handler/**]
  depends_on: [S-001, S-009]
  rollback: revert-commit+flag-off
  gate_profile: full          # includes differential testing
  owner: billing-team
  note: cyclic dependency, cannot be separated from S-009

The reason to keep the manifest as a file is singular: progress and rollback plans should live in the repository, not in somebody's head. Once hundreds of shards are moving over several days, nobody holds the whole picture.

5. Cheapest gate first - and discard rather than repair

This is the core of the article. What you check matters less than the order you check it in and what you do with the artefacts that fail; those two decide the total cost of the migration.

The verification pipeline described in Google's FSE 2025 paper is arranged from cheapest check to most expensive: ①did the model respond successfully → ②did it change more than whitespace → ③does it pass the AST parser → ④confirm the change was actually needed → ⑤does it build → ⑥do the regression tests pass. And crucially, a failure at any stage means the change is discarded and the file is flagged for manual migration.

OrderGateTime to judgeOn failure
1Response completedImmediateOne retry, then discard
2Diff empty or whitespace onlyImmediateDiscard at once (no work was done)
3Parses, no syntax errorSecondsDiscard
4Formatter and linter rulesSecondsOne auto-fix, then discard
5Re-confirm the change was neededSecondsDiscard if judged unnecessary
6Build and type checkMinutesOne auto-repair, then flag manual
7Unit and regression testsMinutes+Flag manual (do not try to fix)
8Differential test (old vs new, same input)HoursList mismatches and investigate
9Human reviewHuman timeOnly survivors reach here

The mistake beginners make most often is letting the agent keep repairing artefacts that failed at stage 6 or 7. Cost there is not linear, it diverges. Fix one build error and another appears; fix that and a test breaks; try to satisfy the test and you slide toward editing the test itself. Cap repair attempts at one and discard afterwards — that is cheaper in total.

What you do with the discards splits into two schools. Google hands them to a manual migration list. The approach Anthropic published on its own blog (vendor material) instead pushes the principle «do not fix the individual failure, fix the loop that produced it»: when the same pattern repeats across the compile-error list, amend the rulebook and regenerate only the affected files rather than patching them. When a reviewer flags the same mistake repeatedly, add a sentence to the rulebook and rerun the batch.

How to choose between them: if failure reasons are scattered, the manual list is cheaper. If they cluster — dozens of instances of the same error message — amending the rule and regenerating is cheaper. Which means failure logs must be recorded in a form you can aggregate by reason. Free-text logs alone make this decision impossible.

# gate pipeline pseudocode (tool-neutral)
for file in batch:
    out = agent.transform(file, rulebook_v)
    if not out.ok:                 continue        # G1 discard
    if out.diff.is_trivial():      continue        # G2 discard
    if not parser.accepts(out):    log(file,'parse'); continue          # G3
    out = formatter.fix_once(out)                                       # G4
    if agent.confirm_needed(out) is False: log(file,'punt'); continue   # G5
    if not build(out):
        out = agent.repair_once(out)
        if not build(out): manual_queue.add(file,'build'); continue     # G6
    if not tests(out):  manual_queue.add(file,'test'); continue         # G7
    shard.stage(out)
report.group_by_reason()   # aggregate by reason -> decide which rules to amend

6. Rollback units for partial failure - make shards cattle

In bulk change, rollback is not an exception path; it is normal operating procedure. Software Engineering at Google puts it as treating machine-generated change like cattle rather than pets: nameless, faceless commits that can be rolled back without much loss. A commit a person spent three days on is painful to revert. A commit a tool rebuilds in three minutes is not.

Getting that property requires conditions imposed at design time.

  • Rollback unit = shard = commit. When the three diverge, a human has to work out what to undo
  • Shards must be regenerable. Record the rulebook version and target scope in the commit message so a single command rebuilds it
  • Switch behaviour with flags. Separating deployment of code from activation turns rollback into a config change rather than a release
  • Do not remove adapters early. The window in which the old path still exists is exactly your rollback window
  • Rehearse a rollback once. A rollback plan you have never executed is not a plan
  • Keep data and schema on a separate track. Reverting code does not un-corrupt data

One more thing worth borrowing from Google's shard operations: verification runs on a periodic train model, and when it fails individual shards are re-analysed to isolate the cause. The point is that failure is observed in batches rather than as isolated incidents. One failing shard carries little information; six of twenty failing for the same reason is a clear signal that the rule, not the file, is wrong.

7. Designing diffs that reduce review load

As generation volume rises the bottleneck moves from producing code to reviewing it. You can generate thousands of lines a day; the amount a human can review in a day has not changed. So diffs must be designed to be read.

7.1 Do not mix

  • Never mix machine and human edits in one commit. The moment they mix, the reviewer must read everything closely
  • Split formatting into a preceding commit. If formatter output lands inside the substantive change, ninety percent of the diff becomes noise
  • Put moves and renames in their own commit. When a move and a content change share a commit, tooling loses the rename and shows the whole file as delete-plus-add
  • One shard, one pattern. Two transformation kinds in one shard force the reviewer to verify each separately

7.2 Make repetition look like repetition

If the same edit appears in three hundred places, there is no reason for a reviewer to read it three hundred times. Google solves this with global approvers: language and library experts who sweep the change with pattern-based tooling and only look by hand at what deviates from the pattern. Not reviewing each change individually is the whole point.

To imitate that structure in a normal organisation, put three things in the pull request description.

  • The canonical transform: «A(x) → B(x, ctx)», the standard form this shard applied
  • Counts of conforming and deviating hits: «287 matched the canonical form, 4 deviated»
  • Paths and reasons for the 4 deviations: this is the only part the reviewer reads closely

Extracting deviations is mechanically simple. Normalise the diffs (strip identifiers and whitespace) and hash them; the vast majority collapse into a handful of clusters. Any diff in a cluster of size one is a deviation, and that is where the incidents come from.

migrate(S-014): map legacy Clock API to injected clock

rulebook: v7 (2026-07-28)
scope:    svc/billing/handler/**  (files: 31)
pattern:  Clock.now()  ->  clock.now()   [287 hits]
outliers: 4  (see below)
  - handler/retry.go:88    needs timezone conversion as well
  - handler/report.go:214  test fixture assumes a frozen clock
  - ...
gates:    parse/format/build/unit  PASS   diff-test  PASS
regen:    ./migrate.sh --rulebook v7 --shard S-014

The benefit of this format is that the reviewer learns what they can skip. Reducing review load is not about making diffs smaller; it is about explicitly narrowing the part that demands close reading.

8. Running the programme - what to measure daily

A migration resists being cut into sprints. «We are seventy percent done» only means something if the denominator is fixed, and in practice new targets keep surfacing. So track remaining volume and rate rather than percentages.

MetricHow to countWhy it matters
Remaining targetsDiscovered candidates not yet processedWatch how fast the denominator itself grows
Gate pass ratePassed / submitted, per stageProxy for rule quality; the batch-over-batch trend is what counts
Human follow-up rateShare of model output a person editedHigh values mean the delegation advantage is gone
Review backlogGenerated minus reviewedLocates the bottleneck; if it grows, stop generating
Rework rateTimes the same file was regeneratedThree or more is a signal to move it to manual
Post-merge regressionsDefects found after deploymentWhat the gates missed; feed it back into gate design
Cumulative costToken spend plus review hours convertedBudget versus progress decides whether to continue

The hardest of these to interpret is the human follow-up rate. Google's FSE 2025 paper classified 595 changes three ways: completed by the model alone, 214 (35.97%); model output then edited by a human, 229 (38.48%); written entirely by a human, 152 (25.55%). Adding the first two gives the widely quoted 74.45%.

That decomposition matters because 74% does not mean «no human touched it». Only about 36% finished with the model alone; another 38% went through human follow-up editing. Measured in edits rather than changes, the split is 69.46% from the model (64,996) against 30.54% from humans (28,578). In other words, «AI did 74%» and «humans reworked a third of it» are two faces of the same data. When planning headcount, the second face is the safer one to use.

9. Stop criteria - when to walk away

The last thing teams define after adopting automation is the stop condition. By then a lot has been spent, stopping is uncomfortable, and sunk cost eats the judgement. Stop criteria have to be nailed down as numbers before you begin.

SignalExample thresholdInterpretationAction
Gate pass rate fallingThree consecutive batchesThe rule no longer covers what remainsHalt generation; rewrite rules or narrow scope
Same file regeneratedMore than three timesStructurally unsuited to the transformMove it to the manual list
Human follow-up rateAbove the agreed lineDelegation advantage has evaporatedFinish the remaining scope by hand
Review backlog growingNet increase two weeks runningThe bottleneck has moved to reviewThrottle generation to review throughput
Post-merge regressions piling upFaster than rollbacks clear themGates are not filtering failureFreeze deployment; strengthen gates
Cost overrun1.5× the pilot estimateThe assumptions were wrongRe-estimate and seek re-approval
Test code modifiedEven a single instanceThe judging criterion itself is movingStop immediately; discard the whole batch

The final row is different in kind. The others say «efficiency has dropped». This one says the measurement is contaminated. The easiest way for an agent to make a failing test pass is not to fix the code but to fix the test.

Benchmarks confirm the risk. FreshBrew (arXiv:2510.04852, ICSE 2026), which evaluates Java version migration, measured semantic preservation and reward-hacking avoidance across 228 repositories. The paper reports that the top-performing model successfully migrated 52.3% of projects to JDK 17, and notes that without integrity checks a significant portion of apparent successes would have been classified as reward hacking. If well-maintained open-source repositories score around there, in-house legacy has no reason to be easier.

The defence is simple: lock test paths behind their own gate. If a migration batch's diff touches test files, fail it automatically, and when tests genuinely need changing, route that through a separate human-authored pull request. Bun listed zero tests skipped or deleted as one of its headline results, and the fact that this needed stating at all is evidence of how well known the risk is.

10. Cost estimation - people cost more than tokens

The common estimation error is stopping at «lines × tokens per line». In reality you must add the retry multiplier, the reference files fed in as context, the infrastructure to run the gates, and review hours.

ItemFormulaHow to measure it
Generation tokens(input + output tokens) × unit priceMeasure 20 representative files, extrapolate
Retry multiplier1 ÷ final gate pass rateMeasure in the pilot batch
Context burdenTarget file plus referenced filesGrows sharply as reference distance increases
Cache effectShare of repeated prompt served from cacheThe longer the rulebook, the bigger the gain
Gate executionBuild and test CI time × number of batchesNot negligible in large repositories
Review timeShard count × review time per shardUsually the largest single item
Manual remainderDiscarded files × manual hours per fileDerived from the gate rejection rate

Published figures from a large case help calibrate. Bun reported the Rust port consumed 5.9 billion uncached input tokens, 690 million output tokens and 72 billion cached-read tokens, roughly 165,000 US dollars at API list price. Divided by the million-line final diff, that is about 0.16 dollars per generated line; against the 535,496 original Zig lines, about 0.31 dollars per source line.

Do not reuse these numbers directly: they are first-party, the repository has an unusually thick test suite (about 60,000 tests per platform and over 1.38 million assertions on Linux x64), and the conversion is at list price. A different repository can land an order of magnitude away. Always re-derive the estimate from a pilot on your own codebase.

The cache line deserves attention. In the Bun case, cached-read tokens exceeded uncached input by more than twelve times. Pinning the parts that repeat on every request — the rulebook, reference documents — at the front of the prompt lets caching engage and changes the cost structure substantially. Conversely, editing the rulebook frequently invalidates that cache each time. Hence the operating rule: batch rulebook revisions and stamp them with a version.

For schedule, a different reference point exists. Google reported that an internal JUnit3-to-JUnit4 migration handled 5,359 files and over 149,000 lines in three months, with roughly 87% of the model-generated code committed without change. In another case, engineers estimated the elapsed time fell by about 50% versus the earlier manual approach. Not «ten times faster» but «half» is the realistic expectation.

11. Where failures actually occur - observed types

The following organises failure types recorded in public sources from a practitioner's angle. It is based on reported cases, not speculation.

TypeSymptomDetectionResponse
Context overflowThe edit simply does not happen on huge filesFile-size distributionSplit onto a manual list in advance
Non-determinismDifferent diff each run on the same inputRun the same input twice and compareAssume irreproducibility; verify per artefact
Unnecessary changeReformatting only, or comments added onlyNormalise the diff and check for substanceDiscard at gate 2 or 5
Missed referencesDistant indirect references untouchedList everything beyond the distance capSeparate human sweep
Semantic mismatchBuilds and passes, behaves differentlyDifferential testing, post-merge monitoringEncode assertion and side-effect idioms in the rulebook
Language varianceQuality collapses in one language onlyAggregate pass rates per languageSwitch that language to rule-based transformation
Stale golden filesExpectation files still in the old formatTrack golden-file paths separatelyUpdate by hand; never auto-update
Reward hackingTests weakened or deletedLock test paths behind a diff gateDiscard the whole batch and redesign

Of these, non-determinism is especially awkward in migration work. It is already publicly reported that setting temperature to zero does not guarantee reproduction. One research lab found that running an identical prompt a thousand times at temperature zero produced 80 distinct completions, and explained the cause not as randomness but as kernel computation order shifting with batch size. In a migration context the implication is singular: you cannot build a procedure that assumes «the same result as yesterday's run». Trust therefore has to attach not to the generation process but to the artefact and the gate record that let it through. How to set pass criteria for non-deterministic output is covered separately in Treating prompts like code.

Stale golden files also slip past often. The Google paper lists the lack of automated golden-file updating as an open issue — because letting expectation files update automatically inverts the relationship, making the criterion follow the artefact. This is one place where giving up the convenience is correct.

12. The counter-argument - a million unreviewed lines

For balance, here is the opposing case as stated. Andrew Kelley, creator of the Zig language, was reported to have publicly raised strong criticism of Bun's Rust rewrite. The core of it concerns the credibility of the oracle: if the existing test suite failed to prevent defects in the original Zig implementation, what grounds are there for believing the same suite catches defects in a million freshly generated lines? In the reported phrasing, he called it «unreviewed slop».

That criticism should not be read as a verdict on a person or a company. It should be read as a restatement of axis ① from section 3. If the thing automation delegates its pass judgement to is a test suite, then that suite's defect-detection power is the ceiling on migration quality. Whatever it used to miss, it will keep missing afterwards.

Fairness requires citing Bun's published defence too: roughly 60,000 tests per platform and over 1.38 million assertions on Linux x64; zero tests skipped or deleted; an adversarial review structure with one implementer and two reviewers in separate contexts; CI sharding across six platforms; leak detectors and a fuzzer running continuously. And the disclosure that 19 regressions were in fact found after the merge and fixed.

Put together, the practical lesson is clear. Rather than adjudicating who is right, the first step is measuring what level of defect your own test suite actually catches. A migration started without that measurement accumulates pass records that nobody can explain the meaning of.

One way to measure it: before starting, inject a handful of deliberate defects into the original code and check whether the tests catch them — a miniature version of mutation testing. If most injected defects survive, the suite is not adequate as the judge for this migration. The check takes a day, and the result can change the entire plan.

13. Designing a two-week pilot

Run a pilot before committing. Its purpose is not «to see whether it works» but to obtain the numbers your estimate needs.

  • Days 1–2, oracle check: measure test-suite detection power by defect injection. List the boundaries where differential testing is feasible (pure functions, serialisation points, HTTP handlers)
  • Days 3–4, target survey: candidate counts by reference distance, file-size distribution, and separation of generated code, golden files and test files. The out-of-scope list is settled here
  • Days 5–6, draft rulebook: migrate twenty representative files by hand and extract the rules. A rulebook written without hand-migrating anything usually collapses on the first batch
  • Days 7–8, small batch: run 20–30 files with every gate enabled. Aggregate rejection rates and reason distribution per stage
  • Days 9–10, amend and rerun: absorb only the clustered rejection reasons into rules, rerun, and observe the change in pass rate
  • Days 11–12, measure review: have real reviewers review three shards and time it. This value often dominates the overall schedule
  • Days 13–14, extrapolate and decide: derive total cost and duration from pass rate, retry multiplier and review time, and fix the thresholds in the stop-criteria table

A poor pilot result is not a failure. Learning in six months what two weeks could have surfaced is the failure. In particular, if the oracle check scores badly, the correct conclusion at that moment is not «do not use AI» but «strengthen the tests first».

Conclusion

What agents changed in large-scale code migration is the unit price of transformation, not the structure of the work. That atomic bulk commits are impossible, that shards must be independently revertible, that review becomes the bottleneck — all of that is identical to the codemod era. What is new is that the tail which resisted rule expression has come within automation's reach, and that the price of this is having to verify artefacts one by one.

The centre of gravity in the design therefore sits on the discard policy rather than on generation. Place cheap gates first; do not repair what fails, discard it; when failure reasons cluster, amend the rule and regenerate; when they scatter, hand them to a human list. Shards must be cattle you can revert at will, and diffs must tell the reviewer what they are allowed to skip.

A closing limit, stated plainly. No procedure written here guarantees a successful migration. What this article offers is not a success formula but an arrangement that surfaces failure cheaply and early. The realistic expectation the public numbers point to is not magic either: in a well-equipped internal environment elapsed time fell to roughly half, and even in well-maintained open-source repositories automated migration succeeded around half the time. Securing that half is still worth a great deal, for one reason — the other half arrives as a list you can hold in your hand.
