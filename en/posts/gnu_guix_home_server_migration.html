Why I Migrated a Decade-Old Arch Linux Home Server to GNU Guix - Declarative Infrastructure 2026

Eliminating scattered configuration entropy with unified Guile Scheme and Git-tracked literate infrastructure

2026-09-14 Dev & Infra

Engineers who have maintained long-running Linux home servers or personal infrastructure over several years eventually encounter a universal maintenance dilemma. When a server is initially deployed, every configuration line, directory mapping, and package installation is crisp and well-understood. However, as years of incremental tweaks, experimental services, and emergency hotfixes accumulate, the underlying operating system gradually degrades into an inscrutable black box. Files scattered across arbitrary directories, orphaned dynamic libraries left behind from past builds, and manually edited daemon configurations slowly pull the server state beyond transparent control.

On September 13, 2026, software engineer Wai Hon Law published a comprehensive retrospective detailing how he resolved this pervasive maintenance burden. After relying on Arch Linux as his primary distribution for more than ten years, he migrated his 24/7 dedicated home server to GNU Guix—a functional package manager and advanced standalone operating system. While the broader engineering community frequently gravitates toward NixOS when exploring declarative systems, Law explained why he deliberately chose GNU Guix instead, and how one month of continuous production operations validated that technical architecture.

This technical analysis does not aim to dismiss traditional distributions or promote one operating system above all others. Instead, it examines how an engineer methodically dismantled a decade of configuration entropy, uniting system-level declarations and user-space dotfiles into a single Git-tracked Org-mode document. The architectural patterns and practical compromises documented here offer concrete insights for infrastructure engineers, homelab hobbyists, and development teams evaluating declarative infrastructure paradigms.

The technical analysis, architecture comparisons, configuration code, and operational strategies described in this article are directly based on the published experiences of Wai Hon Law in his September 13, 2026 post, 「Switching to GNU Guix: A Beginner's Perspective」. All statements reflect empirical infrastructure realities without commercial bias.

Background: A Decade of Arch Linux and Configuration Entropy

For more than a decade, Arch Linux served as Law's premier distribution of choice. Its rolling-release model ensured that bleeding-edge upstream software arrived immediately, its minimal base installation allowed granular customization without vendor bloat, and the peerless depth of the ArchWiki made troubleshooting virtually any Linux problem straightforward. For years, it genuinely felt like the final distribution an experienced Linux enthusiast would ever need.

24/7 Home Server and Compounding Configuration Fragmentation

However, the operational demands of a dedicated, continuous home server differ fundamentally from those of an interactive desktop workstation. Law's primary server was tasked with running critical self-hosted services around the clock: an orchestration instance of Home Assistant for domestic automation, local DNS caching and resolution, continuous background automated cron routines, and developer sandboxes for testing experimental toolchains. For a physical machine operating 24 hours a day, 7 days a week, long-term stability and deterministic maintainability are paramount.

Over years of continuous micro-adjustments, configuration entropy inevitably crept into the underlying OS. The actual operating state of the machine became fragmented across disparate, disconnected silos:

  • Accumulated manual modifications and pending merge configurations distributed beneath the /etc directory hierarchy
  • Installed binaries, ad-hoc build artifacts, and shared library dependencies lingering across /usr and global paths
  • Scattered systemd service unit files placed in /etc/systemd/system/ with disconnected dependency trees
  • Historical package manager transaction states from pacman alongside unrecorded manual compile jobs

Whenever an adjustment was necessary, the administrator had to maintain meticulous manual notes documenting which specific configuration files were touched, when the edit occurred, and why the change was introduced. Despite diligent bookkeeping, the risk of configuration drift, accidental overwrites during package upgrades, or inability to reproduce the exact server state after hardware failure remained an ever-present source of operational anxiety.

AUR Security Incidents and the Impetus for Fundamental Re-evaluation

The catalyst that accelerated a complete architectural re-evaluation was community repository security. Recent security incidents surrounding packages in the Arch User Repository (AUR)—which Law had previously discussed in the context of maintaining custom Caddy web server builds—alongside evolving developments in the broader Arch ecosystem prompted him to rethink his operational foundation.

What the infrastructure required was not merely another package manager capable of downloading updates, but an operating system paradigm that was strictly declarative, mathematically reproducible, and verifiable entirely through revision-controlled source code.

NixOS VM Evaluation and the Friction of Documentation Fragmentation

When searching for operating systems engineered specifically to eliminate configuration drift, NixOS naturally emerged as the foremost candidate. Boasting the largest community footprint, the most expansive repository of packaged software in the functional distribution landscape, and significant industry adoption, NixOS was Law's initial choice for experimental evaluation.

Testing NixOS in a VM and Experiencing Declarative Power

Law provisioned a NixOS virtual machine and invested substantial effort into systematically replicating the core services running on his Arch home server. The inherent advantages of functional package management and declarative operating systems were immediately evident:

  • Declaring the entire desired state of the operating system inside unified configuration files without manual system mutation
  • Instantaneous, atomic rollback capabilities allowing the machine to revert safely to a prior working generation if a deployment failed
  • Strict immutability in system paths preventing leftover installation debris from conflicting with active runtimes

The experiment firmly validated the overarching concept: managing an entire operating system through declarative code with generational rollback capability was unquestionably the superior operational model. Nevertheless, as the evaluation transitioned from simple proofs of concept to intricate service configurations, friction within the NixOS developer experience became increasingly acute.

Experimental Tooling and Split Wikis as Cognitive Barriers

The primary stumbling block encountered within NixOS centered on documentation fragmentation and an unresolved ecosystem transition. The Nix community was navigating a multi-year paradigm shift between legacy tooling and modern workflows:

  • The newer unified nix command-line interface and the Nix Flakes feature set remained classified as experimental capabilities, requiring explicit opt-in flags rather than being standardized defaults
  • Because Flakes were not universally enforced as the singular standard across the ecosystem, tutorials, community guides, and official materials frequently presented contradictory syntax and patterns
  • The presence of two separate, competing community wikis compounded the difficulty of identifying authoritative, up-to-date guidance for complex service setups

For a production home server intended to run reliably for years with minimal maintenance overhead, building upon experimental core tooling and navigating divergent documentation represented an unwelcome cognitive tax.

Architectural Cohesion: Why Guile Scheme and Shepherd Won

During his deep dive into the declarative landscape, Law encountered two influential technical videos: David Wilson's presentation on the System Crafters channel, 「Why I Choose Guix Over NixOS」, and YouTux's analysis, 「One of the Best Linux Distros Isn't Even in DistroWatch's Top 100」. The architectural arguments presented in these critiques resonated strongly, prompting him to spin up a GNU Guix virtual machine for evaluation.

GNU Guix shares the same foundational computer science pillars as NixOS: functional package management, declarative configuration declarations, and atomic generational rollbacks. However, the architectural design choices implemented by the Guix project exhibited significantly higher cohesion across the software stack.

Guile Scheme: A General-Purpose Language Over a Specialized DSL

While NixOS relies upon its own bespoke, domain-specific configuration language (the Nix expression language), GNU Guix utilizes GNU Guile—a robust, general-purpose implementation of the Scheme programming language (a member of the Lisp family)—across the entire system.

As an active Emacs user accustomed to Emacs Lisp (Elisp), Scheme felt natural, expressive, and immediately familiar to Law. Rather than mastering the idiosyncrasies of a specialized configuration DSL with limited utility outside package declarations, he could leverage a complete, standardized programming language equipped with first-class functions, hygienic macros, powerful module systems, and rich interactive debugging capabilities.

GNU Shepherd: Unified Data Model Down to PID 1

The service management tier highlighted another profound architectural divergence. While NixOS builds upon standard systemd as its init and service daemon, Guix System incorporates GNU Shepherd as its native service manager. Shepherd itself is authored entirely in Guile Scheme.

Consequently, within GNU Guix, every layer of the operating system—from low-level package build recipes and system daemon declarations to PID 1 itself—shares an identical programming language and a unified data model. There is no conceptual impedance mismatch between system declaration code, shell scripts, and init service specifications.

Free Software Principles and the 357-Byte Bootstrap Seed

The philosophical stances of the two projects also diverge sharply. NixOS embraces pragmatic convenience, offering simple configuration toggles to enable proprietary software and binary firmware blobs. GNU Guix strictly adheres to the GNU Free System Distribution Guidelines (FSDG), shipping exclusively with the Linux-libre kernel and free software by default.

Because Law's home server connected to the household network via a physical Ethernet cable, proprietary Wi-Fi firmware was entirely unnecessary; the Linux-libre kernel functioned out of the box without requiring manual driver interventions. Furthermore, Guix's uncompromising focus on bootstrapping integrity—exemplified by reducing the bootstrap binary seed down to approximately 357 bytes through the stage0/Mes bootstrap project—offered deep technical rigor. The ability to verify and build an entire computing foundation from minimal, transparent roots provided immense architectural trust.

Literate Infrastructure: Managing System and Home via Org-mode in Git

Upon completing his migration to GNU Guix, Law established a streamlined infrastructure management pattern characterized by complete transparency. The configuration for the entire machine lives within a single literate Org-mode document (guix.org) tracked entirely in Git.

Unifying Guix System and Guix Home in a Single Repository

In conventional operating systems, administrative privileges divide system-level settings from user-space environments into separate, uncoordinated silos. In Guix, these two operational layers integrate harmoniously:

  • Guix System: Declares foundational operating system parameters, kernel specifications, file system mounts, and background system daemons
  • Guix Home: Declares user-level application packages, shell configurations, environment variables, and symlinked dotfiles

By leveraging Emacs Org Babel, Law structured guix.org as an executable literate document. Detailed explanations of architectural decisions sit directly beside the executable Scheme blocks that implement them, transforming the server repository into a self-documenting, auditable specification.

Predictable Operations with Literate Specifications

Under this literate declarative model, configuration anxiety vanished. In previous years on Arch Linux, performing extensive system overhauls felt risky due to unrecorded interdependencies. Under Guix, an operator can inspect the codebase and immediately determine exactly which packages are active and which services are running. Tuning the operating system now feels as safe, predictable, and manageable as editing an Emacs configuration file.

Co-locating Services and Infrastructure with Streamlined Shepherd Timers

Writing system infrastructure in a general-purpose programming language rather than static configuration files (YAML, JSON) or rigid DSLs unlocks unprecedented compositional flexibility.

Co-locating Containers and Reverse Proxies via simple-service

Deploying a self-hosted web service in traditional distributions forces an administrator to fragment its configuration across completely disconnected subsystems. One must draft a systemd unit in /etc/systemd/system/ to govern container lifecycle, and independently author virtual host proxy blocks inside /etc/nginx/conf.d/. When deprovisioning or altering the service, an administrator must hunt down every disconnected file.

Guix solves this cleanly through its service extension architecture via simple-service. An administrator can co-locate a service definition and its surrounding network ingress side by side within the exact same configuration block:

;; Home Assistant container
(simple-service 'home-assistant-container
                oci-service-type
                (oci-extension
                 (containers
                  (list
                   (oci-container-configuration
                    (provision "home-assistant")
                    (image "ghcr.io/home-assistant/home-assistant:stable")
                    ...details config...)))))

;; Inject the Nginx reverse proxy configuration for Home Assistant
(simple-service 'home-assistant-nginx-server
                nginx-service-type
                (list
                 (nginx-server-configuration
                  (inherit ssl-server-configuration)
                  (server-name (list (string-append "home." domain)))
                  (locations
                   (list
                    (nginx-location-configuration
                     ...details config...)))))

In this block, the Home Assistant OCI container specification and its companion Nginx SSL reverse proxy route reside within a single logical grouping. Understanding, updating, or deleting the entire service becomes atomic, self-contained, and completely free of orphaned configuration artifacts.

Declaring Shepherd Timers and Dependencies in Single Expressions

A similar degree of cohesion extends to scheduled recurring maintenance tasks. While systemd requires drafting separate .service execution units alongside companion .timer schedule units, GNU Shepherd allows the executable script, its explicit libraries, and its execution schedule to be declared in one unified Guile expression:

(let* ((duckdns-script
        (program-file
         "duckdns-update"
         (with-extensions (list guile-gnutls) ;required by (web client)
                          #~(begin
                              (use-modules (ice-9 textual-ports)
                                           (web client))
                              (let ((token (string-trim-both
                                            (call-with-input-file "/etc/secrets/duckdns.token"
                                              get-string-all))))
                                    (query-template (string-append "https://www.duckdns.org/"
                                                                   "update?domains=<mydomain>"
                                                                   "&token=~a&ip=")))
                                (http-get (format #f query-template token)))))))
       (duckdns-timer
        (shepherd-timer '(duckdns)
                        "*/5 * * * *"
                        #~(#$duckdns-script)
                        #:requirement '(networking)
                        #:documentation "Update personal domain IP on DuckDNS every 5 minutes.")))
  (simple-service 'duckdns-timer
                  shepherd-root-service-type
                  (list duckdns-timer)))

This snippet demonstrates an automated routine updating a home server's dynamic public IP with DuckDNS every five minutes. The necessary HTTP TLS extension (guile-gnutls) is injected cleanly, and the timer explicitly declares a requirement on active network connectivity (#:requirement '(networking)), preventing execution failures during system boot.

Containerized Isolation via guix shell and Agent Sandboxing

Operational reality frequently requires administrators to run one-off command-line utilities or evaluate experimental tools. In traditional Linux environments, installing these utilities globally pollutes package state, leaving obsolete dependencies scattered across the file system.

Ephemeral Environments Preventing Profile Pollution

The guix shell command provides an elegant resolution. Rather than altering the user's permanent environment profile, guix shell instantiates an ephemeral, self-contained runtime containing exactly the requested packages. Once the terminal session terminates, the environment disappears cleanly without leaving global residue.

Sandboxing Untrusted Software and AI Coding Agents

Furthermore, the container mode of guix shell (invoked via -C or --container) enables lightweight Linux namespace isolation. By combining container flags with explicit directory sharing (--share) and granular network permissions (--network), an operator can construct an impervious sandbox for untrusted commands or autonomous software.

Law applied this mechanism to safely execute the Antigravity CLI (agy), an autonomous AI coding agent. By isolating the agent in a sandbox, he guaranteed that it could not inspect arbitrary private directories or accidentally alter core operating system files:

# Run Antigravity CLI in a Guix sandbox with access to its config and the project directories.
agy-guix() {
    guix shell --container --network --emulate-fhs \
         --share="$PWD" \
         --share="$HOME/.gemini" \
         --share="$HOME/.local/bin" \
         --preserve='^(TERM)$' \
         coreutils nss-certs bash guix guile emacs git ripgrep fd zip unzip -- $HOME/.local/bin/agy "$@"
}

Through this shell wrapper, the agent operates inside a container that can only see the current working repository ($PWD), its specific configuration directory ($HOME/.gemini), and its execution binary path ($HOME/.local/bin). Sensitive private keys, personal documents, and underlying operating system internals remain completely hidden from the autonomous runtime.

Addressing the Package Catalog Gap: Four Practical Strategies

Every architectural choice carries practical trade-offs, and GNU Guix is no exception. For an engineer migrating from Arch Linux, the most noticeable immediate friction is the disparity in package ecosystem size.

Strict Software Freedom Guidelines vs Package Breadth

Unlike the Arch User Repository (AUR), which contains virtually any modern software utility packaged by community volunteers, the official GNU Guix channel enforces rigorous free software standards and auditable source-build requirements. Consequently, popular utilities such as the static site generator hugo and the modern web server caddy are absent from the default distribution channels. To overcome this repository gap, Law established four pragmatic operational strategies.

Strategy Number & Pattern Applicable Scenario Concrete Implementation Method Operational Advantages & Trade-offs
1. Custom Package Definitions Missing standalone binary releases Author Guile Scheme package recipe fetching official upstream release archives Seamless system integration; requires maintaining personal recipe code
2. Ephemeral Language Toolchains Utilities existing within language ecosystems Pair guix shell with language runners like npx or uvx Zero global profile clutter; automatic runtime dependency isolation
3. Automated guix import Upstream open-source libraries (PyPI, Crates.io) Generate Guix Scheme definitions automatically from upstream registry metadata Drastically cuts manual packaging effort across vast software registries
4. Adopting Native Alternatives Complex tools carrying heavy maintenance debt Revert to first-class, natively supported Guix system services Maximizes long-term operational stability; eliminates custom build plugins

From Binary Packaging to Language Toolchains and Native Services

The first strategy involves authoring custom package recipes. In Guile Scheme, defining a local package that downloads an official prebuilt upstream archive is straightforward. Law authored a concise definition for Hugo, making the binary available across his deployment pipeline without waiting for upstream distribution packaging:

(define hugo
  (package
    (name "hugo")
    (version "0.165.0")
    (source (origin
              (method url-fetch)
              (uri (string-append
                    "https://github.com/gohugoio/hugo/releases/download/v"
                    version "/hugo_" version "_linux-amd64.tar.gz"))
              (sha256 (base32 "0..."))))
    (build-system trivial-build-system)
    ...))

The second strategy leverages ephemeral toolchain runners. For software belonging to active language package ecosystems, tools can be executed on-demand via guix shell paired with ecosystem runners like npx or uvx, avoiding global installations entirely. Law publishes his static website using this exact pattern:

# That is how I publish my blog to Cloudflare now.
guix shell node -- npx -y wrangler

The third strategy relies on the built-in guix import command. This utility automatically translates package metadata from major upstream registries—including PyPI, Crates.io, CPAN, and GNU ELPA—directly into valid Guix Scheme recipes, dramatically reducing the manual burden of writing packaging boilerplate.

The fourth strategy embraces readily available native alternatives. Rather than spending hours maintaining a custom Caddy build with third-party extensions on an unsupported distribution, Law chose to return to Nginx combined with Certbot. Because both are officially supported, first-class services within Guix System, long-term maintenance overhead dropped to zero.

Managing Substitute Timing and Reflections After One Month of Operation

Another fundamental characteristic of GNU Guix that operators must understand is that it is fundamentally a source-based distribution backed by binary substitute build farms (such as ci.guix.gnu.org and Bordeaux).

Substitute Misses and Pinning Channel Revisions

When an operator runs guix pull to fetch the latest channel commit, if the official continuous integration build farm has not yet compiled the corresponding binaries for that exact revision, Guix gracefully falls back to compiling packages from source locally on the machine. On a home server with constrained hardware resources, triggering unexpected local compiles of large software packages can saturate CPU cores and cause excessive delays.

Law's practical workaround was to pin guix pull to a specific Git commit from a day or two earlier. By targeting an established commit rather than tracking the absolute tip of tree, he ensured that substitute binaries were already fully compiled, cached, and ready for instant download:

;; ~/.config/guix/channels.scm (or: guix pull --commit=<hash>)
(list (channel
       (inherit %default-guix-channel)
       ;; faster pull via Codeberg mirror
       (url "https://codeberg.org/guix/guix.git")
       (commit "5b52edf051a020947b1d4859853799f2bbce176e")))

This source-based architecture is simultaneously one of Guix's greatest strengths. It unlocks foundational verification tools like guix challenge (which cross-references build artifacts against independent build servers to detect compilation tampering) and guix time-machine (which allows reproducing identical system states from historical Git revisions at any point in the future).

Operational Retrospective and Architectural Takeaways

One month into managing his dedicated home server on GNU Guix, Law concluded that the migration had achieved its core objectives. Configuration drift was entirely eliminated, and tracking system state through Git provided deep operational confidence. The seamless synergy between Guile Scheme and Emacs transformed routine systems administration into an enjoyable, cohesive programming activity.

While navigating a smaller package ecosystem and managing substitute caching require occasional tactical planning, the benefits of deterministic reproducibility, architectural elegance, and robust container sandboxing make GNU Guix a remarkably sturdy platform. To deepen his mastery of functional systems and Scheme, Law noted that he has begun studying the classic computer science text SICP (Structure and Interpretation of Computer Programs).
