10,000韩元三人平分只剩9,999 - 韩元没有小数位带来的那1元

分摊、折扣、退款、税额拆分中1元消失又出现的位置，以及必须保存分摊结果的理由

2026-08-01 开发/基础设施

症状：结算页的合计比实收金额少了1元

情形是虚构的，但形态很常见。三个人分摊了一笔10,000韩元的订单，卡组织那边正好授权了10,000元。可结算页的合计栏显示的是9,999元。没人知道那1元去了哪里，对账批处理卡在合计不一致上。

1元的误差按金额看什么都不是。问题在于这1元过不了自动对账。结算会机械地检查合计是否相符，不符就只能由人手工去查。在一天流转数万笔的地方，这类工单积压几百条，金额只有几百元，工作量却是好几天。

先把结论写在前面。常见的处方「把取整做好」只说中了一半。真正的问题是这三点。

  • 除法必然留下余数。 韩元没有承载这个余数的小数位。无论选哪种取整方式，合计都会错开
  • 不保存除法的结果，以后就还原不出来。 退款、撤销、部分结算都需要知道「当时谁付了多少」，而重新计算得不出那个值
  • 1元很小，但合计对不上结算就会卡住。 这是一个金额大小和事故大小不成正比的领域

下面所有数字都不是估计，而是实际运行得到的输出。这些都可以用计算器复核，有疑问请自己复现一遍。

运行环境。 下面的输出都是在 Windows 10 Pro (10.0.19045) 上实际执行的结果。运行时为 Python 3.13.3 (win32) 与 Node.js v22.16.0 (win32, ICU 77.1)，shell 为 GNU bash 5.2.37 (MSYS2/MinGW64)。脚本全部保存为文件后执行。金额一律为韩元。

本文不涉及的内容。 税法和会计规程要求哪种取整，本文不作断言。那属于企业政策、合同以及相关专业人士判断的范围。本文只看无论那个政策定成什么样，代码如何实现才不会与之偏离。数值在序列化与反序列化过程中被压坏的问题在JSON数字精度丢失中单独讨论过。这里只挖整元分摊这一个点。文中出现的金额和购物车都是虚构的。

1. 韩元没有承载小数的位置

起点是货币本身的性质。美元有美分，欧元有欧分，所以都用两位小数。韩元不是这样。国际货币代码标准为每种货币指定一个小数位数(exponent)，韩元登记为 0。直接问了运行环境。

node v22.16.0 / ICU 77.1

--- 0-1. default fraction digits per currency, straight from Intl ---
currency  formatted 1234.5        min  max
---------------------------------------------------
KRW       ₩1,235                 0    0
JPY       ¥1,235                 0    0
USD       $1,234.50              2    2
EUR       €1,234.50              2    2
KWD       KWD 1,234.500          3    3
CLF       CLF 1,234.5000         4    4

这张表就是全文的背景。「两位小数」不是货币的普遍性质。 科威特第纳尔用三位，智利计价单位用四位。而韩元和日元是0位。

货币小数位数最小单位实务上意味着什么
KRW (韩元)01元直接按整数存储。 乘100存储毫无意义
JPY (日元)01日元与韩元性质相同
USD (美元)20.01美元按美分整数存储的惯例成立
EUR (欧元)20.01欧元与美元相同
KWD (第纳尔)30.001第纳尔乘1000存储。两位前提被打破的反例
CLF (计价单位)40.0001与物价挂钩的计算单位

名义上韩元也还留着一个叫钱的辅币单位。但它不用于交易，只出现在汇率报价一类的场合，国际标准的小数位数是0。实务上，流通的最小面额是1元就是全部。

这里出现了韩国特有的陷阱。处理金额的库大多默认「按最小单位的整数存储，显示时除以100」。以美元为基准这是优秀的设计。原封不动套到韩元上会怎样，实测了一下。

--- 0-2. what the generic cents pattern does to a KRW amount ---
amount in KRW                      : 1234
generic "store minor units" x100   : 123400
display that back /100 as KRW      : ₩1,234
the x100 is dead weight: KRW has no 1/100 to hold

--- 0-3. formatting a fractional KRW value ---
3333.3333333333335     -> ₩3,333
3333.5                 -> ₩3,334
3334.5                 -> ₩3,335
2450.5                 -> ₩2,451
2451.5                 -> ₩2,452
the formatter hides the fraction. it does not remove it,
and it is not the value that gets stored or charged
  • 乘100是纯粹的浪费。 韩元没有百分之一，所以只增加存储空间和转换代码。而且那个乘100的值一旦在什么地方原样漏到页面上，就成了123,400元的事故
  • 更危险的是 0-3 里格式化器的行为。传入带小数的值，格式化器会悄悄显示成整数。页面看着正常，存储的值里小数还活着
  • 在这种状态下把多条相加，页面合计和真实合计就分道扬镳。格式化不会修改值。 在显示层取整和在存储层取整是完全不同的两件事
  • 顺带一提，这个格式化器把 3334.5 进位成了 3,335。和后面要看的另一种取整实现行为不一致。同一个项目里混着两种方式，本身就是1元误差的来源

2. 10,000韩元三个人分

下面进入核心复现，从最简单的情形开始。

python 3.13.3 / win32   currency KRW (integer, no minor unit)

--- 1-1. 10000 KRW, 3 payers, the plain way ---
total                : 10000
total / n            : 3333.3333333333335
Decimal exact        : 3333.333333333333333333333333
floor           3333  3333  3333  sum   9999   total-sum +1
round-half-up   3333  3333  3333  sum   9999   total-sum +1
ceil            3334  3334  3334  sum  10002   total-sum -2

开头说的9,999元就是这个。逐行读的话是这样。

  • 精确份额是 3333.333…，没有办法用韩元表示。3,333元和3,334元之间什么都没有
  • 向下取整三个人都是3,333元，合计9,999元。1元消失了
  • 四舍五入在这个金额上小数部分是0.33，结果与向下取整相同。这是换成四舍五入并不能解决问题的第一个证据
  • 向上取整三个人都是3,334元，合计10,002元。多收了2元。从顾客角度看这一种更糟

也许有人怀疑10,000这个数字特殊。把范围放宽看看。

--- 1-2. it is not only 10000: same split, other totals ---
total    exact         floor x3   sum      round x3   sum      ceil x3    sum
-------------------------------------------------------------------------------
10000    3333.3333     3333       9999     3333       9999     3334       10002
10001    3333.6667     3333       9999     3334       10002    3334       10002
10002    3334.0000     3334       10002    3334       10002    3334       10002
9999     3333.0000     3333       9999     3333       9999     3333       9999
35000    11666.6667    11666      34998    11667      35001    11667      35001
100000   33333.3333    33333      99999    33333      99999    33334      100002
1        0.3333        0          0        0          0        1          3

note: the three modes agree with the total only on 10002 and 9999 - the two rows
      already divisible by 3. every other row is off by -2, -1 or +2.

结论很明确。只有总额是3的倍数的那两行合计才对得上。 其余五行无论选哪种方式都会在 -2元到 +2元之间错开。最后一行很极端：1元分给三个人，向下取整和四舍五入三个人都是0元，1元全部蒸发；向上取整三个人都是1元，收到了原额的三倍。

从这张表要带走的只有一点。取整方式只改变误差的方向，不消除误差。 想消除就得做别的事。

3. 向下、四舍、向上 - 三种方式的合计差

不是一条而是多行汇总时，误差也会累积。把五行共同费用各自除以3组成一个人的份额，再乘回三倍与商家实收的总额比较。

--- 2-1. three rounding modes on one 5-line order (each line 1/3 of a shared cost) ---
line total   /3 exact      floor  round  ceil
-------------------------------------------------
7000         2333.333333    2333   2333   2334
12500        4166.666667    4166   4167   4167
3300         1100.000000    1100   1100   1100
990          330.000000     330    330    330
45000        15000.000000   15000  15000  15000
-------------------------------------------------
one payer's share sums to   floor  22929   round  22930   ceil  22931
x3 (what the shop collects) floor  68787   round  68790   ceil  68793
order total                 68790
gap vs order total          floor -3      round +0       ceil +3

这里四舍五入碰巧对了。产生小数的只有两行，而这两行互相抵消了。不要把这个巧合读成「四舍五入是对的」。上一节的10,000元里，同样的四舍五入丢了1元。有时对有时不对，正是这种做法的性质。

而且关于四舍五入还有一件必须确认的事。「取整」这个词指的行为不止一种。

--- 2-2. the default round() in this runtime is NOT half-up ---
0.5        python round() 0       ROUND_HALF_UP 1       ROUND_HALF_EVEN 0
1.5        python round() 2       ROUND_HALF_UP 2       ROUND_HALF_EVEN 2
2.5        python round() 2       ROUND_HALF_UP 3       ROUND_HALF_EVEN 2
3.5        python round() 4       ROUND_HALF_UP 4       ROUND_HALF_EVEN 4
4.5        python round() 4       ROUND_HALF_UP 5       ROUND_HALF_EVEN 4
2450.5     python round() 2450    ROUND_HALF_UP 2451    ROUND_HALF_EVEN 2450
2451.5     python round() 2452    ROUND_HALF_UP 2452    ROUND_HALF_EVEN 2452
half-even sends x.5 to the nearest even integer, so 2.5 becomes 2, not 3

这个运行时的默认取整函数不是四舍五入。它把 2.5 送到 2 而不是3。正好是一半时送往最近的偶数，统计上偏差更小，但与人的预期不一致。前面看到的国际化格式化器把 3334.5 进位成了3,335。如果这两者共存于同一个项目，就会有的行上去有的行下来，散发出难以追因的1元差异。

方式10,000元分3份的合计误差方向性质用在哪里
向下取整9,999元总是不足商家吃亏，顾客得利有顾客优先原则并另行处理余数时
四舍五入9,999元双向，难以预测最直观但没有保证显示用。存储值的计算不够用
银行家舍入9,999元双向，长期偏差小许多运行时的默认值正因是默认值而不知不觉在用的地方
向上取整10,002元总是超出顾客吃亏。退款场景尤其危险仅限手续费、利息等政策明示时
分摊(余数明示)10,000元无误差合计永远等于原额应设为分摊与结算的默认

4. 多出来的1元给谁

最后一行就是本文的处方。不要去挑取整方式，而是把余数明确地分摊掉。做法很简单：给所有人向下取整的值，再把剩下的金额一元一元地加给某些人。余数永远小于人数，所以不会有人多付2元以上。

剩下的问题是加给谁。四种策略实测比较如下。

--- 3-1. who gets the leftover 1 KRW: four policies, equal weights ---
total 10000  weights [1, 1, 1]   floor share 3333  leftover 1
policy      A      B      C      sum    sum==total
---------------------------------------------------
first      3334   3333   3333   10000  True
last       3333   3333   3334   10000  True
largest    3334   3333   3333   10000  True
rotate     3334   3333   3333   10000  True

--- 3-2. unequal weights: a 100000 KRW bill shared by usage ---
total 100000  weights [3, 3, 1] (sum 7)
  member 0 exact share : 42857.14285714285714285714286
  member 1 exact share : 42857.14285714285714285714286
  member 2 exact share : 14285.71428571428571428571429
policy      A      B      C      sum    sum==total
---------------------------------------------------
first      42858  42857  14285  100000 True
last       42857  42857  14286  100000 True
largest    42857  42857  14286  100000 True
rotate     42858  42857  14285  100000 True
largest-remainder gives the extra KRW to the biggest fractional part,
so the member who was cut the most is the one paid back first

四种策略的合计都正好等于原额。 sum==total 这一列全是 True。区别只在于谁多付那1元。

第二段展示了选择策略的依据。按用量3:3:1分摊100,000元时，小数部分最大的是第三个人(0.714)。最大余额法把1元给他。规则是「优先补偿被削得最多的人」，所以单看一次分摊，这一种最公平。

可结算通常是反复发生的。如果每月按同样构成分摊，情况就不同了。

--- 3-3. rotate across 6 monthly bills keeps the unfairness bounded ---
month  total   A     B     C     sum   start
--------------------------------------------
1      10000   3334  3333  3333  10000 0
2      10000   3333  3334  3333  10000 1
3      10000   3333  3333  3334  10000 2
4      10000   3334  3333  3333  10000 0
5      10000   3333  3334  3333  10000 1
6      10000   3333  3333  3334  10000 2
--------------------------------------------
6-month cumulative      20000 20000 20000 60000
max-min spread over 6 months : 0 KRW
same 6 months with policy=first : [20004, 19998, 19998]  spread 6 KRW

差别一目了然。每月轮换起始位置，六个月后三个人正好各付20,000元，差距为0。而固定给第一个人的策略让A每月多付1元，累积出6元的差距。只看一个月是1元，但像订阅那样持续下去，偏差就会朝一个方向堆积。

分摊策略合计保证单次公平性重复时的偏差实现成本推荐场景
给第一个人有低朝一个方向累积最简单一次性分摊
给最后一个人有低朝一个方向累积简单一次性分摊
最大余额有最高权重固定时可能累积一次排序权重不同的单次分摊
轮换有中等相互抵消(6个月差0)需保存起始位置反复发生的周期结算
单纯四舍五入没有--最简单不要用

重要的不是哪一个才是正确答案。四种方式合计都对得上。要确定的是把「我们用这一种」写进代码的某一处和文档里，然后是保存它的结果。

5. 折扣在哪一步取整会改变金额

产生除法的不只有分摊。定率折扣也是除法。 打八五折就是乘85再除以100，同样会产生余数。用一个虚构的四行购物车验证。

--- 4-1. where you round a percent discount changes the bill ---
cart [1990, 2990, 5990, 990]   subtotal 11960 KRW   discount 15 percent

line   price    exact discounted   per-line floor  per-line half-up
--------------------------------------------------------------------
A      1990     1691.5             1691            1692
B      2990     2541.5             2541            2542
C      5990     5091.5             5091            5092
D      990      841.5              841             842
--------------------------------------------------------------------
A. round every line, then add  : floor 10164   half-up 10168
B. add first, then round once  : floor 10166   half-up 10166
exact untouched value          : 10166
A minus B                      : floor -2       half-up +2
same cart, same rate, same rounding mode - two different totals

同一个购物车、同样的折扣率、同样的取整方式，却出来两个总额。造成差别的只有在哪一步取整这一点。

  • 四行都以 .5 结尾，差别格外鲜明。逐行四舍五入四次都进位，得 +2元；逐行向下取整四次都舍去，得 -2元
  • 实际误差幅度与行数成正比。二十行的订单最多差10元，一百行最多差50元。到这一步就很难再叫它「1元问题」了
  • 两者都不是算错。它们只是不同问题的答案。问题出在下单页面和结算批处理各用一种的时候
  • 如果顾客看到的小票会打印逐行折扣额，那就必须按行计算并保存。只保存总额而在页面上重算逐行金额，小票各行相加就与实付金额对不上

5.1 两个折扣叠加时顺序会改变结果

优惠券叠加会员折扣这类定率折扣重叠很常见。若是纯粹的乘法，顺序不会改变结果。中间夹了取整就不一样了。

--- 4-2. two stacked discounts, same rates, reversed order ---
price    10 then 3      3 then 10      one combined rate
-----------------------------------------------------------
28900    26010  -> 25230  28033  -> 25230  25230
33000    29700  -> 28809  32010  -> 28809  28809
19900    17910  -> 17373  19303  -> 17373  17373
12345    11111  -> 10778  11975  -> 10778  10777
7700     6930   -> 6722   7469   -> 6722   6722

sweep 1..50000 KRW : 15550 prices give a different final amount (31.1 percent)
  first six : 17 gives 15 or 14, 18 gives 16 or 15, 26 gives 22 or 23,
              36 gives 31 or 32, 46 gives 40 or 41, 51 gives 45 or 44
rounding BETWEEN the two steps is what makes the order matter

五个常见价位上换顺序结果都相同。可是从1元到50,000元全部扫描后，有15,550个金额答案不同。差不多每三个价格就有一个。

12345 那一行还藏着另一个陷阱。两个折扣分步应用得到10,778元，而把0.90和0.97先乘起来一次应用得到10,777元。数学上是同一个折扣率，有没有中间取整就分出了1元。

  • 只用几个值做测试是能通过的。上面那五行就是证据。这类缺陷能长期存活的原因就在这里
  • 顾客反馈的形式是「先用优惠券便宜1元」。很难复现，所以经常被以无法复现关掉
  • 对策是中间步骤不取整。用有理数或定点数一路带到底，在生成最终应收金额时只落一次整数
  • 如果中间值必须显示，就只为显示取整，传给下一步计算的仍是取整前的值

6. 部分退款 - 不留着分摊值就还原不出来

这里是本文论点最清晰的地方。前面讲的都是「怎么分」，从这里开始是「分完了怎么还原」。

--- 5-1. partial refund with no stored allocation ---
charged : [3334, 3333, 3333]   sum 10000

case A - refund recomputed as total/3 at refund time
  floor     refund each 3333  x3 = 9999    shop ends up +1 KRW off
  half-up   refund each 3333  x3 = 9999    shop ends up +1 KRW off
  ceil      refund each 3334  x3 = 10002   shop ends up -2 KRW off
case B - refund reads the stored per-payer amount
  refunds [3334, 3333, 3333]  sum 10000   shop ends up +0 KRW off

收款时按 [3334, 3333, 3333] 分得很好。问题在退款。

  • 情形A 在退款时重算 总额 / 3。三个人各退3,333元共9,999元，1元留在了商家手里。有个顾客付了3,334元却只拿回3,333元
  • 改成向上取整更糟。 退出10,002元，商家亏2元。这是把从未收到的钱付出去，会计上无法解释
  • 情形B 读取保存的值，合计正好10,000元。造成差别的不是算法，而是有没有保存

更贴近现实的形态是购物车整单折扣的情况。这时哪一行「实际付了多少」本来就是含糊的。

--- 5-2. refunding one line out of a cart-level discount ---
subtotal 11960, 15 percent off, actually charged 10166
line   list price   allocated paid   line x 0.85 rounded
---------------------------------------------------------
A      1990         1692             1692
B      2990         2542             2542
C      5990         5091             5092
D      990          841              842
---------------------------------------------------------
allocated sum 10166   equals charged : True
per-line   sum 10168   equals charged : False

return line A (list 1990) -> refund 1990 / 1692 / 1692  (list / recomputed / stored)
   remaining after each : 8176    8474    8474      should be 8474
return line B (list 2990) -> refund 2990 / 2542 / 2542  (list / recomputed / stored)
   remaining after each : 7176    7624    7624      should be 7624
return line C (list 5990) -> refund 5990 / 5092 / 5091  (list / recomputed / stored)
   remaining after each : 4176    5074    5075      should be 5075
return line D (list 990) -> refund 990 / 842 / 841  (list / recomputed / stored)
   remaining after each : 9176    9324    9325      should be 9325

return ALL FOUR lines one at a time:
  list price   refunded 11960    charged 10166    gap +1794 KRW
  recomputed   refunded 10168    charged 10166    gap +2 KRW
  stored       refunded 10166    charged 10166    gap +0 KRW

三种退款实现并排放在一起。最后三行就是结论。

  • 按原价退款要退11,960元，而收到的是10,166元。白送1,794元。 用了折扣券再全部退货就能凭空多出钱，这类著名事故就是它
  • 退款时重算退出10,168元，亏2元。好多了但仍然对不上，因为C行和D行各与保存值差了1元
  • 读取保存的分摊值正好是10,166元，差额为0
  • 值得注意的是重算方式在大多数行上是对的。A和B与保存值相同。这意味着必须全量跑一遍才会暴露偏差，所以部分退款的缺陷才能藏那么久
  • 为什么会错，答案在表的最后两行。逐行重算的合计是 10,168元，而实际收款是 10,166元。分摊和重算本来就产生不同的值

本文的论点。 问题的本质不是取整。除法是一个丢失信息的运算，不保存它的结果，以后就没有办法还原。没保存的分摊只能重算，而重算并不保证与原值一致。

所以处方不是算法而是表结构。在收款时把逐行分摊金额作为记录留下来。折扣额也按行分摊后保存。退款是读取那些记录来处理，而不是计算。

9. 设计规则 - 把取整集中到一处

把前面看到的搬进代码，规则只有三句：用整数处理。取整只在一个函数里做。保存结果。 那个函数长这样。

def split_krw(total, weights, policy="largest"):
    """Divide an integer KRW amount over integer weights.

    Rounds in exactly one place. Returns integers whose sum is total.
    """
    if not isinstance(total, int):
        raise TypeError("total must be an int in KRW")
    if not weights or any(w < 0 for w in weights):
        raise ValueError("weights must be non-negative")
    tw = sum(weights)
    if tw == 0:
        raise ValueError("weights sum to zero")
    base = [total * w // tw for w in weights]
    rem = total - sum(base)
    k = len(weights)
    if policy == "largest":
        frac = [(total * w) % tw for w in weights]
        order = sorted(range(k), key=lambda i: (-frac[i], i))
    elif policy == "first":
        order = list(range(k))
    else:
        raise ValueError(policy)
    for i in range(rem):
        base[order[i]] += 1
    assert sum(base) == total, "split_krw broke its own invariant"
    return base

结构很简单。total * w // tw 是整数乘法在先，所以没有浮点误差。余数汇集到 rem，按排好的顺序一元一元加上去。最后一行的断言让函数自己检查合计是否等于原额。

11. 检查清单

看新的支付与结算代码时按这个顺序确认即可。

  • 金额是否用整数(元)处理。是否还有浮点类型残留在什么地方
  • 是否把乘100存储的惯例原样套到了韩元上。韩元的小数位数是0
  • 比率计算是否是先整数乘法后除法的写法。若还留着浮点乘法，特定比率上就会差1元
  • 代码库里取整的函数有几个。应该只有一个
  • 那个函数是四舍五入还是银行家舍入，文档里写了吗。是不是在原样用运行时的默认值
  • 有没有丢弃除法余数的地方。有的话那个余数去哪了
  • 分摊函数里有没有合计等于原额的断言
  • 分摊结果有没有写入表。逐行实付额有没有作为记录留下
  • 折扣额是否也按行分摊并保存。是不是只保存了总额
  • 退款代码是读取保存值还是重新计算
  • 有没有全额退款等于收款合计的测试
  • 部分退款是否对每一行都试过。只有部分行对得上的情况很常见
  • 定率折扣叠加时，有没有调换顺序结果相同的测试
  • 不含税价与税额是不是两边都在取整。其中一边应当用减法求出
  • 逐项反推与整单反推用哪一种定下来了吗。是不是各系统用的不一样
  • 周期结算中余数是不是总落在同一个人身上
  • 可能产生0元分摊的路径上，那一行怎么处理定下来了吗
  • 结算批处理有没有差额等于0的检查，不为0时会不会停下
  • 测试数据是不是只用了3的倍数、11的倍数这类能整除的值
  • 有没有用大批量做过累积误差测试。几条数据是看不出来的

# 韩元1元分摊 — 算法·对比表·校验

> 来源: braindetox.kr — 10,000韩元三人平分只剩9,999
> 依据: Windows 10 / Python 3.13.3 / Node 22.16.0 (ICU 77.1) 实测验证
> 币种: KRW。ISO 4217 小数位为 0（无辅币单位）。以下金额均为韩元

## 1. 一处写清原则

- 金额用 **整数（元）** 处理。乘100按最小单位存储的做法在韩元上毫无意义
- 除法的 **余数不要丢弃，要分摊**
- 取整只在 **整个代码库的一个函数** 里做
- **保存** 分摊结果。退款是读取，不是重算

## 2. 分摊算法（合计必然等于原额）

```python
def split_krw(total, weights, policy="largest"):
    if not isinstance(total, int):
        raise TypeError("total must be an int in KRW")
    if not weights or any(w < 0 for w in weights):
        raise ValueError("weights must be non-negative")
    tw = sum(weights)
    if tw == 0:
        raise ValueError("weights sum to zero")

    base = [total * w // tw for w in weights]   # 先整数乘法，后除法
    rem  = total - sum(base)                     # 余数，恒有 0 <= rem < len(weights)
    k    = len(weights)

    if policy == "largest":                      # 按小数部分从大到小
        frac  = [(total * w) % tw for w in weights]
        order = sorted(range(k), key=lambda i: (-frac[i], i))
    elif policy == "first":
        order = list(range(k))
    elif policy == "rotate":                     # 周期结算用，需持久化 START
        order = [(START + i) % k for i in range(k)]
    else:
        raise ValueError(policy)

    for i in range(rem):
        base[order[i]] += 1

    assert sum(base) == total, "split_krw broke its own invariant"
    return base
```

## 3. 各方式对比（10,000韩元分3份）

| 方式 | 结果 | 合计 | 差额 | 判断 |
|---|---|---|---|---|
| 向下取整 | 3333 / 3333 / 3333 | 9,999 | **-1** | 不要用 |
| 四舍五入 | 3333 / 3333 / 3333 | 9,999 | **-1** | 没有保证 |
| 银行家舍入 | 3333 / 3333 / 3333 | 9,999 | **-1** | 多数运行时的默认值 |
| 向上取整 | 3334 / 3334 / 3334 | 10,002 | **+2** | 顾客吃亏 |
| **分摊 first** | 3334 / 3333 / 3333 | **10,000** | **0** | 一次性 |
| **分摊 largest** | 3334 / 3333 / 3333 | **10,000** | **0** | 加权分摊 |
| **分摊 rotate** | 每期轮换 | **10,000** | **0** | **周期结算** |

## 4. 如何选余数分摊策略

| 策略 | 合计保证 | 单次公平性 | 重复时的偏差 | 推荐 |
|---|---|---|---|---|
| first / last | 有 | 低 | **会累积**（6个月6元） | 仅一次性 |
| largest | 有 | **最高** | 权重固定时会累积 | 加权分摊 |
| rotate | 有 | 中等 | **相互抵消**（6个月0元） | **订阅·周期** |

## 5. 校验断言（必须全部通过）

```python
assert sum(parts) == total                    # 合计 = 原额
assert all(p >= 0 for p in parts)             # 无负值
assert len(parts) == len(weights)             # 条数保持
assert max(abs(p * tw - total * w) for ...) < tw   # 每人误差小于1元
assert sum(refunds) == charged                # 全额退款 = 已收金额
assert supply + tax == price_incl             # 不含税价 + 税额 = 含税价
```

实测: 随机30万例全部通过。相对精确份额的最大偏离为 **0.873479元**（小于1元）

## 6. 拆分税额的规则

- **只对一边取整，另一边用减法求出** → 与税率无关，合计永远对得上
- 两边都向下取整 / 两边都向上取整 → 20万个价格中有 **181,819个** 合计对不上
- 逐行反推与整单反推得出的是 **不同的值**（样本729个中239个，32.8%）
- 用哪一种由 **企业政策·合同·专业人士的判断** 决定，并写进文档

## 7. 折扣规则

- 中间步骤不要取整。**只在最终应收金额上取整一次**
- 两个折扣叠加时顺序会改变结果 → 5万个价格中有 **15,550个**（31.1%）
- 逐行取整之和与整单取整不同 → 示例购物车相差 **2元**
- 若小票要打印逐行金额，就 **按行计算并保存**，合计由这些行相加得出

## 8. 禁用浮点的理由

- `金额 * 0.7`（浮点）与 `金额 * 7 / 10`（整数）在 **100万中有18,724个** 答案不同
- 45元打七折: 浮点得 `31.499999999999996` 取整为31 / 整数正好 `31.5` 取整为32
- 有些比率的分歧数为 **0**，所以试几个用例根本抓不到
- 金额本身在约9,007万亿以内都精确 → **危险的不是存储，而是除法和比率乘法**

## 9. 存储结构的最低要求

- 每个收款行都要有 **实付金额** 列（分摊后的值，不是原价）
- 折扣额也按 **逐行分摊值** 保存
- 税额与不含税价也是 **保存的值**，而非读取时再算
- 若用轮换分摊，还要把 **下一个起始位置** 一并保存
- 退款行 **引用** 原收款行，并约束不得超过其金额

## 10. 检查清单

- [ ] 金额是否全为整数（没有残留的浮点类型）
- [ ] 是否对韩元套用了乘100存储
- [ ] 比率计算是否先做整数乘法
- [ ] 取整函数是否只有 **一个**
- [ ] 该函数是四舍五入还是银行家舍入，文档里写了吗
- [ ] 分摊函数里有没有合计断言
- [ ] 分摊结果有没有写入表
- [ ] 退款是否 **读取** 保存值（而不是重算）
- [ ] 有没有全额退款等于已收金额的测试
- [ ] 部分退款是否对 **每一行** 都测过
- [ ] 调换折扣顺序结果是否相同
- [ ] 不含税价与税额是否只对一边取整
- [ ] 逐行反推还是整单反推，是否已确定
- [ ] 周期结算中余数是否总落在同一个人身上
- [ ] 0元分摊行有没有处理策略
- [ ] 结算批处理有没有差额为0的检查，不为0时是否停止
- [ ] 测试数据是否只用了3的倍数和11的倍数
- [ ] 有没有做大批量的累积误差测试

## 11. 不要做的事

- 只靠换取整方式来凑合计 — **任何方式都不提供保证**
- 不保存除法结果，需要时再算一遍 — **还原不出来**
- 按原价退款 — 示例中多退了 **1,794元**
- 用浮点比率乘金额 — 只在特定比率上悄悄出错
- 每一步都取整 — 顺序会改变结果
- 对不含税价和税额分别取整 — 九成以上的价格合计会崩
- 只用能整除的金额做测试 — 3的倍数上看不出这个缺陷
- 放过1元的差额 — 到下个月就查不出它从哪来
