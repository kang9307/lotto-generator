서론: ~/.ssh/config 수동 편집의 고통

관리하는 서버가 다섯 대를 넘어가는 순간부터 ~/.ssh/config 파일은 슬그머니 무거워집니다. IP 주소 몇 개만 외우면 되던 시절과 달리, 클라우드 인스턴스와 사내 서버와 bastion 호스트가 뒤섞이기 시작하면 상황이 달라집니다. 매번 ssh user@10.x.x.x -p 2222 -i ~/.ssh/some_key 같은 긴 명령을 외우거나, 에디터로 config 파일을 열어 별칭을 확인한 뒤 복사해 붙여 넣는 왕복이 반복됩니다. 이 작업의 진짜 비용은 타이핑이 아니라 흐름의 단절입니다. 무언가에 집중하던 중에 서버 별칭이 기억나지 않아 config 파일을 열고, 스크롤하며 찾고, 다시 터미널로 돌아오는 그 몇 초가 하루에 수십 번 쌓이면 결코 작지 않은 마찰이 됩니다.

2026년 5월 29일 GeekNews(news.hada.io)에 9번으로 오른 「Show GN: Rust 기반 TUI SSH 호스트 매니저, sshc」는 정확히 이 마찰을 겨냥한 도구입니다. 저장소는 github.com/hang-in/sshc이고 라이선스는 MIT입니다. 이 글은 sshc를 소개하는 데 그치지 않고 기존 방식 대비 무엇이 다른지, 설치와 설정 파일이 실제로 어떻게 움직이는지, 한국 개발 환경에서 어떻게 적용할 수 있는지를 정리합니다. 결론을 먼저 말하면, sshc는 모두에게 필요한 도구는 아니지만 config가 손에 벅찰 만큼 커진 사람에게는 분명한 가치가 있습니다.

명령·경로·키 바인딩은 2026-09-29 기준 저장소 README와 CHANGELOG(최신 릴리스 v0.13.1)에 맞췄습니다. 본문 구성은 다음과 같습니다. (1) sshc 개요, (2) 핵심 기능 5가지, (3) 왜 Rust와 TUI인가, (4) 기존 SSH 관리 방법 비교표, (5) 설치 및 시작 가이드, (6) ~/.ssh/config와의 관계, (7) 활용 시나리오 5가지, (8) BrainDetox SSH Config Generator와의 보완 관계, (9) 한국 개발 환경 적용, (10) 위험과 한계, (11) 결론과 즉시 적용 3가지, 그리고 갱신 이력과 참고 자료입니다.

1. sshc란 - Rust TUI SSH 관리자 개요

README의 한 줄 소개는 「Manage and connect to your SSH hosts from a fast Rust TUI」입니다. 풀어 쓰면 "~/.ssh/config와 그 파일이 Include하는 파일을 읽어, 셸 프롬프트 바로 아래에 뜨는 선택기에서 호스트를 골라 접속하게 해 주는 단일 바이너리 TUI 도구"입니다. 핵심 단어는 세 가지입니다. TUI, 단일 바이너리, 그리고 기존 config를 존중하는 구조입니다.

TUI는 Text-based User Interface의 약자로, 그래픽 창이 아니라 터미널 문자 화면 안에서 동작하는 인터페이스입니다. 마우스 없이 키보드만으로 목록을 탐색하고 검색하며 선택합니다. sshc의 기본 모드는 화면 전체를 차지하지 않는 인라인 선택기라서, 고르고 접속한 뒤 셸로 돌아와도 스크롤백이 그대로 남습니다. 추가·편집·삭제가 필요할 때만 sshc -m으로 전체 화면 관리 모드를 엽니다.

단일 바이너리라는 점은 운영 측면에서 결정적입니다. README는 「Single-binary, no daemon」이라고 적고, 최근 릴리스 산출물 크기를 macOS arm64 약 810KB, Linux x64 약 1.16MB, Windows x64 약 1.10MB로 밝힙니다. 인터프리터나 패키지를 깔 필요 없이 실행 파일 하나를 PATH가 잡힌 디렉터리에 두면 됩니다.

마지막으로 sshc는 손으로 쓴 ~/.ssh/config를 선택적인 Include 한 줄 말고는 고치지 않습니다. 관리 모드에서 추가한 호스트는 별도 파일 ~/.ssh/config.d/sshc.conf에만 기록됩니다. 자세한 구조는 6절에서 다룹니다. 참고로 이 프로젝트는 처음(v0.1.0~v0.4.0)에는 이름이 sshs였고, 무관한 다른 CLI와 이름이 겹쳐 v0.4.1에서 sshc로 바뀌었습니다.

2. 핵심 기능 5가지

README가 설명하는 기능을 다섯 가지로 묶어 정리합니다.

2-1) 셸 프롬프트 아래 뜨는 인라인 선택기

sshc만 치면 호스트 목록이 프롬프트 아래에 나타납니다. 관리 모드에서 즐겨찾기(f)로 고정한 호스트와 최근 접속한 호스트가 위로 올라오므로, 자주 쓰는 서버는 「sshc를 열고 엔터」로 끝납니다. 이동은 ↑/↓ 또는 j/k입니다.

2-2) 엔터 한 번 또는 sshc <별칭>으로 바로 접속

선택기에서 엔터를 누르면 ssh 접속이 시작되고, 세션이 끝나면 셸로 돌아옵니다. 별칭을 이미 안다면 sshc <별칭>으로 선택기를 건너뛸 수 있습니다. CHANGELOG에 따르면 이 직접 모드는 config에서 별칭을 찾아 ssh <별칭>을 그대로 실행하고, 없는 별칭이면 ssh를 부르지 않고 종료 코드 1로 끝납니다. 셸 alias나 스크립트에 넣기 좋은 형태입니다.

2-3) / 검색과 @태그 필터

인라인 선택기는 모드가 나뉘어 있습니다. 기본은 이동 모드이고, /를 눌러야 검색 모드로 들어가 글자를 입력해 목록을 좁힙니다. 검색 모드에서 Esc를 누르면 선택기는 연 채로 검색만 빠져나옵니다. 관리 모드의 필터에서는 @prod처럼 @태그로 태그만 골라낼 수 있습니다.

2-4) 관리 모드(sshc -m)에서 추가·편집·삭제

관리 모드는 전체 화면 TUI입니다. a 추가, d 삭제(확인 후), t 태그 편집, e $EDITOR로 해당 줄 열기, v ssh -G <별칭> 결과 보기, c 접속 명령 복사, g 선택 호스트 TCP 도달성 확인, r 전체 호스트 재확인, ? 도움말입니다. 편집 폼에는 LocalForward·RemoteForward·DynamicForward 목록과 여러 개의 IdentityFile 목록을 넣을 수 있습니다(v0.9~v0.12에서 추가).

2-5) 태그와 즐겨찾기로 묶기

그룹은 별도 데이터베이스가 아니라 Host 블록 바로 위의 주석 # @tags: prod, db로 표현합니다. 태그는 config 파일 안에 남으므로 파일을 옮기면 같이 따라갑니다. 여기에 즐겨찾기 고정과 정렬 기준 전환(S: 별칭 → 최근 접속 → 도달성)을 더하면 대규모 목록에서도 탐색이 빨라집니다.

3. 왜 Rust + TUI인가 - 속도·단일 바이너리·크로스플랫폼

sshc가 Rust로 작성되고 TUI 형태를 택한 것은 도구의 목적과 잘 맞는 선택입니다.

3-1) 시작 속도

SSH 관리 도구는 하루에도 수십 번 띄웠다 닫습니다. 시작이 느리면 그 자체가 마찰입니다. 네이티브로 컴파일된 바이너리는 런타임 워밍업이 필요 없어서, 수 초씩 걸리는 무거운 GUI 앱과 대비됩니다. sshc는 화면 구성에 ratatui와 crossterm을, 목록 검색에 nucleo를 씁니다(Cargo.toml).

3-2) 단일 바이너리 배포

데몬이 없고 실행 파일 하나로 끝나므로, 서버마다 인터프리터 버전을 맞출 필요가 없습니다. 여러 환경에 같은 도구를 깔아야 할 때 운영 비용이 크게 줄어듭니다. 폐쇄망 반입에서도 이 특성이 장점이 됩니다(9절).

3-3) 크로스플랫폼

macOS와 Linux 외에 Windows 네이티브 빌드가 v0.7.0부터 나옵니다. Windows는 x64와 ARM64(v0.8부터) zip이 있고, Windows 10 1809 이상 또는 Windows 11과 OpenSSH 클라이언트가 필요합니다. WSL2에서는 Linux 빌드가 그대로 동작합니다. 단 Windows에서는 파일 권한(0600/0700) 검사를 하지 않습니다.

3-4) 메모리 안전과 안정성

SSH 관리 도구는 한 번 설치하면 오래 쓰는 인프라성 도구입니다. Rust는 메모리 안전 버그의 상당 부분을 컴파일 단계에서 걸러 내므로 오래 쓰는 도구의 기반으로 적합합니다. 이 부분이 궁금하다면 이 사이트의 Go에서 Rust로 마이그레이션 완전 가이드 2026도 함께 참고할 만합니다.

5. 설치 및 시작 가이드

주의 - cargo install sshc는 이 도구를 설치하지 않습니다. crates.io의 sshc 이름은 2017년에 올라온 다른 프로젝트(netvl/sshc 1.0.0, SSH 연결·터널 관리자)가 쓰고 있습니다(2026-09-29 기준). 이 글의 sshc는 아래 경로로 설치합니다.

README가 안내하는 설치 경로는 네 가지입니다.

# 1) Homebrew (macOS·Linux) - 새 릴리스는 brew upgrade sshc로 따라감
brew install hang-in/tap/sshc

# 2) cargo로 git 태그에서 설치 (Rust 1.85 이상)
cargo install --git https://github.com/hang-in/sshc --tag v0.13.1

# 3) 소스에서 빌드
git clone https://github.com/hang-in/sshc
cd sshc
cargo install --path .

# 설치 확인과 첫 실행
sshc --version
sshc --doctor
sshc
# 4) Windows (PowerShell) - %CARGO_HOME%\bin에 설치하고 PATH를 갱신
irm https://github.com/hang-in/sshc/releases/latest/download/sshc-installer.ps1 | iex

Windows는 릴리스 페이지의 sshc-x86_64-pc-windows-msvc.zip 또는 sshc-aarch64-pc-windows-msvc.zip을 받아 PATH가 잡힌 디렉터리에 두는 방법도 있습니다. --version(-V)과 --help(-h)는 v0.4.2부터 있습니다.

팁 - 첫 실행 전에 sshc --doctor를 한 번 돌려 보십시오. ~/.ssh, sshc.conf, Include 줄, ssh 바이너리, 에이전트 연결, 새 릴리스 여부를 읽기 전용으로 점검하고 FAIL이 있을 때만 0이 아닌 코드로 끝납니다. 목록이 비어 보이면 config 경로와 권한(Unix에서 600)부터 보면 됩니다.

키 바인딩과 옵션은 버전마다 조금씩 늘어 왔으므로, 설치한 버전의 sshc --help와 저장소 README를 함께 보는 편이 안전합니다.

6. ~/.ssh/config와의 관계 - 읽기와 격리된 쓰기

sshc 설계에서 가장 본질적인 부분이 이 호환성입니다. sshc는 기존 ~/.ssh/config와 그 파일이 Include하는 파일을 읽어 목록을 만듭니다. 아래 같은 평범한 config가 그대로 목록이 되고, Host 위의 # @tags: 주석은 태그로 인식됩니다.

# @tags: prod, web
Host prod-web
    HostName 10.0.1.10
    User deploy
    Port 22
    IdentityFile ~/.ssh/prod_key

Host bastion
    HostName bastion.example.com
    User jump
    Port 2222

# @tags: prod, db
Host prod-db
    HostName 10.0.2.20
    User dbadmin
    ProxyJump bastion

쓰기는 격리되어 있습니다. README가 밝힌 동작은 다음과 같습니다.

  • sshc -m으로 추가한 호스트는 ~/.ssh/config.d/sshc.conf(권한 0600)에만 기록됩니다. 이 파일 첫 줄에는 「Host 블록 안의 수동 편집은 다음 저장 때 덮어쓰일 수 있다」는 안내 주석이 붙습니다.
  • 관리 모드를 처음 열면 ~/.ssh/config 끝에 Include ~/.ssh/config.d/sshc.conf를 붙일지 묻고, 붙이기 전에 날짜가 붙은 백업(.bak.sshc-YYYYMMDD)을 만듭니다. 거절하면 관리 모드는 읽기 전용이 되고 탐색과 접속은 그대로 됩니다.
  • Include 여부와 마지막 접속 별칭, 정렬 기준 같은 상태는 ~/.config/sshc/state.toml에 저장됩니다.

이 구조 덕분에 탈출 비용이 작습니다. sshc를 지워도 손으로 쓴 config는 그대로이고, sshc.conf도 표준 OpenSSH 문법 파일이라 ssh prod-db 같은 명령은 변함없이 동작합니다. 더 쓰지 않을 거라면 Include 한 줄과 sshc.conf, state.toml을 정리하면 됩니다.

도입 전에 cp ~/.ssh/config ~/.ssh/config.bak으로 한 번 더 백업해 두면, 손으로 정리한 주석 구조까지 안전하게 지킬 수 있습니다.

7. 활용 시나리오 5가지

sshc가 가장 빛나는 상황 다섯 가지입니다.

7-1) 다중 서버 운영

수십 대의 서버를 오가는 SRE·인프라 엔지니어에게 검색 기반 빠른 접속은 곧 생산성입니다. /를 누르고 호스트명 일부를 입력해 좁힌 뒤 엔터로 들어가는 흐름이 하루에 쌓이는 마찰을 줄입니다.

7-2) bastion·점프 호스트 환경

ProxyJump로 bastion을 거쳐 내부망에 접근하는 구조에서, config에 ProxyJump를 한 번 정의해 두면 sshc 목록에서 내부 서버를 고르는 것만으로 다단계 접속이 이뤄집니다. sshc는 별칭으로 ssh를 실행하므로 ProxyJump 해석은 OpenSSH가 맡습니다. v로 ssh -G 결과를 보면 실제로 적용된 값을 확인할 수 있습니다.

7-3) 클라우드 인스턴스 관리

AWS·GCP·NCP 인스턴스는 자주 생성·삭제되어 IP가 바뀝니다. config를 갱신하는 워크플로와 결합하면 sshc는 최신 인스턴스 목록을 보는 창이 됩니다. g(선택 호스트)나 r(전체)로 TCP 도달성을 확인하면 사라진 인스턴스를 빨리 가려낼 수 있습니다.

7-4) 팀 단위 config 공유

표준 config 파일이므로 Git 저장소나 팀 문서로 공유하기 쉽고, 태그도 주석으로 파일 안에 남습니다. 팀원이 같은 config(또는 Include로 분리한 조각)를 받아 sshc로 열면 같은 목록을 봅니다. 다만 자격 증명(키 파일)은 공유 대상이 아니라는 점을 분명히 해야 합니다.

7-5) DevOps·CI 점검

배포 직후 여러 노드를 빠르게 점검해야 할 때, 노드별 별칭을 config에 정의해 두면 sshc로 노드를 순회하며 로그를 확인하는 흐름이 매끄럽습니다. 스크립트에서는 sshc <별칭> 직접 모드를 쓰면 됩니다.

8. BrainDetox SSH Config Generator와의 보완 관계

BrainDetox가 제공하는 웹 기반 SSH Config Generator는 sshc와 잘 맞물립니다. sshc가 이미 존재하는 config를 소비(읽고 접속)하는 도구라면, SSH Config Generator는 그 config를 처음 만들어 내는 도구입니다. 둘은 경쟁이 아니라 워크플로의 앞뒤를 담당하는 보완재입니다.

결합 방식은 이렇습니다. 새 서버 환경을 셋업할 때 SSH Config Generator로 HostName·User·Port·IdentityFile·ProxyJump 같은 항목을 폼에서 채워 표준 config 블록을 생성하고, 그 출력을 ~/.ssh/config에 붙여 넣습니다. 그다음부터의 일상 접속은 sshc로 처리합니다. 즉 "생성은 웹 도구, 소비는 TUI"라는 역할 분담입니다. 몇 개만 추가할 때는 sshc -m의 a로 넣어도 되며, 이 경우 항목은 sshc.conf에 들어갑니다.

9. 한국 개발 환경 적용 - 사내망·다중 클라우드

한국 개발 환경에 sshc를 적용할 때의 관점을 정리합니다.

9-1) 사내망과 bastion 패턴

국내 다수 기업은 보안 정책상 내부 서버에 직접 접근하지 못하고 bastion(점프 서버)을 거치게 합니다. 이 환경에서 ProxyJump 기반 config와 sshc의 조합은 잘 맞습니다. bastion을 한 번 정의해 두면 이후 내부 서버 선택만으로 다단계 접속이 이뤄져, 신규 입사자 온보딩 때 "어떻게 접속하느냐"를 설명하는 비용도 줄어듭니다.

9-2) 다중 클라우드(NCP·AWS·온프레미스 혼재)

네이버 클라우드, AWS, 온프레미스 서버가 뒤섞인 환경은 국내에서 흔합니다. config를 환경별로 Include로 분리하고 명명 규칙(ncp-, aws-, onprem- 접두사)이나 # @tags: ncp 태그를 정해 두면, 검색이나 @ncp 필터로 특정 클라우드의 서버군을 바로 좁힐 수 있습니다.

9-3) 도입 시 현실적 고려

현실적 제약은 폐쇄망에서의 설치입니다. 인터넷이 차단된 사내망에서는 Homebrew도 cargo install --git도 막히므로, 릴리스 페이지의 빌드된 바이너리를 반입하는 경로를 미리 확보해야 합니다. 파일 하나만 반입 절차를 통과하면 된다는 점은 장점입니다. 또 sshc --doctor는 새 릴리스 확인을 위해 네트워크에 접속하므로, 폐쇄망에서는 SSHC_NO_UPDATE_CHECK=1을 설정해 그 호출을 건너뛰게 합니다.

10. 위험과 한계

sshc를 도입할 때 알아 둘 한계는 다음과 같습니다.

10-1) Include 한 줄과 sshc.conf 덮어쓰기

sshc가 손으로 쓴 config에 하는 일은 Include 한 줄 추가뿐이지만, 그 한 줄의 위치는 중요합니다. v0.8.4에서 고친 버그로, config가 Host 블록으로 끝나면 끝에 붙인 Include가 마지막 Host 블록 안에 들어가 sshc가 관리하는 호스트가 ssh <별칭>에서 보이지 않던 문제가 있었습니다(OpenSSH는 빈 줄이나 주석으로 Host 블록을 끝내지 않습니다). v0.9부터 --doctor가 이런 중첩 Include와 config의 CRLF를 검사합니다. 또 sshc.conf의 Host 블록 안을 손으로 고치면 다음 저장 때 덮어쓰일 수 있고, M으로 외부 호스트를 sshc.conf로 옮기면 원래 항목은 남아 중복이 생기므로 원하지 않으면 직접 지워야 합니다.

10-2) GUI 기능의 부재

SFTP 파일 브라우징, 세션 녹화, 모바일 접근 같은 풀 GUI 기능은 README 기능 목록에 없습니다. 이런 기능이 핵심이라면 sshc가 아니라 Termius 같은 도구가 맞습니다. sshc는 의도적으로 기능을 줄인 도구입니다.

10-3) 자격 증명은 여전히 별도 관리

sshc는 호스트 목록을 다룰 뿐 키 파일이나 비밀번호를 보관해 주는 도구가 아닙니다. 에이전트는 환경이 제공하는 것(Unix의 SSH_AUTH_SOCK, Windows의 OpenSSH 에이전트나 Pageant)을 씁니다. 키 권한 관리, 키 로테이션 같은 보안 위생은 여전히 사용자 책임입니다.

10-4) 생태계 성숙도와 유지 상태

sshc는 2026년 5월 19일 v0.1.0으로 시작해 6월 26일 v0.13.1까지 약 5주 동안 GitHub 릴리스 24개(v0.2.0~v0.13.1)가 나온 신생 도구입니다. 2026-09-29 기준 마지막 릴리스와 마지막 커밋은 모두 2026-06-26이고, CHANGELOG의 Unreleased 항목은 비어 있으며, 저장소는 보관(archived) 상태가 아닙니다. 버전에 따라 키 바인딩과 동작이 바뀌어 왔으므로, 업무 워크플로에 깊이 엮기 전에 README와 CHANGELOG를 보고 핵심 동작인 "표준 ssh 호출"이 유지되는지를 기준으로 판단하는 편이 좋습니다.

11. 결론 + 즉시 적용 가능한 3가지

sshc를 한 문장으로 요약하면 이렇습니다. "손으로 쓴 ~/.ssh/config는 그대로 둔 채, 그 위에 빠른 검색과 즉시 접속이라는 얇은 레이어를 얹고, 새 항목은 별도 파일로 격리하는 도구." 모두에게 필요하지는 않지만, config가 손에 벅찰 만큼 커진 사람에게는 마찰을 눈에 띄게 줄여 줍니다. 바로 적용할 수 있는 세 가지입니다.

11-1) 즉시 적용 1: config 백업 후 한 번 실행해 보기

먼저 cp ~/.ssh/config ~/.ssh/config.bak으로 백업한 뒤 Homebrew나 cargo install --git으로 설치하고 sshc --doctor, sshc 순서로 띄워 보십시오. 기존 호스트가 그대로 목록에 나타나는 것만으로도 도구의 가치를 가늠할 수 있습니다.

11-2) 즉시 적용 2: 명명 규칙과 태그로 묶기

호스트 별칭에 환경·클라우드 접두사(prod-, dev-, ncp-, aws-)를 붙이고, Host 위에 # @tags: 주석을 달아 두면 검색과 @태그 필터가 곧 그룹 필터가 됩니다. 작은 규칙 하나가 수십 개 호스트의 탐색 비용을 크게 낮춥니다.

11-3) 즉시 적용 3: 생성은 웹 도구, 소비는 sshc로 분업

새 config 블록은 BrainDetox SSH Config Generator로 폼에서 만들어 붙여 넣고, 일상 접속은 sshc로 처리하는 분업 워크플로가 가볍습니다. 생성과 소비를 분리하면 config 관리가 한결 단순해집니다.

마지막으로 강조할 메시지는 이것입니다. 좋은 도구는 표준을 대체하지 않고 표준 위에 얇게 얹힙니다. sshc가 매력적인 이유는 화려한 기능이 아니라, OpenSSH라는 검증된 표준을 존중하면서 가장 잦은 작업의 마찰만 덜어 주기 때문입니다.

# sshc 도입 점검표 - 설치·설정 파일·키

기준일: 2026-09-29.
명령·경로·키는 저장소 github.com/hang-in/sshc 의 README·CHANGELOG(최신 릴리스 v0.13.1, 2026-06-26)에 맞춘 값이다. 버전이 바뀌면 `sshc --help` 와 README를 다시 볼 것.

## 1. 설치 경로 고르기

| 환경 | 명령 | 조건 |
|---|---|---|
| macOS·Linux | `brew install hang-in/tap/sshc` | Homebrew. 업데이트는 `brew upgrade sshc` |
| Rust 툴체인 있음 | `cargo install --git https://github.com/hang-in/sshc --tag v0.13.1` | Rust 1.85 이상 |
| 소스 빌드 | `git clone` 후 `cargo install --path .` | Rust 1.85 이상 |
| Windows | `irm https://github.com/hang-in/sshc/releases/latest/download/sshc-installer.ps1 \| iex` | Windows 10 1809+ 또는 11, OpenSSH 클라이언트 |
| 폐쇄망 | 릴리스 페이지의 빌드된 바이너리·zip 반입 | `SSHC_NO_UPDATE_CHECK=1` 설정 |

- [ ] `cargo install sshc` 를 쓰지 않는다 (crates.io의 `sshc` 는 2017년의 다른 프로젝트 netvl/sshc)
- [ ] 설치 뒤 `sshc --version` 으로 버전 확인
- [ ] `sshc --doctor` 로 `~/.ssh`·sshc.conf·Include 줄·ssh 바이너리·에이전트 점검 (FAIL일 때만 0이 아닌 종료 코드)

---

## 2. 도입 전 점검

- [ ] `cp ~/.ssh/config ~/.ssh/config.bak` 으로 백업
- [ ] config가 Host 블록으로 끝나는지 확인 (끝에 붙은 Include가 마지막 Host 블록 안으로 들어가던 버그는 v0.8.4에서 수정, v0.9부터 `--doctor` 가 검사)
- [ ] config 줄바꿈이 CRLF가 아닌지 확인 (v0.9부터 `--doctor` 가 검사)
- [ ] Unix에서 config 권한 600 (Windows는 권한 검사 안 함)
- [ ] 태그를 쓸 거라면 Host 바로 위에 `# @tags: prod, db` 형식 주석

---

## 3. sshc가 만들고 건드리는 파일

| 파일 | 내용 | 언제 |
|---|---|---|
| `~/.ssh/config` | `Include ~/.ssh/config.d/sshc.conf` 한 줄만 추가 | 관리 모드 첫 실행 때 묻고, 동의하면 |
| `~/.ssh/config.bak.sshc-YYYYMMDD` | 위 추가 전 백업 | Include 추가 직전 |
| `~/.ssh/config.d/sshc.conf` | `sshc -m` 으로 추가한 호스트 (권한 0600) | 관리 모드에서 저장할 때 |
| `~/.config/sshc/state.toml` | Include 여부, 마지막 접속 별칭, 정렬 기준 | 실행 중 |

- [ ] sshc.conf의 Host 블록 안은 손으로 고치지 않는다 (다음 저장 때 덮어쓰일 수 있음)
- [ ] `M` 으로 외부 호스트를 옮긴 뒤 원래 항목을 지울지 결정 (자동으로 지우지 않음)
- [ ] 제거할 때: Include 한 줄, sshc.conf, state.toml 정리

## 4. 키 요약

| 모드 | 키 | 동작 |
|---|---|---|
| 인라인 (`sshc`) | ↑/↓, j/k | 이동 |
| 인라인 | `/` | 검색 모드 (Esc로 검색만 빠짐) |
| 인라인 | Enter | 접속 후 셸로 복귀 |
| 인라인 | q, Esc / Ctrl+C | 종료 |
| 직접 (`sshc <별칭>`) | - | `ssh <별칭>` 실행, 없는 별칭은 종료 코드 1 |
| 관리 (`sshc -m`) | a / d / t / f | 추가 / 삭제 / 태그 / 즐겨찾기 |
| 관리 | v / c | `ssh -G` 결과 / 접속 명령 복사 |
| 관리 | g / r | 선택 호스트 / 전체 TCP 도달성 확인 |
