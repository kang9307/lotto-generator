引言: 转写稿总在同一处出问题

把录好的会议丢进自动转写的人，都会在结果里看到同一种模式。普通句子干净得出乎意料。可一旦碰上英语技术词后面接着本地语词尾的那种句子，就突然乱套。merge 变成别的词，rollback 消失，运气差时整个分句都不见了。

识别器并不是不懂那门语言。它是在一句话内部语言发生切换的地方塌掉的。而韩国的开发与业务场景，每天要越过这个点几百次。

KRAFTON 公开的 A.X K2 Raon-Speech-21B-A3B 正面瞄准的就是这里。它以 SK 电讯的 A.X K2 Light 20B-A3B 文本骨干为底，叠上自行训练的语音编码器与语音编解码器，构成一个韩英双语语音模型。总量约 21.2B，活跃约 3.5B。

先把判断写出来。这次公开的价值不在排行榜名次，而在于把语言边界处理写进设计目标的语音模型，以开放形态出现了。而这份价值因为许可里的一行字，当下只能在研究和验证环节兑现。CC BY-NC 4.0，非商业。

本文先把边界问题拆开，再看模型拼装了什么、21.2B 这个规模在语音任务上到底让人付出什么代价，最后落到什么活该看它、什么活留在商用 API 上。至于已经存在的语音合成模型该用哪些镜头去量，那是另一件事，写在用三种镜头比较 55 款本地 TTS 的基准里。这里谈的不是测量，而是一个新拼装物的设计。

1. 塌掉的不是语言，是边界

说韩语语音处理难，这话太钝，落不到手上。真正难的是几条具体的边界。

  • 语言边界。一句话里韩语和英语来回切，而且多半是单个词的粒度
  • 语素边界。黏着语让助词和词尾一串接在词干后面，分词单位和意义单位对不上
  • 书写边界。同一个音写成谚文还是拉丁字母，取决于文档惯例
  • 语体边界。句尾一个词尾就改变整句的正式程度，两种敬语在声音和用法上都不同

其中最贵的是第一条。为衡量韩英混用而建的 HiKE 基准把混用程度分成词、短语、句子三级来标注。之所以要分三级，是因为每一级的难度不同。句子级混用可以切开分别处理，词级混用根本无处可切。

该论文的结论很冷静。多数多语言语音识别模型在混用语音上的初始表现并不足够，这项能力要靠合成的混用数据微调才会出现。换句话说，用多语言训练过，并不等于自动学会听懂两种语言编织在一起的话。分别懂几门语言，和一口气听清两门语言，是两种能力。

1.1 黏着语让边界更模糊

韩语词尾接到英语词干上的那一刻，问题又深一层。表示已合并、虽然部署了、必须回滚的那些形态里，一个词里装着两种语言。要在这里分开语言，就得下到比词更小的单位，而在那个粒度上语言识别器已经没用了。

如果是英语和西班牙语这种谱系接近、形态学相仿的组合，问题会浅得多。韩语和英语在语序、形态、音系上都很远。这既是数据稀缺的原因，也是这一语言对需要专门模型的理由。

2. 外来词和语码转换是两回事

把这两者混为一谈，评测在建模之前就已经坏了。用中文类比，就是「我用 React 写的」里那个词到底算什么。

类型例期望输出为何分叉
已定型的外来词电脑、巴士、项目本地文字写法是标准，写成拉丁字母反而别扭
技术专有名词React、Kubernetes、PostgreSQL文档惯例是拉丁字母，转成本地文字就搜不到
仍在摇摆的中间层Docker、Slack同一个组织内部写法都不统一
真正的语码转换这个已经 deprecated 了把英语词写成英语几乎是唯一正解
混合词形merge 完了、commit 过了一个词内部的书写基准互相冲突

HiKE 之所以把外来词标注单列在混用级别标注之外，正是因为表里第一行和第四行不能用同一把尺子量。把定型外来词写成拉丁字母，和把真正的英语词揉成本地文字，是性质完全不同的错误，可一旦压成单一的词错误率，两者都只是各扣一分。

由此可以给实务者一条判断。在混用环境里挑语音识别器，只看一个公开的错误率数字几乎什么都得不到。更快的办法是自己做一份把本组织书写惯例当作标准答案的小评测集。三十分钟会议录音就够，里面已经包含了你们实际在用的全部术语。

3. 数词、单位、敬语 - 答案不唯一的地方

文本规范化在语音的两个方向上疼法不同。

识别方向上，一个音对应多种写法。念出来的日期可以写成 2026-08-05，也可以写成 2026 年 8 月 5 日，还可以按读音展开。哪个正确取决于这段文本要去哪里。要进日历就必须是数字，做字幕时照读音写反而更合适。

合成方向上正好相反，一种写法对应多个读音。韩语数词分固有词和汉字词两套，后面跟的量词决定用哪一套。中文读者能感受到的近似情形，是「一」在不同词里读法和声调都会变。

  • 3 点 20 分里，小时用固有词系，分钟用汉字词系，一口气切换两套
  • 3 个用固有词系，3 号用汉字词系，同一个数字读法就分叉
  • 1,200 韩元按数量读，电话号码里的 1200 要一位一位读
  • 3.5B 可以读成三点五 B，也可以按十亿量级读，没有上下文就定不了
  • 80GB 有的团队读作吉字节，有的团队直接读两个字母

敬语又是另一层。识别方向上，句尾漏掉一个音节就改变整句的语体。合成方向上，同一句话用郑重体读和用柔和敬体读，语调曲线本身就不同。英语语音合成里礼貌主要体现在词汇选择，韩语则同时接在语法和韵律上。

这些条目之所以重要，是因为它们属于规模解决不了的那一类问题。参数翻十倍，3.5B 该怎么读的答案依然在组织内部。规模解决的是从声音里取出语言这件事，这类条目属于其后的约定层。

4. 双语单模型与两个模型拼接的分水岭

这是本文的核心。为什么不各取两种语言最强的模型，前面放个语言识别器就行？答案不是行不通，而是切换粒度太粗，跟不上真实语流。

比较维度单语模型 + 语言识别双语单一模型
最小切换单位整段话或整句在词元级别连续
混合词形无处可送在同一表示空间内处理
上下文连续性换模型时上下文断掉保持同一份上下文
延迟多出识别等待与切换开销没有切换开销
运维复杂度两个模型加识别器加路由规则一个模型
单语言峰值质量可以直接用各语言最强模型共享容量带来取舍
内存两个模型同时常驻一份权重

最后两行是诚实的代价。而这次公开把这份代价以数字形式留在了自家材料里。模型卡的综合排名表中，A.X K2 Raon-Speech 韩语 0.72 排第一，英语 0.75 排第三。同一张表里另有一个名为 Raon-Speech 的模型，韩语 0.70、英语 0.79，英语排第一。

模型卡没有说明两者的谱系关系，所以不能下断言，但表格呈现的对比很清楚。韩语抬高 0.02 的同一处，英语下降了 0.04。这就是双语整合的价钱，也是挑多语言模型时必须去找的那一行。只读到综合第一就翻页，等到自己的负载偏英语时，就不知道自己放弃了什么。

4.1 流水线失去的不只是准确率

把语音对话排成语音活动检测 → 语音识别 → 文本对话 → 语音合成的做法用了很久，如今许多产品仍靠它运转。Moshi 论文把这种方式的问题归为两点。一是交互之间会产生数秒的延迟，二是经过文本这一道，情绪、非语言声响这类会改变含义的信息被丢掉了。

第二点更重。一个单音节的应答，凭语调可以是同意、是反问、也可以是放弃。一旦落成文本，这个信息就再也找不回来。语音直通语音的模型之所以必要，理由更靠近这里而不是准确率。

5. A.X K2 Raon-Speech 拼装了什么

这个模型不是从零全做的。它是把别人的部件和自家部件分开使用的拼装物，而这条界线在模型卡里写得很清楚。

5.1 编解码器到底是干什么的部件

在语音语言模型里，编解码器负责把声音变成模型能处理的离散词元。它在音频上做的事，相当于分词器在文本上做的事。作为参考的 Mimi 把 24kHz 音频压到每秒 12.5 个表示、1.1kbps 带宽，并以完全流式方式运行，延迟为与帧长相等的 80ms。

每秒帧数为何重要，到这里就显出来了。帧周期就是响应延迟的下限。每秒 12.5 帧意味着一帧 80ms，硬件再快也压不到它以下。反过来提高帧率能缩短延迟，但语言模型要处理的词元也按比例增加。语音模型设计中最赤裸的一次交换就在这里。

6. 21.2B 却活跃 3.5B - 规模与实时性的交换

这两个数字必须并排读。总量约 21.2B，活跃约 3.5B。在专家混合结构里，每个词元点亮 128 个专家中的 8 个。

这种结构给什么、不给什么，界线很清楚。

  • 给。运算量在 3.5B 级别，单词元处理时间远低于稠密的 21.2B 模型
  • 给。知识容量来自完整的 21.2B，不同专家可以装不同的东西
  • 不给。内存按总规模计，不知道哪个专家会点亮，只能全部常驻
  • 不给。批处理效率不如稠密模型干净，不同请求点亮的专家不同

模型卡的运行要求直接印证了这一点。BF16 权重约 42.4GB，需要一张 80GB 显卡或多卡配置；vLLM-Omni 路径下单卡需要约 96GB 显存。同时标注的条件是张量并行 1、最大上下文 4,096、批词元 4,096。

归纳一句：质量按 21.2B 买，速度按 3.5B 买，账单按 21.2B 结。换个说法，这不是拿个人设备跑着玩的东西。

实时语音里真正的延迟来自哪里。决定对话质感的不是总吞吐，而是第一声出来之前的时间。Moshi 论文报告理论延迟 160ms、实测 200ms。人类自然对话的换轮间隔就在这一带，所以这个数字常被当作基线。如何把延迟拆成几段再据此选模型，写在快模型胜出的那一段区间里。

编解码器这张表是本次公开最值得读的地方。信号保真度指标 PESQ 掉到 83.5%，而经过编解码器的韩语语音识别却升到 112.6%。方向相反的两个数字出现在同一张表里。

这不是缺陷，应当读作有意的折中。语音语言模型里编解码器的目的不是原样还原波形，而是在保住语言信息的前提下压缩词元数量。往保语言、舍保真的方向调，得到的正是这个形状。同时这张表也画出了边界：不要把这个编解码器挪去做音乐或通用音频压缩。那些用途看重的恰恰是被削掉的那一侧。

8. 权重开放，许可关闭

模型卡上写的许可是 CC BY-NC 4.0。NC 意为非商业。能下载权重和能装进产品，是完全不同的两句话。

这里指出一个真正容易出事的地方。同一张卡也提到 Apache License 2.0，但明确写着适用范围仅限随附的 A.X K2 Light 实现代码。代码是 Apache，不代表权重能商用。做骨干的 SK 电讯那边的开放方针，和这个语音模型的开放方针，是两码事。

  • 权重 — CC BY-NC 4.0，非商业条件
  • 随附的骨干实现代码 — Apache 2.0，仅在该范围内
  • 说话人同意 — 卡片写明，涉及可识别说话人的声音条件化或生成，取得同意的责任在使用者
  • 官方声明用途 — 双语语音识别与生成、音频理解、语音助手研究，全部在非商业范围内

第三条的分量与许可无关。说话人条件合成能从一小段参考音频里迁移特定人的音色，而这个模型明确提供了该 API。技术上做得到与法律上做得的之间，这个功能的落差最大。中文互联网上关于配音演员声音被未经许可克隆的争议已经反复出现过，这个落差在合规之前，先是行业信任的问题。

开放权重这个词实际覆盖多少层次，之前在写 Krea 2 开放权重图像模型时整理过一次。这次是同一个陷阱。有下载按钮这件事，对许可什么都没说。

9. 什么活该看它，什么活商用 API 更划算

把判据压成一句：眼下压着营收就用商用 API，处于验证与学习阶段就值得折腾这个。许可已经把线画好了，其实没多少可纠结的。

场景选择理由
想自己实测韩英混用识别效果这个模型针对混用而造的公开模型很少
语音对话智能体原型这个模型识别、合成、对话在同一个模型里
数据不出域环境下的先期验证这个模型可以本地部署，但商用转化是另一回事
研究编解码器或编码器本身这个模型部件级相对性能已公开
放进面向客户的服务商用 API非商业许可，根本不成立
实时通话字幕商用 API需要流式、断线重连、部分结果
需要说话人分离和时间戳商用 API模型卡没有提到相关功能
没有 80GB 级显卡商用 API光权重就有 42.4GB

补一句表里放不下的话。开放权重语音模型真正的成本不是显卡，而是它周边的一切。说话人分离、标点还原、术语词表、部分结果流式输出、断线续传、长音频切分与拼接。商用语音 API 卖的东西里，一半以上是这份清单而不是模型本身。白拿到模型，这份清单还得自己造，而那通常更费时间。

10. 在语音 AI 版图中的位置

关于版图，这次公开里能确认的事实有三条。

  1. 文本骨干是 SK 电讯的 A.X K2 Light，语音编码器和编解码器是 KRAFTON 自训。一家韩国机构在另一家韩国机构的骨干上叠了语音层
  2. 比较表里有 Naver 的 HyperCLOVA X 8B Omni，韩语综合 0.60，意味着韩语全模态模型之间已经可以互相对照
  3. 同一张表里 Qwen3-Omni 以韩语 0.65 排第三。在韩语性能上，中国的开放模型已经是直接的比较对象

第三条的实务含义最重。母语所以本国模型当然更强，这个假设现在已经被表格反驳。0.65 和 0.72 的差距是实在的，但为了这个差距去接受非商业许可，是另一笔账。对中文读者来说，同一种读法可以原样搬到中文全模态模型上：本国语言就用本国模型，从此是需要用表格验证的假设，而不是前提。

用角色配音或 NPC 对话来解释游戏公司为何发布语音模型，是很自然的联想，但公开材料里没有可以确认的说法，因此本文只把它留作推测。模型卡明示的用途是双语语音识别与生成、音频理解、语音助手研究。

追着模型名字和排名跑为什么大多是亏本买卖，写在别去背所有 AI 模型名字里。这次也一样，该记住的不是名字，而是部件构成和两行许可。掌握这两样，半年后出现的下一个模型也能用同一种读法读懂。

11. 未能确认的部分

以下条目找不到可指认的一手依据，因此本文没有把它们当作数字或断言使用。

  • 绝对错误率。公开的综合分是归一化到 0 到 1 的合算值，单个数据集上的词或音节错误率不在卡上
  • 46 个基准的具体构成。只能确认数量为韩语 24 个、英语 22 个，具体是哪些数据集无法核对
  • 实测延迟与实时系数。文中的 160ms、200ms、80ms 属于 Moshi 与 Mimi，不是这个模型的值。卡上没有本模型的延迟数字
  • 比较表里的 Raon-Speech 是什么。只能确认名字和分数，与本模型的谱系关系、规模、训练条件都无法核实，因此只引用了韩英分数的对比
  • 语码转换专项性能。卡上没有 HiKE 这类混用专项基准的结果。为混用而设计，和混用性能被测量过，是两回事
  • 商用许可能否另议。公开文档里没有找到单独的商用许可路径
  • 说话人分离、时间戳、术语词表。不在支持任务列表里，无法判断是不支持还是只是没写进文档

结论: 别看那两个名字，去看那两张表

这次公开里能留下来的不是名次。是把句中韩英混用写进设计目标的语音模型以开放形态出现了，而且这次尝试的代价以数字形式留在了同一份文档里。韩语抬高 0.02 的地方英语降了 0.04。原样公开这种表格的一方，比藏起来的一方更值得信。

所以留给要看这个模型的人两样东西。一是编解码器那张表。PESQ 被削、韩语识别升高的那个形状，比任何文字都更准确地说明了这个部件的性格。它是语音语言模型用的零件，不是音频压缩器。二是许可的那一行。没看清 CC BY-NC 4.0 就放上路线图，后面没有退路。

再留一件今天就能做的事。用本组织三十分钟会议录音做一份小评测集。你们实际在用的英语术语全在里面，书写惯例也早就定下来了。那一份评测集对采纳决策的说明力，胜过别人的 46 个基准。附带的好处是模型换了评测集还在，而这个附带好处通常比本金更值钱。
