sed -i はインプレース編集ではない — 一括置換前のプレビュー・バックアップ・diff 手順

ファイルID変化・ハードリンク切断・CRLF改行変更の実測と安全な置換手順

2026-09-29 開発・インフラ

数多くの自動化スクリプトやデプロイパイプラインにおいて、設定ファイルのテキストを書き換える際に最も頻繁に呼び出されるコマンドが sed -i である。オプション名が --in-place であるため、多くのエンジニアはこのコマンドがディスク上の元ファイルを直接開き、そのデータブロックをインプレースで上書き更新するものと期待しがちである。しかし、実際の実行測定結果および公式マニュアルが示す事実は正反対である。sed -i は元ファイルを直接改変するツールではなく、新しい一時ファイルを生成して置換結果を書き込み、元ファイル名へと差し替えるファイル置換ツールである。

この差し替えの仕組みを知らずに一括置換を行うと、予想外の結果になる。ハードリンクでつながっていたもう一方の名前には変更が届かず、ファイル ID も変わる。とりわけ Windows の Git Bash では、置換パターンが1件も一致しないファイルまで改行が CRLF から LF に変わり、触っていないファイルが変更として現れる。本稿は実際の実行記録でこの差し替えの結果を示し、一括置換の前に踏むべき 5 段階の手順を整理する。

本分析は以下の環境において直接実行し記録された実測データに基づいている：Windows 10 Pro 10.0.19045、Git Bash (GNU sed 4.9、GNU Awk 5.0.0)、curl 8.12.1 (Schannel)、git 2.48.1.windows.1、Windows PowerShell 5.1、Python 3.13.3、Node 22.16.0 (管理者権限なし)。改行コードの一般的な背景については CRLFとLF ガイド を、シェル引用符の展開規則は シェル引用規則ガイド を、正規表現の互換性は 正規表現互換性ガイド を、スクリプトの冪等性設計は 冪等性スクリプト設計ガイド をそれぞれ参照されたい。

1. sed -i の動作原理 — なぜ直接編集ではなく新規ファイル置換なのか

オプション名である -i は英語の in-place に由来する。利用者は言葉通りに対象ファイルの該当箇所だけが書き換わると誤解しやすいが、その内部アーキテクチャは根本的に異なる。ストリームエディタとして誕生した sed は、標準入力からテキストを1行ずつパターン空間へ読み込んで編集し、標準出力へと排出するフィルタ処理を基本構造としており、ファイルストレージ上の特定バイト位置へシークして上書きするようには設計されていない。

一時ファイル生成と rename 置換の仕組み

GNU sed マニュアルの Command-Line Options 項は -i の動作を次のように説明している。GNU sed は出力を標準出力ではなく一時ファイルへ送り、ファイル終端に達するとその一時ファイルの名前を元のファイル名に変更する。

つまり元ファイルのデータをその場で書き換えるのではなく、新たに書かれたファイルが元の名前を引き継ぐ構造である。バックアップ拡張子を指定すると (-i.bak)、変更前の内容が app.conf.bak のように拡張子付きの名前で残る (6 章の実行結果)。この差し替えがハードリンクや改行とどう絡むかは、以下の実行結果が示す。

リダイレクト上書き (>) との本質的な相違

シェルで printf 'y\n' > keep.txt のようにリダイレクトで上書きすると、同じファイルに新しい内容が書き込まれる。実行では keep.txt の inode 番号は上書きの前後で同じだった。これに対し sed -i は新しいファイルに差し替えるので番号が変わる。この違いがハードリンクと改行でどのような結果になるかを次章の実行結果で見る。

2. 実測検証: ファイルIDの変化とハードリンク切断の実態

この置換処理が実際のオペレーティングシステム上でどのような現象として現れるかを、具体的なコマンドと実行出力により検証した。

inode および NTFS ファイル ID の変更実測

Git Bash 環境においてテスト用設定ファイル conf.txt を作成し、sed -i の実行前後における inode 番号および Windows NTFS ファイル ID を stat と fsutil コマンドで計測した。

printf 'host=old.example\nport=80\n' > conf.txt
ls -i conf.txt; stat -c 'ino=%i links=%h mtime=%y' conf.txt
sed -i 's/old/new/' conf.txt
ls -i conf.txt; stat -c 'ino=%i links=%h mtime=%y' conf.txt
# 比較: > で上書き
printf 'x\n' > keep.txt; ls -i keep.txt; printf 'y\n' > keep.txt; ls -i keep.txt
# Windows ファイル ID
fsutil file queryfileid conf.txt; sed -i 's/new/newer/' conf.txt; fsutil file queryfileid conf.txt

実際のターミナル出力は以下の通りである：

ino=57702370226752894 links=1 mtime=2026-09-29 07:44:07.786669900 +0900
=== after sed -i
314689023964208355 conf.txt
ino=314689023964208355 links=1 mtime=2026-09-29 07:44:08.149979700 +0900
host=new.example
port=80
=== compare: in-place write via > redirect keeps id?
57983845203463550 keep.txt
57983845203463550 keep.txt
=== fsutil file id (before)
ファイル ID: 0x0000000000000000045e00000019dce3
=== fsutil file id (after sed -i)
ファイル ID: 0x000000000000000000230000001f9069

置換前、conf.txt の inode 番号は 57702370226752894 であったが、sed -i の実行直後に 314689023964208355 へと切り替わった。fsutil で確認した NTFS ファイル ID も 0x0000000000000000045e00000019dce3 から 0x000000000000000000230000001f9069 へと完全に更新されている。一方でリダイレクト (>) によって上書きされた keep.txt は、2回の上書き作業を経ても 57983845203463550 の同一番号を維持した。すなわち sed -i は完全に別個の新規ファイルへと差し替えられていることが証明された。

ハードリンクの同期切断実験

同一のファイル実体を指すハードリンクが存在する状態で sed -i を実行した場合の挙動を追跡した。

printf 'a=1\n' > orig.txt; ln orig.txt hard.txt
stat -c '%n ino=%i links=%h' orig.txt hard.txt
sed -i 's/1/2/' orig.txt
stat -c '%n ino=%i links=%h' orig.txt hard.txt
echo "orig: $(cat orig.txt) / hard: $(cat hard.txt)"

出力結果は以下の通りである：

orig.txt ino=314970498940919011 links=2
hard.txt ino=314970498940919011 links=2
orig.txt ino=28147497673134196 links=1
hard.txt ino=314970498940919011 links=1
orig: a=2 / hard: a=1

当初、双方のファイルは inode 314970498940919011、リンク数 2 として完全に同期していた。しかし orig.txt に対して sed -i を実行した瞬間、orig.txt は新しい inode (28147497673134196) を持つ単独ファイル (links=1) へと分離された。その結果、orig.txt は a=2 へと変更されたものの、hard.txt は過去の inode のまま取り残され a=1 を保持し続けた。ハードリンクによって同期維持されていた構成が静かに崩壊したのである。

3. 改行コードの落とし穴: 置換対象0件でもCRLFがLF化する現象

Windows で作業するときによくある事故の一つが、改行コードの意図しない一括変換である。Git Bash の GNU sed にはこの点で落とし穴がある。以下は CRLF ファイルに sed を実行した結果である。

Git Bash sed の CR 無視挙動と -b オプション

CRLF 改行コードを持つファイルを対象に置換処理を行い、od -c コマンドを用いてバイト単位のダンプを確認した。

printf 'line1=a\r\nline2=b\r\n' > crlf.txt
file crlf.txt; od -c crlf.txt
sed -i 's/a/A/' crlf.txt
file crlf.txt; od -c crlf.txt
sed -i -b 's/a/A/' crlf_b.txt; file crlf_b.txt; od -c crlf_b.txt      # -b(binary)
sed 's/a$/Z/' crlf_c.txt | od -c | head -2                           # $ アンカー
sed 's/\r$//' crlf_c.txt | od -c | head -2
printf 'p=a\r\n' | sed 's/a$/Z/' | od -c                               # パイプでも

実際のターミナル出力は以下の通りである：

=== CRLF before
crlf.txt: ASCII text, with CRLF line terminators
0000000   l   i   n   e   1   =   a  \r  \n   l   i   n   e   2   =   b
0000020  \r  \n
=== after sed -i 's/a/A/'
crlf.txt: ASCII text
0000000   l   i   n   e   1   =   A  \n   l   i   n   e   2   =   b  \n
=== sed -i -b (binary)
crlf_b.txt: ASCII text, with CRLF line terminators
0000000   l   i   n   e   1   =   A  \r  \n   l   i   n   e   2   =   b
0000020  \r  \n
=== $ anchor test: s/a$/Z/ on CRLF
0000000   l   i   n   e   1   =   Z  \n   l   i   n   e   2   =   b  \n
=== s/\r$// strip
0000000   l   i   n   e   1   =   a  \n   l   i   n   e   2   =   b  \n
(パイプ) 0000000   p   =   Z  \n

測定結果から2点が分かる。第1に、Git Bash の sed はキャリッジリターン (CR, \r) を見ない。そのため末尾アンカー $ が CR の前でも一致した (a$ が a\r の行に一致して Z に置換)。第2に、sed -i 1回で置換のなかった line2 行まで CR が消え、ファイル全体の改行が LF になった。-b (--binary) を付けると CRLF はそのまま残った。GNU sed マニュアルは、MS-DOS、Windows、Cygwin のようにテキストファイルとバイナリファイルを区別する環境ではテキストの行が CR と LF で区切られ、sed は行末の CR を見ないと記し、--binary はそうした区別がある OS でのみ効果があると記している。したがってこの結果は Windows (MSYS) ビルドの挙動である。Linux の GNU sed でも同じかどうかは 8 章に記した。

一致箇所が 0 行のファイルにおける強制改行変換実測

置換対象の文字列が全く存在しないファイルに対して sed -i を実行した際の結果は極めて深刻である。

printf 'x=1\r\ny=2\r\n' > nomatch.txt
stat -c 'ino=%i' nomatch.txt; sed -i 's/ZZZ/QQQ/' nomatch.txt; stat -c 'ino=%i' nomatch.txt; file nomatch.txt

出力結果：

ino=153685337286086914
ino=10977524093784323
nomatch.txt: ASCII text

一致する行が1行もなかったのに、inode は 153685337286086914 から 10977524093784323 に変わった。printf で CRLF を入れて作ったファイルが、file では ASCII text と表示された (with CRLF line terminators の表示なし)。つまり改行が LF になった。多数のファイルに一度に sed -i をかけると、変更の必要がなかったファイルまで改行が変わり、置換していないファイルが git diff にすべて変更として現れる。

表 2. Windows Git Bash 環境における CRLF ファイルに対する sed 挙動と改行保持実測表
実行コマンド 置換対象の有無 改行コード変化 inode 変化有無 実務上の影響
sed -i 's/a/A/' file あり (1件) CRLF → LF (全行) このファイルでは未計測 未変更行の CR も一括消去
sed -i -b 's/a/A/' file あり (1件) CRLF 保持 このファイルでは未計測 -b で CRLF を維持
sed -i 's/ZZZ/QQQ/' file なし (0件) CRLF → LF (全行) 変更あり (新規ファイル) 一致 0 件でもファイル置換と LF 化が発生

4. オプション結合の誤りと空ファイル惨事: -iE と -n -i

コマンドライン引数の指定方法においても、引数を伴うフラグの結合規則を見落とすと致命的な誤動作を引き起こす。

-iE がバックアップ拡張子 E と解釈される罠

拡張正規表現 (ERE) を有効化する -E オプションとインプレース編集の -i オプションをまとめて記述する際、順序を取り違えた場合の実測を行った。

printf 'a=1\n' > ie.txt
sed -iE 's/(a)=1/\1=2/' ie.txt; echo "exit=$?"; ls ie.txt*
sed -Ei 's/(a)=1/\1=2/' ie.txt; cat ie.txt
sed -iE 's/a=2/a=3/' ie.txt; ls ie.txt*; echo "ie.txt: $(cat ie.txt) / ie.txtE: $(cat ie.txtE)"
printf 'k1\nk2\n' > n.txt; sed -n -i 's/k1/K1/' n.txt; echo "size after: $(wc -c < n.txt)"

実際のターミナル出力は以下の通りである：

sed: -e expression #1, char 13: invalid reference \1 on `s' command's RHS
exit=1
ie.txt
---
a=2
exit=0
ie.txt
ie.txtE
ie.txt: a=3 / ie.txtE: a=2
size after: 0

GNU sed のマニュアルに規定されている通り、-i の直後に空白を置かずに続く文字はすべてバックアップ拡張子の文字列として構文解析される。したがって -iE は拡張正規表現を有効にするのではなく、--in-place=E として解釈され、拡張子 E を持つバックアップファイルを作成しようとする。その結果、正規表現エンジンは基本正規表現 (BRE) のまま動作するため、(a) グループキャプチャが無効化されて invalid reference \1 エラーとなる。グループを用いない単純置換ではエラーすら出ず、静かに ie.txtE という不要ファイルが作られる。必ず -Ei または -E -i と書かなければならない。

-n と -i 併用による 0 バイト消滅事故

さらに危険な過失は、変更行をプレビューするために使っていた -n フラグを残したまま -i を追加し、出力指示子 p をつけ忘れるケースである。上記の実行出力末尾が示す通り、sed -n -i 's/k1/K1/' n.txt を実行した直後、ファイルサイズは 0 バイトへと消滅した。-n が自動出力を抑制し、何も書き出されないまま新規ファイルで置き換えられたためである。バックアップもないため、ファイル内容はそのまま失われた。GNU sed マニュアルも、-n は自動出力を止め -i はバックアップなしでファイルを書き換えるので、両者の併用には注意するよう記している。

表 3. オプション結合手法の違いによる sed 実行結果と危険度分析
オプション指定 パーサーによる実際の解釈 実行結果 危険度分類
-iE --in-place=E (バックアップ拡張子 E) ERE 無効エラーまたは .txtE 生成 警告 (意図と異なる動作)
-Ei または -E -i ERE 有効化 + インプレース置換 正常な正規表現置換の実行 安全 (推奨される構文)
-n -i (p なし) 出力抑止 + インプレース置換 ファイル内容の全消去 (0バイト化) 致命的 (即時データ喪失)

5. 置換文字列内の & とパス区切り文字の衝突

置換式内部の文法規則においても、エスケープの不備によってデータが予期せぬ破壊を被る落とし穴が存在する。

置換部アンパサンド (&) の全体マッチ展開と変数汚染

sed の置換構文 s/パターン/置換文字列/ において、置換文字列側の & は単なる文字ではなく、検索パターン全体に一致したテキストを参照するメタ文字である。

echo 'name=Tom' | sed 's/Tom/Tom & Jerry/'
echo 'name=Tom' | sed 's/Tom/Tom \& Jerry/'
echo 'root=/usr/local/app' | sed 's/\/usr\/local/\/opt/'
echo 'root=/usr/local/app' | sed 's//usr/local//opt/'; echo "exit=$?"
NEW=/opt/app; echo 'root=OLD' | sed "s/OLD/$NEW/"; echo "exit=$?"
echo 'root=OLD' | sed "s|OLD|$NEW|"
V='A&B'; echo 'x=OLD' | sed "s|OLD|$V|"
echo 'ab' | sed -E 's/(a)(b)/[\10]/'
echo 'port=80' | sed -E 's/(port)=([0-9]+)/\1=8\2/'

出力結果：

name=Tom Tom Jerry
name=Tom & Jerry
root=/opt/app
sed: -e expression #1, char 8: unknown option to `s'
exit=1
sed: -e expression #1, char 8: unknown option to `s'
exit=1
root=/opt/app
x=AOLDB
[a0]
port=880

echo 'name=Tom' | sed 's/Tom/Tom & Jerry/' の実行結果は Tom Tom Jerry となった。& が検索元テキストである Tom に展開されたためである。文字通りの & を挿入するには \& とエスケープしなければならない。この仕様は、シェル変数を動的に埋め込む際に最も猛威を振るう。変数 V='A&B' を渡した結果、x=AOLDB となり、置換文字列の中央に元の検索テキスト OLD が紛れ込む事態となった。動的変数を渡す際は事前に & を \& へ変換しておく前処理が不可欠である。

パス置換時のスラッシュ (/) エラーと縦線 (|) 区切り文字

ファイルパス置換で変数 NEW=/opt/app を s/OLD/$NEW/ に入れると、パス内のスラッシュが区切り文字として読まれ、unknown option to `s' エラー (終了コード 1) になった。GNU sed マニュアルによれば、s コマンドの / は別の任意の1文字に統一して置き換えられる。縦線 (|) を使った s|OLD|$NEW| は root=/opt/app を正しく出力した。なお後方参照 \10 は 10 番目のグループではなく \1 の後にリテラル 0 が付いたものとして扱われ ([a0])、\1=8\2 は 8 と 80 がつながって 880 になったので、後方参照の直後に数字を置くときは注意が要る。

入力パターンおよび実行例 実際の出力結果 エラー原因 正しい解決策
s/Tom/Tom & Jerry/ Tom Tom Jerry & がマッチテキスト 'Tom' へ展開 s/Tom/Tom \& Jerry/

6. 安全な一括置換の 5 段階手順

ここまでの実行結果をもとに、ファイルを変更する前に踏む 5 段階の順序を整理する。一度に sed -i をかけるのではなく、段階ごとに結果を確認する。

手順1から手順5までの安全パイプライン

以下のコマンドは、プレビュー → 一致行数 → バックアップ付き適用 → diff の順に実際に実行したものである。

printf 'root=/usr/local/app\nlog=/usr/local/app/log\nname=Tom\n' > app.conf
sed -n 's|/usr/local/app|/opt/app|gp' app.conf          # 1) プレビュー
grep -c '/usr/local/app' app.conf                        #    一致行数
sed -i.bak 's|/usr/local/app|/opt/app|g' app.conf        # 2) バックアップを残して適用
ls app.conf*
diff app.conf.bak app.conf; echo "diff exit=$?"          # 3) 確認

実際のターミナル出力：

=== 1) preview
root=/opt/app
log=/opt/app/log
=== match count
2
=== 2) apply with backup
app.conf
app.conf.bak
=== 3) diff
1,2c1,2
< root=/usr/local/app
< log=/usr/local/app/log
---
> root=/opt/app
> log=/opt/app/log
diff exit=1

このパイプラインの要点は以下の通りである：

  • 手順 1 (マッチ行数の確認): grep -c 'パターン' ファイル で置換対象が何行あるかを数える。0件ならそのファイルはスキップする。一致行が0行でも sed -i はファイルを新しく作り、Git Bash では改行まで変えた。
  • 手順 2 (変更箇所の事前プレビュー): sed -n 's|パターン|置換文字列|gp' ファイル で実際に置換される行のみを出力し、手順 1 の件数と一致するか確認する。
  • 手順 3 (改行コードの形式検査): file ファイル や od -c ファイル | head で CRLF の有無を調べる。Windows 環境であれば -b オプションを付与するか決定する。
  • 手順 4 (バックアップ付きで適用): sed -i.bak 's|パターン|置換文字列|g' ファイル でバックアップを保持しつつ置換を実行する。
  • 手順 5 (diff による差分検証): diff ファイル.bak ファイル で意図した行以外に変更が波及していないか検証する。diff の終了コード 1 は正常な差分の発生を意味する。

7. GNU sed と BSD sed の文法差と移植性

Linux (GNU sed) と macOS・FreeBSD (BSD sed) を行き来するスクリプトでは、-i の引数の扱いが異なる。この章の BSD 側の内容は macOS で実行しておらず、ドキュメントに基づく。

インプレース編集における引数処理の相違点

ドキュメントによれば、違いは次のとおりである：

  • GNU sed: -i の後のバックアップ拡張子はフラグに付けて書く省略可能な引数である。バックアップなしなら sed -i 's/.../.../' file、バックアップを残すなら sed -i.bak 's/.../.../' file のように付けて書く (本稿の実行もこの形)。マニュアルは sed -iE が --in-place=E と同じだと記しており、-i に付いた文字は拡張子として読まれる。
  • BSD sed (FreeBSD・macOS): FreeBSD のマニュアルは -i extension という形式を示し、拡張子を空文字列にするとバックアップを残さないと記している。例は sed -i '' -e 's/foo/bar/g' test.txt である。同じ文書は、ディスク容量が尽きた場合などにファイルが破損したり一部しか残らなかったりするおそれがあるため、空の拡張子は勧めないと記している。

クロスプラットフォーム対応のスクリプト記述戦略

両方で使える形は sed -i.bak である。GNU は付けて書いた拡張子を受け取り、BSD は拡張子を引数として受け取るので、バックアップを作って diff で確認し、不要なら削除するやり方が両方のドキュメントに合う。ただしこの部分はドキュメントに基づくもので、macOS では実行していない。

表 7. GNU sed と BSD sed (macOS) におけるインプレース置換構文の比較

8. 確認できなかったこと

本実測検証環境およびリソースの制約により確認できなかった項目は以下の通りである：

  • シンボリックリンクに対する sed -i の実体置換実測: 検証環境 (Windows 10 一般ユーザ権限、開発者モード未有効) では Git Bash の ln -s がシンボリックリンクではなく複製ファイルを作成し (NOT a symlink)、OS ネイティブのリンク作成も権限不足で失敗したため、本物のシンボリックリンクが通常ファイルへと書き換わる現象を直接実測することはできなかった。代わりに、GNU sed マニュアルは既定の動作がシンボリックリンクを切ることであり、リンク先は変更されないと記している。
  • Linux ネイティブ環境における CRLF 保持挙動: 本実験における改行コードの自動変換 (CRLF → LF) および CR 無視挙動は、Windows MSYS ビルドの Git Bash 環境で実測されたものである。テキストモードの概念を持たない純粋な Linux 上の GNU sed においても同一の挙動を示すかについては、Linux 実機で直接テストを行っていないため未確認である。
  • macOS/FreeBSD 実機における BSD sed の動作実測: BSD sed に関する sed -i '' 構文および必須引数の仕様は、FreeBSD の man ページに依拠したものであり、実際の macOS 実機ターミナル上で終了コードやディスク変更を直接実行確認したものではない。

# sed -i 一括置換の安全チェックリストと実務リファレンス

検証環境: Windows 10 Pro 10.0.19045、Git Bash (GNU sed 4.9、GNU Awk 5.0.0)、curl 8.12.1 (Schannel)、git 2.48.1.windows.1、Windows PowerShell 5.1、Python 3.13.3、Node 22.16.0 (管理者権限なし)。
以下はこの環境での実行結果と GNU sed・FreeBSD のマニュアルに基づいています。改行 (CRLF) に関する項目は Git Bash (Windows) ビルドで確認した挙動です。

## 1. 一括置換の安全な 5 段階パイプライン

ファイルを直接編集する前に、必ず次の手順を実行します。

1. **対象行数の確認**: `grep -c 'パターン' ファイル` で置換対象となる行数を数える。0 ならそのファイルはスキップする。
2. **変更内容の事前プレビュー**: `sed -n 's|パターン|置換文字列|gp' ファイル` で実際に置換される行のみを出力し、手順 1 の行数と一致するか確認する。
3. **改行コード (CRLF/LF) の確認**: `file ファイル` または `od -c ファイル | head` で改行形式を確認し、Git Bash では改行を維持するために `-b` オプションを指定するか判断する。
4. **バックアップ生成と適用**: `sed -i.bak 's|パターン|置換文字列|g' ファイル` で原本バックアップ (`ファイル.bak`) を残して置換を実行する。
5. **diff による差分検証**: `diff ファイル.bak ファイル` で意図した行のみが変更されたか確認する (終了コード 1 は差分があるという意味で、エラーではない)。

## 2. 症状別の原因と対策一覧 (実測ベース)

| 症状 | 原因 | 対策 |
|---|---|---|
| 置換していないファイルまで git diff で全体が変更扱いになる | Git Bash の sed が CRLF を LF に変換 (一致する行が 0 行でも発生) | `sed -i -b` を指定するか、変更対象ファイルのみを選んで実行する |
| ハードリンクでつながったもう一方の名前に変更が反映されない | `sed -i` は既存ファイルの上書きではなく一時ファイル生成後の rename 置換 | ハードリンクを保つ必要があるファイルは `sed -i` で差し替えず別の方法を使う |
| ``unknown option to `s'`` エラーが発生する | パス文字列に含まれるスラッシュ (`/`) が区切り文字と衝突 | 置換の区切り文字を `s|パターン|置換文字列|g` のように縦線 (`|`) に変更する |
| 置換結果の途中に検索元テキストが混入する (`A&B` が `AOLDB` になる) | 置換文字列に含まれる `&` がマッチ全体に展開される | 置換文字列内の `&` を事前に `\&` にエスケープする |
| `ie.txtE` のような意図しないバックアップファイルが作られる | `-iE` とオプションを結合したことで sed が `E` をバックアップ拡張子と解釈 | `-Ei` の順序で記述するか `-E -i` と分離する |
| ファイルの内容が 0 バイトになって消滅する | `-n` と `-i` を併用し、かつ出力指示子 (`p`) を省略した | プレビュー用の `-n` とファイル修正用の `-i` を同時に実行しない |
| `ln -s` で作成した「リンク」が実体と同期しない | Git Bash のデフォルト `ln -s` はシンボリックリンクではなくファイルコピーを作成 | `[ -L ファイル ]` 条件で事前に本物のリンクか判定する |

## 3. sed -i 主要落とし穴チェックリスト

- [ ] `sed -i` は inode 番号と NTFS ファイル ID を変えるため、ハードリンクが切断される (Git Bash で実測)。
- [ ] Git Bash (MSYS) 環境では、置換対象が 0 件でもファイルの改行コードが LF に変わる。
- [ ] Git Bash で CRLF 改行を維持するには `-b` (--binary) オプションを付ける。
- [ ] 拡張正規表現を併用する場合は、`-iE` ではなく `-Ei` の順序で指定する。
- [ ] シェル変数を置換文字列に渡す際は、変数内部の `&` が `\&` にエスケープされているか確認する。
- [ ] (ドキュメントのみ) BSD/FreeBSD の sed では、バックアップなしの置換に空の拡張子 `sed -i ''` を渡す。マニュアルは空の拡張子を勧めていない。
- [ ] (ドキュメントのみ) GNU sed と BSD sed の双方で使うには、`sed -i.bak` でバックアップを残し、不要なら削除する。
