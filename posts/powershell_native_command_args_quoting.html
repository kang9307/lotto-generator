여기 실린 인수 목록은 Windows PowerShell 5.1.19041.6456 에서 powershell.exe -NoProfile 로 실행하고, 받은 프로그램이 직접 찍은 명령줄과 argv 를 그대로 옮긴 것이다. 인수를 세는 프로그램은 파이썬 3.13 이고 실제 도구로 git 2.48.1 과 curl.exe 를 썼다. curl.exe 는 PATH 에서 먼저 잡히는 것이 실행되므로 환경에 따라 다르고, 경로와 버전은 11절의 Get-Command curl.exe 출력이 기준이다. PowerShell 7(pwsh)은 환경에 없어 7 쪽 동작은 공식 문서의 문장까지만 인용한다. bash 쪽 인용 규칙은 셸 인용 규칙 가이드에, 5.1 에서 큰따옴표와 빈 문자열이 사라진다는 기본 사실은 셸 인용과 한글 이름 가이드의 6절에 있다. 여기서는 그 위에 PowerShell 에서 네이티브 프로그램으로 가는 인수 전달의 전체 목록, 이스케이프 방법별 성패, 끝 역슬래시, 스플랫·--%·here-string, git·curl.exe 사례를 더한다.

측정 방법 — 받는 프로그램이 명령줄과 argv 를 직접 찍는다

PowerShell 이 인수를 어떻게 쪼개 넘기는지는 PowerShell 쪽 출력으로는 알 수 없다. 프로세스가 실제로 받은 문자열을 받는 쪽이 찍어야 한다. 아래 작은 프로그램은 Windows API 가 돌려주는 원본 명령줄(raw)과, 그것을 C 런타임이 나눈 argv 를 함께 출력한다. 이후 모든 블록에서 raw 줄은 PowerShell 이 조립한 명령줄이고 argv 줄은 받는 프로그램이 본 인수다. 인수 개수 줄(n)은 argv 의 길이이므로 생략했고, 줄 맨 앞의 >>> 는 시험한 입력이다.

import sys, json, ctypes
                    ctypes.windll.kernel32.GetCommandLineW.restype = ctypes.c_wchar_p
                    raw = ctypes.windll.kernel32.GetCommandLineW()
                    i = raw.find('argv.py')
                    print('  raw : ' + raw[i + 7:].lstrip().encode('ascii','backslashreplace').decode())
                    print('  argv: ' + json.dumps(sys.argv[1:], ensure_ascii=True))
                    print('  n   : %d' % (len(sys.argv) - 1))

공식 문서는 이 과정을 이렇게 설명한다. 네이티브 명령을 호출할 때 PowerShell 이 인수를 먼저 파싱하고, 파싱된 인수를 공백으로 이어 한 문자열로 만들며, 그 문자열이 ProcessStartInfo 의 Arguments 속성에 들어간다. 안쪽 따옴표는 따옴표를 겹치거나 백슬래시로 이스케이프해야 하고, 백슬래시는 PowerShell 의 이스케이프 문자가 아니라 하위 API 의 이스케이프 문자라고 문서는 적는다. 이 한 문단이 글 전체의 틀이다. PowerShell 이 한 줄을 만들고, 받는 프로그램이 그 한 줄을 다시 쪼갠다. 결과는 PowerShell 의 규칙과 받는 프로그램의 분해 규칙이 만나는 자리에서 정해진다.

기본 규칙 — 공백이 있으면 감싸고 빈 문자열은 버린다

가장 단순한 입력부터 본다. $v 에는 a b(공백 포함)가 들어 있다.

>>> python argv.py a b
                      raw : a b
                      argv: ["a", "b"]
                    
                    >>> python argv.py ''
                      raw : 
                      argv: []
                    
                    >>> python argv.py '' x
                      raw : x
                      argv: ["x"]
                    
                    >>> python argv.py 'a b'
                      raw : "a b"
                      argv: ["a b"]
                    
                    >>> python argv.py "$v"   ($v = 'a b')
                      raw : "a b"
                      argv: ["a b"]
                    
                    >>> python argv.py '$v'
                      raw : $v
                      argv: ["$v"]
                    
                    >>> python argv.py a$v
                      raw : "aa b"
                      argv: ["aa b"]
입력raw (조립된 명령줄)받은 argv
a ba b인수 2개
''(아무것도 없음)인수 0개
'' xx인수 1개, x 만 남음
'a b'"a b"인수 1개
"$v""a b"인수 1개
'$v'$v인수 1개, 문자 그대로
a$v"aa b"인수 1개
  • 공백이 든 인수만 큰따옴표로 감싸진다. 공백이 없으면 감싸지 않는다.
  • 작은따옴표는 PowerShell 이 벗기고 내용을 그대로 넘긴다. '$v' 는 확장되지 않고 "$v" 는 확장된다. 확장된 값에 공백이 있어도 단어 분리가 없어 한 인수다.
  • a$v 처럼 변수에 문자가 붙은 형태도 한 인수로 이어진다. 공식 문서도 단순 변수 참조 뒤의 문자는 같은 인수의 일부라고 적는다.
  • 빈 문자열은 raw 에 흔적을 남기지 않는다. 그 뒤의 인수는 위치가 하나씩 당겨진다.

마지막 항목이 조용한 사고의 출발점이다. --name '' --flag 같은 호출에서 빈 값을 넘겼다고 믿어도 받는 쪽은 --name --flag 를 본다.

큰따옴표가 사라진다 — JSON 이 가장 먼저 깨진다

인수 안의 큰따옴표는 5.1 에서 이스케이프되지 않는다. 문서도 PowerShell 의 명령줄 파싱이 입력한 따옴표를 제거한다고 적는다.

>>> python argv.py 'say "hi"'   (single-quoted, contains double quotes)
                      raw : "say "hi""
                      argv: ["say hi"]
                    
                    >>> python argv.py 'say"hi'   (no space in value)
                      raw : say"hi
                      argv: ["sayhi"]
                    
                    >>> python argv.py '{"a":1}'
                      raw : {"a":1}
                      argv: ["{a:1}"]
                    
                    >>> python argv.py '{"a": 1}'   (JSON with a space)
                      raw : "{"a": 1}"
                      argv: ["{a: 1}"]
  • 'say "hi"' 는 공백이 있어 큰따옴표로 감싸지는데, 안쪽 따옴표가 그대로 들어가 raw 가 "say "hi"" 가 된다. 받는 쪽은 따옴표를 구분자로 소비해 say hi 를 얻는다.
  • 'say"hi' 처럼 공백이 없으면 감싸지 않고 따옴표가 raw 에 그대로 들어가는데도 결과는 sayhi 다. 감싸기 여부와 무관하게 따옴표는 소비된다.
  • '{"a":1}' 은 {a:1} 로 도착한다. 따옴표가 사라진 JSON 은 유효하지 않다. 공백이 든 '{"a": 1}' 도 {a: 1} 이다.

이 증상은 curl -d, git commit -m, python -c, node -e 처럼 인수에 따옴표가 든 값을 넘기는 모든 호출에서 같은 모양으로 나타난다. 오류가 나지 않고 값이 조용히 바뀐다는 점이 위험하다.

큰따옴표를 살리는 방법 — 백슬래시 이스케이프, 겹따옴표, 이미 감싼 값

문서가 말하는 두 방법(따옴표 겹치기, 백슬래시)과 이미 따옴표로 감싼 값을 시험했다.

>>> python argv.py 'say \"hi\"'   (backslash-escaped quotes)
                      raw : "say \"hi\""
                      argv: ["say \"hi\""]
                    
                    >>> python argv.py '{\"a\":1}'
                      raw : {\"a\":1}
                      argv: ["{\"a\":1}"]
                    
                    >>> python argv.py '{\"a\": 1}'
                      raw : "{\"a\": 1}"
                      argv: ["{\"a\": 1}"]
                    
                    >>> python argv.py 'say ""hi""'   (doubled quotes inside single quotes)
                      raw : "say ""hi"""
                      argv: ["say \"hi\""]
                    
                    >>> python argv.py 'a""b'
                      raw : a""b
                      argv: ["ab"]
                    
                    >>> python argv.py '{""a"":1}'
                      raw : {""a"":1}
                      argv: ["{a:1}"]
                    
                    >>> python argv.py '"a b"'
                      raw : "a b"
                      argv: ["a b"]
                    
                    >>> python argv.py 'x "a b"'
                      raw : "x "a b""
                      argv: ["x a", "b"]
                    
                    >>> python argv.py '""'
                      raw : ""
                      argv: [""]
방법입력받은 값판정
역슬래시 이스케이프'say \"hi\"'say "hi"성공 (공백 있음)
역슬래시 이스케이프'{\"a\":1}'{"a":1}성공 (공백 없음)
역슬래시 이스케이프'{\"a\": 1}'{"a": 1}성공
겹따옴표'say ""hi""'say "hi"성공 (공백 있음, python)
겹따옴표'a""b'ab실패 (공백 없음)
겹따옴표'{""a"":1}'{a:1}실패
겹따옴표git 의 -m 'fix ""x"" bug'pathspec 오류실패 (11절)
이미 감싼 값'"a b"'a b따옴표 소실, 이중 감싸기는 없음
이미 감싼 값'x "a b"'x a 와 b인수가 둘로 갈림
빈 인수'""'빈 문자열 1개성공, 3절의 빈 인수 소실 우회
  • 값 안의 큰따옴표를 역슬래시와 큰따옴표로 바꾸면 공백 유무와 관계없이 살아서 도착했다.
  • 겹따옴표는 PowerShell 이 인수를 큰따옴표로 감쌀 때(공백이 있을 때)만 파이썬에서 통했다. 감싸지 않는 인수에서는 따옴표가 소비되었고, git 에서는 같은 형태가 오류였다. 같은 명령줄이라도 받는 프로그램의 분해 규칙이 다를 수 있다는 뜻이다.
  • 이미 큰따옴표로 감싼 "a b" 는 5.1 이 다시 감싸지 않았지만(이미 감싼 값이 늘 그런 것은 아니다. 조건은 10절에서 실험했다), 그 따옴표는 구분자로 소비된다. 따옴표가 값의 일부여야 한다면 이 방법은 쓸 수 없다.
  • 큰따옴표 두 개를 값으로 넘기면 빈 문자열 한 개가 도착한다. 3절에서 사라진 빈 인수를 되살리는 방법이다.

끝의 역슬래시가 뒤 인수를 삼킨다

공백이 든 경로는 큰따옴표로 감싸진다. 그 경로가 역슬래시로 끝나면 문제가 생긴다. 아래 argv 줄은 JSON 형식이라 역슬래시 한 개가 두 개로 표기된다.

>>> python argv.py 'C:\Program Files\x'
                      raw : "C:\Program Files\x"
                      argv: ["C:\\Program Files\\x"]
                    
                    >>> python argv.py 'C:\Program Files\x\'   (path ends with backslash)
                      raw : "C:\Program Files\x\" next
                      argv: ["C:\\Program Files\\x\" next"]
                    
                    >>> python argv.py 'C:\Program Files\x\\'   (two backslashes)
                      raw : "C:\Program Files\x\\" next
                      argv: ["C:\\Program Files\\x\\", "next"]
                    
                    >>> python argv.py 'C:\x\' next   (no space in path)
                      raw : C:\x\ next
                      argv: ["C:\\x\\", "next"]
  • 공백이 든 경로 C:\Program Files\x 는 정상이다.
  • 같은 경로가 \ 한 개로 끝나면 raw 가 "C:\Program Files\x\" next 가 되어 닫는 따옴표가 이스케이프된 따옴표로 읽히고, 뒤의 next 가 같은 인수에 합쳐진다. 받은 인수는 하나이고 값이 C:\Program Files\x" next 다. 인수가 하나 줄어든 것이 아니라 두 개가 하나로 뭉쳤다.
  • 끝에 \\ 두 개를 두면 하나의 역슬래시와 닫는 따옴표로 읽혀 next 가 따로 도착한다. 도착한 경로의 끝에는 역슬래시가 하나 남는다.
  • 공백이 없는 경로 C:\x\ 는 감싸지 않으므로 이 문제가 없다.

조건은 둘이 동시에 맞을 때다. 인수에 공백이 있어 감싸지고, 끝이 역슬래시다. 폴더 경로를 끝 구분자까지 붙여 만드는 코드, 예를 들어 사용자 폴더 아래 공백이 든 폴더를 가리키는 변수가 여기에 걸린다. 끝의 역슬래시를 TrimEnd('\') 로 떼거나 두 개로 늘려서 넘기면 정상이다.

변수·쉼표·메타문자 — 어디까지가 PowerShell 의 일인가

인수에는 PowerShell 이 먼저 해석하는 것과 그대로 넘기는 것이 섞여 있다.

>>> python argv.py 1,2
                      raw : 1,2
                      argv: ["1,2"]
                    
                    >>> python argv.py $env:OS
                      raw : Windows_NT
                      argv: ["Windows_NT"]
                    
                    >>> python argv.py (1+2)
                      raw : 3
                      argv: ["3"]
                    
                    >>> python argv.py '%OS%'
                      raw : %OS%
                      argv: ["%OS%"]
                    
                    >>> python argv.py *.nothing  (no match, wildcard)
                      raw : *.nothing
                      argv: ["*.nothing"]
                    
                    >>> python argv.py 'a & b' 'a | b'
                      raw : "a & b" "a | b"
                      argv: ["a & b", "a | b"]
                    
                    >>> python argv.py a;echo b   (semicolon ends the statement)
                      raw : a
                      argv: ["a"]
                    b
                    
                    >>> python argv.py ('caf' + [char]0xE9) ('x' + [char]0xD55C)
                      raw : caf\xe9 x\ud55c
                      argv: ["caf\u00e9", "x\ud55c"]
  • 1,2 는 한 인수 1,2 로 도착한다. 공식 문서는 쉼표가 PowerShell 명령에서는 배열을 만들지만 네이티브 응용 프로그램에서는 확장 가능한 문자열의 일부로 해석된다고 적는다.
  • $env:OS, (1+2) 같은 변수·괄호 식은 PowerShell 이 먼저 평가해 값이 넘어간다. '%OS%' 는 PowerShell 이 건드리지 않아 문자 그대로다.
  • 와일드카드 *.nothing 은 확장되지 않고 그대로 넘어간다. 파일 이름 확장은 PowerShell 이 하지 않는다.
  • 'a & b' 처럼 따옴표 안의 메타문자는 한 인수로 보존된다. 따옴표 밖의 세미콜론은 명령을 끝낸다. a;echo b 에서 파이썬은 인수 a 만 받았고 echo b 는 별도의 명령으로 실행되어 b 가 출력됐다.
  • 비ASCII 문자는 출력을 ASCII 이스케이프로 찍었기 때문에 \xe9, \ud55c 로 보이지만 인수는 정상 도착했다. 명령줄이 유니코드로 전달되기 때문이다.

문서가 정리한 인수 모드의 메타문자는 공백, 작은따옴표, 큰따옴표, 백틱, 쉼표, 세미콜론, 괄호, 중괄호, 파이프, 앰퍼샌드, 꺾쇠, 골뱅이, 샵이다. 이 중 꺾쇠·골뱅이·샵은 토큰 맨 앞에서만 특별하다. 따옴표 없이 넘길 인수에 이런 문자가 있으면 PowerShell 이 먼저 가져간다.

배열과 스플랫 — 문자열 한 덩어리는 한 인수다

인수 목록이 가변적이면 변수에 담아 넘기게 되는데, 담는 형태가 결과를 가른다.

>>> $arr = 'x','y z'; python argv.py $arr
                      raw : x "y z"
                      argv: ["x", "y z"]
                    
                    >>> $s = '--flag "a b"'; python argv.py $s
                      raw : "--flag "a b""
                      argv: ["--flag a", "b"]
                    
                    >>> $sp = @('--flag','a b'); python argv.py @sp
                      raw : --flag "a b"
                      argv: ["--flag", "a b"]
                    
                    >>> $h = @{k=1}; python argv.py @h  (hashtable splat)
                      raw : -k:1
                      argv: ["-k:1"]
  • 배열 변수 $arr 는 원소마다 한 인수가 되고, 공백이 든 원소만 감싸진다.
  • 인수 목록을 문자열 한 덩어리로 담은 $s 는 전체가 한 인수가 된다. 공백이 있어 감싸지고 안쪽 따옴표가 소비되어 --flag a 와 b 로 갈렸다. 목록을 문자열로 조립해 넘기는 방식이 틀어지는 전형이다.
  • 배열을 스플랫(@sp)하면 변수에 담긴 원소가 인수 하나씩이 된다. 가변 인수는 이 방식이 안전하다.
  • 해시테이블 스플랫 @h 는 키와 값을 -k:1 형태의 한 인수로 바꿨다. 네이티브 프로그램의 옵션 형식과 맞는지는 프로그램에 달려 있다.

--% 와 -- — 파싱을 끄는 토큰

stop-parsing 토큰 --% 는 그 뒤의 문자를 PowerShell 해석 없이 넘기는 토큰이다. 문서는 같은 줄의 나머지를 리터럴로 취급하되 %USERPROFILE% 같은 Windows 표기의 환경 변수만 치환한다고 설명한다.

>>> python argv.py --% a "b c" %OS%
                      raw : a "b c" Windows_NT
                      argv: ["a", "b c", "Windows_NT"]
                    
                    >>> python argv.py --% --opt="a b" 'q'
                      raw : --opt="a b" 'q'
                      argv: ["--opt=a b", "'q'"]
                    
                    >>> python argv.py --% "a b" "c
                      raw : "a b" "c
                      argv: ["a b", "c"]
                    
                    >>> python argv.py -x -- y
                      raw : -x -- y
                      argv: ["-x", "--", "y"]
                    
                    >>> python argv.py --opt="a b"
                      raw : "--opt=a b"
                      argv: ["--opt=a b"]
                    
                    >>> python argv.py --opt=$v
                      raw : "--opt=a b"
                      argv: ["--opt=a b"]
                    
                    >>> python argv.py -p:val
                      raw : -p:val
                      argv: ["-p:val"]
  • --% a "b c" %OS% 는 큰따옴표가 그대로 구분자로 쓰여 b c 가 한 인수가 되고 %OS% 는 Windows_NT 로 치환됐다. 문서가 밝히듯 %이름% 형태는 항상 확장되고, 정의되지 않은 이름이면 그대로 남는다.
  • --% 뒤의 작은따옴표는 PowerShell 이 벗기지 않는다. 'q' 는 따옴표 달린 'q' 로 도착했다.
  • 따옴표가 짝이 맞지 않아도 그대로 넘어간다. 닫히지 않은 "c 가 한 인수 c 로 도착했다.
  • 문서에 따르면 --% 는 다음 줄바꿈이나 파이프까지만 유효하고, 리다이렉트도 인수로 넘어가며, 변수 같은 동적 요소는 환경 변수 외에는 넣을 수 없다.
  • 모두 PowerShell 명령용 토큰인 -- 는 네이티브 프로그램에서는 그냥 -- 인수로 전달된다. -x -- y 가 세 인수가 되었다.
  • --opt="a b" 와 --opt=$v 는 모두 "--opt=a b" 한 인수로 조립되었다. 옵션 이름과 값이 이어진 한 토큰이기 때문이다.

백틱과 here-string — 여러 줄 인수

백틱은 큰따옴표 문자열 안에서만 이스케이프다. 작은따옴표 안에서는 문자 그대로다. 줄바꿈이 든 값은 here-string 으로 만들 수 있다.

>>> python argv.py 'a`tb' "a`tb"
                      raw : a`tb "a	b"
                      argv: ["a`tb", "a\tb"]
                    
                    >>> python argv.py "line1`nline2"
                      raw : "line1
                    line2"
                      argv: ["line1\nline2"]
                    
                    >>> here-string: python argv.py (@'...'@)  with a double quote inside
                      raw : "first line
                    second "quoted" line"
                      argv: ["first line\nsecond quoted line"]
  • 작은따옴표 안의 백틱t 는 글자 그대로 도착했고, 큰따옴표 안의 백틱t 는 탭 문자가 되었다.
  • 줄바꿈이 든 인수는 raw 에 줄바꿈이 그대로 들어가고 한 인수로 도착한다. 공백이 있는 인수와 마찬가지로 큰따옴표로 감싸진다.
  • here-string 안의 큰따옴표는 3절과 같이 소비되어 second quoted line 이 되었다. 문서가 설명하듯 here-string 은 안의 따옴표를 리터럴로 해석하지만, 네이티브 프로그램으로 넘어가는 단계에서 다시 벗겨진다.

여러 줄에 따옴표가 든 값을 안전하게 넘기는 방법은 11절의 curl.exe 사례에서 비교한다.

명령줄을 정확히 통제하는 방법 — Start-Process 와 ProcessStartInfo

PowerShell 의 조립 규칙을 피하려면 명령줄을 직접 만들어 넘기면 된다. Start-Process 의 -ArgumentList 가 문자열이면 어떻게 되는지, 배열이면 어떻게 되는지부터 확인했다.

>>> Start-Process python -ArgumentList 'argv.py "a b" {\"k\":1}' -NoNewWindow -Wait
                      raw : "a b" {\"k\":1} 
                      argv: ["a b", "{\"k\":1}"]
                    
                    >>> Start-Process python -ArgumentList @('argv.py','a b','c') -NoNewWindow -Wait
                      raw : a b c 
                      argv: ["a", "b", "c"]

문자열 하나를 주면 raw 가 입력 문자열과 같아서 호출자가 큰따옴표와 역슬래시를 직접 통제한다. 배열을 주면 원소를 공백으로 이을 뿐 감싸지 않아 'a b' 가 a 와 b 두 인수로 갈렸다. 배열이 안전하다고 가정하면 안 된다.

임의의 값을 정확히 전달하려면 C 런타임의 규칙에 맞게 직접 이스케이프하는 헬퍼를 두고 ProcessStartInfo.Arguments 에 넣는 방법이 있다. 아래 헬퍼는 값 안의 큰따옴표 앞 역슬래시를 두 배로 하고 큰따옴표를 역슬래시로 이스케이프하며, 끝의 역슬래시를 두 배로 한 뒤 전체를 큰따옴표로 감싼다.

function ConvertTo-NativeArg([string]$a) {
                      if ($a -eq '') { return '""' }
                      $r = $a -replace '(\\*)"', '$1$1\"'
                      $r = $r -replace '(\\+)$', '$1$1'
                      '"' + $r + '"'
                    }
                    function Invoke-NativeExact([string]$File, [string[]]$ArgList) {
                      $psi = New-Object Diagnostics.ProcessStartInfo
                      $psi.FileName = $File
                      $psi.Arguments = ($ArgList | % { ConvertTo-NativeArg $_ }) -join ' '
                      $psi.UseShellExecute = $false
                      $psi.RedirectStandardOutput = $true
                      $psi.StandardOutputEncoding = [Text.Encoding]::UTF8
                      $p = [Diagnostics.Process]::Start($psi)
                      $out = $p.StandardOutput.ReadToEnd()
                      $p.WaitForExit()
                      $out
                    }
$cases = @('plain', 'a b', 'say "hi"', '{"a": 1}', 'C:\Program Files\x\', 'tail\\', 'q"', '', 'a\"b c')
                    foreach ($c in $cases) {
                      $json = Invoke-NativeExact 'python' @('-c', 'import sys,json;print(json.dumps(sys.argv[1]))', $c)
                      $back = $json | ConvertFrom-Json
                      '{0,-22} -> received equal: {1}' -f ("'" + $c + "'"), ($back -ceq $c)
                    }

아홉 가지 값을 파이썬이 argv 로 받아 JSON 으로 돌려주게 하고 원래 값과 비교한 결과다. 공백, 큰따옴표, 끝 역슬래시, 빈 문자열, 역슬래시와 큰따옴표의 조합이 들어 있다.

'plain'                -> received equal: True
                    'a b'                  -> received equal: True
                    'say "hi"'             -> received equal: True
                    '{"a": 1}'             -> received equal: True
                    'C:\Program Files\x\'  -> received equal: True
                    'tail\\'               -> received equal: True
                    'q"'                   -> received equal: True
                    ''                     -> received equal: True
                    'a\"b c'               -> received equal: True

아홉 건이 모두 일치했다. 같은 헬퍼의 결과 문자열을 ProcessStartInfo 를 거치지 않고 일반 호출의 인수로 넘기면 어떻게 되는지도 시험했다.

foreach ($c in $cases) {
                      $enc = ConvertTo-NativeArg $c
                      $json = (& python -c 'import sys,json;print(json.dumps(sys.argv[1]))' $enc)
                      $back = $json | ConvertFrom-Json
                      '{0,-22} -> arg {1,-30} -> received equal: {2}' -f ("'" + $c + "'"), $enc, ($back -ceq $c)
                    }
'plain'                -> arg "plain"                        -> received equal: True
                    'a b'                  -> arg "a b"                          -> received equal: True
                    'say "hi"'             -> arg "say \"hi\""                   -> received equal: True
                    '{"a": 1}'             -> arg "{\"a\": 1}"                   -> received equal: True
                    'C:\Program Files\x\'  -> arg "C:\Program Files\x\\"         -> received equal: True
                    'tail\\'               -> arg "tail\\\\"                     -> received equal: True
                    'q"'                   -> arg "q\""                          -> received equal: True
                    ''                     -> arg ""                             -> received equal: True

아홉 건 중 여덟 건이 일치했고, 값에 역슬래시와 큰따옴표가 함께 든 a\"b c 가 불일치였다. 이 값의 헬퍼 결과는 이미 큰따옴표로 시작하고 끝나는데도 5.1 이 한 번 더 감싸 raw 가 큰따옴표 두 개로 시작하는 형태가 되었고, 받은 인수는 둘로 갈렸다. 그런데 나머지 여덟 건의 헬퍼 결과("say \"hi\"" 등)는 같은 방식으로 넘겼는데도 다시 감싸이지 않았다. 이 값만 감싸인 이유를 변인을 나눠 확인했다. 헬퍼 없이 따옴표·역슬래시·공백의 위치만 바꾼 문자열 열네 개를 변수에 담아 같은 방식으로 넘기고, 받은 raw 가 입력을 큰따옴표로 한 번 더 감싼 것인지(rewrapped)를 기록했다. rule 열은 관찰을 보고 세운 가설(공백 문자 앞에 있는 큰따옴표의 개수가 짝수(0 포함)인 공백이 하나라도 있으면 감싼다)을 계산한 값이다.

function Test-Rule([string]$s) {
                      $n = 0
                      foreach ($ch in $s.ToCharArray()) {
                        if ($ch -eq '"') { $n++ }
                        elseif ([char]::IsWhiteSpace($ch) -and $n % 2 -eq 0) { return $true }
                      }
                      $false
                    }
                    $cases = @(
                      '"a b"',
                      '"a\"b c"',
                      '"a\\"b c"',
                      '"a\\\"b c"',
                      '"a\\\\"b c"',
                      '"a\\\"bc"',
                      '"a\\\b c"',
                      '"say \"hi\""',
                      'a\\\"b c',
                      '"a" b',
                      '"a b" c',
                      'a "b c"',
                      'x y',
                      '"x""y z"'
                    )
                    foreach ($v in $cases) {
                      $raw = (python argv.py $v)[0] -replace '^\s*raw : ', ''
                      '{0,-14} raw={1,-16} rewrapped={2,-5} rule={3}' -f $v, $raw, ($raw -ceq ('"' + $v + '"')), (Test-Rule $v)
                    }
"a b"          raw="a b"            rewrapped=False rule=False
                    "a\"b c"       raw=""a\"b c""       rewrapped=True  rule=True
                    "a\\"b c"      raw=""a\\"b c""      rewrapped=True  rule=True
                    "a\\\"b c"     raw=""a\\\"b c""     rewrapped=True  rule=True
                    "a\\\\"b c"    raw=""a\\\\"b c""    rewrapped=True  rule=True
                    "a\\\"bc"      raw="a\\\"bc"        rewrapped=False rule=False
                    "a\\\b c"      raw="a\\\b c"        rewrapped=False rule=False
                    "say \"hi\""   raw="say \"hi\""     rewrapped=False rule=False
                    a\\\"b c       raw=a\\\"b c         rewrapped=False rule=False
                    "a" b          raw=""a" b"          rewrapped=True  rule=True
                    "a b" c        raw=""a b" c"        rewrapped=True  rule=True
                    a "b c"        raw="a "b c""        rewrapped=True  rule=True
                    x y            raw="x y"            rewrapped=True  rule=True
                    "x""y z"       raw="x""y z"         rewrapped=False rule=False
  • 다시 감싸인 것은 열네 개 중 여덟 개였고, 가설의 예측은 열네 개 모두 관찰과 일치했다. 어떤 공백 앞의 큰따옴표가 짝수 개일 때 감싸였다(x y, "a" b, a "b c", "a b" c 의 두 번째 공백).
  • 역슬래시의 개수(1·2·3·4개)는 결과를 바꾸지 않았다. 2~5번째 줄이 모두 감싸였으며, 역슬래시가 앞에 있는 따옴표도 한 개로 센 것과 같은 결과다.
  • 감싸이지 않은 여섯 줄(1·6·7·8·9·14번째)은 공백이 없거나(6번째), 공백 앞의 큰따옴표가 홀수 개(나머지)였다.
  • 헬퍼 결과 아홉 개 중 공백 앞에 큰따옴표가 둘(여는 따옴표와 이스케이프된 따옴표) 있는 것은 a\"b c 의 결과뿐이고, 나머지 여덟 개는 공백이 없거나 공백 앞이 홀수 개(하나 또는 셋)다.

이 규칙은 열네 개 관찰에 맞춰 세운 가설이다. 5.1 의 구현이나 문서로 확인한 것이 아니며, 이 글이 인용한 공식 문서 발췌에도 이런 판정은 나오지 않는다. 확인된 것은 5.1 이 다시 감싸는지가 공백 앞 큰따옴표의 개수에 따라 갈린다는 관찰까지다. 그래서 헬퍼의 결과는 5.1 의 일반 호출에 넘길 것이 아니라 명령줄을 그대로 쓰는 경로에 넘겨야 한다.

실제 사례 — git commit 과 curl.exe

임시 저장소에서 큰따옴표가 든 커밋 메시지를 넘겨 보았다. 아래 호출 다섯 개에 이어지는 출력의 번호는 호출 순서와 같다.

git commit -q --allow-empty -m 'fix "x" bug'
                    git commit -q --allow-empty -m 'fix \"x\" bug'
                    git commit -q --allow-empty -m "fix ""x"" bug"
                    git commit -q --allow-empty -m 'fix ""x"" bug'
                    git commit -q --allow-empty -m 'fix "x"'
1) -m 'fix "x" bug'          -> fix x bug
                    2) -m 'fix \"x\" bug'        -> fix "x" bug
                    3) -m "fix ""x"" bug"          -> fix x bug
                    error: pathspec 'bug' did not match any file(s) known to git
                    4) -m 'fix ""x"" bug'        -> fix x bug
                    5) -m 'fix "x"'              -> fix x
  • 1번은 fix x bug 로 큰따옴표가 사라졌고, 5번도 fix x 다.
  • 2번은 역슬래시 이스케이프를 써서 fix "x" bug 가 정확히 들어갔다.
  • 3번은 PowerShell 의 큰따옴표 문자열 안에서 따옴표를 겹쳤는데, 변수로 만들어지는 값은 1번과 같은 fix "x" bug 라 결과도 1번과 같다. PowerShell 수준의 이스케이프는 네이티브 프로그램에 따옴표를 이스케이프해 주지 않는다.
  • 4번은 명령줄에 겹따옴표를 넣었더니 git 이 pathspec 'bug' did not match 오류를 냈다. 4번 줄에 찍힌 메시지는 직전 커밋의 것이다. 같은 입력이 파이썬에서는 통했으므로, 겹따옴표는 프로그램마다 결과가 다르다.

JSON 본문을 보내는 curl.exe -d 는 더 흔한 사례다. 로컬에 POST 본문을 파일로 저장하는 작은 서버를 띄워 받은 본문을 읽었다.

import http.server, sys
                    class H(http.server.BaseHTTPRequestHandler):
                        def do_POST(self):
                            n = int(self.headers.get('Content-Length', 0))
                            body = self.rfile.read(n)
                            open('last_body.txt', 'wb').write(body)
                            self.send_response(200); self.end_headers(); self.wfile.write(b'ok')
                        def log_message(self, *a): pass
                    http.server.HTTPServer(('127.0.0.1', 18080), H).serve_forever()

                    here-string, quotes escaped        body received: {"a": 1,
                     "b": "two words"}
                    file via @body.json                body received: {"a": 1,
                     "b": "two words"}
  • 작은따옴표로 쓴 JSON 은 따옴표가 모두 사라진 {a: 1} 로 도착했다.
  • 큰따옴표를 역슬래시로 이스케이프하면 {"a": 1} 로 정확히 도착했다.
  • here-string 변수를 그대로 넘기면 따옴표가 사라질 뿐 아니라 본문이 b: two 에서 끝났다. 따옴표가 소비되면서 words} 가 별도 인수로 갈린 것으로 보이며, 이는 3절과 같은 패턴에서의 추정이다.
  • here-string 의 따옴표를 -replace '"', '\"' 로 이스케이프하거나 본문을 파일에 쓰고 --data-binary '@body.json' 으로 넘기면 여러 줄 본문이 정확히 도착했다.

여러 줄이거나 따옴표가 많은 본문은 이스케이프를 고치기보다 파일로 넘기는 편이 인수 전달 규칙에서 벗어나 가장 단순하다. 파일은 5.1 파일 인코딩 글의 방식으로 BOM 없이 쓰면 된다.

PowerShell 7.3 이후는 다르다 — 문서에 적힌 것만

공식 문서(7.4 판)에 따르면 PowerShell 7.3 은 네이티브 명령의 명령줄을 파싱하는 방식을 바꿨고, 새 변수 $PSNativeCommandArgumentPassing 이 이를 제어한다. 문서는 이 변경이 파괴적 변경이며 네이티브 응용 프로그램 호출의 여러 문제를 우회하던 스크립트와 자동화를 깨뜨릴 수 있다고 경고한다.

  • 값은 Legacy, Standard, Windows 이고 Legacy 가 기존 동작이다.
  • Windows 에서 기본값은 Windows, 그 밖의 플랫폼에서는 Standard 다.
  • Windows 모드는 Standard 와 같되, cmd.exe, cscript.exe, find.exe, sqlcmd.exe, wscript.exe 와 .bat·.cmd·.js·.vbs·.wsf 파일에는 Legacy 방식을 쓴다.

이 환경에는 pwsh 가 없어 7 의 동작은 실행하지 못했다. 위 내용은 문서의 문장이며, 이 글의 5.1 우회(역슬래시 이스케이프, 헬퍼)가 7 에서 어떻게 동작하는지는 확인하지 않았다. 5.1 용 우회를 7 로 옮기기 전에 같은 방식으로 raw 와 argv 를 찍어 보는 것이 확실한 확인법이다.

상황별 선택표

5.1 에서 실측한 결과로 상황별 방법을 정리한다. 받는 프로그램은 파이썬, git, curl.exe 세 가지만 시험했다.

상황방법근거
공백·따옴표 없는 단순 인수그대로 쓴다실측, raw 와 argv 가 입력과 같음
공백이 든 변수 값"$v" 또는 $v 그대로실측, 한 인수로 감싸짐
값에 큰따옴표가 있음큰따옴표를 역슬래시와 큰따옴표로 치환해서 넘긴다실측, python·git·curl.exe 에서 모두 살아 도착
빈 문자열 인수큰따옴표 두 개를 값으로 넘긴다실측, 빈 문자열 한 개로 도착
끝이 역슬래시인 경로끝의 역슬래시를 떼거나 두 개로 한다실측, 뒤 인수가 합쳐지는 것을 방지
가변 인수 목록배열을 만들어 스플랫한다실측, 문자열 한 덩어리는 한 인수로 도착
따옴표가 많거나 여러 줄인 본문파일로 쓰고 프로그램의 파일 인수 옵션을 쓴다실측, curl.exe 의 파일 입력이 정확히 도착
명령줄을 글자 단위로 통제해야 함ProcessStartInfo.Arguments 와 직접 만든 이스케이프 헬퍼, 또는 Start-Process 에 문자열 하나실측, 헬퍼 아홉 건 일치
신뢰할 수 없는 입력, 배치 파일 경유인수로 직접 넘기지 않는다문서의 경고, 배치 파일에서는 인수가 cmd.exe 에 원문 명령줄로 전달됨

모든 행의 공통 원칙은 하나다. 받는 프로그램이 본 인수는 받는 프로그램이 찍어 보지 않으면 알 수 없다. 새 도구를 호출할 때는 먼저 인수를 세는 프로그램으로 같은 형태를 넘겨 raw 와 argv 를 확인하는 것이 이 표의 어느 행보다 확실하다.

확인하지 못한 것

  • PowerShell 7(pwsh): 환경에 없어 직접 실행하지 못했다. 7.3 이후의 인수 전달과 $PSNativeCommandArgumentPassing 세 가지 값의 동작은 공식 문서의 문장이다.
  • 5.1 의 우회(역슬래시 이스케이프, 겹따옴표, 헬퍼)가 7.3 이후에서 어떻게 동작하는지: 실행하지 않았다.
  • 파이썬·git·curl.exe 이외 프로그램: Node, Go, Java, .NET, 다른 MinGW 계열 도구의 명령줄 분해 규칙. 겹따옴표가 git 에서 실패한 이유는 확인하지 못했고 결과만 기록했다.
  • cmd.exe, .bat, .cmd 를 거치는 호출(npm.cmd 등): 실행하지 않았다. 문서는 배치 파일에서 인수가 원문 명령줄로 전달된다고 경고한다.
  • here-string 본문이 curl.exe 에서 중간에 끊긴 원인: 인수가 둘로 갈렸을 것이라는 추정이며 curl 쪽 인수를 직접 확인하지 않았다.
  • 다른 Windows 빌드나 로캘, 콘솔 코드페이지에서의 차이: 한국어 Windows 10 의 5.1.19041 하나에서만 확인했다. 비ASCII 인수는 파이썬 한 경우만 시험했다.
  • 5.1 이 인수를 다시 감싸는 내부 조건: 열네 개 문자열의 관찰과 맞는 규칙까지만 확인했고, 5.1 의 구현이나 문서로는 확인하지 못했다. 더 다양한 입력에서 이 규칙이 성립하는지도 시험하지 않았다.
  • Start-Process 의 -Verb 등 ShellExecute 경로, 호출 연산자 & 로 실행하는 경우: 다루지 않았다.
