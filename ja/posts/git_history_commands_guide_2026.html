もっと使うべき Git 履歴コマンド - pickaxe・log -L・bisect・reflog 実務ガイド

コミット一つひとつを掘り下げる log -S/-G・log -L・blame --ignore-rev・bisect・reflog、実務でいつどう使うか

2026年7月16日 開発・インフラ

序論: なぜ私たちは log と blame しか使わないのか

多くの開発者にとって「git の履歴を見る」とは、git log でコミットメッセージをざっと眺めるか、git blame でこの行を誰が書いたか確認する程度で終わる。しかし git はその二つのコマンドの裏に、はるかに精密な道具箱を隠し持っている。特定の文字列がいつコードベースから消えたかを見つける pickaxe(-S/-G)、特定の関数一つだけの変遷を抜き出す -L、バグが混入した正確なコミットを二分探索で見つけ出す bisect、誤って消したコミットさえ蘇らせる reflog といったコマンドだ。

本稿はこれらのコマンドを羅列する辞書ではなく、「こういうときはこのコマンドを使う」という実務シナリオ中心にまとめたガイドだ。文法は公式ドキュメントと複数の実践事例を突き合わせて整理しており(2026年7月時点の最新 git 基準)、各コマンドの限界や落とし穴も併せて押さえる。

1. git log の強化オプション - グラフとフィルタで絞り込む

本格的なツールに移る前に、素の git log もオプションを組み合わせるだけでかなり強力になる。複数のブランチが絡んだ履歴を一目で見るには、グラフオプションが欠かせない。

git log --oneline --graph --all --decorate

この組み合わせは全ブランチ(--all)をグラフ(--graph)で、タグ・ブランチ名まで表示(--decorate)し、1行ずつ(--oneline)出力する。ここに検索フィルタを重ねれば範囲を大きく絞れる。

git log --author="Kim" --since="2026-06-01" --until="2026-07-01" --grep="fix"

作成者・期間・コミットメッセージのキーワードで同時に絞り込むこの組み合わせは、「先月 Kim さんが直したバグ修正コミット」のような具体的な問いに直接答える。ここまで覚えるだけでも、ログをスクロールして目で探す習慣から抜け出せる。

2. git log -S / -G (pickaxe) - 「この文字列はいつ消えたのか」

pickaxe はコミットメッセージではなく実際のコード変更内容(diff)を検索対象にするオプションだ。「この API キー文字列を誰がいつ消したか」「この関数呼び出しがいつ追加されたか」といった問いに直接答える。

2.1 -S: 出現回数の変化を追跡

-S はリテラル文字列を対象に、その文字列が diff 内で出現した回数(追加-削除)が変わったコミットだけを見つける。大文字小文字を区別し、デフォルトは正規表現ではない。

git log -S'API_SECRET_KEY' --oneline -- src/

正規表現を使いたければ --pickaxe-regex を追加し、一致したファイルだけでなくそのコミットで変わったすべてのファイルを見たければ --pickaxe-all を付ける。

2.2 -G: 正規表現で「触れられた行」を追跡

-G'正規表現' は git 1.7.4 からあるオプションで、パターンに一致する行が diff のどこかに現れさえすれば検出する。-S と違い、出現回数がそのままでも、その行が移動したり微妙に修正されたりしていれば -G は検知する。

git log -G'function\s+parseConfig' --oneline

2.3 実践的な違い - コードが移動しただけのとき

たとえばある設定値がファイル内で位置だけ移動し総出現回数は変わらない場合、-S はこのコミットを見つけられない(回数変化がないため)。一方 -G はその行を含む diff ハンクが存在する限りコミットを検出する。まとめると-S は「ある・ない」の変化、-G は「その行に手を加えたすべての履歴」を見る。削除された機能の痕跡を探すときは -S から始め、それで見つからなければ -G に広げる順序が合理的だ。

3. git log -L - 特定の関数・行範囲の変遷

blame が「今この行を最後に直したのは誰か」を示すのに対し、-L は「この行(または関数)が時間とともにどう変わってきたか」を diff 形式で時系列に示す。

3.1 行範囲の指定

git log -L 120,150:src/parser.c

ファイルの120〜150行目が各コミットでどう変わったかを時系列で出力する。git がコミットを遡りながら該当する行ブロックを自動的に追跡し、範囲を調整してくれる。

3.2 関数単位の指定

git log -L :parseConfig:src/parser.c

:関数名:ファイル の形式は関数名を正規表現として扱い関数の開始位置を探し、言語別の userdiff ドライバ(C、Python、Java など内蔵サポート)を使って関数の終わりを判定する。git が関数の境界を自動検出できない場合は、正規表現で開始・終了行を直接指定することもできる。

git log -L '/^int parseConfig/',/^}/:src/parser.c

「この関数がなぜ今の形になったのか」を追跡するのに、これほど直接的な道具はない。複数のコミットにわたって少しずつ変わったロジックを diff で時系列に見ると、コードレビューだけでは見えない設計意図や回避策の履歴が浮かび上がる。

4. git blame を正しく使う - フォーマットコミットを無視する

素の git blame ファイル は強力だが大きな落とし穴がある。コード全体を再フォーマットしたり一括置換したりしたコミットが履歴に紛れていると、その行の本当の作成者ではなくフォーマットコミットばかりを指し続ける。

4.1 --ignore-rev で特定のコミットをスキップ

git blame --ignore-rev a1b2c3d4 src/app.js

git 2.23 から対応する機能で、無視されたコミットが触れた行はそれ以前に最後に変更したリビジョンに帰属する。複数を無視したい場合はオプションを繰り返すか、ファイルで管理する。

4.2 .git-blame-ignore-revs ファイルで管理

# .git-blame-ignore-revs
# 2026年5月の全体フォーマット(prettier適用)
a1b2c3d4e5f6...

git blame --ignore-revs-file .git-blame-ignore-revs src/app.js

ファイル名を慣例どおり .git-blame-ignore-revs にすると、GitHub がこれを自動認識し Web UI の blame ビューにもそのまま反映する。毎回オプションを付けるのが面倒なら、リポジトリの設定に登録しておけばよい。

git config blame.ignoreRevsFile .git-blame-ignore-revs

5. git bisect - バグ混入コミットの二分探索

「以前は動いていたのに今は動かない」という状況で、コミットを一つずつチェックアウトして目視確認するのは時間の無駄だ。bisect は良いコミットと悪いコミットの間を二分探索で絞り込み、原因コミットを正確に突き止める。

5.1 手動での二分探索

git bisect start
git bisect bad                 # 現在(HEAD)はバグがある
git bisect good v1.2.0         # このタグ時点では正常だった

以降 git が自動的に中間点のコミットをチェックアウトする。その状態で実際にテストし、結果に応じて git bisect good または git bisect bad を繰り返し入力すれば、log(N)回の試行で犯人コミットを見つけ出す。

5.2 git bisect run で完全自動化

テスト過程自体をスクリプト化できれば、全過程を自動化できる。スクリプトは終了コードで結果を伝える必要がある: 0=正常(good)、1〜127のいずれか(ただし125を除く)=バグ(bad)、125=このコミットはテスト不可(skip)だ。

git bisect start HEAD v1.2.0
git bisect run npm test

あるいはカスタムスクリプトを組むこともできる。

#!/bin/bash
# check.sh - ビルド後、特定のレスポンスを確認
npm run build || exit 125   # ビルド自体が失敗したら skip
curl -sf http://localhost:3000/health | grep -q '"ok":true' && exit 0 || exit 1

git bisect run ./check.sh を実行すると、git が自動的に二分探索しながらスクリプトを繰り返し実行し、人が介入しなくても原因コミットを見つけ出す。終わったら git bisect reset で元のブランチに戻る。

6. git reflog - 失ったコミットを取り戻す

誤って git reset --hard を間違った対象に実行してしまったり、リベース中にコミットが消えたように見えたりするとき、reflog が救世主になる。reflog は実際のコミットグラフではなく、HEAD とブランチが指していた位置の履歴をローカルに記録したものだ。

git reflog
# または
git reflog show HEAD

各エントリは HEAD@{0}、HEAD@{1} のように番号が振られ、その時点でどんな操作(commit、checkout、reset、rebase など)があったかも記録される。目的のエントリを見つけたら、まず git show <ハッシュ> や git checkout <ハッシュ> で内容を確認し、確信が持てたら元に戻す。

git reset --hard HEAD@{2}

ただし reflog は永久ではない。現在のブランチから到達可能なエントリはデフォルト90日(gc.reflogExpire)、どこからも到達不可能になったエントリはデフォルト30日(gc.reflogExpireUnreachable)を過ぎると、git gc 実行時に整理される。事故直後にできるだけ早く確認する習慣が安全だ。

7. git log --follow - 名前が変わったファイルの歴史をつなぐ

ファイルを移動したり名前を変えたりすると、git log ファイルパス はその名前に変わって以降のコミットしか表示しない。--follow を付ければ、名前変更を越えて元のファイルの履歴までつなげて表示する(単一ファイルにのみ適用される)。

git log --follow -p -- src/utils/format.js

ここに -p を加えると、各コミットで実際に何が変わったかを diff まで併せて確認できる。リネームを検出するしきい値を調整したいなら -M(または --find-renames)オプションを併用する。

削除されたファイルやコードを取り戻したいときも同様の原理を使う。まずどのコミットで削除されたかを見つけ、

git log --diff-filter=D --oneline -- src/legacy/old_parser.js

そのコミットの親リビジョンからファイルを復元する。

git checkout <削除されたコミット>^ -- src/legacy/old_parser.js

8. git rev-list / git shortlog - スクリプティングと統計

rev-list は人が読む log と違い、コミットハッシュだけを列挙する低水準(plumbing)コマンドなのでスクリプトに組み込みやすい。shortlog は作成者ごとにコミットを集計し統計を出す。

git rev-list --count HEAD                 # 全コミット数
git rev-list --count v1.0.0..v2.0.0        # 2つのタグ間のコミット数
git rev-list --count --since=yesterday HEAD

git shortlog -sn --no-merges              # 作成者別コミット数、マージ除外
git shortlog -sn --all                    # 全ブランチ基準

CI スクリプトで「今回のリリースにコミットがいくつ入ったか」「この期間で誰が一番多くコミットしたか」を出すとき、この二つのコマンドの方がはるかに軽くパースしやすい。

9. シナリオ別に何を使うか

実務ではコマンド名より「今知りたいことは何か」から出発する方が速い。以下の表に整理した。

知りたいこと使うコマンド
このバグが正確にいつ入ったかgit bisect(runで自動化)
このコードがなぜ今の形になったかgit log -L :関数:ファイル
この行を最後に直した人は誰か(フォーマットコミットを無視)git blame --ignore-revs-file
削除された文字列・設定値がどこへ行ったかgit log -S(見つからなければ -G)
誤って消したコミットを復元したいgit reflog + reset --hard
名前が変わったファイルの過去の履歴が知りたいgit log --follow
リリース統計・CIスクリプトにコミット数を入れたいgit rev-list --count、git shortlog -sn

10. 関連情報 - コミットを「書き換える」側も進化中

本稿は履歴を探索するコマンドに焦点を当てたが、最近の git 2.54〜2.55 では履歴を書き換える側にも新しい実験的コマンドが追加された。git history reword、git history split、git history fixup は、過去のコミットのメッセージを直したり、一つのコミットを二つに分割したり、ステージされた変更を古いコミットに畳み込んだりしながら、それ以降のブランチを自動的にリベースしてくれる。rebase -i の代表的な使用パターンをより安全に包んだものだが、まだマージコミットを扱えないなどの制約があり、実務導入は慎重に検討する段階だ。履歴を「読む」本稿のコマンドと対になる流れとして覚えておくとよい。

結論: 道具はすでにある、あとは習慣だけ

ここで紹介したコマンドのどれも最近追加されたものではない。-S は git の初期から、--ignore-rev だけが比較的最近(2.23)で、残りはすべて昔から存在していた。問題は道具がないことではなく、log と blame の外に出てみる習慣がなかったことにある。次に「このバグはいつ入ったのか」という疑問が浮かんだら、コミットを一つずつチェックアウトする代わりに bisect を、「この文字列はどこへ行ったのか」が気になったら全ファイルを grep で探す代わりに log -S をまず思い浮かべよう。誤って消したコミットの前でパニックになる前に reflog をまず確認する習慣を一つ身につけるだけでも、履歴探索にかける時間は目に見えて減る。
