What Deleting Site Data Leaves Behind - When the Browser Vendor Also Runs Services on It

What the setting promises, where the exemptions sit, and the screen a user can read for themselves

2026-09-07 Tech & IT

Somewhere in every modern browser there is a switch that offers to delete the data websites have stored on the device. The mental picture a person forms when flipping that switch and the range of storage the implementing code actually walks are not the same thing. The gap between them almost always opens on a single word, and that word is site.

Where does a site end and where does a browser feature begin? The answer decides what the same click removes and what it leaves untouched. And there is a structural wrinkle worth naming early: the organisation that draws that line and the organisation that benefits from where the line lands can be the same organisation. That is not an accusation about anyone's character. It is a description of an arrangement, and arrangements can be examined calmly.

Everything stated as fact below comes from the browser settings string resources, the Chromium source tree, administrator policy definitions, and each vendor's own documentation. Observations from a personal blog are attributed as observations. Anything that could not be matched against a primary source was kept out of the body and collected near the end with the reason attached.

The trigger - an exemption from what, exactly

The piece that circulated in early September 2026 is a personal blog post. Jeff Johnson, who builds Mac software, published it on his own site, and the headline says that Chrome once again exempts Google from the user's site data settings. It is written in a tone aimed squarely at one vendor, and saying so up front makes the rest of the reading easier rather than harder.

The detail that falls out first as a story is copied and summarised is which setting the exemption is supposedly an exemption from. Here the answer is narrow and specific. It is the second of three choices at chrome://settings/content/siteData, the one that deletes what sites have saved to the device once all windows are closed. It is not third-party cookie blocking in general. It is not ad tracking in general. It is one radio button on one screen.

The procedure described in the post runs like this. Turn that choice on. Without being signed in to Chrome, run a single Google search. Close every window. Then look at the on-device site data list. According to the post, an entry for www.google.com remained, holding roughly 1,216 KB, and it survived a restart of the browser as well. The kinds of data still present are given as cookies, local storage and session storage. The version tested is given as 152.0.7977.83. The author adds that his screenshots were meant as explanation rather than proof, and he explicitly declines to assert intent.

The same author wrote a post along similar lines in 2020, and the current post says the earlier issue was eventually fixed. The word again in the headline points at that history. Everything above is an observation. Observations and rules carry different weight, so the cleanest way to begin is to separate them in a table before going any further.

Pinning down the sentence the setting promises

In Chrome this setting is named On-device site data, and the path is Settings, then Privacy and security, then Site settings, then Additional content settings, then On-device site data. The paragraph at the top of that page says a site you visit can save information about what you are doing so that it works as expected, and it offers keeping you signed in and saving items in a shopping cart as the two examples. Below that paragraph sit three radio buttons under the heading Default behavior.

ChoiceThe sentence on screenThe consequence shown alongside
AllowAllow sites to save data on your deviceSites are more likely to work as you would expect
Delete on closeDelete data sites have saved to your device when you close all windowsThe help page says sites are less likely to remember you from one visit to the next
BlockDo not allow sites to save data on your device, marked not recommendedSites may not work as you would expect
Customized behaviorsSites listed below follow a custom setting instead of the defaultTwo lists: allowed to save data on your device, and not allowed

This is where the gap opens. The help page names the three choices and describes their effect in broad terms. What it does not describe is what happens when an entry in the customized list conflicts with the default, which of the two wins, or what routes exist for an entry to appear in that list in the first place. The word a user reads on screen is default, but the actual decision is not settled by the default alone. There is a second stage, and the second stage is where every interesting case lives.

Site data is not one thing

Under the single phrase site data sit several storage systems with different lifetimes, different scoping rules and different APIs. The routine that runs when the last window closes follows exactly those divisions, so it is worth having them laid out before reading any code.

  • Cookies — values a server sets through a header and the browser replays on subsequent requests. Their scope is defined by domain rather than by origin, which matters more than it sounds
  • Local storage and session storage — key and value stores written by scripts. Session storage is bound to the lifetime of a tab, local storage is not
  • IndexedDB — a structured database, typically the largest of these by volume, and the usual home for offline application state
  • Cache storage and service workers — the store that holds offline responses, plus the registration record that controls it
  • Origin Private File System and Storage Buckets — a file hierarchy private to an origin, and the newer API for dividing storage into separately evictable units
  • The HTTP cache — not a store the site controls but a copy the browser keeps for performance. A separate category with separate rules

The code Chromium runs when every window closes splits into two paths. Non-cookie storage is cleared per storage area in one sweep, and cookies are handled on their own. The comment in the source gives the reason plainly: cookies are not scoped by origin, so they cannot ride along with an origin-based matcher. The function that answers the question is this origin session only then does something worth pausing on. It reads the cookie content setting and nothing else.

// chrome/browser/sessions/session_data_deleter.cc
bool OriginMatcher(const blink::StorageKey& storage_key,
                   storage::SpecialStoragePolicy* policy) {
  return policy->IsStorageSessionOnly(storage_key.origin().GetURL()) &&
         !policy->IsStorageProtected(storage_key.origin().GetURL());
}

// chrome/browser/extensions/extension_special_storage_policy.cc
bool ExtensionSpecialStoragePolicy::IsStorageSessionOnly(const GURL& origin) {
  return cookie_settings_->IsCookieSessionOnly(origin);
}

So the state a person picks on the On-device site data screen is stored internally as the cookie content setting, and that single value governs the fate of storage that has nothing to do with cookies. Two concepts in the interface are one concept in the code. Knowing only this, a situation where a cookie exemption produces surviving local storage stops being mysterious and becomes the expected consequence of a shared code path.

Where the site ends and the browser feature begins

What this setting governs is what a site saved. What the browser itself saves lives in a different compartment, and that compartment is outside the reach of this switch. The profile directory holds both kinds in one folder. The Profile Path shown at chrome://version points at it, and while site storage sits there, so do browsing history, bookmarks, preferences and extension data.

Storage used by browser features does not travel through the storage APIs a web page can call, which is precisely why the site data deletion routine never looks at it. Sync state, the lists Safe Browsing downloads in advance, the history the address bar consults when suggesting completions, translation preferences — none of these are stores a site created. They belong to other entries on the delete browsing data screen, or to account settings that live on a server rather than on the device.

The boundary is therefore drawn twice, not once. The first line asks whether the data sits in site storage or in browser-internal storage. The second line asks how far the deletion routine has been written to sweep. And the second line has explicit exceptions of its own. The Chromium source classifies origins on the extension scheme, together with hosted apps the user installed, as protected storage and skips them during the on-close sweep. The same function is careful to state that apps installed by default do not receive this protection.

This exception has nothing to do with any particular company. It is browser-level design, and the reason is obvious once stated: an extension that lost its configuration every time the last window closed would be unusable. The existence of exemptions is not the finding. The finding worth pursuing is always which exemptions exist and where they are written down.

The exemptions that are written down - account and activity

Chrome's help page on deleting browsing data contains three sentences that most people skim past. All three narrow the meaning of the word deleted, and none of them are hidden. They are printed in the documentation, which is the important part.

  • If you delete cookies while signed in to Chrome, you will not be signed out of your Google Account
  • Cards and addresses saved in the Google Account are not removed by this action
  • Searches and other activity on Google services are saved to the account and are deleted separately from the account side

The enterprise policy documentation carries a matching statement in the same place. The policy that lets an administrator choose which categories are wiped when all browser windows close is described with the sentence that the user will stay signed into their Google account when cookies are deleted. The same description adds a second condition that changes how the whole feature should be read: if the browser or the operating system does not exit cleanly, that round of deletion does not occur at all, because the shutdown was not the result of the user closing all the windows.

This is the heart of the matter. The action labelled delete site data is designed not to disturb account state, and that design is documented. The point where a user's expectation of deletion and the documented scope of deletion diverge is exactly this line. And the placement of that line is simultaneously a technical judgement and a commercial one. Staying signed in is genuinely convenient for the person using the browser, and it is also valuable to whoever operates the account system. Both descriptions fit the same behaviour equally well, which is why the placement deserves documentation rather than trust.

The precedence the code sets - one allow entry beats deletion

On the cookie side the decision lives in one Chromium function with a clearly ordered sequence of checks. That sequence is the precise location of the slot where an exemption can sit, so it repays being read line by line rather than summarised loosely.

  1. If the cookie setting for that origin is allow, the cookie is not a deletion candidate and the function returns immediately
  2. Otherwise the exception entries are walked, and if any entry whose domain matches is set to allow, the cookie is again not a deletion candidate. Session-only entries merely raise a flag
  3. Finally the cookie is deleted if the effective setting is session only, or if a session-only rule matched during the walk
// components/content_settings/core/common/cookie_settings_base.cc
ContentSetting setting = GetContentSetting(
    origin, GURL(), ContentSettingsType::COOKIES, &setting_info);
if (setting == CONTENT_SETTING_ALLOW) {
  return false;              // do not delete
}
for (const auto& entry : cookie_settings) {
  if (net::cookie_util::IsDomainMatch(domain, host)) {
    if (entry.GetContentSetting() == CONTENT_SETTING_ALLOW) {
      return false;          // a single allow entry wins
    } else if (entry.GetContentSetting() == CONTENT_SETTING_SESSION_ONLY) {
      matches_session_only_rule = true;
    }
  }
}
return setting == CONTENT_SETTING_SESSION_ONLY || matches_session_only_rule;

Even with the default set to delete on close, a single allow entry with a matching domain wins. Domain matching works so that a rule written on a registrable domain reaches its subdomains too, which means one line can cover a whole family of hosts rather than a single one. And, per the previous section, the same content setting value also decides whether the non-cookie storage for that origin is swept.

The administrator policy documentation carries a warning in the same spirit. Where the allow, block and session-only URL policies contain overlapping patterns, the documentation states that it is unspecified which policy takes precedence. An unspecified precedence is by definition an area where behaviour may differ between versions, which is a reason to record versions whenever behaviour is described.

All of which means the observation that an exemption exists does not, on its own, identify a cause. The slot for exemptions is already part of the design, and it is surfaced in the interface under the heading Customized behaviors. The remaining question is what ended up in that slot and by which route, and that is a question a running profile answers, not a document.

The fine print attached to closing all windows

The conditional clause deserves reading as carefully as the promise. The trigger for this setting is closing all windows, not quitting the browser, and those are not the same event on any desktop operating system.

If a single window remains open, the routine never runs at all. A background app setting or a tray-resident process can keep the browser alive in a state that looks, to the person at the keyboard, exactly like everything having been closed. An unclean shutdown produces the same outcome by a different route, and here the policy documentation is explicit that the deletion for that round is skipped.

Configuring the browser to restore the previous session on startup adds another branch. In that configuration the shutdown routine skips the step that performs a blanket removal of session cookies, meaning cookies with no expiry. Entries caught by a session-only rule are still cleared. Two deletions with different scopes are entangled here, and nothing on the settings screen indicates that one of them has been switched off by a choice made on a different screen entirely. In the same routine, session-only origins also have their media device identifiers and their session-only trust token data cleared, which is a reminder that the sweep touches more categories than the interface enumerates.

Put together, a state in which nothing was deleted is far more often a condition that never held than a malfunction. When surviving data turns up, this is the first fork to take.

What a site means after partitioning

The word site has been subdivided once more over the last few years. Chrome has applied storage partitioning to all users since version 115. The key for storage is no longer an origin alone but the combination of the origin and the top-level site, with an additional bit recording whether a cross-site frame appeared anywhere in the ancestor chain.

  • Storage APIs — the quota system, local and session storage, IndexedDB, Cache Storage, the Origin Private File System, Storage Buckets, the reach of the Clear-Site-Data header, and the blob URL store from version 137 onward
  • Communication APIs — Broadcast Channel, SharedWorker and Web Locks are keyed the same way
  • Service workers — registrations made from third-party contexts are partitioned to close timing side channels

The consequence is that the local storage belonging to a given domain is not one thing. It divides into as many compartments as there are top-level sites under which it was created. An entry that collapses into a single domain row in a settings list may in fact be the sum of several partitions. This is one concrete reason a residual byte count alone is a weak basis for concluding which site put it there.

Cookie scoping is a separate axis from all of this. Whether a cookie rides along on a given request is settled by the decision table SameSite builds per request type. Recognition techniques that need no storage at all form yet another axis, and as covered in the piece on tracking with nothing to delete, they sit entirely outside the reach of any deletion setting.

Other browsers have the same slot

Every browser that offers deletion on exit ships exemption machinery alongside it, because without exemptions features such as staying signed in could not exist. What differs between vendors is the naming and, more consequentially, the density of documentation.

BrowserDeletion mechanism on exit or elapsed timeDocumented exemptionsNature of the source
Chrome and ChromiumOn-device site data delete on close, plus the administrator policy listing categories to clear on exitThe customized allow list, the policy allow URL list, protected storage, and the account remaining signed inSettings strings, source, policy definitions, help pages
FirefoxAdministrator policy for sanitising on shutdown, category by category across cache, cookies, history, sessions and site settingsA list of origins whose cookies and site data are not cleared at shutdown, available from version 154, plus the allow and session-allow lists in the cookies policyOfficial administrator documentation
Safari and WebKitScript-writable storage removed after a fixed period without user interaction on the siteWeb apps added to the home screen keep separate counters and are excluded, plus grants obtained through the Storage Access APIThe engine team's official blog
EdgeClear browsing data on closeA do-not-clear site listA support representative's forum answer rather than product documentation

The Edge row in particular needs its provenance kept visible. In a public question and answer thread, a Microsoft support engineer wrote that default cookies for the company's own domains not being removed is by design behaviour. That is an answer from a support channel, not a rule published in product documentation, and the two carry different evidential weight when quoted. It is nonetheless entirely sufficient to establish the point that matters here: the same arrangement exists at more than one vendor.

The Firefox exemption is a recent addition rather than a long-standing one. The list of origins spared at shutdown arrived with version 154; before that the policy offered only per-category switches. Recognition that exemptions need to exist, and then need to be written down, tends to arrive late, but it does arrive.

When the line drawer and the beneficiary overlap

When the organisation that builds a browser also runs search, advertising and account businesses on top of it, the party deciding where the border between site and browser feature falls and the party that gains from where it falls are the same party. This is a statement about arrangement, not about character. The same arrangement recurs elsewhere: an operating system vendor shipping the default browser, a search company building a browser engine, a content company operating the distribution channel its own content travels through.

What the arrangement produces is not a conclusion but a direction for the burden of proof. When a boundary happens to fall in a place favourable to the vendor's own services, an outsider cannot easily distinguish functional necessity from commercial convenience. An exemption that keeps a person signed in is a genuine convenience and an asset to the account business at once. Two explanations account for the same behaviour with equal ease, and no amount of arguing about motive will separate them.

Which is why, in arrangements like this, documentation substitutes for trust. Write the exemption down. Put the list somewhere a person can open it. If a precedence order exists in the code, state the order. Within a single product this density varies noticeably. The account-stays-signed-in exemption appears in two places, the help page and the policy description. The on-device site data page, by contrast, says nothing about an allow entry outranking the default. That rule is legible only in the source and in the policy definitions, which is to say, legible only to people who already know where to look.

The lesson travels straight into ordinary engineering work. If one setting silently governs several storage systems, if an exception list quietly outranks the default, and if there is a region where precedence is deliberately left unspecified, those are facts that belong in the documentation rather than in the reader's inference. The distribution of power around ad blocking and extension APIs is the same structure wearing a different face.

The procedure a user can follow

The settings screen shows state. The storage screens show outcome. When the two disagree, the answer is always on the second one, so it is worth knowing the addresses before needing them.

chrome://settings/content/siteData      three default choices plus customized lists
chrome://settings/content/all           on-device site data list, per-site volume
chrome://settings/clearBrowserData      delete browsing data, category by category
chrome://version                        Profile Path — where this profile is stored
chrome://extensions                     installed extensions
  1. Read which of the three default behaviours is currently selected on the settings screen
  2. Read the two customized lists below it. Any site appearing there is not following the default at all
  3. Read the on-device site data list for surviving sites and volumes, remembering that one domain row may be the sum of several partitions
  4. Close every window, reopen the browser, and read the same list again. If a window was still alive, the condition simply never held
  5. Split the result by type in the Application panel of DevTools, where Cookies, Local storage, Session storage, IndexedDB and Cache storage are separate entries and the storage overview shows the usage breakdown

Profiles and Guest windows divide scope by a different mechanism. A profile is a subdirectory inside the user data directory, so separating profiles separates storage. A Guest window, according to Chrome's own help page, deletes browsing history, cookies and site data from the computer when the session ends. The same page states the limits alongside the promise: the activity remains visible to the sites visited, to sites signed in to, to whoever runs the network, to the internet service provider and to search engines. Leaving nothing on the device and not being observed are two different claims, and only the first one is being made.

How to read the next report of this kind

Reports of surprising browser behaviour will keep arriving. Six separations put almost all of them in their proper place without needing to decide who is right.

  • An exemption from which setting — is the setting named, with its screen path? Blocking third-party cookies and deleting data on close are different features with different code paths
  • Observation or rule — one person's reproduction is an observation; official documentation and source are rules. Observations do not overturn rules, and rules are obliged to explain observations
  • Is there a control — does the report include the result of running the same procedure against other sites, under the same conditions?
  • Does a slot for exemptions already exist — if it does, witnessing an exemption is not by itself an identification of cause
  • Is the version recorded — browser behaviour changes between versions, and regions of unspecified precedence change most of all
  • Is the sentence about intent or about behaviour — intent cannot be settled by documents. Keep only the behavioural claims and what remains is considerably firmer

None of this is specific to browsers. Inferring a server-side rule from something observed on the client happens everywhere, and where that inference breaks down is the same problem examined in the piece on trust boundaries.

What could not be confirmed

The following items were kept out of the body as statements of fact because no primary source could be matched to them. The reason is recorded beside each one.

  • The reported behaviour itself — the observation that a particular domain's data survives shutdown is a reproduction result and is not corroborated by any official document, so the body attributes it as an observation only. The version cited, 152.0.7977.83, is a genuine released stable build number, and the stable release at the time of writing is 153.0.8010.27. Different versions can produce different results
  • Whether Chrome ships a default allow entry for any particular domain — neither the settings string resources nor the help pages define such a thing. This cannot be settled without reading the exception list inside a running profile
  • The cause of the observed residue — an allow entry, an extension, session restore, an unclean shutdown and a lingering background process all produce the same symptom. The original post says several of these were ruled out, but it does not claim that every remaining route was eliminated
  • When and by what change the 2020 issue was fixed — the current post says it was fixed but gives no change identifier, version or Chromium issue number for it
  • The extent of the control group — the post says the domain in question appears to be the only one exempted, while also noting that its screenshots were explanation rather than proof. How many sites were compared, and under which conditions, is not stated
  • Product documentation defining the Edge behaviour — the statement that the company's own domain cookies persisting is by design appears only in a support channel answer. No equivalent product document was located
  • The per-feature storage locations in Chrome's privacy whitepaper — that document renders its body through script, so a plain static request returns only the shell. Browser-internal storage locations were therefore described only within what help pages and source make explicit
