dbtrail — MySQLのバイナリログで作る巻き戻し可能なデータタイムマシン

誤ったUPDATEも消してしまった行も秒単位で戻す - binlogベースのCDCが監査と復旧を変える

2026-07-07 開発・インフラ

序論：WHERE句のないUPDATEを実行した瞬間

夜11時、本番DBにUPDATE orders SET status = 'cancelled'という一行を実行してしまった。WHERE句を書き忘れたまま。数秒後にSlackに通知が殺到し、そこでようやく何が起きたのかに気づく。この状況を経験したことのないバックエンドエンジニアは少ない。問題はその後だ。最新のフルバックアップが前夜のものなら復元には数時間かかり、その間に正常に積み上がったデータまで一緒に失われる。Point-in-Time Recovery(PITR)で事故直前まで戻したとしても、戻す単位は依然としてデータベース全体か、少なくともテーブル全体だ。あの一行の誤りだけをピンポイントで戻す方法は長らく存在しなかった。

2026年7月、GeekNews(hada)で紹介されたオープンソースプロジェクトdbtrailは、この狭い隙間を正確に狙う。MySQLのバイナリログ(binlog)をリアルタイムでtail(追跡)し、全行変更をbefore/afterイメージとともに検索可能な索引として蓄積し、必要ならその変更一つだけを戻す。本稿ではdbtrailの原理をbinlogベースのCDC(Change Data Capture)の観点から解き明かし、既存のバックアップ・トリガー・監査ログ・Debeziumといった手法と比較しながら、実務にとってどのような意味を持ち、どのような限界を抱えて導入すべきかを分析する。

1. dbtrailとは何か - binlogをtailする監査・復旧ツール

1.1 核心アイデア：全行変更を索引化する

dbtrailのGitHubリポジトリは自らを「Time-travel for your MySQL」(GitHub, dbtrail/dbtrail)と紹介する。表現は派手だが、やっていることは単純明快だ。MySQLのバイナリログに記録される全てのINSERT・UPDATE・DELETEをリアルタイムで読み取り、変更前(before)イメージと変更後(after)イメージを合わせて別の検索可能なストアに蓄積する。この索引があれば、この行がいつ、誰によって、どのように変わったのかを推測ではなく実際のクエリで確認でき、誤った変更であれば正確な復旧用SQLを自動生成して元に戻せる。CASCADEで一緒に削除された子行まで復旧対象に含める点も注目に値する。

1.2 アーキテクチャ：レプリケーションプロトコル、ファイルは不要

dbtrailはbinlogファイルを直接開いて解析しない。代わりにMySQLのレプリケーションプロトコルで対象サーバーに接続し、自らを一つのレプリカ(複製スレーブ)のように登録してストリームを受け取る。その結果、ディスク上のbinlogファイル自体にアクセスする必要がない。この設計選択は些細に見えるが実務への影響は大きい。Amazon RDS・Aurora、Google Cloud SQL、Percona Serverのようにファイルシステムアクセスが制限されたマネージドクラウドMySQLでもそのまま動作するという意味だからだ。binlog2sqlのような従来型ツールが往々にしてローカルのbinlogファイルパスを前提とするのとは対照的である。

1.3 インストールとインターフェース：Webコンソール、MCPサーバー

インストールはcurl一行でDocker Composeスタックを立ち上げる方式だ。その後127.0.0.1:8090のWebコンソールで対象MySQLサーバーを登録すればすぐに監視が始まる。インターフェースとしてWebコンソールとともにMCP(Model Context Protocol)サーバーを提供する点は2026年らしい設計である。AIコーディングエージェントや運用チャットボットが「昨日午後3時にordersテーブルで何が起きたか」を自然言語で問い合わせ、必要なら復旧SQLの草案まで受け取れる経路が開かれるという意味だ。人がダッシュボードを漁る代わりにエージェントが一次調査を代行する流れは、障害対応(オンコール)の初動対応時間を短縮する実質的な利点につながり得る。

1.4 要件と対応範囲

dbtrailはMySQL 8.0以上を要求し、binlog_format=ROWとbinlog_row_image=FULLの設定が必須である。Percona Server、Amazon RDS/Aurora、Google Cloud SQLなど主要なマネージド・派生ディストリビューションを対応対象として明示する。ライセンスはApache-2.0で、商用利用や本番デプロイに制約はない。

2. binlogベースCDCの原理 - なぜロックフリーかつ非侵襲的なのか

2.1 ROW形式とbefore/afterイメージ

MySQLのbinlogはSTATEMENT、ROW、MIXEDの3形式に対応する。STATEMENTは実行されたSQL文自体を記録し、ROWはそのSQLが実際に変更した各行の値を記録する。dbtrailのようなCDCツールがROW形式を要求する理由は明確だ。UPDATE users SET point = point + 10 WHERE active = 1という文だけでは、実際にどの行がどの値からどの値へ変わったのかを再構成できない。ROW形式はその結果を行単位でそのまま残す。ここにbinlog_row_image=FULLを加えると、変更された列だけでなく行全体の変更前・変更後の値がすべて記録され、正確な復旧SQLを作る材料が揃う。

2.2 レプリカを装うことの意味

binlogはもともと複製(レプリケーション)のために存在するログである。MySQLのプライマリは自身に接続されたレプリカへこのログをストリーミングで流し、レプリカはそれを受け取って自らのデータを追随更新する。dbtrailはこの流れにレプリカをもう一つ挟み込むのと変わらない。つまりアプリケーションが実行するトランザクションのコミット経路には一切関与せず、その結果がすでに作られたログを後ろから読むだけだ。トランザクションを処理するコネクションプールやロックマネージャの立場からすれば、dbtrailは存在しないのと同じである。

2.3 スキーマ変更も性能低下もない

この非侵襲性が実務的に意味するところは3つある。第一に、監査対象テーブルにトリガーや監査カラムを追加する必要がない。第二に、アプリケーションの書き込み経路に追加のレイテンシが生じない。トランザクションはdbtrailの存在を知らないまま普段通りコミットされる。第三に、事前にどのテーブルを監査するか選択(opt-in)しなくても、インスタンス全体の変更を遡って捕捉できる。今日事故が起きたテーブルが昨日は監査対象ではなかったという後悔が構造的に減る。

3. 行単位で元に戻すことの実務的価値

3.1 「全体復元」と「一行だけの復旧」の違い

従来のバックアップ復元は単位が大きい。スナップショットやフルバックアップで戻すと、事故時点以降に正常に積み上がった他のデータまで一緒に消えてしまう。PITRでbinlogを再生し特定の秒単位まで復元しても、その時点以降の正しい変更と誤った変更を見分ける方法はない。dbtrailが示す答えは違う。問題となった行(または複数行)だけを選び、その行の変更前イメージへ正確に戻すSQLを生成する。事故時点以降に他のテーブル・他の行に積み上がった正常データには手を触れない。全体を数時間前に戻すことと、この100行だけを5分前に戻すことでは、復旧時間と副次被害の規模が桁違いである。

3.2 誰が変更したかを追跡すること

dbtrailは各変更を引き起こしたDBユーザー、接続ホスト、クライアントプログラムまで併せて索引化する。昨日のあのバッチスクリプトがこの値を変えたのか、それとも誰かがコンソールから直接手を加えたのかは、事故原因分析における常に最初の問いである。この問いにログを漁らず即座に答えられることは、監査(audit)の観点から実質的な価値がある。

3.3 戻す前の検証が必要な理由

dbtrailは復旧SQLを自動生成するだけでなく、復旧の安全性を検証する機能も併せて提供するとしている。これは重要な設計判断である。自動生成されたロールバックSQLであっても、その間に同じ行が再度変更されていたり、参照整合性制約のかかった他のテーブルが一緒に変わっていれば、そのまま適用したときに新たな事故を生む可能性がある。自動生成イコール無条件に安全ではないという前提の上に検証段階を置くのは正しいアプローチである。

4. 既存手法との比較

4.1 バックアップ + PITR

最も古い安全網である。定期フルバックアップにbinlogを順次再生し、任意の時点まで復元する。長所は実績のある成熟度と、災害復旧全般をカバーする汎用性だ。短所は復元単位がインスタンスまたはスキーマ全体に近く、戻す時点の選択も秒単位以下で精密に下すのが難しい点、復元自体にかなりのダウンタイムがかかる点である。

4.2 トリガーベースの監査テーブル

UPDATE・DELETEの時点でトリガーが変更前の値を別テーブルへコピーしておく方式だ。実装が直感的で追加インフラが不要な点が長所である。しかし監査対象テーブルごとにトリガーを個別に作る必要があるopt-in構造であり、トリガー自体が毎回のDML実行経路にかかる追加負荷となる。何より最初からトリガーを設定していないテーブルは事故が起きても手の打ちようがない。

4.3 監査ログプラグイン・クエリログ

MySQL Enterprise Audit、Percona/MariaDB Audit Plugin、あるいはgeneral_logは実行されたクエリ自体を記録する。誰が何を実行したかというコンプライアンス目的の監査には強いが、そのUPDATEが実際にどの値をどう変えたのかまでは別途再構成する必要がある。general_logはオーバーヘッドが大きく常時運用より短期調査向きであり、専用の監査プラグインも有効化自体に若干の負荷が伴う。

4.4 binlog2sql - 最も近い前身

binlog2sqlはbinlogを解析して生のSQLへ変換し、DELETE/UPDATEに限りロールバックSQL(フラッシュバック)を生成するオープンソースツールである。dbtrailのアプローチと発想が最も近い。ただしbinlog2sqlは事故発生後に必要な際、ローカルのbinlogファイルを対象にオフライン解析するコマンドラインツールに近く、DDLは扱わない。dbtrailはこれを常時ストリーミング索引とWebコンソール・MCPインターフェースへ拡張した形と見ることができる。

4.5 Debezium + Kafka - CDCプラットフォームとの違い

DebeziumもbinlogをレプリカのようにReadし、ROW形式のbefore/afterイメージをイベント化するという点で原理はdbtrailと同じである。違いは行き先にある。DebeziumはそのイベントをKafkaトピックへ流す汎用ストリーミングCDCプラットフォームであり、検索可能な監査履歴やロールバックSQLの生成はそのイベントを消費する側で自ら構築しなければならない。dbtrailはその消費ロジックまで含め、監査・復旧という単一目的に最適化された完成品に近い。Kafkaクラスタの運用負担なしにすぐ使えることが実務的な長所だが、データパイプライン全般に再利用できる汎用性はDebeziumより狭い。

5. 設計の変遷 - Bintrailからdbtrailへ

興味深いのは、dbtrailの公式ブログ(blog.dbtrail.com)に残る過去の記事が、今とは異なる名前とインターフェースを示していることだ。ある記事は「Bintrail」という名前で、ProxySQLシムの背後でSELECT * FROM _flashback.orders AS OF '2026-04-15 09:30:00'のようなSQL構文を直接拡張し、時点照会を支援するアーキテクチャを紹介している。一方、現在のGitHubリポジトリのdbtrailはProxySQLなしにレプリケーションプロトコルで直接接続し、照会はSQL構文の拡張ではなく別のWebコンソールとMCPサーバーで処理する。正確な内部経緯は確認できないが、同じブログドメインに残るこの痕跡は、プロジェクトがリブランディングとともにインターフェース設計自体も「SQLの中に時間旅行構文を組み込む」方式から「別の照会チャネルを設ける」方式へ移行したことを示唆していると推測される。これは設計の選択肢が一つではないことを物語る。SQL構文の拡張は既存のクエリと自然に混ざる一方でプロキシ層とパーサの複雑さを増し、別インターフェースは統合負担が少ない代わりに運用者が別のツールを学ぶ必要がある。

6. 本番導入時の考慮事項

6.1 ストレージ - FULL row imageのコスト

binlog_row_image=FULLは変更された列だけでなく行全体の前後イメージを記録するため、MINIMAL設定に比べbinlog自体の容量が目立って増える。秒間書き込みが多いテーブルほどこの差は大きくなる。ここにdbtrail自体が蓄積する索引ストレージの容量まで加わるため、導入前に現在の書き込みスループットを基準に日次・月次の増分容量を見積もっておく必要がある。

6.2 性能 - レプリカが一つ増えるということ

dbtrail自体はトランザクション経路に関与しないが、MySQLプライマリの立場からすればレプリケーション接続が一つ増えるのと同じである。すでに複数のレプリカが接続されている環境なら実質的な負担は軽微だが、ネットワーク帯域幅とプライマリのbinlog送信スレッドの負荷は定量的に確認しておくのが安全だ。

6.3 保持期間ポリシー - 監査要件とコストの綱引き

どこまで過去に戻せるかは結局dbtrailが索引をどれだけ長く保持するかにかかっている。規制産業の監査要件(例:1年以上の履歴保管)とストレージコストは正面から衝突する。binlog自体の失効ポリシー(例:binlog_expire_logs_seconds)とdbtrail索引の保持ポリシーを別個に設計し、実際に必要な巻き戻し期間(通常は数日〜数週間)と規制上必要な閲覧期間(長ければ数年)を区別して取り組むのが合理的である。

6.4 マネージドクラウドDBとの相性

レプリケーションプロトコルベースの設計のおかげで、RDS・Aurora・Cloud SQLのようにファイルシステムアクセスが制限された環境でも同様に動作する点は実務上大きい。ただしマネージドサービスごとにbinlog_row_image=FULLのようなパラメータグループの変更権限やレプリケーションユーザーの作成手順が異なるため、クラウド提供者ごとの設定ガイドを先に確認する必要がある。

6.5 個人情報と「忘れられる権利」との衝突

全行変更を遡って、しかも別ストアにほぼ永続的に蓄積するという設計は監査には強みだが、個人情報保護要件とは緊張関係に置かれる。ユーザーが削除を要請した個人情報がアプリケーションテーブルからは消えても、dbtrailの履歴索引には変更前イメージとして残っている可能性がある。導入時には保持ポリシーに個人情報削除要請へ対応する別の消去(パージ)手順を必ず含めるべきである。

7. 限界

7.1 戻したSQLも副作用までは戻せない

dbtrailが生成するロールバックSQLはデータベース内の行の状態を戻すだけである。その行変更をトリガーとして送信されたメール、キャッシュに反映された値、下流システムがすでに読み取ったイベント、外部API呼び出しといった副作用は戻さない。行単位の復旧が全てを完全に元通りにすることを保証するわけではない点は、導入前に明確に認識しておく必要がある。

7.2 DDLは別領域

binlog2sqlをはじめとするほとんどのbinlogベースの巻き戻しツールはDML(INSERT/UPDATE/DELETE)に焦点を当て、列の追加・削除のようなDDL変更自体を戻すことは別の問題として扱う。dbtrailの公開資料でもスキーマ変更自体のロールバックを中核機能として掲げていない以上、誤ったスキーマ変更まで対象とするツールではないと保守的に仮定し、別途の対応手順(マイグレーションツールのダウンスクリプトなど)を維持するのが安全である。

7.3 まだ新しいプロジェクトであるという事実

Apache-2.0のオープンソースで商用利用に制約はないが、2026年上半期から知られ始めた比較的新しいプロジェクトである。大規模本番環境での検証事例、障害時のコミュニティ対応速度、長期的な保守の見通しはまだ蓄積中だ。監査・復旧のように信頼が核心となる領域に導入するなら、まずステージング環境や低リスクのテーブルで十分に検証してから本番の中核テーブルへ広げていく段階的な導入が合理的である。

8. 結論 - 今日から適用できる3つのこと

dbtrailは「なぜMySQLだけ時間旅行がないのか」という長年の不便に、binlogというすでに存在する資源で答える。スキーマ変更なし、ロックなし、事前opt-inなしに全行変更を索引化し戻すという提案は魅力的だ。ただしこれがバックアップ・PITR・監査ログを完全に代替するものではなく、秒単位まで絞り込まれたミスを素早く戻すという狭く鋭い用途に強いツールであることを明確にした上で導入するのが正確である。

8.1 自分のワークロードの書き込みパターンをまず測定せよ

binlog_row_image=FULLへ切り替えたときに増えるbinlog容量をステージングで先に測定せよ。秒間書き込みの多いホットテーブル(頻繁に更新されるカウンタ・ステータス列など)があるなら、そのテーブルから容量増加幅を見積もってこそ実際の導入コストを予測できる。

8.2 低リスクのテーブルでまず巻き戻しを練習せよ

ミスによる事故が多い低リスクのテーブル(例:内部設定、バッチ状態テーブル)でまずdbtrailの照会・復旧フローを練習し、自動生成されたロールバックSQLを適用する前に検証する習慣をチームプロセスに組み込め。その後、決済・注文のようにリスクの高いテーブルへ信頼を積み重ねながら拡張せよ。

8.3 個人情報削除要請と保持ポリシーを先に設計せよ

全行をほぼ永続的に索引化する前に、個人情報削除要請が来た際にdbtrailの履歴からも併せて消去する手順をまず整えよ。監査履歴の価値は信頼から生まれ、信頼は規制遵守を前提とする。
