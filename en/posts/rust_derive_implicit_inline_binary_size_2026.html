Context — Uncovering Implicit #[inline] in #[derive(...)]

In Rust, the most common way to implement core traits such as Debug, Display and Clone is to write #[derive(...)] above a struct or enum. In a TIL post dated October 3, 2026, yossarian writes that what he did not know until recently is that Rust currently emits #[inline] as part of these derivations. He adds that this is seemingly not guaranteed, but that it is implied by an example in the reference and that anyone can see it by expanding the macros. The Rust Reference bears this out in a small way: its section on the #[automatically_derived] attribute shows a generated Clone implementation with #[inline] sitting directly above fn clone.

For readers who need the term, inlining means replacing a call with a copy of the called function's body at the call site, which removes the call overhead but copies the body once per call site. The post is not a complaint about this behavior. It calls the behavior almost always what we want: #[inline] is just a hint, and typical derived Debug, Clone and similar implementations benefit from being inlined because they are often trivial. The post then gives a counterexample, an error hierarchy whose types have many fields and are wrapped several layers deep. If the Debug implementation of such a type is inlined at every logging call, the code grows, and that growth is the point of the whole post.

This article reads three layers of material and tries not to blend them. The first layer is what the original post itself says: the expansion output and the experience of shrinking the uv binary by roughly 160KB. The second layer is the record on the rust-lang/rust pull request pages, namely PR #117727, which added #[inline] to derived Debug, and PR #118031, which tried a variation of it. The original post never mentions these pull request numbers, so everything about them below rests on the pull request pages and not on the post. The third layer is facts read directly from the current rustc source. Interpretation is added only where these layers meet, and each sentence says whose statement it relays.

Examining Generated Implementations Through Macro Expansion

The method of checking is one the original post already demonstrates: expand the macro and look. It starts from the smallest possible struct.

#[derive(Debug)]
                    struct Widgets {
                        foo: u32,
                        bar: usize,
                    }

The post shows that expanding this in the Rust Playground produces the following implementation.

struct Widgets {
                        foo: u32,
                        bar: usize,
                    }
                    #[automatically_derived]
                    impl ::core::fmt::Debug for Widgets {
                        #[inline]
                        fn fmt(&self, f: &mut ::core::fmt::Formatter) -> ::core::fmt::Result {
                            ::core::fmt::Formatter::debug_struct_field2_finish(
                                f,
                                "Widgets",
                                "foo",
                                &self.foo,
                                "bar",
                                &&self.bar,
                            )
                        }
                    }

The line to look at is the #[inline] attribute directly above fn fmt. The developer never wrote it, yet the derive macro attached it. The whole body is one call to debug_struct_field2_finish. The macro does not format anything itself: it only forwards the type name, the field names and references to the field values to a helper method on Formatter, and that helper does the actual formatting work. Only the last field gets an extra layer of reference (&&self.bar). A comment in the rustc source explains why: an unsized type needs an extra indirection, and only the last field of a struct is allowed to be unsized.

Sources disagree a little about what #[inline] actually does. The original post calls it just a hint. In the Lobste.rs discussion, tsion objects that it is not quite only a hint: inlining across crate boundaries is always possible for generic functions but not for non-generic functions by default, and #[inline] is what makes it possible for the latter. In the comments on PR #117727, saethlin gives a similar account. The attribute only applies LLVM's inlinehint, and the final decision stays with LLVM, but it also makes a function eligible for MIR inlining and causes it to be lowered lazily, and possibly lowered more than once. The shared message of the two commenters is that the effect of the attribute is hard to compress into one sentence.

The scope deserves a note. The Rust Reference lists nine built-in derives, Clone, Copy, Debug, Default, Eq, Hash, Ord, PartialEq and PartialOrd, and says that the implementations they generate carry the automatically_derived attribute. Whether the compiler also adds #[inline] to very small functions by itself is answered on Lobste.rs by ralfj, who says it does: really small functions are automatically marked #[inline], and a getter that someone found not inlined was either bigger than that or written before Rust did automatic inlining of this kind.

Structural Bloat in Deeply Nested Error Hierarchies

A struct with two fields has a Debug body that is a single call, so inlining it costs almost nothing. The original post says that is not the only case, and asks the reader to imagine an error hierarchy like the following.

  • ErrorA: a struct with seven String fields (lots, of, chunky, fields, within, this, type).
  • ErrorB: a struct holding an ErrorA in a field named inner.
  • ErrorC: a struct holding an ErrorB in a field named inner.
  • Errors: an enum with three variants, A(ErrorA), B(ErrorB) and C(ErrorC).
  • Default: in the post's expansion output a default implementation appears only for ErrorA, and it also carries #[inline]. The derive lines in the input code list only Debug, so input and output do not quite match inside the post itself.

In the expansion the post shows, ErrorA::fmt builds an array of field-name string slices (names) and an array of &dyn Debug values (values) and then calls debug_struct_fields_finish. ErrorB and ErrorC make a single debug_struct_field1_finish call each, and Errors branches with a match and calls debug_tuple_field1_finish for each variant. The reason only the seven-field struct uses arrays is in the rustc source. In deriving/debug.rs a constant named CUTOFF is 5: with five fields or fewer, the macro calls a method specific to the field count (such as debug_struct_field2_finish) without building any array, and with more than five it builds the arrays. In other words, the five-field boundary is a property of how the derive itself is written and not of how the optimizer behaves, and it decides whether the body that gets inlined is a single forwarding call or a body that first assembles two arrays and then makes the call.

The concern in the post is that all of this code can be inlined at every place where the Debug implementation of Errors is invoked. The post notes that such invocations can occur repeatedly, for example in debug or trace logging. A footnote adds that the hierarchy is drastically simplified and that real-world Rust applications often have deeply nested error enumerations with a nontrivial number of fields. The post does not show how many lines of assembly this inlining adds, so this article does not estimate that number either.

The uv Case Study: Saving 160KB and Missing Prerequisites

The key figure in the post is one sentence. That much code can turn out to be a non-trivial share of a Rust binary's total size, and by preventing rustc from inlining a given Debug implementation, the authors found they could shrink uv's binary by approximately 160KB. The original wording is a given Debug implementation, so the 160KB belongs to the implementation they chose and not to Debug implementations in general.

The method is in a footnote. The team added their own proc-macro, that is, a compiler plug-in that receives the tokens of an item and returns new code, in the same way derive itself is implemented. It behaves like derive(Debug) but with #[inline(never)], and that is how the inlining was prevented. The 160KB is also an absolute number without a denominator: the post does not say how large the uv binary is, so it cannot be converted into a percentage. The post names two things that surprised its author: the size cost added up fast, and rustc (seemingly) applied no limit to the size or number of times a Debug implementation was inlined. Right after that he adds that he suspects this is the right decision in many programs. Because footnote 2 is the only place that describes the remedy, nothing can be assumed about how widely the macro was applied: the post says a given Debug implementation, and one implementation is all that the 160KB is attributed to. So the post is not an attack on the compiler default. It is a report of one case where a sensible default came back as a cost for a particular shape of type.

Compiler Trade-Offs: Pull Request 117727 and Benchmarks

The change that put #[inline] on derived Debug is rust-lang/rust PR #117727, titled Emit #[inline] on derive(Debug). saethlin opened it on November 8, 2023, and it was merged the next day, November 9. The original post does not mention this PR, so everything below is based on the pull request page. The PR description is short. While working on PR #116583, the author noticed that the cross_crate_inlinable query identifies many derived Debug impls as an MIR body that is little more than a call, which suggests they may be good candidates for #[inline], so he implemented that change on its own, and it seems to provide a nice improvement to build times. The comparison numbers quoted below were produced by the rust-timer bot, which benchmarks a try build of the pull request with the rustc-perf suite against its parent commit. The bot itself says that instruction count is a highly reliable metric that it used to decide the overall result, and that max RSS, cycles and binary size are less reliable metrics that did not decide it.

  • Perf results: in the first try build, instruction counts improved in 107 of 111 primary benchmarks (mean -2.4%) and regressed in 4 (mean +0.5%). The bot summarized the outcome as regressions and improvements. For binary size, the primary benchmarks show 113 improvements (mean -2.7%) and 26 regressions (mean +0.9%). In the secondary instruction counts there were 163 improvements (mean -3.4%) and 4 regressions (mean +2.7%). Bootstrap time went from 663.159 s to 673.479 s, which is 1.56% slower, and the artifact size grew from 308.75 MiB to 308.99 MiB, a 0.08% increase.
  • The reviewer's reaction: nnethercote, who was pinged automatically because the PR changed the code generated for built-in derives and was then assigned as reviewer, says the lack of inline on fmt had been deliberate, the idea being that it would not be hot code and should not be inlined. But he cannot argue with the perf results, which he describes as faster and smaller binaries, and he finds it curious that bootstrap got 10 seconds slower and the compiler artifacts slightly bigger.
  • A hypothesis about the cause: Noratrieb suspects a simple reason for the speedup. #[inline] makes functions get compiled downstream, or, in the case of dead code, never, and Debug impls are frequently dead code. As evidence he points to the hello world benchmark, where linking got significantly faster. This is a hypothesis in a comment, not a statement in the PR description.
  • Another hypothesis: scottmcm thinks it is a happy consequence of the move to helpers such as debug_tuple_field4_finish. Those helpers are not #[inline], so the fmt methods inlined by the PR only do pointer projection and vtable pointer copying before one call. He also says he is puzzled about how check builds, which do no code generation, got so much faster.
  • After the merge: the perf run on the merged commit again showed a mix, with 5 primary instruction regressions (mean 3.1%, up to 13.7%) and 110 improvements (mean -2.3%). saethlin judged that the improvements outweigh the regressions, thought the large regression looked spurious because of collector slowness, and added the perf-regression-triaged label.

The idea of distinguishing by field count came up in a comment on PR #117727 after the merge. RalfJung asked whether it would be worth applying the attribute only to structs with at most 5 fields, leaving out enums and larger structs, and saethlin tried it on November 18 as PR #118031. The real title of that PR is Try not applying #[inline] to big structs, and its state is closed, not merged. The change removed #[inline] only from structs with more than 5 fields and left enums alone. The result was a regression across the board: in the primary instruction counts there were 54 regressions (mean +1.5%) and no improvements at all. In the same run, cycles showed 33 primary regressions (mean +2.3%) and no improvements, and binary size showed 66 primary regressions (mean +2.4%) against 4 improvements (-0.2%), while bootstrap time was nearly unchanged (-0.19%). saethlin answered that it was a huge regression and concluded that both the dead-code effect and the MIR optimization effects seem to matter. The five-field boundary is therefore the threshold of an experiment that was tried and closed, not of a merged policy.

Putting the two pull requests side by side is instructive. Both were judged on the same benchmark suite, and neither measured a binary shaped like uv. Even the binary-size column of PR #117727 is mixed, with improvements in some benchmarks and regressions in others, so a suite-wide improvement and a 160KB saving in one specific program do not contradict each other.

Hypotheses about the same phenomenon also appeared on Lobste.rs. ralfj suspects that part of the reason is that many Debug impls are never called, and that adding #[inline] avoids ever generating code for them, which points in the same direction as Noratrieb's hypothesis. evmar asks whether functions that are never called would not be dropped from the final binary anyway, and wonders how that matters for run time rather than only for compile time. yshui sees a limitation that comes from Rust's proc macros operating on tokens instead of actual types: with type information, a macro could look at how many levels of nesting there are and stop adding #[inline] when it gets too deep. All of these are hypotheses or questions, and none is a fact confirmed by the pull request pages or by the original post.

Comparing Inlining Behavior Across Core Derive Macros

The current rustc source (compiler/rustc_builtin_macros/src/deriving/) was opened directly to check whether the method generated by each built-in derive carries #[inline]. The check consisted of reading, in each file, the definition of the generated method and looking at its list of attributes. What was checked is the presence of the attribute in the source. Neither the original post nor the pull requests show how much this inlining affects binary size for each derive separately.

The row worth noticing is Eq. The source comment explains that the method is never called, so the purpose of #[inline] there is to avoid code generation, which shows that the same attribute has a different character in a different derive. In the Lobste.rs thread, kornel writes that he would expect #[inline] on Ord and Eq and maybe Clone, but that having it on Debug is surprising, and that he puts #[cold] on his own fmt implementations. In the same thread ralfj explains that the inline default is hard because it trades off code size, compile time and run time. The author of the post answers in the same spirit that he is sympathetic to the notion that there is no perfect default or heuristic Rust can pick here.

What the Post and the Discussion Offer as Responses

The post itself offers one response, and the rest come from the discussion on the same topic, so they differ in weight: the first item is a method, the second is something uv actually did, and the remaining ones are opinions or proposals. Each item below says who said it. General size-trimming advice appeared in neither the post nor the pull requests, so none is included.

  • Expand and look: this is the method the post used. Expand the derive of a suspect type in the Playground or with a macro expansion tool and see how long the body carrying #[inline] is. That a struct with six or more fields takes the array-building form is explained by the source check above.
  • Your own proc-macro: this is what uv did. Write a macro that behaves like derive(Debug) but with #[inline(never)] and apply it. The post does not give the macro's name or say whether it is public.
  • Use #[cold]: this is what kornel says he does on Lobste.rs for his own fmt implementations. Code generated by a derive cannot be annotated by hand, so this applies to hand-written implementations.
  • Report it to the compiler: ralfj says on Lobste.rs that this is worth a bug report in rust-lang/rust. The inline default has been changed before and can be changed again, and several reports saying the heuristics are bad would justify rebalancing. The author of the post replied that he would raise it that week.
  • Move the choice into a crate: schneems on Lobste.rs thinks this choice could be pushed out to a crate, with separate cold and inline Debug derives or a container attribute to pick one. It is not implemented and is one person's proposal.
  • Compare on your own build: 160KB is uv's figure, and the post gives neither the target nor the settings. The only way to know whether the same effect exists in your binary is to measure the size before and after for one suspect type.

What Was Not Verified

  • The version, commit, target triple and build profile (LTO, strip) of uv at which the 160KB reduction was measured. The post does not give them.
  • The name and source of the proc-macro that uv wrote, and the list of types it was applied to.
  • Why LLVM's inliner did not cap large Debug implementations. The post itself only says that rustc (seemingly) did not apply a limit.
  • Details of which individual benchmarks produced the large perf regressions in PR #118031, beyond the summary tables.
  • Measurements of how implicit inlining of Default, PartialEq and other derives besides Debug affects the binary size of real large projects.
