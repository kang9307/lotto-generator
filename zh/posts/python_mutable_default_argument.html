把空列表放进默认参数后每次调用都在往上堆 - Python 默认值求值的时点

不止步于「用 None 就好」，而是问这套设计为什么长成这样

2026-07-31 开发/基础设施

开篇：从第二次调用起，结果里混进了别人的数据

有一个函数逐个接收订单，放进列表再把列表返回。测试通过了，第一个请求也正常。可是第二个请求的响应里 还留着第一个请求的订单号。 第三个请求里前两个都在。翻数据库没有异常，找全局变量也没有，缓存层压根就没接。

元凶是函数签名里的一行。参数的默认值写成了一个空列表。这个陷阱广为人知，一搜就能在三秒内得到「用 None」的答案。可是只背下这条处方，就会永远认不出同一原因引出的另外两种症状。

这篇文章的主轴不是处方，而是原因。原因只有一句话。

默认值表达式在执行 def 语句时只计算一次，得到的对象会附着在函数上长期存在。

错的是「每次调用应该都会重新创建」这个直觉，列表可变并不是原因。可变性只是 让这个事实变得可见 的条件。这个区分为何重要，把下面三种症状并排放在一起就清楚了。

  • 症状 A。 空列表默认值随调用不断累积 → 原因：定义时只求值一次
  • 症状 B。 放进默认值的「今天日期」过了几天还是原样 → 原因：定义时只求值一次
  • 症状 C。 放在类体里的列表被所有实例共享 → 原因：类体只执行一次

三件外表毫不相干的事，其实是同一张脸。B 发生在 不可变类型 上，所以「因为它可变」根本解释不通。因此这篇文章把原因摆在处方前面。

运行环境。 下面所有输出都是在 Windows 10 Pro (10.0.19045) 上实际跑出来的。解释器是 Python 3.13.3 (tags/v3.13.3:6280bb5, 2025-04-08) [MSC v.1943 64 bit (AMD64)]，平台标识为 win32。所有脚本都先写成文件再执行。 缩进带有语义的语言，一旦通过 shell 参数或 here-document 传递就会被悄悄改形。

本文不涉及的内容。 Python 语法通识与入门内容在 Python 自动化入门 系列里。本文只把 默认参数的求值时点 这一个点挖到底。运行中使用的示例代码全部是虚构的。

1. 复现 - 调用三次，三次都不一样

用最短的形式写出来。函数接收一个名字放进篮子，再把篮子返回。不传篮子就从空篮子开始 - 读起来是这样，实际并非如此。

python 3.13.3 / win32

--- 1-1. three calls, one function ---
call 1 -> ['apple']
call 2 -> ['apple', 'banana']
call 3 -> ['apple', 'banana', 'cherry']

--- 1-2. two unrelated callers share one list ---
order_a = ['A-1001', 'B-2002']
order_b = ['A-1001', 'B-2002']
order_a is order_b : True

1-1 是教科书式的复现。三次调用各自返回了不同结果，而且越往后越保留着前面的东西。 函数看上去每次都在做「往空篮子里放一个」，实际做的却是「往同一个篮子里一直放」。

1-2 才是生产环境里真正会痛的部分。两个毫无关系的调用方拿到了同一个对象。 order_a is order_b 为真，意味着它们是指向同一个列表的两个名字。两个 Web 请求先后经过这样的函数，一个用户的数据就会混进另一个用户的响应里。 开篇的症状正是这个。

  • 第一次调用 永远正常。所以只调用一次的单元测试绝对抓不到
  • 改变测试顺序结果就变。相当一部分「我们的测试依赖顺序」的反馈都是这个形态
  • 重启进程症状就消失。于是被以 「重启之后就好了」 结案，然后再次复发
  • 不会抛异常。日志里没有痕迹，错误率指标也不会动

2. 默认值在哪里 - 把那个对象直接取出来

与其猜测，不如把东西取出来。函数对象上有一个存放默认值的位置。

--- 1-3. the default object itself ---
add_item.__defaults__      : (['apple', 'banana', 'cherry'],)
type of default[0]         : list
len of default[0]          : 3

--- 1-4. identity across calls ---
id(default) before call    : 1997832273600
id(returned) call 1        : 1997832273600  same: True
id(returned) call 2        : 1997832273600  same: True
id(default) after 2 calls  : 1997832273600
r1 is r2                   : True

--- 1-5. mutating through the returned reference ---
probe.__defaults__         : (['touched from outside'],)
a caller that never passed anything now sees : ['touched from outside']

1-3 是决定性的。三次调用结束后去看函数的默认值，里面装着三个元素。 写着「空列表」的位置堆满了数据。函数确实一直在修改自己的默认值。

1-4 把原因钉死。调用前默认值的地址，与调用返回的对象地址完全一致。 第二次调用也一样。不是新建，而是 把同一个一直递出去。

1-5 是这个结构最令人不快的一面。调用方在外部修改了函数返回的列表，函数的默认值就跟着变了。 从此以后所有省略参数的调用方都会看到别人种下的值。把函数内部的代码读烂了也看不见这条路径。

诊断要领。 遇到来路不明的状态污染时，第一件事是把可疑函数的默认值原样打印出来。只要 本该为空的位置里有数据，诊断就结束了。在翻全局变量和怀疑缓存之前先看这个。这个检查一行就够，也不需要停进程。

3. 什么时候计算 - 执行 def 语句时，恰好一次

现在直接观测原因。把 带副作用的函数调用 放进默认值位置，就能用眼睛数出它跑了几次。

--- 2-1. the default expression runs at def time, not call time ---
about to execute the def statement
    [side effect] make_default() ran
def statement finished
now calling f() three times:
make_default ran exactly once, before any call

请仔细看顺序。制造默认值的那个调用发生在 def 语句内部，而且在函数被调用之前就跑完了。 之后调用了三次函数，那个调用再也没有发生。

这里顺便澄清一个常见误解。def 不是「声明函数的标记」，而是 一条会执行的语句。Python 走到那一行时会从左到右计算各个默认值表达式，构造出携带这些结果的函数对象，再绑定到名字上。计算默认值是 def 语句本身的工作，不是函数体的工作。

--- 2-2. defaults are attached to the function object ---
g.__defaults__        : (1, [])
g.__kwdefaults__      : {'d': 2, 'e': {}}
g.__code__.co_varnames: ('a', 'b', 'c', 'd', 'e')

--- 2-3. the default is writable state ---
before : (1, [])
after  : (99, ['patched'])
g('x') : ('x', 99, ['patched'], 2, {})

2-2 展示了存放结构。位置参数的默认值和仅限关键字参数的默认值放在不同的地方。 前者是元组，后者是字典。自己写检查脚本时两处都要看，否则会漏。

2-3 说明这是 可写的状态，而不是只读的元数据。 从外部整个替换掉默认值之后，后续调用的行为就变了。函数对象是把代码和数据一起随身携带的东西，默认值属于数据那一侧。

  • 默认值在 定义方的作用域 中计算。之后改变那个名字所指的值，已经算好的默认值不会跟着变
  • 默认值表达式 从左向右 计算。后面参数的默认值表达式不能引用前面参数的默认值
  • 加装饰器也没用，装饰器运行时这套计算早就结束了。装饰器拿到的是已经造好的函数对象
  • 导入模块的那一刻这套计算就发生了。也就是说 默认值的年龄等于进程的年龄

4. 时间被冻住 - 放进默认值里的今天日期

从这里开始才是本文的价值。懂了上面的原理，就能预测出 与可变类型毫无关系的 第二种症状。把计算「当前时刻」的调用放进默认值位置试试。

--- 3-1. today captured in a default never moves ---
bad  ('row0', '2026-07-31 05:25:19.168606')
good ('row0', '2026-07-31 05:25:19.569502')
bad  ('row1', '2026-07-31 05:25:19.168606')
good ('row1', '2026-07-31 05:25:19.969964')
bad  ('row2', '2026-07-31 05:25:19.168606')
good ('row2', '2026-07-31 05:25:20.370294')

--- 3-2. the frozen value, straight from __defaults__ ---
stamp_bad.__defaults__ : (datetime.datetime(2026, 7, 31, 5, 25, 19, 168606),)
same object 0.5s later : (datetime.datetime(2026, 7, 31, 5, 25, 19, 168606),)
id stays the same      : 2480663196656
datetime.now() right now: 2026-07-31 05:25:20.870691

三次调用之间各歇了 0.4 秒。正确的那一侧 (good) 连微秒都每次不同，而把值放进默认值的那一侧 (bad) 三次都是完全相同的时刻。 系统时间一点没动，只是这个值不会刷新。

3-2 把原因钉死。相隔 0.5 秒打印了两次函数的默认值，同一个对象带着同一个值还在原地。 而这期间真实时间一直在走，最后一行就是证据。

--- 3-3. a date default: the day the module was imported ---
captured end date      : 2026-07-31
report_range.__defaults__: (7, datetime.date(2026, 7, 31))
date.today() now       : 2026-07-31
note: date is IMMUTABLE, yet the value is still stale
      the bug here is not mutation, it is one-time evaluation

--- 3-4. the same shape with a counter ---
{'id': 1, 'payload': 'first'}
{'id': 1, 'payload': 'second'}
{'id': 1, 'payload': 'third'}
_seq module counter    : 1   (next_id ran exactly once)

3-3 里的注释是本节的核心。日期对象明明是不可变的，取值却是陈旧的。 没有任何人修改过那个对象，只是导入那一刻的日期仍然钉在那里。用「因为可变才出的问题」这套说法根本解释不了这段输出。

这种症状在生产里可怕的地方在于 发作需要时间。 上线当天完美运行。几天后凌晨来了一条「报表区间不对劲」的反馈，值班的人重启服务器就恢复正常。然后过几天又偏了。重启周期越短的环境，越晚被发现。

3-4 把同样的形态换成了流水号。造了三行，编号却全是 1。 号码生成器在导入时跑了一次，结果就作为默认值冻住了。模块计数器停在 1 就是证据。

  • 默认值位置上 只要看见括号 就先怀疑。调用表达式会在那里执行一次，只留下结果
  • 时刻、随机数、唯一标识、读配置文件、创建连接对象 - 全都会掉进同一个坑
  • 「默认使用当前连接」这种写法尤其危险。会变成 整个进程生命周期里复用最初那一个连接
  • 由于症状 不是上线后立刻出现而是过很久才出现，追责往往指向完全不相干的地方

5. 哪些类型危险 - 以及这个区分的边界

现在按类型划分。对十二种默认值候选，实际尝试了 能否哈希 与 能否原地修改。

--- 4-1. which default types can be mutated in place ---
type        hash   in-place  verdict
--------------------------------------------------------------
list        no     OK        MUTABLE  -> state leaks between calls
dict        no     OK        MUTABLE  -> state leaks between calls
set         no     OK        MUTABLE  -> state leaks between calls
bytearray   no     OK        MUTABLE  -> state leaks between calls
int         yes    Attribute immutable-> no leak, but value frozen
str         yes    Attribute immutable-> no leak, but value frozen
tuple       yes    Attribute immutable-> no leak, but value frozen
frozenset   yes    Attribute immutable-> no leak, but value frozen
bytes       yes    Attribute immutable-> no leak, but value frozen
NoneType    yes    Attribute immutable-> no leak, but value frozen
date        yes    Attribute immutable-> no leak, but value frozen
Decimal     yes    Attribute immutable-> no leak, but value frozen

中间那一列有规律。不能哈希的全都可以原地修改，能哈希的全都不行。 这不是巧合的依据就在标准库里。数据类禁止可变默认值，文档写明这项判定用 不可哈希作为可变性的近似。也就是说「hash(默认值) 抛异常就说明这个默认值危险」与标准库采用的是同一个判据。

默认值类型哈希原地修改危险的种类判断
list, dict, set不可可以状态泄漏不要使用
bytearray不可可以状态泄漏不要使用
defaultdict, Counter, deque不可可以状态泄漏不要使用
用户自定义类的实例多半可以多半可以状态泄漏不要使用 (哈希判定拦不住)
int, float, str, bytes可以不可没有字面量则安全
tuple, frozenset可以不可成员可变则泄漏要检查内容物
None可以不可没有推荐的默认值
date, datetime, Decimal可以不可取值被冻住写成调用表达式就不要用

这张表里最重要的一格是 「用户自定义类的实例」 那一行。哈希判定筛不掉它，危险却分毫不减。所以 哈希规则只是方便的近似，不是完整的判定。 下面这段输出会说明「不可变就安全」这个命题究竟只在哪个范围内成立。

--- 4-2. proof: the immutable default is REBOUND, not changed ---
bump  id-in=140731345413000 id-out=140731345413032  same=False value=1
bump  id-in=140731345413000 id-out=140731345413032  same=False value=1
bump  id-in=140731345413000 id-out=140731345413032  same=False value=1
bump.__defaults__ : (0,)  <- never moved

grow  id-in=2415089405120 id-out=2415089405120  same=True  value=[1]
grow  id-in=2415089405120 id-out=2415089405120  same=True  value=[1, 1]
grow  id-in=2415089405120 id-out=2415089405120  same=True  value=[1, 1, 1]
grow.__defaults__ : ([1, 1, 1],)  <- grew every call

两个函数的源码几乎一样。一个给整数默认值加一，一个给列表默认值追加一个元素。结果却完全相反。

  • 整数这一侧： 运算前后地址 变了。 相加的结果成为新对象重新绑到局部名字上，函数的默认值仍是 0。所以调用三次每次都出 1
  • 列表这一侧： 运算前后地址 相同。 追加元素的运算修改了那个对象本身，函数的默认值也跟着长大了
  • 同样形状的语法 随类型不同，有时是重新绑定，有时是原地修改。 这就是把两种症状分开的真实机制
  • 归纳起来 不可变的默认值只保证「状态不会泄漏」。 它完全不保证「取值是最新的」
--- 4-3. tuple default holding a mutable member ---
call 1 -> (['x'], {})
call 2 -> (['x', 'x'], {})
call 3 -> (['x', 'x', 'x'], {})
the tuple itself never changed; its member did

--- 4-4. immutable default, still evaluated once ---
seeded.__defaults__ : (6,)
value is fixed at def time even though int is immutable
so 'immutable = safe' is only half true:
  mutable   -> shared state leaks between calls
  immutable -> value is frozen at import time

4-3 证明了表里「成员可变则泄漏」那一格。用元组做默认值，值照样累积了。 元组本身一次都没变，是里面装的列表长大了。不可变容器只守住自己，守不住内容物。

4-4 把第 3 节和第 5 节连了起来。把整数默认值写成计算表达式，那个值就在定义时确定了。整数不可变所以不存在泄漏，但 「只计算一次」这个性质照样适用。 危险的种类不同，原因只有一个。

6. 正确写法 - None 哨兵与它周围的坑

处方很简单。默认值位置只放不可变的标记，真正的对象在函数内部创建。 运行确认累积消失了。

--- 5-1. the None sentinel idiom ---
call 1 -> ['apple']
call 2 -> ['banana']
call 3 -> ['cherry']
add_item.__defaults__ : (None,)

--- 5-2. caller-supplied container still works ---
passed in  -> ['seed', 'apple']
passed in  -> ['seed', 'apple', 'banana']
caller list: ['seed', 'apple', 'banana']  (caller owns it, as intended)

第 1 节里同一个函数现在 三次都返回只有一个元素的列表。 函数的默认值只有一个 None，列表的创建在函数体内每次调用重新发生。

5-2 很关键。这条处方 不会破坏调用方自己传容器进来的场景。 传进来的列表照原样使用，调用方那边也能看到结果。这不是缺陷，而是 调用方交出了自己的东西，本来就该如此。

--- 5-3. why 'or' is not the same as 'is None' ---
arg=[]      or-> ['a', 'DEFAULT']        is-None-> ['a']
arg=['x']   or-> ['a', 'x']              is-None-> ['a', 'x']
arg=None    or-> ['a', 'DEFAULT']        is-None-> ['a', 'DEFAULT']

--- 5-4. when None is a legitimate argument value ---
lookup('a')            : 1
lookup('b')            : None
lookup('z', None)      : None
lookup('z')            : KeyError 'z'

5-3 说明了常用的简写为什么并不等价。分歧出现在第一行。调用方明确传了空列表，一边尊重了它，另一边把它换成了默认值。 因为空容器、0 和空字符串在布尔判断中全为假。

这种偏差 不会抛异常。 它会在几天后以「我发了空过滤条件却把全部都查出来了」这样的反馈回来。哨兵判断一定要用同一性比较。

5-4 讨论的是这条处方本身的边界。如果 None 可能是函数的 合法参数取值，就不能拿它当哨兵。输出里「没有值所以抛异常」和「收到的值就是 None」被准确区分开了。在模块里另建一个私有标记对象来比较即可。

--- 5-5. copying a caller's list so you do not own their data ---
r1 tags : ['urgent', 'processed']
r2 tags : ['urgent', 'processed']
caller  : ['urgent']  (untouched)

--- 5-6. frozen empty containers as a read-only default ---
render('a')            : a({})
render('b', {'x': 1})  : b({'x': 1})
writing to the default : TypeError 'mappingproxy' object does not support item assignment

5-5 更进一步。把调用方传进来的列表复制一份，好让函数 不会悄悄改动它。 输出里两次调用互不干扰，调用方的原件也原封不动。「函数可不可以改动调用方的东西」是另一个设计决定，而答案通常是不可以。

5-6 是想把「空映射」当默认值时的安全写法。把只读视图放进默认值位置，一旦不小心去改就会立刻抛异常。共享一个改不了的东西是安全的。 这段输出再次确认，问题从来不是共享本身，而是 去修改被共享的东西。

7. 同一原因的另一张脸 - 类体里的可变属性

第三种症状。正如开篇预告的，同一个原因会出现在完全不同的地方。 在类体里放一个列表。

--- 6-1. a mutable attribute in the class body ---
a.items : ['apple', 'banana']
b.items : ['apple', 'banana']
a.items is b.items      : True
Cart.items              : ['apple', 'banana']
id(Cart.items)          : 1409693232192
id(a.items)             : 1409693232192
'items' in a.__dict__   : False

--- 6-2. the fix: build it in __init__ ---
c.items : ['apple']
d.items : ['banana']
c.items is d.items      : False
'items' in c.__dict__   : True

造了两个不同的实例各放进一个，结果 两个都装着两个。 最后一行揭穿了真相。实例上根本没有这个名字。 读属性时实例上没有就会往类上找，所以所有实例看的都是附着在类上的那一个。

结构和默认参数完全相同。类体同样在定义类时只执行一次，在那里创建的对象会附着在类上长期存在。 6-2 的处方也一样。在创建实例时新建，各自就有了自己的那一份。

--- 6-3. rebinding vs mutating on a class attribute ---
p.hits : 2   q.hits : 1   Counter.hits : 0
p.log  : [1, 2, 1]
q.log  : [1, 2, 1]
the int looks per-instance because += REBINDS onto the instance
the list is shared because append MUTATES the class-level object

--- 6-4. dataclasses refuse the same shape ---
dataclass with list default : ValueError mutable default <class 'list'> for field items is not allowed: use default_factory
Good() g1.items : ['x']
Good() g2.items : []
g1.items is g2.items : False

--- 6-5. plain functions get no such protection ---
plain() -> ['x']
plain() -> ['x', 'x']
no error, no warning: dataclasses check, the interpreter does not

6-3 解释了本节最容易混淆的现象。同一个类里，整数属性是按实例分别计数的，列表属性却被共享。 代码就挨在一起，语法看着也差不多。

  • 对整数的增量赋值 会算出一个新值并绑回实例。 所以每个实例都有了自己的值，类那一侧仍是 0
  • 给列表追加元素则是 直接修改附着在类上的那个对象。 没有发生重新绑定，所以大家看到的是同一个
  • 4-2 里看到的重新绑定与原地修改的对照 在这里原样重演。 函数和类是不同的语法，站的却是同一条规则
  • 所以「类变量会被共享」这句话只对了一半。被共享的是对象，重新绑定就切断了共享

6-4 展示了标准库如何处理这个问题。数据类干脆拒绝可变默认值并抛出异常。 错误信息还顺便给出了替代方案。指定工厂函数后每个实例都会新建，两个实例的列表成了不同的对象。

6-5 是本文最令人后背发凉的部分。普通函数完全没有这种保护。 形态完全相同的代码不声不响地通过。数据类替你挡住的东西，函数不会替你挡。所以检出必须自己加上去。

8. 检出 - 解释器什么都不说

先确认解释器为你做了什么。答案是「什么都没做」。而且 这个环境里一个专用静态分析工具都没装。 于是只用标准库自制了一个扫描器跑起来。

做法是遍历语法树，看每个默认值位置上的节点类型。抓到七处，而且退出码是 1，可以直接挂进 CI。 值得注意的是分类。

  • MUTABLE - 列表、字典、集合字面量与推导式，以及已知的工厂调用。这是会泄漏的那一侧
  • CALL - 默认值位置上的所有调用表达式与计算表达式。这是 会冻住的那一侧，正如第 4 节所示，不可变类型也落在这里
  • CLASSATTR - 类体里的可变属性。原因相同，所以同一个工具就能抓到
  • 写法安全的函数以及在 __init__ 里创建的形态 一处误报都没有

检查已经在跑的进程时，另一种办法更有说服力：在运行中直接读取函数对象上的默认值。

把这个扫描挂到运行中的服务上，就能量出 「此时此刻漏了多少」。 静态分析需要源码，而这个办法 对别人写的库同样有效。

9. 故意使用的场景 - 把默认值当缓存

有一种用法是 知道这个行为并加以利用。 直接借用状态会在调用之间留存的性质来缓存计算结果。它确实能跑。

--- 8-1. the deliberate version: a default used as a cache ---
fib(60)      : 1548008755920
elapsed      : 0.000050 s
cache size   : 61
cache leaks into introspection: fib.__defaults__[0][10] = 55

--- 8-2. a caller can overwrite the cache from outside ---
fib(10) normal            : 55
fib(10, {0: 0, 1: 100})   : 5500
fib(10) again             : 55
the parameter is part of the public signature; nothing hides it

8-1 表明这个技巧确实快。递归计算几乎是瞬间完成的。但缓存就那样暴露在函数的默认值位置上。 最后一行从外部把内部缓存里的值取了出来。

8-2 是不推荐这种做法的第一个理由。缓存属于公开签名的一部分，所以调用方可以传别的进去。 传了一个乱来的初始值，结果就完全变了。它并没有被藏起来，只不过是 一个你假定没人会用的参数。

--- 8-3b. read-modify-write on a shared default, 8 threads ---
switch interval default : 0.005
switch interval set to  : 1e-06
expected increments : 160000
observed increments : 99462
lost updates        : 60538
keys retained       : 8

第二个理由是并发。让八个线程对同一个默认值字典反复做读取、修改、写回。累加了十六万次，只剩下九万九千多次，六万次消失了。

这里还有一个重要的观测。按默认设置跑的时候丢失是 0 次。 把线程切换间隔调到远小于默认值之后才显形。这正是这类缺陷可怕的地方。在测试机上一次都复现不了，到了有负载的生产机上才第一次出现。 「我们环境里没问题」这个结论，其实是「我们还没看见」。

--- 8-4. the supported alternative ---
fib2(60)     : 1548008755920
elapsed      : 0.000080 s
cache_info   : CacheInfo(hits=58, misses=61, maxsize=128, currsize=61)
signature    : None (no hidden parameter)
after clear  : CacheInfo(hits=0, misses=0, maxsize=128, currsize=0)

--- 8-5. closure: state without touching the signature ---
c1('a') -> 1  c1('a') -> 2
c2('a') -> 1
two independent instances; callers cannot reach the state

8-4 是替代方案。用标准库的缓存装饰器，速度基本一样，而 缺的东西全都补齐了。

  • 签名很干净。 被包装的原函数压根没有默认值，缓存不会作为参数漏出来
  • 有上限。 默认参数缓存永远不清空、会无限长大，而这一个可以设定最大容量
  • 可以观测。 命中、未命中、当前大小都能直接读到，缓存效率可以做成指标
  • 可以清空。 有失效手段。8-3 里看到的「永远不清空」在这里得到了解决

8-5 是想把状态彻底藏起来时的写法。把状态放进一个生产函数的函数里，调用方就碰不到，而且每个实例互相独立。 造了两个各自计数，互不干扰。如果用默认参数做缓存的理由是「想把状态放在某处」，那个某处应该是闭包，而不是签名。

10. 归纳 - 从症状回到原因

如果这篇文章只带走一样东西，就带走这张表。从左边开始向右读。

遇到的症状常见的误诊真正的原因确认方法处方
从第二次调用起混进别人的数据「缓存问题」「某处的全局变量」默认值在定义时只算了一次打印 函数.__defaults__None 哨兵
改变测试顺序结果就变「测试隔离不足」多个测试共用同一个默认值对象在测试之间比较 __defaults__None 哨兵
重启就好，几天后复发「内存泄漏」默认值冻在了导入时的取值上比较默认值的时刻与当前时刻在函数体里现算
报表区间或流水号不变「日期库的缺陷」默认值位置的调用表达式只跑了一次看默认值位置有没有括号在函数体里现算

表的第二列就是这篇文章存在的理由。八种症状的第一诊断全都指向了别处。 缓存、内存泄漏、测试隔离、日期库、怪环境 - 每一条都合情合理，每一条都是错的。原因只有一个，而确认多半一行就够。

11. 检查清单

整理成可以直接用于代码评审的形式。

  • 签名里没有任何 =[]、={}、=set()
  • 没有 =defaultdict(...)、=Counter()、=deque() 这类 工厂调用
  • 默认值位置上没有 调用表达式 - 时刻、随机数、唯一标识、读配置、创建连接
  • 默认值位置上没有 计算表达式 - 会在导入时冻住
  • 如果用了元组默认值，已确认 里面没有可变成员
  • 哨兵判断用的是 is None 而不是 or
  • None 可能是合法取值的参数改用 私有标记对象
  • 函数不会 悄悄修改 调用方传进来的容器 (需要时先复制)
  • 类体里没有列表、字典、集合属性
  • 数据类字段用 工厂函数 指定
  • 需要缓存时用 标准缓存装饰器或闭包，绝不用默认参数
  • 把语法树扫描器 挂进 CI，挡住新写进来的
  • 长期运行的进程用 运行时默认值扫描 排查残留状态
  • 并发相关的验证也在 调低线程切换间隔的状态下 跑一遍

11.1 不要这样做

  • 「只要小心可变类型就行」 - 不可变的默认值同样在定义时冻住。第 3 节就是反例
  • 「测试通过了就没事」 - 第一次调用永远正常，从第二次才显形
  • 「线程问题有解释器挡着」 - 它会随切换间隔时而显形时而隐藏
  • 从外部覆盖默认值来修 - 2-3 展示了这可行，但那是在动症状
  • 把复现不了的状态污染推给环境 - 先把默认值打印出来看看
  • 只把这个陷阱记成「一个有名的坑」 - 不知道原因，第 3 节和第 7 节的症状就永远是另外的问题

# Python 默认参数 — 定义时求值检查清单

> 来源: braindetox.kr — 把空列表放进默认参数后，每次调用都在往上堆
> 依据: 在 Windows 10 Pro (10.0.19045) / Python 3.13.3 (MSC v.1943, 64 位) 上实际运行验证
> 把本文件直接贴给 AI，写一句「按这些标准检查我们的代码库」即可使用。

## 0. 一句话前提

**默认值表达式在执行 def 语句时只求值一次，得到的对象会附着在函数上长期存在。**

它不会在每次调用时重新计算。这一句就是下面三种症状的共同原因。

| 症状 | 表面原因 | 真正原因 |
|---|---|---|
| 空列表默认值不断累积 | 因为列表可变 | 定义时只求值一次 |
| 默认值里的今天日期不更新 | 日期缓存的缺陷 | 定义时只求值一次 |
| 类属性在实例之间共享 | 因为它是类变量 | 类体只执行一次 |

## 1. 三行复现

```python
def add_item(name, basket=[]):
    basket.append(name)
    return basket

print(add_item("apple"))    # ['apple']
print(add_item("banana"))   # ['apple', 'banana']
print(add_item("cherry"))   # ['apple', 'banana', 'cherry']

print(add_item.__defaults__)
# (['apple', 'banana', 'cherry'],)
```

默认值放在 `函数.__defaults__` 元组里。调用前后 `id()` 完全相同。
仅限关键字参数的默认值放在 `函数.__kwdefaults__` 里。

## 2. 危险类型判定表 (按实际运行结果划分)

| 默认值类型 | 可哈希 | 原地修改 | 判定 |
|---|---|---|---|
| `list` | 否 | 可以 | **状态在调用之间泄漏** |
| `dict` | 否 | 可以 | **状态在调用之间泄漏** |
| `set` | 否 | 可以 | **状态在调用之间泄漏** |
| `bytearray` | 否 | 可以 | **状态在调用之间泄漏** |
| `defaultdict` · `Counter` · `deque` | 否 | 可以 | **状态在调用之间泄漏** |
| `int` · `float` | 是 | 不可 | 不泄漏 |
| `str` · `bytes` | 是 | 不可 | 不泄漏 |
| `tuple` · `frozenset` | 是 | 不可 | 不泄漏 (成员可变时除外) |
| `None` | 是 | 不可 | 不泄漏 — **推荐的默认值** |
| `date` · `datetime` · `Decimal` | 是 | 不可 | 不泄漏，但**取值被冻住** |

**判定规则**: 如果 `hash(默认值)` 抛出 `TypeError`，这个默认值就是危险的。
标准库的数据类也是这样判断的 — 用不可哈希来近似可变性。

**但不可变并不等于安全。** 不可变的默认值只是不会泄漏状态，它依然
**在定义时被冻住。** 形态如下。

```python
from datetime import datetime

def stamp(label, when=datetime.now()):   # 差: 导入那一刻被永久烙进去
    return label, when

def stamp(label, when=None):             # 好: 每次调用重新读取
    if when is None:
        when = datetime.now()
    return label, when
```

**默认值位置上出现调用表达式，无论返回什么类型都要怀疑。**

## 3. 正确写法

```python
# 标准写法 — 用 None 做哨兵
def add_item(name, basket=None):
    if basket is None:
        basket = []
    basket.append(name)
    return basket

# 不想占有调用方的数据就复制一份
def tag_all(rows, tags=None):
    tags = list(tags) if tags is not None else []
    tags.append("processed")
    return {"rows": rows, "tags": tags}

# 当 None 本身也是合法取值时，另建一个私有哨兵
_MISSING = object()

def lookup(key, fallback=_MISSING):
    table = {"a": 1, "b": None}
    if key in table:
        return table[key]
    if fallback is _MISSING:
        raise KeyError(key)
    return fallback

# 把只读映射当作默认值
from types import MappingProxyType
_EMPTY = MappingProxyType({})

def render(name, opts=_EMPTY):
    return name, dict(opts)
```

### 为什么不能用 `or` 代替

```python
extra = extra or ["DEFAULT"]     # 差: 会把空列表换成默认值
if extra is None:                # 好: 只筛掉 None
    extra = ["DEFAULT"]
```

空列表、空字典、`0`、空字符串在布尔判断中都为假。
调用方故意传了「空」，却被悄悄换回默认值。

### 类与数据类

```python
class Cart:
    items = []                # 差: 所有实例共用一个对象

class Cart:
    def __init__(self, items=None):
        self.items = [] if items is None else list(items)   # 好

from dataclasses import dataclass, field

@dataclass
class Good:
    items: list = field(default_factory=list)   # 好
```

数据类会用 `ValueError` 拒绝可变默认值。**普通函数则什么警告都不给。**

## 4. 检出

如果环境里没有装专用的检查工具，就用标准库 `ast` 自己扫。

```python
# find_mutable_defaults.py — 只用标准库
import ast, os, sys

FACTORIES = {"list", "dict", "set", "bytearray", "defaultdict",
             "OrderedDict", "Counter", "deque"}

def describe(node):
    if isinstance(node, (ast.List, ast.Dict, ast.Set)):
        return "MUTABLE", "可变字面量"
    if isinstance(node, (ast.ListComp, ast.DictComp, ast.SetComp)):
        return "MUTABLE", "推导式"
    if isinstance(node, ast.Call):
        f = node.func
        name = f.id if isinstance(f, ast.Name) else getattr(f, "attr", "")
        if name in FACTORIES:
            return "MUTABLE", "工厂调用"
        return "CALL", "定义时只求值一次的调用"
    if isinstance(node, ast.BinOp):
        return "CALL", "定义时只求值一次的表达式"
    return None, None

def scan(path):
    tree = ast.parse(open(path, encoding="utf-8").read(), filename=path)
    for node in ast.walk(tree):
        if isinstance(node, ast.ClassDef):
            for stmt in node.body:
                value = getattr(stmt, "value", None)
                if value is not None and describe(value)[0] == "MUTABLE":
                    print(path, stmt.lineno, "CLASSATTR", node.name)
        if not isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef, ast.Lambda)):
            continue
        a = node.args
        pos = a.posonlyargs + a.args
        pairs = list(zip(pos[len(pos) - len(a.defaults):], a.defaults)) if a.defaults else []
        pairs += [(k, d) for k, d in zip(a.kwonlyargs, a.kw_defaults) if d is not None]
        for arg, default in pairs:
            kind, why = describe(default)
            if kind:
                print(path, default.lineno, kind,
                      getattr(node, "name", "lambda"), arg.arg, why)

for target in sys.argv[1:] or ["."]:
    if os.path.isdir(target):
        for root, _d, files in os.walk(target):
            for f in files:
                if f.endswith(".py"):
                    scan(os.path.join(root, f))
    else:
        scan(target)
```

要检查已经在跑的进程，运行时扫描更有说服力。

```python
import inspect

MUTABLE = (list, dict, set, bytearray)

def scan_live(module):
    for name, obj in vars(module).items():
        if not inspect.isfunction(obj):
            continue
        for pname, p in inspect.signature(obj).parameters.items():
            if p.default is not inspect.Parameter.empty and isinstance(p.default, MUTABLE):
                print(name, pname, type(p.default).__name__, repr(p.default)[:40])
```

**对着正在运行的服务跑这个扫描，就能看到之前调用留下的数据还躺在默认值里。**
那就是状态泄漏被看见的样子。

### 检出手段对比

| 手段 | 多行签名 | 工厂调用 | 类属性 | 第三方代码 |
|---|---|---|---|---|
| 正则 grep | 漏掉 | 漏掉 | 漏掉 | 可以 |
| `ast` 扫描器 | 命中 | 命中 | 命中 | 有源码就可以 |
| 运行时 `__defaults__` 扫描 | 不适用 | 命中 | 命中 | **可以** |
| 解释器本身 | — | — | — | **完全不给提示** |

## 5. 把默认值当缓存用 — 为什么不推荐

```python
def fib(n, _memo={0: 0, 1: 1}):     # 能跑，但是
    if n not in _memo:
        _memo[n] = fib(n - 1, _memo) + fib(n - 2, _memo)
    return _memo[n]
```

- 缓存被**暴露在公开签名里**。调用方可以用 `fib(10, {0: 0, 1: 100})` 污染它
- **永远不会清空。** 没有上限，也没有失效机制
- **不是线程安全的。** 读取、修改、写回被切开，更新就会丢失
- 文档工具和类型检查器会把这个位置当成真正的参数

替代方案:

```python
from functools import lru_cache

@lru_cache(maxsize=128)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

fib.cache_info()    # 命中、未命中、当前大小
fib.cache_clear()   # 清空
```

想让状态藏起来就用闭包。调用方碰不到，而且每个实例互相独立。

```python
def make_counter():
    tally = {}
    def bump(key):
        tally[key] = tally.get(key, 0) + 1
        return tally[key]
    return bump
```

## 6. 检查清单

- [ ] 函数签名里没有任何 `=[]`、`={}`、`=set()`
- [ ] 没有 `=defaultdict(...)`、`=Counter()`、`=deque()` 这类工厂调用
- [ ] 默认值位置上没有**调用表达式** (`datetime.now()`、`uuid4()`、`time()`)
- [ ] 默认值位置上没有**计算表达式** (会在导入时被冻住)
- [ ] 哨兵判断用的是 `is None` 而不是 `or`
- [ ] `None` 可能是合法取值的参数使用私有哨兵对象
- [ ] 函数不会**悄悄修改**调用方传进来的容器 (需要时先复制)
- [ ] 类体里没有列表、字典、集合属性
- [ ] 数据类字段使用 `field(default_factory=...)`
- [ ] 需要缓存时走 `lru_cache` 或闭包，绝不用默认参数
- [ ] CI 里挂上 `ast` 扫描器或检查工具，挡住新写进来的
- [ ] 长期运行的进程用运行时 `__defaults__` 扫描排查残留状态

## 7. 不要这样做

- 以为「只要小心可变类型就行」 — 不可变的默认值同样**在定义时被冻住**
- 以为「测试通过就没事」 — 第一次调用永远正常，**从第二次才显形**
- 以为「线程问题有 GIL 挡着」 — 它会随切换间隔**时而显形时而隐藏**
- 直接给 `函数.__defaults__` 赋值来修 — 那是在动症状而不是原因
- 把复现不了的状态污染推给「环境问题」 — 先把 `__defaults__` 打印出来
