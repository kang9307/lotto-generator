서론: 12 → 52, 그 사이에 일어난 일

OpenAI 개발자 사이트의 Codex 활용 사례 페이지는 2026년 3월 27일 인터넷 아카이브 보관본에서 12개의 사례를 싣고 있었고, 5월 24일 보관본에서는 52개를 싣고 있었습니다. 한국 개발자 커뮤니티 GeekNews에도 「Codex, 활용 사례 모음 대폭 확장」이라는 제목으로 소개됐고, 이 글은 그 직후인 2026년 5월 26일에 처음 나갔습니다.

발행 당시 이 글은 52개를 마이그레이션·리팩토링·테스트·문서화·운영 자동화·학습의 6개 코딩 카테고리로 나누고, 새 항목 중 주목할 7가지로 Rails 5→7 마이그레이션, I18n 자동 추가, GraphQL 스키마 진화 등을 꼽았습니다. 2026-09-29에 보관본의 목록을 한 항목씩 다시 세어 보니 그 7가지는 공식 목록에 없었고, 늘어난 40개 중 17개는 코딩이 아닌 업무였습니다. 이번 갱신은 그 부분을 공식 목록 기준으로 바로잡았습니다. 확인할 수 없는 1인칭 사용 경험과 효과 수치도 모두 뺐습니다.

그래서 결론도 달라집니다. 12→52 확장은 「코딩 도구의 사례가 깊어졌다」기보다 「Codex에 맡기는 일의 범위가 개발 밖으로 넓어졌다」에 가깝습니다. 이 글은 그 목록을 어떻게 읽고, 어디서부터 써 보고, 팀에 맞는 목록으로 어떻게 옮길지를 다룹니다.

1. 12개 시절과 52개 시점 - 무엇이 달라졌나

3월 보관본의 12개는 대부분 개발자가 바로 떠올릴 만한 작업이었습니다. 대형 코드베이스 이해(Understand large codebases), 풀 리퀘스트 리뷰(Review pull requests faster), OpenAI API 연동 업그레이드(Upgrade your API integration), 어려운 문제 반복 해결(Iterate on difficult problems), Slack에서 코딩 작업 시작(Kick off coding tasks from Slack), 반응형 프런트엔드와 Figma 디자인 구현, 브라우저 게임, ChatGPT 앱, iOS·macOS 앱, 슬라이드 생성, 데이터 분석 보고서입니다.

5월 보관본의 52개에는 이 가운데 11개가 그대로 남았고, iOS·macOS 앱은 두 사례로 나뉘었습니다. 새로 들어온 것에는 코드 이전(Run code migrations), 리팩터링(Refactor your codebase), 문서 최신화(Keep documentation up-to-date) 같은 개발 작업도 있지만, 메일 정리(Manage your inbox), 회의 준비와 후속 조치, 현금흐름 예측(Forecast cash flow), DCF 가치평가 모델(Model a DCF valuation), 예산 대비 실적 검토 같은 업무도 함께 들어왔습니다. 사례를 묶는 모음(collections)은 게임 개발·네이티브 개발·프로덕션 시스템·생산성과 협업·웹 개발의 5개였습니다.

Goals와의 관계도 정정합니다. 발행 당시에는 「2025년 말 OpenAI가 Codex를 Goals 단위 에이전트로 재정의했다」고 적었지만, /goal 명령은 2026년 4월 30일 Codex CLI 0.128.0에 실험 기능으로 처음 들어왔고 5월 21일 0.133.0에서 기본으로 켜졌습니다. 52개 시점 목록에는 「Follow a goal」이 사례 하나로 들어 있었습니다. Goals는 목록의 상위 개념이 아니라, 목록 안의 긴 작업을 끝까지 끌고 가는 방법 중 하나입니다. 사용법은 같은 날 공식 문서 기준으로 갱신한 OpenAI Codex Goals 실전 가이드에 정리했습니다.

2. 52개 분류 - 공식 분류가 아닌 이 글의 5분류

OpenAI 페이지는 카테고리·팀·작업 유형 필터를 제공하지만, 사례 하나에 태그가 여러 개 붙어 있어 개수를 세는 데는 맞지 않습니다. 아래 표는 보관본의 사례 제목을 이 글이 다섯 묶음으로 나눈 것입니다. 경계에 걸친 사례는 제목이 가리키는 주된 작업을 기준으로 한 곳에만 넣었습니다.

발행 당시 적었던 「마이그레이션 약 12개, 리팩토링 약 10개, 테스트 약 8개」 같은 개수는 공식 목록과 맞지 않아 지웠습니다. 52개 시점에 코드 이전을 직접 다루는 사례는 「Run code migrations」와 「Upgrade your API integration」 두 개였고, 뒤의 것은 일반적인 API 버전 전환이 아니라 기존 OpenAI API 연동을 최신 권장 모델·기능으로 올리는 사례입니다.

3. 늘어난 40개 중 눈여겨볼 7가지

아래 설명은 각 사례 카드의 공식 요약을 옮긴 것이고, 난이도와 예상 시간은 2026-09-29 기준 카드 표기입니다. 발행 당시 이 절에 있던 Rails 5→7 마이그레이션, 마이크로서비스 추출, 보안 패치 자동화, 성능 회귀 헌트, I18n 자동 추가, SQL 인덱스 추천, GraphQL 스키마 진화는 52개 시점 목록과 현재 목록 어디에서도 해당 제목을 찾지 못해 뺐습니다.

3-1. 코드 이전 (Run code migrations)

레거시 시스템을 새 스택에 대응시키고, 이전을 마일스톤 단위로 나눠 진행하며, 각 전환 전에 동작이 같은지 확인하는 사례입니다. 카드 표기는 고급·1시간입니다. 특정 프레임워크 버전을 지목하지 않고 「통제된 체크포인트」를 강조한다는 점이 핵심입니다. 한 번에 옮기지 말고 확인 지점을 여러 개 두라는 뜻입니다.

3-2. 리팩터링 (Refactor your codebase)

동작을 바꾸지 않은 채 죽은 코드를 지우고, 큰 파일을 풀고, 중복 로직을 합치고, 낡은 패턴을 현대화하는 사례입니다. 공식 요약은 이 작업을 작고 리뷰 가능한 단위로 나눠 진행하라고 적고 있습니다. 카드 표기는 고급·1시간입니다.

3-3. 목표 따라가기 (Follow a goal)

여러 턴에 걸쳐, 검증할 수 있는 멈춤 조건을 향해 계속 작업해야 할 때 목표를 걸어 두는 사례입니다. 카드 표기는 고급·장시간입니다. 위 두 사례처럼 끝을 테스트로 판정할 수 있는 작업과 함께 쓸 때 쓸모가 큽니다.

3-4. 컴퓨터 사용으로 앱 QA (QA your app with Computer Use)

실제 제품 흐름을 클릭해 가며 무엇이 깨지는지 기록하고 버그 보고서로 마무리하는 사례입니다. 카드 표기는 중급·30분입니다. 코드를 읽는 대신 화면을 조작해 검사한다는 점에서 12개 시절에는 없던 유형입니다.

3-5. 의존성 사고 점검 (Audit dependency incidents)

공개된 패키지·공급망 보안 권고를 읽기 전용 점검 계획으로 바꾼 뒤, 매니페스트·잠금 파일·CI 워크플로·스크립트를 신뢰할 수 없는 코드를 실행하지 않고 살피는 사례입니다. 카드 표기는 고급·1시간입니다. 보안 사례가 「자동 패치」가 아니라 「읽기 전용 점검」으로 설계돼 있다는 점이 눈여겨볼 대목입니다.

3-6. 작업 흐름을 스킬로 저장 (Save workflows as skills)

잘 된 Codex 대화, 리뷰 규칙, 테스트 명령, 릴리스 점검표, 디자인 규칙, 저장소 전용 스크립트를 이후 작업에서 다시 쓸 수 있는 스킬로 바꾸는 사례입니다. 카드 표기는 쉬움·5분입니다. 비슷한 결의 사례로, 어느 폴더에서나 Codex가 실행할 수 있는 CLI를 만드는 「Create a CLI Codex can use」도 함께 들어왔습니다.

3-7. 코딩 밖 업무 (Manage your inbox · Forecast cash flow)

메일 정리 사례는 밀린 메일을 정리하고, 사용자의 말투로 답장 초안을 쓰고, 정해 둔 주기로 새 메일을 확인합니다(쉬움·10분). 현금흐름 예측 사례는 입력값과 제약을 받아 편집 가능한 예측 워크북을 만들고, 안전 잔액을 밑도는 지점과 현금 압박을 만드는 가정을 표시합니다(중급·30분). 2026-09-29 기준 두 카드의 요약은 작업 주체를 ChatGPT로 적고 있어, 이 목록이 코딩 도구 안에 머물지 않는다는 점을 보여 줍니다.

4. Codex Use Cases vs Claude Code vs Cursor - 비교할 때 볼 것

발행 당시 이 절은 「새 기능·아키텍처 토론은 Claude Code, 대규모 일괄 변환·운영 자동화는 Codex, 일상 수정은 Cursor」라는 구분을 사용 경험으로 제시했습니다. 공식 자료나 공개된 비교 측정으로 뒷받침되지 않아 이번 갱신에서 판정을 뺐고, 대신 비교할 때 같은 기준으로 적어야 할 세 가지를 남깁니다.

  • 외부 연결: 52개 중 상당수는 Slack·GitHub·메일 같은 도구와의 연결을 전제로 합니다(「Kick off coding tasks from Slack」, 「Review GitHub pull requests」, 「Manage your inbox」). 다른 도구로 같은 일을 하려면 그 연결이 공식적으로 지원되는지부터 확인해야 합니다.
  • 긴 작업의 멈춤 조건: Codex는 /goal로 목표를 걸고 성공·일시정지·예산 한도·사용자 입력이 필요한 막힘 같은 조건에서 멈춥니다. 비교하는 도구가 긴 작업을 어떤 조건에서 멈추고 무엇을 보고하는지 공식 문서로 확인해 같은 표에 적으세요.
  • 검증 방법: 공식 사례 설명은 반복해서 검증을 요구합니다. 코드 이전은 전환 전 동작 동일성 확인, 문서 갱신은 게시 전 검증 단계, 운영 작업은 로그·산출물 확인입니다. 어느 도구를 쓰든 결과를 테스트·로그·점검표 중 무엇으로 확인했는지가 도구 이름보다 중요합니다.

같은 작업을 세 도구에 맡겨 보고 위 세 칸을 채운 메모가 쌓이면, 팀의 도구 분담 기준은 그 메모에서 나옵니다. 도구를 비교할 때 흔한 측정 실수는 AI 코딩 측정에서 흔히 틀리는 12가지에서 따로 다뤘습니다.

5. 한국 SI 환경에 옮겨 볼 8가지

아래 8가지는 OpenAI 공식 목록의 사례가 아닙니다. 한국 SI·SM·자체 서비스 환경에서 흔한 기술 부채를 공식 사례 가운데 가장 가까운 것에 대응시킨 것입니다. 발행 당시 붙였던 「실제 적용해 본 것들」이라는 설명은 확인할 수 없어 뺐습니다.

  1. Spring 3.x → Spring Boot 3.x 이전: 「Run code migrations」의 단계별 체크포인트 방식이 맞습니다. 한국 SI에서 가장 많이 쌓인 부채 가운데 하나입니다.
  2. JSP → Thymeleaf 또는 React 전환: 「Run code migrations」와 「Build responsive front-end designs」를 함께 봅니다.
  3. jQuery → 바닐라 JS 또는 React 전환: 「Refactor your codebase」의 작은 리뷰 단위 원칙을 따릅니다.
  4. Oracle PL/SQL → PostgreSQL 함수 이전: 「Run code migrations」에 해당합니다. DB 이전은 결과 대조 쿼리를 완료 조건으로 두세요.
  5. JUnit 4 → JUnit 5 이전과 테스트 보강: 이전은 「Run code migrations」로, 보강한 테스트는 이후 리팩터링의 안전망으로 씁니다.
  6. 로그 포맷 표준화와 운영 절차 자동화: 「Run verified operations」처럼 승인된 스크립트만 실행하고 로그·산출물로 결과를 확인하는 방식이 맞습니다.
  7. 레거시 코드베이스 온보딩 문서: 「Understand large codebases」가 요청 흐름 추적, 낯선 모듈 지도, 다음에 읽을 파일 안내를 다룹니다.
  8. 문서·변경 이력 최신화: 「Keep documentation up-to-date」가 코드 변경과 PR 맥락을 비교해 문서 갱신 초안을 만들고, 게시 전 검증 단계를 둡니다.

공식 사례 가운데 망분리 환경에서 그대로 쓸 수 있다고 밝힌 것은 찾지 못했습니다. 외부 AI 서비스 사용이 막힌 공공 SI에서는 위 대응표를 작업 설계용으로만 쓰는 편이 현실적입니다.

6. 함정: 52개를 그대로 받아들이면 안 되는 이유

52개라는 숫자는 제품 소개이기도 합니다. 발행 당시 적었던 「52개 중 실제 일에 활용한 것은 20개 미만」이라는 개인 측정은 뺐고, 대신 목록 자체에서 확인되는 함정을 적습니다.

  1. 개발 사례만 있다고 가정하지 말 것: 52개 중 19개는 업무 보조·데이터·재무 사례입니다(12개 시절부터 있던 슬라이드 생성과 데이터 분석 보고서 포함). 개발팀이 도입 효과를 따질 때 전체 숫자를 그대로 쓰면 과대평가가 됩니다.
  2. 「가능하다」와 「프로덕션에 쓸 수 있다」는 다르다: 공식 사례도 코드 이전은 단계별 동작 확인을, 리팩터링은 작은 리뷰 단위를 전제로 합니다. PoC → 작은 범위 → 전사 확장 순서를 지키세요.
  3. 난이도 표기를 무시하지 말 것: 같은 목록 안에서도 카드 표기가 쉬움·5분부터 고급·장시간까지 벌어져 있습니다. 첫 시도는 쉬움 사례로 하세요.
  4. 비용을 실측할 것: 긴 작업은 사용량이 쌓입니다. Goals의 멈춤 조건에 예산 한도가 들어 있는 것도 그 때문입니다. 작업 전에 이번 작업에 쓸 한도를 정해 두세요.
  5. 법적·라이선스 함정: 생성·변환한 코드의 라이선스와 저작권, 사내 코드·고객 데이터를 외부 모델에 보내도 되는지를 먼저 확인하세요. 한국 SI 계약에서는 특히 주의가 필요합니다.

7. 개발자가 만들어야 할 자기만의 Use Case Library

OpenAI 목록을 그대로 받기보다 팀의 일하는 방식에 맞춘 목록을 만드는 편이 쓸모가 큽니다. 절차는 다음과 같습니다.

  1. 한 주 동안 반복한 작업 20개 적기: 코드 작성, 리팩터링, 문서화, 회의 준비, 보고서 작성까지 모두 적습니다.
  2. 각 항목에 위탁 가능도 매기기: 완전 / 부분 / 불가로 나눕니다. 기준은 「결과를 무엇으로 검증할 수 있는가」입니다.
  3. 완전 위탁 항목부터 지시문 템플릿 만들기: 입력·출력 형식과 검증 절차를 적습니다. 공식 목록의 「Save workflows as skills」처럼 템플릿을 스킬로 저장해 두면 다음 작업에서 다시 쓸 수 있습니다.
  4. 한 달에 한 번 회고: 잘 된 템플릿은 다듬고, 안 된 것은 고치거나 지웁니다.
  5. 팀과 공유: 안정된 목록은 팀 위키로 옮겨 팀 자산으로 만듭니다.

발행 당시의 「6개월이면 20~30개가 쌓인다」는 예상치는 근거가 없어 뺐습니다. 몇 개가 쌓이는지보다 각 항목에 검증 방법이 적혀 있는지가 목록의 품질을 정합니다.

8. 2026 하반기 Codex 진화 예측 (당시 전망)

아래 세 문단은 2026년 5월 발행 당시의 전망이고, 문단마다 2026-09-29에 확인한 결과를 덧붙였습니다.

첫째, 사례 목록이 80~100개로 다시 늘어나고, 늘어나는 쪽은 도메인 특화 작업이 될 것이라고 봤습니다. 9월 29일 확인 시 카드는 105개이고, 사례 모음에 비즈니스 운영·데이터 과학·교육·재무·생명과학·영업·보안이 새로 생겼습니다. 방향은 맞았고 숫자는 전망을 넘었습니다.

둘째, 한 에이전트가 코드를 짜고 다른 에이전트가 리뷰하는 다중 에이전트 협업이 공식 사례로 들어올 것이라고 봤습니다. 현재 목록에서 다중 에이전트 협업을 제목으로 내건 사례는 찾지 못했습니다. 「Set up a project teammate」와 「Scan multiple repositories」가 있지만, 에이전트끼리의 분업을 다루는지는 이번에 확인하지 않았습니다.

셋째, 비코드 영역으로 확장될 것이라고 봤습니다. 이 전망은 사실 발행 시점에 이미 진행 중이었습니다. 52개 시점에 업무 보조·데이터·재무 사례가 19개 있었고, 현재 목록에는 수업 자료 준비(Create a classroom materials pack), 영업 계정 우선순위(Prioritize accounts), 예산·일정 계획(Plan a budget and schedule) 같은 사례가 더해졌습니다.

10. 결론 + 즉시 실행 가능한 3가지

12→52는 단순한 항목 추가가 아니었습니다. 다만 그 의미는 발행 당시 적은 「코딩 어시스턴트에서 엔지니어링 작업 에이전트로」보다 넓었습니다. 늘어난 40개 중 17개가 개발 밖 업무였고, 목록은 그 뒤 105개로 늘며 ChatGPT 쪽 사이트로 옮겨 갔습니다. 개발자에게 필요한 것은 전체 숫자가 아니라 자기 팀의 일에 맞는 몇 개와, 그것을 검증하는 방법입니다.

오늘부터 할 수 있는 3가지입니다.

실행 1 - 반복 작업 20개 적기: 이번 주 안에 한 주 동안 반복하는 작업 20개를 적고, 각 항목에 위탁 가능도(완전/부분/불가)와 검증 방법을 한 줄씩 붙이세요.

실행 2 - 쉬움 사례 하나로 시작: 「Understand large codebases」나 「Keep documentation up-to-date」처럼 카드 표기가 쉬움인 사례를 실제 저장소에 적용해 보세요. 결과를 사람이 검증하기 쉬운 일부터 시작하는 편이 안전합니다.

실행 3 - 도구 3개 비교 메모: 같은 작업을 Codex·Claude Code·Cursor에 맡기고, 4절의 세 칸(외부 연결·멈춤 조건·검증 방법)을 채운 메모를 1주일 동안 쌓으세요.

52개, 지금은 105개라는 숫자는 출발선입니다. 그 목록을 팀의 목록으로 옮기는 작업이 도구 선택보다 오래 남습니다.
