Paca — Open-Source AI-Native Project Management Where Humans and Agents Share the Board

Designed from the ground up for a world where AI agents are first-class teammates, not chatbot add-ons

2026-06-29 Tech & IT

Introduction: Why "AI Collaboration" Has Been a Lie

As of June 2026, almost every project management tool ships with an AI feature. Jira auto-classifies issues. Notion summarizes documents. ClickUp suggests smart tasks. But they all share one structural truth: the AI lives in a side panel. You open it, ask a question, get a response, then manually update the board yourself. The agent is a tool you use, not a teammate you work with.

The problem with this structure runs deep. In a world where agents actually write code, file issues, and open pull requests, none of that activity is visible on the sprint board. Boards only show human work. Tracking what an agent did requires digging through logs. Humans must manually reflect agent output back into the project management system.

Paca (github.com/Paca-AI/paca) is a direct challenge to this structure. Rather than bolting AI onto a traditional PM tool, Paca starts from the premise that AI agents are already first-class team members, and builds the collaboration infrastructure around that reality. This analysis examines what Paca actually built, what genuinely differentiates it, and what still falls short — as of June 2026.

1. What Paca Is — The AI-Native PM Definition Made Concrete

Paca is an open-source, self-hosted project management platform positioning itself as a free alternative to Jira, Trello, ClickUp, and Monday.com. Its central claim: AI agents are equal Scrum teammates, assigned to sprints, visible on the board, and updating their own task status in real time.

"AI-native" is an overused phrase. In Paca's case it resolves to specific design decisions. Agents have names on the board. They are assigned to sprints. They pull tasks. They post updates. Humans do not manually proxy agent work into the system — agents interact directly. This distinction matters more than it may initially appear.

The technical stack: React + TanStack Start (frontend), Go + Gin (backend), Node.js + Socket.IO (real-time), Python + FastAPI + OpenHands SDK (agents), PostgreSQL + Valkey (data/cache). Apache 2.0 license. Single Docker Compose deployment.

2. The P-A-C-A Cycle — What Agents Actually Do

Paca structures team workflow around four phases — Plan, Act, Check, Adapt — that give the tool its name and define its collaboration model.

2.1 Plan — Agents Participate in Backlog Refinement

In the planning phase, agents are not simply drafting tools. Product owners, business analysts, and AI agents co-author BDD (Behavior-Driven Development) Gherkin scenarios and System Design Documents together. Paca's in-app AI chat operates at the project level, letting anyone create epics, stories, and tasks in plain English that land directly on the backlog. The key architectural point: this chat is embedded in the project context, not a disconnected assistant window. Tasks created by agents can be immediately pulled into a sprint.

2.2 Act — Agents Pull Tasks from the Same Board as Humans

This is Paca's most dramatic differentiator. When a sprint begins, agents pull their assigned tasks just as humans do, updating status in real time via Socket.IO. OpenHands-based agents run in isolated containers, write and commit code, and log their results back to the task. Humans observe agent progress on the sprint board itself — not in a separate dashboard. The board is the single source of truth for the entire team, human and machine alike.

2.3 Check — Automated Verification with Human Review

Agent output is not accepted without verification. QA agents run automated checks against the BDD scenarios defined in the Plan phase. Human reviewers examine visual before/after diffs in the activity trail. Every field change can be reverted in one click. This structure does not blindly trust agents — it treats agent output as a verifiable artifact requiring sign-off, which is the correct security posture for 2026-era agent capabilities.

2.4 Adapt — Retrospectives Include Agent Performance

At sprint close, retrospective data covers both human and agent work. Which task types did agents handle well? Where did they stall and require human intervention? This data informs the next sprint's task allocation decisions. The feedback loop includes both parties, rather than optimizing only human performance while treating agent failures as black-box system issues.

3. The MCP Server and Claude Code Integration — An Agent Ecosystem Entry Point

Paca bundles an MCP (Model Context Protocol) server (@paca-ai/paca-mcp). MCP has become the industry standard protocol for AI agents accessing external data sources and tools. Through this server, Claude Desktop, Claude Code, and any MCP-compatible client can structurally read and write Paca's projects, tasks, sprints, documents, and members.

More concretely: Paca ships a /paca slash command set for Claude Code. Developers manage tasks and sprints in natural language without leaving their editor. This looks like a convenience feature. I read it as a design signal: Paca assumes PM tooling should live on the same plane as the agentic coding workflow. Where agents write code is where task management should happen.

The WebAssembly plugin sandbox follows the same logic. Plugins execute in isolated WASM environments, preventing malicious or poorly-written extensions from accessing the host system. This is how you keep a system secure when agents may execute plugins autonomously.

4. Self-Hosting and Data Ownership — What SaaS Cannot Give You

Jira's Data Center (self-hosted) edition stopped accepting new customers in 2024. Atlassian's direction is unambiguous: migrate to cloud SaaS. Against this backdrop, Paca's self-hosting-first design is not just a feature — it is a market position.

Paca defaults to self-hosted infrastructure. Installation is either an interactive bash script (one-command production setup) or customizable Docker Compose. External PostgreSQL, AWS S3, and optional agent disabling (to reduce resource overhead) are supported. Data stays on your infrastructure.

Why this matters at depth: when AI agents are deeply integrated into project management, the sensitivity of the context they process increases substantially. An agent reading your codebase, creating issues, modifying design documents, and logging conversation history generates a rich organizational intelligence record. For teams who cannot send that context to a third-party SaaS, self-hosting is not a preference — it is a prerequisite.

The cost arithmetic is also real. Jira runs $7–14 per seat per month. ClickUp and Monday.com run $9–20+. A 20-person team spends $140–$400 per month. Paca's cost is the server. Apache 2.0 means no commercial use restrictions.

5. Structural Differences from Jira, Notion, and ClickUp

The meaningful comparison is not feature lists. It is design premises.

5.1 Is AI a Tool or a Teammate?

Jira AI classifies and summarizes. It does not pull tasks, execute them, and post results as a sprint board entity. Notion AI drafts documents but does not integrate with sprint structure. ClickUp AI suggests tasks but does not operate as an agent within the Scrum framework. In Paca, agents are board members. This difference cannot be bridged by adding features to existing tools — the underlying data model and collaboration architecture are different.

5.2 BDD and System Design Documents as Agent Context

Paca integrates BDD scenarios and System Design Documents within the project itself. Agents read this documentation as execution context. In Jira, such documents typically live in Confluence or an external wiki, decoupled from the task execution layer. Paca's approach lets agents reference the full project context from one space, which directly affects execution quality when agents interpret requirements and generate code.

5.3 Cynefin Framework as Design Philosophy

Paca explicitly references the Cynefin and Stacey frameworks in its design philosophy. For complex work, agents are intended to "probe, sense, and respond" rather than follow predetermined automation pipelines. Whether this translates reliably into agent behavior on real production tasks requires empirical validation — but the explicit design intent separates Paca from tools that treat automation as simple rule execution.

6. The Future of Agent Collaboration Workflows — What Paca Signals

As of June 2026, AI agents are performing real work. Claude Code, GitHub Copilot Workspace, and Devin are moving beyond code snippets to issue resolution, PR generation, and test execution. The artifacts these agents produce must integrate into the team's workflow. The integration point is the project management tool.

Paca is an early experiment in what that integration looks like. It is less a finished product than a concrete answer to the question: what should PM infrastructure look like in a world where agents are teammates? The 1,400 GitHub stars and 84 forks signal that this question resonates.

The most important proposition Paca demonstrates: the next evolution of PM tools is not adding AI features to existing architectures — it is rebuilding the collaboration structure around agents as participants. Assigning tasks to agents, seeing agent progress on the board, verifying agent output, and retrospecting with agent performance data. None of this can be assembled by adding a chatbot button to a traditional PM interface.

7. Limitations and Honest Assessment

An uncritical introduction of Paca would be misleading. As of June 2026, concrete limitations exist.

7.1 Early-Stage Maturity

1,400 GitHub stars signals interest, not validated stability. Paca does not yet match the SLA maturity, enterprise support structures, or edge-case stability of Jira built over two decades. Production scenarios with dozens of concurrent users, thousands of historical issues, and complex agent failure recovery have not been publicly validated.

7.2 Agent Execution Infrastructure Cost

Running agents requires OpenHands container infrastructure and LLM API call costs. "Free" means Paca the software has no license fee — it does not mean agent execution is free. At meaningful task volumes, LLM API costs can be substantial. This must be modeled before adoption.

7.3 Plugin and MCP Ecosystem Depth

The MCP server and WASM plugin system are architectural strengths, but the catalog of third-party plugins and MCP integrations in June 2026 is a fraction of Jira's marketplace. Teams needing specific external service integrations (CI/CD, monitoring, Slack workflows) may need to build or contribute these themselves.

7.4 Agent Autonomy Claims Need Empirical Validation

The design intent for agents to "probe, sense, and respond" in complex scenarios depends heavily on OpenHands SDK capabilities and LLM reasoning quality. How far agents reliably operate autonomously before requiring human intervention on real production codebases requires direct experimentation with your specific tasks — not extrapolation from demos.

8. Practical Adoption Guidance

8.1 Right Fit Today

Teams already using agentic coding tools who want agent activity visible in sprint planning are the ideal early adopters. Security-sensitive teams who cannot send codebase context to SaaS PM vendors gain immediate value from self-hosting. Startups and small teams where Jira seat costs are meaningful will find the economics compelling.

8.2 Exercise Caution

Large enterprise teams considering full PM migration should wait for more maturity evidence. Teams deeply dependent on Jira marketplace integrations face ecosystem gaps. Teams without infrastructure capacity to run agent containers and LLM APIs should model total costs carefully.

8.3 Recommended Adoption Pattern

Run Paca in parallel with your existing PM tool, using it specifically for workflows that involve AI agents. Measure whether agent task visibility on the sprint board changes how your team coordinates around agent work. After three to four sprint cycles with real agent tasks, you will have empirical data to drive a more considered adoption decision.

Conclusion — The Starting Point of AI-Native PM

Paca is not a finished Jira replacement. It is the most concrete open-source implementation of the distinction between "a PM tool with AI features added" and "a PM tool redesigned for AI agents as participants." As of June 2026, this distinction is an early-adopter concern. Given the pace of agentic coding adoption, it may become the central PM tool selection criterion within one to two years. The question Paca is answering — what does project management look like when agents are teammates — is worth taking seriously now.
