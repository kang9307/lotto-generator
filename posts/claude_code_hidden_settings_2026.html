서론: 문서 너머의 Claude Code

Claude Code를 처음 설치한 사람과 몇 달째 쓰는 사람의 가장 큰 차이는 무엇일까요. 저는 단연 설정 파일을 얼마나 길들였는가라고 봅니다. 많은 사용자가 도구를 설치한 그대로, 즉 기본값으로만 사용합니다. 매번 같은 확인 프롬프트에 엔터를 누르고, 똑같은 포매터를 손으로 돌리고, 반복되는 작업을 반복되는 채로 둡니다. 그러면서 정작 도구가 제공하는 설정의 절반도 건드려 보지 않습니다.

이 글의 제목에 들어간 숨겨진 설정이라는 말은 오해를 살 수 있어 먼저 분명히 해 둡니다. 저는 어떤 비밀스러운 백도어 키를 폭로하려는 것이 아닙니다. 대부분은 공식 문서에 분명히 존재하지만, 전면에 크게 부각되지 않아 많은 사람이 그냥 지나치는 영역을 가리킵니다. settings.json의 깊은 구석, hooks를 통한 자동화, MCP 서버 연결, 권한의 세밀한 제어 같은 것들입니다.

이 글은 hada.io에 올라온 Claude Code 설정 분석 토픽에서 주제를 발굴했지만, 원문을 번역하거나 요약하지 않습니다. 대신 제가 실제로 정리하고 활용해 온 관점에서, 일반적으로 알려진 설정 카테고리를 한국 개발자에게 도움이 되는 방식으로 풀어냅니다. 한 가지 중요한 전제가 있습니다. Claude Code는 빠르게 업데이트되는 도구이므로, 특정 버전의 동작을 단정하지 않고 일반적 활용 원칙을 중심으로 서술합니다. 적용 전에는 반드시 본인이 쓰는 버전의 공식 문서를 함께 확인하시길 권합니다.

1. settings.json 구조 - 알아야 할 핵심 영역

모든 길은 settings.json으로 통합니다. Claude Code의 동작을 바꾸고 싶다면 결국 이 JSON 파일을 다루게 됩니다. 가장 먼저 이해해야 할 것은 설정이 여러 계층으로 나뉜다는 점입니다. 일반적으로 사용자 전역 설정(보통 홈 디렉터리의 ~/.claude/settings.json)과 프로젝트 설정(저장소의 .claude/settings.json), 그리고 개인 로컬 설정(.claude/settings.local.json)이 함께 작동한다고 알려져 있습니다.

이 계층 구조가 왜 중요할까요. 같은 설정 키라도 어느 파일에 두느냐에 따라 적용 범위와 공유 여부가 완전히 달라지기 때문입니다. 전역 설정은 내 모든 프로젝트에 영향을 주고, 프로젝트 설정은 그 저장소를 클론하는 모든 팀원에게 적용되며, 로컬 설정은 나에게만 적용됩니다. 이 차이를 모르면 팀에 강제하면 안 될 개인 취향을 공유 파일에 넣거나, 반대로 모두가 써야 할 규칙을 본인 로컬에만 넣는 실수를 하게 됩니다.

settings.json에서 자주 다루게 되는 핵심 영역은 대략 다음과 같습니다.

  • permissions: 어떤 명령을 자동 허용하거나 차단할지 정하는 영역
  • env: Claude Code 세션에 주입할 환경 변수
  • model: 기본으로 사용할 모델 지정
  • hooks: 특정 이벤트에 셸 명령을 연결하는 자동화
  • statusLine: 하단 상태 표시줄을 커스터마이징하는 설정

구조를 파악할 때 가장 안전한 방법은 빈 파일에서 키 하나씩 추가하며 동작을 확인하는 것입니다. JSON은 문법에 엄격해서 쉼표 하나 빠져도 전체가 무시될 수 있으니, 작은 변경 후 바로 검증하는 습관을 들이는 편이 좋습니다.

2. 덜 알려진 유용한 설정 7가지

이제 실제로 손에 잡히는 설정을 봅시다. 아래 일곱 가지는 모두 일반적으로 공개된 기능이지만, 깊이 활용하는 사람은 의외로 적은 영역입니다.

2.1 permissions allow로 반복 프롬프트 줄이기

가장 체감이 큰 설정입니다. git status나 ls처럼 명백히 안전한 읽기 전용 명령을 allow 목록에 넣으면, 매번 확인을 누르는 마찰이 사라집니다. 다만 삭제나 외부 전송 같은 위험한 명령은 절대 넓게 허용하지 마세요.

2.2 env로 프로젝트별 환경 변수 주입

특정 프로젝트에서만 필요한 환경 변수를 env에 정의하면, 세션마다 손으로 export 하던 수고를 덜 수 있습니다. 단, 토큰 같은 민감 값은 공유 파일이 아닌 로컬 설정에 두는 것이 원칙입니다.

2.3 model로 작업 성격에 맞는 모델 고정

프로젝트 성격에 따라 기본 모델을 지정해 두면, 매번 모델을 바꾸는 번거로움이 줄어듭니다. 무거운 추론이 필요한 저장소와 가벼운 편집 위주의 저장소를 다르게 설정하는 식입니다.

2.4 hooks로 포매터 자동화

파일 수정 후 자동으로 포매터를 돌리도록 hook을 걸면, 코드 스타일이 사람 손을 거치지 않고도 일관되게 유지됩니다. 자동화의 핵심이라 뒤에서 별도로 다룹니다.

2.5 statusLine으로 컨텍스트 가시화

상태 표시줄을 커스터마이징해 현재 브랜치, 모델, 디렉터리 같은 정보를 항상 보이게 하면, 컨텍스트 전환 비용이 줄어든다고 알려져 있습니다.

2.6 슬래시 커맨드로 반복 프롬프트 템플릿화

자주 쓰는 지시를 슬래시 커맨드로 저장하면, 긴 프롬프트를 매번 타이핑하지 않아도 됩니다. 팀 공용 커맨드로 만들면 작업 방식이 표준화됩니다.

2.7 출력 스타일로 응답 톤 조정

출력 스타일을 활용하면 응답의 형식과 톤을 본인 취향에 맞게 조정할 수 있습니다. 간결함을 선호하는지, 설명을 선호하는지에 따라 경험이 달라집니다.

3. Hooks 활용 - 자동화의 핵심

제가 Claude Code 설정 중에서 가장 강력하다고 보는 것이 바로 hooks입니다. hooks는 특정 이벤트가 발생하는 시점에 미리 정해 둔 셸 명령을 자동으로 실행하는 기능으로 알려져 있습니다. 도구 실행 전후, 세션 시작 같은 시점에 스크립트를 묶어, 사람이 매번 챙기던 일을 도구가 알아서 처리하게 만드는 것입니다.

대표적인 활용 시나리오는 다음과 같습니다.

  • 자동 포매팅: 파일이 수정되면 포매터를 돌려 스타일을 일관되게 유지
  • 로깅과 감사: 특정 명령이 실행될 때 기록을 남겨 추적성 확보
  • 알림: 긴 작업이 끝나면 데스크톱 알림이나 메시지를 발송
  • 가드레일: 위험한 패턴을 사전에 점검하는 안전장치

다만 hooks는 실제 셸 명령을 실행한다는 점에서 양날의 검입니다. 의도치 않은 명령이나 신뢰할 수 없는 입력을 그대로 넣으면 위험할 수 있습니다. 그래서 제가 권하는 방식은 작게 시작하기입니다. 처음에는 단순한 echo나 포매터 실행 같은 안전한 동작 하나만 걸어 두고, 의도대로 트리거되는지 확인한 뒤 점진적으로 확장하세요. 정확한 이벤트 이름과 입력 형식은 버전마다 다를 수 있으므로, 공식 문서의 hooks 항목을 기준으로 삼는 것이 안전합니다.

4. MCP 서버 설정 - 도구 연결

MCP(Model Context Protocol)는 Claude Code가 외부 도구·데이터 소스와 연결되는 통로 역할을 합니다. MCP 서버를 설정에 등록하면, 모델이 파일 시스템 너머의 자원에 접근하거나 특정 서비스의 기능을 호출할 수 있게 된다고 알려져 있습니다. 데이터베이스 조회, 이슈 트래커 연동, 사내 문서 검색 같은 작업을 도구 안에서 처리하려는 시도가 모두 여기에 해당합니다.

MCP 설정에서 제가 강조하고 싶은 점은 연결 범위를 신중하게 정하라는 것입니다. MCP 서버는 강력한 만큼, 무엇에 접근하게 할지를 명확히 통제해야 합니다. 신뢰할 수 있는 서버만 등록하고, 민감한 자원에 대한 접근은 꼭 필요한 범위로 제한하는 것이 안전합니다.

실무에서는 MCP를 모든 프로젝트에 전역으로 켜기보다, 필요한 프로젝트에만 선택적으로 연결하는 방식을 권합니다. 예를 들어 사내 데이터에 접근하는 MCP 서버는 해당 업무 저장소에서만 활성화하고, 개인 실험 프로젝트에는 연결하지 않는 식입니다. 구체적인 서버 등록 방법과 설정 키는 버전과 서버 종류에 따라 다르므로, 각 MCP 서버의 안내와 공식 문서를 함께 참고하시기 바랍니다.

5. Slash Commands·Skills 커스터마이징

반복되는 긴 프롬프트를 매번 타이핑하는 것만큼 비효율적인 일도 없습니다. 슬래시 커맨드는 이 문제를 정면으로 해결합니다. 자주 쓰는 지시를 파일로 저장해 두면, 짧은 명령 한 줄로 그 긴 프롬프트를 불러올 수 있습니다.

제가 특히 유용하다고 보는 활용은 팀 공용 커맨드입니다. 코드 리뷰 체크리스트, 커밋 메시지 규칙, 배포 전 점검 절차 같은 반복 작업을 슬래시 커맨드로 표준화하면, 팀원 모두가 동일한 방식으로 작업하게 됩니다. 사람마다 들쭉날쭉하던 품질이 도구 수준에서 정렬되는 효과가 있습니다.

여기에 더해 Skills 같은 확장 메커니즘을 활용하면, 단순 프롬프트를 넘어 특정 작업 흐름 전체를 패키징할 수 있습니다. 보고서 생성, 특정 형식의 문서 작성처럼 절차가 정해진 작업을 재사용 가능한 단위로 만들어 두는 것입니다. 커맨드와 Skills의 정확한 등록 위치와 형식은 버전에 따라 차이가 있을 수 있으니, 실제 적용 시에는 현재 버전의 안내를 확인하세요.

6. 권한(permissions) 세밀 제어 - allow/deny 패턴

권한 설정은 생산성과 안전성이 정면으로 충돌하는 지점입니다. 너무 많은 확인 프롬프트는 흐름을 끊고, 너무 넓은 허용은 사고를 부릅니다. 그 사이의 균형을 잡는 것이 permissions의 핵심입니다.

일반적으로 권한은 settings.json의 permissions 영역에서 allow와 deny 목록으로 제어합니다. allow에 넣은 패턴은 확인 없이 실행되고, deny에 넣은 패턴은 차단됩니다. 제가 권하는 원칙은 보수적 시작입니다.

  • 안전한 읽기 전용부터: git status, git diff, 디렉터리 조회처럼 명백히 안전한 명령만 먼저 allow에 추가하세요.
  • 위험한 동작은 제외: 파일 삭제, 강제 푸시, 외부로 데이터를 보내는 명령은 자동 허용 대상에서 빼는 것이 안전합니다.
  • 패턴은 좁게: 너무 넓은 와일드카드 허용은 의도치 않은 실행을 부를 수 있으니, 가능한 한 구체적으로 지정하세요.

이렇게 점진적으로 allow 목록을 다듬으면, 반복 프롬프트는 줄어들면서도 위험한 동작에 대한 통제는 유지됩니다. 패턴 문법의 세부 규칙과 우선순위는 버전별 공식 문서를 확인하는 것이 정확합니다.

7. 생산성 팁 7가지

설정 자체를 넘어, 제가 실제로 효과를 본 활용 팁을 정리합니다. 이는 제 경험에 근거한 권고이며, 절대적 규칙은 아닙니다.

  1. 안전한 명령부터 allow 하기: 가장 자주 마주치는 읽기 전용 프롬프트를 먼저 없애면 체감 효과가 큽니다.
  2. 슬래시 커맨드로 루틴 묶기: 반복되는 지시는 즉시 커맨드로 만들어 재사용하세요.
  3. hook은 작게 시작하기: 검증되지 않은 자동화를 한꺼번에 거는 대신, 한 개씩 확인하며 늘리세요.
  4. 프로젝트별 설정 분리: 저장소마다 .claude 디렉터리에 맞춤 설정을 두면 컨텍스트가 자동으로 맞춰집니다.
  5. 민감 값은 로컬 설정에: 토큰과 개인 경로는 절대 공유 파일에 넣지 마세요.
  6. 정기적인 설정 점검: 도구가 업데이트되면 설정도 한 번씩 검토해 deprecated 키가 없는지 확인하세요.
  7. 설정도 버전 관리하기: 공유 가능한 설정은 저장소에 커밋해 변경 이력을 남기면, 문제가 생겼을 때 되돌리기 쉽습니다.

8. 팀 설정 공유 - settings.json vs settings.local.json

혼자 쓰는 도구라면 설정 파일이 하나든 둘이든 상관없습니다. 그러나 팀으로 쓰는 순간, 두 파일을 구분하는 것이 협업의 핵심 규율이 됩니다.

구분 기준은 단순합니다. 공유해야 하는가, 아닌가입니다.

  • settings.json (공유): 팀 공통 규칙, 표준 권한 정책, 공용 hooks, 공용 슬래시 커맨드. 버전 관리에 포함해 모두가 클론과 동시에 적용받게 합니다.
  • settings.local.json (개인): 개인 API 토큰, 로컬 경로, 실험적 설정. 보통 .gitignore 처리해 커밋하지 않습니다.

이 분리가 주는 이점은 분명합니다. 협업자가 저장소를 클론하는 순간 팀 표준이 자동으로 적용되면서도, 각자의 로컬 취향이 서로 충돌하거나 민감 정보가 실수로 커밋되는 일을 막을 수 있습니다. 제가 본 가장 흔한 사고는 개인 토큰을 공유 settings.json에 넣고 그대로 커밋하는 경우입니다. 처음부터 두 파일의 역할을 분명히 나눠 두면 이런 실수를 구조적으로 차단할 수 있습니다.

9. 한국 개발 환경 적용 - 한글 입력, 사내망, 프록시

해외 도구를 한국 환경에서 쓸 때는 늘 현지화 변수가 따라옵니다. Claude Code도 예외는 아닙니다. 제가 특히 신경 쓰라고 권하는 세 가지를 정리합니다.

9.1 한글 입력과 인코딩

한글 주석과 한글 파일명이 섞인 저장소에서는 인코딩 일관성이 중요합니다. UTF-8을 기본으로 통일하고, 터미널과 에디터의 인코딩 설정을 맞춰 두면 한글 깨짐 문제를 줄일 수 있습니다.

9.2 사내망과 보안 정책

금융·공공처럼 보안이 엄격한 사내망에서는 외부 연결이 제한되는 경우가 많습니다. 이때는 MCP 서버나 외부 도구 연동의 접근 범위를 사내 정책에 맞게 좁히고, 민감 데이터가 외부로 나가지 않도록 권한과 연결을 보수적으로 설정해야 합니다.

9.3 프록시 환경

사내 프록시를 거쳐야 하는 환경이라면, 프록시 관련 환경 변수를 올바르게 설정하는 것이 첫 단추입니다. 일반적으로 HTTP_PROXY, HTTPS_PROXY 같은 표준 환경 변수를 활용하며, 구체적인 적용 방식은 도구 버전과 사내 네트워크 구성에 따라 다를 수 있으니 인프라 담당자와 함께 확인하는 것이 안전합니다.

10. 주의 - 버전별 차이와 공식 문서 확인 권장

여기까지 읽으셨다면 한 가지를 꼭 기억해 주시길 바랍니다. Claude Code는 빠르게 진화하는 도구라는 점입니다. 설정 키 이름, hooks 이벤트 이름, 권한 패턴 문법은 버전에 따라 추가·변경·폐기될 수 있습니다.

그래서 저는 이 글의 모든 내용을 일반적 활용 원칙으로 읽어 주시길 권합니다. 특정 버전에서 정확히 이렇게 동작한다고 단정하기보다, 이런 카테고리의 설정이 존재하며 이런 식으로 활용할 수 있다는 방향성을 잡는 용도입니다. 실제 적용 단계에서는 반드시 다음을 확인하세요.

  • 본인이 설치한 버전의 공식 문서
  • 도구 내 도움말 슬래시 커맨드로 보는 현재 버전 안내
  • 설정 변경 후 작은 단위로 동작 검증

블로그나 커뮤니티 글은 아이디어를 얻기에 훌륭한 출발점이지만, 특정 버전의 동작을 단정하는 내용은 공식 문서로 교차 검증하는 것이 안전합니다. 이 글 역시 그 출발점 중 하나로 활용해 주시면 좋겠습니다.

11. 결론 + 즉시 적용 가능한 3가지

Claude Code의 진짜 힘은 모델 자체만이 아니라, 그 모델을 내 워크플로에 맞게 길들이는 설정에서 나옵니다. 숨겨진 설정이라는 표현은 비밀을 뜻하는 것이 아니라, 이미 존재하지만 많은 사람이 지나치는 영역을 본인 것으로 만들자는 초대에 가깝습니다. 오늘 바로 적용할 수 있는 세 가지를 정리합니다.

  • 안전한 명령을 allow에 추가하세요: 가장 자주 마주치는 읽기 전용 프롬프트부터 없애면, 마찰이 즉시 줄어듭니다.
  • 반복 프롬프트를 슬래시 커맨드로 만드세요: 매번 타이핑하던 긴 지시를 한 줄 명령으로 바꾸면, 작업 속도와 일관성이 함께 오릅니다.
  • 공유 설정과 로컬 설정을 분리하세요: settings.json과 settings.local.json의 역할을 처음부터 나눠 두면, 협업 사고와 민감 정보 유출을 구조적으로 막습니다.

설정은 한 번 만들고 끝나는 것이 아니라, 도구와 함께 자라는 살아 있는 자산입니다. 작게 시작해 검증하며 늘려 가는 습관이, 결국 문서 너머의 Claude Code를 내 것으로 만드는 가장 확실한 길입니다.
