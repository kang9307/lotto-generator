What Actually Makes a C Rewrite Faster

Where the gains come from when you lower speech enhancement inference, and what becomes fragile

2026-07-29 Tech & IT

Introduction: The Half of That Sentence Nobody Reads

We rewrote it in C and it got several times faster is a sentence that comes back around every so often. And it always has two parts. The first is the result, the second is the conditions. The trouble is that only the first part travels. A multiplier stripped of its conditions stops being information and becomes an impression.

A fresh example appeared recently: a neural network for speech enhancement, the task of recovering speech from noisy audio, reimplemented in pure C. This article is not a project write-up. The repository already does that job well. The two questions here are different. Why does rewriting inference code at a lower level make it faster, and when is that worth paying for?

Let me state the direction of the conclusion up front. The speedup is not because it is C. The real gains come from removing runtime overhead, controlling memory allocation, using vector instructions, and discarding generality that is never used. The language merely offers a comfortable place to do those things. Miss that distinction and you will prescribe the same treatment to entirely the wrong project.

Every technical statement below comes from the repositories, the paper, and the official ONNX Runtime documentation, checked directly on 29 July 2026. Figures that could not be verified were left out, and speed claims published without conditions were not used as evidence. Section 2 explains why. All scenarios in the body are generalized, hypothetical examples.

1. What Can Actually Be Verified - The Original and the Rewrite

There are two repositories in play: the original model and a C reimplementation of it. Different authors, different goals.

The original is FastEnhancer, hosted at github.com/aask1357/fastenhancer, with a paper on arXiv as 2509.21867 that reports acceptance to ICASSP 2026. According to the paper the architecture is an encoder-decoder built around RNNFormer blocks, with five size variants running from 22 thousand to 1.105 million parameters. The license is MIT.

The rewrite is github.com/kdrkdrkdr/faster-enhancer.c. It describes itself as a dependency-free C and SIMD integer runtime for FastEnhancer-Medium at 48 kHz. The license is also MIT, and the repository was created on 27 July 2026, which makes it very new.

The single most important fact here is what was rewritten. The model architecture did not change. What was rewritten is the runtime, and its scope is not some preprocessing corner but the entire inference path.

This project is specialized to a single model, and on a host that does not meet the baseline instruction set it fails at initialization rather than running slowly. That is not a defect, it is a choice. And that choice is precisely where the speed comes from. More on this below.

2. Where the 3.3x Figure Is Written, and Where It Is Not

This is the most practically useful section in the article. The one line repository description reads: 3.3x faster than the ONNX Runtime graph, same quality. It is an eye-catching claim, and it is a large part of why the project circulated.

And yet the performance section of the README contains no speed comparison against ONNX Runtime. The place ONNX appears in the README is the quality section, and there the ONNX graph serves not as a speed target but as an accuracy baseline: a 32-bit floating point graph of the same weights, against which the 8-bit engine's output is checked.

So that multiplier has no conditions beside it. Which device, how many threads the baseline used, how long the input was, what settings the baseline build carried, none of it is stated. A multiplier without conditions can be neither reproduced nor refuted. This article therefore mentions the number but does not rest anything on it.

By contrast, the values the README puts in its own table do come with conditions. It specifies measurements on 5,569-frame clips, steady state percentiles after discarding the first 200 frames, taken as medians over repeats.

DeviceKernel tierRTF p50RTF p99Time per frame
Apple M2I8MM0.0690.0840.458 ms
Galaxy S23+I8MM0.0960.1050.640 ms

This table reports its own real-time headroom. It says nothing about how much faster it is than any other runtime. Two kinds of claim coexist in the same document: one carries conditions and is checkable, the other does not and is not.

Reading this as a failure of the author's honesty teaches you nothing. A one line description is one line, and measurement conditions do not fit in it. The real problem starts on the reading side. That line gets quoted, and the quote gets requoted, and the conditions never once come along. Which suggests a habit: when you see a speed claim, read the conditions column before the multiplier. If the conditions column is empty, the number has not said anything yet.

3. Splitting the Speedup Into Four Sources

Now the mechanics. The gain from a low-level rewrite is not one lump. It splits into at least four sources, each contributing a different amount, and each differing in whether you could have obtained it without changing languages at all.

a. Removing runtime overhead

A general purpose inference runtime interprets a graph, selects a kernel per node, validates tensor descriptors, and crosses execution provider boundaries. That work is paid every single call, regardless of the arithmetic. And here is the key point: this fixed cost does not scale with model size.

Which turns it into a question of ratio. In this case the per-frame budget is 6.667 ms and the actual arithmetic is on the order of 0.458 ms. When the arithmetic is that small, the per-call fixed cost becomes a relatively large share. In a large model that spends hundreds of milliseconds per call, the very same fixed cost is rounding error. That is why an identical rewrite wins big on small models and barely wins at all on large ones. Miss this asymmetry and you will spend effort in the wrong place.

b. Controlling memory allocation

The repository states that it is allocation-free after initialization and that all state lives in a single 432,384-byte structure. What this design reduces is the tail, not the average.

In audio that distinction decides everything. However good the average is, one frame that misses its deadline produces an audible dropout. People do not hear mean latency, they hear the glitch. Which is why the number to read in the table above is not p50 but p99. Against 0.069, a p99 of 0.084 means the tail sits tightly packed. Allocation during execution is what pries that gap open, and so do garbage collection pauses and just-in-time warm-up, since anything that occasionally takes a long time shows up right here.

c. SIMD and integer arithmetic

The third axis is instructions. The repository states that it hand-wrote 8-bit integer matrix multiply kernels in six variants, one per instruction set. But the gain here belongs to the hardware, not the language.

The official ONNX Runtime documentation is explicit about this. The performance improvement depends on your model and hardware, and old hardware has none or few of the instructions needed to perform efficient inference in int8. It further notes that x86-64 with VNNI and Arm-based processors with dot-product instructions generally achieve better performance.

Invert that statement and you get a working rule. If the target hardware is not fixed, you cannot count this axis in your estimate at all. And this axis is one you can largely obtain without changing languages, because a general runtime's quantization path already reaches for the same instructions.

d. Discarding generality you never use

The most underrated axis, and in practice probably the largest contributor. A general runtime prepares for the unknown: arbitrary operators, dynamic shapes, multiple precisions, arbitrary batch sizes. That preparation is not free.

This repository threw all of it away. It fixed one model, one sample rate, one frame size. The price is that there is not even a scalar fallback: a host that does not meet the baseline instruction set fails at initialization. The speed was bought with surrendered flexibility, and that trade is hard to reverse.

So how much does the language itself contribute?

Honestly, it is hard to isolate and usually overstated. Given the same algorithm, the same precision and the same instructions, another compiled language would emit broadly similar machine code. What C provided was not magic but a comfortable place to do the four things above: an environment where controlling allocation directly, dictating memory layout, and reaching instructions through intrinsics all feel natural.

Deciding whether to switch languages at all is a separate axis, covered in Moving Python to Rust. This article stays on a different problem: reimplementing the same model on a different runtime, and proving it still produces the same answer.

The last column is the point of the table. Of five rows, only one is genuinely exclusive to a rewrite. The rest are largely reachable inside the runtime you already use. Which is why a rewrite should be a last resort rather than a first move.

4. Get the Signal Processing Right First

Before continuing with speed, it is worth being precise about what is being processed. Skim this layer and every measurement and verification that follows will wobble.

STFT - frames and hops

Most speech enhancement models do not consume the waveform directly. They go through a short-time Fourier transform, in three steps: cut the waveform into fixed-length frames, multiply each frame by a window function, and apply a discrete Fourier transform. Frames are cut overlapping, and the non-overlapping advance between them is the hop length.

  • Frame length sets frequency resolution. Longer frames separate frequencies better and smear time.
  • Hop length sets the frame rate. Shorter hops mean more frames per second and proportionally more computation.
  • The window function softens the discontinuity at frame edges. Analysis and synthesis windows must be paired with the hop so that amplitude is restored when frames are added back together.
  • The values this rewrite states are a 1024-point real FFT, 320 samples in and out per frame, and a 6.667 ms cadence. At 48 kHz, 320 samples is exactly 6.667 ms.
  • The original paper gives a transform size of 512 for the 16 kHz models and varies the hop size across model variants.

Masking versus direct waveform generation

This is where reimplementation difficulty is decided, so it matters more than it looks.

According to the original paper the model predicts a two-channel mask and multiplies it with the input spectrogram to produce the enhanced spectrogram. In other words it is mask based. The model decides how much of what to keep, and the sound itself comes from the input.

  • Property of mask based models - the output is a deterministic function of the input. The same input must yield the same output, which makes reimplementation comparison easy. Feed both implementations the same file and compare numbers.
  • Property of direct generation - if sampling is involved, the same input may produce different outputs. At that point numeric comparison stops being available as a method, and you must fall back on perceptual metrics and statistical comparison. Verification cost jumps a level.
  • Practical implication - before planning a rewrite, check whether the model is deterministic. If it is not, the plan to confirm they match must be redesigned from scratch.

There are two real-time measures, not one

Here are the two numbers that get conflated most often.

RTF = processing time / duration of the input audio

  one frame = 320 samples @ 48 kHz = 6.667 ms
  if one frame takes 0.458 ms to process
      RTF = 0.458 / 6.667 = 0.069

  RTF < 1     there is headroom
  RTF >= 1    the deadline is missed - audio drops out

  Note: RTF is throughput. Algorithmic latency is structure.
    Even driving RTF toward zero leaves the
    704 samples (14.67 ms) added by STFT alignment untouched.

The real-time factor is processing time divided by input audio duration, which is how the original paper defines it, and it is a throughput measure. Algorithmic latency is instead the delay created by the structure. This rewrite states that STFT alignment adds a fixed 704 samples, or 14.67 ms.

Their relationship fits in one sentence. Buying a faster chip lowers RTF and does not lower algorithmic latency by a single microsecond. Cutting latency means changing the structure. That is exactly why the original paper observes that causal convolutions with a time-axis kernel size greater than one introduce latency, and states that it uses only convolutions with a time-axis kernel size of one to keep latency minimal. The absence of look-ahead was nailed down at design time.

5. The Measurement Trap - A Benchmark Races, an Audio Callback Does Not

This section carries the most valuable lesson in the whole case. Fittingly, the lesson is one the repository wrote into its own documentation.

The README line is short: A benchmark races; an audio callback does not. That single sentence contains the most common error in performance measurement.

  • A benchmark loop pushes frames in as fast as the core will take them. The core never idles and the clock stays pinned at its ceiling.
  • A real audio callback delivers one frame per 6.667 ms. The core idles in between, and the frequency governor responds by dropping the clock.
  • The repository measured that difference and published it. On an M2 performance core, running the same work paced costs 4.2x more per frame, giving an RTF of 0.286, while using 49% less energy.

Same code, same device, same amount of work, and the RTF splits into 0.069 and 0.286. Neither is a lie. The conditions simply differ. It is hard to find a cleaner demonstration of why a speed claim without conditions says nothing. And it takes us straight back to the 3.3x in section 2: a multiplier with no stated conditions is a number that can swing by roughly this much.

ConditionWhy it mattersDistortion when omitted
Warm-upEarly frames are slow from cache fills, branch prediction and page faultsIncluding the first frames reports worse than reality
Feeding styleRacing and paced feeding make the governor pick different clocksThe same code is reported with a 4x spread
Thread countRuntime defaults usually equal the physical core countA single-thread build gets compared against an all-core baseline
Batch sizeStreaming inference runs at batch oneBatch throughput gets used to claim real-time headroom
PercentilesIn audio the upper percentile, not the mean, decides dropoutsPeriodic spikes get swallowed by the average
Input length and repeatsShort clips never reach steady stateMeasurement noise overturns the result
Hardware and ISAInteger gains depend on instruction supportNothing reproduces on a different device
Baseline settingsThe comparison target's options drive the outcomeBeating an untuned baseline gets reported as an achievement

The thread row deserves emphasis. The official ONNX Runtime documentation distinguishes threads that parallelize inside an operator from those that parallelize across graph nodes, and notes that by default the total for the former equals the number of physical CPU cores. It also explains that spin waiting, where threads spin waiting for work, provides faster inference but consumes more CPU cycles, resources and power, and offers settings to disable it or bound it in time.

The practical conclusion is blunt. Put a single-threaded rewrite next to a general runtime left on defaults, and the multiplier you report may be measuring a thread setting rather than runtime quality. Tuning the baseline fairly matters as much as building the rewrite, and it is usually far cheaper.

6. The Real Risk of a Rewrite Is Not Speed, It Is Subtle Numeric Drift

Now the axis changes. Everything so far has been about getting faster; from here it is about getting it wrong. In practice a rewrite does not fail by not working. If it does not work you find out immediately. The real accidents come from working, but slightly differently.

In audio that slightly is especially bad. Human ears do not hear mean error, they hear artifacts. A value that spikes in one frame barely moves an averaged metric but leaves a clearly audible click. So verification cannot end at a single average and must be built in layers.

Layer 1 - Freeze a baseline to disk

The first task is not optimization but capturing a baseline. Dump the original runtime's output to a file and record the runtime version, settings and preprocessing alongside it. Without this every later comparison is meaningless, because when a difference appears you will have no way to know which side moved.

# 1) freeze the baseline to a file (record version and settings too)
ref_infer  --model base.onnx --in clip.wav --out ref.f32

# 2) run the rewrite over the same input
fe_cli     --in clip.wav --out new.f32

# 3) judge against a tolerance decided in advance
compare    ref.f32 new.f32 --atol 1e-4 --rtol 1e-3
#   max_abs_err      = 3.1e-05     pass
#   frames_over_tol  = 0 / 5569    pass
#   first_bad_frame  = none        pass

Layer 2 - Decide the tolerance first

Order is everything. Set a tolerance after seeing the results and people will invariably set it to whatever passes. So write it down before looking at any number. And when setting it, separate two cases.

  • Cases where bit-exactness is a reasonable target - a port that keeps the same precision and the same order of operations. Here you can demand exact equality, and any divergence is a bug.
  • Cases where it is not - a rewrite that introduces quantization or reorders arithmetic. Floating point addition is not associative, so reordering alone changes the last digits. Here the verdict must come from metrics, not exact equality.
  • What happens if you confuse them - set an unachievable bar and the team will soon start ignoring the bar. An ignored gate is worse than no gate.

Layer 3 - Judge with metrics

The comparison table this repository published is a good template. It sets the 32-bit floating point ONNX graph of the same weights as the baseline and lays four metrics side by side on an 824 utterance test set.

MetricNoisy inputfp32 ONNXint8 rewrite
PESQ1.9673.0603.054
STOI0.92110.95120.9509
SNR (dB)8.3919.4319.35
LSD14.7212.5612.33

What this table gets right is keeping the noisy input column. Without it there is no basis for judging whether the gap between 3.060 and 3.054 is large or small. With it, the answer is immediate: the model lifted 1.967 to 3.060, and dropping to 8 bits gave up 0.006. A loss figure without a denominator cannot be read. That is the format to carry into any rewrite report you write.

The official ONNX Runtime documentation also states that quantization is not a loss-less transformation and may negatively affect a model's accuracy, and recommends comparing tensors between the original and quantized models to locate problem areas. It further notes that dynamic quantization is recommended for RNNs and transformer-based models, and static quantization for convolutional models. The fact that the recommendation splits by model family is itself the reason not to apply quantization as a default.

Layer 4 - Keep a separate determinism gate

Metric verification alone is not enough. Metrics are averages, so they swallow a rare error that occurs in only one kernel. Hence one more layer.

This repository placed a gate requiring that every kernel tier produce the same hash per clip. In the document's own framing, bit-identity across tiers is a gate, not an aspiration. Run it on NEON or on I8MM and the output bytes must match to pass.

# output must be identical across kernel tiers
for tier in neon dotprod i8mm; do
    fe_cli --tier "$tier" --in clip.wav --out "out_$tier.f32"
    sha256sum "out_$tier.f32"
done

# all three hashes equal means pass.
# any mismatch means that tier's kernel is quietly producing different values.
# Note: before trusting the gate, deliberately perturb one rounding step
#   and confirm that it actually turns red.

Those last two lines matter. A verification system cannot be trusted until you have confirmed it catches something you broke on purpose. Perturb the rounding in one kernel and watch whether the gate really goes red. If it does not, every green light up to that point meant nothing.

The structure of what you are reimplementing matters too. The layers in this project include convolutions, GRU and multi-head attention mixed together. Recurrent layers carry state forward, so a small error in one frame propagates into the next. Which means that in a model with recurrence you cannot compare a single frame and call it done. You have to check on long clips whether the error grows or decays over time. That is why the example above counts frames over tolerance across all 5,569 frames.

Below is the shape of an interface that makes this kind of verification easy to attach. It is not an implementation but a conceptual sketch of where to draw the boundary.

/* concept sketch - a frame loop with no allocation after init */
#include <stdint.h>

typedef struct fe_state fe_state;      /* all state in one block */

int  fe_init(fe_state **s);            /* allocation happens only here */
void fe_process(fe_state *s,
                const int16_t *in,     /* 320 samples in  */
                int16_t *out);         /* 320 samples out */

/* audio callback - invoked once every 6.667 ms */
void on_frame(fe_state *s, const int16_t *in, int16_t *out) {
    fe_process(s, in, out);   /* no malloc, no locks, no exceptions */
}

The advantage of this shape is that it is easy to verify. State in one block is easy to dump and diff, and a callback close to a pure function makes it easy to demand the same output for the same input. An implementation with state scattered everywhere may be fast but is hard to prove equivalent. In a rewrite, provability should itself be a design goal.

7. Other Verifiable Cases - A Lineage, Not a Ranking

This approach is not a new idea. Below are only the things confirmable from official repositories and documentation. No ranking is implied. The three sit at different layers.

  • RNNoise - github.com/xiph/rnnoise. A noise suppression library based on a recurrent neural network, implemented in C with Python used for training and model conversion. It is BSD-3-Clause and handles 48 kHz 16-bit mono PCM, describing itself as a hybrid DSP and deep learning approach. The documentation recommends using an architecture with AVX2 support, or enabling x86 runtime CPU dispatch, for performance. Here too what gets named as the source of the gain is not the language but the instruction set.
  • ggml - github.com/ggml-org/ggml. A tensor library for machine learning, MIT licensed. Its README lists among its own features no third-party dependencies, zero memory allocations during runtime, and integer quantization support, side by side. That is three of the four axes from section 3 written down as library-level design goals. The well-known local speech recognition and language model projects sit on top of it.
  • ONNX Runtime - the official documentation. This is the opposite choice: a documented path for extracting remaining performance without rewriting anything. The quantization page splits which quantization suits which model family and states that improvement depends on the model and hardware. The threading page separates intra-operator from inter-operator parallelism and offers spin-wait controls.

Line the three up and one sentence remains. The gain comes not from the name of a language but from what you decline to do and which instructions you use. ggml advertising no and zero as features, the RNNoise docs naming instruction sets first, and ONNX Runtime spelling out hardware dependence are all the same statement.

8. When Is It Worth Paying For?

Now the judgement. A rewrite is not free. Maintaining it costs more than building it, and that bill is issued every time the model changes.

Signals that it is worth it

  • You must fit on edge or on-device targets - some environments simply cannot host a framework. The gap between a 162 KiB static library and a typical inference framework is not a question of fast versus slow but of fits versus does not fit. Here there is often no alternative.
  • You have a hard real-time deadline - a fixed budget like 6.667 ms where the upper percentile decides product quality. Architectures where allocation, garbage collection or JIT warm-up create tails are structurally disadvantaged.
  • Deployment size and startup time are requirements - products where processes start and stop constantly, or where download size directly affects conversion.
  • The dependencies themselves are the bottleneck - in environments requiring import review or supply chain audit, zero dependencies sharply reduces audit cost. This is the rare case where a rewrite is justified for reasons unrelated to performance.
  • The model is frozen - discussed again below, but this is effectively the most important precondition of all.

Signals to stop

  • The model is still changing - a rewrite pins the weights and graph down by hand. Add a layer next week and the kernels must be reworked, while the research side waits on the rewrite. The moment optimization starts eating experiment velocity, the economics usually invert.
  • There is no accuracy verification setup - with no baseline output, no test set and no metrics, there is no way to prove the rewrite is correct. A speedup measured in that state is hope, not measurement.
  • One person maintains it - few people can read hand-written vector kernels. When that person leaves, what remains is fast code nobody can fix. That is a liability, not an asset.
  • The bottleneck has not been located - a rewrite begun without profiling usually optimizes something that was never hot. The time may be going into file I/O, resampling or copies.
  • The target hardware is undecided - integer gains depend on instruction support. Skip the scalar fallback and some devices will not run at all; add one and it becomes another thing to verify.
  • The goal is only to be faster - if you cannot state numerically how fast is fast enough, there is no finish line. Write down the deadline and the target percentile first.

What to try before rewriting

In order of cheapest and most reversible first.

  1. Profiling - find out where the time actually goes. Arithmetic, dispatch, copies or I/O. Without this answer every later step is guesswork.
  2. Runtime options - pin the thread count explicitly, control spin waiting, and check the graph optimization level. A single configuration line genuinely can be worth weeks of rewriting.
  3. Quantization - start with what works without retraining, choosing the approach the documentation recommends for your model family. And always record the loss next to the improvement.
  4. Narrowing generality - fix input shapes, pin batch size to one, and remove needless copies and dtype conversions in pre and post processing. This axis is largely reachable without changing runtimes at all.
  5. Then rewrite - after all of the above still misses the deadline, and the model is frozen, and the verification setup exists. Only when all three hold at once.

Conclusion: Going Low-Level Means Making Fewer Promises

Start with what this case actually demonstrated. A small streaming speech model can run on a fraction of a CPU core with no inference framework at all; dropping to 8 bits can cost a metric loss that is small relative to the improvement; and that fact can be left behind in a provable form, across two layers of metrics and hashes. All of that is confirmable from documentation and tables.

Be equally clear about what it did not demonstrate. The conditions behind the 3.3x figure appear nowhere in the public documentation. And whether this approach yields the same value on large models or on models that change often is outside what this case can answer. It is also worth weighing that the repository is only days old.

Three things to take away.

  1. Read the conditions column before the multiplier. Without conditions the number is not information. This very repository documented that the same code on the same device can yield RTF 0.069 and 0.286.
  2. What justifies a rewrite is a constraint, not speed. When it must fit and does not, when there is a deadline and the tail spikes, when the dependencies themselves block approval. Wanting it faster is not a constraint.
  3. Build the way you will judge completion before you start. Baseline outputs, a tolerance fixed in advance, metrics reported next to the improvement, and a regression gate validated by breaking it on purpose. Without those four the project does not end.

One last line. The essence of going low-level is not changing languages but withdrawing promises. The promise to accept any model, the promise to accept any shape, the promise to run on any device, taken back one at a time. You get faster in proportion to the promises withdrawn, and more brittle in exactly the same proportion. Asking whether that trade fits the product in front of you should come long before choosing which language to rewrite it in.
