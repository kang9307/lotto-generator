きっかけ — SvelteKitの案件で再会したNode

筆者のDavid Bushellは、今月SvelteKitベースのクライアント案件でNodeを集中的に使ったと書いている。長いあいだDenoを標準のランタイムとして使ってきたためNodeの扱い方を忘れていたが、戻ってみるとECMAScriptの構文がサポートされ、以前の煩わしいAPIが置き換えられるか近代化されていた、というのが記事の出発点である。彼が「最も重要」として挙げるのは、require()を目にする必要がないという点だ。

回顧は四つの部分から成る。パッケージ管理ツールの選択、TypeScriptの実行、自作の静的サイトジェネレーターをDenoからNodeへ移した経験、そしてDenoを離れた理由である。測定や比較実験を目的とした文章ではなく、短い個人の記録である。「Denoを使い続けたのは習慣と慣れのためだった」という一文も筆者自身のものだ。

以下では、筆者がNodeへ戻る過程で使ったものを一つずつ取り上げ、該当する公式ドキュメントの定義と制限の隣に置いていく。ランタイムを選ぶ際に分かれ目となる一般的な軸は、ランタイムを書き直すという決断に整理してある。

バージョン管理とパッケージ管理 — fnmとpnpm

筆者はNodeのバージョン切り替えツールとしてFast Node Manager(fnm)を選んだ。NVMとnpmについての自身の古い経験が良くなかったこと、そしてバージョンの切り替えにはfnmのほうが良いと聞いたことが理由である。自分は最新版を使うほうだが、安定性を求めるクライアント案件があるためバージョンを行き来する必要がある、と書いている。fnmのREADMEが示す特徴は次のとおりである。

  • 性格。 READMEはfnmを、Rustで作られた高速でシンプルなNode.jsバージョンマネージャーと紹介し、単一ファイルでインストールが容易であり、即座に起動することを特徴に挙げている。
  • 対応プラットフォーム。 macOS、Windows、Linuxである。
  • バージョンファイル。 .node-versionと.nvmrcのファイルを認識する。
  • インストール経路。 インストールスクリプトのほかに、Homebrew、Winget、Scoop、Chocolatey、Cargo、リリースバイナリを案内している。
  • シェルの設定。 fnm envの出力をシェルで評価して環境変数を設定しなければ使えない。--use-on-cdオプションを付けた例が、Bash、Zsh、Fish、PowerShellごとに載っている。

パッケージマネージャーにはpnpmを選んだ。筆者はその理由を、侵害されるのを避けるためだと書いている。自分が使うスクリプトのいくつかがバイナリ名を固定で書いているため、次の二つのエイリアスを追加したという。

alias npm=pnpm
                    alias npx=pnpx

筆者は後から追記した注で、このエイリアスは、npmがインストールされていることを前提にしたインストール手順のコマンドをそのまま写して使うときに役立つと説明している。設定を置く場所は、pnpmのドキュメントが別に定めている。pnpmはコマンドライン、環境変数、pnpm-workspace.yamlから設定を読み、.npmrcからは認証とレジストリの設定だけを読む。それ以外の設定はpnpm-workspace.yamlかグローバルのconfig.yamlに置く。以下の設定がすべてpnpm-workspace.yamlに入るのはそのためである。

pnpmのインストール遅延と信頼ポリシー — minimumReleaseAgeとtrustPolicy

筆者はpnpm-workspace.yamlに次の二行を追加した。

minimumReleaseAge: 1440
                    trustPolicy: no-downgrade

minimumReleaseAge — 公開後の経過時間

pnpmのドキュメントの定義は次のとおりである。minimumReleaseAgeは、あるバージョンが公開されてからpnpmがそれをインストールするまでに経過していなければならない最小の時間を、分単位で定める。直接の依存関係だけでなく、推移的依存関係を含むすべての依存関係に適用される。ドキュメントは目的を「侵害された、あるいは欠陥のあるパッケージをインストールするリスクを減らすこと」と記し、ほとんどの場合、悪意あるリリースは1時間以内に発見されてレジストリから削除されると付け加えている。

  • 導入バージョンと既定値。 v10.16.0で追加された。既定値はv11から1440で、それより前は0である。
  • 1440の意味。 単位は分なので、1440は1日である。ドキュメントの例も同じ値を「少なくとも1日前にリリースされたパッケージだけをインストールする」と説明している。
  • 除外リスト。 minimumReleaseAgeExcludeにパッケージ名を書くと、そのパッケージは公開直後にインストールされる。パターンはv10.17.0から、特定バージョンの指定はv10.19.0から使える。
  • 該当するバージョンがないとき。 minimumReleaseAgeStrict(v11.0.0)が決める。値がfalseなら条件を満たさないバージョンにフォールバックしてインストールを続行し、trueなら依存関係の解決が失敗する。この値はminimumReleaseAgeを明示的に設定した場合に既定でtrueになり、組み込みの既定値1440だけを使う場合は後方互換性のために厳格ではない動作になる。
  • 公開時刻を持たないレジストリ。 minimumReleaseAgeIgnoreMissingTime(v11.0.0、既定はtrue)が有効であれば、メタデータにtimeフィールドがないパッケージはこの検査を飛ばす。

筆者は、最初この値を「1か月」に設定したところ、pnpmが適合するバージョンを選ぶのに苦労する依存関係の問題が生じたため、「1日」に下げたと書いている。彼が書いた1440は、ドキュメントにあるv11の既定値と同じ数字である。ただし、値をファイルに明示的に書くと、上記の厳格モードが既定で有効になる点が異なる。1か月にしたときの問題がこの厳格モードに関係していた可能性は、ドキュメントの文言から導いた解釈であり、原文は原因を説明していない。

trustPolicy — 信頼レベルが下がったバージョン

pnpmのドキュメントによれば、trustPolicyをno-downgradeにすると、パッケージの信頼レベルが以前のリリースより下がった場合にインストールが失敗する。ドキュメントが挙げる例は、以前は信頼された公開者(trusted publisher)が公開していたのに、いまは来歴証明(provenance)しかない、あるいは信頼の証拠がまったくない場合である。

  • 導入バージョンと既定値。 v10.21.0で追加され、既定値はoffである。取り得る値はno-downgradeとoffの二つである。
  • 比較の基準。 信頼の検査はsemverではなく、公開日だけを基準にする。より早く公開されたバージョンの中に、より強い信頼の証拠を持つものが一つでもあれば、そのパッケージはインストールできない。
  • プレリリース。 v10.24.0以降、正式版をインストールする際には、プレリリース版の信頼の証拠は評価から除外される。
  • 除外リスト。 trustPolicyExclude(v10.22.0)に書いたパッケージやバージョンは検査から外れる。
  • 古いバージョン。 trustPolicyIgnoreAfter(v10.27.0)は、公開から指定した分数より長く経過したパッケージについて検査を無視させる。

筆者は、自前でホストするForgejoのインスタンスに移った後、自分のパッケージが「provenance」を失い、自分のパッケージを許可するようにpnpmの信頼ポリシーを設定しなければならなかったと書いている。どのキーを使ったのかは原文にない。ドキュメントでその用途に当たる設定はtrustPolicyExcludeである。

設定キー pnpmのドキュメントの定義 既定値・導入バージョン 筆者が選んだ値
minimumReleaseAge 公開後、インストールまでに経過していなければならない最小時間(分) 1440(v11から)、それ以前は0・v10.16.0 1440(最初は「1か月」)
minimumReleaseAgeStrict 条件を満たすバージョンがないときに解決を失敗させるかどうか 明示的に設定するとtrue・v11.0.0 —
trustPolicy 信頼レベルが以前のリリースより下がるとインストールが失敗する off・v10.21.0 no-downgrade
trustPolicyExclude 信頼ポリシーの検査から除外するパッケージセレクターのリスト 空のリスト・v10.22.0 — (自分のパッケージを許可したとだけ書いている)
strictDepBuilds 未レビューのビルドスクリプトがあると、0以外の終了コードで終わる true・v10.3.0 —

インストールスクリプトのブロック — allowBuildsとstrictDepBuilds

筆者は「pnpmはpost-installスクリプトもブロックする」と一行で書いている。pnpmのドキュメントでこの動作を決めている設定は次のとおりである。

  • 既定の動作。 allowBuildsに書かれていないパッケージは、既定でスクリプトの実行が許可されず、「未レビュー」のものとして扱われる。
  • エラーか警告か。 strictDepBuildsの既定値がtrueであるため、既定ではエラーが出力され、未レビューのビルドスクリプト(ドキュメントの表現ではpostinstallスクリプト)を持つ依存関係があると、インストールは0以外の終了コードで終わる。falseにすると警告に変わる。
  • 許可の方法。 allowBuildsはパッケージのマッチャーをキーとするマップで、trueは許可、falseは不許可を表す。インストール中にスクリプトが無視された依存関係は、プレースホルダーの値とともにpnpm-workspace.yamlへ自動的に追加され、pnpm approve-buildsとpnpm addの--allow-buildフラグも同じ場所に書き込む。
  • 以前の設定。 onlyBuiltDependencies、neverBuiltDependencies、ignoredBuiltDependenciesなどはv11で削除され、allowBuildsに置き換えられた。
  • すべてを許可する。 dangerouslyAllowAllBuilds(v10.9.0、既定はfalse)をtrueにすると、依存関係のpreinstall、install、postinstallスクリプトが承認なしで実行される。ドキュメントは、推移的依存関係も含めて、現在と将来のすべてのスクリプトが許可されるという警告を付けている。
  • ignoreScriptsとの違い。 ignoreScripts(既定はfalse)は、プロジェクトのpackage.jsonと依存関係に定義されたスクリプトを一切実行しない、別個の設定である。

原文は、npm側の動作については疑問符の付いた一文を残しているだけである。原文が名前を挙げるサプライチェーンの事例はShai-Huludだけであり、その経過はnpmサプライチェーン攻撃の分析で扱っている。

Nodeの型の除去 — ドキュメントが定義する範囲

筆者は、NodeがいまやTypeScriptを実行できると書いている。Node.js v26.10.0のドキュメント「Modules: TypeScript」は、ランタイムでTypeScriptを使う道を二つに分けている。TypeScriptのすべての構文と機能を完全にサポートするにはサードパーティのパッケージを使い(ドキュメントはtsxを例に挙げる)、軽量なサポートとしては組み込みの型の除去(type stripping)を使う。

組み込み機能の定義は短い。Node.jsは既定で、消去可能な(erasable)TypeScript構文だけを含むTypeScriptファイルを実行する。TypeScript構文は空白に置き換える。型チェックは行わない。この機能を無効にするには--no-strip-typesフラグを使う。ドキュメントの変更履歴は次のとおりである。

  • v22.6.0。 型の除去が追加された。
  • v23.6.0、v22.18.0。 型の除去が既定で有効になった。
  • v24.3.0、v22.18.0。 実験的機能の警告を出さなくなった。
  • v25.2.0、v24.12.0。 型の除去が安定(stable)になった。
  • v26.0.0。 --experimental-transform-typesフラグが削除された。v22.7.0で追加されていたフラグである。
項目 Node.jsの動作 ドキュメントの節
消去可能なTypeScript構文 空白に置き換えてから実行する Type stripping
型チェック 行わない Type stripping
tsconfig.json 読まない。pathsや古い構文への変換のように、その設定に依存する機能は意図的にサポートしない Type stripping
enum宣言 エラー TypeScript features
ランタイムコードを持つnamespace エラー(ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX)。ランタイムコードを含まないnamespaceはサポートされる TypeScript features
parameter properties、import aliases エラー TypeScript features
デコレーター 変換せず、パーサーエラーになる TypeScript features
typeキーワードのない型のimport 値のimportとして扱われ、ランタイムエラーになる Importing types without type keyword
.tsxファイル サポートしない Determining module system
ソースマップ 生成しない。空白への置き換えなので行番号が保たれる Source maps
REPL、--check、inspect TypeScript構文をサポートしない Non-file forms of input
node_modules配下のファイル 処理を拒否する Type stripping in dependencies

ドキュメントは、この範囲が意図されたものだと説明している。JavaScriptのコード生成が必要な構文をあえてサポートせず、インラインの型を空白に置き換えることで、ソースマップなしにTypeScriptのコードを実行できるという。デコレーターについては、現在TC39のStage 3の提案であるため変換せず、JavaScriptがネイティブにサポートするまではサポートしないと書いている。推奨事項としては、TypeScript 5.8以降と次のtsconfig.jsonの設定を挙げる。

{
                      "compilerOptions": {
                         "noEmit": true, // Optional - see note below
                         "target": "esnext",
                         "module": "nodenext",
                         "rewriteRelativeImportExtensions": true,
                         "erasableSyntaxOnly": true,
                         "verbatimModuleSyntax": true
                      }
                    }

ドキュメントの注によれば、noEmitはビルドスクリプトのように*.tsファイルを実行するだけの場合に使い、*.jsファイルを配布するつもりであれば不要である。モジュールシステムも変換しない。.tsファイルのモジュールシステムは.jsと同じ方法で決まり、.mtsは常にESモジュールとして、.ctsは常にCommonJSとして実行される。import文ではファイル拡張子が必須であり、import './file.ts'のように書く。tsconfigのpathsは変換されないためエラーになり、ドキュメントは最も近い機能として、#で始める必要があるsubpath importsを挙げている。ファイル以外の入力のうち、--evalとSTDINでは型の除去を使える。

node_modulesの配下では型を除去しない

筆者がぶつかったのは、上の表の最後の行である。彼は、TypeScriptのパッケージをそのままnpmに公開することはできないと書き、次のエラーを示している。

error: [ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING]:
                    Stripping types is currently unsupported for files under node_modules

Node.jsのエラーのドキュメントは、ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPINGを「node_modulesディレクトリの配下にあるファイルについては型の除去がサポートされない」と説明し、v22.6.0で追加されたエラーコードだと記している。型の除去の機能そのものと同じバージョンである。理由は、TypeScriptのドキュメントの「Type stripping in dependencies」の節に一文で書かれている。パッケージ作者がTypeScriptで書かれたパッケージを公開するのを思いとどまらせるため、Node.jsはnode_modulesのパス配下のフォルダにあるTypeScriptファイルの処理を拒否する、というものだ。

筆者はこの制限を「技術的というより哲学的」と評している。ドキュメントが示す理由が実装上の限界ではなく公開の慣行に関するものであるという点で、その読み方はドキュメントの文言と食い違わない。彼は、ECMAScriptに軽量な「ネイティブの型」が入ることを望むと書き、型アノテーションの提案があることに触れつつも、それが実を結ぶ前に自分は引退しているだろうと付け加えている。この制限が筆者の作業にもたらした結果は三つある。

  • バンドラー。 TypeScriptのパッケージをそのまま公開できないため、バンドルツールが必要になり、筆者はTsdownを使った。追加された設定ファイルは二つである。
  • 設定ファイルの数。 彼は、deno.jsonなどを削除した分と合わせれば差し引きゼロだと書いている。
  • 来歴証明。 自前でホストするForgejoに移った後、パッケージのprovenanceが失われ、前の節で触れた信頼ポリシーの例外が必要になった。

静的サイトジェネレーターの移行 — 変えたものと15%という値

筆者がNodeに対する最後の試験としたのは、自作の静的サイトジェネレーターをDenoから移すことだった。彼は、Nodeのバージョンで数個前までなら大規模なリファクタリングが必要だったはずの作業が、Node v26.10.0では意外なほど少なくて済んだと書いている。

  • ファイルシステム。 必須の変更の一つ目は、DenoのファイルシステムAPIをnode:fsに置き換えることだった。彼は、node:fsは自分の記憶にある約10年前と比べて大きく改善されていると書いている。
  • HTTPサーバー。 二つ目は、Deno.serveをHonoのnodeアダプターに置き換えることだった。筆者はこのアダプターを、node:httpを包んだものだと説明している。
  • パスのモジュール。 その後に行った追加の変更は、Denoの@std/pathをnode:pathに置き換えたことだけで、importを差し替えるだけの置き換えだったという。
  • ビルド時間。 この最小限の移行を終えた後、ビルドが15%速くなったと書いている。
  • 残された余地。 コードベースは依然としてDenoの慣用的な書き方に従っており、ほかの組み込みのNode APIを使っていない分、性能を取りこぼしているだろうと彼は推測している。

15%は、筆者一人のサイトジェネレーター一つから得られた値である。原文には、ビルドの絶対時間、サイトの規模、測定回数、比較対象のDenoのバージョンがない。この数字は、同じコードを最小限の修正で移したときに、筆者の環境でビルドが遅くならなかったという記録であり、二つのランタイムの一般的な性能差を示す値ではない。

筆者が挙げた離脱の理由と、この事例の範囲

筆者がDenoを離れる直接のきっかけとして挙げるのは三つである。

  • 数週間にわたって続いたZSH統合の不具合
  • JSRの「429 (Too Many Requests)」応答
  • 同時HTTPリクエストでDenoが詰まるバグ

三つの項目はいずれも原文に一行ずつ書かれているだけで、バージョンや再現条件、issueへのリンクはない。JSRのサポートが依頼に応じてすぐにアカウントを削除してくれたこと、自分のパッケージは表示されないが古いバージョンは引き続きインストールできることも書かれている。原文にはこのほか、Denoを作っている会社の方向性についての筆者の評価が載っているが、それは個人の意見であり、上記の技術的事実とは別のものである。筆者が使ったものを公式ドキュメントと並べると次のようになる。

この事例が語れる範囲は狭い。一人が、自分の静的サイトジェネレーター一つをNode v26.10.0へ移した記録である。筆者自身も、Denoを使い続けた理由は習慣と慣れだったと書き、最近はサーバーサイドのJavaScriptを書くことにあまり意欲がなかったと付け加えている。別の種類の作業や別の規模のコードベースで同じ結果になるかどうかは、原文だけでは分からない。Node側で得たものにも代価が付いている。型の除去は型チェックを行わず、筆者の場合はパッケージを公開するのにバンドルの工程が必要になり、信頼ポリシーは自分のパッケージを許可する設定を別途必要とした。

  • 15%の測定条件。 ビルドの絶対時間、サイトの規模、測定回数、比較対象のDenoのバージョン、実行環境は原文にない。

  • Deno側の三つの問題の詳細。 該当するバージョン、再現条件、issue番号がなく、現在も再現するかどうかは確認できなかった。
