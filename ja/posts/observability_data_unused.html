集めた観測データがなぜ読まれないのか - ログ・メトリクス・トレースは別の問いに答える

計装を入れるのは一度きり、読むのは毎日だ

2026年8月23日 開発/インフラ

はじめに: ダッシュボードは40枚、障害時に開くのは3枚

観測ツールを数年運用したチームには、だいたい同じ風景がある。ダッシュボードのフォルダには画面が数十枚あり、その名前が何を指すのか分かるのは作った本人だけだ。障害が起きると、人はそのフォルダを開かない。各自が覚えている3枚ほどを開き、残りはその場でクエリを書き直す。

奇妙な話だ。データはすべて入っている。コレクタも動いているし、保管費用も毎月出ていくし、計装を入れる作業には数四半期分の工数がかかった。それなのに、いざ必要な瞬間には集めたものを使わず、その場で作り直している。

この隔たりについてよく出る診断は「ツールが貧弱だ」か「みんな怠けている」のどちらかだ。どちらも違う。これは個人の習慣の問題ではなく、収集と活用の費用構造が違うために必ず生じるずれである。計装を入れる仕事には終わりがあり、読む仕事には終わりがない。終わりがある側にだけ予算と評価指標が付けば、結果は最初から決まっている。

ちょうどこの主題の隣を突く記事が出た。OpenTelemetry の開発速度がなぜ遅いのかをリポジトリのデータで検討した OTel isn't going well, and I made a spreadsheet about it だ。その記事は標準が遅れて届く問題を扱った。この記事はその隣の欄を見る。すでに届いた標準で集め終えたデータが、なぜ開かれないのか。

この記事が扱わないこと。 特定ベンダーの課金体系や製品比較は入れていない。どの保存エンジンがログに向くかは ClickHouseがオブザーバビリティ戦争で先行する理由で、無料の組み合わせでどこまでできるかは 監視は自分で作るなで別に扱った。ここではツールを選ぶ前の段階、つまり何をなぜ集め、それをいつ開くのかだけを見る。

1. 元記事が実際に数えたもの - 詰まりはセマンティック規約ではなかった

まず、きっかけになった記事の中身を短く公正に写す。著者の Mat Duggan は OpenTelemetry の複数の言語 SDK リポジトリとセマンティック規約のリポジトリを対象に24か月分のマージ履歴を集め、比較対象として Prometheus と Envoy を並べた。数えようとしたのは二つだ。実際に誰がマージしているのか、そしてレビューがどこで止まるのか。

結果は鮮明だった。複数の言語 SDK でマージの大半を一人が処理していた。

もっとも興味深いのは、著者が自分の仮説を自ら取り下げた箇所だ。彼は詰まりがセマンティック規約の議論だろうと踏んで始めたが、実際に時間がかかっていたのは個別機能の公開 API 承認レビューだった。最も長かった例として、セマンティック規約側の PR が277.5日でレビュー115回、Python SDK 側の PR が361.1日でレビュー19回と挙げられている。レビューが足りないのではなく、承認権限を持つ人の数が少ないために列が伸びる形だ。

著者の提案は三つある。一つ目は実験段階と安定段階のあいだに期間が保証されるベータ層を置くという案で、12か月を例に挙げている。二つ目は言語ごとの保守水準を正直に公開するという案だ。すべての言語が同じ水準であるかのように見せることが利用者を誤らせる、という理由である。三つ目は安定性の約束と対応範囲と人数のうち一つは調整するしかないというものだ。三つとも守ろうとするから速度が死ぬ、という診断である。

ここまでが元記事だ。妥当な診断であり、とくに二つ目の提案は利用者の立場ですぐに値打ちがある。ただしこの分析が立っている場所は供給側だ。標準がいつ何を出すかという話である。使う側が毎日ぶつかる問題はその一階下に別にある。標準は届き、計装も入れたのに、そうして集まったデータが開かれない。

2. 三つの軸は同じものの三つの形ではない - 問う内容が違う

オブザーバビリティを紹介する文章はたいてい、ログ・メトリクス・トレースを三本柱と呼ぶ。この言い方が生む誤解が一つある。同じ事実を三つの形式で持っているように聞こえる、という点だ。そう理解すると自然に「どうせ全部あるのだから、どれを開いてもよい」という結論に行き着く。実際にはそうではない。

三つは持つものではなく問うものが違う。 各軸は特定の形の問いに答えるようデータの形が前もって決まっており、その形が別の問いを塞ぐ。

  • メトリクスは事前に決めた次元であらかじめ集計された数値だ。保存の時点で個々の事象はすでに消えている。だからいま正常か、いつから悪くなったか、平常比でどれだけ悪いかに答える
  • ログは個々の事象の記述だ。任意のフィールドを付けられ、事象一つを丸ごとたどれる。だからこのリクエストがなぜ失敗したのか、そのときどんな値が入ってきたのかに答える
  • トレースは一つのリクエストが通った経路と区間ごとの所要だ。サービス境界を越えて因果がつながっている。だから時間がどこで消えたのか、どのホップが遅いのかに答える

この違いは好みではなく費用曲線の違いである。メトリクスはトラフィックが十倍になっても時系列の本数が同じなら保存費用はほとんど変わらない。ログはトラフィックに正比例して増える。トレースは正比例したうえでサンプリングによって削られる。三つの軸の保持期間が同じであるべき理由は、はじめから存在しない。

2.1 何をいつ使うか

順序がある。Google の SRE 本は、監視が答えるべき問いを何が壊れているかとなぜかの二つに分ける。前者は症状で後者は原因であり、この区別こそシグナルを最大にしノイズを最小にする良い監視を書くうえで最も重要な分かれ目だと書かれている。その区別を三つの軸にそのまま重ねると順序が出る。

メトリクスが先だ。 何が壊れたのか、そして利用者に実際に影響が出たのかをここで判断する。同じ本が挙げた四つのゴールデンシグナル、すなわちレイテンシとトラフィックとエラーと飽和度がこの場所に来る。次がトレースだ。 影響範囲を確かめたら、どの区間で時間が消えたのかを絞る。複数のサービスが絡むリクエストでこの段を飛ばすと、結局は他人のサービスのログを漁ることになる。ログは最後だ。 区間を絞ったあとにその中の個々の事象を開く。最初からログに入ると、何を探しているのか分からないまま検索語だけを変えて彷徨うことになる。

この順序は費用の順序でもある。絞られた時間窓でだけログを開く習慣が、そのままクエリ費用の削減になる。逆にログから開く習慣は、毎回いちばん高い軸をいちばん広い範囲でなめる作業になる。

2.2 軸を間違えると静かに誤った答えが出る

軸を取り違えると、たいてい二つのうち一つが起きる。費用が跳ねるか、より悪いことに誤った答えがもっともらしく出るかだ。

費用が跳ねる側は見分けやすい。ログを集計軸に使えば毎回のクエリがスキャンになり、ダッシュボード一枚が5分ごとに一日分のログをなめ始めれば、その画面はチームでいちばん高い画面になる。メトリクスにリクエスト識別子や利用者識別子をラベルとして入れる場合も同じだ。最初はよく回り、そしてトラフィックが増えたある日、コレクタが真っ先に落ちる。

本当に危ないのはもう一方だ。トレースで件数を数えることは、どこにも警告を残さない。トレースはたいていサンプリングされて届くので、失敗件数を数えると実際よりはるかに小さい数が出るのに、画面にはその表示がない。数値が静かに間違い、その数値で判断が下される。

3. 計装は一度きり、読むのは毎日だ

ここからが本題だ。データが読まれない理由は人の勤勉さではなく、二つの仕事の性質が違うことにある。

計装を入れる仕事には終わりがある。 チケットが開き、PR が上がり、レビューが付き、マージされれば閉じる。成果として数えられ、四半期の目標に書ける。一方で読む仕事に終わりはない。昨日見たグラフを今日も見なければならず、何も起きなければ何の成果物も残らない。よく読んで事故を防いだ日は記録に残らない日だ。

組織は終わりのある仕事に資源を付ける。だから時間が経つとこういう形になる。収集量は単調に増え、読む量は人数に縛られて頭打ちになる。二つのあいだの距離が、そのまま「集めたのに読まれないデータ」だ。

この非対称はコードにもそのまま残る。計装を入れるときはレビューを受けるが、外すときは誰も見ないので、実質的に巻き戻しがない。新規サービスは既存のテンプレートを複製するが、その中には以前のチームが必要とした計装がそのまま入っている。外す根拠を作るには誰も使っていないという証拠が要るのに、その証拠を集めること自体がもう一つの仕事だ。結局追加は個人が決め、削除には合意が要るという構造が居座る。

3.1 ダッシュボードが増えるほど誰も見なくなる構造

同じ非対称が画面ではもっとひどく出る。ダッシュボードは複製ボタン一つで増え、作るのに承認が要らない。問題はその次だ。

  • 名前が説明しない。 画面の題は作った人のその日の文脈を含んでいるので、半年後の他人には開いてみないと分からない名前になる
  • 壊れたパネル一枚が画面全体の信頼を削る。 指標名が変わったりラベルが消えたりして空のグラフができると、残りのパネルの数値まで疑われる。障害中に疑わしい画面は開かれない
  • 重複が判断を遅らせる。 似た名前の画面が三枚あり、それぞれ違う時間範囲と違うフィルタが掛かっていると、どれが正しいかを確かめる時間が先に出ていく
  • 持ち主がいない。 作った人がチームを移ると、その画面は保守対象から外れるのに一覧からは外れない

この問題を正面から書いた公開文書が Google の SRE 本だ。収集はされているがどのダッシュボードにも出ておらず、どのアラートにも使われていないシグナルは削除候補という一文がそれである。同じ章では、実際の事故を捉える規則ほど単純で予測可能で信頼できるものであるべきだとも述べている。監視そのものが壊れやすく変更が難しい保守負担になりうるという警告も一緒にある。

3.2 それで実際に生き残るもの

現場で長く生き残るのはダッシュボードではなくアラートだ。理由は単純で、アラートは間違えると痛いからである。誤って鳴れば人が起き、鳴らなければ事故が大きくなる。だから手入れを受ける。ダッシュボードは間違っても誰も痛くない。ただ開かれなくなるだけだ。

だから長く生き残る画面はたいていアラートからリンクでつながった画面である。使われる経路があれば壊れたことがすぐに見つかるからだ。ランブックに埋め込まれたクエリも同じように長持ちする。使い所が文書化されれば、その瞬間に保守対象になる。逆に「いつか見るかもしれないから」作った画面は例外なく放置される。見る契機が定義されていないからだ。

新しく加わった人にはこの区別が見えないという点のほうが大きな問題だ。生きている画面と死んだ画面が同じ一覧に混ざっているので、どれを信じるべきかを人に聞いて覚えることになる。オンボーディング費用が静かに上がる場所がここだ。

4. 標準が解決することと、しないこと

ここで標準の持ち場を正確に引いておく必要がある。OpenTelemetry が実際に解決した問題と、そもそも解決対象ではない問題が混ざって語られることが多いからだ。

標準が解決したことは計装とバックエンドの結合である。以前は観測ベンダーを替えることがアプリケーションのコードを書き直すことだった。いまは計装が標準 API で書かれ、送信が共通のプロトコルで出ていくので、バックエンドの交換はおおむね設定の問題に降りてくる。ライブラリが計装を内蔵していればアプリケーションは何も書かなくてよい。言語境界を越えるコンテキストの伝播も標準の仕事だ。

標準が解決しないことはその上の階すべてである。

  • 何を計装するかはドメイン知識だ。決済の失敗をどの単位で数えるか、再試行を別個の事象と見るかは規約が決めてくれない
  • どう読むかはなおさらだ。標準はデータの形を決めるのであって、問いを決めてはくれない
  • 何を消すかは誰も決めてくれない。標準化されたデータも読まれなければただの費用だ
  • アラートの閾値とノイズ管理はサービスごとに違い、これは標準が触れる領域ではない

そのうえ「標準を導入した」という言葉の中身がチームごとに違う。公式のステータスページを見ると、同じ標準の中でも言語とシグナルの組み合わせによって成熟度が分かれる。

5. 費用 - カーディナリティ、保持期間、サンプリング

読まれないデータが無害なら、この記事はここで終わってよい。そうではない理由が費用だ。そして費用は三つの筋から入ってくる。

5.1 カーディナリティ - ラベルの追加は足し算ではなく掛け算だ

メトリクスでもっとも頻繁に破裂する場所である。Prometheus の公式な計装ガイドは、それぞれのラベルセットが RAM と CPU とディスクとネットワークの費用を持つ別個の時系列であると明記している。同じ文書が示す実務の基準は、ラベルの値の種類を10以下に保ち、それを超えるラベルはシステム全体でごく少数に限り、100 を超えるなら別の方式を検討せよというものだ。

  • ラベル三つがそれぞれ10種類の値を持つと組み合わせは千個になる。一つ足すだけで一万個だ。人の直感はこの増え方に追いつかない
  • 値の種類が事実上無限のものをラベルに入れるのが最悪だ。リクエスト識別子と利用者識別子が代表例で、こうした値は個々の事象を扱うログやトレースへ軸を移す必要がある
  • パスはとくに罠だ。/orders/{id} のようにテンプレートへ正規化しなければ、注文一件ごとに時系列ができる
  • すでに破裂したなら、ラベルを消すだけでは終わらない。古い時系列が保持期間のあいだ残り、クエリを遅いままにする

5.2 保持期間とサンプリング - 全部持つと使えない値になる

三つの軸の保持期間を同じにするのは楽だからであって、正しいからではない。メトリクスは小さく長く役に立つので、昨年の同じ月と比べるには一年分が要る。ログは大きく、たいてい数日以内に使い切られる。トレースはそれより短い。

トレースではサンプリング戦略がそのまま費用設計になる。OpenTelemetry の文書は二つの方式を分ける。ヘッドサンプリングはできるだけ早い時点で決める方式なので理解しやすく構成が単純で効率的だが、トレース全体を見ないまま決めるためエラーを含むトレースを必ず残すという保証ができない。 テールサンプリングはトレースのスパンの大部分または全部を見たうえで決めるので、エラーの有無やレイテンシのような基準で選べる。その代わり同じ文書が対価をはっきり書いている。

  • テールサンプリングは状態を持つシステムだ。決定を下すまでスパンを抱えておく必要があるためメモリとノードが要り、規模が大きくなると数十から数百のノードが必要になりうる
  • システムが変われば規則を更新し続ける必要がある。一度書いて忘れる設定ではない
  • 効果的なテールサンプリングが特定ベンダーのソリューションに縛られうる点も文書が指摘している。ベンダー中立を目的に標準を導入した組織には、これは皮肉だ
  • 実務でよく使う折衷はエラーと遅いリクエストは全部残し、残りは低い比率で残す形だ。ただしこの場合、残った標本から割合を計算してはいけない

ここでこの記事の題につながる逆説が出る。全部持つと使えない値になる。 保管量が増えればクエリが遅くなり、クエリが遅くなれば人が開かなくなる。開かないデータの保管料は出続ける。つまり「とりあえず全部集めておこう」という決定は安全側の選択に見えて、実際には費用を増やしながら活用度も一緒に下げる選択であることが多い。

6. 障害時に実際に見るもの

平常時のダッシュボードと障害時に必要なクエリは目的が違う。平常時の画面は正常範囲を確かめるのに使う。いくつかの時系列が見慣れた形をしているかだけ見ればよく、だから画面が固定でも構わない。

障害時に必要なものは正反対だ。何が変わったのかを絞る力であり、この問いは固定された画面では答えが出ない。軸を割り続けなければならないからだ。

  • エラー率をリリース版ごとに割る。出たばかりの版にだけ偏っていれば原因がすぐに絞られる
  • 経路・エンドポイントごとに割る。全体ではなく一つの経路だけが悪ければ、依存先を一つ疑う
  • アベイラビリティゾーンやノードごとに割る。片側に偏るならインフラ側だ
  • クライアント種別や顧客等級ごとに割る。特定の連携だけが失敗する場合は意外に多い
  • そしてこの割り方ができるには、その次元が前もって計装されていなければならない。 障害中に計装を足すことはできない

6.1 事前に準備できること

障害時の速さは、その瞬間の手さばきではなく普段から敷いておいた接続から出る。前もってできることははっきりある。

  • 三つの軸をつなぐ識別子を入れる。 ログの各行にトレース識別子を一緒に残せば、指標で異常を見たあと個々のリクエストへ一息で降りられる。この接続がなければ三つの軸はそれぞれ別のツールに孤立する
  • デプロイと設定変更を同じ時間軸に載せる。 リリース時刻、機能フラグの切り替え、インフラ変更がグラフ上に描かれていれば、何が変わったのかという問いの候補が画面の中で絞られる
  • 障害時に使うクエリを保存しておく。 急ごしらえのクエリはその場で消えるので、繰り返し使うものは名前を付けて保存し、ランブックとアラート本文から直接リンクを張る。アラートを受けた人が検索から始めずに済むだけで初動が数分速くなる
  • 正常の基準線を文章で書いておく。 この指標が普段いくつなのか知っている人が席にいないとき、数値だけを見て異常かどうかは判断できない
  • アラートは症状基準で張る。 原因候補ごとにアラートを付ける方式はノイズを生み、原因の一覧になかった新しい原因はどのみち捕まえられない

7. 反対側 - 標準化と自動計装が実際にもたらしたもの

ここまで読んで「だから昔のほうがよかった」に行くなら、それは誤った結論だ。標準化以前がどうだったかを一緒に並べてこそ公正になる。

標準化以前はベンダーごとに独自のエージェントと独自の SDK があった。観測ツールを替えることがアプリケーションのコードを触ることであり、その費用が事実上の錠として働いた。サービスごとに指標名とタグの規則がばらばらで、同じ会社の中でもダッシュボードを再利用できなかった。言語が違えばリクエストのコンテキストが境界で切れ、サービス間のリクエストをつなぐのが毎回手作業だった。計装を入れるにはアプリのコードを直す必要があったのもその頃だ。いまはその相当部分をライブラリと自動計装が肩代わりしている。

これは小さな改善ではない。きっかけとなった元記事の著者もベンダー中立という目標そのものは達成されたと認めて書き始めている。彼が問題にしたのは方向ではなく速度だ。コメント側でもベンダー中立が実現したという評価とともに、ログ対応の改善を求める意見や、言語によって満足度が分かれるという話が混ざって出てくる。

整理するとこうだ。標準は自分の分を果たした。 残っているのは標準がそもそも埋められない欄であり、何を計装するかといつそれを開くかはドメインを知る人が決めるべきことである。標準にその期待を掛けて失望するのは、期待の向きが間違っているのだ。

8. 導入の順序 - 問いを決めてから計装を付ける

ここまでの話を順序に直すと、一つの原則に集まる。計装が先ではなく問いが先だ。 ほとんどのチームは逆の順序でやる。エージェントを入れ、既定のダッシュボードを点け、データが届くのを確認してから、そのデータで何を見るかを後で考える。それでは埋まらない欄がそのまま残る。

  1. 答えるべき問いを文章で書く。 五つから十でよい。決済の失敗率が平常より高いか、昨日のリリース後にレイテンシが悪化したかのように、答えがはいかいいえで落ちる形がよい
  2. 問いごとに軸を割り当てる。 割合と傾向はメトリクス、区間のレイテンシはトレース、個々の失敗の理由はログだ。ここで軸が決まらない問いは、問いがまだ曖昧なのである
  3. その軸に必要な最小限の計装だけを付ける。 割る次元を前もって決め、その次元だけをラベルに入れる。後で必要になりそうという理由で入れたラベルがカーディナリティ事故の大半だ
  4. 問いごとに保存済みクエリを一つ作る。 問いと画面が一対一でくっついてはじめて画面に持ち主ができる
  5. アラートは症状基準でだけ張る。 原因候補ごとにアラートを付ければノイズが増え、ノイズが増えれば本物のアラートが埋もれる
  6. 四半期ごとに開かれなかったものを一覧にする。 どのダッシュボードにもなくどのアラートも使っていないシグナル、そして閲覧履歴のない画面が対象だ。消す前に持ち主へ知らせ、返答がなければ消す
  7. 新しい計装の PR に問いを書かせる。 この計装がどの問いに答えるのかを一行で書けないなら、その計装はまだ必要ない。この一行が後で削除判断の根拠になる

六つ目の項目が実際にはいちばん難しい。消す仕事には成果がなく危険だけがあるからだ。だからこれは個人の意志ではなく日程に組み込まれた手順であるべきだ。四半期に一度、時間を決めておき、一覧を出すところまでは自動化しておくほうがよい。

確認できなかったこと

  • 元記事の著者の集計を独立に再現していない。 上の表の数値は桁の違いを示す値としてだけ読むのが正しい
  • ダッシュボードの閲覧率に関する公開統計は見つからなかった。この記事の「誰も見ない」は測定値ではなく、費用構造から出る構造の説明である
  • 三つの軸の適正な保持期間に関する業界標準の数値はない。規制要件と事故対応の周期によって分かれる
  • ベンダー別の課金体系と費用比較は扱っていない。料金体系がよく変わり、使い方によって結果が変わる
  • 元記事が提案したベータ層が実際に採用されるかはまだ決まっていない
  • OpenTelemetry の言語別状態は2026年8月23日時点であり、リリースごとに変わる

結論: 読まれないデータは、ないデータとは違う

読まれないデータは、ないデータより悪い。ないデータは費用がゼロで、誰もそれがあると錯覚しない。読まれないデータは保管料を取りながら、備えができているという錯覚まで与える。 障害中に開いてみてはじめて必要な次元がないと知る状況が、その錯覚の結果だ。

きっかけとなった元記事は供給側の速度を語った。使う側の問題は別の場所にある。標準はデータの形を決めてくれたが問いは決めてくれず、問いなしに集めたデータは開かれない。 三つの軸が別の問いに答えると分かってしまえば、そのあとは単純だ。答えるべき問いを先に書き、その問いに合う軸を選び、その軸に必要な最小限だけを計装する。

そして四半期に一度、誰も開かなかったものを消す。増やす仕事にはすでに十分な推進力があるので、わざわざ手順にすべきなのは減らす仕事のほうだ。
