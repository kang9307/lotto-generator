neko-master Network Traffic Dashboard - How It Differs From ntopng

Not just another dashboard, but a look at when a tool like this actually becomes necessary

Jul 27, 2026 Dev & Infra

Introduction: The Old Problem of Finding the Bandwidth Culprit

When a home or small office network slows down, the frustration is always the same. You can tell it is slow, but you have no idea who is eating the pipe or why. Open the router admin page and you usually get a total sent and received figure, nothing about which device is pushing how much to where. If uploads suddenly spike at three in the morning, there is no way to tell whether that is a backup client, a cloud sync, an automatic update, or a compromised smart device.

Tools that try to fill this gap have existed for several generations. New dashboards keep appearing and drawing attention anyway, and the reason is that there is no single correct answer to this problem. Where you pull the data from completely changes what you can see, what stays invisible, and what price you pay. neko-master, which reached the top of GeekNews in July 2026, belongs to this lineage, but its collection point is different from what most people picture when they hear traffic monitor. That single difference determines almost everything about its usefulness and its limits.

This article treats as fact only what can be verified in the repository, then layers general knowledge about homelab and small-network monitoring on top, in order to work out when a tool like this is genuinely needed and when it is overkill. The goal is a decision framework rather than a feature tour. It also weighs what recording traffic actually means for privacy, and which conditions tend to block this kind of setup in ordinary residential environments.

1. What neko-master Actually Does - The Verifiable Part

Start with what can be confirmed. Everything below comes from the public repository documentation, and items that are not documented are flagged separately afterwards.

1.1 Where the Data Comes From

This is the crucial point. neko-master does not capture packets, and it does not receive flow exports either. Instead it attaches to the control API of a gateway and pulls data from it. Per the documentation, Clash and Mihomo style gateways are read over real-time WebSocket collection, Surge v5 and later over HTTP polling, and the system falls back to polling when WebSocket is unavailable. Gateways in this family expose connection lists and traffic statistics through an external controller API so that rule-based routing can be managed, and neko-master is a consumer of that output.

That one sentence determines every other characteristic. It explains why collection is cheap and setup is simple, and equally why the blind spots discussed below exist at all.

1.2 Documented Features

  • Real-time monitoring - WebSocket based collection, described as millisecond latency
  • Trend analysis - traffic movement across 30 minute, 1 hour and 24 hour windows
  • Domain analysis - per-domain traffic, associated IP addresses, connection counts
  • IP analysis - autonomous system number, geolocation, associated domains
  • Proxy node statistics - traffic distribution per node
  • Multi-backend - several gateway instances observed on one screen
  • Agent mode - an agent sits near the gateway, pulls data and reports to the panel, so the panel never connects to the gateway directly
  • Extras - PWA installation, dark mode, internationalization in English and Chinese

The item worth pausing on is agent mode. A design where the panel does not connect to the gateway directly and an agent relays instead reads as a deliberate attempt to avoid exposing the gateway control API while still watching several sites from one screen. Control APIs frequently allow configuration changes and not just reads, which makes exposing them directly a genuine hazard. Adding a relay layer is a sound call.

What is not documented deserves equal clarity. Minimum memory and CPU requirements, default data retention, and the number of connections processed per second do not appear in the documentation. One more thing. The repository states that the project provides no network access service, subscription, or cross-network connectivity, and that all data is collected from the user's own network environment. That boundary lines up precisely with the privacy discussion later on.

2. The Big Misconception - This Is Not an ntopng Replacement

2.1 What Stays Invisible

Reading a gateway control API means only connections that traversed that gateway are visible. On a home network that distinction is anything but trivial. The following traffic is structurally out of reach.

  • Traffic routed directly around the gateway - connections that rules send down a bypass never enter the statistics
  • Communication that stays inside the LAN - NAS access, local media streaming, printers, backups that never leave the building
  • Devices configured not to use the gateway - game consoles, smart televisions and a large share of connected home devices land here
  • Broadcast or media traffic on a separate path - set-top devices commonly ride a different route
  • Host resource state - system load, disk and temperature were never in scope to begin with

So the question why is our internet slow is hard to answer with this tool alone. What it answers is the narrower and more specific question of where the traffic crossing my gateway is going and in what volume. Adopt it without keeping that distinction clear and you end up staring at data that never explains the symptom.

2.2 What You Get Instead - Accurate Domain Attribution

This architecture does have one advantage that packet-based tools struggle to match, and it is arguably the whole reason the tool exists. It knows the destination domain precisely.

Most traffic today is encrypted, so inspecting packets rarely yields a reliable destination host. Older approaches read the server name exposed early in the handshake, but standards have been moving to encrypt that field as well. Packet-based tools therefore keep retreating toward IP address and port level information, and once only an IP remains, hundreds of services hiding behind a large content delivery network make meaningful attribution effectively impossible.

A rule-based gateway, by contrast, must already know the domain in order to decide which path a destination should take. Domain information is not a byproduct there; it is required input. neko-master simply consumes that already-established fact, so it shows the gateway's own routing decision rather than an inference. That is exactly why the combination of per-domain traffic, associated IPs and connection counts is feasible at all.

In short, this tool sees a narrow slice accurately. It is closer to a complement of the tools that see a wide slice fuzzily than a competitor to them.

3. Four Ways to Collect Traffic and What Each Costs

A fair comparison needs the collection method as its main axis. Sorting by where the data originates is far more useful than listing product names. What follows is general background.

Collection methodInformation gainedLoadPrivacy exposureTypical examples
Interface countersTotal bytes and packets onlyEffectively noneVery low (no content, no destination)vnStat, SNMP polling
Flow export (NetFlow, sFlow, IPFIX)Source and destination IP and port, protocol, byte and packet counts, timestampsLow to moderate (sFlow is low and predictable thanks to sampling)Moderate (who talked to whom is retained, content is not)Router export plus a collector
Packet capture and deep inspectionFull headers and payload where requiredHigh, rising steeply with line rateHigh, most sensitive when raw data is storedDeep modes of ntopng class tools
Control plane API consumptionConnection, domain and path data the gateway already holdsLow, only aggregated results are receivedModerate to high, domain history is retainedneko-master, DNS layer tools

Three points matter in that table.

  • Detail and load rise together. Seeing more means processing more, and the cost climbs sharply as the line gets faster.
  • Detail and privacy risk rise together too. Counters hold almost no personal information, while domain history is sensitive on its own.
  • Sampling is not free. Sampled approaches keep load low and predictable but raise the odds of missing rare anomalies. That is fine for bandwidth rankings and weak for catching intermittent oddities.

One more observation. Control plane consumption is unusual in pairing low load with high privacy exposure. The intuition that cheaply obtained data must be innocuous breaks down here. These two axes have to be judged separately when deciding what to deploy.

4.1 The Relationship With Pi-hole Is the Interesting One

The closest relative in that table is not ntopng but Pi-hole. Both read facts the control layer already possesses rather than observing traffic itself. There is one decisive difference, though.

  • Pi-hole knows the name but not the volume. It records exactly which domain was queried, but not how many bytes that connection moved. A single query might mean one kilobyte or ten gigabytes.
  • neko-master sees name and volume together, because the gateway counts bytes per connection. For the original bandwidth-culprit problem, that is the more direct answer.
  • Pi-hole covers far more of the network. Anything pointed at the DNS server is included, whereas neko-master is limited to traffic crossing its gateway.

In practice the most realistic setup is a two-stage one: sketch the overall shape at the DNS layer, then confirm actual volume in the gateway statistics. Attempts to solve everything with one of them usually fail.

4.2 Do Not Underestimate vnStat

Flashy dashboards make this easy to forget, but in real homelabs the tool that survives longest is usually the simplest one. Something that only reads interface counters uses almost no resources, stores essentially no personal data, and leaves years of monthly totals behind. For managing a data cap or deciding whether to upgrade a line it is sufficient, and arguably better. The key insight is that it endures not because it does less, but because it records less.

5. Homelab Reality - What Happens on Small Hardware

5.1 The Bottleneck Appears in Storage, Not the CPU

Receiving connection summaries, unlike capturing packets, does not tie CPU usage directly to line rate, so running it on a small board is generally fine. The problem lies elsewhere. Connection records are an event log, not a statistic, so they accumulate in proportion to how often connections occur rather than how fast the line is.

Modern applications and web pages open dozens of connections just to load a single view. Add connected home devices polling their servers on a schedule and you routinely get a situation where bandwidth is negligible while record counts explode. What actually strains the system is not one large file but tens of thousands of tiny connections.

5.2 Decide Retention Before You Start

The documentation keeps a 180 minute realtime window in memory and offers a separate database for aggregating ranges of seven days and beyond. That design itself concedes that long-term storage is a distinct problem. In a homelab the following order is safer.

  1. Derive the period from the purpose. Diagnosing bandwidth needs a few days. If you cannot explain why you need months of domain history, that data should not exist.
  2. Move the data path off the card. microSD handles sustained writes poorly. Relocating the database file to an external SSD or a separate volume helps both endurance and stability.
  3. Run it for a day and measure the growth. Checking the file size after 24 hours gives you a monthly estimate immediately, far more accurate than guessing.
  4. Keep only downsampled summaries long term. Daily per-domain totals instead of individual connection records preserve trend visibility while cutting both volume and privacy risk.

One thing that gets overlooked is backup. A monitoring database is easy to omit from a backup plan, but including it means copying gigabytes of sensitive history into backup storage every day. Choosing not to back it up is still a decision that has to be made explicitly.

5.3 The Dashboard Itself Is New Attack Surface

This gets neglected in homelabs in particular. A traffic dashboard is the point where the most sensitive data on the network is concentrated, and yet it often ends up exposed for convenience.

  • Keep the dashboard reachable from the internal network only, and route any external access through a VPN or an authenticated tunnel
  • Never expose the gateway control API directly to the internet - it may permit configuration changes and not just reads
  • The agent mode mentioned earlier helps here, since the panel does not attach to the gateway directly and the exposed surface shrinks
  • Even in containers, verify the port mapping scope; binding to every interface can open it outward unintentionally
  • Before enabling any export of monitoring data to an external service, check exactly what leaves the network

6. Privacy - The Weight of Recording Household Traffic

6.1 A List of Domains Says More Than You Think

Technical documentation tends to treat this lightly, but it is the heaviest factor in the adoption decision. Even without content, a list of destinations reveals a great deal about a person.

Sites about a specific medical condition, communities that expose religious or political leaning, job boards, counselling services, the server domains of dating applications - the names alone report on someone's situation. Attach timestamps and daily routines, including whether anyone was home, can be reconstructed. Worse, such records are very hard to unmake. A log that looks harmless today can carry an entirely different meaning months later during a family conflict or a dispute.

So the principle is simple. Operate only on a network you have administrative authority over. If other people share that network, tell them what is recorded. Intercepting or logging another person's communications without consent can raise legal issues in many jurisdictions, and being inside a household grants no automatic exemption. Even where child safety is the stated reason, recording covertly and agreeing on rules before using a tool produce very different outcomes.

6.2 The Minimum Data Each Purpose Requires

The practical approach is to start from the purpose and collect only the minimum it needs. Here is what common goals actually require.

PurposeMinimum data requiredDomain history neededSuggested retention
Managing a data capTotal sent and received on the lineNoMonths, totals only
Diagnosing slowdownsLive per-device usage rankingUsually noHours to days
Checking one device for odd trafficThat device's destinations and frequencyYes, for that device onlyDays
Deciding on a line upgradePeak usage trend by hourNoMonths, aggregated
Auditing what smart devices contactPer-device destination domainsYes, during the auditDelete after the audit

As the table shows, the two most common purposes need no domain history at all. Wanting to know why the connection is slow and wanting to know who visited what are entirely different questions. Failing to separate them before switching a tool on means accumulating data you do not need for a period you cannot justify.

6.3 The Geolocation Lookup Trap

A side point worth flagging. If IP geolocation or autonomous system lookups are resolved through an external lookup service, the list of destinations from your household is handed to that service. A tool self-hosted for privacy ends up leaking destination information outward, which is a genuine paradox. neko-master offering lookups via local MMDB files reads as a response to this problem, and it is a general checklist item worth verifying in any self-hosted tool.

7. Environmental Constraints Worth Checking First

7.1 The Prerequisite May Simply Not Be Met

The most realistic barrier is not a feature but a precondition. This tool requires that a Clash, Mihomo or Surge style gateway already exists with its control API enabled. Many households, in Korea and elsewhere, run whatever router the internet provider supplied, and no such gateway exists in that environment. The documented interface languages are English and Chinese, with no Korean included.

For most users, then, installing the dashboard is far smaller work than building what sits in front of it. A separate router or server has to be stood up and routing configured before this screen means anything. If you already run such a gateway it is an excellent addition; introducing a gateway purely to use this dashboard inverts the proper order of decisions.

7.2 Double NAT and Port Forwarding

Residential lines commonly end up with a provider device and a personal router stacked together. That configuration produces recurring problems.

  • Port forwarding has to be done twice - both the upstream device and the downstream router need rules before external access works
  • The upstream device may block ports outright, so no amount of downstream configuration opens them, burning hours of troubleshooting
  • Private addresses are assigned twice, splitting the device list across layers and making it unclear which screen to trust
  • Bridge mode is often used to demote the provider device and make the personal router primary, though the procedure varies by hardware and plan

The monitoring-specific lesson is that results change depending on where you measure. Measure at the downstream router and traffic from devices attached upstream is invisible. When the numbers look wrong, checking which point you are actually measuring is usually faster than suspecting the tool.

7.3 Bundled Internet and Television Lines

Bundled internet and television service is common in many markets, and it affects monitoring in two ways. First, broadcast traffic frequently travels a different path from ordinary internet traffic, so it may be missing from dashboard figures or, conversely, appear abnormally large. Interpreting statistics without separating that out leads to wrong conclusions.

Second and more practically, changing cabling or router settings carelessly can knock the television service offline. Restructuring the network to add monitoring and then discovering the living room television no longer works is a common homelab accident. Have a rollback path ready before structural changes, and prefer an observation point that leaves the existing path untouched where possible.

8. So When Should You Use It - Choosing by Situation

  • You already operate a rule-based gateway - neko-master fits well. It converts existing API output into a screen without new infrastructure, so the return on effort is high
  • You only need line totals and cap management - an interface counter tool is the right answer, and anything more complex is a net loss
  • You want to tell whether a slow server is network or disk - use something that shows host metrics alongside, because traffic alone will not reveal the cause
  • You want broad visibility into what every device contacts - a DNS layer tool has the widest coverage
  • You need deep inspection of everything crossing a segment - packet observation is required, at the cost of resources and privacy exposure
  • You want long retention across many metrics with alerting - a metrics collector and visualization stack fits, with the highest build cost and the highest ceiling

One conclusion keeps repeating. Picking the tool first and fitting the problem to it mostly fails. Write the question you want answered as a single sentence, then choose the least invasive collection method that answers it.

9. Three Questions to Ask Before Adopting

Every new dashboard looks good enough to spin up on impulse. Here are three questions that filter that impulse.

  1. Can the question I want answered be written in one sentence? Wanting to see the network better is not a question. Something like what causes the upload spike every night at eleven is. If it will not compress to one sentence, there is no reason to open the dashboard, and in two months it sits abandoned.
  2. Does this tool actually observe the point where the answer lives? Collection method equals field of view. If the culprit is a device that bypasses the gateway, a tool reading the gateway API will never find it. Ten minutes spent confirming that your subject falls inside the tool's field of view saves days.
  3. Could I live with this log leaking? A traffic dashboard concentrates the most sensitive data in the household at one point. Turning it on without deciding access control, retention and backup policy trades one problem for a larger one. If the answer is uncomfortable, drop the collection detail by one level.

Conclusion

neko-master is well built. By choosing the gateway control API as its source - an accurate data origin that already exists - it produces a sharp domain-level view without the weight of packet inspection. MIT licensing, container deployment, an agent mode that reduces gateway exposure, and the option of local geolocation files instead of external lookups all read as defensible design calls.

What matters is naming the tool correctly. This is not a network monitor but a gateway traffic dashboard. Its view being limited to traffic crossing that gateway is design, not defect, and within that narrow scope it delivers accuracy other methods struggle to reach. Understand the boundary and it is useful; misread it and you have simply added one more screen that never answers the question.

Check the preconditions and your line topology before anything else. With a gateway already in place there is ample reason to attach it; without one, starting from a volume-based tool or a DNS layer tool is far more sensible. And whichever tool you choose, the final principle holds. Observe only networks you administer, collect only the minimum the purpose requires, and keep it only as long as needed. Logging an entire day of the people you live with in order to catch a bandwidth hog is not solving the problem, only relocating it.
