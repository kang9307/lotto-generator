Paca — 인간과 AI 에이전트가 함께 쓰는 오픈소스 프로젝트 관리 도구

에이전트를 1급 팀원으로 가정해 설계한 AI 네이티브 PM — 같은 보드, 같은 스프린트, 같은 목표

2026-06-29 IT/기술

서론: "AI 협업"이라는 말이 늘 거짓말이었던 이유

2026년 6월 기준, 대부분의 프로젝트 관리 도구는 AI 기능을 달고 나왔다. Jira는 이슈를 자동 분류하는 AI 버튼을 붙였고, Notion은 글 요약 기능을 추가했으며, ClickUp은 스마트 작업 제안을 내세운다. 그러나 이들의 공통점이 있다. AI는 여전히 사람이 여는 사이드 패널 안에 있다. 에이전트는 팀원이 아니라 도구다. 물어보면 답하고, 물어보지 않으면 조용하다.

이 구조의 문제는 근본적이다. AI 에이전트가 실제로 코드를 작성하고, 이슈를 만들고, PR을 올리는 세계에서, 그 에이전트의 작업 상태는 어디에도 보이지 않는다. 스프린트 보드는 사람의 작업만 보여준다. 에이전트가 무엇을 하고 있는지는 로그를 뒤져야 안다. 사람이 에이전트의 결과물을 확인하고, 다음 작업을 할당하고, 상태를 업데이트하는 일을 여전히 수작업으로 해야 한다.

Paca는 이 구조 자체를 바꾸려는 시도다. AI 에이전트를 프로젝트 관리 도구에 붙이는 것이 아니라, 에이전트가 1급 팀원인 세계를 전제하고 처음부터 설계한 도구다. 이 글은 Paca가 무엇을 했고, 무엇이 진짜 다른지, 그리고 무엇이 아직 부족한지를 본인 시각으로 풀어낸다. 마케팅 문구를 옮기는 게 아니라, 설계 철학과 실제 작동 구조를 분석한다.

1. Paca란 무엇인가 — AI 네이티브 PM의 정의

Paca(github.com/Paca-AI/paca)는 2026년 공개된 오픈소스 셀프호스팅 프로젝트 관리 플랫폼이다. Jira·Trello·ClickUp·Monday.com의 무료 대체를 표방하며, 핵심 차별점은 단 하나다. AI 에이전트를 스크럼 팀의 동등한 팀원으로 취급한다는 것.

"AI 네이티브"라는 표현은 업계에서 남용된다. 그러나 Paca에서는 이 표현이 구체적 설계 결정으로 구현된다. 에이전트는 보드에 이름이 올라가고, 스프린트에 배정되며, 태스크를 끌어가고, 실시간으로 상태를 업데이트한다. 사람이 에이전트 대신 상태를 옮기는 작업이 없다. 에이전트가 직접 한다.

기술 스택은 프론트엔드 React+TanStack Start, 백엔드 Go+Gin, 실시간 통신 Node.js+Socket.IO, 에이전트 레이어 Python+FastAPI+OpenHands SDK, 저장소 PostgreSQL+Valkey(캐시/스트림)으로 구성된다. 라이선스는 Apache 2.0이며, 싱글 Docker Compose 명령으로 셀프호스팅이 가능하다.

2. P-A-C-A 사이클 — 에이전트가 실제로 하는 일

Paca는 팀 협업 구조를 Plan → Act → Check → Adapt 네 단계로 정의한다. 이름이 도구 이름과 같은 것은 우연이 아니다. 이 사이클이 도구의 설계 원칙이다.

2.1 Plan — 에이전트와 함께 백로그를 정제한다

기획 단계에서 에이전트는 단순 초안 작성자가 아니다. 제품 오너·비즈니스 애널리스트·AI 에이전트가 함께 BDD(행동 주도 개발) 시나리오를 작성하고 시스템 설계 문서를 구체화한다. Paca의 인앱 AI 채팅은 프로젝트 레벨에서 동작해, 자연어로 에픽·스토리·태스크를 생성하고 백로그에 직접 반영한다. 채팅창이 별도 사이드바가 아니라 보드의 맥락 안에 있다는 것이 중요하다. 에이전트가 만든 태스크가 바로 스프린트에 붙을 수 있다.

2.2 Act — 에이전트가 보드에서 태스크를 직접 끌어간다

이 단계가 Paca의 가장 극적인 차별점이다. 스프린트가 시작되면, 사람이 태스크를 집어 진행 중으로 옮기듯이, 에이전트도 자신에게 배정된 태스크를 끌어가 상태를 업데이트한다. 실시간 Socket.IO 통신이 이 업데이트를 보드에 즉시 반영한다. OpenHands 기반 에이전트는 격리 컨테이너에서 실행되어 코드를 작성하고 커밋하며 결과를 태스크에 기록한다. 사람은 에이전트의 진행 상황을 별도 대시보드가 아니라 스프린트 보드 그 자체에서 확인한다.

2.3 Check — QA 에이전트가 검증하고 사람이 리뷰한다

에이전트의 작업 결과는 자동 검증 단계를 거친다. QA 에이전트가 BDD 시나리오 기준으로 검증을 실행하고, 사람 리뷰어가 액티비티 트레일의 전후 diff를 보며 변경 내용을 확인한다. 원클릭 되돌리기가 모든 필드 변경에 붙어 있어, 에이전트가 잘못된 방향으로 작업을 진행했을 때 빠른 복구가 가능하다. 이 구조는 에이전트를 맹목적으로 신뢰하지 않는다. 에이전트 출력을 검증 가능한 아티팩트로 다루는 설계다.

2.4 Adapt — 회고가 팀 전체의 것이 된다

스프린트가 끝나면 사람과 에이전트 모두가 회고에 참여한다. 에이전트가 어떤 작업을 더 잘 처리했는지, 어디서 막혔는지가 데이터로 남는다. 이 데이터가 다음 스프린트의 태스크 배분을 조정하는 근거가 된다. 이것은 단순 로그 기록이 아니라, 에이전트와 사람이 같은 팀 피드백 루프에 들어간다는 의미다.

3. MCP 서버와 Claude Code 연동 — 에이전트 생태계의 입구

Paca가 단일 에이전트 런타임에 종속되지 않는 이유가 여기 있다. Paca는 MCP(Model Context Protocol) 서버(@paca-ai/paca-mcp)를 번들로 제공한다. MCP는 AI 에이전트가 외부 데이터 소스와 도구에 접근하는 업계 표준 프로토콜이다. 이 MCP 서버를 통해 Claude Desktop, Claude Code 등 MCP를 지원하는 AI 클라이언트가 Paca의 프로젝트·태스크·스프린트·문서·멤버 데이터에 구조적으로 접근할 수 있다.

더 구체적으로, Paca는 Claude Code용 /paca 슬래시 커맨드 세트를 제공한다. 개발자는 에디터를 떠나지 않고 자연어로 태스크를 만들고 스프린트를 관리할 수 있다. 이것은 편의 기능처럼 보이지만, 본인이 읽기엔 중요한 설계 신호다. Paca는 PM 도구가 코딩 에이전트의 워크플로와 같은 평면에 있어야 한다고 전제한다. 에이전트가 코드를 쓰는 곳에서 태스크도 관리해야 한다는 것이다.

WebAssembly 플러그인 시스템도 같은 맥락이다. 플러그인이 샌드박스된 WASM 환경에서 실행되어, 악의적이거나 잘못 작성된 플러그인이 호스트 시스템에 접근하지 못한다. 이 설계는 에이전트가 플러그인을 실행할 수 있는 환경에서 보안을 유지하는 방법이다.

4. 셀프호스팅과 데이터 소유권 — Jira가 줄 수 없는 것

Jira의 Data Center(셀프호스팅) 버전은 2024년부터 신규 고객에게 판매가 종료됐다. Atlassian의 방향은 명확하다. 클라우드 SaaS로 전부 이전하라는 것이다. 이 맥락에서 Paca의 셀프호스팅 우선 설계는 단순한 기능이 아니라 포지셔닝이다.

Paca는 처음부터 자체 인프라에서 돌리는 것을 기본 경로로 설계했다. 설치는 인터랙티브 배시 스크립트(원 커맨드 프로덕션 셋업) 또는 커스터마이즈 가능한 Docker Compose 두 가지다. PostgreSQL 외부 연결, AWS S3, AI 에이전트 비활성화(자원 절감)를 지원한다. 데이터는 사용자 인프라에 남는다.

이것이 왜 중요한가. 코드베이스·이슈·설계 문서·에이전트 대화 로그는 기업의 핵심 자산이다. AI 에이전트가 프로젝트 관리에 깊이 통합될수록, 그 에이전트가 처리하는 맥락의 민감도가 높아진다. 에이전트가 코드를 읽고 이슈를 만들고 문서를 수정하는 과정에서 생성되는 데이터가 외부 SaaS로 나가지 않는다는 보장이 필요한 팀에, 셀프호스팅은 선택이 아니라 전제 조건이다.

비용 측면도 뚜렷하다. Jira는 팀 규모에 따라 좌석당 월 $7~$14, ClickUp·Monday.com은 $9~$20 이상이다. 20인 팀이면 월 $140~$400이 나간다. Paca는 서버 운영비가 전부다. Apache 2.0 라이선스로 상업 이용도 제한 없다.

5. Jira·Notion·ClickUp 대비 구조적 차이 — 무엇이 진짜 다른가

기능 표를 나열하는 것은 의미가 없다. 핵심은 설계 전제의 차이다.

5.1 AI가 도구인가, 팀원인가

Jira AI는 이슈를 분류하고 요약한다. 에이전트가 그 이슈를 직접 끌어가 작업하고 상태를 올리는 구조가 아니다. Notion AI는 문서를 작성하지만 프로젝트 보드와 통합되지 않는다. ClickUp AI는 태스크를 제안하지만 스프린트 구조 안에서 에이전트로서 작동하지 않는다. Paca는 에이전트가 보드의 구성원이다. 이 차이는 기능 추가로 메울 수 없다. 설계 전제가 다르기 때문이다.

5.2 BDD와 시스템 설계 문서의 위치

Paca는 BDD 시나리오와 시스템 설계 문서를 프로젝트 내부에 통합한다. 에이전트가 이 문서를 컨텍스트로 읽고 태스크를 실행한다. Jira에서는 이런 문서가 Confluence에 분리되거나 외부 위키에 있다. Paca의 접근은 에이전트가 프로젝트 맥락 전체를 하나의 공간에서 참조할 수 있게 한다는 것이다. 이것은 에이전트 실행 품질에 직접 영향을 준다.

5.3 Cynefin 프레임워크와 복잡성 대응

Paca는 Cynefin·Stacey 프레임워크를 설계 철학으로 명시한다. 복잡한 작업에서 에이전트가 단일 경로를 따르는 것이 아니라 "탐색하고, 감지하고, 대응하는" 방식으로 작동한다. 이것은 단순 자동화 파이프라인과 다르다. 에이전트가 작업 중 새로운 정보를 만나면 경로를 조정할 수 있다는 전제다. 이 철학이 실제 에이전트 행동으로 얼마나 구현됐는지는 직접 실험해봐야 알 수 있다. 그러나 이런 설계 전제를 명시적으로 갖고 있다는 것 자체가 기존 PM 도구와 다르다.

6. 에이전트 협업 워크플로의 미래 — Paca가 보여주는 방향

2026년 기준, AI 에이전트는 실제 작업을 수행하기 시작했다. Claude Code, GitHub Copilot Workspace, Devin 같은 도구가 코드 작성을 넘어 이슈 해결, PR 생성, 테스트 실행까지 한다. 이 에이전트들이 생성하는 아티팩트는 팀의 작업 흐름 안에 통합되어야 한다. 그 통합점이 프로젝트 관리 도구다.

Paca는 이 방향의 선행 실험이다. 완성된 제품이라기보다는, "에이전트가 팀원인 세계에서 PM 도구는 어떤 모양이어야 하는가"라는 질문에 구체적 답을 제시하는 프로토타입에 가깝다. 1,400개 GitHub 스타와 84개 포크는 이 질문이 공명하고 있다는 신호다.

본인이 보기에 Paca가 제시하는 가장 중요한 명제는 하나다. PM 도구의 다음 단계는 AI 기능 추가가 아니라 에이전트를 위한 협업 구조 재설계다. 에이전트에게 태스크를 할당하고, 에이전트의 진행을 보드에서 보고, 에이전트의 결과를 검증하고, 에이전트와 함께 회고하는 구조. 이것은 기존 도구에 AI 버튼을 추가해서 만들 수 없다.

7. 한계와 현실적 평가 — 아직 부족한 것

Paca를 비판 없이 소개하는 것은 부정직하다. 2026년 6월 기준 명확한 한계가 있다.

7.1 초기 프로젝트의 미성숙

GitHub 별 1,400개는 관심의 신호이지 검증의 증거가 아니다. 대규모 팀이 수년간 써온 Jira의 SLA 성숙도, 지원 체계, 엣지케이스 안정성에 Paca는 아직 미치지 못한다. 실제 생산 환경에서 수십 명이 동시에 사용하는 시나리오, 수천 개의 이슈와 스프린트 이력이 쌓였을 때의 성능, 에이전트 실패 복구 시나리오는 아직 충분히 검증되지 않았다.

7.2 에이전트 실행 인프라 비용

에이전트를 실제로 돌리려면 OpenHands 컨테이너를 운영할 인프라와 LLM API 호출 비용이 발생한다. "무료"는 Paca 소프트웨어 자체의 비용이지, 에이전트 실행 비용이 없다는 뜻이 아니다. 작업 규모와 에이전트 활용 빈도에 따라 LLM API 비용이 상당할 수 있다. 이 부분을 도입 전에 명확히 계산해야 한다.

7.3 플러그인·MCP 생태계 성숙도

MCP 서버와 WebAssembly 플러그인 시스템은 Paca 생태계의 핵심이지만, 2026년 6월 현재 서드파티 플러그인과 MCP 통합의 숫자와 품질은 Jira 마켓플레이스 수천 개의 앱과 비교할 수 없다. 팀이 필요한 외부 서비스 연동(CI/CD, 모니터링, 슬랙 등)을 스스로 구축하거나 기여해야 하는 경우가 생길 수 있다.

7.4 에이전트 자율성의 실제 검증

에이전트가 "탐색하고 대응한다"는 설계 철학과, 실제로 복잡한 코드베이스에서 예상치 못한 상황을 만났을 때 올바르게 대응하는 것은 별개다. 에이전트 자율성에 대한 Paca의 주장은 OpenHands SDK의 능력에 상당 부분 의존한다. 에이전트가 실제로 어디까지 자율로 작업하고 어디서 사람의 개입이 필요한지는 팀의 실제 태스크로 직접 실험해야 안다.

8. 도입 판단을 위한 실용적 기준

Paca가 지금 적합한 팀과 아직 신중해야 할 팀을 구분해 보자.

8.1 지금 실험해볼 만한 팀

에이전트 코딩 도구(Claude Code, Copilot Workspace, Devin 등)를 이미 쓰고 있고, 에이전트의 작업을 스프린트 보드에 통합하고 싶은 팀이 1순위다. 데이터 소유권이 중요해 SaaS PM 도구에 코드베이스 맥락을 올리기 꺼리는 팀도 해당된다. 스타트업이나 소규모 팀으로 Jira 비용이 부담이고 실험적 채택에 열려 있는 팀이라면, 셀프호스팅 비용이 실질적으로 의미 있다.

8.2 신중히 접근해야 할 팀

수십 명 이상 대규모 팀의 전면 PM 도구 전환은 이르다. Jira 마켓플레이스 앱이나 Atlassian 생태계에 깊이 의존하는 팀도 마찬가지다. 에이전트 인프라 운영 역량이 없는 팀은 셋업 비용이 절감 효과를 상쇄할 수 있다.

8.3 권장 도입 패턴

기존 PM 도구를 유지하면서, 에이전트 집중 작업 흐름 하나에 Paca를 병행 실험하는 것이 안전하다. 에이전트 태스크 할당·진행 추적에서 Paca가 주는 가시성이 실제로 가치를 만드는지 먼저 확인하라. 보드에서 에이전트의 작업을 직접 보는 경험이 팀의 작업 방식을 어떻게 바꾸는지를 3-4주 스프린트 단위로 측정한 뒤 판단하라.

결론 — AI 네이티브 PM의 출발점

Paca는 완성된 Jira 대체재가 아니다. 그러나 "AI 기능이 추가된 PM 도구"와 "AI 에이전트를 위해 재설계된 PM 도구"의 차이를 가장 명확하게 구현한 오픈소스 실험이다. 2026년 6월 기준, 이 구분은 아직 얼리어답터의 관심사다. 그러나 에이전트 코딩의 속도를 보면, 1-2년 안에 이것이 PM 도구 선택의 핵심 기준이 될 가능성이 있다.

지금 Paca를 써야 할 이유는 완성도 때문이 아니다. 에이전트가 팀원인 세계에서 프로젝트 관리가 어떤 모양이어야 하는지를 실제로 경험해보기 위해서다. 그 경험이 팀의 다음 도구 선택을 더 명확하게 만들 것이다.
