What an AI Companion Needs Before It Can Act Inside a Game

The moment it reads and rewrites world state, constraints appear that conversational AI never had

Aug 25, 2026 Trends & Culture

Demos where you speak to an NPC and get an answer back are common now. Common enough that the novelty burns off fast. After a few exchanges you notice the same thing every time: that character lives inside the dialogue box, and has no relationship whatsoever with the world outside it.

Lately there are attempts to step into the next square. Not just talking, but following you, fighting, picking things up, and remembering an order to carry out later. Written as a sentence it sounds like one small step. In practice the nature of the system changes completely.

This piece does not grade any particular project. There is no comment here on how a thing feels to play, because that would require having played it. What it does instead is lay out, structurally, what has to be in place before an AI can act inside a game: what it must observe, what it must be able to execute, where it inevitably breaks, and why the old approach was shaped the way it was.

1. What is being attempted - the confirmed scope

The trigger was Varkos, a project published by an individual developer. It targets a real-time AI companion running in Skyrim, and the developer describes it as a companion that actually plays alongside you. From the published write-up, the following is confirmable.

  • Setup - the game runs on Windows while AI processing runs on a separate M4 MacBook, or on a Windows machine with roughly 12GB or more of graphics memory
  • Pipeline - speech recognition uses a kernel-optimized Qwen3-ASR 1.7b at 40 to 80 milliseconds, speech synthesis uses PocketTTS-Raven and related models at 20 to 60 milliseconds, command parsing runs through a custom module called ALE (Action Latent Encoder) at about 20 milliseconds, and response generation with validation takes 300 to 600 milliseconds
  • Action - ALE takes world JSON as input and matches it against the player request; actions are bound to grounded references pointing at real game objects and executed through native body control

The developer also states a limit plainly: models that are fast and local are not very capable at keeping the thread across multiple turns. A one to two year estimate for improvement sits alongside it. Most of what this article deals with is already contained in that single sentence.

2. The distance between speaking and moving

What separates conversational AI from acting AI is not intelligence. It is where the output lands.

Dialogue puts a sentence on the screen and ends. If the line is awkward the player asks again, and the world keeps no trace. The cost of undo is effectively zero. Action is different. The instant a door opens, an item is taken, an enemy is struck, world state changes, and that change is written to the save file. An item sold by mistake has to be bought back. An NPC killed by mistake takes the quest they were going to hand you along with them.

That asymmetry decides the entire design. A conversational system takes context in and hands sentences out. An acting system needs at least two more paths: an observation path that determines what the world currently is, and an execution path that converts model intent into a command the engine can actually run. And the moment those two attach, permissions, validation, failure handling and undo all come in with them.

AxisNPC that only talksCompanion that acts
Required inputDialogue history, character sheetPlus position, inventory, quest progress, nearby objects, combat state
Shape of outputNatural languageAn executable command and its target object
When it is wrongAsk againThe world has already changed
Need for validationTone and persona consistencyRule violations, permissions, physical feasibility
Latency toleranceGenerous within conversational rhythmIn combat, even a few hundred milliseconds is long
State persistenceSession onlyPermanently, in the save file

The last row carries the most weight. A chat model error disappears when the chat ends. An acting model error remains inside progress the player spent dozens of hours building. Studios are conservative about autonomous behavior not from lack of imagination but because of that row.

3. Two kinds of perception - watching pixels or reading state

Perceiving the game world means two entirely different things in practice, and which one a system picked determines nearly all of its performance and its ceiling.

The first is watching the screen. Read rendered pixels and infer what is there. No change to the game is needed, and in principle it attaches to anything. But whatever is off screen might as well not exist, and an object in view without a label cannot be pointed at. How many arrows remain in the inventory, whether this door is locked, are knowable only if drawn. On top of that, interpreting an image every frame competes for the same resources the game uses to render it.

The second is reading internal state. The game exports its own world as structured data and that becomes the model input directly. The world JSON in the project above is exactly this shape. Accuracy is not comparable, and more importantly the target of an action can be bound to a real object handle instead of a name string. The price is that nothing starts unless the game opens that channel.

Comparison axisScreen observationInternal state query
Game modificationNot requiredRequired - a channel must be opened
What is knowableOnly what is drawnObject properties and relations in full
Pointing at targetsDepends on coordinate guessworkStable object references
Latency and costHigh - contends with renderingLow - reads data that already exists
Patch fragilityBreaks when the UI changesBreaks when data structures change
GeneralityBroadMust be rebuilt per game

Real implementations lean to the second option for more than accuracy. To execute anything, you have to attach to the game side regardless. If a channel for issuing commands is already cut, the channel for reading state sits in the same place. A screen-only approach tends to end up as a half-system that observes but cannot act.

4. The latency budget decides the model size

A game running at 60 frames per second has about 16.7 milliseconds per frame. An AI companion does not have to answer inside that budget, but the player's sense of rhythm has been trained at frame scale. Speak to it, wait several seconds for a reply, and the character does not read as thoughtful. It reads as vacant.

So design in this field almost always reduces to a trade between size and responsiveness. A bigger model writes better lines but takes longer to reach a first token, and that stretch is experienced as silence. Running locally adds one more constraint: the model has to share graphics memory with the game. Resources the game reserved to draw frames get taken away while the companion thinks.

The fact that the project above splits game and AI onto entirely separate machines reads as evidence that this contention is real. For a personal experiment with two devices on hand it is an elegant answer. As a premise for shipped software it is not usable.

  • Split the work - resolving the structure of a command and writing a natural sentence are different difficulties. The former can finish in tens of milliseconds in a dedicated small module, leaving the language model only the latter
  • React first, speak second - if the body moves before the line arrives, identical latency feels far shorter. Human conversation works the same way; a nod precedes the sentence
  • Pre-generate - reactions to predictable moments such as combat starting or taking a hit can be produced ahead of time and cached, skipping live generation entirely
  • Separate urgent from non-urgent - an order during combat has a few hundred milliseconds; camp chatter is not late at one or two seconds. There is no reason to apply one budget everywhere

Engine vendors are moving the same way. NVIDIA's ACE Game Agent SDK presents itself as a lightweight C/C++ framework meant to sit natively inside a game, with Unreal Engine 5 plugins for speech recognition, small language models and speech synthesis. The documented lineup is nemo-conformer-ctc-120m for recognition, Qwen 3.5 4B for generation, and Chatterbox Turbo 350M for synthesis. Every one of those numbers is small, and that says where this field currently stands. The baseline is not a giant cloud model but something that fits on the device.

5. Where it breaks, and the mechanism behind each

These systems fail in roughly three ways, and all three have different causes. Grouping them by symptom guarantees you will not fix any of them.

It mentions things that are not there. A language model does not query the world; it produces the text likely to follow the context. If world state never entered that context, or was cut by a length limit, the model fills the gap with linguistic plausibility. It names a chest that is not in the cave and a key it never held. This is not lying. The structure was never one that checks facts.

It attempts actions the rules forbid. The set of actions a model can imagine is always wider than the set the game permits. Cooldowns, ownership, faction standing, physical reachability, quest gating are not inside the model. Execute without validation and you get one of two outcomes: a silent failure that leaves the companion oddly frozen, or a partial success that corrupts state.

It says lines that contradict quest progress. Dialogue comes from a context window; quest state lives in a database. There is always a gap between the two. If the snapshot is stale, or earlier information was pushed out over several turns, the character speaks like someone living one moment in the past. The developer limitation quoted earlier, about local models losing the thread across turns, is precisely this symptom.

  • Invented references → put world state in context and explicitly constrain the list of nameable entities. Filter proper nouns that fall outside it
  • Illegal actions → treat model output as intent only and validate against game rules before execution. When it fails, emit a refusal line rather than an action
  • State mismatch → re-read state immediately before each utterance and order the context so that current state outranks older dialogue history

The three fixes share a shape. None of them make the model smarter; all of them build a fence outside the model. This is not specific to games but recurs across tool-using AI generally. The same problem seen from the development-tooling side was covered in making an agent measure the engine instead of guessing at it.

6. What old NPC design was actually buying

Finite state machines and dialogue trees are old. Being old, they get talked about as leftovers from a time before the technology was good enough. That is half right. The structure was buying something, and the purchase still holds value.

A finite state machine describes behavior as a set of states and transition conditions. Compute cost is near zero and, more importantly, the space of possibilities is finite. Finite brings four things with it.

  • Exhaustive checking is possible - with finite states and transitions, unreachable states and missing transitions can be found mechanically
  • Voice actors can record ahead - because dialogue is a finite set of strings. Generation destroys that premise outright
  • Translators can work ahead - same reason. Localization completes at build time, and so does its quality pass
  • Bugs are reproducible - identical input yields identical result, so regression testing holds. Without that premise, QA chases reports that cannot be reproduced

There was a price, of course. It is well documented that state counts explode and reuse becomes difficult as soon as behavior grows slightly complex. Behavior trees emerged from that. As an introduction to behavior trees lays out, they generalize state machines while gaining modularity, and they keep predictability intact. Goal-oriented action planning went a step further, letting designers declare a goal while the agent assembles the action sequence itself. Even there, the raw material is a finite list the designer defined in advance.

In other words, the history of game AI is a history of increasing autonomy, but always by expanding within finite materials. What is new about the generative approach is not autonomy itself. It is that the list of materials became unbounded.

7. Freedom and control - neither comes free

A common misreading sits here: the picture where generative NPCs replace the old approach. Looking at actual implementations, that is not the shape. They are converging on a compromise where dialogue is generated while actions are chosen from a finite list.

The reason is that the four items from the previous section have not gone anywhere. Moving dialogue to generation means giving up pre-recording and pre-translation, but synthesis and runtime translation can partly cover that loss. Moving actions to generation, by contrast, collapses the premise of regression testing. A system with no guarantee that the same situation yields the same result cannot reproduce a bug report, and what cannot be reproduced cannot be fixed. There is no obvious substitute for that.

So the working boundary tends to be drawn right there. The model works at the layer that chooses what to do, and predefined actions handle the doing. The SDK mentioned above foregrounding function calling as a small-model capability comes from the same logic: speak freely, but execute only from a defined list of functions.

This compromise has a price too. If the action list is finite, so is what the companion can do. When a player issues a creative instruction outside the list, the system understands it and still cannot perform it. The boundary of capability becomes ragged in a the words land but the action does not way, and that mismatch amplifies disappointment. A companion that is uniformly useless is easier to work with than one where some things work, some do not, and the rule is unknowable.

8. Conditions for a modding ecosystem

A large share of these experiments arrive as mods for existing games, because attaching to a world whose content is already finished is far faster than building a new one. But games that can host mods and games that cannot are clearly separated.

  • Is there an extension channel - only games with a vendor-provided creation toolset or scripting layer are at the starting line. Forcing a way into games without one is not something this article covers
  • Does the world have addresses - objects need stable identifiers before an action can point at them. Without that you fall back to screen observation and inherit every limitation in section 3
  • Does it survive the patch cycle - every game update shakes the attachment points. What is built on an official extension layer generally holds; what leans on internal structure needs realigning each time
  • Is distribution tractable - shipping a local model alongside pushes download size into gigabytes and drags a hardware floor along with it. That is a different animal from mods made of text and scripts
  • Does it coexist with other mods - mods touching the same points conflict. An AI companion touches dialogue, combat and inventory at once, so its conflict surface is unusually wide

One more thing belongs on top of that list. Complying with a game's terms of service and copyright policy is the user's responsibility. Some games actively encourage mods; others prohibit them explicitly. In games played with other people, modifying the client is frequently a sanctionable act on its own. This article describes no method for circumventing any protection, and whether something can be attached should be read as a question of what the game permits, not of what is technically possible.

9. Cost and privacy - where the conversation goes

Where to run the model looks like a performance question, but it is really a question of where money and information flow.

An external API makes the performance problem mostly disappear. Two others appear instead. First, cost scales with hours played. A game sells once, but a talkative companion bills for as long as it is switched on, and unless someone is designated to pay that bill the structure does not last. Second, the conversation leaves the machine. With always-on voice input, what leaves is not only in-game dialogue. Whatever is audible in the room while the microphone is live goes with it.

  • External API - strong performance, light distribution. In exchange there is a per-hour cost, and when the service shuts down the companion goes with it
  • Local model - nothing leaves, nothing is billed. In exchange a hardware floor appears, the model competes with the game for resources, and redistribution terms for the weights have to be checked
  • Mixed - speech recognition and short reactions local, long narrative sent out. Practical, but it leaves the problem that the line between what leaves and what stays is invisible to the player
  • Disclosure - whichever route is taken, microphone use and transmission belong somewhere visible, not buried in a settings submenu. Games get left running in rooms with other people in them

The project above choosing a local setup reads as the outcome of this same calculation. Running locally gives up performance and in return settles both billing and egress at once. Much of the reason on-device small models are becoming the baseline in this field is that practical one. The same current seen from the development-tooling side is covered in the piece on local LLM agent tooling.

What could not be confirmed

Here are the items left unjudged because they could not be verified. None of the following appears anywhere in the body as fact.

  • The project was not run directly. Actual response quality, how natural the conversation feels, and whether it is fun as a companion are therefore not evaluated here
  • The published latency figures do not come with the scene, the load conditions, or the number of runs they were measured over
  • Whether source or binaries are publicly available, the licensing terms, and any distribution plan could not be confirmed
  • On the engine vendor SDK side, the concrete format for passing game state to an agent and its graphics memory requirements are not stated in the public documentation
  • Which rule set an action validator actually uses, and what happens to an action that fails validation, is not described in detail by either source

12. How far this has actually come

To sum up: the pipeline works. Taking speech in, extracting intent, producing a sentence and pushing it back out as sound, on-device, inside a window that does not wreck conversational rhythm, is something several implementations now demonstrate together. That engine vendors have begun shipping this as an SDK is another signal that the experimental phase has passed.

What has not arrived is persistence. Holding context across many turns, keeping a personality stable through a long session, and producing safe actions without a validator standing behind them. The developer limitation quoted earlier names the first of those precisely, and it is not the kind of thing prompt tuning resolves. It is closer to a problem that unlocks when the model size you can run on-device rises.

So when the next announcement of this kind appears, the question is not how smart is it. It is three questions. How does it observe the world, what filters an action before execution, and is it the same character several turns later. A demo that has not filled those three can be impressive and still not be a companion yet. The same current can be followed through where AI actually lands across the game development pipeline, and through the experiment of designing bots as citizens.
