韩文排序为何与预期不同 - 区域设置与排序规则

同一份列表在不同工具里排出不同顺序的分叉点，以及如何固定在一处

2026年8月4日 IT/技术

引言：数据只有一份，顺序却有三种

在管理后台看会员名单。把同一份名单导出成 CSV 打开。再用 ls 查看服务器上的附件。三处的顺序完全不同，可原始数据只有一份。

遇到这种情况，多数人会怀疑两件事：编码坏了，或者排序代码有 bug。实际上两者都不是的情况要多得多。三个工具是各自正确地应用了不同的排序规则，没有一个出故障。出故障的是「排序在哪里做结果都一样」这个假设。

先给结论。如果顺序是产品需求，就别把它交给 shell 环境变量或数据库服务器配置，而要在应用代码里以排序器的形式明确固定下来。下面逐条说明原因，以及不这么做时会在哪里、以什么方式产生偏差。

字符被拆成字母这一现象本身，以及它在文件系统、检索和长度校验上破坏了什么，已在韩文被拆成字母的瞬间 - NFC 与 NFD中讲过。本文只谈顺序。字符真的显示成乱码属于定位韩文乱码发生的那一点，压缩包内文件名被破坏属于zip 里的文件名在哪一步坏掉。用正则匹配韩文时的坑在韩文正则陷阱里。

从这张表里要读出三点。

  • 最大的差别是韩文与拉丁字母的先后。ICU 的韩语排序规则把韩文放在前面，其余全部把拉丁字母放在前面。只比两个字符就一目了然：韩语排序器里 compare('가', 'a') 为负，而英语、日语、中文排序器都返回正值。
  • 以下划线开头的 _temp 位置会跳。码位顺序里 _ 是 U+005F，夹在大写与小写之间；排序规则里它被当作标点，跑到最前面。如果你的约定用下划线前缀表示临时文件或系统条目，这个差别会直接显示在界面上。
  • 六行里有五行 10번째 排在 1번째 前面。无论怎么调区域设置都修不好，因为数值比较是与区域无关的另一条轴。

2. 码位顺序 - 韩文为什么「大体上」是对的

码位排序把字符看作数字比大小，跟人类的排列习惯毫无关系。Unicode 排序算法的标准文档 UTS #10 开篇就写死了这一点：

字符在 Unicode 代码图表中的位置并不规定它们的排序顺序。

可在韩文上这两者却吻合得出奇地好。好到什么程度？把韩文音节区 U+AC00 到 U+D7A3 的全部 11,172 个字符列出来，分别按码位顺序和韩语排序规则排序，再逐位比对，没有一处不一致。3,000 条双音节组合的抽样结果也一样。

这不是巧合。韩文音节码位按 0xAC00 + (初声 × 588) + (中声 × 28) + 终声 这个公式排布，而初声、中声、终声的枚举顺序与字典顺序一致。有无收音也遵循同一结构。用韩语排序器验证，가 < 각、간 < 갈、강 < 개 给出的答案都与码位顺序相同。

由此可以下一个明确判断：只要输入全是完整音节且统一为组合形式，码位排序就是通往字典顺序的精确捷径。它同时也是最快的。问题在于，谁来保证这个前提。

3. 崩掉的地方 - 当别的东西混进来

前提被打破有三条路径。

3.1 分解形韩文混进来

组合形的 가 是 U+AC00 一个字符，分解形的 가 是 U+1100 和 U+1161 两个字符。按码位看，0x1100 远小于 0xAC00，所以分解形必定排在组合形之前。列表里一旦混入分解形，这些条目就会全部涌到前面。

输入：가방(组合形) 나무(组合形) 다리(组合形)
      각목(分解形) 남산(分解形) 대구(分解形)

码位排序     → 각목 | 남산 | 대구 | 가방 | 나무 | 다리
韩语排序器   → 가방 | 각목 | 나무 | 남산 | 다리 | 대구

码位排序那一行与字典顺序毫无关系。把同样的输入交给 SQLite 默认的 ORDER BY，或用 LC_ALL=C sort 跑一遍，分解形照样排在前面。这不是某种语言的问题，而是码位比较这条规则本身的性质。

分解形为什么会进入列表、在哪些边界上形态会改变，都整理在NFC·NFD 那篇里。这里要补的是排序侧的一个事实：ICU 排序器认为这两种形态相等。比较组合形 가방 与分解形 가방 会返回 0，也就是说排序不会有问题。可把同样这两个值放进 Set，大小却是 2。

排序能做到而去重做不到的那段区间
排序器把两种形态当作等价，但 === 和基于哈希的数据结构不这么看。「排完序它们挨在一起，那重复应该也去掉了吧」这个推断就在这里悄悄失效。去重不是排序器的活，是规范化的活。

3.2 字母与符号混进来

兼容字母 ㅏ 是 U+314F，位于完整音节区之前，按码位排序会排在 가 前面。而韩语排序器把这个字符送到列表最末尾。如果界面上用单个韩文字母作标签或索引键，两种方式的结果正好相反。

表情符号也一样。它们码位很大，按码位排序落在末尾，而韩语排序器却把它们放在数字之前。在用户昵称这类什么都可能填进来的字段上，这个差别相当显眼。

3.3 大小写混在一起

码位排序会把大写全部聚到前面：Apple、Banana 之后才是 apple、zebra，怎么看都不像字母顺序。排序规则会把相同拼写放在一起，只在最后一级才考虑大小写。JavaScript 里用 sensitivity 选择这一级。

设置区分什么apple vs Apple
base仅基本字母0（相等）
accent基本字母 + 变音符号0（相等）
case基本字母 + 大小写不同
variant（默认）全部-1（apple 在前）
caseFirst: 'upper'大写优先+1（Apple 在前）

SQLite 的 NOCASE 远不及此。官方文档明确写着只折叠 26 个 ASCII 字母，并说明 SQLite 因为表体积的关系不做完整的 UTF 大小写折叠。实际上 'A' = 'a' COLLATE NOCASE 为真，而 'Ä' = 'ä' COLLATE NOCASE 为假。用 NOCASE 做姓名检索再灌入多语言数据，就会留下一处静默的漏洞。

4. 区域设置能改什么，不能改什么

「把区域设置调成韩语就会得到韩语顺序」这个期待只对了一半。区域名称只是指向某套规则的标签，规则本身归解释这个名称的库所有。所以同一个名称在不同环境里会给出不同顺序。

以下是在测量环境（见后文「测量环境与复现」一节）中确认到的：

  • LC_ALL=ko_KR.UTF-8 sort 与 LC_ALL=en_US.UTF-8 sort 的输出一个字符都不差。指定韩语区域并不等于挂上了韩语排序规则。
  • Python 的 locale.strxfrm 在 ko_KR.UTF-8、en_US.UTF-8、Korean_Korea.949 三种区域下给出相同结果。
  • 同一台机器上只有 Intl.Collator('ko') 把韩文排在拉丁字母之前。ICU 用的是另一张规则表。
  • locale.setlocale(locale.LC_COLLATE, '') 会跟随机器自身的系统设置；在测量机器上它解析成了 Korean_Korea.949。开发笔记本和生产服务器的系统区域不同，同一份代码就会给出不同顺序。

UTS #10 的说明正好点中这个局面。默认排序表 DUCET 无法独自满足所有语言，规范因此指出「对大多数语言而言，要符合用户预期都需要一定程度的定制（tailoring）」。ICU 带着这些定制表，而 C 库的实现可能有、也可能没有。

Python 官方文档还补了一条警告：区域设置是进程全局的属性，而 setlocale() 在多数系统上不是线程安全的。因此在 Web 服务器里按请求切换区域再排序的设计，结构上就用不了。

5. 数字排序 - 文件2 与 文件10

字符串比较走到 파일2 和 파일10 的数字位，拿 2 和 1 相比，因为 1 更小就把 파일10 放前面。这是规则如实运作的结果，换区域设置也不会变。

输入：파일1.txt 파일2.txt 파일10.txt 파일20.txt 파일3.txt 파일100.txt

默认排序     → 파일1 · 파일10 · 파일100 · 파일2 · 파일20 · 파일3
开启数值比较 → 파일1 · 파일2 · 파일3 · 파일10 · 파일20 · 파일100

各个工具都有对应的修法。

  • JavaScript：new Intl.Collator('ko', { numeric: true })
  • GNU sort：sort -V（版本排序），上面这份列表能直接排出预期顺序
  • Python：把数字块转成 int 后作为排序键
import re, unicodedata

def natural_key(s):
    s = unicodedata.normalize('NFC', s)
    return [int(t) if t.isdigit() else t
            for t in re.split(r'(\d+)', s)]

sorted(names, key=natural_key)
开启数值比较带来的坑 - 补零会变成并列
在 numeric: true 下比较 A-007 和 A-7，结果是 0，也就是并列，因为按数值解释两者都是 7。如果补零时代的数据和不补零的数据混在同一张表里，顺序就会每次渲染都晃动。要么统一位数，要么在后面再加一个唯一的辅助排序键。

6. 按工具逐个固定

6.1 Shell - 别信区域设置，钉死它

如果脚本产生的顺序会留在产物里（校验和清单、manifest、比对用 dump 等），就必须显式固定区域设置。方向只有两个。

# 1) 目的是可复现的字节顺序 - 任何机器上结果都一样
LC_ALL=C sort names.txt

# 2) 目的是给人看的顺序 - 别在 shell 里做，交出去
#    （区域名称相同，机器之间规则也可能不同）

判断是这样的：如果是机器要比对的列表，用 LC_ALL=C 钉死；如果是给人读的列表，干脆别在 shell 里排序。最糟的状态是含糊地交给系统默认值。开发机与 CI 容器的 LANG 不同，同一个脚本就会产出不同的文件。

6.2 JavaScript - 建好排序器并复用

// 建一次，反复使用
const collator = new Intl.Collator('ko', {
  numeric: true,          // 파일2 < 파일10
  sensitivity: 'variant', // 区分大小写与变音符号
  caseFirst: 'false'      // 区域默认值
});

names.sort(collator.compare);

有三点要记住。

  • 复用排序器实例。每次比较都调 a.localeCompare(b, 'ko')，就会每次重新组装一个排序器。排序 2 万条时，localeCompare 的做法比复用排序器慢两倍以上。
  • 不要用 usage: 'search' 排序。MDN 写得很死：「把 search 用于排序／定序是不恰当的。」实测比较 가 和 까，sort 与 search 返回的符号相反。search 的返回值只该看是否为 0。
  • 没法预先提取排序键。JavaScript 没有对应 ICU 排序键提取的公开 API，Python 的 strxfrm 那套做法用不上。所以若性能吃紧，复用排序器几乎是唯一的手段。

6.3 Python - 在标准库与 ICU 之间

只用标准库的话，locale 模块就是全部。strxfrm 把字符串转成可比较的形式，文档建议在「同一字符串被反复比较时，例如对一串字符串排序时」使用它。

import locale
locale.setlocale(locale.LC_COLLATE, 'ko_KR.UTF-8')
result = sorted(names, key=locale.strxfrm)

不过如前所述，这种做法是把结果交给机器的 C 库，而且不是线程安全的。需要 ICU 规则时，接上 PyICU 才是正解。若连这也做不到，实务上行得通的折中是自己造一个规范化 + 自然排序键。它不依赖区域设置，在任何机器上都给出相同结果。

import re, unicodedata

def sort_key(s):
    s = unicodedata.normalize('NFC', s)          # 分解形转为组合形
    parts = re.split(r'(\d+)', s)
    return [(1, int(t), '') if t.isdigit() else (0, 0, t) for t in parts]

对只含完整韩文音节的列表，光靠这个键就能排出准确的字典顺序。第 2 节的全量比对结果就是依据。

7. 数据库 - COLLATE 写在哪里决定了索引

在数据库里修顺序看似有两种办法：给查询加 COLLATE，或写进列定义。结果一样，代价完全不同。

在 SQLite 里建一个名字列、加上索引再看执行计划，差别一目了然。

查询执行计划
ORDER BY nameSCAN t USING COVERING INDEX idx_name
ORDER BY name COLLATE NFCSCAN t
USE TEMP B-TREE FOR ORDER BY
WHERE name = ?SEARCH t USING COVERING INDEX idx_name (name=?)
WHERE name = ? COLLATE NFCSCAN t
列定义写 COLLATE NFC + 索引SCAN t USING COVERING INDEX idx（顺序也正常）

给查询加上 COLLATE 的那一刻，排序用的索引和检索用的索引会一起死掉。索引是按默认排序规则建立的，要求另一套规则它就用不上，于是每次排序都要建临时 B 树，等值比较则退化成全表扫描。

该修的地方是表结构。

-- SQLite：把排序规则钉在列上，再在其上建索引
CREATE TABLE members (name TEXT COLLATE NOCASE);
CREATE INDEX idx_members_name ON members(name);

-- PostgreSQL：用 ICU 提供程序创建排序规则并挂到列上
CREATE COLLATION ko_icu (provider = icu, locale = 'ko-KR');
CREATE TABLE members (name text COLLATE ko_icu);

-- MySQL 8.x：在列上指定 utf8mb4 系的排序规则
CREATE TABLE members (
  name VARCHAR(100) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_as_cs
);

各产品需要知道的要点。

  • SQLite：内置排序规则只有 BINARY、NOCASE、RTRIM 三种。默认的 BINARY 用 memcmp() 比较，也就是码位顺序。需要韩语规则就得从应用侧注册排序规则。
  • PostgreSQL：有 libc 和 ICU 两种提供程序，ICU 排序规则与编码无关，同名的在一个数据库里只有一个。想把顺序稳定地固定下来，选 ICU 更好。
  • MySQL 8.x：Unicode 排序规则清单里没有韩语专用的排序规则。日语、中文、俄语、德语等都在，韩语却没有列出。默认的 utf8mb4_0900_ai_ci 基于 UCA 9.0.0 / CLDR v30，不区分变音符号和大小写。若姓名顺序需要严格处理，就用 _as_cs 系。
排序规则一变，索引可能损坏
PostgreSQL 文档写得很直白：「排序规则定义的变化可能导致索引损坏及其他问题，因为数据库系统依赖已存储对象具有特定的排序顺序。」并补充说这会在把操作系统升级到新的主版本、或迁移到链接了更新版 ICU 的服务器二进制时真实发生。应对办法是对受影响的对象执行 REINDEX，再运行 ALTER COLLATION ... REFRESH VERSION——不过文档自己也说明，这条命令并不会真去检查是否全部正确重建了。

8. 并列 - 排序结束了顺序却没定下来

排序规则可以判定两个值「相等」。那一刻，这些条目的最终顺序就交给了排序算法。JavaScript 的 Array.prototype.sort 是稳定排序，所以输入顺序会被原样保留。听上去是好性质，反过来看却是这个意思：

开启忽略标点选项的状态 (compare('한-국', '한국') === 0)

输入 [한-국, 한국, 한.국]  →  输出 한-국 | 한국 | 한.국
输入 [한.국, 한국, 한-국]  →  输出 한.국 | 한국 | 한-국

数据相同，进来的顺序不同，屏幕上的顺序就不同。而且产生并列的路径不止排序规则一条。

  • 设为 sensitivity: 'base' 或 'accent'，只有大小写不同的值会并列
  • 设为 ignorePunctuation: true，只有连字符、句点不同的值会并列
  • 设为 numeric: true，只有补零不同的值会并列
  • 数据库里只写 ORDER BY name，同名同姓会并列

解法只有一个：给排序键再加一个唯一值。数据库里就是 ORDER BY name, id，应用侧则是比较函数返回 0 时再用 ID 比一次。

这个并列问题在把列表切成分页时会破坏什么，另见偏移量分页在结构上做不到的事。排序键不唯一时，条目会在分页边界处消失或重复出现。

9. 性能 - 各种做法慢多少

对 2 万条韩文字符串排序的耗时，跑五次取中位数。

方式耗时相对默认
默认 sort()（码位）10.1 ms1.0 倍
复用 Intl.Collator 实例27.0 ms2.7 倍
每次调用 a.localeCompare(b, 'ko')59.5 ms5.9 倍

该怎么读。

  • 排序规则的代价是 2.7 倍。2 万条 27 毫秒，在多数界面上不构成争论。「怕慢所以保持码位排序」这个判断在这个量级上依据很弱。
  • 真正的损失是在比较函数里直接调 localeCompare。把排序器提到外面建一次，一行就能省掉一半，结果完全相同。
  • 如果每次请求都要排几十万条，那问题不在排序方式而在排序的位置，应该下沉到数据库索引。

10. 判断 - 排序规则放在应用层

把上面的事实汇成一条判断标准，就是下表。

场景固定在哪里理由
展示给用户的列表应用层的显式排序器
（Intl.Collator·ICU）		与环境无关，顺序一致。选项留在代码里，可以被评审
大列表的分页查询数据库列排序规则 + 索引查询级 COLLATE 会杀死索引。同时配一个唯一的决胜键
脚本与 CI 产物显式写 LC_ALL=C目的是可复现，不是给人读的顺序
去重与键比较NFC 规范化排序器只判定等价，不会合并值
文件名与路径先规范化再比较混入分解形会让码位排序崩掉

「放在应用层」这条建议的依据不是偏好，而是以下四点。

  1. 同一个区域名称并不保证同一个顺序。在同一台机器上，ko_KR.UTF-8 与 en_US.UTF-8 的 shell 排序结果相同，而同一台机器上的 ICU 韩语排序器给出了完全不同的顺序。环境变量不足以充当固定顺序的手段。
  2. 区域设置是进程全局的，且非线程安全。需要按请求切换规则的服务器在结构上无法使用它。
  3. 数据库排序规则会被基础设施变更牵着走。PostgreSQL 文档警告，操作系统或 ICU 版本升级时可能需要重建索引。这等于把顺序规则绑在了基础设施的排期上。
  4. 选项会留在代码里。numeric、sensitivity、caseFirst 是怎么设的，源码里看得见。散落在服务器环境变量里的话，没人能解释界面顺序为什么是那样。

这并不是说不要用数据库排序。要把几万条切成分页展示，排序就该由索引来做。即便如此，也要把排序规则钉在列定义上，索引建在它之上。给查询加 COLLATE 是只拿对结果、代价却一分不少的选择。

12. 未能验证的部分

以下内容本文没有实测。凡是以官方文档为依据的地方都已标明。

  • Linux glibc 环境下 sort 的区域行为。上面的 shell 测量来自 Windows 的 MSYS2 运行时。glibc 可能使用不同的排序表，不应期待相同结果。如果服务器上 shell 排序的输出会进入产物，必须在那台服务器上直接确认。
  • PyICU 的实际输出。测量环境未安装，只测了 Python 标准库 locale 模块的行为。
  • PostgreSQL、MySQL 服务器的实际排序结果。本文的数据库实测是用 SQLite 做的，关于 PostgreSQL 和 MySQL 的叙述依据各自的官方文档。索引与排序规则的关系在各产品上细节不同，落地前请在目标版本上直接确认执行计划。
  • macOS 文件系统存储名称形态的细节。本文只讨论分解形混入列表时排序会变成什么样，哪个文件系统在何时以何种形态存储属于NFC·NFD 那篇的范围。
  • ICU 版本升级时顺序会变动多少。只在一个版本（ICU 77.1）上做了测量。排序规则数据在版本之间会被修订，若顺序属于契约的一部分，固定 ICU 版本并配上回归测试更稳妥。

13. 常见问题

只用完整韩文音节的话，直接用默认排序行吗？

行。11,172 个字符的全量比对里，码位顺序与韩语排序规则顺序完全一致。但代码里得有东西撑住「只有完整韩文音节」这个前提。一旦列表里混进用户输入、上传的文件名和外部 API 响应，这个前提很快就守不住。

Intl.Collator 在各浏览器里结果不会不同吗？

内置的 ICU、CLDR 版本不同，细节就可能不同。所以如果某个界面要求服务端和客户端顺序一致，就只在其中一侧排序。由服务端排好返回、客户端原样渲染，抖动更小。

明明是韩语，为什么韩文跑到后面去了？

多半是排序器的区域不是 ko。只有 ICU 的韩语排序规则把韩文放在拉丁字母之前，英语、日语、中文区域都是拉丁字母在先。如果直接沿用浏览器的语言设置，顺序会因用户而异。

ORDER BY 的结果和界面顺序不一致，该改哪一边？

别去凑合两边，而要把排序的地方减到一处。如果数据库排好的数组前端又排了一遍，只要两套规则不同，结果就会一直对不上。需要分页时统一到数据库侧，并对齐列的排序规则更好。

规范化应该在什么时候做？

存储前做一次最便宜。每次读取都规范化会用不上索引；只在比较时规范化，存储里两种形态会不断堆积。如果已经存了混杂的数据，用一次迁移清理干净，之后在输入路径上拦住。
