들어가며: 보안은 선택이 아닌 필수

서버 보안은 단일 솔루션이 아닌 다층 방어(Defense in Depth) 전략이 필요합니다. 이번 마지막 편에서는 Linux 서버 보안 강화의 핵심을 다룹니다.

이 글의 명령과 설정은 OpenSSH·Linux-PAM·UFW·DNF Automatic·Greenbone 의 공식 문서를 기준으로 한다(2026-09-29 기준). 배포판마다 다른 부분(패키지 이름·서비스 이름·로그 위치)은 본문에 표시했다. 원격 서버에서 SSH·방화벽·PAM 을 고칠 때는 지금 접속 중인 세션을 닫지 않은 채 새 터미널로 시험하는 것이 모든 절차의 전제다. 또한 이 글의 명령은 자기 소유이거나 관리 권한이 있는 서버에서만 사용한다.

1. 시스템 하드닝 기초

1.1 불필요한 서비스 비활성화

# 실행 중인 서비스 확인
systemctl list-units --type=service --state=running

# 불필요한 서비스 비활성화 (설치돼 있지 않은 서비스면 오류가 나는 것이 정상)
sudo systemctl disable --now cups
sudo systemctl disable --now avahi-daemon
sudo systemctl disable --now bluetooth

# 부팅 시 시작 서비스 확인
systemctl list-unit-files --type=service --state=enabled

운영 서버에서는 서비스를 끄기 전에 그 서비스에 의존하는 것이 없는지 systemctl list-dependencies --reverse 서비스이름 등으로 먼저 확인한다.

1.2 보안 업데이트

# Ubuntu/Debian
sudo apt update && sudo apt upgrade -y
sudo apt install unattended-upgrades
sudo dpkg-reconfigure unattended-upgrades

# RHEL 계열 (RHEL, Rocky Linux, AlmaLinux)
sudo dnf update -y
sudo dnf install dnf-automatic
# dnf-automatic.timer 는 automatic.conf 를 따르고 apply_updates 기본값이 False 라 설치하지 않는다
sudo systemctl enable --now dnf-automatic-install.timer

RHEL 계열에서 dnf-automatic.timer 는 automatic.conf 설정을 그대로 따르고, apply_updates 기본값은 False 다. 그래서 이 타이머만 켜면 업데이트를 내려받거나 알리기만 하고 설치하지 않는다. 설치까지 자동화하려면 dnf-automatic-install.timer 를 쓴다(DNF Automatic 문서). 이 글의 이전 판은 앞의 타이머를 켜라고 적어 실제로는 설치되지 않았다.

1.3 GRUB 보안

# Debian/Ubuntu 기준. 편집 전에 백업하고, 콘솔 접근 수단을 확보해 둔다
sudo cp -a /etc/grub.d/40_custom /root/40_custom.bak

# GRUB 비밀번호 해시 생성
sudo grub-mkpasswd-pbkdf2
# 해시값 복사

# /etc/grub.d/40_custom 편집
set superusers="admin"
password_pbkdf2 admin grub.pbkdf2.sha512...

# 설정 적용 (Debian/Ubuntu)
sudo update-grub

GRUB 비밀번호는 부팅 메뉴 편집을 막는 장치라, 잘못 넣으면 부팅 메뉴를 쓸 수 없게 될 수 있다. 40_custom 백업과 콘솔(가상 머신 콘솔·IPMI 등) 접근 수단을 확보한 뒤에 진행한다. RHEL 계열은 명령이 달라 이 글에서는 다루지 않는다.

2. 사용자 보안

2.1 비밀번호 정책

# /etc/login.defs
PASS_MAX_DAYS   90    # 최대 사용 기간
PASS_MIN_DAYS   7     # 최소 사용 기간
PASS_WARN_AGE   14    # 만료 경고

# PAM 비밀번호 복잡성 (Debian/Ubuntu: /etc/pam.d/common-password)
password requisite pam_pwquality.so retry=3 minlen=12 dcredit=-1 ucredit=-1 ocredit=-1 lcredit=-1

# 기존 사용자에게 적용
sudo chage -M 90 -m 7 -W 14 username

RHEL 계열에는 /etc/pam.d/common-password 가 없다. 같은 옵션(minlen 등)을 pwquality 설정에 두며 정확한 위치는 배포판 문서를 따른다. PAM 파일을 고칠 때는 지금 열린 root 세션을 닫지 말고, 다른 터미널에서 passwd 로 시험한다.

2.2 sudo 설정

# /etc/sudoers (반드시 sudo visudo 로 편집 - 문법 오류가 있으면 sudo 자체를 못 쓴다)
# 로그 기록
Defaults logfile=/var/log/sudo.log
Defaults log_input, log_output

# 타임아웃 설정
Defaults timestamp_timeout=5

# 특정 명령만 허용
username ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx

NOPASSWD 예시는 명령 하나로 좁힌 경우에만 쓴다. 범위를 넓히면 그 계정이 뚫렸을 때 곧바로 root 권한이 된다.

2.3 계정 잠금

# RHEL 계열: authselect 로 faillock 기능을 켠다 (pam_tally2 는 대체됨)
sudo authselect current
sudo authselect enable-feature with-faillock

# /etc/security/faillock.conf
deny = 5
unlock_time = 900

# 실패 횟수 확인 / 잠금 해제
sudo faillock --user username
sudo faillock --user username --reset

pam_tally2 는 Linux-PAM 1.5.0 에서 제거됐다(1.5.0 릴리스 노트: 「Removed deprecated pam_tally and pam_tally2 modules, use pam_faillock instead」). 이 글의 이전 판이 쓰던 pam_tally2.so deny=5 unlock_time=900 은 그 이후 배포판에서 동작하지 않고, 후계는 pam_faillock 이다. 설정 파일은 /etc/security/faillock.conf 이며 기본값은 deny 3회, fail_interval 900초, unlock_time 600초다(faillock.conf(5)). 서비스 거부를 막으려고 root 는 기본적으로 잠기지 않는데(pam_faillock(8)), even_deny_root 로 바꿀 수 있다. 원격 root 가 잠기면 콘솔 없이는 복구가 어려우니 켜기 전에 콘솔 접근을 확인한다.

Debian/Ubuntu 에서는 common-auth·common-account 에 pam_faillock 줄을 직접 넣어야 하고, 순서는 man pam_faillock 의 예시(auth 의 preauth, pam_unix, authfail, 그리고 account)를 따른다. 편집 전에 백업하고, 열려 있는 root 세션을 닫지 않은 채 다른 계정으로 로그인해 시험한다.

3. SSH 보안 강화

# 0) 편집 전 백업. 지금 접속 중인 SSH 세션은 끝까지 닫지 않는다
sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.bak

# /etc/ssh/sshd_config

# 기본 포트 변경 (선택). 방화벽(4절)과 RHEL 계열은 SELinux 포트 레이블(6.1절)을 먼저 준비한 뒤에만
Port 2222

# root 로그인 금지
PermitRootLogin no

# 비밀번호 인증 비활성화 - 새 세션에서 키 로그인이 성공하는 것을 확인한 뒤에만
PasswordAuthentication no

# 키 인증만 허용
PubkeyAuthentication yes

# 빈 비밀번호 금지
PermitEmptyPasswords no

# 로그인 시도 제한
MaxAuthTries 3
LoginGraceTime 30

# 특정 사용자만 허용 (AllowGroups 를 함께 쓸 때의 결합 규칙은 sshd_config(5) 로 확인하고 시험한 뒤에)
AllowUsers admin deploy
#AllowGroups sshusers

# (Protocol 2 는 더 이상 쓰지 않는다: OpenSSH 7.4 가 SSH v1 서버 지원을 제거했다)

# 1) 문법 검사 - 출력이 없으면 정상
sudo sshd -t
# 2) 실효 설정 확인
sudo sshd -T | grep -Ei '^(port|permitrootlogin|passwordauthentication|maxauthtries) '

# 3) 적용 (Debian/Ubuntu 서비스 이름은 ssh, RHEL 계열은 sshd)
sudo systemctl restart ssh
sudo ss -tlnp | grep sshd

# 4) 기존 세션은 둔 채, 새 터미널에서 접속 시험
ssh -p 2222 admin@server

# 5) 실패하면 남겨 둔 기존 세션에서 되돌린다
sudo cp -a /etc/ssh/sshd_config.bak /etc/ssh/sshd_config
sudo systemctl restart ssh

OpenSSH 기본값은 PermitRootLogin prohibit-password, MaxAuthTries 6, LoginGraceTime 120초다(sshd_config(5)). Protocol 2 줄은 OpenSSH 7.4 가 SSH v1 서버 지원을 제거한 뒤로 의미가 없어 뺐다(7.4 릴리스 노트). sshd -t 는 설정 파일 유효성과 키를 검사하고 sshd -T 는 실효 설정을 출력한다(sshd(8)). Ubuntu 문서는 재시작 전에 sudo sshd -t 로 설정을 확인하라고 하고, 실수하면 서버에서 잠길 수 있다고 경고한다(Ubuntu Server 문서). 그래서 위 순서(백업, 문법 검사, 재시작, 새 터미널 시험, 실패 시 되돌리기)를 지키고 기존 세션은 시험이 끝날 때까지 닫지 않는다.

Ubuntu 의 소켓 활성화(ssh.socket) 환경에서 Port 변경이 재시작만으로 반영되는지는 근거 문서가 없다. 재시작 뒤 ss -tlnp | grep sshd 로 실제로 듣는 포트를 확인하라. 포트 변경은 자동 스캔의 로그 소음을 줄일 뿐이고 실제 방어선은 키 인증과 접근 제한이다. AllowUsers 와 AllowGroups 를 함께 쓸 때 어떻게 결합되는지는 sshd_config(5) 를 읽고 시험한 뒤에 쓴다.

4. 방화벽 설정

4.1 UFW (Ubuntu)

# 기본 정책
sudo ufw default deny incoming
sudo ufw default allow outgoing

# ★ ufw enable 보다 먼저 SSH 를 허용한다. 포트는 sshd 가 실제로 듣는 포트와 같아야 한다
sudo ss -tlnp | grep sshd
sudo ufw allow 2222/tcp comment 'SSH'
sudo ufw allow 80/tcp comment 'HTTP'
sudo ufw allow 443/tcp comment 'HTTPS'

# IP 기반 제한 (SSH 포트는 위와 같은 2222)
sudo ufw allow from 192.168.1.0/24 to any port 2222 proto tcp

# 활성화. 잠기면 콘솔에서 sudo ufw disable
sudo ufw enable
sudo ufw status verbose

ufw enable 은 체인을 비우면서 기존 SSH 연결 같은 것을 끊을 수 있다고 매뉴얼에 적혀 있다(ufw(8)). 그래서 SSH 허용 규칙을 enable 보다 먼저 넣고, 그 포트를 sshd 가 실제로 듣는 포트와 맞춘다. 이 글의 이전 판은 SSH 를 2222 로 바꾸면서 IP 제한 규칙은 22번으로 적어 서로 어긋나 있었다. ufw limit 규칙은 30초 안에 6회 이상 연결을 시도하는 IP 의 연결을 거부한다.

4.2 firewalld (RHEL/CentOS)

# 기본 존 확인
sudo firewall-cmd --get-default-zone

# 서비스 허용
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=https

# 포트 허용 - sshd 를 새 Port 로 재시작하기 전에 먼저 연다
sudo firewall-cmd --permanent --add-port=2222/tcp

# 규칙 적용 후 확인
sudo firewall-cmd --reload
sudo firewall-cmd --list-all

sshd 의 Port 를 바꿀 때는 방화벽 --permanent 규칙과 --reload, 그리고 SELinux 포트 레이블(6.1절)까지 끝낸 뒤에 sshd 를 재시작한다. 순서가 뒤집히면 새 포트로 못 들어가거나 sshd 가 뜨지 않는다.

5. 침입 탐지 시스템

5.1 Fail2Ban

# 설치 (RHEL 계열은 dnf 로 설치하며 제공 저장소는 배포판마다 다르다)
sudo apt install fail2ban

# /etc/fail2ban/jail.local
[DEFAULT]
bantime = 3600
findtime = 600
maxretry = 3
# 자기 자신을 차단하지 않도록 관리자 IP 를 추가한다
ignoreip = 127.0.0.1/8 ::1

[sshd]
enabled = true
port = 2222
# journald 만 쓰는 시스템(/var/log/auth.log 가 없는 경우)은 저널을 읽게 한다
backend = systemd
# 파일 로그를 쓰는 시스템: logpath = /var/log/auth.log

[nginx-http-auth]
enabled = true

# 시작 및 상태 확인
sudo systemctl enable --now fail2ban
sudo fail2ban-client status
sudo fail2ban-client status sshd
# 잘못 차단된 IP 해제
sudo fail2ban-client unban 203.0.113.10

Debian 12 처럼 저널(journald)만 쓰는 시스템에는 /var/log/auth.log 가 없어, 예전처럼 logpath 만 적으면 sshd jail 이 읽을 로그가 없다. 이런 시스템에서는 backend = systemd 를 쓴다. 이 부분과 ignoreip·unban 옵션은 fail2ban 공식 문서가 아니라 2차 자료에 근거한다. 적용 후 fail2ban-client status sshd 로 jail 이 실제로 동작하는지 확인한다.

5.2 AIDE (무결성 검사)

# 설치 (Debian/Ubuntu)
sudo apt install aide

# 데이터베이스 초기화
sudo aideinit

# 검사 실행
sudo aide --check

# 데이터베이스 업데이트
sudo aide --update

6. SELinux / AppArmor

6.1 SELinux (RHEL/CentOS)

# 상태 확인
getenforce
sestatus

# 모드 변경 (재부팅 전까지만 유효). Permissive 는 원인 진단용이다
sudo setenforce 0  # Permissive
sudo setenforce 1  # Enforcing

# 영구 설정 (/etc/selinux/config)
SELINUX=enforcing

# SSH 포트를 바꿨다면 sshd 재시작 전에 레이블을 붙인다 (안 붙이면 bind 가 Permission denied)
sudo semanage port -a -t ssh_port_t -p tcp 2222
sudo semanage port -l | grep ssh_port_t

# 문제 해결
sudo ausearch -m avc -ts recent
sudo sealert -a /var/log/audit/audit.log

RHEL 계열에서 SSH 포트를 바꿨다면 SELinux 는 sshd 가 ssh_port_t 로 레이블된 포트에만 bind 하게 한다. 레이블을 붙이지 않고 재시작하면 Permission denied 로 sshd 가 뜨지 않는다. semanage 는 policycoreutils-python-utils 패키지에 들어 있다. 이 절차는 공식 문서가 아니라 2차 자료에 근거한다. sealert 는 별도 패키지 설치가 필요할 수 있다. setenforce 0 은 원인을 가리는 진단용이고, 확인이 끝나면 곧바로 setenforce 1 로 돌린다.

6.2 AppArmor (Ubuntu)

# 상태 확인
sudo aa-status

# 프로파일 관리
sudo aa-enforce /etc/apparmor.d/usr.sbin.nginx
sudo aa-complain /etc/apparmor.d/usr.sbin.nginx

# 로그 확인
sudo journalctl -fx | grep apparmor

7. 취약점 스캔

7.1 Lynis

# 설치
sudo apt install lynis

# 시스템 감사
sudo lynis audit system

# 보고서 확인
sudo cat /var/log/lynis.log
sudo cat /var/log/lynis-report.dat

7.2 OpenVAS

# Greenbone Community Edition: 공식 컨테이너 설치 안내를 따른다
# https://greenbone.github.io/docs/latest/22.4/container/index.html
# (Docker/Podman 과 docker-compose 필요. 공식 문서 지원 배포판: Debian stable, Ubuntu 24.04 LTS 등)
# 스캔은 내가 소유하거나 스캔을 허가받은 시스템에만 실행한다
docker compose version

이 글의 이전 판은 apt install openvas 와 gvm-setup 을 안내했지만, Greenbone 공식 문서는 컨테이너(Docker/Podman + docker-compose) 설치를 안내하고 배포판 패키지 설치는 다루지 않는다. 공식 문서가 지원한다고 밝힌 배포판은 Debian stable(bookworm), Ubuntu 24.04 LTS 등이며, 그 컨테이너 안내는 운영 환경용이 아니라고 스스로 밝힌다(Greenbone Community Containers). 스캔은 소유하거나 허가받은 시스템에만 실행한다.

8. 로그 모니터링

# 의심스러운 활동 모니터링
# 로그인 실패 (Debian/Ubuntu)
sudo grep "Failed password" /var/log/auth.log | tail -20
# 로그인 실패 (RHEL 계열)
sudo grep "Failed password" /var/log/secure | tail -20
# journald 만 쓰는 시스템 (RHEL 계열은 -u sshd)
sudo journalctl -u ssh --since today | grep "Failed password" | tail -20

# sudo 사용 기록
sudo grep "sudo" /var/log/auth.log

# 시스템 부팅/종료
last reboot
last shutdown

# 현재 접속 사용자
who
w

# 네트워크 연결
ss -tuln

로그 위치는 배포판마다 다르다. Debian/Ubuntu 는 /var/log/auth.log, RHEL 계열은 /var/log/secure 이고, 저널만 쓰는 시스템에서는 journalctl 로 본다. 이전 판에 있던 netstat 줄은 ss 와 같은 목적이라 뺐다.

9. 보안 체크리스트

#!/bin/bash
# security_audit.sh (읽기 전용 점검)

echo "=== Linux 보안 감사 ==="

echo -e "\n[1] 시스템 업데이트 확인"
apt list --upgradable 2>/dev/null | head -10

echo -e "\n[2] root 로그인 가능 여부 (실효 설정)"
sudo sshd -T 2>/dev/null | grep -i "^permitrootlogin"

echo -e "\n[3] 비밀번호 인증 여부 (실효 설정)"
sudo sshd -T 2>/dev/null | grep -i "^passwordauthentication"

echo -e "\n[4] 열린 포트"
ss -tuln | grep LISTEN

echo -e "\n[5] SUID 파일 (같은 파일시스템만)"
find / -xdev -perm -4000 -type f 2>/dev/null | head -10

echo -e "\n[6] 빈 비밀번호 계정 (root 권한 필요)"
sudo awk -F: '($2 == "") {print $1}' /etc/shadow

echo -e "\n[7] 최근 로그인 실패"
sudo grep "Failed password" /var/log/auth.log /var/log/secure 2>/dev/null | tail -5

echo -e "\n[8] 방화벽 상태"
sudo ufw status 2>/dev/null || sudo firewall-cmd --state 2>/dev/null

echo -e "\n감사 완료"

다음 갱신을 부르는 조건은 다음과 같다.

  • 새 OpenSSH 릴리스가 기본값을 바꾸거나 지시어를 제거할 때 - 3절의 설정 예시와 기본값 문장이 바뀐다.
  • 새 Linux-PAM 릴리스가 pam_faillock 기본값이나 모듈 구성을 바꿀 때 - 2.3절이 바뀐다.
  • Ubuntu·Debian·Rocky Linux 의 새 주 버전(LTS) 출시 - 서비스 이름·로그 위치·소켓 활성화 관련 문장을 다시 확인한다.
  • Greenbone 공식 문서의 지원 배포판이나 설치 방식이 바뀔 때 - 7.2절이 바뀐다.

이번 갱신에서 공식 근거를 갖추지 못한 것은 다음과 같다.

  • Ubuntu 소켓 활성화(ssh.socket) 환경에서 Port 변경이 재시작만으로 반영되는지
  • fail2ban 의 backend·ignoreip·unban 옵션과 SELinux 의 semanage 절차(2차 자료로만 확인, 공식 문서 미대조)
  • AllowUsers 와 AllowGroups 를 함께 쓸 때의 결합 규칙, RHEL 계열의 pwquality 설정 위치와 GRUB 비밀번호 절차

# 원격 서버 보안 변경 점검표 - SSH·방화벽·PAM

기준일: 2026-09-29
출처: OpenSSH 7.4 릴리스 노트, sshd(8), sshd_config(5), ufw(8), Linux-PAM 1.5.0 릴리스 노트, faillock.conf(5), DNF Automatic 문서, Greenbone Community Containers 문서

---

## 1. 변경 전 (SSH·방화벽·PAM 공통)

- [ ] 지금 접속 중인 세션은 시험이 끝날 때까지 닫지 않는다
- [ ] 콘솔(가상 머신 콘솔·IPMI) 접근 수단이 있는지 확인했다
- [ ] 고칠 파일을 백업했다 (`cp -a 파일 파일.bak`)

## 2. SSH 설정 변경 순서

| 순서 | 할 일 | 명령 |
|---|---|---|
| 1 | 백업 | `sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.bak` |
| 2 | 문법 검사 (출력 없으면 정상) | `sudo sshd -t` |
| 3 | 실효 설정 확인 | `sudo sshd -T` |
| 4 | 재시작 (Debian/Ubuntu 는 ssh, RHEL 계열은 sshd) | `sudo systemctl restart ssh` |
| 5 | 실제로 듣는 포트 확인 | `sudo ss -tlnp` |
| 6 | 새 터미널에서 접속 시험 | `ssh -p 포트 사용자@서버` |
| 7 | 실패하면 기존 세션에서 되돌림 | `.bak` 복원 후 재시작 |

- [ ] 비밀번호 인증을 끄기 전에 새 세션에서 키 로그인이 성공했다
- [ ] `Protocol 2` 줄은 넣지 않는다 (OpenSSH 7.4 가 SSH v1 서버 지원을 제거)

## 3. SSH 포트를 바꾼다면 (순서가 중요)

- [ ] 방화벽에 새 포트를 먼저 연다 (UFW: `ufw allow`, firewalld: `--permanent` 후 `--reload`)
- [ ] RHEL 계열은 SELinux 포트 레이블을 붙인다 (`semanage port -a -t ssh_port_t -p tcp 포트`)
- [ ] 그 다음에 sshd 를 재시작한다
- [ ] UFW 는 `ufw enable` 보다 SSH 허용 규칙을 먼저 넣는다 (enable 이 기존 연결을 끊을 수 있다)

## 4. 로그인 실패 잠금

| 항목 | 값 |
|---|---|
| `pam_tally2` | Linux-PAM 1.5.0 에서 제거됨 - 쓰지 않는다 |
| 대체 | `pam_faillock` (설정 `/etc/security/faillock.conf`) |
| 기본값 | deny 3회 / fail_interval 900초 / unlock_time 600초 |
| root | 기본적으로 잠기지 않음 (`even_deny_root` 로 변경) |

- [ ] 원격 root 를 잠그기 전에 콘솔 접근을 확인했다
- [ ] PAM 파일을 고친 뒤 다른 계정으로 로그인해 시험했다

## 5. 자동 업데이트 (RHEL 계열)

- [ ] 설치까지 자동화하려면 `dnf-automatic-install.timer` 를 켠다
- [ ] `dnf-automatic.timer` 만 켜면 `apply_updates` 기본값(False) 때문에 설치되지 않는다

## 6. 배포판별로 다른 곳

| 항목 | Debian/Ubuntu | RHEL 계열 |
|---|---|---|
| SSH 서비스 이름 | `ssh` | `sshd` |
| 인증 로그 | `/var/log/auth.log` | `/var/log/secure` |
| 저널만 쓰는 시스템 | `journalctl -u ssh` | `journalctl -u sshd` |
| fail2ban 저널 사용 | `backend = systemd` | 동일 |
