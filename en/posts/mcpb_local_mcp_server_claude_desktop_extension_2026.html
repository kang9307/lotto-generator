This article covers what the Anthropic documentation (Build a desktop extension with MCPB), the modelcontextprotocol/mcpb repository (README, MANIFEST.md v0.3, CLI.md), and the engineering blog post Desktop Extensions state.

Context - Transforming Complex Config Editing into Single-Click Extension Installs

The engineering blog post Desktop Extensions says that local MCP servers opened up everything from file systems to databases for Claude, but that the same feedback kept coming back: installation was too complex. Users needed developer tools, had to edit configuration files by hand, and often got stuck on dependency issues. The post lists five barriers. Developer tools were required, meaning a Node.js, Python, or other runtime had to be installed. Configuration was manual, since each server required editing JSON configuration files. Dependency management fell to the user, who had to resolve package conflicts and version mismatches. There was no discovery mechanism, so finding a useful server meant searching GitHub. And updates were complex, because keeping a server current meant reinstalling it manually.

MCPB (.mcpb) is introduced as the answer to that problem. The official documentation defines an MCP Bundle as a zip archive containing a local MCP server and a manifest.json, which Claude Desktop installs in a single click the way a browser installs an extension. The format was originally named DXT (Desktop Extensions, .dxt). The README carries a notice that the project is being renamed from DXT to MCPB, and it lists three consequences: the dxt CLI is now mcpb, .dxt files are now .mcpb files, and the @anthropic-ai/dxt package will be moved to @anthropic-ai/mcpb. The README gives no reason for the rename. In a note dated September 11, 2025 the blog says that existing .dxt extensions continue to work, that .mcpb is recommended for new extensions, and that all functionality remains the same. The README describes the format as spiritually similar to Chrome extensions (.crx) or VS Code extensions (.vsix).

The blog summarizes the user side in three steps: download a .mcpb file, double-click it to open it with Claude Desktop, and click Install. In its words there is no terminal, no configuration files, and no dependency conflicts.

  • First, installation no longer involves editing configuration files by hand, which is the difference the blog draws between the earlier procedure and the new one.
  • Second, how the server is run and what settings it needs are declared in manifest.json, and MANIFEST.md lists manifest_version, name, version, description, author, and server as required fields.
  • Third, sensitive settings are handled separately: the blog says sensitive values such as API keys are stored in the OS keychain, and MANIFEST.md says a sensitive value is masked and stored securely.
  • Fourth, the server runs on the user's machine over stdio, needs no cloud infrastructure, works offline, and requires no OAuth, which are the characteristics the official documentation lists for an MCPB, and the documentation adds that an MCPB bundles all of its dependencies.

The README introduces the repository as providing three things: the bundle specification in MANIFEST.md, a CLI tool for creating bundles, and the code that Claude for macOS and Windows uses to load and verify MCPB bundles.

Architecture - A Local Server Running over stdio on the User's Machine

The first paragraph of the official documentation states the heart of the architecture. The server runs on the user's machine over stdio, so it can reach local files, locally installed tools, and systems behind the user's firewall without any cloud infrastructure. The same page contrasts where the two options run: MCPBs run on the user's machine via stdio with access to local and internal resources, while remote connectors run on your servers via HTTPS and are accessed through Anthropic's infrastructure. The page says this guidance is for developers packaging a local MCP server for Claude Desktop, whether for internal use or private distribution. It adds that organizations commonly build MCPBs as secure proxies to internal MCP servers, for internal documentation access, and to connect development tools while preserving their security architecture.

The documentation lists five characteristics of an MCPB: it runs locally on the user's machine, it communicates via stdio transport, it bundles all dependencies, it works offline, and it requires no OAuth.

The official documentation (Build a desktop extension with MCPB) offers a table of the needs that point to a local MCPB and to a remote connector. The table below regroups those entries under four viewpoints.

Decision Criteria Local MCPB (.mcpb) Remote Connector
Network and Firewalls Access systems behind corporate firewalls (issue trackers, internal wikis, private DBs) Public cloud APIs and services requiring centralized infrastructure
Authentication and Credentials Leverage existing SSO and browser sessions with no token management required OAuth flows with server-side token management
Data Privacy and Isolation Privacy-sensitive tasks that must not leave the device; local filesystem access Centralized updates and distribution across Claude web, mobile, and desktop
Runtime and Infrastructure Bundled Node.js runtime in Claude Desktop; zero external cloud infrastructure Centralized deployments requiring ongoing cloud hosting maintenance

The original table contains further reasons to choose an MCPB beyond the items above. These include direct filesystem access for code editing and Git operations, integration with locally installed tools such as Docker, IDEs, and databases, hardware integration and desktop application control, a one-click install with a bundled Node.js runtime and no dependencies to manage, no cloud infrastructure, VPN configuration, or firewall rules, organization-level admin controls such as custom uploads and allowlists, and full control over authentication, authorization, and audit logs.

For the local stdio execution model, the documents state the following four things directly.

  • Local execution: the server runs on the user's machine and reaches local files and locally installed tools.
  • stdio transport: Claude Desktop and the server communicate over the stdio transport.
  • Offline operation: the documentation says an MCPB works offline.
  • Authentication and infrastructure: no OAuth is required, authentication can use existing SSO and browser sessions so that no tokens need to be managed, and no cloud infrastructure is needed.

Interpretations that go beyond these four points, for example statements about whether ports are opened or about the boundary of process privileges, do not appear in these documents. This article therefore carries that part only as far as the documents go.

Runtime Choices - Bundled Node.js Environment vs Python Dependencies

The first thing to decide when developing an MCPB extension is the implementation language. The official documentation strongly recommends Node.js and gives three reasons: it is included with Claude Desktop on macOS and Windows, so users need no separate runtime; it has the best compatibility and reliability with Claude Desktop; and the MCP SDK support is extensive. The blog likewise says that Node.js is shipped with Claude Desktop, eliminating external dependencies.

The README makes the same recommendation from the standpoint of installation friction. Because Node.js ships with Claude for macOS and Windows, a bundle works out of the box without requiring users to install an additional Python runtime, or the developer to package one manually. The supported platforms are macOS (darwin) and Windows (win32), and the supported platforms are declared in the compatibility section of manifest.json. The documentation advises testing on both platforms even when a developer works mainly on one, and the manifest spec points to its compatibility section for the details of platform and runtime requirements.

The Bundling Dependencies section of the README explains that dependencies are handled differently for each server type.

  • Node.js bundles: run npm install --production to create node_modules and bundle that whole directory with the bundle. For reproducible builds the README suggests npm ci or yarn install --frozen-lockfile, and the server entry point is specified in server.entry_point. MANIFEST.md likewise says that a Node.js extension must bundle all of its dependencies in node_modules.
  • Python bundles, the traditional approach: use server.type = "python" and bundle the required packages in the server/lib/ directory, or bundle a complete virtual environment in server/venv/. Set PYTHONPATH through mcp_config.env so that it points at the bundled packages. The README also states a limitation: compiled dependencies, such as pydantic, which the MCP Python SDK requires, cannot be bundled portably.
  • The uv type (v0.4+): set server.type = "uv" and include a pyproject.toml that lists the dependencies. No bundled packages are needed, the host application manages Python and dependencies automatically, and it works across platforms without a user Python installation, according to the README. The uv example in MANIFEST.md uses a manifest_version of 0.4.
  • Binary bundles: static linking is preferred for maximum compatibility, all required shared libraries should be included if dynamic linking is used, and the bundle should be tested on clean systems without development tools. MANIFEST.md describes the binary type as a pre-compiled executable with all dependencies included, and platform-specific binaries are supported.

In summary, the README gives as its reason for recommending Node.js that Node.js is included with Claude, so no Python runtime needs to be installed or packaged separately. That does not mean every Python server must bundle its dependencies wholesale. The traditional python type needs packages in the bundle and has a limitation for compiled dependencies, while the uv type hands that burden to the host.

Manifest Specification (v0.3) - Required Fields and Auto-Generated Configuration UI

The manifest.json is the only file that a bundle must contain. The official documentation describes it as required metadata describing what the MCPB does, how to run it, which tools it provides, and what configuration it needs. MANIFEST.md states that the current version is 0.3, that it was last updated on December 2, 2025, and that most fields are optional. A basic manifest with only the required fields looks as follows.

{
                      "manifest_version": "0.3",
                      "name": "my-extension",
                      "version": "1.0.0",
                      "description": "A simple MCP extension",
                      "author": {
                        "name": "Extension Author"
                      },
                      "server": {
                        "type": "node",
                        "entry_point": "server/index.js",
                        "mcp_config": {
                          "command": "node",
                          "args": [
                            "${__dirname}/server/index.js"
                          ]
                        }
                      }
                    }

According to MANIFEST.md, ${__dirname} is replaced with the extension's directory, and the blog says it becomes the full path of the directory where the extension is unpacked. A server that needs values from the user declares a user_config block. The official documentation says that defining user_config makes Claude Desktop generate a settings UI for the extension automatically. The blog's walkthrough of the example is more concrete: when the developer declares that the user must supply an api_key, Claude will not enable the extension until the user has supplied that value, keeps it automatically in the operating system's secret vault, and transparently replaces ${user_config.api_key} with the user-supplied value when launching the server.

{
                      "manifest_version": "0.3",
                      "name": "my-extension",
                      "version": "1.0.0",
                      "description": "A simple MCP extension",
                      "author": {
                        "name": "Extension Author"
                      },
                      "server": {
                        "type": "node",
                        "entry_point": "server/index.js",
                        "mcp_config": {
                          "command": "node",
                          "args": ["${__dirname}/server/index.js"],
                          "env": {
                            "API_KEY": "${user_config.api_key}"
                          }
                        }
                      },
                      "user_config": {
                        "api_key": {
                          "type": "string",
                          "title": "API Key",
                          "description": "Your API key for authentication",
                          "sensitive": true,
                          "required": true
                        }
                      }
                    }

The main fields summarized in MANIFEST.md are the following.

  • manifest_version (required, string): the specification version the manifest conforms to, currently 0.3 in the examples. The other required fields are name, version (semver), description, and author, where the name is required and the email and URL are optional.
  • server (required, object): the type is one of node, python, or binary, and entry_point points at the main server file. The mcp_config object holds command, args, and env. For the uv type described in the same document the host manages execution, so mcp_config is optional.
  • user_config (optional, object): the input types are string, number, boolean, directory, and file. Properties such as title, description, required, default, multiple, min, and max can also be defined, and turning on sensitive for a string type masks the input and stores it securely.
  • compatibility (optional, object): platforms lists darwin, win32, and linux, and runtimes states runtime version requirements. The example in the documentation is node: ">=16.0.0", and when the field is omitted all platforms are treated as supported.
  • icon (optional, string): a path relative to the package or an https:// URL. The official documentation recommends a 512×512 pixel PNG with transparency and sets the minimum at 256×256, and an icons array covers light and dark themes or several sizes.

Substitution variables are written like ${user_config.KEY}, and values chosen as multiple selections are expanded as separate arguments. MANIFEST.md adds that environment variables are ideal for sensitive data, while command arguments work well for paths and non-sensitive options.

The blog also shows a fuller manifest in which many optional fields appear: display_name, long_description, repository, homepage, documentation, support, screenshots, tools, prompts, keywords, and license. Its cross-platform example places a platforms block under mcp_config so that win32 can use node.exe and its own environment variables while darwin sets different ones. Of these, only the fields in the list above are required or central to this article, and the rest simply describe the extension to users.

Build Toolchain - @anthropic-ai/mcpb CLI Commands and Packaging Workflow

The flow that the official documentation walks through has five steps. Install the MCPB CLI, build a stdio MCP server with the MCP SDK, generate the manifest with mcpb init, bundle with mcpb pack, and then double-click the generated .mcpb file to install and test it in Claude Desktop. The README also says that turning a local MCP server into a bundle only requires putting all required files in a folder, creating a manifest.json, and creating an archive. The earlier @anthropic-ai/dxt package, in the README's wording, will be moved to @anthropic-ai/mcpb.

npm install -g @anthropic-ai/mcpb
                    
                    # Generate a manifest interactively
                    mcpb init
                    
                    # Validate the manifest against the schema
                    mcpb validate manifest.json
                    
                    # Pack the directory into an .mcpb bundle
                    mcpb pack .

CLI.md lists seven commands. The main ones are the following.

  • mcpb init [directory]: creates a new manifest interactively. It asks for the extension name, author, extension ID, display name, version, description, the author's email and URL, the server type (Node.js, Python, or Binary), the entry point, the tools configuration, and keyword, license, and repository information. The blog adds that a --yes parameter produces the most basic manifest quickly.
  • mcpb validate <path>: validates a manifest against the schema. A direct path to a manifest.json file or a directory containing one can be given.
  • mcpb pack <directory> [output]: packs a directory into a .mcpb file. It validates manifest.json automatically, excludes common development files such as .git, node_modules/.cache, and .DS_Store, and creates a ZIP with maximum compression.
  • mcpb sign and mcpb verify: sign signs a .mcpb file with a certificate, and options accept certificate and key paths and intermediate certificates. There is also --self-signed, which creates and uses a self-signed certificate. verify reports signature validity, the certificate subject and issuer, validity dates, and the fingerprint, and it warns when the certificate is self-signed.

The remaining two commands are info, which displays file size, signature status, and certificate details, and unsign, which removes the signature for development and testing. The directory structure that the README shows for a Node.js bundle consists of manifest.json (required), server/index.js, a bundled node_modules/, an optional package.json and icon.png, and assets/.

CLI.md also gives short usage examples. mcpb pack . packs the current directory into extension.mcpb, and mcpb pack my-extension/ my-extension-v1.0.mcpb packs a directory into a custom output filename. mcpb validate ./my-extension and mcpb validate . validate the manifest in a directory, and mcpb sign my-extension.mcpb --cert /path/to/cert.pem --key /path/to/key.pem signs with a custom certificate and key. These are the commands the documentation itself uses, and no further workflow is implied beyond them.

Installation Experience and Distribution - Deprecated Directory and Plugins

The official documentation explains that users install the .mcpb file themselves in Claude Desktop. The installation methods are the following.

  • Double-click the .mcpb file in the file explorer.
  • Drag and drop the .mcpb file into the running Claude Desktop window.
  • In Claude Desktop, go to Settings > Extensions > Advanced settings > Install Extension… and select the .mcpb file.
  • Per-user installation: because installation is per-user, each user installs separately on their own system.

All three methods open an installation UI. According to the documentation, the user reviews extension details and permissions on this screen, configures the required settings, grants permissions, and completes installation. The blog describes the same screen as showing human-readable information about the extension, the required permissions and configuration, and a simple Install button.

Distribution carries a policy change. The Distribute your MCPB section, which sits on the same documentation page rather than in a separate document, says that users install the .mcpb file themselves, then states that desktop extension listings in the directory are deprecated and that the directory no longer accepts MCPB submissions. It continues that to distribute a local MCP server through the directory, the server should be included in a plugin. The opening of the page likewise says that for a directory listing one should build a remote MCP server, which reaches people on every surface, or include the local server in a plugin.

The .mcpb format is therefore used for passing files directly, for internal or private distribution, while a directory listing has to go through the plugin route. The engineering blog described a procedure for submitting extensions to the directory when it launched, but the current documentation says that route is deprecated, so the statements differ by date, and this article follows the current documentation. Admin controls for deploying extensions across a Team or Enterprise organization, such as allowlists and policy configuration, and the end-user installation experience are covered separately in Anthropic's support documentation.

The blog also lists safeguards for users and enterprises that it built into the preview release of Desktop Extensions. For users these are sensitive data staying in the OS keychain, automatic updates, and the ability to audit which extensions are installed. For enterprises it names Group Policy on Windows and MDM on macOS support, the ability to pre-install approved extensions, blocklisting specific extensions or publishers, disabling the extension directory entirely, and deploying private extension directories. These statements come from the blog, which describes a preview release, so they should be read against the current Team and Enterprise documentation before being relied on.

Documented Statements vs Unverified Points Across MCPB Components

Before adopting a local extension for real work, it helps to separate what the official documentation says from what it leaves out. The table below contrasts the two for each MCPB component.

Component Area Explicitly Documented Statements Unverified Items and Implementation Caveats
Process Execution Model Local execution via stdio; variable substitution of ${__dirname} Pipe forwarding behaviors when wrapping servers in custom launcher scripts
Config UI and Secrets Generates UI from user_config; sensitive values are masked and stored securely (blog: OS keychain) The storage mechanism and encryption per OS, and whether the file type supports arbitrary absolute filesystem paths
Runtime Dependencies Node.js is included with Claude Desktop on macOS and Windows; python type bundles packages, uv type lets the host manage Python and dependencies Exact Node.js minor version and supported v8 runtime engine flags
Distribution Channels Direct .mcpb sharing or plugin inclusion; directory submissions deprecated Enterprise policy controls for whitelisting specific signing certificate authorities

The points to watch when designing against this contrast are limited to those that follow directly from the documents.

  • Platform checks: the documentation advises testing on both macOS and Windows even when development happens mainly on one of them.
  • Path input: user_config supports the directory and file types, and multiple allows several selections. How far the file picker allows arbitrary paths is not stated in the documents, so it has to be checked directly.
  • Distribution route: because directory submissions are deprecated, the .mcpb file is handed over directly or included in a plugin. Organization-level admin controls such as custom uploads and allowlists are covered by the Team and Enterprise documentation.
  • Signing: mcpb sign signs with a certificate and can also create a self-signed one, and verify warns when the certificate is self-signed. Anyone adopting signatures should decide beforehand what that warning means.

What could not be confirmed

  • The exact version of the bundled Node.js runtime distributed inside the latest Claude Desktop desktop builds.
  • Whether user_config properties configured with type: "file" support selecting arbitrary absolute paths outside the unpacked bundle folder.
  • The internal child process hierarchy in Claude Desktop and its specific handling of stdin EOF when custom wrapper scripts spawn grandchildren.
  • Whether the Claude in Chrome browser extension will natively interface with local MCPB servers running inside Claude Desktop.
  • Specific Windows Group Policy Objects (GPO) or macOS MDM payload keys for restricting unsigned .mcpb bundle installations across enterprise fleets.
