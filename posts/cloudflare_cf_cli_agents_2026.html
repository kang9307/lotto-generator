cf 가 무엇이고 어디까지 확인되는가

cf 는 Cloudflare 가 공개 베타로 내놓은 명령줄 도구다. README 는 이 도구를 「다음 세대 소프트웨어 개발을 위해 만든 CLI」로 소개하고, 네 가지 특징을 나열한다. 에이전트가 맞춤 검색과 유도(search and steering)로 명령을 찾을 수 있고, JSON 이 기본 인터페이스이며, TypeScript 설정 파일 cloudflare.config.ts 가 안전성과 정확성을 주고, Vite 통합으로 로컬 개발을 지원한다는 것이다.

이 글의 축은 새 도구의 소개가 아니라 설계 방향이다. 명령줄 도구는 오랫동안 사람이 읽고 치는 것을 전제로 만들어졌다. cf 는 그 전제를 에이전트로 옮겼을 때 무엇이 달라지는지를 명령 발견, 출력 형식, 설정 형식 세 곳에서 보여 준다. 세 곳 모두 원문에 근거가 있으므로 하나씩 대응 관계를 따라간다.

설치 명령은 README 에 있는 그대로 다음 한 줄이다. README 는 「오픈 베타를 지금 전역 설치해 어디서든 실행하라」고 안내한다.

npm i -g cf

명령이 API 스키마에서 직접 생성된다는 점은 범위 문제와 이어진다. 손으로 명령을 하나씩 추가하는 방식에서는 명령의 수가 작성자의 작업량에 묶이지만, 스키마에서 만들어 내는 방식에서는 API 가 늘어나면 명령도 따라 늘어난다. Wrangler 가 약 280개 작업에 머문 것과 수천 개 작업을 다루는 cf 의 차이가 이 생성 방식에서 나온다는 것이 블로그의 설명이다. 다만 생성된 명령이 사람이 다듬은 명령만큼 읽기 쉬운지는 원문이 다루지 않는다.

사람용 CLI 가 에이전트 앞에서 어긋나는 자리

명령줄 도구가 사람을 위해 설계됐다는 말은 구체적으로 세 가지 가정을 뜻한다. 사용자는 명령 이름을 대략 기억하거나 문서에서 찾아낼 수 있고, 출력은 눈으로 훑어 필요한 줄을 고를 수 있으며, 설정은 예제를 복사해 조금 고치는 방식으로 쓴다는 가정이다. 에이전트는 이 가정 어느 쪽에도 그대로 맞지 않는다. 아래는 해설이며, cf 가 그 어긋남을 어디서 메우는지가 다음 절들의 내용이다.

  • 명령 발견. 사람은 도움말과 문서 검색으로 명령을 찾는다. 에이전트가 명령 수천 개의 도움말 전문을 컨텍스트에 싣는 방식은 비용이 크므로, 필요한 명령만 골라 주는 진입점이 따로 필요하다.
  • 출력 소비. 사람에게는 정렬과 색이 도움이 되지만 에이전트에게는 파싱 가능한 구조와 짧은 길이가 중요하다. 같은 정보라도 표현에 따라 컨텍스트 사용량이 달라진다.
  • 설정 검증. 사람은 설정을 잘못 쓰면 배포 단계의 오류 메시지를 읽고 고친다. 에이전트는 편집 시점에 오류를 알려 주는 타입 검사가 있으면 시행착오가 줄어든다.
  • 범위. 명령이 없는 작업은 에이전트가 다른 경로로 우회해야 한다. 명령이 닿는 작업의 범위가 곧 에이전트가 CLI 만으로 할 수 있는 일의 범위다.

이 네 가지가 cf 발표문이 특징으로 내세운 것과 겹친다. 다만 겹친다는 것은 설계 의도의 방향이 같다는 뜻이지, 실제 에이전트 작업에서 효과가 측정됐다는 뜻이 아니다. 발표문과 README 는 효과 측정치를 제시하지 않는다.

이 표는 세 갈래로 읽으면 된다. 근거가 원문인 칸은 그대로 인용해도 되는 사실이고, 원문과 해설이 함께 적힌 칸은 앞부분만 사실이며, 해설 뒤쪽은 자기 환경에서 검증해야 할 가설이다. 예를 들어 타입 오류가 시행착오를 줄인다는 서술은 그럴듯한 추론이지만 측정된 결과가 아니다. 도입을 판단하는 자리에서는 이 구분을 유지해야 발표문의 의도와 실제 효과가 섞이지 않는다.

검색 가능한 명령 - cf cli search

수천 개의 작업이 명령이 되면 목록 자체가 탐색의 장애물이 된다. 블로그는 이 문제를 검색 명령으로 푼다. 원문 문장은 다음과 같다. 「이 명령은 에이전트가 해야 할 일을 자연어로 물을 수 있게 하고, 작은 검색 색인이 API 설명과 파라미터를 바탕으로 알맞은 명령 목록을 제공한다.」

  • 입력은 자연어다. 명령 이름을 알아야 하는 것이 아니라 하려는 일을 적으면 된다. 이 방식은 명령 이름이 API 스키마에서 생성되는 구조와 맞물린다.
  • 색인의 재료는 API 설명과 파라미터다. 별도로 손으로 쓴 문서가 아니라 API 스키마에 이미 있는 설명이 검색 대상이라는 뜻이다. 명령이 스키마에서 나오므로 검색 대상도 같은 원천에서 나온다.
  • 안내는 첫 도움말 실행 때 자동이다. 원문은 에이전트가 --help 를 처음 실행할 때 이 명령을 자동으로 알려 준다고 적었다. README 가 말하는 유도(steering)는 이 지점을 가리키는 것으로 읽힌다.

해설을 덧붙이면, 검색 결과가 에이전트의 다음 행동 후보를 좁힌다는 점이 핵심이다. 전체 도움말을 읽게 하는 대신 질문에 해당하는 소수의 명령만 컨텍스트에 들어오게 만든다. 다만 검색이 잘못된 명령을 앞에 올리는 경우 에이전트가 그 명령을 그대로 실행할 위험은 남는다. 이 점에 대한 정확도 수치나 실패 사례는 원문에 없다.

구조화 출력 - JSON 이 기본값인 이유

README 의 문장은 짧다. JSON 이 기본 인터페이스이고, 사람에게는 보기 좋게 출력하고 에이전트에게는 압축해 출력한다. 블로그는 여기에 한마디를 더했다. 압축의 목적은 컨텍스트를 최대한 절약하는 것이다.

  • 같은 데이터, 두 가지 표현. 데이터 형식은 하나의 JSON 이고, 들여쓰기와 공백을 살리느냐 줄이느냐가 대상에 따라 갈린다. 형식이 하나이므로 사람과 에이전트가 서로 다른 출력 경로를 갖지 않는다.
  • 컨텍스트는 예산이다. 에이전트가 읽는 모든 출력은 컨텍스트 창을 소비한다. 공백 몇 글자는 작아 보여도 수백 번의 호출에서는 누적된다. 원문은 이를 「최대한의 컨텍스트 절약」이라는 표현으로 정리한다.
  • 파싱 가능성. 해설이다. 줄 단위 텍스트 표를 정규식으로 잘라 읽는 것보다 JSON 필드를 읽는 편이 오독이 적다. 필드 이름이 안정적인지는 원문이 다루지 않았다.

이 절의 한계도 분명하다. 원문은 어떤 명령이 어떤 필드를 내는지, 압축된 출력이 사람용 대비 얼마나 작은지 수치를 제시하지 않았다. 컨텍스트 절약이 얼마나 되는지는 자기 작업에서 재 봐야 하는 값이다.

컨텍스트 절약이 실제로 얼마인지는 직접 재 볼 수 있다. 같은 조회 명령의 압축 출력과 보기 좋게 정리된 출력을 각각 파일로 저장해 글자 수를 비교하면 된다. 이 비교는 읽기 전용이고 부하가 없다. 다만 글자 수와 토큰 수는 같지 않으므로 사용하는 모델의 토큰 계산 도구로 다시 세는 편이 정확하다. 원문은 이 비교를 제시하지 않았으므로, 여기서 나오는 값은 각자의 작업에서만 유효하다.

설정의 타입화 - cloudflare.config.ts

cf 는 설정을 TOML 이 아니라 TypeScript 파일 cloudflare.config.ts 로 쓴다. README 는 이것이 안전성과 정확성을 준다고 하고, 블로그는 타입 검사와 자동완성, 그리고 코드로 환경을 만드는 방식을 설명한다. 블로그의 예시는 cf/config 에서 bindings 와 defineConfig 를 불러와 worker 이름과 환경 값을 함수로 반환하는 형태이며, 함수 인자로 mode 를 받는다.

  • 타입 검사와 자동완성. 설정 값의 이름과 형식이 편집 시점에 검사된다. 사람에게는 자동완성이 되고, 에이전트에게는 잘못된 키를 배포 이전에 알려 주는 피드백이 된다(후자는 해설).
  • 코드로 만드는 환경. 정적 파일 대신 함수가 mode 에 따라 설정을 반환한다. 환경이 많아질수록 복사한 파일을 여러 개 유지하는 방식보다 함수 하나로 파생시키는 방식이 유리하다는 것이 발표문의 논리다.
  • 40% 압축 사례. 블로그는 Cloudflare 내부의 일부 Wrangler 설정 파일이 개발자별 커스텀 환경이 많은 5,000줄 넘는 규모에서, 각 개발자의 설정을 만들어 내는 팩토리 파일로 40% 압축됐다고 적었다. 사례는 내부 파일 일부에 대한 서술이다.

이 40% 는 외부 프로젝트에 그대로 적용될 수치가 아니다. 문장이 무엇을 기준으로 40% 인지, 예를 들어 줄 수인지 파일 크기인지는 발표문 문장만으로는 확정되지 않는다. 설정의 타입화가 에이전트의 작업 성공률을 얼마나 올리는지도 원문에 수치가 없다.

Wrangler 와의 관계와 cf migrate

기존 Workers 프로젝트를 가진 쪽에서 가장 궁금한 것은 이전 절차다. 블로그가 밝힌 관계는 세 갈래다. 이전 명령은 cf migrate 이고, 변환 결과는 프로젝트의 빌드 방식에 따라 갈리며, 베타가 끝난 뒤에도 Wrangler 는 일정 기간 유지보수된다.

프로젝트 상태cf 의 동작(원문)이 글의 해설
이미 Vite 로 빌드하는 Workercloudflare.config.ts 로 변환된다변환 후 설정이 TypeScript 로 바뀌므로 diff 를 검토 대상으로 삼는다
Wrangler 의 esbuild 에 의존하는 Workercf 가 빌드를 계속 Wrangler 에 위임한다Wrangler 를 당분간 함께 유지해야 하는 구성이다
정적 사이트설정 파일 없이 시작하며 cf deploy 로 배포한다신규 정적 프로젝트의 진입 장벽이 낮다
베타 종료 이후Wrangler 를 18개월간 유지보수한다18개월이 이전 유예 기간의 상한이다
  • 이전은 명령 하나로 시작한다. 원문이 안내하는 이전 진입점은 cf migrate 다. 변환 대상이 무엇인지는 프로젝트의 빌드 방식이 정한다.
  • Wrangler 는 즉시 사라지지 않는다. 베타가 끝난 뒤 18개월의 유지보수가 약속되어 있다. 이 문장은 이전할 시간을 준다는 취지로 적혀 있다.
  • 완전 이전이 아닌 혼합 구성이 있다. esbuild 에 의존하는 Worker 는 cf 를 쓰면서도 빌드는 Wrangler 에 남는다. 이전 후에도 두 도구가 공존한다.

베타 기간의 이전은 되돌릴 방법을 먼저 정해 두는 편이 안전하다. 해설이지만, 설정 파일을 버전 관리에 두고 변환 결과를 별도 브랜치에서 검토하면 원상 복구가 간단하다. 이 글은 삭제나 배포 같은 상태 변경 명령을 예로 들지 않는다.

18개월이라는 기간은 이전 계획을 세우는 기준선이 된다. 베타가 끝나는 시점이 정해지지 않았으므로 18개월의 시작점도 미정이다. 그래서 일정표에 넣을 수 있는 것은 날짜가 아니라 순서다. 먼저 Vite 로 빌드하는 프로젝트부터 변환 결과를 검토하고, esbuild 에 의존하는 프로젝트는 Wrangler 를 함께 두는 구성으로 남기며, 베타 종료 공지가 나오면 남은 프로젝트의 이전 시점을 그때 정한다.

에이전트 작업 흐름으로 그려 보기 - 조회에서 변경 검토까지

앞의 절들은 기능을 하나씩 나눠 보았다. 이 절은 그 기능들을 하나의 작업 흐름으로 이어 붙여 본다. 아래는 원문에 있는 기능만 사용해 그린 해설용 시나리오이며, 실제 cf 의 동작을 시연한 기록이 아니다. 삭제나 배포처럼 상태를 바꾸는 단계는 일부러 뺐다.

  1. 첫 도움말 실행. 에이전트가 cf 의 --help 를 처음 실행하면 cf cli search 라는 진입점이 자동으로 안내된다. 사람이 프롬프트에 명령 목록을 붙여 넣을 필요가 없다는 것이 이 설계의 첫 이점이다.
  2. 자연어로 후보 묻기. 에이전트가 하려는 일을 문장으로 물으면 API 설명과 파라미터를 바탕으로 한 명령 후보 목록이 돌아온다. 후보는 여러 개일 수 있고, 이 목록이 다음 결정의 재료가 된다.
  3. 조회성 명령만 고르기. 사람이 정해 둔 규칙으로, 후보 가운데 상태를 바꾸지 않는 명령만 실행하게 한다. 원문에는 명령이 조회인지 변경인지 구분해 주는 기능이 언급되지 않으므로 이 구분은 사용하는 쪽의 규칙이다.
  4. 압축된 JSON 읽기. 실행 결과는 에이전트용으로 압축된 JSON 으로 돌아온다. 같은 결과를 사람이 보고 싶다면 같은 명령이 보기 좋게 정리된 형태로 출력한다.
  5. 설정 변경은 타입 검사 뒤에. 설정이 필요한 변경은 cloudflare.config.ts 에서 하고, 편집기의 타입 검사와 자동완성이 알려 주는 오류를 먼저 해결한다. 적용하기 전에 사람이 변경분을 검토하는 단계를 마지막에 둔다.

이 흐름에서 cf 가 맡는 부분은 명령 발견과 출력, 설정의 검사이고, 무엇을 허용할지의 판단은 맡지 않는다. 판단은 사람이 정한 규칙과 검토 단계에 남는다. 발표문은 그 판단 계층에 관한 기능을 언급하지 않았다.

흐름을 이렇게 나누면 병목이 어디에 생기는지도 보인다. 명령이 수천 개인 도구에서 병목은 명령이 부족한 데 있지 않고 어떤 명령을 어떤 조건에서 허용할지 정하는 데 있다. 에이전트가 쓸 수 있는 명령의 범위를 넓히는 일과 그 범위 안에서 허용 목록을 좁히는 일은 함께 가야 한다. 명령 범위를 넓히는 것은 도구가 하고, 좁히는 것은 운영자가 한다.

도입 전에 점검할 것과 베타의 한계

설계 의도가 그럴듯하다는 것과 운영에 올려도 된다는 것은 다른 문제다. cf 는 발표 시점에 공개 베타이며, 아래는 도입 전에 스스로 답해 볼 점검 항목이다. 항목마다 원문이 말하는 것과 말하지 않는 것을 나눴다.

  • 패키지 이름 확인. 설치 명령은 npm i -g cf 다. 이름이 두 글자라 다른 패키지와 혼동될 수 있으므로 README 를 낸 저장소가 cloudflare/cf 인지 확인한 뒤 설치한다.
  • 베타의 범위. 공개 베타이므로 명령과 출력 형식이 바뀔 수 있다. 어떤 명령이 안정 단계인지 원문에 구분이 없으므로 에이전트 스크립트가 출력 필드에 의존한다면 버전을 고정한다.
  • 읽기 전용부터. 에이전트에게 처음 맡기는 작업은 조회처럼 상태를 바꾸지 않는 것이 좋다. 검색으로 고른 명령이 삭제나 변경 명령일 수 있으므로 실행 전에 사람이 확인하는 단계를 둔다.
  • 자격 증명의 범위. 명령이 수천 개라는 것은 에이전트가 쓸 수 있는 권한의 폭이 넓다는 뜻이기도 하다. 토큰은 필요한 범위로 좁힌다. 자격 증명 설계는 CLI 인증 가이드에서 다뤘다.
  • Wrangler 의존 확인. 프로젝트가 esbuild 에 의존하는지 먼저 본다. 그렇다면 cf 로 이전해도 Wrangler 가 남는다.

같은 회사의 다른 발표와의 관계는 각각의 글에서 다뤘다. 에이전트 런타임 쪽은 Cloudflare OS 글, Vite 팀 합류는 VoidZero 합류 글을 참고한다. 명령을 미리보기 없이 실행하지 않는 설계는 --dry-run 설계 글이 정리했다.

점검 항목 가운데 상당수는 실행하지 않고도 답할 수 있다. 패키지 이름과 저장소 확인, 프로젝트의 빌드 방식 확인, 토큰 범위 검토는 모두 읽기만으로 끝난다. 실행이 필요한 것은 검색과 출력 형식을 직접 확인하는 일뿐이며, 그것도 조회성 명령 하나면 충분하다. 도입 판단에 필요한 정보의 대부분이 이렇게 상태를 바꾸지 않는 확인으로 얻어진다는 점이 베타 도구를 다룰 때의 안전한 출발점이다.

확인하지 못한 것

  • 「3,000 이상」이라는 작업 수. 블로그 원문 문장은 「수천 개」이고, 정확한 개수는 README 에도 블로그에도 없다. 3,000 이라는 값은 GeekNews 요약에만 있다.
  • cf cli search 의 검색 정확도와 실제 출력 예. 원문은 동작 방식만 설명하고 질의별 결과나 실패율을 제시하지 않았다.
  • JSON 출력의 스키마와 압축 수준. 필드 구성이나 사람용 대비 절감 비율은 원문에 없다.
  • 설정 40% 압축의 기준. 5,000줄이 넘던 내부 설정이 무엇 대비 40% 줄었는지, 줄 수인지 크기인지 문장만으로 확정되지 않는다.
  • 공개 베타 종료 시점과 정식 출시일. 베타 종료 이후 18개월이라는 기간만 있고 종료일은 밝혀지지 않았다.
