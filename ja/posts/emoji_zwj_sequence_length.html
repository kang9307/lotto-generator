絵文字1つが11文字と数えられる - ZWJシーケンスと文字数検証

文字列の長さは1つではない。5つの数のうち何を数えるべきかを決める方法

2026-07-30 開発・インフラ

序論: 「20文字制限」が絵文字1つで破られる

ニックネームの入力欄に「最大20文字」と書かれている。ユーザーが12文字を書き、絵文字を2つ付けた。画面のカウンターは14を表示するのに、保存ボタンを押すと「20文字を超えています」が出る。ユーザーは14文字を数え、サーバーは別のものを数えた。

この報告は再現できないと言われて閉じられやすい。開発者が自分の名前でテストすれば問題が起きないからだ。そしてそれこそが、このバグが何年も生き延びる理由だ。

原因は1つだけだ。文字列の長さは1つではない。

  • UTF-8バイト — 保存と転送が見る数
  • UTF-16コードユニット — JavaScriptの.lengthが返す数
  • コードポイント — Pythonのlen()が返す数
  • 書記素クラスタ — 人が数える「1文字」
  • 表示幅 — 画面で占めるセル数

5つだ。そしてほとんどの入力ではこの5つの数がすべて同じになる。英数字だけが入ってくるならhello worldはどの物差しで測っても11だ。ハングルが入るとバイトだけが分かれる。絵文字が入ってきた瞬間、5つがすべてばらける。

「20文字制限」という文はこの5つのうちどれなのかを書いていないので仕様ではない。この記事は5つの数を実際に数えて見せ、最後に目的別に何を数えるべきかを決める表を置く。結論は「絵文字を禁止しなさい」ではない。

実行環境。以下のすべての出力はWindows 10 Pro (10.0.19045)で実際に実行した結果だ。ランタイムはNode.js v22.16.0 (win32/x64, V8 12.4, ICU 77.1, Unicode 16.0)とPython 3.13.3 (unicodedata 15.1.0)である。Intl.Segmenterは利用可能で、Python側のサードパーティregexモジュールはインストールされていなかった。無いものは無いと書いた。

コードポイントはU+XXXXで併記する。この記事の題材が絵文字なので、ブラウザや端末がグリフを描けなければ何も確認できない。だからすべての標本にコードポイントの一覧を併記する。実際の検証でも、目で見た形ではなく16進の出力で判断した。文字列はすべてString.fromCodePointとchr()でコードポイントから組み立て、ソースのリテラルと一致するか照合して確認した。

この記事が扱わないこと。ハングルがUnicodeの中で2通りのコードポイント列になる正規化の原理はNFCとNFDで扱った。ここでは5節で長さが分かれるという数だけを示す。文字セットを読み違えて文字が壊れるエンコーディング診断はcp949とUTF-8にあり、8節ではバイト長だけを扱う。ハングル音節を正規表現の範囲で扱う算術はハングル正規表現の罠にあり、7節は絵文字に対するドットとフラグだけを見る。

  • ピクトグラフ4つがそれぞれUTF-16コードユニットを2個占める。U+1F468のような文字はU+FFFFより上にあるので、UTF-16では1枠に収まらない。2つのコードユニット(サロゲートペア)で表現される。4かける2は8
  • 接着剤のU+200D 3つがそれぞれ1個を占める。この文字はU+FFFFより下なので1枠に収まる。8足す3で11

  • 書記素クラスタは1だ。Unicode標準附属書29が定めた規則で分割した結果であり、人が数える数と同じだ

2. ZWJが接着剤だ - U+200Dを抜くと1つが4つになる

この記事のタイトルにあるZWJはU+200D ZERO WIDTH JOINERだ。幅が0の目に見えない文字で、やることは前後のピクトグラフを1つにくっつけることだ。本当にそうなのか抜いてみればいい。

with    U+200D : cps=7  units=11  bytes=25  graphemes=1
without U+200D : cps=4  units=8   bytes=16  graphemes=4
without U+200D code points : U+1F468 U+1F469 U+1F467 U+1F466
grapheme split             : [U+1F468] [U+1F469] [U+1F467] [U+1F466]

one glue character removed -> 1 grapheme becomes 4.
the utf-8 byte count only dropped from 25 to 16.

接着剤を3つ抜いたら書記素が1から4になった。画面で一塊に見えていた家族が、男性・女性・女の子・男の子の4つに散らばる。ところがバイトは25から16に少し減っただけだ。この対比が重要だ。保存容量で見れば大きな変化がないのに「文字数」は4倍になった。

鎖を1つずつ伸ばしていくと構造がさらにはっきりする。

growing the chain, one link at a time:
  cps units bytes graphemes  code points
  ----------------------------------------------------------------------
  1    2     4      1          U+1F468
  2    3     7      1          U+1F468 U+200D
  3    5     11     1          U+1F468 U+200D U+1F469
  5    8     18     1          U+1F468 U+200D U+1F469 U+200D U+1F467
  7    11    25     1          U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466

note row 2: U+1F468 U+200D is a DANGLING joiner, an invalid sequence,
and it still counts as 1 grapheme.
  • 書記素はずっと1のままだ。コードポイントが1から7へ、バイトが4から25へと6倍以上に増える間、人が数える数は変わらない
  • 2行目が実務で重要だ。U+1F468 U+200Dは何もつないでいない接着剤がぶら下がった状態だ。Unicodeの仕様上は有効なシーケンスではないが書記素の数は依然として1で、どの層でもエラーにならない
  • この状態は文字列を切ったときに実際に発生する。5節でその地点を見る
  • 附属書29の規則GB11がこの挙動を定義している。ピクトグラフと接着剤とピクトグラフの間では分割しないという規則だ。だからぶら下がった接着剤も前の文字にくっつく

Unicode技術標準51はこの方式をemoji ZWJ sequenceと呼び、実装がこのシーケンスを1つのグリフとして扱うための仕組みだと説明する。つまりこれはバグでも副作用でもなく設計された挙動だ。絵文字を増やすには新しいコードポイントを作り続けなければならないが、接着剤を使えば既存の文字を組み合わせて新しい絵を作れる。その代償が長さの爆発である。

3. 肌の色と国旗 - くっついて1つになる別の方式

接着剤のほかにも、複数のコードポイントが1つにまとまる方式があと3つある。それぞれ確認した。

3.1 肌の色の修飾子は別のコードポイントだ

label                  cps  units  bytes  graphemes  code points
------------------------------------------------------------------------------
thumbs up bare         1    2      4      1          U+1F44D
thumbs up tone-2       2    4      8      1          U+1F44D U+1F3FC
thumbs up tone-3       2    4      8      1          U+1F44D U+1F3FD
thumbs up tone-5       2    4      8      1          U+1F44D U+1F3FF
modifier alone         1    2      4      1          U+1F3FD
man + tone-3           2    4      8      1          U+1F468 U+1F3FD

toned couple with a variation selector - the realistic worst case:
  U+1F468 U+1F3FB U+200D U+2764 U+FE0F U+200D U+1F469 U+1F3FF
  cps=8  units=12  bytes=28  graphemes=1
  U+FE0F is VARIATION SELECTOR-16, 3 more bytes that draw nothing.
  • 肌の色は元の文字に色を塗るのではない。後ろに修飾子のコードポイントをもう1つ付ける。だから長さがちょうど2倍になる。コードポイントは1から2、バイトは4から8
  • 5段階のどれを付けても長さは同じだ。U+1F3FBからU+1F3FFまですべて4バイトである
  • 修飾子は単独でも1つの書記素だ。土台の文字なしにU+1F3FDだけが残ると、色見本のようなものが描かれる
  • 最後の標本が実務で出会う最悪に近い。肌の色2つに接着剤2つ、そしてU+FE0Fが付いてコードポイント8個、28バイトが1文字だ
  • U+FE0FはVARIATION SELECTOR-16だ。前の文字を絵の形で描けという指示にすぎず何も描かないまま3バイトを使う。長さの計算でよく抜け落ちる値である

3.2 国旗は地域表示文字2つだ

label        cps  units  bytes  graphemes  code points
----------------------------------------------------------------------
KR flag      2    4      8      1          U+1F1F0 U+1F1F7
JP flag      2    4      8      1          U+1F1EF U+1F1F5
US flag      2    4      8      1          U+1F1FA U+1F1F8

a single regional indicator U+1F1F0 alone:
  cps=1  units=2  bytes=4  graphemes=1
  it is not half a flag - it is a boxed letter K.

pairing is greedy, left to right:
  2 RI  U+1F1F0 U+1F1F7   graphemes=1   [U+1F1F0 U+1F1F7]
  3 RI  + U+1F1FA         graphemes=2   [U+1F1F0 U+1F1F7] [U+1F1FA]
  4 RI  + U+1F1F8         graphemes=2   [U+1F1F0 U+1F1F7] [U+1F1FA U+1F1F8]

deleting ONE regional indicator re-pairs everything after it.

tag sequence flag (black flag + 5 tag letters + terminator):
  U+1F3F4 U+E0067 U+E0062 U+E0073 U+E0063 U+E0074 U+E007F
  cps=7  units=14  bytes=28  graphemes=1

国旗には専用のコードポイントがない。アルファベットに対応する地域表示文字を2つ並べるとレンダラが国旗として描く。韓国の国旗はKに当たるU+1F1F0とRに当たるU+1F1F7だ。

  • 1つだけ残しても半分の国旗にはならない。四角の中に入った文字Kが見える。データとしては完全に有効な1つの書記素だ
  • ペアリングは左から貪欲だ。3つ置くと前の2つが国旗になり、3つ目は単独で残る。附属書29の規則GB12とGB13が奇数番目の前でだけ分割すると定義した結果だ
  • だから真ん中の1つを消すと、後ろにあった国旗がすべて別の国に変わる。国旗を複数使う入力では、バックスペース1回がこれをやってのける
  • 最後の標本はタグシーケンスだ。黒い旗1つにタグ文字5つと終端子が付いてコードポイント7個、28バイトが1文字だ。国の下位地域の旗がこの方式を使う
  • 技術標準51は有効な国旗シーケンスは仕様のデータファイルに登録されたものだけだと明記している。つまり任意の2文字をくっつけても国旗にはならず、文字2つに見える

絵文字が長くなる方式をまとめると4つだ。

4. 絵文字だけの問題ではない - ハングルNFDと結合アクセント

ここまで読んで「絵文字を禁止すればいい」と考えたくなる。ところが絵文字がなくても長さは分かれる。確認してみた。

label              .length  cps  bytes  graphemes  code points
--------------------------------------------------------------------------------
hangul NFC         1        1    3      1          U+D55C
hangul NFD         3        3    9      1          U+1112 U+1161 U+11AB
hangul x2 NFC      2        2    6      2          U+D55C U+AE00
hangul x2 NFD      6        6    18     2          U+1112 U+1161 U+11AB U+1100 U+1173 U+11AF
e-acute NFC        1        1    2      1          U+00E9
e-acute NFD        2        2    3      1          U+0065 U+0301
3 stacked marks    4        4    7      1          U+0065 U+0301 U+0323 U+0304

NFC === NFD for the same visible text : false
  .length 2 vs 6   bytes 6 vs 18   graphemes 2 vs 2
no emoji involved. the split between units and graphemes is already there.

数だけ読めばいい。画面に同じ2文字として見えるものが、一方は.lengthが2、もう一方は6だ。バイトは6対18で3倍の差がある。ところが書記素は両方とも2だ。

  • 同じ文字が合成済みのコードポイント1つでも、字母3つでも表現される。どちらも有効なUnicodeだ
  • なぜこうなるのかの原理と、どこで発生するのかはこの記事の範囲外だ。NFCとNFDにまとめてある。ここでは長さが分かれるという事実だけが必要だ
  • ラテン文字も同じだ。U+00E91つとU+0065 U+03012つが画面では同じ文字に見える
  • 結合文字には個数の制限がない。3つ重ねても書記素は1で、後で見るように200個重ねても1だ
  • 結論が重要だ。コードユニットと書記素が分かれる現象は絵文字が作ったものではない。絵文字はその差を25倍まで広げて目に見えるようにしただけだ

附属書29がこの問題を正面から述べている。1つのコードポイントがユーザーの考える「1文字」と常に同じとは限らないということであり、文書が挙げる例も文字にアクセントを結合した場合だ。書記素クラスタはその差を埋めるために定義された単位である。

5. 切り詰め事故 - 20文字だけ残すと絵文字が半分に割れる

ここで序論の症状を再現する。標本のニックネームはDevTeam01の後ろに空白、家族の絵文字、2026を付けたものだ。絵文字が1つ入っただけの平凡なニックネームである。

code points  : U+0044 U+0065 U+0076 U+0054 U+0065 U+0061 U+006D U+0030 U+0031
               U+0020 U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466
               U+0032 U+0030 U+0032 U+0036

  utf-8 bytes            : 39
  utf-16 code units      : 25
  code points            : 21

the rule says "at most 20 characters". which number is that?

同じニックネームが3回拒否され、1回通過する。ユーザーが数える方式(書記素)では15文字なので余裕があるのに、サーバーが.lengthを使うと25で拒否する。序論の報告がまさにこれだ。

最後のコードユニットが0xD83Dだ。これは文字ではなくサロゲートペアの前半であり、相方が切り落とされている。この状態を呼ぶ名前が孤立サロゲートだ。

  • isWellFormed()がfalseを返す。このメソッドは孤立サロゲートがあるかどうかだけを見る。この記事で唯一必要な検証関数だ
  • この文字列をUTF-8でエンコードすると最後がEF BF BDになる。U+FFFD置換文字だ。元のバイトはその時点で消え、どの文字の代わりなのかという情報は残らない
  • 往復が壊れる。エンコードしてからデコードした結果が原本と違う。保存して読み直すと別の値になるという意味だ
  • substringも結果は同じだ。どちらもコードユニットを切る
  • コードポイント単位で切ると(Array.fromの後にスライス)孤立サロゲートは発生しない。ところが今度は接着剤が切れて4人家族が3人になり、書記素が14に減る。有効なデータではあるがユーザーが入力したものとは違う絵だ

5.1 コードポイント言語でも安全ではない

Pythonは文字列がコードポイントの配列なので孤立サロゲートを作れない。それでも安全ではない。

6. 反転事故 - 国旗が別の国になる

9.1 半分の絵文字は層ごとに違う反応をする

what happens to a half emoji downstream:
  JSON.stringify(lone high surrogate) : "\ud83d"
  JSON.parse of that                  : succeeds, isWellFormed=false
  encodeURIComponent(...)             : THROWS URIError - URI malformed
  Buffer.from(...,"utf8")             : EF BF BD   silently replaced by U+FFFD
  -> JSON accepts it, the URL layer throws, the byte layer corrupts it.
     three layers, three different behaviours, no error at the source.

これが診断を難しくする構造だ。発生地点では何のエラーも出ない。

  • JSONは通す。シリアライズもでき、デシリアライズも成功する。ただし結果がisWellFormed()でfalseになる
  • URLの層は例外を投げる。この地点で初めてエラーが見える。ところが切り詰めたコードとは遠く離れているので原因の追跡が難しい
  • バイトの層は黙って壊す。置換文字に変えておいて成功として報告する。最も危険な挙動だ
  • だから切った直後に検証しなければならない。isWellFormed()の1行が3つの層の問題を発生地点で捕まえる

11.2 SMSの課金はまた別の物差しだ

  --------------------------------------------------------------
  ascii only                 GSM-7     93     93         1
  + 1 grinning               UCS-2     95     94         2
  + 1 KR flag                UCS-2     97     94         2

  the ascii message is 93 characters, GSM-7, ONE segment (limit 160).
  adding ONE emoji forces UCS-2, where the limit is 70 units.

  ascii or ideographs   70 of them
  grinning              35 of them
  KR flag               17 of them
  thumb + tone          17 of them
  family                6 of them

  • ASCIIだけならGSM-7でエンコードされ、1セグメントが160文字だ。93文字のメッセージは1セグメントである
  • 非ASCII文字が1つでも入るとメッセージ全体がUCS-2に変わる。その瞬間、1セグメントの上限が70ユニットに減る
  • だから絵文字を1つ付けたら93文字のメッセージが2セグメントになった。ユーザーは1文字足したと思っているのに料金は2倍だ
  • 1セグメントに入る家族の絵文字は6個だ。ユーザーの目には6文字なのに、それでSMS1通が埋まる
  • ここで数えるべきものはUTF-16コードユニットだ。書記素で数えると料金の計算が狂う

同じ絵文字1つを6つの物差しで測るとこうなる。

物差し👨‍👩‍👧‍👦 の値この数が正解になる場面
UTF-8バイト25カラムサイズ、ネットワーク予算、言語間の契約
UTF-16コードユニット11JavaScriptの検証、SMSの課金

1つのグリフ、6つの数。そして6つとも、ある目的に対しては正解だ。

12. 何を数えるべきか - 目的別の判断表

この記事の結論は「絵文字を禁止しなさい」ではない。あなたが数えようとしている「文字」が何なのかを決めろということだ。目的が単位を決める。

目的数えるべき単位なぜそれなのか検証方法
画面の「あとn文字」カウンター書記素人が数える数と一致しなければならない家族の絵文字1つが1と数えられるか確認
DBカラムサイズの決定バイト保存上限の単位がバイトだ最悪ケースのバイトで計算したか

表を使うときの核心は3行目だ。実務の入力検証は単位を1つだけ選ぶ問題ではない。表示用と保存用を別に置き、両方を検査しなければならない。この2つを1つにまとめようとする試みが序論のバグを作る。

  • 仕様書に単位を書け。「ニックネームは最大20文字」ではなく「ニックネームは最大20書記素、保存の上限80バイト」と書く
  • フロントとバックエンドが同じ単位を使っているか、同じ標本で確認せよ。言語が違えばlengthの意味が違う
  • 拒否メッセージに単位と超過量を入れろ。「20文字を超えています」は15文字を数えたユーザーには無意味だ
  • 切らずに拒否せよ。黙って切るとデータが損傷し、ユーザーは気づかない。切るしかないなら書記素単位で切って検証する
  • 保存の層が4バイト文字を受け取るか先に確認せよ。長さの計算が合っていても、ここで止められれば全部無意味だ

13. 静かに通り過ぎる理由とテスト標本

最後にこのバグの性質を整理する。なぜ何年も生き延びるのか。

  • ほとんどの入力で5つの数が同じだ。ASCII 11文字はバイト・コードユニット・コードポイント・書記素がすべて11だ。開発者が自分の名前でテストすれば何の問題も起きない
  • 再現の条件が狭い。特定の種類の絵文字、特定の長さ、特定の切り詰め地点が揃って初めて爆発する。報告が「再現不可」で閉じられる
  • 失敗が静かだ。孤立サロゲートはJSONを通り抜け、置換文字はエラーなしに保存される。ログに何も残らない
  • 見える場所と爆発する場所が遠い。切ったコードと例外を投げるURLの層が別のモジュールだ
  • 目視で検査しても捕まらない。U+200Dの残骸とU+FEFFは画面に何も描かない

だから必要なのは標本だ。テストデータに以下を入れれば、この記事のすべての事故が開発の段階で捕まる。

  • ZWJシーケンス — U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466 (書記素1、コードユニット11、バイト25)
  • 国旗 — U+1F1F0 U+1F1F7と国旗を3つ連続で置いた標本 (ペアリングの再編成の確認)
  • 肌の色の修飾子 — U+1F44D U+1F3FD
  • U+FE0Fの入ったシーケンス — 幅0の3バイトが計算から漏れないか
  • ハングルNFD — U+1112 U+1161 U+11AB (書記素1、コードポイント3)
  • 結合アクセント — U+0065 U+0301とマークを複数重ねた標本
  • タグシーケンス — 近似の正規表現が外すことを確認する標本
  • 孤立サロゲートの入った文字列 — 検証関数が実際に捕まえるか確認
  • 境界の長さの標本 — 上限の直前、上限、上限の直後で、切り詰め地点が絵文字の途中に来るよう合わせたもの
  • ASCIIだけの標本 — 対照群として。ここではすべての単位が同じでなければならない

最後の項目が意外に重要だ。ASCII標本だけを通すテストは何も検証していない。5つの数が同じ区間でだけ確認したものだからだ。

# 絵文字の文字数 — 5つの長さ対照表と安全な数え方・切り方

> 出典: braindetox.kr — 絵文字1つが11文字と数えられる
> 根拠: Windows 10 / Node.js v22.16.0 (ICU 77.1, Unicode 16.0) / Python 3.13.3 の実行検証
> このファイルをそのままAIに貼って「この基準でうちの入力検証を点検して」と書けば使えます。
> ⚠ 結論から: 「20文字制限」は文ではなく、**単位を書いて**はじめて仕様になります。

## 0. 30秒まとめ

文字列の長さは**1つではない。**同じ絵文字1つ(👨‍👩‍👧‍👦)を数えると数がこう分かれる。

| 単位 | 値 | この数を見る場所 |
|---|---|---|
| UTF-8バイト | 25 | DB保存、ネットワーク、Go・Rustのlen |
| UTF-16コードユニット | 11 | JavaScript `.length`、Java、C#、SMSのUCS-2 |
| コードポイント | 7 | Python `len()`、Swift `unicodeScalars` |
| 書記素クラスタ | 1 | 人が数える「文字」、カーソル移動、バックスペース |
| 端末の表示幅 | 2 (レンダラが対応しているとき) | 等幅の桁揃え、表のレイアウト |

ほとんどの入力ではこの5つの数が同じだ。**絵文字が入ってきた瞬間にだけ分かれる。**だから静かに通り過ぎて、ある日爆発する。

|---|---|---|---|---|
| `hello world` | 11 | 11 | 11 | 11 |
| 漢字 (U+6F22 U+5B57) | 6 | 2 | 2 | 2 |
| é NFC (U+00E9) | 2 | 1 | 1 | 1 |
| é NFD (U+0065 U+0301) | 3 | 2 | 2 | 1 |

最後の行が核心だ。**「20文字以下」の規則にこのニックネームを入れると、どの単位で数えるかによって結果が分かれる。**

- バイトで数えれば 39 → 拒否
- UTF-16で数えれば 25 → 拒否
- コードポイントで数えれば 21 → 拒否
- 書記素で数えれば 15 → 通過

## 2. 絵文字が長くなる4つの方式

| 方式 | 構造 | 例 | コードポイント |
|---|---|---|---|
| ZWJシーケンス | ピクトグラフの間にU+200D | 👨‍👩‍👧‍👦 | 7 |
| 修飾子シーケンス | 土台 + 肌の色修飾子 | 👍🏽 | 2 |
| 国旗シーケンス | 地域表示文字2個 | 🇰🇷 | 2 |
| タグシーケンス | 黒い旗 + タグ文字 + 終端子 | スコットランドの旗 | 7 |

- **U+200D(ZWJ)が接着剤だ。**4人家族からU+200Dを3つ抜くと書記素が1から**4に**増える。バイトは25から16に少しだけ減る
- **U+FE0F(VS16)は幅0の3バイト**だ。何も描かないまま長さを増やす
- **国旗のペアリングは左から貪欲**だ。地域表示文字を1つ消すと、その後ろが全部あらためてペアになる
- 肌の色・国旗・タグもすべて書記素1個だ

## 3. 目的別に数えるべき単位

**この表がこの文書の核心だ。**「何を数えるか」は要件が決める。

| 目的 | 数えるべき単位 | 理由 | 検証方法 |
|---|---|---|---|
| ユーザーに見せる「あとn文字」 | **書記素** | 人が数える数と一致する | 絵文字1個を1と数えるか確認 |
| DBカラムサイズの決定 | **バイト** | 保存の上限はバイトだ | 最悪ケースのバイトで計算 |
| 入力フォームのハードリミット | **バイトと書記素の両方** | 表示用と保存用が違う | 2つの条件を両方掛けろ |
| SMSの課金 | **UTF-16コードユニット** | UCS-2セグメントはユニット単位 | 70ユニット(連結時67)の境界 |
| 等幅画面のレイアウト | **表示幅** | セル数がレイアウトを決める | 実際のフォントで目視確認 |
| 言語間のAPI契約 | **バイト** | 唯一すべての言語で同じ | 両側で同じ数が出るか |
| ログ・ハッシュ・重複検査 | **正規化後のバイト** | NFC/NFDは違うバイトだ | 正規化を先に |

## 4. すぐ使えるコード (JavaScript)

`Intl.Segmenter`はNode 16以上と最新のブラウザで使える。検証環境(Node v22.16.0, ICU 77.1)で正常動作を確認した。

```js
const seg = new Intl.Segmenter('ko', { granularity: 'grapheme' });

// 数える — 絵文字1つを1と数える
function countGraphemes(s) {
  return [...seg.segment(s)].length;
}

// 切る — 絵文字を絶対に半分に割らない
function sliceGraphemes(s, n) {
  return [...seg.segment(s)].slice(0, n).map(function (x) { return x.segment; }).join('');
}

// 反転する — 国旗が別の国にならない
function reverseGraphemes(s) {
  return [...seg.segment(s)].map(function (x) { return x.segment; }).reverse().join('');
}

// バイト基準で切る — カラムの上限を守りつつ絵文字を保つ
function sliceByBytes(s, maxBytes) {
  const enc = new TextEncoder();
  let outStr = '';
  let used = 0;
  for (const part of seg.segment(s)) {
    const n = enc.encode(part.segment).length;
    if (used + n > maxBytes) break;
    outStr += part.segment;
    used += n;
  }
  return outStr;
}

// 検証 — 孤立サロゲートが混じっていないか
function isIntact(s) {
  if (typeof s.isWellFormed === 'function') return s.isWellFormed();
  const paired = s.replace(/[\uD800-\uDBFF][\uDC00-\uDFFF]/g, '');
  return !/[\uD800-\uDFFF]/.test(paired);
}
```

**確認された挙動**

- `countGraphemes` で 👨‍👩‍👧‍👦 を数えると **1**
- `DevTeam01 👨‍👩‍👧‍👦2026` を12書記素で切ると絵文字が無傷で `isWellFormed()` が true
- 同じ文字列を `.slice(0, 20)` で切ると `isWellFormed()` が **false**、UTF-8エンコード時に最後が `EF BF BD`(U+FFFD)になる

## 5. Intl.Segmenter が無い環境

正規表現の近似が使える。**完全ではないと知って使え。**

```js
const RX = new RegExp(
  '(?:\\p{RI}\\p{RI})' +
  '|(?:\\p{Extended_Pictographic}(?:\\p{Emoji_Modifier}|\\uFE0F)?' +
  '(?:\\u200D\\p{Extended_Pictographic}(?:\\p{Emoji_Modifier}|\\uFE0F)?)*)' +
  '|(?:\\P{M}\\p{M}*)|.', 'gu');

```

実測の精度

| 対象 | 近似値 | 正解 |
|---|---|---|
| 👨‍👩‍👧‍👦 | 1 | 1 |
| 🇰🇷 | 1 | 1 |
| 👍🏽 | 1 | 1 |
| `DevTeam01 👨‍👩‍👧‍👦2026` | 15 | 15 |

絵文字は当てるが**ハングルNFDとタグシーケンスで外す。**UAX #29 は規則が16個なのにこの正規表現は4個だ。近似は代替品ではない。

## 6. Python 側

- `len()` は**コードポイント**を数える。👨‍👩‍👧‍👦 は **7**だ。JavaScript の 11 と違う
- 標準ライブラリに**書記素APIが無い。**検証環境で確認: `hasattr(str, 'graphemes')` は False、標準の `re` は `\X` を拒否(`PatternError: bad escape \X`)
- サードパーティ `regex` モジュールの `\X` が必要だ。検証環境には**インストールされていなかった**
- スライシングは孤立サロゲートを作らないが**ZWJの鎖はそのまま断ち切る。**`NICK[:16]` は最後がU+200Dの「何もつないでいない接着剤」になる

```python
# 書記素が必要ならサードパーティのモジュールが要る
import regex
def count_graphemes(s):
    return len(regex.findall(r'\X', s))

# バイトの上限を守りながら切る (標準ライブラリだけ)
def slice_by_bytes(s, max_bytes):
    b = s.encode('utf-8')[:max_bytes]
    return b.decode('utf-8', 'ignore')   # 境界で切れた断片は捨てる
```

`decode(..., 'ignore')` は切れた断片を黙って捨てる。ログが必要なら `strict` で捕まえて自分で処理せよ。

## 7. 保存・転送の層の計算

- 絵文字はすべて **U+FFFFより上**にある。U+FFFF はUTF-8で3バイト、U+10000 は **4バイト**だ
- 1文字あたり最大3バイトまでしか受け取らない文字セットは**絵文字を1つも収められない。**検証では cp949 と shift_jis の両方が 😀 を拒否した(`UnicodeEncodeError`)
- 「20文字」をバイトに換算するときは**必ず最悪ケースで**取れ

| 「20文字」の意味 | 必要なUTF-8バイト |
|---|---|
| 20コードポイント | 最大80 |
| 20書記素 (家族の絵文字) | 500 |
| 20書記素 (結合文字200個ずつ) | 8,020 |
| 20書記素 (一般) | **上限なし** |

**書記素でカラムサイズを取るな。**書記素1つに入るコードポイントの個数には上限がない。

## 8. JSON・URL の膨張率

| 変換 | 結果 | 倍率 |
|---|---|---|
| 👨‍👩‍👧‍👦 UTF-8 | 25バイト | 1.0x |
| JSON `{"nick":"..."}` UTF-8 | 36バイト | — |
| JSON ASCIIエスケープ | 77バイト | 2.14x |
| `encodeURIComponent` | 75 ASCII文字 | 3.0x (1バイトあたり3) |
| Base64 | 36文字 | 1.44x |

- JSON の `\u` エスケープはUTF-16基準なので、**U+1F468 1つがエスケープ2つ**(`\uD83D` と `\uDC68`)になる
- URLクエリの長さ予算が2048なら、20書記素の家族文字列は**1つ**しか入らない
- 孤立サロゲートは層ごとに違う反応をする: JSON は**通し**、`encodeURIComponent` は**URIErrorを投げ**、UTF-8エンコードは**黙ってU+FFFDに変える**。発生地点では何のエラーも出ない

## 9. SMSの課金 (別の規則)

- ASCII だけなら GSM-7、1セグメント **160文字**
- 非GSM文字が**1つでも**入ると全体が UCS-2 に変わり、1セグメント **70ユニット**(連結時67)
- 実測: 93文字のASCIIメッセージは GSM-7 で1セグメント。**絵文字を1つ付けると UCS-2 に切り替わって2セグメント**になる
- 1セグメント(70ユニット)に入る個数: 一般の文字70個 / 😀 35個 / 🇰🇷 17個 / 👨‍👩‍👧‍👦 **6個**

ユーザーは「1文字」足したと思っているのに料金は2倍になる。

## 10. 正規表現で絵文字を遮断しようとするとき

| パターン | 👨‍👩‍👧‍👦 のマッチ回数 |
|---|---|
| `/./g` | 11 |
| `/./gu` | 7 |
| `/./gv` | 7 |
| `\p{Emoji}` | 4 |
| `\p{Emoji_Presentation}` | 4 |
| `\p{Extended_Pictographic}` | 4 |
| `\p{RGI_Emoji}` (v フラグ) | **1** |

- `u` フラグが無ければ `.` が**コードユニット**を数える。11回マッチする
- `u` フラグを付けるとコードポイント単位になって7回だ。**依然として1ではない**
- 1つとして数えるには **`v` フラグと `\p{RGI_Emoji}`** が必要だ。検証環境では両方とも対応していた
- `\p{Extended_Pictographic}` で消すと **U+200D が3つ残る。**目に見えない残骸だ
- `\p{Emoji}` は**数字と `#`、`*` もマッチする。**これで絵文字を遮断すると注文番号が拒否される

- [ ] 検証失敗のメッセージが、ユーザーに**どの単位で何文字超過か**を知らせる

## 12. やってはいけないこと

- ❌ **「絵文字を禁止しなさい」で終わらせること** — 数えたい単位を決めなければ規則は壊れ続ける
- ❌ `.length` を「文字数」と呼ぶこと — UTF-16コードユニットだ
- ❌ 書記素で **DBカラムサイズを取ること** — 上限が無い
- ❌ フロントは書記素、サーバーはバイトで数えながら**同じ数を期待すること**
- ❌ `.slice()` で切った後に**検証せず保存すること** — 孤立サロゲートが流れていく
- ❌ 配列の反転で文字列の逆順を作ること — 国旗が**別の国**になる
- ❌ `\p{Emoji}` で絵文字を遮断すること — 数字を遮断してしまう
- ❌ 正規表現の近似を**完全な書記素分割だと信じること** — ハングルNFDとタグシーケンスで外す
- ❌ テスト標本に **ASCII だけを入れること** — 5つの数が全部同じで何も捕まらない
