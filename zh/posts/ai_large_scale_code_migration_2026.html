用AI智能体做大规模代码迁移

搬运数十万行时失败发生在哪里 - 任务拆分·验证闸门·回滚单位·中止判断

2026年7月28日 开发/基础设施

引言: 「搬了一百万行」没有告诉你的事

2026年上半年开发者社区讨论最多的事件之一，是把大规模代码迁移交给AI智能体的若干案例。JavaScript运行时Bun在自家博客中披露，把用Zig写的535,496行移植到Rust，最终diff口径产生了+1,009,272行与6,502次提交，耗时11天(5月3日至14日)。据称峰值时有四个工作树各跑16个，共约64个智能体并行工作。

这类数字本身对实务毫无帮助，因为它是结果报告而不是流程。要决定是否搬迁自家用了十五年的支付模块的人，需要的不是成功故事，而是「在哪里失败、失败后要退回到哪一步、什么时候该收手」。

本文只讨论这一段。它不是从某种语言迁到另一种语言的方法，而是把一次性大批量变更这种工作形态委托给智能体时的设计。共七条轴线：①区分可委托与不可委托的迁移，②拆分任务单位的方法，③过程中的验证闸门，④部分失败时的回滚单位，⑤降低评审负担的diff设计，⑥中止判断标准，⑦成本估算。

先划清范围。如何设计检查器、如何管理误报，不是本文主题。语法层、运行时层、语义层三层检查、黄金文件以及抽样评审的统计局限，已在搭建AI产出的验收体系中另行讨论。这里只看这些检查以什么顺序、施加在什么单位、配合什么样的丢弃策略。若想了解某一特定语言迁移本身的技术判断，从Go迁移到Rust更合适。

1. 大规模自动变更并不是新鲜事

早在智能体出现之前，大型代码库就一直由机器修改。JavaScript阵营的jscodeshift把源码解析成抽象语法树(AST)，找到匹配模式的节点加以改写，并尽可能保留原有格式。Java阵营的OpenRewrite更进一步，采用称为无损语义树(Lossless Semantic Tree)的数据模型。由于它不仅保存结构，还保存类型归属与格式，因此能像编译器那样区分类型、变量与字面量。按厂商自己的说法，同一份配方每次都会产生相同的结果。

这种确定性的重要性在组织规模上才显现出来。《Software Engineering at Google》第22章讨论数十亿行代码库中的大规模变更(LSC)，并明确指出原子性的大规模提交在原理上不可能。文件数越多合并冲突的概率越高，版本控制系统与CI都无法承载单个巨型提交。因此谷歌用名为Rosie的平台，把工具生成的全局变更按所有权边界切成分片，各自独立测试、评审与提交。

同一章还给出实务者可直接采用的门槛：作为经验法则，当一次变更需要超过500处编辑时，学习并使用变更生成工具通常比手工编辑更高效，而对熟练的代码清理者来说这个数字往往更小。也就是说，「要不要自动化」早已有定论，2026年的新问题是「把自动化的哪一段交给概率模型」。

2. LLM方式的不同之处 - 填补规则够不到的区间

传统工具与智能体并非竞争关系，而是覆盖的区间不同。基于规则的转换在「这个模式变成那个模式」可以明确表述时最强。反过来，当迁移对象需要读懂上下文才能判断时，例如各语言错误处理惯用法不同，或需要照顾注释中写明的意图，规则就很难写。一条规则覆盖九成、剩下一成全是例外的情形，那条尾巴正是智能体值回成本的位置。

维度规则/AST型(codemod·配方)LLM智能体
可复现性相同输入相同输出，重跑一致相同输入每次结果也可能不同
覆盖面仅限规则写明的模式，例外全靠手工会尝试处理未被规则化的变体
前期成本集中投入在编写规则与配方规则集很薄，但每次运行都消耗令牌
失效点没有类型信息就分不清同名符号在超出上下文窗口的巨型文件上崩溃
验证需求验证规则即可信任其应用结果必须逐个验证产出物
失败形态匹配失败(什么都没发生)看似合理但语义不同的代码

最后一行在实务中最关键。规则型工具的失败是安静而安全的方向：没被匹配到的文件原样保留，且可以列成清单。智能体的失败则是不吵闹却危险的方向：能编译、能过测试，语义却有微妙偏差。Bun公开表示合并后发现19处回归并已全部修复，主因是语法一致而语义不同的翻译(断言内部带有副作用的代码在发布构建中被消除属于典型)。这类缺陷语法检查永远抓不到。

实务结论：这不是二选一的问题。能用规则表达的区间交给确定性工具推进，只把尾巴交给智能体，在成本与验证两方面都更有利。还可以让智能体撰写转换规则本身，而由确定性工具负责应用。

3. 可委托与不可委托的迁移 - 五轴判别

动工前要回答的问题不是「AI能不能做」，而是「用什么来判定它做完了」。没有答案，后面的设计都无从谈起。用以下五条轴线检查。

轴要问的问题适合委托不适合委托
①等价判定(判据)迁移之后用什么证明「一样」覆盖率高的测试、可重放的输入输出记录、黄金文件测试稀薄、只依赖人工QA
②规则性转换能否用模式描述规则覆盖大部分，例外很少每个文件的判断都不同
③语义保持是一一对应还是重新设计API名称与签名替换、类型位宽扩展并发模型、事务边界、内存模型变更
④撤销成本出错时能否恢复原状代码变更(撤销提交即可恢复)模式变更、数据迁移、外部契约变更
⑤上下文适配一个工作单位能否装进窗口文件级独立、体量普通数万行的生成文件、巨型分支块

①最重要，也是实务中最常被跳过的一条。谷歌公开的内部案例无一例外都把「能否构建」与「回归测试是否通过」钉进流水线，这并非偶然。判定手段就是自动化的上限。如果测试很薄，就要把顺序反过来：在开始迁移之前先造好判定装置。看似绕路，通常反而更快。

④经常被误解。代码容易回退，数据却回不去。若存储模式或序列化格式随代码一同变更，必须把代码轨道与数据轨道严格分开，数据侧由人以先扩展后收缩(expand-contract)的顺序掌控。可以委托给智能体的只有代码轨道。

⑤不是理论而是被观测到的失败。谷歌论文记录：当大文件的全部内容超出上下文窗口时模型无法完成修改，只能由开发者手工处理。事前把文件体量分布拉出来，把最大的百分之几先划入手工清单更稳妥。

4. 拆分任务单位 - 引用距离与依赖顺序

大批量变更首先撞上的问题是不知道该改哪里。仅仅一次改名，也可能从直接引用连锁波及到包裹这些引用的函数，乃至调用这些函数的代码。

4.1 变更位置发现

谷歌的FSE 2025论文描述了用内部代码索引系统Kythe逐层外扩的做法：先找直接引用，再找对这些引用的引用，一直收集到引用距离5为止。距离1是对字段的直接访问，距离2是包含它的方法，依此递增。论文出于实用原因把上限定在5，并明确指出更远的位置可能被遗漏。这个上限就是自动化范围的边界，遗漏部分需要人另行清扫。

没有内部索引器时，替代手段是语言服务器(LSP)的引用查找、编译器插件与构建图。字符串搜索是最后手段：它无法区分同名符号，会导致候选清单本身被污染，而这种污染会传播到后续每一个阶段。

4.2 确定顺序

  • 拓扑排序：从依赖图的叶子开始。工具函数与类型定义这类不依赖他者的先做
  • 环要成块处理：相互依赖的模块不要拆开，合并为一个分片
  • 适配层先行：先放入让新旧接口暂时共存的薄转换层，后续分片才能彼此独立提交
  • 测试代码放最后：先迁测试会动摇判定标准。判定者最后再动
  • 排除生成代码：生成器的产物要改生成器。直接改产物，下次构建就被抹掉

4.3 分片大小的标准

分片大小不由令牌预算决定，而由两个问题决定。第一，这一片单独提交能否通过构建与测试。第二，是否是人一次能审完的量。同时满足两者的最小单位就是分片，而它同时就是回滚单位。

# shards.yaml - 分片清单示例(工具中立)
- id: S-001
  scope: [lib/util/**]        # 从叶子模块开始
  depends_on: []
  rollback: revert-commit     # 撤销方式
  gate_profile: fast          # 到构建+单元测试为止
  owner: platform-team
- id: S-014
  scope: [svc/billing/handler/**]
  depends_on: [S-001, S-009]
  rollback: revert-commit+flag-off
  gate_profile: full          # 包含差分测试
  owner: billing-team
  note: 存在循环依赖，无法与S-009分离

把清单落成文件只有一个理由：让进度与回滚计划留在仓库里，而不是留在某个人的记忆里。当数百个分片连跑数日，没有人能把全局装进脑子。

5. 闸门从便宜的开始 - 失败就丢弃而不是修补

这是本文的核心。比起检查项目本身，以什么顺序摆放、以及对落选产出如何处置，才真正决定迁移的总成本。

谷歌FSE 2025论文描述的验证流水线是按成本从低到高排列的：①模型是否成功响应 → ②是否只改了空白 → ③能否通过AST解析器 → ④再确认这次变更是否真有必要 → ⑤能否构建 → ⑥回归测试是否通过。而且关键在于，任何一环失败即丢弃该变更，并把该文件标记为手工迁移对象。

顺序闸门判定耗时落选处置
1响应是否成功即时重试一次后丢弃
2diff为空或仅空白即时立即丢弃(等于没做)
3解析通过、无语法错误秒级丢弃
4格式化器与静态检查规则秒级自动纠正一次，仍失败则丢弃
5再确认变更必要性秒级判定为不必要则丢弃
6构建与类型检查分钟级自动修复一次，失败转手工
7单元与回归测试分钟级以上转手工(不去修)
8差分测试(新旧同输入)小时级列出不一致并调查
9人工评审人力时间只看走到这里的部分

新手最常犯的错误是让智能体不断修补在第6、7环落选的产出。此时成本不是线性增长而是发散：修好一个构建错误又冒出另一个，修完又把测试弄坏，为了让测试通过就滑向去改测试本身。把修复尝试限制为一次，之后就丢弃，在总成本上更划算。

被丢弃的部分如何处理，分成两种流派。谷歌把它们转入手工迁移清单。而Anthropic在自家博客整理的做法(厂商资料)则强调「不要修单个失败，要修产生这个失败的循环」：当编译错误清单中反复出现同一模式时，不去动文件，而是修改规则集并只重新生成受影响的文件。评审者反复提出同一意见时，就在规则集里加一句话再重跑批次。

两种做法的取舍标准：落选原因零散时，转入手工清单更便宜；落选原因成簇时(同一错误信息几十条)，改规则再生成更便宜。因此落选日志必须以可按原因聚合的形式留存。只留自由文本日志，连这个判断都做不了。

# 闸门流水线伪代码(工具中立)
for file in batch:
    out = agent.transform(file, rulebook_v)
    if not out.ok:                 continue        # G1 丢弃
    if out.diff.is_trivial():      continue        # G2 丢弃
    if not parser.accepts(out):    log(file,'parse'); continue          # G3
    out = formatter.fix_once(out)                                       # G4
    if agent.confirm_needed(out) is False: log(file,'punt'); continue   # G5
    if not build(out):
        out = agent.repair_once(out)
        if not build(out): manual_queue.add(file,'build'); continue     # G6
    if not tests(out):  manual_queue.add(file,'test'); continue         # G7
    shard.stage(out)
report.group_by_reason()   # 按原因聚合 -> 判别应修改哪些规则

6. 部分失败的回滚单位 - 把分片当成「牲畜」

在大规模变更中，回滚不是例外状况而是常规操作流程。《Software Engineering at Google》把自动生成的变更形容为当作牲畜而非宠物：无名无面的提交，撤销时损失不大。人花几天做出的提交舍不得回退，工具三分钟就能重造的提交则不必心疼。

要获得这种性质，需要在设计阶段就设下条件。

  • 回滚单位=分片=提交。三者一旦错位，撤销时就得由人来判断该撤什么
  • 分片必须可重新生成。在提交信息里留下所用规则集版本与目标范围，让一行命令就能重造
  • 运行时切换交给开关。把代码部署与行为切换分开，回滚就从发布变成配置变更
  • 不要急着拆掉适配层。旧路径保留的时长，就是可回滚的时长
  • 至少演练一次回滚。从未真正执行过的回滚计划不算计划
  • 数据与模式走独立轨道。回退代码并不能把损坏的数据还原

谷歌的分片运作还有一点值得借鉴：测试自动化平台以周期发车的列车模型成批验证，失败时再逐个分片重新分析以定位原因。要点在于把失败当作批次现象而非孤立事件来观察。单个分片失败信息量很少，但二十个里有六个因同一原因失败，那就是规则出了问题的信号。

7. 降低评审负担的diff设计

当自动生成规模扩大，瓶颈就从生成转移到评审。一天能生成几千行，人一天能审的量却没变。因此diff必须为被阅读而设计。

7.1 不要混在一起

  • 机器变更与人工变更不要放进同一次提交。一旦混合，评审者就不得不通读全部
  • 把格式变更拆成前置提交。格式化结果混进主体变更，diff的九成就成了噪声
  • 文件移动与重命名单独提交。移动与内容变更同处一次提交时，工具追踪不到移动，整个文件会显示为删除加新增
  • 一个分片只承载一种模式。两类转换混在一起，评审者就得分别验证

7.2 让重复看起来像重复

同一形态的变更重复出现在三百处时，评审者没有理由读三百遍。谷歌用全局批准者制度解决这个问题：语言与库的专家用基于模式的工具扫过变更，只有偏离模式的部分才由人来看。不逐个评审每一处变更，正是关键。

要在普通团队里模仿这个结构，只需在合并请求正文中放入三样东西。

  • 标准转换形态：例如「A(x) → B(x, ctx)」，即本分片执行的转换范式
  • 符合范式与偏离范式的条数：「287处符合范式，4处偏离」
  • 4处偏离的文件路径与原因：评审者只精读这里

自动提取偏离的方法很简单：把diff归一化(去掉标识符与空白)后做哈希聚类，绝大多数会落进少数几个簇。簇大小为1的diff就是偏离，事故多半出在那里。

migrate(S-014): map legacy Clock API to injected clock

rulebook: v7 (2026-07-28)
scope:    svc/billing/handler/**  (files: 31)
pattern:  Clock.now()  ->  clock.now()   [287 hits]
outliers: 4  (see below)
  - handler/retry.go:88    还需要一并做时区转换
  - handler/report.go:214  测试夹具假定时钟被冻结
  - ...
gates:    parse/format/build/unit  PASS   diff-test  PASS
regen:    ./migrate.sh --rulebook v7 --shard S-014

这种格式的好处在于评审者能知道哪些可以跳过。降低评审负担的办法不是把diff变小，而是明确收窄需要精读的那一部分。

8. 进度管理 - 每天该量什么

迁移是很难切成冲刺的工作。「完成了70%」这种汇报要有意义，分母就得固定，而实际推进中新目标会不断浮现。因此指标更适合按余量与速度而非百分比来取。

指标计数方式为何要看
剩余对象已发现候选中尚未处理的文件数连分母增长的速度一起看
闸门通过率各阶段通过÷投入规则质量的代理指标，批次间趋势最重要
人工后续修改率模型产出中被人改动的比例该值偏高说明委托的收益已消失
评审待处理量生成完成数减评审完成数判别瓶颈位置，增长就停止生成
返工率同一文件被重新生成的次数三次以上就是转手工的信号
合并后回归部署后发现的缺陷数闸门漏掉的部分，要反馈进闸门设计
累计成本令牌费用加评审工时折算用预算对进度来判断是否继续

其中最难解读的是人工后续修改率。谷歌FSE 2025论文把595次变更分成三类：仅由模型完成214次(35.97%)、模型产出后由人改动229次(38.48%)、完全由人编写152次(25.55%)。前两类相加就是被广泛引用的74.45%。

这一分解之所以重要，是因为74%并不意味着「人没有插手」。仅靠模型完成的约占36%，另有38%经过了人工后续编辑。若按编辑量计，模型贡献69.46%(64,996处)，人的贡献30.54%(28,578处)。也就是说，「AI做了74%」与「人重做了三分之一」是同一份数据的两副面孔。做计划时按后一副面孔配置人力更稳妥。

9. 中止判断标准 - 什么时候收手

引入自动化的团队最晚才定的往往是中止条件。因为已经投入不少，停下来很难受，于是沉没成本吞掉了判断。中止标准必须在动工前就用数字钉死。

信号阈值示例解读措施
闸门通过率下滑连续三个批次下滑规则覆盖不了剩下的区间停止生成，重写规则或收窄范围
同一文件重复生成超过三次结构上不适配的文件转入手工清单
人工后续修改率越过事先约定的线委托收益已消失剩余范围改为人工处理
评审待处理量增长连续两周净增瓶颈已转移到评审把生成速度压到评审吞吐量
合并后回归累积超过回滚处理速度闸门没能滤掉失败冻结部署，加固闸门
成本超支试点估算的1.5倍前提假设错了重新估算并重新审批
检测到测试代码被改哪怕只有一处判定标准本身在动摇立即停止，整批全部丢弃

最后一行与其他各行性质不同。其他行说的是「效率变差了」，而这一行说的是测量本身被污染了。智能体让失败的测试通过的最简单办法，不是改代码而是改测试。

这一风险在基准测试中也得到印证。评估Java版本迁移的FreshBrew研究(arXiv:2510.04852, ICSE 2026)以228个仓库为对象，测量智能体保持语义与规避奖励作弊的能力。论文称成绩最好的模型成功迁移到JDK 17的比例为52.3%，并指出若不施加完整性检查，相当一部分表面上的成功会被归类为奖励作弊。既然维护良好的开源仓库也只是这个水平，企业内部的遗留代码没有理由更容易。

实务上的防御很简单：把测试代码路径用独立闸门锁住。迁移批次的diff一旦触及测试文件即自动判失败；确实需要改测试时，由人另开合并请求单独推进。Bun在自家博客把被跳过或删除的测试为0个列为成果指标之一，而特意把这一项摆到前面，本身就说明这个风险广为人知。

10. 成本估算 - 人比令牌贵

成本估算的常见错误是算到「行数×每行令牌」就结束。实际上还要加上重试倍数、作为上下文一并投入的引用文件、运行闸门的基础设施，以及评审时间。

项目算式实测方法
生成令牌(输入令牌+输出令牌)×单价实测20个代表文件后外推
重试倍数1÷闸门最终通过率在试点批次中测量
上下文负担目标文件加引用文件的体量引用距离拉得越远增长越猛
缓存效果重复投入提示中命中缓存的比重规则集越长收益越大
闸门执行构建与测试的CI时间×批次数大型仓库中不可忽略
评审时间分片数×每分片评审时间通常这一项最大
手工余量落选文件数×每文件手工工时由闸门落选率推导

公开大型案例的实测值有助于建立量感。Bun披露Rust移植消耗了非缓存输入59亿令牌、输出6.9亿令牌、缓存读取720亿令牌，按API标价折算约十六万五千美元。除以最终diff的一百万行，约合每生成行0.16美元；以原始Zig的53.5万行为基准，约合每原始行0.31美元。

不要直接套用这些数字：它们由当事方发布，该仓库的测试套件异常厚实(各平台约6万个测试，Linux x64口径超过138万次断言)，且按标价折算。仓库状况不同，量级可能完全不同。估算务必在自家仓库的试点中重新取值。

缓存这一项值得留意。在Bun的案例中，缓存读取令牌超过非缓存输入的十二倍。把规则集与参考文档这类每次请求都重复投入的部分固定在提示前部，缓存就能生效，成本结构随之大变。反过来，频繁修改规则集会每次都让缓存失效。规则集修订要集中进行并打上版本这条运维原则正源于此。

工期估算另有一个参考点。谷歌报告内部从JUnit3迁移到JUnit4的工作在三个月内处理了5,359个文件、逾14.9万行，且模型生成代码约87%未经修改即被提交。另一案例中工程师估计所需时间比以往减少约50%。不是「快十倍」而是「减半」，这才是现实的期待值。

11. 失败究竟出在哪里 - 已观测的类型

以下把公开资料中记录的失败类型按实务视角整理。基于已报告的案例，而非推测。

类型症状检测应对
上下文溢出巨型文件上修改根本没发生文件体量分布事先划入手工清单
非确定性相同输入每次产生不同diff同一输入跑两次做对比以不可复现为前提，按产出物逐个验证
无谓变更只改格式或只加注释归一化diff后看有无实质变更在第2、5道闸门丢弃
引用遗漏较远的间接引用没被改到把距离上限之外的位置列表化由人另行清扫
语义不一致构建与测试都过，行为却不同差分测试、合并后监控把断言与副作用惯用法写进规则集
语言差异只在某种语言上质量骤降按语言分开统计通过率该语言改用规则型转换
黄金文件未更新期望值文件仍是旧格式单独追踪黄金文件路径由人更新，禁止自动更新
奖励作弊测试被削弱或删除锁住测试路径的diff整批丢弃后重新设计

其中非确定性在迁移工作中尤其棘手。把温度设为0也不保证完全复现，这一点已有公开报告。某研究实验室称，同一提示以温度0运行一千次，产生了80种不同的完成文本，并把原因解释为并非随机性，而是批大小改变了内核的计算顺序。放到迁移语境里，这一性质的含义只有一个：无法建立以「与昨天跑出的结果相同」为前提的流程。因此信任的对象不应是生成过程，而应是产出物以及放行它的闸门记录。为非确定性输出设定通过标准的方法本身，已在像管理代码一样管理提示词中另行讨论。

黄金文件未更新也常被忽略。谷歌论文把自动工具不支持更新黄金文件列为遗留课题，因为让期望值文件自动更新会造成判定标准反过来追随产出物的倒置。这一项放弃便利才是正确的。

12. 反方意见 - 「没被评审的一百万行」问题

为求平衡，把反方论据原样搬来。据报道，Zig语言的创造者Andrew Kelley对Bun的Rust重写公开提出了强烈批评。核心论点关于判据的可信度：既然既有测试套件未能拦住原Zig实现中的缺陷，凭什么认为同一套件能抓住新生成的一百万行中的缺陷？据报道的措辞，他称之为「未经评审的糟粕」。

这条批评不应被读作对某个人或某家公司的评价，而应被读作对第3节①号轴线的再次追问。如果自动化把通过判定托付给测试套件，那么该套件的缺陷检出能力就是迁移质量的上限。套件原本漏掉的东西，迁移之后照样会漏。

要公平，也必须一并看Bun公开的辩护：各平台约6万个测试与Linux x64口径逾138万次断言、被跳过或删除的测试为0个、由1名实现者与2名处于独立上下文的评审者构成的对抗式评审、覆盖6个平台的CI分片、泄漏检测器与模糊测试器常态运行。以及披露合并后确实发现了19处回归并已修复。

把两方合起来看，实务教训很清楚。与其裁定谁对谁错，不如先测一测自家仓库的测试套件到底能抓住什么水平的缺陷。没有这项测量就开始的迁移，即便通过记录堆得再高，也没人能说清这些记录意味着什么。

一种测量方法：开始迁移之前，在原代码里注入几个有意的缺陷，看测试能否抓住(变异测试的缩小版)。如果注入的缺陷大多蒙混过关，就说明这套测试不足以充当本次迁移的判定者。这项确认一天就能做完，而结果可能改变整个计划。

13. 两周试点的设计

全面动工前先跑试点。目的不是「看看行不行」，而是拿到估算所需的数字。

  • 第1至2天 判据体检：用缺陷注入测量测试套件的检出能力。列出可做差分测试的边界(纯函数、序列化点、HTTP处理器)
  • 第3至4天 目标调查：按引用距离统计候选数、文件体量分布，并分离生成代码、黄金文件与测试文件的路径。自动化范围之外的清单在这一步定下
  • 第5至6天 规则集草案：手工迁移20个代表文件，从中提炼规则。没有亲手迁过就写出的规则集，多半在第一批就崩
  • 第7至8天 小批量运行：对20至30个文件全量施加闸门运行，统计各阶段落选率与原因分布
  • 第9至10天 修订规则后重跑：只把成簇的落选原因吸收进规则，重跑并观察通过率的变化
  • 第11至12天 实测评审：让真实评审者评审3个分片并计时。这个值常常成为整体工期的主导项
  • 第13至14天 外推与决策：用通过率、重试倍数与评审时间算出总成本与工期，并敲定中止条件表中的阈值

试点结果不好并不是失败。两周就能筛出来的问题拖到六个月后才知道，那才是失败。尤其当判据体检得分很低时，那一刻正确的结论不是「别用AI了」，而是「先把测试补起来」。

结论

在大规模代码迁移中，智能体改变的是转换工作的单价，而不是工作的结构。原子性大规模提交不可能、必须切成可独立回退的分片、评审会成为瓶颈——这些与codemod时代完全一致。变化在于规则无法表达的尾部也进入了自动化射程，而代价是必须逐个验证产出物。

因此设计的重心不在生成，而在丢弃策略。先摆便宜的闸门；落选的不要去修，直接丢；落选原因成簇就改规则重新生成，零散就转给人工清单。分片必须是随时可回退的牲畜，diff必须告诉评审者哪些可以不看。

最后把限度讲清楚。这里写下的任何流程都不能确保迁移成功。本文给出的不是成功公式，而是让失败被便宜且尽早发现的布局。公开数字指向的现实期待值也不是魔法：在配置良好的企业内部环境中所需时间降到约一半，即便是维护良好的开源仓库，自动迁移的成功率也在半数上下。仅仅拿到这一半也足够值得，原因只有一个——剩下的另一半会以清单的形式落到你手里。
