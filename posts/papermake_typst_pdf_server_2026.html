Papermake와 Typst - 셀프호스팅 PDF 생성 서버는 LaTeX·헤드리스 브라우저의 대안이 될까

청구서·리포트·증명서를 서버에서 PDF로 찍어내야 하는 실무자를 위해, Typst 기반 오픈소스 문서 생성 서버 Papermake를 뜯어본다

2026-07-15 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 서버가 PDF를 뱉어내야 하는 순간은 늘 있다

주문이 완료되면 청구서가 나가야 하고, 배치가 끝나면 리포트가 쌓여야 하고, 신청이 승인되면 증명서가 발급돼야 하고, 출고가 끝나면 라벨이 인쇄돼야 한다. 이런 순간마다 서버 어딘가에서 PDF를 동적으로 찍어내는 파이프라인이 조용히 돌아간다. 화려하지 않지만 없어서는 안 되는 인프라다. 2026년 7월 기준, 이 오래된 문제를 새 각도로 푸는 시도가 눈에 띈다. Typst 템플릿을 REST API로 렌더링하는 셀프호스팅 오픈소스 서버 Papermake다. 이 글은 Papermake 자체를 소개하는 데 그치지 않고, 왜 서버 PDF 생성이 여전히 고통스러운 문제인지, Typst가 그 고통을 어떻게 완화하는지, 그리고 셀프호스팅과 상용 API 중 무엇을 택할지를 실무 기준으로 분석한다.

실무에서 반복되는 4가지 PDF 니즈

  • 청구서/인보이스 - 주문·결제 직후 즉시 생성돼야 하고, 국가별 전자세금계산서 규격 같은 형식 준수가 요구된다.
  • 리포트 - 정기 배치로 수백~수천 건을 한 번에 렌더링해야 하며, 레이아웃 일관성이 핵심이다.
  • 증명서 - 재직증명서·수료증처럼 빈도는 낮지만 서명·워터마크 등 신뢰성 요소가 중요하다.
  • 라벨 - 물류 라벨처럼 초저지연·고빈도로 찍어야 하고, 작고 반복적인 레이아웃이 특징이다.

1. 기존 방식의 고통 - 왜 다들 이 문제로 고생하나

1.1 LaTeX - 품질은 높지만 무겁고 느리다

LaTeX는 수십 년간 고품질 조판의 표준이었다. 그러나 자동화 파이프라인에 얹기엔 마찰이 크다. 전체 배포판은 수 GB에 달하고, 모놀리식 .tex 파일에 이미지·복잡한 다이어그램이 섞이면 컴파일이 눈에 띄게 느려진다. 요청 하나마다 무거운 조판 프로세스를 새로 띄워야 하고, 실패 시 나오는 로그는 개발자가 아닌 운영자가 해석하기엔 진입장벽이 높다. 인보이스 라인아이템처럼 자동화 코드가 템플릿 내부 값을 주입하는 구조를 짤 수는 있지만, 그 구조 자체를 유지보수하는 비용이 만만치 않다.

1.2 HTML→PDF 헤드리스 브라우저 - 유연하지만 자원을 먹는다

Puppeteer·wkhtmltopdf로 대표되는 HTML→PDF 방식은 웹 개발자에게 익숙한 CSS·템플릿 엔진을 그대로 쓸 수 있다는 매력이 있다. 그러나 대가가 뚜렷하다. 헤드리스 크롬은 기동만으로 200~300MB 메모리를 쓰고, 이미지·폰트가 많은 페이지에서는 500MB를 넘기기 쉽다. 동시 렌더링을 걸면 프로세스가 정리되지 않고 남아 CPU를 밀어붙이는 사례도 보고된다. 반대로 오래된 WebKit 엔진 기반 wkhtmltopdf는 가볍지만 최신 CSS Grid·Flexbox를 제대로 그리지 못한다. 결국 실무자는 "가벼움"과 "최신 웹 표준 렌더링" 사이에서 양자택일을 강요받아 왔다.

2. Typst란 무엇인가 - 조판 언어의 세 번째 길

Typst는 2023년 공개된 마크업 기반 조판 언어다. LaTeX의 방대한 백슬래시·중괄호 문법 대신 Markdown에 가까운 간결한 문법을 쓰고, 계산과 조판 사이의 경계를 없애 변수·반복·조건문 같은 프로그래밍 로직을 매끄럽게 섞어 쓸 수 있게 설계됐다. 성능 차이가 특히 인상적인데, 큰 논문 기준 LaTeX가 풀 컴파일에 90초 걸리는 문서를 Typst는 약 15초에 처리하고, 내용을 조금 고친 뒤의 증분 컴파일은 1초 이내로 끝난다는 벤치마크가 보고돼 있다. 컴파일러 수준의 명확한 오류 메시지, 화학식·악보·회로도 패키지를 모은 "Typst Universe" 생태계도 갖춰져 있다.

2.1 왜 백엔드 PDF 엔진으로 매력적인가

Typst는 Rust로 구현돼 있어 브라우저 없이 순수 라이브러리 형태로 서버 프로세스에 직접 임베딩할 수 있다. 즉 헤드리스 브라우저처럼 무거운 서브프로세스 여러 개를 띄울 필요 없이, 서버 안에서 곧바로 문서를 렌더링할 수 있다는 뜻이다. 이는 정확히 "서버 사이드 PDF 생성"이라는 용도에 맞아떨어지는 특성이며, Papermake 같은 프로젝트가 Typst를 렌더링 엔진으로 택한 이유이기도 하다.

3. Papermake - 템플릿을 API로 만드는 접근

Papermake는 독일 개발자 Erik Steiger(rkstgr)가 만든 오픈소스 프로젝트로, 스스로를 "문서 템플릿을 위한 Docker 레지스트리"에 비유한다. Typst 템플릿을 SHA-256 해시로 콘텐츠 주소화해 저장하고, invoice:latest 같은 태그로 특정 버전을 가리키는 방식이다. 템플릿은 한 번 발행(publish)하면 불변(immutable)이며, 렌더링 요청마다 입력·출력 해시가 기록돼 전체 이력을 재현·감사할 수 있다.

3.1 아키텍처

구조는 네 조각이다. 코어 papermake는 가상 파일시스템을 갖춘 Typst 렌더링 엔진이고, papermake-registry는 S3 호환 스토리지(템플릿 저장)와 ClickHouse(렌더 이력)를 묶는다. papermake-server는 Axum 기반 HTTP API 계층으로 템플릿 발행·렌더링·PDF 조회 엔드포인트를 제공하며, papermake-worker는 큐 기반 렌더링을 맡는다(아직 초기 단계). PDF 1.7은 물론 전자 인보이스에 쓰이는 PDF/A-2b·PDF/A-3b까지 지원한다는 점은 실무 인보이스 자동화를 염두에 둔 설계로 읽힌다. Apache 2.0 라이선스로 공개돼 있다.

3.2 템플릿 중앙관리 + REST API가 주는 가치

이 구조가 실무에 갖는 의미는 명확하다. 첫째, 마이크로서비스 환경에서 주문·정산·CS 등 여러 서비스가 하나의 인보이스 템플릿을 API 호출만으로 공유할 수 있어, 템플릿 로직이 서비스마다 중복되지 않는다. 둘째, 다국어·다포맷 대응이 쉬워진다. 템플릿 버전을 언어·국가별로 태깅해 관리하면 애플리케이션 코드 변경 없이 새 버전을 배포할 수 있다. 셋째, 불변 버전과 렌더 감사 로그는 "이 청구서가 왜 이 모양으로 나왔는가"를 나중에 정확히 재현할 수 있게 해준다. 규제 산업이나 회계 감사가 걸린 문서에서 이는 사소한 부가 기능이 아니라 핵심 요건이다.

4. 셀프호스팅 vs 상용 PDF API

Papermake 같은 셀프호스팅 오픈소스와 CraftMyPDF·APITemplate.io류 관리형 상용 API는 트레이드오프가 뚜렷하다. 셀프호스팅의 이점은 데이터가 외부로 나가지 않는다는 것, 그리고 고볼륨에서 단위 비용이 낮아질 수 있다는 것이다. 실제로 한 상용 벤더는 브라우저 기반 셀프호스팅 비용을 연 2만 7천 달러 수준으로, 자사 관리형 API를 그보다 훨씬 저렴하게 제시하는 비교 자료를 공개한 적이 있다(벤더 자체 비교이므로 액면 그대로 받아들이기보다 본인 워크로드로 직접 검증하길 권한다). 반대로 상용 API의 이점은 운영 부담이 없다는 데 있다. Docker 이미지 비대화, 서버리스 크기 제한, 브라우저 프로세스 크래시 같은 문제를 신경 쓸 필요가 없다. 결론은 명확하다. 발송량이 적고 별도 운영 인력이 없다면 관리형 API가 합리적이고, 데이터 주권이 중요하거나 고빈도·정형 문서(청구서·라벨)를 대량 처리해야 한다면 Papermake 같은 셀프호스팅 옵션을 저울질할 가치가 있다.

5. 실무 도입 시 고려할 것 - 폰트·CJK·성능·보안

5.1 CJK(한중일) 폰트 지원은 아직 미성숙

가장 신중해야 할 지점이다. Typst 프로젝트 자체에 CJK 조판 지원이 부족하다는 이슈가 공개적으로 제기돼 있다. 폰트 스타일(명조체 대 고딕체) 전환, CJK-라틴 문자 간 자간 조정, 세로쓰기, 루비(독음) 표기 같은 기능이 아직 갖춰지지 않은 것으로 보고된다. 한글 청구서·증명서처럼 CJK 텍스트가 중심인 문서를 Papermake/Typst로 옮기려 한다면, 실제 한글 폰트 렌더링과 줄바꿈 품질을 파일럿 단계에서 먼저 검증해야 한다.

5.2 성능과 보안

성능 면에서는 Rust 구현과 브라우저 미기동 구조 덕에 고빈도 렌더링에 유리할 것으로 기대되지만, 공개된 독립 벤치마크는 아직 부족하다. 보안 면에서는 셀프호스팅이므로 템플릿 자체(사용자 입력이 렌더링에 흘러드는 인젝션 경로), S3 스토리지 접근 권한, 렌더 이력 DB의 개인정보 보존 정책을 직접 설계·점검해야 하는 부담이 따른다.

결론: 어디에 쓸 것인가

Papermake는 2026년 7월 기준 초기 단계(버전 0.3.0, GitHub 스타 166개) 프로젝트다. 곧바로 프로덕션 전면 전환보다는 우선 낮은 리스크의 워크로드 - 사내 리포트, 내부 증명서처럼 실패해도 큰 타격이 없는 문서 - 로 파일럿을 돌려보는 편이 합리적이다. 반대로 고빈도·정형화된 문서(청구서·라벨)를 대량으로 찍어야 하고 LaTeX나 헤드리스 브라우저의 무게가 실제로 부담이었다면, Typst와 Papermake의 조합은 진지하게 검토할 가치가 있는 선택지다. 다만 CJK 폰트 품질과 프로젝트 성숙도는 도입 전 본인 데이터로 직접 검증하는 것이 필수다.
