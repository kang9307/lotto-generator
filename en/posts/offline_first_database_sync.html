The Price of Holding the Data

Offline-first databases - where schema, partial sync, permissions and deletion get hard

Aug 30, 2026 Dev & Infra

Intro: after you hit save in a tunnel

The train enters a tunnel, the list empties, and the save button spins without landing. You close the screen not knowing whether what you just wrote survived. Offline-first is the proposal to delete those few seconds. Instead of borrowing data from a server, you keep a copy inside the device, finish both reads and writes there, and reconcile with the server when the connection returns.

In late August 2026 an engine built on that idea showed up on GeekNews. Per its repository description it keeps an SQLite database on each client and reconciles them through a server-owned commit log. In the browser it runs SQLite on OPFS; on native it shares a Rust core across Swift, Kotlin, Flutter, React Native and Tauri; on the server it runs on Bun, Node and Cloudflare Workers with SQLite, Postgres or D1 behind it. The license is Apache-2.0. That is the extent of what the repository states.

The interesting part is what comes next. The moment you decide to keep data on the device, a set of problems arrives that simply did not exist when the data lived in one place. Changing the schema. Deciding how much to send down. Taking back what you already handed over. Remembering that something was deleted. What follows is that bill.

This article does not recommend adopting any particular product and makes no claim that one approach is better than another. The repository that prompted it is used only as a starting point, and the design discussion is written in general terms.

1. A cache and a local database are not the same thing

Both are just data on the device, so the words get used interchangeably, but this distinction splits the entire design. The test reduces to one question. If you wiped this store right now, would anything be unrecoverable?

For a cache, nothing is. The original lives on the server and the local copy is a copy, so deleting it costs you one slow screen. Being disposable is nearly the whole of cache design. You can get the expiry wrong and the worst outcome is a stale value showing briefly.

A local database is different. It legitimately holds writes that are not on the server yet. Three hours of work done on a plane exists only inside that file, by design, for as long as the flight lasts. Delete it and the user's work is gone with nowhere to fall back to.

  • Storage location changes. Put a local database in the cache area the OS reclaims for space and one day it quietly empties. The user never deleted anything.
  • Browsers are stricter. If your storage is eligible for eviction it can vanish between tab visits. Requesting persistence and checking remaining quota become preconditions rather than features.
  • Logout behaves differently. Clearing a cache on logout is correct. Running the same code against a database holding unsent writes turns logout into a delete-my-work button.
  • Just download it again stops being an answer. A standard support phrase becomes a data destruction procedure.

If the team never agrees on this one line, everything downstream wobbles. Cleanup code written by someone who thinks it is a cache ends up touching the same store as sync code written by someone who thinks it is a database.

2. Why you end up wanting offline-first - and why it is not free

The motivation usually comes from three places. First, instant response: write locally, repaint immediately, and the spinner is replaced by the result while sorting, filtering and search run without a round trip. Second, the network. Tunnels, underground car parks, warehouse floors and aircraft cabins are not slow connections, they are no connection, and no amount of retry logic keeps the screen from going blank. Third, server load, since pushing reads and aggregation to the device cuts both call volume and bill.

All three are real gains. The cost is that the architecture moves up a level.

  • The client now holds state. The layer that only drew screens becomes responsible for one copy of the data. You get as many databases as you have users, and most of them are outside your control.
  • Deployment stops being atomic. The server flips in an instant; devices flip over weeks. During that window, old and new code touch the same data.
  • Failure arrives late. In a server-authoritative model failure comes back as an error right after the request. Here the local write succeeds and the problem surfaces days later, during sync.
  • Storage and security requirements attach themselves. Device capacity, lost handsets, column-level encryption and backup copies all become design items.

3. Writes now happen on both sides

In a server-authoritative model, order is decided in one place. The client proposes, the server commits, and anything uncommitted does not exist. In offline-first, writes that each succeeded on their own side meet later. Everything else follows from that single difference.

The theory of conflict resolution itself — version vectors, Lamport clocks, CRDTs, tombstones, and the symptoms that appear because last-write-wins leans on device clocks — is laid out in a dedicated section of One Toggle Becomes a Distributed System - Why Offline Sync Revives Settings You Turned Off. Rather than unrolling that again, this piece looks at what stacks on top once the whole database lives offline.

One point is worth keeping, though. What actually breaks during a merge is not a field but an invariant. However carefully you write per-field merge rules, two devices can each produce a valid state and the combination lands on something invalid that neither side ever held.

  • Uniqueness. Two devices create a row with the same email. Both pass locally, and one of them has nowhere to go on the server.
  • Counters and balances. Overwriting the value discards one side's delta. Recording the change amount instead is what makes them combinable.
  • State transitions. One side moves a record to paid while the other moves it to cancelled, and the merged result can end up being neither.
  • Reference order. A child row arriving before its parent leaves a foreign key briefly unsatisfied. Application order has to be grouped per commit.

4. What happens when the schema changes

This is the core of it. A server schema is done when you deploy. The migration runs and from that instant only the new schema exists. If it fails you roll back, and the thing being rolled back is data you own.

A schema on a device does not work that way. The migration runs only when the user opens the app. If they do not open it, the old schema stays. And users open apps again eventually.

  • A tablet untouched for four months wakes up and connects to a v20 server on schema v12. It is still writing a column you dropped.
  • There is always a share of users who defer updates, disable automatic updates, or run an OS too old to receive the newest build at all.
  • If the server ships days ahead of store review, that whole window is a version-mismatch period.
  • When a migration fails on a device, there is no pristine original to restore. Because the user's unsent writes live in that file, wipe and recreate is not a safe recovery.
  • Restoring a device backup resurrects a database from months ago, producing the combination of a current app build with past data.
AspectServer onlyAlso on the device
When the migration runsOne deploy timeEach moment a user opens the app
Versions alive at onceOneThe whole supported range, months wide
Rolling back a failureA rollback scriptThe original is user data, so there is nothing to roll back to
Undoing a releaseRedeploy the previous buildDevices already converted do not come back
Dropping a columnOne DDL statementStaged retirement across several releases
Adding a required columnSet a default and move onOld clients keep sending writes without it
How you verifyOnce on stagingRound trips per version combination

So the sync protocol needs a version of its own, separate from the schema, negotiated on every connection. The shape usually looks like this.

client -> server : schema v12, last commit received #8421
server decides
  v12 within supported range (v10-v20)  -> translate and send in v12 shape
  v9 or older                           -> stop syncing, ask for an app update
                                           (local reads and writes keep working)

That last parenthesis matters. Telling an out-of-range device to delete and reinstall the app destroys the unsent writes inside it. There has to be a way to export the local data on that very screen.

Two working rules follow. Never drop or rename a column in one step — add the new one, dual-write for a while, move the reads, and remove the old one only after the old build leaves the supported range. And decide, as a number you write down, how far back you will accept a schema. Without that number you support every version forever.

5. Partial sync - when you cannot ship it all down

Once a user's data passes tens of megabytes, shipping all of it stops being an option, so you cut a scope. The criteria are usually ownership, time (the last six months), membership (projects you belong to), or region.

The hard part is not the cut but the scope moving. It shifts when someone joins or leaves a project, when a share is granted or revoked, and when time drags a row past the six-month boundary.

  • Shrinking scope means deleting. Rows already on the device need a removal instruction, and that instruction only runs when the device connects.
  • Growing scope drops a payload. Being invited to a project pulls down tens of thousands of rows at once. First-sync time and battery cost are decided right here.
  • Absent and out-of-scope look identical. When a local query returns zero rows, the app cannot tell whether there really are none or it simply never received them. Compute a count or a total locally in that state and the number on screen is quietly wrong.
  • References cross the boundary. A document inside your scope names an author outside it. To render the name, that minimal record has to travel regardless of scope.
  • Search results diverge. The same query returns twelve hits online and three offline. If the screen does not say so, users conclude their data was lost.

One practical rule. Store scope metadata alongside local results. Recording which conditions and which point in time you have received lets the app say this list covers the last six months. That single line noticeably reduces support tickets.

6. Where permissions get hard

When the server holds the data, permission is checked per request. Cut access and the next call is blocked, and who saw what is in the log. Once data is replicated onto a device the situation inverts. Revocation is an instruction, not a guarantee.

EventServer-authoritativeWith a copy on the device
A document share is revokedBlocked on the next requestEffective once the delete arrives; still present on offline devices
Role downgradeImmediateData already sent under the higher role needs separate recall
Leaving an organisationDeactivate the account and doneDepends on a device wipe or remote delete succeeding
Account suspensionRevoke the tokenLocal reads continue without any token
Device backupNot applicableDelete instructions never reach the cloud backup copy
Data deletion requestDelete on the serverHard to demonstrate that every copy is gone

That the right-hand column keeps ending in depends on is the nature of the problem. Responses split three ways.

  • Do not send it in the first place. This is the only certain revocation. Keep sensitive columns out of sync scope and ask the server while online. Offline, that screen reads connection required.
  • Give it a short life. Put an expiry on local data so it locks itself after a period without contact. Time performs the recall when the device cannot be reached.
  • Split at the column level. The repository behind this piece lists column-level encryption among its features. Note that if the decryption key lives on the device, that key is now something you also have to revoke.

For products that deal with departures or contract terminations, it is better to decide as policy rather than as a feature which data may leave as an offline copy. Narrowing it later means chasing copies that already left.

7. Why deletion is hard

Simply removing a deleted row brings it back. Another device still has it, treats its own copy as valid data, and pushes it up again. So deletion becomes not removal but recording that something was removed. Without that marker, called a tombstone, deletes get undone.

Deciding to keep the record raises the next question immediately. When do you delete the record of the deletion? Keep it forever and the database grows with every delete; drop it early and a device that was switched off in the meantime resurrects the row.

  • The usual compromise is a retention window. Keep tombstones for, say, thirty days, and devices absent longer lose their incremental sync eligibility and take a full resync.
  • If that full resync swallows the local unsent writes, that is data loss. There must be a path that uploads or preserves pending writes before the resync begins.
  • What goes into the tombstone is also a decision. Row identifier only, or deletion time and actor too, changes how much it collides with data deletion requests.
  • Locally, deletion, falling out of scope and losing permission all look like the row disappeared. Different causes deserve different wording on screen. Deleted and no longer visible are entirely different events to a user.

8. Debugging and support - the repro lives on someone else's device

A server bug is a log away. A local database bug reproduces only inside the sequence of events that device went through. Which commits arrived in which order, how far the clock was off at the time, when each migration ran — all of it is a precondition, and none of that history is on your server.

So you ask for diagnostics, and the second problem starts. Taking the whole local database is moving user data onto your side. A file containing work documents and contacts travels through a support channel. From a data protection standpoint that is collection, not debugging.

  • Build a metadata-only diagnostic. Schema version, last sync time, pending queue length, row counts per table, conflict counts and the last error code narrow down most causes.
  • When you need values, send shapes instead. Lengths, types and hashes still answer is this the same value without moving the content.
  • Show it before sending. A screen where the user reviews and approves what leaves gives you something to point at later.
  • Support staff opening a user database is an access control matter. If there is no record of who opened what and when, the procedure itself becomes the new exposure.
  • Do not let reinstall become the standard answer. Delete and reinstall the app means discard your unsent writes. Put an export step in front of that advice.
  • Set a retention period for diagnostic files. Attachments living forever in a ticket system are in practice the most common leak path.

9. When not to choose this shape

Offline-first is not always the better choice. A model where the server decides order still fits many products, and forcing a move away from it makes merge rules more complex than the product.

Data and usage patternFitting modelWhy
Partitions cleanly per user, writes mostly from that person (notes, journals, tasks)Offline-firstConflicts are rare and merge rules stay simple
Connectivity drops as a matter of routine (field survey, logistics, in-flight)Offline-firstThe online assumption does not hold at all
Several people edit the same record at once (shared stock, seats, dispatch)Server-authoritativeConflicts become routine and merge cost exceeds the product
Transactions needing strong consistency: balances, limits, stock decrementsServer-authoritativeThese values cannot be reconciled after the fact
Large per-user data touched rarely (archives, long histories)Server-authoritativeThere is no reason to ship it all down
Regulated or audited dataServer-authoritativeProving where every copy sits is a heavy burden

For products sitting on the boundary there is a middle path: keep only the personal workspace in a local database and leave shared resources and anything involving money to the server. Offline-first holds up better treated as a per-data-area choice than as a property of the whole app.

10. Where testing changes

Unit tests and API tests catch almost none of the defects in this shape, because the problems live in combinations of time, order and reconnection rather than in a single function. So those axes go into the test plan explicitly.

  • Clock skew. Run the same scenario with the device clock pushed forward and back. Any last-write-wins path shows itself here.
  • Reordered arrival. Apply commits deliberately out of order. Remaining order dependencies surface immediately.
  • Cut mid-transfer. Break the connection halfway through a batch and resume, checking that nothing applies twice — that the path is idempotent.
  • A long-dormant device. Bring one back past the tombstone retention window and exercise the full resync path. It only means something if it carries unsent writes.
  • Version combinations. Round-trip an old-schema client against a new server and the reverse. Untested range edges exist only in documentation.
  • Exhaustion and hard kill. Write with storage full, and kill the process mid-transaction. Journal mode and the recovery path are verified here.
  • Backup restore. Restore a local database from an earlier point and attach it to the current build. It is the most frequent real-world incident path and the one most often missing from test lists.

These do not reproduce reliably on real devices over real networks. Swapping in a fake clock and fake network to build a deterministically replayable simulation pays for itself quickly. Store the failing order as a seed and you never debug the same incident twice.

What could not be confirmed

  • The repository behind this piece does not spell out its specific conflict resolution rules, its schema migration approach, or how partial sync is defined. Its mention of authorization interfaces on the server is as far as the stated material goes.
  • The project links a separate benchmarks page, but the measurement conditions were not verified, so no figure from it appears here.
  • How the design items described here map onto the names and shapes of any particular implementation needs separate verification. They are written as general axes only.
  • Per-device storage policies and eviction behaviour vary by platform and version. There was no basis for generalising specific numbers, so only the qualitative behaviour is stated.

Conclusion: what may vanish and what may not

The gains are real. The spinner disappears, the app stays alive when the line drops, and server calls fall. What you take on in exchange is a class of problem that does not exist when data lives in one place. Schemas coexist in several versions, scope keeps moving, permissions have to be recalled, deletions have to be remembered, and bugs reproduce inside someone else's device.

They share one trait. Failure shows up as silence rather than an error screen. The list shows three items, a deleted entry climbs back, yesterday's work is missing. None of it throws. Which is why what you watch shifts from response codes to pending queue length, last sync time and conflict counts.

The question to answer first reduces to one. If this device went into the water tonight, what would go with it? If the answer is nothing, it is a cache and you can push it offline with a clear conscience. If anything is written down, it is a database from that point on, and the items above each need a decision. Leave them undecided and a default gets chosen for you, and that default usually favours the thing that disappears quietly.
