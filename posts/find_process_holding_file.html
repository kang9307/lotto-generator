파일을 붙잡고 있는 프로세스 찾기 - 지웠는데 공간이 안 돌 때

rm 은 이름만 지운다. 아직 붙잡고 있는 쪽을 리눅스와 윈도우 양쪽에서 짚어 내는 순서

2026-09-02 개발/인프라

가장 흔한 순서는 이렇다. 디스크가 찼다는 경보가 온다. 큰 로그를 하나 찾아 rm 으로 지운다. ls 에는 더 이상 보이지 않는다. 그런데 df 는 조금도 줄지 않았다. 몇 분 기다려도 같다. 그래서 지울 것을 더 찾는다.

이 지점에서 방향이 이미 틀어져 있다. 문제는 지울 것이 부족한 게 아니라 이미 지운 것이 아직 살아 있다는 것이다. 이 글은 그 상황에서 누가 붙잡고 있는지 특정해 내는 절차만 다룬다. 왜 이런 일이 생기는지에 대한 네 갈래 원인 분류는 디스크는 안 찼는데 No space left on device 쪽에 있고, 이 글은 그중 하나를 이어받는다.

이 글에 나오는 명령 중 프로세스 종료와 파일 서술자 절단은 되돌릴 수 없다. 해당 절에 위험 표기를 따로 달아 두었으니 운영 장비에서는 그 문단을 먼저 읽고 손을 대는 편이 낫다. 확인만 하는 명령과 상태를 바꾸는 명령을 섞어 쓰지 않는 것이 이 작업의 전부에 가깝다.

카운터가 둘이다 - 이름의 수와 참조의 수

이 현상 전체가 문장 하나에서 나온다. rm 은 데이터를 지우는 명령이 아니다. rm 이 호출하는 시스템 콜은 unlink 이고, 이것은 디렉터리에 적힌 이름 하나를 떼어 내는 연산이다. 데이터가 있는 곳은 이름이 아니라 inode 이고, inode 는 이름이 사라졌다고 해서 함께 사라지지 않는다.

POSIX 규격은 이 동작을 오해할 여지가 없이 못 박아 두었다. 링크는 unlink 가 반환하기 전에 제거되지만, 파일 내용의 제거는 그 파일에 대한 모든 참조가 닫힐 때까지 미뤄진다는 것이다. 그러니까 파일 하나에는 성격이 다른 카운터가 둘 붙어 있다. 둘이 동시에 0 이 되어야 블록이 돌아온다.

카운터세는 것0 으로 만드는 것여기서 보인다
링크 카운트이 inode 를 가리키는 디렉터리 항목의 수rm · unlink · mv 로 덮어쓰기stat -c %h · ls -l 두 번째 열
열린 참조이 inode 를 열어 둔 파일 서술자와 매핑의 수프로세스 종료 · close() · 로그 재개 신호lsof · fuser · /proc/<pid>/fd
블록 반환 조건둘 다 0 이 되는 시점마지막 참조가 닫히는 순간, 커널이 한꺼번에df 의 여유 블록이 계단처럼 뛴다
관측 도구의 시야du 는 이름을 걸어 다니고 df 는 블록을 센다이름이 없으면 du 는 못 본다두 값이 벌어진 폭 = 붙잡힌 용량

이 동작 자체는 결함이 아니라 안전장치다. 어떤 프로세스가 읽는 도중에 다른 프로세스가 그 파일을 지웠다고 해서 읽던 쪽이 깨져서는 곤란하다. 문제는 이 안전장치가 운영 중에 조용히 발동한다는 데 있다. 아무 오류도 나지 않고, 로그도 남지 않고, 그저 공간이 돌아오지 않을 뿐이다.

이 글의 실행 환경과 검증 범위

주제는 리눅스 서버인데 아래 출력을 만든 환경은 Windows 10 위의 Git Bash 다. 이것을 먼저 밝히는 이유는 어떤 출력이 실제로 나온 것이고 어떤 명령이 여기 출력 없이 적혀 있는지를 독자가 구분할 수 있어야 하기 때문이다.

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

$ uname -a
MINGW64_NT-10.0-19045 3.5.7-882031da.x86_64 2025-01-30 11:14 UTC x86_64 Msys

$ git --version
git version 2.48.1.windows.1

$ stat --version | head -1
stat (GNU coreutils) 8.32

$ stat -f -c 'bsize=%s' /tmp/demo
bsize=4096

# PowerShell 쪽
PS> $PSVersionTable.PSVersion.ToString()
5.1.19041.6456

coreutils 는 리눅스와 같은 GNU 8.32 이므로 stat·df·du·truncate 의 옵션 동작은 동일하다. MSYS 는 /proc 을 자체적으로 흉내 내 제공하는데, 이것이 리눅스 커널의 procfs 가 아니라는 점이 뒤에서 한 번 중요해진다. 아래는 이 글에서 실제로 돌린 것과 돌리지 못한 것의 목록이다.

  • 돌린 것 (리눅스 쪽) — 삭제 후에도 열려 있는 파일 재현, stat -c 로 inode·링크 카운트 추적, stat -f 여유 블록 계측, /proc/<pid>/fd 조회와 전수 훑기, 홀더가 둘일 때의 거동, 파일 서술자 절단 시도, 열자마자 unlink 하는 관용구
  • 돌린 것 (윈도우 쪽) — 공유 모드를 달리한 파일 잠금 재현, 잠긴 파일에 대한 Remove-Item·Rename-Item·Get-Content, Git Bash 의 rm·cat, Restart Manager API 로 점유 프로세스 특정, openfiles, Get-Process 의 모듈 목록 검색
  • 돌리지 못한 것 — lsof·fuser(이 환경에 설치돼 있지 않다), 컨테이너·네임스페이스 관련 전부, NFS 마운트
  • 지어내지 않은 것 — 돌리지 못한 명령의 출력은 이 글에 한 줄도 없다. 명령 형태와 읽는 법만 적었고, 그 근거는 각 도구의 매뉴얼이다
  • 손댄 것 — 경로를 /tmp/demo 로 줄여 적었다. 숫자는 하나도 고치지 않았다. 이 장비는 다른 작업이 함께 도는 개인용 PC 라 여유 블록 값에 수백 블록 단위의 잡음이 섞여 있고, 그 잡음도 그대로 두었다
  • 블록 크기는 4,096 바이트로 보고된다. 아래 여유 블록 수에 4,096 을 곱하면 바이트가 된다

증상 - df 와 du 가 어긋난다

진단의 출발점은 두 도구가 서로 다른 답을 하는 것이다. du 는 디렉터리를 걸어 다니며 이름이 붙은 파일을 센다. 이름이 없어진 파일은 du 의 시야 밖이다. df 는 파일시스템의 블록 계정을 읽으므로 붙잡힌 공간을 사용 중으로 본다. 그래서 둘이 벌어지고, 벌어진 폭이 곧 붙잡힌 용량이다.

200MiB 파일을 만들고 tail -f 로 붙잡은 채 지운 뒤 df -h 를 그대로 찍었다.

--- rm 전 ---
du -sh . = 200M
  Filesystem   Size  Used Avail Use% Mounted on
  /tmp/demo    931G  601G  331G  65% /tmp

--- rm 후 ---
du -sh . = 0
  Filesystem   Size  Used Avail Use% Mounted on
  /tmp/demo    931G  601G  331G  65% /tmp

--- 붙잡은 프로세스 종료 후 ---
  Filesystem   Size  Used Avail Use% Mounted on
  /tmp/demo    931G  600G  332G  65% /tmp

세 블록을 나란히 읽으면 순서가 분명해진다. rm 은 du 만 200M 에서 0 으로 바꿨고 df 는 한 자리도 움직이지 않았다. df 가 601G/331G 에서 600G/332G 로 바뀐 것은 rm 이 아니라 프로세스를 종료한 뒤였다. 공간을 돌려준 것은 rm 이 아니라 kill 이다.

  • 현장에서 이 증상은 대개 그래프로 먼저 보인다. 정리 작업을 돌렸는데 디스크 사용량 그래프가 계단으로 안 떨어지고 평평하면 이 원인일 가능성이 높다
  • du -sh / 합계와 df 의 Used 를 비교하는 것이 가장 싼 1차 판별이다. 큰 차이가 나면 이름 없는 파일이 있다는 뜻이다
  • 다만 두 값은 원래도 완전히 같지 않다. 예약 블록·저널·마운트로 가려진 디렉터리 때문에 몇 퍼센트 차이는 정상이다. 수십 GiB 단위로 벌어질 때가 신호다
  • 주의할 함정이 하나 있다. du 를 root 가 아닌 계정으로 돌리면 읽을 수 없는 디렉터리가 조용히 빠진다. 이때 생긴 차이는 이 현상과 무관하다

이름은 지워지고 inode 는 남는다

앞 절이 증상이라면 이 절은 원리를 눈으로 확인하는 자리다. 512MiB 파일을 만들고, tail -f 로 붙잡고, 지운 다음 같은 inode 를 파일 서술자를 통해 다시 들여다봤다.

[1] 생성 직후
    name=app.log inode=4503599629412470 links=1 size=536870912 blocks=524288
    free=86810586   du -sh . = 512M

[2] tail -f (pid=1442) 가 열어 둠

[3] rm 직후 - 이름은 사라졌다
    ls -A: []
    du -sh . = 0    free=86811452

[4] 그런데 fd 를 통하면 inode 가 살아 있다
    /proc/1442/fd/3  inode=4503599629412470 links=0 size=536870912 blocks=524288
    readlink        /tmp/demo/app.log (deleted)

[5] 붙잡은 fd 로 여전히 읽힌다
    $ head -c 16 /proc/1442/fd/3 | od -An -tx1
      00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00

[6] kill 후 free=86939254

읽는 순서는 이렇다. inode 번호가 [1] 과 [4] 에서 같다. 지운 뒤에도 같은 객체다. 바뀐 것은 links 하나로, 1 에서 0 이 됐다. 반면 size 와 blocks 는 536870912 와 524288 그대로다. 이름은 없어졌지만 데이터는 한 바이트도 반환되지 않았다는 뜻이다.

여유 블록도 같은 이야기를 한다. rm 전후로 86810586 에서 86811452 로, 866 블록만 움직였다. 4,096 을 곱하면 3.4MiB 남짓이고 이것은 같은 장비에서 도는 다른 작업의 잡음이다. 512MiB 는 131,072 블록인데 그중 아무것도 돌아오지 않았다. 그리고 kill 뒤에 86811452 에서 86939254 로 127,802 블록이 한꺼번에 돌아왔다.

  • links=0 인데 size 가 큰 것 — 이것이 이 상황의 지문이다. 다른 어떤 상태에서도 이 조합은 나오지 않는다
  • 커널이 붙여 주는 (deleted) 꼬리표는 경로 문자열의 일부가 아니라 표시다. 그 문자열을 그대로 cat 에 넘기면 없는 파일이라고 나온다
  • [5] 가 보여 주듯 붙잡은 쪽은 아무 지장 없이 계속 읽고 쓴다. 그래서 응용 프로그램은 이 상황을 오류로 보고하지 않는다
  • 회복이 한꺼번에 일어난다는 점도 기억할 만하다. 조금씩 돌아오다가 멈추는 것이 아니라, 마지막 참조가 닫히는 그 순간에 전량이다

찾는 법 ① /proc 을 직접 훑는다

운영 장비에 lsof 가 없는 경우는 생각보다 흔하다. 최소 설치 이미지, 컨테이너 안, 폐쇄망 서버에서는 도구를 새로 넣는 것 자체가 절차를 요구한다. 그런데 커널이 이미 답을 노출하고 있어서 도구 없이도 된다. 각 프로세스의 /proc/<pid>/fd 는 그 프로세스가 열어 둔 파일들을 가리키는 심볼릭 링크 묶음이고, 대상이 지워진 경우 목적지 끝에 (deleted) 가 붙는다.

# 특정 프로세스 하나만 볼 때
$ ls -l /proc/1442/fd | grep -i deleted
lrwx------ 3 -> /tmp/demo/app.log (deleted)

# 전수 훑기 - 셸만으로
$ for p in /proc/[0-9]*; do
    pid=${p##*/}
    for fd in "$p"/fd/*; do
      tgt=$(readlink "$fd" 2>/dev/null) || continue
      case "$tgt" in *"(deleted)") echo "pid=$pid fd=${fd##*/} -> $tgt";; esac
    done
  done

pid=318  fd=3  -> /tmp/demo/app.log (deleted)
pid=319  fd=3  -> /tmp/demo/app.log (deleted)

# 붙잡힌 크기까지 같이 보고 싶으면
$ stat -L -c '%i %h %s %n' /proc/318/fd/3
16607023627971255 0 268435456 /proc/318/fd/3

이 방식의 값어치는 추가 설치가 필요 없다는 것뿐이 아니다. stat -L 을 붙이면 붙잡힌 용량까지 바로 나오므로, 여러 후보가 나왔을 때 어느 것부터 처리해야 공간이 실제로 도는지를 크기 순으로 정할 수 있다. 반대로 한계도 분명하다.

  • 다른 사용자의 프로세스는 권한이 없으면 안 보인다. 위 순회는 조용히 그 줄을 건너뛰므로, 결과가 비었다고 해서 없는 것이 아니다. 되도록 sudo 로 돈다
  • fd 만 보면 메모리 매핑을 놓친다. 파일을 mmap 한 뒤 서술자를 닫아도 매핑은 참조로 남는다. 그쪽은 /proc/<pid>/maps 에 있다
  • 순회 도중 프로세스가 사라지면 readlink 가 실패한다. 위 관용구가 실패를 넘기는 이유이고, 이 때문에 같은 명령을 두 번 돌리면 결과가 다를 수 있다
  • 프로세스 수가 수천이면 이 순회에도 시간이 든다. 급한 상황이라면 먼저 후보를 좁힌다. 로그를 쓰는 응용 프로그램과 그 로그를 읽어 전송하는 수집기 양쪽이 같은 파일을 잡고 있는 경우가 가장 흔하다

찾는 법 ② lsof - 명령과 읽는 법

표준 도구는 lsof 다. 이 환경에는 설치돼 있지 않아 돌리지 못했다. 그래서 아래에는 출력 예시가 없다. 대신 매뉴얼이 규정하는 동작과, 출력에서 어느 열을 봐야 하는지를 적는다.

# 지워졌는데 열려 있는 파일만 - 이 상황의 정확한 질의
$ sudo lsof +L1

# 마운트로 좁히기 (전체 스캔은 느리다)
$ sudo lsof -nP +L1 /var

# 특정 경로를 누가 열고 있나
$ sudo lsof /var/log/app.log

# 특정 프로세스가 무엇을 열고 있나
$ sudo lsof -p 1234

# 디렉터리 트리 전체 (재귀 - 매우 느릴 수 있다)
$ sudo lsof +D /var/log

핵심 옵션은 +L1 이다. 매뉴얼은 +L 뒤에 숫자를 주면 링크 수가 그 값보다 작은 파일만 나열한다고 적는다. 그러니 +L1 은 링크 수가 0 인 파일, 즉 이름이 전부 지워졌는데 아직 열려 있는 파일을 정확히 고른다. 그리고 +L 을 주면 출력에 NLINK 열이 추가된다.

  • 기본 열 구성은 COMMAND · PID · USER · FD · TYPE · DEVICE · SIZE/OFF · NODE · NAME 이다. 여기서 PID 와 SIZE/OFF 와 NAME 셋만 보면 대체로 끝난다
  • +L 을 주면 NLINK 열이 끼어들어 열 위치가 밀린다. awk '{print $2}' 같은 자리 기반 처리는 옵션을 바꾸는 순간 깨진다. 자동화한다면 열 위치를 옵션마다 다시 확인한다
  • FD 열에는 숫자 외에 cwd·txt·mem 같은 값도 온다. mem 은 메모리 매핑이라 /proc/<pid>/fd 순회로는 안 잡히던 참조다. lsof 가 fd 훑기보다 나은 지점이 여기다
  • 숫자 뒤에 붙는 r·w·u 는 읽기·쓰기·양방향을 뜻한다. 로그 파일을 쓰기로 열고 있는 쪽이 대개 처리 대상이다
  • -n 과 -P 는 이름·포트 변환을 끄는 옵션이다. 매뉴얼도 속도 개선을 이유로 든다. 디스크가 찬 급한 상황에서는 습관적으로 붙이는 편이 낫다
  • +D 는 디렉터리 트리를 재귀로 훑는다. 편하지만 대상이 크면 오래 걸린다. 마운트 단위로 좁히는 쪽을 먼저 시도한다

찾는 법 ③ fuser - 경로에서 프로세스로

fuser 도 이 환경에 없어 돌리지 못했다. 성격이 lsof 와 다르다. lsof 가 목록을 뽑는 도구라면 fuser 는 경로 하나를 물어 그것을 쓰는 프로세스를 답하는 도구다. 이미 파일을 특정했을 때 더 빠르다.

# 이 파일을 누가 쓰고 있나 (ps 형태로)
$ sudo fuser -v /var/log/app.log

# 이 파일시스템 전체를 누가 쓰고 있나 - 언마운트가 안 될 때
$ sudo fuser -vm /var

# 아래 두 줄은 프로세스를 죽인다. 확인 없이 치지 말 것
$ sudo fuser -k  /var/log/app.log     # 즉시 종료
$ sudo fuser -ki /var/log/app.log     # 하나씩 확인하며 종료

-v 를 주면 매뉴얼 표현대로 ps 와 비슷한 형태로 PID·USER·COMMAND 가 나오고, 그 사이에 ACCESS 열이 붙는다. 이 열이 fuser 를 읽는 요령의 전부다. 매뉴얼이 정의하는 문자는 다음과 같다.

문자매뉴얼의 정의이 상황에서의 의미
f열린 파일 (기본 표시에서는 생략된다)읽기로 열고 있다. 수집기·모니터링이 흔하다
F쓰기로 열린 파일 (기본 표시에서는 생략된다)가장 유력한 대상. 지금도 이 파일에 쓰고 있다
mmmap 된 파일 또는 공유 라이브러리매핑으로 잡고 있다. fd 훑기로는 안 잡히던 쪽
c현재 디렉터리거기서 돌고 있을 뿐이다. 언마운트만 막는다
e실행 중인 실행 파일바이너리 자체가 그 파일시스템에 있다
r루트 디렉터리chroot 된 프로세스에서 보인다
위험 — fuser -k 는 매뉴얼 그대로 파일에 접근 중인 프로세스를 죽인다. 경로를 넓게 주면 그 아래를 쓰는 프로세스가 전부 대상이 된다. -m 과 -k 를 같이 주면 그 파일시스템을 쓰는 모든 프로세스가 종료된다. 먼저 -v 로 목록을 보고, 죽일 대상이 그 목록과 정확히 같은지 확인한 뒤에만 -k 를 붙인다. 확인을 원하면 -i 를 함께 주는데, 매뉴얼은 -k 없이 -i 만 주면 조용히 무시된다고 적는다.

붙잡은 쪽이 하나가 아닐 때

실무에서 헛수고가 가장 많이 생기는 자리다. 하나를 찾아 재시작했는데 공간이 그대로면, 대개 도구가 틀린 것이 아니라 참조가 하나가 아니었던 것이다. 256MiB 파일을 두 프로세스가 붙잡게 하고 한쪽씩 종료해 봤다.

[1] 256MiB 생성            free=86679271
[2] rm 완료                free=86680587   ls -A=[]
[3] 남은 참조 전수 조사
    pid=318  fd=3  -> /tmp/demo/app.log (deleted)
    pid=319  fd=3  -> /tmp/demo/app.log (deleted)
[4] 한쪽만 종료 (pid 318)  free=86682346   <-- 아직이다
[5] 나머지도 종료 (pid 319) free=86748978   <-- 이제 돌아온다

[4] 에서 움직인 것은 1,759 블록, 7MiB 남짓의 잡음이다. 256MiB 는 65,536 블록인데 한쪽을 죽여도 아무것도 안 돌아왔다. [5] 에서야 66,632 블록이 한꺼번에 돌아온다. 커널은 참조를 세지 프로세스를 세지 않는다.

  • 그래서 처리 순서는 목록을 먼저 완성하고 나서 손대는 것이다. 하나 찾고 죽이고 다시 보는 방식은 그때마다 목록이 바뀌어 판단이 흔들린다
  • 같은 프로세스가 같은 파일을 여러 서술자로 열고 있는 경우도 있다. 이때는 프로세스 하나만 처리하면 되지만, fd 절단으로 대응하면 번호를 전부 잘라야 한다
  • 전형적인 다중 참조 조합은 정해져 있다. 로그를 쓰는 응용 프로그램, 그것을 읽는 수집기, 그리고 사람이 며칠 전에 띄워 놓고 잊은 tail -f 세션이다
  • 부모가 열어 둔 파일을 자식이 상속받은 경우도 흔하다. 부모만 재시작하면 자식이 그대로 붙잡고 있다

윈도우 - 누가 잠갔는지 찾아내기

윈도우에서는 증상 자체가 다르게 나타난다. 지운 파일이 공간을 무는 것이 아니라 애초에 지워지지 않는다. 사용 중이라는 메시지가 뜨는데 정작 어느 프로그램인지는 알려 주지 않는 것이 보통이다.

여기서 실제로 쓸 만한 것은 Restart Manager API 다. 마이크로소프트 문서는 이 API 의 목적을 설치·업데이트 도중 파일을 쓰고 있는 응용 프로그램을 종료했다가 다시 시작해 재부팅을 줄이는 것이라고 설명한다. 그 과정에 필요한 것이 정확히 우리가 원하는 정보, 즉 이 파일을 지금 누가 쥐고 있는가다. 관리자 권한 없이 동작하고, 별도 설치도 필요 없다.

Add-Type -Namespace Rm -Name Api -MemberDefinition @'
[StructLayout(LayoutKind.Sequential)]
public struct RM_UNIQUE_PROCESS { public int dwProcessId;
  public System.Runtime.InteropServices.ComTypes.FILETIME ProcessStartTime; }
[StructLayout(LayoutKind.Sequential, CharSet = CharSet.Unicode)]
public struct RM_PROCESS_INFO {
  public RM_UNIQUE_PROCESS Process;
  [MarshalAs(UnmanagedType.ByValTStr, SizeConst = 256)] public string strAppName;
  [MarshalAs(UnmanagedType.ByValTStr, SizeConst = 64)]  public string strServiceShortName;
  public int ApplicationStatus; public uint TSSessionId;
  [MarshalAs(UnmanagedType.Bool)] public bool bRestartable; }
[DllImport("rstrtmgr.dll", CharSet = CharSet.Unicode)]
public static extern int RmStartSession(out uint h, int flags, string key);
[DllImport("rstrtmgr.dll")] public static extern int RmEndSession(uint h);
[DllImport("rstrtmgr.dll", CharSet = CharSet.Unicode)]
public static extern int RmRegisterResources(uint h, uint nFiles, string[] files,
  uint nApps, RM_UNIQUE_PROCESS[] apps, uint nSvc, string[] svc);
[DllImport("rstrtmgr.dll")]
public static extern int RmGetList(uint h, out uint needed, ref uint count,
  [In, Out] RM_PROCESS_INFO[] arr, ref uint reasons);
'@

$h = 0
[void][Rm.Api]::RmStartSession([ref]$h, 0, [guid]::NewGuid().ToString())

이 환경에서 실제로 돌린 결과다. 같은 파일을 두 번 물었고, 두 번째는 다른 프로세스가 공유 없이 열어 둔 상태였다.

=== A. 아무도 안 잡고 있을 때 ===
holders of: C:\tmp\demo\locked.txt
  (none - no process holds this file)

=== B. 다른 프로세스가 잡고 있을 때 ===
holders of: C:\tmp\demo\locked.txt
  PID 25328   Windows PowerShell     restartable=True
  • PID 와 함께 restartable 이 나온다는 점이 실용적이다. 참이면 그 프로그램은 종료 후 재시작을 견디도록 등록돼 있다는 뜻이라 조치 판단이 쉬워진다
  • 첫 RmGetList 호출이 234(ERROR_MORE_DATA)를 돌려주는 것은 실패가 아니라 필요한 배열 크기를 알려 주는 정상 흐름이다. 이 값을 오류로 처리하면 결과가 늘 비어 보인다
  • 탐색기의 파일이 사용 중 대화상자가 프로그램 이름을 보여 줄 때가 있는데, 그것이 바로 이 API 다. 같은 정보를 스크립트로 뽑는 것뿐이다
  • GUI 로 같은 일을 하려면 리소스 모니터(resmon)의 CPU 탭에 있는 연결된 핸들 검색 상자에 파일명을 넣으면 된다. 이 글은 GUI 를 캡처하지 않았으므로 화면 설명은 여기까지만 적는다

윈도우 - 잘 안 되는 방법들

검색하면 자주 나오지만 실제로는 잘 안 되는 방법이 둘 있다. 둘 다 돌려 봤고, 왜 안 되는지가 오히려 쓸모 있다.

PS> openfiles /Local
오류: 로그온한 사용자는 관리자 권한을 가지고 있지 않습니다.

PS> openfiles /Query /FO TABLE
정보: 로컬에서 열린 파일을 보려면 시스템 글로벌 플래그
      'maintain objects list'을 사용하도록 설정해야 합니다.
로컬 공유 지점을 통해 원격으로 열린 파일:
오류: 액세스가 거부되었습니다.

PS> # Modules 로 찾기 - DLL 은 나온다
PS> Get-Process | Where-Object { $_.Modules.FileName -contains
      'C:\WINDOWS\System32\kernel32.dll' } | Select-Object -First 3 Id,ProcessName
   Id ProcessName
   -- -----------
19744 AMDInstallManager
11128 AMDRSSrcExt
21760 ApplicationFrameHost

PS> # 같은 방식으로 데이터 파일을 찾으면
PS> Get-Process | Where-Object { $_.Modules.FileName -contains $target }
(결과 0건)

openfiles 는 두 겹으로 막힌다. 로컬 목록을 보려면 maintain objects list 라는 시스템 전역 플래그를 켜야 하는데, 그것을 켜는 openfiles /Local ON 자체가 관리자 권한을 요구하고 적용에는 재부팅이 필요하다. 즉 이미 문제가 난 뒤에 켜서 쓸 수 있는 도구가 아니다. 플래그가 꺼진 상태에서 /Query 가 답하는 것은 공유를 통해 원격으로 열린 파일뿐이다.

Get-Process 의 Modules 는 결이 다르다. 아예 안 되는 것이 아니라 대상이 다르다. 이 목록에 담기는 것은 프로세스에 로드된 실행 이미지, 즉 EXE 와 DLL 이다. 위 출력에서 kernel32.dll 은 잘 찾아냈다. 그러나 로그 파일이나 데이터 파일은 모듈이 아니므로 영원히 0 건이다.

  • 정리하면 이렇다. DLL 이 잠겨 갱신이 막힌 상황이면 Modules 검색으로 충분하고, 그 밖의 파일이면 앞 절의 Restart Manager 쪽으로 간다
  • Sysinternals 의 handle 계열 도구가 널리 쓰이지만 이 환경에는 설치돼 있지 않아 돌리지 못했다. 그래서 이 글에는 그 출력이 없다
  • 실제 상황에서 잠금의 범인이 백신·백업·색인 서비스인 경우가 꽤 있다. 이들은 파일을 잠깐 열었다 닫으므로 같은 조회를 몇 초 간격으로 두 번 해 보면 성격이 갈린다

재시작이 답이지만 재시작을 못 할 때

붙잡은 쪽을 찾았다면 조치는 단순하다. 재시작이 가장 확실하다. 로그 파일이라면 재시작 대신 로그 재개 신호로 충분한 경우도 많다. 그런데 운영 중인 서비스라 둘 다 지금은 못 한다면, 널리 알려진 우회가 하나 있다. 열린 파일 서술자를 직접 잘라 내는 것이다.

위험 — 아래 방법은 되돌릴 수 없고 확인 절차도 없다. 파일 서술자 번호를 하나 잘못 고르면 그 프로세스가 열어 둔 다른 파일이 통째로 비워진다. 실행 전에 readlink /proc/<pid>/fd/<n> 로 목적지를 눈으로 확인하고, 그것이 (deleted) 표시가 붙은 로그 파일이 맞는지 본 뒤에만 손댄다. 재시작이 가능하면 재시작이 언제나 안전한 쪽이다. 
# 1) 반드시 먼저 - 무엇을 자르려는지 눈으로 확인
$ readlink /proc/957/fd/3
/tmp/demo/big.log (deleted)

# 2) 그 다음에만 - 서술자 절단 (되돌릴 수 없음)
$ : > /proc/957/fd/3

# 이 환경에서 나온 결과
[A] rm 후                free=86771292
    fd: inode=16607023627971255 links=0 size=268435456 blocks=262144
[B] : > /proc/957/fd/3
    tail: big.log: file truncated
    절단 시도 후: size=0  blocks=262144
    free=86770524                     <-- 안 돌아왔다
[C] truncate -s 0 /proc/957/fd/3
    size=0  blocks=262144
    free=86769107                     <-- 여전히
[D] kill 후               free=86833972

결과를 정직하게 읽어야 한다. 절단 자체는 통했다. size 가 268435456 에서 0 이 됐고, 붙잡고 있던 tail 이 file truncated 라고 반응한 것이 그 증거다. 그런데 여유 블록은 돌아오지 않았고 blocks 도 262144 그대로였다. 실제 반환은 kill 뒤인 [D] 에서 일어났다.

여기서 결론을 서두르면 안 된다. 이 환경의 /proc 은 리눅스 커널의 procfs 가 아니라 MSYS 가 흉내 낸 것이고, 그 아래는 NTFS 다. 리눅스에서 같은 결과가 나온다는 근거가 되지 못한다. 다만 이 실패에서 가져갈 교훈은 환경과 무관하게 유효하다. 절단이 통했는지는 size 가 아니라 df 로 확인해야 한다. 크기 표시가 0 이 됐다는 것과 공간이 돌아왔다는 것은 별개의 사실이다.

그리고 이 방법에는 대상 제한이 있다. 로그에는 통하고 데이터 파일에는 통하지 않는다. 이유는 파일을 다루는 방식이 다르기 때문이다.

  • 로그 파일 — 대개 추가 모드로 열려 끝에만 덧붙인다. 앞부분이 사라져도 다음 쓰기는 새 끝에서 이어진다. 잘라도 응용 프로그램의 세계관이 깨지지 않는다
  • 데이터 파일·DB 파일 — 오프셋을 계산해 특정 위치를 읽고 쓴다. 잘라 낸 순간 프로세스가 기억하는 구조와 파일 실제가 어긋난다. 다음 읽기가 0 으로 채워진 영역을 정상 데이터로 해석하면 손상은 조용히 번진다
  • 추가 모드가 아닌 로그 — 오프셋을 유지한 채 쓰는 구현이면 잘라도 파일 크기가 원래 오프셋까지 다시 커진다. 앞부분이 0 으로 채워진 희소 파일이 되어 겉보기 크기만 크고 실제 사용량은 작은 상태가 된다
  • 여러 서술자로 열린 파일 — 하나만 잘라서는 다른 서술자가 그대로 붙잡고 있다. 앞 절에서 본 그대로다

잠금은 다른 이야기다

여기까지가 지워졌는데 열려 있는 파일 이야기였다. 파일 잠금은 이름이 비슷하고 증상도 겹쳐 보이지만 별개의 기제다. 그리고 이 지점에서 리눅스와 윈도우가 정확히 갈린다.

유닉스의 flock 은 권고적이다. 매뉴얼은 이렇게 적는다. 적절한 권한이 있으면 프로세스는 다른 프로세스의 flock 사용을 무시하고 입출력을 수행할 자유가 있다. 즉 잠금은 참여하기로 한 프로그램들 사이의 약속이지 커널이 강제하는 벽이 아니다. 그래서 리눅스에서는 다른 쪽이 잠갔다는 이유로 rm 이 실패하는 일이 없다.

윈도우는 다르다. 다만 흔한 오해와도 다르다. 윈도우가 무조건 막는 것이 아니라, 파일을 여는 쪽이 열 때 공유 모드를 정하고 커널이 그것을 강제한다. CreateFile 문서는 공유 모드가 0 이면 그 파일은 공유될 수 없고 핸들이 닫힐 때까지 다시 열 수 없다고 적고, 충돌하는 요청은 ERROR_SHARING_VIOLATION 으로 실패한다고 적는다. 실제로 확인해 보면 같은 파일이 공유 모드에 따라 정반대로 갈린다.

=== 공유 모드 None 으로 연 파일 ===
PS> Remove-Item $target
ERR: IOException
MSG: The process cannot access the file ... because it is being used by another process.
PS> Rename-Item $target renamed.txt      -> 같은 오류
PS> Get-Content $target                  -> 같은 오류

$ stat -c 'inode=%i links=%h size=%s' locked.txt
inode=6192449489676514 links=1 size=19       # 메타데이터는 읽힌다
$ cat locked.txt
cat: locked.txt: Device or resource busy
$ rm locked.txt
rm: cannot remove 'locked.txt': Device or resource busy
$ ls -l
-rw-r--r-- 1 ... 19 Sep  2 09:12 locked.txt  # 그대로 남아 있다

=== 같은 파일을 공유 모드 ReadWrite, Delete 로 연 경우 ===
$ cat shared.txt
share-delete payload
$ rm -v shared.txt
removed 'shared.txt'                          # 성공. 프로세스는 아직 살아 있다
$ ls -A
(비어 있음)

두 블록의 차이는 파일도 아니고 지우는 명령도 아니다. 여는 쪽이 무엇을 허용했는가 하나다. 공유 없이 연 파일은 삭제·이름 변경·읽기가 전부 막혔고, 공유 목록에 삭제를 포함해 연 파일은 붙잡은 프로세스가 살아 있는데도 이름이 즉시 사라졌다. 뒤쪽은 유닉스와 사실상 같은 모양이다.

구분리눅스 / 유닉스윈도우
잠금의 성격권고적. 참여하는 프로그램끼리의 약속열 때 정한 공유 모드를 커널이 강제
사용 중인 파일 삭제항상 성공. 이름만 사라진다여는 쪽이 삭제를 허용했을 때만 성공
실패했을 때 보이는 것실패하지 않는다사용 중이라는 메시지 · Device or resource busy
그래서 생기는 문제공간이 조용히 안 돌아온다배포·갱신이 시끄럽게 막힌다
찾는 도구lsof · fuser · /procRestart Manager · 리소스 모니터
흔한 오해rm 이 데이터를 지운다윈도우는 사용 중이면 무조건 못 지운다

실무적으로 남는 것은 이것이다. 윈도우에서 배포가 파일 잠금으로 막힌다면, 고칠 자리는 지우는 쪽이 아니라 여는 쪽이다. 로그를 여는 코드가 삭제 공유를 허용하면 회전이 막히지 않는다.

컨테이너 - pid 가 관점마다 다르다

컨테이너에서 이 작업이 어려워지는 이유는 도구가 없어서가 아니라 pid 와 경로가 관점마다 다르기 때문이다. 호스트에서 lsof 를 돌려 얻은 pid 를 컨테이너 안에서 kill 에 넘기면 엉뚱한 프로세스를 죽인다. 반대도 같다.

컨테이너 자체는 이 환경에서 돌리지 못했다. 다만 같은 성질의 어긋남은 여기서도 그대로 나온다. MSYS 는 자기만의 pid 를 쓰고 윈도우 커널은 별도의 pid 를 쓴다.

$ tail -f hold.log > /dev/null &
$ echo $!
1410

$ ls -l /proc/1410/fd | grep -i deleted
lrwxrwxrwx 3 -> /tmp/demo/hold.log (deleted)

$ ps -W | head -1
      PID    PPID    PGID     WINPID  TTY   UID    STIME COMMAND
$ ps -W | grep 1410
     1410    1405    1403        580  ?  197609 09:18:32 /usr/bin/tail

셸이 아는 pid 는 1410 인데 커널이 아는 pid 는 580 이다. 같은 프로세스이고, 어느 쪽도 틀리지 않았다. 번역표 없이 한쪽 숫자를 다른 쪽에 넘기면 안 된다는 것이 요점이고, 컨테이너의 pid 네임스페이스에서 벌어지는 일도 성질이 같다. 아래는 그 상황에서 확인할 자리들이다.

  • 호스트에서 본 pid 를 컨테이너 안의 pid 로 옮기려면 번역이 필요하다. 리눅스에서는 /proc/<host-pid>/status 의 NSpid 줄에 두 값이 나란히 적힌다
  • 경로도 어긋난다. 컨테이너 안의 /var/log/app.log 는 호스트에서 보면 오버레이 상위 계층 어딘가의 긴 경로다. 호스트에서 잡은 lsof 결과의 경로를 컨테이너 경로로 착각하지 않는다
  • 컨테이너 안에 lsof 도 /proc 접근 권한도 없는 경우가 많다. 그럴 때는 호스트에서 보는 편이 빠르다. 호스트의 /proc/<pid>/root/ 아래에 그 컨테이너의 파일시스템이 그대로 보인다
  • 가장 흔한 실수는 컨테이너를 재시작하면 해결된다고 보고 로그 볼륨은 그대로 두는 것이다. 붙잡은 프로세스가 컨테이너 밖의 로그 수집기라면 컨테이너를 몇 번 재시작해도 공간은 돌아오지 않는다
  • 오케스트레이터가 붙어 있으면 사람이 죽인 프로세스를 다시 띄운다. 새로 뜬 프로세스가 같은 파일을 다시 잡는지까지 확인해야 조치가 끝난다

네트워크 파일시스템의 .nfs 파일

NFS 에서는 같은 상황이 눈에 보이는 형태로 나타난다. 지운 파일이 사라지지 않고 .nfs 로 시작하는 이름으로 남아 있는 것을 본 적이 있을 것이다. 이것은 고장이 아니라 NFS 클라이언트가 POSIX 동작을 흉내 내려고 하는 일이고, 보통 sillyrename 이라고 부른다.

사정은 이렇다. 로컬 파일시스템에서는 이름이 사라져도 열린 참조가 있으면 계속 읽을 수 있다. NFS 프로토콜은 이것을 직접 지원하지 않는다. 그래서 클라이언트 커널이 지우는 대신 .nfsXXXX 형태의 이름으로 옮겨 둔다. 리눅스 NFS 위키의 설명대로, 클라이언트는 해당 vnode 가 비활성이 될 때 그 새 이름을 지운다. NFS 마운트는 이 환경에 없어 직접 재현하지 못했다.

  • 그러므로 .nfs 파일은 지워야 할 쓰레기가 아니라 표지다. 아직 누가 열어 두고 있다는 뜻이므로, 붙잡은 프로세스를 찾아 정리하면 이름은 저절로 사라진다
  • 지우려고 해도 잘 안 된다. 참조가 살아 있는 동안에는 클라이언트가 그 이름을 보호한다
  • 같은 위키가 적는 예외가 있다. rename 과 remove 사이에 클라이언트가 죽으면 서버에 쓰레기 파일이 남는다. 이 경우에만 진짜로 지워야 할 대상이 되고, 판단 기준은 클라이언트를 재부팅한 뒤에도 남아 있는지다
  • 이 흉내 내기는 클라이언트가 하나일 때만 성립한다. 다른 클라이언트가 그 파일을 열고 있는지 알 방법이 없으므로, 여러 클라이언트가 같은 파일을 공유하는 배치에서는 열려 있는 파일이 지워지는 상황이 가능하다
  • rmdir 이 비어 보이는 디렉터리에서 실패하는 것도 같은 이유다. ls -a 로 보면 .nfs 파일이 안에 있다

애초에 안 생기게 하는 법

이 상황을 만드는 원인은 사실상 하나로 수렴한다. 로그 회전 설정이 조용히 어긋나 있는 것이다. 파일을 옮기거나 지운 뒤 프로세스에게 다시 열라는 신호를 주지 않으면, 프로세스는 이름 없는 옛 파일에 계속 쓴다. 회전이 어떻게 이 상황을 만드는지는 로그 회전이 조용히 실패하는 자리 쪽에서 따로 다룬다.

설계 쪽에서 할 수 있는 것도 있다. 임시 파일이 필요할 때는 열자마자 이름을 지우는 관용구가 있다. 이름이 없으므로 다른 프로세스가 건드릴 수 없고, 프로세스가 어떤 식으로 끝나든 커널이 알아서 공간을 반환한다. 정리 코드를 짤 필요가 없어진다.

# 열자마자 unlink - 익명 임시 파일
$ exec 9> tmpdata
$ rm tmpdata                      # 이름은 여기서 사라진다
$ echo "hello anonymous" >&9      # 그래도 쓰기는 계속 된다
$ ls -A
(비어 있음)
$ stat -L -c 'inode=%i links=%h size=%s' /proc/self/fd/9
inode=16325548651260599 links=0 size=16
$ exec 9>&-                       # 닫는 순간 공간 반환. 정리 코드 불필요

# 모니터링에 넣을 값 - df 와 du 의 차이
$ used_df=$(df -k --output=used /var | tail -1)
$ used_du=$(du -sk /var 2>/dev/null | cut -f1)
$ echo "gap_kb=$(( used_df - used_du ))"
  • 모니터링에 df 와 du 의 차이를 지표로 넣어 두면 이 상황이 사고가 되기 전에 보인다. 절대값이 아니라 추세를 본다. 평소 폭에서 벗어나 계속 벌어지면 붙잡힌 파일이 쌓이는 중이다
  • du 는 큰 파일시스템에서 부담이 크므로 주기를 길게 잡는다. CephFS 처럼 전수 순회가 비싼 파일시스템에서는 이 방식 자체를 피하고 파일시스템이 제공하는 재귀 통계를 쓴다
  • 로그를 쓰는 쪽과 읽는 쪽 양쪽 모두에 재개 신호가 전달되는지 확인한다. 응용 프로그램만 신호를 받고 수집기가 못 받으면 절반만 놓는다
  • 회전을 이름 바꾸기가 아니라 내용 비우기 방식으로 하면 이 문제가 원천적으로 생기지 않는다. 대신 회전 순간에 기록되는 줄이 유실될 수 있다는 대가가 있다
  • 사람이 남기는 tail -f 세션도 원인이 된다. 조사 목적으로 띄운 세션은 끝나면 닫는다는 습관 하나로 없앨 수 있는 부류다

급할 때 순서

디스크가 찬 상태에서는 판단할 시간이 없다. 그래서 순서를 미리 정해 두는 편이 낫다. 아래는 확인이 싼 것부터 위험한 것 순이다.

순서할 것보는 값여기서 하면 안 되는 것
1실패한 경로를 df 에 직접 준다그 경로가 정말 그 파일시스템인가루트 줄만 보고 판단하기
2du -sh 합계와 df 의 Used 비교차이가 수십 GiB 인가차이를 즉시 원인으로 단정하기

4같은 파일의 참조를 전부 모은다부모·자식·수집기·사람 세션하나 죽이고 다시 세기
5재시작 또는 로그 재개 신호df 여유가 계단으로 뛰는가kill -9 를 먼저 쓰기

위험 — kill -9(SIGKILL)는 프로세스에 정리할 기회를 주지 않는다. 버퍼에 남은 로그가 사라지는 정도로 끝날 수도 있지만, 쓰기 도중이던 파일이 중간 상태로 남을 수도 있다. 먼저 기본 종료 신호로 보내고, 몇 초 기다린 뒤에도 살아 있을 때만 강제 종료를 쓴다. 어느 쪽이든 데이터베이스나 상태를 가진 프로세스에는 마지막 수단이다.
  • 3번에서 후보가 0 건으로 나오면 권한부터 의심한다. 다른 사용자의 프로세스는 조용히 빠진다
  • 5번을 하고도 df 가 안 움직이면 4번으로 돌아간다. 도구가 틀린 것이 아니라 참조가 남아 있는 것이다
  • 급한 상황에서 지울 것을 더 찾는 방향으로 가면 대개 시간을 잃는다. du 와 df 가 어긋나 있다면 지우는 것으로는 해결되지 않는다
  • 조치가 끝난 뒤에는 같은 파일이 다시 잡히는지를 한 번 더 본다. 회전 설정이 그대로면 며칠 뒤 같은 자리로 돌아온다
  • 메모리 쪽이 원인일 때는 증상이 비슷해 보여도 다른 문제다. 그 갈래는 OOM Killer 가 무엇을 골랐는지 읽는 법 쪽에 있다

정리

rm 은 이름을 지우는 명령이다. 데이터를 지우는 것은 마지막 참조가 닫히는 순간의 커널이다. 그래서 이 상황의 해결은 파일을 또 지우는 것이 아니라 붙잡은 쪽을 놓게 만드는 것이고, 그러려면 먼저 누가 붙잡고 있는지를 특정해야 한다.

특정하는 길은 셋이다. lsof +L1 은 링크 수가 0 인 열린 파일만 정확히 고른다. fuser -v 는 경로 하나를 물어 프로세스를 답하고 ACCESS 열이 성격을 알려 준다. 둘 다 없으면 /proc/<pid>/fd 를 셸로 훑으면 되고, (deleted) 꼬리표가 답을 대신한다. 윈도우에서는 증상이 반대로 나타나며 Restart Manager 가 그 답을 내놓는다.

그리고 잊기 쉬운 두 가지가 있다. 참조는 하나가 아닐 수 있다는 것, 그리고 파일 서술자 절단은 로그에는 통하고 데이터 파일에는 통하지 않는다는 것이다. 이 둘을 놓치면 조치를 했는데도 df 가 움직이지 않거나, 움직였는데 다른 것이 망가진다.

확인하지 못한 것

  • lsof 와 fuser 는 이 환경에 설치돼 있지 않아 한 번도 실행하지 못했다. 해당 절의 명령과 열 설명은 각 도구의 매뉴얼에 근거한 것이고, 실행 출력은 이 글에 없다. 버전과 배포판에 따라 열 구성이 달라질 수 있으므로 자동화 전에 각자의 장비에서 한 번 확인하는 편이 낫다
  • 파일 서술자 절단은 이 환경에서 size 만 0 이 되고 여유 블록은 돌아오지 않았다. MSYS 의 /proc 이 리눅스 커널의 procfs 가 아니고 그 아래가 NTFS 이므로, 리눅스 ext4·XFS 에서 같은 결과가 나오는지는 확인하지 못했다. 이 글은 그 환경의 결과를 단정하지 않는다
  • 컨테이너와 pid 네임스페이스는 직접 재현하지 못했다. 본문에 실은 pid 어긋남은 MSYS 와 윈도우 커널 사이의 것이고, 성질이 같다는 유비로 적은 것이지 컨테이너에서 뽑은 출력이 아니다. /proc/<pid>/status 의 NSpid 줄도 이 환경에서는 확인하지 못했다
  • NFS 마운트가 없어 .nfsXXXX 파일을 직접 만들어 보지 못했다. 해당 절은 리눅스 NFS 위키의 설명에 근거한 것이다
  • Sysinternals 의 handle 계열 도구는 설치돼 있지 않아 돌리지 못했고, 그래서 이 글은 그 도구의 출력을 인용하지 않았다. 리소스 모니터도 GUI 라 화면 캡처 없이 조작 위치만 적었다
  • openfiles /Local ON 을 실제로 켜서 플래그가 활성화된 상태의 동작은 확인하지 못했다. 관리자 권한과 재부팅이 필요하기 때문이다. 본문의 두 오류 메시지는 꺼진 상태에서 나온 실제 출력이다
  • 여유 블록 값에 섞인 잡음은 제거하지 않았다. 이 장비에서 다른 작업이 함께 도는 탓이며, 수백에서 수천 블록 단위의 흔들림은 그 때문이다. 재현할 때 같은 숫자가 나오지는 않는다
