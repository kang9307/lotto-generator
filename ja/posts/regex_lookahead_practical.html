先読みは位置だけを見る - 幅ゼロで解く正規表現の問題

マッチに含まれないからこそできること - 条件の重ね掛け、境界だけを残す置換、重なるマッチ、そしてハングルで最初に崩れる箇所

2026-08-11 開発・インフラ

序論: 条件は掛けたいが、結果には入れたくない

ログから ERROR の入った行だけを抜き出しつつ、timeout の入った行は除かなければならない。grep をパイプでつなぐ。その次は、その行から host= の後ろの値だけが必要になる。パイプをもう一本つないで sed で前の部分を切り落とす。パイプが四つほどになると、そのコマンドは読み返しても何をしているのか分からなくなる。

置換ではこの問題がもっと露骨に出る。password=hunter2 を password=*** に変えなければならない。password= まで一緒にマッチさせなければ hunter2 だけを取り出す方法がないのに、マッチさせると置換のときにそれまで消えてしまう。そこでキャプチャグループで捕まえておいて $1 で付け直す。キーが一つのうちは耐えられるが、三つになると番号を数え始めることになる。

この二つの状況には共通点がある。条件としては必要だが、結果としては不要な部分があるということだ。ルックアラウンドはまさにこの地点のために存在する。条件は検査しつつ、マッチには含めず、次のマッチが始まる位置も動かさない。この性質を幅ゼロ(zero-width)と呼ぶ。

たいていの解説はここで記号を四つ紹介して終わる。ところが実務で値打ちが出るのは記号ではなく、幅がゼロであることから派生する結果のほうだ。条件をいくつでも同じ位置に重ねて積めるし、境界に触れずに値だけを変えられるし、互いに重なり合うマッチを数えられる。この記事はそちら側に紙幅を使う。

実行環境。以下の出力は Windows 10 Pro 上の Node.js v22.16.0、Python 3.13.3 と 3.11.9、Perl 5.38.2、GNU grep 3.0 を基準にしている。ハングルの入ったパターンはシェル引数として渡すとエスケープが剥がれるため、すべてスクリプトファイルに保存して実行した結果である。

範囲。エンジンごとに文法が分かれる問題の全般はどこでも動く正規表現で扱う。ここでは後読みの一点だけを短く押さえる。ハングル正規表現の罠そのものはハングル正規表現の罠が本拠地であり、この記事はルックアラウンドという道具が韓国語のどこで空回りするかだけを見る。

1. 幅ゼロ - 検査はするが食べはしない

言葉で言うと抽象的なので、長さを測ってみればよい。

A1 match = "foo" | length = 3 | index = 0
A2 lastIndex after exec(g): 3
A3 replace = Xbar
A4 without lookahead = X
A5 consuming = "foobar"

パターンは /foo(?=bar)/、入力は foobar だ。bar が後続するかを確かに検査したにもかかわらず、マッチ文字列は foo の三文字である。もっと重要なのは lastIndex だ。消費していたなら 6 であるべきところが 3 になっている。カーソルが bar の手前で止まっているという意味であり、次のマッチはそこから再び始まる。

だから置換結果が Xbar になる(A3)。条件として使った bar は原文にそのまま残る。消費するパターン /foobar/ で同じ置換をすると X だけが残る(A4)。条件に使った部分を結果に復活させるためにキャプチャグループを使う必要がないこと、これが第一の実用的な価値だ。

幅がゼロだという言葉は文字どおりの意味である。ルックアラウンドだけでできたパターンは空文字列にマッチする。

C1 split by zero-width = [ 'one', 'Two', 'Three' ]
C2 empty match array = [ '' ]
C3 empty match str  = ""

'abc'.match(/(?=b)/) のマッチ文字列は長さ 0 の空文字列だ。位置情報だけがあって中身がない。'oneTwoThree'.split(/(?=[A-Z])/) が文字を一つも失わずに三つに分かれるのも同じ理由である。区切り文字を消費しないので大文字がそのまま残る。

2. 四つのルックアラウンドとそれが立つ位置

記号は四つ、軸も二つだけだ。どちら側を見るか(前/後ろ)とあるべきか、あってはならないか(肯定/否定)の組み合わせである。

記号名称見る方向成功条件
(?=...)肯定先読み現在位置の右側右側が ... で始まる
(?!...)否定先読み現在位置の右側右側が ... で始まらない
(?<=...)肯定後読み現在位置の左側左側が ... で終わる
(?<!...)否定後読み現在位置の左側左側が ... で終わらない

同じ文字列に四つを掛けてみると、それぞれが何を選り分けるのかが鮮明になる。

입력: price: 100USD, 200EUR, 300USD

B1 /\d+(?=USD)/g       = [ '100', '300' ]
B2 /\d+(?!\d)(?!USD)/g = [ '200' ]
B3 /(?<=price: )\d+/g   = [ '100' ]

입력: a1 b2 c3
B4 /(?<![ab])\d/g      = [ '3' ]

2.1 否定先読みがバックトラッキングで破られる場所

B2 に (?!\d) がなぜもう一つ付いているのかが、この節の核心だ。それなしで /\d+(?!USD)/g だけを使うとこうなる。

입력: 100USD 200EUR

K1 /\d+(?!USD)/g       = [ '10', '200' ]
K2 /\d+(?!\d)(?!USD)/g = [ '200' ]
K4 첫 매치 = "10"

USD の付いた 100 を除外しようとしたパターンが 10 を返す。エンジンはまず \d+ で 100 を捕まえて (?!USD) を検査し、失敗すると、あきらめずに消費する長さを縮めながら条件を回避する方法を探す。10 まで縮めればその右側は 0USD であり、これは USD で始まらないので否定条件が通ってしまう。

否定先読みはまさにその位置に対する判定にすぎず、「この数字の塊全体の後ろに USD がない」という意味ではない。だから右端を (?!\d) で釘付けにして、\d+ が短くなる余地をなくさなければならない。否定条件を掛けるときは、マッチの境界が固定されているかをまず確認すること。これがルックアラウンドで最も頻繁に起きる論理エラーだ。

2.2 キャプチャは肯定側でしか生き残らない

L1 /(?!(\d+))X/ 의 그룹 1 = undefined
L2 /(?=(\d+))\d+/ 의 그룹 1 = 123 | 전체 매치 = 123

否定先読みの中のグループには値が残らない。否定条件は内部のマッチが失敗してこそ成功するので、成功した時点ではグループに詰めるものがない。逆に肯定先読みの中のグループは正常にキャプチャされる。5 節の重なるマッチはこの性質の上に立っている。

3.「A はあって B はない行」 - 条件を同じ位置に積む

序論のログ問題だ。ルックアラウンドは位置を動かさないので、いくつも並べて付ければ全部が同じ地点で判定される。行頭に条件をいくつでも重ねて積めるという意味である。

$ grep -P '^(?=.*ERROR)(?!.*timeout)' app.log
2026-08-11 10:00:01 ERROR db connect failed host=db01 retry=1
2026-08-11 10:00:04 ERROR auth rejected user=svc_batch
2026-08-11 10:00:06 ERROR db connect failed host=db02 retry=2

ERROR upstream timeout の行は二番目の条件で落ち、INFO timeout tuning applied の行は一番目の条件で落ちた。条件をもう一つ乗せるのも、ただもう一つ書けばよい。

D2 /^(?=.*ERROR)(?!.*timeout)(?=.*(db|auth))/ 매치 = 2건
D3 순서를 바꿔도 같은 결과 = true
D4 소비형 /ERROR.*db/ : 'db ERROR' → false, 'ERROR db' → true

D3 がこの節の要点だ。条件どうしに順序依存がない。先読みはカーソルを動かさないので、一番目を検査したあともカーソルは依然として行頭にある。だから順序を入れ替えて書いても結果は同じであり、条件をあとから追加するときにどこへ挟み込むか悩む必要がない。

消費するパターンで同じことをやろうとすると、この自由が消える(D4)。/ERROR.*db/ は文書に ERROR が db より先に現れるときだけ合う。ログフォーマットが変わってフィールドの順序がひっくり返ると、静かに何も捕まえなくなる。

3.1 フィルタと抽出を一度に

条件の組み合わせに \K を付ければ、パイプ四本ぶんのコマンドが一つに畳まれる。

$ grep -oP '^(?=.*ERROR)(?!.*timeout).*?host=\K\S+' app.log
db01
db02

$ grep -oP '(?<=retry=)\d+' app.log
1
2

$ grep -oP '\w+(?==)' app.log | sort -u
host pool retry user

最後のものは等号の前のキー名だけを抜き出す。(?==) は目には奇妙に映るが「等号が後続する位置」という意味であり、等号自体は消費しないので出力には現れない。

4. 置換で境界だけを捕まえる

値は変えるがキーは残さなければならない置換だ。後読みで左の境界を「検査だけ」すれば、キャプチャグループは要らない。

입력: user=admin&password=hunter2&host=db01&token=abc123def

E1 /(?<=password=)[^&]+/g  → '***'
   user=admin&password=***&host=db01&token=abc123def
E2 /(password=)[^&]+/g     → '$1***'
   user=admin&password=***&host=db01&token=abc123def
E3 /(?<=(?:password|token)=)[^&]+/g → '***'
   user=admin&password=***&host=db01&token=***

E1 と E2 は結果が同じだ。キャプチャグループでもできる仕事だという意味であり、ここだけを見れば好みの問題である。差が開くのは E3 だ。キーが複数に増えても置換文は依然として *** ひと塊である。キャプチャ方式ならグループ番号を数えながら $1 を管理しなければならず、あとでグループをもう一つ入れた瞬間に番号がずれて静かに壊れる。

4.1 まったく消費しない置換

もっと極端なほうはマッチ文字列が空文字列である置換だ。何も消さずに位置へ差し込むだけである。

F1 '1234567'      .replace(/\B(?=(\d{3})+(?!\d))/g, ',') = 1,234,567
F2 '999'          .replace(같은 패턴, ',')              = 999
F3 '1000'         .replace(같은 패턴, ',')              = 1,000
F4 '123456789012' .replace(같은 패턴, ',')              = 123,456,789,012

V1 'oneTwoThreeID'  .replace(/(?<=[a-z])(?=[A-Z])/g, '_') = one_two_three_id
V2 'HTTPServerError'.replace(/(?<=[A-Z])(?=[A-Z][a-z])/g, '_') = HTTP_ServerError

三桁区切りのパターンを分解すると条件は三つだ。単語境界でないこと(\B、先頭にカンマが付くのを防ぐ)、右側に三桁の塊が続くこと、その塊の後ろに数字がもうないこと。三つとも幅ゼロなのでマッチ文字列は空文字列であり、置換は純粋な挿入になる。

V2 は略語の処理だ。HTTPServerError を大文字ごとに切ると H_T_T_P_... になってしまう。「大文字の後ろであり、かつ大文字の次に小文字が来る位置」へ条件を狭めれば、略語の塊はくっついたままで単語の境界だけで分かれる。左と右を同時に見るこうした条件は、消費型のパターンでは表現しにくい。

4.2 すでに処理された箇所は飛ばす

입력: see http://a.example and <a href="http://b.example">b</a>
패턴: /(?<!href=")http:\/\/\S+?(?=[\s<])/g → '[LINK]'
결과: see [LINK] and <a href="http://b.example">b</a>

裸の URL だけをリンクに変え、すでにタグの中にあるものは放っておくというのはよくある要求だ。否定後読みで href=" の後ろでないことを掛け、先読みで右の境界を捕まえつつ、その文字は消費しない。消費していたら結果から空白や不等号が消えていたはずだ。

4.3 マスキング

$ echo '카드 4111111111111111 로 결제' | perl -pe 's/\d(?=\d{4})/*/g'
카드 ************1111 로 결제

「後ろに数字が四つ以上残っている数字」だけをアスタリスクに変える。桁数を数えたり長さを計算したりはしない。条件が位置で表現されているので、カード番号の長さが十六でも十四でも同じパターンがそのまま動く。

5. 重なるマッチ - 幅ゼロだからできること

正規表現エンジンはマッチを見つけると、その終わりへカーソルを移す。だから重なり合うマッチを見つけられない。

H1 'AAAA'.match(/AA/g)                    = [ 'AA', 'AA' ]
H2 [...'AAAA'.matchAll(/(?=(AA))/g)]      = [ 'AA', 'AA', 'AA' ]
H3 그 위치                                 = [ 0, 1, 2 ]

H4 'ABABABA'.match(/ABA/g)                = [ 'ABA', 'ABA' ]
H5 [...'ABABABA'.matchAll(/(?=(ABA))/g)]  = 위치 [ 0, 2, 4 ]

AAAA に含まれる AA は位置 0、1、2 の三つだ。ところが消費型のパターンは二つしか数えない。0 で見つけてカーソルが 2 へ進むときに位置 1 を飛ばしてしまうからである。

(?=(AA)) はこの問題を迂回する。外側のマッチは幅ゼロなのでカーソルは一つずつしか前進せず、実際に見つけたい文字列は先読みの内側のキャプチャグループから取り出す。2.2 節で見た「肯定側のキャプチャは生き残る」がここで使われる。

5.1 幅ゼロマッチの無限ループ

この技法には落とし穴が一つ付いている。exec を直接回すとカーソルが前進せず止まらない。

const r = /(?=a)/g;
let m;
while ((m = r.exec('aaa')) !== null) {
  // ...
  if (m.index === r.lastIndex) r.lastIndex++;   // 이 줄이 없으면 끝나지 않는다
}
M1 결과 = 3
M2 [...'aaa'.matchAll(/(?=a)/g)].length = 3

マッチ長が 0 だと lastIndex がそのままなので、同じ位置を永遠に探し直す。matchAll と replace(/.../g) は内部でこの処理をしてくれるので安全だ。幅ゼロのパターンに exec ループを直接使わず、matchAll を使うこと。この落とし穴は他の言語にもそのままあり、Perl でも pos() を手で押し進めてやらなければならない。

$ echo 'AAAA' | grep -oP '(?=(AA))'
(출력 없음 - 매치가 빈 문자열이라 -o 가 찍을 것이 없다)

$ echo 'AAAA' | perl -ne 'while (/(?=(AA))/g) { print "$1 at ", pos(), "\n"; pos() = pos() + 1 }'
AA at 0
AA at 1
AA at 2

6. 単語境界を自分で定義する

\b も幅ゼロの条件だ。ただし単語文字の定義が固定されているので、その定義が自分のデータと合わないと手を入れる方法がない。ルックアラウンドはその定義を自分で書かせてくれる。

パターンマッチ数捕まるもの
/cat\b/g3cat、cat-x の前半、concat の後半
/cat(?!s)/g4上の三つ + catx の前半
/cat(?![a-z])/g3cat、cat-x、concat
/(?<![a-z])cat(?![a-z])/g2cat、cat-x だけ

入力は cat cats catx cat-x concat だ。\b はハイフンを境界と見なすので cat-x を捕まえ、concat の末尾も捕まえる。それが望む動作でないなら、両側を否定ルックアラウンドで自分で塞ぐことが唯一の方法である。

ハングルではこの違いが好みではなく、動くか動かないかを分ける。

입력: 고양이 고양이들 왕고양이

T6 /\b고양이\b/g                    = null
T7 /(?<![가-힣])고양이(?![가-힣])/g = [ '고양이' ]

\b は一文字も捕まえられない。\b の単語文字の定義が [A-Za-z0-9_] なのでハングルはそもそも単語文字ではなく、空白と 고 のあいだは両側とも非単語文字なので境界が成立しない。例外も警告もなく null が返る。韓国語のテキストで語単位の検索が必要なら、\b を捨ててルックアラウンドで境界を自分で定義しなければならない。

7. パスワード規則 - できることとできないこと

先読みが最も広くコピー&ペーストされる用途だ。「文字種が混ざっているか」を複数の条件として積み上げる。

/^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[^A-Za-z0-9]).{12,}$/

PASS | Passw0rd!1234
FAIL | passw0rd!1234     (대문자 없음)
FAIL | PASSW0RD!1234     (소문자 없음)
PASS | Password!1234
PASS | Pw0!aaaaaaaaaaaa

意図したとおりに動く。ところが実際に使うと引っかかる限界が三つあり、三つとも先読みの落ち度ではなく、この道具でやろうとした仕事がそもそも正規表現の仕事ではないために生じる。

7.1 どこで落ちたのかを教えてくれない

結果は真か偽の一つだけだ。利用者に「大文字と記号が抜けていて、あと四文字必要です」と伝える情報がない。条件を分割すればその情報が生まれる。

규칙을 조각으로 나눠 각각 판정:
I7 'passw0rd' 미충족 = 대문자, 특수문자, 12자 이상

正規表現ひとつに条件を全部積むのは検査結果を捨てる設計だ。判定だけが必要なサーバー側の最終確認なら一行のほうがよく、利用者に案内しなければならない画面なら分割するほうがよい。両方で使うのなら、断片の配列ひとつを真実の源として置き、必要なときに合成するほうが食い違わない。

7.2 長さを数える単位が人間と違う

J1 'Passw0rdAB😀'  사람이 센 글자 = 11 | .{12,} 가 센 것 = 12 | 통과 = true
J2 'Passw0rdABc!'  사람이 센 글자 = 12 | .{12,} 가 센 것 = 12 | 통과 = true
J3 이모지가 특수문자 조건을 충족시킨다 = true
J5 같은 J1 입력에 u 플래그를 붙이면      = false

J1 が問題だ。利用者は十一文字を入力したのに「12 文字以上」の規則を通過した。JavaScript の . が UTF-16 コード単位を数えるため、絵文字ひとつが二つとして計算されたのである。おまけに絵文字の片割れが [^A-Za-z0-9] に引っかかって記号条件まで満たしてしまう。u フラグを付ければコードポイント単位になり、正常に戻る(J5)。

ハングルは正規化形式によって分かれる。

K1 '비밀번호입니다'  NFC 길이 = 7 | NFD 길이 = 17
K2 /^.{12,}$/       NFC = false | NFD = true

画面上まったく同じに見える文字列が、どの形で入ってきたかによって同じ規則を通過したり落ちたりする。入力の境界で normalize('NFC') を一度掛けておくのが対策であり、この問題の全容はハングル正規表現の罠のほうに整理されている。

7.3 規則を通ったからといって良いパスワードではない

I2 통과 = true  | Password1234!
I3 통과 = true  | Qwerty12345!
I4 통과 = false | correct horse battery staple   (28자)

最も一般的な流出リストの上位が通過し、28 文字の文章は落ちる。文字構成の規則はエントロピーを測る道具ではなく、形を測る道具だ。先読みでどれほど精巧に積み上げても、この隔たりは縮まらない。長さの下限を上げ、流出リストとの照合を付けるほうが効き目が大きい。通過させる形をまず決めるという考え方そのものは、禁止リストは常に後手に回るで扱った許可リストの議論と同じ流れにある。

8. 後読みと可変長 - エンジンが分かれる一点

先読みは、まともなバックトラッキングエンジンならたいてい備えている。分かれるのは後読みの長さが固定でなければならないかの一点だけだ。理由は実装にある。前を見るときは現在位置から右へ読み進めればよいが、後ろを見るときはどこから読み始めるかを先に知らなければならない。長さが固定ならその分だけ左へ下がればよく、可変なら下がる距離を一つずつ試してみるしかない。

エンジン(確認バージョン)先読み固定長後読み可変長後読み根拠
JavaScript (Node.js 22.16)OOO — 制限なし実行
Python re (3.13.3 · 3.11.9)OOX — コンパイル拒否実行
Perl 5.38.2OO△ — 有界のみ、上限 255実行
PCRE (GNU grep 3.0 -P)OO△ — 選択は可、無限量指定子は拒否実行

エラーメッセージを直接見れば、各エンジンがどこに線を引いているのかがはっきりする。

[Python 3.13.3]
(?<=price: )\d+     → ok
(?<=price:\s+)\d+   → error: look-behind requires fixed-width pattern
(?<=ab|abc)\d       → error: look-behind requires fixed-width pattern
(?<=a{1,3})\d       → error: look-behind requires fixed-width pattern

[Perl 5.38.2]
(?<=price: )\d+     → compiled
(?<=price:\s+)\d+   → ERROR: Lookbehind longer than 255 not implemented
(?<=ab|abcd)\d      → compiled
(?<=a{1,3})\d       → compiled
(?<=a{1,300})\d     → ERROR: Lookbehind longer than 255 not implemented

[Node.js 22.16]
(?<=price:\s+)\d+   → 'price:    100' 에서 100
(?<=ab|abc)\d       → 'xab7 yabc8' 에서 7, 8
(?<=a{1,3})\d       → 'aaa9' 에서 9

線が三か所に別々に引かれている。Python は長さの異なる選択すら拒否する。Perl と PCRE は有界であれば受け入れ、無限量指定子で止まる。JavaScript はすべて受け入れる。移植性を考えるなら、後読みは固定長でのみ使うことが安全な下限線だ。

8.1 可変長が必要なときの代替案

  • \K を使う。PCRE と Perl には「ここまではマッチから外せ」という印がある。password=\K[^&]+ は password= を消費したあとに結果から捨てる。前へ読み進めるので長さの制約がない。
  • キャプチャグループで戻す。どこでも通じる最小公倍数だ。(password=)[^&]+ を $1*** に置換すれば、Python・POSIX sed・Go まですべて同じ結果になる。
  • 二段階に分ける。広めに捕まえてマッチさせたあと、プログラム側で切り出す。パターンが短くなり読みやすくなるという副次的な効果がある。
  • Python ならサードパーティの regex モジュールが可変長後読みに対応している。ただし標準ライブラリではないので依存が一つ増える。
  • 後読みをまったく使わない設計もある。ログや設定のように自分でフォーマットを制御しているデータなら、区切り文字を一意にしておくことで話が終わる。パターンが精巧になるほど、それはたいていデータが曖昧だという合図であって、正規表現の腕前が必要だという合図ではない。
$ perl -pe 's/password=\K[^&]+/***/'     → user=a&password=***&x=1
$ sed -E 's/(password=)[^ ]+/\1***/'    → user=a&password=***&x=1
  Python: re.sub(r'(password=)[^&]+', r'\1***', s) → user=a&password=***&x=1

8.2 POSIX ERE はエラーを出さない

表の中で最も危険なマスだ。ルックアラウンドがないこと自体は問題ではないのだが、ないと言ってくれない。

입력 파일: foobar / foobaz
의도: bar 가 뒤따르는 foo 만

$ grep -oE 'foo(?=bar)' input.txt
(출력 없음)
$ echo $?
1
$ grep -oP 'foo(?=bar)' input.txt
foo

# ERE 가 (?=bar) 를 무엇으로 읽었나
입력에 foo?=bar / foo=bar / foobar 를 넣고 같은 ERE 패턴을 돌리면
$ grep -oE 'foo(?=bar)' input2.txt
foo=bar

ERE において (?=bar) は「等号で始まる =bar があってもなくてもよいグループ」程度に解釈される。だから foo=bar というまったく別の文字列に合い、本来意図した foobar には合わず、終了コードはただの 1 だ。スクリプトで grep -E と grep -P を取り違えると、「マッチがない」という正常な結果に見える沈黙が返ってくる。ルックアラウンドを使うなら -P を明示し、そのスクリプトが -P のないビルドで動く可能性を確認すること。

8.3 後読みは右から左へ合わせる

R1 /(?<=(\d+))$/.exec('1234')[1]  = "1234"
R3 /(?<=(\d+))/ .exec('1234')[1]  = "1"

同じ後読みなのに結果が違う。R3 はアンカーがないので最も左の成功位置であるインデックス 1 でマッチし、そこから左へ読むと 1 の一つだけだ。R1 は $ があるために末尾でしか成功せず、そこから左へ貪欲に読んで 1234 の全部を持っていく。MDN も同じ性質を説明しながら、/(?<=([ab]+)([bc]+))$/ が abc で a と bc をキャプチャするという例を挙げている。後ろのグループが先に貪欲さを発揮するという意味だ。後読みの中にグループを二つ以上置くと、貪欲さの向きが直感と逆に見える。

9. 先読みで韓国語の語尾を除外しようとするとき

「아니」を探しつつ「아니요」は除きたい。自然な試みは /아니(?!요)/ だ。

HIT  이것은 사실이 아니다
miss 이것은 사실이 아닙니다      ← 의도하지 않은 누락
HIT  이것은 사실이 아니라고 들었다
miss 이것은 사실이 아니요        ← 의도한 배제
miss 이것은 사실이 아님          ← 의도하지 않은 누락

除外したかった「아니요」はきれいに外れた。ところが「아닙니다」と「아님」まで一緒に外れてしまった。ここで先読みを直し始めると時間を無駄にする。先読みには何の落ち度もない。前半の 아니 がそもそもマッチしていないので、否定条件は検査される機会すらなかったのだ。

N2 '아닙니다'.indexOf('아니') = -1
N3 '아님'.indexOf('아니')     = -1
N4 니 = U+B2C8  닙 = U+B2D9  님 = U+B2D8

ハングルの音節は初声・中声・終声を合成して作られたひとつのコードポイントだ。終声(パッチム)が付くと前の文字が別の文字に置き換わる。だから語幹が部分文字列として残らない。原理はハングル正規表現の罠に整理されており、ここで見るべきはこの性質がルックアラウンドの使い方に及ぼす影響のほうだ。

順序がひっくり返る。英語なら語幹を捕まえておいて、先読みで望まない活用形を削ぎ落とせばよい。韓国語ではまず終声の位置を開いてマッチが成立するようにしてから、はじめて先読みが意味を持つ。

/아[니닙님](?!요)/ 로 자리를 연 뒤:
HIT  이것은 사실이 아니다
HIT  이것은 사실이 아닙니다
HIT  이것은 사실이 아니라고 들었다
miss 이것은 사실이 아니요
HIT  이것은 사실이 아님

これで先読みが本来の仕事をする。除外条件に手を入れる前に、包含条件が一度でも合ったことがあるかをまず確認すること。否定先読みの失敗は結果が減る形で現れるが、マッチ自体が 0 件であることも同じく結果がない形なので、区別がつかない。

9.1 ルックアラウンドで終声を判定することはできない

連体形語尾の「ㄹ」が付いた位置を探したいとしよう。[을ㄹ] で開けばよさそうに見える。

miss 할 수 있다
miss 갈 예정이다
HIT  먹을 만하다
miss 하는 중이다

四つのうち一つしか捕まらない。「먹을」は「을」が独立した音節なので合ったが、「할」と「갈」の ㄹ は音節の中に収まった終声であり、独立した文字ではない。文字クラスでもルックアラウンドでもアクセスできない。終声の判定は文字比較ではなく算術である。

종성 인덱스 = (코드포인트 - 0xAC00) % 28

할 = 8 (ㄹ)   하 = 0 (없음)   갈 = 8 (ㄹ)

산술로 판정하면:
HIT  할 수 있다   (종성 = ㄹ)
HIT  갈 예정이다  (종성 = ㄹ)
HIT  먹을 만하다  (종성 = ㄹ)
miss 하는 중이다  (종성 = ㄴ)

正規表現にできる仕事ではない。韓国語の形態条件はルックアラウンドへ押し込まず、コードへ追い出すこと。ルックアラウンドを使える場所は、音節がまるごと境界の役目を果たす場合に限られる。

P1 '재고가 있음, 재고가 없음'.match(/(?<=재고가 )있음/g) = [ '있음' ]
P2 '재고가 있음, 재고가 없음'.match(/(?<!없)음/g)        = [ '음' ]

この程度、つまり音節単位できっちり割り切れる条件であればルックアラウンドはよく合う。固定長なのでどのエンジンでも動くという利点もある。

10. 性能 - 本当に危険なのは何か

「先読みは遅い」という話がよく出回るが、測ってみると危険の所在は別のところにある。50 万字の入力に条件数だけを増やしてみた結果だ。

입력 길이 500,004자

조건 1개  : 0.276 ms
조건 2개  : 0.422 ms
조건 4개  : 0.734 ms
한 번 훑기 : 5.291 ms   ← 같은 판정을 손으로 구현
길이 가드 : 0.00004 ms  ← 128자 넘으면 정규식을 돌리지 않음

条件を四つに増やしても、一つのときの三倍を超えない。入力を何度も走査するのは事実だが、走査の回数が条件数に比例するだけである。もっと目を引くのは、同じ判定を文字ループで自分で書いたほうが七倍遅いという事実だ。文字クラスのスキャンはエンジン内部で最適化された経路を通るので、「正規表現が遅そうだから手で書いた」がかえって損になる場合が多い。

10.1 本当の危険 - ルックアラウンドの中の入れ子量指定子

패턴: /^(?=(a+)+$)/     입력: 'a' * n + 'b'

n=20    6.6 ms
n=22   27.2 ms
n=24  108.6 ms
n=26  431.4 ms
n=28 1764.6 ms
n=30 7104.6 ms

二文字増えるごとに四倍だ。n=30 で 7 秒かかるパターンは、n=40 になれば人が待てる時間ではない。これが ReDoS の典型であり、原因は先読みではなく、その中にある (a+)+ だ。量指定子の付いたグループにさらに量指定子を付けると、同じ文字列を分割する方法が指数的に増え、マッチが失敗するときにそのすべての場合を試すことになる。

先読みが状況を悪くする地点は一つある。先読みは毎回失敗しなければならない条件を作りやすい。否定先読みは定義上、内部のマッチが最後まで失敗してこそ成功するので、中に爆発するパターンを入れると最悪の経路が常に実行される。一方、入れ子なしで書いた /^(?=a+$)/ は 10 万字の入力でも 0.15 ミリ秒だ。

10.2 対策

  • 長さの上限を正規表現より先に検査する。最も安上がりで、最も確実だ。上の表で 0.00004 ミリ秒の行がそれである。パスワード・ID・ファイル名のように上限が自明な入力なら、これだけで事実上決着がつく。
  • 入れ子の量指定子を作らない。(a+)+、(a|a)*、(\s*)+ の形をパターンレビューのチェック項目に入れておく。
  • 利用者がパターンを入力する場所ではバックトラッキングエンジンを使わない。Go の regexp や Rust の regex は入力長に対して線形の時間を保証する代わりに、ルックアラウンドを提供しない。このトレードオフは偶然ではなく、同じ設計判断の表と裏である。
  • タイムアウトがあれば掛ける。.NET のように正規表現の実行に時間制限を掛けられるランタイムがある。根本的な解決ではないが、障害を遅延に変えてくれる。
  • 否定先読みの中は特に単純に保つ。そこは正常な入力でも毎回最後まで探索される区間だ。
  • パターンを定数として固定する。文字列を連結して正規表現を作ると、利用者の入力がパターン自体に混ざり込み、爆発する形が偶然できあがる。値はパターンではなく引数として渡すこと。

11. 確認できなかったこと

  • Java java.util.regex の可変長後読み。この環境に JDK がないため実行で確認できなかった。8 節の表の該当マスを空けておいた理由だ。
  • .NET の可変長後読み。同じ理由で実行確認ができなかった。ルックアラウンド自体に対応していることまでを文書ベースで記した。
  • Go regexp の動作。Go ツールチェーンがないため、表の該当行は regexp/syntax の文書が列挙する幅ゼロ条件の一覧(^ $ \A \b \B \z)にルックアラウンドがないという事実に基づいている。実行で確認したものではない。
  • 最新の PCRE2 の可変長後読み。表の PCRE 行は GNU grep 3.0 にリンクされたビルドを基準にしている。PCRE2 はその後のリリースでこの制約を緩和したと言われているが、この環境では確認できなかった。PCRE とひとくくりにせず、使っているビルドで直接コンパイルしてみること。
  • ReDoS の数値の移植性。10 節の測定値は V8 が基準だ。指数的に伸びるという性質はバックトラッキングエンジンに共通するが、具体的なミリ秒と閾値の n はエンジンとハードウェアによって変わる。絶対値ではなく増加率を見ること。
  • Unicode プロパティエスケープとルックアラウンドの組み合わせ。6 節のハングル境界の例は [가-힣] で書いたが、これは完成形の音節しか覆わない。字母単独や分解された形まで必要な場合の動作は、この記事では扱わなかった。

結論: 何を捕まえるかではなく、どこで捕まえるか

ルックアラウンドを「条件をもっと付ける文法」として学ぶと、パスワード検証の一行をコピーして使うところで止まる。その場面では実のところキャプチャグループでもたいてい間に合う。この道具が値打ちを発揮するのは条件と結果を分離しなければならない場所だ。

  • 条件に使った文字が結果に残らなければならないとき — 境界だけを捕まえる置換
  • 複数の条件が同じ地点で判定されなければならないとき — 順序に縛られないフィルタ
  • カーソルが前進してはならないとき — 重なるマッチ
  • エンジンが決めた境界の定義が自分のデータと合わないとき — 自分で書く \b
  • 左と右を同時に見なければならないとき — 略語の境界のように双方向の条件が必要な場所

判断基準を一つに絞るとこうなる。マッチ結果に含まれてはならない条件があるか。あればルックアラウンドであり、なければたいていもっと単純なパターンで足りる。

そして二つを習慣にしておけば事故が減る。第一に、後読みは固定長で使う。Python は長さの異なる選択すら拒否し、Perl と PCRE は無限量指定子で止まる。可変長がどうしても必要なら、\K やキャプチャグループへ降りてくるほうが移し替えやすい。第二に、否定条件を掛けるときはマッチ境界も一緒に固定する。\d+(?!USD) が 10 を返していた場面がその理由だ。

最後に、韓国語を扱うなら順序をひっくり返さなければならない。先読みで活用形を削ぎ落とす前に、包含条件が一度でもマッチしたことがあるかをまず確認すること。マッチ 0 件と除外がうまくいった状態は、結果の画面ではまったく同じ見た目をしている。
