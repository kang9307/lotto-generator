Building a LoadBalancer Outside the Cloud

From a pending EXTERNAL-IP to ARP proxying and asymmetric routing

Jul 28, 2026 Dev & Infra

Introduction: the day EXTERNAL-IP would not budge

Almost everyone who moves from managed Kubernetes to on-premises hardware or a homelab meets the same screen. You create a Service with type: LoadBalancer, and minutes later the EXTERNAL-IP column is still pending.

$ kubectl get svc web
NAME   TYPE           CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
web    LoadBalancer   10.96.31.10    <pending>     80:31942/TCP   12m

Most people start digging through logs at this point. But there is no error to fix here. This is not a failure; it is the absence of a counterparty. The Kubernetes documentation is unusually direct about it: if the cloud provider supports load balancers, an external IP address is provisioned for the Service, and the cloud provider is responsible for assigning that address. No provider, no address.

A post that surfaced on GeekNews in July 2026 turned this abstract point into something very concrete. To use an IPv4 address leased from a carrier over DHCP as the external address of a Kubernetes LoadBalancer, the author ended up writing a DHCP client that never puts the address on an interface, an eBPF program that answers ARP on its behalf, and finally a fix for asymmetric routing. You can read it as a success story, but I think its real value lies elsewhere: it honestly exposes how many independent layers hide behind a single checkbox in the cloud.

So this article is not a tour of one implementation. It decomposes the question what do you actually have to build to make a LoadBalancer Service work outside a cloud, layer by layer, spells out the cost attached to each option, and lays out where to look when it breaks. Whether you end up using MetalLB, Cilium, or something you wrote yourself, the structure below makes the decision much faster.

1. Who hands out the IP in the cloud - the real contract behind type LoadBalancer

1.1 Kubernetes does not create addresses

Clear one misconception first. There is no load balancer implementation inside Kubernetes. Declaring type: LoadBalancer is closer to filing a request than issuing an instruction. What actually happens is this:

  • A user creates a Service of type LoadBalancer
  • An external controller observes the request; in a cloud that is the cloud-controller-manager
  • The controller obtains an address in its own environment and provisions whatever load balancing resource it owns
  • It writes the resulting address into status.loadBalancer.ingress on the Service
  • Only then does the EXTERNAL-IP column in kubectl get svc fill in

EXTERNAL-IP is therefore a report of a result, not a command. Accept that, and the on-premises task defines itself: you must stand up something that fills in that status.

1.2 When you want a specific address

Historically you asked for a specific address with spec.loadBalancerIP, but that field is now marked deprecated in the documentation, because implementations interpreted it inconsistently and it cannot express dual stack. Two mechanisms replaced it:

  • Implementation-specific annotations — each controller defines its own way to request an address or a pool. Less portable, more expressive
  • spec.loadBalancerClass — selects which implementation should handle this Service when several load balancer controllers coexist in the cluster. Particularly useful on premises when MetalLB shares a cluster with another controller

1.3 On premises, two separate jobs appear

This is the most important distinction in the whole article. What looked like one operation in the cloud splits into two jobs of completely different character on premises.

  • Allocation — which address does this Service get. An IPAM problem: manage a pool and hand out addresses without collisions
  • Announcement — how does traffic for that address reach your cluster. Either link-layer ARP and NDP, or a network-layer routing protocol

The two are independent, and Cilium exposes that split structurally. Per its documentation, LB IPAM only picks addresses from a CiliumLoadBalancerIPPool and assigns them to Services, while advertising those addresses is the job of separate features such as the BGP control plane or L2 Announcements. MetalLB is built the same way internally.

This is exactly why on-premises troubleshooting is confusing. An address appearing in EXTERNAL-IP means allocation succeeded; it is no evidence at all that the address is reachable. The state where an address is assigned but nothing connects almost always lives in the announcement layer.

Any service that needs real client addresses in its logs needs this setting, and yet, as we will see, Local collides with some announcement mechanisms.

2. Three families of on-premises solutions - L2, BGP, and building it yourself

There are broadly three ways to solve the announcement problem. It helps to classify them not by product name but by which layer you tell the fib on.

2.1 Layer 2 mode - answering on someone else's behalf at the link layer

This is the most widely deployed approach. To paraphrase MetalLB's own documentation, in this mode one machine in the cluster takes ownership of the Service and uses standard address discovery protocols, ARP for IPv4 and NDP for IPv6, to make those IPs reachable on the local network. Technically, that node is made to look as though its interface holds several addresses.

The advantage is decisive: you do not have to touch a router. The switch does not need to know either. In offices and homelabs where you have limited rights over network gear, this is effectively the only realistic option. But the documented costs are equally clear.

  • Bandwidth is capped at one node. In the documentation's words, all traffic for a Service IP goes to one node. Adding nodes does not raise the ingress ceiling for that Service
  • Failover depends on the clients. MetalLB sends unsolicited link-layer packets announcing the MAC change; most modern operating systems handle it within seconds, but poorly behaved clients keep using the stale MAC until their cache expires
  • For planned failover the documentation recommends keeping the old leader alive for several minutes so it can forward traffic from clients with stale caches
  • Leader election is stateless. Each speaker independently computes a sorted list of hashed node-plus-VIP entries and announces if it ranks first. Adding a node may change the leader
  • Split brain is an acknowledged risk. If speakers wrongly consider each other inactive during a partition, several speakers, or none, may announce the same VIP

Cilium's L2 Announcements lives under the same physics. Its documentation notes that because hosts store only one MAC per IP, only one node in the cluster may reply, and so each Service maps to a Kubernetes Lease whose holder answers. Several practical conditions come attached:

  • It is documented as beta, and kube-proxy replacement mode must be enabled
  • Lease acquisition is first come, first served, which the documentation says may cause asymmetric load across nodes
  • It is stated to be incompatible with externalTrafficPolicy: Local, because Service IPs may be announced on nodes without pods and traffic gets dropped. If you need source IP preservation, avoid this combination from the start
  • Clients that reject gratuitous ARP will not re-query until their own table entry ages out, so they can experience a longer outage than the lease timings suggest

kube-vip works on the same principle in ARP mode: its documentation describes broadcasting gratuitous ARP when the virtual IP moves between nodes to update the IP-to-MAC mapping, with leader election backed by Kubernetes Leases. Whatever the implementation, the ceiling of what the link layer can do is identical.

2.2 BGP mode - telling the routers about a path

In BGP mode each node establishes a peering session with nearby routers and advertises the path to the Service IP. The routers treat the nodes as equal-cost next hops and spread traffic with ECMP. The single-node bottleneck disappears, and router policy becomes available as a control surface.

And here sits the most consistently underestimated trap in on-premises load balancing, one MetalLB warns about directly. Routers pick a next hop by hashing header fields, commonly a three-tuple of protocol and source and destination IP, or a five-tuple that adds ports. That keeps packets of one session on one node. The problem is what comes next.

Whenever the size of the backend set changes, existing connections will be rehashed effectively randomly. — MetalLB BGP documentation

The moment you reboot one node or one BGP session drops, connections that had nothing to do with that node get reassigned to different nodes. The new node holds no state for them, so they break. The mitigations the documentation offers are compromises rather than fixes: use resilient ECMP hashing on the routers, pin deployments to specific nodes, schedule changes during quiet hours, migrate between Services via DNS, add client-side retries, put an ingress controller layer in front, or simply accept occasional resets for non-critical services.

In practice the most workable answer is usually the last two combined: expose only a handful of ingress controllers over BGP and keep applications behind them. That confines the blast radius of rehashing to the ingress layer.

2.3 Building it yourself - when the tool's premise does not hold

The third family is to write your own. It sounds reckless, but when the assumption a tool is built on simply does not hold in your environment, it can be the only option left. This case is exactly that.

MetalLB assumes the operator knows the address pool. As the documentation puts it, MetalLB cannot create IP addresses out of thin air, so an administrator has to supply pools. In an environment where addresses arrive from a carrier over DHCP, that assumption collapses: you cannot know in advance which addresses you will get, and they may change. Requests for external IPAM and DHCP integration have sat in the project's issue tracker for years, but implementing dynamic allocation would break the assumption that the core logic can stay single-threaded, and reworking that has not been undertaken.

If you do build one, writing down how it works and how to diagnose it is part of the implementation, not an optional extra.

3. What changes on a carrier circuit - the constraints DHCP imposes

Before anything else. How many addresses you may use, whether running servers is permitted, and how static addressing is offered all differ by plan and are defined in your contract and terms of service. What is technically possible and what is contractually permitted are different questions, so read the terms and, if needed, ask the provider before you start building. This article covers how the network behaves and how to diagnose it; it does not describe ways to work around provider policy.

3.1 A DHCP address is a lease, not property

This is the most fundamental constraint. RFC 2131 defines the combination of the client identifier or hardware address and the assigned network address as the unique identifier of the lease. And leases are finite. A client tries to renew by unicast at T1, and if that fails it retries by broadcast at T2. If the server concludes that the client's notion of its address is wrong, or that the lease has expired, it sends a DHCPNAK.

Viewed as a service address, that carries weight. An address changing is not an incident; it is normal operation. So the design has to include the following as expected scenarios:

  • Renewal can fail and the address can be reclaimed. What happens to the Service that was using it
  • After a reboot or line switch you may receive a different address. Who updates DNS
  • When the address changes, certificates, firewall allowlists and external registrations all drift out of sync
  • If the DHCP client process dies, the lease expires silently. Is that process actually monitored

3.2 One MAC per address

The second constraint is identity. Because a lease is bound to an identifier, obtaining several addresses means issuing several requests under distinct identifiers. That is why the original case created multiple virtual interfaces, each with its own MAC: there is no clean way to obtain several leases through a single physical interface.

A practical caution follows. Upstream network equipment may limit how many MAC addresses a port may learn, or treat unexpected MACs as an anomaly. Such policies exist for good reasons, to keep the network stable, so they are not something to work around but a design constraint to confirm in advance.

3.3 The gateway and the firewall are not yours

The third constraint is where control ends. In a cloud the network is effectively all yours; on a carrier circuit everything beyond the default gateway belongs to someone else. That boundary produces several consequences:

  • Packets whose source address does not match expectations may be filtered upstream. This is the root of the asymmetric routing problem discussed later
  • Some ports may be blocked upstream, which no amount of local configuration will reveal
  • Header fields such as QoS marks may be rewritten as they cross the boundary. RFC 2474 assumes codepoints can be re-marked when entering another domain
  • On circuits that bundle internet and broadcast services, cabling or configuration changes can affect the other service

4. Answering ARP on behalf of an address - what breaks and what you gain

4.1 Why something has to answer

ARP is the protocol by which an IPv4 host broadcasts the question, whoever owns this IP, please tell me your MAC address. A router or client on the same link cannot send a frame until it receives that reply. Because a Service IP is not a real device address but a virtual address the cluster claims, if nobody answers on its behalf, that address effectively does not exist on the link.

The simplest approach is to genuinely put the address on a node interface and let the kernel answer. That brings side effects peculiar to on-premises setups:

  • Since the address is local, the node may short-circuit traffic to it internally
  • The kernel may select it as a source address, producing unintended source IPs on outbound traffic
  • If no listener is bound to the port, the kernel immediately answers with a connection refusal, even where being silently ignored would be preferable
  • Putting the same address on multiple nodes produces an address conflict

Hence the phrase quiet DHCP client in the original case. The choice is to take the lease but never put the address on an interface. As far as the Linux stack is concerned the address does not exist, so none of the above can happen. In exchange, nobody is left to answer ARP, and a separate responder becomes necessary.

4.2 The problems that arrive with proxying

The moment you take over ARP replies, the following arrive together. The shape is the same regardless of tooling.

  • There must be exactly one truth. Hosts cache one MAC per IP, so if two parties answer, the later reply wins. A mechanism guaranteeing a single responder, that is leader election, is mandatory
  • Caches do not update instantly. After a leader change, clients keep using the old MAC until entries expire, and some implementations ignore gratuitous ARP entirely
  • Gratuitous ARP is treated with suspicion. The same technique is used for spoofing, so ignoring it is a common policy. Assuming a broadcast was accepted is unsafe
  • Security features conflict with it. Switch features such as dynamic ARP inspection and port security exist precisely to block unauthorised address claims. In such environments, agreeing the design with the network administrators in advance is mandatory
  • Node failure equals service failure. In layer 2 mode, when the answering node dies the address is unreachable until a new leader is elected and caches refresh

Linux does expose knobs for neighbour behaviour such as arp_ignore, arp_announce and arp_filter, and in multi-homed setups they genuinely matter. However, an address that was never put on an interface is outside the kernel's management entirely, so those switches cannot help. That is exactly why a separate responder, in user space or in XDP, is needed.

5. Choosing eBPF and XDP to answer ARP

5.1 XDP sits in front of the stack

XDP is a hook that runs an eBPF program at the very start of the driver receive path, that is before the packet reaches the kernel network stack. The program's return value decides what the driver does next. The main actions per the kernel documentation are:

  • XDP_DROP — drop the packet by recycling it back into the RX ring it arrived on. The simplest and fastest action
  • XDP_PASS — hand it to normal kernel stack processing
  • XDP_TX — bounce the packet back out the same NIC it arrived on, usually after modifying its contents
  • XDP_ABORTED — signals a program error and the packet is dropped. Not a value functional code should return

It becomes obvious why an ARP responder fits here. Take the ARP request frame, swap sender and target, rewrite it as a reply, and return XDP_TX: a complete reply leaves on the wire even though the kernel stack has never heard of the address. That dovetails logically with the decision not to put the address on an interface.

5.2 What you gain and what you pay

The benefits are real:

  • The address is never exposed to the stack. The source-selection surprises and unwanted connection refusals above simply cannot occur
  • Any address can be added instantly. Updating a map is enough, with no interface reconfiguration, which suits environments where addresses change dynamically
  • No stack overhead. Broadcast ARP requests are handled at the entrance instead of travelling up the stack

The costs are equally definite:

  • Debugging gets much harder. Nothing appears in ip neigh or ip addr. An address that answers on the wire but does not exist in host configuration is nearly impossible to reason about without tcpdump
  • Driver support varies. Native XDP is not available everywhere, and falling back to generic mode does not deliver the expected performance. Virtualised environments need explicit verification
  • It sits in a monitoring blind spot. Most tooling observes metrics above the stack. Anything handled or dropped in XDP is invisible unless you add counters yourself
  • The staffing bar is higher. How many people can read this layer at three in the morning is what actually determines recovery time
In short, eBPF and XDP are an elegant answer to the question of how to reply to ARP, but the price is that the truth of the system becomes invisible to standard tools. That is an operations problem, not a performance one.

6. Asymmetric routing - when replies do not leave by the door they came in

6.1 Why it happens

This is the most exhausting stretch of building an on-premises load balancer. The symptom is always similar: it works from the same building and the same switch, but connections from outside get no response.

The cause is usually simple. The request came in over one path, but the reply leaves through the server's default route. A server picks an exit from its routing table based on the destination address alone; by default it does not consider where the request arrived from. In multi-circuit setups, tunnels, or topologies with several routers, that mismatch arises naturally.

Why does the same LAN work? Because the reply reaches the peer directly at the link layer without passing a router. The path is simply too short for the problem to show. That difference produces the classic pattern of works internally, fails externally.

6.2 rp_filter - the switch that drops silently

An asymmetric path is not always a problem in itself. The real problem starts when something in the middle decides to drop the packet. In Linux, the canonical mechanism for that decision is reverse path filtering. Per the kernel documentation:

  • 0 — no source validation
  • 1 — RFC 3704 strict mode. Each incoming packet is tested against the routing information, and if the interface is not the best reverse path the check fails
  • 2 — RFC 3704 loose mode. The check fails only when the source address is not reachable via any interface

Two more facts matter in practice. First, the value actually applied is the maximum of conf/all and conf/{interface}. Lowering only the per-interface value and then wondering why nothing changed is a recurring incident. Second, the kernel documentation itself states that loose mode is recommended if you use asymmetric routing or other complicated routing. Adjusting this is a documented option, not a hack.

# the effective value is the max of all and the interface setting
sysctl net.ipv4.conf.all.rp_filter
sysctl net.ipv4.conf.eth0.rp_filter

# traces of dropped packets (entries vary by kernel build)
grep -i martian /proc/net/stat/* 2>/dev/null
nstat -az | grep -i -E 'InAddrErrors|InNoRoutes'

That said, lowering the value gives up that much anti-spoofing protection. So order matters: first see whether the path can be corrected, and only relax the filter when correction is structurally impossible. Reverse that order and you hide the symptom while leaving the cause in place.

6.3 The families of fixes

There are broadly four ways to deal with asymmetry, and the right one depends on the situation.

ApproachPrincipleUpsideDownsideWhere it fits
Collapse to one pathFunnel ingress through a single path so asymmetry cannot occurSimplest and most robustGives up multi-circuit benefitsEffectively one circuit, or simplicity is the priority
Connection marks plus policy routingRecord the ingress interface on the connection and restore it to force the exitCorrect across multiple circuitsNeeds state tracking, rules grow complexTwo or more circuits both serving traffic

Relax reverse path filteringLower validation so asymmetry is toleratedImmediate effectWeaker spoofing defence, cause remainsA supporting measure when asymmetry is unavoidable

The second is what most sites end up using, and the idea is simple: note where a connection came in, and when replying, read that note back to choose the exit. On Linux you build it from firewall connection marks and policy routing rules.

# minimal form, only enough to show the concept
# 1) marked packets consult a separate routing table
ip rule add fwmark 0x64 lookup 100

# 2) that table's default route points at the right circuit
ip route add default via 203.0.113.1 dev eth1 table 100

# 3) verify
ip rule show
ip route show table 100

# 4) compute the actual exit for a given reply
ip route get 198.51.100.7 from 203.0.113.10 mark 0x64

That last ip route get is the single most useful command in this area, because it asks the kernel directly instead of guessing. Setting and restoring the mark is handled at the firewall layer with connection marks, that is storing a value on the connection and restoring it onto reply packets. The concept is identical whether you use nftables or iptables.

7. The path the original case took - DSCP tagging and its price

7.1 The shape of the problem

The original setup was more involved. An edge router held the carrier addresses, while the cluster sat elsewhere across a tunnel. External client requests arrived through the edge router into the cluster, but replies tried to leave straight to the internet from the cluster side. That made the packet source address inconsistent with the actual exit point, and upstream filtering discarded them. Clients in the same building worked because their traffic ended at the link layer, which made the failure look even more confusing.

The obvious answer is the second family above, policy routing keyed on source address. According to the write-up, that produced asymmetry in the opposite direction: replies to local network clients were also pushed back through the edge router. Source address alone cannot express which door a connection came in through.

7.2 Why DSCP of all things

So the chosen mechanism was to carry an ingress-point identifier in the packet's DSCP field. DSCP is the six-bit codepoint of the DS field defined by RFC 2474, originally used to select the per-hop behaviour a packet receives at each node. The flow, summarised:

  • On ingress at the edge, eBPF marks the DSCP value with which edge the packet entered through
  • Daemons along the path track the flow using that mark
  • On the way out, policy routing sends the reply back through the edge it came in from
  • Before leaving toward the provider network, the original DSCP value is restored

It is important not to misread the last step. This is not about hiding anything; it is hygiene that keeps an internal signal inside its internal boundary. DSCP is a QoS field, so an arbitrary internal value leaking into someone else's network becomes meaningless input to their policy. Moreover RFC 2474 itself assumes codepoints may be re-marked as packets cross a domain boundary, which means the value cannot be trusted as an end-to-end signal in the first place. Using it only inside the boundary and restoring it at the edge is the usage the protocol design intends.

7.3 Do not treat this as the general solution

It is a clever fix, but consider the following before copying it.

  • The mark space is tiny. Six bits, some of which carry conventional meanings, so the usable values are fewer still. Add ingress points and you run out quickly
  • It can collide with existing QoS policy. If DSCP already manages priority in your organisation, internal signalling and QoS intent become entangled
  • Preservation is not guaranteed outside the boundary. Intermediate devices may rewrite the value, so the trust boundary must be stated explicitly
  • Connection marks are the more standard answer. If the problem is solvable within one box, there is no reason to put information into the packet header
  • Diagnostic tools do not surface this value well. Without a rehearsed procedure, incident analysis slows dramatically

In sum, this is an answer produced under a fairly unusual constraint: carrying flow information across several routers. Most on-premises environments are fully served by connection marks and policy routing. The principle that when you borrow someone's solution you must borrow their constraints too applies here as well.

8. Triage order - where do you point tcpdump first

The single biggest time sink when this setup breaks is starting from the pods. The failure almost always lives far below them. Work upward from the bottom.

The commands at each step need not be elaborate. The addresses below are documentation ranges.

# step 2 - who claims this address as their own
tcpdump -ni eth0 arp and host 203.0.113.10

# steps 3-4 - watch request and reply at the same point
tcpdump -ni eth0 host 203.0.113.10 and tcp port 80

# step 4 follow-up - check whether replies leak out another interface

ip route get 198.51.100.7 from 203.0.113.10

A few practical habits worth adding:

  • Capture both ends simultaneously. Looking at one side leaves the discussion stuck at it seems to have been sent but never arrived. Aligning client and server captures by timestamp is what pins down the hop where packets vanish
  • Start at ARP. If there is no reply here, nothing above matters. A flapping MAC points at leader election or duplicate claims
  • Test same-LAN and external separately. Works inside, fails outside is the textbook fingerprint of asymmetric routing
  • Do not filter too narrowly. Filtering by port alone hides ICMP error messages, and path problems often leave their clues there
  • Check the change log first. Right after a node addition, a reboot, a kernel update or a firewall rollout, the candidate causes narrow dramatically
  • Capture packets only on networks you administer. Recording other people's communications without consent can carry legal consequences

10. Correcting the common misconceptions

  • A pending EXTERNAL-IP is a bug — No. It is the normal state when no controller owns allocation. On premises you must supply that role
  • Install MetalLB and it becomes like the cloud — Allocation and announcement get solved, but return paths, source IP preservation and failover remain your job
  • BGP is always better than layer 2 — Better on bandwidth, but with the documented limitation that backend changes break unrelated connections through rehashing, plus the need for router operations skills
  • eBPF makes it faster — In this context the benefit is not speed but the ability to intervene at a chosen layer without involving the stack. The trade is that state becomes invisible to standard tools
  • Setting rp_filter to 0 fixes it — The symptom may go, but the cause stays and spoofing defence weakens. People also routinely forget that the maximum of the all and interface values applies
  • It works internally, so it cannot be a firewall issue — Quite the opposite fingerprint. The same LAN never crosses a router, so path problems stay hidden
  • An address from DHCP is mine anyway — It is a lease. It can be reclaimed, and the permitted scope of use is defined by your circuit terms
  • Inside the cluster I can use QoS fields freely — They may be re-marked across boundaries and can affect someone else's policy. Internal signals should be restored at the edge

Conclusion

What one line of type: LoadBalancer did in the cloud was in fact a bundle of at least five jobs: obtain an address, announce it to the network, pull traffic to a node, forward it to a backend inside the node, and make the reply return by the path it came. The cloud sold the five together, so we assumed it was one thing. Try to do it yourself and each turns out to be an independent problem.

What makes this case interesting is not the stack but that it pinpoints exactly where an existing tool's premise breaks. MetalLB assumes the operator knows the address pool, and that assumption is right almost everywhere. It is not right when addresses arrive dynamically. Working out what has to be built at that point is itself an education in what was hiding under someone else's abstraction.

The practical conclusion is deliberately plain. Layer 2 announcement is enough for most on-premises and homelab setups, and BGP is the next step if you run your own routers. A custom build deserves consideration only when both premises clearly break, and even then, documenting how it works and how to diagnose it is part of the scope. And if you are building on a carrier circuit, reading the terms comes before the technical review. Designs that stay inside the contract are the ones that last.

One final note. Failures in this area leave no trace in application logs. Packets disappear quietly in the kernel or upstream, and developers see nothing but a timeout. So if you decide to run this kind of setup, rehearsing the order in which you check ARP, routes and filters is more useful preparation than any amount of automation.
