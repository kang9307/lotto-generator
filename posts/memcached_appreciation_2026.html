memcached 예찬 — 단순함이 만든 20년 캐싱의 힘

화려한 신기술이 쏟아지는 2026년에도 memcached가 여전히 사랑받는 이유 — 의도적 단순성과 '지루하지만 믿음직한 기술'의 진짜 가치

2026-06-25 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 20년 된 도구가 여전히 살아있다

2026년 6월 기준, 소프트웨어 인프라 세계는 새 도구의 홍수 속에 있다. Rust 기반 캐시, AI가 설정해주는 오케스트레이터, 분산 스트리밍과 캐싱을 통합하는 플랫폼들이 매달 등장한다. 그런데 이 소음 한가운데서 memcached가 조용히 버티고 있다. 2003년 Brad Fitzpatrick이 LiveJournal의 데이터베이스 과부하를 해결하기 위해 만든, 이제 갓 20년을 넘긴 이 도구가 Facebook·Twitter·Pinterest 같은 초거대 플랫폼의 핵심 캐시로 여전히 동작하고 있다.

나는 이 현상이 단순한 레거시 타성이라고 생각하지 않는다. memcached가 살아남은 것은 의도적으로 단순하게 설계됐기 때문이고, 그 의도가 지금도 유효하기 때문이다. 이 글은 그 이유를 내 관점에서 풀어본다. 기술 사실은 공개 문서와 실제 사례를 교차 검증했다.

1. memcached가 무엇인지 — 그리고 무엇이 아닌지

memcached의 공식 소개는 단순하다. "분산 메모리 오브젝트 캐싱 시스템"이다. 키를 넣으면 값을 저장하고, 키를 물으면 값을 돌려준다. 값은 TTL이 지나면 사라진다. 디스크에 쓰지 않는다. 서버들은 서로 통신하지 않는다. 복잡한 자료구조, 트랜잭션, 영속성, 쿼리 언어 — 이것들은 memcached가 처음부터 선택하지 않은 것들이다.

이 점이 중요하다. 기능이 없는 것이 아니라, 기능을 의도적으로 뺐다. memcached의 설계 철학은 "한 가지 일을 아주 잘 하자"는 Unix 철학과 맞닿아 있다. 초창기 설계자들은 캐시에 복잡성을 더할수록 예측 불가능성이 올라가고, 운영 부담이 커지며, 가장 필요한 것인 '빠른 읽기·쓰기'가 흐릿해진다는 것을 알았다.

1.1 slab allocator — 예측 가능한 메모리 관리

memcached의 메모리 관리는 slab allocator라는 독특한 방식을 쓴다. 미리 정해진 크기 클래스로 메모리를 쪼개 관리하는 방식이다. 일반 malloc을 쓰면 오래 실행될수록 메모리 단편화가 생기는데, slab 방식은 각 슬랩 클래스 안에서 청크를 재사용하기 때문에 외부 단편화가 거의 없다. 대신 내부 단편화(청크보다 작은 값을 저장할 때 낭비)는 발생하지만, 이것은 운영자가 미리 계산하고 튜닝할 수 있는 예측 가능한 낭비다.

이 설계는 운영 관점에서 큰 차이를 만든다. 메모리 사용이 예측 가능하면 용량 계획이 쉬워지고, 갑작스러운 메모리 부족으로 인한 장애 위험이 줄어든다. '지루하지만 믿음직한(boring but reliable)' 기술의 핵심은 여기서도 드러난다.

1.2 멀티스레드 아키텍처 — 코어를 다 쓴다

memcached는 설계 초기부터 멀티스레드를 지원한다. 워커 스레드를 여러 개 띄워 CPU 코어를 병렬로 활용한다. Redis가 기본적으로 단일 이벤트 루프(싱글스레드 연산)를 쓰는 것과 대비된다. 이 차이는 단순 읽기·쓰기가 폭발적으로 많은 환경에서 처리량과 지연에 직접 영향을 준다.

2026년 Rails 캐시 벤치마크 데이터에 따르면, 단순 get/set 위주의 고동시성 부하에서 memcached가 Redis 대비 약 30% 낮은 지연, 약 20% 높은 처리량을 보였다. 물론 워크로드에 따라 결과는 다를 수 있고, Redis도 버전이 올라가면서 I/O 멀티스레딩을 강화했다. 하지만 "단순 캐싱만 한다면 memcached가 빠를 수 있다"는 명제는 2026년에도 유효하다.

2. 클라이언트 샤딩과 consistent hashing — 서버를 멍청하게, 클라이언트를 똑똑하게

memcached 클러스터의 가장 독특한 특성은 서버들이 서로 통신하지 않는다는 점이다. 분산 처리의 모든 지능은 클라이언트 라이브러리에 있다. 클라이언트가 키의 해시값을 계산하고, 그 값에 따라 요청을 특정 서버로 보낸다.

2.1 consistent hashing의 역할

일반적인 모듈러 해싱(hash(key) % N)은 서버 수 N이 바뀌면 거의 모든 키의 서버 배정이 달라져 캐시를 통째로 날리는 것과 같다. Consistent Hashing은 이 문제를 해결한다. 키와 서버를 같은 해시 링(hash ring)에 올리고, 각 키는 시계 방향으로 가장 가까운 서버에 배정된다. 서버가 하나 추가되거나 빠질 때 영향을 받는 키는 전체의 1/N 수준에 그친다.

이 설계는 중앙 코디네이터 없이도 선형 확장을 가능하게 한다. 서버를 더 붙이면 처리량이 늘고, 하나가 죽어도 나머지 서버의 데이터는 그대로다. 단지 죽은 서버에 있던 키들이 캐시 미스를 내고 데이터베이스에서 다시 채워질 뿐이다. 이것도 예측 가능한 동작이다.

2.2 "서버를 멍청하게"의 운영 이점

서버 사이에 클러스터 메타데이터, 리더 선출, 복제 로그 같은 것이 없다. memcached 서버 자체는 정말 단순하다. 이 덕분에 운영이 쉽다. 서버 장애 시 복잡한 페일오버 절차가 없고, 새 서버를 추가할 때도 클라이언트 설정을 업데이트하는 것으로 충분하다. 대규모 운영팀 입장에서 이 단순성은 밤 3시 장애 대응 시 엄청난 차이를 만든다.

3. Redis와의 철학적 차이 — 기능 풍부 vs 단순·예측 가능

memcached와 Redis를 비교할 때 흔히 "Redis가 기능이 더 많으니 더 좋다"는 결론이 나온다. 나는 이것이 잘못된 프레이밍이라고 생각한다. 두 도구는 다른 철학적 선택을 한 것이지, 하나가 다른 하나의 발전된 버전이 아니다.

3.1 Redis가 선택한 것

Redis는 문자열, 해시, 리스트, 셋, 정렬된 셋, 스트림, Pub/Sub, Lua 스크립팅, RDB/AOF 영속성을 제공한다. 이 풍부함은 Redis를 캐시를 넘어서 세션 저장소, 메시지 브로커, 실시간 리더보드, 분산 잠금 등 다양한 역할로 쓸 수 있게 한다. 하나의 도구로 여러 문제를 해결하는 방향이다.

3.2 memcached가 선택한 것

memcached는 이 모든 것을 거절했다. 영속성이 없어서 서버가 재시작되면 캐시는 비워진다. 복잡한 자료구조가 없어서 애플리케이션이 직렬화·역직렬화를 처리해야 한다. 이 "결핍"들은 사실 장점이다. 영속성이 없으니 쓰기가 빠르고, 재시작이 간단하며, 데이터 일관성 문제가 생기지 않는다. 복잡한 자료구조가 없으니 내부 구현이 단순하고, 그 단순함이 멀티스레드 성능을 뒷받침한다.

3.3 2026년의 추가 변수: Valkey

2026년 Redis 관련 환경은 더 복잡해졌다. Redis Labs의 라이선스 변경(2024년)에 반발해 Linux Foundation이 Redis 7.2.4 포크인 Valkey를 출범시켰고, 2026년 3월 기준 Redis의 명령셋 및 프로토콜과 완전 호환을 달성했다. 이 혼란 속에서 memcached는 조용히 원래 자리를 지켰다. 라이선스 분란, 포크, 마이그레이션 비용 — memcached는 이 소용돌이와 무관하다. 오픈소스 BSD 라이선스로 처음부터 지금까지 흔들리지 않았다.

4. Facebook의 사례 — 초당 수십억 요청을 memcached로

추상적인 철학 논쟁보다 구체적인 사례가 더 설득력 있다. Facebook은 2013년 NSDI에서 "Scaling Memcache at Facebook" 논문을 발표했다. 이 논문이 기술하는 규모는 압도적이다.

Facebook은 memcached를 기반으로 초당 수십억 요청을 처리하고, 트릴리온 개의 아이템을 보유하는 분산 키-값 저장소를 구축했다. 수십 개 데이터센터에 수천 개의 캐시 서버가 퍼져 있으며, 인기 있는 페이지 하나를 렌더링하는 데 100개 이상의 memcached 서버와 통신하는 경우도 있다고 밝혔다.

Facebook은 이 규모에서 memcached의 단순성 때문에 오히려 복잡한 최적화가 가능했다고 설명한다. 서버 자체는 단순하게 두고, 클러스터링·레플리케이션·핫 키 처리 같은 복잡성을 인프라 계층과 클라이언트 계층에서 흡수했다. 이것이 memcached의 설계 철학을 대규모로 검증한 사례다.

5. 'Boring Technology'의 가치 — 지루함이 덕목이 되는 이유

소프트웨어 엔지니어링에는 오래된 격언이 있다. "새 도구를 쓰는 비용은 도구 자체의 학습 비용만이 아니다." 새 도구를 도입하면 새로운 장애 모드, 새로운 운영 패턴, 새로운 트러블슈팅 방법론이 따라온다. 팀이 그 도구에 익숙해지는 데 걸리는 시간과 잠재적 사고 비용이 진짜 비용이다.

QCon London 2026 발표에서 한 엔지니어는 이렇게 말했다. "사용자는 당신의 기술 스택에 관심 없다. 버튼을 눌렀을 때 작동하는지에 관심 있다." 지루한 기술을 선택하면 도구를 설정하는 데 쓰는 시간 대신 기능을 만드는 데 시간을 쓸 수 있다.

5.1 memcached가 지루한 이유

memcached는 놀랍도록 지루하다. 새 버전이 나와도 API가 안 바뀐다. 20년 전 쓰던 클라이언트 라이브러리 코드가 지금도 동작한다. 운영 커맨드가 단순해서 처음 다루는 엔지니어도 빠르게 트러블슈팅할 수 있다. 알려진 장애 모드가 잘 문서화됐고, 해결책이 이미 블로그와 레퍼런스에 가득하다.

5.2 신기술의 유혹과 진짜 질문

새 캐시 도구를 도입할 때 물어야 할 진짜 질문은 "이 도구가 더 기능이 많은가?"가 아니다. "우리 워크로드에서 이 도구가 필요한 것을 단순하고 예측 가능하게 제공하는가?"여야 한다. 단순한 키-값 캐싱이 필요한 팀이 Redis의 모든 기능을 쓰지 않으면서도 Redis를 운영하는 복잡성을 끌어안는 것은, 트럭이 필요할 때 탱크를 모는 것과 비슷하다.

6. memcached를 선택해야 할 때와 아닐 때

memcached 예찬이라고 해서 항상 memcached가 답이라는 주장은 아니다. 도구는 문제에 맞아야 한다.

6.1 memcached가 적합한 경우

  • 단순 키-값 캐싱이 목적의 전부일 때 — 데이터베이스 쿼리 결과, API 응답, HTML 프래그먼트 캐싱
  • 고동시성·저지연이 최우선일 때 — 멀티스레드 아키텍처가 코어를 모두 쓰는 이점이 크다
  • 수평 확장을 단순하게 가져가고 싶을 때 — 서버를 늘리면 선형으로 처리량이 오른다
  • 운영 복잡성을 최소화하고 싶을 때 — 서버 간 통신이 없으니 클러스터 상태 관리가 없다
  • 캐시는 캐시여야 한다고 생각할 때 — 영속성이 없어야 올바른 설계 결정을 유도한다

6.2 Redis(또는 Valkey)가 적합한 경우

  • 리더보드, 큐, Pub/Sub, 지리 인덱스 같은 복잡한 자료구조가 필요할 때
  • 캐시 외에도 세션 저장소, 메시지 브로커 역할을 하나의 도구에서 처리하고 싶을 때
  • 영속성이나 복제가 필요할 때
  • Lua 스크립팅이나 트랜잭션적 연산이 필요할 때

실제로 Facebook을 포함한 많은 대형 서비스들이 두 도구를 계층적으로 혼합해서 쓴다. 가장 단순하고 볼륨이 큰 캐싱 계층에는 memcached를, 복잡한 연산이 필요한 곳에는 Redis를 쓰는 방식이다.

7. 2026년에 memcached가 주는 교훈

20년간 memcached가 살아남은 것은 마케팅의 승리가 아니다. 올바른 설계 선택이 시간을 이기는 것을 보여주는 사례다. 기술 세계에서 단순성은 상대적으로 희귀한 덕목이다. 무언가를 추가하는 것은 쉽고, 제거하거나 처음부터 배제하는 것은 어렵다.

memcached는 처음부터 무엇을 포함하고 무엇을 배제할지 명확히 결정했다. 그 명확성이 20년의 생명력을 만들었다. 새 도구를 평가할 때마다 "이 복잡성이 정말 내 문제를 해결하는가, 아니면 새로운 문제를 만드는가"라는 질문을 던지게 하는 것 — 그것이 memcached가 2026년에도 우리에게 주는 교훈이다.

지루하다. 그리고 그것이 정확히 의도한 바다.
