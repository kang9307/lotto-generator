The Trigger — One SQL Function Calls the Model for Every Row

Quail, which was posted to GeekNews on October 6, 2026, is an engine for executing AI-SQL, that is, queries that call an LLM from inside SQL. The source is a post published on the Full Stack Data Lab blog on September 24, and it lists six authors: Shreya Shankar, Charles Frye, Fergus Finn, Arnav Dhariya, Joseph Barrow, and Meryem Arik. The name stands for QUery-Aware Inference Layer, and the post describes the goal as jointly optimizing query planning and model inference for open-weight models.

AI-SQL is also called AI functions. In the source's definition, it extends SQL with user-defined functions that invoke LLMs, and users specify each function with a natural-language prompt. The shortest example the source gives looks like this.

SELECT *
                    FROM reviews AS r
                    WHERE AI.IF(PROMPT('Does this review discuss the ending?\n\n{0}', r.review));

The source names Snowflake Cortex AISQL, BigQuery AI functions, Databricks AI Functions, and, recently, MotherDuck as offerings that support this kind of feature. The problem is the cost of execution. An AI function evaluates its prompt row by row, so a single SQL query can create hundreds of thousands or millions of model calls. A filter needs one LLM call per row, and a naive join needs one LLM call for every pair of rows in its two input tables.

There is already a body of research aimed at reducing this cost. The source cites DocETL from UC Berkeley, LOTUS from Stanford, Palimpzest from MIT, and ThalamusDB from Cornell, and it summarizes the methods that these systems and database vendors primarily use as two families. One is to eliminate as many LLM calls as possible (MOAR, Task Cascades, Abacus), and the other is to use cheaper models where possible (BARGAIN). The source's starting point is the sentence that follows: even after these optimizations, a query plan may still require hundreds of thousands or millions of LLM calls. What Quail targets is how to execute the calls that remain.

The interface side of the discussion, where calls are declared as dataframe operations, is covered in fenic and semantic operators; a third-party measurement of a model specialized for yes-or-no decisions is in the Jev field evaluation; and the concept of the KV cache is explained in KV cache sharing and attention compression. The subject here is the layer beneath those: once the number of calls has been fixed, where time leaks inside the execution engine, and under what conditions the source measured it.

Where Time Leaks When Requests Are Sent One by One — The BIO-4 Case

A natural thought is to have a general-purpose inference engine such as vLLM execute the query plan. The source says that sending millions of related model calls as separate requests carries a large cost, and it uses a query called BIO-4 as its evidence. Given a dataset of medical reports and a dataset of possible adverse reaction terms, the query finds serious adverse event reports that mention both a cardiovascular reaction and a neurological reaction. It is based on the BioDEX dataset, and its SQL form appears in note 1 of the source.

SELECT r.id,
                        n.id AS neurological_reaction_id,
                        c.id AS cardiovascular_reaction_id
                    FROM reports AS r
                    JOIN reaction_terms AS n
                        ON AI.IF(PROMPT(
                            'Does the medical report in {0} describe the reaction in {1} as '
                            'something the patient experienced?',
                            r.report,
                            n.term
                        ))
                    JOIN reaction_terms AS c
                        ON AI.IF(PROMPT(
                            'Does the medical report in {0} describe the reaction in {1} as '
                            'something the patient experienced?',
                            r.report,
                            c.term
                        ))
                    WHERE AI.IF(PROMPT(
                        'Does {0} describe a serious or life-threatening adverse event?',
                        r.report
                    ))
                    AND AI.IF(PROMPT(
                        'Is this reaction neurological, affecting the nervous system? {0}',
                        n.term
                    ))
                    AND AI.IF(PROMPT(
                        'Is this reaction cardiovascular, affecting the heart or blood vessels? {0}',
                        c.term
                    ));

The inputs are 5,000 long reports and 4,144 reaction terms, and because there are two joins, the term table is used twice. The logical plan in Figure 1 of the source has three steps.

  • It filters the reports for serious adverse events.
  • It filters the two reaction-term inputs, one for cardiovascular reactions and the other for neurological reactions.
  • It joins the surviving reports first with the cardiovascular terms and then with the neurological terms.

If there were no filters at all, the candidate pairs for a single join would number 5,000 × 4,144 = 20.72 million (calculated). Because the filters shrink the inputs first, the actual number of requests is smaller than that, and the source says only that BIO-4 compiles to millions of requests.

The baseline that executes this with vLLM follows what databases do. It renders one prompt for each filter input and, for the join, one prompt for each candidate pair of report and reaction term, and it sends each prompt as a separate inference request. In the join prompts, the much longer medical report is placed first as the anchor and the reaction term second as the partner, so that more of the prefix's KV can be reused, and the operators are executed one at a time with the requests ordered so that requests for the same document are evaluated together. In other words, the baseline is already a configuration that was built with KV reuse in mind.

As a yardstick for the comparison, the source first computes a theoretical lower bound for the same plan. The value is obtained by counting the model's arithmetic work and HBM traffic from the token lengths and then estimating the time with a roofline model, and the source calls it the speed of light (SoL) estimate. It rests on three assumptions.

  • The GPU delivers its peak throughput.
  • CPU work and GPU work overlap completely.
  • There is unlimited space for the KV that is retained.

No implementation can meet all of these assumptions, so the SoL estimate is an optimistic lower bound. For BIO-4, the SoL estimate is 894.37 seconds, or 14.91 minutes. Each request produces a single token constrained to TRUE or FALSE, so all of the model's work is prefill, and because there are millions of requests there should always be a large batch ready for the H100. What the source hoped for was that vLLM would get close to the SoL estimate under these conditions.

The measurement turned out differently. With vLLM 0.26.0, Qwen3 4B FP8, one H100, and scale factor 1.0, the vLLM baseline took 6.84 hours, which is 27.55 times the SoL estimate. The source gives two reasons.

  • Host overhead (the primary reason). The CPU spends long stretches scheduling and tracking requests while the H100 waits. Figure 2 of the source shows the gaps during which the GPU sits idle, in a PyTorch profiler trace of a 3.5-second window from the first join.
  • KV regret. vLLM sometimes discards KV that it needs again later. On BIO-4 at scale factor 1.0 it therefore processed 174.6 million tokens instead of 124.3 million. That is 50.3 million extra tokens, or 40% more work.

What this case shows is that the bottleneck was not the arithmetic speed of the model but the CPU side that handles requests and the discarding of KV that is needed again later. The source's conclusion is that both sources of waste can, and should, be reduced by optimizing inference for AI-SQL.

How It Differs from a General-Purpose Inference Engine — An Item-by-Item Contrast

Quail did not reimplement every model and GPU operation from scratch. It takes the operations required for a forward pass from vLLM's model implementations and runs them with its own scheduler and KV manager. The difference lies in the fact that the side that knows the whole query decides the order of inference and what happens to the cache. The table below collects only the items on which the source directly contrasts general-purpose inference (the vLLM used as its baseline) with Quail.

The Planning Stage — SQL Rewrites and Inference-Specific Decisions Made Together

Quail consists of a query frontend, a query planner, and an execution engine. The user provides Arrow tables or datasets, an AI-SQL or Python query, and the model and GPU or GPUs to use. For AI-SQL it accepts both Snowflake's and BigQuery's spellings (AI_FILTER and AI.IF), and there is also a Python query builder similar to pandas. Each query is parsed with SQLGlot into a logical plan. The source says that the design is inspired by Apache DataFusion, an extensible analytical query engine, and that one can add new query operators, planning rules, execution backends, models, or support for other hardware.

Database query optimizers already apply rules such as pushing down filters, reordering predicates, and choosing a join order. According to the source, AI-SQL adds several new decisions on top of these: which document should be the join anchor, which KV will be needed by a later operator, and how much model work should enter each forward pass. Quail plans both kinds of decisions together. Given a logical query plan, it goes through the following four steps.

  1. Dataset statistics. For each input dataset it estimates the row count, the average document length, and the maximum document length.
  2. Forward pass and KV limits. From the selected model size and the GPU memory size, it calculates the maximum number of tokens to compute in each forward pass. It reserves HBM for the model weights and for two forward passes, and leaves the rest of the HBM for the KV cache. The source adds that this is more conservative than vLLM and that it can probably be improved.
  3. SQL rewrites. It pushes projections and filters down to the source datasets. Filters are ordered by their estimated cost and selectivity, and the source states that this follows well-known prior work (Hellerstein and Stonebraker et al.). For joins it uses a Selinger-style search (that is, System R) to choose the join order and the anchor for each join. The cost model uses the SoL estimate described above.
  4. Inference-specific rewrites. It translates the logical plan into a DAG of physical operators. AiFilter evaluates AI predicates over documents, while AiJoin evaluates AI predicates over document pairs that share an anchor. Each operator specifies its prompt, model, forward pass token budget, and KV settings. As an example of a KV setting, the source mentions whether to write KV to HBM because a subsequent operator follows in the query.

There are two pieces of planning information that a user can supply. Selectivity is the expected fraction of documents or document pairs that will pass, and the anchor of a join chooses which input comes first in the prompt for the sake of KV reuse. The blog post explains that without a selectivity Quail keeps predicates in their written order, and that without an anchor the planner chooses one.

For an anchor to work, the document has to be placed ahead of the question in the prompt. Note 2 of the source explains that the documents do not have to appear exactly where their numbered placeholders ({0}, {1}) occur in the question, and it shows the input that the model receives for a prompt comparing a report with a term as follows.

DOCUMENT:
                    [contents of r.report]
                    
                    (The document above is DOCUMENT {0}.)
                    
                    Evaluate TRUE or FALSE for the following question:
                    Does {0} mention {1}?
                    
                    DOCUMENT {1}:
                    [contents of n.term]
                    ANSWER:

Because the report comes first, its KV can be reused when the same report is compared with another term. The result of planning is reflected in how execution proceeds as well. Drawing inspiration from vectorized query execution, Quail streams intermediate results directly between operators rather than materializing complete datasets on disk or in main memory. In BIO-4, as soon as a batch of reports passes the initial filter it is pipelined to the first join, and the report KV cache is kept in HBM throughout both joins, so the comparisons against the filtered reaction terms do not recompute that KV.

The Execution Stage — KV Rewinding and Three Changes to the Forward Pass

The execution engine has three parts: a physical plan executor, a KV manager, and an inference program. The executor is pull-based, as in Volcano, but it processes one batch at a time, as in MonetDB. Before execution, Quail tokenizes every document column referenced by an AI filter or join with Gigatoken and loads one copy of the model per GPU. During execution, the CPU prepares the next batch while the GPU processes the current one.

The KV manager keeps a fixed pool of KV pages in HBM for each GPU, and after each model evaluation it retains only the KV that a later evaluation can reuse. For a filter, the document is placed before the predicate-specific question. Once the predicate returns TRUE or FALSE, Quail discards the KV of the question part and "rewinds" to the end of the document KV. After that, if the predicate returned TRUE and another AI operator uses the document, the rewound KV is retained in HBM; otherwise it is released. Rewound KV is retained in the same way for joins. If space runs short and eviction is necessary, the shortest documents are evicted first. The reason the source gives is that attention is a quadratic operation, so longer documents take disproportionately longer to recompute.

An inference program is the procedure by which a single AiFilter or AiJoin runs on the GPU. It takes token IDs and positions, plus the locations of any reusable KV pages, and it returns TRUE and FALSE scores for each row or pair of rows. The source describes its modifications to the forward pass as "three small changes".

  • Fusing small operations. It uses Triton kernels that fuse normalization with FP8 quantization, Q/K normalization with RoPE, and activation with FP8 quantization. This reduces the number of kernel launches and the amount of intermediate HBM traffic. The source remarks that this is extremely easy to do now with AI agents and that it requires no novel kernel design ideas.
  • Attention specialized for joins. An AI join compares one anchor with many partners. Standard vLLM treats each anchor and partner pair as a separate sequence, so the same anchor KV is read again for every partner. Quail groups the partners that share an anchor and evaluates attention in two parts. One FlashAttention 3 call computes causal attention within each partner, and a second call applies all of the partner queries to the shared anchor KV. The two results are combined using their log-sum-exp values and the online softmax formula, and the source states that this produces the same output as attention over each full anchor and partner sequence.
  • Restricting the output head to TRUE and FALSE. Normally the output head computes a score for every token in the vocabulary. AI filters and joins need only the scores for the token IDs that represent TRUE or FALSE, so Quail multiplies the final hidden state by only the corresponding rows of the output head matrix. For Qwen it scores four spellings of each answer (TRUE, TRUE with a leading space, True, True with a leading space, and the corresponding four on the FALSE side).

Regarding join attention, the source says it follows a long line of "tree"-based attention approaches, which evaluate several branches that share a prefix without allowing one branch to attend to another, and it cites SpecInfer for speculative decoding and Hydragen for shared-prefix attention as examples. Quail applies the same structure during prefill rather than during decoding. Organized by what each technique reduces and what it presupposes, the techniques described so far look like this.

The second and third columns rearrange what the source describes. The source lists three performance goals, namely minimizing KV regret, keeping the GPU busy by reducing CPU scheduling overhead, and reaching high MFU (model FLOP/s utilization) while the GPU is active, and it states that its current evaluation focuses on the first two and that a full MFU study is deferred to future work.

Measurement Conditions — What Was Held Equal and What Was Compared

Before reading any single multiple, one has to know what its denominator is. The conditions disclosed in Section 4.1 and note 11 of the source are as follows.

  • Benchmark. QUAIL-B, which the lab created itself. It consists of 29 AI-SQL queries covering IMDB reviews, medical reports, fact-checking claims, legal documents, and software-agent traces, and the queries include filters, filter sequences, and one or more joins.
  • Scale factor. Each dataset comes at scale factors 0.1, 0.5, and 1.0. The comparison across all 29 queries was made at 0.1, and only BIO-4 was examined separately at 1.0. According to the table in the QUAIL-B README, 0.1 corresponds to 5,000 IMDB reviews, 500 BioDEX reports with 1,127 terms, and 1,772 agent traces.
  • Model and hardware. Every query uses Qwen3 4B FP8 with BF16 KV on one H100. Quail and each vLLM baseline were run one after the other on the same physical GPU.
  • What was held equal. The model, the prompts, and the logical query plan are the same. Both baselines use the operator ordering chosen by Quail's query planner, and for each operator the requests are prepared and ordered to improve KV reuse.
  • Tokenization. For fairness, both baselines also use Gigatoken, as Quail does, instead of vLLM's Hugging Face tokenizer.
  • Baseline 1, stock vLLM. This is the configuration that executes one operator at a time.
  • Baseline 2, pipelined vLLM. For queries with multiple filters or joins, this configuration pipelines requests between consecutive filters and between consecutive joins.
  • vLLM settings. Version 0.26.0 with automatic prefix caching. The maximum batched tokens are 25,305, the sequences 4,096, the GPU memory utilization 0.91, with one CUDA graph for 8,192 tokens. The source says these are the largest stable settings and that larger settings ran out of GPU memory.
  • Cost conversion. The query runtime in hours is multiplied by 3.9492 US dollars per H100-hour, which is Modal's H100 price.

There are three metrics. KV regret is repeated model work, defined as fresh input tokens beyond the minimum needed to compute each reusable prefix once. Cost per query follows the conversion above as is. Input tokens per second is the total requested input tokens divided by the query runtime, and it counts the full input length of every evaluated prompt, including tokens served from KV. Lower is better for the first two, and higher is better for the last.

Two things can be read from these conditions. The benefit of choosing the operator order and the fast tokenizer are already included in the baselines, so the reported multiples read as a measurement of what is left over, namely the difference in KV planning and in the manner of execution. In addition, input tokens per second puts tokens served from the cache into the numerator as well, so the value grows for queries that involve more reuse. It is therefore hard to set the throughput of different queries side by side and draw conclusions about how fast an engine is. Both points are interpretations that follow from the source's definitions and are not sentences from the source.

Results, Part 1 — 29 Queries at Scale Factor 0.1

At scale factor 0.1, Quail was faster than stock vLLM on 27 of the 29 queries. The geometric mean of the per-query speedups is 1.84x, and the maximum is 11.22x on BIO-2. Table 1 of the source gives averages by dataset. The cost multipliers are relative to Quail, which is set to 1.00.

To complete all 29 queries, Quail took 1,643.74 seconds and stock vLLM took 4,451.95 seconds. Converted to minutes, that is roughly 27.4 and 74.2 minutes, and the ratio of the total times is about 2.71x (calculated). The reason this differs from the geometric mean of 1.84x is that the total time is pulled toward the queries that take the longest. Whichever number is quoted, it only makes sense when the way the average was taken is stated alongside it.

The combined SoL estimate for the same 29 queries is 491.17 seconds, and Quail takes 3.35 times that. The source itself notes that there is substantial room to improve. Pipelined vLLM was faster than stock vLLM on seven of the eight queries where pipelining changes how requests are submitted, by 1.12x on average and by up to 1.27x on IMDB-6.

What stands out in the table is how widely the multiples vary by dataset. In cost terms BIO is 8.72x and LEP is 1.27x, while AGENT is 0.43x, meaning that Quail is the more expensive side there. In the source's summary line, "1.84x faster on average ... up to 14x", the first value is the geometric mean over the 29 queries at scale factor 0.1, and the second value comes from a single query (BIO-4) at scale factor 1.0. The two numbers were obtained under different conditions.

BIO-4 contains the kind of reuse that Quail currently handles well: long shared documents, two joins, and millions of related model calls whose order is known before execution. AGENT-1 contains a different kind of reuse. It is a query that filters 1,772 cumulative snapshots from software agent runs, and the form that the source prints, simplified for the post, is as follows.

SELECT t.id
                    FROM agent_traces AS t
                    WHERE AI.IF(PROMPT(
                        'Did the agent recover after trying an approach that did not work?\n\n{0}',
                        t.trace
                    ));

Because the snapshots are cumulative, in the example shown in Table 3 of the source the row for turn 10 of an agent trace begins with the complete content of the row for turn 5 of the same trace. In other words, separate rows have overlapping prefixes. Stock vLLM's automatic prefix caching reuses KV across rows with matching token prefixes. Quail currently reuses KV only when the same document appears again in the query, not across different documents. As a result, Quail incurs 11.89 million KV regret tokens while stock vLLM incurs 23,928, and the runtime is 239.12 seconds against 103.07 seconds, so Quail takes 2.32x as long. Even on this query, stock vLLM takes 2.17 times the SoL estimate of 47.47 seconds.

The source says it plans to add automatic prefix caching to Quail, and it attaches a condition: the lookup must remain cheap at the request volumes that AI-SQL queries can produce. The two queries out of the 29 on which stock vLLM won are AGENT-1 and AGENT-2, and the source attributes both to this missing feature.

Measuring Speed Is Not the Same as Measuring Decision Quality

All of the figures so far concern the speed and cost with which the same model answers the same prompts. Whether the model's decisions are correct is a separate question, and there are four places in the source that touch on it.

  • Agreement between models. Quail also supports DiffusionGemma 26B-A4B FP8, a larger mixture-of-experts model with 4B active parameters per token. On IMDB-2 at scale factor 0.1, DiffusionGemma matched 88.89% of Qwen3 32B's answers, compared with 76.41% for Qwen3 4B. It ran the query in 32.41 seconds on one H100, which is 1.53 times Qwen3 4B's 21.20 seconds. These figures are not a comparison against human-assigned ground truth; they are rates of agreement with the answers of a larger model.
  • Prompt layout. Moving the document to the front is the precondition for KV reuse, and note 2 of the source says that whether other prompt layouts affect accuracy remains an open question, adding that the authors expect this to matter less as models improve.
  • The benchmark's reference answers. The QUAIL-B README states that accuracy is not a focus of the benchmark. Its explanation is that most labels are the answers of one arbitrarily chosen model (Qwen3 32B FP8), so measuring accuracy against them is not really meaningful. Real labels exist for two kinds of joins: the claim annotations from FEVER and the citation links from LePaRD.
  • Equivalence of the computation. For join-specific attention, the source states that it produces the same output as attention over the full sequence. That is a statement about the method of computation.

The cost comparison should be read along the same lines. The example in Section 3.1 of the source is a query that applies two AI filters to 100,000 IMDB reviews. The estimated time in the plan output was 124 seconds, while the actual run took 277.41 seconds with a cold boot of 57.65 seconds at 360.5 documents per second, and it cost 0.3675 US dollars on one H100 including model startup. The selectivity hints were 25% and 50%, and the pass rates actually printed were 0.283 and 0.568. The source estimates that the same workload would cost about 1.75 US dollars at current GPT-5 nano prices, or 4.8 times as much. That estimate comes with the assumptions that the cached-token price is used and that the cache is infinite, so every reusable document token receives that rate, and the measurement excludes the time and cost of downloading the IMDB dataset because it was already on disk. The two amounts compare the cost of doing the same job; they are not numbers that also assert the two models' answers are of the same quality.

The source states that Modal sponsored the compute used in the research. The release status is as follows.

  • Installation. According to the README, the PyPI package is named quail-engine and it is imported in Python as quail. It requires Python 3.12 and a CUDA GPU. The Modal example in the blog post pins quail-engine==0.1.0.
  • Models. The blog post says Quail supports three models on H100 GPUs: Qwen3 4B FP8, Qwen3 32B FP8, and DiffusionGemma. The table in the README pairs Qwen3 4B and DiffusionGemma 26B-A4B with the NVIDIA H100 SXM, and Qwen3 32B with the NVIDIA RTX PRO 6000 Blackwell Server Edition.
  • Number of GPUs. The README says 1, 2, 4, or 8 GPUs per query. The blog post describes the multi-GPU support as still quite basic. It places one complete model copy and one KV pool on each GPU, partitions filter documents and join anchors randomly and uniformly across the GPUs, runs them independently, and combines the results on the CPU.
  • Operators. According to the blog post, the current release supports AI filters and joins along with relational projections and LIMIT. The README adds EXISTS and NOT EXISTS, numeric scores (AI.SCORE), and classification (AI.CLASSIFY) to that list, and says that AI.EXTRACT and AI.MAP are planned additions.
  • How it is run. The README introduces Quail Server, an optional HTTP server that runs on the machine with the GPU. The blog post includes an example that puts the whole query inside a Modal GPU function for those without a dedicated GPU, as well as a link to a live demo.

It is also worth recording that the blog post and the repository describe some things differently. That is true of the supported operators and of the target device for Qwen3 32B, and it is true of the default selectivity as well. The blog post said that without a selectivity the predicates are kept in their written order, whereas the SQL reference says the default is 0.2, meaning 20%, and that the hint does not change model answers. KV regret is also defined as a token count in the blog post and as a percentage of fresh tokens in the QUAIL-B README, and the number of queries is given as 29 in the blog post and 50 in the README. The supported models differ as well: the blog post and the README give three, whereas the SQL reference also names the Qwen3 rerankers and Decision 2.0 Kai. Since the source itself says that Quail is still being actively built, the reference point for real use is the documentation of the version that is installed. The items that the SQL reference explicitly lists as unsupported are the following, and using any of them raises a compile error.

  • Window functions and QUALIFY
  • UNION, EXCEPT, and INTERSECT
  • OR between conditions
  • BETWEEN, LIKE, and arithmetic in column comparisons
  • Queries with no AI operator
  • A JOIN with only relational predicates and no AI operator
  • Outer joins (LEFT, RIGHT, FULL)
  • AI.EXTRACT and AI.MAP

The same document also records the constraint that all AI filters on one table must read the same document column.

Limitations and Future Work Stated in the Source

Section 3.2 of the source opens by saying that it describes the design only at a high level and that the full technical details will be provided in a future report. The limitations of the current implementation that are written directly in the text are as follows.

  • There is no prefix reuse across rows. This is why it lost to stock vLLM on AGENT-1 and AGENT-2.
  • Reusable KV is either kept in GPU HBM or recomputed. There is not yet a hierarchy that moves it down to host memory or a local SSD and brings it back before reuse.
  • The main GPU kernels rely on DeepGEMM and FlashAttention, and the kernels themselves have not been optimized. A full evaluation of MFU has also been deferred.
  • In a join, the anchor's KV is reused within one join loop, but every partner is recomputed for each new anchor. The same document is therefore encoded once per pair.
  • Summed over the 29 queries, Quail takes 3.35 times the SoL estimate.
  • Multi-GPU support is at the level of random uniform partitioning.

As future work the source lists support for more AI-SQL operators, more models, and more hardware, and it says the authors especially want to support tiny hybrid models so that Quail can run on a MacBook. As research ideas it lists using the full memory hierarchy for KV (including automatic prefix caching across rows and, perhaps, KV compression), kernel optimization together with Modal and Doubleword, training small models for execution and planning (models that evaluate filters cheaply and predict selectivity for the planner), and whether an AI join can be made to work like a hash join. The last item asks whether every document could be encoded once and its KV used as a position-independent index entry, and the source adds that this may require removing or separating the position information that RoPE adds to KV.

There is also a remark about how the system was built. The source says the authors used AI coding agents heavily to build the current version of Quail, and it names as an open task finding better ways to check that every agent-written change keeps answers correct and keeps runtime close to SoL. On the cost model, a follow-up post titled "How to Cost Your AI-Powered Filters" was published on October 1. It derives the SoL estimate for queries that contain only filters, and it says that for an example applying three filters to 5,000 IMDB reviews the SoL estimate is about 6.86 seconds while actual runtime may be much longer. It also carries the caveat that, when comparing filter orders, it assumes each filter keeps the same fraction of documents regardless of which filters ran before it, and that correlated filter outcomes can make that estimate inaccurate.

Questions to Settle When Evaluating Adoption

Translated into a judgment about one's own workload, the figures and constraints in the source become the following questions. They are not sentences carried over from the source but a summary drawn from the facts above.

  • Is each call a one-token decision? Quail targets fast, bounded decisions rather than long generated responses. The source cites Jev as the example that highlighted demand for this pattern in application backends, and says Quail targets the batch, OLAP version, in which one query creates thousands or millions of related decisions. The uses the source names are LLM judge workflows, trace compaction, labeling, and other large-scale data transformations.
  • What shape does the reuse take? If the same long document appears again across several filters and many join pairs, the workload is on the BIO-4 side. If different rows share long prefixes, it is on the AGENT-1 side, and at the time of the source vLLM with prefix caching was the faster option.
  • Which baseline is the current way of running things closest to? The baseline in the source is a vLLM setup in which the operator order, the request ordering, and even the tokenizer have been aligned. The source has no figure for a configuration that sends requests without ordering them, so the multiples can only be applied after working out whether one's current setup is better or worse than this baseline.
  • Which scale is the data closest to? The 14.04x on BIO-4 comes from scale factor 1.0, and the 1.84x over 29 queries comes from 0.1.
  • Do the hardware and the model fit? Every measurement uses one H100 and Qwen3 4B FP8. Three models are supported according to the blog post and the README (the SQL reference also names the Qwen3 rerankers and Decision 2.0 Kai), and the README lists a target device for each model separately.
  • Does the required SQL fall on the unsupported list? OR conditions, outer joins, set operations, and queries with no AI operator raise a compile error.
  • How will decision quality be validated? The evaluation in the source is about speed and cost. Whether the decisions of a small open-weight model are good enough for the task has to be measured separately against one's own labels, and the source also leaves open the effect that placing the document first in the prompt has on the answers.

What Could Not Be Confirmed

  • The contribution of each technique. The performance figures in the source are at the level of the whole system, and it gives no breakdown of how much KV rewinding, join attention, operation fusion, and the smaller output head each saved.
  • Accuracy against ground truth. The source contains only a single agreement rate between models, and it does not publish a query-by-query check of whether the baselines and Quail returned the same answers.
  • Performance outside one H100 and Qwen3 4B FP8. The source has no comparative figures for multiple GPUs, for Qwen3 32B, or for other GPUs. For DiffusionGemma there is only the runtime of the single query IMDB-2.
  • Results at scale factor 0.5, and results at scale factor 1.0 for queries other than BIO-4.
  • The derivation of the SoL estimate for plans that include joins. The source links to the calculation code and defers the explanation to a later post, and the follow-up post of October 1 covers queries that contain only filters. The code was not opened.
  • Why tokens per second and KV regret are printed as the same numbers for the AGENT dataset average in Table 1 (two queries) and for the single query AGENT-1 in Table 4. The source does not explain it.
  • How the 29 QUAIL-B queries in the blog post relate to the 50 in the README, the current latest version on PyPI, the affiliation of each individual author, and the behavior of the live demo. The PyPI page and the demo were not opened, and affiliations are not written in the blog post.
  • A direct performance comparison with the AI functions of Snowflake, BigQuery, Databricks, or MotherDuck, or with systems such as DocETL and LOTUS. The comparison targets in the source are the two vLLM baselines and a single cost estimate for GPT-5 nano.
