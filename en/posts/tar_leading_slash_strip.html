Introduction - the path inside an archive is the string given when packing

A tar archive stores a name string together with the file content. When extracting, tar interprets that name as a path under the current directory (or under a base directory that was specified) and creates the file there. So the string passed at packing time decides where the file lands later. If a relative path is given, as in tar -cf out.tar app, the names start with app/...; if an absolute path such as /home/user/app is given, the whole path tries to go into the name. At that point tar removes the leading slash and prints a warning.

The trouble comes afterwards. Only the leading slash is removed; the parent directory names stay, so extracting somewhere else creates the whole nested parent path instead of just app. The same dummy tree reproduces this and then walks through the base directory option -C, the absolute-path option -P, entries that contain a .. component, listing before extracting, and the convention of packing under a single top-level directory. The trailing slash in rsync, which changes the meaning of the source, is covered in the rsync trailing slash article; this article stays with the leading slash and path names in tar.

The questions covered are the following.

  • What does tar print when packing an absolute path, and what is the exit code?
  • Where do the files appear when that archive is extracted into another directory?
  • Do -C and relative paths produce the same archive, and what is the position rule of -C?
  • Does -P affect only packing, or also extraction?
  • How are entries with a .. component and entries with an absolute name handled on extraction?
  • What should be checked before extracting, and in what shape should an archive be packed so that nothing is scattered?

Demonstration environment and the safety frame

Every demonstration creates files only inside a fresh temporary folder made with mktemp -d, and only that folder is removed at the end. Examples that use absolute paths also target only paths inside that temporary folder. The show function is a display filter that rewrites the temporary folder path in the output to /tmp/demo; it plays no part in what tar does. The dummy tree is three files under src/app.

D=$(mktemp -d) && cd "$D" || exit 1
                    show() { sed -e "s#$D#/tmp/demo#g" -e "s#${D#/}#tmp/demo#g"; }
                    mkdir -p src/app/bin src/app/conf src/app/data
                    echo 'echo run' > src/app/bin/run.sh
                    echo 'port=8080' > src/app/conf/app.conf
                    echo 'alpha' > src/app/data/a.txt
                    tar --version | head -1
tar (GNU tar) 1.35

The kind and version are told apart by the first line of tar --version. In Git Bash on this PC it is GNU tar 1.35, and all later output comes from this tar.

The first line is the warning Removing leading `/' from member names, printed to stderr. The exit code is 0, so it is a warning and not a failure. The member names in the listing (tar -tf) do not start with a slash, yet the whole parent path is in the name, as in tmp/demo/src/app/.... Only the demo path was rewritten to /tmp/demo; the real name is the absolute path that was passed when packing, minus its single leading slash.

Extracting - the whole parent path appears

mkdir restore1
                    tar -C restore1 -xf abs.tar
                    (cd restore1 && find . -type f | sort) | show
./tmp/demo/src/app/bin/run.sh
                    ./tmp/demo/src/app/conf/app.conf
                    ./tmp/demo/src/app/data/a.txt

Although the base directory was set with -C restore1, the files did not appear under restore1/app/...; they appeared under restore1/tmp/demo/src/app/.... Because the name carries the parent path, extraction recreates the nested directories as they are. This is the shape that the problem of files ending up in an unexpected place after extracting took in this demonstration. The files are not lost; they sit deep below the base directory.

-P - keeping absolute paths makes -C powerless

The -P entry of the GNU tar manual page is a single line: "-P, --absolute-names: Don't strip leading slashes from file names when creating archives." The sentence speaks about creating, but in the output below the effect also appears when listing and extracting. The archive packs the same target as in the previous sections, this time with -P.

tar -P -cf p.tar "$D/src/app"
                    echo "exit=$?"
                    echo '--- list without -P'
                    tar -tf p.tar 2>&1 | show | head -3
                    echo '--- list with -P'
                    tar -P -tf p.tar | show | head -3
exit=0
                    --- list without -P
                    tar: Removing leading `/' from member names
                    /tmp/demo/src/app/
                    /tmp/demo/src/app/bin/
                    --- list with -P
                    /tmp/demo/src/app/
                    /tmp/demo/src/app/bin/
                    /tmp/demo/src/app/bin/run.sh

Packing with -P prints no warning and exits with 0. The listing output has two forms. tar -tf without -P prints the warning again and still shows the names as stored, starting with a slash, as in /tmp/demo/src/app/. With -P the same list appears without a warning. So whether the first character of a listed name is a slash is the clue that identifies an archive made with -P.

Next, this archive was extracted with both -P and -C restore3. The original src was first moved to src_before so that its original place is empty, and every extraction target is inside the temporary folder.

mv src src_before
                    mkdir restore3
                    tar -P -C restore3 -xf p.tar
                    echo "exit=$?"
                    echo "files under restore3: $(find restore3 -type f | wc -l)"
                    find src -type f | sort
                    diff -r src src_before && echo "recreated src is identical to src_before"
                    mkdir restore4
                    tar -C restore4 -xf p.tar
                    (cd restore4 && find . -type f | sort) | show

                    files under restore3: 0
                    src/app/bin/run.sh
                    src/app/conf/app.conf
                    src/app/data/a.txt

                    ./tmp/demo/src/app/bin/run.sh
                    ./tmp/demo/src/app/conf/app.conf
                    ./tmp/demo/src/app/data/a.txt

There are three results. First, after extracting with -P -C restore3, restore3 held 0 files, and the files were recreated at the emptied original place src/app. -C had no effect on entries with absolute names. Second, the recreated src was identical to src_before by diff -r. Third, extracting the same archive without -P into -C restore4 nested the files under restore4/tmp/demo/src/app/... together with a warning.

  • Extracting with -P ignores -C and writes to the recorded absolute location. That location does not depend on the -C of the extraction command, so the extraction command alone does not tell where the files will appear.
  • That is why -P fits restoring one's own files to the same place, and for an archive of unclear origin the first character of each listed name should be checked before extracting (section 8).
  • In this demonstration, the place written by -P was the original spot inside the temporary folder; nothing was written to system or home paths.

Entries with a .. component and entries with absolute names - handling on extraction

First, what tar does when packing a path that starts with ... A file one level up, ../outside.txt, was packed from a subfolder.

mkdir -p work/sub
                    echo 'outside content' > work/outside.txt
                    (cd work/sub && tar -cf ../dd.tar ../outside.txt)
                    tar -tf work/dd.tar
tar: Removing leading `../' from member names
                    outside.txt

When packing, tar printed the warning Removing leading `../' from member names and shortened the name to outside.txt. So a leading ../ is stripped when packing with GNU tar, and no .. entry was produced. To observe extraction, a tool that writes names verbatim is needed; below, two demonstration archives were made with the Python standard library tarfile. One holds ok/inside.txt and ../escape.txt; the other holds an absolute name inside the temporary folder, .../ext/abs_target.txt. MSYS_NO_PATHCONV=1 keeps Git Bash from rewriting the path passed as an argument; that prefix is specific to Git Bash.

mkdir craft ext
                    cat > craft/make.py <<'PYEOF'
                    import io, sys, tarfile
                    target = sys.argv[1]
                    def add(tf, name, data):
                        info = tarfile.TarInfo(name)
                        info.size = len(data)
                        tf.addfile(info, io.BytesIO(data))
                    with tarfile.open('craft/dotdot.tar', 'w') as tf:
                        add(tf, 'ok/inside.txt', b'inside')
                        add(tf, '../escape.txt', b'escaped')
                    with tarfile.open('craft/abs.tar', 'w') as tf:
                        add(tf, target + '/ext/abs_target.txt', b'absolute')
                    PYEOF
                    MSYS_NO_PATHCONV=1 python craft/make.py "$D"
                    tar -tf craft/dotdot.tar
                    tar -tf craft/abs.tar 2>&1 | show
ok/inside.txt
                    tar: Removing leading `../' from member names
                    ../escape.txt
                    tar: Removing leading `/' from member names
                    /tmp/demo/ext/abs_target.txt

With the default settings, ../escape.txt was not extracted, with the error Member name contains '..' and exit code 2. The normal entry ok/inside.txt of the same archive was extracted. Adding -P ended with exit code 0 and created ext/escape.txt outside ext/inner. Two facts are directly visible in the output above: the refusal of one entry did not stop the extraction of the others, and -P lifted the .. check as well.

The absolute-name entry was extracted the same way. The find below prints only where abs_target.txt was placed.

With the default settings the file was nested at ext/inner/tmp/demo/ext/abs_target.txt with a warning, and the second extraction with -P also created the file at the recorded absolute location ext/abs_target.txt. In summary, the default settings strip the leading slash and refuse .., while -P lifts both.

Checking before extracting and the single top-level directory convention

The two risks of section 7 can be screened out at the listing stage. The grep below picks out only names that start with a slash or have a .. component. This regular expression is for the demonstration and is not a feature provided by tar.

tar -tf p.tar 2>/dev/null | grep -E '^/|(^|/)\.\.(/|$)' | show | head -2
                    tar -tf craft/dotdot.tar 2>/dev/null | grep -E '^/|(^|/)\.\.(/|$)'
                    tar -tf rel.tar | grep -cE '^/|(^|/)\.\.(/|$)'
/tmp/demo/src/app/
                    /tmp/demo/src/app/bin/
                    ../escape.txt
                    0

p.tar, made with -P, was flagged for its names starting with a slash, dotdot.tar for ../escape.txt, and rel.tar, made with relative paths, had zero hits. If a person reads this list or a script checks it before extracting, the archive can be screened out before the behavior of section 7 is reached. Reading a listing creates no files, so there is nothing to undo. Using the listing as a rehearsal for extraction also appears in the article on dry-run design for shell scripts.

The number of top-level entries can also be read from the listing. An archive packed as the three names bin conf data is compared with one packed as the single name app, and the first is extracted into a directory that already holds a file (mine.txt).

tar -C src/app -cf bomb.tar bin conf data
                    tar -tf bomb.tar | cut -d/ -f1 | sort -u
                    tar -C src -cf one.tar app
                    tar -tf one.tar | cut -d/ -f1 | sort -u
                    mkdir spill
                    echo keep > spill/mine.txt
                    (cd spill && tar -xf ../bomb.tar && ls)
                    mkdir clean
                    (cd clean && tar --one-top-level=out -xf ../bomb.tar && find . | sort)
bin
                    conf
                    data
                    app
                    bin
                    conf
                    data
                    mine.txt
                    .
                    ./out
                    ./out/bin
                    ./out/bin/run.sh
                    ./out/conf
                    ./out/conf/app.conf
                    ./out/data
                    ./out/data/a.txt
  • The archive packed as bin conf data has three top-level names, and extracting it mixed bin, conf and data into the directory that holds mine.txt.
  • The archive packed as the single name app has only one top-level name, so wherever it is extracted, the files gather under app.
  • --one-top-level=out is a safeguard used on the receiving side. The manual page describes it as "Extract all files into DIR, or, if used without argument, into a subdirectory named by the base name of the archive", and in the output the files are gathered under out/.
  • The convention on the packing side is to move -C to the parent directory and pass a single directory name (tar -C src -cf one.tar app).

Last is the default behavior when a name collides with an existing file. ow/note.txt holds OLD, and a file of the same name holding NEW is extracted. The manual page describes -k as "Don't replace existing files when extracting."

mkdir ow t1
                    echo OLD > ow/note.txt
                    echo NEW > t1/note.txt
                    tar -C t1 -cf note.tar note.txt
                    (cd ow && tar -k -xf ../note.tar; echo "exit=$?"; cat note.txt)
                    (cd ow && tar -xf ../note.tar; echo "exit=$?"; cat note.txt)
tar: note.txt: Cannot open: File exists
                    tar: Exiting with failure status due to previous errors
                    exit=2
                    OLD
                    exit=0
                    NEW

With -k, the error note.txt: Cannot open: File exists and exit code 2 appeared, and the content stayed OLD. Without an option, the exit code was 0 and the content changed to NEW. The default overwrites without asking and without any message. When extracting into a directory that may contain the same names, creating an empty directory and pointing -C at it avoids this outcome.

Two tars on the same PC - GNU tar and the Windows built-in tar.exe

Windows 10 ships C:\Windows\System32\tar.exe, which is a different kind of tar from the one in Git Bash. Its behavior was compared using the same dummy tree and the same demonstration archives. The temporary folder made by the demonstration was removed as below. The case statement is a guard that runs rm -rf only when the target is a path under the temporary folder, and the last line checks that the folder is gone.

case "$D" in "${TMPDIR:-/tmp}"/*) cd / && rm -rf "$D" ;; esac
                    test -e "$D" && echo "still exists" || echo "removed"

Summary - the order when packing and when extracting

  • When packing, set the parent directory as the base with -C and pass a single directory name (tar -C parent -cf out.tar name). No warning appears, and the member names start with name/... (section 5).
  • If the Removing leading warning appears, an absolute path has already been packed, so expect the parent path to be nested when that archive is extracted (sections 3 and 4).
  • For a received archive, read the list with tar -tf before extracting and check for names starting with a slash, .. components, and the number of top-level names (section 8).
  • When extracting, point -C at a newly made empty directory. Existing files of the same name are replaced without asking in the default settings (section 8), and an empty directory prevents that case.
  • -P ignores -C on extraction and writes to the recorded absolute location. Use it only to restore one's own files to the same place, and not for archives of unclear origin (sections 6 and 7).
  • The Git Bash tar and the built-in tar.exe on Windows differ in messages and exit codes, so a script that reads output strings should first fix which tar it uses (section 9).

The encoding problem of archive file names is not covered here; the article on Korean file names inside zip covers it, including the absence of an encoding declaration in tar. What Could Not Be Verified

  • The official GNU tar manual (gnu.org) could not be opened because the connection from this PC was refused. The quoted sentences come from the man.archlinux.org edition shown as the GNU TAR Manual page, and that edition shows the package notation 1.35-5.
  • The developers' own explanation of the purpose of stripping the leading slash. The reasoning in the body is limited to behavior shown by the run output (warning, nesting, -C being ignored, .. being refused).
  • The output of tar on Linux and macOS. Only GNU tar 1.35 in Git Bash and bsdtar 3.5.2 on Windows were run on this PC.
  • Warning wording and the .. check in other GNU tar versions, and extraction behavior for archives with symbolic link or hard link members.
  • Name-rewriting options such as --strip-components and --transform, and combinations with compression formats (gz, xz).
  • The behavior of -P in bsdtar, and extraction results for names that mix long Windows paths or drive letters.
