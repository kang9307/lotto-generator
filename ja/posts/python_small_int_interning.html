is で比べると、ある数は真で、ある数は偽になる - 整数キャッシュと同一性比較

テストは通るのに本番でだけ条件が合わない理由 - 最適化は仕様ではない

2026-08-01 開発・インフラ

はじめに: テストは通ったのに本番でだけ条件が合わなかった

ステータスコードが特定の値かどうかを調べる関数があった。単体テストはすべて通った。ところが本番に上げると、その分岐が一度も通らない。コードを読み直しても論理には何の問題もなさそうだ。値をログに出せば確かに期待したその数字である。それなのに条件が偽になる。

原因は比較演算子ひとつだった。== を書くべき場所に is が入っていた。そしてこの間違いが恐ろしいのは、間違えたことそのものではない。テストが通ってしまったことである。テストはコードに数字を直接書き込んでいて、本番はその値をソケットと文字列パースを経て受け取っていた。同じ数字なのに結果が分かれた。

この記事の主張は「is を使うな」ではない。is はまっとうな演算子で、必ず必要な場面がある。正確な主張はこうだ。

  • is は「同じオブジェクトか」を問う。「値が同じか」を問うのではない。この 2 つは別の問いである
  • 同じ値が同じオブジェクトかどうかはインタプリタの最適化が決める。 よく使うオブジェクトを再利用するのは速度のための実装上の選択であって、言語が約束したことではない
  • 最適化は仕様ではないので、その結果に頼ってはいけない。 実装が変われば答えも変わる
  • 小さい数でたまたま真になることのほうが危ない。 たまたま合う答えのせいで テストが通ってしまうからだ

最後の項目が核心である。いつも間違えるバグはすぐ見つかる。たまにしか合わないバグがリリースまで生き延びる。 以下はその「たまに」の境界がどこなのかを、実際に走らせて突き止めた記録だ。

実行環境。 以下の出力はすべて Windows 10 Pro (10.0.19045) で実際に実行した結果である。インタプリタは CPython 3.13.3、ビルドは tags/v3.13.3:6280bb5, Apr 8 2025, 14:47:33 [MSC v.1943 64 bit (AMD64)] だ。スクリプトはすべてファイルに保存してから実行した。

この記事に出てくるキャッシュ範囲の数字は仕様ではない。「どこからどこまでが共有される」という値は このインタプリタ、このバージョンで測定した結果にすぎない。他の実装や他のバージョンでは異なり得る。この記事はその数字を覚えろと言っているのではなく、そういう数字に頼るコードがなぜ危ないのかを示すために書かれている。

この記事が扱わないこと。 関数のデフォルト引数がいつ評価されるかは デフォルト値が評価される時点で扱った。話題は違うが教訓はつながる。実装の詳細に頼ってはいけないということだ。

ここは必ず押さえておきたい。 上の「-5 から 256 まで」は 測定値であって規格ではない。 Python の言語リファレンスはこの点を明確に書いている。a = 1; b = 1 の後に 2 つの名前が同じオブジェクトを指すこともあれば指さないこともあり、実装によって異なるのでこれに頼ってはならないとある。同じ文書は、値の等しいリテラルを複数回評価したとき 同じオブジェクトを得ることも、値だけ同じ別のオブジェクトを得ることもあるとも書いている。

だからこの記事から持ち帰るべきものは数字 2 つではない。「ある範囲ではたまたま合う」という事実そのものだ。その偶然がテストを緑にする。

2. id で覗く - 同じ値、違うアドレス

is が実際に何を見ているのかを確かめる。公式ドキュメントは is が オブジェクトのアイデンティティを比較し、そのアイデンティティは id() で得られると定義している。そこで id() を直接出力してみた。

--- 2-1. id() of two equal values ---
n        id(a)              id(b)              same  a==b
------------------------------------------------------------------
5        140735027553320    140735027553320    True  True
100      140735027556360    140735027556360    True  True
256      140735027561352    140735027561352    True  True
257      1406444444016      1406444443248      False True
1000     1406444443280      1406444443312      False True
1000000000000 1406444443248      1406444444016      False True

--- 2-2. the same object every time you ask for it ---
distinct ids for the value 7 across 5 builds : 1
distinct ids for the value 777 across 5 builds: 3
  (777 ids can repeat by accident: a freed object's address gets reused)

アドレスの桁を見ると面白いことが見える。キャッシュされた値は 140735… で始まる区画に固まっていて、キャッシュ外の値は 1406… で始まる別の区画にある。 前者はインタプリタの起動時から存在する領域で、後者は必要になるたびに確保される領域だ。

ところが 2-2 の最後の行に落とし穴がある。値 777 を 5 回作ったところ、異なるアドレスが 3 つしか出てこなかった。5 回のうち 2 回は、先に作ったオブジェクトが消えた場所に新しいオブジェクトが座ったのである。これをもっと極端な形で示した。

--- 2-3. id reuse makes id() alone untrustworthy ---
id of a dead 999999 : 1406444443312
id of a fresh 888888: 1406444443312
addresses equal     : True  <- equal ids, different values

--- 2-4. keeping a reference changes the answer ---
both alive at once  : id equal = False  a is b = False

--- 2-6. sys.getrefcount on a cached object ---
refcount of 1  : 4294967295
refcount of 777: 1
  a cached object is referenced from everywhere in the process
  • 値が 999999 のオブジェクトと 888888 のオブジェクトが同じアドレスを報告した。 最初のオブジェクトが消えた後、その場所を 2 つ目が再利用したからである。公式ドキュメントも id() は オブジェクトの生存期間の間だけ一意で、生存期間が重ならない 2 つのオブジェクトは同じ値を持ち得ると明記している
  • だから id() の値をどこかに保存して後で比べるコードは 原理的に誤っている。 保存した瞬間にそのオブジェクトが生きている保証が消える
  • 2-4 では 2 つのオブジェクトを同時に生かしておくとアドレスが分かれた。つまり 同じコードでも参照を握っているかどうかで答えが変わる
  • 最後のブロックの参照カウントが目を引く。キャッシュされた 1 のカウントが 42 億台だ。このインタプリタで常時再利用されるオブジェクトは回収対象から外れるよう印が付けられる。一方 777 は 1 だった

ところがここで予想外の結果がひとつ出た。キャッシュ範囲の 外である 257 を演算で作って比べたら真になったのだ。

--- 2-5. two address regions, and an unexpected True ---
200 + 56 = 256  300 - 44 = 256  x is y = True
200 + 57 = 257  300 - 43 = 257  p is q = True
  the second pair is OUTSIDE the cache yet still True.
  the cache is not the only thing that makes 'is' true - see experiment 3.
  compare with values built at run time:
  make(257) is make(257) = False

同じ 257 なのに 演算式として書けば真、実行時に作れば偽である。キャッシュだけでは説明できない。第 2 の原因がある。

3. 同じコードなのに実行方法で答えが違う

第 2 の原因は コンパイラの定数処理だ。コードをコンパイルするとき同じリテラルが複数回現れると、コンパイラはそれを 1 つのオブジェクトにまとめてコードオブジェクトの定数表に入れる。200 + 57 のような式もコンパイル時に計算されて定数になる。実行中はその定数を取り出すだけなので、2 つの名前が同じオブジェクトを指すことになる。

--- 3-1. module level, one file, two statements ---
a = 257 ; b = 257   ->  a is b = True

--- 3-2. inside a function, same code object ---
same function body  -> True
two function bodies -> True

--- 3-3. what the compiler stored ---
co_consts of f() : (None, 257)
g1 const id      : 140735026668016
g2 const id      : 140735026668016
same object      : True

bytecode of f():
 13           RESUME                   0

 14           LOAD_CONST               1 (257)
              STORE_FAST               0 (a)

 15           LOAD_CONST               1 (257)
              STORE_FAST               1 (b)

 16           LOAD_FAST_LOAD_FAST      1 (a, b)
              IS_OP                    0
              RETURN_VALUE

バイトコードがすべてを語っている。2 行とも LOAD_CONST 1 だ。定数表の同じ枠を 2 回読んだのだから同じオブジェクトにしかなり得ない。 さらに別々の 2 つの関数の定数までもが同じオブジェクトだった。1 つのモジュールをコンパイルする間、定数が共有されるからである。

ではコンパイル単位を分けるとどうなるか。

--- 3-4. exec: one string vs two strings ---
exec, single string  -> True
exec, three strings  -> False

--- 3-5. compile() separately then exec ---
separate code objects -> False
const in c1 : [257]
const in c2 : [257]
same object : False

--- 3-6. a real REPL, statement by statement (code module) ---
REPL, line by line  -> False
REPL, small number -> True

結果が完全に分かれた。3-5 を見ると 2 つのコードオブジェクトがそれぞれ 257 という定数を持っているのに その 2 つは別のオブジェクトだ。実務で最も重要なのは 3-6 である。対話型インタプリタは 1 行がそのまま 1 つのコンパイル単位なので定数が共有されない。だから対話型では偽になる。

プロセスを分けても確かめた。

--- 3-7. child process: python -c, script file, piped stdin, -i ---
python -c            -> True
script file          -> True
piped stdin (python) -> True
piped stdin (-i)     -> False
  stderr tail of -i  : >>> >>> >>> >>>

--- 3-8. the same test written so the compiler cannot help ---
module level, run-time values -> make(257) is make(257) = False
module level, literal values  -> 257 is 257 (via consts)  = True

同じ 2 行についての結果を表にまとめるとこうなる。これがこの記事で 2 番目に重要な表だ。

実行方法a = 257; b = 257 の後の a is b理由

引数として渡したコードTrue文字列全体が 1 つの単位
標準入力に流し込むTrue全体を読んで一度にコンパイル

実務上の含意は大きい。対話型で確かめた結果とスクリプトの挙動が違い得る。 対話型で偽が出たので「やはり使ってはいけないのだな」と == に直したなら幸いだが、逆にスクリプトで真が出て「動くじゃないか」と流したなら、そのコードは 値の出どころが変わった瞬間に静かに崩れる。

4. 文字列も同じだ

整数だけの話ではない。文字列も同じ原理で共有される。ただし条件が少し違う。

--- 4-1. literals in one compilation unit ---
s1 = "total" ; s2 = "total"      -> s1 is s2 = True
with a space in it               -> t1 is t2 = True

--- 4-2. built at run time ---
"to" + "tal"        is base : True   == base : True
parts[0] + parts[1] is base : False   == base : True
"".join(parts)      is base : False   == base : True
percent format      is base : False   == base : True
f-string            is base : False   == base : True

--- 4-3. length matters for run-time strings ---
built            is-literal   len
----------------------------------------
''               True         0
'x'              True         1
'xx'             False        2
'xxx'            False        3
'xxxx'           False        4
'xxxxx'          False        5

4-2 の 1 行目と 2 行目の違いが重要だ。リテラルどうしの足し算はコンパイル時に合成されて定数になるが、リストから取り出した断片を足したものは実行時に新しいオブジェクトになる。値は同じなのに同一性検査だけが分かれる。

4-3 は空文字列と 1 文字だけが共有されることを示している。これもよく使うオブジェクトをあらかじめ作っておく最適化だ。ではコンパイル単位を分けて見直す。

--- 4-4. identifier-shaped vs not, from a REPL (separate units) ---
  identifier-shaped     -> True
  with a space          -> False
  with a hyphen         -> False
  empty string          -> True
  single ascii char     -> True

--- 4-5. sys.intern forces sharing ---
run-time built, two copies       : False
after sys.intern on both         : True
interned is the literal          : True

--- 4-6. slicing produces new objects ---
name[:] is name       : True    (full slice can return self)
name[0:7] is name     : True
name[1:] is "ser_id"  : False
name[1:] == "ser_id"  : True

4-4 が「識別子の形をした文字列はインターンされる」という話の実体だ。コンパイル単位が別々なのに user_id は真になり、空白やハイフンが入った途端に偽になった。変数名として使える形の文字列だけが自動的に共有されるからである。

  • つまり キー名のような識別子の形の文字列は is がたまたま合う確率が高い。 これがこのバグを特にうまく隠す
  • 逆にユーザー名、文、ハイフン混じりのコード値はほぼ常に偽になる。同じコードがデータによって違う動きをする
  • 強制的に共有させたければインターン関数を明示的に呼ぶ必要がある。4-5 でその結果が真に変わった。ただしこれは メモリ節約が目的であって比較のための道具ではない
  • 4-6 の 1 行目も落とし穴だ。全体スライスが 同じオブジェクトを返すこともある。「スライスは常に新しいオブジェクト」という当て推量も外れる

実務でこの問題がどこで爆発するかが最後のピースだ。値が 外から入ってくる瞬間である。

--- 4-7. where this bites: values that came from outside ---
json value  is literal : False   == literal : True
csv  value  is literal : False   == literal : True

--- 4-8. the same for other immutable types ---
() is ()            : True
tuple() is tuple()  : True
(1,2) built vs lit  : False
0.0 is 0.0 (consts) : True
float('0.0') twice  : False

同じ文字列なのに シリアライズ形式から取り出した値はリテラルとは別のオブジェクトだ。設定ファイル、API 応答、表形式ファイル、ユーザー入力すべて同じである。冒頭のシナリオがまさにこれだ。テストはコードに値を書き、本番は外から受け取った。

5. == と is は別の問いを立てている

ここで整理する。2 つの演算子は代替品ではなく 別の問いである。

--- 5-1. the two questions are different ---
a == b : True    same value
a is b : False   different objects
a is c : True    same object
after b.append(4)  a = [1, 2, 3]  b = [1, 2, 3, 4]
after c.append(9)  a = [1, 2, 3, 9]  c = [1, 2, 3, 9]   <- c IS a

--- 5-2. equal but not identical, identical but not equal ---
x = float('nan')
  x is x : True    same object
  x == x : False   a value that is not equal to itself
  x in y : True    'in' tries 'is' first, then '=='
  any(v == x for v in y) : False

--- 5-3. __eq__ can say anything; 'is' cannot be overridden ---
p == q : True   __eq__ decides
p is q : False  identity is not overridable
p == 5 : True
p is p : True

--- 5-4. objects that define no __eq__ fall back to identity ---
m == n : False   default __eq__ IS identity
m is n : False

5-2 が 2 つの問いが完全に独立であることを証明している。同じオブジェクトなのに自分自身と等しくない値が存在する。そして所属を問う演算は同一性を先に確認するので真になるのに、値比較だけで確かめると偽になる。同じ問いだったらこんなことは起こり得ない。

5-4 はこのバグがなぜ遅れて見つかるのかを説明する。等価の動作を定義していないクラスは既定値がそのまま同一性比較だ。だからそういうクラスでは 2 つの演算子が常に同じ答えを出す。後日そのクラスに等価の動作が追加された瞬間、それまで動いていた同一性比較が突然間違いになる。

演算子問うこと実装クラスが変えられるか使う場所
a == b値が同じかクラスの等価動作変えられる値比較のすべて
a is b同じオブジェクトかアイデンティティ比較変えられないシングルトン、センチネル、共有判定
a != b値が違うかクラスの非等価動作変えられる値比較のすべて
a is not b違うオブジェクトかアイデンティティ比較変えられないシングルトン、センチネル

「変えられない」が is の唯一の強みだ。そしてその強みが必要な場所は実際にある。

--- 5-5. when 'is' is the right tool: singletons ---
None is None            : True
Ellipsis is Ellipsis    : True
NotImplemented is itself: True
  fetch('a' ) -> None
  fetch('b' ) -> 0
  fetch('c' ) -> ''
  fetch('zz') -> 'MISS'
  note 'a' holds None and 'b' holds 0: a truthiness check would lose both

--- 5-6. the falsy trap that 'is SENTINEL' avoids ---
  bad('a' )   -> 'MISS'
  bad('b' )   -> 'MISS'
  bad('c' )   -> 'MISS'
  bad('zz')   -> 'MISS'
  three stored values were reported as missing

2 つのブロックを並べて見てほしい。同じ保管庫に対して一方は正確に答え、もう一方は 3 件を失った。 保存された値が「なし」だったり 0 だったり空文字列だったりするとき、真偽だけを見る検査はそれらをすべて「ない」と判定する。こういうときに必要なのが 世界に 1 つしかない目印のオブジェクトであり、それを確認する唯一の方法が is だ。

6. is None はなぜ安全で is True はなぜ違うのか

「None の比較には同一性検査を使え」という規則は広く知られている。その理由を実行で確かめた。

--- 6-1. None is a singleton: try to make a second one ---
type(None)          : <class 'NoneType'>
type(None)() worked : True  <- it returns the same object
copy.copy(None) is None      : True
copy.deepcopy(None) is None  : True
pickle round trip is None    : True
id(None) stable in a loop    : True

--- 6-2. None across a process boundary ---
id(None) here      : 140735026668016
id(None) in child  : 140735026668016

--- 6-3. why 'is None' and not '== None' ---
w == None : True   <- a class talked its way into looking like None
w is None : False  <- identity cannot be talked into anything

a column-style 'missing' object:
  m == None : True
  m is None : False
  if m == None: would take the branch; if m is None: would not
  • 2 つ目を作る方法がない。 型を直接呼び出しても元のオブジェクトが返ってきた。コピー、深いコピー、シリアライズの往復すべて同じオブジェクトだった
  • だから x is None は インタプリタの最適化とは無関係に常に正確だ。1 節のキャッシュの話とは性格がまったく違う
  • 6-3 が等価演算子を使ってはいけない理由である。クラスが等価の動作を再定義すると、None ではないオブジェクトが None と等しいと答える。 表形式データを扱うライブラリが実際にこういう「欠損値」オブジェクトを使っている
  • 6-2 は興味深いが誤解しやすい。親プロセスと子プロセスで同じアドレスが出たのは、このオブジェクトが実行ファイルの中に固定の場所を持っているからだ。だからといって id() の値をプロセス間で比べてよいという意味ではない。 2 節で見たとおり通常のオブジェクトのアドレスは再利用される

では真偽値も 1 つしかないオブジェクトなのだから is True も構わないのか。構文的には安全だが 意味がずれる。

--- 6-4. True is a singleton too, but the comparison is still wrong ---
bool(1) is True     : True
True is True        : True

value    type           == True    is True    if value:
--------------------------------------------------------
1        int            True       False      True
1.0      float          True       False      True
True     bool           True       True       True
'1'      str            False      False      True
[1]      list           False      False      True

--- 6-5. a function returning 1 instead of True ---
legacy_flag    -> 1      if v:True    v == True:True    v is True:False
modern_flag    -> True   if v:True    v == True:True    v is True:True

表の最後の列を見てほしい。5 つの値がすべて真だ。 ところが同一性検査の列は 1 つしか真でない。つまり「真かどうか」を is True で問うと 真である値の大半を偽と判定する。

6-5 が実務のシナリオだ。古い関数が 1 を返していたのが真に変わったり、その逆になったりすると、真偽検査と等価比較はそのままで、同一性の分岐だけがひっくり返る。 変更履歴には「真偽値に整理」としか書かれていないので、原因を突き止めるのが難しい。

ここで冒頭の事故をそのまま再現する。

--- 6-6. 'is 0' and friends: run-time values break the spell ---
  value 0       v == 0:True   v is zero:True   | v == 257:False  v is big:False
  value 1       v == 0:False  v is zero:False  | v == 257:False  v is big:False
  value 256     v == 0:False  v is zero:False  | v == 257:False  v is big:False
  value 257     v == 0:False  v is zero:False  | v == 257:True   v is big:False
  value 1000    v == 0:False  v is zero:False  | v == 257:False  v is big:False

--- 6-7. the dangerous shape: a test that passes for the wrong reason ---
status_code_ok(200)          : True   <- literal 200, same const pool
status_code_ok(int('200'))   : True   <- 200 is inside the cache
status_code_ok(199 + 1)      : True
status_code_ok2(500)         : True   <- literal, const pool again
status_code_ok2(int('500'))  : False   <- outside the cache: FALSE
status_code_ok2(499 + 1)     : True

6-7 がこの記事全体の要約だ。code is 200 と書いた関数は 3 通りの呼び出し方すべてで通った。 200 がキャッシュ範囲の中だからである。ところが同じ書き方の code is 500 の関数は 文字列から作った値を入れた途端に偽になった。

ここがこの記事の核心だ。 2 つの関数は まったく同じ間違いを犯している。それなのに一方は通り、一方は失敗する。違いはただ、ステータスコードの数字がキャッシュ範囲の内か外かだけだ。

そしてなぜこれが危ないのか。200 番台の成功コードで書いたテストはすべて緑になる。 エラー処理の経路をテストしていなければ、400 番台・500 番台でしか壊れないバグがリリースされる。失敗経路はテストのカバレッジが薄い場所でもあるので、このバグは まさに最も見つけにくい場所に隠れる。

真偽値と整数の関係は別の話題に見えるが根は同じだ。何が同じものとして扱われるかという問題である。

7-7 が解法だ。型そのものが真偽値かどうかを確認しなければならない。 整数かどうかを問う検査は真偽値を通す。「数値だけ受け付ける」という検証をそう書いておくと、真偽値がそのまま流れ込む。

7-8 の 2 行目がその結果を示している。2 項目を書いたのに シリアライズ結果には 1 つしか残らず、キーが文字列の true に変わった。 シリアライズ関数が悪いのではない。その関数が見る前にすでに辞書でまとまった後だった。

8.2 第 2 段階 - 構文木を自分で走査する

死角を埋めるにはコードを構造として読む必要がある。標準ライブラリの構文木モジュールで検査器を作った。核心部分はこうだ。

SAFE = {"None", "True", "False", "Ellipsis", "NotImplemented"}

class Checker(ast.NodeVisitor):
    def classify(self, node):
        if isinstance(node, ast.Constant):
            if node.value is None or isinstance(node.value, bool):
                return None                       # singleton, fine
            return "LITERAL", "literal comparison"
        if isinstance(node, (ast.Tuple, ast.List, ast.Dict, ast.Set)):
            return "LITERAL", "display literal"
        if isinstance(node, ast.BinOp):
            return "EXPR", "arithmetic result"
        if isinstance(node, ast.Call):
            fn = getattr(node.func, "id", None)
            if fn in ("int", "float", "str", "bytes", "tuple", "list"):
                return "EXPR", "conversion result"
            return None
        if isinstance(node, ast.Name):
            if node.id in SAFE:
                return None                       # singleton name, fine
            if node.id in self.consts:
                return "CONSTNAME", "name bound to a literal"
        return None

    def visit_Compare(self, node):
        for op, right in zip(node.ops, node.comparators):
            if not isinstance(op, (ast.Is, ast.IsNot)):
                continue
            for side in (node.left, right):
                got = self.classify(side)
                if got:
                    self.hits.append((node.lineno, got[0], got[1]))
                if isinstance(side, ast.Constant) and isinstance(side.value, bool):
                    self.hits.append((node.lineno, "BOOLSINGLETON", "is True/False"))
        self.generic_visit(node)

モジュール最上位の 名前 = リテラル の代入をまず集めておき、比較式の両側をその一覧と照合するのが要点だ。見本ファイルに走らせた結果である。

9. チームの規約とチェックリスト

ツールはコードにすでにあるものを見つけるだけだ。新しく入ってくるのを防ぐには規約が要る。以下は上の実行結果から直接導かれるものだけを書いた。

9.1 規約

  1. is はシングルトン専用。 None、明示的に作った目印オブジェクト、列挙型のメンバ。この 3 つ以外で is を見たらレビューで理由を問う
  2. 値比較は例外なく ==。 整数、文字列、ステータスコード、設定値すべて該当する。「小さい数だから大丈夫」は根拠にならない
  3. 「値なし」の判定に真偽検査を使わない。 5-6 で見たとおり 0 と空文字列が一緒に消える。目印オブジェクトを作って is で確認する
  4. is True は「ちょうどそのオブジェクトか」を問うときだけ。 その意図なら なぜそうなのかコメントを残す。 コメントのない is True は間違いとみなす
  5. 型の判別は型を直接見る。 整数かどうかを問う検査は真偽値を通す(7-7)
  6. 辞書と集合のキーに 0 と偽、1 と真を混ぜない。 7-5 のように行が静かに消える
  7. テストにリテラルだけを入れない。 これが最も重要だ。文字列パース、シリアライズの往復、実際の入出力を経た値でも同じ検証をする。6-7 がその理由である
  8. id() の値を保存したりプロセス間で比べたりしない。 2-3 で見たとおりアドレスは再利用される

9.2 チェックリスト

  • インタプリタの警告をエラーに昇格させる手順をビルドに入れた
  • 構文木の検査器をリポジトリ全体に一度走らせ、結果を検討した
  • == None をすべて同一性検査に変えた
  • 残っている is True と is False のすべてに理由のコメントが付いている
  • 定数名と is で比較している箇所がない(インタプリタの警告が捕まえられない形だ)
  • 「値なし」の判定に目印オブジェクトを使っており、そのオブジェクトがモジュールの外に漏れていない
  • 整数の検証で真偽値が通ってもよいかを各地点で判断した
  • 辞書・集合のキーに 0 と偽が一緒に使われている箇所がない
  • 集計・計数のロジックに真偽値と整数が混ざって入ってこない
  • テストが 外から入ってきた値でも同じ分岐を検証している
  • 成功コードだけでなく 失敗コードの経路もテストしている(6-7 の罠がここにある)
  • コメントや文書にキャッシュ範囲の数字を根拠として書いた箇所がない
  • 対話型で確かめた結果をスクリプトの挙動の根拠に使った箇所がない
  • 列挙型や目印オブジェクトのような 意図的なシングルトンにだけ is が残っている

10. この記事で確認できなかったこと

確認していないことを確認したかのように書くと、次の人を誤って導く。限界を明確にしておく。

  • 他の実装。 すべての測定は 1 つのインタプリタ実装、1 つのバージョン、1 つのオペレーティングシステムで行われた。他の実装で同じ結果になるとは主張しない。 むしろこの記事の主張はそれが変わり得るという側にある
  • 他のバージョン。 同じ実装でもバージョンによって最適化が変わり得る。2-6 で見た参照カウントの動作もバージョンごとに違い得る領域だ
  • 静的検査ツールの実際の挙動。 8-1 で述べたとおりこの環境には 1 つも入っていなかった。規則番号に言及しなかった理由がこれである
  • マルチスレッド・マルチインタプリタ環境。 オブジェクトの共有の仕方が変わり得る領域だが、この記事では扱わなかった
  • 性能への影響。 同一性検査が等価比較より速いのは事実だが、その差は測定していない。そして 間違った答えを速く出すことに価値はない
  • 他の言語の同一性比較。 似た落とし穴があると言われているが、この記事では実行していない

ただし確認できなかったものには共通点がある。すべて「実装がどうするか」に関する問いだ。 そしてこの記事の結論は実装の挙動を知らないと成り立たないものではない。実装が何をしようと、値比較には == を使えばよい。 それが実装を知らなくてよくする唯一の方法である。

結論: 通ってしまうテストが最も危ない

整理するとこうだ。is は「同じオブジェクトか」を問う。値比較にそれを使うと、答えが合うかどうかは インタプリタの最適化が決める。このインタプリタで測定した共有範囲は -5 から 256 までで、短い文字列と識別子の形の文字列も共有された。ところがその範囲は 測定値であって規格ではない。

そして原因が 1 つではないことがこの問題をさらに難しくしている。キャッシュが 1 つ、コンパイル単位の中の定数共有がもう 1 つだ。後者のせいで 同じコードがスクリプトでは真、対話型では偽になった。確かめ方によって結論がひっくり返るのである。

最も重要なのは最後の点だ。このバグはいつも間違えるわけではない。たまに合う。 200 番のステータスコードで書いたテストは通り、500 番台でだけ崩れる。値をコードに書いたテストは通り、外から受け取った値でだけ崩れる。だからこのバグはテストを通ってリリースされた後、最も確かめにくい経路で初めて姿を現す。

規則は短い。is は None と目印オブジェクトと列挙型のメンバにだけ使う。 残りはすべて == だ。この規則を守ればキャッシュ範囲がいくつからいくつまでかを知る必要がなくなる。実装の詳細を知らなくてよくすることが良い規則の条件である。

今すぐできることがひとつある。リポジトリで is を検索し、None 以外と比較している行を数えてみてほしい。 そのうち定数名と比較しているものがあれば、インタプリタの警告では絶対に捕まらない。そしてそのコードのテストが緑なら、緑である理由がコードが正しいからなのか値が小さいからなのかを確かめてみる価値がある。

# `==` と `is` — 判断表・再現コード・検出器・チェックリスト

> 出典: braindetox.kr — is で比べると、ある数は真で、ある数は偽になる
> 測定環境: Windows 10 Pro (10.0.19045) / CPython 3.13.3 (MSC v.1943 64bit AMD64)
> このファイルをそのまま AI に貼って「この基準でうちのコードベースを点検して」と書けば使えます。
> 以下に出てくるキャッシュ範囲の数値は **このインタプリタで測定した値**であって、言語仕様ではありません。他の実装・他のバージョンでは変わり得ます。

## 0. 一行でいうと

`is` は「同じオブジェクトか」を問い、`==` は「同じ値か」を問う。
値を比べたいのに `is` を書くと、答えが合うかどうかは **インタプリタの最適化**が決める。
最適化は仕様ではないので、**その結果に依存してはいけない。**

## 1. 判断表 — 何を使うか

| やりたいこと | 使うもの | 使ってはいけないもの | 理由 |
|---|---|---|---|
| 値が同じか | `a == b` | `a is b` | 同じ値が同じオブジェクトである保証はない |
| None か | `x is None` | `x == None` | `__eq__` はクラスが再定義できる |
| None でないか | `x is not None` | `x != None` | 同じ理由 |
| 真かどうか (一般) | `if x:` | `x is True` | `1`, `[1]`, `'a'` は真だが `is True` は偽 |
| ちょうど `True` オブジェクトか | `x is True` | — | その意図ならば正しい。ただしコメントを残すこと |
| bool 型かどうか | `type(x) is bool` | `isinstance(x, int)` | `bool` は `int` のサブクラス |
| 「値がない」の判別 | `x is SENTINEL` | `if not x:` | `0`, `''`, `[]` を「ない」と誤認する |
| 同じオブジェクトを共有しているか | `a is b` | `a == b` | これこそが `is` の本来の用途 |
| Enum メンバの比較 | `x is Color.RED` | `x == 'RED'` | Enum メンバはシングルトン |
| 文字列の値の比較 | `s == 'admin'` | `s is 'admin'` | 実行時に作られた文字列は共有されない |

## 2. 再現コード — そのまま貼って実行

```python
# repro.py
import sys

def make(n):
    """実行時に整数を作る。コンパイル時定数の再利用を避けるための仕掛け。"""
    return int(str(n))

print(sys.version)

for n in (0, 5, 256, 257, 1000):
    a, b = make(n), make(n)
    print(n, "is:", a is b, " ==:", a == b)

def shared(n):
    return make(n) is make(n)

lo, hi = 0, 1 << 20
while hi - lo > 1:
    mid = (lo + hi) // 2
    if shared(mid):
        lo = mid
    else:
        hi = mid
print("共有される最後の値 :", lo)

lo2, hi2 = -(1 << 20), 0
while hi2 - lo2 > 1:
    mid = (lo2 + hi2) // 2
    if shared(mid):
        hi2 = mid
    else:
        lo2 = mid
print("共有される最初の値 :", hi2)
print("測定された範囲     :", hi2, "..", lo)
```

測定結果 (CPython 3.13.3 / Windows): 共有範囲 `-5 .. 256`、262 個のオブジェクト。
繰り返すが、これは **測定値**であって規格ではない。

## 3. 実行方法によって答えが変わる

同じ 2 行なのに結果が違う。実測:

| 実行方法 | `a = 257; b = 257` の後の `a is b` |
|---|---|
| スクリプトファイル | `True` |
| `python -c` | `True` |
| 標準入力に流し込む | `True` |
| `exec()` に 1 つの文字列で | `True` |
| `exec()` に 3 つの文字列で | `False` |
| `compile()` を別々に 2 回 | `False` |
| 対話型インタプリタ (1 行ずつ) | `False` |
| 実行時に作った値 `make(257)` | `False` |

教訓: **同じコンパイル単位の中の同じリテラルは 1 つのオブジェクトにまとめられる。**
対話型で確かめた結果とスクリプトの挙動は食い違い得る。

## 4. 危険なパターンの検出

### 4-1. 標準ライブラリだけで — コンパイラの警告をエラーにする

```bash
# リテラルと is を比べるとインタプリタが SyntaxWarning を出す
python -W error::SyntaxWarning -c "import py_compile,sys; py_compile.compile(sys.argv[1], cfile=None, doraise=True)" target.py
```

- 捕まるもの: `x is 200`, `x is 'admin'`, `x is ()`
- **捕まらないもの**: `x is CONST`, `flag is True`, `a is b`
- サードパーティ依存なしでビルド段階を失敗させられる

### 4-2. `ast` で自分で走査する (`is_lint.py`)

```python
#!/usr/bin/env python3
"""危険な is の使用を探す。見つかったら終了コード 1。"""
import ast, os, sys

SAFE = {"None", "True", "False", "Ellipsis", "NotImplemented"}

def module_consts(tree):
    out = {}
    for stmt in tree.body:
        if isinstance(stmt, ast.Assign) and isinstance(stmt.value, ast.Constant):
            v = stmt.value.value
            if isinstance(v, (int, float, str, bytes)) and not isinstance(v, bool):
                for t in stmt.targets:
                    if isinstance(t, ast.Name):
                        out[t.id] = v
    return out

class Checker(ast.NodeVisitor):
    def __init__(self, consts):
        self.consts, self.hits = consts, []

    def classify(self, node):
        if isinstance(node, ast.Constant):
            if node.value is None or isinstance(node.value, bool):
                return None
            return "LITERAL", "%s リテラル %r" % (type(node.value).__name__, node.value)
        if isinstance(node, (ast.Tuple, ast.List, ast.Dict, ast.Set)):
            return "LITERAL", "表示式リテラル"
        if isinstance(node, ast.JoinedStr):
            return "LITERAL", "f-string"
        if isinstance(node, ast.BinOp):
            return "EXPR", "演算結果"
        if isinstance(node, ast.Call):
            fn = getattr(node.func, "id", None)
            if fn in ("int", "float", "str", "bytes", "tuple", "list"):
                return "EXPR", fn + "() の結果"
            return None
        if isinstance(node, ast.Name):
            if node.id in SAFE:
                return None
            if node.id in self.consts:
                return "CONSTNAME", "リテラルに束縛された名前 %r" % (self.consts[node.id],)
        return None

    def visit_Compare(self, node):
        for op, right in zip(node.ops, node.comparators):
            if not isinstance(op, (ast.Is, ast.IsNot)):
                continue
            for side in (node.left, right):
                got = self.classify(side)
                if got:
                    self.hits.append((node.lineno, got[0], got[1]))
                if isinstance(side, ast.Constant) and isinstance(side.value, bool):
                    self.hits.append((node.lineno, "BOOLSINGLETON",
                                      "is %r ではなく真偽検査か == を使う" % side.value))
        self.generic_visit(node)

def scan(path):
    src = open(path, encoding="utf-8").read()
    tree = ast.parse(src, filename=path)
    ck = Checker(module_consts(tree))
    ck.visit(tree)
    return sorted(set(ck.hits))

def main(root):
    total = 0
    for dirpath, dirnames, filenames in os.walk(root):
        dirnames[:] = [d for d in dirnames
                       if d not in ("__pycache__", ".git", ".venv", "node_modules")]
        for fn in sorted(filenames):
            if not fn.endswith(".py"):
                continue
            p = os.path.join(dirpath, fn)
            try:
                hits = scan(p)
            except SyntaxError as exc:
                print("%s: パース失敗 %s" % (p, exc))
                continue
            for lineno, kind, detail in hits:
                print("%s:%d: %s %s" % (p, lineno, kind, detail))
                total += 1
    print("合計 %d 件" % total)
    return 1 if total else 0

if __name__ == "__main__":
    sys.exit(main(sys.argv[1] if len(sys.argv) > 1 else "."))
```

検出の種類:

| 表示 | 意味 | 対処 |
|---|---|---|
| `LITERAL` | リテラルとの `is` 比較 | 直ちに `==` に置き換える |
| `EXPR` | 演算・変換結果との `is` 比較 | 直ちに `==` に置き換える |
| `CONSTNAME` | 数値・文字列定数の名前との `is` 比較 | 値の比較なら `==`、シングルトン意図なら `object()` センチネルに |
| `BOOLSINGLETON` | `is True` / `is False` | 真偽検査か `==` に。意図的ならコメントを |

### 4-3. サードパーティ製ツールが使えるなら

- `flake8` 系: `F632` (リテラルとの is 比較)、`E712` (`== True` の比較)
- `pylint`: `literal-comparison`, `singleton-comparison`
- `ruff`: `F632`, `E711`, `E712`
- この環境にはどれも入っていなかったため 4-1・4-2 で代替した

## 5. 真偽値と整数 — 重なるところ

| 式 | 結果 | 備考 |
|---|---|---|
| `issubclass(bool, int)` | `True` | bool は int のサブクラス |
| `True == 1` | `True` | 値が同じ |
| `True is 1` | `False` | 別のオブジェクト |
| `hash(True) == hash(1)` | `True` | 辞書で同じスロットに入る |
| `{1: 'a', True: 'b', 1.0: 'c'}` | `{1: 'c'}` | **先に入れたキーが残り、値だけ上書きされる** |
| `{1, True, 1.0}` | `{1}` | 集合も同様 |
| `sum([True, True, False])` | `2` | 整数として足される |
| `type(True) is bool` | `True` | 型判定はこれで |
| `isinstance(True, int)` | `True` | int 検査では真偽値を除外できない |

## 6. チェックリスト

- [ ] 値の比較に `is` を使っている箇所がない (`is_lint.py` を通過)
- [ ] `-W error::SyntaxWarning` を CI に入れた
- [ ] `x == None` を `x is None` に直した
- [ ] `x is True` は「ちょうど True オブジェクト」を意味する場所だけに残し、コメントを付けた
- [ ] 「値がない」の判定に `if not x:` ではなくセンチネル (`object()`) を使った
- [ ] `isinstance(x, int)` を使っている箇所で真偽値が通っても問題ないか確認した
- [ ] 辞書・集合のキーに `0/False`、`1/True` を混ぜていない
- [ ] テストがリテラルだけを入れていない。**パース・シリアライズ・ソケットを経た値**でも検証する
- [ ] `is` の結果がキャッシュ範囲に依存すると書いたコメントや文書がない
- [ ] `id()` の値を保存したりプロセス間で比較したりしていない
- [ ] Enum やセンチネルのような **意図的なシングルトン**にだけ `is` を使う
- [ ] レビュー規約に「`is` はシングルトン専用」と明記した

## 7. やってはいけないこと

- キャッシュ範囲の数値を **言語仕様のように**文書に書くこと — 実装の詳細である
- 対話型で確認した `is` の結果をスクリプトの挙動の根拠にすること — コンパイル単位が違う
- `id()` が同じだから同じオブジェクトだと結論づけること — 生存期間が重ならない 2 つのオブジェクトは同じ `id()` を持ち得る
- `is True` で「真かどうか」を問うこと — 真である値のほとんどが弾かれる
- `isinstance(x, int)` で真偽値を除こうとすること — 通過してしまう
- テストが緑だからと `is` 比較をそのままにすること — **小さい値でたまたま通っただけかもしれない**
