boring — TOML 설정 기반 경량 SSH 터널 매니저 실무 분석

매번 긴 ssh -L 명령을 치는 번거로움을 선언형 TOML로 끝내는 도구 — 포워딩 3종의 차이와 autossh 비교까지

2026-06-25 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: SSH 터널, 왜 아직도 불편한가

SSH 포트 포워딩은 인프라 엔지니어와 개발자 모두에게 일상적인 도구다. 방화벽 뒤의 DB에 접근하거나, 개발 PC의 로컬 서비스를 원격에 노출하거나, SSH 서버를 SOCKS5 프록시로 쓰는 것은 자주 있는 일이다. 그런데 2026년 기준으로도 이 작업의 UX는 놀랍도록 원시적이다. ssh -L 5432:db-server:5432 -N -f user@bastion 같은 명령을 매번 타이핑하거나, 셸 히스토리를 뒤적이거나, 별칭을 .bashrc에 박아 두는 것이 전부다.

문제는 이뿐만이 아니다. 터널이 여러 개면 관리는 더 복잡해진다. 어떤 터널이 살아 있는지 확인하기 위해 ps aux | grep ssh를 쳐야 하고, 재연결이 필요하면 또 명령을 찾아 실행해야 한다. 팀 환경이라면 동료에게 "이 터널은 이렇게 열어"를 텍스트로 전달하는 일도 생긴다.

boring은 이 불편함을 정면으로 겨냥한다. GitHub의 alebeck이 개발한 이 도구는 "그냥 동작하는 단순한 CLI SSH 터널 매니저"를 표방한다. 핵심 아이디어는 하나다. 터널 정의를 TOML 파일에 선언해 두고, 명령 한 줄로 원하는 터널을 열거나 닫는다. 이 글은 그 아이디어가 실제로 어떤 문제를 얼마나 잘 해결하는지, 그리고 기존 방식과 무엇이 다른지 실무 시각으로 분석한다.

1. boring이란 — Go로 만든 경량 SSH 터널 데몬

boring은 Go 언어(코드베이스의 95.5%)로 작성된 MIT 라이선스 오픈소스 CLI 도구다. 2026년 6월 기준 v0.16.0이며, GitHub에서 1,600개 이상의 스타를 받았고 266개의 커밋과 Coveralls 연동 테스트 커버리지를 유지하는 활발한 프로젝트다.

아키텍처는 단순하다. boring 명령이 데몬(boringd)을 실행하고, 이후 open/close 등의 서브커맨드는 Unix 소켓($BORING_SOCK, 기본 /tmp/boringd.sock)을 통해 데몬에 명령을 전달한다. 데몬이 실제 SSH 연결과 재연결을 담당하고, CLI는 그 프론트엔드다.

1.1 설치

macOS라면 brew install boring 한 줄로 끝난다. Linux와 Windows는 GitHub 릴리스 페이지에서 바이너리를 받아 $PATH에 두면 된다. 소스 빌드는 make로 가능하고, Windows는 별도의 build_win.bat을 쓴다(Go 1.25 이상 필요). Homebrew 설치 시 bash/zsh/fish 셸 자동완성도 함께 구성된다.

1.2 설정 파일 위치

설정은 ~/.boring.toml(macOS/Windows) 또는 $XDG_CONFIG_HOME/boring/.boring.toml(Linux)에 둔다. $BORING_CONFIG 환경변수로 경로를 오버라이드할 수 있어, 여러 환경 설정을 파일 단위로 교체하는 운용도 가능하다.

2. TOML 선언형 설정의 실체

boring의 차별점은 터널 정의가 "명령어 기억"이 아니라 "파일 선언"이라는 데 있다. TOML을 선택한 이유는 명확하다. YAML보다 들여쓰기 오류가 없고, JSON보다 가독성이 높으며, 주석을 지원한다.

2.1 기본 구조

# ~/.boring.toml

[[tunnels]]
name    = "dev-db"
local   = "5432"
remote  = "localhost:5432"
host    = "bastion"
mode    = "local"

[[tunnels]]
name    = "prod-redis"
local   = "6379"
remote  = "cache-01:6379"
host    = "prod-bastion"
user    = "deploy"
identity = "~/.ssh/id_prod"
group   = "prod"

[[tunnels]]
name    = "socks-proxy"
local   = "1080"
host    = "jump-server"
mode    = "socks"
keep_alive = 60

각 터널은 [[tunnels]] 배열 항목으로 정의한다. 필드는 직관적이다. name은 참조용 식별자, local은 바인딩할 로컬 주소(포트만 써도 됨), remote는 원격 목적지, host는 SSH 접속 대상, mode는 터널 종류다.

2.2 주요 필드 정리

필드필수기본값설명
name필수—터널 식별자 (CLI에서 참조)
local필수*—로컬 바인딩 주소/포트 또는 Unix 소켓 경로
remote필수*—원격 목적지 주소/포트 또는 Unix 소켓 경로
host필수—SSH 접속 대상 (ssh_config 별칭 사용 가능)
mode선택locallocal / remote / socks / socks-remote
user선택ssh_config → $USERSSH 사용자 이름
identity선택기본 키 파일SSH 개인키 경로
port선택22SSH 포트
group선택—그룹명 (그룹 단위 일괄 제어용)
keep_alive선택120킵얼라이브 간격(초)

(*) mode에 따라 일부 필드 생략 가능. socks 모드는 remote 불필요.

2.3 선언형 설정의 실질 이점

이 방식은 단순히 "명령어를 파일로 옮겼다"는 것 이상이다. 첫째, 설정이 파일로 존재하므로 Git으로 버전 관리할 수 있다. 어느 터널이 언제 추가됐는지 이력이 남는다. 둘째, 팀 공유가 쉽다. "이 터널 설정 복사해서 ~/.boring.toml에 붙여" 한 줄로 공유된다. 셋째, 실행 시점에 타이핑 오류가 없다. 설정 파일을 한 번 검증하면 이후엔 boring open dev-db만 누른다.

3. SSH 포워딩 3종의 차이와 실무 쓰임

boring이 지원하는 포워딩 타입을 정확히 이해해야 TOML을 제대로 쓸 수 있다. 이 세 가지는 SSH의 -L/-R/-D 플래그에 대응하지만, boring에서는 mode 필드 하나로 선택한다.

3.1 로컬 포워딩 (mode = "local", SSH -L)

가장 흔한 패턴이다. 내 PC의 특정 포트로 들어오는 트래픽을 SSH 서버를 경유해 지정한 목적지로 전달한다. 트래픽 방향은 내 PC → SSH 서버 → 목적지다.

실무 시나리오: 회사 내부 네트워크에만 열려 있는 PostgreSQL(192.168.1.100:5432)에 로컬 DB 클라이언트로 접근하고 싶다. local = "5432", remote = "192.168.1.100:5432", host = "bastion"으로 설정하면 localhost:5432가 곧장 DB로 연결된다.

[[tunnels]]
name   = "internal-db"
local  = "5432"
remote = "192.168.1.100:5432"
host   = "bastion"
mode   = "local"

등가 ssh 명령: ssh -L 5432:192.168.1.100:5432 -N bastion

3.2 리모트 포워딩 (mode = "remote", SSH -R)

방향이 반대다. 원격 서버의 포트로 들어오는 트래픽을 내 로컬로 보낸다. 원격 서버 → SSH 터널 → 내 PC다.

실무 시나리오: 개발 PC에서 돌리는 웹 앱(localhost:3000)을 사내 서버의 퍼블릭 포트로 잠시 노출해 QA 팀에게 URL을 주고 싶다. local = "3000", remote = "0.0.0.0:9000", host = "qa-server", mode = "remote"로 설정하면 qa-server:9000으로 접근하는 트래픽이 내 로컬 앱으로 도달한다.

[[tunnels]]
name   = "expose-dev"
local  = "3000"
remote = "0.0.0.0:9000"
host   = "qa-server"
mode   = "remote"

ngrok의 개념과 유사하지만, 이미 접근 가능한 SSH 서버를 그대로 활용한다는 점이 다르다. 추가 서비스 가입이 필요 없다.

3.3 다이나믹 포워딩 / SOCKS5 (mode = "socks", SSH -D)

로컬/리모트 포워딩은 포트 하나를 목적지 하나에 매핑한다. 반면 다이나믹 포워딩은 SSH 서버를 SOCKS5 프록시 서버로 만든다. 브라우저나 앱이 이 SOCKS5 프록시를 통해 통신하면, 트래픽은 SSH 서버를 경유해 나간다. 목적지 주소/포트는 사전에 지정할 필요가 없다.

실무 시나리오: 공용 Wi-Fi에서 회사 내부 여러 서비스에 접근해야 할 때, 또는 특정 국가 IP로 보이고 싶을 때. SOCKS5 터널 하나로 브라우저 트래픽 전체를 SSH 서버 측에서 내보낼 수 있다.

[[tunnels]]
name  = "proxy"
local = "1080"
host  = "remote-server"
mode  = "socks"

등가 ssh 명령: ssh -D 1080 -N remote-server. 브라우저에서 SOCKS5 프록시를 localhost:1080으로 설정하면 된다.

3.4 Unix 소켓 지원

boring은 local과 remote 필드에 host:port가 아닌 Unix 소켓 경로도 받는다. Docker 소켓이나 PostgreSQL Unix 소켓처럼 소켓 기반으로 통신하는 서비스를 SSH 터널로 연결할 때 유용하다.

[[tunnels]]
name   = "docker-remote"
local  = "/tmp/remote-docker.sock"
remote = "/var/run/docker.sock"
host   = "remote-host"

이렇게 하면 DOCKER_HOST=unix:///tmp/remote-docker.sock docker ps 처럼 원격 Docker 데몬을 로컬 CLI로 제어할 수 있다.

4. CLI 사용법 — open/close/list

boring의 CLI는 의도적으로 단순하게 설계됐다. 자주 쓰는 명령은 몇 개 되지 않는다.

명령단축설명
boring open [이름]o지정 터널 시작. -a면 전체, -g 그룹이면 그룹 일괄 시작
boring close [이름]c지정 터널 종료. -a면 전체 종료
boring listl터널 목록과 현재 상태(열림/닫힘) 조회. -g 그룹으로 필터 가능
boring edite설정 파일을 $EDITOR로 바로 열기
boring versionv버전 정보 출력

그룹 기능이 실무에서 특히 유용하다. group = "dev"로 묶인 터널들을 boring open -g dev 한 줄로 전부 시작할 수 있다. 개발 환경(DB + Redis + 내부 API)과 프로덕션 환경을 그룹으로 분리해 두면, 환경 전환이 두 명령으로 끝난다.

5. autossh와의 비교 — 무엇이 다른가

SSH 터널 자동화 도구로 가장 널리 쓰이는 것은 여전히 autossh다. 둘의 철학 차이를 짚어 보자.

5.1 autossh의 방식

autossh는 SSH 프로세스를 감시하다가 죽으면 재시작하는 단일 목적 도구다. 사용법은 ssh 명령에 autossh를 씌우는 것으로, autossh -M 0 -L 5432:db:5432 -N bastion처럼 쓴다. 여기서 -M 0은 자체 모니터링 포트를 끄고 SSH 내장 킵얼라이브에 맡기는 옵션이다.

여러 터널을 상시 유지하려면 보통 systemd 서비스 유닛을 터널마다 만들고, ExecStart에 autossh 명령을 넣고, Restart=always를 설정한다. 이는 강력하지만 파일이 많아지고, 새 터널을 추가할 때마다 서비스 유닛을 새로 만들고 systemctl daemon-reload와 systemctl enable을 해야 한다.

5.2 boring의 방식

boring은 설정을 TOML 파일 하나로 통합하고, 자체 데몬이 모든 터널의 재연결을 관리한다. 새 터널을 추가하려면 TOML에 [[tunnels]] 블록을 추가하고 저장하면 끝이다. 서비스 유닛 작성, reload, enable이 없다. boring open -a로 전체를 시작하거나, 원하는 터널만 열고 닫을 수 있다.

5.3 각각 어디에 맞나

autossh + systemd 조합은 서버나 CI/CD 환경에서 터널을 시스템 서비스로 상시 유지해야 할 때 여전히 강력하다. 재부팅 후 자동 복구, 다른 서비스와의 의존 관계 표현이 필요한 운영 환경에 맞는 선택이다. 반면 boring은 개인 워크스테이션에서 필요할 때 열고 닫는 터널 관리에 훨씬 쾌적하다. 개발자가 여러 환경을 오가며 터널을 스위칭하는 시나리오에서 마찰이 훨씬 적다.

6. ssh_config와의 통합

boring은 독자적인 SSH 스택을 구현하는 것이 아니라 시스템의 ssh_config를 그대로 읽는다. host 필드에 ~/.ssh/config에 정의된 Host 별칭을 쓸 수 있다. ProxyJump, ProxyCommand, IdentityFile 등 ssh_config에서 이미 설정한 것들이 boring 터널에도 그대로 적용된다는 뜻이다.

이는 큰 장점이다. ssh_config에 이미 복잡한 점프 호스트 체인이나 인증서 기반 인증을 설정해 뒀다면, boring TOML에는 그 별칭만 적으면 된다. 인증 로직을 두 곳에서 관리하지 않아도 된다. ssh-agent와도 호환돼, 에이전트에 키가 올려져 있으면 별도 passphrase 입력 없이 터널이 열린다.

7. 실무 구성 예시 — 개발자 워크스테이션

2026년 기준 개발자가 실제로 쓸 만한 boring 설정 예를 보여 준다.

# ~/.boring.toml

# 개발 환경 그룹
[[tunnels]]
name   = "dev-pg"
local  = "5432"
remote = "pg-dev.internal:5432"
host   = "dev-bastion"
group  = "dev"

[[tunnels]]
name   = "dev-redis"
local  = "6379"
remote = "redis-dev.internal:6379"
host   = "dev-bastion"
group  = "dev"

[[tunnels]]
name   = "dev-api"
local  = "8080"
remote = "api-dev.internal:8080"
host   = "dev-bastion"
group  = "dev"

# 프로덕션 모니터링 (읽기 전용 목적)
[[tunnels]]
name     = "prod-pg-ro"
local    = "15432"
remote   = "pg-prod.internal:5432"
host     = "prod-bastion"
user     = "readonly"
identity = "~/.ssh/id_prod_ro"
group    = "prod-readonly"

# 범용 SOCKS5 프록시
[[tunnels]]
name       = "office-proxy"
local      = "1080"
host       = "office-gateway"
mode       = "socks"
keep_alive = 30

이 설정으로 가능한 워크플로: 아침 출근(재택)에 boring open -g dev 한 줄이면 개발 환경 DB·Redis·API 터널이 전부 열린다. 퇴근 전 boring close -a로 전부 닫는다. 프로덕션 작업 시 boring open prod-pg-ro만 열고, 완료 후 boring close prod-pg-ro. 이 흐름에서 40자짜리 ssh 명령을 기억할 필요가 없다.

8. 한계와 주의점

boring이 모든 상황의 해답은 아니다. 정직하게 짚어 보자.

8.1 데몬 생명주기 관리

boring은 자체 데몬을 /tmp/boringd.sock 기반으로 실행한다. 이 데몬의 시작/종료는 사용자 수동 또는 로그인 스크립트에 의존한다. autossh + systemd처럼 OS 부팅 시 자동 시작하려면 별도의 런처(launchd, systemd 사용자 서비스 등)를 구성해야 한다. 서버 환경에서 상시 유지형 터널에 쓰기엔 이 부분이 아직 불편하다.

8.2 단일 사용자 도구

boring은 개인 설정 파일 기반으로 설계됐다. 팀 단위로 중앙 관리되는 터널 정책, 권한 제어, 감사 로그 같은 요구사항에는 맞지 않는다. 그런 수요라면 Vault SSH나 다른 인프라 레벨 솔루션이 맞다.

8.3 socks-remote 모드의 쓰임새

문서에 언급된 socks-remote 모드(원격 서버에 SOCKS5 프록시 리스너를 여는 모드)는 실무 쓰임새가 좁다. 일반적인 시나리오에서는 local이나 socks로 충분하다. 혼동하지 않도록 필요할 때만 쓰는 것이 좋다.

9. 결론 — 선언형 설정이 가져오는 마찰의 감소

boring은 거창한 혁신이 아니다. SSH 터널을 여는 방법 자체를 바꾸지는 않는다. 그러나 그 관리 방식을 "명령어를 기억하고 타이핑"에서 "파일을 선언하고 이름을 호출"로 바꾼다. 이 차이가 일상 업무에서 축적되는 마찰의 양은 생각보다 크다.

2026년 6월 기준으로 boring은 v0.16.0까지 활발히 개발되고 있고, 테스트 커버리지와 크로스플랫폼 지원이 안정적이다. 개인 워크스테이션에서 여러 SSH 터널을 관리하는 개발자·인프라 엔지니어라면 한 번 써 볼 가치가 충분하다.

autossh + systemd가 여전히 서버 상시 운영에 강점이 있지만, boring은 그 반대 극단 — 개발자가 하루 수차례 컨텍스트를 전환하며 필요한 터널을 빠르게 열고 닫는 워크플로 — 에서 더 나은 경험을 준다. 해결하려는 문제의 레이어가 다를 뿐, 선택은 시나리오에 따라 달라진다.
