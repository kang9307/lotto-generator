Why WARN Becomes a Landfill - Agreeing on a Log Level Convention

A level is not a severity rating. It is a signal you send to whoever reads it

2026-08-01 Development/Infrastructure

Opening: thirty thousand warning lines a day, and nobody reads them

Every service arrives at the same place eventually. Put a WARN filter on the dashboard and the screen scrolls forever, and nobody looks at it. Ask whether a warning ought to be looked at and everyone says yes, but nobody actually opens it. Then the one line that really did need looking at slides past inside that stream.

The usual prescription at this point is to log less. That is the wrong target. The problem is not the volume, it is that the level stopped meaning anything. If WARN does not mean a human must touch this, then the WARN filter filters nothing, and there is no longer anywhere to hang an alert.

The claim of this article fits in one sentence. A level is not a rating of how bad something is. It is a signal to whoever reads it. ERROR has to mean somebody needs to look now before you can attach a pager to it. If WARN means nothing, the filter is meaningless. That is why a log level convention is not a matter of coding taste but a piece of alerting design.

Everything below was checked by actually running a logger. The same code was executed at different thresholds to see which lines vanish, the internal numbers behind the level names were printed, and the claim that a filtered log is free was measured.

Environment. Every output below was produced on Windows 10 Pro (10.0.19045). The tools are the logging module from the standard library of Python 3.13.3 and the standard library of Node.js v22.16.0. No dedicated logging library is installed on this machine. Two widely used Node packages were required and both failed to resolve, so the Node side was checked using only console and util.debuglog. No tool was described as available when it was not.

Every script was saved to a file before running. Passing code through shell arguments or heredocs quietly deforms it. All logger names and messages are invented for a fictional order and payment service.

What this article does not cover. Which fields a log record should carry, where personal data gets masked, and how an identifier is threaded across requests are each their own subject. This article stays on the single point of levels.

1. A level is not importance, it is a cutoff

Start with what a level actually does. The same eight calls were run four times, changing nothing but the threshold.

python 3.13.3 / win32
--- 1-1. same eight calls, four thresholds ---

threshold = DEBUG     -> 8 of 8 lines survive
   DEBUG    cache miss key=order:8821
   DEBUG    sql took 12ms rows=3
   INFO     order 8821 accepted
   INFO     payment captured amount=19900
   WARNING  retry 1/3 upstream=billing
   WARNING  config key TIMEOUT missing, using default
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: (none)

threshold = INFO      -> 6 of 8 lines survive
   INFO     order 8821 accepted
   INFO     payment captured amount=19900
   WARNING  retry 1/3 upstream=billing
   WARNING  config key TIMEOUT missing, using default
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: DEBUG

threshold = WARNING   -> 4 of 8 lines survive
   WARNING  retry 1/3 upstream=billing
   WARNING  config key TIMEOUT missing, using default
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: DEBUG, INFO

threshold = ERROR     -> 2 of 8 lines survive
   ERROR    payment capture failed order=8821
   CRITICAL database connection pool exhausted
   dropped entirely: DEBUG, INFO, WARNING

Not one character of the code changed. The only thing that moved was the threshold. Yet each step up removes one more level entirely. The first conclusion follows from that.

  • A level is not a label recording how important a line is
  • A level decides at which threshold this line disappears. That is the whole mechanism
  • So choosing a level is choosing who gets to see this line
  • When two people record the same fact at different levels, they have sent that fact to two different audiences

Taking a single line and marking whether it is visible at each threshold makes it plainer.

--- 1-2. the same line, seen or not seen, by threshold ---
threshold  visible    note
--------------------------------------------------------------
DEBUG      True       written out
INFO       True       written out
WARNING    True       written out
ERROR      False      the call still ran
CRITICAL   False      the call still ran

Watch the right-hand column. Not visible does not mean not executed. The call happened exactly as written and only the result was discarded. That fact leads straight into the cost section later.

2. Levels are just integers - what a custom level costs

What a level really is turns out to be simple. Here are the internal numbers, printed as they are.

python 3.13.3 / win32
--- 2-1. the levels are just integers ---
name       value
------------------------
NOTSET     0
DEBUG      10
INFO       20
WARNING    30
ERROR      40
CRITICAL   50

WARNING is WARN  : True
gap between them : 10

--- 2-2. wedging a custom level in between ---
   TRACE    5    entered handler
   DEBUG    10   cache miss
   INFO     20   order accepted
   NOTICE   25   deploy finished, build 4412
   WARNING  30   retry 1/3
   ERROR    40   capture failed

The gap of ten between levels is not an accident. It is empty so that you can wedge your own levels in. Registering TRACE at 5 and NOTICE at 25 slotted them in exactly where the numbers said they should go.

There is a price attached, though. Turning an unregistered number back into a name looks like this.

--- 2-3. what a custom level costs you ---
threshold=INFO(20), NOTICE(25) and INFO(20) both pass:
   NOTICE   deploy finished
   INFO     order accepted

an unknown name reads back as a placeholder, not an error:
   getLevelName(25)  -> NOTICE
   getLevelName(23)  -> Level 23
   getLevelName(999) -> Level 999

a receiver that only knows the five names has to guess what 23 means.
the number sorts fine. the meaning does not travel.

The last two lines are the point. The number sorts. The meaning does not travel. A collector receiving 23 can tell it outranks INFO and nothing more. Worse, nothing errors out. It quietly flows on as a placeholder reading Level 23.

  • A custom level has a name only inside your own process
  • If collection, search and alerting do not know that number, those lines become a grey zone that can be neither filtered nor alerted on
  • The widely cited standard severity definition itself states that severities are very subjective and that a receiver should not assume all originators share the same definition
  • So the practical advice is short. Either avoid custom levels, or make sure the collector configuration knows the number
  • The urge to add a level is usually a sign that you need a field, not a level. A deploy event belongs in a category field on an INFO record, not in a new level

3. There are two gates - what the logger dropped is gone

Here is the misunderstanding that comes up most often. There is not one threshold. There is one on the logger and one on each sink. Both were combined and run.

python 3.13.3 / win32
--- 9-1. there are two gates, not one ---
4 calls each time: DEBUG, INFO, WARNING, ERROR

logger=DEBUG    console_h=NOTSET   audit_h=NOTSET   -> console 4, audit 4
logger=DEBUG    console_h=INFO     audit_h=ERROR    -> console 3, audit 1
logger=WARNING  console_h=DEBUG    audit_h=DEBUG    -> console 2, audit 2
logger=ERROR    console_h=DEBUG    audit_h=DEBUG    -> console 1, audit 1

--- 9-2. the practical shape: one lenient logger, several picky sinks ---
logger=DEBUG    console_h=INFO     audit_h=ERROR    -> console 3, audit 1

--- 9-3. the blunt instrument, and why it surprises people ---
logging.disable(WARNING) is active, logger level is DEBUG:
   ERROR line at ERROR
   -> 1 of 4 survived. it is a process-wide floor that outranks every logger.
   after disable(NOTSET): 4 of 4 survive again

Look at the third and fourth rows. The sinks asked for DEBUG and it made no difference, because the logger had already cut those lines. The logger gate runs first, and a sink can only narrow what already came through.

  • Most reports of setting the sink to DEBUG and still seeing nothing are exactly this. Nobody looked at the logger
  • The practical arrangement is a permissive logger and narrow sinks
  • Putting the console a human tails at INFO and the pager or ticket queue at ERROR means one emitted line reaches two audiences differently
  • There is also a process-wide floor. It outranks logger configuration, so even with the logger at DEBUG only 1 of 4 lines survived. If a library sets that switch, no amount of fixing your own config brings the logs back

4. How WARN swells up

Back to the symptom from the opening. A day in a small service was modelled and aggregated by call site.

--- 3-2. inside WARNING, sorted by volume ---

This table is the whole story of how WARN becomes a landfill. Read it in order.

  • WARN is 49.2 percent of everything. In a log that is half warnings, a warning means nothing
  • The top three call sites produce 74.2 percent of WARN. Those thirty thousand lines are not many kinds of warning, they are the same three lines repeated
  • Those three are a deprecated field being used, a cache miss, and a missing optional header. None of them is something a human acts on
  • The lines that genuinely need a person are the bottom three, 77 a day. That is one line in 390
  • Crucially, no bad engineer produced this. Every call site was reasonable when it was written. The judgement that this is not quite normal, so WARN, simply accumulated nine times

What alerting on this stream would do was calculated too.

--- 3-3. what an alert on WARNING would do ---
  a  1-minute window carries     20.9 WARNING lines
  a  5-minute window carries    104.4 WARNING lines
  a 60-minute window carries   1252.4 WARNING lines
  an alert that pages on 'any WARNING' pages every window, forever.
  an alert that pages above a threshold has to sit above 20/min noise,
  which is higher than the 3 lines/day that actually mattered.

--- 3-4. same stream after reclassifying by 'must a human act now' ---
level          before      after
--------------------------------
ERROR              13         16
WARNING         30057         74
INFO            31000      48480
DEBUG               0      12500

WARNING/day : 30057 -> 74
ERROR/day   : 13 -> 16
now 'any WARNING today' is a 74-line list a person can read.
and ERROR stays small enough to page on.

Here is where the thesis becomes visible. Whether you can alert at all is determined by the quality of your level definitions. No threshold works on a channel carrying 20.9 lines a minute. What actually mattered was 3 lines a day, and the noise floor sits far above it.

Look at the numbers after reclassification. Total volume is identical at 61,070 lines. Only WARN shrank, while INFO and DEBUG grew to absorb it. The claim that the goal is not fewer logs but readable ERROR and WARN is sitting right there in the table.

5. The decision rule - must a human act now

So what actually separates them. A rule was built with the Node standard library and applied to real call sites.

node v22.16.0 / win32
installed logging packages on this machine: none
  require("winston") -> MODULE_NOT_FOUND
  require("pino")    -> MODULE_NOT_FOUND

--- 4-1. console has level-looking names but no threshold ---
method      stream    dropped when quiet
----------------------------------------------
console.log     stdout    never
console.debug   stdout    never
console.info    stdout    never
console.warn    stderr    never
console.error   stderr    never

there is no setLevel and no threshold. nothing is ever dropped.
a debug line in a hot loop is written in production exactly as
often as on a laptop. the four names only pick a stream.

--- 4-2. the stdlib does ship one gated channel: util.debuglog ---
NODE_DEBUG              : ""
payment channel enabled : false
db channel enabled      : false
(no channel output above: both are off)

What this output shows matters. Having names that look like levels is not the same as having levels. The four default console functions in this runtime have no threshold, and the only thing they decide is which output stream you land on. Discarding standard output while running leaves only warn and error behind. In other words, code that uses only these functions writes every DEBUG line to disk in production, without exception.

The standard library of this runtime does ship one channel that can be turned on and off. It emits only when the channel name is named in an environment variable, and code can ask whether it is on. Naming only the payment channel and running it produced true for payment, false for the database channel, and output for the payment line alone. This is the simplest form of the per-module lowering discussed later.

5.1 Change the question and the answer narrows to one

Level arguments never end because the question is wrong. Asking how serious this is makes the answer a matter of taste. The question has to change.

When this line appears, what does a human do, and when?

There are only four answers to that question, and those four answers are the four levels.

LevelOne-sentence definitionWhat the reader doesTimeframeAlerting
ERRORThe system failed at its job and we have to fix itLook nowEven at 3 a.m.Page
WARNA human must touch this, but not tonightHandle in work hoursThis weekDaily digest
INFONobody acts. It records what the system didRead only when tracing-None
DEBUGUseful only while reproducing a bugTurn on during repro-None

Notice that the definitions contain no adjectives at all. Words like serious, critical and important sit at different places for different people, and they are what leaves a convention stranded in a document. Whether it wakes someone at 3 a.m., on the other hand, gets the same answer from two people.

5.2 Applying it to real call sites

Two of those nine always start an argument on a team. Those two lines are the entire route by which WARN becomes a landfill.

The single most expensive habit. Reaching for WARN because it is not quite normal is what built the thirty thousand lines above. There is a firm replacement rule. If you are unsure, it is INFO. WARN has to stay a narrow drawer holding only what a human will touch this week, and only while it stays narrow is it worth opening.

6. Where to log a caught exception

Exception handling is where a level convention collapses most often. The common pattern of catching, logging and re-raising at every layer was run as written.

python 3.13.3 / win32
--- 5-1. log-and-rethrow at every layer ---
   ERROR    app.db         db call failed: connect timeout to billing-db after 3000ms
   ERROR    app.service    could not load order: connect timeout to billing-db after 3000ms
   ERROR    app.api        request failed: connect timeout to billing-db after 3000ms
   -> 3 ERROR lines, 1 actual failure, 1 user-visible 500

--- 5-2. raise once, log once at the boundary that decides ---
   ERROR    app.api        request failed order=8821
   + 8 traceback lines attached to that single record
   -> 1 ERROR line, and it carries the full stack

--- 5-3. exception that was recovered from ---
   INFO     app.service    retry 1/3 after connect timeout
   INFO     app.service    retry 2/3 after connect timeout
   result: {'order': 8821}
   nothing failed for the user, so nothing is ERROR

--- 5-4. exception deliberately ignored ---
   5 lines at DEBUG (traceback included)
   visible only when someone turns DEBUG on for this module

The first block is the problem. One real failure left three ERROR lines. The user saw a single error. Counting ERRORs a day in this state gives three times the failure count, and any alert threshold placed on it inherits that multiplier as pure error.

The second block is the fix. The layers that re-raise log nothing at all, because raising is already how a layer tells its caller. Instead the one boundary that decided to give up logs once with a stack trace attached. The result is one ERROR line carrying eight lines of call stack. The line count fell to a third and the information went up.

SituationLevelWho logs itRationale
Recovered by retryINFOThe layer that recoveredNothing happened to the user
Swallowed, no impactDEBUGThe layer that swallowed itNeeded only during a repro
Re-raised to the callernobody-The raise itself is the message
Turned into a 500ERRORThe one boundary that gave upWe have to fix it
Turned into a 400INFOThat same boundaryThe caller was wrong
  • The habit of logging at every layer in case the cause is lost later is fully replaced by one stack trace
  • Logging retries at WARN is what produced the 4,200 lines above. If the recovery succeeded, nothing failed
  • An exception logged three times cannot be told apart afterwards from three separate incidents, especially without a per-request identifier
  • Logging a malformed client request as ERROR means traffic somebody else generates rings your pager. You have handed outsiders a button that pages you

7. Filtered out, but you already paid

Now to put a number on the earlier point that not visible is not the same as not executed. With the threshold at WARNING, 200,000 DEBUG calls were timed in five forms.

python 3.13.3 / win32
one run on one machine. treat the ratios, not the absolute numbers.

--- 6-1. cost of a DEBUG line that is thrown away (threshold=WARNING) ---
form                                  total sec    per call us   vs guard
--------------------------------------------------------------------------
f-string built up front                  0.8994          4.497
json.dumps built up front                0.8100          4.050
%-style args, lazy                       0.0416          0.208
isEnabledFor guard                       0.0226          0.113       1.0x
no logging call at all                   0.0081          0.040       0.4x

f-string form is 39.9x the guarded form
json form is     35.9x the guarded form
lazy %-args is   1.8x the guarded form

all five produced ZERO output lines. the threshold was WARNING throughout.

--- 6-2. where the money actually goes ---
building the string only        : 0.8064 sec  (4.032 us/call)
calling lg.debug('x') only      : 0.0373 sec  (0.187 us/call)
-> the call itself is cheap. the argument you built is not.

--- 6-3. at production volume ---
    1000 debug calls/sec -> eager    4.5 ms/sec of cpu, guarded   0.1 ms/sec
   20000 debug calls/sec -> eager   89.9 ms/sec of cpu, guarded   2.3 ms/sec
  and none of it reaches a file, because DEBUG is off.

--- 6-4. the same guard, when DEBUG is ON ---
threshold=DEBUG, 20000 lazy calls : 0.3750 sec (18.749 us/call)
bytes written                     : 2960000
-> once the line is kept, formatting happens anyway. lazy only helps when filtered.

These figures come from a single measurement on one machine. On a different machine, a different build, or under different load, the absolute values will move. Take the ratios, not the wall-clock times. Measured again, your environment should show roughly the same ordering.

Here is how to read it.

  • All five forms produced zero output lines. The threshold was WARNING, so every DEBUG call was cut
  • Yet building the string up front ran 39.9 times slower than checking the threshold first. What the filter discarded was the output, not the cost of building
  • Where the money goes is answered by 6-2. The logger call itself is cheap at 0.187 microseconds. Building the string to pass costs 4.032 microseconds. The expensive part is the argument, not the call
  • Passing the format string and the values separately, the lazy form costs 0.208 microseconds, over twenty times cheaper than building up front, because only surviving lines get assembled
  • At twenty thousand calls a second that gap becomes 89.9 milliseconds of CPU against 2.3. And not one character of it reaches a file
  • The last block restores the balance. Once a line passes the threshold, formatting happens anyway. Laziness pays only when the line is dropped, and turning DEBUG on pushes it to 18.749 microseconds a call

As practical rules that is three lines. Pass arguments lazily. Build heavy arguments like serialization only after checking the threshold. And turn DEBUG on knowing it is not free.

8. Changing levels without a redeploy

For a convention to actually hold, lowering a level has to be easy. Make it hard and people pre-emptively raise things to WARN in case they need them later, and that becomes the thirty thousand lines above. Logger names were made hierarchical and run.

python 3.13.3 / win32
--- 7-1. baseline: root of the tree at WARNING ---
shop=WARNING  -> 1 lines
   WARNING  shop.payment.gateway retry 1/3

--- 7-2. same process, one line changes the threshold ---
shop=INFO  -> 4 lines
   INFO     shop.db            pool size 8/20
   INFO     shop.payment       capture ok order=8821
   WARNING  shop.payment.gateway retry 1/3
   INFO     shop.web           200 GET /orders/8821 12ms

--- 7-3. turn up ONE module only, leave the rest alone ---
shop=WARNING, shop.payment=DEBUG  -> 4 lines
   DEBUG    shop.payment       building capture request amount=19900
   INFO     shop.payment       capture ok order=8821
   DEBUG    shop.payment.gateway http POST /v1/charges
   WARNING  shop.payment.gateway retry 1/3
   note shop.payment.gateway inherited DEBUG from its parent

Block 7-3 is the point. Only the payment module was lowered to DEBUG and nothing else was touched. Yet its gateway child came down with it. The next output explains why.

--- 7-4. effective level is resolved by walking up the name ---
logger                   own level    effective
--------------------------------------------------
shop                     WARNING      WARNING
shop.db                  DEBUG        DEBUG
shop.payment             NOTSET       WARNING
shop.payment.gateway     NOTSET       WARNING
shop.web                 NOTSET       WARNING
NOTSET means 'ask my parent'. that is why one name can steer a whole subtree.

--- 7-5. driving it from the environment, no redeploy ---
  LOG_LEVELS=shop=WARNING                       -> 1 lines
     WARNING  shop.payment.gateway retry 1/3

  LOG_LEVELS=shop=WARNING,shop.payment=DEBUG    -> 4 lines
     DEBUG    shop.payment       building capture request amount=19900
     INFO     shop.payment       capture ok order=8821
     DEBUG    shop.payment.gateway http POST /v1/charges
     WARNING  shop.payment.gateway retry 1/3

  LOG_LEVELS=shop=ERROR,shop.web=INFO           -> 1 lines
     INFO     shop.web           200 GET /orders/8821 12ms

--- 7-6. the safety rail: a raise-only window ---
  shop=DEBUG                         depth=0  allowed=False
  shop.payment=DEBUG                 depth=1  allowed=True
  shop.payment.gateway=DEBUG         depth=2  allowed=True
  • Leaving a child logger unset makes it delegate to its parent. That is what lets one parent name steer a whole subtree
  • Conversely, pinning a value on a child means changing the parent no longer moves that branch. Code that sets a level on every logger at startup blocks runtime adjustment entirely
  • Accepting a list of name=level pairs from an environment variable changes the filter without restarting the process. The three blocks in 7-5 ran in sequence inside one process
  • Note the last case in 7-5. Raising the top level to ERROR made the gateway WARNING disappear, because the unset child inherited ERROR from its parent. Delegation works in both directions
  • A safety rail is needed. Reject a request that lowers the whole top-level name to DEBUG and allow it only for submodules. Otherwise a single typo buries the cluster in its own logs
  • Give a temporarily lowered level an expiry. Forgetting to revert is the default outcome

9. Writing the convention - what a team must agree on

That was the material. Now to what a team actually has to put in writing, and how to unwind a repository that already carries thirty thousand lines.

Item to agree onWhat to write down specificallyIf you skip it
Level definitionsOne sentence each, phrased as an action, with no adjectivesEveryone draws the line somewhere else
Alert mappingWhich level goes where, right beside the definitionsDefinitions drift away from alerting

9.1 The procedure for reclassifying what you already have

The order of operations for an existing repository was checked by running it.

python 3.13.3 / win32
--- 8-1. inventory a day of logs by call site, not by line ---
template                                 level     lines/day   verdict
------------------------------------------------------------------------
deprecated field used by client          WARNING        9800 DEMOTE (too many to act on)
cache miss, falling back to db           WARNING        7400 DEMOTE (too many to act on)
optional header absent                   WARNING        5100 DEMOTE (too many to act on)
retry 1/3 upstream=billing               WARNING        4200 DEMOTE (too many to act on)
slow query 340ms                         WARNING        2600 DEMOTE (too many to act on)

--- 8-2. a grep-shaped rule you can run against source ---
  log.warn("retry %s/3", attempt)                       WARN nobody acts on -> INFO or DEBUG
  log.warning("cache miss for key %s", key)             WARN nobody acts on -> INFO or DEBUG
  log.error("could not parse client json: %s", err)     ERROR caused by the caller -> probably INFO
  log.warning("deprecated endpoint hit by %s", ua)      WARN nobody acts on -> INFO or DEBUG
  log.error("could not load user, returning cached cop  ERROR that recovered -> probably INFO
  5 of 7 call sites flagged by three regexes
  this finds candidates, not answers. a human confirms each one.

--- 8-3. did the change actually work? measure before and after ---
level          before      after    readable?
----------------------------------------------
ERROR              13         16          yes
WARNING         30057         74          yes
INFO            31000      48480          yes
DEBUG               0      12500          yes

the target is not 'fewer logs'. total lines went UP: 61070 -> 61070
the target is that ERROR and WARNING became short enough to read.
  1. Count call sites, not lines. Aggregate by template. The top ten usually hold ninety percent of the volume
  2. Let arithmetic do the first pass. An ERROR or WARN call site firing more than 500 times a day cannot be something a person acts on. Six of twelve tripped it, and those six alone made 29,980 lines. Up to here no judgement is required
  3. Run regexes over the source to gather candidates. Three patterns for recovered-but-ERROR, caller-fault-but-ERROR, and nobody-reads-this WARN flagged 5 of 7. Regexes find candidates only. A human confirms each one
  4. Demote first, promote later. Demotion is easy to undo and does not touch alerting
  5. One module per change set. Keep it small enough that a reviewer can genuinely judge the who-and-when of each line
  6. Measure before and after. Look at 8-3. Total lines are unchanged at 61,070 while WARN went from 30,057 to 74. The target is readability, not volume
  7. Fix the alert rules in the same change set. Change levels without changing alerts and the convention lives only in a document

9.2 Checklist

  • Level definitions are written as action sentences with no adjectives
  • The ERROR definition and the alert rule live in the same document
  • Retry-succeeded is not WARN
  • Client input errors are not ERROR
  • The same exception is logged in exactly one place
  • The stack trace is attached once, at the boundary that gives up
  • DEBUG arguments are not assembled up front
  • Expensive arguments are built only after a threshold check
  • Thresholds can be lowered per module without a redeploy
  • A temporarily lowered level carries an expiry
  • Something prevents lowering the whole top-level name to DEBUG
  • An ERROR daily budget exists with a defined response when exceeded
  • Custom levels are avoided, or the collector knows what the numbers mean
  • A periodic sweep finds ERROR and WARN lines nobody acted on for 30 days
  • The share held by the top call sites is reviewed regularly

Conclusion: a level is alert design

Back to the opening question. Why does WARN become a landfill? Not because of bad engineers. Because the judgement that this is not quite normal, so WARN, accumulated nine times while each instance was individually reasonable. The result is the 390-to-1 ratio above.

If you take one thing away, take this. Choosing a level is choosing who this line is addressed to. Ask how bad it is and the answer becomes taste, and taste never reaches agreement. Ask who does what and when, and the answer narrows to one, and that answer is already your alert rule.

So writing a convention is not paperwork. Only when ERROR means look now can you hang a pager on it, and only while WARN stays narrow is that drawer worth opening. Whether the filter means anything at all rests on a single page of agreement.

Finally, the widely cited standard severity definition admits the same thing. It states that severities are very subjective and that a receiver should not assume all originators share the same definition. Even the standard will not write the definition for you. The team has to write it.

# Log Level Convention — Copy-Paste Definitions, Reclassification Steps, Checklist

> Source: braindetox.kr — Why WARN becomes a landfill
> Verified on: Windows 10 / Python 3.13.3 standard logging / Node.js v22.16.0
> Principle: a level is not a severity rating. It declares **who does what, and when**

## 1. Level definitions, written as actions

| Level | One-sentence definition | What the reader does | Timeframe | Alerting |
|---|---|---|---|---|
| **ERROR** | The system failed at its job and we have to fix it | Look now | Even at 3 a.m. | Page |
| **WARN** | A human must touch this, but not tonight | Handle in work hours | This week | Daily digest |
| **INFO** | Nobody acts. It records what the system did | Read only when tracing | — | None |
| **DEBUG** | Useful only while reproducing a bug | Turn on during repro | — | None |

The whole decision reduces to one question.

> **When this line appears, what does a human do, and when?**

Ask how bad it is and the answer becomes taste. Ask who acts and when, and the answer narrows to one.

### The two lines teams always get wrong

| Situation | Common choice | Correct choice | Why |
|---|---|---|---|
| Retry succeeded | WARN | **INFO** | Nothing happened to the user |
| Malformed JSON from a client | ERROR | **INFO** | Returning 400 is the system working |
| Cache miss | WARN | **DEBUG** | The cache is doing its job |
| Falling back to a default config | WARN | **INFO** | Having a default is the normal path |
| Certificate expires in 9 days | INFO | **WARN** | A human must act this week |
| Payment capture failed | WARN | **ERROR** | Money did not move and we must fix it |

## 2. Where to log a caught exception

| Situation | Level | Who logs it |
|---|---|---|
| Recovered by retry | INFO | The layer that recovered |
| Swallowed, no impact | DEBUG | The layer that swallowed it |
| Re-raised to the caller | **nobody** | The raise itself is the message |
| Turned into a 500 | ERROR | The one boundary that gave up |
| Turned into a 400 | INFO | The boundary. The caller was wrong |

**The same exception logged three times** comes from catching, logging and re-raising at every layer.
Running it produces 3 ERROR lines for 1 failure and 1 user-visible error.
Logging once at the boundary, with a stack trace attached, drops it to 1 ERROR line and carries more information, not less.

## 3. What the team has to write down

| Item | Why it is needed |
|---|---|
| Four or five level definitions | Phrased as actions, not severities |
| How a level gets raised | Raising to ERROR touches the pager, so a reviewer signs off |
| How a level gets lowered | Anyone, in the same PR as the noise complaint |
| Required fields | Every record carries the same fields whatever the level |
| ERROR budget | Above N per day the convention is broken, not the code |
| Automatic demotion rule | A line nobody acted on for 30 days gets demoted by default |
| Which level alerts where | Write it next to the definitions or the definitions drift |

## 4. Reclassifying the logs you already have

1. **Count call sites, not lines.** Aggregate by template. The top ten usually account for ninety percent of the volume.
2. **Let arithmetic do the first pass.** An ERROR or WARN call site that fires more than 500 times a day cannot be something a person acts on. No judgement required.
3. **Run regexes over the source to gather candidates.**
   - `\.error\(.*(retry|fallback|cached)` — recovered, but logged as ERROR
   - `\.error\(.*(client|invalid|parse|malformed)` — the caller was wrong, logged as ERROR
   - `\.(warn|warning)\(.*(cache miss|deprecated|retry)` — WARN nobody reads
   - Regexes find **candidates only**. A human confirms every one.
4. **Demote first, promote later.** Demotion is easy to undo and does not touch alerting.
5. **One module per PR.** Keep it small enough that a reviewer can genuinely judge the who-and-when of each line.
6. **Measure before and after.** The goal is not fewer logs. The goal is that **ERROR and WARN become short enough to read.** Total volume may go up and that is fine.
7. **Fix the alert rules in the same PR.** Change levels without changing alerts and the convention lives only in a document.

### Metrics worth tracking

| Metric | Target | What it means |
|---|---|---|
| ERROR per day | A number a person can read through | Above it the pager gets ignored |
| WARN per day | A number you can skim at standup | Above it the filter is meaningless |
| Share of ERRORs actually acted on | Higher is better | Low means the ERROR definition is wrong |
| Share held by the top 3 call sites | Lower is better | High means one or two lines are eating the log |

## 5. Changing levels in production

- Set thresholds **per logger name**. Make names hierarchical with dots and one parent name steers the whole subtree.
- Leave child loggers **unset** so they delegate upward. That is what makes a one-line change move a whole subtree.
- Accept a `name=level` list from an environment variable or a config endpoint. **No redeploy should be required.**
- Safety rail: reject a request that lowers the top-level name to DEBUG, and allow it **only for a submodule**. Otherwise one typo buries the cluster in its own logs.
- Give a temporarily lowered level an **expiry**. Forgetting to revert is the default outcome.

### Do not confuse the two gates

The logger threshold applies first, then each sink applies its own.
**What the logger dropped never comes back, no matter how low you set the sink.**
"I set the sink to DEBUG and still see nothing" is almost always this.

The practical shape is usually:

- Logger: permissive, so records get created at all
- Console sink: INFO, what a human tails
- Alert sink: ERROR, what a pager or a ticket queue reads

## 6. Cost rules

- **Building the argument costs you even when the filter throws the line away.** Concatenate or serialize before handing it to the logger and the CPU is spent whether or not the line survives.
- Pass arguments **lazily**. Hand over the format string and the values separately so only surviving lines get assembled.
- Build expensive arguments — serialization, walking a large collection — **only after checking the threshold**.
- Once a line passes the threshold, formatting happens anyway. Laziness only pays **when the line is dropped**.

## 7. Pre-ship checklist

- [ ] Level definitions are written as **action sentences** (no adjectives like serious or important)
- [ ] The ERROR definition and the **alert rule live in the same document**
- [ ] Retry-succeeded is not WARN
- [ ] Client input errors are not ERROR
- [ ] The same exception is logged **in exactly one place**
- [ ] The stack trace is attached once, at the **boundary that gives up**
- [ ] DEBUG arguments are not assembled up front
- [ ] Expensive arguments are built only after a threshold check
- [ ] Thresholds can be lowered **per module** without a redeploy
- [ ] A temporarily lowered level has an **expiry**
- [ ] Something prevents lowering the whole top-level name to DEBUG
- [ ] An **ERROR daily budget** exists and there is a defined response when it is exceeded
- [ ] Custom levels are **avoided**, or the collector knows what the numbers mean
- [ ] A periodic sweep finds ERROR and WARN lines nobody acted on for 30 days
- [ ] The share held by top call sites is reviewed regularly

## 8. What not to do

- Reaching for WARN by default — if you are unsure it is INFO. WARN holds only what a human touches this week
- Writing definitions with severity adjectives — everyone draws the line for critical somewhere different
- Catching, logging and re-raising at every layer — one failure becomes several lines and skews every count
- Wedging in a custom level because the number sorts correctly — it sorts, but **the meaning does not reach the collector**
- Changing levels while leaving the alert rules alone — the convention stays on paper
- Targeting total log volume — the target is that **ERROR and WARN get read**
- Lowering only the sink threshold without looking at the logger — what the logger dropped is gone
- Keeping an old level because it has always been that way — a line nobody acts on is a demotion candidate
