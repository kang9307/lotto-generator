서론: 「다시 돌려도 되나요」에 답할 수 없는 스크립트

배포 스크립트가 중간에 죽었다. 로그를 보니 8단계 중 5단계까지는 갔다. 원인은 금방 잡혔고, 이제 남은 질문은 하나다. 「이거 그냥 다시 돌려도 됩니까?」

이 질문에 즉답하지 못하는 순간, 그날 밤은 길어진다. 스크립트를 처음부터 읽으면서 이 줄은 두 번 돌면 어떻게 되지를 한 줄씩 손으로 따져야 하기 때문이다. 그리고 대개는 다 따지지 못한 채 「일단 5단계부터 손으로 하겠습니다」로 끝난다. 손으로 한 그 부분은 기록에 남지 않고, 다음 사람은 서버 상태가 왜 스크립트와 다른지 모르게 된다.

멱등성은 이 질문에 0.5초 안에 「예」라고 답할 수 있게 만드는 성질이다. 정의를 외우는 문제가 아니라, 내 스크립트의 각 줄이 두 번째 실행에서 정확히 무엇을 하는지 아는 문제다. 그래서 이 글은 정의로 시작하지 않는다. 실제로 두 번 돌려서 깨뜨려 본 출력으로 시작한다.

다루는 순서는 이렇다. 먼저 실제로 깨지는 여섯 가지 패턴을 하나씩 재현하고 각각의 안전형을 붙인다. 그다음 마커 블록이라는 범용 해법과, 재실행 결과가 같음을 해시로 증명하는 절차를 보인다. 마지막으로 부분 실패 후 재개 설계와 락이 필요한 조건을 정리한다.

먼저 용어 하나만 정리하자. 실무에서 「멱등」이라고 뭉뚱그려 부르는 것은 사실 세 층위다. 이 구분을 해 두면 뒤의 논의가 훨씬 간단해진다.

수준보장하는 것보장하지 않는 것대표 수단
① 재실행 안전두 번 돌려도 깨지지 않는다(오류로 중단되지 않음)결과가 같아지는 것mkdir -p, rm -f
② 결과 수렴몇 번을 돌리든 같은 최종 상태에 도달사람이 만든 드리프트 제거존재 확인 후 변경, 마커 블록
③ 자기 치유상태가 어긋나면 목표 상태로 되돌림선언하지 않은 항목전체 블록 교체, 전체 파일 생성

대부분의 사고는 ①만 해 놓고 ②를 했다고 믿을 때 일어난다. mkdir -p로 바꿔 놓고 「멱등하게 고쳤다」고 말하는 경우다. 아래 재현에서 그 간극이 정확히 어디인지 보게 된다.

실행 전 안전 고지. 이 글의 모든 재현은 새로 만든 임시 디렉터리 안에서만 수행했다. 본문에 rm -rf가 등장하는 곳은 그 임시 디렉터리 또는 그 안의 하위 경로를 지우는 용도뿐이다. 실제 서버에서 따라 하지 말 것. 특히 rm -rf "$DIR" 형태는 $DIR이 비어 있으면 rm -rf ""가 되어 의도치 않은 곳을 훑을 수 있으므로, 변수를 지우는 명령에 쓸 때는 [ -n "$DIR" ] && [ "$DIR" != "/" ] 같은 방어를 반드시 앞에 둔다. 크론이나 CI에 넣기 전에는 --check류 시험 실행으로 대상 경로를 먼저 눈으로 확인하는 편이 안전하다.

1. 실행 환경과 검증 방식

아래 출력은 전부 실제로 돌린 결과를 그대로 붙인 것이다. 재현 환경은 다음과 같다.

===== T0 ENVIRONMENT =====
MINGW64_NT-10.0-19045 3.5.7-882031da.x86_64
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)
sed (GNU sed) 4.9
grep (GNU grep) 3.0
sha256sum (GNU coreutils) 8.32

Windows 10 위의 MSYS2/Git Bash 환경이다. GNU 도구 계열이라 리눅스와 동작이 같지만, 세 가지는 이 환경 고유의 제약이므로 미리 밝혀 둔다. 읽는 분이 결과를 판단할 때 필요한 정보다.

  • 심볼릭 링크는 기본 설정에서 파일 복사로 처리된다. 진짜 링크를 만들기 위해 MSYS=winsymlinks:sys를 설정한 상태에서 실행했다.
  • POSIX 권한 비트는 NTFS 위에서 그대로 반영되지 않는다. 실제로 chmod 600 후에도 모드가 644로 표시됐다. 그래서 권한 관련 멱등성은 이 글에서 실행 결과로 주장하지 않는다. 관련 항목은 체크리스트에만 규칙으로 남겼다.
  • crontab과 flock 바이너리가 없다. 크론은 crontab -l이 출력할 텍스트를 파일로 모사해 줄 조작 로직만 검증했고, 락은 flock 대신 mkdir의 원자성을 이용한 방식으로 실증했다.

검증 방식은 세 가지를 섞었다. 종료 코드(명령이 성공했는지), 파일 내용(무엇이 남았는지), SHA-256 해시(반복 실행 결과가 같은지). 특히 해시는 「같아 보인다」와 「같다」를 가르는 유일한 도구라서 반복해서 쓴다.

2. 패턴 ① append가 조용히 누적된다

가장 흔하고, 가장 늦게 발견된다. 오류가 나지 않기 때문이다. .bashrc에 PATH 한 줄을 넣는 스크립트를 두 번 돌려 보자.

--- 1회차 ---
export PATH=/opt/tool/bin:$PATH
--- 2회차 (같은 명령 재실행) ---
export PATH=/opt/tool/bin:$PATH
export PATH=/opt/tool/bin:$PATH
줄 수: 2

종료 코드는 두 번 다 0이다. 아무도 실패했다고 말해 주지 않는다. 이 줄이 PATH라면 경로가 중복될 뿐이지만, 같은 파일을 매번 조금씩 늘리는 크론이 붙으면 몇 달 뒤 설정 파일이 수천 줄이 된다. 실제 사고는 대개 이 형태로 온다.

2.1 안전형 - 존재를 확인하고 넣는다

LINE='export PATH=/opt/tool/bin:$PATH'
grep -qxF -- "$LINE" safe.conf || printf '%s\n' "$LINE" >> safe.conf

3회 실행 결과다. 줄 수와 해시가 모두 고정된다.

run1 -> 1 line(s) | sha=0a0746b7d8c9bd1f
run2 -> 1 line(s) | sha=0a0746b7d8c9bd1f
run3 -> 1 line(s) | sha=0a0746b7d8c9bd1f

2.2 함정 - grep 옵션 하나로 결과가 뒤집힌다

여기서 -qxF의 x와 F는 장식이 아니다. 둘을 빼면 정반대 방향의 사고가 각각 난다.

함정 A - 주석을 「이미 설정됨」으로 오판한다. 배포 대상 파일에 해당 줄이 주석 처리된 채 들어 있는 경우다. 흔하다. 누군가 임시로 껐다가 잊은 것이다.

파일 내용: #export PATH=/opt/tool/bin:$PATH
grep -qF  판정 -> 이미 있음 (추가 안 함) ... 설정이 영원히 적용되지 않는다
grep -qxF 판정 -> 없음 (정답: 주석은 활성 설정이 아니다)

부분 일치인 -F만 쓰면 주석 줄에도 걸린다. 스크립트는 매번 「이미 되어 있다」며 조용히 넘어가고, 설정은 영원히 적용되지 않는다. 오류가 없어서 몇 달을 간다. -x(줄 전체 일치)가 이걸 막는다.

함정 B - 정규식 메타문자 때문에 중복이 쌓인다. 반대 방향이다. 넣으려는 줄에 [, ], ., * 같은 문자가 있으면 grep -q는 그것을 정규식으로 읽는다.

파일 내용: PATH=/opt/tool[1]/bin
grep -q   판정 -> 없음! ([1] 이 문자클래스로 해석돼 리터럴과 안 맞음) -> 중복 append
grep -qxF 판정 -> 있음 (정답)
3회 실행 결과 비교:
  grep -q   사용: 4 줄
  grep -qxF 사용: 1 줄

[1]은 「문자 1 하나」를 뜻하는 문자 클래스라서 리터럴 [1]과 일치하지 않는다. 그래서 매번 「없다」고 판정하고 3회 실행에 4줄이 된다. -F(고정 문자열)가 이걸 막는다.

2.3 더 조용한 함정 - grep의 종료 코드 2

이건 문서를 봐야 알 수 있다. grep은 세 가지 종료 코드를 돌려준다. 직접 확인한 값이다.

match      -> 0
no match   -> 1
read error -> 2  (|| append 는 이걸 '불일치'와 똑같이 취급한다)

grep -qxF ... || append 형태는 1(불일치)과 2(오류)를 구분하지 못한다. 파일을 읽을 권한이 없거나 경로가 잘못됐을 때 스크립트는 「없구나」로 판단하고 계속 추가한다. 정확히 하려면 종료 코드를 나눠 받아야 한다.

grep -qxF -- "$LINE" "$F"; rc=$?
case $rc in
  0) : ;;                                   # 이미 있음
  1) printf '%s\n' "$LINE" >> "$F" ;;       # 없음 -> 추가
  *) echo "grep 실패(rc=$rc): $F" >&2; exit 1 ;;   # 오류 -> 중단
esac

3. 패턴 ② mkdir·rm의 종료 코드가 스크립트를 반으로 자른다

가장 널리 알려진 항목이라 짧게 짚고, 덜 알려진 부작용에 지면을 쓴다.

--- mkdir d1 (1회차) ---
exit=0
--- mkdir d1 (2회차) ---
mkdir: cannot create directory 'd1': File exists
exit=1
--- mkdir -p d1 (3회차) ---
exit=0

--- rm f1 (1회차) ---
exit=0
--- rm f1 (2회차) ---
rm: cannot remove 'f1': No such file or directory
exit=1
--- rm -f f1 (3회차) ---
exit=0

POSIX 명세가 이 동작을 규정한다. mkdir -p에 대해 「이미 존재하는 디렉터리를 이름으로 갖는 각 dir 피연산자는 오류 없이 무시된다」고 적고, rm -f에 대해 「존재하지 않는 피연산자의 경우 진단 메시지를 쓰거나 종료 상태를 바꾸지 않는다」고 적는다. 옵션이 하는 일은 정확히 그것뿐이다.

3.1 진짜 피해는 set -e와 만날 때 나온다

종료 코드 1 자체는 큰일이 아니다. 문제는 set -e가 걸린 스크립트에서 그 뒤 단계가 통째로 사라진다는 것이다. 3단계짜리 스크립트를 두 번 돌린 결과다.

--- seq.sh 1회차 ---
  [2단계] 설정 파일 배치
  [3단계] 서비스 재시작
exit=0
--- seq.sh 2회차 ---
mkdir: cannot create directory '.../s/stage': File exists
exit=1 <- 2·3단계가 실행되지 않았다

재실행하면 디렉터리를 만드는 1단계에서 막혀 설정 배치도 서비스 재시작도 일어나지 않는다. 그런데 스크립트는 「실패」라고만 말한다. 어디까지 갔는지는 말해 주지 않는다. 운영자는 로그의 마지막 줄만 보고 「디렉터리 문제」라고 판단하고, 정작 서비스가 옛 설정으로 돌고 있다는 사실은 나중에 발견한다.

3.2 옵션이 대신해 주지 않는 것

  • mkdir -p는 존재 여부만 무시한다. 이미 있는 디렉터리의 소유자·권한을 목표 값으로 맞춰 주지 않는다. -m은 새로 만들 때만 적용되므로, 권한을 보장하려면 chmod·chown을 별도 줄로 못 박아야 한다. (앞서 밝혔듯 이 환경에서는 권한 비트를 검증할 수 없어 실행 출력으로 제시하지 않는다.)
  • rm -f는 없는 파일만 눈감아 준다. 지우려던 대상이 디렉터리면 여전히 실패한다.
  • 둘 다 내용에는 관여하지 않는다. 디렉터리가 있다는 것과 그 안이 목표 상태라는 것은 다른 이야기다.

4. 패턴 ③ ln -s는 두 번째에 링크 안으로 파고든다

이 항목이 이 글에서 가장 재현할 가치가 있다. 실패하지 않으면서 엉뚱한 결과를 남기기 때문이다. 무중단 배포에서 current 심링크를 새 릴리스로 옮기는 그 코드다.

--- ln -s rel_a current (1회차) ---
exit=0 | readlink=rel_a
--- ln -s rel_b current (2회차, 같은 명령 재실행) ---
exit=0

2회차가 종료 코드 0이다. 성공처럼 보인다. 실제로 무엇이 생겼는지 확인해 보자.

### ln -sf 로 강제하면? (대상이 디렉터리 심링크일 때)
ln -sf exit=0
readlink current = rel_a   <- 여전히 rel_a 를 가리킨다
current/ 내용:
FROM_A
rel_b
실제로 생긴 것: lrwxrwxrwx 1 user  users 5 Jul 29 05:03 rel_a/rel_b -> rel_b
  -> 링크를 바꾼 게 아니라 링크가 가리키는 디렉터리 '안에' 새 링크를 만들었다

핵심은 마지막 줄이다. current가 디렉터리를 가리키는 심링크일 때, ln -sf rel_b current는 current를 디렉터리로 따라 들어가서 그 안에 rel_b라는 새 링크를 만든다. readlink current는 여전히 rel_a다.

운영에서 이게 무슨 뜻인지 생각해 보자. 배포 스크립트가 성공을 반환하고, 모니터링도 초록불이고, 서비스는 옛 버전으로 계속 돌고 있다. 게다가 이전 릴리스 디렉터리 안에는 정체불명의 링크가 하나씩 쌓인다. 배포할 때마다.

4.1 안전형 - ln -sfn

GNU coreutils의 ln은 -n을 「링크 이름이 디렉터리를 가리키는 심볼릭 링크일 때 그것을 보통 파일처럼 다룬다」고 설명한다. 따라 들어가지 말라는 뜻이다. 3회 실행 결과다.

run1 -> readlink=rel_b | rel_a 오염 여부: FROM_A
run2 -> readlink=rel_b | rel_a 오염 여부: FROM_A
run3 -> readlink=rel_b | rel_a 오염 여부: FROM_A

세 번 모두 rel_b로 고정되고, rel_a 안에는 FROM_A 외에 아무것도 추가되지 않았다. 실무 규칙은 하나로 요약된다. 디렉터리를 가리키는 심링크를 갈아 끼울 때는 언제나 -n을 붙인다. -T(--no-target-directory)를 쓰면 더 엄격하게 강제할 수도 있다.

더 안전한 방식. 심링크 교체를 진짜 원자적으로 하려면 임시 이름으로 링크를 만든 뒤 mv -T로 갈아 끼우는 2단계가 필요하다. ln -sfn은 내부적으로 지우고 다시 만드는 순간이 있어, 그 찰나에 current가 존재하지 않는 시점이 생길 수 있다. 트래픽이 많은 경로라면 이 차이가 의미를 가진다.

5. 패턴 ④ sed -i는 성공을 돌려주며 거짓말한다

sed -i의 재실행 안전성은 패턴에 따라 셋으로 갈린다. 하나씩 재현했다.

5.1 케이스 A - 결과가 패턴과 겹치지 않으면 안전하다

sed -i 's/^timeout = 30$/timeout = 60/' a.conf

run1 sha=ca1a53713b3fbd1d | timeout = 60 retries = 3
run2 sha=ca1a53713b3fbd1d | timeout = 60 retries = 3
run3 sha=ca1a53713b3fbd1d | timeout = 60 retries = 3

치환 결과인 timeout = 60은 패턴 ^timeout = 30$와 겹치지 않는다. 그래서 2회차부터는 매칭이 없고 파일이 변하지 않는다. 해시가 3회 동일하다. 이것이 운 좋게 멱등한 경우다.

5.2 케이스 B - 결과가 패턴을 다시 만족하면 무한 누적된다

sed -i 's#PATH=#PATH=/opt/bin:#' b.conf

run1: PATH=/opt/bin:/usr/bin
run2: PATH=/opt/bin:/opt/bin:/usr/bin
run3: PATH=/opt/bin:/opt/bin:/opt/bin:/usr/bin

치환 결과에 PATH=가 그대로 남아 있어 다음 실행에서 또 걸린다. 돌릴 때마다 경로가 하나씩 늘어난다. 앞선 append 누적보다 훨씬 눈에 안 띈다. 줄 수가 늘지 않기 때문이다. 파일을 열어 한 줄을 끝까지 읽어야 발견된다.

5.3 케이스 C - 아무것도 안 하고 성공을 돌려준다

sed -i 's/^debug = true$/debug = false/' c.conf
exit=0 | 내용=debug = false  <- '적용됐다'의 근거로 종료 코드를 쓰면 안 된다

파일에는 이미 debug = false가 들어 있어 패턴이 하나도 매칭되지 않았다. 그런데 sed는 종료 코드 0을 돌려준다. 이건 결함이 아니라 설계다. sed는 「치환을 몇 건 했는가」를 종료 코드로 알려주지 않는다.

여기서 나오는 실무 규칙이 중요하다. sed -i의 종료 코드는 「적용됐다」의 증거가 아니다. 설정이 실제로 반영됐는지 확인하려면 치환 후에 결과를 다시 읽어서 검사해야 한다. 조용한 실패가 가장 무서운 이유는, 파일 경로 오타나 앵커 불일치도 똑같이 0을 돌려주기 때문이다.

5.4 안전형 - 목표 상태를 먼저 검사하고 사후 검증한다

TARGET='PATH=/opt/bin:/usr/bin'
grep -qxF "$TARGET" d.conf || sed -i 's#^PATH=/usr/bin$#PATH=/opt/bin:/usr/bin#' d.conf
grep -qxF "$TARGET" d.conf || { echo "적용 실패"; exit 1; }

run1: PATH=/opt/bin:/usr/bin
run2: PATH=/opt/bin:/usr/bin
run3: PATH=/opt/bin:/usr/bin
사후 검증: 목표 상태 도달 확인(0)

세 가지를 동시에 했다. ①목표 상태를 먼저 검사해 이미 도달했으면 건드리지 않고, ②앵커를 ^...$로 묶어 결과가 패턴을 다시 만족하지 못하게 하고, ③치환 후 다시 읽어 실제 도달을 확인했다. 이 셋이 갖춰지면 sed -i도 안전하게 쓸 수 있다.

6. 패턴 ⑤ crontab 등록이 실행할 때마다 배가된다

널리 퍼진 관용구가 있다. (crontab -l; echo "$JOB") | crontab -. 세 번 돌린 결과다.

run1 -> sync.sh 줄 수 1
run2 -> sync.sh 줄 수 2
run3 -> sync.sh 줄 수 3
*/5 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1
*/5 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1
*/5 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1
  -> 5분마다 돌아야 할 작업이 한 틱에 3번 동시 기동된다

이 결과의 위험도는 다른 패턴과 급이 다르다. 앞선 것들은 파일이 지저분해지는 문제였지만, 이건 같은 작업이 동시에 여러 개 뜨는 문제다. 동기화 스크립트라면 서로 같은 파일을 건드리고, 백업이라면 대역폭을 나눠 쓰며 둘 다 느려지고, DB 정리 작업이라면 잠금 경합이 난다. 게다가 프로비저닝을 세 번 돌린 것과 부하가 정확히 3배가 되므로 원인을 짚기도 어렵다.

6.1 안전형 - 지우고 다시 넣는다

「있으면 건너뛴다」가 아니라 「해당 스크립트를 참조하는 줄을 전부 지우고 새로 넣는다」가 정답이다. 이유는 곧 설명한다.

{ crontab -l 2>/dev/null | grep -vF '/opt/app/bin/sync.sh'
  printf '%s\n' "$JOB"; } | crontab -

run1 -> 줄 수 1 | sha=7352c0d47610f2d1
run2 -> 줄 수 1 | sha=7352c0d47610f2d1
run3 -> 줄 수 1 | sha=7352c0d47610f2d1

3회 모두 1줄이고 해시가 같다. 「있으면 건너뛴다」 방식보다 이게 나은 이유는 스케줄 변경 때문이다. 존재만 확인하는 방식은 */5를 */10으로 바꿔도 「이미 있다」며 옛 줄을 그대로 둔다. 지우고 넣는 방식은 그렇지 않다. 다른 잡을 건드리지 않는지도 함께 확인했다.

-- 스케줄을 */10 으로 바꾸고, 무관한 잡이 있는 상태에서 2회 실행 --
0 3 * * * /opt/other/backup.sh
*/10 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1

backup.sh 줄은 그대로 남고 sync.sh 줄만 새 스케줄로 갱신됐다. 여기서 필터 문자열을 얼마나 좁게 잡는가가 관건이다. sync.sh처럼 흔한 이름으로 거르면 다른 팀의 /opt/legacy/sync.sh까지 지워질 수 있다. 절대 경로 전체를 쓰거나, 아래 마커 블록 방식을 쓰는 편이 안전하다.

가능하면 crontab을 직접 쓰지 않는 선택지도 있다. /etc/cron.d/에 파일 하나를 통째로 배치하면 그 자체가 「전체 교체」라서 중복이 원천적으로 불가능하다. 임시 파일에 쓰고 mv로 갈아 끼우면 원자성까지 얻는다. 다만 배포판마다 파일명 규칙(점이 든 이름은 무시되는 등)과 사용자 필드 유무가 다르므로, 해당 배포판 문서를 확인하고 적용한다.

7. 패턴 ⑥ 멱등처럼 보이지만 아닌 것들

여기까지가 「알려진 함정」이라면, 이 절은 대부분이 멱등하다고 착각하는 명령들이다.

7.1 cp -r - 첫 실행과 재실행의 결과 구조가 다르다

cp -r src dst   # 를 세 번

run1: dst dst/a.txt
run2: dst dst/a.txt dst/src dst/src/a.txt
run3: dst dst/a.txt dst/src dst/src/a.txt
  -> 1회차는 dst/a.txt, 2회차부터 dst/src/a.txt 가 추가로 생겼다

원인은 대상이 존재하느냐에 따라 cp -r의 의미가 달라지기 때문이다. dst가 없으면 dst를 src의 복사본으로 만든다(dst/a.txt). dst가 있으면 src를 dst 안으로 넣는다(dst/src/a.txt). 같은 명령인데 신규 서버와 재배포 서버의 결과가 다르다. 「신규 설치는 되는데 갱신하면 이상해진다」는 증상의 단골 원인이다.

안전형은 디렉터리가 아니라 내용물을 지정하는 것이다.

cp -r src/. dst2/   # 를 세 번

run1: dst2 dst2/a.txt
run2: dst2 dst2/a.txt
run3: dst2 dst2/a.txt

7.2 mv - 두 번째는 그냥 실패한다

1회차 exit=0
mv: cannot stat 'mvsrc/data.bin': No such file or directory
2회차 exit=1

mv는 본질적으로 재실행할 수 없는 명령이다. 출발지가 사라지기 때문이다. 재실행 가능하게 만들려면 [ -e "$SRC" ] && mv ...처럼 출발지 존재를 조건으로 걸거나, 애초에 mv 대신 목표 상태를 기술하는 방식(복사 후 검증, 혹은 목적지 기준 판단)으로 바꿔야 한다.

7.3 sed의 「줄 추가」 - a 명령은 append와 같다

sed -i '/^\[core\]$/a\    autocrlf = input' gitcfg.ini   # 를 세 번

run1: [core]|    autocrlf = input|
run2: [core]|    autocrlf = input|    autocrlf = input|
run3: [core]|    autocrlf = input|    autocrlf = input|    autocrlf = input|

sed를 썼다고 치환인 것이 아니다. a(append) 명령은 이름 그대로 추가이므로 >>와 성질이 같다. 안전형은 「있으면 교체, 없으면 삽입」의 두 갈래다.

if grep -q '^[[:space:]]*autocrlf[[:space:]]*=' f.ini; then
  sed -i 's/^[[:space:]]*autocrlf[[:space:]]*=.*/    autocrlf = input/' f.ini
else
  sed -i '/^\[core\]$/a\    autocrlf = input' f.ini
fi

run1 sha=94ff19468316c369 | [core]|    autocrlf = input|
run2 sha=94ff19468316c369 | [core]|    autocrlf = input|
run3 sha=94ff19468316c369 | [core]|    autocrlf = input|

7.4 타임스탬프와 난수 - 멱등 검증 자체를 불가능하게 만든다

파일 안에 date 출력이나 $RANDOM이 들어가면, 그 파일은 돌릴 때마다 해시가 달라진다. 로직이 멱등한지와 무관하게 검증 수단을 잃는다. 규칙은 간단하다. 상태 파일과 감사 로그를 분리한다. 언제 무엇을 했는지는 별도 로그로 남기고, 스크립트가 관리하는 설정 파일에는 결정적인 내용만 쓴다.

7.5 정리 - 재실행 안전성 3단계로 다시 보기

  • mkdir -p, rm -f는 ①재실행 안전까지만 준다.
  • grep -qxF 후 append, ln -sfn은 ②결과 수렴에 도달한다.
  • 마커 블록 교체와 파일 전체 생성은 ③자기 치유까지 간다. 사람이 블록 안을 고쳐 놔도 되돌린다.
  • cp -r, mv, sed ... a\는 아무 층에도 속하지 않는다. 감싸지 않으면 그대로 사고다.

8. 마커 블록 - 세 번 돌려도 해시가 같은 이유

지금까지의 방어책은 줄 단위였다. 관리할 줄이 다섯 개가 넘어가면 이 방식은 급격히 지저분해진다. 그때 쓰는 것이 마커 블록이다. Ansible의 blockinfile 모듈이 기본값으로 # BEGIN ANSIBLE MANAGED BLOCK과 # END ANSIBLE MANAGED BLOCK을 쓰는 바로 그 방식이다.

발상은 단순하다. 「내가 관리하는 구간」을 마커로 표시하고, 그 사이를 통째로 갈아 끼운다. 줄마다 존재를 확인할 필요가 없어진다.

apply_block(){
  local file="$1" tag="$2" body="$3"
  local begin="# BEGIN ${tag}" end="# END ${tag}"
  [ -e "$file" ] || : > "$file"
  if grep -qxF "$begin" "$file"; then
    awk -v b="$begin" -v e="$end" -v body="$body" '
      $0==b { print b; printf "%s", body; skip=1; next }
      $0==e { print e; skip=0; next }
      skip==1 { next }
      { print }' "$file" > "$file.new" && mv "$file.new" "$file"
  else
    { printf '%s\n' "$begin"; printf '%s' "$body"; printf '%s\n' "$end"; } >> "$file"
  fi
}

사람이 손으로 관리하는 3줄이 이미 들어 있는 파일에 이 함수를 3회 적용했다.

run1 sha256=45d66418ac3e78277d89be6373e6ccd359b09c546513691db3089ad4210584ed
run2 sha256=45d66418ac3e78277d89be6373e6ccd359b09c546513691db3089ad4210584ed
run3 sha256=45d66418ac3e78277d89be6373e6ccd359b09c546513691db3089ad4210584ed
--- 최종 파일 ---
# 기존 설정 (사람이 손으로 관리하는 영역)
Port 22
PermitRootLogin no
# BEGIN braindetox-keepalive
ClientAliveInterval 60
ClientAliveCountMax 3
# END braindetox-keepalive
--- 마커 밖 원본 무손상 확인 ---
OK: 사람이 관리하는 3줄 그대로

3회 실행 해시가 완전히 동일하고, 마커 밖의 기존 설정은 손상되지 않았다. 이것이 ②결과 수렴이다.

8.1 값이 바뀌면 블록만 갱신된다

### ClientAliveInterval 60 -> 30 으로 바꾸고 3회 더
run4 sha256=4689049ab2047632f5fc4e8935053700b71d560f96215d12d2299bbefcead793
run5 sha256=4689049ab2047632f5fc4e8935053700b71d560f96215d12d2299bbefcead793
run6 sha256=4689049ab2047632f5fc4e8935053700b71d560f96215d12d2299bbefcead793
총 줄 수 7 (블록 누적 없음)

새 값으로 새 해시에 다시 고정된다. 줄 수는 7로 유지된다. 블록이 쌓이지 않는다.

8.2 append 방식이 절대 못 하는 일 - 항목 삭제

여기가 마커 블록의 진짜 가치다. 관리 항목을 2줄에서 1줄로 줄여 보자.

# BEGIN braindetox-keepalive
ClientAliveInterval 30
# END braindetox-keepalive
  -> append 방식은 못 하는 일이다. 지운 항목이 파일에 남지 않는다

ClientAliveCountMax가 사라졌다. 「존재하면 건너뛴다」 방식으로는 이게 불가능하다. 스크립트에서 그 줄을 지워도 이미 배포된 서버의 파일에는 영원히 남는다. 몇 년 지나면 아무도 왜 있는지 모르는 설정이 서버마다 다르게 쌓인다. 마커 블록은 블록 전체가 곧 선언이라 이 문제가 구조적으로 생기지 않는다.

8.3 마커 블록을 쓸 때의 주의점

  • 태그를 고유하게 잡는다. 같은 파일에 여러 스크립트가 블록을 넣을 수 있다. # BEGIN myapp-nginx-upstream처럼 소유자와 용도를 함께 적는다.
  • 주석 문자가 파일마다 다르다. #이 아니라 ;나 //를 쓰는 형식이면 마커도 그 문법을 따라야 한다. 그렇지 않으면 파서가 죽는다.
  • 마커를 사람이 지우면 다음 실행에서 블록이 새로 추가되어 중복이 생긴다. 「손대지 마시오」 안내를 블록 첫 줄에 함께 넣어 두면 도움이 된다.
  • 구조가 있는 형식(JSON·YAML)에는 쓰지 않는다. 줄 기반 삽입은 이런 형식을 깨뜨린다. 전용 파서로 읽고 써야 한다.
  • 블록 안에서만 관리한다. 스크립트가 마커 밖을 건드리기 시작하면 이 패턴의 장점이 사라진다.

9. 재실행을 증명하는 법 - 상태 해시와 dry-run

「멱등하게 짰다」는 주장은 검증할 수 있어야 한다. 가장 싼 방법은 대상 트리 전체를 해시 하나로 접는 것이다.

state_hash(){
  ( cd "$1" && {
      find . -type f | LC_ALL=C sort | xargs sha256sum
      find . -type l | LC_ALL=C sort | while read -r l; do echo "$(readlink "$l")  $l"; done
    } | sha256sum | awk '{print $1}' )
}

일반 파일은 내용 해시로, 심링크는 readlink 결과로 접는다. LC_ALL=C sort로 정렬 순서를 고정하는 것이 중요하다. 로케일에 따라 순서가 달라지면 해시도 달라진다. 프로비저닝 함수를 3회 돌린 결과다.

provision run2  state_hash=219dd1b402f930f92ce94faa467761005c47cb12d740c452e7609d3d6d0d4526
provision run3  state_hash=219dd1b402f930f92ce94faa467761005c47cb12d740c452e7609d3d6d0d4526

9.1 드리프트를 넣고 다시 돌리면 - 정직한 결과

여기서 불편한 결과가 하나 나왔고, 그대로 싣는다. 상태를 일부러 어긋뜨린 뒤 재실행했다.

오염 후 state_hash=74c1a29f825801f98c4d235c47df56ad943e386df4697f5ffd3b1709e7d3785b
재실행 후 state_hash=3e25756382253f698945962c75d2fd19bc1455d5dc20b79aa672057b3220cb81
app.env 내용:
MODE=production
TZ=Asia/Seoul
MODE=debug

재실행 후 해시가 원래 값(219dd1...)으로 돌아오지 않았다. 무엇이 복구되고 무엇이 남았는지 보자.

  • 복구됨 - 사람이 만든 obsolete.conf는 rm -f로 지워졌다.
  • 복구됨 - current 심링크는 ln -sfn으로 releases/v2를 다시 가리켰다.
  • 남음 - 사람이 손으로 넣은 MODE=debug 줄은 그대로 남았다.

이유는 명확하다. grep -qxF ... || append 방식은 「내가 원하는 줄이 있는가」만 묻고 「내가 원하지 않는 줄이 있는가」는 묻지 않는다. 즉 ②결과 수렴에는 도달했지만 ③자기 치유는 아니다. 앱이 파일을 마지막 줄 우선으로 읽는다면, 이 서버는 production이라고 선언해 놓고 debug로 돌아간다.

이걸 막으려면 append를 버리고 파일 전체 또는 마커 블록을 선언해야 한다. 재실행 검증을 「해시가 3회 같다」에서 멈추면 이 구멍을 못 본다. 드리프트를 일부러 넣고 돌려 보는 절차가 필요한 이유다.

9.2 dry-run - 바꾸기 전에 무엇이 바뀔지 본다

운영에서 실제로 더 자주 쓰는 것은 해시보다 시험 실행이다. --check 모드는 두 가지를 준다. 무엇이 바뀔지 미리 보는 것과 수렴했는지 판정하는 것이다.

-- --check (1회차, 아직 아무것도 없음) --
  would add to app.env: MODE=production
  would add to app.env: TZ=Asia/Seoul
  changed=1
-- 실제 적용 --
  changed=1
-- --check (2회차) --
  changed=0 (이미 목표 상태)

두 번째 --check가 changed=0을 돌려준다. 이것이 멱등성의 운영 정의다. 「두 번째 실행에서 바꿀 것이 없다고 스스로 말할 수 있는가」. CI에 넣기도 쉽다. 적용 직후 --check를 한 번 더 돌려서 changed=1이 나오면 그 스크립트는 수렴하지 않은 것이므로 빌드를 깨뜨리면 된다.

구현의 핵심은 모든 변경을 한 함수에 모으는 것이다. 위 예에서는 want_line 하나만 CHECK 플래그를 보면 되게 만들었다. 변경 지점이 코드 곳곳에 흩어져 있으면 dry-run은 유지되지 않는다.

10. 부분 실패 후 재개 - 스텝 마커와 그 함정

서론의 질문으로 돌아가자. 8단계 중 5단계에서 죽었을 때 어떻게 해야 하는가.

10.1 나쁜 설계 - 앞 단계가 멱등이 아니면 영영 못 지나간다

-- 1회차(실패 유도) --
  3단계에서 실패
exit=3
-- 원인 제거 후 2회차 --
mkdir: cannot create directory 'rbad/data': File exists
exit=1  <- 1단계에서 막혀 영영 완주 못 한다

실패 원인을 고쳤는데도 1단계에서 막힌다. 이 상태에서 운영자가 할 수 있는 일은 스크립트를 열어 앞부분을 주석 처리하고 돌리는 것뿐이다. 그 순간 「스크립트로 배포한다」는 전제가 무너진다.

10.2 좋은 설계 - 각 단계 멱등 + 완료 표식

run_step(){
  local name="$1"; shift
  if [ -f "$S/$name.done" ]; then echo "  [skip] $name"; return 0; fi
  "$@" && : > "$S/$name.done" && echo "  [done] $name"
}
run_step schema s1 && run_step seed s2 && run_step release s3
-- 1회차(3단계 실패) --
  [done] schema
  [done] seed
   상태: schema.done seed.done
-- 원인 제거 후 2회차 --
  [skip] schema
  [skip] seed
  [done] release
  완주
-- 3회차(아무 것도 안 해야 정상) --
  [skip] schema
  [skip] seed
  [skip] release
  완주
seed.csv 줄 수: 1 | version: v1

2회차는 실패한 지점부터 이어서 완주했고, 3회차는 아무것도 하지 않고 완주했다. seed.csv가 1줄인 것도 중요하다. 각 단계 자체가 멱등하기 때문에 표식이 없어도 안전하다.

10.3 스텝 마커의 함정 - 표식은 수렴을 보장하지 않는다

이 패턴에는 함정이 있다. 사람이 결과물을 지운 뒤 재실행해 봤다.

version 파일을 사람이 지운 뒤 재실행:
  [skip] schema
  [skip] seed
  [skip] release
  완주
version 존재? 아니오 — 표식이 있어 건너뛰었다

스크립트는 「완주」라고 보고했지만 결과물은 없다. 표식만 보고 실제 상태를 보지 않았기 때문이다. 여기서 나오는 원칙은 명확하다.

  • 스텝 마커는 재개 속도 최적화이지 수렴 보장이 아니다. 무거운 단계(대용량 내려받기, 마이그레이션)를 건너뛰는 용도로만 쓴다.
  • 가벼운 단계에는 표식을 달지 않는다. 매번 확인하는 편이 안전하고 비용도 없다.
  • 표식은 입력이 바뀌면 무효화한다. 파일 이름에 입력 해시를 넣으면(release.$(sha256 of config).done) 설정이 바뀌었을 때 자동으로 다시 실행된다.
  • 마지막에는 상태를 직접 검증한다. 표식과 무관하게 [ -f "$R/version" ] 같은 최종 확인을 붙인다.
  • 표식 저장 위치를 신중히 정한다. 대상 서버에 두면 서버 교체 시 사라지고, 중앙에 두면 서버별 상태를 반영하지 못한다.

11. 락이 필요한 조건, 필요 없는 조건

지금까지의 모든 방어책에는 공통 전제가 있었다. 한 번에 하나만 돈다는 것. 이 전제가 깨지면 「확인 후 변경」 자체가 무너진다. 이른바 check-then-act 문제다.

11.1 재현 - 8개가 동시에 「없으면 만든다」

round1: 락 없이 SEED=5 | 락 사용 SEED=1 (기대값 1)
round2: 락 없이 SEED=4 | 락 사용 SEED=1 (기대값 1)
round3: 락 없이 SEED=5 | 락 사용 SEED=1 (기대값 1)
round4: 락 없이 SEED=5 | 락 사용 SEED=1 (기대값 1)
round5: 락 없이 SEED=4 | 락 사용 SEED=1 (기대값 1)

5회 반복 모두 4~5줄이 생겼다. 기대값은 1이다. grep으로 확인하는 순간과 >>로 추가하는 순간 사이에 다른 프로세스가 끼어들었기 때문이다. 앞 절에서 그렇게 공들여 만든 grep -qxF || append가 동시 실행 앞에서는 무력하다.

실제로 이런 상황이 언제 생기는지가 중요하다. 크론 작업이 5분 주기인데 실행이 6분 걸릴 때, 배포 파이프라인이 재시도로 같은 잡을 두 번 띄울 때, 여러 노드가 공유 스토리지의 같은 파일을 만질 때다. 셋 다 흔하다.

11.2 락이 필요 없는 경우 - 전체 교체

모든 경우에 락이 필요한 것은 아니다. 파일 전체를 임시 파일에 쓴 뒤 mv로 갈아 끼우는 방식은 8개가 동시에 달려들어도 멀쩡했다.

printf 'value=42\n' > ".atomic.$i.tmp" && mv ".atomic.$i.tmp" atomic.txt

줄 수 1 | 내용 value=42 | sha=72cc615c7f451bd5

근거는 rename(2)의 보장이다. 매뉴얼은 「newpath가 이미 존재하면 원자적으로 교체되어, 다른 프로세스가 newpath에 접근하려 할 때 그것이 없는 시점이 존재하지 않는다」고 적는다. 임시 파일과 목적지가 같은 파일시스템에 있어야 한다는 조건만 지키면 된다(다른 파일시스템이면 복사가 되어 원자성이 깨진다).

11.3 락이 반드시 필요한 경우 - 읽고 고쳐 쓰기

### 8개가 동시에 count 를 1씩 증가
최종 count=2  (기대값 count=8)

8회 증가가 2회로 유실됐다. 읽은 값이 쓰기 전에 낡아 버리는 전형적인 갱신 유실이다. 판단표로 정리하면 이렇다.

작업 형태락 필요이유대안
파일 전체를 새로 써서 교체불필요rename이 원자적임시 파일 + mv(같은 파일시스템)
디렉터리 생성 mkdir -p불필요커널이 원자적으로 처리그대로 사용
줄 존재 확인 후 append필요검사와 변경 사이에 틈락 또는 전체 교체로 전환
읽고 고쳐 쓰기(카운터·목록)필요갱신 유실락, 또는 append-only 후 집계
장시간 잡의 중복 기동 방지필요주기보다 실행이 길어질 수 있음잡 진입점에서 락 획득

11.4 무엇으로 잠글 것인가

리눅스라면 util-linux의 flock이 표준적인 선택이다. 매뉴얼은 스크립트 자기 자신을 잠그는 관용구를 제시한다.

[ "${FLOCKER}" != "$0" ] && exec env FLOCKER="$0" flock -en "$0" "$0" "$@" || :

-n(비차단)으로 락을 못 얻으면 기본 종료 코드 1을 돌려준다(-E로 변경 가능). 크론에 넣을 때는 이 값을 「정상적인 중복 방지」로 취급할지 「실패」로 볼지 정해야 알림이 시끄러워지지 않는다.

flock이 없는 환경이라면 mkdir의 원자성을 쓸 수 있다. 이번 재현에서 5회 모두 정확히 1줄을 유지한 방식이다.

if mkdir "$LOCKDIR" 2>/dev/null; then
  trap 'rmdir "$LOCKDIR"' EXIT INT TERM
  ... 임계 구역 ...
else
  echo "다른 인스턴스가 실행 중"; exit 0
fi
  • trap으로 반드시 해제한다. 넣지 않으면 비정상 종료 시 락이 남아 다음 실행이 영원히 막힌다.
  • 락 디렉터리에 PID와 시각을 남긴다. 남은 락이 살아 있는 프로세스의 것인지 판단할 근거가 된다.
  • 고아 락 회수 정책을 정한다. 시간 기준으로 자동 회수하면 편하지만, 느린 정상 실행을 죽일 위험이 있다.
  • NFS 등 네트워크 파일시스템에서는 락 의미가 달라진다. 여러 노드가 참여한다면 파일 락 대신 전용 조정 수단을 검토한다.
  • 락은 멱등성의 대체재가 아니다. 락은 동시성만 막는다. 순차 재실행에서 깨지는 코드는 락을 걸어도 여전히 깨진다.

12. 명령별 안전형 대조표

지금까지 재현한 내용을 한 장으로 접었다. 스크립트를 쓰다가 손이 멈출 때 이 표만 보면 된다.

하려는 일위험한 형태안전한 형태재실행 시 관찰된 결과
디렉터리 생성mkdir dmkdir -p d + 권한은 chmod로 별도2회차 exit=1 → -p는 0

결론: 멱등성은 성격이 아니라 설계다

이 글에서 재현한 사고들에는 공통점이 있다. 대부분이 오류를 내지 않는다. ln -sf는 0을 돌려주고 옛 버전을 서비스했고, sed -i는 0을 돌려주고 아무것도 안 했으며, 주석에 걸린 grep -qF는 몇 달간 설정을 적용하지 않았다. 종료 코드가 0이라는 것과 목표 상태에 도달했다는 것은 다른 이야기다. 이 문장 하나만 남겨도 이 글은 값을 한다.

그래서 실무 규칙은 세 줄로 줄어든다. 첫째, 「이 명령이 이미 된 상태에서 실행되면 무엇을 하는가」를 줄마다 묻는다. 대부분의 사고는 이 질문을 한 번도 안 해서 생긴다. 둘째, 「했는가」가 아니라 「목표 상태인가」를 검사한다. 작업 이력이 아니라 현재 상태가 기준이다. 셋째, 주장하지 말고 증명한다. 세 번 돌리고 해시를 비교하는 데 드는 시간은 1분이고, 그 1분이 새벽 3시의 두 시간을 아낀다.

규모가 커지면 결국 Ansible 같은 도구로 가게 된다. 그 도구들이 「멱등하다」고 말하는 것의 정체가 바로 이 글에서 손으로 만든 것들이다. lineinfile은 존재 확인 후 변경이고, blockinfile은 마커 블록이며, --check는 dry-run이고, changed 값은 수렴 여부다. 도구를 쓰더라도 이 원리를 모르면 shell 모듈 한 줄로 같은 사고를 낸다. 실제로 도구 도입 후에도 사고가 이어지는 조직은 대개 이 지점에 있다.

마지막으로 오늘 할 수 있는 일 하나. 가장 자주 도는 스크립트를 임시 디렉터리에서 세 번 돌리고 상태 해시를 찍어 보는 것. 세 값이 다르다면 그 스크립트는 이미 매일 조금씩 무언가를 바꾸고 있는 중이다. 아직 아무도 눈치채지 못했을 뿐이다.

# 멱등 스크립트 체크리스트 — 쓰기 전에 훑는 목록

> 출처: braindetox.kr — 두 번 돌려도 안전한 스크립트
> 근거: POSIX Issue 8 (mkdir/rm), GNU coreutils(ln -n), rename(2), flock(1)
> 이 파일을 그대로 AI에 붙여 「우리 스크립트를 이 기준으로 고쳐줘」라고 쓰면 됩니다.

## 1. 명령별 안전 형태 — 붙여 쓰는 형태

| 하려는 일 | 이 형태로 쓴다 |
|---|---|
| 디렉터리 | `mkdir -p "$D"` + 권한은 `chmod 0750 "$D"` 별도 줄 |
| 파일 삭제 | `rm -f "$F"` (디렉터리면 `rm -rf` — 변수 방어 필수) |
| 줄 추가 | `grep -qxF -- "$L" "$F" \|\| printf '%s\n' "$L" >> "$F"` |
| 줄 삭제 | `grep -vxF -- "$L" "$F" > "$F.t" && mv "$F.t" "$F"` |
| 심링크 | `ln -sfn "$TARGET" "$LINK"` |
| 값 치환 | `grep -qxF "$WANT" "$F" \|\| sed -i "s#^$OLD\$#$WANT#" "$F"` |
| 줄 삽입 | 있으면 `sed -i 's/^key=.*/key=v/'`, 없으면 `a\` 분기 |
| 크론 | `{ crontab -l 2>/dev/null \| grep -vF "$ABS_PATH"; echo "$JOB"; } \| crontab -` |
| 디렉터리 복사 | `cp -r "$SRC/." "$DST/"` (`cp -r src dst` 아님) |
| 파일 이동 | `[ -e "$S" ] && mv "$S" "$D"` |
| 파일 전체 쓰기 | `... > "$F.tmp" && mv "$F.tmp" "$F"` (같은 파일시스템) |

## 2. 쓰기 전 자문 (한 줄씩)
- [ ] 이 줄은 **이미 된 상태**에서 실행되면 무엇을 하는가
- [ ] 「했는가」가 아니라 **「목표 상태인가」**를 검사하고 있는가
- [ ] `grep` 확인에 `-x`(줄 전체)와 `-F`(고정 문자열)가 둘 다 있는가
- [ ] `grep` 종료 코드 **2(오류)** 를 1(불일치)과 구분하는가
- [ ] `sed` 치환 결과가 **패턴을 다시 만족**하지는 않는가
- [ ] `sed -i` 종료 코드를 「적용됨」의 근거로 쓰고 있지 않은가
- [ ] 심링크 교체에 **`-n`** 이 붙어 있는가
- [ ] `set -e` 아래에서 앞 단계 실패가 **뒤 단계를 통째로 삼키지** 않는가
- [ ] 파일에 **타임스탬프·난수**를 넣어 해시 비교를 막고 있지 않은가
- [ ] 관리 항목을 **줄일 때** 이미 배포된 파일에서 사라지는가

## 3. 마커 블록 템플릿 — 줄이 5개를 넘으면 이걸로

```bash
apply_block(){                     # apply_block <파일> <태그> <본문>
  local file="$1" tag="$2" body="$3"
  local begin="# BEGIN ${tag}" end="# END ${tag}"
  [ -e "$file" ] || : > "$file"
  if grep -qxF "$begin" "$file"; then
    awk -v b="$begin" -v e="$end" -v body="$body" '
      $0==b { print b; printf "%s", body; skip=1; next }
      $0==e { print e; skip=0; next }
      skip==1 { next }
      { print }' "$file" > "$file.new" && mv "$file.new" "$file"
  else
    { printf '%s\n' "$begin"; printf '%s' "$body"; printf '%s\n' "$end"; } >> "$file"
  fi
}
apply_block /etc/ssh/sshd_config "myapp-keepalive" \
  $'ClientAliveInterval 30\nClientAliveCountMax 3\n'
```

- [ ] 태그에 **소유자와 용도**를 넣었다 (`myapp-nginx-upstream`)
- [ ] 파일의 **주석 문자**에 맞췄다 (`#` / `;` / `//`)
- [ ] JSON·YAML 등 **구조 있는 형식에는 쓰지 않았다**
- [ ] 스크립트가 **마커 밖을 건드리지 않는다**

## 4. 재실행 검증 절차 — 커밋 전에 1분

```bash
state_hash(){
  ( cd "$1" && {
      find . -type f | LC_ALL=C sort | xargs sha256sum
      find . -type l | LC_ALL=C sort | while read -r l; do echo "$(readlink "$l")  $l"; done
    } | sha256sum | awk '{print $1}' )
}
for i in 1 2 3; do ./provision.sh "$ROOT"; echo "run$i $(state_hash "$ROOT")"; done
```

- [ ] 3회 해시가 **모두 같다** (다르면 어딘가 누적 중)
- [ ] `LC_ALL=C sort` 로 정렬을 고정했다
- [ ] **드리프트를 일부러 넣고** 다시 돌려 봤다 (설정 한 줄 추가·심링크 변경·잉여 파일)
- [ ] `--check` 두 번째 실행이 **changed=0** 을 돌려준다
- [ ] 시험은 **임시 디렉터리**에서만 했다

## 5. 락이 필요한 조건

| 상황 | 락 | 대안 |
|---|---|---|
| 파일 전체 교체 | 불필요 | 임시 파일 + `mv` |
| `mkdir -p` | 불필요 | 그대로 |
| 확인 후 append | **필요** | 전체 교체로 전환 |
| 읽고-고쳐-쓰기 | **필요** | append-only 후 집계 |
| 주기보다 오래 걸리는 크론 | **필요** | 진입점에서 락 |
| 마커 블록 교체 | **필요** | 락 + 임시 파일 `mv` |

```bash
# flock 이 있으면
[ "${FLOCKER}" != "$0" ] && exec env FLOCKER="$0" flock -en "$0" "$0" "$@" || :

# 없으면 mkdir 원자성
if mkdir "$LOCKDIR" 2>/dev/null; then
  trap 'rmdir "$LOCKDIR"' EXIT INT TERM
else
  echo "다른 인스턴스 실행 중"; exit 0
fi
```

- [ ] `trap` 으로 락을 반드시 해제한다
- [ ] 락 디렉터리에 **PID·시각**을 남긴다
- [ ] **고아 락 회수 정책**을 정했다
- [ ] 락은 **동시성만** 막는다 — 순차 재실행 결함은 그대로 남는다
