Pokemon Emerald at 100k FPS in the Browser - The WASM Recompilation of a Decompiled Game

Beyond Emulation - Decompilation, Static Recompilation, and the Real Meaning of WebAssembly

Jun 8, 2026 Tech & IT

Introduction: A 2004 Game Running at 100k FPS in the Browser

Released in 2004, Pokemon Emerald was a small game running at about 60 FPS on the Game Boy Advance (GBA), atop a 16.78 MHz ARM7 CPU. Yet in June 2026, a developer published a project that runs this game in the browser at "100k FPS," sparking discussion on GeekNews and Hacker News. The number alone seems impossible. How can a 60 FPS game reach a speed more than 1,600 times higher?

The key is that this project is not the emulator we usually imagine. An emulator simulates GBA hardware in software. This project, instead, reverse-engineers the game itself into reconstructed C source code (decompilation) and recompiles that source to WebAssembly (recompilation). As a result, Pokemon Emerald is no longer a game being "simulated" - it becomes native code running directly in the browser.

This article tells the real story behind that provocative 100k FPS figure: how emulation differs from decompilation and recompilation, why native WASM is so dramatically faster, what the context and copyright issues of decompilation projects like pret are, and what this technique means for retro game preservation and the WebAssembly ecosystem. Let us be clear up front - this project does not distribute Nintendo's ROM or copyrighted assets. To run the game, the user must supply a legally owned original ROM.

1. Project Overview - What Is pokeemerald-wasm

The project that went viral is pokeemerald-wasm. The name says everything. Its foundation is pret/pokeemerald, an open-source project that fully decompiles Pokemon Emerald. pokeemerald-wasm recompiles that decompilation to WebAssembly and adds a front end that runs it in the browser.

The flow in one line: original ROM → (pret's decompilation) C source code → (Emscripten recompilation) WebAssembly → browser execution. What matters is that nowhere in this pipeline is there a step that "simulates GBA hardware." Because the game logic exists as code, you only need to translate that code into a format the browser understands (WASM).

An emulator "simulates the console"; recompilation "rebuilds the game itself." In the latter, the hardware to simulate disappears entirely.

2. Emulation vs Recompilation - The Fundamental Difference

This is the most important distinction in the article, so let us take it slowly. There are two ways to run the same game on a different device.

Aspect Emulation (Static) Recompilation
What it does Simulates the original hardware in software Recompiles the game code for a new architecture
Execution unit Interprets/translates original CPU instructions one by one Runs as the host's native instructions directly
Overhead High - instruction interpretation and hardware mimicry Near zero - on par with native
What you need ROM + emulator Game source (decompilation) or binary conversion

Emulation reproduces the GBA's CPU, graphics, and sound chips in software. When the game says "write a value to this memory address," the emulator builds a virtual GBA and mimics that behavior. It is accurate, but it pays an "interpretation tax" on every instruction.

Recompilation takes an entirely different approach. Instead of mimicking the game's behavior, it rebuilds the game code itself for the new platform. pokeemerald-wasm is source-level recompilation: since the source is already reconstructed in C, you simply compile it to WASM. The result does not simulate a GBA. It is just the program "Pokemon Emerald" running in the browser.

2.1 Static vs Dynamic Recompilation

Recompilation has branches too. Dynamic recompilation (JIT) translates blocks of original instructions into native code on the fly at runtime and caches them - the technique modern high-performance emulators use. Static recompilation converts everything ahead of time, before execution. When you have decompiled source, as pokeemerald-wasm does, you get the cleanest possible form of static recompilation - everything is resolved to native code at build time.

3. Why Native WASM Is So Much Faster

Now we can unpack the meaning of 100k FPS. The speed difference comes from three things.

  • The interpretation tax disappears: An emulator runs dozens of host instructions to execute one GBA instruction. Recompilation does that middle step once at build time, so at runtime the host CPU executes the game logic directly.
  • Hardware mimicry disappears: There is no need to simulate the virtual GBA's memory map, interrupts, and timing every frame. The compiler optimizes the code and strips away unnecessary abstraction.
  • Timing shackles come off: The original GBA is bound to a 60 Hz refresh. With vsync and the frame cap removed, the recompiled code loops the game logic as fast as the CPU allows.

Here we should be honest about what "100k FPS" means. It does not mean the screen is drawn 100,000 times per second, nor could a human play that way. The number is closer to the throughput the host reaches when the game logic (frame updates) runs uncapped. In other words, it is a benchmark-style symbol of how much headroom native recompilation has over emulation. Real play simply syncs to 60 FPS - the spare performance becomes fast-forward, smooth input handling, and support for low-end devices.

4. What Is WebAssembly

The technical foundation that makes this project possible is WebAssembly (WASM). WASM is a low-level binary instruction format that runs in the browser at near-native speed. If JavaScript is a dynamic, high-level language, WASM is a portable compilation target produced by compiling languages like C, C++, and Rust.

The core traits of WASM:

  • Near-native performance: The browser quickly validates and executes a pre-compiled binary, delivering more predictable performance than JavaScript that needs JIT warm-up.
  • Language-independent: Code written in C/C++/Rust/Go and more can be compiled to WASM. For Pokemon Emerald, the input is the decompiled C code.
  • Sandboxed safety: WASM runs inside the browser's security sandbox. It delivers strong performance while having no direct access to the system.

The bridge that turns this game from C into WASM is Emscripten. Emscripten is an LLVM-based toolchain that compiles C/C++ to WASM and even generates the glue code that connects graphics, input, and audio to browser APIs. The trend of WASM growing in importance for high-performance web apps, codecs, and image processing also touches the world of video codec standards, and the broader context continues in the AV2 video codec standard.

5. The Context of Decompilation Projects - What Is pret

pret (Pokemon Reverse Engineering Tools), the foundation of pokeemerald-wasm, is a community organization that decompiles the Pokemon series. Their work is in a different league from simple ROM hacking.

pret's pokeemerald reconstructs all of Pokemon Emerald's game logic into human-readable C and ARM assembly. Its defining property is being a match - recompiling this source produces a binary that is byte-for-byte identical to the original ROM. That is proof the decompilation is exact rather than approximate, and a powerful form of game preservation.

The value this decompilation creates is significant:

  • Game preservation: Even if the hardware and ROM vanish, readable source lets the game be understood and reconstructed indefinitely.
  • Portability: With C source, you can recompile to any platform - PC, mobile, browser. pokeemerald-wasm is exactly that proof.
  • Research and modding: ROM hackers and researchers can understand the game's internal structure precisely and extend it safely.

6. How Decompilation Works - The Principle of Reverse Engineering

You may wonder how it is even possible to turn a binary back into C. The process is grueling, but the principle is clear.

  1. Disassemble: Unpack the ROM's machine code into ARM assembly. This part is mechanical.
  2. Identify structure: Determine function boundaries, call relationships, and data structures. Distinguish what is code from what is data.
  3. Rewrite in C: A human writes C code whose behavior and semantics match the assembly.
  4. Verify the match: Check whether compiling that C produces a byte-for-byte identical binary. If it matches, that function is confirmed as "exactly reconstructed."

The crux is the byte-match verification in step 4. This rigor makes the decompilation not "roughly similar code" but "verified equivalent code." Matching function after function over years, with hundreds of contributors, is closer to a giant collaborative puzzle.

7. Copyright and Legality - The Most Important Distinction

This is the most frequently misunderstood part and the one that must be most precise. Framing it as "they cracked a Nintendo game into code and posted it online" is simply wrong.

Let us state the core principles clearly:

  • The ROM is not distributed: Decompilation projects do not include Nintendo's ROM file. To build the game, the user must separately supply a legally owned original ROM.
  • Copyrighted assets are not distributed: Nintendo's creative assets - sprites, music, text, maps - are not in the repository. Code (logic) is the "behavior" that operates on assets, and it is legally distinct from the assets themselves.
  • Only logic is reconstructed: Decompilation expresses "how the game works" as code. This is where it connects to reverse engineering for interoperability and research.

That said, legality is not simple. Whether reverse engineering and fair use are recognized depends on jurisdiction and methodology. That is why decompilation teams follow a "clean room" approach that never references leaked source, and document their process transparently. Also, bundling the "Pokemon" trademark or copyrighted assets is an infringement separate from the code. In short, the legitimacy of reconstructing code and the rights over assets and trademarks must be viewed separately. This article respects that boundary and points to no source for any ROM or asset.

What Nintendo usually objects to is "distribution of ROMs and assets" and "trademark use," not the act of cleanly reconstructing game logic. Mixing the two muddies the discussion.

8. The Real Application Areas of WebAssembly

Pokemon is just the stage for the spectacle; the true domain of this technique is far broader. Here is where WASM actually delivers value.

  • High-performance web apps: Heavy computation like image/video editing, CAD, and 3D rendering runs in the browser at near-native speed, delivering desktop-class tools with no installation.
  • Codecs and compression: Video/audio codecs and compression libraries are ported to WASM for fast decoding in the browser.
  • Porting existing C/C++ assets to the web: Decades-old C libraries are reused on the web by compiling to WASM rather than rewriting them.
  • Retro game preservation and porting: Decompiled games are ported natively to the browser and PC. pokeemerald-wasm is the flagship example.

The last two especially are the same problem: "bringing old native code to a modern platform." The theme of reusing existing systems-language code safely and quickly also runs through the story of reimplementing compression libraries, and the broader view continues in Zstandard implemented in Rust.

9. Technical Achievements and Limits

For balance, let us cover both what this project accomplished and what remains hard.

9.1 Achievements

  • Fully native execution: The game runs as native browser code with no emulation overhead, giving an overwhelmingly high performance ceiling.
  • Proof of portability: It showed that with decompiled source, moving to a new platform becomes a very clean task called "recompilation."
  • Evolution of preservation: It demonstrated, to a broad audience, the practical value of preserving games as "readable code."

9.2 Limits

  • Requires prior decompilation: This cleanliness exists only because someone spent years fully decompiling the game. It cannot be applied as-is to games without a decompilation.
  • Peripheral reimplementation: The game logic recompiles, but hardware-dependent parts - graphics output, input, audio, saving - must be separately wired to and reimplemented against browser APIs.
  • Legal gray zone: The legality boundary from Section 7 always follows along. Step outside the no-ROM, no-asset premise and it becomes infringement immediately.

10. The Developer's Perspective - What to Learn

The lessons this project offers ordinary developers go beyond Pokemon.

First, it makes the cost of abstraction tangible. Peeling away one layer of abstraction - the hardware mimicry of emulation - boosted performance by hundreds of times. It is a reminder that the abstraction layers we stack daily hide a similar tax.

Second, it shows how powerful WASM as a compilation target is. "The browser is slow" is no longer a general truth. Compiled properly, the browser becomes a near-native stage.

Third, the value of source. For the same game, the future is completely different "with only a binary" versus "with readable source." Source opens every door to porting, extension, and preservation. That perspective treats code not as a mere artifact but as an asset, and it connects to the evolution of developer tooling and harnesses, a context also touched in dynamic workflows and the harness.

11. The Future of Retro Game Preservation

Placed in a larger arc, this project reads as one evolutionary step of "retro game preservation." Preservation has roughly advanced through three stages.

Stage 1: ROM dump          Preserve the original cartridge as a file (distribution is separate)
   |
   v
Stage 2: Emulation         Run the ROM on virtual hardware (escape hardware dependency)
   |
   v
Stage 3: Decompile/recompile  Reconstruct the game as source -> native port to any platform

Stage 3 is powerful because the game is no longer tied to specific hardware or an emulator. Native ports of Nintendo 64 games to PC already demonstrated this trend, and pokeemerald-wasm extends the target to "the browser." As more games complete decompilation, this "recompilation porting" will become more common.

12. The Korean Developer's Perspective - What to Try

Finally, let us map this trend onto a real development environment.

  • Hands-on WASM learning: Compiling your own C/C++ code to WASM with Emscripten is a great foundation for future high-performance web app and codec work. Starting with a small algorithm is ideal.
  • Porting legacy assets to the web: If you have old in-house C/C++ libraries, a WASM port is worth considering instead of a rewrite. You keep proven logic intact.
  • Legality first: When dealing with games or media, build the habit of separating the rights of "code" from "assets and trademarks." Apart from technical curiosity, the line of not distributing ROMs and assets must be respected clearly.
  • Code with a preservation mindset: The code we write becomes "legacy" someday too. This project, paradoxically, reminds us of the value of leaving code in a readable, portable form.

13. Conclusion + 3 Key Takeaways

"Pokemon Emerald at 100k FPS" is a provocative headline, but inside it lies a solid technical story. Let us close with three takeaways.

  1. It is recompilation, not emulation. By rebuilding the game code for a new platform instead of mimicking hardware, the interpretation and mimicry taxes disappear and the performance ceiling rises hundredfold. 100k FPS is a symbol of that headroom.
  2. Decompilation makes it all possible. Without pret's byte-matched decompilation as a foundation, this recompilation would not exist. Readable source is the real asset that opens the doors to porting, extension, and preservation.
  3. The legality boundary lies in separating code from assets. The clean-room reconstruction of game logic and the rights over ROMs, copyrighted assets, and trademarks are different matters. When the no-ROM-distribution premise is respected, all these technical achievements stand in a legitimate place.
