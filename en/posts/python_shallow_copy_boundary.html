Introduction - copying happens one layer at a time

Sometimes a settings dictionary is copied so that values can be changed per user, and the default settings turn out to have changed as well. The copy code ran without trouble and a new dictionary was clearly created. Yet an inner list was the same object as in the original. The number of layers that get copied differs from method to method. Object identity (is) shows how many layers each method creates and where it stops, and the output below covers the methods that go past that stopping point and their cost.

The axis differs from neighboring articles. The default argument article covers the problem of a default object created once when the def statement runs and shared between calls, and the small integer article covers how comparing integers and strings with is gives results that vary because of optimization. This article is limited to how many layers become new objects when an existing container is copied. The points that connect to those two articles are handed over by link in the text.

The questions covered are these.

  • How many objects does assignment (=) create?
  • For copy(), list(), slicing, dict.copy(), copy.copy and copy.deepcopy, how far is the outside and the inside a new object?
  • Under what conditions does the original change in nested lists and dictionaries?
  • How are a list inside a tuple, dataclasses, and user-defined classes handled by copying?
  • How does deepcopy handle a structure that references the same object twice, and circular references?
  • What is the time cost of deepcopy on this PC?

Assignment is not a copy

The first case people run into is something thought of as a copy that is actually an assignment. The first sentence of the copy module documentation reads: "Assignment statements in Python do not copy objects, they create bindings between a target and an object." The output below agrees with that sentence.

a = [1, 2]
                    b = a
                    print(a is b, id(a) == id(b))
                    b.append(3)
                    print(a)
                    c = list(a)
                    print(c is a, c == a)
                    c.append(4)
                    print(a, c)
True True
                    [1, 2, 3]
                    False True
                    [1, 2, 3] [1, 2, 3, 4]

On the first line both a is b and id(a) == id(b) are True. The data model documentation states that is compares the identity of two objects and that id() returns an integer representing that identity, and it adds that in CPython id(x) is the memory address where x is stored. So a and b are two names attached to one object. After b.append(3), a also became [1, 2, 3]. By contrast, c made with list(a) is a new list for which c is a is False, and c == a being True only means the contents are equal and not that they are the same object. c.append(4) did not affect a.

  • == asks whether values are equal and is asks whether the objects are the same. Whether a copy happened is seen with is.
  • Here is is used to look at the identity of container objects. The problem that comparing values such as integers and strings with is gives varying results because of optimization is covered in the small integer article.
  • Run output for the pattern of copying a list passed in by the caller is in section 5 of the default argument article.

Which layers each copy method creates

The code below runs several copy expressions on one nested list and one dictionary, and prints with is not whether the outer container of the result is a different object from the original (new outer) and whether the inner list is a different object from the original (new inner).

                    orig = [[1, 2], [3, 4]]
                    cases = [
                        ('b = orig', lambda: orig),
                        ('orig.copy()', lambda: orig.copy()),
                        ('list(orig)', lambda: list(orig)),
                        ('orig[:]', lambda: orig[:]),
                        ('[*orig]', lambda: [*orig]),
                        ('copy.copy(orig)', lambda: copy.copy(orig)),
                        ('copy.deepcopy(orig)', lambda: copy.deepcopy(orig)),
                    ]
                    print('%-22s %-10s %s' % ('expression', 'new outer', 'new inner'))
                    for name, make in cases:
                        b = make()
                        print('%-22s %-10s %s' % (name, b is not orig, b[0] is not orig[0]))
                    d = {'name': 'x', 'tags': ['a']}
                    cases = [
                        ('d.copy()', lambda: d.copy()),
                        ('dict(d)', lambda: dict(d)),
                        ('{**d}', lambda: {**d}),

                        ('copy.deepcopy(d)', lambda: copy.deepcopy(d)),

                    print()

The copy module documentation defines the two copies like this. "A shallow copy constructs a new compound object and then (to the extent possible) inserts references into it to the objects found in the original." "A deep copy constructs a new compound object and then, recursively, inserts copies into it of the objects found in the original." The output agrees with these definitions.

ExpressionOuter containerInner objects
b = origSame objectSame object

d.copy(), dict(d), {**d}, copy.copy(d)New objectShared with the original

What can be read from the table is as follows.

  • Only assignment keeps the same object even at the outer level. The other eleven expressions, apart from assignment, all created a new outer container.
  • List copy(), list(), slicing and [*x], dictionary copy(), dict() and {**d}, and copy.copy all had the same depth, one layer, in this environment.
  • The built-in sequence entry of the official documentation describes copy() of a mutable sequence as "Create a shallow copy of sequence. This is equivalent to writing sequence[:]." That matches the output in which slicing and copy() have the same depth.
  • The copy module documentation says shallow copies of collections can be made with list.copy(), dict.copy(), set.copy() and a slice of the entire sequence. The documentation lists these methods as shallow copies, and the is table in the output shows this.
  • Only deepcopy created new inner objects as well.

Reproducing the original changing in a nested structure

When a change is made to a copy with only one layer rebuilt, the original sometimes changes and sometimes does not, depending on which layer is changed. The code below applies three kinds of change to the copy in turn and prints the original each time. The latter part is a situation where a default settings dictionary is copy()-ed to make a user's settings.

orig = [[1, 2], [3, 4]]
                    dup = orig.copy()
                    dup.append([5, 6])
                    print('after append to the copy   :', orig)
                    dup[0].append(99)
                    print('after changing an inner list:', orig)
                    dup[1] = 'replaced'
                    print('after replacing an element  :', orig)
                    
                    defaults = {'name': 'base', 'tags': ['a']}
                    user = defaults.copy()
                    user['name'] = 'mine'
                    user['tags'].append('b')
                    print(defaults)
                    print(user)
after append to the copy   : [[1, 2], [3, 4]]
                    after changing an inner list: [[1, 2, 99], [3, 4]]
                    after replacing an element  : [[1, 2, 99], [3, 4]]
                    {'name': 'base', 'tags': ['a', 'b']}
                    {'name': 'mine', 'tags': ['a', 'b']}

Appending a new item to the copy (a change to the outer container) and replacing an element of the copy with another value (dup[1] = 'replaced') did not affect the original. But when append(99) was applied to the inner list dup[0] of the copy, orig[0] of the original also became [1, 2, 99]. The copy and the original point to the same inner list, and the new inner False output of the previous section foreshadows this result.

The dictionary behaves the same way. user['name'] = 'mine' changed only user, and defaults['name'] stayed 'base'. But user['tags'].append('b') also put 'b' into defaults['tags']. Code meant to build user settings polluted the default settings.

  • Operations that change the outer container of the copy (adding, replacing or deleting items) do not affect the original.
  • Operations that change in place an inner mutable object that the copy shares (append, [k] = v and the like) are visible in the original too.
  • Even on the same copy the result depends on which field was touched, so a test that checks only one field may not expose the problem.

Repetition is the same reference repeated, not a copy

Building a two-dimensional list with [[0] * 2] * 3 is another face of the same problem. For s * n the official documentation states "items in the sequence s are not copied; they are referenced multiple times", and gives the example where lists[0].append(3) after lists = [[]] * 3 gives [[3], [3], [3]]. The output below comes from similar code.

grid = [[0] * 2] * 3
                    print(grid[0] is grid[1] is grid[2])
                    grid[0][0] = 1
                    print(grid)
                    fresh = [[0] * 2 for _ in range(3)]
                    print(fresh[0] is fresh[1])
                    fresh[0][0] = 1
                    print(fresh)
True
                    [[1, 0], [1, 0], [1, 0]]
                    False
                    [[1, 0], [0, 0], [0, 0]]

The first line is True. All three rows are the same list object, and grid[0][0] = 1 appeared in all three rows. fresh, which builds a new list for each row with a list comprehension, has rows that are different objects (False) and only one row changed. The reason the same phenomenon occurs without any copy function is that the problem is not the copy method but the fact that several names or positions are attached to the same object.

A list inside a tuple - the trap of an immutable container

The data model documentation states: "The value of an immutable container object that contains a reference to a mutable object can change when the latter's value is changed; however the container is still considered immutable, because the collection of objects it contains cannot be changed." It says an immutable container holding a mutable object can change in value when that mutable object changes. What happens when this meets copying is in the output below.

import copy
                    t = ([1, 2], 3)
                    print(copy.copy(t) is t)
                    deep = copy.deepcopy(t)
                    print(deep is t, deep[0] is t[0], deep == t)
                    t[0].append(99)
                    print(t)
                    try:
                        t[0] += [4]
                    except TypeError as e:
                        print(type(e).__name__, e)
                    print(t)
                    print(deep)
                    u = (1, 'a')
                    print(copy.deepcopy(u) is u)
True
                    False False True
                    ([1, 2, 99], 3)
                    TypeError 'tuple' object does not support item assignment
                    ([1, 2, 99, 4], 3)
                    ([1, 2], 3)
                    True

On the first line copy.copy(t) is t is True. The shallow copy of a tuple returned the same object instead of creating a new tuple. On the second line, deepcopy(t) is a new tuple (deep is t is False), the list inside is also a new object (deep[0] is t[0] is False), and the values are equal (deep == t). Calling append(99) on the list inside the original t made it ([1, 2, 99], 3) even though the tuple is immutable.

The next line is the scene where the trap shows itself. t[0] += [4] raised TypeError: 'tuple' object does not support item assignment, and printing t right after gives ([1, 2, 99, 4], 3). Although the exception was raised, 4 had already been added to the list. What the output establishes is that both the exception and the change happened. On the last two lines, deep, which had been detached with deepcopy, remains ([1, 2], 3), and for the tuple u = (1, 'a') that holds no mutable object, deepcopy(u) is u was True.

  • copy.copy of a tuple returns the same object, so nothing is created despite the feeling of having copied. If a list is inside, that list is of course shared.
  • That a tuple is immutable means the element slots of the tuple do not change, and it does not freeze the contents of the lists the elements point to.
  • If a tuple is used as a dictionary key or a settings value and a list is put inside, that list is shared between copies.
  • deepcopy created a new tuple when it held a mutable object and returned the same object for a tuple holding only immutable objects. These two output lines are observations from CPython.

Copying classes and dataclasses

Instances of user-defined classes follow the same rules. The code makes an object with a list field with a dataclass, obtains a new object in four ways, and prints whether each shares the list field. The last line shows the lists of the four copies after an item was appended to the original's list.

import copy
                    import dataclasses
                    from dataclasses import dataclass, field
                    
                    @dataclass
                    class Box:
                        name: str
                        items: list = field(default_factory=list)
                    
                    a = Box('a', [1, 2])
                    b = copy.copy(a)
                    c = copy.deepcopy(a)
                    d = dataclasses.replace(a, name='d')
                    e = copy.replace(a, name='e')
                    for label, x in [('copy.copy', b), ('copy.deepcopy', c), ('dataclasses.replace', d), ('copy.replace', e)]:
                        print('%-20s new object: %-5s shares items: %s' % (label, x is not a, x.items is a.items))
                    a.items.append(3)
                    print(b.items, c.items, d.items, e.items)
copy.copy            new object: True  shares items: True
                    copy.deepcopy        new object: True  shares items: False
                    dataclasses.replace  new object: True  shares items: True
                    copy.replace         new object: True  shares items: True
                    [1, 2, 3] [1, 2] [1, 2, 3] [1, 2, 3]

All four methods created a new object, but only deepcopy detached the list. copy.copy, dataclasses.replace and the copy.replace added in 3.13 shared the list with the original, and on the last line, when 3 was put into the original, 3 was visible in the lists of these three. The copy module documentation says copy.replace() was added in 3.13, is more limited than copy() and deepcopy(), and supports only named tuples, dataclasses and classes that define __replace__(). The replace family, which builds a new object by changing some fields, carries the unchanged fields over as they are, so mutable fields are shared.

deepcopy cannot copy every object. The code below applies copy.copy and copy.deepcopy to an object that holds a lock (threading.Lock) as an attribute, and to a subclass that defines __deepcopy__.

import copy
                    import threading
                    
                    class Job:
                        def __init__(self, name):
                            self.name = name
                            self.lock = threading.Lock()
                            self.log = []
                    
                    job = Job('j1')
                    try:
                        copy.deepcopy(job)
                    except TypeError as e:
                        print(type(e).__name__, e)
                    print(copy.copy(job).lock is job.lock)
                    
                    class SafeJob(Job):
                        def __deepcopy__(self, memo):
                            new = SafeJob(self.name)
                            new.log = copy.deepcopy(self.log, memo)
                            return new
                    
                    s = SafeJob('j2')
                    s.log.append('start')
                    t = copy.deepcopy(s)
                    print(t.log, t.log is s.log, t.lock is s.lock)
TypeError cannot pickle '_thread.lock' object
                    True
                    ['start'] False False

copy.deepcopy(job) failed with TypeError: cannot pickle '_thread.lock' object, and copy.copy(job).lock is job.lock was True. The shallow copy does not touch the lock object and shares it. SafeJob, which defines __deepcopy__(self, memo), made a new object with a new lock (t.lock is s.lock is False), and the log list was copied separately and detached (t.log is s.log is False, with contents ['start']). The copy module documentation says deepcopy lets user-defined classes override the copying operation or the set of components copied, and explains that object.__deepcopy__(self, memo) implements the deep copy and is passed the memo dictionary. The description and the output agree.

  • A shallow copy (copy.copy) copies only references whatever the attributes are, so it succeeded even with a lock.
  • deepcopy fails with TypeError when it meets an attribute that cannot be copied. In this output the example is the lock.
  • For a class that holds resources that must be shared (locks, connections and so on), the copying method is specified with __deepcopy__.

What deepcopy solves - memo and circular references

The copy module documentation says deep copy has two problems. First, recursive objects (compound objects that, directly or indirectly, contain a reference to themselves) may cause a recursive loop. Second, because deep copy copies everything it may copy too much, such as data which is intended to be shared between copies. It then says deepcopy() avoids them in two ways: by keeping a memo dictionary of objects already copied during the current copying pass, and by letting user-defined classes override the copying operation or the set of components copied. The output below bears on the first mechanism. It covers a structure holding the same list twice, a circular structure, and a pre-filled memo.

import copy
                    a = [1]
                    orig = [a, a]
                    deep = copy.deepcopy(orig)
                    print('deepcopy keeps sharing :', deep[0] is deep[1], '| detached from original:', deep[0] is not orig[0])
                    naive = [copy.deepcopy(x) for x in orig]
                    print('per-element deepcopy   :', naive[0] is naive[1])
                    shallow = copy.copy(orig)
                    print('shallow copy           :', shallow[0] is shallow[1], shallow[0] is orig[0])
                    
                    memo = {}
                    copy.deepcopy(orig, memo)
                    print('memo entries           :', len(memo))
                    
                    loop = []
                    loop.append(loop)
                    print('cyclic shallow         :', copy.copy(loop)[0] is loop)
                    dup = copy.deepcopy(loop)
                    print('cyclic deepcopy        :', dup is not loop, dup[0] is dup)
                    
                    keep = {id(a): a}
                    part = copy.deepcopy(orig, keep)
                    print('pre-filled memo        :', part[0] is a, part[0] is part[1])
deepcopy keeps sharing : True | detached from original: True
                    per-element deepcopy   : False
                    shallow copy           : True True
                    memo entries           : 3
                    cyclic shallow         : True
                    cyclic deepcopy        : True True
                    pre-filled memo        : True True
  • When orig = [a, a], which holds the same list a twice, is deep-copied, the two positions in the copy are also one and the same object (deep[0] is deep[1] is True). At the same time it is detached from the original (deep[0] is not orig[0] is True). The structure was preserved.
  • naive, where each element was deep-copied separately, ended up with two positions that are different objects (False). The structure in which the same object was shared is lost. The memo lives only during one deepcopy call, so splitting the call does not preserve it.
  • The shallow copy has its two inner positions pointing straight at the original a (shallow[0] is orig[0] is True).
  • The memo that deepcopy filled held 3 entries.
  • For the list loop that contains itself, the first element of the shallow copy points to the original loop (True). deepcopy finished without infinite recursion, and the copy is a different object from the original while containing itself (dup[0] is dup is True). Even the circular structure was preserved.
  • When {id(a): a} was put into the memo in advance and deepcopy was called, part[0] is a was True. An object already in the memo is not copied and is used as it is.

The last item can serve as a way of leaving an object out of the copy when it must be shared. For the problem the documentation describes, that deep copy may copy too much, such as data intended to be shared between copies, this output shows that pre-filling the memo can leave one object shared. That is, however, an observation that exploits how the memo behaves, and the method the documentation presents is to define __deepcopy__.

The cost of deepcopy - values measured on this PC

Because deepcopy visits and copies all the inner objects, it takes longer than a shallow copy. How much longer is given by timeit values. For a nested list with ten thousand inner lists (nested) and a flat list of ten thousand integers (flat), each expression is repeated 5 times and the fastest value is printed in microseconds per call. The two outputs below come from the same script run twice, and one run takes 2 to 3 seconds on this PC.

import copy
                    import timeit
                    
                    def best_us(stmt, glb, number):
                        runs = timeit.repeat(stmt, globals=glb, number=number, repeat=5)
                        return min(runs) / number * 1e6
                    
                    for n in (100, 10000):
                        nested = [[i, i + 1, i + 2] for i in range(n)]
                        flat = list(range(n))
                        fast, slow = (2000, 200) if n == 100 else (200, 5)
                        g = {'copy': copy, 'nested': nested, 'flat': flat}
                        print('n =', n)
                        print('  nested.copy()             %10.1f us' % best_us('nested.copy()', g, fast))
                        print('  copy.copy(nested)         %10.1f us' % best_us('copy.copy(nested)', g, fast))
                        print('  copy.deepcopy(nested)     %10.1f us' % best_us('copy.deepcopy(nested)', g, slow))
                        print('  flat.copy()               %10.1f us' % best_us('flat.copy()', g, fast))
                        print('  copy.deepcopy(flat)       %10.1f us' % best_us('copy.deepcopy(flat)', g, slow))

The values of the same code differed quite a bit between the two outputs. Since the value of the same expression differs between outputs, the difference in magnitude should be read and not the absolute numbers. For the nested list of ten thousand, copy.deepcopy(nested) took about 624~641 times as long as copy.copy(nested) (a computed value over the two outputs), and copy.deepcopy(flat) for ten thousand integers also took about 167~173 times as long as flat.copy() (computed). Even for a list of integers, which holds no mutable object inside, the deepcopy value was larger than the shallow copy. The ratios above are values of this PC and change when run again.

  • At this size the shallow copy values were tens of microseconds, and the deepcopy values were thousands to tens of thousands of microseconds (milliseconds).
  • deepcopy is needed when inner mutable objects are changed in the copy. A copy that is only read, or whose inside is not changed, leaves the original unaffected with a shallow copy, as the result of section 4 shows.
  • In code that calls deepcopy inside a loop, the cost is multiplied by the number of iterations.
  • This measurement is two runs on one PC. The values are not a promise of improvement or reduction, and a different data shape can give different results.

What to choose - selection criteria

The criteria obtained from the earlier outputs are gathered in a table. The selective copy and deepcopy rows are based on the output of the code below. The first block copies only the fields to be changed, and the second block copies everything with deepcopy. In both, limits of the copy is changed and the original is printed.

import copy
                    
                    def make():
                        return {'name': 'base', 'tags': ['a'], 'limits': {'cpu': 1}}
                    
                    defaults = make()
                    one = {**defaults, 'tags': defaults['tags'].copy()}
                    one['tags'].append('b')
                    one['limits']['cpu'] = 8
                    print('selective copy:', defaults)
                    
                    defaults = make()
                    two = copy.deepcopy(defaults)
                    two['tags'].append('b')
                    two['limits']['cpu'] = 8
                    print('deepcopy      :', defaults)
selective copy: {'name': 'base', 'tags': ['a'], 'limits': {'cpu': 8}}
                    deepcopy      : {'name': 'base', 'tags': ['a'], 'limits': {'cpu': 1}}

The selective copy copied tags, so tags of the original was protected, but limits, which was not copied, was shared, and limits of the original became {'cpu': 8}. With deepcopy, both tags and limits of a freshly made original stayed as they were. A selective copy can miss a field to copy, and deepcopy has a cost.

Reduced to check questions, they are as follows.

  • After copying, are inner mutable objects changed in place?
  • Was it checked with is whether the inner objects of the copy are the same objects as the original?
  • If deepcopy is used, are there attributes that cannot be copied or must be shared?
  • Does a deepcopy inside a loop affect the time?
  • Is a repetition expression such as [[0] * n] * m being used?

What Could Not Be Verified

  • The internal reason deepcopy is slow. Only values measured on this PC exist, and which step takes the time was not profiled.
  • What each of the 3 memo entries filled by deepcopy is. Only the count was printed and the entries themselves were not opened.
  • The copy depth for containers other than lists and dictionaries, such as sets, bytearrays and user-defined containers.
  • Behavior in other implementations such as PyPy or in other Python versions. That the shallow copy of a tuple returns the same object is also an observation of this environment (CPython 3.13.3).
  • The meaning of copying for objects of external libraries such as NumPy arrays and pandas data frames.
  • Extending copying through __copy__, __reduce__ and copyreg, and how that relates to the TypeError of deepcopy.
  • The deepcopy result for classes that use slots (__slots__) and for objects with complicated inheritance.
  • Behavior when the original is changed during a copy in a multithreaded program.
