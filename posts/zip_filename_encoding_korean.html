zip 안의 한글 파일명이 깨지는 지점 - 누가 어떤 인코딩으로 적었는가

파일명은 바이트열이다. 그 바이트를 어떻게 읽을지는 플래그 한 비트와 도구의 추측에 달렸다

2026-07-30 개발/인프라

서론: 받은 압축 파일을 푸니 이름이 전부 깨져 있었다

거래처에서 보낸 zip을 내려받아 풀었다. 파일은 다 나왔는데 이름이 ║╕░φ╝¡.txt, 1║╨▒Γ ╕┼├Γ.xlsx 같은 것으로 바뀌어 있다. 상대에게 물어보면 「우리 쪽에서는 잘 보인다」고 한다. 반대 상황도 흔하다. 내가 압축해 보낸 파일을 상대가 풀었더니 이름이 깨졌다는 연락이 온다. 내 컴퓨터에서는 아무 문제가 없다.

이 대화가 끝없이 반복되는 이유는 양쪽 모두 틀린 일을 하지 않았기 때문이다. 여기서 흔히 나오는 조언은 「UTF-8로 압축하세요」인데, 이 말은 절반만 맞는다. zip 아카이브 안에서 파일명은 그냥 바이트열로 저장된다. 그 바이트를 어떤 인코딩으로 읽어야 하는지 알려주는 수단은 플래그 한 비트뿐이고, 그 비트가 꺼져 있을 때 무엇으로 읽어야 하는지는 명세가 정해 두지 않았다.

그래서 이 글은 설정을 바꾸는 이야기가 아니다. 아카이브를 바이트로 뜯어 파일명 필드와 플래그를 직접 읽는 이야기다. 그 두 값만 보면 깨진 이유가 즉시 확정되고, 되돌릴 수 있는지 없는지도 그 자리에서 갈린다. 아래 모든 출력은 직접 실행해 얻은 것이다.

실행 환경. 아카이브는 struct로 바이트를 직접 조립해 만들었고, 읽을 때도 표준 라이브러리에 맡기지 않고 중앙 디렉터리를 손으로 파싱했다. 스크립트는 모두 파일로 저장해 실행했다. 한글과 역슬래시가 섞인 코드를 셸 인자로 넘기면 조용히 변형되기 때문이다. 작업 경로는 \work\demo 같은 자리표시자로 옮겨 적었다.

이 글이 다루지 않는 것. 파일 내용의 인코딩 오변환과 그 진단법은 cp949와 UTF-8, 두 종류의 인코딩 오류에서 다뤘다. 유니코드 정규화의 원리는 NFC와 NFD에 있다. 여기서는 zip 아카이브 안의 파일명 필드 한 점만 본다.

1. 명세가 정하지 않은 것

zip 형식의 규격은 PKWARE의 APPNOTE 문서다. 파일명 인코딩에 관한 내용은 놀랄 만큼 짧다. 범용 목적 플래그(general purpose bit flag)의 비트 11에 관한 한 문장이 사실상 전부다.

Bit 11: Language encoding flag (EFS). If this bit is set, the filename and comment fields for this file MUST be encoded using UTF-8.

이 문장은 비트가 켜졌을 때만 말한다. 꺼져 있을 때는 무엇인가? 부록 D의 서술이 답이다. zip 형식은 역사적으로 원래의 IBM PC 문자 인코딩 집합만 지원해 왔다는 것이다. 즉 비트 11이 없던 시절의 기본값은 도스 시대의 코드페이지이고, 그 밖의 인코딩을 쓰고 있다고 선언할 방법이 없다.

  • 파일명 필드는 길이와 바이트열만 갖는다. 인코딩 이름이 들어가는 자리가 없다
  • 비트 11은 켜짐만 의미가 있다. 꺼짐은 「UTF-8이 아니다」가 아니라 「선언하지 않았다」다
  • 그래서 선언 없는 UTF-8 아카이브가 존재할 수 있다. 명세를 어긴 것도 아니다. 켜라고 강제되지 않았기 때문이다
  • 같은 문서 4.4.17은 경로 구분자에 대해 반드시 정방향 슬래시를 쓰라고 적었다. 이쪽은 강제다. 뒤에서 이 규칙을 어긴 도구를 만난다
  • 결론: 파일명이 깨지는 것은 누구의 잘못도 아니고 명세의 여백이다. 그 여백을 도구들이 각자의 추측으로 메운다

이 구조를 알면 다음 질문이 바뀐다. 「인코딩이 뭐냐」가 아니라 「비트 11이 켜져 있냐, 그리고 그 바이트는 무엇이냐」가 된다. 두 질문 다 아카이브를 열어 보면 즉시 답이 나온다.

2. 파일명 필드를 바이트로 뜯는다

먼저 재료를 만들었다. 같은 이름을 두 인코딩으로 적으면 바이트가 이렇게 다르다.

--- 2-1. one name, two encodings ---
name : 보고서.txt
  utf-8 bytes : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74   (13 B)
  cp949 bytes : BA B8 B0 ED BC AD 2E 74 78 74            (10 B)

name : 1분기 매출.xlsx
  utf-8 bytes : 31 EB B6 84 EA B8 B0 20 EB A7 A4 EC B6 9C 2E 78 6C 73 78   (19 B)
  cp949 bytes : 31 BA D0 B1 E2 20 B8 C5 C3 E2 2E 78 6C 73 78               (15 B)

한글 한 글자가 UTF-8에서 3바이트, cp949에서 2바이트다. 그래서 같은 이름이 13바이트짜리와 10바이트짜리로 두 종류 존재한다. 이 두 바이트열을 각각 아카이브에 담고, 중앙 디렉터리를 손으로 파싱했다. 먼저 옛 도구가 만드는 형태다.

이 출력이 진단의 전부다. 세 줄만 보면 된다.

  • 플래그가 0x0000이다. 비트 11이 꺼져 있으니 이 아카이브는 인코딩을 선언하지 않았다
  • 이름 바이트가 BA B8 B0 ED BC AD다. UTF-8로 디코드하면 예외가 나고 cp949로는 깔끔하게 읽힌다. 바이트가 인코딩을 말해 준다
  • 확장 필드가 없다. 이름을 한 번 더 실어 둔 자리도 없다
  • 결론은 확정적이다. 선언 없는 cp949 아카이브다. 한국어 윈도우에서는 정상으로 보이고 그 밖에서는 깨진다

여기서 눈여겨볼 것이 as cp437 줄이다. 파일명 바이트를 도스 시대 기본 코드페이지로 읽으면 ║╕░φ╝¡.txt가 된다. 서론에서 본 그 문자열이다. 즉 이 글의 첫 증상은 「선언 없는 cp949 아카이브를 명세의 기본값대로 읽은 결과」였다.

3.1 선언하지 않은 UTF-8이라는 함정

세 번째 경우가 있다. 바이트는 UTF-8인데 비트 11을 켜지 않은 아카이브다. 이것도 명세 위반이 아니다.

=== C_utf8_noflag.zip  (141 B) ===
EOCD  entries=1  cd_offset=60  cd_size=59
--- entry 1 ---

  bit 11 (UTF-8)   : not set
  name field len   : 13 bytes
  name field hex   : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74
  as utf-8         : [보고서.txt]
  as cp949         : <UnicodeDecodeError>
  as cp437         : [δ│┤Ω│á∞ä£.txt]
  extra len        : 0 bytes  (no extra field)
  • A와 C는 플래그 값이 똑같다. 둘 다 0x0000이다
  • 그런데 이름 바이트가 다르다. A는 cp949로만 읽히고 C는 UTF-8로만 읽힌다
  • 즉 플래그만 봐서는 부족하다. 플래그가 꺼져 있을 때는 바이트의 유효성을 함께 봐야 어느 쪽인지 갈린다
  • C는 한국어 윈도우에서 오히려 깨진다. 시스템 코드페이지가 949이니 UTF-8 바이트를 949로 읽어 버린다
  • A와 C가 서로 반대 방향의 사고를 낸다는 것이 이 문제의 골치 아픈 점이다. 한쪽을 고치는 조치가 다른 쪽을 만든다

4.1 확장자가 사라지는 이유

위 표본 중 蹂닿퀬�꽌.txt는 점이 살아 있다. 그런데 실제로 아카이브를 풀어 디스크에 남은 이름은 蹂닿퀬__txt였다. 확장자가 없어졌다. 왜 그런지 바이트를 두 개씩 묶어 봤다.

--- 4-3. why the extension disappears ---
utf-8 bytes of the name : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74  (13 B)
cp949 reads two at a time:
  EB B3 -> [蹂] U+8E42
  B4 EA -> [닿] U+B2FF
  B3 A0 -> [퀬] U+D02C
  EC 84 -> <UnicodeDecodeError>
  9C 2E -> <UnicodeDecodeError>
  74 -> [t] single byte
  78 -> [x] single byte
  74 -> [t] single byte

the pair that eats the dot:
  9C 2E   the byte 2E is the '.' of .txt
          a cp949 lead byte 9C swallowed it

what the platform decoder returned for the same bytes:
  [蹂닿퀬??txt]
  U+8E42 U+B2FF U+D02C U+003F U+003F U+0074 U+0078 U+0074   (8 chars)
  chars illegal in a Windows file name : U+003F U+003F
  the extractor replaced them with underscores -> [蹂닿퀬__txt]

이 연쇄가 정확히 이렇다. UTF-8 이름을 2바이트 단위로 읽다 보니 선두 바이트 9C가 점을 짝으로 끌어갔다. 그 쌍은 유효한 글자가 아니라 물음표가 되고, 물음표는 윈도우 파일명에 쓸 수 없는 문자이므로 압축을 푸는 도구가 밑줄로 바꿨다. 결과적으로 확장자가 사라진다.

  • 「이름만 깨진 것」이 아니다. 확장자가 없어져 연결 프로그램이 사라지고, 두 번 클릭해도 열리지 않는다
  • 점이 먹히는 조건은 이름의 마지막 한글 글자의 세 번째 바이트가 cp949 선두 바이트 구간에 들어갈 때다. 이름에 따라 되기도 하고 안 되기도 한다
  • 그래서 「어떤 파일은 확장자가 남고 어떤 파일은 없어진다」는 현상이 같은 아카이브 안에서 동시에 나타난다
  • 확장자 유무로 깨짐 여부를 판단하는 스크립트는 여기서 조용히 잘못 판정한다

5. 되돌릴 수 있는가 - 바이트가 남았는지가 전부

깨진 이름을 보면 복구를 시도하고 싶다. 되는 경우와 안 되는 경우를 실행으로 갈랐다. 먼저 되는 쪽이다.

  • 5-3은 대체문자가 먹은 경우다. 대체문자는 어떤 바이트를 대신했는지에 대한 정보를 하나도 갖고 있지 않다. 10바이트가 22바이트로 늘어난 것은 정보가 늘어난 게 아니라 같은 값이 여섯 번 반복됐을 뿐이다
  • 그래서 판단 순서가 중요하다. 디스크에 풀린 이름을 보고 판단하지 말고, 아카이브 안의 바이트를 먼저 보라. 아카이브가 온전하면 다른 도구로 다시 풀면 되고, 이미 이상한 이름으로 풀어 놓은 파일들은 지우고 다시 시작하는 것이 빠르다
  • 원본 아카이브 파일을 지우지 않고 보관하는 것이 첫 번째 방어다. 아카이브가 있으면 언제든 되돌릴 수 있다

  • C는 윈도우에서 최악이다. tar는 확장자까지 날려 버렸고, Expand-Archive는 예외를 던지고 아무 파일도 풀지 않았다. 깨진 이름이라도 파일이 나오는 게 아니라 작업 자체가 실패한다
  • UnZip 6.00은 비트 11을 무시했다. B는 UTF-8이라고 명시적으로 선언했는데도 자체 문자 변환을 적용해 이름 바이트를 갈아 놓았다. 2009년 판이라 그렇다. 오래된 도구는 선언을 지켜 줄 의무를 모른다
  • 여기서 나온 아랍 문자 ٦과 ۦ는 원본과 아무 관계가 없다. 도구가 만든 바이트 D9 A6, DB A6이 나중에 UTF-8로 해석되면서 아랍 문자 영역에 떨어진 결과다. 깨진 표본에 뜬금없는 문자가 섞이는 것은 이런 이중 해석 때문이다
  • 실무 교훈은 하나다. 「깨졌다」는 신고를 받으면 상대의 도구를 먼저 물어라. 아카이브가 아니라 도구가 원인일 수 있다

  • 압축을 푸는 도구는 받은 형태를 그대로 디스크에 쓴다. 정규화해 주지 않는다. 확인한 환경에서 분해된 열 글자 이름이 그대로 남았다

  • 대응은 비교하기 전에 양쪽을 같은 형태로 정규화하는 것이다. 마지막 줄에서 정규화 후에는 같아졌다

  • 필드 구조는 버전 1바이트 + 헤더 이름의 CRC 4바이트 + UTF-8 이름이다. CRC가 있어서, 다른 도구가 헤더 이름을 고쳐 버린 경우 이 필드가 낡았다는 것을 감지할 수 있다
  • 파이썬 zipfile은 이 필드를 읽으면 헤더의 이름을 덮어쓴다. 그래서 5절의 cp437 복구 절차가 필요 없어진다
  • 다만 확인한 세 도구 중 이 필드를 쓰는 도구는 하나도 없었다. 읽기는 널리 지원되는데 쓰기는 드물다
  • APPNOTE 자신도 비트 11을 쓰면 이 확장 필드는 필요하지 않다고 적었다. 새로 만드는 아카이브는 비트 11로 가는 것이 맞다
  • 이 필드의 실용적 의미는 진단에 있다. 받은 아카이브에 이 필드가 있으면 원래 이름을 추측 없이 알 수 있다

12. 이름과 내용은 별개다

아카이브 하나 안에서 이름은 UTF-8이고 내용은 cp949인 항목을 일부러 만들었다. 이 조합이 규격상 아무 문제가 없다는 것을 확인하는 절이다. 내용 인코딩의 진단법은 cp949와 UTF-8, 두 종류의 인코딩 오류에서 다뤘으므로 여기서는 두 층이 서로 무관하다는 사실만 짚는다.

  • 항목이 가진 필드를 전부 늘어놓아도 내용 인코딩을 적는 자리가 없다. 텍스트냐 바이너리냐를 암시하는 비트 하나가 전부다
  • 그래서 「이름이 잘 보이니 내용도 괜찮겠지」는 근거가 없다. 두 층은 서로 아무 정보도 공유하지 않는다
  • 역도 성립한다. 이름이 깨진 아카이브의 내용은 온전할 수 있다. 압축 해제는 이름과 무관하게 바이트를 그대로 복원한다
  • 실무에서는 두 층을 따로 확인해야 한다. 이름은 중앙 디렉터리로, 내용은 풀어 낸 바이트로

13. 진단 절차 - 받은 아카이브가 어느 경우인가

  2. 중앙 디렉터리에서 비트 11을 읽는다. 켜져 있으면 이름은 UTF-8이고, 그래도 깨져 보인다면 원인은 아카이브가 아니라 읽는 도구다
  3. 꺼져 있으면 이름 바이트의 유효성을 본다. UTF-8로만 유효한지, cp949로만 유효한지, 둘 다인지
  4. 확장 필드 0x7075를 찾는다. 있으면 추측할 필요가 없다. 그 안에 UTF-8 이름이 들어 있다
  5. 항목 하나만 보지 않는다. 아스키 이름은 플래그가 꺼져 있고, 한 아카이브 안에 두 인코딩이 섞일 수 있다
  6. 판정이 끝난 뒤에 풀되, 원본 아카이브는 지우지 않는다. 아카이브가 있으면 다시 시작할 수 있다

둘 다 유효한 경우가 실제로 있다. 어떤 바이트열은 UTF-8로도 cp949로도 예외 없이 읽힌다. 아스키만 든 이름이 가장 흔한 예이고, 그 밖에도 겹치는 구간이 존재한다. 이때는 바이트만으로 확정할 수 없다. 유효성 검사는 후보를 줄여 주는 도구이고 결론을 내려 주지 않는다. 그래서 마지막 판단은 사람이 이름을 읽어 뜻이 통하는지 보는 것이 된다.

마무리: 명세의 여백을 규칙으로 덮는다

「UTF-8로 압축하세요」는 조언으로서 절반만 맞는다. 절반이 맞는 이유는 비트 11을 켜는 도구를 쓰면 대부분 해결되기 때문이고, 절반이 틀린 이유는 zip이 파일명 인코딩을 강제하지 않는다는 사실을 감추기 때문이다. 감추면 다음 사고를 진단할 수 없다.

실행해서 확인한 것을 다시 정리하면 이렇다. 아카이브 안의 파일명은 길이와 바이트열뿐이다. 인코딩을 알리는 수단은 비트 하나이고, 그 비트가 꺼졌을 때 무엇으로 읽어야 하는지는 명세가 정하지 않았다. 그래서 도구들이 각자 추측하는데, 윈도우 도구는 시스템 코드페이지를 적용하고 파이썬은 도스 기본값을 적용하고 옛 unzip은 자체 변환표를 적용한다. 세 추측이 모두 명세에 어긋나지 않는다.

그리고 이것이 한국에서 특히 잦은 이유도 여기 있다. cp949 시대의 파일과 관행이 아직 유통되고, 시스템 코드페이지가 949인 환경끼리 주고받는 동안에는 아무 문제가 드러나지 않는다. 문제는 받는 쪽이 다른 환경일 때만 나타나므로, 만든 쪽은 자기 아카이브가 깨진다는 사실을 알 방법이 없다. 오늘 윈도우에 기본 포함된 tar가 그런 아카이브를 만든다는 것을 확인한 것이 이 글의 가장 실용적인 결론이다.

지금 당장 할 수 있는 일이 하나 있다. 최근 대외로 보낸 아카이브를 하나 열어 비트 11을 읽어 보라. 켜져 있으면 안심해도 된다. 꺼져 있고 이름에 한글이 있다면, 그 파일을 받은 사람은 지금 깨진 이름을 보고 있을 가능성이 높고 당신에게 말하지 않았을 뿐이다.

# zip 파일명 인코딩 판별 시트

## 0. 한 줄 요약

zip은 파일명 인코딩을 명세로 강제하지 않는다. 이름은 바이트열이고, 선언 수단은 범용 목적 플래그 **비트 11** 하나뿐이다. 비트가 꺼졌을 때 무엇으로 읽는지는 도구마다 다르다.

## 1. 먼저 볼 세 가지 (압축 풀기 전)

| 볼 것 | 위치 | 의미 |
|---|---|---|
| 범용 목적 플래그 비트 11 | 중앙 디렉터리 헤더 오프셋 +8, 2바이트 리틀엔디언 | `0x0800` 이면 UTF-8 선언 |
| 파일명 필드 원시 바이트 | 헤더 +46 부터 이름 길이만큼 | UTF-8 / cp949 유효성 판정 |
| 확장 필드 `0x7075` | 이름 필드 뒤 | 있으면 UTF-8 이름이 한 번 더 들어 있음 |

## 2. 깨진 모양 판별표

| 보이는 이름 | 표본 | 원인 | 복구 |
|---|---|---|---|

| 한자 + 확장자 소실 | `蹂닿퀬__txt` | 같음. 점이 선두 바이트에 먹힘 | 아카이브에서 다시 풀 것 |

## 3. 바이트 확인 명령

```
# 아카이브 목록만 (풀지 않는다)
python -c "import zipfile,sys; z=zipfile.ZipFile(sys.argv[1]); [print(hex(i.flag_bits), i.filename) for i in z.infolist()]" archive.zip

# 파일명 필드를 16진수로
python -c "import sys; b=open(sys.argv[1],'rb').read(); i=b.find(b'PK\x01\x02'); n=int.from_bytes(b[i+28:i+30],'little'); print(b[i+46:i+46+n].hex(' ').upper())" archive.zip

# 되돌리기 (도구가 cp437을 적용한 경우)
python -c "print('SEEN'.encode('cp437').decode('cp949'))"

# 이름 바이트가 어느 인코딩으로 유효한지
python -c "b=bytes.fromhex('BAB8B0EDBCAD'); [print(e, (lambda: b.decode(e))() if True else '') for e in ('utf-8','cp949')]"
```

## 5. 배포 시 결정 항목

- [ ] 만드는 도구를 **비트 11을 켜는 것으로 고정**했다
- [ ] 아카이브 생성을 스크립트 하나로 묶어 사람이 도구를 고르지 않게 했다
- [ ] 대외 배포용 이름은 **아스키로 제한**하거나, 한글 허용 시 규칙을 문서에 적었다
- [ ] 이름을 **조합형으로 정규화**해 담았다
- [ ] 경로 구분자가 `2F` 인지 확인했다
- [ ] **모든 항목**의 플래그를 검사했다 (첫 항목만 보지 않는다)
- [ ] 목록 파일이나 매니페스트를 함께 넣어 이름 의존을 줄였다
- [ ] 원본 아카이브를 보관한다 (다시 풀 수 있는 유일한 경로)

## 6. 하지 말 것

- 판정 전에 **압축을 푸는 것** — 잘못된 이름으로 디스크에 쓰면 복구 경로가 좁아진다
- **첫 항목만 검사**하는 것 — 아스키 이름은 플래그가 꺼져 있고 항목별 혼용이 가능하다
- **확장자 유무로 깨짐을 판정**하는 것 — 점이 선두 바이트에 먹혀 사라질 수 있다
- 이름 필드만 **바이트 편집**으로 고치는 것 — 로컬 헤더와 중앙 디렉터리, 오프셋이 어긋난다
- 「예외가 안 났으니 이 인코딩이다」 — 두 인코딩 모두로 유효한 바이트열이 존재한다
- 옛 도구를 쓰는 상대에게 **확장 필드에 기대는 것** — 옵션 하나로 무시된다
- 이름이 잘 보이는 것을 근거로 **내용도 괜찮다고 추정**하는 것 — 두 층은 무관하다
