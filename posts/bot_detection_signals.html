서론: 로그의 빈칸 하나에서 시작되는 판단

가입자 목록에 매일 비슷한 시각쯤 계정이 몇 개씩 늘어 있다. 글도 안 쓰고 다시 로그인하지도 않는다. 접속 기록을 열어 보면 그 계정들이 만들어지던 요청의 User-Agent 칸이 비어 있다. 그다음에 떠오르는 생각은 대개 하나다. User-Agent가 비어 있으면 거절하자.

그 한 줄은 실제로 유령 계정을 줄인다. 동시에 아무 소리 없이 진짜 사용자 일부를 밖으로 내보낸다. 막힌 사람은 고객센터에 글을 쓰지 않고 창을 닫기 때문에, 지표에는 「차단 성공」만 남고 「잃은 사람」은 남지 않는다.

이 글은 그 한 줄을 넣기 전에 알아야 할 것을 다룬다. 클라이언트가 보내는 값으로 왜 사람과 자동화를 가를 수 없는지, 그러면 무엇을 봐야 하는지, 그리고 정확도가 아니라 틀렸을 때의 비용으로 대응 강도를 정하는 설계가 왜 실무에서 버티는지까지 간다. 공격 쪽 기법은 다루지 않는다.

1. 빈 User-Agent는 봇의 증거가 아니다

HTTP 의미론을 정의하는 RFC 9110은 10.1.5절에서 A user agent SHOULD generate a User-Agent header field라고 적는다. SHOULD이지 MUST가 아니다. 보내지 않아도 위반이 아니다.

같은 절은 a user agent MAY allow its User-Agent value to be configured by the user라고 덧붙인다. 값을 사용자가 바꾸는 것도 규격이 예정한 동작이다. 이 칸은 처음부터 클라이언트가 채우거나 비워도 되는 자리로 설계됐고, 그래서 현실의 트래픽에서 다양한 이유로 비거나 이상해진다.

로그에서 관찰되는 것흔한 원인자동화인가
값 없음브라우저가 아닌 네이티브 앱과 모바일 SDK의 연결아니다. 우리 앱 사용자다
값 없음사내 프록시·보안 게이트웨이의 헤더 정규화아니다. 기업 고객이다
단순하거나 빈 값프라이버시 확장·설정으로 값을 지운 이용자아니다. 의도적 선택이다
낯설고 오래된 문자열임베디드 기기, 스마트TV, 키오스크대체로 아니다
도구 이름이 적힌 값명령줄 도구, API 클라이언트, 연동 스크립트대개 정당한 자동화다
완전한 브라우저 문자열실제 브라우저이거나 브라우저를 구동하는 자동화이 값으로는 구분되지 않는다

표의 마지막 줄이 이 절의 결론이다. 빈 값은 자동화의 증거가 아니고, 완전한 값은 사람의 증거가 아니다. 두 방향 모두 무너져 있으므로 이 칸 하나로는 어느 쪽으로도 판정할 수 없다.

  • 보내는 것은 권고이지 의무가 아니다 - 없어도 정상 요청이다
  • 값의 내용은 클라이언트가 정한다 - 사용자 설정으로 바꾸는 것도 예정된 동작이다
  • 서버가 값을 검증할 수단이 프로토콜에 없다 - 대조할 원본이 없다

2. 위조가 자유롭다 - 주장이지 증거가 아니다

셋째 항목이 핵심이다. User-Agent는 클라이언트가 스스로 적어 보내는 자기소개이고, 서버에는 대조할 원본이 없다. 클라이언트가 보낸 값을 신뢰 경계 안쪽으로 들이면 안 되는 이유가 여기에도 적용된다. 요청 본문의 가격 필드를 믿으면 안 되는 것과 같은 이유로, 헤더의 신원 주장도 믿을 수 없다.

브라우저 문서를 만드는 쪽에서도 이 값으로 분기하는 관행을 말린다. MDN은 User-Agent 문서 상단에 브라우저마다 다른 콘텐츠를 내보내는 것이 대개 나쁜 생각인 이유를 따로 읽으라는 경고를 걸어 두었고, 이 헤더가 특정 사용자 에이전트를 식별해 지문 채취에 이용될 수 있다고 적는다.

그 결과가 값의 축소다. 브라우저들이 이 헤더에 담기는 정보를 의도적으로 줄이고, 더 필요하면 별도의 힌트 방식으로 요청하라고 안내한다. 이 문자열로 무언가를 구분하는 규칙은 시간이 갈수록 해상도가 떨어진다.

2.1 그래도 남아 있는 쓸모

쓸모가 없다는 말은 아니다. 접근을 허용하고 거절하는 단독 근거로 못 쓴다는 것이지, 값 자체는 세 자리에서 여전히 일한다.

  • 통계와 감사 - 어떤 클라이언트 구성이 서비스에 들어오는지 파악하는 용도. 판정에 쓰지 않으므로 위조 가능성이 문제되지 않는다
  • 자기를 밝히는 크롤러 식별 - 검색 크롤러는 대개 이름과 안내 주소를 값에 적는다. 다만 확인은 다른 축이 해야 한다. 구글은 검증 문서에서 역방향 조회 뒤 정방향으로 되짚는 방법과 공개된 주소 대역에 대조하는 방법을 안내한다
  • 후보 좁히기 - 어디를 더 들여다볼지 정하는 실마리. 판정은 뒤에 오는 축이 한다

정리하면 - 자기를 밝히는 봇은 이름으로 알아볼 수 있지만, 밝히지 않기로 한 자동화는 그럴 수 없다. User-Agent 기반 규칙은 정직한 쪽만 걸러 내는 비대칭을 만든다. 정직한 크롤러의 접근 정책은 robots.txt로 선언하는 편이 낫다.

3. 오차단의 비용 - 조용히 쫓아내는 사람들

차단 규칙을 평가할 때 흔히 보는 숫자는 「막은 건수」다. 이 숫자는 규칙이 옳게 일하는지는 알려 주지 않는다. 알아야 할 것은 막힌 것 중 사람이 얼마나 섞였는지인데, 그건 기본 로그에 없다. 오차단이 위험한 이유는 조용하기 때문이다.

  • 봇은 실패해도 다시 온다. 재시도가 기본값이므로 차단은 자동화 총량을 줄이는 데 생각만큼 효과적이지 않다
  • 사람은 실패하면 다시 오지 않는다. 가입 화면에서 한 번 거절당한 사람이 재시도하는 비율은 높지 않다
  • 불만이 우리에게 도달하지 않는다. 문의에는 대개 로그인이 필요한데, 가입에서 막힌 사람에게는 계정이 없다
  • 공유 주소 뒤에 사람이 많다. 통신사 단위 주소 공유와 기업 프록시 때문에 출발지 하나 뒤에 수백에서 수천 명이 있을 수 있다

여기에 접근성 문제가 겹친다. 보조 기술, 저사양 기기, 좁은 회선, 자동 완성과 비밀번호 관리자를 쓰는 이용자는 「사람답지 않은」 패턴을 자연스럽게 만들어 낸다. 판별기를 정교하게 만들수록 이 집단이 먼저 걸린다. 검증 방식이 점점 무거워지는 흐름에서 반복 지적되는 문제도 같다.

그래서 규칙을 넣기 전에 거치는 단계가 관측 모드다. 규칙을 적용하지 않고, 적용됐다면 어떤 요청이 걸렸을지만 기록한다. 하루 이틀 치를 훑어보면 우리 앱 사용자나 기업 고객이 섞여 있는지 대개 바로 보인다. 이 단계를 건너뛴 규칙은 자기가 무엇을 잘라 냈는지 알려 주지 않는다.

4. 신호를 조합한다는 것 - 행동·네트워크·시간

그러면 무엇을 보는가. 축은 크게 셋이고, 셋 다 단독으로는 약하다는 것이 전제다.

4.1 행동 - 입력의 속도와 순서

  • 사람은 폼을 위에서 아래로 한 번에 채우지 않는다. 되돌아가 고치고, 필드 사이 간격이 들쭉날쭉하다
  • 타이핑과 붙여넣기가 섞이고, 화면 밖으로 초점이 옮겨 갔다 돌아오는 일이 잦다
  • 자동화는 대개 균일하다. 다만 균일함은 비밀번호 관리자와 자동 완성에서도 나온다

4.2 네트워크와 연결 특성

  • 같은 출발지에서 짧은 시간에 반복되는 생성 요청. 개별 요청이 아니라 묶음으로 봐야 보인다
  • 선언과 동작의 어긋남. 완전한 브라우저 문자열을 보내면서 브라우저가 늘 함께 가져가는 부수 자원 요청이 하나도 없다면 그 불일치가 관찰 대상이다
  • 여기서도 단독 판정은 금지다. 출발지 하나가 사람 하나를 뜻하지 않는다

4.3 시간 분포 - 집합에서만 보이는 신호

  • 사람의 가입은 하루 곡선을 그린다. 아침에 늘고 새벽에 줄며, 요일에도 형태가 있다
  • 정확히 같은 시·분에 반복되는 생성은 사람의 리듬이 아니라 스케줄러의 리듬이다. 며칠 치를 겹쳐야 드러난다
축무엇을 보나단독으로 약한 이유겹쳤을 때 뜻하는 것
선언 값User-Agent 등 요청 헤더 구성클라이언트가 자유롭게 정한다다른 축과 어긋날 때만 의미가 생긴다
행동입력 순서와 간격의 분포보조 기술·자동 완성이 같은 모양을 만든다시간 분포와 겹치면 가능성이 오른다
네트워크출발지별 요청 묶음, 선언과 동작의 불일치주소 하나 뒤에 다수의 사람이 있다같은 출발지에 같은 시각이면 강해진다
시간 분포생성 시각의 하루·요일 분포사람도 특정 시간대에 몰릴 수 있다분 단위 반복이면 사람 설명이 어렵다

각 신호는 혼자서는 근거가 못 되고, 여러 축이 같은 방향을 가리킬 때만 강해진다. 강해졌다는 말이 「차단해도 된다」를 뜻하지 않는다는 것이 다음 절의 주제다.

5. 오탐이 비싼 쪽과 싼 쪽 - 대응 강도 설계

봇 대응이 실패하는 지점은 대개 판별 정확도가 아니라 대응이 이진이라는 데 있다. 통과 아니면 차단, 둘뿐이면 모든 판단이 사형 선고가 된다. 그러면 규칙을 느슨하게 잡을 수밖에 없고, 느슨한 규칙은 아무것도 못 막는다. 먼저 만들 것은 임계값이 아니라 단계다.

신호 강도대응틀렸을 때 사용자가 겪는 일되돌리는 비용
약함기록만 남긴다없다없다
약함~중간목록 노출을 미루고 색인에서 제외내 글이 늦게 보인다표시 상태만 되돌리면 된다
중간신규 계정의 일부 기능을 유예링크 게시나 초대를 나중에 쓴다유예를 풀면 끝난다
중간~강함사람이 확인할 대기열로 보낸다승인까지 기다린다승인 처리 시간
강함가입 거절 또는 계정 정지못 쓰고 대개 그대로 떠난다되돌려도 돌아오지 않는다

마지막 열이 설계의 전부다. 위쪽 세 줄은 틀려도 되돌릴 수 있고, 맨 아래 줄은 되돌려도 복구되지 않는다. 되돌릴 수 있는 대응부터 소진한 뒤에 마지막 줄을 꺼낸다.

임의로 만든 접근은 아니다. OWASP가 자동화 위협을 정리한 목록에서 대량 계정 생성은 OAT-019로 등재돼 있고, 권고 대응 중 하나가 limiting the functionality and/or capacity available to all newly created accounts다. 나쁜 쪽만 골라 제한하라는 것이 아니라 신규 계정 전체의 초기 권한을 낮추라는 뜻이다.

5.1 점수와 결정을 분리한다

신호 평가와 결정이 한 덩어리로 붙어 있으면 기준을 바꿀 때마다 배포를 해야 하고, 과거 요청에 새 기준을 적용해 볼 수도 없다.

// 개념 예시 - 구조를 보이기 위한 것이며 실행해 검증하지 않았다.
// 가중치와 경계값은 서비스마다 다르므로 그대로 쓰지 말 것.

score = 0
if (ua_absent)            score += 1   // 약한 신호. 단독으로는 어떤 결정도 하지 않는다
if (source_burst)         score += 2   // 같은 출발지에서 짧은 시간에 반복
if (schedule_like_timing) score += 2   // 집합을 겹쳐야 보이는 신호
if (declared_vs_observed) score += 3   // 브라우저라 선언했으나 부수 요청이 없다

decision =
    score >= 6 ? "queue_for_human_review"   // 사람이 본다
  : score >= 3 ? "limit_new_account"        // 되돌릴 수 있는 제한
  :              "log_only"                 // 기록만

// 차단은 이 표에 없다. 자동으로 내리는 최고 등급은 사람에게 넘기는 것까지다.

마지막 주석이 요지다. 자동으로 내릴 수 있는 가장 강한 결정을 「사람에게 넘김」으로 두면 오탐이 사용자에게 직접 닿지 않는다.

6. 나중에 판별하려면 지금 무엇을 남기나

봇 판별은 대개 사후에 이뤄진다. 이상한 계정이 눈에 띄고 그다음에 로그를 연다. 그때 답을 낼 수 있느냐는 오늘 무엇을 남겼느냐로 정해진다. 양이 아니라 구조의 문제다.

  • 시각은 밀리초까지. 시간 분포를 보려면 초 단위로는 부족하다. 서버들의 시계가 맞는지도 확인한다
  • 요청과 이벤트를 잇는 상관 키. 계정 생성이 어느 요청에서 나왔는지 이어지지 않으면 맥락을 복원할 수 없다. 이 키 하나가 조사 시간을 며칠에서 몇 분으로 줄인다
  • 규칙 식별자와 점수와 결정을 함께. 결과만 남기면 규칙을 고칠 수 없다. 어떤 규칙이 몇 점을 줬고 무엇을 결정했는지가 같은 줄에 있어야 한다
  • 관측 모드의 가상 판정. 막지 않고 「막았을 것」이라고만 표시한 기록
  • 헤더는 값이 아니라 형태로. 어떤 헤더가 있었고 집합이 어떤 모양이었는지가 판별에 쓰인다. 값 전체를 남기면 개인정보만 늘어난다

남기지 말아야 할 것도 분명하다. 입력 내용 자체는 남기지 않는다. 필요한 것은 간격의 분포이지 무엇을 쳤는가가 아니다. 로그 등급을 정할 때 쓰는 기준이 여기에도 적용된다. 답할 질문을 먼저 정하고 그것에 필요한 것만 남긴다.

7. 개인정보 관점 - 판별용 값도 개인정보다

봇을 가려내려고 모은 값이라는 이유로 개인정보 규율에서 빠지지 않는다. 오히려 더 예민하다. 판별력을 올리는 방향과 식별력을 올리는 방향이 사실상 같기 때문이다.

유럽 일반 개인정보 보호 규정은 전문 30항에서 이 점을 직접 말한다. 자연인은 기기·도구·프로토콜이 제공하는 온라인 식별자와 결부될 수 있고 여기에 internet protocol addresses, cookie identifiers 같은 것이 포함되며, 이런 흔적이 다른 정보와 결합해 프로파일을 만들고 개인을 식별하는 데 쓰일 수 있다는 내용이다.

한국 개인정보 보호법도 같은 방향이다. 제3조는 처리 목적을 명확하게 하고 그 목적에 필요한 범위에서 최소한의 개인정보만 수집하도록 하며 목적 외 활용을 막는다. 제21조는 목적을 달성해 불필요해졌을 때 지체 없이 파기하고 복구·재생이 되지 않도록 조치하도록 한다.

7.1 설계로 옮기면 네 가지

  • 목적을 적는다. 「자동 가입 방지」처럼 좁게 쓰고, 그 값을 개인화나 마케팅에 돌려 쓰지 않는다
  • 보관 기간을 자른다. 시간 분포를 보는 데는 몇 주면 충분하다. 원문 값을 1년씩 들고 있을 이유는 대개 없다
  • 해상도를 낮춘다. 정확한 밀리초 대신 구간, 정확한 주소 대신 대역 단위로 두어도 「반복되는가」는 그대로 보인다
  • 처리방침에 쓴다. 무엇을 왜 얼마나 모으는지 적을 수 없다면, 그 수집을 다시 봐야 한다는 신호다

지문 정밀도를 계속 올리는 방향은 이 규율과 부딪힌다. 세션 전체의 행동을 보는 방식이 논쟁이 되는 지점도 여기다.

실무 기준 하나 - 새 신호를 추가할 때마다 「이 값이 유출되면 이용자에게 어떤 피해가 가는가」를 먼저 답해 본다. 답이 「기기와 습관이 드러난다」이면 그 신호는 얻는 판별력에 비해 비싸다.

8. 신호보다 먼저 흐름을 고치는 쪽

지금까지가 판별의 이야기였다면, 이 절은 판별할 일을 줄이는 이야기다. 그리고 대개 이쪽이 훨씬 싸다.

자동 가입이 대량으로 생기는 서비스를 열어 보면 계정 생성이 사용자의 명시적 동작보다 앞에 놓여 있는 경우가 많다. 앱이 켜질 때, 화면이 처음 열릴 때 익명 계정을 먼저 만들고 나중에 정보를 채우는 구조다. 편리하지만 대가가 있다. 링크를 여는 모든 것이 가입자가 된다. 미리보기를 만드는 쪽도 색인을 만드는 쪽도 포함된다. 공격이 아니라 그냥 웹의 일상이다.

고치는 방향은 판별기를 붙이는 것이 아니라 순서를 바꾸는 것이다. 계정 생성을 동의하고 시작한다는 명시적 동작 뒤로 옮기면 자동 방문은 계정을 만들지 않는다. 판별할 대상이 사라지므로 신호가 정확할 필요도 없어진다. 이건 보안 조치이기 전에 측정 문제다. 가입 수가 부풀어 있으면 전환율도 활성 사용자 수도 틀린 값이 된다. 고친 뒤 가입 수가 줄어드는 것은 손해가 아니라 숫자가 정직해지는 것이다.

일반화하면 이렇다. 상태를 바꾸는 동작을 자동 요청이 우연히 통과할 수 있는 자리에 두지 않는다. 열람만 해도 카운터가 오르는 화면, 미리보기 요청만으로 알림이 나가는 흐름, 링크를 여는 것만으로 초대가 소모되는 설계가 전부 같은 문제를 안고 있다.

2026년 8월 국내 개발자 커뮤니티에 이 문제를 3주간 추적한 기록이 올라왔다. 익명 커뮤니티 운영자가 크롤러 이름을 막는 규칙과 빈 User-Agent를 거절하는 규칙을 차례로 넣었지만 실제 앱 사용자가 함께 막히는 부작용을 겪었고, 마지막에 동의 버튼을 누르기 전에는 연결과 계정 생성을 하지 않도록 흐름을 바꿔 해결했다는 내용이다. 결론이 신호 목록이 아니라 흐름 변경이었다는 점이 이 기록의 값어치다.

9. 확인하지 못한 것

  • 자동화가 트래픽에서 차지하는 비율이나 특정 방식의 탐지율은 넣지 않았다. 공개 수치는 측정 주체와 정의와 모수가 제각각이고 자사 제품 효과를 보이려 만든 자료가 많다
  • 상용 봇 관리 제품의 성능은 비교하지 않았다. 판매자와 독립적으로 같은 조건에서 측정한 공개 자료를 확인하지 못했다
  • 실시간 통신 라이브러리가 어떤 조건에서 User-Agent를 보내는지는 구현과 전송 방식에 따라 달라진다. 공개된 운영 기록의 사례로만 다뤘고 일반 동작으로 단정하지 않았다
  • 본문의 코드 조각은 구조를 보이기 위한 개념 예시이며 실행해 검증하지 않았다

10. 자주 묻는 질문

빈 User-Agent는 봇이라고 봐도 되나?

아니다. HTTP 규격은 이 헤더를 권고로 두었을 뿐이고, 값을 사용자가 바꾸는 것도 예정된 동작이다. 빈 값은 「봇이다」가 아니라 「브라우저다운 자기소개가 없다」는 관찰이고, 다른 축과 겹칠 때만 의미를 가진다.

그러면 User-Agent는 아예 쓸모가 없나?

접근을 막고 허용하는 단독 근거로 못 쓴다는 뜻이다. 통계와 감사에는 충분하고, 자기를 밝히는 크롤러를 알아보는 데도 쓰인다. 다만 확인은 역방향 조회나 공개 주소 대역 대조가 해야 한다.

신호 몇 개가 겹치면 차단해도 되나?

개수로 정할 문제가 아니다. 기록만 남기기나 신규 계정 기능 유예처럼 되돌릴 수 있는 대응은 신호가 약해도 걸 수 있다. 가입 거절처럼 사용자가 그대로 떠나는 대응은 여러 축이 같은 방향을 가리킬 때만 쓴다.

봇을 가려내려고 모은 주소와 헤더도 개인정보인가?

그렇게 다루는 편이 맞다. 유럽 규정은 프로토콜 주소와 쿠키 식별자가 개인 식별에 쓰일 수 있다고 명시하고, 국내법도 최소한만 수집하고 불필요해지면 지체 없이 파기하도록 한다. 목적을 좁게 적고, 보관 기간을 자르고, 해상도를 낮춘다.

자동 가입을 줄이는 가장 값싼 방법은 무엇인가?

판별기를 붙이기 전에 계정이 만들어지는 지점을 옮기는 것이다. 명시적인 사용자 동작 뒤로 생성을 밀면 자동 방문은 계정을 만들지 않고, 판별할 대상 자체가 줄어든다.

11. 결론 - 오늘 정할 세 가지

첫째, 지금 있는 차단 규칙을 관측 모드로 하루만 돌려 본다. 막지 말고 걸렸을 목록만 모아 훑는다. 그 목록에 우리 앱 사용자나 기업 고객이 보이면 그 규칙은 이미 사람을 자르고 있었던 것이다.

둘째, 통과와 차단 사이에 단계를 하나 만든다. 신규 계정의 초기 권한을 낮춰 두는 것이 가장 손이 덜 간다. 이 한 단계가 생기면 판별기가 어설퍼도 사용자가 다치지 않는다.

셋째, 계정이 어느 지점에서 만들어지는지 코드에서 확인한다. 사용자의 명시적 동작보다 앞에 있으면 그것부터 옮긴다. 판별기 하나 붙이는 것보다 이쪽이 대개 더 적은 코드로 더 많은 문제를 없앤다.

가장 흔한 착각은 정확한 신호를 찾으면 문제가 끝난다는 생각이다. 클라이언트가 보내는 값은 검증할 수 없고, 행동과 시간은 사람 쪽에도 예외가 많다. 완벽한 신호는 오지 않는다. 대신 틀려도 되는 구조는 오늘 만들 수 있다. 그게 오래 버티는 순서다.
