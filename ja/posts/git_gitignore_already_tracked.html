.gitignore に入れたのにコミットされ続ける - すでに追跡中のファイル

ルールが間違っているのではなく順序が間違っている。外す方法と、外しても履歴には残るという問題

2026年9月1日 開発・インフラ

設定ファイルが一つ、いつもコミットに付いてくる。名前を .gitignore に書き、ファイルを直し、git status を打つ。そのままだ。打ち間違いを疑って書き直し、スラッシュを付けたり外したり、アスタリスクを入れてみる。それでもそのままだ。

ここで多くの人はパターン構文を検索し始める。ところがこの症状の大半は構文の問題ではない。ルールが間違っているのではなく、ルールを書いた時点が遅かったのだ。この記事ではその理由を一時的なリポジトリで再現して見せ、外すコマンドと、そのコマンドにはできないことまで整理する。最後の部分が最も重要だ。

以下の出力はすべて、一時ディレクトリに新しく作った空のリポジトリで実際に実行して得たものだ。コマンドの一部は取り消せないので、読みながら試すときも実際の作業リポジトリではなく、捨ててよいディレクトリで行うほうがよい。

実行環境

この記事の出力はすべて以下の環境で得た。Git 自体の動作はプラットフォームに大きく左右されないが、改行の扱いやパスの表記のようにシェルと OS によって変わる部分があるので明記しておく。

  • OS - Windows 10 Pro (ビルド 10.0.19045)
  • シェル - Git Bash (GNU bash 5.2.37(1)-release, x86_64-pc-msys)
  • Git - git version 2.48.1.windows.1
  • リポジトリ - 一時ディレクトリに git init -b main で新しく作った空のリポジトリ。実際の作業リポジトリには手を付けていない

Linux や macOS の bash・zsh でも以下の出力はほぼそのまま再現される。差が出うるのは二か所だ。ファイル名の大文字小文字の区別(Windows と既定設定の macOS は区別しないため Build/ と build/ が同じものとして扱われることがある)、そして core.autocrlf だ。後者は結果がぶれないように false に固定した。

再現 - すでにコミットされたファイルはルールを見ない

言葉で説明するより一度動かすほうが早い。空のリポジトリを作り、設定ファイルを一つコミットし、その次に .gitignore を書く。現実で起こる順序とまったく同じだ。

$ git init -b main demo && cd demo
$ echo 'API_KEY=placeholder' > config.local.json
$ git add -A && git commit -m "initial commit"

# ここまでは何の問題もない。ここでルールを掛ける。
$ echo 'config.local.json' > .gitignore
$ git add .gitignore && git commit -m "add gitignore"

# そしてそのファイルを直す。
$ printf 'API_KEY=changed-secret\n' > config.local.json
$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   config.local.json

no changes added to commit (use "git add" and/or "git commit -a")

ルールは確かに書いてあるのに modified: config.local.json がそのまま出る。理由はインデックスを覗けばすぐに見える。

$ git ls-files
.gitignore
README.md
config.local.json
src/app.js

$ git check-ignore -v config.local.json
$ echo $?
1

git ls-files はインデックスに登録されたパス、つまり現在追跡中のファイル一覧を出力する。ここに config.local.json が堂々と入っている。そして git check-ignore は何も言わずに終了コード 1 を返す。ルールがないからではなく、追跡中のパスは無視判定の対象ではないので検査を飛ばしたのだ。この沈黙は後の診断の節で改めて扱う。

  • 症状は「ルールを無視する」に見えるが、実際はルールを読みもしない状態だ
  • パターンを十回直しても結果が同じなら、構文をさらにいじるのは時間の無駄だ。まずインデックスを見る
  • 判別は一行で終わる。git ls-files にそのパスがあれば原因は確定だ

なぜそう設計されたのか

公式ドキュメントはこの動作を最初の一文に明記している。gitignore のドキュメントは「意図的に追跡しないファイルを指定する。すでに Git が追跡中のファイルは影響を受けない」で始まる。例外的な動作ではなく宣言された仕様だ。

なぜこう決めたのかは逆の場合を想像すると腑に落ちる。.gitignore に一行足すだけで、すでにリポジトリの一部であるファイルが静かに抜けるとしたら、テキスト一行がバージョン管理対象の削除命令になるわけだ。*.conf のような広いパターン一つで数十個の追跡ファイルが一度に履歴から離脱しうる。しかもこのファイルはコミットされてチーム全体に伝播する。一人の都合のための一行が、他人のリポジトリでファイルを落としては困る。

そこで Git は二つを分離した。何を新たに入れないかは設定ファイルが決め、すでに入っているものを取り出す作業は明示的なコマンドでのみ行えるようにした。ドキュメントの NOTES の節もこの順序を案内している。追跡をやめるには git rm --cached でインデックスから消し、その次に .gitignore に名前を書いて再び入らないようにせよ、ということだ。

  • 設定ファイルは未来に対するルールであり、すでに存在する履歴に遡及しない
  • 履歴から何かを抜くのは取り消しにくい動作なので、別のコマンドを要求する
  • この分離のおかげで .gitignore を誤って広く書いても、最悪の結果は「新しいファイルが拾われない」で止まる

外す方法 - git rm --cached

追跡をやめるコマンドは一つだ。git rm --cached だ。インデックスからのみ項目を削除し、作業ディレクトリの実ファイルには手を付けない。先ほどのリポジトリで続けて実行するとこうなる。

$ git rm --cached config.local.json
rm 'config.local.json'

$ ls -1
README.md
config.local.json
src

$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	deleted:    config.local.json

$ git commit -m "stop tracking config.local.json"
$ printf 'API_KEY=another-change\n' > config.local.json
$ git status --short

$ git check-ignore -v config.local.json
.gitignore:1:config.local.json	config.local.json

順に読むとこうだ。rm --cached の直後、ファイルはディスクにそのまま残っており(ls -1 の出力に残っている)、インデックスでは削除としてステージされる。コミットを終えたあとに同じファイルを直しても git status --short は何も出力しない。そしてここでようやく check-ignore が口を開く。どのルールがこのパスを捕まえたのかを行番号まで教えてくれる。

注意 - --cached を落とした git rm パス は、インデックスと作業ディレクトリのファイルを一緒に削除する。コミットされていない内容が入っていたローカル設定ファイルだったなら復旧の方法がない。この記事で扱う目的では --cached が必ず付いていなければならない。

ディレクトリをまるごと外すときは -r が必要だ。付けないと Git が拒否する。実行する前に --dry-run で対象一覧を先に見る習慣がよい。

$ git rm --cached node_modules
fatal: not removing 'node_modules' recursively without -r

$ git rm -r --cached --dry-run node_modules
rm 'node_modules/pkg/index.js'

$ git rm -r --cached node_modules
  • --cached - インデックスからのみ削除する。作業ディレクトリのファイルは残る
  • -r - ディレクトリを対象にするときに必要だ。ないと fatal で拒否される
  • --dry-run - 一覧だけ出力し、実際には何も変えない
  • 削除をコミットして初めて効果が確定する。それまではインデックスにのみ反映された状態だ

一度に片づける定番と、その代償

追跡をやめるべきファイルが複数あるときによく使われる方法がある。インデックスをまるごと空にして詰め直すのだ。空にしたあと git add . で入れ直すと、その時点で有効な .gitignore のルールが適用され、無視対象だけが自然に抜ける。

$ git rm -r --cached . --dry-run
rm '.gitignore'
rm 'build.log'
rm 'src/app.js'

便利だが条件が一つ付く。コミットされていない変更が一つもない状態でだけ使うべきだ。インデックスを空にして詰め直す動作は無視ルールだけをふるい落とすのではなく、その瞬間に作業ディレクトリにあるすべての状態をそのまま入れてしまうからだ。以下はコミットされていない編集が一つある状態で定番を実行した結果だ。

$ echo 'app-edited-but-not-committed' > src/app.js
$ git status --short
 M src/app.js

$ git rm -r --cached .
$ git add .
$ git status --short
D  build.log
M  src/app.js

$ git diff --cached --stat
 build.log  | 1 -
 src/app.js | 2 +-
 2 files changed, 1 insertion(+), 2 deletions(-)

意図したのは build.log の追跡解除一つだけなのに、まだ検討していない src/app.js の編集が同じコミットに混ざった。ファイルが数百個のリポジトリならコミットメッセージと実際の内容が食い違い、あとから原因を探しにくくなる。だから順序はこう組む。

  • まず git status がきれいかを確認する。残った変更はコミットするか別に取っておく
  • --dry-run で一覧を見る。想定より多く出るならルールが広すぎるという合図だ
  • 対象が数個だけなら定番ではなくパスを一つずつ指定する。事故の範囲がそのパスに限定される
  • コミット前に git diff --cached --stat で何が入ったかを確認する

外しても履歴には残る

ここがこの記事で最も重要な部分だ。git rm --cached はそのコミット以降だけファイルを除外する。過去のコミットには内容が少しも損なわれないまま残っている。インデックスから消えたことを「消えた」と読むと危険な思い違いになる。

以下はパスワードの入ったファイルを二回コミットしたあとに追跡を解除し、その次に何が読めるかを確認した結果だ。値は実験用のプレースホルダーだ。

$ git ls-files
.gitignore
src/app.js

$ git log --oneline -- config/secrets.env
295c575 stop tracking secrets.env
dec8b71 update settings
61f23fd initial commit

$ git show HEAD~2:config/secrets.env
DB_PASSWORD=placeholder-not-a-real-secret

$ git rev-list --objects --all | grep secrets.env
c6dd1f3ef86e381a694fa8c4ad29b2ea0463e33e config/secrets.env
934ceb11a04aff62ef5aaa84c79377a41d57ba15 config/secrets.env

現在の追跡一覧にはない。ところが git log はそのファイルに触れたコミットをすべて並べ、git show コミット:パス の一行で当時の内容がそのまま出力される。最後のコマンドがもっとはっきりしている。二つのバージョンのブロブオブジェクトがオブジェクトデータベースにそのまま残っており、リポジトリをクローンした人はこれも一緒に受け取る。

過去のコミットからもファイルを消すには履歴の書き換えが必要で、それは性格のまったく違う作業だ。すべてのコミットハッシュが変わるのでリポジトリをクローンしていった人が全員影響を受け、ブランチ・タグ・マージリクエストとの整合が崩れる。この記事ではそういう作業が別途必要だという事実までを押さえ、手順は扱わない。ほとんどの状況でそれは最初にやることでもない。

  • rm --cached は未来のコミットだけを変える。過去はそのままだ
  • ブランチを消したりコミットを戻したりしてもオブジェクトはすぐには消えない。reflog が残っている間は読まれ続ける
  • 履歴の書き換えはすべてのコミットハッシュを変えるので、共有されたリポジトリでは協業者全員の調整が前提だ
  • リモートにすでに上げたなら、ローカルで何をしても相手側の複製は残っていると考えるべきだ

認証情報が入ったならキーの入れ替えが先だ

パスワードや API キーがコミットに入ったのを見つけると、反射的に手が伸びるのはファイルを消すほうだ。順序が逆だ。ファイルをどれだけきれいに消してもすでに読まれた値は戻ってこない。リモートに上がったか、誰かがクローンしたか、バックアップやミラーや CI キャッシュに複製が残っているなら、その値は流出したものとして扱わなければならない。

だから優先順位は明確だ。流出した認証情報を破棄して新しく発行するのが一番目だ。新しい値が有効になった瞬間に古い値は役に立たなくなり、履歴に残っていようがいまいが危険が消える。逆に履歴のほうから手を付けると、その作業が進んでいる間も古いキーは生き続ける。

  • 1 番目 - 当該のキー・トークン・パスワードを破棄して新しく発行する。発行元のコンソールで古い値を直ちに無効化する
  • 2 番目 - その認証情報でアクセスできる場所のログを確認し、実際に使われた痕跡があったかを見る
  • 3 番目 - git rm --cached と .gitignore で同じことが繰り返されないようにする
  • 4 番目 - 必要なら履歴の書き換えを計画する。協業者の調整が済んだあとに行う

付け加えると、認証情報はそもそもファイルとしてリポジトリに置かないほうがよい。環境変数か別のシークレット管理手段を使い、リポジトリには値が空の例示ファイルだけを置く。config.example.json のように名前を分ければ、例示は追跡し実ファイルはルールで止める構成になる。

効かない理由 1 - パスのパターン

インデックスの問題ではないのにルールが効かないなら、次の候補はパターンの表記だ。紛らわしい点は二つに絞られる。前に付くスラッシュと、後ろに付くスラッシュだ。

公式ドキュメントの規定はこうだ。パターンの先頭か途中に区切り文字があると、その .gitignore があるディレクトリを基準にした相対パスになり、なければその下のどの深さでもマッチする。パターンの末尾に区切り文字があるとディレクトリのみ、なければファイルとディレクトリの両方にマッチする。

# build/ と src/build/ の二つのディレクトリがある状態

$ printf '/build/\n' > .gitignore
$ git check-ignore -v build/out.o src/build/out.o
.gitignore:1:/build/	build/out.o
# src/build/out.o は出力にない = 無視されなかった

$ printf 'build/\n' > .gitignore
$ git check-ignore -v build/out.o src/build/out.o
.gitignore:1:build/	build/out.o
.gitignore:1:build/	src/build/out.o

先行スラッシュ一つが「最上位の build だけ」と「どの深さの build でも」を分けた。次は後ろに付くスラッシュだ。cache をディレクトリにしてからファイルに変えて、同じルールを掛けてみた結果だ。

# cache がディレクトリのとき
$ printf 'cache\n' > .gitignore
$ git check-ignore -v cache/a.txt
.gitignore:1:cache	cache/a.txt

# cache がファイルのとき - 同じルールがそのまま効く
$ git check-ignore -v cache
.gitignore:1:cache	cache

# ルールの末尾にスラッシュを付けるとファイルには効かない
$ printf 'cache/\n' > .gitignore
$ git check-ignore -v cache
$ echo $?
1

# 同じルールがディレクトリには効く
$ git check-ignore -v cache/a.txt
.gitignore:1:cache/	cache/a.txt

以下はよく使う表記とその結果だ。

表記意味マッチする例マッチしない例
buildbuild という名前のファイルとディレクトリ、深さ問わずbuild, src/build名前が違うもの
build/ディレクトリのみ、深さ問わずbuild/, src/build/build という名前のファイル
/build/最上位の build ディレクトリのみ最上位の build/src/build/
*.loglog 拡張子、深さ問わずa.log, logs/b.loglog.txt
logs/*.loglogs の直下のみ。途中のスラッシュが位置を固定するlogs/a.loglogs/sub/a.log
logs/**/*.loglogs の下のすべての深さlogs/sub/a.loglogs の外のログ
  • パターンにスラッシュが一つもなければ位置が自由だ。意図より広く掛かる事故はここから出る
  • ディレクトリだけを狙うなら末尾にスラッシュを付ける。同じ名前のファイルまで捕まることを防ぐ
  • パターンはその .gitignore が置かれたディレクトリを基準に解釈される。下位ディレクトリに置かれたファイルの /foo はリポジトリの最上位ではなく、そのディレクトリの foo だ

効かない理由 2 - 否定パターンが復活しない場所

「このディレクトリは全部無視するが、このファイル一つだけ残したい」という要求はよくある。そこでディレクトリをまるごと除外し、その下のファイル一つに感嘆符を付ける。ところがこの組み合わせは動作しない。

$ printf 'logs/\n!logs/error.log\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:1:logs/	logs/error.log
# ! を書いたのに 1 行目が勝った

$ printf 'logs/*\n!logs/error.log\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:2:!logs/error.log	logs/error.log
$ git check-ignore -v logs/debug.log
.gitignore:1:logs/*	logs/debug.log

違いは logs/ と logs/* 一つだ。前者はディレクトリ自体を除外し、後者はディレクトリの中の項目を除外する。公式ドキュメントは理由を明確に書いている。親ディレクトリが除外されたファイルは再び含めることができず、性能上の理由で Git が除外されたディレクトリの中身を列挙しないため、その中のファイルに対するパターンはどこに書いても効果がない、ということだ。ディレクトリをまるごと閉じると Git はその中を覗きもしない。

二つ目の落とし穴は順序だ。無視ルールは最後にマッチしたパターンが結果を決める。例外を先に書いて広いルールをあとに書くと、例外が覆される。

$ printf '!logs/error.log\nlogs/*\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:2:logs/*	logs/error.log

同じ二行なのに順序を変えただけで結果がひっくり返った。2 行目の広いルールが 1 行目の例外を覆った。このため .gitignore は広いルールを上に、例外を下に置く順序が事実上の標準だ。

  • ディレクトリの中の例外が必要なら dir/ ではなく dir/* と書く。一文字の違いがすべてだ
  • 入れ子が深ければ段階ごとに開けてやる必要がある。dir/*、!dir/sub/、dir/sub/*、!dir/sub/keep.txt という具合だ
  • 感嘆符の行は常に、それがひっくり返そうとするルールより下に来る

効かない理由 3 - どのファイルのルールが勝ったか

無視ルールを書ける場所は一か所ではない。リポジトリの .gitignore、下位ディレクトリごとに置かれた .gitignore、.git/info/exclude、そして core.excludesFile で指定したグローバルファイルがすべて同時に働く。

公式ドキュメントが定めた優先順位は高いほうからこうだ。コマンドラインで渡したパターン、当該パスのあるディレクトリとその上位ディレクトリの .gitignore(下位に近いファイルが上位を覆う)、info/exclude、最後がグローバルファイルだ。同じ段階の中では最後のマッチが勝つ。四つの段階を順に重ねてみるとこうなる。

# 1) グローバル無視だけがあるとき (my_global_ignore の内容は *.log)
$ git config core.excludesFile my_global_ignore
$ git check-ignore -v logs/error.log
my_global_ignore:1:*.log	logs/error.log

# 2) .git/info/exclude がグローバルに勝つ
$ printf '!logs/error.log\n' > .git/info/exclude
$ git check-ignore -v logs/error.log
.git/info/exclude:1:!logs/error.log	logs/error.log

# 3) リポジトリの .gitignore が info/exclude に勝つ
$ printf 'logs/error.log\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:1:logs/error.log	logs/error.log

# 4) 下位ディレクトリの .gitignore が上位に勝つ
$ printf '!error.log\n' > logs/.gitignore
$ git check-ignore -v logs/error.log
logs/.gitignore:1:!error.log	logs/error.log

四回の実行で毎回違うファイルが判定者として指し示された。ルールを何か所かに分けて書いておいて、なぜ効かないのかと悩んでいる状況なら、この出力そのものが答えだ。

書く場所共有されるか優先順位書くのに向いているもの
下位ディレクトリの .gitignoreコミットされて共有最も高いそのディレクトリにだけ当てはまるルール
最上位の .gitignoreコミットされて共有高いビルド成果物、依存関係、秘密ファイルの名前
.git/info/exclude共有されない中くらいこのリポジトリで自分だけが使う一時ファイル
core.excludesFile のグローバルファイル共有されない最も低いエディタや OS が作る副産物
  • 同じパスに複数のルールが掛かると、下位ディレクトリのファイルが上位に勝つ。上位で塞ぎ、下位で開ける構成が可能だ
  • グローバルファイルは最も弱い。リポジトリが明示的に無視すると書いたものを、グローバル設定がひっくり返すことはできない
  • ルールが見当たらないのにファイルが無視されるなら、グローバルファイルと info/exclude を疑う。どちらもリポジトリの中には見えない場所だ

診断 - check-ignore が犯人を指し示す

前の節々で使い続けてきた git check-ignore -v が標準の診断ツールだ。パスを渡すとどのファイルの何行目のどのルールが判定したのかをタブ区切りで出力する。読むときに知っておくべき特性が三つある。

# 1) 追跡中のファイルには何も言わない
$ git check-ignore -v kept.txt
$ echo $?
1

# 2) --no-index を付けるとルールが見える
$ git check-ignore -v --no-index kept.txt
.gitignore:1:kept.txt	kept.txt

# 3) -v の終了コードは「無視される」ではなく「ルールに掛かった」だ
#    ルール: logs/* と !logs/error.log
$ git check-ignore -v logs/error.log
.gitignore:2:!logs/error.log	logs/error.log
$ echo $?
0
$ git check-ignore logs/error.log
$ echo $?
1

第一に、すでに追跡中のファイルには沈黙する。この記事の前半で見たあの沈黙だ。--no-index の説明がこの用途をそのまま書いている。git add . のようなコマンドでファイルが追跡状態になった理由をデバッグするときに使え、ということだ。出力が空なのに --no-index を付けると出てくるなら、そのファイルは追跡中であり、答えはもう出ている。

第二に、出力されたルールが感嘆符で始まるなら、そのパスは無視されない。ドキュメントの -v の説明にも「パターンが ! で始まる場合は否定パターンであり、マッチしたということはそのパスが除外されないという意味だ」と書かれている。出力があるからといって「無視された」と読むと正反対になる。

第三に、だから終了コードも注意して読まなければならない。上の実行では -v を付けたときは 0、外したときは 1 が出た。判定がひっくり返ったのではなく、-v は「ルールにマッチした」を成功と見なし、-v のない形は「実際に無視される」を成功と見なす。スクリプトで判定に使うときは -v のない形を使わなければならない。

補助のツールも二つある。git status --ignored は無視されたものまで !! の表示で見せてくれ、git ls-files -i -c --exclude-standard はルールに掛かっているのにまだ追跡中のファイルだけを選び出す。この記事の主題にぴったり合う一覧だ。

$ git status --short

$ git status --short --ignored
!! logs/
!! scratch.tmp

# *.log のルールを追加したが build.log はすでに追跡中の状態
$ git ls-files -i -c --exclude-standard
build.log
  • git check-ignore -v パス - どのルールが勝ったかを一行で答える。最初に打つべきコマンド
  • --no-index を付けて初めて出てくるなら原因は追跡状態だ。git rm --cached に進む
  • git status --ignored - 何が無視されているのかを目で確認する
  • git ls-files -i -c --exclude-standard - 片づける一覧をまるごと抜き出してくれる

空のディレクトリは追跡されない

この主題とセットで出る質問がある。ディレクトリ構造だけ作ってコミットしたのに、他の人が受け取るとそのディレクトリがないというものだ。無視ルールとは無関係だ。Git はファイルだけを記録し、ディレクトリという概念を別に保存しない。パスに含まれるディレクトリ名が副次的に再現されるだけだ。

$ mkdir uploads
$ git add uploads
$ git status --short

$ touch uploads/.gitkeep
$ git add uploads
$ git status --short
A  uploads/.gitkeep

空のディレクトリを git add してもエラーも出ず何も起こらない。中にファイルを一つ入れて初めてステージされる。.gitkeep の慣行はここから出た。Git が知っている特別な名前ではなく、ディレクトリを維持するために入れる空ファイルに付いた通称でしかない。README を入れても結果は同じだ。

  • 名前は慣習だ。ツールが特別扱いしないので、チームで一つに決めて使えばよい
  • アップロード用ディレクトリのように中身は無視するがディレクトリは残したい場合が典型的だ
  • その場合のルールは uploads/* と !uploads/.gitkeep の二行だ。前の節の理由で uploads/ と書くと例外が復活しない

リポジトリのルールと個人の好みを混ぜない

.gitignore はコミットされるファイルなので、リポジトリを受け取るすべての人にそのまま伝わる。ここに何を書くかは一人で決める問題のように見えるが、実際には協業の取り決めに近い。個人のエディタ設定を書いた瞬間、そのエディタを使わない人にも意味のない行が配布される。

基準は単純だ。誰が受け取っても同じようにできるものはリポジトリのルールに、人によって違うものは個人設定に書く。ビルド成果物や依存関係のディレクトリはどのマシンでも同じ名前でできるのでリポジトリのルールが正しい。一方でどのエディタを使うかは人によって違う。

  • リポジトリの .gitignore - ビルド成果物、依存関係のディレクトリ、ログ、実際の秘密ファイルの名前
  • .git/info/exclude - このリポジトリでだけ自分に必要なもの。実験用スクリプト、個人的なメモ
  • グローバルファイル(core.excludesFile) - エディタ設定、OS の副産物のようにすべてのリポジトリで繰り返されるもの
  • 三か所とも前の節の優先順位に従う。個人設定は最も弱く、リポジトリのルールをひっくり返せない

リポジトリの .gitignore に個人的な項目が積もるのは、たいていそれを書く別の場所を知らないからだ。.git/info/exclude があるという事実を伝えるだけで、このファイルは目に見えてすっきりする。

最初から入れる一覧とコミット前の習慣

この記事の問題はすべて順序から出る。ルールがファイルより遅く到着して起きることだ。予防も順序で行う。リポジトリの最初のコミットに .gitignore を一緒に入れることだ。言語やフレームワークごとに一覧は違うが、性格は四つに分かれる。

性格例なぜ入れるか抜かしたとき
ビルド成果物dist/, build/, target/, *.oソースからいつでも作り直せるコミットのたびに巨大な差分が出てレビューが難しい
依存関係node_modules/, vendor/, .venv/ロックファイルで再現されるので履歴に置く理由がないリポジトリの容量が数十倍になりクローンが遅くなる
ログと一時ファイル*.log, *.tmp, .cache/実行するたびに変わる値だ意味のない変更が積もり続けて実際の変更を覆い隠す
認証情報.env, *.pem, *_rsa, secrets.*一度入ると履歴から抜くのが難しいキーの入れ替え以外に解決方法がない

最後の行が最も高くつく。前の三つは気づくのが遅れても rm --cached 一回で片づくが、認証情報はそれだけでは終わらない。.env 系を最初のコミットの前に入れておくことが最も大きな値打ちを持つ。

習慣も一つ添える価値がある。git add . は楽だがルールがまだない新しいファイルをすべて入れてしまう。ルールがあれば Git が止めてくれるが、なければ静かに入る。

$ printf 'TOKEN=placeholder-not-a-real-token\n' > .env.local
$ echo 'note' > memo.txt
$ git add .
$ git status --short
A  .env.local
A  memo.txt
A  uploads/.gitkeep

# ルールがあればこう止めてくれる
$ git add logs/error.log
The following paths are ignored by one of your .gitignore files:
logs/error.log
hint: Use -f if you really want to add them.
hint: Disable this message with "git config set advice.addIgnoredFile false"

上の git add . は .env.local を何の警告もなく入れた。下はルールがあったので拒否され、本当に入れたいなら -f を使えと案内している。この対比がルールをあらかじめ入れておく理由だ。そしてどちらにせよコミットの直前に git status を一度見る習慣が最後の安全網だ。数行を読むのにかかる時間は数秒だ。

  • 新しいリポジトリの最初のコミットに .gitignore を含める。この記事の問題のほとんどが消える
  • 認証情報のパターンはプロジェクトが空のときに入れる。あとから入れては遅い
  • git add . のあとは git status --short で何が入ったかを見る
  • 拒否メッセージが出たら反射的に -f を付けない。止めた理由があるかもしれない

一枚まとめ

症状ごとにどこを見るかを整理すると以下のようになる。順に上から確認すれば、ほとんどは二行目までで原因が捕まる。

症状確認することコマンド解決

まとめ

.gitignore は追跡されていないファイルだけを無視する。一文だがこの記事の大部分がここから出る。ルールが遅れて到着したファイルはルールを読みもせず、だからパターンをいくら直しても結果が変わらない。外すコマンドは git rm --cached パス で、ディレクトリには -r が必要で、--cached を落とすとディスクのファイルまで消える。

パターン自体が問題の場合もある。先行スラッシュが位置を固定し、末尾のスラッシュがディレクトリに限定し、親をまるごと塞ぐと内側の例外が復活せず、同じ段階では最後のマッチが勝つ。ルールが四か所に散らばっていることもある。このすべての場合に git check-ignore -v の一行が犯人を指し示す。推測でパターンを直す代わりに、このコマンドを先に打つ。

そしてもう一度、git rm --cached は以降のコミットでのみファイルを外す。過去のコミットにはそのまま残り、git show の一行で読まれる。パスワードやキーが入ったなら、ファイルをどう消すか悩む前にその値を破棄して新しく発行するのが最初の手当てだ。

確認できなかったこと

  • 実験は Windows 10 の Git Bash と git 2.48.1.windows.1 でのみ回した。他の Git バージョンでは出力の文言が違うことがある。特に hint: で始まる案内はバージョンによって変わってきた部分だ
  • 大文字小文字を区別するファイルシステムでの動作の違いは直接確認できなかった。Windows では再現できない項目だ
  • 履歴書き換えツールの実際の動作と副作用は範囲から外した。共有リポジトリで行う作業なので検証に協業環境が必要で、復旧も別の主題だ
  • 大規模なリポジトリで git rm -r --cached . にかかる時間は測定していない。実験リポジトリのファイル数が少なく、意味のある数値が出ない
