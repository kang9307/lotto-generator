계기 — 코드를 생성하기 전에 요구사항과 설계 결정을 고정하는 이유

대규모 언어 모델(LLM) 기반의 코딩 에이전트가 발전하면서, 자연어 요구사항을 바탕으로 소스코드를 직접 생성하고 수정하는 속도는 획기적으로 빨라졌다. 그러나 지시문 몇 줄만으로 즉각 코드 작성에 돌입하는 방식은 프로젝트 규모가 커질수록 치명적인 한계에 부딪힌다. 에이전트는 사용자가 명시하지 않은 요구사항의 빈틈을 임의의 추론으로 채우며, 아키텍처적 트레이드오프나 비기능적 제약조건을 고려하지 않고 가장 직관적인 형태의 단기 구현을 선택하기 쉽다.

명세 없이 코드를 생성할 때 실무 프로젝트에서 발생하는 대표적인 세 가지 결함은 다음과 같다.

  • 임의 추론에 의한 요구사항 왜곡: 사용자가 명시하지 않은 예외 처리나 데이터 정밀도를 에이전트가 자체 판단으로 단순화하여 비즈니스 규칙을 훼손한다.
  • 아키텍처적 비기능 제약의 누락: 동시성 모델, 에러 바운더리, 멱등성 보장과 같은 구조적 요구사항을 건너뛰고 기능 동작에만 매몰된다.
  • 후속 세션에서의 회귀(Regression) 발생: 과거 구현의 설계 의도와 제약조건을 알지 못하는 새로운 세션이 기존 코드를 수정하다가 핵심 아키텍처를 파괴한다.

이러한 모호성은 구현 단계에서 잦은 롤백을 유발한다. 이전 글에서 살펴본 플랜 모드와 기획 문서의 관계(plan_mode_planning_vs_plan_document_2026)나 코드로부터 시스템 구조를 역산하는 에이전트 스킬(archify_code_to_system_diagram_agent_skill_2026)이 지적했듯, 에이전트가 생성한 결과물이 지속 가능하려면 실행 골격과 설계 기록이 명시적인 계약으로 남아 있어야 한다.

2026년 10월 GitHub에 MIT 라이선스로 공개된 alps-writer-plugins는 Claude Code와 OpenAI Codex 환경에서 이러한 문제를 해결하기 위해 고안된 마켓플레이스 플러그인 모음이다. 에이전트가 코드를 쓰기 전에 질문과 답변을 통해 요구사항 명세(ALPS PRD)를 확정하고, 설계 선택의 근거를 아키텍처 결정 기록(ADR)으로 구조화하여 저장소에 남기도록 강제한다.

핵심 원칙 — 복구 가능한 사실을 버리고 재현 가능한 조건만 보존한다

플러그인의 설계 철학을 관통하는 가장 핵심적인 규칙은 「복구 가능한 사실을 버리고, 재현 가능한 조건만 보존한다(preserve reproducible conditions, not recoverable facts)」는 원칙이다. 전통적인 개발 문서화의 가장 흔한 실패는 코드의 함수 목록, 변수 이름, 파일 경로 등을 문서에 장황하게 복사해 두었다가 코드가 수정되는 순간 문서가 낡아버리는 정보의 이중 관리 현상이다.

저장소 README는 어떤 정보를 문서에 남기고 어떤 정보를 코드에 맡겨야 하는지 명확한 3단계 판정 게이트를 규정한다.

  • 요구사항 게이트(Requirement gate): 해당 사실이 사라졌을 때, 향후 에이전트가 코드를 다시 생성하면 필수적인 비즈니스 값, 권한 제약, 상태 전이 규칙, 실패 보장, 경계 조건을 위반할 가능성이 있는가? 그렇다면 계약을 소유하는 수준(PRD 또는 ADR)에 반드시 보존한다.
  • 코드 독해 테스트(Code-readthrough test): 해당 사실이 필수 요구사항이 아니며, 에이전트가 기존 구현 코드, 단위 테스트, 의존성 설정 파일(Cargo.toml, package.json 등)을 읽어서 온전히 복구할 수 있는 정보인가? 그렇다면 문서에서 제거하고 오직 코드와 테스트에만 둔다.
  • ADR 진입 게이트(ADR admission gate): 소스코드 자체만으로는 왜 여러 대안 중 특정 아키텍처 방식을 선택했는지 그 이유(Rationale)를 설명할 수 없으며, 해당 사실이 바뀌면 시스템 설계 결정 자체가 변경되는가? 그렇다면 선택의 이유, 트레이드오프, 전제 가정을 ADR에 보존한다.

이 원칙에 따른 시스템 계층별 정보 보존 범위는 아래 표와 같이 엄격하게 분리된다.

문서 및 시스템 계층 보존하는 정보 (Persist) 보존하지 않는 정보 (Do not persist)
ALPS PRD (제품 요구사항) 사용자 문제, 관찰 가능한 결과, 비즈니스 계약, 성공 조건, 제외 범위(Out of Scope), 장기 시스템 제약 구체적 코드 경로, 스택 인벤토리 목록, 임시 구현 계획, 복사된 티켓 및 로그
ADR (아키텍처 결정 기록) 확정된 설계 결정, 엄격한 요구사항 계약, 선택 근거, 대안 및 트레이드오프, 구현 독립적 관찰 증거 선택된 라이브러리 및 SDK 상세, 함수 시그니처, 데이터베이스 필드 테이블, 내부 호출 흐름
코드 및 자동화 테스트 구현 구조, 식별자 명칭, 패키지 의존성, 튜닝 파라미터, 실행 가능한 검증 로직 PRD 또는 ADR 파일에 대한 역참조 주석
Issue, PR, Commit 특정 변경의 의도 및 변경 이력 제품이나 아키텍처의 정본(Truth) 역할을 대체하는 서술

산출물 구조 — ALPS PRD·Lite ALPS·ADR의 역할 분담

플러그인이 다루는 산출물은 크게 세 가지 문서 형식으로 나뉘며, 각각 명확한 용도와 수명주기를 가진다.

산출물 형식 README 명세 설명 사용 시점 및 진입 경로 미확인 항목
Full ALPS PRD 9개 섹션으로 구성된 에이전트 전용 요구사항 명세, Out of Scope 1급 포함 새로운 복합 제품 기획 시 (/alps-init) 9개 섹션의 세부 소제목 명칭 전체 목록
Lite ALPS 최소 PoC를 위한 4개 절 단순화 명세 (문제, C4 Context, 핵심 경험, 데모 시나리오) 빠른 개념 검증 및 목업 개발 시 (/lite-alps-init) 4개 절 이외의 사용자 커스텀 섹션 추가 지원 여부
ADR 단일 결정과 근거, 요구사항 계약, 대안을 보존하는 독립 기록 개별 결정 작성 (/adr-new) 또는 PRD 이관 (/feature-to-adr) 외부 ADR 뷰어와의 마크다운 메타데이터 호환 규격
.mapping.json ADR 간의 정식 키, 상태, 요약, 의존 관계(dependsOn)를 추적하는 내부 인덱스 구현 승인 및 토폴로지컬 의존성 검사 시 자동 조회 대규모 모노레포에서 매핑 파일의 분할 관리 방식
glossary.md 문서 전반에서 사용되는 특수 용어, 약어의 정의를 모은 용어집 부록 일반 언어로 설명되지 않는 도메인 용어 등장 시 다국어 도메인 환경에서의 용어집 병기 규칙

산출물 간의 기능적 경계와 규약은 다음과 같이 세부화된다.

  • Full ALPS의 엄격성: 9개 섹션과 명시적 의존 관계 그래프(6.3)를 통해 버티컬 슬라이스 기능 명세를 완성한다. 에이전트는 사용자의 승인 없이 섹션을 임의 저장할 수 없다.
  • Out of Scope의 1급 배치: 에이전트가 만들지 말아야 할 범위를 최상위 섹션으로 명시하여 프롬프트 상의 기능 과잉 팽창을 물리적으로 차단한다.
  • Lite ALPS의 PoC 최적화: C4 Context 다이어그램과 실행 가능한 데모 시나리오만을 포함시켜 최소 개념 검증 시간을 단축한다.
  • .mapping.json의 인덱스 역할: 개별 ADR의 정규 키(canonical key), 파일 경로, 현재 상태(Proposed, Accepted 등), 그리고 선행 의존 배열(dependsOn)을 기계적으로 추적한다.

ALPS(Agentic Lean Product Spec)는 인간이 아닌 AI 에이전트를 위해 고안된 PRD 포맷이다. 인간 독자는 요구사항의 빈틈을 직관으로 유추하여 메우지만, 에이전트는 모호함이 없는 명시적 조건이 주어져야만 결함 없는 코드를 작성할 수 있다. ALPS는 작성 루프를 뒤집어 에이전트가 먼저 사용자에게 초점 맞춘 질문을 던지고 사용자가 답변하는 인터뷰 방식을 취하며, 사용자의 명시적 확인 없이는 어떠한 섹션도 디스크에 저장하지 않는다.

Lite ALPS는 기획자나 제품 관리자가 빠른 PoC를 도출할 수 있도록 설계된 4개 섹션의 간소화 포맷이다. 사용자가 대상 문제와 기대 비즈니스 임팩트를 확인하면, 에이전트가 최소 솔루션, 제품 수준의 C4 Context 다이어그램, 핵심 사용자 경험, 그리고 실행 가능한 구체적 데모 시나리오를 제안하여 승인을 받는다.

ADR(Architecture Decision Record)은 adr.github.io에 정의된 표준 개념에 기반하여, 소프트웨어 시스템의 아키텍처에 중대한 영향을 미치는 기능적·비기능적 요구사항에 대한 결정과 그 근거를 기록한다. 결정이 승인되면 .mapping.json 파일에 정식 키와 의존 관계가 등록된다.

플러그인 아키텍처 — alps-writer와 adr-writer의 단방향 결합

alps-writer-plugins는 단일 모놀리식 도구가 아니라 alps-writer와 adr-writer라는 두 개의 독립된 플러그인으로 분리되어 있다.

alps-writer (PRD 작성 도구)
                      │
                      │ /feature-to-adr (단방향 계약 이관)
                      ▼
                    adr-writer  (ADR 주기 관리 도구, 완전 독립 실행형)
                      ├── /adr-new, /adr-impl, /adr-impl-refactor, /adr-impl-review
                      ├── /adr-sync (구현 드리프트 수리)
                      ├── /adr-rollup (분산된 결정 이력 통합)
                      └── SessionStart 훅 (.mapping.json 기반 컨텍스트 복원)

이 분리 구조의 핵심은 adr-writer가 ALPS를 전혀 참조하지 않는다는 점이다. adr-writer는 PRD가 없는 프로젝트에서도 완벽하게 단독 작동한다. 두 플러그인 간의 유일한 연결점은 alps-writer에서 adr-writer로 향하는 단방향 명령인 /feature-to-adr뿐이다.

  • adr-writer의 무의존성: ADR 플러그인은 ALPS PRD의 존재 여부와 무관하게 모든 프로젝트에서 독립형 아키텍처 결정 관리 도구로 실행된다.
  • 단방향 계약 이관 (/feature-to-adr): ALPS PRD 섹션 7에 정의된 각 구현 가능 기능(Feature)의 전체 계약을 1개 이상의 ADR로 넘긴다. 이때 기능 계약은 누락 없이 100% ADR로 전환된다.
  • PRD의 레거시 문서화: 이관이 완료되는 즉시 PRD는 과거의 기획 문서(Legacy planning document)로 취급되며, 이후의 실제 코드 구현과 검증은 오직 ADR의 권위(Authority)에 의해서만 통제된다.

네 가지 진입 흐름 — 기존 프로젝트 분석부터 PRD 우선 구현까지

플러그인은 프로젝트의 성격과 착수 시점에 따라 네 가지 독립된 진입 워크플로를 제공한다. Claude Code에서는 /skill-name 형식으로, Codex에서는 $skill-name 형식으로 호출된다.

  • 기존 프로젝트 도입 (Existing Project): /adr-import [경로]를 실행하면 에이전트가 기존 코드베이스의 소스, 테스트, 문서를 읽어 비즈니스 이벤트와 규칙을 도출하는 EventStorming 분석을 수행한다. 분석 결과는 단일 의도/충돌 보고서로 제시되며, 사용자가 확인하면 Proposed 상태의 ADR들이 생성되어 점진적인 ADR 주기로 편입된다.
  • PoC 명세 작성 (PoC Authoring): /lite-alps-init을 실행하여 4개 핵심 절로 이루어진 최소 PoC 범위와 실행 데모 시나리오를 대화형으로 확정한다.
  • PRD 우선 흐름 (PRD-First): /alps-init으로 완전한 ALPS 9개 섹션을 작성한 뒤, /feature-to-adr로 설계 결정을 ADR로 넘기고, 이후 구현 단계로 진입한다.
  • ADR 직접 작성 (ADR-Only): PRD 단계 없이 곧바로 /adr-new [카테고리]를 실행하여 단일 설계 결정을 작성하고 구현 사이클로 진입한다.

도구의 설치 절차는 복잡한 빌드나 npm 전역 패키지 설치 없이 마켓플레이스 명령만으로 완결된다.

실행 환경으로는 해당 코딩 CLI 도구와 함께 Node.js 24 이상이 요구된다.

실행 라이프사이클 — 토폴로지컬 의존성 게이트와 리팩토링·리뷰 루프

ADR이 작성되어 Proposed 상태가 된 이후, 실제 코드가 작성되고 승인되는 과정은 엄격한 자동화 게이트에 의해 제어된다.

가장 중요한 제약은 토폴로지컬 의존성 게이트(Topological Dependency Gate)다. 개발자가 /adr-impl [id]를 호출하면, 에이전트는 무작정 코드 작성에 착수하지 않고 .mapping.json에 정의된 dependsOn 관계를 추적한다. 만약 선행 의존 ADR 중 하나라도 Accepted 상태가 아니라 Proposed로 남아 있거나 선행 문서가 누락되어 있다면, 에이전트는 구현을 즉시 거부하고 선행 ADR의 구현을 먼저 요구한다.

선행 조건이 모두 충족되어 코드가 작성된 후에는 아래와 같은 폐루프 검증이 이어진다.

  • 초기 단위 테스트: 작성된 버티컬 슬라이스(UI → API → 데이터)에 대해 프로젝트 표준 테스트 명령을 수행한다. 이상적인 성공 케이스뿐만 아니라 모든 경계 조건(Edge cases)에 대한 테스트가 필수적이며, 단순 해피 패스 테스트만으로는 게이트를 통과할 수 없다.
  • 검증된 리팩토링 (/adr-impl-refactor): 초기 테스트를 통과하면 에이전트가 실행 효율성, 복잡도, 중복성, 재사용성을 점검한다. 동작을 파괴하지 않는 안전한 로컬 변경만 즉시 적용되며, 전후 테스트를 통해 기능 무결성을 입증한다.
  • 위험 기반 최종 리뷰 (/adr-impl-review): 변경된 코드와 ADR 명세를 대조하는 완결성 게이트다. 의사결정 원장(Ledger)과 요구사항의 충족성을 검사하며, 리뷰를 통과해야만 ADR의 상태가 비로소 Accepted로 전환된다.
  • 구현 드리프트 수리 (/adr-sync): 대규모 리팩토링이나 수동 코드 변경으로 인해 문서와 구현 간의 불일치가 발견되면, /adr-sync를 실행하여 정밀한 드리프트 수리를 수행한다.
  • 결정 이력 통합 (/adr-rollup): 하나의 논리적 결정이 여러 ADR로 쪼개져 진화한 경우, /adr-rollup을 통해 분산된 이력을 단일 결정 체인으로 안전하게 병합한다.

비침투적 하네스 — 플러그인 제거 후에도 온전히 남는 표준 마크다운

소프트웨어 공학 관점에서 도구의 도입을 망설이게 만드는 가장 큰 요인은 도구 종속성(Vendor Lock-in)이다. 특정 프레임워크나 플러그인 전용 바이너리 포맷에 데이터가 갇히게 되면 도구를 교체할 때 엄청난 마이그레이션 비용이 발생한다.

alps-writer-plugins는 자신을 제거 가능한 비침투적 하네스(A removable, non-invasive harness)로 정의한다. 플러그인이 생성하고 관리하는 모든 결과물은 일반 마크다운 파일(docs/adr/*.md, docs/adr/glossary.md, docs/adr//decision-log.md)과 순수 소스코드, 그리고 표준 JSON 파일(.mapping.json)뿐이다.

이 비침투적 설계가 보장하는 지속 가능성의 세 가지 축은 다음과 같다.

  • 표준 파일 형식 보존: 모든 설계 문서가 GitHub 웹 뷰어와 마크다운 렌더러에서 즉시 읽을 수 있는 표준 텍스트로 저장된다.
  • 숨겨진 전용 상태의 배제: 플러그인을 제거해도 저장소에 파괴적인 데이터 유실이 발생하지 않으며, 문서가 고아 상태로 남지 않는다.
  • 다양한 모델과의 상호운용성: 향후 새로운 AI 코딩 모델이 저장소에 투입되더라도 별도의 변환 없이 표준 문서를 읽고 컨텍스트를 즉시 파악할 수 있다.

확인하지 못한 것

  • 플러그인 도입 시 개발 속도나 버그 감소율에 대한 정량적 벤치마크 수치. 공식 README에는 철학과 사용법만 기술되어 있으며 계량화된 통계는 없다.
  • Claude Code 및 Codex 외에 Cursor, Windsurf, GitHub Copilot CLI 등 타사 에이전트 도구에서의 공식 지원 계획.
  • 대규모 모노레포 환경에서 카테고리별로 .mapping.json을 분할 격리하는 공식 멀티 프로젝트 구성 가이드의 유무.
  • Full ALPS의 9개 섹션 전체에 대한 세부 항목 명칭과 표준 섹션별 작성 템플릿의 전문.
  • SessionStart 훅이 지원되지 않는 구형 CLI 환경에서의 수동 컨텍스트 시딩 절차.
