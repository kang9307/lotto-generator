This article draws on LWN’s October 6, 2026 piece by Joe Brockmeier, “Last rites for Gentoo’s Chromium package,” together with Gentoo bug 982204, the mask text in Gentoo’s package database and the package-removal steps in the Gentoo developer manual. The facts stated are remarks by Gentoo maintainers and developers, or wording from Gentoo documents; figures and forecasts that are not in the sources are left out, and what could not be confirmed is gathered in the second-to-last section.

What happened — a removal procedure, not an ended project

According to LWN, Sam James, the maintainer of Gentoo’s Chromium package, declared last rites for the www-client/chromium source package on September 24, 2026. A change to package.mask with the commit message “Last rite www-client/chromium” went in the same day at 06:53 UTC, and the bug 982204 record preserves it. LWN opens by saying that Chromium’s complex build system, its many bundled dependencies and its frequent releases, together with user complaints, led the maintainers of the Gentoo Chromium package to give up on maintaining it.

Two states need to be kept apart here: “ended” and “entered the procedure to end.” Gentoo’s package database shows the notice “This package is masked and could be removed soon!” for the package, and its mask text says “Removal on 2026-10-24.” At the time of the article, then, the package is masked with removal scheduled, and removal from the tree has not been completed. In the bug, James wrote that the decision is not “final final”: the last rites could be cancelled or the package could be restored at some point, but he would not like to see that unless there is a plan for sustainable maintenance.

The scope is limited as well. This is a decision about one source package in the Gentoo tree. It is not a decision by the Chromium project, and it is not a decision by any other distribution. LWN describes Chromium as the browser of choice for many Linux users that has gained a reputation for being difficult for distributions to package and build.

How Gentoo works — Portage, ebuilds, USE flags, Binhost

LWN first explains what kind of distribution Gentoo is: one that focuses on letting users build their own software from source, using the Portage software-management tool. The components the article describes are these.

  • ebuild: text files written by Gentoo packagers in a Bash-like syntax. They contain the information Portage needs to build the software.
  • emerge: the command-line interface for Portage. Users build packages themselves with it.
  • Binhost: for some software, Gentoo also offers prebuilt binary packages through its Binhost project.
  • USE flags: the means by which a user sets compile-time options or changes a package’s configuration. The article’s examples are which optional libraries are linked and whether accompanying documentation is installed.
  • bundled-toolchain: Chromium’s -bundled-toolchain USE flag tells Portage not to use the bundled toolchain, so the system’s Clang compiles Chromium. It is optional on x86-64 and required on other architectures, since Chromium’s bundled toolchain is only shipped for x86-64.
  • No binary package: LWN notes that Chromium is currently not available as a Gentoo binary package because of problems building it with proprietary codecs.

Matt Jolly added to this in the bug record. The Chromium ebuilds were binpkg-ready, he wrote, but Portage does not currently support building it because of the way RESTRICT=bindist works, and there are several proposals to fix this. Why success on one machine is not enough is picked up through James’s explanations in the sections on procedure and on the path to the declaration. The design philosophy of the distribution is treated separately in the article on why Gentoo.

Procedure and dates — the steps of last rites

LWN compares Gentoo’s last rites with what Arch Linux, Debian, Fedora and others call “orphaning.” A package maintainer announces last rites on the gentoo-dev-announce mailing list to notify the project that the package will be unmaintained, and as an opportunity for other developers to claim maintainership. After a developer declares last rites, the ebuild is masked in Gentoo’s ebuild repository so that users will not accidentally install a package that is no longer maintained. Users who have it installed and attempt an upgrade receive a warning that it has been masked.

The Gentoo developer manual, under “Removing a package,” lists the order of steps for removing a package.

  • Make sure no dependencies in the Gentoo repository are broken by the removal.
  • Send last rites to gentoo-dev-announce and gentoo-dev.
  • Mask the package.
  • Wait 30 days (or more).
  • Remove it from the git tree unless the reason for removal has been fixed.
  • Clean up references in other ebuilds, the package.mask entry and the metadata.xml references in other packages, and close open bugs as PKGREMOVED.

The path to the declaration — September 9 to 24

LWN relays the bug record leading up to the declaration in chronological order. The quotations below are all things James, Jolly and users said in the bug, as carried by the article. Nothing is said about the user who filed the bug beyond what the article itself covers.

  • An earlier bug in August: the same user had filed a similar bug in August over the number of vulnerabilities in the Chromium ebuild, and James replied that the package had always been difficult to maintain and that “now they’ve added Go.”
  • The September 9 report: it said the latest stable version 151.0.7922.169 had 602 known vulnerabilities. The user attached an ebuild for a newer version but noted that it would not work if compiled with the -bundled-toolchain USE flag.
  • James’s first reply: “Chromium is horrible to maintain as a source package. It is easily the package in Gentoo that burns through maintainers the most.” He added that the maintainers had come close to last rites several times over the years and that help would be welcome.
  • Jolly’s reply: the maintainers are a team of volunteers doing their best, and the biggest causes of delays are “build failures, human factors, and my own limited free time.”
  • James on September 18: the submitted patches and ebuilds were “useful and appreciated,” but it was not as simple as grabbing and committing them. Users would complain, he said, if untested ebuilds broke on their systems.
  • One user’s laptop: compiling Chromium took 15 to 16 hours, so he could not test every possible USE flag.
  • The need to reverse-engineer: James wrote that if no patch against the Gentoo ebuild is submitted, the maintainers must diff the ebuilds to work out what was modified. He called it a “non-trivial amount of work” and said one cannot simply add, commit and push.
  • The declaration: on September 24 James declared last rites.

Difficulties the maintainers cited — release cadence, dependencies, source archives

What the maintainers themselves gave as reasons for the difficulty is listed below. Statements that amount to an evaluation of the Chromium project are left out; only facts as the maintainers explained them are carried over.

  • Release cadence: LWN says Chromium ships a new major branch roughly every two weeks via the stable channel and a new version every week. James said the release cycle had shortened twice since he took over the package in 2023, and Jolly wrote that it became fortnightly from September 2026.
  • Summary in the mask text: it names the increased release cadence, upstream toolchain changes, and the conflict between providing a consistent experience that avoids bundled components where possible and getting updates out in a timely manner, and it adds “Many unfixed vulnerabilities.”
  • Go dependency: James explained that the Go build had to be wrangled so it would not need network access, which is forbidden in Gentoo ebuilds.
  • Rust dependency: James said experimental Rust features can break on new releases. Jolly wrote that from milestone 152 Rust bindings became required to build Chromium.
  • Release source archives: James explained that upstream’s CI that produces release tarballs is not reliable. One maintainer sent patches to fix it, review took a long time, and it broke again a few times afterwards, with archives either not produced or produced incomplete.
  • Rust options Jolly described: teaching Rust ebuilds to fetch components for both binary and source (done), pinning Chromium to a specific older Rust and carrying additional patches, and possibly introducing a Chromium-specific Rust slot USE. The actual work, he wrote, involves reshaping a symlinked Rust sysroot until GN will accept it and regenerating the GN files with gnrt.
  • Toolchain choice: James and Jolly explained that using Google’s toolchain would be simpler but would restrict the ebuild to x86-64, losing arm64, ppc64 and the RISC-V overlay.

Time and people — figures and conditions from Matt Jolly

Jolly left a long comment on bug 982204 on September 29, and LWN quoted part of it. The figures below are values he gave, with the conditions that came with them.

  • Compile time: maintaining Chromium can take upwards of six hours each week, counting only the compilation of three channels on a ramdisk. The machine is a fast 16-core, 32-thread PC with “an absurd amount of RAM.”
  • arm64: it can take more than 12 hours on his fastest hardware. LWN said compilation takes even longer on 64-bit Arm machines.
  • Three channels: keeping up requires maintaining three channels, all the more since the cycle became fortnightly in September 2026.
  • Volunteer time: adding up rebasing patches, cherry-picking fixes, iterating on ebuild ... clean compile, identifying and fixing new bugs, working out how far Gentoo policy is violated, and automation work, he wrote that it takes “at least a business day’s worth of your free time” each week.
  • Skills needed: LWN reports that multiple maintainers familiar with C, C++, Go, JavaScript and Rust are needed. The bug record says JS/TS, and also warns that one must learn Google’s NIH tools, skills that cannot be used anywhere else.
  • Headcount: he held that at least three people are needed, writing “History has shown that one maintainer isn’t working.”
  • Whether it can be solved: he said there is no insurmountable technical issue. Jolly also wrote that the Chromium ebuild work is the groundwork needed if Gentoo ever wants to handle Electron properly.

These figures are values for the hardware and method Jolly used. Generalizations to other machines or configurations are not in the sources.

Why it cannot be kept — best effort and copying overlay ebuilds

In the bug record, one user asked whether the ebuild could stay in the tree and simply be declared maintained at “best effort” level. That question and James’s answer are the heart of the reasoning.

  • The best-effort proposal: James said he did not think so. He added that the explanation that volunteers maintain Chromium had already not been accepted.
  • Maintaining elsewhere: people are free to maintain it in another repository, he said, but then they must do the work themselves or accept someone doing it to a lower standard.
  • The Bentoo overlay: LWN reports James pointing out that creating the Bentoo ebuilds seemed to be “heavily automated” and had missed some fixes in the Gentoo version. The bug record gives an example in which an automatic nodejs bump led to reports of gn hanging.
  • One line to sum it up: “Copying ebuilds works fine until it doesn’t.”
  • The mask text: keeping it in the tree is not a matter of supplying an updated ebuild but a commitment to keep it up to date and to find a compromise between users’ expectations (such as various USE flags and not forcing all bundled components) and maintainability.
  • James’s reflection: if another distribution chooses always to use the bundled toolchain, nobody cares as long as the binary is produced, he wrote, whereas in Gentoo someone will be upset that it is impure, that their flags are not used, or that distcc no longer works.
  • Conditions for revival: someone can take it over before the last-rites period ends, or it can be restored later, but he does not want that without a plan for sustainable maintenance.

Other distributions in the article

LWN wrote that other distributions continue to supply Chromium packages, though their approach does not provide the same flexibility as Gentoo’s. The cases the article gives follow. The scope here is one package decision in Gentoo, so other distributions are carried only as far as the article goes.

  • Fedora: its package was at 154.0.8037.92, one version behind the upstream 154.0.8037.97 published on October 1.
  • Debian: the package in its security repository was the same version, and its information page showed at least 11 known CVEs addressed in 154.0.8037.97.
  • The September 18 comparison: a user noted in a comment that 153.0.8010.47 was already available in Arch Linux, openSUSE, SUSE and Ubuntu.
  • The article’s ending: LWN allowed that Gentoo might find a team willing and able to maintain the package to the standards its users expect, while writing that it seems unlikely Chromium will become any easier to maintain in the interim.

As a case outside source-build distributions, a browser project changing how it develops is covered in the article on Ladybird stopping public pull requests.

What could not be confirmed

  • The original text of the last-rites announcement on gentoo-dev-announce. The declaration itself is confirmed through LWN’s account and the commit message in the bug record.
  • What actually happens after October 24, 2026. Whether a taker appears and whether the package is removed from the tree is a matter for the future.
  • The specifics of the proprietary-codec build problem. LWN states the reason in one sentence only.
  • A separate binary package with a name like chromium-bin. It appears in none of the sources above, so it is not described. The list of packages that Jolly’s “binary ebuilds” refers to is omitted for the same reason.
  • Whether figures such as six or twelve hours hold on other hardware. The sources give only the values for the hardware Jolly used.
  • Whether the 503 state of the upstream documentation that LWN saw continues today.
