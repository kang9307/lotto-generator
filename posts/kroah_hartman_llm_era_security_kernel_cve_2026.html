발표의 배경과 핵심 질문 — 취약점 숫자와 패치의 간극

2026년 9월 하순 프랑스 파리에서 열린 커널 기술 콘퍼런스 Kernel Recipes 2026에서 리눅스 커널의 주요 서브시스템과 안정 브랜치를 총괄 관리하는 Greg Kroah-Hartman은 「Security in the LLM Age(LLM 시대의 보안)」이라는 제목으로 발표를 진행했다. 인공지능 기반 보안 분석 도구가 대규모 코드베이스에서 수십에서 수백 건에 이르는 취약점을 자동으로 발견했다고 주장하는 사례가 늘어나는 상황에서, 커널 유지보수팀이 실제 현장에서 접수한 보고서들의 기술적 실체를 검토한 결과를 공유한 것이다.

발표의 중심 질문은 간결하다. 인공지능이 찾아냈다고 주장하는 취약점의 숫자가 실제로 운영체제를 방어하기 위해 고쳐야 하는 유효한 결함의 수와 얼마나 일치하는가이다. 대규모 언어 모델(LLM)을 활용한 보안 분석 도구는 방대한 양의 개념 증명 보고서를 신속하게 생성해 낼 수 있지만, 그것이 소프트웨어의 실질적인 보안 강화로 이어지기 위해서는 보고서에 기술된 내용이 현실적인 공격 경로를 구성하는지, 그리고 제안된 코드가 또 다른 부작용을 일으키지 않는지에 대한 엄밀한 사람의 검증을 거쳐야 한다.

이 발표는 특히 Anthropic이 개발한 보안 분석 도구 Mythos가 리눅스 커널을 대상으로 제출한 79건의 취약점 보고서를 전수 조사한 데이터를 공개하면서 큰 주목을 받았다. 화려한 수식어와 장황한 설명 뒤에 숨어 있던 실제 코드의 상태를 파악하는 작업은 오픈소스 프로젝트가 마주한 인공지능 시대의 검증 비용 문제를 정면으로 드러냈다.

  • 인공지능 모델이 주장하는 취약점 총수와 실제 유효한 결함 수정의 수치적 괴리.
  • 자동 생성된 장황한 설명 문서가 유지보수자의 검토 시간을 소모시키는 현상.
  • 오픈소스 커널의 안정성을 위협하지 않으면서 새로운 도구를 수용하기 위한 기술적 기준의 필요성.

Mythos 보고서 79건의 실제 분류 — 숫자의 덧셈과 검토 결과

발표에서 공개된 자료에 따르면, Mythos 도구는 리눅스 커널에서 총 79건의 취약점을 탐지했다고 보고했다. 그러나 커널 유지보수팀이 원자료와 코드를 대조 검토한 결과, 다수의 보고서는 보안 패치가 필요한 독립적인 소프트웨어 결함으로 보기 어려웠다. 발표 슬라이드에 제시된 세부 분류 결과는 다음과 같다.

분류 항목보고서 수치커널 유지보수팀의 검토 결과 및 성격비고
세부 정보 부재24건단순히 무언가 비정상 종료(crash)되었다는 언급만 있고 재현 절차나 원인 정보가 없음검증 불가능
버그 아님14건커널 코드의 정상적인 제어 흐름이거나 정상 오류 처리 경로에 해당함오탐(False Positive)
조작된 데이터3건실제 커널 소스에 존재하지 않거나 임의로 조작된 환경 데이터를 전제함환각(Hallucination)
이미 수정됨15건최신 릴리스에서 이미 패치됨 (11건은 다른 개발자 선행 패치, 4건은 도구 측 패치)최신성 미반영
수정 필요 후보20건코드 결함은 있으나 중복이 있고 위협 모델 밖의 가정이 다수 섞여 있음세부 분기 검토

위 표의 세부 수치를 단순 합산하면 24 + 14 + 3 + 15 + 20 = 76건이 된다. 이는 발표 현장과 기술 커뮤니티에서도 지적된 부분으로, 전체 보고서 수치로 제시된 79건과 세부 분류의 합계 76건 사이에 3건의 차이가 존재한다. 발표자는 강연 중 언어 모델의 계산 오류를 가볍게 언급하며 지나갔으나, 공식적으로 그 3건이 분류 중복에 의한 것인지 단순 집계 오차인지는 구체적으로 밝혀지지 않았다. 확인되지 않은 숫자를 자의적으로 보정하지 않는 것이 이 글의 원칙이다.

나아가 수정이 필요하다고 분류된 20건의 내부 구성을 살펴보면, 커널의 일반적인 위협 모델에 들어맞지 않는 가정을 둔 경우가 다수를 차지했다. 세부 내역은 다음과 같다.

  • 악성 파일시스템 이미지를 시스템 관리자가 직접 마운트한다고 가정한 시나리오 7건.
  • 신뢰할 수 없는 원격 장치와의 SCTP 네트워킹 상황을 다룬 문제 6건.
  • 네트워크 스택 중간에 공격자가 악성 패킷을 임의 주입할 수 있다고 가정한 시나리오 2건.
  • 가상 메모리 관리자가 없는 특수 환경(NOMMU)과 관련된 문제 2건.
  • 경미한 수준의 IPv6 프로토콜 처리 결함 2건.
  • 로컬 악성 사용자의 비정상 동작을 가정한 GPU 드라이버 문제 1건.

이들 중 중복된 오류와 보안 위협으로 간주하기 어려운 비현실적 전제를 걷어내자, 최종적으로 남은 것은 「실제 버그 수정 10개」였다. 79건이라는 초기 주장 중 커널 소스 트리에 실제로 머지할 가치가 있었던 것은 약 12.6%에 불과했던 셈이다.

「커널 개발 한 시간 분량」의 의미 — 시간당 패치 반영량과 심각도

발표에서 가장 화제가 된 문구 중 하나는 79건의 소동 끝에 남은 10개의 수정을 두고 「커널 개발 한 시간 분량」이라고 표현한 대목이다. 일부 보도나 커뮤니티에서는 이 문구를 발표자 개인이 단 한 시간 만에 모든 취약점을 찾아내고 고쳤다는 뜻으로 오해하기도 했으나, 실제 발표의 취지는 전혀 달랐다.

리눅스 커널은 전 세계 수천 명의 기여자가 참여하는 초대형 오픈소스 프로젝트다. 공식 저장소에 단위 시간당 반영되는 커밋과 패치의 총량을 시간 단위로 환산했을 때, 10건 내외의 단순 코드 결함 패치는 커널 생태계 전체가 평상시 한 시간 동안 처리하는 일반적인 작업량 규모에 불과하다는 점을 짚은 것이다.

이는 두 가지 사실을 시사한다.

  • 보고된 결함들의 심각도가 커널 구조를 뒤흔들 만한 고위험 취약점이 아니라 일상적인 버그 수준이었다는 점.
  • 방대한 마케팅 수치와 달리 실질적인 엔지니어링 기여 규모는 기존 커널 개발 속도 안에서 미미한 비중에 그쳤다는 점.
  • 수정에 소요되는 시간 자체보다, 결함이 아니거나 이미 해결된 문제를 걸러내는 데 투입된 사람의 검토 비용이 훨씬 컸다는 점.

보안 패치의 중요성이 작업 시간에 의해 결정되는 것은 아니지만, 인공지능 모델이 발견했다고 선전하는 수십 건의 취약점이 실제로는 일상적인 정적 분석 도구로도 잡히는 경미한 결함들의 집합이었음을 명확히 보여주는 지표다.

LLM 보안 분석의 작동 기법과 기존 도구와의 비교 — 패턴 매칭과 Coccinelle

그렇다면 인공지능 보안 도구는 실제로 어떤 원리로 리눅스 커널의 결함을 찾아냈는가. 발표에서 밝혀진 바에 따르면, Mythos가 취한 핵심 접근법은 커널 개발자들이 과거에 수정했던 보안 패치의 패턴을 학습한 뒤, 코드베이스의 다른 영역에 여전히 동일하거나 유사한 형태의 잘못된 패턴이 남아 있는지를 탐색하는 방식이었다.

이 방식은 기술적으로 완전히 새로운 개념이 아니다. 리눅스 커널 진영에서는 수십 년 전부터 Coccinelle과 같은 시맨틱 패치 도구를 활용해 C 언어 소스 코드에서 구조적 버그 패턴을 찾아내고 대규모로 일괄 수정해 왔다. 기존 정적 분석 도구와 LLM 기반 도구의 공통점과 차이점은 명확하다.

  • 패턴 전파의 유사성: 특정 하위 드라이버에서 발견된 자원 해제 누락이나 널 포인터 역참조 패턴을 다른 드라이버로 확장해 검색한다는 점은 동일하다.
  • 퍼징과의 차이점: 퍼징(Fuzzing) 도구는 외부에서 입력을 주입할 수 있는 인터페이스(시스템 콜, 네트워크 패킷 등)로 탐색 경로가 제한되는 반면, 코드 정적 분석 모델은 직접적인 입력 경로가 없는 내부 함수도 들여다볼 수 있다.
  • 재현 환경 구성의 가능성: 발표에서는 LLM이 NOMMU 환경의 결함을 재현하기 위해 가상 머신 설정과 테스트 코드를 함께 제안한 사례를 긍정적인 활용 가능성으로 꼽았다.

즉, LLM 기반 보안 도구는 과거 패치 패턴을 다각도로 확장 탐색하고 테스트 시나리오를 구성하는 데 유용한 보조 수단이 될 수 있지만, 그 원리는 근본적으로 과거 인간 개발자들이 축적해 둔 버그 수정 데이터의 패턴 매칭에 기대고 있다는 한계도 함께 지닌다.

생성된 패치의 실증적 한계 — 대학원생 실험과 환각의 양상

발표자는 인공지능이 생성한 패치의 신뢰도를 실증적으로 검증하기 위해 대학원생 6명과 함께 진행한 별도의 실험 결과도 공유했다. 모델이 그럴듯하게 작성해 낸 패치들을 정밀하게 검토한 결과, 겉보기에 완벽해 보이는 패치의 약 절반(50%)이 심각한 오류를 포함하고 있었다는 것이다.

오류의 양상은 단순한 오타 수준을 넘어 운영체제의 동시성 모델과 실행 경로를 오해한 구조적 결함들이었다.

  • 컴파일 및 적용 실패: 최신 커널 소스 트리에 패치가 충돌을 일으키며 제대로 적용되지 않거나 빌드가 깨지는 경우.
  • 실제 원인 미해결: 겉으로 드러난 증상만 가리고 근본적인 동시성 경합이나 메모리 릭을 방치한 경우.
  • 존재하지 않는 가상 버그 수정: 코드베이스에 실제로는 존재하지 않는 취약점을 상상해 내고 이를 고치기 위한 잉여 코드를 추가한 경우.
  • 실행 불가능한 경로 전제: 조건문이나 락킹 구조상 절대 실행될 수 없는 논리적 분기를 공격 가능 경로로 단정한 경우.
  • 새로운 결함 유발: 가령 락을 해제해야 하는 자리에 mutex_unlock 대신 락 자체를 파괴하는 mutex_destroy를 호출하여 커널 패닉을 유발하는 등, 이름만 유사하고 동작이 전혀 다른 함수를 삽입한 경우.

언어 모델이 덧붙인 수십 페이지의 장황한 기술 보고서와 논리적인 설명은 패치의 정당성을 입증하는 근거가 되지 못했다. 오히려 설명 문서를 모두 제거하고 오직 패치 diff와 실제 테스트 코드만 남겨두었을 때 오류를 훨씬 빠르게 식별할 수 있었다는 점은 실무에 시사하는 바가 크다.

커널 CVE 처리량의 급증과 위협 모델의 명문화

최근 리눅스 커널을 둘러싼 보안 생태계는 CVE 발급 건수의 급증이라는 또 다른 국면을 맞이하고 있다. 발표에 따르면 리눅스 커널의 CVE 처리량은 지난해 주당 약 50건 수준에서 최근 하루 평균 33건으로 대폭 증가했다. 이와 같은 현상의 구조적 배경은 이 사이트의 기존 분석 글인 데비안 보안 업데이트의 숫자를 읽는 법 — rsync 33건과 커널 1,313건의 내막의 6절에서 상세히 다룬 커널 CNA(CVE Numbering Authority) 정책 전환과 맞물려 있다.

커널 보안팀이 외부 기관에 의존하지 않고 직접 CNA로서 잠재적 버그 수정 패치 다수에 CVE 번호를 부여하기 시작하면서, 지표상의 취약점 숫자는 과거와 비교할 수 없을 정도로 불어났다. 그러나 숫자의 증가가 곧바로 실질적인 침해 위협의 폭증을 뜻하는 것은 아니다.

이러한 혼란 속에서 외부 인공지능 도구들이 비현실적인 취약점을 대량으로 보고하는 것을 차단하기 위해, 커널 보안팀은 커널이 상정하는 공식 보안 위협 모델(Threat Model)을 문서화하여 공개했다. 예를 들어 시스템의 최고 관리자(root)가 손상되었거나 악의적으로 조작된 파일시스템 이미지를 로컬 블록 장치로 마운트하는 상황은 커널 보안의 방어 경계 안에 포함되지 않는다. 이미 root 권한을 가진 사용자는 드라이버의 취약점을 통하지 않고도 시스템을 완전히 제어할 수 있기 때문이다.

  • 위협 모델 밖의 시나리오를 전제로 한 보고서는 검토 단계에서 즉시 기각된다.
  • CVE 번호의 절대적 수량보다 해당 취약점이 요구하는 권한 수준과 공격 벡터를 구분해야 한다.
  • 안정 브랜치에 올라오는 패치들을 시스템에 신속하게 배포하고 반영하는 운영 절차가 가장 중요하다.

유지보수자의 방어책 — 패치 동봉 요구·전담 인력·불필요한 코드 삭제

인공지능 도구의 확산으로 인한 검토 부담을 완화하기 위해 리눅스 커널 유지보수팀은 실무적인 방어 수칙들을 확립해 나가고 있다. 아래 표는 기존의 일반 취약점 보고 처리 방식과 새롭게 강화된 커널 팀의 대응 기준을 비교한 것이다.

코드베이스 관리취약점 패치 누적으로 코드 복잡도 증가사용되지 않는 노후 드라이버 및 프로토콜 적극 삭제공격 표면 및 유지보수 대상 원천 축소

특히 주목할 만한 조치는 불필요한 레거시 코드의 적극적인 제거다. 유지보수팀은 실제로 최근 사용 빈도가 거의 없는 구형 드라이버를 커널 트리에서 완전히 삭제함으로써 한 번에 약 3,000줄의 소스 코드를 제거했다. 관리되지 않는 코드를 억지로 고쳐가며 떠안기보다는 코드를 지움으로써 잠재적 취약점과 인공지능의 오탐 가능성을 원천적으로 차단하는 방식이다.

또한 비공개 취약점 데이터를 다룰 때에는 외부 기업의 클라우드 서비스로 운영되는 모델에 소스 코드나 메모리 덤프를 직접 업로드하지 말고, 자체 구축된 로컬 오프라인 모델을 활용할 것을 강력히 권고했다. 자동화 도구의 보조를 받되, 최종 판단과 코드 병합의 책임은 여전히 숙련된 인간 엔지니어의 영역에 머물러야 한다는 것이 커널 진영의 일관된 결론이다.
