コードはスクリプトファイルとして保存し、powershell.exe -NoProfile -Fileで実行した。出力はWindows PowerShell 5.1(5.1.19041.6456、コンソール幅120)で得られたそのままである。比較用のbash出力は同じファイルを対象にGit Bash(GNU bash 5.2.37、GNU grep 3.0、Windows向けMSYSビルド)で得たもので、Linuxディストリビューションの出力ではない。作業フォルダーはC:\demo\tである。PowerShellセッションのPATHにはGitのusr\binが入っておらず、この条件に左右される結果は9節で別に示す。

はじめに - 同じパイプ記号、流れるものは違う

bashもPowerShellも|でコマンドをつなぐ。しかしその線の上を流れるものが違う。Microsoft Learnのabout_Pipelinesは、パイプライン演算子が前のコマンドの結果を次のコマンドへ送ると説明し、送られるのがオブジェクトだと明らかにしている。最初のコマンドが出したオブジェクトが2番目へ行き、2番目が処理したオブジェクトが3番目へ行く。同じ文書は、PowerShellのパイプラインがオブジェクト指向で生のバイトデータをサポートしないこと、標準入力(stdin)がPowerShellパイプラインの入力に接続されないことも書いている。bashのパイプがプロセスの出力テキストを次のプロセスの入力につなぐのと対照的だ。

結果は大きく分かれる。テキストパイプラインでは、すべてのツールが列の位置と区切り文字を自分で解釈する。ls -l | awk '{print $5}'の$5は「5番目の列」という約束に頼った値だ。オブジェクトパイプラインではLengthというプロパティ名で値を取り出す。この違いを理解すれば、コマンド対応表を暗記しなくても大半の翻訳ができる。逆にこの違いを知らないと、同じ名前の別名を打ったのにオプションが通らなかったり、出力は似ているのに並べ替えや比較の結果が違ったりする。

扱う軸は概念(オブジェクト対テキスト)と対応表だ。grepとawkの文法やオプション集はLinux GrepとAWK 使い方ガイドが、障害ログを集計するレシピはLinuxログ分析コマンド完全ガイドが扱う。バッチファイルやタスクスケジューラまで広げた自動化入門はWindows作業自動化入門ガイドに、WindowsにUNIXユーティリティをネイティブで入れたときPowerShellの別名と名前が衝突する問題はMicrosoft Coreutils for Windowsにある。

実習に使ったログファイルapp.logは12行だ。以降の集計はすべてこのファイルを対象にする。同じフォルダーにはold.log(3行)、readme.txt(helloの1行)、2,000文字のnotes.md、名前に角括弧を含むfile[1].txt、サブフォルダーsub(中にdeep.log)がある。

以下で繰り返し確かめる違いは5つにまとめられる。

  • パイプで流れるのが文字列ではなくオブジェクトである。
  • ワイルドカードとオプションを解釈する主体が、シェルではなく各コマンドレットである。
  • 大文字小文字の既定値がgrepと逆である。Select-Stringと比較演算子は既定で大文字小文字を区別しない。
  • 別名がbashのコマンド名と同じでも、オプション体系はbashではない。
  • オブジェクトを文字列に変える瞬間に、表示幅のせいで値が切れることがある。

ls | grepがWhere-Objectに変わる理由 - 出力は文字列ではない

最初の対応は、ファイル一覧から.logで終わるものだけを選ぶことだ。bashでは一覧のテキストから行を選ぶ。

$ ls | grep '\.log$'
                    app.log
                    old.log

PowerShellでは、Get-ChildItemが出したオブジェクトのNameプロパティで絞り込む。

Get-ChildItem | Where-Object { $_.Name -like '*.log' } | Select-Object Name, Length | Format-Table -AutoSize
Name    Length
                    ----    ------
                    app.log    532
                    old.log     36

表示された表はテキストだが、パイプを流れている間はオブジェクトだった。Where-Objectがしたのは、行の文字列を走査することではなく、オブジェクト1つ1つのNameプロパティをワイルドカードパターンと比べることだ。この点は実行で確かめられる。

$first = Get-ChildItem | Select-Object -First 1
                    $first.GetType().FullName
                    (Get-ChildItem | ForEach-Object { $_.GetType().Name } | Group-Object | ForEach-Object { $_.Name + ' x' + $_.Count }) -join ', '
                    Get-ChildItem -File | Get-Member -MemberType Property | Where-Object { $_.Name -in 'Name','Length','LastWriteTime','Extension' } | Select-Object Name, Definition | Format-Table -AutoSize
System.IO.DirectoryInfo
                    DirectoryInfo x1, FileInfo x5
                    
                    Name          Definition
                    ----          ----------
                    Extension     string Extension {get;}
                    LastWriteTime datetime LastWriteTime {get;set;}
                    Length        long Length {get;}
                    Name          string Name {get;}

最初の要素はSystem.IO.DirectoryInfoで、一覧全体はディレクトリオブジェクト1個とファイルオブジェクト5個だ。ファイルオブジェクトには、文字列ではなくLength(long)やLastWriteTime(datetime)のような型を持つプロパティがある。ここから2つのことが導かれる。第一に、列番号を数えるawkが要らない。第二に、サイズの比較と並べ替えが文字順ではなく数値順で行われる。

2つ目の対応は、サイズの列だけを取り出すことだ。bashではls -lの5番目の列をawkで取る(ディレクトリの行は除外した)。

$ ls -l | awk '$1 !~ /^d/ && NF > 2 {print $5}'

                    9
                    2002
                    36

Get-ChildItem -File | Select-Object -ExpandProperty Length
532

値は同じだが、得る方法が違う。前者はls -lの出力形式が変わると壊れ、後者はプロパティ名がある限り形式に左右されない。サイズ順の並べ替えでは差がもっとはっきりする。数値の列を並べ替えるとき、bashのsortは既定が文字順なので-nを付ける必要がある。

$ printf '10\n9\n100\n' | sort
                    10
                    100
                    9
                    $ printf '10\n9\n100\n' | sort -n

                    10
                    100

PowerShellのSort-Objectは入力の型に従う。文字列'10','9','100'は文字順に並び、数値に変えた値は数値順になる。ファイルオブジェクトのLengthはもともとlongなので、オプションなしで数値順になる。

'10','9','100' | Sort-Object
                    '10','9','100' | Sort-Object { [int]$_ }
                    Get-ChildItem -File | Sort-Object Length -Descending | Select-Object -First 2 Name, Length | Format-Table -AutoSize
10
                    100
                    9

                    10
                    100

                    ----     ------
                    notes.md   2002
                    app.log     532

前の2つの結果は、文字列のときbashと同じ順序で(10, 100, 9)、型を変えると-nの並べ替えと同じになる(9, 10, 100)。3つ目の結果は、最も大きいファイル2つを名前とサイズで示している。オブジェクトを文字列に変えるのは、変換が起きる場所だけだ。ファイルオブジェクトを文字列の中に入れると、名前だけが残る。

Select-Stringはgrepではない - MatchInfoと既定値の違い

Select-Stringのドキュメントは、このコマンドレットを「UnixのgrepやWindowsのfindstr.exeと同じように使える」と紹介している。似ているが同じではない。同じファイルでERRORを探すと、両者の結果が分かれる。bashは大文字小文字を区別して3件を見つける。

$ grep -n ERROR app.log
                    3:2026-10-05 09:01:12 ERROR db timeout after 30s
                    7:2026-10-05 09:03:02 ERROR upstream 502
                    10:2026-10-05 09:05:00 ERROR db timeout after 30s
Select-String -Path .\app.log -Pattern 'ERROR'
app.log:3:2026-10-05 09:01:12 ERROR db timeout after 30s
                    app.log:5:2026-10-05 09:01:20 INFO  retry succeeded after error in cache
                    app.log:7:2026-10-05 09:03:02 ERROR upstream 502
                    app.log:10:2026-10-05 09:05:00 ERROR db timeout after 30s

PowerShell側は4件だ。5行目に小文字のerrorが含まれている。Select-Stringのドキュメントは-CaseSensitiveパラメーターについて「既定では一致は大文字小文字を区別しない」と書いている。grepは逆で、既定が大文字小文字の区別であり、無視するには-iを付ける。両者の件数を合わせるとこうなる。

$ grep -c error app.log
                    1
                    $ grep -ci error app.log
                    4
'matches for error (no flag): ' + @(Select-String -Path .\app.log -Pattern 'error').Count
                    'matches for error -CaseSensitive: ' + @(Select-String -Path .\app.log -Pattern 'error' -CaseSensitive).Count
matches for error (no flag): 4
                    matches for error -CaseSensitive: 1

出力の頭に付くapp.log:3:はファイル名と行番号だ。これがテキストではなくMatchInfoオブジェクトの表示形式であることは、プロパティを読めば分かる。

$m = Select-String -Path .\app.log -Pattern 'ERROR' | Select-Object -First 1
                    $m.GetType().FullName
                    'LineNumber = ' + $m.LineNumber
                    'Filename   = ' + $m.Filename
                    'Line       = ' + $m.Line
                    'Pattern    = ' + $m.Pattern
Microsoft.PowerShell.Commands.MatchInfo
                    LineNumber = 3
                    Filename   = app.log
                    Line       = 2026-10-05 09:01:12 ERROR db timeout after 30s
                    Pattern    = ERROR

ドキュメントも、Select-Stringが一致ごとにMatchInfoオブジェクトを返し、FilenameやLineといったプロパティを持つと書いている。そのため、件数を数えるgrep -cは結果を配列で包んで.Countを読むことになり、一致した部分だけを取り出すgrep -oはMatches.Valueを読むことになる。grepのオプションとの対応を同じファイルで実行した結果が下の表だ。

ファイルオブジェクトをパイプで入れたときの動作もgrepと違う。Select-Stringのドキュメントは、FileInfoオブジェクトが入力されると、オブジェクトの文字列表現ではなくそのファイルの内容を検索すると書いている。名前を検索するls | grep appとは正反対だ。

この4行は、先に作った一時フォルダ(app.log、old.log、readme.txtなどがある場所)で実行した結果だ。最後の行の1件は、そのフォルダの一覧にapp.logがあるために出た値なので、名前にappを含む項目がないフォルダではこの数字が変わる。

Set-Location C:\demo\t

                    FileInfo objects | Select-String hello (readme.txt content): 1

名前にappを含むファイルは1つだが、ファイルオブジェクトをそのままパイプすると内容からappを探すので0件になった。helloはreadme.txtの内容なので1件だ。一覧のテキスト表現から名前を探すには、Out-String -Streamで行ごとの文字列に変えてから渡す必要がある。これはgrepの感覚で考える人が最もよく出会う落とし穴だ。

大文字小文字の既定値はSelect-Stringだけのものではない。about_Comparison_Operatorsは、文字列比較は明示的な大文字小文字区別の演算子を使わない限り区別しないと書き、-replaceも既定で大文字小文字を区別しないと書いている。sed 's/error/X/g'を移すとき、この違いがそのまま表に出る。

$ echo 'Error ERROR error' | sed 's/error/X/g'
                    Error ERROR X
                    $ echo 'a.b.c' | sed 's/./-/g'
                    -----
'ERROR' -eq 'error'      -> True
                    'ERROR' -ceq 'error'     -> False
                    'ERROR db' -match 'error'  -> True
                    'ERROR db' -cmatch 'error' -> False
                    'ERROR db' -like 'error*'  -> True
                    'Error ERROR error' -replace 'error','X' -> X X X
                    'Error ERROR error' -creplace 'error','X' -> Error ERROR X
                    'a.b.c' -replace '.','-'    -> -----
                    'a.b.c' -replace '\.','-'   -> a-b-c
                    'a.b.c'.Replace('.','-')    -> a-b-c

上のブロックは、PowerShellを1行ずつ実行して「式 -> 結果」の形で出力したものだ。-replaceの最初の引数が正規表現なので'.'が全文字に一致する点はsedと同じで、大文字小文字の既定値だけが逆になる。-ceq・-cmatch・-creplaceのようにcを付けると区別する。

  • 同じ名前の概念でも既定の大文字小文字の規則が逆の場合があるので、件数を比べる集計では、まず-CaseSensitiveを使うかどうかを決める。
  • Select-Stringにファイルオブジェクトを渡すと内容の検索になり、文字列やOut-String -Streamの結果を渡すとその行の検索になる。
  • パターンは既定で正規表現で、リテラル検索は-SimpleMatchだ。grepの-Fに当たる。

sort | uniq -c | wcをGroup-Object・Sort-Object・Measure-Objectで

ログのレベル(INFO・WARN・ERROR)ごとの件数を数える集計は、bashでは次のように書く。3番目の列を取り出して並べ替え、同じ値を数え、件数順にもう一度並べ替える。

$ awk '{print $3}' app.log | sort | uniq -c | sort -rn
                          6 INFO
                          3 WARN
                          3 ERROR

PowerShellでは、列を取り出す場所に-splitとインデックスを、数えてから並べ替える場所にGroup-ObjectとSort-Objectを使う。

Get-Content .\app.log | ForEach-Object { ($_ -split '\s+')[2] } | Group-Object | Sort-Object Count -Descending | Select-Object Count, Name | Format-Table -AutoSize
Count Name
                    ----- ----
                        6 INFO
                        3 ERROR
                        3 WARN

2つの出力で、件数が同じWARNとERRORの順序が逆だ。同じ件数どうしの順序は決まった約束ではないので、順序に頼る処理は避けるのが安全だ。Group-Objectが返すものも文字列ではなくオブジェクトだ。そのため件数の列はCountプロパティでアクセスする。

$g = Get-Content .\app.log | ForEach-Object { ($_ -split '\s+')[2] } | Group-Object | Select-Object -First 1
                    $g.GetType().FullName
                    $g | Get-Member -MemberType Property | Select-Object Name | Format-Table -AutoSize
Microsoft.PowerShell.Commands.GroupInfo
                    
                    Name
                    ----
                    Count
                    Group
                    Name
                    Values

GroupInfoのGroupプロパティには、その値でまとめられた元の項目が入っているので、件数だけでなくグループの中身まで続けて処理できる。行数と合計はMeasure-Objectが担当する。wc -lはMeasure-Object -Lineか配列の.Countになり、awk '{sum += $5}'は-Property Length -Sumになる。

'wc -l       -> ' + (Get-Content .\app.log | Measure-Object -Line).Lines
                    'count       -> ' + @(Get-Content .\app.log).Count
                    Get-ChildItem -File | Measure-Object -Property Length -Sum -Average -Maximum -Minimum | Format-List Count, Sum, Average, Maximum, Minimum
wc -l       -> 12
                    count       -> 12
                    Count   : 5
                    Sum     : 2586
                    Average : 517.2
                    Maximum : 2002
                    Minimum : 7

bashのwc -l < app.logも同じ12を返す。Measure-Object1回で件数・合計・平均・最大・最小をすべて得られる点が、awk1行の集計より便利なところだ。重複の除去sort -uはSort-Object -Uniqueで、'b','a','b','c','a' | Sort-Object -Uniqueの結果はa、b、cである。

about_Pipelinesの「1つずつ処理」という規則は、集計で結果を分ける。パイプで入れるとオブジェクトが1つずつ流れて数えられるが、パラメーターで配列を丸ごと渡すと1つのオブジェクトとして扱われる。

'[1,2,3] | Measure-Object            -> ' + (1,2,3 | Measure-Object).Count
                    'Measure-Object -InputObject @(1,2,3) -> ' + (Measure-Object -InputObject @(1,2,3)).Count
                    '@{a=1;b=2} | Measure-Object          -> ' + (@{a=1;b=2} | Measure-Object).Count
[1,2,3] | Measure-Object            -> 3
                    Measure-Object -InputObject @(1,2,3) -> 1
                    @{a=1;b=2} | Measure-Object          -> 1

ドキュメントの例と同じ結果だ。配列はほどかれて3になるが、ハッシュテーブルはほどかれず1になる。ハッシュテーブルを項目ごとに流すにはGetEnumerator()を呼ぶ必要があると、ドキュメントは書いている。

head・tail・cat・awk・cut・xargs・teeの対応

残りのツールは、名前の似た対応コマンドレットがあるか、オブジェクトパイプラインの基本コマンドレットの組み合わせで解ける。同じapp.logで実行した結果をまとめた。head -n 2とtail -n 2はGet-Contentのパラメーターだ。

'head -n 2   ->'
                    Get-Content .\app.log -TotalCount 2
                    'tail -n 2   ->'
                    Get-Content .\app.log -Tail 2
                    'cat type    -> ' + (Get-Content .\app.log).GetType().FullName
                    'cat -Raw    -> ' + (Get-Content .\app.log -Raw).GetType().FullName + ', length ' + (Get-Content .\app.log -Raw).Length
head -n 2   ->
                    2026-10-05 09:00:01 INFO  service started
                    2026-10-05 09:00:07 WARN  cache miss ratio high
                    tail -n 2   ->
                    2026-10-05 09:05:01 INFO  retry 1
                    2026-10-05 09:05:44 INFO  service stopped
                    cat type    -> System.Object[]
                    cat -Raw    -> System.String, length 532

bashのhead -n 2 app.logとtail -n 2 app.logは同じ4行を返す。違うのはcatの戻り値の型だ。Get-Contentはファイルを行ごとの文字列の配列として読み、丸ごとの文字列が必要なら-Rawを付ける。行の配列がパイプを流れて、ForEach-Objectが行ごとに実行される。awk '{print $3}'は-splitとインデックスに移し、xargsはForEach-Objectになる。

変数と環境変数 - $xは子プロセスに渡らない

bashのexport FOO=barに当たるのは$env:FOO = 'bar'だ。通常の変数$xはPowerShellのセッション内にだけあり、環境変数$env:Yは子プロセスにまで継承される。この区別は、bashでexportの有無で分かれるのと同じだ。両方で同じ試験をした。

$ x=shell-only
                    $ export Y=exported
                    $ bash -c 'echo "x=[$x] Y=[$Y]"'
                    x=[] Y=[exported]
$x = 'shell-only'
                    $env:Y = 'exported'
                    'bash $PATH -> [' + $PATH + ']   (the PowerShell variable $PATH is empty)'
                    '$env:PATH has entries: ' + (($env:PATH -split ';').Count -gt 3)
                    'child process sees:'
                    powershell.exe -NoProfile -File C:\demo\child.ps1
                    (Get-ChildItem Env: | Where-Object { $_.Name -eq 'Y' }).Value
                    Remove-Item Env:\Y
                    'after Remove-Item Env:\Y -> [' + $env:Y + ']'
bash $PATH -> []   (the PowerShell variable $PATH is empty)
                    $env:PATH has entries: True
                    child process sees:
                    x=[] Y=[exported]
                    exported
                    after Remove-Item Env:\Y -> []

子プロセス(child.ps1は$xと$env:Yを1行で出力する)が見たものは、bashと同じx=[] Y=[exported]だ。落とし穴のひとつは名前である。bashの$PATHは環境変数だが、PowerShellの$PATHはただの未定義の通常変数なので空になる。環境変数は$env:PATHで読み、区切りは;だ。環境変数を消すのはRemove-Item Env:\Yで、環境変数の全体はEnv:ドライブとしてGet-ChildItemで一覧できる。

  • exportが必要な値は$env:名前で作り、スクリプト内部でだけ使う値は通常の変数にしておく。
  • $PATHのようにbashで慣れた名前が、PowerShellでは空の変数のことがある。$env:の接頭辞を忘れない。
  • 環境変数はEnv:ドライブを通じてファイルのように一覧・削除できる。

ワイルドカードは誰が展開するか - シェルではなくコマンドレット

bashでは、*.logはコマンドが実行される前にシェルがファイルの一覧に展開して引数として渡す。同じ入力をbashで確かめた。

$ echo *.log
                    app.log old.log
                    $ node -e "console.log(JSON.stringify(process.argv.slice(1)))" *.log
                    ["app.log","old.log"]

PowerShellは違う。about_Wildcardsは、ワイルドカードが-like演算子や「ワイルドカードを受けるすべてのパラメーター」で使われ、どのパラメーターが受けるかは各コマンドレットのヘルプに書いてあると説明している。だから、ネイティブプログラムには展開されていない文字列がそのまま行く。

'Get-ChildItem *.log ->'
                    (Get-ChildItem *.log).Name
                    'Write-Output *.log ->'
                    Write-Output *.log
                    'native program (node) args for *.log ->'
                    node -e "console.log(JSON.stringify(process.argv.slice(1)))" *.log
                    'cmd /c echo *.log ->'
                    cmd /c echo *.log
Get-ChildItem *.log ->
                    app.log
                    old.log
                    Write-Output *.log ->
                    *.log
                    native program (node) args for *.log ->
                    ["*.log"]
                    cmd /c echo *.log ->
                    *.log

Get-ChildItem *.logはコマンドレットがパターンを自分で解釈して2つのファイルを返す。一方、Write-Output *.logとネイティブプログラム(node)とcmd /c echoは*.logという文字をそのまま受け取った。シェルが代わりに展開してくれることはないので、ネイティブプログラムにファイル一覧を渡すには、Get-ChildItemで名前を得て引数として渡す必要がある。ワイルドカードを解釈する主体が違うことで生じる結果がもうひとつある。角括弧はワイルドカード文字なので、名前に角括弧を含むファイルはそのままでは見つからない。

'Test-Path file[1].txt              -> ' + (Test-Path 'C:\demo\t\file[1].txt')
                    'Test-Path -LiteralPath file[1].txt -> ' + (Test-Path -LiteralPath 'C:\demo\t\file[1].txt')
                    'Get-ChildItem file[1].txt (count)   -> ' + @(Get-ChildItem 'file[1].txt' -ErrorAction SilentlyContinue).Count
                    'Get-ChildItem file[[]1].txt (count)  -> ' + @(Get-ChildItem 'file[[]1].txt' -ErrorAction SilentlyContinue).Count
                    'Get-ChildItem -LiteralPath (count)  -> ' + @(Get-ChildItem -LiteralPath 'file[1].txt').Count
                    'Get-ChildItem -Filter file[1].txt   -> ' + @(Get-ChildItem -Filter 'file[1].txt').Count
Test-Path file[1].txt              -> False
                    Test-Path -LiteralPath file[1].txt -> True
                    Get-ChildItem file[1].txt (count)   -> 0
                    Get-ChildItem file[[]1].txt (count)  -> 1
                    Get-ChildItem -LiteralPath (count)  -> 1
                    Get-ChildItem -Filter file[1].txt   -> 1

about_Wildcardsは、角括弧が文字の範囲や特定の文字の集合に一致するワイルドカードであること、ワイルドカード文字を含むファイル名にアクセスするにはエスケープが必要であること、その方法のひとつが-LiteralPathパラメーターであることを書いている。file[1].txtというパターンはfile1.txtに一致するので、このフォルダーでは0件だ。-LiteralPathと[[]の形は1件を見つけ、-Filterも1件だった。同じ文書は、ファイルシステム項目のワイルドカード一致が文字列の場合と違う動作をするとも書いている。最後に-Includeの動作だ。

'-Include *.log alone      -> ' + @(Get-ChildItem -Include *.log).Count
                    '-Include with C:\demo\t\* -> ' + @(Get-ChildItem C:\demo\t\* -Include *.log).Count
                    '-Filter *.log             -> ' + @(Get-ChildItem -Filter *.log).Count
-Include *.log alone      -> 0
                    -Include with C:\demo\t\* -> 2
                    -Filter *.log             -> 2

-Includeだけを単独で使うとこのフォルダーでは0件で、パスの末尾に\*を付けると2件が出た。名前パターンだけを使うときは、-Filterが同じ2件を返した。bashのls *.logを移す最も単純な形はGet-ChildItem -Filter *.logだ。

  • ネイティブプログラムにワイルドカードの一覧を渡すには、PowerShellが展開してくれないので、Get-ChildItemの結果から引数を自分で作る。
  • 名前に[や]を含むファイルは-LiteralPathでアクセスする。
  • -Includeは、パスパターンと一緒に使った場合と単独で使った場合で結果が違ったので、単純な名前パターンには-Filterのほうが予測しやすい。
  • 同じ*でも、-like演算子とファイルシステム項目では一致の規則が違うと、ドキュメントは書いている。

  • ファイルや別のツールに値を渡すときは、表の形式ではなくConvertTo-Csvのようなデータ形式を使う。

同じ演算子はGit Bashでは正常に動いた(true && echo "and-list ran"がand-list ranを出力した)。PowerShellではコマンドを;でつなぎ、前のコマンドの成否は$?で調べる。ひと目で見渡せるように、ここまでに出会ったずれを表にまとめた。

症状原因(実行で確認)対応
ls | grep appの形で名前を絞ったのに結果が違う流れるのがオブジェクトだ。Select-Stringはファイルオブジェクトを受けると内容を検索するWhere-Object { $_.Name -like ... }
大文字小文字の混じった行がより多く拾われるSelect-Stringと比較演算子の既定値が大文字小文字の無視だ-CaseSensitive、-ceq、-creplace
数値の並べ替えが文字順で出る入力が文字列だ(10, 100, 9)Sort-Object { [int]$_ }
*.logが展開されずそのまま渡るネイティブプログラムにはPowerShellがワイルドカードを展開しないGet-ChildItemで名前を得る
角括弧を含むファイル名が見つからない角括弧がワイルドカード文字だ-LiteralPath
表で保存したファイルで値が切れた表示形式の幅の制限(コンソール幅120で119文字)だSelect-ObjectのあとConvertTo-Csv
curlがcurl.exeではない5.1ではInvoke-WebRequestの別名だcurl.exeとして呼ぶ
ls -l、rm -rfがエラーになるパラメーター名として解釈されるGet-ChildItem、Remove-Item -Recurse -Force
cmd1 && cmd2が構文エラーになる5.1の構文に&&演算子がない;と$?の検査
  • 翻訳はコマンド名ではなく「何が流れているか」から始める。文字列ならSelect-Stringと-split、ファイルやプロセスのようなオブジェクトならプロパティだ。
  • 既定値が変わる場所(大文字小文字、並べ替え、ワイルドカード)では、同じ名前のオプションがあっても結果の件数が変わりうるので、まず件数で突き合わせる。
  • 元に戻せないコマンド(Remove-Item -Recurse -Forceなど)は、存在しないパスを対象にまず実行して、パラメーターの解釈だけを確かめる。上のls -lとrm -rfの試験もそうした。

確認できなかったこと

  • PowerShell 7(pwsh)。このPCにpwshがなく、5.1との違いを実行で比べられなかった。&&演算子、curlの別名、Select-Stringの既定のエンコーディング処理など、7で変わりうる項目は、参照した公式ドキュメント5件では扱われておらず確認できなかった。
  • Linuxのbashとgnuツール。比較出力はWindowsのGit Bash(MSYSビルド、GNU grep 3.0)で得たので、ディストリビューションごとのgrepやsortの動作とロケールの影響は確認できなかった。
  • コンソール幅120以外でのFormat-Tableの切れる位置。今回の実行は幅120だけで行った。
  • このPCの-NoProfileセッションの外の別名。ユーザープロファイルやモジュールが別名を追加・上書きすると一覧が変わりうる。
  • 日本語や、BOMのないUTF-8のファイルをSelect-Stringで検索するときのエンコーディング処理。実習ファイルはASCIIだけで、ドキュメントが書くBOMに基づくエンコーディングの判定は実行していない。
  • 件数が同じGroup-Objectの結果の並び順が常に同じかどうか。1回の実行でERRORがWARNの前に出たことだけを確認した。
  • 大きなファイルでの性能の違い。Get-ContentとSelect-String、bashツールの処理速度は測っていない。
