从gh-attach看GitHub附件API的空白 - CLI自动化的绕行方案及其局限

借用浏览器会话在CLI中为Issue/PR添加附件的工具，它绕过了什么，又能信任到什么程度

2026年7月9日 开发/基础设施

引言: 一个只靠拖拽存在的功能

你可能会问，往 GitHub 的 Issue 或 PR 里贴一张截图能有多难? 在浏览器里把图片拖进评论框放开就行了。可如果「拖拽放开」实际上是通往这个功能的唯一正门，事情就不一样了。截至 2026 年 7 月，GitHub 依然没有为 Issue、PR、评论提供官方的 REST 或 GraphQL 附件上传 API。这是一扇只有人坐在浏览器前用鼠标才能打开的门。

而在 CLI 创建 Issue、机器人把部署日志留在评论里、AI 智能体自己开 PR 已成常态的今天，这扇门就是一个明显的瓶颈。gh-attach 没有选择正面突破，而是从侧面绕了过去。它被 GeekNews 报道后，收获了一片「这正是我需要的」的反响。本文不打算复述这种反响，而是直接审视: 这个工具究竟绕过了什么，在自动化工作流中值多少价值，以及能信到什么程度。

1. 问题的本质 - 为何没有附件 API

1.1 拖拽上传实际做了什么

在浏览器里把图片拖进 Issue 或 PR 的评论输入框，前端代码会立即向 github.com/upload/policies/assets 发起请求。这个请求要通过，必须携带 user_session Cookie，也就是一个已登录的浏览器会话。拿到签发的上传策略后，文件被送入内部资产管道(存储+CDN)，完成后一条形如 github.com/user-attachments/assets/{uuid} 的链接会被插入到评论正文里。你在 Issue 里常见的那些图片链接，正是这个过程的产物。

1.2 一个被反复提出近六年的诉求

问题在于，这整套流程从头到尾都是基于会话 Cookie 的。以 Token 或 OAuth 认证的 REST/GraphQL API 中，没有与之对应的端点。GitHub Community 讨论区里，「给评论加个上传图片的 API」的诉求被反复提出; gh CLI 仓库的一个 Issue 更是把这个空白重新表述为「对智能体工作流至关重要」，并举例说明智能体能写出完美的 Issue 正文，却贴不上能让问题变得可操作的那张截图。这类诉求可以追溯到 2020~2021 年，该 Issue 本身也被作为更早期 Issue 的重复项关闭。也就是说，同一个诉求已被重复了近六年，官方 API 依然没有出现。

2. gh-attach 到底绕过了什么

2.1 借用浏览器已有的会话

sudosubin/gh-attach(用 Go 编写，MIT 许可)的核心思路很直接: 让 CLI 借用浏览器已经持有的登录会话。它先通过 gh api 确认当前已认证的 GitHub 账号与目标仓库，再在本地已安装的 Chrome 系、Firefox 系、Safari 浏览器的 Cookie 存储中，查找 dotcom_user Cookie 值与该账号匹配的会话。

2.2 上传方式与浏览器完全一致

拿到会话后，它用这些 Cookie 向 /upload/policies/assets 申请上传策略，上传文件二进制，再完成资产确认。这本质上是用代码原样复现了浏览器在拖拽上传时执行的每一步。

2.3 结果与手动上传完全相同

由此产生的 URL 形如 github.com/user-attachments/assets/{uuid}，与人工手动拖拽上传得到的链接是完全同一种类型。一行 gh attach ./image.png -R owner/repo 就能拿到这个 URL，直接贴进 Issue 或 PR 正文; 加上 --json 可供脚本解析，--template 可与其他命令串联。浏览器与配置文件的选择可以保存在 ~/.config/gh/attach.yml 配置文件里，无需每次重复指定。

3. 在 CLI/自动化工作流中的价值

3.1 自动贴截图与日志的机器人

最直接的用法，是让机器人在无人干预的情况下，把部署失败日志、视觉回归测试的截图、性能图表留在 Issue 或 PR 上。以往的流程是 CI 留下一份产物，人再打开截屏贴上去，中间隔着一道人工步骤; gh-attach 消除的正是这一步。

3.2 当智能体自己开 PR 的时候

随着 AI 编程智能体越来越多地自己修改文件、自己开 PR，人们自然希望那个 PR 能一并附上说明改动的截图或示意图。gh-attach 的作者本人就表示，做这个工具正是为了让智能体能自动附上示意图和截图。一份只有文字的 PR 说明，和一份能让人一眼看到实际变化的 PR 说明，对审阅者来说是完全不同的体验。

3.3 在 gh CLI 扩展生态中的位置

gh-attach 是一个 gh CLI 扩展，一行 gh extension install owner/repo 即可安装。GitHub 官方文档支持这套扩展机制，任何人都可以创建以 gh- 开头的仓库并发布。有意思的是，解决同一问题的扩展并不止 gh-attach 一个——名字都相互重叠的多个独立实现同时存在(例如 enthus-appdev/gh-attach，以及兼具 MCP 服务器功能的 Addono/gh-attach)。这既说明这个瓶颈普遍到足以让多名开发者各自撞上，也说明这个领域尚无「标准」可言。

4. 依赖非官方端点的风险

4.1 一个自动化工具，却和自动化环境水土不服的悖论

首先要指出的局限是: gh-attach 打着「智能体/机器人自动化」的旗号，但它的运作原理却依赖一个已登录的浏览器会话。而绝大多数 CI 运行器和智能体沙箱本来就没有这样的会话。要在自动化流水线中直接使用，需要事先在该环境里准备好已认证的浏览器配置文件，或把会话复制进无头浏览器。「机器人自动贴上截图」这幅图景，只有做完这一步准备工作后才成立——而这恰恰是把这个工具误当作「全自动」工具时最先绊脚的地方。

4.2 随时可能失效的契约

/upload/policies/assets 并非 GitHub 正式文档化或做版本承诺的 API，而是供其网页前端内部使用的端点。一旦 GitHub 调整上传流程，这个工具就可能在毫无预警的情况下失效。这是所有依赖抓取式实现的工具共同背负的债务，相关讨论也明确把这类绕行方案定位为「权宜之计」，把争取官方 API 留作长期目标。

4.3 读取 Cookie 这件事的分量

读取本地浏览器的 Cookie 存储绝非小事。部分操作系统会要求访问钥匙串或凭据管理器的权限，一些浏览器本身也会在系统层面加密 Cookie。即便是值得信赖的开源工具，安装一个能触及登录会话 Cookie 的 CLI，本身就是在扩大安全暴露面的选择，这一点应当被清楚地认识到。

5. 与官方替代方案的比较

GitHub CLI 社区也很清楚这个空白。除了 gh-attach 式的会话绕行外，还讨论过两种仅凭 Token 即可完成的替代方案。

方式认证结果 URL优点缺点
gh-attach(会话绕行)浏览器 Cookieuser-attachments/assets 链接与网页端结果一致，即刻可用非官方端点，CI 需额外准备
gh release uploadPAT/Token发布资产下载链接官方 API，仅凭 Token 即可在 CI 运行发布列表变杂乱，用于临时截图显得过重

我个人的判断是: 如果只是人偶尔手动贴一次附件，gh-attach 最顺手。如果是常驻的 CI 机器人习惯性地留日志，没有会话管理负担的发布资产在运维上更稳妥。孤立分支方案，我更多把它看作两种条件都不占优时的折中选择。

结论: gh-attach 是权宜之计，不是最终答案

gh-attach 是一个相当不错的权宜之计。在 GitHub 拿出官方的 Issue/PR 附件 API 之前，这类会话绕行工具注定会不断出现——名字相互重叠的多个独立实现同时存在，本身就是需求真实存在的证明。如果你现在就想在 CLI 里贴一张截图，gh-attach 已经足够。

但要记住两点: 把它接入 CI 或智能体流水线，还留着「准备会话」这项作业没做; 而它所依赖的端点，是一份 GitHub 随时可能废弃的非官方契约。真正的解决之道，是 GitHub 拿出仅凭 Token 就能用的官方上传 API。在那之前，把 gh-attach 看作填补这一空白的众多实验之一，才是准确的定位。
