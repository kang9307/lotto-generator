静态类型的崛起 - 为何自2010年代中期再度流行

The Rise of Static Typing - Why It Has Been Back in Favor Since the Mid-2010s

2026年6月13日 IT/技术

引言：类型的钟摆又荡了回来

把编程语言的历史拉长来看，"语言应在多大程度上强制声明类型"这个问题，像钟摆一样在两端来回摆动。从1990年代后期到2010年代初期，无疑是动态类型（dynamic typing）的时代。Python、Ruby、JavaScript、PHP成为Web与创业公司的基础语言，"类型声明是繁琐的形式主义"这种情绪广为流传。然而以2010年代中期为界，潮流悄然而又明确地反转了。TypeScript席卷JavaScript生态，Rust跃升为系统编程的宠儿，连Python也接纳了类型提示（type hints）。

本文以GeekNews（news.hada.io）上引发热议的一则分析为出发点——即2010年代中期以来静态类型的急速上升并非单纯的流行轮回，而是反映了语言系统本身的改进。我们将冷静地梳理静态类型与动态类型的差异、动态类型为何一度流行，以及是什么改变使其再度回归静态。先给出结论：回归的静态类型，已不是从前的静态类型。类型推断与渐进式类型这两项发明，几乎消除了"静态类型的繁琐"，再叠加大型代码库与AI编程这两股新压力，才是其本质所在。

1. 静态类型 vs 动态类型 - 基本概念

先把基础打牢。两者的差异可凝练为一句话：何时检查类型。

  • 静态类型（static typing）：在程序运行之前，于编译或类型检查阶段确定并验证所有变量、函数的类型。类型不匹配则根本无法运行。C、C++、Java、Go、Rust、TypeScript都属于此类。
  • 动态类型（dynamic typing）：类型在运行过程中根据实际的值确定。先把代码跑起来，遇到类型不匹配的运算时才会报错。Python、Ruby、JavaScript、PHP是典型代表。

常被混淆的"强类型/弱类型（strong/weak typing）"是另一条轴，指的是语言在多大程度上允许隐式类型转换。例如JavaScript是动态且弱类型，"3" + 1 会变成 "31"；Python是动态但相对强类型，同样的运算会报错。本文讨论的是"静态 vs 动态"这条轴。

用一个极简例子建立直觉。

# 动态类型（Python） - 运行前看起来毫无问题
def add(a, b):
    return a + b

add(1, 2)        # 3
add("a", "b")    # "ab"  -- 同一个函数却以完全不同的含义运行
add(1, "b")      # 直到运行时才报 TypeError！

// 静态类型（TypeScript） - 运行前就被捕获
function add(a: number, b: number): number {
  return a + b;
}

add(1, 2);     // OK
add(1, "b");   // 编译错误: Argument of type 'string' is not assignable to 'number'

关键在最后一行。在动态类型中，add(1, "b") 一直潜伏到真正执行时才爆发；而在静态类型中，你写下它的那一刻编辑器就画上了红线。这种"遇到错误的时点之差"，正是后续一切讨论的根源。

2. 动态类型为何一度流行

要理解静态类型为何回归，先要诚实地审视动态类型为何如此受宠。它的流行绝非偶然。

第一，编写速度与灵活性。无需类型声明就能把想法直接写成代码，这在原型开发和脚本编写中是压倒性优势。2000年代后期创业公司快速投放、快速验证产品，"先让它跑起来"的文化与动态语言完美契合。

第二，当时静态类型的痛苦。那个年代的代表性静态语言是Java和C++，需要逐一手写类型声明。诸如 Map<String, List<Integer>> m = new HashMap<String, List<Integer>>(); 的冗长声明，深深刻下了"静态类型＝麻烦而仪式化"的印象。人们抗拒的与其说是静态类型本身，不如说是那个年代静态类型糟糕的开发体验。

第三，Web的爆发。浏览器唯一的语言JavaScript是动态的，服务端也有PHP、Ruby on Rails、Django提升Web开发的生产力。动态语言搭上了那个时代的浪潮。

2000年代人们背弃的不是"类型"，而是"为声明类型所付出的成本"。把这个成本去掉，整个故事就完全不同了。

3. 动态类型暴露的成本 - 当代码变大时

动态类型的优点在代码量小时熠熠生辉。问题在于代码库长到数万、数十万行，团队扩大，代码存活数年之后才显现。动态类型推迟的成本，开始以复利的方式被追讨。

  • 重构恐惧：当你想改函数名或参数时，编译器并不保证它在何处、如何被使用。你无法判断这次改动是否会悄悄弄坏某处，于是在大型动态代码库中，重构本身就成了一件可怕的事。
  • 文档缺失：函数接受什么类型、返回什么，并未在代码中明示。新加入的开发者只能翻遍调用点，或亲自运行去猜。
  • 迟到爆发的Bug：类型不匹配的错误不在开发期、而在生产环境爆发，而且常在罕有经过的代码路径上。None/undefined 流到意想不到的地方，在深夜引发故障。

这三者都是"规模问题"。在你独自编写的200行脚本里几乎无感，但在50人维护五年的50万行服务中却是致命的。到2010年代中期，恰好许多公司的代码库正越过那个临界点。Facebook为JavaScript打造类型检查器Flow、Microsoft打造TypeScript、Dropbox为Python打造mypy、Stripe为Ruby发布Sorbet，绝非偶然。背负庞大动态代码库的公司，仿佛事先约定好一般，开出了同一张药方。

4. 决定性发明之一 - 类型推断（Type Inference）

那么，为何"这一次"静态类型能被毫无抵触地接纳？第一个答案是类型推断。类型推断让开发者无需逐一书写类型，编译器便能从上下文中自动推断出类型。

这个想法本身并不新鲜。函数式语言ML和Haskell所用的Hindley-Milner类型推断是一种已有数十年的算法，几乎不加注解就能精确还原整个程序的类型。分析指出，该算法处于语言设计的甜蜜点：表达力很强，而推断却可自动完成。2010年代的新语言，把这份古老的智慧带入了主流。

// Rust - 类型推断让声明很轻
let count = 42;                 // 推断为 i32
let name = "BrainDetox";        // 推断为 &str
let scores = vec![90, 85, 88];  // 推断为 Vec<i32>

// 在函数边界处显式标注 -> 既是文档也是契约
fn average(scores: &[i32]) -> f64 {
    let sum: i32 = scores.iter().sum();
    sum as f64 / scores.len() as f64
}

这里的平衡感很关键。现代语言大多设计为对局部变量进行推断，而在函数边界（参数、返回类型）处显式标注。函数内部琐碎的类型声明交给编译器，让书写轻盈；边界处的类型则显式写出，作为"文档兼契约"留存。这一折中决定性地击碎了"静态类型很冗长"的旧印象。代码既能像动态语言一样简洁，又保留了安全网。

不过类型推断并非万能。一般而言，在高阶多态等表达力很强的领域，推断会触及极限，需要显式注解。因此现代的类型推断追求一种务实的平衡：不是"全部自动"，而是"只把麻烦的部分自动化"。

5. 决定性发明之二 - 渐进式类型（Gradual Typing）

第二个答案是渐进式类型，它或许更为重要。如果说类型推断降低了静态类型的成本，那么渐进式类型则拆除了静态类型的准入门槛。

渐进式类型让你能在同一个程序中自由混用静态类型代码与动态类型代码。无需对所有代码一次性加上类型。可以先给最重要、最危险的部分加类型，其余保持动态，再慢慢迁移。分析指出，这一方式的核心价值，在于让"静态类型的安全性"与"动态类型的灵活性"在同一个代码库中同时被享有。

它为何具有革命性？因为它开辟了把安全性逐步引入数百万行既有动态代码库的路径。倘若TypeScript要求"必须把所有JS一次性转为类型才能使用"，那就没人会采用它。相反，TypeScript原样接纳既有的JavaScript，让你一个文件、一个函数地逐步加上类型。

// 渐进式类型 - 从 any 起步，再逐步收紧
function parseConfig(raw: any) {   // 起初是 any（与动态无异）
  return JSON.parse(raw);
}

// 之后加上类型以提升安全性
interface Config {
  port: number;
  host: string;
  debug?: boolean;
}
function parseConfigTyped(raw: string): Config {
  return JSON.parse(raw) as Config;
}

Python的类型提示（PEP 484）秉持的正是同一理念。类型提示是可选的。不加也能运行，一旦接上mypy或pyright这样的外部类型检查器，验证便随之开始。这是一种巧妙的折中：在不损伤动态语言灵魂的前提下，借来静态类型的好处。

6. 渐进式类型也有陷阱

为求平衡，也要点明另一面。渐进式类型并非免费。静态代码与动态代码的边界处，潜伏着微妙的危险。

最大的问题是类型可能撒谎。TypeScript的类型在编译后会消失（类型擦除），运行时并不强制执行。若你用 as Config 断言了外部API的响应，而实际数据并不相符，类型检查器会说"安全"，运行时却悄悄放行了错误的值。研究者普遍警告这类"渐进式类型的意外危险"：静态与动态的边界可能制造安全的错觉。

实务教训很清楚：在不可信输入（网络、文件、用户）进入的边界处，应当采用真正的运行时校验（如zod、pydantic），而非类型断言。类型系统守护的是"我所写代码"的一致性，并不保证"来自外部的数据"会遵守约定。

7. 重回静态 - TypeScript、Rust，以及类型提示

现在用具体案例印证这一趋势。2010年代中期以来的"回归静态"，沿三条线索清晰显现。

7.1 TypeScript - 成为Web的标准

Microsoft于2012年公开的TypeScript，是在JavaScript之上加入渐进式静态类型的语言。据分析，其使用率从2017年约12%升至2022年的34%，几乎翻了三倍；并据报道在2025年按GitHub贡献者数同时超越JavaScript与Python，登上第一。曾是动态语言大本营的前端转向静态类型，是一个具有象征意义的事件。

7.2 Rust - 系统编程的新标杆

2015年发布1.0的Rust，凭借强静态类型与所有权系统，实现了"无垃圾回收器的内存安全"。在C/C++长期把持的系统领域，类型与借用检查器在编译期保证内存安全这一点，推动了它的采用。Rust的流行让"静态类型与安全直接相关"的认知广为传播。更深入的脉络可见从Go迁移到Rust指南。

7.3 Python类型提示 - 动态语言的可选装备

Python通过PEP 484（2015）引入类型提示，并培育出mypy、pyright等外部检查器生态。某项调查中，mypy以约58%的采用率被报告为使用最广的检查器。连动态语言的旗手，也开辟了"需要时借用静态类型"的道路。

语言/工具 登场时期 方式 解决的问题
TypeScript 2012 渐进式静态类型 大型JS的维护
Rust 2015 强静态类型＋所有权 无GC的内存安全
Python类型提示 2015 可选的渐进式类型 动态代码的文档化与校验
Sorbet (Ruby) 2019 渐进式类型 大型Ruby代码的安全

8. 新的压力 - AI编程与类型

如果说2010年代的回归源于"大型代码库"，那么2020年代又叠加了一股全新的压力：AI编程。而这股压力强烈地偏向于静态类型。

核心很简单：LLM生成的代码常常是错的。它会调用不存在的函数、弄错参数顺序、传错类型。此时静态类型系统就像一张安全网，在那些错误代码运行之前把它们过滤掉。某项研究报告称，LLM所写代码的编译错误中约94%是类型检查失败。反过来说，类型系统在编译阶段自动捕获了AI的大部分失误。

GitHub的分析更为直接：类型为LLM提供了"护栏（guardrail）"，并进而影响开发者的语言选择。其解读是，2025年TypeScript按GitHub贡献者数登顶，背后正有AI工具普及的推动。类型清晰的代码，AI更易理解、也更易被验证。"AI时代类型更重要"这一命题，正被数据所支撑。

核心
AI写的代码越多，能在运行前验证这些代码的手段就越重要。静态类型把编译变为"一级安全过滤器"，在AI的失误酿成生产故障之前将其拦下。

9. 静态类型带来的实质收益

下面从"开发者真正得到什么"的角度重新梳理这一趋势。静态类型的收益不在抽象的优雅，而在具体的生产力。

  • 提早发现Bug：在编写时而非生产环境捕获类型错误——在修复成本最低的时点，清除最常见的一类失误。
  • 无所畏惧的重构：一改函数签名，编译器就会在所有受影响的调用点画上红线。大规模结构调整由"赌博"变成"清单"。
  • 活的文档：类型签名本身就是永远最新的文档。def fetch(url: str) -> Response 比注释更准确，且绝不会与代码脱节。
  • 强大的IDE支持：有了类型，自动补全、跳转到定义、安全重命名都更精准。日常编码速度有可感知的提升。

这些收益的共同点在于，它们都"随着时间推移与规模增长而变大"。在短命的原型中，动态类型的速度取胜；在长期维护的系统中，静态类型的复利取胜。这与稳健地进行技术选型的策略相通，更广的讨论见选择无聊的技术 - AI时代与TypeScript编译器的原生化重写。

10. 切忌过度信赖 - 类型并非万能

现在把平衡的砝码牢牢压向另一端。若静态类型的复兴沦为"只要加上类型就安全"的盲信，本身就会成为新的陷阱。你必须准确知道类型捕获不到什么。

  • 逻辑错误：该用 + 却用了 -，类型捕获不到。只要两个值都是 number，类型检查器就满意。业务规则的错误在类型的管辖之外。
  • 竞态条件与副作用：并发Bug、错误的状态变更、与外部系统的偏差，大多无法用类型表达。
  • 错误的建模：若类型对现实建模有误，类型检查器会放行"一致地错误"的代码。类型只守护你所定义规则的一致性。
  • 边界处的谎言：正如第6节所示，只断言外部数据而不加校验，类型就会给出虚假的安心。

因此，静态类型并不替代测试。类型负责"形状"的一致，测试负责"行为"的正确，代码评审负责"意图"的合理，可观测性负责"运维"的现实。这四者不是竞争者，而是层层防线。妄图仅凭类型解决全部质量问题，与当年盲目排斥动态类型的旧情绪一样失衡。

11. 开发者应取的平衡 - 实战指引

那么，2026年的开发者在这股潮流中应取何种姿态？没必要把"静态还是动态"变成一场宗教战争。这里给出因地制宜的务实平衡。

  1. 代码越长寿，越该加类型。用完即弃的脚本可保持动态、求快；维护多年的服务则应以静态类型加固。代码的"预期寿命"是第一判断标准。
  2. 渐进式地引入。不要试图一次性改造既有的动态代码库。从最危险、改动最频繁的核心模块开始加类型，再逐步收紧 any，这才现实。
  3. 在边界处加运行时校验。外部输入进入之处，应使用真正的校验（zod、pydantic），而非类型断言。类型与校验各司其职。
  4. 把类型当作文档与设计工具。函数边界的类型是最准确的文档。好的类型设计让非法状态"无法表达"，从结构上消除Bug的容身之处。
  5. 但不要把一切都押在类型上。通过类型检查并不等于代码正确。请同时保留测试与评审。编译成功是"起点"，而非"保证"。

12. 结语 + 可立即落地的3点

静态类型的崛起并非钟摆的简单往复。它是类型推断消除静态类型成本、渐进式类型拆除准入门槛、再加上大型代码库与AI编程重新抬高类型价值的共同结果。回归的静态类型，已不是2000年代那种冗长的静态类型，而是同时握有动态语言的简洁与静态语言安全网的新物种。而在AI写下越来越多代码的时代，作为"运行前验证能力"的类型，其价值很可能进一步增大。

以可立即落地的3点收尾。

  1. 先给核心模块加类型。不是全部，而是改动最频繁、最危险的部分。这是以最小投入获得渐进式类型最大效果的起点。
  2. 在边界处放置运行时校验。来自外部的数据，仅凭类型断言并不安全。用校验库去"真正地"确认它。
  3. 别把类型当万能。即便类型通过，仍需测试与评审。类型是众多防线之一，唯有与其他工具协同时才发挥最佳作用。
