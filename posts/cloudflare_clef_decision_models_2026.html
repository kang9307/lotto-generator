의사결정 모델의 등장 배경 — 텍스트 생성에서 구조화된 확률 판정으로

생성형 인공지능이 엔터프라이즈 워크플로우에 본격 도입되면서, 전통적인 자기회귀(autoregressive) 언어 모델이 지닌 구조적 한계가 핫패스(hot path) 시스템에서 두드러지기 시작했다. 고객 지원 티켓 분류, API 도구 호출(tool calling), 보안 위협 탐지, 에이전트 분기 제어와 같은 작업은 장황한 문장을 필요로 하지 않는다. 시스템이 실제로 요구하는 것은 「참/거짓」, 「부서 카테고리」, 「위험 점수」와 같이 타입이 명확히 정의된 소수의 이산적 선택지와 그에 대한 신뢰도 확률이다.

그러나 범용 LLM은 단 하나의 단답형 결론을 도출하기 위해서도 문장 생성 파이프라인 전체를 가동하며, 토큰 하나마다 수십 밀리초의 디코딩 지연을 발생시킨다. 또한 출력 형식을 JSON 스키마로 강제하더라도 환각(hallucination)이나 문법 오류의 위험이 상존한다. 이러한 배경에서 텍스트 토큰 생성을 근본적으로 제거하고, 입력 상태와 선택지 목록을 받아 직접 확률 분포를 출력하는 「의사결정 모델(Decision Model)」이라는 독립된 모델 계열이 부상했다.

이 분야의 흐름은 Jev 실측 평가 기술 분석과 비전 확장을 다룬 Jev 스타일 비전 LLM 래퍼 실험, 그리고 판단에 추론을 결합한 Jeeves 의사결정 모델 분석에서 지속적으로 다루어진 바 있다. 2026년 10월 1일, Cloudflare는 이 흐름에 정면으로 대응하는 자체 오픈소스 의사결정 모델 Clef와 Clef-flash를 전격 공개했다.

  • 본질적 워크로드 불일치: 문장 생성을 목적으로 설계된 LLM을 단순 분류 및 라우팅 핫패스에 투입할 때 발생하는 지연과 비용 낭비.
  • 비자기회귀 패러다임: 다음 토큰 예측 루프를 배제하고, 입력된 모든 후보 선택지를 단일 포워드 패스로 병렬 평가.
  • 확률 점수 직접 출력: 텍스트 파싱 없이 실수형 확률값(0.0~1.0)을 직접 수신하여 결정 임계값 기반 제어 구성.
  • 에이전트 인프라와의 결합: Cloudflare cf CLI 에이전트 설계 등과 연계되는 엣지 실행 파이프라인 구축.
  • 오픈 가중치 정책: 벤더 종속을 방지하기 위해 Apache-2.0 라이선스로 가중치 공개 및 Workers AI 호스팅 병행.

Clef와 Clef-flash의 모델 제원과 비자기회귀 병렬 평가 메커니즘

Cloudflare가 공개한 Clef 제품군은 목적에 따라 두 가지 모델로 나뉜다. 복잡한 다중 레이블 분류와 고정밀 도구 선택을 겨냥한 플래그십 모델 Clef는 Qwen3.8-27B를 베이스로 하며, 초저지연 에이전트 루프와 실시간 트래픽 처리를 겨냥한 Clef-flash는 Qwen3.5-9B를 기반으로 구축되었다. 두 모델 모두 기본 트랜스포머 백본의 가중치는 고정한 채, 특화된 라우팅 헤드와 저랭크 어댑터(LoRA) 레이어를 후속 학습하는 구조를 채택했다.

Clef의 추론 방식은 자기회귀 디코딩을 거치지 않는 비자기회귀(non-autoregressive) 메커니즘이다. 입력 프롬프트를 처리하는 단 한 번의 프리필(prefill) 단계 이후, 모델의 은닉 표현(hidden states) 공간에서 전달된 모든 선택지를 2단계 어텐션 구조로 평가한다. 첫 단계에서는 각 선택지가 입력 텍스트의 관련 문맥을 독립적으로 읽어내고, 두 번째 단계에서는 질문 간의 상호 관계와 전체 입력을 종합하여 최종 정규화 점수를 산출한다.

{
                      "messages": [
                        { "role": "user", "content": "Payment failed for all customers over the past hour. DB connection pool exhausted." }
                      ],
                      "questions": [
                        { "id": "urgency", "type": "choice", "options": ["low", "medium", "critical"] },
                        { "id": "assignee", "type": "choice", "options": ["billing_team", "infra_team", "support"] },
                        { "id": "customer_impact", "type": "boolean" }
                      ]
                    }

위 요청 구조에서 보듯, 시스템은 하나의 문맥에 대해 여러 개의 질문(선택형, 불리언, 점수형)을 단일 API 호출로 묶어 전달할 수 있다. Clef는 각 질문에 대해 토큰을 하나씩 풀어내는 것이 아니라, 모든 선택지의 조건부 확률을 한꺼번에 계산하여 반환한다. 이는 생성 루프가 없기 때문에 출력 토큰 수에 비례하여 지연 시간이 늘어나는 현상을 구조적으로 차단한다.

  • Clef (27B 모델): Qwen3.8-27B 기반, 복잡한 비즈니스 룰 및 고난도 엔터프라이즈 도구 호출 분류에 최적화.
  • Clef-flash (9B 모델): Qwen3.5-9B 기반, 엣지 환경의 초저지연 분기 제어 및 실시간 봇 판별에 최적화.
  • 2단계 어텐션 레이어: 개별 선택지의 문맥 참조와 질문 간 상관관계를 분리하여 교차 평가하는 특화 아키텍처.
  • 고정 백본과 어댑터 분리: 대규모 사전학습 모델의 범용 지식을 보존하면서 결정 헤드만을 집중 미세조정.
  • 병렬 결정 처리: 단일 컨텍스트에 대해 수십 개의 분류 질문을 전달해도 추론 시간이 선형 증가하지 않는 특성.

Cloudflare 자체 측정 벤치마크와 응답 지연 수치의 해석

Cloudflare는 발표문에서 자사 엣지 GPU 인프라와 벤치마크 데이터셋에서 측정한 자체 성능 평가 결과를 공개했다. 도구 선택 정확도를 측정하는 BFCL(Berkeley Function-Calling Leaderboard)에서 Clef는 98.47%, Clef-flash는 98.76%의 정확 일치율을 기록하여, 비교군으로 제시된 Jev의 95.75%를 상회했다고 보고했다. 또한 API-Bank 정확도에서도 Clef 91.93%, Clef-flash 93.11%로 Jev(88.19%)보다 높은 수치를 발표했다.

반면 모든 벤치마크에서 Clef가 일관되게 앞선 것은 아니다. 도구 호출 여부를 엄격히 판단하는 When2Call 벤치마크에서는 Jev가 80.97%를 기록한 반면, Clef는 72.37%, Clef-flash는 65.58%에 머물렀다. Cloudflare 역시 When2Call 및 BRIGHT 평가에서는 Jev가 더 우세했음을 발표문에서 가감 없이 명시했다. 이는 도구 선택의 정밀도와 호출 트리거의 보수성 사이에서 모델마다 서로 다른 학습 편향이 존재함을 시사한다.

응답 속도 면에서 Cloudflare는 43개 벤치마크를 통합한 지연 시간 통계를 제시했다. Clef-flash의 중앙값 지연은 38.8ms로 보고되었으며, 이는 비교 대상인 Jev의 524.1ms 대비 현저히 짧은 수치다. 또한 꼬리 지연(tail latency)을 나타내는 p95 기준에서도 Clef-flash는 122.4ms를 기록하여 비교 모델군 중 가장 낮은 분산을 보였다고 밝혔다. 다만 이 측정은 Cloudflare가 관리하는 특정 엣지 GPU 인프라에서 수행된 자체 결과이며, 독립된 제3자 하드웨어 검증 수치는 포함되어 있지 않다는 점에 유의해야 한다.

  • 자체 측정 수치의 귀속: 본문의 모든 벤치마크와 응답 지연은 Cloudflare가 공식 발표문에서 자체 집계한 결과.
  • Clef-flash의 38.8ms 중앙값: 9B 파라미터 경량 모델과 비자기회귀 구조의 결합을 통해 달성한 자체 엣지 지연.
  • 도구 선택과 호출 판단의 엇갈림: BFCL에서는 Clef 계열이, When2Call에서는 Jev가 우세하여 과제별 트레이드오프 확인.
  • 실제 워크플로우 종합 소요: 웹사이트 렌더링(Browser Run) 및 분류 실험에서 전체 파이프라인 2.2초 소요 보고.
  • Laya 비교군 언급: 발표문에서는 초경량 모델 Laya가 중앙값 5.8ms로 더 빨랐으나 p95 안정성은 Clef-flash가 우위였다고 서술.

멀티모달 64K 컨텍스트와 Jev API 호환성

Clef의 두드러진 기술적 차별점 중 하나는 텍스트를 넘어선 멀티모달(multimodal) 지원과 64K 토큰에 이르는 대형 컨텍스트 윈도우다. 기존에 널리 사용되던 Jev 모델은 텍스트 전용에 32K 컨텍스트를 지원하는 구조였으나, Clef는 고해상도 이미지 입력과 대용량 문맥을 동시에 수용할 수 있도록 설계되었다. 이는 웹페이지 스크린샷 판별, 문서 OCR 기반 청구서 분류, UI 요소 인식 등 시각 정보가 결합된 의사결정 파이프라인에 직접 투입될 수 있음을 의미한다.

또한 Cloudflare는 기존 의사결정 모델 생태계를 흡수하기 위해 Jev API와의 상위 호환성을 제공한다. 클라이언트는 TypeSafe의 기존 Jev SDK나 REST 스키마를 수정할 필요 없이, 엔드포인트 URL만을 Workers AI로 전환하여 동일한 입력 포맷을 전달할 수 있다. 모델이 반환하는 출력 역시 각 선택지별 정규화된 점수와 확률값을 담은 표준 JSON 구조로 구성된다.

{
                      "decisions": {
                        "urgency": {
                          "selected": "critical",
                          "probabilities": { "low": 0.012, "medium": 0.045, "critical": 0.943 }
                        },
                        "assignee": {
                          "selected": "infra_team",
                          "probabilities": { "billing_team": 0.021, "infra_team": 0.965, "support": 0.014 }
                        },
                        "customer_impact": {
                          "selected": true,
                          "probability": 0.988
                        }
                      }
                    }

이와 같은 일관된 구조화 출력은 애플리케이션 코드가 복잡한 정규표현식이나 JSON 스키마 검증기 없이도 결정론적(deterministic)인 분기 처리를 수행할 수 있게 한다. 에이전트는 반환된 critical 확률이 사내 기준치(예: 0.90)를 초과할 경우 즉각 페이저를 울리고, 임계값 이하일 경우 인간 검토 큐로 이관하는 식의 안전 마진 설계를 직관적으로 구현할 수 있다.

  • 64K 대용량 컨텍스트: 복잡한 API 스펙 문서나 장문의 고객 상담 이력을 한 번에 주입 가능한 컨텍스트 버퍼.
  • 이미지 입력 공식 지원: 시각적 웹사이트 분류 및 이미지 기반 에이전트 인터랙션에 의사결정 모델 직접 적용.
  • Jev 호환 스키마 제공: 기존 Jev 기반으로 작성된 클라이언트 파이프라인의 손쉬운 드롭인(drop-in) 교체 지원.
  • 결정론적 JSON 응답: 자유 텍스트 생성에 따르는 파싱 실패 위험을 배제한 고정 키-값 구조 반환.
  • 엔터프라이즈 프라이버시 원칙: 미세조정 계약 고객을 제외하고 사용자 요청 및 응답 데이터를 저장하거나 학습에 미활용.

RLCD 보정과 전담 미세조정 서비스 및 플랫폼 로드맵

단순한 분류 정확도 못지않게 의사결정 모델에서 필수적인 요소는 확률의 정밀도(calibration)다. 모델이 어떤 선택지에 대해 80%의 확률을 제시했다면, 실제로 해당 사례 100건 중 80건이 정답이어야 한다. 일반적인 LLM은 자기 확신이 과도하여(overconfident) 99% 확신을 표명하면서도 오답을 내는 경향이 잦다. Cloudflare는 이 문제를 해결하기 위해 보조 학습 목표로 RLCD(Reinforcement Learning for Calibrated Decisions) 기법을 적용했다고 밝혔다.

RLCD는 순서가 존재하는 선택지(예: 낮음/보통/높음)에서 정답에 인접한 선택지에도 부분 보상을 부여하며, 한 요청에 포함된 복수의 질문 필드를 모두 정확하게 맞춘 결과에 가중 보상을 제공한다. 이를 통해 산출된 확률값이 실제 통계적 참일 가능성과 정확히 수렴하도록 유도함으로써, 엔지니어가 확률 수치 자체를 시스템 자동화의 신뢰 지표로 직접 활용할 수 있도록 보장한다.

비즈니스 모델 측면에서 Cloudflare는 현재 고객 전담 엔지니어링(Forward Deployed Engineering, FDE) 팀을 통해 도메인 특화 미세조정을 제공하고 있다. 향후에는 Cloudflare 내부 생태계를 결합한 셀프서비스 RL 플랫폼으로 확장한다는 계획을 발표했다. 이 플랫폼 로드맵은 AI Gateway를 통한 운영 로그 수집, Workers AI를 통한 추론 기록 생성, Containers 기반 에이전트 샌드박스 평가, 신규 Trainer를 통한 모델 학습 및 재배포 파이프라인으로 구성된다. 다만 공식 발표문은 셀프서비스 플랫폼이 아직 개발 중인 단계이며 현재는 FDE 협력 방식으로만 지원된다는 점을 명확히 선을 그었다.

  • RLCD(Reinforcement Learning for Calibrated Decisions): 반환 확률이 실제 정답률과 일치하도록 유도하는 보정 학습.
  • 부분 점수 및 다중 필드 결합 보상: 순서형 선택지의 오차 거리를 반영하고 전체 필드 적중률에 기반한 정책 최적화.
  • 현재 제공 모델과 플랫폼의 구분: 모델(Clef/Clef-flash)은 즉시 가용하나, 셀프서비스 RL 플랫폼은 현재 개발 중.
  • FDE 기반 전담 미세조정: 봇 탐지, 신뢰 및 안전(Trust & Safety), 지원 티켓 등에 특화된 모델 개발 협력.
  • Cloudflare 내부 인프라 연계 구상: AI Gateway, Containers 샌드박스, Workers AI 배포를 아우르는 엔드투엔드 파이프라인.

의사결정 모델 계열의 지형 — Jev, Luna, Jeeves와의 공통점과 차이

의사결정 모델은 단일 업체의 독자적 시도를 넘어 AI 인프라의 새로운 축으로 자리잡고 있다. 이 분야의 기준점을 제시한 것은 TypeSafe의 Jev System One이었다. Jev는 분류 질문에 특화된 포인터 헤드 구조를 통해 범용 LLM 대비 수십 배 빠른 분류 성능을 입증하며 시장을 개척했다. 관련 세부 아키텍처와 측정 결과는 본 사이트의 Jev 실측 평가 기술 분석에 상세히 정리되어 있다.

이후 진영은 두 갈래로 분화했다. 한쪽은 OpenAI Luna Decision API 분석에서 다룬 것과 같이, 클라우드 독점 API 형태로 라우팅을 극도로 단순화하려는 시도다. 다른 한쪽은 오픈소스 진영으로, PostHog가 공개한 Jeeves 의사결정 모델처럼 판단 직전에 가벼운 생각 토큰(reasoning)을 수행하여 고난도 벤치마크의 정확도를 끌어올리는 접근법이다.

Cloudflare Clef의 위치는 이들 사이에서 「엣지 분산 인프라」와 「멀티모달 64K 지원」을 앞세운 오픈 가중치 모델로 정의된다. Jeeves가 추론 토큰을 생성하느라 수 초의 지연 시간을 소모하는 것과 달리, Clef는 순수 비자기회귀 구조를 고수하여 수십 밀리초 대의 응답 속도를 사수했다. 또한 Jev의 독점 호스팅 모델에 맞서 Apache-2.0 오픈 가중치와 Workers AI의 저렴한 토큰당 과금(Clef $0.24, Clef-flash $0.09)을 전면에 내세웠다.

  • Jev와의 관계: API 스키마를 완벽히 호환하면서 컨텍스트를 32K에서 64K로 확장하고 이미지 입력을 추가.
  • OpenAI Decision API와의 차이: 독점 클라우드 API에 갇히지 않고 로컬 구동이 가능한 오픈소스 가중치 제공.
  • PostHog Jeeves와의 차이: Jeeves가 추론 토큰을 통한 정확도 향상을 택했다면, Clef는 비자기회귀 초저지연을 선택.
  • 인프라 통합 경쟁력: Cloudflare Python Workers 및 Workers AI 생태계 내에서의 원클릭 배포 연동.
  • 도메인 트레이드오프: 복잡한 인과 추론은 Jeeves나 범용 LLM이 우세하며, 밀리초 단위 핫패스 분기는 Clef 계열이 우세.

실제 프로덕션 환경에 의사결정 모델을 투입하기 전에 점검해야 할 선택 기준을 아래 표에 요약한다.

도입 워크로드 시나리오 권장 아키텍처 선택 선택 이유 및 고려사항
수십 밀리초 이내의 API 게이트웨이 인라인 트래픽 인가 및 봇 차단 Clef-flash (9B) 비자기회귀 38.8ms 지연(자체 측정 기준)으로 요청 타임아웃 방지
수십 개 필드의 복합 청구서 분류 및 멀티모달 이미지 서류 판정 Clef (27B) 이미지 입력 지원, 64K 컨텍스트, 다중 질문 동시 병렬 평가
복잡한 논리 인과관계 검증 및 다단계 추론이 필요한 사기 탐지 Jeeves (추론 결합형) 또는 범용 추론 LLM 비자기회귀 모델은 생각 체인이 없으므로 심층 인과 추론에 한계
사내 폐쇄망 규제 준수 및 자체 인프라 온프레미스 구동 Clef 오픈 가중치 (Apache-2.0) Hugging Face에서 가중치를 받아 사내 GPU 클러스터에 배포
기존 Jev SDK 기반으로 이미 작성된 파이프라인의 비용 최적화 Workers AI Clef 엔드포인트 Jev API 완전 호환으로 코드 수정 없이 엔드포인트 변경 적용

도입을 검토하는 팀은 먼저 대상 워크로드가 「텍스트 생성이 필요한 과제」인지 「선택지 확률 판정이 필요한 과제」인지를 엄격히 분리해야 한다. 요약문이나 사용자 대화는 일반 LLM에 맡기고, 시스템 분기와 티켓 라우팅은 Clef와 같은 의사결정 모델에 위임하는 이원화 구성이 가장 비용 효율적이다.

  • 과제 성격의 엄격한 분리: 서술형 콘텐츠 생성과 이산형 분기 결정을 단일 파이프라인에서 혼용하지 말 것.
  • 확률 임계값 설계: RLCD로 보정된 실수형 확률을 활용해 안전 마진(Safety margin) 기반 자동화 구축.
  • API 엔드포인트 테스트: Workers AI의 @cf/cloudflare/clef 모델 ID를 이용해 사전 프로토타이핑 수행.
  • 자체 가중치 호스팅 검토: 클라우드 지연에 민감한 환경에서는 Hugging Face 가중치를 활용한 로컬 배포 검토.
  • 플랫폼 성숙도 주의: 셀프서비스 RL 미세조정 플랫폼은 개발 중이므로 초기에는 기본 모델 성능 평가에 집중.

확인하지 못한 것

  • Cloudflare가 38.8ms(Clef-flash) 및 524.1ms(Jev)를 도출한 벤치마크 테스트의 구체적인 GPU 하드웨어 사양(예: A100, H100, L40S 여부)과 네트워크 배치 조건. 공식 블로그에 명시되지 않았다.
  • 비교군으로 사용된 Jev 모델의 구체적인 버전 번호 및 해당 측정이 TypeSafe 호스팅 API를 통해 이루어졌는지 자체 호스팅 가중치로 측정되었는지의 여부.
  • 64K 최대 컨텍스트 윈도우를 모두 채운 상태에서 입력 이미지와 장문 텍스트가 함께 처리될 때 발생하는 추론 지연 시간의 실측 감쇠율.
  • 향후 출시 예정인 셀프서비스 RL 미세조정 플랫폼의 구체적인 출시 일정 및 일반 고객 대상 과금 요금제.
  • 공개된 Apache-2.0 가중치를 TensorRT-LLM이나 vLLM 등 주요 오픈소스 추론 서빙 프레임워크에 즉시 탑재할 수 있는 표준 서빙 레시피의 공식 제공 여부.
