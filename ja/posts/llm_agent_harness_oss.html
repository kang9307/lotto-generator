モデルはテキストを出すだけだ - 残りを決めているのはすべてハーネスである

ツールを呼ぶことも、いつ止めるかも、失敗を再試行するかも、モデルの決定ではない

2026-09-05 開発・インフラ

エージェントがファイルを消したなら、そのファイルを消したのはモデルではない。モデルがしたのは消すツールをこの引数で呼ぶのが適切だという内容の構造化テキストを一塊生成したことだけである。そのテキストを読んで実際のシステムコールを行ったのは、その外側のプログラムだ。

この区別はささいに見えるが、エージェントを運用したことがあればここで分かれる問題がほとんどだと知っている。同じモデルがあるツール群では問題なく回り、別の場所では同じ照会を十回繰り返す。ある環境では失敗したツールをもう一度呼び、別の環境ではすぐに諦める。モデルを替えたら挙動が変わったという報告の多くも、実際にはモデルを包む層の契約が変わったという話である。

その層についた名前がハーネスだ。以下ではハーネスが実際に何を決める場所なのかをベンダー文書の原文フィールドで確かめ、その決定を抜かしたときにどんな症状が出るのかを項目ごとに整理する。フレームワークの紹介や比較はここでは扱わない。コード上でエージェントをどんな形に表すかという問題はクラス・グラフ・設定ファイルがそれぞれ隠すもので別に扱った。

以下に出てくるフィールド名と既定値はすべて Claude API 文書、OpenAI 関数呼び出しガイド、Gemini API 型リファレンス、MCP 仕様とその JSON スキーマの原文表記である。ツール呼び出しの規格はベンダーごとに違い、同じベンダーのなかでも改定されるため、他人が書き写したフィールド名をさらに書き写すことがこの主題で最も多い誤りになる。

きっかけ - あるリポジトリがハーネスという語を掲げた

2026年9月初め、韓国の開発者コミュニティに TrueForge というリポジトリが紹介された。紹介文はLLM を実際のエージェントとして実行するオープンソースのハーネスだった。フレームワークでもライブラリでもなく、ハーネスという語を前面に出したところが目を引く。

リポジトリの公開指標は2026年9月5日04時22分 UTC 時点の値で次のとおりである。スター5,221、フォーク374、オープンな課題91、コミット約515、コントリビューター約31名、言語は TypeScript、ライセンスは MIT、リポジトリ作成日は2026年7月23日で、最後のプッシュは前日の9月4日だ。タグ付きリリースは8月27日付の @truefoundry/trueforge@0.2.0-rc.0 系が最新で、四つの npm パッケージがいずれも1.0以前のリリース候補段階にある。README は Node 22.14 以上を要求する。

スターの数は成熟度ではない。作成から6週間で5千個ついたのは話題性の指標であって安定性の指標ではなく、0.2.0-rc というバージョン表記と91件のオープンな課題が同じ時点の事実として並んでいる。これらの値の解釈は各自に委ね、ここではこのリポジトリが自ら定義したハーネスの範囲だけを借りる。文書はハーネスをLLM の周囲を包み、それを信頼できる長時間実行エージェントに変えるランタイム層と書き、その責任として計画、ツールのルーティングと実行、長い作業のためのコンテキスト管理、サンドボックスや人間の承認といったセキュリティ境界、再接続と再起動をまたいで生き残るセッション状態を挙げる。

この一覧が興味深いのはここにモデルがする仕事が一つもないという点だ。計画もハーネスが管理し、ツールのルーティングも、コンテキストも、承認も、状態もハーネスである。ではモデルは何をするのか。

モデルが実際に返すもの - テキストと止まった理由

モデル API を一度呼ぶと返ってくるのは二つだ。コンテンツブロックの配列となぜ生成を止めたのかである。それがすべてだ。ストリーミングを使おうが使うまいが、ツールを付けようが付けまいが変わらない。

ツールを付けると、その配列のなかにテキストブロックのほかに tool_use ブロックが混じることがある。Claude API 文書はこのブロックが id、name、input の三フィールドを持つと書く。それぞれ、この呼び出しを後で結果と突き合わせるための識別子、呼ぶツールの名前、そしてツール定義の input_schema に従う引数オブジェクトだ。ここのどこにも実行はない。ブロックが届いた時点でファイルはまだそのままである。

止まった理由を載せる stop_reason は、ハーネスが次に何をするかを決める唯一の信号だ。値ごとに要求される処理が違い、そのうちいくつかは抜かしやすい。

stop_reason文書が書く意味ハーネスがすべきこと
end_turn自然に応答を終えたループを終え、結果をそのまま使う
tool_useツールを呼んでおり、実行結果を待っているツールを実行し、結果を戻してから再度呼ぶ
max_tokens要求で指定した上限にかかって切れた上限を上げるか続きを書かせる。切れた tool_use ブロックがあればそのターンは捨てる
stop_sequence指定した停止文字列が出たどの文字列がかかったかを stop_sequence フィールドで確認する
pause_turnサーバー側のツールループが反復上限に達した。既定の上限は要求あたり10回アシスタント応答をそのまま戻して続行させる。ツール結果だけ送るのとは違う
refusal応答を拒否した。エラーではなく正常な200応答であるstop_details で理由の分類を読み、代替経路へ回す
model_context_window_exceededコンテキスト窓の限界に達して止まった切れた応答として扱う。max_tokens とは別の状況である

この表で実務上いちばん抜けやすいのが pause_turn と model_context_window_exceeded だ。前者は tool_use に似た形をしているが処理の仕方が逆であり、後者を max_tokens と取り違えると上限を上げる無駄を繰り返すことになる。分岐を一つ抜かしたハーネスは、その条件で静かに止まったように見える。

責任の境界 - 誰が何を決めるのか

ここで一度まとめておくほうがよい。次の表の左列はエージェントを回すとき必ず誰かが決めなければならない項目であり、中央はその決定が実際にどこで行われるか、右は誰もそれを決めなかったときに出る症状である。

ツールを実際に実行する全面的にハーネスモデルは呼び続けるのに何も起こらない
実行結果を会話へ戻す全面的にハーネス同じツールを無限に呼び直す。結果が見えないので呼んでいないと判断する

失敗を再試行するか全面的にハーネス一時障害で課題全体が死ぬか、逆に認証失敗を二十回再試行する

右列を縦に読むと見覚えのある障害一覧になる。そしてその一覧のどれ一つとしてモデルをより良いものに替えて解決するものはない。最後の行は特にそうだ。Claude API 文書は、ツール結果がウェブページ、受信メール、利用者のアップロード、サードパーティ API のように統制外の出所から来ることが多いため信頼できない内容として扱い、システムプロンプトや通常の利用者テキストブロックではなく tool_result ブロックのなかに置くよう書く。これは配置の問題であってモデル能力の問題ではない。

ツール呼び出しは実行ではなく要求である

モデルがツールを呼ぶという表現が誤解を生む。実際に起きているのは申請書の作成に近い。モデルはツール名と引数を書いた構造を生成し、そこでターンを終える。その後はすべて外側の仕事だ。

この申請書を処理する過程でハーネスが下す決定が少なくとも六つある。

  • 名前の解決 - モデルが書いた名前に対応する実際の関数は何か。同じ名前が複数の MCP サーバーにあるならどちらか
  • 引数の検証 - スキーマに合うか。合わないなら実行するか差し戻すか
  • 権限の判定 - このセッションはこのツールを呼べるか。承認が要る等級か
  • 実行環境 - ハーネスのプロセス内で回すか、隔離されたサンドボックスで回すか
  • タイムアウト - どれだけ待つか。MCP 仕様はクライアントがツール呼び出しにタイムアウトを設けるよう書く
  • 結果の加工 - 戻り値が大きいならそのまま入れるか、要約するかファイルへ逃がしてプレビューだけ入れるか

最後の項目はとりわけ結果に直接影響する。300KB のログをそのままコンテキストに入れると、次のターンからモデルはそのログに押し潰される。プレビューだけ入れると必要な行が切り落とされることがある。どちらを選んでもモデルが見る世界はハーネスが編集した結果物である。ツールを多く付けたときに選択そのものが崩れる地点とカタログを絞る方法はツールは何個まで付けられるかで扱った。

ツール呼び出しという概念は共通だが、契約はベンダーごとに違う。その差がハーネスコードの分岐になり、移植のときに事故が起きる地点になる。

表でまず目に留まる行は引数の形だ。OpenAI の arguments はJSON でエンコードされた文字列で、ほかはオブジェクトである。この一行のためにハーネスには解析失敗の経路がもう一つ生じる。モデルが文法的に壊れた JSON を出したらそれはツール失敗ではなく引数デコードの失敗であり、この二つを同じ通路で処理すると再試行方針がもつれる。

結果をどこに入れるかも分かれる。Claude API は別途の tool ロールを置かず利用者メッセージのなかに tool_result ブロックを入れる方式で、文書はこの点をほかの API との違いとして明記する。ここには守らないと400が返る規則が付く。ツール結果ブロックはそのツール使用メッセージの直後に来なければならず、結果を載せた利用者メッセージでは結果ブロックが配列の先頭に来なければならない。テキストを前に置くと拒否される。

ツール定義が無料ではないという点も契約の一部だ。Claude API 文書は、ツールを付けるとツール使用を有効にするシステムプロンプトが自動で入り、そのトークン数がモデルと tool_choice 設定によって違うと書き、表を提供する。Claude Opus 5 の場合、auto か none なら286トークン、any か特定ツール指定なら406トークンである。ここにツール名と説明とスキーマのトークンが加わる。

失敗をモデルにどう返すか

ツールは失敗する。問題はその失敗をモデルがどんな形で見ることになるのかであり、これは全面的にハーネスが決める。ベンダー規格が決めてくれる部分は思ったより狭い。

区分規格が決めてくれるものハーネスが決めるべきもの
Claude APItool_result の is_error を true に。文書は何が失敗し次に何を試せばよいかを書くよう勧める文面。失敗としか書かないか、再試行可否と待ち時間まで書くか
OpenAI専用のエラーフィールドなし。output の形式は JSON、エラーコード、平文のいずれでも呼び出し側に委ねるエラー表記の規約すべて。モデルが成功と失敗を区別する手がかりを自分で作る必要がある
GeminifunctionResponse の response オブジェクトエラーをそのオブジェクトのどのキーに載せるか
MCPプロトコルエラーとツール実行エラーを分ける。存在しないツールや不正な引数は JSON-RPC エラー、実行中の失敗は結果の isError: true でどの失敗をどちらへ送るかの判定基準

MCP が二つを分けた理由がそのままハーネス設計に使える。モデルが見るべき失敗とモデルが見る必要のない失敗は違う。存在しないツールを呼んだのはプロトコル違反でありクライアントが処理する問題だ。API が429を返したならそれはモデルが知るべき状況である。次に別のツールを使うか少し後で再試行するかという判断の材料になるからだ。

ここでよくある失敗が一つ。エラー文字列をそのまま入れることだ。スタックトレース全体を content に流し込むとコンテキストが侵食され、そのなかに内部パスや資格情報の断片が混じり込むことがある。値ではなく参照を渡す原則はエージェントに資格情報を渡さずに仕事をさせる方法で別に扱った。エラーも同じ原則が当てはまる場所である。

並列呼び出し - パラメータ一つが分けるもの

モデルが一ターンでツールを複数呼べるか。ベンダーはおおむね許し、切る方法を提供する。Claude API は tool_choice のなかの disable_parallel_tool_use を true にすると一ターンのツール呼び出しが最大一つになる。OpenAI は parallel_tool_calls を false にすると正確に0個または1個が呼ばれる。Gemini は並列呼び出しと複数ターンにまたがる連鎖呼び出しをいずれも既定で支援すると文書に書く。

このスイッチ一つがハーネスの構造を大きく変える。

  • 入れると遅延が減り往復回数が減る。代わりにハーネスは複数の結果をすべて集めて戻さねばならず、そのうち一つだけ失敗したときの扱いを決める必要がある
  • 入れたまま副作用のあるツールを開けておくと順序の保証が消える。読みと書きの二つのツールが同じターンに出ると、どちらが先に終わるかはハーネスの実行方式が決める
  • 切ると追跡が楽になり承認の流れが単純になる。代わりに同じ課題に必要なモデル呼び出し回数が増え、費用と時間が増える
  • Claude API 文書はサーバー側ツールとクライアントツールが同じ並列の束に混じる場合を別に説明する。このとき利用者メッセージは結果ブロックだけを載せねばならず、後ろにテキストを付けるとターンが早く終わり400が返る

ここで大事なのはどちらが良いかという結論ではなく、この選択をしていないハーネスはベンダーの既定値をそのまま使っているという事実だ。そして既定値はベンダーごとに違う。

モデルを替えたら挙動が変わったの正体

最初の観察に戻る。モデル交換後にエージェントが違う振る舞いをするとき、その差のどこまでがモデルでどこからがハーネスか。

モデルの能力は明らかに影響する。文書は必須引数が抜けたとき、Claude Opus のほうがそれに気づいて聞き返す可能性がはるかに高く、Claude Sonnet は聞き返すこともあればもっともらしい値を埋めることもあると書く。こうした差は実在する。ただしその上に契約の差が重なっており、後者のほうがはるかに大きく効く場合が多い。

  • ツールスキーマの表現 - 同じツールでも説明文の一行が違えば選択頻度が変わる。ベンダー別アダプタが説明を切ったりスキーマを平坦化したりすると、モデルが見るものが変わる
  • 強制の水準 - auto にするか required にするかはモデル設定ではなくハーネス設定である。アダプタがこれを別々に対応付けると同じプロンプトが違う動きをする
  • 並列の許可 - 前節のとおりだ。既定値の違う二つのベンダーのあいだを移ると呼び出しパターンそのものが変わる
  • エラーの表現 - 失敗を is_error で知らせるハーネスと、ただ文字列で入れるハーネスとでは、モデルの復旧行動が違って出る
  • コンテキストの切り詰め - どの時点で何を要約して捨てるかが違えば、後半の行動がまるごと変わる
  • システムプロンプトの注入 - ツールを付けるだけでベンダーが自動で入れるシステムプロンプトがあり、その内容と大きさはベンダーと設定によって違う

実務的にこれが意味するのは一つだ。モデル比較をするならハーネスを固定しなければならない。ハーネスの違う二つの環境から出た数字をモデル性能比較と呼べば、再現しない結論が残る。検証そのものを自動化するときどこまで機械が判定できるかの境界は検証ハーネスが引いた境界線で別に整理した。

停止条件 - いつ止めるかを決めないと

ここからがハーネスが必ず決めなければならない項目だ。決めないと既定値がないのではなく、暗黙のうちに制限なしが既定値になる。

モデルには予算という概念がない。毎ターン、ツールをもう一つ呼ぶほうがもっともらしく見えればそうする。その判断は残りの費用や経過時間を材料にしない。それを測る場所は外側だけである。

上限何を測るかないときの症状かかったとき何をするか
最大ステップ数モデル呼び出しの往復回数同じ照会を変形しながら繰り返す。結果は正常に見える中断し、ここまでの進捗を要約して利用者へ渡す
費用上限累積の入出力トークンと換算金額請求書で事後に知ることになる中断するか、より安いモデルへ落とす
実時間上限セッション開始からの実際の経過時間利用者が応答を待たされたまま放置される部分結果を出し、続けるかどうかを尋ねる
ツール別の呼び出し回数同じツールを何回呼んだか一つのツールだけでループが回る。全体のステップ数はまだ余裕があるそのツールをこのセッションで封じ、モデルへ知らせる
無進捗の検知連続して同じ引数の呼び出しが何回かステップ数は増えるのに状態はそのままだ同じ呼び出しであることを結果で知らせ、別の経路を探させる

実務でより頻繁に問題になるのは無限ループではなく静かな浪費だ。二十ステップで終わる課題を八十ステップで回るエージェントは、最終結果が合っているので誰も異常を感じない。その差は記録を付けるまで表に出てこない。自律エージェントが予算を焼く極端な事例はAI エージェントの請求書事故にまとめてある。

失敗の分類 - もう一度呼ぶものとそうでないもの

ツールが失敗したときハーネスが答えるべき問いは二つだ。もう一度呼ぶか、そしてモデルに知らせるか。この二つは別物である。

  • 一時的な失敗 - ネットワークのタイムアウト、502、429。ハーネスが静かに再試行するのが正しい。バックオフを置き、回数の上限を置き、それでも失敗したらそのときモデルへ知らせる。毎回の試行をモデルへ知らせればコンテキストを浪費するだけだ
  • 恒久的な失敗 - 404、認証拒否、存在しないリソース。再試行しても同じ結果である。モデルへ即座に知らせ、別の経路を探させるのが正しい
  • 引数の誤り - スキーマ違反、必須値の欠落、JSON の解析失敗。モデルが直せる唯一の分類だ。何が抜けたかを書いて戻す。Claude API 文書はこの場合、モデルが情報を埋めて二三回やり直したのち利用者に謝ると書く
  • ポリシーによる拒否 - 承認の却下、権限不足。再試行の対象ではなく、モデルへ知らせるべきである。ただし拒否理由をそのまま伝えるかは別の判断だ
  • 部分成功 - 十件のうち三件が失敗。最も扱いが難しい。全体を失敗と見るか、成功分を確定して失敗分だけ知らせるかがツールごとに違う

この分類をしないと二方向に壊れる。すべて再試行すれば認証失敗を二十回繰り返し、すべてモデルへ渡せば一時的な502一つで課題全体が方向を変える。どちらもモデルが悪くて起きたことではない。

冪等性 - 二度呼んでよいツールか

再試行を導入した瞬間に新しい問いが付いてくる。そのツールを二度呼んでよいのか。決済、メール送信、チケット生成、デプロイは二度呼べば二度起きる。最初の呼び出しがタイムアウトで終わったからといって実行されなかったという意味ではない。応答を受け取れなかったことと実行されなかったことは違う。

MCP はツールが自分の性質を表示する場所を用意している。ToolAnnotations の四つのフィールドだ。ただしスキーマの説明文がその位置づけをはっきり釘刺ししている。

  • readOnlyHint - 真なら環境を変えないツールである。既定値は偽
  • destructiveHint - 真なら破壊的な更新をしうる。偽なら追加のみを行う。readOnlyHint が偽のときにだけ意味を持つ。既定値は真
  • idempotentHint - 真なら同じ引数で繰り返し呼んでも追加の効果がない。これも readOnlyHint が偽のときにだけ意味を持つ。既定値は偽
  • openWorldHint - 真なら外部の実体からなる開いた世界と相互作用する。ウェブ検索は開いた世界でメモリツールは閉じた世界だというのがスキーマの例示だ。既定値は真
  • そして決定的な一文 - ToolAnnotations のすべての属性はヒントであり、ツールの挙動を忠実に説明する保証はない。スキーマは信頼できないサーバーから受け取った値でツール使用の判断をしてはならないと明記する

既定値の向きがすべて保守的だという点は見ておく価値がある。何の表示もないツールは破壊的で冪等でなく開いた世界と相互作用するツールとして扱えという意味だ。そしてヒントはヒントであるから、再試行の安全性は結局ハーネスが自分の側で担保するしかない。方法は三つのうち一つだ。呼び出しごとに冪等キーを作ってツールへ渡すか、再試行の前に照会で状態を確かめるか、副作用のあるツールはそもそも再試行の対象から外すかである。最後の選択肢が最も頻繁に正解になる。

承認地点 - 人が割り込む場所

MCP 仕様は信頼と安全を理由にツール呼び出しを拒否できる人が常にループのなかにいるべきだと書き、アプリケーションに三つを勧める。どのツールがモデルへ露出しているかがはっきり見える UI、ツールが呼ばれるときの視覚的な表示、そして確認プロンプトである。サーバーを呼ぶ前にツール入力を利用者へ見せよという条項も別にある。悪意あるいは過失によるデータ流出を防ぐためだ。

承認をどこに置くかはハーネスの方針の問題である。位置はおおむね四つのうち一つだ。

  • ツール単位 - 特定のツールは常に承認。実装が最も単純で予測しやすい
  • 引数単位 - 同じツールでも引数によって分かれる。一時ディレクトリの削除は自動、それ以外の経路は承認といった具合だ
  • 累積単位 - このセッションですでに N 回承認したならそれ以降は自動。承認疲れは減るが境界がぼやける
  • 結果単位 - 実行はするが確定の前に止める。ドライランが可能なツールでのみ成り立つ

承認地点をまったく置かないと取り消せない操作が通知なしに実行される。逆にすべてに置くと人が内容を見ずに押しはじめる。二つの軸で等級を分ける方法は権限設計と事故の遮断線にまとめてあるのでここでは繰り返さない。ハーネスの観点から付け加えることは一つだ。承認待ちのセッションの状態をどこに置くか。メモリにしかなければデプロイ一回で待機中の作業がすべて消える。

記録 - どのツールをどの引数で呼んだのか

事故が起きたら答えるべき問いは決まっている。どのツールを、どの引数で、何時に、誰の要求で呼び、結果は何だったのか。この問いに答えられる記録はハーネスにしか作れない。モデルは自分が何を呼んだかを覚えていない。会話履歴に残っているものを読み直すだけである。

MCP 仕様はクライアントに監査目的のツール使用ログを勧め、結果をモデルへ渡す前に検証せよと書く。最低限残すべき項目は次のとおりだ。

  • 呼び出し識別子とそれに対応する結果 - 対が合っていてはじめて事後の再構成ができる
  • ツール名と引数の全文 - 要約だけ残すと事故調査で役に立たない。ただし引数に機微な値が入りうるのでマスキング規則が併せて要る
  • 実行時刻と所要時間 - どのツールが遅延の原因かはこれなしには分からない
  • 失敗の分類と再試行回数 - 前節の分類が記録に残ってはじめて方針が正しかったか判定できる
  • トークン使用量と累積費用 - ステップ別に残してはじめてどの区間が高かったかが出る
  • コンテキスト編集の履歴 - 何が切り落とされたかが残らなければ、モデルがなぜその判断をしたのかを再構成できない

最後の項目が最も頻繁に抜ける。要約と切り詰めはハーネスが静かに行う作業なのでログに残さない場合が多く、その結果同じ入力でもう一度回しても同じ結果が出ない状態になる。セッション実行をトークン浪費の観点で解剖する方法はエージェントのブラックボックス分析に、本番で誤りを追跡する構成はLLM 可観測性の実務ガイドにある。

状態とコンテキスト - 切り詰めるとき消えるもの

長い課題はコンテキスト窓を超える。そのときハーネスがするのが切り詰めだ。TrueForge の文書はこの機能を既定で有効にし、発動条件をモデルのコンテキスト長の80パーセント、その値が分からないときは入力トークン5万と書く。併せて書かれた一文のほうが重要である。圧縮は作業コンテキストでは損失を伴い、セッション履歴の全体は API で照会できる。

この二文が状態設計の核心を含んでいる。モデルが見るものとシステムが保管するものは別の物である。前者は呼び出しのたびに再構成される編集版で、後者は追記のみの記録だ。この二つを同じものとして扱うハーネスは二方向のどちらかで壊れる。編集版しかなければ事後の再構成ができず、記録しかなければ窓を超えて要求が失敗する。

切り詰めの方式ごとに失うものが違う。

  • 古いものから捨てる - 実装が最も楽だ。失うのは初期の指示と制約条件である。長い作業の後半で元の要求を破る典型的な症状はここから出る
  • 要約で置き換える - 分量は減るが、要約が何を残すかはもう一つのモデル呼び出しが決める。要約の段階で消えた情報は戻ってこない
  • 大きな結果を外へ逃がす - ツールの戻り値をファイルに保存しプレビューだけ入れる方式だ。モデルが必要なら読み直せるので損失は小さいが、読み直す呼び出しがステップ数を増やす
  • ツールスキーマを後から載せる - 名前と説明だけ先に与え、スキーマは必要なときに取りに行く方式だ。TrueForge の文書はこの機能の既定値が先読みしないことだと書く
  • 下位エージェントへ隔離する - 細部の作業を別のコンテキストで回し、最終結果だけを上へ上げる。伝達の損失と調整の費用が新たに生じ、その境界は役割分担シミュレーションの境界で別に扱った

どの方式であれモデルは自分が何を忘れたかを知らない。切り落とされた場所に印が残らないからだ。だから切り詰めの方針は記録すべき項目でなければならない。

ループをコードで見ると

前の項目を一つの流れに載せるとこんな形になる。以下は特定の SDK の API ではなく、決定地点を浮かび上がらせるための骨格だ。実際のフィールド名は上の表のベンダー別契約に従う。

// ハーネスループの骨格 - 決定地点に注釈を付けた
async function runAgent(task, tools, limits) {
  const messages = [{ role: 'user', content: task }];
  let steps = 0, spent = 0;
  const startedAt = Date.now();

  while (true) {
    // 決定1: 停止条件。モデルはこれを測らない
    if (steps >= limits.maxSteps) return stop('MAX_STEPS', messages);
    if (spent >= limits.maxCost) return stop('BUDGET', messages);
    if (Date.now() - startedAt >= limits.maxWallClockMs) return stop('TIMEOUT', messages);

    const res = await model.call({ messages, tools, toolChoice: limits.toolChoice });
    steps += 1;
    spent += estimateCost(res.usage);
    record({ steps, usage: res.usage, stopReason: res.stopReason });  // 決定6: 記録

    // 決定2: stop_reason の分岐。一つ抜けるとその条件で止まったように見える
    if (res.stopReason === 'end_turn') return finish(res);
    if (res.stopReason === 'refusal') return handleRefusal(res);
    if (res.stopReason === 'max_tokens') return handleTruncated(res);
    if (res.stopReason === 'pause_turn') { messages.push(asAssistant(res)); continue; }

    const calls = res.content.filter((b) => b.type === 'tool_use');
    if (!calls.length) return finish(res);

    // 決定3: 並列で実行するか順次にするか
    const results = limits.parallel
      ? await Promise.all(calls.map(execute))
      : await runSequentially(calls, execute);

    messages.push(asAssistant(res));
    messages.push(asToolResults(results));   // 結果ブロックは配列の先頭に来なければならない

    // 決定4: コンテキストが閾値に達したら何を捨てるか
    if (estimateTokens(messages) >= limits.compactAt) await compact(messages);
  }
}

ツールを一つ実行する部分には承認と失敗の分類が入る。以下で classify が返す値が再試行の可否を決め、冪等キーが副作用の重複を防ぐ。

// ツールの実行 - 承認、冪等性、失敗の分類がすべてここに集まる
async function execute(call) {
  // 決定5: 承認地点。引数を見せてから尋ねる
  if (needsApproval(call)) {
    const verdict = await askUser(call.name, call.input);   // 待機状態は永続ストレージへ
    if (verdict !== 'allow') return toolError(call.id, 'POLICY_DENIED: 利用者が拒否');
  }

  // 副作用のあるツールには呼び出しごとに固定されたキーを与える。
  // 表示のないツールは破壊的で冪等でないものとして扱う
  const key = isSideEffecting(call) ? idempotencyKey(call) : null;

  let attempt = 0;
  while (true) {
    try {
      const out = await invoke(call.name, call.input, { key, timeoutMs: TOOL_TIMEOUT_MS });
      return toolResult(call.id, truncateOrOffload(out));   // 大きな結果は外へ逃がす
    } catch (err) {
      const kind = classify(err);   // TRANSIENT / PERMANENT / BAD_ARGS / DENIED
      // 一時的な失敗だけ静かに呼び直す。それ以外はモデルの判断へ渡す
      if (kind === 'TRANSIENT' && key && attempt < MAX_RETRY) {
        await backoff(attempt++);
        continue;
      }
      return toolError(call.id, redact(summarize(err, kind)));   // 原文ではなく要約とマスキング
    }
  }
}

同じ結果を三つのベンダーへ返すときの形はこう分かれる。概念は一つなのにフィールドが三つあることが、アダプタ層が必要な理由である。

// 同じ失敗を三つの契約で返す - 値はすべてプレースホルダである
// Claude API - 利用者メッセージ内の結果ブロック。専用のエラーフラグがある
{ "role": "user", "content": [
  { "type": "tool_result", "tool_use_id": "TOOL_USE_ID",
    "content": "RateLimited: 60秒後に再試行可能", "is_error": true } ] }

// OpenAI - 専用のエラーフィールドがない。表記の規約はハーネスが決める
{ "type": "function_call_output", "call_id": "CALL_ID",
  "output": "{\"ok\":false,\"code\":\"rate_limited\",\"retry_after_s\":60}" }

// MCP - 実行中の失敗は結果のなかで、存在しないツールや不正な引数は JSON-RPC エラーで
{ "jsonrpc": "2.0", "id": 4, "result": {
  "content": [ { "type": "text", "text": "RateLimited: 60秒後に再試行可能" } ],
  "isError": true } }

自分で作るか、既存のものを使うか

ハーネスは薄く見える。ループ一つに分岐がいくつかあればよさそうに見えるし、実際に最初の版は半日でできる。問題は上で並べた項目こそがハーネスだという点である。停止条件、失敗の分類、冪等性、承認、記録、コンテキストの編集、セッションの永続化をすべて入れてしまえば薄くはない。

判断の軸自分で作るほうが合う条件既存のものを使うほうが合う条件
ツールの数三つ四つで固定されており増える予定がないMCP サーバーを継続的に付ける予定だ
副作用すべて読み取り専用である書き込みと決済と送信が混じっている
実行時間一回の要求のなかで終わる再接続と再起動をまたいで続かねばならない
利用者作った本人だけが使う複数人が使い、誰が何をしたか残らねばならない
ベンダー一つに固定である複数のベンダーを行き来する。アダプタ層がどのみち要る
承認の流れ不要か、すべて自動である人が途中で割り込み、その状態が生き残らねばならない
記録の要求標準出力で足りる監査記録と費用の分解が求められる
運用の余力一プロセスで足りる複数のレプリカとデータベースを運用する余力がある

右列に二つ以上当てはまるなら自分で作る費用は思ったより大きい。逆に左列にすべて当てはまるなら他人の抽象を持ち込むほうがむしろ損だ。複数のエージェントを一つのリポジトリに同時に放したときに生じる隔離の問題はハーネス選択とはまた別の軸であり、並列コーディングエージェントの衝突と隔離で扱った。

きっかけになったリポジトリへ戻ると、その文書が掲げる機能一覧は上の表の右列とほぼ重なる。サンドボックスをツールとして置く方式、下位エージェント、ツールスキーマの遅延読み込み、大きな結果のオフロード、圧縮、ツールの承認、聞き返し、生成 UI、そしてローカルモードの SQLite とホスト型モードの Postgres および Redis だ。README はローカルモードは自分の機器専用であり、既定でログインがなく、本番やインターネット公開向けではないと自ら書く。こうした一文が文書にあるかないかが導入判断の材料になる。

リポジトリは自前のベンチマークも公開する。DevRev の Enterprise-Bench から取った14の課題を、同じモデル、同じ三つの MCP サーバー、同じシステムプロンプトで構成ごとに3回ずつ回し、別の LLM 審査者が採点する方式で、相手は閉鎖型が一つとオープンソースが一つだ。ただしこの測定はプロジェクト自身が行ったものであり、第三者による再現結果は併せて提示されていない。自前のベンチマークは設定を公開したという点で意味があるが、独立検証とは別の物である。

確認できなかったこと

  • Gemini の関数呼び出し文書で表記が二通りに見える。型リファレンスは functionCall と functionResponse のパートに args と response のオブジェクトを使う形を書くが、ガイドページのほうは function_call と function_result に call_id を使う形に読める。どちらがどの SDK バージョンの正本なのかは文書だけでは分かれなかったため、本文の表には型リファレンスの表記を載せた
  • Gemini の functionResponse にエラー専用のフィールドがあるかは型リファレンスで見つけられなかった。本文には response オブジェクトのなかに載せるとだけ書いた
  • OpenAI の文書にはツール実行エラーを表す専用フィールドがなく、output の形式は呼び出し側の裁量だとだけある。モデルが失敗をどんな形で認識するよう訓練されたかは文書にないため、エラー表記の規約の効果は各自が測る問題として残る
  • Claude API の pause_turn の既定上限10回を要求単位で調整できるかは当該文書に明記が見当たらなかった
  • TrueForge の再試行方針、最大ステップ数の既定値、費用上限の設定場所は公開文書の目次の項目名だけでは特定できなかった。本文で引いたのは圧縮の閾値や遅延読み込みの既定値のように文書に数値が書かれた項目だけである
  • リポジトリの指標は2026年9月5日04時22分 UTC 時点の値だ。スター5,221やコミット約515、コントリビューター約31名といった数値が運用の安定性とどう関係するかは、これらの値だけでは言えない
  • MCP 仕様はクライアントにツール呼び出しのタイムアウトを設けよと書くが推奨値は示さない
