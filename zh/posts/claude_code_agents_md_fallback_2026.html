1. 缘起与背景 — 2.1.277版本所公布的AGENTS.md支持本质

一般而言，在运用人工智能编程助手的开发环境中，开发者普遍习惯在代码仓库中维护标准的Markdown规范文件，借此在会话阶段向模型灌注项目开发规范以引导一贯的输出。

在Claude Code体系内，CLAUDE.md长期承担着项目指令集的核心标准角色。2026年9月，伴随2.1.277版本的发布，相关消息得以公布。依据通过X平台转述的文句，Thariq指出：「We're adding support for AGENTS.md to Claude Code. Starting today in version 2.1.277, if there is no CLAUDE.md in a folder, Claude will check for and use AGENTS.md. You can toggle this behavior in /config.」。

据GeekNews的二次摘要阐述，该功能作为Claude Code全新客制化系统Mods之上的内建模块（built-in mod）实现，源码已在官方代码库全面开放。摘要指出这一改进「使得开发者无需额外复制CLAUDE.md或建立软链接」。社区反响中亦涌现出「终于支持」等欢迎态度。

查阅官方代码库中的核心README文件，该模块定位被明确表述为：「The agents-md mod allows Claude Code to read AGENTS.md files as instruction files, similar to how it reads CLAUDE.md files.」。本篇分析的推论认为，在默认配置下仅当CLAUDE.md缺失时才会加载AGENTS.md，因此项目现有文件构成将直接决定模型实际接收到的指令内容。

2. 基本工作原理 — 属于替代而非合并（claude-md-or-agents-md）的运行边界

官方README明确指明，插件的默认选项取值为claude-md-or-agents-md。依据文档中所规定的实际规则，仅当项目自身不存在指令文件时，系统才会在原本加载CLAUDE.md的相应位置替代并加载AGENTS.md。

README对所谓「项目自身指令文件（of its own）」的判定标准作出了如下界定：

  • 从项目根目录至当前工作目录的整条路径链条中，若引擎成功加载了任意目录下的CLAUDE.md、.claude/CLAUDE.md或CLAUDE.local.md文件；
  • 一旦上述三类专属文件中有任一存在，引擎将全权接管项目指令处理，插件将保持静默且完全不介入上下文注入（leaves the whole project to the engine, and the plugin stays out）；
  • 相对而言，企业组织托管文件、用户家目录下的~/.claude/CLAUDE.md、.claude/rules规则文件，以及通过--add-dir参数动态挂载目录内的CLAUDE.md，由于不会在嵌套目录树遍历中被检视，因而均不被计入项目自身文件；
  • 唯有当上述排查确认整条路径上毫无项目专属指令文件时，该路径上所有的AGENTS.md及.claude/AGENTS.md方可被统一纳入引擎渲染的指令列表之中。

在同级目录优先权判定上，规则同样明确。若在同一物理目录下同时存在CLAUDE.md与AGENTS.md，则CLAUDE.md独占该目录的处理权，同级AGENTS.md将被完全忽略。在默认状态下，若工程内存在CLAUDE.md，新增编写的AGENTS.md将不会传递至模型。

本篇分析的推论认为，在默认配置下只要存在任一CLAUDE.md则AGENTS.md完全不会生效，若需两类文件共存则必须显式切换至合并模式。

3. 4种instructionFiles选项与加载策略对比

根据README阐述，该内建插件受控于单一的instructionFiles配置项，且内置支持四种互斥的运行模式。每种取值均会改变核心引擎与插件间的指令文件汇聚机制。

规范中列出的四种模式详细定义如下：

  • claude-md：引擎遵循既有行为模式仅加载CLAUDE.md文件体系，插件处于静默状态，不向上下文增添任何内容。
  • claude-md-or-agents-md：插件的默认设置。仅在项目自身完全缺乏CLAUDE.md指令文件的前提下，替补注入AGENTS.md。
  • claude-md-and-agents-md：纵贯目录树上下层级，将所有AGENTS.md与CLAUDE.md并行合并载入，同时执行严格的链接与导入查重。
  • managed-only：强制从提示词上下文中剔除项目代码库检入的指令、本地私有指令以及个人配置，仅保留组织集中托管的指令文件与会话记忆。

下表依据官方文档技术细节，全面比对了四种工作模式的载入对象与其触发准则：

配置模式取值 注入模型上下文的指令文件 默认状态及触发约束
claude-md 仅加载引擎原生遍历发现的CLAUDE.md文件 非默认。插件完全静默，仅维持原生引擎单轨读取
claude-md-or-agents-md 当项目缺失CLAUDE.md时替补加载AGENTS.md 默认（default）。若项目内存在自身指令则插件自动退避
claude-md-and-agents-md 在整个目录树内全量合并CLAUDE.md与AGENTS.md 非默认。两套规范共存，按路径与内容两阶段比对去重
managed-only 仅保留组织管控的CLAUDE.md与引擎会话内部记忆 非默认。强制剥离仓库自身检入与个人本地的全部非托管指令

README进一步披露了文件交付至底层语言模型的调用管道。文件最终呈现并非由插件独立执行，而属于引擎的专属调度职责。底层钩子prompt.context将挂载于claudeMd之后的指令文件数组（数据结构为{ path, kind, content, parent? }，按managed、user、project、local、memory分类排序）递交给插件，插件钩子计算后返回修改后的列表。引擎随即运用统一样式渲染前言和框架标记，向控制台汇报装载文件名，并在针对特定智能代理角色（如Explore、Plan或带有omitClaudeMd的自定义代理）时执行合规过滤，仅保留托管类文件。

本篇分析的推论认为，4种选项确定性地分流了项目指令的纳入判定与实际读取范围。

4. 场景检索规则 — 同级目录、子目录Read读取、软链接匹配

随着仓库规模演进，指令文件在何种时机被检索加载具有重要意义。官方文档针对层级递进与链接判定制定了具体规则。

关于子目录中AGENTS.md文件的加载时机，README写明：「Nested AGENTS.md files attach on text Read operations only」。当智能代理执行文本Read操作读取源码文件时，引擎回溯从项目根目录至目标文件路径中间的所有目录节点，途经发现的AGENTS.md被动态追加至当次会话上下文。即便处于此动态追加链路中，只要某子目录内存在CLAUDE.md，依然由其抢占该节点，对应的AGENTS.md不被附加。

下表归纳了典型工程目录布局在不同运行模式下的加载结算形态：

测试场景与目录文件构成 生效工作模式 实际生效结果与运行表现
项目根目录下同时放置CLAUDE.md与AGENTS.md claude-md-or-agents-md（默认） CLAUDE.md独占根节点，同级AGENTS.md完全被忽视
仓库内无任何CLAUDE.md，仅在根目录放置AGENTS.md claude-md-or-agents-md（默认） AGENTS.md被装载至原本属于CLAUDE.md的指令槽位
根目录有CLAUDE.md，特定子包目录下有AGENTS.md claude-md-or-agents-md（默认） 因根目录已存在项目指令，子包目录下的AGENTS.md不被读取
根目录有CLAUDE.md，特定子包目录下有AGENTS.md claude-md-and-agents-md（合并） 当读取该子包内文件时，路径上的AGENTS.md按需动态挂载
通过软链接将AGENTS.md映射至同目录CLAUDE.md claude-md-and-agents-md（合并） 经由路径字符串及文件内容比对检出重复，自动避免二次加载

关于符号软链接（symlink）的处理边界，README指出，插件在比对去重时依据文件路径的字面拼写（spelling）直接进行比对，并不会如同原生引擎那般将软链接解析为真实物理路径。若路径格式存在差异，引擎的文件探索与插件的重复判定之间可能产生分歧。

本篇分析的推论认为，子目录中的AGENTS.md在执行文本Read操作之前的常规对话阶段并不会被纳入上下文。

5. @导入审批与去重机制 — claude-md-and-agents-md合并模式细节

在开启claude-md-and-agents-md模式时，处理@指令导入具有明确规则。

README阐明了去重机制：

  • 凡是被CLAUDE.md已然通过@语法导入，或作为符号链接目标引用的文件，免除二次加载；
  • 去重判定机制优先比对文件路径字面量，若路径不同，则进一步对文件原始文本内容（content）执行直接比对；
  • 在AGENTS.md内部所编写的@导入语法，套用与CLAUDE.md完全等同的外部导入审批（approval）机制；
  • 任何未获得明确用户批准的外部文件引入请求，均被排除在有效指令上下文之外。

本篇分析的推论认为，当路径不同但文本内容一致时重复加载将被拦截，外部指令导入仅在通过审批后方可注入。

6. 组织治理与managed-only模式下的上下文隔离

在组织环境中，存在统一治理指令文件的要求。managed-only选项正是为了应对这种集中治理诉求而设计的隔离配置。

依照README所列出的运行特征，在managed-only模式生效时：

  • 项目中检入的代码库指令（包含CLAUDE.md与AGENTS.md）、本地个人文件（CLAUDE.local.md）以及用户个人配置（~/.claude/CLAUDE.md）均被剔除出上下文；
  • 仅保留组织集中部署的托管类CLAUDE.md以及引擎内建的会话记忆；
  • 引擎全局的claudeMdExcludes排除过滤机制照常运转，并覆盖由本插件读取的AGENTS.md文件；
  • 企业在prompt.context钩子链最前端预先挂载的插件位列本插件之上，对最终指令集拥有决定权。

技术文档中注明：在文本Read操作时触发的引擎内部嵌套CLAUDE.md附加机制，由于尚未完全转换为外部钩子事件，因而在managed-only模式下仍可能会动态抵达（still arrive）。源码register.ts中展示了利用Files.isKeptWithoutInstructions对Files.DROPPED_KINDS进行数组过滤的实现逻辑。

本篇分析的推论认为，managed-only模式排除了仓库内部的指令文件，仅保留组织托管文件与引擎记忆。

7. 配置方式与向后兼容 — /config、JSON配置与旧版键名迁移

该插件的控制界面同时支持交互式命令行指令与静态配置文件两种途径。README针对具体的配置参数格式与位置给出了说明。

在交互终端内，用户可输入/config命令，并在列表中选中「Project instructions」项。官方文档将该界面定义为一个在四项可选模式间切换的选择器（picker），并逐项附带说明。

通过静态配置文件进行配置时，开发者可在用户级配置文件（~/.claude/settings.json）、CLI启动时通过--settings参数指定的文件，或者托管配置中注入如下JSON结构。README所给出的配置模板如下：

{
  "pluginConfigs": {
    "agents-md@builtin": {
      "options": { "instructionFiles": "claude-md-and-agents-md" }
    }
  }
}

个别工程根目录下的.claude/settings.json文件并不会被读取用于解析插件选项。README声明该选项仅在全局用户配置或托管配置中生效。配置项一经更改，插件模块将即时重载，并在引擎构建下一次上下文时（包括随后的对话回合、开启新会话、运行/clear或执行上下文压缩）应用新模式。

若手动输入了不属于标准四值的字符串，控制台日志（transcript）将输出单次提示，并自动回退至默认的claude-md-or-agents-md模式。在/plugin命令列表中，该内建插件同样支持手动禁用，关闭后引擎将退回单纯解析CLAUDE.md的状态。

关于配置键的历史演进，文档亦提供了说明。早期阶段该配置项曾命名为projectInstructions，对应枚举值为claude、agents-fallback、both及none。根据README与register.ts源码，在instructionFiles未被显式覆写的情况下，旧键名将按如下映射关系继续被识别生效：

  • none → managed-only
  • claude → claude-md
  • agents-fallback → claude-md-or-agents-md
  • both → claude-md-and-agents-md

其余非法值将被映射至不附带额外文件的claude-md。首个session.start事件会在日志中记录该旧键的解析结果。一旦新配置项instructionFiles被赋予非默认值，系统将停用旧键读取，并提示用户从配置文件中移除旧键。

8. 实务验证流程与注意事项 — 测试命令与架构权衡

分析代码库目录形态可知，该模块主要由清单.claude-plugin、包含入口register.ts的钩子目录hooks/、自动化测试集tests/以及核心说明文档README.md组成。工程团队可执行README中记载的原生测试指令对模块进行校验：

claude plugin test mods/agents-md

在将这一机制落入工程环境时，开发团队应审视以下注意事项：

  • 根目录指令造成的隐蔽屏蔽：在默认的claude-md-or-agents-md模式下，只要根目录存在CLAUDE.md，子目录中的AGENTS.md就会失效。启用AGENTS.md需将配置显式切换至claude-md-and-agents-md（本篇分析的推论）。
  • 多包单体仓库的动态载入滞后：子目录规范仅在文本Read发生时才被动态附加。因此在文件读取前的总体规划阶段，下层规则尚未注入模型（本篇分析的推论）。
  • 符号链接字面量比对边界：去重逻辑依赖路径字符串字面值而非物理路径解析。相对路径格式各异可能导致去重逻辑未被触发（本篇分析的推论）。
  • 本地配置引发的团队行为不一致：插件配置存放于个人全局而非仓库本地的.claude/settings.json。团队成员配置不一致会导致同一仓库下加载的指令产生分歧（本篇分析的推论）。

本篇分析的推论认为，由于默认行为属于条件替代而非无条件合并，团队必须依据代码库文件结构显式设定instructionFiles模式。
