自己写数据网格为什么会塌

前三个需求是加法，第四个开始是乘法 - 表格UI比看上去难的真正原因

2026-07-29 IT/技术

引言：一张表格如何变成三周的长篇故事

分步骤自己实现数据网格的记录，在开发者社区里会周期性地回来一次。这是个有意思的体裁。第一步永远三十分钟搞定，而到最后一步，作者通常会抵达某种版本的「原来这就是大家用现成库的理由」。本文并不是对其中某一篇的摘要。由于无法确定作为起点的那篇原文，与其照搬别人的目录，本文选择处理「自己实现数据网格」这个问题本身。

同时这也不是教程。它不讲「照这样做」。它要回答的是两个问题：「到底该不该自己做」，以及「如果要做，究竟会在哪里塌掉」。代码只出现到足以说明概念的最小程度。

先把原则钉住。本文的技术性叙述均于2026年7月29日在MDN、W3C的WAI-ARIA创作实践指南(APG)以及各项目官方文档中直接核实，无法核实的说法一律删去。文中不推荐也不排名任何库，涉及库的叙述仅限于官方文档中写明的设计与许可事实。

1. 从加法到乘法 - 三个需求与四个需求之间

大家都说表格UI难，但为什么难却很少被讲清楚。关键不在功能的数量，而在功能之间相互作用的数量。

排序、筛选、分页。到这里三者几乎互不干扰。它们都可以归结为「接收一个数据数组、返回另一个数组的函数」，渲染只需把结果画出来。定好顺序塞进管线就完事。所以头三天是愉快的。

从第四个开始性质变了。虚拟滚动、列冻结、列宽调整、单元格编辑和键盘无障碍动的不是数据，而是渲染与交互的状态。而这份状态是共享资源：滚动位置、真正存在于DOM中的行集合、焦点在哪里、由谁计算布局。五个功能同时抓住这四项资源。

功能组合性质相互争夺的资源体感难度
排序数据变换无半天
排序 + 筛选数据变换大致只有应用顺序一天
排序 + 筛选 + 分页数据变换筛选后总数的重新计算两天
+ 虚拟滚动渲染状态DOM行集合、滚动位置进入以周计的区间
+ 列冻结布局层叠上下文、横向滚动再加几天，浏览器差异明显
+ 列宽调整布局布局算法、重算频率与虚拟滚动再次冲突
+ 单元格编辑焦点与输入焦点位置、输入合成状态加上输入法后陡增
+ 键盘无障碍结构决策Tab序列、焦点所有权后补等于重写

表格最右一列说的事情很简单：做排期时数功能个数会得到错误的数字。数功能两两配对的个数才更接近现实。五个功能就是十对，而这十对中的每一对都是一个独立问题：这两个同时开启时会发生什么。

下面各节逐一打开这些问题。

2. 虚拟滚动悄悄拿走的东西

虚拟滚动的原理只有一句话：只为可视范围内的行创建DOM，其余的不创建。不画十万行只画三十行，自然快。做到这一步谁都可以。

问题在后面。浏览器的许多内置能力都建立在「东西存在于文档中」这个前提之上，而虚拟滚动恰恰打破了这个前提。

  • 页内查找 — 浏览器只找文档里有的东西。被删掉的行不是搜索对象。用户得出的结论不是找不到，而是它不存在。
  • 文本选择与复制 — 拖拽跨越几屏做选择的操作不再成立，因为滚动过程中身后的行会消失。
  • 无障碍树 — 对屏幕阅读器来说那些行同样不存在。此处就需要ARIA来补偿。
  • 表格语义 — 做虚拟化时常用的手段是改表格元素的display，而MDN对这一点有明确警告。
  • 浏览器默认的锚定 — 滚动途中上方内容尺寸变化会导致位置跳动。第5节单独讨论。

第四条值得引用。MDN的display文档在无障碍一节写道，在某些浏览器中把表格元素的display值改成block、grid或flex会改变它在无障碍树中的表示，导致表格无法被正确朗读。同一文档还写明display: none会把元素从无障碍树中移除，而display: contents在部分实现中会把元素自身从无障碍树中移除，并指出这依照规范属于不正确的行为。也就是说，你以为只改了外观的一行，动到了语义结构。

ARIA一侧的补偿是有定论的。MDN的aria-rowcount文档说明该属性定义表格、网格或树形网格的总行数，而取值-1表示尺寸未知，用来告诉浏览器不要去统计总行数。文档明确指出，应当在并非所有行都始终存在于DOM中时加上这个属性；当全部行都已加载并在DOM中时不必加，因为浏览器会自动统计。W3C的APG网格模式也表达同样的意思：当行或列被隐藏或不在DOM中，例如滚动时数据被动态加载的情况，就用aria-rowcount与aria-colcount配合aria-rowindex与aria-colindex，把总体规模与当前可见项区分开来传达。

只看概念大致是下面这个样子。真实标记要长得多，但要点是让代码自己说出「可见的是30行，总量是12万行」这个事实。

<!-- 总共12万行，DOM 中只有从第 40012 行开始的部分 -->
<div role="grid" aria-rowcount="120000" aria-colcount="6">
  <div role="rowgroup">
    <div role="row" aria-rowindex="1">
      <span role="columnheader" aria-colindex="1">订单号</span>
      <span role="columnheader" aria-colindex="2">客户</span>
    </div>
  </div>
  <div role="rowgroup">
    <!-- 前面的四万多行不在 DOM 中，所以必须直接告知 index -->
    <div role="row" aria-rowindex="40012">
      <span role="gridcell" aria-colindex="1">A-40012</span>
      <span role="gridcell" aria-colindex="2">王先生</span>
    </div>
  </div>
</div>

这里出现一个岔路：是真的删掉行，还是留着行只跳过渲染。MDN的content-visibility文档描述了后者所用的取值。auto会开启布局、样式与绘制包含，并在元素与用户无关时跳过其内容，但被跳过的内容仍必须像平常一样提供给页内查找、Tab顺序导航等用户代理功能，并且必须照常可聚焦、可选择。相对地，hidden意味着被跳过的内容不得被这些功能访问，也不可被选择或聚焦。同一文档给出用contain-intrinsic-size提供尺寸估计以减少布局偏移的示例。

HTML一侧也有类似思路。MDN的hidden属性文档写道，until-found状态表示元素被隐藏，但其内容仍可被浏览器的页内查找功能或片段导航访问；当这些功能触发滚动到该元素时，浏览器会触发beforematch事件、移除hidden属性，然后滚动过去。文档还写明浏览器通常用content-visibility: hidden来实现，并且若元素的display为none、contents或inline，则不会通过这种方式被揭示出来。

结论不是二选一，而是规模问题。几千行时把行留在DOM里只削减渲染，既保住浏览器内置能力又足够快。到几十万行，节点数本身就是负担，只能删；而从那一刻起，自己重新实现查找、选择与无障碍的成本就进入了预算。不先做这个判断而以「先虚拟化再说」开局，日后回退的代价很大。

3. 列冻结 - 为什么一行sticky解决不了

「请把第一列冻住」在会议上三秒就能说完。实现之所以不是三秒，是因为position: sticky不是一个孤立属性，而是依赖周围结构的属性。

把MDN在position文档中给出的sticky定义拆开，条件有三层。第一，元素先按文档正常流布局，然后相对最近的滚动祖先与包含块，依据top、right、bottom、left的值进行偏移；定义中明确写着包含表格相关元素。第二，在你想让它粘住的那个轴上，至少要有一个inset属性为非auto的值；若该轴两个inset都是auto，则在该轴上表现得像relative。第三，sticky元素会粘附到最近的、因overflow为hidden、scroll、auto或overlay而产生滚动机制的祖先，即使那个祖先并不是最近的实际滚动祖先。而且这个取值总会创建新的层叠上下文。

看看这三条在实务里如何变成事故。

  • 中间多出的一层包装 — 出于设计原因加了overflow: hidden的包装元素夹在表格与滚动容器之间时，冻结列会粘到那个包装元素上。它并不滚动，于是冻结看起来什么都没做。既无报错也无警告。
  • 漏掉inset — 纵向表头冻结给了top，横向列冻结却漏了left，那个轴就悄悄退化成relative。这是表头生效而列不生效的常见原因。
  • 层叠上下文 — 由于sticky创建新的层叠上下文，本应浮在冻结列之上的下拉框、气泡提示、拖拽手柄的层次会与预期错位。调高z-index也无效的情形正出于此。
  • 角落单元格 — 表头行与第一列相交的那格必须在两个轴上都粘住，并且在两个方向上都压过其他单元格。为这一格需要单独的规则。
  • 边框的归属 — MDN的border-collapse文档定义collapse下相邻单元格共享边框，separate下各自拥有边框。共享的边框究竟由冻结单元格还是滚动单元格来绘制变得含糊，因此实务上往往避开合并模式，改用阴影来表现分界。
  • 阴影 — 想让冻结列只在横向滚动时显示阴影，就得知道「当前是否发生了横向滚动」，而这个状态单靠CSS无法得知，于是滚动事件又回来了。

概念层面的最小示例大致如下。真实代码里每个冻结列的left值必须是前面各列实际宽度之和，所以一旦启用列宽调整，这些值就必须动态计算。下一节的主题正是这个。

/* 滚动容器：让 sticky 的粘附目标明确无歧义 */
.grid-scroll { overflow: auto; max-block-size: 70vh; }

/* 表头行：纵轴 inset(top) 必不可少 */
.grid-scroll thead th { position: sticky; top: 0; z-index: 2; }

/* 冻结列：横轴 inset(left) 必需，取值为前面各列宽度的累计 */
.grid-scroll .col-fixed-1 { position: sticky; left: 0;     z-index: 1; }
.grid-scroll .col-fixed-2 { position: sticky; left: 120px; z-index: 1; }

/* 角落单元格：两轴都粘住，并且压过两边 */
.grid-scroll thead .col-fixed-1 { z-index: 3; }

/* 避开共享边框的归属问题，分界改用阴影表达 */
.grid-scroll table { border-collapse: separate; border-spacing: 0; }
.grid-scroll .col-fixed-2 { box-shadow: 1px 0 0 0 #e0e0e0; }

4. 列宽调整 - 先要选定布局算法

拖动列边界改宽度，看起来三个鼠标事件就够。实际上这是一个先决问题：表格采用哪种布局算法。

MDN的table-layout文档区分两种算法。默认的auto会让表格与单元格的宽度适配内容。fixed则要求显式指定表格宽度，若为auto或未指定，浏览器会退回自动算法。在固定算法下，每一列的宽度依次由带显式宽度的列元素决定，否则由首行单元格上指定的显式宽度决定，再否则均分剩余的横向空间。关于性能的表述也很明确：固定算法更快，因为横向布局只依赖表格宽度、列宽以及边框或单元格间距，而不依赖单元格的内容，并且在下载并分析完第一行之后就可以渲染整张表。

这句话实际上决定了列宽调整功能的设计。在自动算法下，改变一列的宽度会让浏览器重新计算其他列，于是用户拉宽A列而C列缩了。拖动期间这种重算每帧都在发生。改用固定算法可以消除这个问题，但代价是所有列宽都必须由应用自己持有。换言之，一个功能凭空生出了一份新状态。

这份状态一旦存在，其他要求就接踵而来。

  • 冻结列的偏移量 — 第3节里的left值不再是常量。任何一列宽度变化，其后所有冻结列的偏移都要重算。
  • 与虚拟滚动的关系 — 若横向也做了虚拟化，必须知道屏幕外列的宽度才能算出滚动区域的总宽。
  • 内容溢出处理 — MDN指出在固定算法下后续单元格的内容可能放不进给定宽度，单元格要靠overflow属性决定是否裁切。省略号与气泡提示的需求就产生在这里。
  • 双击自适应 — 双击边界自适应内容这个惯例操作，在固定算法下需要由应用自己测量内容宽度。若又开了虚拟滚动，屏幕外的行根本不在可测量之列。
  • 拖动时的性能 — 每帧更新状态会让所有可见单元格重新渲染。于是需要诸如用CSS自定义属性传宽度、绕开重渲染之类的变通。
  • 持久化 — 用户调好的宽度只有存下来才有意义，随之还需要一条规则：列集合变化时旧设置如何处理。

这份清单就是第1节所说乘法的具体面貌。「列宽调整」这一行需求，实际上牵来了六个决策。

5. 可变行高 - 滚动条开始撒谎

若所有行高一致，虚拟滚动的计算就是算术。总高等于行数 × 行高，滚动位置除以行高即得第一个可见行的序号。滚动条的长度与位置都准确。

行高随内容变化的那一刻，这套算术就崩了，因为画之前不知道高度，而想知道高度就得先画。实务上的做法是先放一个估计值，再用实际渲染出来的行高去更新，于是出现一组特有症状。

  • 滚动条忽长忽短 — 越往下实测值替换估计值，总高随之改变，滑块在滚动过程中改变大小。
  • 往上滚会跳 — 上方各行的高度被更新后，下方内容位置随之推移，用户正在看的那一行跑出视口。
  • 始终到不了底 — 若估计总和大于实际，即使已到最后一行，看起来仍有滚动余量。
  • 「跳到第N行」不准 — 跳到特定行需要它之前所有行高之和，而这个和若是估计值，就落不到目标位置。
  • 窗口尺寸变化让一切作废 — 换行方式一变，已经测过的高度全都过期。

浏览器也有处理这一类问题的机制。MDN的overflow-anchor文档把滚动锚定描述为浏览器调整滚动位置以尽量减少内容偏移的行为，在视口上方内容改变尺寸或加载时守住你正在阅读的位置。auto让元素成为潜在锚点，none将其排除。不过同一文档也标注了该特性并非Baseline的有限可用性说明，原因是它在一些使用最广泛的浏览器中并不生效。也就是说，它作为辅助手段有用，但不能作为设计所依赖的基础。

于是真正的选项收窄为三个：固定行高并裁切内容、把高度限制为若干档位，或者允许完全可变并逐条处理上述症状。提前知道第三条的代价，正是本节的目的。

6. 单元格编辑 - 焦点管理与输入法两堵墙

在表格里改值这个功能，把数据网格从显示装置变成输入装置。而输入装置要面对显示装置没有的要求。

第一堵墙是焦点。W3C的APG网格模式规定了可编辑网格的按键行为。Enter停用网格导航，进入编辑模式或聚焦第一个控件。F2切换编辑模式或控件焦点。字母数字键进入编辑模式。Escape恢复网格导航。当单元格内有多个控件时，Tab与Shift+Tab在控件之间移动。

规定本身是清楚的。问题在于它与虚拟滚动相遇的地方。正在编辑的单元格若因滚动移出视口，那一行就离开DOM，持有焦点的元素随之消失。浏览器把焦点退回文档主体，用户丢失了刚才所在的位置。要在回来时把焦点还原到同一格，就必须把「哪一行哪一列处于活动状态」保存在应用状态里，而不是DOM里。这个要求与第7节要讲的结构决策完全一致。

第二堵墙是输入法，在中文、日文、韩文环境中尤其显著。MDN把compositionstart事件定义为当输入法编辑器之类的文本合成系统开始一次新的合成会话时触发，并以用户用拼音输入法开始输入汉字为例。而KeyboardEvent.isComposing文档写明，这个只读属性返回一个布尔值，指示事件是否在合成会话之内触发，即在compositionstart之后、compositionend之前。

把这两个事实叠到前面的按键规定上，冲突就浮现了。

  • Enter的双重含义 — 合成过程中的Enter是确认候选词。若网格把Enter处理成「保存并移到下一行」，用户按了一次却同时完成确认与移动。这个缺陷在拉丁字母环境里根本复现不出来。
  • Escape的双重含义 — 合成过程中的Escape是取消合成。APG把Escape规定为恢复网格导航，于是想取消候选词的用户丢掉了整个编辑。
  • 字母数字键进入编辑 — 这个惯例建立在按键直接变成字符的前提上。输入法开启时，该按键属于合成会话，于是首字丢失或编辑器根本不打开。
  • 方向键 — 合成过程中的方向键用于在候选词列表中移动。若网格把它们截走当作单元格移动，就选不了候选词。
  • 校验时机 — 合成中间的字符串尚未完成。每次输入都校验，会在完全正常的输入过程中持续报错。

解法方向只有一个：合成会话期间，网格不截取按键。写成概念代码大致如下。

// 单元格编辑器的按键处理 - 合成会话期间网格不介入
input.addEventListener('keydown', (e) => {
  // MDN: isComposing 在 compositionstart 之后、compositionend 之前为 true
  if (e.isComposing) return;   // 候选词的确认、取消、移动归输入法管

  if (e.key === 'Enter')  { commitAndMoveDown(); }
  if (e.key === 'Escape') { cancelAndRestoreGridNavigation(); }
});

// 合成结束之后再校验 - 中间字符串不是最终形态
input.addEventListener('compositionend', () => validate(input.value));

缺了这八行，结果就是英文环境的测试全部通过，只有中日韩用户撞上缺陷。评估一个库时，确认这一项是否真的被处理，远比比较功能清单的长度有用。

7. 无障碍为什么不能最后再贴上去

无障碍工作分两类：能后补的与补不上的。标签、对比度、表格标题属于前者。MDN的table文档说，清楚而简洁地描述表格用途的caption能帮助人们判断要不要看其余内容或跳过；th上的scope属性在简单语境下因可被推断而显得冗余，但某些辅助技术可能推断失败，因此显式指定可能改善体验。对于复杂表格，文档建议用id与headers组合把每个单元格与相关表头以程序化方式关联起来。这些东西什么时候加都加得上。

补不上的是键盘网格导航。原因在于它不是添加标记，而是关于焦点所有权的结构决策。

W3C APG关于开发键盘界面的指引把原则写得很短：Tab序列中只应包含复合UI组件的一个可聚焦元素；一旦复合组件获得焦点，就用Tab与Shift加Tab以外的按键在其内部可聚焦元素之间移动焦点。这条规则防止的是一张一万格的表格要按一万次Tab才能离开。文档给出两种实现。漫游tabindex把tabindex="0"放在当前聚焦的元素上、其余为tabindex="-1"，移动时交换这两个取值再调用focus()，好处是浏览器会把新聚焦的元素滚入视野。aria-activedescendant则只把容器留在Tab序列中并指向活动子元素的id，辅助技术会把被引用的元素视为获得焦点的元素，尽管DOM焦点其实在容器上。

两种方式的共同点才是关键：单元格不决定自己的焦点。知道活动坐标的主体是上层容器。因此，如果你已经把每个单元格做成独立管理焦点，再想引入这条原则，就得连同单元格组件的接口与状态归属结构一起改。那是重写，而不是追加。

APG网格模式规定的按键清单也最好在动手前就知道。方向键在横纵方向逐格移动，Page Up/Page Down移动多行，Home与End到当前行的首格与末格，Ctrl+Home与Ctrl+End到首行首格与末行末格。若支持选择，则Ctrl+Space选列、Shift+Space选行、Ctrl+A全选、Shift+方向键扩展选区。角色方面，容器用grid，行用row，单元格用columnheader、rowheader或gridcell；已排序的表头带aria-sort，被选中的元素带aria-selected，不可编辑时带aria-readonly。

// 漫游 tabindex 的骨架 - 活动坐标由容器持有，而不是单元格
let active = { row: 0, col: 0 };   // 应用状态，不是 DOM

function moveTo(row, col) {
  active = clampToBounds(row, col);
  // 虚拟滚动时目标行可能不在 DOM 中 - 先让它渲染出来
  ensureRowRendered(active.row);
  const cell = findCell(active.row, active.col);
  setRovingTabindex(cell);   // 上一格置 -1，新格置 0
  cell.focus();              // 浏览器会把它滚入视野
}

grid.addEventListener('keydown', (e) => {
  if (e.key === 'ArrowDown')  moveTo(active.row + 1, active.col);
  if (e.key === 'ArrowRight') moveTo(active.row, active.col + 1);
  if (e.key === 'Home')       moveTo(active.row, 0);
  if (e.ctrlKey && e.key === 'Home') moveTo(0, 0);
});

这里ensureRowRendered这一行把第2节与第7节连了起来。无障碍需求调用了虚拟滚动实现的内部。这意味着两个功能无法分开来做，也正是「以后再补」会失败的原因。

把前面出现过的冲突汇总成一张表。左边两列是组合，第三列是实际出现的症状，第四列是处理该组合的方向。

9. 何时自研，何时选型

「别自己写」这条建议只对了一半。确实存在自己写更好的情形。把判断标准整理成团队规模、需求数量、生命周期三个轴，大致如下。

判断轴倾向自研的条件倾向选型的条件原因
需求数量以排序、筛选、分页为主的三项以内虚拟滚动、冻结、编辑、无障碍中有两项以上是硬需求三项以内没有组合成本，超过之后按乘法增长
数据规模几百到几千行且可用服务端分页需要在客户端处理数万行以上是否必须虚拟化就是分水岭
设计掌控连标记都要精确贴合设计系统常规外观即可满足若需要掌控标记，无头方案是中间选项
团队规模有人会持续负责这个界面负责人频繁更替或身兼多职自研的网格在维护者离开后会变成负债
生命周期一年内会被替换的内部工具要维护数年的产品核心界面活得越久，跟踪浏览器变化的成本越高
无障碍要求内部工具，标准由团队自定公共、金融、教育等有合规义务的场景键盘网格属于结构决策，事后补不上
多语言输入没有编辑功能，或仅简单文本要用中日韩输入法编辑单元格输入法处理另有一份验证成本
许可与费用包体积与依赖最小化是硬约束所需功能落在付费区间但仍低于人力成本要把人月与许可费用放在同一单位下比较

归纳起来，判断的问题不是「难还是不难」，而是「这份复杂度我们要不要一直持有」。自研的网格不会在交付当天收账，而是在三年后浏览器发生变化的那一天把真正的成本递上来。

10. 库之间的设计差异 - 只讲事实

接下来谈选型，但不做排名。这里只点出官方文档中写明的设计分岔。知道这些分岔，读比较表的眼光就不一样了。

第一个分岔是是否包含渲染。TanStack Table官方文档把自己介绍为面向TS/JS、React、Vue、Solid、Qwik与Svelte的无头UI库，并明确表示无头UI不提供标记、样式或预先做好的实现。它提供的是函数、状态、工具方法与事件监听器，负责数据处理、状态管理与业务逻辑，把标记与样式的完全掌控权留给开发者。同一页也划出选择线：想要更轻量的表格或对设计的完全掌控就考虑无头，设计与包体积不是硬性要求、想要开箱即用的实现就考虑组件式。

这里常出现一个误解。选了无头，本文第2到第7节并不会因此消失。数据管线与状态由库承担，但标记、ARIA角色、焦点管理与输入法处理仍然是你自己要写的部分。也就是说，无头替你分担了第1节中「前面三项」，而「后面五项」原封不动地留着。

第二个分岔是许可区间。AG Grid官方许可与价格页面写明社区版采用MIT许可，企业版遵循单独的最终用户许可协议并包含一年更新。功能划分也以表格形式呈现在页面上：基础列操作、文本/数字/日期筛选、行选择、基础单元格编辑器与CSV导出属于社区版一侧；集合筛选与高级筛选、单元格区域选择与填充手柄、批量编辑与撤销重做、Excel导出、剪贴板集成、行分组与透视、树形数据、主从视图、服务端处理、集成图表等属于企业版一侧。支持渠道也有区分，社区版通过GitHub，企业版通过单独的支持窗口。

这个事实在实务上的含义只有一条：先把功能清单定下来，再确认许可区间。顺序颠倒的话，就会以免费区间开局，半年后因为一项需求而仓促做出采购决定。

设计分岔无头一类组件一类选择时要确认什么
提供范围状态与数据处理逻辑含渲染在内的成品我们是否必须掌控标记
标记归属开发者库是否会与设计系统冲突
ARIA与焦点仍有自实现的部分通过文档与演示确认实现程度亲自测试键盘规定的符合度
输入法处理自写编辑器就得自己处理实际验证内置编辑器的行为务必用中日韩输入法手动试一遍
包体积容易保持小巧随功能增长与首屏加载预算对照
学习曲线需要学概念，应用自由需要学配置，迁出有成本团队的更替周期
许可多为开源可能划分免费与付费区间必需功能落在哪个区间

11. 决定要做的话 - 不会塌的顺序

如果决定自研，顺序会大幅改变结果。前面各节的冲突，多数是在「打算以后再加的东西」原来要求结构时引爆的。所以要从要求结构的东西开始放。

  • 先把需求清单封口 — 连「以后可能会加」的条目也写下来。这一步的目的是确认自己在第1节的表里会下到第几行。
  • 把活动坐标变成应用状态 — 哪一行哪一列处于活动状态，保存在状态里而不是DOM里。无障碍、编辑、虚拟滚动三者都需要这个值。
  • 从第一天就采用单一Tab停靠点 — 以每格都可聚焦的结构开局，之后很难回退。
  • 尽早确定布局算法 — 若路线图上有列宽调整，就从一开始采用固定算法与宽度状态。
  • 按数据规模决定是否虚拟化 — 不需要就不要加。虚拟化会带来把浏览器内置能力再还回来的成本。
  • 把ARIA角色与索引属性挂在渲染器上 — 事后扫描注入的做法一旦和虚拟化并用就会错位。
  • 让编辑器尊重合成会话 — 从一开始就放进第6节那八行。后补的话会以难以复现的缺陷报告形式回来。
  • 确定唯一的滚动容器 — 把「中间包装层不得设置overflow」这条规则在团队内写进文档。
  • 建立只用键盘验收全部功能的流程 — 只用鼠标验收，第7节的缺陷会一路活到发布。
  • 用中日韩输入法手动测试编辑 — 合成会话很难用自动化测试复现。
  • 性能目标按交互而非行数来定 — 「渲染十万行」不是体感，「拖动过程中维持帧率」才是。
  • 写下撤退方案 — 事先约定加入哪项需求就转向选型，到那一刻的决定就不会变成情绪之争。

这份清单里前四条是结构，其余是流程。结构一旦往后拖，流程补不回来。

12. 判断表 - 从需求组合到接近方式

最后把以上内容压缩成一张决策表。在左侧找到符合自己情况的一行，读右边两列即可。

需求组合预估难度最先塌掉的地方建议的接近方式
只做展示，无排序极低没有纯HTML表格，无需任何库
排序 + 筛选低筛选后的状态同步自研，拆成数据变换函数
排序 + 筛选 + 服务端分页低到中总数与分页边界自研，规模由服务端吸收
以上 + 列冻结中滚动容器与层叠上下文可以自研，先钉死容器结构
以上 + 虚拟滚动(固定行高)中到高页内查找与无障碍树考虑无头方案搭配虚拟化工具
以上 + 可变行高高滚动位置估计与跳转先争取限制高度档位，否则选型
以上 + 列宽调整高冻结列偏移的动态重算有宽度状态归属结构则自研，否则选型
以上 + 单元格编辑(仅拉丁字母)高焦点还原先定义编辑器的契约
以上 + 单元格编辑(中日韩输入)极高合成会话与按键冲突优先选择已验证内置编辑器输入法行为的库
以上 + 有合规义务的无障碍极高单一Tab停靠点与焦点所有权第一天就写进结构，不要计划事后补
以上 + 行分组、透视、Excel导出极端数据模型本身需要重新设计已不属于自研范畴，转为工具选型问题

沿着表格往下走，「最先塌掉的地方」会从UI迁移到结构。上半部分改代码就能解决，下半部分要改设计才能解决。这条界线就是自研的实际上限。

结论：难的不是表格，是组合

说数据网格难，其实不够准确。画一张表格是容易的。难的是八个功能在同一屏幕上同时抓住滚动位置、DOM行集合、焦点与布局这四项资源时产生的组合。所以这个问题的成本与功能两两配对的数量成正比，而不与功能清单的长度成正比。

而本文反复呈现了一种模式：能后补的与补不上的界限分明。标签与表格标题补得上。焦点所有权、活动坐标由谁持有、布局算法的选择补不上。这三者是第一天的决定，拖延的代价是日后的重写。

因此实用的结论既不是「别做」也不是「去做」，而是先把需求清单封口，再确认自己在第1节的表里会下到第几行。停在第三行，自研更轻更准确。下到第五行以下，剩下的问题就不是「怎么做」，而是「这份复杂度我们准备持有几年」。

最后再写一遍本文的态度。这里列出的约束不是谁的能力问题，而是网页平台被文档化的行为。所以提前读一遍，就能把三周的长篇故事缩成三天的一个决定。
