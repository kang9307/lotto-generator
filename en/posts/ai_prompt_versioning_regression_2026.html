Treating Prompts Like Code - Versioning and Regression Testing

One line changed, another case broke - designing change, verification and rollback for production prompts

Jul 27, 2026 Dev & Infra

Introduction: prompts are treated as configuration, not as code

There is no shortage of writing on how to compose a prompt. Assign a role, add examples, specify the output format. What almost nobody covers is what happens after that prompt goes into production. Nobody remembers why a sentence was added three months ago. Last week someone edited one line and an apparently unrelated case started producing different output. The vendor upgraded the model and the same prompt now behaves differently. This article is about that phase.

The root of the problem is simple. Prompts are not treated as code; they are treated as configuration. Configuration values usually have no tests. Someone tweaks one in a console and nothing happens, and the person who tweaked it does not consider that a deployment. But a prompt is nothing like a configuration value. Changing a timeout from 30 seconds to 60 has a predictable blast radius. Adding keep tables to at most three rows to a prompt shifts the length, tone and format of requests that have nothing to do with tables.

In other words, a prompt change is not local. In code, changing a function affects only the call paths that reach it. In a prompt, the sentence you added is read together with every input. Because of this property, what prompts need is not a better place to store them but a device that observes the side effects of change. That device has had a name for decades: the regression test.

The catch is that you cannot lift software regression testing wholesale, because the same input does not produce the same output. So this article covers three threads together: (1) how to record the history of the prompt as an artifact, (2) how to define pass and fail criteria for non-deterministic output, and (3) what to re-measure when the model changes underneath you. The downstream question of inspecting artifacts after they are produced — syntax, runtime and semantic layers, false positive management, golden files — is a different axis and is covered separately in building a verification pipeline for AI output. Here the subject is the instruction that produces the artifact.

1. Three ways prompts fall out of version control

Even teams that say they keep prompts in a repository often have broken history. There are three usual paths.

  • Hardcoded as a string inside application code — technically under version control, but the commit message reads improve prompt, so what changed and why is not recorded. When you want to revert, you cannot tell which commit to go back to.
  • Edited through an admin screen — convenient because non-engineers can iterate, but that edit never passes through the deployment pipeline. No review, no tests, no record of when it went live. It is structurally indistinguishable from an unauthorised change in production.
  • Assembled from several fragments — the system prompt, tool definitions, retrieval templates and user message templates all live in different places. Each fragment has history, but the history of the full string actually sent to the model that day exists nowhere. When an incident happens, it cannot be reproduced.

The third is the most dangerous. When fragments carry independent versions, the number of combinations multiplies, and the thing that broke was a specific combination. That is why the unit of prompt versioning must be the rendered final prompt, not the fragments. Fragments are source; the final prompt is a build artifact. If you do not record the hash of the build artifact, you cannot identify what you actually ran.

One diagnostic. If you cannot answer, within thirty seconds, the question can you reconstruct the exact prompt that request received at 3pm yesterday, then your team does not have prompt version control. Where the file lives is a secondary concern.

2. Prompt changes are not local

Once you understand why regressions happen so often, the rest of the design follows. There are four routes.

2.1 Instructions do not discriminate between cases

A familiar production scene. Customer A complains that responses are too long, so someone adds answer in three sentences or fewer. The following week customer B complains that explanations have become useless. B's requests were the kind that should be answered at length, but the new instruction was read together with every request. This is not a model defect. The prompt carried no condition, so it was applied unconditionally, which is correct behaviour.

2.2 Examples teach more than explicit instructions do

Attaching a few examples to lock in format works well, but examples also teach everything the text did not say. If all three examples are formal, tone gets fixed. If all three are short, length gets fixed. If all three come from one industry, that industry's vocabulary leaks in. This is why replacing a single example is riskier than editing a line of instruction.

2.3 Order and position change the result

The same content lands differently depending on whether it sits near the front or the back. That property belongs to prompt design generally and is covered in context engineering, but the implication for versioning is one sentence: a change that only moves a sentence is still a behaviour change. In a diff it looks like a relocation and sails through review, yet the result can differ.

2.4 Things outside the prompt change the prompt's effect

Model snapshot, tool definitions, retrieval chunk size, output schema — change any of them and behaviour changes. Yet none of these are usually recorded in the prompt's change history. A large share of reports that say we did not touch the prompt but the output changed fall into this bucket. So a prompt version must bundle not just the prompt text but the entire environment in which it executes.

3. What to record - prompt metadata

Turn the previous section directly into a schema. The governing principle is can this record alone reproduce that execution, and anything not needed for reproduction stays out.

# prompts/support_reply/v0007.yaml
id: support_reply            # logical name, never changes
version: 7                   # monotonic integer, not semver - see below
content_hash: 9f2c1ab4       # hash after normalisation; same hash means same run
created_at: 2026-07-27T10:12:00+09:00
author: platform-team
status: active               # draft | canary | active | rolled_back | retired

# Execution environment - without this there is no reproduction
runtime:
  model: vendor-model-2026-05-14   # a snapshot id, never an alias
  params: { max_tokens: 1024 }     # sampling params differ in support by vendor
  tools_version: 3                 # tool definitions are part of the prompt
  output_schema: reply_v2          # the contract with the downstream parser

# Composition - how the final string was built
compose:
  parts: [system_base@12, policy_en@4, fewshot_support@6]
  cache_boundary_after: policy_en  # cache prefix boundary, see section 9

# Change info - used for review and rollback decisions
change:
  type: add_constraint       # change type from section 4
  risk: high                 # derived from type; humans must not lower it
  reason: "long-answer complaints (ticket #4821)"
  reverts: null

# Verification record - without these numbers rollback is a guess
eval:
  suite: support_v5          # eval sets are versioned too
  runs_per_case: 5
  hard_gate: pass
  pass_rate: 0.94            # over 180 cases
  baseline_version: 6
  delta: +0.01               # inside the interval, so do not call it an improvement
  judge: rubric_checklist_v2 # the judging method is versioned too, see section 7

Several of those choices are deliberate.

  • A monotonic integer instead of semver — semver asks a human to declare whether backward compatibility broke. For prompts, a one-line edit can break compatibility, so that judgement is not available. The number therefore records order only, and blast radius is expressed separately by change.risk.
  • A snapshot id, not an alias — an alias silently follows whatever the vendor points it at. To keep a reproducible record, write down the snapshot string that was actually called that day.
  • Eval results live in the prompt metadata — if they exist only on a dashboard, nobody consults them during a rollback. When you open the file of the version you are reverting to, its score must be right there.
  • Record the judge as well — if the judging method changes, comparison with past scores becomes impossible. Section 7 covers this.
  • Keep rolled_back in status — deleting reverted versions erases the information that this direction already failed, and the same attempt reappears months later.

4. Risk grading by change type

If every prompt edit triggers the full eval set, nobody will edit prompts. If everything passes through, regressions accumulate. The practical answer is to fix the verification depth in advance by change type. The table below is a starting point for that mapping.

Change typeExampleBlast radiusCache impactRiskMinimum verification
Typo fixSpelling, punctuationTheoretically none (token boundaries do shift)Full invalidation if it sits near the frontLowHard gate plus 10 smoke cases
Sentence relocationSame text moved laterMedium - emphasis changesInvalidates from the move point onwardMediumOne full eval run
Constraint addedA limit such as three sentencesWide - applies to unrelated casesMediumHighFull run plus counter cases
Example added or replacedOne few-shot example changedWide - tone, length and vocabulary move togetherLarge, since examples are bulkyHighFull run plus counter cases
Output schema changeField added or renamedReaches the downstream parserMediumVery highFull run, integration tests, compatibility check
Tool definition changeOne line of a parameter descriptionTool selection behaviour overallMaximum - invalidates every layer belowVery highFull run plus tool-calling cases
Model snapshot swapVersion upgradeEverythingEverythingVery highBaseline re-measurement and parallel running (section 8)
Sampling parameter changeTemperature or top-p adjustedVariance shiftsUsually noneMediumRe-measure pass rate over repeated runs

The most valuable cell in that table is the counter cases attached to constraint additions. Whenever you add an instruction, you must also add a case where that instruction must not apply. Otherwise the eval set only ever confirms that the instruction worked, and the side effect is discovered in production by a customer. Calling that single rule the core of prompt regression testing is not an exaggeration.

Risk must not be self-assessed by the person making the change. The more urgent the change, the lower it gets rated. It is more realistic to derive risk automatically from the change type and require a separate approval to lower it.

5. Eval sets - where cases come from and how many you need

The substance of prompt regression testing is the eval set. Yet while the advice to build one is common, the question of where cases come from rarely gets answered. Five sources are actually usable.

SourceWhat it givesWhat to watchSuggested share
Production log sampleThe real input distributionNeeds personal data removal; injection attempts can slip inaround 40%
Incident and complaint ticketsCases that already blew up onceSkewed toward failure, so pass rates read lowaround 20%
Counter casesSide effects of new instructionsTedious to write, so they go missing firstaround 20%
Hand-built boundary casesEmpty input, very long input, contradictory instructions, mixed languagesUnrealistic cases only distort the pass ratearound 15%
Synthetic variantsVolumeAmplifies whatever bias the originals hadaround 5%

Those shares are a starting point, not gospel. What matters is that the mix is being managed at all. Left alone, an eval set drifts toward things that broke in the past and stops resembling live traffic.

5.1 Eval sets are grown, not designed

Trying to build a complete eval set up front usually fails. Two rules are enough to make it grow on its own.

  • One incident equals one case. When something is reported in production, add the input to the eval set before fixing it. Add it after the fix and it never gets added.
  • One instruction equals one counter case. Every time you add a constraint, add an input where that constraint must not apply.

Keep the case file in a form that is not tied to any one tool. A text format with one case per line can be read by anything.

// eval/support_v5.jsonl  - one case per line
{"id":"c101","kind":"positive","input":"When will my refund arrive?",
 "must":["refund","business days"],"must_not":["account number"],"max_chars":400}

{"id":"c102","kind":"counter","input":"Explain clause 3 of the contract with reasoning",
 "note":"long answer is correct here - the three-sentence limit must not apply",
 "min_chars":600,"must":["clause 3"]}

{"id":"c103","kind":"boundary","input":"",
 "note":"empty input","must":["try again"],"must_not":["stack trace"]}

{"id":"c104","kind":"schema","input":"Status of my 3 orders",
 "expect_json":true,"required_fields":["orders","count"]}

Track how many cases carry kind: counter as a metric. An eval set whose counter-case share tends to zero cannot catch regressions.

5.2 How many is enough - precision decides the number

There is no universal answer to how large an eval set should be. Ask the question backwards and an answer appears: how large a difference do you want to be able to distinguish? The half-width of a 95% interval on an estimated pass rate is roughly 1.96 × √(p(1−p)/n), which around a pass rate of 0.9 gives the following.

Eval set size n95% interval half-width at 0.9Difference you can distinguishReasonable use
20about ±13.1 pointsOnly large breakageSmoke check
30about ±10.7 pointsOnly large breakageQuick post-edit check
50about ±8.3 points10 points and upEveryday regression runs
100about ±5.9 points6 points and upApproval gate
300about ±3.4 points3 points and upModel swap decisions
500about ±2.6 points2 points and upLarge migrations

Reading the table is simple. Claiming a 2 point improvement from a 100 case eval set has no statistical basis. What looks like a gain may be noise, and conversely real degradation can hide inside the noise. That is exactly why the table in section 4 grades a model swap as very high risk: that decision needs a bigger eval set.

Two caveats. First, the approximation above becomes unreliable as the pass rate approaches 1, where a different interval method is preferable. Second, this calculation is about how many cases to look at, which is a different question from the probability of finding a rare defect hiding in a population by sampling. The latter is tabulated in the artifact verification article, so use that one for it.

Vendor documentation offers a reference point too. Anthropic's guidance on writing evaluations shows examples ranging from dozens of grouped cases to a thousand depending on the task, and states the principle that many automatically graded questions beat a handful of hand-graded ones. Note that this is a vendor's own recommendation and the right answer varies with task and risk.

6. Setting pass criteria for non-deterministic output

This is where prompt regression testing parts ways with software regression testing. The same input does not produce the same output.

6.1 Temperature zero does not guarantee reproducibility

A common belief is that temperature zero makes inference deterministic. It does not. An engineering article published by Thinking Machines Lab reports that running the same prompt at temperature zero 1,000 times produced 80 distinct completions, the most frequent appearing 78 times, with the first divergence at token 103. The article's central claim is that the cause is neither GPU concurrency nor randomness but a lack of batch invariance in the kernels. The number of requests the server batches together changes the order of reduction operations, and because floating point addition is not associative, the last bits drift. At some point that drift flips a token choice. The same article adds that with batch-invariant kernels all 1,000 runs became identical. It is worth reading with the caveat that this is a research lab engineering blog rather than a peer-reviewed paper.

Two practical implications. First, non-determinism is a controllable property but the control usually sits outside your hands — a team on a managed API cannot govern server batching. Second, therefore, a test design that assumes reproducibility is unsound from the start.

Beyond that, the temperature parameter itself is not forever. Anthropic's documentation marks temperature, top-p and top-k as returning a 400 error when set to a non-default value on Claude Opus 4.7 and later, and advises steering behaviour through prompting instead. Which means the strategy of pinning temperature to zero for reproducibility can disappear through nothing more than a vendor parameter policy change.

6.2 Put the criterion on the distribution, not on one output

So the judgement applies to the distribution of k runs of the same case. Different items have different natures, so the form of the criterion should differ too.

TargetCriterion formRepeats kExampleOn failure
Format contractHard gate (all k runs)3-5JSON parses, required fields presentImmediate fail
ProhibitionsHard gate (all k runs)5 or moreBanned terms, personal data, absolute claimsImmediate fail
Factual matchPass-rate threshold3-5Extracted field match rate at least 0.95Decompose and decide
Subjective qualityRelative to baseline version3 or moreIs it no worse than the previous versionWatch list
Cost and latencyBudget ceilingAggregated over all runsMean tokens, p95 latencyHold the release

Three points deserve emphasis in this design.

  • Relative comparison beats absolute scoring. A statement like this answer scores 4 out of 5 wobbles with judge and time, while which of the baseline and the new version is better wobbles less. The question a regression test asks was never did it improve but did it get worse.
  • Do not mix hard gates with quality metrics. Managing banned-term exposure at a 0.98 pass rate means twice in a hundred is acceptable. Format and safety items must be all-pass, not thresholded.
  • Raising k raises the cost of flakiness. If each case fails spuriously with probability 1%, an eval set of 100 cases fails somewhere with probability about 63% (1 − 0.99100). You need per-case flakiness down near 0.1% to bring that to roughly 10%. In other words, a flaky suite will be ignored. Flaky cases must be moved to a pass-rate threshold or have their criteria narrowed; leaving them alone destroys trust in the whole set.
// Minimal judging logic with no framework dependency
async function judgeCase(runModel, testCase, k = 5) {
  const outputs = [];
  for (let i = 0; i < k; i++) outputs.push(await runModel(testCase.input));

  // 1) Hard gates - one violation ends it
  for (const out of outputs) {
    if (testCase.expect_json && !tryParse(out)) return fail('schema');
    for (const bad of testCase.must_not || []) {
      if (out.includes(bad)) return fail('forbidden:' + bad);
    }
  }

  // 2) Pass-rate criteria - items allowed to wobble
  const softPass = outputs.filter(out =>
    (testCase.must || []).every(t => out.includes(t)) &&
    (!testCase.max_chars || out.length <= testCase.max_chars) &&
    (!testCase.min_chars || out.length >= testCase.min_chars)
  ).length;

  return { id: testCase.id, hard: 'pass', rate: softPass / k, k };
}

What matters is that this code is tied to no particular tool. Swap runModel and the judging logic stays yours across vendor changes and tooling changes alike. Section 11 returns to this.

7. The judge is a versioned artifact too

Delegating quality judgement to an LLM is widespread, but using it inside a regression test carries a specific trap. A regression test is fundamentally the act of placing two versions side by side, and side-by-side placement is exactly the situation where judge bias shows up most strongly.

  • Position bias — the phenomenon where which candidate appears first changes the choice. A study that examined 15 judges across 22 tasks on two benchmarks and produced more than 150,000 evaluation instances measured this with three metrics — repetition stability, position consistency and preference fairness — and concluded that the bias is systematic rather than chance and varies considerably by judge and task. The same work reports that the bias is driven strongly by the quality gap between the two candidates and only weakly by the length of prompt components. That means the subtler the difference between versions, the larger the ordering effect — and in a regression test the two versions are almost always subtly different.
  • Self-preference bias — the tendency of a judge to rate outputs from its own lineage generously. One study argues that the essence of the bias is not authorship but a preference for low-perplexity, familiar text, which LLMs rate more generously than humans do. Which means that using either the old or the new model as the judge during an upgrade evaluation can tilt the result.
  • Judge drift — more common in practice than either of the above. If the model doing the judging changes, past and present scores cannot be compared. A 3 point drop with an unchanged prompt becomes impossible to attribute between prompt regression and judge replacement.

From this article's angle, the conclusions converge on one line. The judge is not evaluation infrastructure; it is a versioned artifact. That is why the schema in section 3 carries a judge field. As working rules, the following hold up well.

  • Freeze the judge model and the judging prompt, and re-measure the entire baseline when you change them. Judge replacement belongs in the very high row of the section 4 table.
  • For comparative judgements, ask twice with the order reversed and accept only agreement. Treat disagreement as no difference.
  • Separate the generating model from the judging model. Anthropic's documentation likewise advises that it is generally better to grade with a model other than the one that produced the output.
  • Use per-item yes/no checklists instead of scores. Scale scores drift in calibration between judges, which makes time series comparison awkward.
  • Use LLM judgement to order what humans should look at, and leave release approval itself to hard gates and human review.

The general theory of judge bias and its mitigations is covered further in the artifact verification article. What is stressed here is the versioning implication: the moment you swap the judge, the history breaks.

8. A model upgrade is itself a regression event

There is an event that changes behaviour without a single character of the prompt moving: the model changes. And that event arrives on the vendor's schedule, not yours.

8.1 What vendors announce and what they do not

As of July 2026, the published policies of two vendors read as follows.

  • Anthropic — defines a four-stage lifecycle of Active, Legacy, Deprecated and Retired, and states at least 60 days of notice before retirement for publicly released models. Requests to a retired model fail. The documentation also describes exporting per-key, per-model usage from the console to audit where deprecated models are still called.
  • OpenAI — states at least 6 months for generally available models, at least 3 months for specialised variants such as chat variants, Codex and deep research models, and a much shorter window on the order of two weeks for preview models, with a recommendation not to place preview models on business-critical paths.

The important part is that this notice concerns retirement, not behaviour change. Teams on aliases do not see an error on the retirement date; instead they quietly start running a different model one day. Errors come with alerts; behaviour changes do not. That is why section 3 insists on snapshot ids over aliases. The broader lock-in structure around prompts and models is laid out layer by layer in the vendor lock-in exit strategy article.

8.2 Six steps for a model swap

StepWhat to doOutputCommon mistake
0. InventoryList which prompts run on which snapshotsPrompt-by-model matrixMissing hidden calls in batch jobs and back office
1. FreezeNo prompt edits during the verification windowFreeze noticeEditing prompts at the same time, making causes inseparable
2. Re-measure baselineRun the eval set on the old model again, nowBaseline scoreUsing a number from months ago as the baseline
3. Paired runRun the same eval set on the new modelImproved / unchanged / regressed splitReading only the total and ignoring case movement
4. Local fixesFix only regressed cases, one change at a timeChange logFixing several places at once so nothing is attributable
5. Canary and parallelShift a small slice of traffic first, keep the rollback pathMigration planStarting just before the retirement date with no room to revert

Step 2 deserves emphasis. Always re-measure the baseline now. An old record came from that day's eval set, judge and server conditions. Comparing it against a new model's score tells you nothing about cause. Comparison is meaningful only between two numbers produced on the same day, on the same eval set, with the same judge.

Step 3's decomposition matters as well. An identical total can hide large internal movement. If ten cases improve and ten degrade, the total is flat, but if those ten degraded cases sit on the revenue path, that is not an improvement, it is an incident.

run_eval --suite support_v5 --model new-snapshot --k 5 --out cand.json

9. With prompt caching, a line at the front costs differently

For teams using prompt caching, the position of a change drives cost. That fact feeds straight back into prompt management rules.

Per Anthropic's documentation, the cache has a prefix structure ordered tools → system → messages, and a change at an earlier layer invalidates everything after it. Editing a tool definition's name, description or parameters invalidates the entire cache; editing the system prompt invalidates system and messages. The pricing structure is as follows.

ItemRelative to base inputMeaningOperational implication
Cache write (5 min)1.25×Storing a new entryThe first requests after a release pay this
Cache write (1 hour)2.0×Longer retention optionUnfavourable where changes are frequent
Cache read0.1×Reusing an entryThe larger the stable prefix, the bigger the win
Default lifetime5 minutesRefreshed on each useThin traffic means the cache goes cold often

Three working rules fall out of this.

  • Push volatile content to the back. Instructions under experiment, per-segment branches and recently changed policy text belong after the cache boundary. Put them at the front and a one-character edit invalidates the whole prefix.
  • Do not interpolate variables such as current time or user name near the front of the system prompt. The prefix then differs on every request and caching effectively stops working.
  • Record the cache boundary in the prompt metadata. That is what cache_boundary_after is for in the section 3 schema. Without it, a reviewer cannot judge the cost impact of adding one line at the front.

There is a release-process implication too. Cost rises temporarily right after a prompt release because every cache is written again. Look at deployment timestamps alongside cost graphs so that this rise is not mistaken for an anomaly and rolled back. The figures and layer structure above are from Anthropic's own documentation; cache implementation and billing differ by vendor, so verify against the relevant documentation if you use another.

10. Rollback criteria

Rollback should be a designed path, not a failure. The problem is that teams try to decide when to revert after the incident has already started, at which point judgement is already compromised.

SignalThresholdActionRationale
Hard gate violationOne occurrenceRoll back immediatelyFormat and safety items are not managed probabilistically
Eval pass rate dropA drop outside the intervalRoll backInside the interval it may be noise (section 5.2)
One segment dropsEven with a flat totalPartial rollback or branchTotals conceal movement
Cost spikeSustained beyond 30 minutes post-releaseCheck the cache boundary, then decideAn immediate rise may just be cache rewriting (section 9)
Human review complaintsTrend does not bendObserve, then decideReverting on one complaint pollutes the history
Non-reproducible report—Do not revert; turn it into a caseReverting what you cannot reproduce loses the cause forever

Rollback carries one rarely discussed precondition. The version you revert to has to still be alive together with its model. If prompt v6 was only ever verified on an old model snapshot and that snapshot has retired, reverting to v6 means moving to an unverified combination. In other words, when a model retires, the rollback paths bound to it retire with it. That is the real reason to leave generous room in the parallel-running window of section 8.

It also helps to fix what happens after a rollback. Do not delete the reverted version; mark it rolled_back, and add whatever broke to the eval set as a case. Skip those two and the same attempt returns in a few months.

11. Three questions to answer before choosing a tool

As of 2026 the prompt evaluation and regression tooling landscape splits roughly three ways. This is not a claim that one is better, but that they solve different problems.

  • File and CI centric — eval sets live as text in the repository and run in CI, blocking releases by exit code. The goal is stopping bad changes. promptfoo is the well-known example.
  • Tracing and observability centric — production traffic is collected into datasets and scored online. The goal is seeing what actually happens. LangSmith and Braintrust are described as belonging here.
  • Provider built-in — evaluation features offered by the vendor platform. Easy to reach, but coupled to that vendor's models and formats.

More important than tool choice is what survives a tool change. On 9 March 2026 OpenAI announced its acquisition of promptfoo, stating that the project would remain open source under its current licence. There is no reason to grade the acquisition itself, but the event illustrates clearly that the ownership of evaluation tooling changes too. Model vendors change, tool owners change, teams change. The asset that has to stay yours through all of it is not the tool but the eval set and the judging criteria.

So answering three questions before picking a tool hurts less later.

  • Can the eval set be exported from your repository as plain text? A dataset that lives only inside a screen disappears with the tool.
  • Is the judging logic your code? Holding something like judgeCase from section 6 is what preserves score continuity across a tool migration.
  • Can CI block a release by exit code? An evaluation that cannot block is a report, not a gate.

12. Starting with a minimal setup

Nobody starts if starting requires all of the above. With an order, it breaks into one- and two-day pieces.

  1. Day 1 — inventory. Tabulate the prompts in production and the model snapshot each uses. This is usually where somebody says we had one of those?
  2. Day 2 — log the final prompt. Record the hash of the assembled final string plus the model id in the request log. If keeping the full text is hard, keep at least the hash.
  3. Day 3 — ten hard-gate cases. Pick only the things that must never wobble, such as format and forbidden terms, and write ten. Leave quality evaluation alone for now.
  4. Day 4 — wire it to CI. Make the hard gate run automatically when a prompt file changes, and block the merge if it fails.
  5. Week 1 — adopt the counter-case rule. Put it on the review checklist that constraint-adding changes must ship with a counter case.
  6. Week 2 — incidents become cases. Every production incident adds a case before the fix. That single rule grows the eval set by itself.
  7. Month 1 — baseline and relative comparison. Once you pass 50 cases, start tracking the pass rate and judge new versions relative to the baseline.
  8. Quarterly — rehearse a model swap. Run through the section 8 procedure once before a real deprecation notice arrives. Doing it for the first time after the notice is too late.

If you pick only the cheapest one, take day 3's ten hard-gate cases. Quality evaluation is hard to design and drags the judge problem along with it, whereas does the JSON parse and is a forbidden term present are mechanical to judge and automate immediately. And a large share of real production incidents happen in exactly those two items.

Conclusion

Treating prompts like code does not mean putting prompts in a repository. It means that changes carry reasons, side effects are observable, and a live path back exists. Miss any one of the three and the repository is just a string cabinet.

Prompt management is uniquely awkward because three properties overlap: changes are not local, outputs are not deterministic, and the execution environment shifts outside your control. The respective answers are counter cases, distribution-based pass criteria, and snapshot pinning with baseline re-measurement. Every table and schema in this article derives from those three.

One limitation, stated plainly. None of these procedures guarantees prompt quality or performance. What a regression test does is not prove that something improved but discover before release that something which used to work no longer does. That alone is worth the cost, because the most frequent incident in AI-backed systems is not a novel failure but an old failure that quietly came back.
