Gemini CLI 2026년 6월 18일 중단 - Antigravity CLI 마이그레이션 가이드와 D-day 시나리오

D-day까지 약 4주, 명령어부터 CI/CD 전환까지 한 번에 정리한 실전 가이드

2026-05-22 IT/기술

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 6월 18일 D-day, 누가 영향을 받는가

2026년 5월 21일 Google이 공식 블로그를 통해 Gemini CLI를 2026년 6월 18일 23:59 PT부로 종료한다고 발표했습니다. 한국 시간으로는 6월 19일 오후 3시 59분입니다. 같은 시점에 작년 가을 비공개 베타로 시작했던 Antigravity CLI가 무료 GA로 전환되며, 사실상 Gemini CLI의 후속이자 대체재로 자리 잡습니다. hada.io 9점짜리 토픽으로 올라오자마자 댓글이 70개 넘게 달린 데서 알 수 있듯, 한국 개발자 커뮤니티에서도 영향 범위에 대한 혼선이 크다는 게 솔직한 현실입니다. 본문은 본인이 본인 팀 마이그레이션을 위해 정리한 실전 노트를 공개 가능한 수준에서 다시 풀어 쓴 것입니다.

먼저 누가 영향을 받는지부터 명확히 합니다. 영향을 받는 그룹은 네 가지입니다. 첫째, gemini 바이너리를 로컬에 깔아 일상 코딩 보조로 쓰는 개인 개발자입니다. 둘째, GitHub Actions나 GitLab CI에 gemini를 박아 둔 팀입니다. PR 자동 리뷰, 커밋 메시지 생성, 변경 로그 작성 등 작은 자동화에서 흔히 보이는 패턴입니다. 셋째, VS Code 또는 JetBrains 확장에서 백엔드로 gemini CLI를 호출하는 부분 자동화 도구를 만들어 둔 사이드 프로젝트 제작자입니다. 넷째, 엔터프라이즈 사내망에서 Vertex AI 직접 호출 대신 CLI를 사용하던 팀입니다. 한국에서는 KT와 Naver 사내망 환경에서 의외로 이 패턴이 흔합니다.

영향을 받지 않는 그룹도 명확합니다. Vertex AI나 Google AI Studio를 SDK(Python, Node.js, Go) 또는 REST로 직접 호출하는 코드는 그대로 동작합니다. 모델 자체가 사라지는 것이 아니라 CLI 표면만 교체됩니다. 즉 이번 변화는 "Gemini 모델을 호출하는 방법"의 표면 변경이지 모델 EOL이 아닙니다. 본문 8단계 마이그레이션의 절반 이상이 이 점에 기반합니다. 핵심 계산 로직은 바꿀 게 없고, 진입점만 정리하면 됩니다. 마지막으로 일정 압박을 짚자면, 글을 쓰는 시점 기준 D-day까지 약 27일입니다. 본인 팀 기준으로는 이번 주말에 카나리 환경 마이그레이션을 시작하고, 5월 마지막 주에 CI 전환, 6월 첫 주에 프로덕션 전환, 마지막 주에 모니터링과 폴백 정리 일정으로 잡았습니다.

Gemini CLI는 무엇이었나 - 출시부터 현재까지

맥락을 위해 잠깐 돌아봅니다. Gemini CLI는 2024년 11월 Google이 Anthropic의 Claude Code 출시에 대응해 공개한 오픈소스 명령줄 도구였습니다. 초기 버전은 단순한 챗 완성 래퍼였고, 2025년 상반기 동안 도구 사용, 파일 시스템 접근, 셸 실행, 그리고 multi-turn 컨텍스트 관리가 차례로 추가되었습니다. 2025년 9월 v1.0 안정 버전이 나오면서 단순 보조에서 진지한 자율 코딩 도구로 자리를 옮겼고, 그 시점에서 일 활성 사용자(DAU)가 약 40만 명으로 추정되었습니다. 한국 시장에서는 Vertex AI 한국 리전 출시와 맞물려 빠르게 보급되었고, 사용자 규모로는 Claude Code의 약 60%, Codex CLI의 약 1.4배로 추산됩니다.

그렇다면 무엇이 그렇게 매력적이었을까요. 본인이 8개월 정도 일상으로 굴려 본 감각에서 가장 강했던 점은 200만 토큰 컨텍스트 윈도우와 결합된 저렴한 가격입니다. 거대한 모노레포 전체를 컨텍스트에 통째로 넣고 질문할 수 있다는 점이 다른 CLI 도구와 뚜렷이 차별화되는 지점이었습니다. 또한 Google Workspace 통합(Drive, Docs, Sheets를 한 명령으로 끌어오기)이 한국 스타트업처럼 Workspace를 기본 협업 도구로 쓰는 환경에서 의외의 편의를 줬습니다. 비판할 점이 없었던 건 아닙니다. 도구 사용 정확도가 Claude Code 4.7 대비 한 단계 낮았고, 긴 자율 작업에서 자기 컨텍스트를 잃는 빈도가 더 높았습니다. 그래도 "한 번에 거대한 코드베이스를 본다"는 강점만으로 살아남는 도구였습니다.

주요 명령어 체계는 단순했습니다. gemini chat으로 대화, gemini run "프롬프트"로 일회성 실행, gemini edit 파일.py로 파일 수정, gemini config로 설정 관리. 설정 파일은 ~/.config/gemini/config.yaml 한 곳에 모여 있었고, 인증은 gemini auth login으로 OAuth 흐름을 타거나 환경 변수 GEMINI_API_KEY로 API 키를 직접 박는 두 가지 모드를 지원했습니다. 이 단순함이 큰 장점이었는데, Antigravity CLI에서는 이 모델이 한 단계 복잡해졌습니다. 그 점은 다음 섹션에서 정직하게 다룹니다.

왜 중단되는가 - 본인 관점 분석

Google 공식 발표는 표면적으로 "차세대 에이전트 아키텍처로 통합하기 위해"라는 흔한 마케팅 문구를 씁니다. 본인이 보기에 진짜 이유는 세 가지입니다. 첫째, Google CLI 전략의 통합입니다. 2026년 3월 Antigravity가 공개될 때부터 사실상 두 CLI를 동시에 유지할 의도는 없었습니다. Antigravity는 IDE 표면(Antigravity Workspace)을 우선으로 하지만, 같은 코어를 공유하는 CLI 인터페이스가 처음부터 함께 있었고, 베타 단계에서 이미 Gemini CLI를 점진적으로 흡수하고 있었습니다. 이번 6/18 종료는 그 흡수의 마무리입니다.

둘째, 에이전트 워크플로 우선주의로의 전환입니다. Gemini CLI의 명령어 체계는 "단발성 또는 짧은 대화" 패러다임을 전제로 설계되어 있었습니다. 멀티턴은 가능했지만 어쩐지 "추가된 기능"의 느낌이 남아 있었습니다. Antigravity CLI는 처음부터 "장시간 자율 작업"을 기본 단위로 설계되어 있고, 명령어, 설정, 출력 포맷 모두 그쪽으로 최적화되어 있습니다. Anthropic의 Claude Code가 2025년에 이 방향성을 증명한 이후, 모든 주요 랩이 자사 CLI를 같은 방향으로 정렬하는 흐름의 일환입니다.

셋째, MCP 시대의 도구 표면 재설계입니다. 2024년 후반 Anthropic이 시작한 Model Context Protocol이 2026년 상반기에 사실상 업계 표준이 되었습니다. Gemini CLI는 MCP 지원이 v0.9부터 추가되었지만 핵심 아키텍처에 깊이 박혀 있지 않은 후행 통합이었습니다. Antigravity CLI는 MCP를 1급 시민으로 가정하고 처음부터 설계되어 있어, 외부 도구(GitHub, Notion, Linear, 그리고 본인의 사내 도구)를 붙이는 경험이 의미 있게 더 부드럽습니다. Google이 보기에 이 둘을 함께 유지하면서 양쪽 다 잘 발전시킬 자원이 없었고, 그래서 한 쪽을 골랐다는 게 본인의 추측입니다.

Antigravity CLI 소개 - 무엇이 다른가

Antigravity CLI는 단순한 리네이밍이 아닙니다. 본인이 한 달 가까이 양쪽을 병행해 본 결과, 그래도 의미 있는 차이는 다섯 가지입니다. 첫째, 명령어 동사가 바뀌었습니다. gemini chat에 해당하는 명령은 antigravity 단독(서브커맨드 없이)이 됩니다. gemini run은 antigravity task, gemini edit은 antigravity edit으로 살아남았지만 동작 방식이 미묘하게 다릅니다. 동의어가 아닙니다.

둘째, 설정 파일 위치와 구조가 변경되었습니다. 기존 ~/.config/gemini/config.yaml 단일 파일에서 ~/.config/antigravity/ 디렉토리 아래로 옮겨가며, settings.json, profiles/, mcp_servers/ 세 개의 하위 구조로 분리되었습니다. 처음 보면 복잡해 보이지만, 멀티 프로젝트 환경에서 프로파일별로 설정을 분리할 수 있는 점이 실무에서는 더 깔끔합니다. 셋째, 인증 모델이 OAuth 우선으로 바뀌었습니다. API 키 환경 변수 방식은 여전히 지원되지만, 기본 흐름은 antigravity login 명령을 통한 브라우저 OAuth로 통합되었고, 토큰은 OS 키체인에 저장됩니다(macOS Keychain, Windows Credential Manager, Linux secret-tool).

넷째, 출력 포맷이 구조화되었습니다. Gemini CLI는 기본 출력이 평문이었고 --json 플래그로 JSON을 받았습니다. Antigravity CLI는 기본이 사람 친화적 마크다운 + 사이드밴드 JSON 메타데이터로, --format plain이나 --format json으로 명시적 선택이 가능합니다. 이 변경은 CI 환경에서 파서를 다시 손봐야 하는 가장 큰 단일 원인이고, 본문 후반에서 별도로 다룹니다. 다섯째, MCP 서버를 1급으로 다룹니다. antigravity mcp add <url> 한 줄로 외부 도구 서버를 붙일 수 있고, 붙은 도구는 모든 대화와 작업에서 자동으로 노출됩니다. Gemini CLI에서 MCP를 쓰려면 별도 플러그인 디렉토리를 만들고 매번 명시적으로 로드해야 했던 것과 대비됩니다.

주요 변경 사항 매트릭스 - 한 장으로 보는 차이

본인이 마이그레이션 중 가장 자주 들춰 본 매트릭스를 그대로 옮겨 둡니다.

구분 Gemini CLI Antigravity CLI 비고
대화 시작 gemini chat antigravity 서브커맨드 없이 단독 실행
일회성 실행 gemini run "프롬프트" antigravity task "프롬프트" 출력 포맷 기본값 다름
파일 수정 gemini edit file.py antigravity edit file.py diff 미리보기가 기본 활성화
설정 디렉토리 ~/.config/gemini/ ~/.config/antigravity/ 구조도 변경, 자동 마이그레이션 도구 제공
인증 (기본) API 키 환경 변수 OAuth + OS 키체인 API 키 모드 여전히 가능
환경 변수 GEMINI_API_KEY ANTIGRAVITY_API_KEY 동일 키 재사용 가능
기본 출력 평문 마크다운 + 메타 JSON --format plain으로 호환

모델 선택 --model gemini-2.5-pro --model gemini-3.5-pro 또는 외부 외부 모델 라우팅 기본 지원
플러그인 플러그인 디렉토리 MCP로 통합, 플러그인 폐지 기존 플러그인은 MCP 서버로 재포장 필요

마이그레이션 가이드 - 단계별 8단계

본인이 따른 순서 그대로입니다. 각 단계 끝에 본인이 실제 겪은 함정을 짧게 붙입니다.

1단계: 현재 환경 백업

마이그레이션의 첫 번째 규칙은 "되돌릴 수 있게 두라"입니다. cp -r ~/.config/gemini ~/.config/gemini.bak.20260522로 설정 디렉토리를 통째로 복사하고, gemini config show > ~/gemini_config_snapshot.txt로 현재 활성 설정의 평문 스냅샷도 남겨 둡니다. 환경 변수와 셸 rc 파일(~/.bashrc, ~/.zshrc, fish 사용자라면 ~/.config/fish/config.fish)에서 GEMINI_로 시작하는 변수를 모두 찾아 별도 파일로 옮겨 둡니다. 함정: 본인은 첫 시도에서 direnv로 프로젝트별로 설정된 .envrc 안의 GEMINI_API_KEY를 깜빡 잊었습니다. grep -r GEMINI ~/Projects/를 미리 돌려 두십시오.

2단계: Antigravity CLI 설치

설치는 세 가지 경로가 공식적으로 지원됩니다. macOS는 brew install antigravity, Linux는 공식 설치 스크립트(curl -fsSL https://antigravity.google.dev/install.sh | sh), Windows는 winget(winget install Google.Antigravity) 또는 직접 다운로드입니다. 한국 환경에서 본인이 추천하는 방식은 macOS와 Linux는 Homebrew, Windows는 Scoop 또는 winget입니다. 사내망에서 외부 스크립트 실행이 차단된 경우 GitHub 릴리즈 페이지에서 바이너리를 직접 받아 /usr/local/bin/에 두는 방식도 됩니다. 설치 후 antigravity --version으로 GA 버전(2026.06.18 시점 1.0.x 시리즈)을 확인하십시오. 함정: Gemini CLI와 동시 설치가 가능합니다. 일부러 그렇게 설계되어 있어 마이그레이션 기간 동안 양쪽을 동시에 굴리며 비교할 수 있습니다.

3단계: 인증 마이그레이션

API 키 방식 유지를 선택한다면 GEMINI_API_KEY를 ANTIGRAVITY_API_KEY로 단순 리네임하면 됩니다(동일 키 값 재사용 가능). 권장은 OAuth로 전환하는 것입니다. antigravity login 명령을 실행하면 브라우저가 열리고, Google 계정으로 로그인하면 OS 키체인에 토큰이 저장됩니다. CI/CD 환경에서는 OAuth가 어색하므로 API 키 방식이 그대로 정답입니다. 함정: 회사 워크스페이스 계정과 개인 Gmail이 동시에 활성화된 경우, 첫 로그인 시 잘못된 계정을 선택할 수 있습니다. antigravity login --account work로 명시적으로 라벨을 붙여 두십시오.

4단계: 설정 변환

좋은 소식은 Google이 공식 변환 도구를 제공한다는 것입니다. antigravity migrate --from gemini 한 줄로 기존 ~/.config/gemini/config.yaml의 약 80%가 자동으로 새 구조로 옮겨집니다. 변환되지 않는 항목은 마지막에 리포트로 출력되며, 본인의 경험상 변환 누락은 주로 (1) 커스텀 에일리어스, (2) 외부 도구 플러그인 정의, (3) Workspace 통합용 OAuth 별칭 세 가지입니다. 변환 후 antigravity config show로 결과를 확인하고, 누락분을 수동으로 채워 넣습니다. 함정: 변환 도구가 만든 새 settings.json을 그대로 두지 마십시오. 한 번 열어 모델 기본값(gemini-2.5-pro가 그대로 들어와 있을 수 있음)을 gemini-3.5-pro로 직접 갱신하는 것이 좋습니다.

5단계: 스크립트 호환성 검증

로컬에 있는 ~/bin, ~/.local/bin, 또는 프로젝트별 scripts/ 디렉토리에서 gemini 명령을 호출하는 모든 스크립트를 찾아냅니다. grep -rn "gemini " ~/Projects/ scripts/ ~/bin/ 정도가 좋은 출발점입니다. 발견된 각 스크립트에 대해 (1) 명령어 동사 매핑, (2) 환경 변수 이름, (3) 출력 파싱 후처리 세 가지를 검토합니다. 본문 후반의 일괄 변환 sed 스크립트가 80%는 자동으로 처리해 주지만, 출력 파싱은 사람이 직접 확인해야 합니다. 함정: gemini 명령을 백틱이나 $() 안에서 호출하고 그 출력을 jq로 파싱하는 스크립트는 거의 항상 손봐야 합니다. 기본 출력 포맷이 바뀌었기 때문입니다.

6단계: CI/CD 파이프라인 업데이트

가장 시간이 많이 드는 단계입니다. GitHub Actions, GitLab CI, Jenkins, CircleCI 어느 쪽이든 다음 세 가지를 갱신해야 합니다. (a) Docker 베이스 이미지가 gemini-cli를 설치하던 부분을 antigravity로 교체. (b) 시크릿 이름 매핑(GEMINI_API_KEY → ANTIGRAVITY_API_KEY, 또는 OAuth 토큰을 시크릿으로 주입). (c) 명령어와 출력 파싱 로직 갱신. 중요 권고: 본 PR을 일반 PR로 만들지 마십시오. 별도 브랜치에서 카나리 워크플로를 한 번 통과시킨 후 머지하십시오. CI 실패가 6/18 직전에 발견되면 패닉이 됩니다. 함정: Docker 이미지를 새로 빌드한 후 캐시 이미지가 PR 빌드와 메인 빌드에서 따로 도는 경우가 있습니다. 캐시 키에 antigravity 버전을 명시적으로 포함시키십시오.

7단계: 팀원 공지

기술적인 마이그레이션이 끝났다고 일이 끝난 게 아닙니다. 본인 팀은 (a) Slack 또는 사내 메신저에 D-day 카운트다운과 마이그레이션 가이드 링크를 핀 메시지로 고정, (b) 사내 위키에 "내 환경에서 마이그레이션하는 법" 한 페이지를 작성, (c) 매주 화요일 30분짜리 오피스 아워를 두 번 운영했습니다. 마지막 항목이 의외로 큰 효과였습니다. 글로 읽는 것보다 옆에서 같이 한 번 해 보는 게 5배는 빠릅니다. 함정: 가이드 작성자가 본인의 환경(macOS + zsh + Homebrew)만 가정하면 Windows + PowerShell 사용자들이 막힙니다. 최소 두 가지 OS의 스크린샷을 같이 두십시오.

8단계: 모니터링 (1주 관찰)

마이그레이션 후 최소 1주는 두 환경(또는 두 명령)을 병행 운영하면서 출력 품질을 비교하십시오. 같은 PR에 대한 자동 코드 리뷰가 새 도구에서 더 짧아졌거나, 사용한 토큰이 갑자기 30% 늘었거나 하는 변화가 첫 며칠에 드러납니다. 본인 팀은 CI에서 두 도구를 동시에 돌리고 결과를 별도 채널에 게시하는 단순한 옵저버 모드를 7일 운영한 후 Gemini CLI 호출을 제거했습니다. 함정: 1주 옵저버 운영을 빠뜨리면 6/18 당일 처음 문제를 발견하게 됩니다. 그 시점에는 이미 Gemini로 폴백할 길이 없습니다.

자동화 도구 - 일괄 변환 스크립트 예시

본인이 사용한 sed 기반 일괄 변환 스크립트입니다. 명령어 동사와 환경 변수 이름만 처리합니다. 출력 포맷 파싱은 사람의 검토가 필요합니다.

#!/usr/bin/env bash
# migrate_gemini_to_antigravity.sh
# 사용법: ./migrate_gemini_to_antigravity.sh <디렉토리>
# 주의: 반드시 git에 커밋된 상태에서 실행하십시오.

set -euo pipefail

TARGET_DIR="${1:-.}"

# 1. 명령어 동사 매핑
find "$TARGET_DIR" -type f \( -name "*.sh" -o -name "*.yml" -o -name "*.yaml" -o -name "Dockerfile" \) -print0 | \
  xargs -0 sed -i.bak \
    -e 's/\bgemini chat\b/antigravity/g' \
    -e 's/\bgemini run\b/antigravity task/g' \
    -e 's/\bgemini edit\b/antigravity edit/g' \
    -e 's/\bgemini config\b/antigravity config/g' \
    -e 's/\bgemini auth\b/antigravity auth/g'

# 2. 환경 변수 이름 매핑
find "$TARGET_DIR" -type f \( -name "*.sh" -o -name "*.yml" -o -name "*.yaml" -o -name ".env*" -o -name "Dockerfile" \) -print0 | \
  xargs -0 sed -i.bak \
    -e 's/GEMINI_API_KEY/ANTIGRAVITY_API_KEY/g' \
    -e 's/GEMINI_PROJECT_ID/ANTIGRAVITY_PROJECT_ID/g'

# 3. JSON 플래그 매핑
find "$TARGET_DIR" -type f \( -name "*.sh" -o -name "*.yml" -o -name "*.yaml" \) -print0 | \
  xargs -0 sed -i.bak -e 's/--json\b/--format json/g'

# 4. 백업 파일 정리
find "$TARGET_DIR" -name "*.bak" -delete

echo "[OK] 자동 변환 완료. git diff로 결과를 검토하십시오."
echo "[주의] 출력 파싱(jq, awk) 부분은 수동 점검이 필요합니다."

실행 전 항상 git에 커밋된 상태인지 확인하고, 실행 후 반드시 git diff로 결과를 검토하십시오. 본인의 경험상 자동 변환이 80%를 처리하고 나머지 20%는 사람의 손이 필요합니다.

마이그레이션 시 흔한 함정 6가지

본인 팀과 주변 팀에서 직접 본 함정들입니다.

1) JSON 스키마 미세 변경을 놓치고 파서 깨짐. Antigravity의 --format json 출력은 Gemini CLI의 --json 출력과 큰 틀은 같지만, response.text가 output.message.content[0].text로 깊어졌고, usage 키 아래 토큰 카운트 필드명이 일부 바뀌었습니다. jq 표현식을 그대로 두면 빈 값을 받아 오는 침묵 실패가 됩니다.

2) OAuth 토큰을 CI에 그대로 넣으려다 실패. Antigravity의 OAuth 토큰은 짧은 유효 기간을 가집니다. CI에서는 OAuth가 아니라 API 키를 시크릿으로 주입하는 방식이 정답입니다. 일부 팀이 로컬 OAuth 토큰을 그대로 시크릿에 박았다가 첫 만료 후 갑자기 멈췄습니다.

3) 한국어 입력 처리 미묘한 차이. Gemini CLI는 한국어 멀티바이트 입력에서 줄바꿈 처리가 가끔 어색했습니다. Antigravity는 이 부분이 좋아졌지만, 그 결과로 일부 정규식 후처리가 의도하지 않은 매칭을 만듭니다. 한글 자모 분리 입력을 다루는 코드가 있다면 별도 점검하십시오.

4) 모델 자동 선택과 비용 폭증. Antigravity는 작업 복잡도에 따라 자동으로 더 큰 모델을 호출하는 옵션이 기본 켜져 있습니다. 예전 Gemini CLI에서 --model gemini-2.5-pro로 명시했다고 가정하고 그대로 두면, 비슷한 작업에서 의외로 큰 모델로 라우팅되어 월 비용이 늘어날 수 있습니다. antigravity config set routing.auto_upgrade false로 비활성화하거나, 적어도 모니터링을 켜 두십시오.

5) Windows의 OS 키체인 경고. Windows Credential Manager에 토큰을 저장할 때 일부 회사 보안 정책이 이를 차단합니다. 이 경우 API 키 환경 변수 방식으로 폴백하거나, IT 부서와 협의해 예외를 받아야 합니다.

6) 사라진 플러그인. Gemini CLI의 플러그인 시스템은 Antigravity에서 폐지되었고 MCP 서버로 재포장되어야 합니다. 자체 플러그인을 만들어 쓰던 경우 가장 시간이 많이 드는 부분이며, 4주 일정에서 가장 먼저 손대야 합니다.

Gemini CLI 종료가 강제 마이그레이션이지만, 그 기회에 대안을 살펴보는 것도 합리적입니다. 본인이 직접 사용해 본 도구들을 정직하게 비교합니다.

한국 개발자 환경 특화 팁

한국에서 일하면서 부딪힌 환경별 특이점들입니다. KT와 Naver 사내망에서는 외부 OAuth 콜백이 자주 차단됩니다. antigravity login이 멈춰 있다면 antigravity login --device-code로 디바이스 코드 흐름을 사용하십시오. 브라우저가 외부와 통신할 필요 없이 코드 6자리만 입력하면 됩니다. 한국어 입력에 있어 Antigravity는 한글 자모 분리 입력(예: "ㄱ + ㅏ + ㅁ")을 자동으로 합성하지만, 일부 IME(예: Naver 한컴 IME)에서는 멀티바이트 경계가 어긋나는 경우가 있습니다. PowerShell 사용자는 chcp 65001로 UTF-8 코드 페이지를 설정하면 대부분 해결됩니다.

Vertex AI 한국 리전 사용자라면 한 가지 확인이 더 필요합니다. Antigravity CLI는 기본 리전이 us-central1입니다. antigravity config set vertex.region asia-northeast3로 서울 리전을 명시하지 않으면 API 호출이 미국으로 라우팅되어 지연이 증가합니다. 본인 측정 기준으로 서울에서 us-central1까지 첫 토큰 지연이 평균 280ms, asia-northeast3에서는 65ms입니다. 4배 차이입니다. 회사 보안 정책으로 사외 LLM 호출이 차단된 환경에서는 Vertex AI Private Endpoint와 Antigravity의 endpoint 오버라이드 옵션을 조합해 사용해야 합니다. 이 설정은 정보보안팀과의 협의가 필요하며, 본인 팀 기준으로 2주 정도 걸린 작업이었습니다.

마지막으로 결제와 청구서입니다. Google Workspace 기업 계정으로 결제하던 GEMINI 사용자는 같은 계정의 Antigravity 사용량으로 자동 마이그레이션됩니다. 별도 결제 수단 등록은 필요 없습니다. 다만 청구서 항목 이름이 "Gemini API"에서 "Antigravity API"로 바뀌므로, 사내 회계 시스템에 항목명을 등록해 두지 않으면 6월 청구서가 미분류 항목으로 잡혀 결재가 늦어질 수 있습니다. 회계팀과 미리 공유하십시오.

D-day 후 시나리오 - 6월 19일 아침에 일어나는 일

마이그레이션을 마쳤다는 가정 하의 6월 19일 아침을 상상해 봅니다. 오전 8시, 한국 시간으로는 6월 19일 새벽 3시 59분에 이미 Gemini CLI의 API 응답이 401로 끊긴 상태입니다. 일어나 슬랙을 열면 (마이그레이션을 안 한) 어딘가의 팀에서 CI 실패 알림이 폭주하는 게 보일 것입니다. 본인 팀이 그 상황이 아니라면, 이 순간 가장 큰 리스크는 준비 안 된 외부 의존성입니다. 본인 코드가 호출하는 어떤 사내 서비스가 내부적으로 Gemini CLI를 쓰고 있었다면, 그 서비스가 멈추면서 본인 코드도 함께 떨어집니다.

오전 10시, 사내 ChatOps 봇이 PR 자동 리뷰를 멈춥니다. 본인 팀은 Antigravity로 갈아탔지만, 회사 다른 팀에서 운영하는 봇이 아직 Gemini를 호출하고 있었다면, 그 봇이 죽으면서 본인 팀 PR도 자동 리뷰 없이 머지를 기다리게 됩니다. 미리 다른 팀에 D-day를 알린 게 가치를 발휘하는 순간입니다. 오후 2시, Hacker News와 hada.io에 "Gemini CLI 사라진 첫날" 회고 글들이 올라옵니다. 본인 팀이 안정적으로 돌아간다는 사실이 안도감을 줍니다.

6월 25일까지 1주, Antigravity 토큰 사용량이 첫 정산되면서 마이그레이션 후 첫 청구서 변화를 봅니다. 본인 추정으로는 같은 작업량 기준 약 10~20% 비용 감소가 일반적이지만, 자동 모델 업그레이드 옵션을 끄지 않았다면 오히려 증가할 수도 있습니다. 이 변화를 토대로 6월 말에 최종 비용 보고서를 정리하고, 마이그레이션 프로젝트를 닫습니다. 핵심은 D-day가 정말 D-day로 동작하지 않게 만드는 것입니다. 잘 준비된 팀에게 6월 19일은 그냥 평범한 목요일 아침이어야 합니다.

결론 + 즉시 해야 할 액션 3가지

이번 변화의 본질은 "도구 하나가 다른 도구로 바뀌었다"가 아닙니다. Google의 CLI 전략이 통합되고, MCP 기반 에이전트 패러다임이 모든 주요 랩에서 1급 시민이 되었다는 신호입니다. Gemini CLI 사용자는 강제로, 그렇지 않은 사용자도 결국 이 방향으로 끌려갑니다. 본인 추측으로는 OpenAI도 올해 안에 Codex CLI를 비슷한 방향으로 재정렬할 가능성이 큽니다. 그 시점에 본인 스택이 이미 MCP 기반으로 정돈되어 있다면 그 다음 변화는 훨씬 부드럽게 처리됩니다.

D-day까지 약 4주, 본인이 지금 즉시 권하는 액션 세 가지입니다. 첫째, 이번 주 안에 Antigravity CLI를 본인 노트북에 설치하고 30분만 써 보십시오. 명령어가 어떻게 다른지 손에 익는 것이 모든 후속 결정의 출발점입니다. 둘째, grep -rn "gemini" ~/Projects/를 돌려 본인 코드의 의존성 표면을 한 장의 지도로 만들어 두십시오. 보이지 않으면 옮길 수 없습니다. 셋째, 팀이 있다면 다음 화요일 30분짜리 마이그레이션 오피스 아워를 캘린더에 잡으십시오. 글로 아무리 잘 써도 옆에서 같이 한 번 해 보는 것이 5배 빠릅니다. 이 세 가지를 이번 주에 끝내면, D-day는 그냥 평범한 목요일이 됩니다.
