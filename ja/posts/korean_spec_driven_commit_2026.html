コードの代わりに韓国語の仕様書をコミットする

スペック駆動開発がひっくり返す「ソース」の定義 - 仕様が真実の源泉になり、コードが成果物になるとき何が変わるか

2026年7月18日 開発・インフラ

はじめに: コードではなく仕様をコミットするという発想

GeekNewsに最近投稿された一つの記事が目を引いた。投稿者は自ら作ったPWAアプリを例に、152行のコードを28行の仕様書に置き換えてバージョン管理にコミットしたと紹介している。最初は奇妙に聞こえる。バージョン管理はもともとソースコードのためのものではないか。しかしAIが瞬時にコードを書き上げる時代に、本当に守るべきものがコードそのものなのかを改めて問うと、話は変わってくる。

本稿はこの一つの実験だけを紹介したいわけではない。この実験が指し示すより大きな流れ - スペック駆動開発(spec-driven development)、そしてその根底にある「仕様がソースであり、コードは成果物である」という発想の転換 - を掘り下げてみたい。この流れはすでにGitHub Spec KitやAWS Kiroのようなツールを通じて主流のコーディングエージェント・エコシステムに浸透しており、昨日取り上げた理解こそが新しいボトルネックだとSpecifyの2本の記事ともつながっている。3本の記事はいずれも、結局同じ問いを別の角度から投げかけている。AIがコードをタダ同然で作ってくれる世界で、人間が守るべきものは何か。

1. 何が話題なのか - 数枚の仕様でアプリとサーバーを動かす

1.1 実験の骨格

GeekNewsで紹介された事例は「Rimlog」という読書・学習記録PWAアプリである。投稿者は自作ツールで韓国語仕様をコードに変換すると紹介している。サーバー側も1枚の仕様から出発したNode単一ファイルで、外部依存はゼロ、NVIDIA・Claude CLI・OpenAI・Googleなど複数のAIバックエンドを選んで使えるよう設計したと述べている。

1.2 整合性をどう守るか

最も興味深いのは、仕様とコードの整合性を守る方法だ。投稿者は仕様のハッシュ値を生成されたコードに埋め込み、仕様が変更されたのにコードがそれに合わせて再生成されていなければコミット自体をブロックすると紹介している。つまり仕様とコードがずれた状態を機械的にふるい落とす仕組みだ。これは単なる文書化ではなく、仕様をコードと強く結びついた契約として扱うという宣言である。

2. 発想の転換 - コードは成果物、仕様が真実の源泉

2.1 SSoTの移動

ソフトウェア開発において長らく「真実の源泉(source of truth)」はコードだった。文書・設計書・コメントはコードを説明する副次的な資料であり、コードと文書が食い違えば大抵は文書のほうが間違っているとみなされた。スペック駆動開発はこの序列をひっくり返す。バージョン管理された構造化仕様が真実の源泉となり、コードはその仕様から人間とAIエージェントが生成または検証する二次的な成果物になる。

2.2 レビュー対象が移る

この転換が実務に与える最も直接的な影響は、レビュー対象の移動だと本稿は見る。コードレビューが「この実装は正しいか」を見るものだったなら、仕様レビューは「この意図は正しいか」を見る。AIが実装段階を事実上代行してくれる今、人間が本当に判断すべき点はコードの文法ではなく、要件の整合性と完結性のほうへ移っていく。GitHub Spec Kitもこれを「コードは開発の最後の一歩(last-mile)にすぎない」という言葉で表現している。

2.3 再現性という利点

仕様がソースであるということは、再現性の問題でもある。コードだけがコミットされていると、なぜこの構造を選んだのかはチャット画面の中だけに残って消えてしまう。昨日のSpecify分析で指摘した通り、「この関数はなぜこう書いたのか」という問いに答えられる人がいなくなる問題は、AIコーディング時代にむしろ深刻化した。仕様をコミットしておけば、その意図自体がバージョン管理の履歴に残り、後で再び実装し直しても元の意図に立ち返れる基準線が生まれる。

3. なぜ今なのか - スペック駆動開発の流れとの接点

3.1 すでに主流ツールに入り込んでいる

この発想は一個人のプロジェクトだけのものではない。2026年現在、GitHub Spec Kit、AWS Kiro、Claude Code、Cursor、OpenSpec、BMAD、Tessl、Google Antigravityなど主要なAIコーディングツールの大半が、独自のスペック駆動開発方式を備えていると報告されている。多くはリポジトリ内にspecs/のようなディレクトリを置き、バグや機能要求が来ると仕様を先に修正し、コードをそれに合わせて再生成または修正する流れを取る。

3.2 三つの失敗モードへの対応

この流れが対応しようとしている問題ははっきりしている。第一は意図の漂流(intent drift)だ。「ログイン機能を追加して」のような指示はひどく不十分で、モデルはそれらしいデフォルト値を選んで埋めるが、そのデフォルトがチームが本当に望んでいたものと違うことが多い。第二は文脈の喪失(context decay)だ。会話が長くなりセッションが変わると、以前合意した制約があいまいになる。第三は検証不可能な成果物だ。もっともらしく見えるコードが実際に要件を満たしているかを確認する基準がない。仕様を固定された契約として前面に出せば、この三つの問題すべてに検証可能な基準線が生まれる。

3.3 ADR・intentコミットとの接点

実は「決定の背景を記録しておく」という発想自体は新しくない。アーキテクチャ決定記録(ADR)は昔から「なぜこの構造を選んだか」を別文書として残す慣行だった。ただし以前はADRが人間だけが読む副次的な文書だったのに対し、今はAIエージェントが作業を始める前にその文書を直接参照するよう設計される点が異なる。仕様をコミットするという行為は、この古い慣行がAI時代に再び呼び戻され、文書ではなく実行可能な契約へと格上げされた事例として読むのが本稿の判断だ。

4. 韓国語(自然言語)の仕様をコミットする意味

4.1 意図の保存と非開発者との協業

自然言語仕様の最も直接的な利点は、参入障壁が低いことだ。コードが読めなくても「この機能はこう動くべきだ」という文なら、企画者・PM・デザイナーも読んで修正できる。特に母語で書かれた仕様は、翻訳という認知的負担なしに意図をそのまま込められる。思考を英語に移す過程で微妙なニュアンスが抜け落ちることは実務ではよくあるが、韓国語で先に仕様を整理すればこの損失を減らせる。

4.2 実装の乗り換えやすさ

仕様が特定の言語やフレームワークに縛られていなければ、同じ仕様から別の実装を新たに引き出すことが理論上容易になる。Rimlogの事例でサーバーが複数のAIバックエンドを選んで使えるよう設計されている点も、こうした言語中立性の延長として読める。ただしこれは、仕様が実際に実装の詳細をどれだけ排除し「何を」というレベルにとどまっているかに左右される。仕様の中に特定のライブラリ関数名やAPIシグネチャがそのまま書き込まれていれば、言語中立性は名ばかりになる。

5. 難点 - 良いことずくめではない

5.1 自然言語仕様の根本的な曖昧さ

自然言語はブール条件ではない。「素早く応答すべきだ」という文は人間には自然に聞こえるが、どれくらい速いのか、どんな条件下なのかが定義されなければ、AIも人間もそれぞれ違う解釈をする。関連研究も、自然言語仕様は実行可能な具体的条件を直接定義できないため、実行結果とすぐに照合するのが難しいと指摘する。結局、仕様がどれほど丁寧に書かれても曖昧さを完全になくすことはできず、どれだけ減らせるかという問題として残る。

5.2 非決定的な生成

同じ仕様を入力しても毎回同じコードが出る保証はない。関連研究によれば、LLMは温度(temperature)を0に設定しても完全には決定的でなく、一部のモデルは同一入力に対しても4回に1回程度異なる出力を出すと報告されている。コードが成果物にすぎないという発想は、裏を返せば「同じ仕様から毎回まったく同じコードが出るとは限らない」という事実を受け入れる必要があるということでもある。再現性を仕様側で確保したなら、コード側の再現性はむしろ緩くなり得るというトレードオフだ。

5.3 検証とテストの問題

関連調査によれば、QAとステージングを通過したAI生成コードの変更のうちでも43%は結局本番環境で手動デバッグが必要だったという。単体テストはコードが仕様に合っているかをある程度捉えられるが、サービス境界をまたぐアーキテクチャ違反やAPI契約のずれまでは捉えきれない場合が多いという指摘もある。仕様を前面に出したからといって検証の負担が消えるわけではなく、検証対象が「コードが仕様と一致しているか」という一つ増えると見るのが正確だろう。

5.4 仕様ドリフト

より厄介な問題は仕様ドリフトだ。時間が経つにつれ実際の挙動が仕様から少しずつずれていくが、テストが壊れることもパイプラインが失敗することもないままそれが起こり得るという指摘がある。コードだけを直し続けて仕様を更新しなければ、仕様はすぐに「かつてそうだった文書」に成り下がる。Rimlogの事例が仕様ハッシュをコードに埋め込み、不一致時にコミットをブロックする仕組みを設けたのも、まさにこのドリフトを機械的に防ぐための試みとして読める。ただし、すべてのチームがこうした仕組みを自前で構築する余力があるわけではない。

5.5 結局デバッグはコードで行う

最も現実的な限界はこれだ。仕様がどれほど真実の源泉であっても、本番環境で実際に動いているのはコードである。バグが起きればログを追い、スタックトレースを読み、実行経路をたどる必要があるが、この作業は仕様ではなくコードのレベルで起こる。スペック駆動開発がコードをまったく見なくて済むようにしてくれるという期待は誇張だ。仕様は「何を作るか」を明確にする点では強力だが、「なぜ今これが壊れたのか」を診断する点では依然としてコードを読む力が必要だ。

6. 韓国語で仕様を書くこと - 実益と限界

6.1 母語の実益

韓国の開発チーム内だけで回るプロジェクトなら、韓国語仕様には明確な利点がある。企画会議で出た文をほぼそのまま仕様に書き写せ、非開発職もレビューに参加できる。思考過程を英語に移す際に生じる微細な損失も減る。

6.2 国際協業・オープンソースにおける限界

逆にオープンソースとして公開したり海外チームと協業する必要があるプロジェクトなら、韓国語仕様はそれ自体が参入障壁になる。またLLMの自然言語理解の品質が言語ごとに均一でない点も考慮すべきだ。英語の学習データが依然として圧倒的に多い状況で、同じ精緻さの韓国語仕様と英語仕様を同じモデルに入れたとき結果の品質が同じだと断定するのは早い。結局、韓国語仕様は「チーム内部の思考と協業」には強く、「外部公開と言語間の移植性」には別途の翻訳層が必要だと見るのがバランスの取れた見方だ。

7. 実務適用ガイド - 仕様に何を盛り込むか

7.1 意図・制約・インターフェースを盛り込め

仕様には詳細な実装ではなく「何を、なぜ、どんな制約の中で」を盛り込むべきだというのが、複数の事例で共通して確認される。特定の関数名や内部アルゴリズムまで仕様に固定してしまうと、かえってAIがより良い代案を提案する余地を自ら失わせることになる。

7.2 テストで仕様を固定せよ

仕様だけでは曖昧さを完全になくせないため、中核となる挙動はテストで固定しておくほうが安全だ。関連調査でも、仕様とTDDを組み合わせた方式が実際に出荷可能なAI生成コードを作る組み合わせとして紹介されている。仕様が「意図」を表すなら、テストはその意図が実際に守られたかを機械的に確認する役割を担う。

7.3 仕様とコードを並行して進化させよ

極端に「コードは一切見ない」という態度よりも、仕様とコードが並んで生きた文書として共に進化する方式が現実的だ。関連研究でもこうした「スペック・アンカード(spec-anchored)」アプローチを、ほとんどのプロダクションシステムに合った折衷点として紹介している。仕様を先に修正しコードを再生成しつつ、生成されたコードも人間が目を通し、必要なら直接手を入れる構造である。

8. 昨日の2本の記事とつながる点

この流れは昨日取り上げた2本の記事と正確に噛み合う。理解こそが新しいボトルネックだは、AIがコードを安く作ってくれる世界で本当に不足している資源は人間の理解速度だと指摘した。スペック駆動開発はこの問題に対する一つの構造的な答えになり得る。コードを一行ずつ検証する代わりに、仕様レベルで意図を検証すれば、理解すべき表面積が減るからだ。もちろんこれは「検証的理解」の負担を減らすだけで、「参加的理解」 - なぜこの方向が正しいのかを判断する能力 - までは代わりにしてくれない。

Specifyの分析で指摘したワークスペースメモリの概念とも通じる。Specifyが決定の背景を記録してAIエージェントが直接参照できるようにすると言っていたなら、仕様をコミットする方式はその背景記録を別のワークスペースではなくバージョン管理システムの中に引き込むアプローチだ。どちらがより優れているかはツールの問題であり、本質は同じである。AI時代に人間が守るべき資産はコードそのものではなく、「なぜこう作ったのか」という文脈だということだ。

結論: コードではなく意図をコミットせよ

仕様をコミットするという発想は、ソフトウェア開発の真実の源泉をコードから意図へ移そうとする試みだ。2026年7月時点で、この流れは一個人の実験を超え、GitHub Spec KitやAWS Kiroのような主流ツールにすでに浸透している。利点ははっきりしている。意図がバージョン管理に残り、非開発者もレビューに参加でき、実装の乗り換えが容易になる。しかし自然言語の曖昧さ、非決定的な生成、ドリフト、そして結局デバッグはコードで行うという現実はそのまま残る。

本稿の結論はこうだ。スペック駆動開発を「コードを見なくて済む魔法」として受け止めれば失望しやすい。代わりに「レビューと再現性の単位をコードから意図へ一段引き上げる道具」として受け止めれば実益は大きい。次にAIエージェントに機能を一つ任せる前に、プロンプトを投げる代わりに短い仕様 - 何を、なぜ、どんな制約の中で - をファイルに先に書いてコミットしてみることから始めてもよいだろう。
