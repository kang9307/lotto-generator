决定把视觉AI放到现场设备上 - 这个决定其实已经替你定下了什么

是带宽、延迟还是合规，理由不同设计就不同。而且运行时会先于精度被定下来

2026年9月1日 IT/技术

视觉识别项目出问题的地方，多半不在模型上。精度在办公室里早就跑出来了，演示也顺利。麻烦在之后才来：摄像头从十二路变成六十路，安装地点从会议室换到车间通道和室外闸口，网络从办公室的千兆换成现场的上行链路。在这个节点上重新被打开的问题，不是「模型怎么缩小」，而是「这项作业要不要放到现场」。

而这个决定一旦落下，后面的大部分选项就已经被它替你定好了。能用哪一类加速器、哪些模型系列还能进候选、什么东西允许上传到服务器、部署之后怎么更新，全都在这里分岔。这篇文章按顺序讲这个决定该怎么做，以及它实际上替你定下了什么。

本文是对现场视觉识别系统部署结构的一般性梳理，不是对任何特定产品或厂商的评价与推荐。文中引用的许可证与文档内容以2026年9月初的公开资料为准，条款此后可能变动，实际选型前需核对原文。法规部分只是条文本身的介绍，不构成针对具体安装情形的法律意见。

画面全部上传再处理这个前提在哪里崩掉

大多数数据是在有事发生时才产生的。来了一笔订单就有一条订单记录，有人登录就有一行日志。视频不是这样。什么都没发生的时候，它照样以同样的速度不停产生。这是视觉部署成为另一类问题的第一个原因。

换成数字就清楚了。一路 1080p 视频以 4Mbps 全天不停地传，一天大约 43GB。三十路摄像头是一天 1.3TB，一个月接近 40TB。要紧的是这个值是下限而不是平均。场景一复杂、夜间噪声一上来，可变码率就往上贴；凌晨安静也不会因此减半。

上行链路的不对称还要叠加上来。进到现场的线路通常下行宽、上行窄。办公室里跑得好好的方案到了现场垮掉，原因往往不是模型变重了，而是往外送的通道变窄了。存储也沿同一条轴增长：把保留期多延几天，和多装几路摄像头，落在同一条成本线上。

不能上传的三个理由要的是不同设计

「不能全都送到云上」这一句话里，其实混着三样不同的东西：带宽与存储要花的钱、从画面到动作的时间、以及规定画面不得离开现场的法规或合同。这三样看起来结论一样，要的设计却完全不同。所以在项目早期必须把理由收敛成一个。

把三者搅在一起，常见的结果是这样：真实的理由是成本，却为了压延迟买了昂贵的加速器，线路费一分没少。或者在数据不得外流的情形下把推理搬到了现场，调试用的缩略图和崩溃报告却照旧往外走。边界不是只画在推理这一处的。

不能上传的理由它真正要求的东西读错了会怎样
带宽与存储成本减少上行链路上的字节。判定晚上几秒往往并无妨碍为了压延迟去买高性能加速器，而每月照付的那笔钱纹丝不动
响应延迟从画面到达到动作输出的时间上限，要按最差值而不是平均值来卡只量平均延迟就放行。人真正感到难受的是偶尔跳起来的那一段
数据不得外流把边界画成物理的，除推理外还要覆盖日志、缩略图、崩溃转储与模型更新通道只把推理搬到现场，画面仍从各种附带通道持续渗出去
  • 如果理由是成本，优化对象就是上行字节而不是模型。模型砍掉一半，只要原始视频照传，什么也不会变
  • 如果理由是延迟，验收标准要写成分位数。平均 40 毫秒当不了两个团队之间的共识
  • 如果理由是合规，先要画的不是架构图，而是数据经过的每一条线。远程支援会话和日志收集器是最常被漏掉的两处
  • 三者中确实有两个同时成立的情况。即便如此也必须有一个排在第一，否则折中方案定不下来

上传的不是原始视频，而是事件

让这个部署决定真正可执行的，是一次视角的转换。放在现场的不是模型，而是把视频变成事件的那一步转换。摄像头产出的是无尽的像素流，而下游系统需要的通常只是几句话，比如：三号闸口，14时22分07秒，一台叉车越过了停止线。

用前面的数字重算一遍，差距就出来了。假设一条带时间、类别、坐标、置信度再加一张小缩略图的事件是 20KB，一路摄像头一天产生两百条，那么三十路一天合计约 120MB。跟传原始视频的 1.3TB 相比，是四个数量级的差。这些数字是从假设推出来的算术而非实测，但把假设改动两三倍，数量级也翻不过来。

  • 一旦变成事件，下游系统就成了一条普通的数据管道，不再需要视频专用的基础设施
  • 代价也随之而来。没有被识别成事件的画面，等同于从未发生过。事后无法回看
  • 所以稳妥的顺序是前几个月刻意多留，等判定标准稳定下来再收紧
  • 保留策略不是技术决定，而是要和运营与法务一起定的决定。后补上去时，已经堆下的数据本身就成了问题

那条线画在哪里

原始视频还是事件，这不是二选一，而是一条连续的刻度。刻度落在哪里，一次性决定了带宽成本、再训练的可能性和个人信息的暴露范围。这一行几乎就是系统设计文档本身。

实务中常用的位置大致有五处。越往上信息留得越多，成本与风险也一同上升。

线的位置上传到服务器的东西再也拿不回来的东西适合的情形
原始视频全量每一帧没有摄像头数量少、带宽有余，且早期急需再训练数据
事件前后的片段包含判定瞬间的一小段视频没有产生判定的那些时段的画面需要人来最终确认的判定
事件加缩略图元数据与一张低分辨率图像只有原始画质才看得出来的依据工业检测、计数这类判定明确的作业
只有事件元数据时间、类别、坐标、置信度画面本身。错判无法用眼睛核对不允许留存视频本身的区域
只有汇总值每小时条数之类的统计单个事件的可追溯性线路极窄的偏远站点
  • 这条线可以逐路摄像头不同。实际上给出入口区域和产线套同一套策略才更奇怪
  • 把线往下挪容易，往上抬难。已经丢掉的帧不会回来
  • 所以在定这条线时要把回退成本一并写下。重新采一次的代价通常比存下来更大

现场设备强加给你的约束

决定放到现场，那台设备就跟机房里的服务器是两码事。它要装进无法加风扇的密闭外壳，电从既有配电盘上引，夏天环境温度还会往上走。发热的上限比性能的上限先到。基准测试里的吞吐是一小段时间的值，实际运行则是连续几个月不停。

内存的性质也不一样。服务器上不够可以加，现场设备的内存多半是固定的，没有扩展插槽。里面不是只有一个模型，而是解码器、预处理缓冲、跟踪状态和操作系统共用同一块内存。摄像头一加，先卡住的就是这里。

  • 持续吞吐和瞬时吞吐是两个数。在温度上来就降频的结构里，三十分钟之后的那个值才是真的
  • 功率预算由现场而不是外壳来定。装不进既有的配电容量，电气施工就会被算进项目里
  • 物理接触很贵。如果重启一次就得有人跑一趟，稳定性就不是舒适度，而是一条成本项
  • 供货周期开始变得重要。开发板今天好买，三年后还能不能买到同一型号是另一回事
  • 开机后自动恢复是基本要求。停电不会按计划来，而现场通常无人值守

运行时先于精度被定下来的位置

这是这个话题里顺序最常被颠倒的一步。习惯做法是看精度表挑模型，然后再配硬件。现场部署恰恰相反。加速器执行的不是模型，而是算子。模型里若有那块加速器的运行时不支持的运算，那部分只能跑到别处去。

ONNX Runtime 的文档把这套机制说得很明白。执行提供器通过 GetCapability() 接口报告自己能承接的节点与子图，运行时据此切分计算图；而提供器列表是按优先级排序的。写成 ['CUDAExecutionProvider', 'CPUExecutionProvider']，能跑的节点交给 CUDA，其余交给 CPU。

正因为有这套设计，转换整体失败的情况很少。问题恰恰就出在它不会失败。模型跑得好好的，结果也对，可图中间那几个节点已经悄悄掉到了 CPU 上，每一处接缝都要来回搬一次内存。吞吐达不到预期的原因，在任何地方都不会以错误的形式留下痕迹。

  • 收敛候选模型时，在精度旁边那一栏一并写上「在目标运行时上是否整体卸载」
  • 确认的办法是运行而不是文档。在目标设备上真转一次比读支持列表快
  • 后处理里如果含有冷门算子，把那一段挪到模型之外往往更划算
  • 也有一开始就设计成不需要 NMS 的系列。Ultralytics 在文档中写明，2026年1月发布的 YOLO26 默认采用一对一头部，因而无需 NMS 就能给出端到端的预测

转换环节里悄悄发生的变化

转换不是只换个格式。精度一降下来，结果也跟着动。ONNX Runtime 的文档写得毫不含糊：量化不是无损变换，它可能对模型的精度产生负面影响。所以同一份文档还一并介绍了把原始计算图与量化后计算图的权重、激活张量拿来对比的调试工具。

选择依据文档里也写了：循环神经网络与 Transformer 系推荐动态量化，卷积神经网络推荐静态量化。静态方式要先灌一批校准输入求出量化参数，再作为常量写死，因此校准数据一旦和现场的真实画面有出入，这个差距会原样落到精度上。训练后量化达不到目标时，文档接着建议改用量化感知训练重新训练。

缩小模型的技法本身怎么运作、又先丢掉什么，不是这篇文章的主题。平均精度守住了、罕见样本却先塌掉的那种结构，在蒸馏与量化后的小模型失去了什么里另行讲过。这里只需记住一点：不用同一批数据比对转换前后，你连精度已经变了这件事本身都不会知道就上线了。

  • 验收标准要按在目标设备上运行的转换后模型来卡，而不是转换前的模型
  • 校准数据必须来自将要安装的现场抽出来的帧，用训练集是没有意义的
  • 夜间、逆光、粉尘这类条件差的时段，一定要放进评测集。平均值正好会把它们盖住
  • 转换流程别用手工，要固定成脚本。无法复现的转换，事后根本查不出原因

许可证要在部署之前读

这一项之所以总是被晚发现，原因很简单：在训练和评测阶段它不会惹任何麻烦。麻烦是在那个模型进入被销售的设备时才出现的，而那时整条流水线早已围着这个模型搭好了。它属于在收敛候选名单阶段就该和精度并排放在一起读的项目。

瓶颈通常不在推理

把推理时间压掉几毫秒，这活儿看得见，汇报起来也好听。可把从摄像头输入到事件产出的整条路径摊开来看，那几毫秒往往只是其中很小的一块。把压缩流解开、把像素改成模型要的尺寸与格式、把出来的框整理干净并在帧与帧之间把同一个物体接起来，这些都在吃时间。

摄像头输入 → 解码 → 预处理 → 模型推理 → 后处理 → 跟踪与判定 → 事件

[由加速器承担的段]   模型推理
[压到 CPU 上的段]    预处理 · 后处理 · 跟踪 · 事件发送
[硬件解码器]         解码 (有它就从 CPU 上卸下，没有就落到 CPU 上)

这里反复出现的情况是这样：加速器占用率不高，吞吐却上不去。原因多半是解码与内存拷贝。没有硬件解码器，或者流水线根本没走它，这份负担就整个压到 CPU 上。加摄像头时先饱和的也不是加速器，而是这一段。

  • 动模型之前，先把各阶段的耗时分开量一遍才是顺序。不量就优化，多半是在挖空地
  • 有没有硬件解码器，和选定的流水线是否真的在用它，是两个问题
  • 减少加速器与 CPU 之间的拷贝，效果往往比缩小模型更大
  • 后处理随摄像头数量线性增长，却常常没被加速。这里往往才是横向扩展的真实上限
  • 把不是瓶颈的地方加快，整体不会变。哪条轴上真正拉开差距，在选推理硬件时真正拉开差距的是什么里按带宽、延迟、生态三条轴梳理过

该数的不是每秒几帧，而是每秒几条事件

上一节的结构直接决定了该怎么测。模型单独的吞吐只是流水线里一个环节的值。决定一套系统能带多少路摄像头的，是从摄像头输入到事件发出的端到端吞吐。这两个数在同一台设备上也会拉得很开。

不写测试条件的吞吐值之所以没有用，原因也在这里。输入分辨率、批大小、精度、并发流数、是否含后处理，以及是跑到第几分钟量的，都会改变结果。哪怕是同一台设备上同一个模型跑出来的数，条件不同就无法比较。所以厂商资料里的数字，更适合当作缩小候选范围的提示，而不是选型决定的依据。

实务上能用的形式，一句话就写完了：这台设备在这个分辨率下用这个模型，同时处理这么多路摄像头、每路每秒多少帧，并且在环境温度多少度下连续跑多少小时。这句话填不满，就还谈不上测过。

  • 验收标准里一定要有并发流数。单路量出来的值，到十路不会正好除以十
  • 要等散热稳定之后再测。开跑头几分钟的值不是运行值
  • 丢帧策略要事先定好。积压时丢掉什么没定下来，延迟就会一直往上累
  • 事件扎堆的那一刻要单独测。系统崩掉的不是平时，而是事件互相叠在一起的那一段

在现场更新模型意味着什么

在服务器上，部署是件容易回退的事。在现场设备上不是。更新一旦出错，那台设备得有人跑过去才能救活。所以在做部署决定的那一刻，更新方式也一并被决定了。它是从一开始就存在的需求，不是事后再补的东西。

而这里更新的从来不是一个模型文件。模型、转换后的可执行形式、前处理与后处理的参数、判定阈值，以及它们的组合是一起动的。这个组合若没有被绑成一个版本，各个现场就会漂成不同的状态。出了问题却说不清是哪个组合出的问题，这在运维里是最贵的一种状态。

  • 更新失败时必须有自动回到上一版本的通道。非得有人到场才能恢复的结构，本身就是成本
  • 把先推几台设成默认，而不是全量下发。现场条件是逐站不同的
  • 模型和阈值要绑成同一个版本下发。单独去动阈值的习惯，制造的是无法复现的状态
  • 如果无法远程看到设备当前跑的是哪个版本，那套系统就不处于可更新的状态

把错判收回来的那条通道

部署出去的模型一定会判错。要紧的不是错了多少次，而是错的那些有没有一条回来的通道。没有这条通道，系统就被钉死在上线那天的性能上，现场条件一变就悄悄变差。

可这条通道跟前面那条边界的决定正面冲突。要留下再训练用的材料就得存画面，而不存画面正是那条边界所定的。没有两全的答案，有的只是关于留到什么程度的一个共识。这个共识若由技术团队独自定下，日后一定会被推翻。

  • 现场人员必须能一步操作就标出一次错判。要走另一套流程，就没人会做
  • 该收集的不只是判错的样本。判对了但很悬的样本预告着下一次失败
  • 收集范围与保留期限要一开始就写明。事后再定，已经堆下的数据本身就是问题
  • 换模型之前，把上一版在哪些样本上判错列成清单。这份清单会变成下一轮的评测集

视频紧挨着个人信息

视觉识别系统常常装在会拍到人的地方。韩国个人信息保护法把这一块分成固定式与移动式来规定。第25条规范固定式视频信息处理设备的安装与运营限制，其第4款要求设置信息主体能够容易识别的告示牌，载明安装目的与地点、拍摄范围与时间、管理责任人的联系方式等。同条第5款禁止为安装目的以外的目的擅自操作设备或将其对准别处，并规定不得使用录音功能。

第25条之2另行规定移动式视频信息处理设备的运营限制。以业务为目的运营时原则上限制拍摄，在允许的情形下拍摄时，也须通过灯光、声音、告示牌等方式标示并告知拍摄事实。两条条文依据2023年3月14日修订的第19234号法律，自2023年9月15日起施行。实际适用范围随安装地点与目的而变，具体个案仍需另行确认。

  • 从设计角度看，比条文本身更要紧的是它和那条边界的决定指向同一个方向。没有留下的东西，也就不需要管理
  • 把视频变成事件的结构，顺带收窄了暴露范围。这是现场处理的实质好处之一
  • 为调试而存的图像是最常被漏掉的一处。挂着「临时」名字的存储放了好几年是常见的情形
  • 文件是不是真的和画面是不是真的，是两个问题。这个区分在相机签名不担保的东西里另行讲过

为什么最聪明的模型不是答案

把前面这些项摊开摆一遍，共同点就出来了：带宽、发热、运行时支持、转换误差、许可证、更新通道、个人信息范围。这里面没有一项会出现在精度表上。可部署出去的系统之所以停掉或被撤回，理由大多正是从这份清单里来的。

在工业现场胜出的方案通常并不好看。它在既定的功率和既定的外壳里，用既定的成本，夏天冬天都以同样的速度运转。而且关键在于，它是能在一百个安装地点以同样方式重复出来的东西。在一台上做出最好结果的配置，和在一百台上做出同样结果的配置，不是同一套配置。

选模型规模本身是另一个问题，而那取决于任务是怎么定义的，不取决于能力上限；那部分在小模型够用吗里讲过。这篇文章的轴在它前面一步：这项作业要不要放到现场，又凭什么这么定。把理由收敛成一个、把边界画成一行、再把这条边界所要求的运行时、许可证与更新通道一并敲定，剩下的多半会自己跟上来。顺序一颠倒，做出来的就是精度很好却装不上去的系统。

未能确认的部分

  • 没有写任何特定加速器模组的实测吞吐。公开的那些数字在分辨率、批大小、精度、并发流数与测量时长上各不相同，无法确认成可比较的形式
  • 工业设备的供货保证期与产品生命周期政策挂在逐个产品的合同条款里，在公开文档中未能确认。正文只写到它属于需要审查的项目为止
  • ONNX Runtime 之外其他运行时的算子支持清单未逐一确认。部分卸载这套机制本身，是由 ONNX Runtime 文档确认的范围
  • 正文里带宽与存储的计算是从假设的码率与事件大小推出来的算术，不是实测。实际资费单价与现场上行带宽未作确认
  • 关于韩国工业现场视觉AI导入率或失败率的统计资料未能确认，因此没有写
  • 法规部分只是条文内容的介绍，它在某个具体安装情形下如何适用未能确认。具体个案需要另行审查
