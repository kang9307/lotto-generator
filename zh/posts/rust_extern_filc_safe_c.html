一行 extern C 抹掉的保证 - 填补 Rust FFI 边界的方法与代价

封装层和绑定生成器都检查不了契约，那么边界本身能不能被缩小

2026年8月16日 开发/基础设施

引言：编译过了，但不知道什么被关掉了

无论是图像解码器还是加密库，把一份已经成熟的 C 实现接进 Rust 项目时，真正要动手写的代码不过十来行。在 extern 块里写下函数签名，在构建脚本里链接，再套一层薄封装就完事了。能编译，测试也过。

但就在这一刻，项目的性质变了。此前 Rust 编译器施加在整份代码上的保证 — 不读已释放的内存、同一份数据不会出现两个可变引用、不发生数据竞争 — 只在编译器能看见的代码范围内成立。被链接进来的 C 目标文件在这个范围之外。

这篇文章要讲的是：在那条边界上究竟有什么被切断，此前用来填补这道缝隙的各种手法分别挡得住什么、挡不住什么，以及2026年8月出现的 extern "fil-c" 提案如何用另一种方式切分这个问题。先说清楚，那个提案还不是已被采纳的特性 — 具体处于哪个阶段，后文会准确交代。

这篇文章不谈什么也一并讲明。「把 C 用 Rust 重写，还是让 C 留在原地加固」这场路线之争，内存安全绝对主义者 - Rust 与 Fil-C 之争，什么才现实 已经处理过了。这里看的不是那场争论的胜负，而是两个世界相遇的那个点本身。

1. unsafe 在 FFI 里意味着什么 - 编译器停止检查的位置

1.1 声明不是被检查的代码，而是人做出的断言

Rust 安全性成立的依据很简单：编译器对整份代码检查所有权、生命周期与别名规则。这种检查只有在能看到全部检查对象时才有意义。

extern 块正是这个前提破裂的地方。写在那里的签名不是编译器核实过的事实，而是开发者做出的断言。参数个数、整数宽度、结构体字段顺序，一律不会被验证。写错了照样编译、照样运行，问题会在很久之后从毫不相干的地方冒出来。

Rust 2024 版次把语法改成 extern 块本身必须标注 unsafe，正是为了把这个性质摆到语法上。这件事在 RFC 3484 里定了下来，2024 及之后的版次中 unsafe extern 是强制的。块内的单个条目可以加 safe 修饰符，表示可以安全调用 — 但那个标注同样是由人承担责任的断言，不是机器核实的结果。

// 概念示例，并非验证过行为的代码。
unsafe extern "C" {
    // 这个签名与头文件是否一致，编译器无从知晓
    fn img_open(path: *const c_char) -> *mut ImgCtx;

    // 加上 safe 后调用处不再需要 unsafe 块。
    // 这不会凭空产生检查，只是表示责任由此处承担。
    safe fn img_version() -> u32;
}

1.2 边界上真正断掉的那些保证

「内存安全被破坏」是一句笼统的话。把它拆成具体从检查集合里掉出去的项目，对策也就跟着分了开。

  • 生命周期 — C 返回的指针能有效到什么时候。是到下一次调用为止，还是上下文存活期间，抑或是静态的，函数签名里都没有。
  • 所有权与释放责任 — 返回的缓冲区该由 Rust 释放，还是要调用专门的释放函数，或者根本不该碰。
  • 可变独占性 — 如果 C 库内部持有同一缓冲区的别名，Rust 这边构造 &mut 的瞬间语言规则就已经被破坏了。优化器会信任那条规则去重排代码。
  • 空值许可、对齐与初始化状态 — 返回的指针会不会是空的，返回的内存有没有被初始化。
  • 线程安全性 — 是否使用全局状态、是否可重入、是否只能在特定线程调用。一旦手写实现 Send 与 Sync，这个判断就完全落在人身上。
  • panic 与栈展开 — Rust 回调穿过 C 栈帧发生 panic 是未定义行为。回调边界上需要捕获并吞掉。
  • ABI 布局 — 漏掉 #[repr(C)] 的结构体传过去，字段排布可能不同。枚举取值范围、位域与填充也属于同一类。
  • 错误约定 — 是返回负值、用 errno，还是调用取最后错误的函数。读错约定就会把失败当成功继续往下走。

这八项里编译器一项也不替你检查。所以 FFI 里的 unsafe 与其说是「这段代码危险」的警告，不如说更接近检查器管辖到此为止的界碑。

2. 此前的应对 - 封装层、绑定生成器与渐进重写

2.1 安全封装：把契约誊写成类型

Rust 生态的标准做法是两层结构。底层放一个只装原始声明的 -sys crate，上层放一个暴露安全接口的 crate。上层用 RAII 把释放责任绑到类型上，用生命周期参数表达有效区间，把空值可能性用 Option 摆到明面。

这套做法确实管用。用上一个做得好的封装层，使用者一次 unsafe 都不用写。风险没有消失，只是被收拢到了一处，而这是缩小审计面的正当策略。

局限在两个地方。封装层正确与否仍然由人来担保，读错契约就会让这份误读披着安全接口的名义扩散出去。而且契约会变 — C 库发个小版本，把行为改成「这个指针从此只在下一次调用之前有效」，封装层照样能编译。

2.2 绑定生成器：誊写失误变少，但契约不在头文件里

bindgen 这类工具解析 C 头文件自动生成声明。手抄时的错别字、整数宽度弄错、结构体字段漏掉，这些都会大幅减少；随平台变化的类型尺寸也会在构建时重新取，因此在交叉编译中格外有用。

但生成器读到的只有头文件，而上一节列的八项里，写在头文件中的几乎没有。char* 到底是以空字符结尾的字符串还是另外接收长度的缓冲区，返回的指针由谁释放，这些都躺在文档里，而不是以可编译的形式存在。生成器给你的是准确的声明，不是安全的接口。

2.3 渐进重写：边界不会消失，只会移动

从叶子模块开始往 Rust 迁移是常见做法，大体上也合理。只是这套策略的账要算准。重写过程中，边界不减反增。原本一个接触点，会变成迁移模块数那么多个，每个接触点都会重新产生前述那八项。

  • 容易迁的模块通常是纯计算代码，本来风险就小。相对于付出的力气，换来的安全性并不多。
  • 真正危险的代码 — 解析器、协议处理、年久失修的状态机 — 契约都在文档之外，恰恰最难迁。
  • 重写要么要求功能冻结，要么就得让两套实现并存一段时间。无论哪种，成本都由组织来出。
  • 重写完成之前不能声称安全。迁走九成，剩下一成还在同一地址空间里，整体就带着那一成的安全性。

2.4 动态检查工具：只看跑过的路径

AddressSanitizer 和 Valgrind 确实能抓到不少东西，但性质不同。它们只在执行过的路径上发现违规，所以覆盖率就等于保证的范围。在发布版里常开代价太大，而 Rust 侧的解释器 Miri 原理上看不到 FFI 的另一侧。

2.5 各种做法的对比

做法真正挡住的挡不住的成本的性质
安全封装（两层结构）调用方误用、漏释放、漏处理空值契约误读、上游库行为变更、C 内部的缺陷前期设计时间 + 跟踪上游的负担
绑定生成器声明错别字、类型宽度弄错、各平台布局差异生命周期、所有权、线程安全性等一切不在头文件里的契约增加构建依赖，需评审生成结果
渐进重写已迁移模块内部的内存错误剩下的 C 代码，以及被增加出来的边界本身长期投入人力，双份维护期
动态检查（ASan 等）在执行过的路径上实际发生的违规没执行到的路径，发布环境特有的问题运行时间增加，构建覆盖率的投入
模糊测试异常输入下暴露的边界违规依赖状态或与时序纠缠的缺陷编写测试桩 + 持续的算力

把表格竖着读，共同点就出来了：没有任何一格能保证「C 那边的代码遵守规则」。它们全都是在边界上防守、把边界挪走，或者事后再发现。

3. Fil-C 瞄准的位置 - 不搬动边界，而是缩小它

思路在这里翻转了一次。与其在边界上防守，不如让边界内侧变安全，边界上要丢的东西自然就少了。Fil-C 站的就是这个位置。

Fil-C 是 Filip Pizlo 基于 Clang 与 LLVM 分叉做出的 C/C++ 编译器，不改源码重新编译一遍，就赋予运行时内存安全。核心有三点。

  • InvisiCaps — 指针表面上像个64位值，实际上被拆成受信任的权能（capability）与不受信任的地址。权能信息存放在另一块区域，每次访问都检查是否越界。
  • 并发垃圾回收器 — 为了从根上消除释放后使用，把生命周期管理交给运行时。
  • 没有逃生口 — 按仓库的说明，Fil-C 里没有任何能关掉保护的 unsafe 关键字。这不是便利性缺失，而是设计上的声明。

违规发生时，程序不会滑向可被利用的状态，而是以 panic 终止。也就是说 Fil-C 改变的不是「缺陷消失了」，而是「缺陷的后果从任意代码执行降到进程终止」。写威胁模型时这个区分至关重要 — 可用性依旧可被攻击，但机密性与完整性守住了。

由此引出与本文主题直接相关的一个性质。Fil-C 源码兼容，但 ABI 有意不兼容，因为指针表示不同。所以它无法与普通编译器产出的目标文件链接，程序及其整个依赖树都必须用 Fil-C 重新编译。在 Fil-C 的术语里，普通 C ABI 被称作 Yolo-C — 而 Rust 的 extern "C" 说的正是这个 Yolo-C。

4. extern fil-c 提案当前处于哪个阶段 - 有什么，还没有什么

2026年8月13日，Domen Kožar 在自己的博客上发表了 I want extern fil-c。主旨可以缩成一句话 — 希望有一个说 Fil-C ABI 的 Rust FFI。

把阶段准确写下来：截至2026年8月16日核对时点，这是一篇个人博客文章，而不是提交到 rust-lang 仓库的 RFC。没有带编号的 RFC，没有跟踪议题，也没有实现分支。文章读起来更像邀约而非规范，结尾提议 Rust、Fil-C、Zig、Nix 几个圈子的人明年在 OceanSprint 聚起来一起做。把 Fil-C 打包成 Nix 交叉编译平台的 filnix 的作者 Mikael Brockman 已经表示参与。

提案为第一版划定的范围是有意收窄的。

  • 标量值、复制过来的字符串与切片、不透明句柄 — 先做这三样。把复杂指针图原样传递的情形一开始就不碰。
  • 生成安全的 Rust 封装。去掉由人誊写契约那一步，正是其目标。
  • 把 C 的整个依赖图都用 Fil-C 编译。局部套用是行不通的。
  • 不留回到普通 unsafe C 的逃生口。按作者的说法，关键在于不要悄悄凿出一个 Yolo 形状的洞。

为什么需要新的 ABI 字符串，到这里也清楚了。extern "…" 里的字符串是挑选调用约定的开关，而 Fil-C 连指针表示都不同，用 extern "C" 根本谈不下去。这不是语法口味问题，而是向另一个世界搭话所需的最小装置。

// 假想语法。并未定案，也未验证过行为。
// 只是把提案的方向作为概念写出来。
extern "fil-c" {
    // Fil-C 那侧的指针带着权能，
    // 因此越界访问会在被调用方以 panic 收场。
    fn parse_config(text: &str) -> Result<ConfigHandle, ParseError>;
}

作者自己承认的难点也很明确：边界才是难的那部分，而且 Fil-C 从设计上就没把与普通 C 的互操作当作目标。Rust 这侧这座桥要做的不只是把函数调起来，而是在搭桥的过程中不损坏 Fil-C 施加于整个程序的那份保证。

5. 代价之一 - 性能、内存，以及数字该怎么读

加上运行时检查和垃圾回收，不可能是免费的。麻烦在于每个被引用的数字条件都不一样，凑成一个数就会误导。把确认过的内容连同条件一起写在下面。

出处与时点条件数值
LWN 文章（2025-10-28）按 Fil-C 文档，一般程序约慢4倍，指针使用越多开销越大
LWN 文章（2025-10-28）含指针的结构体内存占用约为2倍
LWN 文章（2025-10-28）用 Fil-C 构建 bash 5.2.32 并使用感觉不出性能差别
Zig 提案议题（2026-07-20）讨论引入该方式时提到的区间1倍到6倍
extern fil-c 提案文章（2026-08-13）未给出具体基准测试无数值 — 只表述了检查变为静态后开销即消失的方向

照表直读，跨度之大本身就是信息。检查成本与追指针的频率成正比。于是分化如下。

  • 数值计算、信号处理、压缩的内层循环这类以数组下标为主的代码，相对吃亏较少。
  • 链表、树、图遍历这类持续追指针的数据结构，吃亏很大。
  • 进程寿命短、以 I/O 等待为主的工具 — shell、构建脚本、命令行工具 — 可能几乎感觉不出差别。bash 的例子就属于这一类。
  • 内存增长会先影响容器上限与部署密度，而不是吞吐量。每个节点能塞下几个实例会变。
  • 垃圾回收器介入后，变化更大的是尾延迟的分布而非平均延迟。若某条路径有实时要求，这一项要单独量。

所以判断的轴不是「4倍扛不扛得住」，而是「我的热路径上有没有 C」。缩略图生成器里的解码器慢4倍，对大多数服务都不构成问题。同样的倍率落在请求路径正中间，容量规划就得整个重来。

6. 代价之二 - 构建、生态与工具成熟度

在工程上更常绊住人的其实不是性能，而是这一侧。

6.1 必须整体重新编译，这件事的分量

ABI 不同，发行版提供的 .so 就不能直接用。包括 libc 在内的整棵依赖树都得用 Fil-C 构建。这不只是构建耗时的问题，而是供应链构成本身发生变化的问题。包管理器原本提供的安全更新通道，必须由自家的构建流水线来接手。

filnix 的意义正在此处。它把 Fil-C 打包成 Nix 的交叉编译平台，提供可复现的工具链与软件包世界，已经移植了一百多个 nixpkgs 软件包。换句话说，它是先把承接整体重编译这项要求的基础设施搭起来的项目；没有类似的东西，这条路子本身很难走出实验室。

6.2 平台与成熟度

  • 按仓库说明，Fil-C 只在 Linux/x86_64 与 Linux/ARM64 上工作。曾经支持过的 Darwin/ARM64 与 FreeBSD 目前不在目标之列。
  • 没有 Windows 支持。如果是桌面应用或跨平台库，这一行就把它从候选名单里划掉了。
  • 版本号尚未到 1.0；按 LWN 的说法，这是2023年才起步的较新项目，实际上由一个人主导。
  • 许可证分成多层。编译器一侧、运行时一侧，以及基于 musl 或 glibc 的发行物，各自适用不同条款。在公司内推广之前这是需要法务确认的项目。
  • 调试器、性能分析器、核心转储分析与静态分析器对新指针表示的理解程度，需要另行确认。故障时读不出调用栈，安全性的收益就被抵消了一部分。

归结起来，这套做法的门槛不在代码，而集中在构建基础设施与运维工具上。已经自建容器镜像、并且备有可复现工具链的团队离它很近；依赖厂商提供二进制的团队离它很远。

7. Zig 也在往同一个方向走 - 这不是一个人的想法

同样的思路在另一门语言里也冒出来，这件事本身就是信息。2026年7月20日，Zig 的 Andrew Kelley 提出了一个受 Fil-C 启发的完全内存安全编译模式。议题上挂着 accepted 标签和后续里程碑，但尚未实现。这里同样要把时点和状态放在一起读。

  • 保留现有的优化模式，另外新增一个名为 fil 的可选 ABI。
  • 计划在 Zig 编译器中独立实现 Invisicaps 方式以及系统调用包装。
  • 从 x86_64-linux 起步，再逐步扩展到其他平台。
  • 明确打出与 Rust 的对照 — 不留 unsafe 逃生口，并且覆盖整棵 C/C++ 依赖树。
  • Fil-C 的作者也参与了议题讨论，正在处理分配器接口与架构兼容性之类的技术争点。

把两份提案并排放，共同结构就显出来了：两边切分问题的方式都不是「用安全语言重写」，而是「把不安全的那一侧变安全，从而消掉边界」。而且两边都还停在提案阶段。哪一个都不是今天就能在生产环境打开的开关。

8. 该怎么选 - 按条件的判定表

这些选项彼此并不排斥。同一个组织内部对不同代码给出不同答案，才是常态。下面这张表不替你做决定，只是理清应该先看哪个轴。

常见问题（FAQ）

extern fil-c 已经进入 Rust 了吗？

没有。截至2026年8月16日，它是一篇个人博客文章提出的设想，既无编号 RFC，也无跟踪议题和实现。文章以邀请大家明年在冲刺活动上一起做作结，这本身就说明了它的性质。它今天给出的实质不是特性，而是一种切分问题的方法。

只要认真使用 unsafe 块，FFI 不就安全了吗？

unsafe 不是让检查通过的关键字，而是声明由人来代替编译器做检查。返回指针的生命周期、释放责任、线程安全性都不在头文件里，编译器看不到。所谓用好，意思是你正确读懂了契约并把它搬进封装层；一旦上游发版改了契约，这份誊写就会在照样能编译的情况下变错。

用 Fil-C 编译会损失多少性能？

视条件而定。文档口径的约4倍常被引用，但同一篇文章里 bash 感觉不出差别，Zig 一侧的讨论提到的是1倍到6倍。原因在于检查成本与追指针的频率成正比。在自己的负载上量过之前，没有哪个单一数字是诚实的。

为什么不能直接用 extern C 而要新增 ABI 字符串？

Fil-C 源码兼容但 ABI 有意不兼容，因为指针是权能与地址分离的表示。Rust 的 extern "C" 说的是普通 C ABI，在 Fil-C 术语里叫 Yolo-C。两个世界无法用同一个字符串对话，所以需要另一个字符串。

眼下在工程上能做什么？

有三件事无论提案是否被采纳都有收益：把项目的 FFI 边界列成清单；把每个边界函数的契约（生命周期、释放责任、线程安全性、是否允许空值）明确写进封装层注释；给不可信输入能抵达的边界挂上模糊测试。无论最终选择哪条转型路径，这三样都会成为它的输入。

结语：即便不被采纳，也仍会留下的东西

extern "fil-c" 最终会不会真的进入 Rust，无从知晓。单看概率，从个人博客起头的想法成为语言特性的例子并不多。它依然有价值，因为它把问题重新定义了一遍。

此前关于 FFI 安全性的讨论，大体都在问「在边界上要防得多好」。更好的封装层、更聪明的生成器、更细密的检查工具 — 全都必要，也全都共享同一个前提：另一侧反正信不过。这份提案戳的就是那个前提。

缩到今天真正能用的部分，有三件。

  • 数一数自己项目里的 FFI 边界。不知道有几条、每条各自预设了什么契约，任何选项都无从比较。
  • 逐条边界写下违规的后果。是任意代码执行还是进程终止，会彻底改变应对的优先级。
  • 保持把提案阶段与采纳阶段分开读的习惯。这个领域常出有意思的想法，其中相当一部分会长久停留在想法状态。

这不是判语言优劣的问题。C 积累了四十年经过检验的实现，Rust 有在编译期就被核实的规则。只要两份资产还共处同一个地址空间，边界就存在，而如何对待那条边界，才是工程上要回答的问题。提案被采纳与否，这个问题都还在。
