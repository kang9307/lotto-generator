把10台服务器的p99平均了 - 那个数字什么都不是

百分位数无法合并。用固定随机种子可复现的计算，检验聚合错误与采集设计

2026-07-30 开发/基础设施

引言: 面板一切正常，用户却说很慢

响应时间面板上有一条p99曲线。整整一个月都平稳在90毫秒左右。可是工单在增加。页面经常卡住，点了支付按钮要转很久。自己去翻访问日志，超过400毫秒的请求一抓一大把。面板为什么没有把它们显示出来？

常见的回答是「p99本来就丢掉百分之一」。这话没错，但不是这次的原因。真正的原因更简单也更糟。屏幕上那个90毫秒，压根就不是p99。它是10台服务器各自算出来的10个p99值取的平均。而百分位数并不是能靠取平均来合并的那类数字。

本文用数字把这个差距摆出来。同样的10万条请求用两种方式做了汇总。先算每台服务器的p99再取平均，得到91.04毫秒；把全部请求倒进一个桶里再算p99，得到449.63毫秒。相差4.94倍。两个数字都顶着p99这个名字，也都不是程序出错的产物。两边都严格执行了各自被要求的运算。

更麻烦的是这个错误很安静。屏幕上的值看着合理，单位也对，流量上来它会跟着上来，上线出问题它也会跟着变差。方向大体是对的，所以没有任何契机让人起疑。而且被错误合并的百分位数不会抛异常。编码错了会显示成乱码让你看见，聚合错了的数字看起来就只是个数字。

在实际工作中，这个问题通常先以下面四种症状出现。

  • 面板上的p99一直平稳，可工单和日志里的慢请求条数却一起上涨
  • 把同一时间段按服务器拆开看，有一台明显很差，但在全局曲线上那个尖峰消失了
  • 在面板上换一个分组维度（按主机 → 按地域 → 全部），「同一个p99」变成了另一个值
  • 按分钟的p99曲线上有尖锐的峰，而同一屏上标着「本小时p99」的那个数字却风平浪静

后面两条是决定性线索，第12节和第9节会用计算说明原因。先把结论写在前面：百分位数不是一个值，而是分布的性质，而性质无法取平均。所以真正该问的不是「看p99还是看p95」，而是你当初采集了什么。采集设计决定指标精度。

用别的方式折叠这同样的10个数字，就更有意思了。

  • 用最大值折叠得到1020.21毫秒 - 比真值高386.57%。严重高估，但它一次也没有掉到真值下面。第12节会说明这不是巧合
  • 用中位数折叠得到40.59毫秒 - 低了80.64%。那台坏机器被彻底抹掉了。对离群点稳健这个通常令人满意的性质，在这里恰好反向起作用
  • 用最小值折叠得到39.90毫秒 - 是个下界。没什么用，但方向是诚实的
  • 用平均折叠得到138.51毫秒 - 既不是上界也不是下界，而且它不指向任何一条请求。10万条里也许确实有耗时138.51毫秒的请求，但那跟这个值为什么出现毫无关系
  • 这10个数字怎么折叠都得不到209.67。那份信息在每台服务器做汇总的那一刻就已经被丢掉了

百分位数聚合的核心到这里就显出来了。要正确算出整体p99，必须知道每台服务器在整体前1%里所占的份额。这个份额跟流量份额毫无关系（10%对100%）。而一旦每台服务器只留下一个p99数字，计算这个份额的原料也随之消失。被丢掉的不是精度，而是结构。

那么这个错误为什么能长期存活？只改一个条件，答案就出来了。把10台服务器都设成同一个分布，流量也均匀分配。

per-server p99 values : 128.99, 126.51, 125.63, 129.69, 118.68, 129.06, 132.86, 123.23, 129.23, 131.61
MEAN of them          :   127.55 ms
TRUE pooled p99       :   127.59 ms
deviation             :    -0.03 %

取平均的p99是127.55毫秒，真正的p99是127.59毫秒。误差0.03%。实际上就是对的。

这就是它不被发现的原因。平时是对的。只要集群是同质的、负载均衡分得均匀，这两个数字就贴在一起。而它们分道扬镳的时刻，正是某台机器掉队的时刻，也就是最需要这个指标的时刻。

  • 正常时准确、异常时出错的指标，没法用来发现异常 - 尽管这是指标唯一的用途
  • 验证也很难。平时把两个值一比，是一致的，于是得出「查过了，没问题」的结论。只在健康状态下做的验证，这个缺陷一定能通过
  • 误差的大小与同质性被破坏的程度成正比。而同质性被破坏本身，就是我们要找的那个事件。这是信号变强时仪表跟着坏掉的结构

3. 最大值可以合并 - p100与p99的决定性差别

这里可能有一个反问：最大值不就是第100百分位吗？它也不能合并？算一下，答案就分开了。而这个分岔是本文最重要的概念节点。

per-group max : 402.68, 409.36, 451.85, 627.13, 577.14, 699.29, 517.51, 531.50, 1107.77, 729.08

MEAN of per-group max :   605.3333 ms
MAX  of per-group max :  1107.7706 ms
TRUE max of pooled    :  1107.7706 ms
mean equals truth     : False   (off by -45.36 %)
max-of-max equals truth: True
min-of-min equals truth: True

各组最大值取平均是605.33毫秒，真正的最大值是1107.77毫秒，低估45.36% - 平均在这里同样是错的。但把各组最大值再取最大值，就完全一致：小数点后四位都一样，用浮点比较也是True。最小值同理。

差别不在名字，而在运算的性质。最大值有一条从部分构建整体的折叠规则：两个集合并集的最大值，恒等于各集合最大值的最大值。p99没有这样的规则。不存在一个函数，能仅凭各集合的p99算出并集的p99。这不是说近似得不好，而是说这个函数不存在。

  • 最大值之所以可折叠，是因为每个部分的最大值已经携带了关于该部分所需的全部信息。能成为整体最大值的候选只有各部分的最大值，其余的值本来就不是候选
  • p99不是这样。会成为整体p99的那个值，可能位于某个部分内部的任何位置。第1节里真正的p99是209.67，它既不是web-10的p99（1020.21），也不是其他机器的p99（约40）。它落在web-10中间的某处
  • 所以「p100可以而p99不行」是成立的。p100不是百分位数家族里的极端成员，而是另一类统计量，名字相似正是误解的来源
  • 这有实际含义。基于最大值的指标，按任何粒度聚合都是安全的 - 最慢的请求、最长的队列、最大并发。你不需要怀疑它的计算路径。代价是它完全被一条请求左右，噪声很大。安全和有用是两回事

4. 能合并的指标与不能合并的指标

现在逐个指标来验。取6个分组，故意让大小各不相同（从3000到7500）。大小相同的话，简单平均和加权平均会碰巧相等，区别就看不出来了。另外，为了不让浮点舍入把「完全相等」这个判定弄模糊，先把数值转成整数微秒再计算。

表的最后一列就是本节的要点。计数、求和、最大、最小仅凭部分结果就能完全还原，那里的True是整数相等而不是近似。平均是有条件的：简单平均偏差11.2681%，按计数加权则完全相等。p99和p50用任何方式都还原不了。

整理如下。

指标从部分折叠的方法是否精确要合并需要有什么
计数各部分计数之和精确计数。它本身就是完整的
求和各部分和之和精确和。加法满足结合律
最大各部分最大值的最大精确一个最大值
最小各部分最小值的最小精确一个最小值
平均各部分平均的简单平均错误-- 分组大小不同就会偏
平均各部分平均按计数加权精确和与计数。只留平均是不够的
方差、标准差由计数、和、平方和重算有条件精确三个都存下来就能还原
中位数(p50)没有折叠规则不可能原始数据或直方图
p95、p99没有折叠规则不可能原始数据或直方图

方差那两行是这张表里最有教益的。只存标准差就无法合并，存下计数、和、平方和三个值则能精确还原。同一个指标，会因为你存了什么而变成可合并或不可合并。这个性质正是第10节直方图方案的依据。

  • 「能不能合并」不是指标的属性，而是你所保存的那份汇总的属性。这一点直通本文的实践结论
  • 没有一起保存计数的平均是合不起来的。如果面板只留平均、丢掉计数，连平均都合不起来。而如表所示，这种情况的误差在11%量级，小到不容易被察觉
  • 百分位数无论额外保存什么辅助数字都还原不了。例外只有近似分布本身的那类汇总（分桶直方图之类），而那是一个结构，不是一个数字
  • 反过来读就是采集设计的规则。以后需要换粒度重算的指标，必须以可折叠的形式保存。存成不可折叠的形式，之后所有的重新聚合都是错的
  • 表里标着「不可能」的两行，偏偏是面板上使用频率最高的两个指标。这就是这个问题的规模

真正的p99是413.37毫秒。简单平均高116.40%，请求数加权低32.70%，平方根加权高26.04%。没有一个是对的，也没有一个是稳定地朝同一方向偏的。

请注意，按「请求数的0.01倍」加权的那一行，跟请求数加权得到了完全相同的值。把所有权重乘上一个常数，加权平均不会改变。也就是说，任何从请求数推导出来的权重，给出的答案都和请求数加权一样。因为没有新的信息进来。这就是「调权重」这条路撞墙的地方。

那么正确的权重是什么？正确的权重是每个分组在整体前1%中所占的份额。这个值被直接取了出来。

group  share of traffic   share of the pooled top 1 percent
------------------------------------------------------------------------------
a               60.00 %                         0.00 %
b               25.00 %                         0.00 %
c               10.00 %                        42.86 %
d                5.00 %                        57.14 %
------------------------------------------------------------------------------

占据85%流量的分组a和b，对尾部的贡献是0%。造出尾巴的是只占15%流量的c和d。也就是说，正确的权重向量接近(0, 0, 0.4286, 0.5714)，而请求数权重是(0.6, 0.25, 0.1, 0.05)。这两个向量实际上指向相反的方向。

  • 正确的权重是各分组对尾部的贡献度，而这个值只有看原始数据才能得到。在只留下各服务器p99的那一刻，这份信息已经不在了
  • 所以这不是选权重的问题。这是在试图表达加权平均这个形式根本无法表达的值。是表达能力不够，不是系数没调好
  • 流量份额与尾部份额无关，这是实践上的核心。「接得多的服务器更重要」这条直觉在尾部不成立。安静的节点独自造出整条尾巴，是很常见的情况
  • 加权平均也有碰巧接近的时候（第2节情形A的10.11%）。但即便如此，要确认它确实接近，唯一的办法还是看原始数据。无法核对的近似不是近似，是猜测

6. 平均掩盖了什么 - 只用一节

使用百分位数的理由本身只做简短确认，因为那不是本文的主题。这里构造了平均响应时间几乎相同的两个分布。

shape                     mean      p50      p90      p99     p999      max
------------------------------------------------------------------------------
A near-normal             40.00    40.01    47.68    53.92    58.41    66.46
B long tail               39.85    24.36    46.17   473.97  1670.75  6766.82
------------------------------------------------------------------------------
means differ by 0.38 %, but p99 differs by 8.79 x and p999 by 28.60 x.

平均是40.00和39.85，相差0.38%。p99是53.92和473.97，相差8.79倍，p99.9相差28.60倍。两个服务的「平均响应时间」报告实际上会是同一份文档，而用户体验截然不同。

  • 平均有用，是在分布像A那样对称的时候。真实的响应时间大多更接近B。这就是尾部指标存在的理由
  • B的中位数(24.36)低于它的平均(39.85)。在长尾分布里，平均比大多数用户看到的还要差，于是「比平均更快的用户」成了多数派。平均谁也代表不了
  • 这一节到此为止。平均与尾部的关系本身是另一个主题，而本文的论点是在决定使用尾部指标之后，该如何合并它。第6节和第7节各占一节，不再展开

7. 百分位数的定义不止一种 - 只用一节

在跨工具比较数字之前，还有一件事要确认。「p95」这一个名字下面藏着好几种计算规则。这里把多种规则作用在一个n=20的小样本上。

同样的20个数字，p95从1200到2910都有，相差2.42倍。再看最后一行。排他式(exclusive)方法的p99是4422毫秒，而这个样本的最大值是3000毫秒。它返回了一个比任何观测值都大的数。

这不是bug。Python标准库文档写明该方法针对的是「可能拥有比样本中所见更极端的值的总体」，并且下侧切点按i / (m + 1)计算。它是按规格工作的。而我自己实现的那版在最大值处做了截断，所以两者在p95上一致，到p99才分开。同一个名字，两个答案。

  • 跨工具比较数字时，先把定义对齐再比。各工具的默认定义可能不同，先查各自的文档。本文不对任何具体产品的内部实现下断言
  • 定义差异只在样本小的时候才成为问题。每分钟只有几十条请求的低流量端点就是危险区间，第8节讲的就是这个
  • 定义差异不是本文这些4到5倍误差的原因。把两个问题混在一起就会错过真正的原因。数字差得离谱时，先查聚合路径，再去翻定义
  • 这一节也到此为止。逐一深挖各定义的特点是另一个主题

8. 样本一小，p99就是最大值的别名

撇开聚合不谈，如果一个窗口里的请求数本身就少，p99也是不稳定的。这里从同一个总体出发，只改变样本量反复计算。因为是对数正态分布，真p99可以解析地算出来，于是能对照估计值到底在瞄准哪里。

population: lognormal, median 20.0 ms, sigma 0.80
analytic population p99 = median * exp(sigma * 2.3263478740408408) = 128.6133 ms

     n   trials      p5   median      p95     min      max   p95/p5   which rank is used
------------------------------------------------------------------------------
   100     2000   75.89   109.77   166.90   53.84   300.51    2.199   rank 99 of 100 (1 above it)
  1000     2000  109.97   126.51   148.66   94.90   176.01    1.352   rank 990 of 1000 (10 above it)

100000      100  126.87   128.62   130.55  125.97   131.80    1.029   rank 99000 of 100000 (1000 above it)
------------------------------------------------------------------------------

a single n=100 window, its top 5 values : 63.23, 63.43, 67.21, 75.07, 80.44
nearest-rank p99 of it                 : 75.07 ms   (the 99th of 100, i.e. 2nd largest)
drop that one request and p99 becomes  : 80.44 ms

总体的真p99是128.6133毫秒。从100个样本估出的p99，下5%分位是75.89，上5%分位是166.90 - 2.199倍的跨度在晃。2000次里最小出到53.84，最大出到300.51。到10万个样本时，这个跨度收窄到1.029倍。

为什么晃得这么厉害，最右边那一列给出了答案。100个样本的p99是第99个值，在它上面的请求只有一条。这里打开了一个真实窗口来看。前5个是63.23、63.43、67.21、75.07、80.44，而p99是75.07。把那一条请求拿掉，p99就变成80.44。

  • 100个样本的p99实际上就是「第二慢的那条请求」。百分位数这个名字并不保证统计上的稳定性
  • 所以低流量端点的p99告警会被一条请求带着晃。把窗口拉宽，或者改用更低的分位数(p90、p95)才是诚实的做法。只有100条请求却盯着p99，跟盯着最大值然后管它叫p99差不多
  • 拉宽窗口和把各窗口的p99合并起来是两回事。后者按第9节所示是不成立的。要拉宽窗口，就得跨着更宽的窗口从原始数据重算
  • 不标出样本量的百分位数曲线是没法读的。把分母一起画出来。请求量骤降那一段的p99波动，可能是样本不足而不是性能变化

9. 时间轴也一样 - 60个1分钟p99拼不出1小时p99

到目前为止的分组轴是主机。换成时间，结果一样。每分钟1200条共60分钟，合计72000条。在中间的5分钟插入了一段性能劣化。这是照着真实故障的形状做的。

这就是引言里最后一条症状的真相。按分钟曲线上的那些峰，和标着「本小时p99」的那一个数字，是两个不同的量，任何一个都算不出另一个。两个数字不一致，也不意味着其中哪一个是bug。

  • 时间轴并不会让百分位数变得可加。把12个5分钟p99拼成1小时，或把24个小时p99拼成一天，都是同一个错误
  • 在面板上改变时间范围时，要确认数字是怎么算的。会按图表横向像素数自动重新分桶的工具，正是在这里可能悄悄重新聚合。如果缩放会改变数值，那就是信号
  • 把告警阈值定在1分钟窗口，而周报用1小时窗口写，那么这两个数字无法互相验证。告警响了而报表风平浪静，可能是完全正常的行为
  • 用中位数折叠得到68.07毫秒。劣化的那5分钟被其余55分钟埋掉，彻底消失了。尾部事件在主机轴和时间轴上被稀释的方式完全一样

10. 直方图 - 一种真能合并的近似

那么就必须永远抱着10万条原始数据吗？有替代方案，而它的依据第4节里已经有了。计数可以合并。把数值切成区间（桶），保存每个桶的计数，那些计数就能在服务器之间相加。下面把它用在与第2节情形A相同的集群上。

改变桶边界反复计算。7个桶的粗糙方案高12.11%，15个2的幂次方案高9.16%，每档增长10%的112个桶只差0.25%，10毫秒间隔的399个桶只差0.03%。同一份数据上，各服务器p99取平均错了79.68%。连最粗糙的直方图都比p99取平均准确六倍以上。

造成差别的不是公式，而是顺序。直方图方案在求任何百分位数之前先把计数加了起来。各服务器p99方案则在每台机器上先把百分位数求掉了。全部区别就在这个顺序上。这也是本文的实践结论：把合并这一步放在汇总之前。

不过这终究是近似，误差的性质需要确认。

  linear10     true 438.68 and est 438.82 both inside [430.00, 440.00] : True   abs error 0.1410 ms, bucket width 10.0000 ms

装着答案的那个桶（256到512毫秒）里有2185条。如果均匀分布，应该有一半落在中点384毫秒以下，而实际上72.72%落在下面。也就是说这个桶里的值挤在低的一侧，所以基于均匀假设的插值读高了。

这里不下断言。上面的72.72%和误差的符号，是在这个分布和这组桶边界下观测到的。换一种分布形状或换一组边界，符号可能反过来。请不要从这一次运行里提炼出「直方图插值总是读高」这类通用规则。想知道自己那边误差的方向，就得用自己的数据和自己的桶边界做同样的检查。

同理，本文也不对任何具体监控产品如何从直方图估计分位数下断言。插值方式和桶的定义在不同实现之间可能不同。请查阅你所用工具的文档。本节展示的是方法的性质，而不是哪个产品做了什么。

但运行确实立住了一个形状清楚的边界条件。估计值会停留在包含真实秩的那个桶之内，真值也在同一个桶里。因此误差的绝对值不会超过该桶的宽度。四种方案全部得到验证：粗糙方案误差53.1056毫秒对应桶宽400毫秒，最细方案误差0.1410毫秒对应桶宽10毫秒。

  • 减小误差的办法是把关心区间的桶做细。这比改插值方式更确定、更可预测
  • 哪个区间需要细，必须事先决定。这里p99落在400毫秒量级，所以那个区间重要。桶边界要设计成覆盖预期的延迟范围。事后再改边界，历史数据就没法比较了
  • 一旦有值落进最后一个桶（超出上限），那个点上的百分位数就算不出来了。上限要留得宽裕 - 放到超时值之上是稳妥的做法
  • 直方图的存储成本是桶数乘以序列数。精度与成本直接互换。日志与链路追踪本身的存储成本，在ClickHouse可观测性那篇里讲过
  • 除直方图之外，还有若干种用于近似分位数的汇总数据结构，误差保证的形式各不相同。最重要的共同点只有一个：它们都带有把各部分合并起来的运算，而一个百分位数字没有

11. 用户遇到的不是请求，而是一屏页面

就算把请求的p99算准了，还剩一层。用户不是只发一个请求。一屏页面会打出好几个请求。跳过这一层，就无法解释「p99改善了为什么投诉没变」。

把同样的10万条分别归成10组、5组、2组、1组，每次求「各组p99的平均」。结果从128.39变到159.47、190.62、198.82。晃了1.55倍。数据一条都没变，变的只是归组方式。

与之相对，求和、计数、最大值在四种情况下完全相同，固定在2.67、100000、50869.28。这个对比就是诊断的全部。换分组维度会动的数字是被错误折叠的，不会动的数字是算对了的。

最大值那一列也动了（从916.06到634.13、340.29、198.82），但方向只有一个，而且一次也没有落到真值下面。这是不是巧合，也验了。

the max column moved too, but only downward, and it never went below the
truth. that is not a coincidence. checking the bounds over 400 random

  trials                                   : 400
  times pooled p99 exceeded max of group p99: 0
  times pooled p99 fell below min of group p99: 0
  worst overshoot above the max bound       : +0.000000 %
  worst undershoot below the min bound      : +0.000000 %

counting argument behind it: each group has at most 1 percent of its own
requests above its own p99, so at most 1 percent of the pooled requests
sit above the largest of those values. that makes max of group p99 an
upper bound for the pooled p99, and min a lower bound. it is not the
answer, but it is a bound, which a mean is not.

so if per-group percentiles are all you have, fold with max, not mean.
the bound tightens as groups get coarser; it is loosest when cardinality
is highest, which is exactly when dashboards slice most finely.

在400个随机集群配置中，真p99超过各组p99最大值的次数是0次，落到它们最小值以下的次数也是0次。原因可以用计数论证给出：每个分组在自己p99之上最多只有自己请求的1%，因此在这些值中最大的那个之上，最多只有整体请求的1%。所以它是整体p99的上界，最小值同理成为下界。

在实践中，当只剩下各服务器的百分位数时，这就是最好的选择。用最大值折叠，不要用平均。它不是答案，但它是一个界，而界可以支撑「最坏也不过如此」这样的判断。平均既不是上界也不是下界，因此支撑不了任何判断。而且这个界会随着分组变粗而收紧，也就是说在基数高的时候最松，而面板恰恰在那时切得最细。

  • 时间范围检查抓的是第9节那个错误。缩放会改变p99的话，就怀疑重新聚合

  • 就算确认了算式没问题，第8节和第11节依然存在。算对了的p99在样本小的时候照样晃，而且它和用户在一屏上的体感是两个量

  • [ ] 保存错误率时分子与分母分开保存

# 百分位数聚合检查 - 可合并性判断表与复现代码

> 来源: braindetox.kr - 把10台服务器的p99平均了
> 依据: Windows 10 / Python 3.13.3 标准库，固定种子20260730 实测验证
> 把这个文件原样粘贴给AI，然后说「按这些标准检查我们的面板和采集设计」即可。
> 数据全部是虚构的，不是真实服务的指标。

## 0. 一句话总结

百分位数不是一个值，而是**分布的性质**。性质无法取平均。
要合并就需要**原始数据或可合并的汇总（直方图）**。
**把合并这一步放在汇总之前。**

## 1. 可合并性判断表

| 指标 | 从部分折叠的方法 | 是否精确 | 要合并需要有什么 |
|---|---|---|---|
| 计数 | 各部分计数之和 | 精确 | 计数 |
| 求和 | 各部分和之和 | 精确 | 和 |
| 最大 | 各部分最大值的最大 | 精确 | 最大值 |
| 最小 | 各部分最小值的最小 | 精确 | 最小值 |
| 平均 | 各部分平均的简单平均 | **错误** | - |
| 平均 | 各部分平均按计数加权 | 精确 | **和与计数** |
| 方差、标准差 | 由计数、和、平方和重算 | 有条件精确 | 三个都要 |
| 中位数 p50 | 没有折叠规则 | **不可能** | 原始数据或直方图 |
| p90、p95、p99 | 没有折叠规则 | **不可能** | 原始数据或直方图 |
| 错误率 | 比值之间取平均 | **错误** | **分子与分母分开** |

「能不能合并」不是指标的属性，而是**你所保存的那份汇总的属性**。

## 2. 绝对不能做的聚合

- 把各服务器p99取平均（观测误差 -33.94 % ~ -79.75 %）
- 把各服务器p99按请求数加权平均（符号会翻转: -36.99 % / -10.11 %）
- 把60个1分钟p99取平均当作小时p99（-36.98 %）
- 把60个1分钟p99取最大当作小时p99（+570.19 %）
- 对比值（错误率、成功率）取平均
- 对各部分最大值取平均（-45.36 %）

## 4. 复现代码（Python 3.13，仅标准库）

```python
import math, random

def p99(xs):
    s = sorted(xs)
    return s[math.ceil(0.99 * len(s)) - 1]      # nearest-rank

def nrm(rng, _s=[None]):                        # Box-Muller
    if _s[0] is not None:
        v = _s[0]; _s[0] = None; return v
    u1 = rng.random() or 1e-12
    u2 = rng.random()
    r = math.sqrt(-2.0 * math.log(u1))
    _s[0] = r * math.sin(2 * math.pi * u2)
    return r * math.cos(2 * math.pi * u2)

rng = random.Random(20260730 + 1)               # 第1节的种子

def ln(med, sig, n):
    return [math.exp(math.log(med) + sig * nrm(rng)) for _ in range(n)]

groups = [ln(18.0, 0.35, 10000) for _ in range(9)] + [ln(30.0, 1.50, 10000)]
per  = [p99(g) for g in groups]
pool = [v for g in groups for v in g]

print('mean of per-server p99 :', round(sum(per) / len(per), 2))   # 138.51
print('true pooled p99        :', round(p99(pool), 2))             # 209.67
print('max of per-server p99  :', round(max(per), 2))              # 1020.21 (上界)
```

三个数字原样出现就说明复现成功。

## 5. 面板检查流程

| 检查 | 做什么 | 被错误合并的迹象 |
|---|---|---|
| 换分组维度 | 按主机 → 按地域 → 全局 | **数字会动** |
| 换时间范围 | 1小时 → 6小时 → 1天 | 越拉宽p99越**低** |
| 数超阈值条数 | 在日志里数超过p99值的请求数 | 比整体的1 %**多得多** |
| 上界检查 | 比较各服务器p99的最大值与全局p99 | 全局**大于那个最大值** |
| 单节点对照 | 比较最差节点的p99与全局p99 | 全局**低得多** |

**超阈值计数检查最强。**如果p99是X，按定义就有整体的1 %超过X。

## 6. 采集设计规则

- 延迟要**以直方图采集，而不是百分位数**
- 直方图的桶要覆盖**预期延迟范围以及超时值之上**
- 把关心区间（当前p99附近）的桶做**细** — 比改插值方式更确定
- 保存平均时**连同和与计数一起**保存
- 保存错误率时**分子与分母分开**保存
- 保存标准差时保存**计数、和、平方和**
- 不要把百分位数值存成时间序列而丢掉原始数据或直方图
- 在百分位数曲线上**同时标出请求数（分母）**
- 低流量端点采用更宽的窗口或**更低的分位数**
- **页面与事务级延迟**与请求级分开测量
- 跨工具比较数字之前**对齐百分位数定义**（各工具可能不同）

## 7. 改不了时的次优解

如果只剩各服务器的百分位数，就**用最大值折叠，不要用平均。**

- 在400个随机集群配置中，真p99超过各组p99**最大值的次数为0**
- 落到它们最小值以下的次数也是**0**
- 依据: 每个分组在自己p99之上最多只有自己请求的1 % → 在这些值的最大者之上最多只有整体的1 % → 上界
- 界可以支撑「最坏也不过如此」的判断，而平均既不是上界也不是下界
- 界会随分组变粗而收紧。**在基数高的时候最松**

## 8. 把百分位数算对之后仍然存在的两个问题

- **样本不足**: 100条请求窗口的p99实际上就是第二慢的那条请求。2000次重复中估计值在53.84 ~ 300.51 ms之间晃动（真值128.61 ms）
- **页面级体感**: 一屏打出k个请求时，至少含一个慢请求的概率是 1 - 0.99^k。k=20时为18.21 %，k=69时超过50 %。20个请求的页面串行p99是2552.58 ms（请求级p99是435.58 ms）

## 9. 不该做的事

- 把百分位数取平均
- 加上权重然后宣称「修好了」
- 只在正常状态下验证指标
- 丢掉原始数据或直方图而只留百分位数值
- 把100条请求窗口的p99当作告警阈值
- 遇到大误差先去翻定义（定义差异大多在0.02 %量级）
- 看一次就把直方图误差的符号推广成通则（取决于分布和边界）
- 只改善请求p99而不检查每屏请求数
