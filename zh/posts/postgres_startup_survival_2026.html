创业公司的Postgres生存指南 - 从连接耗尽到分区

连接池、索引、autovacuum、零停机迁移、备份演练 - 梳理团队在实务中真正会撞上的坑与应对方法

2026-07-24 开发/基础设施

引言: 为什么Postgres总能一再让创业公司措手不及

创业公司的数据库通常不会一次性垮掉。早期一台Postgres往往能撑上几个月,甚至一两年都相安无事。一旦流量越过某个门槛,情况就变了。部署刚结束连接数就骤然见底,昨天还好好的查询今天突然要跑五秒,凌晨autovacuum把CPU全占满,改一个列的迁移直接把整个服务停掉。每一种情况第一次遇到时都很难判断原因,大多数团队都是事后才意识到「这本该提前知道」。

本文是一份按实务顺序梳理这些坑的生存指南。不是新闻或产品介绍,而是实际运维Postgres时会撞上的问题 - 连接耗尽、索引、N+1查询、autovacuum与膨胀、锁与零停机迁移、备份与恢复、监控、扩容顺序、托管与自托管的取舍 - 一路讲到概念和具体命令层面。为保证准确性,本文交叉核对了官方文档与实务参考资料,内容截至2026年7月。

1. 连接耗尽 - PgBouncer与连接池

创业公司最先撞上的坑通常是连接耗尽。Postgres默认的max_connections在100左右,一旦后端跑在多个实例上,或者在无服务器、自动伸缩环境下每个实例各自维护连接池,这个数字很快就会耗尽。每一个连接在Postgres一侧都要开一个专属进程,连接数越多,上下文切换和内存压力也随之上升。

1.1 为什么光靠应用层连接池不够

ORM或驱动自带的连接池只按单个实例计算。若有10个实例、每个连接池大小设为20,数据库端瞬间就可能承受多达200个连接。再加上批处理任务、管理后台、监控代理,超过max_connections只是时间问题。应用重启或部署时连接一齐涌入的「连接风暴」也是常见的故障模式。

1.2 用PgBouncer在前端过滤

最经过验证的做法是在应用与Postgres之间放置PgBouncer这类连接池组件,把应用看到的连接数与实际数据库连接数解耦。使用事务模式(pool_mode = transaction)时,连接只在一次事务期间被短暂占用,用完立即归还,因此少得多的数据库连接就能支撑更多应用连接。

[databases]
mydb = host=127.0.0.1 port=5432 dbname=mydb

[pgbouncer]
listen_port = 6432
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 20
reserve_pool_size = 5

1.3 事务模式的陷阱

事务模式会在每次事务结束时把连接重新分配给别的客户端,因此与假定会话状态一直存在的代码会发生冲突。未包裹在事务中的SET语句、会话级prepared statement、advisory lock这类默认「这个连接一直只归我用」的功能,在事务模式下会出现意外行为。如果代码里用到这些功能,应把这部分单独切到会话模式,或者改写代码以适配事务模式。连接池大小不宜随意加大,应以数据库服务器的CPU核数为基准,并结合客户端等待时间(cl_waiting、平均等待时间)指标持续调整。

2. 索引的缺失与过度 - 如何找到平衡

索引是创业公司最常走两个极端的领域: 要么完全不建,要么习惯性地给每一列都建。

2.1 没有索引会发生什么

如果WHERE、JOIN、ORDER BY中常用的列缺少索引,优化器就会选择扫描整张表的顺序扫描(Seq Scan)。数据量小时感觉不出来,但表一旦涨到几十万到几百万行,同样的查询会突然变成要花几秒。这种变化是随流量增长慢慢发生的,所以感觉像是「某一天突然变慢了」,实际上只是表越过了临界点。

2.2 索引过多的代价

反过来,如果索引建得太多,每次INSERT、UPDATE、DELETE都要连带更新相关索引,写入延迟增加,存储占用也随之增加。尤其是那些「以防万一」建的索引,常常实际从未被用到过。可以通过pg_stat_user_indexes的idx_scan列确认实际使用频率,把未被使用的索引清理掉。

SELECT relname AS table_name, indexrelname AS index_name, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY relname;

2.3 复合索引的设计原则

如果很多查询同时按多个列过滤,一个复合(多列)索引往往比建多个单列索引更高效。这里列的顺序很关键: 用于等值(=)条件的列放前面,用于范围(>、BETWEEN)条件或排序的列放后面。对生产环境中的表新建索引时,务必使用CREATE INDEX CONCURRENTLY,避免锁表。

3. N+1与慢查询 - 用EXPLAIN和pg_stat_statements揪出来

即便连接和索引都处理好了,应用代码层面的N+1查询依然是一个独立的问题。

3.1 如何发现N+1查询

N+1是指先取出一个列表,再对每一项分别发一次查询去取相关数据的模式,使用ORM时尤其常见。这个问题光看日志很难察觉,因为每条查询本身很快,往往不到1毫秒。但用pg_stat_statements一看,就会清楚看到同一模式的查询在短时间内被调用了成千上万次。「查询很快,但调用次数异常高」正是N+1的信号。

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY calls DESC
LIMIT 20;

3.2 如何读懂EXPLAIN ANALYZE

找到慢查询候选后,用EXPLAIN (ANALYZE, BUFFERS)查看实际执行计划和耗时。如果计划中大表出现Seq Scan,预估行数(estimate)与实际行数(actual)相差很大,或者Buffers: shared read数值很大(意味着磁盘I/O很多),都是有调优空间的信号。

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.total, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at > now() - interval '7 days';

3.3 总执行时间 vs 平均执行时间

调优优先级应该从「总执行时间最大的查询」入手,而不是「单次最慢的查询」。一条1秒的查询跑一次,往往不如一条10毫秒的查询一天跑一百万次对数据库整体负载的贡献大。按pg_stat_statements的total_exec_time排序,有助于确定这个优先级。

4. autovacuum、表膨胀(bloat)与事务ID回卷

这是创业团队最晚才意识到的坑,但放任不管后果也最严重。

4.1 MVCC与死元组

Postgres采用MVCC(多版本并发控制)机制,UPDATE、DELETE不会立即删除旧行,而是留下旧版本(死元组)。autovacuum需要周期性运行来回收这些死元组,表和索引才不会膨胀。如果autovacuum跟不上或配置不适合负载,膨胀(bloat)就会不断累积,同一个查询要读取更多页面,速度也随之变慢。

4.2 表级调优才是正确做法

默认的autovacuum_vacuum_scale_factor(默认20%)对大型、高频写入的表来说太宽松了。一张有几百万行的表,要等20%的行发生变化才触发vacuum,实在太晚。正确做法不是整体关闭autovacuum,而是通过ALTER TABLE只针对出问题的表单独降低该参数。

ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_cost_limit = 2000
);

4.3 事务ID回卷这道悬崖

Postgres的事务ID(XID)是32位,大约40亿次后会回卷(wraparound)。旧的行版本必须在XID年龄越过某个阈值之前被冻结(freeze)。XID年龄超过约16亿时会开始堆积警告日志,超过18亿会触发强制vacuum,接近约20亿时Postgres会为防止数据损坏而自行拒绝新的写入。走到这一步就会演变成整个服务停摆的严重故障。autovacuum要正常工作,依赖track_counts处于开启状态,因此默认原则是不要随意关闭这个参数。养成用下面这条查询定期检查每张表XID年龄的习惯是个好办法。

SELECT relname, age(relfrozenxid) AS xid_age
FROM pg_class
WHERE relkind = 'r'
ORDER BY xid_age DESC
LIMIT 10;

5. 锁与零停机迁移

架构变更是创业公司反复撞上的坑。早期毫无问题的ALTER TABLE,在数据积累之后可能变成让服务停摆的事故。

5.1 哪些DDL很危险

需要重写整张表或做全表扫描的操作 - 修改列类型、不带CONCURRENTLY的CREATE INDEX、在较旧Postgres版本上添加NOT NULL - 会在整个处理期间持有强锁(ACCESS EXCLUSIVE)。这把锁生效期间,其他查询会在队列中堆积,等待查询一多,还会连锁引发连接耗尽。Postgres 11起,带默认值的加列已经改进为即时完成(默认值存在系统目录中,读取时才应用),但像类型转换这种真正需要重写整表的操作依然很重。

5.2 扩展-收缩(expand-contract)模式

安全的零停机变更标准模式是扩展-收缩。①先以可为空(nullable)方式部署添加新列。②部署让应用同时双写新旧两列。③用后台批处理把已有数据回填到新列。④验证无误后把读取切换到新列。⑤观察一段时间确认无问题后删除旧列。把每一步拆成独立部署,任何一步失败都容易回滚。

5.3 会话超时与工具

迁移会话应始终设置较短的lock_timeout和statement_timeout,让锁等待尽早中断,而不是让一连串其他查询被堵塞。对大表的在线重组,可以考虑pg_repack(建影子副本、最后短暂加锁完成切换)或pgroll这类扩展-收缩自动化工具。

SET lock_timeout = '2s';
SET statement_timeout = '5s';
CREATE INDEX CONCURRENTLY idx_orders_customer_id ON orders (customer_id);

6. 备份、PITR与恢复演练

备份的关键不在于「有没有」,而在于「恢复能否真的做到」。

6.1 PITR的组成部分

时间点恢复(PITR,Point-in-Time Recovery)是在pg_basebackup生成的物理基础备份之上重放WAL(预写日志)归档,把数据库回滚到事故发生前的任意时刻。当误删了一张表,或者部署引入的bug把数据改错了,仅靠快照恢复是不够的,必须精确回到「事故发生前几分钟」的状态,这时PITR是必需的。

6.2 pgBackRest这类工具

与其手动管理pg_basebackup和WAL归档,生产环境更标准的做法是使用pgBackRest或WAL-G这类专用工具,它们能自动完成增量/差异备份、备份加密、并行处理和保留策略管理。

pgbackrest --stanza=mydb --type=full backup
pgbackrest --stanza=mydb --type=diff backup

# 恢复到指定时间点
pgbackrest --stanza=mydb --type=time \
  --target="2026-07-24 03:00:00" restore

6.3 为什么恢复演练比备份本身更重要

一次都没恢复过的备份,成功率其实是未知数。应当把「恢复」而不是备份文件本身当作交付物来对待。哪怕每季度只做一次,也要在独立环境里真正跑完一次时间点恢复并核对数据完整性,把这类演练固定进日程。应先定义好RPO(可接受的数据丢失范围)和RTO(可接受的恢复耗时)目标,再通过演练验证这些目标是否真能达成,这个顺序才是对的。

7. 监控指标 - 缓存命中率、等待、复制延迟

要在故障发生前察觉苗头,关键在于知道该看哪些数字。以下三项最核心。

7.1 缓存命中率

缓冲区缓存命中率衡量的是读请求中由内存(shared_buffers)而非磁盘处理的比例。通常99%以上为理想水平,一旦跌破80%,就意味着缓存相对工作集偏小,或者查询正在引发不必要的磁盘I/O。

SELECT
  sum(heap_blks_hit) / nullif(sum(heap_blks_hit) + sum(heap_blks_read), 0) AS cache_hit_ratio
FROM pg_statio_user_tables;

7.2 连接饱和与查询等待

需要同时关注当前连接数距离max_connections还有多近,以及等待锁的查询堆积了多少。等待查询数量上升,正是前文提到的连接耗尽或沉重的DDL锁正在发生的先行信号。

7.3 复制延迟

如果使用了读副本,就必须监控复制延迟(replication lag)。延迟变大意味着从副本读到的数据可能是过时的,而如果延迟已经很大时主库恰好发生故障,故障切换时的数据丢失范围也会随之扩大。用Prometheus的postgres_exporter配合Grafana,把这三项指标(缓存命中率、连接等待、复制延迟)放进同一个仪表盘并设置阈值告警,在实务上已经足够。

8. 扩容顺序 - 从垂直扩展到分片,不要跳步

有些团队一看流量增长就直接想到分片,但在实务中按顺序推进要安全和省钱得多。

8.1 垂直扩展与连接管理优先

最先该尝试的是提升实例规格的垂直扩展、前文提到的参数调优,以及通过PgBouncer做连接管理。对大多数创业公司的流量规模而言,光是这一步就能撑相当长的时间。

8.2 读副本与分区

如果读多写少,可以用流复制增加读副本来分散读流量。接下来是分区: 把一张大表在物理上拆成多个分片,让查询只扫描需要的分片。时序数据适合按日期做RANGE分区,想让写入均匀分散时,按租户ID或用户ID做HASH分区更合适。

8.3 分片才是真正的最后手段

分片(把数据分散到多个独立数据库节点)会把「应用需要知道数据在哪个分片」这种结构性复杂度引入进来,是最后的手段。只有当主节点的CPU、I/O在调优后仍持续超过70%,最大的表已达数百GB且增长速度超过存储承受能力,业务要求按租户隔离数据,或者备份、恢复所需时间本身已经无法接受时,才值得考虑分片。在这些信号出现之前就提前设计分片,大多属于过度工程。

9. 托管(RDS、Supabase、Neon) vs 自托管的取舍

这个决定更多取决于团队情况,而非技术本身。

9.1 什么情况下托管更合适

如果是没有专职数据库运维人员的早期创业公司,从能代管备份、故障切换、补丁和监控的托管服务起步,可以降低失败成本。Neon和Supabase凭借按量计费和分支(瞬间克隆开发库)功能在早期开发速度上有优势,RDS则胜在AWS生态集成和经过长期验证的运维工具。

9.2 什么情况下自托管更合适

如果成本优化很重要,且团队真正有能力自己运维Patroni式高可用、pgBackRest备份和自建监控,自托管在同等配置下可能便宜得多。但必须清楚认识到,这份节省是用团队自己承担运维负担换来的。

9.3 无论选哪边都该守住的原则

无论选哪一边,从一开始就不要过度依赖某个厂商的私有扩展或非标准功能,而应保持标准Postgres兼容性。这样当流量增长、确实需要切换时,迁移成本才会停留在改配置的量级,而不是推倒重写。

10. 早期就该做好的事 - 检查清单

把前面讲到的内容整理成一份可以在初期搭建阶段直接对照执行的清单。

  • 从一开始就把PgBouncer放在应用与数据库之间。趁流量还小时就接入,日后就不必仓促上线。
  • 从一开始就启用pg_stat_statements扩展。等出了问题才打开,恰恰会缺少最需要的那段数据。
  • 对大型、高频写入的候选表(事件日志、会话等),提前规划好逐表的autovacuum设置。
  • 从一开始就把扩展-收缩模式和CREATE INDEX CONCURRENTLY作为架构变更的默认流程。
  • 尽早搭建支持PITR的备份体系(如pgBackRest),并把恢复演练排进固定日程。
  • 把缓存命中率、连接饱和度、复制延迟三项指标放进同一个仪表盘,并设置阈值告警。
  • 先用文档明确RPO、RTO目标,再据此和团队能力决定选托管还是自托管。
  • 大量时序、事件类的表从一开始就按可分区的结构(如带日期列)设计,方便日后无停机引入分区。

结论

Postgres让创业公司措手不及的地方,大多相似: 连接毫无预兆地耗尽,索引要么缺失要么过度且无人打理,autovacuum跟不上导致膨胀累积,架构变更触发意料之外的锁,备份存在但从未真正恢复过。本文提到的每一项,如果提前知道并做好准备,代价都不大;但如果非要等事故发生后才去学,付出的就是停机和信任受损的代价。检查一下团队现在的Postgres已经覆盖了这份清单里的多少项,是今天就能迈出的最实用的一步。
