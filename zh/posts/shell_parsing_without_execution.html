Shell 命令在执行之前并不确定自己要做什么 - 结构可读而结果不可读的那条界线

解析可以做安全判定的一级过滤，却当不了安全边界

2026-09-10 开发/基础设施

盯着一行 Shell 命令，能说出它要做什么吗。多数人觉得能。可是把 echo *.json 这十一个字符摆在面前，问一句这条命令收到几个参数，答案就出不来了。因为那个数字并不在这十一个字符里。在某个仓库的顶层，这一行展开成 43 个单词；往下走一级目录，它展开成 1 个。同样的文本，不同的参数向量。

这一点决定了 Shell 是一门什么样的语言。Shell 源码与其说本身是程序，不如说是一组在执行时才把程序造出来的指令。最终交给 execve 的参数数组，不是单靠文本形成的，而是那一刻的文件系统、环境变量、前一条命令的输出和 Shell 选项状态共同拼出来的。只看文本就把那个数组钉死，在原理上做不到。

但这不等于静态分析没用。读不出的只是结果，结构是读得出的。管道有几段，重定向绑在哪个文件描述符上，命令位置放着什么，子 Shell 在哪里开始和结束，这些单凭文本就已经定下来。麻烦出在把这两件事混着用的时候。而它们正面相撞的一个地方，就是为 AI 智能体要执行的 Shell 命令做批准或拒绝的闸门。

起因是 unbash，一个 TypeScript 写的解析器，把 bash 源码在不执行的前提下变成带位置信息的语法树。有意思的是这个仓库给自己划的线。它不执行代码，不做 Shell 展开，不提供沙箱，也不判定某条命令是否安全。这四句话就是本文的全部概括。

本文的执行示例全部是只读的。输出来自 GNU bash 5.2.37(1)-release (x86_64-pc-msys)，没有使用任何创建或删除文件的例子。下面任何一行都不是按照读者复制过去直接跑的前提写的 — 它们只是为了暴露语法性质的最小示例。破坏性命令在示例中已经换成了中性命令。

不执行就分析，准确说是什么意思

这句话有两种读法。一种是不跑也知道会发生什么，另一种是不跑，只把文本的结构弄清楚。在 Shell 里能做到的只有第二种。

差别看着不大，结果却相反。按第一种读法造闸门，那个闸门会把自己没检查过的东西报成检查过了。按第二种读法造，闸门知道自己不知道什么，遇上不知道的就交给下一道防线。用同一个解析器而结果分岔，就分在这里。

拿到语法树，意思是把文本切成语法要素。这个单词是命令名，那个单词是参数，这个符号是管道，那一块是子 Shell。每个要素再附上它在原始源码里的起止位置，编辑器就能在准确的行列打标记；输入中途断了，也能返回到那一步为止的部分树和出错位置。这些是关于文本的事实，而且全都为真。

可它们不是关于执行的事实。命令位置上有 ls 这两个字符，这是真的。这两个字符在执行时会变成什么，是另一个问题，答案不在文本里，而在那个 Shell 的别名表、函数表和 PATH 里。解析器交出前一种事实，而人们常常期待后一种。

解析器给自己划的那条线

unbash 的 README 把做什么和不做什么分开写了。会写下自身边界的工具很少见，见到了就值得直接引用。

列在所处理的语法下的有这些：命令、控制流、管道、重定向和赋值，复合命令，参数展开与单词展开，进程替换与嵌套替换，coproc，here 文档与 here 字符串，C 风格 for，select，数组赋值，扩展通配符，case 的贯穿运算符（;& 和 ;;&），以及 bash 5.3 的命令替换形式。也就是说，bash 语法的大部分都覆盖到了。

列在不做的事下的有四条。不执行代码，不做 Shell 展开，不提供沙箱，不判定命令是否安全。除此之外还写明 PowerShell 和 cmd.exe 不在范围内，也写明它不是用来解析进程参数的工具。恢复能力也标了上限 — 在深度嵌套的参数展开和算术展开处，错误恢复是受限的。

关于安全的那句尤其诚实。README 直接给调用方下了要求：对安全敏感的使用者必须自己检查每个脚本的单词片段（word parts）、嵌套脚本和错误列表。把这句翻过来就是：解析器返回了一棵树，这件事本身不批准任何东西。拿到树的一方得在树上立判定规则，而那套规则的质量就是闸门的质量。

体积和性能也写着。零依赖的同步 API，压缩前 80KB、gzip 后 19KB，ISC 许可。吞吐数字和相对另一个解析器的倍数在 README 里也有，但那是仓库在自己环境下测的，不是可以脱离条件搬走的数值。

Shell 抵抗静态分析的五个理由

这里是本文的心脏。让 Shell 难以静态分析的，不是语法复杂。而是语法本来就被设计成会把执行时的状态拉进来。可以分成五支。

① 通配符由那一刻的目录决定

一个模式展开成几个单词，答案不在模式里，在文件系统里。而且一个名字都匹配不上时的行为，还会按Shell 选项状态分成三岔。

# 同样的文本，不同的目录 - 单词数不一样
$ echo *.json          # 仓库顶层
PHASE2_STAGES.json _h2_index.json ... package.json trend_topics.json   # 43 个单词

$ echo *.json          # 下面的 posts 目录
index.json                                                             # 1 个单词

# 一个都匹配不上时 - 默认把模式原样留下
$ echo zzz*.nosuch
zzz*.nosuch

$ ( shopt -s nullglob; echo "[" zzz*.nosuch "]" )
[ ]                                              # 单词消失了

$ ( shopt -s failglob; echo zzz*.nosuch )
bash: no match: zzz*.nosuch                      # 命令本身不会执行

三行用的是同一个模式。结果却分成1 个单词、0 个单词、根本没执行。落到哪一种，取决于那个 Shell 实例开了哪些选项，而那个状态不在文本里。

所以静态分析能说的大概只有这些。这个位置有个模式。这个单词的参数个数是可变的。个数下限是 0，上限定不下来。说不了的是个数和全部的值。通配符语法本身和正则的区别，另在 glob 与正则不同 - 星号含义分岔的那一刻里处理。

② 变量展开和命令替换要执行才定值

$VAR 的值在环境里，$(...) 和反引号的值则要把里面的命令真的跑一遍才出得来。后者尤其麻烦，因为那个值连确定性都没有。同一段文本求值两次，拿到不同的值是常事。

# 命令替换 - 里面跑完才有值
$ echo "$(echo one two)"
one two

# 同样的文本，每次的值都不同
$ echo $RANDOM; echo $RANDOM
11194
27279

# 展开结果不会被重新解析 - 不会变成运算符
$ v='echo a; echo b'; $v
a; echo b

$ v='echo a | tr a-z A-Z'; $v
a | tr a-z A-Z

后两个例子很关键。把 ; 或 | 放进变量里，它们不会变成运算符，只会成为普通参数。正因为有这个性质，静态分析的骨架大体守得住。展开不会凭空造出新结构。

静态分析能说的是存在一处替换，以及那里面嵌套脚本的结构。$(...) 的里面同样是 Shell 语法，所以其中的命令名和管道结构在词法上读得出来。README 之所以要求检查嵌套脚本，原因就在这儿。说不了的是值，以及那个值会怎样改变外层命令的参数边界。

③ 同一个名字指向不同的东西

命令位置上的单词执行的是什么，由名字解析规则决定：别名优先，其次函数，其次内建，最后走 PATH。同一个名字可以同时存在于这四层。

# 一个名字下同时有四个候选
$ type -a echo
echo is aliased to `echo A'
echo is a function
echo is a shell builtin
echo is /usr/bin/echo

# 函数遮住外部命令
$ printf() { builtin printf "FUNC:%s\n" "$*"; }; printf hello
FUNC:hello

# 把 PATH 收窄，刚才还找得到的现在找不到了
$ type -p node
/c/Program Files/nodejs/node
$ PATH=/usr/bin; type -p node || echo "not found"
not found

# 别名甚至还有时机问题 - 同一行里定义再用就不生效
$ shopt -s expand_aliases; alias hi="echo ok"; hi
bash: hi: command not found          # 同一行

$ shopt -s expand_aliases
$ alias hi="echo ok"
$ hi
ok                                    # 下一行

最后一个例子把静态分析的极限摆得最清楚。别名展开发生在 Shell 读这一行的时候，而那一刻的别名表是这个 Shell 的执行状态。换句话说，执行状态在解析阶段就已经介入了。同样的文本喂给另一个 Shell 实例，连解析结果都可能不同。

静态分析能说的止步于命令位置上有这段文本。这段文本在执行时解析成什么，说不了。造闸门时守住这个区分，判定语句就会准确。别写这条命令是 ls，要写这个命令位置上的单词是 ls。

④ eval 把字符串重新变成代码

第 ② 点说过展开结果不会被重新解析。eval 是这条规则的例外。它把收到的字符串当作 Shell 源码再读一遍。

# 只靠展开的话只有一条命令
$ v='echo a; echo b'; $v
a; echo b

# eval 把同一个字符串变成两条命令
$ v='echo a; echo b'; eval "$v"
a
b

# 字符串还能装下赋值和算术展开
$ s='a=1; echo $((a+1))'; echo "$s"
a=1; echo $((a+1))
$ eval "$s"
2

eval 一出现，语法树就在执行时重新诞生。静态分析能说的只到这里会生出一个新脚本为止，而那个脚本的内容取决于字符串的值，于是又绕回第 ② 点的问题。. 和 source 性质相同。它们把另一个文件的内容带进当前 Shell，那个文件装着什么在文本之外。

⑤ 单词拆分和引号改动参数边界

展开出来的值会变成几个参数，由是否加引号和 IFS 变量决定。没加引号的展开结果会被拆分，加了引号的不会，而以什么作为边界，由一个运行时变量说了算。

$ x='a b c'

$ set -- $x;   echo "argc=$#"      # 无引号 - 拆成三个
argc=3
$ set -- "$x"; echo "argc=$#"      # 有引号 - 保持一个
argc=1

# 空值如果不加引号会整个消失
$ e=''
$ set -- a $e b;   echo "argc=$#"
argc=2
$ set -- a "$e" b; echo "argc=$#"
argc=3

# 决定边界的是一个运行时变量
$ y='a:b:c'
$ ( IFS=:; for w in $y; do printf ' [%s]' "$w"; done; echo )
 [a] [b] [c]

第二个例子直接扎在闸门设计上。一个参数会整个消失。文本里明明有三个单词，实际执行的却是两个元素的参数向量。靠数位置来判定的规则在这里就错了。

静态分析能说的是这个单词没加引号，因此可能被拆分这种可能性判定。引号本身完全是词法层面的，所以这个判定是准确的。个数依旧读不出来。哪种引号关掉哪种展开，整理在 Shell 引号规则 - 哪个引号挡住了什么里。

展开顺序划定的管辖范围

五支看着各自独立，其实被一条规定捆在一起。GNU Bash 手册把展开的顺序钉死如下：花括号展开；然后是波浪号展开、参数与变量展开、算术展开和命令替换（从左到右）；然后是单词拆分；然后是文件名展开；最后是引号移除。

能增加单词数量的只有花括号展开、单词拆分和文件名展开三种，其余的展开都是把一个单词展开成一个单词。

这一句正好把静态分析的管辖范围划了出来。能改变单词数的三个阶段里，有两个依赖执行时状态。单词拆分依赖 IFS 和展开出的值，文件名展开依赖目录内容和 Shell 选项。所以参数向量不会被静态确定下来。

而剩下的那一个，花括号展开是纯词法的。它既不看文件系统也不看环境变量。这是唯一的例外，因此也是解析器能把结果都说准的唯一一种展开。

# 花括号展开不看文件系统
$ echo {a,b}.txt
a.txt b.txt

$ echo /nonexistent/{p,q}/r          # 路径不存在照样展开
/nonexistent/p/r /nonexistent/q/r

$ set -- {a,b,c}.txt; echo "argc=$#"  # 单词数是静态确定的
argc=3

# 加了引号展开就不发生 - 这一点同样是词法判定
$ echo "{a,b}.txt"
{a,b}.txt

POSIX Shell 规范把展开顺序写得稍有不同。先是波浪号展开、参数展开、命令替换、算术展开；然后是字段拆分；然后是路径名展开（除非 set -f 生效）；引号移除若要做，永远排在最后。这份清单里没有花括号展开。

阶段bash 手册的顺序POSIX 规范的顺序结果是否静态确定
花括号展开第 1 位 - 最先清单里没有确定
波浪号展开第 2 组第 1 组取决于主目录的值
参数与变量展开第 2 组第 1 组不确定
算术展开第 2 组第 1 组引用了变量就不确定
命令替换第 2 组 · 从左到右第 1 组不确定
单词拆分 · 字段拆分第 3 位第 2 位不确定 - 取决于 IFS
文件名 · 路径名展开第 4 位第 3 位 - set -f 时跳过不确定 - 取决于目录
引号移除第 5 位 - 最后永远最后确定

表里最后一列就是本文的一半。确定的那两行，是语法自己闭合的阶段；其余的全都把外部状态拉了进来。解析器看到的是这架梯子的最顶端，执行看到的是最底端。中间这一段，单词会增、会减、会消失。

执行之前照样定下来的那些

前面讲的是做不到的一侧，从这里开始是做得到的一侧。而且做得到的清单比想象中长。

# 管道结构在词法上是确定的
$ echo hi | tr a-z A-Z
HI

# 重定向可以写在命令名之前 - 第一个单词是命令这条规则是错的
$ 2>/dev/null echo redir-first-ok
redir-first-ok

# 前面挂的是赋值还是命令，同样是词法上分得清的
$ A=1 B=2 env | grep -E '^(A|B)=' | sort
A=1
B=2

# 子 Shell 边界 - 圆括号是新 Shell，花括号是同一个 Shell
$ x=1; ( x=2; echo "inner=$x" ); echo "outer=$x"
inner=2
outer=1
$ x=1; { x=2; echo "brace=$x"; }; echo "after=$x"
brace=2
after=2

重定向可以写在命令名之前，这件事在实务上造成的差别不小。凡是按行首第一个单词就是命令名这条规则做出来的检查器，在这种写法上立刻就错。结构解析器会把它准确地拆成一个重定向和一条命令。反过来也有只有赋值而没有命令的语句，这时候命令名这个槽本身是空的，这一点同样是静态确定的。

子 Shell 边界确定，意味着不执行也能说出哪些赋值会漏到外面、哪些会被关在里面。这条边界造成的实务事故，另在 管道里的while为什么变量会消失 - 子shell 2026里处理。

# 流程运算符 - 候选是确定的，执行与否由退出码决定
$ true && echo ran-A; false && echo ran-B; echo always-C
ran-A
always-C

# here 文档正文是否展开，由定界符的引号在词法上判定
$ v=VALUE; cat <<EOF
plain: $v
EOF
plain: VALUE

$ v=VALUE; cat <<"EOF"
quoted: $v
EOF
quoted: $v

流程运算符确定下来的是可能被执行的命令的上界集合。哪一条真的跑取决于退出码，属于不确定；但光是上界确定，对白名单判定就已经够用。只要上界里的每条命令都在白名单内，无论走哪个分支安全条件都成立。退出码究竟抓住什么又漏掉什么，整理在 Shell 退出码与 set -e - 它抓住什么又漏掉什么里。

here 文档这边也很干净。只看定界符有没有加引号，就能定下正文里会不会发生展开。定界符加了引号，正文就是纯文本，里面就算有看着像命令的字符串也不是命令。没加引号，正文里的替换是活的，就得当作嵌套脚本来数。这个判定是词法的，而且准确。here 文档本身怎么用，在 Here Document 实战 - 变量展开的开与关，以及缩进陷阱里。

把上面这些压成一句话就是：结构可读而结果不可读。

按构件列出的判定表

把五支和展开顺序合到一张表里，写闸门规则时就是现成的对照表。从左往右读就是：这个确定吗 → 取决于什么 → 那么能写到什么程度。

eval 参数造出的代码不确定字符串的值这里会生出一个新脚本
. · source 引入的内容不确定目标文件的内容 · 路径展开存在引入指令，以及它的目标槽在哪
参数字符串里嵌的另一种语言从 Shell 看只是一个单词那门语言的解释器单词的边界和位置 - 含义在 Shell 语法之外

最后一行最常被忘掉。有些参数本身就是用另一种语言写的程序：交给模式处理工具的脚本正文，交给远程 Shell 的命令字符串，以及那些接过参数再去拼别的命令的工具后面跟的一切。对 Shell 解析器来说，它们只是被引号裹住的一个单词。就算 Shell 的 AST 完美无缺，那里面也不归 Shell 语法管。

用字符串匹配来滤，会漏掉什么

把拦截危险命令用字符串匹配实现，造出来的是假安心。理由分三层。

  • 写法的集合是开放的。Shell 提供了多条到达同一个单词的路径。本文不去列举那些路径 — 要点不是清单有多长，而是清单关不上这个性质。靠枚举来堵的规则，只要有一种没被枚举，就会在那一种上垮掉。
  • 被检查的是展开前的文本。真正执行的参数向量，是把第 4 节那架梯子整个走完之后才拼出来的。字符串匹配只在梯子最顶端看。上面看着无害的单词到了下面变成什么，从来没被检查过。
  • 没有边界。正则不区分命令位置、参数位置、字符串内部和注释内部。于是假通过和假拦截同时发生。把 here 文档正文里的单词误当成命令而挡掉正常脚本的那一侧，和因为重定向写在前面、第一个单词并非命令而漏掉的那一侧，出自同一个原因。

第三条尤其棘手，因为失败是双向的。只往一个方向失败的检查器还能调：放得太松就收紧规则，挡得太狠就开例外。双向失败的检查器，收紧就挡住正常作业，放松就让判定变虚。两个旋钮被拴在同一根轴上。

而在实务里先出问题的是假拦截。正常命令一再被挡，人就会去找绕过闸门的办法，或者把规则整体放松。假拦截积累下来，最后归结为假安心。这就是字符串匹配闸门随时间变坏的路径。

结构判定多抓到的和依然抓不到的

先整理拿到语法树之后有什么变化。

  • 槽被区分开。命令位置、参数位置和字符串内部是不同的节点。字符串里的单词不会被当成命令来数，假拦截因此大幅减少。
  • 管道的每一段都被数到。只看前段或只看后段就放行的失误，在结构上变得不可能。
  • 嵌套脚本被单独成集。命令替换、进程替换，以及未加引号的 here 文档正文里的命令，各自拥有自己的节点。
  • 重定向的位置不再干扰。写在命令前还是命令后，都读成同一种结构。
  • 解析失败可以当信号用。语法不成立的输入一律拒绝，这条规则成立。这是字符串匹配没有的一根轴。
  • 位置信息留下判定依据。因为哪一行哪一列的哪个节点而拒绝，日志里留着，规则才改得动。

可依然有抓不到的，而且那份清单和第 3 节严丝合缝地重合。

  • 展开结果。通配符展开成什么，替换给出什么值，树里都没有。
  • 名字的解析。命令位置上的单词是别名、函数还是可执行文件，属于那个 Shell 的状态。
  • eval 与 source 之后生出的代码。树只说到这里会生出一棵新树为止。
  • 参数的语义。参数字符串里嵌的另一种语言在 Shell 语法之外。
  • 副作用的大小。同一条命令在哪个目录里跑，影响范围完全不同，而工作目录属于执行状态。
检查方式看到的假通过假拦截是否作用于展开结果
字符串与正则匹配展开前的文本，不分槽多 - 写法集合是开放的多 - 把字符串和注释里的也数进去否
基于结构的判定语法树，槽有区分减少但仍在 - 名字解析与展开大幅减少否
语法子集白名单树 + 只认允许的节点类型进一步减少 - 不认识的形式一律拒绝增加 - 正常作业也会被挡否
运行环境隔离根本不看文本不适用 - 它限定的是受损范围不适用是 - 作用在结果上

表里最后一列定下了先后。前三行都在看文本，只有最后一行在看结果。拿文本去判定原理上不确定的东西，能提高准确率，却造不出保证。

隔离、白名单、黑名单的先后

三种防御的强弱，由各自作用在什么上决定。

  • 隔离作用在结果上。无论命令展开成什么，只要文件系统可达范围、网络可达范围和权限从外部被限住，损害就有了上界。这个上界不读一个字符也成立。
  • 白名单作用在补集上。只放行枚举过的，于是没枚举的全都被挡。写法的自由度不再是攻击面，而翻转成拒绝的理由。遇上不认识的形式，默认就是拒绝。
  • 黑名单只作用在枚举过的东西上。它挡住已知的。只要有一种新写法在清单之外，就靠那一种被穿透。

所以顺序是隔离 → 白名单 → 黑名单。这不是说黑名单没用。它能早点抓住明显的失误并告诉人。关键在于它一旦成了第一道防线，那一刻就变成了假安心。

用结构解析来实现白名单，形状是这样的。这不是滤掉危险的东西，而是定义愿意接受的那个语法子集。

  • 解析失败，或错误列表不为空，就拒绝。
  • 出现允许的节点类型之外的构件就拒绝。eval、source、进程替换、coproc、嵌套命令替换放在不认识的那一侧更稳妥。
  • 命令位置上的单词不在白名单里就拒绝。同一条规则要套到管道的每一段和每个嵌套脚本的每条命令上。
  • 参数里有未加引号的展开就拒绝，或者只在把隔离强度提高一级的前提下放行。
  • 重定向目标里含有展开的，按同样办法处理。
  • 通过的命令照样在隔离里跑。过了闸门并不豁免隔离。

这份清单里最重要的一点是所有判定都朝拒绝那一侧倾斜。静态分析的不确定性必须全部压在拒绝这一侧。把不确定的东西压到放行那一侧，那份不确定就原样变成了风险。

它能出力的地方和出不了力的地方

Shell 解析器能出力的地方是明确的，而且这些地方有个共同点：判定失手不会直接变成事故。

用途需要什么失手时是否合适
代码评审与 lint结构和准确位置少提一条意见合适 - 由人做最终判断
CI 里的脚本形式检查对禁止形式的结构性检出放过一次构建合适 - 后面还有别的闸门
智能体命令闸门的一级过滤对允许语法子集的判定由下一道防线隔离接住合适 - 前提是不单独站立
日志里的命令归一与聚合抽出命令名和形状聚合项偏一格合适 - 属于可观测问题而非安全问题
编辑器高亮与补全不完整输入的部分树显示短暂错位合适 - 错误恢复反而是刚需
脚本重构工具按节点的变换和位置变换被拒绝合适 - 限于不改变展开语义的范围
安全边界本身对展开结果的保证边界被穿透不合适 - 原理上不可确定
任意脚本的安全或危险二分类对执行结果的预测放出一次错误批准不合适 - 问题定义本身不成立

第四行的日志归一较少被提起，却是静态分析嵌得最干净的位置。把执行过的命令字符串原样聚合，参数各不相同，基数会爆炸。用结构解析出来，只留命令名和选项形状，把参数值换成占位符，形状相同的命令就聚成了一项。在这里，不知道展开结果反而是优势，因为要的是形状而不是值。

反过来，最后两行换任何解析器都不会变。这不是解析器成熟度的问题，而是问题本身就不是文本能回答的问题。执行前的验证能保证什么、不能保证什么，其一般形状和 如何做出真正的 --dry-run - 要验证而不是模仿是同一种结构。

方言 - 你解析的到底是哪个 Shell

还剩最后一根轴。不确认解析器针对的是哪个方言，判定就会偏。

POSIX Shell 规范和 bash 重合得很多，但不是一回事。数组在 POSIX 规范里没有，进程替换也没有。[[ 和 ]] 在现行版里只是被列进了实现可以识别为保留字的词清单，含义并未规定。而带美元符号的单引号形式，在现行版里有专门的一节。有些地方两边一致，比如用 set -f 关掉路径名展开；也有只在一边存在的，比如花括号展开。

在这之上还叠着名字与实体错位的问题。产出上述输出的那个环境里，sh 并不是另一个实现，它就是 bash。sh -c 'echo $BASH_VERSION' 会返回 5.2.37(1)-release。也就是说，在那个环境里用 sh 试出来的结果，并不是试了 POSIX。第 3 节第 ③ 点讲的同一个名字指向不同的东西，对 Shell 自身同样成立。

这种错位在闸门里怎么显形。把以 #!/bin/sh 开头的脚本交给 bash 语法的解析器，就可能放过在真实执行环境里会是语法错误的东西。反方向也有。用了 bash 扩展的脚本只按 POSIX 标准检查就会解析失败，而在把解析失败当作拒绝信号的闸门里，正常脚本会被挡住。

语法要素POSIX Shell 规范bash对闸门的含义
数组赋值没有有POSIX 解析器会解析失败 → 假拦截
进程替换没有有漏掉嵌套脚本就是假通过
[[ 条件式只规定为可被识别的保留字连含义一起规定其行为并不依托于规范
花括号展开不在展开顺序清单里最先执行单词数的预测按方言分岔
美元单引号现行版有专门一节有转义的解释可能不同
扩展通配符没有作为选项存在同一段文本会变成不同的模式
PowerShell 与 cmd.exe不适用不适用需要完全不同的解析器

最后一行也是 unbash 自己标明的范围。Windows 系的 Shell 不在其中。如果一个闸门要接收多个平台的命令，每个方言都需要各自的解析器和各自的白名单。Shell 不同，同一段字符串连引号规则都不同，这一点在 同一个文件名在不同 Shell 里为何显示不同 - Git Bash 与 PowerShell 错开的规则里以名字处理为例做了展开。

命令闸门的接线顺序

把上面这些搬到实际接线上，顺序是这样的。

  1. 先立隔离。装解析器之前，先造出无论命令做什么受损范围都已经定死的状态。少了这一步，后面每一步都只是尽力而为。
  2. 把方言钉死。用哪个 Shell 执行，就用哪套语法检查，两边对齐。两边不同，判定和执行看的就是两种语言。
  3. 把解析失败当成拒绝。错误列表不为空就一律不放行。
  4. 收窄到语法子集。允许的节点类型之外一律拒绝。需要新语法时，明确地把规则放宽。
  5. 套上命令名白名单。管道的每一段和每个嵌套脚本的每条命令，一个不漏地套。
  6. 还留着展开的就降级。有未加引号的展开或通配符，要么拒绝，要么送进更窄的隔离。
  7. 留下判定依据。记录因为哪个节点的哪个位置而拒绝。没有依据的拒绝，最后会让人把规则整个关掉。

守住这个顺序，解析器的角色自然就回到了它该在的位置。解析器不是闸门的守卫，而是闸门的前台。看看格式对不对，不认识的退回去，通过的也交给里面真正的边界。

再回到本文开头那句，就理清了。读一行 Shell 命令然后说出它要做什么，做不到。但说出它是什么形状，做得到；判定这个形状在不在一个已定的集合里，也做得到。把闸门要回答的问题从前者换成后者 — 静态分析真正做的就是这件事。

没能确认的部分

  • GNU Bash 手册的文件名展开条目 — 该页面两次都以 HTTP 429 响应打不开。匹配不上时模式原样保留这一行为，以及 nullglob 与 failglob 的效果，只由上面的执行输出支撑，没能与手册条文比对。展开顺序那一条是直接从手册引用的。
  • POSIX 规范中路径名展开匹配失败时的规定 — 展开顺序那一节没有这种情况的表述，也没能把确认范围扩到另外的章节。
  • unbash 的 AST 节点类型全清单及各节点的字段 — README 所示例子之外的部分没能确定。因此上面允许的节点类型这一设计属于一般形状，并非贴着这个解析器实际的类型名写的。
  • README 里的吞吐数值和相对其他解析器的倍数 — 那是仓库自身的测量值，测量条件和输入集合都没能复现。就当作不能脱离条件搬走的数值放着。
  • unbash 覆盖的 bash 语法版本范围 — README 提到了 5.3 的命令替换形式，但没有按版本的对应表。
  • POSIX 规范各版本之间的差异 — 上面的表述以现行版为准，美元单引号或保留字清单在早先版本里是什么样，不在这里的范围内。
  • 其他 Shell 方言的解析器 — 针对 zsh、mksh、dash 的解析器如何处理同一条界线，没有涉及。
