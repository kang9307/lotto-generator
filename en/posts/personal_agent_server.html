A Server With a Resident Agent - What Changes When One Person Runs It

How it differs from hosting a web app: triggers, ceilings, resume, boundaries and records all move

Sep 1, 2026 Dev & Infra

Putting things on a machine at home is an old hobby. A photo store, notes, a media server, and lately model serving. One more item has joined that list recently, and it behaves unlike the rest. A resident agent. It runs when no screen is open, it starts without being asked, and what it does next is decided by itself rather than by the code.

This piece deals only with that difference. Which hardware to buy and how to open a port belong to the home server basics. What matters here is one thing: what a process that moves while nobody is watching newly demands of a server. Instincts built on request-response services cover about half of it. The other half comes back overnight as a bill and as a failure nobody heard.

This is not an install or operations guide for any product. The project that prompted it is cited as a single case, and the scope checked stops at the repository and the documents inside it. Everything written about security here is defensive; no bypass techniques are covered.

The prompt - a design where the agent is a resident

In late August 2026 a project called mu circulated in a Korean developer community. It is a personal server: one Go binary carrying mail, chat, files, notes, calendar, contacts and a shell, with agents on top. The licence is AGPL-3.0, the repository was created in November 2025, and at the time of checking it shows 420 stars, 20 forks, 30 tags with v1.6.2 the latest, and a push from the previous day. Young and active, but not a proven thing. That is also how this piece uses it: as one case, not as a recommended stack.

More interesting than the feature list is how the project explains itself. The documents inside the repository compare the system to a home and begin by stating what the metaphor forbids. No surface here scrolls forever. You do not add a ninth room because a ninth thing happened. Any surface with exactly one author is a defect. And it says why a home was chosen at all: putting agents in the position of residents is what makes 「another party lives here and does things while you are out」 an ordinary sentence instead of a feature description.

The structural lines are clear too. Services are atoms; they never call each other and never call an agent. That rule is enforced by tests rather than by prose, and the document lists the test names outright. An agent is neither code nor a deployment but an id plus a subset of services plus a prompt. Pricing is per endpoint, with the markup published in a single config file.

Then the same document lists four of its own gaps, and two of them are where this piece starts. One is 「the house never speaks first」: news fetching and a fired event are stated to be the only two motions that originate there. The other is 「composition happens only inside a model call」: services stay leaves, and the only thing able to combine two of them is a model choosing to.

Those two sentences are not modesty. They are an accurate statement of the problem. The distance between 「an agent lives here」 and 「an agent is resident here」 sits exactly there. The first is a deployment question and the second is an operations question. What follows is what actually fills that gap.

How this differs from a request-response service

A web app has a simple shape. A request arrives, work happens, a response leaves, the process goes idle again. Nearly all of operations derives from that shape. Failures surface quickly because someone is waiting. The resources one unit of work consumes are bounded by one request. Concurrency tracks traffic. Which is why watching the 5xx rate, latency and requests per second usually gets you an answer.

A resident agent violates all four.

  • It does not start from a request. Nobody is waiting for the failure. And the hours during which nobody is looking at a screen make up most of the day
  • You cannot know in advance how many calls one start will produce. How many tools get invoked is decided by the model. The ceiling on cost and elapsed time is written nowhere in the code
  • The stopping condition lives in a judgement, not in the code. So an infinite loop is syntactically normal. The process is alive, the CPU is busy, and the log keeps growing
  • The work outlives the process. A restart stops meaning 「from the beginning」. How far it got has to be written down somewhere outside the process

What you observe changes with it. In a web app one log line and one response are the same event. In an agent the thing you actually want to know — why this tool was called with these arguments — appears on no request path. If you do not decide to record it, it simply is not there.

When the trigger is not a person

Residency comes down to the trigger. When the only trigger is a user, operations are easy. The moment there are three, each brings its own class of incident.

TriggerWhen it runsWhat it newly needsWhat happens without it
User requestA person is waitingA timeoutThe screen hangs. You find out shortly
Clock (periodic run)A fixed timeOverlap prevention, a pinned time zone, a tolerance for late runsThe next run starts before the previous one finished. At a daylight-saving boundary it runs twice or not at all
External event (mail arrival, webhook, file change)Someone else decidesIngress rate limiting, de-duplication, sender restrictionsOne burst upstream becomes a burst of calls here
Its own judgement (one result calls the next action)Not predictableA step ceiling, a cost ceiling, a stop conditionAn infinite loop is indistinguishable from normal operation

Overlap prevention is sometimes handled for you and sometimes not. cron launches the next run whether or not the previous one is still going. A systemd timer will not start a second copy of a unit that is already running; it queues it instead. If you have not decided which one you are on, and whether a pile-up of delayed runs later is acceptable behaviour, then everything is quiet until the one day things ran slowly, and that is the day it breaks. A file lock you place yourself covers most of this.

  • Pin scheduled times to UTC and convert only for display. If the server sits in a region with daylight saving, or the job runs on a machine that travels, this rule earns its keep
  • Avoid the top of the hour. Every periodic job in the world clusters there, and external rate limits bite at exactly that moment
  • For event triggers, start by writing down who is able to pull them. If an inbox is the trigger, everyone who knows the address is a co-owner of it
  • Give judgement-driven triggers three ceilings at once: step count, total cost, wall-clock time. Set only one and the other two leak

While nobody is watching

Cost first. mu pricing each endpoint and publishing those prices in a single file is a good shape. But what that shape answers stops at 「how much is this call」. The question that hurts in operations is the other one. How many were there last night? Ceilings therefore belong at two levels: the maximum one run may consume (tool calls, tokens, wall-clock time), and the total a day or a month may consume. And the default behaviour on reaching a ceiling has to be stop and notify rather than warn and continue. A warning raised in the hours when nobody looks is the same as no warning.

Quiet failure arrives wearing three faces. All three share the property of looking fine on the dashboard.

  • Retries absorb the failure. Succeed on the third attempt and the success rate records as 100 percent. What changed is cost and latency, and nobody is watching either of those
  • A failure is recorded as a success. The model replies 「I could not find that file」 and exits cleanly. The exit code is 0. This is the hardest form to catch in a periodic job
  • Nothing happens at all. The timer died, or the unit is disabled. Failure alerts only arrive when something fails, so not running is indistinguishable from being quiet

The third is the most common and the longest-lived on a personal server. The fix inverts the idea. Instead of announcing failure, announce success. Every time a run finishes normally it pings something outside, and if that ping does not arrive within a set window, the other side contacts you. If your own server watches itself, a power cut takes out the watcher too. Whatever else stays in the box, this one thing has to live outside it.

Where does it resume from after it dies

Processes die. Kernel updates, memory pressure, power loss, a restart from a slipped hand. In request-response this question is easy: the client sends it again. A resident agent has no client to send it again.

So when designing a single job, three things get answered first.

  • Is how far this job got recorded outside the process? If it lives only in memory, resumption is not even a coherent concept
  • Is there anything mixed in there that must not happen twice when the job runs again?
  • Is a half-finished state a valid state? If not, is there a way to undo that half?
ActionSafe to do twice?What it needs
Read a file and summarise itYesNothing. It just costs twice as much
Write a result to local notes or a databaseConditionallyOverwrite under the same key. Appending a new row each time will not do
Send mail or a messageNoRecord 「will send」 before sending, then flip that record to 「sent」 afterwards
Order, pay or post through an external APIAbsolutely notThe caller mints a request identifier and the receiver rejects duplicates
Delete or move a fileNoMove to a quarantine folder instead of deleting, and delete after a grace period

The third row is the heart of the table. Before a side effect leaves the server, write down that it is about to leave, and only then send it. A restart can now distinguish 「recorded but not sent」 from 「sent」. The window where you die immediately after writing still exists, but its length shrinks from the whole job to a single call. What operations actually buys you is not the removal of incidents but the shrinking of the ambiguous window.

When exactly-once cannot be guaranteed

Exactly-once execution is not generally guaranteed. What gets used in practice is run at least once, and make the side effects land on the same result however many times they run. Up to here it is familiar to anyone who has handled a queue. The trap specific to agents comes after that.

  • Never build an idempotency key out of model output. Ask for the same job again and the sentences differ every time. Hash the output into a key and the key is new on every run, leaving idempotency in form only
  • Build the key from intent, not from result. 「The daily digest mail for 1 September」 is the same job even if the body differs. The target period and the job type are the raw material of the key
  • Do not put the execution time in the key. If a run that came late and a run that came on time get different keys, two of them go out that day
  • Do not mix actions that are safe to repeat with actions that are not inside one function. The retry unit becomes the whole function, so the safe first half runs again along with everything else
  • An action requiring human approval is not a candidate for resumption but for re-approval. Reusing an approval granted before the crash, after the crash, turns it into approval of a different situation

That last item drops out of designs regularly. An approval is not 「this action is permitted」 but 「this action is permitted in this situation」, and a restart is precisely the possibility that the situation changed. Carry out a file move approved thirty minutes ago, after another job has touched the same folder in the interval, and the approval survives only as an alibi.

Boundaries - what isolation blocks and what it does not

How much should the agent be able to reach? The question usually ends at 「can we not just put it in a container」, but every isolation mechanism blocks a different axis. Get the axis wrong and all that remains is the fact that you put it somewhere.

Isolation mechanismWhat it blocksWhat it does not block
ContainerHost filesystem access, package and dependency contaminationOutbound network. Calling out from inside works by default
Dedicated OS accountReading another user's home, keys and configurationEvery token that account holds. Splitting accounts while handing over the same tokens is not a split
Read-only mountTampering and deletionExfiltration. What can be read can be sent out
Outbound allow listExfiltration to arbitrary destinationsWhatever happens inside a permitted destination. One permitted API becomes the channel
Separate physical host or VMProblems arising from a shared kernelMaintenance load. Each extra box is another box one person maintains

Isolation shrinks the list of things that can be done; it does not change what something is trying to do. So boundaries have to be drawn per capability, and the capability list should hold only 「what this job needs now」. The moment one line of 「something we might use later」 goes in, the list becomes documentation and the boundary is gone.

Expressing permissions as a tool list carries a trap of its own. One tool in the list can contain all the others. mu's two built-in agents show the contrast plainly. One reaches every service; the other is narrowed to two, shell and apps. By count the second is far narrower. But one of those two is a shell. Once a shell is on the list, the length of the list stops meaning anything. Whether you narrowed the surface is judged by the widest item, not by the count.

  • It is better to narrow permissions per run than per agent. Even within one agent, the run that reads external input has no reason to hold the same rights as the run that writes results
  • Define file access as a list of paths. Opening the whole home directory and writing 「be careful」 in the prompt is a request, not a boundary
  • Start outbound connections from deny-by-default and open only what is needed. A list built in the opposite order never shrinks
  • Create a fresh, least-privilege account for each external service. Reuse a personal account you already had and the blast radius becomes that account's entire history

Credentials are a separate problem

Talk about boundaries and the conversation immediately moves to 「so how do we hand over the keys」, which is not this piece's axis. The direction, in one line: do not give the agent the credential at all, give it a narrow channel that performs the credential-requiring action on its behalf. What that channel permits and refuses is the real permission set. The concrete separation techniques are written up in getting work done without handing an agent your credentials, and how far to widen the delegation itself belongs to agent autonomy levels.

It has to be reconstructable later

One criterion is easiest. Three weeks from now, when someone asks 「why did it do that」, can you answer? Work backwards from that and what to record falls out on its own.

  • What started this run. The trigger type and, for an event, its raw content. A record holding only a timestamp has thrown away half the reconstruction in advance
  • What input went into the model. Even if you cannot keep the full text, keep which document, which conversation, and how many bytes
  • Which tool was called with which arguments, and what came back. The cause of an incident is almost always on this line
  • The model identifier and version. The same prompt behaves differently next month. Without the version, reproduction is impossible
  • What this run cost. Cost cannot be attributed after the fact. Attach it per run or you are left with one bill at the end of the month
  • How it ended. Distinguish completed, ceiling exceeded, error, and killed. Collapse those four into one column and the success-rate number starts lying

The mu document defining a thread as 「the causal record, everything that happened, whichever door it came through」 points exactly at this spot. In a system with five doors — mail, web, MCP, SSH, XMPP — records kept per door make reconstruction impossible from the start. The unit of the record has to be the event, not the door.

The trap goes down alongside it. Keep prompts and tool responses wholesale and the log itself becomes a new secret store. Along with what to keep you have to decide what not to keep, and settle the retention period in the same sitting. On a personal server the disk usually fills first.

Where outside text becomes an instruction

In a request-response app, external data is stored or displayed. In an agent, external data enters the model's context, and inside a context instructions and material have the same shape. Mail bodies, a web page that got opened, an issue description, a calendar invitation title, even a file name all land in that position.

This is not a newly discovered problem; it is the first line of the list. In OWASP's list of vulnerabilities for large language model applications, the first entry is prompt injection, and its indirect variety refers to instructions planted inside external documents or web pages the model processes. A resident agent meets every condition for it. It fetches external input on its own, it holds tools, and nobody is watching.

  • Draw the trust boundary around capability, not around data. Runs that read external content get no side-effect tools. Separate reading runs from writing runs and the most a planted instruction can reach is bounded by 「read」
  • Insert external content marked as quotation, not as instruction. Use it knowing it is not sufficient on its own. It is the first layer, not the last line of defence
  • Put human approval in front of irreversible actions. The approval screen has to show not 「what」 but 「what, and where to」. An approval that hides the destination is not an approval
  • Narrow the outbound destinations. If a summary can be sent to an arbitrary address, read access is already an exfiltration path
  • One spot is specific to personal servers. The moment an inbox is a trigger, anyone who knows the address can pull it. In a setup that receives SMTP directly, as mu does, that door stands open by default, so a sender allow list is the first setting

The condition of having exactly one maintainer

Everything above is scale-independent. Add the condition that one person runs it and a few more items attach. These are the ones an organisation used to absorb on your behalf, which is why they are invisible at first.

  • With one person on call, alerts must carry only things you can act on. Forty alerts a day carry exactly as much information as zero. Every time you add one, answer 「when this arrives, what do I do right now」 first
  • If your own server watches what you built, one incident takes out both. Keep at least the liveness signal outside. A periodic job on another device is enough
  • A holiday, a house move or sick leave is an unattended window. Those two weeks are when the design is actually tested. Whether the ceilings hold through them is effectively the whole story
  • Without a rollback plan you stop upgrading. Stop upgrading and six months later it is scarier. Keeping one snapshot and one previous binary is the precondition for staying current
  • Documentation is for yourself in six months. Without 「why it was done this way」 you will undo your own constraints. In practice the constraint undone most often is the cost ceiling
  • The shutdown procedure is part of the design. Without a list of what stops when you stop a given piece, the only option in a hurry is pulling the plug

Work worth putting on a personal server

Not everything belongs there. Judge by the property of the work, not by the feature. The same 「daily digest」 is worth a lot when the subject is your own mailbox and is not even the right venue when someone else is waiting for the report.

Property of the workOn a personal serverVerdict
The data is already here (personal mail, files, notes)The reason to ship it out disappearsThe highest value case
A person sees the result soon even if it is wrong (summaries, sorting, drafts)Quiet failure costs littleSuitable
Low, predictable frequency (once a day)Ceiling design stays simpleSuitable
It has irreversible side effects (sending, paying, deleting)Unattended execution costs a lotNot without approval
Someone else is waiting (availability is required)One person cannot hold it upUnsuitable
Freshness is the point and external dependence is heavyIt stops quietly when the outside changesMonitoring cost tends to exceed the benefit
There is a record-keeping or audit obligationYou maintain the trail aloneGenerally unsuitable

Reduced to one criterion, it reads like this. If it fails quietly overnight, will you notice in the morning, and once you notice, can you undo it? Two yeses and it is worth putting on your own box. A single no and you build that one thing first, then put it up. Reverse the order and the occasion to build it never comes.

The ledger of self-hosting deployment itself, what disappears and what you newly own, is in self-hosting your deployment platform, and moving a whole working environment onto your own side is in the self-hosted AI workspace.

Wrapping up

The distance between hosting a web app and keeping an agent resident is not install difficulty; it is the trigger. The moment the starter stops being a person, the person who notices failure disappears, the person who sets ceilings disappears, and the only thing remembering how far it got is a single process. Every other problem derives from there.

Which is why none of what you newly need is glamorous. A lock so runs do not overlap, three layers of ceiling, one line written before a side effect leaves, a boundary drawn per capability, a record kept per event, and a liveness signal parked outside the box. There are only six because without them the rest loses its meaning, not because they are easy.

Borrowing again from what that project's own document wrote down, most personal servers today never speak first. Making one speak is the next step, and most of that step lives on the operations side rather than the model side. The boring half is the half that is left.

What I could not verify

  • I did not install and run mu. Everything written here about mu is limited to the repository page and two documents inside it, and is not a verification of actual behaviour
  • The 420 stars, 20 forks, 30 tags with v1.6.2 latest and the repository creation date are values as checked on 1 September 2026. They keep moving, and activity does not imply stability
  • I could not confirm from the documents in what form mu supports scheduled or recurring jobs. I relied only as far as the document's own line that news fetching and a fired event are the only two motions that originate there
  • I found no public statistics on what incidents resident agents actually produce and how often. The failure taxonomy here comes from periodic jobs and queue operations, and it claims nothing about the frequency of agent-specific incidents
  • For the OWASP item I cited only the name of the first entry and the definition of indirect injection. Entry numbers further down the list changed between versions, so check the version alongside any individual number
