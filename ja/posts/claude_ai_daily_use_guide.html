AIアシスタントを実務で使う方法

機能紹介ではなく境界線 - どの仕事に向き、どの仕事に向かないのかを作業タイプで切り分ける

2026-07-29 IT・技術

序論: 「AIはこれができますか」は答えられない質問だ

この質問に答えはない。ほとんどすべての作業について答えが「何かは出す」だからだ。問題はできるかどうかではなく、出したものを使える状態にするまでにかかる費用である。その費用を計算しなければ、道具を使うほど仕事が増える区間が生まれ、しかもそれに気づく手段がない。

だからこの記事は機能を並べない。答えたい質問はひとつだ。「いま自分がやろうとしているこの作業は、任せてよい種類の作業か。」 これに答えるには宣伝文句ではなくふたつを知る必要がある。ひとつはこれらのモデルがどう作られているために、どう失敗するのか。もうひとつは自分が結果をどれだけ安く検証できるかだ。

原則を先に定めておく。この記事に書いた製品事実はすべて公式文書で2026年7月29日に直接確認したものであり、確認できなかった数値は最初から外した。モデル構成・価格・利用量の上限は数か月で変わる項目なので、この記事はその位置に数字ではなく確認の手順を置く。そしてどのサービスが優れているかの判定もしない。順位づけは別の記事の役目であり、ここで扱うのはどの道具を使っても同じく当てはまる境界線だ。

誇張も卑下もしない。「AIが全部やってくれる」も間違いで「役に立たない」も間違いだ。正しい文には必ず条件が付く。

1. 仕組みから生まれる境界 - なぜある仕事は得意でありある仕事は苦手なのか

長所と短所を別々に覚える必要はない。両者は同じ性質から生まれるので、性質をひとつ理解すれば一覧はおのずと出てくる。

核心はこうだ。これらのモデルは人が一行ずつ規則を書き込んだプログラムではない。 アンソロピックの解釈可能性研究はこの点を明確にしている。モデルは大量のデータで訓練され、問題を解く戦略を自分で作り出す。その戦略は人が設計した手順ではなく、学習過程で形成された内部計算に収まる。同じ研究は決定的な観察をひとつ付け加える。モデルが語る解き方と実際に起きた計算が一致しないことがあるという点だ。

最も鮮明な例が足し算である。研究陣が観察した限り、モデルはおおよその値をつかむ経路と最終桁を決める経路を並列で動かす。ところがどう計算したのかと尋ねると、繰り上がりを使う学校式の標準手順を説明する。実際の内部過程とは違う説明を出すのだ。同じ研究はモデルが望む結論から逆算して根拠を組み立てる動機づけられた推論を示すこともあり、もっともらしく聞こえるが実際の計算を反映していない段階を作り出しうると記している。

このひとつの性質から長所と短所が同時に出てくる。表にまとめるとこうなる。

性質そこから生まれる長所同じ性質から生まれる短所
規則ではなくデータから戦略を形成する形式の定まらない言語作業に柔軟だ正解がひとつの手続き的作業でずれる
もっともらしい続きを作るのがうまい下書き・要約・書き直しが速い知らないときももっともらしい文を作る
説明と実際の過程が分かれうる人が読みやすい根拠の記述を添えるその根拠の記述が検算にならない
学習の時点が固定されている蓄積された一般知識の幅が広いそれ以降の事実は構造的に存在しない
与えられた文脈の中で答える貼り付けた資料に対する処理は精度が高い社内データなしでは組織の事情を知らない

表の右のふたつの列は別々の一覧ではなく、同じ枠を前後から見たものだ。だから「短所を直してくれる設定」を探す発想は方向がずれている。直す対象は道具ではなく作業の配置である。

最新情報の問題も同じ考え方で理解すればよい。公式文書はモデルごとに知識が最も充実し信頼できる時点を別に表記している。2026年7月29日時点の表記を見ると、Claude Opus 5は2026年5月、Claude Fable 5とClaude Sonnet 5は2026年1月、Claude Haiku 4.5は2025年2月である。この時点以降の事実はモデルの中にない。 検索ツールが付いていれば調べて答えられるが、付いていない状態で尋ねるとないものをないと答えられず作り出しうるというのが前段落の性質だ。

2. 向いている仕事6つ - 共通点は「正解が複数あり人が選ぶ」

次の6つは性格がばらばらに見えるが共通条件がある。成果物が複数あり得ること、人が最終選択権を握り続けること、間違いがすぐ目につくことだ。

  • 下書きの作成 — 白紙から始める費用をなくす。下書きは定義上あとで直すものなので、間違いがあっても損失が小さい。ここで得るのは完成品ではなく編集する対象だ。
  • 形式変換 — 文章を表に、表をJSONに、ログを整理された一覧に変える作業だ。情報が新しく作られず並べ替えだけが起きるので、原本と並べれば検証がほぼ無料になる。
  • 要約 — 長い資料から何があったのかを抜き出す。原文が一緒にあるので、疑わしい行を原文で探して照合できる。原文を捨てて要約だけ残した瞬間にこの長所が消える点が重要だ。
  • コードレビューの一次確認 — 人が見る前に明白なものをふるい落とす。指摘が正しいかはコードを開けばその場で判定される。検証が安いということだ。
  • ブレインストーミング — 選択肢を増やす作業である。ここでは間違ったアイデアも費用にならない。どうせ人が選ぶし、悪い候補は良い候補の境界を描いてくれる。
  • 不慣れな分野の地図づくり — 初めて見る分野で何を検索すべきかを知るための用途だ。答えを得るのではなく用語と分岐を得るのが目的なので、続く調査で自然に修正される。

6項目を一文に縮めると「人が判断主体として残っている作業」である。逆に人が結果をそのまま次の工程へ流した瞬間、同じ作業も次節の一覧に移る。

3. 向いていない仕事5つ - 共通点は「正解がひとつで代償が大きい」

次の5つは道具の完成度が上がっても性格が変わらない。1節の性質から直接導かれるからだ。

  • 検証なしの事実確認 — 最も多く最も高くつく誤用だ。モデルは知らないと言うよりもっともらしい文を作るほうが自然である。アンソロピックの公式文書が勧める最初の緩和策が知らないと言ってよいと明示的に許可することだという事実が、この性質を裏づける。わざわざ許可を書かねばならないほど既定の動作ではないという意味だ。
  • 最新情報 — 知識の時点以降の事実はない。検索ツールなしで尋ねればないものをないと答えられない危険がそのまま残る。価格、バージョン、人事、法令改正のように変わることが本質である項目が特に危ない。
  • 正確な計算 — 1節の足し算の事例がそのまま当てはまる。結果が合うこともあるが、説明が実際の過程と違うので説明では検算できない。金額・比率・締切の計算は電卓や表計算に渡し、モデルには計算式を組む仕事までを任せるほうが安全だ。
  • 法務・医療・税務の最終判断 — ここでは間違った答えの代償が非対称に大きく、正解が管轄・時点・個別事情によって変わる。背景を理解したり専門家に尋ねる質問を整理する用途には有用だが、結論を代替させてはいけない。
  • 社内データなしの意思決定 — 自組織の実際の数値、契約条件、人員事情、政治的制約を知らない状態で出てきた勧告は一般論だ。一般論は会議で反論しにくいので、かえって危険である。資料を入れて尋ねれば状況は変わるが、そのときは次節の入力管理が先だ。

5項目の共通点は「正解がひとつで、間違えたときに戻しにくい」ことだ。2節と3節の境界線は道具がどれだけ賢いかではなく作業の構造に引かれている。

4. 核心基準 - 検証コストが執筆コストを超えるなら使うな

前のふたつの一覧を毎回覚える必要はない。基準ひとつに圧縮できる。

AIが作った成果物はそのまま使うものではなく確認を通すものだ。 したがって実際に浮いた時間は「執筆時間 − 検証時間」であって「執筆時間」ではない。この引き算が負になる区間は確実に存在し、その区間で道具を使えば遅くなるか危うくなる。遅くなるほうがまだましだ。検証を省いて危険側へ行く場合のほうが多い。

この基準の根拠は公式文書にもある。ハルシネーションを減らす手法をまとめた文書は最後に、これらの手法でもハルシネーションを完全になくすことはできず、特に重要な判断では常に情報を検証せよと明記している。検証は選択肢ではなく費用項目だという意味だ。費用項目なら計算しなければならない。

作業検証方法検証コスト判断
会議の書き起こしを決定・担当・期限に整理原本と並べて照合低い任せる
表をJSON・CSVに変換行数と数行の抽出確認、パーサで実行低い任せる
報告書の下書き作成どのみち人が全面的に編集する低い任せる
コード変更分の一次レビュー指摘された行を開いて確認、テスト実行低い任せる
不慣れな分野の用語・分岐の整理続く調査で自然に修正される低い任せるが結論には使わない
社内文書の要約(原文を保管)疑わしい文だけ原文で確認中くらい条件付きで任せる
出典のない統計・数値の引用一次出典を自分で探す必要がある高い任せない
法令・判例・約款の条項の引用原文の条項を照会する必要がある高い任せない
金額・税額・用量の計算結局は電卓で計算し直す高い計算は別の道具に渡す
最新の相場・バージョン・規定の確認公式ページを開き直す必要がある高い最初から公式ページへ行く

表で検証コストが低い行の共通点はひとつだ。確認に必要な資料がすでに手元にあること。書き起こしの原本、原本の表、コード、テストがそうである。逆にコストが高い行はすべて確認しに外へ出なければならない。その移動時間が節約分を削っていく。

実務で使える形に書き直すとこうなる。

  • 確認資料がすでに会話の中にあるなら任せる — 貼り付けた文書に対する要約・変換・抽出がこれに当たる。
  • 確認しに外へ出るなら最初から外へ行く — どのみち公式ページを開くなら、その順序を逆にする理由がない。
  • 検証を省きたくなったらそれが合図だ — 省きたくなった理由はたいてい検証が高いからで、高いということはすでに答えが出ている。
  • 間違ったとき誰が責任を負うかを先に決める — 責任の所在が自分にあるなら検証は交渉の対象ではない。

5. 入力管理 - 何を入れてはいけないのか

出力だけ管理して入力を管理しなければ、節約した時間より大きな問題が後ろで生じる。確認すべき層はふたつだ。サービスのデータ取り扱い方法と所属組織の方針であり、互いに代替できない。

アンソロピックの公式プライバシー案内を2026年7月29日に確認した内容はこうだ。個人向けプランでは利用者がモデル改善に使うよう自分で有効にした場合に会話とコーディングセッションがモデル改善に使われ、安全審査の対象として記録された場合などの別条件が併記されている。シークレット会話はその設定を有効にしていてもモデル改善には使われないと明記する。そして業務向け製品とAPIには別の規約が適用されると案内し、別の文書へ誘導する。つまり同じ会社の製品でも、どの製品をどの設定で使うかによって取り扱いが変わる。設定画面を自分で開いて確認する手順を飛ばしてはいけない理由だ。

そしてサービスが許可していることと組織が許可していることは別である。会社の端末、会社のアカウント、会社の資料には組織の規定が別にあり、そちらのほうが厳しい場合が多い。

入力の種類既定の判断理由代替
パスワード・APIキー・トークンなどの資格情報絶対に入れない漏れた時点で即座に被害が出るプレースホルダに置換、実値は秘密管理ツールへ
公的な識別番号・口座・カード番号絶対に入れない法的保護の対象で代替不能な識別子だ形式だけ残して値を除去
顧客の実名・連絡先・住所入れない目的外利用や第三者提供の問題が生じる顧客A、000-0000-0000の形に仮名化
未公表の財務数値・契約条件組織方針の確認前は入れない営業秘密や開示規制と絡む数値を比率や相対値に変えて質問
社内ソースコード方針と製品の種類による業務向け製品と個人向けプランの規約が違う許可された道具・アカウントで必要な範囲だけ
公開文書・標準・論文入れてよいすでに公開された資料だ制限なし。ただし引用は原文で確認
自分が書いた下書き・メモおおむね問題ない自分の著作物で機微情報がなければ危険が低い第三者の情報が混ざっていないかだけ確認

実務的には仮名化がほとんどの問題を解決する。「顧客の山田氏の3月の売上が4200万円だが前月比で落ちた原因を分析してほしい」を「顧客Aの3月の売上が前月比18パーセント下落した」に変えても答えの質はほぼそのままだ。モデルに必要なのは実名ではなく構造だからである。名前と実数値を外すと悪くなりそうだという感覚は、たいてい根拠がない。

6. 実務ワークフロー(1) - 議事録・文書の下書き・形式変換

ここからは実際に使う形で書く。各ワークフローはプロンプトの構造と検証方法を一組で示す。検証方法のないワークフローはワークフローではなく賭けだ。

プロンプトを書くときの原則は公式のプロンプトガイドにまとまっている。文書は文脈のない新人の同僚に説明するように明確かつ直接的に書けと勧め、同僚にプロンプトを見せてたどらせたときに混乱するならモデルも混乱するという点検法を示す。また指示の理由と動機を併記すれば結果がよくなり、XMLタグで指示・文脈・入力を区切れば解釈の誤りが減ると記している。以下のテンプレートはその勧告をそのまま踏襲した形だ。

ワークフローA - 会議の書き起こしから決定と作業を抜き出す

<役割>
あなたは会議記録を整理する実務担当者だ。
</役割>

<目的>
この整理版は会議に出られなかったメンバーが読む。
だから背景説明よりも決定と担当者が重要だ。
</目的>

<規則>
1. 書き起こしに書かれた内容だけを使う。推測で埋めない。
2. 担当者や期限が決まっていなければ「未定」と書く。
3. 決定と見なすには曖昧な発言は「保留」に分けて集める。
4. 各項目の末尾に根拠となる発言を一行そのまま引用する。
</規則>

<出力形式>
## 決定事項
- 決定 | 担当 | 期限 | 根拠発言
## 作業項目
- 作業 | 担当 | 期限 | 根拠発言
## 保留
- 議題 | 理由
</出力形式>

<書き起こし>
(ここに貼り付け)
</書き起こし>
  • 検証 — 各項目に付いた根拠発言を書き起こしで文字列検索する。見つからなければその項目は作られたものだ。
  • なぜ根拠引用を求めるのか — 公式文書は長い文書を扱うときまず原文どおりの引用を抜き出させれば答えが実際のテキストに結びつきハルシネーションが減ると案内する。ここではその手法を検証装置として使っている。
  • 「未定」を許す理由 — 空欄を埋めようとする圧力が消える。知らないと言える場所を作ってやることが最初の緩和策だ。

ワークフローB - 文書の下書きを作る

<役割>
あなたは社内のお知らせを書く担当者だ。
</役割>

<読者と目的>
読者: 非開発職を含む全社員
目的: 来週のシステム点検で生じる不便を事前に知らせる
</読者と目的>

<必ず含める>
- 点検の日時と所要時間
- その時間に使えなくなる機能
- 代替手段
- 問い合わせ先
</必ず含める>

<制約>
- 800字以内、段落は4つ以下
- 技術用語を使うなら括弧で一行の説明を付ける
- お詫びの表現は最後に一度だけ
- 私が与えていない事実(例: 原因、再発防止策)は作らない
</制約>

<材料>
(確定した事実だけをここに並べる)
</材料>

まず下書きを書き、その下に「要確認」の一覧として
私が与えなかったために空けた項目を書け。
  • 検証 — 「要確認」の一覧を先に見る。この一覧が空なのに下書きには具体的な数値が入っているならその数値は作られたものだ。
  • なぜ制約を長く書くのか — 公式ガイドは望む出力形式と制約を具体的に指定せよと勧める。分量と段落数を数字で固定するほうが「簡潔に」よりはるかによく効く。
  • 要確認一覧の効果 — モデルが空欄を自分で埋める代わりに空欄を申告するようにさせる。検証地点が文書全体から数行に縮む。

ワークフローC - データの形式変換

<作業>
以下の表をJSON配列に変換する。
</作業>

<スキーマ>
[
  {
    "id": 文字列,
    "name": 文字列,
    "qty": 整数,
    "note": 文字列またはnull
  }
]
</スキーマ>

<規則>
1. 原本にない値を推測で埋めない。空欄はnull。
2. 数字にカンマがあれば除去して整数にする。
3. 変換できない行は捨てず <問題行> ブロックに原文のまま移す。
4. 出力はJSONコードブロック1つと <問題行> ブロック1つだけ。説明は書かない。
</規則>

<検証>
最終行に「入力行数 = N、出力要素数 = M」と書け。
</検証>

<表>
(ここに貼り付け)
</表>
  • 検証 — 行数と要素数を自分で数えて照合し、JSONをパーサに通す。形式変換は機械が検証してくれる数少ない作業だ。
  • 問題行ブロックの役割 — 変換の失敗を黙って削除する代わりに表に出させる。行数が減る事故がここで捕まる。
  • 説明禁止条項 — 出力に散文が混ざると自動処理が壊れる。公式ガイドはするなという指示よりせよという指示のほうがよく効くと案内するので、「説明するな」より「出力はブロック2つだけ」がよい。

7. 実務ワークフロー(2) - コードレビュー・不慣れな領域・学習補助

ワークフローD - コードレビューの一次確認

<役割>
あなたはこの変更分を人がレビューする前に確認する一次レビュアーだ。
最終判断は人が行う。
</役割>

<確認の順序>
1. この変更で壊れうる既存の動作
2. 入力検証が抜けている箇所
3. エラー処理のない経路
4. テストが必要なのに存在しない部分
5. 読みにくい部分 (最後に、短く)
</確認の順序>

<規則>
- 開いていないファイルについて推測しない。
  コードがここになければ「要確認: ファイル名」とだけ書く。
- 各指摘にファイルと行番号を併記する。
- 確信度を高・中・低で示す。
- 確信度が低くても外さず全部書く。ふるい落とすのは私の仕事だ。
</規則>

<変更分>
(diffを貼り付け)
</変更分>
  • 検証 — 指摘された行を実際に開く。コードレビューは指摘の真偽がその場で判定されるので、検証が最も安い作業のひとつだ。
  • 推測禁止条項の根拠 — 公式のプロンプトガイドはコーディング作業のハルシネーションを減らす方法として、開いていないコードについて推測せずまずファイルを読めという趣旨の指示を例に挙げる。上の規則はその形を移したものだ。
  • 確信度を求める理由 — 「重要なものだけ言え」と指示すると実際のバグまでふるい落とされる。ふるい落とす段階を人の側へ移すほうが回収率が高い。

ワークフローE - 不慣れな領域の地図づくり

私は<分野>を初めて扱う。答えがほしいのではなく
何を調べるべきかを知りたい。

次の順で整理してほしい。

1. この分野を理解するのに必要な中心概念を5〜8個
   - 各概念を一行で説明
2. 実務で分かれる主な選択肢と、その選択を分ける基準
3. 初心者がよく持つ誤った前提を3つ
4. 私が自分で確認すべき一次出典の種類
   - 標準文書か、公式マニュアルか、規定か
5. この主題で最近変わった可能性が高い項目
   - あなたの知識の時点より後かもしれない部分を明示

各項目に確信度を示し、
確信が低ければ低いと書け。知らなければ知らないと書け。
  • 検証 — このワークフローは結論を得るのではなく検索語を得るものだ。4番で指し示した一次出典を自分で開いて確認した瞬間に誤りが修正される。
  • 5番の意味 — 知識の時点より後かもしれない部分を自ら明示させる。前述のとおりモデルごとに知識の時点の表記が違うので、この項目がそのまま「必ず外で確認する一覧」になる。
  • 結論として使わない — この段階の出力は地図であって目的地ではない。地図を目的地と取り違えることが、このワークフローの唯一の失敗の仕方だ。

ワークフローF - 学習補助

<主題>について私が理解した内容を以下に書いた。
採点者ではなく対話相手として反応してほしい。

<私の理解>
(ここに自分の言葉で説明)
</私の理解>

順序:
1. 私の説明で事実と違う部分をまず指摘せよ。理由も併せて。
2. 合っているが不正確に表現された部分を指摘せよ。
3. 私の説明に抜けている重要な条件や例外を教えてほしい。
4. 私が本当に理解したか確かめる質問を3つ投げよ。
   - 答えは先に教えないこと。
5. この主題で私が必ず原文で確認すべき項目を書け。

正解を要約してくれるのではなく、私にもう一度説明させよ。
  • 検証 — 4番の質問に自分で答えてみることが検証だ。答えに詰まれば理解していないということであり、この構造ではその事実がすぐに表れる。
  • なぜ要約を禁じるのか — 要約をもらうと読んで理解した気になるが再現する力は伸びない。説明を人の側に残しておくことがこのプロンプトのすべてだ。
  • 5番の役割 — 学習内容のうち原文確認が必要な項目を分離する。試験範囲と検証範囲を分けるわけだ。

8. プロンプトは文章ではなく構造で書く

前の6つのテンプレートは長く見えるが原理はいくつかしかなく、その原理は公式ガイドにそのまま書かれている。覚えるべきは次の6つだ。

  • 明確かつ直接的に書く — 文書は文脈のない新人の同僚に説明するように書けと勧め、同僚がその指示文を見て混乱するならモデルも混乱するという点検法を示す。「よしなに」は指示ではない。
  • 理由を併記する — 同じ文書は指示の動機と背景を説明すれば結果がよくなると記す。「三点リーダを使うな」より「この文は音声で読まれるので三点リーダを使うな」のほうがよいということだ。
  • 例を3〜5個入れる — 文書は例が出力形式と語調を決める最も信頼できる手段だとし、実際の事例に似ていて互いに十分異なる例を3〜5個入れることを勧める。
  • XMLタグで区画を分ける — 指示・文脈・例・入力がひと塊に混ざると解釈が揺れる。文書は各種類をそれぞれのタグで包めと案内する。
  • 長い資料は上に、質問は下に置く — 文書は2万トークンを超える資料を扱うとき長い文書をプロンプトの上側、質問と指示の上に置けと勧め、質問を末尾に置くと複雑な複数文書の入力で応答品質が最大30パーセント改善した試験結果があると記す。
  • 知らないと言える場所を作る — ハルシネーション緩和の文書の第一項目が知らないと認めてよいと明示的に許可せよである。「確実でなければ確実でないと書け」の一行が実際に効く。

付け加えることがひとつある。公式文書はすべての問題がプロンプトで解けるわけではないと明記する。たとえば遅延と費用はプロンプトを磨くより別のモデルを選ぶほうが容易な場合があると記す。プロンプトを5回直しても同じ失敗が繰り返されるなら、それはプロンプトの問題ではなく作業配置の問題である可能性が高い。3節の一覧へ戻るべき合図だ。

手法そのものを深く見たいなら、軸の違う記事が別にある。基礎はプロンプトエンジニアリング基礎、思考の連鎖やチェイニングのような高度な手法は高度なプロンプト手法で扱う。この記事は手法の一覧ではなく作業を任せるかどうかの判断だけを扱う。

9. モデルとプラン - 数字ではなく確認の手順を持つ

この節には意図的に数字が少ない。モデル構成と料金はこの記事で最も速く古びる部分だからだ。代わりに毎回どこで何を確認すればよいかを書く。

2026年7月29日に公式のモデル文書で確認した構成はこうだ。最新世代としてClaude Fable 5、Claude Opus 5、Claude Sonnet 5、Claude Haiku 4.5が表に載っており、以前の世代であるClaude Opus 4.8・4.7・4.6やClaude Sonnet 4.6・4.5などは別項目にまとめられている。文書はどれを使うか分からなければClaude Opus 5から始めよと案内し、最も高い能力が必要な作業にはClaude Fable 5を勧める。コンテキスト長はFable 5・Opus 5・Sonnet 5が100万トークン、Haiku 4.5が20万トークンと表記される。この構成は変わりうる。

プランは個人向けが無料・Pro・Max、組織向けがTeam・Enterpriseに分かれる。価格と利用量の上限はここには書かない。 変動が多く、間違った数字はない数字より悪いからだ。支払う前に公式の料金ページで直接確認するのが唯一正しい手順である。

選択は好みではなく三つの確認で終わる。

  • 扱う資料がコンテキストに収まるか — 数百ページの契約書の束をまるごと扱うのか、メール一通を整えるのかで必要な長さが違う。文書に表記されたコンテキスト長を見て判断する。
  • 必要な情報が知識の時点より後のものか — そうであればモデルを変えるのではなく検索ツールを使うか資料を自分で貼り付ける必要がある。これはプランの問題ではなく作業設計の問題だ。
  • 組織が求めるデータ取り扱い条件を満たすか — 5節で見たとおり個人向け製品と業務向け製品では適用される規約が違う。この確認が先だ。
  • 速度と費用が問題ならモデルを変えてみる — 公式文書が直接触れているとおり、遅延と費用はプロンプトよりモデル選択で解決する場合がある。

モデル間の性能比較そのものが気になるなら、その軸はAIモデル比較ハブで別に扱う。この記事はどのモデルにも共通して当てはまる境界だけを扱う。

10. よくある失敗5つとそれぞれの是正

失敗はたいてい道具のせいではなく配置のせいだ。よく見る5つを原因とともに書く。

症状実際の原因是正
もっともらしいが事実が違う検証の高い作業を検証なしで任せた4節の表に戻って作業を配置し直す
答えが毎回違い形式も揺れる出力形式と制約を指定していない分量・区画・禁止項目を数字で固定する
貼り付けた資料を無視して一般論を言う資料が指示の下に埋もれた長い資料を最上部に上げ質問を末尾に置く
知らないと言わず作り出す知らないと言える場所を与えなかった不確実なら不確実と書くよう明示する
計算結果が違うのに説明は完璧だ説明と実際の計算過程が違う計算は電卓へ、モデルには式だけ任せる

表の最後の行が最も危険だ。説明が完璧であるほど検算を飛ばしてしまうからである。 1節で見たとおり説明は実際の計算過程の記録ではない。根拠の記述は読みやすい散文であって検算ではない。

三行目もよく見落とされる。資料を貼り付けたのに一般論が出るとモデルが資料を無視したと結論しやすいが、実際は資料の位置が問題である場合が多い。公式ガイドが長い資料を上に上げよと勧める理由がここにある。

事実検証を工程にする方法はこの記事の範囲を超える。主張の抽出と一次出典への逆追跡を段階に分けた手順はハルシネーションのファクトチェック工程で別に扱う。この記事はいつその工程を回すべきかまでを判断する。

11. 判断表 - 作業 → 任せるか → 検証方法

ここまでの内容を実際の決定に変える表だ。左から右へ一行で読めばよい。

作業任せるか理由検証方法
書き起こしから決定・作業を抽出そうだ原本が手元にある根拠発言を原文で文字列検索
表・ログの形式変換そうだ情報が新しく作られない行数の照合 + パーサ通過
お知らせ・報告書の下書きそうだどのみち全面的に編集する要確認一覧の点検、数値の出典確認
コード変更分の一次レビューそうだ指摘の真偽がその場で判定される指摘された行を開く + テスト実行

表で「そうだ」が付いた行には共通点がある。検証に必要な資料がすべて手元にあることだ。「いいえ」が付いた行にも共通点がひとつ。確認するには外へ出なければならないことである。この一行が事実上この記事のすべてだ。

結論: 道具を選ぶ前に作業を分類する

「AIを使うべきか」は答えの出ない質問だ。代わりに三つに分ければ毎回答えが出る。

  • この作業は正解がひとつか、複数か — 複数で自分が選ぶ構造なら向いている。ひとつだけで間違えると戻しにくいなら向いていない。
  • 結果を確認するのに何が必要か — いま手元にある資料で済むなら任せる。外へ出て探す必要があるなら最初から外へ行く。
  • 間違ったとき誰が責任を負うか — 自分が負うなら検証は交渉の対象ではなく費用だ。その費用を先に計算へ入れる。

この道具は有用だ。ただし有用な理由は宣伝が語る理由と少し違う。白紙を埋める仕事、形式を移す仕事、長い資料から分岐を抜き出す仕事、人が見る前に一度確認する仕事 — ここでは代替が見当たらない。一方で事実の確定、正確な計算、最新情報、最終判断では別の道具と別の人がその仕事をはるかに正確にこなす。

最後に姿勢をもう一度書く。怖がらせる理由もなければ膨らませる理由もない。必要なのは道具が実際に得意な範囲を正確に知ることであり、その範囲は宣伝文句ではなく公式文書と検証コストの計算から出てくる。

## 2. すぐ使えるプロンプトのひな型6種

### T1. 会議の書き起こし整理

```
<役割>
あなたは会議記録を整理する実務担当者だ。
</役割>

<目的>
この整理版は会議に出られなかったメンバーが読む。
だから背景説明よりも決定と担当者が重要だ。
</目的>

<規則>
1. 書き起こしに書かれた内容だけを使う。推測で埋めない。
2. 担当者や期限が決まっていなければ「未定」と書く。
3. 決定と見なすには曖昧な発言は「保留」に分けて集める。
4. 各項目の末尾に根拠となる発言を一行そのまま引用する。
</規則>

<出力形式>
## 決定事項
- 決定 | 担当 | 期限 | 根拠発言
## 作業項目
- 作業 | 担当 | 期限 | 根拠発言
## 保留
- 議題 | 理由
</出力形式>

<書き起こし>
(ここに貼り付け)
</書き起こし>
```

**検証**: 根拠発言を原文で文字列検索する。見つからなければ作られた項目だ。

---

### T2. 文書の下書き

```
<役割>
あなたは社内のお知らせを書く担当者だ。
</役割>

<読者と目的>
読者: (ここに記入)

<必ず含める>
```

```
<作業>

</検証>

```

### T4. コードレビューの一次確認

```
<役割>
あなたはこの変更分を人がレビューする前に確認する一次レビュアーだ。
最終判断は人が行う。
</役割>

<確認の順序>
1. この変更で壊れうる既存の動作
2. 入力検証が抜けている箇所
3. エラー処理のない経路
4. テストが必要なのに存在しない部分
5. 読みにくい部分 (最後に、短く)
</確認の順序>

<規則>
- 開いていないファイルについて推測しない。
  コードがここになければ「要確認: ファイル名」とだけ書く。
- 各指摘にファイルと行番号を併記する。
- 確信度を高・中・低で示す。
- 確信度が低くても外さず全部書く。ふるい落とすのは私の仕事だ。
</規則>

<変更分>
(diffを貼り付け)
</変更分>
```

**検証**: 指摘された行を実際に開く + テスト実行。

### T5. 不慣れな領域の地図づくり

```
私は<分野>を初めて扱う。答えがほしいのではなく

   - 各概念を一行で説明

   - 標準文書か、公式マニュアルか、規定か
5. この主題で最近変わった可能性が高い項目
   - あなたの知識の時点より後かもしれない部分を明示
```

## 3. 検証チェックリスト

作業を渡す前:

- [ ] この作業の正解はひとつか、複数か
- [ ] 結果を確認する資料がいま手元にあるか
- [ ] 外へ出て確認するなら、最初から外へ行くほうが速くないか
- [ ] 間違ったとき責任は自分にあるか
- [ ] 入れようとしている資料に、入れてはいけないものが混ざっていないか

結果を受け取った後:

- [ ] 数値があるなら出典を求め、その出典を開いたか
- [ ] 引用があるなら原文で文字列検索して確認したか
- [ ] 計算があるなら電卓で計算し直したか
- [ ] 知らないと言える場所を作ったのに、そこが空のままではないか
- [ ] 最新情報が必要な項目を公式ページで確認したか
- [ ] 検証を省きたくなったなら、それはこの作業を渡すなという合図ではないか

## 4. 入れてはいけないもの

| 入力の種類 | 判断 | 代替 |
|---|---|---|
| パスワード・APIキー・トークン | 絶対に禁止 | プレースホルダに置換、実値は秘密管理ツールへ |
| 公的な識別番号・口座・カード番号 | 絶対に禁止 | 形式だけ残して値を除去 |
| 顧客の実名・連絡先・住所 | 禁止 | 顧客A、000-0000-0000の形に仮名化 |
| 未公表の財務数値・契約条件 | 方針確認前は禁止 | 比率や相対値に変えて質問 |
| 社内ソースコード | 方針と製品による | 許可された道具とアカウントで必要な範囲だけ |
| 他人の個人情報が混ざったメモ | 整理後のみ | 第三者情報を除去してから使う |
| 公開文書・標準・論文 | 可能 | 引用は原文で確認 |
| 自分が書いた下書き・メモ | おおむね可能 | 第三者の情報が混ざっていないかだけ確認 |

**入力管理のふたつの層**

1. サービスのデータ取り扱い方法 — 個人向け製品と業務向け製品・APIでは適用される規約が違う。設定画面を自分で開いて確認する。
2. 所属組織の方針 — サービスが許可しても組織が禁じることがあり、たいてい組織側のほうが厳しい。

**仮名化の原則**: モデルに必要なのは実名ではなく構造だ。名前と実数値を外しても答えの質はほぼ変わらない。

## 5. プロンプトの6原則

1. 文脈のない新人の同僚に説明するように、明確かつ直接的に書く。
2. 指示の理由を併記する。
3. 例を3〜5個入れる。実際の事例に似ていて互いに十分異なるものを。
4. XMLタグで指示・文脈・例・入力を区切る。
5. 長い資料はプロンプトの上側に、質問と指示は下に置く。
6. 「確実でなければ確実でないと書け」を入れて、知らないと言える場所を作る。

プロンプトを5回直しても同じ失敗が繰り返されるなら、それはプロンプトの問題ではなく作業配置の問題だ。1番の表へ戻る。
