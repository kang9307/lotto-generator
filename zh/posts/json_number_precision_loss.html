开篇: 查不到订单，可 ID 明明是对的

客服那边上来一个工单。客户输入了订单号却查不到。经办人核对记下来的号码，那笔订单在数据库里明明存在。可是在管理后台用同一个号码搜索却没有结果。把屏幕上的号码与数据库里的号码并排放着看，前面 16 位一模一样，只有末尾 3 位不同。

这时常见的猜测有三种。复制时被截断了、界面在四舍五入显示、数据有两份。三种都不对。值发生变化的地方不是服务器、不是数据库、也不是界面，而是它们之间那一行 JSON。

本文的要点不是「标识符请用字符串发送」这个结论。那条建议人人都知道，而且仅凭它在一个已经运行的系统里什么也找不到。本文要谈的是精度在哪里消失、代价是要放弃什么，以及为什么这个事故总是被很晚才发现。

先用一句话概括这个问题的性质。这句话解释了其余的一切。

JSON 标准并未规定数字的精度。出问题的不是标准，而是解析器，也就是语言的选择。所以当发送方与接收方使用不同语言时，两边都完全正常运作而值却错位了。

1. 复现: 19 位 ID 在 JSON 里走一遍

首先要做的是亲眼看到。就像推特和雪花系的 ID 那样，把一个 19 位整数装进 JSON 走了一趟往返。把原值与结果并排打了出来。

node v22.16.0 / win32

--- 1-1. snowflake-style 19-digit id through JSON round trip ---
sent text     : {"order_id":1234567890123456789,"amount":1000}
parsed value  : 1234567890123456800
re-serialized : {"order_id":1234567890123456800,"amount":1000}
original digits : 1234567890123456789
result   digits : 1234567890123456800
same length     : true
first differing position (0-based) : 16
digits kept     : 1234567890123456
lost tail       : 789  ->  800

这样读。发送的文本里确实装着 1234567890123456789。解析出来的值是 1234567890123456800。长度还是 19 位，前面 16 位也原封不动。从第 17 位起 789 变成了 800。

  • 没有异常。解析成功了，重新序列化也成功了。也没有违反标准
  • 长度相同。所以带位数校验的系统也会放它通过
  • 前几位相同。人用眼睛扫日志也认不出来。眼睛是从左往右读的
  • 重新序列化的 JSON 又是有效的。所以它会原样流向下一个系统。谁也拦不住

不是只试一例，而是用多种形态确认过。把实务中会遇到的形状收集了一下。

这里有好几处值得指出。

  • 999999999999999999 变成了 1000000000000000000。位数多了一位。18 位变成 19 位，所以连长度检查都过不了
  • 9007199254740993 恰好少了 1。误差不是很大，而是正好 1。这是最危险的形状
  • 像 1541815603606036480 这种末尾已经是 0 的值偏了 20。把毫秒时间戳左移做出来的 ID 常常是这个形状
  • 20 位的 12345678901234567890 偏了 890。位数越多，损失的幅度越大

误差是 1 为什么特别危险?因为旁边那个号码可能是真实存在的另一笔订单。查不到反而还比较显眼。可万一相邻的 ID 存在，查询就会成功，打开的是别人的订单。这种情况下系统到最后都不会报告任何异常。

这张表是本文最重要的输出之一。越过边界并不是全都坏，而是只有偶数活下来。

  • 9007199254740992 是精确的。越过了边界却仍然对
  • 9007199254740993 降到了 9007199254740992
  • 9007199254740994 又是精确的
  • 9007199254740995 升到了 9007199254740996。方向都不一致

由此引出一个实务上致命的陷阱。「我测过了，可以啊」这句话是成立的。挑几个偶数 ID 去验，全都通过。挑奇数就失败。随机验几条的验证方式在这一段会概率性地通过。所以验证必须用边界值清单而不是抽样。

为什么只有偶数留下来?双精度浮点用 53 比特的有效位承载有效数字。越过 2 的 53 次方之后，可表示值之间的间隔从 1 拉大到 2。再往上间隔会继续翻倍到 4、8。在 19 位这一段间隔有多大，第 1 节里 -11、-20、890 这几个误差已经直接展示了。

把两个互不相同的整数字面量原样写在代码里，严格相等比较却是真。求差是 0。不是值变得相同了，而是一开始就被读成了同一个值。

更违反直觉的是下面那段。存在一个让 x 与 x + 1 相等的点。给 9007199254740992 加 1，值还是原样。19 位的 ID 就更不用说了。从整数论上讲这不可能，而它之所以成立，是因为这里处理的不是整数，而是整数的近似值。

来看它在真实代码里如何浮现。

--- 3-3. a lookup that silently matches the wrong row ---
key sent by client   : 1234567890123456789
key after JSON.parse : 1234567890123456800
Map lookup result    : undefined
deduplication test   : how many distinct ids survive?
  sent   : 4 distinct id strings
  after  : 1 distinct numbers -> ["1234567890123456800"]
  • 用客户端发来的键去查，没有结果。因为键已经变成了另一个值
  • 更严重的是下半段。把四个互不相同的 ID 放进数组发过去，解析后合并成了一个。去重逻辑吞掉了三个
  • 这种情况下系统会判断「有重复所以整理掉了」。它被记录为正常运作
  • 批处理里发生这种事，剩下三条没被处理却被统计为成功。察觉到事故的时刻是客户来问的时候

验证时必须守住的一条。往返验证不能用值比较。受损的值彼此相等，所以值比较会通过。必须把原始文本与重新序列化的文本按字符串比较，损失才会显形。这一行之差决定了验证到底成不成立。

5. 标准规定了什么，又没规定什么

这里必须先确认规范再往下走。因为把这件事误解成「实现的缺陷」，应对方向会整个偏掉。

RFC 8259 的数字一节在定义了书写文法之后，对精度写的不是规定而是建议。打开后确认到的原文如下。

「good interoperability can be achieved by implementations that expect no more precision or range than these provide」 — 彼此都不期待超出这个精度或范围的实现之间，可以获得良好的互操作性。

「numbers that are integers and are in the range [-(2**53)+1, (2**53)-1] are interoperable in the sense that implementations will agree exactly on their numeric values」 — 是整数且落在这个范围内的数，在各实现会对其数值取得完全一致这个意义上是可互操作的。

必须准确地读这两句。它没有说「不得超出这个范围」。超出去在文法上仍然是完全有效的 JSON。标准说的是只有在那个范围内才有各实现对同一个值取得一致的保证。范围之外只是没有保证，而没有保证意味着坏掉也不算违反规范。

结论由此而来。

  • 这是一个找不到对象去提缺陷的问题。解析器是对的，序列化器也是对的
  • 能修的地方只有契约，也就是决定哪些值以什么形式往来的那一个点
  • 所以这个问题的解法不是换库，而是在规范里写上一行
  • RFC 之所以明确写出 2**53，原因也在这里。这个数字被刻进文档，不是因为 JavaScript 的具体情况，而是作为互操作的公约数

同一份文档对 Infinity 和 NaN 也钉死了: 「Numeric values that cannot be represented in the grammar below (such as Infinity and NaN) are not permitted.」 这句话在第 10 节还会再用。

6. 装进字符串 - 以及要放弃什么

把最广为人知的解法实际验证一遍。把同一个值放进引号里发了出去。

--- 5-1. the id sent as a JSON string instead ---
parsed value : 1234567890123456789
parsed type  : str
exact        : True

--- 5-2. what you give up: string ordering is not numeric ordering ---
as numbers sorted : [9, 10, 99, 100, 999999999999999999, 1000000000000000000]
as strings sorted : ['10', '100', '1000000000000000000', '9', '99', '999999999999999999']
zero padded to 20 : ['00000000000000000009', '00000000000000000010', '00000000000000000099', '00000000000000000100', '00999999999999999999', '01000000000000000000']

--- 5-3. string ids do not survive arithmetic or range filters ---
string + 1 -> TypeError: can only concatenate str (not "int") to str
"9" > "100"  (lexicographic) : True
  9  > 100   (numeric)       : False

保住了，这是理所当然的。字符串不会被解析器当作数字来解释，所以没有理由去动它。可如果这么简单，为什么大家一开始不都这么做?第二段就是答案。

  • 排序顺序变了。按数值排是 9, 10, 99, 100，按字符串排则是 10, 100, ... 排在前面。位数不同的值混在一起，顺序会完全错乱
  • 比较运算被反转。在字符串比较里 9 会被判定大于 100，因为是字典序
  • 用 0 补齐就能恢复顺序。补到 20 位后，排序结果与数值顺序一致了。代价是存储与索引变大，而且以后位数增加时要整体重做
  • 算术被堵住。想给字符串加 1 会报类型错误。这与其说是缺点，不如说更接近一道安全阀
  • 范围查询变难。那种用 ID 本身去表达「昨天以后签发的 ID」这类条件的设计，得重新设计

所以判断依据是用途而不是类型。你要用这个值做算术或范围比较吗?如果不做，用字符串实际上没什么可失去的。如果要做，字符串不是答案，而应该在契约里限制值的大小。

7. 用 BigInt 来接就行了吗

JavaScript 有任意精度的整数类型。那么用它来接不就行了，这是很自然的下一个问题。先说结论: 直接这么做不行。

确认了两件事。第一，标准解析器不会替你造出 BigInt。反方向想序列化 BigInt，则会直接抛异常。第二，解析之后再转换太迟了。把已经受损的数字转成 BigInt，只是把受损的值精确保存下来。

  result : 1234567890123456789
  type   : bigint
  exact  : true

--- 6-4. the portable workaround: quote the digits before parsing ---

  result : 1234567890123456789

  input  : {"memo":"call 01012345678901234567 back","id":1234567890123456789}

unquoted number form              : {"order_id":1234567890123456789,"amount":1000}
  the second form is valid JSON, and it breaks again at the next JS reader
  • 在这个环境的 Node 22 上，reviver 的第三个参数可以拿到原始文本片段。用它就能精确复原 1234567890123456789
  • 如果环境里没有这个功能，还有在解析前改写文本、给它套上引号的做法。这是被广泛使用的绕行法
  • 不过那种绕行法有代价，上面输出的最后一例就是。字符串里面的长数字本该不去碰它，而用正则改写文本可能把边界判断错
  • 输出一侧也是问题。把 BigInt 以字符串输出是安全的，但去掉引号以数字输出，到下一个消费方又会坏

归纳起来，BigInt 是用于计算的工具，而不是守住 JSON 边界的工具。要守边界反正得在文本层介入，既然如此，一开始就用字符串往来更简单。

8. 浮点数的往返 - 要写几位才有保证

整数讲完了，转到小数。从最有名的例子开始确认。

--- 7-1. the classic float sum, in python ---
0.1 + 0.2                  = 0.30000000000000004
0.1 + 0.2 == 0.3           : False
Decimal of 0.1             = 0.1000000000000000055511151231257827021181583404541015625
json.dumps(0.1 + 0.2)      = 0.30000000000000004
json.loads of that == sum  : True

--- 7-2. how many decimal digits guarantee a float round trip ---
sys.float_info.dig     : 15  (digits guaranteed to survive text -> float -> text)
mant_dig               : 53 bits
  %.15g : 183351 failures out of 200000
      first failure  original 399955.7584213044 -> text 399955.758421304 -> back 399955.758421304
  %.16g :  51352 failures out of 200000
      first failure  original -377762.57764660777 -> text -377762.5776466078 -> back -377762.5776466078
  %.17g :      0 failures out of 200000

--- 7-3. repr already picks the shortest text that round trips ---
  0.1                    len= 3  round trip: True
  0.30000000000000004    len=19  round trip: True
  0.3333333333333333     len=18  round trip: True
  1.4142135623730951     len=18  round trip: True
  1e-07                  len= 5  round trip: True

0.1 + 0.2 不等于 0.3 很有名。这里要看的是接下来那件事。把那个值以 JSON 输出再读回来，回来的是完全相同的值。也就是说浮点数的往返是安全的。与整数正好相反。

安全的原因在第二段里。改变位数各做了 20 万次往返。

  • 写 15 位时失败超过 18 万次。也就是说 15 位无法保证往返
  • 16 位也失败超过 5 万次
  • 到 17 位失败降为 0。20 万条全部精确返回

这就是双精度实数里 17 位这个数字的由来。要在十进制里区分 53 比特有效位所能表示的那些值，就需要这么多位。这与 Python 报告的「保证位数」是 15 很容易混淆，但两者方向不同。15 是从十进制出发做往返时的保证，17 是从二进制出发做往返时所需的位数。

在 JavaScript 里做了同样的实验。

--- 7-4. the same float questions in JS ---
0.1 + 0.2                       = 0.30000000000000004
0.1 + 0.2 === 0.3               : false
JSON.stringify(0.1 + 0.2)       = 0.30000000000000004
JSON.parse of that === sum      : true
(0.1).toFixed(20)               = 0.10000000000000000555

--- 7-5. how many digits does a float need to survive text -> float -> text ---
  toPrecision(15) : 183313 failures out of 200000
      first failure  original -209512.3501494527 -> text -209512.350149453 -> back -209512.350149453
  toPrecision(16) :  51116 failures out of 200000
      first failure  original 280978.53949293494 -> text 280978.5394929349 -> back 280978.5394929349
  toPrecision(17) :      0 failures out of 200000
  JSON.stringify picks the shortest text that round trips, not a fixed width:
    0.1                    len= 3  round trip: true
    0.30000000000000004    len=19  round trip: true
    0.3333333333333333     len=18  round trip: true
    1.4142135623730951     len=18  round trip: true
    1e-7                   len= 4  round trip: true

结果一致。17 位时失败为 0。而且两种语言的序列化器都不会总是写 17 位。0.1 输出为三个字符，0.30000000000000004 输出为 19 个字符。它挑的是能保证往返的最短写法，所以自己去指定位数反而会造成损失。

实务规则。把小数以 JSON 输出时不要自己指定位数。那种为了四舍五入弄漂亮而做的介入，会破坏往返保证。显示格式在界面上决定，传输时用默认序列化才对。

9. 金额 - JSON 边界上的序列化

金额不能用浮点数这条原则本身已在金融科技工程手册里讲过。这里只看发生在 JSON 边界上的事。

--- 8-1. money at the JSON boundary (serialization only) ---
float sum of [19.99,19.99,19.99,0.1,0.2] = 60.27
JSON.stringify(sum)                     = 60.27
rounded to 2dp                          = 60.27
integer minor units sum                 = 6027  (60.27)
difference                              = 0 minor units

  the JSON boundary problem is not the arithmetic, it is the text:
    text 0.10      -> number 0.1       -> re-stringified 0.1       text preserved: false
    text 19.99     -> number 19.99     -> re-stringified 19.99     text preserved: true
    text 1234.50   -> number 1234.5    -> re-stringified 1234.5    text preserved: false
    text 100.00    -> number 100       -> re-stringified 100       text preserved: false
  trailing zeros and the scale of the amount are not part of a JSON number

先看上半段。在这个样本里，实数求和与整数求和之差是 0。意思是四舍五入之后结果相同，这说明「用小数相加必定会少一块钱」这种通行说法并不总是成立。有会丢的情况也有不会的情况，而这个样本属于后者。所以才更危险。测试会通过。

真正的问题在下半段。在 JSON 边界上消失的不是值，而是写法。

  • 发 0.10 回来的是 0.1。末尾的 0 消失了
  • 1234.50 变成 1234.5。作为金额的写法很别扭，而在字符串比较或签名校验里就是不一致
  • 100.00 变成 100。小数点本身消失了，币种的小数位数信息也随之没有了
  • 只有 19.99 保持原样，那也只是恰好最短写法与原值相同

也就是说 JSON 数字没有小数位数这个概念。100.00 与 100 是同一个数，序列化器会挑短的那个。在同时处理小数位数不同的币种的系统里，这就成了问题。

替代方案只有两个。以最小单位整数发送并把币种代码一起装上，或者以字符串发送并把写法原样保住。前者是通行做法，后者用于难以在契约里固定小数位数的场合。无论哪一种，唯一被排除的选项就是用 JSON 数字发送金额。

10. NaN 与无穷大 - 标准里没有的值

正如第 5 节引用的 RFC 原文所说，这两个值在 JSON 文法里并不存在。可程序里会造出来。除以 0 或超出范围就会产生。那么序列化器会做什么?

--- 9-2. NaN and Infinity at the JSON boundary in JS ---
JSON.stringify(NaN)                  : null
JSON.stringify(Infinity)             : null
JSON.stringify(-Infinity)            : null
JSON.stringify({a:NaN,b:Infinity})   : {"a":null,"b":null}
JSON.stringify([NaN, Infinity])      : [null,null]
JSON.stringify(-0)                   : 0
JSON.parse(JSON.stringify(-0))       : 0  Object.is(-0) : false
  JSON.parse("NaN"        ) -> SyntaxError
  JSON.parse("Infinity"   ) -> SyntaxError
  JSON.parse("-Infinity"  ) -> SyntaxError
  JSON.parse("nan"        ) -> SyntaxError
  JSON.parse("1e400"      ) -> Infinity
  JSON.parse("-1e400"     ) -> -Infinity
  JSON.parse("1e-400"     ) -> 0

JavaScript 的选择是把它们变成 null，既不抛异常也不警告。来看这在实务上意味着什么。因为测量失败而变成 NaN 的值，与本来就没测量所以是 null 的值，在接收侧变得完全无法区分。「没有数据」与「计算失败」合成了一个值。

另外还确认到几件事。

  • 负零消失了。输出 -0 会变成 0，回来的值不再是负零
  • 超出范围的字面量会变成无穷大。1e400 不是解析错误而是 Infinity。也就是读的时候静默接受，写的时候变成 null
  • 太小的值会变成 0。1e-400 被解析成了 0。非零的值变成 0，在有除法的代码里很危险
  • 反过来读的一侧是严格的。把 NaN 或 Infinity 这几个字母放进去会报语法错误

其他语言在这个点上行为又不一样。

--- 9-1. NaN and Infinity: python writes them, the standard has them not ---
json.dumps default      : {"nan": NaN, "inf": Infinity, "ninf": -Infinity}
json.loads of that back : {"nan": NaN, "inf": Infinity, "ninf": -Infinity}
json.dumps allow_nan=False -> ValueError: Out of range float values are not JSON compliant: nan
json.loads('NaN')       : nan
json.loads('Infinity')  : inf
with parse_constant     -> ValueError: rejected NaN

--- 11-5. NaN and Infinity in a third parser ---
  decode(NaN) -> error: malformed JSON string, neither array, object, number, string or atom,
  decode(Infinity) -> error: malformed JSON string, neither array, object, number, string or atom,
  decode(-Infinity) -> error: malformed number (no digits after initial minus),
  decode(1e400) -> Inf
  encode([inf, nan]) -> [Inf,NaN]

这份输出显示的不对称很大。

  • Python 按默认设置会把 NaN 与 Infinity 原样写出去。这不是标准 JSON。而且它写出来的自己还能读回去，所以只在同一种语言之间测试永远发现不了
  • Python 有禁止这件事的选项，打开就会抛异常。默认是宽松那一侧才是关键
  • Perl 拒绝读取。NaN 与 Infinity 都是解析错误
  • 可是 Perl 写的时候会写出去。对装着无穷大与 NaN 的数组做编码，出来的是 [Inf,NaN]。这段文本 Perl 自己也读不回去

11. 大数的指数记法 - 它会穿过位数检查

把整数防御写成「16 位及以上就有风险」这条规则，会漏掉一个洞。确认了从多大开始记法会切换。

--- 10-2. where JS flips to exponent notation ---
n                        String(n)                          JSON.stringify(n)
----------------------------------------------------------------------------------
10^18                    1000000000000000000                1000000000000000000
10^19                    10000000000000000000               10000000000000000000
10^20                    100000000000000000000              100000000000000000000
10^21                    1e+21                              1e+21
10^22                    1e+22                              1e+22
10^100                   1e+100                             1e+100

  and back again:
    JSON.parse(1e21                    ) -> 1e+21   re-stringified -> 1e+21
    JSON.parse(1e+21                   ) -> 1e+21   re-stringified -> 1e+21
    JSON.parse(1E21                    ) -> 1e+21   re-stringified -> 1e+21
    JSON.parse(1000000000000000000000  ) -> 1e+21   re-stringified -> 1e+21
  a naive digit-count guard misses this shape entirely:
    text          : 1e+21
    /^\d{16,}$/   : false   <- the guard does not fire

恰好从 10 的 21 次方开始变成指数记法。在它之下直到 10 的 20 次方，数字都是原样排开的。这个边界由语言规范定下，不会随意改变。

这在实务上为什么是问题?最后两行是答案。找 16 位及以上的正则对 1e+21 没有反应。因为文本只有五个字符。一个实际上丢了 21 位的值，就这样通过了位数检查。

  • 再解析一次也换不回原来的位数。1000000000000000000000 与 1e21 被当作同一个值
  • 大写的 1E21 也被读成同一个值。在检查用的正则里漏掉大小写是很常见的失误
  • 这一段的值很少用作标识符，但累计总额或字节数会到达
  • 所以诊断步骤里必须把搜索指数记法作为单独一项加进去

数据库的 JSON 函数也确认了。这里暴露出即使在同一个引擎内部，结果也会因路径而分野。

  • 把同一个值转成实数再构造 JSON 对象，出来的是 1.23456789012346e+18。精度缩到了 15 位
  • 1e21 被识别为实数类型。也就是说文本的写法有时也决定存储类型

还看了 CSV 与表格软件这条路径。这里之所以特别重要，是因为结算资料是以表格来往的现实。

13. 重复键、键顺序、规范化哈希

把与数字同样常纠缠在一起的周边问题放在同一次执行里确认了。

--- 13-1. duplicate keys: last one wins, silently ---
  JSON.parse({"id":1,"id":2,"id":3}) -> {"id":3}
  a signed payload can carry two values for the same field, and two
  parsers can disagree about which one is real

--- 13-2. key order is not preserved the way you think ---
  input  : {"b":1,"2":2,"a":3,"1":4}
  output : {"1":4,"2":2,"b":1,"a":3}
  integer-like keys are reordered ahead of the rest by the object model

--- 13-3. canonicalize before hashing, or the signature breaks ---
  a raw sha256      : 342ae634b438dfbe6c65969e
  b raw sha256      : 760edb200363c660478ae117
  c raw sha256      : 6225dd8ec799896b92e0af16
  a canonical sha256: 85bdc381b4aff3953e97ddeb
  b canonical sha256: 85bdc381b4aff3953e97ddeb
  c canonical sha256: 85bdc381b4aff3953e97ddeb
  canonical form of a : {"amount":19.99,"id":1234567890123456800}
  and here is the catch:
    canonical form still contains 1234567890123456800
    which is NOT the id that was sent. canonicalization does not undo the loss.

出来了三件事。

  • 重复键是最后一个值胜出。RFC 8259 一方面建议名字应当唯一，一方面写明当它们不唯一时行为是不可预测的。实际确认的三个解析器都取了最后一个值，但这是惯例而不是保证
  • 键顺序被重排。看起来像整数的键被拉到了前面。给顺序赋予了含义的设计会在这里坏掉
  • 规范化之后哈希一致。仅在空白与键顺序上不同的三段文本，规范化之后得到了相同的哈希

可是本节的要点在最后那一段。规范化结果里装着的 ID 已经是受损的值。规范化只是消除写法上的差异，换不回已经消失的位数。意思是签名一致并不保证值是原本的值。用规范化哈希确认完整性的系统必须对这一点另行防御。

--- 13-4. escapes and lone surrogates in the same payload ---
  JSON.parse of \u escaped digits stays a string:
    value : 1234567890123456789   length : 19
  numbers cannot be escaped that way:
    JSON.parse of an escaped bare digit -> SyntaxError
  JSON.stringify of a lone surrogate : "\ud800"  (well-formed output, ES2019)
    code unit : U+D800
    round trip identical : true
  and a number-shaped string is not a number:
    JSON.parse('"1e21"') typeof : string

--- 11-6. key order and duplicate keys, third parser ---
  decode of three identical keys -> id = 3
  canonical encode of {b,a,c}    -> {"a":2,"b":1,"c":3}
  default encode of the same     -> {"c":3,"b":1,"a":2}
  • 字符串里的数字即使写成 Unicode 转义也还是字符串。不会受损
  • 反过来数字字面量无法转义。一转义就是语法错误
  • 没有配对的代理项在序列化时以转义形式安全输出，往返也完全相同
  • 看起来像数字的字符串仍然是字符串。把 1e21 放进引号里它不会变成数字
  • 在 Perl 里重复键同样是最后一个值，而且另有固定键顺序的选项

14. 为什么总是很晚才被发现

这个事故最难缠的性质不在技术而在时间。发现之所以晚，原因是结构性的。

  • 开发数据的 ID 很小。用 1、2、3 开发，这个问题就不存在。正如第 2 节的输出，16 位以内全都正常
  • 预发布环境通常也很小。一般不会直接用生产数据，所以这里也抓不到
  • 上线初期也抓不到。如果是顺序编号，ID 要长到 16 位需要很久
  • 爆的时点是改 ID 体系的时候。从顺序号迁到分布式 ID、引入基于时间戳的 ID，或者开始接收别的系统的 ID 时，19 位会突然进来
  • 到那个时点代码已经散在好几处。最初设计时改一处就够的事，现在是全链路
  • 测试全都通过。因为既有测试数据里的 ID 很小。写了新代码，用旧数据去验证，照样通过

应对很简单: 在开发数据里混进 19 位的 ID。只改一条数据，这个问题就会在开发阶段显形。成本几乎为零而效果最大。

另外还有办法确认这个问题是否已经发生过。就是在日志与审计记录里找同一字段的值只有末尾一两位不同的成对值。如果前面几位完全相同、只有后面不同的值反复出现，那不是巧合，而是已经发生过的事故的痕迹。

15. 诊断步骤 - 在已经运行的 API 里找出来

把巡检运行中 API 的顺序做成了可执行的形式。核心原则只有一条: 要看原始文本，而不是解析后的对象。

这个扫描器不把 JSON 当作数字来解析，而是在文本里找字面量。只有这样才能看到受损之前的值。结果里抓到了四种类型。

  • 超过 2 的 53 次方的整数三处: 订单 ID、钱包余额、纳秒时刻
  • 指数记法一处，就是上一节看到的那个洞
  • 写法会变的小数一处，1234.50 变成 1234.5
  • 字符串里面的 20 位数字没有被抓到。这是正确的行为，因为字符串不会受损

--- 12-4. a guard you can actually ship ---
  {"order_id":1234567890123456789}
    -> 1234567890123456789  : integer beyond 2^53-1
  {"order_id":"1234567890123456789"}
    -> clean
  {"memo":"ref 1234567890123456789","id":42}
    -> clean
  {"amount":100.00,"qty":3}
    -> 100.00  : text changes on round trip -> 100
  {"big":1e21}

  {"epoch_ns":1753833600123456789,"ok":1699999999999}
    -> 1753833600123456789  : integer beyond 2^53-1
  • 以数字发送的大整数被抓到
  • 以字符串发送的同一个值报告为干净。这是正确的判定
  • 字符串里面的长数字也被跳过，因为正则被写成先消费字符串
  • 金额写法 100.00 与指数写法 1e21 也被分别抓到
  • 纳秒时刻被抓到，而毫秒时刻报告为安全。它确实是安全的

顺便把 schema 那一侧的惯例也一并整理。在 OpenAPI 系的 schema 里给整数字段加 format: int64 的做法被广泛使用，但这个标注属于文档层面的声明，并不强制解析器。它只是帮助代码生成器据此挑选合适的类型而已，写进 schema 并不会让 JavaScript 的消费方突然变精确。把规范作为契约来运营的做法属于API 文档治理那一侧的主题。

17. 没有下断言的部分

把本文确认过的范围与没能确认的范围区分开。

  • 并没有确认所有语言。确认过的只有 JavaScript、Python、Perl 以及 SQLite。其他语言和其他解析器实现可能又有不同的行为
  • 即使同一种语言内部也有多个解析器。这里看到的是各语言的默认实现，替代解析器在选项与行为上都不同
  • 存在版本依赖。在 reviver 里拿到原始文本是比较新的规范，较旧的运行时没有。「在这个环境里可以」不等于「在哪里都可以」
  • 没有把金额实验的结论一般化。在这个样本里实数求和与整数求和一致。换个样本就会错开。本文只说这个差异取决于样本
  • 没有运行表格软件本身。只确认了 CSV 的文本层与数字转换层。具体产品的行为必须另行确认
  • 没有测量性能。字符串标识符对索引与查询造成多大负担取决于数据规模，需要各自测量

结语: 标准留白的那个位置

再用一句话写一遍: JSON 标准没有规定数字的精度，而各个语言用自己的方式填了那处空白。因为这些选择彼此不同，所以两边各自正常运作而值却错开了。

所以这个问题在代码里修不了。换解析器、换库、换语言，只要下一个消费方是别的语言，它就会再次发生。能修的地方只有契约: 写下哪些值以什么形式往来，并把它作为边界测试常驻下来。

如果要在当下只挑一个最便宜的措施，那就是在开发数据里混进一个 19 位的 ID。一条数据就够。正是因为缺了这一条，这个事故才总是在生产环境、在 ID 变大之后、通过客户咨询被发现。

# JSON 数字精度 — 类型判断表与边界测试值

> 来源: braindetox.kr — 装进 JSON 的 64 位 ID 末尾会变
> 依据: 在 Windows 10 / Node 22.16.0 / Python 3.13.3 / Perl 5.38.2 (JSON::PP 4.16) / SQLite 3.49.1 上实际执行验证
> 规范: RFC 8259 Section 6 — 可互操作的整数区间是 -(2^53)+1 到 (2^53)-1

## 1. 一句话结论

JSON 标准并未规定数字的精度。出问题的是解析器，也就是语言的选择。
发送方与接收方使用不同语言时，值会**不抛出任何异常地**改变。

## 2. 由数据性质决定类型

| 数据性质 | 例子 | 放进 JSON 的形式 | 理由 | 验证方法 |
|---|---|---|---|---|
| 标识符 (不做运算) | 订单号、用户 ID、雪花 ID | **字符串** | 不需要算术，唯一要求是保住位数 | 往返后按字符串比较是否完全一致 |
| 纳秒时刻 | epoch_ns、追踪时间戳 | **字符串** 或毫秒整数 | 纳秒的 19 位超过 2^53 | 往返一个 19 位样本并检查末尾 |
| 金额 | 支付额、余额 | **最小单位整数** 加币种代码 (或字符串) | 小数写法与位数都不会保留在 JSON 数字里 | 往返 100.00 看它是否变成 100 |
| 数量与计数 | 库存、页码 | 整数原样 | 没有触及 2^53 的余地 | 契约里是否写了上限 |
| 测量值与比率 | 响应时间、坐标、概率 | 数字原样 | 精度损失在容忍范围内 | 17 位有效数字能否往返 |
| 哈希与签名 | SHA-256、校验和 | **十六进制字符串** | 本来就不是当作整数处理的值 | 校验长度与字符集 |
| 64 位标志位 | 权限掩码 | **字符串** 或数组 | 有些语言把位运算截断到 32 位 | 最高位是否还在 |

## 5. API 契约用语 (可直接贴进规范或评审)

- 本字段是**标识符**，不参与算术。以 JSON 字符串传输，最大长度 20 个字符。
- 本字段以 JSON 数字传输，并保证取值始终在 -(2^53)+1 与 (2^53)-1 之间 (含端点)。
- 金额字段以币种的**最小单位整数**传输。单位与币种代码放在同一个对象内一起传。
- 响应中不会出现 NaN、Infinity、-Infinity。无法测量的值用 `null` 表示。
- 消费方可以假定把任何数字字段解析为双精度浮点都不会有损失。
- 在 schema 中同时写 `type: integer` 与 `format: int64`，并注明 `format` 属于文档层面的记法，并不强制任何语言的解析器。
- 客户端回传标识符时，要求**原样返回收到的文本**。

## 6. 对已上线 API 的诊断步骤

1. 拿到响应的**原始文本**。看解析后的对象就已经太迟了。
2. 在原始文本中找出 16 位及以上的整数字面量。排除字符串内部的数字。
3. 把找到的字面量与 `2^53-1` 比较。只要有一个超过，风险即可确认。
4. 单独搜索带指数记法 (`e`、`E`) 的字面量。只数位数的检查抓不到它们。
5. 把小数字面量与其再序列化的结果**按字符串**比较。观察末尾的 0 与位数是否消失。
6. 在日志与审计记录里搜索同一字段**只有末尾一两位不同**的成对值。那是事故已经发生过的痕迹。
7. 把第 3 节的边界值放进契约测试，并按字符串而不是按值断言。

## 7. 防御位置

| 位置 | 该做的 | 不该做的 |
|---|---|---|
| schema 与规范 | 把标识符钉死为字符串并写下上限 | 猜测「一般不会变大」 |
| 服务端序列化 | 把标识符以字符串输出 | 输出为数字并交给客户端处理 |
| 客户端解析 | 在原始文本里找出大整数并以字符串或大整数类型接收 | 解析之后再转成大整数，那时已经太迟 |
| 存储 | 放进整数列 | 浮点列，以及表格软件的自动转换 |
| 测试 | 在开发数据里混入 19 位 ID | 只用 1、2、3 做开发 |
| 审计 | 让边界值常驻在契约测试中 | 只在出事之后才检查 |

## 8. 不要做的事

- 解析之后再把大整数转成字符串或大整数类型 — 那一刻位数已经没了
- 只数位数的检查 — 指数记法会径直穿过去
- 用值是否相等来验证往返 — 两个受损的值彼此相等
- 只用小 ID 做开发和测试 — 等生产环境的 ID 变大之后才爆
- 用规范化之后的哈希比较来确认完整性 — 规范化无法找回已经丢失的位数
- 认为「用字符串发送就完事了」 — 还要决定在哪里承担排序、范围查询与比较的代价
