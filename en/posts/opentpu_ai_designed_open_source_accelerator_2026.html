This article rests on the sentences and tables in the README of the GitHub repository FeSens/openTPU, in its docs files (board.md, isa.md and quant.md), in its LICENSE file, and in the README of the predecessor repository auto-arch-tournament. Figures are carried over together with their measurement conditions, and any value that does not appear in the sources is marked as a calculation.

Background — The Scope of the One Line That Says Developed by AI

The README of the openTPU repository introduces the project in its first line as an open-source AI accelerator, developed by AI. The sentence that follows states the two questions the project asks: how far AI agents can go at hardware design, and whether they can build the chip that runs their own inference. The README adds that the project brings the lessons of an earlier project, auto-arch-tournament, to AI accelerators. It was introduced on GeekNews on October 7, 2026. Those few sentences, a tagline followed by a pair of open questions, are the whole of what the project says about itself before the README moves on to what is in the repository and what was measured.

That one line is easy to read broadly. The two sentences above are everything the README attaches to the word developed. It does not say which parts agents wrote and what people did, and it does not say which agents or models were used. A statement such as AI designed a chip entirely on its own therefore does not come out of the README. The only place the word chip appears in the README is the question quoted above, and what the results section describes is a design running on an FPGA card: the design runs ten modern models with their real weights on an Inspur YPCB-00338 card (Xilinx Kintex-7 xc7k480t, two DDR3 channels). The README contains no statement about a fabricated ASIC or a tape-out. Reading the tagline closely therefore means keeping two things apart: the claim about who developed the design, which the README states without elaboration, and the description of what the design is and where it runs, which the README documents in detail.

What the README actually puts forward comes down to three things.

  • A repository: The whole accelerator lives in one small monorepo that can be read from end to end.
  • Measurements: Decode and prefill speeds and DRAM bandwidth measured on the card are printed in a table, broken down by model and by weight quantization.
  • Verification: The card produces the same tokens as the simulator, bit for bit.

What Is in the Repository — Design, Instruction Set, Simulator, Compiler, Host

The README also presents openTPU as a learning project. The repository holds, side by side, the hardware design (SystemVerilog), the instruction set, a bit-exact simulator, a kernel language and its compiler, and the host software that drives a real PCIe card. In the words of the README, it is a good place to start for anyone who wants to understand how an AI accelerator works, from a matmul in Python down to the wires. The table below lists those parts in the order in which the README's own diagram stacks them, together with the place in the repository where each one is found.

Component Location in the repository Role as described in the README
Kernels opentpu/kernels mlp, attention and full model layers written in the ol language, marked with the @ol.jit decorator
Language and compiler docs/compiler.md Layouts, affine loop addressing and fusion; this is where a kernel becomes instructions
Instruction set (ISA) docs/isa.md Each instruction is 8 x 32-bit words; everything else is built on it
ISA simulator opentpu/isasim.py (Python) The simulator is the spec; the tests check that it and the RTL produce the same bits
Hardware (RTL) rtl/, starting from rtl/top/otpu_top.sv (SystemVerilog) Becomes a Vivado bitstream that is loaded onto the FPGA card
Host otpu-chat, otpu-smi, otpu-lens Drives the card over PCIe

The README states that the machine is deliberately simple. A sequencer issues one instruction per cycle to a few units: DMA moves data, the matrix unit multiplies int8 weights streamed from DRAM, the vector unit does fp32 math, and a quantizer turns results back into int8. There is no cache and no hidden scheduling. Because every data movement is an instruction, the README says, a trace shows exactly where the cycles go. The kernel example printed in the README is the following; its own comment says that it is simplified and that the original is in kernels/mlp.py. Read from top to bottom, the function loads an input, normalizes and quantizes it, takes dot products against the gate and up weights, combines the two through an activation, takes one more dot product against the down weights, and stores the sum of the input and that result.

from opentpu import language as ol
                    
                    @ol.jit
                    def mlp(h, gamma, w_gate, w_up, w_down, out, eps):   # simplified; see kernels/mlp.py
                        x = ol.load(h)
                        xs = ol.quantize(rmsnorm(x, ol.load(gamma), eps))
                        g = ol.dot(xs, w_gate)
                        u = ol.dot(xs, w_up)
                        a = ol.all_gather(silu(g) * u)
                        y = ol.all_gather(ol.dot(a, w_down))
                        if ol.program_id() == 0:
                            ol.store(out, x + y)

Lens, the profiler, records a run from the RTL, from the simulator or from the card, and opens it in the browser with a roofline, a timeline and per-instruction tables. The README ties this directly to the design choice described above: because every data movement is an instruction, a trace of a run explains its speed. The host commands are summarized in a table in the README as four entries.

  • otpu-chat: Chats with a model. Qwen3-0.6B is the default, and --model selects lfm2 (LFM2.5-230M), qwen35 (Qwen3.5-0.8B), lfm2-2.6b, smollm3, phi4-mini, qwen35-2b or qwen35-4b.
  • otpu-smi: Shows temperature, power, DRAM bandwidth and per-unit utilization.
  • otpu-lens: Records a run and opens it in the profiler.
  • otpu-selftest and otpu-diag: Check that the card works.

The Card and the Build — Inspur YPCB-00338, Kintex-7, Two DDR3 Channels

The hardware on which the measurements were taken is an FPGA card. The results section of the README and docs/board.md describe the setup as follows, covering the card itself, the image loaded onto it, the memory, the host machine, the timing margin and the calibration that runs at start-up.

  • Card: An Inspur YPCB-00338. The FPGA is a Xilinx Kintex-7 xc7k480t (written as xc7k480t-ffg1156-2 in board.md), and it has two DDR3 channels of 2 GiB each, which gives the card 4 GiB of memory.
  • Image: main e698dcd at 133.33 MHz, with one bitstream for all models. It contains LiteDRAM controllers calibrated by a small CPU inside the memory core, a four-column systolic matrix unit and the stream engine.
  • Memory speed: DDR3-1066, with a 17.1 GB/s peak. board.md computes this peak as the sum of two x64 channels, with ECC bits not counted, and writes it as 17.07 GB/s.
  • Host: The card sits in a PC named opentpu (Intel Core i7-4790), and the link is PCIe Gen2 x8 using Xilinx XDMA.
  • Timing: The design closes 133.33 MHz, but in the words of the README only just (WNS +0.032 ns). 133.33 MHz is the clock at which the 128-byte port matches the two DDR3 channels.
  • Calibration: When the image starts, the CPU of the core calibrates both DDR3 channels in 12 seconds, with no host involvement.

Building the bitstream comes with conditions. According to board.md, it requires Vivado 2026.1 with a license that covers the xc7k480t; the free edition does not include this device, so a paid license or the 30-day evaluation license from AMD has to be used. The document says to expect 1.5 to 3 hours for one build. For a reader who wants to repeat the card measurements, this means that a suitable toolchain license, and not only the card, has to be in hand before the first build can start. Another case of putting hardware onto an FPGA in SystemVerilog is covered in Recreating 3dfx Voodoo Graphics and a DOS PC on an FPGA.

The Performance Table — Decode, Prefill, and DRAM for 10 Models in 18 Configurations

The results table in the README lists values for 10 models in 18 configurations. All of them were measured on the card, and the method is tools/qual/perf.py. Decode is 64 greedy tokens generated after a 512-token prompt, with the argmax of the host in the loop (not streamed). The device figure counts only the cycles the accelerator runs, and the wall figure adds the host. Prefill is the speed at which the 512-token prompt is processed on the device. The DRAM traffic comes from the card's own counters while it runs. Each row of the table is therefore one model in one weight format, with two decode figures that differ only in whether host time is included, one prefill figure, and the DRAM bandwidth observed during decode together with its share of the peak.

The dates matter because the production image changed between them, which is what the next point takes up.
  • Difference between builds: Build B decodes LFM2-2.6B, SmolLM3 and Phi-4-mini 8 to 9% faster than e698dcd7 (10% for Gemma 4 E2B), at 91 to 94% of the DRAM peak instead of 82 to 87%. The rows of the table therefore do not all come from a single image.
  • Missing rows: Qwen3.5-4B has only a 4-bit row because its int8 image is over 4 GiB. Gemma 4 E2B does not fit on the card in int8 either. Both gaps in the table come from the 4 GiB of memory on the card.
  • The embedding tables of Gemma 4: E2B keeps its per-layer embedding tables on the card (its images are 3.5 to 3.6 GiB). The table of E4B (2.95 GB) stays on the host, which copies one 11 KB row into the card per token (its image is 3.96 GiB).
  • Bottleneck: Decode is bound by DRAM. As board.md explains it, this is because every token streams all the weights once. The first item under what comes next in the README is also DRAM efficiency. Put differently, the decode speeds in this table follow how fast weights can be read out of memory rather than how fast the arithmetic units can multiply.
  • Scale: The models in the table are small models, ranging from the 230-million-parameter class to the class of a few billion parameters. Phi-4-mini, at 3.8B, decodes at 3.99 tok/s on the device in int8.

The comparison the README makes is a comparison with its own earlier image. Measured the same way as the previous production image se-cand3 (Xilinx MIG, a two-column matrix unit and a 120.755 MHz clock), the decode of the new image is within 2.3% in every configuration, and its prefill is 1.3x (Qwen3.5) to 2.0x (LFM2 4-bit) faster. The README contains no comparison with a GPU or with any other accelerator, so anyone who wants to place these figures next to other hardware has to bring that comparison from elsewhere, under the same prompt length, token count and weight format. The general picture in which decode is bound by bandwidth and prefill by compute is laid out in What Actually Decides Inference Hardware.

What the Token-for-Token Match Refers To — Simulator Versus Card

The first sentence of the results section in the README is that the card produces the same tokens as the simulator, bit for bit. A note under the table narrows this down further: every configuration matches the simulator token for token, per-position and also when run with the resident decode program. The claim is thus about identical output from two executions of the same program, one in software and one on the card, and it is stated for every row of the table rather than for a selected few.

The two things compared in that sentence are the card and the simulator. docs/isa.md calls the ISA document the contract between the compiler, the bit-exact instruction-set simulator and the RTL, and says all three must agree on every bit written to TMEM or DRAM. This is why the README calls the simulator the spec. The match is to be read within the following scope.

  • What it verifies: It verifies that the hardware implementation (the RTL and the card) produces the same result as the specification (the simulator). It is not a claim about the quality or the accuracy of the answers a model gives.
  • What makes it possible: isa.md specifies fp32 arithmetic as IEEE-754 binary32 with round to nearest even and flush to zero, and it defines composite functions as fixed sequences of add and mul so that every implementation is bit exact.
  • A separate comparison: For some models a comparison with the Hugging Face implementation is noted separately. Gemma 4 E2B matches the greedy tokens of Hugging Face on three prompts, and Qwen3.5-35B-A3B matches 16 greedy tokens of Hugging Face. The stated number of prompts and of tokens is the extent of that comparison, and it is a comparison against a reference implementation of the model, which is a different question from whether the card agrees with the simulator.
  • The quality-side figures: The effect of quantization on the output of a model is reported separately, as perplexity, in docs/quant.md.

The contribution rules sit on the same line. Changes to the ISA, the simulator or the RTL must keep python3 -m pytest -q passing, and performance claims should say how they were measured. Both rules guard the same property: a change that would make the card and the simulator diverge is meant to be caught by the tests, and a speed figure is expected to arrive together with the method that produced it.

4-Bit Weights and Models Larger Than 4 GiB — Speed and Its Price

The 4-bit weights use FP4 values with two-level block scales, which comes to 4.25 bits per weight, and the LM head is kept in int8 for accuracy. According to the README, they cut the bytes per token by about a third and raise decode speed by 40% (Qwen3.5) to 45% (Qwen3 and LFM2). In the table this is the rise of the device decode of LFM2.5-230M from 59.0 to 85.8 tok/s and of Qwen3-0.6B from 21.6 to 31.3 tok/s. The price is perplexity: the README calls it a measurable cost and leaves the per-model figures to docs/quant.md. quant.md reports that on Qwen3-0.6B the perplexity of its book sample rises from 23.5 in fp32 and int8 to 28.3 with 4-bit weights (a value measured in simulation). The speed gain and the quality cost are thus reported in two different places, the first in the README table and the second in the quantization document, and the two have to be read together.

With the logits streamed back while the card runs (tools/decode_profile.py, 96 tokens), 4-bit decode is faster. In device / wall tok/s, the figures are 89.5 / 84.5 for LFM2, 33.7 / 33.3 for Qwen3 and 24.6 / 24.2 for Qwen3.5.

Mixture-of-experts (MoE) models bigger than the 4 GiB of the card run with their expert weights streamed from host storage. The card routes each token and computes every expert, and it keeps the experts in per-layer slots in its DRAM. The host only copies missing experts from a pool file into those slots. In this arrangement the card still performs all of the computation, and the host serves as a store from which weights are fetched whenever they are not already on the card. The following values were measured on October 1, 2026 with build B, with the card's own decode loop picking every token, 4-bit experts and an int8 head.

  • LFM2.5-8B-A1B (8.5B parameters, 1.7B active): 10.6 tok/s over 160 tokens. 98.5% of expert uses hit the slots, and 5.2 MB was streamed per token.
  • Qwen3.5-35B-A3B (34.7B parameters, 3.0B active): 3.95 tok/s. 62% of expert uses hit, and 153 MB was streamed per token at 1.41 GB/s over PCIe.
  • Verification: Both models match the simulator bit for bit.

The share of the host is small. For LFM2 and Qwen3 the card runs one decode program compiled once, and the time the host adds per token is 0.17 to 0.30 ms on omarchy, the development PC, and 0.45 to 1.3 ms on opentpu. The README sums this up by saying that the host is nearly out of the way, and it notes one exception: Qwen3.5 runs the same way for decode, but its prefill still compiles the program of each chunk on the host, ahead of the card.

Reproduction Steps and the Predecessor auto-arch-tournament

The README says that everything except the card runs on a laptop. The commands in its section on trying it are the following; they install the package and the test dependencies, run the test suite, download a model and start a chat on the simulator backend.

pip install -e .
                    pip install pytest torch transformers
                    python3 -m pytest -q          # RTL tests also need Verilator 5
                    
                    hf download LiquidAI/LFM2.5-230M --local-dir models/LFM2.5-230M
                    otpu-chat --model lfm2 --backend isa    # chat on the simulator

With a card, the bitstream is built with make bit in boards/ypcb-00338 and loaded over JTAG, after which sudo otpu-setup and otpu-chat --backend board are run. The whole procedure is in docs/board.md. The contributing section says that most of the work needs only Python and Verilator, not an FPGA. The license is the Apache License 2.0, and the README points to the LICENSE file in the repository for its full text.

The README of the predecessor, auto-arch-tournament, introduces that project as an autonomous research loop pointed at a SystemVerilog RV32IM CPU. Each round the agent proposes a microarchitectural hypothesis, implements it in an isolated git worktree, and then runs it through riscv-formal, Verilator cosimulation and 3-seed FPGA place-and-route. Only hypotheses that beat the current champion on CoreMark/MHz get merged. That README states the following about the outcome of one run, about the boundary it draws around the agent, and about what its author concluded from the exercise.

  • Results: 73 hypotheses in 9 hours 51 minutes of wall-clock time. The locked baseline of 301 iter/s (2.23 CoreMark/MHz) became a champion at 577 iter/s (2.91 CoreMark/MHz). Ten hypotheses were accepted, and 63 were rejected by the verifier.
  • What the agent may touch: Only the rtl/ directory and the test/test_*.py files of the target core. The orchestrator is hardcoded, and the model never edits it.
  • The evaluation side is off-limits: If the agent touches formal/, tools/, fpga/ and the like, the path sandbox rejects the round before any evaluation runs. The README puts it this way: the agent does not get to soften its own grader.
  • The author's conclusion: The loop is not the moat, and the artifact that survived 10 wins past 63 rejections was not the agent but the verifier.
  • Agents: Codex CLI is the default, and Claude Code can be used as well.

What the openTPU README says about the predecessor is the single sentence that it brings those lessons to AI accelerators. Whether openTPU was built with the same loop and the same sandbox rules is not written in the README. The account of the predecessor is therefore background on where the project comes from, and it cannot be carried over as an account of how openTPU itself was produced. Its section on what comes next does, however, contain the sentence that a tournament of Vivado runs keeps working on the timing margin and the area. Another case of using LLMs in chip design, and the extent of human involvement there, is covered in Analysis of OpenAI's Jalapeño Chip Using Internal LLMs. The table below sets what the README and the docs state next to what they leave unstated, one item per row.

What Could Not Be Confirmed

  • The division of work between people and agents. No statement about who wrote which part was found in the README, board.md, isa.md or quant.md. The same goes for the names of the agents and models used and for the development period. These are the points on which the tagline invites the most assumptions, and they are the points on which the documents read here are silent.
  • Whether the loop of the predecessor was used as it is. The openTPU README only says that it brings the lessons over. Run records such as a number of hypotheses or a number of rejections could not be confirmed in the openTPU documents.
  • Power. otpu-smi is described as showing power, but the README gives no measured power figure for the card. The Vivado power estimates in board.md are for earlier builds and carry the qualifier low confidence, so they were not carried over.
  • Comparison with other hardware. The README has no figures that set the same models against a GPU, a CPU or another accelerator. The only comparison it does make is the one against its own earlier image, described above in the section on the performance table.
  • Per-model quality figures. The full per-model perplexity tables in quant.md, and any evaluation of the output quality of the models in the table, were not carried over. Only the single value for Qwen3-0.6B is cited.
  • How to obtain the card, and its price. Neither is stated in the README or in board.md.
