进程无声无息地死了 - 读懂 OOM Killer

应用日志一片空白时，从内核留下的记录里挑出真凶的顺序

2026-09-02 开发/基础设施

进程不见了。应用日志的最后一行是一条再普通不过的请求处理记录，之后什么都没有。没有异常堆栈，也没有关闭钩子留下的告别语。监控工具只告诉你这个进程已经不存在了。

此时被浪费得最多的时间，都花在把应用日志再翻得更细一些上。那里没有，也不可能有。SIGKILL 不是进程接收并处理的信号，而是把进程就地终结的动作，所以在那一刻应用连一个字都来不及写。因此第一步不是继续挖日志，而是换掉假设。它不是死了，而是被杀了。

本文写作环境是 Windows 10 加 Git Bash（MSYS2，GNU bash 5.2.37(1)-release）。这里没有 Linux 内核、没有 cgroup、也没有 dmesg，所以下面出现的内核行为、字段定义、文件路径，全部是在 kernel.org 官方文档和内核源码中确认的，而不是复现真实 OOM 日志贴上来的。在这个环境里真正执行并确认过的只有退出码规则一项，其输出原样附在正文里。确认到什么、没能确认什么，边界都收在倒数第二节。

应用日志为什么什么都不说

内核内存管理文档这样描述 OOM Killer：在负载很高的机器上内存可能被耗尽，内核回收不到足以继续运行的内存，为了保住系统的其余部分，内核会调用 OOM Killer。文档接着写道，它会为了整体系统的健康而挑选一个任务来牺牲。要紧的是那个「挑选」。选择发生在内核这一侧，被选中的一方不会收到通知。

于是应用平时会留下的东西整块消失。异常堆栈要有异常才会产生，可异常并没有发生。关闭钩子要能捕获信号才会运转，而 SIGKILL 捕获不到。还留在缓冲区里的日志没被刷盘就没了。最后一行日志看起来很普通，这件事本身就是信号，而不是说没有信息。

  • 不会留下的 — 异常堆栈、关闭钩子运行过的痕迹、未刷盘的日志缓冲、应用自己记录的退出码
  • 会留下的 — 内核环形缓冲区里的 OOM 记录、父进程收到的退出状态、容器运行时贴上的终止原因、指标采集器最后一次抓到的值
  • 顺序反过来了 — 平时应用日志是一手资料、内核日志是辅助。在这类事件里正好相反
  • 指标断掉的那个点是线索 — 采集周期是 15 秒，那么死前 15 秒内的值就没有。最后一个点看着平稳，中间也可能有过陡增

不是死了而是被杀了 - 137 与 OOMKilled

切换假设的依据是退出码。当命令因致命信号结束时，shell 会把 128 加上信号编号作为退出状态报告出来。这条规则在非 Linux 环境下只要 shell 相同也照样成立，所以在本文写作用的 Git Bash 里可以直接确认。

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

$ bash -c 'kill -9 $$'; echo "exit=$?"
/usr/bin/bash: line 1:  1419 Killed                  bash -c 'kill -9 $$'
exit=137

$ bash -c 'kill -15 $$'; echo "term_exit=$?"
Terminated
term_exit=143

9 号是 SIGKILL，所以 128 加 9 得 137；15 号是 SIGTERM，所以是 143。需要点明的是137 能告诉你的范围比想象中窄。它只说到「被强制终止了」为止。是谁发的 SIGKILL，并不包含在这个数字里。可能是内核的 OOM Killer，可能是超过终止宽限期后编排系统补发的，也可能是某个批处理脚本。

信号编号shell 报告的退出码这个码能告诉你什么
SIGTERM15143有过收尾的机会。它做了什么会留在应用日志里
SIGKILL9137立即终止。发送方只能靠比对内核日志才知道
SIGSEGV11139非法内存访问。和内存不足是两回事
SIGABRT6134运行时自己放弃了。把分配失败当作 abort 处理的实现会出这个
正常退出-0 ~ 125应用自己决定的值。不是强制终止

信号编号遵循各平台的信号表。上面的 6、9、11、15 在 Linux 上是稳定一致的，但并非所有编号都如此。在本文写作用的 MSYS 环境里执行 kill -l，7 号显示为 SIGEMT，而在 Linux x86 上 7 号是 SIGBUS。与其背编号，不如把那台机器的表打出来看一遍更稳妥。

在容器里还会多贴一个标签。运行时把终止原因记为 OOMKilled，编排系统再把它暴露到 Pod 状态上。这比退出码明确，但它仍然不告诉你是哪一种 OOM。整个节点耗尽和容器撞到自己的上限，会顶着同一个标签出现。

另外，Kubernetes 文档指出内存上限是被动式强制的。容器用超上限时内核可能终止它，但终止只在内核检测到内存压力时才发生，因此超额分配的容器未必会被立刻杀掉。「昨天也超了上限，为什么今天才死」的答案就在这里。

该看哪里

内核写入的地方只有一个，但读它的窗口有好几个，而且每个窗口的保留时长不同。正是这个差别，让「没有记录」这个结论经常出错。

# 1) 内核环形缓冲区 - 最快，但留不久
dmesg -T | grep -i -E 'out of memory|oom-killer|killed process'

# 2) journal - 只看内核消息，并收窄时间范围
journalctl -k --since '2 hours ago' | grep -i -E 'oom|killed process'

# 3) 中间发生过重启就按引导次数往回翻
journalctl --list-boots
journalctl -k -b -1 | grep -i 'killed process'

# 4) 环形缓冲区已经滚掉时 - 路径因发行版而异
grep -i -E 'oom-killer|killed process' /var/log/messages
grep -i -E 'oom-killer|killed process' /var/log/syslog

dmesg 看的环形缓冲区大小固定，新消息进来就把最旧的挤出去。如果节点上存储或网络相关消息每秒能刷好几行，那几小时前的 OOM 记录早就没了。「dmesg 里没有所以不是 OOM」这个结论，只有在确认过环形缓冲区没有滚掉之后才成立。journal 那边同理，存储方式若是易失的，重启就一起消失。日志到底能留多久本身是另一个题目，轮转配置造成的坑在日志轮转悄悄出错的地方里另行讨论。

容器这一侧的窗口握在运行时和编排系统手里。很多时候你并没有访问内核日志的权限，所以这边反而更先够得着。

# Kubernetes - 上一次终止的原因和退出码
kubectl describe pod <pod> | sed -n '/Last State/,/Restart Count/p'
kubectl get pod <pod> -o jsonpath='{range .status.containerStatuses[*]}{.name}{"\t"}{.lastState.terminated.reason}{"\t"}{.lastState.terminated.exitCode}{"\n"}{end}'

# Docker - 把 OOMKilled 标志和退出码打在一行
docker inspect --format '{{.Name}} oom={{.State.OOMKilled}} exit={{.State.ExitCode}}' <container>

# 如果能登上节点，就把时刻和内核那边对齐
journalctl -k --since '2026-09-02 09:00' --until '2026-09-02 10:00'

第一个岔路口就出现在这里。容器状态是 OOMKilled，但节点的内核日志里没有系统 OOM 记录，那就说明节点是好好的，事件属于 cgroup 上限那一侧。反过来，如果同一时刻多个 Pod 一起死，而且内核日志里留下了整个节点的内存转储，那就是节点这一侧。没过这个岔路口就去调上限或扩容节点，等于抛硬币。

内核打印的那张表怎么读

内核在执行 OOM 终止时会把任务列表以表格形式转储出来，这个行为由 sysctl 开关控制。内核 sysctl 文档写道，oom_dump_tasks 会生成一份排除内核线程的全系统任务转储，并包含 pid、uid、tgid、vm size、rss、pgtables_bytes、swapents、oom_score_adj 分数、name 之类的信息。内核源码里打印表头的那个函数也清楚显示，这份转储挂在该 sysctl 值上。

真正落到日志里的字符串是三块。下面是从内核源码里原样抄来的格式字符串，输出时会把实际值填进 %s 或 %d 的位置。

# (1) 谁调用了 OOM Killer - dump_header()
%s invoked oom-killer: gfp_mask=%#x(%pGg), order=%d, oom_score_adj=%d

# (2) 候选列表的列名 - dump_tasks()
[  pid  ]   uid  tgid total_vm      rss rss_anon rss_file rss_shmem pgtables_bytes swapents oom_score_adj name

# (3) 结论 - __oom_kill_process()
%s: Killed process %d (%s) total-vm:%lukB, anon-rss:%lukB, file-rss:%lukB, shmem-rss:%lukB, UID:%u pgtables:%lukB oom_score_adj:%d

大多数人只读 (3) 就收工。可 (3) 是结论，原因候选名单在 (2) 下面接着的那张表里。不看表就答不出「为什么是那个进程」，答不出来，下次还会再来一遍。

列单位是什么挑真凶时的用处
total_vm页虚拟地址空间大小参考价值低。包含了只预留而未使用的区域
rss页实际驻留在物理内存里的总量从这里开始。按降序排一遍，候选就收窄了
rss_anon页没有文件背景的部分，即堆和栈怀疑泄漏时的头号目标。只能靠交换分区回收
rss_file页映射的文件页大多可回收。只有这一列大的进程多半不是真凶
rss_shmem页tmpfs 与共享内存/dev/shm 的用量。看着像文件却不会被回收
pgtables_bytes字节页表本身占用的内存线程多或者映射被切得很碎时会变大
swapents页已换出到交换分区的页数有交换分区时 rss 会显得偏小，要一起看
oom_score_adj无作用于选择的权重死掉的进程如果不是 rss 第一名，答案就在这一列
name无可执行文件名太长会被截断。同名有多个时要用 pid 比对

读的时候容易出错的地方有两处。一是单位是页。只有名字里带 _bytes 的 pgtables_bytes 是字节，其余内存列都是页数。页大小随架构和配置而异，所以要先确认那台机器的值再去乘。二是列的构成随内核版本而异。上面 sysctl 文档给的清单和当前源码里的表头字符串已经对不上了（源码那边多了 rss_anon、rss_file、rss_shmem）。必须先读自己日志里的表头行，再把列位置对齐。

# 从存下来的日志里只抽出表格部分
# 列号随内核版本不同，所以务必把表头行一起打出来
awk '/\[ *pid *\]/{print; f=1; next} f && /^\[/{print} f && !/^\[/{f=0}' oom.log | head -40

# 先在表头里数清 rss 是第几列再排序（下面假定是第 4 列）
awk '/^\[/{print $4, $NF, $0}' oom.log | sort -nr | head -20

为什么偏偏是那个进程死了

内核给每个候选打 badness 分，挑最高的那个。在当前源码里，这个计算从把 RSS、交换条目数，以及折算成页单位的页表大小相加开始。可以理解成对「现在结束掉这个进程能拿回多少页」的估计值。之后再加上 oom_score_adj，而且不是直接加，是先乘以总页数除以 1000 的结果再加。

这个乘法在实操上很关键。oom_score_adj 每 1 分折算成总内存百分之零点一所对应的页数，所以把这个值调到 100 的进程，会被当作多占了总内存的百分之十来对待。放在 128GiB 的节点上就相当于多占 13GiB。「占内存最多的进程会死」并不总成立，算术上的理由就在这里。

按内核文档，这个值的范围是 -1000 到 +1000。文档对最低值 -1000 的说法是，它实际上等于关闭该任务的 OOM 终止，因为它会始终报告 badness 分数为 0。文档还写明，通过 /proc/<pid>/oom_score 暴露出来的值已经包含了这个权重，所以实际范围是 0 到 2000。

# 某个进程当前的分数和权重
cat /proc/<pid>/oom_score
cat /proc/<pid>/oom_score_adj

# 只挑出权重不为 0 的进程扫一遍（看看是谁动过手）
for p in /proc/[0-9]*; do
  a=$(cat "$p/oom_score_adj" 2>/dev/null) || continue
  [ "$a" = "0" ] && continue
  printf '%s\t%s\t%s\n' "${p#/proc/}" "$a" "$(tr -d '\0' < "$p/comm")"
done
  • 内核是以线程组而不是单个线程为单位来看的。表里之所以有 tgid 列就是这个缘故
  • 监控代理和 sidecar 通常分数很低，因为它们占内存少。所以死的是主体，而主体死了之后代理还活着，向你报告「进程不存在」
  • 反过来也有给 sidecar 调高了权重之后忘掉的情况。占得少得多却先死，就该怀疑这一列
  • 编排系统有时会按工作负载等级自动设定这个值。就算你没动过，它也可能不是 0
风险提示。把 oom_score_adj 调到 -1000，是把那个进程从候选池里移出去，而不是给它更多内存。短缺依旧存在，只是换成别的东西去死。把数据库豁免掉，旁边的监控代理就会死，而监控代理一死，就没人来告诉你出了故障。豁免不是处置，而是改变死亡的先后顺序，所以这是要先想清楚「什么可以替它去死」之后才动的值。

系统 OOM 与 cgroup OOM 是两件事

内核源码里把这两者分开的地方只有一行。调用 OOM 处理函数时用三元运算符挑选消息字符串，若不是内存 cgroup 的 OOM 就传 "Out of memory"，是的话就传 "Memory cgroup out of memory"。这个字符串会进到上一节 (3) 号格式最前面的 %s 位置。日志的第一个词就告诉你事件属于哪一类。

项目系统（节点）OOMcgroup OOM
触发整个节点范围内回收失败该 cgroup 撞到了自己的上限
日志开头Out of memory: Killed process ...Memory cgroup out of memory: Killed process ...
候选范围节点上的所有进程该 cgroup 及其子层
节点的余量没有。所以才发生了这件事可能还很宽裕。看板上一片平静
连带受影响的无关的工作负载也跟着晃只有那个容器死
常见误诊一口咬定是应用泄漏去扩容节点
先看哪里/proc/meminfo、内核日志里的内存转储memory.events、memory.max、memory.current

内核 cgroup v2 文档把 memory.max 定义为内存用量的硬上限，并写道当 cgroup 的用量达到该上限且无法减少时，就会在该 cgroup 内部调用 OOM Killer。memory.high 则不同。用量越过 high 边界时该 cgroup 的进程会被限流并承受强烈的回收压力，但越过 high 上限绝不会调用 OOM Killer，同一份文档如此写道。high 是刹车，max 是墙。

# 在容器内部 - cgroup v2
cat /sys/fs/cgroup/memory.max        # 墙。显示 max 表示没有上限
cat /sys/fs/cgroup/memory.high       # 刹车
cat /sys/fs/cgroup/memory.current    # 现在用了多少
cat /sys/fs/cgroup/memory.events     # 在这里看 low/high/max/oom/oom_kill
cat /sys/fs/cgroup/memory.stat | head -20

# 从节点上指定某个具体 cgroup 路径时
cat /sys/fs/cgroup/kubepods.slice/.../memory.events

memory.events 里的两个值含义不同，而这个差别起到了预报作用。文档把 oom 定义为该 cgroup 的用量达到上限、分配即将失败的次数，把 oom_kill 定义为属于该 cgroup 的进程被任何形式的 OOM Killer 杀掉的次数。也就是说 oom 在涨而 oom_kill 还是 0，意味着还没有人死，而这是下一次发布或下一个流量高峰就会死的预告。把这个值挂到告警上，就能在事前而不是事后动手。

同一份文档里还有 memory.oom.group。它决定 OOM Killer 是否把这个 cgroup 当作不可分割的单一工作负载，设上之后，该 cgroup 及其子层的所有任务要么一起死、要么都不死。这是防止只死掉一个进程、其余的以半残状态继续运转的开关。

运行时自身如何感知内存上限，那是另一个层次的问题。像 JVM 这种从容器上限推断堆大小的运行时有其特有的坑，那部分在容器里的 JVM 误读上限时另行讨论。本文只看内核和 cgroup 这一侧的通则。

cgroup v1 与 v2 的差别

同样一句「内存上限 512Mi」，在两个版本里可能指的不是一回事。文件名就不一样，交换分区的计法也不一样。

# 正跑在哪个版本上 - 只显示 cgroup2fs 表示纯 v2
stat -fc %T /sys/fs/cgroup
mount | grep -E 'cgroup|cgroup2'

# v1 这一侧要看的文件
cat /sys/fs/cgroup/memory/memory.limit_in_bytes
cat /sys/fs/cgroup/memory/memory.usage_in_bytes
cat /sys/fs/cgroup/memory/memory.failcnt
cat /sys/fs/cgroup/memory/memory.memsw.limit_in_bytes
cat /sys/fs/cgroup/memory/memory.oom_control
grep -E '^(cache|rss|mapped_file) ' /sys/fs/cgroup/memory/memory.stat
  • 交换分区的计法。v1 用 memory.memsw.limit_in_bytes 把内存和交换分区合在一起设上限。v2 用 memory.swap.max 单独设。这是同一个数字含义会变的典型位置
  • 用量数值的准确度。v1 文档自己承认 memory.usage_in_bytes 给出的不是精确值，并建议想看得更准就用 memory.stat 里的 RSS 和 CACHE（以及 SWAP）
  • 失败次数计数器。v1 的 memory.failcnt 统计撞上限的次数。在 v2 里顶替这个位置的是 memory.events
  • 撞上限时的流程骨架相同。v1 文档写道，cgroup 超出上限时会先尝试从该 cgroup 回收内存，回收不成功就调用 OOM 例程，挑出个头最大的任务杀掉
  • 关闭 OOM 终止的开关。v1 的 memory.oom_control 里有 oom_kill_disable 和 under_oom。文档写道，under_oom 为 1 时该 cgroup 处于 OOM 状态，而且任务可能被停住
风险提示。打开 v1 的 oom_kill_disable，换来的不是不死，而是停住。进程还在列表里活着，视健康检查的类型甚至可能通过，却一个请求也处理不了。多数时候死掉并被重启反而更好，所以只有在你另有手段能察觉那种状态时才考虑这个值。

内存超额分配 - malloc 成功了也照样死

Linux 默认承诺的内存多于它实际拥有的，因为多数情况下这样做更划算。fork 之后紧接着 exec 的进程几乎不会用到复制来的地址空间，先申请一大块数组却只用前面一小段的代码也很常见。物理页是在首次写入该地址时才挂上去的。

所以失败来得晚。分配函数成功拿到了地址空间，而死亡发生在首次写入那个地址的瞬间。落到代码上看，就是在成功的分配的下一行死掉。分配失败的处理写得再细密也走不到那条路径，原因就在这里。

vm.overcommit_memory内核文档的说法实际发生的事副作用
0（默认）内核把用户态的申请大小与总内存加交换分区之和作比较，拒绝明显的超额申请一般的申请都能过失败不在分配时刻而在使用时刻以 OOM 的形式出现
1在真正耗尽之前，内核一直假装内存永远够用几乎所有申请都成功分配失败这个信号消失，所有问题都收敛成 OOM
2采用试图阻止任何超额分配的绝不超额策略超过 CommitLimit 的承诺本身就被拒绝此前一直成功的分配开始失败

超额分配记账文档把 2 号模式的上限说明为交换分区加上物理 RAM 的一个可配置比例（默认百分之五十）。这个比例用 vm.overcommit_ratio 设定，绝对值用 vm.overcommit_kbytes 设定，两者都只在 2 号模式下生效。文档还写道，当前的上限和已承诺量可以在 /proc/meminfo 的 CommitLimit 与 Committed_AS 中查看。

sysctl vm.overcommit_memory vm.overcommit_ratio vm.overcommit_kbytes

# 现在承诺了多少 - 看 Committed_AS 贴 CommitLimit 贴到什么程度
grep -E '^(MemTotal|SwapTotal|CommitLimit|Committed_AS):' /proc/meminfo

按文档，Committed_AS 是系统当前已分配的内存量，即各进程已分配内存之和，并附有一条说明：即便它们尚未真正使用也计算在内。因此这个值远超 MemTotal 是正常的，而且正是超额分配在起作用的证据。它不是一个该当成问题看的数字。

风险提示。把 vm.overcommit_memory 改成 2，OOM 会被分配失败取代。那些预留很大却只用一点点的进程可能连启动都启动不起来。在生产节点上用 sysctl 立即改动，等于同时摇动所有服务，所以要先把 Committed_AS 与 CommitLimit 的日常走势测上几天，并在预发环境确认能正常启动之后再做。

交换分区改变了什么

有交换分区，内核就多了一处可回收的地方。匿名页可以被推到存储设备上、腾出的位置再拿来用，所以 OOM 来得更晚。代价是那一段时间会变慢。而这个「慢」是不是比死掉更好，取决于服务的性质。

内核 PSI 文档把这个状态拆成两行来展示。some 是至少有部分任务因该资源而停滞的时间占比，full 是所有非空闲任务同时停滞的时间占比。文档把 full 状态描述为被浪费掉的 CPU 周期，并说它指向抖动。full 在往上走，就说明那个节点只是还没死而已，其实已经不在干活了。

swapon --show
free -h
grep -E '^(SwapTotal|SwapFree|SwapCached):' /proc/meminfo

# 当前停滞的比例 - some 和 full 分开看
cat /proc/pressure/memory
cat /sys/fs/cgroup/memory.pressure

# 哪些进程被换出去了
grep -H VmSwap /proc/[0-9]*/status | sort -t: -k3 -n -r | head -10

容器环境里关掉交换分区的惯例，背后是这样一层考虑：有些服务的响应延迟比死掉更糟。要 30 秒才回来的响应其实已经是失败了，可进程还活着、健康检查照样通过，于是流量继续涌入、状态进一步恶化。这种情况下快点死、快点重启对整体可用性更有利。

  • Kubernetes 文档写明，默认情况下 kubelet 不会在开启了交换分区的 Linux 节点上启动。要让它启动就必须显式设置 failSwapOn: false
  • 交换行为由 memorySwap.swapBehavior 决定。默认的 NoSwap 下，以 Pod 形式运行在该节点上的工作负载既不使用也不能使用交换分区；LimitedSwap 下则可以使用
  • 同一份文档里有一条值得留意的线索。即便设成 NoSwap 并容忍交换分区，不受 Kubernetes 管理的进程，也就是 systemd 服务乃至 kubelet 自身，仍然可以使用交换分区。节点的交换用量不为 0，并不代表就是 Pod 在用
  • kubelet 通过容器运行时 API 下达配置，文档为 cgroup v2 的情形举的例子正是 memory.swap.max。这与上一节的文件直接衔接
  • 如果决定开启交换分区，先把延迟的容忍边界定下来。不定下来，「不死但一直很慢」的状态就会常态化，而这种状态很难触发告警
风险提示。在生产节点上执行 swapoff -a，是把换出去的页全部读回物理内存的动作。若那一刻的物理余量小于交换用量，就会当场引发 OOM。关闭之前先确认 SwapTotal 减去 SwapFree 的值能装进 MemAvailable，并在流量低谷时段一块一块地关。

RSS 不是全部

看内存时最常被读错的值是 free 的 free 那一列。free 手册把 free 仅定义为未被使用的内存，并把 used 计算为total 减去 available。内核这一侧与那个 available 对应的是 /proc/meminfo 的 MemAvailable，内核文档把它定义为在不发生交换的情况下，可用于启动新应用的内存量的估计值，并说明它由 MemFree、SReclaimable、文件 LRU 列表的大小以及各 zone 的 low watermark 计算而来。该看的值是 available，不是 free。

free -h
grep -E '^(MemTotal|MemFree|MemAvailable|Buffers|Cached|Shmem|Slab|SReclaimable|SUnreclaim):' /proc/meminfo

# 单个进程的明细 - VmRSS 是下面三项之和
grep -E '^(VmRSS|RssAnon|RssFile|RssShmem|VmSwap):' /proc/<pid>/status

# 看着像文件其实是内存的地方
df -h /dev/shm
  • 页缓存不是被锁住的内存。需要时就会被回收。缓存大导致 free 看着小是正常的，把这种状态当成内存不足报上去，只会去修错地方
  • 共享内存和 tmpfs 是另一回事。堆在 /dev/shm 里的东西看着像文件，实际是内存，也不会像缓存那样被回收。内核文档把 Shmem 定义为共享内存和 tmpfs 所占用的总量
  • 内核 slab 也占内存。SReclaimable 是可能被回收的部分，SUnreclaim 是在内存压力下也回收不了的部分。后者涨得厉害的话，在用户态怎么翻都翻不出答案
  • RSS 不能相加。按内核文档，VmRSS 是 RssAnon、RssFile、RssShmem 之和，而像共享库这种多个进程共用的页会被逐个进程重复计入。把各进程的 RSS 相加去估算节点用量，得到的数会比实际大
  • 攥着文件的进程同样计入内存。要找出那些握着已删除却仍打开的文件、或握着大块映射的进程，方法整理在哪个进程占着这个文件里

OOM 是症状，不是原因

OOM 终止只告诉你内存不够了，不告诉你为什么不够。而为什么不够，不在死亡那一刻的快照里，而在它前面那一段的形状里。死亡时点的数值已经全都涨大了，因和果分不出来。症状只有一个而原因有好几种、必须按顺序切分，从这一点上说，它和磁盘没满却报 No space left on device 是同一类问题。

  • 泄漏 — 随时间线性上涨。重启之后仍以相同的斜率重新上涨。连没有流量的凌晨都在涨，那基本可以确定
  • 请求激增 — 呈阶梯上涨，时刻与流量曲线重合。高峰过去就会回落。不回落就说明激增和泄漏叠在了一起
  • 上限配错 — 从发布之后立刻开始。把上一次发布的清单并排放着看，几分钟就能了结，所以在顺序上放在前面
  • 没有上限的缓存 — 命中率一路走好、内存一路往上。低负载时看不出来，负载一上来就一次性炸掉。先看内存缓存有没有设最大条目数或最大字节数
  • 结果集变大 — 没有分页的查询、按行反复读取关联数据而膨胀的列表。代码没改却某天忽然炸掉的多半属于这一类，而且斜率平缓，很容易被漏掉
  • 并发数值 — 每请求缓冲区大小乘以并发请求数。调高工作线程数或连接池的第二天就炸。这一项要到配置变更记录里找，而不是发布记录
  • 邻居 — 明明是系统 OOM，却选中了自己的进程。原因是同一节点上别的工作负载，自己这边只是块头大而已，所以自己的代码怎么看都看不出东西
  • 节点上的其他消费者 — 日志采集守护进程、备份代理、内核 slab 这类不是容器的东西。Pod 用量之和与节点用量拉开很大差距时就属于这一种

如果只能挑一样对切分最有用的，那就是斜率的形状。是直线、阶梯还是锯齿，光看这个就能筛掉一半候选。所以事后复盘时最该先拿到手的不是日志，而是死亡前几个小时的内存时间序列。没有它，调查就变成了猜测。

怎么防 - 上限与请求，以及重启循环

设上限是必要的，但只有上限还不够。调度器是看请求值来决定放置的，请求值缺失或者远小于实际，就会在一个节点上发生过密放置。于是各容器的上限都守住了，整个节点却先塌了。Kubernetes 文档写道，节点资源耗尽时会先驱逐 BestEffort 的 Pod，其次是 Burstable，最后才是 Guaranteed。请求和上限写成什么样，就决定了驱逐的顺序。

  • 上限和请求一起设。只有上限，调度器就不知道实际消耗；只有请求，就挡不住失控
  • 请求值从平时用量出发，上限从峰值加余量出发。把两者设成相同会提升等级，但节点利用率会下降
  • 调高上限是买时间。若是泄漏，只会把周期拉长。决定要买，就把买到什么时候写进工单。不写，那个上限就会变成永久的
  • 没有 readiness，重启刚结束那一刻最危险。流量会打进还在预热的实例，那份负载又会把内存顶上去
  • liveness 过于激进，就会混进不是 OOM 的死亡。把短暂卡顿当成死亡而触发重启，这条路径走的是 SIGTERM，所以退出码是 143。137 和 143 混在一起，说明你把两件事当成了一件
  • 超过终止宽限期，143 就变成 137。同样是 137，如果内核日志里那个时刻没有 OOM 记录，那就属于这一种
  • 增加副本这一招要看原因。属于请求可以分散的类型就有效；若结构是每个实例都多出一份同样大小的缓存，节点总量反而会上升
  • 多进程容器要考虑 memory.oom.group。只死一个而其余还在，容器就成了活着但功能残缺的状态，这种状态靠重启也理不干净

蔓延成重启循环的顺序大致是这样：死掉，重启，预热期间一口气接下积压的请求，再死掉。编排系统会逐步拉长重启间隔，所以最初几分钟是连着死，之后转为断续地死。一旦把后半段叫作「偶发故障」，就离原因越来越远。先确认重启间隔是不是呈指数拉长的形状，是不是同一件事马上就分得清了。

风险提示。干脆去掉内存上限，并不是消除问题，而是把 cgroup OOM 升格成系统 OOM。有上限时，死的对象被限定在那个容器；去掉上限，内核就会在整个节点范围内挑候选。到那时挑中谁不由我们决定，无关的工作负载也会跟着一起晃。

排查顺序

之所以要定下顺序，是因为每一步都会收窄下一步。跳过前面的，后面的就算看了也解读不出来。

  1. 确认它真的死了。退出码是 137、143，还是 0 到 125 之间？是容器就把上一次终止的原因和退出码一起看。这里若出现 143 或正常退出，OOM 的调查就收摊
  2. 确认是不是内核杀的。同一时刻内核日志里有没有 OOM 记录？没有就先确认环形缓冲区是不是滚掉了，没滚掉就说明不是内核，而是编排系统、监控程序或人
  3. 分清是系统还是 cgroup。日志开头是 Out of memory 还是 Memory cgroup out of memory？容器这一侧则看 memory.events 的 oom_kill 有没有增加。应对方向在这一步就完全分岔
  4. 看是谁涨了。把内核留下的表按 rss 排序。死掉的进程如果不是第一名，就看 oom_score_adj 那一列；如果确实是第一名，就分开看 rss_anon 和 rss_shmem 的占比
  5. 看是从什么时候开始涨的。拿到死亡前几个小时的时间序列。是直线、阶梯还是锯齿，在这一步定下来
  6. 对照为什么涨。把发布时刻、配置变更记录、流量曲线、数据增长量叠到那条时间序列上。只有一项重合基本就是答案；一项都没有，就往下一层看缓存上限、结果集大小和并发数
  7. 决定改什么。调高上限是最后的选项。在它前面还有缓存上限、分页大小、工作线程数和连接池。如果决定要调，就把这个状态要保持多久一并写下来

小结

应用日志一片空白，不是说没有信息，而是说记录的主体换人了。SIGKILL 捕获不到，应用什么都写不了，这件事被留在了内核那一侧。所以调查的起点不是把应用日志挖得更深，而是确认退出码之后转向内核日志。

转过去之后的岔路口只有一个。是节点不够了，还是撞上限了？日志的第一个词会告诉你，而应对方式从这里开始就完全不同。对节点的问题去动上限，或者对上限的问题去扩容节点，两者都改变不了任何事情。而且不论哪一种，OOM 本身都不是原因。原因在死亡前几个小时的斜率里，而那条斜率在事件结束之后就拿不到了。所以该留下的不是命令清单，而是顺序：是不是真死了、是不是内核杀的、是系统还是 cgroup、谁涨了、从什么时候开始、为什么。把这六步按顺序走完，最后那个问题通常只剩下一个答案。

未能确认的部分

  • 本文写作环境是 Windows 10 加 Git Bash（MSYS2，GNU bash 5.2.37(1)-release），没有 Linux 内核。dmesg、journalctl、/proc/meminfo、/sys/fs/cgroup 的真实输出并未复现并贴出。正文里的命令都是依据官方文档和内核源码写下的
  • 实际执行并确认过的恰好是三项：bash -c 'kill -9 $$' 的退出状态是 137、kill -15 是 143、shell 版本是 GNU bash 5.2.37(1)-release。只有这三项作为真实结果出现在正文的输出块里
  • 内核文档（docs.kernel.org）是直接打开确认的，但内核源码原文因 git.kernel.org 返回 403 而无法打开。格式字符串和 badness 计算是在官方镜像 raw.githubusercontent.com/torvalds/linux 的 master 分支上确认的，并不是某个特定发行版内核的代码
  • dump_tasks 的列构成随内核版本而异。sysctl 文档给的清单和 master 源码里的表头字符串已经对不上。必须直接确认自己内核的表头行
  • badness 计算所用的函数名在各版本间变动过，因此没有照搬函数名，只写了它的构成以及 oom_score_adj 的折算方式。具体实现需要按内核版本各自确认
  • 日志文件路径随发行版和日志守护进程配置而异。/var/log/messages 与 /var/log/syslog 究竟哪一个在用，未能确认
  • 容器运行时贴上退出码 137 的确切规则未能在官方文档中确认。128 加信号编号是 shell 的规则，是在本环境里确认的，而运行时是否遵循同一规则，没有找到文档依据。Bash 手册的相关条款也因 gnu.org 以速率限制拒绝响应而未能打开原文
  • Kubernetes 的 QoS 文档只说明驱逐顺序，并未提及如何按等级设定 oom_score_adj。这也是正文里只写到「编排系统有时会设定」为止的原因。像 systemd-oomd 这类跑在用户态的 OOM 管理器同样不在本文范围内
