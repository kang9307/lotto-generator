2026-09-08 開発・インフラ

圧縮器を変えるという決定は、たいてい一行の数字で下される。同じファイルが30パーセント小さくなるという文で十分に見える。その数字は真かもしれない。問題は、それが決定に必要な情報の五つのうち一つでしかないことだ。

圧縮器は一つの軸を得れば別の軸を差し出す。圧縮率を上げれば圧縮時間が伸び、展開まで遅くなる方式もあれば展開だけは守る方式もある。ブロックを大きくすれば圧縮率は上がるが、解く側のメモリ要求がその分だけ大きくなる。しかもその要求は圧縮する瞬間に確定してファイルの中に刻まれる。後から取り消すことはできない。

軸はもう一つある。その形式を読む道具が相手の手にあるか。これはアルゴリズムの性質ではなく生態系の状態であり、長期保存においては前の四つを合わせたよりも重い。

きっかけ - 三つの形容詞が一文に入るとき

BZip3 リポジトリの最初の一文は、自らを bzip2 のより良く、より速く、より強力な精神的後継作と紹介する。圧縮を長く触ってきた側なら、この一文をまず分けて読む。より良いとは圧縮率であり、より速いとは圧縮速度か展開速度かで分かれ、より強力とはたいてい大きなブロックと複数スレッドを指す。三つの形容詞はそれぞれ別の軸で真であり、それぞれ別の条件でだけ真である。

ここで取る角度はツール紹介ではない。一つの後継作がどの軸を得てどの軸を差し出したかを追いながら、圧縮器を選ぶという決定が実際には何と何を交換する行為なのかを立てることだ。圧縮率と予測精度がなぜ同じ値なのかという理論側の問いは別に扱ったことがある。ここで扱うのはその理論ではなく選択である。

圧縮器が争う三つの軸、その後ろに付く二つ

まず三つの軸がある。圧縮率、圧縮速度、展開速度である。この三つは互いに貼り付いてはいない。圧縮率を上げるにはより精緻なモデルが要り、モデルが精緻になれば圧縮は遅くなるが、展開側は方式によって一緒に遅くなることもほぼそのままのこともある。LZ 系は展開が圧縮よりずっと安い。辞書を作り直す必要がなく、指示されたとおりに複写するだけだからだ。文脈モデル系は圧縮と展開が同じモデルを同じ順で回さねばならず、両方向が対称に近い。

ここに二つの軸が付く。メモリ使用量と並列性である。この二つは長く副次的なものとして扱われてきたが、いま実務で決定をひっくり返すのはむしろこちらだ。コンテナのメモリ上限、CI ランナーのコア数、復旧メディアの搭載メモリが、圧縮率の数パーセントより先に効いてくる。

非対称性という基本性質

ほとんどの可逆圧縮器は展開が圧縮より速い。1994年の原論文も結論で、自らのアルゴリズムがレンペル・ジフ系と同様に圧縮より展開が速いと記す。この非対称は実務で大きな意味を持つ。配布物は一度圧縮されて何千回も解かれる。したがって配布において圧縮時間はほぼ費用ではなく、展開時間と展開メモリだけが費用である。逆に毎日回るバックアップは圧縮時間がそのまま作業窓を食う。

1994年の論文はすでにそのトレードオフを表にしていた

ブロックソート圧縮の原典は、マイケル・バロウズとデビッド・ウィーラーが1994年5月10日にディジタル・イクイップメントのシステム研究センターで出した SRC 研究報告 124 である。論文は、この変換が著者の一人であるウィーラーによって1983年にベル研究所で発見されたが、それまで発表されていなかったと記す。

この論文の本当の価値は、変換そのものよりも表3にある。同じハードウェアで同じ14ファイルを四つの方式で圧縮した結果だ。

表の読み方はこうだ。compress はブロックソートより五倍速いが結果が45パーセント大きい。反対の端の comp-2 は圧縮に12倍、展開に65倍の CPU を使いながら、平均の文字あたりビットが 2.47 とブロックソートの 2.43 より悪い。総バイトでは comp-2 がわずかに小さいが、その差は 0.9 パーセントで、代償は時間の単位が桁で変わることだ。

32年前の表が今も有効な理由は軸の数がそのままだからである。数字はハードウェアとともに変わったが、どの軸を押せばどの軸が押し返されるかという構造は変わっていない。

ブロックソート変換がすること - 並列は易しくストリーミングは難しい

論文のアルゴリズム C はこう定義される。長さ N の文字列 S に対して N 個の回転を作って辞書順に整列し、各回転の最後の文字を集めて文字列 L を作る。整列された一覧の中で元の文字列 S があった位置の番号を I とする。変換の出力はこの二つだけであり、アルゴリズム D は L と I だけから S を復元する。

論文の例示がそのまま説明になる。S が abraca、N が 6 のとき、六つの回転を整列すると L は caraab、I は 1 になる。長さも同じで文字の構成も同じだ。変換そのものは一バイトも減らさない。

順序を変えただけでなぜ圧縮が効くのか

論文の説明は二文である。整列は最初の文字が同じ回転を一箇所に集める。そして回転であるから最初の文字のすぐ左が最後の文字だ。したがって L で隣り合う文字は、原文 S の中で互いに似た文字列の隣にあった文字である。文脈が次の文字をよく予測する資料なら L は同じ文字が固まった文字列になり、その固まりは移動前置符号化のような単純な局所適応方式で安く取り除ける。

論文が明示する限界も同じ場所にある。この方式は各文字の片側の文脈だけを使う。論文の実装は移動前置符号化の後にハフマンまたは算術符号を付ける形であり、実際には16キロバイトの入力ごとにハフマン木を計算し直していた。

ブロック単位という性質が生む二つの結果

論文は、自らのアルゴリズムが入力を逐次的に処理せずテキストのブロックを一つの単位として処理すると記す。この一文から二つが導かれる。

  • 並列化が易しい。ブロック同士に依存がないので、スレッド一つがブロック一つを丸ごと担当すればよい。コアを増やせば実時間はほぼそのまま縮む。bzip3 のマニュアルも並列作業者数のオプションをブロックを一つずつ処理する作業者の数と定義している。
  • 部分復旧が可能である。bzip2 マニュアルは、ブロックがそれぞれ独立に処理され、48ビットのパターンがブロックを区切り、ブロックごとに32ビット CRC が付くと記す。破損したファイルから無事なブロックだけを取り出す bzip2recover が成り立つのは、形式がブロックに切られているからだ。
  • ストリーミングが難しい。ソートはブロックが満ちてからでないと始められない。最初の出力バイトが出るまでの遅延がブロックサイズに縛られるということだ。BZip3 の形式概要文書はこの性質を婉曲に回さず、ストリームのないブロックレベル圧縮と言い切っている。
  • 最後の性質が用途を分ける。ログをリアルタイムで押し込むパイプラインのように、いま書いたバイトがいま出なければならない場所では、圧縮率がどれほど良くてもブロック方式は候補から外れる。逆に、すでに出来上がった tar を夜に圧縮する場所では、この性質は何の費用でもない。

論文の判断はこうだ。圧縮率はブロックがかなり大きくなった後も良くなり続けるが、数千万文字を超えると効果が小さくなる。そしてブロックを無限に大きくしても理論的最適には届かないだろうと記す。バイト単位の移動前置符号化そのものが損失を生むからである。

表で注目すべき行は下から三番目だ。bzip2 はブロックを最大に取っても展開に4メガバイトも要らない。32年前の既定値がいまも復旧メディアと組込みで回っている理由は、圧縮率ではなくこの数字である。逆に bzip3 を最大ブロックで使えば、解く側に3ギガバイト級を要求する。

二つのマニュアルが同じように強調する文がある。展開に必要なメモリは、圧縮時点でブロックサイズを選ぶ瞬間に確定する。bzip2 マニュアルはその値がファイルヘッダから読まれると記し、bzip3 の形式仕様も最大ブロックサイズをヘッダ前方の4バイトに収める。圧縮は自分の都合でするように見えて、実際には未来にこのファイルを解く機械の仕様をいま決める行為である。

同じツール、違う資料、分かれる結論

Silesia の束では、bzip3 はブロック16メビバイトの単一スレッドで17.42秒、最大98メガバイトを使い 47,227,855バイトを出した。同じ条件の lzma -9 は76.88秒、675メガバイトで 48,761,670バイトを、zstd -19 は83.43秒、237メガバイトで 53,000,145バイトを出した。三つの軸がすべて bzip3 側に傾いた稀な場合である。

ところが Linux カーネルの束では方向が変わる。bzip3 は 76.93秒で 129,023,171バイトを出し、lzma -9 は 397.30秒を使う代わりに125,725,455バイトとより小さい。同じ二つのツールが、資料を変えた途端に圧縮率の順序を入れ替えた。どのコーパスで測った値かを抜くと、この二つの文は互いに矛盾しているように見える。

Calgary の束は速度の軸の順序を見せる。bzip2 -9 が 172.9ミリ秒で最も速く、gzip -9 が 224.3ミリ秒、bzip3 -b 3 が 265.3ミリ秒、lzma -9 が 787.9ミリ秒である。同じ束のメモリは gzip 5メガバイト、bzip2 8メガバイト、bzip3 17メガバイト、lzma 95メガバイトだ。結果のサイズは bzip3 807,959バイト、lzma 853,112バイト、bzip2 891,321バイト、gzip 1,062,584バイトの順である。五つの軸のうち三つが互いに違う勝者を指している。

Perl の束でメモリの軸が露わになる場所

最も広く引用される数値は Perl の束である。圧縮結果は bzip3 のブロック511メビバイトが 546,456,978バイト、bzip3 のブロック256メビバイトが 1,001,957,587バイト、xz が 2,056,645,240バイト、zstd が 3,076,143,660バイト、bzip2 が 3,441,163,911バイトだ。数字だけ見れば圧倒的である。

同じ記録のメモリの列を一緒に読むと絵が変わる。bzip2 は8メガバイトでその仕事をしたのに対し、bzip3 はブロック256メビバイト12スレッドで18,301メガバイト、ブロック511メビバイト4スレッドで 12,178メガバイトを使った。xz は16スレッドで 14,658メガバイトである。この表で bzip3 が勝った軸は圧縮率と実時間であり、差し出した軸はメモリで、その幅は2,000倍以上だ。

展開側の実時間は zstd 3分51秒、bzip3 の並列 4分06秒、xz 4分40秒、bzip2 9分22秒と記録されている。ただしこの値は WD Blue 系のハードディスクで測ったものであり、CPU 性能ではなくディスクから読み書きする時間が相当部分を占める。リポジトリの説明文が別に記す処理量の値は、x64 Linux で clang13 を用いてビルドした場合にスレッドあたり圧縮 17MiB/s、展開 23MiB/s であり、同じ文が Windows と32ビットのビルドは相当遅くなりうると付け加える。ここでも展開が圧縮より速いという非対称は保たれている。

形式は固定されたか - BZ3v1 とチェックサム事件

長期保存を考えるなら、圧縮率より先に見るべきは形式が固定されたかである。BZip3 はこの問いに対して有利な材料を持っている。形式仕様が文書として公開されており、バージョン番号が付いており、例示のパーサコードまで入っている。

  • ファイルヘッダは9バイトである。5バイトのシグネチャ BZ3v1 と4バイトの最大ブロックサイズだ。ライブラリの高水準関数が使うフレームヘッダは、ここにブロック数の4バイトが加わって13バイトになる。
  • 整数はすべてリトルエンディアンで非整列であり、仕様は移植可能な読み書き関数を併せて載せている。
  • 最大ブロックサイズの有効範囲は 65,536バイトから 535,822,336バイトである。範囲を外れればパーサは拒否すべきだと仕様が定める。
  • 各チャンクは圧縮サイズと原本サイズを4バイトずつ前置する。原本が64バイト未満なら圧縮を試みず、CRC32 と 0xFFFFFFFF という目印を付けてそのまま収める。
  • ブロックの model バイトは、どの段階を経たかをビットで知らせる。0x02 が LZP、0x04 が RLE である。
  • マニュアルは形式の固定負担がファイルあたり9バイト、ブロックあたり9から17バイトであり、乱数データでも膨張は一般に 0.8 パーセント未満だと記す。

それでもアーカイブが未来を失った事件

リポジトリのリリース記録には1.3.2 の項目にこう書かれている。プログラミングの誤りで CRC32 検査関数のシフト方向が誤っており、その結果 1.3.0 と 1.3.1 がチェックサム計算に破壊的変更を導入したというのだ。この変更は 1.3.2 で戻された。そして同じ項目がこう付け加える。その二つの版で作られたアーカイブは正常経路で解くとチェックサム誤りで失敗し、復旧オプションを付けてはじめて元の内容を取り戻せる。

この事件が示すものは明確である。形式仕様が文書としてあっても、実装が揺れればファイルは未来を失う。仕様ではなく実装が真実であり、二つの版のあいだに作られたファイルは、自分が破損していると主張する正常なファイルになった。

記録には別の層の変更もある。1.5.0 はブロック単位の符号化関数の署名を変えて以前の版と ABI 互換でないと明示し、1.5.1 はその差を知らせるために共有ライブラリ名を変えた。これはファイル形式ではなくライブラリのインタフェースの層であり、揺れたのは主にこちらである。同じ 1.5.0 の項目は、デコーダの LZP と RLE の境界を狭めて圧縮がわずかに良くなったが観測可能な形式変化はないと別途記す。形式と実装を区別して記録する態度そのものが判断材料になる。

アドレスも動いた。1.5.3 の項目は、プロジェクトが新しいアカウントへ移ったと記す。リダイレクトは動くが、論文やパッケージのメタデータ、古い文書に刻まれた旧アドレスはその場に残る。長期保存においてリンクは形式の一部である。

なぜ新しい圧縮器は広まらないのか - 形式ではなくツールチェーンだ

ここがこの記事の心臓である。新しい圧縮器が広まらない理由は、おおむねアルゴリズムが悪いからではない。圧縮器を選ぶとは、その形式を読める環境に自分のデータを縛る決定であり、その環境はコードよりはるかに遅く動く。

実際に確認できる層は四つある。

第一の層 - 標準アーカイバが知っているか

GNU tar 1.35 の圧縮オプション一覧には gzip、bzip2、xz、lzma、lzop、zstd、compress のための専用フラグがある。bz3 はない。逃げ道はある。外部プログラムを圧縮フィルタとして指定するオプションを使えばどんな圧縮器でも付けられる。ただしそのオプションが成り立つには、解く側の機械にそのバイナリが導入されていなければならない。拡張子から圧縮器を自動判別するオプションも、内部の対応表にある拡張子にだけ働く。

第二の層 - 共通ライブラリが知っているか

libarchive の公開ヘッダが定めるフィルタ定数は、なし、gzip、bzip2、compress、外部プログラム、lzma、xz、uuencode、rpm、lzip、lrzip、lzop、grzip、lz4、zstd である。bzip3 の項目はない。この一覧が重要な理由は、libarchive を使う側が一つではないからだ。bsdtar、macOS の tar、ビルドツール、いくつものパッケージ管理ツールがこのライブラリを通して圧縮形式を扱う。ここにないということは、それらのツールがすべて当該の拡張子を知らないという意味である。

第三の層 - 言語標準が知っているか

Python 3.13 の標準ライブラリには gzip、bz2、lzma、zlib が入っている。bz3 モジュールはない。tarfile が受ける圧縮モードも gz、bz2、xz だけだ。スクリプト一行でアーカイブを開く場面で、新しい形式は追加の依存を導入するという敷居を作る。この敷居は開発環境では低く、運用環境や他人の環境では高い。

第四の層 - 手元にある版が同じか

パッケージ集計の基準で bzip3 は148件の項目として登録されており、主要配布版におおむね収められている。問題は版である。Debian 12 安定版は 1.2.2、Ubuntu 24.04 は 1.4.0、Fedora 43 以降と Arch、openSUSE Tumbleweed、nixpkgs、FreeBSD、MSYS2 は 1.5.3、Homebrew と Gentoo は 1.5.4 だ。最も古いものと最も新しいものの間に3年が横たわっている。圧縮した機械と解く機械の版が違うのが既定値だということであり、前節のチェックサム事件はまさにその隙間で起きた。

20年後も開けるのか

この問いに対して BZip3 が残した材料は悪くない。形式仕様が文書としてあり、ヘッダ構造と整数の表現が定義されており、例示のパーサが公開されており、ソースが LGPLv3 で開かれている。シグネチャが5バイト固定なので、ファイルを見るだけで形式が分かる。理論的にはいまの文書だけで再実装が可能だ。

しかし再実装が可能だということと、そのとき手元に道具があるということは別の命題である。gzip と bzip2 がいまもどこにでもある理由は圧縮率ではない。どこにでもあったという事実そのものだ。20年後にアーカイブを開く人に必要なのは最適な圧縮率ではなく、その機械にすでに入っている命令一つである。

だから形式の選択は圧縮率の計算ではなく依存の契約である。自組織の内側だけを回るデータなら契約の範囲は狭く、版も統制できる。外部に出たり10年を超えたりすると、契約の相手が誰なのか分からなくなる。バックアップが本当に生きて戻るのかを扱う復元検証の議論や、20年前の形式が残した符号化の遺産を扱うzip のファイル名の話も、結局は同じ場所を指している。形式は長く残り、それを読んでいた環境は残らない。

読むだけで確かめられること

以下はすべて読み取り系である。ファイルを作りも消しもせず、負荷もない。

いま手元にある道具立てがどの形式を知っているかから見る。前節の四つの層のうち第一と第三を自分の環境でそのまま再現する命令である。

# この機械の tar が内蔵で知っている圧縮器の一覧
tar --help | sed -n '/Compression options/,/^$/p'

# Python の標準ライブラリにある圧縮モジュール
python3 -c "import gzip, bz2, lzma, zlib; print('stdlib ok')"

# ないモジュールは例外で答える。それが正常な結果である
python3 -c "import bz3" ; echo "exit=$?"

ファイルの先頭だけ読めば、形式と展開要求が前もって分かる。bzip3 のファイルヘッダは5バイトのシグネチャと4バイトの最大ブロックサイズなので、先頭9バイトだけ見ればよい。

# シグネチャ5バイト。BZ3v1 が見えれば bzip3 のファイルである
head -c 5 sample.bz3 | od -An -c

# その次の4バイトが最大ブロックサイズ。リトルエンディアンの符号なし32ビット
head -c 9 sample.bz3 | od -An -t u4 -j 5 -N 4

# bzip2 は BZh の次の一桁がブロックサイズの100キロバイト単位の数である
head -c 4 sample.bz2 | od -An -c

ブロックサイズが分かれば、展開に必要なメモリを前もって計算できる。マニュアルの式をそのまま使う。

# bzip3 はブロックサイズのおよそ6倍。511メビバイトのブロックならおよそ3ギガバイト
python3 -c "b=511*1024*1024; print(round(b*6/1024/1024), 'MiB')"

# bzip2 は 100k とブロックサイズの4倍。最大ブロックでも4メガバイト未満
python3 -c "b=900*1000; print(round((100*1000+4*b)/1024/1024,2), 'MiB')"

最後は自分の資料で測るのが正解である。標本を一つ選び、同じ条件で複数の軸を一緒に記録する。サイズだけ書けば、前節で見た罠をそのまま繰り返すことになる。

# 圧縮結果のサイズと最大常駐メモリと時間を一行に残す
/usr/bin/time -v gzip  -9 -k -c sample.tar | wc -c
/usr/bin/time -v bzip2 -9 -k -c sample.tar | wc -c
/usr/bin/time -v xz    -9 -k -c sample.tar | wc -c

# 展開の軸は別に測る。配布物ならこちらが唯一の費用である
/usr/bin/time -v gzip  -dc sample.tar.gz | wc -c

確認できなかったこと

  • Perl ベンチマークのハードウェアは説明文にない。CPU の型番・コア数・メモリ容量が書かれておらず、コマンドラインのスレッド数と展開時に使ったハードディスクの型番だけが出ている。絶対時間を他の環境と比較する根拠にはならない。
  • 同じベンチマークで、ブロック511メビバイト4スレッドの行のユーザ CPU 時間が 17.65秒と記録されているが、同じ表の他の行は数百から数千秒であり、その行の実時間も7分08秒である。桁の合わないこの値の理由は説明文の記述範囲の外にあり、確定できなかった。
  • コーパスのサイズ表17種にはブロックサイズ・スレッド数・ハードウェアが付いていない。同じ文書の他の節にはコマンドラインがあるが、その条件がサイズ表にもそのまま適用されたかは文書上確定しない。本文でこの表はサイズの比較にのみ用いた。
  • 第三者による再現ベンチマークは根拠に入れていない。説明文が指す外部のベンチマーク置き場は開いておらず、したがってこの記事の性能に関する記述はすべて開発者自身の測定である。
  • GNU tar の拡張子自動判別の対応表を上流のソースで照合しようとしたが、当該の経路が応答しなかった。tar に関する記述は GNU tar 1.35 のヘルプ出力の範囲に限った。
  • 配布版ごとのパッケージの版は集計サイトの照会結果であり、各配布版のリポジトリを個別に照合してはいない。照会時点以降に更新されている可能性がある。
  • 0次文脈混合の予測器の内部は扱っていない。文脈の定義と混合の方式はソースコード水準の記述を要し、説明文とマニュアルが明かす範囲は文脈混合と算術符号という名前までである。
  • libsais が実際にどの変種を通るのかは確定できなかった。そのライブラリの説明文は誘導整列系の論文四編を根拠に挙げるとだけ記し、bzip3 がそのうちどの経路を使うのかは別途の記述がない。
  • 中間符号化の段階で移動前置符号化がどう置き換えられたかは文書で確定しない。説明文もマニュアルもその段階に別途言及しておらず、本文の表でもその欄は未詳として残した。
