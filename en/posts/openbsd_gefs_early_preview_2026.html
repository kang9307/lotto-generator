1. The Early Preview Announcement and the Scope of GEFS

In modern operating systems, the storage layer acts as the foundational barrier between volatile memory abstractions and durable media reality. While specialized virtual file systems such as MemNixFS address forensic live-memory analysis and exploratory designs like πFS probe the theoretical limits of informational representation, general-purpose block storage engines must confront concrete physical hurdles: crash consistency, write amplification, and metadata integrity. On September 15, 2026, Ori Bernstein, an active contributor to the 9front operating system project (a community-driven fork of Plan 9 from Bell Labs), announced on the openbsd-tech mailing list an early preview of GEFS running inside the OpenBSD kernel. Following discussions initiated at the EuroBSD conference, this preview represents the first public milestone of porting a modern copy-on-write file system originating in Plan 9 over to the BSD kernel ecosystem.

The author made no attempt to disguise the experimental nature of the code. In his mailing list post, Bernstein explicitly described the release as a 「rough, buggy, issue-filled preview」 that is completely unready for production deployment. Most notably, the post warned that data loss is currently expected, particularly when handling runtime errors. Furthermore, the port has not yet been submitted for inclusion into the upstream OpenBSD source tree. Nevertheless, the announcement attracted immediate technical attention across the kernel engineering community. The core architectural logic and failure modes are already well-understood by the author, and the entire in-kernel implementation weighs in at under 9,000 lines of code—an exceptionally compact footprint for a modern copy-on-write, snapshotting storage engine.

The name GEFS stands for 「Good Enough File-System」. Rather than attempting to maximize theoretical throughput across every conceivable benchmark axis or introducing immense layers of heuristic caching, GEFS embraces an engineering philosophy that asks what happens if a file system adheres strictly to a clean, comprehensible copy-on-write model and stops when it becomes good enough for daily dependable operation. This article examines whether the actual implementation fulfills the explicit hierarchy of promises established by its name, tracing the mechanics of its underlying data structures and detailing the concrete obstacles documented in the preview.

2. Four Core Design Priorities and Their Technical Backing

File system design is inherently an exercise in navigating contradictory engineering trade-offs. Elevating synchronous write performance often degrades structural recoverability following unexpected power loss, while enforcing fine-grained data verification can introduce crippling metadata serialization bottlenecks. In his design documentation for GEFS, Ori Bernstein resolved these tensions by establishing a strict, immutable order of four foundational goals: first, crash-safe; second, corruption-detecting; third, simple; and fourth, fast snapshotting.

This four-fold commitment is not merely an abstract statement of intent; each tier corresponds directly to a concrete structural mechanism within the engine. Crash safety is guaranteed by enforcing copy-on-write allocations across all data and metadata combined with atomic superblock commitments. Corruption detection is achieved by abandoning traditional raw block pointers in favor of 64-bit triple tuples comprising physical offsets, cryptographic checksums, and generational birth tags. Simplicity is maintained by flattening all file system hierarchies into a unified key-value mapping backed by a single Bε-tree structure, deliberately dispensing with traditional directory tables and indirect pointer blocks. Finally, fast snapshotting is realized through epoch-based immutable tree rooting, enabling instantaneous snapshots every 5 seconds with minimal metadata overhead.

Priority (Ranked Order) Core Engineering Objective Implementation Mechanism Architectural Characteristics
① crash-safe Prevent on-disk structural corruption across sudden power cuts Copy-on-Write allocation with atomic superblock sync; 5-second snapshot sync intervals Restores to the last synced disk commit upon reboot; up to 5 seconds of data lost, but zero structural corruption
② corruption-detecting Detect silent physical media bit rot and transmission errors Block pointers structured as 64-bit triples (block address, block hash, birth generation) Hashes verified on read paths; corrupt blocks reported immediately to upper layers rather than silently returned
③ simple Eliminate nested indirection and maintain auditable code volume Flat key-value namespace hosted over Bε-tree; kernel implementation kept under 9,000 lines of code Atomic batch upserts across multiple attributes; lockless read traversals without complex internal concurrency state
④ fast snapshotting Enable frictionless, continuous creation and reclamation of historical points Unique integer IDs per snapshot; immutable upon capture; automatic reclamation via descendant reference counts Root block buffer copying minimizes allocation costs; snapshots taken continuously every 5 seconds

This ranked hierarchy dictates how GEFS resolves operational conflicts. Under no circumstances will the file system sacrifice corruption verification or atomic write ordering to chase raw bandwidth figures. Performance is treated as a derivative benefit that must strictly operate within the boundaries defined by crash safety, data verification, and verifiable structural simplicity.

3. Bε-tree Architecture — Mitigating Write Amplification and Read Path Tradeoffs

At the center of the GEFS architecture lies the Bε-tree (B-epsilon tree), a write-optimized data structure derived from the standard B+tree. In traditional copy-on-write B-tree implementations, modifying even a single byte within a file or altering an access timestamp necessitates allocating and writing new leaf nodes, followed by cascading copy-on-write allocations up the tree to the root. This cascading update pattern induces severe write amplification, exhausting disk bandwidth and accelerating flash storage wear.

The Bε-tree circumvents this pathology by attaching dedicated write buffers directly to intermediate pivot nodes. When a write operation or metadata alteration occurs, the file system does not traverse the entire tree down to the leaves. Instead, it copies the root block and inserts a compact modification message—known as an upsert—into the root node write buffer. As incoming messages accumulate and the buffer reaches capacity, the node inspects the distribution of pending writes and selects the child pointer with the highest message concentration. The buffer contents targeting that child are then flushed downward. This flushing process cascades recursively down the hierarchy until the messages either settle into an intermediate buffer with available capacity or reach the leaf nodes to directly mutate the stored values.

Because these upserts are declarative messages rather than blind byte overwrites, GEFS can perform complex updates without reading existing data from disk. For example, incrementing a file version counter or modifying an access timestamp can be executed by upserting a new version message into the root buffer, entirely bypassing the classic read-modify-write cycle. Furthermore, as long as sufficient space remains in the root buffer, multiple interrelated mutations can be inserted atomically in a single operation.

Nevertheless, fundamental computer science constraints enforce an unavoidable trade-off: write optimization complicates the read path. To retrieve a value in a Bε-tree, the reader cannot simply navigate to a leaf and read the raw bytes. It must record the traversal path from the root downward, inspect every write buffer along that path, and sequentially apply all pending modification messages to the base value before returning it to the caller. While the author did not provide quantitative latency figures for read operations, this requirement to aggregate buffered state across multiple tree tiers represents an inherent structural overhead that distinguishes Bε-trees from classical B+trees.

Kdat(qid, offset) → (ptr)
Kent(pqid, name)  → (stat)
Kup(qid)          → Kent(pqid, name)

The listing above illustrates how GEFS maps an entire hierarchical file system into a single flat key-value namespace. Block pointers are indexed via Kdat keys combining the file QID and byte offset. Directory entries are encoded as Kent keys pairing the parent QID with the entry name. Upward traversals are resolved via Kup keys pointing back to parent directories. Because the underlying Bε-tree maintains sorted order, directory listings become straightforward range scans across all keys matching a parent QID, permanently eradicating the linear O(n) directory traversal bottlenecks historically found in older Plan 9 file systems.

4. Crash Safety Guarantees and Triple-Tuple Corruption Detection

Crash safety in file system design defines how resilient on-disk state remains when the host suffers an ungraceful shutdown, kernel crash, or power loss. GEFS establishes its crash resilience through a strict write-ordering protocol. Modifications to data blocks, pivot buffers, and deadlists are written to unallocated disk space via copy-on-write semantics. Only after all associated blocks have hit the physical storage media does the file system update its root superblock pointers.

The behavioral specification articulated in the design documentation provides explicit clarity on failure recovery: if the file server crashes prior to the superblock being successfully updated on persistent storage, the subsequent mount operation will simply read the last commit that was fully synced to disk. Under default configuration settings, up to 5 seconds of uncommitted write data may be lost, but structural corruption within the file system is impossible. The engine trades a narrow window of recent volatility for an absolute guarantee of structural consistency.

To defend against silent data corruption—where physical media failures or controller bugs return corrupted bitstreams without reporting hardware errors—GEFS replaces standard block pointers with 64-bit triple tuples consisting of three distinct fields:

  • Block address: The physical linear block offset on the underlying block device where the payload resides.
  • Block hash: A cryptographic digest computed across the entire block payload at write time, used to verify integrity upon retrieval.
  • Birth generation: A monotonically increasing integer counter identifying the exact snapshot generation in which the block was allocated.

Whenever a block is fetched from storage during normal read operations, GEFS recomputes its hash and validates it against the block pointer tuple. If bit rot or transmission corruption has altered the payload, the mismatch is detected immediately, preventing corrupted data from silently propagating into application memory. In the current preview, detected corruptions are reported as I/O errors, laying the groundwork for automated self-healing once native mirroring or RAID capabilities are integrated.

5. Snapshot Lifecycles and Space Reclamation — ZFS Deadlists over btrfs

In a pure copy-on-write architecture, snapshots are conceptually inexpensive: preserving a point-in-time image requires nothing more than retaining the tree root pointer corresponding to that generation. In GEFS, each snapshot is assigned a unique integer identifier and becomes strictly immutable once captured. For administrative usability, human-readable string labels can be attached to snapshots, advancing automatically with active commits or remaining fixed upon specific milestones.

However, because GEFS captures automatic snapshots every 5 seconds, storage capacity would be rapidly exhausted unless superseded and unreferenced blocks are efficiently reclaimed. During the architectural phase, Bernstein evaluated multiple space reclamation methodologies used in established operating systems, rejecting two prominent models before settling on his final design.

Reclamation Model ZFS Deadlist Approach (Adopted by GEFS) btrfs Optimized Refcounting (Rejected) HAMMER Garbage Collection (Rejected)
Underlying Mechanism Tracks blocks freed within snapshot intervals using deadlists; merges lists on deletion Maintains and continuously modifies fine-grained reference count trees per block Executes periodic background scans across the entire disk space to detect dead blocks
Write Pattern Behavior Appends freed block descriptors into generational deadlists, maintaining sequential writes Induces a heavy volume of scattered random writes across metadata to adjust counters Generates extensive background read I/O that competes directly with user workloads
Deletion Performance Directly iterates over pre-computed deadlists belonging to the target snapshot Requires complex tree traversals and lock contention to decrement reference counts Suffers significant latency spikes while waiting for sweeping scans to finish
GEFS Architectural Verdict Adopted: Lifted directly from ZFS to avoid scattered writes and preserve code simplicity Rejected: Massive volume of scattered random writes undermines copy-on-write performance Rejected: Periodic throughput degradation and excessive background bandwidth consumption

The explicit rationale for rejecting the btrfs model was that fine-grained reference counting creates a massive volume of scattered, random metadata writes. Whenever shared snapshots diverge, updating individual reference counters forces widespread tree mutations that severely degrade throughput. Similarly, the HAMMER-style garbage collection model was dismissed because scanning entire terabyte-scale drives incurs continuous I/O penalties that scale unfavorably under heavy write pressure.

Consequently, GEFS lifted its space reclamation algorithm directly from ZFS. The engine leverages the birth generation stored in every block pointer: if a block was created within the pending snapshot and released before the snapshot committed, it is returned to the free pool immediately. If the block originated in an earlier generation, it is placed onto the current snapshot deadlist. When a snapshot is deleted, its deadlist is merged into its successor snapshot, and blocks born after the preceding snapshot are freed in bulk. By sharding deadlists by birth generation, GEFS ensures that deletion operations only touch lists consisting entirely of reclaimable blocks, keeping reclamation overhead proportional to deleted volume rather than total drive capacity.

6. Porting Status on OpenBSD and the 12 Caveats Checklist

The current OpenBSD code represents an in-progress kernel port rather than a polished subsystem. In the spirit of transparent engineering, Bernstein outlined 12 specific technical deficiencies and missing components that currently characterize the implementation. For any engineer evaluating this preview, these 12 items serve as an authoritative checklist of the technical debt that remains to be resolved:

  1. Consistency protocol validation pending: Superblock writes must strictly follow the complete on-disk persistence of all snapshot payload blocks. Several write-ordering fixes established in 9front have not yet been backported to the OpenBSD tree.
  2. Error handling largely commented out: The original error handling paradigms developed for 9front are fundamentally incompatible with OpenBSD kernel conventions, leaving numerous error paths temporarily disabled or commented out.
  3. Single-mount limitation via global variables: Several kernel-level global variables remain in the ported codebase, restricting the system to mounting exactly one GEFS instance at any given time.
  4. Total absence of native userspace utilities: OpenBSD lacks native newfs and fsck commands for GEFS. Initializing or repairing a file system currently requires booting 9front inside a virtual machine.
  5. Missing snapshot management tooling: Userspace command-line tools and kernel ioctl interfaces required for creating, labeling, and deleting snapshots have not yet been ported.
  6. Potential POSIX semantic mismatches: Because GEFS was conceived for Plan 9—a non-POSIX operating system—the codebase likely harbors subtle violations of standard POSIX file system constraints and corner cases.
  7. No OpenBSD regression test suite: While a basic test harness exists under 9front, zero automated regression test cases have been established within the OpenBSD regress framework.
  8. Hardlinks unimplemented: Although structurally straightforward to support, per-file reference count tracking files have not yet been implemented.
  9. Missing kqueue integration: The vnode hooks necessary to dispatch kernel event notifications via OpenBSD's standard kqueue subsystem have not been wired up.
  10. No NFS server export hooks: The complex vnode translation hooks required for exporting GEFS partitions over the Network File System (NFS) are absent.
  11. Bootloader and boot environment deficits: GEFS cannot be booted by the OpenBSD bootloader, cannot function as a root partition, and lacks storage quota mechanisms.
  12. Slow bulk deletion of large files: Deleting massive files currently requires individual block upserts, causing measurable latency that the author intends to address via range deletion messages.

This comprehensive list underscores the vast distance separating an early architectural preview from a deployable kernel subsystem. While the core data structure functions as intended, the surrounding kernel infrastructure required for safe, everyday POSIX execution remains heavily incomplete.

7. Lineage and Philosophy — Moving from Plan 9 to OpenBSD

The architectural choices in GEFS reflect its lineage within the Plan 9 and 9front operating systems. Over several decades, Plan 9 developed a variety of on-disk storage systems, each burdened by specific historical constraints. The traditional cwfs file server was performant but completely lacked crash safety, requiring manual intervention after power cuts and lacking any mechanism to reclaim dump space. The experimental hjfs system achieved extreme code simplicity but suffered from sluggish performance and lacked consistency recovery tools. Meanwhile, fossil relied on soft-updates—a mechanism notorious for inducing deadlocks and complex race conditions—while remaining unable to reclaim storage when combined with venti archives.

GEFS was engineered specifically to transcend these limitations by replacing historical ad-hoc structures with a mathematically coherent Bε-tree foundation. In bringing this work to OpenBSD, Bernstein adopted a pragmatic porting strategy: rather than constructing an artificial abstraction layer between Plan 9 and OpenBSD, he chose to duplicate the code while ensuring that data structures and core algorithmic logic strictly 「rhyme」 across both codebases.

# Clone upstream OpenBSD source
git clone https://github.com/openbsd/src
cd src

# Add the remote repository and checkout the branch
git remote add gefs git://shithub.us/ori/openbsd
git fetch gefs
git checkout -b gefs gefs/gefs

The shell sequence above reflects the official build instructions provided in the mailing list announcement. The author explicitly noted that he is not currently conforming the code to OpenBSD's strict KNF (Kernel Normal Form) style guidelines, choosing instead to maintain close textual parity with the 9front repository until upstream integration becomes feasible. This preserves the ability to rapidly backport bug fixes between the two operating systems without getting bogged down in formatting divergence.

8. Where It Fits and Where It Fails — Experimental Sandbox vs Production

Engineering maturity is defined by recognizing the exact context in which a technology delivers value and the boundaries beyond which it becomes dangerous. GEFS occupies two sharply polarized positions depending on the deployment environment.

Where GEFS provides exceptional value is in storage systems research, kernel hacking, and architectural education. Monolithic production file systems such as OpenZFS or btrfs span hundreds of thousands of lines of complex code, making it nearly impossible for an individual engineer to grasp the full execution pipeline. GEFS, in contrast, encapsulates modern copy-on-write mechanics, Bε-tree write buffering, atomic commit protocols, generational deadlists, and hash-based corruption detection within fewer than 9,000 lines of readable C. For developers seeking to understand how write amplification can be mitigated without sacrificing snapshot agility, GEFS serves as an invaluable, transparent reference.

Conversely, GEFS represents an unacceptable risk for any environment housing critical data. Running personal files, databases, or enterprise workloads on a file system whose author openly expects data loss under error conditions is an untenable gamble. Furthermore, the 5-second snapshot sync window means that workloads requiring strict synchronous persistence (such as transactional database write-ahead logs) are mismatched with its current flush semantics. For the foreseeable future, GEFS belongs exclusively within isolated virtual machines and scratch partitions where kernel crashes and data loss carry zero operational impact.

9. Unconfirmed Items and Open Questions

Due to the nascent state of the project and the strict boundaries of available primary documentation, the following technical questions could not be confirmed:

  • Target timeline for OpenBSD in-tree submission: While the author indicated that inclusion is not planned for the immediate future, no roadmap or milestone schedule for an official review request has been published.
  • Completion schedule for native userspace tools: The documentation provides no delivery estimates for native C implementations of newfs_gefs or fsck_gefs within OpenBSD.
  • Quantitative read latency benchmarks under Bε-tree traversal: While the structural necessity of aggregating intermediate node buffers on read paths is documented, empirical latency measurements under OpenBSD remain unrecorded.
  • Concrete specification for native RAID self-healing: The design paper mentions native mirroring and RAID5 write-hole mitigation as future goals, but specific block allocation and parity reconstruction algorithms have not yet been finalized.
