はじめに - コピーは1層ずつ起きる

設定の辞書をコピーしてユーザーごとに値を変えたら、既定の設定まで変わっていた、ということがある。コピーのコードは問題なく実行され、新しい辞書も確かに作られた。ところが内側のリストは元と同じオブジェクトだった。コピーが行われる層の数は、方法ごとに異なる。どの方法が何層まで新しく作り、どこで止まるのかはオブジェクトの同一性(is)で分かり、その止まる地点を越える方法とそのコストは以下の出力が示す。

近隣のテーマの記事とは軸が異なる。デフォルト引数の記事は、デフォルト値のオブジェクトがdef文の実行時に一度だけ作られて呼び出しの間で共有される問題を、小さな整数の記事は、整数や文字列をisで比較すると最適化のせいで結果が変わる問題を扱う。ここでは、すでに存在するコンテナをコピーするとき、どの層まで新しいオブジェクトになるかに限定する。前の2つの記事とつながる点は、本文でリンクにして渡す。

扱う問いは次のとおりである。

  • 代入(=)はオブジェクトをいくつ作るか。
  • copy()、list()、スライス、dict.copy()、copy.copy、copy.deepcopyは、それぞれ外側と内側のどこまでが新しいオブジェクトか。
  • 入れ子のリストや辞書で、元が変わる条件は何か。
  • タプルの中のリスト、データクラス、ユーザー定義クラスは、コピーでどう扱われるか。
  • deepcopyは、同じオブジェクトを2回参照した構造や循環参照をどう処理するか。
  • deepcopyの時間コストは、このPCでどのくらいか。

代入はコピーではない

最初にぶつかるのは、コピーだと思っていたものが代入だった場合である。公式ドキュメントのcopyモジュールの最初の文は次のとおりである。"Assignment statements in Python do not copy objects, they create bindings between a target and an object." 代入文はオブジェクトをコピーせず、対象とオブジェクトの間のバインディングを作る。以下の出力はこの文と一致する。

a = [1, 2]
                    b = a
                    print(a is b, id(a) == id(b))
                    b.append(3)
                    print(a)
                    c = list(a)
                    print(c is a, c == a)
                    c.append(4)
                    print(a, c)
True True
                    [1, 2, 3]
                    False True
                    [1, 2, 3] [1, 2, 3, 4]

1行目では、a is bとid(a) == id(b)がどちらもTrueである。データモデルのドキュメントは、isが2つのオブジェクトの同一性(identity)を比較し、id()がその同一性を表す整数を返すと記し、CPythonではid(x)がxの保存されているメモリアドレスだと付け加えている。つまりaとbは、1つのオブジェクトに付いた2つの名前である。b.append(3)の後、aも[1, 2, 3]になった。一方、list(a)で作ったcは、c is aがFalseの新しいリストであり、c == aがTrueなのは内容が等しいという意味にすぎず、同じオブジェクトという意味ではない。c.append(4)はaに影響を与えなかった。

  • ==は値が等しいかを、isは同じオブジェクトかを問う。コピーされたかどうかはisで見る。
  • ここで使うisは、コンテナオブジェクトの同一性を見るために使う。整数や文字列のような値をisで比べると最適化のせいで結果が変わる問題は、小さな整数の記事が扱っている。
  • 呼び出し側が渡したリストをコピーしておくパターンの実行出力は、デフォルト引数の記事の5節にある。

コピー方法ごとに新しく作られる層

次のコードは、入れ子のリスト1つと辞書1つに対して複数のコピー式を実行し、結果の外側のコンテナが元と別のオブジェクトか(new outer)、内側のリストが元と別のオブジェクトか(new inner)をis notで出力する。

copyモジュールのドキュメントは、2種類のコピーを次のように定義している。"A shallow copy constructs a new compound object and then (to the extent possible) inserts references into it to the objects found in the original." 浅いコピーは新しい複合オブジェクトを作り、元の中のオブジェクトへの参照をそこに入れる。"A deep copy constructs a new compound object and then, recursively, inserts copies into it of the objects found in the original." 深いコピーは新しい複合オブジェクトを作り、元の中のオブジェクトのコピーを再帰的にそこに入れる。出力はこの定義と一致している。

式外側のコンテナ内側のオブジェクト
b = orig同じオブジェクト同じオブジェクト
orig.copy()、list(orig)、orig[:]、[*orig]、copy.copy(orig)新しいオブジェクト元と共有
d.copy()、dict(d)、{**d}、copy.copy(d)新しいオブジェクト元と共有
copy.deepcopy(orig)、copy.deepcopy(d)新しいオブジェクト新しいオブジェクト

表から読み取れることは次のとおりである。

  • 代入だけが、外側まで同じオブジェクトである。代入を除く残りの11の式は、すべて外側のコンテナを新しく作った。
  • リストのcopy()・list()・スライス・[*x]、辞書のcopy()・dict()・{**d}、そしてcopy.copyまで、この環境では同じ深さ(1層)だった。
  • 公式ドキュメントの組み込みシーケンスの項目は、可変シーケンスのcopy()を「Create a shallow copy of sequence. This is equivalent to writing sequence[:].」と記している。スライスとcopy()が同じ深さだという出力と合う。
  • copyモジュールのドキュメントは、コレクションの浅いコピーをlist.copy()・dict.copy()・set.copy()とシーケンス全体のスライスで作れると記している。copyのドキュメントはこれらの方法を浅いコピーとして挙げており、出力のisの表がこれを示す。
  • deepcopyだけが、内側のオブジェクトまで新しく作った。

入れ子構造で元が変わる再現

1層だけ新しく作られた複製に変更を加えると、どの層の変更かによって、元が変わることも変わらないこともある。次のコードは、複製に3種類の変更を順に加え、そのたびに元を出力する。後半は、既定の設定の辞書をcopy()してユーザー設定を作る状況である。

orig = [[1, 2], [3, 4]]
                    dup = orig.copy()
                    dup.append([5, 6])
                    print('after append to the copy   :', orig)
                    dup[0].append(99)
                    print('after changing an inner list:', orig)
                    dup[1] = 'replaced'
                    print('after replacing an element  :', orig)
                    
                    defaults = {'name': 'base', 'tags': ['a']}
                    user = defaults.copy()
                    user['name'] = 'mine'
                    user['tags'].append('b')
                    print(defaults)
                    print(user)
after append to the copy   : [[1, 2], [3, 4]]
                    after changing an inner list: [[1, 2, 99], [3, 4]]
                    after replacing an element  : [[1, 2, 99], [3, 4]]
                    {'name': 'base', 'tags': ['a', 'b']}
                    {'name': 'mine', 'tags': ['a', 'b']}

複製に新しい項目をappendすること(外側のコンテナの変更)と、複製の要素を別の値に置き換えること(dup[1] = 'replaced')は、元に影響がなかった。一方、複製の内側のリストdup[0]にappend(99)をすると、元のorig[0]も[1, 2, 99]になった。複製と元が同じ内側のリストを指しているからであり、前の節のnew inner Falseの出力がこの結果を予告している。

辞書も同じである。user['name'] = 'mine'はuserだけを変え、defaults['name']は'base'のままだった。しかしuser['tags'].append('b')は、defaults['tags']にも'b'を入れた。ユーザー設定を作ろうとしたコードが、既定の設定を汚染したのである。

  • 複製の外側のコンテナを変える操作(項目の追加・置換・削除)は、元に影響しない。
  • 複製が共有している内側の可変オブジェクトをその場で変える操作(append、[k] = vなど)は、元にも見える。
  • 同じ複製でも、どのフィールドに触れたかで結果が分かれるので、テストで1つのフィールドしか確認しないと問題が現れないことがある。

繰り返し演算はコピーではなく同じ参照の繰り返しである

2次元リストを[[0] * 2] * 3で作ることも、同じ問題の別の顔である。公式ドキュメントはs * nについて「items in the sequence s are not copied; they are referenced multiple times」と記し、lists = [[]] * 3の後にlists[0].append(3)が[[3], [3], [3]]になる例を挙げている。以下の出力は似たコードの結果である。

grid = [[0] * 2] * 3
                    print(grid[0] is grid[1] is grid[2])
                    grid[0][0] = 1
                    print(grid)
                    fresh = [[0] * 2 for _ in range(3)]
                    print(fresh[0] is fresh[1])
                    fresh[0][0] = 1
                    print(fresh)
True
                    [[1, 0], [1, 0], [1, 0]]
                    False
                    [[1, 0], [0, 0], [0, 0]]

1行目がTrueである。3つの行はすべて同じリストオブジェクトであり、grid[0][0] = 1が3つの行すべてに現れた。リスト内包表記で行ごとに新しいリストを作ったfreshは、行が互いに別のオブジェクトで(False)、1行だけが変わった。コピー関数を使っていないのに同じ現象が起きるのは、問題がコピーの方法ではなく、同じオブジェクトに名前や位置が複数付いているという点にあるからである。

タプルの中のリスト - 変更できないコンテナの落とし穴

データモデルのドキュメントは次のように記している。"The value of an immutable container object that contains a reference to a mutable object can change when the latter's value is changed; however the container is still considered immutable, because the collection of objects it contains cannot be changed." 不変コンテナが可変オブジェクトを含んでいると、その可変オブジェクトが変わったときにコンテナの値も変わりうるという文である。これがコピーと出会ったときの結果は、以下の出力のとおりである。

import copy
                    t = ([1, 2], 3)
                    print(copy.copy(t) is t)
                    deep = copy.deepcopy(t)
                    print(deep is t, deep[0] is t[0], deep == t)
                    t[0].append(99)
                    print(t)
                    try:
                        t[0] += [4]
                    except TypeError as e:
                        print(type(e).__name__, e)
                    print(t)
                    print(deep)
                    u = (1, 'a')
                    print(copy.deepcopy(u) is u)
True
                    False False True
                    ([1, 2, 99], 3)
                    TypeError 'tuple' object does not support item assignment
                    ([1, 2, 99, 4], 3)
                    ([1, 2], 3)
                    True

1行目で、copy.copy(t) is tがTrueである。タプルの浅いコピーは、新しいタプルを作らず同じオブジェクトを返した。2行目で、deepcopy(t)は新しいタプルで(deep is tがFalse)、中のリストも新しいオブジェクトであり(deep[0] is t[0]がFalse)、値は等しい(deep == t)。元のtのリストにappend(99)をすると、タプルは不変なのに([1, 2, 99], 3)になった。

次の行が、この落とし穴が現れる場面である。t[0] += [4]はTypeError: 'tuple' object does not support item assignmentを出したが、直後にtを出力すると([1, 2, 99, 4], 3)である。例外が出たのに、リストにはすでに4が追加されていた。この出力で確認できるのは、例外と変更の両方が起きたという事実である。最後の2行で、deepcopyで切り離しておいたdeepは([1, 2], 3)のままであり、中に可変オブジェクトを持たないタプルu = (1, 'a')のdeepcopy(u) is uはTrueだった。

  • タプルのcopy.copyは同じオブジェクトを返すので、「コピーした」という感覚に反して何も作られない。中にリストがあれば、そのリストももちろん共有される。
  • タプルが不変であるとは、タプルの要素の位置が変わらないという意味であり、要素が指すリストの内容まで固定するわけではない。
  • タプルを辞書のキーや設定の値として使い、中にリストを入れた場合、複製の間でそのリストが共有される。
  • deepcopyは、可変オブジェクトを含むタプルは新しく作り、不変オブジェクトだけを含むタプルは同じオブジェクトを返した。この2行の出力はCPythonでの観察である。

クラスとデータクラスのコピー

ユーザー定義クラスのインスタンスも、同じ規則に従う。データクラスでリストのフィールドを持つオブジェクトを作り、4つの方法で新しいオブジェクトを得て、それぞれがリストのフィールドを共有しているかを出力する。最後の行は、元のリストに項目を追加した後の、4つの複製のリストである。

import copy
                    import dataclasses
                    from dataclasses import dataclass, field
                    
                    @dataclass
                    class Box:
                        name: str
                        items: list = field(default_factory=list)
                    
                    a = Box('a', [1, 2])
                    b = copy.copy(a)
                    c = copy.deepcopy(a)
                    d = dataclasses.replace(a, name='d')
                    e = copy.replace(a, name='e')
                    for label, x in [('copy.copy', b), ('copy.deepcopy', c), ('dataclasses.replace', d), ('copy.replace', e)]:
                        print('%-20s new object: %-5s shares items: %s' % (label, x is not a, x.items is a.items))
                    a.items.append(3)
                    print(b.items, c.items, d.items, e.items)
copy.copy            new object: True  shares items: True
                    copy.deepcopy        new object: True  shares items: False
                    dataclasses.replace  new object: True  shares items: True
                    copy.replace         new object: True  shares items: True
                    [1, 2, 3] [1, 2] [1, 2, 3] [1, 2, 3]

4つの方法すべてが新しいオブジェクトを作ったが、deepcopyだけがリストを切り離した。copy.copyとdataclasses.replace、そして3.13で追加されたcopy.replaceは、リストを元と共有しており、最後の行で元に3を入れると、この3つのリストにも3が見えた。copyモジュールのドキュメントは、copy.replace()が3.13で追加され、copy()やdeepcopy()より制限が多く、namedtuple、データクラス、__replace__()を定義したクラスだけをサポートすると記している。一部のフィールドを変えて新しいオブジェクトを作るreplace系は、変えなかったフィールドをそのまま引き継ぐので、可変のフィールドは共有される。

deepcopyがすべてのオブジェクトをコピーできるわけではない。ロック(threading.Lock)を属性に持つオブジェクトにcopy.copyとcopy.deepcopyを適用し、__deepcopy__を定義したサブクラスにも適用する。

import copy
                    import threading
                    
                    class Job:
                        def __init__(self, name):
                            self.name = name
                            self.lock = threading.Lock()
                            self.log = []
                    
                    job = Job('j1')
                    try:
                        copy.deepcopy(job)
                    except TypeError as e:
                        print(type(e).__name__, e)
                    print(copy.copy(job).lock is job.lock)
                    
                    class SafeJob(Job):
                        def __deepcopy__(self, memo):
                            new = SafeJob(self.name)
                            new.log = copy.deepcopy(self.log, memo)
                            return new
                    
                    s = SafeJob('j2')
                    s.log.append('start')
                    t = copy.deepcopy(s)
                    print(t.log, t.log is s.log, t.lock is s.lock)
TypeError cannot pickle '_thread.lock' object
                    True
                    ['start'] False False

copy.deepcopy(job)はTypeError: cannot pickle '_thread.lock' objectで失敗し、copy.copy(job).lock is job.lockはTrueだった。浅いコピーはロックのオブジェクトに触れず共有する。__deepcopy__(self, memo)を定義したSafeJobは、新しいロックを持つ新しいオブジェクトを作り(t.lock is s.lockがFalse)、ログのリストは別にコピーされて切り離された(t.log is s.logがFalse、内容は['start'])。copyモジュールのドキュメントは、deepcopyがユーザー定義クラスにコピー動作やコピーする構成要素の集合を上書きさせると記し、object.__deepcopy__(self, memo)が深いコピーを実装し、memo辞書を引数として受け取ると説明している。この説明と出力が一致している。

  • 浅いコピー(copy.copy)は、属性が何であっても参照だけをコピーするので、ロックがあっても成功した。
  • deepcopyは、コピーできない属性に出会うとTypeErrorで失敗する。この出力での例がロックである。
  • 共有すべき資源(ロック、接続など)を持つクラスには、__deepcopy__でコピーの方法を指定する。

deepcopyが解決するもの - memoと循環参照

copyモジュールのドキュメントは、深いコピーに2つの問題があると記している。第一に、再帰的なオブジェクト(直接または間接に自分自身への参照を含む複合オブジェクト)は、再帰ループを起こすことがある。第二に、深いコピーはすべてをコピーするので、コピーの間で共有されるはずのデータまでコピーしてしまうことがある。そしてdeepcopy()は、これを2つの方法で避けると記している。現在のコピー処理の中ですでにコピーしたオブジェクトのmemo辞書を保持すること、ユーザー定義クラスにコピー動作やコピーする構成要素を上書きさせることである。最初の仕組みは以下の出力で確認できる。同じリストが2回入った構造、循環構造、あらかじめ埋めたmemoを扱う。

import copy
                    a = [1]
                    orig = [a, a]
                    deep = copy.deepcopy(orig)
                    print('deepcopy keeps sharing :', deep[0] is deep[1], '| detached from original:', deep[0] is not orig[0])
                    naive = [copy.deepcopy(x) for x in orig]
                    print('per-element deepcopy   :', naive[0] is naive[1])
                    shallow = copy.copy(orig)
                    print('shallow copy           :', shallow[0] is shallow[1], shallow[0] is orig[0])
                    
                    memo = {}
                    copy.deepcopy(orig, memo)
                    print('memo entries           :', len(memo))
                    
                    loop = []
                    loop.append(loop)
                    print('cyclic shallow         :', copy.copy(loop)[0] is loop)
                    dup = copy.deepcopy(loop)
                    print('cyclic deepcopy        :', dup is not loop, dup[0] is dup)
                    
                    keep = {id(a): a}
                    part = copy.deepcopy(orig, keep)
                    print('pre-filled memo        :', part[0] is a, part[0] is part[1])
deepcopy keeps sharing : True | detached from original: True
                    per-element deepcopy   : False
                    shallow copy           : True True
                    memo entries           : 3
                    cyclic shallow         : True
                    cyclic deepcopy        : True True
                    pre-filled memo        : True True
  • 同じリストaを2回含むorig = [a, a]をdeepcopyすると、複製でも2つの位置が同じ1つのオブジェクトである(deep[0] is deep[1]がTrue)。それでいて元とは切り離されている(deep[0] is not orig[0]がTrue)。構造が保たれたのである。
  • 要素ごとに別々にdeepcopyしたnaiveは、2つの位置が別のオブジェクトになった(False)。同じオブジェクトを共有していた構造が失われる。memoは1回のdeepcopy呼び出しの間だけ保持されるので、呼び出しを分けると保たれない。
  • 浅いコピーは、内側の2つの位置が元のaをそのまま指す(shallow[0] is orig[0]がTrue)。
  • deepcopyが埋めたmemoには、3つの項目が入っていた。
  • 自分自身を含むリストloopで、浅いコピーの最初の要素は元のloopを指す(True)。deepcopyは無限再帰なしに終わり、複製は元と別のオブジェクトでありながら自分自身を含む(dup[0] is dupがTrue)。循環構造まで保たれたのである。
  • memoに{id(a): a}をあらかじめ入れてdeepcopyを呼ぶと、part[0] is aがTrueだった。すでにmemoにあるオブジェクトはコピーされず、そのまま使われる。

最後の項目は、共有すべきオブジェクトをコピーの対象から外す方法になりうる。ドキュメントが述べた、コピーの間で共有されるはずのデータまでコピーしてしまうという問題に対して、この出力は、memoをあらかじめ埋めることで1つのオブジェクトを共有のままにできることを示している。ただしこれはmemoの動作を利用した観察であり、ドキュメントが示す正式な方法は__deepcopy__を定義することである。

deepcopyのコスト - このPCでの測定値

deepcopyは内側のオブジェクトをすべてたどってコピーするので、浅いコピーより時間がかかる。どのくらいかかるかはtimeitの値で示す。内側のリストを1万個持つ入れ子のリスト(nested)と、整数1万個の平らなリスト(flat)について、式ごとに5回繰り返し、最も速い値を1回の呼び出しあたりのマイクロ秒で出力する。以下の2つの出力は同じスクリプトを2回動かした結果で、1回の所要時間はこのPCで2~3秒である。

import copy
                    import timeit
                    
                    def best_us(stmt, glb, number):
                        runs = timeit.repeat(stmt, globals=glb, number=number, repeat=5)
                        return min(runs) / number * 1e6
                    
                    for n in (100, 10000):
                        nested = [[i, i + 1, i + 2] for i in range(n)]
                        flat = list(range(n))
                        fast, slow = (2000, 200) if n == 100 else (200, 5)
                        g = {'copy': copy, 'nested': nested, 'flat': flat}
                        print('n =', n)
                        print('  nested.copy()             %10.1f us' % best_us('nested.copy()', g, fast))
                        print('  copy.copy(nested)         %10.1f us' % best_us('copy.copy(nested)', g, fast))
                        print('  copy.deepcopy(nested)     %10.1f us' % best_us('copy.deepcopy(nested)', g, slow))
                        print('  flat.copy()               %10.1f us' % best_us('flat.copy()', g, fast))
                        print('  copy.deepcopy(flat)       %10.1f us' % best_us('copy.deepcopy(flat)', g, slow))

同じコードの値が、2つの出力でかなり異なった。同じ式の値が出力ごとに違うので、絶対的な数値よりも大きさの差を読むべきである。1万個の入れ子のリストでは、copy.deepcopy(nested)はcopy.copy(nested)の約624~641倍(2つの出力の計算値)かかり、整数1万個のcopy.deepcopy(flat)もflat.copy()の約167~173倍(計算値)かかった。内側に可変オブジェクトのない整数のリストでも、deepcopyの値は浅いコピーより大きかった。上の倍率はこのPCの値であり、再実行すると変わる。

  • この大きさでは、浅いコピーの値は数十マイクロ秒で、deepcopyの値は数千~数万マイクロ秒(ミリ秒単位)だった。
  • deepcopyは、複製で内側の可変オブジェクトを変える場合に必要になる。読むだけの複製や内側を変えない複製は、4節の結果のとおり、浅いコピーで元に影響がない。
  • ループの中でdeepcopyを呼ぶコードは、コストが繰り返しの回数だけ掛け算になる。
  • この測定は、1台のPCでの2回の実行である。改善や減少を約束する値ではなく、データの形が違えば別の結果になりうる。

何を選ぶか - 選択の基準

これまでの出力から得た基準を表にまとめる。選択的コピーとdeepcopyの行は、次のコードの出力を根拠とする。最初のブロックは変えるフィールドだけを選んでコピーした場合、2番目のブロックはdeepcopyで丸ごとコピーした場合である。どちらも複製のlimitsを変えて、元を出力する。

import copy
                    
                    def make():
                        return {'name': 'base', 'tags': ['a'], 'limits': {'cpu': 1}}
                    
                    defaults = make()
                    one = {**defaults, 'tags': defaults['tags'].copy()}
                    one['tags'].append('b')
                    one['limits']['cpu'] = 8
                    print('selective copy:', defaults)
                    
                    defaults = make()
                    two = copy.deepcopy(defaults)
                    two['tags'].append('b')
                    two['limits']['cpu'] = 8
                    print('deepcopy      :', defaults)
selective copy: {'name': 'base', 'tags': ['a'], 'limits': {'cpu': 8}}
                    deepcopy      : {'name': 'base', 'tags': ['a'], 'limits': {'cpu': 1}}

選択的コピーはtagsをコピーしておいたので、tagsは元が守られたが、コピーしなかったlimitsが共有されて、元のlimitsは{'cpu': 8}になった。deepcopyでは、新しく作り直した元で、tagsもlimitsもそのままだった。選択的コピーはコピーするフィールドを漏らすことがあり、deepcopyにはコストがかかる。

点検の問いに縮めると、次のとおりである。

  • コピーの後で、内側の可変オブジェクトをその場で変えているか。
  • 複製の内側のオブジェクトが元と同じオブジェクトかどうかを、isで確認したか。
  • deepcopyを使うなら、コピーできない属性や共有すべき属性はないか。
  • ループの中のdeepcopyが、時間に影響していないか。
  • [[0] * n] * mのような繰り返しの式を使っていないか。

確認できなかったこと

  • deepcopyが遅い内部的な理由。このPCの測定値しかなく、どの段階で時間がかかるかはプロファイルしていない。
  • deepcopyが埋めたmemoの3つの項目が、それぞれ何か。個数だけを出力し、項目の正体は開いていない。
  • set、bytearray、ユーザー定義コンテナなど、リストと辞書以外のコンテナでのコピーの深さ。
  • PyPyのような他の実装や、他のPythonバージョンでの動作。タプルの浅いコピーが同じオブジェクトを返すことも、この環境(CPython 3.13.3)での観察である。
  • NumPy配列やpandasのデータフレームなど、外部ライブラリのオブジェクトのコピーの意味。
  • __copy__・__reduce__・copyregによるコピーの拡張と、それがdeepcopyのTypeErrorとどう関係するか。
  • スロット(__slots__)を使うクラスや、継承構造が複雑なオブジェクトのdeepcopyの結果。
  • マルチスレッドで、コピーの最中に元が変更されたときの動作。
