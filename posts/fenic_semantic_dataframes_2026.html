fenic과 시맨틱 연산자 - 데이터프레임에 LLM을 선언적으로 엮는 법

typedef의 오픈소스 PySpark 스타일 엔진이 LLM 호출을 데이터프레임 연산으로 바꾸는 이유와 그 한계

2026-07-11 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 비정형 텍스트는 왜 아직도 for 루프 안에 있는가

2026년 데이터 엔지니어링 현장에서 반복되는 질문이 있다. 정형 테이블은 SQL과 데이터프레임으로 깔끔하게 다루는데, 이메일·통화 녹취록·리뷰 같은 비정형 텍스트는 왜 여전히 별도 스크립트에서 LLM API를 한 건씩 호출하는 방식에 머물러 있는가. fenic은 이 질문에 정면으로 답하는 오픈소스 프로젝트다. 미국 스타트업 typedef가 만든 이 데이터프레임 라이브러리는 PySpark·SQL에 익숙한 연산 모델 위에 LLM 호출을 시맨틱 연산자(semantic operators)라는 이름의 1급 연산으로 얹는다.

이 글은 fenic이 실제로 무엇을 하는 프로젝트인지 먼저 확인한 뒤, 이 접근이 던지는 더 큰 질문 - 데이터 파이프라인에 LLM을 어떻게 결합해야 하는가 - 을 본인 관점에서 분석한다. 보도자료를 옮기는 글이 아니라, 유사 프로젝트인 LOTUS·LangChain·DSPy와 비교하며 이 흐름이 실무에 무엇을 의미하는지 짚는 글이다.

1. fenic이란 무엇인가 - typedef의 PySpark 스타일 데이터프레임

1.1 만든 곳과 배경

fenic을 만든 typedef는 데이터 인프라 엔지니어 Yoni Michael과 Kostas Pardalis가 세운 스타트업이다. 이 회사는 Pear VC가 주도하고 Verissimo Ventures, Monochrome Ventures, Tokyo Black 등이 참여한 550만 달러 규모 시드 투자를 유치하며 스텔스에서 나왔고, 그 발표와 동시에 fenic을 Apache 2.0 라이선스 오픈소스로 공개했다. 깃허브 저장소(typedef-ai/fenic)는 2025년 7월 공개됐고, 문서 사이트(docs.fenic.ai)가 API와 아키텍처를 상세히 안내한다. 핵심 엔진을 처음부터 오픈소스로 내놓았다는 점은, 이 회사의 사업 모델이 엔진 자체의 폐쇄가 아니라 그 위에 얹는 관리형 서비스나 인프라 쪽에 있음을 시사한다.

1.2 무엇을 표방하는가

fenic의 자기소개는 명확하다. 'LLM 추론을 염두에 두고 처음부터 만든 데이터프레임'이라는 표현을 쓴다. 기존 판다스(Pandas)나 스파크(Spark)에 LLM 호출 기능을 나중에 끼워 넣은 것이 아니라, 텍스트·마크다운·통화 녹취록 같은 비정형 데이터와 LLM 추론을 처음부터 1급 시민으로 다루도록 설계했다는 주장이다. 세션(Session) 단위로 모델을 한 번 설정하면 이후 파이프라인 전체에서 재사용되고, 지연 평가(lazy evaluation)와 쿼리 최적화를 거쳐 실행된다. 이 지점이 fenic을 단순한 LLM 래퍼 라이브러리와 구분 짓는 설계 철학이다.

2. 시맨틱 연산자란 무엇인가 - LLM 호출을 데이터프레임 연산으로

2.1 여덟 개의 연산자

fenic 문서 기준으로 semantic 네임스페이스 아래 여덟 개 연산자가 1급 데이터프레임 연산으로 제공된다. semantic.map은 각 행에 자연어 지시를 적용해 새 컬럼을 만들고, semantic.predicate(필터)는 자연어 조건으로 행을 거른다. semantic.join은 값이 정확히 같은지가 아니라 의미가 통하는지를 기준으로 두 데이터프레임을 결합하고, semantic.extract는 스키마를 지정해 비정형 텍스트에서 구조화된 필드를 뽑아낸다. semantic.classify는 소수의 예시만으로 텍스트를 범주에 배정하고, semantic.analyze_sentiment는 감성을 분류하며, semantic.group_by는 의미적 유사성을 기준으로 데이터를 군집화하고, semantic.reduce는 군집화된 데이터를 LLM 연산으로 집계·요약한다.

2.2 연산자로 만든다는 것의 의미

핵심은 이 여덟 개가 별도 API 호출이 아니라 select·filter·join·group_by·agg 같은 기존 데이터프레임 연산과 같은 문법 계층에 놓인다는 점이다. 개발자는 필터링과 구조화 추출, 분류 연산을 한 파이프라인 안에서 그대로 이어 붙일 수 있다. 이렇게 되면 LLM 호출은 '가끔 튀어나오는 예외적 단계'가 아니라 데이터프레임 실행 그래프의 정규 노드가 된다. 쿼리 옵티마이저가 이 노드까지 보고 실행 계획을 짤 수 있다는 뜻이고, 이것이 fenic이 '시맨틱 연산자'라는 용어를 쓰는 이유다.

3. 기존 방식 대비 선언적 통합의 장점

3.1 재현성

본인이 지금까지 봐 온 LLM 데이터 파이프라인의 전형적 패턴은 이렇다. 반복문을 돌며 각 행에 프롬프트를 조립해 API를 호출하고, 응답을 파싱해 담고, 실패하면 예외 처리를 손으로 붙인다. 이 방식은 프롬프트 문자열·파싱 로직·재시도 규칙이 스크립트마다 흩어져 있어, 같은 파이프라인을 두 번 실행해도 정확히 같은 방식으로 재현하기 어렵다. 스키마를 선언하고 연산자를 호출하는 방식은 '무엇을 뽑을지'와 '어떻게 실행할지'를 분리한다. 스키마와 연산은 코드로 버전 관리되고, 실행 방식(배치·재시도·모델 선택)은 엔진이 일관되게 처리한다.

3.2 배치와 비용 관리

수동 호출 방식에서는 배치 크기, 동시 요청 수, 속도 제한(rate limit) 대응을 개발자가 매번 직접 구현해야 한다. fenic은 이를 엔진 레벨 기능으로 제공한다고 밝힌다 - 자동 배치 최적화, 내장 재시도·속도 제한, 토큰·비용 집계다. 데이터프레임 연산 하나가 내부적으로 수천 건의 LLM 호출로 펼쳐질 수 있는 상황에서, 이 부분을 애플리케이션 코드가 아니라 엔진이 맡는다는 것은 실무적으로 꽤 큰 차이다.

3.3 관측 가능성

선언적 파이프라인의 또 다른 이점은 무엇이 실행됐는지 추적하기 쉬워진다는 점이다. 지연 평가 기반 쿼리 엔진은 실행 전에 계획을 세우므로, 각 단계에서 몇 건의 LLM 호출이 발생하는지, 어떤 스키마로 추출됐는지를 코드 전체를 다시 읽지 않고 실행 계획에서 확인할 수 있다. 프로덕션 파이프라인을 감사하거나 비용 급증 원인을 추적할 때 실질적으로 유용한 특성이다.

4. PySpark/SQL 친화 인터페이스가 갖는 의미

익숙한 연산 위에 시맨틱 연산자를 얹는다는 설계는 기술적 선택이자 채택 전략이기도 하다. 데이터 엔지니어링 조직 대다수는 이미 Spark나 SQL 기반 파이프라인을 운영한다. 완전히 새로운 패러다임을 배우게 하는 대신, 익숙한 문법에 LLM 연산 하나를 이어 붙이는 방식은 학습 곡선을 크게 낮춘다. SQL 인터페이스까지 제공한다는 점은 파이썬 스크립트에 익숙하지 않은 분석가·BI 담당자도 시맨틱 연산자를 SQL 문 안에서 호출할 수 있다는 뜻이다. 다만 이는 동시에 한계이기도 하다 - 스파크식 분산 처리 문법과 최적화 모델을 그대로 따르므로, 스트리밍이나 매우 낮은 지연이 필요한 실시간 추론 시나리오에는 애초에 맞지 않는 설계다.

5. 유사 접근과 비교 - LOTUS, LangChain, DSPy

5.1 LOTUS - 개념의 원류

시맨틱 연산자라는 개념 자체는 fenic이 처음 만든 것이 아니다. 스탠퍼드·버클리 연구팀이 만든 LOTUS(LLMs Over Tables of Unstructured and Structured data)가 먼저 이 용어를 학술적으로 정립했다. Apache Spark를 만든 Matei Zaharia와 Carlos Guestrin이 지도한 이 프로젝트는 sem_filter·sem_join 같은 판다스 스타일 API를 제공하고, VLDB 학술지에 게재된 논문에서 연산 최적화로 비용과 지연을 크게 낮출 수 있음을 정량적으로 보였다. fenic은 이 학술적 개념을 프로덕션 지향 엔진으로 가져온 상업적 구현에 가깝다. 개념의 계보는 LOTUS 쪽이 앞서고, fenic은 PySpark 호환성과 엔지니어링 인프라(재시도·배치·비용 추적)에 더 무게를 둔 것으로 읽힌다.

5.2 LangChain - 오케스트레이션 vs 쿼리 엔진

LangChain은 LLM 호출·툴 사용·메모리를 사슬처럼 명령형으로 엮는 오케스트레이션 프레임워크다. 방대한 통합 생태계와 빠른 프로토타이핑이 강점이지만, 데이터 처리량이 커질수록 배치·재시도·비용 관리를 애플리케이션 코드가 직접 짊어져야 한다. fenic은 애초에 '체인을 만드는 도구'가 아니라 '테이블을 처리하는 쿼리 엔진'으로 설계됐다. 수백만 행의 텍스트를 일괄 처리하는 배치형 파이프라인이라면 fenic 쪽 모델이, 대화형 에이전트나 도구 사용이 핵심인 애플리케이션이라면 LangChain 쪽 모델이 더 자연스럽다.

5.3 DSPy - 프롬프트 최적화 vs 데이터 처리

DSPy는 프롬프트 자체를 학습 가능한 파라미터로 놓고, 레이블된 데이터셋에 대해 프롬프트나 파인튜닝 어댑터를 자동으로 최적화하는 프레임워크다. '무엇을 실행할지'를 다루는 fenic·LangChain과 달리, DSPy는 '어떻게 하면 이 프롬프트가 더 잘 작동하게 만들 것인가'라는 다른 축의 문제를 다룬다. 실제로는 상호 배타적이지 않다 - fenic의 semantic.map이 호출하는 프롬프트 자체를 DSPy 스타일로 최적화한 뒤 fenic 파이프라인에 얹는 조합도 이론적으로는 가능하다. 세 프로젝트를 한 줄로 정리하면, fenic은 '데이터를 어떻게 처리할지', LangChain은 '에이전트가 무엇을 할지', DSPy는 '프롬프트를 어떻게 최적화할지'를 각각 답한다.

6. 실무 적용 시나리오 - 어디에 쓸 것인가

본인이 보기에 fenic류 접근이 가장 빛나는 지점은 반복적이고 대량인 비정형 텍스트 처리다. 고객 리뷰 수만 건에서 불만 유형을 분류하는 작업, 통화 녹취록에서 구조화된 필드(고객명·문의 유형·해결 여부)를 뽑아내는 작업, 여러 소스에서 온 상품 설명을 의미 기준으로 조인해 카탈로그를 통합하는 작업이 전형적인 적합 사례다. 이런 작업은 본질적으로 배치이고, 같은 파이프라인을 매일 또는 매주 반복 실행하며, 재현성과 비용 예측이 중요하다. 반대로 사용자와 실시간으로 주고받는 챗봇, 매 요청마다 다른 도구를 골라 써야 하는 자율 에이전트에는 fenic의 배치·쿼리 최적화 모델이 크게 도움이 되지 않는다. 그 영역은 LangChain이나 에이전트 전용 프레임워크의 몫으로 남는다.

7. 한계와 주의점 - 비용, 비결정성, 정확도

세 가지를 분명히 짚어야 한다. 첫째, 비용이다. 시맨틱 연산자 하나가 데이터프레임 한 컬럼처럼 보여도, 내부적으로는 행마다 LLM 호출이 발생한다. 수백만 행에 semantic.extract를 걸면 API 비용이 그대로 수백만 건의 추론 비용으로 이어진다. 엔진이 배치를 최적화해 줄 수는 있어도, 근본적인 추론 횟수를 줄여 주지는 않는다.

둘째, 비결정성이다. SQL의 WHERE 절은 같은 입력에 항상 같은 결과를 내지만, semantic.predicate는 같은 조건이라도 모델 버전이나 온도(temperature) 설정에 따라 결과가 흔들릴 수 있다. 결정적 연산과 확률적 연산을 같은 파이프라인 문법으로 섞어 쓴다는 것은 편리하지만, 그 경계를 팀 전체가 인지하고 있어야 한다.

셋째, 정확도 검증이다. classify나 extract의 출력을 곧바로 다음 단계 입력으로 신뢰하면, 초기 단계의 오류가 파이프라인 뒤로 갈수록 누적·증폭된다. 프로덕션에 넣기 전에 골든 셋으로 각 시맨틱 연산자의 정확도를 별도로 측정하는 절차가 필요하다.

결론: 스크립트 더미에서 선언적 파이프라인으로

fenic이 던지는 진짜 질문은 '이 라이브러리를 쓸 것인가'가 아니라, '비정형 텍스트를 다루는 파이프라인을 계속 스크립트 더미로 유지할 것인가, 아니면 정형 데이터처럼 선언적 연산으로 관리할 것인가'다. 시맨틱 연산자라는 개념은 LOTUS의 연구에서 이미 그 정당성을 학술적으로 입증했고, fenic은 이를 PySpark에 익숙한 데이터 엔지니어가 바로 쓸 수 있는 형태로 제품화했다.

2026년 7월 기준으로 이 프로젝트는 아직 초기 오픈소스 생태계 단계이지만, 비정형 데이터를 대량·반복적으로 처리해야 하는 데이터 엔지니어링 조직이라면 골든 셋 기반의 파일럿으로 먼저 검증해 볼 가치가 있다. 다만 실시간 대화형 에이전트를 만드는 팀이라면 fenic보다 LangChain이나 에이전트 전용 프레임워크가 더 맞는 도구라는 점은 분명히 해 두고 싶다.
