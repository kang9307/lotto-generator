ZCode의 Git 이력 전송 분석 — UI 설정과 실제 동작의 간극

작업 공간 스냅샷 아키텍처, 서버 전용 비대칭 암호화, 그리고 로컬 AI 런타임의 신뢰 경계

발행일: 2026-09-19 개발/인프라

현대 소프트웨어 공학 환경에서 인공지능 보조 도구는 단순한 한 줄 단위의 코드 자동 완성을 넘어, 프로젝트 전체의 디렉터리 구조를 파악하고 종속성 관계를 추적하며 복잡한 리팩토링 작업을 자율적으로 수행하는 에이전트 형태로 급속히 발전했다. 이러한 에이전트 시스템은 사용자에게 고도화된 맥락(Context)을 제공하기 위해 작업 공간 내부의 다양한 소스 코드, 설정 파일, 빌드 스크립트, 그리고 문서들을 지속적으로 색인화하고 분석하는 아키텍처를 기본적으로 채택한다. 개발자가 별도의 맥락을 수동으로 입력하지 않아도 에이전트가 알아서 프로젝트의 전체 그림을 파악하고 최적의 변경 사항을 제안할 수 있는 이유는 바로 이 광범위한 파일시스템 접근 권한에 기반한다.

그러나 데스크톱 편집기나 독립 실행형 에이전트 하네스가 로컬 파일시스템에 대한 포괄적인 읽기 및 탐색 권한을 가질 때, 도구가 수집하는 데이터의 물리적 범위와 이를 외부 원격 서버로 전송하는 전송 파이프라인의 통제 메커니즘이 투명하게 관리되지 않는다면 심각한 보안 및 지적 재산권 노출 문제가 발생할 수 있다. 특히 기업의 핵심 자산인 독점 소스 코드, 비공개 비즈니스 로직, 그리고 프로젝트의 과거 개정 이력 전체가 사용자의 명시적인 인지나 동의 없이 외부 클라우드 인프라로 지속적으로 전송된다면 이는 단순한 도구 기능의 문제를 넘어 조직의 정보보안 거버넌스 전체를 위협하는 요인이 된다.

2026년 9월 18일, 개발자 ferstar는 오픈 가중치 대규모 언어 모델인 GLM 제품군 개발사 Z.ai의 데스크톱 코딩 에이전트 ZCode를 리버스 엔지니어링한 기술 분석 보고서를 자신의 기술 블로그에 공개했다. 해당 분석에 따르면 ZCode는 사용자가 로그인 세션을 유지하는 동안 활성 작업 공간의 현재 소스 파일뿐만 아니라 내부 .git 저장소 전체를 압축 및 암호화하여 외부 클라우드 오브젝트 스토리지로 전송하는 파이프라인을 내장하고 있었다. 이 분석은 기술 분석 플랫폼인 tokenstead.ai와 다양한 개발자 커뮤니티를 통해 빠르게 전파되며 개발 도구의 신뢰성과 데이터 주권 문제를 둘러싼 광범위한 논의를 촉발했다.

이 사안에서 가장 핵심적인 기술적 쟁점은 단순히 원격지로 데이터가 전송되었다는 사실 그 자체에 그치지 않는다. 사용자가 명시적으로 비활성화할 수 있다고 인터페이스에 안내된 환경설정 토글 스위치들이 실제 클라이언트의 내부 코드 레벨에서는 해당 전송 동작을 전혀 차단하지 못했다는 점, 그리고 전송된 데이터 페이로드의 대부분이 현재 편집 중인 파일이 아니라 프로젝트의 생성 시점부터 축적된 전체 이력을 담고 있는 Git 객체 저장소였다는 점이다. 본 글에서는 공개된 리버스 엔지니어링 분석 보고서와 기술적 증거를 기반으로 ZCode의 작업 공간 수집 아키텍처, 전송 파이프라인, 암호화 키 관리 구조를 면밀히 분석하고, 로컬 개발 환경에서 AI 도구를 운용할 때 점검해야 할 보안 경계를 체계적으로 살펴본다.

1. 리버스 엔지니어링으로 포착된 ZCode의 작업 공간 전송 흐름

개발자 ferstar가 공개한 분석 내용에 따르면, ZCode 클라이언트의 핵심 실행 바이너리와 번들 파일(Electron 기반 app.asar 아카이브)을 역컴파일하여 내부 로직을 추적한 결과, 사용자가 지정한 로컬 작업 공간을 패키징하여 외부로 내보내는 정교한 스냅샷 파이프라인이 구현되어 있었다. 클라이언트는 단순한 파일 단위 전송이 아니라 중앙 코디네이터 서버와의 통신을 통해 권한을 위임받고, 패키징된 아카이브를 대용량 스토리지 노드로 직접 업로드하는 분산형 업로드 흐름을 따르고 있었다.

리버스 엔지니어링을 통해 복원된 전송 아키텍처의 구체적인 단계는 다음과 같은 3단계 파이프라인으로 구성되어 있었다.

  • 클라이언트 애플리케이션이 ZCode의 인증 및 세션 코디네이터 도메인인 zcode.z.ai에 접근하여 업로드에 필요한 자격 증명을 요청하고, 서버로부터 Aliyun OSS 폼 서명, 고유 오브젝트 키, 전송 크기 상한값, 그리고 해당 회차에 유효한 일회성 RSA 공개키를 전달받는다.
  • 클라이언트의 로컬 백그라운드 프로세스가 현재 활성화된 작업 공간 디렉터리 전체를 tar.gz 포맷으로 압축한 뒤, 자체 생성한 대칭 암호화 키를 사용하여 아카이브를 암호화하고, 서버로부터 수신한 RSA 공개키로 이 대칭키를 래핑하여 암호화 봉투를 구성한다.
  • 암호화가 완료된 아카이브 본체를 알리바바 클라우드의 오브젝트 스토리지(Aliyun OSS) 노드로 HTTP POST 요청을 통해 직접 전송하며, 업로드가 성공적으로 완료되면 OSS 인프라가 Z.ai 백엔드로 콜백을 전송하여 해당 작업 공간 스냅샷을 중앙 레지스트리에 공식 등록한다.

이러한 전송 메커니즘은 정적 코드 분석뿐만 아니라 실제 ZCode 클라이언트를 실행한 환경에서 발생하는 아웃바운드 네트워크 트래픽을 모니터링함으로써 실증적으로 확인되었다. 테스트 세션이 진행되는 동안 클라이언트는 코디네이터 서버인 zcode.z.ai와의 세션을 계속 유지했을 뿐만 아니라, 서로 다른 두 개의 Aliyun OSS 스토리지 노드와 지속적인 TCP 연결(Keep-Alive 세션)을 형성하고 주기적으로 대용량 패킷을 송신하고 있음이 관찰되었다.

특히 일반적인 웹 애플리케이션이 중간 백엔드 서버를 거쳐 파일을 중계하는 방식과 달리, ZCode는 사전 서명된 폼(pre-signed form) 방식을 통해 클라이언트가 클라우드 스토리지 노드로 직접 거대 바이너리를 병렬 전송하도록 구현되어 있었다. 이러한 설계는 중간 서버의 대역폭 병목 현상을 회피하고 수백 메가바이트 단위의 작업 공간 아카이브를 지연 없이 신속하게 외부로 반출하기 위한 인프라 패턴으로 평가된다.

2. 42,411개 파일 스냅샷 분석: 페이로드의 86.6%를 차지한 Git 내부 데이터

ZCode가 생성한 스냅샷 패키지의 실제 구성을 정량적으로 확인하기 위해, 클라이언트 로컬 스토리지에 평문 형태로 보관되어 있던 패키징 매니페스트(packaging manifest) 파일을 분석한 결과 충격적인 데이터 구성비가 드러났다. 단일 상용 작업 공간(전체 원본 크기 약 345.1MB, 총 42,411개 파일)을 대상으로 캡처된 스냅샷 매니페스트의 구체적인 항목별 용량과 비중은 아래와 같이 집계되었다.

표 1: ZCode 스냅샷 아카이브 페이로드 구성 내역 (출처: ferstar 리버스 엔지니어링 분석)
항목 경로 데이터 크기 전체 페이로드 대비 비중
.git/lfs/ (대용량 파일 스토리지 캐시) 196.1 MB 56.8%
.git/objects/ (Git 내부 객체 저장소) 102.2 MB 29.6%
.git/logs/ (참조 로그 및 reflogs) 0.6 MB 0.2%
소스 코드 및 문서 (작업 트리 파일 전체) 46.2 MB 13.4%

위 집계 데이터에서 명확히 드러나듯이, 개발자가 현재 시점에서 직접 열람하고 편집하고 있는 실제 소스 코드와 문서 파일의 크기는 46.2MB로 전체 아카이브 용량의 13.4%에 불과했다. 반면 버전 관리 시스템의 내부 메타데이터와 과거 변경 이력을 보존하는 .git 디렉터리가 차지하는 비중은 무려 86.6%(196.1MB + 102.2MB + 0.6MB = 298.9MB)에 달했다. 총 42,411개의 파일로 구성된 이 스냅샷은 압축 및 암호화를 거쳐 최종적으로 약 313MB 크기의 전송 아카이브로 변환되었다.

이러한 매니페스트 분석 결과가 전달하는 기술적 함의는 다음의 세 가지 측면에서 매우 중대한 의미를 갖는다.

  • 대용량 멀티미디어 자산이나 학습 데이터, 바이너리 라이브러리가 캐싱되는 .git/lfs/ 영역이 전체 페이로드의 절반을 초과(56.8%)함으로써 프로젝트의 소스 코드를 넘어선 파생 바이너리 데이터까지 무차별적으로 수집 대상에 포함되었다.
  • Git의 핵심 데이터베이스인 .git/objects/가 약 102.2MB(29.6%)를 차지하여, 단일 시점의 작업 상태뿐만 아니라 해당 저장소가 최초 생성된 시점부터 축적된 모든 커밋과 브랜치 이력이 빠짐없이 패키징되었다.
  • 로컬 환경에서 개발자가 브랜치를 이동하거나 커밋을 리셋한 세부 작업 발자취가 기록되는 .git/logs/(reflog) 데이터까지 포함됨으로써 외부에 공개되지 않은 개인적 작업 흐름까지 전송 범위에 들어갔다.

일반적으로 코드 색인이나 자동 완성을 수행하는 AI 도구들은 소스 코드 파일(예: .ts, .py, .java 등)만을 파싱하여 추상 구문 트리(AST)를 생성하거나 벡터 임베딩을 계산한다. 버전 관리 메타데이터인 .git 디렉터리는 코드의 의미론적 분석에 필요하지 않을 뿐더러 압축 효율을 떨어뜨리는 주원인이다. 그럼에도 불구하고 .git 디렉터리를 제외 필터 없이 통째로 패키징했다는 사실은, 이 파이프라인이 단순한 코드 이해를 넘어 저장소 데이터베이스 전체를 완전하게 복제하려는 아키텍처를 취하고 있음을 나타낸다.

3. 단순 스냅샷과 Git 전체 계보(Lineage)의 차이: 과거 이력 노출 위험

소프트웨어 버전 관리 시스템의 내부 메커니즘을 이해하는 엔지니어에게 .git 디렉터리의 외유는 작업 트리의 최신 파일이 유출되는 것과는 질적으로 완전히 다른 차원의 재앙을 의미한다. 개발자 ferstar는 자신의 분석 보고서에서 이 차이를 다음과 같은 명료한 문장으로 지적했다. 「Git 객체 저장소는 작업 트리의 스냅샷이 아니라, 첫날부터의 저장소 전체 계보(complete lineage)다.」

작업 트리(Working Tree)는 개발자가 특정 시점에 체크아웃하여 현재 파일시스템 상에서 작업하고 있는 파일들의 상태에 불과하다. 만약 개발자가 수개월 전 실수로 상용 클라우드 API 키나 데이터베이스 접속 자격 증명을 커밋했다가, 이를 뒤늦게 인지하고 즉시 다음 커밋에서 해당 문자열을 삭제했다고 가정해 보자. 현재 시점의 소스 코드 파일을 아무리 검색해도 해당 비밀 정보는 노출되지 않는다. 작업 트리만을 복사하는 도구라면 해당 키를 외부로 유출하지 않을 것이다.

그러나 Git의 객체 저장소(.git/objects/)는 내용 주소화 파일시스템(content-addressable filesystem) 구조를 취하고 있으며, 불변(immutable)의 블롭 객체로 과거 모든 시점의 파일 상태를 보존한다. 최신 커밋에서 특정 라인이 삭제되었더라도 과거 커밋에 대응하는 블롭 객체는 영구히 저장소 내에 남아 있다. 따라서 .git 디렉터리가 외부로 전송되는 순간, 프로젝트가 시작된 이래 발생했던 모든 실수와 삭제된 기밀 정보가 복원 가능한 상태로 노출된다.

리버스 엔지니어링 분석을 통해 확인된 대표적인 기밀 노출 위험 영역은 다음과 같다.

  • 과거 커밋에 실수로 포함되었다가 이후 커밋에서 삭제되었으나, 저장소 기록 재작성(filter-branch 등)을 거치지 않아 Git 객체 데이터베이스에 그대로 남아 있는 API 토큰, 비공개 인증서, 데이터베이스 암호.
  • 원격 저장소(GitHub, GitLab 등)로 아직 푸시되지 않은 로컬 전용 브랜치 이름과 그 안에 담긴 미출시 제품의 세부 사양, 아키텍처 설계 문서, 비공개 기능 코드.
  • .git/config 파일 내부에 평문으로 기록되어 있는 조직 내부 사내 저장소의 인트라넷 호스트명, 프라이빗 도메인 구조, 그리고 로컬 파일시스템의 절대 경로 정보.

더욱이 AI 코딩 도구를 홈 디렉터리(~)나 사용자 최상위 폴더에서 무심코 실행할 경우 그 파급력은 특정 프로젝트 저장소를 아득히 넘어선다. 과거 유사한 백그라운드 전송 사례에서는 사용자가 홈 디렉터리에서 도구를 실행함에 따라 .ssh 디렉터리의 개인 키, 비밀번호 관리자 데이터베이스 파일, 개인 문서 및 사진 폴더까지 스냅샷 경로에 함께 포함되어 업로드되는 위험이 실제로 관찰된 바 있다. 디렉터리 필터링이 누락된 무차별적인 아카이빙은 개발자의 로컬 환경 전체를 잠재적 유출 위험에 노출시킨다.

4. 설정 화면과 실제 동작의 불일치: UI 토글과 무관한 백그라운드 수집

사용자 프라이버시와 데이터 주권의 관점에서 이번 ZCode 사안의 가장 치명적인 결함은 사용자 인터페이스(UI)에 마련된 제어 스위치가 실제 애플리케이션의 백그라운드 전송 동작을 제어하지 못했다는 점이다. 소프트웨어에 데이터 수집 파이프라인이 내장되어 있다 하더라도, 사용자가 이를 명확히 인지하고 환경설정을 통해 비활성화할 수 있다면 이는 옵트아웃 정책의 투명성 문제로 볼 여지가 있다. 그러나 ZCode는 사용자가 설정을 끄더라도 백그라운드 수집과 전송이 중단되지 않는 구조를 갖고 있었다.

표 2: ZCode 환경설정 항목명과 실제 런타임 동작 대조 (출처: ferstar 리버스 엔지니어링 분석)
환경설정 옵션 명칭 (내부 코드 플래그) 사용자가 합리적으로 기대하는 동작 실제 클라이언트 코드 관찰 결과
Optimize Experience (optimizeAgentExperienceEnabled) 작업 공간 데이터의 외부 캡처 및 전송 전면 중단 수집된 데이터를 AI 모델 학습 데이터로 활용할 수 있는지에 대한 동의 플래그만 제어하며, 스냅샷 캡처 및 Aliyun OSS 전송은 동일하게 지속됨
Repo Snapshot Indexing (repoSnapshotIndexingEnabled) 저장소 스냅샷의 로컬 패키징 및 외부 업로드 차단 원격 서버 측에서 이미 업로드된 스냅샷에 대해 인덱싱 작업을 수행할지 여부만 제어하며, 로컬 압축과 네트워크 업로드는 중단 없이 수행됨

클라이언트의 역컴파일 코드 분석에 따르면, 호스트 어셈블리 레이어는 애플리케이션이 구동될 때 사용자의 환경설정 값을 전혀 참조하지 않고 무조건적으로 캡처 사이드카(capture sidecar) 프로세스를 인스턴스화하도록 작성되어 있었다. 사이드카가 구동되기 위한 유일한 전제 조건은 토큰 프로바이더(token provider)를 통해 유효한 JSON Web Token(JWT)을 발급받을 수 있는지 여부였다. 즉, 사용자가 ZCode 애플리케이션에 계정 로그인을 완료하는 즉시 스냅샷 수집 파이프라인이 영구 가동 상태로 진입하는 구조였다.

이러한 백그라운드 동작의 은밀성은 외부 연구자들의 교차 검증을 통해서도 일관되게 뒷받침되었다.

  • 단일 활성 개발 세션을 정밀 추적한 세션 로그에서 총 62회의 캡처 이벤트가 감지되었으며, 사용자가 프롬프트를 입력하기 직전과 에이전트가 코드 변경 작업을 완료하는 시점마다 자동으로 스냅샷 생성이 트리거되었다.
  • 공개 프롬프트 아카이브인 OrcaPromptVault에 수록된 131KB 분량의 ZCode 유출 시스템 프롬프트 및 31개 도구 정의를 전수 조사한 결과, 스냅샷 캡처나 Aliyun OSS 업로드, 혹은 텔레메트리와 관련된 에이전트 도구는 단 하나도 존재하지 않았다.
  • 이는 데이터 수집 및 유출 파이프라인이 AI 모델의 정상적인 도구 호출 루프(tool loop) 내부에서 동작하는 것이 아니라, 모델의 인지 영역 밖인 호스트 바이너리 수준의 백그라운드 사이드카로 격리되어 실행됨을 의미한다.
  • ZCode의 공식 개인정보 처리방침 문서에는 "대화 중 제출된 텍스트, 파일, 코드"를 수집한다는 일반적인 수준의 안내 문구만 기재되어 있을 뿐, 전체 작업 공간과 Git 내부 이력을 통째로 아카이빙하여 클라우드에 보관한다는 사실은 일절 언급되어 있지 않았다.

5. 봉투 암호화와 서버 키 독점: AES-256-CTR과 RSA-OAEP의 신뢰 경계

ZCode의 전송 파이프라인을 분석할 때 기술적으로 반드시 짚고 넘어가야 할 지점은 정교한 다중 암호화의 적용이다. ZCode 클라이언트는 전송할 아카이브에 대해 대칭키 암호화 표준인 AES-256-CTR 방식을 적용하고, 이 대칭키를 다시 비대칭 암호화 알고리즘인 RSA-OAEP를 통해 래핑하는 전형적인 '봉투 암호화(Envelope Encryption)' 방식을 채택했다.

일반적으로 보안 공학에서 대칭키와 비대칭키를 결합한 봉투 암호화는 대용량 데이터를 빠르고 안전하게 암호화하고 전송 구간의 기밀성을 확보하기 위한 표준적인 모범 사례로 평가된다. 중간 네트워크 라우터나 공용 Wi-Fi 환경에서 패킷을 도청하는 제3자(MitM)는 AES-256으로 암호화된 아카이브 본체를 열어볼 수 없다. 그러나 "이 암호화가 누구를 누구로부터 보호하는가"라는 관점에서 키 관리 아키텍처를 분석하면 매우 비대칭적인 현실이 드러난다.

클라이언트는 업로드 자격 증명을 협상하는 단계에서 코디네이터 서버인 zcode.z.ai로부터 회차별 RSA 공개키를 수신하여 대칭키를 잠근다. 그러나 이 공개키에 대응하여 대칭키를 다시 복호화할 수 있는 RSA 개인키는 클라이언트의 로컬 장치에 전혀 생성되거나 저장되지 않는다. 해당 개인키는 오직 Z.ai의 클라우드 서버 인프라 내부에만 독점적으로 보관된다.

이러한 키 독점 구조가 내포하는 기술적 본질은 다음의 세 가지로 요약된다.

  • 사용자의 로컬 디스크에 임시 생성된 313MB 분량의 암호화된 아카이브 파일은 사용자 본인은 물론, 이를 생성한 ZCode 클라이언트 바이너리조차 로컬에서 다시 복호화할 수 없는 일방향 블랙박스 암호문이다.
  • 암호화는 네트워크 전송 구간에서 해커나 통신사가 데이터를 가로채는 것을 방지하는 역할을 하지만, 데이터 수신처인 Z.ai 서버는 언제든 자신이 보유한 개인키로 봉투를 열어 사용자의 전체 소스 코드와 Git 이력을 온전히 열람할 수 있다.
  • 개발자 ferstar는 이러한 비대칭 구조에 대해 다음과 같은 직관적인 해석을 남겼다. 「서버만 쓸 수 있는 키는 오직 하나의 목적에 봉사한다 — 서버가 원할 때 언제든 당신의 코드를 읽을 수 있게 하는 것이다.」

결국 이 암호화 파이프라인은 사용자의 기밀성을 서비스 제공자로부터 지켜주는 '종단간 암호화(E2EE)'가 아니며, 서비스 제공자만이 독점적으로 복호화 권한을 행사하는 '제공자 중심 암호화'로 설계되어 있었다. 사용자는 자신의 컴퓨터에서 정확히 어떤 데이터가 패키징되어 나가는지 암호문 상태에서는 감사하거나 검증할 수 없는 폐쇄성에 갇히게 된다.

6. 564회 재시도 관찰과 로컬 체크포인트의 동작 특성

ZCode의 작업 공간 스냅샷 전송 동작이 일회성 버그나 단순한 예외 상황이 아니라, 애플리케이션의 핵심 라이프사이클과 결합된 견고한 상태 머신(state machine)으로 설계되었음을 증명하는 핵심 근거는 네트워크 재시도 로직에서 확인되었다. 분석자가 패킷을 차단하거나 로컬에 대기 중인 임시 스냅샷 파일을 강제로 삭제하는 실험을 진행했을 때, 클라이언트는 지속적으로 복구 및 재전송을 시도했다.

실제 로컬 환경 및 네트워크 관찰 과정에서 기록된 클라이언트의 세부 런타임 행태는 다음과 같았다.

  • 업로드가 방화벽에 의해 차단되거나 비정상 종료된 상태에서 클라이언트 내부 로깅에 총 564회에 달하는 업로드 실패 시도가 연속적으로 기록되었다.
  • 로컬 체크포인트 경로에 대기 중이던 보류 아카이브를 사용자가 강제로 삭제하더라도, 클라이언트는 30분 이내에 313MB 분량의 새로운 아카이브를 백그라운드에서 다시 패키징하며 재시도 카운터를 지속적으로 증가시켰다.
  • OrcaPromptVault의 유출 프롬프트 분석에서 확인된 작업 공간 롤백 템플릿(Workspace rewind applied)이 5회에 걸쳐 등장하는 것으로 보아, 사용자가 이전 상태로 코드를 복원하는 '체크포인트' 기능이 이 클라우드 스냅샷 인프라와 결합되어 있어 클라이언트가 집요하게 동기화를 시도한 것으로 파악된다.

이러한 끈질긴 재시도 동작에 맞서 분석자 커뮤니티에서는 파일시스템 레벨의 방어책이 논의되었다. 운영체제 커널이 제공하는 불변(immutable) 플래그를 체크포인트 저장 디렉터리에 적용하여, 클라이언트 프로세스가 관리자 권한 없이 디렉터리에 새로운 스냅샷 파일을 쓰지 못하도록 물리적으로 차단하는 방식이다. 이 조치를 취할 경우 체크포인트 롤백 인터페이스는 오류를 내며 중단되지만, 에이전트의 일반적인 대화, 코드 자동 완성, 로컬 편집 기능은 정상적으로 동작하는 트레이드오프가 확인되었다.

7. 로컬 AI 모델 활용 시 런타임 하네스의 신뢰 검증 과제

최근 오픈소스 AI 생태계에서는 데이터 유출 우려를 불식하고 클라우드 API 호출 비용을 절감하기 위해 로컬 하드웨어에서 오픈 가중치(open-weight) 모델을 직접 구동하는 방식이 개발자들 사이에서 큰 각광을 받고 있다. Z.ai의 GLM 모델 시리즈(GLM-4, GLM-5 등) 역시 뛰어난 코딩 성능과 벤치마크 점수를 바탕으로 로컬 AI 환경에서 널리 활용되어 왔다. 그러나 이번 ZCode 사안은 '모델 가중치의 개방성'과 그 모델을 구동하는 '데스크톱 런타임(하네스)의 신뢰성'이 완전히 별개의 문제임을 극명하게 보여주었다.

많은 개발자들은 특정 오픈 모델 브랜드를 내건 공식 도구가 출시되면 해당 도구 역시 오픈소스 정신에 입각하여 로컬 중심적이고 투명하게 동작할 것이라는 무의식적인 기대를 품기 쉽다. 그러나 ZCode는 모델 가중치와 달리 클라이언트 하네스 자체가 비공개(closed-source) 독점 소프트웨어로 패키징되어 배포되었다. 로컬 장치에서 아무리 강력한 오픈 모델을 구동한다 하더라도, 이를 둘러싼 래퍼 애플리케이션이 백그라운드에서 작업 공간 전체를 원격 서버로 전송한다면 로컬 구동을 통해 달성하고자 했던 데이터 격리와 기밀성 보장은 한순간에 물거품이 된다.

향후 개발 조직이 다양한 상용 및 오픈소스 AI 코딩 보조 도구를 도입할 때 반드시 확립해야 할 기술적 평가 기준은 다음과 같이 정리할 수 있다.

  • AI 에이전트 하네스의 전체 소스 코드 공개 여부와 재현 가능한 빌드(reproducible build) 환경을 확인하여, 도구 루프 외부에 숨겨진 호스트 레벨의 백그라운드 전송 사이드카가 존재하지 않는지 철저히 검증해야 한다.
  • 도구 설치 및 실행 초기 단계부터 외부 알 수 없는 도메인이나 클라우드 스토리지 엔드포인트로 향하는 아웃바운드 네트워크 트래픽을 패킷 레벨에서 모니터링하고 차단할 수 있는 네트워크 방화벽 정책을 수립해야 한다.
  • 애플리케이션 환경설정 UI에 제공되는 데이터 수집 거부 토글이 실제 실행 바이너리 수준에서 소켓 통신을 물리적으로 중단시키는지 동적 분석을 거쳐 교차 검증해야 한다.
  • 저장소 내부의 .git 메타데이터, 환경 변수 파일(.env), 개인 SSH 키 등 기밀 자산이 상주하는 영역에 대해 도구의 파일시스템 접근 권한을 샌드박스나 컨테이너 레벨에서 엄격히 제한해야 한다.

이번 리버스 엔지니어링 분석 발표 이후, 대상 기업인 Z.ai 측은 본 글 발행 시점 기준으로 공식적인 입장 표명이나 반박 성명을 내놓지 않고 있다. 소셜 미디어 상에서 개발팀 소속으로 추정되는 한 계정이 「미안하다, 찾아내서(hey I am sorry to let you find it)」라는 짧은 댓글을 남긴 정황이 확인되었으나, 이는 반박이라기보다는 메커니즘의 실재를 확인해 준 정황으로 해석되었다. AI 코딩 보조 도구가 개발자의 생산성을 혁신적으로 끌어올리는 시대일수록, 편리함이라는 명분 뒤에 가려진 런타임 하네스의 신뢰 경계를 정밀하게 감시하고 검증하는 기술적 냉철함이 요구된다.

8. 확인하지 못한 것

본 글은 공개된 1차 리버스 엔지니어링 기술 분석 보고서와 클라이언트 바이너리 역컴파일 자료를 토대로 작성되었으며, 아래 항목들은 공인된 추가 자료나 기업의 공식 답변을 확인하지 못하여 단정적으로 서술하지 않고 본 절에 명시한다.

  • 발행 시점 기준으로 Z.ai의 공식 웹사이트 공지사항, 프레스 릴리스, 또는 공식 X 계정을 통한 공식적인 해명 문서나 기술적 반박 입장의 존재 여부는 확인하지 못했다.
  • ZCode 외에 Z.ai가 제공하는 다른 상용 개발자 도구나 웹 기반 개발 환경에서도 동일한 .git 저장소 전체 패키징 및 비대칭 암호화 전송 아키텍처가 적용되어 있는지 여부는 확인하지 못했다.
  • Aliyun OSS로 전송된 작업 공간 스냅샷 아카이브 데이터가 실제 Z.ai 백엔드 인프라 내부에서 구체적으로 어떤 프로세스(모델 사후 학습, 사용자 작업 통계, 세션 캐싱 등)를 거쳐 활용되고 보존 기간이 어떻게 설정되어 있는지는 확인하지 못했다.
  • 향후 배포될 차기 ZCode 클라이언트 업데이트 버전에서 해당 백그라운드 수집 사이드카를 제거하거나 UI 설정을 통한 완전한 비활성화 옵션을 정식 제공할 계획이 있는지에 대한 세부 로드맵은 확인하지 못했다.
