본문의 근거는 ClickHouse가 GitHub에 공개한 pg_chdb 저장소의 README(2026-09-15 확인)다. 성능 수치는 README가 밝힌 실측 그대로다. 다른 확장(pg_duckdb·pg_lake·aws_s3)의 성능 서술은 README의 비교 문맥에 한정하고, 그 프로젝트들의 일반적 성격(엔진 종류·대상 스토리지)만 널리 알려진 범위에서 적는다. 각 프로젝트의 현재 상태는 이 글의 범위 밖이다.

무엇을 위한 확장인가 — 외부 데이터를 PostgreSQL 안으로

운영 데이터베이스는 PostgreSQL이고, 분석용 원본은 S3에 Parquet로 쌓여 있는 구성이 흔하다. 두 세계를 잇는 방법은 오래전부터 여럿 있었다. 외부 데이터 래퍼(FDW)를 설치하거나, 별도의 ETL 작업으로 CSV를 내려받아 COPY로 넣거나, 아예 분석 엔진을 따로 두거나. 각각 설치 난이도, 포맷 지원, 속도에서 다른 대가를 치른다.

pg_chdb는 이 자리에 ClickHouse가 내놓은 답이다. 핵심 아이디어는 임베디드 ClickHouse 엔진인 chDB를 PostgreSQL 프로세스 안에서 실행하는 것이다. 외부 파일을 읽고 파싱하고 형식을 변환하는 일은 ClickHouse가 원래 잘하는 일이고, 그 결과를 PostgreSQL 테이블로 흘려 넣는 접점만 확장이 담당한다. 저장소 설명 한 줄은 「chDB 쿼리를 실행하고 외부 소스의 데이터를 PostgreSQL 테이블로 복사하는 PostgreSQL 확장」이다.

아래에서는 README가 밝힌 범위 안에서 이 확장의 구조, 지원 범위, 설치, 성능 수치, 제약을 정리하고, 마지막에 기존 선택지와 견주어 어떤 자리에 맞는지를 판단한다. 라이선스는 Apache-2.0이고, 2026년 9월 15일 기준 저장소는 스타 16개, 커밋 84개, 열린 이슈 4개다. 성숙한 프로젝트가 아니라 초기 프로젝트라는 점을 먼저 적어 둔다.

두 부품 — chdb_query()와 chdb_hook

확장은 두 개의 부품으로 이루어진다. 역할이 다르므로 따로 본다.

  • chdb_query() 함수. 문자열로 받은 ClickHouse SQL을 chDB 엔진으로 실행하고 결과를 PostgreSQL의 행 집합으로 돌려준다. ClickHouse의 테이블 함수(s3() 등)를 그대로 쓸 수 있으므로 외부 파일이 곧 테이블이 된다. 반환 열의 타입은 호출 쪽에서 AS (…)로 선언한다.
  • chdb_hook 모듈. LOAD 'chdb_hook'로 올리면 COPY … FROM 명령을 가로챈다. FROM 뒤에 로컬 경로 대신 S3 같은 외부 URL을 적으면, 훅이 chDB로 파일을 읽어 테이블에 적재한다. 기존 COPY 문법을 그대로 쓰면서 소스만 외부로 바꾸는 셈이다.
  • 둘의 분업. 조회만 필요하면 함수, 테이블에 영구 적재가 필요하면 훅이다. 확장은 파일 URL만 주면 열 구조를 추론해 테이블 생성과 적재를 한 번에 처리하는 경로도 제공한다.

설계상 눈여겨볼 점은 확장이 새 SQL 문법을 만들지 않았다는 것이다. 함수 호출과 COPY라는 PostgreSQL의 기존 문법 두 개에 얹었다. 학습 비용이 낮고, 기존 도구 체인(psql 스크립트, 스케줄러)에 그대로 들어간다.

설치 — PostgreSQL 15, chDB 26.7, Linux·macOS

  • PostgreSQL 15 이상. 14 이하는 지원 목록에 없다.
  • chDB v26.7.0 이상. 확장과 별개로 먼저 설치한다. README가 안내하는 방법은 curl -sL https://lib.chdb.io | bash다. 원격 스크립트를 파이프로 실행하는 방식이므로, 운영 서버에서는 스크립트를 내려받아 내용을 확인한 뒤 실행하는 편이 맞다.
  • Linux와 macOS만. 소스 빌드로 설치하며 Windows는 목록에 없다.
  • 빌드 순서. make → make installcheck → make install. gmake를 쓰는 시스템이나 pg_config 경로가 다른 환경은 env PG_CONFIG=/path/to/pg_config make 형태로 지정한다.

설치 요구사항에서 실무적으로 걸리는 것은 chDB 의존성이다. 임베디드 엔진이라 PostgreSQL 프로세스 안에 ClickHouse 런타임이 들어온다. 메모리 사용량과 라이브러리 충돌은 README에 없는 항목이고, 운영 인스턴스에 넣기 전에 별도 인스턴스에서 재어 볼 대상이다.

사용 예 — 함수 조회와 COPY 적재

README의 첫 번째 예는 S3의 CSV를 함수로 바로 읽는 것이다. ClickHouse SQL을 달러 인용($$ … $$)으로 감싸 넘기고, 반환 열을 선언한다.

SELECT * FROM chdb_query($$
                      SELECT * FROM s3('s3://bucket/file.csv')
                    $$) AS (id int, months int, days int);

두 번째 예는 훅을 올린 뒤 COPY로 여러 파일을 한 번에 적재하는 것이다. 글롭 패턴으로 접두사 두 개와 번호 1~3의 조합, 즉 여섯 파일을 한 문장으로 지정한다.

LOAD 'chdb_hook';
                    COPY times FROM 's3://bucket/{prefix1,prefix2}/file_{1..3}.csv';

두 예의 차이가 곧 사용 방식의 차이다. 첫 번째는 결과를 PostgreSQL 안에 남기지 않는 일회성 조회이고, 두 번째는 테이블에 적재한다. 스키마 추론 경로를 쓰면 테이블을 미리 만들 필요도 없지만, 추론된 타입이 의도와 다를 수 있으므로 운영 테이블에는 명시적 스키마를 두고 적재하는 편이 안전하다.

성능 — 100만 행 실측에서 pg_duckdb·pg_lake보다 2~3배 빠르다

README는 NYC 택시 데이터 약 100만 행을 기준으로 경쟁 확장과 가져오기 시간을 비교했다. 원문이 밝힌 결과는 다음과 같다.

비교 대상README의 서술
chdb_hook (pg_chdb)가장 일관된 성능
pg_duckdb · pg_lakeCSV·JSON·Parquet 가져오기에서 2~3배의 시간
aws_s3chDB 성능에 근접하지만 지원 포맷이 훨씬 제한적

이 수치를 읽을 때 두 가지를 같이 둬야 한다. 첫째, 측정 주체가 프로젝트 자신이다. 벤더 자체 벤치마크는 방향을 알려 주지만 크기를 보장하지 않는다. 둘째, 하드웨어·네트워크·파일 크기·경쟁 확장의 버전 같은 조건이 README에 없다. 100만 행이라는 규모는 분석 워크로드로는 작은 편이라, 수십 GB 단위에서 같은 배수가 유지되는지는 별개의 질문이다.

다만 방향 자체는 그럴듯하다. ClickHouse의 입력 파서는 열 지향 포맷을 대량으로 읽는 데 오랫동안 최적화되어 왔고, 임베디드 실행은 네트워크 왕복을 없앤다. 「빠를 이유가 있다」와 「이 배수가 내 환경에서도 나온다」는 다른 문장이고, 후자는 자기 데이터로 재야 한다.

제약 — 쿼리마다 완전히 격리된다

README가 알려진 제약으로 명시한 것은 하나다. 각 쿼리가 다른 모든 쿼리와 완전히 격리되어 실행된다. 원문의 표현은 「테이블을 만들고 다음 쿼리에서 그것을 조회할 수 있으리라 기대하지 말라」다.

  • chDB 쪽 상태가 유지되지 않는다. chdb_query() 안에서 만든 임시 테이블, 설정, 뷰는 호출이 끝나면 사라진다. 여러 단계로 나눈 변환은 한 호출 안의 SQL로 합치거나, 중간 결과를 PostgreSQL 테이블로 내려서 다음 단계에 넘겨야 한다.
  • PostgreSQL 쪽 상태는 정상이다. 격리는 chDB 실행에 대한 것이다. COPY로 적재한 테이블은 당연히 남는다.
  • 설계상의 결과일 가능성이 크다. 매 호출마다 깨끗한 엔진 상태에서 시작하면 동시 호출 간 간섭이 없고 자원 회수가 단순해진다. 상태 유지가 필요한 워크로드에는 불편이지만, 적재 도구로 쓰는 한 큰 문제는 아니다.

기존 선택지와의 비교 — pg_duckdb · pg_lake · aws_s3 · FDW

같은 자리를 노리는 도구는 여럿이다. README가 비교한 셋에 전통적 FDW를 더해, 이 글이 판단할 수 있는 축만 표로 놓는다. 다른 프로젝트의 현재 기능은 이 글의 범위 밖이라 「—」로 남긴 칸이 있다.

표에서 읽히는 것은 순위가 아니라 결의 차이다. 임베디드 엔진 계열(pg_chdb, pg_duckdb)은 파싱과 변환을 엔진에 맡긴다 — pg_chdb의 14종 포맷은 그 결과다. 네이티브 확장(aws_s3)은 의존성이 가볍고 스토리지 하나에 집중한다. FDW는 적재 없이 외부를 테이블처럼 보는 데 맞다. 어느 쪽이 맞는지는 「포맷이 몇 종인가」와 「적재인가 조회인가」 두 질문으로 대체로 갈린다.

어디에 쓰고 어디에 쓰지 말 것인가

  • 맞는 자리 — 여러 포맷의 외부 파일을 주기적으로 PostgreSQL에 적재하는 파이프라인. Parquet·ORC·Avro가 섞여 들어오는 데이터 레이크에서 COPY 한 문장으로 적재하는 것이 이 확장의 본령이다.
  • 맞는 자리 — 분석 엔진을 따로 운영할 여력이 없는 팀. 별도 ClickHouse 클러스터 없이 PostgreSQL 안에서 ClickHouse의 파서를 쓴다.
  • 맞지 않는 자리 — 다단계 변환을 chDB 안에서 이어 가려는 워크로드. 쿼리 격리 때문에 중간 상태가 남지 않는다.
  • 맞지 않는 자리 — Windows 서버, PostgreSQL 14 이하. 지원 목록 밖이다.
  • 맞지 않는 자리 — 검증 없이 운영 인스턴스에 바로 올리는 것. 스타 16개·커밋 84개의 초기 프로젝트이고, 임베디드 엔진의 메모리·안정성은 README에 없는 항목이다. 별도 인스턴스에서 자기 데이터로 재는 단계가 먼저다.

확인하지 못한 것

  • 벤치마크의 하드웨어·네트워크·파일 크기·경쟁 확장의 버전. README에 없다.
  • chDB 엔진이 PostgreSQL 프로세스 안에서 쓰는 메모리 상한과 동시 호출 시의 거동.
  • ClickHouse 타입에서 PostgreSQL 타입으로의 매핑 규칙과 손실 여부(시간대·소수·중첩 구조).
  • S3 자격 증명을 어떻게 넘기는지 — README 예제에는 인증 부분이 없다.
  • pg_duckdb·pg_lake·aws_s3·FDW의 현재 기능 범위. README의 비교 문맥 밖이다.
  • 프로젝트의 유지보수 계획과 릴리스 주기.
