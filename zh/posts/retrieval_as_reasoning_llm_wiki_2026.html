检索即推理 — LLM-Wiki 对比 RAG 基准测试揭示了什么

多跳上赢、单文档上输 — 用数字划出这组结果适用于自己 RAG 管线的边界

2026-08-06 IT/技术

不调检索器，改变知识的形态

RAG 答不对时，动手顺序大体固定：改分块大小、加重排序器、换新嵌入模型。底下压着一个前提：检索是一次调取，提高准确率答案就变好。

Haoliang Ming、Feifei Li、Xiaoqing Wu、Wenhui Que 的「Retrieval as Reasoning: Self-Evolving Agent-Native Retrieval via LLM-Wiki」（arXiv 2605.25480）正面动了它。作者主张：智能体要的检索不是一次上下文调取，而是更接近推理的行为：查找、阅读、顺链接、自判证据够不够。于是外部知识被做成可编译、可组合、自我演化的结构，而非静态索引。

主张不新。有意思的是作者把它放上四个基准与既有 RAG 正面比过，结果没有干净地倒向一边：多跳赢得多，单文档输了。本文挖的就是这条界线。知识管理侧的同名讨论已在LLM Wiki 与生成性负荷处理，这里只看模型的答对率。

LLM-Wiki 的三件事：编译、遍历、自我纠错

拆三条轴看，收益来源就清楚。

编译：造页面而非分块

入库阶段不原样切分原文，走两步 LLM：SelectPages 挑出与该段落相关的既有页面最多 5 个（k=5），CompileWikiPages 参考这些页面与生效中的约束，生成页面正文、链接与索引更新，产物是层级式 Markdown 维基。

  • 目录索引（_index.md）是维基目次。
  • 实体页面装元数据与事实条目。
  • 页面间以双向维基链接相连，即遍历落脚点。
  • 同一实体散落多篇文档时收拢为一页。

遍历：靠工具调用反复读

查询时智能体只用两个工具。wiki_search(query) 先看页面名、别名、标签、描述这类结构信号，不行再下沉正文；wiki_read(paths) 成批读取目录索引或页面全文并返回该页链接，智能体据此定下一步。

  • 工具调用预算最多 15 次（Tmax=15）。
  • 连续 3 次检索为空即中止（耐心阈值 P=3）。
  • 作答前至少调用 1 次 wiki_read，堵住只看摘要就回答。

自我纠错：错误簿改写下次编译的提示词

这部分最不华丽，却最贴近工程现场。LLM 生成的维基必然出现断链与语义不一致；作者不当它是事后修补对象，而是退回成下次编译的输入，循环五步。

  1. 发现（Discover）：校验器抓出结构与语义错误。
  2. 归因（Attribute）：追踪根本原因。
  3. 约束化（Constrain）：转写为自然语言规则。
  4. 注入（Inject）：塞进后续编译提示词。
  5. 验证与关闭（Verify & Close）：复检后关闭。

修复分两层：代码自动修正每批编译都跑，管结构性问题；LLM 周期修正每 N 篇文档触发，管语义与内容错误。作者归类的错误共七种，其中悬空链接（dangling link）占 29.1~63.8%。让 LLM 造链接，指向不存在页面并不罕见。

基线构成：跟什么比的

对照组覆盖 RAG 的代表性分支。

  • None（closed-book）：不检索，只靠参数知识作答。地板线。
  • Vanilla RAG (BM25)：经典词汇型稀疏检索。
  • Vanilla RAG (Dense)：嵌入型稠密检索，取前 5 个段落。
  • RAPTOR：层级摘要建树。
  • GraphRAG：抽知识图谱并附社区摘要。
  • LightRAG：图与向量结合的轻量系列。
  • HippoRAG 2：取法海马体记忆的长期记忆系列。

骨干模型在索引构建与答案生成两侧都用 GLM-5 系列的 GLM-5.1，需文本表示处一律套 Qwen3-Embedding-8B，基线不是因弱嵌入输的。多跳基准取靠前的 500 道题，2WikiMultiHopQA 语料 3,440 个段落。

跌幅排序就是结论。

  • 去掉渐进式遍历最疼。MuSiQue 从 0.739 掉到 0.601，飞掉 13.8 点；HotpotQA 掉 11.7 点，2Wiki 掉 12.2 点。
  • 去掉维基结构排第二。下降 6.1~7.0 点。没有结构，只要遍历还在就守得住一半以上。
  • 去掉错误簿最小，但不可忽略。3.4~4.0 点，自动生成维基的质量管理值这么多。

换成工程语言：与其把索引做漂亮，不如让智能体多读几遍、顺链接走。维基编译得再好，查询时只调取一次，一半以上收益就没了。反之，不新造维基、只在既有索引上叠一层反复检索与阅读的循环，也能捞回不少。

跳数越多差距越大，延迟反而更短

差距与跳数成正比，表外也能确认。2WikiMultiHopQA 上对 LightRAG 的 F1 差距从 2 跳的 5.7 点拉开到 4 跳的 8.3 点。跳数每加一层，一次取 top-k 漏掉必需段落的概率就乘一次；遍历则能用前一步信息造下一个检索词。

这里有个反直觉的结果：工具调用了好几次，反而更快。

  • LLM-Wiki 每次查询延迟随基准为 14.9~27.1 秒。
  • LightRAG 为 39.7~51.3 秒，HippoRAG 2 为 32.4~38.2 秒。
  • 作者报告 LLM-Wiki 与 BM25、Dense RAG 相当或更快。
  • 智能体每次查询实读页面平均 2.5~3.9 个，比 RAG 基线固定塞 5 个段落还少。

原因很简单：反复调用的开销小于一次推入上下文量下降的好处。图系列慢是因为社区摘要或图遍历要另挂 LLM 调用。上下文 token 既是成本又是延迟，只精读 3 个页面比每次附 5 个无关段落划算，单价也这么反映。

成本与更新这两张暗账单

作者写明的两个局限，就是引入决策的全部。

其一，编译成本

所有原始段落都要过 SelectPages 与 CompileWikiPages，都是 LLM 调用。比切分块只做嵌入初期构建更贵，作者说该成本会被此后的查询摊销，但摊销有条件。

  • 每篇文档的预期查询数要足够大。
  • 语料要活得够久，一个月后作废就没摊销期。
  • 单次查询的成本优势（读 2.5~3.9 个页面对固定 5 个段落）有助摊销，能否盖住入库成本则看语料规模。

其二，扩展性

维基长到数万页时目录索引会难以驾驭，页面选择质量下降。网页规模或频繁变动的语料需要层级化索引、分片、陈旧事实处理与全局目录维护；大规模动态维护、多模态维基、跨语料迁移留作后续。

真正该问的不是基准分数，而是这一侧。

  • 一篇文档被改时，要重编译到哪些页面为止。
  • 凭什么保证重编译不打断既有双向链接。
  • 悬空链接占错误最高 63.8%，我的校验器能自动抓到吗。
  • 每次查询 15 次工具调用的预算，塞得进我的延迟 SLO 吗。
  • 答案需要原文引用时，有没有从维基页回溯原文的路径。

没能确认的部分

以下几项在论文里没能确认，本文不拿数字主张。

  • 编译成本的绝对值。只写了比 chunk-and-embed 更贵，token 数与金额没能确认。
  • 换骨干模型后的可复现性。实验以 GLM-5.1 为准，其他模型的交叉验证没能确认。
  • 方差与统计显著性。表中值是单次运行还是多种子平均、有无置信区间，没能确认。
  • 增量更新成本。语料局部变动时重编译的范围与成本没能确认。
  • 代码与数据是否公开。含 AuthTrace 在内，复现所需产出物没能确认。
  • 英汉之外语言的表现。AuthTrace 是中文语料，其余是英文，其他语言的编译质量没能确认。

常见问题

LLM-Wiki 与既有 RAG 有什么不同？

一般 RAG 把原文切块放进向量索引，每次查询取前 k 个。LLM-Wiki 造的是结构：入库时把原文编译成 Markdown 维基页面并建立双向链接，查询时智能体反复调用 wiki_search 与 wiki_read 检索、阅读、顺链接走，证据靠多次判断攒成。

基准测试上的性能差距有多大？

多跳问答表里 LLM-Wiki 为 HotpotQA F1 0.839、MuSiQue 0.739、2WikiMultiHopQA 0.911；同表最强基线 LightRAG 为 0.819、0.659、0.847。作者把差距概括为相对 HippoRAG 2、LightRAG、GraphRAG 的 2.0 到 8.1 个 F1 点，每基准 500 道题。

LLM-Wiki 也有输的场合吗？

有。AuthTrace 单文档查询上 HippoRAG 2 为 78.3 分、LLM-Wiki 为 76.0 分，落后 2.3 分。作者解释：单文档问题多半原样取原文更有利，LLM-Wiki 重组页面时可能漏掉局部细节。多文档高密度查询则领先 8.9 分。

性能的真正动力是维基结构还是遍历？

消融实验指向遍历。去掉渐进式遍历后 MuSiQue F1 从 0.739 掉到 0.601，跌幅最大；去掉维基结构为 0.669，错误簿为 0.699。光把页面造好只拿一半左右收益，剩下的靠智能体真顺链接读好几遍。

自己的 RAG 管线该改成这种方式吗？

取决于查询类型与语料性质。跨多篇文档才有答案的查询多、语料稳定、同一语料上查询反复进来，就值得引入。反之，多为单篇文档内的局部事实检索、必须原样引用原文、语料每天变动、或每篇文档查询数少到收不回编译成本，则既有分块更好。

结论：要改的是检索的定义

带走的东西压缩成三条。

  1. 收益大部分来自遍历。抽掉遍历，MuSiQue F1 塌了 13.8 点。新造结构之前，先看现在的管线是不是一次调取就收工。
  2. 收益与跳数成正比。2 跳的 HotpotQA 只有 +2.0，4 跳拉开到 +8.3。查询日志大多是 1 跳的话，这篇论文说的不是我的事。
  3. 单文档检索仍是原文赢。AuthTrace Single 上 LLM-Wiki 输给 HippoRAG 2 有 2.3 分；结构化不免费，是拿局部细节换的。

最实用的结论不是二选一。把查询日志按扇入切开，多文档查询走遍历路径、单文档走原文路径，这才最忠实于表。表 2 每列第一名各不相同，本身就指向这设计。

把检索看成推理，说到底是把检索器准确率问题挪成系统设计问题。纠结要不要再加重排序器之前，先问：我的智能体能不能自己察觉第一次检索结果不够用。
