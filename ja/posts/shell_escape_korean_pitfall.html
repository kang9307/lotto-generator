ファイル名がシェルごとに違って見える理由

Git Bashが作った名前をPowerShellが見つけられない地点

2026年8月10日 開発・インフラ

はじめに: 同じフォルダなのに名前が違う

スクリプトはGit Bashで回し、配備はPowerShellで行い、ビルドはWSLの中でという構成はWindowsの開発端末では珍しくない。この組み合わせで空白や非ASCII文字を含むファイル名を扱っていると、説明のつかないことが起きる。Git Bashでは平然と見えているファイルを、PowerShellのスクリプトが「無い」と言う。

# Git Bash 側
$ ls -1
x?y.txt

# PowerShell 側 — 同じフォルダ、同じファイル
PS> Test-Path -LiteralPath '.\x?y.txt'
False

ファイルはそこにある。消えても隠れてもいない。二つのシェルが同じファイルを別々の名前で覚えているだけだ。この種のすれ違いは名前の中の疑問符ひとつに限らない。大文字小文字、ロケール、ユニコード正規化、一覧ファイルのエンコーディングまで、境界ごとに規則が異なり、その差は静かだ。エラーは出ず、結果だけが違う。

この記事はその境界をひとつずつ押さえる。引用符の文法そのものはシェルのクォート規則 - どの引用符が何を止めるのかに、空白や改行を含む名前をfindとxargsで渡す実務的な組み合わせはfindとxargsの空白・改行の罠にまとめてある。ここで扱うのはその次の層だ。引用を正しく付けたのに、道具を乗り換えた瞬間に名前が変わる地点である。

この記事で扱う境界
  1. Windowsの禁止文字と私用領域への置換 — Git BashとPowerShellが分かれる地点
  2. 大文字小文字を区別しないファイルシステム — 二つ作ると一つになる
  3. Git Bashのパス自動変換 — 引数が途中で書き換わる
  4. PowerShell 5.1のネイティブ引数渡し — 引用符と空文字列が消える
  5. 既定のエンコーディングと一覧ファイル — BOM・CR・CP949
  6. ロケールがbash自体を変える三か所
  7. 合成形と分解形が同じフォルダにあるとき

1. 実行環境 — この記事の根拠

本文のすべての出力は以下の環境で得たものだ。バージョンが変われば結果も変わる項目がいくつもあるので、先に固定しておく。

  • OS: Windows 10 Pro、ビルド19045、ファイルシステムはNTFS
  • シェル1: Git for Windows付属のbash 5.2.37(1)-release、カーネル文字列はMINGW64_NT-10.0-19045 … 3.5.7 … Msys
  • シェル2: Windows PowerShell 5.1.19041.6456
  • ロケール: LANGとLC_ALLは未設定、LC_CTYPEはC.UTF-8
  • システムのANSIコードページ: ks_c_5601-1987、韓国語WindowsのCP949
  • 引数確認用の外部プログラム: Node.js v22.16.0（process.argvをそのまま出力する用途）
  • WSL: wsl.exeは存在するがディストリビューションが未導入のため、この記事では何も確認できていない（15節を参照）

すべての実験は空の一時ディレクトリで行った。本文の例はファイルを削除しない形だけを載せている。引数がどう分割されるかはechoとprintfで十分に見えるし、その方が試すにも安全だ。

2. 名前は文字列ではなくバイト列で、層ごとに規則が違う

ファイル名が画面に出るまでに最低でも三つの層を通る。各層は名前の保存と解釈の仕方が異なり、境界で変換が起きる。

  • ファイルシステム — NTFSは名前をUTF-16コードユニットの列として保存する。正規化はせず、いくつかの文字を禁止する。
  • シェルとユーティリティ — POSIX系のツールは名前をバイト列として扱う。それがどのエンコーディングかはロケールが決める。
  • 画面 — フォントが描く。バイトが違っても同じ絵になり得る。

三つ目がこの記事全体を貫く。目で見たものは証拠にならない。名前が怪しければバイトを見るべきで、その手段はどこでも同じだ。

$ printf '%s' "회의 자료.txt" | od -An -tx1
 ed 9a 8c ec 9d 98 20 ec 9e 90 eb a3 8c 2e 74 78 74

名前が合わないときにこの一行をまず打つ習慣をつけると、診断時間が一気に縮む。文字を比べるのではなくバイトを比べる。

3. Git Bashが作った名前をPowerShellが見つけられない — 0xF000置換

Windowsはファイル名に使えない文字を定めている。Cygwinの文書はその一覧を「ASCII値1から31までの制御文字、およびWin32 APIで特別な意味を持つ次の文字」とし、" * : < > ? | \を挙げる。ところがGit Bashではこうした名前が何の抵抗もなく作られる。

$ for c in '<' '>' ':' '"' '|' '?' '*'; do printf 'x\n' > "x${c}y.txt"; done
$ ls -1
x"y.txt
x*y.txt
x:y.txt
x<y.txt
x>y.txt
x?y.txt
x|y.txt

Git Bash側で名前のバイトを出せば打った通りだ。コロンは3a、疑問符は3f。ところがWindows側で同じファイルの名前を読むと別のコードポイントが返る。

PS> Get-ChildItem | ForEach-Object {
      ($_.Name.ToCharArray() | ForEach-Object { 'U+{0:X4}' -f [int]$_ }) -join ' '
    }
U+0078 U+F009 U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F00A U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F022 U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F02A U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F03A U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F03C U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F03E U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F03F U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F07C U+0079 U+002E U+0074 U+0078 U+0074

規則は一目でわかる。禁止文字のコードポイントに0xF000を足し、私用領域へ移している。Cygwinの文書がそう書いている — 逆斜線を除く上記の文字は「ファイルの作成やアクセスの際に、禁止文字のコードポイントに0xf000を足して0xf000から0xf0ffの範囲、すなわち私用領域の特殊なUNICODE文字へ変換される」。逆斜線だけが外れるのは、それがパス区切り文字だからだ。

入力した文字元のコードポイント保存されたコードポイント保存名のUTF-8バイト
タブU+0009U+F009EF 80 89
改行U+000AU+F00AEF 80 8A
"U+0022U+F022EF 80 A2
*U+002AU+F02AEF 80 AA
:U+003AU+F03AEF 80 BA
<U+003CU+F03CEF 80 BC
>U+003EU+F03EEF 80 BE
?U+003FU+F03FEF 80 BF
|U+007CU+F07CEF 81 BC

Git Bashは一覧を読むときにこの変換を戻して表示するので、そちら側では何も問題がない。問題は戻さない道具だ。

PS> Test-Path -LiteralPath '.\x?y.txt'
False

PS> Test-Path -LiteralPath '.\x|y.txt'
Test-Path : Illegal characters in path.

PS> $pua = 'x' + [char]0xF03F + 'y.txt'
PS> Test-Path -LiteralPath ".\$pua"
True

縦棒を含む名前は偽ではなく例外を返す。Windows APIがその文字をパスに許さないため、照会そのものが成立しない。私用領域の文字で組み立てた名前だけが真を返す。同じファイルに名前が二つある状態だ。

実務でこれが効いてくる瞬間
Git Bashで回したスクリプトがログやレポートを作り、それをPowerShellの配備スクリプトが拾う構成で表面化する。名前に時刻を入れようとして%H:%M形式を使えばコロンが入り、その瞬間から二つのシェルはファイルを別物として見始める。時刻を名前に入れるときコロンではなくハイフンを使う慣習は迷信ではなく、この問題を避ける規則だ。

付け加えると、Cygwinの文書はデバイス名（AUX・COM1・LPT1・PRNなど）と名前末尾のピリオド・空白も別項で扱っている。デバイス名はネイティブなWin32アプリケーションではファイル名や拡張子として使えず、末尾のピリオドと空白は「ファイルを作る前にすべて取り除かれる」。Cygwin系のプログラムはこの制約を回避して作れてしまうが、そうして作られたファイルはエクスプローラーや通常のWindowsツールでは片付けにくくなる。実習で試すようなものではない。作らないのが答えだ。

4. 大文字小文字 — 二つ作ると一つしか残らない

Linuxで問題なく動いていたスクリプトがWindowsでファイルをひとつ失う、典型的な地点だ。

$ printf '대문자\n' > "README.txt"
$ printf '소문자\n' > "readme.txt"
$ ls -1
README.txt
$ cat README.txt
소문자

ファイルはひとつ。ところが名前は先に作った方が残り、中身は後に書いた方が残った。NTFSの既定設定が大文字小文字を区別せず、元の表記だけは保持するためだ。二回目のリダイレクトは新しいファイルを作ったのではなく、既存のファイルを開いて上書きした。

  • 大文字小文字だけが違う同名パスを持つリポジトリは、Windowsのチェックアウトでファイルをひとつ失う。
  • スクリプトがConfig.jsonを書き、別のスクリプトがconfig.jsonを読む構成はLinuxでだけ失敗する。失敗が遅れて表に出る方向なので、なお悪い。
  • 大文字小文字の区別がない文字の名前はこの問題を避けられる。代わりに以降の節の問題をすべて引き受ける。

5. Git Bashのパス自動変換 — 引数が途中で書き換わる

Git BashはネイティブなWindows実行ファイルを呼ぶとき、POSIX形式に見える引数をWindowsパスに書き換えて渡す。シェル組み込みコマンドにはこの変換がない。

$ node -e 'console.log(JSON.stringify(process.argv.slice(1)))' "/usr/bin" "a/b" "-Dfoo=/bar"
["C:/Program Files/Git/usr/bin","a/b","-Dfoo=C:/Program Files/Git/bar"]

$ printf '%s\n' "/usr/bin"
/usr/bin

三つのことが一度に見える。第一に/usr/binがGitのインストール先の下へ読み替えられた。第二に先頭にスラッシュのないa/bは触られていない。第三が最も厄介で、-Dfoo=/barのように等号の後ろに付いた値まで変換された。パスではなくアプリケーションのオプション値であっても同じだ。

コンテナのボリュームマウントやRESTのパスを引数で渡すときに、この変換が静かに値を壊す。切る方法は環境変数ひとつだ。

$ MSYS_NO_PATHCONV=1 node -e 'console.log(JSON.stringify(process.argv.slice(1)))' \
      "/usr/bin" "a/b" "-Dfoo=/bar"
["/usr/bin","a/b","-Dfoo=/bar"]
  • コマンドひとつだけに効かせるなら上のように前に付けて使う。スクリプト全体に掛けると本当にパスであるべき引数まで変換されなくなるので、範囲は狭い方がよい。
  • スラッシュ二つで始めれば（//c）変換を回避できる慣用法が通る場合がある。ただし受け取るプログラムがその形を受け入れる必要がある。
  • この変換はネイティブ実行ファイルの呼び出しにのみ適用される。bashの組み込みやMSYSビルドのユーティリティには適用されず、同じ文字列がコマンドによって違う形で届く。

6. PowerShell 5.1 — 単語分割は無いが引数が消える

PowerShellに移るとbashで悩んでいた問題がひとつ消える。単語分割が無い。空白を含む変数をそのまま渡しても一引数だ。

PS> $f = '회의 자료.txt'
PS> node -e 'process.argv.slice(1).forEach(function(a,i){console.log(i+String.fromCharCode(32)+a)})' $f 'a b.txt'
0 회의 자료.txt
1 a b.txt

bashで引用を外すと二つに割れるその値が、ここでは引用なしでもひとつで渡る。ところが代わりに別のものが消える。

PS> $s = 'a"b'
PS> $s.Length
3
PS> node -e 'console.log(JSON.stringify(process.argv.slice(1)))' $s
["ab"]

PS> node -e 'console.log(JSON.stringify(process.argv.slice(1)))' '' 'x'
["x"]

長さ3の文字列が受け取る側では長さ2で届いた。二重引用符が静かに消えた。空文字列の引数はそもそも一覧から抜け落ちた。エラーも警告も出ない。

原因は文書に書かれている。ネイティブコマンドを呼ぶとき、PowerShellは「解析された引数を、各パラメータを空白で区切ったひとつの文字列へ連結する」。この連結の過程で引用符の処理が食い違う。PowerShell 7.3で引数渡しの方式が変わり、その文書はこの変更がWindows PowerShell 5.1の動作に対する破壊的変更であると明記したうえで、新方式では「埋め込まれた引用符が保持される」・「引数としての空文字列が保持される」と述べている。つまり5.1の上記の結果は不具合ではなく既知の動作だ。

5.1に縛られているなら選択肢は三つある。

  • 解析停止トークン --% — 以降の文字列をリテラルとして渡す。ただし文書が明かす通り%変数%形式の環境変数展開は依然として起き、次の改行かパイプまでしか有効でなく、その中ではリダイレクトも引数として渡る。
  • Start-Process — 引数を配列で渡し、コマンドラインの組み立てを明示的に制御する。
  • PowerShell 7以降へ上げる — Windowsでは新方式が既定だ。バッチファイルとcmd.exeの呼び出しだけが旧方式に戻る。
bashと正反対である点が罠だ。bashでは「引用を付けなかったから」引数が増える。PowerShell 5.1では「引用を付けたのに」引数が減る。二つのシェルを行き来して同じスクリプトを移植するとき、直すべき方向が互いに逆になる。

7. -Pathと-LiteralPath — 角括弧ひとつが別のファイルを開く

bashで引用しなかった変数がグロブに膨らむ事故はよく知られている。PowerShellにも同種の罠があり、引用とは無関係にパラメータ名で分かれる。

中身の違う二つのファイルstar1.txtとstar[1].txtを置き、角括弧の方を読んでみるとこうなる。

# bash — 引用の有無で分かれる
$ g='star[1].txt'
$ cat $g
star1 내용
$ cat "$g"
대괄호 파일 내용
# PowerShell — パラメータ名で分かれる
PS> Get-Content -Path 'star[1].txt'
star1 내용
PS> Get-Content -LiteralPath 'star[1].txt'
대괄호 파일 내용

どちらも存在しないファイルを要求したのではなく、別のファイルを開いて静かに成功した。この種の失敗が一番たちが悪い。エラーが出ていればすぐ気づけた。

  • PowerShellの-Pathはワイルドカードを解釈する。*・?・[ ]がすべてパターン文字だ。
  • 利用者の入力や一覧ファイルから来た名前は例外なく-LiteralPathへ渡す。実際のファイル名に角括弧はよく現れる — [最終]報告書.xlsxのような名前は毎日作られている。
  • bash側で同じ防御をするなら引用を付けるか、変数ひとつを一時的にグロブなしで扱いたいならset -fでパス名展開だけを切ってもよい。
$ v='star[1].txt'
$ echo $v          # グロブ有効
star1.txt
$ set -f
$ echo $v          # グロブ無効
star[1].txt
$ set +f

8. 読み書きの既定エンコーディング — PowerShell 5.1のCP949

名前は正確に渡ったのに中身が壊れる境界もある。Git BashがUTF-8で書いたファイルをPowerShell 5.1が読むとこうなる。

PS> Get-Content -LiteralPath 'star1.txt'
star1 ?댁슜
PS> Get-Content -LiteralPath 'star1.txt' -Encoding UTF8
star1 내용

ファイルは無事だ。読む側がエンコーディングを取り違えただけである。Windows PowerShell 5.1はバイト順マーク（BOM）の無いファイルをシステムのANSIコードページで読む。韓国語Windowsではその値が次の通りだ。

PS> [System.Text.Encoding]::Default.WebName
ks_c_5601-1987

書く側も対称だ。同じ文字列を二通りで保存してバイトを剥がすと違いがはっきりする。

PS> Set-Content -LiteralPath 'a.txt' -Value '한글 저장'
PS> Set-Content -LiteralPath 'b.txt' -Value '한글 저장' -Encoding UTF8

a.txt : c7 d1 b1 db 20 c0 fa c0 e5 0d 0a
b.txt : ef bb bf ed 95 9c ea b8 80 20 ec a0 80 ec 9e a5 0d 0a
  • 既定の保存はc7 d1から始まる。一文字が2バイトのCP949だ。
  • UTF-8の保存はef bb bfから始まる。バイト順マークが付く。5.1の-Encoding UTF8はBOM無しのUTF-8ではない。
  • どちらも行末が0d 0a。このCRLFが次節の材料になる。

化けた文字の形から原因を逆に読む方法はハングルが壊れる地点を特定する方法 - cp949とUTF-8に表でまとめてある。圧縮ファイルの中の名前が化けた場合は規則がまた違うので、zipのファイル名エンコーディングの方が合う。

9. 一覧ファイルで受け渡すとき — BOMとCRが名前に付く

処理対象の一覧をテキストファイルにして渡す方式はよくある。表計算やメモ帳で作った一覧をbashのループに流すとファイルがひとつも無いと言われる。理由は三つあり、三つとも目に見えない。

$ while IFS= read -r f; do
      printf '읽은 값=[%s]  존재=%s\n' "$f" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"
  done < list_cp949.txt
읽은 값=[ȸ�� �ڷ�.txt]  존재=없음

$ … < list_utf8.txt      # BOM付きUTF-8
읽은 값=[﻿회의 자료.txt]  존재=없음

一行目はCP949のバイトなので名前が化けた。二行目は目には正常だが先頭に幅ゼロのBOM文字が付いていて別の名前になっている。三つ目の原因であるCRは、単独で見るとこうだ。

$ printf '회의 자료.txt\r\n' > list_crlf.txt
$ while IFS= read -r f; do printf '길이=%d 존재=%s\n' "${#f}" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"; done < list_crlf.txt
길이=18 존재=없음

$ while IFS= read -r f; do f=${f%$'\r'}; printf '길이=%d 존재=%s\n' "${#f}" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"; done < list_crlf.txt
길이=17 존재=있음

バイトひとつの違いだ。画面には何も現れない。一覧を受け取って処理するスクリプトなら三つを最初にまとめて片付けてから始める方がよい。

$ iconv -f CP949 -t UTF-8 list.txt | sed '1s/^\xEF\xBB\xBF//' | tr -d '\r' \
  | while IFS= read -r f; do
        printf '읽은 값=[%s]  존재=%s\n' "$f" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"
    done
읽은 값=[회의 자료.txt]  존재=있음
  • 一覧が既にUTF-8ならiconvは外すが、BOM除去とCR除去は残す。どちらもエンコーディングと無関係に付き得る。
  • 一覧を作る側を制御できるなら、最初からNUL区切りで受け渡す方がよい。名前に入り得ない唯一のバイトなので境界が壊れない。その形はfindとxargsの空白・改行の罠にまとめてある。
  • readから-rを外すと逆斜線が消える。Windowsのパスを扱うスクリプトには致命的だ — C:\temp\새 폴더がC:temp새 폴더になる。

10. ロケールがbash自体を変える — 三か所

ここが最も知られていない軸だ。同じbash、同じスクリプトがロケールによって違う動きをする。三か所で確認できる。

10.1 ANSI-Cクォートのユニコードエスケープ

Bashのマニュアルは$'string'の中の\uHHHHをユニコード文字のエスケープとして規定している。ところが実際の結果はロケールに左右される。

$ LC_ALL=C.UTF-8 bash -c "printf '%s' \$'\u00E9\uD55C' | od -An -tx1"
 c3 a9 ed 95 9c

$ LC_ALL=C bash -c "printf '%s' \$'\u00E9\uD55C' | od -An -tx1"
 e9 5c 75 44 35 35 43

UTF-8ロケールではc3 a9とed 95 9c、つまり正しい二文字が出る。Cロケールではéが単一バイトのe9に落ち、もう一方はまったく変換されず\uD55Cという六文字のまま残る（5c 75 44 35 35 43）。エラーは出ない。静かにリテラルになる。

Git for Windowsの既定インストールではLANGは空だ。つまり既定の状態がこの罠の側にある。スクリプトでユニコードエスケープから文字を組み立てるつもりなら、ロケールを明示しなければならない。

10.2 printf %qの出力

名前を安全な形で記録する慣用法だが、出力の形がロケールごとに違う。

$ LC_ALL=C.UTF-8 bash -c "printf '%q\n' '회의 자료.txt'"
회의\ 자료.txt

$ LC_ALL=C bash -c "printf '%q\n' '회의 자료.txt'"
$'\232\214\235\230 \236\220\214.txt'

どちらもシェルに食わせ直せば同じ値に戻るので、機能としてはどちらも正しい。問題はログだ。下の形で残ったログは人が読めず、チケットに貼っても何のファイルか誰にもわからない。

10.3 角括弧の中の文字範囲

特定の文字だけを選り分けようとして[가-힣]のような範囲を使う習慣は広く定着している。この範囲がロケールによってコードポイント範囲ではなくバイト範囲として解釈される。

$ for loc in C C.UTF-8 en_US.UTF-8 ko_KR.UTF-8; do
      a=$(printf '%s\n' "$NFC" | LC_ALL=$loc grep -cE '^[가-힣]+\.txt$')
      b=$(printf '%s\n' "$NFD" | LC_ALL=$loc grep -cE '^[가-힣]+\.txt$')
      echo "LC_ALL=$loc  composed=$a  decomposed=$b"
  done
LC_ALL=C          composed=1  decomposed=1
LC_ALL=C.UTF-8    composed=1  decomposed=0
LC_ALL=en_US.UTF-8 composed=1  decomposed=0
LC_ALL=ko_KR.UTF-8 composed=1  decomposed=0

Cロケールでは分解された名前まで一致する。誤検出だ。UTF-8ロケールでは一致しない — こちらは正確な動作だが、分解形を取りこぼすという別の問題はそのまま残る。どちらにせよ範囲ひとつで「この種の名前だけ」を選り分けることはできない。

一方でリテラル検索はロケールと無関係だ。同じ二行にgrep '한글'を掛ければどのロケールでも結果は2件中1件で同じになる。範囲表現が問題になりリテラルが問題にならない理由は次節にある。

動作CロケールUTF-8ロケール
$'\uHHHH'（Latin-1超）変換されずリテラルで残る正しいUTF-8バイト
printf %qの非ASCII八進エスケープの塊회의\ 자료.txt
[가-힣]の範囲バイト範囲、分解形も一致コードポイント範囲、分解形は不一致
リテラルのgrep '한글'同一同一

11. 合成形と分解形が同じフォルダにあるとき

NTFSは名前を正規化しない。だから画面上まったく同じに見えるファイルが二つ、同じフォルダに共存できる。

$ ls -1
한글.txt
한글.txt

$ for f in *; do printf '%s  ' "$f"; printf '%s' "$f" | od -An -tx1 | tr -s ' ' | tr -d '\n'; echo; done
한글.txt   e1 84 92 e1 85 a1 e1 86 ab e1 84 80 e1 85 b3 e1 86 af 2e 74 78 74
한글.txt   ed 95 9c ea b8 80 2e 74 78 74

下が合成形（NFC）だ。一文字が3バイトなので名前全体で10バイト。上は分解形（NFD）で、初声・中声・終声がそれぞれ3バイトずつ入り22バイトになる。ユニコード標準附属書15が正規化形式を規定しており、この文字はアルゴリズムで分解・合成される特殊なケースとして明記されている。

シェルでこれがどう現れるかが実務的に重要だ。

$ find . -maxdepth 1 -name '한글*' | wc -l
1

$ n=0; for f in 한글*; do n=$((n+1)); done; echo "$n"
1

$ ls -1 | sort | uniq | wc -l
2
  • シェルのグロブもfind -nameも合成形ひとつしか拾わない。パターンをキーボードで打った以上、それは合成形だからだ。
  • sortは分解形を必ず先に置く。字母のコードポイント（U+1100台）が完成形（U+AC00台）より小さい。
  • uniqは両者を別の行として数える。重複除去スクリプトが「重複なし」と答える。
  • バックアップスクリプトがfindで一覧を作ると分解形のファイルがまるごと抜ける。失敗ではなく欠落なので通知も出ない。

なぜ二つの形が生まれるのか、検索・整列・長さ検証・直列化の各境界で何が壊れるのかはハングルが字母に分解される瞬間 - NFCとNFDに別途まとめた。ここではシェル側の結論だけ置けばよい。パイプラインのどの地点で正規化するかを決め、その地点を文書に書いておく。決めないと、道具ごとに違う時点で違う形へ正規化する。

12. 境界を越えるときに確実な形

ここまでの失敗はすべて「名前を文字列に入れて別の道具へ渡す」地点で起きた。入れなければ壊れない。

同じシェルの中なら配列で受ける。名前の中に何があろうと、要素ひとつがファイルひとつだ。

$ mapfile -d '' files < <(find . -maxdepth 1 -type f -print0)
$ echo "${#files[@]}"
$ printf '  [%s]\n' "${files[@]}"

実行の前にコマンドが実際に受け取る引数を先に見る習慣も、安くて確実だ。実行の代わりにprintfを置けばよい。

$ target="회의 자료.txt"
$ printf '  인자[%s]\n' $target       # 引用なし
  인자[회의]
  인자[자료.txt]
$ printf '  인자[%s]\n' "$target"     # 引用あり
  인자[회의 자료.txt]

上の結果が出ている状態でファイルを移動したり削除したりするコマンドを実行していたら、そのコマンドは存在しない二つのファイルを対象にする。対象が無くて失敗すればまだ幸運で、たまたま同じ名前のファイルがあれば見当違いのものが対象になる。破壊的なコマンドを打つ前に同じ行をprintfで一度回す費用は数秒だ。

空の値や、ダッシュで始まる値も同じ方法で先に見える。

$ empty=""
$ set -- $empty;  echo "미인용 인자 개수=$#"
미인용 인자 개수=0
$ set -- "$empty"; echo "인용 인자 개수=$#"
인용 인자 개수=1

$ opt="-n"
$ echo $opt x
x

最後の行で-nは出力されなかった。echoがそれを値ではなくオプションとして食べたためだ。値がダッシュで始まり得る場所では--でオプション区間を閉じるか、./を前に付ける。

$ touch "-n.txt"
touch: unknown option -- n
$ touch -- "-n.txt"      # オプション区間を閉じる
$ touch ./-n.txt         # パスとして渡す

15. 確認できなかったこと

以下はこの環境で実行によって確認できなかった項目だ。推測で埋めず、そのまま残す。

  • WSLのファイル名処理。wsl.exeは入っているがディストリビューションが無く（wsl -l -qが終了コード1）、何も実行できなかった。WSLがWindowsのドライブをマウントするとき禁止文字と大文字小文字をどう扱うのか、MSYS2の0xF000置換と互換なのかは確認できていない。三つの環境を混ぜて使うなら、この組み合わせは各自の環境で3節と同じ方法でバイトを出して確かめる方が安全だ。
  • macOSの自動分解。macOSのファイルシステムが名前を分解形系で保存するという説明は広く通用しているが、この環境にmacOSが無く実行で確認できなかった。本記事11節の結果はNTFSで二つの形が共存した場合に限定される。
  • 名前末尾のピリオド・空白、およびデバイス名。Cygwin文書の記述だけを引用し、再現はしていない。こうした名前は作った後に通常のWindowsツールでは片付けにくく、実習の対象にする理由がない。
  • PowerShell 7.xの新しい引数渡し。この環境には5.1しかない。7.3以降の動作は公式文書の記述を根拠に書いており、実行で突き合わせていない。
  • ネットワークファイルシステム。Cygwin文書は一部のネットワークファイルシステムで末尾のピリオド・空白の扱いが異なると述べている。ローカルNTFSのみを確認した。

結論: 名前は道具の間を渡るときに変わる

まとめると、この記事の失敗は種類がひとつだ。名前というデータは道具の境界を渡るたびに変換を経て、その変換規則が道具ごとに違う。Git Bashは禁止文字を私用領域へ移して戻す。PowerShell 5.1は引数を文字列に連結してから割り直す。テキストファイルはコードページを経る。ユニコードは二つの形を許す。各変換は自分の領域の中では正しく動き、食い違いは常に境界にだけ現れる。

だから診断の順序も決まる。名前が合わなければ三つを順に見る。

  1. バイトを出す。od -An -tx1かコードポイントの列挙。目で比べない。
  2. どの境界を渡ったか数える。シェルが何回変わり、ファイルとして何回出入りしたか。
  3. その境界の既定値を確認する。ロケール、コードページ、ワイルドカード解釈の有無、引数の渡し方。

予防はもっと単純だ。名前を文字列に入れて渡す回数を減らす。配列で受け、NULで区切り、一覧ファイルの代わりに直接パイプする。そして作る時点からコロン・疑問符・縦棒を名前に入れなければ、3節の問題はそもそも起きない。避けられる文字を避けることが最も安い防御だ。
