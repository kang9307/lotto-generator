서론: 메모리 할당자를 신경 쓰는 이유 - 보이지 않는 성능 지렛대

2026년 5월 24일 news.hada.io에 microsoft/mimalloc GitHub 저장소가 토픽으로 올라왔습니다(당시 17점). 2019년에 설계가 공개된 프로젝트가 다시 주목받은 배경에는 할당자 선택이 성능을 좌우하는 영역, 즉 장기 실행 서버·고동시성 워크로드·언어 런타임이 계속 넓어지고 있다는 사정이 있습니다. 2026-09-29 확인 기준으로 mimalloc은 v3.5.3(2026-09-16)을 권장 버전으로 내놓고 있고, 저장소에는 이날도 커밋이 반영될 만큼 유지보수가 활발합니다.

대부분의 개발자는 malloc·free를 호출할 때 그 뒤에서 어떤 알고리즘이 동작하는지 의식하지 않습니다. Rust·Go·Java처럼 런타임이 할당을 가린 언어를 쓰면 더 그렇습니다. 그러나 장기 실행 서버·고동시성 워크로드·메모리 단편화에 민감한 시스템에서는 할당자 선택이 CPU 사용률, RSS(상주 메모리), 꼬리 지연, 단편화를 함께 바꾸는 결정입니다. 다만 효과의 크기는 워크로드마다 크게 다릅니다. mimalloc README도 「범용 할당자에 최적인 알고리즘은 없고, 어떤 할당자든 그것이 잘 못하는 워크로드를 만들 수 있다」고 적고 있습니다. 이 글이 단일 수치보다 측정 절차를 강조하는 이유입니다.

이 글은 (1) mimalloc이 무엇인지, (2) glibc malloc·jemalloc·tcmalloc·mimalloc·rpmalloc 비교 매트릭스, (3) 핵심 설계 5가지, (4) 공식 벤치마크 읽는 법, (5) 교체할 가치가 있는 5가지 시나리오, (6) 언어별 통합법, (7) Rust 글로벌 할당자 교체 코드, (8) 공개 사용처, (9) 위험과 한계, (10) 2026 할당자 흐름, (11) 즉시 적용 가능한 3가지, 그리고 갱신 이력과 참고 자료를 다룹니다. 공식 자료(README·기술 보고서·릴리스 노트·crates.io)에서 확인한 사실과 이 글의 판단 틀을 구분해 적었습니다.

1. mimalloc이란 무엇인가 - Microsoft Research 산물, MIT 라이센스

mimalloc(「미 말록」)은 Daan Leijen이 Koka·Lean 언어의 런타임용으로 처음 개발한 범용 메모리 할당자입니다. 설계는 2019년 6월 Microsoft Research 기술 보고서 「Mimalloc: Free List Sharding in Action」(MSR-TR-2019-18, Daan Leijen·Benjamin Zorn·Leonardo de Moura)에 정리되어 있습니다. 공식 저장소는 github.com/microsoft/mimalloc, 라이선스는 MIT입니다. 표준 malloc·free·realloc·calloc을 그대로 대체하도록 만들어졌고, README 기준 약 1만 줄의 작은 코드로 Windows·macOS·Linux·WASM·여러 BSD·Haiku·MUSL 등에 이식되어 있습니다. 공유 라이브러리·정적 라이브러리·단일 오브젝트 파일로 빌드되며, cmake 없이 src/static.c 한 파일을 프로젝트에 넣어 빌드하는 방법도 있습니다.

다른 할당자와 구별되는 특징은 세 가지입니다. 첫째, drop-in 호환입니다. 리눅스·BSD에서는 LD_PRELOAD=/usr/lib/libmimalloc.so myprogram처럼 다시 컴파일하지 않고 끼울 수 있고, macOS는 DYLD_INSERT_LIBRARIES, Windows는 별도 리다이렉션 DLL을 씁니다. 둘째, free list sharding입니다. 크기 클래스마다 큰 free list 하나를 두는 대신 mimalloc 페이지마다 작은 목록을 두고, 페이지마다 같은 스레드의 해제용과 다른 스레드의 해제용 목록을 다시 나눕니다. 셋째, secure 모드입니다. -DMI_SECURE=ON으로 빌드하면 guard page·무작위 할당·free list 포인터 인코딩이 들어가며, README는 성능 비용을 자체 벤치마크 평균 약 10%로 적습니다.

버전은 2026-09-29 확인 기준으로 v3.5.3(2026-09-16)이 권장, v2.5.2(2026-09-12)는 「stable, legacy」, v1.15.2(2026-09-12)는 legacy입니다. 새 개발은 주로 v3에서 이루어지고 v1·v2는 보안·버그 수정으로 유지됩니다. 발행 당시 이 글은 「v2.x가 안정, v3.x가 개발 라인」이라고 적었는데, 지금은 v3가 권장판입니다. README에 따르면 v3는 스레드 사이의 메모리 공유를 개선해 일부 큰 워크로드에서 메모리를 훨씬 적게 쓸 수 있고, 어느 스레드에서나 할당할 수 있는 first-class heap을 지원합니다. GitHub 별은 13,410개(2026-09-29, GitHub API)이며, 2026년 4~8월 릴리스 노트에는 LLM 감사로 찾은 버그·보안 수정이 여러 차례 기록되어 있습니다.

주요 할당자 다섯 가지를 한 표로 정리합니다. 개발 주체·라이선스는 각 저장소에서 확인한 값이고, 「특징」과 「어울리는 환경」 열은 이 글의 판단입니다.

이름이 같아도 구현이 여럿이라는 점에 주의해야 합니다. mimalloc README의 벤치마크는 Chrome에서 쓰인 gperftools 판 tcmalloc과, Firefox·FreeBSD에서 쓰이는 jemalloc 5.2.1을 비교 대상으로 삼았습니다. 표의 google/tcmalloc은 별도 저장소입니다. 비교 결과를 인용할 때는 어느 구현·어느 버전인지부터 확인하십시오.

이 글이 정리한 선택 기준은 단순합니다. 기본 리눅스 서비스는 glibc로 시작하고 프로파일에서 할당자 비용이 보일 때 후보를 올립니다. DB·캐시처럼 오래 도는 프로세스는 jemalloc과 mimalloc을 함께, 스레드 간 할당·해제가 많은 서버는 tcmalloc과 mimalloc을, 보안과 성능을 함께 원하면 mimalloc-secure를, 게임 엔진·실시간 시스템은 rpmalloc과 mimalloc을 같은 부하로 비교합니다. 다섯 중 어느 것도 모든 워크로드에서 가장 빠르지는 않습니다.

3. mimalloc의 핵심 설계 5가지

README와 기술 보고서에 나오는 설계를 다섯 가지로 묶었습니다.

3-1) Free list sharding(페이지별 free list)

크기 클래스마다 큰 free list 하나를 두는 대신, 「mimalloc 페이지」마다 작은 free list를 둡니다. 한 페이지는 한 크기 클래스의 블록만 담고 64비트 시스템에서 보통 64KiB입니다. README는 이렇게 하면 시간상 가까이 할당된 객체가 메모리에서도 가까이 놓여 지역성이 좋아지고 단편화가 줄어든다고 설명합니다.

3-2) 다중 샤딩과 작은 객체 경로

README가 「큰 아이디어」라고 부르는 부분입니다. 페이지마다 목록을 다시 나눠, 같은 스레드에서 일어나는 해제용 목록과 다른 스레드에서 오는 동시 해제용 목록을 따로 둡니다. 그래서 다른 스레드의 해제가 CAS 한 번으로 끝나고, 목록이 수천 개로 흩어져 경합이 한곳에 몰리지 않습니다. 작은 객체에는 전용 경로도 있습니다. v3 README는 크기가 MI_SMALL_SIZE_MAX(1KiB) 미만으로 보장될 때 mi_malloc_small·mi_free_small을 쓰면 더 빠르다고 안내합니다.

3-3) Secure 모드(힙 취약점 완화)

-DMI_SECURE=ON으로 빌드하면 다음이 추가됩니다. (a) 내부 페이지 메타데이터를 guard page로 둘러싸 버퍼 오버플로가 메타데이터에 닿지 못하게 합니다. (b) free list 포인터를 페이지별 키로 인코딩해 알려진 포인터로 덮어쓰는 공격을 막고 힙 손상을 탐지합니다. (c) double free를 탐지해 무시합니다. (d) free list 초기화 순서와 할당 위치를 무작위화합니다. -DMI_SECURE=FULL은 64KiB 페이지 끝마다 guard page를 두지만, 비용이 크고 리눅스 VMA 한도에 닿을 수 있어 README가 일반적으로 권장하지 않습니다. 성능 비용은 README 벤치마크 평균 약 10%입니다. README는 이것이 보장이 아니라 완화책이므로 전체 보안 전략 안에서 평가하라고 덧붙입니다.

3-4) 낮은 단편화와 eager page purging

페이지가 비면(sharding 덕에 그럴 가능성이 커집니다) 그 메모리를 OS에 미사용으로 알려(reset 또는 decommit) 실제 메모리 압박과 단편화를 줄입니다. 오래 도는 프로그램에서 특히 의미가 있습니다. README는 메타데이터 오버헤드가 약 0.2%로 제한되고, blowup이 없으며, 최악 할당 시간이 OS 호출을 빼면 제한된다고 설명합니다. 다만 README 스스로 공개 벤치마크가 매우 크고 오래 도는 서버 워크로드를 측정하지 않는다고 밝히므로, 장기 실행 단편화는 직접 측정할 대상입니다.

3-5) Drop-in 호환(LD_PRELOAD)

README는 동적 override를 표준 malloc을 바꾸는 권장 방식으로 소개합니다. 기존 바이너리를 다시 컴파일하지 않고 LD_PRELOAD=/usr/lib/libmimalloc.so myserver 한 줄로 적용하고, MIMALLOC_VERBOSE=1을 함께 주면 실제로 mimalloc이 쓰이는지 확인할 수 있습니다. 되돌리기는 환경변수를 빼는 것으로 끝납니다. jemalloc·tcmalloc도 같은 방식이 가능하지만, 코드가 작고 단일 소스 빌드가 가능하다는 점이 mimalloc의 도입 비용을 낮춥니다.

4. 벤치마크 분석 - 공식 표가 말하는 것과 말하지 않는 것

이 장의 수치는 모두 mimalloc README 「Performance」 절에서 옮겼습니다. 발행 당시 적었던 「glibc 대비 1.5~3배」「32~64 스레드에서 2배 이상」「jemalloc보다 10~30% 빠름」은 원 표에서 찾지 못해 삭제했습니다.

4-1) 측정 조건과 한계

README 성능 절의 마지막 갱신은 2021-01-30입니다. 16코어 AMD 5950x(Ubuntu 20.04, glibc 2.31, GCC 9.3.0)와 36코어 Intel Xeon(AWS c5.18xlarge)에서 mimalloc v1.7.0·v2.0.0(당시 베타)·secure 모드를 tcmalloc(gperftools 2.8.1)·jemalloc 5.2.1·tbb·rpmalloc 1.4.1·Hoard·Mesh·glibc와 비교했습니다. 2026-09-01에는 「오래된 결과이고 다른 할당자들도 그사이 개선되었다」는 주석이 붙었습니다. 벤치마크 모음은 mimalloc-bench로 따로 공개되어 있습니다.

4-2) 벤치마크별 결과 요점

흐름을 요약하면, 단일 스레드·일반적인 패턴에서는 차이가 작고 스레드 사이의 객체 이동이 많을수록 mimalloc의 우위가 커집니다. 페이지별 동시 해제 목록이라는 설계와 맞아떨어지는 결과입니다.

4-3) 거대 객체·장기 실행 워크로드 - 공개 표가 다루지 않는 영역

README는 이 벤치마크가 매우 크고 오래 도는 서버 워크로드나 할당의 최악 지연을 측정하지 않는다고 밝힙니다. 수 MB 버퍼 위주의 워크로드나 며칠씩 사는 객체가 많은 워크로드에서 어느 할당자가 나은지는 공개 표로 판단할 수 없습니다. 이런 워크로드는 자기 환경에서 직접 재야 합니다.

4-4) jemalloc과 비교할 때

발행 당시의 「장수명 객체는 jemalloc 우위 가능성」은 출처가 없는 경향 서술이라 그대로 두지 않았습니다. 확인되는 것은 README가 jemalloc·tcmalloc을 Chrome·FreeBSD 같은 세계 최대 규모 시스템에서 쓰이는 산업용 할당자로 부르며, 대부분의 할당자가 xmalloc-testN에서 약하다고 적은 점입니다. 두 할당자 모두 검증된 선택지이고, 어느 쪽이 빠른지는 해당 워크로드에서 측정해야 합니다.

4-5) 정리

한 줄로 요약하면 「스레드 사이의 할당·해제가 많을수록 공개 벤치마크상 mimalloc의 우위가 크고, 단일 스레드·일반 패턴에서는 차이가 작으며, 장기 실행·거대 객체는 공개 자료로 판단할 수 없다」입니다. 수치가 2021년 측정이므로, 자기 워크로드 트레이스로 mimalloc-bench나 자체 벤치마크를 돌리는 것이 결론입니다.

5. 언제 mimalloc로 바꿀 가치가 있나 - 5가지 시나리오

이 글이 정리한 「mimalloc 교체를 시험할 만한 다섯 시나리오」입니다. 하나라도 해당하면 staging 부하 테스트를 진행할 가치가 있습니다. 성능 보장이 아니라 시험 대상을 고르는 기준입니다.

5-1) 스레드 간 객체 이동이 많은 다중 스레드 서버

요청을 받는 스레드와 처리하는 스레드가 달라, 한 스레드가 할당한 메모리를 다른 스레드가 해제하는 서버입니다. README의 larsonN·xmalloc-testN이 모사하는 패턴이고 mimalloc의 결과가 가장 두드러진 영역입니다. 반대로 단일 스레드 서버는 README의 redis 결과처럼 차이가 작을 수 있습니다. CPU 프로파일에서 malloc·free 경합이 보이면 후보입니다.

5-2) 언어 런타임·인터프리터 환경

mimalloc은 Koka·Lean 런타임용으로 출발했고, README는 런타임 시스템을 위한 heartbeat·지연 해제 훅을 제공한다고 설명합니다. CPython도 3.13부터 mimalloc을 기본으로 번들합니다(자체 수정 포함). 짧은 수명 객체를 많이 만드는 런타임이나 임베디드 인터프리터에서 검토할 만합니다.

5-3) 메모리가 서서히 늘어나는 장기 실행 워크로드

며칠~몇 주 단위로 재시작 없이 동작하는 서비스에서 RSS가 계속 오른다면 할당자 단편화가 원인 후보입니다. mimalloc의 eager page purging과 MIMALLOC_PURGE_DELAY가 관련 장치이고, jemalloc도 함께 비교할 후보입니다. 먼저 실제 메모리 누수가 아닌지부터 구분하십시오.

5-4) 보안이 중요한 시스템(mimalloc-secure)

네트워크에 노출되거나 신뢰할 수 없는 입력을 파싱하는 서비스입니다. secure 빌드의 비용은 README 기준 평균 약 10%로, 발행 당시 적었던 3~5%보다 큽니다. 성능 여유가 있는 서비스부터 적용하는 편이 안전합니다. 2026년 8월 릴리스(v3.4.4·v3.5.0)는 secure 모드의 double free·크기 검사를 강화하고 double free 탐지를 빠르게 했다고 적고 있습니다.

5-5) Rust·C++ 프로젝트의 글로벌 할당자 교체

Rust는 #[global_allocator] 한 줄로 mimalloc을 글로벌 할당자로 지정할 수 있고, C++는 링크 단계에서 교체한 뒤 README가 권하는 대로 mimalloc-new-delete.h로 new·delete도 덮어씁니다. 컴파일 시점 통합은 배포 환경의 LD_PRELOAD 설정에 덜 의존합니다.

6. 언어별 통합 방법 - C/C++·Rust·Go·Java

언어별 통합 난이도를 공식 문서 기준으로 정리합니다.

6-1) C/C++ - LD_PRELOAD 또는 링크

리눅스·BSD는 LD_PRELOAD=/usr/lib/libmimalloc.so, macOS는 DYLD_INSERT_LIBRARIES=/usr/lib/libmimalloc.dylib(셸 보안 제한이 걸릴 수 있음), Windows는 mimalloc-redirect.dll을 쓰는 리다이렉션 방식입니다. 빌드 시점 통합은 -lmimalloc으로 링크하거나 cmake에서 find_package(mimalloc) 후 target_link_libraries(myapp PUBLIC mimalloc)를 쓰고, README가 선호하는 방식대로 mi_malloc API를 직접 호출할 수도 있습니다. C++는 mimalloc-new-delete.h를 소스 파일 하나에만 포함합니다.

6-2) Rust - GlobalAlloc 교체

crates.io의 mimalloc 크레이트(2026-09-29 기준 최신 0.1.52, 2026-05-22 배포)를 씁니다. 저장소는 github.com/purpleprotocol/mimalloc_rust로, microsoft/mimalloc을 감싸는 커뮤니티 래퍼이며 Microsoft가 직접 배포하는 크레이트는 아닙니다. 기본으로 mimalloc v3를 쓰고, v2가 필요하면 features = ["v2"]를 줍니다. 이름이 비슷한 mimalloc-rust 크레이트(lemonhx/mimalloc-rust, 0.2.1, 마지막 갱신 2023-04-27)는 별개 프로젝트입니다. 자세한 코드는 7장에서 다룹니다.

6-3) Go - cgo(제한적)

Go 런타임 할당자는 소스 주석대로 tcmalloc에서 출발했지만 많이 달라졌고, 교체할 수 있는 구조가 아닙니다. mimalloc은 cgo로 호출하는 C 라이브러리 쪽 할당에만 영향을 줍니다. Go 코어 영역까지 바꾸려면 런타임을 직접 패치해야 하므로 권장하지 않습니다.

6-4) Java - JNI / 사용 어려움

JVM은 자체 GC 힙을 가집니다. mimalloc은 JVM 프로세스의 네이티브 할당(JNI 라이브러리 등)에만 영향을 줄 수 있고, 일반 Java 객체에는 적용되지 않습니다. Java 서비스라면 할당자 교체보다 GC와 힙 설정을 먼저 보는 편이 맞습니다.

7. 실전 통합 예시 - Rust로 글로벌 할당자 교체

가장 자주 쓰이는 Rust 통합을 코드로 보입니다. mimalloc 크레이트 README의 사용 예와 같은 형태입니다.

7-1) Cargo.toml 의존성 추가

[dependencies]
mimalloc = "0.1"

# 옵션: secure 모드
# mimalloc = { version = "0.1", features = ["secure"] }
# 옵션: mimalloc v2 사용(기본은 v3)
# mimalloc = { version = "0.1", features = ["v2"] }

7-2) main.rs에서 글로벌 할당자 선언

use mimalloc::MiMalloc;

#[global_allocator]
static GLOBAL: MiMalloc = MiMalloc;

fn main() {
    // 이 시점부터 Box, Vec, String 등 모든 표준 할당이 mimalloc을 거친다
    let v: Vec<i32> = (0..1_000_000).collect();
    println!("sum = {}", v.iter().sum::<i32>());
}

7-3) 빌드와 확인

cargo build --release

# mimalloc 메시지 출력으로 적용 여부 확인
MIMALLOC_VERBOSE=1 ./target/release/myapp

# RSS 확인(Linux)
ps -o pid,rss,command -p $(pgrep myapp)

크레이트 README대로 빌드에는 C 컴파일러(gcc 또는 clang)가 필요하므로 CI 이미지에 build-essential 또는 동등한 패키지를 미리 설치해 두어야 합니다. 빌드 시간과 RSS 변화는 워크로드마다 다르므로 수치를 가정하지 말고 직접 측정하십시오.

팁 - 같은 코드에서 mimalloc과 기본 할당자를 비교하려면 #[global_allocator] 선언이 있는 빌드와 없는 빌드를 만들어 같은 부하로 측정하십시오. 교체와 되돌리기가 이만큼 쉽다는 점이 시험해 볼 가장 큰 이유입니다.

8. 공개 사용처 - README와 공식 문서가 밝힌 곳

공식 문서가 밝힌 사용처만 적습니다(2026-09-29 확인).

  • Microsoft 서비스: README 「Usage」 절은 대규모 저지연 서비스의 예로 Bing과 Azure를 듭니다. README는 mimalloc을 수천 대 머신의 대규모 분산 서비스를 돌리는 산업용 할당자로 설명합니다.
  • 게임: 같은 절에 데스 스트랜딩 PC판과 언리얼 엔진(4.25 릴리스 노트 링크)이 사용처로 올라 있습니다.
  • 언어 런타임·과학 도구: Koka·Lean 런타임에서 출발했고, CPython은 3.13부터 mimalloc을 기본으로 번들합니다(Python 문서 「What's New in Python 3.13」). README 사용처에는 유전체 조립 도구 SPAdes도 있습니다.
  • Rust 생태계: crates.io의 mimalloc 크레이트 누적 다운로드는 57,647,630회입니다(2026-09-29, crates.io API).

발행 당시 적었던 「2026년에 채택 곡선이 더 가파르게 오를 것」은 당시 전망이었습니다. 이번 확인으로 말할 수 있는 것은 v1·v2·v3 세 줄기가 2026년 8~9월에도 동시에 릴리스될 만큼 유지보수가 활발하다는 사실까지입니다.

9. 위험과 한계 - 솔직한 점검

mimalloc도 완벽하지 않습니다. 주요 위험은 다음과 같습니다.

9-1) 메모리 사용량(RSS) 증가 가능성

스레드별 캐시와 지연 purge 때문에 RSS가 glibc malloc보다 높게 보일 수 있습니다. README의 조정 옵션은 이렇습니다. MIMALLOC_PURGE_DELAY=N은 쓰지 않는 OS 페이지를 N밀리초 뒤에 purge합니다(v3 기본 1000, 0이면 즉시 purge해 메모리는 줄지만 성능이 떨어지고, -1이면 purge를 끕니다). MIMALLOC_PURGE_DECOMMITS는 기본값 1에서 decommit(리눅스 MADV_DONTNEED, RSS 즉시 감소)을 쓰고 0이면 reset(MADV_FREE)을 씁니다. 또 v3.5.1부터 리눅스 기본 빌드가 -DMI_ALLOW_THP=FULL이라 THP를 쪼개지 않아 RSS가 늘 수 있으며, 런타임에는 MIMALLOC_ALLOW_THP=0, 빌드 시에는 -DMI_ALLOW_THP=OFF로 끕니다. MIMALLOC_SHOW_STATS=1은 튜닝 옵션이 아니라 종료 시 통계를 보여 주는 옵션입니다.

9-2) 디버깅 도구와의 상호작용

README는 메모리 추적 도구와 함께 쓸 때 기본적으로 표준 할당자를 권장합니다. 대신 mimalloc을 Valgrind 지원(-DMI_TRACK_VALGRIND=ON), AddressSanitizer 지원(-DMI_TRACK_ASAN=ON), Windows ETW 지원(-DMI_TRACK_ETW=ON)으로 빌드할 수 있으며, Valgrind·ASan 지원은 초기 개발 단계라고 적습니다. 디버그 빌드(-DCMAKE_BUILD_TYPE=Debug 또는 -DMI_DEBUG=ON)는 크기별 통계, 블록 끝 padding을 이용한 바이트 단위 오버플로 탐지, double free·잘못된 포인터 해제·free list 손상·일부 use-after-free 탐지를 제공합니다. guarded 모드(-DMI_GUARDED=ON, 디버그 빌드에서 기본 ON)는 MIMALLOC_GUARDED_SAMPLE_RATE=N으로 N번째 할당마다 guard page를 두어 운영 중에도 표본 방식으로 오버플로를 잡을 수 있습니다.

9-3) glibc 특화 동작에 의존하는 코드

mallopt 같은 glibc 전용 튜닝이나 동작에 기대는 레거시 코드는 교체 후 다르게 동작할 수 있습니다. 또 프로세스 전체를 override할 때 다른 경로에서 받은 포인터가 mi_free로 넘어오는 경우가 있는데, README는 이런 경우 모든 포인터의 유효성을 검사하는 -DMI_FREE_IS_CHECKED=ON(secure 모드에서 기본 ON)이 필요할 수 있다고 적습니다. 임베디드·드라이버 영역에서는 사전 검증이 필요합니다.

9-4) fork()와 대형 OS 페이지

README는 대형(2MiB)·초대형(1GiB) OS 페이지를 쓰면서 fork하면 copy-on-write 때문에 쓰기가 일어날 때 페이지 전체가 복사되어 메모리가 큰 단위로 늘 수 있다고 경고합니다. MIMALLOC_ALLOW_LARGE_OS_PAGES나 MIMALLOC_RESERVE_HUGE_OS_PAGES를 켠 상태에서 fork가 잦은 워크로드(prefork 서버 등)는 별도 검증이 필요합니다.

9-5) 정리

위험은 모두 관리 가능한 수준이지만, 운영 적용 전 staging에서 최소 1주 부하 테스트로 RSS·지연·p99를 glibc 대비 정량 비교하는 절차는 생략하지 않는 편이 좋습니다. 이 기간은 이 글의 권장이며 공식 기준은 아닙니다.

10. 2026 메모리 할당자 트렌드 - mimalloc 외 흐름

발행 당시 적었던 흐름 세 가지를 2026-09-29 확인한 사실로 다시 정리합니다.

10-1) 하드웨어를 의식하는 설정

mimalloc은 NUMA 노드를 런타임에 감지하고 MIMALLOC_USE_NUMA_NODES로 조정할 수 있으며, v3에 mi_heap_set_numa_affinity가 추가되었습니다. 1GiB 초대형 페이지 예약(MIMALLOC_RESERVE_HUGE_OS_PAGES, 특정 NUMA 노드는 _AT), THP 활용(v3.5.1부터 리눅스 기본), 아키텍처 최적화 빌드(-DMI_OPT_ARCH: x64는 haswell·avx2, arm64는 armv8.1, Apple은 armv8.3)도 있습니다. README는 NUMA 지역 할당이 최선 노력이지 보장이 아니라고 밝힙니다. 발행 당시의 HBM·persistent memory 전망은 이번에 근거를 확인하지 않아 뺐습니다.

10-2) 다른 계열 할당자와 파생 프로젝트 - 활동성부터 확인

발행 당시 이 글은 snmalloc을 mimalloc의 변종·후속작으로 적었지만, snmalloc은 Microsoft 저장소(microsoft/snmalloc)에 있는 별개 설계의 「메시지 전달 기반 할당자」입니다. 「mi-game」 같은 파생은 확인하지 못해 뺐습니다. 파생이나 포크를 운영에 쓰기 전 maintainer 활동성과 패치 주기를 확인한다는 원칙은 그대로 유효합니다. 참고로 GitHub API 기준 마지막 반영일은 mimalloc 2026-09-29, tcmalloc 2026-09-29, jemalloc 2026-09-27, snmalloc 2026-09-23, rpmalloc 2026-07-15입니다.

10-3) Rust 생태계의 글로벌 할당자 선택

Rust는 #[global_allocator]로 프로세스 전체 할당자를 한 줄로 바꿀 수 있고, mimalloc 크레이트 누적 다운로드는 5,700만 회를 넘었습니다. 발행 당시의 「기본 할당자를 바꾸자는 논의가 주기적으로 나온다」는 당시 관찰이었고 이번에 근거를 확인하지 않았습니다. 이 글의 권장은 신규 Rust 서비스에서 mimalloc을 후보로 두되, 기본값으로 굳히기 전에 자기 워크로드에서 측정하는 것입니다.

11. 결론 + 즉시 적용 가능한 3가지

mimalloc을 한 문장으로 요약하면 이것입니다. 「되돌리기 쉬운 drop-in malloc 대체이고, 공개 벤치마크상 스레드 사이의 할당·해제가 많은 워크로드에서 특히 강하다. 다만 그 수치는 2021년 측정이므로 자기 워크로드에서 다시 재야 한다」. 바로 해 볼 수 있는 세 가지입니다.

11-1) 즉시 적용 1: LD_PRELOAD로 30분 PoC

운영 중인 바이너리에 LD_PRELOAD=/usr/lib/libmimalloc.so와 MIMALLOC_VERBOSE=1을 붙여 적용 여부를 확인하고, 30분 부하를 돌려 RSS·CPU·지연을 glibc 대비 비교하십시오. 이득이 뚜렷하면 staging 부하 테스트로, 미미하면 환경변수를 빼서 되돌리면 됩니다.

11-2) 즉시 적용 2: Rust 신규 프로젝트는 mimalloc을 후보로

Rust로 신규 서비스를 만든다면 Cargo.toml에 mimalloc = "0.1"을 추가하고 #[global_allocator]를 선언해 기본 할당자와 비교해 보십시오. 5분이면 됩니다. 기본은 mimalloc v3이고, 필요하면 v2 feature로 바꿀 수 있습니다. 효과의 크기는 측정으로 확인합니다.

11-3) 즉시 적용 3: 보안 민감 서비스는 mimalloc-secure 검토

네트워크 노출·사용자 입력 파싱 서비스는 README 기준 평균 약 10% 비용으로 guard page·free list 인코딩·double free 탐지·무작위화를 얻는 mimalloc-secure를 검토하십시오. 운영 중 오버플로를 표본으로 잡는 것이 목적이라면 guarded 모드와 MIMALLOC_GUARDED_SAMPLE_RATE도 후보입니다.

마지막으로 이 글이 강조하는 메시지는 이것입니다. 메모리 할당자는 「보이지 않는 성능 지렛대」입니다. 코드 한 줄, 환경변수 한 줄로 성능 지표를 바꿀 수 있는 영역은 흔치 않고, mimalloc은 그중 진입 장벽이 낮은 도구입니다. 다만 효과의 크기는 워크로드가 정합니다. 신규 시스템을 설계한다면 한 번은 측정해 볼 만한 컴포넌트입니다.

## 2. 교체를 시험할지 판단 (하나라도 해당하면 staging 시험)

- [ ] 한 스레드가 할당하고 다른 스레드가 해제하는 일이 많다
- [ ] CPU 프로파일에 `malloc`·`free` 경합이 보인다
- [ ] 짧은 수명 객체를 많이 만드는 언어 런타임·인터프리터다
- [ ] 재시작 없이 며칠 이상 돌며 RSS가 서서히 오른다 (누수가 아님을 먼저 확인)
- [ ] 신뢰할 수 없는 입력을 파싱하며 약 10% 성능 여유가 있다 (secure 후보)
- [ ] Rust·C++ 프로젝트에서 글로벌 할당자를 바꿀 수 있다

전부 해당하지 않으면 기본 할당자로 충분할 수 있다.

---

## 3. 30분 PoC 절차 (리눅스)

- [ ] 기준선: glibc로 같은 부하를 30분 돌려 RSS·CPU·지연·p99 기록
- [ ] `MIMALLOC_VERBOSE=1 LD_PRELOAD=/usr/lib/libmimalloc.so <프로그램>` 으로 적용 확인
- [ ] 같은 부하 30분, 같은 지표 기록
- [ ] 이득이 뚜렷하면 staging 부하 테스트(이 글의 권장: 최소 1주)로 진행
- [ ] 이득이 미미하면 `LD_PRELOAD` 를 빼서 되돌리고 결과를 남김

macOS는 `DYLD_INSERT_LIBRARIES`, Windows는 `mimalloc-redirect.dll` 방식이다.

---

## 4. RSS가 높게 보일 때 조정표

| 옵션 | 뜻 | 쓰는 방향 |
|---|---|---|
| `MIMALLOC_PURGE_DELAY=N` | 쓰지 않는 OS 페이지를 N ms 뒤 purge | 0 = 즉시(메모리↓ 성능↓), -1 = purge 끔 |
| `MIMALLOC_PURGE_DECOMMITS` | 1 = decommit(`MADV_DONTNEED`, RSS 즉시 감소), 0 = reset(`MADV_FREE`) | 기본 1 |
| `MIMALLOC_ALLOW_THP=0` | THP 사용 끄기 | RSS를 줄이고 싶을 때 |
| `-DMI_ALLOW_THP=OFF` | 빌드 시 THP 끄기 | 같은 목적, 빌드 단계 |
| `MIMALLOC_SHOW_STATS=1` | 종료 시 통계 출력 | 튜닝이 아니라 관찰용 |

---

## 5. 빌드 모드 선택표

| 목적 | 빌드 | 비고 |
|---|---|---|
| 힙 공격 완화 | `-DMI_SECURE=ON` | guard page·포인터 인코딩·double free 탐지·무작위화, 평균 약 10% |
| 최대 완화 | `-DMI_SECURE=FULL` | 페이지마다 guard page, README가 일반적으로 비권장(VMA 한도) |
| 개발 중 오류 탐지 | `-DCMAKE_BUILD_TYPE=Debug` 또는 `-DMI_DEBUG=ON` | 바이트 단위 오버플로·double free·일부 use-after-free |
| 운영 중 표본 탐지 | `-DMI_GUARDED=ON` + `MIMALLOC_GUARDED_SAMPLE_RATE=N` | N번째 할당마다 guard page |
| Valgrind·ASan 사용 | `-DMI_TRACK_VALGRIND=ON` / `-DMI_TRACK_ASAN=ON` | 초기 개발 단계, README는 보통 표준 할당자 권장 |

---

## 6. 운영 전 위험 확인

- [ ] `mallopt` 등 glibc 전용 동작에 기대는 코드가 없는가
- [ ] 프로세스 전체 override 시 다른 경로 포인터가 `mi_free` 로 가는가 → `-DMI_FREE_IS_CHECKED=ON` 검토
- [ ] 대형·초대형 OS 페이지(`MIMALLOC_ALLOW_LARGE_OS_PAGES`, `MIMALLOC_RESERVE_HUGE_OS_PAGES`)를 켜고 fork가 잦은가 → COW로 메모리 급증 가능
- [ ] Go·Java라면 영향 범위가 cgo·JNI 네이티브 할당뿐임을 이해했는가
