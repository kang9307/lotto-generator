デモはWindows 10のGit Bash(bash 5.2.37)でGNU tar 1.35を使って実行した。出力は実行結果そのままで、一時フォルダのパスだけを /tmp/demo に置き換えている。同じPCのWindows標準tar.exe(bsdtar 3.5.2)は9節で別に比べる。LinuxとmacOSのtarは実行していないため、以下の動作は「このPCのtarの出力」であり、理由の説明は出力が直接示すこととGNU tarのマニュアルページ(man.archlinux.org)の文に限る。

序論 - アーカイブ内のパスは、まとめるときに渡した文字列である

tarアーカイブはファイルの内容と一緒に名前の文字列を保存する。展開するときは、その名前をカレントディレクトリ(または指定した基準ディレクトリ)以下のパスとして解釈してファイルを作る。したがって、まとめるときにどんな文字列を渡したかが、展開後の位置を決める。tar -cf out.tar app のように相対パスを渡すと名前は app/... で始まり、/home/user/app のような絶対パスを渡すとパス全体が名前に入ろうとする。このときtarは先頭のスラッシュを取り除き、警告を出す。

問題はその後に出てくる。取り除かれるのは先頭のスラッシュだけで、上位ディレクトリの名前は残るため、別の場所に展開すると app ではなく上位パス全体が入れ子になって作られる。この現象を同じダミーツリーの出力で示し、基準ディレクトリの -C、絶対パスを保つ -P、.. 成分を含むエントリ、展開前の一覧確認、最上位ディレクトリを1つにまとめる慣例を順に扱う。後ろのスラッシュが対象を変えるrsync側の事情はrsyncの末尾スラッシュの記事が扱うので、ここではtarの先頭スラッシュとパス名だけを扱う。

扱う問いは次のとおりである。

  • 絶対パスでまとめるとき、tarは何を出力し、終了コードはどうなるか。
  • そのアーカイブを別のディレクトリに展開すると、ファイルはどこにできるか。
  • -C と相対パスは同じアーカイブを作るか。また -C の位置の規則は何か。
  • -P はまとめるときだけに影響するのか、展開時はどう動くのか。
  • .. 成分を含むエントリと絶対パスのエントリは、展開時にどう処理されるか。
  • 展開前に何を確認し、どんな形でまとめれば散らばらないか。

デモ環境と安全の枠

すべてのデモは mktemp -d で作った新しい一時フォルダの中だけにファイルを作り、最後にそのフォルダだけを削除する。絶対パスを使う例も、その一時フォルダ内のパスだけを対象にする。show 関数は出力に現れる一時フォルダのパスを /tmp/demo に置き換える表示用のフィルタで、tarの動作には関与しない。ダミーツリーは src/app の下のファイル3つである。

D=$(mktemp -d) && cd "$D" || exit 1
                    show() { sed -e "s#$D#/tmp/demo#g" -e "s#${D#/}#tmp/demo#g"; }
                    mkdir -p src/app/bin src/app/conf src/app/data
                    echo 'echo run' > src/app/bin/run.sh
                    echo 'port=8080' > src/app/conf/app.conf
                    echo 'alpha' > src/app/data/a.txt
                    tar --version | head -1
tar (GNU tar) 1.35

種類とバージョンは tar --version の1行目で見分ける。このPCのGit BashではGNU tar 1.35で、以降の出力はすべてこのtarのものである。

絶対パスでまとめると - 警告と一覧

tar -cf abs.tar "$D/src/app"
                    echo "exit=$?"
                    tar -tf abs.tar | show
tar: Removing leading `/' from member names
                    exit=0
                    tmp/demo/src/app/
                    tmp/demo/src/app/bin/
                    tmp/demo/src/app/bin/run.sh
                    tmp/demo/src/app/conf/
                    tmp/demo/src/app/conf/app.conf
                    tmp/demo/src/app/data/
                    tmp/demo/src/app/data/a.txt

1行目はstderrに出た警告 Removing leading `/' from member names である。終了コードは0なので、失敗ではなく警告である。一覧(tar -tf)のメンバー名はスラッシュで始まらないが、tmp/demo/src/app/... のように上位パス全体が名前に入っている。デモのパスを /tmp/demo に置き換えただけで、実際の名前はまとめるときに渡した絶対パスから先頭のスラッシュを1つ除いた文字列である。

展開したとき - 上位パスがそのまま作られる

mkdir restore1
                    tar -C restore1 -xf abs.tar
                    (cd restore1 && find . -type f | sort) | show
./tmp/demo/src/app/bin/run.sh
                    ./tmp/demo/src/app/conf/app.conf
                    ./tmp/demo/src/app/data/a.txt

-C restore1 で基準ディレクトリを指定したのに、ファイルは restore1/app/... ではなく restore1/tmp/demo/src/app/... にできた。名前の中に上位パスが入っているので、展開時もそのまま入れ子のディレクトリが作られる。これが「展開したら思わぬ場所にファイルができた」問題がこのデモで現れた形である。ファイルが消えたのではなく、基準ディレクトリの下の深い場所にある。

相対パスと -C - 基準ディレクトリを決めてから入れる

(cd src && tar -cf ../rel.tar app)
                    tar -C src -cf c.tar app
                    tar -tf c.tar
                    cmp rel.tar c.tar && echo "rel.tar and c.tar are byte-identical"
                    mkdir restore2
                    tar -C restore2 -xf c.tar
                    (cd restore2 && find . -type f | sort)
app/
                    app/bin/
                    app/bin/run.sh
                    app/conf/
                    app/conf/app.conf
                    app/data/
                    app/data/a.txt
                    rel.tar and c.tar are byte-identical
                    ./app/bin/run.sh
                    ./app/conf/app.conf
                    ./app/data/a.txt

cd src のあと tar -cf ../rel.tar app で作ったものと、tar -C src -cf c.tar app で作ったものは、cmp がバイト単位で同一と答えた。メンバー名は app/... で始まり、警告もなく、展開すると restore2/app/... になる。GNU tarのマニュアルページは -C を次のように説明している。「Change to DIR before performing any operations. This option is order-sensitive, i.e. it affects all options that follow.」(出典: man.archlinux.org/man/tar.1.en)

「order-sensitive」という文は、次の出力にそのまま現れる。コマンドは、同じファイルを . で入れる形、-C を複数回使う形、そして -C を名前の後ろに置いた形である。

tar -C src/app -cf dot.tar .
                    tar -tf dot.tar
                    mkdir -p pos/a pos/b
                    echo A > pos/a/fa.txt
                    echo B > pos/b/fb.txt
                    tar -cf pos1.tar -C pos/a fa.txt -C ../b fb.txt
                    tar -tf pos1.tar
                    tar -cf pos2.tar fa.txt -C pos/a
                    echo "exit=$?"
./
                    ./bin/
                    ./bin/run.sh
                    ./conf/
                    ./conf/app.conf
                    ./data/
                    ./data/a.txt
                    fa.txt
                    fb.txt
                    tar: fa.txt: Cannot stat: No such file or directory
                    tar: The following options were used after non-option arguments.  These options are positional and affect only arguments that follow them.  Please, rearrange them properly.
                    tar: -C 'pos/a' has no effect
                    tar: Exiting with failure status due to previous errors
                    exit=2
  • -C src/app -cf dot.tar . のメンバー名は ./ で始まり、名前に app のような最上位ディレクトリがない。最上位の名前の問題は8節で扱う。
  • -C pos/a fa.txt -C ../b fb.txt では、2つ目の -C の ../b は1つ目の -C が移した位置(pos/a)を基準に解釈され、pos/b になった。一覧では fa.txt と fb.txt がどちらも名前だけになっている。
  • -C を名前の後ろに置いた tar -cf pos2.tar fa.txt -C pos/a は、fa.txt: Cannot stat に続いて -C 'pos/a' has no effect を出力し、終了コード2で終わった。-C は自分より後ろの名前にだけ適用される。

-P - 絶対パスを保つと -C が効かなくなる

GNU tarのマニュアルページの -P の項目は1行である。「-P, --absolute-names: Don't strip leading slashes from file names when creating archives.」この文は作成時について述べているが、以下の出力では一覧と展開にも影響が現れた。アーカイブは前の節と同じ対象を -P でまとめたものである。

tar -P -cf p.tar "$D/src/app"
                    echo "exit=$?"
                    echo '--- list without -P'
                    tar -tf p.tar 2>&1 | show | head -3
                    echo '--- list with -P'
                    tar -P -tf p.tar | show | head -3
exit=0
                    --- list without -P
                    tar: Removing leading `/' from member names
                    /tmp/demo/src/app/
                    /tmp/demo/src/app/bin/
                    --- list with -P
                    /tmp/demo/src/app/
                    /tmp/demo/src/app/bin/
                    /tmp/demo/src/app/bin/run.sh

-P でまとめるときは警告がなく、終了コードは0である。一覧の出力は2通りある。-P なしで tar -tf を実行すると、警告をもう一度出しつつ、名前は /tmp/demo/src/app/ のようにスラッシュで始まる保存されたままの形で表示される。-P を付けると警告なしで同じ一覧が出る。したがって、一覧の名前の1文字目がスラッシュかどうかが、-Pで作られたアーカイブを見分ける手がかりになる。

続いて、このアーカイブを -P と -C restore3 を併用して展開した。先に元の src を src_before に移して元の場所を空にしてあり、展開先はすべて一時フォルダの中である。

mv src src_before
                    mkdir restore3
                    tar -P -C restore3 -xf p.tar
                    echo "exit=$?"
                    echo "files under restore3: $(find restore3 -type f | wc -l)"
                    find src -type f | sort
                    diff -r src src_before && echo "recreated src is identical to src_before"
                    mkdir restore4
                    tar -C restore4 -xf p.tar
                    (cd restore4 && find . -type f | sort) | show
exit=0
                    files under restore3: 0
                    src/app/bin/run.sh
                    src/app/conf/app.conf
                    src/app/data/a.txt
                    recreated src is identical to src_before
                    tar: Removing leading `/' from member names
                    ./tmp/demo/src/app/bin/run.sh
                    ./tmp/demo/src/app/conf/app.conf
                    ./tmp/demo/src/app/data/a.txt

結果は3つある。第一に、-P -C restore3 で展開したとき restore3 の下のファイルは0個で、ファイルは空けておいた元の場所 src/app に再作成された。絶対名を持つエントリには -C が作用しなかった。第二に、再作成された src は src_before と diff -r で同一だった。第三に、-P なしで同じアーカイブを -C restore4 に展開すると、警告とともに restore4/tmp/demo/src/app/... に入れ子になる。

まとめ方展開の仕方ファイルができた場所警告
-P なしの絶対パス-C restore1restore1/tmp/demo/src/app/...(入れ子)まとめるときのみ
-P ありの絶対パス-C restore4(-P なし)restore4/tmp/demo/src/app/...(入れ子)展開時に出力
-P ありの絶対パス-P -C restore3元の絶対パスの場所 src/app(restore3 は空のまま)なし
  • -P で展開するときは -C を無視し、記録された絶対位置に書き込む。その位置は展開コマンドの -C とは無関係に決まるため、展開コマンドだけを見ても、ファイルがどこにできるかは分からない。
  • そのため -P は自分のファイルを同じ場所に復元する用途で使い、出所が不明なアーカイブでは展開前に一覧の1文字目をまず見る(8節)。
  • このデモで -P によって書き込まれた場所は一時フォルダ内の元の場所で、システムやホームのパスには書いていない。

.. 成分を含むエントリと絶対名のエントリ - 展開時の扱い

まず、.. で始まるパスをまとめるときにtarがどうするかを見る。サブフォルダから上位のファイル ../outside.txt をまとめた。

mkdir -p work/sub
                    echo 'outside content' > work/outside.txt
                    (cd work/sub && tar -cf ../dd.tar ../outside.txt)
                    tar -tf work/dd.tar
tar: Removing leading `../' from member names
                    outside.txt

まとめるときtarは Removing leading `../' from member names という警告を出し、名前を outside.txt に縮めた。そのため、先頭の ../ はGNU tarでまとめる際に取り除かれ、.. のエントリは作られなかった。展開時の動作を見るには名前をそのまま書けるツールが必要で、以下ではPython標準ライブラリの tarfile でデモ用アーカイブを2つ作った。1つは ok/inside.txt と ../escape.txt を含み、もう1つは一時フォルダ内の絶対名 .../ext/abs_target.txt を含む。引数として渡す一時フォルダのパスをGit Bashが書き換えないよう MSYS_NO_PATHCONV=1 を付けた。この接頭辞はGit Bash専用である。

mkdir craft ext
                    cat > craft/make.py <<'PYEOF'
                    import io, sys, tarfile
                    target = sys.argv[1]
                    def add(tf, name, data):
                        info = tarfile.TarInfo(name)
                        info.size = len(data)
                        tf.addfile(info, io.BytesIO(data))
                    with tarfile.open('craft/dotdot.tar', 'w') as tf:
                        add(tf, 'ok/inside.txt', b'inside')
                        add(tf, '../escape.txt', b'escaped')
                    with tarfile.open('craft/abs.tar', 'w') as tf:
                        add(tf, target + '/ext/abs_target.txt', b'absolute')
                    PYEOF
                    MSYS_NO_PATHCONV=1 python craft/make.py "$D"
                    tar -tf craft/dotdot.tar
                    tar -tf craft/abs.tar 2>&1 | show
ok/inside.txt
                    tar: Removing leading `../' from member names
                    ../escape.txt
                    tar: Removing leading `/' from member names
                    /tmp/demo/ext/abs_target.txt

2つのアーカイブの一覧でも、tar -tf は ../ と先頭のスラッシュについて警告を出す。次に、一時フォルダ内の ext/inner で展開してみる。.. エントリの行き先は1つ上の ext で、すべて一時フォルダの中である。

mkdir ext/inner
                    (cd ext/inner && tar -xf ../../craft/dotdot.tar; echo "exit=$?")
                    find ext | sort
                    (cd ext/inner && tar -P -xf ../../craft/dotdot.tar; echo "exit=$?")
                    find ext | sort
tar: Removing leading `../' from member names
                    tar: ../escape.txt: Member name contains '..'
                    tar: Exiting with failure status due to previous errors
                    exit=2
                    ext
                    ext/inner
                    ext/inner/ok
                    ext/inner/ok/inside.txt
                    exit=0
                    ext
                    ext/escape.txt
                    ext/inner
                    ext/inner/ok
                    ext/inner/ok/inside.txt

デフォルト設定では、../escape.txt は Member name contains '..' というエラーで展開されず、終了コードは2だった。同じアーカイブの通常のエントリ ok/inside.txt は展開された。-P を付けると終了コード0で終わり、ext/escape.txt が ext/inner の外側に作られた。1つのエントリの拒否が残りの展開を止めなかったことと、-P が .. の検査まで外したことが、この出力から直接見える。

絶対名のエントリも同じ方法で展開した。以下の find は abs_target.txt が置かれた場所だけを出力する。

(cd ext/inner && tar -xf ../../craft/abs.tar)
                    find ext -name abs_target.txt | show
                    (cd ext/inner && tar -P -xf ../../craft/abs.tar)
                    find ext -name abs_target.txt | show
tar: Removing leading `/' from member names
                    ext/inner/tmp/demo/ext/abs_target.txt
                    ext/abs_target.txt
                    ext/inner/tmp/demo/ext/abs_target.txt

デフォルト設定では警告とともに ext/inner/tmp/demo/ext/abs_target.txt に入れ子になり、-P を付けた2回目の展開では記録された絶対位置 ext/abs_target.txt にもファイルが作られた。まとめると、デフォルト設定は先頭のスラッシュを取り除いて .. を拒否し、-P はその両方を外す。

アーカイブのメンバー名デフォルト設定での展開-P を付けた展開
ok/inside.txt(普通の相対名)ext/inner/ok/inside.txt に作成同じ場所に作成
../escape.txt(.. 成分)Member name contains '..' エラー、終了コード2、ファイルなしext/escape.txt を作成(ext/inner の外)、終了コード0
/tmp/demo/ext/abs_target.txt(絶対名)警告のあと ext/inner/tmp/demo/ext/abs_target.txt に入れ子記録された絶対位置 ext/abs_target.txt に作成

展開前の確認と、最上位ディレクトリを1つにする慣例

7節の2つの危険は、一覧の段階でふるい分けられる。以下の grep は、スラッシュで始まる名前か .. 成分を持つ名前だけを選び出す。この正規表現はデモ用で、tarが提供する機能ではない。

tar -tf p.tar 2>/dev/null | grep -E '^/|(^|/)\.\.(/|$)' | show | head -2
                    tar -tf craft/dotdot.tar 2>/dev/null | grep -E '^/|(^|/)\.\.(/|$)'
                    tar -tf rel.tar | grep -cE '^/|(^|/)\.\.(/|$)'
/tmp/demo/src/app/
                    /tmp/demo/src/app/bin/
                    ../escape.txt
                    0

-P で作った p.tar はスラッシュで始まる名前が、dotdot.tar は ../escape.txt が引っかかり、相対パスで作った rel.tar は0件だった。展開前にこの一覧を人が読むか、スクリプトが検査すれば、7節の動作に至る前にアーカイブをふるい落とせる。一覧を読むことはファイルを作らないので、元に戻すものがない。一覧の確認を展開の予行演習として使う方法は、シェルスクリプトの予行演習設計の記事にも出てくる。

最上位のエントリがいくつあるかも一覧で分かる。同じファイルを bin conf data の3つの名前でまとめたアーカイブと、app 1つでまとめたアーカイブを比べ、すでにファイル(mine.txt)があるディレクトリに展開した。

tar -C src/app -cf bomb.tar bin conf data
                    tar -tf bomb.tar | cut -d/ -f1 | sort -u
                    tar -C src -cf one.tar app
                    tar -tf one.tar | cut -d/ -f1 | sort -u
                    mkdir spill
                    echo keep > spill/mine.txt
                    (cd spill && tar -xf ../bomb.tar && ls)
                    mkdir clean
                    (cd clean && tar --one-top-level=out -xf ../bomb.tar && find . | sort)
bin
                    conf
                    data
                    app
                    bin
                    conf
                    data
                    mine.txt
                    .
                    ./out
                    ./out/bin
                    ./out/bin/run.sh
                    ./out/conf
                    ./out/conf/app.conf
                    ./out/data
                    ./out/data/a.txt
  • bin conf data でまとめたアーカイブは最上位の名前が3つで、展開すると mine.txt があるディレクトリに bin・conf・data が混ざって入った。
  • app 1つでまとめたアーカイブは最上位の名前が1つだけなので、どこに展開しても app の下にまとまる。
  • --one-top-level=out は受け取る側で使う保護手段である。マニュアルページは「Extract all files into DIR, or, if used without argument, into a subdirectory named by the base name of the archive」と説明しており、出力では out/ の下にまとまった。
  • まとめる側の慣例は、-C を親ディレクトリに移してディレクトリ名を1つだけ渡すことである(tar -C src -cf one.tar app)。

最後に、既存のファイルと名前が重なるときのデフォルトの動作である。ow/note.txt に OLD と書いておき、NEW を入れた同名のファイルを展開する。マニュアルページは -k を「Don't replace existing files when extracting.」と記している。

mkdir ow t1
                    echo OLD > ow/note.txt
                    echo NEW > t1/note.txt
                    tar -C t1 -cf note.tar note.txt
                    (cd ow && tar -k -xf ../note.tar; echo "exit=$?"; cat note.txt)
                    (cd ow && tar -xf ../note.tar; echo "exit=$?"; cat note.txt)
tar: note.txt: Cannot open: File exists
                    tar: Exiting with failure status due to previous errors
                    exit=2
                    OLD
                    exit=0
                    NEW

-k を付けると note.txt: Cannot open: File exists というエラーと終了コード2が出て、内容は OLD のままだった。オプションなしで展開すると終了コード0で、内容は NEW に変わった。デフォルトの動作は確認なしで上書きし、メッセージも出ない。同じ名前がありうるディレクトリに展開するときは、空のディレクトリを作って -C で指定すると、この結果を避けられる。

同じPCの2つのtar - GNU tarとWindows標準のtar.exe

Windows 10には C:\Windows\System32\tar.exe があり、Git Bashのtarとは種類が違う。同じダミーツリーと同じデモ用アーカイブで動作を比べた。絶対パスは cygpath -m で得た C:/... の形で渡し、出力のパスは showw フィルタで置き換えた。

BSD=/c/Windows/System32/tar.exe
                    "$BSD" --version
                    DM=$(cygpath -m "$D")
                    showw() { sed -e "s#${DM#?:/}#demo#g" -e "s#$DM#C:/demo#g"; }

まとめ - まとめるときと展開するときの順序

  • まとめるときは、基準にする親ディレクトリを -C で指定し、ディレクトリ名を1つだけ渡す(tar -C 親パス -cf out.tar 名前)。警告は出ず、メンバー名が 名前/... で始まる(5節)。
  • Removing leading の警告が出たら、すでに絶対パスでまとめられたということなので、そのアーカイブを展開すると上位パスが入れ子になることを見込む(3節・4節)。
  • 受け取ったアーカイブは展開前に tar -tf で一覧を読み、スラッシュで始まる名前、.. 成分、最上位の名前の数を確認する(8節)。
  • 展開するときは、新しく作った空のディレクトリを -C で指定する。同名の既存ファイルはデフォルト設定で確認なしに置き換わるので(8節)、空のディレクトリがその場合を防ぐ。
  • -P は展開時に -C を無視して記録された絶対位置に書き込む。自分のファイルを同じ場所に復元するときだけ使い、出所が不明なアーカイブには使わない(6節・7節)。
  • WindowsのGit Bashのtarと標準のtar.exeは、メッセージと終了コードが違うので、出力文字列を読むスクリプトは、使うtarを先に決めておく(9節)。

アーカイブのファイル名のエンコーディングの問題はここでは扱わず、zip内の韓国語ファイル名の記事がtarにエンコーディング宣言がないことも含めて扱っている。バックアップのアーカイブを一時ディレクトリに展開して復旧できるかを点検する手順は、バックアップと復旧戦略の記事にある。

確認できなかったこと

  • GNU tarの公式マニュアル(gnu.org)は、このPCからの接続が拒否されて開けなかった。引用した文は、GNU TAR Manualページと表示されたman.archlinux.org版のもので、その版にはパッケージ表記 1.35-5 が見える。
  • tarが先頭のスラッシュを取り除くよう設計された目的についての開発者側の説明。本文の理由の部分は、実行出力が示した動作(警告、入れ子、-C の無視、.. の拒否)に限った。
  • LinuxとmacOSのtarの出力。このPCで実行したのはGit BashのGNU tar 1.35とWindowsのbsdtar 3.5.2だけである。
  • 他のGNU tarのバージョンでの警告の文言と .. の検査方法、シンボリックリンク・ハードリンクのメンバーを持つアーカイブの展開動作。
  • --strip-components・--transform のような名前加工オプションと、圧縮形式(gz・xz)との組み合わせ。
  • bsdtarの -P の動作と、Windowsの長いパスやドライブ文字が混ざった名前での展開結果。
