Ceph Storage Overview and Detailed Guide

Comprehensive Guide to Ceph Storage

2025-06-02 Dev & Infra

Ceph is an open-source distributed storage system that provides object, block, and file storage capabilities on a single, unified platform. When you need a storage solution that delivers high scalability, reliability, and performance in large-scale data centers and cloud environments, Ceph is an excellent choice.

It combines object, block, and file storage under one roof so that organizations can standardize on a single platform instead of deploying separate systems for each workload.

Core Concepts of Ceph Storage

The Ceph architecture is built around several core concepts, and together they make Ceph's powerful performance and reliability possible.

RADOS (Reliable Autonomic Distributed Object Store)

RADOS is the object storage system that underpins Ceph. All data is stored as objects, and those objects are distributed across the entire cluster.

+-------------------+
|     Applications  |
+-------------------+
          |
+-------------------+
|  LIBRADOS (API)   |
+-------------------+
          |
+-------------------+
|   RADOS Cluster   |
| (OSD + Monitor)   |
+-------------------+

Key characteristics:

  • Automated data distribution and replication
  • Self-healing that automatically recovers from node failures
  • Cluster state monitoring and management

CRUSH Algorithm

CRUSH (Controlled Replication Under Scalable Hashing) is the algorithm that determines how Ceph distributes data across the cluster.

# Command to inspect the CRUSH map
ceph osd crush dump

Advantages of the CRUSH algorithm:

  • Computes data locations without a central lookup table
  • Minimizes data movement when the cluster configuration changes
  • Lets you define storage tiers and failure domains

OSD (Object Storage Daemon)

An OSD is the daemon process that actually stores and manages data. Typically one OSD is run per physical disk.

# Check OSD status
ceph osd status
ceph osd tree

The role of the OSD:

  • Storing and retrieving data
  • Coordinating data replication and recovery
  • Monitoring cluster health via heartbeat exchanges with other OSDs

Monitor

Monitor nodes maintain the cluster's state maps and provide cluster information to clients.

# Check monitor status
ceph mon stat

The role of the monitors:

  • Managing cluster maps (Monitor Map, OSD Map, PG Map, and others)
  • Client authentication and authorization
  • Quorum-based distributed decision-making

Placement Group (PG)

A PG is a logical unit that manages a set of objects, and it is what gives Ceph its scalability.

# Check PG status
ceph pg stat

Why PGs matter:

  • They efficiently manage millions of objects
  • They coordinate data replication and distribution across OSDs
  • They enable recovery work to be parallelized

Ceph's Main Storage Interfaces

Ceph offers three main storage interfaces to support a wide variety of use cases.

1. RADOS Gateway (RGW) - Object Storage

RGW is an object storage interface that exposes a RESTful API compatible with Amazon S3 and OpenStack Swift.

Use cases:

  • Cloud-native applications
  • Static web content hosting
  • Backup and archive solutions
  • Large-scale data repositories
# Start the RGW service
systemctl start ceph-radosgw@rgw.`hostname -s`

2. RADOS Block Device (RBD) - Block Storage

RBD is Ceph's block storage interface, providing block devices for virtual machines and containers.

Use cases:

  • Virtual machine disks (OpenStack, VMware)
  • Database storage
  • Kubernetes persistent volumes for containers
# Example: create an RBD image
rbd create --size 10G --pool rbd my_disk

Features:

  • Thin provisioning
  • Snapshots and clone support
  • Automatic data distribution and replication

3. CephFS - File Storage

CephFS provides a POSIX-compliant file system interface.

Use cases:

  • Shared file systems
  • Data analytics workloads
  • Large-scale home directories
# Example: mount CephFS
mount -t ceph mon1:6789:/ /mnt/cephfs -o name=admin,secret=[YOUR_CEPH_SECRET_KEY]

Features:

  • High-performance file operations through Metadata Servers (MDS)
  • Dynamic directory partitioning for improved scalability
  • POSIX ACL support

Ceph Installation and Configuration Overview

The basic steps for installing and configuring a Ceph cluster are as follows:

1. Prerequisites

# Install required packages on all nodes
apt-get update
apt-get install -y ceph-common python3 ntp

Required hardware:

  • At least 3 OSD nodes (for production environments)
  • At least 3 monitor nodes (for a highly available cluster)
  • Network connectivity between every node

2. Installation with Cephadm (the current recommended approach)

# Bootstrap with Cephadm
curl --silent --remote-name --location https://github.com/ceph/ceph/raw/octopus/src/cephadm/cephadm
chmod +x cephadm
./cephadm bootstrap --mon-ip <mon-ip>

3. Configuring Storage Pools

# Create a default replicated pool
ceph osd pool create mypool 128 128
ceph osd pool set mypool size 3

# Create an erasure-coded pool
ceph osd pool create ecpool 128 erasure
ceph osd pool set ecpool allow_ec_overwrites true

4. Client Configuration

# Distribute the client configuration files
ceph config generate-minimal-conf > /etc/ceph/ceph.conf
ceph auth get client.admin > /etc/ceph/ceph.client.admin.keyring

Performance Tuning for Ceph

Some important considerations for getting the most performance out of a Ceph cluster:

Network Optimization

# Network tuning parameters
net.core.rmem_max = 56623104
net.core.wmem_max = 56623104
net.core.rmem_default = 56623104
net.core.wmem_default = 56623104
net.core.optmem_max = 40960

Network recommendations:

  • Separate the public and cluster networks
  • At least a 10GbE network interface
  • Enable jumbo frames

OSD Optimization

# OSD tuning parameters
osd_memory_target = 4294967296  # 4GB
bluestore_cache_size_ssd = 3221225472  # 3GB for SSD

OSD recommendations:

  • High-performance disks (SSD or NVMe)
  • Dedicated journal devices
  • Separate metadata from data

Monitoring and Troubleshooting

# Monitor cluster health
ceph health detail
ceph -s

# Check performance counters
ceph daemon osd.0 perf dump

Key monitoring metrics:

  • IOPS and throughput
  • Latency
  • Recovery operation status
  • Cluster utilization

Ceph vs. Other Storage Solutions

Ceph vs. GlusterFS

Feature Ceph GlusterFS
Architecture Object-based File-based
Storage types Object, block, file Primarily file
Scalability Exabyte scale Petabyte scale
Complexity Relatively high Relatively low
Use cases Large-scale cloud File sharing / NAS

Ceph vs. Swift

Feature Ceph Swift
Scope Unified storage Object storage only
Consistency Strong consistency Eventual consistency
Block storage Native support Not supported
File system CephFS support Not supported

Ceph vs. HDFS

Feature Ceph HDFS
Primary purpose General-purpose storage Big data analytics
Data model Object-based Block-based
Access pattern Diverse workloads Optimized for sequential access
API S3 / Swift / POSIX HDFS API

The Future of Ceph

Ceph continues to evolve and is leading innovation in several key areas:

Performance Improvements

  • Ongoing improvements to the BlueStore storage engine
  • Optimizations for NVMe and persistent memory
  • Network protocol optimizations

Cloud-Native Integration

  • Tight integration with Kubernetes
  • Simplified containerized deployments
  • Support for microservice architectures

Simplified Management

  • New management tooling like Cephadm and Rook
  • Automated cluster management
  • Adoption of declarative configuration

Conclusion

Ceph is a powerful distributed storage solution that delivers scalability, reliability, and flexibility. Its ability to provide object, block, and file storage from a single system is a major advantage in modern data centers and cloud environments.

Combined with the ability to expand the cluster or add and replace nodes without downtime, Ceph's self-healing mechanisms for responding to hardware failures make it an enterprise-grade storage system.

Thanks to its open-source nature and active community support, Ceph will continue to innovate and evolve, cementing its place as a core component of cloud-native environments and modern data centers.
