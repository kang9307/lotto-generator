Split 10,000 KRW Three Ways and You Get 9,999 - The Won Has No Decimal Place

Where one won disappears and appears in splits, discounts, refunds and tax, and why the allocation has to be stored

2026-08-01 Development/Infrastructure

The symptom: the settlement total was one won short of the charge

The scenario is invented, but the shape is common. Three people split a 10,000 KRW order, and the card network approved exactly 10,000 KRW. Yet the settlement screen shows 9,999 KRW in the total column. Nobody knows where the missing won went, and the reconciliation job has halted on a total mismatch.

As money, one won is nothing. The problem is that this one won will not pass an automated reconciliation. Settlement checks mechanically whether the totals agree, and when they do not, a person has to open the case by hand. In a system carrying tens of thousands of transactions a day, a few hundred such cases add up to a few hundred won in value and several days of work.

Here is the conclusion up front. The usual advice, round more carefully, only covers half the problem. The real one is this.

  • Division always leaves a remainder, and the won has no decimal place to hold it. No choice of rounding mode makes the sum come out right
  • If you do not store the result of a division, you cannot restore it later. Refunds, cancellations and partial settlements all need to know who paid how much at the time, and recomputing does not give the same answer
  • One won is small, but a settlement that does not balance stops moving. This is a domain where the size of the amount and the size of the incident are unrelated

Every number below is not an estimate but output from an actual run. All of it can be checked on a calculator, so reproduce it yourself if any of it looks doubtful.

Environment. Every output below was produced on Windows 10 Pro (10.0.19045). The runtimes are Python 3.13.3 (win32) and Node.js v22.16.0 (win32, ICU 77.1), and the shell is GNU bash 5.2.37 (MSYS2/MinGW64). All scripts were saved to files and executed. All amounts are in Korean won.

What this article does not cover. It does not state what tax or accounting regulation requires of rounding. That is a matter of company policy, contracts and a qualified adviser. This article looks only at how code implements whatever that policy turns out to be, without drifting from it. The separate problem of numbers being mangled during serialization is covered in JSON number precision loss. Here the single subject is allocation in whole won. Every amount and cart shown is fictional.

1. The won has no decimal place to hold a fraction

It starts with the currency itself. The dollar has cents, the euro has cents, so both use two decimal places. The won does not. The international currency code standard assigns each currency a decimal exponent, and the won is listed at 0. The runtime was asked directly.

--- 0-1. default fraction digits per currency, straight from Intl ---
currency  formatted 1234.5        min  max
---------------------------------------------------

JPY       ¥1,235                 0    0
USD       $1,234.50              2    2
EUR       €1,234.50              2    2
KWD       KWD 1,234.500          3    3
CLF       CLF 1,234.5000         4    4

That table is the background for the whole article. Two decimal places is not a universal property of money. The Kuwaiti dinar uses three and the Chilean unit of account uses four. And the won and the yen use zero.

Nominally the won does have a subunit, the jeon, still on the books. It is not used in transactions and shows up only in places like exchange rate quotes, and the international standard puts the decimal count at zero. In practice, the smallest circulating denomination being one won is the whole story.

This is where the specifically Korean trap appears. A great many money libraries default to storing an integer number of minor units and dividing by 100 for display. For the dollar that is a fine design. Here is what happens when it is carried over to the won unchanged.

--- 0-2. what the generic cents pattern does to a KRW amount ---
amount in KRW                      : 1234
generic "store minor units" x100   : 123400
display that back /100 as KRW      : ₩1,234
the x100 is dead weight: KRW has no 1/100 to hold

--- 0-3. formatting a fractional KRW value ---
3333.3333333333335     -> ₩3,333
3333.5                 -> ₩3,334
3334.5                 -> ₩3,335
2450.5                 -> ₩2,451
2451.5                 -> ₩2,452
the formatter hides the fraction. it does not remove it,
and it is not the value that gets stored or charged
  • The x100 is pure waste. The won has no hundredth, so it only adds storage and conversion code. And if that x100 value ever leaks to a screen unconverted, it becomes a 123,400 won incident
  • More dangerous is the formatter behaviour in 0-3. Feed it a value with a fraction and it quietly shows an integer. The screen looks fine while the stored value still carries the fraction
  • Add several such rows and the displayed total parts ways with the real one. Formatting does not change the value. Rounding in the display layer and rounding in the storage layer are entirely different acts
  • Note also that this formatter pushed 3334.5 up to 3,335. That differs from the other rounding implementation shown later. Two such behaviours coexisting in one project is itself a source of one-won gaps

2. Splitting 10,000 KRW three ways

Now the core reproduction, starting from the simplest case.

python 3.13.3 / win32   currency KRW (integer, no minor unit)

--- 1-1. 10000 KRW, 3 payers, the plain way ---
total                : 10000
total / n            : 3333.3333333333335
Decimal exact        : 3333.333333333333333333333333
floor           3333  3333  3333  sum   9999   total-sum +1
round-half-up   3333  3333  3333  sum   9999   total-sum +1
ceil            3334  3334  3334  sum  10002   total-sum -2

That is the 9,999 from the opening. Reading it line by line:

  • The exact share is 3333.333… and there is no way to express it in won. Between 3,333 and 3,334 there is nothing
  • Flooring charges all three 3,333 for a total of 9,999. One won vanishes
  • Half-up rounding lands on the same value here because the fraction is 0.33. That is the first piece of evidence that switching to rounding does not fix anything
  • Ceiling charges all three 3,334 for a total of 10,002. Two won too much, which from the customer side is the worse failure

You might suspect 10,000 is a special number. The range was widened.

The result is unambiguous. Only the two rows whose total is a multiple of three come out right. The remaining five are off by between -2 and +2 no matter which mode is chosen. The last row is extreme: split one won three ways and flooring or rounding gives all three zero, so the whole won evaporates, while ceiling gives all three one won and collects three times the original.

There is one thing to take from this table. The rounding mode changes the direction of the error, not its existence. Removing it requires doing something else.

3. Floor, round, ceil - the difference in the totals

Errors accumulate once there is more than one line. Five shared costs were each divided by three to build one person's share, then multiplied back by three and compared against what the shop collects.

7000         2333.333333    2333   2333   2334
12500        4166.666667    4166   4167   4167
3300         1100.000000    1100   1100   1100
990          330.000000     330    330    330
45000        15000.000000   15000  15000  15000
-------------------------------------------------
one payer's share sums to   floor  22929   round  22930   ceil  22931
x3 (what the shop collects) floor  68787   round  68790   ceil  68793

Here rounding happened to be right. Only two lines produced a fraction and the two cancelled each other out. Do not read that coincidence as proof that rounding is correct. In the 10,000 KRW case above, the same rounding dropped a won. Sometimes right and sometimes not is the defining property of this approach.

And there is one more thing to check about rounding. The word does not name a single behaviour.

--- 2-2. the default round() in this runtime is NOT half-up ---

1.5        python round() 2       ROUND_HALF_UP 2       ROUND_HALF_EVEN 2

half-even sends x.5 to the nearest even integer, so 2.5 becomes 2, not 3

The default rounding function in this runtime is not half-up. It sends 2.5 to 2, not 3. On an exact half it goes to the nearest even integer, which is statistically less biased but differs from what a person expects. The internationalization formatter above pushed 3334.5 up to 3,335. When both live in the same project, some lines go up and some go down, and one-won differences appear scattered with no obvious cause.

4. Who gets the leftover won

That last row is the prescription. Instead of choosing a rounding mode, distribute the remainder explicitly. The method is simple: give everyone the floored share, then hand out the leftover one won at a time. The remainder is always smaller than the number of parties, so nobody ever pays two won extra.

What is left to decide is who receives it. Four policies were compared by running them.

--- 3-1. who gets the leftover 1 KRW: four policies, equal weights ---
total 10000  weights [1, 1, 1]   floor share 3333  leftover 1
policy      A      B      C      sum    sum==total
---------------------------------------------------
first      3334   3333   3333   10000  True
last       3333   3333   3334   10000  True
largest    3334   3333   3333   10000  True
rotate     3334   3333   3333   10000  True

--- 3-2. unequal weights: a 100000 KRW bill shared by usage ---
total 100000  weights [3, 3, 1] (sum 7)
  member 0 exact share : 42857.14285714285714285714286
  member 1 exact share : 42857.14285714285714285714286
  member 2 exact share : 14285.71428571428571428571429
policy      A      B      C      sum    sum==total
---------------------------------------------------
first      42858  42857  14285  100000 True
last       42857  42857  14286  100000 True
largest    42857  42857  14286  100000 True
rotate     42858  42857  14285  100000 True
largest-remainder gives the extra KRW to the biggest fractional part,
so the member who was cut the most is the one paid back first

All four policies produce a sum that is exactly the original amount. Every cell in the sum==total column is True. The only difference is who pays the extra won.

The second block shows the criterion for choosing. Splitting 100,000 KRW by usage in a 3:3:1 ratio, the largest fractional part belongs to the third member at 0.714. Largest-remainder gives the won to that member. The rule is compensate whoever was cut the most, which makes it the fairest choice for a single split.

But settlement usually repeats. Splitting the same way every month changes the picture.

The difference is visible. Rotating the starting position each month left all three payers at exactly 20,000 KRW after six months, a spread of zero. The fixed-first-payer policy had payer A paying one won extra every month, building a cumulative 6 KRW gap. One month it is one won, but in a subscription the bias piles up in one direction.

What matters is not which one is correct. All four balance. What has to be settled is writing down that this is the policy we use, in one place in the code and in the documentation, and after that, storing the result.

5. A discount changes value depending on where you round

Splits are not the only source of division. A percentage discount is a division too. Multiplying by 15 percent means multiplying by 85 and dividing by 100, so it leaves a remainder the same way. A fictional four-line cart was used to check.

--- 4-1. where you round a percent discount changes the bill ---
cart [1990, 2990, 5990, 990]   subtotal 11960 KRW   discount 15 percent

line   price    exact discounted   per-line floor  per-line half-up
--------------------------------------------------------------------
A      1990     1691.5             1691            1692
B      2990     2541.5             2541            2542
C      5990     5091.5             5091            5092
D      990      841.5              841             842
--------------------------------------------------------------------
A. round every line, then add  : floor 10164   half-up 10168
B. add first, then round once  : floor 10166   half-up 10166
exact untouched value          : 10166
A minus B                      : floor -2       half-up +2
same cart, same rate, same rounding mode - two different totals

The same cart, the same rate, the same rounding mode, and two totals come out. The only thing that differs is at which step the rounding happened.

  • All four lines end in .5, which makes the difference sharp. Rounding per line pushes all four up for +2, flooring per line pushes all four down for -2
  • The real spread is proportional to the line count. A twenty-line order can drift by ten won, a hundred-line order by fifty. That is where calling it a one-won problem stops being accurate
  • Neither is a wrong calculation. They are answers to different questions. The trouble starts when the order screen and the settlement job use different ones
  • If the customer receipt prints a discount per line, the calculation must be per line and stored. Store only the total and recompute lines on screen, and the receipt lines will not add up to the charge

5.1 Stack two discounts and the order changes the result

Percentage discounts stacking, a coupon on top of a membership rate, is routine. In pure multiplication the order does not matter. Insert a rounding step and it does.

--- 4-2. two stacked discounts, same rates, reversed order ---
price    10 then 3      3 then 10      one combined rate
-----------------------------------------------------------
28900    26010  -> 25230  28033  -> 25230  25230
33000    29700  -> 28809  32010  -> 28809  28809
19900    17910  -> 17373  19303  -> 17373  17373
12345    11111  -> 10778  11975  -> 10778  10777
7700     6930   -> 6722   7469   -> 6722   6722

sweep 1..50000 KRW : 15550 prices give a different final amount (31.1 percent)
  first six : 17 gives 15 or 14, 18 gives 16 or 15, 26 gives 22 or 23,
              36 gives 31 or 32, 46 gives 40 or 41, 51 gives 45 or 44
rounding BETWEEN the two steps is what makes the order matter

Five common price points all gave the same result when the order was reversed. Then sweeping every amount from 1 to 50,000 KRW found 15,550 prices where the answers differ. That is roughly one price in three.

The 12345 row hides one more trap. Applying the two discounts step by step gives 10,778, but multiplying 0.90 and 0.97 first and applying one combined rate gives 10,777. Mathematically identical rates, and the presence or absence of an intermediate rounding splits them by one won.

  • A test suite with a handful of values passes. Those five rows are the proof. This is why such bugs survive for years
  • The customer report arrives as my order is one won cheaper if I apply the coupon first. It is hard to reproduce, so it tends to get closed as not reproducible
  • The remedy is not rounding at intermediate steps. Carry rationals or fixed-point all the way through and drop to an integer exactly once, when building the final charge
  • If an intermediate value must be shown, round it for display only and pass the unrounded value into the next step

6. Partial refunds - without the stored allocation it cannot be restored

This is where the thesis of the article becomes sharpest. Everything so far was how to divide. From here it is how to undo a division.

--- 5-1. partial refund with no stored allocation ---
charged : [3334, 3333, 3333]   sum 10000

case A - refund recomputed as total/3 at refund time
  floor     refund each 3333  x3 = 9999    shop ends up +1 KRW off
  half-up   refund each 3333  x3 = 9999    shop ends up +1 KRW off
  ceil      refund each 3334  x3 = 10002   shop ends up -2 KRW off
case B - refund reads the stored per-payer amount
  refunds [3334, 3333, 3333]  sum 10000   shop ends up +0 KRW off

The charge was split correctly as [3334, 3333, 3333]. The refund is the problem.

  • Case A recomputes total / 3 at refund time. Returning 3,333 to all three totals 9,999, so one won stays with the shop. One customer paid 3,334 and gets back 3,333
  • Switching to ceiling is worse. It returns 10,002 and the shop loses two won. That is money going out that never came in, an amount with no accounting explanation
  • Case B reads the stored values and totals exactly 10,000. The difference was not the algorithm but whether anything was stored

A more realistic form appears with a cart-level discount, where what each line actually paid is ambiguous to begin with.

--- 5-2. refunding one line out of a cart-level discount ---
subtotal 11960, 15 percent off, actually charged 10166
line   list price   allocated paid   line x 0.85 rounded
---------------------------------------------------------
A      1990         1692             1692
B      2990         2542             2542
C      5990         5091             5092
D      990          841              842
---------------------------------------------------------
allocated sum 10166   equals charged : True
per-line   sum 10168   equals charged : False

return line A (list 1990) -> refund 1990 / 1692 / 1692  (list / recomputed / stored)
   remaining after each : 8176    8474    8474      should be 8474
return line B (list 2990) -> refund 2990 / 2542 / 2542  (list / recomputed / stored)
   remaining after each : 7176    7624    7624      should be 7624
return line C (list 5990) -> refund 5990 / 5092 / 5091  (list / recomputed / stored)
   remaining after each : 4176    5074    5075      should be 5075
return line D (list 990) -> refund 990 / 842 / 841  (list / recomputed / stored)
   remaining after each : 9176    9324    9325      should be 9325

return ALL FOUR lines one at a time:
  list price   refunded 11960    charged 10166    gap +1794 KRW
  recomputed   refunded 10168    charged 10166    gap +2 KRW
  stored       refunded 10166    charged 10166    gap +0 KRW

Three refund implementations side by side. The last three lines are the conclusion.

  • Refunding at list price returns 11,960 against 10,166 received. 1,794 KRW given away. This is the well-known failure where using a coupon and then returning everything leaves you with more money than you started with
  • Recomputing at refund time sends out 10,168, a two won loss. Far better, but still not balanced, because lines C and D each differ from the stored value by one won
  • Reading the stored allocation gives exactly 10,166. A gap of zero
  • Note that recomputation was correct on most lines. A and B matched the stored values. Only testing every line exposes the drift, which is why partial refund bugs hide for so long
  • The reason is in the last two lines of the table. The per-line recomputed sum is 10,168 while the actual charge was 10,166. Allocation and recomputation produce different values from the start

The thesis. The heart of the problem is not rounding. Division is a lossy operation, and if the result is not stored there is no way to restore it later. An allocation that was not saved has to be recomputed, and recomputation carries no guarantee of matching the original.

So the prescription is not an algorithm but a schema. Persist the per-line allocated amount as a row at charge time. Allocate and store the discount per line as well. Refunds read those rows rather than computing anything.

7. The one won that appears when tax is split out

Deriving the supply amount and the tax from a tax-inclusive price is also a division. Assuming a 10 percent rate, the supply amount is ten elevenths of the inclusive price, so unless the price is a multiple of 11 a fraction always appears.

a tax-inclusive price P holds supply = P x 10/11 at a 10 percent rate

what happens if you round supply AND tax separately, over 1..200000 KRW

Those last four lines are directly usable.

  • Flooring both breaks the sum on 181,819 of 200,000 prices. That is over 90 percent. On every price that is not a multiple of 11, one won disappears
  • Ceiling both breaks the same number of prices, with the sign reversed: one won appears from nowhere
  • Half-up on both did not break at this rate. The two fractional parts always sum to one, so when one goes up the other goes down. But this held only for this particular rate, and it must be rechecked if the rate or the currency changes
  • One rule is safe regardless. Round only one of the two and derive the other by subtraction. The sum then cannot break at any rate, because subtraction does no rounding

7.1 Per-line and whole-order reverse calculations give different values

--- 6-2. per-line VAT vs whole-order VAT ---
line   incl price   supply(line)   tax(line)
----------------------------------------------
A      1990         1809           181
B      2990         2718           272
C      5990         5445           545
D      990          900            90
----------------------------------------------
sum of per-line   supply 10872    tax 1088   total 11960
whole-order       supply 10873    tax 1087   total 11960
difference        supply -1        tax +1

sweep of 729 three-line carts : 239 disagree between per-line and whole-order (32.8 percent)
neither number is wrong. they answer two different questions,
so the invoice has to say which one it printed

The same order has two supply amounts, 10,872 and 10,873. Reversing per line and adding differs from reversing the total once. Of 729 sample carts, 239 (32.8 percent) split.

  • The grand total is 11,960 either way. What differs is only the internal division between supply and tax. So payment reconciliation passes and only the tax records break
  • Which one is right is not for the code to decide. It follows from the document format being issued and what the receiving system expects, so it is a policy to settle and write down
  • Real incidents come from both methods coexisting inside one company. The order system computes per line, the settlement job computes on the total, and every month a few won differ with nobody knowing why
  • The practical criterion is simple. If the customer sees per-line tax, compute and store it per line, and build the total tax by adding those lines. Do it the other way and the displayed total will not agree

Everything so far was integer arithmetic. Holding amounts in a floating point type layers on one more source of error.

Now the picture changes. At 30 percent off alone, 18,724 amounts give different answers. A 45 KRW item at 30 percent off yields 31.499999999999996 in float, which rounds down to 31, while integer arithmetic yields exactly 31.5 and rounds up to 32.

  • The same error appeared identically in both runtimes. It is not a quirk of one language but a property of binary floating point representation itself
  • The dangerous part is that some rates produce zero mismatches. At 0.85 and 0.55 not one of a million amounts was wrong. Change the discount rate and a bug that never existed appears
  • The mismatches cluster on amounts landing exactly on a half. Being right at the rounding boundary, they produce a one won difference and never more, which is precisely why nobody notices
  • What needs fixing is not the rounding function. It is multiplying by a float rate at all. Written as amount * 70 / 100, with integer multiplication first and division second, this error cannot occur

that many KRW is about       : 9007 trillion KRW

7-4 shows the accumulation. Add three shares and you get exactly 10,000. But add a thousand and the value parts from the exact one below the decimal point. Invisible at low volume, it only surfaces in bulk batches.

7-5 is reassurance in the other direction. A won amount itself stays exact as a float up to roughly 9,007 trillion. Ordinary billing amounts are well inside the safe range. In other words, the risk is not holding an amount but dividing one. That is the point of this section.

9. The design rule - collect rounding into one place

Turned into code, everything above is three lines. Work in integers. Round in one function only. Store the result. The function looks like this.

def split_krw(total, weights, policy="largest"):
    """Divide an integer KRW amount over integer weights.

    Rounds in exactly one place. Returns integers whose sum is total.
    """
    if not isinstance(total, int):
        raise TypeError("total must be an int in KRW")
    if not weights or any(w < 0 for w in weights):
        raise ValueError("weights must be non-negative")
    tw = sum(weights)
    if tw == 0:
        raise ValueError("weights sum to zero")
    base = [total * w // tw for w in weights]
    rem = total - sum(base)
    k = len(weights)
    if policy == "largest":
        frac = [(total * w) % tw for w in weights]
        order = sorted(range(k), key=lambda i: (-frac[i], i))
    elif policy == "first":
        order = list(range(k))
    else:
        raise ValueError(policy)
    for i in range(rem):
        base[order[i]] += 1
    assert sum(base) == total, "split_krw broke its own invariant"
    return base

The structure is plain. total * w // tw puts the integer multiply first, so there is no float error. The remainder collects in rem and is handed out one won at a time in the sorted order. The assertion on the last line makes the function check for itself that the sum equals the original.

Whether that assertion actually holds was tested.

The warning at the end of 8-2 matters. A zero allocation is a normal result, not a bug. Split one won eight ways and one payer gets one won while seven get zero. Send that straight through as a payment request and you get a zero-amount charge, which the processor rejects. Read new payment and settlement code in this order.

  • Are amounts handled as integers in whole won? Is a float type surviving anywhere
  • Has the x100 minor-unit habit been carried over to the won? The won has zero decimal places

  • How many rounding functions exist in the codebase? There should be one

# Splitting the Korean Won — Algorithm, Comparison Tables, Assertions

> Source: braindetox.kr — Split 10,000 KRW three ways and you get 9,999
> Verified on: Windows 10 / Python 3.13.3 / Node 22.16.0 (ICU 77.1)
> Currency: KRW. ISO 4217 exponent 0 (no minor unit). All amounts below are in Korean won.

## 1. The rules in one block

- Hold amounts as **integers (whole won)**. The multiply-by-100 minor-unit habit buys nothing here
- **Distribute the remainder** of a division instead of dropping it
- Round in **exactly one function** in the whole codebase
- **Store** the allocation. A refund reads it; it does not recompute it

## 2. The allocation function (sum always equals the total)

```python
def split_krw(total, weights, policy="largest"):
    if not isinstance(total, int):
        raise TypeError("total must be an int in KRW")
    if not weights or any(w < 0 for w in weights):
        raise ValueError("weights must be non-negative")
    tw = sum(weights)
    if tw == 0:
        raise ValueError("weights sum to zero")

    base = [total * w // tw for w in weights]   # integer multiply first, divide second
    rem  = total - sum(base)                     # leftover won, always 0 <= rem < len(weights)
    k    = len(weights)

    if policy == "largest":                      # biggest fractional part first
        frac  = [(total * w) % tw for w in weights]
        order = sorted(range(k), key=lambda i: (-frac[i], i))
    elif policy == "first":
        order = list(range(k))
    elif policy == "rotate":                     # for recurring bills, persist START
        order = [(START + i) % k for i in range(k)]
    else:
        raise ValueError(policy)

    for i in range(rem):
        base[order[i]] += 1

    assert sum(base) == total, "split_krw broke its own invariant"
    return base
```

## 3. Mode comparison (10,000 KRW over 3 payers)

| Mode | Result | Sum | Gap | Verdict |
|---|---|---|---|---|
| floor | 3333 / 3333 / 3333 | 9,999 | **-1** | do not use |
| half-up | 3333 / 3333 / 3333 | 9,999 | **-1** | no guarantee |
| half-even | 3333 / 3333 / 3333 | 9,999 | **-1** | many runtimes default to this |
| ceil | 3334 / 3334 / 3334 | 10,002 | **+2** | customer overpays |
| **allocate first** | 3334 / 3333 / 3333 | **10,000** | **0** | one-off splits |
| **allocate largest** | 3334 / 3333 / 3333 | **10,000** | **0** | weighted splits |
| **allocate rotate** | rotates each cycle | **10,000** | **0** | **recurring bills** |

## 4. Picking a remainder policy

| Policy | Sum guaranteed | Fairness in one run | Bias when repeated | Use for |
|---|---|---|---|---|
| first / last | yes | low | **accumulates** (6 KRW over 6 months) | one-off only |
| largest | yes | **highest** | accumulates on fixed weights | weighted splits |
| rotate | yes | medium | **cancels out** (0 KRW over 6 months) | **subscriptions** |

## 5. Assertions to keep (all must pass)

```python
assert sum(parts) == total                    # sum equals the original amount
assert all(p >= 0 for p in parts)             # no negative share
assert len(parts) == len(weights)             # count preserved
assert max(abs(p * tw - total * w) for ...) < tw   # each share off by under 1 KRW
assert sum(refunds) == charged                # full refund equals what was charged
assert supply + tax == price_incl             # supply plus tax equals the inclusive price
```

Measured: 300,000 random cases all passed. Worst deviation from the exact share was **0.873479 KRW** (under 1).

## 6. Tax split-out rule

- **Round one side and derive the other by subtraction** — the sum then holds for any rate
- Flooring both / ceiling both broke the sum on **181,819** of 200,000 prices
- Per-line reverse calculation and whole-order reverse calculation give **different values** (239 of 729 sample carts, 32.8%)
- Which one to use is a matter of **company policy, contract and a qualified adviser** — decide it and write it down

## 7. Discount rules

- Never round at an intermediate step. Round **once, on the final charge**
- Stack two percentage discounts and the order changes the result — **15,550** of 50,000 prices (31.1%)
- Per-line rounding and cart-level rounding differ — **2 KRW** on the sample cart
- If the receipt prints per-line amounts, compute and **store per line**, then build the total by adding

## 8. Why floats are banned

- `amount * 0.7` (float) and `amount * 7 / 10` (integer) disagree on **18,724 of 1,000,000** amounts
- 45 KRW at 30% off: float gives `31.499999999999996` and rounds to 31; integers give exactly `31.5` and round to 32
- Some rates produce **zero mismatches**, so a handful of test cases will not catch it
- A won amount itself stays exact up to ~9,007 trillion — **the danger is the division and the rate multiply, not the storage**

## 9. Minimum storage schema

- A **paid amount** column on every charge line (post-allocation, not the list price)
- The discount also stored as a **per-line allocated value**
- Tax and supply amounts also **stored**, not recomputed at read time
- If using rotate, persist the **next start index** alongside
- Refund rows **reference** the original charge line and are constrained not to exceed it

## 10. Checklist

- [ ] Are all amounts integers (no float type left anywhere)
- [ ] Is the multiply-by-100 minor-unit pattern being applied to KRW
- [ ] Do rate calculations multiply as integers before dividing
- [ ] Is there exactly **one** rounding function
- [ ] Is it documented whether that function is half-up or half-even
- [ ] Does the allocation function assert its sum
- [ ] Is the allocation written to a table
- [ ] Does the refund path **read** the stored value (not recompute)
- [ ] Is there a full-refund-equals-charge test
- [ ] Was partial refund tested on **every line**, not just one
- [ ] Does reversing the discount order give the same result
- [ ] Is only one of supply and tax rounded
- [ ] Is per-line vs whole-order reverse calculation decided
- [ ] Does the remainder go to the same person every cycle

## 11. Do not

- Try to fix the sum by switching rounding modes — **no mode guarantees it**
- Recompute a division later instead of storing it — **it does not come back the same**
- Refund at list price — the sample cart over-refunded by **1,794 KRW**
- Multiply amounts by a float rate — it fails silently on specific rates only
- Round at every step — the order then changes the result
- Round supply and tax separately — the sum breaks on over 90% of prices
- Test only with amounts that divide evenly — multiples of 3 hide the bug
- Let a 1 KRW gap through — next month nobody can trace where it came from
