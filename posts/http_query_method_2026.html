HTTP QUERY 메소드 — GET·POST의 한계를 넘는 새로운 검색 표준

RFC 10008: 멱등성·요청 본문·캐시 가능성을 모두 갖춘 HTTP 동사가 나온 이유와 실무 도입 과제

2026-06-27 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 왜 지금 새 HTTP 동사가 필요한가

HTTP는 수십 년 동안 GET과 POST 두 가지 동사로 웹의 조회와 변경을 처리해 왔다. 단순한 CRUD API에는 충분했지만, 현대 RESTful API에서 복잡한 검색·필터링 요청을 다룰 때는 둘 다 구조적 한계를 드러낸다. GET은 URL에만 쿼리를 담을 수 있어 조건이 복잡해지면 금방 한계에 부딪히고, POST는 본문을 자유롭게 쓸 수 있지만 읽기 전용 의미를 표현하지 못해 캐시와 인프라가 올바르게 처리하지 못한다.

2026년 6월 기준, RFC 10008이 공식 게시되면서 이 공백을 채우는 HTTP QUERY 메소드가 표준으로 등장했다. 저자는 Julian Reschke, James M. Snell(Cloudflare), Mike Bishop(Akamai) 세 명이다. 이 글은 발표 내용을 옮기는 대신, 왜 이런 메소드가 필요했는지 구조적으로 분석하고, 실무에서 어떻게 써야 하는지, 그리고 도입 앞에 놓인 현실적 장벽이 무엇인지를 직접적 시각으로 정리한다.

1. GET의 구조적 한계 — URL이 쿼리의 감옥이 될 때

RESTful 설계의 기본은 조회 요청에 GET을 쓰는 것이다. 단순한 경우엔 문제가 없다. 그러나 상품 목록에 카테고리·가격 범위·태그 배열·정렬 조건·페이지를 모두 실어야 하는 검색 API를 상상해 보면 URL이 어떻게 변하는지 보인다.

GET /products?category=electronics&price_min=100&price_max=500&tags[]=wireless&tags[]=bluetooth&tags[]=noise-cancelling&sort=price_asc&page=2&per_page=20 HTTP/1.1

이 수준은 아직 감당할 만하다. 그러나 실제 검색 API에는 중첩된 필터 구조, 전문 검색 표현식, 집계 조건이 들어간다. 여기에 여러 문제가 겹친다.

첫째, URL 길이 제한이다. RFC 표준 자체는 URL 길이를 제한하지 않지만, 브라우저(예: Chrome은 약 2MB)와 서버(Apache 기본 8KB, Nginx 기본 8KB)가 각자 제한을 둔다. 복잡한 ElasticSearch 쿼리를 URL에 담으면 이 벽에 부딪히는 것은 시간문제다.

둘째, 비ASCII 인코딩 문제다. 한국어 검색어나 특수문자는 퍼센트 인코딩을 거쳐야 한다. 가독성이 크게 떨어지고, 디버깅 시 원래 쿼리를 알아보기 어렵다.

셋째, 로깅과 프라이버시 위험이다. URL은 웹 서버 액세스 로그, CDN 로그, 브라우저 히스토리에 그대로 남는다. 개인 정보나 민감한 검색 조건이 URL 파라미터로 들어가면 의도치 않게 기록되고 유출될 수 있다.

넷째, 배열과 중첩 구조의 비표준이다. tags[]=a&tags[]=b로 표현하는 배열, 중첩 객체를 URL로 직렬화하는 방식은 라이브러리마다 달라 서버·클라이언트 간 호환이 보장되지 않는다.

2. POST 우회의 함정 — 의미 오염과 캐시 실종

이 문제를 피하기 위해 많은 API가 복잡한 검색 요청에 POST를 쓰는 것을 선택했다. GraphQL의 쿼리 실행이 대표적이고, ElasticSearch의 _search 엔드포인트, OpenSearch API도 복잡한 쿼리에 POST를 사용한다. 요청 본문에 JSON을 자유롭게 담을 수 있으니 현실적인 해법처럼 보인다.

그러나 이 우회에는 보이지 않는 비용이 있다.

첫째, 의미 오염이다. POST는 HTTP 명세에서 "서버 상태를 변경할 수 있는" 동사다. 데이터를 읽기만 하는 검색에 POST를 쓰면, HTTP 레이어에서 이 요청이 읽기 전용인지 쓰기인지 알 수 없다. 미들웨어, 프록시, 인프라 전체가 이 의도를 모른 채 동작한다.

둘째, 캐시 불가다. HTTP 명세상 POST 응답은 기본적으로 캐시 불가다. CDN이나 역방향 프록시가 똑같은 검색 쿼리에 대한 응답을 재사용하지 못한다. 트래픽이 몰리는 인기 검색어라도 매번 서버까지 요청이 도달한다. 이는 순전히 HTTP 의미론의 문제이지, 응답 헤더로 억지로 캐시를 활성화해도 표준 동작이 아니다.

셋째, 자동 재시도 불가다. 네트워크 오류가 발생했을 때 HTTP 클라이언트와 로드 밸런서는 멱등한 요청만 자동으로 재시도한다. POST는 멱등성이 보장되지 않으므로 재시도하면 서버 상태가 달라질 수 있다고 간주된다. 읽기 전용 쿼리라도 안전하게 재시도되지 않는다.

정리하면, POST 우회는 단기 편의를 위해 HTTP 의미론 레이어의 세 가지 보증(안전성, 멱등성, 캐시 가능성)을 모두 포기하는 거래다. 이 대가는 인프라 복잡도, 불필요한 서버 부하, 디버깅 어려움으로 되돌아온다.

3. HTTP QUERY 메소드의 설계 — 세 가지 보증의 통합

RFC 10008이 정의하는 QUERY 메소드의 핵심은 단순하다. 요청 본문을 허용하면서, 동시에 안전(safe)·멱등(idempotent)·캐시 가능(cacheable) 세 속성을 모두 보증한다.

RFC의 정의를 직접 인용하면: "A QUERY requests that the request target process the enclosed content in a safe and idempotent manner and then respond with the result of that processing." — 즉, 동봉된 내용을 안전하고 멱등한 방식으로 처리하고 그 결과로 응답하라는 요청이다.

실제 요청은 다음 형태를 취한다.

QUERY /contacts HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json

{
  "filter": {
    "country": "KR",
    "tags": ["developer", "api"],
    "joined_after": "2025-01-01"
  },
  "sort": { "field": "name", "order": "asc" },
  "limit": 20
}

이것이 POST와 달라 보이지 않는다고 느낄 수 있다. 차이는 HTTP 동사 이름이 아니라, 그 이름이 HTTP 스택 전체에 전달하는 의미 신호에 있다.

3.1 안전성(Safe)

QUERY는 서버 상태를 변경하지 않는다고 명시적으로 선언한다. 미들웨어, 모니터링, API 게이트웨이가 이 요청을 부작용 없는 읽기 전용 작업으로 다룰 수 있다. 사람이 봐도, 인프라가 봐도 "이건 검색"이라는 사실이 명확하다.

3.2 멱등성(Idempotent)

같은 QUERY를 여러 번 실행해도 결과가 달라지지 않는다. 네트워크 오류 발생 시 HTTP 클라이언트와 로드 밸런서가 자동으로 재시도할 수 있다. 복잡한 검색 요청이 네트워크 불안정으로 실패해도 인프라가 알아서 처리한다.

3.3 캐시 가능성(Cacheable)

QUERY 응답은 캐시할 수 있다. 단, 캐시 키에는 URL뿐 아니라 요청 본문과 Content-Type 메타데이터가 포함되어야 한다. 동일한 엔드포인트라도 본문이 다르면 다른 쿼리다. CDN과 역방향 프록시가 본문을 포함해 키를 구성하면, 인기 있는 쿼리에 대한 응답을 재사용할 수 있다. 서버는 Content-Location 헤더로 쿼리 결과에 안정적인 URI를 할당해, 이후 GET 요청으로 캐시된 결과를 가져오는 패턴도 지원한다.

4. Accept-QUERY 헤더 — 쿼리 형식 협상

RFC 10008은 Accept-QUERY라는 새 응답 헤더도 도입한다. 서버가 지원하는 쿼리 형식(Content-Type)을 클라이언트에게 광고하기 위한 헤더다. 예를 들어:

Accept-QUERY: application/json, application/x-www-form-urlencoded

클라이언트는 이 헤더를 보고 서버가 어떤 쿼리 구문을 받아들이는지 파악한 뒤, 그에 맞는 형식으로 QUERY 요청을 보낼 수 있다. 이는 REST API에서 쿼리 형식이 서버마다 제각각이던 문제를 표준화한다. JSON 필터, FIQL(Feed Item Query Language), GraphQL 쿼리 등 다양한 형식을 서버가 명시적으로 선언할 수 있게 된다.

6. 실무 활용 — 어디에 써야 하나

QUERY가 빛을 발하는 시나리오는 명확하다. 복잡한 필터와 쿼리 조건이 있으면서 동시에 응답 캐싱이 중요한 검색 API다.

6.1 잘 맞는 곳

복잡한 REST 검색 API가 1순위다. 상품 검색, 문서 검색, 사용자 목록 필터링처럼 조건이 많고 구조가 복잡한 쿼리에서 QUERY는 URL 길이 걱정 없이 JSON 본문을 쓰면서도 캐시 혜택을 누릴 수 있다. GraphQL도 후보다. 현재 GraphQL은 GET과 POST를 혼용하는 비표준 방식을 쓰는데, 쿼리 실행에 QUERY를 쓰면 의미적으로 더 올바르고 캐시도 가능해진다. ElasticSearch·OpenSearch처럼 복잡한 DSL 쿼리를 본문으로 전송하는 API도 QUERY로 전환하면 인프라 레이어의 캐시와 재시도 혜택을 받는다.

6.2 QUERY를 쓰지 말아야 할 곳

반면 URL로 공유하거나 북마크해야 하는 검색 결과에는 QUERY가 맞지 않는다. 쇼핑몰 상품 목록 URL을 복사해 친구에게 보내는 시나리오처럼, URL 자체가 공유 단위가 되는 경우에는 GET의 URL 파라미터 방식이 여전히 유효하다. 단순한 필터 하나 두 개는 GET으로 충분하다. QUERY는 GET이 진짜 한계에 부딪히는 지점에서 써야 한다.

7. 도입 현황과 현실적 장벽

RFC가 공식화됐다고 해서 내일 당장 쓸 수 있는 것은 아니다. HTTP 스택의 모든 계층이 새 메소드를 이해해야 하고, 그 경로는 길다.

7.1 현재 도입 상황 (2026년 6월 기준)

API 클라이언트 도구 Kreya는 버전 1.20에서 QUERY 지원을 추가했다. RFC 공동 저자가 Cloudflare와 Akamai 소속이라 CDN 계층의 지원은 상대적으로 빠르게 이루어질 전망이다. 그러나 브라우저 fetch() API에서 QUERY를 쓰려면 WHATWG 표준 논의와 브라우저 구현이 뒤따라야 하고, Express·FastAPI·Django·Spring 같은 주요 프레임워크의 라우팅 지원, curl·axios 같은 HTTP 클라이언트 라이브러리 지원도 필요하다. 방화벽과 일부 레거시 프록시는 GET·POST·PUT·DELETE 이외의 메소드를 알 수 없는 것으로 보고 차단할 수 있다.

7.2 장기적 전망

IETF 표준은 도입까지 긴 시간이 걸린다. HTTP/2가 RFC 7540으로 확정된 것이 2015년이지만 전면 도입까지 수 년이 걸린 것처럼, QUERY도 프로덕션 전 스택에서 표준으로 쓰이려면 3~5년을 내다봐야 할 수 있다. 특히 국내 환경에서는 일부 기업 방화벽 정책이 비표준 HTTP 메소드를 차단하는 경우가 있어, 도입 전 인프라 호환성 확인이 필수적이다.

본인이 판단하는 합리적 전략은 이렇다. 지금은 새로운 내부 API나 서비스에서 QUERY를 실험하는 단계다. 클라이언트와 서버를 모두 직접 통제하는 환경에서는 지금도 도입 가능하다. 외부에 열린 API나 퍼블릭 엔드포인트에서의 전면 도입은 클라이언트 라이브러리와 CDN 지원이 성숙한 뒤로 미루는 것이 현실적이다.

8. 인프라 관점 — 캐시 키 설계의 새 과제

QUERY가 가져오는 가장 흥미로운 인프라 과제는 캐시 키다. 기존 HTTP 캐시는 URL을 기준으로 동작했다. QUERY는 본문을 포함한 캐시 키를 요구한다. 이는 CDN과 역방향 프록시 구현에 새로운 요구를 추가한다.

RFC는 구현체가 의미 없는 차이를 정규화할 수 있도록 허용한다. 예를 들어 JSON 본문의 키 순서가 다르지만 의미상 동일한 쿼리는 같은 캐시 항목으로 처리할 수 있다. 이는 캐시 효율을 높이는 동시에, 구현 복잡도가 늘어난다는 것을 의미한다.

서버 측 패턴으로는 Content-Location 헤더를 활용하는 방식이 유용하다. 서버가 QUERY 응답에 안정적인 결과 URI를 부여하면, 이후 요청은 그 URI로 GET을 날려 일반적인 URL 기반 캐시를 활용할 수 있다. 복잡한 쿼리 본문 없이 캐시된 결과를 재사용하는 깔끔한 설계다.

9. 결론 — HTTP 의미론을 제대로 쓴다는 것

HTTP QUERY 메소드가 해결하는 문제는 기술적으로 복잡하지 않다. 오히려 너무 오래 방치된 단순한 설계 불일치다. 복잡한 검색을 GET URL에 욱여넣거나, 읽기 전용 쿼리를 POST로 보내는 타협은 당장 돌아가지만 인프라 전체에 의미 오염을 퍼뜨린다. QUERY는 그 타협을 없앤다.

물론 RFC가 나왔다는 것이 곧 "지금 쓰면 된다"는 뜻은 아니다. 스택 전체의 지원을 기다려야 하고, 캐시 키 설계라는 새 과제도 받아들여야 한다. 그러나 방향은 명확하다. 복잡한 검색 API에서 HTTP 의미론을 제대로 표현하는 표준이 생긴 것이고, 그 신호는 이미 클라이언트 도구와 CDN 공급자로 전달되고 있다.

오늘 당장 할 수 있는 것은 두 가지다. 첫째, 지금 POST 우회로 운영하는 읽기 전용 검색 API를 목록으로 만들어 QUERY 전환 후보를 파악하라. 둘째, 내부 API 신규 개발 시 라우팅에 QUERY를 포함해 지금부터 익숙해져라. 전면 도입은 생태계가 성숙하면 자연스럽게 따라온다.
