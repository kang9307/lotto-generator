コミットメッセージはまだ人が書く

いつ誰がコミットメッセージを読むのか、差分に残らない情報とは何か、そして自動生成に任せてよい範囲はどこまでか

2026年8月20日 開発・インフラ

はじめに: エディタが開いてからの3秒

変更は終わりました。git commit と打つとエディタが開き、カーソルが一行目で点滅します。この3秒を、最近は道具が代わりに埋めてくれます。ステージされた変更を読んで一行を提案し、その提案はたいてい間違っていません。ファイル名も合っているし動詞も妥当です。それでも、その提案を消して一から書き直す人がいます。

こだわりや好みの問題に見えます。実際は違います。コミットメッセージは変更内容の要約ではなく、変更内容に残らない情報をつかまえておく場所であり、この二つは性質がまったく異なります。要約は機械のほうが速く、しかも一貫しています。一方で残らなかった情報は、どのモデルにも作り出せません。存在しないものを復元する作業だからです。

この記事は自動生成に反対するものではありません。むしろどのコミットを機械に任せ、どのコミットに人が手を入れるかの線を引くための整理です。コミットメッセージがいつ誰に読まれるのか、公開された慣例がどこまで合意しているのか、チーム規則にするとどこで壊れるのかを順に見ていきます。

1. 元記事の主張 - 手で書く六つの理由

この話題が再燃したきっかけは、2026年8月17日に公開された個人ブログの記事です。題は「Why I still hand-write my commit messages」で、GeekNewsでも紹介され長い議論が付きました。著者が挙げた理由はおおむね六つに整理できます。

  • なぜを残すため - 何を変えたかは変更内容にすでにあり、重要なのはその選択をした理由と文脈である
  • 自分で検証するため - メッセージを書く過程で、その変更を本当に理解しているかが露わになる
  • 所有権を保つため - 補助的な道具で作ったコードでも、成果物への責任はコミットした人にある
  • 道具を使った範囲を残すため - コミットを小さく分ければ、どこで道具を使ったかが履歴にそのまま表れる
  • 文章の質感を守るため - 著者は自分の文体を道具が模倣する状況そのものを望まないと述べています。原文の表現では I do not actually want an AI to be able to write like I do です
  • 記録する習慣の延長として - ブログを書くのと同じように、コミットも自分の記録の一部と捉えている

議論で出た反論も明確でした。第一に、必要になったときにモデルが変更内容から理由を再推論すればよいので前もって書く必要はない、というもの。第二に、チーム全員にこの作法を義務づけるのは現実的に不可能だ、というもの。第三に、設計上の折衷点はコミットよりコードコメントに置くべきだ、というものです。いずれも根拠があり、後段で一つずつ扱います。

2. コミットメッセージはいつ、誰が読むのか

コミットメッセージの価値は書く瞬間には決まりません。数か月後に誰かがその行にたどり着いたときに決まります。そしてその誰かはたいてい著者ではなく、たいてい急いでいます。Linuxカーネルの文書はこの状況を正確に指しています。説明本文は恒久的な変更履歴に入るので、細部をとうに忘れた有能な読者にも意味が通らなければならない、というのです。読者は未来の他人であり、その他人には半年後の自分も含まれます。

具体的にメッセージが開かれる場面は次のとおりです。

読む場面読む人探しているもの到達経路
コードレビューレビュアーこの変更の意図と範囲PRのコミット一覧
深夜の障害調査当番のエンジニアこの行がなぜこうなっているかgit blame
消えたコードの追跡バグ担当者この処理はいつ無くなったかgit log -S
デグレ区間の絞り込みバグ担当者どのコミットから壊れたかgit bisect
リファクタリング着手次の担当者ここに触ってよいのかblameのあと本文を開く
リリースノート作成PM・リリース担当今回何が出るのかタグ区間の git log
参画した最初の週新メンバーこの構造がなぜこうなのかgit log -L

表で注目すべきは道具ではなく道具が止まる地点です。二分探索は問題を作ったコミットを一つ正確に指してくれます。そこまでが道具の仕事です。そのコミットの件名が fix: ロジック修正 の一行だけなら、担当者はまたコードを最初から読むことになります。逆に本文にその日の判断と制約が書いてあれば、この往復は消えます。履歴コマンドそのものの使い方はGit履歴コマンドの実務ガイドで別に扱いました。ここで言いたいのは、それらのコマンドが到着する先の品質です。

もう一点。これらの場面はリポジトリがある場所ならどこでも成立します。課題管理システムが応答しなくても、社内wikiが移設されてリンクが切れていても、複製したノートパソコンさえあればコミットメッセージはそのまま読めます。文脈をコードと同じ場所に置くことの実用的な利点です。

3. 差分が語ることと語らないこと

この記事の核心はここです。変更内容は何を変えたかについては完全で正確な記録です。人がそれを文章で要約すると、むしろ欠落が生まれます。五つのファイルを直したのに本文には三つしか書かれない、という具合です。ですから「何を変えたかを書き直すこと」は、そもそもコミットメッセージの任務ではありません。

変更内容から読み取れることコミットメッセージにしか残らないこと
どのファイルのどの行が変わったかなぜ今この変更をしたのか
追加・削除された関数と署名どの別案を検討して捨てたのか
依存関係のバージョンがどう上がったかなぜそのバージョンで止めたのか
テストが一緒に入ったかどの条件で再現したのか
設定値が何に変わったかその値を決めた根拠の数値は何か
コードが最終的にどんな形かあえて触らなかった隣接コードは何か

右の列にある情報の共通点はリポジトリの外から来たものだということです。障害報告の再現条件、問い合わせで判明した利用パターン、ベンダーが回答した制約、ベンチマークで出た数値、会議で決めた優先順位。これらはコードのどこにもありません。コミットメッセージは、リポジトリの中でその外側の文脈をつかまえられるほとんど唯一の場所です。

ここで三つ目の反論が登場します。そうした折衷点はコードコメントに書くべきではないか、というものです。半分は正しい。区分の基準は単純です。次の人がそのコードを読むたびに必要になる制約ならコメントです。ある定数をその値に固定しなければならない理由、この順序を入れ替えてはいけない理由は、コードのそばに付いているべきです。この変更をたどるときだけ必要な情報ならコミットです。今回何を捨てたか、なぜ範囲を狭めたかは、コードのそばに置けば次のリファクタリングで一緒に消えます。コミットは消えません。

4. やらなかったことと捨てたこと - 記録がなければ再び試される

変更内容が構造的に含められない種類がもう一つあります。やらなかったことです。存在しないコードはどんな道具でも読み取れません。ところが実務で値打ちのある情報は、しばしばここにあります。

  • 検討して捨てた別案 - ライブラリAを先に試し、なぜBに替えたのか
  • あえて触らなかった隣接コード - 一緒に直したかったが今回のリリース範囲外で残したもの
  • 暫定対応であるという事実 - そして何が解決すればこの処理を外せるのか
  • 数値の測定条件 - どのデータ量、どのハードウェアでその数字が出たのか
  • 外部の根拠の所在 - 参照したバグ報告の番号、ベンダーの回答、仕様書の節番号

これらが抜けると何が起きるかは予測可能です。半年後に別の人が同じ場所で同じ別案を試します。同じ落とし穴を踏み、同じ結論に至ります。その時間はまるごと無駄で、無駄の原因はそのとき二文を書かなかったことです。暫定対応に解除条件が書かれていなければ、暫定対応は恒久コードになります。ここまでが自動生成の上限です。モデルは最終状態を見て要約します。捨てたものは最終状態にありません。

5. 自動生成が実際に得意なこと

とはいえ、すべてのコミットに人が張り付くべきだという話ではありません。リポジトリを開けばコミットの相当数は理由が自明です。誤字修正、自動整形の適用、依存関係の定期更新、生成コードの再生成、ファイルの大量移動。こうしたコミットに「なぜ」を求めると fix: 誤字修正 - 誤字があったため のような文が量産されます。規則が雑音を生む典型です。

  • 機械的な要約 - 数十のファイルが同じ形で変わったコミットを一行に正確に圧縮する
  • 形式の統一 - 件名の長さ、語調、接頭辞をチーム規則どおりに毎回そろえる
  • 言語の壁を下げる - 英語が母語でないチームでも、読みやすい件名を負担なく作れる
  • 抜けの回収 - 人が忘れがちな五つのうちの一つを落とさない
  • 下書きの提供 - 空白の画面ではなく直す対象を与え、書き始める障壁を下げる

実務では最後の項目が最も役に立ちます。人がコミットメッセージを雑に書くのは、たいてい怠慢だからではなく空白の画面が重いからです。要約の下書きが先にあり、その下に理由を足す形なら、手で書く分量は二、三文に減ります。ですから実務の規則は「すべて手で」ではなく「理由が自明でないコミットにだけ人が手を入れる」であるべきです。

6. 自動生成が埋められない場所

議論の一つ目の反論、つまり必要なときにモデルが変更内容から理由を再推論すればよいという主張を正面から見ます。この主張の問題は推論と復元を同じものとして扱っている点にあります。モデルはコードを見てもっともらしい理由を作り出します。それはその日に実際にあった理由ではありません。多くの場合その二つは近く、だから問題が表に出ません。問題は二つが食い違う少数の場合に起きます。

そしてその少数の場合こそ、人がコミットメッセージを探しに行く状況です。コードだけで分かる変更は、そもそも誰も履歴をさかのぼりません。深夜にblameを開いたということは、すでにコードが説明してくれなかったということです。その場でのもっともらしい誤答は、情報が何もないより悪い。調査を誤った方向に押し進めるからです。

  • 捨てた別案 - 最終コードに痕跡がなく、推論の材料そのものがない
  • 外部の事実 - ベンダーの回答や障害チケットの内容はリポジトリのどこにもない
  • 優先順位の判断 - なぜ今なのか、なぜこの範囲までなのかは組織の事情である
  • 測定条件 - 数値はコードに残るが、どの環境で測ったかは残らない
  • 確信の度合い - 確実に分かっている修正か推測に頼った修正かは著者しか知らない

最後の項目は実務でとりわけ値打ちがあります。「原因を確定できず症状だけを止めた」という一文は、次の人の調査時間を日単位で削ります。そしてこの一文は道具には作れません。著者がどれだけ確信していたかを知る手立てがないからです。

副次的な効果もあります。メッセージを書こうとしてもどうしても一文にまとまらないなら、そのコミットはたいてい大きすぎるか目的が混ざっています。このとき必要なのは長い文ではなくコミットを分けることです。Gitの公式文書も、複数の課題の変更を一つのコミットにまとめず部分ステージング(git add --patch)で分けるよう勧めています。メッセージを書く行為が、コミットの形を点検する関門になるわけです。

7. よいコミットメッセージの構造 - 件名・本文・トレーラー・取り消し

形については、公開された慣例がすでにかなりの部分で合意しています。ただし細かい数字はプロジェクトごとに違います。その違いが何を意味するかが重要です。

要素慣例根拠となる文書
件名の長さ50文字以内の一行要約を推奨Git git-commit 文書
件名の長さ(カーネル)70から75文字以内、何をとなぜを両方Linuxカーネルの寄稿文書
件名と本文の区切り最初の空行までが件名として扱われるGit git-commit 文書
本文の幅72文字前後で折り返すPro Git 寄稿ガイド
語調命令形の現在形(Fix bug であって Fixed bug ではない)Pro Gitとカーネル文書に共通
バグ参照Fixes: のあとにSHAの先頭12文字以上と一行要約Linuxカーネルの寄稿文書
署名・共同著者本文の後に空行、次に Signed-off-by や Co-authored-byカーネル文書・GitHub文書
取り消し自動生成の文言の後に取り消す理由を自分で書くGit git-revert 文書

件名の長さで50文字と70から75文字が割れていることについて、どちらが正しいか争う必要はありません。二つの文書が実際に求めているものは同じです。一覧画面で一行として読まれたときに趣旨が伝わること。カーネル文書が少し長い長さを許す理由も明快です。要約の一行に、何を変えるのかとなぜ変えるのかを両方入れるよう求めているからです。

命令形の語調は好みのように見えて機能的な理由があります。Gitが自動で作るメッセージ、たとえばマージや取り消しのコミットはすべて命令形なので、語調をそろえると履歴が一つの文書のように読めます。Pro Gitはこれを Fix bug であって Fixed bug ではないと明言しています。

取り消しコミットは特におろそかになりやすい場所です。git revert はどのコミットを取り消したかを本文に自動で書き、端末から実行するとエディタが既定で開きます。ところがその自動文言は何をしか語りません。Gitの文書は、元のコミットをなぜ取り消すのかを説明することを強く推奨すると明記しています。取り消しをさらに取り消すことが重なると件名が Reapply "Reapply "..."" のように膨らむ、という警告まで文書に入っています。理由の一行がなければ、数か月後にその機能を戻そうとする人はなぜ外れたのか分かりません。

規約についても少し触れます。Conventional Commits は type[scope]: description の形で書き、破壊的変更を ! か専用のフッターで示す規格で、目的はchangelogの自動生成とセマンティックバージョンの自動判定です。つまり規約の値打ちは自動化パイプラインが実際にコミットを読み取るときに回収されます。この軸は毛色の違う議論なのでConventional Commitsへの批判で別に扱いました。ただしこの記事の論旨と重なる点が一つあります。接頭辞を正確に付けたという事実は、本文に理由があることをまったく意味しません。

8. AIが書いたコードをコミットするとき - 表記と責任

元記事の著者が最も力を込めた部分がこれです。補助的な道具で作ったコードでも所有権と責任はコミットした人にあり、コミットを小さく分ければどこで道具を使ったかが履歴にそのまま表れる、というものです。

表記の手段はすでに整っています。コミットメッセージのトレーラーがそれです。GitHubの文書は、本文の後に空行を一つ置き Co-authored-by: name <name@example.com> の形の行を著者の数だけ追加するよう案内しています。Git側では git commit --trailer で同じ形の項目を付けられます。形式が一定なので、後から機械的に集計することも可能です。

  • コミットを小さく分ける - 道具を使った範囲と自分で書いた範囲を一つのコミットに混ぜない
  • 道具の名前を書く - 数か月後に特定の道具に特有の癖をたどるとき、これが手がかりになる
  • 検証方法を書く - 何で確認したかのほうが表記そのものより重要である
  • 表記を免責に使わない - トレーラーが付いてもレビューと責任は人に残る
  • チームで形式を先に決める - 人ごとに表記が違えば集計も検索もできない

実務でこの表記が値打ちを出す場面は二つです。一つは品質の振り返りです。特定の時期に特定の道具で作ったコードで同じ欠陥が繰り返されるなら、その傾向は表記があってはじめて見えます。もう一つはレビューの配分で、生成の比率が高い変更はレビューの強度を変えるチームが増えています。レビュー自体を手順にする方法はコードレビューは自然には上達しないで扱いました。

9. チーム規則にするとき - フック・テンプレート・レビュー観点

議論の二つ目の反論、つまりチームに強制できないという指摘はおおむね正しい。ただし強制の対象を取り違えて失敗する場合が多いのです。形式から検査すると、形式は通るのに中身が空のメッセージが増えます。fix: バグ修正 はどの規格検査器も通しますが、情報量はゼロです。

順序を逆にするほうがよい。まず書きやすくし、機械には確実に判定できるものだけを止めさせます。

  • コミットテンプレート - commit.template 設定や -t でエディタの初期内容を指定する。項目名ではなく問いを入れるほうがよい。たとえば「なぜ今必要か」「何を検討して捨てたか」
  • エディタに差分を出す - git commit -v はメッセージの下に変更内容を一緒に表示する。二回指定するとステージされていない変更まで見える。文書の表現どおり、何を変えたかを思い出させて説明を助ける仕掛けだ
  • prepare-commit-msg フック - 既定のメッセージが準備された直後、エディタが開く前に実行される。メッセージファイルをその場で書き換えるのが目的なので --no-verify でも抑制されない。ブランチ名から課題番号を自動で入れる用途に向く
  • commit-msg フック - 書き終わったメッセージファイル一つを引数に受け取り、検査したり標準形式に正規化したりする。ゼロ以外の終了コードを返すとコミットが中断され、--no-verify で回避できる
  • レビュー観点 - 形式ではなく中身を見る。次の五つで足りる

レビューでコミットメッセージを見るとき、実際に問うべきことは次のとおりです。

  • 件名だけ読んでこの変更が何か推測できるか
  • 本文がなぜを語っているか、それとも何をを言い直しているか
  • 捨てた別案や残した範囲があったなら書かれているか
  • 暫定対応なら解除条件があるか
  • 課題・チケットへの参照が付いているか

フックで止めるべきは最後の項目のように機械が確実に判定できるものだけです。本文に理由があるかを機械に判定させようとすると誤検知が積み上がり、誤検知が積み上がればチームは習慣的に --no-verify を付け始めます。その瞬間、フックは消えたのと同じです。

10. 言語の選択 - 母語か英語か

英語圏の外にあるチームがつねに突き当たる問いで、日本や韓国のチームはその典型です。基準は好みではなくこのリポジトリを読む人の範囲です。

  • 社内専用で構成員全員が同じ母語 - 本文を母語で書くほうが一文あたりの情報密度が高い。訳しづらさで正確さを落とすより素直に書くほうがよい
  • 公開する可能性がある - 最初から英語で行く。あとから履歴全体を翻訳するのは事実上不可能だ
  • 外国籍の参画や外注への引き継ぎが見込まれる - 英語。履歴は人より長く残る
  • 折衷型 - 件名は英語の命令形、本文は母語。リリースノートの自動化と道具の互換性を保ちながら説明の精度を得る方式だ
  • どちらであれ一貫性が最優先 - 混ざると git log --grep が半分しか拾わない。文字列検索なので両方の言語を試す必要が出る

折衷型を使うときの注意が一つあります。課題管理システムが認識するキーワードやトレーラー名は、言語に関係なく決められた英語の形をそのまま守る必要があります。Co-authored-by を母語に訳して書くと道具が認識しません。人が読む文だけ母語で書き、機械が読む行は規格どおりに置くのが安全です。

ちなみに最近は、自然言語で書いた仕様そのものをリポジトリにコミットする流れも出ています。その場合コミットメッセージの役割はむしろ大きくなります。仕様が変わった理由を書く場所が必要になるからです。この流れはコードの代わりに韓国語の仕様書をコミットするで別に整理しました。

確認できなかったこと

  • 自動生成のコミットメッセージの品質を人が書いたものと比較した公開ベンチマークや学術研究は、今回は確認できませんでした。この記事の比較は情報の性質、つまり最終状態に残らない情報は復元できないという点に基づいています
  • 開発組織がコミットメッセージをどの言語で書いているかの統計は見つかりませんでした。上の言語選択の基準は統計ではなく判断の枠組みです
  • コミット本文の有無が障害復旧時間に与える影響を測定した資料は確認できませんでした
  • 元記事の著者のチーム規模や使用している道具の構成は原文に書かれていません

おわりに: メッセージはコードより長く残る

コードは消えます。今日書いた関数は次のリファクタリングで名前が変わり、その次の改修で丸ごと無くなります。ところがその関数をそう作った理由を書いておいたコミットは残ります。リポジトリを移しても、wikiが廃止されても、課題管理システムを入れ替えても残ります。コミットメッセージがプロジェクトで最も長生きする文書である理由です。

ですから結論は自動生成を使うかどうかではありません。下書きは道具に任せ、道具に分からないものだけ人が足すことです。実行に移すと三つになります。第一に、件名は一覧で一行として読めるように書き、道具が作った要約をそのまま使ってもかまいません。第二に、理由が自明でないコミットには本文を二、三文かならず付け、そこに捨てた別案と残した範囲を書きます。第三に、取り消すコミットには取り消す理由を書きます。この三つだけでも、半年後の深夜にblameを開く人が出会う画面は変わります。

エディタが開いたあの3秒は、結局のところ自分自身に問う時間です。私はこの変更を説明できるか。説明できないなら、問題は文ではなくコミットのほうです。

よくある質問

Q1: コミットメッセージをAIに生成させてもよいですか

A: 理由が自明なコミットなら自動生成で十分です。依存関係の更新、自動整形、誤字修正のように変更そのものが説明になっている場合がこれにあたります。一方で別案を捨てた、暫定対応を入れた、性能の実測値を根拠に判断したコミットは人が本文を書く必要があります。その情報は最終状態に残っておらず、変更内容だけからは復元できません。

Q2: コミットメッセージの件名は何文字で書くべきですか

A: Gitの公式文書は50文字以内の一行要約と空行、その後に詳しい説明を勧めています。Linuxカーネルの文書は70から75文字以内とし、何をとなぜを両方含めるよう求めています。数字が違うこと自体が要点です。絶対的な基準があるのではなく、一覧で一行だけ読まれたときに趣旨が伝わることが求められています。

Q3: 設計上の理由はコミットメッセージとコードコメントのどちらに書きますか

A: 次の人がそのコードを読むたびに必要になる制約ならコメントです。ある定数をその値に固定する理由がそれです。この変更をたどるときだけ必要な情報ならコミットです。捨てた別案、範囲を狭めた理由、暫定対応の解除条件がここに入ります。コメントは次のリファクタリングで消えることがありますが、コミットは残ります。

Q4: AIが書いたコードをコミットするとき表記は必要ですか

A: 表記はトレーラーで簡単に解決します。本文の後に空行を置いて Co-authored-by の行を足すか、git commit --trailer で付けます。ただし表記は責任を移す仕組みではありません。どこで道具を使ったかをたどれるようにする記録にすぎず、検証と責任はコミットした人に残ります。表記するならコミットを小さく分けて範囲が分かるようにするほうが有効です。

Q5: チームにコミットメッセージの規則をどう導入しますか

A: 形式チェックから始めるとたいてい失敗します。形式は通るのに中身が空のメッセージが増えるからです。まずコミットテンプレートに問いを入れ、コミットエディタに差分を一緒に表示する設定を既定にするほうが効きます。フックで止めるのは課題番号の欠落のように機械が確実に判定できる項目に限り、本文の質はコードレビューで扱うのが現実的です。
