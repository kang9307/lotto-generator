무료 API가 일부러 틀린 데이터를 준다면 - Windy 서핑 예보 사례와 API 신뢰

Windy API 무료 티어의 공식 랜덤 데이터 정책에서 시작된, 프리미엄 유도형 데이터 저하와 API 신뢰 검증에 대한 개발자 관점의 분석

2026-07-03 개발/인프라

서론: 무료 API를 믿고 코드를 짜도 될까

2026년 7월 기준, 서핑 예보를 다루는 한 개발자의 비교 글이 개발자 커뮤니티에서 조용히 회자되고 있다. 여러 무료 서핑·기상 예보 API를 나란히 붙여 테스트하다가, Windy의 API Trial(체험) 키가 실제 관측·모델 데이터가 아니라 무작위로 생성된 값을 반환한다는 사실을 다시 확인한 것이다. 놀라운 지점은 이것이 몰래 숨겨둔 함정이 아니라, Windy가 자사 공식 커뮤니티 포럼에서 스스로 인정한 입장이라는 데 있다.

이 글은 이 한 가지 사례를 출발점 삼아 세 가지를 짚는다. 무료 API 티어가 일부러 데이터 품질을 낮추는 관행이 업계 전반에서 얼마나 흔한지, 이를 모르고 API에 의존하는 개발자가 어떤 위험에 노출되는지, 그리고 새로운 API를 도입하기 전에 실제로 무엇을 확인해야 하는지다. 특정 서비스를 비난하려는 글이 아니라, 이 사례가 드러낸 구조적 문제를 정리하려는 글이다.

1. 무엇이 발견됐나 - Windy Trial API의 "무작위 데이터" 공식 인정

1.1 발견의 경위

계기는 단순하다. 여러 무료 서핑 예보 API를 실제로 테스트해 비교하던 중, Windy Point Forecast API의 무료 Trial 키로 받은 응답 값이 시간이 지나도 물리적으로 말이 되지 않는 패턴을 보였다. 이를 Windy 공식 커뮤니티에서 확인해 보니, Windy 스태프가 관련 질문에 이미 "it generates random data"(Windy 커뮤니티, 스태프 Suty)라고 답한 이력이 있었다. 즉 버그가 아니라 설계된 동작이었다.

1.2 Trial과 Professional, 정확히 뭐가 다른가

Windy API는 Trial과 Professional(유료) 두 축으로 나뉜다. Trial 키는 하루 요청 수가 제한돼 있을 뿐 아니라, 스태프 표현을 빌리면 "테스팅 목적"으로만 존재하며 무작위 데이터를 반환한다. 반면 Professional 플랜은 ECMWF·GFS 등 실제 기상 모델의 관측·예측 값을 그대로 제공한다. 흔히 생각하는 "무료는 요청 횟수만 적을 뿐 값 자체는 진짜"라는 가정이 이 사례에서는 통하지 않는다.

2. 이건 흔한 "무료 제한"과 다르다 - 조용한 실패라는 것

2.1 레이트리밋 vs 데이터 왜곡

레이트리밋(rate limit)이나 해상도 축소는 개발자가 즉시 체감할 수 있는 제한이다. 429 에러를 받거나 격자 간격이 성긴 데이터를 받으면 "여기까지가 무료구나"라고 바로 알아챈다. 그런데 무작위로 뒤섞인 값을 반환하는 것은 다르다. 응답은 200 OK로 정상 도착하고, 값은 숫자로서 그럴듯한 범위 안에 있다. 실패가 아니라 조용한 오답이 오는 셈이다.

2.2 테스트를 통과하는 가짜 데이터의 위험

개발자가 연동 테스트를 할 때는 대체로 "요청이 성공적으로 오는가", "응답 스키마가 맞는가"를 확인한다. 값 자체가 실제 관측치와 일치하는지 하나하나 대조하는 경우는 드물다. 그 결과 Trial 키로 만든 프로토타입은 정상 동작하는 것처럼 보이지만, 그 안의 숫자는 처음부터 의미가 없었을 수 있다. 개인 프로젝트가 그대로 프로덕션으로 넘어가거나, 테스트 코드에 무료 키가 남아 있다면 문제는 배포 이후에야 발견된다.

3. 프리미엄 유도를 위한 데이터 저하 - 업계 전반의 패턴

3.1 무료 티어를 나쁘게 만드는 세 가지 방법

무료 티어를 의도적으로 덜 매력적으로 만드는 방법은 크게 세 가지다. 첫째는 사용량 상한(요청 수, 호출 빈도)이다. 둘째는 기능 잠금(특정 엔드포인트·필터·배치 처리 비활성화)이다. 셋째는 데이터 품질 자체의 저하(해상도 축소, 지연 제공, 그리고 Windy처럼 값 자체를 대체)다. 앞의 두 가지는 업계에서 널리 받아들여지는 정상적인 프리미엄 전략이다. 세 번째, 특히 값을 아예 다른 값으로 바꿔치기하는 방식은 훨씬 드물고 논쟁적이다.

3.2 워터마킹·지연·해상도 저하 - 유사 업종 사례

비슷한 관행은 다른 업종에서도 찾을 수 있다. 금융 데이터 API는 무료 티어에서 실시간 대신 15~20분 지연 시세를 주는 경우가 흔하다. 지도·이미지 API는 무료 요청에 워터마크를 찍거나 저해상도 타일만 제공한다. 이런 사례는 대체로 "지연됐다", "해상도가 낮다"처럼 사용자가 즉시 알아챌 수 있는 형태로 저하된다. Windy 방식이 이례적인 이유는 저하가 아니라 대체이기 때문이다. 값이 늦거나 흐릿한 게 아니라, 애초에 실제 관측과 무관한 숫자가 온다.

4. 진짜 문제는 투명성의 '위치'다

4.1 Windy는 실제로 숨기지 않았다

여기서 Windy를 비난하려는 것은 아니다. Windy는 이 정책을 숨기지 않았다. 스태프가 커뮤니티 질문에 명확히 답했고, Trial이 "테스팅 목적"이라는 점도 여러 차례 언급됐다. 사업적으로도 합리적이다. 실사용 가능한 정확한 데이터를 무료로 무제한 풀면 유료 Professional 플랜을 살 이유가 사라진다.

4.2 "문서에 있다"와 "개발자가 실제로 본다"의 간극

문제는 공개의 위치다. 이 정보는 API 메인 문서의 눈에 띄는 자리가 아니라, 커뮤니티 포럼의 답변 스레드에 묻혀 있었다. 처음 API를 연동하는 개발자가 응답 헤더나 필드 설명, 혹은 최소한 요청 URL 근처에서 "이 응답은 테스트용 무작위 데이터입니다"라는 문구를 직접 마주치기는 어렵다. 기술적으로는 공개됐지만, 실제로 그 정보에 닿는 사람은 이미 문제를 겪고 검색해 본 소수에 그친다. 공개했다는 사실과 발견 가능했다는 사실은 다르다.

5. 개발자가 무료 API에 의존할 때 생기는 위험

5.1 프로토타입에서 프로덕션으로 넘어가는 순간

가장 흔한 실패 경로는 이렇다. 사이드 프로젝트나 MVP를 Trial 키로 빠르게 만들고, 반응이 괜찮으면 그대로 사용자에게 노출한다. 이 단계에서 유료 전환을 검토하지 않으면, 서비스는 겉보기엔 동작하지만 안에 있는 숫자는 신뢰할 수 없는 상태로 굳어진다. 특히 서핑·기상처럼 사용자가 그 값을 믿고 실제 행동을 결정하는 도메인에서는, 조용한 오답이 실질적인 피해로 이어질 수 있다.

5.2 사이드 프로젝트·개인 도구도 예외는 아니다

개인 도구나 사내 대시보드도 예외가 아니다. "어차피 나만 보는 거니까"라는 생각으로 무료 키를 계속 쓰다가, 그 도구의 판단을 근거로 실제 의사결정을 내리기 시작하면 같은 위험이 반복된다. 무료 API를 프로토타입 이상으로 쓸 계획이라면, 애초에 그 데이터가 진짜인지부터 확인하는 습관이 필요하다.

6. API 신뢰성을 검증하는 현실적인 방법

6.1 교차확인 - 권위 있는 소스와 최소 1회 대조

가장 확실한 방법은 교차확인이다. 같은 시각·같은 좌표의 값을 신뢰할 수 있는 다른 소스, 이를테면 정부 기상청이나 NOAA 부이 관측소처럼 원자료를 공개하는 기관의 데이터와 최소 한 번은 직접 대조한다. 상관관계가 없다면 그 API는 프로덕션에 쓸 수 없다고 봐야 한다.

6.2 포럼·이슈트래커까지 검색하라

공식 문서만 보지 말고 지원 포럼·GitHub 이슈·커뮤니티 게시판까지 검색하라. "trial", "sample", "demo", "random", "test data" 같은 키워드로 해당 API 이름과 함께 검색해 보면, 이번 Windy 사례처럼 벤더가 이미 어딘가에서 조용히 인정한 제약이 나오는 경우가 많다. 이런 정보는 공식 랜딩 페이지보다 지원 스레드에 먼저 등장하는 경향이 있다.

6.3 정량적 제한과 정성적 표현을 구분하라

가격 페이지의 표현이 정량적인지 정성적인지 구분해서 읽어라. "월 1,000회", "분당 10회"처럼 숫자로 명시된 제한은 예측 가능하고 검증하기 쉽다. 반면 "테스트 목적", "샘플 데이터", "제한된 정확도"처럼 정성적으로만 표현된 조항은 실제로 무엇을 의미하는지 코드로 확인하기 전까지 알 수 없다. 정성적 표현이 등장하면 그 즉시 실제 응답 값을 검증 대상으로 삼아야 한다.

7. 대안 API를 고를 때 보는 기준

7.1 Open-Meteo 사례 - 라이선스와 모델 출처가 명시된 공급자

이번 사례에서 대안으로 자주 언급되는 것이 Open-Meteo다. API 키 없이 비상업적 용도로 하루 최대 1만 건까지 무료이고, GFS·ECMWF·DWD ICON 등 각국 기상청의 실제 모델을 그대로 제공한다. 데이터는 CC BY 4.0으로 라이선스돼 있고, 서버 코드 자체가 AGPLv3로 공개돼 있어 필요하면 직접 호스팅해 무제한으로 쓸 수도 있다. 무료 티어의 한계가 "숫자로 명시된 호출 한도"이지 "값의 진위"가 아니라는 점이 핵심이다.

7.2 "무엇을 얼마나 주는가"가 명확한 곳을 우선하라

일반화하면 기준은 이렇다. 데이터 출처(어느 모델·어느 관측망을 쓰는지)를 명시하는 공급자를 우선하고, 무료와 유료의 차이가 "무엇을 얼마나"처럼 숫자로 설명되는 곳을 우선하며, 라이선스와 재배포 조건이 분명한 곳을 우선한다. 반대로 무료 티어의 정확도나 데이터 성격에 대해 애매하게만 서술돼 있다면, 실제 값을 직접 검증하기 전까지는 그 API를 신뢰의 기준선으로 삼지 않는 것이 안전하다.

결론: 무료가 공짜라는 뜻은 아니다

Windy의 Trial API가 무작위 데이터를 준다는 사실 자체는 부정한 행위가 아니다. Windy는 이를 부인한 적이 없고, 사업 모델로서도 이해할 수 있는 선택이다. 이 글에서 진짜 짚고 싶었던 것은 다른 데 있다. 프리미엄 사업 모델에서 데이터 품질 저하는 흔한 전략이지만, 그 저하가 조용히, 그리고 문서 깊숙한 곳에서만 이뤄질 때 개발자는 자신도 모르게 가짜 데이터 위에 서비스를 쌓게 된다.

2026년 7월 기준으로 무료 API 생태계는 계속 넓어지고 있고, 그만큼 이런 사례도 늘어날 가능성이 크다. 결론은 단순하다. 무료라는 단어를 검증된 데이터와 동일시하지 말고, 최소 한 번은 권위 있는 소스와 값을 대조한 뒤에 그 API를 신뢰선 위에 올려라.
