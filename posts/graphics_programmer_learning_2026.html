서론: 왜 지금 이 로드맵을 다시 짚어야 하는가

"그래픽스 프로그래머가 되려면 무엇을 배워야 하는가"라는 질문은 오래된 질문이지만, 2026년 현재 다시 물을 가치가 있다. 생성형 AI가 이미지·영상까지 만들어내는 시대에, 굳이 선형대수와 GPU 파이프라인을 밑바닥부터 배워야 하냐는 회의가 나올 법하다. 그런데 역설적으로 실시간 렌더링·게임·XR·시뮬레이션·디지털 트윈처럼 프레임마다 물리적으로 그럴듯한 픽셀을 밀리초 단위로 뽑아내야 하는 영역에서는, 여전히 사람이 파이프라인 내부를 이해하고 있어야 한다.

이 글은 GeekNews에 소개된 그래픽스 학습 로드맵 논의를 계기로, 본인이 관련 자료를 다시 조사하고 정리한 2026년 7월 기준 학습 로드맵이다. 특정 튜토리얼을 그대로 옮기는 대신, 무엇을 먼저 배우고 무엇은 나중으로 미뤄도 되는지 우선순위를 매기는 데 집중했다.

1. 수학이 먼저다 - 선형대수와 삼각함수

그래픽스 학습 로드맵 대부분이 공통으로 강조하는 지점이 있다. 벡터·행렬·내적·외적·좌표 변환 같은 선형대수 기초 없이는 렌더링 코드를 읽을 수조차 없다는 것이다. 모델 행렬, 뷰 행렬, 투영 행렬이 정점을 화면 좌표로 밀어내는 과정 전체가 사실상 행렬 곱셈이기 때문이다. 삼각함수도 마찬가지다. 카메라 회전, 노멀 벡터 계산, 조명 각도가 전부 사인·코사인으로 표현된다. 여기에 더해 미적분 기초(도함수·적분 개념 정도)도 셰이딩 모델이나 물리 기반 애니메이션을 이해하는 데 필요하다는 지적이 반복해서 나온다.

본인이 강조하고 싶은 부분은, 이 수학을 대학 강의처럼 통째로 다 뗀 뒤에 그래픽스를 시작할 필요는 없다는 것이다. 실제로 필요한 것은 벡터 연산과 3×3·4×4 행렬, 그리고 그것이 렌더링에서 어떤 역할을 하는지에 대한 감각이다. 나머지는 코드를 짜면서 필요할 때 채워도 늦지 않는다.

2. 렌더링 파이프라인의 큰 그림 - 소프트웨어 렌더러부터

많은 로드맵이 공통으로 추천하는 첫 실습은, 그래픽스 API를 건드리기 전에 소프트웨어 래스터라이저나 레이트레이서를 직접 짜보는 것이다. Ssloy의 tinyrenderer·tinyraytracer 같은 튜토리얼이 대표적으로 언급된다. GPU도, 드라이버도, API도 없이 순수 CPU 코드로 삼각형을 화면에 찍어보면, 정점 변환·클리핑·래스터화·깊이 테스트로 이어지는 렌더링 파이프라인의 각 단계가 실제로 무엇을 하는 코드인지 몸으로 이해하게 된다.

파이프라인에서 프로그래머가 직접 코드를 짜 넣는 구간은 정점 셰이더·테셀레이션·지오메트리 셰이더·프래그먼트(픽셀) 셰이더, 그리고 별도로 컴퓨트 셰이더다. 나머지 고정 기능 단계(래스터화·깊이 테스트 등)는 GPU가 알아서 처리한다. 이 대응 관계를 소프트웨어 렌더러 단계에서 먼저 익혀두면, 이후 실제 GPU API를 배울 때 학습 속도가 확연히 빨라진다.

3. "두 가지 일을 동시에" - CPU 사이드와 GPU 사이드

2026년 7월 데모폭스(demofox) 블로그에 올라온 실시간 그래픽스 프로그래머 학습 글은 이 분야를 "two jobs in one"이라는 표현으로 요약한다. 하나는 다이렉트X 12·Vulkan·Metal 같은 API와 엔진 프로그래밍(자원 로딩·메모리 관리)을 다루는 CPU 사이드이고, 다른 하나는 조명·셰이딩 수학과 GPU 성능 튜닝을 다루는 GPU 사이드다.

본인이 동의하는 지점은, 이 둘을 동시에 같은 깊이로 파고들면 어느 쪽도 제대로 배우기 어렵다는 것이다. 실용적인 접근은 둘 중 하나를 주력으로 정하고, 나머지 한쪽은 OpenGL·WebGL·기존 엔진 같은 쉬운 도구로 우회하며 익히는 것이다. GPU 사이드(조명·셰이딩)에 집중하고 싶다면 저수준 API 제어는 엔진에 맡기고, 반대로 CPU 사이드(엔진·저수준 API)에 집중하고 싶다면 셰이딩은 단순한 셰이더로 시작하는 식이다.

4. 그래픽스 API 선택 - OpenGL·Vulkan·DirectX·WebGPU

API 선택은 이 주제에서 가장 자주 나오는 질문이다. 본인이 조사한 자료들의 공통된 결론은 "가장 쉬운 것부터, 그다음 저수준으로"다. OpenGL은 상태 기계 방식의 비교적 관대한 API로, 적은 코드로 삼각형 하나를 화면에 띄울 수 있어 입문에 적합하다. 반면 Vulkan과 DirectX 12는 드라이버가 대신해주던 메모리 관리·동기화·커맨드 버퍼 기록을 프로그래머가 명시적으로 제어하는 저수준 API다. 그만큼 코드량이 훨씬 많고 첫 한 프레임을 띄우기까지의 진입장벽이 높지만, 멀티스레드 커맨드 기록과 세밀한 GPU 제어로 성능을 극한까지 뽑아낼 수 있다.

WebGPU는 이 구도에 최근 추가된 변수다. Vulkan·DirectX 12·Metal과 개념적으로 유사하면서도 브라우저에서 바로 돌아가고, 전역 상태가 없어 디버깅이 쉽고 에러 메시지도 더 명확하다는 평가가 많다. 그래서 최근 자료들은 WebGPU를 먼저 익히면 이후 Vulkan으로 넘어가는 다리 역할을 할 수 있다고도 짚는다. 본인의 결론은, 처음 한두 달은 OpenGL이나 WebGPU로 파이프라인 개념을 굳히고, 그다음 실무·채용 요구에 맞춰 Vulkan이나 DirectX 12로 저수준을 공략하는 순서가 시행착오를 가장 줄인다는 것이다.

5. 셰이더 프로그래밍 - GLSL와 HLSL

셰이더 언어는 진영에 따라 갈린다. OpenGL과 웹 계열(WebGL·WebGPU)은 GLSL을, 다이렉트X와 유니티의 기본 렌더 파이프라인은 HLSL을 표준으로 쓴다. 둘 다 C와 비슷한 문법에 벡터·행렬 연산이 1급 시민으로 들어가 있어, 하나를 익히면 다른 하나로 옮기는 데 며칠이면 충분하다는 평가가 일반적이다. 실무 채용 공고 기준으로는 HLSL 언급 빈도가 다소 높게 나타나는데, 이는 다이렉트X·유니티·언리얼 생태계의 규모 때문으로 보인다.

셰이더를 처음 배울 때는 정점 셰이더(정점을 어디로 옮길지)와 프래그먼트 셰이더(픽셀 색을 어떻게 정할지) 두 개만으로 시작하는 것이 정석이다. 여기에 익숙해진 다음에야 테셀레이션·지오메트리·컴퓨트 셰이더로 확장해도 늦지 않다.

6. GPU 아키텍처 이해 - SIMT와 워프

API와 셰이더 문법을 안다고 곧바로 빠른 코드를 짤 수 있는 것은 아니다. GPU가 왜 그렇게 동작하는지, 즉 하드웨어 모델을 이해해야 진짜 성능 튜닝이 가능하다. GPU는 스트리밍 멀티프로세서(SM) 여러 개로 구성되고, 각 SM은 다시 다수의 코어를 묶어 워프(NVIDIA 기준 32개 스레드 단위)로 실행한다. 이 실행 방식은 SIMD와 비슷해 보이지만 정확히는 SIMT(Single Instruction, Multiple Threads)라 불린다.

같은 워프 안의 스레드가 조건문에서 서로 다른 분기를 타면 - 이를 워프 다이버전스라 한다 - 하드웨어는 두 분기를 순차적으로 실행하게 되어 그만큼 느려진다. "왜 내 셰이더의 if문이 예상보다 느린가"라는 질문 대부분의 답이 여기 있다. 이 개념 하나만 제대로 이해해도 셰이더 코드를 훨씬 GPU 친화적으로 짤 수 있게 된다.

7. 레이트레이싱과 PBR - 실시간 포토리얼리즘

피지컬 베이스드 렌더링(PBR)은 이제 게임·영화 업계의 사실상 표준이다. 핵심은 에너지 보존 BRDF와 알베도·노멀·러프니스·메탈릭·AO로 구성된 표준화된 머티리얼 맵 세트로, 어떤 조명 환경에서도 일관된 결과를 낸다는 데 있다. 레이트레이싱은 카메라에서 광선을 쏘아 장면과의 교차를 계산해 픽셀 색을 정하는 기법으로, 원리 자체는 오래됐지만 실시간으로 쓸 만한 속도가 나온 것은 최근이다. NVIDIA RTX 같은 하드웨어가 BVH(경계볼륨계층구조) 구축과 탐색을 가속하고, AI 기반 디노이징으로 광선 수를 줄여도 화면이 지글거리지 않게 만든다.

실무에서는 장면 전체를 순수 레이트레이싱으로 그리기보다, 래스터화로 기본 화면을 그리고 반사·앰비언트 오클루전·부드러운 그림자처럼 시각적 임팩트가 큰 부분만 레이트레이싱으로 보강하는 하이브리드 렌더링이 대세다. 입문 순서로는 무료 공개 자료인 "Ray Tracing in One Weekend" 시리즈로 오프라인 패스트레이서 원리를 손으로 익히고, PBR은 LearnOpenGL의 PBR 섹션에서 시작해 Filament 문서·PBRT 책으로 깊이를 더하는 경로가 자주 추천된다.

8. 게임엔진 vs 로우레벨 - 커리어 갈림길

그래픽스를 배우는 목적이 취업이라면, 언리얼·유니티 같은 완성된 엔진 위에서 셰이더·렌더 기능을 다루는 길과, 엔진 없이 API부터 직접 짜는 로우레벨 길이 갈린다. 유니티는 C# 기반으로 진입장벽이 낮고 모바일·캐주얼·VR/AR 등 채용 시장이 넓다. 언리얼은 C++ 기반으로 진입장벽은 높지만, AAA 스튜디오의 "그래픽스 프로그래머"처럼 특화되고 보수가 높은 직군으로 이어지는 경우가 많다. Casey Muratori의 Handmade Hero처럼 엔진 없이 게임 하나를 밑바닥부터 짜보는 방식은 가장 느리지만 가장 깊이 남는 학습법으로 자주 언급된다.

본인의 판단은 이렇다. 목표로 하는 스튜디오나 팀이 이미 정해져 있다면 그곳에서 쓰는 엔진과 언어부터 맞추는 것이 합리적이고, 아직 방향이 정해지지 않았다면 로우레벨 기초를 먼저 다져 두는 쪽이 이후 어느 엔진으로 옮겨도 응용이 빠르다.

9. 추천 자료와 포트폴리오 프로젝트

자료 조사 과정에서 반복적으로 언급되는 학습 경로를 본인 나름대로 정리하면 다음과 같다. 첫째, C++ 문법과 포인터·메모리 모델을 정리한다. 둘째, tinyrenderer·tinyraytracer 같은 소프트웨어 렌더러 튜토리얼로 파이프라인 개념을 손으로 확인한다. 셋째, LearnOpenGL 같은 자료로 삼각형 하나부터 텍스처·조명·그림자까지 단계적으로 쌓는다. 넷째, WebGPU나 Vulkan 입문 튜토리얼로 저수준 API의 명시적 자원 관리를 경험한다. 다섯째, 작은 PBR 머티리얼 뷰어나 실시간 데모 하나를 완결된 프로젝트로 완성해 포트폴리오에 남긴다.

실제 채용 관점에서 흥미로운 지적도 있다. 그래픽스 채용 담당자는 이력서 문구보다 깃허브의 실제 코드를 본다는 것이다. PBR 조명을 갖춘 엔진형 렌더러 하나와, 포토리얼리스틱 결과물을 보여주는 별도의 패스트레이서 하나, 이 두 가지를 함께 갖춘 포트폴리오가 특히 설득력이 있다고 언급된다. 다섯 단계를 통째로 밟을 필요는 없고, 목표(게임 스튜디오·XR·시각화 툴·GPU 컴퓨팅)에 따라 순서와 비중을 조정하는 것이 현실적이다.

10. AI 시대에도 유효한 근본 지식인가

생성형 AI 이미지·영상 모델이 빠르게 발전하면서, 그래픽스 파이프라인을 직접 배우는 것이 시대에 뒤처진 선택은 아닌지 묻는 사람이 늘었다. 본인의 판단은 그 반대에 가깝다. 신경망 렌더링, 디퍼렌셔블 렌더링, 실시간 업스케일링·디노이징 같은 최신 연구 다수가 결국 선형대수·좌표 변환·GPU 병렬 연산이라는 같은 수학 기반 위에서 작동한다. 그래픽스와 AI가 별개의 두 분야가 아니라, 같은 수학적 토대를 공유하는 두 응용이라는 쪽에 가깝다.

즉 그래픽스 파이프라인을 이해하는 사람이 AI 기반 렌더링·시뮬레이션 연구로 넘어가기가, 그 반대보다 오히려 자연스럽다. 프레임마다 물리적으로 정확한 픽셀을 실시간으로 뽑아내야 하는 게임·XR·시뮬레이션·디지털 트윈 영역은 AI가 대체하기보다, AI를 파이프라인의 한 단계(디노이징·업스케일링·NPC 애니메이션 등)로 흡수하는 방향으로 가고 있다고 보는 것이 더 정확한 진단이다.

결론: 오늘 시작할 수 있는 세 가지

이 로드맵을 한 문장으로 요약하면, 수학 기초 → 소프트웨어 렌더러 → 그래픽스 API → 셰이더 → GPU 아키텍처 → 레이트레이싱/PBR 순으로 난이도를 쌓아 올리되, 처음부터 저수준 API에 뛰어들어 좌절하지 말라는 것이다. 오늘 시작할 수 있는 구체적인 세 가지를 제안한다.

첫째, 벡터·행렬 연산을 손코드로 짜보며 감을 잡아라. 둘째, tinyrenderer 같은 소프트웨어 래스터라이저를 주말 프로젝트로 끝까지 완성해봐라. 셋째, OpenGL이나 WebGPU로 삼각형 하나를 화면에 띄우는 첫 성공 경험을 만들어라. 그래픽스 프로그래밍은 여전히 진입장벽이 있는 분야지만, AI 시대에도 대체되기보다 오히려 그 기반 수학을 공유하는 인접 분야로 자리를 넓혀가고 있다.
