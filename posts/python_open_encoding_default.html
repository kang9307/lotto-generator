출처는 Python 공식 문서(open(), UTF-8 Mode, PEP 686)와 각 설명 바로 앞의 출력이고, 출력의 범위는 Windows 10(한국어 로캘, 콘솔 코드 페이지 949)의 Git Bash 에서 Python 3.13.3 이 낸 값이며 경로만 C:\demo 로 표기했다.

서론 - encoding을 적지 않은 open()은 값을 어디서 가져오는가

한글이 든 텍스트 파일을 open('data.txt').read()로 읽는 코드는 개발자의 PC에서 멀쩡히 돌다가 다른 PC에서 UnicodeDecodeError로 멈추거나, 오류 없이 글자가 바뀌어 나온다. 코드가 같은데 결과가 다르므로 코드 밖에 입력이 하나 더 있다는 뜻이다. 그 입력은 encoding 인수를 생략했을 때 인터프리터가 채워 넣는 기본값이다. 기본값이 어디서 오는지, 얼마나 쉽게 바뀌는지, 바뀌면 어떤 출력이 나오는지는 아래 출력이 보여 준다.

인코딩 문제를 다루는 글은 이미 여럿 있고 축이 다르다. BOM 글은 파일 맨 앞 세 바이트가 파서를 깨뜨리는 경우를, cp949와 UTF-8 mojibake 글은 깨진 모양에서 원인을 역추적하는 방법을, PowerShell 5.1 리다이렉트 글은 PowerShell이 파일을 쓸 때 정해지는 인코딩을, 압축 파일명 글은 zip 안의 이름 바이트를 다룬다. 여기서는 Python의 open()이 인코딩을 생략했을 때 쓰는 값이 정해지는 자리, 그 값을 바꾸는 UTF-8 모드, 위험 지점을 찾는 EncodingWarning, 3.15에 예정된 변화, 그리고 코드에서 안전하게 쓰는 패턴에 한정한다. cp949 글 8절에는 PYTHONUTF8=1이 open() 기본값을 바꾼다는 짧은 실행이 있으며, 아래 내용은 그 위에 변인을 늘려 이어 간다.

다루는 질문은 다음과 같다.

  • encoding을 생략한 open()의 기본값은 무엇이고 어떤 함수가 돌려주는 값과 같은가.
  • UTF-8로 쓴 한글 파일을 기본값으로 읽으면 어떤 예외가 어디에서 나는가.
  • 반대로 기본값으로 쓴 파일을 UTF-8로 읽으면 무엇이 보이는가.
  • 예외 없이 글자가 바뀌는 경우와, 쓰기 단계에서 예외가 나는 경우는 무엇인가.
  • UTF-8 모드는 무엇을 바꾸고 무엇을 바꾸지 않는가.
  • EncodingWarning은 어떤 줄에 경고를 내고 어떤 줄에는 내지 않는가.
  • PEP 686이 정한 3.15의 변화는 무엇인가.

기본값은 locale.getencoding()이 돌려주는 값이다

먼저 실행 환경의 값을 읽는다. 아래 코드는 로캘 인코딩 두 함수, UTF-8 모드 플래그, 관련 환경 변수 두 개, 표준 출력 인코딩을 한 번에 출력한다.

import locale, os, sys
                    print('python                ', sys.version.split()[0])
                    print('getpreferredencoding  ', locale.getpreferredencoding(False))
                    print('getencoding           ', locale.getencoding())
                    print('utf8_mode             ', sys.flags.utf8_mode)
                    print('PYTHONUTF8            ', os.environ.get('PYTHONUTF8'))
                    print('PYTHONIOENCODING      ', os.environ.get('PYTHONIOENCODING'))
                    print('stdout.encoding       ', sys.stdout.encoding)
python                 3.13.3
                    getpreferredencoding   cp949
                    getencoding            cp949
                    utf8_mode              0
                    PYTHONUTF8             None
                    PYTHONIOENCODING       None
                    stdout.encoding        cp949

이 PC에서는 로캘 인코딩이 cp949이고, UTF-8 모드는 꺼져 있으며(utf8_mode 0), PYTHONUTF8과 PYTHONIOENCODING은 설정되어 있지 않다(None). 이 상태에서 open()의 인코딩을 직접 읽는다.

import locale, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    f = open('probe.txt', 'w')
                    print('open(w).encoding  ', f.encoding)
                    f.close()
                    print('open(r).encoding  ', open('probe.txt').encoding)
                    print('explicit utf-8    ', open('probe.txt', encoding='utf-8').encoding)
                    print('== getencoding()  ', open('probe.txt').encoding == locale.getencoding())
open(w).encoding   cp949
                    open(r).encoding   cp949
                    explicit utf-8     utf-8
                    == getencoding()   True

쓰기 모드와 읽기 모드 모두 cp949가 나왔고, encoding='utf-8'을 적으면 utf-8이 나왔다. 마지막 줄은 파일 객체의 기본 인코딩과 locale.getencoding()의 반환값을 비교해 True가 나온 것이다. Python 공식 문서의 open() 항목은 이 관계를 이렇게 적는다. "The default encoding is platform dependent (whatever locale.getencoding() returns), but any text encoding supported by Python can be used." 출력과 문서 문장이 일치한다.

  • 기본값은 Python이 고른 상수가 아니라 실행 환경의 로캘에서 읽어 오는 값이다. 이 PC에서는 cp949이다.
  • 같은 코드를 로캘이 다른 PC에서 실행하면 기본값도 달라질 수 있다. 문서가 「platform dependent」라고 적은 이유이다.
  • 파일 객체의 encoding 속성으로 실제 적용된 값을 바로 읽을 수 있다. 오류 원인을 가리기 전에 가장 먼저 볼 값이다.
  • 출력의 stdout.encoding 줄은 표준 출력의 속성이며 파일을 여는 기본값과 다른 속성이다. 두 값을 함께 움직이는 설정은 6절에서 다룬다.

UTF-8로 쓴 한글을 기본값으로 읽으면

가장 흔한 사고는 UTF-8로 저장된 파일을 encoding 없이 여는 경우이다. 에디터·git·다른 OS에서 만든 파일은 대개 UTF-8이다. 아래 코드는 한글 문장을 UTF-8로 쓰고 바이트를 출력한 뒤, encoding 없이 읽는다.

import os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    with open('ko_utf8.txt', 'w', encoding='utf-8') as f:
                        f.write('한글 테스트')
                    print(open('ko_utf8.txt', 'rb').read().hex(' '))
                    try:
                        open('ko_utf8.txt').read()
                    except UnicodeDecodeError as e:
                        print(type(e).__name__, e)
ed 95 9c ea b8 80 20 ed 85 8c ec 8a a4 ed 8a b8
                    UnicodeDecodeError 'cp949' codec can't decode byte 0xed in position 0: illegal multibyte sequence

첫 줄은 파일에 실제로 들어간 16바이트이다. 한글 한 글자가 3바이트(ed 95 9c은 첫 글자), 공백이 1바이트(20)이다. 읽을 때는 0번 위치의 0xed에서 cp949 코덱이 「illegal multibyte sequence」를 내며 멈췄다. 이유는 출력이 직접 보여 준다. 쓴 쪽은 encoding='utf-8'을 명시했고, 읽은 쪽은 생략해 앞 절에서 본 cp949가 적용됐다. 예외 메시지에 코덱 이름 'cp949'가 들어 있어서, 메시지만으로 읽는 쪽에 어떤 인코딩이 적용됐는지 알 수 있다.

  • 예외 형식은 UnicodeDecodeError이고 메시지는 코덱 이름, 문제의 바이트(0xed), 위치(position 0)를 담는다.
  • 코덱 이름이 cp949이면 읽는 쪽 인코딩이 cp949라는 뜻이므로 먼저 의심할 곳은 파일이 아니라 읽는 코드의 encoding 인수이다.
  • 이 예외는 환경이 같으면 항상 재현된다. 쓰는 쪽과 읽는 쪽이 같은 PC·같은 설정이면 문제가 보이지 않는다는 점은 6절의 왕복 출력에 있다.

반대 방향 - 기본값으로 쓴 파일을 UTF-8로 읽으면

encoding 없이 쓴 파일을 다른 곳에서 UTF-8로 읽으면 방향이 반대인 같은 문제가 생긴다. 아래 코드는 기본값으로 쓴 한글을 바이트로 보고, cp949로 읽은 결과, UTF-8로 읽은 결과, errors='replace'를 붙여 읽은 결과를 차례로 출력한다. 한글이 직접 출력되면 콘솔 인코딩이 끼어들므로 ascii()로 코드 포인트 이스케이프를 출력한다.

import os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    with open('ko_default.txt', 'w') as f:
                        f.write('한글 테스트')
                    print(open('ko_default.txt', 'rb').read().hex(' '))
                    print(ascii(open('ko_default.txt', encoding='cp949').read()))
                    try:
                        open('ko_default.txt', encoding='utf-8').read()
                    except UnicodeDecodeError as e:
                        print(type(e).__name__, e)
                    print(ascii(open('ko_default.txt', encoding='utf-8', errors='replace').read()))
c7 d1 b1 db 20 c5 d7 bd ba c6 ae
                    '\ud55c\uae00 \ud14c\uc2a4\ud2b8'
                    UnicodeDecodeError 'utf-8' codec can't decode byte 0xc7 in position 0: invalid continuation byte
                    '\ufffd\u0471\ufffd \ufffd\u05fd\ufffd\u01ae'

기본값으로 쓴 같은 문장이 이번에는 c7 d1 b1 db …로 저장됐다. 한 글자가 2바이트인 cp949 바이트이다. cp949로 읽으면 원래 한글(\ud55c\uae00 …)이 복원되고, UTF-8로 읽으면 첫 바이트 0xc7에서 「invalid continuation byte」로 멈춘다. errors='replace'를 붙이면 예외는 사라지지만 결과 문자열은 \ufffd(대체 문자)와 엉뚱한 글자(\u0471, \u05fd, \u01ae)로 채워졌고 원래 문장은 문자열에 남아 있지 않다.

공식 문서의 errors 항목은 기본 동작을 이렇게 적는다. "'strict' to raise a ValueError exception if there is an encoding error. The default value of None has the same effect." 즉 errors를 적지 않은 호출은 strict이고, 위의 예외들은 그 기본 동작의 결과이다.

  • cp949로 쓴 한글은 글자당 2바이트, UTF-8로 쓴 한글은 글자당 3바이트로 출력에 나타난다(3절과 4절의 바이트 열 비교).
  • 같은 문장이라도 두 인코딩의 바이트가 다르므로 한쪽에서 쓴 파일을 다른 쪽 인코딩으로 읽는 것은 어느 방향이든 변환이 아니라 오독이다.
  • errors='replace'는 오류를 감추고 정보를 지운다. 이 출력에서 원래 바이트 c7은 \ufffd로 바뀌어 문자열에서 되살릴 수 없었다.
  • 손상 바이트를 남겨 두려면 errors='backslashreplace'가 있고, 9절에서 출력을 비교한다.

조용히 틀리는 경우와 쓰기에서 터지는 경우

모든 오독이 예외로 끝나는 것은 아니다. 아래 코드는 UTF-8 바이트를 cp949로 해석할 때 예외가 나는 문자열과 나지 않는 문자열을 나란히 놓는다. 마지막 두 줄은 cp949로 표현할 수 없는 문자(U+2728)를 기본값으로 쓰는 경우이다.

import os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    print('café'.encode('utf-8').hex(' '))
                    for s in ['한글 테스트', '가나다라마바사', 'abc', 'caf\u00e9', '\u2014 dash']:
                        b = s.encode('utf-8')
                        try:
                            print('silent', ascii(s), '->', ascii(b.decode('cp949')))
                        except UnicodeDecodeError as e:
                            print('error ', ascii(s), '->', e.reason, 'at byte', e.start)
                    try:
                        open('emoji.txt', 'w').write('ok \u2728')
                    except UnicodeEncodeError as e:
                        print(type(e).__name__, e)
                    print(os.path.getsize('emoji.txt'))
63 61 66 c3 a9
                    error  '\ud55c\uae00 \ud14c\uc2a4\ud2b8' -> illegal multibyte sequence at byte 0
                    error  '\uac00\ub098\ub2e4\ub77c\ub9c8\ubc14\uc0ac' -> illegal multibyte sequence at byte 2
                    silent 'abc' -> 'abc'
                    silent 'caf\xe9' -> 'caf\ucc55'
                    error  '\u2014 dash' -> illegal multibyte sequence at byte 0
                    UnicodeEncodeError 'cp949' codec can't encode character '\u2728' in position 3: illegal multibyte sequence
                    0

첫 줄은 café의 UTF-8 바이트 63 61 66 c3 a9이다. 한글 문장과 가나다 문장, 줄표(U+2014)가 든 문자열은 예외로 끝났고, 영문자만 든 abc는 두 인코딩에서 같아 그대로 나왔다. 그런데 café는 예외 없이 caf\ucc55로 읽혔다. 끝의 두 바이트 c3 a9가 cp949에서 유효한 두 바이트 글자 하나(U+CC55)로 해석된 결과이다. 예외가 없으므로 이 오독은 화면이나 데이터를 보기 전까지 드러나지 않는다.

쓰기에서는 반대로 예외가 난다. open('emoji.txt', 'w').write('ok \u2728')은 UnicodeEncodeError: 'cp949' codec can't encode character '\u2728'으로 끝났고, 파일 크기를 읽으면 0이다. 파일은 만들어졌지만 쓰려던 내용은 한 바이트도 들어가지 못했다.

표의 마지막 행이 문제를 늦게 발견하게 만드는 조건이다. 같은 설정에서는 쓰고 읽는 양쪽이 같은 기본값을 쓰므로 어긋남이 없다. 6절의 왕복 출력이 이를 보여 준다.

UTF-8 모드 - 바뀌는 것과 바뀌지 않는 것

공식 문서의 UTF-8 Mode 항목은 활성화 방법을 이렇게 적는다. UTF-8 모드는 -X utf8 명령행 옵션과 PYTHONUTF8 환경 변수로 켜고 끈다. 켜졌을 때 바뀌는 것으로는 파일 시스템 인코딩이 UTF-8이 되고, open()·io.open()·codecs.open()이 기본으로 UTF-8을 쓴다고 적는다. 다만 오류 처리는 여전히 strict라서 바이너리 파일을 텍스트 모드로 열면 엉뚱한 데이터가 아니라 예외가 나기 쉽다고 덧붙인다. 아래 코드는 이 문장들에 대응하는 값을 한 번에 출력한다. 아래 출력은 같은 스크립트에 옵션만 달리 준 결과이다.

import sys, locale, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    open('probe.txt', 'w').close()
                    f = open('probe.txt')
                    print('utf8_mode      ', sys.flags.utf8_mode)
                    print('open() default ', f.encoding)
                    print('stdout         ', sys.stdout.encoding)
                    print('getencoding    ', locale.getencoding())
                    print('preferred      ', locale.getpreferredencoding(False))
                    print('fs encoding    ', sys.getfilesystemencoding())
                    print('locale option  ', open('probe.txt', encoding='locale').encoding)

옵션이 없을 때의 출력이다.

                    open() default  cp949
                    stdout          cp949
                    getencoding     cp949
                    preferred       cp949
                    fs encoding     utf-8
                    locale option   cp949

표는 옵션 다섯 가지의 출력을 그대로 옮긴 것이다. 읽을 수 있는 것은 다음과 같다.

  • -X utf8과 PYTHONUTF8=1은 같은 결과를 냈다. 둘 다 utf8_mode가 1이 되고 open() 기본값과 표준 출력 인코딩이 utf-8로 바뀌었다.
  • -X utf8=0과 PYTHONUTF8=0은 옵션이 없을 때와 같은 결과이다. 이 환경에서는 UTF-8 모드를 끄는 값이 기본 상태와 구분되지 않았다.
  • locale.getencoding()은 어느 경우에도 cp949이다. PEP 686은 이 함수를 UTF-8 모드를 무시하고 로캘 인코딩을 돌려주는 새 API로 설명하며, 출력이 그 설명과 일치한다.
  • locale.getpreferredencoding(False)는 UTF-8 모드에서 utf-8로 바뀐다. 같은 「로캘 인코딩」을 묻는 두 함수의 답이 다르므로, 어느 함수로 값을 확인했는지가 판단을 바꾼다.
  • encoding='locale'을 지정하면 UTF-8 모드에서도 cp949가 나왔다. 로캘 인코딩을 일부러 써야 하는 파일(예: 로캘 인코딩으로 저장된 기존 설정 파일)에는 이 값이 쓰인다.
  • 파일 시스템 인코딩(fs encoding)은 UTF-8 모드 여부와 무관하게 utf-8이었다.

「내 PC에서는 된다」가 생기는 과정은 아래 코드의 출력에 나타난다. 아래 코드는 한글을 encoding 없이 쓰고, 바이트를 출력하고, encoding 없이 다시 읽고, cp949로 읽는다. 표준 출력은 한글이 직접 보이도록 UTF-8로 맞췄다. 같은 코드를 옵션 없이, 그리고 -X utf8로 실행한다.

import sys, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    sys.stdout.reconfigure(encoding='utf-8')
                    with open('m2.txt', 'w') as f:
                        f.write('한글 테스트')
                    print(open('m2.txt', 'rb').read().hex(' '))
                    print(open('m2.txt').read())
                    try:
                        open('m2.txt', encoding='cp949').read()
                    except UnicodeDecodeError as e:
                        print('cp949 read:', type(e).__name__, e)

옵션 없이 실행한 출력이다.

c7 d1 b1 db 20 c5 d7 bd ba c6 ae
                    한글 테스트

-X utf8로 실행한 출력이다.

ed 95 9c ea b8 80 20 ed 85 8c ec 8a a4 ed 8a b8
                    한글 테스트
                    cp949 read: UnicodeDecodeError 'cp949' codec can't decode byte 0xed in position 0: illegal multibyte sequence

옵션 없이는 c7 d1 …(cp949 바이트)가 저장되고 그대로 읽혀서 오류가 없다. 같은 코드에 -X utf8만 더하면 저장되는 바이트가 ed 95 9c …(UTF-8)로 바뀌고, 이번에는 cp949로 읽는 줄에서 UnicodeDecodeError가 난다. 코드는 한 글자도 바뀌지 않았다. 바뀐 것은 기본값 하나뿐이다. 이것이 서로 다른 설정의 PC 사이에서 파일을 주고받을 때 생기는 어긋남의 최소 재현이다.

UTF-8 모드는 과거 파일에도 영향을 준다. 앞에서 cp949로 저장한 파일을 -X utf8로 실행한 인터프리터에서 encoding 없이 열면 다음 예외가 나왔다.

UnicodeDecodeError 'utf-8' codec can't decode byte 0xc7 in position 0: invalid continuation byte

UTF-8 모드를 켜는 것은 문제를 없애는 것이 아니라 기본값의 방향을 바꾸는 것이다. 기존 cp949 파일이 있는 환경에서는 켜는 순간 그 파일이 읽히지 않는다.

EncodingWarning으로 빠뜨린 곳 찾기

-X warn_default_encoding 옵션을 켜면 encoding 인수를 생략한 호출이 EncodingWarning을 낸다. 아래 코드는 인코딩을 쓰는 방식 일곱 가지를 한 파일에 놓은 것이다. 4번째 줄은 생략, 5번째 줄은 Path.read_text()의 생략, 9번째 줄은 encoding=None이다.

import pathlib, os, tempfile; os.chdir(tempfile.mkdtemp())
                    with open('a.txt', 'w', encoding='utf-8') as f:
                        f.write('x')
                    open('a.txt').read()
                    pathlib.Path('a.txt').read_text()
                    open('a.txt', encoding='utf-8').read()
                    open('a.txt', 'rb').read()
                    open('a.txt', encoding='locale').read()
                    open('a.txt', encoding=None).read()
C:\demo\warn.py:4: EncodingWarning: 'encoding' argument not specified
                      open('a.txt').read()
                    C:\demo\warn.py:5: EncodingWarning: 'encoding' argument not specified
                      pathlib.Path('a.txt').read_text()
                    C:\demo\warn.py:9: EncodingWarning: 'encoding' argument not specified
                      open('a.txt', encoding=None).read()

경고는 4·5·9번째 줄에서만 나왔다. 쓰기 모드에서 encoding='utf-8'을 적은 2번째 줄, 읽기에서 적은 6번째 줄, 바이너리 모드('rb')인 7번째 줄, encoding='locale'인 8번째 줄에는 경고가 없었다. 9번째 줄이 보여 주는 것은 encoding=None이 생략과 같이 취급된다는 점이다. 경고를 예외로 올리면 첫 지점에서 멈춘다.

Traceback (most recent call last):
                      File "C:\demo\warn.py", line 4, in <module>
                        open('a.txt').read()
                        ~~~~^^^^^^^^^
                    EncodingWarning: 'encoding' argument not specified

같은 경고를 환경 변수 PYTHONWARNDEFAULTENCODING=1로도 켤 수 있었다. 출력은 옵션으로 켠 경우와 같았다. 환경 변수는 코드를 건드리지 않고 테스트 러너나 CI에서 켜기에 쓸모가 있다. UTF-8 모드(-X utf8)와 함께 켜도 경고는 같은 세 줄에서 나왔다.

경고는 코드가 실행된 줄에서만 나온다. 한 번도 실행되지 않은 분기의 open()은 경고가 없다. 정적으로 훑는 방법도 함께 둔다. 아래는 표준 라이브러리 ast로 encoding 없는 텍스트 모드 open()과 read_text()를 찾는 짧은 검사기이다.

import ast, sys
                    hits = []
                    for path in sys.argv[1:]:
                        tree = ast.parse(open(path, encoding='utf-8').read())
                        for node in ast.walk(tree):
                            if not isinstance(node, ast.Call):
                                continue
                            name = ast.unparse(node.func)
                            has_enc = any(k.arg == 'encoding' for k in node.keywords)
                            if name == 'open':
                                mode = node.args[1].value if len(node.args) > 1 else 'r'
                                if 'b' not in mode and not has_enc and len(node.args) < 4:
                                    hits.append((path, node.lineno, 'open() without encoding'))
                            elif name.endswith('.read_text') and not has_enc and not node.args:
                                hits.append((path, node.lineno, name + '() without encoding'))
                    for path, line, msg in sorted(hits):
                        print(path + ':' + str(line), msg)

검사 대상은 encoding 없이 쓴 흔한 형태를 담은 예제 파일이다.

import json, pathlib
                    cfg = json.load(open('config.json'))
                    with open('out.txt', 'w') as f:
                        f.write('x')
                    raw = open('in.bin', 'rb').read()
                    ok = open('in.txt', encoding='utf-8').read()
                    note = pathlib.Path('note.txt').read_text()

두 파일에 실행한 출력이다.

legacy.py:2 open() without encoding
                    legacy.py:3 open() without encoding
                    legacy.py:7 pathlib.Path('note.txt').read_text() without encoding
                    warn.py:4 open() without encoding
                    warn.py:5 pathlib.Path('a.txt').read_text() without encoding

json.load(open('config.json'))처럼 호출 안에 중첩된 open()도 legacy.py:2로 잡혔고, 바이너리 모드와 encoding을 적은 줄은 잡히지 않았다. 다만 이 검사기는 encoding=None이 있는 9번째 줄을 놓친다(warn.py:9가 목록에 없다). 반면 EncodingWarning은 그 줄을 잡았다. 두 방법이 놓치는 곳이 다르므로 실행 경로는 경고로, 실행되지 않는 분기는 정적 검사로 나눠 쓴다.

  • EncodingWarning은 실제로 실행된 호출에 대해서만 나온다.
  • encoding=None은 생략과 같이 경고를 낸다.
  • UTF-8 모드를 켜도 경고는 사라지지 않았다. 경고의 목적은 기본값에 기대는 줄을 드러내는 것이다.
  • 정적 검사는 실행되지 않는 분기까지 보지만 변수로 넘긴 인수나 encoding=None 같은 경우는 별도 규칙이 필요하다.

PEP 686 - 3.15의 계획

PEP 686의 초록은 이렇게 시작한다. "This PEP proposes enabling UTF-8 mode by default. With this change, Python consistently uses UTF-8 for default encoding of files, stdio, and pipes." 2026-10-06 현재 문서 기준으로 상단의 상태는 Final, 대상 버전은 Python 3.15이다. 명세는 "Python will enable UTF-8 mode by default from Python 3.15."라고 적고, 끄는 방법으로 PYTHONUTF8=0과 -X utf8=0을 안내한다. UTF-8 Mode 문서의 3.15 안내 문장은 한 줄이다. "Python 3.15 will make Python UTF-8 Mode default."

이 계획을 앞의 실행과 겹쳐 읽으면 세 가지가 나온다.

  • 3.13에서 -X utf8을 켠 실행(6절)은 문서가 3.15의 기본 상태로 정한 동작과 같은 모양이다. 3.15에서는 옵션 없이 이 동작이 기본이 된다.
  • 3.15 이후에도 로캘 인코딩이 필요한 파일에는 encoding='locale'을 쓰고, 이 값은 6절의 실행에서 UTF-8 모드와 무관하게 cp949를 돌려줬다.
  • 기본값의 방향이 바뀌는 것이므로, cp949로 저장돼 있고 encoding 없이 읽는 기존 코드는 6절 끝의 예외와 같은 모양으로 읽기에 실패할 수 있다.

3.15 이전 버전에서 같은 코드를 돌릴 때 기본값에 기대는 코드는 환경마다 다르게 동작한다. 계획이 있다는 사실이 현재 버전의 코드를 안전하게 만들지는 않는다. encoding을 적은 호출은 2절과 6절의 출력처럼 지정한 값을 그대로 쓴다.

안전한 읽기·쓰기 패턴

앞의 실행에서 얻은 규칙은 한 줄이다. 텍스트 모드의 읽기와 쓰기 양쪽에 encoding을 적는다. 6절의 왕복 실행에서 UTF-8 모드가 켜진 상태에도 명시한 cp949가 그대로 적용됐다. 상황별로 쓰는 형태와 이 환경에서 나온 출력을 표로 모았다.

상황쓰는 형태이 환경의 출력
일반 텍스트 파일open(path, encoding='utf-8')파일 객체의 encoding이 utf-8(2절)

표의 줄바꿈·BOM·JSON 행은 아래 실행에서 나온 값이다. 먼저 줄바꿈이다. 인코딩과 별개로, 텍스트 모드는 쓸 때 줄바꿈도 변환한다.

import pathlib, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    p = pathlib.Path('p1.txt')
                    p.write_text('한글\n둘째', encoding='utf-8')
                    print(p.read_bytes().hex(' '))
                    with open('nl_default.txt', 'w', encoding='utf-8') as f:
                        f.write('a\nb\n')
                    with open('nl_lf.txt', 'w', encoding='utf-8', newline='\n') as f:
                        f.write('a\nb\n')
                    print(open('nl_default.txt', 'rb').read().hex(' '))
                    print(open('nl_lf.txt', 'rb').read().hex(' '))
ed 95 9c ea b8 80 0d 0a eb 91 98 ec a7 b8
                    61 0d 0a 62 0d 0a
                    61 0a 62 0a

첫 줄은 Path.write_text()로 쓴 한글\n둘째의 바이트로, 줄바꿈 자리에 0d 0a(CRLF)가 들어갔다. 둘째 줄은 open(..., 'w')의 기본 동작으로 a\nb\n이 61 0d 0a 62 0d 0a가 된 것이고, 셋째 줄은 newline='\n'을 붙여 0a만 남은 것이다. 이 PC에서는 줄바꿈이 자동으로 변환된다.

다음은 BOM, JSON, CSV이다.

import csv, json, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    open('bom.txt', 'wb').write(b'\xef\xbb\xbf' + '가'.encode('utf-8'))
                    print(ascii(open('bom.txt', encoding='utf-8').read()))
                    print(ascii(open('bom.txt', encoding='utf-8-sig').read()))
                    with open('d.json', 'w', encoding='utf-8') as f:
                        json.dump({'k': '값'}, f, ensure_ascii=False)
                    print(open('d.json', 'rb').read().hex(' '))
                    with open('c.csv', 'w', encoding='utf-8', newline='') as f:
                        csv.writer(f).writerow(['이름', 'x'])
                    print(open('c.csv', 'rb').read().hex(' '))
'\ufeff\uac00'
                    '\uac00'
                    7b 22 6b 22 3a 20 22 ea b0 92 22 7d
                    ec 9d b4 eb a6 84 2c 78 0d 0a

BOM이 붙은 파일을 utf-8로 읽으면 첫 글자 앞에 \ufeff가 남고('\ufeff\uac00'), utf-8-sig로 읽으면 사라진다('\uac00'). BOM의 쓰임과 문제는 BOM 글이 자세히 다룬다. JSON은 ensure_ascii=False일 때 한글이 UTF-8 3바이트로 저장되고, CSV는 한글 이름이 UTF-8 바이트로 저장됐다.

마지막으로 손상 바이트를 다루는 errors 값의 출력을 비교한다. 입력은 cp949로 저장된 한글을 UTF-8로 잘못 읽는 경우이다.

b = '한글'.encode('cp949')
                    print(b.hex(' '))
                    print(ascii(b.decode('utf-8', errors='replace')))
                    print(ascii(b.decode('utf-8', errors='backslashreplace')))
c7 d1 b1 db
                    '\ufffd\u0471\ufffd'
                    '\\xc7\u0471\\xdb'

replace는 원래 바이트를 지우지만(\ufffd) backslashreplace는 \xc7, \xdb처럼 바이트 값을 문자열에 남긴다. 원인 분석에 쓸 단서가 필요하면 후자가 낫다. 두 방식 모두 오독을 고치지는 못하며, 올바른 인코딩을 적는 것이 해법이다.

정리하면 다음 체크 항목으로 코드를 점검할 수 있다.

  • 텍스트 모드 open()에 encoding이 있는가.
  • Path.read_text()·write_text()에 encoding이 있는가.
  • CSV를 여는 곳에 newline=''이 있는가.
  • 로캘 인코딩을 쓰려는 의도가 있다면 encoding='locale'로 드러나 있는가.
  • 테스트 러너나 CI에서 -X warn_default_encoding으로 경고가 0건인지 확인하는가.
  • 파일을 주고받는 상대의 인코딩이 문서로 정해져 있는가.

확인하지 못한 것

  • Python 3.15 인터프리터에서의 동작. 이 PC에는 3.13만 있으며, 3.15의 기본 UTF-8 모드와 실제 기본값은 PEP 686과 UTF-8 Mode 문서의 문구로만 인용했다. 3.15에서 cp949 파일 읽기가 실패하리라는 서술은 3.13의 UTF-8 모드 출력에서 미루어 본 것이다.
  • 리눅스·macOS에서 같은 코드가 내는 출력. 로캘이 UTF-8인 환경에서의 기본값은 실행하지 않았다.
  • 로캘이 다른 Windows(영어·일본어 등)에서의 기본값. 이 PC는 한국어 로캘 하나이다.
  • Windows 시스템 로캘의 「유니코드 UTF-8 사용」 옵션을 켠 경우의 기본값.
  • sys.stdout이 파이프나 파일로 연결됐을 때의 인코딩. 6절의 표준 출력 값은 콘솔 환경에서 얻은 것이다.
  • EncodingWarning이 subprocess·io.TextIOWrapper 등 open() 밖의 호출에서 나오는 범위.
  • -X utf8=0·PYTHONUTF8=0이 이 환경에서 기본 상태와 같은 결과를 낸 이유. 로캘이 cp949인 환경이라는 점 외에 다른 설정과의 상호작용은 실행하지 않았다.
  • cp949와 UTF-8 이외의 인코딩(UTF-16, EUC-KR 변형, 확장 완성형 밖의 문자)에서의 동작.
