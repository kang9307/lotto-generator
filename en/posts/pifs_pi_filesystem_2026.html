πFS - The Filesystem That Stores Data in the Digits of Pi Instead of a Disk

The idea behind the data-free filesystem, why it saves nothing, and the serious information theory the joke teaches

2026-06-12 Tech & IT

Introduction: A Filesystem That Stores No Data

One of the topics that resurfaced on news.hada.io in June 2026 was πFS, the pi filesystem. The pitch is irresistible: do not write your files to a hard disk. Instead, record only the position (offset) where that file already appears inside the digits of pi. The data itself never needs to be stored anywhere, because pi is infinite.

At first this sounds like genius-level infinite compression. Replace any file with a single number, its location. But think for a moment and you realize it does not work. And why it does not work is exactly where the value of the joke lives. πFS, created by Philip Langdale, is a deliberately useless filesystem and simultaneously a teaching fable about information theory, number theory, and the limits of compression.

This article is more than an introduction. Across twelve H2 sections I will cover (1) the idea behind πFS, (2) how it actually works, (3) what a normal number is, (4) why pi's normality is still unproven, (5) the link to the infinite monkey theorem, (6) why the offset is larger than the data, (7) the astronomical cost of searching, (8) Kolmogorov complexity, (9) the information-theoretic limit on compression via the pigeonhole principle, (10) sibling jokes such as "magic" compression, (11) the lessons for developers, and (12) a conclusion. My rule throughout: keep the humor, but get the math exactly right.

One-line summary - πFS converts data into a position inside pi, but that position is as large as the data, so it saves nothing. Information does not vanish when you change its representation.

1. The Idea - All Your Data Is Already in Pi

The premise rests on a single sentence: "If pi is a normal number, then every finite sequence of digits must appear somewhere in its infinite expansion." Your photos, your movies, your novels, every file is ultimately a finite string of digits or bits. If so, that exact string must appear at some offset within pi.

This observation is not new. People have long marveled that "pi is infinite, so my birthday and even the complete works of Shakespeare are in there somewhere." The cleverness of πFS is that it takes this observation and implements it, seriously yet jokingly, as a filesystem design. Instead of storing the data, store the data's address, much like writing down a library call number instead of photocopying the whole book.

The flaw is already visible in that analogy. If a library physically holds every book, the call numbers are short. But the "library" that is pi is infinite, and finding a specific piece of data inside it requires a call number (offset) that is as long as the data itself, or longer. Every joke in πFS converges on this one point.

2. How It Works - Offsets and Metadata

How does a real πFS implementation operate? Based on Philip Langdale's original, the flow is:

  • Decompose: split the file into bytes (or smaller units).
  • Search: for each unit, find the position where it first appears in pi's digit expansion, computed directly via formulas such as the BBP formula.
  • Record: store that offset and the file structure in a metadata directory on an actual disk.
  • Reconstruct: on read, recompute the corresponding digits of pi from the stored offset to recover the original bytes.

Here is the central contradiction. The data is never written to disk, but the metadata pointing to it is. And that metadata is larger than the original data. So the claim "we store no data" is only formally true; real disk usage actually grows. Even the original README never claims any space savings; it makes this very contradiction the heart of the joke.

# Conceptual pseudocode (showing there is no real saving)
file = [0x48, 0x49]              # "HI", 2 bytes = 16 bits
offset_H = position of 0x48 in pi   # an astronomically large integer
offset_I = position of 0x49 in pi   # another huge integer
metadata = [offset_H, offset_I] # two giant integers -> bigger than the original
# Result: to delete 2 bytes we store offsets of tens to hundreds of bytes

3. What Is a Normal Number?

To understand the premise of πFS you need the concept of a normal number. A real number is normal in a given base when, in that base's expansion, every digit and every block of digits of any length appears with uniform frequency. In base 10, that means 0 through 9 each appear with frequency 1/10, every pair 00 through 99 with frequency 1/100, and so on.

A key consequence is disjunctiveness: a number normal in every base (absolutely normal) contains every finite digit sequence as a substring. So if a number is normal, "whatever data I want is in there somewhere" becomes mathematically true. The premise of πFS is precisely "pi is a normal number."

Careful - Being "infinite and non-repeating" (irrational) alone does not guarantee that all sequences appear. For example, 0.1010010001000010... is irrational yet contains no digit 2 at all. "Contains every sequence" comes not from irrationality but from normality (or at least disjunctiveness).

4. The Normality of Pi Is Still Unproven

Now the most important fact, stated plainly: it has not been proven that pi is a normal number. As of 2026 it is only a conjecture.

Mathematicians believe that most "natural" irrationals such as pi, e, and the square root of two are normal, but proving normality for any specific number is famously hard. For pi, statistics on trillions of computed digits agree well with normality, yet testing any finite number of digits can never amount to a proof. More startling still, it has not even been proven that each digit 0 through 9 occurs infinitely often in pi.

So the accurate phrasing is: "Pi is presumed normal, and if so, every finite piece of data appears within it, but that very premise is unproven." πFS not only fails to work; the mathematical premise required for it to work is itself still a hypothesis. This is the correction I most want to emphasize in this article.

5. The Link to the Infinite Monkey Theorem

The intuition behind normal numbers shares a root with the famous infinite monkey theorem: a monkey hitting keys at random for an infinite time will almost surely eventually type the complete works of Shakespeare.

Formally: if you build an infinite sequence by drawing each character independently and uniformly at random from a finite alphabet, then any given finite string almost surely appears as a substring of that sequence. This rests on the fact that the set of all finite strings is countable. It is essentially the same intuition as a normal number containing every sequence.

But there is a trap. "Almost surely" means probability one, not fast or practical. The expected time for the monkey to type even the six letters of "Hamlet" dwarfs the age of the universe. πFS is the same: that your data exists in pi and that you can find and use it are entirely different problems. Confusing existence with practicality is the exact weak spot of the πFS joke.

6. Why the Offset Is Bigger Than the Data - No Savings

Now let us quantify the core reason πFS is pointless. The bottom line: the position where your data appears in pi is almost always larger than the data itself.

The intuition is simple. Treating pi as a random sequence, a specific pattern of length N bits first appears at roughly position 2 to the power N. But representing a position around 2^N again requires about N bits. So you delete N bits of data only to store an N-bit position. The net saving is zero, or worse.

Just store on diskN0baseline
πFS (store offset)0about N (or more)no saving

The last row is the knockout blow. You might think, "If the offset is big, just store the offset with πFS too." But then you need an index for the index, and an index for that index, forever. At no stage does the information content shrink. This is the concrete form of the information-theoretic truth that there is no free compression.

7. The Astronomical Cost of Searching

Even if you ignored the storage problem, the cost of finding your data in pi is another wall.

There are methods such as the BBP (Bailey–Borwein–Plouffe) formula that compute an arbitrary digit of pi directly. But πFS needs the reverse: finding the first position where a given byte pattern appears in pi. That is a search through an infinite sequence, and the longer the pattern, the exponentially farther its first occurrence lies. Beyond a handful of bytes, the search becomes practically impossible.

That is why real πFS implementations usually find just one byte (or less) at a time and accumulate offsets. This keeps the search cheap, but it slams the offset-explosion problem from Section 6 right back into your face. Reduce the search cost and the storage cost explodes; lengthen the pattern to save storage and the search becomes impossible. Either road is a dead end. This two-front squeeze is what makes πFS a "perfectly useless" design.

8. Kolmogorov Complexity - The Essential Information Content

Why does no representation reduce the information? The answer is Kolmogorov complexity.

The Kolmogorov complexity C(x) of a string x is the length of the shortest program that outputs it. That is the "essential information content" of the data. Regular data (say "010101..." ten thousand times) is generated by a short program and has low complexity; near-random data has no program shorter than writing itself out verbatim, so its complexity is high.

From the πFS angle this is illuminating. "Expressing data as an offset into pi" is exactly writing one program that generates it: "output k digits of pi starting at index i." But the length of that program is dominated by the size of the offset i, and as we saw, i is as large as the data. So the πFS representation does not reduce the data's Kolmogorov complexity. πFS re-confirms, by a roundabout route, that near-random data cannot be compressed by any clever representation.

9. The Limit of Compression - The Pigeonhole Principle

The claim "you cannot build a perfect compressor that shrinks all data" is proven cleanly by the pigeonhole principle.

There are 2^N strings of length N bits. Suppose some lossless compressor mapped all of them to strings shorter than N bits. But there are only 2^N − 1 distinct strings shorter than N bits. Putting 2^N items into 2^N − 1 pigeonholes forces at least two into the same hole. Then one compressed output corresponds to two different originals, making reconstruction impossible, which contradicts the definition of lossless compression.

Therefore a perfect lossless compressor that shrinks every input is mathematically impossible. In fact, the fraction of length-N strings that can be shrunk by c bits is at most 2^(−c), and most strings barely compress at all (such strings are called incompressible or Kolmogorov-random). πFS appears to violate this limit, but in reality it merely relocates the information into an offset, so it never violates anything. The failure of πFS is yet another proof of the compression-limit theorem.

Common misconception - Real compressors (zip, zstd, and so on) work because they handle structured real-world data, not "all data." Text, images, and logs are full of repetition and patterns, giving them low Kolmogorov complexity. Compression is not magic; it is the discovery of structure.

10. Sibling Jokes - Magic Compression and Friends

πFS belongs to a family of "impossible compression" jokes. Some related thought experiments:

10-1) Magic / self-referential compression

Claims like "my compressor shrinks any file to one byte." Refuted instantly by pigeonholing: one byte (256 values) cannot distinguish 257 or more different files. The variant "apply it repeatedly for infinite compression" fails the same way, because the information just hides somewhere (in the number of passes, or in the decompressor itself).

10-2) The library of all books (Borges' Library of Babel)

In a library containing every possible book, the cost of finding the book you want overwhelms the cost of writing it. This is exactly the offset problem of πFS. Existing is not the same as being accessible.

10-3) Mistaking a hash for the data

"Why not just store the file's hash?" is a common confusion. A hash is one-way, so the original cannot be recovered (collisions exist too), and inverting it would effectively require the original information again. Another variation on "there is no free information."

11. The Lessons for Developers

Here is what a working developer should take from this joke, from my point of view.

11-1) Information does not vanish when you change its representation

Moving data into an index, hash, offset, or alternative coordinate system does not lower its essential information content (Kolmogorov complexity). Whenever you meet a design of the form "it already exists somewhere, so just store the location," check the size of that location value first.

11-2) Do not confuse existence with practicality

"Theoretically possible" and "usable in reality" are different. Mathematical properties like infinity, normality, and probability one are powerful, but ignoring search cost and time complexity leads to conclusions opposite to practicality.

11-3) Compression is the discovery of structure

Real data compresses because of repetition and patterns, that is, low Kolmogorov complexity. If you want better compression ratios, understand the structure of your data; representation tricks cannot beat the limit.

11-4) Take the math inside a joke seriously

Even an obviously joking design like πFS is only properly understood when you nail the real mathematics: normal numbers, the pigeonhole principle, Kolmogorov complexity. A habit I recommend: when you meet a plausible claim, run it once through the conservation laws of information theory.

12. Conclusion - A Non-Working but Perfect Thought Experiment

πFS in one sentence: "A deliberately useless filesystem that succeeds at turning data into a position inside pi, but where that position is as large as the data, so it saves nothing at all."

Yet uselessness is precisely the project's value. πFS teaches, all at once, that (1) pi's normality is still an unproven conjecture, (2) "almost surely exists" is different from "practically usable," (3) the two-front squeeze of offset and search makes any saving impossible, and (4) Kolmogorov complexity and the pigeonhole principle forbid perfect compression. A single non-working program compresses an entire semester of information theory, and that is one kind of compression that genuinely works.

The message I want to leave is this: when you meet a clever infinite-storage idea, laugh, then check it against the conservation of information. Compression and storage are not magic; they are the science of structure and limits. πFS teaches that truth in the most delightful possible way.
