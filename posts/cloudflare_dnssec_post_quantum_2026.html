1. 양자 컴퓨팅의 암호학적 위협과 DNSSEC의 구조적 취약점

현대 인터넷의 신뢰 모델은 공개키 암호화 알고리즘에 절대적으로 의존하고 있다. 웹 브라우징을 보호하는 TLS 인증서부터 이메일 서명, 소프트웨어 배포 파이프라인, 그리고 도메인 이름 시스템(DNS)의 위변조를 차단하는 DNSSEC(Domain Name System Security Extensions)에 이르기까지 모든 보안 프로토콜은 수학적 난제에 기반한 비대칭 키 암호 체계를 근간으로 삼는다. 그러나 충분한 큐비트와 오류 정정 능력을 갖춘 암호학적 관련 양자 컴퓨터(CRQC, Cryptographically Relevant Quantum Computer)가 출현할 경우, 피터 쇼어(Peter Shor)가 1994년 발표한 쇼어 알고리즘(Shor's Algorithm)에 의해 현재 널리 쓰이는 RSA(소인수분해 난제)와 ECDSA(타원곡선 이산대수 난제)는 다항 시간(polynomial time) 안에 해독된다.

DNSSEC은 인터넷의 전화번호부라 불리는 DNS 레코드의 무결성과 진본성을 보장하기 위해 고안된 확장 명세다. 루트(Root) 네임서버에서 시작하여 최상위 도메인(TLD), 그리고 2차 및 하위 권위 네임서버로 이어지는 계층 구조를 암호학적 전자서명 사슬로 결합한다. 클라이언트나 재귀 리졸버(Recursive Resolver)는 자신이 전달받은 IP 주소가 중간자 공격(MitM)이나 DNS 캐시 포이즈닝(Cache Poisoning)에 의해 조작되지 않았음을 검증하기 위해 상위 존이 하위 존의 공개키 해시를 보증하는 DS(Delegation Signer) 레코드와 해당 레코드 세트를 직접 서명한 RRSIG 레코드를 대조한다. 네임서버 위임과 계층적 신뢰 구조의 기초에 관한 전반적인 원리는 네임서버 위임과 신뢰 체계 분석 문서에서 체계적으로 다룬 바 있다.

만약 공격자가 양자 컴퓨터를 이용해 특정 도메인의 DNSSEC 개인키를 복원하거나 위조 서명을 생성할 수 있게 된다면, 전 세계 트래픽의 목적지 주소를 완전히 장악할 수 있게 된다. 사용자가 브라우저 주소창에 정상적인 도메인을 입력하더라도 조작된 IP 주소로 유도되며, DNSSEC 유효성 검증(AD 플래그)까지 완벽하게 통과하는 치명적인 위협이 발생한다. 더 나아가 DANE(DNS-based Authentication of Named Entities)이나 TLSA 레코드처럼 DNSSEC의 신뢰를 바탕으로 TLS 인증서의 합법성을 교차 검증하는 최신 보안 체계마저 근본부터 무력화된다. 이러한 파괴적 위험에 대비하기 위해 전자서명을 양자 내성 알고리즘으로 마이그레이션하는 작업은 인프라 보안의 최우선 과제로 부상했다.

  • 쇼어 알고리즘의 위협: RSA의 기반이 되는 소인수분해 문제와 ECDSA의 기반이 되는 타원곡선 이산대수 문제를 다항 시간 복잡도 내에 해결하여 기존 서명 체계를 완전히 무력화한다.
  • 신뢰 사슬의 붕괴 위험: 루트 존에서 최종 도메인에 이르는 RRSIG 및 DS 검증 사슬이 위조될 경우 중간자 공격과 캐시 포이즈닝을 시스템적으로 감지할 수 없게 된다.
  • 포스트 퀀텀 전환의 시급성: 양자 컴퓨터가 실제로 상용화된 이후에는 이미 서명 키가 탈취되어 신뢰 회복이 불가능하므로, 선제적인 표준 배포와 검증 생태계 구축이 요구된다.

2. ML-DSA-44 알고리즘의 표준화와 IANA 알고리즘 번호 18 배정

미국 국립표준기술연구소(NIST)는 수년간의 다단계 공모와 치열한 학계 검증을 거쳐 2024년 8월 양자 내성 전자서명 표준인 FIPS 204(ML-DSA, Module-Lattice-Based Digital Signature Algorithm)를 공식 발표했다. ML-DSA는 격자 기반 암호(Lattice-based cryptography) 연구의 정점으로 꼽히는 CRYSTALS-Dilithium 알고리즘을 모태로 하며, 모듈 격자 상에서의 오차 학습 문제(MLWE, Module Learning with Errors)와 최단 벡터 문제(Shortest Vector Problem)의 근사 난이도에 수학적 안전성을 둔다. 양자 컴퓨터의 중첩과 얽힘 현상을 이용하더라도 고차원 격자 공간에서 최단 벡터를 탐색하는 작업에는 지수적 시간 복잡도가 소요되므로 실질적인 안전성이 유지된다.

FIPS 204 표준은 요구되는 보안 강도에 따라 세 가지 보안 매개변수 집합을 정의한다. 각각 ML-DSA-44(NIST 보안 범주 2, 대칭키 AES-128과 동등한 강도), ML-DSA-65(보안 범주 3, AES-192 동등), ML-DSA-87(보안 범주 5, AES-256 동등)이다. 이 중 DNSSEC 환경에 가장 적합한 후보로 낙점된 것은 가장 작은 크기와 연산 오버헤드를 가진 ML-DSA-44다. 인터넷 번호 할당 기관인 IANA(Internet Assigned Numbers Authority)는 국제인터넷표준화기구(IETF) DNSOP 워킹그룹의 논의에 발맞추어 ML-DSA-44에 공식 DNSSEC 알고리즘 번호 18번을 공식 할당했다.

알고리즘 번호 18의 공식 배정은 인터넷 인프라 소프트웨어 개발자들에게 명확한 표준화 신호를 제공했다. 바인드(BIND), 언바운드(Unbound), 파워디엔에스(PowerDNS), 크놋(Knot DNS) 등 주요 네임서버 및 리졸버 구현체들이 실험적 플래그나 비표준 번호가 아닌 단일한 식별자 아래에서 상호 운용성을 확보할 수 있는 토대가 마련된 것이다. Cloudflare는 이 표준에 기반하여 자사의 글로벌 공용 리졸버인 1.1.1.1에 알고리즘 18 유효성 검증 엔진을 통합하고, 양자 내성 서명이 적용된 도메인에 대한 질의를 자동으로 검증할 수 있도록 기능을 활성화했다.

3. 서명 크기 38배 급증 — 암호학적 제원과 키 크기 비교

ML-DSA-44가 제공하는 암호학적 견고함에는 매우 비싼 대가가 따른다. 타원곡선 암호(ECC)는 작은 비트 크기로도 강력한 보안 강도를 제공하여 현대 인터넷의 경량화 혁신을 이끌었다. 현재 DNSSEC에서 가장 널리 쓰이는 표준 알고리즘인 ECDSA P-256(알고리즘 13)의 경우 공개키 크기와 전자서명 크기가 각각 64바이트에 불과하다. 과거 인터넷 초기에 쓰이던 RSA-2048(알고리즘 8)조차 공개키 약 260바이트, 전자서명 256바이트 수준으로 1킬로바이트(KB)를 넘지 않았다.

반면 모듈 격자 기반 암호인 ML-DSA-44는 행렬 연산과 다항식 계수를 다루는 구조적 특성상 키와 서명의 크기가 본질적으로 거대하다. ML-DSA-44의 공개키 크기는 1,312바이트에 달하며, 단 한 번의 전자서명(RRSIG 레코드 데이터) 크기는 무려 2,420바이트에 이른다. 이는 기존 ECDSA P-256 서명(64바이트)과 비교했을 때 약 37.8배, 즉 38배에 달하는 전례 없는 용량 팽창이다. 아래의 비교 표는 DNSSEC에서 사용되는 세 가지 대표 알고리즘의 암호학적 제원 차이를 극명하게 보여준다.

알고리즘 명칭 IANA 번호 공개키 크기 전자서명 크기 기반 수학적 난제
ECDSA P-256 13 64 bytes 64 bytes 타원곡선 이산대수 (ECDLP)
ML-DSA-44 18 1,312 bytes 2,420 bytes 모듈 격자 오차 학습 (MLWE / Dilithium)
RSA-2048 8 ~260 bytes 256 bytes 대형 소수 정수 소인수분해 (Factoring)

이 크기 폭증은 단순히 디스크 저장 공간이나 데이터베이스 용량의 문제가 아니다. 네트워크 프로토콜 스택 관점에서 2,420바이트의 서명은 DNS 레코드 세트(RRset) 하나를 응답하는 데 필요한 페이로드가 일반적인 네트워크 프레임 단위를 완전히 초과하게 만듦을 의미한다. DNSKEY 레코드 세트 질의 시 전달되어야 하는 1,312바이트의 공개키와 이를 서명한 2,420바이트의 RRSIG 레코드, 그리고 기본 DNS 헤더와 질문 레코드를 합산하면 단일 응답 패킷의 크기는 손쉽게 4킬로바이트(KB)를 돌파한다. 이러한 암호학적 확장은 경량 UDP 질의응답을 전제로 수립된 DNS 전송 계층의 근간을 직접적으로 흔든다.

4. UDP 단편화와 TCP 폴백 — DNS 전송 계층의 병목 메커니즘

DNS는 태생적으로 연결 수립 오버헤드가 없는 비연결형 UDP(User Datagram Protocol)를 기본 전송 계층으로 채택했다(RFC 1035). 전통적인 표준 DNS에서 UDP 메시지의 페이로드 크기는 512바이트로 엄격히 제한되어 있었다. 이후 DNSSEC의 도입으로 서명 데이터가 유입되자, 클라이언트와 서버가 지원 가능한 UDP 버퍼 크기를 상호 협상할 수 있도록 확장 메커니즘인 EDNS(0)(RFC 6891)가 표준화되었다. 그러나 실제 인터넷 물리 환경에서 안전하게 통과할 수 있는 패킷 크기에는 물리적인 상한선이 존재한다.

이더넷(Ethernet)의 표준 최대 전송 단위(MTU, Maximum Transmission Unit)는 1,500바이트다. IPv6 환경에서는 최소 MTU가 1,280바이트로 규정되어 있으며, 터널링 프로토콜이나 헤더 오버헤드를 고려하여 DNS Flag Day 2020 및 관련 IETF 권고에서는 EDNS(0) 버퍼 크기를 1,232바이트(또는 1,400바이트)로 설정할 것을 강력히 권장한다. 만약 DNS 응답 패킷이 이 버퍼 크기를 초과하면 네트워크 계층에서 두 가지 분기 경로 중 하나가 강제된다.

  • IP 계층 단편화(IP Fragmentation): IP 패킷을 여러 조각으로 쪼개어 전송하는 방식이다(IPv4 RFC 791, IPv6 RFC 8200). 그러나 수많은 기업 방화벽, 가정용 공유기(NAT), 통신사 미들박스는 보안 정책상 첫 번째 조각이 아닌 단편화된 UDP 패킷을 비정상 트래픽으로 간주하여 무조건 폐기(Drop)한다. 이로 인해 심각한 패킷 유실과 타임아웃이 초래된다.
  • Truncated(TC) 비트와 TCP 폴백: 권위 DNS 서버는 응답 크기가 클라이언트의 버퍼를 초과할 경우 응답 메시지 헤더의 TC 비트를 1로 설정하여 반환한다. 리졸버는 TC=1을 수신하는 즉시 해당 질의를 완료할 수 없음을 인지하고, 동일한 질의를 TCP(포트 53)를 통해 처음부터 다시 시도한다(RFC 1035, RFC 9715).
  • 왕복 지연 시간(RTT)의 폭증: UDP 단일 왕복(1 RTT)으로 즉시 완료되던 이름 풀이가 TCP 3-Way Handshake(SYN → SYN-ACK → ACK)를 거치게 되면서 최소 2배에서 3배 이상의 왕복 지연 시간이 강제된다. 암호화 전송인 DoT(DNS over TLS)나 DoH(DNS over HTTPS)를 거칠 경우 TLS 핸드셰이크 오버헤드가 추가로 누적된다.
  • 서버 커넥션 자원 고갈: 상태를 보존하지 않는(stateless) UDP와 달리 TCP는 운영체제 커널의 소켓 버퍼, 송수신 큐, 파일 디스크립터(FD), 메모리 상태 테이블을 점유한다. 수천만 대의 단말이 동시다발적으로 TCP 폴백을 일으킬 경우 리졸버와 권위 서버 양측 모두 극심한 연결 고갈에 직면한다.

결국 ML-DSA-44의 2,420바이트 서명은 거의 100%의 확률로 1,232바이트 한도를 초과하므로, DNSSEC 검증을 수행하는 모든 질의에서 예외 없이 TCP 폴백을 유발하게 된다. 암호학적 안전성을 획득하는 대가로 30년 넘게 유지되어 온 고속 UDP 질의응답 아키텍처가 강제로 희생되는 병목 구조가 형성되는 것이다.

5. Cloudflare 트래픽 데이터로 본 DNS 전송 구조의 현실

그렇다면 실제 프로덕션 네트워크 환경에서 DNS 트래픽의 전송 계층 분포는 어떠한 상태인가? Cloudflare가 자사의 글로벌 애니캐스트 인프라 및 'Big Pineapple' 분석 플랫폼을 통해 집계한 실측 데이터는 인터넷이 여전히 얼마나 깊숙이 UDP에 의존하고 있는지를 정량적으로 증명한다.

Cloudflare의 발표에 따르면 공용 재귀 리졸버 서비스인 1.1.1.1로 유입되는 전 세계 쿼리의 약 85%가 전통적인 UDP 프로토콜을 통해 전달된다. DoH(DNS over HTTPS)나 DoT(DNS over TLS) 같은 최신 암호화 프로토콜과 일반 TCP 질의를 모두 합쳐도 1.1.1.1 기준 전체 트래픽의 15%에 불과하다. 한편 Cloudflare가 권위 네임서버 및 프록시를 포함한 전체 네트워크 서비스 전반에서 처리하는 모든 DNS 트래픽을 종합하더라도 UDP의 비중은 여전히 60% 수준을 유지하고 있으며, TCP, DoT, DoH를 아우르는 연결 지향 트래픽은 40% 수준에 머무른다.

이 수치는 포스트 퀀텀 DNSSEC의 전면적인 도입이 네트워크 인프라에 미칠 파급력을 가늠하게 하는 결정적인 근거다. 만약 내일 당장 전 세계 모든 도메인이 ML-DSA-44로 DNSSEC 서명을 교체한다면, 현재 1.1.1.1이 처리하는 트래픽의 85%를 차지하는 경량 UDP 질의들이 일제히 TC=1 응답을 받고 TCP 세션을 맺기 위해 쇄도하게 된다. 이는 글로벌 네임서버 인프라에 수십 배에 달하는 동시 접속 커넥션 유지 부하를 안겨주며, 중간 네트워크 장비의 세션 테이블을 순식간에 포화시킬 수 있다. Cloudflare가 권위 네임서버 전면 적용 대신 1.1.1.1 리졸버 검증부터 단계적으로 출시한 근본적인 배경이 여기에 있다.

6. 다운그레이드 공격 방어 — 1.1.1.1 검증 정책과 RFC 트레이드오프

포스트 퀀텀 암호 전환기에는 고전 암호(ECDSA, RSA)와 포스트 퀀텀 암호(ML-DSA)가 공존하는 과도기적 하이브리드(Hybrid) 배포 모델이 불가피하다. 그러나 이 다중 알고리즘 운영 환경은 심각한 보안 맹점을 야기한다. 바로 다운그레이드 공격(Downgrade Attack)이다.

전통적인 DNSSEC 유효성 검증 표준인 RFC 4035와 RFC 6840은 한 존이 여러 알고리즘으로 다중 서명된 경우에 대한 검증 규칙을 규정하고 있다. 표준 명세에 따르면, 재귀 리졸버는 자신이 지원하는 암호 알고리즘 중 적어도 하나의 유효한 서명 사슬만 성공적으로 검증하면 해당 DNS 레코드 세트 전체를 안전한 것(Secure)으로 판정하고 클라이언트에게 검증 완료를 나타내는 AD(Authentic Data) 플래그를 세팅하여 응답한다. 이 규칙은 알고리즘 전환기 호환성을 위해 제정되었으나, 양자 공격자 모델에서는 치명적인 구멍이 된다.

양자 컴퓨터를 보유한 공격자가 네트워크 경로를 장악했다고 가정해 보자. 도메인 운영자는 양자 공격을 방어하기 위해 존을 ECDSA P-256과 ML-DSA-44 두 가지로 동시에 서명해 두었다. 그러나 공격자는 중간에서 패킷을 가로채 2,420바이트 크기의 ML-DSA-44 서명(RRSIG)을 패킷에서 완전히 제거하거나 깨뜨리고, 쇼어 알고리즘을 이용해 ECDSA 서명을 위조하여 리졸버로 보낸다. 기존 RFC 6840 규칙을 기계적으로 따르는 리졸버라면, 비록 ML-DSA 서명이 누락되었더라도 남아 있는 ECDSA 서명이 정상적으로 검증되므로 이 조작된 응답을 합법적인 것으로 수용하고 만다.

Cloudflare는 1.1.1.1 리졸버를 설계하면서 이 구조적 결함을 차단하기 위해 표준 규격을 엄격하게 재해석한 보안 정책을 수립했다. 만약 특정 도메인이 DNSKEY 및 DS 레코드 세트를 통해 포스트 퀀텀 알고리즘(알고리즘 18)을 지원한다고 선언한 상태라면, 1.1.1.1은 고전 서명의 검증 성공 여부와 관계없이 **반드시 적어도 하나 이상의 유효한 포스트 퀀텀 서명(ML-DSA-44)이 존재하고 완벽히 검증될 때만** 해당 응답을 안전한 것으로 승인한다. 만약 공격자가 포스트 퀀텀 서명을 탈락시키고 고전 서명만 남겨두었다면, 1.1.1.1은 이를 다운그레이드 공격으로 판단하여 클라이언트에게 DNS 질의 실패(SERVFAIL) 오류를 반환한다.

7. 실무 검증 절차 — dig를 이용한 ML-DSA-44 검증 테스트

인프라 엔지니어와 보안 실무자는 표준 DNS 진단 도구인 dig(Domain Information Grok) 명령어를 사용하여 Cloudflare 1.1.1.1이 실제로 ML-DSA-44 서명을 검증하고 있는지 손쉽게 검증해 볼 수 있다. Cloudflare는 이번 배포와 함께 전 세계 엔지니어들이 상호 운용성을 테스트할 수 있도록 포스트 퀀텀 전용 테스트 도메인인 dnstest.dev 존을 구축했다.

정상적으로 서명된 도메인에 대한 검증 질의는 다음과 같이 실행한다. +dnssec 플래그를 추가하여 리졸버에게 DNSSEC 유효성 검증을 수행하고 관련 RRSIG 레코드를 반환할 것을 명시적으로 요청한다.

# 1.1.1.1 리졸버를 통해 ML-DSA-44(알고리즘 18) 서명 검증 테스트
dig @1.1.1.1 valid.mldsa44.dnstest.dev +dnssec

# 서명이 유효하지 않은 도메인 테스트 (SERVFAIL 응답 확인)
dig @1.1.1.1 invalid.mldsa44.dnstest.dev +dnssec

첫 번째 명령어인 valid.mldsa44.dnstest.dev 질의가 성공하면 응답 헤더의 플래그 필드에 ad(Authentic Data) 플래그가 포함되어 반환된다. 이는 리졸버가 도메인의 RRSIG를 검증하기 위해 필요한 공개키와 신뢰 사슬을 끝까지 추적하여 성공적으로 수학적 검증을 마쳤음을 나타낸다. 응답 섹션에는 A 레코드와 함께 알고리즘 번호 18이 명시된 방대한 크기의 RRSIG 레코드가 출력된다.

반면 서명 데이터가 의도적으로 손상되었거나 위조된 invalid.mldsa44.dnstest.dev 도메인으로 동일한 질의를 수행하면, 1.1.1.1은 조작된 데이터를 클라이언트에게 노출하지 않고 즉시 status: SERVFAIL(Server Failure) 코드를 반환한다. 이는 위조 서명을 수신한 리졸버가 클라이언트를 보호하기 위해 이름 풀이를 단호하게 차단하는 정상적인 보안 메커니즘이 포스트 퀀텀 알고리즘 환경에서도 정확히 작동하고 있음을 입증한다.

8. 권위 DNS 서버와 등록처(Registrar)의 과제 — 남은 병목들

1.1.1.1 리졸버의 검증 개시는 중요한 마일스톤이지만, 이것만으로는 일반 도메인 소유자가 자신의 서비스에 포스트 퀀텀 DNSSEC을 도입할 수 없다. DNSSEC이 종단 간 안전하게 작동하기 위해서는 재귀 리졸버뿐만 아니라 도메인의 원본 데이터를 관리하는 권위 네임서버(Authoritative DNS Server), 그리고 상위 존에 DS 레코드를 등록해 주는 도메인 등록처(Registrar)와 최상위 도메인 레지스트리(Registry)가 모두 알고리즘 18을 지원해야 하기 때문이다.

현재 인터넷 생태계가 마주한 가장 큰 병목은 권위 DNS 서버의 연산 부하와 등록처의 지원 공백이다. 리졸버는 이미 생성된 서명을 검증(Verify)하는 연산만 수행하므로 상대적으로 연산 부담이 적다. 그러나 권위 네임서버는 도메인 레코드가 변경되거나 만료 기간이 도래할 때마다 거대한 격자 수학 연산을 수행하여 서명을 생성(Sign)해야 한다. 특히 수백만 개의 존을 실시간으로 관리하는 대형 클라우드 DNS 제공업체에게 ML-DSA-44 서명 연산은 막대한 CPU 코어와 전력을 소모시키는 확장성 문제를 던진다.

  • 등록처(Registrar)의 DS 레코드 등록 인터페이스 부재: 일반 기업이나 도메인 소유자가 도메인 관리 콘솔에서 DNSSEC을 켤 때, 대다수 등록처 시스템은 알고리즘 번호 18을 알지 못하거나 유효성 검사 규칙에서 입력 자체를 거부한다.
  • TLD 레지스트리의 EPP 프로토콜 미지원: 최상위 도메인(.com, .net, 국가 도메인 등)을 운영하는 레지스트리와 등록처 간 통신에 쓰이는 EPP(Extensible Provisioning Protocol) 확장에 새 알고리즘 규격이 조속히 반영되어야 한다.
  • 자동화된 키 롤오버(Key Rollover) 운영의 복잡성: 대형 서명과 키 크기 때문에 롤오버 기간 동안 신구 서명이 존에 동시에 게시되면 DNS 응답 크기가 10KB를 넘어설 수 있어 네트워크 불안정 위험이 배가된다.

9. 점진적 전환과 2029년 로드맵 — 인프라 엔지니어가 준비할 것

Cloudflare는 이번 리졸버 검증 지원을 시작으로, 권위 네임서버에 대한 ML-DSA-44 서명 기능 탑재와 자사 등록처(Cloudflare Registrar)의 알고리즘 18 DS 지원을 단계적으로 확대해 나갈 방침이다. Cloudflare가 공표한 전면적인 포스트 퀀텀 마이그레이션 완성 목표 시점은 2029년이다. 아직 시간이 남아 있는 것처럼 보이지만, 전 세계 수억 대의 라우터와 방화벽, 네임서버 설정을 점진적으로 개선해야 하는 인프라 생태계의 호흡을 고려하면 결코 여유로운 일정이 아니다.

사내 인프라와 서비스 네트워크를 책임지는 엔지니어들은 지금부터 다음과 같은 전송 계층 및 보안 설정을 점검하고 개선해 나가야 한다. 포스트 퀀텀 암호화로의 전환은 단순히 암호학 라이브러리를 업데이트하는 소프트웨어 패치 수준을 넘어 물리적 네트워크 토폴로지와 방화벽 방침을 재정의하는 작업이기 때문이다.

  • TCP 포트 53 개방 상태 전수 조사: 사내 방화벽이나 클라우드 보안 그룹(Security Group)에서 외부 네임서버와의 53번 포트 통신을 UDP로만 제한하고 TCP를 차단해 둔 환경이 여전히 흔하다. TCP 53 아웃바운드 및 인바운드가 차단되어 있으면 포스트 퀀텀 서명 질의 시 100% 장애가 발생한다.
  • EDNS(0) 버퍼 크기 및 MTU 클램핑 최적화: 네트워크 장비와 VPN 게이트웨이에서 잘못된 패킷 단편화 설정으로 인해 1,232바이트 이상의 대형 DNS 패킷이 드롭되지 않도록 인터페이스 MTU 및 MSS 설정을 사전에 조정해야 한다.
  • 암호화 연결형 프로토콜(DoT / DoH) 도입 가속: 대용량 패킷으로 인한 단편화와 TCP 폴백 오버헤드를 근본적으로 해결하기 위해, 처음부터 지속적인 연결을 전제로 설계된 DoH 또는 DoT를 사내 리졸버 인프라의 표준으로 채택하는 방안을 적극 검토해야 한다.

10. 확인하지 못한 것

  • 글로벌 PoP별 TCP 폴백 전환 시 실제 측정된 평균 RTT 지연 시간의 구체적인 밀리초(ms) 단위 수치 및 대륙별 성능 편차 데이터는 공개되지 않아 확인하지 못했다.
  • .com, .net 등 주요 gTLD 및 ccTLD 레지스트리 운영 주체들이 EPP 프로토콜 상에서 알고리즘 18 DS 레코드를 공식 수용하기로 확정한 구체적인 로드맵 일정은 명시되지 않아 특정할 수 없었다.
  • BIND, Unbound, PowerDNS 등 주요 오픈소스 네임서버 프로젝트들이 ML-DSA-44를 기본 활성화 옵션으로 탑재할 공식 안정화 릴리스 버전 번호 및 배포 타임라인은 원문에 언급이 없어 확인하지 못했다.
