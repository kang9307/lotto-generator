What goes in and what comes out

Archify is a skill that is installed into an agent. The first sentence of the README says it turns anything you want to understand, plan or share into an interactive visual. It is not limited to system diagrams and also showcases cases such as a travel itinerary and a learning map, but the GeekNews introduction and this article are concerned with making system diagrams from code and descriptions. The essence is a division of labor: a person does not operate a drawing tool, the agent writes the source of the picture, and a renderer turns that source into a screen.

Input comes in three forms. The first is a description of a system put into words. The README example is a single sentence: a browser calls an API, the API checks Redis, and on a cache miss it queries PostgreSQL and fills the cache. The second is a repository. The agent can be asked to read one and produce an evidence-backed architecture diagram, and the README states that a repository is not required. The third is a follow-up request that refines a diagram already produced: add Redis, move auth to the left, highlight the rollback path. The README says Archify keeps the typed source available, so only the named part is changed.

The outputs divide as follows.

  • A single HTML file. Node details and path exploration are inside the file, so the recipient opens it in a browser without installing Archify. Only external sites and map links need a network.
  • A typed JSON intermediate representation. Every renderer-backed mode has a schema, and the README explains that the same source can rebuild the same result.
  • Image and video exports. PNG can be copied to the clipboard, and static or motion formats can be downloaded. The GeekNews introduction mentions PNG, SVG and WebM.
  • Share cards. A traced route or reach can be downloaded as a 1200x630 PNG, with the full diagram retained as context.
  • A comparison view. Architecture Delta, which compares before and after snapshots, is a separate mode.

The angle of this article compresses into two questions. When an agent reads code and builds a picture, what is handled automatically, and what must the person who receives the result check by hand? Adjacent topics that have already been covered are not repeated. The approach of applying visual rules as post-processing is in the article on the Diagram Design skill, and the approach of combining static analysis with an LLM to extract architecture is in the article on CodeBoarding. Archify differs from both in that JSON written by the agent's own judgment is passed through validation gates, so what those gates guarantee, and what they do not, is the point worth reading.

Install and invoke — only the commands in the README

Installation is one npx skill-install command by default. Cursor, Claude Code, Codex CLI and OpenCode are listed as supported. The two lines below are the commands the README prints as they are: the first is the default install, and the second tries the skill without installing it.

npx skills add tt-a1i/archify -g
                    npx skills use tt-a1i/archify@archify --agent codex

For Cursor, the README lists a separate explicit form that installs without interactive questions. That command specifies the skill name, the agent, a global install, copy mode and confirmation skipping as options. Invocation is natural language, not a command. Ask the agent to use Archify to draw a diagram, which is the README's first example sentence, and then continue the conversation by asking to add authentication, highlight the cache-miss path, or switch to the light theme.

The install location differs per agent. Summarizing the README table:

  • Claude Code. ~/.claude/skills/ or the project's .claude/skills/. The whole renderer and validation workflow runs.
  • Codex CLI and opencode. Each has its own skills directory, and the table states the same full workflow.
  • Claude.ai. Upload archify.zip under the skills item in settings. What works depends on whether Node.js can be used in the sandbox, as the README states.
  • Project Knowledge. Uploading the same zip gives a prompt-driven architecture fallback, which differs from the path that uses the renderer and validation workflow.

The last two items matter most in practice. The renderer and validators run on Node.js, so in an environment where Node cannot be executed, the very validation stage that Archify promises is missing. Having installed the skill and having the validation procedure actually run are separate facts, and that gap returns as an item for a person to check in the table later. The README also lists community integrations for Hermes Agent and DeepSeek Harness, each marked opt-in with the caveats that they are not official products and carry no telemetry.

Five diagram types and what to put in the prompt

Archify divides diagrams into five kinds. Choosing the kind is the first step of the skill procedure, and because what the user writes in the prompt governs the accuracy of the result, the README states what to include for each kind.

TypeSuited forPut in the prompt
ArchitectureComponents, services, storage, boundariesScope, core components, primary path
WorkflowCI/CD, approvals, tool calls, runbooksParticipants, order, branches, exceptions
SequenceAPI calls, cache fallback, auth, async tracesCallers, callees, returns, timing
Data FlowPipelines, lineage, PII, consumersSources, transforms, stores, boundaries
LifecycleStates, retries, waits, terminal outcomesStates, events, retry and cancellation paths

Look at the right-hand column. The items listed as what to put in the prompt are, in effect, the list of facts that will appear in the picture. Even when the agent works things out from code, a person who fixes the scope and the core components beforehand narrows the picture. The README repository-analysis example turns this principle directly into a sentence.

Analyze this repository, then use archify to create a high-level runtime architecture diagram.
                    Show 8–12 core components, one primary path, external dependencies, and trust boundaries.
                    Put supporting detail in cards instead of adding more edges.

This example asks for three things. It limits components to between eight and twelve, keeps a single primary path, and puts supporting information on cards rather than adding lines. The limit is meant to make the picture readable, but it has another meaning for a person. A component that did not fit within twelve is missing from the picture, and the fact that it is missing is not shown in the picture. Only the person who set the scope knows what was left out.

  • Writing the name and boundary of the system in the scope sentence makes it easier for the skill to decide what to include.
  • Pinning down one primary path pushes the rest into supporting detail so that lines do not tangle.
  • Trust boundaries and external dependencies may be absent from the picture unless requested, so stating them is the safer course.

The generation flow — JSON intermediate form and validation gates

The most distinctive part of Archify's structure is that it writes JSON instead of a picture. Combining the README explanation and the skill definition, the flow is as follows.

  1. Identify the type. Decide whether the request is architecture, workflow, sequence, data flow or lifecycle.
  2. Read the schema and example. Read the schema and the example for that type in portions.
  3. Author a candidate JSON. The agent writes a complete candidate JSON directly. The skill definition says that no count of nodes, relationships, sources, views, cards or boundaries is a target or a ceiling, and that no preliminary sketch or prose coordinate plan should be made.
  4. Finalize. Validation and delivery run in one command. The skill definition states that a passing run means the validate, deliver, strict check and real-browser check gates passed.
  5. Repair failures. If a gate fails, edit the JSON and run it again. The chances to correct are limited to two rounds.

The delivery stage is atomic. A candidate is rendered into the same directory and checked, and only a passing result replaces the existing output atomically. As a result a wrong file cannot overwrite the last good version halfway through a save. The README lists the checks as schema, layout, HTML/SVG, routes and the clearance between labels and routes. With the repository commands, validation and delivery can each be run as follows.

cd archify
                    node bin/archify.mjs validate workflow examples/agent-tool-call.workflow.json --quality showcase --json
                    node bin/archify.mjs deliver workflow examples/agent-tool-call.workflow.json /tmp/workflow.html --quality showcase --open --json

The failure format is also fixed. validate --json and deliver --json emit one JSON object containing only stable rule codes, the subject in question, measured evidence and supported repair controls. The agent is meant to apply only the supported fixes attached to each diagnostic, and the skill definition forbids claiming success on a non-zero exit code and claiming a visual inspection without actual review captures. This is a device that ties the agent's report to machine output.

  • A validation failure comes out as a rule code and measured values, not a stack trace, so a retry becomes a designated repair rather than a guess.
  • The optional preview opens only on a random port of 127.0.0.1, and the screen refreshes only when the latest candidate passes every gate.
  • Motion effects are turned on only when requested, and the default output is static.
  • The README states that visual review is separate from the automatic checks.

Evidence for a diagram drawn from code — SRC n and a pinned commit

When a diagram is drawn from a repository, the biggest question is where in the code each box corresponds. The README handles this as an optional source-evidence feature. It is turned on only when requested, and when it is on, evidence-backed architecture nodes carry a mark reading SRC n and open the file and line range pinned to one public commit. The README explains that the file locations are Git-verified. Ordinary results that were not requested stay free of sources.

As a real case the README cites the public repository mco-org/mco. It traced the repository at commit 9f1a1cf, drew its runtime architecture, and presents the result as a checked map. The resulting HTML and the typed JSON source are published together in the repository documentation directory, so the picture can be compared with its source. What to read from this case is that the result is bound to a specific commit. When the code changes, the picture is a fact about that commit and does not update itself.

What the evidence mark guarantees must be distinguished precisely. SRC n opens the file and line range that a node refers to. Whether that range supports the node description, and whether a relationship is a real call path, can be known only when a person opens and reads it. The existence of evidence and the suitability of evidence are different layers, and automation helps with the first and leaves the second to a person.

  • For a marked node, open the file it points to and read whether it matches the description.
  • Treat an unmarked node as drawn without evidence and ask for its source.
  • Check the difference between the pinned commit and the current branch. The picture is a snapshot of that commit.
  • The person who wrote the prompt records which components were dropped in a picture reduced to eight to twelve.
  • External dependencies and trust boundaries exist in the picture only to the extent the prompt asked for them.

What is automated and what a person must check

The gist of the table is that automation is strong in form and reproducibility and hands the truth of the content to a person. The validation gates prove that the picture is not broken, and they do not prove that the picture is right. This is not a defect but a line the documents draw for themselves. It is why the skill definition keeps visual review separate from the automatic checks, and why the README attaches a note to the reach export that it does not claim runtime impact.

  • That a picture came out looking good has a bearing on passing validation but none on agreement with the code.
  • The exit code and the diagnostic JSON take precedence over a success report in the agent final response.
  • Drawing the same repository twice and comparing whether the node composition changes would reveal where judgment wavers. The source material for this article has no such reproduction result, so it is written only as a procedure worth trying.
  • Writing the base commit and the creation date next to the diagram title before sharing reduces the chance that a stale picture is read as current.
  • A picture that covers security boundaries or personal data flows goes through a separate review by the person in charge.

What the diagram does not say — authored relations versus runtime impact

One part that Archify visibly cares about is what its interactions claim. The README calls this truthful interaction. Focus, upstream and downstream reach, exact routes, role comparison and stories reuse only the nodes and relationships the author wrote, and they neither invent topology nor claim runtime impact. When a node is selected and downstream reach is switched on, the lines continuing below that node are highlighted, and that is the result of following the relationships written in the JSON. It is not a prediction of how far a failure actually spreads.

This distinction is tied directly to the attitude in which a person reads the picture. Seeing a node with a wide downstream highlight on screen and reading it as its blast radius means reading something the picture did not say. Whether an actual call is conditional, asynchronous or an unused path is not in the picture. The deployment-ownership profile shows the same attitude. It fails when any of the authored owners, region placement, private database scope or named boundary crossings is missing, it is never enabled implicitly, and the README says it does not inspect live infrastructure.

Change comparison follows the same principle. Architecture Delta compares validated Before, Delta and After snapshots together with a machine receipt, and lets a reader select an authored change or play one finite review. It does not infer impact, risk or merge safety. The comparison command is written in the README as follows.

node archify/bin/archify.mjs compare architecture base.json head.json architecture-delta.html --json

This command takes two JSON files as input. Because the two JSON files describe the structure at each point in time by a person or an agent, the accuracy of the comparison depends on the quality of the two descriptions. If this view is used in code review, it fits the line the document draws to use it for scanning changed facts quickly and not as grounds for an approval decision.

  • Reach is the result of following authored relationships and is not a prediction of runtime impact.
  • Route tracing shows the paths drawn in the picture, and it is not evidence that real traffic flows along them.
  • The deployment-ownership profile only prevents omissions in authored information and does not check agreement with real infrastructure.
  • The Delta view lists changed facts and does not assess risk.

What is left out of scope and how it behaves in operation

The README also states plainly what it does not do. Automatic Mermaid parsing, general-purpose auto-layout, hosted sharing and WYSIWYG editing are intentionally outside the current scope. It defines itself as neither a general-purpose drawing editor nor a Mermaid theme, but a tool that turns technical intent into a communication artifact. Layout, too, is not an automatic layout algorithm: the agent judges hierarchy, spacing, routes and emphasis, and only shared automatic endpoints are spread deterministically so that arrows do not pile onto one point. For a team that already holds Mermaid or draw.io assets, this means there is no function that reads them in directly, so the work of describing the existing assets again is needed.

Several operational properties are also written down.

  • Update check. It sends a GET request for a fixed stable manifest to show an optional reminder and never downloads or installs anything. A successful check waits about 24 hours, and failures are retried after 6 hours and then at 24-hour intervals. The server sees ordinary HTTP metadata such as IP and time but receives no version, agent, project data, prompts, or account and device identifiers, the README says. ARCHIFY_UPDATE_CHECK_DISABLED=1 turns off the networking and the writing of reminder state.
  • Language. meta.locale localizes the page title, legend, states and errors, accessibility text and the lang attribute of HTML/SVG, but it does not translate authored content. English and Simplified Chinese (zh-CN) are built in, and any other language falls back to English unless a translation table is supplied, with the fallback disclosed. A Korean-speaking user should expect the title and legend of the picture to appear in English.
  • Accessibility. Reader-driven motion is finite, follows the system reduced-motion setting, and is not part of the default exports.
  • Viewer controls. The question mark key opens help, slash finds a node, R traces a route, L compares roles, M opens the overview and F enters presentation mode. Link hashes can restore focus, relation, route and lens state.
  • Maintenance state. The repository version badge is 3.0.1, the license is MIT, and community integrations are stated not to be official products. A GeekNews comment reports that asking for a visualization during development gets it drawn by this skill, but it is one person's experience and cannot serve as evidence of performance.

In summary, a team adopting Archify decides three things: who reviews the pictures, how a base commit and date are attached to them, and whether to allow network behavior such as the update check. The design that can be read from the documents is a division of labor in which the tool validates form and a person validates content.

What could not be verified

  • Results of running the skill on an actual repository. This article covers only what the README, the skill definition and the introduction state, and there is no material measuring the accuracy of generated diagrams.
  • The details of the repository authoring procedure inside the full skill definition. Only the summarized rules are used as grounds.
  • The minimum Node.js version. In the README a version condition appears only in the community integration entries, and the condition for the base skill was not found.
  • The extent to which the validation procedure actually runs in a Claude.ai sandbox. The README says only that it depends on Node.js access.
  • The README statements about GitHub trending rank and press coverage. They rest on the author posts, so this article does not cite them as fact.
  • The exact GeekNews listing date. The page shows only a relative time.
