引言：文件名里只多了一个空格，参数就从三个变成五个

跑了好几年一直正常的整理脚本，某一天开始行为诡异。变的不是代码，是输入。有人上传了一个名叫 annual report.pdf 的文件。一个空格。从那一刻起，脚本以为的三个目标变成了五个，命令开始针对根本不存在的 annual 和 report.pdf 执行。如果那条命令是 rm，留下的就不是文件清单而是事故报告。

这不是缺陷，这是 shell 的设计。Shell 展开变量之后，会把结果再切成单词。第二个动作叫单词拆分，引号就是关掉它的开关。到这里为止是广为人知的。真正把人绊倒的在后面。"$@" 和 $@ 不同，"$*" 和 "$@" 又不同，"${arr[@]}" 和 ${arr[@]} 不同，而 IFS 在切的时候和拼的时候用的是两套规则。这六件事里搞混任何一件，参数边界就会塌。

本文专注于把这条边界变得可见。所有示例都用 printf '[%s]\n' 把每个参数装进方括号打印出来。有几个、在哪里断开，一眼就能看到。命令和输出都是在 GNU bash, version 5.2.37(1)-release 以及同一环境下的 dash 里实际跑出来的。

各类引号各自挡住什么，Shell 引号规则已经讲过，这里不重复。本文的主题是参数边界，而不是引号本身。值在进程边界上消失的问题由管道里的 while 为什么变量会消失负责，脚本无论怎样结束都要保证善后的问题由用 trap 确保临时文件被清掉负责。

请先读这一段再看示例。本文讨论的失误会真的删掉文件。在 files="annual report.pdf" 的状态下执行 rm $files，rm 收到的是 annual 和 report.pdf 两个参数。这两个名字里只要有一个真实存在，它就会被删掉。展开结果里混进 * 的话，波及范围还会更大。改动处理文件清单的代码时，把删除命令换成 echo 先跑一遍，用眼睛确认目标清单，然后再改回去。另外给 rm 和 mv 加上 -- 终止符，文件清单不要放进字符串而要放进数组，用 "${files[@]}" 展开。需要连带换行的名字一起处理，就用 find -print0 配 read -d ''。这三条后面都会逐个跑一遍确认。

1. 传进去三个，函数收到五个

造三个参数，用四种形式传给函数并计数。目标是两个带空格的文件名和一个普通名字。

#!/usr/bin/env bash
show() { printf '  count=%d\n' "$#"; printf '  [%s]\n' "$@"; }

f1() { show "$@"; }
f2() { show $@; }
f3() { show "$*"; }
f4() { show $*; }

set -- "annual report.pdf" "q3 data.csv" plain.txt

echo '--- "$@" ---'; f1 "$@"
echo '--- $@  ---';  f2 "$@"
echo '--- "$*" ---'; f3 "$@"
echo '--- $*  ---';  f4 "$@"
$ bash t1.sh
--- "$@" ---
  count=3
  [annual report.pdf]
  [q3 data.csv]
  [plain.txt]
--- $@  ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]
--- "$*" ---
  count=1
  [annual report.pdf q3 data.csv plain.txt]
--- $*  ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]

放进去三个，出来的个数是 3、5、1、5。守住原来个数的只有第一个。其余三个各自用不同方式弄塌了边界。

1.1 四种组合各做什么，一张表说清

形式结果单词数单词拆分通配展开用在哪里
"$@"3（原样）不发生不发生原样传参。事实上唯一的正确答案
$@5发生发生几乎没有用武之地
"$*"1（合并成一个）不发生不发生把参数打进一行日志时
$*5发生发生几乎没有用武之地

表里 $@ 和 $* 的结果看起来一样，这不是巧合。一旦去掉引号，两者的差别就消失了。未加引号的展开反正都会被 IFS 重新切一遍，于是「当初是怎么拼起来的」失去了意义。也就是说，讨论 $@ 与 $* 的差别，只有在加了引号时才有意义。

  • "$@" 展开成与参数个数相同的单词。参数为 0 个时单词也是 0 个
  • "$*" 永远正好是一个单词。参数为 0 个时仍然是一个空字符串
  • $@ 和 $* 结果相同。两者都要过 IFS 拆分和通配展开
  • 在把参数转交给其他命令的地方用 "$*"，参数会挤成一个送达
  • 要写一行给人看的日志时，"$*" 反而合适，比如 echo "执行: $0 $*"
  • $# 是位置参数的个数。上面运行中函数内打出的 3、5、1、5 就是这个值

1.2 for 循环里适用同样的规则

$ bash t12.sh
--- for 循环 ---
for x in "$@"
    [annual report.pdf]
    [q3 data.csv]
for x in $*
    [annual]
    [report.pdf]
    [q3]
    [data.csv]
for x in "$*"
    [annual report.pdf q3 data.csv]
不写列表的 for x 等同于 "$@"
    [annual report.pdf]
    [q3 data.csv]

最后一种形式值得记住。写成 for x; do ... done 而完全不写列表时，shell 会使用 "$@"。连漏掉引号的机会都不存在了。

2. Shell 在展开之后悄悄做的两件事

为什么会这样，看一看 shell 处理一行命令的顺序就清楚了。展开变量只是中间的一步，后面还有两步。

  1. 展开 — $var、${arr[@]}、$(cmd) 之类变成值
  2. 单词拆分 — 把刚才得到的值按 IFS 里的字符切成多个单词
  3. 路径名展开 — 每个单词里若有 * ? [ 就换成真实的文件名

用双引号包起来会跳过第 2 步和第 3 步。第 1 步照样发生。所以 "$var" 取出值的同时把它保持为一个单词。这一句话就是全文的摘要。

要紧的是第 2 步和第 3 步只对展开出来的值生效。直接写在脚本里的字面量不在其列。

$ bash -c 'show() { echo "count=$#"; }; show annual report.pdf'
count=2                # 两个字面量。本来就是两个

$ bash -c 'x="annual report.pdf"; show() { echo "count=$#"; }; show $x'
count=2                # 从变量出来之后被切开了

$ bash -c 'x="annual report.pdf"; show() { echo "count=$#"; }; show "$x"'
count=1                # 引号关掉了第 2 步
  • 中间那一行是事故的原型。在变量里还是一整块的值，到达命令时变成了两个
  • 命令替换 $(cmd) 的结果同样要过第 2、3 步。所以给 $(...) 加引号也是默认做法
  • 算术展开 $((...)) 的结果是数字，实务中很少出事，但规则本身相同
  • 赋值语句的右边是例外。x=$y 即使没有引号也不会被拆分，因为赋值本来就是接收一个单词的位置
  • case 的被测词和 [[ ]] 内部也不发生拆分。而旧的 [ ] 内部会。正因如此，x 为空时 [ $x = y ] 会报语法错误

3. IFS 既是切的刀也是粘的胶

IFS 做两件事，而两边的规则并不相同。不了解这种不对称，就没法预测改动 IFS 之后的结果。

3.1 拼接时只用第一个字符

#!/usr/bin/env bash
set -- alpha beta gamma
echo "默认 IFS   : [$*]"
IFS=,
echo "IFS=,      : [$*]"
IFS=
echo "IFS 空值   : [$*]"
unset IFS
echo "IFS 解除   : [$*]"
IFS=',;|'
echo "IFS=',;|'  : [$*]"
$ bash t3.sh
默认 IFS   : [alpha beta gamma]
IFS=,      : [alpha,beta,gamma]
IFS 空值   : [alphabetagamma]
IFS 解除   : [alpha beta gamma]
IFS=',;|'  : [alpha,beta,gamma]

最后一行是关键。IFS 里放了三个字符，插进元素之间的却只有第一个。把 IFS 设成空值则什么都不插直接接上，而 unset 会恢复默认的空白。空值和解除是完全不同的两种状态。

同一次运行里，把 IFS 改成冒号之后 "$@" 纹丝不动。

IFS=: 生效时 "$@" 依然原样:
  [alpha]
  [beta]
  [gamma]

3.2 切割时用到里面的每一个字符

#!/usr/bin/env bash
line="root:x:0:0:root:/root:/bin/bash"
show() { echo "  count=$#"; printf '  [%s]\n' "$@"; }
echo '--- 默认 IFS，不加引号 ---'
show $line
echo '--- IFS=: 不加引号 ---'
IFS=:
show $line
echo '--- IFS=: 但加了引号 ---'
show "$line"
$ bash t4.sh
--- 默认 IFS，不加引号 ---
  count=1
  [root:x:0:0:root:/root:/bin/bash]
--- IFS=: 不加引号 ---
  count=7
  [root]
  [x]
  [0]
  [0]
  [root]
  [/root]
  [/bin/bash]
--- IFS=: 但加了引号 ---
  count=1
  [root:x:0:0:root:/root:/bin/bash]

这里 IFS 正正经经地扮演了字段分隔符，把一行账户记录准确切成七个字段。可是在同样状态下加上引号，什么都没发生。IFS 只对未加引号的展开起作用。

3.3 改动 IFS 时要守的规矩

把 IFS 全局改掉，之后所有未加引号的展开都会受影响。有办法只让它对一条命令生效。

$ bash t13.sh
--- 保存再还原的写法 ---
old_IFS=$IFS; IFS=,; read -r -a parts <<< "alpha,beta,gamma delta"; IFS=$old_IFS
  3 elements
    [alpha]
    [beta]
    [gamma delta]
--- IFS=, read -a : 只对那一条命令生效 ---
  3 elements
    [alpha]
    [beta]
    [gamma delta]
  IFS after: $' \t\n'

第二种写法更好。像 IFS=, read -r -a parts 这样写在命令前面的赋值，只在那条命令运行期间有效。运行之后查看 IFS 仍是默认值。保存再还原的写法，一旦中途通过 return 或报错跳出就还原不了。

  • 默认 IFS 是空格、制表符、换行三个字符。上面输出里的 $' \t\n' 就是这个值
  • 这三个字符享受特殊待遇。连续的空白算作一个，首尾的空白被丢弃
  • 非空白的分隔符，比如冒号，就不一样。连续的冒号会产生空字段
  • 因此把 a::b 按 IFS=: 切开会得到三个字段，中间那个是空字符串
  • 逐行读文件时之所以写 while IFS= read -r line 把 IFS 清空，就是为了防止行首行尾的空白被削掉
  • read -r 里的 -r 让反斜杠不再被当作转义。读取路径时实际上是必需的

4. 去掉引号，字符串会变成文件名

比单词拆分名气小但更危险的是路径名展开。在有三个文件的目录里验证。

#!/usr/bin/env bash
# 这个目录里有 report.txt、notes.txt、archive.tar
pattern='*.txt'
show() { echo "  count=$#"; printf '  [%s]\n' "$@"; }
echo '--- 不加引号的 $pattern ---'; show $pattern
echo '--- 加引号的 "$pattern" ---'; show "$pattern"
echo '--- 开启 set -f 之后 ---'; set -f; show $pattern; set +f
$ bash t5.sh
files here: archive.tar notes.txt report.txt
--- 不加引号的 $pattern ---
  count=2
  [notes.txt]
  [report.txt]
--- 加引号的 "$pattern" ---
  count=1
  [*.txt]
--- 开启 set -f 之后 ---
  count=1
  [*.txt]

变量里装的值是 *.txt，命令收到的却是两个真实文件。存在变量里的字符串在抵达命令之前变成了别的东西。这个转换取决于文件系统当前的状态，所以同一段代码昨天和今天的行为会不一样。

4.1 数组元素里混进通配符，破坏会翻倍

$ bash t5.sh
--- 元素里带通配符的数组 ---
arr=('*.txt' 'literal name.txt')
  不加引号的 ${arr[@]}:
  count=4
  [notes.txt]
  [report.txt]
  [literal]
  [name.txt]
  加引号的 "${arr[@]}":
  count=2
  [*.txt]
  [literal name.txt]

两个元素的数组变成了四个。第一个元素被通配展开成两个，第二个元素被单词拆分成两个。因为两个阶段是按顺序作用的，破坏是相乘的。

  • 通配符一个文件都匹配不上时，bash 默认把模式字符原样留下。所以问题被发现得很晚
  • 开启 shopt -s nullglob 后，匹配不到时单词会消失。这变成另一种事故：参数整个不见了
  • shopt -s failglob 在匹配不到时报错。交互式下好用，脚本里则会造成意料之外的中断
  • set -f 只关闭通配展开，单词拆分照旧。上面运行中 [*.txt] 作为一个单词留下就是这个结果
  • 把 set -f 整个脚本开着，真正需要通配的地方就不起作用了。只在需要的区间开启，再用 set +f 还原
  • 根本的解法是引号。set -f 更接近于改不动别人代码时的应急手段

5. 数四种数组展开各自的元素个数

在位置参数上看到的四种组合，数组里原样存在，只是写法变了。

#!/usr/bin/env bash
arr=("annual report.pdf" "q3 data.csv" plain.txt)
count() { echo "  count=$#"; printf '  [%s]\n' "$@"; }
count "${arr[@]}"
count ${arr[@]}
count "${arr[*]}"
count ${arr[*]}
echo "元素个数: ${#arr[@]}"
echo "首元素的字符数: ${#arr[0]}"
$ bash t2.sh
--- "${arr[@]}" ---
  count=3
  [annual report.pdf]
  [q3 data.csv]
  [plain.txt]
--- ${arr[@]}   ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]
--- "${arr[*]}" ---
  count=1
  [annual report.pdf q3 data.csv plain.txt]
--- ${arr[*]}   ---
  count=5
--- 元素个数: 3 ---
--- 首元素的字符数: 17 ---

第 1 节的表原样适用。把数组当数组用的方式只有 "${arr[@]}" 一种。其余三种形式会把数组变成不是数组的东西。

最后两行也值得留意。${#arr[@]} 给出元素个数 3，${#arr[0]} 给出首元素的字符数 17。方括号里放什么，# 的含义就跟着变。

5.1 只写数组名得到的是首元素

$ bash t11.sh
arr=("a:b" "c d" "e")
  $arr        = [a:b]
  ${arr[0]}   = [a:b]
  ${arr[@]:1} = [c d e]

$arr 不是整个数组，而是 ${arr[0]}。因为它不报错，所以发现得很晚。只用一个元素的数组做测试，这个失误会一直藏到最后。养成在测试数据里至少放两个元素的习惯，能滤掉这一类缺陷。

5.2 IFS 对数组的未加引号展开同样起作用

$ bash t11.sh
arr=("a:b" "c d" "e")
--- IFS=: 且不加引号 ---
  count=4
  [a]
  [b]
  [c d]
  [e]
--- 同样状态下加上引号 ---
  count=3
  [a:b]
  [c d]
  [e]
--- "${arr[*]}" 用第一个 IFS 字符拼接 ---
  count=1
  [a:b:c d:e]

第一个结果很有意思。因为 IFS 是冒号，a:b 被切成两半，而 c d 里的空格已不再是分隔符，原样留了下来。改动 IFS，被切开的东西会整体换一批。

5.3 切片与稀疏数组

$ bash t11.sh
--- "${arr[@]:1:2}" ---
  count=2
  [c d]
  [e]
--- 删掉一个元素不会重新编号 ---
s=(zero one two); unset 's[1]'
  count=2  indices=0 2
  [zero]
  [two]
--- 用 declare -p 看真实形状 ---
declare -a s=([0]="zero" [2]="two")
declare -a arr=([0]="a:b" [1]="c d" [2]="e")

用 unset 删掉中间的元素后不会重新编号，而是留下一个洞。${#s[@]} 是 2，可有效的最大下标是 2。所以 for ((i=0; i<${#s[@]}; i++)) 这样的下标循环会在这种数组上漏掉元素。

  • 遍历数组请用 for x in "${arr[@]}" 而不是下标循环。它会自动跳过洞
  • 确实需要下标时，用 ${!arr[@]} 取真实存在的下标列表。上面输出的 indices=0 2 就是它
  • declare -p 连下标一起展示数组的真实形状。数组不对劲时应该第一个打印它
  • 切片 "${arr[@]:1:2}" 同样适用引号规则。去掉引号又会被切
  • arr+=("新元素") 是追加，arr=("新元素") 是整体替换。验证结果前者是 2 个，后者是 1 个
  • 关联数组必须先用 declare -A 声明。不声明就用字符串键，它会经过算术求值落到下标 0

6. 空字符串和换行的元素在哪里消失

造一个三元素、中间是空字符串的数组来验证。

$ bash t7.sh
--- 含空字符串元素的数组，${#arr[@]}=3 ---
  count=3
  [first]
  []
  [third]
--- 同一个数组不加引号 ---
  count=2
  [first]
  [third]

空元素消失得无影无踪。元素有三个，到达命令的只有两个。如果设计上把可能为空的可选设置值放进数组再交到命令行上，参数位置会整体错位，下一个参数落到不该去的位置。

$ bash t7.sh
--- 元素里含换行时，${#arr2[@]}=2 ---
  count=2
  [line1
line2]
  [tail]
--- 不加引号：换行也是 IFS 字符，所以被切开 ---
  count=3
  [line1]
  [line2]
  [tail]

换行是默认 IFS 里三个字符之一。所以含换行的文件名在未加引号的展开里会变成两个文件名。在 Linux 文件系统上给文件名放换行是不被禁止的。处理用户上传或解压结果的代码，真有可能碰上。

6.1 在 set -u 下展开空数组

$ bash t6.sh
bash 5.2.37(1)-release
--- set -u 状态下的 "${empty[@]}" ---
  OK, 展开为空: rc=0
--- "${empty[*]}" 不一样 ---
  count=1              # 冒出一个空字符串
--- 把 "${empty[@]}" 交给命令 ---
  count=0              # 完全没有参数
--- ${empty[@]:-默认值} 惯用法 ---
  [<默认值>]

在 bash 5.2.37 下，set -u 状态里把空数组按 "${empty[@]}" 展开没有报错，展开成了 0 个参数。这个行为是在 bash 4.4 变更的，据记载在此之前的版本会抛出 unbound variable 错误。这个环境里没有旧版 bash，未能复现。面向老发行版的脚本至今仍在用 "${empty[@]:-}" 这种防守写法。

同一份输出里 "${empty[*]}" 给出 count=1 值得注意。数组是空的，参数却冒出来一个——一个空字符串。这样交到命令手上，就不是「没有参数」而是「有一个空参数」，命令的行为随之改变。

7. 把命令输出装进数组的正确做法

在有两个文件的目录里比较四种方法，其中一个文件名带空格。

$ bash t8.sh
files: annual report.txt|notes.txt|
--- arr=($(ls)) ---
  3 elements
  [annual]
  [report.txt]
  [notes.txt]
--- mapfile -t arr2 < <(ls) ---
  2 elements
  [annual report.txt]
  [notes.txt]
--- readarray -t arr3 < <(ls) ---
  2 elements
--- arr4=(*) ---
  2 elements
  [annual report.txt]
  [notes.txt]
--- mapfile -d '' arr5 < <(find . -maxdepth 1 -type f -print0) ---
  2 elements
  [./annual report.txt]
  [./notes.txt]

只有第一种是错的。arr=($(ls)) 把命令输出直接送过单词拆分和通配展开。数组赋值括号内部是无法用引号包裹的位置。写成 arr=("$(ls)") 的话，输出整体又变成一个元素，数组的意义就没了。

  • mapfile -t 按行读取，-t 去掉行尾的换行。目标是行清单时这是基本写法
  • readarray 是 mapfile 的别名。同一个内建命令，验证结果也一致
  • 用 < <(cmd) 而不用管道是有原因的。写成 cmd | mapfile 会让 mapfile 跑在子 shell 里，数组出不来。和子 shell 那篇是同一个根源
  • 目标是文件名时，arr=(*) 最安全。Shell 亲自构造清单，任何名字都会落成一个元素
  • 不过 arr=(*) 在没有匹配时会得到只含 * 这个字符串的数组。要么配 shopt -s nullglob，要么用 [ -e "${arr[0]}" ] 检查
  • 要连带换行的名字一起处理，就用 mapfile -d '' 配 find -print0。空字符是唯一不能出现在文件名里的字符，用作分隔符很安全
  • mapfile 是 bash 4 以上的功能。必须退回 POSIX sh 的脚本用不了

7.1 遍历文件清单的两种方式

$ bash t10.sh
--- find -print0 + read -d '' ---
    got [./-rf]
    got [./annual report.pdf]
    got [./keep me.txt]
  total=3
--- for f in $(find . -type f) ---
    got [./-rf]
    got [./annual]
    got [report.pdf]
    got [./keep]
    got [me.txt]
  total=5

三个文件涨成了五个。用下面那种形式跑 rm，会对根本不存在的 report.pdf 和 ./keep 尝试删除，而这些名字的文件若真的存在就没了。上面那种形式的实际代码是这样。

while IFS= read -r -d '' f; do
    echo "处理: [$f]"
done < <(find . -maxdepth 1 -type f -print0)

用 IFS= 清空、用 -r 关掉反斜杠解释、用 -d '' 把分隔符换成空字符，这三件缺一不可。少一件就会在某些名字上崩掉。

8. 数组不会按值传进函数

试图把数组传给函数，到达的不是数组而是若干个参数。

$ bash t9.sh
--- 数组无法按值传递，会摊平成参数 ---
arr=("annual report.pdf" "q3 data.csv")
takes "${arr[@]}"
  inside: $1=[annual report.pdf]  $#=2
--- 在函数里重新组装成数组 ---
h() { local -a mine=("$@"); echo "  mine=${#mine[@]}"; }
  mine=2
--- 只传名字，用 nameref 接收 (bash 4.3+) ---
byref() { local -n ref=$1; echo "  ${#ref[@]} elements, first=[${ref[0]}]"; }
byref arr
  2 elements, first=[annual report.pdf]
--- local -a 不污染全局 ---
  inner has 2
  inner outside: [<unset>]
--- set -- "${arr[@]}" 换进位置参数 ---
  $#=2
  [annual report.pdf]
  [q3 data.csv]

三种办法各有各的位置。

  • 按参数接收再重建数组。一行 local -a mine=("$@") 就够。最简单，可移植性也最好
  • 缺点是只能传一个数组。要传两个就得插入充当分隔符的参数之类的绕行方案
  • 只传名字，用 nameref 接收。local -n ref=$1 直接指向原数组，函数里改动外面也能看到
  • nameref 需要 bash 4.3 以上。而且形参名与传入的数组名相同会引发循环引用错误，所以有加前缀而不用 ref 这类常见名字的惯例
  • 换进位置参数。set -- "${arr[@]}" 之后 "$@" 就是那个数组。这是在 POSIX sh 下也能走通的唯一办法
  • 不过它会覆盖原有的位置参数。之后还要用的话先存到另一个数组里
  • 用 local -a 声明的数组在函数外看不到。上面输出里的 <unset> 就是这个确认
  • 不加 local 在函数里建数组会变成全局的，会和使用同名变量的其他函数悄悄冲突

8.1 原样转发参数的包装脚本

$ bash t13.sh
good: wrapper_good() { inner "$@"; }
  inner sees 2 arg(s):
    [annual report.pdf]
    [q3 data.csv]
bad:  wrapper_bad()  { inner $@; }
  inner sees 4 arg(s):
    [annual]
    [report.pdf]
    [q3]
    [data.csv]
--- 转发时在前面加选项 ---
wrapper_opt() { inner --dry-run "$@"; }
  inner sees 2 arg(s):
    [--dry-run]
    [annual report.pdf]

包装脚本是这个失误出现得最频繁的地方。给 docker 或 kubectl 前面加两三个选项做一层薄包装时，如果在最后一行的 "$@" 上漏掉引号，一旦传入带空格的参数就会静悄悄地坏掉。平时测试用的参数没有空格，所以显不出来。

9. 拼装选项时有时无的命令行

要造一条选项随条件变化的命令时，用字符串拼一定会坏。数组正是为这个问题而存在的。

#!/usr/bin/env bash
opts=()
verbose=1
outfile="my output.log"
[ "$verbose" = 1 ] && opts+=(--verbose)
opts+=(--output "$outfile")
echo "${#opts[@]} args:"; printf '  [%s]\n' "${opts[@]}"
$ bash t12.sh
--- 用数组拼装 ---
  3 args:
    [--verbose]
    [--output]
    [my output.log]
--- 用字符串拼装 ---
optstr="--verbose --output $outfile"
  命令实际收到的:
    [--verbose]
    [--output]
    [my]
    [output.log]

字符串那边的文件名裂成了两片。命令读成 --output my，再把 output.log 当成另一个位置参数收下。能报个错还算走运，多数情况下会生成一个叫 my 的文件。

9.1 条件参数的空字符串陷阱

$ bash t12.sh
flag=""
probe "$flag" other           ->  got 2 arg(s)
probe ${flag:+"$flag"} other  ->  got 1 arg(s)

即使值为空，"$flag" 也会造出一个空参数。要做到完全不传参数，就用 ${flag:+"$flag"} 这种只在有值时才展开的写法，或者干脆按条件往数组里添加，这样读起来更清楚。

args=()
[ -n "$flag" ] && args+=("$flag")
cmd "${args[@]}" other

9.2 以连字符开头的名字与终止符

$ ls -1
-rf
annual report.pdf
keep me.txt

$ ls -1 -rf          # 把 -rf 读成选项
.
..

$ ls -1 -- -rf       # -- 之后全部按文件名处理
-rf

名字以连字符开头的文件会被命令读成选项。这一点靠引号挡不住。引号只能阻止单词被拆开，而这个没被拆开的单词长得像选项这一事实照旧存在。上面的运行中，ls -1 -rf 被解释成 -r 和 -f 选项，列出的是当前目录而不是那个文件。

  • 解法是 -- 终止符。它后面的所有参数都被当作非选项处理
  • 对 rm -- "$file"、mv -- "$src" "$dst" 这类无法撤销的命令，当成习惯加上
  • 另一种办法是让路径以 ./ 开头。./-rf 就不再以连字符开头了
  • find 输出的路径以 ./ 开头，在这一点上很方便。第 7 节输出里的 [./-rf] 就是例子
  • 也有不支持 -- 的命令。那种情况下 ./ 的写法是唯一替代
  • 凡是把用户输入直接交给命令的地方，终止符应视为必需而不是可选

10. 没有数组的 shell 照样能安全传参

Shebang 写着 #!/bin/sh 的脚本在生产环境被 dash 执行是常事。开发机上 /bin/sh 指向 bash 的话，这个差别根本看不见。

$ dash -c 'arr=(a b c); echo "$arr"'
dash: 1: Syntax error: "(" unexpected

数组语法本身就不存在。可位置参数是有的，引号规则也和 bash 一致。

$ dash tp.sh
--- "$@" in POSIX sh ---
  count=3
  [annual report.pdf]
  [q3 data.csv]
  [plain.txt]
--- $@ in POSIX sh ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]
--- "$*" in POSIX sh ---
  count=1
  [annual report.pdf q3 data.csv plain.txt]

和 bash 完全相同的结果。所以即使没有数组，也能安全地处理一份清单：把它放进位置参数，用 "$@" 展开。

set -- "annual report.pdf" "q3 data.csv"
set -- "$@" "新加的文件.txt"     # 追加
for f in "$@"; do
    echo "处理: [$f]"
done
  • set -- "$@" "新项目" 相当于往数组末尾追加。可以一个一个地累积元素
  • $# 给出元素个数，作用等同于 ${#arr[@]}
  • shift 可以从前面逐个取出，这是当队列用的模式
  • 如果需要两份以上的清单，这个办法就到头了。那正是该在 shebang 里点名 bash 的时刻
  • local 是 POSIX 之外的扩展，但已确认它在 dash 下可用。它不是标准，所以并非所有 sh 都保证支持
  • mapfile、readarray、local -n、declare -p 全都是 bash 扩展。需要可移植性就这四个都别用
  • 把 shebang 明确写成 #!/usr/bin/env bash，是用数组的脚本的最低要求。留着 #!/bin/sh 还用数组，迟早会在别的机器上因语法错误而死

11. 要记住的惯用法有六个就够

把到此为止出现过的东西按安全形式和危险形式配对整理。

11.1 检查清单

  • 展开默认加双引号。去掉才是例外，去掉时把理由写在注释里
  • 清单放数组不放字符串。变成字符串的那一刻，边界信息就没了
  • 数组展开只用 "${arr[@]}"。星号形式只留给日志输出
  • 把命令输出转成数组时用 mapfile -t。不要用括号里的命令替换
  • 目标是文件名时直接用 shell 的通配。不要解析 ls 的输出
  • 给删除、移动、复制命令加上 -- 终止符
  • 改完逻辑后，把删除那一行换成 echo 跑一次，用眼睛看目标清单
  • 测试数据里务必放一个带空格的名字。本文所有缺陷都是靠这一件事暴露出来的
  • 可能的话用至少两个元素的数据试。一个元素永远暴露不出 $arr 这个失误
  • 必须改 IFS 时，用 IFS=, read ... 写在命令前面，只对那条命令生效
  • 逐行读文件时，照原样使用 while IFS= read -r line 这个形式
  • 用数组的脚本，shebang 明确写成 #!/usr/bin/env bash
  • 数组不对劲就用 declare -p 连下标一起打印。比猜快
  • 接上静态检查器，本文的失误大半能在提交前被拦下。未加引号的展开是它的招牌检出项

12. 没能验证的部分

把没能用运行来验证、只依据文档写下的项目集中列在这里。

  • bash 4.4 以下的 set -u 行为。关于把空数组按 "${arr[@]}" 展开会报错的说法，依据的是变更历史，这个环境里没有旧版 bash，未能复现。6.1 节推荐的防守写法依据的也是同一份文档
  • zsh 和 ksh 的数组行为。zsh 在未加引号的展开上不做单词拆分等等，规则本身就不同，但没有可运行的环境，未能确认。不要把本文的结论原样套到 zsh 上
  • busybox ash。最小容器镜像里常见的 shell，未能确认。第 10 节的 POSIX 结论在那里是否成立，还是在目标环境上跑一次更可靠
  • Linux glibc 环境。运行环境是面向 x86_64-pc-msys 的 bash 5.2.37 以及同环境的 dash。引号和拆分规则属于与文件系统无关的 shell 内部行为，出现分歧的余地不大，但涉及文件名的例子最好在目标环境上复现一遍
  • 超长数组的极限。参数个数与总长度存在内核侧的上限。在那个边界上 "${arr[@]}" 会怎样失败，没有测量
  • 关联数组的遍历顺序。declare -A 建的数组其键顺序据记载是未定义的，但本文没有用运行去触碰它
  • 不同区域设置下的通配字符范围。[a-z] 这类范围模式随区域设置行为不同的问题在本文范围之外，未作确认

FAQ

Q1. 是不是给所有展开都加上引号就行了

差不多是这样。实务中必须去掉引号的场合很少。需要去掉的情形是有意把一个字符串切成多个参数，可那种情况本来就该用数组。不过有几个位置即便没有引号也安全：赋值语句右边的 x=$y、[[ ]] 内部、case 的被测词。这些位置由 shell 保证不发生单词拆分。即便如此，还是建议一律加上。记住这些例外的成本，比多敲两个引号的成本大。而且在代码评审时，确认「全都加上了」比每次去验证「这里是安全的所以没问题」要快。

Q2. "$*" 什么时候用

要造一个给人看的字符串时。在日志里用一行记下「这条命令是带着这些参数执行的」是典型场景。实际跑一遍可以确认，"$*" 永远造出正好一个单词，元素之间用 IFS 的第一个字符拼接。反过来，在把参数转交给其他命令的地方绝对不要用。传进去三个参数，接收方收到的是一个。还有一点要注意：即便用于日志，原来的参数里有没有空格，在拼好的字符串里也分辨不出来。想把参数边界也准确保留下来，用 printf '[%s] ' "$@" 这样把每个参数包起来输出会更好。

Q3. 说数组赋值不能加引号是什么意思

意思是没有办法把 arr=($(cmd)) 里的整个括号用引号包住。写成 arr="($(cmd))" 得到的不是数组而是含括号的字符串，写成 arr=("$(cmd)") 则命令输出整体变成一个元素。数组赋值括号内部在结构上就是要过单词拆分的位置。所以解决办法是干脆不用这个语法。行清单用 mapfile -t，文件清单就像 arr=(*) 那样直接用通配。也有例外安全的情况：确信输出只有不含空格的记号、且不可能混入通配字符，那就没问题。只不过这份确信日后被推翻，正是事故的典型剧本。

Q4. 能不能把 set -f 在整个脚本里开着

那只是一半的解决，因为它只关掉通配展开而保留单词拆分。带空格的文件名问题原封不动。更糟的是，真正需要通配的地方，比如 for f in *.log 这样的行会不工作。实际跑一遍确认，在 set -f 状态下 *.txt 保持模式字符原样作为一个单词留下。倒也不是完全没有用武之地：改不动别人的代码但必须先挡住通配事故的情形，或者处理用户输入的短区间内开启 set -f、结束后用 set +f 还原，这样是能用的。根本的解决还是引号和数组。

Q5. 文件名里带换行的情况真的会发生吗

会。Linux 文件名里不能出现的字符只有空字符和斜杠两个，换行不在禁止之列。解压用户上传的压缩包，或者处理从别的系统搬来的数据，这样的代码真有可能遇上。验证可见，含换行的元素在未加引号的展开里会被切成两个，因为换行是默认 IFS 三个字符之一。要应付它，只能把分隔符换成空字符：用 find -print0 造清单，用 read -d '' 或 mapfile -d '' 接收。因为空字符是唯一不能出现在文件名里的字符，所以它是能用作分隔符的唯一选择。

结论：今天就改的三件事

第一，别再把清单装进字符串。把多个文件名放进一个字符串的那一刻，边界信息就没了，之后全靠 shell 用 IFS 猜着还原。猜错的那一刻就是事故。清单放进数组，用 "${arr[@]}" 展开。没有数组的 shell 就放进位置参数，用 "$@" 展开。验证结果表明，守住原来个数的只有这两种形式。

第二，把命令输出转成数组时不要用括号里的命令替换。在有两个文件的目录里，arr=($(ls)) 造出了 3 个元素的数组，而 mapfile -t 造出的正好是 2 个。目标是文件名的话，像 arr=(*) 那样直接用 shell 的通配更好，因为解析这一步整个消失了。

第三，给删除、移动命令加上 --，改完逻辑先用 echo 跑一遍。名字以连字符开头的文件靠引号防不住，实际确认到 ls -1 -rf 会把它读成选项而不是文件。删除无法撤销。用眼睛过一遍目标清单，花的时间是几秒钟。

最后一点。本文所有的缺陷，仅仅靠在测试数据里放一个带空格的名字就全部暴露了。下次写处理文件清单的代码时，往测试里加上一行 touch "annual report.pdf" 就行。现在看着运转正常的代码会在哪里崩掉，当场就能知道。
