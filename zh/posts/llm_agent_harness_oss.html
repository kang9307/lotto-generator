模型只输出文本 - 其余的一切都由框架层决定

调用工具、决定何时停止、判断失败是否重试，没有一件是模型的决定

2026-09-05 开发/基础设施

如果智能体删掉了一个文件，删掉它的并不是模型。模型做的只是生成了一段结构化文本，内容大意是用这些参数调用删除工具是合适的。读到这段文本并真的发出系统调用的，是它外面的那个程序。

这个区分看起来很琐碎，但凡运维过智能体的人都知道，绝大多数问题恰恰在这里分岔。同一个模型在一套工具上跑得好好的，换一处就把同一个查询重复十遍。在一个环境里失败的工具会被再调一次，在另一个环境里则立刻放弃。那些以换了模型行为就变了开头的报告，很多其实说的是包在模型外面那一层的契约变了。

那一层的名字叫框架层。下面要做的，是用各家文档里的原文字段确认框架层究竟是决定什么的地方，并逐项列出漏掉某个决定时会出现什么症状。框架介绍和横向比较不在这里讨论。在代码里该把智能体表达成什么形状，另在类、图与配置文件各自遮住了什么中处理过。

下文出现的字段名与默认值，全部取自 Claude API 文档、OpenAI 函数调用指南、Gemini API 类型参考、MCP 规范及其 JSON 模式文件的原文写法。工具调用的规格各家不同，同一家内部也会改版，因此把别人抄过的字段名再抄一遍，是这个主题上最常见的错误来源。

缘起 - 一个仓库把框架层这个词摆在了最前面

2026 年 9 月初，一个叫 TrueForge 的仓库被介绍到韩国开发者社区。介绍语是把 LLM 当作真正的智能体来运行的开源框架层。既不是 framework 也不是 library，而是把 harness 这个词摆在最前面，这一点值得留意。

该仓库的公开指标，截至 2026 年 9 月 5 日 04 时 22 分 UTC，如下所示。星标 5,221、复刻 374、未关闭议题 91、提交约 515 次、贡献者约 31 人，语言为 TypeScript，许可证为 MIT，仓库创建于 2026 年 7 月 23 日，最后一次推送是前一天的 9 月 4 日。带标签的发布中最新的是 8 月 27 日的 @truefoundry/trueforge@0.2.0-rc.0 系列，四个 npm 包都还处在 1.0 之前的候选发布阶段。README 要求 Node 22.14 以上。

星标数不是成熟度。创建六周就攒到五千是热度指标而非稳定性指标，0.2.0-rc 这个版本号和 91 个未关闭议题是同一时刻并列的事实。这些数字怎么解读留给各人，这里只借用该仓库自己给框架层划定的范围。其文档把框架层写成包裹在 LLM 外面、把它变成可靠的长时运行智能体的运行时层，并列出它的职责：规划、工具路由与执行、面向长任务的上下文管理、沙箱与人工审批这类安全边界，以及能跨越重连和重启存活下来的会话状态。

这份清单有意思的地方在于里面没有一项是模型做的。规划由框架层管理，工具路由、上下文、审批、状态也都是。那么模型做什么呢。

模型真正返回的东西 - 文本与停下的理由

调一次模型 API，回来的东西有两样。内容块的数组，以及为什么停止生成。仅此而已。用不用流式、挂不挂工具，都不改变这一点。

挂上工具之后，那个数组里除了文本块还可能混进 tool_use 块。Claude API 文档写明这个块有三个字段：id、name、input。分别是稍后用来把调用与结果配对的标识符、要调用的工具名，以及符合工具定义中 input_schema 的参数对象。这里面没有任何执行。块到达的那一刻，文件还原封不动。

承载停止理由的 stop_reason，是框架层决定下一步做什么的唯一信号。每个取值要求的处理都不同，其中有几个特别容易漏掉。

stop_reason文档写的含义框架层要做的事
end_turn自然地结束了回答结束循环，直接使用结果
tool_use正在调用工具，等待执行结果执行工具、把结果送回，然后再次调用
max_tokens撞上请求里设定的上限被截断提高上限或让它续写。若有被截断的 tool_use 块，这一轮作废
stop_sequence出现了指定的停止字符串用 stop_sequence 字段确认命中的是哪一个
pause_turn服务端工具循环达到迭代上限，默认每次请求 10 轮把助手回复原样送回以继续。这与只回传工具结果不同
refusal拒绝作答。这不是错误而是正常的 200 响应从 stop_details 读出策略分类，转到备用路径
model_context_window_exceeded触到模型上下文窗口的上限而停下当作被截断的回复处理。这与 max_tokens 是两回事

这张表里实务上最常漏掉的是 pause_turn 和 model_context_window_exceeded。前者长得像 tool_use，处理方式却相反；后者若被当成 max_tokens，就会一次次做提高上限这种无用功。漏掉一个分支的框架层，在那个条件下看起来就像悄悄卡住了。

责任的边界 - 谁决定什么

这里一次性整理清楚更好。下表左列是运行智能体时必须有人来定的项目，中列说明这个决定实际发生在哪里，右列是没人去定时出现的症状。

决定项属于模型还是框架层没定时的症状

把右列竖着读下来，就是一份眼熟的故障清单。而这份清单里没有一项是换一个更好的模型就能解决的。最后一行尤其如此。Claude API 文档指出，工具结果常常来自网页、收到的邮件、用户上传、第三方 API 这类不受控的来源，因此要把它当作不可信内容，放进 tool_result 块里，而不是系统提示或普通的用户文本块。这是摆放位置的问题，不是模型能力的问题。

工具调用是请求而不是执行

说模型调用工具，这个表述本身造成了误解。实际发生的事更接近填一张申请单。模型生成一个写着工具名和参数的结构，然后就把这一轮结束掉。之后的一切都是外面的事。

处理这张申请单的过程中，框架层至少要做六个决定。

  • 名称解析 - 模型写的名字对应哪个真实函数。同名工具存在于多个 MCP 服务器时算哪一个
  • 参数校验 - 是否符合模式。不符合时是照样执行还是打回去
  • 权限判定 - 这个会话能不能调这个工具。是不是需要审批的等级
  • 执行环境 - 在框架层进程内跑，还是在隔离的沙箱里跑
  • 超时 - 等多久。MCP 规范要求客户端为工具调用设置超时
  • 结果加工 - 返回值很大时是原样塞进去，还是做摘要或写到文件里只放一段预览

最后一项对结果的影响尤其直接。把 300KB 的日志原样塞进上下文，从下一轮起模型就被这份日志压垮。只放预览，又可能把关键那一行切掉。无论选哪一边，模型看到的世界都是框架层编辑过的成品。工具挂多了之后选择本身崩坏的临界点以及收窄目录的办法，在工具最多能挂几个里处理过。

同一个概念，不同的字段

工具调用这个概念是共通的，契约却各家不同。这些差异会变成框架层代码里的分支，也是移植时出事故的地方。

表里第一眼扎人的是参数形态那一行。OpenAI 的 arguments 是经 JSON 编码的字符串，其余都是对象。就这一行，框架层里就多出一条解析失败的路径。模型吐出语法上损坏的 JSON 时，那不是工具失败而是参数解码失败，把这两者塞进同一条通道，重试策略就乱了。

结果放在哪里也分岔。Claude API 不设单独的 tool 角色，而是把 tool_result 块放进用户消息里，文档明确把这一点标为与其他 API 的差别。伴随而来的是不遵守就返回 400 的规则。工具结果块必须紧跟在对应的工具使用消息之后，而在承载结果的用户消息中，结果块必须排在数组最前面。把文本放在前面就会被拒绝。

工具定义不是免费的，这也是契约的一部分。Claude API 文档说明，挂上工具会自动插入一段启用工具使用的系统提示，其词元数随模型和 tool_choice 设置而异，并给出了表格。以 Claude Opus 5 为例，auto 或 none 时是 286 个词元，any 或指定某个工具时是 406 个。工具名、描述与模式的词元还要加在这之上。

失败怎么还给模型

工具会失败。问题在于这个失败以什么形状被模型看到，而这完全由框架层决定。各家规格替你定下的部分比想象中窄。

类别规格替你定下的框架层必须自己定的
Claude APItool_result 上的 is_error: true。文档建议写清哪里出错、下一步试什么措辞。只写失败，还是把可否重试与等待时间一并写上
OpenAI没有专用错误字段。output 的格式无论 JSON、错误码还是纯文本都交给调用方整套错误表达约定。让模型能区分成败的线索要自己造
GeminifunctionResponse 的 response 对象错误放在那个对象的哪个键里
MCP把协议错误与工具执行错误分开。不存在的工具和不合法参数走 JSON-RPC 错误，运行中的失败走结果里的 isError: true哪种失败走哪条路的判定标准

MCP 把这两者分开的理由可以直接搬进框架层设计。模型该看到的失败和模型不必看到的失败是两回事。调用一个不存在的工具是协议违规，是客户端该处理的问题。API 返回 429 则是模型应当知道的状况，因为那是它决定改用别的工具还是稍后重试的素材。

这里有一个常见的失误。把错误字符串原样塞进去。把整段调用栈倒进 content，上下文会被侵蚀，里面还可能混着内部路径或凭据片段。传引用而不是传值这个原则，在不把凭据交给智能体也能让它干活里另行处理过。错误也是同一个原则适用的地方。

并行调用 - 一个参数分开的东西

模型能不能在一轮里调多个工具。各家大体上允许，并提供关掉的办法。Claude API 把 tool_choice 里的 disable_parallel_tool_use 置为 true，一轮内的工具调用最多就是一个。OpenAI 把 parallel_tool_calls 置为 false，就恰好只会调用 0 个或 1 个。Gemini 在文档里写明并行调用与跨多轮的组合式调用都是原生支持的。

这一个开关会把框架层的结构改动很多。

  • 打开则延迟下降、往返次数减少。代价是框架层必须把多个结果全部收齐再回传，并要定好其中只有一个失败时怎么办
  • 开着并且放出有副作用的工具，顺序保证就消失了。读和写两个工具在同一轮发出时，谁先结束由框架层的执行方式决定
  • 关掉则追踪变容易、审批流程变简单。代价是同一个任务需要的模型调用次数增加，费用和时间都上去
  • Claude API 文档另行说明服务端工具与客户端工具落在同一个并行批次的情形。此时用户消息只能装结果块，在后面附上文本会让该轮提前结束并返回 400

重点不是哪一边更好，而是没做过这个选择的框架层，就是在用各家的默认值，而默认值各家不同。

换了模型行为就变了的真相

回到开头的观察。换模型之后智能体表现不同时，这个差异到哪里为止属于模型，从哪里开始属于框架层。

模型能力显然有影响。文档写道，必填参数缺失时 Claude Opus 更有可能意识到并反问，而 Claude Sonnet 可能会问，也可能填进一个看似合理的值。这类差异是真实存在的。只是在它之上还叠着契约的差异，而后者往往作用更大。

  • 工具模式的表达 - 同一个工具，描述文本差一行，被选中的频率就不同。各家适配器若截断描述或把模式压平，模型看到的东西就变了
  • 强制的级别 - 设成 auto 还是 required 是框架层配置而非模型配置。适配器映射得不一样，同一段提示就会有不同表现
  • 并行的许可 - 与上一节相同。在默认值不同的两家之间迁移，调用模式本身就变了
  • 错误的表达 - 用 is_error 告知失败的框架层，与只塞一段字符串的框架层，模型的恢复行为不一样
  • 上下文的裁剪 - 在什么时点摘要掉什么，如果不同，后半程的行为会整个改变
  • 系统提示的注入 - 光是挂上工具，各家就会自动插入一段系统提示，其内容与体量随厂商和设置而异

这在实务上只意味着一件事。要比较模型，就得把框架层固定住。把来自两个框架层不同的环境的数字称为模型性能比较，留下的是一个复现不了的结论。把验证本身自动化时机器判定的边界在哪里，在验证框架划出的界线里另行整理过。

停止条件 - 没人决定何时停下时

从这里开始是框架层必须定下的项目。不定并不意味着回落到某个默认值，而是没有限制被默默当成了默认值。

模型没有预算这个概念。每一轮，只要再调一个工具看起来更合理，它就会那么做。这个判断不把剩余费用或已用时间当作素材。测量这些的地方只在外面。

上限测量什么没有时的症状触发时做什么
最大步数模型调用的往返次数换着花样重复同一个查询。结果看上去正常中断，把已有进展摘要后交给用户
费用上限累计输入输出词元及其折算金额只能靠账单事后知晓中断，或降级到更便宜的模型
挂钟上限会话开始以来的实际经过时间用户就那样被晾着等回复输出部分结果，并询问是否继续
单工具调用次数同一个工具被调了几次循环只在一个工具里打转，总步数还有余量在本会话中封住该工具，并告知模型
无进展检测连续多少次是参数完全相同的调用步数在涨而状态原地不动把重复这一事实写进结果，逼它换条路

实务中更常见的问题不是死循环而是安静的浪费。二十步能做完的任务跑了八十步的智能体，因为最终答案是对的，谁也感觉不到异常。这个落差在加上运行记录之前根本浮不出来。自主智能体烧掉预算的极端案例，整理在AI 智能体的账单事故里。

失败的分类 - 哪些该再调一次

工具失败时框架层要回答两个问题。要不要再调一次，以及要不要告诉模型。这两者是分开的。

  • 瞬时失败 - 网络超时、502、429。由框架层安静地重试才对。设退避、设次数上限，都失败了再告诉模型。每次尝试都报给模型只会浪费上下文
  • 永久失败 - 404、认证被拒、资源不存在。重试也是同样的结果。立刻告诉模型，让它换条路才对
  • 参数错误 - 违反模式、缺少必填值、JSON 解析失败。这是模型唯一能修的一类。把缺了什么写回去。Claude API 文档说明这种情况下模型会补上信息重试两三次，然后向用户道歉
  • 策略拒绝 - 审批被否、权限不足。不属于重试对象，应当告知模型。但拒绝理由是否原样转达是另一个判断
  • 部分成功 - 十件里三件失败。最难处理。把整体视为失败，还是确认成功的部分只报失败的部分，各个工具都不一样

不做这个分类就会朝两个方向坏掉。全都重试，认证失败会重复二十次；全都交给模型，一次瞬时的 502 就让整个任务掉头。两者都不是因为模型不好才发生的。

幂等性 - 这是可以调用两次的工具吗

引入重试的那一刻就跟来一个新问题。这个工具可以调两次吗。付款、发信、建工单、部署，调两次就发生两次。第一次调用以超时结束，并不等于它没有执行。没收到响应和没有执行是两回事。

MCP 给工具留了一个声明自身性质的位置，就是 ToolAnnotations 的四个字段。不过模式文件里的说明把它们的地位钉得很死。

  • readOnlyHint - 为真表示该工具不修改环境。默认值为假
  • destructiveHint - 为真表示可能做破坏性更新，为假表示只做追加。仅当 readOnlyHint 为假时才有意义。默认值为真
  • idempotentHint - 为真表示用相同参数重复调用不会产生额外影响。同样仅当 readOnlyHint 为假时才有意义。默认值为假
  • openWorldHint - 为真表示可能与外部实体构成的开放世界交互。模式文件举的例子是网页搜索属于开放世界而记忆工具不是。默认值为真
  • 以及那句决定性的话 - ToolAnnotations 中的所有属性都只是提示，不保证如实描述工具行为。模式文件明确要求，不要根据来自不可信服务器的标注做出工具使用决策

默认值的朝向全都偏保守，这一点值得留意。没有任何标注的工具要被当作破坏性的、非幂等的、与开放世界交互的工具。而提示终究只是提示，重试安全归根结底只能由框架层在自己这一侧保证。办法是三选一：每次调用生成幂等键传给工具、重试之前先用查询确认状态，或者干脆把有副作用的工具排除在重试之外。最后这个选项最常是正解。

审批点 - 人介入的位置

MCP 规范出于信任与安全的理由写明循环中应当始终有一个能够拒绝工具调用的人，并向应用建议三件事：让人清楚看到哪些工具暴露给了模型的界面、工具被调用时的明确视觉提示，以及确认对话框。另有一条要求在调用服务器之前把工具输入展示给用户，以避免恶意或意外的数据外泄。

审批放在哪里是框架层的策略问题。位置大体是四者之一。

  • 按工具 - 特定工具一律审批。实现最简单，也最可预测
  • 按参数 - 同一个工具按参数分流。删临时目录自动放行，其他路径需要审批
  • 按累计 - 本会话已批过 N 次之后自动放行。能减轻审批疲劳，但界线会模糊
  • 按结果 - 执行但在落定之前停住。只有支持试运行的工具才成立

完全不设审批点，不可撤销的操作就会在无通知的情况下执行。反过来全都设上，人就开始不看内容直接点。用两个轴来分级的方法整理在权限设计与事故阻断线里，这里不再重复。从框架层的角度要补充的只有一点：等待审批的会话状态放在哪里。只放在内存里，一次部署就会把所有待办清空。

记录 - 用什么参数调了哪个工具

出了事故要回答的问题是固定的。用什么参数、在几点、因谁的请求、调了哪个工具，结果是什么。能回答这些问题的记录只有框架层做得出来。模型不记得自己调过什么，它只是把对话历史里留下的东西再读一遍。

MCP 规范建议客户端为审计目的记录工具使用，并在把结果交给模型之前先做校验。至少要留下的项目如下。

  • 调用标识符及其对应的结果 - 配对完整才谈得上事后重建
  • 工具名与参数全文 - 只留摘要在事故调查里没有用。但参数里可能含敏感值，因此要配一套掩码规则
  • 执行时刻与耗时 - 没有这两项就无从知道哪个工具是延迟的源头
  • 失败分类与重试次数 - 上一节的分类要落到记录里，才判定得了策略是否合适
  • 词元用量与累计费用 - 按步留存，才看得出哪一段贵
  • 上下文编辑历史 - 不留下被切掉了什么，就无法重建模型为何做出那个判断

最后一项最常缺席。摘要和裁剪是框架层悄悄做的事，往往不写进日志，结果就成了同样的输入再跑一遍也出不了同样的结果的状态。从词元浪费的角度解剖会话运行的方法在智能体黑箱分析里，在生产环境追踪失误的构成在LLM 可观测性实务指南里。

状态与上下文 - 裁剪时消失的东西

长任务会超出上下文窗口。此时框架层做的事叫裁剪。TrueForge 的文档把这项功能默认开启，触发条件定为模型上下文长度的百分之八十，不知道该值时则回落到五万输入词元。一并写下的那句话更重要：压缩在工作上下文里是有损的，而完整的会话历史仍可通过 API 查询。

这两句话包含了状态设计的核心。模型看到的和系统保存的是两样东西。前者是每次调用都重建的编辑版，后者是只追加的记录。把这两者当成同一样东西的框架层会朝两个方向之一坏掉。只有编辑版则事后无法重建，只有记录则超出窗口导致请求失败。

不同的裁剪方式失去的东西也不同。

  • 从旧的开始丢 - 实现最省事。失去的是早期的指示与约束条件。长任务后半程违反最初需求这个典型症状就出自这里
  • 用摘要替换 - 体量是降下来了，但摘要留下什么由另一次模型调用决定。在摘要这一步消失的信息回不来
  • 把大结果挪到外面 - 把工具返回值存成文件，只把预览放进去。模型需要时可以再读，所以损失小，但重读的调用会增加步数
  • 工具模式延后加载 - 先给名称和描述，模式等需要时再取。TrueForge 的文档写明这项功能的默认值是不预加载
  • 隔离到子智能体 - 把细节工作放到单独的上下文里跑，只把最终结果往上抬。随之新增的是传递损耗与协调成本，其边界在角色分工模拟的边界里另行处理过

无论采用哪种方式，模型都不知道自己忘掉了什么。因为被切掉的地方不会留下标记。所以裁剪策略必须是一项要被记录的内容。

把循环写成代码

把前面那些项目放到一条流程上，就是下面这个形状。以下不是某个特定 SDK 的 API，而是为了让决定点显形而写的骨架。实际字段名以上表中各家的契约为准。

// 框架层循环的骨架 - 决定点都加了注释
async function runAgent(task, tools, limits) {
  const messages = [{ role: 'user', content: task }];
  let steps = 0, spent = 0;
  const startedAt = Date.now();

  while (true) {
    // 决定 1: 停止条件。模型不会去测这些
    if (steps >= limits.maxSteps) return stop('MAX_STEPS', messages);
    if (spent >= limits.maxCost) return stop('BUDGET', messages);
    if (Date.now() - startedAt >= limits.maxWallClockMs) return stop('TIMEOUT', messages);

    const res = await model.call({ messages, tools, toolChoice: limits.toolChoice });
    steps += 1;
    spent += estimateCost(res.usage);
    record({ steps, usage: res.usage, stopReason: res.stopReason });  // 决定 6: 记录

    // 决定 2: stop_reason 分支。漏掉一个，在那个条件下就像卡住了
    if (res.stopReason === 'end_turn') return finish(res);
    if (res.stopReason === 'refusal') return handleRefusal(res);
    if (res.stopReason === 'max_tokens') return handleTruncated(res);
    if (res.stopReason === 'pause_turn') { messages.push(asAssistant(res)); continue; }

    const calls = res.content.filter((b) => b.type === 'tool_use');
    if (!calls.length) return finish(res);

    // 决定 3: 并行执行还是顺序执行
    const results = limits.parallel
      ? await Promise.all(calls.map(execute))
      : await runSequentially(calls, execute);

    messages.push(asAssistant(res));
    messages.push(asToolResults(results));   // 结果块必须排在数组最前面

    // 决定 4: 上下文触到阈值时丢掉什么
    if (estimateTokens(messages) >= limits.compactAt) await compact(messages);
  }
}

执行单个工具的那一段里装着审批和失败分类。下面 classify 返回的值决定是否重试，幂等键则防止副作用重复。

// 工具执行 - 审批、幂等性与失败分类都聚在这里
async function execute(call) {
  // 决定 5: 审批点。先把参数展示出来再问
  if (needsApproval(call)) {
    const verdict = await askUser(call.name, call.input);   // 待批状态放进持久化存储
    if (verdict !== 'allow') return toolError(call.id, 'POLICY_DENIED: 用户拒绝');
  }

  // 有副作用的工具，每次调用给一个跨重试固定的键。
  // 没有标注的工具当作破坏性且非幂等来对待
  const key = isSideEffecting(call) ? idempotencyKey(call) : null;

  let attempt = 0;
  while (true) {
    try {
      const out = await invoke(call.name, call.input, { key, timeoutMs: TOOL_TIMEOUT_MS });
      return toolResult(call.id, truncateOrOffload(out));   // 大结果挪到外面
    } catch (err) {
      const kind = classify(err);   // TRANSIENT / PERMANENT / BAD_ARGS / DENIED
      // 只有瞬时失败才安静重调。其余交给模型去判断
      if (kind === 'TRANSIENT' && key && attempt < MAX_RETRY) {
        await backoff(attempt++);
        continue;
      }
      return toolError(call.id, redact(summarize(err, kind)));   // 给摘要与掩码而非原文
    }
  }
}

自己做还是拿现成的

框架层看起来很薄。似乎一个循环加几个分支就够，实际上第一版半天就能出来。问题在于上面列举的那些项目本身就是框架层。把停止条件、失败分类、幂等性、审批、记录、上下文编辑、会话持久化全都放进去之后，它就不薄了。

判断的轴适合自己做的条件适合拿现成的条件
工具数量固定在三四个，没有增加的打算打算持续接入 MCP 服务器
副作用全都是只读的写入、付款、发送混在一起
运行时长在一次请求里就结束必须跨重连和重启延续下去
使用者只有做的人自己在用多人在用，谁做了什么必须留痕
厂商固定在一家要在多家之间往返，适配层反正躲不掉
审批流程不需要，或者全自动人会在中途介入，且那个状态必须活下来
记录要求标准输出就够了要求审计记录与费用拆解
运维余力一个进程就够有余力运维多副本和数据库

右列中了两条以上，自己做的成本就比看上去大。反过来左列全中，把别人的抽象搬进来反而是亏的。把多个智能体同时放进同一个仓库时产生的隔离问题，与框架层的选择又是另一条轴，在并行编码智能体的冲突与隔离里处理过。

回到引发本文的那个仓库，它文档里宣传的功能清单几乎与上表右列重合。把沙箱当作工具的做法、子智能体、工具模式的延迟加载、大结果卸载、压缩、工具审批、反问、生成式界面，以及本地模式的 SQLite 与托管模式的 Postgres 和 Redis。README 自己写道本地模式只供自己的机器使用，默认没有登录，不是面向生产或公网暴露的部署。文档里有没有这样一句话，本身就是引入判断的素材。

该仓库还公开了自测基准。取自 DevRev 的 Enterprise-Bench 的十四个任务，在同一个模型、同样三个 MCP 服务器、同一段系统提示下每种配置各跑三次，由另一个 LLM 评审打分，对手是一个闭源系统和一个开源项目。不过这项测量是项目自身完成的，并未同时给出第三方的复现结果。自测基准在公开了设置这一点上有其意义，但它与独立验证是两样东西。

未能确认的部分

  • Gemini 的函数调用文档里写法看起来有两套。类型参考描述的是 functionCall 与 functionResponse 部分承载 args 和 response 对象的形式，而指南页读起来则是 function_call 与 function_result 配 call_id 的形式。哪一套是哪个 SDK 版本的正本，仅凭文档分不出来，因此正文表格采用了类型参考的写法
  • Gemini 的 functionResponse 是否有专用的错误字段，在类型参考里没有找到。正文只写了放进 response 对象里
  • OpenAI 文档没有表示工具执行错误的专用字段，只说 output 的格式由调用方自定。模型被训练成以何种形态识别失败并不在文档里，因此错误表达约定的效果只能各自测量
  • Claude API 的 pause_turn 默认上限 10 轮是否能按请求调整，在该文档里没有找到明确说明
  • TrueForge 的重试策略、最大步数默认值、费用上限的配置位置，仅凭公开文档的目录标题无法确定。正文引用的只有像压缩阈值和延迟加载默认值这样文档里写出了具体数值的项目
  • 仓库指标是 2026 年 9 月 5 日 04 时 22 分 UTC 时点的值。星标 5,221、提交约 515 次、贡献者约 31 人这些数字与运维稳定性是什么关系，单凭这些值说不出来
  • MCP 规范要求客户端为工具调用设置超时，但没有给出推荐值
  • Claude API 文档中工具使用系统提示的词元数表按模型而异，但这些差异从何而来文档没有解释
