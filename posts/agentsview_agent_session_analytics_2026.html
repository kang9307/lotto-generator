AgentsView 출시 - Claude Code·Cursor·Codex 세션을 한곳에 모아 검색하고 비용을 추적하는 로컬 대시보드

여러 AI 코딩 에이전트를 병행 쓰는 시대, 세션 분산과 비용 불투명 문제를 로컬 우선 오픈소스 도구로 어떻게 푸는가

2026-07-14 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 에이전트는 늘었는데, 기억은 흩어졌다

2026년 지금, 개발자 한 명이 하루에 여러 AI 코딩 에이전트를 오가는 일은 예외가 아니라 기본값이 됐다. 어떤 설문은 개발자의 59%가 세 개 이상의 AI 코딩 도구를 병행한다고 보고했고, 65%는 최소 두 개를 매일 쓴다고 답했다. Claude Code로 리팩토링을 시키고, Cursor로 인라인 수정을 받고, Codex나 Gemini CLI, OpenCode로 별도 작업을 던지는 하루가 흔해졌다. 각 도구가 한 가지 일을 잘하기 때문에 생기는 자연스러운 분업이지만, 그 대가로 "어제 그 버그를 어떤 에이전트에게 어떻게 시켰더라", "이번 달 AI 도구에 실제로 얼마를 썼나" 같은 질문에 답하기가 오히려 더 어려워졌다.

이 틈을 파고든 오픈소스 프로젝트가 AgentsView다. hada.io에 2026년 7월 소개된 이 도구는 Claude Code·Codex·Cursor·Gemini CLI·OpenCode 등 여러 AI 코딩 에이전트가 로컬에 남기는 세션 로그를 한 곳에 모아 대화 검색, 토큰·비용 통계, 활동 분석, 파일 변경 추적을 제공한다. 이 글은 GitHub 저장소(kenn-io/agentsview)의 공개 문서를 근거로 이 도구가 실제로 무엇을 하는지 짚고, 여러 에이전트를 병행하는 시대에 이런 도구가 왜 필요한지, 로컬 수집이 갖는 프라이버시 의미, 유사 접근과의 차이, 그리고 실무 활용과 한계까지 2026년 7월 기준으로 분석한다.

1. AgentsView란 무엇인가 - 로컬 우선 세션 분석 대시보드

1.1 40개 이상의 에이전트를 하나의 색인으로

AgentsView가 인식하는 에이전트 목록은 짧지 않다. Claude Code, Codex, Cursor, GitHub Copilot CLI, Windsurf, Zed 같은 주요 도구부터 Devin CLI, OpenCode, Gemini CLI, DeepSeek TUI, Qwen Code 같은 특화 도구, Aider(저장소별 옵트인)·Forge·gptme·OpenHands·Kiro·Mistral Vibe 같은 비교적 덜 알려진 도구까지 40개 이상을 다룬다. 각 에이전트는 자기만의 세션 저장 경로를 갖는데(예: Claude Code는 ~/.claude/projects/), AgentsView는 이 경로들을 각각 파싱해 하나의 로컬 SQLite 데이터베이스로 합친다.

1.2 검색·비용·활동·변경, 네 갈래 기능

핵심 기능은 네 가지로 요약된다. 첫째, 통합 검색이다. FTS5 기반 전문 검색으로 여러 에이전트의 대화 내용을 한 번에 찾을 수 있고, 선택적으로 임베딩 엔드포인트를 연결하면 의미 기반 검색도 가능하다. 둘째, 토큰·비용 집계다. LiteLLM의 가격 데이터를 참조해 세션·모델별 토큰 사용량과 비용을 계산하고, 오프라인 폴백도 지원하며, 프롬프트 캐시를 반영한 비용 계산까지 다룬다. 파일을 매번 다시 파싱하는 방식보다 100배 빠른 조회를 표방한다. 셋째, 활동 분석이다. 세션을 자동화·퀵·표준·딥·마라톤 같은 유형으로 분류하고, 세션 길이·컨텍스트 사용량·도구 호출 분포를 시각화한다. 넷째, 파일 변경 추적이다. 최근 에이전트가 수정한 파일을 피드 형태로 보여 준다. 결과는 HTML이나 GitHub Gist로 내보낼 수 있다.

1.3 아키텍처 - Go 단일 바이너리와 선택적 팀 공유

백엔드는 Go(코드베이스의 약 83.8%), 프런트엔드는 Svelte 5와 TypeScript로 짜였고, Tauri로 감싼 데스크톱 앱도 제공된다. 저장소는 기본이 쓰기 가능한 SQLite(FTS5 인덱스 포함)이고, 팀과 공유하고 싶다면 SQLite에서 읽기 전용으로 밀어 넣는 PostgreSQL을, 대규모 분석용으로는 DuckDB 미러를 선택적으로 붙일 수 있다. 설치는 curl -fsSL https://agentsview.io/install.sh | bash, Homebrew 캐스크, 또는 Docker 이미지(ghcr.io/kenn-io/agentsview)로 가능하며, agentsview serve로 포그라운드 실행하거나 데몬 모드로 15분마다 자동 동기화할 수 있다. 웹 UI는 기본적으로 127.0.0.1:8080에서 뜬다. 라이선스는 MIT다.

2. 문제의 근원 - 여러 에이전트를 병행하는 시대의 세 가지 통증

2.1 세션 분산 - 도구마다 갈라진 기억

AgentsView가 겨냥하는 첫 번째 통증은 세션 분산이다. GitHub Copilot이 여전히 가장 넓은 사용자층(약 67.9%)을 갖고, Claude Code가 근소한 차이로 뒤따르며(약 62.9%), OpenAI Codex도 34.5% 수준까지 올라왔다는 2026년 조사 결과가 있다. 여러 도구를 동시에 쓰는 게 예외가 아니라 표준이 됐다는 뜻이다. 문제는 각 에이전트가 자기만의 세션 파일·포맷·UI를 가지고 있어서, "지난주에 이 리팩토링을 어떤 에이전트에게 어떻게 지시했는지"를 확인하려면 여러 도구를 하나씩 열어 봐야 한다는 점이다. 도구가 늘수록 이 기억은 더 잘게 쪼개진다.

2.2 비용 불투명 - 보이지 않는 지출

두 번째 통증은 비용이다. 에이전트는 계획·실행·재확인을 반복하며 매 단계마다 컨텍스트를 다시 실어 나르기 때문에 일반 챗봇 대비 토큰을 훨씬 빠르게 소모한다는 지적이 여럿 있다. 한 조사에 따르면 에이전트형 코딩 도구를 쓰는 개발자의 월평균 지출은 400~1,500달러 수준이고, 극단적인 경우 며칠 만에 4,000달러를 넘기도 한다. 35명 규모의 한 스타트업이 Claude Code·Cursor·자체 버그 트리아지 에이전트를 병행하다 한 달에 8만 7천 달러 청구서를 받은 사례, 마이크로소프트가 엔지니어 1인당 월 500~2,000달러 수준의 비용을 확인하고 일부 Claude Code 라이선스를 축소했다는 보도도 있다. 도구별 대시보드가 따로 있으면 이런 전체 그림이 잘 보이지 않는다.

2.3 무엇을 언제 시켰는지 추적하기 어렵다

세 번째 통증은 회고와 감사다. 코드 리뷰에서 "이 부분은 왜 이렇게 짰나"라는 질문에 답하려면 그때 에이전트에게 어떤 프롬프트를 줬는지 되짚어야 하는데, 세션이 도구별로 흩어져 있으면 이 되짚기 자체가 일이 된다. 팀 단위로 보면 "이번 스프린트에 AI가 실제로 얼마나, 어디에 기여했나"를 설명할 근거 자료가 없다는 뜻이기도 하다. 세션 분산과 비용 불투명, 회고 불가능이라는 세 통증은 사실 한 뿌리에서 나온다. 에이전트별로 닫힌 로그가 있을 뿐, 이를 가로지르는 하나의 시야가 없다는 것이다.

3. AgentsView가 주는 가시성 - 어디에 값어치가 있나

3.1 검색 가능한 공동 기억

AgentsView의 1차 가치는 단순하다. 여러 에이전트의 대화 로그를 하나의 검색창 뒤에 두는 것만으로, "그때 무엇을 시켰는지" 찾는 일이 여러 앱을 순회하는 작업에서 검색어 하나 입력하는 작업으로 바뀐다. FTS5 전문 검색은 정확한 문구를, 선택적 임베딩 검색은 "그 인증 관련 리팩토링이 뭐였더라" 같은 의미 기반 질의를 지원한다.

3.2 비용·토큰을 한 화면에

두 번째 가치는 비용 가시성이다. 도구별로 흩어진 청구서를 대조하는 대신, LiteLLM 가격 데이터를 기반으로 세션·모델·기간별 토큰과 비용을 한 화면에서 볼 수 있다. 프롬프트 캐시를 반영한 계산이라는 점도 중요하다. 캐시 히트가 잦은 세션과 매번 전체 컨텍스트를 새로 태우는 세션은 실제 비용 구조가 다른데, 이 차이를 단순 토큰 수 곱셈보다 정확하게 근사한다.

3.3 활동 분석과 변경 추적 - 패턴을 보는 눈

세 번째 가치는 활동을 유형화해 패턴을 드러내는 것이다. 세션을 자동화·퀵·표준·딥·마라톤으로 분류하면, "이 프로젝트는 짧은 퀵 세션이 대부분인데 유독 이 모듈만 마라톤 세션이 몰린다" 같은 관찰이 가능해진다. 최근 편집된 파일 피드는 "지난 며칠간 에이전트가 실제로 어디를 건드렸나"를 코드 리뷰 없이도 훑어볼 수 있게 해 준다. 이런 유형화는 개별 세션 로그만 봐서는 잘 드러나지 않는, 누적된 사용 패턴을 보여준다는 점에서 단순 로그 뷰어와는 다른 층위의 가치다.

4. 로컬 수집이 갖는 프라이버시 의미

4.1 기본값은 로컬호스트, 외부 전송 없음

AgentsView는 계정 생성이 필요 없고 세션 데이터가 기본적으로 자기 기기 밖으로 나가지 않는다는 점을 전면에 내세운다. 서버는 기본값으로 127.0.0.1에만 바인딩되며 세션 내용을 외부로 전송하지 않는다. 코드와 프롬프트가 그대로 남아 있는 로그를 다루는 도구인 만큼, 이 기본값은 사소한 설계 선택이 아니다. 클라우드 대시보드에 세션을 업로드하는 방식이었다면, 사내 코드베이스 전체가 벤더 서버를 거치는 문제가 새로 생겼을 것이다.

4.2 최소한의 텔레메트리, 끌 수 있는 옵션

다만 완전한 무통신은 아니다. 앱 버전·OS·CPU 같은 익명 정보가 시작 시와 24시간마다 PostHog로 전송된다. 세션 내용이 아니라 사용 통계라는 점에서 성격이 다르지만, AGENTSVIEW_TELEMETRY_ENABLED=0 환경 변수로 비활성화할 수 있다는 점을 알아 두고, 보안 정책이 엄격한 조직이라면 이 옵션을 확인하는 편이 안전하다.

4.3 팀 공유를 원해도 자기 인프라 안에서

팀과 공유하고 싶을 때도 AgentsView는 벤더 클라우드 대신 자기 인프라 안의 PostgreSQL을 선택지로 제시한다. SQLite에서 읽기 전용으로 데이터를 밀어 넣는 구조라, 팀 공유 상태에서도 "데이터가 어디에 있는가"라는 질문의 답은 여전히 자체 서버다. 이는 셀프호스팅 AI 에이전트 OpenTag 분석에서 짚었던 데이터 주권 논리와 같은 축 위에 있다.

5. 유사 접근과 비교 - 무엇과 겹치고 무엇이 다른가

5.1 에이전트 내장 로그 - 있지만 갇혀 있다

가장 기본적인 대안은 각 에이전트가 이미 제공하는 자체 히스토리다. Claude Code도, Cursor도 자기 세션을 어딘가에 남기고 각자의 UI나 CLI로 들여다볼 수 있게 해 준다. 문제는 이게 도구 하나에 갇혀 있다는 점이다. 도구를 두 개, 세 개 쓰면 "전체를 가로지르는 검색"이라는 기능 자체가 존재하지 않는다.

5.2 비슷한 세션 관리 도구들 - 겹치지만 초점이 다르다

AgentsView가 유일한 시도는 아니다. Mantra는 Claude Code·Cursor·Gemini CLI·Codex 세션을 하나로 모아 두되, 대화 로그를 코드가 변해 온 과정을 되짚어 보는 재생형 타임라인으로 보여 주는 데 강점이 있고, MCP 서버·권한 통합 관리와 API 키·시크릿을 자동 탐지해 한 번에 정리하는 기능까지 갖췄다. coding_agent_session_search는 11개 이상의 공급자를 아우르는 로컬 TUI/CLI 검색기이고, Agent Sessions도 Codex·Claude·OpenCode·Cursor·Copilot 등의 세션 관리에 초점을 둔다. 이들과 견주면 AgentsView의 위치가 또렷해진다. 검색과 리플레이에 강한 도구들 옆에서, AgentsView는 비용·토큰 분석과 팀 공유용 DB 백엔드(PostgreSQL·DuckDB)까지 갖춘 좀 더 분석 지향적인 조합을 택했다.

5.3 LLM 옵저버빌리티 플랫폼 - 다른 제품 범주

LangSmith·Helicone·Langfuse 같은 도구를 떠올릴 수도 있지만, 이들은 근본적으로 다른 문제를 푼다. 이 플랫폼들은 본인이 만든 LLM 애플리케이션에 SDK를 심어 API 트레이스를 계측하는 프로덕션 옵저버빌리티 도구다. LangSmith는 트레이스 수로 과금하고(무료 티어 월 5,000트레이스, 이후 유료 티어), Helicone은 요청 수로 과금하며 300개 이상 모델의 비용을 게이트웨이 단에서 계산한다. 반면 AgentsView는 계측 코드를 심을 대상 애플리케이션이 없다. 이미 로컬 디스크에 쌓여 있는 코딩 에이전트 CLI의 세션 로그 파일을 사후에 읽어 색인할 뿐이다. 월 LLM 지출 3만 달러 이하에서는 Helicone이, 3만~20만 달러 구간에서는 Langfuse가, 그 이상이면서 LangGraph에 깊이 투자한 조직은 LangSmith가 적합하다는 게 업계의 대체적 평가인데, 이 스펙트럼 자체가 애초에 "내가 만든 프로덕트의 API 트래픽"을 전제로 한다. AgentsView는 "내가 쓰는 코딩 에이전트"를 대상으로 한다는 점에서 출발선이 다르다.

5.4 비용 특화 도구들 - 지출 관리에 집중

LMSpend·DevOS·CodeBurn 같은 도구는 팀 단위 지출 추적, 예산 경고, 재무 보고 내보내기처럼 비용 한 축에 더 집중한다. 이런 도구들은 지출 관리에는 강하지만 대화 검색이나 세션 리플레이 같은 기능은 상대적으로 얕은 경우가 많다. AgentsView는 이 스펙트럼에서 검색·비용·활동·변경 추적을 한 도구 안에 묶은 제너럴리스트에 가깝다.

6. 실무 활용 - 팀 비용 배분, 프롬프트 회고, 감사

6.1 팀 비용 배분

여러 명이 각자 다른 에이전트를 쓰는 팀이라면, SQLite를 PostgreSQL로 읽기 전용 동기화해 팀 전체의 세션·비용 데이터를 한 저장소에 모을 수 있다. 이렇게 하면 "이번 스프린트에 AI 도구에 실제로 얼마를 썼고, 어느 프로젝트·어느 모델에 몰렸는지"를 재무 보고나 스프린트 회고에 근거 자료로 제시할 수 있다.

6.2 프롬프트 회고

개인 차원에서도 가치가 있다. 잘 풀린 리팩토링과 그렇지 않은 리팩토링을 나중에 검색해 비교하면, 어떤 프롬프트 패턴이 더 나은 결과를 냈는지 되짚어 볼 수 있다. 이는 "왜 이렇게 짰나"라는 질문에 "그때 이렇게 시켰다"는 답을 즉시 꺼낼 수 있게 해 준다는 점에서, 코드 리뷰와 회고 모두에 실질적으로 도움이 된다.

6.3 감사 관점의 한계 - 거버넌스 게이트는 아니다

다만 감사 용도로 쓸 때는 경계가 필요하다. AgentsView는 이미 벌어진 일을 사후에 색인하는 도구이지, 특정 행동을 사전에 막거나 예산을 실시간으로 강제하는 게이트가 아니다. "이 요청은 승인 없이 실행되지 않는다"거나 "이 팀은 이번 달 예산을 초과하면 자동 차단된다" 같은 통제가 필요하다면, 엔지니어와 모델 제공자 사이에 놓여 모든 요청을 로깅·귀속·통제하는 프록시 게이트웨이형 도구가 별도로 필요하다. AgentsView는 그 전 단계, 즉 "무슨 일이 있었는지 보이게 하는" 가시성 계층이라고 이해하는 편이 정확하다.

7. 한계와 주의점

7.1 사후 분석이지 실시간 통제가 아니다

앞서 짚었듯, AgentsView는 이미 쌓인 로그를 읽는 도구다. 비용이 치솟는 순간 알림을 보내거나 요청 자체를 막는 기능은 이 도구의 몫이 아니다. 실시간 예산 강제가 필요하다면 별도의 게이트웨이·프록시 계층을 함께 설계해야 한다.

7.2 가격 데이터의 정확도는 외부 소스에 달려 있다

비용 계산이 LiteLLM의 가격 데이터에 의존하는 구조라, 모델 가격이 자주 바뀌는 요즘 환경에서는 오프라인 폴백 데이터가 실제 청구서와 미세하게 어긋날 수 있다. 정확한 금액이 걸린 의사결정(예산 승인, 청구서 대사)에는 여전히 벤더의 공식 청구 내역을 기준으로 검증하는 절차가 필요하다.

7.3 로컬 DB에도 민감정보가 쌓인다

로컬에만 두는 구조가 외부 유출은 막아 주지만, 세션 로그 자체에 API 키나 내부 URL, 고객 데이터가 섞여 있을 가능성은 그대로 남는다. Mantra처럼 시크릿을 자동 탐지해 정리해 주는 기능이 AgentsView에는 기본 제공되지 않는 것으로 보이므로, 색인된 데이터베이스 파일을 팀과 공유하거나 백업할 때는 별도로 민감정보를 점검하는 절차를 두는 편이 안전하다.

7.4 에이전트 로그 포맷이 바뀌면 유지보수가 필요하다

40개 이상의 에이전트를 지원한다는 건, 그만큼 많은 로그 포맷을 계속 따라가야 한다는 뜻이기도 하다. 각 에이전트 벤더가 세션 저장 방식을 바꾸면 파서도 함께 갱신돼야 하며, 이런 유지보수 부담은 오픈소스 커뮤니티의 활력에 좌우된다. 도입 전에 저장소의 최근 커밋 빈도와 이슈 대응 속도를 살펴보는 것이 좋다.

8. 결론 - 오늘 할 수 있는 3가지

AgentsView가 보여주는 방향은 명확하다. AI 코딩 에이전트가 늘어날수록 개별 도구의 성능보다 그 위에 놓인 가시성 계층이 중요해진다는 것이다. 세션 검색, 비용 집계, 활동 분석을 한곳에 모으는 것만으로 "무엇을 언제 시켰는지" 되짚는 일이 훨씬 쉬워지고, 로컬 우선 설계 덕분에 이 가시성을 얻는 대가로 코드를 벤더 클라우드에 넘길 필요도 없다. 다만 이는 사후 분석 도구이지 실시간 거버넌스 도구는 아니라는 점, 그리고 감사·예산 통제가 목적이라면 별도의 계층이 필요하다는 점은 분명히 해 두어야 한다.

8.1 이번 주 자신의 에이전트 사용 현황을 직접 점검하라

AgentsView든 유사 도구든 설치해, 지난 한 달 실제로 어느 에이전트에 얼마를 썼는지부터 확인하라. 짐작과 실제 데이터가 다른 경우가 흔하다.

8.2 팀이라면 비용 배분과 감사를 분리해서 설계하라

비용 가시성은 AgentsView 같은 도구로 확보하되, 예산 강제나 요청 차단이 필요하다면 프록시 게이트웨이를 별도로 검토하라. 두 계층을 하나로 착각하면 통제가 빠진 대시보드만 남는다.

8.3 민감정보 점검 절차를 먼저 세워라

세션 로그를 색인하기 전에, API 키나 사내 URL 같은 민감정보가 로그에 섞여 있을 가능성을 먼저 점검하라. 팀과 공유하거나 백업하기 전 한 번 더 걸러내는 절차를 넣는 편이 안전하다. 관련해서는 셀프호스팅 AI 에이전트 OpenTag 분석과 QAMap 로컬 CLI 분석도 참고할 만하다.
