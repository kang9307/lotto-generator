What Actually Ends a Loop - Termination, Feedback, and State Contamination in Agent Loops

A loop that does not end is a failed loop

Aug 16, 2026 Dev & Infra

Introduction: everyone has watched a loop refuse to stop

You tell an agent to keep fixing until the tests pass, then step away. You come back to one of two things. It finished, or it is still going. When it is still going and you open the log, the picture is almost always the same: the same error explained in slightly different words, followed by a slightly different version of the same fix.

It is tempting to blame the model. But take that loop apart and the broken part is usually the wiring, not the model. Who decides success, what gets carried forward on failure, what state the second attempt starts from, and when the thing is allowed to stop — leave those four unspecified and any model will circle the same spot.

This piece is about that wiring. It splits a loop into five parts, shows which symptom points at which broken part, and lays out what genuinely ends a loop versus what quietly ruins it.

The taxonomy of loops — how the inner agent loop, the verification loop, and the outer improvement loop nest — is covered in The Art of Loop Engineering — Designing AI Agents as Iterative Loops. Where to place delegation and checkpoints between a person and an agent is in Delegating Work to AI - The Five Parts of a Handoff and How to Place Checkpoints, and the preconditions for a metric-maximizing search loop, along with measurement noise, are in How to Read a 232x Speedup - What an Automated Search Loop Actually Requires. None of those axes are repeated here.

1. A loop has five parts

Designing iterative execution is not prompt writing. It is filling in five slots.

  • Starting state — where each attempt departs from. Working directory, data, context, and whatever the previous attempt left behind
  • The attempt — what the agent actually does. Scope, permissions, elapsed time
  • The oracle — what decides whether this attempt succeeded. Machine or human
  • Feedback — what gets carried into the next attempt after a failure
  • Termination — when to stop. On success, on exhausted budget, on no progress, on danger

Most loops have only the middle slot filled. The instruction is written carefully and the other four are implicit. The oracle defaults to the agent's own report, feedback just piles up in the conversation, the starting state is whatever wreckage the last attempt left, and termination is a human getting impatient and hitting stop.

So looking for the cause inside the attempt rarely finds it. Loops do not fail because the attempt was bad; they fail because the other four are empty.

The first question to ask. Which command's exit code answers whether this loop succeeded? If there is no answer, the rest of the design is moot. Without an oracle there is nothing to put in the feedback and no basis for a termination rule. The boundary of what a machine can and cannot verify is laid out in What a Machine Can and Cannot Verify in an LLM Answer - Where a Verification Harness Draws the Line.

2. Which part is broken, read from the symptom

When a loop misbehaves the instinct is to dig through logs, but the symptom alone narrows the culprit a long way, because each part fails in a characteristic manner.

The third row shows up constantly. An agent saying it has completed the fix is a claim, not a verdict. Put a claim in the verdict's seat and the loop can issue its own success termination at will, at which point iterative execution stops being a quality device and becomes an auto-approval device.

3. Termination design — wire all four exits

The most common design mistake is having exactly one exit. Stop when the tests pass is success termination alone, and it says nothing about the case where success never arrives. Four exits are what a working loop needs.

Exit typeWhat must be true to stopWithout this exitCommon design mistake
SuccessThe oracle returns passIt keeps polishing after the work is doneLeaving the verdict to the agent's own report
BudgetAttempt count, wall clock, or tokens hits a ceilingFailure becomes unbounded costSetting the ceiling but never deciding what happens when it is reached
StallNo improvement across the last few roundsEvery attempt after improvement ends is wasteHaving no metric, so a stall cannot be detected at all
RiskIrreversible operation, out-of-bounds access, or a change to the oracle itselfThe loop edits the checker until it passesRelying on after-the-fact audit instead of cutting at execution time

3.1 Is the success verdict mechanical — three questions

Success termination only holds if the verdict is mechanical, and three questions settle that.

  • Does one command split pass from fail? If it does not, what you have is a wish, not a goal
  • Can the agent edit that command? If it can, it is not an oracle. The oracle must sit outside the attempt's reach
  • Does the same input yield the same verdict? On a wobbling verdict you cannot tell improvement from luck

When the third one breaks, the loop chases noise. An attempt that passed by accident gets promoted, its output becomes the departure point for the next round, and the direction drifts. What happens when measurement wobbles, and how to defend against it, is covered in the piece on what an automated search loop requires.

If a goal cannot be reduced to one command, rewrite the goal. Improve usability cannot go in a loop; drive these eight accessibility rule violations to zero can. Rewriting the goal to fit a loop is half of loop design.

3.2 Budget exits — ceilings need a basis

People often set attempt ceilings at thirty or fifty, which is not a ceiling but a declaration of surrender. A principled ceiling comes out of a simple count: how many rounds does a human need by hand, times two or three. If it takes two or three tries by hand, five or six is plenty, and needing more than ten is a sign that the problem definition is wrong, not the attempt.

More important than the ceiling is the behavior when the ceiling is hit. Stopping quietly hands a human an artifact with no idea whether the loop succeeded or gave up. At minimum, leave these three behind.

  • The last attempt's verdict and failure message
  • A short history of what each attempt changed and how the metric moved
  • Whether the workspace was restored or left in the final attempt's state

3.3 Stall exits — detecting no further improvement

Stall detection needs only one of three ingredients.

  • With a continuous metric — if the last three deltas are smaller than measurement noise, that is a stall. Get the noise band by running the same measurement ten times while changing nothing
  • With a binary verdict only — if the failure signature (error type plus location) is identical three rounds running, that is a stall. Compare signatures rather than full messages so reworded prose does not fool you
  • With only the diff visible — if this round's change hash matches an earlier one, that is an immediate stall. It means the same edit was reconstructed

The source article puts the same idea briefly: when the same instruction repeats three times with no change, that is where to cut. The number three reads less like a validated constant and more like the principle stop as soon as repetition is confirmed. Twice can be coincidence; three times is a pattern.

3.4 Risk exits — signals that mean stop now

If the other three say enough is enough, the risk exit says stop this instant. The following are not retry material; they are abort material.

  • The oracle, the check code, or a config file was modified by the attempt
  • An operation with no rollback path was attempted (deletion, sending, payment, public disclosure)
  • An out-of-bounds access repeated two or more times
  • The same external call returned quota errors consecutively — that is not a problem a loop solves
  • One attempt burned several times the expected unit cost — a sign the work was scoped wrong

The first line matters most. Editing the checker until it passes is not malice; it is what happens whenever the structure permits it. Anything told to optimize an objective satisfies the metric, not the specification. So the oracle belongs in a no-write area, and any change there ends the loop regardless of the verdict. How to grade what is allowed and where to draw the barrier is in What Should an AI Agent Be Allowed to Do - Permission Design and Failure Barriers.

4. What a non-terminating loop actually burns

Counting the cost of a runaway loop in tokens misses more than half of it. Four things burn.

  • Shared quota. Other work on the same credential or plan starves. One loop eating a team's throughput is the most common incident of this kind
  • Human attention. Repeated round trips to check whether it finished erase the gain from automating. How that fatigue accumulates is covered in The Human in the Loop Is Tired - Supervision Fatigue in the AI Coding Era
  • Trust. If one run in three spins uselessly, people stop believing the output. Then everything gets reviewed by hand and the net gain lands at zero or below
  • State. The longer it runs, the more side effects pile up. Past some point cleaning up costs more than the artifact is worth, and in practice that point is the real break-even

Seen this way, termination design is less a cost-control device than a trust-preservation device. Worse than a loop that ends late is a loop whose end time is unknown. Give it a predictable ceiling and people go do something else in the meantime.

5. Feedback quality — what to return so the next attempt improves

Feedback is the most underrated part of a loop. Termination ends a loop; feedback makes it advance. With bad feedback the loop does end, but it ends without anything having improved.

Feedback shapeWhat it actually gives the next attemptStrong whereWeak where
Raw failure output
(stack traces, compiler output)		Exact coordinates — file, line, symbol, error codeDeterministic machine errors: compile, type, test failuresAt thousands of lines the signal is buried and context is consumed
SummaryToken savings and readabilityLong logs where the failure class is already knownIf the summary drops coordinates, the next attempt rediscovers the same spot — the main cause of repeated failure
Diagnosis
(observation plus a cause hypothesis)		A search direction, including where not to lookWhen the cause spans several layersA wrong hypothesis pins the loop to a wrong direction

(what changed, how the metric moved)		The raw material for stall detection and a point to revert toLoops that have a continuous metricCannot be built without a metric

(approaches already tried)		A constraint against retreading the same pathWide search space with short cyclesWithout grouping by family the list only grows longer

The combination that works in practice is settled. Trim the original but keep the coordinates, attach a short change history, and pass a negative list grouped by idea family. Diagnosis is worth adding only when a human or a separate agent supplies it — a diagnosis written by whoever just failed rests on the same premises that produced the failure, and tends to confirm its own error.

This is exactly the point the source article presses on: separate the agent that proposes from the agent that verifies. When one agent declares its own work complete, it checks the dimensions it happened to consider and the rest are missing entirely. Splitting verification into its own seat is what surfaces the conditions that got skipped.

Re-attach this every round. In a long loop the goal itself blurs. By the fifth attempt the original success condition has drifted to the back of the context and the agent is fixated on erasing the last error. Put one line of success condition at the head of every feedback payload. It is the highest-return line per token in the whole design.

6. State contamination — what one attempt leaves behind ruins the next

Even with good feedback, a contaminated starting state stops the loop from advancing. The second attempt departs from the first attempt's wreckage, so the agent mistakes its own side effects for the original problem and starts fixing those.

Contamination comes in roughly six kinds.

  • Filesystem — half-written files, leftover temp files, undeleted lock files, partial edits never rolled back
  • Processes and ports — a server that did not die, a held port, background jobs still alive. The next attempt receives an irrelevant address already in use error
  • Dependencies — installed packages, a modified lock file, a swapped version. You end up with a state that passes only locally
  • Data — leftover rows, a warmed cache, an applied migration. The second attempt sees different data than the first
  • The outside world — published events, sent notifications, created resources. These do not roll back
  • Context — a wrong premise from an earlier attempt lingering in the conversation. The quietest and the most common. Files can be reverted while a wrong summary of what a function does stays put and becomes the next attempt's departure point

The signal for suspecting contamination is clear. Change the order and the result changes, or it passes alone and fails when run consecutively. How to catch that symptom in tests is covered in What Shuffling Test Order Reveals - Finding the Hidden Dependency, and the diagnostic principle in a loop is identical.

7. Isolation and reset — starting each attempt from zero

Reset strategy is a choice among three, and accuracy trades off honestly against cost.

  • Fresh copy per attempt — the cleanest. Setup cost is high and the cycle lengthens. Use it where side effects spread widely
  • Roll back after each attempt — the practical default. Tracked changes revert; untracked side effects remain. Knowing what falls outside tracking is the whole of this strategy
  • Accumulate — never revert, keep stacking. The shortest cycle. Use it only where accumulation is genuinely the point, such as bulk conversion, and compensate with tighter stall detection and ceilings

Whichever you pick, one device is cheap to add. Run the oracle once, before the attempt, with nothing changed. A failure there is contamination rather than the problem. That single precheck catches a large share of loops that keep fixing something with nothing left to fix.

There is one commonly missed spot in cleanup as well: cleanup being skipped on the failure path. If it only runs on success, the early attempts — which fail most — quietly stack residue. Cleanup must run on success, on failure, and on abort. The principles behind procedures that stay safe on a second run are in Idempotent Shell Scripts - Six Patterns That Break on the Second Run.

Below is every part so far placed in one skeleton. It is illustrative pseudocode and has not been executed or verified on any runtime. Read the order of the lines, not the language or tooling.

# Conceptual example — not executed or verified. A skeleton for seeing the wiring order.

budget  = { tries: 6, wall_min: 20, tokens: T }   # whichever hits first wins
history = []                                      # (change summary, verdict, metric)
stale   = 0

while budget.remaining():
    reset_workspace()                    # (1) starting state back to zero
    if verdict() == FAIL_PRECHECK:       #     precheck: already failing before we touch anything
        stop(OFFSET_DIRTY); break        #     means contamination, not the problem

    change = attempt(goal, feedback)     # (2) one attempt
    v, log = verdict()                   # (3) oracle — must sit where the attempt cannot edit it

    if tampered(judge_files):            # (4) risk exit: the oracle changed
        stop(JUDGE_TAMPERED); break

    if v == PASS:
        stop(SUCCESS); break             # (5) success exit

    sig = signature(log)                 # error type + location. Reworded prose will not fool it
    if sig == last_sig or hash(change) == last_hash:
        stale += 1
        if stale >= 3: stop(NO_PROGRESS); break    # (6) stall exit
    else:
        stale = 0

    history.append((summarize(change), v, metric()))
    feedback = build_feedback(goal, log, history)  # (7) assemble feedback
    rollback()                                     #     side effects are undone here

else:
    stop(BUDGET_EXHAUSTED)               # (8) budget exit — never end silently

The two easiest lines to drop are the precheck after reset_workspace() and the rollback() at the bottom. Without the first, contamination gets mistaken for the problem; without the second, the next round departs from a contaminated state. Each one guarantees the other.

The feedback builder is worth reading separately. Actual quality is decided here.

# Conceptual example — not executed or verified.

def build_feedback(goal, log, history):
    parts = []

    # 1) Re-attach the success condition at the head every round (long loops blur the goal)
    parts += [f"[GOAL] {goal.oneline}  verdict: {goal.command}"]

    # 2) Trim the original, keep the coordinates
    head, tail = log[:1200], log[-800:]
    coords     = extract(log, [file_path, line_no, symbol, error_code])
    parts += [f"[FAIL] {head} …(elided)… {tail}", f"[WHERE] {coords}"]

    # 3) Only the last three history entries. Accumulation buries recent information
    parts += [f"[HISTORY] {history[-3:]}"]

    # 4) Group the negative list by family (idea level, not individual attempt)
    parts += [f"[ALREADY FAILED] {families(history)}"]

    return clamp(parts, max_chars=4000)   # cap by character count

8. Cost control — decide the stop rules first

Set the budget on three axes and let whichever hits first win: attempt count, wall-clock time, and tokens or request count. Wire only one and it leaks through the others. A count-only ceiling cannot stop attempts that take forty minutes each; a time-only ceiling lets hundreds of short attempts burn the quota.

One value is worth measuring before setting any ceiling: the unit cost of an attempt. Take the median tokens and elapsed time across a few successful attempts and ceilings become arithmetic rather than guesswork. Ceilings set without that number are almost always too large.

Early stopping cuts before the budget runs out. These four can fire regardless of budget with nothing lost.

  • The first attempt greatly exceeds the expected unit cost — a signal the scope was set wrong. Stop burning and re-split the problem
  • Stall detected — attempts after improvement has ended have expected value near zero
  • Consecutive infrastructure errors — network, quota, and auth errors are not problems a loop solves. Cut rather than retry through them
  • Unstable oracle — if the same state yields two different verdicts, stop the loop and fix the oracle first

The risk exits from 3.4 sit on the same shelf. The difference between early stopping and a risk exit is only in character: the former says there is nothing more to gain, the latter says continuing increases the damage.

Quota sharing is worth deciding up front too. A loop calls far more densely than a person, so sharing a credential means interactive work is what feels slow first. Give loops a separate credential or a separate queue; managing budgets and attribution at the org level is covered in Governing AI Token Spend at the Org Level - Budgets, Limits, Attribution.

9. When not to use a loop

Whether to attach a loop is decided by structure, not domain. If any one of the six below applies, iterative execution makes the problem worse.

  • The verdict is subjective. Until it looks good and until it feels natural cannot go in a loop. Attach a proxy metric and the proxy becomes the target while the original meaning drains out. Optimize for click-through and screens that bait clicks win; optimize for line count and merely short code wins
  • A wrong step cannot be undone. Deletion, sending, payment, public disclosure. Without a rollback path it does not go in a loop — because a loop is a device for making the same mistake many times
  • Judging costs more than attempting. If a human must look at every round, that is a queue, not a loop. Here the thing to automate is the verdict, not the attempt
  • Attempts are uncorrelated. If feedback does not improve the next attempt, this is a lottery rather than a search. A lottery is worth about three pulls; thirty just multiplies the cost by ten
  • The problem is not yet understood. Automating ambiguity amplifies it. Do it by hand three times, and when those three converge on the same procedure, move it into a loop. The source article likewise says to start from a clearly defined daily manual task
  • Failure is silent. If failure does not surface as an exception or an exit code, the loop counts it as success and keeps going. Making failure loud comes before attaching a loop

The third item has a useful middle band. When a problem is only partly decidable, carve out the decidable part for the loop and leave the rest to a person. Query tuning where result sets must match, build-time reduction where artifacts must match, format conversion where a round trip must agree. The argument that one enforcement point beats a long rules document is in A Long Policy Document Will Not Govern Your Agent - Add Enforcement, Not More Rules.

And there is one distinction the source article keeps returning to: you can delegate the task but not the taste and the judgment. A loop runs well where judgment is already settled and only execution remains. Attach one before judgment is settled and the loop does not substitute for judgment — it propagates the un-judged state faster.

10. What could not be confirmed

This piece covers design principles and uses almost no figures. Here is why.

  • Success rates or cost savings by termination design. No published comparison giving numbers like adding stall detection cuts cost by some percentage could be confirmed, so no percentages appear in the text
  • A recommended value for the attempt ceiling. It varies by kind of work and no general basis could be confirmed. What is offered instead is the derivation rule: hand rounds times two or three
  • Whether telling the agent about remaining budget makes it adjust scope. Plausible and in actual use, but the effect size could not be confirmed, which is why the text does not recommend it
  • The repetition count of three for stall detection. Common in the source and in practice, but no experimental basis could be confirmed. Reading it as stop as soon as repetition is confirmed is safer
  • The two code blocks. Illustrative pseudocode, not executed or verified. They are not meant to be copied as-is

Conclusion: look at the other four before fixing the attempt

When a loop misbehaves, the first thing people do is rewrite the prompt. Yet almost no row in the symptom table above is fixed by a prompt. Repeated failure means fixing feedback. Trouble from round two means fixing the starting state. Never ending means fixing termination.

In order: oracle, then termination, then starting state, then feedback, then the attempt. The oracle comes first because nothing else means anything without it, and the attempt comes last. Most people work in exactly the reverse order.

If only one line survives, make it this. A loop that does not end is a failed loop — even when the result is good. Automation with an unknown finish time holds a person in place, and a person held in place eventually stops using it.
