You Cannot Read Every Release Note - The Four Things That Decide an Upgrade

Security fixes, breaking changes, deprecation notices, and the behaviour that changed quietly. Where the machine's work ends and yours begins

2026-09-03 Dev & Infra

Open a dependency manifest and you will find maybe twenty lines that somebody typed on purpose. Open the lock file next to it and you will find several hundred packages. The active ones among them cut a new version every few weeks. Multiply those two numbers and the volume of release notes arriving each week is already past what one person can read and judge. Skip them and one day a deploy breaks, and when you finally open the note afterwards the explanation is sitting right there.

So what happens in practice is usually one of two things. Nobody reads them from the start, or one person reads all of them until they burn out and then nobody reads them. This article is about the space in between. If reading all of them is impossible, what subset do you have to read in order to decide an upgrade? The answer is shorter than people expect, and one item on it is something most teams never look for at all.

This article does not recommend, evaluate or benchmark any particular tool or service, and it contains no installation or configuration instructions. The specifications and policies quoted were checked against the publishing body's own primary documents as of September 2026 and may be revised afterwards.

The trigger - a service that promises to sort release notes for you

In early September 2026 a Korean developer community picked up a service that claims to extract security fixes, breaking changes and pending deprecations automatically from the release notes of CNCF projects. The stated scope was the 76 projects at CNCF graduated and incubating level. The CNCF projects page lists 38 graduated and 38 incubating as of September 2026, so that number checks out.

The published companion repository is a single MCP server written in Go. Apache-2.0 licence, 102 commits, latest tag 0.8.0, two stars, zero forks. It is a personal project that has just started. So this article neither recommends nor rates the service. What matters is that the existence of such a thing is itself a signal — a signal that reading release notes has become work that no longer fits in human hands.

The service's own web page refused access (HTTP 403) and could not be opened directly. So what follows is not a description of any specific tool's behaviour, but of what this class of tool can take off your hands and what stays yours all the way through.

Reading all of them is already impossible

Nobody skips release notes out of laziness. It is arithmetic. Thirty declared dependencies each dragging in ten more puts several hundred packages on the execution path. Then the platform underneath gets added: the container runtime, the orchestrator, the database, the reverse proxy, and the distribution below all of it. In no organisation is that a volume one person can read and adjudicate.

Three illusions layer on top of that and freeze the problem in place.

  • The important ones will stand out anyway — the most dangerous change is usually written in the least conspicuous sentence. A single line saying the default timeout was adjusted is exactly that
  • You only need to look when the major number moves — the SemVer specification we will get to shortly does not underwrite that expectation as far as people assume
  • If CI passed, it is fine — tests only verify behaviour you know you rely on. Behaviour you were depending on by accident was never in the test suite to begin with

What is needed, then, is not a habit of reading more diligently but a rule for shrinking what gets read. Without a rule, diligence does not survive more than a few weeks.

There are only four things to look for

Release notes mix together performance work, documentation edits, typo corrections, internal refactoring and contributor lists. Four categories out of that mix feed the upgrade decision. The rest can be read after you have shipped.

What you look forWording that usually carries itWhat happens if you miss itCan a machine find it
Security fixSecurity, CVE-, GHSA-, advisoryYou keep running a publicly disclosed vulnerabilityMostly yes
Breaking changeBreaking, Removed, no longerThe deploy breaks immediately. You also learn immediatelyMostly yes
Deprecation noticeDeprecated, will be removed inFine today, everything comes due two versions laterPartly
Behaviour changed quietlyChanged, Fixed, now defaults toNo error at all, only a different resultHardest of the four

Security fixes - best labelled and most often missed

Security fixes have the strongest notation conventions of the four. A CVE or GHSA identifier is attached, a separate advisory page follows, and the entry is indexed in vulnerability databases. They still get missed, and the reason is not the labelling but the delivery path. A security release in a package you declared yourself produces an alert; a security release in what that package pulls in behind it often sits outside your alert configuration. That is where the real incidents tend to come from.

Breaking changes - dangerous but honest

Breaking changes sound frightening and are in practice the easiest of the four to handle. The compile fails, the process refuses to start, or the first request raises. The cost is high but detection is free. The time you spend here is fixing time, not finding time.

Deprecation notices - today's warning, next year's outage

A deprecation notice causes nothing today. That is why people read it and move on. The problem is that this item is debt with a due date attached. If it does not get filed as an issue at the moment you read it, several of them mature in the same week a couple of years later.

Behaviour that changed quietly - nobody labels it

The fourth is a different animal from the first three. There is no notation convention, and it passes as a single sentence inside a 「Changed」 or 「Fixed」 entry. The version number is a minor or a patch, but a default moved, or a sort order changed, or a rounding rule changed. The deploy succeeds and the tests pass. The results are simply different.

Why the fourth one is the most dangerous

The first three give you a signal at some point. A security fix comes with an advisory, a breaking change breaks the deploy, a deprecation leaves a warning in the log. Only the fourth gives you nothing. So the moment of discovery is not just after the deploy but weeks later when a reconciliation does not balance, or when a user files a ticket.

How this category arises is hinted at in the SemVer specification itself. The specification says the patch version is incremented when only backward compatible bug fixes are introduced, and it defines a bug fix as an internal change that fixes incorrect behavior. But if your code was leaning on that incorrect behaviour, the fix is by definition a patch upstream and a breaking change for you. Fixed above, broken below. This asymmetry does not disappear no matter how faithfully the convention is followed.

The way to pull this category out of a note is to distrust a handful of words. When the phrasing on the left appears, that sentence deserves a second reading even if it is filed under performance improvements.

How the note phrases itWhat you actually have to askWhere to check on your side
The default is now XDid we ever set that value explicitlyGrep the option name across config and code
It no longer does YWere we relying on Y as a premiseImplicit premises are rarely covered by tests
Ordering was made stableIs there logic that depends on orderCode taking the first element, pagination
Precision or rounding was fixedDoes it feed amounts or quantitiesStored historical values stop matching new ones
It now raises an errorWas there input that used to pass silentlyPaths that went through with no exception handling

The last row arrives especially often. A library that used to ignore malformed input silently is now 「fixed」 to raise. In the release note it is filed under Fixed.

What semantic versioning promises and what it does not

The Semantic Versioning 2.0.0 specification assigns a meaning to each of the three numbers. Major goes up on incompatible API changes, minor when backward compatible functionality is added, patch on backward compatible bug fixes. The specification then adds one more clause to the minor rule: it must be incremented if any public API functionality is marked as deprecated. In other words the deprecation notice itself is designed to show up in the version number.

That is the extent of the promise. The list of things that are not promised is longer.

What SemVer promisesWhat it does not
If major went up, there is an incompatible changeThat your code survives when major did not go up
Public API deprecations show up in minor or aboveUndocumented behaviour, error messages, log formats
Minor and patch reset to 0 when major incrementsContinuity of performance, latency or memory use
0.y.z warns up front that anything may changeChanges that arrive because transitive deps moved
All of it only for projects that declared the conventionWhere that project draws the line around 「public API」

The first row on the right is the expensive one in practice. The specification FAQ addresses that situation head on. When a backward incompatible change has gone out by accident and reverting would hit a large audience, it says it may be best to perform a major version release, even though the fix could strictly be considered a patch release. The people who wrote the specification assume the version number and the real impact can diverge.

The 0.x carve-out is worth reading literally too. The specification designates 0.y.z for initial development and states that anything may change at any time and that the public API should not be considered stable. The FAQ answer on when to release 1.0.0 is blunter still: if your software is being used in production, it should probably already be 1.0.0. So a 0.x dependency that is in production is a place where the convention guarantees nothing at all.

Reading a security advisory - a score is not a queue

Once a security fix is found, the next question is whether to fix it first. The common mistake here is lining things up by CVSS score. The FIRST CVSS v4.0 User Guide blocks that usage explicitly: CVSS Base scores are designed to measure the severity of a vulnerability and should not be used alone to assess risk. The same document adds that the Base score represents only the intrinsic characteristics of the vulnerability and is independent of any factor associated with threat or the computing environment where the vulnerable system resides, and that it should be supplemented with Environmental and Threat metrics.

What actually reorders the queue is evidence of real exploitation. The CISA KEV catalog is run for that purpose. Three criteria govern inclusion: the vulnerability has an assigned CVE ID, there is reliable evidence it has been actively exploited in the wild, and there is a clear remediation action such as a vendor-provided update. The catalog page describes itself as the authoritative source of vulnerabilities that have been exploited in the wild and tells organisations to use it as an input to their vulnerability management prioritization framework. As of September 2026 it lists 1,694 entries.

The directive that applies to United States federal civilian executive branch agencies was refreshed as BOD 26-04, issued on 10 June 2026. It carries forward the KEV inclusion criteria and sets remediation deadlines not by score but by four binary questions. It does not bind companies in other countries, but the shape of the prioritisation function is worth borrowing directly.

What it asksWhy that question
Is the asset publicly exposedExploitation requires the attacker to be able to reach it
Is it listed in KEVTheoretical possibility and real exploitation are different events
Can exploitation be automatedOnce automated, your turn comes even if you are not a target
Partial control or total controlSame reach, very different size of outcome

To take examples from the directive's own table, the combination of publicly exposed, listed in KEV, automatable and leading to total control carries a three-day deadline together with forensic triage. The same conditions with partial impact carry six days. At the other end, not in KEV, not publicly exposed and partial impact is classified as fix on system upgrade. The deadlines are stated in calendar days and are explicitly described as dynamic as facts change.

What is worth taking from this is the structure rather than the numbers. Instead of comparing one score against a threshold, it asks separately about reachability, real exploitation, automation and blast radius. Three of the four can be answered from outside sources; only the first needs somebody who knows your infrastructure. How much time defenders have after a patch ships is covered separately in the fix itself is a signal.

The hooks that were built for machines

Tools that sweep release notes automatically are not operating in a vacuum. Over the past decade or so, several layers of convention have accumulated for planting machine-readable hooks in prose written for humans. Each answers a different question.

Format or databaseQuestion it answersLimit
Keep a ChangelogDoes this release have a security entryOnly holds if the project follows it
Conventional CommitsWas a breaking change flagged in the commitNo way to verify a missing flag
GitHub Releases APIWhich tag shipped and whenThe body is free-form markdown
OSVDoes this version fall in the affected rangeRanges are per package
GitHub Advisory DatabaseWhich version first carried the fixUnreviewed entries raise no alert
SBOMWhat are we actually shippingShipping it and executing it differ

Keep a Changelog pins the change types to six in its 1.1.0 edition. Added for new features, Changed for changes in existing functionality, Deprecated for soon-to-be removed features, Removed for now removed features, Fixed for any bug fixes, and Security in case of vulnerabilities. The fact that Security gets a heading of its own is where the practical value of this convention sits, because the first question from the previous section is answered by a section name. The same document leads with the principle that changelogs are for humans, not machines, and says using commit log diffs as changelogs is a bad idea because they are full of noise.

Conventional Commits 1.0.0 puts its hook on the commit message instead. The structure looks like this.

<type>[optional scope]: <description>

[optional body]

[optional footer(s)]

One form is a footer consisting of the uppercase text BREAKING CHANGE followed by a colon and a description. The other is a ! placed immediately before the colon after the type or scope. The specification says that when ! is used the footer may be omitted and the commit description itself describes the breaking change. It also says that commits carrying BREAKING CHANGE, regardless of type, should be translated to major releases.

The changelog side has this shape. The section names are fixed, so it parses, and because it parses a machine can shortlist three of the four categories above.

## [2.4.0] - 2026-08-14
### Added
### Changed
### Deprecated
### Removed
### Fixed
### Security

On the collection side the GitHub releases REST API is the common route. There are endpoints for listing releases, fetching the latest release and looking one up by tag, and the response carries fields such as tag_name, body, prerelease, draft and published_at. There is also an endpoint that generates release notes, which the documentation describes as producing a markdown body containing the changes since the last release and the users who contributed. Ignore prerelease and draft and you will start ingesting tags that are not final. What downstream loses when tags themselves disappear is covered in what downstream loses when release tags disappear.

On the vulnerability side two databases carry the weight. OSV describes itself as a distributed vulnerability database for open source, and says its schema provides a human and machine readable data format to describe vulnerabilities in a way that precisely maps to open source package versions or commit hashes. The load-bearing word is precisely. A prose statement such as 「there is a vulnerability somewhere in the 1.x line」 cannot be adjudicated automatically.

The GitHub Advisory Database splits entries three ways: those GitHub has reviewed and mapped to a supported ecosystem and package, those published automatically from the National Vulnerability Database feed without review, and those covering malicious packages. The documentation states that unreviewed advisories do not trigger Dependabot alerts. The absence of an alert is therefore not evidence of not being affected. Each entry carries an identifier in the GHSA-xxxx-xxxx-xxxx form, along with the range of released package versions where the problem exists and the earliest version where the problem was fixed. The latter gets used more in practice, because it tells you immediately how far you have to move.

SBOM answers at a different layer. CISA defines an SBOM as a nested inventory, a list of ingredients that make up software components, and presents it as a key building block in software security and software supply chain risk management. The same page introduces VEX, an attestation, a form of a security advisory that indicates whether a product or products are affected by a known vulnerability or vulnerabilities. That is an attempt to answer the next section's question, whether you are actually affected, from the supplier's side in advance.

Finally there is a way to get the answer outside the release note entirely. Since v1.19 Kubernetes responds to requests against a deprecated REST endpoint with a Warning header, adds a k8s.io/deprecated annotation to the audit event, and sets the apiserver_requested_deprecated_apis gauge metric to 1. That metric even carries a label indicating the release in which the API will no longer be served. It is asking the running system directly instead of reading the note, and for deprecations this route is far more accurate, because it also tells you whether you are actually calling that API.

Where automation works and where it stops

Stack all of those formats together and the boundary comes out fairly sharp. It can be drawn in one line. If the information lives inside the upstream repository, a machine answers. If it lives inside your code, it cannot.

  • What a machine can answer — does this release have a Security section, is a breaking change flagged in the commits, does the version we pinned fall inside this advisory's affected range, which version first carried the fix, how many tags have gone by since our last upgrade
  • What a machine cannot answer — do we actually reach that code path, did we set the changed default explicitly, with what arguments is the removed function called in our code, does this change matter given the shape of our data
  • What sits in between — are we shipping that package at all. An SBOM answers that far, and leaves the gap between shipping something and executing it
  • What suppliers try to answer for you — VEX is the practice of writing down that a product is not affected by a given vulnerability. It only helps where somebody produces it
  • What is left — judgement does not transfer. Automation gets as far as building a shortlist and putting it in order

So the success of an automation rollout should be measured not by how much it catches but by how short it makes the list a human has to read. A tool that throws forty items a day is functionally the same as a tool that throws none. Neither gets read.

Why a summary must not decide a deployment

Summarising is not the work of making sentences shorter. It is the work of choosing what to discard. And in a release note the first things discarded happen to be conditional clauses and negations. 「B changes only if option A is enabled」 collapses into 「B changes」. Humans make this mistake too, but automatic summarisation aimed at a length target makes it structurally more often.

The recurring losses in release note summaries fall into roughly five kinds.

  • Dropped condition — a change scoped to one setting, platform or version combination reads as a change across the board
  • Flipped negation — 「does not」 becomes 「does」, 「is not affected」 becomes 「is affected」
  • Confused subject — a server-side default change migrates to the client side, or the reverse
  • Confused version — the vulnerable version and the version carrying the fix get mixed. This one inverts the remediation direction outright
  • Distorted strength — 「recommended」 hardens into 「required」, and 「no known cases」 hardens into 「none」

So a summary belongs in choosing what to read, and the deployment decision is made from the original. Three display rules are enough to hold the line. Always keep the link to the original note and the tag name beside the summary. Distinguish 「no security entries」 from 「not checked」 with different markers. Quote the sentence the summary was drawn from verbatim.

Running this in a team

A heavy process does not survive two months. What actually keeps running usually looks about like this.

  • Shrink the scope first — make the recurring target your declared dependencies and the underlying platform, not the whole lock file. Leave the rest to vulnerability alerts
  • The weekly sweep is one person for thirty minutes — rotate it, and let the output be a single list of N items a human should look at. The person who reads does not also decide
  • Separate urgent from routine — write the condition for the urgent path down in advance. Publicly exposed assets carrying a vulnerability with confirmed exploitation is a common baseline. Everything else goes to the routine path
  • Fix the auto-merge envelope for bot PRs in advance — patch level, tests green, no breaking flag. Anything outside gets human eyes. GitHub's own documentation tells you to review the changelog and release notes included in the pull request summary when assessing a proposed update
  • Read a pile-up as a policy failure — twenty open PRs is not laziness. It means the auto-merge envelope is too narrow or the target set is too wide
  • Record what you passed on — file this week's deferred upgrades as issues with a date. A deferral that is not written down does not exist next week

One more thing about bot PRs. Automatic update tools exist to keep dependencies updated even when they do not have any vulnerabilities, so the mere fact that a PR opened is not a security event. Line up security PRs and freshness PRs in the same queue and the genuinely urgent one gets buried. Labels or channels, the two streams have to look different. And such collection pipelines usually carry a repository access token; where those tokens leak is covered in the token is sitting in your remote URL.

What the people writing release notes can do

All of the above is the reading side. The work available on the writing side is far cheaper and lands harder. A release note is a document about what has to be done, not about what got committed.

  • Do not leave the Security section out — if there is nothing, say there is nothing. An absent section and an empty one are completely different information to the reader
  • Put breaking changes on the title line — a breaking change on line twenty of the body is the same as no breaking change. The ! marker or the footer in the commit convention creates that slot
  • Treat a default change as breaking — the version number may say minor, but downstream it is breaking. Most of the fourth category above is born right here
  • Publish the deprecation and the removal date together — 「will be removed later」 is not a date. The Kubernetes API deprecation policy is close to the right shape: GA versions may be marked deprecated but must not be removed within a major version, beta versions are deprecated no more than 9 months or 3 minor releases after introduction whichever is longer and are no longer served after the same interval again from deprecation, and alpha versions may be removed in any release without prior notice
  • Emit a runtime warning — it is the only path that reaches someone who did not read the note. The Warning header and the deprecated-API call metric above are the example
  • Write migration guides in code — not 「this changed」 but 「turn this code into this code」. Two lines of before and after read faster than ten lines of explanation

The same policy document carries one more rule worth borrowing: API elements may only be removed by incrementing the version of the API group. Once an element is in a given version it cannot be pulled out of that version or have its behaviour significantly changed. What that gives downstream is the assurance that the ground will not move while you stay on this version, and that assurance is what makes it possible to treat upgrading as a plan.

Deferring accrues interest

The decision to defer an upgrade is frequently the right one. It is not needed now, nobody is free now, and there is no reason to create risk now. The problem is that what accumulates during the deferral is hard to see.

  • You lose the deprecation warnings entirely — warnings only fire on versions you actually pass through. Skip three majors at once and you never once see what the intermediate releases would have told you, and you take all of those changes at the same moment. This is the largest real cost of a deferred upgrade
  • Migration guides interlock — guides are written to be climbed one step at a time. Skip three steps and the preconditions of each stop matching, and in the end none of the guides applies as written
  • Security fixes land only on the newest branch — this policy is common. The further behind you are, the more likely a single vulnerability forces an unplanned large upgrade
  • Other upgrades get blocked too — one stale package holding an upper bound drags everything interlocked with it. Ten lines stop moving because one line will not

So one working rule is enough. Write the deferral down and put a date on it. A deferral without a date is not a decision, it is forgetting, and the cost of forgetting arrives as one bill later. The moment that bill arrives is usually not ours to pick.

Summary

Reading every release note is impossible, so the goal is selection rather than diligence. Four things need pulling out: security fixes, breaking changes, deprecation notices, and items where behaviour changed with no label at all. The first three have notation conventions, so a machine can build the shortlist. The fourth has none, so a person has to distrust particular words. Incidents mostly come from the fourth.

A version number is a signal, not a guarantee. SemVer tells you there is an incompatible change when major went up; it does not tell you that you are safe when major did not. The same holds on the security side. A score measures severity, it does not set the queue, and what sets the queue is real exploitation and how exposed your environment is.

The boundary of automation is equally clear. Information inside the upstream repository gets answered by a machine; information inside your code does not. 「This release contains a security fix」 can be found, but 「our code is affected」 cannot. So what you should expect from a tool is a shorter list, not the disappearance of judgement.
