계기 — 호스트를 오염시키지 않는 개발 환경에 대한 요구

개발 환경에서 라이브러리 충돌과 의존성 오염은 오랜 숙제다. 한 시스템에서 서로 다른 버전의 컴파일러, C 런타임, 특정 배포판 전용 패키지를 동시에 다루다 보면 호스트 운영체제의 시스템 파일이 쉽게 꼬인다. 최근 원자적(atomic) 배포판이나 불변(immutable) 파일시스템을 채택한 운영체제가 주목받는 이유도 바로 여기에 있다. 불변 운영체제는 기본 루트 파일시스템을 읽기 전용으로 보호하여 운영체제의 안정성을 보장하지만, 개발자가 일상적으로 수행하는 패키지 설치(apt install 또는 dnf install)나 시스템 레벨 데몬 테스트를 까다롭게 만든다.

Windows 환경에서는 Windows Subsystem for Linux(WSL)가 이 문제를 실용적으로 해결해 왔다. 호스트 시스템의 레지스트리나 핵심 파일을 건드리지 않고도 격리된 Linux 인스턴스 안에서 패키지를 설치하고, 호스트 디렉터리를 마운트하여 소스 코드를 편집할 수 있기 때문이다. GeekNews에 소개된 오픈소스 프로젝트 NSL(NSpawn Subsystem for Linux)은 이러한 WSL의 사용자 경험을 불변 Linux 환경으로 가져오려는 시도다. 지시서의 일부 요약에서는 이를 「WSL용 Linux」로 표기하기도 했으나, 원문 저장소의 정의에 따르면 NSL은 불변 Linux 호스트 위에서 WSL과 같은 격리 개발 경험을 제공하는 「Linux 호스트용 WSL 스타일 도구」다.

이 글에서는 Microsoft Learn 공식 문서에 기록된 WSL 2의 가상 머신 격리 메커니즘을 먼저 짚고, NSL이 Linux 호스트 위에서 systemd-nspawn과 공유 가상 머신을 결합해 의존성을 격리하는 구조적 원리와 한계를 대조한다. 도구 간의 우열을 주관적으로 평가하는 대신, 각 아키텍처가 선택한 격리 경계와 파일시스템 연동 메커니즘을 문서에 명시된 사실을 중심으로 분석한다.

WSL 2의 격리 아키텍처 — Microsoft Learn 문서로 확인한 경량 VM 모델

Microsoft Learn 공식 문서에 기술된 WSL 2의 핵심 아키텍처는 완전한 Linux 커널을 구동하는 경량 가상 머신(Utility VM)에 기초한다. 호스트 Windows의 하이퍼바이저 위에서 작동하며, 다음과 같은 계층적 격리 원칙을 따른다.

  • 커널 공유 및 컨테이너 분리: 관리형 가상 머신 내부에서 단일 Linux 커널이 실행된다. 설치된 여러 Linux 배포판(예: Ubuntu, Debian)은 동일한 VM 커널과 메모리 공간을 공유하면서, PID·마운트·사용자·cgroup 네임스페이스로 격리된 컨테이너 형태로 구동된다.
  • 시스템 호출 호환성: 시스템 호출을 가로채 변환하던 WSL 1과 달리, 실제 Linux 커널 위에서 시스템 호출을 직접 처리하므로 FUSE 파일시스템이나 Docker 데몬과 같은 복잡한 시스템 수준 의존성을 온전히 지원한다.
  • systemd 지원: /etc/wsl.conf 파일의 [boot] 섹션에 systemd=true를 설정하면 배포판 내부에서 systemctl을 통해 백그라운드 서비스 데몬을 제어할 수 있다.
  • 인스턴스 이식성: wsl --export 명령을 통해 배포판 파일시스템 전체를 .tar 아카이브로 내보내고, wsl --import 명령으로 지정된 경로에 독립된 인스턴스로 복원할 수 있다.

이 구조는 Windows 호스트와 Linux 간의 파일시스템 접근이나 네트워크 연결에서 편의성을 제공하지만, 가상 머신 계층이 개입하므로 호스트 드라이브(9P 마운트)와의 I/O 오버헤드가 발생하거나 메모리 회수 정책에 따른 튜닝이 요구되는 기술적 특성을 갖는다. 아래는 Microsoft Learn 문서에 명시된 안전한 배포판 조회 및 백업 명령이다.

# 현재 설치된 WSL 배포판 목록과 버전, 실행 상태 확인
                    wsl --list -v
                    
                    # 특정 배포판의 전체 환경을 tar 아카이브로 안전하게 백업
                    wsl --export Ubuntu-24.04 backup_ubuntu.tar
                    
                    # 백업된 아카이브를 새로운 독립 인스턴스로 등록
                    wsl --import Custom-Dev C:\WSL\CustomDev backup_ubuntu.tar

NSL의 구조 — 불변 Linux 호스트 위의 공유 VM과 systemd-nspawn

Frostyard의 공식 문서에 따르면 NSL(NSpawn Subsystem for Linux)은 호스트 시스템의 패키지 관리자를 오염시키지 않으면서 다양한 Linux 배포판을 구동하기 위해 다층 격리 설계를 채택했다. 그 중심에는 systemd-nspawn과 공유 가상 머신(QEMU)의 결합이 있다.

전통적인 chroot 환경은 루트 권한 탈출이나 cgroup 자원 제어의 한계가 있었고, 일반적인 Docker 컨테이너는 애플리케이션 격리에는 적합하지만 다중 사용자 로그인이나 systemd 기반 서비스 관리를 기본 전제로 하지 않는다. 반면 systemd-nspawn은 경량 OS 컨테이너를 생성하여 배포판 전체의 init 시스템(PID 1)을 독립적으로 실행할 수 있도록 지원한다.

NSL은 불변 호스트 Linux 위에서 다음과 같은 4단계 레이어로 환경을 구성한다.

  • 비특권 사용자 실행: NSL 자체는 호스트의 일반 사용자 권한으로 실행된다. 호스트의 시스템 파일, 장치 권한, 그룹 설정, /etc/sudoers를 임의로 수정하지 않는다.
  • 공유 가상 머신 계층: 호스트 커널에 직접 nspawn 컨테이너를 올리는 대신, QEMU와 virtiofsd로 구동되는 공유 VM 내부에서 머신들을 실행한다. 이는 호스트 시스템 커널의 네임스페이스 권한 제약 없이도 완전한 루트 환경을 사용자에게 제공하기 위한 설계다.
  • systemd-nspawn 기반 머신: 공유 VM 내부에서 각 배포판은 독립된 systemd-nspawn 컨테이너로 인스턴스화된다. 패키지 설치 상태, 구동 중인 백그라운드 서비스, 사용자 파일은 세션이 종료된 후에도 영구적으로 보존된다.
  • 서명된 배포판 이미지 검증: Frostyard 게시 워크플로에서 매주 다시 빌드되며 서명 검증을 거친 이미지만 로컬에 캐시된다.

아래는 NSL 공식 저장소 README에 수록된 기본 머신 생성 및 실행 워크플로다.

# 서명 검증을 거쳐 Debian 13 이미지를 가져오고 첫 번째 기본 머신으로 생성
                    nsl create debian --distro debian:13
                    
                    # 현재 호스트 작업 디렉터리를 유지한 채 기본 머신의 로그인 셸 진입
                    nsl
                    
                    # 머신 내부에서 단일 테스트 명령을 실행하고 그 종료 상태(exit status)를 호스트로 반환
                    nsl run make test

파일시스템과 사용자 권한 연동 — /mnt/host와 UID 일치

개발자가 격리 환경을 사용할 때 가장 크게 겪는 불편은 파일 복사 작업과 파일 소유권 불일치다. 컨테이너 내부에서 root 권한으로 파일을 생성하면 호스트에서 일반 사용자가 해당 소스 코드를 편집하거나 git 커밋을 수행할 수 없는 권한 충돌 문제가 빈번히 발생한다.

NSL은 이 문제를 해결하기 위해 호스트 파일시스템 바인드와 사용자 매핑 메커니즘을 기본적으로 제공한다.

  • 호스트 디렉터리 매핑: 호스트의 사용자 홈 디렉터리($HOME), 이동식 미디어 경로(/run/media/USER), 그리고 마운트 지점(/mnt)이 머신 내부의 /mnt/host 경로 아래에 자동으로 노출된다.
  • 동일한 사용자 컨텍스트: 머신 내부의 계정은 호스트와 동일한 사용자 이름, UID, GID를 부여받는다. 따라서 머신 안에서 컴파일하거나 빌드한 결과물도 호스트 파일시스템 상에서 원래 사용자의 소유로 정확히 유지된다.
  • 내부 무암호 sudo: 머신 내부에서는 비밀번호 없이 sudo를 사용할 수 있는 권한이 부여된다. 개발자는 시스템 의존성 라이브러리를 자유롭게 apt install할 수 있지만, 이 권한은 머신 내부에 국한되며 호스트 시스템의 파일시스템에는 영향을 미치지 않는다.
  • 현재 작업 디렉터리 동기화: 호스트 터미널에서 특정 프로젝트 폴더에 위치한 상태로 nsl을 실행하면, 머신 내부에서도 동일한 프로젝트 경로가 현재 작업 디렉터리로 열린다.
  • 파일 백업과 인스턴스 내보내기: 정지된 머신을 단일 아카이브로 내보내고(export), 다른 호스트나 새 환경에서 그대로 가져올(import) 수 있다.

이러한 통합 설계는 개발자가 호스트의 텍스트 에디터로 코드를 작성하면서, 컴파일과 테스트 실행만 격리된 머신에 위임할 수 있도록 돕는다. 파일 전송 도구나 rsync 없이도 즉각적인 파일 공유가 이루어진다. 유사한 파일시스템 동기화 개념은 리눅스 Rsync 가이드에서도 다룬 바 있다.

네트워크 포트와 데스크톱 앱 연동 — 127.0.0.1 포워딩과 Waypipe

웹 개발이나 데스크톱 도구 개발 시 격리 환경 내부의 프로세스와 호스트 UI 간의 원활한 통신은 필수적이다. NSL은 네트워크와 그래픽 인터페이스에 대해 다음과 같은 연동 방식을 채택했다.

  • 로컬 포트 포워딩: 머신 내부에서 웹 서버나 API 서버가 특정 포트(예: 3000, 8080)를 열면, 호스트의 브라우저나 도구에서 별도의 IP 주소 조회 없이 호스트의 127.0.0.1 주소로 즉시 접근할 수 있다.
  • Waypipe 기반 데스크톱 창 연동: 머신 내부에서 실행되는 Wayland 기반 GUI 애플리케이션은 Waypipe 프로토콜 브리지를 거쳐 호스트의 데스크톱 화면에 창을 직접 띄운다. 이는 Windows 환경에서 WSLg가 Weston과 RDP를 통해 Linux GUI 창을 Windows 바탕화면에 띄우는 메커니즘과 유사한 경험을 제공한다.
  • SSH 기반 에디터 통합: nsl ssh-config 명령을 제공하여 VS Code의 Remote - SSH 확장이나 Neovim, 기타 SSH 클라이언트가 개별 머신을 독립된 호스트 별칭으로 인식하고 직접 연결할 수 있도록 지원한다.
  • 세션 간 영속성: Docker 컨테이너와 달리, 사용자가 세션을 종료하고 터미널을 빠져나와도 머신 내부에 설치된 패키지와 설정 파일, 생성된 데이터베이스 데이터는 유지된다.
  • 백그라운드 서비스 라이프사이클: 머신 내부의 systemd가 데몬을 관리하므로 백그라운드 데이터베이스나 개발 서버가 안정적으로 상주한다.

이러한 네트워크 및 디스플레이 공유는 호스트 운영체제와 머신 간의 경계를 개발자 관점에서 사실상 투명하게 만들어 준다.

완전 분리가 필요할 때 — --isolated 전용 VM과 보안 경계

앞서 다룬 호스트 파일시스템 마운트, 127.0.0.1 포트 포워딩, Waypipe 데스크톱 연동은 일상적인 개발 작업에는 최적의 편의를 제공하지만, 보안 관점에서는 명확한 양날의 검이다. 신뢰할 수 없는 써드파티 스크립트나 악성 의존성이 포함된 오픈소스 패키지를 머신 내부에서 실행할 경우, /mnt/host를 통해 호스트의 개인 파일에 접근하거나 로컬 네트워크를 탐색할 수 있는 공격 경로가 열릴 수 있다.

NSL은 이러한 위험을 차단하기 위해 --isolated 실행 모드를 공식적으로 분리하여 제공한다.

  • 전용 가상 머신 할당: --isolated 옵션으로 머신을 구동하면 다른 머신들이 함께 사용하는 공유 VM을 사용하지 않고, 오직 해당 머신만을 위한 독립된 전용 QEMU 가상 머신이 실행된다.
  • 호스트 파일시스템 차단: /mnt/host 바인드 마운트가 완전히 비활성화되어 호스트의 $HOME, 미디어, 시스템 경로에 대한 읽기·쓰기가 일체 차단된다.
  • 데스크톱 및 호스트 액션 분리: Waypipe를 통한 데스크톱 디스플레이 연동과 호스트 대상 액션 전달이 중단되어, 외부 소프트웨어의 영향력이 전용 가상 머신 메모리 및 디스크 영역 내로 완전히 격리된다.
  • 보안 테스트 용도: 검증되지 않은 패키지의 빌드 스크립트 실행, 의심스러운 바이너리 분석, 엄격한 샌드박스가 요구되는 작업에 적합한 격리 경계를 형성한다.
  • 호스트 액션 전달 차단: 호스트 시스템으로의 이벤트 통지나 IPC 메시지 전송이 차단되어 악의적 페이로드가 호스트로 전파되지 않는다.

이처럼 일상적 개발을 위한 「투명한 연동 머신」과 위험 분석을 위한 「완전 격리 머신」을 옵션 하나로 전환할 수 있는 구조는 시스템 관리자에게 유연한 안전망을 제공한다.

격리 단위와 구현 방식 비교 — WSLとNSL

두 도구는 지향하는 호스트 운영체제는 다르지만, 호스트를 건드리지 않고 완전한 Linux 환경을 제공한다는 동일한 엔지니어링 목표를 갖는다. 공식 문서와 저장소 명세를 바탕으로 확인된 격리 단위와 기술적 특성을 표로 정리한다.

격리 단위방식확인된 것미확인
호스트 시스템 보호호스트 루트와 개발 환경 분리WSL 2는 Windows 가상 디스크(VHDX) 기반 격리. NSL은 불변 Linux 호스트에서 QEMU 및 systemd-nspawn 컨테이너 분리대규모 동시 머신 기동 시 호스트 메모리 압박 임계치
파일시스템 접근호스트 저장소 마운트WSL 2는 9P/drvfs를 통해 Windows 드라이브 매핑. NSL은 virtiofsd를 통해 /mnt/host에 $HOME 마운트virtiofsd 마운트 경로에서의 SQLite 파일 잠금 안정성
사용자 계정 매핑UID 및 소유권 보존NSL은 호스트 UID/GID를 머신 내 동일 매핑하여 파일 소유권 유지 및 무암호 sudo 지원. WSL 2는 wsl.conf의 default user 지정호스트 다중 사용자 환경에서 UID 충돌 시 처리 규칙
네트워크 및 GUI포트 및 디스플레이 노출WSL 2는 가상 어댑터 및 WSLg(Weston/RDP). NSL은 127.0.0.1 포트 포워딩 및 Waypipe 창 렌더링Waypipe 환경에서 GPU 하드웨어 가속 지원 범위

이어서 NSL의 배포판 이미지 지원 현황과 공식 문서로 확인된 구동 환경 조건을 정리한다.

배포판 및 환경 항목원문 명세동작 원리 및 조건검증 상태
공식 지원 배포판 이미지7종 (Debian 13, Ubuntu 26.04 LTS, Fedora 44, CentOS Stream 10, Arch, openSUSE Tumbleweed, openSUSE Leap 16.0)매주 자동 재빌드되며 Frostyard 게시 워크플로에서 서명 검증 후 로컬 캐싱공식 README 문서에 명시됨
라이선스 및 릴리스 상태MIT 라이선스, 현재 v0.4.0v0.4.0이 현재 아키텍처의 첫 릴리스이며 v0.3.0 이하는 폐기된 프로토타입. 아직 안정(stable) 버전 없음공식 저장소 문서에 명시됨
호스트 권한 및 사전 요구조건일반 사용자 권한으로 구동호스트 패키지 임의 설치나 sudoers 수정 없음. QEMU, virtiofsd 등 필수 의존성은 호스트에 사전 설치 필요공식 시작 가이드에 명시됨
기준 테스트 환경Snow Linux 13, x86-64systemd 261.2, QEMU 10.0.13, virtiofsd 1.13.2, GNOME Wayland 환경에서 테스트 완료GeekNews 및 공식 릴리스 정보에 명시됨

위 표에서 보듯 NSL은 가볍고 투명한 개발 환경을 제공하지만, v0.4.0의 초기 개발 단계에 머물러 있어 운영 환경의 표준 격리 플랫폼으로 도입하기에는 아직 성숙도가 부족하다. 특히 호스트 시스템에 QEMU, virtiofsd 등의 가상화 구성 요소가 미리 갖추어져 있어야 한다는 점은 진입 장벽으로 작용할 수 있다.

확인하지 못한 것

  • NSL 머신 내부에서 Docker나 Podman 같은 중첩 컨테이너 런타임이 정상 동작하는지에 대한 공식 기술 문서의 기술 여부.
  • Waypipe를 통한 GUI 애플리케이션 구동 시 OpenGL/Vulkan 기반 3D 그래픽 하드웨어 가속이 virtio-gpu를 통해 지원되는지 여부.
  • x86-64 아키텍처 외에 AArch64(ARM64) 환경에서의 배포판 빌드 이미지 제공 및 지원 여부.
  • 공유 VM 상태에서 여러 개의 머신이 동시에 실행될 때 CPU 및 메모리 자원 할당을 세부 제어(cgroup limit)할 수 있는 설정 옵션의 존재 여부.
  • 호스트 파일시스템 마운트(virtiofsd) 환경에서 대용량 파일 I/O 수행 시 네이티브 파일시스템 대비 성능 벤치마크 수치.
