모든 요청을 비싼 모델에 맡기지 않는다 - API를 그대로 두고 모델만 바꿔 끼우는 LLM 라우터와 Switchyard

단일 프롬프트 난이도 추정을 넘어 도구 실행 실패 이력으로 모델을 교체하는 계층, 프로토콜 프록시 설계와 프롬프트 캐시·지연시간의 실질적 대가

2026-09-12 개발/인프라

대규모 언어 모델을 소프트웨어 제품과 자율 코딩 에이전트 루프에 내장하는 엔지니어링 환경에서 가장 흔히 마주치는 딜레마는 명확하다. 모든 사용자 쿼리와 내부 도구 실행 턴을 최고 성능의 플래그십 모델에 위임하면 작업 완결률과 추론 정확도는 올라가지만, 분당 수천 건의 세션이 누적되는 순간 인프라 청구서가 통제 불가능할 정도로 폭증한다. 반대로 운영비를 아끼기 위해 경량 모델을 일괄 적용하면 복잡한 코드 리팩터링이나 다단계 디버깅 작업에서 치명적인 환각과 논리 결함이 발생한다.

이 간극을 메우기 위해 많은 시스템은 애플리케이션 코드 곳곳에 조건 분기문을 작성해 특정 키워드나 작업 유형에 따라 서로 다른 모델을 호출하는 방식을 취해 왔다. 그러나 하드코딩된 모델 선택 로직은 공급자 API 규격이 바뀌거나 새로운 단가 효율적 모델이 출시될 때마다 애플리케이션을 다시 빌드하고 배포해야 하는 거대한 유지보수 부채를 양산한다. 이러한 문제를 인프라 계층에서 근본적으로 분리하기 위해 등장한 개념이 바로 LLM 라우터(LLM Router) 계층이다.

NVIDIA NeMo 생태계의 일환으로 공개된 오픈소스 프로젝트 Switchyard는 이 아키텍처적 전환점을 명확히 대변한다. Switchyard의 설계 목표는 에이전트 코드를 단 한 줄도 수정하지 않은 상태에서, 각 LLM 호출을 해당 작업을 완수할 수 있는 가장 저렴한 모델로 동적 분기하는 것이다. 이 글은 단순한 도구 소개를 넘어 소프트웨어 시스템이 왜 모델 선택을 전담하는 라우팅 계층을 필요로 하는지, 런타임 도구 실행 이력을 기반으로 모델을 상향 배정하는 Stage Router의 발상이 무엇을 바꾸는지, 그리고 라우터를 시스템 중간에 끼워 넣을 때 감수해야 하는 실질적인 비용과 지연시간의 대가를 면밀하게 분석한다.

모델 고정 코드가 남기는 기술 부채와 라우팅 계층의 등장

초기 생성형 AI 통합 패턴에서는 모델 이름이 코드베이스 깊숙한 곳에 리터럴 문자열 형태로 박혀 있는 구조가 일반적이었다. SDK 인스턴스를 초기화할 때 model="gpt-4o" 또는 model="claude-3-5-sonnet"과 같이 대상 모델을 정적으로 명시하는 방식이다. 그러나 이러한 정적 결합은 제품이 성숙해질수록 다음과 같은 세 가지 심각한 구조적 한계를 노출한다.

  • 모델 변경 시 배포 수명 주기 종속: 주요 모델 공급자들은 수개월 주기로 가격 인하를 단행하거나 성능이 개선된 신규 세대 모델을 내놓는다. 코드 안에 모델 식별자가 박혀 있으면, 단가를 낮추거나 최신 버전을 적용하기 위해 전체 서비스를 다시 빌드하고 스테이징 배포 파이프라인을 거쳐야 한다.
  • 요청 난이도와 모델 비용의 극단적 비대칭: 단일 에이전트 세션 안에서도 사용자가 보낸 단순 인사말 처리, 파일 탐색 목록 조회, 마크다운 문서 서식 정리 같은 저난도 작업과, 동시성 버그 추적 및 다중 모듈 아키텍처 리팩터링 같은 고난도 작업이 공존한다. 고정 모델 구조에서는 모든 작업에 플래그십 모델의 단가가 부과된다.
  • 공급자 장애 및 쿼터 고갈 시 복원력 부재: 특정 모델 벤더에서 HTTP 429(속도 제한)나 500 계열 서버 오류가 발생했을 때, 애플리케이션 계층에 대체 모델 폴백 로직이 개별 구현되어 있지 않으면 서비스 전체가 즉시 마비된다.

전통적인 마이크로서비스 아키텍처가 데이터베이스 접근 제어나 외부 결제 게이트웨이 연동 시 프록시 계층을 두어 상위 비즈니스 로직을 보호했던 것처럼, AI 인프라에서도 모델 식별과 호출 책임을 애플리케이션 밖으로 떼어내는 독립 라우팅 계층의 등장은 필연적인 흐름이다. 클라이언트는 특정 모델의 이름을 직접 호출하는 것이 아니라, 자신이 해결하고자 하는 논리적 라우트 정책을 호출하고, 실제 업스트림 벤더와 물리적 모델의 매핑은 라우터가 동적으로 결정하는 구조다.

클라이언트를 건드리지 않는 프로토콜 프록시 설계

새로운 인프라 계층을 도입할 때 엔지니어링 조직이 겪는 가장 큰 장벽은 기존 클라이언트 코드의 재작성 비용이다. 사내 개발팀이 이미 구축해 둔 방대한 프롬프트 파이프라인, 서드파티 터미널 에이전트 도구, 오픈소스 워크플로 프레임워크를 새로운 사유 SDK 규격으로 전환해야 한다면 라우터의 도입 장벽은 극도로 높아진다.

따라서 실무에서 기능하는 LLM 라우터의 핵심 설계 요건은 업계 표준 API 프로토콜과의 무손실 호환성이다. Switchyard는 클라이언트가 바라보는 인터페이스로 업계에서 가장 광범위하게 쓰이는 세 가지 표준 형식을 완전히 지원하도록 설계되었다.

  • OpenAI Chat Completions 형식: 기존 /v1/chat/completions 엔드포인트를 그대로 노출하여 OpenAI 공식 SDK, LangChain, LlamaIndex 등 표준 라이브러리와 무수정 연동된다.
  • OpenAI Responses 형식: 구조화된 출력 및 차세대 대화형 응답 인터페이스 규격을 포괄한다.
  • Anthropic Messages 형식: /v1/messages 엔드포인트를 노출하여 Claude 전용 클라이언트와 개발자 도구가 환경 변수 ANTHROPIC_BASE_URL의 수정만으로 프록시를 경유하도록 지원한다.

이러한 프로토콜 호환 프록시 설계 덕분에 클라이언트는 자신이 단일 모델과 직접 통신하고 있는지, 아니면 중간의 프록시가 요청을 분해해 최적의 백엔드로 전달하고 있는지 전혀 인지할 필요가 없다. 클라이언트는 평소처럼 네이티브 API 호출을 전송하고, 라우터는 중간에서 요청 페이로드를 가로채 헤더의 세션 식별자나 메시지 기록을 검사한 뒤 목적지 모델을 선정한다.

Switchyard의 구조와 아키텍처 — libsy부터 switchyard-server까지

NVIDIA NeMo의 Switchyard는 단일 바이너리 도구에 그치지 않고, 시스템 통합 깊이에 따라 선택할 수 있는 다층적 Rust 크레이트 모듈로 설계되어 있다. Apache-2.0 라이선스로 배포되는 Switchyard 저장소의 핵심 크레이트 구성과 각 컴포넌트의 안정성 단계는 다음과 같이 명확히 구분되어 있다.

라이브러리 내장과 독립 프록시의 두 가지 경로

엔지니어링 팀은 Switchyard를 시스템에 결합할 때 두 가지 상이한 통합 방식을 선택할 수 있다. 첫 번째는 라이브러리 내장 방식이다. Python 환경에서는 pip install nemo-switchyard를 통해, Rust 환경에서는 switchyard-libsy 의존성을 추가하여 기존 게이트웨이나 워크플로 엔진 내부에 라우터 알고리즘을 직접 탑재한다. 이 방식의 결정적인 장점은 실제 HTTP 모델 호출, 네트워크 재시도, 인증 토큰 주입 책임을 기존 하네스가 온전히 유지한다는 점이다. Switchyard는 순수 함수처럼 어떤 모델을 선택해야 하는지만 반환하므로, 기존 인프라의 전송 계층 안정성을 전혀 해치지 않는다.

두 번째는 독립 프록시 서버 방식이다. switchyard-server 바이너리를 구동하고 단일 TOML 구성 파일을 통해 업스트림 클라이언트와 라우팅 규칙을 정의한다. 기존 게이트웨이가 없거나 외부 개발 도구에 즉시 라우팅을 적용하고자 할 때 포트 4000 등 로컬 엔드포인트를 열어두고 클라이언트 연결 주소만 변경하면 된다.

# Switchyard 독립 프록시 설정 예시 (routes.toml)
schema_version = 1

[llm_clients.upstream_openai]
format = "openai_chat"
base_url = "https://api.openai.com/v1"
api_key_env = "OPENAI_API_KEY"

[targets.flagship_model]
id = "gpt-4o"
llm_client = "upstream_openai"

[targets.efficient_model]
id = "gpt-4o-mini"
llm_client = "upstream_openai"

[routes.stage_coding]
id = "switchyard/stage"
type = "stage_router"
capable_target = "flagship_model"
efficient_target = "efficient_model"
picker = "efficient_first"
confidence_threshold = 0.5

컴포넌트별 안정성 등급과 1.0 이전의 제약

현재 Switchyard 저장소의 작업 공간 패키지 버전은 0.2.0으로, 공식 문서에서도 명시하듯 아직 1.0 이전의 초기 개발 단계에 머물러 있다. 핵심 라이브러리인 switchyard-libsy는 베타 단계에 도달해 비교적 견고하지만, HTTP 호출과 포맷 번역을 담당하는 switchyard-llm-client나 러너 모듈은 알파 상태다.

특히 독립 실행 프록시인 switchyard-server는 공식 분류상 Demo 등급으로 지정되어 있다. 이는 기능 평가나 로컬 개발 환경에서의 테스트 용도로 적합하며, 무정지 운영이나 대규모 트래픽 처리가 요구되는 엔터프라이즈 프로덕션 환경에 단독 프록시로 배치하는 것은 아직 권장되지 않는다는 의미다. 따라서 실무 환경에서는 기존에 검증된 게이트웨이(예: NeMo Relay, LiteLLM)의 공식 플러그인 인터페이스를 통해 알고리즘을 결합하거나, 라이브러리 형태로 직접 임베딩하는 방식이 훨씬 안정적이다.

Stage Router의 메커니즘 — 실패 이력과 도구 실행 신호로 모델을 올린다

기존의 초보적인 LLM 라우터들은 대부분 프롬프트 기반 단일 분류기 구조를 채택해 왔다. 사용자가 보낸 첫 번째 프롬프트를 작은 경량 분류 모델이나 임베딩 모델에 넣고, 그 텍스트의 난이도나 카테고리를 추정해 특정 모델로 분기하는 방식이다. 그러나 코딩 에이전트 환경에서 이 접근법은 치명적인 결함을 드러낸다.

현실 세계의 개발자는 복잡한 커널 메모리 누수 버그를 제보할 때도 단순히 「이 오류 고쳐줘」라는 짧은 프롬프트만 입력할 수 있으며, 반대로 단순한 오타 수정을 요청하면서 수백 줄의 장황한 배경 설명을 첨부할 수도 있다. 즉, 최초 사용자 입력 텍스트만으로는 실제 디버깅 과정의 복잡도를 사전에 예측할 수 없다. 작업의 진짜 난이도는 에이전트가 코드를 수정하고, 터미널 명령을 실행하고, 테스트 스위트를 돌려보는 실행 런타임에서 비로소 드러난다.

Switchyard의 Stage Router는 바로 이 지점에서 근본적인 발상의 전환을 보여준다. 정적 텍스트 예측을 포기하고, 에이전트가 지금까지 도구를 실행하면서 무엇을 실패했는지를 런타임 신호로 포착해 모델의 상향 배정 여부를 결정한다.

도구 신호 추출기가 포착하는 오류 패턴과 심각도

Switchyard 내부 모듈인 tool_signals.rs는 대화 기록 내의 모든 도구 호출과 그 반환 결과를 순회하며 정규화된 텍스트 패턴 매칭을 수행한다. 네트워크 I/O나 추가 모델 호출 없이 순수 메모리 연산으로 동작하는 이 프로세서는 실패 신호를 세 가지 엄격한 심각도 상수로 분류한다.

  • CRITICAL (가중치 1.0): 프로세스 메모리 고갈(out of memory, memoryerror), 소켓 연결 거부(connection refused, econnrefused) 등 작업이 완전히 교착 상태에 빠졌음을 알리는 시스템 장애.
  • HARD (가중치 0.7): 파이썬 예외 트레이스백(traceback (most recent call last)), 모듈 임포트 실패(modulenotfounderror:), 셸 명령 부재(command not found), 단언문 실패(assertionerror), 문법 오류(syntaxerror:), 실행 시간 초과(timed out, deadline exceeded), 파일 미존재(filenotfounderror:, file does not exist).
  • SOFT (가중치 0.3): 상세 트레이스백은 없으나 0이 아닌 비정상 종료 코드(exit code 1, exit status 1, returned non-zero)를 반환한 경우.

여기에 더해 신호 추출기는 에이전트의 도구 사용 유형을 edit(수정), write(생성), read(단순 조회), plan(계획 수립)으로 나누어 추적한다. 또한 테스트 실행 결과에서 " passed", "all tests passed", "test result: ok", "✓ " 등의 구문이 감지되면 테스트가 성공한 것으로 판단하고, "✗ ", "fatal:", "error:" 등이 나타나면 즉시 실패로 판정한다.

신뢰도 부족 시의 판단 위임과 폴백 메커니즘

Stage Router는 기본적으로 picker = "efficient_first" 전략을 취한다. 즉, 새로운 세션이나 명확한 실패가 없는 초기 탐색 및 파일 읽기 단계에서는 가장 저렴한 efficient_target(예: GPT-4o-mini급)을 배정한다. 그러다 에이전트가 코드를 수정했음에도 테스트 스위트에서 단언문 오류가 연속으로 터지거나, 동일한 파일 수정에서 구문 오류가 반복되는 등 장애 지표가 누적되면, 내부 신뢰도 임계값(confidence_threshold, 기본 0.5)을 넘는 순간 다음 턴의 요청을 플래그십 모델인 capable_target으로 전격 승격시킨다.

만약 도구 실행 이력의 신호가 모호하여 신뢰도 임계값에 도달하지 못하면, 라우터는 억지로 모델을 고르는 대신 판단을 기권하고 캐스케이드 하위의 LlmTaskClassifier(작은 판별 모델을 이용한 2차 평가)로 폴백하거나, 시스템에 미리 지정된 기본 계층으로 안전하게 위임한다. 이처럼 실패의 증거가 명확할 때만 비싼 모델을 호출한다는 메커니즘은 불필요한 모델 상향 배정을 원천적으로 차단한다.

라우터 도입이 치르는 대가 — 지연, 캐시 손실, 단일 장애점

어떠한 인프라 계층도 공짜로 주어지지 않는다. LLM 라우터가 약속하는 토큰 비용 절감 효과 뒤에는 시스템 아키텍처가 반드시 감수해야 하는 실질적인 엔지니어링 대가가 숨어 있다. 이 대가를 정밀하게 계산하지 않은 채 라우터를 도입하면, 아낀 토큰 비용보다 더 큰 운영 손실을 입게 된다.

프롬프트 캐시 적중률 붕괴의 경제적 역풍

현대 클라우드 LLM 인프라에서 가장 극적인 비용 절감 수단 중 하나는 공급자 레벨의 프롬프트 접두사 캐싱이다. Anthropic의 프롬프트 캐싱이나 OpenAI의 자동 프롬프트 캐시는 이전 턴에서 이미 전송했던 긴 시스템 프롬프트, 저장소 구조 정보, 대화 컨텍스트가 동일하게 유지될 경우 입력 토큰 요금을 50%에서 최대 90%까지 대폭 할인해 준다.

그러나 턴마다 모델을 동적으로 바꿔 끼우는 라우팅 구조는 이 프롬프트 캐시 적중률을 정면으로 파괴한다. 예를 들어 1턴부터 4턴까지 3만 토큰의 컨텍스트를 쌓으며 A 모델을 호출하다가, 5턴에서 Stage Router가 B 모델로 에스컬레이션을 단행하면 어떻게 되는가? B 모델의 캐시 저장소에는 해당 세션의 컨텍스트가 전혀 없으므로, 3만 토큰 전체가 캐시 미적중 일반 정가로 청구된다. 만약 A 모델의 캐시 적중 입력 단가가 저렴하고 B 모델의 비캐시 입력 단가가 높다면, 단 한 번의 모델 전환으로 인해 수십 턴 치의 절감액이 일시에 상쇄될 수 있다. 동적 라우팅이 진정한 경제성을 얻으려면, 모델 전환으로 얻는 출력 단가 절감액이 프롬프트 캐시 미스로 인한 손실액을 충분히 압도해야 한다.

네트워크 홉 추가와 관측성 복잡도

라우터가 물리적 프록시 서버로 동작할 경우, 모든 HTTP 연결은 클라이언트와 LLM 공급자 사이에 최소 1회의 추가 네트워크 홉을 겪게 된다. 여기에 JSON 페이로드의 직렬화·역직렬화 오버헤드, 정규표현식 기반 신호 파싱 시간, 만약 LLM 분류기를 거친다면 추가 추론 지연시간까지 합산된다. 이는 사용자 체감 응답 속도를 저하시키는 요인이 된다.

아울러 시스템의 단일 장애점(SPOF) 리스크도 현실화된다. 모델 공급자가 정상 동작하고 있더라도, 중간에 위치한 프록시 프로세스가 강제 종료되거나 네트워크 병목을 겪으면 사내의 모든 에이전트 워크플로가 일제히 중단된다. README 는 독립 프록시에 두 개의 관측 면을 문서화해 두었다. 어느 타깃이 무엇을 처리했는지 돌려주는 /v1/stats 와, 요청·오류·지연·토큰·라우팅 오버헤드를 Prometheus 카운터로 내보내는 /metrics 다.

모델별 동작 차이와 재현성 — 도구 호출 및 포맷 파편화

인프라 엔지니어가 라우터를 도입할 때 흔히 간과하는 또 다른 문제는 서로 다른 모델 공급자 간의 행동 양식 불일치다. OpenAI와 Anthropic은 모두 도구 사용 규격을 지원하지만, 세부적인 동작 방식은 균일하지 않다.

  • 도구 스키마 해석 및 오류 복구 차이: 어떤 모델은 인자 스키마의 작은 타입 불일치를 알아서 묵인하고 유연하게 처리하지만, 다른 모델은 엄격하게 유효성 검사 오류를 반환한다.
  • 추론 태그 및 부가 토큰 처리: 생각 과정을 노출하는 추론 특화 모델과 일반 지시 모델 간의 시스템 프롬프트 해석 차이로 인해, 중간 턴에서 모델을 교체했을 때 에이전트의 페르소나나 지시 준수율이 흔들릴 수 있다.
  • JSON 출력 엄격성: 마크다운 코드 블록 안에 JSON을 감싸서 반환하는 습관이나 주석 허용 여부 등 사소한 출력 포맷 차이가 하류 파서의 파손을 유발할 수 있다.

Switchyard는 이러한 차이를 완화하기 위해 타깃 모델별로 고유한 system_prompt를 자동으로 앞에 덧붙이거나, 업스트림 요청에 공급자별 전용 파라미터(extra_body)를 병합하는 보정 기능을 제공한다. 그러나 본질적으로 서로 다른 가중치를 가진 모델들이 동일한 대화 맥락을 완벽히 매끄럽게 이어받을 수는 없으므로, 교체 대상 모델 풀을 구성할 때는 철저한 교차 회귀 테스트가 선행되어야 한다.

라우팅 효과를 객관적으로 측정하는 방법과 지표

라우터를 도입한 후 기술 문서나 보고서에서 흔히 볼 수 있는 실패 사례는 토큰 비용 절감률만을 단순 집계하는 것이다. 만약 모델을 저렴한 것으로 바꾸느라 작업 완결률이 반토막 났다면, 그것은 비용 절감이 아니라 서비스 품질 파괴에 불과하다.

작업 성공률을 고정한 상태에서의 순수 비용 측정

모델 라우팅의 효율성을 객관적으로 증명하기 위한 제1원칙은 작업 성공률을 엄격하게 고정한 상태에서 비용을 측정하는 것이다. 표준화된 자율 코딩 벤치마크 환경에서 동일한 문제 세트를 해결하도록 한 뒤, 최종 검증 테스트를 통과한 비율이 단일 플래그십 모델 대비 유지되는지 확인해야 한다.

실제로 Switchyard 저장소가 공개한 Terminal-Bench 2.1 벤치마크 데이터에 따르면, 단일 고정 모델들의 작업 정확도는 56% 미만에 머물렀다. 반면 Switchyard의 단계별(staged), 에스컬레이션(escalation), 분류기(classifier) 라우트는 단일 플래그십 기준점인 Opus 4.8 대비 13%에서 30% 적은 총비용으로 71%에서 76%의 정확도에 도달했다. 이처럼 성공률이 동등 이상인 조건 하에서만 비용 절감률은 기술적 설득력을 가진다.

계층 전환 빈도와 신호 오탐률 감사

프로덕션 운영 단계에서는 다음과 같은 시스템 메트릭을 실시간 모니터링해야 한다.

  • 모델 계층별 트래픽 분기 비율: 전체 에이전트 턴 중 경량 효율 모델이 흡수한 비율과 플래그십 모델로 승격된 비율의 시계열 변화.
  • 불필요한 상향 배정 빈도: 단순 경고 메시지나 정상적인 재시도 과정에서 오류 신호가 잘못 격발되어 비싼 모델을 호출한 비율.
  • 세션당 전송 토큰과 프록시 부가 지연시간: 라우터 도입 전후의 엔드투엔드 P95 및 P99 지연시간 비교 및 프롬프트 캐시 적중률 변동 추이.

가격 비교에서 동적 전환으로 — 단가 허브와의 연결

효율적인 LLM 라우팅 시스템을 구축하기 위한 필수적인 전제 조건은 각 공급자별 모델의 정확한 비용 구조를 파악하는 것이다. 입력 토큰당 가격, 출력 토큰당 가격, 그리고 캐시 적중 시와 미적중 시의 가격 격차가 얼마나 벌어지는지 모른다면 어떤 모델을 효율 계층으로 두고 어떤 모델을 상향 계층으로 삼아야 할지 기준을 세울 수 없다.

이와 관련하여 본 블로그의 가격 분석 허브인 Claude·GPT·Gemini·Grok·DeepSeek·GLM의 가격, 컨텍스트, 지역 가용성, 폐기 일정 비교 2026 글에서는 글로벌 주요 파운데이션 모델들의 최신 단가와 토큰당 과금 기준을 상세히 정리해 두고 있다. 해당 글이 「각 모델이 물리적으로 얼마인가」라는 정적 비용의 축을 다룬다면, 본 글에서 살펴본 Switchyard와 LLM 라우터는 「런타임 요청마다 무엇을 고를 것인가」라는 동적 인프라 통제의 축을 다룬다.

정적 단가 분석을 통해 가성비가 입증된 최신 경량 모델을 효율 계층에 배치하고, 검증된 플래그십 모델을 상향 계층에 연결한 뒤, 런타임 실패 신호에 따라 두 계층 사이를 유연하게 오가도록 설계하는 것이야말로 AI 엔지니어링이 나아가야 할 지속 가능한 비용 최적화 표준이다.

확인하지 못한 것

공개된 소스 코드 및 기술 문서의 공개 범위 제한으로 인해, 본 분석 과정에서 독립적으로 검증하지 못한 사항들은 다음과 같다.

  • 초당 수천 건 이상의 고부하 동시성 환경에서 switchyard-server의 정확한 P99 지연시간: 공개 저장소의 문서에는 기본 프록시 사용법과 Terminal-Bench 벤치마크 결과가 명시되어 있으나, 대규모 엔터프라이즈 환경에서 장시간 지속 부하를 가했을 때의 상세 레이턴시 백분위수 분포는 확인하지 못했다.
  • 합성 벤치마크를 벗어난 다양한 기업 실무 워크플로에서의 장기 누적 비용 절감액: README에는 Terminal-Bench 2.1을 기준으로 71~76% 정확도 달성 시 Opus 4.8 대비 13~30% 비용 절감 수치가 명시되어 있으나, 일반 고객 지원 챗봇이나 문서 요약 등 다른 도메인에서의 실측 통계는 공개되지 않았다.
  • 1.0.0 정식 안정화 버전(GA)의 구체적인 출시 로드맵과 일정: 현재 패키지 버전이 0.2.0이며 libsy는 베타, 서버는 데모 등급으로 지정되어 있다는 사실은 확인했으나, 하위 호환성을 보장하는 정식 1.0 배포 시점은 문서에 기재되어 있지 않다.
  • 이기종 모델 공급자 간 프롬프트 캐시 상태 동기화 지원 여부: OpenAI와 Anthropic 등 서로 다른 클라우드 제공업체 간에 턴이 전환될 때, 공급자 레벨의 KV 캐시 소실을 인프라 차원에서 완화하거나 상쇄할 수 있는 독자적인 공유 캐싱 기술의 구현 여부는 확인되지 않았다.
