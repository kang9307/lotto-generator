AI写的Next.js + Supabase会在哪里出事

从边界漏出去的密钥、开着却形同虚设的RLS、账单变高的区间，以及上线前确认它们的顺序

2026年8月3日 开发/基础设施

引言：能跑的代码和安全的代码是两种状态

页面都出来了。能登录、能发帖、部署也过了。走到这一步花的时间，按几年前的标准根本说不通。这正是Next.js配Supabase成为用AI快速做东西时事实标准的原因。认证、数据库、存储、实时、部署打成一个包送到手上，而生成模型见过的这种组合的代码比任何别的都多。

问题不在于这套技术栈不好。它确实是个不错的选择。问题在于有几处便利的抽象把运行原理藏了起来，而这几处偏偏就是出事的地方。密钥能走多远。控制台上写着策略已启用，和真正被拦住，到底差在哪里。服务端渲染怎么处理会话。连接会涨到多少。这些都跟页面渲不渲染得出来没关系，所以刚部署完看不出任何异常。看得出来的时刻，是流量涨上来的时候，或者有人打开浏览器开发者工具的时候。

下面把这些位置逐个过一遍。每一项都给出生成工具常见的写法、它为什么会在后面出事、以及在自己的项目里怎么检查、改成什么。全部按自查的角度来写，不涉及攻击手法。至于技术栈本身该按什么标准选，我在重新审视「选择无聊的技术」里单独写过。

1. 一个边界改变整个打包结果

AI给出的写法

需要交互的组件顶上加'use client'，然后在同一个文件里直接引入数据访问工具。工具里面是读取项目URL和密钥的代码。能跑，于是就留下了。

为什么后面会出事

'use client'不是改变单个文件性质的标记。Next.js官方文档把这个指令描述为在服务端和客户端模块图之间声明一条边界。文件一旦带上它，它引入的所有东西以及它直接渲染的组件都会被打进客户端包。你不是把一个组件挪到了客户端，而是把挂在它下面的整个模块图挪了过去。

这里有一道救命的保险，就是环境变量规则。文档写明只有带NEXT_PUBLIC_前缀的变量才会进入客户端包，没有前缀的变量会被替换成空字符串。所以即使服务端专用的工具被误带到客户端，密钥的值本身也不会被烤进包里。代价是那个函数会悄无声息地失效。

真正的事故发生在有人绕开这条规则的时候。最典型的版本是：本地读到undefined，于是在变量名前面补上NEXT_PUBLIC_就解决了。这一次修改就把密钥以明文字符串的形式烤进了构建产物。把报错原样丢给助手，得到这个修改建议并不罕见。

旁边还有两个不太为人所知的坑。

  • 公开变量在构建时被冻结。文档说构建结束后应用不再响应这些环境变量的变化。如果你把同一个镜像推到多个环境，每个环境用的都是构建那一刻的值。轮换了密钥，在重新构建之前旧的还会继续发出去。
  • 动态取值不会被内联。用变量拼出键名，或者先const env = process.env再访问，都不在内联范围内。以整理配置为由做这种重构，值会在运行时消失。

怎么查、怎么改

最可靠的检查是直接翻构建产物。代码评审看不到三层深的引入链。

# 构建后，在客户端包里找密钥的值
npm run build
grep -rF "$SUPABASE_SECRET_KEY" .next/static/ && echo "LEAK" || echo "clean"

# 不该公开的变量是否被声明成了公开前缀
grep -rn "NEXT_PUBLIC_.*\(SECRET\|SERVICE_ROLE\|PRIVATE\)" .env* next.config.*

修改的方向是在服务端专用模块里打个标记。引入server-only包之后，只要客户端组件试图引用这个模块，就会在构建阶段报错。不是在运行时悄悄拿到空值，而是构建直接停下，事故因此在部署之前就暴露出来。

// lib/supabase/admin.ts
import 'server-only'
import { createClient } from '@supabase/supabase-js'

// 这个客户端会绕过RLS，绝不能离开服务端。
export function createAdminClient() {
  return createClient(
    process.env.SUPABASE_URL!,
    process.env.SUPABASE_SECRET_KEY!, // 不加公开前缀
    { auth: { persistSession: false } }
  )
}

也可以用结构来解决。让服务端组件包住客户端组件，数据在服务端读取，只把可序列化的props传下去。文档介绍的children插槽模式就属于这一类：作为children传给客户端组件的服务端组件不会进入客户端模块图，传过去的只是服务端渲染好的结果。

2. 开启RLS并不算完事

AI给出的写法

建表并开启RLS的语句后面，紧跟着一条读取策略。名字通常是允许所有用户读取之类，条件是using (true)。

alter table public.posts enable row level security;

create policy "Enable read access for all users"
  on public.posts for select
  using (true);

为什么后面会出事

开启RLS之后，在创建策略之前什么都取不到。官方文档写明开启RLS后到创建策略之前，用可公开的密钥无法通过API访问任何数据。这是个安全的默认值。麻烦的是后面跟上的那条策略。using (true)是在RLS保持开启的同时把整张表重新敞开的策略。控制台里RLS徽章显示已启用，实际上匿名角色在读所有行。开启和拦住是两种状态，肉眼看起来却一模一样。

写策略时容易出偏差的地方还有几处。

  • 按命令分别生效。只有读取策略，写入就被拦住。反过来只建更新策略则更新不了，文档明确说执行更新需要有对应的读取策略。如果某个功能本地正常、只在生产失败，先看这个组合。
  • USING和WITH CHECK看的东西不同。USING决定已有行是否可见，作用于读取、更新、删除。WITH CHECK校验插入和更新之后的行是否满足条件。插入策略写成with check (true)，就拦不住有人插入带着别人所有者字段的行。在有所有者列的表上，这是最常见的口子。
  • 未登录请求里auth.uid()是null。文档解释此时条件会悄悄变成假、访问被拒绝，并建议显式检查是否已认证。它是往拦住的方向失败，所以不危险，但那些莫名其妙的空列表基本都是这个。
  • 不要拿用户元数据做授权。这是文档直接点名的常见错误。用户元数据可以被用户自己更新，因此读取其中的角色值来判断是不是管理员的策略会变成提权路径，文档明确给出的替代是应用元数据。
  • 视图默认绕过策略。视图在创建时若不指定，会以定义者权限运行，跳过底层表上的RLS。Supabase的安全顾问把这一项列为错误级别的检查项。那些在控制台里随手建了个视图来快速做列表页的项目，就栽在这里。

怎么查、怎么改

不要靠手工检查，跑顾问工具。Supabase控制台的数据库部分有安全顾问和性能顾问，修完之后可以重新运行。下面是和本文直接相关的检查项。

检查项抓什么级别
0013_rls_disabled_in_public公开模式下的表没开RLS。知道项目URL的人可以读取、修改、删除全部数据错误
0010_security_definer_view视图以定义者权限运行，绕过底层表的策略错误
0002_auth_users_exposed把认证用户表内容暴露给公开访问的视图错误
0007_policy_exists_rls_disabled策略建好了，但表上的RLS没开提示
0008_rls_enabled_no_policyRLS开了却没有策略，API访问全部被拦提示
0015系列依赖用户可修改元数据的策略-

修改的基本形态是围绕所有者按命令拆分策略。这里还附带一项性能措施：文档说把auth.uid()包成(select auth.uid())后，Postgres会按语句缓存结果，基准测试中约有95%的改善。文档同时建议给策略读取的列建索引，并用TO子句收窄目标角色。

-- 按命令拆开，所有者条件两个方向都加上
create policy "owner reads own rows"
  on public.posts for select to authenticated
  using ((select auth.uid()) = user_id);

create policy "owner inserts own rows"
  on public.posts for insert to authenticated
  with check ((select auth.uid()) = user_id);

create policy "owner updates own rows"
  on public.posts for update to authenticated
  using ((select auth.uid()) = user_id)
  with check ((select auth.uid()) = user_id);

create policy "owner deletes own rows"
  on public.posts for delete to authenticated
  using ((select auth.uid()) = user_id);

-- 给策略读取的列建索引
create index if not exists posts_user_id_idx on public.posts (user_id);

-- 如果用视图，就以调用者权限运行
create view public.post_summaries with (security_invoker = on) as
  select id, user_id, title, created_at from public.posts;

确实需要公开读取的表当然存在，公告列表和公开资料就是。即便如此，在用using (true)之前，先看这张表里有没有混着不该公开的列。如果邮箱地址或内部状态值也在同一张表里，答案是拆表而不是写一条更聪明的策略。策略只按行生效，不会帮你隐藏列。

3. anon key能做的事到底有多大

AI给出的写法

用NEXT_PUBLIC_前缀声明项目URL和可公开密钥，在浏览器里创建客户端。这是正确的代码。问题出在以此为据认为密钥管理已经做完了。

为什么后面会出事

官方文档确实说可公开的密钥在网络上暴露是安全的。但理由很重要。文档给出的理由是从公开组件中总能取回密钥。意思是隐藏从来就不是防线，而不是说这把密钥无害。带着这把密钥的请求以匿名角色运行，附上用户令牌后以认证角色运行。之后能看到什么，完全由RLS策略和模式权限决定。

所以结论是这样：可公开密钥泄露不是事故；可公开密钥加上没有RLS的表才是。顾问工具的错误级检查项在描述这种状态时说，知道项目URL的人可以读取、修改、删除全部数据，正是这个意思。

另一侧的密钥性质不同。文档说明它带有绕过RLS的属性、可完全访问项目数据，并要求不要把它放进网页、源码或可执行文件，也不要通过聊天或邮件发送。在浏览器里使用会返回401，但文档紧接着补了一句：这并不能阻止攻击者在别处使用它。401是防误用的装置，不是防御。一旦泄露，文档的指引是立即删除并轮换。

维度可公开密钥(publishable / anon)私密密钥(secret / service_role)
该放哪里浏览器、移动应用、CLI等公开组件仅限服务端、边缘函数等非公开组件
运行角色未登录为匿名角色，登录后为认证角色带有绕过RLS属性的角色
是否受RLS约束受，且这是唯一的防线不受，直接绕过
暴露之后设计上的前提；但RLS为空就是事故立即删除并轮换
Next.js环境变量加NEXT_PUBLIC_前缀不加前缀

怎么查、怎么改

  • 确认浏览器里用的确实是可公开密钥。项目设置的API部分会区分密钥类型。
  • 查看暴露给Data API的模式清单，默认是公开模式。不需要通过REST访问的表应迁到单独的模式并从暴露清单里移除。这样即便有密钥，API路径本身也不存在了。
  • 如果写过用于提权的函数，看看它在哪个模式里。文档明确警告不要在暴露的模式里创建定义者权限的函数。
  • 轮换密钥之后要重新构建客户端包。公开变量在构建时被烤进去，重新部署之前旧密钥还会发出去。

4. 会话与服务端渲染相遇的地方

AI给出的写法

在服务端组件或中间件里读会话，没有就跳转到登录页。这是把客户端的调用原封不动搬到了服务端。

// 服务端不要这么写
const { data: { session } } = await supabase.auth.getSession()
if (!session) redirect('/login')

为什么后面会出事

Supabase面向Next.js的服务端认证指南在这个位置挂了危险标记。第一句是服务端从Cookie里取会话，而Cookie任何人都能伪造；第二句是永远不要在服务端代码里信任getSession()。理由也写着：这个调用不保证重新校验认证令牌。当前指南建议保护页面和用户数据时使用getClaims()，它每次都会用公开的公钥验证JWT签名。直接向认证服务询问的getUser()也能达到同样目的。

事情还没完。会话遇上服务端渲染，还会多出三个坑。

  • 服务端组件写不了Cookie。所以必须有一层中间件来负责令牌刷新和传递。指南描述这一层做三件事：刷新认证令牌、把刷新后的令牌传给服务端组件、再把它传回浏览器。缺了这一层，会话会悄悄过期，用户会莫名其妙被登出。这类问题很难复现，也就很难变成一份有用的缺陷报告。
  • 缓存会把会话交给下一个人。登录状态下渲染的页面被CDN缓存后，下一个访问者会拿到那个页面。指南里设置Cookie的代码之所以一并传递缓存相关的响应头、并要求必须应用到响应上，原因就在这里。让个性化页面不要被静态缓存，这是渲染配置的事，不是认证配置的事。
  • 路由保护不等于数据保护。在中间件里拦住路径，对Data API毫无影响，它跟你的路由无关地开着。匹配清单里漏掉的那条路径，或者新加了却忘记登记的那条路径，要不至于直接变成数据泄露，就得让数据这一侧再被RLS拦一次。这就是第2项和第4项要分开检查的原因。

怎么查、怎么改

// app/dashboard/page.tsx
import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'

export default async function DashboardPage() {
  const supabase = await createClient()

  // 使用会向服务端请求校验的调用
  const { data: { user }, error } = await supabase.auth.getUser()
  if (error || !user) redirect('/login')

  // 这里RLS会再生效一次，保持两层。
  const { data: posts } = await supabase
    .from('posts')
    .select('id, title, created_at')
    .order('created_at', { ascending: false })

  return <PostList posts={posts ?? []} />
}
  • 在未登录状态下请求受保护路径，看返回的是跳转而不是200。用curl而不是浏览器，客户端跳转会把服务端真正返回的东西盖住。
  • 看同一个请求的响应头里的缓存字段。个性化页面上挂着共享缓存指令的话，先修这个。
  • 把中间件匹配清单和实际路由清单并排比对。手工维护的清单一定会漂移。把匹配写成默认保护、例外才公开，忘记登记新路径时也会往安全的方向失败。
  • 在代码库里搜出服务端文件中所有的getSession调用，逐个确认。

5. 无服务器环境下连接漏得不一样

AI给出的写法

把控制台复制来的连接串填进DATABASE_URL，接上ORM。端口5432。本地跑得好，部署上去也跑得好——在用户还少的时候。

为什么后面会出事

无服务器环境是请求变多则实例变多。每个实例各自持有连接池，所以100个并发请求就是100条连接。数据库有连接数上限，触顶之后新请求拿不到连接，只能等待或失败。应用日志里只留下超时，连问题出在数据库这件事都看不出来。连接耗尽这个现象本身和连接池的一般原理我在创业公司的Postgres生存指南里写过，这里只看Supabase和无服务器叠加时才有的那个选择题。

官方文档给出的三条路径目的各不相同。

路径端口适合约束
直接连接5432长期存活的虚拟机、容器等常驻服务默认IPv6，IPv4需要附加组件
连接池 会话模式5432在仅支持IPv4的网络里替代直接连接文档只在这种情况下推荐
连接池 事务模式6543无服务器、边缘函数等短连接很多的场景不支持预处理语句

文档称事务模式对需要大量瞬时连接的无服务器或边缘函数是理想选择，随即附上约束：该模式不支持预处理语句，为避免报错要在连接库里关掉这项功能。不关这个开关的话，负载低时什么都不会发生，等到连接开始被复用才出现间歇性错误。这就是那种复现不出来的错误的典型来源。

地址族也是一个安静的失败因素。直接连接默认IPv6，共享连接池在所有套餐上只支持IPv4。部署目标环境如果出不去IPv6，直接连接串会在建连阶段失败。生成的代码里看不出这个条件，而且本地是好的，就更容易让人困惑。

怎么查、怎么改

  • 确认部署环境里连接串的端口。无服务器函数走5432，这件事本身就是要处理的发现。
  • 如果用事务模式，确认库里的预处理语句开关关掉了。开关名字每个库都不同：Prisma是连接串里的pgbouncer=true，postgres.js是prepare: false。
  • 把迁移用的连接分开。模式变更工具有时依赖会话级状态，与事务模式合不来。应用走事务模式、迁移走直接连接或会话模式更稳妥。
  • 在模块顶层创建一次客户端并复用。在请求处理函数里每次新建连接池的代码，会让单个实例占住好几条连接。
  • 把连接数和等待状态当成指标来看。要看哪些东西才能发现异常，我在让数据库变得「可见」里整理过。

6. 迁移与模式漂移

AI给出的写法

聊天回答里给出一段可以粘进控制台SQL编辑器的SQL。粘上去一执行就生效。文件里什么都没留下。

为什么后面会出事

生产数据库的真实模式和仓库里的迁移文件开始分叉。这个状态带来四个后果。

  • 建不出新环境。想起一套预发布，能走到那一步的SQL哪儿都找不到。
  • 没有回滚依据。什么时候、为什么、改了什么，记录只在聊天记录里。
  • 没有评审。模式变更比应用代码更难撤销，偏偏是它跳过了审批。
  • 安全配置落在版本控制之外。RLS策略是模式的一部分。策略不在迁移文件里，就无从查证是谁在什么时候加了using (true)，而新环境建起来只有表、没有策略。

最后一条和本文其他项连在一起。第2项里策略写得再周到，只要它没有以代码的形式存在，下一次部署就会消失。

怎么查、怎么改

检查方式是把差异导出来。远端模式和本地迁移之间的差会以SQL的形式出现，结果为空才算正常。

# 关联项目
supabase link --project-ref <project-ref>

# 检查漂移，输出应为空
supabase db diff --linked

# 把已经手工改掉的东西回收成文件
supabase db diff --linked -f recover_manual_changes

# 之后一律先改文件
supabase migration new add_posts_rls
supabase db reset          # 在本地从头重放，验证可复现性
supabase db push           # 应用到远端
  • 把差异检查放进CI，输出不为空就让构建失败。漂移在出现当天回收最省事。
  • 策略、索引、函数也要放进迁移文件。只放表定义等于只管了一半。
  • 把本地重放变成习惯。从头跑一遍得不到相同结果的迁移，在新环境里一定会失败。
  • 大的模式变更不要一次上，拆开。拆分这件事本身我在GitHub 堆叠 PR 公开预览里写过，不停机变更时锁是怎么加的则在Postgres生存指南那边。

7. 账单变高的区间

AI给出的写法

查询取全部列，select('*')像默认值一样出现。图片是把存储里上传的原文件直接挂到img标签上。实时订阅在组件里打开，却没有清理代码。

为什么后面会出事

账单变高的位置一般不是数据库容量，而是出站流量。把2026年8月的公开价格页整理出来是这样。

项目Free($0)Pro($25/月)Pro超出单价
月活用户50,000100,000每人$0.00325
数据库容量500MB8GB每GB $0.125
出站流量5GB250GB每GB $0.09
文件存储1GB100GB每GB $0.0213
计算资源共享(500MB内存)每月$10抵扣额外项目单独计费

这里要读的不是绝对金额，而是计费单位是什么。出站流量按GB计费，而某个列表页每次都把整个大文本列或JSON列发下去，那么页面看着没问题，只有账单在长。图片也一样，把原始分辨率的文件挂在列表缩略图的位置，一次访问就是好几MB。

还有两个运营条件要确认。免费套餐一周没有活动项目就会被暂停，活跃项目最多两个。如果是把当初做验证用的项目直接当成生产，这个条件迟早会以服务中断的形式出现。Pro套餐默认开启支出上限，想超出套餐额度使用需要自己关掉。保持上限开启则账单不会飙升，但到额度就会被限流；关掉则相反。选哪边都行，最糟的是自己不知道在哪一边。

怎么查、怎么改

  • 在控制台的用量页面按项目逐条看。出站流量比预期大，就先找出哪些请求重。
  • 查询里写明列名。列表页需要的列通常就三四个。
  • 图片走转换或分尺寸存储，并加上缓存响应头。只要不每次都重新下发同一个文件，流量就会明显下降。
  • 实时订阅一定要在清理函数里取消。页面来回切换时订阅不断累积，连接和流量会一起涨。
  • 确认支出上限的设置，并让团队对选哪一边达成一致。
// 列表页只取需要的列
const { data } = await supabase
  .from('posts')
  .select('id, title, thumbnail_url, created_at')
  .order('created_at', { ascending: false })
  .range(0, 19)
2026年8月为准。计费项和单价会变。上表是查阅时公开价格页的数值，付费决定务必在官方价格页再确认一次。

8. 上线前依次过一遍

顺序是有意义的，因为上面的项是下面各项的前提。没有策略的情况下，路由保护做得再精细也没用；迁移里没有策略，改了策略也会在下次部署时退回去。

序号要确认什么怎么看通过标准
1公开模式下表的RLS运行安全顾问错误级检查项为0
2using (true)策略读策略清单并核对目标表只存在于有意公开的表上
3所有者列的插入与更新条件查看WITH CHECK子句两个方向都有所有者条件
4私密密钥是否进了打包产物构建后对产物做字符串搜索匹配数为0
5服务端代码里的会话判断搜索getSession调用不出现在授权判断的位置
6受保护路由的缓存响应头未登录状态用curl请求个性化页面上没有共享缓存
7无服务器的连接端口与选项检查部署环境变量事务模式下预处理语句已关闭
8模式漂移supabase db diff --linked输出为空
9流量最大的请求用量页面与查询代码对照列表查询里没有取全部列
10套餐与支出上限查看计费设置团队知道当前是哪种状态

这十行不是要一次做完的。第1到第4项是急的，其余等用户开始进来再做也不迟。不过第4项最好今天就做。密钥如果已经出去了，拖得越久回收成本只会越大。

未能确认的部分

  • 计费项、包含额度和超出单价是2026年8月公开价格页的数值。套餐结构会变，付费决定时需重新确认。超出额度后的具体限流行为因套餐和设置而异，因此没有做一般化。
  • getClaims()的返回结构以及是否适用非对称密钥验证，取决于项目设置和库版本。正文示例用的是形态稳定的getUser()。
  • 顾问工具的检查项编号和级别可能会更新。请以控制台显示的说明为准，而不是编号。
  • 哪个AI编程工具给出哪套默认模板，因工具和版本而异。正文里的「AI给出的写法」不指向任何特定产品，只是这套技术栈中反复出现的形态。
  • 各连接库的预处理语句选项以各自文档为准。除文中提到的两个例子外的组合，需要在对应文档里确认。

结论：需要掀开抽象的地方是有限的

这不是在劝你别用这套技术栈，恰恰相反。这个组合好在认证、数据库和策略集中在一处，需要确认的点很少，而上面那十行就是这些少数点的清单。自己拼装同样的能力，要验证同样的性质就得看多得多的地方。

AI写的代码问题也不在代码质量。生成模型是朝着产出能跑的代码优化的，而且做得不错。但能跑、安全、便宜是三个不同的目标，后两个不会显示在页面上。所以确认这件事留给了人。

如果只留一条标准，就是这条：如果你说不出一句话来概括这段代码拦住了什么，就当它还什么都没拦住。RLS已开启不是一句话。哪个角色在什么条件下能访问哪些行，才是一句话。练到能写出这句话大概要半天，而把它往后拖所花的时间无法预估。
