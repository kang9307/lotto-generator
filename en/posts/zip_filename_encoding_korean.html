Where Korean File Names Break Inside a ZIP - Who Wrote Them, and in Which Encoding

A file name is a byte string. How those bytes get read depends on one flag bit and on what the tool guesses

2026-07-30 Development/Infrastructure

Opening: the archive arrived and every name was broken

A ZIP came in from a partner company. Every file was there, but the names had turned into things like ║╕░φ╝¡.txt and 1║╨▒Γ ╕┼├Γ.xlsx. Ask the sender and the answer is «it looks fine on our side». The reverse happens just as often. Something you compressed and sent comes back as a complaint that the names are broken on the recipient's machine, and on yours nothing is wrong at all.

The reason this conversation repeats forever is that neither side did anything wrong. The usual advice at this point is «compress it as UTF-8», which is half right. Inside a ZIP archive a file name is stored as a plain byte string. The only mechanism for saying which encoding those bytes are in is a single flag bit, and what to read them as when that bit is clear is something the specification never decided.

So this is not an article about changing settings. It is about tearing an archive down to bytes and reading the file name field and the flag directly. Those two values pin the cause down immediately, and they also decide on the spot whether the damage can be undone. Every output below came from an actual run.

Environment. The archives were assembled byte by byte with struct, and on the reading side the central directory was parsed by hand rather than handed to a standard library. Every script was saved to a file before running, because code mixing Korean text with backslashes gets silently mangled when passed as a shell argument. Working paths are written as placeholders such as \work\demo.

Out of scope. Misconverted encodings in file contents, and how to diagnose them, are covered in cp949 and UTF-8, the two kinds of encoding error. The mechanics of Unicode normalization live in NFC and NFD. Here we look at exactly one thing: the file name field inside a ZIP archive.

1. What the specification does not decide

The ZIP format is specified by PKWARE's APPNOTE document. What it has to say about file name encoding is startlingly short. One sentence about bit 11 of the general purpose bit flag is effectively the whole of it.

Bit 11: Language encoding flag (EFS). If this bit is set, the filename and comment fields for this file MUST be encoded using UTF-8.

That sentence speaks only about the bit being set. What about when it is clear? Appendix D answers: the ZIP format has historically supported only the original IBM PC character encoding set. The default from the era before bit 11 existed is a DOS code page, and there is no way to declare that you are using anything else.

  • The file name field carries a length and a byte string, nothing more. There is no slot for an encoding name
  • Bit 11 only means something when set. Clear does not mean «not UTF-8», it means «not declared»
  • Which is why an undeclared UTF-8 archive can exist without violating anything. Nothing compels you to set the bit
  • Section 4.4.17 of the same document says path separators MUST be forward slashes. That one is mandatory. We meet a tool that breaks it later on
  • Conclusion: a broken file name is nobody's fault, it is a blank in the specification. Tools fill that blank in with their own guesses

Understanding that structure changes the next question. It stops being «what encoding is this» and becomes «is bit 11 set, and what are those bytes». Both are answered instantly by opening the archive.

2. Tearing the file name field down to bytes

First the materials. Written in two encodings, the same name produces bytes this different.

--- 2-1. one name, two encodings ---
name : 보고서.txt
  utf-8 bytes : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74   (13 B)
  cp949 bytes : BA B8 B0 ED BC AD 2E 74 78 74            (10 B)

name : 1분기 매출.xlsx
  utf-8 bytes : 31 EB B6 84 EA B8 B0 20 EB A7 A4 EC B6 9C 2E 78 6C 73 78   (19 B)
  cp949 bytes : 31 BA D0 B1 E2 20 B8 C5 C3 E2 2E 78 6C 73 78               (15 B)

One Korean syllable is three bytes in UTF-8 and two in cp949. So the same name exists in two forms, one 13 bytes long and one 10. Each byte string went into an archive, and the central directory was parsed by hand. First the shape an older tool produces.

That output is the entire diagnosis. Three lines are enough.

  • The flag is 0x0000. Bit 11 is clear, so this archive declares no encoding
  • The name bytes are BA B8 B0 ED BC AD. Decoding as UTF-8 raises, decoding as cp949 succeeds cleanly. The bytes tell you the encoding
  • There is no extra field. No second copy of the name is stashed anywhere
  • The verdict is definite: an undeclared cp949 archive. It looks correct on Korean Windows and breaks everywhere else

Note the as cp437 line. Reading the name bytes with the DOS era default code page yields ║╕░φ╝¡.txt. That is the string from the opening paragraph. The first symptom in this article was simply «an undeclared cp949 archive read according to the specification's default».

The flag is 0x0800. In binary that is 0000100000000000, and a single position, the twelfth from the right, is all that changed. That one bit is the declaration «this name is UTF-8», and it is the only way to communicate an encoding in the ZIP format.

3.1 The undeclared UTF-8 trap

There is a third case: bytes that are UTF-8 in an archive where bit 11 was never set. This too violates nothing.

=== C_utf8_noflag.zip  (141 B) ===
EOCD  entries=1  cd_offset=60  cd_size=59
--- entry 1 ---
  gp flag raw      : 0x0000   bin 0000000000000000
  bit 11 (UTF-8)   : not set
  name field len   : 13 bytes
  name field hex   : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74
  as utf-8         : [보고서.txt]
  as cp949         : <UnicodeDecodeError>
  as cp437         : [δ│┤Ω│á∞ä£.txt]
  extra len        : 0 bytes  (no extra field)
  • A and C have identical flag values. Both read 0x0000
  • But the name bytes differ. A only decodes as cp949, C only as UTF-8
  • So the flag alone is not enough. When the flag is clear you have to look at byte validity too to split the two apart
  • C breaks on Korean Windows instead. With the system code page at 949, UTF-8 bytes get read as 949
  • A and C failing in opposite directions is what makes this problem nasty. The fix for one manufactures the other

There is a way to read these samples. The kind of character you see tells you the cause.

  • Box drawing mixed with Greek letters, as in ║╕░φ╝¡, means the bytes were read as cp437. The DOS code page places box drawing and Greek characters in exactly that range
  • Han characters tangled with Hangul, as in 1遺꾧린 留ㅼ텧, means UTF-8 bytes were read as cp949. Something written three bytes at a time gets picked up two at a time and lands on accidentally valid characters
  • A run of replacement characters, as in ������, means cp949 bytes were read as UTF-8. Most cp949 pairs simply do not satisfy UTF-8's rules
  • º¸°í¼­.txt shows five visible characters where the original had three. The final byte AD becomes an invisible soft hyphen in latin-1. Any judgement based on counting characters goes wrong right here
  • Greek and Arabic characters turning up in broken samples is normal. They have nothing to do with the original; the wrongly applied code page just happened to have those characters at those positions

4.1 Why the extension disappears

In the samples above, 蹂닿퀬�꽌.txt still has its dot. Yet the name that actually landed on disk after extraction was 蹂닿퀬__txt. The extension is gone. Pairing the bytes up two at a time explains it.

--- 4-3. why the extension disappears ---
utf-8 bytes of the name : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74  (13 B)
cp949 reads two at a time:
  EB B3 -> [蹂] U+8E42
  B4 EA -> [닿] U+B2FF
  B3 A0 -> [퀬] U+D02C
  EC 84 -> <UnicodeDecodeError>
  9C 2E -> <UnicodeDecodeError>
  74 -> [t] single byte
  78 -> [x] single byte
  74 -> [t] single byte

the pair that eats the dot:
  9C 2E   the byte 2E is the '.' of .txt
          a cp949 lead byte 9C swallowed it

what the platform decoder returned for the same bytes:
  [蹂닿퀬??txt]
  U+8E42 U+B2FF U+D02C U+003F U+003F U+0074 U+0078 U+0074   (8 chars)
  chars illegal in a Windows file name : U+003F U+003F
  the extractor replaced them with underscores -> [蹂닿퀬__txt]

The chain is exact. Reading a UTF-8 name two bytes at a time meant the lead byte 9C dragged the dot in as its partner. That pair is not a valid character, so it became a question mark, and a question mark is illegal in a Windows file name, so the extractor swapped it for an underscore. The result is a file with no extension.

  • This is not «just the name». The extension is gone, so the file association is gone and a double click opens nothing
  • The dot gets eaten only when the third byte of the last Korean syllable falls in cp949's lead byte range. Depending on the name it happens or it does not
  • Which is why «some files keep their extension and some lose it» happens simultaneously inside one archive
  • A script that judges breakage by the presence of an extension quietly misclassifies here

5. Can it be reversed - it comes down to whether the bytes survived

Seeing a broken name invites an attempt at repair. The cases that work and the cases that do not were separated by running them. The working side first.

--- 5-1. bytes preserved in the archive -> reversible ---
  as reported by reader : [║╕░φ╝¡.txt]
  codepoints            : U+2551 U+2555 U+2591 U+03C6 U+255D U+00A1 U+002E U+0074 U+0078 U+0074
  re-encode cp437       : BA B8 B0 ED BC AD 2E 74 78 74
  decode cp949          : [보고서.txt]
  round trip ok         : True

  as reported by reader : [1║╨▒Γ ╕┼├Γ.xlsx]
  codepoints            : U+0031 U+2551 U+2568 U+2592 U+0393 U+0020 U+2555 U+253C U+251C U+0393 U+002E U+0078 U+006C U+0073 U+0078
  re-encode cp437       : 31 BA D0 B1 E2 20 B8 C5 C3 E2 2E 78 6C 73 78
  decode cp949          : [1분기 매출.xlsx]
  round trip ok         : True

Two steps. Re-encode with whatever encoding the reader applied to recover the original bytes, then decode those bytes with the correct one. Here the reader applied cp437, so we went back through cp437 and read as cp949. The proof of success is that the bytes came out identical to the original.

  original bytes     : BA B8 B0 ED BC AD 2E 74 78 74

  codepoints         : U+FFFD U+FFFD U+FFFD U+FFFD U+FFFD U+FFFD U+002E U+0074 U+0078 U+0074

  same as original   : False

The two failures are different in kind.

  • 5-2 is a tool that ground the bytes down. Some extractors transcribe the name into their own character set before writing it to disk. BA B8 turned into A6 A9. No encoding exists that brings the originals back
  • 5-3 is the replacement character eating them. A replacement character carries no information about which byte it stood in for. Ten bytes becoming twenty two is not more information, it is the same value repeated six times
  • Hence the order matters. Do not judge from the names that landed on disk; look at the bytes inside the archive first. If the archive is intact, unpack again with a different tool, and the fastest move for already extracted files with mangled names is to delete them and start over
  • Keeping the original archive file rather than deleting it is the first line of defence. With the archive in hand you can always go back

The third row is the most practical finding in this article. The tar command shipped with Windows 10 today writes file names as cp949 bytes and does not set bit 11. Nobody dug up a legacy tool; the standard utility that came with the operating system behaves that way. On a machine with no zip command, tar -a -c -f out.zip is the natural choice, and an archive built that way is guaranteed to break outside the same code page.

The first row hides a trap too. Python's zipfile sets bit 11 only when the name contains non-ASCII characters. The flag on readme.txt was 0x0000. Flags therefore differ per entry inside one archive, and a detection script that inspects only the first entry gets it wrong here.

This table is «it looks fine on our side» explained. The same archive is correct in one tool and broken in another. Three things stand out in particular.

  • The Windows tools read A correctly. With bit 11 absent they apply the system ANSI code page, which is 949. Build in Korea, unpack in Korea, nothing goes wrong. The failure only surfaces when the receiving side is a different environment

Three things are confirmed.

  • A directory goes in as its own entry whose name ends with a slash. The whole path sits in one name field, so if the folder name breaks, the paths of everything beneath it break with it
  • The separator byte 2F is safe. It falls outside cp949's lead byte range, so it never gets swallowed the way the dot did in section 4.1. The tool that writes 5C threw that safety away by itself
  • The length limit on the name field is counted in bytes. A 56 character name was 96 bytes in cp949. The same name in UTF-8 is longer, which means switching to UTF-8 lengthens names and brings path length limits closer
  • You can also build an archive whose directory entry is UTF-8 while the entries beneath it are cp949. The specification allows per entry flags, so mixing two encodings inside one archive is possible

9. When a decomposed name goes into an archive

  decomposed == composed : False
  utf-8 bytes decomposed : E1 84 87 E1 85 A9 E1 84 80 E1 85 A9 E1 84 89 E1 85 A5 2E 74 78 74 (22 B)
  utf-8 bytes composed   : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74 (13 B)
  decomposed to cp949    : <UnicodeEncodeError>
  composed to cp949      : BA B8 B0 ED BC AD 2E 74 78 74

--- 9-2. after extracting it, look for the file by its composed name ---
  Test-Path with composed name : False
  Test-Path with on-disk name  : True
  string equal                 : False
  directory filter by composed : 0 matches
  equal after composing        : True

9-2 is the point of this section. A file that displays as 보고서.txt exists on disk, and searching for it by that name reports it missing. The file is not absent, it exists as a different code point sequence.

  • The name field is 22 bytes, nine more than the composed form's 13. Writing jamo individually costs three bytes each, three times per syllable
  • Bit 11 is set. The declaration is perfect. It really is UTF-8 and decoding succeeds. This is not an encoding problem, it is a normalization form problem
  • The decomposed name cannot be encoded to cp949 at all. cp949 has only precomposed syllables and no mapping for the conjoining jamo block, so this name blows up on any path that recompresses with an older tool
  • Extractors write to disk exactly what they received. They do not normalize for you. In the environment tested the ten character decomposed name stayed as it was
  • Anywhere a script looks a file up by a hardcoded name, you quietly get zero results. It is not an error, it is «file not found», which makes it hard to notice
  • The fix is to normalize both sides to the same form before comparing. On the last line, after normalizing, they matched

10. The Unicode path extra field 0x7075

The specification offers one more detour: an extra field that carries the name in UTF-8 a second time without setting bit 11. APPNOTE 4.6.9 defines it as the Unicode Path Extra Field, header id 0x7075. An archive containing it was built and read.

=== E_cp949_with_up.zip  (179 B) ===
--- entry 1 ---
  gp flag raw      : 0x0000   bin 0000000000000000
  bit 11 (UTF-8)   : not set
  name field len   : 10 bytes
  name field hex   : BA B8 B0 ED BC AD 2E 74 78 74
  as utf-8         : <UnicodeDecodeError>
  as cp949         : [보고서.txt]
  extra len        : 22 bytes
    header id 0x7075 (Info-ZIP Unicode Path) len=18
      hex  : 01 00 D6 47 7B EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74
      ver=1  crc32-of-header-name=0x7B47D600
      unicode name : [보고서.txt]

--- 10-1. who honours it ---
  Python 3.13.3 zipfile   -> [보고서.txt]   U+BCF4 U+ACE0 U+C11C ...   honoured
  Windows tar.exe         -> [보고서.txt]                              honoured
  PowerShell Expand-Archive -> [보고서.txt]                            honoured
  UnZip 6.00              -> bytes EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74   honoured
  UnZip 6.00 with -UU     -> bytes C2 A6 C2 A9 C2 A6 C3 9D 2B C2 A1 2E 74 78 74   ignored

--- 10-2. which of our tools WRITE this field ---
  Python zipfile            : no
  PowerShell Compress-Archive : no
  Windows tar.exe           : no (writes 0x5455 and 0x7875 instead)

The result is interesting. All four tools tested honoured the field. Even UnZip 6.00, which ignored bit 11, read this field and produced the correct name. Passing the option that explicitly disables it brought the breakage back, which means honouring it is the default behaviour.

  • The field is a one byte version, a four byte CRC of the header name, then the UTF-8 name. The CRC lets a reader detect that the field is stale because another tool rewrote the header name
  • Python's zipfile overwrites the header name when it finds this field, which makes the cp437 recovery procedure of section 5 unnecessary
  • However not one of the three tools tested writes the field. Reading it is broadly supported; writing it is rare
  • APPNOTE itself notes the extra field is not needed when bit 11 is used. New archives should go the bit 11 route
  • The practical value of this field is diagnostic. If a received archive has it, you know the original name without guessing

Use tar in a mixed code page environment and diagnosis is harder than with zip.

12. The name and the content are separate problems

An entry was deliberately created inside one archive where the name is UTF-8 and the content is cp949. This section confirms that the combination violates nothing. Diagnosing content encodings is covered in cp949 and UTF-8, the two kinds of encoding error, so here we only establish that the two layers are unrelated.

--- 12-1. name layer and content layer disagree, on purpose ---
  entry name         : [보고서.txt]  bit11=SET
  name bytes (utf-8) : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74
  content bytes      : C7 D1 B1 DB 20 B5 A5 C0 CC C5 CD 0A
  content as utf-8   : '�ѱ� ������\n'
  content as cp949   : [한글 데이터]

--- 12-2. is the content encoding recorded anywhere? ---
  internal_attr = 0x0000     (bit 0 is a text/binary hint only)
  per-entry fields available :
    CRC, comment, compress_size, compress_type, create_system, create_version,
    date_time, external_attr, extra, extract_version, file_size, flag_bits,
    header_offset, internal_attr, orig_filename, volume
  none of them names the content encoding
  • Bit 11 applies to the file name and comment only. The specification nails that down. File contents are not covered
  • Lay out every field an entry owns and there is no slot for a content encoding. One bit hinting text versus binary is all there is
  • So «the name looks fine, the content is probably fine» has no basis. The two layers share no information whatsoever
  • The converse holds too. An archive with broken names can have perfectly intact contents. Extraction restores bytes regardless of names
  • In practice you have to check the two layers separately. Names through the central directory, contents through the extracted bytes

13. A diagnostic order - which case is this archive

A checker was written that runs every judgement above at once. Three values from the central directory settle the classification: the flag, the validity of the name bytes, and the presence of an extra field.

archive                    bit11    ascii  utf8ok 949ok  0x7075 verdict
--------------------------------------------------------------------------------------
A_legacy_cp949.zip         clear    no     no     yes    no    undeclared cp949, breaks off Korean Windows
B_utf8_flagged.zip         SET      no     yes    no     no    declared UTF-8, safe everywhere
C_utf8_noflag.zip          clear    no     yes    no     no    undeclared UTF-8, breaks ON Korean Windows

T_ps_compress.zip          SET      no     yes    no     no    declared UTF-8, safe everywhere
T_python_zipfile.zip       SET      no     yes    no     no    declared UTF-8, safe everywhere
T_wintar.zip               clear    no     no     yes    no    undeclared cp949, breaks off Korean Windows

Put in order, the procedure is this.

  1. List, do not extract. Once wrong names are written to disk you can slide into the unrecoverable cases of section 5
  2. Read bit 11 from the central directory. If it is set the names are UTF-8, and if they still look broken the cause is the reader, not the archive
  3. If it is clear, check byte validity. Valid only as UTF-8, only as cp949, or as both
  4. Look for extra field 0x7075. If it is there no guessing is required; the UTF-8 name is inside it
  5. Do not inspect a single entry. ASCII names have the flag clear, and two encodings can coexist in one archive
  6. Extract after the verdict, and never delete the original archive. With the archive you can always start again

Some byte strings really are valid both ways. Certain sequences decode without error as UTF-8 and as cp949 alike. Names made purely of ASCII are the commonest example, and other overlapping ranges exist. In that situation bytes alone cannot decide. Validity checking narrows the candidates; it does not conclude. The final call ends up being a human reading the name and seeing whether it means anything.

15. What to decide before you distribute

Now the other side of the desk. If you build and distribute archives, what has to be settled in advance? The measurements above yield four items.

DecisionOptionsVerified basisRecommendation

  • The cheapest measure is fixing the build command to one thing. Keep a single script for making archives so nobody picks a tool by hand
  • Second is a pre release check. Read the three values from section 13 and fail the build if any entry has bit 11 clear, and this class of incident stops at the source
  • If you know the recipient uses an old tool, rename to ASCII and put the original names in a manifest. That is more reliable than leaning on the extra field
  • If you can still fix an archive you already shipped, rebuilding it is the answer. Editing only the name field means keeping the local header and the central directory in agreement, and offsets drift easily
  • The sentences for your internal standard are short. «File names in archives are UTF-8 with general purpose bit 11 set. Path separators are forward slashes. Names are normalized to the composed form.» Those three sentences prevent every failure in this article

Closing: covering a blank in the spec with a rule

«Compress it as UTF-8» is half right as advice. Half right because using a tool that sets bit 11 does solve most of it, and half wrong because it hides the fact that ZIP does not mandate a file name encoding. Hide that and you cannot diagnose the next incident.

Restated, what the runs established: a file name inside an archive is a length and a byte string, nothing else. The mechanism for announcing an encoding is one bit, and what to read the bytes as when that bit is clear was never decided by the specification. So tools guess, and the Windows tools apply the system code page while Python applies the DOS default and old unzip applies its own translation table. All three guesses are within spec.

That is also why this is especially frequent in Korea. Files and habits from the cp949 era are still in circulation, and while machines with a 949 system code page exchange files with each other nothing surfaces at all. Because the failure only appears when the receiving side differs, the sender has no way to learn that their archives break. Finding that the tar shipped with Windows today produces exactly such archives is the most practical conclusion here.

There is one thing you can do right now. Open one archive you recently sent outside and read bit 11. If it is set, relax. If it is clear and the names contain Korean, the person who received it is probably looking at broken names right now and simply has not told you.

# ZIP file name encoding diagnostic sheet

## 0. One line

ZIP does not mandate a file name encoding. A name is a byte string, and the only way to declare an encoding is **bit 11** of the general purpose bit flag. What a reader does when the bit is clear differs per tool.

## 1. Three things to look at first (before extracting)

| What | Where | Meaning |
|---|---|---|
| General purpose bit flag, bit 11 | central directory header offset +8, 2 bytes little endian | `0x0800` means UTF-8 declared |
| Raw bytes of the file name field | header +46, for the name length | decide UTF-8 / cp949 validity |
| Extra field `0x7075` | after the name field | if present, the UTF-8 name is stored again |

## 2. Broken shape decision table

| What you see | Sample | Cause | Recovery |
|---|---|---|---|
| Box drawing plus Greek | `║╕░φ╝¡.txt` | cp949 name read as cp437 | yes (re-encode cp437, decode cp949) |
| Lowercase Greek plus symbols | `δ│┤Ω│á∞ä£.txt` | UTF-8 name read as cp437 | yes (re-encode cp437, decode UTF-8) |
| Han tangled with Hangul | `1遺꾧린 留ㅼ텧.xlsx` | UTF-8 name read as cp949 | yes (re-encode cp949, decode UTF-8) |
| Han tangle plus lost extension | `蹂닿퀬__txt` | same, dot eaten by a lead byte | re-extract from the archive |
| Run of replacement characters | `������.txt` | cp949 name read as UTF-8 | yes if not yet saved |
| Latin plus Arabic | `٦¦ۦáýä£.txt` | old tool applied its own table | no, re-extract with another tool |
| More characters than expected | `º¸°í¼­.txt` | single byte code page, invisible character included | yes (re-encode latin-1, decode cp949) |
| Looks fine but cannot be found | `보고서.txt` | name stored in decomposed jamo form | yes, normalize before comparing |
| Extraction aborts | (no files) | undeclared UTF-8 read as a code page | extract with another tool |

## 3. Commands to read the bytes

```
# list only, do not extract
python -c "import zipfile,sys; z=zipfile.ZipFile(sys.argv[1]); [print(hex(i.flag_bits), i.filename) for i in z.infolist()]" archive.zip

# the file name field in hex
python -c "import sys; b=open(sys.argv[1],'rb').read(); i=b.find(b'PK\x01\x02'); n=int.from_bytes(b[i+28:i+30],'little'); print(b[i+46:i+46+n].hex(' ').upper())" archive.zip

# undo it (when the tool applied cp437)
python -c "print('SEEN'.encode('cp437').decode('cp949'))"

# which encodings the name bytes are valid in
python -c "b=bytes.fromhex('BAB8B0EDBCAD'); [print(e, (lambda: b.decode(e))() if True else '') for e in ('utf-8','cp949')]"
```

## 4. Tool behaviour (measured on Windows 10 / ANSI 949)

### Writing side

| Tool | Name bytes | Bit 11 | Separator | Verdict |
|---|---|---|---|---|
| Python 3.13.3 `zipfile` | UTF-8 | sets it (not for ASCII) | `2F` | safe |
| PowerShell 5.1 `Compress-Archive` | UTF-8 | sets it | `5C` spec violation | names safe |
| Windows `tar.exe` (bsdtar 3.5.2) | cp949 | **does not** | `2F` | breaks elsewhere |
| Node.js v22 | no zip archive API in core | not applicable | not applicable | not applicable |
| Info-ZIP `zip` / 7-Zip | not present here, unverified | unverified | unverified | unverified |

### Reading side

| Tool | cp949 + no bit | UTF-8 + bit set | UTF-8 + no bit | `0x7075` |
|---|---|---|---|---|
| Python `zipfile` | applies cp437, breaks | correct | breaks | honours |
| Windows `tar.exe` | correct | correct | extension lost | honours |
| `Expand-Archive` | correct | correct | throws, nothing extracted | honours |
| UnZip 6.00 | breaks | **breaks (ignores the bit)** | breaks | honours |

## 5. Decisions before distributing

- [ ] The building tool is **fixed to one that sets bit 11**
- [ ] Archive creation is wrapped in one script so nobody picks a tool by hand
- [ ] Outbound names are **restricted to ASCII**, or the rule for Korean names is documented
- [ ] Names are **normalized to the composed form** before packing
- [ ] The path separator has been verified as `2F`
- [ ] **Every entry's** flag has been checked (not just the first)
- [ ] A listing or manifest ships alongside to reduce dependence on names
- [ ] The original archive is retained (the only route back)

## 6. Do not

- **Extract before judging** — writing wrong names to disk narrows the recovery path
- **Inspect only the first entry** — ASCII names have the flag clear and mixing is allowed
- **Judge breakage by the presence of an extension** — the dot can vanish into a lead byte
- **Byte edit** just the name field — the local header, the central directory and offsets fall out of step
- «No exception was raised, so it is this encoding» — byte strings valid in both encodings exist
- **Lean on the extra field** with a counterpart on an old tool — one option turns it off
- **Assume the content is fine** because the name looks fine — the two layers are unrelated
