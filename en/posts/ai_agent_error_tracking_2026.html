How to Track AI Agent Mistakes in Production

How to observe non-deterministic, multi-step agent failures and prevent regressions - a practical LLM observability analysis that starts from a community question

Jul 8, 2026 Dev & Infra

Intro: "How Do We Even Know the Agent Messed Up?"

A small team already running several AI agents in production posted a practical question on the developer community hada.io. It boiled down to three things: how do you retrospectively track an agent's mistakes (logs, audit trails, human verification)? How do you balance the principle that "AI proposes, humans decide" against the need for speed? And how do you assign responsibility when multiple agents hand off work sequentially? The team already had role and permission specs and per-task approval badges in place.

The replies converged in one direction: prevention beats after-the-fact tracking. Narrowing what CLI access an agent has in the first place - shrinking the blast radius before anything can go wrong - reduces audit burden in practice, according to the commenters' own experience. What remained unsolved was how to enforce separate CLI restrictions when multiple agents work in sequence.

That answer points the right direction, but it is only half the picture. Good prevention requires first observing what actually fails, and the question of how far to narrow permissions is itself answered by observation data. And a failure mode you have never seen before cannot, by definition, be blocked by an existing prevention rule. Rather than simply restating the hada thread, this piece unpacks the larger topic it points to - how to observe production LLM and AI agent behavior and track failures - from a practical angle: traces, evaluation methodology, the tool landscape, and privacy. Everything here is compiled as of July 2026, based on public material.

1. Why Tracking Is Hard - Non-Determinism and Multi-Step Pipelines

1.1 Same Input, Different Output

Traditional software logging and debugging are built on the premise that the same input yields the same output. LLMs break that premise. Temperature and sampling mean the same prompt can produce a different answer each time, and a silent vendor model-version swap can turn a case that passed yesterday into a failure today. The basic debugging move - reproduce it, then find the cause - gets shaky at the root.

1.2 A Tree, Not a Single Request

An agent is not one question and one answer; it loops through planning, calling a tool, observing the result, and re-planning, often many times. In a multi-agent pipeline, one agent's output becomes the next agent's input, so a single hallucination upstream propagates as a cascading failure downstream. The mistake does not live in one log line - it exists as a causal chain spanning multiple steps.

1.3 Failures That Don't Look Like Errors

A tool call can succeed programmatically (HTTP 200) while the arguments fed into it were themselves hallucinated, producing a quietly wrong result. This kind of tool-parameter hallucination is a different animal from ordinary text hallucination: it is not a visible textual error but a programmatic input - what to query, with what arguments - that is wrong, so the system log alone looks like a normal request. A failure that throws no exception triggers no alert either. That is why black-box monitoring - watching only latency and error rate - does not work for agentic systems.

2. What to Observe - Traces, Spans, and Tool Calls

2.1 Traces and Spans

A concept borrowed from distributed tracing is directly useful here. A trace is the full journey of one user request through the system; a span is a single unit of work within that journey. Recording each step of the agent loop - one LLM call, one tool call, one sub-agent delegation - as a span lets you retrace, tree-shaped, exactly where things went wrong when the final answer looks off. Without this, all that remains is the final input and final output, and the intermediate planning, re-planning, and tool selection vanish into a black box.

2.2 Tool-Call Arguments and Return Values

In practice, the instrumentation with the highest debugging value is often not the final answer text but the arguments and return values of tool calls. Recording which tool was called, with what arguments, how many times, and how the agent folded the result into its next step lets a human retrace exactly why a decision was made. Tool misuse - calling the wrong tool or passing wrong arguments - is widely reported as the single most common agent-specific failure mode.

2.3 Tokens, Cost, and Latency

Operationally, runaway cost is as real a risk as quality problems. A failed tool call that triggers a retry, which fails and triggers another retry, or an agent stuck endlessly "refining" its own output, can burn compute for hours and inflate a bill. Instrumenting token counts, latency, and cost at the span level, and attaching hard caps, turns this kind of runaway into an early alert instead of an outage.

2.4 The Dilemma of Logging Full Prompts and Outputs

For reproducibility alone, logging the full prompt and response verbatim is the most reliable option, since a summarized log is often not enough to reproduce a problem. But this collides head-on with privacy concerns - a tension addressed separately in Section 7.

3. Standardizing Traces - OpenTelemetry GenAI Semantic Conventions

3.1 Why a Standard Is Needed

If field names and structures differ by which framework built the agent, every tool swap or every attempt to consolidate traces across teams demands its own mapping work. The OpenTelemetry GenAI Semantic Conventions are a standard schema defined by the CNCF-backed OTel GenAI working group to solve exactly this. They standardize the attribute names used to record prompts, model responses, token usage, tool and agent calls, and provider metadata, so a span from a LangChain agent looks structurally identical to one from a raw OpenAI API call.

3.2 Core Structure

A single LLM call is represented as a span carrying a gen_ai.operation.name attribute with a value like chat, text_completion, or generate_content (for multimodal). Standard attributes for the requested model name, prompt token count, completion token count, and parameters like temperature attach to that span. Tool calls and inter-agent delegation are handled as their own span types, so within a single trace you can separate "what the model reasoned" from "what a tool actually executed."

3.3 Adoption and Limits

As of early 2026, much of the convention is still in an experimental stage, but multiple observability platforms and clouds - including Datadog, Google Cloud, AWS, and Azure - reportedly already support it. Extensions for multi-agent systems - tracking tasks, actions, agent teams, memory, and artifacts - are under active discussion in the working group. The standard has not fully hardened yet, but adopting this convention as the baseline is still the sensible move if you want vendor-neutral traces today.

4. The LLM Observability Tool Landscape - Three Camps

4.1 Three Types

The market splits roughly into three camps. First, APM extensions: existing infrastructure-monitoring products such as Datadog and New Relic bolt an LLM tab - tokens, latency - onto the same dashboards as infrastructure metrics. Second, AI-native tracing: tools like LangSmith, Langfuse, and Arize Phoenix go deep on trace capture and extend upward into evaluation and drift detection. Third, gateways: tools like Helicone and Portkey sit as a proxy between your app and the LLM provider, adding routing, caching, and cost tracking with minimal code change.

4.2 Comparing the Three

Among the AI-native tracing tools, the strengths diverge clearly.

4.3 How to Choose

If you build on LangGraph and want one platform from development through deployment, LangSmith has the edge. If you want to avoid framework lock-in, or need data sovereignty and self-hosting, Langfuse is closer to the community default. If retrieval quality - context precision, faithfulness, answer relevance - is the core business risk, Phoenix's evaluation-rich workflow fits best. Worth noting: ClickHouse's acquisition of Langfuse has tied its self-hosting story more tightly to a specific database dependency, and managed alternatives like Braintrust have raised significant funding and remain very much in the market - both are variables worth weighing when picking a tool. Whichever you choose, deciding what you actually want to observe should come before the tool choice, not after.

5. Offline Evaluation vs. Online Monitoring

5.1 The Distinction

Offline evaluation runs against a dataset the team fully controls - a golden set with predetermined inputs and expected outputs or grading rubrics. Online monitoring runs against real user traffic, which in most cases has no reference answer at all. Teams typically run these as two separate pipelines: a curated dataset during testing, and messy, reference-free real traces during production.

5.2 Two Different Jobs

Offline evaluation catches known failure modes before deployment. Online monitoring catches novel failures and distribution shifts that the offline suite never anticipated. Neither is sufficient alone: offline-only misses the unexpected inputs real users throw at the system, and online-only means you keep discovering, in production, regressions that could have been caught before deployment.

5.3 Running It as a Loop

The recommended operational pattern is cyclical: validate offline, deploy, collect new failure cases through online monitoring, fold those cases back into the offline golden set, refine the agent, and repeat. Once this loop is in place, LLM operations shift from reacting after an incident to catching problems before they escalate.

5.4 LLM-as-Judge and Its Limits

When grading response quality with no clear right answer, using another LLM as a judge - LLM-as-judge - is widely used, especially at a scale humans cannot grade one by one. But the judge model itself carries bias and consistency issues, so rather than trusting its verdicts blindly, it is safer to pair it with periodic human re-verification on a sample.

6. Collecting Failure Cases and Preventing Regressions

6.1 Classify Failure Modes First

Commonly reported agent-specific failure modes include tool misuse (wrong tool, wrong arguments), infinite loops that spiral into retry storms, hallucination cascades where one agent's error spreads to the next, goal drift away from the original objective, prompt injection, and silent quality degradation that looks fine on the surface while quietly getting worse. Agreeing within the team on what counts as a failure, before deciding what to observe, makes the subsequent trace design far easier.

6.2 Building a Golden Set

A golden set is a reviewed, version-controlled evaluation dataset containing representative inputs plus expected outputs or grading rubrics. It does not need to be huge from the start. Fifty to a hundred examples for a single feature - roughly 40-60 core cases and 15-25 edge cases - catches most regressions without being heavy to run. This dataset is never finished; it grows by continually mining real failure traces from online monitoring - the ones with low judge scores or anomalous trajectories - and folding them in.

6.3 Running It as CI Regression

Pull out a stable core of roughly 30 cases from the golden set and wire them into CI as a regression suite that runs automatically on every PR. When a model update, a prompt edit, or a retrieval-pipeline change causes this suite to flag a drop in accuracy, relevance, or safety, you catch "fixing one thing broke another" at the PR stage instead of after deployment.

7. Privacy - Handling Sensitive Data in Logs

7.1 Why This Matters

Users routinely paste emails, phone numbers, addresses, and sometimes credentials directly into prompts. If an observability tool stores the full prompt and response verbatim into a trace for reproducibility, that personal data sits permanently in the log and trace store. Cumulative GDPR fines since 2018 are reported to already run into the billions of euros, which makes this a real financial risk rather than an abstract one. In healthcare, the moment patient information (PHI) lands in a prompt without a business associate agreement (BAA) in place, that alone can constitute a reportable HIPAA disclosure.

7.2 Redaction Approaches

The standard practice is to detect sensitive data with regex and named-entity recognition (NER), then either mask it irreversibly (anonymization) or tokenize it reversibly when recovery is needed (pseudonymization). Rather than scattering this logic across application code, handling it at a single choke point - a gateway, or a custom PII-redaction processor inserted into the logging pipeline itself - cuts down on the risk of missing a case. The more sensitive the data, the more it is recommended to run the redaction logic inside your own network so the unredacted text never touches the public internet before masking.

7.3 Balancing Against Logging Obligations

The tricky part is that regulation does not only forbid logging - it sometimes mandates it. The EU AI Act imposes a logging obligation (Article 12) on high-risk systems. In other words, "log nothing" is not on the table; the real task is designing what to keep and what to filter out. The compromise observed in practice is to retain redacted traces plus cost and latency metrics for compliance, while applying shorter retention or tighter access controls to highly sensitive fields like raw prompts.

8. Revisiting the hada Debate - Prevention and Tracking Are Not Opposites

8.1 What the Community's Answer Got Right

The hada commenters' point - that narrowing permission scope reduces audit burden - is correct. Whatever an agent cannot do in the first place does not need to be tracked at all. This is an approach that shrinks the blast radius of failure at the system-design stage, before either the offline or online evaluation discussed in Section 5 even comes into play.

8.2 Why Prevention Alone Falls Short

But how far and where to narrow permissions does not settle itself. That answer comes from data about what has actually gone wrong. And a failure mode you have never encountered cannot, by definition, be covered by an existing prevention rule - especially true in an area like prompt injection, where attackers keep finding new paths. Prevention rules are not a fixed answer; they are a living artifact that must be continually updated from observation.

8.3 The Practical Synthesis - Observation Sharpens Prevention

Observability and permission minimization are not two competing options but two halves of the same loop. When a trace surfaces a new failure mode, permission scope and approval gates are narrowed further to block it. This also resolves the hada thread's third question - how to assign responsibility when multiple agents work in sequence. Record each agent's calls as its own span and link them by trace ID, and "who did what, when" becomes an automatic execution record rather than a design document.

9. A Practical Checklist - What to Do Today

9.1 Instrument Traces First

Before choosing an evaluation framework or a tool vendor, add the minimum instrumentation to record each step of the agent loop - LLM call, tool call, sub-agent delegation - as a span. Basing this on the OpenTelemetry GenAI conventions means your trace data survives a future tool swap.

9.2 Set Up a Golden Set and CI Regression

Build a golden set of 50-100 cases from your real workload, and wire roughly 30 stable cases into a CI regression suite that runs on every PR. Periodically fold failure cases surfaced by online monitoring back into this golden set.

9.3 Make Redaction the Default in Your Logging Pipeline

Before turning on full prompt-and-response logging, put sensitive-data redaction into a single default point - the gateway or pipeline - rather than application code. Decide explicitly, as a team, what to keep, balancing logging obligations (such as the EU AI Act) against the principle of minimal collection.
