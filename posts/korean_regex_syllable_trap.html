한글 정규식 함정 - 「아닙니다」 안에 「아니」가 없다

음절 합성, 어미별 안전 패턴, NFC와 NFD, 셸 이스케이프, 가-힣의 한계, 회귀 시험까지 직접 실행한 출력으로

2026-07-29 IT/기술

서론: 검사기는 두 달 동안 「지적 없음」을 반환하고 있었다

본문에 면책 문구가 들어갔는지 확인하는 검사기가 있었다. 규칙은 단순했다. /자문이 아니/ 패턴이 문서에서 발견되면 통과, 없으면 경고. 매일 돌았고 매일 조용했다. 경고가 뜬 적이 한 번도 없었으니 모든 문서에 면책 문구가 잘 들어가 있는 줄 알았다.

실제로는 정반대였다. 그 규칙은 한 번도 매칭된 적이 없었다. 사이트 본문이 전부 합쇼체, 즉 「자문이 아닙니다」였기 때문이다. 규칙이 찾던 「아니」는 「아닙니다」 안에 존재하지 않는다. 검사기는 문서를 성실히 읽고, 규칙을 성실히 돌리고, 성실히 아무것도 찾지 못한 뒤 「지적 없음」을 돌려주고 있었다.

이 사고가 무서운 이유는 결과가 실패가 아니라 성공의 모양을 하고 있었다는 것이다. 예외도 없고, 종료 코드도 0이고, 로그도 깨끗하다. 검사기가 고장 났다는 사실을 알려 줄 신호가 어디에도 없다. 이런 것을 조용한 실패라고 부른다. 그리고 한국어를 다루는 코드에서 조용한 실패는 유독 자주 난다.

원인은 하나다. 영어에서 몸에 밴 습관이 한글에서는 그대로 무너진다. 영어로 advis를 찾으면 advise, advisor, advisory가 한꺼번에 걸린다. 어미가 뒤에 덧붙는 구조라 어간이 항상 부분문자열로 남기 때문이다. 한글은 그렇지 않다. 어미가 붙을 때 앞 글자 자체가 바뀐다. 「아니」에 종결어미가 붙으면 「아니 + ㅂ니다」가 아니라 「아 + 닙 + 니 + 다」가 된다. 두 번째 글자가 다른 글자로 교체되는 것이다.

이 글은 그 원리와, 거기서 파생되는 다섯 가지 함정을 다룬다. 특징이 하나 있다. 모든 주장에 실제로 돌린 출력이 붙어 있다. 설명만 읽으면 「그렇겠지」로 넘어가지만, -1이라는 숫자를 직접 보면 잊히지 않는다.

실행 환경. 아래 모든 출력은 Windows 10 Pro / Node.js v22.16.0 (win32)에서 실제로 실행한 결과를 그대로 옮긴 것이다. 예제는 전부 .js 파일로 저장해 실행했다. 이유는 5절에서 설명한다.

이 글이 다루지 않는 것. 정규식 엔진마다 문법이 다른 문제, 즉 방언과 이식성은 어디서나 동작하는 정규표현식에서 다뤘다. 이 글은 엔진이 아니라 한글이라는 문자 체계 쪽 문제만 파고든다. 두 글은 겹치지 않는다.

1. 「아닙니다」 안에 「아니」가 없는 이유 - 음절은 미리 합성된 한 글자다

먼저 사실 확인부터 하자. 주장이 아니라 출력이다.

node v22.16.0 / win32
--- 1-1. indexOf ---
'아닙니다'.indexOf('아니') = -1
'아닙니다'.includes('아니') = false
'아니다'.indexOf('아니')   = 0
'아니라'.indexOf('아니')   = 0
--- 1-2. 코드포인트 ---
아닙니다 : 아=U+C544 닙=U+B2D9 니=U+B2C8 다=U+B2E4
아니     : 아=U+C544 니=U+B2C8
아니다   : 아=U+C544 니=U+B2C8 다=U+B2E4

「아니다」와 「아니라」에서는 0번 위치에서 바로 찾는다. 그런데 「아닙니다」에서는 -1이다. 코드포인트를 나란히 놓으면 이유가 한눈에 보인다.

  • 찾는 문자열 「아니」 = U+C544, U+B2C8
  • 대상 문자열 「아닙니다」 = U+C544, U+B2D9, U+B2C8, U+B2E4
  • 두 번째 자리가 U+B2C8이 아니라 U+B2D9다. 따라서 연속된 부분열이 성립하지 않는다

1.1 종성이 붙으면 다른 글자가 된다

왜 두 번째 자리가 바뀌었나. 유니코드의 한글 음절 영역(U+AC00~U+D7A3)은 초성·중성·종성의 조합을 산술식으로 미리 계산해 배치한 것이다. 유니코드 표준이 정의하는 합성 공식은 다음과 같다.

음절 코드포인트 = 0xAC00 + (초성인덱스 * 21 + 중성인덱스) * 28 + 종성인덱스

이 식을 거꾸로 돌려 「니」와 「닙」을 분해하면 이렇게 나온다.

--- 1-3. 왜 다른가 (음절 산술) ---
니 U+B2C8 {"초성":2,"중성":20,"종성":0}
닙 U+B2D9 {"초성":2,"중성":20,"종성":17}
종성(받침)이 붙으면 완전히 다른 코드포인트가 된다 → '니' ≠ '닙'

초성(ㄴ)도 같고 중성(ㅣ)도 같다. 다른 것은 종성뿐인데, 종성이 0에서 17(ㅂ)로 바뀌는 순간 코드포인트가 17만큼 이동한다. 문자열 검색기 입장에서 이것은 알파벳 a와 r만큼이나 무관한 두 글자다. 「받침이 하나 붙었을 뿐」이라는 인간의 직관은 코드포인트 배열에 전혀 반영되지 않는다.

1.2 영어와 무엇이 다른가

차이를 표로 정리하면 이렇다. 이 대비가 이 글 전체의 뿌리다.

  • 영어 - 굴절이 문자 추가로 일어난다. advise → advisor. 앞부분 advis는 훼손되지 않고 남는다
  • 한글 - 굴절이 문자 교체로 일어난다. 아니다 → 아닙니다. 두 번째 글자 자체가 다른 글자로 바뀐다
  • 따라서 영어에서 통하는 접두 매칭 전략이 한글에서는 원리적으로 성립하지 않는다
  • 같은 이유로 startsWith, LIKE '아니%', 검색 색인의 전방 일치도 전부 같은 함정을 밟는다

2. 조용한 실패 - 어간만 쓴 규칙은 합쇼체를 한 번도 못 잡는다

1절이 원리라면 2절은 피해 규모다. 다섯 가지 활용형에 대해 나쁜 규칙과 좋은 규칙을 나란히 돌려 봤다.

node v22.16.0 / win32
문장                                             어간만 (BAD)      문자클래스 (GOOD)    받침 열거 (GOOD)
--------------------------------------------------------------------------------------
이 글은 법률 자문이 아닙니다.                        누락 X            매칭 O            매칭 O
이 글은 법률 자문이 아니다.                          매칭 O            매칭 O            매칭 O
이 글은 법률 자문이 아니라 정보 제공입니다.             매칭 O            매칭 O            매칭 O
이 글은 법률 자문이 아님을 밝힙니다.                   누락 X            매칭 O            매칭 O
이 글은 법률 자문이 아녜요.                          누락 X            매칭 O            매칭 O
--------------------------------------------------------------------------------------
어간만 (BAD)              2/5 탐지
문자클래스 (GOOD)          5/5 탐지
받침 열거 (GOOD)           5/5 탐지

쓰인 규칙은 각각 /자문이 아니/, /자문이 아[니닙님녜냐]/, /자문이 아(?:니|닙|님|녜|냐)/다.

2.1 왜 이것이 최악의 실패 유형인가

탐지율 2/5는 「성능이 좀 아쉽다」 수준이 아니다. 실무에서 이 규칙이 어떻게 동작했는지 보면 성격이 달라진다.

  • 공식 문서는 대부분 합쇼체로 쓴다. 즉 실무에서 가장 흔한 형태가 정확히 못 잡는 쪽에 있다
  • 규칙이 걸리지 않으면 검사기는 「위반 없음」이 아니라 사실상 「검사하지 않음」 상태가 된다. 둘의 출력이 같다
  • 검사기가 돌고 있다는 사실 자체가 거짓 안심을 준다. 검사기가 없었으면 사람이 직접 봤을 텐데, 있으니 아무도 안 본다
  • 탐지율 0%가 아니라 40%라는 점이 더 나쁘다. 평서체 문서에서는 가끔 걸리므로 「규칙은 잘 동작한다」는 증거가 주기적으로 생산된다

2.2 규칙을 의심하기 전에 검사기를 의심하라

여기서 배운 실무 원칙이 하나 있다. 어떤 규칙이 오랫동안 한 건도 잡지 않았다면, 그것은 위반이 없다는 뜻이 아니라 규칙이 죽었다는 뜻일 가능성이 높다. 특히 한국어 텍스트라면 더 그렇다. 검사기를 만들 때 매칭 건수를 함께 기록하고, 장기간 0건인 규칙에 경고를 띄우는 장치를 넣으면 이런 사고를 조기에 잡을 수 있다. 8절에서 다룰 회귀 시험이 근본 처방이라면, 이쪽은 값싼 보험이다.

3. 어미별 안전 패턴 - 무엇을 문자 클래스로 열 것인가

그러면 어떻게 써야 하나. 핵심은 받침이 붙는 자리를 미리 열어 두는 것이다. 한국어에서 활용이 일어나는 자리는 대체로 정해져 있으므로, 그 자리를 문자 클래스로 만들면 대부분 덮인다.

찾으려는 표현흔한 활용형위험한 패턴안전한 패턴
아니다 계열 아닙니다 / 아니다 / 아니라 / 아님 / 아녜요 아니 아[니닙님녜냐]
없다 계열 없습니다 / 없다 / 없어요 / 없음 / 없이 없다 없[다습어음이는]
하다 계열 합니다 / 한다 / 해요 / 함 / 하는 하다 (?:합|한|해|함|하)
이다 계열 (서술격) 입니다 / 이다 / 예요 / 임 / 인 이다 (?:입|이|예|임|인)
않다 계열 (부정) 않습니다 / 않다 / 않아요 / 않음 않다 않[다습아음는]
수 있다 / 없다 할 수 있습니다 / 할 수 없다 수 있다 수 (?:있|없)[다습어]

3.1 이 표를 그대로 믿지 말 것

위 표는 출발점이지 완성이 아니다. 한국어 활용형은 나열로 다 덮이지 않는다. 표를 쓰면서 반드시 함께 기억할 한계가 있다.

  • 불규칙 활용은 문자 클래스로 못 덮는다. 「돕다 → 도와」, 「듣다 → 들어」처럼 어간 자체가 변한다
  • 띄어쓰기 변이가 규칙을 뚫는다. 「할 수 있습니다」와 「할수 있습니다」는 다른 문자열이다. 공백 자리는 \s*로 열어야 한다
  • 조사 삽입도 뚫는다. 「자문이 아닙니다」와 「자문은 아닙니다」와 「자문이 결코 아닙니다」가 모두 유효한 문장이다
  • 클래스를 계속 넓히다 보면 오탐이 급증한다. 「아」로 시작하는 무관한 단어가 걸리기 시작한다

3.2 정규식으로 버틸 수 없는 지점

그래서 어느 시점부터는 접근 자체를 바꾸는 편이 낫다. 실무에서 쓸 만한 순서는 이렇다.

  1. 1단계 - 활용하지 않는 핵심 명사만 찾는다. 「자문」, 「면책」처럼 변형이 없는 어휘가 앵커로 쓰기 좋다
  2. 2단계 - 앵커가 걸린 문장 단위로 잘라 그 안에서 부정 표현 여부를 판정한다. 정규식 하나로 문장 전체를 매칭하려 들지 않는다
  3. 3단계 - 정확도가 더 필요하면 형태소 분석기로 어간을 정규화한 뒤 비교한다. 「아닙니다」와 「아니다」가 같은 어간으로 정규화되면 문제 자체가 사라진다
  4. 4단계 - 그래도 남는 애매한 사례는 사람이 확인하도록 목록으로 뽑는다. 자동으로 통과시키는 것보다 낫다

정규식으로 한국어 활용형을 전부 덮으려는 시도는 대체로 실패한다. 규칙이 계속 자라고, 어느 순간 아무도 손대지 못하는 한 줄이 된다. 정규식은 후보를 좁히는 데 쓰고, 판정은 다른 층에 맡기는 것이 오래 간다.

4. NFC와 NFD - 눈에 같은 글자가 같지 않을 때

두 번째 함정은 더 교묘하다. 같은 「한」인데 컴퓨터가 다른 문자열로 보는 경우가 있다. 유니코드 표준 부속서 15가 정의하는 정규화 형식 문제다.

node v22.16.0 / win32
--- 3-1. 길이와 코드포인트 ---
'한'.length              = 1 | U+D55C
'한'.normalize('NFD').length = 3 | U+1112 U+1161 U+11AB
화면 출력은 둘 다: 한 / 한

NFC는 결합된 형태다. 「한」이 U+D55C 한 글자다. NFD는 분해된 형태로, 초성 ㅎ(U+1112) · 중성 ㅏ(U+1161) · 종성 ㄴ(U+11AB) 세 코드포인트로 쪼개진다. 화면에는 둘 다 똑같이 「한」으로 보인다. 눈으로는 절대 구분할 수 없다.

4.1 비교가 전부 실패한다

--- 3-2. 비교가 전부 실패한다 ---
nfc === nfd            : false
'한국'.indexOf(nfd)     : -1
'한국'.normalize('NFD').indexOf('한') : -1
/한/.test(nfd)          : false
/[가-힣]/.test(nfd)      : false
--- 3-3. 정규화하면 해결된다 ---
nfc.normalize('NFC') === nfd.normalize('NFC') : true
'한국'.normalize('NFC').indexOf(nfd.normalize('NFC')) : 0

일치 비교, indexOf, 정규식 테스트, 문자 클래스 검사가 전부 실패한다. 그리고 정규화 한 번으로 전부 해결된다. 문제와 처방이 이렇게 깔끔하게 대응하는 경우도 드물다.

4.2 집합과 정렬도 함께 깨진다

--- 3-4. 정렬·중복제거도 깨진다 ---
Set([nfc, nfd]).size = 2 ← 같은 글자인데 2개
정규화 후 Set.size   = 1
--- 3-5. 파일명 사례 ---
두 파일명이 같은가 : false
NFC 길이 7 / NFD 길이 10
filter(f => f.startsWith('보고서')) 결과 개수 : 1 ← 2개여야 하는데

중복 제거가 안 되고, 파일명 필터가 절반만 걸린다. 「보고서.txt」 두 개 중 하나만 걸러진 것이다. 중복 제거 로직이 조용히 실패하면 원인을 찾는 데 며칠이 걸린다. 눈으로 보면 완전히 같은 문자열이 나란히 있는데 프로그램은 다르다고 우기기 때문이다.

4.3 정규화를 어디서 할 것인가

원칙은 하나다. 외부에서 문자열이 들어오는 경계에서 한 번 정규화하고, 내부는 정규화된 상태라고 가정한다. 곳곳에서 정규화하면 성능도 낭비고, 어디는 하고 어디는 안 하는 구멍이 생긴다.

파일 시스템 목록 읽기필수플랫폼과 프로토콜에 따라 분해형이 섞여 들어올 수 있다
네트워크 수신 / API 응답 파싱필수송신 측이 어떤 형식으로 보낼지 통제할 수 없다
사용자 폼 입력 수신필수입력기와 붙여넣기 경로마다 결과가 다를 수 있다
데이터베이스 저장 직전권장저장 시점에 통일해 두면 조회 조건이 단순해진다
비교·검색 직전차선책동작은 하지만 정규화 누락 지점이 생기기 쉽다
화면 출력 직전무의미비교가 이미 끝난 뒤라 늦다

어떤 형식으로 통일할 것인가. 웹과 저장 계층에서는 대체로 NFC가 무난하다. 문자열이 짧고, 대부분의 시스템이 결합형을 기대하며, 길이 계산도 사람의 직관에 가깝기 때문이다. 다만 초성 검색처럼 자모 단위 처리가 필요한 기능을 만들 때는 그 구간에서만 의도적으로 NFD를 쓰는 편이 편하다. 중요한 것은 형식 선택보다 한 시스템 안에서 하나로 정해 두는 것이다.

5. 셸을 거치면 정규식이 조용히 죽는다

세 번째 함정은 문자 체계가 아니라 계층 경계에서 생긴다. 그런데 결과가 앞의 사고들과 똑같이 조용해서 함께 다룰 가치가 있다.

공백을 지우려고 node -e로 한 줄 실행했다고 하자. 명령을 셸에 넘기는 순간 역슬래시가 한 겹 벗겨지고, 남은 문자열이 자바스크립트 문자열 리터럴로 다시 해석된다. 역슬래시 하나가 두 번 소비되는 것이다. 실제로 돌린 결과다.

$ node -e "console.log(JSON.stringify('\s'))"
"s"

$ node -e "console.log(String(new RegExp('\s+')))"
/s+/

$ node -e "console.log(JSON.stringify('less  space'.replace(new RegExp('\s+','g'),'')))"
"le  pace"

세 번째 줄을 보자. 원본은 less space, 결과는 le pace다. 공백은 그대로 남았고 알파벳 s만 전부 사라졌다. 공백을 지우려던 코드가 정확히 반대로 동작한 것이다.

같은 명령을 Git Bash와 Windows PowerShell 5.1 양쪽에서 실행했고 출력이 동일했다. 특정 셸의 문제가 아니라 계층을 하나 더 거치면 생기는 일반적 현상이라는 뜻이다.

5.1 무엇이 정확히 일어났나

범인은 셸만이 아니다. 자바스크립트 문자열 리터럴 규칙도 공범이다. 파일에 저장해 실행하면 원인이 분리되어 보인다.

node v22.16.0 / win32
--- 4-1. 정규식 리터럴 vs 문자열 생성 ---
리터럴 /\s+/            : /\s+/
new RegExp('\s+')      : /s+/
new RegExp('\\s+')     : /\s+/
--- 4-2. 같은 입력, 세 가지 결과 ---
원본                     : "less  space"
리터럴 사용 (정상)        : "lessspace"
new RegExp('\s+') (파손) : "le  pace"
new RegExp('\\s+') (정상): "lessspace"

정리하면 이렇다.

  • 자바스크립트 문자열 리터럴에서 '\s'는 알려지지 않은 이스케이프라 역슬래시가 버려지고 그냥 's'가 된다
  • 그 문자열로 정규식을 만들면 /s+/가 된다. 공백 문자 클래스가 알파벳 s로 바뀐 것이다
  • 정규식 리터럴 /\s+/는 문자열 리터럴 단계를 거치지 않으므로 안전하다
  • 문자열로 만들어야 한다면 역슬래시를 두 번 써야 한다. '\\s+'
  • 셸을 거치면 여기에 한 겹이 더 필요할 수 있다. 계층마다 한 겹씩 늘어난다

5.2 왜 아무도 눈치채지 못하나

--- 4-3. 한글에서도 같은 일이 난다 ---
원본                   : 자문이 아닙니다
new RegExp('\s') 제거   : "자문이 아닙니다"
리터럴 /\s/ 제거        : "자문이아닙니다"
--- 4-4. 조용한 실패인 이유 ---
던지는 예외 없음. RegExp 생성 성공 : true

한글 문자열에서는 지워야 할 공백이 그대로 남았다. 그리고 마지막 줄이 이 절의 핵심이다. new RegExp('\s+')는 예외를 던지지 않는다. 완벽하게 유효한 정규식 객체가 만들어진다. 다만 당신이 의도한 것과 다른 정규식일 뿐이다. 오류가 없으니 로그도 깨끗하고, 테스트가 없으면 배포까지 그대로 간다.

5.3 실무 규칙

  • 정규식과 한글이 들어간 코드를 셸 인자로 넘기지 않는다. 파일로 저장해 실행한다
  • 문자열에서 정규식을 만들어야 한다면 만든 결과를 한 번 출력해 눈으로 확인한다. console.log(String(re)) 한 줄이면 된다
  • 패턴을 설정 파일이나 데이터베이스에서 읽어 오는 구조라면 역슬래시 이중화 규칙을 문서에 못 박는다
  • 사용자 입력을 패턴에 끼워 넣을 때는 메타문자를 이스케이프한다. 안 하면 오동작을 넘어 성능 사고가 된다
  • 인라인 실행이 불가피하면 작은따옴표로 감싸는 셸 규칙을 쓰되, 그 경우에도 결과를 검증한다

6. [가-힣]가 못 잡는 것과 대신 쓸 것

한글을 검사할 때 거의 반사적으로 쓰는 [가-힣]는 완성형 음절 영역만 가리킨다. 나머지는 전부 빠진다. 아홉 가지 표본으로 확인했다.

구분                 문자       코드포인트                   [가-힣]
------------------------------------------------------------------------
완성형 음절           한        U+D55C                     O
자음 단독            ㄱ        U+3131                     X
모음 단독            ㅏ        U+314F                     X
자모 조합 입력중      ㄱㅏ       U+3131 U+314F              X
NFD 분해 상태        한        U+1112 U+1161 U+11AB       X
옛한글 옛이응         ㆁ        U+3181                     X
옛한글 중성 확장      ힰ        U+D7B0                     X
호환자모 ㅘ          ㅘ        U+3158                     X
반각 한글           ﾠﾡ        U+FFA0 U+FFA1              X

완성형 한 글자를 빼면 여덟 표본이 전부 통과한다. 즉 [가-힣]로 「한글이 아닌 문자」를 걸러 내는 검증기를 만들면, 위 여덟 가지가 모두 한글이 아닌 것으로 판정된다. 조합 중인 입력이나 분해형 파일명이 거부되는 사고가 여기서 나온다.

6.1 대안 두 가지 비교

--- 5-2. 넓게 여는 대안들 ---
구분                 넓은범위    \p{Script=Hangul}
----------------------------------------------------
완성형 음절           O            O
자음 단독            O            O
모음 단독            O            O
자모 조합 입력중      O            O
NFD 분해 상태        O            O
옛한글 옛이응         O            O
옛한글 중성 확장      O            O
호환자모 ㅘ          O            O
반각 한글           X            O

비교한 두 패턴은 다음과 같다.

  • 넓은 범위 나열 - [ᄀ-ᇿ㄰-㆏ꥠ-꥿가-힣ힰ-퟿]. 자모·호환자모·확장 영역까지 손으로 열었다. 여덟 표본을 잡았지만 반각 한글에서 뚫렸다
  • 스크립트 속성 - /\p{Script=Hangul}/u. 아홉 표본을 모두 잡았다. 유니코드 문자 데이터베이스의 Script 속성을 직접 참조하므로 블록 경계를 손으로 관리할 필요가 없다
  • 속성 이스케이프는 u 플래그가 필수다. 빼면 문법 오류가 아니라 다른 의미로 해석되어 또 조용히 틀린다

6.2 개수 세기에서 드러나는 차이

--- 5-3. 한글 개수 세기 비교 ---
대상 문자열 코드포인트 수 : 7
match(/[가-힣]/g)            : 2
match(/\p{Script=Hangul}/gu) : 7

같은 문자열에서 2와 7이 나왔다. 「한글 비율이 몇 퍼센트인가」 같은 지표를 만든다면 어느 쪽을 쓰느냐에 따라 3배 이상 차이가 난다.

6.3 넓게 여는 것이 항상 정답은 아니다

다만 여기서 균형을 잡아야 한다. 목적에 따라 좁은 것이 맞을 때가 있다.

  • 본문에 한글이 섞였는지 탐지하는 용도(다국어 오염 검사 등)라면 넓게 여는 것이 맞다. 놓치면 검사기가 무력해진다
  • 사용자 이름 입력을 검증하는 용도라면 좁게 가는 편이 나을 수 있다. 조합 중인 자모 ㄱㅏ가 이름으로 저장되면 곤란하다
  • 검색 색인을 만든다면 정규화를 먼저 하고, 그다음에 넓은 범위를 쓴다. 순서가 뒤집히면 분해형이 색인에서 누락된다
  • 어느 쪽이든 무엇을 통과시킬지 먼저 문장으로 적고 나서 패턴을 고르는 것이 순서다. 패턴부터 고르면 의도가 사후 정당화된다

7. 길이는 하나가 아니다 - 정규식 바깥의 함정

정규식이 아니어도 같은 뿌리에서 나오는 문제가 있다. 「글자 수」라는 말에 답이 네 개라는 것이다.

node v22.16.0 / win32
대상          .length   [...s].length   byteLength(utf8)   Intl.Segmenter
------------------------------------------------------------------------
한글            2            2                  6                    2
NFD 한글        6            6                  18                   2
abc             3            3                  3                    3
가족 이모지      8            5                  18                   1
한글+영문        5            5                  9                    5

「한글」은 어떤 기준으로 세느냐에 따라 2, 2, 6, 2다. 분해형으로 들어오면 6, 6, 18, 2가 된다. 같은 두 글자인데 저장 단위 길이가 2에서 6으로 뛴다.

세는 방법세는 단위맞는 용도틀리는 경우
s.lengthUTF-16 코드 유닛메모리 추정, 인덱싱분해형·이모지에서 사람의 감각과 어긋난다
[...s].length코드포인트문자 단위 순회분해형에서 여전히 부풀고, 결합 이모지를 쪼갠다
Buffer.byteLength바이트(인코딩 의존)저장 용량, 전송량, 컬럼 크기인코딩을 명시하지 않으면 답이 달라진다
Intl.Segmenter자소 클러스터사용자에게 보이는 글자 수느리고, 로케일 의존이며, 구형 환경에 없다

7.1 저장 용량은 인코딩마다 다르다

--- 6-2. 인코딩별 바이트 ---
'한글' utf8 바이트  : 6 (글자당 3바이트)
'한글' utf16 바이트 : 4

UTF-8에서 한글 한 글자는 3바이트, UTF-16에서는 2바이트다. 데이터베이스 컬럼을 바이트 기준으로 잡는 환경이라면 「10자까지」가 몇 바이트인지를 인코딩과 함께 계산해야 한다. 문자 기준 길이 제한을 그대로 바이트 컬럼에 옮겨 적으면 한글 입력에서 잘린다.

7.2 자르기가 글자를 반토막 낸다

--- 6-3. slice가 글자를 반토막 낸다 ---
NFD 문자열 slice(0,2) : "하" ← 초성+중성만 남아 깨진 글자
NFC 문자열 slice(0,1) : "한"

분해형 문자열을 잘랐더니 종성이 떨어져 나가 「한」이 「하」가 됐다. 미리보기 텍스트를 만들거나 요약을 자를 때 이런 일이 난다. 자르기 전에 정규화하라는 원칙이 여기서도 성립한다. 이모지·국기·가족 이모지까지 안전하게 다루려면 자소 클러스터 단위로 잘라야 한다.

  • 미리보기·요약 자르기 → NFC 정규화 후 자소 클러스터 단위
  • 데이터베이스 컬럼 설계 → 바이트 기준, 인코딩 명시
  • 입력 글자 수 제한 안내 → 사용자에게 보이는 자소 클러스터 기준
  • 해시·서명 대상 → 정규화 형식을 규약으로 고정. 안 하면 같은 글자가 다른 해시를 낳는다

8. 회귀 시험 만드는 법 - 오통과를 잡는 유일한 장치

지금까지의 함정은 전부 조용하다. 예외도 없고 로그도 깨끗하다. 그러면 무엇으로 잡나. 검사기 자체를 검사하는 것 말고는 방법이 없다.

핵심은 시험 항목을 두 종류로 나누는 것이다.

  • MUST_HIT - 이 문장에서는 규칙이 반드시 걸려야 한다. 합쇼체·평서체·연결형·명사형을 각각 넣는다
  • MUST_MISS - 이 문장에서 걸리면 오탐이다. 규칙을 넓히다 보면 여기서 깨진다
  • 둘 중 하나만 있으면 반쪽이다. MUST_HIT만 있으면 규칙을 /./로 만들어도 통과한다

실제로 두 규칙을 같은 시험에 걸어 봤다.

[나쁜 규칙] /자문이 아니/
  [FAIL] MUST_HIT  합쇼체    본 글은 법률 자문이 아닙니다.
  [PASS] MUST_HIT  평서체    본 글은 법률 자문이 아니다.
  [PASS] MUST_HIT  연결형    본 글은 법률 자문이 아니라 일반 정보입니다.
  [FAIL] MUST_HIT  명사형    본 글은 법률 자문이 아님을 알려드립니다.
  [PASS] MUST_MISS 무관 문장  전문가 자문을 받아 작성했습니다.
  [PASS] MUST_MISS 부분 어휘  자문위원회가 심의했습니다.
  => pass 4 / fail 2

[좋은 규칙] /자문이 아[니닙님녜냐]/
  [PASS] MUST_HIT  합쇼체    본 글은 법률 자문이 아닙니다.
  [PASS] MUST_HIT  평서체    본 글은 법률 자문이 아니다.
  [PASS] MUST_HIT  연결형    본 글은 법률 자문이 아니라 일반 정보입니다.
  [PASS] MUST_HIT  명사형    본 글은 법률 자문이 아님을 알려드립니다.
  [PASS] MUST_MISS 무관 문장  전문가 자문을 받아 작성했습니다.
  [PASS] MUST_MISS 부분 어휘  자문위원회가 심의했습니다.
  => pass 6 / fail 0

=== 요약 ===
나쁜 규칙 실패 건수 : 2 ← 회귀 시험이 있었으면 첫날 잡혔다
좋은 규칙 실패 건수 : 0

여섯 줄짜리 시험이 두 달 동안 아무도 몰랐던 결함을 즉시 드러냈다. 서론의 사고는 이 시험 하나면 첫날 막혔을 것이다.

8.1 시험 항목에 반드시 넣을 것

  1. 합쇼체 - 「~습니다 / ~ㅂ니다」. 공식 문서에서 가장 흔하고 가장 잘 놓치는 형태다
  2. 평서체 - 「~다」. 어간이 그대로 남는 경우가 많아 나쁜 규칙도 통과시킨다. 그래서 이것만 넣으면 의미가 없다
  3. 연결형·명사형 - 「~라」, 「~ㅁ을」. 받침 변화가 실제로 일어나는 자리다
  4. 구어체·축약형 - 「~예요 / ~네요」. 사용자 생성 콘텐츠를 다룬다면 필수다
  5. 오통과 표본 3종 - ①규칙과 무관한 문장 ②핵심 어휘가 다른 뜻으로 쓰인 문장 ③앵커 어휘가 다른 단어의 일부인 문장

8.2 검사기를 만들 때의 추가 장치

  • 회귀 시험은 인라인 실행으로 돌리지 않는다. 5절에서 본 이스케이프 사고가 시험 코드에서 나면 시험 자체가 거짓말을 한다. 반드시 파일로 저장한다
  • 일부러 결함을 심어 탐지력을 확인한다. 규칙을 망가뜨렸을 때 시험이 빨간불이 되지 않으면, 그 시험은 아무것도 지키고 있지 않다
  • 규칙별 매칭 건수를 기록한다. 장기간 0건인 규칙은 죽었을 가능성이 높다
  • 표본 문장은 실제 본문에서 가져온다. 상상해서 만든 문장은 실제 문체를 반영하지 못한다
  • 규칙을 고칠 때마다 시험 항목을 먼저 추가한다. 놓친 사례를 발견했다면 그것이 곧 새 시험 항목이다

9. 이 글의 방법으로도 막지 못하는 것

균형을 위해 한계를 밝힌다. 위 처방을 전부 적용해도 남는 문제가 있다.

  • 불규칙 활용 - 어간이 통째로 바뀌는 경우는 문자 클래스로 못 덮는다. 형태소 분석기가 필요하다
  • 띄어쓰기 자유도 - 한국어는 띄어쓰기 오류에 관대해서 실제 문서에는 온갖 변이가 섞인다
  • 의미 판정 - 「자문이 아닙니다」와 「자문이 아니라고 할 수는 없습니다」는 정반대인데 문자열은 비슷하다. 정규식으로는 원리상 구분할 수 없다
  • 형태소 분석기의 비용 - 정확도는 오르지만 사전 관리, 처리 속도, 배포 크기라는 대가가 붙는다. 검사기 하나 때문에 도입할 가치가 있는지는 별개 판단이다
  • 정규화의 부작용 - 드물지만 정규화가 원본 바이트를 바꾸므로, 서명 검증이나 원본 보존이 요구되는 자리에서는 정규화 전 원본을 따로 보관해야 한다
  • Script 속성의 넓이 - \p{Script=Hangul}은 넓어서 좋지만, 좁은 검증이 필요한 화면에서는 오히려 과하다

그러니 이 글의 결론은 「정규식을 잘 쓰자」가 아니다. 정규식이 감당할 수 있는 범위를 알고, 넘어가는 지점에서 다른 도구로 갈아타자는 쪽에 가깝다.

결론: 규칙을 의심하기 전에 검사기를 의심하라

이 글의 출발점은 두 달 동안 조용했던 검사기였다. 원인은 정규식 문법도, 라이브러리 버그도, 인코딩 설정도 아니었다. 한글 음절이 미리 합성된 한 글자라는, 한 줄이면 설명되는 사실이었다. 영어에서 몸에 밴 접두 매칭 습관을 한글에 그대로 옮긴 순간 규칙은 죽었고, 죽었다는 사실을 알려 줄 신호가 없었다.

다시 정리하면 여섯 가지다. ①한글은 어미가 붙을 때 앞 글자가 바뀌므로 어간 매칭이 성립하지 않는다. ②받침 자리를 문자 클래스로 열되, 나열로 다 덮이지 않는다는 것도 안다. ③외부 경계에서 한 번 정규화하고 내부는 정규화됐다고 가정한다. ④정규식을 셸로 넘기지 않고, 만든 정규식을 출력해 확인한다. ⑤[가-힣]는 완성형만이므로 목적에 따라 \p{Script=Hangul}을 고려한다. ⑥그리고 이 전부를 회귀 시험으로 고정한다.

여섯 중 마지막이 가장 중요하다. 앞의 다섯은 지식이고, 마지막은 지식이 잊혀도 버티게 해 주는 구조다. 사람은 반드시 잊는다. 새로 합류한 사람은 애초에 모른다. 시험만이 남는다.

지금 당장 할 수 있는 일이 하나 있다. 한국어 텍스트를 검사하는 규칙 목록을 열어, 최근 3개월간 한 건도 걸리지 않은 규칙이 있는지 보라. 있다면 그 규칙에 합쇼체 문장 하나를 넣어 돌려 보면 된다. 위반이 없어서 조용했던 것인지, 죽어 있어서 조용했던 것인지는 그 한 줄이면 갈린다.

# 한글 정규식 점검 체크리스트

> 출처: braindetox.kr — 한글 정규식 함정, 「아닙니다」 안에 「아니」가 없다
> 표준 근거: Unicode UAX #15(정규화), UAX #29(자소 클러스터), UAX #44(Script 속성)
> 쓰는 법: 한국어를 다루는 검사기·파서·검색 코드를 리뷰하기 전에 위에서 아래로 훑는다.
> 이 파일을 그대로 AI에 붙여 「우리 코드 기준으로 점검해줘」라고 써도 된다.

## 0. 30초 판정 — 아래 중 하나라도 해당하면 아래 전 항목을 본다
- [ ] 한국어 문자열을 정규식이나 `indexOf`로 검사한다
- [ ] 사용자 입력·파일명·외부 API에서 한글이 들어온다
- [ ] 「글자 수」를 세거나 문자열을 자른다
- [ ] 패턴을 설정 파일·환경변수·CLI 인자로 받는다

## 1. 패턴 작성 — 어미를 어떻게 열 것인가
- [ ] 어간만 쓴 패턴이 있는가 (`아니`, `없다`, `하다`, `이다`, `않다`)
- [ ] 받침이 붙는 자리를 문자 클래스나 대안 그룹으로 열었는가
- [ ] 합쇼체(`~ㅂ니다` / `~습니다`)를 명시적으로 넣었는가
- [ ] 명사형(`~ㅁ` / `~음`)을 넣었는가
- [ ] 구어체·축약형이 필요한 서비스인가 (사용자 생성 콘텐츠면 필요)
- [ ] 공백 자리를 `\s*` 또는 `\s+`로 열었는가 (띄어쓰기 변이)
- [ ] 조사 변이를 고려했는가 (`이/은/는/가`)
- [ ] 클래스를 넓힌 만큼 오탐이 늘지 않았는지 확인했는가

### 어미 자리 빠른 참조
| 계열 | 열어야 할 자리 | 최소 후보 |
|---|---|---|
| 아니다 | 둘째 글자 | 니 닙 님 녜 냐 |
| 없다 | 둘째 글자 | 다 습 어 음 이 는 |
| 않다 | 둘째 글자 | 다 습 아 음 는 |
| 하다 | 첫째 글자 | 합 한 해 함 하 |
| 이다 | 첫째 글자 | 입 이 예 임 인 |

### 정규식으로 버틸 수 없을 때의 전환 순서
1. 활용하지 않는 **핵심 명사**만 앵커로 잡는다
2. 앵커가 걸린 **문장 단위로 잘라** 그 안에서 판정한다
3. 정확도가 더 필요하면 **형태소 분석기**로 어간을 정규화한다
4. 남는 애매한 건은 **사람이 볼 목록**으로 뽑는다 (자동 통과시키지 않는다)

## 2. 정규화 — 어디서 한 번 할 것인가
- [ ] 정규화 형식을 하나로 정했는가 (일반적으로 NFC)
- [ ] 파일 시스템 목록 읽기 직후 정규화하는가
- [ ] 네트워크 수신·API 응답 파싱 직후 정규화하는가
- [ ] 폼 입력 수신 직후 정규화하는가
- [ ] DB 저장 직전에 통일하는가
- [ ] 비교·정렬·중복 제거 전에 양쪽이 같은 형식인지 보장되는가
- [ ] 자르기(`slice`, `substring`) 전에 정규화하는가
- [ ] 해시·서명 대상이라면 형식을 **규약으로 고정**했는가
- [ ] 원본 보존이 필요한 자리에서 정규화 전 값을 따로 보관하는가

## 3. 셸·도구 경유 — 역슬래시가 몇 겹인가
- [ ] 정규식을 셸 인자(`-e`, `--pattern`)로 넘기고 있지 않은가
- [ ] 넘긴다면 계층마다 역슬래시가 한 겹씩 늘어난다는 것을 반영했는가
- [ ] 문자열에서 정규식을 만들 때 역슬래시를 두 번 썼는가
- [ ] 만들어진 정규식을 **한 번 출력해 눈으로 확인**했는가
- [ ] 사용자 입력을 패턴에 끼워 넣을 때 메타문자를 이스케이프하는가
- [ ] 회귀 시험 코드를 인라인이 아니라 **파일로 저장**해 돌리는가

### 자가 진단 한 줄
정규식 객체를 만든 직후 그 문자열 표현을 로그로 남긴다.
의도한 패턴과 다르면 그 자리에서 드러난다. 예외는 절대 나지 않는다.

## 4. 문자 범위 — 무엇을 한글로 볼 것인가
- [ ] `[가-힣]`를 쓰고 있다면 **완성형 음절만** 잡는다는 것을 알고 있는가
- [ ] 아래 중 통과시켜야 할 것과 거부해야 할 것을 문장으로 적었는가
  - [ ] 자음·모음 단독 (`ㄱ`, `ㅏ`)
  - [ ] 조합 중인 입력
  - [ ] 분해형(NFD) 문자열
  - [ ] 옛한글 자모
  - [ ] 호환 자모
  - [ ] 반각 한글
- [ ] 넓게 열어야 한다면 `\p{Script=Hangul}`을 검토했는가
- [ ] 속성 이스케이프에 `u` 플래그를 붙였는가 (빠지면 조용히 다른 뜻이 된다)
- [ ] 검색 색인이라면 **정규화 → 범위 검사** 순서인가 (뒤집히면 분해형 누락)

### 목적별 권장
| 목적 | 권장 범위 | 이유 |
|---|---|---|
| 오염·혼입 탐지 | 넓게 (`\p{Script=Hangul}`) | 놓치면 검사기가 무력해진다 |
| 입력값 검증 | 좁게 (`[가-힣]` 등) | 조합 중 자모 저장을 막는다 |
| 검색 색인 | 정규화 후 넓게 | 분해형 유입 대비 |
| 통계·비율 계측 | 넓게 | 좁으면 수치가 몇 배 어긋난다 |

## 5. 길이·자르기 — 어떤 단위로 세는가
- [ ] 「글자 수」의 단위를 정의했는가 (코드 유닛 / 코드포인트 / 바이트 / 자소 클러스터)
- [ ] DB 컬럼이 바이트 기준이라면 인코딩을 명시하고 계산했는가
- [ ] 사용자에게 안내하는 글자 수는 **자소 클러스터** 기준인가
- [ ] 미리보기 자르기가 종성을 떼어내지 않는가
- [ ] 이모지·결합 문자가 섞일 수 있는 필드인가

## 6. 회귀 시험 — 검사기를 검사한다
- [ ] MUST_HIT 항목이 있는가 (걸려야 하는 문장)
  - [ ] 합쇼체
  - [ ] 평서체
  - [ ] 연결형
  - [ ] 명사형
  - [ ] 구어체 (필요 시)
- [ ] MUST_MISS 항목이 3종 이상 있는가 (걸리면 오탐)
  - [ ] 규칙과 무관한 문장
  - [ ] 핵심 어휘가 다른 뜻으로 쓰인 문장
  - [ ] 앵커 어휘가 다른 단어의 일부인 문장
- [ ] 표본 문장을 **실제 본문**에서 가져왔는가 (상상해 만든 문장은 문체가 다르다)
- [ ] 규칙을 일부러 망가뜨렸을 때 시험이 실패하는지 확인했는가
- [ ] 규칙별 매칭 건수를 기록하는가
- [ ] 장기간 0건인 규칙에 경고를 띄우는가

### 시험 골격
```
MUST_HIT  = [합쇼체, 평서체, 연결형, 명사형, (구어체)]
MUST_MISS = [무관 문장, 다른 뜻, 부분 어휘]
결과 = MUST_HIT 전건 매칭 AND MUST_MISS 전건 비매칭
```

## 7. 배포 전 최종 3줄
- [ ] 이 규칙이 **합쇼체 문장 하나**를 실제로 잡는가
- [ ] 이 코드가 **분해형 입력** 하나를 실제로 처리하는가
- [ ] 만들어진 정규식을 **출력해서 봤는가**
