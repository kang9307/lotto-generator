What Is Malloy - The Data Modeling Language That Fixes SQL's Repeated Joins

Looker founder Lloyd Tabb's relationship-declaring language compiles to SQL and runs on engines you already have - compared with dbt, LookML, and Cube, and why semantic models matter again in the AI era

Jul 23, 2026 Dev & Infra

Intro: SQL Still Hurts - Why a Data Modeling Language Again

If you've worked with data for any length of time, you've lived this scene without exception: a "revenue" number that's subtly different on every dashboard, an aggregate quietly doubled by one wrong join, a 200-line stack of CTEs you have to scroll back through just to remember what the query was even trying to answer. SQL is still the lingua franca of data, but it has never been good at letting you declare a relationship or a meaning once and reuse it everywhere.

Malloy, a piece that recently circulated on hada.io (GeekNews), is an open-source language that claims to answer this old pain. Rather than repeat a press release, this analysis verifies the syntax directly against the official docs and repository, places Malloy within the larger "semantic layer" movement, and works out - from my own vantage point - why a language like this is getting fresh attention now that AI agents are the ones touching the data.

1. What Is Malloy - Looker's Founder's Second Language

1.1 Lloyd Tabb, From LookML to Malloy

To understand Malloy, start with who built it. Lloyd Tabb co-founded Looker with Ben Porterfield in 2012 and designed Looker's data modeling language, LookML. LookML was the language that first commercialized the idea of putting metric definitions under version control, and it became the archetype for much of the semantic-layer conversation that followed. After Google acquired Looker in 2019, Tabb began experimenting with a new language alongside a Google team, and that effort became Malloy, released in 2022. In other words, Malloy isn't a hobbyist's side project - it's a second attempt by someone who already pushed a semantic modeling language all the way to commercial scale, informed by that experience.

1.2 The Core Idea, in One Line

Officially, Malloy is "an open source language for describing data relationships and transformations," doubling as a semantic modeling language and a query language. The decisive difference is that it is not a new database or execution engine. Models and queries written in Malloy compile and run directly on SQL engines you're already using, including BigQuery, Snowflake, PostgreSQL, MySQL, Trino, Presto, Databricks, DuckDB, and MotherDuck. It's developed as MIT-licensed open source under malloydata and has passed 2,500 stars on GitHub.

2. SQL's Old Pain - What Was Actually Wrong

2.1 Repeated Joins and Duplicated Logic

SQL is less a language for expressing relationships than a language for re-describing them every single query. The same three-table join gets rewritten this week, next week, and again by every other teammate. SQL itself gives you no way to define a join condition once, in one place, and keep reusing it. The result: join logic gets copy-pasted across dozens of query files, and when the schema changes, you have to hunt down and fix every copy by hand.

2.2 No Semantics - Same Metric Name, Different Number

The deeper problem is that SQL has nowhere to hold "meaning." A metric the organization needs to agree on - "active users," "on-time rate" - still has to be spelled out again in a SELECT clause every time. If analyst A excludes cancellations and analyst B includes them, the same metric name produces a different number on every dashboard. That's not a mistake - it's a structural consequence of SQL never having had a concept of "metric definition" in the first place.

2.3 Long, Unreadable Queries, and the Fan-Out Trap

When joins stack up, aggregates quietly inflate - the fan-out/chasm trap is one of SQL's chronic ailments. Join an orders table to a shipping-events table and run a SUM, and if one order has multiple shipping events attached, revenue gets double-counted. SQL itself gives you no warning. The resulting number looks entirely plausible, which is exactly why it takes so long to notice it's wrong.

3. Malloy's Approach - Declare Relations as a Model, Reuse Them

3.1 source and extend - Define Once, Use Forever

Malloy's starting point is source. You define a source pointing at a table, then bundle the measures, dimensions, and joins that belong to it inside an extend block. Here's the pattern the official documentation shows:

source: airports is duckdb.table('airports.parquet') extend {
  measure:
    airport_count is count()
    avg_elevation is elevation.avg()
}

A source defined this way becomes a reusable model living in a single file. Anyone who later writes a query against it never has to re-litigate what airport_count actually counts.

3.2 measure - Sealing a Metric Behind a Name

A metric like "on-time rate" - which in SQL would demand a repeated CASE WHEN and filter every time - only needs to be defined once in Malloy, then called by name. The official repository's own example makes exactly this point.

measure: on_time_rate is
  count() { where: cancelled = 'N' and diverted = 'N' and arr_delay < 15 }
  /
  count() { where: cancelled = 'N' and diverted = 'N' }

The business logic of what counts as cancelled, diverted, or delayed gets fixed in exactly one place. From then on, anyone just calls on_time_rate, and changing the definition in this one spot propagates to every query that uses it.

3.3 join_one / join_many - Carving Joins Into the Model, Blocking Fan-Out at the Language Level

join_one: carriers with carrier
join_many: flights2 on code = flights2.origin

Declare a join once inside a source definition, and later queries never need to restate the join key - they just reference the related field by name. More important is how aggregation itself works. Malloy computes aggregates using symmetric aggregation, ensuring they don't get double-counted even across joined tables. That means fan-out inflation is blocked at the language level, no matter how many joins are stacked - a problem SQL leaves for the developer to defend against manually with DISTINCT or subqueries.

3.4 run and nest - A Query Inside a Query, Several Groups in One Result

run: airports -> {
  group_by: state
  aggregate: airport_count
  nest: by_facility_type is {
    group_by: fac_type
    aggregate: airport_count
  }
}

The -> pipeline after run: puts the flow of data from source to query directly into the code's shape. nest expresses, in a single block, what SQL would have needed multiple separate queries or a gnarly GROUP BY ROLLUP to do: carrying subgroup detail inside one result. The output itself comes back nested rather than flat, so the relationship between the outer group and the subgroup survives in the result itself. A query you've already written can be saved as a view and refined further by appending + { }. None of these individual syntax pieces is flashy new technology. They simply move what SQL made you rewrite from scratch every time toward "define once, reuse by name." That "simply" compounds - dozens of query files collapse into one model and a handful of short calls.

4. Compiling to SQL - A Layer, Not a New Engine

The Malloy team describes the language not as a replacement for SQL but as a layer on top of it, drawing the comparison to JavaScript and TypeScript. Just as TypeScript ultimately compiles to JavaScript to run in the browser, Malloy ultimately compiles to SQL tailored to whichever database you're targeting. This design matters most in terms of adoption cost: you don't need a new database or a new execution cluster. You simply lay Malloy model files on top of the BigQuery, Snowflake, Postgres, or MySQL you're already running, and locally you can query Parquet and CSV files directly through DuckDB with no server at all. Installing the VS Code extension gets you a schema explorer, a visual query builder, and result previews right inside the editor.

5. Malloy Within the "Semantic Layer" Movement - Compared With dbt, LookML, and Cube

5.1 Lineage - Three Branches of Looker's Legacy

The idea of "define a metric once, reuse it everywhere" is not new by itself. LookML was the archetype that commercialized it, and the semantic-layer movement that followed split into several branches. dbt layers a Semantic Layer on top of its transformation pipeline, defining metrics in YAML and serving them through the dbt Cloud API. Cube is a headless semantic layer that bundles definition and serving together, aimed at APIs, embedded analytics, and AI-agent integration. Malloy shares this lineage while taking a different path: it's an independent open-source language, not tied to any specific BI product or transformation framework.

5.3 A Sober Look

A fair counterpoint raised in the hada discussion is that an existing language like C# LINQ already offers a similar declarative query experience with broader database support. Malloy's real differentiator isn't that it invented something wholly new - it's that it bundles semantic modeling and querying into one compact language and lays the result directly on top of the SQL ecosystem you already have. Each individual piece isn't unfamiliar; the way it's assembled is.

6. What Actually Gets Better

Reuse: define measures, dimensions, and joins once in a source, and every subsequent query inherits that definition - nobody has to reinvent join conditions and filter logic each time. Consistent metrics: because something like on_time_rate is defined in exactly one place, the structural cause of dashboards showing different numbers largely disappears; change the definition once and it propagates to every query using it. Nested results: nest lets you carry subgroup detail inside one query result, cutting down on the multiple round-trip queries and application-side re-joining that SQL would have required. Readability: symmetric aggregation means you never have to hand-defend SUM or COUNT across stacked joins, so the query itself plainly states what it's computing - a reviewer can read the intent directly instead of decoding a pile of subqueries.

7. Limits and Adoption Barriers

Ecosystem: SQL carries decades of tooling, tutorials, and a talent pool. Malloy, released in 2022, has the VS Code extension and malloy-composer as its main tools, and its third-party BI integrations and community size still don't compare to SQL's or dbt's. Learning curve: a team has to relearn a whole new vocabulary - source/extend, measure/dimension, join_one/join_many, run/nest. Teams that already know SQL well are the ones most likely to resist "why learn a new language at all." No team standard yet: a semantic model needs an owner and ongoing maintenance; without someone or some process to enforce it, the model files risk becoming their own new spaghetti. Existing SQL assets: for an organization that already has hundreds of views, stored procedures, and BI dashboards built in SQL, migrating them into Malloy models is itself a cost. Because Malloy is designed to sit on top of SQL rather than replace it, incremental adoption is possible - but a full migration is its own project-scale decision.

8. Why Semantic Models Matter Again in the AI Era

As I noted in my recent analysis of the Wes McKinney interview and in my analysis of "Data Is Your Only Moat", the cheaper AI makes writing code, the more the layer of judgment - what to build, what the correct definition even is - matters. A semantic model is precisely that judgment, fixed in code.

Point an LLM straight at a raw database schema, and it has to re-infer SQL every single time - rewriting joins, redefining metrics from scratch. Along the way, the same mistakes recur: referencing a column that doesn't exist, a wrongly wired join that inflates numbers through fan-out, a metric definition that drifts subtly from one query to the next. The resulting SQL looks syntactically fine, which makes it that much harder to notice it's wrong.

Projects in the Malloy ecosystem, such as malloyyo, answer this directly. They serve a semantic model already defined in Malloy to AI agents over MCP (Model Context Protocol), so the agent requests already-validated measures, dimensions, and joins by name instead of writing SQL from scratch. The scope an AI can even reach is bounded inside the model, and the computation logic gets reused already validated once - so the result is closer to "structurally correct" than merely "correct by luck."

My own reading is this: the thesis that competitive edge migrates to the definitions and judgment stacked on top, as models and code generation get cheaper, is especially sharp in the data domain. A semantic modeling language like Malloy is getting fresh attention in the AI era not because it adds new features, but because it's a tool for building the "already-agreed-correct definition" an AI can lean on.

9. What Team Fits, and How to Start

9.1 What Team Fits

Organizations where multiple analysts compute the same metric differently, or where numbers drift slightly between dashboards. Teams that repeatedly get burned by fan-out on heavily-joined schemas. Teams that want to open data access to an AI agent while still controlling how accurate the results are. Conversely, if your queries are one-off and you have no bandwidth for team-wide standardization, the payoff may not be large right now.

9.2 How to Start - Locally With DuckDB

The barrier to entry is low. Install the Malloy extension for VS Code, and write a single source in a .malloy file pointing at a local Parquet or CSV file via duckdb.table() - that's enough. No separate server, cluster, or account required; you can define a model and run a run: query straight from your laptop and see the result immediately. Once you get a feel for it, the same model definition extends directly onto a real production engine like BigQuery or Postgres.

Conclusion

Malloy isn't a language trying to push SQL out - it's an attempt to fill in, with a compact syntax, what SQL was never good at in the first place: reusable relationships, consistent metrics, safe aggregation. Layer together its history - a second design by someone who already pushed a semantic modeling language to commercial scale - its architecture of sitting on top of SQL rather than replacing it, and its timely usefulness as a source of validated definitions for AI agents to lean on, and Malloy reads as more than a one-off experiment - it's a point in a real movement. Still, the adoption barriers of ecosystem maturity and team standardization are real, and rather than a full rollout, it's more reasonable to start with a lightweight local experiment on DuckDB, aimed at the team that keeps hitting fan-out and metric-inconsistency pain. As of July 2026 it's too early to say whether this language wins the semantic-layer debate. What is clear is that it names SQL's old pain accurately.
