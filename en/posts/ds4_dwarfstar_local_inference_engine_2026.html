Context — Expanding from Single-Model Focus to Multiple Frontier Families

DwarfStar 4 (ds4), the open-source local inference engine authored by Redis creator Salvatore Sanfilippo (antirez), has formalized its architectural documentation on dwarfstar.sh. Originally engineered specifically to run the 284-billion-parameter DeepSeek V4 Flash mixture-of-experts (MoE) model on consumer workstations, ds4 has expanded its scope to support additional frontier open-weight families: GLM 5.x (GLM 5.2 and GLM 5.3 Flash) and Qwen3.8 Flash Next.

Attempting to execute massive MoE architectures on local machines invariably collides with severe hardware boundaries in memory bandwidth and physical capacity. Hundreds of billions of parameters cannot reside inside a 128GB workstation without aggressive quantization, and standard serving stacks are fundamentally architected for multi-node cloud clusters. ds4 approached the problem from the opposite constraint, targeting high-memory Apple Silicon Macs, Linux CUDA machines, and AMD ROCm setups. Foundational hardware trade-offs in local model execution are explored in our local LLM running guide and Apple Silicon unified memory analysis.

As an engine once laser-focused on a single architecture embraces multiple frontier open-weight models, developers must examine how its core design philosophy, kernel scheduling, and memory allocation adapt to these new constraints.

Design Principles — A Narrow Optimization Engine Rather than a Generic Runner

The documentation draws an unambiguous line: ds4 is deliberately not a generic GGUF runner. Unlike frameworks such as llama.cpp or Ollama that aim to load arbitrary user-converted model files across the broader open-source ecosystem, ds4 restricts itself to an opportunistic subset of model families and exclusively ingests project-validated GGUF layouts.

  • The engine exclusively loads GGUF layouts verified end-to-end by the project; generic community conversions will fail to load.
  • Underlying C kernels and acceleration backends (Metal, CUDA, ROCm) are tailored directly to the exact attention formulations of supported models.
  • Supported architectures are rigorously validated against official upstream model outputs layer by layer.

This narrow-on-purpose strategy trades broad ecosystem generality for deep hardware efficiency. By bypassing generic tensor abstraction layers, ds4 implements attention mechanisms and sparse MoE routing directly in specialized C routines.

Asymmetric 2-Bit Quantization and MoE Compression Structure

The technical mechanism allowing massive models to operate inside workstation memory footprints is asymmetric 2-bit quantization. In MoE architectures, only a tiny fraction of routed experts participate in generating any given token. ds4 exploits this sparsity aggressively.

The vast majority of routed experts are compressed down to 2-bit representations (q2), dramatically shrinking total weight volume. Concurrently, critical shared paths—the backbone layers through which every token must flow—and key attention projections maintain higher precision. The project describes this balance as compressed, not lobotomized. Consequently, a 284-billion-parameter network fits within 96GB to 128GB of memory while preserving foundational reasoning capacity.

Weight bundles in download scripts follow project-tuned quantization profiles such as ds4f-q2, glm53-q2, and qwen38-q2, with additional importance-matrix tuned builds available for PRO-class models.

KV Cache as a Disk Citizen — SSD Persistence and Prefill Bypass

In agentic coding workflows, repeated prompt evaluations represent a major performance bottleneck. Evaluating tens of thousands of tokens of repository context during every turn wastes immense time and memory bandwidth.

ds4 elevates the key-value (KV) cache to a first-class disk citizen. The engine computes the SHA1 hash of the rendered prompt prefix, using it as an index key to serialize and persist long KV prefixes directly to SSD. As demonstrated in terminal sessions:

When the engine restarts, if an incoming prompt matches an existing prefix hash, the model skips the entire prefill phase and immediately maps the serialized KV cache from disk into working memory. Even after complete application restarts, sessions resuming with thousands of lines of context respond instantly. One Engine, Three Interfaces — CLI, Server, and Native Agent

A distinctive architectural property of ds4 is that three interaction modalities operate concurrently over a single underlying C engine, sharing identical model weights and KV cache state:

  • ./ds4: An interactive terminal chat CLI with built-in commands like /read, /think, and /ctx.
  • ./ds4-server: A local HTTP API server designed to expose inference endpoints with customizable context lengths like --ctx 100000.
  • ./ds4-agent: A native coding agent capable of persistent multi-turn file inspection and tool execution.

Notably, ./ds4-server natively speaks both OpenAI-style endpoints (/v1/chat/completions, /v1/responses) and Anthropic-style endpoints (/v1/messages). Developers can redirect external coding agents such as Claude Code, OpenAI Codex CLI, OpenCode, or Pi to local ds4 endpoints simply by modifying their base URL configurations. Desktop tool integration patterns are similarly discussed in our analysis of DeepSeek Harness.

Benchmark Analysis — Evaluating Prefill and Generation Separately

Evaluating local inference strictly by output token generation rate is misleading. In agentic workloads, prefill throughput—how quickly the engine ingests codebase context—dominates practical responsiveness. Upstream ds4 benchmarks report prefill and generation metrics independently:

  • M5 Max (128GB, Q2, 2,048 tokens): Prefill 790.2 t/s, Generation 39.4 t/s.
  • M5 Max (128GB, Q2, 65,536 tokens): Prefill 398.5 t/s, Generation 27.6 t/s.
  • DGX Spark (128GB, Q2, 2,048 tokens): Prefill 825.8 t/s, Generation 18.1 t/s.
  • DGX Spark (128GB, Q2, 65,536 tokens): Prefill 823.0 t/s, Generation 13.8 t/s.

These figures illuminate fundamental architectural differences. Apple Silicon unified memory sustains high generation throughput (27.6 t/s at 65K context). Conversely, NVIDIA DGX Spark demonstrates remarkable prefill scaling, maintaining over 823 t/s even across 65,536 tokens. At reference 32K context, M5 Max achieves 34.4 t/s generation and 557 t/s prefill, compared to 14.4 t/s generation and 856 t/s prefill on DGX Spark GB10.

Build and Execution Workflow — Compiling by Backend and Safe Commands

Written in clean C, ds4 requires no heavy framework dependencies. The documented build and setup workflow proceeds in straightforward steps.

Weight retrieval uses the project script targeting verified profiles:

git clone https://github.com/antirez/ds4
                    cd ds4 && ./download_model.sh ds4f-q2

Compilation is directed by specific make targets tailored to host accelerators:

make              # macOS Metal
                    make cuda-spark   # Linux NVIDIA DGX Spark
                    make cuda-generic # Linux generic CUDA
                    make strix-halo   # Linux AMD Strix Halo
                    make cpu          # CPU-only for diagnostics

Execution can initiate an interactive terminal chat or launch a persistent API server:

./ds4
                    ./ds4-server --ctx 100000
                    ./ds4 -m gguf/GLM-5.3-Flash-Q2.gguf --ctx 32768
                    ./ds4 --ctx 8192 --prefill-chunk 1024

External client integration points are routed through standard HTTP API endpoints:

# OpenAI-compatible completions:
                    POST /v1/chat/completions
                    # Anthropic-compatible messages:
                    POST /v1/messages
                    # Responses endpoint:
                    POST /v1/responses
